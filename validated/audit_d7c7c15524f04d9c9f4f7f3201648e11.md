### Title
SignableTransaction trusts attacker-supplied `ReceivedOutput` value, producing signatures for transactions with forged input amounts - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Connext bug derived a price from `balanceOf`, a value an attacker can inflate by donating tokens, instead of the canonical pool reserves. The analog in Serai's in-scope Bitcoin code is `SignableTransaction::new` / `SignableTransaction::multisig`: the value and outpoint of each input are taken verbatim from a `ReceivedOutput`, which is constructible from untrusted bytes via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122`). The only authenticity check performed before signing is that the tweaked key maps to the claimed `script_pubkey` (`send.rs:277`); the claimed `value` is never verified against any canonical source. Like `balanceOf`, it is a caller-supplied balance treated as ground truth.

### Finding Description
`ReceivedOutput` bundles three attacker-controllable fields: `offset`, `output` (a `TxOut` with `value` and `script_pubkey`), and `outpoint` (`networks/bitcoin/src/wallet/mod.rs:90-97`). `ReceivedOutput::read` deserializes all three without validation (`mod.rs:122-134`).

`SignableTransaction::new` uses `input.output.value` as the input amount for funding and change/fee computation (`send.rs:175`, `send.rs:228-232`) and stores the claimed `TxOut`s as `prevouts` (`send.rs:253`). `SignableTransaction::multisig` checks only `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` (`send.rs:277`) — parity with the pool check the report recommends but for the script only, not the amount. `TransactionSignMachine::sign` then commits to these fabricated `prevouts` via `Prevouts::All` in the BIP-341 sighash (`send.rs:375-386`), and BIP-341 binds each prevout's full `TxOut` (amount + script) into the signed message.

An unprivileged party who can feed bytes to `ReceivedOutput::read` (or otherwise inject a `ReceivedOutput`) can therefore supply an output whose `script_pubkey` legitimately belongs to the multisig but whose `value` is arbitrarily inflated or deflated. The consistency check passes because it validates only the script, exactly mirroring how `balanceOf` reflects donations rather than reserves.

### Impact Explanation
Every prevout amount is committed into the sighash the threshold group signs. A forged amount means:

- The produced signatures are for a transaction whose prevout commitments do not match the real UTXOs, so the fully-signed transaction is invalid and unbroadcastable — the group signs an unintended message and the attempted spend fails after signing effort and preprocesses are consumed.
- The change/fee math is corrupted: an inflated `value` creates change outputs and payments exceeding the real input total (the difference being unbacked), while a deflated `value` diverts the difference into miner fees or silently drops change. If any consumer treats `SignableTransaction::fee()` / output values as authoritative accounting, phantom balance is reported.
- This is "funds reported received/available that are not spendable": the claimed input balance does not exist on-chain.

### Likelihood Explanation
Reachability requires an attacker to influence the bytes fed to `ReceivedOutput::read` or the `Vec<ReceivedOutput>` passed to `SignableTransaction::new`. The scanner itself (`scan_transaction`, `mod.rs:199-214`) produces honest values, so the attack requires a deserialization path over untrusted data — permitted under the rules but narrower than a purely on-chain trigger. A wrong offset is detected by the script check; a wrong value is not detected at all. Severity: Medium — deterministic signing of an invalid/unintended transaction and corrupted fee/change accounting, but no direct theft of correctly-recorded funds.

### Recommendation
Validate each input against a canonical source rather than trusting the deserialized `TxOut`: in `SignableTransaction::multisig` (or `new`), re-derive the expected output for each `outpoint` from the UTXO set / scanner eventuality record, or at minimum verify `output.script_pubkey` matches and that `output.value` equals the value recorded when the output was scanned — the analogue of querying `getReserves()` instead of `balanceOf`. Alternatively, store only `(offset, outpoint)` in `ReceivedOutput` and fetch the `TxOut` from the chain at spend time.

### Proof of Concept
1. Serialize a `ReceivedOutput` whose `offset = Scalar::ZERO`, `outpoint` references a real UTXO paying to the multisig's `p2tr_script_buf(group_key)` script, but whose `output.value` is inflated (e.g., real UTXO is 10,000 sats; claim 1,000,000 sats).
2. Feed the bytes to `ReceivedOutput::read` — accepted (`mod.rs:122`).
3. Call `SignableTransaction::new(vec![forged], payments, change, None, fee_rate)` — the funding check passes on the phantom 1,000,000 sats (`send.rs:215`), and an oversized change output is created (`send.rs:230`).
4. `multisig(&keys)` returns `Some` because `p2tr_script_buf(keys.offset(ZERO).group_key())` equals the real script (`send.rs:277-282`).
5. `preprocess`/`sign`/`complete` produce threshold signatures committing, via `Prevouts::All` (`send.rs:375`), to the forged prevout amount — a BIP-341 sighash that no valid blockchain state can satisfy. The signed transaction is rejected by every Bitcoin node, and the change/fee values were computed from funds that do not exist.
