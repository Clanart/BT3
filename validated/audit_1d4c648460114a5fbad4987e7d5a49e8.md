### Title
Reward distribution in `BaseRewardPoolV2`/`BaseRewardPool` can be instantly diluted or extracted via deposit/withdraw front-running around `queueNewRewards` - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2._provisionReward` (also mirrored in `BaseRewardPool` and `vlMGPBaseRewarder`) distributes any newly queued reward instantaneously and pro-rata over `totalStaked()` at the exact moment `queueNewRewards`/`donateRewards` is called, without any streaming/vesting over time. Because deposits and withdrawals into the corresponding `MasterMagpie` pool are unrestricted and immediate (no cooldown, no minimum staking duration), an unprivileged wallet can watch for a large, predictable reward injection (e.g. `WombatStaking.harvest()` or the bribe/vote flow that calls `queueNewRewards`) and front-run it with a large `deposit`, then `withdraw` immediately afterward, capturing a share of the reward proportional only to size, not to time-at-risk — diluting the genuine long-term stakers exactly as described in the referenced Vault `exchangeRate` front-running report.

### Finding Description
`_provisionReward` computes: [1](#0-0) 

`rewardInfo.rewardPerTokenStored` jumps by `_amountReward * 10**decimals / totalStaked()` in a single call, immediately usable by every account currently staked, regardless of how long they have been staked. There is no time-based streaming (unlike typical `duration`-based Synthetix-style reward pools) and no snapshot/checkpoint mechanism that would exclude very recent deposits from a specific reward injection.

The reward-triggering call is externally observable/predictable: `WombatStaking.harvest()` is a public, unrestricted function that ends up calling `_toMasterWomAndSendReward` → `_sendRewards` → `IBaseRewardPool(_rewarder).queueNewRewards(...)`: [2](#0-1) [3](#0-2) 

Similarly, the `vote()`/bribe flow queues rewards to rewarders based on harvested bribe amounts: [4](#0-3) 

Because pending WOM/bonus-token balances accrued in Wombat's underlying `MasterWombat`/pools are visible on-chain before `harvest()` is called, an attacker can estimate the size of the incoming reward injection just like the referenced report's attacker estimates the Vault's `exchangeRate` change from public pool P&L.

`MasterMagpie._deposit`/`_withdraw` place no restriction preventing an attacker from depositing right before, and withdrawing right after, a `harvest()`/`queueNewRewards` call: [5](#0-4) 

Sequence for Bob (attacker):
1. Bob observes unclaimed WOM/bonus rewards accumulating in `MasterWombat` for a given `_lpToken` pool that are about to be harvested (via a public `harvest()` call or `vote()`).
2. Right before that harvest/vote transaction, Bob calls `MasterMagpie.deposit(stakingToken, largeAmount)` (or the pool helper's `deposit`), which internally calls `_deposit`, setting `user.rewardDebt` based on the *pre-harvest* `accMGPPerShare`/`rewardPerTokenStored`.
3. The harvest/vote transaction executes, calling `queueNewRewards`, which instantly bumps `rewardPerTokenStored` for the WOM/bonus reward token proportional to `totalStaked()` — Bob's freshly deposited large balance is included in `totalStaked()` and thus dilutes/captures a share of the reward.
4. Bob immediately calls `withdraw`/`multiclaim` to harvest his disproportionate share of `earned()`, then withdraws his principal, having borne effectively zero time-at-risk.

This exactly parallels the referenced Vault bug: a predictable, discretely-jumping accounting value (`exchangeRate` in the report vs. `rewardPerTokenStored` here) that a large flash-style deposit can capture before immediately exiting, diluting long-term participants' already-accrued rewards.

### Impact Explanation
This allows theft of already-accrued, unclaimed WOM/bonus yield that rightfully belongs to genuine long-term stakers of a Wombat pool — value is transferred from honest depositors to the attacker with a single-block risk-free deposit/withdraw sandwich. This falls under "theft or permanent freezing of unclaimed yield," a directly reachable outcome for any unprivileged wallet with capital and no special role, satisfying the required impact bar.

### Likelihood Explanation
Likelihood is high: `WombatStaking.harvest()` is a permissionless, callable-by-anyone function, so the reward-injection event is not gated behind privileged roles and its timing/size can be triggered or anticipated by the attacker themselves (the attacker can even call `harvest()` right after depositing, rather than waiting for someone else to). No cooldown or minimum holding period exists on `MasterMagpie` deposits/withdrawals, and the underlying `MasterWombat` pending rewards are public/queryable in advance, making the profit estimate low-risk and mechanical, exactly as in the cited report's PoC steps.

### Recommendation
- Stream newly queued rewards linearly over a fixed duration (e.g., add a `periodFinish`/`rewardRate` mechanism similar to Synthetix `StakingRewards`) instead of applying the entire `_amountReward` to `rewardPerTokenStored` in one atomic step, so a deposit immediately before a harvest cannot capture a full lump-sum's worth of rewards.
- Alternatively, snapshot `balanceOf` prior to the block/transaction in which `queueNewRewards` executes, or impose a minimum staking duration/cooldown between `deposit` and `withdraw`/`getReward` eligibility for a given reward epoch.
- Consider restricting who/when `harvest()`/`vote()` can be triggered relative to deposit/withdraw ordering (e.g., disallow claiming rewards accrued in the same block/transaction as a deposit).

### Proof of Concept
1. Attacker monitors `MasterWombat.pendingTokens(pid, wombatStaking)` for a target `_lpToken` pool to estimate the WOM reward about to be harvested via `WombatStaking.harvest(_lpToken)`. [2](#0-1) 
2. Attacker calls the pool helper's `deposit`/`depositLP`, which routes to `MasterMagpie.depositFor`/`_deposit`, staking a large amount and recording `rewardDebt` at the current (pre-harvest) `accMGPPerShare`. [6](#0-5) 
3. Attacker (or anyone) calls `WombatStaking.harvest(_lpToken)`, which triggers `_toMasterWomAndSendReward` → `_sendRewards` → `queueNewRewards`, instantly increasing `rewardPerTokenStored` proportional to `totalStaked()` at that moment (which now includes the attacker's large deposit). [1](#0-0) 
4. Attacker calls `MasterMagpie.withdrawFor`/`withdraw` and `multiclaim` to collect the disproportionate reward share and remove the principal, completing the extraction within one or two transactions with no meaningful holding period. [7](#0-6)

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function _sendRewards(
        address _lpToken,
        address _rewardToken,
        address _rewarder,
        uint256 _amount
    ) internal {
        if (_amount == 0) return;
        uint256 originalRewardAmount = _amount;

        if (!isPoolFeeFree[_lpToken]) {
            for (uint256 i = 0; i < feeInfos.length; i++) {
                Fees storage feeInfo = feeInfos[i];

                if (feeInfo.isActive) {
                    address rewardToken = _rewardToken;
                    uint256 feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR;
                    _amount -= feeAmount;
                    uint256 feeTosend = feeAmount;

                    if (feeInfo.isMWOM && rewardToken == wom) {
                        if (smartWomConverter != address(0)) {
                            IERC20(wom).safeApprove(smartWomConverter, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IConverter(smartWomConverter).smartConvert(feeAmount, 0);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        } else {
                            IERC20(wom).safeApprove(mWom, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IMWom(mWom).deposit(feeAmount);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        }
                    }

                    if (!feeInfo.isAddress) {
                        IERC20(rewardToken).safeApprove(feeInfo.to, 0);
                        IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
                        IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
                    } else {
                        IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
                        emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
                    }
                }
            }
        }

        IERC20(_rewardToken).safeApprove(_rewarder, 0);
        IERC20(_rewardToken).safeApprove(_rewarder, _amount);
        IBaseRewardPool(_rewarder).queueNewRewards(_amount, _rewardToken);
    }
