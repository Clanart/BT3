## Analysis

The seed report's core issue is: **an operation's failure signal is treated as success**, so the caller's internal state (accounting/bookkeeping) silently diverges from what actually happened on-chain (here: on-disk/in-repo).

The closest Desktop analog is in the "Discard Changes" flow, which pairs `git reset` with `git checkout-index`, and explicitly widens the success criteria to include a non-zero exit code without inspecting *which* paths actually succeeded.

### Title
Discard Changes treats `git checkout-index` partial-failure exit code as full success, causing silent, unrecoverable file loss - (File: `app/src/lib/git/checkout-index.ts`)

### Summary
`checkoutIndex()` invokes `git checkout-index -f -u -q --stdin -z` and explicitly configures `successExitCodes: new Set([0, 1])` [1](#0-0) . Exit code `1` from `checkout-index` signals that one or more of the requested paths could **not** be checked out (permission errors, path collisions, problematic filenames, etc.), while the remaining paths may have succeeded. Because `1` is accepted as a "successful" exit code by `git()`'s generic exit-code gate [2](#0-1) , the caller (`GitStore.discardChanges`) has no way to know that some subset of files failed to be restored from the index.

### Finding Description
`GitStore.discardChanges` first moves the user's modified/untracked files to the OS trash, then resets the index for the discarded paths, and finally calls `checkoutIndex` to restore the working-directory copies from the index [3](#0-2) . This is a "trash-then-replace" sequence: the working copy is destructively removed *before* Desktop confirms the replacement copy was actually written back.

`checkoutIndex` blindly stdin-feeds the entire path list to a single `git checkout-index` invocation and only distinguishes clean success (`0`) from a hard/unexpected failure (anything other than `0`/`1`) — exit code `1`, which git-checkout-index uses to indicate that it processed the batch but individual entries failed, is folded into "success" [4](#0-3) . There is no per-path verification (e.g., re-stat'ing each path afterward) anywhere in the call chain — `performFailableOperation` simply awaits the git call and moves on [5](#0-4) .

The broken invariant is the same shape as the ERC20 report: **a boolean/discrete failure signal from an external operation is discarded, so internal state (the app believes discard succeeded) diverges from ground truth (the file was never restored).**

### Impact Explanation
If a file cannot be checked out for one of the batched paths — e.g., because a cloned/fetched attacker-controlled repository contains a path that collides with a directory, a reserved/invalid filename on the host OS, a path exceeding OS length limits, or a permission conflict introduced by a prior operation — `checkout-index` will still exit `1` for the overall batch. Since Desktop already moved the original file to the trash before this step, the net effect is a working-directory file that is **entirely gone**, with the UI reporting the discard as fully successful. This is a silent, hard-to-detect data-loss condition that also affects "what the user commits" — since Desktop only shows what's in the working directory/index, a subsequent commit would omit or corrupt the state of the affected file without any warning.

### Likelihood Explanation
This requires the user to already have local modifications and to invoke "Discard Changes" — an ordinary, frequent workflow — while the working tree contains a file whose path is troublesome for `checkout-index` to write. Because Desktop batches all discarded paths into one `--stdin` call and only gates on the aggregate exit code, a single problematic path in a batch of many is enough to mask that one file's failure; there's no code path that surfaces or retries the individual failure. This does not require admin rights, physical access, or social engineering — it's a natural consequence of discarding changes in a repository that contains such a path (which can originate from cloning/fetching a crafted upstream).

### Recommendation
- Do not accept exit code `1` from `checkout-index` as a blanket success. Instead, parse stderr/output (even with `-q`, failures can be surfaced by dropping `-q` or using `--stdin -z` with per-line reporting) to determine which specific paths failed.
- Re-verify (stat) each discarded path after `checkoutIndex` runs, before considering the discard complete, and surface a clear error for any path that wasn't restored.
- Reorder the "trash-then-replace" flow so the trash step for a given file is only finalized after its replacement from the index is confirmed, avoiding a window where data can be irrecoverably lost.

### Proof of Concept
1. Prepare a repository where a tracked file's discard-time checkout is expected to fail for a specific path (e.g., a path that becomes invalid on Windows due to reserved device names like `CON`, `NUL`, or trailing dot/space, which can be committed on POSIX systems and fetched onto a Windows client), alongside other normal modified files.
2. In Desktop, modify several files including the problematic one, then select "Discard Changes" for all of them.
3. `GitStore.discardChanges` moves all selected files to the trash [6](#0-5) , then calls `resetPaths` and `checkoutIndex` for the batch [7](#0-6) .
4. `git checkout-index` fails to write the problematic path back (non-zero contribution to the batch) but the batch as a whole still exits with code `1`, which `checkoutIndex`'s `successExitCodes: new Set([0, 1])` treats as success [4](#0-3) .
5. Desktop reports the discard operation as completed without error. The problematic file is now missing entirely from the working directory (originally trashed, never restored), with no indication to the user that anything went wrong.
