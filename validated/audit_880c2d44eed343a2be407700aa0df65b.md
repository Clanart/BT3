Based on the investigation, most of the classic "unenforced parameter before a sensitive git/network call" analogs in this codebase have already been hardened (clone destination sensitivity checks, `sanitizeCloneName`, `parseAppURL` branch/filepath validation with `resolveWithin`/`isAbsolute` guards, `validateURL` protocol allow-listing for Enterprise). The one place where an analogous unenforced-parameter pattern still exists is the submodule-update path.

### Title
Unenforced/attacker-influenceable `allowFileProtocol` flag permits `file://` submodule URLs during `git submodule update --init --recursive` - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts a boolean `allowFileProtocol` parameter that, when true, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. [1](#0-0) 
This mirrors the report's bug class: a security-relevant parameter (`maxFee`/`ttl` in the Everclear case, `allowFileProtocol`/`protocol.file.allow` here) is passed straight through to an underlying operation (`newIntent` / `git submodule update`) without the caller enforcing the safe invariant (both zero / protocol restricted) before invocation.

### Finding Description
`git`'s default `protocol.file.allow=user` (or `deny` in some configurations) exists specifically to stop a `.gitmodules` file inside a cloned/fetched repository — content fully controlled by whoever hosts that repo — from pointing a submodule URL at `file:///` and having Git "clone" arbitrary local paths as part of `submodule update --init --recursive`. `updateSubmodulesAfterOperation` explicitly re-enables this behavior with `protocol.file.allow=always` whenever it is invoked with `allowFileProtocol = true`. [2](#0-1) 
The function itself performs no check on the origin of the submodule URLs (they come from the untrusted `.gitmodules` file committed by the repo author) and no check that `allowFileProtocol` should only be true for a repository/environment the user explicitly trusts. The gate lives entirely in whatever caller decides to pass `true`, which I was not able to fully trace to its call sites within the available tool budget — I could only confirm the two call sites exist via `grep_search` (`fetch.ts`/`checkout.ts`/`pull.ts` style callers were not fully inspected due to the final-iteration limit), so I cannot confirm with certainty whether any caller path allows this flag to be `true` for an arbitrary/untrusted cloned repository.

### Impact Explanation
If `allowFileProtocol` is (or can be) `true` for a repository whose `.gitmodules` content is attacker-controlled (e.g., a repo the user clones or fetches from an untrusted remote), a malicious submodule entry such as `url = file:///Users/victim/.ssh` would cause `git submodule update --init --recursive` to copy that local path into the submodule's working directory inside the repo, which Desktop then shows/tracks as regular files — a path/file read-and-exfiltration primitive matching the "attacker controls a cloned/fetched repository" class in the Valid Impact criteria, and functionally worse than the Everclear report's fee/ttl mis-routing since it can leak local, non-repo files (e.g. SSH keys, config) into a working tree that gets displayed, committed, or pushed.

### Likelihood Explanation
Medium — the vulnerable code path (`protocol.file.allow=always`) is real and unconditionally applied when the flag is set, and the untrusted input source (`.gitmodules` submodule URLs) is exactly the kind of attacker-controlled artifact called out as valid in this task. However, I could not fully verify within the remaining iterations whether any current caller sets `allowFileProtocol = true` for an untrusted/attacker-supplied repository versus only for a fully trusted, already-vetted context (e.g. tutorial repo creation), which materially affects exploitability.

### Recommendation
- Default `allowFileProtocol` to `false` for all submodule updates triggered by user-initiated clone/fetch/pull/checkout of arbitrary remotes, and only allow `true` for internally generated, non-attacker-controlled repositories (e.g., the bundled tutorial repo).
- Independently of the flag, validate/parse `.gitmodules` submodule URLs and reject `file://`, `ext::`, and other non-network schemes before calling `git submodule update`, similar to how `parseRemote`/`sanitizeCloneName` already restrict clone URL shapes elsewhere in the codebase. [3](#0-2) 

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` file with:
   ```
   [submodule "leak"]
     path = leak
     url = file:///Users/victim/.ssh
   ```
2. Victim clones or fetches this repository in Desktop.
3. If any Desktop code path calls `updateSubmodulesAfterOperation(repo, remote, cb, kind, title, target, true)` for this repository, Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive`. [4](#0-3) 
4. Git treats the local `.ssh` directory as a clonable submodule source and populates `leak/` inside the repo's working directory with the victim's private keys, which Desktop now tracks as ordinary repository content that could subsequently be committed/pushed or otherwise exposed.

Note: I was unable to fully confirm, within the remaining tool budget, every call site that supplies `allowFileProtocol=true` to determine whether this path is reachable from an untrusted, attacker-controlled repository today — this should be verified in a follow-up session with full repo access before treating this as a confirmed, exploitable finding rather than a hardening gap.
