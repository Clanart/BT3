### Title
Unauthenticated payout OP_RETURN under SIGHASH_SINGLE|ANYONECANPAY lets anyone attribute a payout to an arbitrary operator, extracting bridge funds via a reimbursement the named operator never earned - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout tx's input 0 with `SinglePlusAnyoneCanPay`, which per BIP-341/143 covers only input 0 and output 0 - never output 2 (the OP_RETURN naming the fronting operator). Anyone holding the user's withdrawal signature can therefore assemble and broadcast a payout tx that satisfies the on-chain attribution logic (`update_finalized_payouts` / `get_first_op_return_output` / `parse_op_return_data`) while naming any registered operator `P`, without `P` ever calling `Operator::withdraw`, funding anything, or being aware, triggering `P`'s own `PayoutCheckerTask` to kick off the BitVM reimbursement flow and ultimately spend the deposit's `move_to_vault` UTXO to `P`'s reimbursement address.

### Finding Description
Binding claimed broken: `payer_xonly_pk_credited_in_db == xonly_pk_of_operator_that_called_Operator::withdraw_and_funded_the_payout`.

- `Operator::withdraw` (core/src/operator.rs:560-637) builds the payout tx via `create_payout_txhandler(input_utxo, output_txout, self.signer.xonly_public_key, in_signature, ...)` (core/src/builder/transaction/operator_reimburse.rs:407-436), which places `operator_xonly_pk.serialize()` in output index 2 (OP_RETURN), then signs only input 0 with the user-supplied `in_signature` (`set_p2tr_key_spend_witness`).
- The check `SECP.verify_schnorr(...,payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)...)` (operator.rs:630-637) only verifies the signature is valid for input 0 under whatever `sighash_type` the caller supplied - `parse_withdrawal_sig_params` (core/src/rpc/parser/operator.rs:162-203) requires it be `SinglePlusAnyoneCanPay`.
- `SinglePlusAnyoneCanPay` binds only input 0 and the correspondingly-indexed output 0 (the user's payout destination); it does **not** cover output 1 (anchor) or output 2 (OP_RETURN operator attribution). Anyone possessing the signature can therefore reconstruct the same input0/output0 pair, add whatever additional inputs (ANYONECANPAY permits this) to fund the transaction, and freely substitute the OP_RETURN with an **arbitrary** operator xonly pubkey `P`, then broadcast.
- On-chain attribution is fully derived from unauthenticated chain data: `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2353) finds any tx spending the tracked `withdrawal_utxo` (via `get_payout_txs_for_withdrawal_utxos`, core/src/database/verifier.rs:168-196, which is a pure join on `bitcoin_syncer_spent_utxos` with no operator identity check), reads its first OP_RETURN with `get_first_op_return_output`/`parse_op_return_data` (circuits-lib/src/bridge_circuit/mod.rs:608-617,688-692), and writes it as `payout_payer_operator_xonly_pk` unconditionally.
- `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111) on operator `P`'s own node queries `get_first_unhandled_payout_by_operator_xonly_pk(P)` (core/src/database/verifier.rs:282-313), filtering purely on this attacker-controlled `payout_payer_operator_xonly_pk` column, and automatically calls `Operator::handle_finalized_payout` (core/src/operator.rs:839-970) using `P`'s own signer key and kickoff connectors - with zero verification that `P` actually called `withdraw` or funded output 0.
- `is_kickoff_malicious` (core/src/verifier.rs:1859-1915) only cross-checks that `kickoff_data.operator_xonly_pk == payout_info.operator_xonly_pk` (both ultimately sourced from the same attacker-controlled OP_RETURN), so it cannot detect the forgery.
- The reimbursement (`create_reimburse_txhandler`, core/src/builder/transaction/operator_reimburse.rs:341-385) spends the deposit's actual `move_to_vault` UTXO and pays the full deposit value to `P`'s `reimburse_addr` once the kickoff survives the challenge window - real bridge value leaves the vault credited to `P`, though `P` never funded the payout.

No existing guard (`Operator::is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, DB uniqueness) checks that the party who actually paid output 0 corresponds to the OP_RETURN-named operator, because the signature scheme structurally cannot bind that field.

### Impact Explanation
The named operator `P` is credited via `payout_payer_operator_xonly_pk` and, through automated `PayoutCheckerTask`/`handle_finalized_payout`, is driven into the reimbursement flow and ultimately receives the deposit's full bridge amount from the `move_to_vault` UTXO via `create_reimburse_txhandler`, despite never funding the withdrawal payout. This matches the Critical category "an operator reimbursed for a payout it never funded" (and correspondingly "BTC leaving a move-to-vault UTXO without a matching *operator-fronted* withdrawal", since the actual output-0 funding came from the attacker, not any operator). This is repeatable for every registered withdrawal/deposit and every registered operator xonly pubkey, since the flaw is structural to `SinglePlusAnyoneCanPay` not covering the OP_RETURN output, not tied to any specific operator or deposit.

### Likelihood Explanation
Preconditions are exactly the unprivileged capabilities granted to the attacker: register a withdrawal on the Citrea Bridge contract, obtain a `SinglePlusAnyoneCanPay` signature over their own withdrawal UTXO/output (either by calling `withdraw` on any operator and observing it, or by any off-chain signature-sharing path implied by the protocol's design "signature given to operators off-chain"), and broadcast a Bitcoin transaction paying normal fees. No operator, verifier, or aggregator collusion is required, and the target operator `P` need not be contacted at all. This is fully feasible on regtest/testnet with standard `cargo test` tooling and requires no mainnet or live Citrea.

### Recommendation
Bind the OP_RETURN operator attribution to the signed message. Either:
1. Change the payout tx's sighash type/structure so the operator's OP_RETURN output is covered by the signature (e.g., require `All|AnyOneCanPay` or `Single` covering an output set that includes the OP_RETURN, or use a separate signature/commitment from the party assembling the tx over the OP_RETURN content), or
2. Require the operator to independently attest (e.g., via its own signature over the final broadcast tx, checked before `handle_finalized_payout` proceeds) that it authorized/funded that specific payout, rather than trusting unauthenticated on-chain OP_RETURN data.
