### Title
Cached FROST preprocess deterministically reuses nonces across sign calls for the same context, enabling secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` caches a FROST preprocess seed keyed only by `context` (e.g. `(b"DkgConfirmer", attempt)`), and `share_internal` rebuilds the sign machine from that same cached seed on every call. Because `seeded_preprocess` derives all nonces deterministically from `ChaCha20Rng::from_seed(*seed.0)` and the cache is never deleted, every invocation of `share`/`complete` under the same context reuses identical nonce scalars `d, e`. If the message (`set_keys_message` over a `KeyPair` and `removed` set) or the signing set changes between calls, published shares under the same commitments yield a linear system from which an observer recovers the validator's MuSig/FROST secret share.

### Finding Description

In `SigningProtocol::preprocess_internal`, the seed is stored once under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` when absent, and read back on every subsequent call; nothing removes it after `sign`. `AlgorithmSignMachine::from_cache` calls `seeded_preprocess(cache)`, which regenerates `nonces` and `commitments` purely from `ChaCha20Rng::from_seed(*seed.0)` — fully deterministic given the seed. `share_internal` then invokes `self.preprocess_internal(participants).0` and calls `machine.sign(preprocesses, msg)`, so the same `d, e` are committed again for whatever `msg`/preprocess set is presented.

In `DkgConfirmer::share_internal` / `complete`, `msg = set_keys_message(&self.spec.set(), &removed, key_pair)`, where `key_pair` and `removed` are supplied at call time. A re-attempt or a confirmation executed against a different DKG result/removed set produces a different `msg` — hence a different challenge `c = H(R, group_key, msg)` and different binding factors `ρ_i` — while the nonce pair `(d, e)` is byte-identical. Each published share is `s_j = d + ρ_j·e + c_j·λ·x_i` (per `Schnorr::sign_share` → `SchnorrSignature::sign`, `sign.rs` `nonce` handling). Shares are broadcast on the tributary under `Label::Share`, so any observer collects them.

With the same `(d, e)` reused across `k` signings, the observer obtains `k` equations `s_j = d + ρ_j·e + c_j·(λ_j x_i)` with publicly computable `ρ_j`, `c_j`, `λ_j` — unknowns `d, e, x_i`. Two signings where the challenge differs already pin `d + ρ·e` per session; three sessions (or two sessions plus differing Lagrange coefficients across different included sets) solve for `x_i` directly. Even the documented contract in `crypto/frost/src/sign.rs` states reuse of a `CachedPreprocess` "will enable third-party recovery of your private key share" — this coordinator code performs exactly that reuse whenever it signs more than once for a context.

### Impact Explanation

Recovery of a validator's Ristretto secret share `x_i`. Combined with `t-1` other leaked/compromised shares (or used to weaken the per-set MuSig key the tributary relies on for `set_keys`/validator-set confirmation signatures), this enables forging the Schnorrkel signatures that authorize validator-set key updates. An unprivileged observer of public tributary data is sufficient — no validator compromise needed.

### Likelihood Explanation

The nonce reuse is unconditional: every `share`/`complete` under a given `(label, attempt)` context derives nonces from the same stored seed. Exploitation only requires the same context to sign more than once with differing `msg` or differing preprocess sets — e.g., a DKG confirmation re-signed after the `removed` set or resulting `KeyPair` changed, or a `complete` call issued with a different preprocess subset than the earlier `share` call (different `ρ`). Both are normal protocol flows driven by re-attempt scheduling (`ReattemptDb::schedule_reattempt`).

### Recommendation

Delete or rotate the cached preprocess after the first `sign` consumption: after `AlgorithmSignMachine::from_cache` is used in `share_internal`, clear `CachedPreprocesses` for that context (or store a "consumed" marker) so a second call generates a fresh seed. Alternatively, derive the seed as `H(seed || msg || sorted_participants)` so any change in message or signing set yields different nonces — though one-time consumption is the safer fix matching FROST's single-use requirement.

### Proof of Concept

1. Run a tributary where the coordinator produces a `DkgConfirmer` share for `(b"DkgConfirmer", attempt = k)` with `KeyPair K1` and removed set `R1` → share `s1 = d + ρ1·e + c1·λ·x_i` is published.
2. Cause the confirmation to run again for the same attempt `k` with a different outcome (different `key_pair K2` or `removed R2`, e.g. via a re-attempt where validator removal status changed) → `share_internal` reloads the same cached seed, reusing `d, e`, and publishes `s2 = d + ρ2·e + c2·λ·x_i` (different `c` since `msg` changed).
3. With a third such share `s3` (or a second share produced under a different included set giving a different `λ`), solve the linear system for `x_i` — the validator's secret share — since `d`, `e` are common and `ρ_j, c_j, λ_j` are publicly computable from the published preprocesses/commitments and messages.
