### Title
Silent, unconfirmed rewrite of the repository's `origin` remote URL from GitHub API data enables MITM/credential exfiltration on push/fetch - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` every time the associated GitHub repository is refreshed from the API (e.g., after opening/selecting a repository, background repository refresh cycles). This function silently overwrites the local `origin` remote URL to match `apiRepo.clone_url` with no user confirmation, no diff/warning dialog, and no logging or event emitted to the user, unlike the analogous `UpstreamAlreadyExists` dialog flow which explicitly asks the user before changing the `upstream` remote.

### Finding Description
`updateRemoteUrl` compares the current `origin` remote URL against `apiRepo.clone_url` returned by the GitHub API and rewrites the remote silently if: (1) the URL protocol is unchanged, and (2) the previously cached `gitHubRepository.cloneURL` still matches the current remote (i.e., the user hasn't manually customized it): [1](#0-0) 

This is invoked unconditionally as part of the routine repository-refresh path: [2](#0-1) 

`_selectRepositoryRefreshTasks` calls `repositoryWithRefreshedGitHubRepository` on every repository selection: [3](#0-2) 

The actual write happens via `GitStore.setRemoteURL`, which only calls `git remote set-url` and `emitUpdate()` (a UI re-render signal, not a security-relevant notification or confirmation event): [4](#0-3) 

Contrast this with the analogous "upstream remote mismatch" case, where Desktop explicitly shows a confirmation dialog (`UpstreamAlreadyExists`) before rewriting the `upstream` remote: [5](#0-4) 

No equivalent confirmation, diff display, or audit-trail event exists for `origin` remote rewrites driven by `updateRemoteUrl`. The trust boundary being crossed: `apiRepo.clone_url` originates from a GitHub API response — for GitHub Enterprise Server (GHES) endpoints this is a network-reachable, non-github.com host that an attacker positioned as a malicious/compromised GHES instance (or via a spoofed/similar endpoint accepted during enterprise sign-in) fully controls. `urlMatchesRemote` only checks protocol/hostname/owner/name structurally, not TLS identity or a trust anchor, so an attacker-controlled `clone_url` response for a repository whose owner/name matches the cached `gitHubRepository.cloneURL` can pass all guards and get silently written into `origin`.

### Impact Explanation
If an attacker can influence the `clone_url` field returned for a tracked repository (e.g., by controlling/compromising the GHES/API endpoint the user authenticated against, or via a repository transfer/rename response under attacker control), Desktop will silently repoint the local `origin` remote to an attacker-controlled URL without any user awareness. Subsequent user-initiated `git push`/`git fetch` operations (and Desktop's credential-helper trampoline, which supplies the stored account token keyed by hostname) would then interact with the attacker's endpoint. Depending on the substituted host, this can result in: pushing the user's commits to an attacker-controlled repository (silent corruption/exfiltration of code), or — if the substituted host shares a credential lookup path — leaking authentication material intended for the legitimate host. This matches the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact categories.

### Likelihood Explanation
This requires the attacker to control or spoof responses from the GitHub API endpoint associated with the account (most plausible for GitHub Enterprise/self-hosted endpoints, less so for github.com itself, which is TLS-pinned to GitHub's real infrastructure). It does not require local access, admin rights, or social engineering beyond the user having already added a GHES account — a supported normal workflow. The rewrite happens automatically on ordinary actions (selecting a repository, background refresh), requiring no unusual user interaction, which raises likelihood relative to a report requiring explicit unnatural steps. However, exploitation is gated on network-position/endpoint-compromise on the GHES side, which is a nontrivial precondition.

### Recommendation
Before silently rewriting `origin`'s URL in `updateRemoteUrl`, require explicit user confirmation via a dialog (mirroring `UpstreamAlreadyExists`) showing the old and new URLs, and emit a store event/log entry recording the change so it is auditable. Additionally, validate that hostname changes are never applied silently even when protocol matches, since a same-protocol/different-host response is the primary attack scenario the current `protocolsMatch` check fails to address.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop pointing at `https://ghe.example.com`.
2. Attacker gains control of/spoofs `https://ghe.example.com`'s API and, for a repository the user already has open in Desktop with a cached `gitHubRepository.cloneURL` of `https://ghe.example.com/org/repo.git`, returns a `fetchRepository` response with `clone_url: "https://ghe.example.com/org/repo-mirror.git"` (or any attacker-controlled repo under the same owner/name-matching structural check) — note `urlMatchesRemote` only validates hostname/owner/name structurally, so an attacker fully controlling the endpoint can craft a response matching all constraints while pointing at infrastructure they control.
3. On next repository selection or background refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` → `GitStore.setRemoteURL` silently rewrites `origin` to the attacker-specified URL with no dialog or notification: [6](#0-5) 
4. The user, unaware, pushes/fetches against the attacker-controlled remote.
