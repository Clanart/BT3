### Title
`SignableTransaction::new` computes the fee and relay-check vbytes from `payments` only, omitting the already-pushed OP_RETURN data output - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` builds `tx_outs` including an optional OP_RETURN `data` output, but then calls `calculate_weight_vbytes(tx_ins.len(), payments, change)` with the `payments` slice — which excludes the data output. Analogous to the reported "wrong fee function" bug (using one parameter source where a different one is required), the fee calculation here consumes the wrong output set, so `needed_fee`, the minimum-relay-fee check, and the change amount are all computed against a smaller virtual size than the transaction will actually have.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight calculation: [1](#0-0) 

`calculate_weight_vbytes` only materializes `payments` (and optional `change`) into the template transaction it weighs — the `data`/`tx_outs` contents are invisible to it: [2](#0-1) 

Consequences within the same function:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) uses vbytes missing the OP_RETURN output (~11 + len(data) bytes, up to ~91 bytes / ~91+ WU for 80 bytes of data).
- The minimum-relay-fee guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211) validates against the underestimated vbytes, so a transaction whose *actual* fee rate is below the relay minimum can pass this check.
- The change computation at lines 225–233 (`vbytes_with_change`, `fee_with_change`, and `input_sat - payment_sat - fee_with_change`) has the same defect, so change is oversized by `fee_per_vbyte * missing_vbytes` relative to the intended rate.

### Impact Explanation
Any caller that attaches `data` produces a transaction paying `fee_per_vbyte * (actual_vbytes - omitted_vbytes)` less than requested. If the intended rate was near the relay minimum, the resulting transaction is non-standard/unrelayable; otherwise it confirms at a lower effective rate than specified. For a multisig wallet spending `ReceivedOutput`s (the intended use via `multisig()`/`TransactionMachine`), this yields a signed transaction paying less than the agreed fee and change larger than it should be — funds committed to change are misallocated and the transaction may stall, requiring a re-signed replacement. Unprivileged callers supplying payments/data through the wallet API trigger the miscalculation directly.

### Likelihood Explanation
Deterministic whenever `data.is_some()`; `data` of up to 80 bytes is explicitly supported (line 171), so any send carrying an OP_RETURN payload hits this on every construction.

### Recommendation
Pass the already-assembled outputs to the weight calculation. Change `calculate_weight_vbytes` to accept the full `&[TxOut]` (or pass `&tx_outs` at lines 204 and 226) so the OP_RETURN output is included in `vbytes`, `needed_fee`, the min-fee check, and the change deduction.

### Proof of Concept
```rust
// inputs: single ReceivedOutput worth input_sat
// payments: one payment of payment_sat
// data: Some(vec![0u8; 80])
let tx = SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), 10).unwrap();
// tx.fee() == input_sat - payment_sat (all leftover goes to fee, no change),
// but tx.needed_fee() == 10 * vbytes(without OP_RETURN)
// while the real transaction is ~91 WU (~23 vbytes) larger.
// With fee_per_vbyte = 1 and vbytes chosen so needed_fee just passes the
// min-relay check at line 211, the serialized TX has an actual fee rate
// below DEFAULT_MIN_RELAY_TX_FEE and is rejected for relay.
```
