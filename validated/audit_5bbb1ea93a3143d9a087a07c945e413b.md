### Title
Unbounded `sender`/`recipient` participant index in PedPoP blame evaluation causes a reachable panic (DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame_internal` / `AdditionalBlameMachine::blame` index `self.commitments[&sender]` (and use `recipient` in share-verification statements) with `Participant` values taken directly from protocol inputs. `Participant` only enforces "non-zero u16"; a sender index `> n` is never validated before the `HashMap` index, which panics on a missing key. This is a remotely-triggerable crash analogous to the reported replication DoS: an unauthenticated-attacker-supplied participant index causes a repeatable node crash. [1](#0-0) 

### Finding Description
`blame_internal` is reached through the public `BlameMachine::blame` and `AdditionalBlameMachine::blame` APIs, which are fed by blame transactions whose `accuser`/`faulty` fields are deserialized via `Participant::new(u16)` — the only check is that the index is non-zero, with no bound against the set size `n`. [2](#0-1) 

Inside `blame_internal`, the sender's commitment row is fetched by direct map indexing:

- `&self.commitments[&sender]` at the `multiexp_vartime(&share_verification_statements::<C>(recipient, &self.commitments[&sender], ...))` call. [3](#0-2) 

`self.commitments` is populated only for `1 ..= n` (see `AdditionalBlameMachine::new`, which inserts `Participant::new(i)` for `i in 1..=n` and `calculate_share`, which inserts for `all_participant_indexes()`). Any `sender` value in `(n, u16::MAX]` — e.g. `Participant(0xFFFF)` — is absent from the map, so `HashMap`'s `Index` impl panics. [4](#0-3) 

The same unchecked trust applies to `recipient`: while `recipient` is only used arithmetically inside `share_verification_statements` (no panic), `sender` hits the raw map index. Notably, `AdditionalBlameMachine::new`'s documented warning covers *invalid commitment messages*, not an out-of-range `sender` argument to `blame` — there is no validation of `sender`/`recipient` anywhere in `blame`, `blame_internal`, or the transaction deserialization. [5](#0-4) 

### Impact Explanation
A panic in the blame-handling path crashes the executing node/task. Since blame transactions are handled during consensus-driven DKG processing, a `faulty`/`accuser` index outside `1..=n` produces a deterministically repeatable crash on any node that evaluates it — matching the report's "hang or frequently repeatable crash (complete DOS)" class (availability-only impact, no secret leakage). [6](#0-5) 

### Likelihood Explanation
Triggering requires only that a blame evaluation be invoked with an out-of-range participant index. The deserializer (`Transaction::read`, `Participant::new`) accepts any non-zero `u16`, and neither `blame` nor `blame_internal` validates the index against `commitments`' keyset before indexing. The only mitigation is whether upstream handler code bounds-checks `accuser`/`faulty` before constructing the blame machine — I did not fully verify that path (the relevant portion of `coordinator/src/tributary/handle.rs` for `Transaction::InvalidDkgShare` was truncated), so exploitability depends on that check being absent or bypassable; the library-level defect itself is unconditional. [7](#0-6) 

### Recommendation
In `blame_internal` (and `AdditionalBlameMachine::blame`), validate `sender` and `recipient` against `self.commitments` (e.g., `commitments.get(&sender)` returning an error/`None` path, or an explicit `u16::from(sender) <= n` check) before any map indexing. Return a defined fault result or error instead of panicking. Ideally also bound `accuser`/`faulty` to the participant set at transaction deserialization/handling time. [1](#0-0) 

### Proof of Concept
```rust
// Given an AdditionalBlameMachine built for n = 3 participants:
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// blame() accepts arbitrary Participant values; Participant::new only rejects 0
let bogus_sender = Participant::new(0xFFFF).unwrap();

// Any EncryptedMessage/None proof suffices — execution reaches:
//   multiexp_vartime(&share_verification_statements(recipient, &self.commitments[&sender], ...))
// and HashMap's Index panics on the missing key 0xFFFF.
machine.blame(bogus_sender, recipient, msg, None); // panic: key not found
```
Root cause: `&self.commitments[&sender]` at crypto/dkg/pedpop/src/lib.rs (~line 599) indexes with an attacker-influenced `Participant` that was never validated against `1..=n`. [3](#0-2)

    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
