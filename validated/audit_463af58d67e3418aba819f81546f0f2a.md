### Title
Convex decay term in `getRewardablePercentWAD` lets a user inflate rewardable percent by splitting a single unlock into multiple staggered slots - (File: VLMGP.sol)

### Summary
`VLMGP.getRewardablePercentWAD` sums a per-slot decay term `amountInCoolDown * (endTime-startTime) / (timeNow-startTime)` for every unlock slot that has passed its `endTime`. Because `1/(timeNow-startTime)` is a convex function of `startTime`, splitting one unlock amount into several slots opened at different timestamps (all still ≤ `maxSlot`) yields a strictly larger summed percent than keeping the same total amount in one slot with the equivalent average start time, since the same amount lock-locked MGP can be manipulated using `VLMGP.startUnlock` calls, which is callable by any address holding locked MGP with no privileged role required.

### Finding Description
`getRewardablePercentWAD` computes, for each unlock slot that is already expired (`block.timestamp > userUnlocking[i].endTime`): [1](#0-0) 

The relevant term is `amountInCoolDown * (endTime-startTime) / (timeNow-startTime)`. For a fixed `coolDownInSecs` (`endTime - startTime` is constant per slot, set in `startUnlock`), this term reduces to `amountInCoolDown * c / (t - s)`. The function `f(s) = 1/(t-s)` is convex in `s` for `s < t`. By Jensen's inequality, splitting a total amount `X` across `N` slots with distinct `startTime` values `s_1..s_N` (average `s̄`) gives:

`Σ (X/N) * c/(t - s_i) ≥ X * c/(t - s̄)`

with strict inequality whenever the `s_i` are not identical. This is achievable because `startUnlock` lets any locked-MGP holder open a new unlock slot at any time up to `maxSlot`: [2](#0-1) 
and `getNextAvailableUnlockSlot` simply returns the next free slot index up to `maxSlot`: [3](#0-2) 

There is no requirement that all cooling amounts share the same `startTime`/`endTime`, no per-user amount-invariance check, and no normalization of the decay term against a single "as-if-one-slot" baseline. Thus a user who staggers several `startUnlock` calls (instead of doing one `startUnlock` for the full amount) captures a materially higher "rewardable percent" for the same locked MGP and the same total elapsed/cooldown time, purely due to the non-linearity of the summed formula.

I was not able to fully trace, within the available tool budget, the exact downstream consumer(s) of `getRewardablePercentWAD` (grep matches indicate it is referenced together with `calExpireForfeit` logic in `rewards/vlMGPBaseRewarder.sol`, but I could not read that file's implementation to confirm the precise monetary formula that consumes this percent). The bias in the percent computation itself is directly verified in `VLMGP.sol`.

### Impact Explanation
If `getRewardablePercentWAD` (or the derived percent) is used to determine how much of a user's unclaimed/decaying reward remains claimable versus forfeited (as its name and the `vlMGPBaseRewarder`/`calExpireForfeit` references suggest), an attacker can extract a larger share of otherwise-forfeitable MGP rewards than intended by staggering unlocks instead of doing one unlock for the full amount. This is a theft-of-yield class issue (unclaimed MGP reward inflated beyond entitlement) rather than direct principal theft, since `unlock`/`forceUnLock` amounts themselves are unaffected — only the "rewardable" percentage computation is biased.

### Likelihood Explanation
- Requires only holding locked MGP (no privileged role) — the attacker calls public `startUnlock` repeatedly.
- Bounded by `maxSlot`, so the number of slots (hence exploitable granularity) is limited by protocol configuration, but even 2-3 slots are enough to realize a measurable convexity gain.
- Fully repeatable by any user, at no cost beyond gas and normal cooldown waiting.
- No special capital or flash loan needed — it is purely a scheduling/timing choice by the attacker.

### Recommendation
Redefine the decayed-percent computation so it is amount-invariant regardless of how a user partitions their unlock amount across slots — e.g., compute an amount-weighted average `startTime` across all cooling slots first, then apply the decay function once to the aggregate amount, instead of summing per-slot convex terms independently. Alternatively, replace the harmonic decay `c/(t-s)` with a linearly interpolated (non-convex) decay so that splitting an amount across slots with different `startTime` cannot increase the total relative to a single equivalent slot.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP` with `coolDownInSecs = C` and `maxSlot >= 2`.
2. User A locks `X` MGP, waits, then at `t0` calls `startUnlock(X)` (single slot, `startTime = t0`, `endTime = t0+C`).
3. User B locks `X` MGP; calls `startUnlock(X/2)` at `t0`, and `startUnlock(X/2)` at `t0 + Δ` (staggered second slot, same total `X`).
4. Warp to `timeNow = t0 + C + K` (past both slots' `endTime`).
5. Call `getRewardablePercentWAD` for both users and assert `percent_B > percent_A` for equal total locked/cooldown amount `X` and comparable elapsed time, demonstrating the convex-sum bias.
6. If `calExpireForfeit` (in `rewards/vlMGPBaseRewarder.sol`) consumes this percent to compute forfeiture/claimable reward, extend the test to assert User B's forfeited/claimable MGP differs materially from User A's for equal total unlocked principal and equal elapsed time — confirming extraction of extra unclaimed MGP beyond entitlement.
