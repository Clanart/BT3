### Title
Missing lower-bound check accepts `Participant(0)` in `ThresholdKeys::new`, enabling an inconsistent threshold-key view from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
The referenced bug class is an incorrectly-directed bound/comparison check in a validation routine: the Swivel `ZcToken` allowance check used `allowed >= principalAmount` where `allowed < principalAmount` was intended, so the "valid" branch could never execute. The analog in Serai is the participant-index bound check in `ThresholdKeys::new`, which validates only the *upper* direction of the comparison (`participant > n`) and never rejects the invalid lower value `Participant(0)`. As with the flipped `>=`, the comparison admits exactly the inputs the check exists to exclude, producing an inconsistent key set from attacker-controlled serialized data.

### Finding Description [1](#0-0) 

`ThresholdKeys::new` validates `verification_shares` with two checks:

```rust
if verification_shares.len() != usize::from(params.n()) { ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { Err(DkgError::InvalidParticipant ...)?; }
}
```

Participants are valid indexes `1..=n`. The check rejects `participant > n` but accepts `participant == 0`, so a map keyed by `{0, 1, ..., n-1}` (displacing legitimate participant `n`) passes both the length and bound checks.

The inconsistency compounds because `group_key` is then computed over the fixed set `1..=t`: [2](#0-1) 

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

If `t < n` (the normal threshold case), the participant-`0` share is never folded into `group_key`, yet it remains in `verification_shares` and satisfies the `len == n` invariant. `ThresholdView`/`verify_share` then operate against this asymmetric map: the share at index `0` has a Lagrange factor of `prod(j/(j-0)) = 1` — scalar-valid, so no panic — while the displaced index `n` share is absent. `ThresholdKeys::read`/`ThresholdView` deserialization of untrusted bytes routes through this constructor, so an unprivileged party supplying crafted bytes (e.g., via a tributary-transmitted or peer-supplied `ThresholdKeys`) can produce a `ThresholdKeys` whose `verification_shares` do not correspond to the polynomial underlying `group_key`/`secret_share`.

### Impact Explanation
- A node accepting these keys derives addresses (`tweak_keys`/`Scanner` over `group_key` in `networks/bitcoin/src/wallet/mod.rs`) whose incoming outputs cannot be spent: shares verified against the poisoned map either fail `verify_share` or interpolate to a signature that does not verify under `group_key` — funds reported received that are not spendable.
- Alternatively, where the `0`-indexed share passes `verify_share` (its interpolation factor is a valid scalar), the honest participants' views of the key set diverge, breaking the intended threshold-validation functionality — the same "functionality that can never behave correctly" impact class as the original Medium.

### Likelihood Explanation
Reachable by an unprivileged party via untrusted bytes passed to `ThresholdKeys::read` (explicitly an untrusted-deserialization entry point) or via a malformed DKG/commitment transcript accepted into `ThresholdKeys::new`. The trigger is only an index-`0` entry in the serialized share map — no key compromise, collusion, or validator privileges required — though the attacker must be positioned to supply the keys a victim deserializes, which keeps this at Medium rather than High.

### Recommendation
In `crypto/dkg/src/lib.rs`, extend the participant bound check in `ThresholdKeys::new` to reject both ends of the valid range, mirroring the `allowed >= principalAmount` → `allowed < principalAmount` fix direction:

```rust
if (u16::from(participant) > params.n()) || (u16::from(participant) == 0) {
  Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
}
```

Consider additionally asserting `verification_shares` contains every index in `1..=n`, making the map's key set exactly the canonical participant set.

### Proof of Concept
Conceptually, with `params = ThresholdParams::new(t=2, n=3)`:

1. Build `verification_shares` as a `HashMap` keyed `{Participant(0), Participant(1), Participant(2)}` with arbitrary generator multiples — notably *excluding* `Participant(3)`.
2. Serialize via `ThresholdKeys::write`-compatible framing (or feed a mutated valid serialization where the share keyed `3` is re-keyed `0`) into `ThresholdKeys::read`.
3. `ThresholdKeys::new` accepts it: `len == 3` passes line 355, and the loop at lines 361–365 rejects only `> n`, so `Participant(0)` survives.
4. Result: `group_key` is computed over `{1, 2}` while `verification_shares` claims a 3-of set including a phantom index `0`. Any `ThresholdView`/`verify_share` flow against this view is internally inconsistent — honest share `n` is absent and `0` is unusable for the group's `group_key` — demonstrating that the malformed input is admitted by a check that, like `>=` instead of `<`, tests the wrong side of the boundary.
