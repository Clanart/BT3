## Analysis Summary

The Across `AcceleratingDistributor` finding is a generic "insufficient input validation" pattern: numeric parameters are accepted without range checks and are then fed into arithmetic whose correctness depends on those bounds, leading to either silent miscalculation or reachable arithmetic failures. The strongest transferable analog in Protobuf is in the ProtoJSON `Timestamp` well-known-type parser, which accepts a client-supplied JSON string through the standard public JSON-parsing API and performs date arithmetic on its components without validating that they fall within their documented ranges. [1](#0-0) 

### Title
Missing range validation of month/day/hour/minute/second components in ProtoJSON `Timestamp` parsing silently accepts malformed RFC 3339 strings and produces incorrect epoch values - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
`ParseTimestamp` decodes each date/time component of a `google.protobuf.Timestamp` JSON string using `TakeTimeDigitsWithSuffixAndAdvance`, which only enforces a maximum digit *count* (2 or 4 digits) and, for year/month/day, a non-zero check. It never validates that month ∈ [1,12], day ∈ [1,31] (or is valid for the given month), hour ∈ [0,23], minute ∈ [0,59], or second ∈ [0,60]. These unchecked values are fed directly into the Julian-day/epoch-seconds arithmetic that computes `secs`. [2](#0-1) [3](#0-2) 

### Finding Description
`TakeTimeDigitsWithSuffixAndAdvance(data, max_digits, end)` bounds only the number of consumed digits (e.g., 2 digits → value range 0–99, 4 digits → 0–9999); it performs no semantic range check. The caller `ParseTimestamp` then checks only `*year == 0`, `*mon == 0`, `*day == 0` for a null/zero rejection, but applies **no upper bound** on any component: [4](#0-3) 

These unvalidated values are used directly in the Zeller's-congruence-style date-to-epoch-day conversion and final seconds computation: [5](#0-4) 

This mirrors the audit finding's root cause exactly: a user/attacker-controlled numeric input (`maxMultiplier`/`secondsToMaxMultiplier`/`baseEmissionRate` in the Solidity case, `mon`/`day`/`hour`/`min`/`sec` here) is consumed by downstream arithmetic whose correctness implicitly assumes the input lies within a specific range, but no `require`/bounds check enforces that assumption. For example, a client can submit `"2024-99-99T99:99:99Z"` (each field satisfies the 2-digit-count/non-zero constraint) and the parser accepts it as a syntactically valid timestamp, silently computing `epoch_days`/`secs` from out-of-range inputs via unsigned-wraparound arithmetic (`m_adj = *mon - 3` on a `uint32_t`) instead of rejecting the malformed string.

### Impact Explanation
This is a data-integrity issue rather than a memory-safety one: invalid RFC 3339 strings are silently accepted and converted into an incorrect, attacker-influenced `Timestamp{seconds, nanos}` value instead of causing `ParseTimestamp` to return an `Invalid` status. Any consuming application (via `JsonStringToMessage`/`google::protobuf::json::JsonToBinaryString` or language bindings using this shared parser) that trusts a successfully parsed `Timestamp` to represent a legitimate calendar date can be fed a nonsensical or attacker-steerable epoch value while believing input validation succeeded — directly analogous to the "system destabilizing" incorrect state described in the original report, but here manifesting as accepted-but-wrong data rather than a revert/DoS.

### Likelihood Explanation
High from a reachability standpoint: this is exercised by every call to the public ProtoJSON parsing API when a message contains a `google.protobuf.Timestamp` field and the JSON payload is fully attacker-controlled and bounded (a short string, no huge-allocation vector). No special privileges, hostile schema, or native-binding bypass is required — the only precondition is a message schema (trusted, per the threat model) that includes a `Timestamp` field, which is extremely common (timestamps, gRPC metadata, Any-wrapped well-known types, etc.).

### Recommendation
Add explicit range checks in `ParseTimestamp` (and equivalent logic if duplicated elsewhere) immediately after parsing each component: `mon` ∈ [1,12], `day` ∈ [1, days-in-month(mon, year)], `hour` ∈ [0,23], `min` ∈ [0,59], `sec` ∈ [0,60]; return `str->loc.Invalid(...)` on violation, mirroring the existing zero-checks. This closes the gap the same way `enableStaking` was subsequently patched to `require` bounded inputs in the referenced Across PRs.

### Proof of Concept
Using the JSON parser's public entry point (`google::protobuf::json::JsonStringToMessage` or equivalent language binding) with a trusted schema containing a `google.protobuf.Timestamp` field:

```json
{"ts": "2024-99-31T99:99:99Z"}
```

Trace through `ParseTimestamp`:
- `year=2024` (passes `!=0`), `mon=99` (passes `!=0`, no upper-bound check), `day=31` (>28/29/30 for an invalid month, no calendar validity check), `hour=99`, `min=99`, `sec=99` (all pass only the "has_value" check, no `<24`/`<60` check).
- `m_adj = 99 - 3 = 96` (no wraparound here since 99>3, but for `mon` in [1,2] the subtraction wraps as `uint32_t`).
- `secs` is computed from these out-of-range components and set on the message via `Traits::SetInt64` without any error — the call returns `absl::OkStatus()` instead of a validation error, i.e., a malformed timestamp string is accepted as valid input. [6](#0-5) [7](#0-6)

absl::optional<uint32_t> TakeTimeDigitsWithSuffixAndAdvance(
    absl::string_view& data, int max_digits, absl::string_view end) {
  ABSL_DCHECK_LE(max_digits, 9);

  uint32_t val = 0;
  int limit = max_digits;
  while (!data.empty()) {
    if (limit-- < 0) {
      return absl::nullopt;
    }
    uint32_t digit = data[0] - '0';
    if (digit >= 10) {
      break;
    }

    val *= 10;
    val += digit;
    data = data.substr(1);
  }
  if (!absl::StartsWith(data, end)) {
    return absl::nullopt;
  }

  data = data.substr(end.size());
  return val;
}

absl::optional<int32_t> TakeNanosAndAdvance(absl::string_view& data) {
  int32_t frac_secs = 0;
  size_t frac_digits = 0;
  if (absl::StartsWith(data, ".")) {
    for (char c : data.substr(1)) {
      if (!absl::ascii_isdigit(c)) {
        break;
      }
      ++frac_digits;
    }
    auto digits = data.substr(1, frac_digits);
    if (frac_digits == 0 || frac_digits > 9 ||
        !absl::SimpleAtoi(digits, &frac_secs)) {
      return absl::nullopt;
    }
    data = data.substr(frac_digits + 1);
  }
  for (int i = 0; i < 9 - frac_digits; ++i) {
    frac_secs *= 10;
  }
  return frac_secs;
}
