### Title
Scanner accepts zero-value/dust outputs to the multisig script_pubkey as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` reports any transaction output paying to a registered script as a `ReceivedOutput`, with no check on `output.value`. Analogous to the `castVote` finding (a zero-weight action still produces an emitted, state-mutating effect), an unprivileged party can broadcast a transaction creating zero-value or sub-dust outputs to Serai's multisig/offset addresses and have them reported as received outputs.

### Finding Description
`scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` whenever `output.script_pubkey` matches a script in `self.scripts` [1](#0-0) . `self.scripts` is populated by `Scanner::new` (the tweaked group key's P2TR script) and `register_offset` [2](#0-1) . The output's `value` is never inspected — `ReceivedOutput::value()` merely returns whatever the sender chose [3](#0-2) .

There is no minimum-amount/dust check anywhere in this flow. Bitcoin consensus permits zero-value outputs (they are nonstandard but consensus-valid, e.g. in transactions a miner includes), and sub-dust outputs are trivially broadcastable. Every such output becomes a `ReceivedOutput` that upstream code treats as funds received by the multisig.

### Impact Explanation
- Funds reported received that are not spendable: a zero-value output contributes nothing yet is registered as a received output; dust outputs cost more in signature weight/fees than their value, so they are economically unspendable.
- UTXO-set / event spam: an attacker can create arbitrarily many matching outputs in a single transaction (each just needs to pay the script_pubkey), inflating the set of `ReceivedOutput`s the processor must track, serialize via `ReceivedOutput::write`, and eventually consider as inputs for `send.rs` transaction construction — the exact "spam the emitted event with zero weight" shape of the reference bug.

### Likelihood Explanation
Reachable by any unprivileged party: the only requirement is knowing the multisig/offset script_pubkeys, which are derivable from the public group key and public offsets, and sending a Bitcoin transaction — explicitly within the threat model ("Bitcoin transactions they send"). No validator status, key material, or malformed encodings are needed.

### Recommendation
In `Scanner::scan_transaction` (or at the point outputs are accepted upstream), reject outputs below an economically-spendable threshold, e.g.:

```rust
if output.value.to_sat() < DUST_AND_FEE_THRESHOLD { continue; }
```

where the threshold accounts for the input's signature weight in a future spend, not just the relay dust limit. Zero-value outputs should always be skipped.

### Proof of Concept
1. Obtain the multisig P2TR script via `p2tr_script_buf(tweaked group key)` — public information.
2. Craft a transaction with N outputs each paying `0` sat (or 1 sat) to that script_pubkey; have it mined.
3. `Scanner::scan_transaction(&tx)` returns N `ReceivedOutput`s, each reported as received funds despite being worthless/unspendable.

Key lines: `networks/bitcoin/src/wallet/mod.rs:199-214` — matching is on `script_pubkey` only, with no value check.

  /// Register an offset to scan for.
  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script
  /// path into the output, allowing the output to be spent by satisfaction of an arbitrary script
  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
