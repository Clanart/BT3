## Finding: Missing Ownership/Approval Check in CW721→ERC721 Pointer `transfer_nft` Allows Unauthorized NFT Transfer

The reported CVE-2019-1000011 is a case where a mutation resolver authorized a caller generically but never verified the caller was actually authorized for the *specific* resource being acted upon, letting an authorized-for-something user delete arbitrary resources. The same bug-class pattern (action performed against a resource without validating the invoking principal is the resource's actual owner/approved party) exists in sei-chain's CW-side pointer contract for wrapping EVM ERC-721 tokens as CW721.

### Title
Missing Owner/Approval Check in `transfer_nft` of the CW721→ERC721 Pointer Contract Allows Any Address to Transfer Any Wrapped NFT - (File: example/cosmwasm/cw721/src/contract.rs)

### Summary
The CW721 wrapper contract that exposes a CW-side interface for EVM-native ERC-721 tokens (the reverse-direction pointer, paired with `CW721ERC721Pointer.sol` on the EVM side) implements `TransferNft`/`SendNft` via a shared `transfer_nft` helper. This helper fetches the actual on-chain owner of the token and issues a delegatecall to the underlying ERC-721 `transferFrom(owner, recipient, id)` — but it never checks that `info.sender` (the CW message sender) is the owner or an approved spender of that token.

### Finding Description [1](#0-0) 

`transfer_nft` performs:
1. Look up the real owner of `token_id` via `querier.erc721_owner(...)`.
2. Build a payload to call the ERC-721 `transferFrom(owner, recipient, token_id)` and issue it through `EvmMsg::DelegateCallEvm`.

There is no comparison between `info.sender` and the fetched `owner`, and no check of `isApprovedForAll`/`getApproved` for `info.sender`. Both `execute_transfer_nft` and `execute_send_nft` call this same unguarded helper: [2](#0-1) .

This is a direct architectural mismatch with the equivalent EVM-side pointer, `CW721ERC721Pointer.sol`, which correctly requires `from == ownerOf(tokenId)` (and, unlike this contract, is also missing the approver check in its own `approve` path) before forwarding a transfer: [3](#0-2) . The CW721 direction, however, has no authorization gate at all — it derives `owner` from state and transfers unconditionally regardless of who called `execute`.

Because the underlying `transferFrom` is invoked via `EvmMsg::DelegateCallEvm` (delegatecall semantics), `msg.sender` inside the target ERC-721's `transferFrom` is not the original CW message sender but the pointer/module context executing on the token owner's behalf — meaning the ERC-721 contract's own `_isApprovedOrOwner` check cannot serve as a backstop for this CW-side call path.

### Impact Explanation
Any unprivileged CosmWasm caller can invoke `ExecuteMsg::TransferNft` (or `SendNft`) on this pointer contract for **any** `token_id` and **any** `recipient`, causing the wrapped ERC-721 NFT to be transferred away from its rightful owner without their consent. This is a direct unauthorized-transfer-via-pointer vulnerability resulting in permanent, unauthorized loss of NFT ownership — squarely within the "unauthorized transfer via precompile or pointer" impact category.

### Likelihood Explanation
The bug is trivially reachable: any account can submit a `MsgExecuteContract` targeting this pointer's `TransferNft` variant with an arbitrary `token_id`/`recipient` — no special privilege, approval, or prior state is required from the attacker. This makes exploitation deterministic and low-cost, limited only by whether/how this contract's compiled bytecode is the one actually instantiated as the canonical CW→EVM NFT pointer.

### Recommendation
Add an explicit authorization check in `transfer_nft` before constructing the transfer message: require `info.sender == owner` OR that `info.sender` is `approved`/`isApprovedForAll` for the token, mirroring the checks present in `CW721ERC721Pointer.sol`'s `transferFrom`/OpenZeppelin `_isApprovedOrOwner` pattern. Apply the same pattern to `execute_approve`/`execute_approve_all` (which currently forward spender/operator changes without checking that `info.sender` owns/controls the relevant token or account) and to the analogous CW1155 pointer path.

### Proof of Concept
1. Alice owns ERC-721 token `id=5`, wrapped via the CW721 pointer contract at `sei1...pointer`.
2. Attacker Mallory (no approval, no ownership) submits `MsgExecuteContract{ contract: sei1...pointer, msg: {"transfer_nft": {"recipient": "<mallory_addr>", "token_id": "5"}} }`.
3. `execute_transfer_nft` → `transfer_nft` fetches `owner = Alice` via `querier.erc721_owner(...)`, builds `transferFrom(Alice, Mallory, 5)`, and sends it via `DelegateCallEvm` — with no check that `info.sender == Mallory` has any right to move Alice's token.
4. The token transfers from Alice to Mallory. No error is raised; `execute_transfer_nft` unconditionally emits attributes as if the transfer were legitimate: [4](#0-3) .

**Note on confidence:** I was unable to fully trace the exact runtime semantics of `EvmMsg::DelegateCallEvm` (i.e., what `msg.sender` resolves to inside the ERC-721 contract during this delegatecall, and whether the chain's wasm-to-EVM bridge injects any implicit sender-authorization check before dispatching this message) within the tool budget available, nor could I confirm with certainty that this exact `example/cosmwasm/cw721` source (as opposed to a different, unseen production wasm binary) is the code path instantiated for live CW→EVM NFT pointers. The missing `info.sender` vs. `owner`/approval comparison in the Rust source itself is verified directly from the code shown above.

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
```
