### Title
Malformed `InvalidDkgShare` blame transaction panics honest validators via unindexed `enc_keys` lookup - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG blame-handling code indexes `Decryption::enc_keys` with an attacker-selected `Participant` index (`decryptor`) without checking membership. `enc_keys` only contains entries for *other* participants — the local party's own encryption key is never registered. A DKG participant who submits a blame/accusation whose `accuser` field equals the victim validator's own participant index causes a `HashMap` index panic, crashing the processor mid-protocol. The condition is re-triggerable at will, matching the CVE-2020-14383 class: an authenticated, non-administrative party repeatedly crashing a shared service.

### Finding Description
`Decryption::new` starts with an empty `enc_keys` map (`crypto/dkg/pedpop/src/encryption.rs:348-349`). Keys are inserted only via `Decryption::register`, which is called once per remote participant's `EncryptionKeyMessage` inside `SecretShareMachine::verify_r1` (`crypto/dkg/pedpop/src/lib.rs:313-315`) — the local participant `params.i()` is never registered.

`decrypt_with_proof` then does:

```rust
// crypto/dkg/pedpop/src/encryption.rs:385-389
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
```

`self.enc_keys[&decryptor]` panics on a missing key. `decryptor` is the `Participant` index of the accusing party, supplied by the caller (`BlameMachine::blame` / `AdditionalBlameMachine::blame` in the DKG crates) from the `accuser` field of the accusation.

That field is attacker-controlled: `Transaction::InvalidDkgShare` reads `accuser` as an arbitrary `Participant` from signed transaction bytes (`coordinator/src/tributary/transaction.rs:346-349`) with only a non-zero check at parse time. The processor reaches `blame(accuser, accused, …)` (`processor/src/key_gen.rs:543-556`), which funnels into `decrypt_with_proof` with `decryptor = accuser`. Submitting `accuser = victim's i` hits the missing-key panic. Notably, the same function uses `assert!(!self.enc_keys.contains_key(&participant))` in `register` (`encryption.rs:356-359`), confirming indexing assumptions here are enforced by panic rather than error returns.

### Impact Explanation
A single crafted accusation crashes every honest validator's processor that evaluates the blame (all validators evaluate on-chain DKG transactions). Since the malicious participant can keep signing and submitting new `InvalidDkgShare` transactions, the crash is repeatable, denying the DKG/signing pipeline — directly analogous to the Samba flaw where an authenticated user repeatedly crashes the RPC server. This is availability-only; no key material is leaked. Severity: Medium.

### Likelihood Explanation
Reachable by any current DKG participant able to get a signed `InvalidDkgShare` transaction included — the same low privilege level as the CVE (authenticated, non-administrative). Triggering requires only choosing `accuser` equal to a target's (or each validator's own) participant index; no cryptographic work is needed. It is deterministic, not probabilistic.

### Recommendation
In `crypto/dkg/pedpop/src/encryption.rs`, replace the indexing lookup in `decrypt_with_proof` with a checked access returning `DecryptionError::InvalidProof`, e.g. `let Some(dec_key) = self.enc_keys.get(&decryptor) else { Err(InvalidProof)? }`. Additionally, the `assert!` in `Decryption::register` (`encryption.rs:356`) should be converted to a checked error, and callers should validate that `accuser`/`faulty` participant indexes are within `1 ..= n` and not equal to the local index before invoking `blame`.

### Proof of Concept
```rust
// Given a completed round-2 Decryption<C> where params.i() == Participant(3),
// enc_keys holds keys for all participants *except* 3.
// An InvalidDkgShare tx with accuser = 3 forces:
let decryption: Decryption<Ristretto> = /* victim's decryption state */;
// msg is any EncryptedMessage with a *valid* PoP so execution reaches the dleq.verify line:
decryption.decrypt_with_proof(
    /* from = */ accused,
    /* decryptor = */ Participant::new(3).unwrap(), // == victim's own index
    msg,
    Some(proof),
);
// Panics at crypto/dkg/pedpop/src/encryption.rs:388:
//   self.enc_keys[&decryptor]  ->  index out of bounds / no entry found for key
```

Caveat: the exact plumbing from `accuser` to the `decryptor` argument of `decrypt_with_proof` runs through `AdditionalBlameMachine::blame` and `processor/src/key_gen.rs:543-556`, which I confirmed passes the on-chain `accuser` value through; the panic site itself is unconditional once `decryptor == params.i()` reaches that line.
