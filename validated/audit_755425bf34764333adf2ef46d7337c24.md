### Title
`_has_redos_structure` fails to detect `{m,n}`-style catastrophic backtracking, allowing untimeouted `re.search` DoS in `check_patterns` - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_has_redos_structure` only recognizes catastrophic-backtracking shapes that use the literal `+`/`*` quantifier characters (`_REDOS_SHAPES`) or overlapping-alternation-under-repetition (`_ALT_UNDER_REP`), so a nested-quantifier pattern written with bounded-repetition syntax like `{1,}` instead of `+` bypasses both checks while remaining exponentially explosive. `_validate_pattern` then accepts and `re.compile`s this regex, and `check_patterns()` later calls `re.search(pattern["regex"], content)` with no timeout wrapper, so a crafted `security-patterns.yaml` entry can hang the PostToolUse hook process on every subsequent Edit/Write.

### Finding Description
`_load_user_patterns` → `_validate_pattern` (`plugins/security-guidance/hooks/extensibility.py:199-244`) calls `_has_redos_structure(regex)` (lines 272-289) before accepting a user-supplied regex. That heuristic is purely syntactic and only matches two hardcoded shapes: [1](#0-0) 

Both `_REDOS_SHAPES` regexes require a literal `+` or `*` character *inside* the parenthesized group (or a literal `.*`), and `_ALT_UNDER_REP` requires a `|` alternation. A regex such as `(a{1,})+b` is structurally identical to the canonical evil regex `(a+)+b` (unbounded inner repetition nested inside unbounded outer repetition), but its inner quantifier is spelled `{1,}` rather than `+`, so it contains no `+`/`*`/`.*`/`|` between the parentheses and evades all three checks in `_has_redos_structure`. `re.compile("(a{1,})+b")` succeeds, so `_validate_pattern` accepts it and it is merged into `extensibility.user_patterns()`.

Later, `check_patterns()` in `security_reminder_hook.py` iterates `SECURITY_PATTERNS + extensibility.user_patterns()` and calls: [2](#0-1) 

There is no timeout, `signal.alarm`, thread-based watchdog, or length cap around this `re.search` call — the `except Exception` only catches regex *compile/runtime errors*, not a hang. Against attacker-chosen `content` (any edited file body containing a long run of `a` with no trailing `b`, e.g. `"a" * 40 + "!"`), `re.search` on `(a{1,})+b` exhibits classic exponential backtracking and will not return in any reasonable time. Since `hooks.json` for `PostToolUse` on `Edit|Write|MultiEdit|NotebookEdit` does not declare a `timeout` field (unlike the `SessionStart` entry, which sets `"timeout": 180`), the CLI's default/no explicit per-hook timeout governs this call path, so the hang directly stalls the hook. [3](#0-2) 

### Impact Explanation
Once such a rule is committed to `.claude/security-patterns.yaml` (project-scoped, loaded via `_load_user_patterns`/`_config_paths`), every subsequent `Edit`/`Write`/`MultiEdit`/`NotebookEdit` that produces content matching the trigger substring pattern (e.g. any file containing a run of the letter used in the crafted regex without the required terminator) causes the PostToolUse hook process to hang. This is a repository-content-triggered denial of service against the security-guidance plugin: pattern-based deny/warn coverage silently stops firing (or the hook times out/errors), degrading the security posture on every edit in the session without requiring any elevated privilege — an ordinary contributor who can add `.claude/security-patterns.yaml` to a repo (committed, project-scoped) can inject this.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs write access to a `.claude/security-patterns.yaml`/`.json` file in the repository (a normal, unprivileged content-authoring action, no admin/maintainer access needed), and needs only match `regex` + non-empty `rule_name`/`reminder` fields to pass `_validate_pattern`. The bypass is deterministic — `_has_redos_structure` is a static syntactic check with no dynamic profiling, so `(a{1,})+b` (or equivalent `{n,}`/`{n,m}` nested-repetition variants) will always evade it. No timing race or environment-specific condition is required; the DoS triggers on the very first edit whose content contains the crafted trigger characters.

### Recommendation
Extend `_has_redos_structure` to normalize bounded-repetition syntax before the shape checks — e.g. treat any `{n,}` or `{n,m}` (with unbounded or large `m`) inside a group the same as a literal `+`/`*` for the purposes of `_REDOS_SHAPES`, or generalize the nested-quantifier detector to match `\((?:[^()]*(?:[+*]|\{\d*,\d*\}))+[^()]*\)(?:[+*]|\{\d*,\d*\})` style shapes. Since purely static heuristics will always be incomplete, additionally wrap the `re.search` call in `check_patterns()` with a hard execution-time bound (e.g. a `signal.alarm`-based timeout on POSIX, or run pattern matching in a subprocess/thread with a `join(timeout=...)` and treat expiry as "no match, log and skip"), so no single crafted or accidental regex can stall the PostToolUse hook indefinitely regardless of whether it slips past `_has_redos_structure`.

### Proof of Concept
Unit/fuzz test to add near `_has_redos_structure`'s existing test suite:
```python
import re, time
from extensibility import _has_redos_structure

def test_bounded_repetition_bypasses_redos_heuristic_but_is_catastrophic():
    regex = r"(a{1,})+b"
    assert _has_redos_structure(regex) is False  # demonstrates the bypass

    evil_input = "a" * 35 + "!"  # no trailing 'b' -> forces full backtrack search
    start = time.monotonic()
    re.search(regex, evil_input)
    elapsed = time.monotonic() - start
    assert elapsed < 1.0, f"catastrophic backtracking took {elapsed}s for a validated pattern"
```
Expected result on current code: `_has_redos_structure` returns `False` (heuristic bypassed) and the `re.search` call takes exponentially longer as the input length grows (well over the 1s bound at ~30-40 chars), demonstrating that a pattern accepted by `_validate_pattern` can hang `check_patterns()`'s `re.search(pattern["regex"], content)` call with attacker-controlled edit content.
