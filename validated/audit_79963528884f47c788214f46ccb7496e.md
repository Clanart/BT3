Audit Report

## Title
`BlockIdRepairType::FecSetRoot` Merkle-Proof Verification Accepts Padding-Ambiguous Leaf Index Without Length/Binding Checks - (File: core/src/repair/serve_repair.rs)

## Summary
`BlockIdRepairType::verify_response`'s `FecSetRoot` branch only checks `fec_set_proof.is_empty()` and passes the raw, unbound `fec_set_root` hash into `merkle_tree::verify_merkle_proof` with no exact proof-length check and no binding of `fec_set_index`/leaf count into the leaf value. [1](#0-0)  This mirrors the exact padding-collision issue that the sibling `ParentAndFecSetCount` branch was hardened against (via an exact `proof_size` length check and binding `fec_set_count` into the leaf hash), but the fix was never applied to `FecSetRoot`. [2](#0-1) 

## Finding Description
`MerkleTree::try_new_with_len` duplicates the last node of an odd-sized level against itself when computing parents (`let other = &nodes[(index + 1).min(offset + size - 1)];`), meaning the true last leaf index `L` and the non-existent index `L+1` produce identical proof-folding results. [3](#0-2)  `get_merkle_root` folds the entire supplied proof and only checks `index == 0` at the end, never validating that `proof.len()` matches the real tree depth for the claimed index. [4](#0-3)  `verify_merkle_proof` simply calls `get_merkle_root` and compares the resulting root. [5](#0-4) 

For `ParentAndFecSetCount`, this ambiguity is closed by two independent guards: an exact `parent_proof.len()` check against `proof_size` derived from `fec_set_count`, and binding `fec_set_count` into `parent_info_leaf` via `hashv`. [6](#0-5)  The regression test `test_verify_fec_set_count_non_malleable` demonstrates the exact attack this defeats: replaying a genuine proof for leaf `fec_set_count` while claiming `fec_set_count + 1` succeeds without the binding, and is rejected with it. This confirms the underlying primitive (`get_merkle_root`/`try_new_with_len`) is exploitable when unguarded.

The `FecSetRoot` branch has neither guard: it only checks `fec_set_proof.is_empty()` (not an exact expected length tied to the true leaf count) and feeds `*fec_set_root` directly as the leaf with no binding to `fec_set_index` or leaf count. [7](#0-6)  Because `FecSetRoot` requests/responses never carry `fec_set_count`, the verifier cannot even reconstruct the length check the sibling branch relies on. Given an odd total leaf count (even `fec_set_count`), the last real FEC-set-root leaf at index `L` is self-duplicated at position `L+1`, so a genuine `(fec_set_root, fec_set_proof)` pair for leaf `L` also verifies against a request claiming `fec_set_index` mapping to leaf `L+1`.

## Impact Explanation
`fec_set_root` accepted via `verify_response` is trusted as the authoritative Merkle root for that FEC set and is subsequently used by `ShredForBlockId` (`fec_set_merkle_root`) to validate individually repaired shreds. [8](#0-7)  An unprivileged repair responder that replays a genuine `(fec_set_root, fec_set_proof)` pair from the padding-duplicate boundary can make the requester accept a wrong `fec_set_root` value for the FEC-set index it actually asked about, corrupting which root is trusted for shred verification in that repair flow — a false-acceptance impact within the repair/blockstore-adjacent scope.

## Likelihood Explanation
Exploitation requires only responding to a public repair request as any unprivileged network peer — no staked/privileged validator role, leaked keys, or trusted plugin assumptions are needed. It requires the target block's `fec_set_count` to be even (odd total leaves, triggering self-duplication at the last-leaf boundary), which is observable from public block structure and not something the attacker needs to force. The codebase itself proves the underlying primitive is exploitable when unguarded, via the existing `test_verify_fec_set_count_non_malleable` regression test for the sibling `ParentAndFecSetCount` path, and the fix was never mirrored onto `FecSetRoot`.

## Recommendation
Bind `fec_set_index` (or the leaf's true position) and ideally the true total leaf count into the `fec_set_root` leaf hash before calling `verify_merkle_proof`, analogous to `parent_info_leaf`'s binding of `fec_set_count`. Additionally, enforce an exact expected `fec_set_proof.len()` derived from `merkle_tree::get_proof_size` using a validated total leaf count, rather than merely checking `is_empty()`, mirroring the `ParentAndFecSetCount` branch.

## Proof of Concept
1. Construct a block whose double-Merkle tree has an even `fec_set_count` (odd total leaves), so the last FEC-set-root leaf is self-duplicated per `MerkleTree::try_new_with_len`'s odd-size duplication logic. [3](#0-2) 
2. As an unprivileged repair responder, capture the genuine `(fec_set_root, fec_set_proof)` for the real last leaf index.
3. When a validator sends `BlockIdRepairType::FecSetRoot { slot, block_id, fec_set_index }` targeting the padding-duplicate boundary leaf, reply with the captured `(fec_set_root, fec_set_proof)` unmodified.
4. `verify_response`'s `FecSetRoot` branch calls `merkle_tree::verify_merkle_proof(*fec_set_root, leaf_index, fec_set_proof, *block_id)`, which succeeds because neither an exact-length check nor a leaf-binding check exists, analogous to the pre-fix behavior reproduced by `test_verify_fec_set_count_non_malleable` for the sibling code path.

```rust
pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}
```

```rust
pub fn verify_merkle_proof(
    node: Hash,
    index: usize,
    proof: &[u8],
    expected_root: Hash,
) -> Result<(), Error> {
    let proof = proof
        .chunks(SIZE_OF_MERKLE_PROOF_ENTRY)
        .map(<&MerkleProofEntry>::try_from)
        .map(|entry| entry.map_err(|_| Error::InvalidMerkleProof))
        .collect::<Result<Vec<_>, Error>>()?;
    let merkle_root = get_merkle_root(index, node, proof)?;

    (merkle_root == expected_root)
        .then_some(())
        .ok_or(Error::InvalidMerkleProof)
}
```
