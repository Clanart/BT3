### Title
Division-by-zero panic in consensus liquidity reward split when both CN staking and CL pool are empty — node crash on block finalization (state transition) - ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split` (used by the reward module to divide proposer/staker rewards between a validator's own CN stake and its registered Consensus Liquidity (CL) pool) computes `totalAmount = cnAmountBig + clAmountBig` and unconditionally divides by it. If a validator's CN staking amount is `0` (e.g. it has withdrawn all its CNStaking balance while still registered) and its CL pool (a `PublicDelegation` vault) also has `0` staked (e.g. a freshly registered CL pool that has not yet received its first deposit — the exact "empty pool" precondition from the referenced report), `totalAmount` becomes `0`. `big.Int.Div` in Go panics on division by zero, which is an unrecoverable runtime panic rather than a checked revert. This code runs inside `FinalizeState`/reward-distribution, i.e., deterministic state-transition logic executed by every full node and validator, so the panic crashes every node processing that block.

### Finding Description
`Split` blindly divides by `totalAmount` without a zero check: [1](#0-0) 

This function is invoked for the proposer's reward split with no minimum-stake or non-zero-total guard — the only precondition checked is whether `CLStakingInfo` is non-nil, not whether the combined CN+CL stake is non-zero: [2](#0-1) 

Compare this to the staker-reward path (`assignStakingRewardsFlex`/`assignStakingRewards`), which only calls `Split` for CNs that already passed a `StakingAmount >= minStake` (or `> threshold`) filter, guaranteeing a non-zero numerator for `totalExcess`-style divisions: [3](#0-2) 

The proposer path has no equivalent filter — the block's actual proposer is looked up directly by `RewardAddr == config.Rewardbase` and `Split` is called on it regardless of its stake amount: [4](#0-3) 

`CLStakingInfo.CLStakingAmount` is sourced from the CL registry via `MultiCallDPStakingInfo`, which reflects the current total assets staked into a validator's `PublicDelegation` pool: [5](#0-4) 

`consolidateNodes` attaches a `CLStakingInfo` to a CN purely based on registry entries, independent of whether any assets have actually been deposited into that pool, and independent of the CN's own current `StakingAmount`: [6](#0-5) [7](#0-6) 

So the two independent zero-conditions (CN stake = 0, CL pool stake = 0) can coincide for the elected proposer's `consolidatedNode`, and there is no guard anywhere in the reward path to prevent `Split` from being invoked in that state.

### Impact Explanation
`big.Int.Div(x, 0)` panics in Go; this is not caught anywhere in the reward/state-transition call path shown. A panic during `FinalizeState` (block finalization / deferred reward distribution) is fatal to the node process handling that block. Since this logic is deterministic and executed identically by every full node and validator when processing the same block, a single occurrence of this precondition (0 CN stake + 0 CL stake for the current proposer, post-Prague/KIP-226) would crash every node in the network simultaneously — a total halt of block production/state transition, i.e. loss of core protocol availability, which is categorically worse than the original report's "division reverts, DoS until price recovers" because there is no way to route around a process crash; the chain simply stops until node operators patch and restart.

### Likelihood Explanation
Reaching this requires:
1. A validator (CN) registers a CL pool (`PublicDelegation`) via CLRegistry — an operator action, not requiring any deposit yet (0 CL stake, directly analogous to "first depositor hasn't deposited yet" / "pool value rounds to 0" from the reference report).
2. That same validator's own CNStaking balance is (or becomes) `0` while it is still registered in the AddressBook and can still be selected as block proposer in the window where StakingInfo is sourced from a stale/previous block (per the staking module's source-block lag rules).
3. That validator is selected as the block proposer for a block being finalized under Prague rules (`IsPrague` + `CLStakingInfo != nil`).

This is a narrow window that depends on validator/CN operator behavior (withdrawing stake, registering CL pools before first deposit) rather than an arbitrary unprivileged transaction sender, so likelihood is low but the precondition is achievable through ordinary, unprivileged staking/CL-registration/withdrawal operations without any special privilege, and the reference report explicitly shows the "pool with zero value causes division" pattern is a known, reachable pattern in this exact codebase (public delegation / consensus liquidity feature is new with Prague/KIP-226).

### Recommendation
In `consolidatedNode.Split`, check `totalAmount.Sign() == 0` before dividing and return `(amount, 0)` (or route the entire amount to the CN) instead of dividing. Additionally, in `specWithProposerAndFundsFlex`/`specWithProposerAndFunds`, treat a CN with `StakingAmount == 0` and `CLStakingInfo.CLStakingAmount == 0` the same as `CLStakingInfo == nil` (skip the split and pay the full reward to the CN's reward address), mirroring the existing minStake-based filtering already used for staker-reward allocation.

### Proof of Concept
1. After Prague/KIP-226 activation, validator V registers a `PublicDelegation` CL pool for its node in `CLRegistry` before any user deposits into it → `CLStakingInfo.CLStakingAmount == 0` for V.
2. V withdraws its CNStaking balance to `0` via its `CnStakingV4` contract while remaining registered in AddressBook (still eligible to be selected as proposer during the staking-info lag window described in `kaiax/staking/README.md`).
3. V is elected proposer for block N.
4. During `FinalizeState`/deferred reward computation for block N, `specWithProposerAndFundsFlex` (or `specWithProposerAndFunds`) finds V's `consolidatedNode` with `CLStakingInfo != nil`, and calls `cn.Split(proposer)`. [8](#0-7) 
5. Inside `Split`, `cnAmountBig = 0`, `clAmountBig = 0`, so `totalAmount = 0`, and `clAmount.Div(clAmount, totalAmount)` panics with "division by zero." [9](#0-8) 
6. Every full node/validator processing block N hits the identical panic during block finalization, crashing the node process and halting chain progress network-wide.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}
