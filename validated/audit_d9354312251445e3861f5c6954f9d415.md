### Title
Non-20-byte receiver address passes bech32/hex validation in ERC20 IBC callback, causing minted ERC20 tokens to be credited to a different address than the one holding the escrowed bank coins - ([File: x/erc20/keeper/ibc_callbacks.go])

### Summary
The ENS report shows that an address decoder accepted a byte string whose length was not the required 20 bytes and silently truncated it to derive an unrelated "owner" address instead of rejecting the malformed input. The Cosmos EVM analog is the address-length validation used in the ERC20 IBC receive-callback path: `evmCodec.StringToBytes` (used by `x/erc20/keeper/ibc_callbacks.go`) and `sdk.VerifyAddressFormat` do not enforce a fixed 20-byte length, and the resulting arbitrary-length bytes are later passed through `common.BytesToAddress`, which truncates to the last 20 bytes (or left-pads) instead of rejecting. This creates a mismatch between the account that legitimately holds the bank-escrowed IBC coin and the EVM address that receives the freshly minted ERC20 representation.

### Finding Description
When an IBC token arrives at a Cosmos EVM chain via ICS20, `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket` decodes the packet's `data.Receiver` string using the configured address codec: [1](#0-0) 

That codec is `encoding/address/address_codec.go`'s `evmCodec.StringToBytes`, which accepts either a hex address or a bech32 address and only calls `sdk.VerifyAddressFormat(bz)` before returning the raw bytes: [2](#0-1) 

`sdk.VerifyAddressFormat` in the Cosmos SDK, when no custom `AddressVerifier` is registered (confirmed - no `SetAddressVerifier`/`AddressVerifier` call exists anywhere in this repository), only checks that the address is non-empty and does not exceed `address.MaxAddrLen` (255 bytes by default) — it does **not** require exactly 20 bytes. Bech32 itself has no built-in length constraint tied to a specific decoded-byte length, so an attacker can construct a bech32 string with the chain's HRP prefix that decodes to, e.g., 32 bytes (a common length for module/ICA-derived addresses) and it will pass validation.

The decoded, non-20-byte `recipientBz` is then wrapped as `sdk.AccAddress(recipientBz)`, used to look up/create the receiving account, and — critically — passed into `common.BytesToAddress(recipient.Bytes())` when minting the ERC20 representation: [3](#0-2) [4](#0-3) 

`common.BytesToAddress` (go-ethereum) does not reject wrong-length input — for input longer than 20 bytes it takes the rightmost 20 bytes; for shorter input it left-pads with zeroes. This is precisely the "silently truncate instead of revert" bug class described in the ENS report.

Because the underlying ICS20 bank-side credit (performed earlier by the standard transfer module, before the ERC20 middleware runs) uses the full-length `sdk.AccAddress(recipientBz)` to hold the escrowed/minted native coin, while the ERC20 middleware's mint step derives its EVM recipient by truncating the same bytes via `common.BytesToAddress`, the **native bank balance owner** and the **ERC20-token recipient** can end up being two different, unrelated addresses whenever `recipientBz` is not exactly 20 bytes.

### Impact Explanation
This breaks the 1:1 accounting invariant between native Cosmos coin custody and its ERC20 representation (an explicitly in-scope "asset-representation path" invariant). Two concrete critical outcomes are possible:
1. **Fund misdirection/loss**: the ERC20 tokens are minted to `common.BytesToAddress(recipientBz)` (last-20-bytes truncation), an address that generally has no relationship to, and no ability to withdraw, the underlying bank-held coin sitting under the full-length `sdk.AccAddress(recipientBz)`. The intended recipient can lose access to their transferred value, and an attacker who can predict/target the truncated 20-byte suffix can have ERC20 tokens minted to an address they control while the corresponding bank-side native coin becomes stuck/unreachable (since nothing in the EVM/bank interfaces addresses accounts by anything other than the truncated 20-byte or native 20-byte form) — effectively "duplication"/misallocation of spendable value across the native/ERC20 representations.
2. Because a single sender fully controls the `receiver` field of their own outgoing ICS20 packet, this is triggerable by any ordinary, unprivileged user (not a validator/relayer/admin), satisfying the "unprivileged trigger" requirement.

### Likelihood Explanation
Likelihood is comparable to the downgraded "note" severity in the original ENS finding: it requires the attacker/sender to deliberately construct an invalid-length (non-20-byte) bech32/hex receiver string. Cosmos SDK does not, by default, restrict `sdk.VerifyAddressFormat` to exactly 20 bytes, so this is not blocked by any built-in guard in this repository. No relayer or validator collusion is required — only crafting the `receiver` field of a standard ICS20 transfer message on the counterparty chain.

### Recommendation
- Enforce that `recipientBz` returned from `evmCodec.StringToBytes` (and any other address-codec paths feeding EVM addresses) is exactly 20 bytes before proceeding, rejecting the packet/mint operation otherwise (mirroring the ENS remediation of validating length before deriving an address rather than silently truncating).
- Avoid using `common.BytesToAddress` on Cosmos-side byte slices whose length has not been explicitly validated as 20 bytes; return an error instead of truncating/padding.
- Register a strict `sdk.Config.SetAddressVerifier` (or equivalent explicit length check) for the chain so `sdk.VerifyAddressFormat` cannot be satisfied by non-20-byte inputs used for EVM-facing flows.

### Proof of Concept
Exact byte-level confirmation of the bank-side crediting behavior in `x/erc20/keeper/ibc_callbacks.go`'s companion transfer-module OnRecvPacket call was not fully traced within the available tool budget (specifically, whether the standard ICS20 transfer module's own receiver-address parsing enforces 20 bytes independently, which would affect exploitability). This should be verified with a live/integration test:
1. Craft an ICS20 `FungibleTokenPacketData` with `Receiver` set to a bech32 string (using the destination chain's HRP prefix) that decodes to a byte slice of length ≠ 20 (e.g., 32 bytes, similar to an `address.Module`-derived address).
2. Submit the IBC transfer packet to the Cosmos EVM chain.
3. Observe that `evmCodec.StringToBytes` and `sdk.VerifyAddressFormat` accept the oversized payload (no `AddressVerifier` is registered in this repo).
4. Confirm in `x/erc20/keeper/ibc_callbacks.go` (`OnRecvPacket`) that `common.BytesToAddress(recipient.Bytes())` truncates to the last 20 bytes and that the ERC20 `ConvertCoinNativeERC20` mint uses this truncated address, while the bank keeper's coin balance (if separately checked) remains under the full, untruncated `sdk.AccAddress(recipientBz)`.
