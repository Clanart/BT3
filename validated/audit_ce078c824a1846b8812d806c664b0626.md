### Title
Untrusted identity nonce commitment panics Bitcoin transaction signing - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
A signing participant can supply a Bitcoin FROST preprocess whose aggregate Schnorr nonce commitment is the point at infinity. During `sign`, `Hram::hram` calls `x(R)`, which expects an x-coordinate and panics for the identity point, instead of returning a `FrostError`.

### Finding Description
`TransactionSignMachine::read_preprocess` accepts one serialized FROST preprocess for every transaction input. [1](#0-0)  Each preprocess is decoded by `AlgorithmSignMachine::read_preprocess`, which accepts attacker-controlled nonce commitments and an addendum. [2](#0-1)  The nonce commitments are parsed from public bytes through `Commitments::read`, `NonceCommitments::read`, and `GeneratorCommitments::read`; these functions return `io::Result` rather than requiring nonzero/identity-free commitments. [3](#0-2) [4](#0-3) 

After preprocessing, `AlgorithmSignMachine::sign` binds the submitted commitments, computes the nonce sums `Rs`, and passes them to the algorithm’s `sign_share`. [5](#0-4)  For Bitcoin, `Schnorr::sign_share` delegates to the IETF Schnorr implementation, which computes the challenge by calling `Hram::hram` with `nonce_sums[0][0]`. [6](#0-5) [7](#0-6) 

`Hram::hram` calls the private `x` helper on `R`. [8](#0-7)  `x` unconditionally expects an x-coordinate, and `to_encoded_point(true)` does not provide one for the point at infinity, causing a panic on `expect("point at infinity")`. [9](#0-8)  The Bitcoin Schnorr wrapper explicitly documents that infinity can panic, but the FROST parser has no identity rejection that converts this case into an error before signing. [10](#0-9) 

### Impact Explanation
An unprivileged signing participant can crash the local signing task or process during Bitcoin transaction signing by submitting a malicious preprocess. This is a remote denial of service against threshold transaction production; the signer panics while handling bytes supplied by the peer rather than reporting `FrostError::InvalidPreprocess`.

### Likelihood Explanation
The attacker only needs to participate in a signing round and send a malformed preprocess. The serialized preprocess is fixed-size attacker-controlled data, so no key disclosure, validator privilege, or special transaction is required. The attacker can either encode the identity commitment directly if the ciphersuite accepts the canonical infinity encoding, or choose the two nonce commitments so their bound sum becomes identity.

### Recommendation
Reject identity nonce commitments during `read_preprocess`/`Commitments::read`, or check `R.is_identity()` before invoking `Hram::hram` and return `FrostError::InvalidPreprocess` for the responsible participant. The check should cover the post-binding aggregate nonce, not merely the raw `D` commitment, because an attacker can choose `D` and `E` so that `D + rho * E` is identity.

### Proof of Concept
For a one-input `TransactionSignMachine`, submit a preprocess for each required peer containing an identity nonce-commitment pair. Conceptually:

```rust
let identity = <Secp256k1 as Ciphersuite>::G::identity().to_bytes();
let mut preprocess = Vec::new();
preprocess.extend_from_slice(identity.as_ref()); // D
preprocess.extend_from_slice(identity.as_ref()); // E

let parsed = signing_machine.read_preprocess(&mut preprocess.as_slice())?;
let mut preprocesses = HashMap::new();
preprocesses.insert(attacker_participant, parsed);

// Panics in Hram::hram -> x(R) when the bound aggregate R is infinity.
let _ = signing_machine.sign(preprocesses, &[]);
```

If the aggregate binding factor modifies the raw commitments rather than accepting the direct identity pair, choose `E` nonzero and `D = -rho * E` after calculating the participant’s public binding factor; this produces an identity post-binding `R` and reaches the same panic.
