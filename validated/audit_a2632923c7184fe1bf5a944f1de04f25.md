### Title
Cached FROST preprocess (nonce pair) is deterministically reused for every signing call within a `DkgConfirmer` attempt, enabling secret-share recovery via ROS-style share reuse - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` derives the FROST preprocess deterministically from a `CachedPreprocess` seed stored in the DB under a key consisting only of `context`. For `DkgConfirmer`, `context = (b"DkgConfirmer", attempt)`, so every `share_internal` call inside one attempt rebuilds `AlgorithmSignMachine::from_cache` with the same seed and therefore the same nonce pair `(d, e)`. Each call emits a fresh signature share `s = (d + ρ·e) + c·λ·x` over the same reused nonces. If a confirmer produces three shares under one attempt (e.g., `share()` followed by `complete()`, plus a re-issued `share()` for a different `key_pair`/preprocess set — both publicly reachable entry points), the same `(d, e)` is reused under different binding factors `ρ` and challenges `c`, yielding a linear system from which the secret share `x` (and nonces `d`, `e`) is recovered.

### Finding Description
- `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148) checks `CachedPreprocesses::get(self.txn, &self.context)`; if present it XOR-decrypts the stored 32-byte seed and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`. Per the FROST spec doc (spec/cryptography/FROST.md:47-62), a cached preprocess is a seed deterministically deriving the nonces — reuse of a seed means reuse of the preprocess/nonces.
- `share_internal` (signing_protocol.rs:150-181) calls `self.preprocess_internal(participants).0` — i.e., every share computation reconstructs a machine from the *same* cached seed; the machine is consumed but the DB cache is never invalidated.
- The cache key is only `self.context`. For `DkgConfirmer` the context is `(b"DkgConfirmer", self.attempt)` (signing_protocol.rs:274-277), so it does not vary per `key_pair`, per preprocess set, or per invocation.
- `DkgConfirmer::share` and `DkgConfirmer::complete` (signing_protocol.rs:304-327) each invoke `share_internal`, which signs `set_keys_message(...)`. `complete` re-signs to rebuild the machine (`self.share_internal(preprocesses, key_pair).expect(...)`). Distinct submitted `preprocesses` maps (or distinct `key_pair`s confirmed under the same attempt) change the signing set / message, hence different `ρ` (`BindingFactor::calculate_binding_factors`, crypto/frost/src/nonce.rs:161-173) and different challenge `c`, while `(d, e)` stay constant.
- Each emitted share is `s_i = d + ρ_i·e + c_i·λ·x` (nonce combination `base + rho * actual` at crypto/frost/src/sign.rs:386-396, `sign_share`). With `k` shares under one attempt there are `k` equations in 3 unknowns `(d, e, λ·x)`; `k ≥ 3` determines the secret share `x` exactly.

### Impact Explanation
Recovery of a coordinator's (validator's) MuSig/FROST secret share for the tributary signing key. Combined with the shares of `t-1` colluding or subsequently compromised validators — or repeated across attempts where this pattern recurs — this degrades the threshold assumption of the substrate confirmation signatures (`set_keys_message` authorizes key rotation). It is a nonce-reuse/key-share-recovery primitive: the signer signs unintended linear combinations of its secret because the preprocess, which MUST be single-use per `SignMachine::cache` (crypto/frost/src/sign.rs:209-213), is replayed.

### Likelihood Explanation
Requires the coordinator to emit ≥3 shares under one `attempt` context. `share` and `complete` already produce two; a third arises if `share`/`complete` is invoked again for the same attempt (e.g., re-driven message handling, multiple `key_pair` confirmations, or retry after an error — the DB cache persists across reboots precisely so this path is re-entered). No malicious-validator collusion is needed for the nonce reuse itself; the attacker only needs to observe the broadcast shares, which are public protocol messages.

### Recommendation
Key `CachedPreprocesses` by a value that uniquely identifies the signing session (context + digest of `participants` + digest of the preprocess set or a monotonically increasing counter), and delete the cached seed once consumed rather than re-deriving from it on every `share_internal`. Alternatively, store the consumed machine state instead of rebuilding `from_cache` per call.

### Proof of Concept
1. Within one `DkgConfirmer` attempt, the coordinator calls `share(preprocesses_A, key_pair_1)` → emits `s_1 = d + ρ_1·e + c_1·λ·x`.
2. `complete(preprocesses_B, key_pair_1, shares)` internally calls `share_internal` again → `s_2 = d + ρ_2·e + c_2·λ·x` with identical `(d, e)` since `from_cache` rebuilt the machine from the same `CachedPreprocesses` entry.
3. Any further `share`/`complete` under the same `attempt` (different `key_pair` or preprocess set) → `s_3 = d + ρ_3·e + c_3·λ·x`.
4. ρ_i are computable publicly (crypto/frost/src/nonce.rs:161-173 binds them to the transcript of preprocesses), c_i are public challenges, λ is the public Lagrange coefficient. Solve the 3×3 linear system over `C::F` for `(d, e, λ·x)` → recover the coordinator's secret share `x`.
