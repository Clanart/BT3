## Title
`CommitStatusStore` LRU cache bounds cached CI check-run objects only by entry count, not by byte size, allowing attacker-controlled GitHub Checks data to exhaust renderer memory - ([File: app/src/lib/stores/commit-status-store.ts])

### Summary
`CommitStatusStore` caches the combined CI status for a commit ref keyed by `endpoint/owner/name/ref` in a `QuickLRU` capped at `maxSize: 250` entries. [1](#0-0) 
Like the Besu `FutureMessageBuffer`, eviction is governed purely by a fixed *count* of retained items, with no accounting for the actual byte size of each entry.

### Finding Description
Each cache entry stores an `ICombinedRefCheck`, which embeds a `ReadonlyArray<IRefCheck>` — one object per check run/status returned by the GitHub API for a given ref. [2](#0-1) 
Each `IRefCheck` includes attacker/repo-owner-controlled string fields such as `name`, `description`, `appName`, `htmlUrl`, plus `actionJobSteps` and `actionsWorkflow` (workflow run metadata) for Actions-based checks. [3](#0-2) 

Anyone who can push commits/branches to a repository the victim has cloned in Desktop (or who controls a CI-integrated GitHub App reporting check runs) fully controls: the number of distinct refs (branches/PRs) that will each occupy one cache slot, and the number/size of check runs and their string fields per ref (check names, descriptions, workflow job step names, log/HTML URLs — up to GitHub API limits, which are large, e.g. many KB per field and up to hundreds of check runs per ref). `CommitStatusStore.getChecksForRef` fetches and appends all statuses/check-runs into a single array before caching it: [4](#0-3) 

Because the LRU only enforces "keep at most 250 keys," it does nothing to prevent each of those 250 retained values from being maximally large (many check runs × maximal string fields × large arrays of workflow job steps). Unlike the git-terminal-output buffers in this codebase, which explicitly cap by *character length* via `pushTerminalChunk`, [5](#0-4) 
the `CommitStatusStore` cache (and similarly `AheadBehindStore`'s `QuickLRU<string, IAheadBehind | null>` cache, though that value type is small/fixed-size) has no equivalent byte-size ceiling. [6](#0-5) 

### Impact Explanation
An attacker who controls a repository (or a GitHub App/CI integration reporting checks against it) that the victim has open in GitHub Desktop can cause the victim's Desktop process to retain up to 250 large `ICombinedRefCheck` payloads simultaneously by creating many branches/PRs and causing checks to be requested for each (e.g., via background refresh of open PRs or by having the user browse PR/branch check statuses, which is a normal, low-friction user action). Because entry size is unbounded, total retained memory can be pushed far beyond what a 250-item assumption implies, potentially degrading the renderer or main process and disrupting the user's workflow — a memory-exhaustion condition in the same class as the Besu finding, though the bound here (250 keys, single-repo scope, requires normal UI interaction like viewing PR checks) is much more constrained than an internal consensus buffer, so severity is lower.

### Likelihood Explanation
Medium-to-low likelihood: exploitation requires the victim to actually view/subscribe to CI checks for the attacker-influenced refs (`CommitStatusStore.subscribe`/background refresh path triggers population), and GitHub API responses are themselves subject to server-side size/pagination limits, which caps how large a single entry can realistically get. Still, no client-side guard exists to prevent a determined attacker from maximizing per-entry size within those API limits across up to 250 distinct refs.

### Recommendation
Extend `CommitStatusStore`'s cache (and any other `QuickLRU`/count-only caches storing externally-sourced, variably-sized payloads) to track approximate byte size of cached values (e.g., sum of string field lengths and array lengths) and evict based on a combined byte budget in addition to entry count, mirroring the approach already used for git terminal output buffering (`pushTerminalChunk`). Alternatively, cap the number and size of `IRefCheck` entries per ref before caching (e.g., truncate `description`, `name`, and `actionJobSteps` to a fixed maximum length/count) at the point they are constructed in `ci-checks.ts`.

### Proof of Concept
1. Attacker creates a repository (or GitHub App integration) that the victim clones/adds in GitHub Desktop.
2. Attacker creates a large number of branches/PRs (up to the 250-entry cache ceiling) and, for each, reports many check runs via the Checks API, each with maximal-length `name`, `output.summary`/`text`-derived description strings, and large `actionJobSteps` arrays.
3. Victim opens the repository in Desktop and views/subscribes to CI status for these refs (e.g., via the pull request list or branch checks UI), causing `CommitStatusStore.getChecksForRef` → cache.set for each ref.
4. Because `QuickLRU({ maxSize: 250 })` only limits key count, all 250 maximal-size entries are retained simultaneously in the renderer's memory, with no fallback size-based eviction. This can be confirmed by inspecting `CommitStatusStore`'s cache definition and the unbounded shape of `ICombinedRefCheck`/`IRefCheck` cited above; a full end-to-end memory measurement would require live testing beyond static code review.
