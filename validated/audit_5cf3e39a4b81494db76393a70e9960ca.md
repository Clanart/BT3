## Finding

### Title
Clawback batch auto-claim DoS: one already-spent coin in a batched claim bundle permanently stalls all other batched claims - (File: chia/wallet/clawback_manager.py)

### Summary
`ClawbackManager.spend_clawback_coins()` and `auto_claim_coins()` batch multiple independent clawback merkle coins - which may belong to entirely different sender/recipient pairs - into a single atomic `WalletSpendBundle`. Because a Chia spend bundle either succeeds or fails as a whole, if just one coin in the batch has already been spent (e.g. because its sender exercised their normal right to claw it back before the batch confirms), the whole aggregate bundle is rejected on-chain as a `DOUBLE_SPEND`. Before the bundle is even submitted, however, every coin in the batch has already been marked `sent > 0` via `transaction_store.increment_sent(...)`. Since both the auto-claim loop and the manual `spend_clawback_coins` RPC skip any coin whose transaction record has `sent > 0` (unless `force=True`), the legitimate, still-unspent coins that were bundled alongside the "poisoned" coin become permanently stuck and are silently excluded from all future automatic (and default manual) claim attempts.

### Finding Description
`ClawbackManager.auto_claim_coins()` collects all of a wallet's unspent, mature clawback-recipient coins - which can originate from many unrelated senders - into a single dict and calls `spend_clawback_coins()` once the batch reaches `auto_claim_batch_size`: [1](#0-0) 

Inside `spend_clawback_coins()`, for every coin in the batch it unconditionally marks the underlying incoming transaction as pending/sent before the aggregate bundle is ever pushed to the network: [2](#0-1) 

All coin spends collected in this loop are then combined into one `WalletSpendBundle`: [3](#0-2) 

If any single one of those coins is spent by its sender (a normal, always-available clawback action for the sender) between the time it was selected for this batch and the time the aggregate bundle is broadcast/confirmed, the whole `WalletSpendBundle` will fail consensus/mempool validation with `DOUBLE_SPEND`, because spend bundles are atomic. None of the *other*, still valid, coin spends in that batch get included on-chain.

Because `increment_sent` was already called for every coin in the batch regardless of the eventual broadcast outcome, both the next `auto_claim_coins()` pass and the default manual `spend_clawback_coins` RPC call will skip these coins going forward: [4](#0-3) 

The RPC entry point batches user-selected coin IDs the same way with no per-coin isolation of failures once they enter a batch: [5](#0-4) 

The only escape hatch is the CLI/RPC `force=True` flag on `spend_clawback_coins`, which is not used by the automatic claim path at all: [6](#0-5) 

### Impact Explanation
A clawback sender is not privileged in any special way - clawing back your own outgoing clawback payment before the recipient claims it is a normal, documented feature. However, doing so at the moment the recipient's wallet happens to bundle that coin together with other, unrelated senders' payments into one auto-claim transaction causes the entire bundle to fail on-chain, and - critically - silently and permanently strands every other coin in that batch. Those other coins' `sent` flag is already set, so the wallet's automatic claim loop will never retry them, and even a manual, default (non-`force`) claim attempt from the GUI/CLI will refuse to touch them. Funds that were otherwise fully claimable become effectively frozen for the recipient (a fund-lock / spend-triggered transaction halt on the shared claim path) until the recipient becomes aware of the issue and manually reissues the claim with `force=True` for the specific stuck coin IDs. This mirrors the H-02 pattern precisely: a single "poisoned" item bundled into a shared claim operation blocks legitimate claims of unrelated parties/funds bundled alongside it.

### Likelihood Explanation
This requires no special privilege - it only requires the attacker (or even an ordinary, non-malicious sender) to claw back their own payment, which is a core supported action, timed to land while their coin is part of a `auto_claim_batch_size`-sized batch together with other senders' payments to the same recipient. Any wallet that receives multiple clawback payments from different senders and has auto-claim enabled (the default recommended configuration) is exposed. The batch size is attacker-observable/-influenceable indirectly (default `50`, configurable via `set_auto_claim`), and an attacker sending many small clawback payments to a victim, then clawing one back at the right time, can reliably trigger the stuck-batch condition.

### Recommendation
- Do not call `transaction_store.increment_sent()` for a coin until after the aggregate bundle has actually been accepted into the mempool (or at least attempt push first, then mark only the coins that made it into a **successfully accepted** bundle).
- On `DOUBLE_SPEND` / push failure, detect which specific coin(s) in the batch are already spent, remove them from the batch, and automatically resubmit the remaining coins in a fresh bundle instead of leaving all of them marked `sent`.
- Avoid batching unrelated senders'/recipients' clawback coins together for atomicity reasons; consider constructing an independent spend bundle per coin (or grouping only by common risk of coincidental invalidation) so that one bad coin cannot block others.
- Alternatively, have `auto_claim_coins()` proactively re-check coin spent-state immediately before broadcast and drop stale coins from the batch rather than relying on batch-wide atomic failure handling.

### Proof of Concept
1. Recipient wallet `R` enables `auto_claim` with `batch_size >= 2` (`set_auto_claim`, chia/wallet/wallet_node.py:328-345).
2. Two different senders, `A` (attacker) and `B` (victim/unrelated user), each send `R` a clawback payment with the same/similar timelock, landing in the same auto-claim batch window.
3. Once both coins become claimable (timelock matured) and are selected together into one batch by `auto_claim_coins()` (chia/wallet/clawback_manager.py:191-205), both incoming transactions get `increment_sent` called (line 261) and are combined into one `WalletSpendBundle` (line 266).
4. Before this bundle confirms, `A` spends (claws back) their own clawback coin directly (a normal supported action) - this coin is now spent.
5. `R`'s aggregate bundle (containing both `A`'s now-already-spent coin and `B`'s still-valid coin) is submitted and rejected by the mempool as `DOUBLE_SPEND`.
6. `B`'s legitimate incoming payment remains unclaimed on-chain, but its `TransactionRecord.sent` is already `> 0`, so subsequent `auto_claim_coins()` runs skip it (line 226-230), and a default manual `spend_clawback_coins` RPC call for `B`'s coin also returns no transaction (same `sent > 0` check) until `force=True` is explicitly passed.
