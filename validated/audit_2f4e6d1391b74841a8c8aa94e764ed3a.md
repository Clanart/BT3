### Title
Incorrect burn accounting in `RebalanceTreasury` reads post-mutation balances instead of pre-mutation snapshots for allocated addresses - ([File: blockchain/system/rebalance.go])

### Summary
`RebalanceTreasury` (used for KIP-103/KIP-160 treasury rebalancing, triggered automatically at a governance-approved hard-fork block) computes the "burnt" amount for each allocated address by reading `state.GetBalance(addr)` *after* the zeroed-address balances have already been cleared to zero in the same function call, rather than using the balance snapshot taken before any state mutation (`result.Before.Allocated`, captured earlier by `fillAllocated`). This mirrors the H-33 pattern of computing a delta/accounting value from a balance that has already been changed by an earlier step in the same routine, rather than from the value that existed before the mutation.

### Finding Description
`fillZeroed` and `fillAllocated` snapshot balances into `result.Before.Zeroed` and `result.Before.Allocated` before any state changes occur: [1](#0-0) 

Execution then proceeds in two ordered steps inside `RebalanceTreasury`. Step 1 zeroes out every "Zeroed" address's balance directly via `state.SetBalance(addr, big.NewInt(0))`. Step 2 iterates the "Allocated" addresses and, for each one, re-reads the *current* on-chain balance via `state.GetBalance(addr)` to decide how much to burn, instead of reusing the already-captured `result.Before.Allocated[addr]` value or reading the balance before step 1 executed: [2](#0-1) 

If any address appears in both the "Zeroed" set and the "Allocated" set (nothing in this function enforces that the two sets are disjoint — the sets are populated purely from `contract.Zeroeds`/`contract.Allocateds`, i.e. from a governance-controlled rebalance contract configured off-chain), step 1 will have already zeroed that address's balance before step 2 reads it. Step 2 then computes `currentBalance = 0` for that address (instead of the true pre-rebalance balance), so `result.Burnt` under-counts the true amount burnt for that account — the exact same "read balance after it was already mutated" bug pattern as the LiquidationAccountant issue, where a balance used for a burn/decrease calculation is read after the value has already been zeroed/transferred out rather than before.

### Impact Explanation
The corrupted `Burnt` value does not affect the actual balances written to state — `state.SetBalance(addr, balance)` in step 2 sets the allocated address to the exact `After.Allocated` value from the contract regardless of `currentBalance`. However, `result.Burnt` is persisted into the block's rebalance memo/receipt (`Memo()`), which is the canonical record of total supply change for this hard-fork event and is relied upon by node operators and downstream tooling (e.g., total-supply computation, auditing, `kaia_getTotalSupply`-style APIs) to reconcile the KAIA supply across the KIP-103/KIP-160 rebalancing event. An incorrect burnt figure causes a state-divergent/incorrect canonical accounting record for total supply that all honest nodes will compute identically (since the bug is deterministic), meaning it does not cause consensus divergence between nodes, but it does corrupt the authoritative supply-accounting output of a governance-critical system operation.

### Likelihood Explanation
This can only trigger if the treasury rebalance contract (KIP-103/KIP-160), which is configured by governance/foundation operators ahead of a scheduled hard fork, lists an address in both the "zeroed" and "allocated" sets. This is not attacker-triggerable by an ordinary transaction sender, bidder, or RPC caller — it requires a specific (arguably atypical/misconfigured) governance-approved rebalance contract state. There is no visible on-chain enforcement in `RebalanceTreasury`, `fillZeroed`, or `fillAllocated` preventing such an overlap, so it is a latent correctness bug rather than a directly attacker-reachable exploit path.

### Recommendation
Compute the `currentBalance` used for burn accounting from the pre-execution snapshot (`result.Before.Allocated[addr]`, or read `state.GetBalance(addr)` before executing the "Execution 1) Clear all balances of zeroeds" loop) instead of re-reading state after zeroed balances have already been cleared. Additionally, consider validating that the Zeroed and Allocated address sets are disjoint before proceeding with rebalancing, returning an error otherwise.

### Proof of Concept
Given a hard-fork rebalance contract configured (by the responsible governance operator) with:
- `Zeroeds = [A]`, `A`'s pre-rebalance balance = 100
- `Allocateds = [A]`, target allocation for `A` = 50

1. `fillZeroed` records `Before.Zeroed[A] = 100`.
2. `fillAllocated` records `Before.Allocated[A] = 100` (same account, read before any mutation).
3. Execution 1 runs: `state.SetBalance(A, 0)` — `A`'s balance is now 0.
4. Execution 2 runs for `A`: `currentBalance := state.GetBalance(A)` returns `0` (not the true pre-rebalance 100), so `result.Burnt.Add(result.Burnt, 0)` incorrectly adds 0 instead of 100 to the burnt tally before `state.SetBalance(A, 50)` sets the final balance.
5. The resulting `Burnt` value in the produced `rebalanceResult`/memo under-reports the true amount burnt by 100 KAIA, corrupting the canonical total-supply accounting record for the rebalance event, even though `A`'s final on-chain balance (50) is itself correct. [2](#0-1)

func (result *rebalanceResult) fillZeroed(contract RebalanceCaller, state *state.StateDB) error {
	numRetiredBigInt, err := contract.GetZeroedCount(nil)
	if err != nil {
		logger.Error("Failed to get ZeroedCount from TreasuryRebalance contract", "err", err)
		return err
	}

	for i := 0; i < int(numRetiredBigInt.Int64()); i++ {
		ret, err := contract.Zeroeds(nil, big.NewInt(int64(i)))
		if err != nil {
			logger.Error("Failed to get Zeroeds from TreasuryRebalance contract", "err", err)
			return err
		}
		result.Before.Zeroed[ret] = state.GetBalance(ret)
		result.After.Zeroed[ret] = state.GetBalance(ret) // will be set as zero if rebalance succeeds
	}
	return nil
}

func (result *rebalanceResult) fillAllocated(contract RebalanceCaller, state *state.StateDB) error {
	numNewbieBigInt, err := contract.GetAllocatedCount(nil)
	if err != nil {
		logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
		return nil
	}

	for i := 0; i < int(numNewbieBigInt.Int64()); i++ {
		ret, err := contract.Allocateds(nil, big.NewInt(int64(i)))
		if err != nil {
			logger.Error("Failed to get Allocateds from TreasuryRebalance contract", "err", err)
			return err
		}

		result.Before.Allocated[ret.Addr] = state.GetBalance(ret.Addr)
		result.After.Allocated[ret.Addr] = ret.Amount
	}
	return nil
