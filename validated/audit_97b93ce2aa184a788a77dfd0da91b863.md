## Finding: Liquidation can be permanently blocked by a stale/invalid price on any single asset held by the borrower, even when other assets price correctly

### Title
Liquidation reverts entirely if any one held asset's oracle price is stale/invalid, preventing recovery of unhealthy positions - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The `liquidate` function fetches prices for every collateral and debt asset a borrower currently holds via `get-assets`, which wraps the multi-asset price resolution in `unwrap-panic`. If validation fails for any single asset in that list — even one irrelevant to the specific `collateral-ft`/`debt-ft` pair being liquidated — the entire liquidation call reverts. This mirrors the AladdinDAO report's pattern: a critical protocol-recovery action (there, minting xToken to re-collateralize; here, liquidating an unhealthy position) is unconditionally blocked by oracle validity gating instead of degrading gracefully.

### Finding Description
`liquidate` builds the borrower's position and then resolves all its held-asset prices at once: [1](#0-0) 

`get-assets` narrows to the borrower's own enabled collateral+debt mask and then calls `price-multi-resolve`, unconditionally unwrapping the result: [2](#0-1) 

`price-multi-resolve` folds over every asset in that list and asserts `valid` across the whole batch — a single failed `price-resolve` call marks the entire batch invalid: [3](#0-2) 

`price-resolve` itself hard-reverts (`asserts! ... ERR-ORACLE-INVARIANT`) whenever the resolved price fails positivity, freshness (`oracle-timestamp-fresh`, gated by per-asset `max-staleness`), or monotonic-timestamp checks: [4](#0-3) 

Because `get-assets` is scoped to *all* assets the borrower holds (not just the specific `collateral-ft`/`debt-ft` pair passed into `liquidate`), a borrower with e.g. STX collateral and USDH debt cannot be liquidated at all if the USDH DIA feed goes stale — even though the liquidator is only trying to repay/seize STX, and the STX Pyth feed is perfectly fresh. The disabled-collateral fallback path in `process-collateral-asset` has the same unconditional-panic behavior on price resolution failure: [5](#0-4) 

### Impact Explanation
Liquidation is the sole mechanism by which the protocol recovers value from undercollateralized positions. If any single held asset's feed becomes stale (a DIA feed pausing, a Pyth confidence spike, or simply an update lapse beyond `max-staleness`) for as long as that condition persists, that borrower's unhealthy position becomes entirely unliquidatable, regardless of how underwater it is. Debt can continue accruing interest and price can keep falling on the *other* (fine) collateral, growing bad debt that ultimately socializes losses to lenders — this lands squarely in the "protocol insolvency" / permanent freezing-of-funds impact class, matching the underlying AladdinDAO bug class of a recovery action being blocked by oracle-validity gating.

### Likelihood Explanation
Any staleness event on a lower-liquidity or less frequently pushed feed (e.g., DIA-sourced `USDH`, or any asset relying on Pyth confidence bounds via `check-confidence`) is sufficient to trigger this, without any attacker action or malicious data — it only requires an oracle update lapse that is entirely plausible in normal operation, especially for assets with tighter `max-staleness` windows.

### Recommendation
Scope price resolution and validity checks in `liquidate`/`get-assets` strictly to the specific collateral/debt asset pair being liquidated where possible, and where a batch of assets must be priced, avoid failing the entire liquidation atomically on one bad feed — either exclude/skip the unrelated asset (using a conservative/last-known-good price) from the health/collateral computation, or expose a fallback path so a stale non-relevant asset cannot block liquidation of positions holding it alongside otherwise-priceable assets.

### Proof of Concept
1. Borrower opens a position with STX collateral and USDH debt.
2. USDH's DIA oracle stops updating and exceeds its configured `max-staleness` (or STX's Pyth confidence spikes, tripping `check-confidence`).
3. STX price crashes, making the position eligible for liquidation (`current-ltv >= ltv-liq-partial`).
4. A liquidator calls `liquidate(borrower, sSTX-token, USDH-token, ...)`; internally `get-assets` resolves prices for both STX and USDH since both are held by the borrower.
5. `price-resolve` for USDH fails freshness/confidence check → `price-multi-resolve` marks the whole batch invalid → `unwrap-panic` in `get-assets` reverts the entire `liquidate` transaction, even though STX (the actual collateral being seized) priced fine.
6. The position remains open and unliquidated until USDH's feed recovers, during which bad debt can grow.

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))
