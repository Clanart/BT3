### Title
Stale line-index-based partial-commit selection re-applied to a freshly re-diffed working tree, causing silent inclusion/exclusion of unintended content on commit - (File: `app/src/lib/git/apply.ts`)

### Summary
`AdapterBase.harvest` in the original report is stale-state-before-critical-operation bug: shares are computed on a stale balance before `harvest` mutates it, silently transferring value between users. GitHub Desktop's partial-commit path has a structurally analogous flaw: `applyPatchToIndex` re-fetches the working-directory diff from disk at staging time and blindly re-applies a `DiffSelection` that was computed against a *different, earlier* diff (the one rendered when the user checked lines in the diff viewer). Because the selection is purely positional (line index in the unified diff), not content-addressed, a mismatch between the diff the user reviewed and the diff staged at commit time can silently commit different lines than the user selected.

### Finding Description
`WorkingDirectoryFileChange.selection` (a `DiffSelection`) stores *line indices* relative to a specific diff, not content or hunk identity. That selection is set by the user in the diff viewer against whatever diff was loaded into `changesState` at that point (`app-store.ts` `updateChangesWorkingDirectoryDiff`/`onLineNumberCheckedChanged` in `side-by-side-diff.tsx`).

When the user clicks Commit, `_commitIncludedChanges` (`app-store.ts:3681-3760`) takes the files currently in `state.changesState.workingDirectory.files` (whatever was last loaded by `_loadStatus`) and calls `createCommit` → `stageFiles` → `applyPatchToIndex`: [1](#0-0) 

Critically, `applyPatchToIndex` does **not** reuse the diff that was shown to the user and against which the selection indices were computed — it calls `getWorkingDirectoryDiff(repository, file)` again, right before formatting the patch: [2](#0-1) 

`formatPatch` then walks the *new* diff's hunks and tests `file.selection.isSelected(absoluteIndex)` using indices that were only valid for the *old* diff: [3](#0-2) 

There is validation logic elsewhere that recomputes `selectableLines` when the diff visibly changes while the file is *actively selected in the UI* (`app-store.ts:3466-3497`), but that only prunes lines that no longer exist in the new diff — it does not prevent the fundamental TOCTOU between "diff shown to user for selection" and "diff fetched for staging," and it does not run at all if the file isn't currently open in the diff viewer (e.g., user reviewed the diff, closed it, then hit Commit; or `_loadStatus` is not re-run between selection and the commit call since `_commitIncludedChanges` uses whatever `workingDirectory.files`/selection is already cached in `repositoryStateCache`).

An attacker who can cause the working tree to change between the time the user reviews/selects diff lines and the time the commit executes — e.g. via a malicious `post-checkout`/`post-merge`/file-watcher-triggered build script inside a cloned/fetched repository, an editor auto-format-on-save triggered by opening a file from that repo, or any background process spawned by content in the repo — can shift hunk boundaries so that the same line indices now correspond to different, attacker-controlled content. Because `formatPatch` only checks `absoluteIndex` membership, it will silently include attacker-inserted lines that the user never reviewed/checked, or drop lines the user did intend to commit, with no error, warning, or diff re-confirmation shown to the user.

### Impact Explanation
This is a silent corruption of what the user commits (and subsequently pushes), matching the specified valid-impact class: an unprivileged attacker who controls content that gets executed/dropped into a cloned/fetched repository's working tree can cause the user to commit and push content they never selected or approved, without any indication in the UI. This could be leveraged to smuggle malicious code, backdoors, or altered logic into a push that the user believes only contains their reviewed, hand-picked lines — a meaningful integrity violation of the commit/push pipeline, directly analogous to the "harvest called after share calculation" stale-state bug in the report (state read before the mutating operation, then blindly acted upon afterwards as if unchanged).

### Likelihood Explanation
This requires a non-trivial but realistic timing window: the working tree must change (line-count/content-shifting change to the *same file* under review) between diff selection and the commit's `stageFiles` call. This is plausible in real developer workflows (auto-formatters, linters-on-save, build watchers, git hooks triggered by branch/file operations happening around the same time) and doesn't require local/physical access, admin rights, or pre-existing malware — only a repository whose tooling (build scripts, hooks, editor config) is attacker-influenced, which is within the stated threat model of "attacker controls a cloned/fetched repository." It is a race/staleness condition rather than a guaranteed one-click exploit, so likelihood is moderate rather than certain; I was not able to find any existing mitigation in the codebase (such as diff hash comparison or re-diff-before-stage confirmation) that would prevent this within the code explored.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-fetch the diff and compare it (e.g., via a hash of the diff/hunks, or line-content comparison) against the diff that was active when the user made the selection; if it differs, abort the partial commit and force the user to re-review the new diff instead of silently re-mapping stale line indices onto new content. Alternatively, store content-addressed (not purely positional) identifiers for selected lines so that shifted/changed hunks cannot be silently reinterpreted.

### Proof of Concept
1. Clone an attacker-controlled repository containing a `modified-file.md` with an innocuous local hook/watcher (e.g. `post-checkout`, or an npm `postinstall`/build script triggered on file save) that appends/prepends lines to `modified-file.md` after a short delay.
2. In GitHub Desktop, open the Changes tab, view the diff for `modified-file.md`, and select only specific lines to commit (leaving others unchecked) via `onLineNumberCheckedChanged` (`side-by-side-diff.tsx:935-961`).
3. Before clicking "Commit," let the attacker's background process rewrite/insert lines into `modified-file.md`, shifting hunk boundaries but keeping the file otherwise plausible.
4. Click Commit. `_commitIncludedChanges` uses the stale `WorkingDirectoryFileChange` with old line-index selection; `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-diffs the file fresh from disk and `formatPatch` (`app/src/lib/patch-formatter.ts:157`) applies the old indices to the new hunks.
5. Inspect the resulting commit: it will contain content at those indices that the user never saw or approved (the attacker's injected lines), while the user believed they committed only their originally reviewed selection — demonstrating silent corruption of the commit contents.
