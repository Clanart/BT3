## Summary

The Sherlock report's core issue: a **mandatory push-transfer to multiple parties inside a single atomic operation** lets any one malicious recipient permanently revert the whole operation, causing the *other, innocent* parties to lose their rightful funds. Hyperbridge's `IntentGatewayV2` settlement path (`_withdraw` / `withdraw`) has the same structural flaw — a loop of push-transfers to escrowed input tokens, executed atomically as part of `onAccept`, that the destination host retries but never bypasses.

### Title
Cross-chain intent settlement can be permanently DOS'd by a single malicious/blockable escrowed token, freezing all other legitimately escrowed funds for the solver - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Finding Description
`fillOrder` on the destination chain lets an unprivileged solver deliver output assets to the order's beneficiary and, on success, dispatches a `RedeemEscrow` message back to the source chain (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`, lines 121-171). On the source chain the message is processed by the ISMP host's `dispatchIncoming` for POST requests, which calls `IApp.onAccept` via a low-level `.call`: [1](#0-0) 

`onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`, which iterates over **every escrowed token in `body.tokens` in a single loop** and pushes each one out with `safeTransfer`/native `.call`: [2](#0-1) 

An order's `inputs` array (set by the user at `placeOrder` time) can contain multiple arbitrary tokens. If any one of those tokens is (or later becomes, e.g. via an owner-controlled pause/denylist) unable to transfer to the beneficiary — the solver, in the `RedeemEscrow` case — the entire `_withdraw` call reverts. Because `dispatchIncoming` treats a failed `onAccept` as "retryable" (it only deletes the receipt so the message can be resubmitted, per the comment on line 813), the message can be resubmitted indefinitely but will **always fail identically** if the blocking condition is permanent (a paused/blacklisted token). This means:

- `_filled[commitment]` never gets set, so the order is never finalized.
- **All** other, perfectly legitimate escrowed tokens in the same order are frozen forever in the loop, even though the solver already delivered the required outputs to the beneficiary on the destination chain in good faith.

This is structurally identical to the M-6 bug class: one push-transfer recipient in a batch of push-transfers can unilaterally and permanently block payout to every other party sharing that atomic transaction.

### Impact Explanation
A malicious order creator can list a token they control (which behaves normally until the solver has committed capital by filling the order) as one of several `order.inputs`. After the solver delivers legitimate output tokens on the destination chain (irreversible, atomic, before the settlement message is even dispatched — see `ExtrinsicIntents.sol` lines 121-171), the creator disables transfers of that one input token to the solver. The solver then permanently loses **all** escrowed inputs for that order — not just the poisoned token — because `_withdraw`'s loop reverts entirely on the first failing transfer. This is a direct, unauthorized loss of funds for an innocent, unprivileged actor (the solver) caused by another unprivileged actor (the order creator), matching the bounty's "stealing or loss of funds" / "logic attack" criteria without requiring any relayer, prover, or admin compromise.

### Likelihood Explanation
The attack requires no privileged role: any user can place an order with a self-controlled, initially-benign-looking ERC-20 as one of several `inputs`, wait for a solver to fill it on the destination chain, and then flip the token's transfer restriction before settlement completes. Solvers evaluating multi-token orders may not anticipate that a single poisoned asset can freeze the entire batch of otherwise-safe collateral, especially since the destination-chain fill already occurred atomically and cannot be undone once outputs are delivered.

### Recommendation
Do not process multiple escrowed tokens for the same order in a single all-or-nothing loop that can be permanently blocked by one token. Instead:
- Adopt a per-token pull mechanism (let beneficiaries claim each token individually) so a single malfunctioning/malicious token cannot lock the others, or
- Isolate each token transfer with a try/catch so failures on one asset don't block release of the rest, escrowing the failed asset separately for later recovery instead of reverting the whole `_withdraw` call.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [TokenA (legit), TokenB (attacker-owned pausable token)]`, escrowing both on the source chain.
2. A solver fills the order on the destination chain via `fillOrder`, delivering the required output assets directly to the beneficiary (attacker) — this transfer is irreversible and already completed (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`, lines 121-135).
3. `fillOrder` dispatches a `RedeemEscrow` POST request back to the source chain naming the solver as beneficiary.
4. Before/while the relayer delivers this message, the attacker calls `pause()`/`blacklist(solver)` on TokenB.
5. When the message is delivered, `EvmHost.dispatchIncoming` invokes `IntentGatewayV2.onAccept` → `_withdraw`, which processes `TokenA` first (success) then reverts on `TokenB`'s transfer (`IntentsBase.sol`, lines 394-410), causing the whole call to revert.
6. `dispatchIncoming` swallows the failure and deletes the receipt "so it can be retried" (`EvmHost.sol`, lines 812-816), but every retry hits the same permanent block — `TokenA` (and the fee amount) remain forever un-released to the solver, who already paid the attacker on the destination chain.         if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
