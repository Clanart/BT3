## Analysis

The Bond Protocol bug is a classic **unbounded loop that grows monotonically with permissionless, low-cost user actions**, embedded in a code path that is invoked frequently and whose cost is not amortized or paginated. The closest structural analog in Agave is the global `ProgramCache`'s `entries` index in `program-runtime/src/loaded_programs.rs`, which is keyed by every unique program `Pubkey` ever deployed on the cluster and is walked in full by `prune()` on every rooted-slot advance.

Unlike `BondAggregator.marketCounter`, deploying a BPF program is a completely permissionless, unprivileged, low-cost action (pay rent + upload bytes via `bpf_loader_upgradeable`). Each unique program id becomes a permanent first-level key in `IndexImplementation::V1::entries: HashMap<Pubkey, Vec<Arc<ProgramCacheEntry>>>` [1](#0-0) . The eviction mechanisms (`sort_and_unload`, `evict_using_random_selection`) only ever unload/shrink `Loaded` executables to bound *memory*; they never remove the outer `Pubkey` keys from `entries` — those are only ever removed by `remove_programs_with_no_entries()`, which requires the per-key `Vec` to become fully empty [2](#0-1) . In practice, since programs are rarely closed/undeployed, `entries.len()` grows roughly proportionally to the total number of distinct programs ever deployed cluster-wide, with no cap.

`Bank::prune_program_cache`, which is called on every new root (via `bank_forks.rs`/`blockstore_processor.rs`/consensus root-advance paths) [3](#0-2) , invokes `ProgramCache::prune`, which does `for second_level in entries.values_mut()` — i.e., iterates over **every single program key ever seen**, on **every root** [4](#0-3) . This is structurally identical to `BondAggregator.liveMarketsBy`'s `for i in 0..marketCounter`: a loop bound by a permissionlessly-inflatable counter, executed on a hot, frequently-invoked path (once per root instead of once per external call, but roots advance continuously as the validator runs).

Similarly, `prepare_program_cache_for_upcoming_feature_set` (called near every epoch boundary) calls `program_cache_guard.get_flattened_entries()` which flattens and clones the *entire* cache (`entries.iter().flat_map(...)`) and then sorts it [5](#0-4) , and `get_flattened_entries` itself is `O(total entries)` [6](#0-5) .

### Title
Unbounded growth of `ProgramCache::entries` causes O(total-programs-ever-deployed) work on every rooted slot and epoch boundary - (File: `program-runtime/src/loaded_programs.rs`)

### Summary
`ProgramCache::prune()`, invoked from `Bank::prune_program_cache()` on every new root, iterates `entries.values_mut()` for every unique program `Pubkey` ever deployed cluster-wide, because the outer `HashMap` keys are never removed except when a program's entire version-history vector becomes empty. Since deploying a new program is a cheap, unprivileged action, an attacker (or organic growth) can drive the size of `entries` arbitrarily high, making a per-root/per-epoch-boundary maintenance operation grow linearly with cumulative program count instead of being bounded or paginated — mirroring the Bond `liveMarketsBy` defect where a per-call loop bound (`marketCounter`) was inflated by permissionless market creation.

### Finding Description
`ProgramCache<FG>::index` is a `HashMap<Pubkey, Vec<Arc<ProgramCacheEntry>>>` where the top-level key space is the set of all program ids that have ever appeared in a loaded-programs interaction [1](#0-0) . The value-clearing eviction routines (`sort_and_unload`/`evict_using_random_selection`) act on the flattened list of *loaded* entries to bound cache *memory*, but they replace an entry's `ProgramCacheEntryType::Loaded` with `Unloaded`/tombstone rather than removing the key from `entries` [7](#0-6) . The only place that removes a top-level key is `remove_programs_with_no_entries`, gated on the per-key vector being completely empty [2](#0-1)  — which normal (upgradeable, still-existing) programs never satisfy.

`prune()`, called from `Bank::prune_program_cache` on essentially every consensus root [3](#0-2) , does:
```
for second_level in entries.values_mut() { ... }
```
over the *entire* key set [8](#0-7) . This is directly analogous to the Bond report's `for (uint256 i; i < marketCounter; ++i)`: a loop bound driven by a monotonically growing, permissionlessly-inflatable counter (number of distinct programs ever deployed) rather than the "live"/active working set.

### Impact Explanation
As more unique programs are deployed over the life of the cluster (a normal, unprivileged, cheap operation — anyone can deploy trivial no-op programs for the cost of rent), `entries.len()` grows without bound. `prune()` runs on every rooted slot for every validator, so its per-root cost scales linearly with the *cumulative historical* program count rather than the active set size. This degrades block-processing/validator throughput cluster-wide over time (a non-RPC, validator-internal hot path), which can eventually contribute to missed leader slots or processing delays under sustained low-rate deployment of many unique programs — the Agave analog of "non-RPC remote exhaustion/crash" from unbounded state growth driven by unprivileged actors.

### Likelihood Explanation
Likelihood is moderate: deploying a BPF program only costs rent-exempt lamports and upload bandwidth, so an attacker can cheaply create a very large number of distinct program ids over time without needing elevated privileges. The severity is gradual/performance-degradation rather than an instant crash, since `prune()`'s per-entry work is cheap (a filter/retain), but it is strictly `O(n)` in the total historical program count with no pagination, batching across multiple roots, or removal of long-defunct keys, unlike the Bond fix, which added explicit pagination (`start`/`stop` indices).

### Recommendation
Bound or amortize the `entries.values_mut()` walk in `prune()`/`get_flattened_entries()`: e.g., periodically garbage-collect keys whose only remaining entries are stale tombstones/closed programs, process the prune walk incrementally across multiple roots (similar to how `prepare_program_cache_for_upcoming_feature_set` already amortizes recompilation one program at a time), or cap `entries` size with LRU/expiry so the per-root cost is bounded by an active-set size rather than the lifetime program count.

### Proof of Concept
1. Over an extended period, submit many low-cost `bpf_loader_upgradeable::deploy`/`close` cycles (or simply many distinct minimal programs) from unprivileged accounts, each creating a new, permanent key in `ProgramCache::index`.
2. Observe that `entries.len()` in `ProgramCache` grows monotonically and is never reduced for programs that remain deployed (or whose vector never becomes fully empty).
3. Measure `Bank::prune_program_cache` / `ProgramCache::prune` wall-clock time called on every new root [3](#0-2)  and `prepare_program_cache_for_upcoming_feature_set`'s `get_flattened_entries()` call at epoch boundaries [5](#0-4)  as the deployed-program count increases — cost scales with cumulative program count, not active working-set size, exactly mirroring the unbounded `marketCounter` loop in the Bond Protocol finding.

**Uncertainty**: I could not fully trace the exact call frequency/cost budget of `prune_program_cache` relative to slot time in this pass (e.g., whether it's rate-limited elsewhere, such as only running once per epoch instead of every root), so the concrete performance-impact magnitude is not empirically verified from local code alone — a background agent with profiling/build access should confirm actual per-root invocation frequency and measure wall-clock scaling before treating this as a confirmed, immediately exploitable DoS.

    pub fn get_flattened_entries(&self) -> Vec<(Pubkey, Slot, Arc<ProgramCacheEntry>)> {
        match &self.index {
            IndexImplementation::V1 { entries, .. } => entries
                .iter()
                .flat_map(|(id, second_level)| {
                    second_level
                        .iter()
                        .filter_map(move |program| match program.program {
                            ProgramCacheEntryType::Loaded(_) => Some((*id, 0, program.clone())),
                            _ => None,
                        })
                })

        }

    fn unload_program_entry(
        &mut self,
        id: Pubkey,
        _last_modification_slot: Slot,
        remove_entry: &Arc<ProgramCacheEntry>,
    ) {
        match &mut self.index {
            IndexImplementation::V1 { entries, .. } => {
                let second_level = entries.get_mut(&id).expect("Cache lookup failed");
                let candidate = second_level
                    .iter_mut()
                    .find(|entry| Arc::ptr_eq(entry, remove_entry))
                    .expect("Program entry not found");

                // Only loaded entries shall be unloaded by eviction.
                if let ProgramCacheEntryType::Loaded(_) = candidate.program
                    && let Some(unloaded) = candidate.to_unloaded()
                {
                    if candidate.stats.uses.load(Ordering::Relaxed) == 1 {
                        self.stats.one_hit_wonders.fetch_add(1, Ordering::Relaxed);

                        .evictions
                        .entry(id)
                        .and_modify(|c| *c = c.saturating_add(1))
                        .or_insert(1);
                    *candidate = Arc::new(unloaded);
                }
            }
        }

    fn remove_programs_with_no_entries(&mut self) {
        match &mut self.index {
            IndexImplementation::V1 { entries, .. } => {
                let num_programs_before_removal = entries.len();
                entries.retain(|_key, second_level| !second_level.is_empty());
                if entries.len() < num_programs_before_removal {
                    self.stats.empty_entries.fetch_add(
                        num_programs_before_removal.saturating_sub(entries.len()) as u64,
                        Ordering::Relaxed,
                    );
                }
            }
        }
    }
