## Finding

### Title
Unchecked ERC20 return value on escrow withdrawal permanently settles orders without moving funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.sol` (the Tron variant of the Intents app) checks only that the low-level `call` to an output/fee token's `transfer` did not revert, but never inspects the ABI-decoded boolean return value. Any ERC20 whose `transfer` returns `false` on failure instead of reverting (a legal, common pattern — e.g. a blacklist/pausable stablecoin silently no-opping for a disallowed recipient) will make `success == true` even though no tokens moved, while the contract unconditionally decrements escrow and marks the order as filled/refunded. This is the same class of bug as the report's BGT issue: a token-level transfer failure mode that the caller does not detect, so it proceeds to commit state as if the transfer succeeded — except here it directly and irreversibly settles a cross-chain intent escrow, permanently losing the beneficiary's funds.

### Finding Description
`withdraw()` and the `SweepDust`/`RedeemEscrow`/`RefundEscrow` handling in `onAccept()` move escrowed order tokens and protocol fees using a raw low-level call instead of `SafeERC20.safeTransfer`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
    ...
```

The same unchecked pattern is used for fee redemption and dust sweeping: [2](#0-1) [3](#0-2) 

`success` here is only the *call*-level success flag (did the callee revert). Per the ERC20 standard, `transfer` is allowed to signal failure by returning `false` rather than reverting; OpenZeppelin's `SafeERC20.safeTransfer` (used correctly elsewhere in the codebase, e.g. `IntentsBase.sol`) accounts for exactly this by decoding and checking the boolean return value in addition to call success: [4](#0-3) 

`IntentGatewayV2.sol` (Tron) omits this check. If the output/fee token used in an order returns `false` for a disallowed transfer (blacklisted beneficiary, paused state, insufficient allowance edge cases in nonstandard tokens, etc.) instead of reverting, `success` is still `true`. The function then:
1. Marks `_filled[commitment] = beneficiary` (order considered settled), and
2. Decrements `_orders[commitment][token] -= amount` (escrow record zeroed/reduced),

even though the tokens never left the contract and the beneficiary received nothing. Because `_filled` is now non-zero, subsequent calls (cancel/refund/re-withdraw) revert with `Filled()`, so there is no path to recover the stuck balance for that beneficiary — the tokens are permanently locked in the contract while the protocol's on-chain state asserts settlement occurred.

### Impact Explanation
This is a direct fund-loss / wrong-beneficiary-and-amount bug in bridge custody/order-escrow settlement: the intent's escrowed tokens are released from accounting (decremented, order marked filled) without the beneficiary receiving them, and the false "settled" state is unrecoverable via the contract's own cancel/refund logic. This falls squarely under "Bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount" — here they move zero times while being recorded as moved once.

### Likelihood Explanation
Reachable by an ordinary, unprivileged actor: any order/solver interaction whose output or fee token is a non-standard ERC20 (returns `false` rather than reverting on failure, e.g. compliance/blacklist tokens, some legacy implementations) triggers this on the very first successful proof-driven `withdraw()` call — no malicious relayer, prover, or governance action is required, only the token's normal behavior for a blacklisted/paused beneficiary or edge-case transfer.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check pattern in `withdraw()`, the `TRANSACTION_FEES` redemption block, and `SweepDust` handling with `SafeERC20.safeTransfer`, which is already imported and used correctly in `IntentsBase.sol`. This ensures both call-level success and the ERC20 boolean return value (when present) are validated before committing escrow/settlement state changes.

### Proof of Concept
1. Deploy an ERC20 whose `transfer(to, amount)` returns `false` (no revert) when `to` is on an internal blacklist (mirrors real compliant stablecoins' `false`-return variants, or any nonstandard token).
2. Create and fund an order using this token as an output asset, with `beneficiary` set to an address later blacklisted by the token (or simply mock a token that returns `false` unconditionally for the test).
3. Trigger `onAccept` → `withdraw(body, false)` via a valid `RedeemEscrow` proof.
4. Observe: `token.call(...)` returns `success = true` (call didn't revert) even though the token's internal `_balances` were never updated for `beneficiary`.
5. `_filled[commitment]` is set and `_orders[commitment][token]` is decremented — the order is now permanently "filled" with no tokens delivered, and no further withdrawal/cancellation path exists to recover the escrowed balance.
