Based on the investigation, I found a concrete Desktop analog: `updateSubmodulesAfterOperation` in `submodule.ts` accepts an `allowFileProtocol` boolean that, when true, appends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation, letting Git honor `file://` submodule URLs that are read directly from the attacker-controlled `.gitmodules` file in the cloned/checked-out repository.

### Title
Attacker-controlled `.gitmodules` `file://` URL can exfiltrate arbitrary local files into the working tree when `protocol.file.allow=always` is set for submodule updates - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` builds the `git submodule update --init --recursive` command and conditionally injects `-c protocol.file.allow=always` based on a caller-supplied `allowFileProtocol` flag [1](#0-0) . This is invoked from `checkoutBranch` and `checkoutCommit` with an `allowFileProtocol` parameter that ultimately governs whether Git is allowed to resolve `file://` submodule URLs [2](#0-1) . The actual submodule URLs, however, come entirely from `.gitmodules`, a file fully controlled by whoever authored the commit being checked out — i.e., an untrusted, attacker-controlled repository.

### Finding Description
Git's `protocol.file.allow` setting exists specifically to prevent an untrusted repository from directing a `submodule update` at an arbitrary local path via `file://` URLs (the class of issue behind CVE-2017-1000117 / CVE-2020-11008 and Git's own hardening default of `protocol.file.allow=user` since 2.38). When `protocol.file.allow=always` is passed, Git will clone/checkout whatever `file://` path is specified in `.gitmodules` — including paths completely outside of the current repository, such as `file:///home/user/.ssh` or other sensitive local directories — into the submodule directory of the checked-out tree.

In this codebase, whether that protection is bypassed is controlled by the boolean `allowFileProtocol` threaded through `checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation` [3](#0-2) [4](#0-3) . The `.gitmodules` file that supplies the submodule URL is not sanitized or restricted in any way before this flag is honored — it is fetched/read verbatim from the checked-out commit, i.e., it is fully attacker-controlled content coming from a cloned/fetched repository. This mirrors the root cause pattern in the external report: an admin/attacker-controlled parameter (`tfStartTime`/`tfMaxAmount` there, `allowFileProtocol` + `.gitmodules` URL here) silently changes what a "safe" operation is permitted to do, without validation of the value or of the trust boundary crossed, and the surrounding code offers no guard against the untrusted input driving the operation into unsafe territory.

### Impact Explanation
If a caller path enables `allowFileProtocol: true` for a checkout of an untrusted/attacker-supplied repository (e.g., checking out a branch or commit from a fork, PR, or clone whose `.gitmodules` was crafted by the attacker), Git will read arbitrary local files/directories from the user's machine into the submodule path of the working tree. This is a "read outside the repo" primitive: local files (SSH keys, config, other repos) can be copied into the working directory where the user might inadvertently commit and push them, or where the attacker-authored commit that triggered the checkout can also contain code that reads the newly materialized submodule contents. This fits the valid-impact class: an unprivileged, attacker-controlled repository object (`.gitmodules`) causing file read outside the repo and potential silent corruption of what the user commits.

### Likelihood Explanation
The likelihood depends entirely on which call sites pass `allowFileProtocol: true`; the index available did not show all call sites that set this flag to `true` (only the function signatures and a `false` default were visible), so it is uncertain whether Desktop currently invokes this with `true` for genuinely untrusted, remotely-authored content (e.g., PR checkouts) versus only for trusted local scenarios. Because of this uncertainty, the concrete exploitability cannot be fully confirmed from the available index; a background Devin session would need to grep all call sites of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` with `allowFileProtocol=true` to determine whether any of them are reachable from unprivileged, attacker-controlled repository content.

### Recommendation
1. Audit every call site that passes `allowFileProtocol: true` into `checkoutBranch`/`checkoutCommit` and confirm it is only used for repositories/refs the user already fully trusts (e.g., their own local repo), never for checking out commits/branches originating from an untrusted remote or fork.
2. Consider dropping `protocol.file.allow=always` entirely and instead using Git's default `protocol.file.allow=user` (or scoping the allowance to paths inside the repository's own directory) so `file://` submodule URLs from `.gitmodules` cannot resolve to arbitrary absolute paths.
3. Sanitize/validate submodule URLs parsed from `.gitmodules` before honoring `file://` protocol, rejecting URLs that escape the repository root, mirroring the same rationale already applied to `isClonePathSensitive` in `clone.ts` [5](#0-4) .

### Proof of Concept
Not independently verified end-to-end within this session (would require confirming a reachable call site with `allowFileProtocol=true` on attacker-controlled content), but the underlying Git-level PoC is:
1. Attacker creates a repository with a `.gitmodules` entry: `url = file:///home/victim/.ssh`.
2. Victim opens/checks out that branch/commit in Desktop through a code path where `allowFileProtocol` is `true`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, and Git happily "clones" `/home/victim/.ssh` into the submodule directory of the working tree, exposing its contents inside the repository. [1](#0-0) [6](#0-5)

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
