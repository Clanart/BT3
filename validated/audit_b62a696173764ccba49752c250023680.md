### Title
`ReceivedOutput::read` accepts unauthenticated outputs with forged outpoint/value, letting an unauthenticated party make the wallet sign a spend of nonexistent funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Jenkins XP-Dev advisory is a missing-permission-check bug: code accepts an attacker-supplied identifier and triggers a state-changing action (a build) without verifying the caller is authorized for that resource. The Serai analog lives in `bitcoin-serai`'s wallet deserialization path: `ReceivedOutput::read` ingests untrusted bytes producing an `offset`, a `TxOut`, and an `OutPoint`, and no code path verifies that the claimed outpoint exists on-chain, that its value is real, or that the output's `script_pubkey` is actually bound to `key + offset * G`. `SignableTransaction::new` then treats these forged inputs as spendable balance, and `SignableTransaction::multisig` only validates the script-vs-offset relation — not the outpoint's existence — before driving FROST signing over the fabricated prevouts.

### Finding Description
`ReceivedOutput::read` deserializes three attacker-controlled fields — `offset` via `Secp256k1::read_F`, plus consensus-decoded `TxOut` and `OutPoint` — with no consistency check between them and no authentication of the claimed UTXO (mod.rs:122-134). `SignableTransaction::new` sums `input.output.value` directly into `input_sat` and uses `input.outpoint` / `input.output` as the transaction's `TxIn`s and `Prevouts::All` commitment without any authorization/existence check (send.rs:175-185, 253). In `SignableTransaction::multisig`, the only check is `p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey` (send.rs:277) — i.e., it verifies the offset matches the *declared* script, never that the declared `outpoint`/`script_pubkey`/`value` correspond to a real on-chain output. Since the multisig's P2TR addresses (base key and all registered offset scripts) are publicly derivable, an attacker can construct a `ReceivedOutput` whose `output.script_pubkey` passes this check while the `outpoint` points to a UTXO that does not exist or that pays someone else, with an inflated `value`.

### Impact Explanation
Because `Prevouts::All` is used with `TapSighashType::Default` (send.rs:375-386), the forged prevout values and outpoints are committed into every per-input sighash the threshold group signs. An unauthenticated party who can feed `ReceivedOutput::read` bytes into the wallet (the documented untrusted-bytes entry point) can therefore:

- Cause funds to be reported/received that are not spendable: fabricated `outpoint` + `value` is counted as balance (`input_sat`), letting payments be constructed and signed that can never confirm.
- Cause the threshold set to produce a complete, validly-formed FROST signature over an unintended transaction — one spending nonexistent inputs and paying attacker-chosen outputs — consuming the signing session and the group's nonce/preprocess work while authorizing nothing real.
- Skew fee/change math: the phantom input's value inflates the change output and fee calculation, so even real co-spent inputs are committed to a transaction that miners will reject.

This mirrors the advisory: attacker-specified input is accepted without any check that it refers to a resource the attacker/system is authorized to act on, and it triggers a privileged action (threshold signing).

### Likelihood Explanation
Reachable by any unprivileged party able to submit serialized `ReceivedOutput` bytes (synced/scanned output data, coordinator-provided plans, or any peer-fed byte stream routed to `read`). Constructing the forgery requires only public data — the group's P2TR script — plus arbitrary `outpoint`/`value`. No key material, collusion, or privileged position is needed. Impact is bounded (invalid TX, misreported balance, DoS of a signing session rather than direct theft), consistent with Medium.

### Recommendation
- In `SignableTransaction::new` (or `ReceivedOutput::read` callers), authenticate each input against the chain: verify the `outpoint` resolves to an unspent output whose `script_pubkey` and `value` equal the claimed `TxOut`.
- In `Scanner::scan_transaction` consumers, persist and later re-verify scanned outpoints rather than trusting a `ReceivedOutput` reconstructed from untrusted bytes.
- Optionally add a `ReceivedOutput::verify(key)` helper asserting `p2tr_script_buf(key + offset * G) == output.script_pubkey` and call it at deserialization boundaries, so a forged offset/script pairing fails before reaching `SignableTransaction::new`.

### Proof of Concept
```rust
// Attacker knows the group key `key` (the P2TR address is public).
// Forge a ReceivedOutput claiming a nonexistent UTXO worth 10 BTC:
let forged = {
    let mut buf = Vec::new();
    buf.extend(Scalar::ZERO.to_bytes()); // offset: base key
    buf.extend(serialize(&TxOut {
        value: Amount::from_sat(1_000_000_000),
        script_pubkey: p2tr_script_buf(key).unwrap(), // passes multisig() check
    }));
    buf.extend(serialize(&OutPoint {
        txid: Txid::all_zeros(), vout: 0, // does not exist on-chain
    }));
    buf
};
let input = ReceivedOutput::read(&mut forged.as_slice()).unwrap();

// input_sat counts 10 phantom BTC; payment is signed over Prevouts::All
// including the fake TxOut. multisig() succeeds since script matches.
let tx = SignableTransaction::new(vec![input], &payments, None, None, fee).unwrap();
let machine = tx.multisig(&keys).unwrap(); // no on-chain existence check anywhere
// Threshold signing proceeds and completes; resulting TX is unbroadcastable,
// while the wallet/protocol recorded 10 BTC as received-and-spent.
```
