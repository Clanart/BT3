### Title
Denial of service via O(N³) coin-dependency resolution when cancelling an offer containing many announcement-linked coin spends - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` resolves which coins must be spent to cancel a trade by repeatedly scanning all coin-announcement dependencies with a nested-loop helper, `detect_dependent_coin()`. Like the CommonMark `UniqueSlugNormalizer` bug, the algorithm restarts an expensive full scan after every single item it resolves, turning what should be a linear/near-linear computation into a polynomial-time one driven entirely by attacker-controlled input (the offer's coin spends and their `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions).

### Finding Description
`detect_dependent_coin()` is a triple-nested loop over all coin names, all dependencies of each coin, and all coins' announcement lists, with an `in` membership check against a `list` (not a `set`): [1](#0-0) 

`get_cancellation_coins()` calls this helper inside an outer `while True:` loop that removes only one coin (plus its dependents) per iteration, and rebuilds `remove_these_keys`/`removed_announcements` via linear scans of the remaining dictionaries on every pass: [2](#0-1) 

For an offer with `N` coin spends, each carrying up to the announcement limit (historically 1024 `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions per spend, enforced only pre-hardfork and removed afterward per `TOO_MANY_ANNOUNCEMENTS` checks in [3](#0-2) ), a single call to `detect_dependent_coin` costs `O(N · D · N · A)` (its `dependency in announces` check is a linear list scan, not a set lookup). The outer `while True` loop in `get_cancellation_coins` can run up to `N` times before terminating, since each pass removes only one coin's group. This yields an overall worst case around `O(N² · D · A)` to `O(N³ · D · A)` depending on the announcement structure attacker crafts — directly analogous to the reported bug class where a per-item collision restarts an O(k) scan, producing O(K²) instead of O(K).

### Impact Explanation
`get_cancellation_coins()` runs unconditionally over the full parsed `Offer` object whenever a wallet user calls `cancel_pending_offers` — reachable via the `cancel_offer`/`cancel_offers` RPCs (`chia/wallet/wallet_rpc_api.py`, `CancelOfferCMD` in `chia/cmds/wallet.py`) on any trade record whose stored `offer` bytes originated from an untrusted counterparty (an offer the victim *took* from someone else, or which was crafted to be examined/cancelled). Because the wallet daemon processes RPC calls synchronously while holding `wallet_state_manager.lock` (see `wallet_rpc_api.py:2134`), a single malicious offer can stall the victim's wallet process for an extended period, blocking all other wallet operations (sync, other RPC calls) — a spend/action-triggered processing halt. This matches the "spend-triggered transaction-processing halt" impact class in the rules. It is availability-only (no funds are stolen or invalidly moved), consistent with the CVSS profile of the reference advisory (`C:N/I:N/A:H`).

### Likelihood Explanation
An "offer counterparty" is an explicitly in-scope, unprivileged actor. Constructing an offer with many coin spends each carrying many `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions requires only crafting a `SpendBundle`/`Offer` file — no special privileges, no consensus validation of the *offer* file itself (an offer's incomplete spend bundle is not necessarily fully mempool-validated before the victim's wallet parses and processes it via `Offer.from_bytes()`/`get_cancellation_coins()`). The likelihood of a victim wallet calling `cancel_pending_offers` on a stored, attacker-influenced offer (e.g., an offer they took, later cancelled, or a batch `cancel_offers` call that iterates all stored trades and calls `.arbitrage()`/processes offer content) is a normal, expected wallet workflow, not a corner case.

### Recommendation
Rework `get_cancellation_coins()`/`detect_dependent_coin()` to use index structures (e.g., a reverse map from announcement message → creating coin, built once in `O(N·A)`, and dependency sets rather than lists) so dependency resolution is amortized `O(N + ΣD + ΣA)` instead of restarting full scans after each removal. Additionally, cap the number of coin spends and/or total announcement conditions considered when parsing/processing offers from untrusted sources, and consider moving `get_cancellation_coins` processing off the lock-held RPC path or adding a time-based bailout similar to the mempool's existing >2s duration guard (`chia/full_node/mempool_manager.py`, admission pipeline step 12).

### Proof of Concept
Conceptual construction (cannot be executed in this environment, but derivable from the code paths cited above):
1. Craft a `SpendBundle` with `N` coin spends (e.g., N = few hundred to a few thousand), each using a puzzle/solution that emits many `CREATE_COIN_ANNOUNCEMENT` conditions and `ASSERT_COIN_ANNOUNCEMENT` conditions referencing other coins in the bundle, forming a long dependency chain (D and A both near the historical 1024-per-spend limit, or larger where the limit no longer applies post-hardfork).
2. Wrap it as an `Offer` (`chia/wallet/trading/offer.py`) and have the victim's wallet "take" it, or otherwise store it as a `TradeRecord` (`chia/wallet/trading/trade_store.py`).
3. Have the victim (or an automated `cancel_offers --cancel_all` batch job) call `cancel_pending_offers` (`chia/wallet/trade_manager.py:253`), which invokes `Offer.from_bytes(trade.offer).get_cancellation_coins()` (`trade_manager.py:281`).
4. Observe that `get_cancellation_coins`'s outer `while True` loop combined with the triple-nested `detect_dependent_coin` scan causes CPU time to scale super-linearly with `N`, `D`, and `A`, stalling the wallet process while `wallet_state_manager.lock` is held.

Note: I was not able to fully verify from the available index whether any upstream size/condition-count cap is applied specifically to *offer* spend bundles before `get_cancellation_coins` is reached (as opposed to bundles that go through full mempool admission), nor could I confirm the current post-hardfork announcement-count ceiling per spend. A Devin session with full repository/test access would be needed to confirm the exact achievable N/D/A bounds and measure actual wall-clock impact.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```
