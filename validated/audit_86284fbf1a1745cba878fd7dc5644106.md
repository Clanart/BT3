### Title
Unbacked reward-liability accounting in `ReferralStorage.trigger()`/`claimReward()` allows first-claimer to drain MGP balance and permanently freeze other referrers' rewards - (File: rewards/ReferralStorage.sol)

### Summary
`trigger()` [1](#0-0)  increments `refererInfo.rewardAmount` and `refereeInfo.rewardAmount` purely as internal accounting, with no check against the contract's actual `MGP` token balance. `claimReward()` [2](#0-1)  then performs a raw `MGP.safeTransfer` of the full recorded `rewardAmount` without verifying `MGP.balanceOf(address(this))` is sufficient, so the sum of all users' `rewardAmount` can exceed the real token balance.

### Finding Description
`trigger()` is called from `MasterMagpie._harvestRewards` whenever any staker (referee) harvests MGP rewards: `IReferralStorage(referral).trigger(_user, totalReward)` [3](#0-2) . This is a normal, unprivileged, user-triggerable code path (any staker claiming rewards causes it to fire for their referrer).

Inside `trigger()`, `refererAmount` and `refereeAmount` are computed from `_amount` and added to `userInfos[...].rewardAmount` [4](#0-3) . No MGP tokens are transferred into `ReferralStorage` as part of this call, and nowhere in `trigger()` is there a check that `refererInfo.rewardAmount + refereeInfo.rewardAmount <= MGP.balanceOf(address(this))`.

`claimReward()` reads `userInfo.rewardAmount` and calls `MGP.safeTransfer(msg.sender, userInfo.rewardAmount)` unconditionally, zeroing the balance only after the transfer succeeds [2](#0-1) . There is no global accounting invariant enforced anywhere in the contract tying total outstanding `rewardAmount` liabilities to the actual token balance held by `ReferralStorage`.

An attacker controlling two wallets - one referrer (registers a code via `registerCode`) and one referee (uses the code via `useCode`) - can repeatedly perform many small staking/claim cycles on the referee wallet through `MasterMagpie`, each of which invokes `trigger()` and increments the referrer's `rewardAmount`. Because `rewardAmount` accrual is decoupled from the contract's real MGP balance, this liability can grow (and can be grown for many referrers simultaneously via normal usage) beyond what the contract actually holds. Whichever referrer calls `claimReward()` first drains the available balance; every subsequent referrer with a valid, nonzero `rewardAmount` will have their `MGP.safeTransfer` revert due to insufficient balance, since `SafeERC20.safeTransfer` reverts on transfer failure. Their rewards are then permanently frozen (or frozen indefinitely until the contract is refunded), while the first claimer has already extracted funds ahead of them.

No modifier, reentrancy guard, or balance check in `claimReward()` or `trigger()` prevents this — `_onlyMasterMagpie` on `trigger()` only restricts *who calls* trigger (MasterMagpie), it does not bound the *amount* of liability created relative to actual backing.

### Impact Explanation
This is a "theft of unclaimed yield / freezing of user funds" issue matching the Backing invariant break: `sum(userInfos[*].rewardAmount) > MGP.balanceOf(ReferralStorage)`. Whichever referrer claims first receives their full reward at the expense of MGP tokens that were economically meant to back other referrers' accrued-but-unpaid rewards, and remaining referrers' legitimate `claimReward()` calls revert, freezing their yield potentially indefinitely (until/unless the contract is topped up by an external actor, which is outside the attacker's or victim's control).

### Likelihood Explanation
This requires no privileged role — only two wallets under attacker control (or even just normal, uncoordinated users triggering the flaw as a side effect of their own regular staking/claiming activity). It requires only interacting with `registerCode`/`useCode` and normal `MasterMagpie` staking/claim flows to repeatedly invoke `trigger()`, which are all public/external functions reachable by any EOA. The precondition is simply that `ReferralStorage`'s MGP funding lags behind (or is decoupled from) the accrued `rewardAmount` liabilities it is recording — which the code as written does not prevent by design, since `trigger()` never moves or reserves tokens.

### Recommendation
Enforce a Backing invariant before creating liability or before allowing transfer:
- In `trigger()`, only accrue `rewardAmount` up to what the contract can back, or require the actual MGP to be transferred into `ReferralStorage` atomically as part of the trigger flow (e.g., have `MasterMagpie` transfer MGP tokens to `ReferralStorage` corresponding to `totalReward` before calling `trigger`), so that `rewardAmount` accounting is always fully collateralized.
- Alternatively, in `claimReward()`, cap the transferred amount to `min(userInfo.rewardAmount, MGP.balanceOf(address(this)))` and track/carry over any shortfall, or revert with a clear "insufficient global balance" error, and add a global tracked variable `totalOwedRewards` that is checked against `MGP.balanceOf(address(this))` whenever new rewards are accrued in `trigger()`.

### Proof of Concept
Foundry test plan:
1. Deploy `ReferralStorage`, `VLMGP`, `MasterMagpie`, and `MGP` token stubs; fund `ReferralStorage` with an intentionally small MGP balance (e.g., 100 MGP).
2. Set up two referrer/referee pairs: `referrerA`/`refereeA` and `referrerB`/`refereeB`, each registering/using distinct referral codes.
3. From `MasterMagpie` (acting as `masterMagpie`), call `ReferralStorage.trigger(refereeA, largeAmount)` and `trigger(refereeB, largeAmount)` repeatedly (simulating many small referee claims) such that `userInfos[referrerA].rewardAmount + userInfos[referrerB].rewardAmount` exceeds the 100 MGP actually held by `ReferralStorage`.
4. Have `referrerA` call `claimReward()` first — assert it succeeds and drains most/all of the 100 MGP balance.
5. Have `referrerB` call `claimReward()` — assert it reverts (insufficient balance in `MGP.safeTransfer`) despite `userInfos[referrerB].rewardAmount > 0`, proving the frozen/unbacked liability.
