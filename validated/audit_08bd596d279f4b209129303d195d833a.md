The Tron variant of `IntentGatewayV2` contains exactly the same silent-failure class as the external report: it downgrades every ERC20 transfer to a raw low-level `.call` and only checks that the *call itself* didn't revert, never decoding the boolean return value that `transfer()` is supposed to emit.

### Title
Escrow withdrawal marks orders filled/refunded despite silent ERC20 `transfer()` failure - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron build of the Intent Gateway move escrowed tokens with `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the outer `(bool success,) = ...call(...)` flag, never inspecting the returned `abi.decode(data,(bool))` value that ERC20's `transfer()` is contractually required to return.

### Finding Description
In `withdraw()`, escrow release/refund and fee redemption all use the same unchecked pattern: [1](#0-0) [2](#0-1) 

The `SweepDust` handler in `onAccept()` has the identical pattern: [3](#0-2) 

`success` here is only `true` when the target address is a contract that did not revert — it says nothing about whether the ERC20 `transfer` actually moved funds. Any ERC20 token that follows the "return `false` instead of reverting" convention (the same category of behavior the external report flags for Compound's `mToken.mint`) will make the outer call succeed while zero tokens are transferred. Immediately after this unchecked call, the function irreversibly finalizes the operation regardless of outcome: [4](#0-3) 

`_filled[body.commitment] = beneficiary` is set unconditionally at function entry, and `_orders[body.commitment][token] -= amount` is decremented unconditionally after the unchecked transfer, regardless of whether the beneficiary actually received the tokens.

By contrast, the mainline EVM `IntentGatewayV2`/`IntentsBase` implementations correctly use `SafeERC20.safeTransfer`/`safeTransferFrom`, which decode and assert the boolean return value: [5](#0-4) 

The Tron variant deliberately drops `SafeERC20` for the withdrawal/sweep paths (likely for TVM compatibility reasons) but in doing so reintroduces the exact silent-failure hazard the report describes.

### Impact Explanation
Because `_filled` and `_orders[...][token]` are updated unconditionally after an unchecked transfer, a token whose `transfer()` returns `false` on failure (rather than reverting) causes:
- The commitment to be permanently marked as filled/refunded (`_filled[commitment] = beneficiary`), blocking any retry via `onGetResponse`/`onAccept` for that commitment.
- The escrow accounting to be zeroed out (`_orders[commitment][token] -= amount`) even though the tokens never left the contract.
- The beneficiary receiving nothing while the contract's internal bookkeeping shows the order as fully settled — a direct loss/lock of bridged escrow funds with no recovery path, since the commitment can never be withdrawn again.

This satisfies the "stealing or loss of funds" / "false state acceptance" impact class: order settlement state is accepted as final based on an unverified external call outcome.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — any token used as an order's `input`/`output` asset (chosen by the ordinary, unprivileged order creator/solver) that implements the non-reverting `transfer()` convention is sufficient to trigger it. This is a common real-world ERC20 pattern (deflationary/fee/pausable/blacklist tokens, or any token that opts to signal failure via return value instead of revert), so the trigger condition is not exotic or reliant on a compromised actor — it's a routine ERC20 integration hazard that Hyperbridge's own `SafeERC20` usage elsewhere in the codebase demonstrates awareness of, but which was omitted here.

### Recommendation
Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, or explicitly decode and validate the boolean return value (`success && (data.length == 0 || abi.decode(data, (bool)))`) before finalizing `_filled`/`_orders` state, consistent with the mainline `IntentsBase.sol` implementation.

### Proof of Concept
1. Deploy an ERC20 token on the Tron chain whose `transfer()` implementation returns `false` (rather than reverting) under some condition — e.g. a paused/blacklist-style token, or simply one that returns `false` when the internal balance check fails for any edge case not covered by `require`.
2. Create and escrow an order using this token as an input asset via the standard order-creation flow.
3. Have Hyperbridge deliver a `RedeemEscrow`/`RefundEscrow` request whose `WithdrawalRequest.tokens` includes this token, routing into `withdraw()` at `evm/tron/contracts/apps/IntentGatewayV2.sol:682-721`.
4. Trigger the token's failure condition so `transfer()` returns `false` while the outer `.call` still returns `success = true` (no revert).
5. Observe: `_filled[commitment]` is set, `_orders[commitment][token]` is decremented to 0, and `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's token balance is unchanged. The escrowed tokens are now permanently stranded in the contract with no code path able to re-trigger withdrawal for that commitment.
