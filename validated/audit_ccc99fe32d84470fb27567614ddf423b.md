### Title
Simple-pattern hookify rules for `prompt`/`stop` events silently never trigger due to field-name mismatch - (File: plugins/hookify/core/config_loader.py)

### Summary
`Rule.from_dict` infers `field='content'` for any non-bash/non-file simple-pattern rule (including `event: prompt` and `event: stop`), but `RuleEngine._extract_field` only understands `user_prompt` and `reason`/`transcript` for those events, never `content`. As a result, any user-authored simple `pattern:`-based block/warn rule targeting prompts or stop reasons is a silent dead guard that never matches, regardless of how obviously the pattern matches the actual input text.

### Finding Description
In `plugins/hookify/core/config_loader.py` (`Rule.from_dict`, lines 56-73), when a rule uses the legacy simple `pattern` field, the field name for the generated `Condition` is inferred purely from `event`:
```
if event == 'bash': field = 'command'
elif event == 'file': field = 'new_text'
else: field = 'content'
```
Any event value other than `bash`/`file` — including the documented values `prompt` and `stop` used by `userpromptsubmit.py` (`load_rules(event='prompt')`) and `stop.py` (`load_rules(event='stop')`) — falls into the `else` branch and gets `field='content'`.

At evaluation time, `RuleEngine._extract_field` (rule_engine.py lines 182-254) first checks `if field in tool_input` (line 196) — for prompt/stop events `tool_input` is `{}` (no tool call), so this is `False`. It then checks `input_data` for `field == 'reason'`, `field == 'transcript'`, or `field == 'user_prompt'` — never `field == 'content'`. Finally it falls through to tool-type-specific branches (`Bash`, `Write/Edit`, `MultiEdit`) which also don't apply since `tool_name` is empty. The function returns `None`. `_check_condition` (line 158-160) treats `None` as an automatic non-match and returns `False`, so `_rule_matches` returns `False` for every input, no matter the content.

This makes `evaluate_rules` return `{}` (no block, no warning) unconditionally for such rules, even when `action: block` is specified and the prompt/stop reason obviously contains the dangerous pattern.

### Impact Explanation
This is a "deny means deny" violation: a user/administrator who deploys a `hookify.*.local.md` guardrail with `event: prompt` (or `event: stop`) and the simple `pattern:` syntax believes they have installed an enforced block on dangerous prompts or agent-stop conditions, but the guard is unconditionally inert. Attacker-controlled or accidental dangerous prompt text (e.g., prompt-injection payloads, exfiltration instructions) that the rule author intended to block will always be allowed through, defeating the intended defense-in-depth control without any error or warning being surfaced to the user.

### Likelihood Explanation
Highly likely to occur in practice: the simple `pattern:` format is the documented "legacy"/beginner-friendly syntax (as opposed to `conditions:` lists), so any rule author writing a `prompt` or `stop` rule using the simple form (which is the natural, least-effort way to write a rule) hits this bug deterministically and silently — no attacker action beyond normal prompt submission is needed once the rule is misconfigured this way.

### Recommendation
In `Rule.from_dict` (config_loader.py), map `event: 'prompt'` to `field='user_prompt'` and `event: 'stop'` to `field='reason'` (or another supported Stop field) instead of the generic `'content'` fallback. Alternatively, add `'content'` as a recognized alias inside `_extract_field` that resolves to `user_prompt` for `UserPromptSubmit` and to `reason` for `Stop` events, ensuring consistency between the two files. Additionally, consider adding a startup-time validation warning when `_extract_field` cannot resolve a condition's field for a given event, so misconfigured rules fail loudly instead of silently.

                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields

                return input_data.get('reason', '')

                    except (IOError, OSError) as e:

                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')
