### Title
Unauthenticated operator attribution in the `payout_tx` OP_RETURN allows misattributing/hijacking withdrawal reimbursement credit - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `payout_tx`'s OP_RETURN output, which records which operator "fronted" a withdrawal, is a plain unsigned data push that is not covered by the user's `SIGHASH_SINGLE|ANYONECANPAY` signature used to spend the withdrawal UTXO. This breaks the binding "operator credited == party that funded/broadcast the payout," letting anyone who observes a valid `input_signature` construct a competing payout transaction that attributes the withdrawal to an arbitrary operator (or non-existent one), the same class of bug as the reported unvalidated `ProposerIndex`: an identity field is trusted downstream (for reimbursement bookkeeping and the bridge circuit's claim of who paid) while only being implicitly, and here not even implicitly, checked against the field that actually authorizes the action.

### Finding Description
`create_payout_txhandler` builds the `payout_tx` with a single input (the user's withdrawal UTXO, spent via `SpendPath::KeySpend` using `user_sig`) and adds an OP_RETURN output that encodes `operator_xonly_pk`: [1](#0-0) 

The RPC layer explicitly documents/enforces that the withdrawal's `input_signature` uses `SinglePlusAnyoneCanPay` sighash: [2](#0-1) 

`SIGHASH_SINGLE | ANYONECANPAY` only commits the signature to the single input being spent and the output at the same index (the user payout output). It does **not** commit to any other output, including the anchor output or the OP_RETURN output carrying `operator_xonly_pk`. Consequently, the same `user_sig` remains valid for a transaction that spends the identical withdrawal UTXO to the identical user output, but with a **different OP_RETURN payload** (i.e., a different `operator_xonly_pk`, or additional/removed outputs).

Downstream, verifiers determine which operator gets bookkeeping credit for a withdrawal purely by reading this OP_RETURN field off whichever payout transaction happens to confirm first, with no signature check binding it to the broadcaster/fee-payer: [3](#0-2) 

This attribution is not just cosmetic: the bridge circuit that proves the reimbursement claim explicitly derives `deposit_constant` from the first OP_RETURN output of the payout transaction, i.e., it treats this unauthenticated field as the ground truth for "who fronted this withdrawal": [4](#0-3) 

Because `operator_xonly_pk` is neither signed by the user (sighash excludes it) nor by any operator key (the payout tx has no operator signature at all — only `user_sig` on the key-spend path), any party capable of observing an in-flight payout transaction (e.g., in the mempool, or via the aggregator broadcasting the same signed withdrawal params to multiple operators concurrently, as tests exercise) can extract `input_signature`/`input_outpoint`/`output_script_pubkey`/`output_amount` and construct a competing transaction with an arbitrary `operator_xonly_pk` in the OP_RETURN, then win the confirmation race (e.g., via a higher CPFP fee on the anchor output, which is also unauthenticated).

### Impact Explanation
This breaks the required equality "the operator credited for a payout == the party that actually funded/broadcast that payout." Consequences:
- Verifiers' payout bookkeeping (`update_payout_txs_and_payer_operator_xonly_pk`) can attribute a withdrawal to an operator who never fronted it.
- The bridge circuit's `deposit_constant`, which is meant to bind a reimbursement claim to the operator who actually performed the payout, can be computed from attacker-forged data, allowing a false circuit claim to be provable (or a true claim to be denied to the honest operator who actually paid), matching the "false circuit claim proved / true claim unprovable" and "honest operator permanently unable to be reimbursed" impact categories.
- An operator that never fronted a withdrawal could be misattributed as the payer, potentially letting them (or blocking the real payer from) pursuing reimbursement for funds they did not spend.

### Likelihood Explanation
No privileged role is required: the exploit only needs visibility of a broadcast (even unconfirmed) payout transaction and the ability to submit a competing Bitcoin transaction with a higher fee (standard RBF/CPFP race), both of which are available to any network participant. The design itself widens exposure further since the aggregator sends the same signed withdrawal params to multiple operators simultaneously, making the underlying `SIGHASH_SINGLE|ANYONECANPAY` signature available to more than one party by construction.

### Recommendation
Bind the operator attribution field to the actual signer/broadcaster of the payout transaction, e.g., by requiring the operator's own signature to cover the OP_RETURN output (and ideally the anchor output), or by using a sighash mode (e.g., `SIGHASH_ALL`) for the user's signature that commits to all outputs including the OP_RETURN payload, so a substituted `operator_xonly_pk` invalidates the signature.

### Proof of Concept
1. Operator R broadcasts a valid `payout_tx` (per `create_payout_txhandler`) spending the user's withdrawal UTXO with `user_sig` (sighash `SINGLE|ANYONECANPAY`), with OP_RETURN = R's `xonly_pk`.
2. Attacker A observes this unconfirmed transaction in the mempool, extracts `input_outpoint`, `output_script_pubkey`, `output_amount`, and `user_sig`.
3. A constructs a new transaction spending the same input with the same `user_sig` (still valid, since the sighash doesn't cover OP_RETURN/anchor), producing the same user-facing output, but with OP_RETURN = victim operator V's `xonly_pk` (or A's own key) and a higher-fee anchor output.
4. A broadcasts and gets this transaction mined first via RBF/CPFP.
5. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) records V (or A) as the operator who fronted the withdrawal, and the bridge circuit's `deposit_constant` (`circuits-lib/src/bridge_circuit/mod.rs`) is computed against this forged attribution, decoupling the reimbursement claim from the party (R) who actually incurred the payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
