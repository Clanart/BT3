### Title
Copilot conflict resolution can silently leave real conflict markers in committed/staged files due to hunk-count desync between `extractConflictHunks` and `reassembleResolvedFile` - (File: `app/src/lib/copilot-conflict-context.ts` / `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`extractConflictHunks` (the function that determines both what is sent to the Copilot model and the "expected hunk count" used for validation) silently drops a conflict block when it fails to find its closing marker, and in doing so consumes the rest of the file, causing any later real conflict blocks to be missed entirely. `reassembleResolvedFile`, which later splices the model's per-hunk resolutions back into the real on-disk content, walks the file independently and can hit those "missed" conflict blocks, treating malformed ones as plain text and copying their raw `<<<<<<<`/`=======`/`>>>>>>>` markers verbatim into what is labeled a "fully resolved" file. That content is then written to disk and `git add`-ed without ever re-checking that it is actually marker-free.

### Finding Description
`extractConflictHunks` builds the hunk list that is (a) sent to the LLM and (b) used as the "expected" hunk count for `validateResolutionPaths`: [1](#0-0) 

When the closing `>>>>>>>` marker is never found for a block (`hunkEnd === -1`), the code does `continue` — but by that point the preceding `while` loops have already advanced `i` to `lines.length` while unsuccessfully searching for `theirsMarker`. The outer `while (i < lines.length)` loop therefore terminates immediately, silently discarding **all subsequent hunks in the file**, not just the malformed one.

`validateResolutionPaths` trusts this same undercounted hunk list as ground truth: [2](#0-1) 

Separately, `reassembleResolvedFile` re-walks the *raw* file content independently, using its own marker regexes, and when it hits a `<<<<<<<` that isn't followed by a proper `=======`/`>>>>>>>` pair, it copies the line through as ordinary text rather than failing or flagging it: [3](#0-2) 

Because this walk is line-by-line and only checks for `reassemblyOursMarker` to decide whether to enter "conflict-block" handling, any real `=======`/`>>>>>>>` markers belonging to a hunk that extraction never saw are also just copied through verbatim as plain text (no marker-content check runs on the reassembled whole-file output).

The one marker check that does exist only validates the model's own per-hunk `resolvedContent` fields, not the final spliced file: [4](#0-3) 

The result is handed to the UI/write path as `IFileResolution.resolvedContent`, documented as "The fully resolved file content (all conflict markers removed)": [5](#0-4) 

and is written straight to disk and staged when the user clicks Continue, with no post-hoc check that no conflict markers remain: [6](#0-5) 

The only existing safety check at that call site (`hasUnresolvedConflicts`) is one-directional: it only prevents *overwriting* a file the user already resolved externally; it never verifies that Copilot's own `resolvedContent` is actually marker-free before writing and `git add`-ing it.

### Impact Explanation
This causes silent corruption of what the user commits/pushes — a file staged and (typically) committed as part of completing a merge/rebase/cherry-pick can still contain literal `<<<<<<<`, `=======`, `>>>>>>>` conflict-marker text and/or garbled duplicated content, without any error, warning, or "still conflicted" indication in the UI (the dialog treats the operation as resolved and lets the user Continue). This can break builds, leak unintended code from both branches concatenated together, or (in the worst case) commit syntactically-plausible-but-wrong code silently. This falls squarely under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
The attacker-controlled surface is a cloned/fetched repository: any file in a branch being merged that legitimately contains a line of 7+ `<` characters at the start of a line (matching `oursMarker`/`reassemblyOursMarker` = `/^<{7}(?:\s|$)/`) — e.g. ASCII art, a markdown code sample demonstrating git conflict syntax, a test fixture for a merge tool, or a doc string — is enough to desynchronize `extractConflictHunks`'s count from the real number of conflict blocks in the file whenever that same file also has a genuine, later conflict region. No local access, admin rights, or social engineering is required; the user only needs to attempt an ordinary merge/rebase/cherry-pick with Copilot conflict resolution against a repository/branch containing such content, which is a normal, unprompted Desktop workflow.

### Recommendation
- Fix `extractConflictHunks` so a block with no closing marker does not consume the rest of the file: track the marker-search boundary separately and resume the outer scan from `markerStart + 1` (or the point right after the failed marker) instead of falling through to `lines.length`.
- After `reassembleResolvedFile` produces the final content, run a hard verification (e.g., re-run marker regexes against the full reassembled text) and refuse to treat the file as resolved / refuse to write it if any conflict markers remain, surfacing it as a skipped file instead.
- In `_applyCopilotConflictResolutions`, verify `resolution.resolvedContent` contains no conflict markers immediately before `writeFile`/`git add`, mirroring the existing `hasUnresolvedConflicts` check but applied to the resolution itself rather than only to externally-resolved files.

### Proof of Concept
1. Create a repository where a merge will produce a file containing:
   - A block of code with 7+ leading `<` characters somewhere (e.g. a doc/ASCII-art string: `<<<<<<< example`), which is not an actual git conflict marker but matches `oursMarker`/`reassemblyOursMarker`.
   - Later in the same file, a genuine merge conflict block (`<<<<<<< HEAD ... ======= ... >>>>>>> branch`).
2. Trigger a merge that produces conflicts in this file and invoke "Resolve with Copilot."
3. `extractConflictHunks` hits the fake `<<<<<<<`-like line first, fails to find a closing `>>>>>>>` for it, and (per lines 228–242) consumes the rest of the file while searching — so the real conflict hunk below it is never added to `hunks`. The file is sent to the model with an undercounted (or zero) hunk list.
4. `reassembleResolvedFile` independently walks the same raw file; it copies the fake marker text through as regular content, then — since it operates purely line-by-line rather than paired with `extractConflictHunks`'s hunk boundaries — reaches the real conflict block's markers without a corresponding entry in `hunkResolutions` to consume them correctly, leaving the real `<<<<<<<`/`=======`/`>>>>>>>` lines from the genuine conflict copied verbatim into `resolvedContent`.
5. `_applyCopilotConflictResolutions` writes this content to disk and runs `git add` on it, staging a file that still contains literal conflict-marker text, without any error surfaced to the user.
