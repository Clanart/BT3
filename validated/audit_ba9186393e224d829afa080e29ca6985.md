### Title
Recursive clone of a malicious repository disables Git's built-in clone-protection checks via `GIT_CLONE_PROTECTION_ACTIVE=false` - (File: `app/src/lib/git/clone.ts`)

### Summary
When cloning a repository, GitHub Desktop always passes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment used for `git clone --recursive`. This environment variable is the internal switch Git itself introduced to enforce protections against symlink/embedded-repository tricks that a malicious repository can use during a recursive clone (the class of issues fixed upstream around CVE-2024-32004, where a crafted repo with submodules and symlinks can cause Git to read/execute files outside the intended repository during clone/checkout of hooks or config). By explicitly forcing this flag to `'false'`, Desktop unconditionally disables that protection for every clone it performs, including clones of arbitrary, attacker-controlled remote URLs (the exact "attacker controls a cloned/fetched repository" primitive called out as in-scope).

### Finding Description
`clone()` in [1](#0-0)  builds the execution environment as:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c', `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
```

`GIT_CLONE_PROTECTION_ACTIVE` is Git's own internal guard variable used to detect and block scenarios during a (recursive) clone where a malicious repository plants a symlink or embedded `.git` directory that would cause Git to write, read, or execute files outside the repository working tree that Desktop is cloning into (e.g. via submodule hook setup or config injected through symlinked paths). Git added this protection precisely because such repositories are attacker-controlled and can be cloned by any user simply by pointing their client at a URL — the same threat model Desktop exposes through "Clone repository" or "Open in Desktop" (`x-github-client://openRepo/...` / `github-mac://openRepo/...`, handled in [2](#0-1)  and dispatched via `openOrCloneRepository` in [3](#0-2) ).

The existing Desktop-side guard, `isClonePathSensitive()` in [4](#0-3) , only validates the *destination* directory chosen by the user (blocking clones into `~/.ssh`, `~/.gnupg`, etc.). It does nothing to stop Git-level tricks that write/read files **outside the destination path itself** via symlinks or nested repository objects supplied by the untrusted remote content, which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` is meant to catch. Setting it to `'false'` removes that check entirely, and it is applied uniformly to every clone regardless of URL, protocol, or trust level — there is no allow-list, no confirmation prompt, and no distinction between a first-party GitHub repo and an arbitrary attacker-hosted remote.

### Impact Explanation
Because `--recursive` is always passed and the protection is unconditionally disabled, cloning a crafted malicious repository (from any host reachable by the "Clone repository" dialog or an "Open in Desktop"/deep-link flow) can allow the attacker's repository content to escape the intended clone directory via submodule/symlink tricks that Git's own protection was designed to reject. This falls squarely in the "file write or read outside the repo" and potentially "code execution" impact categories called out as valid, since the underlying upstream issue this protection guards against involves hook/config paths being resolved through attacker-controlled symlinks during recursive submodule initialization.

### Likelihood Explanation
High. No local access, admin rights, or social engineering beyond normal usage is required — a user cloning a repository or clicking a "Clone in Desktop"/`x-github-client://openRepo` deep link that points at an attacker-controlled remote is a fully expected, unprompted user action already supported by the product. The disabling of the protection is unconditional and applies to every clone path in the app (`clone()` is the single implementation used by the Clone dialog, CLI `--cli-clone`, and URL-open flows).

### Recommendation
Remove the hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override so Git's built-in clone protections remain active by default. If disabling it was done to work around a compatibility issue with a specific Git/dugite version or scenario, that should be scoped narrowly (e.g., only for verified local/trusted clones) rather than applied globally to all recursive clones of arbitrary remote URLs. At minimum, pair the override with the destination-path validation already present, and add regression tests that assert protection remains enabled for network clones.

### Proof of Concept
Not independently executed (no filesystem/terminal access in this environment; verification is based on static code review). The concrete reproduction path from local code evidence is:
1. Attacker hosts a Git repository containing a `.gitmodules` entry and crafted symlink/embedded-repository structure of the kind blocked by Git's `GIT_CLONE_PROTECTION_ACTIVE` check (the same class as upstream Git's recursive-clone symlink protections).
2. Victim clones the repository in GitHub Desktop via the normal "Clone repository" dialog, or via a crafted `x-github-client://openRepo/<attacker-url>` deep link handled by `parseAppURL`/`openOrCloneRepository`.
3. `clone()` in `app/src/lib/git/clone.ts` runs `git ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set, disabling the guard Git would otherwise use to reject/neutralize the crafted structure.
4. Git's normal (enabled) protection would have blocked/failed the clone; with it disabled, the crafted repository content can influence files outside the intended `path`.

Because I cannot run Git/dugite in this environment to confirm the exact upstream check gated by `GIT_CLONE_PROTECTION_ACTIVE` in the installed Git version, I recommend a Devin session with terminal access to (a) confirm the Git version bundled with Desktop and the precise behavior gated by this variable, and (b) build a concrete crafted repository fixture to demonstrate the escape end-to-end.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
