### Title
`ReceivedOutput::read` accepts untrusted `(offset, output, outpoint)` triples without verifying the output is actually spendable by that offset - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The oracle bug class here is "only the price is consumed while the other return values that carry validity/freshness information are discarded, so stale/incorrect data is accepted." The Serai analog is in `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`): it deserializes a scalar `offset`, a `TxOut`, and an `OutPoint` from an untrusted reader and returns them as a coherent "spendable output" without checking the one relation that makes the triple meaningful — that `output.script_pubkey` equals the P2TR script for `key + offset*G`, the same check `Scanner::scan_transaction` performs via `self.scripts.get(&output.script_pubkey)` (`mod.rs:205`). The integrity metadata (the script-to-offset binding) is simply never validated, exactly like dropping `answeredInRound`/`timeStamp` from `latestRoundData`.

### Finding Description
`Scanner::scan` builds `ReceivedOutput`s where the offset provably spends the output because the script matched a registered offset (`mod.rs:180-213`). `ReceivedOutput::read`, however, accepts arbitrary bytes: any `offset` (any valid scalar via `Secp256k1::read_F`), any `TxOut` (any script_pubkey, any value), and any `OutPoint` (which need not correspond to a real transaction output paying that script). A peer supplying serialized `ReceivedOutput`s can therefore claim funds were received that are not spendable: e.g., an output paying a script belonging to a *different* registered offset, a script belonging to no offset at all, or a correct script at an `outpoint` that doesn't exist / has a different value than claimed. The `value()`/`output()`/`outpoint()` accessors then report the attacker-chosen amount to the wallet/processor. This is the same acknowledged threat surface as semantically-invalid deserialized `FrostKeys` (`crypto/frost/src/sign.rs:492-493`).

### Impact Explanation
Funds reported received that are not spendable. If a downstream component trusts a deserialized `ReceivedOutput`'s `value()` and `outpoint()` (e.g., to credit a deposit or build a spend), it can record a deposit that can never be signed for (wrong offset for the script) or reference an outpoint whose actual on-chain output differs — book-keeping divergence between reported and real spendable funds.

### Likelihood Explanation
Requires an unprivileged party to feed crafted bytes into `ReceivedOutput::read` — within the allowed reach (untrusted bytes to `ReceivedOutput::read`). Whether a production path deserializes `ReceivedOutput`s from a mutually-distrusting peer could not be fully verified from the indexed code, which bounds the severity; the crypto inconsistency itself is unconditional.

### Recommendation
Bind the fields: either make `ReceivedOutput::read` take the `Scanner`/view key and reject outputs whose `script_pubkey` doesn't match `key + offset*G` (re-running `p2tr_script_buf` and comparing, mirroring `scan_transaction`), or serialize/verify a proof of provenance. At minimum, document that `read` does not authenticate the offset↔output relation and callers must re-verify against the scanner.

### Proof of Concept
```rust
// Attacker crafts bytes: offset o_A for script_A (registered), but pairs it
// with output paying script_B = p2tr(key + o_B*G), or an unregistered script.
let mut buf = Vec::new();
buf.extend(o_A.to_bytes());                      // valid scalar
buf.extend(serialize(&txout_paying_script_B));   // script_pubkey != script_A
buf.extend(serialize(&fake_outpoint));           // arbitrary txid:vout
let ro = ReceivedOutput::read(&mut &buf[..]).unwrap();
// ro.value() reports txout_paying_script_B.value; spending via o_A will fail
// since script_B is only spendable with o_B. Funds are "received" but unspendable.
```
