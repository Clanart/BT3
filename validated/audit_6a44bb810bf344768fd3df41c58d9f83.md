### Title
Line-Selection/Diff Snapshot Mismatch Causes Silent Corruption of Partial Commits - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported Sui vault bug is a "stale snapshot combined with live state" flaw: `VaultNAV` (a snapshot) is later added to a live Bank balance that has since changed, corrupting the computed value. GitHub Desktop has a structurally identical pattern in its partial-commit ("stage selected lines") pipeline: the user's `DiffSelection` (a snapshot of *line indices* taken against a specific rendered diff) is later re-applied against a **freshly re-fetched diff** at staging time, with no check that the two diffs are the same snapshot.

### Finding Description
When a user selects individual lines/hunks of a file to include in a commit, the UI builds a `DiffSelection` whose `divergingLines` are plain integer line indices (`absoluteIndex`) relative to a specific `ITextDiff` object that was rendered at selection time [1](#0-0) . This selection object carries no reference to, or hash of, the diff/content it was computed against — it is pure index state [2](#0-1) .

When the commit is actually created, `createCommit` calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex` [3](#0-2) [4](#0-3) . Critically, `applyPatchToIndex` does **not** reuse the diff that produced the user's selection; it re-fetches a brand-new diff straight from the working directory at apply time and formats a patch by walking that new diff's hunks while testing the *old* selection's `isSelected(absoluteIndex)`: [5](#0-4) 

`formatPatch` then blindly maps `hunk.unifiedDiffStart + lineIndex` from the **new** diff onto the stale selection [6](#0-5) .

If the on-disk file content changes between the moment the diff was rendered/selected in the UI and the moment `createCommit`/`stageFiles` runs (e.g., an attacker-controlled `smudge`/`clean` filter, a `post-checkout`/`pre-commit` hook shipped in a cloned/fetched repository, a background LFS or submodule update, or content rewritten as a side effect of a Copilot/merge-conflict resolution flow that also touches the same file), the hunk layout and absolute line indices shift. The stale `DiffSelection`'s indices no longer point at the lines the user actually reviewed and checked — they now point at arbitrary lines of the new diff. `formatPatch` will silently include unintended additions/deletions (or drop intended ones) while still succeeding, because `git apply --cached` only validates hunk-context consistency, not "does this patch reflect what the user selected."

The one guard that exists — `updateChangesWorkingDirectoryDiff`'s recomputation of `selectableLines` when the *UI* diff is reloaded — only protects the rendering path, not the commit/staging path [7](#0-6) . There is no equivalent re-validation inside `applyPatchToIndex` before it builds and applies the patch.

### Impact Explanation
This produces exactly the class of impact allowed: **silent corruption of what the user commits/pushes**. A file whose content was altered by an attacker-controlled repository artifact (malicious `.gitattributes` filter, git hook, or LFS smudge script shipped in a cloned/fetched repo) between the time a user reviews/selects lines in Desktop and the time they click "Commit" can cause Desktop to stage and commit different content than what was shown and approved in the diff viewer — without any error, warning, or diff mismatch indication to the user. This is worse than a UI display bug because it changes the actual git object graph that gets pushed.

### Likelihood Explanation
Requires no local/physical access or leaked credentials — only a cloned/fetched repository containing a git filter or hook that rewrites tracked file contents on checkout/add, which is fully within scope of "attacker controls a cloned/fetched repository." The race window is realistic: partial-selection commits (staging only some lines) are a normal Desktop workflow, and any operation that touches the working tree between diff render and commit (autosave, filter, background refresh) opens the window. `applyPatchToIndex` provides no defense — it explicitly re-derives the diff from disk rather than trusting/validating against the diff the selection was made from.

### Recommendation
Thread the exact `ITextDiff`/`ILargeTextDiff` object (or a content hash of the file) that produced the `DiffSelection` through to `applyPatchToIndex`, and compare it against a freshly fetched diff before formatting the patch. If they differ, abort staging that file and force the UI to reload the diff and clear/re-map the selection (reusing the existing `withSelectableLines` reconciliation logic already used for live diff updates) rather than silently applying a patch built from mismatched line indices.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file such that the diff view shows a multi-hunk change.
2. Select only specific lines (e.g., lines 5–10) via the diff viewer, producing a `DiffSelection` with `divergingLines` bound to those absolute indices.
3. Before clicking "Commit," have an external process (e.g., a `.gitattributes` `clean`/`smudge` filter defined in the cloned repository, or a script watching the file) rewrite the file so the diff hunk boundaries shift (insert/remove lines above the selected region).
4. Click "Commit." `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [8](#0-7)  and applies the stale `file.selection` against the new hunk layout in `formatPatch` [9](#0-8) .
5. Inspect the resulting commit: it contains different lines than those visually selected by the user in step 2, with no error surfaced.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })
