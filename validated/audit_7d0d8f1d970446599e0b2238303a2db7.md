### Title
Unbounded recursive parsing of `PuzzleWithRestrictions` memos allows pre-authentication stack overflow / wallet DoS - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody spec (used for CHIP-0043 composable custody, including PlotNFT/pool wallets) from an attacker-controlled `Program` memo. When the memo declares a nested `MofN` structure, `from_memo()` calls itself once per member with no depth limit, exactly the "unbounded type nesting" bug class described in the reported Apache Qpid CVE (recursive type deserialization causing `StackOverflowError`).

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses an untrusted `Program` and, when `further_branching` is true, constructs a `MofN` whose members are obtained by calling `PuzzleWithRestrictions.from_memo()` again for every entry in `MofNHint.member_memos`: [1](#0-0) 

There is no nesting-depth check anywhere in this recursive chain — `from_memo` → `MofNHint.from_program` → `from_memo` per member. An attacker who controls the memo `Program` (a plain CLVM byte blob) can nest `MofN` hints arbitrarily deep (e.g., hundreds of thousands of levels via a right-nested `[m, [[m,[[m,[...]]]]]]` structure), and each level only costs a few extra bytes to encode.

This memo is not consensus-validated CLVM output cost-limited by mempool rules — it's just an attacker-chosen `CREATE_COIN` memo blob that gets parsed *outside* of CLVM execution, in plain Python, by wallet code that tracks PlotNFT/pool state: [2](#0-1) 

`get_next_from_coin_spend()` is invoked by wallet sync logic when following a singleton coin's lineage (`PlotNFT`/pool-wallet tracking) and reads `singleton_create_coin.memo_blob`, then calls `PuzzleWithRestrictions.from_memo()` directly on attacker-supplied memo bytes without any recursion-depth or size guard. Because `Program` objects in this codebase are plain Python-wrapped s-expressions (not tail-call optimized, not the iterative `sha256_treehash`-style implementation used elsewhere in `chia/types/blockchain_format/tree_hash.py` specifically to avoid Python recursion limits), a sufficiently deep nested memo will exhaust the Python call stack and crash the wallet process with a `RecursionError`/segfault-class failure, before any authentication or balance/ownership checks are relevant — the parsing happens purely to *recognize* the puzzle.

Note: `Program.get_tree_hash()`/`sha256_treehash()` was deliberately made iterative to avoid this exact class of bug (comment: "This implementation goes to great pains to be non-recursive so we don't have to worry about blowing out the python stack" — [3](#0-2) ), which demonstrates the project is aware of and defends against this bug class elsewhere, but `PuzzleWithRestrictions.from_memo()` was not hardened the same way.

### Impact Explanation
A crafted memo, attached to any coin (e.g., a coin sent to, or observed by, a wallet that tracks PlotNFT/pool singleton lineage), can crash the wallet process performing pool-state sync when it calls `get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()`. This is a transaction-processing/wallet-availability halt (denial of service) triggered purely by data an attacker fully controls and can submit without any special privilege — matching the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
The nesting only requires a small, cheap CLVM blob (linear bytes per nesting level) and no CLVM execution cost is charged for constructing/parsing it via `Program.to()`/`from_memo()` — it is plain Python object traversal, not gated by mempool CLVM cost limits. Any party able to get a coin with a crafted memo observed by an affected wallet (owner of a PlotNFT/pool wallet, or code paths reusing this same recursive `from_memo`/`unknown_puzzles`/`fill_in_unknown_puzzles` pattern) can trigger it. Exploitability is somewhat bounded by needing the target wallet to actually walk that specific PlotNFT/pool-tracking code path, but no signature check, ownership check, or other gating happens before the recursive parse.

### Recommendation
Add an explicit maximum recursion depth (or convert to an iterative worklist algorithm, mirroring the pattern already used in `sha256_treehash`) in `PuzzleWithRestrictions.from_memo()`, `MofN`-related traversal (`unknown_puzzles`, `fill_in_unknown_puzzles`), and any other recursive consumer of untrusted memo `Program` data before further processing (e.g., cap depth to a small constant such as 32–64 and raise a `ValueError` if exceeded).

### Proof of Concept
Conceptually (cannot be executed in this read-only session):
1. Build a deeply right-nested `MofNHint` memo program: start with a leaf `MemberHint`/`UnknownMember` memo, then repeatedly wrap it as `PuzzleWithRestrictions(nonce, [], MofN(m=1, members=[wrap]))` for N ≈ 100,000+ iterations, producing the corresponding `.memo()` `Program`.
2. Encode that memo as a `CREATE_COIN` memo (`memo_blob`) on a coin spend that resembles/hits `PlotNFT.get_next_from_coin_spend()` lookup path (or any other code path calling `PuzzleWithRestrictions.from_memo()` on wallet-observed data).
3. Have the target wallet process this coin's spend during PlotNFT/pool sync — `get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, which recurses N times without any depth check, exhausting the Python call stack and crashing the wallet process.
