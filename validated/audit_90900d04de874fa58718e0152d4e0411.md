## Title
Unbounded Recursion in AccountKey RLP Decoding Allows Remote Node Crash via Deeply Nested `AccountKeyRoleBased` - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
Decoding an `AccountKeyRoleBased` from RLP recursively invokes `AccountKeySerializer.DecodeRLP`, which in turn can construct and decode another `AccountKeyRoleBased`, with no depth limit enforced during decoding. A crafted `TxTypeAccountUpdate` (or fee-delegated variants) transaction, or a direct call to the public RPC method `kaia_decodeAccountKey`, can embed an arbitrarily deep chain of nested `AccountKeyRoleBased` values, causing unbounded Go-stack recursion during RLP decoding and crashing the node — before any semantic validation (`CheckInstallable`/`IsCompositeType`) that would normally reject nested composite keys ever runs. This mirrors the Elasticsearch `innerForbidCircularReferences`/`PatternBank` issue (CVE-2024-52980): a recursive structural check/decoder with no depth bound, reachable by an unprivileged, minimally-privileged caller.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings, and for each element constructs a fresh `AccountKeySerializer` and recursively calls `rlp.DecodeBytes` on it: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type tag, instantiates the corresponding `AccountKey` implementation via `NewAccountKey`, and decodes into it: [2](#0-1) 

`NewAccountKey` allows `AccountKeyTypeRoleBased` to be selected again: [3](#0-2) 

This creates unbounded mutual recursion: `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → (`NewAccountKeyRoleBased`) → `AccountKeyRoleBased.DecodeRLP` → ... with the recursion depth controlled entirely by the encoded byte stream, and no check enforced at decode time.

The only defense against nested composite keys — `IsCompositeType()` combined with `CheckInstallable`/`CheckUpdatable`, which reject `ErrNestedCompositeType` — is applied *after* decoding completes: [4](#0-3) 

Because decoding happens strictly before this validation, a sufficiently deep nesting chain can exhaust the goroutine stack and crash the process (Go stack overflow is fatal and unrecoverable — it cannot be caught by `recover()`), during RLP decoding of the transaction itself.

This is reachable through two unprivileged paths:
1. The public RPC `kaia_decodeAccountKey` (`KaiaAPI.DecodeAccountKey`) directly calls `rlp.DecodeBytes` on arbitrary attacker-supplied bytes with no size/depth pre-check: [5](#0-4) 
2. Any `TxTypeAccountUpdate` / fee-delegated account-update transaction submitted to the node — these transaction types embed an `AccountKey` field that undergoes the same `AccountKeySerializer`/`AccountKeyRoleBased` RLP decoding as part of ordinary transaction decoding in the tx pool/block processing pipeline, prior to any account-key installability checks.

### Impact Explanation
A single malicious transaction or a single RPC request containing a deeply nested `AccountKeyRoleBased` payload can trigger uncontrolled recursion and crash the node process (denial of service), satisfying CWE-400 (uncontrolled resource consumption) analogous to the referenced Elasticsearch advisory. Because transaction decoding happens on every node that receives/propagates or is asked to decode the transaction (and identically for the RPC path on any node exposing the JSON-RPC API), this can be used to crash multiple nodes with a single crafted payload, causing service disruption / potential availability impact to the network (CVSS impact profile matches the referenced advisory: availability-high, no confidentiality/integrity impact).

### Likelihood Explanation
Likelihood is high: no privileged role is required. `kaia_decodeAccountKey` is a standard, non-privileged JSON-RPC method exposed by any node with the API enabled. Crafting the nested `AccountKeyRoleBased` payload requires only knowledge of the RLP/AccountKey encoding scheme (which is public), and no valid signatures or gas are needed for the RPC path. For the transaction path, submitting an account-update transaction requires only a funded account and a valid signature over the (attacker-controlled) key payload — signature validity does not constrain the nesting depth of the embedded account key structure, since signature checks occur logically after/alongside decode.

### Recommendation
- Enforce a maximum recursion/nesting depth (e.g., reject any `AccountKeyRoleBased` decode where a nested `AccountKeyRoleBased` or other composite type appears) directly inside `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP`, mirroring the existing `IsCompositeType`/`ErrNestedCompositeType` check but performed *during* decode rather than only at `CheckInstallable`/`CheckUpdatable` time.
- Alternatively, thread an explicit depth counter/context through the decode call chain and bail out with an error once a small fixed depth (e.g., 1, since nested composite types are never valid) is exceeded.
- Apply the same bound to `kaia_decodeAccountKey`/`kaia_encodeAccountKey` RPC entry points before delegating to `rlp.DecodeBytes`.

### Proof of Concept
Conceptually (exact byte-level PoC would need to be generated with the RLP encoder, but the structure is):
1. Construct innermost key: `AccountKeyPublic` (valid, minimal key).
2. Wrap it: `AccountKeyRoleBased{ pub, pub, pub }` (valid, 3 slots).
3. Wrap that RoleBased key as the sole element inside another `AccountKeyRoleBased{ inner }`.
4. Repeat step 3 recursively N times (e.g., N = 100,000), producing an RLP-encoded byte string representing `AccountKeyRoleBased(AccountKeyRoleBased(AccountKeyRoleBased(...)))`.
5. Submit the resulting bytes to `kaia_decodeAccountKey` via JSON-RPC, or embed it as the `AccountKey` field of a `TxTypeAccountUpdate` transaction and submit it to the node's tx pool.
6. `rlp.DecodeBytes` recurses through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` N times before any `CheckInstallable`/`ErrNestedCompositeType` rejection can occur, exhausting the goroutine stack and crashing the node process.

Note: I was unable to directly inspect the transaction-decoding call path (`tx_internal_data_account_update.go`, `transaction.go`) in full detail within this session to confirm the exact point in block/tx-pool processing where `AccountKey.DecodeRLP` is invoked relative to size/gas checks; a Devin session with full repository access should verify whether any upstream size limit (e.g., overall tx byte-size cap) already bounds the practical nesting depth before recommending/implementing the fix, and should measure the actual stack depth required to crash a real Go goroutine to size the PoC appropriately.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

func NewAccountKey(t AccountKeyType) (AccountKey, error) {

	case AccountKeyTypeLegacy:
		return NewAccountKeyLegacy(), nil
	case AccountKeyTypePublic:
		return NewAccountKeyPublic(), nil
	case AccountKeyTypeFail:
		return NewAccountKeyFail(), nil
	case AccountKeyTypeWeightedMultiSig:
		return NewAccountKeyWeightedMultiSig(), nil
	case AccountKeyTypeRoleBased:
		return NewAccountKeyRoleBased(), nil
	}
