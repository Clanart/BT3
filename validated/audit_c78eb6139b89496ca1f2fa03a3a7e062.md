## Title
Partial-commit line selection is applied against a freshly recomputed diff instead of the cached diff the user reviewed, allowing silent corruption of commit contents - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks of a file's diff for a partial commit. The selection is stored as a set of *absolute line indices* (`DiffSelection`) computed against the specific `ITextDiff` that was rendered in the UI at selection time. When the commit is actually executed, however, `applyPatchToIndex` does **not** reuse that already-loaded diff. Instead it independently re-invokes `getWorkingDirectoryDiff` to fetch a brand-new diff from disk/git, and then feeds the *old* selection indices into `formatPatch` against this *new* diff. This is the same bug class as the reported Solidity issue: a value (`liquidityRate`/`usageRate` there, the working-directory diff here) is recalculated at consumption time instead of reusing the cached value the caller's state was derived from, and the two can diverge.

### Finding Description
The relevant code path: [1](#0-0) 

`getWorkingDirectoryDiff` is called fresh here, completely independent of whatever diff was cached in `repositoryStateCache`'s `changesState.selection.diff` when the user made their line selections in the UI.

The user's selection is stored as position-based booleans, not content-anchored: [2](#0-1) 

`formatPatch` walks the **freshly-fetched** `diff.hunks`, and for every non-context line asks `file.selection.isSelected(absoluteIndex)` — `absoluteIndex` being nothing more than `hunk.unifiedDiffStart + lineIndex`, a positional offset into whatever diff happens to be passed in. There is no re-validation that the hunks/line ordering of the new diff still matches the hunks/line ordering of the diff the selection was made against.

Desktop is aware this class of drift can happen — there's reconciliation logic for the *currently displayed* file that clears selection bits for lines that "no longer exist," but it only runs opportunistically when the diff panel itself is reloaded, is scoped to a single selected file, and is asynchronous (can be superseded/raced): [3](#0-2) 

Crucially, this reconciliation is never invoked as part of the actual commit path. `_commitIncludedChanges` reads whatever `WorkingDirectoryFileChange` objects (with their `.selection`) currently sit in `repositoryStateCache`, and hands them straight to `createCommit` → `stageFiles` → `applyPatchToIndex`, which then does its own independent diff fetch: [4](#0-3) 

So the guard that exists (`withSelectableLines`) only protects the *visual* diff panel; it does nothing to protect the patch that is actually applied to the index at commit time, because that patch is built from a **second, independently-fetched diff**.

### Impact Explanation
If the tracked file's on-disk/index content changes between the moment the user reviews and checks specific lines in the diff panel and the moment they click "Commit" (e.g. an external editor autosave, a build/watch tool regenerating the file, a git attribute-driven smudge/clean or EOL-normalization filter shipped via the repository's own `.gitattributes`, or any other process touching the working tree in that window), the hunk boundaries/line offsets of the diff fetched inside `applyPatchToIndex` can differ from the diff the selection indices were derived from. Because `isSelected(absoluteIndex)` is purely positional, this can cause `formatPatch` to include lines the user never selected, or drop lines the user did select — all silently, with no additional confirmation from git or Desktop. The user believes they committed exactly what they saw and checked; the actual commit (and any subsequent push) can differ. This falls squarely into "silent corruption of what the user commits or pushes," one of the explicitly valid Desktop impact categories.

### Likelihood Explanation
Medium: it requires the working tree content for the specific file to change between diff-render time and commit time, which is not attacker-triggerable purely remotely, but a repository under attacker influence can increase the odds of this race by including `.gitattributes`-driven content filters, `ident`/keyword-expansion, or other checkout-time/apply-time transformations, combined with normal Desktop usage patterns (open file in an editor with autosave, watch/build tooling, or Desktop's own periodic background repository refreshes) that legitimately touch the same file during a partial-commit review session. No admin rights, malware, or unnatural user steps are required beyond ordinary partial-commit usage.

### Recommendation
Do not re-fetch the diff inside `applyPatchToIndex`/`stageFiles`. Instead, thread the exact `ITextDiff`/`ILargeTextDiff` object that was used to compute the user's `DiffSelection` (i.e., the cached diff already held in `changesState`) all the way through to `formatPatch`, and fail/re-prompt the commit if that cached diff can be shown to be stale relative to the current working-tree content (e.g. by comparing blob OIDs before applying), rather than silently regenerating a new diff and reusing old position-based selection state against it.

### Proof of Concept
1. Modify a tracked file with two separate multi-line changes so the diff has ≥2 hunks.
2. In Desktop's Changes view, open the diff and select only the lines belonging to hunk #1 (uncheck hunk #2).
3. Before clicking "Commit", cause the file content to shift on disk in a way that changes the diff's hunk boundaries/line offsets (e.g. an editor autosave adds/removes a blank line earlier in the file, or a `.gitattributes` `ident`/EOL filter changes expansion), without changing the visual diff panel Desktop already rendered.
4. Click "Commit".
5. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a new diff whose hunk offsets no longer line up with the indices in `file.selection`; `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) applies the stale selection bitmap to the new hunk layout, producing a patch that stages different lines than what the user checked in the UI — verifiable by diffing the resulting commit against the lines that were actually checked in step 2.
