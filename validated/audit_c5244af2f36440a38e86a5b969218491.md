### Title
`SignableTransaction::new` omits the `OP_RETURN` output from fee sizing, inflating change and underpaying fees - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts attacker- or caller-supplied `data`, adds it as a zero-value `OP_RETURN` output, but calculates the transaction vsize solely from `payments`. The resulting `needed_fee` omits the serialized `OP_RETURN` output. When change is requested, the omitted fee is added to the change output instead, so the final transaction pays `fee_per_vbyte * vbytes_without_op_return` rather than the fee required for the transaction actually signed.

### Finding Description
The data output is appended to `tx_outs` before fee estimation. [1](#0-0)  However, the initial fee calculation calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing only the payments and no representation of the already-created `OP_RETURN` output. [2](#0-1) 

The change path repeats the same omission by calculating `vbytes_with_change` from only `payments` and `change`, even though the final transaction still contains the data output. [3](#0-2) 

Consequently:

```text
intended_fee = fee_per_vbyte * vbytes(payments + OP_RETURN + change)
actual_fee   = fee_per_vbyte * vbytes(payments + change)
difference   = fee_per_vbyte * vbytes(OP_RETURN)
```

`difference` is erroneously credited to the change output. The transaction ultimately commits to these outputs through the Taproot sighash used by the signing machine. [4](#0-3) 

### Impact Explanation
An unprivileged caller who can cause a transaction with arbitrary `data` to be signed can make the wallet produce a transaction whose change output is larger than intended by the fee attributable to the `OP_RETURN` output. The signed transaction simultaneously underpays relative to the requested `fee_per_vbyte`.

If `fee_per_vbyte` is selected at or near the relay/mining boundary, the transaction can fail propagation or remain unconfirmed despite `needed_fee` and the minimum-fee check appearing to pass. [5](#0-4)  This is an incorrect accounting formula over public transaction data, directly analogous to omitting a required fee component before calculating spendable margin.

### Likelihood Explanation
The defect is deterministic whenever `data.is_some()` and a change output is created. The caller controls `data`, and the code accepts up to 80 bytes. [6](#0-5)  Larger data creates a larger omitted vsize component and therefore a larger incorrectly retained change amount. No malformed encodings, malicious validator, leaked key, or protocol misuse is required.

### Recommendation
Calculate vsize over the actual output set that will be signed, including the zero-value `OP_RETURN` output. `calculate_weight_vbytes` should either accept the complete `tx_outs` list or accept the serialized data parameter and construct the same `TxOut` used at lines 195–201. The change decision, `fee_with_change`, `needed_fee`, and maximum-standard-weight check must all use vbytes for the final transaction containing payments, optional data, and optional change.

### Proof of Concept
The following conceptual test demonstrates the accounting discrepancy:

```rust
let data = vec![0xAA; 80];
let tx = SignableTransaction::new(
    vec![input],
    &payments,
    Some(change_script),
    Some(data),
    fee_per_vbyte,
).unwrap();

let actual_vbytes = tx.transaction().vsize() as u64;
let expected_fee = fee_per_vbyte * actual_vbytes;

assert!(tx.needed_fee() < expected_fee);
assert_eq!(tx.fee(), tx.needed_fee());
```

The assertion holds because `transaction()` contains the `OP_RETURN` output, while `needed_fee()` was calculated before accounting for its vsize. The difference between `expected_fee` and `tx.fee()` is included in the change output instead of being paid as fees.
