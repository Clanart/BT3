### Title
Malicious git remote can spoof `WWW-Authenticate` header to trigger a GitHub Enterprise sign-in prompt against an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Sherlock finding is about shared caller logic (`msgValue`) whose invariant ("always zero for these adapters") is enforced nowhere, so a value the shared caller can legitimately produce reaches code that silently mishandles it. The same class of bug exists in GitHub Desktop's credential-helper trampoline: a shared classification function, `getEndpointKind`, trusts a value forwarded from the remote git server (the `WWW-Authenticate` header) to decide whether a completely arbitrary remote counts as a "GitHub" host, and that decision is used, unchecked, to launch the real GitHub Enterprise sign-in flow against that attacker-chosen origin.

### Finding Description
When Git needs credentials for an HTTPS remote it invokes Desktop's credential helper trampoline and forwards any `WWW-Authenticate` response header it received from the server as `wwwauth[...]` fields in the credential protocol payload.

`getEndpointKind` treats this attacker-influenced field as a trust signal: [1](#0-0) 

If the value contains `realm="GitHub"`, the function returns `'enterprise'` for *any* hostname — there is no correlation with a real GitHub/GHE endpoint, TLS certificate, or previously known account.

This classification feeds directly into `getCredential`, which is the caller shared across all credential requests (GitHub, GHE, and generic hosts): [2](#0-1) 

Because `endpointKind !== 'generic'` for the spoofed host and no stored account matches its API endpoint, the code calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` equal to the attacker's URL. That helper then starts the real GitHub Enterprise sign-in flow pointed at that attacker-chosen origin: [3](#0-2) 

`dispatcher.setSignInEndpoint(origin)` and `dispatcher.beginEnterpriseSignIn(cb)` are invoked with `origin` derived from the attacker-controlled `endpoint`, so the "GitHub Enterprise" sign-in dialog the user sees is wired to authenticate against the attacker's server rather than a real Enterprise instance.

The broken invariant, mirroring the Sherlock report, is: **shared caller code (`getCredential`) assumes `getEndpointKind` only returns `'enterprise'`/`'github.com'` for endpoints that are actually GitHub-operated**, but the classification function derives that verdict from data the remote server fully controls, with no verification (no TLS pinning, no cross-check against `isGitHubHost`'s network probe, no allow-list). None of the existing generic-credential guards (`isGist`, `isDotCom`, `isGHE`, `findGitHubTrampolineAccount`) apply once the `wwwauth[]` short-circuit fires, because it's checked before falling back to the network-based `isGitHubHost` check.

### Impact Explanation
A user cloning/fetching from a repository whose remote HTTPS server (or a MITM/proxy sitting in front of it) returns `WWW-Authenticate: Basic realm="GitHub"` on a 401 response can force Desktop to launch its Enterprise sign-in UI targeting that server's origin. If the user completes the (real-looking) Desktop-native sign-in flow, credentials/OAuth tokens are sent to the attacker's endpoint instead of a genuine GitHub Enterprise server — this is credential/token exfiltration triggered purely by data controlled through an untrusted git remote/proxy response, matching the requested "attacker controls a git remote/proxy response, resulting in credential/token exfiltration or unauthorized OAuth" impact class.

### Likelihood Explanation
Any git server the user is directed to add as a remote (a cloned/forked/malicious repo pointing at a custom HTTPS remote, or a transparent proxy/MITM on an untrusted network) can supply this header on an HTTP 401 response to any authenticated git operation (fetch/push/clone) — no special git configuration or user action beyond a normal git network operation is required. Git forwards `WWW-Authenticate` headers to credential helpers by design, so this is a reachable, unprivileged network response, not a local/host or credential-theft prerequisite.

### Recommendation
Do not let the `wwwauth[]` header alone elevate an unknown host to `'enterprise'`. At minimum:
- Require corroboration (e.g., only honor the header as a hint to skip the network probe, not as the final answer) or perform the same `isGitHubHost` verification even when a `wwwauth[]` realm claims "GitHub".
- Never invoke `promptForGitHubSignIn`/`beginEnterpriseSignIn` for a host that hasn't been positively confirmed as a GitHub API endpoint (via `isDotCom`/`isGHE`/verified `/meta` probe), regardless of what the remote server claims in its headers.

### Proof of Concept
1. Stand up an HTTPS server (attacker.example) that responds to any request with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim `git clone`/`git fetch` from `https://attacker.example/foo/bar.git` in GitHub Desktop (e.g., via a link/deep link adding this as a remote, or via a repo whose configured remote/submodule points there).
3. Git contacts the server, receives the 401 + spoofed header, and forwards `wwwauth[0]=Basic realm="GitHub"` to Desktop's credential helper.
4. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) returns `'enterprise'` for `attacker.example`.
5. `getCredential` finds no matching account for that host and calls `ui.promptForGitHubSignIn('https://attacker.example/...')`.
6. `promptForGitHubSignIn` (`app/src/lib/trampoline/trampoline-ui-helper.ts:87-93`) sets the sign-in endpoint to `https://attacker.example` and opens Desktop's native "Enterprise sign-in" dialog, prompting the user to authenticate against the attacker's origin.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
