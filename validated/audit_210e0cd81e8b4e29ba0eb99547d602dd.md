### Title
Unbounded array indexing on attacker-controlled CLVM atom-length prefix causes unhandled `IndexError` during canonical-encoding validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
The etcd advisory describes a parser that trusts an index/length field embedded in untrusted serialized data without checking it against the actual buffer size, leading to an out-of-bounds access and a crash (`ReadAll` in `wal/wal.go`). Chia has a structurally identical pattern in the CLVM canonical-encoding checker: `is_atom_canonical()` and `is_clvm_canonical()` in [1](#0-0)  and [2](#0-1)  decode a length-prefix byte from a raw `bytes` buffer and then index further into that buffer using an attacker-controlled `atom_len`/`offset` value, with no bounds check against `len(clvm_buffer)`.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the length-prefix mask bits from `clvm_buffer[offset]`, then loops `prefix_len` times doing `offset += 1; atom_len |= clvm_buffer[offset]` [3](#0-2) . If a submitter crafts a buffer where the multi-byte length-prefix header is truncated (e.g. the buffer ends before all prefix bytes are present), this loop indexes past the end of `clvm_buffer`, raising an unhandled `IndexError` instead of returning a validation error.

`is_clvm_canonical(clvm_buffer)` compounds this: after computing `atom_len` (which is directly derived from attacker-supplied bytes and can be arbitrarily large), it advances `offset += atom_len` [4](#0-3)  and then re-enters the loop, doing `b = clvm_buffer[offset]` on the next iteration [5](#0-4) . Because `atom_len` is only bounds-checked implicitly by `is_atom_canonical`'s `min_value` logic (which validates the encoding is "non-redundant," not that the atom fits in the buffer), a declared atom length larger than the remaining buffer causes `offset` to exceed `len(clvm_buffer)`, and the subsequent index raises `IndexError` — this is exactly the etcd bug class: an index/length field greater than the actual data size, unguarded, causing a runtime panic while parsing untrusted serialized input.

This mirrors the CWE-129/CWE-20 root cause of GHSA-m332-53r6-2w93: a length/index taken from untrusted data is used to index a collection without validating it is within bounds first.

### Impact Explanation
An unhandled `IndexError` raised deep in CLVM canonical-encoding validation, if not caught by an enclosing `try/except` at the call site, will propagate out of the code path that processes submitted transaction data (puzzle reveal/solution bytes ultimately derived from a spend bundle's CoinSpends, or generator bytes built from mempool spends), causing that validation task to fail with an unhandled exception rather than a controlled rejection. Depending on the calling context this can disrupt CLVM serialization/canonical-encoding checks tied to mempool admission and block-generator encoding, both of which are on paths reachable from ordinary transaction submission — this is a data-validation robustness bug of the same class as the etcd advisory (attacker-supplied length exceeds real data size → crash instead of graceful error).

### Likelihood Explanation
The indexing pattern is directly reachable with a hand-crafted, malformed CLVM byte buffer: the attacker only needs to control the raw bytes fed into these helpers (a truncated/oversized atom-length prefix), which does not require any privileged position — any entity able to submit CLVM-encoded data (spend bundle puzzle reveal/solution or a constructed generator) can trigger it. The likelihood that the exact same class of bug exists here as in etcd is high given the code performs unchecked raw-byte indexing driven by attacker-controlled length values, but I could not, within the available tool budget, definitively trace every call site of `is_clvm_canonical`/`is_atom_canonical` back to the exact point in `pre_validate_spendbundle()` or block-body validation where raw, unsanitized bytes reach these functions before any length/size pre-check is performed elsewhere (e.g., in the Rust `validate_clvm_and_signature` path). This should be verified by exercising `is_clvm_canonical()` directly with a truncated/malformed multi-byte atom-length header to confirm whether an `IndexError` is raised uncaught, and by tracing all call sites of these two functions to confirm which are on the untrusted-input path versus already-sanitized internal buffers.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` and `is_clvm_canonical()` before every buffer index: verify `offset < len(clvm_buffer)` (and `offset + prefix_len < len(clvm_buffer)`) prior to reading `clvm_buffer[offset]`, and treat an out-of-range offset/length as "not canonical" (return `False`) rather than allowing the index operation to raise. Additionally, audit and, where necessary, wrap all call sites of these functions in `try/except` (catching `IndexError`) so any residual out-of-bounds condition maps to a rejected/invalid input rather than an unhandled exception surfacing during mempool admission or block validation.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
