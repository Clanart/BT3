### Title
`SignableTransaction::new` computes `needed_fee` and the minimum-relay check from a weight/vbytes snapshot taken before the OP_RETURN data output is added — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
Analogous to the IronBank report (`getSupplyBalance` read before `accrueToken`, yielding a stale value), `SignableTransaction::new` derives `vbytes` and `needed_fee` from `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, where `payments` excludes the OP_RETURN output that was already appended to `tx_outs`. The fee accounting is performed on a stale view of the transaction's outputs, so the transaction is signed paying a fee computed for a smaller transaction than the one actually broadcast.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, when `data` is supplied, a zero-valued OP_RETURN output is pushed into `tx_outs`. However, the fee calculation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing the caller's `payments` slice — which never contains the data output. The same omission occurs in the change path at line 225-226. Consequently:

- `weight`/`vbytes` underestimate the real transaction by the size of the OP_RETURN output (base TxOut overhead plus a script of up to ~83 bytes for the maximum 80-byte payload permitted by the `TooMuchData` check at line 171).
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is underpriced.
- The `TooLowFee` guard at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`, so a transaction can pass this check yet actually fall below the minimum relay fee once the data output is included.
- When a change output is created (line 228-230), the change absorbs exactly `input_sat - payment_sat - fee_with_change`, so the effective fee equals the understated `needed_fee`; nothing later compensates for the missing bytes (`fee()` at line 138 confirms the real fee is whatever the stale calculation produced).

The data payload is attacker-influenced: it originates from the `InInstruction`/eventuality path where an external user deposits to Serai's Bitcoin address with up to 80 bytes of attached data, and that data is embedded into the multisig's spend transaction as the OP_RETURN output.

### Impact Explanation
The signed transaction pays a lower absolute fee than intended by `fee_per_vbyte`, and can pass the internal `TooLowFee` check while being under the network's minimum relay fee once broadcast. The transaction may be rejected by relay policy or linger unconfirmed, leaving user funds locked in a signed-but-unusable transaction that requires a new FROST signing round (fresh nonces, new transaction) to recover — directly paralleling the report's "funds left requiring a costly subsequent transaction to recover" impact. The shortfall scales with the attacker-controlled data length (up to ~90 vbytes of uncharged weight per transaction).

### Likelihood Explanation
Any external deposit carrying an `InInstruction` with data triggers the code path, since `data` is only `Some` when the user supplied it. The underestimation is deterministic whenever `data.is_some()`; whether it crosses the minimum-relay threshold depends on the chosen `fee_per_vbyte` and data length, but the fee-rate target is always missed. No collusion, malicious validator, or privileged access is required — only a public Bitcoin transaction with a data payload.

### Recommendation
Include the data output in the weight/vbytes accounting: pass the fully-formed `tx_outs` (or an explicit `has_data`/`data_len` parameter) to `calculate_weight_vbytes` in both the no-change call at line 204 and the with-change call at lines 225-226, so `needed_fee`, the `TooLowFee` check, and the `NotEnoughFunds`/`TooLargeTransaction` checks all reflect the final transaction.

```rust
// Conceptual: in networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 80];
let tx_with_data = SignableTransaction::new(
    inputs.clone(), payments, None, Some(data.clone()), fee_per_vbyte,
).unwrap();
let tx_no_data = SignableTransaction::new(
    inputs, payments, None, None, fee_per_vbyte,
).unwrap();

// needed_fee ignores the OP_RETURN output entirely:
assert_eq!(tx_with_data.needed_fee(), tx_no_data.needed_fee());
// but the actual signed tx is ~90+ vbytes larger:
assert!(tx_with_data.transaction().vsize() > tx_no_data.transaction().vsize());
// => actual fee rate = needed_fee / real_vsize < fee_per_vbyte,
//    and can be < DEFAULT_MIN_RELAY_TX_FEE while still passing TooLowFee.
```
