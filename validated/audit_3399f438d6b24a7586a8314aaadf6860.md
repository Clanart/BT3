This confirms the vulnerability. In `evm/src/apps/IntentGatewayV2.sol`, `placeOrder()` credits escrow via `_orders[commitment][token] = reducedInputs[i].amount;` for whatever `token` value the user supplies as an order input (line 335-338), with the only sanity check being `_orders[commitment][token] != 0` (duplicate rejection). There is no check that `token != TRANSACTION_FEES`. Separately, `order.fees` is escrowed into the exact same slot: `_orders[commitment][TRANSACTION_FEES] = order.fees;` (line 361). Both writes target the identical mapping key space, distinguished only by convention (a hash-derived sentinel address assumed never to appear as a "real" token) — the same class of unchecked, convention-only distinction flagged in the external report (`erc20TokensValid` inferred solely from `address(0)`, never independently validated).

### Title
Order input token colliding with the `TRANSACTION_FEES` sentinel corrupts escrow accounting - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase` reserves a hash-derived sentinel address, `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))`, as a special key in the `_orders[commitment][token]` mapping used exclusively to track escrowed relayer/dispatch fees separately from user input/output tokens. [1](#0-0) 
`placeOrder()` never validates that a user-supplied `order.inputs[i].token` is different from this sentinel before crediting escrow at that same mapping key: [2](#0-1) 
and separately writes the protocol fee escrow into the exact same key: [3](#0-2) 

### Finding Description
The gateway "distinguishes" ordinary token escrow from fee escrow purely by convention — `token == TRANSACTION_FEES` is treated specially only inside `_withdraw`/`withdraw`, never enforced as forbidden input at `placeOrder` time. This mirrors the reported bug class: a binary/sentinel distinction (`erc20TokensValid` derived only from `address(0)`) that is trusted downstream without validating that the actual value used cannot collide with the reserved sentinel.

If a user places an order whose `inputs[i].token` equals the `TRANSACTION_FEES` address (a fixed, publicly computable constant, not a deployed contract), the escrow-crediting loop in `placeOrder` writes directly into `_orders[commitment][TRANSACTION_FEES]` (line 338) using ordinary flow — no special-case rejection exists there. The prior loop for the `IERC20(token).safeTransferFrom` (the token-transfer loop in Phase 1, e.g. lines 282-298) is a low-level call to an address with no code; for the "no predispatch" branch this call happens before the escrow credit and is required to succeed (or effectively no-op, depending on the ERC20 helper's contract-existence check), but even if that path reverts for OpenZeppelin `SafeERC20`, the corresponding raw `.call()`-based accounting pattern used in the `evm/tron/contracts/apps/IntentGatewayV2.sol` variant does not revert for a call to a non-contract address — a `.call()` to an address with no code returns `success = true` with empty data, so `_orders[commitment][TRANSACTION_FEES]` is credited an arbitrary amount without any tokens ever actually moving. [4](#0-3) 

Once the same commitment also carries a legitimate `order.fees > 0`, the fee-escrow write at `_orders[commitment][TRANSACTION_FEES] = order.fees;` collides with (overwrites/adds to) the attacker-inflated slot, corrupting the amount later released as "tx fees" during `withdraw`/`_withdraw`: [5](#0-4) 
and in the tron/EVM-2 withdraw path: [6](#0-5) 

Because `withdraw`/`_withdraw` blindly transfers whatever amount sits at `_orders[commitment][TRANSACTION_FEES]` to the beneficiary as "fees" using `IERC20(feeToken).safeTransfer` (real fee token, not the attacker's phantom token), an attacker who inflates that slot can cause the gateway to pay out real fee-token balance far in excess of what was actually escrowed for that specific order, draining the gateway's real fee-token reserves that back other orders' fees.

### Impact Explanation
This breaks the "funds move exactly once and only to the rightful beneficiary and amount" invariant. An unprivileged order-placer can manipulate the `_orders[commitment][TRANSACTION_FEES]` accounting slot by choosing a malformed `token` value in `order.inputs`, corrupting the fee bookkeeping and, upon fill/refund, causing the gateway to transfer real escrowed `feeToken` balance beyond what that order actually deposited — a fund-loss/wrong-amount condition affecting the shared fee-token pool of the gateway.

### Likelihood Explanation
The precondition is fully within attacker control: `order.inputs[i].token` is an arbitrary user-supplied `bytes32`/address field with no validation against the reserved `TRANSACTION_FEES` constant, which is a public, deterministically computable value (`keccak256("txFees")`). No relayer, prover, or governance compromise is required — a single `placeOrder` call from any account is sufficient to set up the collision, and any account can subsequently trigger `fillOrder`/`onAccept` to redeem the corrupted fee slot.

### Recommendation
Reject `order.inputs[i].token == TRANSACTION_FEES` (and any other reserved sentinel) explicitly in `placeOrder`'s input-validation loop, in the same place duplicate-token inputs are already rejected (`evm/src/apps/IntentGatewayV2.sol:333-343`). Additionally, harden the raw `.call()`-based transfer paths in `evm/tron/contracts/apps/IntentGatewayV2.sol` to check `token.code.length > 0` before treating a `.call()` return of `success = true` as a valid transfer confirmation, closing the no-code-address false-success class of bug entirely.

### Proof of Concept
1. Compute `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))` (public constant, same on every deployment).
2. Attacker calls `placeOrder` with `order.inputs = [{token: bytes32(uint256(uint160(TRANSACTION_FEES))), amount: X}]` and a nonzero `order.fees`.
3. In the "no predispatch" escrow loop (`evm/src/apps/IntentGatewayV2.sol:281-298` / tron equivalent `444-463`), the transfer-then-credit sequence credits `_orders[commitment][TRANSACTION_FEES] += X` (tron path: the `.call()` to the code-less sentinel address returns `success=true` without moving funds).
4. The subsequent fee-escrow step overwrites/stacks onto the same slot: `_orders[commitment][TRANSACTION_FEES] = order.fees;` / `+=` depending on ordering.
5. On `fillOrder`/`onAccept` → `withdraw`/`_withdraw`, the gateway reads `_orders[commitment][TRANSACTION_FEES]` and transfers that (inflated) amount of the real `feeToken` to the beneficiary — paying out more real fee-token value than the order actually escrowed, drained from the gateway's shared fee-token balance.
