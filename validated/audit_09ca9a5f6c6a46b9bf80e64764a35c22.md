### Title
`SignableTransaction::new` computes weight/vbytes and fee ignoring the OP_RETURN data output, producing under-priced and potentially non-standard transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The analog to "share pricing ignores debt": `SignableTransaction::new` computes the transaction's weight, virtual size, required fee, and the standardness check using only the payment outputs and the optional change output, while the optional `data` OP_RETURN output — which is pushed onto `tx_outs` before the measurements — is never included in `calculate_weight_vbytes`. The reported/accounted size of the transaction ignores a component that is actually serialized and paid for, exactly as the vault's `totalAssets` ignored the debt leg.

### Finding Description
In `crypto`-adjacent in-scope code `networks/bitcoin/src/wallet/send.rs`:

1. `tx_outs` is built from `payments`, and then an OP_RETURN `TxOut` is appended when `data` is `Some` (lines 188–202).
2. `calculate_weight_vbytes(tx_ins.len(), payments, None)` is then called with `payments` — the `data` output is not represented (line 204). The function builds a template `Transaction` whose `output` list is `payments` plus optionally `change`, and calls `tx.weight()` on that (lines 85–101).
3. `needed_fee = fee_per_vbyte * vbytes` and the minimum-relay-fee check are computed off this too-small `vbytes` (lines 206–213).
4. When change exists, `calculate_weight_vbytes` is again called with `payments` and `Some(&change)` — still omitting `data` — and `change value = input_sat - payment_sat - fee_with_change` is computed with the under-estimated `fee_with_change` (lines 224–235).
5. The `MAX_STANDARD_TX_WEIGHT` check uses `weight`, which likewise excludes the data output (line 241).

So every transaction carrying a non-empty `data` payload has its serialized size under-accounted by roughly `8 + compactsize + 2 + data.len()` base bytes (≈ up to ~92 vbytes for the 80-byte maximum) times the 4× base-byte weight multiplier. The actual fee rate achieved is `needed_fee / actual_vbytes < fee_per_vbyte`, and the actual weight may exceed `MAX_STANDARD_TX_WEIGHT` without `TooLargeTransaction` ever firing.

### Impact Explanation
- **Effective fee rate below the intended/announced rate**: for any `data`-carrying spend, the fee reserved is priced for a smaller transaction than the one broadcast. When `fee_per_vbyte` is set near the relay/mining floor (the code explicitly checks against `DEFAULT_MIN_RELAY_TX_FEE`), the true fee rate can fall below the minimum relay fee, causing the signed transaction to be rejected by peer mempools — a spend of vault/multisig funds that is produced but not spendable/propagatable on the network.
- **Standardness bypass**: a transaction whose true weight crosses `MAX_STANDARD_TX_WEIGHT` via the omitted OP_RETURN output passes the weight check and yields a non-standard transaction that nodes will not relay.
- **Change over-credit**: `input_sat - payment_sat - fee_with_change` under-deducts the fee needed for the data output, so change outputs are larger than they should be relative to the requested fee policy — the value accounting overstates what remains after paying the fee, paralleling the overvaluation in the source finding.

### Likelihood Explanation
`data` is an attacker-/user-influenced field: in Serai's Bitcoin integration, the OP_RETURN output carries the `InInstruction`/instruction data supplied by external depositors/withdrawers (see `extract_serai_data` usage in `processor/src/networks/bitcoin.rs`), and `SignableTransaction::new` is the single path used to construct spends. Any spend carrying a data payload deterministically misprices; spends priced at the relay floor become unbroadcastable. No special privileges are needed beyond supplying transaction data that flows into a `SignableTransaction`.

### Recommendation
Include the OP_RETURN output in the weight/vbytes measurement: build the template `Transaction` inside `calculate_weight_vbytes` from the full planned output set (payments + OP_RETURN + optional change), or pass `data`/`tx_outs` into the helper so `tx.weight()`, the minimum-fee check, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output. Concretely, move the measurement after `tx_outs` is fully assembled, or extend `calculate_weight_vbytes` to accept a `data: Option<&[u8]>` parameter that appends `ScriptBuf::new_op_return(...)` to the template outputs.
