### Title
Missing Cap on Combined Tier + Boost Percentage in `ReferralStorage.trigger()` Leads to Over-Allocation and Frozen Referral Rewards - (File: rewards/ReferralStorage.sol)

### Summary
The external report describes a bug class where a fee/percentage meant to apply to a combined total is instead applied without accounting for the fact that the pieces being split can, in aggregate, exceed the intended total — leading to over-allocation and downstream failures. The same bug class is present in `ReferralStorage.trigger()`, which splits a referral bonus between referrer and referee using `basic + boostesd` without ever validating that this sum stays within `DENOMINATOR` (100%).

### Finding Description
`trigger()` is called by `MasterMagpie` every time an ordinary user harvests rewards, using the harvested `totalReward` as the base amount for referral bonus accounting: [1](#0-0) 

Inside `trigger()`, the referrer's percentage is the sum of a per-tier `basic` percentage (owner-set, capped individually at `DENOMINATOR` in `setTier`) plus an uncapped `boostesd` term derived from `_calBoosted`, and this combined figure is used to compute both the referrer's and referee's share: [2](#0-1) 

`setTier` only bounds an individual tier's `rewardPercentage` to `<= DENOMINATOR`: [3](#0-2) 

but nowhere is `basic + boostesd` checked against `DENOMINATOR`. Since `refererPercentage + refereePercentage ≈ basic + boostesd`, whenever this sum exceeds `DENOMINATOR`, `refererAmount + refereeAmount` credited via `rewardAmount +=` on lines 190-191 exceeds the actual `_amount` harvested by the referee for that call. This is the same class of bug as the report: a total meant to be split between two parties is instead over-applied to both parts, producing bookkeeping that no longer matches the real underlying amount.

### Impact Explanation
`ReferralStorage.claimReward()` pays out purely from the contract's on-hand `MGP` balance based on the internally tracked `rewardAmount` bookkeeping: [4](#0-3) 

Because `trigger()` can accumulate `rewardAmount` credits across referrers/referees in aggregate exceeding the MGP actually funded/reserved for referral bonuses, once accumulated credits outpace the contract's actual MGP balance, `claimReward()` calls made by any user (referrer or referee) whose turn comes after the balance is exhausted will revert on `safeTransfer` due to insufficient balance. This is a permanent freeze of already-earned, unclaimed referral yield for those users — funds they are owed but can never withdraw until (if ever) the contract is manually re-funded, which is outside the ordinary user's control. This matches the accepted impact category of permanent freezing of unclaimed yield.

### Likelihood Explanation
This requires no malicious admin action — it can occur under a plausible configuration where a tier's `rewardPercentage` (up to 100%) is combined with `_calBoosted`, which for a given referrer is bounded by `BoostPoint` (a value set once at initialization and not shown to be re-validated against remaining headroom under the tier's percentage). Any deployment where `tier.rewardPercentage + BoostPoint > DENOMINATOR` for a referrer's tier will trigger over-allocation on every ordinary harvest call that routes through `trigger()`, since normal users harvesting via `MasterMagpie` are the ones invoking this path — no privileged action is needed to reach the vulnerable code once the parameters are set.

### Recommendation
In `trigger()`, cap the combined percentage: `uint256 combined = basic + boostesd; if (combined > DENOMINATOR) combined = DENOMINATOR;` before computing `refererPercentage` and `refereePercentage`, ensuring `refererAmount + refereeAmount` can never exceed `_amount`. Additionally, enforce at `setTier`/boost-configuration time that the maximum possible `tier.rewardPercentage + BoostPoint` cannot exceed `DENOMINATOR`.

### Proof of Concept
1. Owner deploys `ReferralStorage` with `_boostPoint` set to, e.g., `3000` (30%).
2. Owner calls `setTier(1, 8000)` (80%) for the default tier assigned in `registerCode`.
3. A referrer registers a code and locks a large amount of MGP in `VLMGP`, becoming the dominant holder of `totalBoostFactor`, so `_calBoosted(referrer)` approaches `BoostPoint` (3000).
4. A referee uses that code (`useCode`) and stakes/harvests through `MasterMagpie`, causing `trigger()` to be invoked with `basic + boostesd ≈ 8000 + 3000 = 11000 > DENOMINATOR (10000)`.
5. `refererAmount + refereeAmount` computed from `11000/10000 * _amount` exceeds `_amount`, over-crediting `rewardAmount` for both parties relative to actual harvested MGP.
6. Repeated harvests compound this over-crediting across many referrer/referee pairs until the `ReferralStorage` contract's actual `MGP` token balance is insufficient to cover all outstanding `rewardAmount` balances.
7. Subsequent unprivileged calls to `claimReward()` by legitimate referrers/referees revert on `MGP.safeTransfer` due to insufficient contract balance, permanently freezing their already-earned referral rewards.
