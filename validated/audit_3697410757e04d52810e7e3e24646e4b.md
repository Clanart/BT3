### Title
`git submodule update` re-enables `protocol.file.allow=always`, letting a malicious repo's `.gitmodules` read arbitrary local files via a `file://` submodule URL - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  accepts an `allowFileProtocol` flag that, when set, passes `-c protocol.file.allow=always` to `git submodule update --init --recursive`. Modern Git disables the `file://` transport for submodules by default (`protocol.file.allow=user`) specifically to stop a malicious repository's `.gitmodules` from causing the client to clone an arbitrary local path (e.g. `file:///home/user/.ssh` or another sensitive directory) into the submodule's working tree, which can then be committed/exfiltrated or overwrite files. This flag override is decided by Desktop's own code, not validated against the untrusted `.gitmodules` content the attacker fully controls.

### Finding Description
`.gitmodules` is a file that ships inside a cloned/fetched repository and is therefore fully attacker-controlled content (analogous to the "fake dLoopCore" input from the seed report: an untrusted, caller-supplied object that a privileged operation trusts). When Desktop calls `git submodule update --init --recursive` with `allowFileProtocol: true`, Git's protection against `file://` submodule URLs (added upstream specifically to prevent this class of attack, see git's `protocol.file.allow` hardening) is disabled for that invocation, regardless of what URLs the `.gitmodules` file specifies: [2](#0-1) 

Because the flag is applied unconditionally to the whole `submodule update --init --recursive` command rather than being scoped/validated per submodule URL, a submodule entry crafted by the attacker with `url = file:///some/local/path` will be honored: Git will "clone" the local path as if it were a remote, copying its contents into the submodule directory inside the user's working tree.

### Impact Explanation
If reachable, this allows a malicious repository to read files from arbitrary locations on the victim's filesystem (subject to OS file permissions) into the submodule's working directory, where they become visible/committable inside the repo — a read/exfiltration primitive triggered purely by cloning/fetching a hostile repository, matching the report's "corrupted trust boundary" pattern where a caller-supplied object's fields are used to drive privileged behavior without validation.

### Likelihood Explanation
I could not fully verify, within the indexed portion of the codebase, all the call sites that set `allowFileProtocol: true` versus `false`, nor whether Desktop restricts this to specific trusted flows (e.g. only during initial clone of a repo the user explicitly typed the URL for) or whether it can be reached for repos added generically (`git pull`/`checkout` on an untrusted third-party clone). This materially affects likelihood, and I was not able to enumerate all callers of `updateSubmodulesAfterOperation` with the available tool budget.

### Recommendation
- Do not globally set `protocol.file.allow=always` for `git submodule update`. If file-protocol submodules must be supported for legitimate use cases (e.g. local relative submodule paths within the same repo), scope the allowance narrowly (e.g. only allow `file://` URLs that resolve inside the parent repository's own working directory), rather than passing a blanket `-c protocol.file.allow=always` flag.
- Audit every call site of `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` for trusted, first-party-verified repository content, and default to `false`/`user` otherwise.

### Proof of Concept
Given the code above, an attacker publishes a repository with a `.gitmodules` entry:
```
[submodule "leak"]
    path = leak
    url = file:///Users/victim/.ssh
```
If a Desktop code path invokes `updateSubmodulesAfterOperation(..., allowFileProtocol: true)` when initializing/updating submodules for this cloned repository, Git will execute `git -c protocol.file.allow=always submodule update --init --recursive`, and the `file://` URL protection is bypassed, copying `/Users/victim/.ssh` into the repository's `leak/` submodule directory.

Note: due to index size limits I was not able to inspect every call site that passes `allowFileProtocol`, so I cannot confirm with full certainty whether this flag is reachable for arbitrary untrusted repositories versus only for narrowly trusted scenarios. Starting a full Devin session with complete repository access would allow tracing all callers of `updateSubmodulesAfterOperation` to confirm exploitability with certainty.
