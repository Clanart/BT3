### Title
Malicious Git remote can silently trigger a GitHub Enterprise OAuth sign-in flow pointed at an attacker-controlled endpoint via the credential-helper trampoline - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Like the `BatonFarm` report, the broken invariant here is "a privileged action (`initiateMigration` / here, initiating an OAuth sign-in flow) can only be triggered through a trusted, curated path" — but Desktop's credential-helper trampoline lets an **attacker-controlled Git server** (the analog of the untrusted external contract) drive that trusted path by forging an HTTP `WWW-Authenticate` header, causing Desktop to auto-populate and launch a GitHub Enterprise OAuth flow against an arbitrary attacker-chosen origin without the normal manual "EndpointEntry" confirmation step.

### Finding Description
When Git performs HTTPS authentication it invokes Desktop's credential helper (`git-credential-desktop` → `createCredentialHelperTrampolineHandler`). To classify the remote as GitHub/Enterprise/generic, `getEndpointKind` inspects the `wwwauth[]` values that Git forwards from the **remote server's HTTP response**: [1](#0-0) 

If the attacker-controlled server sends `WWW-Authenticate: Basic realm="GitHub"`, the endpoint is classified as `'enterprise'` purely on the server's say-so, with no verification such as the `isGitHubHost` network check being required first.

Then, in `getCredential`, because there is no existing account bound to that origin, Desktop prompts for GitHub sign-in using the **attacker-supplied endpoint URL itself**: [2](#0-1) 

`ui.promptForGitHubSignIn(endpoint)` does not just show a form for the user to type a URL — for any non-`github.com` hostname it calls `beginEnterpriseSignIn` and *immediately* calls `setSignInEndpoint(origin)` with the attacker's origin, short-circuiting the manual `EndpointEntry` step that is supposed to be the safeguard against arbitrary endpoints: [3](#0-2) 

Once the endpoint is set, `authenticateWithBrowser` opens the system browser at `getOAuthAuthorizationURL(endpoint, csrfToken)` — i.e., an OAuth authorize URL hosted entirely on the attacker's origin: [4](#0-3) 

When the protocol-handler callback fires, `resolveOAuthRequest` only validates the CSRF `state` token (which Desktop itself generated and which the attacker's own page can simply echo back), then exchanges the code by POSTing to the same attacker-controlled `endpoint`: [5](#0-4) 

No guard verifies that `endpoint` actually corresponds to a legitimate/known GHE instance (or one the user manually typed and confirmed) before this flow is launched — the value flows straight from the Git remote's authentication challenge to a live OAuth sign-in attempt.

### Impact Explanation
This lets a malicious or compromised Git remote (or a MITM/proxy on an HTTP git connection) cause Desktop to launch a full OAuth "Sign in to GitHub Enterprise" flow toward a domain the attacker fully controls, purely by having the victim clone or fetch a repository. The attacker's server can serve a convincing fake "Authorize application" / login page at that origin to phish GHE credentials or a personal access token, and since the redirect/callback and token-exchange endpoint are also attacker-controlled, any resulting "account" bound in Desktop is effectively attacker-supplied — enabling credential exfiltration and unauthorized account binding without the user ever intentionally starting a sign-in flow or typing an untrusted URL. This matches the valid impact class ("unauthorized OAuth or account binding" / "credential/token exfiltration" triggered by a git remote/proxy response).

### Likelihood Explanation
Low-to-moderate: it requires the victim to add/clone/fetch from a remote controlled by the attacker (or to be MITM'd on an unauthenticated HTTPS connection), and it depends on Git actually forwarding the crafted `WWW-Authenticate` header during a 401 challenge, which is standard Git HTTP auth behavior and does not require any unusual user action beyond a normal `git fetch`/`clone`.

### Recommendation
- Do not trust the `wwwauth[realm="GitHub"]` heuristic alone to classify an endpoint as `'enterprise'`; require a successful `isGitHubHost` verification (or equivalent) before treating the credential-helper endpoint as GitHub-affiliated.
- In `trampoline-ui-helper.ts`, do not auto-advance past `EndpointEntry` via `setSignInEndpoint(origin)` for endpoints that were not explicitly typed/confirmed by the user; instead pre-fill the field and require explicit user confirmation before initiating the OAuth authorize request.
- Bind the OAuth `state`/callback validation to the specific sign-in session initiated by explicit user action, and surface the endpoint clearly in the sign-in UI so users can recognize unexpected/unfamiliar hosts before authorizing.

### Proof of Concept
1. Attacker stands up an HTTPS git server (e.g. `https://evil.example/repo.git`) that responds to unauthenticated Git HTTP requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this as a remote (or clones/fetches it) in GitHub Desktop.
3. Git invokes the credential helper; `getEndpointKind` (`trampoline-credential-helper.ts:157-165`) classifies the endpoint as `'enterprise'` from the forged header.
4. `getCredential` finds no existing account for `evil.example` and calls `ui.promptForGitHubSignIn('https://evil.example')`.
5. `trampoline-ui-helper.ts:80-99` calls `beginEnterpriseSignIn` + `setSignInEndpoint('https://evil.example')`, bypassing manual endpoint entry.
6. `authenticateWithBrowser` opens the system browser to `https://evil.example/login/oauth/authorize?...`, an attacker-served phishing/OAuth page.
7. Attacker's page redirects back with a forged `state`/`code`; `resolveOAuthRequest` exchanges the code against `https://evil.example/login/oauth/access_token`, completing an "authenticated" flow entirely under attacker control.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
