Based on the report's bug class — a signed structure that omits a binding identifier (marketplace address), letting an attacker replay/mismatch a valid signature against the wrong context — the closest reachable analog in `shopify_app` is in webhook verification, where the HMAC signature covers only the request body and never binds the `shop` context that downstream code trusts from an unsigned header.

### Title
Webhook shop-domain context is not covered by HMAC signature, allowing cross-shop context injection - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates a webhook request solely by comparing an HMAC over the raw request body against the app's shared secret. The shop identifier consumed by the rest of the pipeline (`shop_domain`, used to dispatch and process the webhook job) is read straight from an unsigned HTTP header and is never included in the HMAC-covered data.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the HMAC digest over `request.raw_post` only: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` calls this same `hmac_valid?(data)` where `data = request.raw_post`, and separately exposes `shop_domain` read directly from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, which is not part of the signed data at all: [2](#0-1) 

This `shop_domain` is exactly what downstream job dispatch trusts to determine which shop's context/session the webhook payload belongs to, both in the documented custom-controller pattern and the generated declarative-webhook controller template: [3](#0-2) [4](#0-3) 

The webhook secret used for `hmac_valid?` is the app's single shared client secret (`ShopifyApp.configuration.secret`), not a per-shop secret. This means the same secret validates webhook bodies for every shop that installed the app. Because the signature never binds the shop domain, a party who legitimately received one HMAC-signed webhook body (e.g., from their own store's installation of the same app) can present that exact valid `(body, HMAC)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value pointing at a different, unrelated shop. `hmac_valid?` still returns true (it never looked at the header), so `WebhooksController`/generated controllers accept the request and dispatch a job using the attacker-chosen `shop_domain`: [5](#0-4) 

This is the direct analog of the reported bug class: a cryptographically verified structure (the `Credit` signature / here, the webhook HMAC) omits an identifier (`MarketplaceAddress` / here, the shop domain) that a different, less-trusted channel supplies and that downstream logic relies on for authorization/context — enabling reuse of a validly-signed payload in an unintended context.

### Impact Explanation
An attacker can cause the app to process a validly-HMAC-verified webhook body under an arbitrary victim shop's context (`shop_domain`), without ever compromising that victim shop or its credentials. Depending on what the app's webhook jobs do with `shop_domain` (e.g., `Shop.find_by(shopify_domain: shop_domain)` then acting on that shop's stored access token, as shown in the generated job template), this enables cross-shop data confusion, spurious triggering of privileged flows (e.g., mandatory privacy webhooks like `shop/redact`, `customers/redact`, or `app/uninstalled` handling) attributed to a shop that never sent that data: [6](#0-5) 

### Likelihood Explanation
Exploitability requires only that the attacker obtain one legitimately signed webhook (trivially achievable by installing the same public app on their own store and triggering any webhook topic, e.g., placing an order) and then re-send that raw body with the same valid HMAC header but an attacker-chosen `X-Shopify-Shop-Domain` header to the app's public webhook endpoint. No secret material or victim interaction is needed, making this reachable from an unrelated/anonymous party relative to the victim shop.

### Recommendation
Bind the shop context into the verified signature material, or otherwise independently authenticate/authorize the shop domain before trusting it, e.g.:
- Include the shop domain (and/or webhook id/topic) in the value that is HMAC-verified, or
- Cross-check the `X-Shopify-Shop-Domain` header against the shop the app has an active session with the derived `X-Shopify-Webhook-Id`/API call to Shopify, or
- At minimum, validate that the shop-domain header corresponds to a shop for which the app currently holds an active, installed session before dispatching any job, rejecting otherwise.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), capturing the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` sent by Shopify to the app's webhook endpoint.
2. Attacker sends a new POST request directly to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged — still valid because `H` is a function of `B` and the shared app secret only), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` returns `true` because the body/secret pair matches.
4. The controller/job proceeds using `shop_domain` = `victim-shop.myshopify.com`, processing attacker-supplied webhook data under the victim's shop context.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
