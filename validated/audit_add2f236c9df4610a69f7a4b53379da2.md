### Title
Attacker-controlled `ThresholdKeys` deserialization accepts inconsistent shares/parameters, yielding unusable or attacker-chosen group keys - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation mode/coefficients, the `secret_share`, and all `verification_shares` directly from attacker-influenced bytes, then constructs the object via `ThresholdKeys::new`. `ThresholdKeys::new` validates only structural properties (share count, participant bounds, `t <= n`, Constant interpolation requires `t == n`) and computes `group_key` purely as an interpolation of the supplied verification shares. It never checks that the supplied `secret_share` is consistent with `verification_shares[i]` (i.e., that `secret_share * G == verification_shares[i]`), nor that the supplied `Interpolation::Constant` coefficients are consistent with the verification shares. The result is a deserializer that materializes an internally inconsistent key object — the analog of the report's "arbitrarily set connection parameters via deserialized input" class mapped onto Serai's share/key deserialization surface.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` (lines 574-632) parses everything from the reader:

```rust
// crypto/dkg/src/lib.rs
let secret_share = Zeroizing::new(C::read_F(reader)?);            // attacker-controlled
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?); // attacker-controlled
}
ThresholdKeys::new(ThresholdParams::new(t, n, i)..., interpolation, secret_share, verification_shares)
```

`ThresholdKeys::new` (lines 349-391) checks:
- `verification_shares.len() == n`,
- each key `<= n`,
- Constant interpolation only when `t == n`,

and then derives `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i)`. Nothing binds `secret_share` to `verification_shares[i]` or binds the `Constant(c)` vector to the shares. A crafted byte stream is therefore accepted as a valid `ThresholdKeys` where:

- `secret_share * G != verification_shares[i]` — the holder will emit signature shares that fail `share_verification_statements`-style verification, causing every signing attempt with these keys to abort (in `pedpop`, `calculate_share` blames via `BatchId::Share`; in FROST, `sign`/`verify` will reject).
- With `Interpolation::Constant`, an attacker additionally picks arbitrary coefficients `c[i]`, so `interpolation_factor` returns attacker-chosen scalars — the effective per-participant share weight is whatever the bytes say, decoupled from any real polynomial.
- `group_key` is fully attacker-chosen (pick `verification_shares` arbitrarily), so a reader that trusts a deserialized `ThresholdKeys` reports/receives funds under a key nobody can sign for — matching the "funds reported received that are not spendable" acceptance criterion.

This is the deserialization analog: like the H2O JDBC URL, an unvalidated attacker-controlled field (`connection_url` there; `secret_share`, interpolation coefficients, and `verification_shares` here) is consumed verbatim into a security-relevant object without a consistency proof.

### Impact Explanation
Any code path that accepts serialized `ThresholdKeys` from a peer or untrusted store (the in-scope rule explicitly lists `ThresholdKeys::read` as an untrusted-byte sink) materializes keys that either (a) cannot produce valid signatures — permanently bricking signing for the advertised `group_key` and making any received funds unspendable — or (b) under `Interpolation::Constant`, skew every participant's interpolation weight so honest shares combine into signatures for a key different from what other honest parties computed. The attacker controls the advertised group key outright. Severity: High (integrity/availability of the threshold key with a forged-key angle; no secret leakage, so not Critical).

### Likelihood Explanation
Reachable whenever an unprivileged party can supply or influence the bytes later fed to `ThresholdKeys::read` — e.g., key-share/key registration messages, restores, or coordinator-supplied key blobs. The primitive requires no collusion and no validator privileges; it only needs write access to the serialized input. If the deployment only ever reads keys it wrote itself, impact degrades to a DoS-on-corruption robustness issue (Medium); given the explicit listing of `ThresholdKeys::read` as an untrusted-input sink, High is justified.

### Recommendation
In `ThresholdKeys::new` (and therefore `read`), enforce consistency:
1. Verify `C::generator() * secret_share == verification_shares[&params.i()]` before constructing the object.
2. For `Interpolation::Constant`, additionally verify the coefficient vector is consistent with the verification shares (e.g., recompute expected shares or require a accompanying proof); at minimum, document that Constant-interpolated keys must only be constructed by the DKG, never deserialized from untrusted input.
3. Consider authenticating serialized `ThresholdKeys` (MAC/signature) at the storage/transport layer so `read` cannot see attacker-chosen bytes.

### Proof of Concept
```rust
// Conceptual: craft bytes accepted by ThresholdKeys::<C>::read
// that produce an internally inconsistent key object.
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());            // t = 1
buf.extend(2u16.to_le_bytes());            // n = 2
buf.extend(1u16.to_le_bytes());            // i = 1
buf.push(1);                               // Interpolation::Lagrange
buf.extend(C::F::ZERO.to_repr().as_ref()); // secret_share = 0 (attacker-chosen)
// verification_shares fully attacker-controlled: pick any two points
buf.extend((C::generator() * C::F::from(0xdead)).to_bytes().as_ref());
buf.extend((C::generator() * C::F::from(0xbeef)).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// Accepted despite secret_share * G != verification_shares[Participant(1)].
assert_ne!(
  C::generator() * C::F::ZERO,
  keys.original_verification_share(Participant::new(1).unwrap())
);
// keys.group_key() is whatever the attacker chose; any signature share
// produced from `keys` fails verification -> signing always aborts and
// funds sent to group_key() are unspendable.
```
