### Title
EncryptedMessage deserialization accepts the identity point as the ephemeral key, enabling PoP forgery and chosen-plaintext injection that frames an honest DKG participant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2018-8018 (missing allowlist/validation at deserialization), `EncryptedMessage::read` uses `Ciphersuite::read_G` — which enforces only canonical encoding, not non-identity — to read the per-message ephemeral key. FROST's `Curve::read_G` rejects identity, but PedPoP encryption operates on `C: Ciphersuite`, not `Curve`, so the identity point is accepted. Because the proof-of-possession is a Schnorr signature over that key, and the ECDH shared secret is `enc_key * msg.key`, an identity key collapses both: the PoP becomes trivially forgeable and the ChaCha20 key becomes publicly derivable.

### Finding Description
`EncryptedMessage::read` reads `key` via `C::read_G` (crypto/dkg/pedpop/src/encryption.rs:171-177). `Ciphersuite::read_G` checks canonicality but does not reject the identity point (crypto/ciphersuite/src/lib.rs:91-101). The stronger `Curve::read_G`, which rejects identity (crypto/frost/src/curve/mod.rs:125-131), is not used here.

Verification/decryption path:
- `pop.verify(msg.key, pop_challenge(...))` checks `sG == R + c*key` via `batch_statements` (crypto/schnorr/src/lib.rs:88-110). With `key = identity`, `c*key = 0`, so any `(R = sG, s)` satisfies the equation — a forged PoP for a key nobody knows the discrete log of.
- `ecdh(private, public) = public * private` (encryption.rs:95-97). With `msg.key = identity`, the shared point is `identity`, so `cipher()` derives a ChaCha20 key from publicly known bytes (encryption.rs:101-133). The attacker therefore fully controls the decrypted plaintext of `msg.msg`.

The `from` participant index used in `pop_challenge` and in share verification is supplied by the caller from the (unauthenticated) message metadata — the code itself notes "this still doesn't mean the DKG offers an authenticated channel" (encryption.rs:300-301). An attacker can therefore submit an `EncryptedMessage` with `key = identity`, forged PoP, attacker-chosen ciphertext, and claim `from = <victim Participant>`.

### Impact Explanation
In PedPoP, the decrypted share is verified against the sender's `Commitments`; a controlled plaintext will not match the victim's committed polynomial, so share verification fails and the victim is reported faulty — triggering the blame flow. In the blame flow the accuser reveals the decryption via `EncryptionKeyProof` and `decrypt_with_proof` re-verifies `proof.dleq` against `msg.key` (encryption.rs:381-392); with `msg.key = identity` the accuser "proves" decryption honestly (the DLEq is over `enc_pub_key * identity = identity`, which is true), so the blame lands on the honest victim. Result: an unprivileged party causes an honest DKG participant to be marked malicious/slashed, and can inject arbitrary plaintext into any message encrypted to any registered `enc_key`. This is a deserialization-validation flaw: untrusted bytes produce a group element the protocol implicitly assumed non-trivial.

### Likelihood Explanation
Any party able to submit a DKG `EncryptedMessage` byte stream to a participant (or to whatever layer calls `EncryptedMessage::read`/`decrypt`/`decrypt_with_proof`) can craft this: 32 bytes encoding the identity point, a Schnorr signature `(R = sG, s)` for arbitrary `s`, and arbitrary ciphertext. No discrete logs, collusion, or privileged position required.

### Recommendation
Reject the identity point when reading `EncryptedMessage.key` (and `EncryptionKeyMessage.enc_key`/`EncryptionKeyProof.key`): either use an identity-rejecting read equivalent to `Curve::read_G`, or add `if key.is_identity() { Err(..) }` after `C::read_G`. Defense-in-depth: also reject identity ECDH results in `ecdh()`.

### Proof of Concept
1. Victim participant V registers `enc_pub_key` via `EncryptionKeyMessage`.
2. Attacker serializes an `EncryptedMessage` for `from = V`'s `Participant` index:
   - `key` = 32-byte canonical encoding of `C::G::identity()` (passes `C::read_G`).
   - `pop` = `SchnorrSignature { R: C::generator() * s, s }` for any scalar `s`; `pop.verify(identity, c)` checks `sG == sG + c*identity` → true.
   - `msg` = arbitrary bytes XOR the keystream of `ChaCha20::new(key_from_transcript(identity_bytes), b"DKG IV v0.2\0")`, which the attacker computes locally.
3. V decrypts successfully (shared secret `enc_key * identity = identity`), obtains attacker-chosen share bytes, fails share verification against V's `Commitments`, and flags V faulty.
4. In the blame protocol, V's revealed `EncryptionKeyProof` verifies correctly (`dleq` over `enc_pub_key → identity` is genuine), so `decrypt_with_proof` confirms the (garbage) plaintext — V is blamed/slashed for a message V never sent.
