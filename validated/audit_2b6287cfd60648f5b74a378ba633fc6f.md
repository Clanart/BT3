### Title
mWOMSVBaseRewarder never applies expiry-based forfeiture, letting expired mWomSV lockers steal the full compliant-locker reward pool - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` hardcodes `rewardableAmount = _amount`, making `forfeitAmount` always `0` regardless of the caller's mWomSV lock/unlock state, even though `mWomSV.sol` already implements a working `getRewardablePercentWAD(_account)` that decays a user's rewardable share the longer their unlock slot sits past `endTime`. Because `_sendReward` never queries this function, any account whose mWomSV position is past its cooldown/expiry can call `getReward()`/`getRewards()` and receive 100% of its `earned()` balance instead of the reduced, decaying share that the protocol design (and the parallel `vlMGPBaseRewarder` implementation) intends.

### Finding Description
- In `vlMGPBaseRewarder._calExpireForfeit` (`rewards/vlMGPBaseRewarder.sol:386-400`), the contract calls `vlMGP.getRewardablePercentWAD(_account)` to scale `rewardableAmount`, and any shortfall is queued back into the pool via `_queueNewRewardsWithoutTransfer` as `forfeitAmount`.
- The analogous function in `rewards/mWOMSVBaseRewarder.sol:385-398` does not call `mWOMSV.getRewardablePercentWAD(_account)` at all:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
}
```
Since `rewardableAmount` is always set equal to `_amount`, `forfeitAmount` is unconditionally `0`.
- `mWomSV.sol:181-206` (`getRewardablePercentWAD`) demonstrates that the underlying locker contract *does* track and expose a decaying rewardable percentage for slots that are `block.timestamp > userUnlocking[i].endTime` (fully expired unlock slots), confirming the protocol's intended design of forfeiting rewards for accounts that let their unlock/cooldown lapse.
- `mWOMSVBaseRewarder._sendReward` (`rewards/mWOMSVBaseRewarder.sol:362-376`) trusts `_calExpireForfeit`'s output and transfers `toSend = userRewards[...] - forfeitAmount` via `IERC20(_rewardToken).safeTransfer(_receiver, toSend)`. With `forfeitAmount` always `0`, `toSend` always equals the user's full `earned()` balance.
- `getReward`/`getRewards` are reachable by any account through `onlyMasterMagpie`-gated calls originating from a user's own `claim`/`multiclaim` flow on `MasterMagpie`; no admin or privileged role is required — any unprivileged holder of mWomSV whose unlock slot has expired can trigger this path.
- No other modifier (`updateReward`, `nonReentrant`, `onlyMasterMagpie`) checks or restores the expiry-based reduction; they only gate reentrancy/caller identity, not the forfeiture computation itself.

### Impact Explanation
This results in a permanent, protocol-level shortfall: reward tokens meant to be redistributed to compliant lockers (those who kept mWomSV within lock/cooldown and did not let a slot fully expire) are instead fully paid out to accounts that should have forfeited a decaying percentage. This is a direct theft/misallocation of "unclaimed yield" belonging to the forfeiture pool, causing permanent value transfer from compliant lockers to accounts that let their positions expire — matching the Immunefi "theft of unclaimed yield" / "permanent freezing or loss of value for other users" impact class.

### Likelihood Explanation
The precondition is simply having a mWomSV unlock slot that has passed `endTime` (i.e., `block.timestamp > userUnlocking[i].endTime` in `mWomSV.sol:194`), which any regular staker can reach by not calling `unlock()` promptly. No special capital, flash loans, or privileged role is required — the attacker just calls `getReward`/the standard claim flow through `MasterMagpie` like any legitimate user. This is fully repeatable for every accrual cycle and applies to any account in this state, not just a deliberate attacker, making it a systemic, high-likelihood issue.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder`'s pattern: query `mWOMSV.getRewardablePercentWAD(_account)` (exposing it via the `ILocker` interface if not already present) and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`, so expired/decaying positions correctly forfeit a portion of rewards back into the pool via `_queueNewRewardsWithoutTransfer`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
