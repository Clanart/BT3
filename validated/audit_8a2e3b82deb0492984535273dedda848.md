### Title
Binary-wire `Timestamp`/`Duration` well-known-type fields accept out-of-range `seconds`/`nanos` with no validation at parse time, silently corrupting downstream time calculations - (File: `src/google/protobuf/util/time_util.h` / `src/google/protobuf/util/time_util.cc`)

### Summary
`google.protobuf.Timestamp` and `google.protobuf.Duration` are plain messages whose `.proto` definitions document strict semantic invariants (`seconds`/`nanos` ranges, and matching sign between `seconds` and `nanos`), but these invariants are **not enforced by the core binary parser**. `Timestamp.seconds`/`nanos` and `Duration.seconds`/`nanos` are ordinary `int64`/`int32` fields, so any attacker-controlled bounded binary payload can set them to arbitrary values (e.g. `INT64_MAX`, negative `nanos` on a positive `Timestamp`, or `nanos >= 1e9`). This mirrors the Sherlock finding: a wrapped/packed numeric type with an implicit semantic range (percentage ≤ 100%) is deserialized with no bounds check, and downstream code that assumes the invariant produces incorrect results. [1](#0-0) [2](#0-1) 

### Finding Description
`TimeUtil::IsTimestampValid` / `IsDurationValid` are the only guardians of the documented ranges, and they are **opt-in** helpers that application code must explicitly call — they are never invoked automatically by `ParseFromString`/`MergeFrom` when a message contains a `Timestamp` or `Duration` field. [3](#0-2) 

Once an out-of-range `Timestamp`/`Duration` has been parsed from the wire, protobuf's own conversion utilities assume the invariant holds. `CreateNormalizedTimestamp`/`CreateNormalizedDuration` guard the precondition only with `ABSL_DCHECK`, which compiles to a no-op in release (`NDEBUG`) builds — the exact same class of bug as the reported issue (“no range check” → silently wrong values flow into calculations): [4](#0-3) [5](#0-4) 

The JSON codecs do perform explicit range checks when *writing* a `Duration`/`Timestamp` to JSON (`WriteDuration` rejects `secs`/`nanos` out of range and mismatched signs), which confirms that the project treats these ranges as a real invariant that must be checked — but this check exists only on the JSON *emission* path, not on binary ingestion: [6](#0-5) 

By contrast, JSON *parsing* of `Timestamp` performs some bound checks (rejecting seconds below year 1) but does not fully validate against `kTimestampMaxSeconds`/nanos bounds in all backends, and the primary **binary** wire path (plain `int64`/`int32` field decode via `ArrayDecoders`/`MessageSchema`/`parse_context.h`/`upb`) performs no domain-specific validation at all for these fields — it is indistinguishable from decoding any other `int64`/`int32` field: [7](#0-6) [8](#0-7) 

### Impact Explanation
An ordinary client sending a bounded binary payload can set `Timestamp{seconds: INT64_MAX}`, `Timestamp{seconds: 0, nanos: -1}` (negative nanos, violates "nanos must be ≥0" for Timestamp), or `Duration{seconds: 1, nanos: -1}` (sign mismatch). These deserialize successfully with no error. Consuming application code that trusts the WKT invariant (as protobuf's own `TimeUtil::ToString`, `DurationToNanoseconds`, arithmetic helpers, and any downstream business logic computing expirations, fee schedules, rate limits, or TTLs from these fields do) will:
- Produce nonsensical/incorrect date-time or duration values (silent corruption of calculations), analogous to the reported "incorrect calculations, fees, or other critical parameters" impact.
- In debug/ASan builds trip `ABSL_DCHECK`/`ABSL_CHECK`, but in production (`NDEBUG`) builds these checks are compiled away, so the invalid data flows through unnoticed.

This is a logic/data-integrity issue, not memory corruption or RCE — consistent with a Medium-severity analog (bounded to consuming-application logic errors, not core-library memory safety).

### Likelihood Explanation
High likelihood of triggering: any client that can send an arbitrary `Timestamp`/`Duration` value in a binary or ProtoJSON payload can set out-of-range `seconds`/`nanos` trivially, since these are plain scalar fields with no field-level validation hook. No special tooling or schema tricks are required — a single crafted message field is sufficient. The gating factor for real-world impact is whether the *consuming application* actually relies on `TimeUtil`/`Timestamps`/`Durations` conversions or on the documented invariant without independently calling `IsValid`.

### Recommendation
- Add explicit `IsTimestampValid`/`IsDurationValid` (or `Timestamps.isValid`/`Durations.isValid` in Java, `_CheckTimestampValid`/`_CheckDurationValid` in Python) checks at the point where `Timestamp`/`Duration` fields are consumed by protobuf's own utility conversions (`ToString`, `DurationToNanoseconds`, `TimestampToNanoseconds`, etc.), returning an error/exception instead of relying on `ABSL_DCHECK`/no-op assertions in release builds.
- Consider promoting the `ABSL_DCHECK`s in `CreateNormalizedTimestamp`/`CreateNormalizedDuration` to `ABSL_CHECK` (fail closed) or have callers explicitly validate/clamp before use, since these functions are reachable from field values that originate directly from untrusted binary input.
- Document clearly (and enforce at the JSON parsing layer uniformly across C++/Java/Python/C#/upb) that binary-decoded `Timestamp`/`Duration` values are **not** validated against the documented ranges, so downstream consumers must call the `IsValid`/`isValid` helpers before performing arithmetic.

### Proof of Concept
Conceptual bounded-payload PoC (no privileged access required):
1. Construct a message containing a `google.protobuf.Duration duration = 1;` field.
2. Encode field 1 (`seconds`, varint) as `1`, field 2 (`nanos`, varint zigzag) as `-1` (sign mismatch: `seconds>0`, `nanos<0`), which is invalid per `duration.proto`'s documented sign-matching invariant.
3. Call `MyMessage::ParseFromString(bytes)` — parsing succeeds with no error.
4. Pass the resulting `Duration` to `TimeUtil::DurationToNanoseconds`/`CreateNormalizedDuration` in a release (`NDEBUG`) build — the `ABSL_DCHECK` guarding the precondition is compiled out, and the function proceeds with the invalid input, producing a computed nanosecond value that is inconsistent with the RFC-documented Duration semantics.

Note: I was not able to execute this against the actual build in this environment (no code-execution/terminal access here); the trace above is based on static reading of `time_util.cc`/`time_util.h`, `duration.proto`, `unparser.cc`, and the wire decoders (`ArrayDecoders.java`, `MessageSchema.java`, `parse_context.h`, `upb/wire/decode.c`), which collectively show the binary decode path performs no domain validation while `TimeUtil`'s precondition checks are debug-only. Reproducing this concretely (building the library and running the described encode/decode sequence) would require a Devin session with build/execution tooling.

  // The min/max Timestamp/Duration values we support.
  //
  // For "0001-01-01T00:00:00Z".
  static constexpr int64_t kTimestampMinSeconds = -62135596800LL;
  // For "9999-12-31T23:59:59.999999999Z".
  static constexpr int64_t kTimestampMaxSeconds = 253402300799LL;
  static constexpr int32_t kTimestampMinNanoseconds = 0;
  static constexpr int32_t kTimestampMaxNanoseconds = 999999999;
  static constexpr int64_t kDurationMinSeconds = -315576000000LL;
  static constexpr int64_t kDurationMaxSeconds = 315576000000LL;
  static constexpr int32_t kDurationMinNanoseconds = -999999999;
  static constexpr int32_t kDurationMaxNanoseconds = 999999999;

  static bool IsTimestampValid(const Timestamp& timestamp) {
    return timestamp.seconds() <= kTimestampMaxSeconds &&
           timestamp.seconds() >= kTimestampMinSeconds &&
           timestamp.nanos() <= kTimestampMaxNanoseconds &&
           timestamp.nanos() >= kTimestampMinNanoseconds;
  }

  static bool IsDurationValid(const Duration& duration) {
    return duration.seconds() <= kDurationMaxSeconds &&
           duration.seconds() >= kDurationMinSeconds &&
           duration.nanos() <= kDurationMaxNanoseconds &&
           duration.nanos() >= kDurationMinNanoseconds &&
           !(duration.seconds() >= 1 && duration.nanos() < 0) &&
           !(duration.seconds() <= -1 && duration.nanos() > 0);
  }

Duration CreateNormalizedDuration(int64_t seconds, int32_t nanos) {
  ABSL_DCHECK(seconds >= TimeUtil::kDurationMinSeconds &&
              seconds <= TimeUtil::kDurationMaxSeconds)
      << "Duration seconds are outside of the valid range";

  // Make sure nanos is in the range.
  if (nanos <= -kNanosPerSecond || nanos >= kNanosPerSecond) {
    seconds += nanos / kNanosPerSecond;
    nanos = nanos % kNanosPerSecond;
  }
  // nanos should have the same sign as seconds.
  if (seconds < 0 && nanos > 0) {
    seconds += 1;
    nanos -= kNanosPerSecond;
  } else if (seconds > 0 && nanos < 0) {
    seconds -= 1;
    nanos += kNanosPerSecond;
  }

  ABSL_DCHECK(seconds >= TimeUtil::kDurationMinSeconds &&
              seconds <= TimeUtil::kDurationMaxSeconds &&
              nanos >= TimeUtil::kDurationMinNanoseconds &&
              nanos <= TimeUtil::kDurationMaxNanoseconds)
      << "Duration is outside of the valid range";

template <typename Traits>
absl::Status WriteDuration(JsonWriter& writer, const Msg<Traits>& msg,
                           const Desc<Traits>& desc) {
  constexpr int64_t kMaxSeconds = int64_t{3652500} * 86400;
  constexpr int32_t kMaxNanos = 999999999;

  auto secs_field = Traits::MustHaveField(desc, 1);
  auto status_or_secs = Traits::GetSize(secs_field, msg) > 0
                            ? Traits::GetInt64(secs_field, msg)
                            : 0;
  RETURN_IF_ERROR(status_or_secs.status());
  int64_t secs = *status_or_secs;

  if (secs > kMaxSeconds || secs < -kMaxSeconds) {
    return absl::InvalidArgumentError("duration out of range");
  }

  auto nanos_field = Traits::MustHaveField(desc, 2);
  auto status_or_nanos = Traits::GetSize(nanos_field, msg) > 0
                             ? Traits::GetInt32(nanos_field, msg)
                             : 0;
  RETURN_IF_ERROR(status_or_nanos.status());
  int32_t nanos = *status_or_nanos;

  if (nanos > kMaxNanos || nanos < -kMaxNanos) {
    return absl::InvalidArgumentError("duration out of range");
  }
  if ((secs != 0) && (nanos != 0) && ((secs < 0) != (nanos < 0))) {
    return absl::InvalidArgumentError("nanos and seconds signs do not match");
