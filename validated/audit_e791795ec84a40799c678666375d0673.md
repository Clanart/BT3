### Title
Partial-commit/discard patches are built from stale line-selection indices applied to a freshly re-fetched diff, allowing silent staging of unintended content - ([File: app/src/lib/git/apply.ts])

### Summary
`slashAndStartAuction()` breaks because it derives an absolute slash amount from a percentage taken against `totalSupply()`, but applies that percentage against a *different* (already-changed) total at execution time — the "index" (percentage) and the "base" it's applied to become desynchronized. The same *class* of bug — a set of line-position indices computed against one version of a "document" being applied against a re-fetched, potentially different version of that document — exists in GitHub Desktop's partial-commit / partial-discard patch generation path.

### Finding Description
When a user partially stages or discards changes, Desktop records a `DiffSelection` as a set of *absolute line indices* into a specific `ITextDiff` snapshot (see `DiffSelection.withRangeSelection` / `isSelected` in [1](#0-0)  and the diff-to-selection wiring in `changeFileLineSelection`).

At apply time, `applyPatchToIndex` does **not** reuse the diff that the selection indices were computed against. Instead it independently re-fetches the working directory diff and formats a patch against that fresh diff using the old selection object: [2](#0-1) 

The comparable discard path, `discardChangesFromSelection`, is passed a `diff` argument by the caller and applies `selection.isSelected(absoluteIndex)` against it via `formatPatchToDiscardChanges`: [3](#0-2) [4](#0-3) 

Desktop *is* aware that diffs can go stale relative to a stored selection — there is an explicit reconciliation step run on background refresh that intersects the old selection against a newly computed `selectableLines` set: [5](#0-4) 

However, that reconciliation only runs as part of `_refreshRepository`/`refreshChangesSection` polling cycles. There is no equivalent "recompute diff, revalidate selection, and only then format/apply the patch" step performed atomically inside `applyPatchToIndex` or `discardChangesFromSelection` immediately before the patch is generated and handed to `git apply`. `formatPatch`/`formatPatchToDiscardChanges` blindly trust that `absoluteIndex` (a position in the *old* diff/selection) still identifies the same logical line in the diff object they were given — for `applyPatchToIndex` that object is a diff fetched fresh from disk at that exact moment, which can differ from what the selection was computed and displayed against if the working tree changed in the window between the last UI refresh and the user clicking "Commit" (e.g. content rewritten by an editor autosave, a build tool, a `smudge`/`clean` filter, or a repository-provided git hook such as `post-checkout`/`post-merge` that Desktop itself invokes as part of normal git operations run moments earlier).

### Impact Explanation
If the on-disk file changes between when the user reviewed/selected diff lines and when Desktop stages/commits, `git apply --cached` will apply the "selected" hunk positions against different underlying content. Because hunk headers are rewritten by `formatHunkHeader` from recomputed counts rather than validated against the actual current file state line-for-line, this can result in the wrong lines being staged, included, or excluded — i.e., silent corruption of what the user believes they are committing (unreviewed content silently included, or an intended fix silently dropped), without any error surfaced to the user. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Medium-low. This requires a narrow timing window (working tree mutated between the last diff render and the commit click) combined with a repository/tooling capable of touching the file at that moment (e.g., a git hook shipped in a malicious or compromised clone, an editor with autosave, or a background formatter/linter). It is not remotely triggerable and does not require the attacker to already have code execution on the host — only content control of a checked-out repository (hooks, filters) — but it is a race condition rather than a deterministically reproducible bug, similar in spirit to the report's "frontrunning/race condition" characterization.

### Recommendation
Make `applyPatchToIndex` consume the same diff snapshot the selection was validated against instead of re-fetching a new one at apply time, or re-validate `file.selection` against a freshly fetched diff's `selectableLines` (as already done in the background-refresh reconciliation path) immediately before formatting/applying the patch, aborting/re-prompting the user if the diff has materially changed since the selection was made.

### Proof of Concept
1. Modify a tracked file and open it in Desktop's Changes view; select only a subset of lines/hunks for commit (this fixes a `DiffSelection` with absolute indices against the currently displayed `ITextDiff`).
2. Before clicking "Commit", have another process (e.g., a script, editor autosave, or a repository-provided git hook triggered by a prior Desktop-run git command) rewrite the file so line offsets shift but the file still parses as a valid diff (e.g., insert/remove lines above the hunks Desktop is not currently re-rendering).
3. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) calls `getWorkingDirectoryDiff` fresh, then `formatPatch` (`app/src/lib/patch-formatter.ts:129`) applies the stale `file.selection.isSelected(absoluteIndex)` decisions against the new diff's line indices.
4. Inspect the resulting commit: the staged hunks/lines no longer correspond to what was visually selected in step 1, demonstrating silent corruption of the intended commit contents.

Note: full verification of the exact end-to-end call path from `_commitIncludedChanges`/`performCommit` in `app-store.ts` down to `applyPatchToIndex` (to confirm there is no last-moment re-validation call I might have missed) could not be completed within the available tool budget; this should be checked directly in the repository before treating the finding as fully confirmed.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
