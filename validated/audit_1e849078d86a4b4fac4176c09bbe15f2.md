### Title
Unbounded recursion during `AccountKeyRoleBased` RLP decoding allows stack-exhaustion DoS via nested composite keys - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key of a role-based account key via `rlp.DecodeBytes` before any nesting restriction is enforced. Because a sub-key can itself be another `AccountKeyRoleBased`, an attacker can submit an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction (or call the public `kaia_decodeAccountKey` RPC) with a deeply, recursively nested `AccountKeyRoleBased` blob. Decoding this blob invokes `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursively, with the nesting check (`ErrNestedCompositeType`) only applied afterward in `CheckInstallable`/`CheckUpdatable`. This mirrors the CVE-2018-9918 bug class: "nesting in direct objects is not restricted," leading to stack exhaustion.

### Finding Description
`AccountKeyRoleBased` is decoded as follows: [1](#0-0) 

For each byte-encoded sub-key `b`, it creates a new `AccountKeySerializer` and recursively calls `rlp.DecodeBytes(b, &serializer)`, whose `DecodeRLP` implementation is: [2](#0-1) 

This reads the `keyType` first, then dispatches via `NewAccountKey(serializer.keyType)`: [3](#0-2) 

Because `AccountKeyTypeRoleBased` is itself a valid `keyType`, `NewAccountKey` returns another `*AccountKeyRoleBased`, whose `DecodeRLP` is called again — creating unbounded recursion depth purely controlled by how deeply the attacker nests the RLP-encoded blob (`AccountKeyRoleBased{ AccountKeyRoleBased{ AccountKeyRoleBased{ ... } } }`).

Crucially, the *only* mechanism that rejects nested role-based keys, `ErrNestedCompositeType`, is enforced in `CheckInstallable`/`CheckUpdatable`, which run **after** the recursive RLP decode has already completed: [4](#0-3) 

So by the time nesting is checked and rejected, the decoder has already recursed to the full attacker-chosen depth, which is enough to exhaust the goroutine stack and crash the node process with an unrecoverable Go runtime `fatal error: stack overflow` (not a `panic` that can be `recover()`ed).

This code path is reachable from:
- Public RPC `kaia_decodeAccountKey`, which directly RLP-decodes attacker-supplied bytes with no size/depth guard: [5](#0-4) 
- Submission of an `AccountUpdate` transaction whose `Key` field is decoded the same way in `AccountUpdateTxArgs.toTransaction`: [6](#0-5) 
- The transaction pool's `AddRemote` path also decodes the full transaction (including the account key) via `Transaction.DecodeRLP` before any composite-nesting validation runs.

### Impact Explanation
A single unprivileged transaction sender or public-RPC caller can trigger unbounded recursive stack growth in the node process. This can cause the node's goroutine to hit Go's stack limit and crash the entire process (`fatal error: stack overflow` — not catchable via `recover`), resulting in denial of service. If exploited against many/most validator or RPC nodes simultaneously (e.g., broadcasting the same crafted transaction, or many RPC callers hitting the API), it can cause a network-wide availability disruption, satisfying the High-severity bar (stack-exhaustion DoS matching CVE-2018-9918's bug class).

### Likelihood Explanation
High likelihood of reachability: no authentication or special privileges are required. An attacker only needs to:
1. Construct a nested RLP blob (`AccountKeyRoleBased` wrapping itself many times), and
2. Either call the public `kaia_decodeAccountKey` RPC directly, or submit an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction with this blob as the account key (`tx.Validate`/`CheckInstallable` runs only after the crash-inducing decode).

The construction itself is trivial (RLP encoding is a well-documented byte format), requiring no cryptographic effort — only a valid transaction signature (or none at all for the RPC-only variant) is needed to reach the vulnerable decode path.

### Recommendation
Add an explicit recursion/nesting-depth check inside `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` *before* recursively decoding sub-keys — e.g., track and pass down a decode depth counter, or reject `keyType == AccountKeyTypeRoleBased` when decoding as a sub-key of an existing `AccountKeyRoleBased` (mirroring the existing `checkAccountKeyZeroValues`/`isNested` pattern already used for zero-value validation). This must occur at decode time, not only in the later `CheckInstallable`/`CheckUpdatable` validation, since the stack damage is done during decoding itself.

### Proof of Concept
1. Construct account key bytes recursively:
   - `leafBytes = RLP({AccountKeyTypePublic, <pubkey>})`
   - `wrap(bytes) = RLP({AccountKeyTypeRoleBased, RLP([bytes])})`
   - Apply `wrap` N times (N large, e.g., tens/hundreds of thousands) starting from `leafBytes` to produce `payload`.
2. Call the public JSON-RPC method `kaia_decodeAccountKey(payload)` (no auth required), or submit an `AccountUpdate` transaction with `Key = payload` via `eth_sendRawTransaction`/`kaia_sendRawTransaction`.
3. `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurses N times before `CheckInstallable`'s `ErrNestedCompositeType` check is ever reached, exhausting the goroutine stack and crashing the node with `fatal error: stack overflow`.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
