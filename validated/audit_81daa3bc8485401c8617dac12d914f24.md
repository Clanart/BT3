### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new`/`view` allows CPU DoS from untrusted key bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled participant count `n` (a `u16`, up to 65535) and then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for every participant `1..=t`. Under `Interpolation::Lagrange`, each `interpolation_factor` call loops over the full `included` set, making key construction `O(n²)` in scalar field operations from an input only `O(n)` bytes long. The same quadratic blowup occurs in `ThresholdKeys::view` when building `verification_shares`.

### Finding Description
- `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i` directly from the byte stream, then iterates `1 ..= n` reading verification shares. `n` is only bounded by `u16::MAX` and by `ThresholdParams::new` (t ≤ n).
- `ThresholdKeys::new` (crypto/dkg/src/lib.rs:376-378) computes `group_key = Σ verification_shares[i] * interpolation_factor(i, t)` for `i` in `1..=t`.
- `Interpolation::Lagrange`'s `interpolation_factor` (crypto/dkg/src/lib.rs:229-247) iterates over the entire `included` slice — `O(t)` field multiplications and one inversion per call.
- Result: constructing keys with `t = n = 65535` performs ~4.3 × 10⁹ field multiplications (plus inversion), i.e., quadratic CPU work for a ~2 MB serialized input. The input does not need to contain 65535·32 bytes of shares either — `read_exact` will fail partway, but the quadratic `new` cost is only reached after full parse; however callers like `view` re-run the same `O(|included|²)` interpolation on already-held keys whenever `included` is large.
- Additionally, `Interpolation::Constant` read path allocates `Vec::with_capacity(n)` and indexes `c[i - 1]` (line 228) trusting `c.len() == n`, which holds here but couples allocation size to attacker `n`.

### Impact Explanation
Any component that deserializes or constructs `ThresholdKeys`/`ThresholdView` from bytes supplied by an untrusted party (e.g., via `ThresholdKeys::read` on received key material, or DKG commitment verification paths that call `interpolation_factor` per share) can be stalled for a disproportionate amount of CPU time. A small serialized payload specifying maximal `t`/`n` forces `O(n²)` field arithmetic, blocking the signing/verification thread — a resource-exhaustion DoS analogous to iterating an unbounded array, except here a single short header drives quadratic work.

### Likelihood Explanation
Reachable wherever serialized `ThresholdKeys` or DKG artifacts cross a trust boundary (the prompt's `ThresholdKeys::read` reachability rule). `t`/`n` are u16 fields the attacker sets freely; the only limit is input length, which is linear while cost is quadratic. No privilege, collusion, or validator status is required — only the ability to feed bytes to the read/construct path. Severity is Medium: denial of service of the affected process, no key leakage or forgery.

### Recommendation
- Bound `t`/`n` to a protocol-realistic maximum (e.g., a few hundred) at the `ThresholdParams::new`/deserialization layer.
- Replace per-participant recomputation of Lagrange factors with the standard `O(n)` prefix/suffix product algorithm for denominators, plus a single batch inversion, reducing `ThresholdKeys::new`/`view` interpolation to `O(n)` group/scalar work.

### Proof of Concept

```rust
use std::io::Cursor;
use rand_core::OsRng;
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use dkg::{ThresholdKeys, Participant};

// Build serialized ThresholdKeys bytes with t = n = u16::MAX, Lagrange interpolation.
let mut bytes = vec![];
// C::ID for Ristretto
bytes.extend((Ristretto::ID.len() as u32).to_le_bytes());
bytes.extend(Ristretto::ID);
bytes.extend(u16::MAX.to_le_bytes()); // t
bytes.extend(u16::MAX.to_le_bytes()); // n
bytes.extend(1u16.to_le_bytes());     // i
bytes.push(1);                        // Interpolation::Lagrange
// secret share (canonical scalar encoding), then n verification shares
bytes.extend(Ristretto::F::ONE.to_repr());
for _ in 0 .. u16::MAX {
  bytes.extend(Ristretto::generator().to_bytes());
}
// ~2.1 MB of input triggers ~4.3e9 scalar multiplications inside
// ThresholdKeys::new via per-participant O(t) Lagrange interpolation_factor.
let _ = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(bytes));
```
