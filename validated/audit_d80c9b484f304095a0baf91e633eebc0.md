### Title
Relayer fees are zeroed before cross-chain settlement is confirmed, permanently losing funds when the zero-fee disbursement message is never relayed - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in `pallet-ismp-relayer` mirrors the `recoverToken` bug pattern: it treats an *accounting balance* as settled the instant it *dispatches* a cross-chain instruction to move funds, rather than when the funds actually move. The relayer's `Fees` entry is zeroed immediately after `dispatch_request` returns, but the actual payout only happens later when the dispatched ISMP POST is delivered to, and executed by, the destination chain's `HostManager`/token-gateway equivalent (via `EvmHost.withdraw`, [1](#0-0) ). If that delivery never completes, the relayer's balance is gone with no compensating credit-back path.

### Finding Description
`Pallet::withdraw` computes `available_amount` from `Fees::<T>::get(...)`, dispatches a POST request instructing the destination `HostManager` (or Hyperbridge module) to pay it out, and then **immediately zeroes the local accounting**: [2](#0-1) 

Two properties compound the risk:

1. **The internal dispatch pays a zero relayer fee**: `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` at [3](#0-2) . Hyperbridge's permissionless relayer network is explicitly fee-driven ("Relayers are profit-driven mediators and they will prioritize messages with fees that ensure profitability" - [4](#0-3) ). An unpaid message has no economic incentive to ever be delivered.
2. **No restoring/rollback path exists.** Unlike the generic ISMP dispatch flow, which explicitly refunds `leaf_meta.fee.payer` when a request times out ( [5](#0-4) ), that refund only fires when `leaf_meta.fee.fee > 0`. Since the relayer-withdrawal dispatch always sets `fee: Default::default()` (zero), the generic on-timeout refund path is a no-op even in the best case where a timeout is eventually processed. I found no `IsmpModule`/`on_timeout` implementation in `pallet-ismp-relayer` (`lib.rs`, `withdrawal.rs`) that re-credits `Fees` on failure.

This matches the reported bug class exactly: an accounting variable (`nextAuctionGoldAmount` there, `Fees` here) is decremented/zeroed at the moment funds are "moved," without gating on confirmation that the movement actually completed — so bookkeeping and real-world settlement diverge, and the party expecting to claim funds cannot.

### Impact Explanation
If the dispatched withdrawal POST is never relayed (no incentive, since it carries zero fee) or fails on the destination side (e.g., destination `EvmHost.withdraw` reverts with `WithdrawalFailed` due to insufficient balance, or the message times out on Substrate-to-Substrate legs), the relayer's `Fees[dest_chain][address]` entry is already `0`. There is no code path that restores it. The relayer permanently loses the accrued, legitimately earned fee balance for that destination — a direct loss-of-funds condition with no admin, governance, or malicious-actor precondition; it is triggered purely by the ordinary asynchronous nature of cross-chain delivery.

### Likelihood Explanation
This requires no adversarial relayer, prover, or governance action — only that the zero-fee internal disbursement message is not promptly delivered, which is plausible by design (self-relay-only economics, congestion, or a destination-side execution failure such as insufficient host balance). Any relayer calling `withdraw_fees` is exposed on every withdrawal, making this a systemic, easily-triggerable path rather than an edge case.

### Recommendation
Do not zero `Fees` optimistically at dispatch time. Either:
- Move the debit to an on-chain confirmation callback fired only when the destination side confirms disbursement (mirroring how `on_request_timeout` credits the `payer` back), or
- Keep an intermediate "pending withdrawal" state keyed by commitment, and only fully clear `Fees` once a delivery/ack is observed, restoring the balance if the request times out or fails; and
- Attach a non-zero relayer fee to the internal dispatch (or otherwise guarantee delivery, e.g., self-relay by the pallet) so the message is not left permanently unrelayed.

### Proof of Concept
1. Relayer accrues fees for `dest_chain = Evm(1)` via `accumulate_fees`, reaching `Fees::<T>::get(Evm(1), relayer) = X ≥ MinWithdrawal`.
2. Relayer submits `withdraw_fees` with a valid signature; `Pallet::withdraw` runs:
   - `available_amount = X`
   - Dispatches `DispatchPost` to `HostManager` on `Evm(1)` with `FeeMetadata { fee: 0 }` ( [3](#0-2) )
   - Immediately runs `Fees::<T>::insert(Evm(1), relayer, U256::zero())` ( [6](#0-5) )
3. Because the dispatched message carries zero relayer fee, no external relayer picks it up for delivery to `Evm(1)`; alternatively, assume delivery occurs but `EvmHost.withdraw` reverts with `WithdrawalFailed` because the host's actual token balance is insufficient ( [7](#0-6) ).
4. The relayer never receives the `X` tokens on `Evm(1)`, yet `Fees::<T>::get(Evm(1), relayer)` is permanently `0`. Calling `withdraw_fees` again fails `NotEnoughBalance` ( [8](#0-7) ) since the balance was already zeroed — the fee is unrecoverably lost.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

	fn on_request_timeout(&self, _req: &Request, meta: Vec<u8>) -> Result<(), Error> {
		let leaf_meta = RequestMetadata::<T>::decode(&mut &*meta)
			.map_err(|_| Error::Custom("Failed to decode leaf metadata".to_string()))?;
		if leaf_meta.fee.fee > Zero::zero() {
			T::Currency::transfer(
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				&leaf_meta.fee.payer,
				leaf_meta.fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| Error::Custom(format!("Failed to refund relayer fee: {err:?}")))?;
		}
		Ok(())
	}
