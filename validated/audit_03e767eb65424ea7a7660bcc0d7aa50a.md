### Title
SignableTransaction trusts unauthenticated ReceivedOutput values, producing signatures over false prevout amounts and fictitious change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` derives `input_sat`, the `NotEnoughFunds` check, and the change-output amount entirely from `ReceivedOutput::output.value` — a field that is freely attacker-controlled when the `ReceivedOutput` is reconstructed through `ReceivedOutput::read`. Neither `SignableTransaction::new` nor `multisig` verifies that the claimed value/script corresponds to a real on-chain UTXO; `multisig` checks only that `prevouts[i].script_pubkey` equals the expected offset key's P2TR script. The crafted `TxOut` values are then committed into every input's sighash via `Prevouts::All(&self.tx.prevouts)` in `TransactionSignMachine::sign`. The analog of "swap without a minimum-amount check" is "sign without checking the committed values": the threshold group signs a sighash asserting prevout amounts the attacker fabricated. ### Finding Description
`ReceivedOutput::read` consensus-decodes an arbitrary `TxOut` (any `value: u64`, any `script_pubkey`) and `OutPoint` from untrusted bytes, with no authenticity check. `SignableTransaction::new` consumes these values unchecked:

- `input_sat` is `sum(inputs[].output.value)` — fully attacker-controlled.
- `input_sat < payment_sat + needed_fee` is the only gate on spending; an inflated `value` satisfies it regardless of the real UTXO's worth.
- The change branch `input_sat.checked_sub(payment_sat + fee_with_change)` then mints a change `TxOut` crediting the multisig's own change script with fictitious sats.
- `multisig` validates only the prevout *script* (`p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`), never the value or that the outpoint is a confirmed UTXO.
- `sign` hashes `Prevouts::All(&self.tx.prevouts)` — the forged `TxOut`s — into `taproot_key_spend_signature_hash`, so every honest FROST participant produces a valid share over a message asserting false input amounts.

Like the referenced swap functions, the code performs value-critical arithmetic and commits to a result with no minimum/consistency check against the real value. [5](#0-4) [6](#0-5) 

### Impact Explanation
Two concrete losses follow:

1. **Fictitious change / funds reported received that are not spendable.** With a forged `value`, the change branch emits a change output for sats that were never locked to the multisig; `fee()` and downstream accounting then treat `sum(inputs) - sum(outputs)` as real. The signed transaction can never be mined (Bitcoin consensus requires sighash-committed prevout amounts to match the actual UTXOs), so the reported balance is unspendable while bookkeeping treats it as received.
2. **Signing an unintended message.** Each honest participant's share signs a `TapSighash` binding the attacker's fabricated prevout vector — a message the threshold group never intended to attest to — wasting a FROST signing session and stalling the wallet (every retry built on the same forged inputs is unbroadcastable).

This is reachable by any party able to feed serialized bytes to `ReceivedOutput::read` (peer-supplied output data / integrator-supplied inputs), per the in-scope reachability rules.

### Likelihood Explanation
Any unprivileged party who can supply or corrupt `ReceivedOutput` encodings (network-provided output data, malicious coordinator inputs, tampered serialized state) controls `TxOut.value` directly, since consensus decoding performs no sanity bound. No key material, collusion, or validator power is needed — only a `value` field larger than the real UTXO. The forged path is the default: there is no secondary validation anywhere between `read` and `sign`. Exploitation requires no on-chain setup beyond knowing an outpoint/script the multisig controls.

### Recommendation
- Treat `ReceivedOutput` as unauthenticated: verify each input's `(outpoint, script_pubkey, value)` against the chain (or an SPV/confirmed-output proof) before constructing a `SignableTransaction`, or have `multisig`/`sign` reject prevouts not previously produced by the `Scanner`.
- In `SignableTransaction::new`, use `checked_add`/`checked_sub` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `fee_per_vbyte * vbytes`, returning `NotEnoughFunds`/`TooLowFee` on overflow.
- Document and enforce (e.g., `fee()` returning `checked_sub`) that `sum(prevouts) >= sum(outputs)` rather than relying on unchecked `u64` subtraction.

### Proof of Concept
1. Attacker observes a real multisig P2TR UTXO `O` (outpoint `P`, script `S`, real value `v`).
2. Attacker serializes `ReceivedOutput { offset: <matching offset scalar>, output: TxOut { value: 21_000_000_0000_0000, script_pubkey: S }, outpoint: P }` — `ReceivedOutput::read` accepts it (lines 122–134, mod.rs).
3. Victim calls `SignableTransaction::new(vec![forged], &[(dest, dust_ok)], Some(change_script), None, fee_rate)`:
   - `input_sat` = fabricated value → `NotEnoughFunds` bypassed (lines 175, 215).
   - Change branch pushes `TxOut { value: input_sat - payment - fee_with_change, change_script }` — a massive fictitious change output (lines 224–234).
4. `multisig(&keys)` succeeds because `p2tr_script_buf(offset.group_key()) == S` (lines 273–281).
5. `preprocess`/`sign` produce valid FROST shares over `taproot_key_spend_signature_hash(.., Prevouts::All(&[TxOut{ value: forged, .. }]), ..)` (lines 373–390).
6. `complete` emits a fully signed transaction that any Bitcoin node rejects (committed prevout amount ≠ real `v`): the multisig's signature attested false data, the recorded change is unspendable, and the plan stalls — reachable entirely from attacker-chosen bytes.
