## Analog Found

### Title
CR-CAT (and R-CAT) wallet deduplication is keyed only by tail hash, silently merging distinct assets that differ in `authorized_providers`/`proofs_checker` (or `hidden_puzzle_hash`) - (File: `chia/wallet/vc_wallet/cr_cat_wallet.py`)

### Summary
`CRCATWallet.get_or_create_wallet_for_cat` decides whether a CR-CAT wallet "already exists" by comparing only `get_asset_id()` (the CAT tail/limitations-program hash) against the requested `limitations_program_hash`. It never compares the accompanying `authorized_providers` list or `proofs_checker`, even though these are curried into the on-chain puzzle and are just as much a part of the asset's true identity as the tail hash. `RCATWallet.get_or_create_wallet_for_cat` has the identical pattern, ignoring `hidden_puzzle_hash`.

### Finding Description
For CR-CATs, an asset's full on-chain identity is `(tail_hash, authorized_providers, proofs_checker)` — these three values are curried into `construct_cr_layer`/`construct_puzzle` and directly determine the coin's puzzle hash: [1](#0-0) 

However, the wallet's "does this wallet already exist" uniqueness check only compares the tail hash: [2](#0-1) 

`get_asset_id()` for a CR-CAT wallet returns just the tail hash, discarding the provider/proof-checker component of identity: [3](#0-2) 

This function is reached during normal coin-sync processing whenever a wallet receives a CR-CAT for a tail already in its `default_cats` list (i.e., simply by being sent a payment), via `CATWallet.identify`, which passes the actual on-chain `crcat.authorized_providers`/`proofs_checker` extracted from the incoming coin spend: [4](#0-3) 

If the receiving wallet already has a CR-CAT wallet for that tail hash (created for a legitimate CR-CAT with one set of `authorized_providers`/`proofs_checker`), any counterparty can send a *different* CR-CAT sharing the same tail hash but curried with different `authorized_providers`/`proofs_checker`. Because the "already exists" check ignores these fields, the new, semantically distinct coin is silently folded into the pre-existing wallet instead of causing wallet creation to fail or a new wallet to be created — mirroring the reported class of bug where an incomplete composite key (`(token, strike)` instead of `(token, strike, collateral)`) causes distinct entities to collide.

This is the exact analog of the reported issue: the Y2K `getMarketId` used `(token, strike)` when the true identity was `(token, strike, collateral)`, blocking/mismatching creation of a second, legitimately distinct market. Here, `get_or_create_wallet_for_cat` uses `tail_hash` alone when the true identity is `(tail_hash, authorized_providers, proofs_checker)`, causing a legitimately distinct CR-CAT asset to be merged into (mis-tracked by) the wrong wallet.

### Impact Explanation
Once merged, the wallet's `CRCATInfo` (`self.info.authorized_providers`/`proofs_checker`) no longer matches the actual on-chain puzzle governing the newly received coin. Subsequent operations that reconstruct the coin's puzzle for spending (`construct_puzzle`/`construct_cr_layer`, `match_hinted_coin`) use the wallet's stored (stale/incorrect) `authorized_providers`/`proofs_checker` rather than the coin's real ones: [5](#0-4) 

This produces a puzzle-reveal/puzzle-hash mismatch when the wallet later attempts to spend that coin, causing spend construction/validation to fail for that coin (a spend-triggered halt on that asset's transaction processing) and corrupting the wallet's view of which VC-authorized-provider set actually governs its held CR-CAT balance.

### Likelihood Explanation
Reachable by any unprivileged counterparty: sending a wallet a CR-CAT coin using a tail hash the recipient already tracks (e.g. a widely known CR-CAT tail) but with attacker-chosen `authorized_providers`/`proofs_checker` is a normal wallet-receive action requiring no special privilege, only that `automatically_add_unknown_cats` is enabled or the tail is in the recipient's `default_cats`.

### Recommendation
Include `authorized_providers` and `proofs_checker` (and, for `RCATWallet`, `hidden_puzzle_hash`) in the uniqueness comparison in `get_or_create_wallet_for_cat`, e.g. compare `(w.get_asset_id(), w.info.authorized_providers, w.info.proofs_checker)` rather than `get_asset_id()` alone, and create a distinct wallet (or reject/flag the mismatch) when only the tail hash matches.

### Proof of Concept
1. Wallet A already runs a `CRCATWallet` for tail `T` with `authorized_providers = [P1]`, `proofs_checker = C1`.
2. An attacker creates and sends Wallet A a CR-CAT coin with the same tail `T` but `authorized_providers = [P2]`, `proofs_checker = C2`.
3. During sync, `CATWallet.identify` calls `CRCATWallet.get_or_create_wallet_for_cat(..., limitations_program_hash=T, authorized_providers=[P2], proofs_checker=C2)`.
4. The existing-wallet loop at `cr_cat_wallet.py:116-121` matches purely on `get_asset_id() == T` and returns the original wallet (tracking `[P1]`/`C1`), silently discarding the fact that the new coin is governed by `[P2]`/`C2`.
5. The coin is recorded under the wrong wallet; a later spend attempt reconstructs the puzzle using `[P1]`/`C1`, producing a puzzle hash that does not match the coin, causing the spend to fail.

def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)
