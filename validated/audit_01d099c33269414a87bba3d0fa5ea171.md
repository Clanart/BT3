### Title
`ReceivedOutput::read` deserializes an attacker-controlled scalar offset with no binding to the output's `script_pubkey`, reporting funds that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts untrusted bytes consisting of `(offset: Scalar, output: TxOut, outpoint: OutPoint)` and returns a `ReceivedOutput` without verifying that `offset` actually derives the Taproot script pubkey contained in `output`. The only correct producer of this pairing is `Scanner::scan_transaction`, which populates `offset` from `self.scripts.get(&output.script_pubkey)` — i.e., an offset registered against the key in `Scanner::new`/`register_offset`. By deserializing an unvalidated offset, an unprivileged party who can feed bytes into `ReceivedOutput::read` can cause an output to be recorded as received under a spend offset that does not match the output's locking script.

### Finding Description
The offset/spendability relationship is established only inside `Scanner`:

- `Scanner::register_offset` inserts `script -> offset` pairs where `script = p2tr_script_buf(self.key + GENERATOR * offset)` (`networks/bitcoin/src/wallet/mod.rs:180-196`).
- `Scanner::scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` is found in that map, copying the mapped offset (`networks/bitcoin/src/wallet/mod.rs:199-214`).

`ReceivedOutput::read` bypasses this invariant entirely: it reads `Secp256k1::read_F(r)` for the offset and then consensus-decodes an arbitrary `TxOut` and `OutPoint`, with no check that `p2tr_script_buf(key + G*offset) == output.script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:122-134`). The struct's fields are private and `serialize`/`read` are a public round-trip pair, so any consumer treating deserialized `ReceivedOutput`s as spendable (e.g., feeding them into `SignableTransaction`/`TransactionSignMachine` in `networks/bitcoin/src/wallet/send.rs`, which offsets keys per input via `output.offset()`) will attempt to spend an input whose tweaked key does not equal the key locked in the script pubkey.

### Impact Explanation
Funds are reported received that are not spendable. A `ReceivedOutput` with a mismatched `offset` yields a spending key `key + G*offset` that does not correspond to the output's `script_pubkey`. Any transaction built to consume it will fail script verification on Bitcoin, while downstream accounting that trusts `ReceivedOutput::value()` and `outpoint()` credits the amount. If the attacker substitutes a script pubkey they control with an offset matching the wallet's derivation, the same deserialization asymmetry can also misattribute provenance of outputs.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary (peer messages, coordinator-supplied data, restored state influenced by an untrusted party). Exploitation requires only writing attacker-chosen bytes to the reader; no collusion or cryptographic break is needed. Severity is bounded by how the consumer uses the output — at minimum it enables false crediting and construction of permanently failing spends (medium).

### Recommendation
Bind the deserialized offset to the output. Either:
- Make `ReceivedOutput::read` private to `Scanner`-produced data, or
- Pass the base key into a validating constructor that recomputes `p2tr_script_buf(key + GENERATOR * offset)` and rejects outputs whose `script_pubkey` does not match, mirroring the check in `scan_transaction`.

### Proof of Concept
Conceptual: write `offset = 1`, a `TxOut` paying to a Taproot script `p2tr_script_buf(victim_key + 2*G)` (or any attacker-chosen script), and a valid `OutPoint` into a buffer; `ReceivedOutput::read` accepts it and reports `value()` as received. Any spend attempt applies offset `1`, producing a signature for `victim_key + G`, which cannot unlock a script keyed by `victim_key + 2*G` — the output is reported but unspendable.
