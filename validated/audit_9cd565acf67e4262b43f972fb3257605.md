### Title
`Decryption::decrypt_with_proof` panics indexing `enc_keys` for an unregistered recipient, crashing on a malicious blame accusation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG blame path performs an unchecked `HashMap` index on an attacker-controlled `Participant` index. `BlameMachine::blame` / `AdditionalBlameMachine::blame` forward a caller-supplied `recipient` (and `sender`) into `decrypt_with_proof`, which evaluates `self.enc_keys[&decryptor]` unconditionally. Since `Participant` is only validated as non-zero, any index that was never registered in `enc_keys` (e.g., `n + 1`, or any participant whose `EncryptionKeyMessage` was not registered) causes a `HashMap` index panic — aborting the host process while it is handling an unauthenticated-accusation flow. This is the same bug class as the referenced advisory: an unchecked assumption on the type/validity of externally influenced input produces a panic during processing.

### Finding Description
- `Decryption::decrypt_with_proof` verifies the message PoP, then — when a `proof` is provided — constructs the DLEq verification arguments as `&[self.enc_keys[&decryptor], *proof.key]`. The indexing `self.enc_keys[&decryptor]` is evaluated before and regardless of the DLEq verification result, and panics if `decryptor` is absent from the map (`crypto/dkg/pedpop/src/encryption.rs`, in `decrypt_with_proof`).
- `enc_keys` is only populated by `register`, which is called once per participant `1..=n` in `AdditionalBlameMachine::new` and per round-1 participant in `verify_r1` (`crypto/dkg/pedpop/src/lib.rs`, `register` in `encryption.rs`, and `AdditionalBlameMachine::new` lines 649–662). There is no binding of the `recipient` argument in `blame` to the registered set.
- `blame_internal` takes `recipient: Participant` straight from the `blame` API (`crypto/dkg/pedpop/src/lib.rs` lines 575–609, 623–632, 674–682). `Participant` construction only enforces non-zero (`Participant::new(i).unwrap()` is used for `1..=n`), so an accuser can name `recipient = n + 1` or any participant whose encryption key was never registered.
- The panic is reached after only `msg.pop.verify(...)` succeeds — and the accuser can trivially produce a message with a valid PoP (they control `msg`, a `EncryptedMessage<C, SecretShare>` read via the in-scope `EncryptedMessage::read`, and can sign a PoP for their own key). Only `Some(proof)` needs to be passed; proof validity is irrelevant because the index expression is evaluated while building the verify arguments.

### Impact Explanation
An unprivileged party participating in (or interacting with) the blame phase causes an unconditional panic in the local process. The blame/accusation handling is the DoS-relevant surface: a processor/coordinator evaluating accusations crashes instead of returning a blame verdict, denying service to the DKG/blame resolution and — depending on host crash handling — the whole node. This mirrors the original advisory's impact (denial of service via panic on unexpected input); availability impact, no confidentiality/integrity compromise.

### Likelihood Explanation
Medium. Reaching the panic requires only calling `blame`/`AdditionalBlameMachine::blame` with (a) an unregistered `recipient` `Participant` index and (b) an `EncryptedMessage` whose PoP verifies, which the attacker fully controls. In deployments where blame accusations originate from peer messages (e.g., the processor's key-gen blame handling), the sender/recipient pair is derived from untrusted protocol data. The only mitigating factor is whether the host validates participant indexes before calling `blame`; the library itself performs no such check.

### Recommendation
In `Decryption::decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with a checked lookup (e.g., `self.enc_keys.get(&decryptor).ok_or(DecryptionError::...)` or a dedicated `UnknownParticipant` error). Similarly bound-check `sender`/`recipient` in `BlameMachine::blame_internal` against `self.commitments`/registered keys before indexing, returning the accuser/appropriate party as faulty rather than panicking.

### Proof of Concept
```rust
// AdditionalBlameMachine::new registers enc_keys for participants 1..=n.
let machine = AdditionalBlameMachine::<Secp256k1>::new(context, n, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a valid Schnorr PoP under their own key,
// and an arbitrary EncryptionKeyProof (contents never verified before the panic).
let msg: EncryptedMessage<Secp256k1, SecretShare<_>> =
    EncryptedMessage::read(&mut attacker_bytes.as_ref(), params).unwrap();

// Recipient index n+1 was never registered in enc_keys.
let recipient = Participant::new(n + 1).unwrap();
machine.blame(sender, recipient, msg, Some(attacker_proof));
// thread '...' panicked: index into HashMap on missing key in
// decrypt_with_proof -> self.enc_keys[&decryptor]
```

Note: I verified the panic site and the registration sites in `crypto/dkg/pedpop`; I did not fully trace the exact call path from `processor/src/key_gen.rs` blame wiring to confirm attacker-supplied recipient indexes flow unvalidated into `blame`. If the processor bounds recipient to `1..=n` before calling, the panic remains reachable only through direct library misuse, which would downgrade this to no-vulnerability under the strict acceptance rules.
