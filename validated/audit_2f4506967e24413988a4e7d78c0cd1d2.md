## Title
Relayer fee accounting is zeroed unconditionally at dispatch time, permanently losing rewards if destination-side disbursement fails - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
This is the direct structural analog of the GMX bug: liquidation updates internal accounting without an actual token transfer, while the user-initiated action that *would* need the transfer to succeed can revert and block recovery. In Hyperbridge's relayer-fee withdrawal flow, `Pallet::withdraw` zeroes the relayer's `Fees` balance on Hyperbridge as soon as the ISMP dispatch is *enqueued* — not after the destination-chain payout is confirmed to have executed successfully.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` builds a `WithdrawalParams`/`WithdrawalRequest` body and calls `dispatcher.dispatch_request(...)`, which only queues an ISMP POST request with `timeout: 0` (never times out) [1](#0-0) . Immediately after this dispatch succeeds, the pallet unconditionally zeroes the relayer's balance: [2](#0-1) 

This accounting update happens before any confirmation that the destination chain actually disbursed the funds. On the EVM side, the payout is executed later, asynchronously, when a relayer delivers the message and `HostManager.onAccept` is invoked, which calls `IHostManager(_params.host).withdraw(withdrawParams)` to transfer the fee token to the beneficiary [3](#0-2) . If that destination-side token transfer reverts (e.g., the configured `feeToken` — typically DAI or another ERC-20 — is paused, blacklists the beneficiary, or the `HostManager`/`EvmHost` contract balance can't cover it), the `onAccept` execution fails. Because the request was dispatched with `timeout: 0`, it can never expire and be refunded/retried through a timeout path [4](#0-3) .

This exactly mirrors the GMX report's core broken invariant: an accounting mutation (liquidation bookkeeping / here, `Fees::insert(..., zero)`) is treated as final and irreversible, while the actual value-transfer leg (position-closing transfer / here, the destination ERC-20 payout) is the one that can fail — and no mechanism exists to reconcile the two once they diverge.

### Impact Explanation
A relayer's accumulated, legitimately earned fees can be permanently and irrecoverably lost with no path to reclaim them, once the withdrawal is dispatched and the destination transfer fails. This is a direct "loss of funds" impact under the bounty's live-scope categories (funds must move exactly once and only to the rightful beneficiary — here they move zero times, yet the source-chain balance is wiped as if they had moved). Unlike the discarded categories (malicious relayer/prover, generic DoS), this does not require any malicious actor — it is a pure protocol logic flaw in the sequencing of accounting-vs-transfer that an honest relayer can be victimized by.

### Likelihood Explanation
This requires the destination-chain fee token to be paused/blocklisted/insufficient at the exact time of delivery, or another revert condition in the destination-side transfer path. That is a real, foreseeable operational scenario for common fee tokens (DAI has no blacklist, but other configurable `feeToken` values via governance-settable `HostParams` could) — and once triggered, the `timeout: 0` design guarantees no automatic recovery, unlike normal ISMP requests which use timeouts for exactly this kind of failure handling.

### Recommendation
Do not zero `Fees` at dispatch time. Instead:
- Zero (or reduce) the balance only upon confirmed successful execution of the destination-side disbursement (e.g., via an ISMP response/callback acknowledging success), or
- Set a non-zero timeout on the withdrawal `DispatchPost` so that a failed/undelivered disbursement times out and the relayer's `Fees` balance is restored/refunded through the existing ISMP timeout-handling path, mirroring how `IntentGatewayV2`'s escrow refund flow ties fund release strictly to on-chain proof of destination state [5](#0-4) .

### Proof of Concept
1. Governance sets `HostParams.feeToken` on a destination EVM chain to a token contract that can later be paused/frozen (or the token issuer blacklists the `HostManager`/beneficiary address).
2. A relayer accumulates fees on Hyperbridge via `pallet_ismp_relayer::accumulate` and then calls `Pallet::withdraw` targeting that destination chain.
3. `withdraw` dispatches the `WithdrawalParams` POST request with `timeout: 0` and immediately sets `Fees::<T>::insert(dest_chain, relayer, U256::zero())` [6](#0-5) .
4. The fee token becomes paused/frozen before the message is delivered (or before `HostManager.withdraw` succeeds).
5. When a relayer later submits the message, `HostManager.onAccept` → `IHostManager.withdraw` reverts on the token transfer.
6. Since the request has `timeout: 0`, it never times out and there is no other code path that restores the relayer's `Fees` balance — the relayer's reward is permanently lost, confirmed by no subsequent write to `Fees::<T>` for that relayer/chain pair anywhere else in the withdrawal/accumulate modules.
