### Title
Untrusted `n` length in `ThresholdKeys::read` causes speculative multi-megabyte allocation before a single payload byte is validated - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` in `crypto/dkg` mirrors the Pillow JPEG2000 bug class: a size derived from attacker-controlled input is used to size a heap allocation before the bytes that would justify it are actually read. When the serialized interpolation tag is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` where `n` is an attacker-supplied `u16` read only a few bytes earlier [1](#0-0) . The vector is allocated immediately at full capacity, yet the `n` field elements are only read afterwards — and may not exist in the input at all. A ~10-byte crafted input therefore forces an allocation of up to `65535 × size_of::<C::F>()` (~2 MB per call, more for larger fields), an amplification factor of roughly 200,000x.

### Finding Description

The deserialization flow in `ThresholdKeys::read` is:

1. Read and compare the curve ID header [2](#0-1) .
2. Read `t`, `n`, `i` — all attacker-controlled `u16`s, with no bounds check applied to `n` before it is used [3](#0-2) .
3. If the interpolation byte is `0`, call `Vec::with_capacity(usize::from(n))`, reserving `n` slots of `C::F` up front, then read `n` scalars with `C::read_F` [4](#0-3) .
4. Only later does `ThresholdParams::new(t, n, i)` validate `n` against `t`/`i` [5](#0-4) .

This is the same root cause as the Pillow advisory: a width/count accumulated or trusted from untrusted input is promoted into a buffer-size decision (`with_capacity` here, `realloc` there) that is divorced from the data actually present. `ThresholdKeys::read` is an explicitly in-scope deserialization entry point reachable with untrusted bytes. Note the contrast with safe patterns elsewhere in the codebase — `ethereum::Call::read` explicitly chunks reads in 1 KB pieces to avoid exactly this "claim 4 GB, deliver 4 bytes" amplification [6](#0-5) , while `SchnorrAggregate::read` pushes incrementally so memory tracks real input [7](#0-6) .

### Impact Explanation

Each invocation can be induced to allocate ~2 MB of heap (65535 × 32-byte scalars; larger for wider fields) from a payload of under a dozen bytes, since the capacity reservation happens before any `read_F` call can fail. Repeated calls — e.g., submitting many malformed `ThresholdKeys` blobs — multiply this per-call amplification, producing disproportionate transient memory pressure and allocator churn. The supported impact is denial of service through memory exhaustion, not memory corruption; the allocation is freed on the subsequent read error. Severity is Medium: the per-call amplification is large but capped at `u16::MAX` elements, and exploitation requires a reachable path that feeds attacker bytes into `ThresholdKeys::read`.

### Likelihood Explanation

Reachability exists wherever the stack deserializes `ThresholdKeys` from untrusted input (the rule set explicitly lists `ThresholdKeys::read` as an attacker-reachable entry point). Triggering is trivial: emit a valid curve ID header, two arbitrary `u16`s with `n` large, an interpolation byte of `0`, and then truncate — the oversized reservation is already committed before the first `read_F` fails. No cryptographic validity is needed.

### Recommendation

Do not pre-reserve capacity from the untrusted `n`. Either grow the vector incrementally via `Vec::new()` + `push` (so memory tracks bytes actually consumed, as in `SchnorrAggregate::read`), or validate `n` against `t`/participant bounds via `ThresholdParams::new` *before* allocating. A chunked-read strategy like `ethereum::Call::read` would also bound the worst-case amplification to a small constant.

### Proof of Concept

```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use frost::curve::Ristretto; // or any in-scope Ciphersuite

// Crafted blob: valid curve ID header, t=1, n=0xFFFF, i=1, interpolation=Constant(0),
// then truncated — no scalar bytes follow.
fn blob() -> Vec<u8> {
    let mut b = vec![];
    b.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
    b.extend(Ristretto::ID);
    b.extend(&1u16.to_le_bytes());        // t
    b.extend(&u16::MAX.to_le_bytes());    // n = 65535
    b.extend(&1u16.to_le_bytes());        // i
    b.push(0);                            // Interpolation::Constant
    b                                     // ~30 bytes total
}

// Each call reserves ~65535 * size_of::<Ristretto::F>() (~2 MB) before read_F fails.
// Looping this call produces ~200,000x memory amplification per byte sent.
for _ in 0 .. 1_000_000 {
    let mut slice = blob().as_slice();
    let _ = ThresholdKeys::<Ristretto>::read(&mut slice); // errors, but already allocated
}
```

The allocation occurs at `crypto/dkg/src/lib.rs:608` (`Vec::with_capacity(usize::from(n))`) — committed before the `for _ in 0 .. n { C::read_F(reader)? }` loop can observe the truncated input.

**Caveat:** I verified this path in `crypto/dkg/src/lib.rs` but could not fully confirm every upstream call site that feeds attacker-controlled bytes into `ThresholdKeys::read` within the remaining search budget; reachability is asserted based on the read function being an explicitly allowed untrusted-input target, not on a traced end-to-end network path.
