### Title
External senders can "clobber" internally-reserved output types (Branch/Change/Forwarded), causing deposits to be misclassified as protocol-internal outputs - (File: `networks/bitcoin/src/wallet/mod.rs`, `processor/src/networks/bitcoin.rs`)

### Summary
DOM clobbering works by injecting attacker-controlled content whose name collides with a trusted internal name, causing internal lookups to resolve to attacker-supplied entries. The analog here: Serai's Bitcoin `Scanner` classifies outputs purely by `script_pubkey` match against a fixed namespace of offset-derived scripts (External, Branch, Change, Forwarded). Those script paths are publicly derivable, so an unprivileged sender can craft a transaction paying to an internally-reserved name (e.g., the Change or Forwarded address). The scanner resolves the output as an internal `OutputType` rather than an External deposit — the attacker's input shadows a reserved namespace entry, just as a DOM-clobbering element shadows a built-in.

### Finding Description
`Scanner` maps `ScriptBuf -> Scalar` in `self.scripts` (`networks/bitcoin/src/wallet/mod.rs:153-196`) and `scan_transaction` reports any output whose `script_pubkey` is in that map (lines 205-211), with no check of who created the output.

The processor builds the full scanner with four deterministic offsets in `processor/src/networks/bitcoin.rs:308-346`: External (offset 0), Branch, Change, and Forwarded, where the last three are `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch"|b"change"|b"forward")`. Since the group key is public and the offset derivation is a public constant, anyone can compute `p2tr_script_buf(key + G*offset)` for each reserved path.

In `get_outputs` (`processor/src/networks/bitcoin.rs:686-699`), each scanned output's `kind` is looked up via `kinds[offset_repr_ref]`, and only `OutputType::External` outputs receive the depositor's `data` payload (lines 731-735). An attacker (or ordinary user) who sends funds to the Change/Branch/Forwarded script produces an on-chain output that is reported by the processor as a protocol-internal output type, not as a crediting deposit.

### Impact Explanation
The reserved-namespace collision means attacker-created UTXOs enter the processor's output stream labeled `OutputType::Branch`, `OutputType::Change`, or `OutputType::Forwarded`. Downstream logic distinguishes these kinds: External outputs carry user instructions (`data`, `presumed_origin`); internal types are consumed by the protocol's own branch/change/forward flows. A deposit intentionally sent to a reserved address is misclassified — the depositor is not credited and the associated instruction data is dropped (lines 731-736 only populate `data` for `External`). This is funds received by the multisig but not accounted to any depositor — effectively funds reported received under an internal identity they do not belong to, analogous to a clobbered global being silently substituted for the real object. Because these outputs sit on the internal paths, automated treatment as, e.g., change from a prior spend, can also corrupt accounting of which outputs correspond to which operation.

### Likelihood Explanation
Any party that knows the multisig's group key (which is public, e.g., the external address) can compute the branch/change/forward addresses deterministically — no validator cooperation, leaked keys, or invalid-curve inputs are needed. The attack only requires sending an ordinary Bitcoin transaction, the cheapest reachability class in scope (`Scanner::scan_transaction` on attacker-sent transactions). Whether it is deliberate griefing or an accidental address reuse, misclassification occurs deterministically with no ordering requirements.

### Recommendation
Distinguish reserved-path provenance: do not blindly assign `kind` by offset match in `get_outputs`. Options:
- Track which internal paths were actually generated/used by the protocol (e.g., only classify as `Change` if the output belongs to a transaction the multisig itself produced or that spends a known internal input), and treat unmatched payments to reserved scripts as `External` deposits or reject them explicitly.
- At minimum, still populate `presumed_origin`/`data` for non-External kinds so a deposit to a reserved address isn't silently dereferenced as an internal output, or log/alert on external-spend transactions paying reserved scripts.

### Proof of Concept
1. Observe the target multisig's group key `K` (public, e.g., via `external_address`).
2. Locally compute `off = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` and increment it exactly as `register_offset` does until `K + G*off` yields an even point; build `addr = address_from_key(K + G*off)`.
3. Broadcast an ordinary Bitcoin transaction paying `addr`.
4. When the block is scanned, `get_outputs` (`processor/src/networks/bitcoin.rs:686-699`) emits the output with `kind == OutputType::Change` — not `External` — and skips populating `data`/`presumed_origin` for it (lines 731-735). The deposit is recorded as an internal change-type output rather than a crediting deposit, demonstrating the attacker-controlled namespace collision.
