## Finding

### Title
Uncontrolled slippage in `EvmHost`'s native-token fee-swap subsidizes sandwich attacks on every request dispatch - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core issue is a Uniswap swap executed with no independent slippage bound, letting a sandwich attacker force the swap to execute at an inflated price and extract value from the party paying for it. `EvmHost.sol` reproduces this exact pattern on every one of its public, unprivileged dispatch entrypoints: whenever a caller pays the Hyperbridge protocol fee in native token, the host performs an on-chain `swapETHForExactTokens` where the only "bound" is `msg.value` itself — there is no oracle-, TWAP-, or caller-supplied minimum-output/maximum-input check independent of the swap call itself.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest(...)` all convert native token to `feeToken()` via the local Uniswap V2 router with the identical unguarded pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called with `path = [WETH, feeToken()]`. `amountInMax` is effectively `msg.value`, a value the *caller* chooses on the fly — it is not derived from any price oracle or from a caller-declared willingness-to-pay bound distinct from the swap call. The pool spot price at the moment of execution is what determines how much of the caller's ETH the router consumes to reach the exact `fee`/`amount` output.

This is the same missing-invariant as the `Voting.sol` report: a payment-critical swap has no protection against the AMM price being manipulated immediately before (and reverted immediately after) the victim's transaction. A searcher watching the public mempool for `dispatch()`/`fundRequest()` calls can:
1. Front-run with a large swap that spikes the `WETH -> feeToken` price on the configured Uniswap V2 pool.
2. Let the victim's `swapETHForExactTokens` execute, consuming far more ETH than the fair-price amount to obtain the fixed `fee`/`amount` of `feeToken`.
3. Back-run to unwind their position, capturing the price impact as profit extracted directly from the victim's `msg.value`.

`IntentGatewayV2.placeOrder` and its Tron port repeat the same construction for `order.fees`: [4](#0-3) 

Any unprivileged user calling these public, payable functions with native token is exposed — no relayer, prover, or admin compromise is required, matching the report's original attacker primitive (public entrypoint, AMM price manipulation, no min/max-out guard).

### Impact Explanation
This is a direct value-loss vector reachable by any unprivileged actor against any user or app that pays Hyperbridge dispatch/fund/order fees with native token instead of the fee token directly. Given `dispatch()` is the core entrypoint used by essentially every cross-chain message on EVM Hyperbridge deployments, the attack surface is broad and recurring (every native-token-funded dispatch, timeout-fund top-up, and IntentGateway order placement). Losses accrue to end users/dapps paying fees, not to the protocol's own custody, but they represent real "loss of funds" / "transaction manipulation" through logic that should have converted ETH to feeToken at a fair price but instead lets an unrelated third party extract the difference.

### Likelihood Explanation
Likelihood is high wherever the configured Uniswap V2 pool for `WETH/feeToken` has shallow liquidity relative to typical dispatch fee sizes — a realistic condition for many of the smaller EVM chains Hyperbridge deploys to. No special access is needed; any address can observe pending `dispatch()`/`fundRequest()`/`placeOrder()` transactions and sandwich them, exactly as in the original report's scenario against `Voting.sol`.

### Recommendation
Add an explicit `amountInMax`/slippage parameter (or an oracle-derived bound, as already implemented in `SimplexPaymaster.swapAndDeposit`, see [5](#0-4) ) to the `dispatch()`, `dispatch(DispatchGet)`, `fundRequest()`, and `IntentGatewayV2.placeOrder()` native-fee swap paths, so the caller can bound the ETH they're willing to spend independent of momentary pool conditions, and so the transaction reverts rather than silently overpaying when the pool has been manipulated.

### Proof of Concept
1. Attacker monitors the mempool for a pending `EvmHost.dispatch(DispatchPost)` call with `msg.value > 0` and a nontrivial `post.fee`.
2. Attacker front-runs with a large `WETH -> feeToken` swap on the configured Uniswap V2 pool, spiking the effective price of `feeToken` in ETH terms.
3. The victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)` at the manipulated price, consuming a much larger fraction of `msg.value` than a fair-price swap would require (any leftover is refunded, but the amount actually spent is inflated).
4. Attacker back-runs, reversing their initial swap and pocketing the price-impact profit extracted from the victim's overpayment — with no code path in `EvmHost.sol` to detect or bound this.
