### Title
Unvalidated `Participant` index in PedPoP blame resolution causes a panic (denial of service) on any node verifying an accusation - (crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class of CVE-2018-15468 is "a security-relevant input whose validation is skipped in a configuration the author assumed unreachable, letting an unprivileged actor crash the host." In Serai's PedPoP DKG, the blame-verification path indexes participant-keyed `HashMap`s with attacker-chosen `Participant` values that are only checked to be non-zero, never checked against the actual participant set. `Decryption::decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` [1](#0-0)  and `BlameMachine::blame_internal` dereferences `self.commitments[&sender]` [2](#0-1) . A `Participant` is any non-zero `u16` [3](#0-2) , so an index like `0xFFFF` (larger than `n`) is accepted by the type but absent from both maps, producing a `HashMap` index panic in library code reachable from a `blame(sender, recipient, msg, proof)` call [4](#0-3) .

### Finding Description
`Decryption::decrypt_with_proof` verifies the message's sender-bound PoP (`msg.pop.verify(..., from, ...)`) and then, if a proof is supplied, indexes `self.enc_keys[&decryptor]` [5](#0-4) . `enc_keys` is only populated for participants who registered during `verify_r1` over `self.params.all_participant_indexes()` (i.e., `1..=n`) [6](#0-5) , and `register` asserts only on *re*-registration, not on membership [7](#0-6) . Nothing in `blame` / `AdditionalBlameMachine::blame` bounds `sender` or `recipient` to `1..=n` [8](#0-7) .

The validation "skipped because it was assumed unreachable" is the mapping from the CVE: the code assumes `decryptor` is always a registered participant because honest callers only accuse real participants, exactly as Xen assumed `MSR_DEBUGCTL` values would already have been checked. An attacker crafts an accusation with `accused`/recipient = `Participant(0xFFFF)` (or any index `> n`), a `share` message whose PoP is validly bound to a real `sender` (e.g., a genuine encrypted share observed from that sender, or one the attacker generated while misbehaving), and a well-formed `EncryptionKeyProof`. Any honest node running `BlameMachine::blame` / `AdditionalBlameMachine::blame` (the `VerifyBlame` adjudication path) reaches `self.enc_keys[&decryptor]`, hits a missing `HashMap` entry, and panics.

### Impact Explanation
A panic inside the library aborts the verifying party's blame adjudication. In deployment this is triggered by a blame/accusation message, so a single malicious or malformed accusation with an out-of-range `Participant` crashes every honest node that evaluates it, halting DKG completion and slash adjudication — a denial of service matching the CVE's medium-severity DoS profile. No secret is leaked and no signature is forged; the impact is availability only, hence Medium rather than High.

### Likelihood Explanation
Reachability requires an accusation carrying (a) a `recipient`/`accused` index outside `1..=n` (trivial — the type accepts any non-zero `u16` [3](#0-2) ), (b) a `msg` whose per-message PoP verifies for some real `sender`, and (c) an `EncryptionKeyProof`. A protocol participant satisfies (b) by replaying any genuine `EncryptedMessage` from a real participant and satisfies (c) because `decrypt` hands every honest recipient a valid `EncryptionKeyProof` for each message it decrypts [9](#0-8)  — the proof's DLEq binds `enc_keys[&decryptor]` *after* the panic-inducing lookup, so the proof being "for" a different recipient doesn't save it. Any single participant can therefore crash blame verification.

### Recommendation
Validate `sender` and `recipient` at the top of `BlameMachine::blame_internal` and `Decryption::decrypt_with_proof` against the registered participant set (`self.commitments.contains_key(&sender)`, `self.enc_keys.contains_key(&decryptor)`) and return the accuser/attacker as faulty — or use `.get()` and treat a missing entry as evidence against the accuser — instead of `HashMap` index operators. The same hardening applies to `self.commitments[&sender]` [10](#0-9) .

### Proof of Concept
```rust
// Attacker is any PedPoP participant (or relays a real one's share message).
// In CalculateShare they obtained a genuine EncryptedMessage msg from real sender S
// and the corresponding EncryptionKeyProof via decrypt().

// Nodes adjudicating the accusation run (conceptually):
let machine = AdditionalBlameMachine::new(context, n, commitment_msgs).unwrap();
// accuser submits: accused = Participant::new(0xFFFF).unwrap()  // > n, valid non-zero u16
machine.blame(
    S,                                  // sender whose PoP binds msg (must verify)
    Participant::new(0xFFFF).unwrap(),  // decryptor: NOT in enc_keys
    msg,                                // genuine EncryptedMessage from S
    Some(proof),                        // any EncryptionKeyProof reaching the lookup
);
// decrypt_with_proof: pop.verify passes (msg is genuinely from S),
// then `self.enc_keys[&decryptor]` panics: index out of map -> node crash.
```

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

  /// Given an accusation of fault, determine the faulty party (either the sender, who sent an
  /// invalid secret share, or the receiver, who claimed a valid secret share was invalid). No
  /// matter which, prevent completion of the machine, forcing an abort of the protocol.
  ///
  /// The message should be a copy of the encrypted secret share from the accused sender to the
  /// accusing recipient. This message must have been authenticated as actually having come from
  /// the sender in question.
  ///
  /// In order to enable detecting multiple faults, an `AdditionalBlameMachine` is returned, which
  /// can be used to determine further blame. These machines will process the same blame statements
  /// multiple times, always identifying blame. It is the caller's job to ensure they're unique in
  /// order to prevent multiple instances of blame over a single incident.
  pub fn blame(
    self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> (AdditionalBlameMachine<C>, Participant) {
    let faulty = self.blame_internal(sender, recipient, msg, proof);
    (AdditionalBlameMachine(self), faulty)
  }
