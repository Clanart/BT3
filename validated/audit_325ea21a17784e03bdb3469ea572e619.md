### Title
OP_RETURN data output excluded from fee and weight accounting in `SignableTransaction::new` — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` appends the OP_RETURN output carrying user-supplied `data` to `tx_outs` before computing the transaction weight and required fee, but the weight/vbyte calculation is run over `payments` only. The analog to the Alchemix incident (a vault entry written to the wrong index, silently dropping debt from accounting) is an output present in the transaction but absent from the index of entries used for accounting: the OP_RETURN output is never counted, so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check are all computed against a smaller transaction than the one actually signed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is pushed into `tx_outs` at lines 194–202:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
```

The weight/vbyte computation immediately after, at line 204, uses only `payments`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds its measurement transaction purely from `payments` (lines 85–93), so the OP_RETURN output — up to ~92 bytes (8-byte value + script length + 2-byte opcode/push + up to 80 bytes of data, checked at line 171) — is never included in `weight` or `vbytes`. The same omission recurs in the change path at line 226, where `fee_with_change` is again computed without the data output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) underestimates the fee for the requested rate by `fee_per_vbyte * ~90` satoshis at most.
- The `TooLowFee` check (line 211) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`, so a transaction can pass the check while its real fee rate falls below the minimum relay fee.
- The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses the underestimated `weight`, so a transaction can pass the check while exceeding the standard weight limit.

The `data` field is populated from external inputs (e.g., the Serai `InInstruction` embedded in Bitcoin transactions reaching `get_outputs`/`extract_serai_data`), so the miscalculation is reachable with attacker-influenced bytes rather than being a purely internal constant.

### Impact Explanation
The signed transaction is systematically larger than accounted for. Two failure modes result: (1) the effective fee rate is lower than the caller requested — potentially below the network minimum relay fee — causing the transaction to be rejected or stuck in mempools, leaving the spent outputs unconfirmed and effectively unspendable until a replacement is signed and propagated; (2) a transaction near the weight limit is broadcast at a non-standard weight and is not relayed at all. In a threshold-wallet setting this translates to multisig funds locked pending operator intervention, matching the incident's class of accounting errors that strand real value. Severity: Medium — it does not enable theft or forgery, but reliably produces transactions that misprice fees and can stall funds.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some` — no race, no adversarial control of the curve math required. The only mitigating factor is that the worst case (~90 vbytes) requires near-maximum data, and the absolute fee shortfall is bounded by `fee_per_vbyte * ~92`; at low fee rates the tx may still confirm, but at boundary conditions (minimum relay fee, near-max weight) it fails outright.

### Recommendation
Include the OP_RETURN output in the accounting transaction used by `calculate_weight_vbytes`. Since the data length is known before the fee is computed, either pass the data length (or the constructed script) into `calculate_weight_vbytes` and push the OP_RETURN `TxOut` onto its scratch `tx.output`, or compute weight/vbytes from `tx_outs` (which already contains the OP_RETURN output) instead of from `payments`. The change-aware second call at line 226 must likewise include the data output.

### Proof of Concept
```rust
// 80 bytes is the maximum permitted by the length check at line 171
let data = vec![0u8; 80];

let tx_with_data = SignableTransaction::new(
    vec![output.clone()],
    &[(payment_script.clone(), payment_amount)],
    None,
    Some(data),
    FEE_PER_VBYTE,
).unwrap();

// The real transaction contains the OP_RETURN output...
assert!(tx_with_data.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// ...but needed_fee was computed on a scratch tx containing only `payments`,
// so the effective fee rate is below FEE_PER_VBYTE:
let real_vbytes = tx_with_data.transaction().vsize() as u64;
let paid_fee = tx_with_data.fee();
assert!(paid_fee < FEE_PER_VBYTE * real_vbytes); // under-accounted by ~90 vbytes
```
At `fee_per_vbyte` values near `DEFAULT_MIN_RELAY_TX_FEE`, the resulting transaction passes the `TooLowFee` check yet broadcasts below the minimum relay rate and is dropped by nodes.
