## Analysis Summary

The OpenVPN CVE's failed invariant: attacker-controlled server data (`PUSH_REPLY`) is written into client logs without sanitization, allowing forged/injected log content. The Protobuf analog with the strongest transferable invariant is in the **ProtoJSON parsing error-message construction path**, where attacker-controlled JSON key/token text is embedded verbatim (no escaping of control characters) into the diagnostic string returned from parsing, and that string is the exact value application code is expected to log. ### Title
JSON field-name/token text is embedded unescaped into parser diagnostic messages, enabling log/terminal injection when applications log ProtoJSON parse errors - (File: `src/google/protobuf/json/internal/lexer.cc`)

### Summary
When parsing untrusted ProtoJSON input through the public `JsonStringToMessage`/`JsonToBinaryStream` (C++), `json_format.Parse` (Python), or `JsonFormat.parser().merge()` (Java) APIs, error paths build human-readable diagnostic strings that directly interpolate attacker-controlled JSON text (object keys, unrecognized tokens, enum strings) via `absl::StrFormat("%s", ...)` / Python `.format()` string concatenation, without stripping or escaping control characters (newlines, carriage returns, ANSI escape sequences). Because JSON string literals can decode `\u000a`, `\u001b`, etc. into raw bytes, the resulting `absl::Status`/`ParseError`/`InvalidProtocolBufferException` message can contain arbitrary control bytes. These messages are the documented, expected surface for callers to log when parsing fails.

### Finding Description
- In C++, `JsonLocation::Invalid()` explicitly documents that the message content is *not* hardened, "so that people have a hope of grepping for it in logs," and only applies `HardenAgainstHyrumsLaw()`, which merely randomizes whitespace runs — it performs no control-character stripping or escaping. [4](#0-3) [5](#0-4) 
- Field-name lookups embed the raw JSON key straight into the invalid-input message: `lex.Invalid(absl::StrFormat("no such field: '%s'", name))`, where `name` is the decoded JSON key (attacker-controlled, may contain decoded control bytes from `\u00XX` escapes). [2](#0-1) 
- The Python binding has the same pattern: unknown-field errors interpolate the raw JSON key `name` directly into the `ParseError` message via `.format()`. [3](#0-2) 
- The Java `JsonFormat` parser does the same for invalid enum/type-mismatch messages, concatenating the raw `JsonElement` (`json.toString()`c) into the exception message. [6](#0-5) [7](#0-6) 

**Attacker model / exposure assumption**: an ordinary client sends bounded ProtoJSON to a service that uses one of the above public parse APIs. The consuming application follows the common, encouraged practice of logging the returned parse-error `Status`/exception message (e.g., `LOG(ERROR) << status;` or `logger.warning(e.getMessage())`) for diagnosability — this is exactly the intended use per the code comment "so that people have a hope of grepping for it in logs." No privileged access or hostile schema is required; the schema/generated code is fully trusted, only the JSON payload's field-name/token text is attacker-controlled.

### Impact Explanation
An attacker who can only send malformed/unexpected ProtoJSON can cause the library-provided error message string — which the application is nominally invited to log verbatim — to contain arbitrary control bytes (CR/LF, ANSI escape sequences) decoded from JSON `\u00XX` escapes. This enables:
- Log-injection/forging (fake log lines split via injected `\n`/`\r`), corrupting log integrity used for auditing (directly analogous to OpenVPN's "unexpected arbitrary data ending up in client logs").
- Terminal-escape-sequence injection if logs are viewed live in a terminal (potential terminal spoofing when the log viewer is not itself hardened).

This is bounded to a confidentiality/integrity issue of the *logging* channel (matches the CVE's C:H/I:H/A:N profile) and does not by itself provide RCE or memory-safety impact within Protobuf.

### Likelihood Explanation
High for reachability: any of the public ProtoJSON parse entry points (`JsonStringToMessage`, `json_format.Parse`, `JsonFormat.parser().merge()`) trigger this path on ordinary malformed input (e.g., an unknown/typo'd field name), which is a routine occurrence for untrusted client input, not a crafted edge case. The `HardenAgainstHyrumsLaw` comment shows this was a conscious design choice for greppability, not a hardening bug being masked — meaning the missing invariant ("do not embed raw attacker bytes in log-destined text") was never in scope for this code path, so no existing check silently already blocks it.

### Recommendation
- Escape/strip non-printable and control characters (or CEscape-style encode) from any JSON key/token text before interpolating it into `absl::Status`/`ParseError`/exception messages across the C++, Python, and Java JSON parsers.
- Document in the JSON parsing API surface that returned parse-error text may contain attacker-influenced content and must not be logged verbatim by callers without sanitization, consistent with the existing TextFormat guidance to prefer Binary/ProtoJSON for untrusted input.

### Proof of Concept
Send the following JSON body to any endpoint that calls `json_format.Parse(text, message)` (Python) against a proto message without a field literally named with a newline:
```
{"unknown\nFAKE LOG LINE: admin login succeeded": 1}
```
The decoded key is `unknown\nFAKE LOG LINE: admin login succeeded`. `json_format.Parse` raises:
```
ParseError: Message type "X" has no field named "unknown
FAKE LOG LINE: admin login succeeded" at "X".
 Available Fields(except extensions): [...]
``` [3](#0-2) 
If the calling service logs `str(exception)` (a common pattern for diagnosing bad client input), the resulting log stream now contains an attacker-forged line `FAKE LOG LINE: admin login succeeded`, mirroring the OpenVPN CVE's outcome of unsanitized attacker data reaching client logs. The same construction applies to the C++ `no such field: '%s'` path and the Java enum/type-mismatch messages using `\u000a`-containing JSON keys/enum strings.

void HardenAgainstHyrumsLaw(absl::string_view to_obfuscate, std::string& out) {
  // Get some simple randomness from ASLR, which is enabled in most
  // environments. Our goal is to be annoying, not secure.
  static const void* const kAslrSeed = &kAslrSeed;
  // Per-call randomness from a relaxed atomic.
  static std::atomic<uintptr_t> kCounterSeed{0};

  constexpr uint64_t kA = 0x5851f42d4c957f2dull;
  constexpr uint64_t kB = 0x14057b7ef767814full;

  uint64_t state = absl::bit_cast<uintptr_t>(kAslrSeed) + kB +
                   kCounterSeed.fetch_add(1, std::memory_order_relaxed);
  auto rng = [&state, &kA, &kB] {
    state = state * kA + kB;
    return absl::rotr(static_cast<uint32_t>(((state >> 18) ^ state) >> 27),
                      state >> 59);
  };
  (void)rng();  // Advance state once.

  out.reserve(to_obfuscate.size() + absl::c_count(to_obfuscate, ' '));
  for (char c : to_obfuscate) {
    out.push_back(c);
    if (c != ' ' || rng() % 3 != 0) {
      continue;
    }

    size_t count = rng() % 2 + 1;
    for (size_t i = 0; i < count; ++i) {
      out.push_back(' ');
    }
  }

absl::Status JsonLocation::Invalid(absl::string_view message,
                                   SourceLocation sl) const {
  // NOTE: we intentionally do not harden the "invalid JSON" part, so that
  // people have a hope of grepping for it in logs. That part is easy to
  // commit to, as stability goes.
  //
  // This copies the error twice. Because this is the "unhappy" path, this
  // function is cold and can afford the waste.
  std::string status_message = "invalid JSON";
  std::string to_obfuscate;
  if (path != nullptr) {
    absl::StrAppend(&to_obfuscate, " in ");
    path->Describe(to_obfuscate);
    to_obfuscate.push_back(',');
  }
  absl::StrAppendFormat(&to_obfuscate, " near %zu:%zu (offset %zu): %s",
                        line + 1, col + 1, offset, message);
  HardenAgainstHyrumsLaw(to_obfuscate, status_message);

  return absl::InvalidArgumentError(std::move(status_message));
}
