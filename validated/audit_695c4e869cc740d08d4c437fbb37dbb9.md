Based on my analysis of the new lazy module initialization feature, I found a genuine authorization-bypass gap in the object-ownership guard.

### Title
Lazy module self-init fails open (mints a signer) for deleted objects whose deploy owner was never recorded - ([File: aptos-move/framework/aptos-framework/sources/init.move])

### Summary
`aptos_framework::init::assert_may_self_initialize` is meant to guarantee that a module published to an object address can only mint its own signer via `internal_maybe_initialize` while the object's root owner is unchanged since the module was last (re)published, and that a transfer, ancestor transfer, or **deletion** of the object blocks self-init. This guarantee only holds when a `deploy_owner` was actually recorded for that module at publish time. If it was never recorded — e.g. the module was published while `LAZY_MODULE_INITIALIZATION` was disabled, so `code::publish_package` skipped the recording step — the guard's fallback branch treats "no record" as equivalent to "plain account address," and once the underlying object is deleted, `object::is_object(addr)` becomes `false`, causing the guard to authorize minting a signer for the address to *any* caller.

### Finding Description
`code::publish_package` only records the deploy owner when the feature is enabled at publish time: [1](#0-0) 

The guard itself is: [2](#0-1) 

The `ok` fallback branch is `!object::is_object(addr)` — this is safe for genuine externally-owned accounts (they authorize their own code by publishing), but it also becomes `true` for an address that **used to be an object but was deleted**, if no `deploy_owner` was ever recorded for that module. The doc comment for `assert_may_self_initialize` explicitly claims deletion blocks self-init: [3](#0-2) 

but that claim is only true in the branch where `recorded.is_some()`. The existing test suite only covers: (a) live object with no record → blocked, and (b) recorded owner + deleted object → blocked: [4](#0-3) 

There is no test for "no record + deleted object," which is exactly the gap: `recorded = none()`, `object::is_object(addr) = false` → `ok = true`.

### Impact Explanation
This breaks the module-init/authorization invariant this feature is built around: minting a signer for an object address should require proof that whoever controls the call still controls the object as it stood at last publish. In the deleted+unrecorded case, `internal_maybe_initialize` mints a signer for the (now nonexistent) object address to **any unauthorized caller**, letting them execute the module's self-initializer with that signer (e.g. `move_to` arbitrary resources, capability grabs) under an address the caller does not own and never owned. Because module storage is independent from object/resource storage, the module bytecode remains live at that address after the underlying `ObjectCore` is deleted, so this is directly reachable. This is a protected-state-mutation authorization bypass reachable purely through the publish → feature-toggle → delete → call sequence, matching the "module-init ... failure that reaches protected state mutation" impact category.

### Likelihood Explanation
Reaching the bug requires: (1) a package published to a deletable object address that uses `init::internal_maybe_initialize`, (2) publication occurring while `LAZY_MODULE_INITIALIZATION` is not yet enabled network-wide (a plausible ordering, since this is a governance-toggled, transient feature flag, and code can legitimately be compiled/published before the flag activates), (3) the object being deleted via its `DeleteRef` at some point, and (4) the feature later being enabled. None of these steps require unusual privilege from the attacker — only the object owner needs to delete their own object at some point, and any third party can then trigger the vulnerable call. Given this is a brand-new, not-yet-widely-deployed feature (`FeatureFlag::LAZY_MODULE_INITIALIZATION = 127`), likelihood is currently moderate but the invariant break is unconditional whenever the preconditions are met.

### Recommendation
Change the fallback semantics in `assert_may_self_initialize` so that "no recorded owner" is only treated as authorized when the address was **never** an object (i.e., distinguish "always was a plain account" from "was an object, record missing, now possibly deleted"). Concretely, record a deploy-owner sentinel (or an explicit "is object" marker) for object addresses regardless of the `LAZY_MODULE_INITIALIZATION` flag state, or make the module-init recording flow unconditional in `code::publish_package` instead of gating it on the feature flag, so that `recorded_deploy_owner` is always populated at publish time for object addresses.

### Proof of Concept
1. Enable `OBJECT_CODE_DEPLOYMENT`; keep `LAZY_MODULE_INITIALIZATION` disabled.
2. Create an object `O` with a `DeleteRef` (e.g. via `object::create_object`), and publish a package to `O` whose entry function calls `init::internal_maybe_initialize(false)` (this compiles fine; it will just abort at runtime while the flag is off).
3. Owner calls `object::delete` on `O` using the stored `DeleteRef`. Module bytecode at `O` remains in module storage.
4. Governance enables `LAZY_MODULE_INITIALIZATION`.
5. Any account (not the original owner) calls the entry function at `O`. `check_and_set_initialized` returns `false` (first call), `recorded_deploy_owner` returns `none`, `object::is_object(O)` is `false` → `assert_may_self_initialize` passes → a signer for `O` is minted and handed to the module's initializer, executed by the unauthorized caller.

This mirrors the local test harness pattern already present in `init.move`'s `#[test_only]` helpers (`record_current_owner`, `assert_may_init`, `object::delete`), simply omitting the `record_current_owner` call before `object::delete`, which the current test suite does not exercise.

```text
    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }
```
