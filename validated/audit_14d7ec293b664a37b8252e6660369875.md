## Title
Path traversal via committed/PR file paths in "Reveal in File Manager" / "Open with default program" / "Copy path" actions — path escapes repository root without validation - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/lib/app-shell.ts`)

### Summary
Desktop already applies a strict, `resolveWithin`-based guard against path traversal for filepaths that arrive via the `x-github-client://` deep-link handler (`openRepositoryFromUrl` in `dispatcher.ts`), but the same class of untrusted, attacker-controlled path string — a `CommittedFileChange.path`/`WorkingDirectoryFileChange.path`, which for a pull request comes straight from GitHub API diff data or from `git log --raw`/`git diff --raw` parsing of a fetched commit — is used unchecked in several other file-system-touching actions: reveal-in-Finder/Explorer, "Open with default program", "Copy path", and "Open in external editor". These call sites build the on-disk path with plain `Path.join(repository.path, path)` and never call `resolveWithin`/`isAbsolute` rejection like the deep-link path does.

### Finding Description
`resolveWithin` (`app/src/lib/path.ts:36-100`) is the app's canonical primitive for validating that a repo-relative path segment resolves to a location inside the repository root (it normalizes, rejects null bytes, and uses `realpath` to defeat symlink escapes). It is used deliberately in the deep-link flow: [1](#0-0) 

But `CommittedFileChange.path` — populated directly from `git diff --raw`/`git log --raw` parsing (`parseRawLogWithNumstat`, `app/src/lib/git/log.ts:276-317`) for local commits, and from the GitHub Pull Request "files changed" API response for PR review flows — flows unchecked into: [2](#0-1) [3](#0-2) 

and into the generic reveal helper, which does no validation at all: [4](#0-3) 

The equivalent working-directory-changes context menu (`filter-changes-list.tsx`) and conflict-resolution UI (`unmerged-file.tsx`) build paths the same unchecked way (`Path.join(repository.path, file.path)` / `join(props.repository.path, props.path)`), and `app.tsx`'s `onOpenInExternalEditor` does likewise: [5](#0-4) [6](#0-5) 

`Path.join` does **not** prevent `..` traversal segments from escaping the base directory — that is exactly why `resolveWithin` exists and why it was deliberately added to the deep-link handler. Any code path that can insert a `..`-bearing (or absolute, or symlink-escaping) string into a `file.path`/`path` field will cause these actions to touch a filesystem location outside the repository.

### Impact Explanation
If a crafted diff/raw-log entry or PR-file-list entry can carry a path containing `..` segments (or is otherwise not confined to the repo root), a user simply right-clicking "Reveal in File Manager," "Open with default program," "Copy path," or double-clicking to open in the external editor on that entry causes Desktop to operate on an out-of-repository path chosen by the remote content. Impact ranges from disclosure of file existence/location (via "reveal in Finder"/copy path) to launching arbitrary files with the OS default handler or external editor outside the repository sandbox — i.e., file read/launch outside the repo boundary, matching the "file write or read outside the repo" impact class named in scope. This mirrors the ELFI bug class: an action (open/execute) is performed without validating an invariant (path confinement) that another code path in the same codebase already enforces.

### Likelihood Explanation
This is lower confidence than a fully proven exploit because it depends on whether git itself, or the GitHub API's PR-files endpoint, will actually hand Desktop a raw/numstat entry or diff-file path containing `..`/absolute segments. Git's own index/tree validation normally rejects `..` path components, so exploitability likely requires an edge case (e.g., case-insensitive/NTFS filesystem quirks, historical git path-validation bypasses, or a PR-files API response that isn't re-validated against a strict allowlist) to actually produce such a string. I could not fully verify from static code inspection alone whether such a bypass currently exists in the bundled dugite/git version or in the API response parsing, since that would require testing against a live crafted repository/PR — the index does not give visibility into runtime git binary behavior. The structural defect (missing `resolveWithin` guard at these specific call sites, present at a sibling call site) is confirmed by code; the reachability of a traversal-bearing path string from attacker-controlled input is the part that needs empirical confirmation.

### Recommendation
Apply the same `resolveWithin` (or `isAbsolute` + `resolveWithin`) validation used in `dispatcher.ts`'s `openRepositoryFromUrl` to every call site that turns a `WorkingDirectoryFileChange.path`/`CommittedFileChange.path` into an on-disk path before passing it to `shell.showItemInFolder`, `shell.openExternal`, `launchExternalEditor`, or `clipboard.writeText`: specifically `revealInFileManager` (`app-shell.ts`), `onOpenFile`/`onFileContextMenu` (`pull-request-files-changed.tsx`), `getRevealInFileManagerMenuItem`/`getCopySelectedPathsMenuItem` (`filter-changes-list.tsx`), `onOpenInExternalEditor` (`app.tsx`), and the conflict resolution path builders in `unmerged-file.tsx`. Reject or drop entries whose resolved path is null (outside root) rather than silently joining.

### Proof of Concept
Not independently reproduced in this review (no live git/PR fixture available to confirm a traversal-bearing `file.path` can actually be produced by dugite's raw/numstat parser or by the GitHub PR-files API). The structural gap is demonstrated by contrasting the guarded call site:
```ts
// app/src/ui/dispatcher/dispatcher.ts:1963
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) { shell.showItemInFolder(resolved) } else { /* rejected */ }
```
with the unguarded ones, e.g.:
```ts
// app/src/lib/app-shell.ts:61-63
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
```
A concrete PoC would require constructing a fetched commit or PR-files response whose `path`/raw-diff field contains `../../` segments and confirming dugite's `git log --raw`/`--numstat` parser (or the GitHub API JSON) passes it through unmodified into `CommittedFileChange.path` — this step could not be completed with static code search alone and should be validated with a live Devin/dev environment.
