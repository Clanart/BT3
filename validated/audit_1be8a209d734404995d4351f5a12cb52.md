### Title
`Scanner::scan_block` reports immature coinbase outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the external report is "external data consumed without validating its freshness/maturity". In `serai`, `Scanner::scan_block` iterates over every transaction in a block — including `block.txdata[0]`, the coinbase transaction — and returns any outputs paying to a scanned key as `ReceivedOutput`s. Coinbase outputs are unspendable for 100 blocks (BIP-30/COINBASE_MATURITY), so the scanner reports funds as received that cannot actually be spent or signed over.

### Finding Description
`scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199) matches `output.script_pubkey` against registered scripts and pushes a `ReceivedOutput` with an `OutPoint` built from `tx.compute_txid()`. `scan_block` (mod.rs:221-227) calls it for every `tx` in `block.txdata` with no exclusion of index 0:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

By contrast, the production consumer `get_outputs` in `processor/src/networks/bitcoin.rs:690-691` explicitly skips the coinbase (`for tx in &block.txdata[1 ..]`), confirming the maturity hazard is real and must be handled by callers. Any miner can craft a coinbase output paying to a registered Serai script (trivially obtainable from the public key/address); the block data is untrusted public input fed to `scan_block`, and the API returns it as a spendable-looking `ReceivedOutput` indistinguishable from a normal deposit.

### Impact Explanation
Funds are reported received that are not spendable. A `ReceivedOutput` for an immature coinbase cannot be used as an input in a transaction until 100 confirmations elapse; any downstream accounting or scheduler that trusts `scan_block` results (as the library's own doc comment admits, "If received outputs must be immediately spendable, a post-processing pass is needed") will credit balance that a signing attempt over would produce an invalid transaction rejected by the network. This maps directly to the reported "stale/immature external value consumed without a validity check".

### Likelihood Explanation
Every Bitcoin block contains a coinbase transaction, and any miner can direct part of the block reward to Serai's deposit scripts at zero marginal cost (opportunity cost of the reward itself only). The trigger requires no privileged position beyond mining a block, and the vulnerable code path is the crate's public block-scanning API.

### Recommendation
In `scan_block`, skip `block.txdata[0]` (coinbase) by default, or annotate `ReceivedOutput` with an immaturity flag / required confirmation count so consumers cannot treat it as spendable. Alternatively expose `scan_block` over `block.txdata[1 ..]` and provide a separate `scan_coinbase` API that returns outputs tagged as maturity-bound, matching the handling already implemented in `processor/src/networks/bitcoin.rs` `get_outputs`.

### Proof of Concept
In the crate's own test (`networks/bitcoin/tests/wallet.rs:63-69`), a block is mined with `generatetoaddress` paying the scanned key, then `scanner.scan_block(&block)` is asserted equal to `scanner.scan_transaction(&block.txdata[0])` — demonstrating that `scan_block` returns the coinbase output at index 0 as a `ReceivedOutput`. That outpoint is unspendable for 100 blocks, yet the API reports it identically to a confirmed, spendable deposit.
