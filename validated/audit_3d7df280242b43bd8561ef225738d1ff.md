### Title
Unbounded indexing panic in PedPoP blame evaluation allows remote crash of DKG participants - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to JLSEC-2026-186 (segmentation violation in `Assimp::XFileImporter::CreateMeshes` when parsing untrusted input), `Decryption::decrypt_with_proof` indexes a `HashMap` with an attacker-supplied `Participant` index without a membership check, causing a panic (Rust's equivalent of a crash) reachable purely from peer-supplied blame messages.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept `sender`, `recipient`, an `EncryptedMessage`, and an optional `EncryptionKeyProof`, all originating from an accusing peer [1](#0-0) . Both route into `blame_internal`, which calls `Decryption::decrypt_with_proof` [2](#0-1) .

Inside `decrypt_with_proof`, when `proof` is `Some`, the code indexes `self.enc_keys[&decryptor]`:

```rust
// crypto/dkg/pedpop/src/encryption.rs
if let Some(proof) = proof {
  proof
    .dleq
    .verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],
    )
```

The indexing happens **before** any verification that `decryptor` is a registered participant. `enc_keys` is only populated for participants 1..=n via `register` [3](#0-2) . A `Participant` is any nonzero `u16`, so an accuser can set `recipient` to any value > n (or any index whose encryption key message was never registered). HashMap `Index` panics on a missing key — the panic fires before the DLEq proof is even evaluated, so no valid cryptographic material is required from the attacker beyond structurally-parseable bytes (`EncryptionKeyProof::read` succeeds on any canonical point + scalars) [4](#0-3) .

A secondary instance exists at `self.commitments[&sender]` in `blame_internal` [5](#0-4) , though reaching it additionally requires a valid PoP/decryption, making the `enc_keys[&decryptor]` path the primary reachable crash.

### Impact Explanation
Any party able to submit a blame accusation (e.g., a malicious DKG participant or anyone relaying accusations to a node evaluating blame) can crash the victim's key-generation/blame-evaluation process. In Rust this is a process/thread panic rather than a memory-safety violation, but the security shape matches the advisory exactly: attacker-controlled bytes → unhandled out-of-bounds map access → denial of service. A crashing validator cannot complete DKG blame arbitration, stalling threshold key generation.

### Likelihood Explanation
The trigger requires no valid signatures, no threshold collusion, and no cryptographic forgery — only:
1. `msg.pop.verify` passing *or* the proof path being taken (the panic precedes signature-gated logic only for the `Some(proof)` branch; the PoP check at line 374 must pass first since it precedes the proof block — the accuser needs a message with a valid Schnorr PoP, which they can construct for their *own* encryption key since `pop_challenge` binds only sender/context/key, not the recipient index). The accuser simply crafts a valid `EncryptedMessage` from themselves plus any `EncryptionKeyProof`, and names a non-existent `recipient`.

This is trivially reachable for any DKG participant sending a blame accusation naming an out-of-range recipient.

### Recommendation
Replace infallible indexing with checked lookups returning `DecryptionError`/`PedPoPError`:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
```

Apply the same `get`-based access for `self.commitments[&sender]` in `blame_internal` (treating an unknown sender as blaming the accuser/recipient, or a dedicated `UnknownParticipant` error). Additionally, `AdditionalBlameMachine::new` callers should validate `sender`/`recipient` against `1..=n` before invoking `blame`.

### Proof of Concept
```rust
// Assume a completed/in-progress PedPoP session over any Ciphersuite C.
// Attacker (any Participant p in 1..=n) constructs:
let malicious_recipient = Participant::new(n + 5).unwrap(); // never registered

// Any valid EncryptedMessage the attacker produced for themselves
// (its pop verifies under pop_challenge(context, R, key, attacker, msg)).
let msg: EncryptedMessage<C, SecretShare<C::F>> = attacker_signed_msg;

// Any structurally valid proof: arbitrary canonical point + DLEq scalars.
let proof = Some(EncryptionKeyProof::read(&mut valid_canonical_bytes).unwrap());

// Victim evaluates the accusation:
blame_machine.blame(
  attacker,             // sender (registered)
  malicious_recipient,  // recipient NOT in enc_keys
  msg,
  proof,
);
// Panic at crypto/dkg/pedpop/src/encryption.rs:388:
//   self.enc_keys[&decryptor]  ->  HashMap index on missing key
```

The panic occurs before `proof.dleq.verify` executes, so the DLEq proof need not be valid — only parseable.
