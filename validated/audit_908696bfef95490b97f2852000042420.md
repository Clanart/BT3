### Title
Unchecked ERC20 return value in CW20↔ERC20 pointer wrapper allows silent transfer failure to be reported as success - ([File: example/cosmwasm/cw20/src/contract.rs])

### Summary
The CosmWasm wrapper contract that exposes an arbitrary ERC20 token as a CW20 token (compiled into the production `cwerc20.wasm` artifact embedded at [1](#0-0) ) issues `transfer`/`transferFrom` calls to the underlying ERC20 contract via `EvmMsg::DelegateCallEvm` without ever checking whether the ERC20 call actually returned `true`. This is the exact bug class described in the external report — non-reverting ERC20 tokens that simply return `false` on failure are not handled — mapped onto the CW20-pointer/EVM-bridge path of sei-chain.

### Finding Description
The `transfer` and `transfer_from` handlers build a delegatecall payload and hand it to the chain as a `CosmosMsg::Custom(EvmMsg::DelegateCallEvm{...})`, then immediately return a `Response` with `add_message(msg)` and success attributes (`"action": "transfer"`, `"action": "transfer_from"`, etc.) without waiting for or inspecting the result of the EVM call: [2](#0-1) [3](#0-2) 

`EvmMsg::DelegateCallEvm` is a fire-and-forget `CosmosMsg` (not a reply-based submessage), so the CW20 contract has no mechanism to inspect the ABI-encoded `bool` return value of the ERC20 `transfer`/`transferFrom` call: [4](#0-3) 

For an ERC20 token that does not revert on failure and instead returns `false` (the exact non-standard-token behavior flagged in the external report), the `DelegateCallEvm` message will not fail/abort — it completes "successfully" from the EVM's perspective even though no balance actually moved. The CW20 wrapper's `execute_transfer_from`/`execute_send_from` path is worse: it not only marks the transfer as successful, but for `send_from` it *also* dispatches a second message — `cw20receive_into_cosmos_msg` — invoking the receiving contract's `receive` callback as if funds had actually landed: [5](#0-4) 

Any CosmWasm contract that expects a CW20 pointer to behave with standard atomic-and-truthful semantics (funds are moved if and only if the tx succeeds) can therefore be told "transfer succeeded" and even receive an `onReceive`-style callback while zero tokens were actually moved.

### Impact Explanation
This breaks the fundamental "no partial/false success" guarantee CW20 consumers rely on. A CosmWasm contract (e.g. a DEX pool, escrow, or lending market) that accepts a CW20-pointer-wrapped ERC20 and credits the sender based on the `send`/`transfer_from` succeeding (via `Cw20ReceiveMsg`) can be tricked into crediting balances/collateral/liquidity that were never actually deposited, since the underlying ERC20's `false` return is silently swallowed. This is a real path to unauthorized value creation/fund loss for any downstream CW20-consuming contract that trusts the pointer, satisfying the "unauthorized transfer via pointer" impact category.

### Likelihood Explanation
Reachable by any unprivileged CosmWasm user who deploys/uses an ERC20→CW20 pointer for a token whose implementation follows the well-known (and still-common) `transfer`/`transferFrom` returning `false` instead of reverting (e.g., legacy tokens mimicking pre-EIP20 "USDT-style" semantics, or a malicious ERC20 deployed specifically to exploit this). Because pointer creation and the CW20 send/transfer_from flow are both public, unprivileged operations, no special permission is required — only that a non-standard/malicious token is registered as the pointee, which anyone can do via the pointer-registration precompile.

### Recommendation
After dispatching `DelegateCallEvm` for ERC20 `transfer`/`transferFrom`, verify the ABI-decoded boolean return value before treating the operation as successful, or restructure the flow to use `SubMsg`/`reply` so the wrapper can inspect the EVM call's actual return data and abort (return an error) if the underlying ERC20 call returns `false`. Apply the same fix to the `send`/`send_from` paths so the `Cw20ReceiveMsg` callback is only fired after a confirmed successful transfer.

### Proof of Concept
1. Deploy a "bad" ERC20 contract whose `transferFrom` performs `balanceOf` checks but returns `false` (never reverts) when the allowance/balance is insufficient, mimicking legacy non-compliant tokens.
2. Register an ERC20→CW20 pointer for this token via the pointer-registration precompile (`AddERC20` equivalent), which compiles/instantiates the `cwerc20.wasm` contract shown in `x/evm/artifacts/erc20/artifacts.go`.
3. From a victim CosmWasm contract (e.g., a mock liquidity pool) that implements `receive(Cw20ReceiveMsg)` and credits the sender's balance on receipt, have an attacker call the pointer's `send_from` (`ExecuteMsg::SendFrom`) with an amount exceeding their actual/approved ERC20 balance.
4. Because the underlying ERC20 `transferFrom` returns `false` rather than reverting, `execute_send_from` ( [5](#0-4) ) still returns `Ok(Response)` and dispatches the `Cw20ReceiveMsg` to the victim contract — which credits the attacker even though zero tokens were transferred.

pub fn execute_send_from(
    deps: DepsMut<EvmQueryWrapper>,
    env: Env,
    info: MessageInfo,
    owner: String,
    contract: String,
    amount: Uint128,
    msg: Binary,
) -> Result<Response<EvmMsg>, ContractError> {
    let mut res = transfer_from(deps, env, info.clone(), owner, contract.clone(), amount)?;
    let send = Cw20ReceiveMsg {
        sender: info.sender.to_string(),
        amount: amount.clone(),
        msg,
    };

    res = res
        .add_message(cw20receive_into_cosmos_msg(contract.clone(), send)?)
        .add_attribute("action", "send_from");
    Ok(res)
}

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
