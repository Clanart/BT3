### Title
Out-of-bounds buffer read in CLVM atom length-prefix decoding during mempool canonical-form check - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` decodes an untrusted, spend-bundle-supplied CLVM atom length prefix by repeatedly indexing into `clvm_buffer` for `prefix_len` extra bytes without ever verifying that `offset` stays within `len(clvm_buffer)`. This mirrors the root cause of CVE-2024-26851: a length value taken directly from attacker-controlled wire data is used to drive a decode loop with no bound on how far it may read/shift past the buffer.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the leading byte to determine how many additional prefix bytes encode the atom length, then loops: [1](#0-0) 

```
atom_len = b & mask
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]
return 1 + prefix_len + atom_len, atom_len >= min_value
```
`prefix_len` can be up to 5 (for the `0b11111100` leading-byte case) [2](#0-1) , and nothing checks that `offset + prefix_len < len(clvm_buffer)` before dereferencing `clvm_buffer[offset]`. `is_clvm_canonical()`, the caller, walks the whole CLVM buffer atom-by-atom and calls `is_atom_canonical` whenever it sees an atom header byte `> 0x80`, again with no length validation before dispatch: [3](#0-2) . If a spend bundle's solution buffer is truncated so that a multi-byte atom-length header (e.g., trailing byte `0xF8`–`0xFC`) appears with fewer than `prefix_len` bytes remaining, the `for` loop in `is_atom_canonical` indexes past the end of `clvm_buffer`, raising an unhandled `IndexError`. This is the same bug class as `get_bitmap()` in the reported CVE: a decoder trusts a length value taken from untrusted bytes and uses it to drive further indexing/shifting without bounds checks, corrupting the decode instead of failing safely.

### Impact Explanation
`is_clvm_canonical` is used by the mempool manager's dedup-eligibility path when accepting a submitted spend bundle's solution for DEDUP-eligible spend processing (per the canonical-form documentation attached to this code) [4](#0-3) . A crafted, truncated solution buffer reaching this function from an unprivileged spend-bundle submission can raise an uncaught `IndexError` inside the mempool item admission path, which — if not caught by a broad try/except further up the call stack — halts processing of that transaction path (a spend-triggered transaction-processing/DoS condition) rather than being rejected as `INVALID_SPEND_BUNDLE` cleanly.

### Likelihood Explanation
I could not fully confirm the exact call site that invokes `is_clvm_canonical` (only the definitions and test-file references were located; the direct caller expression itself was not retrieved before the tool budget ran out), nor whether the mempool manager wraps this call in a broad exception handler that would downgrade the crash to an ordinary rejection. This is a material uncertainty: if callers already wrap spend-bundle processing in try/except covering generic exceptions, the practical impact is limited to a single bundle's rejection rather than a broader processing halt. Given this, I can prove the missing-bounds-check root cause with high confidence, but not the full severity/likelihood of the downstream crash without further verification of the caller and its error handling.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access (validate `offset + prefix_len < len(clvm_buffer)` up front, or catch `IndexError` and treat it as "not canonical"/malformed) so truncated buffers are rejected gracefully rather than raising an unhandled exception. Ensure `is_clvm_canonical`'s caller in the mempool path converts any decoding failure into a normal spend-bundle rejection (e.g., `Err.INVALID_SPEND_BUNDLE`) instead of propagating an exception.

### Proof of Concept
Construct a CLVM solution buffer ending in a header byte requiring a 5-byte length continuation, but supply fewer trailing bytes, e.g.:
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xFC signals a 5-extra-byte length prefix, but only 2 bytes follow
buf = b"\xfc\x01\x02"
is_clvm_canonical(buf)  # raises IndexError instead of returning False
```
Submitting a spend bundle whose solution serializes to end in such a truncated multi-byte atom header would trigger this same unhandled `IndexError` if reached via the dedup-eligibility canonical check in mempool admission.
