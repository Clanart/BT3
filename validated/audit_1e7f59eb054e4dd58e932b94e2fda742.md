Deterministic reuse of the cached FROST preprocess across repeated `sign()` invocations leaks the validator's MuSig secret key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The "malformed PONG" CVE is a stale-state reuse: freed data is accessed again after its logical lifetime ends. The direct Serai analog is in `SigningProtocol::preprocess_internal`, which stores a `CachedPreprocess` (a 32-byte ChaCha20 seed) in the DB keyed only by `context = (b"DkgConfirmer", attempt)` and re-loads it on every call. Because the seed fully determines the FROST nonces (`AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)`), every `share_internal` / `complete` invocation signs with byte-identical nonces. If the signing set or message differs between invocations — which can happen because `share()` and `complete()` are called at different times against whatever preprocesses are then on-chain — two signature shares are published that differ only in the challenge term, yielding direct recovery of the validator's secret key.

### Finding Description
`preprocess_internal` writes the seed to `CachedPreprocesses` once and never deletes it:

- `coordinator/src/tributary/signing_protocol.rs:123-145` — on cache hit it decrypts the same seed and calls `AlgorithmSignMachine::from_cache`, regenerating identical `nonces`/`Commitments`.
- `sign()` is reached twice for the same context: `DkgConfirmer::share` → `share_internal` → `preprocess_internal` (line 156), and later `DkgConfirmer::complete` → `share_internal` again (line 322), producing a second share with the same nonces.
- The nonce-reuse safety argument in the file header (lines 25-54) relies entirely on the received preprocesses and message being finalized identically by BFT, and explicitly notes the guard is incomplete: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (line 51), and a matching TODO for processor preprocesses (line 53). The bound "preventing partial rebuilds" is stated but not enforced in code.
- `msg = set_keys_message(set, removed, key_pair)` (lines 296-300) is supplied by the caller per-invocation, and the preprocess map is re-collected per call (lines 290-295 via `threshold_i_map_to_keys_and_musig_i_map`), so neither is bound into the cache key.
- In `crypto/frost/src/sign.rs:127-141`, `seeded_preprocess` derives all `Nonce`s deterministically from the seed, and `docs` (`spec/cryptography/FROST.md:51-62`) confirm reuse recovers the private key share.

The result: two executions of `AlgorithmSignMachine::sign` (line 283-310) produce shares `s_i = k + c_i·λ·sk` with identical `k` but `c_1 ≠ c_2` whenever the included participant set (which changes `R` and the `rho` binding factors) or `msg` differs between calls. `sk = (s_1 - s_2) / ((c_1 - c_2)·λ)` — full recovery of the validator's long-term MuSig/Ristretto secret key, the root of trust for the coordinator.

### Impact Explanation
Both shares are published to the tributary chain, so any observer — a fully unprivileged party who only reads finalized blocks — can recover the validator's private key once two divergent `sign()` executions occur. This is the validator key used as the root of trust for DKG confirmation signing (`musig(musig_context(...), self.key, participants)`, line 119), not an ephemeral share; compromise enables forging any future MuSig participation by that validator.

### Likelihood Explanation
Divergence between the two `sign()` executions requires the signing set or `key_pair` to differ between the `share` and `complete` calls, or a partial rebuild that re-executes with different on-chain data. The code itself flags that the defensive check ensuring this cannot happen is a TODO, and the safety argument rests on unstated assumptions about process rebuilds rather than code invariants. Reachability is the main caveat: the preprocess contents are contributed by validators, so forcing a divergent set plausibly requires a validator posting preprocesses at specific times (a borderline malicious-validator scenario per the scope rules) — though no adversary is needed if on-chain timing alone changes the accumulated map between `share` and `complete`, and the shares are publicly observable regardless.

### Recommendation
Delete `CachedPreprocesses::get(self.txn, &self.context)`'s entry once `share_internal` consumes it (a single-use take), and/or bind the decided commitments into the share: before publishing a share, verify on-chain that the preprocess commitments derived from the cached seed match the ones this validator already published for the context (the TODO at line 51), aborting rather than re-signing. Additionally, key the cache by `(context, spec.set(), msg digest)` so a different message or set can never regenerate the same nonces.

### Proof of Concept
1. Validator V's coordinator reaches `DkgConfirmer::share(preprocesses_A, key_pair)`; `preprocess_internal` stores seed `S` under `("DkgConfirmer", attempt)` and `sign()` emits share `s_1 = k + c_A·λ·sk` (broadcast on-chain).
2. Before `complete` runs, the on-chain preprocess map changes to `preprocesses_B` (a superset/different subset — new preprocesses finalized between the two calls), or a partial rebuild re-executes against different data.
3. `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` calls `share_internal` → `preprocess_internal`, reloads the same seed `S`, and `sign()` emits `s_2 = k + c_B·λ·sk` with `c_B ≠ c_A` (different `R`/binding factors).
4. Observer computes `sk = (s_1 - s_2)·((c_A - c_B)·λ)^{-1}` using the published `R`, `group_key`, and message to recompute `c_A`, `c_B` — recovering V's secret key from chain data alone.
