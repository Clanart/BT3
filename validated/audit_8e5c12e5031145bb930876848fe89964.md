## Finding: TOCTOU on `oauthState` allows a duplicate OAuth code exchange before the session is invalidated - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.resolveOAuthRequest` validates the CSRF `state` and then performs the token exchange, but it never synchronously "consumes" (nulls out) `this.state.oauthState` before awaiting the network call. The state is only replaced with `SignInStep.Success` inside the `.then()` handler of the `Promise` created in `authenticateWithBrowser`, which runs after `onAuthCompleted` resolves and a microtask tick elapses.

### Finding Description
`resolveOAuthRequest` performs its state check synchronously, but the code path from the check to the actual invalidation of `oauthState` spans an `await`: [1](#0-0) 

Specifically:
- Line 341 checks `this.state.oauthState.state !== action.state` — this is the only guard against replay.
- No flag (e.g. "already redeemed") is set before line 349's `await requestOAuthToken(endpoint, action.code)`.
- `this.state.oauthState` is only cleared when the surrounding `Promise` in `authenticateWithBrowser` settles and its `.then()` callback runs, transitioning to `SignInStep.Success`: [2](#0-1) 

Because the invalidation happens asynchronously (after a promise settle + microtask), a second `resolveOAuthRequest` invocation carrying the same (still-valid) `state` value but a different `code` can run its synchronous prefix — including the line 341 check — before the first invocation's continuation clears `oauthState`. Both invocations will then independently call `requestOAuthToken(endpoint, code)`, i.e. two authorization codes get redeemed against the same CSRF session instead of one.

### Impact Explanation
`onAuthCompleted` (`resolve`) and `onAuthError` (`reject`) are the *same* function references captured once per `authenticateWithBrowser` call, so JS `Promise` resolution semantics make the second `resolve()`/`reject()` call a no-op once the promise has already settled — whichever code exchange completes first "wins" the account binding, per [3](#0-2) . This limits, but does not eliminate, exploitability: an attacker who can race a second callback in before the first settles could have their own authorization code exchanged and their account bound to the user's Desktop app instead of the legitimate one, matching the "unauthorized account binding" impact category.

However, this scenario still fundamentally depends on the attacker already possessing the *current, unguessable* `csrfToken` (a `crypto.randomUUID()` value generated per sign-in attempt and never exposed to a passive attacker in the threat model given), plus being able to fire a second callback in the same narrow window before the promise settles. That second precondition is not naturally achievable from a remote/deep-link vector — deep-link / IPC callbacks from the OS to Electron's main process are dispatched as independent OS/IPC events, not synchronously batched JS calls, so winning this race from a real `x-github-client://oauth?...` deep link (as opposed to directly calling `resolveOAuthRequest` twice in a unit test) is not demonstrated to be practically achievable here.

### Likelihood Explanation
Low. The code-level TOCTOU is real (no single-use/consumed flag is set synchronously), but exploitation requires both (1) knowledge of the current unpredictable CSRF `state` value and (2) winning a very narrow, real-world-unlikely race between two OS-level deep-link deliveries before the first `Promise` settles — a condition the report's own reproduction relies on by calling the internal method twice programmatically rather than demonstrating it via genuine OS deep-link delivery.

### Recommendation
Consume `oauthState` synchronously as soon as the CSRF check passes, before any `await`, e.g. by capturing `oauthState` into a local variable and immediately calling `this.setState({ ...this.state, oauthState: undefined })` (or an explicit "redeemed" flag) prior to invoking `requestOAuthToken`. This closes the TOCTOU window entirely regardless of timing/race feasibility.

### Proof of Concept
```ts
// two resolveOAuthRequest calls issued back-to-back with the same state
signInStore.resolveOAuthRequest({ name: 'oauth', code: 'legit-code', state: csrfToken })
signInStore.resolveOAuthRequest({ name: 'oauth', code: 'attacker-code', state: csrfToken })
// Assert requestOAuthToken was invoked twice, once per code, before either promise settles
```

This confirms the missing single-use guard at `app/src/lib/stores/sign-in-store.ts:341` allows two token-exchange requests to be issued for one CSRF session, though converting this into an actual account-binding compromise via a real deep link additionally requires disclosure of the CSRF token and winning a race that is not demonstrated here.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
