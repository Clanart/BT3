### Title
Unauthenticated on-chain mirror URLs enable SSRF against DataLayer sync nodes - (File: chia/data_layer/data_layer_wallet.py)

### Summary
Any wallet holding a small amount of XCH can create a "mirror" coin for **any** DataLayer store `launcher_id` (not just their own) with attacker-chosen URL memos, because `DataLayerWallet.create_new_mirror()` performs no ownership check on the target `launcher_id` and no validation on `urls`. Nodes subscribed to that store id will later fetch those URLs unauthenticated during sync, giving an unprivileged spend-bundle submitter an SSRF vector against every peer node subscribed to the targeted store.

### Finding Description
`create_new_mirror()` at [1](#0-0)  builds a standard-wallet spend that creates a coin with `create_mirror_puzzle()` puzzle hash and memos `[launcher_id, *urls]`. There is no check that the caller's wallet actually owns/derived the singleton for `launcher_id` — it is taken as a raw parameter from the RPC caller (`chia/wallet/wallet_rpc_api.py` `dl_new_mirror` at lines 3255-3274, and CLI `add_mirror` in `chia/cmds/data.py`). Any coin owner can therefore attach mirror URLs to any store, including stores they don't operate.

When a node has this store subscribed, `DataLayer.update_subscriptions_from_wallet()` pulls all mirrors for the `launcher_id` from wallet RPC and stores their URLs as `ServerInfo` records without any scheme/host validation [3](#0-2) . During the periodic sync loop, `fetch_and_validate()` randomly selects one of these `ServerInfo` entries and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an `aiohttp.ClientSession.get(server_info.url + "/" + filename, ...)` request with no allow-list of hosts/schemes [4](#0-3) , [5](#0-4) .

This lets an attacker who merely spends a coin (no special privilege) point victim nodes' outbound HTTP requests at internal-only endpoints (e.g. `http://127.0.0.1:<rpc_port>/...`, cloud metadata services, internal admin panels), matching the reported bug class: an unsanitized externally-supplied "location" reaching a fetch primitive with no host/scheme restriction (CWE-20), causing the victim process itself to make requests to arbitrary/internal resources on the attacker's behalf.

### Impact Explanation
Content returned from these requests is subsequently only accepted if it validates against the wallet-advertised Merkle root, so it cannot directly corrupt DataLayer state; however, the request itself constitutes SSRF from every subscribed peer's DataLayer service process. This can be used to probe/attack internal services reachable from the victim's network position (local RPC endpoints, internal-only HTTP services, cloud metadata endpoints), and consumes victim resources on attacker demand (repeated retries with backoff still recur every sync cycle). Because target selection (`launcher_id`) and destination (`url`) are both attacker controlled with no ownership check, this is reachable by any unprivileged wallet holder, not just store operators.

### Likelihood Explanation
High reachability: any user can call `dl_new_mirror` RPC (or `chia data add_mirror` CLI) against a `launcher_id` they don't own, paying only the mirror-coin amount + fee, no signing authority over the store's singleton required. Any node subscribed to that store — a normal, expected DataLayer usage pattern — will pick up and fetch the URL automatically during its periodic sync loop.

### Recommendation
Add an ownership/authorization check in `create_new_mirror()` (or at the RPC/CLI layer) requiring the caller to prove control of the targeted `launcher_id`'s singleton before permitting mirror creation, or otherwise clearly document mirrors as inherently public/untrusted and restrict `http_download()`/`get_downloader()` to validate URL scheme (only http/https) and disallow private/loopback/link-local address ranges (SSRF allow-list) before issuing requests in `chia/data_layer/download_data.py`.

### Proof of Concept
1. Attacker (any funded wallet) calls `dl_new_mirror` RPC with `launcher_id` set to a victim's store id (publicly visible on chain) and `urls=["http://127.0.0.1:<internal-port>/some/path"]`, paying a small fee.
2. Once confirmed, any node subscribed to that `launcher_id` calls `update_subscriptions_from_wallet()`, pulling this attacker-supplied URL into its `ServerInfo` list [3](#0-2) .
3. On the next `fetch_and_validate()` cycle, the node performs `aiohttp` `GET` to `http://127.0.0.1:<internal-port>/some/path` via `http_download()` [6](#0-5) , demonstrating the victim node making an outbound request to an attacker-chosen (potentially internal) destination it would not otherwise contact.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
