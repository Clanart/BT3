### Title
Referrer can front-run a referee's reward-triggering claim by transiently spiking `getUserTotalLocked` via `_lock`, inflating `userInfo.factor`/`totalBoostFactor` in `ReferralStorage`, and capture disproportionate boosted referral commission in `trigger()` before unwinding the stake via `startUnlock` - ([File: VLMGP.sol], [File: rewards/ReferralStorage.sol])

### Summary
`VLMGP._lock` synchronously calls `IReferralStorage.updateTotalFactor(_for)`, which recomputes `userInfo.factor = sqrt(getUserTotalLocked(_account))` and `totalBoostFactor` using the instantaneous, un-time-weighted locked balance. Since `ReferralStorage.trigger()` computes `_calBoosted(_referer) = BoostPoint * factor / totalBoostFactor` at the exact moment a referee's reward claim fires, a referrer can front-run that transaction with a large `lock`/`lockFor` call to spike their `factor`, capture an inflated share of `BoostPoint` baked irreversibly into `refererInfo.rewardAmount`, and then immediately call `startUnlock` to begin exiting the position.

### Finding Description
`_lock` in `VLMGP.sol` updates `totalAmount` and calls `depositVlMGPFor` before invoking `updateTotalFactor`: [1](#0-0) 

`updateTotalFactor` in `ReferralStorage.sol` reads `getUserTotalLocked` live and recomputes `factor`/`totalBoostFactor` with no time-weighting, cooldown, or minimum holding period: [2](#0-1) 

`trigger()` is invoked by `masterMagpie` when a referee's underlying reward is harvested, and it snapshots `_calBoosted(_referer)` at that instant to compute `refererAmount`, crediting it permanently to `refererInfo.rewardAmount`: [3](#0-2) [4](#0-3) 

Because `factor` is a pure snapshot of `getUserTotalLocked` with no time-integration (unlike typical boosted-vote/veToken designs that require sustained locking), an unprivileged referrer who observes a referee's pending claim transaction in the mempool can front-run it with `lock`/`lockFor` to inflate their own `factor` (and the shared `totalBoostFactor` denominator, which also dilutes other legitimate referrers' `_calBoosted` share for that block), let the referee's transaction execute `trigger()` with the inflated factor baked into `refererAmount`, and then call `startUnlock` immediately afterward. `startUnlock` also calls `updateTotalFactor(msg.sender)`, deflating the factor back down, but this happens **after** the reward has already been irreversibly added via `refererInfo.rewardAmount += refererAmount`: [5](#0-4) 

No modifier, `nonReentrant` guard, or reward-index/time-weighting mechanism in `updateTotalFactor` or `trigger()` prevents this: `_onlyVlMGP` and `_onlyMasterMagpie` only restrict the *caller identity*, not the timing/duration of the underlying lock, and `nonReentrant` on `lock`/`startUnlock` does not prevent sequencing across different transactions within the same block.

### Impact Explanation
This is a theft of unclaimed yield: the attacker (as referrer) captures a boosted commission percentage from `trigger()` that is not representative of a genuine sustained lock, extracting more MGP into `refererInfo.rewardAmount` (later claimable via `claimReward`) than the design intends for real long-term lockers. It also dilutes the `_calBoosted` share of other legitimate referrers during that block via the shared `totalBoostFactor` denominator. This matches the Immunefi "theft of unclaimed yield" impact class since the extra reward is claimable MGP that flows from the referral reward pool to an attacker who did not genuinely qualify for the boost.

### Likelihood Explanation
- Requires only unprivileged capital (MGP tokens the attacker owns) and the ability to front-run a mempool transaction — both explicitly permitted attacker capabilities per the rules.
- Requires an active referral code/relationship where the attacker is registered as a referrer (`userInfos[_referer].myCode != 0`), which is freely obtainable via `registerCode`.
- Requires visibility into a referee's pending claim transaction that will trigger `trigger()` (via `masterMagpie`), which is realistic on public mempools.
- Repeatable each time a referee's reward-triggering transaction is observable, though bounded by the attacker's available MGP capital and by the cooldown period imposed by `startUnlock`/`unlock` before actually reclaiming the locked MGP (real capital is temporarily locked, not a truly costless flash operation).

### Recommendation
Do not compute `factor` from a live, instantaneous `getUserTotalLocked` value. Instead, time-weight the boost factor (e.g., only count locked amounts that have been held for a minimum duration, or use a checkpoint/decay mechanism similar to veToken designs) so that `updateTotalFactor` cannot be manipulated by a same-block lock/unlock sequence. Alternatively, snapshot referrer factors periodically (e.g., once per epoch) rather than synchronously at `_lock`/`startUnlock` time, and/or debounce `trigger()`'s boosted computation against factor changes that occurred within the same block as the lock.

### Proof of Concept
Hardhat test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `ReferralStorage`, and MGP token; wire `referralStorage` into `VLMGP` via `setReferralStorage`.
2. Referrer (attacker) calls `registerCode` to get a code; Referee calls `useCode` to link to attacker.
3. Set up a scenario where a small legitimate lock exists for the attacker (baseline `factor`), and another legitimate referrer also holds a stable, long-term lock (to show dilution).
4. In a single block (via `hardhat_setAutomine(false)` + manual block mining, or a multicall bundling both), queue: (a) attacker's `lockFor`/`lock` call with a large MGP amount, (b) referee's action that causes `masterMagpie` to call `ReferralStorage.trigger(referee, amount)`, (c) attacker's `startUnlock` call to begin exiting.
5. Mine the block, then assert:
   - `refererInfo.rewardAmount` after `trigger()` reflects the inflated `factor`/`totalBoostFactor` ratio present only during step (a)-(b), not the attacker's steady-state `factor` before or after.
   - Compare against a control run where the attacker's lock only happens in a separate later block (no front-run) — `refererInfo.rewardAmount` should be materially lower, and the other legitimate referrer's implied `_calBoosted` share should be higher in the control run than in the exploited run (showing dilution).
   - Confirm `userInfo.factor` for the attacker reverts to a lower value immediately after `startUnlock` in the same block, proving the qualifying stake was transient.

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
