## Title
Attacker-controlled "theirs" content with embedded fake conflict-marker lines causes silent misapplication of Copilot-resolved conflict content, corrupting committed source - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot merge-conflict-resolution feature locates conflict hunk boundaries by scanning raw file bytes for lines matching `^<{7}`, `^={7}$`, and `^>{7}` twice, independently, in two different modules. Neither pass verifies that the matched delimiter is the *real* git-inserted marker rather than incidental text that happens to appear inside one side's own file content (e.g. a malicious "theirs" branch that includes a code comment, ASCII banner, or embedded diff excerpt containing 7+ `>` or `<` characters at the start of a line). Because a hostile branch fully controls its own file content, it can plant a line that satisfies the "closing marker" regex before the real `>>>>>>>` marker is reached. Both `extractConflictHunks` (used to build the prompt) and `reassembleResolvedFile` (used to splice the model's answer back into the file) will terminate the hunk at the fake marker, causing the real closing marker and the remaining genuine "theirs" content to fall outside any recognized hunk and be copied straight into the final file as ordinary content. The corrupted file is then written to disk and `git add`-ed without any marker-integrity check.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks the file line-by-line and, once inside a hunk, stops collecting "theirs" content at the **first** line matching `theirsMarker`: [1](#0-0) 

The same first-match approach is used independently in `reassembleResolvedFile`, which re-scans the on-disk raw content to find where to splice the model's resolved text back in: [2](#0-1) 

The marker regexes used to detect boundaries (`oursMarker`, `separatorMarker`, `theirsMarker`) only check that a line *starts* with 7+ of the marker character — they do not verify that the line was actually inserted by git as part of a real conflict marker (git appends a ref/label after the marker characters, but the regex only requires `(?:\s|$)`): [3](#0-2) [4](#0-3) 

Because "theirs" content is exactly the attacker's own committed file content (the incoming branch/PR being merged), an attacker can embed a line such as `>>>>>>>` (or `>>>>>>> anything`) inside a source file, comment, or fixture on their branch. When the victim merges that branch and a real conflict occurs anywhere in the file, both parsing passes will treat the attacker's fake line as the hunk's closing marker:
- `extractConflictHunks` truncates `theirsContent` early and silently drops the real closing marker line plus the rest of the genuine "theirs" text and any subsequent real conflict hunks from ever being sent to the model (they're never captured into any hunk, and the outer scan only recognizes hunks by seeing an `oursMarker` first, so this trailing content is invisibly skipped) — the model never even sees it, so it cannot resolve it correctly.
- `reassembleResolvedFile` performs the exact same premature-stop, so when the model's single resolved-hunk answer is spliced back in, the real remaining git-inserted `>>>>>>>` line and the real leftover "theirs" content, and potentially the markers of a following legitimate conflict hunk in the same file, are copied through **verbatim as ordinary file content** rather than being reassembled: [5](#0-4) 

The function's own documentation acknowledges that hunks are matched "by order, not by line number," which is exactly the invariant that breaks once the detected hunk count/boundaries diverge from what the model was actually shown, per the recommendation-style logic — no bound or consistency check is enforced between the two independent scans.

The corrupted `resolvedContent` is then written straight to disk and staged without any re-validation that conflict markers were fully and correctly resolved: [6](#0-5) 

### Impact Explanation
The result is silent corruption of what the user commits and pushes: leftover literal git conflict-marker text (e.g. a stray `>>>>>>> branch-name` line) or truncated/duplicated fragments of "theirs" content end up embedded directly in tracked source files, and — in files with multiple conflicts — a later legitimate hunk's model resolution can be spliced into the wrong location because the hunk index drifted. The parser's earlier validation step (`throws when resolvedContent still contains conflict markers`) only checks the *model's own output* for marker text; it never re-validates the final reassembled file against the original hunk boundaries, so this class of corruption is not caught before the file is written and `git add`-ed. Because the user sees a clean "conflicts resolved" dialog and the file no longer shows unresolved markers in Desktop's UI, the corruption ships silently into the commit/push.

### Likelihood Explanation
This requires no local access, malware, or leaked credentials — only that the victim merges/rebases a branch or PR from an untrusted remote (exactly the attacker-controlled-repository scenario) and uses the Copilot "Resolve conflicts" feature (gated by `enableCopilotConflictResolution` and requiring the user's own account, which is a normal, expected user action, not an unnatural step). Any conflicting file where the attacker's side contains a line beginning with 7+ `>` (or `<`/`=`) characters at the start of a line — plausible in generated diffs, ASCII banners, changelogs, or even accidental content — triggers the divergence.

### Recommendation
- Do not rely on bare regex prefix matching (`^>{7}`) to delimit hunks; instead reuse a single authoritative parse (e.g. reuse `extractConflictHunks`'s hunk boundaries/line indices) in `reassembleResolvedFile` instead of independently re-scanning raw content, so both passes can never diverge.
- After reassembly, re-validate that the output file contains none of the marker patterns and that the number of hunks consumed exactly equals the number of hunks originally extracted from that file; if it doesn't, fail closed (skip the file / require manual resolution) instead of writing partially-corrupted content.
- Consider anchoring the marker regexes to require the exact git-generated suffix format (label after the marker) rather than any line that merely starts with the repeated character, reducing accidental/attacker collisions.

### Proof of Concept
1. Attacker pushes a branch/PR where a tracked file's content includes a line `>>>>>>> `(7+ `>` chars) inside normal-looking text (e.g. in a markdown code sample or comment documenting git conflict markers).
2. Victim, with Copilot conflict resolution enabled, merges this branch into a branch that has a genuine, unrelated conflicting change earlier in the same file, producing a real conflict block:
```
<<<<<<< HEAD
victim's change
=======
attacker's change ... (contains a line consisting of 7+ '>' chars)
>>>>>>> attacker-branch
```
3. `extractConflictHunks` stops collecting `theirsContent` at the attacker's embedded `>>>>>>>`-like line instead of the real closing marker [1](#0-0) , so the model is shown a truncated/incorrect "theirs" side and never sees the real trailing marker or content.
4. `reassembleResolvedFile` performs the same early stop when splicing the model's answer back in [7](#0-6) , so the real `>>>>>>> attacker-branch` marker line and the remaining genuine content after it are copied through verbatim as normal file content into `resolvedContent`.
5. `app-store.ts` writes this corrupted content to disk and stages it via `git add` with no further marker/consistency validation [8](#0-7) , so the victim's next commit contains literal residual conflict-marker text / mis-resolved content.
