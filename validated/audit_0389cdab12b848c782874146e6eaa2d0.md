### Title
Index-based partial-commit line selection is silently re-applied to a re-fetched, unvalidated working-directory diff, corrupting what gets committed - ([File: app/src/lib/git/apply.ts])

### Summary
`PoolLib.getInsideFees` trusted a value read from possibly-stale/uninitialized on-chain state (`ticks`) and blindly used it in arithmetic without checking that it corresponded to the state that was actually used to derive the position, corrupting fee accounting. GitHub Desktop has a structurally identical broken invariant in the partial-commit path: a user's line selection (`DiffSelection`, stored purely as abstract line *indices*, not content-addressed) is computed against one snapshot of a file's diff, but at commit time the code silently re-fetches a *fresh* diff and re-applies the old index-based selection to it with no reconciliation or staleness check.

### Finding Description
`DiffSelection` in [1](#0-0)  tracks which lines are selected purely by integer `lineIndex` positions within a unified diff (`divergingLines: Set<number>`), with no binding to the actual line content or to a particular diff object/hash.

When the user views a file in the Changes view, the diff shown and used to build the selection is loaded and cached once via `_changeFileSelection`/`updateChangesWorkingDirectoryDiff`: [2](#0-1) . That diff (and the selection the user makes against it) is stored in `changesState.selection`.

When the user commits, `_commitIncludedChanges` passes the `WorkingDirectoryFileChange` objects (which only carry the `DiffSelection`, not the diff snapshot) into `createCommit` → `stageFiles` → `applyPatchToIndex`: [3](#0-2)  and [4](#0-3) .

Critically, `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it independently re-runs `getWorkingDirectoryDiff` against the current on-disk file state at commit time: [5](#0-4) . It then feeds that brand-new diff, together with the old index-based `DiffSelection`, straight into `formatPatch`, which resolves selection purely by `hunk.unifiedDiffStart + lineIndex` against the *new* diff's hunks: [6](#0-5) .

There is no check anywhere in this path that the diff used to build the selection is the same diff being patched. If the working tree file changes between the moment the user makes their line selection and the moment `applyPatchToIndex` re-reads the diff (e.g., different number/position of hunks, shifted line numbers, added/removed lines), the same integer indices now point at semantically different lines. The only defensive code present is a generic "faulty diff and/or faulty selection" guard that fires solely when the resulting patch is completely empty: [7](#0-6)  — it does not detect or prevent a non-empty but *wrong* patch being produced, so this guard does not stop the corruption path, mirroring how `PoolLib.getInsideFees` had no check that the read tick state matched the state the position was created against.

### Impact Explanation
Because the mismatch produces a syntactically valid, non-empty patch, `git apply --cached` succeeds silently. The user's commit and any subsequent push will silently contain different content than what the user selected and reviewed in the UI — potentially including lines the user explicitly deselected (e.g., secrets, debug code, unwanted changes) or excluding lines the user intended to commit. This is a silent corruption of what the user commits/pushes with no error surfaced to the user, matching the "silent corruption of what the user commits or pushes" impact category. It can be triggered by any external process that legitimately modifies a repository's working tree files after the user opens the diff for review — a common occurrence with build watchers, formatters/linters running on save, or generated files regenerating in the background — none of which require local/physical access, admin rights, or malware; the "attacker" primitive is a cloned/fetched repository configured to run such a watcher/generator as part of a normal, expected developer workflow (e.g., an npm script, webpack watch, or a git smudge/clean filter that rewrites tracked file content).

### Likelihood Explanation
The window between diff display/selection and commit is often nontrivial (users scroll, deliberate, switch files, wait for hooks), and Desktop's own architecture already anticipates file changes during diff loading, guarding against races in other spots (`_changeFileSelection` re-checks selection state after the diff loads, and `getLineFilters` explicitly comments on this exact race class: [8](#0-7) ). However, no equivalent staleness check exists in the commit-time patch application path (`app/src/lib/git/apply.ts`), so any legitimate concurrent file modification (build tooling, format-on-save, background regeneration) during that window will reliably reproduce the corruption without requiring any unusual attacker action.

### Recommendation
Bind `DiffSelection` (or the `WorkingDirectoryFileChange`) to the specific diff snapshot it was computed against (e.g., store a content hash or the diff object itself alongside the selection), and in `applyPatchToIndex`/`stageFiles` verify that the diff re-fetched immediately before staging matches the diff the selection was derived from. If it does not match, abort the partial-commit/stage operation, re-diff, and require the user to re-confirm their selection rather than silently applying stale line indices to new diff content.

### Proof of Concept
1. Modify a tracked file with several distinct changes and open it in the Changes view; Desktop loads and caches the diff via `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3404-3448`).
2. Deselect specific lines (e.g., a hunk containing sensitive debug output) using the line-selection UI, producing a `DiffSelection` with `divergingLines` recorded as raw indices.
3. Before clicking "Commit", have an external process (e.g., a formatter/watcher script bundled in the repo, or simply another editor autosave) rewrite the same file so that hunk boundaries/line counts shift (e.g., add or remove a blank line earlier in the file).
4. Click "Commit". `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff fresh from disk and calls `formatPatch` with the stale `DiffSelection` (`app/src/lib/patch-formatter.ts:129-161`).
5. Inspect the resulting commit: the previously deselected debug output (or other unintended content) is present in the commit, or content the user intended to include is missing — with no error shown to the user, confirming silent corruption of the committed diff.
