### Title
Checking out a Pull Request from a fork resolves the branch by name/URL only, with no SHA pinning against the reviewed PR metadata - ([File: app/src/ui/dispatcher/dispatcher.ts])

### Summary
The reported bug is a request/settlement TOCTOU: a user's action is authorized against a value snapshotted at request time (`response.value`/expected share price), but executed later against whatever value is current, with no bound (`minOutputAmount`) to guarantee the executed result matches what the user approved. The same broken invariant exists in GitHub Desktop's "checkout a pull request" flow: the PR metadata (fork clone URL + branch name) is fetched once, but the actual code that gets checked out is whatever the fork's ref currently resolves to at fetch/checkout time - with no verification that it still matches the `sha` from the PR object the user reviewed.

### Finding Description
`_findPullRequestBranch` in `app/src/lib/stores/app-store.ts` (around lines 8633-8721) receives `headCloneUrl` and `headRefName` (both attacker-controlled, since `headCloneUrl` points to the PR author's fork) and:
1. Adds/looks up a remote for `headCloneUrl`.
2. Fetches that remote if the branch isn't already known locally (`this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)`).
3. Resolves the branch purely by matching `remoteRef = ${remote.name}/${headRefName}` - i.e., by **name**, not by the PR's `head.sha`.
4. Returns that branch to `_checkoutPullRequest`, which calls `_checkoutBranch` on whatever commit the ref currently points to. [1](#0-0) [2](#0-1) 

Both call sites that trigger this - the deep-link "Open Repository from URL" handler and the branch-dropdown/PR-list checkout action - pass only `prNumber`, `headRepoOwner`, `headCloneUrl`, and `headRefName`; the PR's `head.sha` (fetched with the PR object) is never threaded through or re-checked after the fetch completes: [3](#0-2) [4](#0-3) 

`IPullRequestRef` explicitly models a `sha` field, confirming the SHA is known/available in the data model but simply not used as a pinning/verification value at checkout time: [5](#0-4) 

Between the moment the PR is fetched (`fetchPullRequest`) and the moment `_fetchRemote`/`_checkoutBranch` actually complete, the fork owner (an unprivileged, attacker-controlled party who fully owns their fork remote) can force-push new content to that same branch name. Desktop has no guard that compares the fetched branch tip against the `sha` seen when the user decided to check out the PR — it only matches by ref name/URL, so it will happily fetch and check out whatever the attacker has pushed by the time the fetch runs.

### Impact Explanation
This is exactly the "no minimum/expected-value" class of bug: the user approves an action (checking out PR #N, expecting the code they saw on GitHub.com or in the PR diff) based on a snapshot, but the enacted state can silently diverge because the executing code re-resolves the value (the branch tip) from a mutable, attacker-controlled source (the fork remote) instead of pinning to the reviewed SHA. Concretely:
- The user believes they checked out the PR content they reviewed; instead they get whatever the fork owner pushed last, which could contain malicious build scripts, hooks, or source changes.
- If the user subsequently builds/runs the project, or if any Desktop-triggered git hook or IDE auto-run executes on checkout, this becomes an execution-of-attacker-controlled-code path originating purely from a normal "Open PR" / deep-link interaction.
- This also matches the explicitly in-scope category "a cloned/fetched repository ... attacker controls" and "a link or deep link the user clicks" (`openPullRequestFromUrl` is reachable via the `x-github-client://openrepo` deep link).

### Likelihood Explanation
Likelihood is realistic and requires no privileged access: any GitHub user can open a PR from their own fork, wait for a victim to click "Open in Desktop" (or select the PR in Desktop's PR list/dropdown), and force-push new commits to the PR branch in the window between the victim's review and Desktop's fetch/checkout. Desktop's own remote-fetch logic (`_fetchRemote`) always pulls the live ref rather than a pinned commit, so the race window is inherent to the flow, not a rare edge case.

### Recommendation
Thread the PR's `head.sha` (already present in `IPullRequestRef`) through `_checkoutPullRequest`/`_findPullRequestBranch`, and after fetching the fork's branch, verify the resolved branch tip's SHA matches the expected `head.sha` before calling `_checkoutBranch`. If it doesn't match (i.e., the fork was updated since the PR data was fetched), surface a warning to the user (similar to a "the pull request has changed since you reviewed it, refresh and confirm" prompt) instead of silently checking out the new tip - mirroring the recommended `minOutputAmount`-style guard from the original report, adapted to "expected commit SHA" pinning.

### Proof of Concept
1. Attacker (fork owner) opens PR #N against a victim-relevant repo from `attacker/fork` branch `feature`, with benign-looking commit `A`.
2. Victim reviews PR #N on GitHub.com, decides to test it locally, and clicks "Open in Desktop" (`x-github-client://openrepo/...&pr=N`) or selects it from Desktop's PR list.
3. This invokes `openPullRequestFromUrl` → `appStore.fetchPullRequest` → obtains PR metadata with `head.clone_url`, `head.ref='feature'`, `head.sha='A'`. [6](#0-5) 
4. Before Desktop's `_refreshRepository`/`_fetchRemote` step completes, attacker force-pushes malicious commit `B` (e.g., adding a malicious `pre-commit`/build script or altering source) to `attacker/fork:feature`.
5. `_findPullRequestBranch` fetches the remote and resolves `remote/feature` to commit `B` purely by ref name, with no comparison against the originally-fetched `sha='A'`: [7](#0-6) 
6. `_checkoutPullRequest` checks out commit `B` without any warning that it differs from the reviewed PR content. [1](#0-0) 

Note: I could not fully trace `appStore.fetchPullRequest`'s exact implementation (only its call sites were located via search within the given iteration budget), so the precise timing window between PR-object fetch and remote fetch is inferred from the surrounding code rather than directly read line-by-line; a follow-up session with full file access would be needed to confirm exact elapsed-time bounds.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }

  public async checkoutPullRequest(
    repository: RepositoryWithGitHubRepository,
    pullRequest: PullRequest
  ): Promise<void> {
    if (pullRequest.head.gitHubRepository.cloneURL === null) {
      return
    }

    return this.appStore._checkoutPullRequest(
      repository,
      pullRequest.pullRequestNumber,
      pullRequest.head.gitHubRepository.owner.login,
      pullRequest.head.gitHubRepository.cloneURL,
      pullRequest.head.ref
    )
  }
