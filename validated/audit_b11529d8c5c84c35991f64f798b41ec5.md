### Title
Unsynchronized read of mutex-protected `auctionEntryPointVersion` in `getBidTxGasLimit()` allows a data race that can corrupt bid gas-limit calculation - (File: kaiax/auction/impl/bid_pool.go)

### Summary
`BidPool.getBidTxGasLimit()` takes the `auctionInfoMu` read lock only to copy out `bidTxGasBuffer`, then releases the lock and immediately reads the sibling field `bp.auctionEntryPointVersion` without holding any lock, even though that field is protected by the same `auctionInfoMu` and is concurrently written by `updateAuctionInfo()`. This mirrors the reported bug class: a shared buffer/field accessed by a "gauge"-style helper without the lock that guards it, invoked on a recurring background cadence (here, block-insertion driven `updateAuctionInfo`) while user-triggered code paths read it concurrently.

### Finding Description
`BidPool` guards `auctioneer`, `auctionEntryPoint`, `auctionEntryPointVersion`, and `bidTxGasBuffer` with `auctionInfoMu`. [1](#0-0) 

`updateAuctionInfo()` takes the write lock and mutates all four fields together, including `auctionEntryPointVersion`, on every new block via `PostInsertBlock`: [2](#0-1) [3](#0-2) 

However, `getBidTxGasLimit()` only protects the `bidTxGasBuffer` read with `RLock`/`RUnlock`, then releases the lock before reading `bp.auctionEntryPointVersion` directly (used to build call data), leaving that read completely outside the critical section: [4](#0-3) 

This is invoked from `AddBid()`, the code path reached whenever an unprivileged searcher submits a bid to the auction bid pool (via RPC `SubmitBid` or gossip through `HandleBid`): [5](#0-4) [6](#0-5) 

Similarly, `validateBidSigs()` reads `bp.auctionEntryPoint` and `bp.auctioneer` under `auctionInfoMu.RLock()` correctly, but the immediately-following `getBidTxGasLimit()` call reads `auctionEntryPointVersion` unprotected right after — this is the exact "read the buffer, but not under lock" pattern from the reported issue, just applied to a `string` field instead of a `[]byte` buffer.

### Impact Explanation
Because `auctionEntryPointVersion` is a Go `string` (a pointer+length pair), a concurrent unsynchronized read/write can observe a torn value (e.g., correct length with a stale/foreign pointer, or vice versa) under the Go memory model, which is technically undefined behavior and can produce garbage bytes rather than one of the two well-formed versions ("v2.1" or "v3.0"). `EncodeAuctionCallData` selects the ABI encoding path based on this string, so a torn read could select the wrong encoder/selector for the bid, producing a `CallData`/gas-limit computation inconsistent with what other nodes (which read the field consistently, e.g., under the lock in `validateBidSigs`) compute for the same bid. Because gas-limit and call-data correctness feed directly into whether the bid transaction executes successfully and how much gas is reserved, this can cause state divergence between honest nodes processing the same bid/block, or cause a bid to be wrongly encoded/rejected/accepted, undermining the auction settlement integrity that unprivileged searchers and the fee mechanism depend on.

### Likelihood Explanation
The unsynchronized read happens on essentially every bid submission (`AddBid` → `getBidTxGasLimit`), which is directly reachable by any unprivileged auction bidder submitting a bid transaction, so the exposure is high-frequency. The write side (`updateAuctionInfo`) runs on every block via `PostInsertBlock`, which also happens continuously. The race window is therefore hit any time a bid is being processed during a block boundary where the auction entry point version changes (e.g., during a v2.1→v3.0 upgrade), which is a realistic, externally triggerable condition rather than a purely theoretical one — though it does require a version transition to occur to produce an observably different outcome (outside of a transition, both values read are identical, so undefined behavior manifests without an app-visible symptom most of the time). This constrains the practical likelihood of an exploitable divergence to the (rare but real) migration window.

### Recommendation
Extend the `auctionInfoMu.RLock()` critical section in `getBidTxGasLimit()` to also cover the read of `bp.auctionEntryPointVersion`, i.e., copy both `bidTxGasBuffer` and `auctionEntryPointVersion` into local variables while holding the lock, then use only the local copies for the subsequent `EncodeAuctionCallData` call and gas computation — analogous to creating a thread-safe accessor as recommended in the reported analog.

### Proof of Concept
Conceptual PoC (data race, detectable with `go test -race`):
1. Goroutine A repeatedly calls `bp.AddBid(bid)` for valid bids, which internally calls `getBidTxGasLimit()` reading `bp.auctionEntryPointVersion` unprotected.
2. Goroutine B repeatedly calls `bp.updateAuctionInfo(auctioneer, entryPoint, "v3.0", buffer)` alternating with `"v2.1"`, simulating `PostInsertBlock` updates across a version-upgrade block boundary.
3. Running both concurrently under Go's race detector flags a data race on `auctionEntryPointVersion` between `getBidTxGasLimit` (unprotected read at line 490) and `updateAuctionInfo` (protected write at line 209), confirming the field is accessed outside its designated mutex in the exact pattern described in the reported issue. func (bp *BidPool) updateAuctionInfo(auctioneer common.Address, auctionEntryPoint common.Address, auctionEntryPointVersion string, bidTxGasBuffer uint64) {
	bp.auctionInfoMu.Lock()
	defer bp.auctionInfoMu.Unlock()

	if bp.auctioneer == auctioneer && bp.auctionEntryPoint == auctionEntryPoint && bp.auctionEntryPointVersion == auctionEntryPointVersion && bp.bidTxGasBuffer == bidTxGasBuffer {
		return
	}

	// Clear the existing auction pool since the auctioneer or auction entry point address is changed.
	bp.clearBidPool()

	bp.auctioneer = auctioneer
	bp.auctionEntryPoint = auctionEntryPoint
	bp.auctionEntryPointVersion = auctionEntryPointVersion
	bp.bidTxGasBuffer = bidTxGasBuffer

	logger.Info("Update auction info", "auctioneer", auctioneer, "auctionEntryPoint", auctionEntryPoint, "auctionEntryPointVersion", auctionEntryPointVersion, "bidTxGasBuffer", bidTxGasBuffer)
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (a *AuctionModule) PostInsertBlock(block *types.Block) error {
	if a.Downloader.Synchronising() || !a.ChainConfig.IsRandaoForkEnabled(block.Number()) {
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}

	if !a.updateAuctionInfo(block.Number()) {
		logger.Debug("stop auction since auctioneer or auction entry point is not set")
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}

	atomic.CompareAndSwapUint32(&a.bidPool.running, 0, 1)

	txHashMap := make(map[common.Hash]struct{})
	for _, tx := range block.Transactions() {
		txHashMap[tx.Hash()] = struct{}{}
	}
	a.bidPool.removeOldBids(block.Number().Uint64(), txHashMap)

	return nil
}

// updateAuctionInfo updates the auctioneer address and auction entry point address for the given block number.
// It expects the `num` is after Randao fork.
// It returns true if the non-zero auctioneer address and auction entry point address are set, otherwise false.
