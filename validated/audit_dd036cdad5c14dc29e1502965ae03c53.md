### Title
`update_finalized_payouts` attributes a payout to an operator based solely on an unsigned OP_RETURN pubkey, letting an attacker-funded payout consume a victim operator's kickoff/round slot - (File: core/src/verifier.rs, core/src/task/payout_checker.rs, core/src/operator.rs)

### Summary
`PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered by the local operator's own `xonly_public_key`, and if a matching row exists it unconditionally calls `Operator::handle_finalized_payout` and `Operator::end_round`, consuming that operator's round/kickoff resources. The row is populated by `update_finalized_payouts`, which reads the OP_RETURN xonly-pubkey embedded in the on-chain payout transaction with no cryptographic proof (Schnorr signature) that the named operator actually authored/funded that transaction, so anyone able to broadcast a Bitcoin transaction can attribute a payout to an arbitrary operator's pubkey.

### Finding Description
The binding that should hold is:
`operator_credited_with_payout(OP_RETURN.xonly_pk) == operator_who_actually_funded_the_payout_tx`

Trace:
- `send_asserts` in `core/src/operator.rs:1275-1296` only checks `payout_op_xonly_pk != kickoff_data.operator_xonly_pk` — a comparison between two values both ultimately derived from the DB row written from the OP_RETURN and from the operator currently broadcasting the kickoff — it never checks a Schnorr signature from that operator over the payout transaction. [1](#0-0) 
- `PayoutCheckerTask::run_once` fetches `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)`, and on any hit proceeds to `handle_finalized_payout`, `end_round`, and `mark_payout_handled` without any independent verification that the operator whose pubkey appears in the OP_RETURN actually broadcast/funded the payout input. [2](#0-1) 
- Because Bitcoin places no restriction on who can construct a transaction paying an arbitrary withdrawal output with an arbitrary OP_RETURN payload, an unprivileged attacker (who is explicitly permitted to "choose the bytes of a withdrawal UTXO ... an OP_RETURN") can fund the withdrawal payout themselves while embedding a victim operator's `xonly_pk` in the OP_RETURN instead of their own.
- None of the checks enumerated in the audit scope (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr` on payout attribution, `is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, `lc_proof_verifier`, watchtower flags) validate that the OP_RETURN-named operator is cryptographically tied to the payout transaction; they validate deposit legitimacy, L2 state correctness, and chain inclusion — none of them bind "named operator" to "actual funder."
- Once the victim operator's own automation (`PayoutCheckerTask`, running under that operator's own signer/xonly key) observes the spoofed OP_RETURN, it will itself call `end_round`/`handle_finalized_payout` and progress its round/kickoff cycle for a payment it never made, consuming `used_kickoff_connectors` for that round.

### Impact Explanation
This lets an unprivileged attacker force an honest operator's round/kickoff resource to be consumed and the operator's own reimbursement pipeline (kickoff → assert → payout proof) to fire for a withdrawal the operator never funded. Because the payout to the withdrawer was genuinely fulfilled (by the attacker's own funds), the on-chain/storage-proof checks that gate reimbursement (proof the withdrawal's L2 event and matching Bitcoin payout exist) will pass, and the operator ends up reimbursed by the bridge's collateral for a payout it never funded — matching the Critical category "an operator reimbursed for a payout it never funded." This is repeatable per-withdrawal and can be targeted at any specific operator whose `xonly_pk` is known (operator pubkeys are public), draining a chosen operator's kickoff/round slots and/or triggering unjustified reimbursements at the bridge's expense across arbitrary deposits/withdrawals.

### Likelihood Explanation
The attacker needs no special privilege: only the ability to fund a Bitcoin transaction that satisfies the withdrawal's payout conditions (amount/recipient) and to embed a victim operator's public `xonly_pk` in the OP_RETURN output, which the prompt explicitly grants ("choose ... a Schnorr signature and its sighash flag, an OP_RETURN"). Cost is the withdrawal amount plus fees (which is also the cost a legitimate front-runner would pay), and each attempt is deterministic and repeatable against any operator whose pubkey is publicly known, for any withdrawal the attacker chooses to front. No mainnet or live Citrea deployment specifics are required — it works against the standard payout-attribution flow.

### Recommendation
Require a Schnorr signature from the operator named in the payout OP_RETURN (e.g., over the payout txid/withdrawal index) before `update_finalized_payouts` records the payout as attributable to that operator, or otherwise cryptographically bind the payout transaction to the operator (for example, require the payout input to be spent from a script/key path only that operator controls, verified via `SECP.verify_schnorr`) before `PayoutCheckerTask` is allowed to consume that operator's round/kickoff slot.

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }
