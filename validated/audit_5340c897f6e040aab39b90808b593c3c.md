### Title
First-staker sandwich of queued rewards via public `donateRewards` flush - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
When `queueNewRewards()`/`donateRewards()` is called while `totalStaked() == 0`, the reward amount is parked in `queuedRewards` instead of being distributed. `_provisionReward` only flushes `queuedRewards` into `rewardPerTokenStored` on the *next* call to `_provisionReward` — not on stake/deposit events — and this flush attributes the entire queued amount to whatever `totalStaked()` is *at flush time*. Because `donateRewards` is a public, permissionless function that also triggers `_provisionReward`, an attacker who is the sole staker at that moment can trigger the flush themselves and capture the whole queued pool.

### Finding Description
`_provisionReward` (rewards/BaseRewardPoolV2.sol:290-314) routes new rewards to `queuedRewards` when `totalStaked() == 0`: [1](#0-0) 

The queued amount is only merged into `rewardPerTokenStored` the next time `_provisionReward` runs, and it is divided by whatever `totalStaked()` is at that exact call, with no time-weighting or vesting:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingTokenDecimals) / totalStaked();
```
Critically, `donateRewards` (rewards/BaseRewardPoolV2.sol:255-260) is callable by **anyone** (`isRewardToken` check only, no `onlyManager`) and calls `_provisionReward` directly: [2](#0-1) 

Exploit flow:
1. A manager/legit reward source calls `queueNewRewards(largeAmount, token)` while `totalStaked() == 0`. This is an external event the attacker doesn't need to control (they only need to observe it, e.g. via mempool or state).
2. Attacker front-runs all other stakers and stakes a minimal amount through `MasterMagpie`, becoming the sole staked balance (`balanceOf`/`totalStaked()` now equal attacker's tiny deposit). At this point `userRewardPerTokenPaid` for the attacker is set to the current (pre-flush) `rewardPerTokenStored`.
3. Attacker calls `donateRewards(1, token)` (or any dust amount) themselves. Since `totalStaked() > 0` now, `_provisionReward` flushes the entire accumulated `queuedRewards` into `rewardPerTokenStored`, dividing by `totalStaked()` — which is only the attacker's minimal stake.
4. Attacker calls `getReward()` and receives the entire queued reward pool, which was intended to be shared pro-rata with all subsequent stakers.

Existing checks do not stop this: `getReward`/`getRewards` are gated by `onlyMasterMagpie` and `updateReward`/`updateRewards` modifiers, but these only compute earned rewards correctly according to the (manipulable) `rewardPerTokenStored` — they don't prevent the sole-staker capturing a flush triggered by their own permissionless `donateRewards` call. There is no minimum stake duration, no vesting/streaming of queued rewards, and no restriction on who can trigger the flush.

### Impact Explanation
Direct theft of user funds / theft of unclaimed yield: rewards contributed by protocol/managers and meant to be shared pro-rata among all future stakers can be entirely captured by a single attacker with minimal capital, at the expense of legitimate stakers who would otherwise have received a share. This matches Immunefi's "theft of unclaimed yield" / "direct theft of user funds" impact class.

### Likelihood Explanation
- Requires `totalStaked() == 0` at the time of a `queueNewRewards` call — plausible in new pools, freshly-migrated pools, or pools that experience full withdrawal before new incentives are queued.
- Attacker needs only capital for a minimal stake (can be extremely small, even 1 wei of staking token if allowed) plus dust amount of reward token for `donateRewards`.
- Fully repeatable whenever a pool transitions through zero-TVL before a reward injection, and requires no privileged role — attacker only needs public `stake`/`deposit` via MasterMagpie and the permissionless `donateRewards` function.
- Front-running is straightforward via mempool monitoring or bundle inclusion.

### Recommendation
- Restrict `donateRewards` (or any trigger of `_provisionReward`) so the flush of `queuedRewards` cannot be manipulated by a single, just-arrived minimal staker — e.g., require a minimum elapsed time or minimum total-staked threshold before flushing queued rewards, or stream `queuedRewards` linearly over time rather than allocating it instantaneously to whatever `totalStaked()` is when the next provision call happens.
- Alternatively, only allow trusted managers to trigger the flush (remove public `donateRewards`, or make it also gate on `totalStaked() == 0` else revert / defer), and/or snapshot minimum lock-up before newly staked balances become eligible for pre-existing queued rewards.
- Consider tracking "queued reward eligibility" per reward epoch so only stakers present when the reward was queued (or over a fair distribution window) can claim it.

### Proof of Concept
Foundry test plan:
1. Deploy `BaseRewardPoolV2` with a mock staking token and mock `MasterMagpie` returning `balanceOf`/`totalStaked` based on real transfers.
2. Ensure `totalStaked() == 0`.
3. As `manager`, call `queueNewRewards(1_000_000e18, rewardToken)` — assert `rewards[rewardToken].queuedRewards == 1_000_000e18` and `rewardPerTokenStored == 0`.
4. As `attacker`, stake `1` wei of staking token via `MasterMagpie` (assert `totalStaked() == 1`).
5. As `attacker`, call `donateRewards(1, rewardToken)` — assert `rewardPerTokenStored` jumps to reflect `(1_000_000e18 + 1) * 10**decimals / 1`.
6. As `attacker`, call `getReward(attacker, attacker)` via `MasterMagpie` — assert attacker receives ~`1_000_000e18` reward tokens.
7. Have a second, legitimate staker deposit afterward and assert they receive 0 of the originally queued reward, confirming the pro-rata sharing invariant was broken.
