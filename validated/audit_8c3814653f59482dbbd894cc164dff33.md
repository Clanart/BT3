## Finding

### Title
IntentGateway's `_paused` circuit breaker is stored but never enforced, allowing fund drains to continue after an incident is flagged — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase.sol` declares a `_paused` storage flag intended as an emergency circuit breaker for the IntentGateway, but no function in the gateway (`placeOrder`, `fillOrder`, `cancelOrder`, `select`) ever checks it. This is the same root cause as the external `StakedToken.cooldown()` report: a pause is expected to gate an action that moves or commits value, but the enforcement is missing, so users can continue interacting with the system during a period when operators believe (and signal) that it is halted.

### Finding Description
`IntentsBase` reserves a dedicated pause flag: [1](#0-0) 

The comment "Appended last to preserve existing storage slots" indicates this was deliberately added to the storage layout for an upgradeable proxy, implying it was meant to be wired into pause logic. However, across the entire `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents`/`IntentGatewayV2` composition, `_paused` is never read. The three externally reachable, fund-moving entry points have no pause guard at all:

- `placeOrder` (escrows user funds) is guarded only by `nonReentrant`: [2](#0-1) 
- `fillOrder` (releases escrowed inputs to a solver) is guarded only by `nonReentrant`: [3](#0-2) 
- `cancelOrder` (refunds escrow) is guarded only by `nonReentrant`: [4](#0-3) 

By contrast, the SDK's `HyperFungibleToken`/`HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken` apps correctly implement OpenZeppelin's `Pausable` and gate `send`, `onAccept`, `onPostRequestTimeout`, `transfer`, and `transferFrom` with `whenNotPaused`: [5](#0-4) 

This confirms pausing is a recognized safety pattern elsewhere in the codebase for exactly this class of app (escrow-and-release cross-chain value transfer), but the pattern was not carried into `IntentGatewayV2`'s `_paused` flag — it's dead state.

### Impact Explanation
If operators detect an active exploit against the IntentGateway (e.g., a malicious `priceOracle`, a `CallDispatcher` bug being abused via `predispatch`/postdispatch calldata, or a compromised solver draining escrow), the intended mitigation is to flip `_paused` to stop new `placeOrder`/`fillOrder`/`cancelOrder` calls. Because no code path reads `_paused`, this "emergency stop" has zero effect: an attacker (or a user racing to exploit a known bug) can continue to place orders, fill orders, and drain or manipulate escrow exactly as before the pause was set. This mirrors the external report's core failure mode — a state-mutating, fund-affecting action that should be blocked during an emergency window is not — except here the blast radius is direct fund custody (escrowed inputs, solver payouts, fee-token balances) rather than a staking/slashing accounting delta.

### Likelihood Explanation
Low-to-moderate: this only matters at the moment governance/operators believe they have paused the gateway in response to an incident. It requires an existing separate vulnerability or malicious actor to be actively exploiting the gateway; the missing enforcement removes the last line of defense during that window, extending or making possible additional fund loss that a working pause would have stopped.

### Recommendation
Wire `_paused` into an actual guard (e.g., a `whenNotPaused` modifier, matching the pattern already used in `HyperFungibleToken`/`WrappedHyperFungibleToken`) and apply it to `placeOrder`, `fillOrder`, `select`, and the cancel paths that move funds. Ensure a governance-only setter (via `onAccept`/`UpdateParams` or a dedicated admin path) exists to toggle `_paused`, and add tests asserting that these entry points revert while paused, analogous to `HyperFungibleTokenTest.testSendRevertsWhenPaused`.

### Proof of Concept
1. Governance/operators observe an active exploit (e.g., a malicious `priceOracle` or a solver abusing `output.call` postdispatch execution) and set `_paused = true` (assuming a setter were added, or simply note the flag is set by whatever mechanism was intended).
2. An attacker calls `IntentGatewayV2.placeOrder`/`fillOrder`/`cancelOrder` directly.
3. None of these functions check `_paused`; execution proceeds normally — escrow is created, released, or refunded — because `_paused` is read nowhere in `IntentsBase.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`, or `IntentGatewayV2.sol` [1](#0-0) .
4. The attacker continues exploiting the underlying vulnerability during the entire window operators believed the contract was halted, resulting in additional stolen or misdirected escrow funds.

     * @notice Handles incoming cross-chain token transfer messages
     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then mints tokens to the
     * recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
