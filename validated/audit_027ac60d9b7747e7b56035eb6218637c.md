### Title
Identity public key enables universal Schnorr signature forgery - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` accepts the group identity as a public key. Because multiplication by the identity removes the challenge and private-key terms from the verification equation, any caller-controlled verification accepting an identity public key can be bypassed with an arbitrary scalar `s` and `R = sG`.

This is analogous to accepting `address(0)` as an authorized signer after an invalid `ecrecover`: the additive identity is a valid encoded group element, but it corresponds to the publicly known scalar zero and must not be accepted as a key.

### Finding Description
`SchnorrSignature::read` accepts any canonically encoded point for `R` and scalar for `s`. `Ciphersuite::read_G` checks only that the point decodes and re-encodes canonically; it does not reject the identity. [1](#0-0) [2](#0-1) 

Verification builds the statement:

```text
R + cA - sG = identity
```

where `A` is the supplied public key. If `A` is the identity, the `cA` term is always identity regardless of `c`. An attacker can therefore select any scalar `s`, set `R = sG`, and satisfy the equation for every challenge. [3](#0-2) 

The same issue applies to `batch_verify`, which queues these same statements. [4](#0-3) 

### Impact Explanation
Any protocol path that obtains a public key from untrusted bytes and then calls `SchnorrSignature::verify` or `batch_verify` without separately rejecting the identity accepts a forged signature for arbitrary challenge and message data.

This can turn an absent, malformed, or attacker-selected identity key into an authorization oracle equivalent to a known-zero private key. The concrete cryptographic failure is a universally forgeable signature under the identity key.

### Likelihood Explanation
The attack is deterministic and requires no secret, timing condition, or participant cooperation. It is reachable when an attacker controls the public-key input or can induce a verifier to use a default, missing, or decoded identity key.

The identity is canonically encodable, so ordinary `read_G` canonicality checks do not prevent it. Exploitability in a consuming protocol depends on whether that protocol separately rejects identity public keys; this crate itself does not.

### Recommendation
Reject the identity element wherever a public key is accepted for authentication or signature verification.

At minimum, add an explicit check in `SchnorrSignature::verify` and `batch_verify`:

```rust
if bool::from(public_key.is_identity()) {
  return false;
}
```

For `batch_verify`, return an error or otherwise fail before queueing the statement. Preferably enforce non-identity keys at the deserialization/type boundary as well, by introducing a validated public-key type or rejecting identity in readers used for public keys. Individual projects should still reject identity at their own trust boundary because not every `C::G` value is semantically a public key.

### Proof of Concept
Conceptually, for any `C: Ciphersuite`, attacker-selected values are:

```rust
let public_key = C::G::identity();
let s = C::random_nonzero_F(&mut OsRng);
let forged = SchnorrSignature::<C> {
  R: C::generator() * s,
  s,
};

assert!(forged.verify(public_key, arbitrary_challenge));
```

The equation becomes:

```text
R + c * identity - sG
= sG - sG
= identity
```

so `verify` returns `true` for every `arbitrary_challenge`.
