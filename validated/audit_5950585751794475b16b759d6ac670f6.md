### Title
Consensus/messaging relayer rewards and Reputation Asset (collator voting power) are minted immediately on `StateMachineUpdated`, before the challenge period elapses or a fisherman veto can occur, with no clawback — ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
The external report's core invariant is: value/power (tokens with voting weight) was made available to a beneficiary immediately, before the process that should gate it (vesting) had run, creating downstream governance risk. The local analog is `pallet-consensus-incentives` (and `pallet-messaging-incentives` / `pallet-beefy-consensus-proofs`), which pay real `$BRIDGE` and mint the soulbound `ReputationAsset` the instant a `StateMachineUpdated` event fires — i.e., the moment a consensus proof is accepted — rather than after the mandatory challenge period during which fishermen can veto a fraudulent commitment.

### Finding Description
Hyperbridge's own documentation establishes that a `StateMachineUpdated` event does **not** mean the state is trusted yet: relayers must wait for the `challenge_period` to elapse before using the associated state proofs, and fishermen may veto the commitment during that window via `pallet_fishermen::veto_state_commitment` [1](#0-0) . `veto_state_commitment` only deletes the stored state commitment; it performs no reward or reputation clawback [2](#0-1) .

However, `pallet-consensus-incentives::on_executed` reacts to the very same `StateMachineUpdated` events emitted during the *same* message-handling batch that accepted the (possibly fraudulent) consensus proof, and immediately transfers `$BRIDGE` from the treasury and mints an equal amount of the soulbound `ReputationAsset` to the account that signed the consensus message — with no challenge-period gate whatsoever: [3](#0-2) [4](#0-3) 

The `ReputationAsset` is not cosmetic — it is the sole input to collator (block-producer) selection in `pallet-collator-manager`, directly analogous to "voting power in a DAO": the higher the balance, the better the chance of being promoted into the set that authors Hyperbridge's blocks [5](#0-4) . The same immediate-mint pattern exists for BEEFY proof rewards [6](#0-5)  and messaging rewards [7](#0-6) .

This is the same broken invariant as the source report: an asset that confers real power (there: DAO voting power from unvested presale tokens; here: real `$BRIDGE` plus reputation that gates collator selection) is granted unconditionally and immediately, before the safeguard designed to validate the underlying claim (there: token vesting; here: the ISMP challenge period / fisherman veto) has had a chance to run.

### Impact Explanation
If a byzantine or eclipsed validator set on a connected chain produces a consensus proof that passes signature verification but represents a forged/invalid chain state (the exact "Eclipse Attack" and "51% Attack" scenarios the protocol's own threat model documents) [8](#0-7) , the relayer submitting that proof is rewarded in real, transferable `$BRIDGE` (a permanent loss of treasury funds to a bad actor) and gains reputation immediately upon `StateMachineUpdated`, before fishermen can react. If the commitment is later vetoed, the fraudulent state is removed from the trie, but the reward payout and reputation gain are never reversed — the attacker keeps stolen treasury funds and an advantage toward becoming a collator (block producer), which is a governance/execution-authority escalation, not merely a lost fee.

### Likelihood Explanation
The reward path runs on every accepted consensus update with no dependency on `verify_delay_passed`/challenge period — that check is only enforced for request/response/timeout handling in `validate_state_machine`, not for the reward-issuing `on_executed` hook [9](#0-8) . The veto mechanism itself is documented as fallible ("If your fisherman vetoes a valid state commitment... governance can remove a fisherman"), i.e., fisherman coverage is not guaranteed to catch every fraudulent update within the window [10](#0-9) . Any successful eclipse/51% attack that lands even briefly before detection is enough to trigger irreversible reward/reputation issuance.

### Recommendation
Defer both the `$BRIDGE` transfer and the `ReputationAsset` mint in `pallet-consensus-incentives`, `pallet-messaging-incentives`, and `pallet-beefy-consensus-proofs` until the relevant `challenge_period` has elapsed without a veto (mirroring the gate already used for state proof consumption in `validate_state_machine`), or implement a clawback: when `veto_state_commitment`/`freeze_client` fires for a height, burn any reputation and claw back any `$BRIDGE` reward paid for the vetoed/frozen consensus update.

### Proof of Concept
1. A byzantine/eclipsed validator supermajority for a connected chain signs a forged finalized header.
2. A relayer submits this as a `ConsensusMessage`; it passes `ConsensusClient::verify_consensus` and is accepted, emitting `StateMachineUpdated` [11](#0-10) .
3. In the same `on_executed` batch, `pallet_consensus_incentives::Pallet::process_message` immediately transfers `reward` `$BRIDGE` from the treasury to the relayer and mints an equal `ReputationAsset` amount — no challenge-period check anywhere in this path [3](#0-2) .
4. Within the challenge period, a fisherman detects the forged state and calls `veto_state_commitment`, deleting the state commitment [2](#0-1) .
5. The relayer's `$BRIDGE` balance and `ReputationAsset` balance are unaffected by the veto — the reward is not reversed, and the reputation gain persists into the next collator-selection ranking [5](#0-4) .

Note: I was unable to fully verify (due to iteration limits) whether any other pallet-level hook exists elsewhere in the runtime that specifically claws back consensus-incentive rewards on veto/freeze; the code paths inspected (`pallet-fishermen::veto_state_commitment`, `freeze_client` in `modules/ismp/core/src/handlers/consensus.rs`, and `pallet-consensus-incentives`) show no such linkage, but a full audit of runtime-level glue code in `parachain/runtimes/*` was not completed.

A `StateMachineUpdated` event is emitted to notify network participants (both relayers and fishermen) of some newly available `StateCommitment`s for a given state machine. Relayers will wait for the configured `challenge_period` before attempting to transmit new requests & responses. While fishermen will check if these pending `StateCommitment`s describe valid states on the counterparty network. If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

### Eclipse Attacks

This is not a new vulnerability in blockchain systems, as even off-chain consensus clients are vulnerable to this attack vector. This is a scenario where the super majority of a validator set finalizes a fork of the canonical chain that they do not gossip on the network, rather only to a consensus client with the sole purpose of fooling this client that some transactions are final.

It’s important to note that consensus clients are vulnerable to this attack because they do not validate the *state transition function* of the blocks, where they would’ve detected the invalid transactions and immediately rejected the block. This is of course why they’re called consensus *clients*; instead, they rely on full nodes to gossip the consensus proofs of finalized headers.

This vulnerability can be mitigated by having consensus clients that actively participate in the p2p swarm and can ask as many nodes of the latest finalized header in the chain. Proof of stake consensus protocols mitigates this further with it’s use of an equivocation (aka slashing) protocol.

This protocol prevents validators from signing two headers at the same height by allowing anyone to report this misbehaviour on-chain causing the stake of the validator in question to be slashed. So, for off-chain consensus clients, this eclipse attack can be mitigated so long as the client is connected to at least one honest node.

On-chain consensus clients however do not participate in the p2p network and cannot gossip headers they receive and instead rely on relayers who do not need to be trusted to provide cryptographic proofs alongside the submitted headers. The whole point of on-chain consensus clients is anyone can be a relayer, but unfortunately in this scenario that also includes a potentially byzantine authority set of a counterparty chain.

Now that the consensus client has been eclipsed, the byzantine authority set can send state proofs of cross-chain messages associated with the forged chain allowing them to bridge tokens that simply don’t exist to the counterparty blockchain and swap them for other assets, bridging them back and destroying the peg of these assets on the counterparty.

### Long Range Attacks

The attack involves a consensus client that hasn't been updated in some period *n*. Unfortunately, this $n$ period of time is also how long it takes for validators to unstake their funds from the network the consensus client is tracking. This is a major problem for any consensus-verifying bridge because the stake is what prevents malicious behaviour. Without it, malicious actors can sign a forked chain, update the on-chain consensus client with this forked chain, and perform an eclipse attack. This time, however, there is no risk of slashing. This vulnerability is present even in full nodes of Proof of Stake systems<sup>[2]</sup>.

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>

	H: IsmpHost,

			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;

			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)

## RPC Endpoint Quality is Critical

> **Warning: using low-quality or unreliable RPC endpoints exposes you to governance punishment.**
>
> If your fisherman vetoes a valid state commitment because one of your RPC providers returned stale, incorrect, or temporarily unavailable data, that veto harms the network. Governance can remove a fisherman from the collator set for submitting bad vetoes, and in the future slashing conditions may apply. The 2 `$BRIDGE` block reward is large enough to cover the cost of premium endpoints — there is no excuse for cutting corners here.

The fisherman reaches a supermajority quorum (`floor(2/3 * N) + 1`) across all configured RPC URLs before it will veto. With only two endpoints, a single bad response from one provider can swing the quorum. With three, two providers must agree before the fisherman acts — this is why **three premium RPC URLs per L2 is the strong recommendation**, even though the minimum enforced by the node is two.

### What "premium" means

- **Dedicated, non-shared endpoints** from a provider that guarantees archive access and high availability SLAs. Free-tier public nodes are not acceptable.
- **Three genuinely distinct providers** — Alchemy, Infura, QuickNode, Ankr, and similar infrastructure vendors all count as distinct. Multiple API keys from the same provider resolve to the same host and are rejected by the config validator.
- **Low latency and high reliability**. A provider that regularly lags behind the chain head can cause your quorum to disagree with reality during the brief window Hyperbridge is verifying a new state commitment.
