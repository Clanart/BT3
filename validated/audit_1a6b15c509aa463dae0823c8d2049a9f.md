### Title
Reward dilution via direct stakingToken donation to operator (MasterMagpie) inflates `totalStaked()` denominator - (File: rewards/BaseRewardPool.sol)

### Summary
`totalStaked()` computes the reward denominator as the raw ERC20 balance of the `operator` (MasterMagpie) contract rather than the sum of user stakes tracked internally. An attacker can transfer `stakingToken` directly to `operator` without calling `deposit()`, inflating this balance, then trigger `_provisionReward` via `donateRewards()` (or wait for `queueNewRewards`) so that `rewardPerTokenStored` is computed against an inflated, unbacked denominator, permanently diluting the reward-per-token accrued by legitimate stakers.

### Finding Description
`totalStaked()` returns `IERC20(stakingToken).balanceOf(operator)` [1](#0-0)  while a staker's own balance used for reward accrual, `balanceOf(_account)`, is derived from MasterMagpie's internally tracked `stakingInfo` mapping, not the token balance [2](#0-1) . These two accounting sources are only meant to be kept in sync through `deposit()`/`withdraw()` flows in MasterMagpie, but nothing prevents a plain ERC20 `transfer()` directly to the `operator` address, which raises `balanceOf(operator)` without updating any user's `stakingInfo` entry.

`_provisionReward` (invoked by both `queueNewRewards` and the permissionless `donateRewards`) uses `this.totalStaked()` as the divisor when updating `rewardPerTokenStored`: [3](#0-2) 

Because `donateRewards` is unpermissioned (no `onlyManager`/`onlyMasterMagpie` modifier, only requires `isRewardToken[_rewardToken]`) [4](#0-3) , an attacker's sequence is:
1. `IERC20(stakingToken).transfer(operator, X)` — inflates `totalStaked()` without crediting any account's `stakingInfo`.
2. `donateRewards(_amountReward, _rewardToken)` — forces `rewardPerTokenStored` to be computed as `reward * 10**decimals / totalStaked()`, where `totalStaked()` now includes the attacker's phantom `X`.

Since `earned()` for legitimate stakers is `balanceOf(account) * rewardPerToken / 10**decimals`, and `rewardPerToken` is now permanently lower than it would be if computed against the true sum of tracked stakes, every future and even the just-provisioned reward distribution is diluted. This dilution is permanent for that reward event (the phantom `X` is baked into `rewardPerTokenStored`'s historical calculation and cannot be "undone" — no code path reconciles or skims the excess balance back out of `totalStaked()`).

Existing checks do not stop this: there is no reentrancy or access-control issue involved, and no code in `BaseRewardPool.sol` verifies that `balanceOf(operator)` matches the sum of tracked `stakingInfo` balances before using it as a divisor.

### Impact Explanation
This causes theft/permanent freezing of unclaimed yield for legitimate stakers: a portion of every reward distribution processed while the phantom balance is present is diluted away and effectively becomes unclaimable by any staker (it isn't attributed to any account's `balanceOf`), matching the Immunefi "theft or permanent freezing of unclaimed yield" impact class. The attacker does not directly profit from stolen funds (the donated tokens are not later reclaimable either), but this is a griefing vector that permanently damages the reward-accounting invariant `totalStaked() == Σ user stakes`.

### Likelihood Explanation
Low capital is required (attacker only needs any amount of `stakingToken`, even a tiny amount) and the attack is fully permissionless and repeatable at any time — any address can call `IERC20.transfer` to `operator` and then call the public `donateRewards` function. The main precondition is that a manager calls `queueNewRewards` (or the attacker calls `donateRewards` themselves, supplying the reward token) while phantom balance is present; since `donateRewards` is public, the attacker can self-trigger the whole flow with a single reward token they hold, making this trivially and cheaply repeatable.

### Recommendation
Track `totalStaked` as an explicit internal accounting variable incremented/decremented only via authenticated `stake`/`withdraw` calls from `operator`, rather than reading the live ERC20 `balanceOf(operator)`. Alternatively, have `MasterMagpie` expose an authoritative `totalStaked(stakingToken)` view backed by its internal ledger, and have `BaseRewardPool.totalStaked()` call that instead of `IERC20.balanceOf`.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (via MasterMagpie's registration flow), a mock `stakingToken`, and a mock `rewardToken`.
2. Two legitimate users (`alice`, `bob`) each `deposit()` `100e18` `stakingToken` through MasterMagpie into the pool, so `stakingInfo` records `100e18` each and `totalStaked() == 200e18`.
3. Manager calls `queueNewRewards(200e18, rewardToken)` — assert `rewardPerTokenStored == 1e18` (200e18*1e18/200e18), i.e., 1:1 baseline.
4. Reset state or continue: attacker (no stake, no deposit) calls `stakingToken.transfer(address(masterMagpie), 200e18)` directly — assert `pool.totalStaked() == 400e18` while `stakingInfo` sum is still `200e18`.
5. Attacker (or manager) calls `donateRewards(200e18, rewardToken)` — assert `rewardPerTokenStored` increases by only `200e18*1e18/400e18 = 0.5e18` instead of the `1e18` it would have increased by absent the donation.
6. Assert `alice.earned(rewardToken) + bob.earned(rewardToken) < 200e18` (the full donated reward), proving a portion of reward is permanently unattributable to any staker, confirming dilution/freezing of yield.
