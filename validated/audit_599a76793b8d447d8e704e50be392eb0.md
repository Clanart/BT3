### Title
Unbounded attacker-controlled point count in `SchnorrAggregate::read` causes amplified deserialization/verification DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::<C>::read` trusts an attacker-supplied `u32` element count and then performs up to ~4.29 billion `C::read_G` decompressions, followed (if parsing succeeds) by `SchnorrAggregate::verify`, which builds a transcript, a `weight()` per signer, and a `multiexp_vartime` over `2n + 1` pairs. An unprivileged party feeding untrusted bytes into an aggregate-signature verification path causes the node to burn CPU and memory proportional to the declared count before the signature check can fail, mirroring the reported "expensive verification not charged on failure" class.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads a 4-byte length and loops `u32::from_le_bytes(len)` times calling `C::read_G(reader)` with no cap:

- `read` at `crypto/schnorr/src/aggregate.rs:77-88` — `len` is a raw `u32`; there is no bound check against any expected signer count before the loop pushes decompressed points into `Rs`.
- Each `C::read_G` performs canonical-encoding validation plus a full point decompression (square root / curve recovery), so each ~32 attacker bytes costs orders of magnitude more node CPU than the bandwidth spent sending them.
- `verify` at `crypto/schnorr/src/aggregate.rs:127-146` then iterates all `keys_and_challenges`, calling `weight(&mut digest)` per signer and running a single `multiexp_vartime` over `2n + 1` scalar-point pairs — superlinear effective cost as n grows.

The only sanity check is `self.Rs.len() != keys_and_challenges.len()` inside `verify`, which happens *after* all `n` decompressions have already been paid for. Callers that deserialize an aggregate signature from untrusted bytes (e.g., the `SignatureScheme::verify_aggregate` flow at `coordinator/tributary/src/tendermint/mod.rs:207`, which calls `SchnorrAggregate::<Ristretto>::read(&mut sig.as_slice())` on validator-supplied signature bytes before checking `signers.len()`) hit the expensive decode first and only reject afterwards — the failure path is cheap for the attacker and expensive for the node.

### Impact Explanation
An attacker can craft an aggregate-signature blob claiming millions of signers. The node performs millions of Ristretto (or other ciphersuite) decompressions plus a large multiexp before the verification fails. Since the invalid signature carries no cost to the attacker (no stake burn, no fee, no per-byte accounting in the read path), this is a repeatable resource-exhaustion vector: each relayed/validated message forces expensive group operations whose cost is never charged back, enabling sustained CPU/memory pressure on every node that processes the message — the same asymmetric-cost DoS shape as the reported `Restore()` finding.

### Likelihood Explanation
Reachability requires a deployment path that deserializes an aggregate signature from unauthenticated bytes; the in-repo `Validators::verify_aggregate` does exactly that on network messages. Within the in-scope crates the primitive itself is unconditionally reachable via `SchnorrAggregate::read` / `SchnorrAggregate::verify` on untrusted input, and no caller-independent bound exists (the validator-set size is known to callers, yet `read` never receives or enforces it). Exploitation needs no key material, no collusion, and no protocol position — only the ability to submit bytes to a verification endpoint.

### Recommendation
Pass the expected signer count (or a hard upper bound, e.g., the validator-set size) into `SchnorrAggregate::read` and reject `len` values exceeding it before looping, so the length check precedes all decompression work. Alternatively, enforce the `Rs.len() == keys_and_challenges.len()` equality during decoding rather than inside `verify`. This makes invalid signatures cost O(1) work regardless of the claimed count.

### Proof of Concept
```rust
// Conceptual PoC against crypto/schnorr SchnorrAggregate::read
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;
use ciphersuite::group::GroupEncoding;

// Attacker-controlled blob: u32 count + count * <G as GroupEncoding>::Repr bytes.
// Each 32-byte element triggers a full Ristretto decompression in C::read_G.
let n: u32 = 10_000_000; // ~10M decompressions before any signer-count check
let mut blob = n.to_le_bytes().to_vec();
// 32 bytes of a validly-encoded point repeated (or just zeros to fail late/fast per impl)
let mut point = vec![0u8; 32];
for _ in 0..n { blob.extend_from_slice(&point); }

// Node side (e.g., Validators::verify_aggregate calling):
let agg = SchnorrAggregate::<ciphersuite::Ristretto>::read(&mut blob.as_slice());
// Even when read/verify ultimately fails, ~10M decompressions + a multiexp over
// 2n+1 pairs were consumed; the attacker only paid the bandwidth for the blob.
```
The asymmetry is that failure is detected only after O(n) decompression and O(n) multiexp work, while the attacker's cost is bounded by input size and nothing else.
