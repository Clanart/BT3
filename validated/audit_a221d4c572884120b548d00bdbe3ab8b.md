### Title
Truncated ThresholdKeys input forces oversized interpolation allocation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized `n` field before validating the threshold parameters or confirming the serialization contains `n` scalar encodings. When the interpolation variant is `Constant`, it immediately calls `Vec::with_capacity(usize::from(n))`. An unauthenticated party supplying untrusted `ThresholdKeys` bytes can therefore force a maximum allocation of 65,535 scalar elements with a truncated input, causing repeated parsing to consume disproportionate memory and CPU.

### Finding Description
The deserializer reads `t`, `n`, and `i` at `crypto/dkg/src/lib.rs:591-601`, then reads the interpolation selector at `crypto/dkg/src/lib.rs:604-615`. For selector `0`, it immediately reserves `n` scalar elements before reading even the first scalar:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
```

`ThresholdParams::new` rejects zero `n`, `t > n`, and `i > n`, but that validation occurs only after the allocation and attempted scalar decoding at `crypto/dkg/src/lib.rs:625-630`. Consequently, malformed or truncated input can trigger the allocation even though deserialization cannot succeed. A scalar such as a Ristretto255 field element is approximately 32 bytes, so `n = 65,535` reserves roughly 2 MiB per call before the input fails.

### Impact Explanation
An attacker who can submit bytes to `ThresholdKeys::read` can cause memory amplification: a request containing only the small header triggers an allocation proportional to the attacker-selected `n`. Repeated requests can force numerous simultaneous or short-lived allocations, increasing allocator pressure and potentially causing process termination through memory exhaustion.

### Likelihood Explanation
`n` is a serialized `u16` under the sender's control. The attacker does not need valid scalars, valid threshold parameters, or a complete message because the capacity reservation happens first. Reachability exists wherever serialized `ThresholdKeys` from storage, protocol messages, recovery data, or another untrusted source are deserialized through this API.

### Recommendation
Validate `t`, `n`, and `i` with `ThresholdParams::new` before allocating. For `Interpolation::Constant`, avoid `Vec::with_capacity(n)` or cap it to a conservative initial value; push each successfully decoded scalar and reserve only after enough input has been consumed. Reject malformed and truncated input before performing attacker-controlled allocation.

### Proof of Concept
For a ciphersuite whose ID is `C::ID`, construct:

```text
u32le(C::ID.len())
C::ID
u16le(t = 1)
u16le(n = 65_535)
u16le(i = 1)
u8(interpolation = 0)
EOF
```

Calling `ThresholdKeys::<C>::read` on this truncated byte string reaches `Vec::with_capacity(65_535)` before `C::read_F` encounters EOF. The call therefore allocates space for 65,535 scalar elements even though it cannot deserialize successfully.
