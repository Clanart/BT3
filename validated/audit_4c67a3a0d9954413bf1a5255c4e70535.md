## Title
Attacker-controlled Pull Request `headCloneUrl` is passed unsanitized to `git remote add` / `git fetch`, allowing a malicious fork to smuggle a `ext::`/foreign-transport remote URL - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user checks out a pull request from a fork, GitHub Desktop derives the remote URL to add and fetch entirely from the `headCloneUrl` value supplied by the GitHub API for the PR's head repository. Since anyone can open a PR from a public fork, this string is fully attacker-controlled. The value is passed straight into `addRemote()` and then `git fetch` with no scheme/format validation, mirroring the underlying issue class in the report: a value supplied by a party the app doesn't fully trust is consumed downstream without a bound/allowlist check that the rest of the flow implicitly assumes is in place.

### Finding Description
`_checkoutPullRequest` / `_findPullRequestBranch` receive `headCloneUrl` from PR metadata and use it directly: [1](#0-0) 

Specifically, if no existing remote matches the URL, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)` and later fetches it via `this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)`: [2](#0-1) 

`addRemote` and `getRemotes` (`app/src/lib/git/remote.ts`) simply forward the string to `git remote add name url`/`git fetch` without validating the URL's transport scheme: [3](#0-2) 

The env-preparation helper `envForRemoteOperation`/`envForProxy` only special-cases `http(s)://` prefixes for proxy resolution; it does not set `GIT_ALLOW_PROTOCOL` or otherwise restrict which git transport helpers can be invoked: [4](#0-3) 

Git itself supports the `ext::` (and similarly `fd::`) remote helper transport, which executes an arbitrary shell command supplied inside the URL as the "transport." Nothing in the reviewed remote-parsing/validation code (`app/src/lib/remote-parsing.ts`, `parseRemote`) is invoked on this PR path to reject non-`https`/`ssh`/`git` schemes before the value reaches `git remote add`/`git fetch` — `parseRemote`'s regexes are used elsewhere (e.g. clone-path derivation) but `_findPullRequestBranch` does not run the URL through any such allowlist before calling `addRemote`.

This is the structural analog of the 1inch bug: the report's root cause is that a value from a less-trusted party (maker) flows into a downstream computation (`_getTakingAmount`) without a hard bound, silently overriding the taker's protective threshold. Here, a value from a less-trusted party (a PR author on a public fork) flows into a downstream git invocation without a hard bound (scheme allowlist), silently letting the "url" mean "run this command" instead of "fetch from this remote."

### Impact Explanation
If exploitable, checking out a malicious pull request (an action Desktop explicitly supports and encourages via "Checkout this PR") could result in local command execution on the victim's machine merely by clicking checkout on an attacker-crafted PR, without any git clone/fetch of actual malicious repo content required — the URL itself is the payload. This would constitute code execution originating from an attacker-controlled GitHub API object (the PR's head repository clone URL), squarely within the valid-impact criteria (attacker controls a GitHub API object, result is code execution).

### Likelihood Explanation
Likelihood is **uncertain and not confirmed** from the available code: I was not able to fully verify (a) what exact shape the `headCloneUrl` takes as returned by the GitHub API client/model (`app/src/lib/api.ts`, PR fetch code) — whether it's normalized/typed to a strict `https://` GitHub clone URL before reaching this function, and (b) whether `dugite`/the embedded git binary is built or configured with `protocol.ext.allow`/`GIT_ALLOW_PROTOCOL` defaults that already block `ext::`/`fd::` helpers (many modern git distributions disable these by default, in which case this path is not exploitable as-is). I could not locate any explicit `GIT_ALLOW_PROTOCOL` setting or scheme allowlist in the reachable Desktop code, which is what makes this worth flagging, but I could not confirm the git binary's own default protections within the scope of this investigation.

### Recommendation
- Before calling `addRemote`/fetching a PR head clone URL, validate it with `parseRemote`/`parseRepositoryIdentifier` (already used for clone-path safety elsewhere) and reject anything that isn't a well-formed `https://` or `ssh://`/`git@` GitHub-style URL.
- Explicitly set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (excluding `ext`, `fd`, `file` as appropriate) in `envForRemoteOperation` for all remote-fetching operations, not just proxy resolution, so this is defense-in-depth even if a scheme check is missed elsewhere.

### Proof of Concept
Not executed — this is a code-review-derived finding, not a confirmed exploit. Conceptually: an attacker forks a public repository, opens a PR whose head repository's `clone_url` (as surfaced through the GitHub API and consumed as `headCloneUrl`) is set to `ext::sh -c calc` (or similar shell-invoking transport string). If the victim opens that PR in GitHub Desktop and clicks "Checkout this PR," `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` followed by a fetch of that remote, which — absent a protocol allowlist — would invoke the `ext::` git remote helper and execute the attacker's command. Confirming this requires testing whether the bundled `dugite`/git binary permits the `ext::` helper by default, which I could not verify from the indexed source alone.

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {

/** Add a new remote with the given URL. */
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
