### Title
Rebasing/deflationary ERC20 token pairs permanently unbacked native-coin supply after conversion, freezing user funds - ([File: x/erc20/keeper/msg_server.go])

### Summary
This repository already implements a defense specifically against the bug class from the external report (evil/fee-on-transfer ERC20 tokens): `convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20` both compute the ERC20 `balanceOf` before and after the escrow/unescrow `transfer` call within the *same transaction* and revert with `types.ErrBalanceInvariance` if the observed delta doesn't match the expected amount [1](#0-0) [2](#0-1) . There is even a dedicated malicious test contract, `ERC20DirectBalanceManipulation.sol`, used in the test suite to exercise this exact guard [3](#0-2) . This mitigates fee-on-transfer/skimming tokens where the balance change happens *synchronously as a side effect of the `transfer()` call*.

### Finding Description
The invariant check only covers balance changes that occur *during* the `transfer` call inside `ConvertERC20`/`ConvertCoin`. It cannot and does not cover tokens whose balance changes **autonomously, out-of-band, and asynchronously** from any transfer call — i.e., true rebasing or interest-accruing tokens (e.g., stETH-style rebase, aTokens, etc.) where `balanceOf(moduleAddress)` can shrink on its own between blocks with no `transfer` invocation at all.

`RegisterERC20` can be invoked permissionlessly by any unprivileged account when `params.PermissionlessRegistration` is true [4](#0-3) , and `registerERC20` performs no validation of the token's balance semantics (no whitelist, no rebase detection) [5](#0-4) . Once registered, any user can call `MsgConvertERC20` to escrow ERC20 tokens on the module account and mint an equal amount of native Cosmos coin 1:1 [6](#0-5) . The one-time balance-invariance check at mint time only guarantees the state is consistent *at that instant*; it does not, and cannot, protect against the escrowed token balance later drifting downward due to a negative rebase or interest-bearing mechanic that fires per-block independent of any `transfer` call.

Because the minted native coin supply is tracked purely in the bank module (a static accounting ledger) while the actual backing asset is a dynamic-balance ERC20 held by `types.ModuleAddress`, a negative rebase after minting permanently decouples the two: the bank module still shows the full native coin supply as spendable/transferable, but `ConvertCoinNativeERC20` (used to redeem/unescrow) will eventually fail once the module's actual token balance is smaller than the cumulative claims (`balanceTokenAfter` != `balanceToken + amount`), tripping `ErrBalanceInvariance` and reverting for the coin holder attempting redemption — while earlier redeemers were able to walk away with a first-come, first-served share of the shrinking real balance [2](#0-1) .

### Impact Explanation
This produces a Critical, permanent freezing/loss-of-funds condition: later holders of the native-coin representation of a rebasing/interest-accruing ERC20 token pair cannot redeem their coins because the escrowed collateral has autonomously shrunk below the total minted supply, and the invariant check (designed to catch in-tx manipulation, not out-of-band drift) will simply block redemption permanently rather than allow a graceful pro-rata unwind. This matches the "permanent freezing/locking of user funds / escrowed assets / token-pair-backed balances" impact category. It is a native analog of the reported ERC20 report's dynamic-balance concern, distinct from the already-mitigated fee-on-transfer case.

### Likelihood Explanation
The trigger requires only two conditions controllable by an unprivileged actor: (1) `params.PermissionlessRegistration` enabled (a governance-controlled parameter, not attacker-controlled — reducing likelihood if this defaults to false in production genesis, which I could not fully confirm from available files), and (2) any user registering and using a real-world rebasing/interest-bearing token (which exist on many chains) as a token pair. If `PermissionlessRegistration` defaults to `false`, this would instead require a validator/community proposal to register such a token pair, which somewhat lowers likelihood but does not eliminate it, since the report itself notes the client's stated intent to rely on an off-chain/frontend whitelist rather than an on-chain one — meaning nothing in the contract logic itself prevents this token class from being registered on-chain, on any deployment where permissionless registration is enabled or where a rebasing token is inadvertently approved by governance.

### Recommendation
- Enforce an on-chain denylist/allowlist or a static-supply/rebase self-check at `RegisterERC20` time (e.g., mint+immediately-check-balance-twice across a block boundary, or require ERC-4626/EIP-2612-style guarantees) rather than relying solely on a frontend whitelist.
- Consider tracking per-pair "backing shortfall" and gracefully degrading redemption (pro-rata) instead of reverting outright with `ErrBalanceInvariance`, or pausing/disable the token pair automatically once a shortfall is detected, to convert a fund-freeze into a fair-loss-sharing mechanism.
- Re-validate the balance-invariance assumption periodically (e.g., in `BeginBlock`) for native ERC20 token pairs to detect and disable drifting pairs before more users are affected.

### Proof of Concept
Conceptual sequence (not runnable without an actual rebasing token contract, since none exists in the indexed test fixtures):
1. Governance/permissionless flow registers a rebasing ERC20 `R` as a token pair via `RegisterERC20` [4](#0-3) .
2. User A calls `MsgConvertERC20` with 1000 `R`, escrowing 1000 `R` on `types.ModuleAddress` and minting 1000 native coins to A; the in-tx invariance check passes since balance matches exactly at that moment [7](#0-6) .
3. A transfers/distributes the 1000 native coins to other users (B, C, ...).
4. `R`'s rebase mechanism reduces `balanceOf(ModuleAddress)` to 800 over subsequent blocks with no `transfer()` call ever occurring on the module account.
5. B calls `MsgConvertCoin` to redeem 300 coins back to `R`; this succeeds only if the module's balance is still sufficient. Eventually, once cumulative redemptions exceed 800, the next redeemer's `ConvertCoinNativeERC20` call fails permanently with `ErrBalanceInvariance` [2](#0-1) , even though their native coin balance shows a spendable, seemingly fully-backed balance in the bank module — resulting in an unredeemable, permanently frozen coin balance for that user.

// convertERC20IntoCoinsForNativeToken handles the erc20 conversion for a native erc20 token
// pair:
//   - escrow tokens on module account
//   - mint coins on bank module
//   - send minted coins to the receiver
//   - check if coin balance increased by amount
//   - check if token balance decreased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// This is an evil token. Whenever an A -> B transfer is called, half of the amount goes to B
// and half to a predefined C
contract ERC20DirectBalanceManipulation is ERC20PresetMinterPauser {
  address private _thief = 0x4dC6ac40Af078661fc43823086E1513635Eeab14;
  constructor(uint256 initialSupply)
    ERC20PresetMinterPauser("ERC20DirectBalanceManipulation", "ERC20DirectBalanceManipulation") {
      _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
      _mint(msg.sender, initialSupply);
  }
  function transfer(address recipient, uint256 amount) public virtual override returns (bool) {
    // Any time a transaction happens, the thief account siphons half.
    uint256 half = amount / 2;

    super.transfer(_thief, amount - half); // a - h for rounding
    return super.transfer(recipient, half);
  }
}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
