## Title
Recursive precompile calls share a single-scoped `prevEventsLen` cursor, allowing double-processing of bank events into `StateDB` balances - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
The Alchemix report's root cause is that an operation (`merge()`) that increases a token's balance can be interleaved with a claim, causing the "claimable" quantity to be computed and paid out more than once against the same underlying value. The Cosmos EVM analog found in this repository is a **documented, unresolved bug** (already captured by the repository's own regression tests) in the precompile `BalanceHandler`: recursive/nested precompile calls (e.g., a contract's `_beforeTokenTransfer`/token hook re-entering a distribution/staking precompile, or ERC20 transfer hooks calling back into precompiles) can cause bank events belonging to an outer call to be re-processed by an inner or subsequent `AfterBalanceChange` pass, corrupting the `StateDB` balance relative to the native bank ledger.

### Finding Description
Each stateful precompile invocation goes through `Precompile.runNativeAction` in [1](#0-0) . Before invoking the native action, it records a "before" cursor via `balanceHandler.BeforeBalanceChange(ctx)`, which stores `len(ctx.EventManager().Events())` [2](#0-1) . After the action runs, `AfterBalanceChange` slices `events[bh.prevEventsLen:]` and replays every `CoinSpent`/`CoinReceived`/fractional-balance event since that cursor into `stateDB.AddBalance`/`SubBalance` [3](#0-2) .

This design assumes that the `sdk.Context`'s `EventManager` event log is scoped per top-level precompile call. However, when a precompile call recursively re-enters another precompile (e.g., an ERC20 token hook calling `distribution.DISTRIBUTION_CONTRACT.claimRewards`, as demonstrated in the repo's own test fixtures `ERC20RecursiveNonRevertingPrecompileCall.sol` and `ERC20RecursiveRevertingPrecompileCall.sol` [4](#0-3) ), the underlying `ctx.EventManager()` is shared across the whole call stack (it comes from the same cached SDK context obtained via `stateDB.GetCacheContext()`). The repository's own integration test explicitly documents this: *"BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) , and a companion IBC/ICS20 test states: *"Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated"* [6](#0-5) .

The mechanism mirrors the FLUX bug's structure exactly: a value-affecting side effect (bank events from a real coin movement) gets captured by a "window" (`prevEventsLen` in this case, `claimableFlux` snapshot in Alchemix's) that can be manipulated or reused across nested/repeated invocations before that window is properly reset, letting the same underlying delta be applied to `StateDB` balances more than once (double-crediting a receiver or double-debiting/omitting a spender), producing state where `stateDB` balances diverge from the actual bank-keeper balances that back them.

### Impact Explanation
If bank events already consumed by an inner `AfterBalanceChange` call are re-consumed by an outer call's `AfterBalanceChange` (or vice versa, if outer events set a `prevEventsLen` that an inner nested handler ends up using instead of its own), the EVM-visible balance (`StateDB`) can diverge from the actual native bank balance backing it. Since `StateDB` balances are what the EVM uses for further transfers, calls, and value checks within the same transaction and are what get committed at the end of tx execution, this can result in unauthorized inflation of a contract or account's spendable EVM balance relative to real bank-module holdings — i.e., accounting corruption between native coin balances and EVM-visible balances, matching the "Critical unauthorized minting/duplication ... across native balances, EVM balances ... " impact category. This is precisely the class of bug the repository's own test suites (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`) were written to catch, indicating it is recognized internally as a live risk in the precompile balance-synchronization path (`precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`).

### Likelihood Explanation
Triggering recursion is achievable by an ordinary, unprivileged user: deploying an ERC20-like contract with a transfer hook (`_beforeTokenTransfer`) that calls back into a stateful precompile (staking/distribution/ICS20), then performing a normal token transfer or IBC transfer that invokes that hook. The repository's own Solidity fixtures (`ERC20RecursiveNonRevertingPrecompileCall.sol`, `ERC20RecursiveRevertingPrecompileCall.sol`) and Go test harnesses (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`) demonstrate this is directly reachable through normal contract-deployment and transaction flows, without any privileged role — this is a good indicator of high likelihood once an exploitable double-credit path is confirmed.

### Recommendation
- Scope the "before/after" event cursor per precompile-call-frame rather than as a mutable field on a shared/reused handler; e.g., snapshot and consume events using a stack keyed by call depth, or bind the cursor to the specific cache-context/journal frame created in `runNativeAction`'s `stateDB.GetCacheContext()`/`AddPrecompileFn` calls [7](#0-6) .
- Ensure that events consumed by an inner `AfterBalanceChange` are marked/removed so an outer, enclosing call cannot re-process the same events.
- Add an invariant check post-transaction reconciling `StateDB` balances against native bank-keeper balances for all touched addresses, failing (reverting) the transaction if they diverge, as a defense-in-depth measure while the underlying event-scoping design is hardened.

### Proof of Concept
The repository already contains reproducing test scaffolding demonstrating the mechanism:
- `evmd/tests/integration/balance_handler/balance_handler_test.go` — deploys a `DebugPrecompileCaller` contract that recursively calls a debug precompile and asserts on the resulting event/state counts [8](#0-7) .
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` combined with `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol`/`ERC20RecursiveRevertingPrecompileCall.sol`, which have a `_beforeTokenTransfer` hook recursively invoking `distribution.DISTRIBUTION_CONTRACT.claimRewards` up to 5 times during a single token transfer/IBC transfer flow [4](#0-3) .

I was not able to fully trace, within the available tool budget, the exact concrete numeric divergence (i.e., a step-by-step balance-before/balance-after showing `StateDB` credited twice for one real bank transfer) because that requires running these existing test suites and inspecting `x/vm/statedb/statedb.go`'s `GetCacheContext`/`CommitWithCacheCtx`/`AddPrecompileFn` snapshot/journal semantics in full, which I could not complete before the iteration limit. The repository's own test names and comments (quoted above) strongly indicate the desync is real and already flagged internally, but confirming the exact exploitable direction (double-credit vs. double-debit) and quantifying it would require executing `TestRecursivePrecompileCallsWithDebugPrecompile` and the ICS20 recursive test with balance assertions added, which I recommend a Devin session with full repo/test execution access carry out to produce a definitive numeric PoC.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
