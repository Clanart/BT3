### Title
Fee/weight calculation omits the OP_RETURN data output, so the signed transaction pays a lower fee rate than the one verified - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` measures the transaction's weight/vbytes using only `tx_ins` and `payments`, then appends an OP_RETURN data output to `tx_outs` that was never included in the measurement. This is the same bug class as the report: two coupled quantities in a ratio check (fee rate = fee / vbytes) are computed against inconsistent states — the "denominator" (vbytes of the transaction actually signed) is larger than the vbytes the fee was charged for. The result is a transaction whose actual fee rate is strictly below `fee_per_vbyte`, and a `needed_fee`/minimum-relay-fee check evaluated against a smaller transaction than the one produced.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output carrying caller-supplied `data` (up to 80 bytes) is pushed to `tx_outs` *before* the weight calculation, yet `calculate_weight_vbytes` is invoked with `payments` — not `tx_outs` — so the data output is excluded from `weight`/`vbytes` [1](#0-0) . `needed_fee = fee_per_vbyte * vbytes` is therefore computed for a strictly smaller transaction [2](#0-1) . The same omission occurs in the change path, where `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again ignores the already-added data output, so both the change amount (`input_sat - payment_sat - fee_with_change`) and `needed_fee` use the wrong size [3](#0-2) . The final `MAX_STANDARD_TX_WEIGHT` check also uses this undercounted `weight` [4](#0-3) . `calculate_weight_vbytes` itself faithfully builds and weighs whatever it is given — the defect is purely that the caller passes an incomplete output set [5](#0-4) .

### Impact Explanation
Any caller that supplies `data` gets a transaction whose real fee rate is `needed_fee / actual_vsize < fee_per_vbyte`, with the discrepancy proportional to the data output (~9 bytes of output overhead plus up to ~83 bytes of OP_RETURN script, roughly 30+ vbytes unaccounted). Because the minimum-relay-fee check is performed against the undercounted `vbytes`, a transaction can be produced whose actual fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, causing it to be rejected by node policy after the multisig has already committed nonces and signed — burning a signing attempt and stalling the spend. The public `fee()`/`needed_fee()` accessors also misreport the economics of the produced transaction [6](#0-5) .

### Likelihood Explanation
The `data` parameter is a public input to `SignableTransaction::new` (used for OP_RETURN-embedded instructions), so any flow attaching data deterministically triggers the undercount — no special conditions needed. Exploitation as an *attack* is limited (an attacker gains nothing directly), but as a correctness flaw it is a guaranteed miscalculation on every data-carrying transaction, analogous to the quorum denominator being read at a different height: the check silently validates a different quantity than the one that matters.

### Recommendation
Include the data output in the weight measurement. The simplest fix is to reorder `SignableTransaction::new` so `calculate_weight_vbytes` is called with the final output set (or to pass a `&[TxOut]`/`tx_outs` slice rather than `payments`), for both the no-change and change calls, so `needed_fee`, the dust/change decision, the min-relay check, and `MAX_STANDARD_TX_WEIGHT` all evaluate the same transaction that is actually signed and broadcast [7](#0-6) .

### Proof of Concept
Construct `SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` where `inputs` is a single scanned `ReceivedOutput` and `payments` is a single non-dust P2TR payment. Observe:
1. `tx.needed_fee() == fee_per_vbyte * vbytes`, where `vbytes` was computed over `inputs + payments` only (`send.rs:204-206`).
2. `tx.tx.output` contains an additional `TxOut { value: 0, script_pubkey: OP_RETURN <80 bytes> }` (`send.rs:194-202`) that contributes ~34+ vbytes to `tx.vsize()`.
3. `tx.fee() / tx.vsize() < fee_per_vbyte` — the signed transaction undershoots the requested fee rate, and if `fee_per_vbyte` was chosen as the minimum relay rate, the resulting transaction is under the policy floor while `TooLowFee` was never raised.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
