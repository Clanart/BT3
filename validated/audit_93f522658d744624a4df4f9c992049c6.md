Confirmed: the `unvote` function's active-pool check is inverted relative to its own documentation, creating a genuine, non-privileged self-lockout analogous to the Nexus validator report.

### Title
Users permanently lose ability to withdraw their vote-stake once a pool they voted on is deactivated - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.unvote()` is documented to let users retrieve their staked vlMGP-vote stake from a pool that has been deactivated, but the implementation reverts precisely in that scenario, permanently freezing the user's vote allocation and the corresponding portion of their locked MGP/mWOM. [1](#0-0) 

### Finding Description
`unvote()` is the designated unprivileged, user-callable exit path for a vote position: the NatSpec explicitly states "Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing." [2](#0-1) 

However, the actual guard does the opposite of what the comment promises — it reverts when the pool is **not** active, instead of only reverting (or allowing) when it **is** active:
```solidity
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
    if(!pool.isActive)
        revert PoolNotActive();
    ...
    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
}
``` [3](#0-2) 

Once a pool is deactivated (an ordinary, expected admin lifecycle event — not malicious), any user who has a non-zero vote in `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` for that pool can no longer call `unvote()` to reduce it, because the call unconditionally reverts with `PoolNotActive()`. The general `vote()` function also reverts for the same pool because it enforces `if (!pool.isActive) revert PoolNotActive();` for every `_lp` in the batch. [4](#0-3) 

This means there is no remaining path for the user to zero out their vote for that specific pool — `userVotedForPoolInVlmgp` and the aggregate `userTotalVotedInVlmgp[msg.sender]` remain stuck at their pre-deactivation values forever, and the user's staked position inside `IBribeRewardPool(pool.rewarder)` (set via `stakeFor` in a prior `vote()` call) can never be withdrawn through `withdrawFor`. [5](#0-4) 

### Impact Explanation
This directly parallels the Nexus analog: an ordinary user action (`unvote`, the designated self-service exit) becomes permanently blocked by a code defect (inverted condition), causing the user to lose access to funds/positions they legitimately control. Concretely:
1. The user's vlMGP votes remain locked against a dead pool, unable to be redirected to a currently active pool via `vote()` for that pool (since `vote()` also blocks inactive pools).
2. Because `VLMGP.startUnlock` requires `totalLockAfterStartUnlock >= IWombatBribeManager(wombatBribeManager).userTotalVotedInVlmgp(msg.sender)`, the stuck vote balance permanently prevents the user from unlocking the corresponding portion of their locked MGP, freezing those tokens indefinitely. [6](#0-5) 
3. Any bribe/reward stake held inside the deactivated pool's `IBribeRewardPool` rewarder also becomes permanently unretrievable, since `withdrawFor` is unreachable through the intended user-facing path.

This is a permanent (well beyond 24-hour) freeze of user funds/positions, not a privileged exploit — the trigger (pool deactivation) is a normal expected lifecycle action, and the loss is caused purely by the contract's own inverted logic, matching the "unprivileged wallet self-lockout due to code bug" bug class from the report.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the ordinary combination of (a) a user having voted for a pool, and (b) that pool later being deactivated by the protocol during its normal course of operations (pool retirement, rewarder migration, etc., which is an expected and periodically occurring admin action, not an attack). Once that combination occurs, every affected user is deterministically and permanently locked out — no attacker action or malicious intent is required.

### Recommendation
Fix the inverted condition in `unvote()` so that it succeeds specifically when the pool is inactive (or removes the active-check entirely, allowing unvoting regardless of pool status), matching the documented intent. Additionally, consider allowing users to reduce/zero their vote for an inactive pool via `vote()` as well, or provide a dedicated emergency-withdraw path from `IBribeRewardPool` that does not depend on `poolInfos[_lp].isActive`.

### Proof of Concept
1. User calls `vote([lpA], [1000])` while `lpA` is active — `userVotedForPoolInVlmgp[user][lpA] = 1000`, `userTotalVotedInVlmgp[user] = 1000`, and `IBribeRewardPool(rewarderA).stakeFor(user, 1000)` is executed. [7](#0-6) 
2. Admin calls `removePool`/deactivates `lpA` (sets `poolInfos[lpA].isActive = false` as part of normal pool lifecycle management — analogous contracts show `removePool` patterns elsewhere in the codebase, e.g. `wombat/WombatStaking.sol:501-505`). [8](#0-7) 
3. User calls `unvote(lpA)` to reclaim their 1000 vlMGP-vote stake — the call reverts with `PoolNotActive()` due to the inverted check. [9](#0-8) 
4. User calls `vote([lpA], [-1000])` to try to reduce via the general path — also reverts with `PoolNotActive()`. [10](#0-9) 
5. User's `userTotalVotedInVlmgp[user]` remains 1000 forever; calling `VLMGP.startUnlock(amount)` for the full locked balance reverts with `NotEnoughLockedMPG` because `totalLockAfterStartUnlock < userTotalVotedInVlmgp(user)`, permanently freezing that portion of the user's locked MGP and their stake inside the dead rewarder. [6](#0-5)
