### Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL based on trusted GitHub API `clone_url` - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The reported Polynomial bug is about the protocol trusting a previously-approved external value (a collateral's nominal transfer amount) and applying it to internal state without re-validating the actual outcome, with no mechanism to revoke trust once conditions change. The GitHub Desktop analog is `updateRemoteUrl`, which trusts a GitHub API response (`apiRepo.clone_url`) as authoritative and silently rewrites the local Git `origin` remote to that value whenever a set of heuristic conditions match, without any user confirmation, unlike the analogous "upstream remote" flow which explicitly prompts the user via `UpstreamAlreadyExists`.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` fetches repository metadata from the GitHub API (`api.fetchRepository(owner, name)`) and, if the repo already has an associated `gitHubRepository`, calls: [1](#0-0) 

into `updateRemoteUrl`: [2](#0-1) 

The function decides to silently call `gitStore.setRemoteURL` (which runs `git remote set-url origin <url>`) based only on:
1. protocol staying the same (`http:`/`https:`), and
2. the *previous* API-reported clone URL matching the *current* remote URL (`remoteUrlUnchanged`). [3](#0-2) 

There is no user prompt, no diff shown, and no way to opt out or "disapprove" this automatic remote rewriting — unlike the deliberately-designed `UpstreamAlreadyExists` dialog used for the fork-upstream-remote case, which requires explicit user consent (`onUpdate` / `onIgnore`): [4](#0-3) 

`urlMatchesRemote` (used to decide `urlsMatch`/`remoteUrlUnchanged`) only compares hostname/owner/name in a case-insensitive way — it does not verify TLS pinning, account ownership, or that the API's `clone_url` genuinely still refers to a repository the user trusts: [5](#0-4) 

Because `apiRepo` is data returned from the GitHub API (attacker-influenced if the account's GitHub Enterprise endpoint is malicious/compromised, or if a repository is renamed/transferred and its `clone_url` changes while the owner/name portion still parses to match the old cached value), the local `origin` remote can be silently repointed to a different, attacker-controlled URL. This corrupts a critical piece of "what the user commits or pushes" state — the destination of the next `git push`/`git fetch` — without any user-visible warning, mirroring the seed report's core defect: the code trusts an externally-supplied value at face value and updates internal (position/remote) state without giving the operator any way to be warned or to opt out.

### Impact Explanation
If `origin` is silently rewritten to an attacker-controlled URL:
- Subsequent `git push` operations would send the user's code/commits to a different, potentially attacker-controlled remote, which is a form of "silent corruption of what the user commits or pushes."
- Subsequent `git fetch`/`git pull` would pull refs from that attacker-controlled remote into the user's working repository (already covered generally by desktop's remote/fetch trust model, but this path reaches it without any user action or awareness).
- Because there is no dialog (unlike the upstream-remote case), the user has no chance to notice or reject the change, and no built-in mechanism exists to "disapprove"/pin a remote once set from the API — analogous to the seed report's core complaint that there's no way to stop trusting a previously-approved external value once conditions change.

### Likelihood Explanation
This path is reached routinely during passive/background operations (`repositoryWithRefreshedGitHubRepository`, called e.g. on account changes and repository refresh), and requires only that: the user's GitHub/Enterprise API endpoint returns a `clone_url` for a matching owner/name whose hostname/owner/name (post `parseRemote`) match the previously cached clone URL, and the URL scheme (http/https) is unchanged. This is plausible under a compromised/malicious GitHub Enterprise server, a DNS/hostname take-over scenario, or an owner-name collision, none of which require local access, admin rights, or prior malware — matching the in-scope threat model ("attacker controls ... a GitHub API object").

### Recommendation
- Require explicit user confirmation before rewriting an existing remote URL based on API data, mirroring the `UpstreamAlreadyExists` pattern already used for upstream remotes.
- Do not silently trust `clone_url` from the API for pre-existing repositories; instead, surface a diff (old vs. new URL) and let the user accept/reject, with an option to pin/lock the remote so future automatic updates are suppressed ("disapprove" future changes), directly addressing the seed report's core recommendation.
- Strengthen `urlMatchesRemote`/`urlsMatch` to include stronger provenance checks (e.g., matching repository ID, not just owner/name string equality) before considering two URLs "the same repository."

### Proof of Concept
1. User has a repository with `origin` pointing to `https://github.com/acme/widget`, cached `gitHubRepository.cloneURL === 'https://github.com/acme/widget'`.
2. Desktop calls `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository('acme', 'widget')` — this API call could be served by a compromised endpoint (or reflect a rename where owner/name still normalizes the same, e.g. a case-only or trailing-slash difference through `parseRemote`) and returns `clone_url: 'https://github.com/acme/widget-fork-mirror'` or similar attacker-hosted mirror while `urlMatchesRemote` heuristics still evaluate `remoteUrlUnchanged=true` and `protocolsMatch=true`.
3. `updateRemoteUrl` computes `urlsMatch=false` (new URL differs) but `protocolsMatch && remoteUrlUnchanged && !urlsMatch` evaluates true, so it calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)` — see condition at: [6](#0-5) 
4. `origin` is now silently repointed with no dialog shown to the user (contrast with `upstream-already-exists.tsx` dialog for the equivalent upstream case), and the next push/fetch operates against the new, unverified remote.

Note: I was not able to fully trace every caller/trigger path for `repositoryWithRefreshedGitHubRepository` (e.g., exact background refresh cadence) within the available index; a Devin session with full repo access would be needed to enumerate all call sites and confirm exploitability end-to-end (e.g., whether `parseRemote`/`urlMatchesRemote` normalization allows an attacker-chosen distinct URL to satisfy `remoteUrlUnchanged` while differing from the true origin).

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
