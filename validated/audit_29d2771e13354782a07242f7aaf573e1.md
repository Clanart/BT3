### Title
Null-input orders permanently block cross-chain cancellation via zero-amount existence check - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` fails to validate that `order.inputs[i].amount != 0` when the predispatch path is used, unlike the direct-transfer path (and unlike the mainline `evm/src/apps/IntentGatewayV2.sol`, which enforces the check in both paths). This lets a user place an order containing a zero-amount input token. `cancelOrder`'s cross-chain branch then loops over `order.inputs` and treats `_orders[commitment][token] == 0` as "unknown order," reverting the entire cancellation for a legitimate order that happens to include a null-amount leg — mirroring the Autonolas H-05 pattern of a $0 deposit later causing an existence-check revert that can never be bypassed.

### Finding Description
In `placeOrder` (predispatch branch), the source-side per-asset checks only validate `order.predispatch.assets[i].amount != 0` [1](#0-0) , but the subsequent loop building `transferCalls`/escrow for `order.inputs` never checks `order.inputs[i].amount == 0` before writing `_orders[commitment][token] += reducedInputs[i].amount` [2](#0-1) . If `order.inputs[i].amount` is `0`, `reducedInputs[i].amount` is also `0` (since `protocolFee = (0 * bps)/10000 = 0`), so this leg legitimately reaches `emit OrderPlaced` with a stored escrow value of exactly zero for that token.

By contrast, the non-predispatch (direct transfer) branch explicitly reverts on this condition: `if (order.inputs[i].amount == 0) revert InvalidInput();` [3](#0-2) . This asymmetry means the zero-amount guard is missing specifically on the predispatch code path, letting an attacker who supplies predispatch calldata smuggle a valid order with a null-amount input leg — analogous to how the Autonolas lockbox's `_getPositionData` was missing a liquidity != 0 check for one particular path.

`cancelOrder`'s cross-chain branch subsequently loops over every `order.inputs[i]` and uses the value stored in `_orders[commitment][token]` purely as an existence check:
```solidity
for (uint256 i; i < inputsLen;) {
    // check for order existence
    if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();
    unchecked { ++i; }
}
``` [4](#0-3) 

For a genuinely-placed order that legitimately contains a zero-amount input leg (permitted by the predispatch path), this check reads `0 == 0` and unconditionally reverts with `UnknownOrder()` — even though the order commitment is real and other input tokens in the same order have nonzero escrow. There is no way to bypass this loop once such an order exists: it always runs over every input index, and `revert` unwinds the whole call, so the order can never take the cross-chain cancel/refund path.

### Impact Explanation
This freezes the source-chain cancellation/refund flow for any order that contains a zero-amount input leg placed via the predispatch route. The user's genuinely-escrowed non-zero inputs on the same order commitment become permanently unrecoverable through `cancelOrder`'s cross-chain branch (the only mechanism to reclaim funds for unfilled cross-chain orders after expiry) — a direct loss/lock of user funds, matching the "stealing or loss of funds" bounty category. It is a public entry point (`placeOrder` is unprivileged, `cancelOrder` is callable by the order owner or, post-deadline, by anyone) reachable without any relayer, prover, or governance involvement.

### Likelihood Explanation
Any user calling `placeOrder` with `order.predispatch.call.length > 0 && order.predispatch.assets.length > 0` and at least one `order.inputs[i].amount == 0` triggers this — no privileged role, malicious relayer, or race condition required. It is a self-inflicted or attacker-inflicted state, requiring only a normally-formed transaction with a crafted `order.inputs` array.

### Recommendation
Add the same guard used in the non-predispatch branch to the predispatch branch: revert with `InvalidInput()` if `order.inputs[i].amount == 0` before building `transferCalls`, mirroring `evm/src/apps/IntentGatewayV2.sol`'s treatment of both paths symmetrically. Additionally, `cancelOrder`'s existence check should not rely purely on `_orders[commitment][token] == 0`; it should instead validate against a dedicated "order placed" marker (e.g., a separate existence mapping/commitment set) so that legitimate zero-value entries cannot be mistaken for "no such order."

### Proof of Concept
1. Attacker/user calls `placeOrder` with `order.predispatch.call` and `order.predispatch.assets` both non-empty, and `order.inputs = [{token: TOKEN_A, amount: 100}, {token: TOKEN_B, amount: 0}]`.
2. The predispatch-assets loop only requires `predispatch.assets[i].amount != 0`; it does not touch `order.inputs`, so it passes [1](#0-0) .
3. The subsequent `order.inputs` loop stores `_orders[commitment][TOKEN_A] = 100 - fee` and `_orders[commitment][TOKEN_B] = 0` with no revert, since there is no zero-amount check in this branch [2](#0-1) .
4. `OrderPlaced` is emitted; the order is fully valid on-chain with a real, nonzero `TOKEN_A` escrow.
5. Order goes unfilled past `order.deadline`. The user calls `cancelOrder` from the source chain to trigger the cross-chain cancel path.
6. The loop at lines 540–548 hits `i` corresponding to `TOKEN_B`, reads `_orders[commitment][TOKEN_B] == 0`, and reverts with `UnknownOrder()` — freezing the entire cancellation and permanently locking the escrowed `TOKEN_A` funds.
