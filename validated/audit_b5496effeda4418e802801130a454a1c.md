### Title
Unauthenticated SSRF via arbitrary DataLayer mirror URLs fetched by peer nodes - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can create a DataLayer "mirror" record via the `dl_new_mirror` RPC, attaching arbitrary attacker-controlled URLs to a store id. Any other node subscribed to that store id will later automatically fetch those URLs via `http_download`/`get_downloader`, causing that peer's own machine to issue outbound HTTP requests to attacker-chosen hosts — a classic SSRF pattern, directly analogous to the Mautic Focus SSRF where user-supplied URLs are fetched server-side without restricting the destination.

### Finding Description
`dl_new_mirror` in `chia/wallet/wallet_rpc_api.py` lets a wallet owner create an on-chain mirror coin for any `launcher_id`/store id with a list of caller-supplied `urls`, with no scheme/host/IP validation: [1](#0-0) 

These URLs are only encoded (`Mirror.encode_urls`) and stored/announced on chain; there is no validation of scheme, host, or target (e.g., no rejection of `http://127.0.0.1`, `http://169.254.169.254`, internal RFC1918 ranges, or non-HTTP schemes).

Once a mirror is published, `DataLayer.update_subscriptions_from_wallet()` pulls all mirror URLs for a store id it is subscribed to and stores them locally as candidate servers: [2](#0-1) 

Later, the periodic sync loop (`fetch_and_validate`) randomly selects one of these server URLs and issues an outbound request to it via `http_download`, with no destination filtering: [3](#0-2) [4](#0-3) 

This means the mirror URL, entirely attacker-controlled, is fetched directly by every peer's local `DataLayer` process that subscribes to (or already tracks) that store — hitting arbitrary hosts/ports, including internal-network or loopback addresses on the victim's own machine, with no server-side URL validation analogous to Mautic's unsanitized Focus URL fetch.

### Impact Explanation
An attacker who creates any DataLayer store (trivial, unprivileged action) and adds a mirror with a malicious URL (e.g., `http://127.0.0.1:<internal-port>/...` or an internal-network address) can force any other DataLayer node that subscribes to that store to send outbound HTTP requests to attacker-chosen destinations from the victim's own host or network. This enables internal port scanning/probing and reconnaissance of firewalled infrastructure behind the victim's DataLayer node, matching CWE-918 (SSRF) impact class (confidentiality/integrity of internal network mapping), consistent with the Medium severity of the Mautic advisory.

### Likelihood Explanation
Likelihood is moderate-to-high: creating a store and adding a mirror only requires normal wallet RPC access (`create_new_dl`, `dl_new_mirror`) and a small on-chain fee — no special privilege. Any third party who subscribes to that store id (a normal, expected DataLayer workflow) will automatically trigger the fetch during periodic `update_subscription()`/`fetch_and_validate()` cycles without further victim interaction.

### Recommendation
Validate and restrict mirror URLs before persisting/using them: enforce an allow-listed scheme (`http`/`https` only), resolve and reject loopback/link-local/private/multicast/metadata-service IP ranges, and optionally allow operators to configure a strict host allow-list for DataLayer mirror fetches. Apply this validation both at `dl_new_mirror` (to discourage publishing) and at `update_subscriptions_from_wallet`/`fetch_and_validate`/`http_download` (defense-in-depth against externally-sourced mirror lists).

### Proof of Concept
1. Attacker creates a DataLayer store via `create_new_dl` and calls `dl_new_mirror` with `urls=["http://127.0.0.1:8555/some-internal-path"]` (or an internal RFC1918/metadata address).
2. Victim's DataLayer node discovers this store (e.g., via `dl_track_new`/subscription) and calls `update_subscriptions_from_wallet`, which stores the malicious URL as a subscription server (`chia/data_layer/data_layer.py:979-985`).
3. During the victim's periodic `fetch_and_validate` cycle, the victim node calls `http_download` against the attacker's URL (`chia/data_layer/download_data.py:298-323`), causing the victim host to issue an outbound HTTP request to the attacker-chosen internal target, confirmed via response timing/error behavior or an attacker-controlled listener capturing the request.

        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,

            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            await dl_wallet.create_new_mirror(
                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
            )

        # tx_endpoint will take care of default values here
        return DLNewMirrorResponse(unsigned_transactions=[], transactions=[])

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
