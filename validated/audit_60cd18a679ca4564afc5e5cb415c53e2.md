### Title
TextFormat parse-error messages embed raw attacker-supplied field values, which are logged via the default `ErrorCollector` bypassing field redaction - (File: `src/google/protobuf/text_format.cc`)

### Summary
The mapstructure CVE's failed invariant is: detailed decode-error messages embed the raw attacker-supplied input value, and that message is surfaced to logs without any sensitivity-aware redaction. In `protobuf`'s C++ `TextFormat::Parser`, malformed-value parse errors are constructed with `ReportError(...)` calls that directly concatenate the raw token text taken from the tokenizer into the error string (e.g. `"Invalid float number: " + text`, `"Cannot skip field value, unexpected token: " + text`) at [1](#0-0) . Confirmed observable behavior for this pattern is in the unit test expectations, e.g. `"Invalid value for boolean field \"optional_bool\". Value: \"meh\"."` [2](#0-1) , and similarly Python's text_format raises `ParseError('Invalid field value: ' + tokenizer.token)` embedding the raw token [3](#0-2) .

### Finding Description
`TextFormat::Parser::Parse` documents that on failure "an error will also be logged to `ABSL_LOG(ERROR)`" by default [4](#0-3) . The redaction machinery (`debug_redact` field option, `TryRedactFieldValue`, `enablingSafeDebugFormat`) that Protobuf built specifically to prevent sensitive field values from leaking into debug/log output [5](#0-4)  only applies to the `Printer`/`DebugString` serialization path, not to the parser's error-reporting path. When `SkipFieldValue`/`ConsumeFieldValue` hit an invalid or unparseable token, the raw token text is embedded verbatim into the error string via `ReportError` (e.g., `absl::StrCat("Invalid float number: ", text)`) [6](#0-5) . This text is attacker-controlled: it is exactly the substring of the input TextFormat payload the attacker supplied. Because the redaction check (`shouldRedact`/`debug_redact`) is never consulted in this code path, there is no mechanism to prevent a value intended for a `debug_redact=true` field from appearing in the parse-error message and, consequently, in `ABSL_LOG(ERROR)` output.

### Impact Explanation
If an application logs or displays `TextFormat` parse failures (a common pattern for config/RPC debugging), and a field marked `debug_redact=true` (intended to hold credentials/secrets) receives a malformed value from an untrusted source, the raw secret-adjacent value could be echoed into application logs — the same "information disclosure through detailed error messages... via malformed user-supplied data" pattern described in the mapstructure advisory. This is analogous confidentiality impact (C:H, I:N, A:N) with no memory-safety or availability effect.

### Likelihood Explanation
This requires: (1) the consuming application to actually surface/log `TextFormat` parse errors (default behavior logs to `ABSL_LOG(ERROR)`), and (2) an attacker-controlled/malformed value for a `debug_redact` field to trigger a scalar-parse failure. This is a real, low-friction trigger path — no special privileges needed, just supplying malformed TextFormat input — but the actual sensitivity depends on the application's schema using `debug_redact` and on whether parse-error logs are exposed to the attacker or a lower-trust log sink.

### Recommendation
Investigate whether `ParserImpl::ReportError` (and equivalent code paths in Python/Java text_format implementations) should consult `FieldDescriptor::options().debug_redact()` for the specific field being parsed before embedding the raw token text into the error string, replacing it with a redacted placeholder analogous to `kFieldValueReplacement` used by the `Printer`.

### Proof of Concept
I was not able to fully verify this within my remaining tool budget — specifically I could not confirm the exact `ReportError` implementation/signature that ties into `ABSL_LOG(ERROR)` (my last `grep_search` for `ReportError`/`ABSL_LOG(ERROR)` definitions in `text_format.cc` returned only a match count without content, cutting off before I could read the actual `ReportError` function body). What is confirmed via unit tests is that invalid scalar-field TextFormat input (e.g., `optional_bool: meh`) produces an error string containing the raw value verbatim: `"Invalid value for boolean field \"optional_bool\". Value: \"meh\"."` [2](#0-1) . A minimal reproduction concept: define a message with a `string` (or similarly redacted) field marked `[debug_redact = true]`, feed a TextFormat payload that causes a scalar-parse failure at that field (e.g., an invalid enum or int value on a redacted field), and inspect whether the resulting `ParseError`/`ABSL_LOG(ERROR)` output contains the raw attacker-supplied text. I did not execute this reproduction, so this should be treated as an unverified analog requiring confirmation via an actual test run.

**Caveat:** Given the incomplete verification of `ReportError`'s exact logging sink and whether any redaction check exists elsewhere in that call chain that I didn't locate, I'd rate confidence in this analog as moderate, not high. A background engineering session with full read access to `text_format.cc`, `text_format.h`, and the Java/Python equivalents would be needed to conclusively confirm or refute this transfer.

  if (redaction_state.redact) {

        if (single_line_mode_) {
          generator->PrintLiteral(" ");
        } else {

        }
      }
