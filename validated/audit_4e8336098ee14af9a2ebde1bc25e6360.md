### Title
Symlink-following arbitrary file overwrite via `.claude/ralph-loop.local.md` in setup-ralph-loop.sh - (File: plugins/ralph-wiggum/scripts/setup-ralph-loop.sh)

### Summary
`setup-ralph-loop.sh` writes the Ralph loop state via `cat > .claude/ralph-loop.local.md <<EOF` without checking whether that path already exists as a symlink. Since shell `>` redirection follows symlinks and truncates/writes the link target, an attacker who can plant a symlink at that path (e.g., via malicious repository content committed to `.claude/ralph-loop.local.md`) can redirect the write to any file the invoking user can write to, outside the intended `.claude/` directory.

### Finding Description
The script does:
```bash
mkdir -p .claude
...
cat > .claude/ralph-loop.local.md <<EOF
...
EOF
``` [1](#0-0) 

There is no `-L`/`readlink`/`test -h` check anywhere in this script (or in `stop-hook.sh`, which later re-opens and rewrites the same path via `sed ... > "$TEMP_FILE"; mv "$TEMP_FILE" "$RALPH_STATE_FILE"`) to detect that `.claude/ralph-loop.local.md` is a symlink before writing to it. [2](#0-1) 

Attack flow: an attacker who controls repository content the victim will clone/open (e.g. a poisoned public repo, or a PR branch) commits a file at `.claude/ralph-loop.local.md` that is a symlink pointing to some other path writable by the victim's OS user (e.g. `~/.bashrc`, `~/.ssh/authorized_keys`, another project's config file, or any file the user's process can write). When the victim opens the repo in Claude Code and runs `/ralph-loop <prompt>`, the script's `mkdir -p .claude` is a no-op (directory already exists from checkout), and the `cat > .claude/ralph-loop.local.md <<EOF` heredoc redirection follows the symlink and overwrites the target file's contents with the Ralph state markdown, entirely outside `.claude/`. No allowlist, workspace guard, or path canonicalization exists in this script to prevent this.

### Impact Explanation
This is an arbitrary file overwrite constrained only by the invoking user's own filesystem permissions — i.e., a workspace-confinement bypass where a plugin script writes outside the `.claude/` directory it is supposed to be scoped to. Depending on the symlink target, this could corrupt user dotfiles/shell rc files, other project files, or (if the target is something like `~/.ssh/authorized_keys` or a shell profile) lead to follow-on code execution the next time the shell/profile is loaded. This matches "unauthorized file action / workspace escape" impact category, though it is bounded to files the OS-level user can already write (no privilege escalation beyond the user's own account).

### Likelihood Explanation
Requires the attacker to get a symlink checked into repository content that the victim subsequently opens with Claude Code and then explicitly runs `/ralph-loop` on. This is a normal, low-effort attack vector (malicious/poisoned public repo, malicious branch/PR) reachable through ordinary repository content, and does not require any special privilege beyond the victim opening the repo and running the command — a plausible and repeatable scenario for any plugin that blindly writes state files by path.

### Recommendation
Before writing, verify the target path is not a symlink (or resolve and confirm it stays within the intended `.claude` directory), e.g.:
```bash
if [[ -L ".claude/ralph-loop.local.md" ]]; then
  echo "❌ Error: refusing to write through symlink at .claude/ralph-loop.local.md" >&2
  exit 1
fi
```
Alternatively write to a temp file inside `.claude/` and `mv` it atomically only after confirming the destination is a regular file or does not exist, or use `install -m 0644 --no-target-directory` semantics / `noclobber`-safe patterns. Apply the same guard in `hooks/stop-hook.sh` before its `sed ... > "$TEMP_FILE"; mv` update, and also verify `.claude` itself is a real directory (not a symlink) before `mkdir -p`/writing into it.

### Proof of Concept
Unit/integration test:
1. In a fresh temp workspace, create a sentinel file `victim.txt` with known content outside `.claude/`.
2. Run `mkdir -p .claude && ln -s "$(pwd)/victim.txt" .claude/ralph-loop.local.md`.
3. Invoke `setup-ralph-loop.sh "test prompt"`.
4. Assert: `victim.txt` content is unchanged (or the script errors out refusing to proceed) — currently, running the script will overwrite `victim.txt` with the Ralph frontmatter/prompt content, and `readlink .claude/ralph-loop.local.md` will still show it as a symlink pointing to `victim.txt`, proving the write escaped `.claude/`.
5. Expected secure behavior: the script should detect the symlink and exit non-zero without touching `victim.txt`, or write only through a path verified to resolve inside `.claude/`.
