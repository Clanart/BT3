### Title
Stale line-selection is applied against a freshly re-fetched diff, allowing silent corruption of partially-committed content - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop lets a user commit only a subset of lines in a modified file (partial/line-level staging). The user's line selection (`DiffSelection`) is built by the renderer against a diff snapshot taken when the Changes view loads a file's diff. When the commit is actually performed, Desktop re-fetches a *brand-new* diff of the working directory (`getWorkingDirectoryDiff`) and reuses the *old* selection object (with absolute line indices) against that fresh diff to build the patch that is `git apply --cached`'d into the index. If the file's on-disk content differs between the time the diff was shown/selected and the time staging happens, the index-based selection no longer corresponds to the same lines, and the wrong hunks/lines get silently staged and committed — with no diff/hash comparison to detect the mismatch.

### Finding Description
The renderer computes the diff to display and to build the selection UI in `updateChangesWorkingDirectoryDiff`: [1](#0-0) 

The user's partial-line selection (`DiffSelection`) records only *absolute line indices* (`unifiedDiffStart`/offsets) — it carries no reference to file content or diff identity: [2](#0-1) 

When the commit is issued, `_commitIncludedChanges` passes the working-directory `WorkingDirectoryFileChange` objects (which still carry the old `DiffSelection`) straight to `createCommit`: [3](#0-2) 

`createCommit` → `stageFiles` → `applyPatchToIndex` for any file with a partial selection re-runs `getWorkingDirectoryDiff` to get a **fresh** diff and then formats a patch by walking that fresh diff's lines and checking `file.selection.isSelected(absoluteIndex)` — using the *old* indices against the *new* diff: [4](#0-3) [5](#0-4) 

There is no check anywhere in this path that the diff used to build the selection is the same diff being staged (no hash/etag/mtime comparison of the file or diff content). This is structurally identical to the reported oracle bug: two different "prices" (diffs) are fetched at two different points, and stale data from the first fetch is combined with fresh data from the second to produce an inconsistent, exploitable result — except here the "profit" is silent corruption of commit content rather than financial arbitrage.

### Impact Explanation
If the working tree content changes between the diff render/selection step and the commit/staging step (e.g., a build tool, editor auto-format-on-save, a git `clean`/`smudge` filter defined by `.gitattributes` in a cloned/fetched malicious repository, or any background process touching the file), `formatPatch` walks stale absolute indices over new hunk content. Depending on how hunks shifted, this can:
- Select/deselect the wrong lines, staging content the user never reviewed or omitting content the user intended to include.
- Because `git apply` is invoked with `--unidiff-zero --whitespace=nowarn`, zero-context patches can apply "successfully" even when they no longer correspond to the reviewed hunk, silently corrupting what actually gets committed and later pushed — matching the "silent corruption of what the user commits or pushes" impact category.

This is most exploitable when a malicious/cloned repository ships a `.gitattributes`-defined smudge/clean filter or checkout-time content transform that Desktop applies to files as part of normal working-directory operations, causing file content served by consecutive `git diff` invocations to differ without any explicit user action — the attacker fully controls the repository content and filter definitions, satisfying the "attacker controls a cloned/fetched repository" requirement.

### Likelihood Explanation
Medium. It requires a narrow race window between diff-render and commit, and a mechanism that changes tracked file content in that window without altering the file's on-disk mtime tracked by Desktop's status cache (or a legitimate content-changing mechanism such as a smudge filter, external formatter/linter running on save, or a background sync tool). The requirement of "content changes between two diff fetches in the same logical operation" is exactly the same pattern acknowledged as valid (Medium-severity) in the source report for the Pyth oracle bug, so the underlying bug class is realistic; however, unlike the financial oracle case, GitHub Desktop's own UI generally discourages committing while continuing to edit a file, which lowers but does not eliminate the practical likelihood.

### Recommendation
Before staging a partially-selected file, do not re-fetch a brand-new diff independent of the one the user's selection was built from. Instead:
- Persist the diff (or a content hash of the working-directory blob) alongside the `DiffSelection` at the time the selection was made, and pass that exact diff through to `applyPatchToIndex`/`formatPatch` instead of re-querying `getWorkingDirectoryDiff` at apply time.
- If the working directory content hash differs from the one captured when the selection was made, refuse to stage/commit the file and force the user to re-review the diff/selection.

### Proof of Concept
1. Open a modified tracked file in Desktop's Changes view; Desktop calls `getWorkingDirectoryDiff` and displays hunks, and the user makes a partial line selection (e.g., selects only hunk 1) — `app/src/lib/stores/app-store.ts:3444`.
2. Before clicking "Commit", have the file's tracked content change via a mechanism outside direct further user editing (e.g., a `.gitattributes` smudge/clean filter shipped in the cloned repository re-writes the file on the next `git diff`/checkout invocation, or an external tool touches the file).
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-invokes `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`), producing a diff with shifted/different hunks than the one the user reviewed.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-201`) uses the old `file.selection.isSelected(absoluteIndex)` against the new hunk lines, producing a patch that doesn't correspond to what the user actually selected.
5. `git apply --cached --unidiff-zero --whitespace=nowarn` stages this mismatched patch without error, and the resulting commit silently contains different content than what the user reviewed and intended to commit.
