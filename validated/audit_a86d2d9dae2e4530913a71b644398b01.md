### Title
SSRF via unauthenticated on-chain DataLayer mirror coins with no URL/host validation before HTTP fetch - (File: chia/data_layer/data_layer_wallet.py, chia/data_layer/data_layer.py, chia/data_layer/download_data.py)

### Summary
DataLayer mirror URLs are accepted from on-chain coin memos with no ownership check on who created the coin and no SSRF filtering (no loopback/private-IP/host validation of any kind) before the DataLayer service fetches those URLs over HTTP. This is a stronger, unfiltered analog of the PraisonAI `spider_tools` bug class (CWE-918): where PraisonAI at least attempted a (bypassable) blocklist, Chia's DataLayer mirror-fetch path performs *no* validation at all.

### Finding Description
Any coin whose puzzle hash equals the fixed `create_mirror_puzzle()` hash is treated as a "mirror" coin by every node tracking the referenced `launcher_id`, regardless of who created/spent that coin: [1](#0-0) 

`coin_added()` extracts `launcher_id` and `urls` purely from the parent coin's puzzle reveal/solution memos via `get_mirror_info()`, and if that `launcher_id` is tracked locally it stores the mirror with attacker-supplied URLs, without any check that the spender controls or is authorized for that store/launcher: [1](#0-0) 

The service-level `add_mirror()` merely rejects an empty URL list — it performs no scheme/host/IP validation whatsoever: [2](#0-1) 

These mirror URLs are later pulled into `update_subscriptions_from_wallet()` and consumed by `fetch_and_validate()`, which randomizes and iterates the reported server URLs and calls `insert_from_delta_file()` → `download_file()`: [3](#0-2) 

`download_file()` performs the HTTP GET (`http_download`) or plugin POST directly against `server_info.url`, with no host/IP filtering, no loopback/private-network blocklist, and no DNS-resolution check of any kind: [4](#0-3) 

The project's own module notes confirm mirror/plugin URLs are treated only as untrusted *data* sources (i.e., the downloaded file content is verified against the wallet root), but never says the URL/host itself is validated against SSRF targets: [5](#0-4) [6](#0-5) 

This is architecturally analogous to the PraisonAI report: an attacker-influenced URL flows into an HTTP client (`aiohttp`) with no protection against loopback/link-local/private targets. In Chia's case the exposure is broader, since there is no blocklist attempt at all (vs. PraisonAI's weak exact-string check), and the URL is attacker-injectable purely by broadcasting a cheap coin spend with the right puzzle hash/memo — the attacker does not need to own the DataLayer store, be the wallet operator, or have any RPC privilege.

### Impact Explanation
Any user who can submit a spend bundle to the mempool can create a low-value coin with puzzle hash `create_mirror_puzzle()` and memos naming any tracked `launcher_id` plus an arbitrary URL. Any full node/wallet running the DataLayer service that tracks (subscribes to) that store will, on its next periodic sync cycle, issue outbound HTTP(S) requests to the attacker-chosen URL/host — including loopback addresses, link-local/metadata endpoints, or other internal-only services reachable from that host. This can be used to probe or interact with local-only administrative/RPC endpoints on the machine running the DataLayer service, matching the confidentiality-impact profile of the referenced advisory (`C:H`). No signature or ownership of the target store is required to inject the URL.

### Likelihood Explanation
Likelihood is high for any DataLayer operator subscribing to third-party stores (the intended, documented use case for mirrors/subscriptions): the attacker only needs to spend a coin with a specific, publicly-known puzzle hash and arbitrary memo bytes, which costs a standard mempool fee and requires no special privilege, ownership, or timing. The periodic subscription-management loop (`periodically_manage_data()` / `update_subscription()`) automatically discovers and fetches these attacker-provided URLs without any operator action.

### Recommendation
Before dereferencing any mirror or plugin URL (`chia/data_layer/data_layer.py::add_mirror`/`update_subscriptions_from_wallet`, `chia/data_layer/download_data.py::download_file`), resolve the target host and reject requests whose resolved IP falls in loopback, link-local, private, or other non-public ranges (and reject alternate encodings such as octal/hex/decimal IPv4 forms and trailing-dot hostnames by normalizing before comparison, per the referenced CVE guidance). Additionally, consider requiring mirror coins to be validated against ownership/authorization of the referenced `launcher_id` before being trusted as sync sources, rather than accepting mirrors from any coin matching the fixed puzzle hash.

### Proof of Concept
1. Attacker crafts and broadcasts a spend bundle creating a coin with puzzle hash `create_mirror_puzzle().get_tree_hash()` and memos `[launcher_id, b"http://127.0.0.1:PORT/"]` (or `http://169.254.169.254/`, `http://0x7f000001/`, etc.), where `launcher_id` is any store the target node/wallet is tracking. [1](#0-0) 
2. Once confirmed, the tracking wallet's `coin_added()` records this as a `Mirror` with the attacker URL, with no authorization check against the store owner. [7](#0-6) 
3. On the next DataLayer sync cycle, `update_subscriptions_from_wallet()`/`fetch_and_validate()` pick this URL as a candidate server and call `download_file()`, which issues an HTTP GET directly to the attacker-controlled host with zero SSRF filtering. [3](#0-2) [4](#0-3) 
4. The DataLayer host process makes an outbound request to the loopback/internal target, confirming the SSRF.

        self, coin: Coin, height: uint32, peer: WSChiaConnection, coin_data: object | None, sync_scope: WalletSyncScope

            )[0]
            parent_spend = await fetch_coin_spend(height, parent_state.coin, peer)

                        uint64(coin.amount),
                        Mirror.decode_urls(urls),
                        ours,
                        height,
                    )
                )
                await self.wallet_state_manager.add_interested_coin_ids([coin.name()])

async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
- DataLayer wallet code depends on singleton CLVM structure, odd singleton amounts, lineage proofs, and offer solver field names. Changes in wallet puzzle drivers or offer summaries can break this module without direct edits here.
