### Title
Unrestricted `superApprove` on `HyperFungibleTokenImpl` allows any address to grant itself unlimited allowance over any holder's balance - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.superApprove(address owner, address spender)` is a `public` function with **no access control** that internally calls `_approve(owner, spender, type(uint256).max)`. Any unprivileged caller can invoke it with arbitrary `owner`/`spender` arguments, which means an attacker can pre-set `allowance[owner][attacker] = max` for any account, including a bridge custody/fee-token holder that will later receive minted or bridged funds.

### Finding Description
`superApprove` is meant, per its own docstring, as a "Helper function for tests," but it is defined directly in the production implementation contract `evm/src/utils/HyperFungibleTokenImpl.sol` (lines 110-117), not gated behind any `onlyRole`/`onlyOwner` modifier, and not excluded from production deployment: [1](#0-0) 

This contract is not a test-only artifact — it is deployed by the production deployment script `evm/script/DeployIsmp.s.sol` as the actual fee token (`feeTokenInstance`) used by `EvmHost`, with a `TokenFaucet` granted `MINTER_ROLE`: [2](#0-1) 

Since `superApprove` takes `owner` as an arbitrary parameter (not `msg.sender`) and has no authorization check, an attacker can:
1. Call `superApprove(victim, attacker)` for any address `victim` that they anticipate will receive tokens (e.g., a bridge beneficiary or the host/faucet's minting target), before any funds arrive.
2. Wait for a `MINTER_ROLE` holder (e.g., `TokenFaucet`, or any future minting flow) to `mint(victim, amount)`.
3. Call `transferFrom(victim, attacker, amount)` using the pre-set max allowance to redirect the entire newly-minted/bridged balance to themselves.

This matches the standard ERC-20 "front-run/pre-approve" pattern, except here there is no front-running needed at all — the attacker does not need to race any transaction, since the malicious approval can be set at any time, arbitrarily far in advance, and remains valid indefinitely (`type(uint256).max`) until the victim explicitly revokes it (which they have no reason to do, since they never granted it and may not even monitor `Approval` events on this token).

### Impact Explanation
This directly satisfies the "stealing or loss of funds" and "unauthorized transaction or execution" impact categories. Any address that ever receives tokens minted by `HyperFungibleTokenImpl` (used as the network's fee token in the deployment script) can have its balance drained by an attacker who front-loaded an unlimited allowance, with no participation, error, or compromise required from the victim, minter, or any relayer/operator. Because the contract is the fee token used across the bridge deployment (`FEE_TOKEN` config, `EvmHost` fee accounting), draining a beneficiary's or custody account's balance here undermines bridge fee accounting and any cross-chain settlement value denominated in this token.

### Likelihood Explanation
High. The call requires no privilege, role, or special conditions — `superApprove` is `public` with no `onlyRole`/`onlyOwner` guard and no `msg.sender == owner` check. An attacker can call it cheaply and repeatedly against any address, including well-known bridge contracts (faucet, host, or beneficiaries), and simply wait for tokens to arrive.

### Recommendation
Remove `superApprove` from the production contract entirely, or move it into a test-only mock/helper contract that is never deployed via `DeployIsmp.s.sol`. If a test helper approve function is genuinely needed for `FeeToken.sol` (test contract), restrict it with `onlyRole(DEFAULT_ADMIN_ROLE)` or compile it only under test build profiles, and ensure it is never present in the bytecode used in the `deploy()` path of `DeployIsmp.s.sol`.

### Proof of Concept
1. Deploy `HyperFungibleTokenImpl` (as done in `DeployIsmp.s.sol`), granting `MINTER_ROLE` to `faucet`.
2. Attacker (no role) calls `token.superApprove(beneficiary, attacker)` — succeeds because there is no access check: [3](#0-2) 
3. `faucet` (MINTER_ROLE holder) later calls `token.mint(beneficiary, amount)`: [4](#0-3) 
4. Attacker calls `token.transferFrom(beneficiary, attacker, amount)`, which succeeds using the pre-set `type(uint256).max` allowance, transferring the beneficiary's entire balance to the attacker.
