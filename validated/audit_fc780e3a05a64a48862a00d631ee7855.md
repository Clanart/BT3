### Title
Hardcoded `_filled` mapping storage slot used for cross-chain fill-proof verification can silently desync from actual layout - ([File: evm/src/apps/intentsv2/IntentsBase.sol], [File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core defect is a mismatch between actual storage layout changes and a manually-tracked layout constant (`__gap`), which is not automatically re-derived from the compiler and can silently desync from reality. The direct Hyperbridge analog is `FILLED_SLOT_BIG_ENDIAN_BYTES`, a hardcoded constant asserting that the `_filled` mapping sits at storage slot `2`, used to build the raw storage-proof key that Hyperbridge's cross-chain fill/cancellation logic trusts as ground truth.

### Finding Description
`IntentGatewayV2` declares `_filled` (mapping `bytes32 => address`) and manually encodes its assumed slot as a literal constant: [1](#0-0) 

This constant is combined with a commitment to derive the exact storage key a remote state-proof must resolve to, via `calculateCommitmentSlotHash`: [2](#0-1) 

The main upgradeable EVM `IntentGatewayV2` (composed via `IntrinsicIntents`/`ExtrinsicIntents`/`IntentsBase` diamond inheritance) relies on the exact same slot-2 assumption, and the project's own test explicitly documents that correctness of the *cross-chain cancel proof* depends on this exact slot never moving: [3](#0-2) 

This is structurally identical to the reported bug class: a manually tracked storage offset (`__gap`, here `FILLED_SLOT_BIG_ENDIAN_BYTES`) that must be kept in perfect sync with the compiler-derived storage layout, with no automated enforcement other than an offchain/test-time check. Unlike a plain `__gap`, this slot constant is not just an upgrade-safety padding value — it is consumed as security-critical input to remote state-proof verification that determines whether an order was filled on the destination chain, gating refund/cancellation of escrowed funds on the source chain.

Any change to declaration order across the diamond inheritance chain (`IntentsBase` → `IntrinsicIntents`/`ExtrinsicIntents` → `IntentGatewayV2`), or divergence between the Tron flat-contract layout and the main proxy-based EVM layout, would shift `_filled` off slot 2 without any compiler-enforced guardrail tying `FILLED_SLOT_BIG_ENDIAN_BYTES` to the real slot.

### Impact Explanation
If the constant slot ever desyncs from the real slot of `_filled` (e.g., through a future refactor of `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` that adds or reorders a state variable ahead of `_filled`, or a discrepancy introduced when porting the Tron flat-contract layout), the destination-chain storage proof used to prove "order not filled" would instead resolve to whatever unrelated storage word now occupies slot 2. If that word reads as zero/empty, a source-chain cancellation/refund proof would incorrectly validate for an order that was actually filled by a solver, letting the escrowed input assets be refunded to the user via `cancelOrder` even though the filler already delivered assets and is separately paid out via `_filled` lookup on redemption — a double-settlement / duplicate-claim on the escrowed funds, i.e., direct loss of bridged funds.

### Likelihood Explanation
This is not exploitable by an ordinary external caller under the current, verified layout — the current slot-2 alignment is correct and pinned by a dedicated test. The risk materializes only through a future code change to the inheritance/layout that is not accompanied by an update to `FILLED_SLOT_BIG_ENDIAN_BYTES`, which is exactly the class of silent regression the external `__gap` report warns about: nothing in the compiler or runtime enforces the slot constant stays correct, only a single foundry test (`testFilledMappingStaysAtSlotTwo`). Given the diamond inheritance in the production EVM contract is significantly more complex than the flat Tron contract sharing the same hardcoded constant, the surface for an inadvertent slot shift during a routine feature addition is real, even though no such shift is proven to exist in the code as currently written.

### Recommendation
- Derive the fill-proof storage slot programmatically (e.g., via Solidity's `bytes32 internal constant FILLED_SLOT = <computed from a documented, single source of truth>`), or centralize it as a shared constant imported by every consumer (Tron, main EVM, tests) rather than independently hardcoded in each.
- Add an explicit inline storage-layout comment block (like `VaultStorage`'s recommended fix) directly above `_filled`'s declaration in `IntentsBase.sol` stating the required absolute slot and cross-referencing `FILLED_SLOT_BIG_ENDIAN_BYTES`.
- Turn `testFilledMappingStaysAtSlotTwo` into a CI-blocking invariant check that runs against every deployed variant (main EVM, Tron) on every PR that touches `IntentsBase`, `IntrinsicIntents`, or `ExtrinsicIntents`.
- Consider deriving the slot check via `forge inspect --storage-layout` on both contract variants automatically in CI rather than relying on a single hand-written regression test.

### Proof of Concept
Not exploitable against current code as verified — `testFilledMappingStaysAtSlotTwo` in `evm/tests/foundry/IntentGatewayV2Test.sol` confirms `_filled` is at slot 2 today. The exploit path is conditional/future-facing:
1. A developer adds a new state variable to `IntentsBase` (or reorders diamond inheritance) ahead of `_filled`, shifting it to slot 3, without updating `FILLED_SLOT_BIG_ENDIAN_BYTES`.
2. A solver fills a cross-chain order, populating the real `_filled[commitment]` at the new slot 3.
3. The user (or an attacker acting as the user) submits a state proof targeting slot 2 (still `FILLED_SLOT_BIG_ENDIAN_BYTES`), which now resolves to an unrelated, empty/zero storage word.
4. The destination-chain proof verifies "not filled," and the source-chain escrow is refunded via `cancelOrder`, while the filler still separately claims payment for having filled the order — resulting in duplicate payout from the same escrowed funds. [1](#0-0) [2](#0-1) [3](#0-2)

    /**
     * @notice Calculates the commitment slot hash required for storage queries.
     * @dev The commitment slot hash is used as part of the proof verification process
     * @param commitment The commitment value as a bytes32 hash
     * @return bytes The calculated commitment slot hash
     */
    function calculateCommitmentSlotHash(bytes32 commitment) public pure returns (bytes memory) {
        return abi.encodePacked(keccak256(abi.encodePacked(commitment, FILLED_SLOT_BIG_ENDIAN_BYTES)));
    }

        // _filled is `mapping(bytes32 => address)` declared at storage slot 2. The cross-chain
        // cancel proof (FILLED_SLOT_BIG_ENDIAN_BYTES) depends on this exact slot.

        address filledFromSlot = address(uint160(uint256(vm.load(address(intentGateway), slot))));

        assertEq(filledFromSlot, filler, "_filled must occupy storage slot 2");
        assertEq(filledFromSlot, intentGateway._filled(filledCommitment), "slot-2 read matches getter");
