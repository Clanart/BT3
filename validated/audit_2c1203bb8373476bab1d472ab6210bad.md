### Title
Operator's payout tx is malleable via `SinglePlusAnyoneCanPay`, letting an attacker null out the OP_RETURN operator-attribution and get an honest operator's kickoff flagged malicious - (`core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs the payout transaction's input with a user-provided `SinglePlusAnyoneCanPay` Schnorr signature that (per BIP341) only commits to input 0 and output 0. Outputs 1 (anchor) and 2 (OP_RETURN carrying the operator's xonly pubkey) are completely unauthenticated and can be freely rewritten by anyone who observes the transaction, allowing an attacker to replace/garble output 2 and get their malleated version confirmed instead of the operator's, which nulls the operator attribution used later by `Verifier::is_kickoff_malicious`.

### Finding Description
The binding claimed by the protocol is: `stored payout_payer_operator_xonly_pk for withdrawal i == the operator whose payout output funded output 0`. This binding is enforced solely by the OP_RETURN in output 2 of the payout tx, which is *not* covered by the witness signature's sighash commitment.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a 3-output tx: output 0 (user payout), output 1 (anchor), output 2 (`OP_RETURN` with `operator_xonly_pk.serialize()`), and signs input 0 key-spend with the user's pre-supplied signature via `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)`. The signature's sighash type is enforced to be `SinglePlusAnyoneCanPay` both in the aggregator's `withdraw` RPC input validation (`core/src/rpc/parser/operator.rs:174-187`) and verified against that type in `Operator::withdraw` (`core/src/operator.rs:630-637`). `calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`) computes the Taproot sighash using `Prevouts::One` for `*PlusAnyoneCanPay` types and passes the flag straight to `taproot_key_spend_signature_hash`, which under BIP341 SIGHASH_SINGLE|ANYONECANPAY only commits input 0 and output 0 - outputs 1 and 2 are entirely unconstrained.

Exploit: an attacker scrapes operator A's broadcast (but unconfirmed) payout_tx from the mempool, keeps input 0 (same outpoint, same witness containing `user_sig`) and output 0 unchanged, but replaces output 2's OP_RETURN with garbage bytes (or a syntactically valid OP_RETURN push that is not a valid 32-byte xonly pubkey), adjusts fees/anchor as desired, and rebroadcasts with higher fee. This new tx is fully witness-valid (same signature verifies against the same sighash, since the sighash didn't change) and gets mined ahead of A's original.

`Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) later processes the confirmed block; `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) matches by `withdrawal_utxo_txid`/`vout` being spent in that block - it has no dependency on which specific txid the operator originally submitted. It fetches whatever tx actually spent the withdrawal UTXO, extracts `get_first_op_return_output`/`parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617,686-692`), fails to get a valid `XOnlyPublicKey`, and stores `payout_payer_operator_xonly_pk = NULL` for that withdrawal (`core/src/database/verifier.rs:199-251`, `core/src/verifier.rs:2319-2321`).

When operator A later submits its kickoff for this deposit, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) loads `payout_info` and hits the `None` `operator_xonly_pk_opt` branch (line 1882-1885), unconditionally returning `true` ("assuming malicious"). `handle_kickoff` (`core/src/verifier.rs:1969-2026`) then queues a `Challenge` transaction, initiating the challenge/disprove flow that burns operator A's collateral, even though A genuinely fronted the withdrawal.

No existing guard prevents this: there is no txid pinning of the operator's submitted payout tx, no check that the confirmed spending tx equals a specific pre-registered candidate, and the sighash type mandated by the protocol (`SinglePlusAnyoneCanPay`) is exactly the one that leaves outputs beyond index 0 unauthenticated.

### Impact Explanation
An honest operator that genuinely funded a withdrawal (output 0 pays the user, from the operator's own funds via the malleated tx) is nonetheless flagged as malicious on kickoff, triggering `Challenge`/`Disprove` and burning that operator's collateral - this is the "an honest operator's collateral burned" Critical category. It is repeatable across every withdrawal/operator pair as long as the attacker can observe the operator's payout tx in mempool before it confirms and outbid it in fees; the attacker need not spend any of their own bridge funds, only fees, and does not gain money directly but can grief any/every operator on any withdrawal.

### Likelihood Explanation
Preconditions are minimal and squarely within the unprivileged attacker's stated capabilities: observe mempool (public), reconstruct a transaction reusing a publicly-visible witness (`SinglePlusAnyoneCanPay` witnesses are, by design, valid for any set of trailing outputs), and pay a bumped fee to get preferential confirmation. No special access, keys, or majority hashrate is needed - only mempool visibility and fee-bumping capability, both explicitly in-scope for the "unprivileged attacker."

### Recommendation
Change the payout transaction's commitment so that the OP_RETURN operator-attribution output is covered by an authenticated commitment: either require `TapSighashType::All`/`AllPlusAnyoneCanPay` (which commits to all outputs) for the user's signature over the specific operator-fronted payout, or have the verifier/aggregator pin and check the exact expected payout txid (not merely "whichever tx spent this outpoint") before accepting confirmation, or add operator-side redundancy (store operator identity via a mechanism outside output 2, such as an operator-specific pre-signed template whose txid is registered before broadcast) so that malleating trailing outputs cannot erase attribution.

    output_txout: TxOut,

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
