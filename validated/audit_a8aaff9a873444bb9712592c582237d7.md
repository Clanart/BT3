## Analysis

The bug-class seed is the **shared measurement address** problem: using a balance-delta on an address that is *not exclusively dedicated* to one payment/settlement flow means any unrelated token movement into that address gets misattributed as "the intended payment." Hyperbridge's `IntentGatewayV2` reproduces exactly this pattern with its `_params.dispatcher` contract, which is a **single, persistent, globally shared** contract used by *every* `placeOrder` call across *every* user, rather than a fresh, order-scoped address. [1](#0-0) 

In the predispatch branch of `placeOrder`, the contract measures `IERC20(token).balanceOf(dispatcher)` **as a whole** (not a delta captured before/after this specific call) to decide how much of `token` was "received" for escrow purposes, then sweeps that *entire* balance into the gateway: [2](#0-1) 

The subsequent accounting caps the credited amount at `order.inputs[i].amount` (excess becomes `DustCollected` protocol revenue), but everything at or below that requirement — including tokens the caller never contributed — is credited to `order.inputs[i].amount` and, after fee deduction, escrowed under the caller's commitment: [3](#0-2) [4](#0-3) 

Because `dispatcher` is a plain contract address stored once in `_params` and reused by the whole gateway, it has no built-in isolation between unrelated orders' predispatch flows — an ERC-20 `transfer()` directly to it (or leftover, uncaptured output from a prior user's predispatch call whose `order.inputs` didn't enumerate that particular token) simply sits there until some later, unrelated `placeOrder` call happens to name that same token in its own `inputs` and sweeps it for free. This is the same root cause the external report describes for `ERC20BalanceGteEnforcer`: a balance check against a shared/non-fresh address cannot distinguish the "intended payment" from any other transfer that happens to land on it.

### Title
Shared `dispatcher` balance sweep in `IntentGatewayV2.placeOrder` lets a caller escrow tokens they never contributed - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s predispatch escrow path measures `IERC20(token).balanceOf(dispatcher)` on the gateway's single, persistent `_params.dispatcher` contract instead of tracking a delta scoped to the current call. Because `dispatcher` is shared across every order and every user, any token balance sitting on it — from a direct external transfer, or from a prior predispatch call whose `order.inputs` did not enumerate that token — is swept into the *current* caller's escrow, up to their declared `order.inputs[i].amount`, without the current caller contributing those tokens themselves.

### Finding Description
`placeOrder` first moves `order.predispatch.assets` to `dispatcher` and executes `order.predispatch.call` there [5](#0-4) . It then reads the dispatcher's *total* balance for each `order.inputs[i].token`, requires it to be `>= requiredAmount`, and sweeps that whole balance into the gateway [2](#0-1) . The escrow ledger (`_orders[commitment][token]`) is then credited from this swept amount [4](#0-3) .

Nothing ties the swept balance to tokens the *current caller* supplied. `dispatcher` is a single address stored in `_params` for the entire gateway [6](#0-5) , so its balance for any ERC-20 is whatever the sum of all past inflows (minus past sweeps) happens to be at call time. Sources of unswept balance include:
- A prior legitimate order whose predispatch call (e.g., an LP unwrap) produced a second token that wasn't one of that order's `order.inputs` entries — that token is never swept by that order and stays parked on `dispatcher` indefinitely.
- A direct, unsolicited ERC-20 `transfer()` to `dispatcher` from any address (accidental or deliberate) — plain contracts accept incoming ERC-20 transfers with no callback/authorization needed.

Any subsequent, unrelated caller who lists that same token in their own `order.inputs` and provides a `predispatch.call`/`predispatch.assets` combination that leaves the pre-existing balance untouched (or a no-op predispatch call) will have that balance counted toward their required escrow amount, at the original depositor's expense.

### Impact Explanation
This is a direct "stealing/loss of funds" and "false state acceptance" vector in intent settlement: an unprivileged caller can obtain escrow credit — enforceable against solvers via `_orders[commitment][token]` and later released through `withdraw()`/`RedeemEscrow` — using tokens they never contributed. The rightful depositor (whoever's tokens ended up stranded on the shared `dispatcher`) permanently loses those funds, while the exploiting order-placer receives a solver's real output tokens in exchange for value they did not provide. This matches the bounty's "stealing or loss of funds" and "logic attacks" categories in bridge custody / intent settlement.

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required. The only preconditions are (a) `dispatcher` accumulating an uncaptured token balance — plausible given the predispatch design explicitly allows arbitrary calldata that need not perfectly match `order.inputs`, and (b) an attacker later placing an order for that same token. Since `dispatcher` is a long-lived, address-stable, publicly known contract, an attacker can simply monitor its token balances and time their own `placeOrder` call whenever a exploitable balance appears — this is not a front-run race against a specific victim transaction, but an opportunistic, asynchronous drain of whatever residual value has accumulated.

### Recommendation
Do not use `balanceOf(dispatcher)` as the received-amount signal. Track a delta scoped strictly to the current call (snapshot dispatcher balance *before* transferring this order's `predispatch.assets` and executing this order's `predispatch.call`, then measure only the increase caused by *this* call), or route each order's predispatch flow through a fresh, order-scoped intermediary (e.g., a minimal proxy/clone deployed per commitment) rather than a shared long-lived `dispatcher`. Additionally, any residual balance left on `dispatcher` after a sweep should be swept to the protocol treasury within the same transaction rather than left available for a later, unrelated caller to claim.

### Proof of Concept
1. User A calls `placeOrder` with a predispatch call that unwraps an LP token into `TokenX` and `TokenY`, but `order.inputs` for User A's order lists only `TokenX`. The sweep loop only touches `TokenX`; the `TokenY` proceeds remain on `dispatcher` un-swept (confirmed by the sweep loop in [2](#0-1)  only iterating over `order.inputs`, not all tokens the predispatch call may have produced).
2. Attacker B observes `TokenY` balance sitting on `dispatcher` (e.g., via `TokenY.balanceOf(dispatcher)`).
3. Attacker B calls `placeOrder` with `order.inputs = [{token: TokenY, amount: <= existing dispatcher balance}]` and a no-op `predispatch.call` (empty `Call[]`, as already exercised in `testPlaceOrder_FeeOnTransferToken_Predispatch`-style tests using `Call[](0)` [7](#0-6) ).
4. The sweep step reads `IERC20(TokenY).balanceOf(dispatcher)`, finds it satisfies the required amount, and sweeps User A's leftover `TokenY` into Attacker B's escrow entirely for free.
5. Attacker B's order is later filled by a solver who transfers genuine output tokens to B, and B's fake `TokenY` escrow is released to the solver — User A's `TokenY` is gone, permanently unaccounted for, and B has monetized funds they never contributed.
