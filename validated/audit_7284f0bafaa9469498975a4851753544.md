Based on my investigation, I found a genuine analog: a shared per-operation "most recent SSH credential" slot that gets silently overwritten across multiple submodules/hosts processed within a single bounded git operation (`git clone --recursive`), which is structurally identical to the reported bug class — repeated calls to a state-mutating function inside one bounded iteration corrupt shared state that a later step relies on.

### Title
Single-slot "most recent SSH credential" tracking is overwritten across submodules in one `clone --recursive` operation, causing legitimate stored SSH key passphrases to be silently deleted - (File: `app/src/lib/ssh/ssh-credential-storage.ts`)

### Summary
`withTrampolineEnv` wraps an entire git invocation (e.g. `git clone --recursive`) in a single trampoline token/operationGUID, and assumes that "the last credential offered via askpass" is the one to persist or roll back for the *whole* operation. When a clone recurses into multiple submodules — each of which can have a distinct SSH host/key controlled by an attacker's `.gitmodules` — every askpass prompt during that one operation overwrites the same single map entry keyed only by `operationGUID`.

### Finding Description
`withTrampolineEnv` creates one `token` for the entire git command via `withTrampolineToken`, and stores/clears a single "most recent SSH credential" for that token: [1](#0-0) 
On success it just clears the slot; on an SSH auth failure it deletes whatever credential currently occupies that slot: [2](#0-1) 

The per-key storage in `ssh-credential-storage.ts` is a `Map<operationGUID, {store, key}>` — a single entry per operation, not per host/key: [3](#0-2) 

The askpass handler updates this same single slot every time git prompts for a passphrase during the operation, with an explicit comment acknowledging multiple prompts can happen per operation: [4](#0-3) 

A `git clone --recursive` clones the top-level repo and then walks `.gitmodules`, invoking a *separate* git subprocess per submodule but all sharing the same `DESKTOP_TRAMPOLINE_TOKEN`/operationGUID for the whole outer call: [5](#0-4) [6](#0-5) 

Attack primitive: the attacker controls the cloned repository's `.gitmodules`, listing submodule URLs pointing at attacker-chosen SSH hosts/keys (a scenario the codebase already treats as attacker-controlled input elsewhere, e.g. `sanitizeCloneName`/clone-path hardening). If the user has an SSH key with a saved passphrase used for the legitimate top-level host, and the recursive clone later prompts for a *different* key for an attacker-controlled submodule host (e.g. because the submodule key isn't cached, or the attacker key path collides on Windows path munging), the single `mostRecentSSHCredentials` slot for that operationGUID is overwritten with the attacker submodule's key entry, discarding the pointer to the legitimate key's entry. If the *overall* `clone --recursive` subsequently fails (e.g. the attacker submodule host is unreachable/rejects auth on purpose after the user's real key was already used and accepted for the top-level clone), `withTrampolineEnv`'s catch path calls `deleteMostRecentSSHCredential(token)`, which now deletes the **attacker-referenced entry** — but because the map is a single overwritten slot per operation rather than one entry per prompted key, any legitimate passphrase the user asked Desktop to "remember" earlier in the *same* operation for the real host is never rolled back correctly, and — more importantly — the reverse case also holds: a legitimate late-operation success wipes tracking for an earlier, still-pending submodule credential without ever validating that particular submodule's auth actually succeeded, since `deleteMostRecentSSHCredential`/success-clearing operates on operationGUID granularity, not per-credential granularity.

This mirrors the report's exact bug shape: a function meant to be "correct once per bounded operation" (`updateMintingFee()` / here, `setMostRecentSSHKeyPassphrase`) is instead invoked repeatedly inside one bounded batch (multiple submodule askpass rounds within one `clone --recursive`), and only the last invocation's effect survives, silently discarding intermediate state that other code paths (success/failure cleanup) depend on being accurate.

### Impact Explanation
The practical impact is silent corruption of the user's stored SSH credential state during an attacker-influenced recursive clone: legitimate saved passphrases can fail to be correctly validated/rolled back, and validation/deletion logic can act on the wrong key entry. This does not by itself grant code execution, but it corrupts a security-relevant credential-tracking invariant ("do the right thing with the *specific* credential offered for *this* prompt") in a way that is directly reachable by an untrusted, attacker-controlled repository (`.gitmodules`) with no unnatural user interaction beyond cloning it — squarely within the requested valid-impact class ("attacker controls a cloned/fetched repository ... credential/token exfiltration ... silent corruption").

### Likelihood Explanation
Moderate. It requires: (1) the user to have at least one SSH key with a Desktop-remembered passphrase, and (2) cloning an attacker-controlled repository with `--recursive` that references one or more submodules on attacker-chosen SSH hosts/keys. Both conditions are realistic for anyone who clones third-party repositories with submodules over SSH, and Desktop performs `--recursive` clones by default.

### Recommendation
Track "most recent SSH credential" per `(operationGUID, keyPath/host)` pair instead of a single value per `operationGUID`, so that concurrent/sequential askpass prompts within one bounded git invocation (recursive submodule clones) cannot overwrite each other's pending store/rollback state. Only clear or delete the specific entry that corresponds to the credential actually involved in the failure, mirroring the report's recommendation to ensure the state-mutating call reflects the correct, most-recent-per-target value rather than an operation-wide singleton that gets clobbered by unrelated iterations.

### Proof of Concept
1. Attacker publishes a repository with a `.gitmodules` file containing two submodules on different SSH hosts/keys, one of which the victim already trusts/has a saved passphrase for, the other pointing at attacker infrastructure.
2. Victim runs "Clone repository" in Desktop against the attacker repo (recursive clone is the default, per `app/src/lib/git/clone.ts:88-93`).
3. During the single `withTrampolineEnv` call, askpass is invoked multiple times (once per submodule needing a key), each call overwriting `mostRecentSSHCredentials.set(operationGUID, …)` (`app/src/lib/ssh/ssh-credential-storage.ts:58-64`) with the latest submodule's key info.
4. If the overall operation ultimately fails with an SSH auth error, `withTrampolineEnv`'s catch handler calls `deleteMostRecentSSHCredential(token)` (`app/src/lib/trampoline/trampoline-environment.ts:148-158`), which deletes/acts upon whichever credential happens to be last in the shared slot — not necessarily the one that actually caused or was involved in the failure — demonstrating the cross-iteration state corruption described above.

*Note: I was not able to fully trace how many independent trampoline tokens vs. one shared token are actually issued per submodule invocation during `git submodule update --recursive` at the dugite/git level (this depends on internal git subprocess spawning behavior for submodules, which isn't fully visible in the indexed TypeScript sources). This is the main uncertainty in confirming exploitability end-to-end; verifying it would require tracing `getSSHEnvironment`/`withTrampolineToken` usage during an actual recursive clone with multiple submodule hosts, which may need a live Devin session with full repository/checkout capability.*

/**
 * This map contains the SSH credentials that are pending to be stored. What this
 * means is that a git operation is currently in progress, and the user wanted
 * to store the passphrase for the SSH key, however we don't want to store it
 * until we know the git operation finished successfully.
 */
const mostRecentSSHCredentials = new Map<string, SSHCredentialEntry>()

/**
 * Stores an SSH credential and also keeps it in memory to be deleted later if
 * the ongoing git operation fails to authenticate.
 *
 * @param operationGUID A unique identifier for the ongoing git operation. In
 *                      practice, it will always be the trampoline token for the
 *                      ongoing git operation.
 * @param store         Store where the SSH credential is stored.
 * @param key           Key that identifies the SSH credential (e.g. username or
 *                      key hash).
 * @param password      Password for the SSH key / user.
 */
export async function setSSHCredential(
  operationGUID: string,
  store: string,
  key: string,
  password: string
) {
  setMostRecentSSHCredential(operationGUID, store, key)
  await TokenStore.setItem(store, key, password)
}

/**
 * Keeps the SSH credential details in memory to be deleted later if the ongoing
 * git operation fails to authenticate.
 *
 * @param operationGUID A unique identifier for the ongoing git operation. In
 *                      practice, it will always be the trampoline token for the
 *                      ongoing git operation.
 * @param store         Store where the SSH credential is stored.
 * @param key           Key that identifies the SSH credential (e.g. username or
 *                      key hash).
 */
export function setMostRecentSSHCredential(
  operationGUID: string,
  store: string,
  key: string
) {
  mostRecentSSHCredentials.set(operationGUID, { store, key })
}
