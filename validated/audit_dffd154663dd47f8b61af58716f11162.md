## Title
Malformed .dds texture reaches an unvalidated `Uint8Array(buffer, offset, length)` view, causing an uncaught RangeError/renderer crash when viewing an attacker-controlled binary diff - (File: app/src/ui/diff/image-diffs/dds-converter.ts)

### Summary
GitHub Desktop renders `.dds` (DirectDraw Surface) image diffs by feeding the raw bytes of a file taken directly from a cloned/fetched repository (or its working directory) into a third‑party DDS header parser (`parse-dds`) and then constructing a typed array view over the *same underlying ArrayBuffer* using offset/length fields taken from that untrusted parse result, with no bounds validation against the buffer's actual size. [1](#0-0) 

### Finding Description
When Desktop shows a diff for a file whose extension is `.dds`, it maps the extension to media type `image/vnd-ms.dds`: [2](#0-1) 

The image bytes are obtained straight from `git show`/working-directory read of a path controlled by whatever is in the cloned repository or working tree (`getBlobImage` / `getWorkingDirectoryImage`), with no sanitization of contents beyond base64 encoding: [3](#0-2) 

`ImageContainer.loadImage` detects the DDS media type and calls `convertDDSImage(image.rawContents)` with `image.rawContents` being the raw `ArrayBufferLike` backing the file's bytes: [4](#0-3) 

Inside `convertDDSImage`, the DDS header is parsed by the `parse-dds` library, which returns `ddsData.images[0].offset` / `.length` derived from attacker-controlled header fields (mipmap count, width/height, pixel format, data size, etc. from the DDS file's `DDS_HEADER`). These values are used directly to slice a view over the original buffer:
```
const [image] = ddsData.images
const [imageWidth, imageHeight] = image.shape
const imageData = new Uint8Array(contents, image.offset, image.length)
``` [5](#0-4) 

There is no check that `image.offset + image.length` is within the bounds of `contents.byteLength`, and no check that `ddsData.images` is non-empty (a malformed file with zero declared mipmaps would make `image` `undefined`, and `image.shape` would throw a `TypeError`). If `offset`/`length` are attacker-inflated beyond the buffer size, the `Uint8Array` constructor throws a `RangeError: Invalid typed array length` — this is the JS-safe analog of the native `INVALID_POINTER_WRITE` primitive in the original GoldSRC report: an out-of-bounds region computed from an untrusted length/offset field is handed to a low-level buffer/view constructor without validation. In a memory-unsafe native decoder this class of bug is what produces write-AVs like `hw!CreateInterface`; in V8's typed-array machinery the same broken invariant is caught by the engine and turned into an exception instead of memory corruption.

The exception is only caught at the top level of `loadImage`'s call to `convertDDSImage`: [6](#0-5) 
so the immediate effect in the current renderer sandbox is contained (caught and logged), not remote code execution. There is no depth-based validation of `parse-dds`'s output structure (missing `images[0]`, negative/overflowing `offset`/`length`, or an `offset`/`length` that reads far beyond the actual pixel data into adjacent heap-backed regions of the same buffer) before it's used to build the WebGL texture upload in `drawToCanvas`, which further trusts `imageWidth`/`imageHeight`/`format` from the same untrusted parse. [7](#0-6) 

### Impact Explanation
Worst realistic impact given JS/V8 memory safety: a crafted `.dds` file committed to (or present in the working directory of) a cloned/fetched repository can throw an unhandled/partially-handled exception when a user views its diff, causing the renderer's diff view to fail (denial of view / minor crash) and could feed corrupted-looking pixel data (reading past the intended DDS payload but still within the same ArrayBuffer, e.g. adjacent bytes of the git blob) into the WebGL texture if `offset+length` stays within `contents.byteLength` but past the real image data — this is a silent data-integrity/rendering corruption case rather than code execution. It does **not** demonstrate memory corruption or RCE equivalent to the original GoldSRC report, because V8 enforces typed-array bounds; this is the key limitation of this analog. Per the task's "Valid Impact" bar (code execution, cross-repo file read/write, credential exfiltration, OAuth abuse, sandbox/IPC escape, or silent corruption of committed/pushed content), the strongest defensible claim here is a renderer crash / unhandled exception path when viewing an attacker-supplied binary diff, which is a lower-severity, best-effort analog to the reported bug class rather than a full equivalent.

### Likelihood Explanation
High trigger likelihood: simply cloning a hostile repository (or checking out/pulling a branch) that contains a malformed `.dds` file and opening its diff in the Changes/History view is sufficient — no special user action beyond normal repository browsing, matching the "attacker controls a cloned/fetched repository" threat model. The code path (`getBlobImage`/`getWorkingDirectoryImage` → `convertDiff` → `ImageContainer.loadImage` → `convertDDSImage`) is reached automatically whenever a `.dds` file shows up in a diff.

### Recommendation
- Validate `parse-dds`'s output before use: reject if `ddsData.images.length === 0`, and verify `image.offset >= 0`, `image.length >= 0`, and `image.offset + image.length <= contents.byteLength` before constructing the `Uint8Array` view; treat failures as an unrenderable/binary diff rather than allowing the exception (or corrupted read) to propagate.
- Wrap the whole `convertDDSImage` call (already partially caught) with explicit, descriptive validation errors so out-of-bounds header fields are treated the same way oversized diffs already are (`isValidBuffer`/`MaxDiffBufferSize` pattern used for text diffs). [8](#0-7) 
- Consider bounding `imageWidth`/`imageHeight` before passing to `canvas.width`/`canvas.height` and `gl.compressedTexImage2D` to avoid pathological allocation sizes derived from untrusted header fields.

### Proof of Concept
1. Craft a minimal `.dds` file with a valid magic header but a manipulated pitch/linear-size or mipmap-count field so that `parse-dds` computes an `images[0].offset`/`.length` pair whose sum exceeds the actual file size (e.g., set `dwPitchOrLinearSize` and `dwMipMapCount` to large values while keeping the actual file short).
2. Commit this file (e.g., `evil.dds`) to a branch of a repository and have the victim clone/fetch and check it out in GitHub Desktop.
3. In Desktop, select the commit/working-directory change that introduces `evil.dds` and open the diff view.
4. `ImageContainer.loadImage` invokes `convertDDSImage(image.rawContents)`; the `new Uint8Array(contents, image.offset, image.length)` call throws `RangeError: Offset/length out of bounds` (or, if within buffer bounds but past the real pixel payload, silently renders adjacent buffer bytes as image content), which is only caught generically and logged. [1](#0-0) [6](#0-5) 

**Confidence caveat:** I was not able to inspect the source of the third-party `parse-dds` dependency in this index to confirm exactly which header fields it trusts unchecked or whether it independently clamps `offset`/`length` to the buffer size; the finding is based on the local call site's lack of validation of the values it consumes from that library's output. This should be verified against `parse-dds`'s actual implementation before treating the bound-check gap as fully confirmed.

function drawToCanvas(
  canvas: HTMLCanvasElement,
  format: string,
  width: number,
  height: number,
  imageData: ArrayBufferView
) {
  canvas.width = width
  canvas.height = height
  const gl = canvas.getContext('webgl2', { preserveDrawingBuffer: true })
  if (!gl) {
    throw new Error('Failed to get webgl2 context')
  }

  gl.bindTexture(gl.TEXTURE_2D, gl.createTexture())
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.LINEAR)
  gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MIN_FILTER, gl.LINEAR)
  const ext = gl.getExtension('WEBGL_compressed_texture_s3tc')
  if (!ext) {
    throw new Error('Failed to get WEBGL_compressed_texture_s3tc extension')
  }

  const internalFormat = getFormat(ext, format)
  gl.compressedTexImage2D(
    gl.TEXTURE_2D,
    0,
    internalFormat,
    width,
    height,
    0,
    imageData
  )

  const program = compileProgram(gl, vert, frag)
  gl.useProgram(program)

  gl.viewport(0, 0, width, height)
  triangle(gl)
}

export function convertDDSImage(contents: ArrayBufferLike) {
  const ddsData = parseDDS(contents)

  // Get the first mipmap texture.
  const [image] = ddsData.images
  const [imageWidth, imageHeight] = image.shape
  const imageData = new Uint8Array(contents, image.offset, image.length)

  // Draw the DXT texture to the canvas using WebGL2.
  const canvas = document.createElement('canvas')
  drawToCanvas(canvas, ddsData.format, imageWidth, imageHeight, imageData)

export async function getBlobImage(
  repository: Repository,
  path: string,
  commitish: string
): Promise<Image> {
  const extension = Path.extname(path)
  const contents = await getBlobContents(repository, commitish, path)
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(extension),
    contents.length
  )
}
/**
 * Retrieve the binary contents of a blob from the working directory
 *
 * Returns an image object containing the base64 encoded string,
 * as <img> tags support the data URI scheme instead of
 * needing to reference a file:// URI
 *
 * https://en.wikipedia.org/wiki/Data_URI_scheme
 */
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )

  public loadImage(image: Image) {
