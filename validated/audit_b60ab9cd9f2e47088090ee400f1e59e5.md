### Title
Cached FROST preprocess seed is never scoped to the session nor deleted, causing nonce reuse across DKG confirmation sessions and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The upstream bug is a stale reference that survives past the lifetime it was valid for: `ip6_negative_advice()` intentionally held a reference to an expired dst so the socket's cache reset was counteracted, leaving the expired object pinned and reused/leaked past its valid scope. The Serai analog lives in `SigningProtocol::preprocess_internal`: a FROST preprocess seed is cached in the DB under a context key of `(b"DkgConfirmer", attempt)` — which does **not** include the tributary genesis, session, or validator set — and is never deleted. When a new DKG confirmation runs for a different session with the same `attempt` number, the same seed is loaded via `AlgorithmSignMachine::from_cache`, deterministically regenerating the identical FROST nonces for a different message.

### Finding Description

`preprocess_internal` writes and reads `CachedPreprocesses` keyed only by `self.context.encode()`: [1](#0-0) [2](#0-1) 

For the DKG confirmer the context is `(b"DkgConfirmer", self.attempt)` — a static tag plus a `u32` attempt counter, with no `spec.genesis()`, session, or network mixed in: [3](#0-2) 

Every other DB entry in this handler (`DataDb`, `ConfirmationNonces`, `DkgKeyPair`, `FatallySlashed`, etc.) is keyed by `genesis` precisely because `self.txn` is the shared coordinator DB spanning all tributaries: [4](#0-3) 

`CachedPreprocesses` is the exception: its key has no genesis. Meanwhile `from_cache`/`seeded_preprocess` deterministically derives the nonces and commitments from `ChaCha20Rng::from_seed(*seed.0)`: [5](#0-4) 

So a cached seed produced for session/genesis A's attempt-0 DKG confirmation is silently reused for session/genesis B's attempt-0 confirmation — the expired object is never invalidated when its scope (the session) ends, exactly mirroring the pinned expired dst. The signed message differs (`set_keys_message` binds the set, removed keys, and the new `KeyPair`), while the nonce pair `(d, e)` is identical.

There is also no deletion path: `cache()` returns `self.seed`, the docs require "the preprocess must be deleted so it's never reused," yet nothing ever removes the `CachedPreprocesses` row after `share_internal`/`complete_internal` succeed: [6](#0-5) 

### Impact Explanation

Each FROST signature share has the form `z = d + e·ρ + λ·s·c`, where `ρ` is the binding factor, `c` the challenge, `λ` the Lagrange coefficient, and `s` the validator's MuSig secret share — which here is the validator's persistent Ristretto key (`musig(...)` is built from `self.key`, the same key across sessions). With the same `(d, e)` reused across N distinct confirmation signatures (different sessions, or different participant sets/messages yielding different `ρ`, `c`, `λ`), the attacker obtains N linear equations in the three unknowns `d`, `e`, `s`; N ≥ 3 (or fewer when `λ`, `ρ`, or `s` coincide) suffices to solve for `s`. The confirmation signatures and the identical preprocess commitments (identical `R` values) are published on-chain via `publish_set_keys` and tributary `DkgConfirmed`/`DkgShares` transactions, so recovery is fully passive.

Recovering `s` yields the validator's root-of-trust signing key: the attacker can forge tributary transaction signatures and MuSig confirmations. This meets the "key share recovery" acceptance bar.

### Likelihood Explanation

The trigger requires no malicious action: every new validator set/session runs `DkgConfirmer` starting at `attempt = 0` (DKG attempts reset per session, and `removed_as_of_dkg_attempt` is indexed by attempt per genesis). Any validator whose coordinator survives a session rotation — the normal handover flow — reuses its seed the moment the new session's confirmation begins. The file's own safety argument ("nonces being context-bound under a BFT protocol") holds only within one BFT instance; the cache key fails to bind the context to that instance, so the invariant breaks exactly at session boundaries, which are routine, not adversarial. No collusion, malicious validator, or leaked key is needed — the victim is the honest validator itself.

### Recommendation

- Include the session identifier in the cache context, e.g. `context = (b"DkgConfirmer", spec.genesis(), attempt)` (or fold `spec.set()`), so seeds cannot cross session boundaries.
- Delete the `CachedPreprocesses` entry once the confirmation signature is completed (or once `DkgLocallyCompleted` is set), satisfying the `from_cache` contract that "the preprocess must be deleted so it's never reused."
- Before publishing a share, verify the derived commitments match the ones already published on the tributary for this attempt (the file's own TODO at lines 50–54), which would also catch cross-session reuse.

### Proof of Concept

1. Validator V runs DKG confirmation for session A, attempt 0. `preprocess_internal` stores seed `S` under key `("DkgConfirmer", 0)` and publishes preprocess `P` (commitments `D, E`). The confirmation produces signature share `z₁ = d + e·ρ₁ + λ₁·s·c₁` over `set_keys_message(set_A, key_pair_A)`, published on-chain.
2. A new validator set forms session B (handover/tributary rotation). V's coordinator runs `DkgConfirmer` for attempt 0 again; `CachedPreprocesses::get(("DkgConfirmer", 0))` returns `S`, so `from_cache` regenerates the identical `(d, e)` and the identical published preprocess bytes.
3. V signs `set_keys_message(set_B, key_pair_B)` producing `z₂` (and `z₃`, … for further sessions/attempts).
4. An observer collects the shares `z_i` with the public `(ρ_i, c_i, λ_i)` and solves the linear system for `d`, `e`, and `s`. With a single-nonce algorithm (`d` only) two signatures suffice; with the binomial `(d, e)` three reused-nonce signatures suffice, and each new session reuses every attempt-indexed seed again.
5. The recovered `s` is V's Ristretto private key, verifiable against `Ristretto::generator() * s == V's public key`.

Uncertainty noted: the exact count of signatures needed depends on `Schnorrkel::nonces()` length (1 vs. 2 nonces), but seed reuse is guaranteed and monotonically accumulates exploitable equations each session, so recovery is only a matter of how many confirmations are observed.
