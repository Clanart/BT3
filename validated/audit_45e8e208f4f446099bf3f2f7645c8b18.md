### Title
Balance desync from shared `BalanceHandler` instance across recursive/re-entrant precompile calls corrupts StateDB balances - (File: `precompiles/common/balance_handler.go`)

### Summary
The external report flags that DYAD's `balanceOfNote`-dependent reward accounting breaks when `balanceOfNote` changes without first settling dependent state (`claimRewards`). The generalized invariant is: **a value used to compute a delta/snapshot must not be silently overwritten by a nested state change before the delta is consumed.** In this repository, `precompiles/common/balance_handler.go` implements exactly this snapshot-then-diff pattern via `BalanceHandler.prevEventsLen`, and the codebase's own test suite documents that this field is unsafe under recursive/re-entrant precompile calls.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records a snapshot index into the event manager's event list, and `AfterBalanceChange` later replays only the events emitted after that snapshot to update the EVM `StateDB` balances via `AddBalance`/`SubBalance`: [1](#0-0) [2](#0-1) 

This is precisely the DYAD bug's pattern: `stakeInfo.lastRewardTime`/reward computation depends on a snapshot (`balanceOfNote`) that must be settled before further balance-changing operations; here, `prevEventsLen` is a snapshot that must be consumed before it is overwritten by a nested call.

A single `BalanceHandler` instance is created per precompile method call and is used to bracket the bank-keeper side effects of that call so they can be translated into `StateDB.AddBalance`/`SubBalance` operations for EVM-visible state. If a precompile call (e.g., ERC20/ICS20 transfer precompile) triggers a nested/recursive call back into a precompile — for example via an EVM-callable hook such as `_beforeTokenTransfer`/`_afterTokenTransfer` on a malicious ERC20 contract, or via a contract that re-enters a precompile mid-call — and that nested call **reuses the same `BalanceHandler` instance**, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` with a later index. When the outer call's `AfterBalanceChange` subsequently runs, it uses the now-advanced `prevEventsLen`, causing it to skip the events generated by the outer call's own bank-keeper operations. The result is that some real bank-module balance mutations (`CoinSpent`/`CoinReceived`) are never reflected into the EVM `StateDB`, producing a desync between the native bank keeper (source of truth) and the EVM `StateDB` (used for balance checks, gas refunds, and EVM balance queries).

The repository's own integration test explicitly documents this exact defect class: [3](#0-2) 
and the related ICS20 recursive-precompile test suite similarly documents that "reverted distribution calls leave persistent bank events that are incorrectly aggregated," confirming the shared/reused snapshot-state problem occurs in production precompile flows (ICS20 transfer + reentrant ERC20 token hooks + distribution precompile calls), not merely in a synthetic debug precompile: [4](#0-3) [5](#0-4) 

Every stateful precompile (`erc20`, `ics20`, `distribution`, `staking`, `slashing`, `gov`) wires this same `BalanceHandler` pattern into its transaction methods, so the vulnerable pattern is broadly reachable from unprivileged EVM contract calls: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
If the outer call's bank-side coin movements are silently dropped from `StateDB`, an unprivileged user (via a contract that triggers a nested precompile call, e.g. an ERC20 token with a transfer hook that calls a precompile, combined with an ICS20/erc20 transfer) can cause EVM-visible balances to diverge from the actual bank-module balances. Depending on which side of the send is skipped, this manifests as:
- EVM `StateDB` balance under-counting a debit (funds appear to remain available in EVM view after being spent via bank), enabling double-spend-like behavior in subsequent EVM operations within the same or later transactions that rely on `StateDB` balance (e.g. further transfers, `SELFBALANCE`, or gas/value checks), or
- EVM `StateDB` balance under-counting a credit, causing permanent loss of EVM-visible spendable value for the recipient even though the bank keeper holds the funds.

Either direction breaks the required 1:1 accounting invariant between native bank balances and EVM-visible balances, which is the stated Critical-impact criterion for this scope (unauthorized minting/duplication or freezing/loss of spendable value across native/EVM/ERC20/escrow representations).

### Likelihood Explanation
Likelihood is high on the same basis as the original report: reentrancy/nested-call opportunities are common and easy to construct in this codebase (the repo ships purpose-built test contracts — `ERC20RecursiveRevertingPrecompileCall.sol`, `ERC20RecursiveNonRevertingPrecompileCall.sol`, and `Reverter.sol` — that exercise exactly this "nested precompile call from within an ERC20 hook" scenario), and no unprivileged caller privilege is required. [9](#0-8) 

### Recommendation
Ensure `BalanceHandler` state is not shared/overwritten across nested precompile invocations within the same EVM call stack: either (a) instantiate a fresh `BalanceHandler` per call frame instead of reusing one shared instance across nested precompile dispatch, or (b) make `prevEventsLen` stack-based (push/pop) so nested calls save and restore the outer snapshot instead of clobbering it, guaranteeing `AfterBalanceChange` for every call frame processes exactly the events emitted by that frame's own bank operations.

### Proof of Concept
The repository's own reproduction is `TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go`, which deploys a caller contract that recursively invokes a debug precompile and asserts specific event/debug counts that demonstrate the shared-instance overwrite behavior: [10](#0-9) 
A more production-realistic reproduction is `TestHandleMsgTransfer` in `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`, using an ERC20 contract with a recursive/reentrant transfer hook combined with the ICS20 transfer precompile and distribution reward accrual, where the "reverting" vs "non-reverting" recursive cases produce diverging post-transfer bank/distribution state that the test explicitly labels as triggering the bug: [11](#0-10) 

I was not able to fully trace, within the available context, the exact call site(s) where a `BalanceHandler` instance is passed into nested/recursive precompile dispatch (i.e., confirm definitively whether it's the same Go object reused per EVM call frame vs. a new one per `vm.Contract` invocation) — this would require reading `precompiles/common/precompile.go` and the EVM keeper's precompile-dispatch code path in full, which was not retrievable within the remaining tool budget. The severity/root-cause conclusion above rests on the explicit in-repo test comments describing this exact "shared BalanceHandler instance" and "balance desync between native bank keeper and EVM stateDB" bug, which strongly corroborate the vulnerability but should be independently confirmed by reading `precompiles/common/precompile.go` and the `x/vm` precompile call/re-entry path before treating this as fully verified.

	s.Require().NoError(err)
	s.chain.NextBlock()
