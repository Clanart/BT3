### Title
Aggregate Schnorr signature verifier accepts duplicate signers, allowing one signature to count multiple times - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The Illuminate bug class is a `lend` function that consumes a caller-supplied external address/parameter without validation, letting an attacker over-issue tokens. The Serai analog is a verifier consuming an attacker-supplied *list* (`keys_and_challenges`) without validating its entries for uniqueness: `SchnorrAggregate::verify` in `crypto/schnorr`. Because the half-aggregation verification equation is linear in the per-signer weight, a single valid `(R, s)` from one signer can be replayed under multiple list entries, inflating the effective signer count and forging an aggregate signature that satisfies a threshold/weight check it never actually met — the same "overissuance of credited units" consequence.

### Finding Description
`SchnorrAggregate::verify` checks only that `self.Rs.len() == keys_and_challenges.len()` and then computes, per index `i`, a deterministic weight `z_i = weight(digest)` bound only to the *sequence of challenges*, and verifies `Σ z_i·R_i + Σ z_i·c_i·A_i - s·G == 0`. [1](#0-0) 

There is no rejection of duplicate `A_i` keys, duplicate `R_i` nonces, or duplicate `(key, challenge)` pairs. The weights `z_i` are deterministic functions of the challenges (`digest.append_message(b"challenge", ...)` then `weight(&mut digest)`), so the attacker knows them all before choosing `s`. [2](#0-1) 

Given one honest signature `(R_0, s_0)` under challenge `c_0` for key `A_0` (i.e. `s_0·G = R_0 + c_0·A_0`), an attacker constructs `keys_and_challenges = [(A_0, c_0), (A_0, c_0), ...]` repeated `k` times and `Rs = [R_0; k]`. The verification equation is satisfied by setting:

```
s = (Σ_{i=0..k} z_i) · s_0
```

since `Σ z_i·R_0 + Σ z_i·c_0·A_0 = (Σ z_i)·(R_0 + c_0·A_0) = (Σ z_i)·s_0·G`. Each `z_i` is distinct (different index in the digest stream) yet fully computable by the attacker, and `s` is freely chosen in the serialized aggregate (`SchnorrAggregate::read` accepts any canonical `s` and any `Rs` list from untrusted bytes). [3](#0-2) 

This is directly reachable from public inputs: `verify_aggregate` callers feed an attacker-proposed `signers` list and attacker-supplied `AggregateSignature` bytes (`SchnorrAggregate::read`) into `verify`. If the caller attributes voting weight per list entry (the documented intent — "checking the list is sorted and the list's weight exceeds the threshold"), `k` repetitions of one validator count that validator `k` times.

### Impact Explanation
High. One valid Schnorr signature from a single signer can be expanded into an aggregate signature that passes verification for an arbitrary number of "signers", defeating any threshold/2⁄3-supermajority accounting the caller performs over the signers list. This is the exact consequence shape of the Illuminate finding: unvalidated caller-controlled input lets an attacker over-issue a scarce resource (here, signer weight; there, iTokens) and then redeem it for disproportionate effect (consensus acceptance; there, protocol funds).

### Likelihood Explanation
The attack requires only: one eavesdropped legitimately-produced `(R, s, challenge)` tuple for any key the attacker wants to amplify, plus control of the aggregate bytes and signer list passed to `verify`. No secret material, no malicious validator cooperation, no broken BFT assumptions are needed — the forgery is pure algebra over public values because `weight()` is a deterministic transcript function.

### Recommendation
In `SchnorrAggregate::verify`, reject inputs where any `(key, challenge)` pair — or at minimum any `key` — appears more than once; alternatively document that callers MUST enforce uniqueness of signers and sort/dedup `keys_and_challenges` before calling. Since `Rs` are also untrusted, consider rejecting identity `Rs` and duplicate `R` values as well.

### Proof of Concept
```rust
// Honest signer produces one signature
let key = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
let pub_key = C::generator() * key.deref();
let c = C::random_nonzero_F(&mut OsRng); // caller-supplied challenge
let sig = SchnorrSignature::<C>::sign(&key, Zeroizing::new(C::random_nonzero_F(&mut OsRng)), c);

// Attacker replays it K times as K distinct "signers"
const K: usize = 8;
let keys_and_challenges = vec![(pub_key, c); K];

// Reproduce verifier's weights
let mut digest = DigestTranscript::<C::H>::new(DST);
digest.domain_separate(b"signatures");
for (_, c) in &keys_and_challenges {
  digest.append_message(b"challenge", c.to_repr());
}
let mut s_forged = C::F::ZERO;
for _ in 0 .. K {
  s_forged += weight::<_, C::F>(&mut digest) * sig.s;
}

let forged = SchnorrAggregate::<C> { Rs: vec![sig.R; K], s: s_forged };
assert!(forged.verify(DST, &keys_and_challenges)); // passes with only 1 real signature
```

Root cause: `crypto/schnorr/src/aggregate.rs:127-146` performs no uniqueness validation on `keys_and_challenges` before summing weighted statements.

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
