### Title
Stale access-list slot index after slot-removal shift causes wrong warm/cold storage-access gas accounting - (File: `x/evm/state/journal.go`, `x/evm/state/accesslist.go`)

### Summary
`x/evm/state/accesslist.go` (and its duplicate in `giga/deps/xevm/state/accesslist.go`) stores the EIP-2929/2930 transient access list as a `map[common.Address]int` (`Addresses`) pointing into a parallel `Slots []map[common.Hash]struct{}` slice. When a snapshot revert removes the last slot for one address, `accessListAddSlotChange.revert()` deletes that address's entry from `Slots` by shifting all subsequent elements down (`append(slotsList[:idx], slotsList[idx+1:]...)`), but it only updates the removed address's own `Addresses[addr]` entry (`-1`). It never re-indexes the `Addresses[otherAddr]` entries of every other address whose slot-map lives at an index greater than the removed one. This is exactly the index-shift/stale-index class of bug described in the reported Solidity issue (`removeInternalRewardToken`/`removeExternalRewardToken`), applied here to the EVM StateDB access list instead of an array of reward tokens.

### Finding Description
```go
// x/evm/state/journal.go
func (e *accessListAddSlotChange) revert(s *DBImpl) {
	idx, ok := s.tempState.transientAccessLists.Addresses[e.address]
	if !ok || idx == -1 {
		return
	}
	slotsList := s.tempState.transientAccessLists.Slots
	if idx >= len(slotsList) {
		return
	}
	slots := slotsList[idx]
	delete(slots, e.slot)
	if len(slots) == 0 {
		s.tempState.transientAccessLists.Slots = append(slotsList[:idx], slotsList[idx+1:]...)
		s.tempState.transientAccessLists.Addresses[e.address] = -1
	}
}

Sequence that triggers the bug within a single top-level transaction:
1. Address `A` gets a slot added — `Addresses[A] = 0`, `Slots = [slotsA]`.
2. Address `B` gets a slot added in a subsequent (nested) call — `Addresses[B] = 1`, `Slots = [slotsA, slotsB]`.
3. The nested call for `B` reverts (e.g. Solidity `revert()`/an inner call failure causes `RevertToSnapshot`). The journal entry for `B`'s slot add is unwound: `slotsB` becomes empty, so `Slots` shrinks by removing index `1` → `Slots = [slotsA]`, and `Addresses[B] = -1`.
   - This particular shift removes the *last* element, so no other address is corrupted in this specific case.
4. However, if a third address `C` had been added *after* `B` (`Addresses[C] = 2`) before the revert unwinds `B`'s entry, then removing index `1` (`B`) via `append(slotsList[:1], slotsList[2:]...)` shifts `C`'s slot map from index `2` down to index `1`, but `Addresses[C]` is left at `2` — pointing past the end of the shrunk slice, or (if more entries exist) at the wrong slot map belonging to a different address altogether. From that point, `SlotInAccessList(C, slot)`/`AddSlotToAccessList(C, ...)` read/write the wrong `map[common.Hash]struct{}`, either indexing out of bounds (panic → node crash) or silently reusing a different address's warm-slot set.

The comment in the code even acknowledges partial ordering assumptions ("since slot change always comes after address change, and revert happens in reverse order, the address access list hasn't been cleared at this point") but does not address the multi-address index-shift case, mirroring the exact class of bug flagged in the reported audit (swap/shift-based array removal without updating dependent indices).

### Impact Explanation
`AddressInAccessList`/`SlotInAccessList` implement the go-ethereum `vm.StateDB` interface methods that back EIP-2929/EIP-2930 warm/cold gas pricing (`SLOAD`/`SSTORE`/`CALL` cost 100 vs 2100/2600 gas depending on whether a slot/address is "warm"). If the access-list index bookkeeping desyncs from the underlying `Slots` slice:
- A transaction could be charged the cheap "warm" gas cost for a cold slot (fee/refund abuse — the sender pays less gas than the EVM spec requires for that access, corresponding to "fee or refund abuse" impact class), or the reverse (overcharging), or
- Index `idx` from a stale `Addresses[addr]` entry could exceed `len(Slots)` after enough nested reverts remove entries, causing an out-of-bounds slice access panic in `Slots[idx]` inside `AddSlotToAccessList`/`SlotInAccessList`, which is invoked from EVM opcode execution during normal `eth_call`/`eth_sendRawTransaction` processing — a crash reachable from ordinary EVM transactions/RPC calls, which can halt block execution if it occurs deterministically for all validators processing the same transaction.

### Likelihood Explanation
Reaching the vulnerable path requires a specific sequence: a transaction whose execution touches storage slots for address `A`, then for address `B`, then adds `C` to the access list, and then a nested/inner-call revert unwinds the `B` slot addition while `C`'s entry remains — i.e., contracts that perform `SSTORE`/`SLOAD`/cross-contract `CALL` touching several distinct storage slots and revert intermediate sub-calls (common with reentrancy guards, DeFi routers, or contracts using try/catch-style low-level calls). This pattern is plausible in normal EVM contract usage (any dApp with nested calls that revert), so it is reachable by an ordinary transaction sender without special privileges, though the exact conditions to trigger observable gas-accounting drift or an out-of-bounds panic require a specific slot/address ordering across nested reverts, making it a real but not trivially/always-triggered condition. Full confirmation would require tracing the exact `Snapshot`/`RevertToSnapshot` journal replay implementation in `x/evm/state/statedb.go`, which the current index did not return in the available search window — this part is unverified due to index size limits, and a Devin session with full repository access would be needed to trace `RevertToSnapshot` precisely and construct a concrete failing EVM bytecode PoC.

### Recommendation
Maintain index integrity when shrinking `Slots`: either (a) swap-and-pop instead of shift-and-append so that only the address whose slot map moved to the removed index needs its `Addresses` entry updated (update the moved address's index explicitly, similar to the fix suggested in the report for `internalTokensId`/`externalTokensId`), or (b) after any shift, iterate `Addresses` and decrement every index greater than the removed one (or maintain a reverse `Slots index -> address` array so the shift can directly patch the correct `Addresses` entries in O(1)). Add regression tests that create access-list slots for 3+ addresses, revert only the middle one via snapshot revert, and assert that `SlotInAccessList` for the address that originally held the last index still returns correct results and that no out-of-bounds access occurs.

### Proof of Concept
Conceptual repro (requires wiring into `x/evm/state` test harness, not fully executed due to tool limits):
1. `db.Snapshot()` → snap0.
2. `db.AddSlotToAccessList(A, slot1)` → `Addresses[A]=0`, `Slots=[{slot1}]`.
3. `db.Snapshot()` → snap1.
4. `db.AddSlotToAccessList(B, slot2)` → `Addresses[B]=1`, `Slots=[{slot1},{slot2}]`.
5. `db.AddSlotToAccessList(C, slot3)` → `Addresses[C]=2`, `Slots=[{slot1},{slot2},{slot3}]`.
6. `db.RevertToSnapshot(snap1)` — replays journal in reverse: removes `C`'s add (empties `Slots[2]`, shift → `Slots=[{slot1},{slot2}]`, `Addresses[C]=-1`, fine), then removes `B`'s add (empties `Slots[1]`, shift → `Slots=[{slot1}]`, `Addresses[B]=-1`, fine in this order).
   - To actually reproduce corruption, the revert order must unwind `B` (middle index) while `C` (originally at a higher index) is *not* also reverted in the same pass — e.g. `C`'s access is added to a *separate*, still-valid snapshot branch that survives the revert of `B` alone. This requires a snapshot layering scenario (e.g., nested `CALL` where the inner call for `B` reverts but the outer transaction keeps `C`'s access), which needs the full `Snapshot`/`RevertToSnapshot` mechanics in `x/evm/state/statedb.go` to construct precisely — unavailable in the current search results.

func (e *accessListAddSlotChange) revert(s *DBImpl) {
	// since slot change always comes after address change, and revert
	// happens in reverse order, the address access list hasn't been
	// cleared at this point.
	idx, ok := s.tempState.transientAccessLists.Addresses[e.address]
	// If the address was already removed or has no slots (idx == -1),
	// there is nothing to revert.
	if !ok || idx == -1 {
		return
	}
	slotsList := s.tempState.transientAccessLists.Slots
	// Bounds check in case a prior revert already modified the slots slice.
	if idx >= len(slotsList) {
		return
	}

		s.tempState.transientAccessLists.Slots = append(slotsList[:idx], slotsList[idx+1:]...)

func (s *DBImpl) AddSlotToAccessList(addr common.Address, slot common.Hash) {
	s.k.PrepareReplayedAddr(s.ctx, addr)
	al := s.getCurrentAccessList()
	idx, addrPresent := al.Addresses[addr]
	if !addrPresent {
		s.AddAddressToAccessList(addr)
	}
	if !addrPresent || idx == -1 {
		// Address not present, or addr present but no slots there
		al.Addresses[addr] = len(al.Slots)
		slotmap := map[common.Hash]struct{}{slot: {}}
		al.Slots = append(al.Slots, slotmap)
		s.journal = append(s.journal, &accessListAddSlotChange{address: addr, slot: slot})
		return
	}
	slotmap := al.Slots[idx]
	if _, ok := slotmap[slot]; ok {
		// Slot already present, nothing to do (no journal entry needed)
		return
	}
	slotmap[slot] = struct{}{}
	s.journal = append(s.journal, &accessListAddSlotChange{address: addr, slot: slot})
}
