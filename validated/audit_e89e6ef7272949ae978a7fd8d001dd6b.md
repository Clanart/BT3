### Title
Recursive `AccountKeyRoleBased`/`AccountKeySerializer` RLP decoding lacks depth enforcement, enabling stack-overflow DoS from a single transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeySerializer.DecodeRLP` is a type-tag-driven "union" decoder analogous to MessagePack's `DynamicUnionResolver`-generated deserializers: it reads a `keyType` byte and then dispatches to `NewAccountKey(keyType)` followed by a type-specific `Decode` call. One of the dispatch targets, `AccountKeyRoleBased`, itself decodes an array of independently RLP-encoded sub-keys and recursively re-invokes the exact same union decoder (`NewAccountKeySerializer()` + `rlp.DecodeBytes`) for each element, with no depth counter or nesting-depth cap enforced anywhere in the decode path.

### Finding Description
The account key union decoder: [1](#0-0) 

dispatches based on an attacker-controlled `keyType` byte and then decodes the type-specific payload with no bound on how many times this can be nested.

`AccountKeyRoleBased.DecodeRLP` reads a list of independently-encoded sub-key byte strings and, for each one, constructs a *new* `AccountKeySerializer` and recursively calls `rlp.DecodeBytes`, re-entering the same union-dispatch code path: [2](#0-1) 

Because `NewAccountKey(AccountKeyTypeRoleBased)` returns another `AccountKeyRoleBased`, an attacker can encode a `RoleBased` key whose single sub-key is itself an encoded `RoleBased` key, and repeat this arbitrarily. Each nesting level only costs a few bytes of RLP overhead (a keyType byte plus small list/string headers), so tens of thousands of nesting levels fit comfortably within normal transaction size limits.

Critically, the check that is supposed to forbid nested `RoleBased` keys — `IsCompositeType()` / `ErrNestedCompositeType` in `CheckInstallable`/`CheckUpdatable` — is only invoked *after* the recursive RLP decode has already fully completed: [3](#0-2) 

This mirrors the reported bug class exactly: a recursive, type-tag-based ("union") deserializer that fails to enforce a depth limit during decoding, relying instead on a semantic validation step that only runs after the vulnerable recursive decode has already executed (CWE-674, uncontrolled recursion).

The entry point reachable from an unprivileged actor is `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable`, which unconditionally decodes the `Key` field via `AccountKeySerializer` before any validation occurs: [4](#0-3) 

This decode path runs whenever a raw transaction is parsed — i.e., on every node that receives the transaction via `eth_sendRawTransaction`/public RPC, p2p transaction propagation, or block/body decoding — long before the tx pool or state transition performs any semantic checks such as `CheckInstallable`.

I could not locate, within the indexed portion of the `rlp` package, any general nesting-depth counter analogous to `MessagePackSecurity.DepthStep` that would independently bound Go-level recursion depth for `Decoder`-implementing types; the RLP `Stream`'s `stack` field only tracks list-size accounting, not call-stack recursion depth, and each `Decoder.DecodeRLP` invocation (including `AccountKeyRoleBased.DecodeRLP`) is free to recurse without any counter check.

### Impact Explanation
A single crafted `AccountUpdate` transaction (submitted by any unprivileged sender via public RPC or gossiped over p2p) containing a deeply self-nested `AccountKeyRoleBased` payload can trigger unbounded Go-level recursion during RLP decoding on every node that parses the transaction (mempool ingestion, block validation, and re-execution by all consensus participants). This can exhaust the goroutine stack and crash the process with an uncatchable `SIGSEGV`/stack-overflow fatal error — a process-crashing Denial of Service that is simultaneously reachable by every peer/validator/RPC node that decodes the same transaction or block, i.e. a network-wide availability impact triggered by one transaction.

### Likelihood Explanation
Likelihood is high: constructing the malicious payload requires only manual RLP encoding of nested byte strings (no valid signature is even strictly required to reach the decode step, since decoding happens before signature/role validation), and the per-level overhead is small enough that a large nesting depth fits within ordinary transaction size constraints. No special privileges, staking, or governance role is needed — any transaction sender or public RPC caller can construct and submit the payload.

### Recommendation
Add explicit recursion/nesting-depth accounting to the account-key union decode path, mirroring the pattern requested in the analog advisory (`DepthStep`/`Depth--`): track a decode depth counter (e.g., via `rlp.Stream` or a package-level context threaded through `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP`), and reject decoding once a small fixed maximum depth (e.g., 1, since nested `RoleBased` keys are never semantically valid) is exceeded — enforcing the `IsCompositeType`/`ErrNestedCompositeType` invariant *during* decode rather than only after decode completes.

### Proof of Concept
Conceptually (Go-like pseudocode, since the actual encoding must be RLP bytes):
```
sub := AccountKeyLegacy{}                     // innermost real key
for i := 0; i < N; i++ {                       // N large enough to exhaust stack, e.g. 50,000+
    sub = AccountKeyRoleBased{ sub }           // wrap as RoleBased([ sub ])
}
keyBytes := rlp.EncodeToBytes(NewAccountKeySerializerWithAccountKey(sub))
txBytes  := rlp.EncodeToBytes(TxInternalDataAccountUpdate{ ..., Key: keyBytes /* raw field is []byte per serializable struct */ })
```
Submitting `txBytes` via `eth_sendRawTransaction` (or gossiping it over the p2p tx-propagation protocol) causes every receiving node to invoke `TxInternalDataAccountUpdate.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` recursively N times before any `CheckInstallable`/`IsCompositeType` rejection can occur, exhausting the Go call stack and crashing the node process.

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
```
