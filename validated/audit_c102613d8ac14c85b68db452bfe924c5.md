### Title
Unauthenticated payout OP_RETURN attribution lets an attacker frame an arbitrary operator for a withdrawal it never funded - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` attributes a Citrea withdrawal to whichever operator xonly-pubkey appears in the OP_RETURN output of the payout transaction that actually got mined for that withdrawal UTXO, with no cryptographic check that this pubkey corresponds to the entity that actually funded the payout. Because the withdrawal's Schnorr signature is only enforced/verified with `TapSighashType::SinglePlusAnyoneCanPay` (covering only input 0 and output 0), anyone who observes the honest operator's broadcast can reuse that exact signed input, add their own funding inputs, and freely rewrite every other output — including the OP_RETURN — then win the block via a fee race.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk == xonly_pk of the entity that actually supplied the funds for the mined payout_txid`.

Root cause chain:
1. `parse_withdrawal_sig_params` enforces `input_signature.sighash_type == TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) , and `Operator::withdraw` verifies the schnorr signature against this sighash [2](#0-1) . This sighash type commits **only** to the current input and the output at the same index (index 0, the user's payout output), and `ANYONECANPAY` explicitly allows arbitrary other inputs.
2. `create_payout_txhandler` builds input 0 as the user's withdrawal outpoint (key-spend), output 0 as the user payout, output 1 as an anchor, and output 2 as an OP_RETURN carrying the *fronting operator's* xonly pubkey [3](#0-2) . None of outputs 1/2 (anchor, OP_RETURN) or any additional funding inputs are covered by the user's signature.
3. `Verifier::update_finalized_payouts` looks up, per block, which payout txid actually spent each withdrawal UTXO (`get_payout_txs_for_withdrawal_utxos`, joined only on `bitcoin_syncer_spent_utxos`, i.e. whatever won on-chain) [4](#0-3) , then blindly parses the OP_RETURN of that mined transaction and writes it as `payout_payer_operator_xonly_pk` for that withdrawal index [5](#0-4) .
4. `PayoutCheckerTask` polls `get_first_unhandled_payout_by_operator_xonly_pk` keyed on the operator's own public key and, upon finding a match, automatically calls `Operator::handle_finalized_payout`, which allocates a kickoff connector and drives the full reimbursement flow — with no check that the operator actually broadcast or funded the winning payout tx [6](#0-5) , [7](#0-6) .
5. `Operator::validate_payer_is_operator` only checks `payer_xonly_pk == self.signer.xonly_public_key`, never that the payer actually funded the mined transaction [8](#0-7) .

Exploit flow: The honest operator (Operator A) broadcasts a valid payout tx (input 0 = user's signed withdrawal UTXO with `SinglePlusAnyoneCanPay`, own funding inputs, OP_RETURN = Operator A's xonly pubkey). The attacker observes this in the mempool, copies the exact witness for input 0 (a valid signature reusable under `ANYONECANPAY`), builds a conflicting transaction with the same input 0 + output 0 (mandatory to keep the signature valid) but attaches its **own** funding inputs to cover the payout amount, and substitutes the OP_RETURN with **Operator B's** (any known operator's) xonly pubkey. The attacker pays a higher fee so its version gets mined instead of Operator A's. `update_finalized_payouts` then attributes the withdrawal to Operator B. Operator B's `PayoutCheckerTask`, trusting the DB, automatically kicks off the reimbursement process and eventually receives BTC via the Reimburse transaction from bridge/round funds — despite never funding or intending to front that withdrawal. Meanwhile Operator A's own transaction is orphaned/never confirmed (A loses nothing but also gets no credit), and the attacker's own funds (used to pay the user output) are irrecoverably spent for no operator benefit to itself, purely to weaponize the misattribution against Operator B.

None of the listed guards prevent this: `is_deposit_valid` and `verify_storage_proofs` operate on the Citrea deposit/withdrawal registration, not on which Bitcoin transaction/OP_RETURN wins the block; `SECP.verify_schnorr` only verifies input 0/output 0 due to the enforced sighash flag; `is_kickoff_malicious`/BitVM circuits validate the OP_RETURN against the claiming operator's own pubkey, which is exactly the attacker-controlled field, so it does not detect the forgery; there is no DB uniqueness constraint tying `payout_payer_operator_xonly_pk` to actual UTXO ownership of the extra funding inputs.

### Impact Explanation
This directly matches the Critical category "an operator reimbursed for a payout it never funded": bridge/round collateral (BTC that should only leave to reimburse the entity that actually fronted a withdrawal) is paid out to an operator based purely on an unauthenticated OP_RETURN byte string that any unprivileged Bitcoin user can set. The attack is repeatable per Citrea withdrawal (any withdrawal race) and its target can be any operator whose xonly pubkey is public (all operators' keys are public bridge parameters), so the blast radius spans all operators and all deposits/withdrawals processed through the standard (non-optimistic) payout path.

### Likelihood Explanation
Preconditions are exactly as stated by the attacker model: mempool visibility of the honest operator's broadcast and the ability to RBF/fee-bump a conflicting transaction — both available to any unprivileged Bitcoin user with no verifier/operator/aggregator privileges. The attacker's cost is funding the user's payout output themselves (comparable to the withdrawal amount) plus the fee premium needed to win the race; there is no cryptographic barrier once the enforced sighash type (`SinglePlusAnyoneCanPay`) is understood, since it was specifically chosen to allow flexible fee-bumping/funding but as a side effect leaves the OP_RETURN and extra outputs completely unauthenticated.

### Recommendation
Bind the payout attribution cryptographically to the actual funder: either (a) require the operator's own commitment/signature over the OP_RETURN output (e.g., extend the musig/signature scheme so the fronting operator's identity is covered by a signature the verifier can check, not just embedded as free-form bytes), or (b) require `TapSighashType::All` (or `AllPlusAnyoneCanPay`, which still commits to all outputs) for the user's signature so the OP_RETURN and other outputs cannot be altered after signing while still allowing additional funding inputs, or (c) verify at kickoff/reimbursement time that the funding inputs of the mined payout tx are provably controlled by the claiming operator (e.g., via wallet-attested spend of previously registered operator collateral UTXOs) rather than trusting the OP_RETURN alone.

Test plan:
1. Set up regtest with two registered operators A and B (xonly_pk_A, xonly_pk_B known).
2. Register a Citrea withdrawal UTXO and have Operator A build+sign (via `Operator::withdraw`) a valid payout tx `tx_A` with `SinglePlusAnyoneCanPay` witness on input 0, own funding inputs, OP_RETURN = xonly_pk_A. Broadcast `tx_A` to the mempool but do not mine.
3. Construct `tx_attacker` reusing `tx_A`'s input 0 (same outpoint + copied witness) and output 0 (identical script/amount, required for the signature to remain valid), but with attacker-controlled additional funding inputs (covering the payout amount) and OP_RETURN = xonly_pk_B, at a strictly higher feerate than `tx_A`.
4. Broadcast `tx_attacker`, mine a block; assert `tx_attacker` confirms and `tx_A` is evicted/never confirms.
5. Run bitcoin-syncer/`update_finalized_payouts` processing for that block.
6. Assert `db.get_payout_info_from_move_txid(move_txid)` returns `operator_xonly_pk == Some(xonly_pk_B)` and `payout_txid == tx_attacker.txid()`, i.e., diverges from the actual funder (attacker) and from the intended operator (A).
7. Run Operator B's `PayoutCheckerTask::run_once` and assert it proceeds to call `handle_finalized_payout` and produces a `kickoff_txid`/queues the Reimburse tx for Operator B, despite Operator B never funding or signing `tx_attacker` — demonstrating the false-attribution-driven reimbursement.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
