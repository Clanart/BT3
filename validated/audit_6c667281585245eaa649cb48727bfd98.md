### Title
Payout attribution relies on an unsigned OP_RETURN output, letting anyone front a withdrawal under a chosen operator's identity - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The payout transaction's OP_RETURN output, which encodes the operator x-only pubkey used to attribute reimbursement, is not covered by the user's `SinglePlusAnyoneCanPay` signature. Any party who obtains the user's off-chain-shared payout signature can construct and broadcast the payout transaction with an arbitrary OP_RETURN value, then the bridge's chain-scanning logic (`update_finalized_payouts`) will credit reimbursement rights to whichever xonly pubkey the broadcaster chose — not necessarily the entity that actually funded the withdrawal.

### Finding Description
`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds input 0 as `SpendPath::KeySpend` signed only by `user_sig`, and adds an OP_RETURN output containing `operator_xonly_pk` at output index 2 that is unsigned. Because the user's signature uses `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` (as documented at `core/src/operator.rs:637`'s error message and the function doc at operator.rs:539-559), the signature only binds input 0 to output 0. Any other inputs (the actual BTC funding source) and the OP_RETURN output (index 2, "operator xonly pubkey that fronts the peg-out") are completely unconstrained.

`verifier.rs::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) scans confirmed payout transactions and extracts the OP_RETURN's xonly pubkey via `parse_op_return_data`, storing it unconditionally as `payer_xonly_pk` for the withdrawal (`core/src/verifier.rs:2319-2321`, persisted via `update_payout_txs_and_payer_operator_xonly_pk`). There is no check that the funding inputs of the payout transaction are actually owned/controlled by that pubkey, or that the party who added funding inputs is the same as the one referenced in OP_RETURN.

This value is later trusted as authoritative: `operator.rs::validate_payer_is_operator` (`core/src/operator.rs:1687-1740`) compares `payer_xonly_pk` against `self.signer.xonly_public_key` to decide whether *this* operator may claim reimbursement, and `PayoutCheckerTask`/`handle_finalized_payout` drive the kickoff/reimbursement flow off this same attribution.

Binding broken: `operator credited (payer_xonly_pk in OP_RETURN) == operator that actually paid (controls the funding inputs of the payout tx)`. Because the OP_RETURN is unsigned by the withdrawing user, an unprivileged actor holding the user's leaked/shared payout signature can break this equality — fronting the withdrawal with their own funds while writing a *different*, targeted operator's pubkey into the OP_RETURN, or fronting on behalf of themselves by inserting an operator pubkey that isn't theirs, or wiping the honest operator out of the race entirely by broadcasting first with a false or empty attribution.

### Impact Explanation
If an attacker (who obtains the user's payout signature, e.g. from off-chain relay traffic, a compromised operator, or simply front-running an operator's own payout broadcast in mempool) fronts the withdrawal but writes an arbitrary/foreign operator's xonly pubkey into OP_RETURN, the bridge would attribute the reimbursement right to a party who never funded the payout. Depending on which path this hits:
- If the attacker names an *honest, real* operator's pubkey while funding it with the attacker's own coins, that operator becomes "credited" and can claim BitVM reimbursement from the vault for money it never spent (reimbursed for a payout it never funded) — a Critical-class impact.
- Conversely, if the attacker races an honest operator's real payout broadcast, spending the same user withdrawal UTXO first with a mangled/invalid OP_RETURN, the true operator that actually would have funded the payout is locked out (`payer_xonly_pk` mismatch in `validate_payer_is_operator`), permanently preventing that operator from being reimbursed even though the withdrawal was fulfilled.

Both scenarios directly break bridge custody-attribution invariants specified in the scope (operator credited vs. party that paid).

### Likelihood Explanation
Exploitability requires the attacker to obtain the raw withdrawal signature before it's mined (it's shared "off-chain" per the doc comment, `# Inputs 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)`), then win a fee/mempool race to get their own OP_RETURN-mangled variant of the payout transaction confirmed first. This is plausible in a competitive multi-operator environment or if the signature leaks through logs/mempool monitoring, but it does require timing/mempool control, which lowers likelihood from certain to opportunistic.

### Recommendation
Bind the OP_RETURN operator-attribution output to the same signature the user provides. Either:
1. Change the sighash type for the payout input to cover the OP_RETURN output (e.g., `SIGHASH_ALL` or a custom sighash type covering all outputs), or
2. Have the withdrawing user (or the aggregator/verifiers at withdrawal registration time) independently commit to which operator pubkey is authorized to claim reimbursement for that specific withdrawal (e.g., store the intended operator xonly pubkey on Citrea alongside the withdrawal request, and cross-check it against the on-chain OP_RETURN in `update_finalized_payouts`, rejecting/ignoring mismatches rather than blindly trusting the OP_RETURN).

### Proof of Concept
1. Obtain the user's payout signature (`in_signature`, `SinglePlusAnyoneCanPay`) for a pending withdrawal, e.g. via mempool snooping or by being any operator that received it off-chain per the withdraw flow.
2. Construct a payout transaction reusing `input_utxo`/`user_sig` at input 0 (satisfies key-spend signature check unaffected by ANYONECANPAY), add your own funding input(s) for the output value, and add an OP_RETURN output at the expected index containing an arbitrary xonly pubkey (an honest victim operator's key, or garbage).
3. Broadcast and get it confirmed before the legitimate operator's own payout tx.
4. `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) picks up this payout, extracts the attacker-chosen pubkey via `parse_op_return_data`, and stores it as `payer_xonly_pk`.
5. `validate_payer_is_operator` (`core/src/operator.rs:1687-1740`) subsequently treats whichever operator matches that pubkey as the legitimate payer, letting them claim reimbursement they never earned — or blocking the true funder if the pubkey doesn't match any operator/matches the wrong one. pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
