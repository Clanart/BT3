### Title
Deposits confirmed before a key's activation block are permanently skipped by the scanner — ([File: processor/src/multisigs/scanner.rs](processor/src/multisigs/scanner.rs))

### Summary
Analogous to M-09 — where rewards accrued during past `boostPeriods` are silently dropped for users who did not claim inside the window — the processor's `Scanner` evaluates each block only against keys whose `activation_number <= block_being_scanned`. Any output paying to a multisig key's external address that confirms in a block *before* that key's activation block is skipped by the scan, and since the scanner only advances forward (`ram_scanned + 1 ..= latest_block_to_scan`), the output is never reported. The deposit is real on-chain yet never credited nor spendable through the protocol — the "reward earned in a past window is lost" class mapped onto Serai's block-window shape.

### Finding Description
`Scanner::run` iterates blocks strictly forward and, per block, only scans outputs for keys that are already active:

```rust
for block_being_scanned in (ram_scanned + 1) ..= latest_block_to_scan {
  ...
  for (activation_number, key) in scanner.keys.clone() {
    if activation_number > block_being_scanned {
      continue;
    }
``` [1](#0-0) 

Keys are registered with an activation block via `register_key`, which persists `(activation_number, key)` pairs: [2](#0-1) 

For Bitcoin, the external deposit address `p2tr_script_buf(key)` is a pure function of the group key — it is knowable and payable before the scanner considers the key active: [3](#0-2) 

There is no retroactive scan: once `block_being_scanned` passes, blocks below `activation_number` are never revisited for that key, and `ram_scanned` only moves forward. The deduplication/`seen` logic likewise never sees the output.

### Impact Explanation
An unprivileged depositor sends a Bitcoin transaction paying the (already-published or predictable) vault external address while a new multisig key is pending activation — e.g., racing a set rotation or simply because the address was publicly derivable ahead of the activation block. The output confirms at height `h < activation_number`. The scanner skips it (`activation_number > block_being_scanned → continue`), so no `ScannerEvent::Block` output is ever emitted for it and `ack_block` never records it. Result: funds reported/credited never occur — a received output that the protocol treats as nonexistent and therefore never spends, permanently stranding the deposit unless manual recovery is performed. This matches the report's impact class (accrued value in an earlier window silently forfeited due to evaluation-time filtering).

### Likelihood Explanation
Low. It requires a deposit to confirm inside the narrow window between key/address derivability and `activation_number`. However, it requires no privileged position — only a normal Bitcoin transaction any user can send — and the race is natural around multisig rotations, where the external address of the incoming set may be known to integrators before activation.

### Recommendation
When a key is registered, scan from the earliest block at which its address could have been paid (or from the activation block minus a safe lookback bound), rather than only blocks `>= activation_number`. Alternatively, track per-key credit independently of activation: record candidate outputs for inactive keys and emit them once the key activates, mirroring the report's recommendation to track per-window accruals independently rather than collapsing them into a single forward-only pass.

### Proof of Concept
1. Derive the next set's external address from the published/pre-activation group key `K`: `p2tr_script_buf(K)` (`networks/bitcoin/src/wallet/mod.rs:80`).
2. Send a Bitcoin tx paying that address; it confirms at block `h` while `register_key` records `activation_number = a > h` (`processor/src/multisigs/scanner.rs:98`).
3. `Scanner::run` reaches `h` either before the key is in `scanner.keys` or with `activation_number > h`, so the `continue` at line 551 skips it; once `ram_scanned >= a`, block `h` is never rescanned.
4. No `ScannerEvent` is emitted; the output is absent from `ack_block` results — funds on-chain but invisible and unspendable by the protocol.
