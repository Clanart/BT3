## Finding is valid

### Title
`get_first_op_return_output` scan lets an attacker rebind `payout_payer_operator_xonly_pk` via un-signed output injection/reordering in the `payout_tx` - ([File: circuits-lib/src/bridge_circuit/mod.rs], [File: core/src/verifier.rs], [File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs the payout input with `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP-341 only commits to the spent prevout and to the single output at the same index as the input (output 0: the user payout). The anchor output and the OP_RETURN output that carries the funding operator's x-only pubkey are never covered by the signature or by the output count. `get_first_op_return_output` then finds the operator identity by scanning `tx.output` for the *first* OP_RETURN script rather than trusting a fixed index, so anyone who can see the signature (the withdrawing user themselves, or anyone observing the honest tx in the mempool) can rebuild an alternative, still-validly-signed transaction with extra/reordered outputs and a forged OP_RETURN, and get it mined first.

### Finding Description
Binding claimed: `op_return_output.script_pubkey` read by `update_finalized_payouts` at `core/src/verifier.rs:2312-2321` (via `get_first_op_return_output`, `circuits-lib/src/bridge_circuit/mod.rs:688-692`) == the OP_RETURN written by `create_payout_txhandler` at `core/src/builder/transaction/operator_reimburse.rs:407-436` for the operator who actually fronted the withdrawal (`operator_xonly_pk` argument at line 410/418).

`create_payout_txhandler` builds the tx as `[payout_output, anchor_output, op_return(operator_xonly_pk)]` (lines 428-432) and signs only input 0 with the user's key via `set_p2tr_key_spend_witness` (line 434). The `withdraw` flow in `core/src/operator.rs:630-637` verifies this signature with `calculate_sighash_txin(0, in_signature.sighash_type)`, and `TapSighashType::SinglePlusAnyoneCanPay` uses `Prevouts::One(txin_index, ...)` (confirmed for the script-spend variant at `core/src/builder/transaction/txhandler.rs:315-321`, and the same rule applies to key-spend sighash per BIP-341). Under this sighash flag, the signature commits to: the single spent prevout, and (per BIP-341's SIGHASH_SINGLE rule) `sha_single_output` = hash of the output at the same index as the input (i.e. output 0 only). It does **not** commit to the number of outputs, their order, or the content of outputs 1..n. This is explicitly documented as intended in this codebase (`WithdrawParams` proto comment: "output_script_pubkey ... user's signature is only valid for this pubkey", `output_amount ... valid for this amount" — only output 0 is claimed as covered).

Consequently, once a signature exists for an outpoint/output0 pair (created by the withdrawing user, who under the threat model is the unprivileged attacker and legitimately possesses this signature), anyone can build a *different* transaction spending the same input, with the identical output 0 (satisfying the sighash), but with an arbitrary number of additional outputs and an arbitrary OP_RETURN placed anywhere, including before any output an honest operator intended. `get_first_op_return_output` (`circuits-lib/src/bridge_circuit/mod.rs:688-692`) simply does `tx.output.iter().find(|out| out.script_pubkey.is_op_return())` — first match wins, with no positional or uniqueness check.

Exploit flow:
1. Attacker (the withdrawing user) obtains a valid `SinglePlusAnyoneCanPay` signature over their own withdrawal input/output (as normal, via the `withdraw`/gRPC flow, `core/src/rpc/parser/operator.rs:161-203` enforces this exact sighash type but nothing more).
2. An honest operator constructs and broadcasts the real `payout_tx` = `[payout, anchor, OP_RETURN(honest_operator_pk)]` (after `fund_raw_transaction` this becomes `[payout, change, anchor, OP_RETURN]` per `change_position: Some(1)` in `core/src/operator.rs:660`, itself proof indices are not fixed/reliable even in the honest path).
3. Before the honest tx confirms, the attacker crafts a competing transaction spending the same input, keeping output 0 byte-identical (script+value), reusing the same witness signature, but inserting a dust output and a forged OP_RETURN (e.g. containing a different/incorrect xonly pubkey, or the pubkey of an operator who never funded anything) as the first OP_RETURN encountered by `.find()`.
4. Attacker broadcasts this transaction with higher fee/priority so it confirms first; the honest tx is now double-spent and can never confirm.
5. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) scans the confirmed (attacker) tx, extracts the forged pubkey via `get_first_op_return_output`/`parse_op_return_data`, and stores it as `payout_payer_operator_xonly_pk` in `withdrawals` table (`core/src/database/verifier.rs:199-251`).
6. When the real, honest operator subsequently submits a kickoff for this deposit, `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) compares `operator_xonly_pk` from the DB (forged) against `kickoff_data.operator_xonly_pk` (honest operator) at line 1887 — mismatch — the kickoff is flagged malicious and a challenge is fired (`handle_kickoff`, `core/src/verifier.rs:1966-2026`), even though the honest operator genuinely fronted the withdrawal. This can end in the honest operator's collateral being burned (if disprove path completes) or in the honest operator never being able to be reimbursed via `PayoutCheckerTask` (`core/src/task/payout_checker.rs`), since `get_first_unhandled_payout_by_operator_xonly_pk` filters `payout_payer_operator_xonly_pk = $1` and will never surface this payout to the correct operator.

No existing guard intercepts this: `SECP.verify_schnorr` only checks the signature is valid for the sighash it was created over (which itself excludes outputs 1..n and output count), `is_deposit_valid`/`is_profitable` operate before broadcast and don't observe on-chain output ordering, and `get_first_op_return_output` has no notion of a canonical/expected index.

### Impact Explanation
- The `payout_payer_operator_xonly_pk` binding — which downstream code (`is_kickoff_malicious`, `PayoutCheckerTask`) treats as ground truth for which operator gets reimbursed — can be forged by anyone controlling a valid withdrawal signature, without any privileged role.
- Consequences match Critical severity buckets: "an honest operator permanently unable to be reimbursed" and "an honest operator's collateral burned" (via a false challenge/disprove sequence triggered by `is_kickoff_malicious` misattribution), or "a false claim proved... by the bridge... circuit" if the forged pubkey happens to match some other operator who is then wrongly credited.
- Repeatable per withdrawal; the attack is available to the withdrawing user for every withdrawal they initiate (they always legitimately hold the SinglePlusAnyoneCanPay signature for their own outpoint), so blast radius scales with every withdrawal processed by any operator.

### Likelihood Explanation
- Preconditions: attacker must win a fee/priority race against the honest operator's broadcast payout transaction for the same withdrawal UTXO — feasible with standard RBF/CPFP fee bumping, no special access needed.
- Attacker cost: only Bitcoin transaction fees (must outbid the honest operator's fee rate) — no BTC stake, no keys, no privileged role required, matching the stated "unprivileged attacker" threat model exactly (they can "choose the bytes of a withdrawal UTXO, a Schnorr signature and its sighash flag, an OP_RETURN").
- Deployment config: applies to every deployment using the standard `payout_tx` construction path (`create_payout_txhandler`), i.e. the default/mainstream flow, not an edge case.

### Recommendation
Bind the OP_RETURN commitment cryptographically to the signature, or make its position/content unambiguous and covered by the signed data:
1. Change the withdrawal signature requirement to `SinglePlusAnyoneCanPay` is insufficient — require the user to sign with `AllPlusAnyoneCanPay` (or `Default`) over the full transaction template (including anchor and OP_RETURN with the intended operator pubkey), so any tampering with outputs 1..n invalidates the signature. If the protocol needs to let different operators substitute their own pubkey into the same user signature (which is the reason `SinglePlusAnyoneCanPay` was chosen), instead have the operator's own commitment be enforced by a mechanism outside the payout tx (e.g. requiring the kickoff's own signature/commitment to independently attest to the payout txid it claims to have funded, cross-checked against watch-only indexing that requires an *exact* canonical output template, not merely "contains an OP_RETURN somewhere").
2. At minimum, enforce a canonical output template check when accepting a `payout_tx` as valid for `update_finalized_payouts`/`is_kickoff_malicious`: reject transactions whose output count/order does not match the expected `[payout, anchor, OP_RETURN]` (or `[payout, change, anchor, OP_RETURN]` for the funded variant) rather than blindly taking the first OP_RETURN found.
3. Have `get_first_op_return_output` (or its caller) verify uniqueness (exactly one OP_RETURN output) and reject/flag ambiguous transactions instead of silently accepting the first match.
