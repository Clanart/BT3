### Title
Melting a PlotNFT2 singleton permanently strands unclaimed pool rewards - ([File: chia/pools/plotnft_drivers.py])

### Summary
`PlotNFT.melt()` and its wallet wrapper `PlotNFT2Wallet.melt_plotnft()` destroy the plot-NFT singleton (via the `MELT_CONDITION`/escape-value `-113` `CREATE_COIN` odd-amount trick) without first verifying that all pool rewards owed to that singleton have been claimed or forwarded. This is directly analogous to the reported `SdtStakingPositionManager.burn()` issue: an "empty state" check is used as a proxy for "safe to destroy," but pending rewards tied to the destroyed identity are not accounted for, and once the identity is destroyed those rewards become permanently unclaimable.

### Finding Description
`PlotNFT.melt()` only guards against melting while actively pooling:

```python
def melt(self, extra_conditions: tuple[Condition, ...] = tuple()) -> list[CoinSpend]:
    if self.pooling:
        raise ValueError("Cannot melt a pooling PlotNFT")
    ...
``` [1](#0-0) 

It never checks whether there are outstanding, unclaimed pool-reward coins sitting at the singleton's `RewardPuzzle` address (`p2_singleton_puzzle_hash`), i.e. rewards farmed to the singleton's self-custody reward puzzle but not yet swept via `claim_pool_rewards()` / `claim_rewards()`.

The wallet-level entry point, `PlotNFT2Wallet.melt_plotnft()`, simply calls `plotnft.melt(...)` and submits the spend without querying `plotnft2_store.get_pool_rewards()` for any pending, unclaimed rewards belonging to `self.plotnft_id`:

```python
async def melt_plotnft(self, *, action_scope, fee=uint64(0), extra_conditions=tuple()) -> None:
    plotnft = await self.get_current_plotnft()
    fee_hook = CreateCoinAnnouncement(msg=b"", coin_id=plotnft.coin.name())
    coin_spends = plotnft.melt(extra_conditions=(fee_hook, *extra_conditions))
    ...
``` [2](#0-1) 

Compare this with `claim_rewards()`, which correctly enumerates and consumes `plotnft2_store.get_pool_rewards()` before spending, and which explicitly rejects claiming while pooling: [3](#0-2) 

The reward coins are locked in a `RewardPuzzle`/`SingletonMember` puzzle that can only be spent by presenting a valid `SEND_MESSAGE` proof originating from the still-live plot-NFT singleton (identified by `singleton_id == launcher_id`), as constructed in `claim_pool_rewards()`: [4](#0-3) 
and in the reward puzzle's own `solve()`, which requires `singleton_inner_puzzle_hash` supplied by the live singleton coin: [5](#0-4) 

Once `melt()` is executed, the plot-NFT singleton spends itself with the melt/escape condition (`CREATE_COIN 0 -113`), permanently ending the singleton's coin lineage for that `launcher_id`: [6](#0-5) 

After that spend, there is no longer any live singleton coin that can send the authorizing `SEND_MESSAGE` required by the reward puzzle's solution. Any reward coin still sitting at the plot-NFT's `p2_singleton_puzzle_hash` — i.e., rewards farmed but not yet claimed/forwarded at the time of melt — becomes permanently unspendable, since the singleton needed to authorize their redemption no longer exists.

### Impact Explanation
A wallet user who melts a self-pooling plot NFT (via `plotnft melt`/`MeltPlotNFTCMD` → `melt_cmd` → `plotnft_melt` RPC → `PlotNFT2Wallet.melt_plotnft()`) while rewards are still outstanding permanently loses those funds — they become unrecoverable coins with no valid spend path (the only puzzle that can unlock them, `SingletonMember`, is now permanently unauthorizable). This is a concrete, unrecoverable loss of user funds triggered entirely by a normal wallet action (no attacker or malicious peer required), matching the "concrete unsigned or unauthorized coin movement / fund loss" bar. Because the destruction is irreversible (singleton lineage cannot be recreated for that `launcher_id`), the impact is High/Medium-severity fund loss for the affected user, directly analogous to the original report's "user rewards could be trapped."

### Likelihood Explanation
This can be triggered by any ordinary wallet user performing routine plot-NFT lifecycle management: farm rewards while self-pooling, decide to melt (dissolve) the plot NFT before running the claim step, and submit the melt transaction. There is no special timing or race condition needed — simply melting before claiming is sufficient, and the code paths (`melt_plotnft`, `MeltPlotNFTCMD`) provide no warning or guard rail against this sequence. Given plot-NFT melting is an expected, user-facing feature (`chia plotnft melt`), likelihood of accidental fund loss is realistic, especially for less-experienced users or scripted farm-management workflows that don't call `claim`/`pw_absorb_rewards` before `melt`.

### Recommendation
Before allowing a melt, check for and reject (or automatically claim) any unclaimed pool-reward coins associated with the plot-NFT's `p2_singleton_puzzle_hash`/`launcher_id`:
- In `PlotNFT2Wallet.melt_plotnft()`, query `self.wallet_state_manager.plotnft2_store.get_pool_rewards(plotnft_id=self.plotnft_id)` and raise a `ValueError` (similar to `claim_rewards()`'s "No rewards to claim" / "Cannot claim rewards while pooling" checks) if there are unclaimed rewards, instructing the user to call `claim_rewards()` first.
- Optionally, extend `melt_plotnft()`/`melt_cmd()` to atomically claim all outstanding rewards in the same transaction/bundle before or alongside the melt spend, so the melt cannot silently strand funds.
- Apply the analogous check to `PoolWallet`'s melt/leave flows if they share this trust boundary (self-pooled p2-singleton coins awaiting `claim_pool_rewards()`).

### Proof of Concept
1. Create a self-pooling plot NFT: `CreatePlotNFTCMD` with `state="local"` → `PlotNFT2Wallet.create_new()`.
2. Farm one or more blocks to the plot NFT's `p2_singleton_puzzle_hash` so that pool reward coins accumulate, as done in the test harness's `farm_blocks_to_puzzlehash(count=..., farm_to=plotnft_wallet.p2_singleton_puzzle_hash, ...)` [7](#0-6) .
3. Skip calling `plotnft_wallet.claim_rewards(...)`.
4. Call `plotnft_wallet.melt_plotnft(action_scope=...)` (or run `chia plotnft melt`), which calls `plotnft.melt()` and pushes the melt spend bundle, exactly as shown in the melt test flow [8](#0-7)  and `test_plotnft_cli_melt` [9](#0-8)  — note neither test farms/leaves outstanding rewards unclaimed before melt, which is exactly the gap: no test exercises "melt while rewards are pending," and no guard exists to prevent it.
5. After the melt spend confirms, the plot-NFT singleton coin no longer exists (destroyed via `-113` melt condition). Attempting `claim_rewards()`/`claim_pool_rewards()` for the same `plotnft_id` will fail because `get_current_plotnft()` can no longer resolve a live singleton to authorize the `SendMessage` required by `RewardPuzzle.solve()` [10](#0-9) , leaving the previously-farmed reward coin(s) permanently unspendable.

@dataclass(kw_only=True, frozen=True)
class RewardPuzzle:
    singleton_id: bytes32

    @property
    def singleton_member(self) -> SingletonMember:
        return SingletonMember(singleton_id=self.singleton_id)

    def puzzle_with_restrictions(self) -> PuzzleWithRestrictions:
        return PuzzleWithRestrictions(nonce=0, restrictions=[], puzzle=self.singleton_member)

    def puzzle(self) -> Program:
        return self.puzzle_with_restrictions().puzzle_reveal()

    def puzzle_hash(self) -> bytes32:
        return self.puzzle().get_tree_hash()

    def solve(
        self, singleton_inner_puzzle_hash: bytes32, delegated_puzzle_and_solution: DelegatedPuzzleAndSolution
    ) -> Program:
        return self.puzzle_with_restrictions().solve(
            [],
            [],
            self.singleton_member.solve(singleton_inner_puzzle_hash),
            delegated_puzzle_and_solution,
        )
