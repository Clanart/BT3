### Title
Cached FROST preprocess seed is reused across signing sessions, enabling remote secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2022-0805 is a use-after-free: a stale object is reused after its lifetime should have ended, giving heap corruption. The Serai analog is reuse of a consumed signing artifact: the coordinator caches a `CachedPreprocess` seed keyed only by `context`, and every call to `preprocess_internal` deterministically regenerates the *same* FROST nonces from that seed. Any second signing session under the same context therefore reuses an already-spent nonce pair `(d, e)`, which is exactly the condition FROST's own docs say allows third-party recovery of the signer's secret share.

### Finding Description
`AlgorithmMachine::seeded_preprocess` derives all nonce material from `ChaCha20Rng::from_seed(*seed.0)`, so the same `CachedPreprocess` always produces identical `nonces` and identical published `commitments` (`crypto/frost/src/sign.rs` lines 121-144). `from_cache` routes back through `seeded_preprocess` unchanged (`crypto/frost/src/sign.rs` lines 268-274). FROST's own spec text states "Reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md` lines 51-55).

In the coordinator, `preprocess_internal` stores the encrypted seed under `CachedPreprocesses` keyed solely by `self.context` and re-loads and re-decrypts it on every invocation (`coordinator/src/tributary/signing_protocol.rs` lines 123-147). `share_internal` calls `preprocess_internal` again to rebuild a machine (`signing_protocol.rs` line 156). Consequently, if the same context ever drives two `share_internal` calls — a retry after a `FrostError::InvalidShare`/`InvalidPreprocess` blame event, a second signing round ordered for the same context, or a re-attempt after partial failure — the returned machine carries the identical nonce pair, and `machine.sign(preprocesses, msg)` emits a second share `s = d + e·rho + λ·x·c` with the same `d`, `e` but a different `rho`/`c`/`λ`.

### Impact Explanation
Two shares `s1`, `s2` produced with the same `(d, e)` under different binding factors/messages yield `s1 − s2 = e·(rho1 − rho2) + x·(λ1·c1 − λ2·c2)`. With `e` recoverable (or when `rho1 == rho2` because the preprocess-set transcript is unchanged but the message differs, `s1 − s2 = x·λ·(c1 − c2)` directly), an observer of the two broadcast shares solves for the interpolated secret share `λ·x`. Any participant — or even a passive observer of the public share broadcasts — who triggers or merely witnesses a repeated session under one context recovers the victim validator's secret share, collapsing the threshold scheme's security. This is a key-share recovery reachable entirely via public signing-protocol messages.

### Likelihood Explanation
The design makes reuse the default: the seed is stored persistently, is only ever *written* once (`if ... is_none()` at `signing_protocol.rs` line 123), is never deleted after use, and every `share_internal` regenerates nonces from it. There is no attempt counter, message hash, or participant-set binding in the `CachedPreprocesses` key. Any code path that calls the signing protocol more than once per `context` — retries, blame-and-resume, or duplicate coordinator messages — triggers reuse without any attacker-held secret.

### Recommendation
Delete or one-shot the cached seed: after `share_internal` consumes a cached preprocess, overwrite/remove the `CachedPreprocesses` entry for that context, and/or key the cache by `(context, attempt/session-nonce)` so each signing session derives a fresh seed. At the `crypto/frost` layer, `from_cache` could additionally mix a caller-supplied session identifier into `ChaCha20Rng` seed material so nonce derivation is bound to the exact signing session rather than only to the stored seed.

### Proof of Concept
1. Context `C` is used for a signing round: `share_internal` regenerates machine `M` from cached seed, signs message `m1` with nonce commitments `(D, E)`, emits share `s1`.
2. The same context `C` is invoked again (retry or second order): `preprocess_internal` reloads the same seed, `seeded_preprocess` reproduces identical `(d, e)` and identical commitments, and `sign` emits share `s2` over `m2` (or a different participant set).
3. Observer computes `s1 − s2`. With identical nonce material, the known/public differences in `rho`, `λ`, and challenge `c` reduce this to a linear equation exposing `λ·x`, the victim's interpolated secret share — recovering the FROST key share from two public messages.
