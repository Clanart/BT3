### Title
Fee and weight calculation omits the OP_RETURN data output, understating transaction fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The VADER report describes a rate parameter initialized to a wrong value (1 second instead of 1 day), producing a rate orders of magnitude off. In Serai's in-scope code, the analogous defect lives in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: the size used for the fee-rate and weight-limit calculations is computed from an incompletely initialized transaction that omits the attacker-supplied OP_RETURN `data` output, so the achieved fee rate and the standardness weight check are computed against the wrong (smaller) transaction size.

### Finding Description
`SignableTransaction::new` accepts an optional `data: Option<Vec<u8>>` (up to 80 bytes, checked at line 171) which is pushed as an OP_RETURN `TxOut` into `tx_outs` at lines 194-202. However, the fee and weight computation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a scratch `Transaction` containing only `payments` outputs — the `data` output is never included (lines 62-99 only iterate `payments` and an optional `change`). The same omission applies to the change-recomputation at lines 225-226. As a result:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) underpays the intended fee rate by `fee_per_vbyte` × the serialized OP_RETURN output size (~10-90 vbytes depending on data length and script serialization).
2. The minimum-relay-fee check at line 211 uses the understated `vbytes`, so the comparison `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` is evaluated against a smaller size than the real transaction's. A caller passing `fee_per_vbyte = 1` with `data` produces a real transaction whose actual fee rate is below the 1000 sat/kvB relay minimum.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` that excludes the data output, so a transaction can pass the check while the actual signed transaction exceeds the standardness weight limit.

An unprivileged party controls `data` (it is public input to transaction construction, e.g. burn/metadata payloads), so this is reachable purely through public inputs.

### Impact Explanation
Transactions carrying a data payload pay a lower effective fee rate than requested. In the worst case (minimal `fee_per_vbyte`, large `data`), the signed transaction falls below the Bitcoin relay minimum fee rate and will not propagate, stalling the bridge operation it was created for; combined with the weight-check omission, an edge-case transaction can exceed `MAX_STANDARD_TX_WEIGHT` and be rejected as non-standard. This is a Medium-severity incorrect-formula issue: funds are not directly stealable, but withdrawals/metadata transactions can be produced that fail relay policy.

### Likelihood Explanation
Any construction path that passes non-empty `data` triggers the underpayment deterministically. Whether the resulting transaction actually falls under relay minimums depends on the chosen `fee_per_vbyte` and data length, but the fee shortfall occurs on every `data`-carrying transaction.

### Recommendation
Include the serialized OP_RETURN output in the weight calculation. Pass the data output (or its serialized size) into `calculate_weight_vbytes` — e.g., extend it to accept the full set of outputs including `ScriptBuf::new_op_return(...)`, in both the initial call at line 204 and the change-recomputation at line 226 — so `needed_fee`, the minimum-fee check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the real transaction.

### Proof of Concept
- `data` is appended to `tx_outs` before the weight call: `networks/bitcoin/src/wallet/send.rs:194-202`.
- `calculate_weight_vbytes` is invoked with only `payments` and no data output: `send.rs:204`, and its scratch `tx.output` is built solely from `payments` plus optional `change`: `send.rs:85-99`.
- `needed_fee` and the relay-minimum check both derive from that understated `vbytes`: `send.rs:206-213`.
- The standardness check uses the same understated `weight` unless change is added: `send.rs:241-243`.

Concrete case: `fee_per_vbyte = 1`, a payment, no change, `data` of 80 bytes. `vbytes` excludes the ~91-byte OP_RETURN output; `needed_fee` passes the min-fee check at line 211 while the real ~+91-vbyte transaction's actual fee rate is below 1000 sat/kvB, so it fails relay policy despite `SignableTransaction::new` returning `Ok`.
