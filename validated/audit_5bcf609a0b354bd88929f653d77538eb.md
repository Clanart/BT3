Audit Report

## Title
Stake accounts closed/withdrawn between epoch-reward calculation and partitioned distribution cause permanently burned rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

## Summary
`calculate_stake_rewards_and_commissions` computes each stake account's epoch reward once, at the epoch boundary, against a snapshot of `stake_delegations`. The actual payout happens later, over up to 10% of the epoch's blocks, via `build_updated_stake_reward`, which re-looks-up the account by pubkey in the *live* `stakes_cache_accounts`. If a staker fully deactivates and withdraws (closing the account) between calculation and their assigned distribution partition, the lookup fails and the already-earned reward is added to `stake_reward_lamports_burned`/`block_reward_lamports_burned` instead of being paid to anyone.

## Finding Description
`calculate_stake_rewards_and_commissions` iterates the epoch-boundary snapshot of `stake_delegations` and produces a `PartitionedStakeReward` for every stake account that had a delegation at that point, including accounts that finished deactivating during the rewarded epoch (`DeactivatedStake` case) [5](#0-4) . These rewards are hashed into partitions and distributed one partition per block over `distribution_starting_block_height .. distribution_end_exclusive`, an interval that can span up to 10% of the epoch's slots per `get_reward_distribution_num_blocks` [6](#0-5) .

When a partition is processed, `build_updated_stake_reward` re-fetches the account from the *current* stakes cache rather than using any state captured at calculation time:
```rust
let stake_account = stakes_cache_accounts
    .get(&partitioned_stake_reward.stake_pubkey)
    .ok_or(DistributionError::AccountNotFound)?
    .clone();
``` [1](#0-0) 

If that account was closed in the interim (fully deactivated stake withdrawn to zero, which is ordinary, unprivileged stake-account lifecycle usage as exercised in this repo's own CLI tests [7](#0-6) ), the lookup fails and `store_stake_accounts_in_partition`'s error branch burns the reward instead of paying it:
```rust
Err(err) => {
    error!(...);
    stake_reward_lamports_burned += stake_reward_amount;
    block_reward_lamports_burned += block_reward_amount;
}
``` [2](#0-1) 

The code comment asserts this "should never" happen because "further state mutation prevents by stake-program restrictions" [8](#0-7) , but no such bank-level guard exists in production code: the `RewardInterval` enum that models "inside/outside reward distribution interval" is defined only under `#[cfg(test)] mod tests`, not wired into transaction processing [3](#0-2) . A test in this same file explicitly documents that ordinary transactions to stake accounts proceed normally "regardless of rewards period" [4](#0-3) , confirming the assumed invariant is not enforced anywhere in the bank.

## Impact Explanation
This is a fund/accounting-correctness bug in `runtime`: the affected staker's already-earned inflation and block reward for the rewarded epoch is converted into a straight capitalization decrease (burned) instead of being paid to the account owner or their withdrawal destination. No malicious peer, validator, or privileged component is involved — an ordinary staker performing the standard deactivate → withdraw sequence can trigger this against their own reward.

## Likelihood Explanation
Likelihood is low-to-moderate, gated by timing: the delegation must be fully deactivated as of the rewarded epoch (still earning a final `DeactivatedStake` reward for the portion of the epoch it was active), and the `Withdraw` must land before that pubkey's specific partition height is processed — a window of up to ~10% of an epoch's blocks. Because partition assignment is a deterministic hash of `parent_blockhash` (public), a staker or observer can compute the target block height in advance, making deliberate self-triggering feasible with no special privilege, though it only affects the individual staker's own final reward rather than third-party funds.

## Recommendation
Do not resolve rewards by a fresh stakes-cache lookup at distribution time. Either capture the exact stake account state at calculation time and carry it forward to apply/pay the reward independently of whether the live account still exists, or enforce an actual `RewardInterval`/`EpochRewardStatus`-based guard that blocks `Withdraw`/closing instructions against a stake account that still has an outstanding, undistributed computed reward, so `AccountNotFound` genuinely cannot occur as the code comment assumes.

## Proof of Concept
1. Create and delegate a stake account; request deactivation such that it is fully deactivated as of `rewarded_epoch = current_epoch - 1`.
2. Advance to the epoch boundary; `calculate_stake_rewards_and_commissions` produces a nonzero `PartitionedStakeReward` (`DeactivatedStake`) for this pubkey.
3. Before this pubkey's assigned partition block (`distribution_starting_block_height + partition_index`, derivable from the public `parent_blockhash` via `hash_rewards_into_partitions`) is reached, submit a `Withdraw` instruction draining the account to 0 lamports, removing it from `stakes_cache_accounts`.
4. When that partition block is processed, `build_updated_stake_reward` returns `Err(DistributionError::AccountNotFound)`, and `store_stake_accounts_in_partition` adds the reward to `stake_reward_lamports_burned`/`block_reward_lamports_burned`.
5. Verify capitalization decreases by the burned amount while the staker's own final-epoch reward is never credited anywhere, using an integration test built against `runtime/src/bank/partitioned_epoch_rewards/*` similar to `test_recalculate_partitioned_rewards`/`test_rewards_computation_and_partitioned_distribution_one_block`.
