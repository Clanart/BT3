### Title
Unauthenticated attacker-controlled mirror URLs enable Server-Side Request Forgery in DataLayer sync (`chia/data_layer/download_data.py`, `chia/data_layer/data_layer_wallet.py`)

### Summary
Any wallet user can create a coin spending to the fixed `MIRROR_PUZZLE_HASH` with memos encoding an arbitrary DataLayer `launcher_id` and arbitrary URL strings [1](#0-0) . When any node tracks that `launcher_id`, `DataLayerWallet.coin_added()` parses the mirror coin's parent spend via `get_mirror_info()` and unconditionally stores the attacker-supplied URLs in the mirrors table as long as the launcher is tracked [2](#0-1) . There is no validation that the spender owns or is authorized for that store.

### Finding Description
The mirror puzzle (`create_mirror_puzzle()` = `P2_PARENT.curry(Program.to(1))`) is a fixed, unowned puzzle — anyone can spend any of their own coins to create an output with this puzzle hash [1](#0-0) . `get_mirror_info()` extracts the `launcher_id` and URL list purely from the `CREATE_COIN` condition's memos, with no signature or ownership check tying the spender to that `launcher_id` [3](#0-2) .

`DataLayerWallet.coin_added()` accepts and persists this mirror entry whenever `is_launcher_tracked(launcher_id)` is true — which happens for any store a node subscribes to or owns (launcher IDs are public, discoverable on-chain) [4](#0-3) .

These stored URLs are subsequently treated as trusted mirror servers. `DataLayer.update_subscriptions_from_wallet()` pulls all mirror URLs for a store [5](#0-4) , and `fetch_and_validate()`/`update_subscription()` iterate these server URLs, issuing outbound requests via `http_download()` (`aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)`) [6](#0-5)  or, if a downloader plugin is configured, POSTing the attacker-controlled `server_info.url` as the `url` field in `download_file()`'s request JSON to the plugin [7](#0-6) .

This is directly analogous to CVE-2018-1999017: a user-controlled URL is persisted and later fetched server-side without validating the destination — except here the "user" is not even an authenticated admin of the target resource, but any unrelated coin spender on the network.

### Impact Explanation
A DataLayer node that tracks/subscribes to a given store can be coerced into making arbitrary outbound HTTP(S) requests (SSRF) to attacker-chosen hosts, including internal network addresses, cloud metadata endpoints (e.g., `169.254.169.254`), or other services reachable from the node's network position — without the attacker needing any relationship to that store or its owner. It can also be used to trigger repeated connection attempts to third-party hosts (facilitating DoS-by-proxy against victims) or to feed attacker-controlled data into `insert_from_delta_file()`'s parsing path (mitigated somewhat by the subsequent Merkle-root verification, but the outbound-request/SSRF primitive itself is not gated by that check).

### Likelihood Explanation
Likelihood is high for triggering the SSRF request itself: creating a mirror coin only requires spending any owned coin with a `CREATE_COIN` condition to `MIRROR_PUZZLE_HASH` and appropriate memos — a standard, permissionless wallet operation reachable by any unprivileged spend-bundle submitter [8](#0-7) . The only precondition is that some victim node already tracks the targeted `launcher_id`, which is trivially satisfiable since store `launcher_id`s are public.

### Recommendation
Restrict acceptance of mirror URLs to mirrors created by the actual store's authorized publishers (e.g., verify the mirror-creating spend is associated with the DL wallet/owner of that `launcher_id`, or require an on-chain link between the mirror coin and the singleton's current owner). At minimum, apply strict URL/host validation (scheme allowlist, DNS-rebinding protection, blocking private/link-local/metadata IP ranges) before `http_download()` or the downloader plugin POST is allowed to dereference a mirror URL, mirroring the fix pattern in the Pydio advisory (validating/allowlisting destinations for the server-initiated fetch).

### Proof of Concept
1. Attacker identifies any public DataLayer `launcher_id` that some target node subscribes to or owns (visible on-chain).
2. Attacker spends any of their own coins with a `CREATE_COIN` condition targeting `MIRROR_PUZZLE_HASH` (`create_mirror_puzzle().get_tree_hash()`), with memos `[launcher_id, b"http://169.254.169.254/latest/meta-data/", ...]`.
3. Once the spend confirms, the victim's `DataLayerWallet.coin_added()` sees the mirror coin, calls `get_mirror_info()`, confirms `is_launcher_tracked(launcher_id)` is true, and stores the attacker URL as a legitimate mirror [2](#0-1) .
4. On the next `periodically_manage_data()` cycle, the victim's DataLayer service calls `update_subscriptions_from_wallet()` → `fetch_and_validate()` → `http_download()`, issuing an outbound GET to the attacker-chosen URL [6](#0-5) .

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```
