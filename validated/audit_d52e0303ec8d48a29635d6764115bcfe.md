### Title
Classic ERC20 approve() front-running/race condition in `CW20ERC20Pointer` allows spender to double-spend allowance - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer.approve()` implements Solidity's `approve(spender, amount)` by first querying the *current* on-chain CW20 allowance and then issuing a CosmWasm `increase_allowance`/`decrease_allowance` delta message to reach the target value, instead of atomically setting the allowance to the requested value. [1](#0-0) 
This reproduces the well-known ERC20 approve front-running/race-condition bug class (analogous to the collateral-overwrite front-running issue in the external report, where a party can race a pending state-changing transaction to extract more value than the counterparty intended) but here it is baked into Sei's own pointer contract used to represent CW20 tokens as ERC20 on the EVM.

### Finding Description
When an owner wants to change a spender's allowance from `A` to `B` via `approve(spender, B)`, the pointer contract computes the delta at execution time:
- If `B < A`: calls CW20 `decrease_allowance` by `A - B`.
- If `B > A`: calls CW20 `increase_allowance` by `B - A`. [2](#0-1) 

A malicious `spender` who is the target of the owner's `approve` call can watch the mempool for the owner's `approve(spender, B)` transaction and front-run it with a `transferFrom` that consumes the existing allowance `A` (spending the tokens) before the owner's transaction lands. When the owner's `approve` transaction subsequently executes, `CW20ERC20Pointer.approve()` re-queries the allowance (now `0` after the front-run drain) via `allowance(msg.sender, spender)` [3](#0-2) 
and issues an `increase_allowance` for the full new amount `B` on top of the drained allowance, rather than replacing it. The net effect: the spender has spent `A` tokens via the front-run `transferFrom`, and is left with allowance `B` afterward — effectively `A + B` total spend capability instead of the `B` the owner intended, all funded from the owner's balance and controlled entirely by the spender's own transaction ordering/gas bid (a standard front-run, no validator collusion required).

This mirrors the report's root cause: a state value (allowance/collateral) that a counterparty relies on for a subsequent action is mutable by an unprivileged party via a race, and the accepting/updating logic derives its new value from a stale/mid-flight read rather than performing an atomic, front-run-resistant update.

### Impact Explanation
Any holder of a CW20-backed ERC20 pointer token who calls `approve()` to change (especially to reduce) a spender's allowance is exposed to this attack. A malicious spender can extract more tokens from the owner's balance than the owner ever intended to authorize, i.e., unauthorized transfer of funds via the pointer contract that Sei registers and exposes on the EVM side. This satisfies the "unauthorized transfer via precompile or pointer" impact category and results in concrete fund loss for the owner.

### Likelihood Explanation
This requires only an unprivileged EVM account acting as `spender`, observing the public mempool, and submitting a higher-gas `transferFrom` transaction ahead of the owner's `approve` update — exactly the "front-run" primitive the analog scan targets. No special privileges, validator collusion, or non-default configuration are needed. Any dApp or user pattern that changes an existing non-zero allowance to a different non-zero value (a common allowance-management pattern) is vulnerable.

### Recommendation
Change `CW20ERC20Pointer.approve()` to atomically set the allowance to the exact requested value rather than computing an increase/decrease delta from a live-queried "current" allowance, if the underlying CW20 base contract exposes (or can be extended to expose) a `set_allowance`-style message; otherwise document/require the standard "approve(0) then approve(newAmount)" two-step mitigation, and consider adding first-class `increaseAllowance`/`decreaseAllowance` methods to the pointer's ABI so callers can perform race-free delta updates instead of relying on the racy `approve()` recompute-and-diff logic.

### Proof of Concept
1. Owner approves `spender` for `A = 100` tokens via `CW20ERC20Pointer.approve(spender, 100)`.
2. Owner decides to reduce the allowance and submits `approve(spender, B = 10)`.
3. `spender` observes this transaction in the mempool and front-runs it with `transferFrom(owner, spender, 100)`, draining the full existing allowance of `100` tokens before the owner's `approve` transaction is included.
4. Owner's `approve(spender, 10)` now executes: `currentAllowance` is read as `0` (drained in step 3), so per lines 70-75 it issues `increase_allowance(spender, 10)`. [4](#0-3) 
5. Net result: spender has received `100` tokens via the drained allowance plus a fresh `10`-token allowance — `110` total value extracted/controllable versus the `10` the owner intended after reducing exposure.

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
