### Title
Forged `ReceivedOutput` deserialization reports unspendable Bitcoin outputs as wallet funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an attacker-supplied scalar offset, `TxOut`, and `OutPoint` without proving that the outpoint exists or that the offset was derived through `Scanner` authorization. A forged serialized output can therefore claim that a transaction paid the wallet when no such spendable UTXO exists. [1](#0-0) 

### Finding Description
`Scanner::scan_transaction` only creates a `ReceivedOutput` after the transaction output's `script_pubkey` matches a registered script and then records the real transaction ID and output index. [2](#0-1)  `ReceivedOutput::read` bypasses that stateful registration-and-scanning process and directly trusts the encoded `offset`, `output`, and `outpoint` fields. [1](#0-0)  `SignableTransaction::new` then trusts those fields as spendable inputs, using the supplied `outpoint`, output value, and offset to construct the transaction. [3](#0-2)  The only later consistency check verifies that `key + offset·G` produces the claimed `script_pubkey`; it does not verify that the referenced outpoint exists on-chain. [4](#0-3) 

### Impact Explanation
An attacker who can provide serialized `ReceivedOutput` bytes can report a phantom deposit using the wallet's own P2TR script and a nonexistent `OutPoint`. The wallet will treat it as spendable input value, potentially accounting for funds that were never received and constructing a transaction that cannot be broadcast because its input does not exist. [3](#0-2)  This matches the report class's failure to reauthorize security-relevant fields after an initially trusted representation has been replaced by attacker-controlled data. [1](#0-0) 

### Likelihood Explanation
The attack only requires the ability to submit untrusted serialized bytes to `ReceivedOutput::read`; no private key, validator status, malformed curve point, or consensus invalidity is needed. The encoded output must use a script already associated with the target wallet and an offset that passes `multisig`, with offset zero sufficient for the wallet's base P2TR script. [5](#0-4) [4](#0-3) 

### Recommendation
Treat `ReceivedOutput` as an authenticated scanned artifact rather than a self-authenticating format. Require deserialization to bind the output to a scanner context, or expose a separate untrusted-input type whose `outpoint` and `TxOut` must be resolved against chain data and re-scanned before conversion into `ReceivedOutput`. At minimum, `SignableTransaction::new` should receive independently verified UTXOs rather than trusting deserialized `ReceivedOutput` values. [1](#0-0) [6](#0-5) 

### Proof of Concept
Construct consensus-serialized `ReceivedOutput` bytes containing:

1. A 32-byte canonical zero scalar.
2. A `TxOut` containing an arbitrary value and the victim wallet's base P2TR `script_pubkey`.
3. A random, nonexistent `OutPoint`.

Feeding those bytes to `ReceivedOutput::read` succeeds because it performs no scanner or chain verification. [1](#0-0)  Passing the result to `SignableTransaction::new` records the fabricated value and outpoint as an input. [3](#0-2)  Calling `SignableTransaction::multisig` succeeds with offset zero because the forged `TxOut` contains the wallet's real script, even though the referenced outpoint is fake. [4](#0-3)
