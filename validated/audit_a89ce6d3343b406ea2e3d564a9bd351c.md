### Title
Use of `transfer()` for native SEI unwrapping in `WSEI.withdraw()` can permanently freeze user funds - (File: contracts/src/WSEI.sol)

### Summary
The canonical Wrapped SEI (`WSEI`) contract, which is baked into the chain's genesis EVM artifacts and referenced by `x/evm/artifacts/wsei/artifacts.go` and `x/evm/client/cli/tx.go`, unwraps tokens back to native SEI using Solidity's `.transfer()`, which forwards a hard-coded 2300 gas stipend to the recipient.

### Finding Description
`WSEI.withdraw()` burns the caller's wrapped balance and sends the corresponding native value back using `payable(msg.sender).transfer(wad)`: [1](#0-0) 
Because `.transfer()`/`.send()` hard-code a 2300 gas stipend, any `msg.sender` that is a smart contract (multisig wallet, DEX router, EIP-7702 delegated account such as `BatchCallAndSponsor`, or any contract whose `receive()`/`fallback()` performs an `SLOAD`, emits an event, or does any nontrivial bookkeeping) will have its receive/fallback execution run out of gas and revert. This is the exact bug class described in the referenced report: gas-cost changes to opcodes such as `SLOAD` (post-Istanbul) can make previously-working 2300-gas fallback functions fail, and any contract that hard-codes this stipend via `transfer()`/`send()` takes an implicit, brittle dependency on gas costs. `WSEI` is a system-level wrapped-native-token contract deployed as part of the EVM module's artifacts, reachable by any unprivileged EVM transaction sender who wraps SEI and later tries to unwrap it from a smart-contract account. [2](#0-1) 

### Impact Explanation
Because `WSEI` is the standard wrapped-SEI token used across the EVM ecosystem on Sei (DEXes, routers, aggregators typically hold/interact with WSEI on behalf of contract accounts), any smart-contract holder whose fallback/receive logic exceeds 2300 gas can never successfully call `withdraw()`. The wrapped balance remains permanently locked inside the `WSEI` contract with no alternative unwrap path, resulting in permanent freezing of funds for any smart-contract holder (multisigs, routers, EIP-7702 delegated accounts, vaults) — matching the "permanent freezing" impact criterion.

### Likelihood Explanation
Likelihood is meaningful but not universal: EOAs are unaffected since they have no fallback logic, so the bug only manifests for smart-contract holders of `WSEI` whose receive/fallback consumes more than 2300 gas. Given Sei's EVM compatibility invites use of smart-contract wallets, multisigs, and EIP-7702 delegated accounts (the repo itself ships `BatchCallAndSponsor.sol` as a 7702 delegate target) that hold and route wrapped-native tokens, this is a realistically reachable path triggered by a single unprivileged transaction (`withdraw()` call).

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `WSEI.withdraw()` with a low-level `call{value: wad}("")` and check the boolean return value, following the same safe pattern already used elsewhere in the repo's `TransferHelper.safeTransferETH()`: [3](#0-2) 
Add reentrancy protection (checks-effects-interactions is already followed by decrementing balance before the external call) since `call()` forwards all remaining gas.

### Proof of Concept
1. Deploy or use the genesis `WSEI` contract instance produced from `x/evm/artifacts/wsei/artifacts.go`.
2. From an EOA, call `deposit()` with some SEI value, then `transfer()` the WSEI balance to a smart-contract account (e.g., a minimal contract whose `receive()` performs an `SLOAD` from a mapping or emits an event, consuming more than 2300 gas).
3. Have the smart-contract account call `withdraw(wad)` on `WSEI`.
4. The internal `payable(msg.sender).transfer(wad)` call reverts due to out-of-gas in the recipient's `receive()`, causing the entire `withdraw()` transaction to revert — the smart contract can never redeem its wrapped SEI balance for native SEI through this function, permanently freezing those funds. [4](#0-3)

        balanceOf[msg.sender] += msg.value;
        emit Deposit(msg.sender, msg.value);
    }
    function withdraw(uint wad) public {
        require(balanceOf[msg.sender] >= wad);
        balanceOf[msg.sender] -= wad;
        payable(msg.sender).transfer(wad);
        emit Withdrawal(msg.sender, wad);
