Audit Report

## Title
Per-IP `TokenBucket` clones inherit a stale zero `last_update` checkpoint relative to a shared `base_time`, causing every newly-seen IP to be granted a full `max_burst` token allowance instead of the configured throttled starting allotment - ([File: net-utils/src/token_bucket.rs])

## Summary
`KeyedRateLimiter::consume_tokens` creates a per-key `TokenBucket` for each new source IP by cloning a single `prototype_bucket`, which is never itself consumed from or updated [1](#0-0) . Because `Clone` copies `base_time` and `last_update` verbatim from the prototype instead of resetting them relative to the clone's own creation time [2](#0-1) , every freshly cloned bucket's first `update_state` call computes a large spurious `elapsed = now - 0` (where `now` is time since limiter construction), minting far more tokens than intended and saturating the bucket at `max_tokens` on its very first touch [3](#0-2) .

## Finding Description
`TokenBucket::new` sets `last_update = AtomicU64::new(0)` relative to a freshly captured `base_time = Instant::now()` [4](#0-3) . `time_us()` returns elapsed microseconds since `base_time` [5](#0-4) , and `update_state` mints `elapsed * new_tokens_per_us` tokens (capped at `max_tokens` via `add_tokens`) based on `now - last_update` [3](#0-2) .

`KeyedRateLimiter` holds one `prototype_bucket` and, on a cache miss (`Entry::Vacant`), clones it to create the bucket for a new key, then immediately calls `consume_tokens` on the *clone* — never on the prototype itself [6](#0-5) [1](#0-0) . Since the prototype is never touched, its `last_update` remains `0` for the lifetime of the limiter, while its `base_time` is fixed at limiter/prototype construction time. `Clone` copies both fields as-is rather than resetting `base_time` to the clone's own creation instant [2](#0-1) . Consequently, any bucket cloned after the limiter has been alive for some time will see `now` (µs since the *original*, distant `base_time`) far exceed `last_update = 0` on its first `consume_tokens`/`current_tokens` call, causing `update_state` to mint tokens well beyond `max_tokens - initial_tokens`, and `add_tokens`'s `.min(self.max_tokens)` saturates the bucket straight to `max_tokens`.

This is used directly to gate QUIC/TPU connection admission per source IP via `ConnectionRateLimiter`, which is built with `TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0)` — i.e., `initial_tokens = limit_per_minute` (intended throttled start) and `max_tokens = max_burst` (higher ceiling meant to be reached only by accruing tokens over time) [7](#0-6) . `register_connection` calls `consume_tokens` per accepted QUIC connection [8](#0-7) , and this gates connection acceptance in the QUIC listener [9](#0-8) .

I was unable to independently locate the exact call site of `ConnectionRateLimiter::new(...)` in `quic.rs` within the indexed content (the `grep_search` matched but the surrounding lines weren't retrieved with the concrete `limit_per_minute`/`max_burst` values used in production), so the exact production parameters (and thus the exact real-world time window before the bug triggers) could not be confirmed from the index. However, the mechanism itself — clone inheriting stale `last_update=0` and a distant `base_time` — is confirmed directly in `net-utils/src/token_bucket.rs`.

Existing guards reviewed: the LRU eviction (`maybe_shrink`) does not mitigate this — it only removes buckets from the map, and any subsequent re-creation for that key goes through the same buggy `prototype_bucket.clone()` path, reproducing the same bug on eviction/reconnection [10](#0-9) . The existing unit test `test_keyed_rate_limiter` does not catch this because it uses `initial_tokens == max_tokens` (`TokenBucket::new(100, 100, ...)`), which masks the bug since there is no "throttled start below max" to observe [11](#0-10) ; similarly `test_connection_rate_limiter` uses `limit_per_minute == max_burst == 3` [12](#0-11) .

## Impact Explanation
This weakens the per-IP QUIC/TPU connection-admission rate limiter, an unprivileged-remote-exhaustion defense on the non-RPC ingest path. Any source IP first observed after the limiter (and its prototype bucket) has been running long enough for `elapsed * new_tokens_per_us` to exceed `max_tokens - initial_tokens` is granted the full `max_burst` allowance on its very first connection attempt instead of the configured `limit_per_minute` throttled starting allotment — the corrupted value is the per-bucket `tokens` count immediately after creation, which should equal `initial_tokens` (=`limit_per_minute`) but instead equals `max_tokens` (=`max_burst`). This matches the in-scope "QUIC/TPU ... non-RPC remote exhaustion/crash" impact category, since it lets each newly-seen (or LRU-evicted-then-reconnecting) IP burst substantially harder than the configured admission policy intends.

## Likelihood Explanation
The bug is deterministic and requires no privileged access, timing races, or trusted assumptions — it is a pure consequence of the `Clone` implementation copying `base_time`/`last_update` from a never-touched prototype. It is triggered by ordinary conditions (any validator uptime exceeding the small threshold time, or any IP churn/eviction via `maybe_shrink`), and is reproducible by any unprivileged remote peer simply connecting from a new (or previously evicted) source IP after the relevant elapsed time.

## Recommendation
In `TokenBucket::clone`, reset `base_time` to `Instant::now()` and `last_update` to `0` for the new instance rather than copying the prototype's stale values, or alternatively store `last_update` as an absolute per-bucket instant rather than an offset from a shared, distant `base_time`, so each new bucket's elapsed-time accounting starts from its own creation time.

## Proof of Concept
1. Construct `KeyedRateLimiter::<IpAddr>::new(capacity, TokenBucket::new(60, 600, 1.0), shards)` (mirroring `ConnectionRateLimiter::new(60, 600, shards)`) and let it sit idle (no `consume_tokens`/`current_tokens` calls) for a duration such that `elapsed_us * (1.0/1e6) > 600 - 60 = 540` seconds, i.e., roughly 9+ minutes of limiter uptime.
2. Call `limiter.consume_tokens(new_ip, 1)` for a never-before-seen `new_ip`. This hits the `Entry::Vacant` branch, cloning `prototype_bucket` (inheriting `last_update = 0`, `base_time` = limiter construction time) and immediately calling `consume_tokens` on the clone [13](#0-12) .
3. Inside that call, `update_state` computes `elapsed = now (~540+ seconds in µs) - 0`, mints far more than `540` tokens, and `add_tokens` saturates `tokens` to `max_tokens = 600` [14](#0-13) .
4. Assert `limiter.current_tokens(new_ip)` returns a value close to `600` (full `max_burst`) rather than the expected `~60` (`initial_tokens`/`limit_per_minute`), demonstrating the newly-seen IP receives the full burst ceiling instead of the intended throttled starting allotment.

```rust
    fn update_state(&self, now: u64) {
        // fetch last update time
        let last = self.last_update.load(Ordering::SeqCst);

        // If time has not advanced, nothing to do.
        if now <= last {
            return;
        }

        // Try to claim the interval [last, now].
        // If we can not claim it, someone else will claim [last..some other time] when they
        // touch the bucket.
        // If we can claim interval [last, now], no other thread can credit tokens for it anymore.
        // If [last, now] is too short to mint any tokens, spare time will be preserved in credit_time_us.
        match self.last_update.compare_exchange(
            last,
            now,
            Ordering::AcqRel,  // winner publishes new timestamp
            Ordering::Acquire, // loser observes updates
        ) {
            Ok(_) => {
                // This thread won the race and is responsible for minting tokens
                let elapsed = now.saturating_sub(last);

                // also add leftovers from previous conversion attempts.
                // we do not care about who uses the spare_time_us, so relaxed is ok here.
                let elapsed =
                    elapsed.saturating_add(self.credit_time_us.swap(0, Ordering::Relaxed));

                let new_tokens_f64 = elapsed as f64 * self.new_tokens_per_us;

                // amount of full tokens to be minted
                let new_tokens = new_tokens_f64.floor() as u64;

                let time_to_return = if new_tokens >= 1 {
                    // Credit tokens, saturating at max_tokens
                    self.add_tokens(new_tokens);
                    // Fractional remainder of elapsed time (not enough to mint a whole token)
                    // that will be credited to other minters
                    (new_tokens_f64.fract() / self.new_tokens_per_us) as u64
                } else {
                    // No whole tokens minted → return whole interval
                    elapsed
                };
                // Save unused elapsed time for other threads
                self.credit_time_us
                    .fetch_add(time_to_return, Ordering::Relaxed);
            }
            Err(_) => {
                // Another thread advanced last_update first → nothing we can do now.
            }
        }
    }
```

```rust
    #[allow(clippy::arithmetic_side_effects)]
    fn maybe_shrink(&self) {
        let mut actual_len = 0;
        let target_shard_size = self.target_capacity / self.data.shards().len();
        if target_shard_size == 0 {
            return;
        }
        let mut entries = Vec::with_capacity(target_shard_size * 2);
        for shardlock in self.data.shards() {
            let mut shard = shardlock.write();

            if shard.len() <= target_shard_size * 3 / 2 {
                actual_len += shard.len();
                continue;
            }
            entries.clear();
            entries.extend(
                shard.drain().map(|(key, value)| {
                    (key, value.get().last_update.load(Ordering::SeqCst), value)
                }),
            );

            entries.select_nth_unstable_by_key(target_shard_size, |(_, last_update, _)| {
                Reverse(*last_update)
            });

            shard.extend(
                entries
                    .drain(..)
                    .take(target_shard_size)
                    .map(|(key, _last_update, value)| (key, value)),
            );
            debug_assert!(shard.len() <= target_shard_size);
            actual_len += shard.len();
        }
        self.approx_len.store(actual_len, Ordering::Relaxed);
    }
```
