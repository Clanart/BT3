### Title
Unauthenticated `ReceivedOutput` deserialization permits forged unspendable Bitcoin inputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

**Severity: Medium**

`ReceivedOutput::read` accepts an offset, claimed `TxOut`, and arbitrary `OutPoint` without verifying that the outpoint actually contains that output or that the output was produced by a `Scanner` for the relevant key. [1](#0-0) 

This is analogous to improper path sanitization: the serialized `OutPoint` is treated as authority over which blockchain object is being accessed, while the accompanying `TxOut` is merely attacker-supplied metadata. [2](#0-1) 

### Finding Description

`Scanner::scan_transaction` constructs a trustworthy binding by copying an actual transaction output and setting `outpoint` to `OutPoint::new(tx.compute_txid(), vout)`. [3](#0-2) 

`ReceivedOutput::read` does not preserve that binding and instead independently deserializes `offset`, `output`, and `outpoint`. [4](#0-3) 

`SignableTransaction::new` then trusts the deserialized value for balance/fee checks and the deserialized outpoint as the transaction's `previous_output`. [5](#0-4) 

The only later ownership check verifies that the supplied `offset` derives the claimed `script_pubkey`; it does not verify that the referenced UTXO exists or equals the claimed `TxOut`. [6](#0-5) 

The signing path commits to this attacker-controlled prevout metadata through `Prevouts::All` and signs the resulting Taproot sighash. [7](#0-6) 

### Impact Explanation

An attacker who can supply bytes to `ReceivedOutput::read`, including through a containing `Output`/`Plan` deserialization boundary, can create a deposit record for a Serai-controlled address while naming an arbitrary or nonexistent outpoint. [8](#0-7) 

That forged record reports `balance()` from the attacker-chosen `TxOut`, even though no corresponding spendable UTXO was proven. [9](#0-8) 

If passed into `SignableTransaction::new`, the forged input can be used to build and sign a transaction spending the bogus `previous_output`. [10](#0-9) 

This produces the concrete failure mode of funds being reported as received but not being spendable, and can additionally consume a signing attempt for a transaction Bitcoin will reject. [11](#0-10) 

### Likelihood Explanation

The attacker needs control over serialized `ReceivedOutput` bytes and knowledge of a scanned script and its registered offset. [12](#0-11) 

The base output uses offset zero, and other scripts are determined by registered scalar offsets, so no private key material is needed to make the later script check pass. [13](#0-12) 

This is not exploitable through `Scanner::scan_transaction` itself, because that constructor derives the `OutPoint` from the actual transaction; the vulnerable boundary is specifically deserialization or another path that accepts `ReceivedOutput` without chain validation. [14](#0-13) 

### Recommendation

Do not expose `ReceivedOutput::read` as proof of spendability. [1](#0-0) 

For untrusted input, require a `Scanner` plus the containing transaction or a UTXO lookup, then reconstruct the `ReceivedOutput` only after confirming `tx.output[vout] == claimed_output` and `tx.compute_txid() == claimed_outpoint.txid`. [14](#0-13) 

Alternatively, make `SignableTransaction::new` or `multisig` take an authenticated UTXO provider so `prevouts` cannot be replaced independently of `previous_output`. [6](#0-5) 

### Proof of Concept

```rust
// Conceptual PoC over untrusted serialized bytes.
// Assume `group_key` is the even key used by Scanner::new(group_key).

let script = p2tr_script_buf(group_key).unwrap();

let claimed_output = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: script,
};

// Completely arbitrary/nonexistent UTXO reference.
let forged_outpoint = OutPoint {
  txid: Txid::all_zeros(),
  vout: 0,
};

let mut serialized = Vec::new();
serialized.extend(Scalar::ZERO.to_bytes());
serialized.extend(serialize(&claimed_output));
serialized.extend(serialize(&forged_outpoint));

// Accepted despite no proof that txid:vout contains claimed_output.
let forged = ReceivedOutput::read(&mut serialized.as_slice()).unwrap();

// The wallet reports the claimed amount as received.
assert_eq!(forged.value(), 1_000_000);

// The spend uses the forged outpoint and claimed prevout metadata.
let signable = SignableTransaction::new(
  vec![forged],
  &[(destination_script, 10_000)],
  None,
  None,
  20,
).unwrap();

// The base-key offset/script check passes even though the referenced
// UTXO was never authenticated.
assert!(signable.multisig(&keys).is_some());
```

The deserialization succeeds because `read` performs only canonical field and consensus decoding. [4](#0-3)  The resulting transaction construction consumes `forged.outpoint` as `previous_output`, while `multisig` checks only that the claimed script corresponds to the claimed offset-derived key. [5](#0-4)
