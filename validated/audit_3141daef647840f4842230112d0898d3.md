### Title
`solo.Claim` sweeps the *entire current balance* of the legacy sender account instead of a fixed claimable snapshot amount - ([File: precompiles/solo/solo.go])

### Summary
`precompiles/solo/solo.go`'s `Claim` method authenticates a signed `MsgClaim`/`MsgClaimSpecific` from a legacy Sei account (`sender`), and then transfers away that account's balance to the caller's associated address. Like the GMX `deposit`/`withdraw` functions that sweep "whole balance" to the Trove under the assumption that only the tracked amount can arrive there, `Claim` sweeps `p.bankKeeper.GetAllBalances(ctx, sender)` — the sender's *live, current* balance — rather than any amount fixed/snapshotted at claim-authorization time. Any coins that land in `sender` between when the claim message was signed and when the `claim()` precompile call is broadcast/executed are swept along with the intended funds to the caller, not to the rightful depositor of those later funds.

### Finding Description
`Claim` does:
```go
if err := p.bankKeeper.SendCoins(ctx, sender,
    p.evmKeeper.GetSeiAddressOrDefault(ctx, caller), p.bankKeeper.GetAllBalances(ctx, sender)); err != nil {
``` [1](#0-0) 

This mirrors the GMX report's root cause precisely: the contract assumes the *only* funds that can be present in the account it is about to sweep are the ones intended for the current operation, and unconditionally moves the entire live balance rather than a bounded, pre-committed amount. `sigverify` only proves that `sender` authorized a claim tx with a certain sequence number at signing time — it does not fix or attest to *how much* is being claimed — so `GetAllBalances` is evaluated fresh at execution time in `Claim`. [2](#0-1) 

Because `sender` is a legacy Sei (non-EVM-associated) account address that remains capable of receiving ordinary bank sends from anyone at any time (nothing blocks deposits into it), any usei/token sent to `sender` after the claim message was signed but before the `claim()` transaction lands on-chain will be captured by the same `SendCoins(ctx, sender, callerSeiAddr, GetAllBalances(...))` call and forwarded to `caller`'s associated address — exactly analogous to GMX rewards arriving during the deposit/withdraw delay window and being swept to the wrong destination.

Note that `ClaimSpecific` (the sibling method) narrows this by only sending `GetBalance(ctx, sender, denom)` for the exact denom listed in the asset list, per-asset — it is not vulnerable to this over-sweep pattern in the same way. `Claim`, however, has no analogous restriction to a fixed claimable set/amount.

### Impact Explanation
This allows an unrelated third party's transfer to a legacy account to be redirected to whoever races a `claim()` transaction for that account, if that legacy account still has a valid unclaimed authorization outstanding (a signed but not-yet-broadcast `MsgClaim`) or if the claim tx is broadcast after the deposit lands but the signature was generated before. Funds sent to `sender` in that window are unconditionally transferred out via the EVM `SoloAddress` precompile to the caller instead of remaining under the depositor's/sender's control — a direct fund-misdirection/loss for whoever deposited to `sender` in that window, and an unintended windfall for the entity broadcasting the claim.

### Likelihood Explanation
Likelihood is constrained: an attacker/caller must already possess a validly signed `MsgClaim` tx for the target `sender` account (i.e., co-operating with or is the account holder), and must time the `claim()` broadcast to land after a third party's incoming transfer to `sender`. This can happen naturally (e.g. someone republishes/holds a signed claim message and only submits it later, or exchanges/relays doing async legacy-account migrations), and is entirely within the reach of a normal unprivileged EVM caller invoking the `solo` precompile — no validator/node privilege is required. It does not require a malicious node or consensus-level assumption, only an ordinary transaction submission at an opportunistic moment.

### Recommendation
Bind the amount transferred by `Claim` to a value fixed at signing/authorization time rather than the live balance read at execution:
- Include the intended claim amount (or a coin-list snapshot) inside `MsgClaim` itself, sign over it, and have `Claim` transfer exactly that amount (failing if the current balance is insufficient), mirroring the approach already used in `ClaimSpecific` for per-asset amounts.
- Alternatively, snapshot `sender`'s balance at the time the claim message's sequence number was valid (e.g., require the claim to be broadcast in the same block/sequence window, or store a snapshot balance keyed by account+sequence) so that later inbound transfers are excluded from the sweep.

### Proof of Concept
1. Legacy account `S` (not yet EVM-associated) holds balance `B`, and its owner signs a `MsgClaim{Claimer: attackerEVMAddr, Sender: S}` (sequence `n`) but does not immediately broadcast the `claim()` EVM tx.
2. Before the `claim()` call lands on-chain, a third party sends additional funds `X` to `S` via an ordinary bank transfer (unaware a claim is pending).
3. The holder of the signed claim message calls `SOLO.claim(signedTxBytes)` from `attackerEVMAddr`.
4. `validate`/`sigverify` succeed (sequence `n` still matches, since `S` hasn't sent any tx to bump its sequence).
5. `Claim` executes `SendCoins(ctx, S, attackerSeiAddr, GetAllBalances(ctx, S))`, transferring `B + X` to the attacker's associated address — the third party's `X` is misdirected instead of remaining recoverable by/for `S`'s legitimate depositor.

func (p PrecompileExecutor) sigverify(ctx sdk.Context, tx sdk.Tx, claimMsg claimMsg, sender sdk.AccAddress) error {
	sigTx, ok := tx.(authsigning.SigVerifiableTx)
	if !ok {
		return errors.New("claim tx must be a SigVerifiableTx")
	}
	var pubkey cryptotypes.PubKey
	pubkeys, err := sigTx.GetPubKeys()
	acct := p.accountKeeper.GetAccount(ctx, sender)
	if acct == nil {
		return fmt.Errorf("account %s does not exist", claimMsg.GetSender())
	}
	if err == nil {
		if len(pubkeys) != 1 {
			return fmt.Errorf("claim tx can be signed by exactly 1 key but %d signed", len(pubkeys))
		}
		pubkey = pubkeys[0]
	} else {
		// try find pubkey from storage
		pubkey = acct.GetPubKey()
		if pubkey == nil {
			return errors.New("must provide pubkey from accounts that have never sent transactions")
		}
	}
	pubkeyAddr := sdk.AccAddress(pubkey.Address())
	if !bytes.Equal(pubkeyAddr, sender) {
		return fmt.Errorf("claim message is for %s but was signed by %s", sender.String(), pubkeyAddr.String())
	}
	sigs, err := sigTx.GetSignaturesV2()
	if err != nil {
		return fmt.Errorf("failed to get signatures due to %w", err)
	}
	if len(sigs) != 1 {
		return fmt.Errorf("claim tx should have exactly 1 signature but got %d", len(sigs))
	}
	sig := sigs[0]
	if sig.Sequence != acct.GetSequence() {
		return fmt.Errorf("account sequence mismatch for claim tx (%d vs. %d)", sig.Sequence, acct.GetSequence())
	}
	if err := authante.DefaultSigVerificationGasConsumer(ctx.GasMeter(), sig, p.accountKeeper.GetParams(ctx)); err != nil {
		return fmt.Errorf("insufficient gas for sig verification: %w", err)
	}
	signerData := authsigning.SignerData{
		ChainID:       ctx.ChainID(),
		AccountNumber: acct.GetAccountNumber(),
		Sequence:      acct.GetSequence(),
	}
	if err := authsigning.VerifySignature(pubkey, signerData, sig.Data, p.txConfig.SignModeHandler(), tx); err != nil {
		return fmt.Errorf("failed to verify signature for claim tx: %w", err)
	}
	// increment sequence
	_ = acct.SetSequence(acct.GetSequence() + 1)
	p.accountKeeper.SetAccount(ctx, acct)
	return nil
```
