### Title
Front-runnable "flash-vote" dilutes newly-harvested Wombat bribes at the expense of long-term voters - ([File: rewards/BaseRewardPoolV2.sol], [File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.vote()`/`castVotes()`/`claimBribe()` distribute freshly harvested bribes through `BribeRewardPool`'s `rewardPerTokenStored` accounting, which is updated as an instantaneous lump-sum division by `totalStaked()` rather than a time-weighted rate. Because `stakeFor` (invoked from `vote`) snapshots `userRewardPerTokenPaid` to the *pre-harvest* `rewardPerTokenStored` before the caller's new stake is added to `totalStaked()`, an attacker who stakes (votes) immediately before `castVotes()` harvests bribes captures a full pro-rata share of that harvest despite having zero time-weighted exposure, diluting the share earned by voters who held their position through the whole epoch.

### Finding Description
- `vote(_lps, _deltas)` with a positive delta calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))`. [1](#0-0) 
- `stakeFor` in `BribeRewardPool` runs the `updateRewards(_for, rewardTokens)` modifier before increasing `_balances[_for]`. That modifier computes `_earned` using the pre-stake balance and then sets `userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken)` (the *current*, pre-harvest `rewardPerTokenStored`), only after that does the staking body increase `_balances`. [2](#0-1) [3](#0-2) 
- `castVotes()` harvests bribes from Wombat and forwards them into the pool rewarders (`wombatStaking.vote(...)`), which eventually calls the internal reward-queuing logic. That logic adds the new bribe as `rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()` — an instantaneous, non-time-weighted distribution based on whoever is currently staked at that exact call. [4](#0-3) 
- Because the attacker's `stakeFor` already incremented `_balances`/`totalSupply` before `castVotes()` runs (front-run in the same block, or simply the preceding transaction), the attacker's stake is counted in `totalStaked()` when the new `rewardPerTokenStored` is computed, entitling the attacker to a pro-rata share of the entire harvested bribe.
- `earned()`/`_earned()` computes `userShare * (rewardPerToken - userRewardPerTokenPaid) / decimals + userRewards`, so the attacker's `userRewardPerTokenPaid` (frozen at the pre-harvest value) times the post-harvest jump in `rewardPerTokenStored` yields a nonzero, and proportionally large, `earned` value immediately after `castVotes()`. [5](#0-4) 
- The attacker then calls `claimBribe([lp])` → `_claimBribeFor` → `getReward(_for, _for)` on the rewarder to withdraw the profit in the same block, or can immediately withdraw the vote via `vote()` with a negative delta (no lock/cooldown enforced in `vote()`). [6](#0-5) [7](#0-6) 
- Neither `vote()` nor `castVotes()` nor `stakeFor`/`withdrawFor` enforce any minimum holding period, cooldown, or snapshot-based eligibility check that would prevent a same-block stake-then-harvest-then-claim sequence. [8](#0-7) [9](#0-8) 

This is a legitimate design flaw distinct from the "conservation" framing in the prompt: the attacker is not claiming rewards accrued strictly *before* their stake existed in the ledger sense (the reward-per-token snapshot mechanism is internally consistent and `earned == 0` immediately at stake time, before any new reward is queued). The actual bug is that the reward-per-token model treats the entire epoch's bribe as accruing atomically at harvest time rather than continuously over the epoch, so a stake placed one block before harvest captures the same share as a stake held the entire epoch, diluting long-term voters' fair share.

### Impact Explanation
This enables **theft of unclaimed yield from long-term voters**: an attacker can direct freshly acquired/locked vlMGP voting power at a specific pool right before a (public, permissionless) `castVotes()` call harvests that pool's Wombat bribe, capture a pro-rata share of the entire harvested bribe amount, then immediately unvote/withdraw — with essentially zero time-weighted contribution to that pool's votes. This directly reduces the payout available to voters who maintained their allocation throughout the epoch, i.e. redistribution of yield away from legitimate long-term stakers to a last-block entrant.

### Likelihood Explanation
- Feasibility is moderate: the attacker needs vlMGP (locked MGP) voting power, which is not flash-loanable in a single transaction (locking generally requires time), but existing vlMGP holders — including large holders who already control votes elsewhere — can redirect their vote at will via `vote()` with no lock or delay.
- `castVotes()` is a public function with no access control and no restriction preventing anyone from front-running it once it's visible in the mempool (or simply calling `vote()` immediately before calling/observing `castVotes()`). [10](#0-9) 
- The attack is repeatable every harvest cycle and scales with the size of the harvested bribe and the attacker's available vlMGP.
- No reentrancy or privileged role is required — this is achievable by any EOA holding vlMGP.

### Recommendation
Introduce time-weighted reward accrual so that reward eligibility is proportional to the duration a voter's stake has been present, not just their balance at the instant of harvest. Options:
- Convert `BribeRewardPool` reward distribution to a rate-based/streaming model (à la classic `StakingRewards`, tracking `rewardRate` and `lastUpdateTime`) instead of instantaneous lump-sum `rewardPerTokenStored` updates.
- Alternatively, snapshot voting weight at the start of each epoch (e.g., require votes to be locked in before a defined cutoff prior to `castVotes()`, and only count balances as of that snapshot for reward calculation), rejecting/deferring stakes that occur after the snapshot to the next epoch.
- Add a minimum holding period (cooldown) before a newly staked/voted balance becomes eligible for currently-pending bribe distributions.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `BribeRewardPool`, mock `WombatStaking`/Wombat bribe contracts, and vlMGP/veWom mocks with a pool having existing long-term voter `Alice` with a large vote balance.
2. Simulate bribe accrual on the Wombat side (mock bribe contract holding a known reward amount for the pool).
3. In one block: attacker `Bob` (already holding vlMGP) calls `vote([lp], [+delta])` directing a large vote weight at the target pool.
4. Immediately in the same block: call `castVotes(false)` to harvest the bribe, causing `rewardPerTokenStored` to jump based on `totalStaked()` that now includes Bob's newly staked delta.
5. Bob calls `claimBribe([lp])`.
6. Assert `earned(Bob, rewardToken) > 0` right after step 4 (before claim) and that the transferred amount in step 5 is proportional to `delta / totalStaked()` of the full harvested bribe — despite Bob having staked in the same block as harvest.
7. Compare Alice's `earned()` before/after to show her effective share of the harvest was diluted below what it would have been absent Bob's front-run stake.
8. Optionally show Bob can immediately call `vote([lp], [-delta])` to withdraw his voting power right after claiming, completing a same-block stake→harvest→claim→unstake cycle.

        if (_lps.length != _deltas.length)
            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
                totalVlMgpInVote += uint256(totalUserVote);
            } else {
                userTotalVotedInVlmgp[msg.sender] -= uint256(-totalUserVote);
                totalVlMgpInVote -= uint256(-totalUserVote);
            }
        }

        if (userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender))
            revert NotEnoughVote();
    }

    modifier updateRewards(address _account, address[] memory _rewards) {
        uint256 length = _rewards.length;
        uint256 userShare = balanceOf(_account);
        
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewards[index];
            // if a reward stopped queuing, no need to recalculate to save gas fee
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userShare);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
