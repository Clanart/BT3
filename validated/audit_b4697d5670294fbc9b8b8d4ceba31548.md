### Title
Unvalidated `beneficiary` bytes32 truncation in IntentGatewayV2 causes silent misdirection of settled funds - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2.placeOrder()` accepts a user-supplied `order.output.beneficiary` as a raw `bytes32` and never validates that it is a canonically zero-padded 20-byte EVM address before escrowing the user's input tokens and computing the order commitment. When the order is later filled — same-chain via `IntrinsicIntents` or cross-chain via `ExtrinsicIntents._fillCrossChain`/`_release` — the contract derives the payout address with a raw truncating cast `address(uint160(uint256(order.output.beneficiary)))`, silently discarding any non-zero upper 96 bits instead of reverting. This is the same bug class as the external report: malformed/non-canonical recipient bytes pass every validation step, funds are moved (escrowed/settled), and the destination logic silently truncates/misinterprets the bytes instead of rejecting them — resulting in funds landing at an address the user never controlled, with no recovery path.

### Finding Description
`PaymentInfo.beneficiary` is declared as `bytes32` [2](#0-1) . `placeOrder()` stamps `order.user`, `order.source`, `order.nonce`, validates input amounts and duplicate output tokens, computes the commitment over the full `order` struct (including the raw `output.beneficiary` bytes32), and escrows tokens — at no point checking that `output.beneficiary`'s upper 96 bits are zero [3](#0-2) . The commitment and escrow are finalized with whatever bytes32 the caller supplied [4](#0-3) .

When a solver fills the order, both cross-chain and same-chain paths derive the actual payout address by truncating cast rather than validated decode:

```solidity
address beneficiary = address(uint160(uint256(order.output.beneficiary)));
``` [5](#0-4) 

The same pattern recurs in the escrow-release path used for both `RedeemEscrow` and `RefundEscrow`:
```solidity
address beneficiary = address(uint160(uint256(body.beneficiary)));
``` [6](#0-5) 

Because `commitment = keccak256(abi.encode(order))` is computed over the raw, unvalidated `bytes32` [7](#0-6) , the order can only be filled/matched using the exact same non-canonical `beneficiary` value — so the truncation at fill-time is deterministic and reproducible, but it delivers funds to `address(uint160(x))`, not to the address the user actually intended if they (or a wallet/integration bug) supplied a value with non-zero upper bytes. This mirrors the report's root cause precisely: the entrypoint (`placeOrder`) that moves/escrows value never validates recipient-format correctness, and the destination-side decode (`address(uint160(uint256(...)))`) never reverts on malformed input — it just silently produces a wrong-but-valid address, worse than reverting because there is no `Unrecoverable`/failure signal at all.

Notably, the codebase demonstrates it knows how to guard exactly this class of bug elsewhere: `HyperFungibleToken._toAddr()` explicitly reverts with `InvalidAddress(length)` if the recipient bytes aren't exactly 20 bytes [8](#0-7) , and `_authenticate()` in the same intents module reverts on a malformed 20-byte module identity [1](#0-0) . No equivalent guard exists for `PaymentInfo.beneficiary` anywhere in `placeOrder`, `fillOrder`, or `_release`.

### Impact Explanation
Any unprivileged user calling `placeOrder()` with a non-canonically-padded `output.beneficiary` (e.g., a full 32-byte value from a non-EVM address book, a client bug that doesn't left-pad, or accidental byte corruption) will have their input tokens escrowed against a commitment that bakes in the bad value. Fillers execute `fillOrder`/cross-chain fill using the exact `order` struct that reproduces the commitment, so they correctly compute `beneficiary = address(uint160(uint256(order.output.beneficiary)))` per the contract's own logic — sending real output funds to a derived, effectively arbitrary 20-byte address that the depositor does not control. The escrowed input tokens are then released to the solver as designed, closing the loop with the funds gone to the wrong party. There is no revert, no `Unrecoverable` event, and no retry path — this is a direct, permanent loss/misdirection of user funds triggered purely by an unprivileged user-supplied field, matching the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" impact categories.

### Likelihood Explanation
`placeOrder()` is a fully public, unprivileged entrypoint; no relayer, prover, or admin collusion is required. The only precondition is that the caller (or its integrating wallet/SDK) supplies a `bytes32` beneficiary that isn't canonically zero-padded — plausible for any integration that doesn't go through the reference SDK helpers (`bytes20ToBytes32`) and instead passes a raw hash, an address concatenated with extra data, or a corrupted value. Because the contract silently accepts and commits to the bad value rather than rejecting it up front, the mistake is not caught until settlement, by which point escrowed funds have already moved.

### Recommendation
Validate `order.output.beneficiary` (and any other `bytes32` address-like fields consumed via truncating casts, e.g. `WithdrawalRequest.beneficiary`) at the point of first use — either in `placeOrder()` before escrow, or immediately before the truncating cast in `_fillCrossChain`/`_release`/`IntrinsicIntents` fill logic — by requiring the upper 96 bits to be zero (mirroring `HyperFungibleToken._toAddr`'s revert-on-mismatch pattern) rather than silently truncating. Reject the order/fill with a descriptive error (e.g. `InvalidBeneficiary`) instead of allowing settlement to proceed against an unintended address.

### Proof of Concept
1. Attacker/careless user calls `placeOrder(order, graffiti)` where `order.output.beneficiary = bytes32(uint256(0xAAAABBBB...<32 bytes with non-zero upper 96 bits>))` (i.e., not left-padded to a 20-byte address). `placeOrder()` performs no format check on this field [3](#0-2) ; input tokens are escrowed and `commitment = keccak256(abi.encode(order))` is recorded with the raw value.
2. A solver observes the order, matches outputs, and calls `fillOrder`/cross-chain fill with the identical `order` struct (required to match `commitment`).
3. `_fillCrossChain` (or the same-chain equivalent) computes `beneficiary = address(uint160(uint256(order.output.beneficiary)))` [5](#0-4) , silently truncating the non-zero upper bytes, and transfers the output tokens to this derived address.
4. `RedeemEscrow` releases the escrowed input tokens to the solver via `_release`, which likewise truncates any malformed `body.beneficiary` without validation [6](#0-5) .
5. The user's intended beneficiary never receives the funds; there is no revert, no unrecoverable-state event, and no mechanism to reclaim or redirect the settled tokens.
