### Title
Swallowed conversion error in IBC refund/timeout path permanently locks user funds in the erc20 module account - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
This is a Cosmos EVM analog of the HydraDX "irreversible state after partial operation" bug class. Instead of an AMM's shares/reserve invariant breaking after full liquidity removal, the broken invariant here is the 1:1 "escrow coin ↔ unescrow ERC20 token" atomicity that `ConvertCoinNativeERC20` is supposed to guarantee. When this function is invoked from the IBC refund/timeout path (`ConvertCoinToERC20FromPacket`), a failure in the second half of the conversion (the EVM `transfer` call) is silently discarded, but the first half (escrowing the user's bank coin into the `erc20` module account) has already been committed. The result: the user's refunded coin is consumed into the module account and neither the coin nor the equivalent ERC20 token is ever returned to them.

### Finding Description
`ConvertCoinNativeERC20` performs the ERC20 reconversion in two sequential, non-atomic steps: [1](#0-0) 

1. `SendCoinsFromAccountToModule` — escrows the user's native coin into the `erc20` module account.
2. `CallEVM(... "transfer" ...)` — unescrows the equivalent ERC20 token from `types.ModuleAddress` to the receiver.

If step 2 fails (e.g., the ERC20 contract exists but reverts, is paused, lacks sufficient balance, or otherwise errors post-escrow), the function returns an error, but **step 1 is never rolled back** because there is no `CacheContext`/`write` pattern around the two operations.

This function is called from `ConvertCoinToERC20FromPacket`, which is invoked by both `OnAcknowledgementPacket` (on an IBC error acknowledgement) and `OnTimeoutPacket`: [2](#0-1) 

Critically, the caller swallows the error from `ConvertCoinNativeERC20` and returns `nil`: [3](#0-2) 

Because `OnAcknowledgementPacket`/`OnTimeoutPacket` return `nil` regardless of the internal failure, the enclosing `MsgAcknowledgement`/`MsgTimeout` transaction is treated as fully successful by baseapp and its cached state (including the already-executed `SendCoinsFromAccountToModule` escrow) is committed to the store. The user is left with neither the refunded native coin (now sitting in the `erc20` module account) nor the ERC20 token they were supposed to receive back.

The code comment even acknowledges the fallback design intent ("the user receives the corresponding bank token from the TokenPair instead") but this design assumption is violated because the coin has already been moved out of the user's account into the module account before the failure is detected — the fallback state described in the comment is not what actually happens on this code path.

### Impact Explanation
This matches the "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... escrowed assets" impact category. A user's coins are moved into the `erc20` module account with no corresponding ERC20 unescrow and no way for the user to reclaim them (no query/msg path exists to pull funds back out of this specific stuck state), constituting a permanent, unauthorized loss of spendable value triggered through ordinary, unprivileged IBC transfer failure/timeout handling — not requiring any relayer or validator misbehavior. Any user whose IBC transfer of a native-ERC20-backed token fails or times out to a chain where the paired ERC20 contract cannot execute the internal `transfer` call (contract paused, insufficient allowance/balance at `ModuleAddress`, EVM-level revert, gas issues, etc.) is exposed.

### Likelihood Explanation
Triggering requires: (1) a `TokenPair` of type `OWNER_EXTERNAL` (native ERC20), (2) an IBC transfer of that denom that fails to be received or times out (both are ordinary, permissionless occurrences — a relayer simply not delivering the packet in time is enough to trigger `OnTimeoutPacket`), and (3) the `CallEVM` unescrow step failing for any reason after the coin has already been escrowed. Condition (3) can occur naturally (e.g., module account's ERC20 balance transiently exhausted by concurrent conversions, contract owner pausing transfers, or the contract self-destructing) without any attacker action, making this a realistic, not merely theoretical, edge case — directly mirroring the HydraDX report's framing that the trigger is a normal/edge condition, not necessarily malicious.

### Recommendation
Wrap the two-step operation in `ConvertCoinNativeERC20` (escrow coin / unescrow ERC20) in a `ctx.CacheContext()` and only commit if both steps succeed, or reorder operations to escrow coins only after confirming the EVM transfer will succeed (or perform the EVM call first). Additionally, `ConvertCoinToERC20FromPacket` should propagate the real error instead of swallowing it (or, if the intent is to leave the user with bank coins on failure, it must guarantee no partial escrow occurred by using a cached context that is discarded on failure).

### Proof of Concept
Conceptual reproduction (would require a full IBC test harness, similar to the existing `TestOnAcknowledgementPacket` "self-destructed contract" test found in the repo):
1. Register a native ERC20 token pair (`OWNER_EXTERNAL`) and use it to send an IBC transfer that later times out or receives an error acknowledgement, invoking `ConvertCoinToERC20FromPacket`.
2. Before the timeout/ack is processed, cause the module's ERC20 `transfer` call to fail deterministically — e.g., drain `ModuleAddress`'s ERC20 balance via an unrelated legitimate `ConvertERC20` from another user, or pause the token contract if it supports pausability, so that step 2 (`CallEVM ... "transfer"`) reverts while step 1 (`SendCoinsFromAccountToModule`) has already executed.
3. Observe: the user's native coin balance is now in the `erc20` module account (verify via `BankKeeper.GetBalance(ctx, types.ModuleAddress-equivalent-account, denom)`), the sender received no ERC20 tokens, and `OnTimeoutPacket`/`OnAcknowledgementPacket` returned `nil` (transaction succeeded), so this state is permanently committed.

Note: I was not able to trace whether any other unrelated recovery path (e.g., a governance msg) exists to sweep stuck balances out of the `erc20` module account; if such a path exists it would reduce this to a privileged-recovery-only issue rather than truly permanent loss, but I found no such mechanism in the reachable, unprivileged code paths reviewed.

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
