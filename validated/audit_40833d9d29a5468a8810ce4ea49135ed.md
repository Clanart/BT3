Based on my investigation, I found a concrete, unprivileged, link-triggered path from `x-github-client://` deep links into a git operation where the value that reaches git is not fully sanitized. I could not fully confirm the exact argument-construction code in `app/src/lib/git/checkout.ts` (index does not surface its contents), so I flag that gap explicitly below.

### Title
Deep-link `branch` parameter reaches `git checkout` without blocking leading-dash values, enabling git argument injection - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/sanitize-ref-name.ts`, `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
GitHub Desktop registers custom protocol handlers (`x-github-client://`, `github-mac://`, etc.) and parses attacker-influenced URLs via `parseAppURL`. The `branch` query parameter is validated only against `testForInvalidChars`, a regex that filters git-ref-illegal characters but does not reject values beginning with `-`. That value is later passed straight into `Dispatcher.checkoutLocalBranch(repository, branchName)` after cloning/opening the repository, which is called from `openBranchNameFromUrl`.

### Finding Description
`parseAppURL` extracts `branch` from the deep link and only rejects it if `testForInvalidChars(branch)` matches: [1](#0-0) 

The regex used for that check comes from `sanitize-ref-name.ts` and blocks control characters, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing slash — but a leading `-` is not in the blocked set: [2](#0-1) 

This value flows unmodified into `Dispatcher.openBranchNameFromUrl`, which clones/opens the target repo and then calls `this.checkoutLocalBranch(repository, branchName)`: [3](#0-2) 

This is invoked from `dispatchURLAction`'s `open-repository-from-url` handler, which is the direct consumer of the parsed deep-link action: [4](#0-3) 

The broken invariant mirrors the seed report's pattern: a value that is supposed to be constrained/validated before being handed to a lower-level dispatch (there, a missing function; here, a missing character class in the allow/deny list) is not actually constrained, so attacker-controlled input reaches an unintended code path. Here the "unintended path" is that a string starting with `-` (e.g. `--upload-pack=...`, `-B`, or other git flags depending on how `checkoutLocalBranch` shells out to `git checkout`) could be interpreted by the underlying git invocation as an option rather than a ref name, if the implementation does not insert a `--` separator before the branch argument.

### Impact Explanation
If confirmed unmitigated at the `git checkout` call site, this would let a remote, unauthenticated party (anyone who can get a victim to click a `x-github-client://openRepo/...?branch=...` link, e.g. embedded in a webpage, README, or GitHub PR description) inject flags into the `git checkout` invocation Desktop performs automatically on the user's machine, silently altering what gets checked out/committed or potentially escalating to more dangerous git subcommands depending on the exact argv construction.

### Likelihood Explanation
The trigger requires only clicking a link — no local access, no credentials, and no prior compromise — satisfying the "unprivileged, link-triggered" criteria. However, exploitability depends entirely on whether `checkoutLocalBranch`'s underlying git call inserts a `--` separator or otherwise validates against leading dashes; I was unable to retrieve `app/src/lib/git/checkout.ts` contents through the index to confirm this, so I cannot assert the guard is definitively absent versus merely not visible to me.

### Recommendation
- In `sanitizedRefName`/`testForInvalidChars`, explicitly reject or strip ref names beginning with `-` before they are used as CLI arguments.
- Independently, ensure every git invocation that accepts a ref/branch/path derived from external input (deep links, PR objects, remote responses) inserts a `--` separator before the first positional argument, so a leading `-` can never be interpreted as a flag regardless of upstream validation gaps.

### Proof of Concept
1. Attacker crafts: `x-github-client://openRepo/https://github.com/attacker/repo?branch=--upload-pack=touch%20/tmp/pwned`
2. Victim clicks the link; `parseAppURL` accepts `branch` since it contains no character blocked by `invalidCharacterRegex`. [5](#0-4) 
3. `Dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` clones/opens the repo and calls `checkoutLocalBranch(repository, branchName)` with the unvalidated value. [3](#0-2) 
4. Whether this results in argument injection depends on the unverified internals of the git checkout wrapper — this is the piece I could not confirm from the available index.

**Note on confidence:** I could not load `app/src/lib/git/checkout.ts` to verify whether it uses a `--` separator (which would neutralize this issue). If it does, this finding reduces to a defense-in-depth gap in `sanitize-ref-name.ts` rather than an exploitable injection. I recommend a Devin session with full filesystem access to inspect `app/src/lib/git/checkout.ts` before treating this as confirmed exploitable.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
