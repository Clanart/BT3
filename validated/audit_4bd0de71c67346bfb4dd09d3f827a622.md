## Title
Fee-on-transfer reward token accounting mismatch in `BaseRewardPool.donateRewards()` permanently freezes user reward claims - (`File: rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool.donateRewards()` is an unprivileged, externally-callable function that lets any wallet top up rewards for a pool's stakers. It pulls `_amountReward` of `_rewardToken` via `safeTransferFrom` and then credits the *stated* `_amountReward` into `rewardPerTokenStored` accounting, without verifying the actual tokens received by the contract.

### Finding Description
`donateRewards()` calls `_provisionReward`, which transfers tokens using the caller-supplied `_amountReward` and immediately uses that same nominal value to update `rewardInfo.rewardPerTokenStored`: [1](#0-0) 

```solidity
function donateRewards(uint256 _amountReward, address _rewardToken) external {
    if (!isRewardToken[_rewardToken])
        revert MustBeRewardToken();

    _provisionReward(_amountReward, _rewardToken);
}
...
function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
    IERC20(_rewardToken).safeTransferFrom(
        msg.sender,
        address(this),
        _amountReward
    );
    Reward storage rewardInfo = rewards[_rewardToken];
    rewardInfo.historicalRewards =
        rewardInfo.historicalRewards +
        _amountReward;
    if (this.totalStaked() == 0) {
        rewardInfo.queuedRewards += _amountReward;
    } else {
        if (rewardInfo.queuedRewards > 0) {
            _amountReward += rewardInfo.queuedRewards;
            rewardInfo.queuedRewards = 0;
        }
        rewardInfo.rewardPerTokenStored =
            rewardInfo.rewardPerTokenStored +
            (_amountReward * 10**stakingDecimals()) /
            this.totalStaked();
    }
    emit RewardAdded(_amountReward, _rewardToken);
}
```

No balance-before/balance-after check is performed on the transfer. If `_rewardToken` has a transfer fee (or any deflationary/rebasing behavior), the pool's actual token balance increases by less than `_amountReward`, yet `rewardPerTokenStored` is incremented as if the full `_amountReward` was received. Any staker (`getReward`, in the same contract) is later entitled to a `earned()` amount computed off this inflated `rewardPerTokenStored`: [2](#0-1) 

`getReward` performs a plain `safeTransfer(_receiver, reward)` of the accrued amount with no availability check, so once the contract's real balance of that reward token is exhausted, subsequent claimants' `safeTransfer` calls revert, leaving their already-accrued, non-recoverable reward balance stuck in `userRewards` forever (the tokens simply are not there to pay them).

### Impact Explanation
This produces a genuine insolvency/accounting break in reward distribution: the pool promises stakers more of `_rewardToken` than it actually holds. Because `donateRewards` is unauthenticated (any wallet can call it for any already-registered reward token), and `isRewardToken` is a broad allow-list populated over the life of the pool (potentially including tokens whose transfer behavior could later be affected by fee/tax logic, rebasing, or blacklist-style burns), a portion of stakers will be permanently unable to claim their already-accrued yield once the shortfall manifests — a permanent freeze of unclaimed yield for the last claimants.

### Likelihood Explanation
The path is trivially reachable by any wallet — `donateRewards` has no access control beyond the reward token being on the `isRewardToken` list, and callers control `_amountReward` and pick the timing. The precondition (the reward token behaving as fee-on-transfer/deflationary at time of donation) is outside the contract's control and not validated anywhere in `BaseRewardPool`, so the contract offers no protection if such a token is ever used.

### Recommendation
In `_provisionReward`, measure the actual amount received rather than trusting the caller-supplied `_amountReward`:
```solidity
uint256 before = IERC20(_rewardToken).balanceOf(address(this));
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
uint256 received = IERC20(_rewardToken).balanceOf(address(this)) - before;
// use `received` for all subsequent accounting instead of `_amountReward`
```

### Proof of Concept
1. Assume `_rewardToken` charges a 5% transfer fee (or such a token is later added/behaves this way).
2. Any wallet calls `donateRewards(1000e18, rewardToken)`.
3. `_provisionReward` transfers in only 950e18 tokens (actual contract balance increase), but credits `rewardPerTokenStored` based on the full 1000e18.
4. Over time, cumulative `rewardPerTokenStored` credits exceed the contract's real token balance by the aggregate fee amount.
5. Stakers who call `getReward` early receive their full share; stakers who claim later find `safeTransfer` reverting because the contract balance is insufficient, permanently losing access to their accrued (but unbacked) reward balance recorded in `userRewards`.
