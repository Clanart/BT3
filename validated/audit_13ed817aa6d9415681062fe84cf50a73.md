### Title
Data Layer mirror URLs are fetched via unauthenticated outbound HTTP requests without host/scheme validation, enabling SSRF - ([File: chia/data_layer/download_data.py])

### Summary
`DataLayer.add_mirror()` lets any store owner publish arbitrary URLs on-chain as a mirror for their store, with the only validation being that the URL list is non-empty. Any Data Layer node that subscribes to that store will later fetch data from those exact URLs via `http_download()` using `aiohttp` with no scheme allow-list, no host/IP filtering, and no protection against private/loopback/link-local addresses. This mirrors CVE-2020-25787's root cause in tt-rss: user-supplied URLs are requested by the server without validating that they are safe/expected destinations, enabling SSRF.

### Finding Description
`DataLayer.add_mirror()` only checks that the URL list isn't empty before publishing the URLs on-chain via `dl_new_mirror`: [1](#0-0) 

`update_subscriptions_from_wallet()` reads these mirror URLs straight from wallet/chain state with no filtering beyond trailing-slash stripping, and stores them for later use by any subscribing node: [2](#0-1) 

During `fetch_and_validate()`, the local Data Layer service randomly picks one of these attacker-controlled server URLs and initiates a download from it: [3](#0-2) 

The request itself is issued from `http_download()`, which performs a bare `aiohttp` GET to `server_info.url + "/" + filename` with no scheme restriction (e.g. `file://`, `ftp://` are not blocked by `aiohttp` itself but arbitrary `http(s)://` hosts including internal/loopback/link-local IPs are fully permitted) and no allow-list of destinations: [4](#0-3) 

The `.cursor/context/data-layer.md` notes explicitly flag mirror URLs as an "external trust input," but only mention that *downloaded data content* is verified against the wallet-advertised root — not that the destination itself is validated before the request is sent: [5](#0-4) 

Tests demonstrate that arbitrary loopback-style URLs (`http://127.0.0.1/8000`) are accepted and stored as mirror URLs without rejection, confirming the lack of validation: [6](#0-5) 

### Impact Explanation
Any wallet user can add a mirror with a URL pointing at an internal service (e.g. localhost admin ports, cloud metadata endpoints, internal RPC/HTTP services on the machine or LAN running the subscribing Data Layer node) and publish it on-chain via a normal `add_mirror`/`dl_new_mirror` spend. Any other Data Layer node that subscribes to that store — a routine, low-privilege action any DL participant can take — will then have its Data Layer service issue outbound HTTP GET requests to that attacker-chosen destination. This is a server-side request forgery: it can be used to probe/interact with internal network services, hit cloud metadata endpoints, or trigger requests against arbitrary hosts from the node operator's network position, all without any interaction other than subscribing to a malicious store.

### Likelihood Explanation
The path is trivially reachable: publishing a mirror only requires a normal wallet transaction (`add_mirror`), and subscribing to a store is a standard Data Layer client action exposed via RPC. No special privileges, malicious peer behavior, or network-layer position is required — only that a victim node subscribes to an attacker's DataLayer store, which is the store's/mirror's entire intended purpose (replication discovery).

### Recommendation
Validate mirror URLs before persisting/publishing them and again before dereferencing them in `http_download()`/`get_downloader()`: enforce an `http`/`https` scheme allow-list, resolve and reject requests to private, loopback, link-local, and multicast address ranges (and re-check after DNS resolution/redirects), and consider requiring an explicit opt-in/allow-list for mirror hosts. Apply the same checks to the plugin `downloader.url` posts (`get_downloader()`), and consider disabling automatic following of redirects to untrusted destinations.

### Proof of Concept
1. Attacker creates a Data Layer store and calls `add_mirror` with `urls=["http://169.254.169.254/latest/meta-data/"]` (or `http://127.0.0.1:<internal-port>/...`), paying the on-chain fee — accepted as shown by the test at `chia/_tests/core/data_layer/test_data_rpc.py:2782-2791` where `http://127.0.0.1/8000` is accepted without error.
2. Victim operator's Data Layer node subscribes to the attacker's store id (`subscribe` RPC).
3. On the next sync cycle, `update_subscriptions_from_wallet()` pulls this URL into the subscription's server list, and `fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()` issues a GET request from the victim's node to the attacker-controlled/internal URL, as traced in `chia/data_layer/data_layer.py:642-666` and `chia/data_layer/download_data.py:298-324`.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
