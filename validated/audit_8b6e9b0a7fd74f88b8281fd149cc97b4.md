### Title
Permissionless `donateRewards` + zero-totalStaked reward carry-over lets a 1-wei staker capture 100% of pool-wide queued rewards - ([File: rewards/BaseRewardPool.sol])

### Summary
When `totalStaked()==0`, `_provisionReward` stores the entire incoming reward into `rewardInfo.queuedRewards` without updating `rewardPerTokenStored` [1](#0-0) . Because `donateRewards` is callable by anyone with no manager restriction (only an `isRewardToken` check), an attacker who is the sole/first staker after the pool goes empty can permissionlessly trigger the fold-in of `queuedRewards` into `rewardPerTokenStored` while `totalStaked()` is a negligible 1 wei, causing the entire accumulated queued reward to be attributed to their tiny stake alone.

### Finding Description
`_provisionReward` behaves as follows: [2](#0-1) 
- If `totalStaked()==0`, the whole `_amountReward` is added to `queuedRewards` and `rewardPerTokenStored` is left untouched.
- Otherwise, any pending `queuedRewards` is folded into the current `_amountReward` and `rewardPerTokenStored` is incremented by `_amountReward * 10**decimals / totalStaked()`.

Critically, `donateRewards` — which calls `_provisionReward` — has no access control beyond `isRewardToken[_rewardToken]`: [3](#0-2) . This means any unprivileged address can invoke it, including with `_amountReward == 0` (a `safeTransferFrom` of 0 succeeds on standard ERC20s).

Exploit flow:
1. All existing stakers withdraw, so `totalStaked() == 0` (their prior earned rewards were already finalized via `_updateFor` at withdrawal time, so this is a clean state with no residual per-user claim on prior reward flows).
2. `manager.queueNewRewards(amount, token)` runs while `totalStaked()==0`, so the full `amount` is added to `rewardInfo.queuedRewards` and `rewardPerTokenStored` stays unchanged [4](#0-3) .
3. Attacker deposits a negligible amount (e.g., 1 wei) via the staking flow, becoming effectively the sole entry in `totalStaked()`.
4. Attacker calls the permissionless `donateRewards(0, token)`. Since `totalStaked() != 0` now, `_provisionReward` folds all of `queuedRewards` into `rewardPerTokenStored`, dividing by the attacker-dominated `totalStaked()` (≈1 wei), producing an enormous `rewardPerTokenStored` increment [5](#0-4) .
5. Attacker calls `getReward(attacker, attacker)`, and `earned()` computes nearly the entire queued reward attributable to the attacker's 1-wei balance [6](#0-5) [7](#0-6) .

Note: the literal call sequence in the question (`deposit` -> `getReward` with no intervening reward-provisioning call) does **not** trigger the bug, since `rewardPerTokenStored` is only updated inside `_provisionReward`. The missing but trivially reachable step is the unprivileged `donateRewards` call, which requires no special role and can be executed with a zero or minimal donation amount purely to trigger the reward-per-token recalculation while `totalStaked()` is attacker-dominated.

Any future depositor who stakes normal amounts after this point receives `userRewardPerTokenPaid` set to the already-inflated `rewardPerTokenStored`, so they get none of that queued reward despite being the intended long-term recipients of it.

### Impact Explanation
This results in a permissionless capture of the entire pool-wide queued reward balance by a single, effectively capital-free (1 wei) attacker, at the expense of future legitimate depositors who would otherwise have shared in that reward proportionally as the pool refills. This is a direct theft of yield that belongs to the pool as a whole (Impact class: theft of unclaimed yield / direct theft of user funds).

### Likelihood Explanation
Feasibility is high and repeatable: it requires (a) a pool reaching `totalStaked()==0` (achievable any time all depositors happen to fully withdraw, or can be induced by an attacker who is briefly the only staker and withdraws first), (b) a reward provisioning event while empty, and (c) the attacker being first to re-stake and calling the fully permissionless `donateRewards`. No privileged role, flash loan, or governance action is needed — only ordinary stake/withdraw/donate/getReward calls available to any EOA. Capital required is negligible (1 wei stake + 0 or minimal donation amount).

### Recommendation
Do not allow `rewardPerTokenStored` to be updated (i.e., queued rewards folded in) when `totalStaked()` is at or near zero/dust levels, or require a minimum meaningful `totalStaked()` threshold before folding queued rewards. Alternatively, restrict `donateRewards` to trusted roles, or snapshot/distribute queued rewards pro-rata based on stake duration rather than instantaneous balance at the moment of the fold. A more robust fix is to track queued rewards separately and distribute them over time (e.g., via a reward-rate/duration mechanism) rather than an instantaneous divide-by-current-totalStaked operation.

### Proof of Concept
Foundry test plan:
1. Deploy `BaseRewardPool` with a reward token and mock `MasterMagpie`/staking token; register a manager.
2. Have userA stake, then withdraw fully so `totalStaked()==0`.
3. As `manager`, call `queueNewRewards(1000e18, rewardToken)`; assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
4. As `attacker`, stake 1 wei of staking token (via MasterMagpie mock so `balanceOf(attacker)==1`).
5. As `attacker`, call `donateRewards(0, rewardToken)` (no special role needed, only `isRewardToken` must be true).
6. Assert `rewards[rewardToken].queuedRewards == 0` and `rewardPerTokenStored` jumped to reflect ~1000e18 distributed over `totalStaked()==1`.
7. As `attacker`, call `getReward(attacker, attacker)` and assert the attacker receives ~1000e18 reward tokens despite staking only 1 wei.
8. Have a normal userB then stake a large amount and confirm `earned(userB, rewardToken) == 0` for that already-distributed reward batch, proving the queued reward was fully diverted away from the pool's intended future beneficiaries.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
