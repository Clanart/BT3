### Title
`clone()` explicitly disables Git's built-in hook-execution protection via `GIT_CLONE_PROTECTION_ACTIVE=false` - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to the literal string `'false'` on every clone Desktop performs [1](#0-0) . This variable is Git's own internal guard (added to fix the 2024 hook-execution CVEs in `clone`/`--recurse-submodules`) that tells `hook.c` to refuse to execute any repository-supplied hook while a clone is still in progress. By unconditionally forcing this guard to `false`, Desktop re-opens the exact hook-execution path that upstream Git closed, for every single `git clone --recursive` invocation it performs.

### Finding Description
The broken invariant mirrors the report's pattern exactly: a security check exists (`GuardCM` blocking arbitrary calls / Git's clone-protection guard blocking hook execution mid-clone), but there is one code path that the guard's own author explicitly disables, and that path is fully attacker-reachable.

- Git's clone protection ("hidden .git" / symlink-hook attacks, CVE-2024-32004 family) exists because a maliciously crafted repository can embed a nested `.git` directory, a symlinked hooks directory, or `.gitmodules` content that — if a hook were allowed to run during the initial checkout/clone/submodule-recurse phase — would execute attacker-controlled code before Desktop or the user has ever inspected the content.
- Git's fix is to set `GIT_CLONE_PROTECTION_ACTIVE=true` for the duration of the clone so that `hook.c` short-circuits and refuses to run *any* hook (regardless of `core.hooksPath`, nested `.git`, or submodule tricks) until the clone has fully and safely completed.
- Desktop's `clone()` explicitly overrides this to `'false'`: [2](#0-1) 
- The clone is additionally run with `--recursive` (auto-recursing into submodules) [3](#0-2) , which is precisely the amplifying factor in the original CVEs: submodule URLs/paths under attacker control are processed during the same clone operation whose hook protection has just been turned off.
- Desktop's own hook-sandboxing mechanism (`withHooksEnv`/`interceptHooks`) is not applied to `clone()` at all — `clone()`'s `IGitStringExecutionOptions` never sets `interceptHooks` [4](#0-3) , unlike `pull()` which does intercept the hooks that can run during a pull [5](#0-4) . So there is no secondary guard (proxy/sandbox) to fall back on for clone — the only protection is Git's own `GIT_CLONE_PROTECTION_ACTIVE` check, and Desktop turns that off itself.

This is functionally identical to the `GuardCM` bug: the developer added a targeted bypass (`operation == delegatecall` skipped only when `to == owner`) that neuters the check for the one case that matters most; here, Desktop adds a bypass (`GIT_CLONE_PROTECTION_ACTIVE=false`) that neuters Git's own check for the one operation (clone with recursive submodules) where a fully untrusted, attacker-authored repository is being processed for the very first time.

### Impact Explanation
If the embedded Git version still honors `GIT_CLONE_PROTECTION_ACTIVE` (i.e., protection is opt-in rather than default-on, or default-on but overridable), then cloning any attacker-controlled repository or repository URL (including "Open in Desktop" deep links and PR-fork checkouts that call the same clone/fetch paths) can result in native code execution on the victim's machine as soon as the clone/recursive-submodule step runs — before the user ever opens or reviews the repository. This satisfies the report's class of "attacker controls a cloned/fetched repository ... result is code execution" and is high severity because it requires no unusual user action beyond the normal, expected "Clone repository" or "Open in Desktop" flow.

### Likelihood Explanation
Likelihood depends on the exact semantics of `GIT_CLONE_PROTECTION_ACTIVE` in the bundled Git/dugite version (whether the variable is default-on and this override disables it, or whether Git already treats an explicit `false` the same as unset). This needs to be verified against the specific embedded Git version, but the code intent is unambiguous: this line exists solely to force the variable to `'false'`, which only makes sense as a deliberate opt-out of the protection. Every `clone()` call goes through this same code path (initial clones, "Open in Desktop", clone-from-URL flows), and `--recursive` is always appended, so the exposure surface is the entirety of Desktop's clone functionality.

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or set it to `'true'`) so Git's built-in clone-time hook protection remains active. [1](#0-0) 
- If the override was added to work around a compatibility issue, gate it behind the specific narrow case that required it rather than disabling the protection for all clones.
- Consider applying the same `interceptHooks`/sandbox mechanism used by `pull()`/`push()`/`merge()`/`commit()` to `clone()` as defense-in-depth, since clone is the highest-risk operation (100% untrusted content, first contact with attacker-supplied repository data).

### Proof of Concept
Because reproducing the underlying Git hook-execution CVE requires a specific vulnerable/patched embedded Git version and a crafted repository (nested `.git`/symlinked hooks or `.gitmodules` payload), a full working exploit could not be constructed from static analysis alone. The concrete, verifiable finding is the source-level fact that Desktop unconditionally sets:
```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```
for every `clone(url, path, options)` call [1](#0-0) , combined with the use of `--recursive` [3](#0-2)  and the absence of `interceptHooks` for this operation. A Devin/engineering follow-up should: (1) confirm the exact behavior of `GIT_CLONE_PROTECTION_ACTIVE` in the bundled dugite/Git version, and (2) build a test repository containing a nested `.git`/hook or malicious `.gitmodules` entry to confirm hook execution occurs when cloned through Desktop's `clone()` versus a stock `git clone --recursive` without the override.
