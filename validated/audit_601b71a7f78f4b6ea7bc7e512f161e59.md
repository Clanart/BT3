This confirms the vulnerability path is real. `pallet-ismp`'s `handle_unsigned`/dispatch infrastructure and the docs example (`docs/content/developers/polkadot/dispatching.mdx`) show that **any signed account on Hyperbridge can call a `send_message`-style extrinsic through `pallet_ismp::Pallet::dispatch_request`, freely choosing `from` (the source module id) and `to` (destination contract)** — the dispatcher does not restrict `from` to a specific pallet id. That `PostRequest` is committed with `source = self.host_state_machine()` (i.e., "Hyperbridge"), which is exactly the value `BandwidthManager::onAccept` checks.

### Title
Missing sender-module authentication in `BandwidthManager.onAccept` allows unprivileged draining of escrowed fee tokens - (File: evm/src/apps/BandwidthManager.sol)

### Summary
### Finding Description
`BandwidthManager.onAccept` (evm/src/apps/BandwidthManager.sol:201-225) only checks `request.source.equals(hyperbridge)` before trusting the message body for `Withdraw`/`SetTiers` governance actions. It never checks `request.from` against `PALLET_BANDWIDTH_MODULE_ID` ("BWMARKET"), unlike other governance-receiving apps in the same codebase (e.g. HyperFungibleToken, per `docs/content/developers/evm/hyper-fungible-token/overview.mdx:113-122`, which explicitly checks `request.from == expectedSource`). Since `pallet-ismp`'s generic dispatch path (`modules/pallets/ismp/src/dispatcher.rs:128-146`, exposed to any signed account via a `send_message`-style extrinsic as documented in `docs/content/developers/polkadot/dispatching.mdx:57-77`) lets **any caller choose an arbitrary `from` module id** while `source` is always forced to the host state machine ("Hyperbridge"), an unprivileged Hyperbridge account can craft a `DispatchPost{ from: <anything>, to: <BandwidthManager address>, body: Withdraw{token, beneficiary, amount} }` and have it delivered by any relayer. [1](#0-0) [2](#0-1) 

### Impact Explanation
Once delivered and relayed, `onAccept` decodes `OnAcceptActions.Withdraw` and unconditionally transfers `w.amount` of `w.token` (or native ETH) from the contract's balance to `w.beneficiary` — an attacker-controlled address: [3](#0-2) 

This drains all fee-token proceeds accrued from bandwidth purchases (and any native balance) to an address the attacker controls — direct theft of protocol/user funds, satisfying "stealing or loss of funds" and "cross-chain admin effects reachable through … wrong module bindings." No admin, relayer collusion, or forged consensus proof is required beyond the standard (permissionless) relaying of a validly-proven Hyperbridge-origin message — the message's proof is legitimate because it genuinely originates from Hyperbridge; the flaw is that the app never checks *which module* on Hyperbridge sent it.

### Likelihood Explanation
High. It only requires an unprivileged Hyperbridge account able to pay the ISMP dispatch fee (documented as a normal, signed, permissionless extrinsic) plus a relayer to deliver the message — relayers are permissionless and profit-motivated, not "malicious" in the excluded sense. This matches the report's core broken invariant (a privileged-looking cross-chain action executable by an unintended actor) but manifests here as a missing authentication check reachable by any user, not an admin decision.

### Recommendation
Add a `request.from == PALLET_BANDWIDTH_MODULE_ID` (or equivalent module-id) check in `BandwidthManager.onAccept`, mirroring the `HostManager`/`HyperFungibleToken` pattern, before acting on `SetTiers`/`Withdraw` payloads.

### Proof of Concept
1. Attacker (any funded Hyperbridge account) calls a generic ISMP dispatch extrinsic (as in `docs/content/developers/polkadot/dispatching.mdx:57-77`) with `DispatchPost{ dest: <BandwidthManager's chain>, from: b"ANYTHING", to: <BandwidthManagerAddress>, body: abi.encode(uint8(1) /*Withdraw*/, Withdrawal{ token: feeToken, beneficiary: attacker, amount: fullBalance }) }`.
2. `pallet_ismp::dispatch_request` commits this as a `PostRequest` with `source = Hyperbridge` (unconditionally, per `dispatcher.rs:130`), regardless of the caller's identity or the chosen `from`.
3. Any relayer delivers the message and its (legitimate) proof to the destination `EvmHost`; the host invokes `BandwidthManager.onAccept`.
4. `onAccept` checks only `request.source.equals(hyperbridge)` (true) and never checks `request.from`, so it executes the forged `Withdraw` action, transferring the contract's entire fee-token balance to the attacker. [4](#0-3)
