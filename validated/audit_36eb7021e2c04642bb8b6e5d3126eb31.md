The `IntentGatewayV2.sol` deployed for Tron still contains the exact checks-effects-interactions violation that the main EVM `IntentGatewayV2`/`IntentsBase.sol` code was explicitly patched for (see the dedicated `IntrinsicIntentsReentrancyTest.sol` regression suite documenting that fix). The Tron variant's `withdraw()` was never given the same fix.

### Title
Unchecked ERC20 transfer + effects-after-interactions in `withdraw()` permanently deletes escrow accounting on failed/reentrant transfers - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` releases escrowed order inputs to a beneficiary by making a raw low-level external call to the token contract, and only decrements the escrow accounting mapping `_orders[body.commitment][token]` **after** that call returns [1](#0-0) . This is precisely the "external call before effects" pattern flagged in H-4, but the main EVM app code (`IntentsBase.sol`) was already patched to decrement state **before** transferring [2](#0-1)  — the Tron copy of the contract was left with the vulnerable ordering.

### Finding Description
In `withdraw()`:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

Two compounding defects:
1. **Effects-after-interactions**: the escrow debit happens after the external call, not before, reopening the exact ordering bug the report describes (state change deferred past the point where control is relinquished to attacker-influenced code — here the token contract itself, since `order.inputs[i].token` is fully chosen by whoever placed the order).
2. **Unchecked return value**: `token.call(...)` only verifies that the low-level call did not revert (`success`), it never decodes/verifies the ABI-encoded boolean that `IERC20.transfer` returns. A non-reverting ERC20 that returns `false` on failure (a legitimate, spec-compliant pattern many tokens use) is treated identically to a successful transfer: `success == true` even though no tokens moved. Execution then proceeds to `_orders[body.commitment][token] -= amount`, permanently erasing the escrow record for tokens that were never actually delivered.

This mirrors H-4's core broken invariant exactly: "transfer silently fails → state is nonetheless mutated to reflect success → the value becomes permanently unrecoverable," except here it's ERC20 escrow instead of an NFT lock. The identical `_filled[commitment] = beneficiary` CEI-safe pattern was retrofitted for the reentrancy guard on order state [4](#0-3) , but the per-token escrow debit inside the very same function was not given the same treatment, and the return-value check on `transfer` was never added at all (compare with the same file's `SweepDust` handler which has the identical unchecked-`.call()` pattern [5](#0-4) ).

`onGetResponse` in the same file reaches the identical vulnerable `withdraw()` on the refund path [6](#0-5) .

### Impact Explanation
Any order that escrows a token whose `transfer()` can return `false` without reverting (a common, standards-compliant behavior, e.g. tokens implementing checks that intentionally fail-soft) will have its escrow accounting zeroed out by `withdraw()` even though the beneficiary received nothing. The escrowed tokens remain trapped in the `IntentGatewayV2` contract with no code path left to reclaim them, since `_orders[commitment][token]` — the only bookkeeping for that escrow — has already been decremented and `_filled[commitment]` is already set, blocking `cancelOrder`. This is a direct, unrecoverable loss of user funds, matching the Hyperbridge bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
No privileged actor, relayer collusion, or malicious node is required — the order creator picks `order.inputs[i].token` when placing the order, and standard non-reverting-failure ERC20 semantics are common enough (and can also be deliberately engineered by an attacker deploying a custom token for their own order) that this triggers under ordinary operation, not just adversarial conditions.

### Recommendation
- Use `SafeERC20.safeTransfer` (already used correctly in `IntentsBase.sol` [7](#0-6) ) instead of the raw `.call` + selector pattern, so that both revert and false-return failures propagate as reverts.
- Apply checks-effects-interactions: decrement `_orders[body.commitment][token]` before making the external transfer call, exactly as done in `IntentsBase._withdraw()`.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` returns `false` (no revert) whenever called from `IntentGatewayV2` for amounts above some threshold, or unconditionally.
2. Attacker calls `placeOrder` with `order.inputs[0].token = EvilToken`, escrowing `amount` of `EvilToken` into the contract.
3. A solver fills the cross-chain order on the destination chain; the `RedeemEscrow` message is relayed back and delivered via `onAccept` → `withdraw(body, false)`.
4. Inside `withdraw`, `EvilToken.call(transfer.selector, beneficiary, amount)` returns `(true, abi.encode(false))`; `success` is `true` so no revert occurs.
5. `_orders[body.commitment][EvilToken] -= amount` executes, zeroing the escrow record even though `beneficiary` received zero tokens.
6. The `amount` of `EvilToken` is now permanently stuck in `IntentGatewayV2` with no remaining code path to withdraw it (`_filled` is set, `cancelOrder` reverts with `Filled()`).
