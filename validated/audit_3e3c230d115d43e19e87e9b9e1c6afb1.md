### Title
Tokenfactory denom admin can permanently freeze all holders' funds by setting a hostile `AllowList` via `MsgUpdateDenom` - (File: x/tokenfactory/keeper/msg_server.go)

### Summary
A tokenfactory denom's admin can call `MsgUpdateDenom` at any time to set an `AllowList` that excludes every existing holder of that denom (other than the admin itself). Because `IsInDenomAllowList` is enforced on both the sender and receiver side of every `Send`/`MultiSend` for that denom, this instantly and permanently blocks transfers for all non-admin holders, with no burn-to-unlock, timelock, or any other on-chain escape mechanism available to affected users — unlike the referenced Basket auction bug, which at least offered `bondBurn` as a costly recovery path.

### Finding Description
`MsgUpdateDenom` is handled by `server.msgServer.UpdateDenom` in `x/tokenfactory/keeper/msg_server.go`. After confirming the sender is the denom's admin, it directly forwards the caller-supplied `AllowList` to `server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)` with no validation that existing holders remain included in the list (unlike `CreateDenom`, `UpdateDenom` does not even call `validateAllowList`). [1](#0-0) 

Once set, every subsequent `Send` and `MultiSend` for that denom is checked against the allow list via `IsInDenomAllowList`/`getAllowedAddresses`: if the list is non-empty and the sender or recipient address is absent from it, the transfer is rejected with `ErrUnauthorized`. [2](#0-1) [3](#0-2) 

Because this check applies retroactively to balances the admin never controls, the admin can lock in place all coins already held by third parties simply by publishing a list containing only its own address (or any address set that excludes existing holders). There is no analog of the Basket's `Auction.bondBurn` recovery path in this module — the tokenfactory `AllowList` mechanism provides no way for a non-admin holder to force removal from a hostile allow list. The only route back to solvency is the admin voluntarily calling `MsgUpdateDenom` again (or `MsgChangeAdmin` to a cooperative party), i.e., trust in the very party that caused the freeze.

### Impact Explanation
Any tokenfactory denom with non-trivial circulating balances held by third parties (e.g., wrapped/synthetic assets, staking derivative shares, or any application-issued token using tokenfactory) is at risk of the admin unilaterally and instantly freezing all non-admin balances with no on-chain recourse. This is a permanent freezing-of-funds class issue reachable by any account holding tokenfactory admin rights over a denom, matching the report's "abuse of privileged role" pattern but with a strictly worse outcome for victims since sei-chain's tokenfactory offers no bond-burn/timelock/self-help unlock equivalent.

### Likelihood Explanation
Exploitation requires only that the denom's admin be malicious or compromised and send a single `MsgUpdateDenom` transaction — no timelock, governance, or multi-step process gates this action, and the change takes effect immediately in the same block. Given tokenfactory's permissionless denom creation model, any user issuing a tokenfactory-based token and then distributing it can later grief holders this way, or an initially-trustworthy admin key could be compromised and misused for the same effect.

### Recommendation
- Require that `MsgUpdateDenom`'s new `AllowList` be validated (mirroring `validateAllowList` used in `CreateDenom`) and, ideally, warn/require inclusion of any address currently holding a non-zero balance of the denom, or restrict allow-list tightening to addresses that opt in.
- Consider adding a timelock or grace period before a newly set (more restrictive) `AllowList` takes effect, giving holders a window to exit positions, analogous to community mitigations suggested for the Basket auction issue.
- Provide an explicit, permissionless "unlock" mechanism for holders excluded from an allow list (e.g., ability to at least withdraw/burn their own balance regardless of allow-list membership), removing sole reliance on admin goodwill.

### Proof of Concept
1. Account `A` creates a tokenfactory denom `factory/A/test` via `MsgCreateDenom` with no allow list, becoming its admin.
2. Users `B`, `C`, ... acquire balances of `factory/A/test` through normal transfers (`MsgSend`/`MsgMultiSend`), which succeed because `IsInDenomAllowList` returns `true` when no allow list is set.
3. Admin `A` submits `MsgUpdateDenom{Sender: A, Denom: "factory/A/test", AllowList: {Addresses: [A]}}`. This passes the `msg.Sender != authorityMetadata.GetAdmin()` check and calls `bankKeeper.SetDenomAllowList` with the new restrictive list — no validation is performed against existing holders.
4. Any subsequent `MsgSend` by `B` or `C` (as sender or receiver) of `factory/A/test` now fails `IsInDenomAllowList` and returns `"... is not allowed to send/receive funds"`, permanently freezing their balances with no on-chain recovery path other than admin `A` reversing the change.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
