### Title
Unrestricted `updateEndRemainingAllocation()` allows re-snapshotting the bonus denominator after other users claim, letting an attacker inflate their own bonus share and break conservation - (File: `rewards/Airdrop.sol`)

### Summary
`updateEndRemainingAllocation()` is `public`, has no re-entry/one-time guard, and unconditionally overwrites `totalEndRemainingAllocation = totalRemainingAllocation` whenever `block.timestamp >= periodsEndTime[4]`. Because `totalRemainingAllocation` shrinks with every `claim()` (regardless of period), any eligible claimant can wait for others to claim first, then call `updateEndRemainingAllocation()` again to shrink the bonus denominator before calling `claim()`, inflating `getBonusAmount()` for themselves at the expense of `totalBonus` conservation.

### Finding Description
`getBonusAmount()` computes a pro-rata share of `totalBonus`: [1](#0-0) 

The denominator `totalEndRemainingAllocation` is meant to be a **single, fixed snapshot** taken the first time someone claims after period 4 starts (`claim()` only auto-triggers the update `if (totalEndRemainingAllocation == 0)`): [2](#0-1) 

However, `updateEndRemainingAllocation()` itself has no such guard - it can be called directly by anyone at any time after `periodsEndTime[4]`, and it will overwrite the snapshot again: [3](#0-2) 

Because every `claim()` unconditionally subtracts the claimer's full `userAllocation` from `totalRemainingAllocation` (line 164), each prior claim shrinks the pool that a *later* direct call to `updateEndRemainingAllocation()` will re-snapshot into `totalEndRemainingAllocation` — even though those prior claimers already received their bonus computed against the *original*, larger denominator. An attacker who waits for other users to claim first, then calls `updateEndRemainingAllocation()` again before their own `claim()`, locks in an artificially small denominator relative to the fixed `totalBonus` numerator, over-computing their own bonus share.

Concretely, with users A, B, C each holding allocation 100 and `totalBonus = 30`:
- A claims first → auto-sets `totalEndRemainingAllocation = 300` → bonus = 10 (correct pro-rata).
- B claims → bonus = 10 (denominator still 300).
- Attacker C calls `updateEndRemainingAllocation()` directly → resets `totalEndRemainingAllocation = totalRemainingAllocation = 100` (since A and B's 200 was already subtracted) → C claims → bonus = `100*30/100 = 30`.

Total bonus paid out = 10+10+30 = 50, exceeding the `totalBonus` pool of 30 — a direct conservation violation. No modifier, `nonReentrant` guard, or one-time-set flag prevents this; `updateEndRemainingAllocation()` is callable by any unprivileged address with no state check beyond the timestamp.

### Impact Explanation
This is a direct theft-of-funds vulnerability: an attacker who is merely an eligible allocatee (no privileged role required) can extract more than their fair share of the bonus pool, which is funded from other allocatees' forfeited allocations. The over-payment either comes out of tokens meant for later claimants (causing later legitimate claimants to receive less or nothing, i.e. `InsufficientBalance` reverts / stuck claims) or drains balance intended for `withdrawDust()`. This matches "direct theft of user funds" / "protocol insolvency" impact classes.

### Likelihood Explanation
- Requires no special privileges — any address with `allocations[msg.sender] > 0` can execute it.
- Requires no capital beyond gas — `updateEndRemainingAllocation()` and `claim()` are both public/external with no fee or stake requirement.
- Fully repeatable each time the airdrop reaches period 4 and multiple allocatees exist; attacker simply needs to observe on-chain state (other claims already mined) and time their own two transactions accordingly — no flash loan or reentrancy needed, only transaction ordering, which is trivially achievable via a normal transaction or front-running.

### Recommendation
Add a one-time-set guard to `updateEndRemainingAllocation()` (e.g., `if (totalEndRemainingAllocation != 0) return;` or restrict it to only ever set once, mirroring the intent already expressed in `claim()`), or remove public callability entirely and only allow the internal auto-snapshot inside `claim()`'s first invocation after period 4.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, register allocations for users A, B, C (100 each) and D/E who claim early in periods 0–3 to generate `totalBonus` (e.g., forfeiting 30 tokens total).
2. Warp to `periodsEndTime[4]`.
3. Have A call `claim()` (auto-sets `totalEndRemainingAllocation = totalRemainingAllocation`), record bonus paid.
4. Have B call `claim()`, record bonus paid.
5. As attacker C, call `updateEndRemainingAllocation()` directly (re-snapshotting to the now-reduced `totalRemainingAllocation`), then call `claim()`, record bonus paid.
6. Assert `sum(bonus_A + bonus_B + bonus_C) > totalBonus` (the value before any claims), proving conservation is broken.
7. Assert that remaining users' `getClaimableAmount()` plus already-paid amounts can exceed `aidropToken.balanceOf(address(this))` at some point, causing legitimate later claimants to revert with `InsufficientBalance`.

    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
