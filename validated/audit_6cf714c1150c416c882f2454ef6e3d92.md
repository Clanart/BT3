## Finding

### Title
Stale, index-based partial-commit line selection can be silently re-applied to a changed diff, causing Desktop to commit different content than what the user reviewed - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The bug class in the C4 report is: derived/cached state (`ts.tokens`) is carried forward across a state transition without being recalculated relative to the *current* underlying data, so a later operation (withdraw) silently computes an incorrect result using stale state. The Desktop analog is structurally identical: a user's partial line selection for a file is represented as a set of **line indices** (`DiffSelection`), and that index-based selection is preserved across diff/status refreshes without verifying that the same indices still refer to the same content. When the working tree changes between the time the diff was displayed/selected and the time the commit patch is actually generated, the stale index-based selection is silently re-applied to different content.

### Finding Description
`DiffSelection` tracks selected lines purely by numeric index, not by content identity: [1](#0-0) 

When the working directory status is refreshed, `updateChangedFiles` preserves the previously selected file's `selection` object as-is and only decides whether to keep the cached `diff` based on whether the *same file id* is still singly selected — it does not compare diff content: [2](#0-1) 

In `updateChangesWorkingDirectoryDiff`, when a new diff is loaded, the code explicitly acknowledges that the diff "might have changed dramatically" since it was last loaded, and instead of invalidating/renormalizing the user's selection against actual line content, it simply recomputes which *indices* are selectable and keeps whichever indices the user had already toggled: [3](#0-2) 

At commit time, `_commitIncludedChanges` takes the files (and their index-based `selection`) straight from `changesState.workingDirectory.files` and passes them to `createCommit`: [4](#0-3) 

The actual patch used for partial commits is built by `formatPatch`, which decides what to keep purely via `file.selection.isSelected(absoluteIndex)` against whatever diff/hunks are supplied at that moment — there is no check that this diff is the same diff the user visually reviewed when making their selection: [5](#0-4) 

This is the exact shape of the Locke.sol flaw: a piece of state (`ts.tokens` / the user's line selection) is retained across an update event (`stake()` / working-directory refresh) without being recomputed relative to fresh underlying data, and a later operation (`withdraw()` / commit) uses the stale state combined with newly fetched data (`ts.lastUpdate` / a newly loaded diff) to produce an incorrect result — extra tokens withdrawn / different lines committed than the user intended.

### Impact Explanation
If the tracked file's on-disk content changes between the moment a user checks/unchecks specific lines in the Changes view and the moment Desktop actually stages/commits (e.g. because a build tool, formatter, git hook, filter driver, or a background process controlled by content in an attacker-supplied/cloned/fetched repository rewrites the file, or because Desktop's own background status refresh races with the diff load), the previously selected line indices no longer correspond to the same lines. The resulting commit can silently include or exclude different content than what the user reviewed and approved — "silent corruption of what the user commits," which is explicitly in scope. Because Desktop shows no warning (the code comment even states it doesn't validate line identity), the user has no indication their commit no longer matches their intended selection.

### Likelihood Explanation
This requires only that a repository under active use (cloned/fetched, or containing a hook/filter/build step common to legitimate workflows) modify a tracked file while Desktop's Changes view has stale selection state cached — a realistic race given Desktop's asynchronous status → diff → selection pipeline, and one the code's own comment acknowledges as a known gap ("The diff might have changed dramatically since last we loaded it..."). No elevated privileges, local access, or unnatural user steps are required beyond normal use of Desktop with a repository whose content can change between refreshes.

### Recommendation
Validate line-selection identity against diff content, not just index position, before reusing a cached selection across a diff/status refresh — e.g., hash or fingerprint each hunk/line's text and only retain a selected index if the corresponding line's content is unchanged; otherwise clear/mark the selection as stale and force the user to re-review before allowing a partial commit. Alternatively, always regenerate the diff and re-validate selection consistency immediately before `formatPatch`/`createCommit` is invoked, rejecting or re-prompting if the diff used for patch generation differs from the diff the user last saw.

### Proof of Concept
1. Open a repository in Desktop; modify a tracked file so it has multiple hunks.
2. In the Changes view, partially select specific added/removed lines (this stores selected line *indices* in `DiffSelection`).
3. Before committing, have the working copy of that file change in a way that shifts line positions but is *not yet reflected* in the currently rendered diff (e.g., an external process, filter/clean driver, or a repository-provided hook/tool modifies the file) — this is the same "time gap" the code comment in `updateChangesWorkingDirectoryDiff` acknowledges.
4. Commit. `updateChangedFiles`/`updateChangesWorkingDirectoryDiff` recompute `selectableLines` and reapply the old index-based selection rather than invalidating it; `formatPatch` builds the patch using `file.selection.isSelected(absoluteIndex)` against the new hunks.
5. The resulting commit contains different line content than what the user visually reviewed and checked, with no warning shown — silent corruption of the commit.
