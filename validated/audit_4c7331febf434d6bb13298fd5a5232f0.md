### Title
FROST nonce reuse via cached preprocess unbound to message/participant set in `DkgConfirmer` — attacker-controlled preprocesses/`key_pair` enable secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Jenkins advisory's bug class is session fixation: a value decided once is reused after the surrounding context changes, because the system fails to rotate/re-derive it. The direct Serai analog lives in `SigningProtocol::preprocess_internal`: the FROST preprocess (and therefore the signing nonces `d`, `e`) is generated from a seed cached in the DB keyed **only** by `self.context`, which for `DkgConfirmer` is the tuple `(b"DkgConfirmer", attempt)`. It does **not** bind the message (`key_pair` → `set_keys_message`) or the remote participants' preprocesses. Every call to `share_internal`/`complete` re-derives the identical nonce pair from the identical seed via `from_cache`/`seeded_preprocess`, while the attacker-influenced inputs (other participants' preprocess bytes via `read_preprocess`, and the `key_pair` in the `DkgConfirmed` message) may vary.

### Finding Description
- `preprocess_internal` stores `CachedPreprocess` under `CachedPreprocesses::set(self.txn, &self.context, ...)` and reconstructs the machine with `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` on every invocation ( [1](#0-0) ).
- `DkgConfirmer::signing_protocol` sets `context = (b"DkgConfirmer", self.attempt)` — the message and the signing set are absent ( [2](#0-1) ).
- `seeded_preprocess` derives all nonces deterministically from the cached 32-byte seed via `ChaCha20Rng::from_seed(*seed.0)` → `Commitments::new(&mut rng, original_secret_share, ...)` ( [3](#0-2) ).
- `share_internal` accepts `preprocesses: HashMap<Participant, Vec<u8>>` — raw bytes produced by other validators — parses them through `read_preprocess`, and calls `machine.sign(preprocesses, msg)` where `msg` is derived from the supplied `key_pair` ( [4](#0-3) , [5](#0-4) ).
- The per-participant binding factor `rho` is a hash of `(group_key, hash_msg(msg), preprocesses)` ( [6](#0-5) ), so any change to a remote participant's commitments or to the message changes `rho` and `c` while the local `d`, `e` stay fixed.
- The file's own header concedes the hazard is unmitigated: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" ( [7](#0-6) ).

### Impact Explanation
Each `share` call emits `s = d + rho·e + c·λ·a_i` with the same `d`, `e`, `a_i`. An unprivileged participant who causes a second `share`/`complete` evaluation for the same `attempt` with different bytes (a different remote commitment in `preprocesses`, or a different `key_pair` in the `DkgConfirmed` transaction) obtains a second equation with a different `rho`/`c`. Two shares suffice to solve for the reused nonces (`s − s′ = (rho − rho′)·e + (c − c′)·λ·a_i` combined with a third share, or directly once `rho ≠ rho′` isolates `e`), after which the victim's threshold secret share `a_i` is recovered from any single share. Recovering a validator's FROST/MuSig share compromises that validator's contribution to all DKG-confirmation signatures for the set — secret share recovery, the highest-impact outcome. The `spec/cryptography/FROST.md` documentation confirms reuse of a preprocess enables recovery of the private key share ( [8](#0-7) ).

### Likelihood Explanation
The reachability hinges on the coordinator evaluating `share`/`complete` more than once under the same `(b"DkgConfirmer", attempt)` context with differing attacker-influenced inputs. Both variable inputs are reachable with public inputs per the scope rules: `preprocesses` are untrusted validator-supplied bytes fed to `read_preprocess`, and `key_pair` is carried in the on-chain `DkgConfirmed` message each validator evaluates. The in-code TODO acknowledges that the check which would prevent a second divergent evaluation (verifying this node's commitments against the presumed on-chain preprocess before publishing a share) is not implemented. The residual uncertainty is whether BFT finalization guarantees each `share` path executes at most once per attempt — the code authors explicitly flag this is only *assumed*, not enforced, and partial rebuilds are a known hole.

### Recommendation
Bind the cached preprocess to everything that varies the signature: include `key_pair`/message hash and the participant set (or the hash of all received preprocesses) in the `CachedPreprocesses` key/context, and/or implement the noted TODO — before publishing a share, verify the node-decided commitments match the preprocesses actually finalized on-chain and refuse to sign otherwise. Additionally, `share_internal` should not regenerate from a cache that was already consumed for a completed share.

### Proof of Concept
1. Validator V calls `DkgConfirmer::share(preprocesses_A, key_pair_A)`; internally `preprocess_internal` loads seed `S` under context `(b"DkgConfirmer", attempt)`, deriving fixed nonces `d, e` and emitting `s1 = d + rho_A·e + c_A·λ·a`.
2. The same attempt context is re-evaluated with attacker-modified input — e.g., a `preprocesses_B` map where one remote participant's commitment bytes differ, or a `key_pair_B` — producing `rho_B ≠ rho_A` and/or `c_B ≠ c_A`, and emitting `s2 = d + rho_B·e + c_B·λ·a`.
3. Since `Commitments::new` regenerates the same `d, e` from `S` ( [9](#0-8) ), the attacker solves the linear system over the scalar field for `d, e`, then computes `a = (s1 − d − rho_A·e) / (c_A·λ)`, recovering the validator's secret share.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
