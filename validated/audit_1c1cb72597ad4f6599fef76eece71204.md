## Analysis

`TrampolineServer.processCommand` only validates the token's *existence* against the global `isValidTrampolineToken` set and then dispatches by `command.identifier`, exactly as the question states. Tracing further into the credential-helper handler confirms the token carries no binding to a specific repository, remote, or host. [1](#0-0) 

The token is minted per git operation (e.g. per `clone`/`fetch`) and handed to the subprocess purely via environment variables, along with the port and a global `credential.helper=desktop` config that is deliberately propagated to filters/LFS so they can also use it: [2](#0-1) 

`withTrampolineEnv`/`trampolineEnvironmentPath` only stores a filesystem *path* for the token, never a remote URL or repository identity: [3](#0-2) 

The `get` credential handler resolves the account purely from the **URL embedded in the request payload** (`cred`), which is fully attacker-controlled stdin sent over the socket — not from anything tied to the actual git operation/remote that owns the token: [4](#0-3) [5](#0-4) 

`findGitHubTrampolineAccount` matches any signed-in account whose endpoint origin equals the origin found in the attacker-supplied URL — with no check that this endpoint corresponds to the repository/remote for which the token was issued: [6](#0-5) 

Since the wire protocol parsed by `TrampolineCommandParser` is a simple, undocumented-but-trivial `\0`-delimited stream of parameter count / parameters / env-var count / env-vars / stdin, any process that has `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` in its environment (e.g. an LFS clean/smudge filter configured via a repository's tracked `.gitattributes`, which git invokes automatically during checkout without prompting) can speak this protocol directly, bypassing Git's own credential-helper request scoping entirely: [7](#0-6) 

## Title
Trampoline token is not scoped to the originating repository/remote, allowing any co-spawned git subprocess to harvest credentials for arbitrary GitHub hosts/accounts - (File: `app/src/lib/trampoline/trampoline-server.ts`)

### Summary
`TrampolineServer.processCommand` and the credential-helper handler chain validate only that a trampoline token exists in the global `isValidTrampolineToken` set; they never verify that the requesting client is the specific git process the token was minted for, nor that the credential request's target host corresponds to the repository/remote associated with that git operation.

### Finding Description
A trampoline token/port pair is generated once per git operation and exposed via `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` env vars, plus a globally-scoped `credential.helper=desktop` `GIT_CONFIG_PARAMETERS` entry that Desktop intentionally propagates to child filters (e.g. Git LFS) because "arguments passed to git commands are not passed down to filters" (comment in `trampoline-environment.ts`). Any process that inherits this environment — including LFS clean/smudge filters declared in a repository's tracked `.gitattributes`, which git executes automatically on checkout — can independently connect to `127.0.0.1:<DESKTOP_PORT>` and speak the plaintext trampoline protocol itself, sending a `CREDENTIALHELPER get` request with an arbitrary `url=` field in stdin. `processCommand` only checks `isValidTrampolineToken(command.trampolineToken)`; it never checks that the connecting socket belongs to the original git process, nor that the requested host matches the repository being operated on. `getGitHubCredential`/`findGitHubTrampolineAccount` then resolve credentials purely from the requested URL's origin against whichever GitHub accounts are signed into Desktop, with no cross-check against the token's originating repository or remote.

### Impact Explanation
A malicious repository can ship a `.gitattributes`/LFS filter (or otherwise arrange for a subprocess to run with the trampoline env inherited) that, during a clone/fetch operation on that untrusted repository, requests and exfiltrates the OAuth token of any other GitHub.com/GHE account currently signed into the victim's Desktop app — accounts entirely unrelated to the malicious repository. This is credential/token exfiltration of GitHub account tokens, which is explicitly in-scope impact.

### Likelihood Explanation
Exploitation requires the victim to have Git LFS (or similar filter/hook mechanism) installed and to clone/fetch the attacker's repository — a standard operation that does not require unnatural user steps, admin rights, or pre-existing malware. The protocol is simple and undocumented but not secret, and env vars are freely readable by any child/co-process of the git invocation.

### Recommendation
Bind each trampoline token to the specific remote/repository context it was issued for (e.g. store the expected endpoint(s)/remote URL alongside the token in `trampoline-environment.ts`), and have `getCredential`/`getGitHubCredential` reject or ignore requests whose target host doesn't match the operation's registered remote(s). Additionally, revoke/scope tokens more tightly so they cannot be reused to query unrelated hosts.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitattributes` with `* filter=lfs` and an LFS "clean" filter script (or a custom `filter.lfs.clean` command) that, instead of doing normal LFS work, reads `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its environment.
2. Victim, already signed into `github.com/victim-org` in Desktop, clones the attacker's repository.
3. During checkout, the LFS filter subprocess runs, inheriting the trampoline env vars.
4. The filter connects to `127.0.0.1:<DESKTOP_PORT>` and sends a hand-crafted trampoline `CREDENTIALHELPER get` command with `url=https://github.com` (or an enterprise host) in stdin, using the inherited token.
5. `TrampolineServer.processCommand` accepts the request (token is valid, no origin/socket check), and `getGitHubCredential`/`findGitHubTrampolineAccount` return the victim's github.com OAuth token, which the filter script exfiltrates over the network.

  public processValue(value: string) {
    switch (this.state) {
      case TrampolineCommandParserState.ParameterCount:
        this.parameterCount = parseInt(value)

        if (this.parameterCount > 0) {
          this.state = TrampolineCommandParserState.Parameters
        } else {
          this.state = TrampolineCommandParserState.EnvironmentVariablesCount
        }

        break

      case TrampolineCommandParserState.Parameters:
        this.parameters.push(value)
        if (this.parameters.length === this.parameterCount) {
          this.state = TrampolineCommandParserState.EnvironmentVariablesCount
        }
        break

      case TrampolineCommandParserState.EnvironmentVariablesCount:
        this.environmentVariablesCount = parseInt(value)

        if (this.environmentVariablesCount > 0) {
          this.state = TrampolineCommandParserState.EnvironmentVariables
        } else {
          this.state = TrampolineCommandParserState.Stdin
        }

        break

      case TrampolineCommandParserState.EnvironmentVariables:
        // Split after the first '='
        const match = /([^=]+)=(.*)/.exec(value)

        if (
          match === null ||
          // Length must be 3: the 2 groups + the whole string
          match.length !== 3
        ) {
          throw new Error(`Unexpected environment variable format: ${value}`)
        }

        const variableKey = match[1]
        const variableValue = match[2]

        this.environmentVariables.set(variableKey, variableValue)

        if (this.environmentVariables.size === this.environmentVariablesCount) {
          this.state = TrampolineCommandParserState.Stdin
        }
        break
      case TrampolineCommandParserState.Stdin:
        this.stdin = value
        this.state = TrampolineCommandParserState.Finished
        break
      case TrampolineCommandParserState.Finished:
        throw new Error(`Received value when in Finished`)
      default:
        assertNever(this.state, `Invalid state: ${this.state}`)
    }
  }
