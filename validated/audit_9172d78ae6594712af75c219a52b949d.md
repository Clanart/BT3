### Title
Asymmetric `PuzzleInfo.__eq__` allows subset-driver spoofing to bypass offer/CAT asset-identity equality checks - ([File: chia/wallet/puzzle_drivers.py])

### Summary
`PuzzleInfo.__eq__` (used to compare asset "driver" metadata for CATs, CR-CATs, NFTs, and VCs throughout the offer/trade code) implements a non-commutative, one-sided equality check: it only iterates over `self.info` keys and checks that `other` has matching values for those keys, but never verifies that `other` doesn't contain additional/different keys. This mirrors the CedarJava advisory's "incorrect equality comparison" bug class (CWE-697/CWE-843), where inverted/incomplete equality logic on identity-bearing objects breaks security-relevant comparisons.

### Finding Description
```python
# chia/wallet/puzzle_drivers.py
def __eq__(self, other: object) -> bool:
    for key, value in self.info.items():
        try:
            if self[key] != other[key]:  # type: ignore
                return False
        except Exception:
            return False
    return True
``` [1](#0-0) 

This only checks keys present in `self.info`; it never checks whether `other` has extra keys that `self` lacks. Thus `PuzzleInfo(A) == PuzzleInfo(A ∪ B)` can be `True` even though `PuzzleInfo(A ∪ B) == PuzzleInfo(A)` is evaluated by the same buggy logic and would actually iterate the superset's keys and fail — so the comparison is directionally inconsistent (`a == b` is not guaranteed to equal `b == a`), which is exactly the class of "incorrect equality" defect called out in the advisory (non-reflexive/non-symmetric comparison logic on an identity-bearing type).

This asymmetric equality is used to validate agreement between drivers for the same asset ID when aggregating offers:
```python
for key, value in offer.driver_dict.items():
    if key in total_driver_dict and total_driver_dict[key] != value:
        raise ValueError(f"The offers to aggregate disagree on the drivers for {key.hex()}")
``` [2](#0-1) 

Because `!=` here resolves via the asymmetric `__eq__`, whichever `PuzzleInfo` happens to be on the left of the comparison (`total_driver_dict[key]`, i.e., whichever offer was aggregated first) determines whether extra/conflicting fields on the right-hand `value` are checked at all. A `PuzzleInfo` with a superset of keys (e.g. containing an extra nested `"also"` layer, or additional CR-CAT/VC restriction fields) compared against a subset `PuzzleInfo` on the left can pass this "disagreement" check even though the two drivers describe materially different puzzles (e.g. differing CR-CAT authorized-provider/restriction data, or an extra masking layer), because the subset side never inspects the keys it doesn't have. `Solver.__eq__` has the identical asymmetric logic, and is used for puzzle-driver solve-time argument comparisons. [3](#0-2) 

### Impact Explanation
Driver equality is the mechanism the wallet uses to detect "the offers to aggregate disagree on the drivers" for a given asset ID — i.e., it's the check meant to prevent an attacker from supplying a `PuzzleInfo`/asset driver for one offer that silently differs (in restriction/ownership fields) from the driver already established for that asset ID, when aggregating multiple offers via `Offer.aggregate`. An offer counterparty could craft an offer whose `driver_dict` entry is built with additional/mismatched fields (e.g. different CR-CAT authorized providers, different "also" layers describing ownership/restrictions) that the asymmetric check fails to catch when merged against an already-narrower driver, letting `Offer.aggregate` accept and construct a spend for an asset under an unintended puzzle configuration. Since `driver_dict` values are subsequently used directly to `construct_puzzle`/`solve_puzzle` and derive the settlement puzzle hash used in `calculate_announcements`/`to_valid_spend`, a mismatched driver being silently accepted can cause the offer to be completed against a different, attacker-influenced puzzle configuration than the honest side intended, undermining asset-identity guarantees during offer settlement.

### Likelihood Explanation
Exploitation requires only submitting/aggregating offers with crafted `driver_dict` entries — reachable by any offer counterparty during normal trade-manager offer-taking/aggregation flow, with no privileged access needed. However, triggering an actually exploitable divergence requires carefully constructing a `PuzzleInfo` whose key superset still produces a puzzle that both (a) hashes/matches acceptably for offer settlement and (b) differs meaningfully in security-relevant fields (e.g., CR-CAT restrictions) — this makes practical exploitation non-trivial and asset-specific, even though the underlying comparison logic is demonstrably broken.

### Recommendation
Fix `PuzzleInfo.__eq__` (and `Solver.__eq__`) to be a proper symmetric equality: compare the full key sets of both `self.info` and `other.info` (e.g., `self.info.keys() == other.info.keys()` followed by value comparison), so that supersets/subsets of keys are never considered equal.

### Proof of Concept
```python
from chia.wallet.puzzle_drivers import PuzzleInfo

a = PuzzleInfo({"type": "CAT", "tail": "0xaa"})
b = PuzzleInfo({"type": "CAT", "tail": "0xaa", "extra_restriction": "0xbb"})

print(a == b)  # True  -- 'a' only checks its own keys, ignoring b's extra key
print(b == a)  # False -- 'b' checks 'extra_restriction' which 'a' lacks -> Exception -> False
```
This demonstrates the equality is not symmetric, matching the analog of the CedarJava `EntityIdentifier.equals()` inverted/incorrect-comparison bug class, and shows how the same asymmetric check embedded in `Offer.aggregate`'s driver-conflict detection can be bypassed depending on comparison order.
