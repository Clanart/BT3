### Title
Unvalidated attacker-supplied ECDH encryption key allows identity point, publicly exposing PedPoP secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
In `SablierV2ProxyTarget._transferAndApprove`, the security-critical component (the permit2 contract performing the authorization check) was supplied by the caller rather than fixed/allowlisted, so an envoy could substitute a do-nothing contract and have the "required check" silently pass. Serai's PedPoP DKG has the same shape: the public key used to ECDH-encrypt each participant's secret share (`enc_key`) is supplied by the participant in `EncryptionKeyMessage` and registered verbatim. It is never checked against identity (or any validity set), so a participant can publish the identity point, causing every share encrypted to them to be encrypted under a publicly known "shared" secret — the confidentiality layer is a do-nothing component, exactly like the dummy permit2 contract.

### Finding Description
`EncryptionKeyMessage::read` deserializes `enc_key` with `C::read_G` (the `Ciphersuite` implementation), which enforces canonical encoding but does not reject the identity point — only `Curve::read_G` in `crypto/frost/src/curve/mod.rs` rejects identity.

```rust
// crypto/dkg/pedpop/src/encryption.rs
pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
  Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })
}
```

`Decryption::register` inserts the supplied key with no validation beyond "not previously registered":

```rust
self.enc_keys.insert(participant, msg.enc_key);
```

When an honest participant encrypts a share to that participant, `encrypt` computes the shared secret as `ecdh(key, to) = key * enc_key`:

```rust
cipher::<C>(context, &ecdh::<C>(&key, to)).apply_keystream(msg.as_mut().as_mut());
```

If `enc_key` is the identity, `ecdh` is always the identity point regardless of the ephemeral `key`, so the ChaCha20 keystream is derived purely from public data (`context || identity_encoding`) via `cipher()`. Anyone who observes the `EncryptedMessage` can recompute the keystream and recover the plaintext share. Note `pop` proves possession of the *per-message ephemeral* key, not of `enc_key`, and nothing binds `enc_key` to a proof of possession or a non-identity set — the "trusted component" is fully attacker-selected.

### Impact Explanation
Every `EncryptedMessage` addressed to a participant who registered an identity `enc_key` is effectively broadcast in plaintext to all observers of the DKG channel. In PedPoP those messages carry secret shares, so the share intended for the malicious participant is exposed to everyone. An adversary who can also observe or collect other shares (e.g., across a compromised/malleable DKG session or by combining leaked shares over multiple sessions) gains additional evaluation points of the dealing polynomials, degrading the threshold assumption and enabling key-share recovery once enough shares are public. This is a confidentiality failure of the DKG's transport layer that the protocol assumes provides secrecy.

### Likelihood Explanation
The malicious party only needs to be a DKG participant publishing a malformed `EncryptionKeyMessage` — an unprivileged input path (bytes fed to `read_G` inside `EncryptionKeyMessage::read` and then to `register`). No cryptographic assumption is broken and no permit-style check exists to be bypassed; the attack is deterministic, costs nothing, and leaves the protocol succeeding normally so the leak is silent. Severity is bounded because each participant can only expose shares addressed to themselves, so exploitation meaningfully combines with other leaked shares rather than alone recovering a key.

### Recommendation
Reject the identity point (and ideally require non-identity plus proof of possession) for `enc_key` in `EncryptionKeyMessage::read`/`Decryption::register`, mirroring the permit2 allowlist fix: constrain the security-critical input to a valid set instead of trusting caller-supplied bytes. Using `Curve::read_G`-style identity rejection or an explicit `is_identity` check suffices for the identity case; binding a PoP to `enc_key` additionally prevents claiming keys with unknown discrete logs.

### Proof of Concept
1. Malicious participant `j` broadcasts `EncryptionKeyMessage { msg, enc_key: identity }` (identity serializes to the canonical all-zeros Ristretto encoding, accepted by `C::read_G`).
2. Honest dealer `i` calls `encrypt(rng, context, i, enc_keys[j]=identity, share)`; `ecdh = share_key * identity = identity`; ciphertext = `share XOR keystream(H(context || identity_bytes || ...))` with the static IV `"DKG IV v0.2\0"`.
3. Any observer of `EncryptedMessage` computes `cipher::<C>(context, &identity)` from entirely public values, applies the keystream, and recovers the share plaintext — no private key required.
4. Contrast: with a proper non-identity `enc_key`, the ECDH point is unknowable without `j`'s private key or the ephemeral `key` scalar.
