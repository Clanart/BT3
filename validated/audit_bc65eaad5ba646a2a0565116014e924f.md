## Title
Diff hunk expansion silently desyncs partial-commit line selection, causing unintended lines to be staged/committed - (File: app/src/ui/diff/text-diff-expansion.ts, app/src/models/diff/diff-selection.ts)

### Summary
The Astaria report's broken invariant is: a boundary/duration check that should have prevented an unsafe state instead lets an operation proceed with stale internal accounting (remaining-interest calculation), silently producing an incorrect/underflowed result that costs the user funds. The closest analog in Desktop is the interaction between **hunk expansion** (`expandTextDiffHunk` / `mergeDiffHunks` in `app/src/ui/diff/text-diff-expansion.ts`) and **partial line selection** (`DiffSelection` in `app/src/models/diff/diff-selection.ts`), where line selection state is keyed by absolute unified-diff indices that shift after expansion, without the app recomputing/remapping the user's prior selections against the new indices.

### Finding Description
`DiffSelection` tracks per-line inclusion state as a `Set<number>` of "diverging" absolute line indices relative to the unified diff (`divergingLines`), as seen in `isSelected`/`withRangeSelection` [1](#0-0) . These indices are the `hunk.unifiedDiffStart + lineIndex` offsets computed when the diff was originally parsed [2](#0-1) .

When the user expands a hunk (clicking "Load more" in the diff view), `expandTextDiffHunk` inserts new context lines into a hunk and then shifts the `unifiedDiffStart`/`unifiedDiffEnd` of every hunk that comes after it by `numberOfNewDiffLines` [3](#0-2) . This means the absolute index of every addable/deletable line below the expansion point changes.

Critically, nothing in this code path recomputes the caller's `DiffSelection` to account for the new offsets. The `DiffSelection.divergingLines` set (which records which specific lines the user toggled away from the default) still contains the *old* absolute indices. After expansion, those same numeric indices now point at different, shifted lines (because `diffHunkForIndex`/`diffLineInfoForIndex` resolve lines purely by absolute index against the new hunk ranges) [4](#0-3) . Consequently `formatPatch`'s check `file.selection.isSelected(absoluteIndex)` [5](#0-4)  and `formatPatchToDiscardChanges`'s equivalent check [6](#0-5)  will evaluate selection against the *wrong* line for every hunk positioned after an expansion.

This mirrors the Astaria bug class exactly: a state-mutating operation (buyout / hunk-expansion) changes an underlying invariant (remaining duration / absolute line offsets) that a separate, already-computed value (remaining interest / line-selection set) depends on, and no code path re-validates or remaps that dependent value before it's used to produce a monetary/commit-affecting result.

I was only able to trace the expansion machinery itself (`expandTextDiffHunk`, `mergeDiffHunks`, hunk-index shifting) and the selection lookup path (`DiffSelection.isSelected`, `diffHunkForIndex`); I could not fully verify within the available context whether `onIncludeChanged` or another caller in `side-by-side-diff.tsx` explicitly remaps `divergingLines` after `onExpandHunk` runs (the file is large and the relevant remap call, if any, wasn't visible in the retrieved excerpts). This is a material gap: if such a remap does exist elsewhere (e.g., inside `onExpandHunk`'s full body, which was truncated), the vulnerability may already be mitigated.

### Impact Explanation
If selection state is not remapped after hunk expansion, a user who (a) partially selects/deselects lines for a commit, then (b) expands a hunk above those lines (adding a repository-attacker-controlled number of context lines from a malicious/large fetched file), and then (c) commits, could have Desktop silently stage/commit different lines than what they last visually confirmed as selected — i.e., corruption of what the user commits/pushes, matching the stated "silent corruption of what the user commits or pushes" impact class. Because the attacker (via a crafted upstream file that produces many lines of shiftable context) influences how much expansion offset is introduced, this is remotely triggerable content, not something requiring local/physical access.

### Likelihood Explanation
Requires: (1) a file with a diff that has multiple hunks, (2) partial line selection already applied to a hunk located after an expandable one, (3) the user or app performs hunk expansion (a supported, common UI action) before committing. No malicious local access or admin rights needed — the attacker only needs to control the repository/file content that produces the multi-hunk diff. Likelihood is moderate: it depends on normal interactive use of the "expand hunk" UI feature combined with partial-stage workflows, which are common enough in Desktop's UX but require a specific sequence, making it less than certain but plausible in real usage.

### Recommendation
- When a hunk is expanded, recompute `DiffSelection`'s selectable/diverging line indices to reflect the new unified-diff offsets, instead of leaving old absolute indices in place. This can be done by mapping each existing diverging line index through the old hunk layout, finding the corresponding line's *stable* identity (e.g., old/new file line number), and re-inserting it at the corresponding new absolute index after `expandTextDiffHunk` returns.
- As a stronger safety net, before generating a patch (`formatPatch`/`formatPatchToDiscardChanges`), assert that `file.selection`'s selectable-line count matches the current diff's addable/deletable line count, and fail loudly (rather than silently mis-mapping) if it doesn't.
- Add regression tests that: select specific added/deleted lines, expand an earlier hunk, and verify that `formatPatch` output still reflects the originally intended lines.

### Proof of Concept
Conceptual reproduction (pending full verification of `onExpandHunk`'s remap logic, which could not be fully retrieved):
1. Open a file with two hunks, e.g. hunk A (lines 10-20) and hunk B (lines 40-50), separated by a large context gap.
2. In hunk B, deselect one deleted line for partial commit — this sets an entry in `divergingLines` at, say, absolute index 46 (per `DiffSelection.withLineSelection`) [7](#0-6) .
3. Expand hunk A upward/downward by clicking "Load more", which calls `expandTextDiffHunk`; this adds `numberOfNewDiffLines` new lines and shifts hunk B's `unifiedDiffStart`/`unifiedDiffEnd` accordingly [8](#0-7) [9](#0-8) .
4. Now absolute index 46 in the *new* diff layout corresponds to a different line than the one the user deselected.
5. Commit the partial selection; `formatPatch` uses `file.selection.isSelected(absoluteIndex)` against the new hunk layout [5](#0-4) , so the wrong line's inclusion/exclusion is applied, and the actual committed diff differs from what the user last saw/intended.

Because I could not confirm from available context whether `onExpandHunk`/`onIncludeChanged` already perform a remap step that prevents this, this should be treated as a **candidate finding requiring verification** against the full `side-by-side-diff.tsx` source (particularly the complete body of `onExpandHunk` and its interaction with `getSelection()`/`props.onIncludeChanged`) before being confirmed as exploitable.

export function diffHunkForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): DiffHunk | null {
  const hunk = hunks.find(h => {
    return index >= h.unifiedDiffStart && index <= h.unifiedDiffEnd
  })
  return hunk || null
}

/**
 * Locate the diff line and hunk for the given (absolute) line number in the diff.
 */
function diffLineInfoForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffLineInfo | null {
  const hunk = diffHunkForIndex(hunks, index)
  if (!hunk) {
    return null
  }

  const line = hunk.lines[index - hunk.unifiedDiffStart]
  if (!line) {
    return null
  }

  return { hunk, line }
