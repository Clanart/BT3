## Title
Uncaught exception in PlotNFT memo parsing crashes wallet sync on malformed CREATE_COIN memo - (File: chia/pools/plotnft_drivers.py)

### Summary
The reported CVE describes belle-sip crashing when it parses an unauthenticated SIP header that is missing an expected sub-part (a From header without a required parameter), because the parser assumes well-formed structure and raises/crashes instead of gracefully rejecting the malformed input. The analogous pattern exists in `PlotNFT.get_next_from_coin_spend()` in `chia/pools/plotnft_drivers.py`, which parses attacker-influenced `CREATE_COIN` memo data from an on-chain (or even not-yet-confirmed, wallet-observed) coin spend and only guards part of that parsing with a narrow `except ValueError`, leaving other steps unguarded.

### Finding Description
`PlotNFT.get_next_from_coin_spend()` is invoked by wallet sync code (`chia/wallet/plotnft_wallet/plotnft_wallet.py::identify()` and `::_finish_leaving_pool()`) whenever a coin spend is examined that curries like a PlotNFT singleton. This is untrusted, attacker-controllable data: anyone can create a coin whose puzzle uncurries to match the singleton mod/launcher shape and whose `CREATE_COIN` memo blob is crafted arbitrarily.

Only the `PuzzleWithRestrictions.from_memo(...)` call is wrapped in `try/except ValueError`. Immediately afterward, `unknown_inner_puzzle.additional_memos.at("f").as_atom()` is passed directly into `G1Element.from_bytes(...)` with **no exception handling at all**. If `additional_memos` navigates to a non-atom (e.g., a cons pair) `.as_atom()` returns `None`, and `G1Element.from_bytes(None)` will raise a `TypeError` (or similar non-`ValueError` exception from the `chia_rs` binding) rather than the `ValueError` the surrounding code anticipates. Likewise, if the atom has the wrong byte length or is not a valid curve point, `G1Element.from_bytes()` (a `chia_rs`/PyO3-bound Rust function) can raise exception types other than plain Python `ValueError` depending on the binding's error mapping.

Because the call site's exception handling only catches `GetNextPlotNFTError` at the caller (`identify()` in `plotnft_wallet.py`, `except GetNextPlotNFTError: pass`), any other exception type raised deeper in `get_next_from_coin_spend()` (i.e., anything not converted to `GetNextPlotNFTError` and not a plain `ValueError` caught in the driver) propagates unhandled through the wallet's coin-processing/sync pipeline.

This mirrors the belle-sip bug class: a message/coin that is *almost* well-formed (passes an initial spec/namespace check) but is missing or malforms a downstream required field causes the parser to throw an exception type the caller did not anticipate, crashing message/coin processing instead of being cleanly rejected.

### Impact Explanation
A wallet that is watching PlotNFT-shaped coins (any Chia wallet running plotnft syncing, since `identify()` is called generically during coin-spend processing) can be made to raise an unhandled exception simply by observing (via mempool broadcast, or by inclusion in a block) a spend whose puzzle uncurries as a plausible PlotNFT singleton but whose memo's pubkey field is a malformed/non-atom value. Depending on how far up the call stack this exception propagates uncaught, this can interrupt wallet sync processing (a spend-triggered processing halt for the specific wallet peer/client), which is the exact impact category called out as valid in the assignment (spend-triggered transaction-processing halt). This does not require the victim to own the coin — only that their wallet inspects the coin spend during normal chain-sync/coin-spend classification.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to construct a puzzle reveal that satisfies the initial singleton/mod and launcher-hash checks in `get_next_from_coin_spend()` (`singleton.curried_args[0].at("rr") != singleton_launcher_hash` and one `CREATE_COIN` condition) and a memo that passes `PuzzleWithRestrictions.from_memo()`'s namespace check (`Program.to(cls.spec_namespace)` at `custody_architecture.py:273`) but has a malformed `additional_memos` structure at the point the pubkey is extracted. This is achievable by any unprivileged spend-bundle submitter crafting the coin spend/memo bytes directly (no signature validity is required for these specific inspection paths since they run during sync/coin classification, prior to/independent of spend validity checks by the wallet).

### Recommendation
Wrap the entire memo interpretation block in `get_next_from_coin_spend()` (from `PuzzleWithRestrictions.from_memo(...)` through `G1Element.from_bytes(...)` and the `PoolConfig` construction) in a broad exception handler that converts any parsing failure (`ValueError`, `TypeError`, `AttributeError`, and any `chia_rs`-raised binding errors) into `GetNextPlotNFTError`, consistent with how malformed on-chain data is handled elsewhere in this function (e.g., the puzzle-hash mismatch check at the end already raises `GetNextPlotNFTError`). Alternatively, validate the atom length/type of `additional_memos.at("f").as_atom()` before calling `G1Element.from_bytes()`.

### Proof of Concept
1. Construct a `CoinSpend` whose puzzle reveal uncurries to the singleton mod with `curried_args[0].at("rr")` equal to the singleton launcher hash (satisfying the launcher check) and whose inner puzzle solution outputs exactly one `CREATE_COIN` condition.
2. Set that `CREATE_COIN`'s memo to `(spec_namespace, [nonce, [], 0, member_hint_program, additional_memos])` where `additional_memos` is a cons pair (not an atom) in the position read by `.at("f")` — e.g., `additional_memos = ((1 . 2), ...)` so `additional_memos.at("f").as_atom()` returns `None`.
3. Broadcast/observe this spend so it reaches a wallet's `PlotNFT2Wallet.identify()` path during coin-spend classification (`chia/wallet/plotnft_wallet/plotnft_wallet.py:539`), which calls `PlotNFT.get_next_from_coin_spend()`.
4. `G1Element.from_bytes(None)` raises an exception type other than `ValueError` inside `plotnft_drivers.py:486`, which is not caught by the `except ValueError` at line 482 (already passed) nor by the `except GetNextPlotNFTError` in `identify()` (line 591), propagating up uncaught and interrupting wallet coin-spend processing for that sync cycle.
