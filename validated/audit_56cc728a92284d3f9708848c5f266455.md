### Title
Background repository refresh silently rewrites the `origin` remote URL to an attacker-controlled host supplied via the GitHub API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` is invoked automatically during ordinary background repository refresh/fetch cycles with the `clone_url` from a freshly fetched API repository object, and rewrites the local `origin` remote via `git remote set-url` if a small set of heuristic checks pass. None of those checks verify that the new URL's hostname belongs to a trusted/expected GitHub endpoint — only that the URL scheme (`https`/`ssh`) is unchanged and that the owner/name/hostname triple differs from the current remote. An API response with an attacker-chosen `clone_url` on an arbitrary host therefore silently becomes the user's `origin`.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches the repository object from the API and, if the local repository already has an associated `GitHubRepository`, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

This function runs automatically on every `_fetch`/`_selectRepositoryRefreshTasks` cycle, i.e. background fetching, not just on explicit user action: [2](#0-1) [3](#0-2) 

Inside `updateRemoteUrl`, the guard logic is: [4](#0-3) 

The checks are:
- `protocolsMatch`: only compares `URL.parse().protocol` (i.e. `https:` vs `https:`), not the host.
- `remoteUrlUnchanged`: confirms the *current* remote still matches the previously cached `gitHubRepository.cloneURL` (protects against clobbering a manually-edited remote, not against a malicious new value).
- `!urlsMatch`: confirms the *new* URL differs from the current remote.

None of these validate that the new hostname is the same GitHub/GHE host the repository was originally associated with. `urlMatchesRemote`/`parseRemote` treat hostname purely as a regex capture group, with no allow-list of trusted hosts: [5](#0-4) [6](#0-5) 

If a hostname/owner/name is returned as `https://evil.example.com/attacker/repo.git`, it parses successfully, has the same `https:` protocol as the existing remote, doesn't match the current remote (so `!urlsMatch` is true), and the current remote still matches the previously-cached clone URL (`remoteUrlUnchanged` true) — so `gitStore.setRemoteURL` is called and `git remote set-url origin https://evil.example.com/attacker/repo.git` is executed without any user prompt or confirmation: [7](#0-6) [8](#0-7) 

The existing unit tests only exercise the "GitHub renamed the repo, still same host" scenario and never assert that a cross-host `clone_url` is rejected: [9](#0-8) 

### Impact Explanation
Once `origin` is silently repointed to an attacker-controlled host, the next background fetch, pull, or push made by the user targets that host instead of the real GitHub/GHE repository. This is a silent corruption of what the user commits/fetches/pushes: the user believes they're syncing with their real repository while Desktop is quietly talking to a different remote. Depending on the user's authentication configuration (generic git auth / GHE with a non-standard endpoint), this can also surface a credential prompt scoped to the attacker's host (`promptForGenericGitAuthentication` in `trampoline-credential-helper.ts`), which could be used to phish credentials for that host under a false sense of trust since the app made the change, not the user. GitHub.com/dotcom-tied account tokens are not directly leaked (scoped credential lookup prevents that), but push/fetch traffic and any locally-typed generic credentials for the spoofed host are exposed.

### Likelihood Explanation
The trigger is a single field (`clone_url`) in the repository object returned by `api.fetchRepository(owner, name)` for whatever endpoint the account is associated with. Any attacker who can influence that API response — a compromised/malicious GHES instance the user has added an account for, a network position able to tamper with a non-github.com API response, or a compromised GitHub Enterprise deployment — can trigger this on the next background refresh, which happens automatically and repeatedly while the app is open, without any user interaction beyond having the repository open/selected.

### Recommendation
In `updateRemoteUrl`, add a check that the hostname of `apiRepo.clone_url` matches the hostname of `gitHubRepository.endpoint` (or the currently trusted API endpoint) before calling `setRemoteURL`, analogous to the missing invariant check the original report recommends for `maxInvocations`. Reject/log-and-skip the update if the hostnames differ, and/or surface a confirmation prompt to the user (similar to the existing `UpstreamAlreadyExists` dialog pattern) instead of silently rewriting the remote.

### Proof of Concept
1. Add a GitHub Enterprise (or generic-auth) account in Desktop pointing at an attacker-influenced/compromised API endpoint (or intercept the API response for `GET /repos/{owner}/{repo}` for that endpoint).
2. Open/select a repository already tracked with that account, with `origin` pointing at `https://ghe.example.com/owner/repo.git`.
3. Have the API response return `clone_url: "https://evil.example.com/attacker/repo.git"` (same `https:` scheme, different host/owner/name).
4. Trigger a background fetch/refresh (automatic, or via `_fetch`).
5. Observe `updateRemoteUrl` calling `gitStore.setRemoteURL('origin', 'https://evil.example.com/attacker/repo.git')`, confirmable via `git remote -v` in the repo directory — the origin now points to the attacker's host with no user prompt.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
