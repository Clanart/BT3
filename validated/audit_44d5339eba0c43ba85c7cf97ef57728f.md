### Title
`VLMGP.unlock()` can permanently revert and freeze user's own locked MGP due to forced reward claim - (File: `VLMGP.sol`)

### Summary
`VLMGP.unlock()` forces a reward claim (`multiclaimFor`) through `MasterMagpie` before releasing the user's own principal MGP tokens. If that claim call reverts for any reason (e.g. one of the registered bonus/reward tokens becomes non-transferable, is paused, blacklists this contract, or otherwise misbehaves), the entire `unlock()` transaction reverts, permanently preventing the user from withdrawing MGP that has already finished cool-down — the exact same "critical withdrawal function bundled with an external call that can revert" pattern as the referenced `Vault.blacklistProtocol` bug.

### Finding Description
`unlock()` validates the slot, then unconditionally calls: [1](#0-0) 

```
function unlock(uint256 _slotIndex) external override whenNotPaused nonReentrant {
    _checkIdexInBoundary(msg.sender, _slotIndex);
    UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];
    if (slot.endTime > block.timestamp) revert StillInCoolDown();
    if (slot.amountInCoolDown == 0) revert UnlockedAlready();
    address[] memory lps = new address[](1);
    address[][] memory vlMGPrewards = new address[][](1);
    lps[0] = address(this);
    IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender);
    uint256 unlockedAmount = slot.amountInCoolDown;
    _unlock(unlockedAmount);
    slot.amountInCoolDown = 0;
    IERC20(MGP).safeTransfer(msg.sender, unlockedAmount);
    emit Unlock(msg.sender, block.timestamp, unlockedAmount);
}
```

`multiclaimFor` routes into `MasterMagpie`'s internal `_multiClaim`, which for each registered pool calls `getReward` on the pool's `BaseRewardPool`/`BaseRewardPoolV2`, iterating over every reward token and calling `IERC20(rewardToken).safeTransfer(...)`: [2](#0-1) [3](#0-2) 

If any single reward token used across the vlMGP/associated pools reverts on transfer (paused token, blacklist-style token, insufficient balance from reward-accounting rounding, or a bonus token contract that later becomes non-functional), the whole `unlock()` call reverts. Since the claim step happens before the principal (`MGP`) is released, a single bad reward token permanently blocks users from ever withdrawing their own already-unlocked principal via this slot — `startUnlock()` has the identical pattern of calling `multiclaimFor` before setting the slot, so re-attempting is not a workaround, as the same claim step is present there too: [4](#0-3) 

This mirrors the reported bug class exactly: an emergency/critical state-mutating action (`blacklistProtocol` withdrawing before blacklisting) is coupled with an unrelated external call that can revert, blocking the critical action from ever completing.

### Impact Explanation
A user's own principal MGP, once unlocked from cooldown, can become permanently stuck if any reward token registered on the associated staking pool becomes non-transferable (paused, blacklisting the VLMGP/pool address, or otherwise reverting on transfer). There is no path in `unlock()` to skip the claim step, so this is a genuine permanent freezing-of-funds scenario for the affected user(s), satisfying the impact bar of "permanent freezing of funds."

### Likelihood Explanation
This does not require any privileged/admin action — it is triggered purely by ordinary token behavior of a bonus/reward token used by the system (many of the pools support external bonus reward tokens via `queueNewRewards`), or by reward-accounting rounding causing the pool's balance to be insufficient for the last claimant's transfer. Given that reward tokens are added over the life of the protocol and are not guaranteed to always remain functional/transferable, this is a plausible failure mode, though it is conditioned on a reward token misbehaving rather than being triggerable at will by an attacker.

### Recommendation
Decouple the mandatory reward claim from the principal-unlock path in `VLMGP.unlock()` (and `startUnlock()`): wrap the `multiclaimFor` call in a try/catch (or expose a separate parameter/flag to skip claiming) so that a failing reward transfer cannot block release of the user's own principal MGP.

### Proof of Concept
1. A reward token is added to the `BaseRewardPool`/`BaseRewardPoolV2` backing the vlMGP staking pool via `queueNewRewards`.
2. That reward token later reverts on `transfer` to a given account (e.g., token owner blacklists the VLMGP contract, or the token is paused, or reward accounting produces a shortfall).
3. A user with a fully cooled-down unlock slot calls `unlock(slotIndex)`.
4. `unlock()` invokes `IMasterMagpie(masterMagpie).multiclaimFor(...)`, which internally calls `getReward` on the affected `BaseRewardPool`, which reverts on `IERC20(rewardToken).safeTransfer(...)`.
5. The entire `unlock()` transaction reverts, and the user's already-unlockable MGP principal remains permanently locked in the slot with no way to bypass the failing claim step.
