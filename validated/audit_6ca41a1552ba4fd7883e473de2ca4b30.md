### Title
Attacker-controlled remote hostname is misclassified as a trusted GitHub Enterprise host via a weak regex heuristic, triggering an unauthorized OAuth/enterprise sign-in binding - (File: `app/src/lib/api.ts`)

### Summary
GitHub Desktop's `isGitHubHost()` decides whether an arbitrary remote/credential-helper hostname "belongs to GitHub" using string-pattern heuristics rather than a strict allow-list or cryptographic check, mirroring the MetaMask bug class where an untrusted, attacker-controllable value (`net_version`) was used to decide which chain/identity to trust. Here, the untrusted value is the *hostname of a git remote a user clones or fetches from*, and the trust decision it drives is whether Desktop should treat that remote as a genuine "enterprise" GitHub host and route it into the internal GitHub sign-in / credential-binding flow instead of a neutral generic-git-auth prompt.

### Finding Description
`isGitHubHost()` classifies a hostname as GitHub-like using a bare substring/regex test: [1](#0-0) 

`/(^|\.)(github)\./.test(hostname)` returns `true` for any hostname that merely contains the literal label `github` followed by a dot anywhere in it (e.g. `github.attacker.com`, `foo.github.attacker.net`). This is checked before any real connectivity/meta-endpoint verification, and it is *not* covered by the third-party denylist (`isKnownThirdPartyHost`), which only lists a handful of known unrelated SaaS domains: [2](#0-1) 

This classification result feeds directly into the git credential-helper trampoline used on every clone/fetch/push, via `getEndpointKind()`: [3](#0-2) 

When `endpointKind !== 'generic'` and there is no existing account matching the (attacker) endpoint, `getCredential()` does **not** fall back to the safe, host-agnostic generic-git-auth prompt or an external credential manager. Instead it explicitly routes the user into the internal GitHub/Enterprise sign-in flow, bound to the attacker's URL, and returns whatever account results from that flow bound to the credential: [4](#0-3) 

The broken invariant is: *"a hostname string pattern is sufficient proof that a remote endpoint is a legitimate GitHub/GHE host."* Just as MetaMask trusted an RPC-returned `net_version` value to decide which chain a transaction should be signed for, Desktop trusts an attacker-controlled hostname string to decide which authentication/account-binding path a git operation should take, without an authoritative check (e.g., strict allow-list of the user's actual configured Enterprise endpoints, or requiring the `/meta` `x-github-request-id` verification step to run first for *all* undecided hosts instead of only as a last resort).

### Impact Explanation
An attacker who controls a git remote/proxy the victim clones, fetches, or adds (e.g. a "helpful mirror" URL like `https://github.mycompany.attacker.com/...` or `https://github.attacker.io/org/repo.git`) can cause Desktop to:
1. Skip the neutral generic-credential path and instead invoke `ui.promptForGitHubSignIn(endpoint)` bound to the attacker's host, which is exactly the "unauthorized OAuth or account binding" impact category — Desktop is initiating an account-binding/sign-in flow toward a host the attacker fully controls.
2. Because `endpointKind !== 'generic'` also disables storing/erasing of the credential through the external/generic credential helper for hosts that are misclassified this way, any legitimate credential-manager fallback the user might otherwise rely on for that host is bypassed.

This does not require local/physical access, admin rights, prior malware, or leaked credentials — it only requires the victim to add or use a git remote pointing at an attacker-chosen hostname, which is a normal, expected Desktop workflow (adding a remote / cloning from a link).

### Likelihood Explanation
Likelihood is moderate: the attacker only needs to register a domain containing the literal substring `github.` (widely available, e.g. `github.<anything>.com`) and get a user to clone/fetch/push against it — a realistic scenario via a malicious fork URL, deep link, or compromised proxy in front of the real remote. The regex has no length/position constraints beyond "preceded by start-or-dot, followed by dot," making it trivial to satisfy while looking superficially legitimate to a user (`github-mirror.company-cdn.com`, `raw.github.cdn-proxy.net`, etc.).

### Recommendation
- Replace the substring heuristic in `isGitHubHost()` (`app/src/lib/api.ts`, lines 2451-2454) with a check against the user's actually-configured Enterprise account endpoints and/or require the authoritative `/meta` + `x-github-request-id` verification (already implemented later in the same function) to run unconditionally instead of being skipped whenever the regex "looks like" GitHub.
- Ensure `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts` never routes an unrecognized host into the internal GitHub sign-in / account-binding flow based purely on a heuristic string match; only do so once the host has been positively confirmed via the `/meta` request or matches a previously user-added Enterprise endpoint.

### Proof of Concept
1. Attacker stands up a server at `https://github.mycompany.evil.com` (or any hostname containing `github.` per the regex) that does not need to implement anything beyond responding to normal git protocol requests (or nothing at all, since the classification happens client-side before/independently of a successful request).
2. Victim adds this URL as a remote/clone target in GitHub Desktop (e.g., via a shared "fork" link).
3. On the first git network operation, Desktop's credential-helper trampoline calls `getEndpointKind()` → `isGitHubHost()`, which matches the regex and returns `true`/`'enterprise'` without needing the attacker's server to prove anything.
4. `getCredential()` sees `endpointKind !== 'generic'` and no existing account for this endpoint, and calls `ui.promptForGitHubSignIn(endpoint)`, presenting the user with Desktop's native "Sign in to GitHub Enterprise" UI pre-bound to the attacker's host instead of a generic-credentials prompt — completing the account-binding step toward an attacker-controlled endpoint.

const isKnownThirdPartyHost = (hostname: string) => {
  if (knownThirdPartyHosts.has(hostname)) {
    return true
  }

  for (const knownHost of knownThirdPartyHosts) {
    if (hostname.endsWith(`.${knownHost}`)) {
      return true
    }
  }

  return false
}
