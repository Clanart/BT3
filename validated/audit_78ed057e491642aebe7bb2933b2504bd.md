### Title
`SignableTransaction::new` excludes the OP_RETURN data output from the fee/vbytes calculation, causing the fee rate to be underpaid — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the Arcadia issue where a reserved quantity (minimum margin) was wrongly included in a value computation, here the OP_RETURN output's weight is wrongly *excluded* from the transaction's weight/vbytes computation. The data output is pushed into `tx_outs` at lines 194–202, but `calculate_weight_vbytes` is invoked with `payments` (which does not contain the data output) at lines 204 and 225–226, so the OP_RETURN output contributes nothing to `vbytes`, `needed_fee`, or the `MAX_STANDARD_TX_WEIGHT` check.

### Finding Description
In `SignableTransaction::new`:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ... })   // line ~194
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None); // line ~204
let mut needed_fee = fee_per_vbyte * vbytes;                                          // line ~206
```

`calculate_weight_vbytes` builds a transaction whose outputs are derived only from `payments` and `change`. The OP_RETURN output added earlier to `tx_outs` is never represented in the weight estimate. The same omission affects `fee_with_change` (lines 225–227). Consequently:

- `needed_fee` (the fee actually paid, since `fee() = sum(inputs) - sum(outputs)`) is computed for a smaller transaction than the one constructed. An 80-byte OP_RETURN adds roughly 30–90+ vbytes whose fee is never charged.
- The `TooLowFee` check (line 211) and the `NotEnoughFunds` check (line 215) are both evaluated against this understated `vbytes`/`needed_fee`, so they cannot catch the shortfall.
- The `TooLargeTransaction` check (line 241) uses `weight` that omits the data output, so a transaction exceeding `MAX_STANDARD_TX_WEIGHT` can be accepted as standard.

### Impact Explanation
The caller-specified `fee_per_vbyte` is silently underpaid on the real transaction size. If the caller specifies a fee rate near the minimum relay fee, the actual fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, making the signed transaction non-relayable — the threshold-signed spend is a validly-signed transaction the network will not propagate, so the wallet's funds cannot move as intended. Additionally, a data-bearing transaction that should be rejected as non-standard (> `MAX_STANDARD_TX_WEIGHT`) is produced and signed. An unprivileged party that can cause a `data` payload to be included in a spend (a supported public input) triggers the mispriced fee and the skipped weight bound.

### Likelihood Explanation
Any caller passing `Some(data)` to `SignableTransaction::new` hits this path deterministically; data up to 80 bytes is explicitly allowed (lines 171–173). The underpayment scales with the data length. Whether the resulting transaction fails relay depends on how close `fee_per_vbyte` is to the relay minimum, but the fee-rate invariant (`fee() == needed_fee >= fee_per_vbyte * actual_vbytes`) is broken in all cases, and the standardness bound is unenforced whenever the OP_RETURN pushes the real weight over the limit.

### Recommendation
Include the data output in the weight estimate: build the OP_RETURN `TxOut` before computing weight and pass a `payments`-plus-data output list (or the actual `tx_outs`) into `calculate_weight_vbytes`, for both the no-change and with-change calls. Alternatively, add the measured serialized size of the OP_RETURN output to `weight`/`vbytes` after the fact.

### Proof of Concept
```rust
// Conceptual: inside SignableTransaction::new
let data = vec![0u8; 80];
// tx_outs gets the OP_RETURN pushed (line ~194), but:
let (_, vbytes) = Self::calculate_weight_vbytes(inputs, &payments, None);
// `vbytes` is computed on a tx whose outputs = payments only.
// The real tx has outputs = payments + OP_RETURN(~91 serialized bytes ≈ 91 wu ≈ 23 vbytes,
// plus output overhead ≈ ~34+ vbytes total).
// needed_fee = fee_per_vbyte * vbytes  → misses ~30-40 vbytes of fee.
// With fee_per_vbyte == min relay rate, actual fee rate < min relay → TX rejected by mempool.
// With many inputs near MAX_STANDARD_TX_WEIGHT, real weight exceeds the standardness
// limit while `weight` passes the check at line ~241.
```

Both defects are fixed by feeding the OP_RETURN output into `calculate_weight_vbytes` at the call sites in `networks/bitcoin/src/wallet/send.rs:204` and `networks/bitcoin/src/wallet/send.rs:225-226`.
