### Title
Missing Confidence Gating in `get-asset-price` / `get-pyth-price` Price Path Used for Health-Factor and Liquidation Display Calculations - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
The `v0-1-data.clar` utility contract re-implements a full Pyth price-resolution pipeline (`get-pyth-price` → `normalize-pyth` → `get-asset-price` → `sum-collateral-usd` / `sum-debt-usd` → health-factor/liquidatable computation), but this parallel implementation omits the confidence-interval gate (`check-confidence`) that the core `market.clar` / `v0-4-market.clar` oracle-resolution path enforces before accepting a Pyth price.

### Finding Description
In the production market contract, every Pyth price read is validated through `resolve-pyth`, which calls `check-confidence` to reject prices whose confidence interval exceeds `max-confidence-ratio` before the value is used: [1](#0-0) 

The `v0-1-data.clar` utility contract, however, has its own independent Pyth-price-fetch helper, `get-pyth-price`, which calls `pyth-storage-v4 get-price` directly and normalizes the returned price/exponent — but never calls anything analogous to `check-confidence`, and drops the `conf` field entirely: [2](#0-1) 

This unguarded price is then fed into `get-asset-price`, which is used by `sum-collateral-usd` and `sum-debt-usd` to compute `total-collateral-usd`, `total-debt-usd`, `current-ltv`, `health-factor`, and the `is-liquidatable` boolean returned to callers: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported bug class: just as Filsnap exposed a value (the wallet address) through an RPC path that skipped the security gate (`fil_configure` confirmation) that the primary path enforced, `v0-1-data.clar` exposes/derives a value (asset USD price, and therefore health factor / liquidatable status) through a duplicate resolution path that skips the confidence gate (`check-confidence`) that the primary oracle-resolution path in `v0-4-market.clar` enforces. A low-confidence (wide-spread, unreliable) Pyth quote — one that would be rejected by `check-confidence` in the market contract — is accepted uncritically in `v0-1-data.clar`.

### Impact Explanation
This lands in scope as a data-path integrity flaw feeding a health/liquidation verdict computation with an unfiltered price, i.e., "confidence gating" missing on a pricing path that determines `is-liquidatable`/`health-factor`. If this data contract's output is relied upon (directly or by any off-chain/on-chain consumer) to decide whether a position is liquidatable, an attacker or a stale/low-confidence oracle tick could cause `is-liquidatable` to be computed incorrectly (true when it should be false, or vice versa), producing a wrong liquidation verdict and consequent theft or improper freezing of user funds if acted upon.

### Likelihood Explanation
Likelihood is moderate to low: it requires a genuine low-confidence Pyth update (something Pyth itself can emit during volatile conditions) to occur while this specific helper's output is being consulted for a liquidation-relevant decision, rather than the canonical `resolve-pyth` path in `v0-4-market.clar`. Whether this parallel data path is used purely as a read-only reporting/UI helper or is actually consumed for on-chain-relevant decisions could not be fully confirmed from the code reviewed — no caller other than the contract's own read-only endpoints was located.

### Recommendation
Route `get-pyth-price` in `v0-1-data.clar` (and its duplicate in `protocol-data.clar`) through the same `check-confidence` gate used in `v0-4-market.clar`'s `resolve-pyth`, or better, have this utility contract delegate price resolution entirely to the market contract's public price-resolution entry point rather than maintaining a second, divergent implementation that can silently drift out of sync with the security checks in the canonical path.

### Proof of Concept
1. Pyth publishes an STX/USD update with a legitimate `price` but an abnormally wide `conf` (confidence interval) — a scenario `check-confidence` in `v0-4-market.clar` would reject via `ERR-PRICE-CONFIDENCE-LOW`.
2. A call to `v0-4-market.clar`'s price-resolution path for STX correctly reverts/rejects this price.
3. A call to `v0-1-data.clar`'s `get-asset-price`/`sum-collateral-usd`/`sum-debt-usd` (e.g., via the health-factor read-only endpoint) for the same feed succeeds and returns a `health-factor`/`is-liquidatable` verdict computed from the unfiltered low-confidence price, since `get-pyth-price` never inspects `conf`.
4. Any downstream consumer of `v0-1-data.clar`'s health/liquidatable output receives a verdict inconsistent with, and potentially contradicting, what the protected `market.clar` path would have produced.

(define-private (resolve-pyth (ident (buff 32)))
  (let ((response (try! (call-pyth ident)))
        (price (get price response))
        (expo (get expo response))
        (conf (get conf response))
        (final-price (normalize-pyth price expo))
        (timestamp (get publish-time response)))

    (ok { value: final-price, timestamp: timestamp })))

;; Helper: Get asset price from oracles
;; Returns price in 8 decimal precision (e.g., $1.00 = 100000000)
;; Handles all asset types: underlying, stSTX (with ratio), and zTokens (with liquidity index)
(define-private (get-asset-price (aid uint))
  ;; STX - Pyth oracle
  (if (is-eq aid STX) (default-to u0 (get-pyth-price PYTH-STX))
  ;; sBTC - Pyth oracle (BTC price)
  (if (is-eq aid sBTC) (default-to u0 (get-pyth-price PYTH-BTC))
  ;; stSTX - STX price x stSTX ratio
  (if (is-eq aid stSTX) 
      (let ((stx-price (default-to u0 (get-pyth-price PYTH-STX)))
            (ratio (unwrap-panic (get-ststx-ratio))))
        (mul-div-down stx-price ratio STSTX-RATIO-DECIMALS))
  ;; USDC - Pyth oracle
  (if (is-eq aid USDC) (default-to u0 (get-pyth-price PYTH-USDC))
  ;; USDH - DIA oracle
  (if (is-eq aid USDH) (default-to u0 (get-dia-price DIA-USDH))
  ;; zSTX - STX price x liquidity index
  (if (is-eq aid zSTX)
      (let ((stx-price (default-to u0 (get-pyth-price PYTH-STX)))
            (lindex (get-vault-liquidity-index STX)))
        (mul-div-down stx-price lindex INDEX-PRECISION))
  ;; zsBTC - BTC price x liquidity index
  (if (is-eq aid zsBTC)
      (let ((btc-price (default-to u0 (get-pyth-price PYTH-BTC)))
            (lindex (get-vault-liquidity-index sBTC)))
        (mul-div-down btc-price lindex INDEX-PRECISION))
  ;; zstSTX - stSTX price x liquidity index (stSTX already includes ratio)
  (if (is-eq aid zstSTX)
      (let ((stx-price (default-to u0 (get-pyth-price PYTH-STX)))
            (ratio (unwrap-panic (get-ststx-ratio)))
            (ststx-price (mul-div-down stx-price ratio STSTX-RATIO-DECIMALS))
            (lindex (get-vault-liquidity-index stSTX)))
        (mul-div-down ststx-price lindex INDEX-PRECISION))
  ;; zUSDC - USDC price x liquidity index
  (if (is-eq aid zUSDC)
      (let ((usdc-price (default-to u0 (get-pyth-price PYTH-USDC)))
            (lindex (get-vault-liquidity-index USDC)))
        (mul-div-down usdc-price lindex INDEX-PRECISION))
  ;; zUSDH - USDH price x liquidity index
  (if (is-eq aid zUSDH)
      (let ((usdh-price (default-to u0 (get-dia-price DIA-USDH)))
            (lindex (get-vault-liquidity-index USDH)))
        (mul-div-down usdh-price lindex INDEX-PRECISION))

  (if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
  ;; zstSTXbtc - stSTXbtc price x liquidity index
  (if (is-eq aid zstSTXbtc)

            (lindex (get-vault-liquidity-index stSTXbtc)))
        (mul-div-down btc-price lindex INDEX-PRECISION))
