### Title
Direct-transfer donation of a staking token permanently dilutes `accMGPPerShare` via `_calLpSupply()` balance-based denominator - (File: rewards/MasterMagpie.sol)

### Summary
`_calLpSupply()` uses `IERC20(_stakingToken).balanceOf(address(this))` as the reward denominator for every pool except the `vlmgp`/`mWomSV` special cases. Since deposits/withdrawals move the real staking token but any unprivileged actor can also `transfer()` the same token straight into `MasterMagpie` without calling `deposit()`, an attacker can permanently inflate the denominator used in `updatePool()`/`massUpdatePools()`, diluting the MGP-per-second emission credited to legitimate, `UserInfo`-tracked stakers forever.

### Finding Description
`updatePool()` computes:
```solidity
uint256 lpSupply = _calLpSupply(_stakingToken);
...
uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
``` [1](#0-0) 

and
```solidity
function _calLpSupply(address _stakingToken) internal view returns (uint256) {
    if (_stakingToken == address(vlmgp)) { return IERC20(address(vlmgp)).totalSupply(); }
    if (_stakingToken == address(mWomSV)) { return IERC20(address(mWomSV)).totalSupply(); }
    return IERC20(_stakingToken).balanceOf(address(this));
}
``` [2](#0-1) 

`mgpReward` is a fixed quantity per second, computed purely from elapsed time, `mgpPerSec`, and `allocPoint`/`totalAllocPoint` — it is independent of `lpSupply`. Dividing it by an artificially inflated `lpSupply` (via a raw ERC20 `transfer` of the staking token into the contract, bypassing `deposit()`/`depositFor()`) permanently shrinks the per-share increment credited on every subsequent `updatePool` call, for as long as the donated balance remains in the contract. Because the deposit path is the only mechanism that credits `UserInfo.amount` [3](#0-2) , and withdrawal only ever moves out amounts tracked in `UserInfo` [4](#0-3) , the donated tokens can never be reclaimed by anyone and the balance-based denominator remains permanently inflated.

Regarding the specific invariant framed in the question — "`tokenToPoolInfo[_stakingToken].lastRewardTimestamp` must stay reconciled with `block.timestamp`" — `updatePool()` unconditionally sets `pool.lastRewardTimestamp = block.timestamp` whenever `lpSupply != 0` [1](#0-0) , so this specific timestamp-reconciliation check is **not** broken by the donation; a single `massUpdatePools()` call versus split calls will produce identical final `lastRewardTimestamp` values in both scenarios (only the intermediate multiplier segmentation differs, and the sum of multipliers is the same). The real, exploitable defect is the permanent dilution of `accMGPPerShare` growth for genuine stakers, not a timestamp divergence.

MGP is distributed via `IERC20(mgp).safeTransfer` in `_sendMGP`/`_sendMGPForVlMGPPool` [5](#0-4)  based only on the `accMGPPerShare`-derived `claimableMgp` computed in `_multiClaim` [6](#0-5) ; it is not minted on-the-fly. So the diluted portion of `mgpReward` is never transferred to anyone — it is a bookkeeping under-credit relative to what the emission schedule nominally allocates for that time window, and once `lastRewardTimestamp` advances past that window, that under-credited amount can never be recovered by legitimate stakers for that period.

### Impact Explanation
Any unprivileged address can transfer even a small amount of a pool's staking token directly to `MasterMagpie` to inflate `_calLpSupply()`'s balance-based denominator. This permanently and irreversibly reduces the `accMGPPerShare` increment attributable to legitimate depositors for every future `updatePool()` call on that pool, since the donated balance is never returned or credited to `UserInfo`. This matches "Permanent freezing/loss of unclaimed yield" for legitimate stakers, since MGP nominally allocated to the pool by the time-based emission formula becomes permanently under-distributed relative to what stakers would have earned absent the donation.

### Likelihood Explanation
This requires no privileged role — any EOA holding some of the target pool's staking token (an ERC20 receipt/LP token) can call `IERC20(stakingToken).transfer(masterMagpie, amount)` directly, bypassing `deposit()`. The precondition described (fresh unpause with `lastRewardTimestamp` far behind `block.timestamp`) simply maximizes the single-shot dilution effect by concentrating a large `multiplier * mgpReward` over an artificially inflated denominator in one `updatePool` call, but the underlying dilution mechanism (balance-based `_calLpSupply`) works at any time and is fully repeatable — an attacker/griefer can keep donating small amounts over time to progressively worsen the dilution at relatively low capital cost (the donated tokens themselves are lost to the attacker, making this a costly griefing vector rather than a profit-motivated theft, which should be noted when assessing real-world likelihood).

### Recommendation
Do not use `balanceOf(address(this))` as the reward-share denominator. Track staking-token supply explicitly (e.g., a `pool.totalStaked` counter incremented/decremented only in `_deposit`/`_withdraw`), and use that internal counter in `_calLpSupply()` instead of the raw ERC20 balance, so unsolicited transfers cannot influence `accMGPPerShare` computations.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `MGP`, a mock ERC20 staking token, register a pool with `add()`, fund the contract with enough MGP for emissions, set `mgpPerSec` and unpause.
2. User A deposits `1000` staking tokens via `deposit()`.
3. Advance time by `T` seconds (do not call `updatePool`).
4. Branch 1 (baseline): call `updatePool(stakingToken)`; record `pool.accMGPPerShare` and A's `pendingTokens()`.
5. Branch 2 (attack), starting from same state before step 4: an unprivileged attacker calls `stakingToken.transfer(masterMagpie, 1_000_000)` (large relative to the 1000 staked) without calling `deposit()`; then call `updatePool(stakingToken)`.
6. Assert: in Branch 2, `pool.accMGPPerShare` increment and A's `pendingTokens()`/claimable MGP after the same elapsed time `T` are drastically smaller than in Branch 1, despite identical `mgpPerSec`, `allocPoint`, and elapsed time — demonstrating permanent yield dilution.
7. Assert: `pool.lastRewardTimestamp == block.timestamp` in both branches (confirming the timestamp-reconciliation invariant itself holds; the actual bug is the share-price/yield dilution, not a timestamp divergence).
8. Confirm the attacker's donated tokens cannot be withdrawn by anyone (no `UserInfo` entry credited), and that A cannot later recover the diluted yield differential even after further `updatePool` calls.

    function _multiClaim(address[] calldata _stakingTokens, address _user, address _receiver, address[][] memory _rewardTokens) internal nonReentrant {
        uint256 length = _stakingTokens.length;
        if (length != _rewardTokens.length) revert LengthMismatch();

        uint256 vlMGPPoolAmount;
        uint256 mWOmPoolAmount;
        uint256 defaultPoolAmount;

        for (uint256 i = 0; i < length; ++i) {
            address _stakingToken = _stakingTokens[i];
            UserInfo storage user = userInfo[_stakingToken][_user];
            
            updatePool(_stakingToken);
            uint256 claimableMgp = _calNewMGP(_stakingToken, _user) + unClaimedMgp[_stakingToken][_user];

            if (_stakingToken == address(vlmgp)) {
                vlMGPPoolAmount += claimableMgp;
            } else if (MPGRewardPool[_stakingToken]) {
                mWOmPoolAmount += claimableMgp;
            } else {
                defaultPoolAmount += claimableMgp;
            }

            unClaimedMgp[_stakingToken][_user] = 0;
            user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
            _claimBaseRewarder(_stakingToken, _user, _receiver, _rewardTokens[i]);
        }

        if (vlMGPPoolAmount > 0) {
            _sendMGPForVlMGPPool(_user, _receiver, vlMGPPoolAmount);
        }

        if (mWOmPoolAmount > 0) {
            _sendMGP(_user, _receiver, mWOmPoolAmount);
        }

        if (defaultPoolAmount > 0) {
            _sendVlMGPFor(_user, _receiver, defaultPoolAmount);
        }

        uint256 totalReward = vlMGPPoolAmount + mWOmPoolAmount + defaultPoolAmount;

        if (totalReward > 0 && referral != address(0)) {
            IReferralStorage(referral).trigger(_user, totalReward);
        }
    }
