### Title
`SignableTransaction::new` excludes the OP_RETURN output from the fee/weight calculation, so transactions carrying `data` pay a lower fee rate than requested and can be unrelayable or over the standard-weight limit - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Tokemak report describes a value-transfer path that fails because required resources (ETH protocol fee) were not attached and leftover value could not be received — causing the operation to revert and funds to be stuck. The direct analog in Serai is `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: the size/weight used to compute the transaction fee and the standardness check is derived only from `payments` and `change`, while an extra output (`OP_RETURN` carrying `data`) is pushed onto the real transaction but never included in `calculate_weight_vbytes`. The transaction therefore underpays relative to the requested `fee_per_vbyte`, and the final weight check passes even though the true transaction is heavier.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is appended to `tx_outs` at `send.rs:194-202`, before the weight/vbyte calculation:

```rust
// send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

// send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` reconstructs a mock `Transaction` from `inputs`, `payments`, and `change` only (`send.rs:62-99`). It is called twice — at line 204 (no change) and inside the change branch at line 226 — and in both cases the `OP_RETURN` output is omitted. Consequently:

- `vbytes`/`vbytes_with_change` are under-estimates, so `needed_fee = fee_per_vbyte * vbytes` is smaller than `fee_per_vbyte * actual_vsize`.
- The minimum-relay-fee check at `send.rs:211` uses the under-estimated `vbytes`, so a transaction whose true fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` can pass the check.
- The `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` uses the under-estimated `weight`, so a transaction that is actually non-standard (over 400,000 WU) can be constructed.

A caller (e.g. the processor path in `processor/src/networks/bitcoin.rs::make_signable_transaction`) supplies `fee_per_vbyte` and expects the signed TX to meet that rate; since the fee is fixed at construction (`fee() = sum(inputs) - sum(outputs)`), the shortfall cannot be corrected later — mirroring the unpayable `swap()` call that could never attach the required ETH.

### Impact Explanation
An attacker does not need privileges: any flow that produces a `SignableTransaction` with `data` set (the 80-byte OP_RETURN path) yields a transaction whose real sat/vbyte is below the requested rate — by up to ~`fee_per_vbyte * (OP_RETURN output size)` satoshis. At boundary fee rates this drops the real rate below the relay minimum, so the signed transaction is rejected by the network and the inputs (which may be threshold-controlled FROST/Taproot funds) are locked in an unbroadcastable plan — the same "revert / tokens stuck" impact as the original report. Similarly, a data-carrying transaction near the weight cap can exceed `MAX_STANDARD_TX_WEIGHT` and be non-standard despite passing the internal check.

### Likelihood Explanation
The trigger is any caller passing `Some(data)` to `SignableTransaction::new` together with a fee rate or size near the boundary. No malicious validator or collusion is required — the miscalculation is deterministic in the constructor itself. Severity is Medium: it causes temporary inability to spend inputs / stuck plans rather than direct theft, and only in the data-carrying path.

### Recommendation
Include the fully-built `tx_outs` (or a `payments`-plus-`data-output` view) in `calculate_weight_vbytes` so `vbytes`, `needed_fee`, the minimum-fee check, the change-value decision, and the `MAX_STANDARD_TX_WEIGHT` check all account for the `OP_RETURN` output. Alternatively, pass the data output into the mock transaction inside `calculate_weight_vbytes` (e.g. `change: Option<&ScriptBuf>, extra: Option<&ScriptBuf>`).

### Proof of Concept
Conceptual: call `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0; 80]), fee_per_vbyte)` where `inputs` is sized so `needed_fee` barely satisfies the minimum-fee check. The returned `SignableTransaction`'s actual vsize exceeds the computed `vbytes` by the serialized size of the `OP_RETURN` output (~90+ bytes of script push + 8-byte value + overhead → ~30 vbytes), so `fee()/actual_vsize < fee_per_vbyte`, and it may be below `DEFAULT_MIN_RELAY_TX_FEE` despite passing the `TooLowFee` check at `send.rs:211`. Likewise, padding `payments` so computed `weight` is just under `MAX_STANDARD_TX_WEIGHT` produces a real transaction over the limit once the `OP_RETURN` output is added.
