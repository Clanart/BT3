## Title
Stale per-repository session state (force-push / commit-hook flags) survives `_removeRepository` and is silently reused when the same repository is re-added via "Clone Again" - (File: `app/src/lib/stores/repository-state-cache.ts`)

### Summary
This is the closest verifiable Desktop analog to the ParaSpace `NFTFloorOracle` bug class: a per-identity cache that is supposed to be reset on logical "removal" of an entity, but instead only removes the top-level index entry while leaving nested/session state behind, so a later re-registration of the *same identity* silently reuses stale data.

In Desktop, `RepositoryStateCache` and `GitStoreCache` are both keyed by `Repository.hash`, and `Repository.hash` is derived from `path`, the local DB `id`, and the associated `GitHubRepository.hash` (plus a few UI flags) — not from the repository's actual on-disk/remote content: [1](#0-0) 

`_removeRepository` / `repositoriesStore.removeRepository` only deletes the Dexie row and clears the "tags to push" cache — it never purges `RepositoryStateCache` and only purges `GitStoreCache` in the unrelated "missing repository" branch of `_selectRepository`: [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`RepositoryStateCache` is a plain in-memory `Map<hash, IRepositoryState>` with no eviction on repository removal: [5](#0-4) 

`GitStoreCache` behaves the same way — it only removes an entry when explicitly told to (`.remove()`), which is not invoked from `_removeRepository`: [6](#0-5) [7](#0-6) 

Desktop has a built-in, fully natural user flow that reproduces exactly the "removed then added back" pattern from the report: when a repository goes missing, `missing-repository.tsx` offers a **"Clone Again"** button that re-clones the *same* `gitHubRepository.cloneURL` to the *same* `path`: [8](#0-7) [9](#0-8) 

Because `Repository.hash` is computed from `path + id + gitHubRepository.hash + missing + alias + …` rather than from repository content, a repository re-added this way can end up with the exact same hash it had before removal (same path, same GitHub repository identity). Neither `RepositoryStateCache` nor (in the normal, non-"missing"-repository-detected `_removeRepository` path) `GitStoreCache` is cleared for the old hash, so `RepositoryStateCache.get()` will return the previously-cached `IRepositoryState` object for the "new" repository instance instead of a freshly-initialized one from `getInitialRepositoryState()`: [10](#0-9) 

That cached object carries several session flags that are **not** part of the routine post-clone refresh and are therefore reused verbatim from the prior (removed) repository instance: `skipCommitHooks`, `allowEmptyCommit`, `signOffCommits`, `commitToAmend`, `changesState.conflictState`, `changesState.currentBranchProtected`, `changesState.currentRepoRulesInfo`, and `branchesState.forcePushBranches`: [11](#0-10) 

Only a subset of fields (`commitLookup`, `localCommitSHAs`, `localTags`, `aheadBehind`, `tagsToPush`, `remote`, `lastFetched`) are explicitly overwritten on refresh: [12](#0-11) 

This mirrors the report's core defect precisely: `_removeAsset()` deletes the top-level `assetFeederMap[_asset]` struct but leaves the nested `feederPrice` mapping behind, so `_addAsset()` for the same key silently reuses stale, unvetted data. Here, `_removeRepository()` deletes the top-level DB row but leaves the nested in-memory `RepositoryStateCache`/`GitStoreCache` entries behind, so a repository re-added under the same hash silently reuses stale, unvetted session flags.

### Impact Explanation
If a user removes a repository (for example because they suspect it's compromised, or because the folder disappeared) and then uses the built-in "Clone Again" action to re-fetch it, any session-only safety flags from the prior instance are silently carried forward:
- `skipCommitHooks: true` would keep pre-commit/pre-push hooks (e.g. secret-scanning or lint hooks) disabled for the "new" clone without any UI indication that hooks are being skipped.
- `forcePushBranches` stale entries (or the absence of a freshly-computed protected-branch marker via `currentBranchProtected`/`currentRepoRulesInfo`) can cause Desktop's force-push confirmation logic to make decisions based on outdated protection status rather than the branch protection state of the freshly re-fetched repository.

Both scenarios fall squarely into "silent corruption of what the user commits or pushes," since the user has no visibility that these carried-over flags are stale and not derived from the current state of the re-added repository.

### Likelihood Explanation
The trigger path (`remove` → `Clone Again`) is a normal, documented Desktop UI flow requiring no local/physical access, no admin rights, and no prior host compromise — it is reachable purely through everyday interaction with a repository whose remote content or history the attacker controls (a malicious/compromised GitHub repository or clone target). The likelihood is bounded by the fact that `id` reuse and hash collision depend on Desktop's local Dexie ID allocation behavior across a remove/re-add cycle, which I was not able to fully verify in the remaining tool budget (i.e., I could not conclusively confirm from the index whether the local database ever reissues the same numeric `id` to a newly added repository row after a prior row with that path was deleted). This is the main open uncertainty limiting confidence from "likely" to "confirmed."

### Recommendation
- In `RepositoriesStore.removeRepository()` and/or `AppStore._removeRepository()`, explicitly purge the corresponding `RepositoryStateCache` entry and unconditionally call `GitStoreCache.remove(repository)` (not only in the "missing repository" branch), so no session state can outlive the DB row.
- Add a `remove(repository)` method to `RepositoryStateCache` (mirroring `GitStoreCache.remove`) and call it from every repository-removal code path, including `_removeRepository` and `_cloneAgain`'s pre-clone bookkeeping.
- Consider deriving `Repository.hash` (or at least gating cache reuse) from something that changes across removal/re-add cycles (e.g., a freshly generated in-memory session token), rather than relying solely on `path + id + gitHubRepository.hash`.

### Proof of Concept
1. Add a repository R backed by GitHub repo `owner/repo`; toggle `skipCommitHooks` (or otherwise put the repository into a state that sets `forcePushBranches`/`currentBranchProtected` in its cached `IRepositoryState`).
2. Remove R via `dispatcher.removeRepository` (this only calls `repositoriesStore.removeRepository`, which deletes the DB row and clears `tagsToPush`, but never touches `RepositoryStateCache`) — see [2](#0-1) .
3. From the "missing repository" screen, click "Clone Again", which re-clones the same `cloneURL` to the same `path` — see [9](#0-8) .
4. If the resulting `Repository` object hashes identically to the removed one, `RepositoryStateCache.get()` returns the pre-existing `IRepositoryState` object (see [10](#0-9) ), silently carrying over `skipCommitHooks`/`forcePushBranches`/`currentBranchProtected` from before the repository was removed, with no UI cue that this state is stale.

**Note:** I was unable to fully confirm, within the remaining investigation budget, whether Desktop's local repository ID allocation can actually reproduce an identical `Repository.hash` after a remove/re-add cycle in all cases; this should be verified with a live Devin session before treating this as a confirmed, weaponizable bug rather than a structural weakness.

export class RepositoryStateCache {
  private readonly repositoryState = new Map<string, IRepositoryState>()

  public constructor(private readonly statsStore: IStatsStore) {}

  /** Get the state for the repository. */
  public get(repository: Repository): IRepositoryState {
    const existing = this.repositoryState.get(repository.hash)
    if (existing != null) {
      return existing
    }

    const newItem = getInitialRepositoryState()
    this.repositoryState.set(repository.hash, newItem)
    return newItem
  }

export class GitStoreCache {
  /** GitStores keyed by their hash. */
  private readonly gitStores = new Map<string, GitStore>()

  public constructor(
    private readonly shell: IAppShell,
    private readonly statsStore: IStatsStore,
    private readonly onGitStoreUpdated: (
      repository: Repository,
      gitStore: GitStore
    ) => void,
    private readonly onDidError: (error: Error) => void
  ) {}

  public remove(repository: Repository) {
    if (this.gitStores.has(repository.hash)) {
      this.gitStores.delete(repository.hash)
    }
  }
