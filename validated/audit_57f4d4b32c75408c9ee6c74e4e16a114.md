### Title
Cross-chain `send()` truncates ERC20-denomination amounts to zero with no minimum-transfer guard, causing locked/burned funds with zero credited on the destination chain - ([File: modules/pallets/hyper-fungible-token/src/lib.rs], [File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The report's core broken invariant is: a fixed-point conversion between different decimal precisions is done with a naive integer division that can round a nonzero, economically meaningful amount down to `0`, while the surrounding code proceeds to consume/mint that truncated value as if it were valid — destroying user funds. `pallet-hyper-fungible-token::send()` reproduces exactly this pattern on the Substrate→EVM leg: `convert_to_erc20()` in `modules/pallets/hyper-fungible-token/src/impls.rs` and the receiving `convert_to_balance()` used in `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs`) perform plain multiply/divide decimal scaling with **no minimum-amount / representability check**, unlike the analogous `BandwidthManager.purchase()` (`evm/src/apps/BandwidthManager.sol:156-161`) which explicitly reverts with `PriceNotRepresentable()` when a scaled value would truncate.

### Finding Description
In `send()` (`modules/pallets/hyper-fungible-token/src/lib.rs:241-325`), a user's local asset is irrevocably locked (`NativeCurrency::transfer` / `Assets::transfer` / `Assets::burn_from`, lines 260-286) **before** the cross-chain amount is computed. The amount that is actually dispatched to the destination chain is: [1](#0-0) 

`convert_to_erc20()` scales up (multiplies), which is safe in this direction. The dangerous direction is the reverse conversion done on `on_accept` when tokens flow **EVM → Substrate**, via `convert_to_balance()`: [2](#0-1) 

This is a straight integer division `value / 10^(erc_decimals - local_decimals)` with no remainder check and no minimum-value guard — precisely the "premature division" pattern described in the source report. When `local_decimals` is small relative to `erc_decimals` (e.g., an 18-decimal EVM token bridging into a Substrate asset registered with far fewer decimals — the pallet only enforces `config.decimals >= local_decimals` at registration time in `register_token`/`update_token`, `modules/pallets/hyper-fungible-token/src/lib.rs:352-355`, `403-406`, not that conversions never truncate to zero), a nonzero but small ERC20 `amount` truncates to `0` local balance.

Critically, `on_accept` never checks the converted `amount` for zero before acting on it: [3](#0-2) 

`NativeCurrency::transfer(...,amount=0,...)` and `Assets::mint_into(...,0)` both succeed as no-ops rather than failing, so the ISMP message is accepted and considered successfully processed even though the beneficiary receives nothing.

### Impact Explanation
This is a direct, unauthorized loss of user funds during legitimate cross-chain settlement — exactly the "stealing or loss of funds" bounty category. A user who bridges tokens whose ERC20-side balance, once scaled down to `local_decimals` on the Substrate side, computes to `0` will have their tokens locked/burned on the EVM/source leg while receiving **zero** tokens on the destination leg. There is no revert path (unlike `BandwidthManager.purchase()`'s `PriceNotRepresentable()` guard), so the loss is silent and the request is marked delivered, closing off any timeout-based refund path since the message succeeded.

### Likelihood Explanation
This requires no privileged actor, relayer collusion, or malformed proof — an ordinary unprivileged user calling the public `send()` extrinsic with a small enough amount for a token pair with a wide decimals gap triggers it. Given `register_token`/`update_token` only require `erc_decimals >= local_decimals` (not equal, and with no bound on the gap), any governance-configured token pair with, say, `erc_decimals = 18` and `local_decimals = 6` or lower creates a wide truncation zone (any bridged amount below `10^(erc_decimals-local_decimals)` in ERC20 units becomes `0`). This is a realistic configuration for many real tokens (e.g., wrapped BTC-like assets bridging into a chain with a coarser-precision asset), so likelihood is high whenever such a token pairing exists.

### Recommendation
In `convert_to_balance()` (`modules/pallets/hyper-fungible-token/src/impls.rs`), reject conversions that truncate to zero from a nonzero input, and/or reject conversions where the input has a nonzero remainder below the local precision (mirroring `BandwidthManager`'s `PriceNotRepresentable()` pattern):
```rust
let scale = U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32));
if !value.is_zero() && value < scale {
    return Err(...); // reject dust that would round to zero
}
```
Propagate this as an explicit `HftError` (e.g., `AmountTooSmall`) so `on_accept` fails cleanly instead of silently minting/transferring zero, ensuring the ISMP message is treated as failed (enabling relayer/timeout handling) rather than falsely "successful."

### Proof of Concept
1. Governance registers an asset via `register_token` with `local_decimals = 6` and an EVM chain config `erc_decimals = 18` (allowed since `18 >= 6` passes the only check at `modules/pallets/hyper-fungible-token/src/lib.rs:352-355`).
2. On the EVM side, a user (or the pallet itself acting on an inbound message) sends a token amount of, e.g., `500_000_000_000` wei-equivalent (0.0000005 in 18-decimal terms) — nonzero, but less than `10^(18-6) = 10^12`.
3. In `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:84-91`), `convert_to_balance(value=5*10^11, erc_decimals=18, local_decimals=6)` computes `5*10^11 / 10^12 = 0` (integer division truncates).
4. `amount = 0` is passed to `NativeCurrency::transfer`/`Assets::mint_into` (lines 94-116), which succeed trivially.
5. The message is processed without error; `TokenReceived`/mint events show `amount = 0`; the corresponding locked/burned value on the source chain is permanently unrecoverable by the beneficiary.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
