### Title
Recursive clone explicitly disables Git's post-CVE-2024-32002 clone-protection guard, re-enabling submodule symlink/hook-injection RCE - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in GitHub Desktop always invokes `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'`. This variable is the internal signal Git itself uses to keep active the hardening added after CVE-2024-32002/CVE-2024-32004 (the "malicious repository can write outside the worktree via a symlinked/case-folded submodule `.git` directory during recursive clone" family of bugs, fixed across Git 2.39.4–2.45.1). By force-setting this flag to `false` for every clone Desktop performs, the app deliberately turns that upstream protection off, restoring the exact attacker path the fix was designed to close, for any repository a user clones via the GUI. [1](#0-0) 

### Finding Description
The relevant code path is: [2](#0-1) 

`envForRemoteOperation(url)` builds the normal environment for talking to the remote, and then the object literal unconditionally overrides/adds `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before `git clone --recursive -- url path` is executed via `git()` in `core.ts`. There is no branch, no user preference, and no per-repository trust decision gating this — it applies to every single `clone` call made from the Desktop UI, including cloning arbitrary/untrusted URLs entered by the user or opened via the `x-github-client://` protocol handler / "Open with GitHub Desktop" deep links (`openRepositoryFromUrl` in `app-store.ts`/`dispatcher.ts`).

The broken invariant, mirroring the Sherlock report's root cause (an operation is performed in an order/mode the underlying system was never designed to tolerate, silently defeating a safety check), is: Desktop is telling Git "the protections that guard recursive submodule cloning are not needed here," even though the whole point of `--recursive` clone is to pull in submodule content that is fully attacker-controlled (submodule URLs, `.gitmodules`, and nested repo layouts are all defined by the remote repository being cloned). The upstream Git fix relies on this flag being left in its default state so that Git can detect and refuse submodule checkouts whose paths would (via symlinks, case-insensitive/normalizing filesystems, or Unicode look-alikes) resolve into the top-level `.git` directory or another submodule's `.git` directory, which would let an attacker plant/overwrite hooks or config that later execute code or write files outside the intended repo tree. Setting the flag to `false` before invoking Git's own `--recursive` clone/submodule logic short-circuits that detection.

None of the other guards found in this codebase cover this gap:
- `isClonePathSensitive()` only checks the *destination directory* the user chose, not what the malicious repo's submodules do to the tree once fetched.
- `resolveWithin()`/`sanitizeCloneName()` (in `remote-parsing.ts`/`path.ts`) protect clone-path derivation from URL traversal and later file-open operations, not the recursive-clone-time write path controlled by Git's own submodule machinery.
- `updateSubmodulesAfterOperation()`'s `allowFileProtocol` flag only toggles `protocol.file.allow`, unrelated to this symlink/hook-planting class of bug. [3](#0-2) [4](#0-3) 

### Impact Explanation
If Git's `GIT_CLONE_PROTECTION_ACTIVE`-gated defenses are the only thing standing between a crafted recursive-submodule repository and writing/executing content outside the intended clone directory (the scenario the upstream CVE class addresses), disabling that flag for every Desktop clone means any attacker who gets a victim to clone their repository through Desktop (a normal, expected workflow — pasting a URL, clicking a GitHub "Open in Desktop" link, or opening a PR/branch deep link that triggers `openOrCloneRepository`) can potentially achieve file writes outside the repository root or code execution via planted hooks, without the user ever suspecting anything beyond "cloning a repo." This satisfies the requested impact bar: attacker controls the cloned repository, and the outcome is code execution / file write outside the repo, achieved silently during a normal clone.

### Likelihood Explanation
Likelihood is high for exposure (every recursive clone in Desktop takes this path unconditionally) but is bounded by how much of the underlying Git-level protection is actually still enforced when the flag is off — i.e., whether disabling `GIT_CLONE_PROTECTION_ACTIVE` fully reopens the original CVE-2024-32002/32004 class or only a subset of checks depends on the exact behavior of the bundled Git version, which could not be fully verified from the indexed sources (the bundled `dugite`/Git binary version and its exact use of this variable were not directly inspected). No comment, test, or changelog entry in this repo explains or justifies forcing this value to `'false'`, which is itself a red flag — legitimate reasons to intentionally disable a security-hardening env var this specific (added specifically for a submodule-clone CVE) are hard to justify for a general-purpose "clone any URL" feature.

### Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` and let Git use its default (protection-enabled) behavior for recursive clones.
- If this override exists to work around a specific compatibility problem (e.g., with certain legitimate nested/symlinked repo layouts), gate it behind an explicit, narrowly-scoped opt-in with a clear justification and code comment, and ensure it is never applied to first-time clones of untrusted remote URLs.
- Add a regression test that clones a crafted fixture repository containing a submodule whose path is a symlink/case-fold collision with `.git`, and assert that Desktop's clone refuses/warns rather than silently completing.
- Audit `updateSubmodulesAfterOperation` and other recursive-submodule call sites (`checkout.ts`, `pull.ts`) for the same environment variable to ensure the fix is applied consistently, not just in `clone.ts`.

### Proof of Concept
Full weaponization (an actual working malicious repository triggering RCE through the disabled protection) could not be constructed from the indexed code alone since it depends on the exact behavior of the bundled Git binary version. The concrete, verifiable evidence from local code is:

1. `clone()` always sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before running `git clone --recursive`: [5](#0-4) 

2. This function is reached from user-facing, attacker-influenceable entry points such as opening a repository from an external URL/deep link: [6](#0-5) 

3. No other guard in the codebase (`isClonePathSensitive`, `resolveWithin`, `sanitizeCloneName`) inspects or restricts what a malicious repository's own submodule definitions can do once `--recursive` clone begins, since those guards operate on the destination path and later file-open operations, not on Git's own submodule-checkout safety checks: [3](#0-2) 

To fully confirm exploitability, a Devin session with terminal access to build/run the bundled `dugite` Git binary and construct a submodule fixture repository (symlinked/case-colliding `.git` path) would be needed to reproduce the write-outside-repo condition end-to-end.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,

    '--recursive',
  ]
