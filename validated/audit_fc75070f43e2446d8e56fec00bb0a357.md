### Title
Missing Input-to-Deposit Binding in `send_move_to_vault_tx` Enables Deposit Metadata Corruption — (File: `core/src/rpc/aggregator.rs`)

### Summary
The `send_move_to_vault_tx` RPC handler validates the movetx's output structure but never verifies that `movetx.input[0].previous_output` matches the caller-supplied `deposit_outpoint`. Any TLS client can associate an arbitrary deposit outpoint with a structurally valid movetx, corrupting the tx-sender metadata and the bridge state machine's deposit tracking, which can permanently lock a victim's bridged BTC.

### Finding Description
`send_move_to_vault_tx` (lines 1973–2100 of `core/src/rpc/aggregator.rs`) performs three structural checks on the submitted movetx:

1. Exactly 1 input and 2 outputs
2. Output values: `bridge_amount` + 0-sat anchor
3. Output scriptpubkeys: vault taproot address + anchor scriptpubkey

After passing these checks, the transaction is queued in the tx-sender with:

```rust
TxMetadata {
    deposit_outpoint: Some(deposit_outpoint),   // taken verbatim from the RPC request
    tx_type: TransactionType::MoveToVault,
    ...
}
``` [1](#0-0) 

The `deposit_outpoint` field is taken directly from the RPC request and is **never cross-checked against `movetx.input[0].previous_output`**. The three output-side checks confirm the transaction looks like a movetx, but nothing binds it to the specific deposit UTXO it is supposed to spend. [2](#0-1) 

The aggregator server is configured with the `Noop` interceptor (no mTLS client-certificate enforcement), so any TLS client can invoke this RPC without holding an aggregator or operator certificate. [3](#0-2) 

### Impact Explanation
An attacker who has completed their own legitimate deposit ceremony (obtaining a valid signed movetx, `movetx_A`, that spends their own UTXO `outpoint_A`) can call:

```
send_move_to_vault_tx(raw_tx = movetx_A, deposit_outpoint = outpoint_B)
```

where `outpoint_B` is a victim's deposit outpoint observed on-chain. The tx-sender queues `movetx_A` with `deposit_outpoint = outpoint_B` in its metadata. When `movetx_A` confirms on-chain:

- The attacker's UTXO (`outpoint_A`) is spent; the attacker's BTC moves to the vault.
- The bridge state machine processes this confirmation as **deposit B being finalized**, because the metadata says `deposit_outpoint = outpoint_B`.
- The victim's actual movetx (`movetx_B`) is never queued or sent; `outpoint_B` remains unspent.
- The bridge believes deposit B is complete, so it will not re-attempt `movetx_B`.
- The victim's BTC is permanently locked in the deposit address with no corresponding L2 tokens minted.

The `deposit_outpoint` in `TxMetadata` is the sole identifier used by the state machine to correlate a confirmed movetx with a deposit record. [4](#0-3) 

### Likelihood Explanation
Medium. The attacker must be a legitimate bridge user to obtain a valid signed movetx (by completing their own deposit). No privileged keys, internal network access, or operator role is required. The aggregator server accepts connections from any TLS client, and victim deposit outpoints are publicly visible on the Bitcoin blockchain.

### Recommendation
Add an explicit binding check immediately after deserializing the movetx, before queuing it:

```rust
if movetx.input[0].previous_output != deposit_outpoint {
    return Err(Status::invalid_argument(
        "movetx input does not spend the claimed deposit_outpoint"
    ));
}
```

This ensures the submitted transaction actually spends the UTXO it claims to represent, closing the gap between the output-side structural checks and the input-side binding. [5](#0-4) 

### Proof of Concept
1. Attacker completes a legitimate deposit ceremony via `new_deposit`, receiving a valid signed `movetx_A` that spends `outpoint_A`.
2. Attacker observes the Bitcoin blockchain and identifies a victim's confirmed deposit UTXO `outpoint_B`.
3. Attacker opens a TLS connection to the aggregator server (no client certificate required) and calls:
   ```
   send_move_to_vault_tx(raw_tx = movetx_A, deposit_outpoint = outpoint_B)
   ```
4. The three output-side checks pass (correct structure, `bridge_amount`, vault scriptpubkey).
5. The tx-sender queues `movetx_A` with `TxMetadata { deposit_outpoint: outpoint_B, tx_type: MoveToVault }`.
6. `movetx_A` is broadcast and confirmed, spending `outpoint_A`.
7. The bridge state machine reads the metadata, concludes deposit B's movetx was confirmed, and marks deposit B as finalized.
8. `movetx_B` is never sent; `outpoint_B` remains unspent; the victim's BTC is permanently locked in the deposit address with no L2 tokens minted. [6](#0-5)
