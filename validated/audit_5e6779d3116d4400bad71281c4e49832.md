### Title
Permissionless registration of arbitrary ERC20 contracts allows fabricating token-pair-backed bank coins that bypass the balance-invariance check - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`MsgRegisterERC20` lets any account permissionlessly register an arbitrary, attacker-deployed ERC20 contract as a token pair when `PermissionlessRegistration` is enabled — which is the **default param value**. [1](#0-0) [2](#0-1)  Once registered, `convertERC20IntoCoinsForNativeToken` mints native bank coins based entirely on `balanceOf`/`transfer` return values queried from that same attacker-controlled contract, exactly the "trust the external contract's self-reported state" pattern from the Rubicon `withdrawForETH` report.

### Finding Description
The Rubicon bug trusted a caller-supplied, arbitrary contract (`targetPool`) to honestly report `balanceOf`/`transferFrom` results before releasing real value (ETH). The Cosmos EVM analog is `x/erc20`'s ERC20→Coin conversion flow:

1. `RegisterERC20` allows any signer to register any ERC20 address as a token pair without governance approval when `PermissionlessRegistration` is true (the default): [3](#0-2) , [2](#0-1) .
2. `convertERC20IntoCoinsForNativeToken` then queries `balanceOf` on the attacker's own contract, calls `transfer` on that same contract, and mints/sends bank coins based solely on the delta reported by that contract's own `balanceOf` return values: [4](#0-3) .
3. The only defense is an "invariance" check comparing `balanceTokenAfter` to `balanceToken + amount` — both values obtained via `k.BalanceOf`, which itself just calls into the attacker contract and blindly unpacks whatever it returns: [5](#0-4) .

Because the attacker fully controls the contract code, `balanceOf` can be implemented to always return `previous + amount` (or any attacker-chosen value) regardless of whether any real token movement occurred, and `transfer` can return `true` unconditionally or simply emit a fabricated `Transfer` event to satisfy the log-based fallback check. This lets the invariance check pass trivially while no genuine value is transferred, letting the caller mint bank coins for their chosen new denom (`erc20/<contractAddress>`) with no economic backing — matching the identical trust-the-callee-return-value flaw in the Rubicon report.

The repo does contain awareness of this bug class — test scaffolding exists for `ERC20DirectBalanceManipulation` and `ERC20MaliciousDelayed` contracts [6](#0-5) [7](#0-6)  — indicating the team has tested naive manipulation, but I could not confirm from the index whether these test contracts cover the specific "always self-consistent balanceOf" bypass described above (the balance-invariance check as implemented only compares two return values that are both fully attacker-controlled, so it cannot detect a self-consistent lie).

### Impact Explanation
If exploitable, this allows unauthorized minting of a bank-module coin under the `erc20/<contractAddress>` denom scheme, with the token-pair registration and metadata mechanism (identical to that used for legitimate registered ERC20s) giving the fabricated coin the appearance of being 1:1 backed by an escrowed ERC20 balance. This directly targets the "unauthorized minting ... duplication ... of token-pair-backed balances" critical impact category, since any downstream system (IBC transfer, DEX, lending/precompile integrations) that trusts x/erc20 token-pair coins as genuinely backed would be defrauded.

### Likelihood Explanation
Likelihood is uncertain without deeper verification. The permissionless-registration default and unprivileged trigger path are confirmed. However, I could not fully verify from the available index (1) whether the two `BalanceOf` calls are separated by state that an attacker cannot simply hardcode around (e.g., whether other tests like `ERC20DirectBalanceManipulation`/`ERC20MaliciousDelayed` already demonstrate and confirm this exact bypass fails or succeeds), and (2) whether the newly-minted denom for an attacker-chosen fresh contract has any exploitable "spendable value" consequence beyond the attacker's own wallet (since it's a brand-new denom they invented, real-world impact depends on whether other protocol components treat all `erc20/*` denoms as trustworthy).

### Recommendation
- Do not rely solely on the target contract's own `balanceOf`/`transfer` return values to gate minting. Where possible, cross-check against independently tracked escrow accounting, or require additional validation (e.g., ERC20 contracts registered permissionlessly should not be eligible for the native-Coin minting path without further vetting).
- Consider disabling `PermissionlessRegistration` by default, or restricting `ConvertERC20`/`ConvertCoinNativeERC20` mint paths to governance-vetted (`OWNER_MODULE`) token pairs only.
- Since the codebase already has `ERC20DirectBalanceManipulation`/`ERC20MaliciousDelayed` test fixtures, extend them to cover a "self-consistent liar" contract (one whose `balanceOf` always reports `prevReturnedValue + amount` regardless of true transfer) to confirm whether the current invariance check is actually bypassable.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to index limitations):
1. Attacker deploys a malicious ERC20 contract `Fake` where:
   - `balanceOf(addr)` returns a value stored in a mapping that the contract increments by `amount` on every `transfer` call regardless of real balances (i.e., it always "reports" as if the transfer succeeded).
   - `transfer(to, amount)` always returns `true` and emits a `Transfer` event, without maintaining any real backing.
2. Attacker calls `MsgRegisterERC20{Signer: attacker, Erc20Addresses: [Fake]}` — succeeds because `PermissionlessRegistration` defaults to `true`. [1](#0-0) 
3. Attacker calls `MsgConvertERC20{Amount: X, ContractAddress: Fake, Sender: attacker, Receiver: attacker}`.
4. `convertERC20IntoCoinsForNativeToken` queries `balanceOf` (pre), calls `transfer` (which just always reports success), queries `balanceOf` (post) — since `Fake.balanceOf` is designed to trivially satisfy `after == before + X`, the invariance check passes. [8](#0-7) 
5. Bank module mints and sends `X` coins of denom `erc20/<Fake>` to attacker, with zero genuine backing. [9](#0-8)

func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// BalanceOf queries an account's balance for a given ERC20 contract
func (k Keeper) BalanceOf(
	ctx sdk.Context,
	abi abi.ABI,
	contract, account common.Address,
) *big.Int {
	res, err := k.evmKeeper.CallEVM(ctx, abi, types.ModuleAddress, contract, false, nil, "balanceOf", account)
	if err != nil {
		return nil
	}

	unpacked, err := abi.Unpack("balanceOf", res.Ret)
	if err != nil || len(unpacked) == 0 {
		return nil
	}

	balance, ok := unpacked[0].(*big.Int)
	if !ok {
		return nil
	}

	return balance
}
