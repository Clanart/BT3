### Title
Cached FROST preprocess reused across distinct `set_keys_message` payloads within one DKG attempt enables nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to CVE-2017-15041 (where `go get` was tricked into *reusing* a previously materialized, attacker-influenced checkout in a context it did not belong to), the coordinator's `SigningProtocol` caches a deterministic FROST preprocess seed keyed only by `context = (b"DkgConfirmer", attempt)`. Every call to `share` / `complete` for that attempt re-derives the *same* nonces via `AlgorithmSignMachine::from_cache`, regardless of which `KeyPair` (i.e., which message) is being signed. If `share` is ever invoked twice under the same attempt with different `key_pair` values — or with a different `removed` set / participant mapping producing a different `msg` — the validator produces two Schnorr signature shares over different messages using identical nonces, allowing recovery of its MuSig secret key.

### Finding Description
`preprocess_internal` stores the preprocess seed in `CachedPreprocesses` keyed by `self.context`, and reuses it whenever the key exists (`signing_protocol.rs:123-145`). The cache key is only `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`). Neither the message (`set_keys_message(...)` built from `key_pair` and `removed` at `signing_protocol.rs:296-301`), nor the participant set, is part of the context.

`from_cache` deterministically re-derives nonces from the seed via `ChaCha20Rng::from_seed` and `Commitments::new` (`crypto/frost/src/sign.rs:121-143`, `from_cache` at `sign.rs:268-274`). `Commitments::new` calls `Curve::random_nonce(original_secret_share, rng)`, so the nonces depend only on the seed and the validator's secret share — not on the message or the cosigners' preprocesses.

`share_internal` then calls `machine.sign(preprocesses, msg)` (`signing_protocol.rs:156-180`). `DkgConfirmer::share` (`signing_protocol.rs:304-310`) and `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) each rebuild `msg` from whatever `key_pair` is passed in. Nothing enforces that only one distinct `key_pair` is signed per attempt; the file's own safety argument (lines 25-51) concedes nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again", and relies solely on BFT ordering plus a noted-but-unimplemented check ("we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)").

The CVE-2017-15041 mechanism — trusting a cached artifact whose provenance is not bound to the operation actually being performed — maps directly onto this cache: the seed cached for one confirmation is silently reused for a different confirmation message under the same attempt key.

### Impact Explanation
Two signature shares `s1 = k + c1*x_i` and `s2 = k + c2*x_i` over different `set_keys_message` payloads with the same nonce `k` yield `x_i = (s1 - s2)/(c1 - c2)`. Since these are MuSig shares of the *validator's own Ristretto key* (the root-of-trust key, `signing_protocol.rs:2-5`), the attacker recovers the validator's private key share — full compromise of that validator's signing identity, exceeding "key share recovery" severity.

### Likelihood Explanation
Trigger requires `share`/`complete` to be executed for two distinct `key_pair`s (or distinct `removed` sets) under one `attempt`. Whether multiple distinct `KeyPair` confirmations can be finalized within a single DKG attempt depends on caller logic in `coordinator/src/tributary/handle.rs` which I could not fully confirm in this pass; however, the code contains no guard preventing it, the designers explicitly flag the missing commitment-consistency check as TODO, and a participant who can influence which confirmation data is finalized (e.g., a processor submitting competing key shares) forces a distinct message. Because this path requires influence over finalized tributary data rather than mere public network inputs, likelihood is moderate.

### Recommendation
Bind the cached preprocess to the full signing instance: extend `context` to include the message digest (`set_keys_message` output) or the `KeyPair`, so a different message generates a fresh seed. Additionally, before publishing a share, verify on-chain that the preprocess commitments match what was decided for that context (the existing TODO), and refuse to `sign` a second distinct message under a consumed cache key.

### Proof of Concept
1. Attempt `a` reaches `share(preprocesses, key_pair_A)`; `preprocess_internal` stores seed `S` under `("DkgConfirmer", a)` and signs `msg_A = set_keys_message(set, removed, key_pair_A)` with nonce `k` derived from `S`, emitting share `s_A`.
2. A second finalized confirmation causes `share(preprocesses', key_pair_B)` (or `complete` with a differing `key_pair_B`) under the same attempt `a`. The cache hit at `signing_protocol.rs:137` reloads `S`; `from_cache`/`seeded_preprocess` reproduces the identical `k`.
3. `sign` emits `s_B` over `msg_B ≠ msg_A`. From the two published shares and the two public challenges, compute `x_i = (s_A - s_B)·(c_A - c_B)⁻¹`, recovering the validator's MuSig secret share — and hence its validator key, since MuSig aggregation of a single known share reveals the signing scalar.
