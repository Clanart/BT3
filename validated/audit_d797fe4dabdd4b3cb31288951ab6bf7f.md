### Title
Missing proof-of-possession / validation on the registered ECDH encryption key lets a participant register a degenerate key, making all secret shares addressed to them publicly decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The external report concerns a state-changing function (`setPoolActive`) that lacks the access control its documentation promises. The analog in Serai is `Decryption::register` / `EncryptionKeyMessage::read` in `crypto/dkg/pedpop`, which accepts a per-participant long-term encryption key (`enc_key`) from untrusted wire bytes and registers it as the ECDH recipient key for all subsequent `EncryptedMessage`s to that participant — with no proof of possession and no validity check (identity/small-order/canonicality) on the point. The codebase demonstrates it knows this control is necessary: the *ephemeral* per-message key inside `EncryptedMessage` carries a Schnorr PoP (`pop`) explicitly to prevent third-party abuse, yet the far more sensitive *registered* key has none.

### Finding Description
- `EncryptionKeyMessage::read` (encryption.rs:57-59) deserializes `enc_key` via `C::read_G` with no checks beyond raw point decoding.
- `Decryption::register` (encryption.rs:351-362) stores `msg.enc_key` in `enc_keys` unconditionally — no PoP, no identity/torsion rejection.
- `Encryption::encrypt` (encryption.rs:460-467, 135-168) derives the ChaCha20 stream key from `ecdh(key, to = enc_keys[participant]) = enc_key * k`. If `enc_key` is the identity element, the shared point is the identity for every message to that participant, so `cipher()` derives a key from publicly known bytes (`transcript(context || identity_bytes)`). Any passive observer of the wire can recompute the keystream and decrypt every `SecretShare` sent to that index.

This is precisely the reported bug class: a control the protocol requires (authenticate/validate who sets the recipient encryption key) is documented for one path but never codified for the other, and the unauthenticated input directly determines the security of downstream operations (share confidentiality), analogous to how the unauthenticated flag gates `withdraw`/`distribute`.

### Impact Explanation
A participant (or whoever controls the untrusted bytes fed into `EncryptionKeyMessage::read` for a given index) can publish `enc_key = identity` (or another degenerate/known-DL point such as `G` itself). Every other participant then encrypts their PedPoP secret shares for that index under a shared secret any observer can compute. The victim index's accumulated secret share `s_l = Σ f_i(l)` leaks to non-participants — direct secret-share/key-material leakage, the exact class of harm (unauthenticated party silently degrading a critical security property) as the report's pool toggling halting allocations. Because shares are encrypted individually per sender, *all* t share contributions to that index are exposed.

### Likelihood Explanation
The input path is fully attacker-controlled wire data (`EncryptionKeyMessage::read` → `register`, pedpop/src/lib.rs:315). The attack requires no collusion, no timing, and only publishing a malformed round-1 message — indistinguishable from a normal registration since nothing verifies the key. Confirmed absence of mitigation: the only assertion in `register` is duplicate re-registration (encryption.rs:356-359). Caveat: whether `C::read_G` rejects the identity point is ciphersuite-dependent and was not exhaustively verified for every in-scope ciphersuite; for the dalek-ff-group Edwards curves, standard decompression accepts the identity encoding. Even where identity is rejected, any low-order or attacker-known-DL point (e.g., `G`, enabling the registrar — and anyone the registrar tells — to decrypt) yields the same leak, which no check prevents.

### Recommendation
Require a Schnorr proof of possession over `enc_key` bound to `(context, participant, commitments)` at registration time — reusing the existing `pop_challenge`/`SchnorrSignature` machinery already used for ephemeral keys — and reject identity/small-order points in `Decryption::register`. Mirror the `EncryptedMessage.pop` pattern (encryption.rs:84-91) for the `EncryptionKeyMessage.enc_key` field.

### Proof of Concept
1. Participant `l` calls `KeyGenMachine::generate_coefficients`, then mutates the produced `EncryptionKeyMessage` to set `enc_key = C::G::identity()` (or serializes one directly via `EncryptionKeyMessage::read` on crafted bytes, since `read` performs no PoP/validity check).
2. All honest participants call `SecretShareMachine::generate_secret_shares` → `verify_r1` → `self.encryption.register(l, msg)` (lib.rs:315), which stores the identity key without complaint.
3. Each honest sender calls `encrypt(..., l, share)` → `ecdh(k, identity) = identity` → `cipher(context, identity)` produces a keystream derivable by anyone who knows the public `context`.
4. An observer reading the broadcast `EncryptedMessage`s to `l` applies the same keystream to `msg`, recovering every plaintext `SecretShare` and hence `l`'s full secret share — with no signature, no consensus position, and no detection, since the PoP over the ephemeral key still verifies correctly.
