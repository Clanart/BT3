### Title
Partial-line staging bypasses Git's line-ending/clean-filter normalization, causing silently corrupted commits - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines/hunks of a modified file (interactive partial staging), Desktop builds a patch straight from the raw bytes it read via `git diff` and injects it into the index with `git apply --cached`, instead of going through Git's normal add/normalize path. If the repository declares text normalization or a clean filter in `.gitattributes` (fully attacker-controlled content in a cloned/fetched repo, e.g. `* text=auto`), the partially-staged blob that actually gets committed silently differs from what a full `git add` of the same content — and from what the Changes diff shown to the user — would produce.

### Finding Description
`getWorkingDirectoryDiff` runs `git diff … HEAD` to build the diff shown in the UI, and separately inspects stderr for Git's own "line endings will be replaced" warning via `parseLineEndingsWarning`: [1](#0-0) [2](#0-1) 

That warning/state (`lineEndingsChange`) is only used to render an informational banner in the diff viewer: [3](#0-2) 

It is *not* consulted anywhere in the partial-staging path. When a file has a mixed selection (`DiffSelectionType` other than `All`), `stageFiles` routes it to `applyPatchToIndex` instead of a normal `git add`: [4](#0-3) 

`applyPatchToIndex` takes the raw hunk text from `getWorkingDirectoryDiff`, formats it with `formatPatch` (which copies `line.text` verbatim, byte for byte, from the working-tree diff), and applies it directly against the index with `git apply --cached --unidiff-zero --whitespace=nowarn -`: [5](#0-4) [6](#0-5) 

`git apply --cached` writes the patched blob straight into the index; it does not run the repository's configured `clean` filter, nor does it perform Git's usual working-tree→index line-ending renormalization the way `git add`/`update-index` (used for the "select all" path) does. So the two staging code paths in the very same function, `stageFiles`, can silently produce different index content for the same file depending only on whether the user selected "all" or "some" lines: [7](#0-6) 

The corrupted value here is the **staged/committed blob content** for any partially-selected hunk: the code treats the exact bytes captured from `git diff` as if they were already the final, normalized form that Git would write to an object, exactly as the Tapioca `_handleToftWrapToSender` code treated the requested `_amount` as the actual minted amount without accounting for the fee/transformation `wrap()` applies internally.

### Impact Explanation
This falls squarely in the "silent corruption of what the user commits or pushes" impact category. A user who clones a repository containing an attacker-authored `.gitattributes` (a completely ordinary, unprivileged repo file) and later does line-level (not whole-file) staging on a text file can end up committing content that differs from both (a) what the diff view showed them and (b) what would have been committed had they staged the whole file. Because `git apply --cached` silently succeeds (it's byte-exact for the parts it touches), there is no error, warning, or diff mismatch surfaced to the user — the corruption is invisible until later inspected with raw `git show`/`cat-file`.

### Likelihood Explanation
Interactive/partial hunk-and-line staging is a core, everyday Desktop feature (`applyPatchToIndex`/`formatPatch` are exercised by ordinary partial commits, as shown by the extensive test suite around them), and `.gitattributes`-based normalization/filters (`text=auto`, LFS-style clean filters, etc.) are extremely common in real-world repositories. No unusual local configuration, admin rights, or social engineering is required beyond the user opening a normal cloned repository and using the "select lines to commit" UI, which is a primary, advertised Desktop workflow.

### Recommendation
Route partial selections through the same normalization path full-file staging uses — e.g., write the constructed patch to a temp blob and stage it via `git add`/`hash-object --stdin -w` plus `update-index --cacheinfo`, or invoke `git apply --cached` together with the appropriate `--renormalize`/attribute-aware handling — so line-ending and clean-filter behavior is identical regardless of whether the user staged the whole file or only some lines. At minimum, detect when `.gitattributes` normalization or a clean filter applies to a file with a partial selection and either force a full-file stage or surface an explicit warning before committing.

### Proof of Concept
1. Attacker publishes/pushes a repository containing `.gitattributes` with `* text=auto` (or a `clean` filter definition plus a matching pattern).
2. Victim clones this repository in Desktop, then edits a text file locally introducing mixed CR/LF content (common when editing cross-platform or via certain editors) and stages only some of the new lines via the line-selection UI (not "select all").
3. `applyPatchToIndex`/`formatPatch` copy the raw bytes from `getWorkingDirectoryDiff` verbatim into a patch, which is applied with `git apply --cached`, bypassing the renormalization that `.gitattributes` would trigger for a normal `git add`.
4. The resulting commit's blob for that file differs from what `git add <file>` (or `git add -p` staged consistently with attributes) would have produced, and from what Desktop's own diff view displayed — the corruption is committed and pushed without any indication to the user.

const lineEndingsChangeRegex =
  /', (CRLF|CR|LF) will be replaced by (CRLF|CR|LF) the .*/

/**
 * Utility function for inspecting the stderr output for the line endings
 * warning that Git may report.
 *
 * @param error A buffer of binary text from a spawned process
 */
function parseLineEndingsWarning(error: Buffer): LineEndingsChange | undefined {
  if (error.length === 0) {
    return undefined
  }

  const errorText = error.toString('utf-8')
  const match = lineEndingsChangeRegex.exec(errorText)
  if (match) {
    const from = parseLineEndingText(match[1])
    const to = parseLineEndingText(match[2])
    if (from && to) {
      return { from, to }
    }
  }

  return undefined
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
