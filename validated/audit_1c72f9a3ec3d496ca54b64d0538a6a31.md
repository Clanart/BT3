### Title
SignableTransaction fee estimation omits the OP_RETURN data output, underestimating `needed_fee` and the actual paid fee rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the PerpDepository issue — where a fee formula valid only for one case (`isBaseToQuote == true`) was applied to all order directions, producing an incorrect `totalFeesPaid` in `getCurrentState` — `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` applies a weight/fee formula that only accounts for the payment outputs, while the actual signed transaction additionally contains an OP_RETURN data output. The result is an incorrectly computed `needed_fee` and an effective fee rate lower than the one requested, in exactly the case where `data` is supplied.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then appends an OP_RETURN output when `data` is provided (send.rs:194–202). However, the fee is computed from `calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204), which reconstructs a transaction containing only the payment outputs (send.rs:85–99) — the data output is never included in the weight/vbytes estimate. [1](#0-0) 

```rust
    // Add the OP_RETURN output
    if let Some(data) = data {
      tx_outs.push(TxOut { ... ScriptBuf::new_op_return(...) })
    }

    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
    let mut needed_fee = fee_per_vbyte * vbytes;
```

Inside `calculate_weight_vbytes`, only `payments` and an optional `change` output are serialized into the dummy transaction whose `weight()` is measured — there is no parameter for the data output (send.rs:62–99). [2](#0-1) 

Consequences, all stemming from the underestimated `vbytes`:

1. `needed_fee = fee_per_vbyte * vbytes` is too small by `fee_per_vbyte * vbytes(data_output)` — up to ~90+ vbytes for an 80-byte payload (output overhead + OP_RETURN script).
2. The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (send.rs:211) uses the same underestimated `vbytes`, so a transaction can pass this check while its real fee rate is below the relay minimum.
3. The `NotEnoughFunds` check `input_sat < payment_sat + needed_fee` (send.rs:215) uses the underestimated fee, so a transaction can be constructed and signed whose real fee (inputs − outputs) still equals only the underestimated `needed_fee` — the actual fee paid is `sum(inputs) - sum(outputs)` (send.rs:139–141), which is exactly `needed_fee` when there is no change output, i.e., lower per-vbyte than requested.
4. The `MAX_STANDARD_TX_WEIGHT` check (send.rs:241) uses the weight that excludes the data output, so an oversized transaction can be produced.

The final signed transaction therefore commits to a lower effective fee rate than `fee_per_vbyte` requested, and the caller-reported `needed_fee()` / `fee()` semantics are wrong whenever `data.is_some()` — a formula correct only for the no-data case applied to the data case, mirroring the PerpDepository bug where the `isBaseToQuote` fee formula was applied to all orders.

### Impact Explanation
When a `data` payload is supplied, the produced transaction pays a lower fee rate than requested and can fall below `DEFAULT_MIN_RELAY_TX_FEE` on its true vsize. Such a transaction will be rejected by Bitcoin relay policy: the threshold multisig signs a transaction that cannot be broadcast, and any funds it was meant to move are stuck until a new, properly-funded transaction is constructed and re-signed. It also lets the transaction silently exceed `MAX_STANDARD_TX_WEIGHT`, producing a non-standard, non-relayable transaction despite the explicit check. This matches the report's impact class: an incorrect fee/state calculation that produces a wrong economic outcome on an otherwise valid signed message.

### Likelihood Explanation
`SignableTransaction::new` accepts attacker/user-influenced `data` (up to 80 bytes) and `payments` as public inputs; the miscalculation is deterministic whenever `data.is_some()`, requiring no special timing or adversary cooperation. Note that the in-repo processor caller currently passes `None` for `data` (`processor/src/networks/bitcoin.rs:450`), so the practical severity is bounded by how the wallet library is consumed; the bug itself is unconditional on the `data` code path.

### Recommendation
Include the data output in the weight estimation. Either pass the fully assembled `tx_outs` (payments + OP_RETURN + potential change) into `calculate_weight_vbytes`, or add a `data_len`/`op_return_script` parameter so the dummy transaction mirrors the real output set:

```rust
// build the OP_RETURN script first, then estimate weight over
// payments + op_return (+ change), so vbytes matches the final tx
let (mut weight, vbytes) =
    Self::calculate_weight_vbytes(tx_ins.len(), &all_outputs_so_far, None);
```

The `needed_fee`, `TooLowFee`, `NotEnoughFunds`, and `MAX_STANDARD_TX_WEIGHT` checks must all use the vbytes/weight of the transaction as actually constructed, including the data output — analogous to the report's recommendation to use the fee value the clearing house actually charges rather than a formula valid for only one order direction.

### Proof of Concept
```rust
// In networks/bitcoin, with any valid input `output` and payment:
let data = vec![0u8; 80]; // max allowed
let tx = SignableTransaction::new(
    vec![output],
    &payments,
    None,               // no change: actual fee == needed_fee
    Some(data),
    fee_per_vbyte,
).unwrap();

// The signed transaction's true vsize includes the OP_RETURN output,
// but needed_fee() was computed on payments-only vbytes:
let true_vsize = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < true_vsize * fee_per_vbyte);
// => effective fee rate = needed_fee / true_vsize < fee_per_vbyte,
//    potentially below DEFAULT_MIN_RELAY_TX_FEE.
```
