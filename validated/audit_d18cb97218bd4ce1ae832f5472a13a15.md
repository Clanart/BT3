### Title
Unprivileged senders can make deposits resolve to internal output identities (Branch/Change/Forwarded), causing funds to be dropped or mis-attributed - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The NounsBuilder issue is an identity-aliasing bug: the same L1 sender resolves to two different L2 identities depending on which transport (OptimismPortal vs CrossDomainMessenger) delivered the message, so the second leg of a migration looks up a mapping keyed by a differently-computed identity and funds are lost. Serai's Bitcoin wallet exhibits the same bug class: the identity (`offset`, and hence `OutputType`) of a received output is resolved *solely* from the destination `script_pubkey`, and `register_offset` lets several distinct logical destinations converge onto scripts that any external party can compute and pay to. A sender paying to a "Forwarded", "Change", or "Branch" script gets classified as an internal output rather than an external deposit, so the funds are never credited as a deposit — and a `Forwarded` output keyed only by balance can prematurely consume a pending forwarding instruction.

### Finding Description
`Scanner` maps received outputs to identities purely via a `script_pubkey -> offset` table (`self.scripts.get(&output.script_pubkey)`), and `register_offset` publicly derives those scripts from `key + GENERATOR * offset`, incrementing the offset until an even-Y point is produced [1](#0-0) . The processor registers the Branch, Change, and Forwarded offsets with deterministic, publicly computable scalars (`hash_to_F(KEY_DST, b"branch")`, `b"change"`, `b"forward"`), so any Bitcoin user can derive these addresses for the known group key [2](#0-1) . On scan, the output kind is assigned solely from the matched offset — there is no distinction between "this output was created by us" and "an external party paid to this script" [3](#0-2) . Downstream, `Forwarded` outputs are consumed via `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` — keyed only by the amount — and non-`External` outputs are explicitly dropped from deposit reporting [4](#0-3) .

### Impact Explanation
Two concrete harms, both reachable by any unprivileged Bitcoin sender:

1. **Funds received but never credited/spendable**: BTC sent to the Change/Branch/Forwarded script is classified as an internal output. `Forwarded` outputs without a matching stored instruction are retained in neither the instruction flow nor the external-output set (the `retain` keeps only `External`), so a real deposit disappears from accounting — directly analogous to the report's lost migration funds [5](#0-4) .
2. **Forged forwarding evidence**: `take_forwarded_output` is keyed solely by `Balance`. An attacker who sends an output to the Forwarded address with an amount equal to a pending instruction's forwarded balance causes that instruction to fire prematurely/against the attacker's output, corrupting which InInstruction is considered executed [6](#0-5) .

### Likelihood Explanation
The offset scripts are deterministic functions of the public group key and fixed DST strings — no secret is needed to compute them. Any party (a depositor by mistake, or a griefer deliberately) can broadcast a transaction paying to those scripts. The Forwarded-consumption path additionally requires a pending forwarding instruction, which occurs routinely during multisig rotation (`RotationStep::ForwardFromExisting`).

### Recommendation
Bind internal outputs to provenance, not just script identity: for `Change`/`Forwarded`/`Branch` kinds, only treat the output as internal if the spending transaction was created by the multisig (e.g., require the tx to also spend a known input or be registered as an eventuality). Treat unexpected payments to internal offset scripts as `External` deposits (or explicitly refund/drop with logging). Additionally, key `ForwardedOutputDb` by the outpoint/txid of the expected forward rather than by balance alone.

### Proof of Concept
1. Multisig group key `K` is public. Attacker computes `forward_script = p2tr( K + G*hash_to_F("Serai Bitcoin Output Offset", "forward") )`, incrementing the scalar until even — replicating `scanner(key)` exactly [7](#0-6) .
2. During rotation, a pending instruction with forwarded balance `B` exists in `ForwardedOutputDb`.
3. Attacker broadcasts a tx paying `B` sats to `forward_script`. `get_outputs` classifies it `OutputType::Forwarded` via the script→offset→kind chain [8](#0-7) .
4. `take_forwarded_output(txn, B)` returns the pending instruction, which is pushed as executed — the attacker's output is treated as the multisig's own forward [6](#0-5) .
5. Alternatively, a depositor (or the attacker) pays to the Forwarded/Branch/Change script with no pending instruction: the output is neither retained as `External` nor produces an instruction — funds confirmed on-chain but absent from spendable accounting.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );
