### Title
Proof-of-possession check deferred while decryption proceeds unconditionally in `Encryption::decrypt` - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The reported bug class is a low-level call whose boolean success value is discarded, so execution continues as if the call succeeded. The direct Serai analog is `Encryption::decrypt` in the PedPoP DKG encryption layer: the sender's Schnorr proof-of-possession over the per-message encryption key is *queued* into an external `BatchVerifier`, but the function then performs ECDH, decrypts the message, and returns the plaintext plus an `EncryptionKeyProof` unconditionally — the verification result is not available (let alone checked) at the point the message is consumed. Any failure is only observable later if the caller separately drives the batch verifier and correctly maps the `batch_id` blame back to this message.

### Finding Description
`EncryptedMessage::read` accepts fully attacker-controlled bytes (`key`, `pop`, `msg`) from the DKG channel. In `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:469-501):

```rust
msg.pop.batch_verify(rng, batch, batch_id, msg.key,
  pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()));

let key = ecdh::<C>(&self.enc_key, msg.key);
cipher::<C>(self.context, &key).apply_keystream(msg.msg.as_mut().as_mut());
(msg.msg, EncryptionKeyProof { key, dleq: DLEqProof::prove(...) })
```

`batch_verify` only enqueues statements; `decrypt` then computes `ecdh` over the untrusted `msg.key`, decrypts the ciphertext, generates a DLEq proof of the ECDH key, and returns all of it. Nothing in this function branches on whether the PoP is valid — the boolean outcome lives entirely inside `batch`, owned by the caller. This is structurally identical to `(, results_[i]) = poolInfoUtils.call(callData)`: the fallible operation's status is dropped and downstream logic executes on the result regardless.

The consuming contract depends on the caller (1) actually calling `batch.verify_vartime_with_vartime_blame()` (or equivalent) on that verifier, (2) doing so *before* the returned plaintext share and `EncryptionKeyProof` are used in share verification or blame construction, and (3) treating a `batch_id` blame as "PoP failed → use `None` for the proof" per the in-code comment. If the batch is ever dropped, reused for a different purpose, or its result not propagated into the PedPoP state machine, a sender's message with an invalid PoP is decrypted and processed exactly as a valid one — the failure is silently ignored. I was not able to fully trace every PedPoP call site of `decrypt` to confirm the batch result is always consumed before the plaintext is; that is the open question determining exploitability.

### Impact Explanation
An unprivileged DKG participant can submit an `EncryptedMessage` carrying a forged/invalid PoP (e.g., replaying another participant's encryption key `key` — precisely the attack the PoP exists to prevent per the comment at lines 84-90). If the batch result is not enforced, the forged message decrypts and flows into share handling; downstream blame machinery (`decrypt_with_proof`, blame proofs revealing ECDH shared keys) can then be triggered on a message whose provenance was never authenticated, enabling the key-reuse/leak side effects the PoP was designed to stop. Worst case is attribution confusion and ECDH-key disclosure via blame proofs for messages the accuser never legitimately encrypted.

### Likelihood Explanation
Reachability is high: `EncryptedMessage::read` + `Encryption::decrypt` are reachable with purely public inputs from a DKG peer. The conditional element is caller-side enforcement of the batch verifier; the deferred-check pattern across an async/partitioned DKG message flow makes misuse plausible, and the code comment itself acknowledges the batch may be "reused," which is exactly when the PoP failure can be attributed to the wrong message or missed.

### Recommendation
Do not return usable plaintext before the PoP is known-good. Either verify the PoP inline in `decrypt` (`if !msg.pop.verify(...) { return Err(...) }`, matching `decrypt_with_proof` at lines 374-379), or return a token/`PendingDecryption` that only releases the plaintext after the caller proves the batch verifier passed — making the unchecked-status state unrepresentable.

### Proof of Concept
1. As a malicious DKG participant, call `EncryptedMessage::read`-compatible serialization with `key` set to another participant's encryption key and a `pop` with `s = s + 1` (see `invalidate_pop`, lines 192-194) over arbitrary `msg` bytes; deliver it to a victim running PedPoP.
2. Victim calls `Encryption::decrypt` — it computes `ecdh(enc_key, msg.key)`, decrypts, and returns `(plaintext, EncryptionKeyProof)` with no error, despite the PoP being invalid; the only record of failure sits in `batch` under `batch_id`.
3. If the victim's batch verification is skipped, dropped, or misattributed, the forged message is accepted as decrypted input; alternatively the attacker elicits a blame path in which the victim reveals `proof.key` (the ECDH shared point) for an unauthenticated message — the side effect the PoP comment at lines 84-90 explicitly warns about.
