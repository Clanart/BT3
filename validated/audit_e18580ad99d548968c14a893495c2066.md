## Title
Reveal/Open file actions resolve attacker-controlled tracked symlinks outside the repository without the `resolveWithin` containment check - (File: `app/src/lib/app-shell.ts`)

### Summary
GitHub Desktop enforces a real-path-aware containment check (`resolveWithin`, which calls `realpath` on both the root and the resolved target and rejects anything that escapes the root after symlink resolution) in some places that turn a repository-relative path into a filesystem path — e.g. `openRepositoryFromUrl` in the dispatcher and the Copilot conflict-resolution writer in `app-store.ts`. However, the much more commonly used "reveal file" / "open file" / "open in external editor" code paths (`revealInFileManager` in `app/src/lib/app-shell.ts`, `openFile` in `app/src/ui/lib/open-file.ts`, and the various `Path.join(repository.path, file.path)` call sites in `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`, `app.tsx`) never call `resolveWithin`. They simply do `Path.join(repository.path, path)` and hand the resulting string to Electron's `shell.showItemInFolder`, `shell.openExternal(file://...)`, or the external editor launcher.

### Finding Description
`file.path` for a `WorkingDirectoryFileChange`/`CommittedFileChange` is attacker-controlled data: it comes straight from `git status`/`git show` output for a cloned or fetched repository. Git allows tracking symlinks (mode `120000`) as ordinary tree entries. A malicious repository can commit a symlink such as `evil -> /Users/victim/.ssh` (or any other sensitive/arbitrary absolute path) as a tracked entry. When the victim clones/opens the repository and any file inside that symlinked directory shows up in the changes list, commit history, PR "Files changed" view, or merge-conflict view, Desktop computes:

```
app/src/lib/app-shell.ts:61-64
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}

`Path.join` performs pure string concatenation/normalization; it never calls `realpath`, so it has no way to detect that one of the intermediate path segments is actually a symlink pointing outside the repository. This is the exact class of bug the codebase already knows about and mitigates elsewhere with `resolveWithin`:

```
app/src/lib/path.ts:64-71
  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null

but this same protection was never applied to the changes list / history / PR-files / conflict-resolution "reveal in file manager", "open with default program", or "open in external editor" actions, all of which take an attacker-influenced `file.path` and turn it into a filesystem path with plain `Path.join`.

### Impact Explanation
An attacker who can get a victim to clone, fetch, or open a crafted repository (a normal, unprivileged Desktop workflow — no local/physical access or malware required) can plant a tracked symlink pointing at any absolute path on the victim's machine. When the victim right-clicks a file under that symlinked path and chooses "Reveal in File Manager," "Open with Default Program," or "Open in [external editor]," Desktop resolves and opens a location entirely of the attacker's choosing, outside the repository's boundary. This can expose sensitive files/directories (e.g., `~/.ssh`, `~/.aws`, browser profile directories) to the victim's file manager, or, when combined with `openFile`'s `shell.openExternal('file://' + fullPath)` / the external-editor launcher, cause an attacker-chosen file elsewhere on disk to be opened/executed by its associated default handler. This matches the same "unchecked capability inherited from attacker-controlled input" root cause as the original freeze-authority report: a boundary/authority check that exists and is enforced elsewhere in the codebase is silently missing on this path, letting attacker-supplied data escape the trust boundary (the repository directory) that the rest of the application assumes is intact.

### Likelihood Explanation
Medium: it requires the victim to interact with a specific file's context menu inside a repository they've cloned/opened, but that is completely normal Desktop usage (the changes list, history view, and PR review view are core, frequently-used features), the symlink is a standard, freely committable git object, and no special repository permissions, non-standard user steps, or elevated OS privileges are needed on macOS/Linux (Windows requires Developer Mode or admin for symlink checkout, which is a platform limitation rather than a mitigation Desktop itself relies on).

### Recommendation
Route every place that turns a repository-relative `file.path`/status path into a filesystem path for `shell.showItemInFolder`, `shell.openExternal`, or external-editor invocation through the existing `resolveWithin` helper (as already done in `dispatcher.openRepositoryFromUrl` and the Copilot conflict-resolution writer), and refuse the action (with a clear error, mirroring `Prevented attempt to open path outside of the repository root`) whenever `resolveWithin` returns `null`. This should be applied at minimum to `revealInFileManager` (`app/src/lib/app-shell.ts`), `openFile` (`app/src/ui/lib/open-file.ts`), and the `Path.join(repository.path, file.path)` call sites in `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`, and `app.tsx`.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink entry, e.g. `git symlink-add evil ~/.ssh` (mode `120000`, target `/home/victim/.ssh` or any absolute path of interest), and commits it.
2. Attacker adds/commits (or leaves untracked) a file so that git status/log reports a path such as `evil/id_rsa` under the symlinked directory.
3. Victim clones the repository in GitHub Desktop (normal, unprivileged flow) and the symlink is materialized on disk by `git checkout` following normal git symlink semantics.
4. In the Changes list (or History / PR Files Changed view), the victim right-clicks the file shown at `evil/id_rsa` and selects "Reveal in Finder/Explorer" or "Open with Default Program."
5. `revealInFileManager`/`openFile` computes `Path.join(repository.path, 'evil/id_rsa')`, which the OS resolves through the symlink to `/home/victim/.ssh/id_rsa` — a location entirely outside the cloned repository — and reveals/opens it, with no `resolveWithin`/`realpath` check ever performed to catch the escape.
