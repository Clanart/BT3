### Title
Integer division truncation in `calc-liq-factor-exp` collapses non-integer-multiple `curve-exponent` values to the linear liquidation-factor branch - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`calc-liq-factor-exp` computes the liquidation-penalty scaling factor for the super-linear branch as `(/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))`, where `exp` is the egroup's `curve-exponent` in BPS units. Because Clarity division truncates, `(/ exp BPS)` for any `exp` strictly between `BPS` (10000) and `2*BPS` (20000) evaluates to `u1`, making the formula reduce to `factor^1 / BPS^0 = factor` — identical to the plain linear branch — instead of approximating the intended `factor^1.5` (or any other non-integer multiplier).

### Finding Description
The liquidation-factor computation is intended to give a super-linear penalty curve once a position's `current-ltv` passes `ltv-liq-partial`, scaling by `factor^(exp/BPS)`. Since Clarity's `pow` only accepts a `uint` exponent, the contract approximates the fractional power using `n = (/ exp BPS)` as an integer exponent and rescales by `BPS^(n-1)`. This is mathematically only a correct approximation when `exp` is an exact multiple of `BPS` (i.e., 10000, 20000, 30000, …, representing 1.0x, 2.0x, 3.0x, …). For any `curve-exponent` configured strictly between `BPS+1` and `2*BPS-1` (e.g. `15000` = 1.5x, a perfectly normal, intended DAO-configured curve steepness), integer division of `(/ exp BPS)` truncates to `u1`, so the "super-linear" branch silently computes `factor^1 / BPS^0 = factor`, i.e., exactly the linear branch's output. The liquidation-factor value that feeds into the liquidator's collateral seizure/bonus calculation is therefore wrong for the whole range `(BPS, 2*BPS)` (and similarly for `(2*BPS, 3*BPS)`, etc., where it truncates to a lower integer exponent than intended) — no subsequent gate (health check, slippage bound, price legality check) inspects or corrects this scaling factor, since it is a penalty-curve/economic parameter, not a price feed value.

### Impact Explanation
The error understates the liquidation-bonus growth exactly in the LTV band between `ltv-liq-partial` and `ltv-liq-full` whenever the DAO configures a non-integer-multiple `curve-exponent`. This benefits the borrower being liquidated (they retain more collateral than the curve design intends) and reduces the economic incentive for liquidators to act on positions in that intermediate risk band. If the bonus becomes too small relative to gas/price-risk, liquidators may decline to liquidate risky positions, allowing bad debt to accumulate — a protocol-insolvency risk. This falls under the Critical category (protocol insolvency) as defined in scope.

### Likelihood Explanation
This is not attacker-triggered manipulation; it is a deterministic contract-logic defect that manifests any time the DAO sets `curve-exponent` to a value that is not an exact multiple of `BPS` (10000) — e.g., 15000, 12500, 17500, 25000+1, etc. Since a fractional/non-integer curve steepness (1.5x, 1.25x, etc.) is a plausible and intended DAO configuration choice (not a misconfiguration), the bug will reproducibly occur for any position whose `current-ltv` falls in the partial-liquidation band under such a curve setting. No special capital or privileged access is required to trigger it — any liquidator interacting with `liquidate` on an affected position experiences the wrong factor.

### Recommendation
Rework `calc-liq-factor-exp` to correctly support fractional exponents, e.g. by using a fixed-point exponentiation/logarithm approximation (or restricting `curve-exponent` at the egroup-registration layer to only accept exact multiples of `BPS`, with an assertion/validation that rejects non-multiple values), so the on-chain math cannot silently truncate a configured super-linear curve into the linear branch.

### Proof of Concept
1. In a Clarinet simnet test, deploy/register an egroup with `curve-exponent = u15000` (1.5x) and standard `ltv-liq-partial` / `ltv-liq-full` thresholds.
2. Set up a borrower position and manipulate price/collateral so `current-ltv` lands strictly between `ltv-liq-partial` and `ltv-liq-full`.
3. Call `liquidate` (or directly call `calc-liq-factor-exp` if exposed as read-only/testable) with the resulting `factor` and `exp = u15000`.
4. Assert the returned value equals plain `factor` (linear branch output) rather than an approximation of `factor^1.5`.
5. Repeat with `curve-exponent = u20000` (exact multiple) and confirm the output differs, demonstrating the exponent-truncation discontinuity at non-multiple values.
