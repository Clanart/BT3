Based on my research, I found a valid unprivileged-wallet analog in `rewards/ReferralStorage.sol`. I was unable to fully trace how `MasterMagpie.sol` funds `ReferralStorage` with MGP tokens before calling `trigger()` (ran out of tool budget), so that specific interaction should be verified, but the core arithmetic flaw is directly supported by the code I examined.

### Title
Unbounded referral boost percentage can push (`tier.rewardPercentage` + `boosted`) above `DENOMINATOR`, causing referrer/referee rewards to be over-credited beyond the amount actually deposited - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.trigger()` computes the referrer/referee reward split as a fraction of `_amount` using `basic + boostesd`, where `basic` is capped at `DENOMINATOR` (10,000) via `setTier`, but `boostesd` (the boosted portion) has no such bound. Because there is no check that `basic + boostesd <= DENOMINATOR`, the combined percentage can exceed 100%, causing `refererAmount + refereeAmount` to exceed the `_amount` that was actually forwarded for that claim event, mirroring the reported bug class where two independently-restricted BPS-like values are not jointly bounded.

### Finding Description
`setTier` restricts `basic` (`tiers[tierId].rewardPercentage`) to be `<= DENOMINATOR`: [1](#0-0) 

However, the boosted factor computed for a referrer is unbounded relative to `DENOMINATOR`: [2](#0-1) 

`BoostPoint` is set once at initialization with no cap check against `DENOMINATOR`: [3](#0-2) 

In `trigger()`, `basic` and `boostesd` are summed without any combined-limit validation before being used to split `_amount` between referrer and referee: [4](#0-3) 

If `_calBoosted(_referer)` returns a value such that `basic + boostesd > DENOMINATOR` (which can happen whenever a referrer's `factor` is a large enough share of `totalBoostFactor`, e.g. when few other referrers have registered/locked, which any user can influence by locking/unlocking vlMGP through `VLMGP.lock`/`unlock`, triggering `updateTotalFactor`), then `refererPercentage + refereePercentage > DENOMINATOR`, and `refererAmount + refereeAmount > _amount`. This is the same root cause as the reported bug (`athleteBPS + fantiumBPS` unrestricted sum over the 10,000 base), except here it does not revert - it silently over-credits `rewardAmount` in storage, which is later paid out as real MGP via `claimReward`: [5](#0-4) 

### Impact Explanation
Because `trigger()` credits `rewardAmount` mappings that are independent of how much MGP was actually transferred into `ReferralStorage` for that specific claim, an inflated combined percentage lets referrer+referee jointly claim more MGP than was deposited for their referral event. Over repeated claims this drains the shared MGP balance held by `ReferralStorage`, which is used to pay out all referrers/referees — this can result in insufficient balance for other legitimate claimants (`claimReward` reverting for them) or effectively theft of other users' unclaimed referral rewards, satisfying "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
Reaching the vulnerable path is possible without any privileged role: `_calBoosted` depends on the ratio `factor / totalBoostFactor`, which changes purely as a function of ordinary users locking/unlocking vlMGP (`VLMGP.lock` → `IReferralStorage.updateTotalFactor`). A referrer with a comparatively large locked amount (especially early on, or if boost factor concentration occurs naturally) can end up with a `boostesd` large enough that `basic + boostesd` exceeds `DENOMINATOR`, especially if `setTier` has already set `basic` close to `DENOMINATOR` for a top tier. The exact `BoostPoint` value chosen by the admin at initialization directly affects likelihood — this part is admin-influenced (not caller-controlled), so while triggering the miscalculation doesn't require a malicious admin action, its magnitude/likelihood in production depends on how `BoostPoint` and tier percentages were configured, which I could not fully verify from the code available to me.

### Recommendation
Add a check in `trigger()` (or in `_calBoosted`) ensuring `basic + boostesd <= DENOMINATOR`, capping `boostesd` if necessary, e.g.:
```solidity
uint256 combined = basic + boostesd;
if (combined > DENOMINATOR) combined = DENOMINATOR;
```
and use `combined` in place of `basic + boostesd` for computing `refererPercentage`/`refereePercentage`.

### Proof of Concept
1. Admin calls `setTier(1, 10000)` giving tier 1 referrers a 100% base rate (a valid call per current bounds check). [1](#0-0) 
2. A referrer (ordinary user) locks a large amount of MGP into `VLMGP`, becoming the dominant (or sole) contributor to `totalBoostFactor`, so `_calBoosted(referrer)` returns a value close to `BoostPoint` (set by admin at init, e.g. 2000). [2](#0-1) 
3. A referee referred by this user claims a reward through `MasterMagpie`, which calls `ReferralStorage.trigger(referee, amount)`.
4. `basic (10000) + boostesd (~2000) = 12000 > DENOMINATOR`, so `refererAmount + refereeAmount = amount * 12000 / 10000 = 1.2 * amount`, crediting 20% more MGP than was actually provided for that event. [6](#0-5) 
5. Over repeated referee claims, `claimReward()` pays out the inflated `rewardAmount` from the shared MGP balance, eventually depleting funds owed to other referrers/referees. [5](#0-4) 

Note: I was not able to fully verify, within my available tool budget, how `MasterMagpie.sol` supplies MGP tokens to `ReferralStorage` before/at the time `trigger()` is called (i.e., whether `_amount` in `trigger` is fully pre-funded 1:1 or drawn from a shared pool), which affects the precise mechanics of the drain. This should be confirmed by reviewing `MasterMagpie.sol`'s calls into `ReferralStorage`. [7](#0-6)
