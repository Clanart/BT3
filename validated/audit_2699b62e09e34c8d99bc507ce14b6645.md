### Title
ReDoS in hookify's `_regex_match` allows an attacker-influenced value to stall a `PreToolUse` blocking rule past its hook timeout, bypassing the block - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The `hookify` plugin evaluates user-defined "block"/"warn" rules against tool-call fields (Bash `command`, Edit/Write `new_string`/`content`, etc.) using `re.search()` with attacker-influenceable text as the subject and an admin-authored pattern. If a configured rule's regex is vulnerable to catastrophic backtracking, a crafted value in the matched field can make the match hang past the hook's fixed timeout. Because the wrapping hook scripts are architected to fail open on any anomaly and the process is killed externally on timeout (not caught by the internal `try/except`), the intended "block" decision never gets emitted, and the dangerous tool call proceeds — the resource-exhaustion equivalent of the reported "force gas exhaustion to land in an unintended catch path" bug class.

### Finding Description
`RuleEngine._regex_match()` compiles the rule's `pattern` and calls `regex.search(text)` directly, with only `re.error` handled: [1](#0-0) 

`text` is produced by `_extract_field()`, which pulls straight from `tool_input` — e.g. a Bash `command` string, or the `new_string`/`content` of an `Edit`/`Write` call: [2](#0-1) 

These tool-input values are exactly the kind of data an attacker can influence indirectly (e.g., through prompt injection causing Claude to write a file or run a command containing attacker-chosen content), while the *pattern* side is whatever the project's `.claude/hookify.*.local.md` rule author wrote — commonly broad patterns intended to catch dangerous commands/secrets, which are exactly the kind of hand-written regexes prone to catastrophic backtracking (nested quantifiers like `(a+)+`, `(.*)+`, alternation with overlapping branches, etc.).

The `PreToolUse` hook entrypoint wraps rule evaluation in a broad `try/except Exception`, but that only guards in-process Python exceptions — it does nothing for a regex hang, which instead runs until the hook's configured `timeout` (10s) elapses and Claude Code kills the subprocess: [3](#0-2) [4](#0-3) 

Every hookify hook script is explicitly designed to fail open — "On any error, allow the operation" / "ALWAYS exit 0 - never block operations due to hook errors" — reinforcing that any non-completion of the hook (crash, exception, or externally-enforced timeout) results in no block decision being delivered for that tool call: [5](#0-4) 

This is structurally the same primitive as the Nouns Builder finding: an attacker manipulates a resource budget (there: EVM gas; here: the hook's wall-clock timeout) so that a code path meant to reach a normal/expected branch instead exits abnormally, and the abnormal-exit handling has an unintended, attacker-favorable security effect (there: forced pause; here: forced bypass of a configured block rule).

### Impact Explanation
If a project relies on hookify's `block` action (e.g., to prevent destructive `rm -rf`, credential exfiltration, or writes to sensitive paths) and the corresponding rule's regex is vulnerable to catastrophic backtracking, an attacker who can influence the matched tool-input field (directly, or indirectly via prompt injection steering Claude to embed a crafted string in a command/file write) can make the `PreToolUse` hook stall until it is killed by its timeout. Because the wrapper's design treats any non-delivery of a decision as "allow," the intended safety block silently fails to apply and the dangerous tool call executes anyway. This is a concrete `PreToolUse` hook-bypass leading to unauthorized command/file execution that the project explicitly configured to be blocked.

### Likelihood Explanation
Exploitability depends entirely on the specific regex patterns configured in a project's `.claude/hookify.*.local.md` files — this is not a vulnerability in a fixed, built-in check but in user-authored rules run through an unguarded `re.search`. Hand-written security regexes (especially ones intended to catch "dangerous patterns" generically) commonly contain nested-quantifier constructs susceptible to catastrophic backtracking, so the precondition is plausible but not guaranteed for any given deployment. The attack additionally requires the attacker to influence the value being matched (command text, file content, etc.), which in agentic use is realistic via prompt injection or untrusted file/web content that Claude incorporates into a tool call. Overall likelihood is comparable to the original Medium-severity Nouns finding: non-trivial precondition (a vulnerable regex must exist), but a real and predictable class of DoS/bypass once the precondition holds.

### Recommendation
- Enforce a hard per-match time budget for `_regex_match` (e.g., run the regex in a worker with `signal.alarm`/subprocess timeout, or use a linear-time regex engine such as `re2`/`regex` with a backtracking cap) and treat a timeout as "condition matched" (fail closed) rather than silently falling through.
- Statically lint hookify rule patterns for known catastrophic-backtracking constructs (nested quantifiers, ambiguous alternation) at rule-load time and warn/reject them, similar to the existing `re.error` handling.
- Change the fail-open philosophy for `PreToolUse` specifically: an incomplete/timed-out security check should default to **deny/ask**, not silently allow, since `PreToolUse` is the sole point enforcing configured `block` rules.
- Add an overall wall-clock ceiling inside `evaluate_rules` across all rules/conditions so one slow pattern cannot consume the entire hook timeout budget unnoticed.

### Proof of Concept
1. In a project, add `.claude/hookify.block-secrets.local.md`:
```
---
name: block-secrets
enabled: true
event: file
action: block
conditions:
  - field: new_text, operator: regex_match, pattern: "([A-Za-z0-9+/]+)+=" 
---
Blocked: possible secret material in write.
```
(Pattern shown is illustrative of a nested-quantifier construct prone to catastrophic backtracking against long non-matching input.)
2. Get Claude to perform an `Edit`/`Write` whose `new_string`/`content` contains a long attacker-supplied string engineered against that pattern (e.g., many repeated near-matching base64-like characters followed by a non-matching terminator) — such a string can be introduced via prompt injection from a fetched web page or file that Claude is asked to reproduce/write.
3. `RuleEngine._regex_match()` (`plugins/hookify/core/rule_engine.py:266-273`) calls `regex.search(text)`, which hangs due to backtracking.
4. The `PreToolUse` hook process (`plugins/hookify/hooks/pretooluse.py`) never reaches `print(json.dumps(result))`/`sys.exit(0)` within the hook's configured `timeout` (`plugins/hookify/hooks/hooks.json`, 10s) and is killed externally.
5. Because no `permissionDecision: deny` was returned before the timeout, the `Write`/`Edit` proceeds despite the configured `block` rule — the security control is bypassed via attacker-influenced resource exhaustion, analogous to forcing an unintended catch-path outcome in the original Nouns Builder `_createAuction` bug.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
