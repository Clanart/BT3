### Title
Windows "Open in Shell" command injection via attacker-controlled repository folder name - (File: `app/src/lib/shells/win32.ts`)

### Summary
GitHub Desktop's "Open in [Shell]" feature on Windows builds a single shell command line by naively string-interpolating the repository's local folder path into quoted arguments and then executes it with Node's `child_process.spawn(..., { shell: true })`. Because the folder name for a newly cloned repository is derived directly from the attacker-supplied clone URL (via `sanitizeCloneName`, which only strips path-traversal segments, not shell metacharacters), a malicious remote repository/URL can plant `&`, `|`, `^`, or `%` characters into the local directory name. When the victim later clicks "Open in Git Bash" / "Open in PowerShell" / "Open in Hyper" / etc. from Desktop's repository menu, those characters are executed as separate cmd.exe commands.

### Finding Description
`clone()` clones into a directory whose name is not chosen freely by the user in the default flow — it comes from `sanitizeCloneName()`, which only strips traversal components (`..`, `.`) and rejects only pure traversal names: [1](#0-0) 

This is called from the Clone dialog while resolving/parsing the identifier from an arbitrary, attacker-controlled clone URL/repo name, and the resulting directory becomes `repository.path`: [2](#0-1) 

`sanitizeCloneName` does not reject or escape characters such as `&`, `%`, `^`, `!`, `(`, `)`, all of which are legal in Windows filenames (only `<>:"/\|?*` are illegal). So a repository name like `demo&calc.exe&` from a Generic/custom git host survives sanitization and becomes the on-disk folder name.

Later, `Dispatcher.openShell` → `AppStore._openShell` → `launchShell` invoke the platform launcher with that raw folder path: [3](#0-2) [4](#0-3) [5](#0-4) 

On Windows, `Win32.launch()` builds command lines like this, all executed with `shell: true`: [6](#0-5) 

Each branch wraps `foundShell.path` in its own `"…"` quotes and then wraps `path` (the attacker-influenced folder path) in a *separate* `"…"` pair (e.g. `--cd="${path}"`, `--working-directory "${path}"`). Because Node's Windows `shell:true` execution funnels the whole joined string through `cmd.exe`, and `cmd.exe` toggles its "inside quotes" state on every literal `"` character it scans (parity-based, not nesting-based), the pre-existing quoted `foundShell.path` segment flips the parity such that the subsequent quoted `path` segment is effectively evaluated as *unquoted* from cmd's command-separator perspective. This means `&`, `|`, or `^` embedded in the folder name are interpreted by `cmd.exe` as command separators/escapes rather than literal path characters — classic Windows `shell:true`/quote-parity command injection.

Notably, the codebase already contains a hardened, purpose-built cmd/PowerShell/bash escaping module (`shell-escape.ts`) used for a different feature (fetching shell env vars for hooks), but `win32.ts`'s repository-shell launcher does **not** use it: [7](#0-6) 

This mirrors the structure of the original `meta-git` bug: user/attacker-controlled data (there, a clone URL; here, a repo-name-derived folder path) is formatted into a command string that is executed via a shell, without using the escaping utilities that exist elsewhere in the same codebase for exactly this class of problem.

### Impact Explanation
An attacker who controls a git remote (any clone URL, not limited to github.com, since Desktop's Generic clone tab accepts arbitrary URLs) can achieve arbitrary command execution on a victim's Windows machine, without the victim doing anything more than the completely ordinary GitHub Desktop workflow of cloning a repository and using the built-in "Open in Shell" menu entry. This is unprivileged remote code execution, matching the report's required impact class ("attacker controls a cloned/fetched repository ... resulting code execution").

### Likelihood Explanation
Medium. It requires: (1) attacker convinces victim to clone a URL/repo with a crafted name containing `&`/`|`/`^` (Generic clone tab imposes no GitHub-style naming restrictions), and (2) the victim later invokes "Open in Git Bash"/PowerShell/Hyper/Alacritty/Warp/WSL from that repository — a very common, expected action for developers. No special privileges, physical access, or pre-existing malware are needed; only the ordinary product feature flow.

### Recommendation
- Reject or replace shell-metacharacters (`&`, `|`, `^`, `%`, `!`, `<`, `>`) in `sanitizeCloneName()` output, not just path-traversal segments.
- In `app/src/lib/shells/win32.ts`, stop building `shell: true` command lines via raw string interpolation. Either avoid `shell: true` entirely (spawn the shell executable directly with an argument array, as is already done for most Linux/macOS launchers), or route all interpolated arguments through the existing `cmd`/`powershell` escaping functions in `app/src/lib/hooks/shell-escape.ts` before building the command string.

### Proof of Concept
1. Set up (or use) a git server/URL that serves an arbitrary repository whose owner/name resolves, through Desktop's URL parsing, to a `name` component such as `demo&calc.exe&`.
2. In GitHub Desktop, use "Clone repository" → Generic/URL tab, pasting the crafted clone URL. The clone succeeds into a local folder literally named `demo&calc.exe&` (via `sanitizeCloneName`/`Path.join`), since no character-level sanitization is applied.
3. Open the newly cloned repository in Desktop, then choose Repository → "Open in Git Bash" (or any other shell option that funnels `path` into a `shell:true` `spawn` call in `app/src/lib/shells/win32.ts`).
4. Due to the quote-parity issue in the generated `cmd.exe /d /s /c "..."` command line, `calc.exe` (or any attacker-chosen command) executes as a separate command instead of being treated as part of the literal folder path.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

/** Launch the given shell at the path. */
export async function launchShell(
  shell: AnyFoundShell,
  path: string,
  onError: (error: Error) => void
): Promise<void> {
  // We have to manually cast the wider `Shell` type into the platform-specific
  // type. This is less than ideal, but maybe the best we can do without
  // platform-specific build targets.
  const exists = await pathExists(shell.path)
  if (!exists) {
    const label = __DARWIN__ ? 'Settings' : 'Options'
    throw new ShellError(
      `Could not find executable for '${shell.shell}' at path '${shell.path}'.  Please open ${label} and select an available shell.`
    )
  }

  let cp: ChildProcess | null = null

  if (__DARWIN__) {
    cp = Darwin.launch(shell as FoundShell<Darwin.Shell>, path)
  } else if (__WIN32__) {
    cp = Win32.launch(shell as FoundShell<Win32.Shell>, path)
  } else if (__LINUX__) {
    cp = Linux.launch(shell as FoundShell<Linux.Shell>, path)
  }

  if (cp != null) {
    addErrorTracing(shell.shell, cp, onError)
    return Promise.resolve()
  } else {
    return Promise.reject(
      `Platform not currently supported for launching shells: ${process.platform}`
    )
  }
}

// https://github.com/ericcornelissen/shescape/blob/89072ba7de233f81f5553b52098671c94eb9bd0c/src/internal/win/cmd.js#L35
const cmdEscape = (arg: string) =>
  arg
    .replace(/[\0\u0008\r\u001B\u009B]/gu, '')
    .replace(/\n/gu, ' ')
    .replace(/"/gu, '""')
    .replace(/([%&<>^|])/gu, '"^$1"')
    .replace(/(?<!\\)(\\*)(?="|$)/gu, '$1$1')

export const cmd: Shell = {
  args: ['/d', '/s', '/c'],
  quoteCommand: (cmd, ...args) =>
    `"${[cmd, ...args].map(a => `"${cmdEscape(a)}"`).join(' ')}"`,
}
