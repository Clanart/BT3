### Title
Aggregator gRPC server enforces no client authentication, allowing an unauthenticated caller to invoke privileged, state-changing/broadcasting RPCs - (File: core/src/servers.rs, core/src/rpc/clementine.proto)

### Summary
The `ClementineVerifier` and `ClementineOperator` gRPC servers restrict every call to either the aggregator's own certificate or the entity's own certificate via the `Interceptors::OnlyAggregatorAndSelf` interceptor [1](#0-0) . The aggregator server, however, is documented and implemented to skip this check entirely: "The aggregator does not enforce client certificates but does use TLS for encryption" [2](#0-1) . This mirrors the external report's bug class — a privileged, state-changing entry point ("meant for" a specific caller, here the `clementine-backend` service) that any unauthenticated party reaching the endpoint can invoke, because the intermediary component (aggregator server, analogous to `Router_Adapter`) does not gate access to it.

### Finding Description
`create_aggregator_grpc_server` builds the aggregator's gRPC service and passes it through the same generic `create_grpc_server` helper used by verifier/operator, but the resulting `InterceptedService` only applies `OnlyAggregatorAndSelf` when `config.client_verification` is true [3](#0-2) . For the aggregator, this cert check restricts callers to holders of the aggregator's own client certificate — i.e., anyone possessing that one shared secret, but by design/documentation TLS client verification is not enforced for the aggregator at all, so any network-reachable client can complete the TLS handshake and issue RPCs [4](#0-3) .

The `ClementineAggregator` service exposes RPCs that are explicitly documented to be restricted to "the `clementine-backend` service" — i.e., a specific privileged party — but are not authenticated at all in code:
- `NewDeposit` — orchestrates the full N-of-N signing flow to produce a move-to-vault transaction [5](#0-4) 
- `Withdraw` / `OptimisticPayout` — trigger operator reimbursement/payout flows [6](#0-5) 
- `InternalSendTx` and `SendMoveToVaultTx` — broadcast pre-signed, privileged transactions to the Bitcoin network [7](#0-6) 

This is the direct analog of the report's binding-break pattern: "a caller reaching a signing or state-changing method versus the party it is meant for." In `ForwarderBase`/`Router_Adapter`, the problem was that the intermediary contract provided no way to reach privileged functions for the intended admin. Here the inverse but equally invalid binding exists: the intermediary (aggregator gRPC server) provides an unrestricted way to reach privileged, state-changing/broadcasting functions for callers who are *not* the intended party (`clementine-backend`), because no authentication boundary is enforced at all.

### Impact Explanation
This matches the "High" impact category explicitly listed in scope: "an unauthenticated state-changing or broadcasting call." Any network-reachable, unprivileged actor can invoke `SendMoveToVaultTx`/`InternalSendTx` to broadcast a transaction, or trigger `NewDeposit`/`Withdraw`/`OptimisticPayout`, flows that are meant to be gated to the backend orchestrator only, potentially disrupting deposit/withdrawal orchestration, causing premature or conflicting broadcasts, or interfering with in-flight signing ceremonies coordinated by the legitimate backend.

### Likelihood Explanation
Likelihood is high in any deployment that follows the documented default (aggregator client_verification left unenforced, relying only on TLS-for-encryption), since reaching the aggregator's exposed port is the only precondition — no keys, credentials, or privileged roles are needed, consistent with the "unprivileged attacker" baseline in scope.

### Recommendation
Apply an authentication boundary to the aggregator's gRPC server equivalent to `OnlyAggregatorAndSelf`, e.g., restrict state-changing/broadcasting RPCs (`NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`) to a specific backend client certificate, rather than relying on TLS alone.

### Proof of Concept
1. Start an aggregator server with default/documented configuration (client_verification not enforced for the aggregator, per `docs/usage.md`).
2. From any machine able to reach the aggregator's TCP/TLS port (no client certificate matching the backend's private key required, since `Interceptors::Noop`/absence of cert-check path is taken as documented), establish a TLS connection and call `SendMoveToVaultTx` or `NewDeposit` on `ClementineAggregatorClient`.
3. Observe the RPC is processed and can trigger transaction broadcast / orchestration flows, despite the proto/documentation stating these are "Used by the clementine-backend service" only [8](#0-7) .

    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
and to authenticate clients. Client certificates are verified and filtered by
the verifier/operator to ensure that:

1. Verifier/Operator methods can only be called by the aggregator (using
   aggregator's client certificate `aggregator_cert_path`)
2. Internal methods can only be called by the entity's own client certificate
   (using the entity's client certificate `client_cert_path`)

The aggregator does not enforce client certificates but does use TLS for encryption.
