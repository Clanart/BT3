### Title
Uniform Noop interceptor applies to every `ClementineAggregator` RPC with no per-method override - ([File: core/src/servers.rs])

### Summary
`create_grpc_server` wraps the entire `ClementineAggregatorServer<AggregatorServer>` service in a single `InterceptedService` (either `OnlyAggregatorAndSelf` or `Noop`), and this wrapping happens once, outside of and before the generated `Service::call` method dispatches on `req.uri().path()`. There is no code anywhere in `add_service`/`ClementineAggregatorServer::call` that assigns a different interceptor, or any interceptor at all, to a subset of the seven state-mutating methods (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`).

### Finding Description
Binding claimed: `{methods protected by OnlyAggregatorAndSelf}` == `{methods that mutate protocol state or spend a bridge UTXO}`.

Tracing the code:
- `create_grpc_server` in `core/src/servers.rs` builds one `Interceptors` value (`OnlyAggregatorAndSelf{...}` if `config.client_verification` else `Noop`) and wraps the *whole* `svc` argument with a single `InterceptedService::new(service, interceptor)` call [1](#0-0) .
- The generated `ClementineAggregatorServer<T>::call` (in `core/src/rpc/clementine.rs`, generated code, out of scope for defect analysis but relevant for tracing) only performs `match req.uri().path()` to dispatch to the correct method handler after the interceptor has already run; it contains no per-path authorization logic of its own [2](#0-1) .
- `Interceptors::call` dispatches uniformly: for `Noop` it unconditionally returns `Ok(req)` for any request path; for `OnlyAggregatorAndSelf` it applies the same `only_aggregator_and_self` check to every path, distinguishing only "Internal*" methods from others (still requiring a valid cert either way) [3](#0-2) [4](#0-3) .
- `create_aggregator_grpc_server` constructs the aggregator service and passes it through this same single-interceptor path with no additional per-method wrapping [5](#0-4) .

Consequently, under `Interceptors::Noop` the protected set is empty for all methods including the seven state-mutating ones, while the state-mutating set has 7 members — the equality fails uniformly, not selectively. There is no per-method override anywhere in `add_service`.

### Impact Explanation
If the aggregator's `client_verification` is `false`, an unauthenticated network peer can call `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`, `Setup`, and `InternalGetEmergencyStopTx` with no authentication whatsoever — matching the "High - an unauthenticated state-changing or broadcasting call" impact category. This is repeatable across every deposit/withdrawal/operator handled by that aggregator instance, since the lack of protection is server-wide rather than tied to a specific RPC.

### Likelihood Explanation
This requires the operator to run the aggregator with `client_verification = false`. This is **not** the repo's actual default: `BridgeConfig::default()` sets `client_verification: true` [6](#0-5) , and all shipped example/reference configs (`.env.example`, `core/src/test/data/bridge_config.toml`, `scripts/docker/configs/testnet4/bridge_config.toml`) also set it to `true`. The code even emits a warning when `client_verification` is enabled on the aggregator (`tracing::warn!("Client verification is enabled on aggregator gRPC server")`) [7](#0-6) , suggesting the aggregator may be intentionally deployed without mTLS-based auth in some setups — but this is a deployment/config choice, not a hardcoded default in this repo. Exploitation is trivial and free for an attacker once such a misconfiguration exists (no cert needed, no BTC cost to call the RPC), but it is contingent on that non-default configuration.

### Recommendation
Not applicable as a code-level fix within this repo since the interceptor architecture itself is a legitimate all-or-nothing mTLS gate; the actionable recommendation is operational: never deploy the aggregator with `client_verification = false`, and consider making that field required to be `true` (removing the `false` code path entirely, or gating it behind an explicit `--insecure` flag with mainnet checks) so it cannot be disabled by accident in production.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;
