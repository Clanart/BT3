### Title
Submodule `file://` protocol re-enabled during checkout/update, bypassing Git's local file disclosure protection - ([File: app/src/lib/git/submodule.ts](app/src/lib/git/submodule.ts))

### Summary
The Marmo report's broken invariant is: a privileged operation (`delegatecall`) blindly executes whatever an attacker-supplied value (`_implementation`) points to, because the caller never verifies it against a trusted allow-list. The closest verified analog in this codebase is `updateSubmodulesAfterOperation` in [1](#0-0) , which takes a caller-supplied `allowFileProtocol` boolean and, when `true`, explicitly re-arms Git's `file://` submodule transport with `-c protocol.file.allow=always` before running `git submodule update --init --recursive`.

### Finding Description
Since Git 2.38.1 (GHSA/CVE‑2022‑39253), Git itself disables the `file://` transport for submodule operations by default specifically to stop a cloned/fetched repository's `.gitmodules` from being used to read arbitrary local files or trigger unexpected local clones. GitHub Desktop's `updateSubmodulesAfterOperation` accepts an `allowFileProtocol` flag and, when set, passes `-c protocol.file.allow=always` into the `git submodule update --init --recursive` invocation [2](#0-1) . This is functionally the same failure mode as `relay()`'s `delegatecall`: a privileged, unrestricted capability (arbitrary local `file://` reads/clones driven by a value inside the attacker-supplied `.gitmodules`) is granted based on the caller's decision to flip a trust flag, rather than by validating the actual submodule URL against the security boundary Git itself put in place.

The flag is threaded from `checkout.ts` (confirmed via 7 call sites for `allowFileProtocol`/`updateSubmodulesAfterOperation`), but I was not able to fully verify, within the scope of this session, the exact heuristic `checkout.ts` uses to decide when `allowFileProtocol` should be `true` (e.g., whether it's conditioned on the superproject's own remote also being a local path). That heuristic is the crux of whether this is exploitable by a remote attacker: if it can be satisfied by content the attacker controls (rather than strictly by an operation the user explicitly initiated against a local-only repository), then any repository fetched from the network with a `.gitmodules` submodule URL of `file:///home/user/.ssh` (or similar) would have Git's file-transport safeguard silently disabled by Desktop, allowing the "submodule clone" to copy arbitrary local files into the working tree, or path-traverse via the `file://` URL.

### Impact Explanation
If the `allowFileProtocol=true` path can be reached for a repository whose submodule URLs originate from untrusted, attacker-controlled content (a cloned/fetched repo), this defeats an upstream Git security control specifically designed to stop local file disclosure via crafted `.gitmodules`. That maps to "file write or read outside the repo" in the accepted impact categories, since a submodule "clone" of `file:///Users/victim/.ssh` (or another sensitive local path) would place its contents into the working directory where the user could then inadvertently commit/exfiltrate them.

### Likelihood Explanation
Likelihood is uncertain without confirming the exact trigger condition in `checkout.ts`. Git's own default (`protocol.file.allow=user`) already blocks the naive form of this attack, so Desktop overriding it to `always` is a deliberate design decision that must be scoped very narrowly (e.g., only for local-to-local test/dev clones) to be safe. Given the test fixtures in this repo use the identical `-c protocol.file.allow=always` override purely for local, developer-created submodule fixtures, it's plausible the production code path only allows this for repositories whose own remote is already local — but this needs to be confirmed by inspecting `checkout.ts`'s call sites directly.

### Recommendation
Audit every call site in `app/src/lib/git/checkout.ts` that passes `allowFileProtocol: true` to `updateSubmodulesAfterOperation`, and confirm the condition cannot be satisfied by content that originates from a network-fetched/cloned repository (i.e., only allow it when the top-level repository's own remote/proxy is verified to be a local, non-network path, and never based on `.gitmodules` content itself). If the flag is user-controllable indirectly (e.g., via repository settings that a malicious repo could influence), remove it or tie it to an explicit, per-operation user confirmation rather than an implicit heuristic.

### Proof of Concept
Not able to construct a concrete end-to-end PoC without confirming the exact `allowFileProtocol` trigger logic in `checkout.ts`. Conceptually: an attacker publishes a repository containing `.gitmodules` with `url = file:///<sensitive-local-path>`; if a Desktop code path calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)` while processing this repository (e.g., during checkout of a branch that adds this submodule), Git's `protocol.file.allow=always` override would let the "submodule clone" read from the local filesystem path instead of being blocked by Git's built-in default protection.
