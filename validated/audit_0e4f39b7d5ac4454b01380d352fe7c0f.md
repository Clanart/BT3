## Analog Found

### Title
`GIT_CLONE_PROTECTION_ACTIVE` hardcoded to `'false'` disables Git's clone symlink/hook protection - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to `git clone --recursive`, and this is unconditional and hardcoded — mirroring the reported bug class of a boolean safety parameter being hardcoded to the weaker/unsafe value so that a downstream protective check is silently loosened. Here the "protective check" is Git's own built-in clone-time protection mechanism, and the attacker-controlled input is a malicious remote/repository fetched via `git clone --recursive` (submodules, refs, tree entries) that Desktop lets users clone directly from a URL.

### Finding Description
`clone()` builds the execution environment as:

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

and then always invokes `git clone --recursive ... -- url path` with that environment [2](#0-1) .

This is structurally identical to the reported pattern: a hardcoded flag that should reflect a "safe" state is instead hardcoded to the value that weakens a security-relevant guard, with no configuration path to override it. In the `GlpOracle` report, `glpManager.getPrice(false)` hardcodes the "don't maximize" branch of a price-rounding safety mechanism, causing the `_minGlp` slippage guard to be looser than intended and letting `GlpManager` mint less GLP without reverting. In `clone.ts`, `GIT_CLONE_PROTECTION_ACTIVE: 'false'` hardcodes the "protection disabled" branch of Git's own clone-time defense, which exists specifically to guard against recursive/`--recursive` clones of untrusted remotes containing crafted submodule paths, symlinks, or `.git`-adjacent entries designed to escape the intended checkout directory or clobber files outside it (the class of issues addressed by Git's CVE-2024-32002/CVE-2025-27614-style clone hardening). By turning this protection off unconditionally for every clone operation Desktop performs — including "Clone from URL" flows where the URL and remote content are fully attacker-controlled — the app removes a defense-in-depth check that Git itself would otherwise enforce during the very `--recursive` clone Desktop always requests.

The existing guard `isClonePathSensitive()` [3](#0-2)  only validates the top-level destination directory chosen by the user (e.g. not `~/.ssh`, not `~/.gnupg`); it does nothing to constrain what a malicious remote can do to paths and symlinks *inside* the cloned tree during a recursive clone, which is precisely the class of attack `GIT_CLONE_PROTECTION_ACTIVE` is designed to stop. So the destination-level check does not compensate for disabling the in-tree protection.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` disables Git's built-in defenses against malicious recursive-clone content (crafted submodule paths/symlinks that can escape the working directory boundary or overwrite files during checkout), then any user who clones or fetches a malicious/attacker-controlled repository through Desktop (a normal, expected, unprivileged action) could have files written outside the intended clone directory or have arbitrary tracked paths clobbered — silent corruption of the on-disk repository the user believes they cloned. This matches the report's severity class (Medium-to-High): the safety flag is inert unless disabled, disabling it is silent (no error, no warning, no revert), and the trigger (`git clone --recursive <untrusted-url>`) is a core, everyday Desktop feature.

### Likelihood Explanation
High. The unsafe value is hardcoded and unconditional — every single clone Desktop performs (including "Clone repository from URL", a one-click, no-privilege user action) sends this flag, so there is no code path where the protection is actually active. This exactly parallels the report's "Likelihood: High — false is hardcoded so it is very likely it will happen."

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` (or the underlying Git protection it maps to). If it was added for a specific compatibility reason, verify what protection it disables, scope the override to only the narrow scenario requiring it, and set it to `'true'` (or omit it, if Git's default is already the safe state) for the general clone path so Git's own recursive-clone safety checks remain active.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
