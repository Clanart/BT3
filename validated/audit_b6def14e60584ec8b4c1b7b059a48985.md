### Title
Hardcoded `DUST` constant does not match the Taproot dust limit, causing valid payments to be rejected and change to be burned as fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` in `bitcoin-serai` gates both user payments and change creation on the constant `DUST = 546`. Because every output this wallet creates/spends is a Taproot (P2TR) output, the correct dust threshold is 330 satoshis, not 546. The oversized constant silently rejects legitimate payments in the 330–545 sat range and converts change in that range into additional miner fee — a wrong-constant analog of the external report where a wrongly-set `ETH` constant made `registerPool` always revert.

### Finding Description
The external report's bug class is: a hardcoded constant holds a value that does not match what the protocol semantics require, so every comparison against it produces the wrong branch decision.

In `networks/bitcoin/src/wallet/send.rs`:

```rust
// https://github.com/bitcoin/bitcoin/blob/306ccd4927a2efe325c8d84be1bdb79edeb29b04/src/policy/policy.cpp#L26-L63
// As the above notes, a lower amount may not be considered dust if contained in a SegWit output
// This doesn't bother with delineation due to how marginal these values are, and because it isn't
// worth the complexity to implement differentation
pub const DUST: u64 = 546;
```

This constant is used in two places in `SignableTransaction::new`:

1. Payment validation — any payment below `DUST` is rejected:
```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

2. Change handling — change below `DUST` is not emitted and is instead absorbed into the fee:
```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
    ...
  }
}
```

The comment itself acknowledges the value is only the *non-SegWit* dust limit (a P2PKH output spends 148 bytes on redeem, giving 3 × 182 = 546). This wallet, however, exclusively produces and spends P2TR key-path outputs: `multisig` verifies `p2tr_script_buf(offset.group_key())? == self.prevouts[i].script_pubkey` and signs with `TapSighashType::Default` via `taproot_key_spend_signature_hash`. For SegWit outputs, Bitcoin Core computes dust at 294 sat for SegWit v0 and **330 sat for Taproot** (output size 43 B + input spend ~67.5 vB ⇒ ⌈(43 + 67.5) × 3⌉ = 330 at the default 3000 sat/kvB relay fee).

The hardcoded `546` therefore mismatches the actual standardness rule for every output this code touches: amounts 330 ≤ v < 546 are wrongly treated as dust.

### Impact Explanation
- **Payment denial:** a user attempting a perfectly standard P2TR payment of e.g. 400 sats always gets `TransactionError::DustPayment` — the analog of `registerPool` "reverting every time" because the constant doesn't match reality. The functionality is only unavailable for the 330–545 sat band, but the check is unconditional and deterministic.
- **Silent fee inflation / fund loss:** leftover change in the 330–545 sat range fails `value >= DUST`, so no change output is created. Those sats are added to the fee paid to miners (`fee() = sum(inputs) − sum(outputs)`), permanently forfeiting funds that were correctly spendable as change. The wallet gives no error or warning in this path.

Losses are bounded per transaction (≤ 216 sats of change per output, plus blocked small payments), so the practical impact is moderate rather than critical — hence Medium.

### Likelihood Explanation
Change amounts are a function of the difference between selected inputs and payments; small change values in the 330–545 sat band occur routinely in ordinary wallet operation (any time the leftover is a few hundred sats). Dust-band payment amounts are also common for micropayments and test transactions. The bug is deterministic — there is no probabilistic or adversarial component — it triggers whenever the value falls in the wrong-constant band, reachable purely through public transaction data (the payment amounts and input set the caller supplies).

### Recommendation
Set the constant to the value matching the outputs this wallet actually creates:

```rust
// Dust limit for P2TR outputs: (43 bytes output + ~67.5 vB input) * 3 sat/vB
pub const DUST: u64 = 330;
```

If non-Taproot payment script types are ever supported via `payments: &[(ScriptBuf, u64)]`, compute the dust threshold per output based on its script type (the `bitcoin` crate's `TxOut` / `dust_value` helpers, or Core's `GetDustThreshold` logic) rather than a single global constant. Add a regression test asserting a 400 sat P2TR payment is accepted and that 330–545 sat change produces a change output.

### Proof of Concept
Conceptual, determinable directly from the code paths cited:

```rust
// Any caller building a spend with a 400-sat P2TR payment:
let payments = vec![(p2tr_script_buf(some_key).unwrap(), 400)];
// A 400-sat Taproot output is standard (>= 330 sat dust limit), yet:
let res = SignableTransaction::new(inputs, &payments, None, None, 1);
// res == Err(TransactionError::DustPayment)  -> always "reverts"

// Or, with inputs totalling payment_sat + fee_with_change + 400:
// checked_sub succeeds with value = 400, but 400 >= 546 is false,
// so no change TxOut is pushed and `fee()` reports those 400 sats
// as miner fee instead of returning them to the change script.
```

The root cause is identical in shape to the external finding: `pub const DUST: u64 = 546` at `networks/bitcoin/src/wallet/send.rs:32` encodes the P2PKH dust value while every comparison site (`send.rs:165-169` for payments, `send.rs:228-234` for change) operates exclusively on P2TR outputs, making the constant wrong for 100% of its uses.
