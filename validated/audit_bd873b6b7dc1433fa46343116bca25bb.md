### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block — including `block.txdata[0]`, the coinbase — and passes each to `scan_transaction`, which matches outputs solely on `script_pubkey` membership in the `scripts` map. The resulting `ReceivedOutput` carries only `(offset, TxOut, OutPoint)`; no field records that the output originated from a coinbase. Any downstream consumer treating these outputs as spendable inputs to `SignableTransaction::new` will construct transactions that are consensus-invalid (coinbase outputs require 100 confirmations of maturity). This is the direct analog of the reported bug class: an untrusted input is accepted under one interpretation ("script matches one of our offsets → it is ours") while the downstream consumer uses it under a stronger interpretation ("this is a spendable UTXO"), with the type/context information that distinguishes the two cases dropped at the boundary.

### Finding Description
- `scan_block` calls `scan_transaction` on `block.txdata` with no exclusion of the coinbase transaction and no maturity/confirmation-height check (`networks/bitcoin/src/wallet/mod.rs:221-227`).
- `scan_transaction` keys only on `output.script_pubkey` and returns `ReceivedOutput { offset, output, outpoint }` (`networks/bitcoin/src/wallet/mod.rs:199-214`).
- `ReceivedOutput` has no maturity flag; `SignableTransaction::new` consumes `Vec<ReceivedOutput>` and builds a Taproot key-spend transaction committing to those prevouts via `Prevouts::All` in the sighash (`networks/bitcoin/src/wallet/send.rs:150-256`, `send.rs:375-386`).
- A block proposer (any miner, an unprivileged external party relative to the Serai validator set) can include a coinbase output paying to a scanned script. Every downstream scanner call on that block reports it identically to a normal, spendable payment.

### Impact Explanation
Funds are reported received that are not spendable. A coinbase output credited to Serai's address will be reported by `scan_block` as a normal received output. If the coordinator/processor immediately selects it as an input to `SignableTransaction`, the produced and threshold-signed transaction spends an immature coinbase and is rejected by Bitcoin consensus — meanwhile the protocol has already accounted the value as received/spendable. The same signed "intent" can also waste fees on a guaranteed-invalid broadcast, and repeated selection of the immature output can stall payment processing.

### Likelihood Explanation
Any miner can create a coinbase paying to the observed Serai Taproot script at negligible cost (a dust-value coinbase output). Exploitation requires the integrator to feed `scan_block` results directly into spend selection without a maturity post-pass. The doc comment on `scan_block` acknowledges the issue (`mod.rs:218-220`), but the API provides no maturity metadata on `ReceivedOutput`, so the distinguishing information cannot be recovered downstream — the type confusion is baked into the interface, and the failure mode is silent. Severity is bounded because the funds do eventually mature (100 blocks) and no key material is leaked: Medium.

### Recommendation
Either exclude the coinbase from `scan_block` (`block.txdata[1..]`) or, preferably, tag each `ReceivedOutput` with its origin (transaction index / `is_coinbase` flag / block height) in `scan_transaction`/`scan_block` so consumers can enforce maturity before signing. `SignableTransaction::new` should ideally reject inputs known to be immature.

### Proof of Concept
```rust
// Conceptual: a block whose coinbase pays DUST or more to the scanned P2TR script.
let scanner = Scanner::new(group_key).unwrap();
let block: Block = /* block whose txdata[0] coinbase contains
                      TxOut { value, script_pubkey: p2tr_script_buf(key) } */;

let received = scanner.scan_block(&block);
// `received` contains a ReceivedOutput indistinguishable from a normal payment.
// There is no API on ReceivedOutput to detect it is an immature coinbase.

let stx = SignableTransaction::new(received, payments, change, data, fee_rate)
  .unwrap(); // succeeds — no maturity check anywhere
// Signing produces a transaction spending an immature coinbase output.
// Bitcoin consensus rejects it (BIP-34/rule: coinbase spends require 100 confs),
// yet the output was already accounted as received value.
```
