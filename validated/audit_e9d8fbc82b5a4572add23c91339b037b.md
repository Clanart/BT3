This is the key point: `PayoutCheckerTask::run_once` calls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` [1](#0-0)  — an operator only ever picks up and acts on payouts whose recorded OP_RETURN `operator_xonly_pk` matches **its own** key. The victim operator's automation would simply never see a payout tagged with the victim's key unless that payout row is filtered by `operator_xonly_pk == victim`. If the attacker crafts a payout tx naming the victim's `operator_xonly_pk` in the OP_RETURN, the victim's own `PayoutCheckerTask` will pick it up as "its" unhandled payout and call `self.operator.handle_finalized_payout(...)`, which builds and sends a **real kickoff signed with the victim's own keys and collateral** for a deposit the victim never actually funded [2](#0-1) . Since `is_kickoff_malicious` only compares the OP_RETURN operator field against `kickoff_data.operator_xonly_pk` (which is the victim's own key, matching), it reports non-malicious [3](#0-2) . The end result is exactly what the question describes: the victim burns its own collateral and consumes its round/kickoff slot to legitimately "reimburse" a withdrawal actually funded by the attacker, while the attacker gets the withdrawal fronted for free and the victim gets nothing back (the reimbursement UTXO pays out per the presigned `reimburse_tx` script to the operator's registered address, but the operator spent real BTC issuing the kickoff/round machinery for a payout it didn't make, and possibly consumes/exposes its round to challenge without any actual funding credit — depending on exact reimbursement destination this can also cause the attacker's payout to be reimbursed to the victim's address, which is a different failure mode, or worse if the victim is slashed for a round that never matches its own real payouts).

This does confirm the described attribution break is real and reachable purely through the OP_RETURN embedding no cryptographic binding to actual funding, exactly as the question states, and it is reachable by an unprivileged attacker who only needs the `SinglePlusAnyoneCanPay` signature (obtainable, per the threat model, since the attacker can itself call `withdraw` on the Citrea Bridge contract and control the signature/bytes) — no verifier, operator, or aggregator privilege is required to broadcast such a payout naming an arbitrary operator.

### Title
Unauthenticated `operator_xonly_pk` in payout OP_RETURN allows attacker to force a victim operator to fund reimbursement for an attacker-funded withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` embeds the caller-supplied `operator_xonly_pk` into the payout tx's OP_RETURN with no proof that this key funded `output_txout` [4](#0-3) . Because `PayoutCheckerTask` filters "unhandled payouts" strictly by matching this OP_RETURN field to the local operator's own key [1](#0-0) , an attacker who broadcasts a self-funded payout tagged with a victim operator's pubkey causes the victim's own automation to autonomously sign and broadcast a genuine kickoff/reimbursement flow for a withdrawal it never funded.

### Finding Description
The claimed binding is: `op_return_txout.operator_xonly_pk == funder_of(output_txout)`. Tracing the code shows this equality is never enforced. `create_payout_txhandler` takes `operator_xonly_pk` purely as a function argument and pushes `operator_xonly_pk.serialize()` into the OP_RETURN with no signature or proof tying it to the input UTXO's spender [4](#0-3) . The only cryptographic constraint on the transaction is the withdrawer's `SinglePlusAnyoneCanPay` signature over the single specified input/output pair, which under that sighash flag permits **any other output** (including the OP_RETURN) and any funding of the transaction fee/anchor, as confirmed in `Operator::withdraw`, which verifies `SECP.verify_schnorr` only over the payout tx's calculated sighash for the user's outpoint, independent of who is broadcasting or fee-funding the tx [5](#0-4) .

Downstream, `is_kickoff_malicious` reads the OP_RETURN-derived `operator_xonly_pk_opt` from the payout info stored in the DB and compares it only to `kickoff_data.operator_xonly_pk` of whichever kickoff arrives for that `move_txid` [6](#0-5) . Separately and more critically, `PayoutCheckerTask::run_once` selects "its own" unhandled payout purely by matching this attacker-controlled OP_RETURN field against `self.operator.signer.xonly_public_key` [1](#0-0) , then automatically calls `handle_finalized_payout`, which drives the victim operator to sign and broadcast a real kickoff transaction backed by its own collateral and presigned round/kickoff graph [2](#0-1) , [7](#0-6) .

Attacker flow: attacker calls Citrea `withdraw`, obtains/derives the user's `SinglePlusAnyoneCanPay` signature over the withdrawal outpoint, then constructs their own `create_payout_txhandler(input_utxo, output_txout, victim_operator_xonly_pk, user_sig, network)` transaction, funds the missing inputs/fees themselves, and broadcasts it. No verifier or operator privilege check gates this — the payout tx is a plain Bitcoin transaction requiring only a valid signature over the specific committed sighash, and the OP_RETURN content is fully attacker-chosen. `is_deposit_valid`, `SPV::verify`, and the presigned transaction graph checks never validate that the OP_RETURN operator key corresponds to the actual funder of `output_txout`; they only validate deposit and move-tx structure, not payout attribution.

### Impact Explanation
This causes an honest operator to unknowingly spend its own kickoff-round resources and expose its collateral/challenge-timeout window to reimburse a withdrawal it never fronted, matching the "operator reimbursed for a payout it never funded" / "honest operator's collateral put at risk" Critical-severity category. The attack is repeatable per deposit and per operator: any victim operator that is running automation (`PayoutCheckerTask`) can be targeted for any withdrawal an attacker chooses to front themselves, since the only requirement is possession of the withdrawer's sighash-committed signature, which the attacker themselves can generate by calling `withdraw` on the bridge with parameters of their choosing. Blast radius scales with the number of automated operators and withdrawals; the true funder (attacker) is never accurately recorded, breaking attribution used for reimbursement bookkeeping and challenge/malicious-kickoff detection.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged threat model exactly: the attacker needs only to be able to deposit/withdraw through Citrea (or otherwise obtain a withdrawer's `SinglePlusAnyoneCanPay` signature) and pay Bitcoin transaction fees to fund and broadcast their own payout transaction — no verifier, operator, or aggregator credential is required. The victim operator's automation (`PayoutCheckerTask`) runs unconditionally in the background whenever `feature = "automation"` is enabled, which is the standard operator deployment mode, making exploitation highly feasible and fully repeatable across withdrawals and operators.

### Recommendation
Bind the OP_RETURN `operator_xonly_pk` cryptographically to the actual transaction: require the payout to be co-signed/authorized by the named operator (e.g., have the operator itself provide the outer funding signature, or require an operator signature over the OP_RETURN commitment), or have `PayoutCheckerTask`/`is_kickoff_malicious` additionally verify that the entity claiming reimbursement actually broadcast/fee-funded the payout tx (e.g., verify the operator's known key controls one of the transaction's other inputs, or require the operator's kickoff commitment to include a proof-of-funding signature over the payout txid rather than trusting an unauthenticated OP_RETURN field).
