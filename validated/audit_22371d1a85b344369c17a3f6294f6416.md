### Title
Auctioneer signature does not bind chain/contract/bid context, enabling cross-bid replay of auctioneer approval - (File: kaiax/auction/bid.go)

### Summary
This is a direct analog of the reported `StoryBadgeNFT` bug class: a signature that is meant to authorize a specific, context-bound action is computed over an under-specified digest, allowing the same signature to be validly reused where it shouldn't be. In the Kaia auction (KIP-249 MEV auction) module, `Bid.ValidateAuctioneerSig` verifies the auctioneer's approval over a digest that binds only the `SearcherSig` bytes, not the chain ID, the auction entry-point contract, the auction version, or any of the bid's economic fields directly.

### Finding Description
The searcher signature is correctly bound to chain and contract context via EIP-712 (`GetHashTypedData` includes `chainId`, `verifyingContract`, and `version` in the domain separator): [1](#0-0) 

However, the auctioneer signature — which is the second, independently-checked signature required to admit a bid into the pool — is computed differently: [2](#0-1) [3](#0-2) 

`GetEthSignedMessageHash()` builds the digest solely from `b.SearcherSig` (`"\x19Ethereum Signed Message:\n" + len(SearcherSig) + SearcherSig`). It does not include `chainId`, `verifyingContract` (the auction entry point address), the auction version, or any of `TargetTxHash`, `BlockNumber`, `Sender`, `To`, `Nonce`, `Bid`, `MaxGasPrice`, `CallGasLimit`, or `Data` directly. The auctioneer's signature therefore is not scoped to a specific auction entry-point/chain deployment the way the report's fix required the `StoryNFT` contract address to be included in the signature digest.

Both signatures are required and independently verified in `BidPool.validateBidSigs`: [4](#0-3) 

`bp.auctioneer` and `bp.auctionEntryPoint`/`bp.auctionEntryPointVersion` are read from on-chain contract state per node (`ReadAuctioneer`, `ReadAuctionVersion` in `blockchain/system/auction.go`) and are mutable over time (upgrades, re-deployments, or different KIP-249 entry-point contract versions sharing the same auctioneer key), yet the auctioneer's authorization signature itself carries none of that context.

### Impact Explanation
Because the auctioneer digest only commits to the raw `SearcherSig` bytes, any `(SearcherSig, AuctioneerSig)` pair obtained for one auction context (a given chain / auction entry-point contract / version) is not cryptographically bound to that context by the auctioneer's own signature. If the same auctioneer key is used to approve bids across multiple deployments of the auction entry point (e.g., v2.1 vs v3.0 upgrade, or a redeployed entry point after governance change), or if an attacker can otherwise obtain/observe an `AuctioneerSig` value tied to a `SearcherSig`, the auctioneer approval does not itself prevent misuse outside its intended domain — unlike the searcher-side EIP-712 digest which properly scopes to `chainId`/`verifyingContract`/`version`. This weakens the auction admission control (`validateBidSigs`) that gates which bids enter the priority bid pool and are ultimately executed via `system.EncodeAuctionCallData`/`call` on the entry point, i.e., it affects fee/priority-auction settlement integrity reachable from a plain bid submission.

### Likelihood Explanation
Reachable directly from an unprivileged bid submission path (`BidPool.AddBid` → `validateBid` → `validateBidSigs`), which any external bidder/searcher/relayer can trigger by submitting a `Bid` over the auction network handler. The auctioneer address and auction entry-point/version are read from mutable on-chain state (`updateAuctionInfo`), so cross-context replay becomes plausible whenever the auctioneer key is reused across auction contract versions/deployments — a realistic operational pattern flagged as the exact bug class in the external report (signature missing contract/context binding).

### Recommendation
Bind the auctioneer signature to the same context as the searcher signature: include `chainId`, `verifyingContract` (auction entry point), the auction version, and/or the full bid struct hash (e.g., sign over the EIP-712 struct hash of the bid, or at minimum `SearcherSig || chainId || verifyingContract || version`) instead of `SearcherSig` alone. This mirrors the Story team's fix of including the target contract address in the signature digest.

### Proof of Concept
Conceptual PoC (Go, using existing test helpers in `kaiax/auction`):
1. Deploy/configure two auction entry-point contexts that share the same `auctioneer` key but differ in `verifyingContract`/`version` (e.g., v2.1 and v3.0 KIP-249 entry points), as already modeled by `AuctionVersionV2`/`AuctionVersionV3` in `kaiax/auction/eip712.go`.
2. Have the auctioneer produce `AuctioneerSig = Sign(GetEthSignedMessageHash())` for a legitimate `SearcherSig` obtained under context A.
3. Show that `ValidateAuctioneerSig` for that same `AuctioneerSig` succeeds identically regardless of `chainId`/`verifyingContract`/version, because `GetEthSignedMessageHash()` in `kaiax/auction/bid.go:52-55` never consumes those parameters — confirming the auctioneer's signature offers no domain separation, contrary to the searcher's properly-scoped EIP-712 digest in `kaiax/auction/eip712.go:124-149`.

(Note: I was not able to fully trace every downstream consumer of `bp.auctioneer` to construct a fully weaponized end-to-end replay across two live deployments within this session; the root-cause code path — the missing binding in `GetEthSignedMessageHash`/`ValidateAuctioneerSig` — is confirmed directly from source.)

func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)

func (b *Bid) GetEthSignedMessageHash() []byte {
	data := b.SearcherSig
	return crypto.Keccak256(fmt.Appendf(nil, "\x19Ethereum Signed Message:\n%d%s", len(data), data))
}

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
