### Title
Gasless swap fee-repayment validation relies on manipulable spot DEX reserves (Uniswap-V2-style `getReserves`), analogous to `slot0` spot-price manipulation - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The gasless transaction flow (KIP-247) lends a user gas fee via a proposer-funded `LendTxGenerator`, and the user is expected to repay it by swapping ERC-20 tokens through `GaslessSwapRouter`. Both the tx-pool admission check and the on-chain exchange-rate computation depend on `GetAmountIn`, which — like the reported Arrakis `Underlying.sol` bug that reads `slot0` — is derived from the DEX pair's *instantaneous* reserves (`getReserves()`), not a time-weighted price. This spot value can be manipulated within the same block by a party that controls transaction ordering (e.g., an auction bidder or the block proposer itself), analogous to the "manipulate `slot0` via flashloan" pattern in the original report.

### Finding Description
In `checkBalanceForSwap`, the gasless tx pool computes the token amount required to satisfy the declared `minAmountOut` by querying the router's exchange rate: [1](#0-0) 

The comment explicitly states this uses "the current exchange rate," and the underlying `GaslessSwapRouter.GetAmountIn` binding is a `view` call into the router/DEX contract: [2](#0-1) 

The DEX pair bound into this system (Uniswap V2-style, per the bytecode-regression pins in the gasless test) computes swap amounts from `getReserves()`, which returns the pool's current, spot reserve balances with no TWAP protection: [3](#0-2) [4](#0-3) 

The lend/repay accounting that depends on this swap succeeding at the expected rate is defined in `lendAmount`/`repayAmount`: [5](#0-4) 

As documented, the proposer funds the gas fee upfront and expects repayment from the swap output:


Because the swap-amount computation used both to admit the transaction into the pool and (per the router ABI comment) at execution time (`swapForGas`) is based on the pool's spot reserves rather than a manipulation-resistant oracle, a party able to influence transaction ordering within the same block — most notably a KIP-249 auction bidder, whose bid transaction is guaranteed to execute immediately before/after a specific target transaction — can insert large swaps against the same pool right before the gasless `SwapTx` executes. This shifts the reserves so that the actual `getAmountOut` realized by the gasless swap is worse than what was priced in when the transaction was validated for admission, directly affecting whether the user's swap output covers `amountRepay` (the proposer's lent gas fee).

### Impact Explanation
If the effective swap rate is manipulated downward at execution time:
- The user's swap may yield less than `amountRepay`, but the `LendTxGenerator`/`GaslessApproveTx`/`GaslessSwapTx` bundle is still built and submitted as a fixed sequence by the builder (`kaiax/gasless/impl/builder.go`), and the proposer has already advanced the gas fee. This can result in the proposer's advanced KAIA not being fully recouped, i.e., fee-delegation loss for the block proposer, or
- Conversely, if manipulated favorably to the attacker (e.g., a searcher sandwiching the gasless swap), value can be extracted from the user's token balance in excess of the intended commission/repay amounts.

This is a concrete instance of "fee or fee-delegation abuse" reachable from a public transaction/bid, matching the Medium-severity class of the original report (spot-price read used for critical accounting without manipulation resistance).

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to have capital to move the specific DEX pool's reserves and the ability to guarantee ordering adjacency to the target gasless swap within a block — both of which are directly supported by the in-scope KIP-249 auction module (bids are guaranteed to execute immediately before/after a target transaction) or simply by being the block proposer building the bundle. I was unable to inspect the actual Solidity source of `GaslessSwapRouter.sol` (only generated Go bindings are indexed), so I cannot fully confirm whether `swapForGas`'s internal accounting re-derives the rate from `getReserves()` at execution time versus solely relying on user-supplied `minAmountOut`/`amountRepay` bounds enforced elsewhindependently; this should be verified against the actual contract source before treating this as conclusively exploitable.

### Recommendation
- Use a manipulation-resistant price reference (e.g., TWAP oracle, or a maximum allowed reserve deviation check) instead of raw `getReserves()`/instantaneous `getAmountIn` for both mempool admission (`checkBalanceForSwap`) and on-chain `swapForGas` settlement.
- Re-validate `amountRepay` coverage strictly at execution time inside `swapForGas` using the actual realized swap output, reverting the whole bundle if insufficient, rather than relying on the pre-execution `GetAmountIn` estimate.
- Restrict same-block ordering advantages around gasless swap bundles (e.g., disallow auction bids or other transactions between the whitelisted DEX pool and the gasless bundle in the same block).

### Proof of Concept
Conceptual sequence (execution details of `GaslessSwapRouter.sol` not directly verifiable from the indexed bindings):
1. Attacker identifies a pending `GaslessSwapTx` bundle (`LendTxGenerator → GaslessApproveTx → GaslessSwapTx`) targeting a specific whitelisted token/DEX pool, validated via `checkBalanceForSwap` using the pool's current `getReserves()`-based `GetAmountIn`. [1](#0-0) 
2. Using the KIP-249 auction mechanism (or proposer-level ordering control), the attacker inserts a large swap against the same DEX pool immediately before the gasless bundle executes within the same block, shifting `getReserves()`. [3](#0-2) 
3. When `GaslessSwapTx` executes `swapForGas`, the realized exchange rate differs from the one used during pool admission, so the token swap output no longer safely covers `repayAmount` (`R1+R2+R3`), causing the proposer's lent gas fee to be under-recouped (or the user to be over-charged), while the attacker's own trade (potentially reversed afterward) reaps the price difference. func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
