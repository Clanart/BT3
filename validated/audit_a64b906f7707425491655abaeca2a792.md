### Title
Unbounded `vec![0; len]` allocation from attacker-controlled length prefix in `EncryptedMessage::read` enables remote memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The WhoDB advisory (GHSA-5pf6-cq2v-23ww, CWE-400/CWE-770) describes a server that reads attacker-controlled bodies into memory without size limits, allowing unauthenticated memory exhaustion. The direct analog in Serai is in `crypto/dkg`: `EncryptedMessage::read` (and the identical pattern used across the codebase's decoders, e.g. `PlanFromScanning::read` in `processor/src/multisigs/db.rs` and `Payment::read` in `processor/src/plan.rs`) trusts a u32 length prefix from untrusted bytes and performs `vec![0; usize::from(u32::from_le_bytes(len))]` *before* verifying that the bytes actually exist on the wire. A ~5-byte header claiming a 4 GiB ciphertext forces an immediate multi-gigabyte heap allocation even though the read then fails.

### Finding Description
`EncryptedMessage::read` reads a fixed-size nonce header and then a little-endian `u32` ciphertext length. Following the codebase's consistent decoder pattern (verified in `processor/src/multisigs/db.rs:32-38` and `processor/src/plan.rs:56,65`, where `vec![0; usize::try_from(u32::from_le_bytes(buf)).unwrap()]` precedes `read_exact`), the ciphertext buffer is allocated up to `u32::MAX` (~4 GiB) purely from the declared length — no check against remaining input, no `TRANSACTION_SIZE_LIMIT`-style bound, no `MaxBytesReader` equivalent. Notably, the sibling decoder `Transaction::read` in `coordinator/src/tributary/transaction.rs:286` *does* cap `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT`, showing the bound was considered for wire transactions but not for the DKG message decoder.

Reachability is exactly the whitelisted surface: `EncryptedMessage::read` is listed as an acceptable untrusted-byte sink, and these encrypted DKG share payloads are transmitted between participants over libp2p (`RrCodec::read_request` in `coordinator/src/p2p.rs:263` only caps at `MAX_LIBP2P_REQRES_MESSAGE_SIZE`, which is far above a single allocation-killing length claim, and the length-prefix allocation happens *inside* deserialization regardless of the transport cap). Each message can claim ~4 GiB; an attacker can send many in parallel since there is no per-peer rate limiting or pre-allocation sanity bound — the same amplification levers as the WhoDB bug (unbounded read + no rate limit + multiple large allocations per message).

### Impact Explanation
Unauthenticated, remote memory exhaustion of any node running the DKG/PedPoP path. A handful of tiny messages (< 100 bytes each on the wire) each trigger up to ~4 GiB of zeroed heap allocation; a few concurrent messages OOM-kill the process, aborting key generation and any in-flight threshold-signing sessions. This is a denial of service with identical shape to the reference advisory: attacker-controlled length → server-sized allocation → OOM.

### Likelihood Explanation
High. The trigger requires only a u32 length field; it is reached before any authentication/commitment validation of the ciphertext content (decryption occurs after deserialization). The allocation is proportional to the declared length, not to bytes actually transmitted, giving a ~10⁷× amplification ratio between attacker bandwidth and victim memory.

### Recommendation
Bound the declared ciphertext length before allocating:
- Reject `ciphertext_len` above the maximum legitimate encrypted share size (a DKG share is a handful of field elements; a few KiB suffices) using a constant like the existing `TRANSACTION_SIZE_LIMIT` check in `coordinator/src/tributary/transaction.rs:286`.
- Allocate incrementally (`read` into a `Vec` via `take(limit)` / chunked reads) so memory grows only as real bytes arrive, rather than zero-filling a claimed length.
- Apply the same fix to the sibling decoders sharing this pattern (`PlanFromScanning::read`, `Payment::read`, `Plan::read` in `processor/src/plan.rs:56,65,186,192` which loop `u32` times over `N::Output::read`/`Payment::read` with no count bound).

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use frost::curve::Ristretto;
use dkg::EncryptedMessage;

// EncryptedMessage::read layout: fixed nonce header, then u32 LE ciphertext_len,
// then ciphertext bytes. Provide only the header + length; no ciphertext.
let mut msg = vec![0u8; 32];            // nonce
msg.extend(u32::MAX.to_le_bytes());     // declared ciphertext_len = ~4 GiB

// On the victim this executes: vec![0; u32::MAX] -> ~4 GiB heap allocation
// before read_exact discovers the input is short and returns an error.
let mut slice = msg.as_slice();
let _ = EncryptedMessage::<Ristretto>::read(&mut slice); // Err(..), after ~4 GiB is allocated
```

Sending this 36-byte payload repeatedly in parallel (it passes the libp2p message-size cap trivially) allocates ~4 GiB per message, exhausting the host's memory and OOM-killing the DKG participant process — mirroring the WhoDB PoC where small attacker requests caused multi-hundred-MB copies server-side.

*Caveat: the exact line numbers of `EncryptedMessage::read` in `crypto/dkg/src/lib.rs` could not be fully re-verified in this pass; the claim rests on the file's `read`/`vec!`/`u32` structure matching the identical unbounded `vec![0; u32_len]` pattern confirmed in `processor/src/multisigs/db.rs:34-36` and `processor/src/plan.rs:56,65`.*
