Found a valid analog: `AddressBookV2` (KIP-286/287 permissionless staking registry) is deployed as a UUPS ERC1967 proxy at the fixed system address `0x400`, and its owner has unrestricted power to swap the implementation and redirect staking rewards/profile data for every validator.

### Title
Owner of the upgradeable `AddressBookV2` proxy can arbitrarily redirect validator staking rewards and corrupt consensus staking data — (File: blockchain/system/addressbook_v2.go)

### Summary
`AddressBookV2` is installed as a UUPS (ERC1967) upgradeable proxy at the fixed system address `AddressBookAddr` (`0x400`) [1](#0-0) , and its implementation slot is set by `InstallAddressBookV2` pointing to a governance-supplied logic contract [2](#0-1) . The contract exposes standard UUPS/Ownable functions including `owner()`, `transferOwnership`, and `Upgraded` events [3](#0-2) [4](#0-3) . This is the exact same "admin of the upgradeable proxy contract" pattern flagged in the Rolla `Controller.sol` report: whoever controls the proxy admin/owner key can call `upgradeToAndCall()` and replace the entire logic of a contract that other core protocol components trust unconditionally.

### Finding Description
`AddressBookV2` stores, per validator node, a `Profile` struct containing `NodeId`, `StakingContract`, `RewardAddress`, `TimeoutAt`, and `State` [5](#0-4) , and provides mutator functions such as `updateRewardAddress(nodeId, newRewardAddress)` [6](#0-5)  and `createNode(...)` [7](#0-6) . `kaiax/staking` reads this contract at every block via the `MultiCall` contract to compute effective stake and reward-eligible validators for the permissionless fork (`MultiCallStakingInfoPermissionless`) [8](#0-7) , and `kaiax/valset` consumes the same registry for validator-set transitions [9](#0-8) .

Because `AddressBookV2` is a UUPS proxy, its `owner` (set at genesis/deployment, see the `Owner` field used across `permissionless.go` alloc logic) can call `upgradeToAndCall(newImplementation, data)` to swap out the entire logic contract with an atomicity that bypasses any of the existing access-control checks that were compiled into the old logic. A malicious or compromised owner can deploy a new implementation that:
- Rewrites `getAllProfiles()` / `MultiCallStakingInfoPermissionless()` results to redirect all validator staking rewards (`RewardAddress`) to attacker-controlled addresses, or
- Fabricates `StakingContract` / stake-amount data consumed by `kaiax/staking` and `kaiax/valset`, causing state divergence between nodes that query at different times relative to the upgrade, or acceptance of blocks based on falsified staking/validator data.

This mirrors the Rolla issue precisely: a single admin-controlled `upgradeToAndCall` call on a proxy that other transaction-reachable protocol logic (staking, reward distribution, validator set) trusts as ground truth.

### Impact Explanation
Reward redirection and staking-data corruption at the `AddressBookV2` layer directly affects consensus-critical values: reward distribution to all current cluster validators and the effective-stake/valset computation used by `kaiax/staking` and `kaiax/valset` for every permissionless-fork block. Because `MultiCallStakingInfoPermissionless` is called from block-processing state-transition logic [10](#0-9) , a malicious implementation swap can cause fund misdirection (reward theft) and, depending on timing of nodes reading pre/post-upgrade state, divergence in staking/validator computation between honest nodes.

### Likelihood Explanation
Exploitation requires control of the `AddressBookV2` `owner` key (a single `upgradeToAndCall` transaction, reachable by any owner-key holder with no on-chain multisig/timelock enforced by the current code as shown) — same precondition as the original Rolla finding, which was itself judged Medium because "a governance attack must happen first." Here the equivalent precondition is compromise/misuse of the `AddressBookV2` owner key, which is plausible in a permissionless-staking deployment scenario before further governance hardening (e.g., timelocks) is added.

### Recommendation
- Enforce a timelock or multisig-guarded upgrade path (e.g., require a delay + on-chain announcement) before `upgradeToAndCall` on `AddressBookV2` takes effect, so validators/consumers of staking data can react.
- Consider making the reward-address/stake-accounting fields immutable or governed by a separate non-upgradeable escrow/registry contract, analogous to the Rolla recommendation to hold user-facing state in a non-upgradeable contract.
- Emit and require confirmation for `Upgraded` events with a mandatory min-delay before the new implementation becomes active for `kaiax/staking`/`kaiax/valset` consumption.

### Proof of Concept
1. `AddressBookV2` is installed at genesis via `InstallAddressBookV2`, setting `ERC1967ProxyV5Code` and the implementation slot [2](#0-1) .
2. The `owner` (set during permissionless alloc, e.g. `config.Owner`) holds full UUPS admin rights, confirmed by the `Owner`/`TransferOwnership`/`Upgraded` bindings [3](#0-2) .
3. The owner sends a transaction calling `upgradeToAndCall(maliciousImpl, initCalldata)`.
4. The malicious implementation overrides `getAllProfiles`/`updateRewardAddress` semantics so that the next block's `kaiax/staking.getFromState` → `MultiCallStakingInfoPermissionless` call [8](#0-7)  returns attacker-chosen `RewardAddress` values for all validators, redirecting subsequent block rewards.

**Uncertainty note:** I could not locate the actual Solidity source of `AddressBookV2`'s upgrade-authorization logic (e.g., `_authorizeUpgrade`) or confirm whether a timelock/multisig is already enforced off-chain/on-chain for the owner key, since the index only exposes the generated Go bindings and system-contract installer, not the full Solidity implementation. If a timelock/multisig is already enforced by the actual owner account (e.g., a governance multisig contract), the practical likelihood would be lower than stated above. A full Devin session with repo access would be needed to inspect `AddressBookV2.sol` directly to confirm this.

// InstallAddressBookV2 sets up the AddressBookV2 UUPS proxy at AddressBookAddr (0x400).
// logicAddr is the pre-deployed ABv2 implementation contract address
// (stored in ABv2DataContract.implementation()).
func InstallAddressBookV2(state *state.StateDB, logicAddr common.Address) error {
	// Set ERC1967 proxy code at 0x400
	if err := state.SetCode(AddressBookAddr, ERC1967ProxyV5Code); err != nil {
		return err
	}
	// Point proxy's implementation slot to the logic contract
	state.SetState(AddressBookAddr, common.BytesToHash(ImplementationSlot), lpad32(logicAddr))

	return nil

func (s *StakingModule) getFromState(header *types.Header, statedb *state.StateDB) (*staking.StakingInfo, error) {
	isForPrague := s.ChainConfig.IsPragueForkEnabled(new(big.Int).Add(header.Number, common.Big1))
	isForPermissionless := s.ChainConfig.IsPermissionlessForkEnabled(new(big.Int).Add(header.Number, common.Big1))
	num := header.Number.Uint64()

	// Bail out if AddressBook is not installed.
	// This is a common case for private nets.
	if statedb.GetCode(system.AddressBookAddr) == nil {
		logger.Trace("AddressBook not installed", "sourceNum", num)
		return emptyStakingInfo(num), nil
	}

	// Now we're safe to call the MultiCall contract.
	contract, err := system.NewMultiCallContractCaller(statedb, s.Chain, header)
	if err != nil {
		return nil, staking.ErrMultiCallCall(err)
	}

	callOpts := &bind.CallOpts{BlockNumber: header.Number}

	// Helper to read CL registry info, shared by permissioned and permissionless paths.
	// Permissionless is ordered after Prague (Randao <= Kaia <= Prague <= Permissionless),
	// so permissionless blocks always need CL registry info too.
	readCLInfo := func() (clRegistryResult, error) {
		var clRes clRegistryResult
		// If Registry is not installed, do not handle CL staking info.
		// In private network, Randao and Prague hardfork can be activated at the same block.
		// It leads to staking info inconsistency between block processing and rpc query since the Registry hasn't been installed when finalizing the header.
		// Note that Randao can't be activated after Prague according to fork ordering (Randao <= Kaia <= Prague).
		if statedb.GetCode(system.RegistryAddr) == nil || s.ChainConfig.IsRandaoForkBlockParent(header.Number) {
			logger.Trace("Registry not installed", "sourceNum", num)
			return clRes, nil
		}
		// Note that if CLRegistry is not registered in Registry,
		// it will return empty result and no error.
		clRes, err = contract.MultiCallDPStakingInfo(callOpts)
		if err != nil {
			return clRes, staking.ErrCLRegistryCall(err)
		}
		return clRes, nil
	}

	// Permissionless: read from AddressBookV2 (effective stake, reward-eligible only).
	if isForPermissionless {
		res, err := contract.MultiCallStakingInfoPermissionless(callOpts)
		if err != nil {
			return nil, staking.ErrAddressBookCall(err)
		}
		clRes, err := readCLInfo()
		if err != nil {
			return nil, err
		}
		return parsePermissionlessCallResult(num, res.Profiles, res.StakingAmounts, res.KefAddr, res.KifAddr, res.KpfAddr, clRes)
	}
