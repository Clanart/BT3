### Title
Deserialized `ThresholdKeys` never validate the secret share against the verification shares, so a forged key set yields an address whose received funds are unspendable — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a `secret_share` and a set of `verification_shares` from attacker-controlled bytes and passes them straight into `ThresholdKeys::new`. `ThresholdKeys::new` (and `ThresholdView`/signing built on it) never checks that `C::generator() * secret_share == verification_shares[i]`. The `group_key` is derived solely from the verification shares (`verification_shares[1..=t]` interpolated), while the secret material used to sign is the independent `secret_share` field. A crafted byte stream therefore produces internally inconsistent keys: the wallet/scanner advertises and deposits to a key nobody can sign for — the exact analog of "funds credited that can never be released".

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), the params `(t, n, i)`, interpolation, `secret_share`, and `n` verification shares are all read from the reader and passed to `ThresholdKeys::new`. `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) only validates:
- `verification_shares.len() == n` and all indices `<= n` (lines 355-365)
- `Constant` interpolation requires `t == n` (lines 367-374)
- computes `group_key` as the interpolation of `verification_shares[1..=t]` (lines 376-378)

It never verifies `C::generator() * secret_share == verification_shares[&params.i()]`. Legitimate constructors (`dkg::key_gen`, `pedpop::KeyMachine::calculate_share`, `musig`, `promote`) always supply consistent pairs, so the missing check is only exploitable via the deserialization path — which is precisely the path fed by untrusted bytes per `ThresholdKeys::read`.

Downstream, `Scanner::new(key)`/`p2tr_script_buf(key)` (`networks/bitcoin/src/wallet/mod.rs:80-85, 162-165`) derives the deposit address purely from `group_key()` = interpolated verification shares (plus offset). `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`) checks `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey` — which still passes, because group key consistency is fine; the problem is that `secret_share` doesn't correspond to `verification_shares[i]`, so every FROST signature share produced is invalid and any spend fails verification. Equivalently, an attacker can set `verification_shares[i]` to a *different* key than the honest network's so honest shares are blamed and the forged share is accepted.

### Impact Explanation
Any funds sent to the address derived from a forged `ThresholdKeys` are permanently unspendable: the reported/scanned balance (`Scanner::scan_transaction`, `ReceivedOutput`) exists on-chain and is attributed to the group key, but no valid threshold signature can ever be produced because the secret share does not match the verification share of participant `i`. This is a loss-of-funds analog of the escrow bug — value is "vested" to a beneficiary who can never claim it. Additionally, inconsistent verification shares corrupt FROST blame attribution: honest participants' shares fail against the attacker's injected shares.

### Likelihood Explanation
Exploitation requires an attacker to supply the serialized `ThresholdKeys` bytes that a node/integrator deserializes (key backup recovery, key import, or any peer-supplied key material path). The format is fully attacker-controlled (ID length/ID checked against a fixed `C::ID`, then raw `t`, `n`, `i`, interpolation tag, scalar, and `n` points). No other defense exists downstream — `view()` and signing trust `core.verification_shares` and `core.secret_share` as consistent.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]`, and for `Interpolation::Constant` additionally verify the interpolated/bound group key is consistent with the supplied binding factors. Reject inconsistent inputs with a `DkgError` before any group key or address is derived from them.

### Proof of Concept
1. Attacker chooses `t = n = 1`, `i = 1`, `Interpolation::Lagrange`.
2. Attacker picks a random scalar `s_bad` for `secret_share` and a random point `V` for `verification_shares[1]` such that `G * s_bad != V`.
3. Attacker serializes: `len(C::ID) || C::ID || 1u16 || 1u16 || 1u16 || 0x01 || s_bad || V` and submits it to a code path calling `ThresholdKeys::<Secp256k1>::read`.
4. `ThresholdKeys::new` accepts; `group_key() == V`. `Scanner::new(V)` produces a valid P2TR deposit address (`p2tr_script_buf` succeeds whenever `V` is even; retry `V` until even).
5. A payer sends BTC to that address; `scan_transaction` reports a `ReceivedOutput` — funds "received".
6. `SignableTransaction::new(...).multisig(&keys)` succeeds (script check passes), but `TransactionSignMachine::sign`/`complete` produce a signature share `d + e*s_bad` that fails verification against `V` — no valid spend can ever be produced; the funds are lost exactly as the escrow beneficiary's pending `X` is lost after `terminate()`.
