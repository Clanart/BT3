### Title
Silent commit of unresolved merge/rebase conflicts due to reliance on `git diff --check` marker counting as the "resolved" invariant - ([File: app/src/lib/git/diff-check.ts])

### Summary
The reported Hubble bug is fundamentally about a state machine that trusts a single derived numeric value (token `balanceOf == 0`) to decide "this process is finished/safe," while an attacker who controls the underlying data (auction proceeds/donations) can keep that value away from the terminating condition and thereby keep the system in an exploitable intermediate state. The Desktop analog is `hasUnresolvedConflicts()`/`getResolvedFiles()`, which decide whether a conflicted file is "resolved" purely from a derived count, `conflictMarkerCount`, produced by regex-matching the output of `git diff --check` in `getFilesWithConflictMarkers`. If that count is `0`, Desktop and the Copilot conflict-resolution flow treat the file as fully resolved and will silently commit/overwrite it, even though the working tree may still contain real, unresolved `<<<<<<<`/`=======`/`>>>>>>>` conflict markers that `git diff --check` failed to flag for a crafted-repository reason (e.g. a file marked `binary`/`-diff` via `.gitattributes`, or markers embedded in a file type `diff --check` doesn't scan).

### Finding Description
`getFilesWithConflictMarkers` (`app/src/lib/git/diff-check.ts:9-27`) derives the "number of conflict markers" for each conflicted file solely by parsing lines matching `leftover conflict marker` from `git diff --check` stdout: [1](#0-0) 

This count is stored as `conflictMarkerCount` in `parseConflictedState` (`app/src/lib/git/status.ts:83-127`), and is the *sole* signal used by `hasUnresolvedConflicts()` (`app/src/lib/status.ts:68-84`) to decide if a file still needs attention: [2](#0-1) 

That boolean in turn gates:
- `getResolvedFiles`/`getConflictedFiles` (`app/src/lib/status.ts:151-173`), which drive the conflicts dialog's file lists.
- `stageManualConflictResolution` (`app/src/lib/git/stage.ts:34-39`), which explicitly **returns early (no-op)** when `conflictMarkerCount === 0`, assuming the user "manually resolved" it.
- The Copilot auto-resolution apply path in `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7241-7256`), which **skips writing Copilot's resolved content** and lets the on-disk file "stand" whenever `hasUnresolvedConflicts` reports `false`: [3](#0-2) 

`git diff --check`'s "leftover conflict marker" detection is a heuristic: it does not scan files git treats as binary, and it depends on the file being part of the diff it's checking. A malicious/crafted branch or commit that a user merges/rebases/cherry-picks (an attacker-controlled repository object per the valid-impact scope) can be constructed so that:
1. The merged file is unmerged (has a real `AA`/`UU`/etc. porcelain status and both-sides conflict entries), and
2. It still contains literal `<<<<<<<`, `=======`, `>>>>>>>` marker text in the tree, but
3. `git diff --check` does not report it as having a "leftover conflict marker" for that path (for example due to a `.gitattributes` `-diff`/`binary` attribute shipped in the attacker's branch, mismatched line-ending/whitespace handling, or the file falling outside the compared diff hunks that `--check` inspects).

Because `conflictMarkerCount` will then read `0` from `getFilesWithConflictMarkers`, `hasUnresolvedConflicts` returns `false` even though the file is not actually resolved. Every consumer of that boolean — the conflicts dialog's "remaining conflicts" count, `stageManualConflictResolution`'s early-return guard, and the Copilot apply flow's "don't clobber the user's external resolution" skip — treats the file as safely resolved and will proceed to stage/commit it as-is, with the attacker's injected marker text (or attacker-controlled payload disguised as markers) baked into the resulting commit and eventual push, without ever surfacing it to the user for review. This mirrors the auction bug precisely: the "is this done?" check collapses to an exact/derived value (`conflictMarkerCount == 0` vs. `balanceOf == 0`) that the attacker (who supplies the repository content) can decouple from ground truth, letting Desktop finalize a state (auto-commit) that should still be blocked.

### Impact Explanation
This falls squarely within the valid-impact category "silent corruption of what the user commits or pushes": a user who merges/pulls/cherry-picks from an attacker-supplied branch or PR can end up with unresolved-conflict content (or attacker-crafted payload text) silently committed and pushed as if it were a clean, fully-resolved merge, with no warning in the conflicts dialog or the Copilot result view. Depending on the crafted content, this can also mean previously reviewed/approved code is replaced by conflicting/malicious content without any diff review step, since Desktop's own guard rails treat the file as already resolved.

### Likelihood Explanation
Exploitation only requires the victim to merge, rebase, or cherry-pick from a repository/branch the attacker controls (a normal, expected Desktop workflow, not "local access" or "malware already on host"). Crafting a `.gitattributes`-driven binary/`-diff` marking or a diff-check blind spot for a specific file is straightforward for an attacker who controls the branch content; this doesn't require any privileged operation. The main uncertainty (noted below) is exactly which `git diff --check` blind spots are reachable given how `getMergeConflictDetails`/`getRebaseConflictDetails`/`getWorkingDirectoryConflictDetails` invoke it (`app/src/lib/git/status.ts:392-453`) — this needs to be validated against the local git version's `diff --check` behavior, but the architectural flaw (trusting a heuristic external-tool count as the sole "resolved" signal, with a silent commit path on `count === 0`) is clearly present in the code regardless.

### Recommendation
Do not treat `conflictMarkerCount === 0` as proof of resolution. Cross-check against the git index/porcelain status (`AA`/`UU`/etc. unmerged entries persisting) before allowing `stageManualConflictResolution` to no-op or before letting `_applyCopilotConflictResolutions` skip writing resolved content. Additionally/alternatively, independently scan file contents for literal conflict marker sequences (not solely relying on `git diff --check`) before finalizing a resolution, and surface an explicit warning/dialog rather than silently completing the operation when the two signals disagree.

### Proof of Concept
1. Attacker creates a branch where a file that will conflict with the victim's branch has (or gains, via a crafted merge) a `.gitattributes` entry marking it `-diff` (or binary), while its content still contains literal `<<<<<<<`/`=======`/`>>>>>>>` text due to an unresolved three-way merge.
2. Victim, using Desktop, merges/pulls/cherry-picks the attacker's branch. Desktop detects `AA`/`UU` conflict status via porcelain, so the file appears in the conflicts dialog, but `getFilesWithConflictMarkers` (`app/src/lib/git/diff-check.ts:9-26`) does not report a "leftover conflict marker" line for that path because `git diff --check` skips it as binary/`-diff`.
3. `conflictMarkerCount` for the file resolves to `0` (`app/src/lib/git/status.ts:95-96`), so `hasUnresolvedConflicts` (`app/src/lib/status.ts:68-84`) returns `false`.
4. The file drops out of `getConflictedFiles` and appears in `getResolvedFiles` (`app/src/lib/status.ts:151-173`); if the victim uses "Resolve with Copilot," `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7241-7256`) treats the on-disk state as already resolved and skips overwriting it, leaving the attacker's marker/payload content in place.
5. The victim proceeds to "Continue Merge"/commit; Desktop stages and commits the file as resolved, and the victim subsequently pushes a commit containing the unresolved/attacker-controlled content without ever being warned.

```typescript
export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
```
