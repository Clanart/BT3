### Title
Precompile signature verification bypasses the compute-unit meter entirely, decoupling real CPU cost from charged compute units - (File: `program-runtime/src/invoke_context.rs`, `precompiles/src/secp256r1.rs`, `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`)

### Summary
The external report's root cause is a loop over an attacker-controlled list (`creators`) where each iteration performs real, potentially expensive work (external call + storage writes) that is charged at a flat/underestimated cost, letting the caller make the total real cost far exceed what the gas accounting assumes. The closest concrete Agave analog is the precompile programs (`secp256k1`, `ed25519`, `secp256r1`), whose `verify` functions loop `0..num_signatures` (attacker-controlled, up to 255 for secp256k1/ed25519, up to 8 for secp256r1) doing real elliptic-curve/hash cryptography per iteration [1](#0-0) , while the runtime's `process_precompile` path that re-executes this verification during instruction processing never touches the transaction's compute meter [2](#0-1) .

### Finding Description
`InvokeContext::process_precompile` calls the registered callback's `process_precompile`, which in turn calls `Precompile::verify` (i.e. the actual `secp256k1::verify` / `ed25519::verify` / `secp256r1::verify` functions) directly — with no call to `self.compute_meter.consume_checked(..)` anywhere in the function [2](#0-1) . This is confirmed by the test comment in `scheduler_cost_adjustment.rs`: "VM Execution: consume 0 from CU-meter" for a precompiled instruction, with the cost adjustment equal to the entire `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` [3](#0-2) .

By contrast, all other builtin programs (System, BPF Loader, ZK ElGamal proof, etc.) explicitly call `compute_meter.consume_checked(...)` for the actual cost of their work, e.g. the ZK ElGamal proof program charges per-proof-type fixed costs before doing the real verification work [4](#0-3) , and BPF loader management instructions consume fixed CU amounts before doing their work [5](#0-4) .

The actual cryptographic cost of a precompile invocation scales with `num_signatures`, an attacker-controlled byte in the instruction data, read directly off the wire in all three `verify` implementations [6](#0-5) [7](#0-6) [8](#0-7) . The `secp256r1` precompile is particularly heavy per-iteration, performing multiple `BigNum`, `EcPoint`, `EcKey` and OpenSSL `Verifier` operations per signature [9](#0-8) .

The cost-model's fixed per-signature multipliers (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) are used only for transaction/block-cost accounting and fee/scheduling purposes at the cost-model layer [10](#0-9) [11](#0-10)  — they are never enforced as an actual compute-unit deduction during the second, real execution of `verify()` that happens inside `process_precompile` at instruction-processing time. This means the number-of-signatures-driven real CPU work done during block execution/replay is completely decoupled from the compute-unit budget that is supposed to bound per-transaction and per-block execution cost, exactly mirroring the C4 report's core issue: a loop whose iteration count and per-iteration cost is attacker-controlled, with the accounting mechanism (gas estimate / CU cost) not actually gating the real work performed.

### Impact Explanation
If a leader/validator processes many transactions each carrying maximal precompile instructions (multiple `secp256r1`/`secp256k1`/`ed25519` instructions, each declaring the maximum permitted signature count), the real wall-clock CPU cost of processing/replaying the block can be substantially higher than what the compute-unit-based block-cost model assumes, because the second pass of verification during instruction execution consumes zero compute units. This creates a mismatch between the intended "materially underpriced compute" bound (execution should not exceed the block compute limit's implied CPU time) and the actual CPU time spent, which can slow down block production/replay across the cluster — a validator-execution-time DoS vector distinct from, but conceptually analogous to, the `AuctionHouse::_settleAuction` gas-DoS in the original report (attacker-controlled loop count × real external/heavy work not properly gated by the accounting mechanism).

### Likelihood Explanation
Transaction size limits (1232 bytes) and the requirement that signature/pubkey/message data be present somewhere in the transaction's instructions constrain how many total signatures can be packed into a single transaction, but multiple precompile instructions can be combined within one transaction and multiple transactions can be submitted in parallel per block, and the attacker fully controls `num_signatures`, offsets, and (for secp256r1) up to 8 signatures per instruction doing expensive OpenSSL EC math. This is a real, reachable code path that any user can exercise without needing special privileges (unprivileged transaction submission), and no compute-unit consumption is charged for the actual verification work at execution time, which is a concrete architectural gap rather than a theoretical one.

### Recommendation
Charge compute units for the actual verification work performed inside `InvokeContext::process_precompile`, proportional to `num_signatures` and the signature/curve type (mirroring the cost-model's `SIGNATURE_COST`/`SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` constants), via `self.compute_meter.consume_checked(...)` before or during the loop in each `verify` function (or in the `process_precompile` wrapper), so that the compute budget actually bounds the real cryptographic work done per instruction, consistent with how every other builtin program meters its cost.

### Proof of Concept
Not independently reproduced in this analysis (no execution environment available); the finding is derived directly from static code inspection: `process_precompile` never calls `compute_meter.consume_checked` [2](#0-1) , and the test `test_builtin_ix_precompiled` explicitly documents/asserts "consume 0 from CU-meter" for a precompile instruction [3](#0-2) , while the `verify` functions perform `O(num_signatures)` real cryptographic work driven by attacker-supplied instruction data [8](#0-7) . A background Devin agent with a build/test environment could construct a transaction with multiple maximal `secp256r1`/`secp256k1`/`ed25519` instructions and measure wall-clock time of `process_precompile` versus reported `compute_units_consumed` to empirically confirm the zero-CU-consumption claim.

    /// Returns signature details and the total signature cost
    fn get_signature_cost(transaction: &impl TransactionMeta) -> u64 {
        let signatures_count_detail = transaction.signature_details();

        signatures_count_detail
            .num_transaction_signatures()
            .saturating_mul(SIGNATURE_COST)
            .saturating_add(
                signatures_count_detail
                    .num_secp256k1_instruction_signatures()
