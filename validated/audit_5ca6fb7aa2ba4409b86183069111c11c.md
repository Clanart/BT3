Based on my investigation, I found a legitimate structural analog in the same bug class (an unhandled/assumed-exhaustive variant in parsing attacker-influenced repository data), but it manifests as **silent misclassification** rather than a crash — which better fits the accepted impact criteria than the `DiffParser` throw path (which is DoS-only and therefore excluded).

### Title
Malformed/unrecognized git raw status codes are silently coerced to "Modified" - ([File: app/src/lib/git/log.ts])

### Summary
`exitCodeFromTx()` in the TON report assumed a Sum type (`TrComputePhase`) always resolves to the `TrPhaseComputeVm` variant, panicking when the attacker-influenced transaction instead produced the `TrPhaseComputeSkipped` variant. GitHub Desktop's `mapStatus()` has the analogous defect: it enumerates only the git raw-status letters it expects (`M`, `A`, `?`, `D`, `R`, `C`, `R###`, `C###`) and, for anything else — including malformed or unhandled variants that a crafted repository/commit can produce (e.g. `U` unmerged, `T` typechange, or a bare `R`/`C` without an accompanying old-path record) — falls through to a default that silently pretends the file is `Modified`.

### Finding Description
`mapStatus` is invoked from `parseRawLogWithNumstat`, which parses `git log --raw --numstat -z` output — output entirely derived from the content and history of a cloned/fetched repository, which is attacker-controlled in the threat model (malicious repo, malicious remote/proxy response, or a crafted commit merged/cherry-picked into history). [1](#0-0) 

Unlike the TON `TrComputePhase`, which is a strict two-variant Sum type, the git raw status field is an open string that git itself can emit values Desktop never accounts for (e.g. `U` for unmerged paths in a conflicted merge commit, or `T` for a type change such as file → symlink). When none of the explicit `if` branches match, execution reaches the final unconditioned fallback: [2](#0-1) 

This silently returns `{ kind: AppFileStatusKind.Modified, submoduleStatus }` for a status the code never actually validated, discarding the old-path/rename/copy/type information that a correct classification would have carried. Additionally, in the raw-diff+numstat merge routine, the numstat-side line-consumption logic (`i += 2` for renames/copies) is driven by `isCopyOrRename(files[numStatCount].status)` — i.e., by the *already-miscategorized* status — so a status that should have been `Renamed`/`Copied` but got coerced to `Modified` will desynchronize the index used to pair numstat records with raw-diff records: [3](#0-2) 

This is structurally the same class of bug as M-34: a parser assumes it has covered all variants of attacker-influenced structured data and silently mishandles the case it didn't anticipate, rather than failing safe or explicitly rejecting the unknown state.

### Impact Explanation
Because history/changed-file views (`getChangedFiles`, `getStashedFiles`) rely on this mapping, a crafted repository can cause Desktop to display an incorrect file status/old-path for a commit — masking a rename, copy, or type change as a plain modification. If a user relies on this display when deciding what to cherry-pick, revert, or push forward (e.g. via "Amend commit," "View file at commit," or the changes list feeding subsequent git operations), the mismatch between actual and displayed file state constitutes the kind of "silent corruption of what the user commits/pushes" that is in scope. The desynchronized index in `parseRawLogWithNumstat` also risks associating stat/line-count data with the wrong file entry.

### Likelihood Explanation
Requires no local access, admin rights, or social engineering beyond the normal act of cloning or fetching a repository (or pulling in a commit) — the same attacker model as the TON report's "malicious message sender." However, I was not able to fully confirm with the tools available (which are exhausted for this session) whether git ever actually emits an unhandled letter (`U`, `T`) through the specific `--raw` invocation Desktop uses, or whether some other guard upstream normalizes these before reaching `mapStatus`. This uncertainty means the likelihood is moderate rather than confirmed, and should be validated against real git output for merge-conflict and typechange scenarios.

### Recommendation
Make `mapStatus` exhaustive and fail loudly instead of silently defaulting: enumerate every raw status letter git can emit (including `U` and `T`), and for any truly unrecognized value throw/log rather than falling back to `Modified`. This mirrors the TON fix recommendation of explicitly checking the discriminant instead of assuming a fixed variant.

### Proof of Concept
Not independently verified in this session due to tool-call exhaustion. A concrete PoC would involve constructing a malicious repository containing a merge commit with unresolved-conflict raw status (`U`) or a typechange (`T`) entry, cloning it in Desktop, and observing that `getChangedFiles`/history view reports the file as `Modified` with no rename/old-path metadata instead of surfacing the real status — this should be confirmed with an actual `git log --raw --numstat -z` run against such a commit before treating this as fully validated.

function mapStatus(
  rawStatus: string,
  oldPath: string | undefined,
  srcMode: string,
  dstMode: string
): PlainFileStatus | CopiedOrRenamedFileStatus | UntrackedFileStatus {
  const status = rawStatus.trim()
  const submoduleStatus = mapSubmoduleStatusFileModes(status, srcMode, dstMode)

  if (status === 'M') {
    return { kind: AppFileStatusKind.Modified, submoduleStatus }
  } // modified
  if (status === 'A') {
    return { kind: AppFileStatusKind.New, submoduleStatus }
  } // added
  if (status === '?') {
    return { kind: AppFileStatusKind.Untracked, submoduleStatus }
  } // untracked
  if (status === 'D') {
    return { kind: AppFileStatusKind.Deleted, submoduleStatus }
  } // deleted
  if (status === 'R' && oldPath != null) {
    return {
      kind: AppFileStatusKind.Renamed,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: false,
    }
  } // renamed
  if (status === 'C' && oldPath != null) {
    return {
      kind: AppFileStatusKind.Copied,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: false,
    }
  } // copied

  // git log -M --name-status will return a RXXX - where XXX is a percentage
  if (status.match(/R[0-9]+/) && oldPath != null) {
    return {
      kind: AppFileStatusKind.Renamed,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: status !== 'R100',
    }
  }

  // git log -C --name-status will return a CXXX - where XXX is a percentage
  if (status.match(/C[0-9]+/) && oldPath != null) {
    return {
      kind: AppFileStatusKind.Copied,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: false,
    }
  }

  return { kind: AppFileStatusKind.Modified, submoduleStatus }
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}
