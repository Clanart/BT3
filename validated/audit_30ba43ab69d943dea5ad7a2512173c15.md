## Finding confirmed — Nested/reentrant precompile calls cause double-application of bank events to the EVM StateDB

### Title
Balance duplication via overlapping event windows in nested `BalanceHandler`/`runNativeAction` calls — (File: `precompiles/common/precompile.go`, `x/vm/statedb/statedb.go`)

### Summary
When a stateful precompile's native action triggers a nested call into another (or the same) `BalanceHandler`-enabled precompile, the inner call's bank events are captured and applied to the EVM `StateDB` **twice**: once by the inner call's own `AfterBalanceChange`, and again by the outer call's `AfterBalanceChange`, because both calls share the same `sdk.Context`/`EventManager` via `StateDB.cacheCtx`.

### Finding Description
`StateDB.GetCacheContext()` lazily creates `s.cacheCtx` once (guarded by `s.writeCache == nil`) and returns the **same** cached context object on every subsequent call, including from nested/re-entrant precompile invocations: [1](#0-0) 

`runNativeAction` uses this shared context for `BeforeBalanceChange`/`AfterBalanceChange` bookkeeping. Each call creates its own `BalanceHandler` instance, but that instance's `prevEventsLen` is measured against the *shared* `EventManager` on the shared `ctx`: [2](#0-1) 

`BeforeBalanceChange` snapshots `len(ctx.EventManager().Events())`, and `AfterBalanceChange` replays every event from that index to the *current* end of the list: [3](#0-2) [4](#0-3) 

Sequence for a nested call (outer precompile A → contract callback → inner precompile B, both sharing the same `EVM.StateDB`/`cacheCtx`):
1. Outer `runNativeAction` for A: `BeforeBalanceChange` records `prevEventsLen = N0`.
2. A's `action(ctx)` emits `k` bank events, then makes a nested EVM call that invokes precompile B.
3. Inner `runNativeAction` for B calls `GetCacheContext()` → same shared `ctx` (same `EventManager`). `BeforeBalanceChange` records `prevEventsLen = N0+k` (already includes A's `k` events).
4. B emits `m` events; B's own `AfterBalanceChange` correctly applies only `events[N0+k : N0+k+m]` to StateDB.
5. Control returns to A. Its `AfterBalanceChange` is called on the *same* `ctx`, and processes `events[N0 : N0+k+m]` — which **re-applies B's `m` events that were already committed to the StateDB by step 4**.

The result: the coins moved during the nested call are subtracted/added twice on the EVM `StateDB`, while the bank keeper's underlying ledger (updated once via the actual `SendCoins`/keeper calls) reflects the change only once. This breaks the native/EVM balance parity invariant described in `BalanceHandler`'s own documentation and duplicates spendable EVM-visible balance.

This exact defect is independently reproduced by the repository's own regression test, which states the bug plainly: [5](#0-4) 
using a debug precompile that recursively calls back into itself via `CallEVMWithData`: [6](#0-5) 

The debug precompile used in the test is explicitly test-only (`"Package debug defines test utilities... *not* for use in production"`), so I could **not confirm** which specific production precompile provides a synchronous, attacker-triggerable nested-precompile-call path (e.g., `staking.Undelegate` calling back into `staking.Delegate` as suggested in the question) within the scoped code I reviewed. The vulnerable mechanism itself — shared `cacheCtx`/`EventManager` causing overlapping `BeforeBalanceChange`/`AfterBalanceChange` windows — is present in production files (`precompiles/common/precompile.go`, `x/vm/statedb/statedb.go`) and is triggered by *any* nested call between two `BalanceHandlerFactory`-enabled precompiles within the same EVM call frame, not merely the debug one.

### Impact Explanation
If a real, attacker-reachable nested precompile call chain exists (e.g., via a malicious contract that receives control mid-precompile-execution and calls back into another stateful precompile such as `staking`, `distribution`, `bank`, `erc20`, `gov`, `slashing`, `ics20`, or `werc20` — all of which use the shared `BalanceHandlerFactory`/`RunNativeAction` pattern), the inner call's balance delta is double-counted on the EVM `StateDB` relative to the bank keeper's actual ledger. This is an accounting-corruption / balance-duplication bug: EVM-visible balance can exceed real backing coins, enabling the attacker to subsequently transfer/spend value that was never actually credited by the bank keeper — a critical unauthorized duplication of spendable value.

### Likelihood Explanation
The core mechanism is unconditionally present whenever two `RunNativeAction` calls nest within one EVM call tree, since `GetCacheContext()` always returns the same cached context after first creation. However, exploitability depends on finding a **production** precompile path where the native action itself (not test/debug code) causes a synchronous re-entrant call into another `BalanceHandler`-enabled precompile within the same transaction — I was unable to verify such a path in the scoped, non-test precompile code within the time/tools available. The repository's own dedicated regression test (using debug-only tooling) indicates the maintainers are aware of and are actively testing for this class of bug, suggesting it's a live but only partially confirmed-in-production concern.

### Recommendation
- Make `BeforeBalanceChange`/`AfterBalanceChange` re-entrant-safe by tracking event-window boundaries per-call (e.g., pass and restore the caller's `prevEventsLen`, or exclude any event range already consumed by a nested `AfterBalanceChange`) instead of relying on a single shared `EventManager` position.
- Alternatively, give each nested `runNativeAction` invocation an isolated `EventManager`/sub-context so inner and outer event windows cannot overlap.
- Add an explicit re-entrancy guard/counter (beyond the existing `MaxPrecompileCalls` check in `AddPrecompileFn`) around `BalanceHandler` usage to detect and reject overlapping windows.

### Proof of Concept

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
