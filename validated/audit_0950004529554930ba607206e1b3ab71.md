### Title
Flash-loan-driven reward dilution/theft via unprotected, instantly-applied `donateRewards`/`queueNewRewards` in `BaseRewardPool` reward accounting - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` distribute reward tokens to stakers by instantly bumping `rewardPerTokenStored` in proportion to the pool's **live** `totalStaked()` at the moment a reward is provisioned, with no time-vesting/streaming and no minimum staking duration. Because `MasterMagpie.deposit`/`withdraw` (the only way to change a user's staked balance in these pools) have no lock, cooldown, or same-block/flash-loan protection, an attacker can flash-loan a large amount of the pool's staking token, deposit it immediately before a reward injection, and withdraw immediately after harvesting, all in one transaction. This lets the attacker capture a disproportionate share of freshly injected/bribed rewards, diluting the yield legitimately accrued by long-term stakers — directly analogous to the reported "manipulate pools within one transaction using a flash loan" bug class.

### Finding Description
`_provisionReward` in `BaseRewardPool.sol` computes the reward-per-token increment using the pool's current total stake read live from `MasterMagpie`: [1](#0-0) 

`totalStaked()` simply reads `IERC20(stakingToken).balanceOf(operator)` at call time — i.e., whatever is staked in `MasterMagpie` right now, with no snapshotting or time-weighting: [2](#0-1) 

Crucially, `donateRewards` is **unauthenticated** — any address can call it to inject reward tokens and trigger the instantaneous `rewardPerTokenStored` update: [3](#0-2) 

Meanwhile, staking/unstaking through `MasterMagpie.deposit`/`withdraw` is open to any wallet, has no lock period, and immediately updates `user.amount`/`user.available` and harvests pending rewards on both deposit and withdraw: [4](#0-3) [5](#0-4) 

Because a user's earned reward is computed as `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid)`, and `rewardPerTokenStored` jumps discretely at the instant a reward is provisioned (rather than streaming continuously over time), a staker who deposits **immediately before** that jump and withdraws **immediately after** harvesting captures a full pro-rata share of the reward despite having staked for zero economic time: [6](#0-5) 

The identical pattern exists in `BaseRewardPoolV2.sol`'s `_provisionReward`/`_earned`, and in the specialized rewarders (`vlMGPBaseRewarder.sol`, `mWOMSVBaseRewarder.sol`) which share the same discrete `rewardPerTokenStored` update logic: [7](#0-6) 

### Impact Explanation
An attacker can:
1. Flash-loan a large amount of the LP/staking token (or wrap it via `WombatPoolHelper.depositLP`/`deposit`, which stakes into `MasterMagpie` on the caller's behalf) — [8](#0-7) .
2. In the same transaction, call `donateRewards` (unauthenticated) themselves or front-run/back-run a manager's `queueNewRewards`/bribe distribution to instantly inflate `rewardPerTokenStored` while their newly deposited stake is counted in `totalStaked()`.
3. Immediately withdraw (`MasterMagpie.withdraw`), which harvests the reward at the now-updated `rewardPerTokenStored`, before repaying the flash loan.

This dilutes/steals the yield that should have accrued to genuine long-term stakers of that reward pool, since the attacker's transient, flash-loaned stake absorbs a share of `rewardPerTokenStored` increments proportional to its (temporarily inflated) size, without contributing any real staking duration. This constitutes theft of unclaimed yield belonging to other users, falling within the accepted impact categories.

### Likelihood Explanation
Every action required (flash-loaning the staking/LP token, depositing/withdrawing via `MasterMagpie` or the pool helpers, and calling the unauthenticated `donateRewards`) is reachable by any ordinary wallet in a single atomic transaction, with no privileged role, admin cooperation, or governance action needed. The only external dependency is availability of a flash loan for the specific LP/staking token, which is a standard, low-cost primitive on any DeFi chain.

### Recommendation
- Stream/vest injected rewards over time (e.g., a `rewardRate`/`periodFinish` model as used in `WomUp.sol`'s `rewardPerToken()`) instead of applying the full amount instantly to `rewardPerTokenStored`.
- Alternatively/additionally, snapshot a user's eligible stake using a time-weighted or block-delay mechanism (e.g., require `block.number > depositBlock` before rewards from a given injection can be harvested), or restrict/rate-limit `donateRewards` to trusted managers and add a minimum holding period before newly deposited stake counts toward `earned()`.
- Add flash-loan protections such as `_preventSameTxOrigin`-style same-block deposit/withdraw checks in `MasterMagpie._deposit`/`_withdraw` for a given `(stakingToken, account)` pair.

### Proof of Concept
1. Attacker flash-loans a large amount of `stakingToken` (e.g., a Wombat LP receipt token).
2. Attacker calls `WombatPoolHelper.depositLP()` / directly stakes into `MasterMagpie.deposit(stakingToken, hugeAmount)` — [9](#0-8) , inflating `totalStaked()` for that pool's `BaseRewardPool`.
3. In the same transaction, attacker (or a pending manager tx that attacker sandwiches) calls `donateRewards`/`queueNewRewards`, causing `_provisionReward` to compute `rewardPerTokenStored += (amountReward * 10**decimals) / totalStaked()` using the now-inflated `totalStaked()` — [10](#0-9) .
4. Attacker calls `MasterMagpie.withdraw(stakingToken, hugeAmount)`, which internally calls `_harvestBaseRewarder` → `BaseRewardPool.getReward`, paying out `balanceOf(attacker) * rewardPerTokenStored` worth of reward tokens to the attacker — [11](#0-10) .
5. Attacker repays the flash loan within the same transaction, keeping the harvested reward share that was diluted from genuine long-term stakers.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
