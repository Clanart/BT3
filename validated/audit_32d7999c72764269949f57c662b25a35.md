### Title
`castVotes()` uses inconsistent numerator/denominator basis when `delegatedPool` votes alongside regular users, inflating `targetVote` for shared pools - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.vote()` adds every non-`delegatedPool` caller's positive vote delta to the global `totalVlMgpInVote` accumulator, but skips this accounting entirely when `msg.sender == delegatedPool` [1](#0-0) . However, `delegatedPool` is not restricted from calling `vote()` on any of the regular pools stored in the `pools` array (only the delegatedPool's own address is excluded from being pushed into `pools` in `addPool`) [2](#0-1) . This means `pool.totalVoteInVlmgp` (the numerator used in `castVotes()`) can include `delegatedPool`'s contribution, while `totalVlMgpInVote` (the denominator) never does, producing a numerator/denominator basis mismatch.

### Finding Description
In `vote()`, any caller's positive delta increases `pool.totalVoteInVlmgp` for the target pool unconditionally [3](#0-2) . Then, only if `msg.sender != delegatedPool`, the same delta is added to the global `totalVlMgpInVote` [1](#0-0) . If `delegatedPool` itself calls `vote()` targeting a normal, already-registered pool (poolA) instead of only affecting its own dedicated slot, poolA's `totalVoteInVlmgp` increases by `delegatedPool`'s vote amount, but `totalVlMgpInVote` does not.

In `castVotes()`, the proportional target vote for every pool is computed as:
```
targetVote = pool.totalVoteInVlmgp * totalVotes() / totalVlMgpInVote
``` [4](#0-3) 
Because `pool.totalVoteInVlmgp` (numerator) can carry `delegatedPool`'s untracked contribution while `totalVlMgpInVote` (denominator) is computed from a strictly smaller set of votes (excluding `delegatedPool`), the ratio for the pool(s) that `delegatedPool` also voted on becomes inflated relative to pools that only regular users voted on. This is a real, code-verifiable inconsistency between the numerator's accounting basis (`totalVoteInVlmgp`, updated for all callers) and the denominator's accounting basis (`totalVlMgpInVote`, updated only for non-delegatedPool callers). There is no modifier, check, or reconciliation step that prevents `delegatedPool` from voting on the same shared pools as regular users, nor does `castVotes()` normalize per-pool contributions by source.

An attacker does not even need to act — the mismatch is structural whenever `delegatedPool` votes for any pool present in the shared `pools` array. An unprivileged actor can amplify the effect by voting a comparatively small amount on the same pool `delegatedPool` has heavily voted for, right before `castVotes()` is called, causing that pool's `targetVote` to capture a disproportionate share of the total emitted votes (`totalVotes()`), at the expense of other pools whose proportional share is depressed because they are competing against an artificially shrunk denominator basis while the numerator for the "shared" pool is boosted.

### Impact Explanation
This directly manipulates a governance/voting result: the aggregate vote allocation to Wombat's voter contract via `wombatStaking.vote()` no longer reflects true proportional voting power. Pools that intersect with `delegatedPool`'s votes receive systematically inflated `targetVote`, redirecting bribe rewards and veWOM voting emissions away from other pools that vote fairly. This falls under "governance voting result manipulation," matching the specified Immunefi scoped impact class.

### Likelihood Explanation
The precondition is only that `delegatedPool` is set to a nonzero address (`setDelegatedPool`, an admin action already assumed as a normal system state, not an attack) and that it votes on at least one pool shared with regular voters. Given that, any unprivileged EOA can then vote a comparatively small amount on that same pool immediately before `castVotes()` is invoked (which is itself a public, callable-by-anyone function) to benefit from/amplify the skew. No special capital or privileged role is required beyond holding locked MGP (vlMGP) to vote, and the action is repeatable every voting epoch.

### Recommendation
Make the numerator and denominator use the same accounting basis: either (a) always include every caller's vote (including `delegatedPool`) in `totalVlMgpInVote`, or (b) exclude `delegatedPool`'s contribution from `pool.totalVoteInVlmgp` when computing `targetVoteInLMGP` in `castVotes()`, e.g. by tracking a separate `delegatedPoolVoteInVlmgp` per pool and subtracting it from `pool.totalVoteInVlmgp` before the proportional calculation. Additionally, consider restricting `delegatedPool` from calling `vote()` on pools other than its own dedicated allocation path, if that is the intended design.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatBribeManager`, set `delegatedPool` to a mock contract address (via `setDelegatedPool`).
2. `addPool` for `poolA` and `poolB` (both pushed to `pools[]` since neither equals `delegatedPool`).
3. Have `delegatedPool` (impersonated) call `vote([poolA], [+1000e18])` — assert `poolA.totalVoteInVlmgp == 1000e18` and `totalVlMgpInVote == 0` (unchanged).
4. Have a regular attacker user call `vote([poolA], [+10e18])` and another regular user call `vote([poolB], [+100e18])` — assert `totalVlMgpInVote == 110e18`.
5. Call `castVotes()` and compute `targetVote` for poolA and poolB manually using the same formula as the contract.
6. Assert `targetVote(poolA) = 1010e18 * totalVotes() / 110e18` is disproportionately large — e.g., show `targetVote(poolA) + targetVote(poolB) != totalVotes() * (sum of totalVoteInVlmgp among only tracked/non-delegated voters)/totalVlMgpInVote`, confirming the conservation-of-vote-budget invariant is broken and poolA captures more than its fair proportional share purely due to the numerator including `delegatedPool`'s untracked vote.
