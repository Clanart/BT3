### Title
CSRF bypass via cross-account session token in `CsrfProtection` — signature is verified but never bound to the resource/session being mutated (`File: lib/shopify_app/controller_concerns/csrf_protection.rb`)

### Summary
`ShopifyApp::CsrfProtection` disables Rails' standard CSRF check whenever *any* validly-signed Shopify session token (JWT) is present in the request, regardless of which shop/account that token was issued for. This mirrors the root cause of the referenced report: a signature/signer is validated, but the code never checks that the verified identity is actually authorized for the account/context the action is being performed against.

### Finding Description
`CsrfProtection` wires up `protect_from_forgery` to be skipped whenever `valid_session_token?` returns true: [1](#0-0) 

`valid_session_token?` only checks that `jwt_payload` is present — i.e., that the `Authorization: Bearer <jwt>` header decodes/verifies as *some* validly-signed Shopify JWT: [2](#0-1) 

The JWT is parsed via `ShopifyApp::WithShopifyIdToken#jwt_payload`, which only verifies the token's cryptographic signature/expiry — it does not compare the token's `dest` (shop) or `sub` (user) claims against the shop/user the mutating action is actually going to operate on (e.g. `params[:shop]`, or the shop bound to the browser's cookie-based session used elsewhere in the same request): [3](#0-2) 

Because the app's session token signing secret (`ShopifyAPI::Context.api_secret_key` / app client secret) is the same for every shop that installs the app, **any merchant/attacker who has installed the app on their own store can mint a session token that will satisfy `valid_session_token?` for every other request in the application**, including requests whose actual mutating logic is driven by a completely different account context (e.g. the Rails cookie session, or `params[:shop]`) — this is exactly the same class of bug as the report: the signer is verified, but never checked to be "allowed" for the account/resource being acted on.

This directly parallels `VerifierBase.verifyCommon()`/`validateAndCancel()`: signature checked against `common.signer`, action executed against unrelated `common.account`, with no linkage enforced between the two.

### Impact Explanation
An attacker who has legitimately installed the app on their own (attacker-controlled) shop can obtain a validly signed session token for that shop. Because `valid_session_token?` performs no binding check between the token's shop/user and the target of the state-changing request, that attacker-controlled token can be used to satisfy the CSRF-bypass condition for *any* controller action in the host application that includes `ShopifyApp::CsrfProtection`, as long as the attacker can get the header attached to a cross-site/forged request (e.g., via an app-embedded `fetch` from an attacker page, or any client-side code path an attacker fully controls under their own installed shop). This defeats the purpose of CSRF protection for any state-changing endpoint relying on this concern, potentially enabling state-changing requests to be forged against a different shop's browser session (cookie-authenticated) than the one the token was issued for.

### Likelihood Explanation
Moderate-to-low but concretely reachable: it requires the attacker to install the app on a shop they control (a normal, unprivileged, self-service action any merchant can perform), and to be able to attach a custom `Authorization` header to the forged request (feasible from any origin the attacker controls, e.g. a page they serve, using `fetch` with a manually set header — no special CORS permission needed to *send* a header if the target endpoint doesn't require credentials to be blocked by CORS, and Shopify session-token flows are explicitly designed to be sent this way from JS). The gem exposes no guard preventing an unrelated shop's token from satisfying this check for another shop's action.

### Recommendation
`valid_session_token?` should not just check `jwt_payload.present?`. It must additionally verify that the token's shop (`jwt_shopify_domain`/`dest`) and/or user (`jwt_shopify_user_id`/`sub`) match the account/session context that the current request is actually operating against (e.g., the currently loaded `current_shopify_session`'s shop, or `params[:shop]`), analogous to how `TokenExchange#reject_mismatched_requested_shopify_domain` already does for the token-exchange flow: [4](#0-3) 

That existing pattern should be reused/enforced inside `CsrfProtection` so that a token is only accepted as CSRF-bypass proof when it matches the shop/session the request is bound to.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and, through normal embedded-app usage, obtains a validly-signed session token `T` (signed by the shared app secret) with `dest: "https://attacker-shop.myshopify.com"`.
2. Victim merchant has an active browser session (cookie-based) with the same app for `victim-shop.myshopify.com`.
3. Attacker lures the victim into visiting an attacker-controlled page while their cookie session with the app is still valid; the page issues a cross-origin `fetch()` POST to a state-changing endpoint in the app that includes `ShopifyApp::CsrfProtection`, setting `Authorization: Bearer T` (attacker's own valid token) — the victim's session cookies are attached automatically by the browser to the same-origin request.
4. `protect_from_forgery` is skipped because `valid_session_token?` returns true (token `T` decodes/verifies fine), even though `T` belongs to the attacker's shop, not the victim's. The request proceeds and executes using the victim's cookie-derived session/account, achieving a CSRF bypass.

*(Note: exploitability in step 3 depends on the target app's own CORS/network configuration allowing the cross-origin request with a custom header to reach the server; this is an application-integration detail outside `shopify_app` itself, but the missing binding check inside the gem is the root cause enabling the bypass once the request reaches the controller.)*

```ruby
# frozen_string_literal: true

module ShopifyApp
  module CsrfProtection
    extend ActiveSupport::Concern
    included do
      include ShopifyApp::WithShopifyIdToken
      protect_from_forgery with: :exception, unless: :valid_session_token?
    end

    private

    def valid_session_token?
      jwt_payload.present?
    end
  end
end
```
