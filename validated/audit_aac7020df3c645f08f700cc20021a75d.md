### Title
Unhandled `ValueError` in condition-opcode parsing crashes wallet signing on a malicious spend — (File: `chia/consensus/condition_tools.py`)

### Summary
`parse_sexp_to_condition()` converts a raw CLVM output atom into a `ConditionOpcode` via `ConditionOpcode(op)` without guarding against unrecognized-but-well-formed single-byte values, and its caller `conditions_for_solution()` only catches `Program.EvalError`, letting the resulting `ValueError` propagate uncaught. This is directly analogous to CVE-2015-5194, where `log_config_command()` in `ntp_parser.y` crashed `ntpd` because a crafted, syntactically valid input value was not defensively rejected before being consumed by downstream logic, causing an unhandled failure.

### Finding Description
`chia/consensus/condition_tools.py:19-45` (`parse_sexp_to_condition`) only validates that the opcode atom has length 1: [1](#0-0) 

If `op` is exactly one byte but not one of the values defined in `ConditionOpcode` (e.g. any of the many unused byte values between the defined opcodes such as `2`-`42`, `53`-`59`, `68`-`69`, `77`-`79`, `88`-`89`, `91`+), `ConditionOpcode(op)` raises a plain `ValueError` rather than the `ConsensusError` the function otherwise uses for malformed input: [2](#0-1) 

The sole caller, `conditions_for_solution()`, only guards against `Program.EvalError`: [3](#0-2) 

so the `ValueError` from an unrecognized opcode is never converted to a `ConsensusError` and propagates as an unhandled exception.

This path is reachable by an unprivileged, untrusted party: `WalletSigner.gather_signing_info()` runs `conditions_dict_for_solution()` (which calls `conditions_for_solution()` internally) directly on the `puzzle_reveal`/`solution` of every `Spend` being signed: [4](#0-3) 

This is invoked from `sign_offers()` when accepting/signing an offer supplied by an untrusted counterparty, and from `sign_bundle()`/`sign_transactions()` on arbitrary coin spends the wallet is asked to sign: [5](#0-4) 

An attacker only needs to craft a puzzle whose CLVM output (a condition list) contains an atom that is exactly one byte long but not a value defined by `ConditionOpcode`. Such an inner puzzle (e.g. layered under an otherwise-valid offer or a spend they ask the target wallet to co-sign) will run successfully through `run_with_cost()` (no `EvalError`), then fail unhandled inside `parse_sexp_to_condition()` when the wallet attempts to derive AGG_SIG conditions for signing.

### Impact Explanation
This is a spend/offer-triggered processing halt reachable from an untrusted offer counterparty or any caller requesting the wallet sign an attacker-supplied spend. Because the exception is unhandled at the point of raise, it can abort the in-progress signing/offer-acceptance operation for the victim wallet, denying that operation, and — depending on how far up the call stack the exception is caught — can disrupt the wallet's trade/signing task. This matches the accepted impact category "a spend-triggered transaction-processing halt."

### Likelihood Explanation
Likelihood is high for anyone who can supply a coin spend or offer to be signed: crafting a puzzle that outputs a `CREATE_COIN`-like list with a single stray one-byte atom in an unused numeric slot is trivial CLVM authorship, requires no privileged access, and does not require valid signatures since it is exercised before/while gathering signing info, not after successful mempool admission.

### Recommendation
In `parse_sexp_to_condition()`, wrap `ConditionOpcode(op)` in a try/except and raise `ConsensusError(Err.INVALID_CONDITION, ...)` on `ValueError`, so any malformed-but-well-shaped opcode atom is turned into the expected typed error instead of an unhandled exception. Additionally broaden `conditions_for_solution()`'s exception handling (or the call sites in `wallet_signer.py`) to catch `ConsensusError`/`ValueError` around CLVM output parsing so a hostile puzzle cannot abort wallet signing flows.

### Proof of Concept
1. Construct a puzzle that, given any solution, outputs a condition list containing an atom such as `(2 0xAA 0xBB)` (opcode byte `2`, which is not defined in `ConditionOpcode`).
2. Embed this puzzle as an inner spend within an offer file (or as a `CoinSpend` handed to `sign_bundle`/`sign_offers`).
3. Have the victim wallet call `WalletSigner.gather_signing_info()` (via `sign_offers`, `sign_transactions`, or `sign_bundle`) on this spend.
4. `run_with_cost()` succeeds (valid CLVM execution) and returns the condition list; `parse_sexp_to_conditions()` → `parse_sexp_to_condition()` executes `ConditionOpcode(op)` with `op = b"\x02"`, raising an uncaught `ValueError` that is not caught by `except Program.EvalError` in `conditions_for_solution()`, aborting the signing operation.
