### Title
Missing upper-bound range check on `Timestamp.seconds` in upb JSON decoder allows out-of-range values to bypass validation - ([File: upb/json/decode.c])

### Summary
The Sherlock report describes `judgeExpired`, a modifier that is supposed to gate execution on a `deadline` value, but only performs a partial/incomplete comparison, letting an attacker-supplied value slip past the intended bound and defeat the check entirely. The transferable invariant is: *a bounds check that validates only one side of a documented valid range can be trivially bypassed by supplying a value beyond the unchecked side*. In upb's ProtoJSON `Timestamp` decoder, the well-known-type contract requires `seconds` to be in `[-62135596800, 253402300799]` (`0001-01-01T00:00:00Z` to `9999-12-31T23:59:59Z`), as enforced by `TimeUtil::IsTimestampValid` [1](#0-0)  and mirrored by Java's `Timestamps.isValid`/`checkValid` [2](#0-1)  and C++'s `TimeUtil::FromString`, which checks both `kTimestampMinSeconds` and `kTimestampMaxSeconds` [3](#0-2) . However, `jsondec_timestamp` in `upb/json/decode.c` (the upb ProtoJSON decoder used by PHP/Ruby native bindings) only checks the lower bound:

```
if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
}
```

There is no corresponding `seconds.int64_val > 253402300799` check [4](#0-3) .

### Finding Description
`jsondec_timestamp` parses an RFC 3339 string into `seconds`/`nanos` fields for the well-known `google.protobuf.Timestamp` message [5](#0-4) . The year is parsed as a 4-digit field via `jsondec_tsdigits`, so a malicious/bounded ProtoJSON input like `"9999-99-99T00:00:00Z"`-style values, or more precisely any year within `0000`-`9999` combined with a timezone offset, is converted to Unix seconds by `jsondec_unixtime`/`jsondec_epochdays` [6](#0-5) . After computing `seconds.int64_val` (including the timezone-offset adjustment, which can push the value further outside the documented range in either direction) [7](#0-6) , the code performs only a lower-bound sanity check before writing the field unconditionally into the message via `upb_Message_SetFieldByDef` [8](#0-7) .

This means a value corresponding to a year at or beyond `9999-12-31T23:59:59Z` (e.g., `"9999-12-31T23:59:60Z"`-style constructions, or a valid 4-digit year at the top of the parse combined with a negative offset that pushes seconds > `253402300799`) is accepted and stored, producing a `Timestamp` message that fails `TimeUtil::IsTimestampValid`/`Timestamps.isValid` and is documented as invalid. Downstream consumers that rely on the documented invariant "a successfully-decoded ProtoJSON `Timestamp` is within `[MIN_VALUE, MAX_VALUE]`" (e.g., callers using `Timestamps.checkValid` after JSON round-trip, or code assuming range-limited values before doing safe date arithmetic) receive a corrupted, out-of-contract value instead of a rejection — the exact "check exists but attacker-controlled input bypasses it" pattern from the source report, transferred to a protobuf-specific range invariant instead of a smart-contract deadline.

### Impact Explanation
This is a data-integrity issue, not a memory-safety issue: the upb JSON decoder accepts and silently propagates a `Timestamp` value outside its documented valid range for `google.protobuf.Timestamp` (via PHP/Ruby native JSON parsing, which is backed by `upb/json/decode.c`). Any application logic that trusts "a Timestamp decoded from ProtoJSON is within the documented range" (many `TimeUtil`/`Timestamps` helper functions assume this and will throw on out-of-range input, but the value has already been merged into the message and may be consumed by other logic first, e.g. arithmetic, serialization back to string, or duration calculations) can silently misbehave or later crash/throw at an unexpected point instead of failing fast at parse time. This is a Medium-severity correctness/validation gap: it does not by itself grant memory corruption or code execution, but it violates a documented invariant enforced everywhere else in the codebase (C++, Java, Python) for the exact same well-known type, which is precisely the "modifier check bypassed by out-of-band value" class of bug in the source report.

### Likelihood Explanation
Likelihood is straightforward: this triggers on ordinary, well-formed ProtoJSON input to a public parsing API (`Timestamp` field within a trusted schema, parsed via the standard JSON unmarshal path for PHP/Ruby, which use upb natively). No privileged access or malicious schema is required — only a client-supplied JSON string with an extreme (but syntactically valid, 4-digit-year) date/timezone-offset combination. The upper-bound check is simply absent, so the bypass is deterministic, not dependent on race conditions or specific compiler behavior.

### Recommendation
Add the missing upper-bound check to mirror `TimeUtil::kTimestampMaxSeconds` (`253402300799`) in `jsondec_timestamp`:

```c
if (seconds.int64_val < -62135596800 || seconds.int64_val > 253402300799) {
    jsondec_err(d, "Timestamp out of range");
}
```

Apply the analogous fix in the PHP/Ruby-embedded copies of this decoder (`php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`), which are generated from/mirror the same `jsondec_timestamp` logic [9](#0-8) [10](#0-9) .

### Proof of Concept
Not independently executed (no runtime/tooling access in this session), but the code-path trace is exact and reproducible from source:
1. Construct a ProtoJSON payload for a `google.protobuf.Timestamp` field with a value such as `"9999-12-31T23:59:59-01:00"` (a syntactically valid RFC-3339 string with a negative offset).
2. `jsondec_timestamp` parses year=9999, computing `seconds.int64_val` for `9999-12-31T23:59:59Z` (= `253402300799`, the documented max) and then subtracts the offset adjustment `ofs_min` (1 hour = 3600) per the `neg` branch [11](#0-10) , yielding `seconds.int64_val = 253402304399`, which exceeds `kTimestampMaxSeconds` (`253402300799`).
3. Only the `< -62135596800` check runs [4](#0-3) ; this out-of-range value passes and is written into the message.
4. Passing the resulting `Timestamp` to `TimeUtil::IsTimestampValid`/`Timestamps.isValid` in a different (trusted) part of the same application would return `false` (or throw via `checkValid`), demonstrating the message now violates its own documented invariant despite having been "successfully" parsed.

```c
/* jsondec_epochdays(1970, 1, 1) == 1970-01-01 == 0. */
int jsondec_epochdays(int y, int m, int d) {
  const uint32_t year_base = 4800; /* Before min year, multiple of 400. */
  const uint32_t m_adj = m - 3;    /* March-based month. */
  const uint32_t carry = m_adj > (uint32_t)m ? 1 : 0;
  const uint32_t adjust = carry ? 12 : 0;
  const uint32_t y_adj = y + year_base - carry;
  const uint32_t month_days = ((m_adj + adjust) * 62719 + 769) / 2048;
  const uint32_t leap_days = y_adj / 4 - y_adj / 100 + y_adj / 400;
  return y_adj * 365 + leap_days + month_days + (d - 1) - 2472632;
}

static int64_t jsondec_unixtime(int y, int m, int d, int h, int min, int s) {
  return (int64_t)jsondec_epochdays(y, m, d) * 86400 + h * 3600 + min * 60 + s;
}
```
