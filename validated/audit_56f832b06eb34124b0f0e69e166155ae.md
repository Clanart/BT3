## Title
"Open with Default Program" / "Reveal in File Manager" resolve file paths without symlink/traversal validation, allowing a malicious repo to redirect file opens outside the working directory - (File: `app/src/ui/lib/open-file.ts`, `app/src/lib/app-shell.ts`, `app/src/ui/changes/sidebar.tsx`, `app/src/ui/history/selected-commits.tsx`)

### Summary
Several "open file" code paths in GitHub Desktop build the full filesystem path for a repo-relative entry with plain `Path.join(repository.path, path)` and then hand that path straight to Electron's `shell.openExternal`/`shell.showItemInFolder`, with no check that the resolved path (after following symlinks) stays inside the repository. Elsewhere in the same codebase (`app/src/lib/copilot-conflict-context.ts`, `app/src/ui/dispatcher/dispatcher.ts`) the developers explicitly use `resolveWithin()` — a helper built specifically to defend against "path traversal and symlink escapes" — before touching disk. The Changes list and Commit History "Open with Default Program" / "Reveal in Finder" actions skip that helper entirely.

### Finding Description
`app/src/lib/path.ts` defines `resolveWithin()`, which normalizes a path, resolves it against a root, and then calls `realpath()` on both the root and the resolved path to make sure a symlink hasn't been used to escape the root: [1](#0-0) 

This helper is used correctly in at least two places to stop exactly this class of attack — deep-link file opening and Copilot conflict-context file reads: [2](#0-1) [3](#0-2) 

However, the Changes pane's context-menu "Open with Default Program" handler builds the path with plain `Path.join` and passes it directly to `openFile()`: [4](#0-3) 

and the History pane's file context menu does the same for both "Reveal in File Manager" and "Open with Default Program": [5](#0-4) 

`revealInFileManager()` itself also joins the repository path with the untrusted relative path with no traversal/symlink check before calling `shell.showItemInFolder`: [6](#0-5) 

`openFile()` then simply forwards the resulting path to `shell.openExternal('file://' + fullPath)`: [7](#0-6) 

The only gate applied before "Open with Default Program" is enabled is `isSafeFileExtension`, which on macOS/Linux always returns `true` and on Windows only blocks a hard-coded list of four extensions (`.cmd`, `.exe`, `.bat`, `.sh`): [8](#0-7) 

Git fully supports committing symbolic links (mode `120000`), and a symlink target string is attacker-controlled tracked content, e.g. `evil.pdf -> ../../../../.ssh/id_rsa` or `evil.pdf -> /etc/passwd`. When a victim clones/fetches such a malicious repository and the file appears in the Changes list (as untracked/modified) or in a commit's file list in History, the path shown in the UI is the symlink's path inside the repo (`evil.pdf`), but `Path.join(repository.path, 'evil.pdf')` on disk *is* the symlink, and `shell.openExternal`/`shell.showItemInFolder` will follow it to whatever target the attacker chose — which can be entirely outside the repository (and outside the sandboxed clone directory). This directly matches the "read outside the repo" and "silent misdirection of a user action against untrusted repo content" classes named in the impact policy, and is architecturally the same "unvalidated linked/first entry causes the app to act on attacker-chosen data outside the intended safe boundary" pattern used as the seed report's bug class (an unchecked, attacker-supplied indirection that the surrounding code trusts implicitly).

### Impact Explanation
Because `isSafeFileExtension` is a no-op on macOS/Linux and only extension-based (not content/type based) on Windows, an attacker can disguise the symlink with any extension. Clicking "Open with Default Program" on such an entry launches the OS's default handler for that extension against the *resolved* symlink target rather than a file confined to the clone. Depending on target and default handler, this can:
- Disclose the contents of sensitive files outside the repository (e.g., private keys, browser profiles, other project source) by opening them in a viewer/editor and rendering/displaying their contents.
- With "Reveal in File Manager", reveal/select an arbitrary file or directory on the victim's machine, and via the OS file manager's context actions the user might inadvertently execute or move content the attacker chose to surface.
- If the symlink is aimed at another location the app itself writes to later (e.g., another repository's working tree), this also creates a vector for corrupting content the user believes belongs to the cloned project.

This satisfies the "file read outside the repo" bucket of the accepted-impact list. It requires no local/physical access, no prior malware, and no credentials — only that the victim clones/fetches a malicious repository and clicks a normal, expected UI action (view Changes/History and open/reveal a file), which is standard Desktop usage, not an "unnatural" step.

### Likelihood Explanation
Git symlinks are trivially created and committed (`ln -s ../../../.ssh/id_rsa evil.pdf && git add evil.pdf`). They check out as real filesystem symlinks by default on macOS/Linux (and on Windows when Developer Mode/symlink privileges or `core.symlinks=true` apply, which GitHub Desktop's bundled Git commonly enables under Developer Mode). Any user who clones an untrusted repository — a common workflow for reviewing external PRs/forks in Desktop — and opens the Changes tab or browses a commit's file list is exposed. The action ("Open with Default Program"/"Reveal in Finder") is one of the most commonly used context-menu items, making accidental triggering realistic, especially since the file shows up with an innocuous name/extension chosen by the attacker.

### Recommendation
Route every filesystem path built from repository-relative, attacker-influenced strings (Changes list, History file list, PR files-changed view, "Reveal in File Manager") through `resolveWithin()`/`resolveWithinPosix()`/`resolveWithinWin32()` before calling `shell.openExternal`, `shell.showItemInFolder`, or `openFile()`, mirroring what `copilot-conflict-context.ts` and `dispatcher.ts`'s `openRepositoryFromUrl` already do. If `resolveWithin` returns `null` (traversal or symlink escape detected), refuse the action and surface an error instead of silently opening/revealing the target.

### Proof of Concept
1. Create a malicious repository:
   ```
   git init evil-repo && cd evil-repo
   ln -s ../../../../../../etc/passwd leak.pdf   # or a path into the victim's home dir, e.g. ~/.ssh/id_rsa
   git add leak.pdf
   git commit -m "add report"
   ```
2. Host/share this repository and have the victim clone it in GitHub Desktop (or open a PR/fork containing this commit).
3. In the Changes pane (for an untracked symlink) or in History → select the commit containing `leak.pdf`, right-click the file and choose "Open with Default Program" (or "Reveal in Finder"/"Show in Explorer").
4. Because `onOpenItem`/`onContextMenu` in `app/src/ui/changes/sidebar.tsx` and `app/src/ui/history/selected-commits.tsx` build the path via plain `Path.join(repository.path, file.path)` with no `resolveWithin` check, the OS resolves the symlink and opens/reveals the real target (`/etc/passwd` or the SSH key) instead of a file confined to the cloned repository, disclosing its content in the OS default viewer/file manager.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
