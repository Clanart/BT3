### Title
Stale line-selection applied to a freshly re-fetched working-tree diff can silently corrupt a partial commit - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported TridentRouter bug is a classic "stale-state at execution time" flaw: a user authorizes an action (add liquidity) based on parameters computed from state observed at time T (spot price), but the action is actually executed against state at time T+n, and nothing re-validates that the two states still match, so the wrong (or reverted) outcome occurs. The GitHub Desktop analog is the partial-commit / line-selection staging path: the user's line selection is captured as an index bitmap against a diff computed at time T, but when the commit is actually staged, `applyPatchToIndex` recomputes the diff fresh from disk at time T+n and blindly re-applies the old index-based selection to the new hunk structure, with no check that the diff hasn't changed underneath it.

### Finding Description
When a user stages a partial file (selecting specific lines/hunks instead of the whole file), the UI keeps a `DiffSelection` — a bitmap of *absolute diff line indices* — tied to whichever `ITextDiff` was rendered at selection time (see `formatPatch`, which walks `diff.hunks` and calls `file.selection.isSelected(absoluteIndex)` for each line) [1](#0-0) .

That selection object travels through the store (`WorkingDirectoryFileChange.selection`) and is eventually consumed at commit time in `_commitIncludedChanges`, which reads the currently cached `state.changesState.workingDirectory.files` and passes them straight to `createCommit` [2](#0-1) . Before staging happens, an `await formatCommitMessage(...)` runs (which can be a slow/async operation, e.g. commit-message generation) [3](#0-2) .

`createCommit` calls `stageFiles`, which for any file with a partial selection invokes `applyPatchToIndex` [4](#0-3) . Critically, `applyPatchToIndex` does **not** reuse the diff the user actually looked at and selected lines against — it re-fetches a brand-new diff straight from the working tree at that moment: `const diff = await getWorkingDirectoryDiff(repository, file)` [5](#0-4) , and then builds the patch with `formatPatch(file, diff)` using the *old* selection bitmap against this *new* diff [6](#0-5) .

Because `DiffSelection.isSelected()` only knows about absolute line indices, not content or hunk identity, if the on-disk file content changes between the moment the user made their line selection and the moment `applyPatchToIndex` re-fetches the diff, the same indices can now refer to entirely different lines/hunks. Depending on how the hunks shift, `git apply --cached` will either fail outright (safe but confusing to the user) or — worse — succeed while staging different lines than the ones the user actually selected in the UI, i.e. **silently corrupting what gets committed** relative to the user's intent. This exactly matches the impact class called out in the report's methodology (silent corruption of what the user commits).

### Impact Explanation
If the working tree changes between the user's line selection and the actual staging step (e.g., a smudge/clean filter defined in a malicious repo's `.gitattributes` rewriting file content during `git add`, a repo-provided pre-commit/prepare-commit-msg hook that intercepts and modifies files, or any background write triggered by repo-controlled tooling), the partial commit produced can contain lines the user never selected, or omit lines they did select — without any error being surfaced. Since Desktop is a git client that many developers trust to accurately reflect "what I selected is what gets committed", this breaks that core invariant and can result in unintended code silently entering a commit/push.

### Likelihood Explanation
The window between selection capture and the `applyPatchToIndex` re-fetch is not instantaneous — `formatCommitMessage` is awaited beforehand, and `stageFiles`/`unstageAll` calls add further asynchronous git-process round trips before the partial-file loop runs [7](#0-6) . Any repository-controlled mechanism that can rewrite working-tree file content during that window (clean/smudge filters, hook-driven mutation, or any tool that reacts to `git add`/`git commit` invocations) can hit this race without needing local malware, admin rights, or unusual user steps — the user is simply doing a normal partial commit. However, actually landing on a hunk-shift that produces a *plausible-looking but wrong* patch (rather than a hard `git apply` failure) is probabilistic and depends on the exact content delta, which lowers overall likelihood to moderate rather than trivial.

### Recommendation
`applyPatchToIndex` should not silently re-fetch a new diff and reapply an old selection. Instead:
- Pass the exact `ITextDiff` (and/or a content hash/mtime) that was used to build the user's `DiffSelection` through to `stageFiles`/`applyPatchToIndex`, and verify it still matches the current working-tree file before generating the patch.
- If the diff has changed since selection, abort staging that file and force the UI to refresh the diff and require the user to reselect, analogous to Uniswap V2's router recomputing/validating optimal amounts instead of trusting stale caller-supplied values.
- At minimum, treat a mismatch as a hard failure surfaced to the user rather than best-effort application of stale indices to new hunks.

### Proof of Concept
1. Open a modified file with multiple hunks in Desktop's Changes view; select only specific lines from hunk #2 (this builds a `DiffSelection` keyed to line indices of the diff currently displayed) — see the same selection mechanism exercised in `app/test/unit/patch-formatter-test.ts:41-131`.
2. Trigger a slow async step before commit completes (e.g., AI commit-message generation via `formatCommitMessage`, referenced in `app-store.ts:3696`).
3. During that window, have a repository-controlled clean filter / hook rewrite the file on disk, shifting line numbers/hunks without the UI being told to refresh.
4. Click "Commit" — `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the stale selection bitmap to it (`app/src/lib/git/apply.ts:80-81`), producing a patch that no longer corresponds to the lines the user actually chose — either failing `git apply` or staging incorrect content silently.

Note: I could not find any explicit re-validation logic between diff-fetch and selection application in `apply.ts`, `update-index.ts`, or the commit path in `app-store.ts`; this gap appears to be a genuine, unaddressed invariant violation rather than a documented/guarded behavior.
