Based on the search, I found a real inconsistency in the Aptos object-ownership traversal logic that is directly wired into the new publish/module-init path (`code::publish_package` and `init::assert_may_self_initialize`), which is exactly the kind of "code ownership at publish time" analog the report seed points to.

### Title
Unbounded ownership-chain traversal in `object::root_owner()` allows gas-exhaustion DoS of the code-ownership check used by `code::publish_package` and `init::assert_may_self_initialize` - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
Aptos added a `LAZY_MODULE_INITIALIZATION` feature where the "owner" of an object-hosted package is captured at publish time via `object::root_owner()` and later re-checked at self-init time to gate who may mint the module's signer. Unlike every other ownership-traversal helper in the same module (`owns`, `verify_ungated_and_descendant`), `root_owner()` has no bound on how many hops it will walk up the ownership chain, even though the object model explicitly allows constructing cyclic ownership graphs.

### Finding Description
`object::root_owner()` is defined as: [1](#0-0) 
with an unbounded `while (is_object(obj_owner))` loop, in contrast to the two other ownership-walking functions in the same file which both explicitly cap traversal at `MAXIMUM_OBJECT_NESTING` (8) and abort otherwise: [2](#0-1) [3](#0-2) 

The module's own comment on `MAXIMUM_OBJECT_NESTING` acknowledges objects can have "technically infinite nesting": [4](#0-3) 

Crucially, nothing in `transfer_raw`/`verify_ungated_and_descendant` prevents constructing a cycle in the ownership graph: the check only verifies that the *current signer* transitively owns the *source* object being transferred; it never checks whether the new owner (`to`) is itself a descendant of the object being moved. Consequently, a user who owns two objects (say `A` and `B`, with `B` already owned by `A`) can transfer `A` to `B`, producing the 2-cycle `A → B → A`.

This unbounded `root_owner()` is exactly what two newly-added, publish-path-critical functions rely on:
- `code::publish_package` calls it to record the code object's owner for lazy self-init gating on every (re)publish: [5](#0-4) 
- `init::assert_may_self_initialize` calls it again at self-init time to compare against the recorded owner: [6](#0-5) 

If the object hosting a package (or any of its ancestors) is part of a cycle when either of these functions runs, `root_owner()` never terminates and the transaction can only be stopped by running out of gas, aborting the transaction. Both entry points are on the protected publish/module-init state-mutation path (`code::publish_package` performs the write-set publish, `init::internal_maybe_initialize` mints a signer that gates protected `move_to` calls), so this is a legitimate write-set-publish/module-init native-validation failure rather than a generic DoS.

### Impact Explanation
Any account that can arrange (directly, or by owning an ancestor object with `allow_ungated_transfer` in the chain of a target code object) for that chain to become cyclic can permanently prevent:
1. Republishing/upgrading a package hosted at that object address (`code::publish_package` will exhaust gas trying to compute `root_owner()` before the write-set publish even runs), and
2. All calls into any module on that object that use `init::internal_maybe_initialize` for lazy self-init (every call aborts on gas exhaustion instead of returning a signer), bricking legitimate protected-state mutation for all downstream users of that object.

This is a self-DoS in the simplest case (an owner cycling their own object), but because object ownership chains are composable and third parties can be granted ungated-transfer rights over ancestor objects in shared protocols, it can also be used to grief other users' ability to upgrade or lazily initialize code they otherwise legitimately own.

### Likelihood Explanation
Medium. Constructing a 2-object ownership cycle requires only two `object::create_object` calls plus one `object::transfer` and is possible with an ordinary account under the existing API — no privileged access needed. The harder part is placing a code-hosting object (or one of its ancestors) into that cycle, which in the general case requires the attacker to control transfer rights somewhere in the ancestor chain of the target; for a self-owned object, the code owner can trivially do it to themselves, and for shared/nested object hierarchies (a growing pattern in Aptos DeFi/token composability) a malicious or compromised intermediate owner could do it to a victim's descendant object.

### Recommendation
Bound `object::root_owner()` the same way `owns()` and `verify_ungated_and_descendant()` are bounded — cap traversal at `MAXIMUM_OBJECT_NESTING` and either return the address reached at the cap or abort with `EMAXIMUM_NESTING`, so callers on the publish/module-init path (`code::publish_package`, `init::assert_may_self_initialize`) get deterministic, gas-bounded behavior instead of relying on out-of-gas as an implicit failure mode.

### Proof of Concept
```move
// 1. Create two objects owned by `user`.
let a_ref = object::create_object(user_addr);
let a_addr = object::address_from_constructor_ref(&a_ref);
let b_ref = object::create_object(a_addr); // b is owned by a
let b_addr = object::address_from_constructor_ref(&b_ref);

// 2. Publish a lazily-self-initializing module to object `a` (or one of its
//    descendants) with LAZY_MODULE_INITIALIZATION enabled; code::publish_package
//    records root_owner(a) = user at this point.

// 3. Create the cycle: transfer `a` to be owned by `b`.
object::transfer_raw(&create_signer::create_signer(user_addr), a_addr, b_addr);
// Now: a.owner == b, b.owner == a  -> cycle a <-> b

// 4. Any subsequent call into the published module's entry function that invokes
//    init::internal_maybe_initialize (or any republish attempt via
//    code::publish_package) computes object::root_owner(a), which loops forever
//    between a and b and aborts only via out-of-gas, permanently blocking the
//    protected publish/self-init path for object `a`.
```

**Uncertainty:** I could not fully trace every real-world scenario in which an attacker gains transfer control over an *ancestor* of a victim-owned code object without the code object owner's own cooperation — that part depends on how shared/nested object hierarchies are used by specific protocols built on top of this framework, which is outside what the indexed code shows. The self-inflicted case (owner cycling their own object to brick their own upgrade/init path) is fully verified in the code above.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(

                error::permission_denied(ENOT_OBJECT_OWNER),

            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
