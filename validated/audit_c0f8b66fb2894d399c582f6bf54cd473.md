### Title
Stale Light Client Proof Returned Without Block-Height Validation Causes Operator Collateral Slashability — (File: `core/src/citrea.rs`)

### Summary

`fetch_validate_and_store_lcp` unconditionally returns a DB-cached `Receipt` for a `deposit_index` without verifying that the cached proof covers the requested `payout_block_height`. The underlying `insert_lcp_for_assert` uses `ON CONFLICT (deposit_id) DO NOTHING`, making the first-stored LCP permanently immutable. After a Bitcoin reorg that moves the payout transaction to a different block, the cached LCP (for the pre-reorg block) is silently returned for a different `payout_block_height`, causing the bridge-circuit proof to fail and the operator to be unable to defend against a challenge — resulting in slashable collateral loss.

---

### Finding Description

**Root cause — `core/src/citrea.rs` lines 326–361:**

```rust
async fn fetch_validate_and_store_lcp(
    &self,
    payout_block_height: u64,   // ← caller's required height
    deposit_index: u32,
    db: &Database,
    mut dbtx: Option<DatabaseTransaction<'_>>,
    paramset: &'static ProtocolParamset,
) -> Result<Receipt, BridgeError> {
    let saved_data = db
        .get_lcp_for_assert(dbtx.as_deref_mut(), deposit_index)
        .await?;
    if let Some(lcp) = saved_data {
        // if already saved, do nothing   ← NO height check
        return Ok(lcp);
    };
    // ... fetch fresh LCP for payout_block_height ...
    db.insert_lcp_for_assert(dbtx, deposit_index, lcp_receipt.clone())
        .await?;
    Ok(lcp_receipt)
}
```

The function checks only whether *any* LCP exists for `deposit_index`; it never verifies that the stored receipt's embedded `latest_da_state.block_hash` matches the block at `payout_block_height`.

**Immutability — `core/src/database/operator.rs` lines 678–688:**

```rust
let query = sqlx::query(
    "INSERT INTO lcp_for_asserts (deposit_id, lcp_receipt)
     VALUES ($1, $2)
     ON CONFLICT (deposit_id) DO NOTHING;",   // ← first write wins, forever
)
```

The schema (`core/src/database/schema.sql` lines 71–74) stores only `(deposit_id, lcp_receipt)` — no `payout_block_height` column — so there is no way to detect or correct a stale entry.

**Call sites that write then read the cache:**

1. `core/src/task/payout_checker.rs` lines 89–99 — stores LCP when payout is first detected (block A).
2. `core/src/operator.rs` lines 1826–1835 — stores LCP during kickoff preparation.
3. `core/src/operator.rs` lines 1315–1324 — reads LCP during `send_asserts` (may now need block B after reorg).

**Bridge-circuit enforcement — `circuits-lib/src/bridge_circuit/mod.rs` lines 172–179:**

```rust
let light_client_circuit_output = lc_proof_verifier(input.lcp.clone());
let lc_l1_block_hash = light_client_circuit_output.latest_da_state.block_hash;
let spv_l1_block_hash = input.payout_spv.block_header.compute_block_hash();

```

If the cached LCP covers block A but the SPV proof covers block B (post-reorg), the zkVM panics and no valid proof can be generated.

---

### Impact Explanation

When a Bitcoin reorg moves the payout transaction from block A to block B:

1. The LCP cached during `PayoutCheckerTask` (block A) is permanently locked in `lcp_for_asserts` via `ON CONFLICT DO NOTHING`.
2. `send_asserts` calls `fetch_validate_and_store_lcp(block_B_height, deposit_idx, …)` — the stale block-A LCP is returned without any height check.
3. The bridge-circuit host (`bridge-circuit-host/src/bridge_circuit_host.rs` lines 120–122, 146–167) and the zkVM guest both enforce `lc_l1_block_hash == spv_l1_block_hash`; with a mismatched LCP the proof generation fails.
4. The operator cannot produce a valid assert, cannot disprove a challenge, and their collateral is burned.

This is **slashable exposure of operator collateral** — a direct financial loss with no recovery path because the DB entry can never be updated.

---

### Likelihood Explanation

The trigger is a Bitcoin reorg deeper than the configured `finality_depth`. On mainnet this is rare; on testnet4/regtest (where Clementine is actively tested) reorgs are routine. The finality depth is operator-configurable and may be set low in non-mainnet deployments. No privileged access to the Clementine system is required — the reorg is an external Bitcoin-network event. Once triggered, the impact is permanent and unrecoverable without manual DB intervention.

---

### Recommendation

1. **Add `payout_block_height` to the `lcp_for_asserts` table** and validate it on every read:

```sql
ALTER TABLE lcp_for_asserts ADD COLUMN payout_block_height BIGINT NOT NULL DEFAULT 0;
```

2. **In `fetch_validate_and_store_lcp`, reject a cached LCP whose block height does not match the caller's `payout_block_height`** and re-fetch:

```rust
if let Some((lcp, stored_height)) = saved_data {
    if stored_height == payout_block_height {
        return Ok(lcp);
    }
    // stale — fall through to re-fetch and overwrite
}
```

3. **Change `ON CONFLICT DO NOTHING` to `ON CONFLICT (deposit_id) DO UPDATE SET lcp_receipt = EXCLUDED.lcp_receipt, payout_block_height = EXCLUDED.payout_block_height`** so a post-reorg fetch can replace the stale entry.

---

### Proof of Concept

```
1. Operator fronts withdrawal; payout tx lands in Bitcoin block A (height H_A).
2. PayoutCheckerTask fires: fetch_validate_and_store_lcp(H_A, deposit_idx, …)
   → LCP_A stored in lcp_for_asserts for deposit_idx.
3. Bitcoin reorg: block A is orphaned; payout tx re-confirms in block B (height H_B ≠ H_A).
4. Bitcoin syncer updates payout_block_hash in DB to block B's hash.
5. Verifier challenges the operator's kickoff (committed block hash now invalid).
6. Operator's send_asserts calls fetch_validate_and_store_lcp(H_B, deposit_idx, …).
7. get_lcp_for_assert returns LCP_A (for block A) — no height check performed.
8. Bridge circuit host: lcp_receipt.journal encodes block A's hash;
   payout_spv.block_header is block B → lc_l1_block_hash ≠ spv_l1_block_hash → panic.
9. Proof generation fails; operator submits no valid assert.
10. Challenge timeout expires; operator collateral is slashed.

    /// Saves the light client proof for a deposit to be used while sending an assert.
    /// We save first before sending kickoff to be sure we have the LCP available if we need to assert.
    pub async fn insert_lcp_for_assert(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
        lcp: Receipt,
    ) -> Result<(), BridgeError> {
        let query = sqlx::query(
            "INSERT INTO lcp_for_asserts (deposit_id, lcp_receipt)
             VALUES ($1, $2)
             ON CONFLICT (deposit_id) DO NOTHING;",
        )
        .bind(i32::try_from(deposit_id).wrap_err("Failed to convert deposit id to i32")?)
        .bind(ReceiptDB(lcp));

        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
