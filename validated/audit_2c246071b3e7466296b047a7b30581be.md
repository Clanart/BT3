### Title
Unbounded participant count causes multi-megabyte allocation in `ThresholdKeys::read` - ([File: `crypto/dkg/src/lib.rs`](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized `n` participant count before validating `ThresholdParams`. When the interpolation marker selects `Interpolation::Constant`, it immediately executes `Vec::with_capacity(usize::from(n))`. An attacker can therefore force allocation for up to 65,535 scalar elements using only the serialized header; no corresponding scalar payload is required because allocation happens before the first `read_F` call. Repeated calls create substantial allocation pressure and can exhaust memory or deny service to the process handling untrusted threshold-key blobs. This is analogous to a size guard failing open before bounded resource consumption. [1](#0-0) 

### Finding Description
The deserializer reads `t`, `n`, and participant index `i`, but does not call `ThresholdParams::new` until after it has consumed the interpolation variant, secret share, and all verification shares. For interpolation byte `0`, `n` directly controls the capacity passed to `Vec::with_capacity`. The resulting vector is allocated before `ThresholdParams::new` can reject invalid combinations such as `t != n` for constant interpolation, and before the availability of the corresponding encoded scalars is known. [2](#0-1) 

Because `Participant` and `n` are `u16` values, `n` can be as large as 65,535. For a typical 32-byte scalar representation, that capacity requests roughly 2 MiB; larger field representations increase the allocation proportionally. The subsequent `read_F` may fail immediately on a short input, but the large allocation has already occurred. [3](#0-2) [4](#0-3) 

The later `ThresholdParams::new` check is too late to protect this allocation: it is invoked only inside the final `ThresholdKeys::new` call after deserialization has already allocated and attempted to parse `n` scalars and `n` verification shares. [5](#0-4) 

### Impact Explanation
An unprivileged party supplying an untrusted `ThresholdKeys` serialization can amplify a tiny input into repeated multi-megabyte allocations. Concurrent requests can retain enough concurrent allocations to exhaust memory, trigger allocator pressure, or terminate the process. Since the input can terminate immediately after the interpolation selector, the attacker does not need to transmit data proportional to the requested allocation. [6](#0-5) 

### Likelihood Explanation
The attack requires only control of bytes passed to `ThresholdKeys::read`. No key material, valid proof, valid signature, malformed cryptographic object, or sustained bandwidth is needed. A repeated stream of truncated records declaring `n = 0xffff` and selecting constant interpolation is sufficient. The maximum bounded allocation is finite, so the issue is a Medium-severity availability impact rather than Critical or High. [7](#0-6) 

### Recommendation
Validate `t`, `n`, and `i` with `ThresholdParams::new` immediately after reading those fields. Enforce a protocol-specific maximum `n` before allocating any attacker-controlled collection. For `Interpolation::Constant`, reject `t != n` before allocating the coefficient vector, and prefer incremental parsing without `with_capacity` or with capacity capped by an independently enforced maximum. The same ordering should apply before reading the `n` verification shares. [8](#0-7) [9](#0-8) 

### Proof of Concept
Conceptually, construct a serialized `ThresholdKeys` prefix:

```text
u32_le(C::ID.len()) ||
C::ID ||
u16_le(t = 1) ||
u16_le(n = 65535) ||
u16_le(i = 1) ||
u8(interpolation = 0)
```

Call `ThresholdKeys::<C>::read` on this prefix. At `interpolation == 0`, the function executes `Vec::with_capacity(65535)` before `read_F` observes end-of-input and before `ThresholdParams::new` rejects constant interpolation for `t != n`. Repeating the truncated record in parallel produces repeated large allocations with minimal attacker bandwidth. [10](#0-9)
