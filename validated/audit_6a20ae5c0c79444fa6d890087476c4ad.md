### Title
Unvalidated participant indexes in blame handling panic on out-of-range `Participant`, crashing the node - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to GHSA-jc55-246c-r88f (an `unwrap()` on a conversion of a nonexistent role), Serai's PedPoP blame path indexes `HashMap`s keyed by `Participant` with attacker-influenced indexes that are never validated against `n`, causing a panic instead of an error — a remotely triggerable denial of service.

### Finding Description
`Participant` accepts any nonzero `u16` (`Participant::new` only rejects 0). `BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender` and `recipient` from external accusation messages and pass them straight to `blame_internal`, which calls `Decryption::decrypt_with_proof`. Inside `decrypt_with_proof`, after the PoP signature is checked, the code indexes `self.enc_keys[&decryptor]`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:388
&[self.enc_keys[&decryptor], *proof.key],
```

Indexing a `HashMap` with `[]` panics on a missing key, so any `decryptor`/`recipient` index `> n` panics. Likewise, `blame_internal` later evaluates `&self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599), panicking for a `sender` index that was never registered. Neither `blame` nor `blame_internal` checks `u16::from(participant) <= n`, unlike `ThresholdKeys::view` (crypto/dkg/src/lib.rs:487-490) and `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:302-304), which both explicitly reject `InvalidParticipant`. The panic can be hit before the share check because the PoP is attacker-satisfiable: `msg.pop.verify` only requires a Schnorr signature over `msg.key`, which the accuser controls, and reaching the panicking line only requires a syntactically valid `EncryptionKeyProof` (any `key: C::G` plus a `DLEqProof` encoding — the DLEq itself is verified only after the indexing occurs).

### Impact Explanation
A participant (or any party able to submit a blame accusation referencing arbitrary `Participant` indexes) can crash every node that processes the accusation by citing a nonexistent participant (e.g., `Participant(n + 1)` as `recipient`, or as `sender` with a valid PoP). In a validator/coordinator deployment this aborts the DKG and can deny service to the threshold group — mirroring the SurrealDB bug where a privileged-but-untrusted user could crash the server via a value that "should be an enum" but wasn't validated.

### Likelihood Explanation
Blame evaluation is an expected post-DKG flow whenever any participant reports a bad share, and accusation contents (sender/recipient indexes, the forwarded `EncryptedMessage`, the `EncryptionKeyProof`) are supplied by the accusing party. The missing `enc_keys`/`commitments` entries require only an index in `1..=u16::MAX` outside `1..=n`, so a single malicious or even buggy participant suffices. The only mitigation is the doc note that callers authenticate messages — which does not bound the index range.

### Recommendation
In `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal`, validate `sender` and `recipient` against the registered sets (e.g., `self.commitments.contains_key(&sender)` and `self.encryption.enc_keys.contains_key(&decryptor)`) and return an error/`PedPoPError` instead of indexing. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` + error propagation.

### Proof of Concept
```rust
// After a t-of-n PedPoP DKG, node holds BlameMachine (or an outside observer
// builds AdditionalBlameMachine::new(context, n, commitment_msgs)).
// Attacker submits an accusation referencing participant n+1 as recipient:

let evil = Participant::new(n + 1).unwrap(); // valid Participant, unregistered

// msg/pop crafted by attacker: any Schnorr sig over attacker-chosen key verifies,
// or sender itself is out-of-range so commitments[&sender] panics first.
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* EncryptedMessage::read bytes */;
let proof = Some(EncryptionKeyProof::read(&mut proof_bytes).unwrap());

// Panics: `self.enc_keys[&decryptor]` (encryption.rs:388) — index out of map,
// or `self.commitments[&sender]` (lib.rs:599) for an out-of-range sender.
blame_machine.blame(sender, evil, msg, proof);
```

Both `enc_keys` and `commitments` only ever contain keys `1..=n` (populated in `verify_r1`/`AdditionalBlameMachine::new` via `all_participant_indexes`), so any `Participant` with `u16 > n` deterministically panics. Uncertainty: whether the deployment layer exposes blame with attacker-chosen indexes is application-dependent, but the library API accepts them without validation, and the PoP gate does not prevent reaching the panicking indexing expressions.
