## Title
Escrow finalized and accounting zeroed without validating ERC-20 transfer success in `withdraw()` / `SweepDust` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) pays out escrowed tokens via a raw low-level `call` to the ERC-20 `transfer` selector and only checks that the *call itself* did not revert, never decoding the boolean return value mandated by the ERC-20 standard. Escrow accounting and the permanent "filled" state are updated unconditionally once the call succeeds, even if the token contract returned `false` instead of transferring funds. This is the exact bug class from the external report (`MultiTokenPeriodEnforcer.beforeHook`), reproduced locally in a real fund-custody path.

## Finding Description
In `withdraw()`: [1](#0-0) 

the function marks the order permanently filled (`_filled[body.commitment] = beneficiary`) and decrements the escrow ledger (`_orders[body.commitment][token] -= amount`) based solely on the low-level call succeeding, not on the actual ERC-20 return data:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
A non-reverting, non-compliant ERC-20 (or a compliant token whose `transfer` legitimately returns `false` on failure, e.g. due to a blocklist/pause condition) makes `success == true` while `amount` never reaches `beneficiary`. The same pattern recurs in `SweepDust` handling inside `onAccept`: [2](#0-1) 
and for transaction fee payout: [3](#0-2) 

Both `withdraw()` call sites — the direct `RedeemEscrow`/`RefundEscrow` path via `onAccept`: [4](#0-3) 
and the cross-chain cancel path via `onGetResponse`: [5](#0-4) 

both finalize the order and zero the escrow entry unconditionally once `withdraw()` returns without reverting.

This contrasts with the sibling EVM contract's equivalent function, `IntentsBase._withdraw`, which uses OpenZeppelin's `SafeERC20.safeTransfer`, correctly validating the return data: [6](#0-5) 

The Tron file imports `SafeERC20` and even uses `safeTransferFrom` for *inbound* deposits during `placeOrder`, but the *outbound* payout paths (`withdraw`, `SweepDust`) bypass `SafeERC20` entirely and use the raw, unchecked-return-data `call` pattern instead.

## Impact Explanation
Once `withdraw()` completes without reverting, `_orders[commitment][token]` is decremented to zero and `_filled[commitment]` is permanently set. If the underlying token's `transfer` call returns `false` without reverting, the user/solver beneficiary receives no tokens, yet the contract's internal bookkeeping treats the order as fully and finally settled. There is no code path to retry or recover the escrowed balance afterward — the escrow slot is already zeroed and the commitment is marked filled/refunded, so any subsequent claim reverts with `UnknownOrder()`/`Filled()`. This results in permanent loss of the user's escrowed funds inside the contract with no recovery mechanism, matching the bounty's "stealing or loss of funds" category.

## Likelihood Explanation
This is reachable by any user or solver who places or fills an order using a token whose `transfer` implementation can return `false` on failure without reverting (a known category of ERC-20 non-compliance, and also achievable via blocklist/pausable tokens where transfers to a blocklisted/paused beneficiary return `false`). No malicious relayer, prover, or admin is required — the flaw exists purely in local execution logic that decodes the low-level call's success flag but ignores the ABI-decoded boolean return value.

## Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the deposit-side `safeTransferFrom` usage already present in the same file, so that non-compliant or return-`false` tokens revert the entire transaction instead of allowing escrow state to be finalized without an actual transfer.

## Proof of Concept
1. Deploy a mock ERC-20 whose `transfer` function returns `false` (instead of reverting) when the recipient is in a defined blocklist, or simply always returns `false` while still consuming the call successfully.
2. Place an order via `placeOrder` using this token as an input, escrowing funds into `_orders[commitment][token]`.
3. Trigger `onAccept` with a `RedeemEscrow`/`RefundEscrow` request (or drive it through `cancelOrder` → `onGetResponse`) so `withdraw()` executes.
4. Observe: `token.call(...)` returns `success = true` (call succeeded) even though the token's internal logic returned `false` and did not move any balance.
5. `_orders[commitment][token]` is decremented to zero and `_filled[commitment]` is set — the order is now permanently marked settled, `EscrowReleased`/`EscrowRefunded` is emitted — while `beneficiary`'s token balance never increased. The escrowed tokens remain trapped in the `IntentGatewayV2` contract with no code path to reclaim them.
