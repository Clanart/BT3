### Title
Line-selection index reused against a freshly re-read working-directory diff can silently stage/commit unintended content - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The report's bug class is "using a stale observation as if it were fresh" — an average/selection computed at one point in time is later treated as valid input for a decision made at a different, later point in time, with no check that the underlying data hasn't changed in between. In GitHub Desktop the analogous invariant is: the set of line indices a user selected for a *partial commit* (`file.selection`, an instance of `DiffSelection`) is computed against a diff snapshot taken when the Changes view rendered the file. That selection is stored as raw line indices (`absoluteIndex`/`unifiedDiffStart`), not against content hashes. When the commit is actually performed, `applyPatchToIndex` re-fetches the diff from disk (`getWorkingDirectoryDiff`) and feeds the *old* selection indices into `formatPatch` against the *new* hunk layout, with no re-validation that the file didn't change between selection-time and commit-time.

### Finding Description
`formatPatch` builds the unified diff to `git apply --cached` purely by walking the (freshly fetched) diff's hunks and asking `file.selection.isSelected(absoluteIndex)` for each line, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex`: [1](#0-0) 

The selection itself (`file.selection`) is not derived at commit time — it comes from whatever the UI last computed in `updateChangesWorkingDirectoryDiff`, which recomputes `selectableLines` (a `Set<number>` of line indices) only when the user is actively viewing/selecting that file's diff: [2](#0-1) 

Crucially, `applyPatchToIndex` re-reads the diff from disk immediately before generating the patch to stage: [3](#0-2) 

Nothing between the last UI diff refresh and this re-fetch verifies that the file content (and therefore the hunk boundaries/line indices) is unchanged. If the file is modified on disk after the user made their line selection but before `Commit` is clicked — for example by a build tool, an editor auto-save, a `post-checkout`/`pre-commit` hook shipped in a cloned/fetched malicious repository, or any background process writing to the working tree — the hunk layout used by `formatPatch` at commit time can differ from the hunk layout the user actually looked at when selecting lines. Because selection is keyed purely by numeric line offset and not by content/hash, the same offsets can now point at entirely different lines (different additions/deletions), and `formatPatch`/`git apply --cached` will silently include or exclude the wrong content in the staged patch.

This is architecturally identical to the "TWAP" flaw: the code treats an old observation (line-index selection taken at time T1) as if it reflects the state of the world at the time it's consumed (T2), with no timestamp/hash-based guard analogous to "amount of time passed since last beat."

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user could believe they are staging/committing a specific reviewed hunk (e.g., excluding a sensitive line, or including only an intended change) while Desktop actually stages different lines because the working file was mutated by an attacker-controlled or attacker-influenced process between selection and commit (e.g., a malicious `post-checkout` hook in a freshly cloned repository that rewrites a tracked file shortly after checkout, or a build/watch script triggered by files in the cloned repository). The result is a commit whose content silently diverges from what the diff view showed the user, which can lead to committing/pushing unintended or malicious content, or omitting content the user believed was excluded — without any error or warning.

### Likelihood Explanation
Medium-low. It requires a window between the user's diff-view/selection action and the "Commit" click during which the working file changes in a way that shifts hunk boundaries (not just content within the same lines). This is plausible for repositories that ship build tooling, file watchers, or git hooks that fire on checkout/merge and rewrite tracked files — all of which an attacker fully controls when the victim clones/fetches a malicious repository. It does not require local/physical access, admin rights, or social engineering beyond the normal act of cloning a repository and using Desktop's partial-commit UI, which is a core, frequently used feature.

### Recommendation
Bind `DiffSelection` state to a content-derived identity of the diff it was computed against (e.g., a hash of the diff text or hunk headers), and re-validate that identity at commit time before calling `formatPatch`/`applyPatchToIndex`. If the on-disk diff at commit time doesn't match the diff the selection was derived from, either recompute selectable lines against the fresh diff (as already partially done for the UI's `selectableLines` recomputation) or abort the partial-commit and prompt the user to re-review the diff, rather than silently applying stale line-index selections to a new hunk layout.

### Proof of Concept
Conceptual repro (not executed, based on code inspection):
1. Clone a repository containing a `post-checkout` hook (or rely on any background process/build tool) that appends/removes lines in a tracked file shortly after checkout, shifting line numbers in that file's diff.
2. Open the file in Desktop's Changes view, and select only specific lines/hunks for partial commit (e.g., deselect a sensitive addition). This computes `file.selection` against the diff hunk layout at that moment: [2](#0-1) 
3. Before clicking "Commit," the hook/tool fires and mutates the file, shifting hunk boundaries without the user reopening the diff.
4. Click "Commit." `stageFiles` → `applyPatchToIndex` re-fetches the diff fresh from disk and calls `formatPatch(file, diff)` using the *old* `file.selection` indices against the *new* hunks: [3](#0-2) [4](#0-3) 
5. The resulting staged/committed patch includes or omits different lines than what the user actually selected in the UI, with no warning.
