### Title
Cached FROST preprocess seed is never reclaimed after signing, causing deterministic nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` writes a `CachedPreprocess` seed into `CachedPreprocesses` the first time a given `context` is used, then re-reads that same seed on every subsequent `share()`/`complete()` call for the context — and never deletes or rotates it after consumption. Because `AlgorithmSignMachine::from_cache` → `seeded_preprocess` deterministically regenerates the FROST nonces from that seed (`ChaCha20Rng::from_seed(*seed.0)`), every signature produced under the same context reuses identical nonces. Signing two different messages (or the same message with different binding sets) under reused nonces lets any party who observes the two signature shares algebraically recover the signer's secret share.

### Finding Description
The analog of the upstream bug ("flush rings but forget to reclaim the flushed packets") is exactly present here: a one-shot resource (the preprocess seed) is consumed but never reclaimed.

In `preprocess_internal`, the cache entry is created once and then read back on every call:

```rust
// coordinator/src/tributary/signing_protocol.rs:123-145
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  let mut cache = machine.cache();
  ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

There is no `CachedPreprocesses::del`/removal after the machine is consumed by `share_internal` (line 156 calls `self.preprocess_internal(participants).0` again for every share). The cache survives across the whole lifetime of the context.

`DkgConfirmer` fixes its context to `(b"DkgConfirmer", self.attempt)` (line 275). Its public surface calls into `share_internal` twice per confirmation:

- `DkgConfirmer::share` (line 304-309) signs `set_keys_message(set, removed, key_pair)`, where `key_pair` is attacker-influenced data arriving over the tributary protocol.
- `DkgConfirmer::complete` (line 312-327) invokes `share_internal` a second time to rebuild the machine.

Because the seed is identical, `self.nonces` regenerated inside `AlgorithmSignMachine` are identical each time (`seeded_preprocess`, crypto/frost/src/sign.rs:121-144; `from_cache` at lines 268-274). The FROST share is `nonce + challenge * lagrange * secret_share` (share computed in `sign_share` at sign.rs:398 with nonces drained at lines 386-396). Two shares over the same nonce but different challenges `c1, c2` (different `msg` or different preprocess sets change `rho_transcript`/challenge at sign.rs:361-379) yield `secret_share = (s1 - s2) / ((c1 - c2) * lagrange)`. The `CachedPreprocess` doc itself warns reuse "will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:84-92, 209-224).

### Impact Explanation
An unprivileged participant (or anyone who observes two distinct `key_pair`/preprocess sets submitted under the same DKG attempt — shares are broadcast on the tributary) can recover the validator's Ristretto secret share for the MuSig confirmation key. That key authenticates `set_keys_message` confirmations of newly generated group keys; recovering it enables forging confirmations/signing as that validator for anything under the same context, and the same pattern repeats for other `SigningProtocol` contexts in this file. This is direct key-share recovery from publicly broadcast signature shares — the exact consequence the FROST caching API documents it must prevent.

### Likelihood Explanation
Reachable whenever `share()` is invoked more than once per attempt with differing inputs — e.g., a `complete()` after a `share()` with different shares/preprocesses, or a retried confirmation carrying a different `key_pair`. `share` is reachable by any tributary participant supplying preprocess/key_pair data; no privileged access, collusion, or leaked key is required. The nonces are guaranteed identical because the seed is deterministic and never rotated.

### Recommendation
Delete the `CachedPreprocesses` entry atomically when the machine is consumed for signing (e.g., remove it inside `share_internal` before `machine.sign(...)` returns, or make `preprocess_internal` take-and-delete rather than get). Ensure a new seed is generated for each signing operation under a context, so `preprocess()`/rebuild paths never resurrect the same nonces.

### Proof of Concept
1. For a fixed `attempt`, submit a `key_pair` `K1` so the target validator runs `DkgConfirmer::share(preprocesses_A, K1)` → share `s1` over nonce `k` (derived from the cached seed for context `(b"DkgConfirmer", attempt)`).
2. Submit a different `key_pair` `K2` (or different preprocess set `preprocesses_B`) so `share`/`complete` runs again → share `s2` over the *same* nonce `k` but different challenge `c2`.
3. With `s1 = k + c1·λ·x` and `s2 = k + c2·λ·x`, compute `x = (s1 - s2) / (λ·(c1 - c2))`, recovering the validator's secret share. The reuse is guaranteed because `CachedPreprocesses::get` at signing_protocol.rs:137 always returns the seed written at line 134 and nothing ever removes it.
