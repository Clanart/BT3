## Title
Cross-chain and cross-deployment replay of `SubstrateCalldata` signatures in `pallet-hyper-fungible-token` enables unauthorized dispatch of arbitrary runtime calls as the beneficiary - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler lets a cross-chain token transfer carry optional `SubstrateCalldata` — a signed `runtime_call` that is dispatched with `RawOrigin::Signed(beneficiary)` once the signature is verified. The signed payload is `(nonce, runtime_call)` only: it does not include a chain identifier, genesis hash, spec version, pallet/module instance identifier, or the source/destination state machine. This is exactly the missing-chain-id / missing-domain-binding replay pattern described in the external report.

### Finding Description
In `on_accept` [1](#0-0) , when `message.data` is non-empty the pallet decodes `SubstrateCalldata { signature, runtime_call }` and, if a signature is present, verifies it over:

```rust
let nonce = frame_system::Pallet::<T>::account_nonce(beneficiary.clone());
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
``` [2](#0-1) 

This same unbound `(nonce, runtime_call)` scheme is repeated identically for Ed25519, Sr25519, and ECDSA branches [3](#0-2) . After verification, the call is dispatched as the beneficiary and the beneficiary's local account nonce is incremented, which is the *only* replay guard used [4](#0-3) .

Contrast this with every other signed cross-chain payload in this codebase, which explicitly binds the destination `StateMachine` to prevent exactly this class of bug:
- relayer fee withdrawal: `(nonce, dest_chain, beneficiary)` [5](#0-4) 
- outbound consensus/request delivery claims: `(commitment/set_id, dest_chain, payee)` [6](#0-5) [7](#0-6) 
- beneficiary redirect: `(nonce, state_machine, beneficiary)` [8](#0-7) 

The HFT calldata signature is the one place in the repo that dropped this binding. Because Substrate `AccountId32` public keys are portable across chains, and `pallet-hyper-fungible-token` (plus its companion `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contracts, per the docs) is meant to be deployed on multiple chains with the same wire format [9](#0-8) , a signature the beneficiary produced authorizing a call at nonce `N` on chain A is byte-identical to what would be required to authorize the same call at nonce `N` on chain B (or a redeployed/second instance of the pallet on the same relay, or an upgraded/migrated chain where the account's nonce is reset). The message body containing the signature and `runtime_call` bytes is visible in the public `PostRequest` on both source and destination, so any observer can lift `substrate_data` (signature + `runtime_call`) and resubmit it via their own `HyperFungibleToken::send` call to any other chain hosting the same pallet, targeting the same beneficiary bytes as `to`. `authenticate`/`ContractToAsset` checks the *source contract → asset* mapping, not the calldata's originating chain [10](#0-9) , so it does nothing to stop this: it only gates which asset/decimals apply, not whether the embedded calldata signature is chain-scoped.

The existing test explicitly validates only same-chain nonce-increment replay protection, not cross-chain reuse [11](#0-10) , confirming the cross-chain gap was never exercised or closed.

### Impact Explanation
This allows unauthorized execution of an arbitrary (filter-permitted) `RuntimeCall` as the victim beneficiary on any additional chain/instance running `pallet-hyper-fungible-token`, without the beneficiary's consent for that chain. Since `RawOrigin::Signed(beneficiary)` is used, the dispatched call can move the beneficiary's balance (e.g. `Balances::transfer`) or otherwise act with their full signed-origin privileges, matching the bounty's "unauthorized transaction or execution" / "transaction manipulation" / "stealing or loss of funds" categories. It requires no relayer, admin, or governance compromise — any unprivileged party who observes the on-chain calldata can trigger it.

### Likelihood Explanation
Likelihood depends on the HFT pallet actually being deployed identically (same beneficiary AccountId reachable, same nonce state) on more than one chain, which is the pallet's documented multi-chain design intent [9](#0-8) . An attacker does not need to guess the nonce — they can simply resend the exact captured `SubstrateCalldata` blob to a chain where the beneficiary's nonce still matches (e.g., a fresh account, a newly onboarded chain, or shortly after the original valid use before the beneficiary's nonce advances there). This is a realistic, unprivileged, public-entrypoint path.

### Recommendation
Bind the signed payload to the specific chain/pallet instance and to the actual delivery context, mirroring the pattern already used elsewhere in the repo:
- Include a genesis hash or `StateMachine`/`ChainId` value (and ideally the pallet's own `PALLET_ID`) in the signed `payload`, i.e. `(nonce, chain_id, pallet_id, runtime_call)`.
- Alternatively, derive the "nonce" domain from the ISMP request's `source`/`dest` fields already available in `on_accept`, so the same signature can never be valid across two different `(source, dest)` pairs.
- Add a regression test that captures a valid `SubstrateCalldata` from one simulated destination context and asserts it is rejected when replayed against a different destination state machine / pallet instance.

### Proof of Concept
1. Beneficiary Bob (AccountId32 `B`) signs `SubstrateCalldata` off-chain to authorize `Balances::transfer_allow_death { dest: Attacker, value: X }` at his current nonce `0` on chain A, intending it to run once inside a `HyperFungibleToken::send` from chain A.
2. The resulting `PostRequest.body` (containing `Message.data = SubstrateCalldata { signature, runtime_call }.encode()`) is delivered and executed on chain A per `on_accept`, incrementing Bob's nonce there to `1` [12](#0-11) .
3. Chain B also runs `pallet-hyper-fungible-token` and Bob's account there still has nonce `0` (e.g., he has never transacted on chain B). An attacker, having observed the public `SubstrateCalldata` bytes from chain A's request/event log, submits `HyperFungibleToken::send` on chain B (or any chain) with `to = Bob`'s bytes and `data` set to the same captured `SubstrateCalldata`.
4. On chain B, `on_accept` recomputes `nonce = account_nonce(Bob) = 0`, matching the original signed payload; signature verification succeeds; `Balances::transfer_allow_death` is dispatched with `RawOrigin::Signed(Bob)`, moving Bob's chain-B balance to the attacker's address — something Bob never authorized on chain B.

*Confidence note:* I was not able to fully verify from the index whether every real-world deployment plan for `pallet-hyper-fungible-token` places it on more than one live chain with reachable duplicate/reset nonce states — the documentation supports the multi-chain deployment model, but the exact production topology is outside what the indexed code confirms. The code-level absence of chain binding in the signed payload, however, is directly confirmed.

## Cross-Chain Message Format

The pallet encodes messages using the same ABI format as the Solidity contracts:

```solidity
struct Message {
    bytes from;    // original sender (for timeout refunds)
    bytes to;      // recipient on destination chain
    uint256 amount;
    bytes data;    // optional calldata
}
```

This ensures full compatibility between `pallet-hyper-fungible-token`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` on any chain.

---

## Calldata Execution

The `call_data` field in `SendParams` allows executing arbitrary runtime calls on the destination substrate chain after the tokens are transferred. The calldata is SCALE-encoded as:

```rust lineNumbers
pub struct SubstrateCalldata {
    /// Optional SCALE-encoded MultiSignature of (account_nonce, runtime_call)
    pub signature: Option<Vec<u8>>,
    /// SCALE-encoded runtime call to execute
    pub runtime_call: Vec<u8>,
}
```

If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch. Supported signature types: Ed25519, Sr25519, ECDSA. The account nonce is incremented after dispatch to prevent replay.

If no signature is provided, the origin is derived from the sender address in the cross-chain message.
```
