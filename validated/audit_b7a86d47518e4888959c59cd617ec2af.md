### Title
Future-dated oracle timestamps bypass staleness gating in `oracle-timestamp-fresh` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`oracle-timestamp-fresh` in `mainnet/contracts/market/v0-4-market.clar` computes the staleness `delta` as `u0` whenever a feed's `publish-time` is greater than `stacks-block-time`, rather than rejecting or bounding future-dated timestamps. This lets any price update whose timestamp is ahead of the chain's current time pass the staleness check unconditionally, for as long as `stacks-block-time` has not caught up to that timestamp — effectively disabling the freshness gate for that feed during that window.

### Finding Description
The freshness check is:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 

This is invoked from `price-resolve`, which asserts both price legality and timestamp freshness before returning the price used downstream:
```clarity
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
``` [2](#0-1) 

The intent of the `if` branch is presumably to tolerate small clock skew between Pythnet/DIA publish times and the Stacks chain's `stacks-block-time`. But the implementation clamps `delta` to `u0` for *any* magnitude of future skew — one second or one year ahead both yield `delta = u0`, which trivially satisfies `(<= delta max-staleness)`. There is no upper bound rejecting timestamps that are implausibly far in the future. Once a feed's stored `publish-time` is ahead of `stacks-block-time` (via a legitimately signed but clock-skewed update, or any feed whose `publish-time` value is simply large), the freshness gate stays satisfied unconditionally until real chain time catches up — at which point the "monotonic" `(>= ts prev)` guard means a stale, no-longer-updated feed still reads as "fresh" throughout that entire forward window, regardless of `max-staleness`.

This is a defect in Zest's own staleness-gating logic (`oracle-timestamp-fresh`), not a third-party data-correctness issue: it is Zest's code that decides how to treat `ts > stacks-block-time`, and it chooses to always pass rather than reject or clamp to a bounded skew tolerance.

### Impact Explanation
`price-resolve`/`price-multi-resolve` (which calls `oracle-timestamp-fresh` per asset) supplies the prices used to value collateral and debt for LTV/health computations in the market contract [3](#0-2) . If a feed's price is frozen at a future-dated timestamp (whether from clock skew, feed staleness after the last real update, or a feed simply not being refreshed), the market will keep treating that (now economically stale) price as valid for the duration of the forward window. A stale price that happens to favor a borrower's position (e.g., overvalues their collateral or undervalues their debt) can be used to avoid liquidation or to borrow more than actual collateral value supports. If the market ever moves against the stale price before it's corrected, this results in under-collateralized positions and bad debt — a form of temporary/permanent freezing or loss of protocol funds through mispriced collateral, landing in the High/Critical impact classes described (protocol insolvency / theft via mispriced collateral) depending on how large the price staleness window and price divergence are.

### Likelihood Explanation
This does not require oracle compromise or third-party bad data — it can be triggered by ordinary clock skew between the price source's `publish-time` and the Stacks chain's `stacks-block-time`, or simply by a feed publish-time value that is momentarily ahead of chain time. Given `stacks-block-time` reflects the Stacks blockchain clock while `publish-time` reflects Pythnet/DIA clocks, some skew is expected in practice, making this reachable under normal operating conditions rather than requiring an attack precondition.

### Recommendation
Change `oracle-timestamp-fresh` to reject (or bound to a small, explicit tolerance) timestamps that are ahead of `stacks-block-time`, instead of clamping `delta` to `u0`:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)                 ;; reject/clamp future timestamps, don't zero-out delta
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
If minor clock skew tolerance is desired, bound it explicitly (e.g., a small constant `MAX_CLOCK_SKEW`) rather than allowing an unbounded future timestamp to always pass.

### Proof of Concept
1. A price feed publishes (or has previously published) an update with `publish-time = T_future`, where `T_future > stacks-block-time` at write time (e.g., due to clock skew or a malformed but validly-processed update).
2. `market.clar` stores this as `last-update` for that feed key.
3. On any subsequent call to `price-resolve` for that asset while `stacks-block-time < T_future`, `oracle-timestamp-fresh` computes `delta = u0`, which always satisfies `(<= delta max-staleness)` — the price is accepted as fresh no matter how outdated the actual market price has become.
4. A user exploits this by opening/maintaining a borrow position sized against the favorable stale price, or by avoiding liquidation, until real market price moves further away from the frozen quoted price, at which point the position is under-collateralized relative to true market value but still reads as healthy on-chain.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
