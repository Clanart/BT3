Scanner reports immature coinbase outputs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates `block.txdata` including `txdata[0]`, the coinbase transaction, and emits `ReceivedOutput`s for it via `scan_transaction` (networks/bitcoin/src/wallet/mod.rs:221-227, 199-214). Coinbase outputs are unspendable for 100 blocks (Bitcoin's maturity rule), and if the block is ever reorganized out within that window they become permanently unspendable — they are removed from the UTXO set entirely, unlike normal transactions which can re-confirm. Serai's processor treats outputs as final after `N::CONFIRMATIONS` confirmations (far fewer than 100), so a coinbase output paying the multisig's tweaked key is credited as a received deposit while it is not yet — and may never be — spendable. This mirrors the report's bug class: state is snapshotted/scanned at a point in time and credited, while a subsequent state change (coinbase maturation/reorg) can invalidate the credited funds.

### Finding Description
`scan_block` unconditionally calls `scan_transaction` on every transaction in `block.txdata` (mod.rs:223-224), and `scan_transaction` returns a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script (mod.rs:205-210), with no `tx.is_coinbase()` check and no maturity tracking on `ReceivedOutput`. The only guard is a doc comment on `scan_block` noting that "a post-processing pass is needed" for spendability — but nothing in the type enforces it, and `scan_transaction` itself performs no such filtering. The downstream processor scan loop (`processor/src/multisigs/scanner.rs:562-566`) collects `network.get_outputs(&block, key)` and only filters on `amount >= N::DUST`, emitting `ScannerEvent::Block` carrying the outputs for crediting; whether the Bitcoin `get_outputs` wrapper additionally skips coinbases could not be fully confirmed in the indexed code (there is a single coinbase-related reference in `processor/src/networks/bitcoin.rs`, but the wallet-level API itself unconditionally exposes the immature output and the dedup/`seen` machinery marks it as processed).

### Impact Explanation
Funds are reported received that are not spendable. An unprivileged miner can direct a coinbase payout (or any pooled-mining payout derived from coinbase flow) to a Serai multisig address. The output is credited after `N::CONFIRMATIONS`, yet for ~100 blocks any attempt by `SignableTransaction`/`TransactionMachine` to spend it produces a transaction the network rejects. Worse, if the containing block is orphaned before maturity — which a miner with modest hash rate can arrange, or which occurs naturally — the output can never be spent at all, while the deposit has already been credited/minted against, creating unbacked liabilities analogous to the double-credited rewards/deposits in the report.

### Likelihood Explanation
Triggering requires a miner (or mining pool) to pay a Serai address via a coinbase and for that block to be orphaned inside the maturity window, or for Serai to attempt spending within 100 blocks of crediting. Mining a block is costly but no privileged access, collusion, or leaked key is needed — only public Bitcoin transactions the attacker causes to exist. Natural orphaning of confirmed coinbase blocks is rare but non-negligible over long operation, and the "credited but unspendable" state exists deterministically for 100 blocks every time.

### Recommendation
In `Scanner::scan_block`/`scan_transaction` (networks/bitcoin/src/wallet/mod.rs), skip `txdata[0]`/coinbase transactions when emitting `ReceivedOutput`s, or attach the containing block height to `ReceivedOutput` and enforce the 100-block maturity before the output is eligible for `SignableTransaction::new`. In `processor/src/networks/bitcoin.rs`'s `get_outputs`, explicitly exclude `tx.is_coinbase()` outputs unless the block depth exceeds maturity.

1. An attacker mines (or controls a pool that mines) block B whose coinbase includes an output paying `p2tr_script_buf(multisig_key)` — no signature or key knowledge required.
