### Title

`SignableTransaction` omits `OP_RETURN` outputs from transaction fee and weight calculations - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Kirstentat/serai--020/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` adds a caller-supplied `OP_RETURN` output before estimating transaction weight and required fees, but `calculate_weight_vbytes` is called with only `payments` and `change`, omitting the data output from the estimated transaction. The resulting transaction therefore reserves the fee required for a smaller transaction while actually committing to the larger transaction containing the `OP_RETURN` output.

### Finding Description

The constructor appends an `OP_RETURN` output to `tx_outs` when `data` is supplied. [1](#0-0)  It subsequently invokes `calculate_weight_vbytes(tx_ins.len(), payments, None)`, whose synthetic transaction contains only inputs and `payments`. [2](#0-1)  When change is present, the second call similarly includes the change output but still omits the already-created `OP_RETURN` output. [3](#0-2) 

Because `needed_fee` is calculated as `fee_per_vbyte * vbytes` from the incomplete transaction, it excludes the data output's serialized size. [4](#0-3)  The actual fee is later defined as input value minus the final transaction's outputs, including the `OP_RETURN` output, so the requested fee rate is applied to a smaller vsize than the transaction ultimately signed. [5](#0-4) 

For an `OP_RETURN` payload up to 75 bytes, the omitted output contributes `11 + data_len` serialized bytes; for 76–80 bytes, `PUSHDATA1` makes it `12 + data_len` bytes. These are non-witness bytes, so the transaction's vsize and weight increase by that amount and four times that amount respectively.

### Impact Explanation

Every transaction using `data` and a change output reserves too little fee for its final size. At a requested rate of 1 sat/vbyte, the signed transaction can fall below Bitcoin's minimum relay rate and be rejected or fail to propagate. At higher requested rates, it still pays less than the explicitly requested fee rate and can remain unconfirmed during congestion.

An unprivileged party that can cause transaction data to be included can therefore cause the threshold wallet to produce a transaction with a materially lower effective fee rate than requested. The UTXOs are not permanently lost, but the intended spend can be stalled and may require constructing and coordinating signatures for a replacement transaction.

### Likelihood Explanation

The issue is deterministic whenever `SignableTransaction::new` receives `Some(data)` together with a change output. The API permits up to 80 bytes, and neither fee-estimation call accounts for the resulting output. [6](#0-5)  No race, malformed encoding, or attacker-controlled cryptographic state is required.

### Recommendation

Calculate weight and virtual size from the complete output set, including the `OP_RETURN` output. This can be done by passing the final `tx_outs` to the estimator or by explicitly adding the `OP_RETURN` output inside `calculate_weight_vbytes`. After construction, add an assertion equivalent to `tx.fee() >= fee_per_vbyte * tx.transaction().vsize()`.

### Proof of Concept

A unit test can construct a transaction with one input, one payment, one change output, and an 80-byte `OP_RETURN` payload:

```rust
let tx = SignableTransaction::new(
  vec![received_output],              // e.g. 100_000 sat input
  &[(payment_script, 10_000)],
  Some(change_script),
  Some(vec![0; 80]),
  1,                                  // sat/vbyte
)
.unwrap();

let actual_vsize = u64::try_from(tx.transaction().vsize()).unwrap();
let actual_fee = tx.fee();

assert_eq!(actual_fee, tx.needed_fee());
assert!(actual_fee < actual_vsize);
```

The final assertion holds because `needed_fee` and the change calculation are based on an estimated transaction without the 92-byte `OP_RETURN` output, while `transaction().vsize()` includes it.
