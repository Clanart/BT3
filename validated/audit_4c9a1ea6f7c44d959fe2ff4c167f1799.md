## Analog Found: Non-Canonical Protobuf Wire-Format Encoding (Serialization Malleability)

### Title
Protobuf binary wire format admits multiple non-canonical byte encodings for identical decoded values, enabling malleability of any security control that relies on raw serialized bytes - (File: `src/google/protobuf/varint_shuffle.h`, `docs/field_presence.md`)

### Summary
The external report's core invariant is: EVM's `ecrecover` accepts multiple distinct signature byte-encodings (`s` and `n-s`) that both validate to the same signer, so any security logic keyed on the *raw signature bytes* (rather than the semantic recovered value) is malleable/replayable unless mitigated. The Protobuf analog is structural: the binary wire format is explicitly documented and tested to have **no canonical representation** — multiple distinct byte streams decode to the exact same logical message (overlong/non-canonical varints, duplicate scalar fields with "last-wins" merge semantics, reordered fields, "extra zero" overwrites). Any consuming application that fingerprints, deduplicates, signs, or replay-protects based on the raw serialized bytes of an attacker-supplied Protobuf payload — instead of the semantic decoded message — inherits the same malleability class as SWC-117.

### Finding Description
Protobuf's own documentation states there is no canonical byte-level representation of a message: [1](#0-0) 

The same warning is repeated verbatim in the C# implementation: [2](#0-1) 

And in the core coded-stream header: [3](#0-2) 

Concretely, the wire-format parser accepts "over-serialized" (non-canonical) varints — values padded with extra continuation-bit bytes that still decode to the identical integer — as valid input rather than rejecting them: [4](#0-3) 

This is exercised extensively by the parser conformance tests, which explicitly construct "canonical and non-canonical encodings" of the same field value and assert they parse to identical results: [5](#0-4) [6](#0-5) 

Separately, when a singular field or oneof member appears multiple times on the wire, the last occurrence silently overwrites earlier ones ("last one wins"), which is documented behavior: [7](#0-6) 

and is directly tested, including the case where a trailing zero-value byte sequence silently overwrites a previously-decoded non-zero value: [8](#0-7) 

Taken together: an attacker who controls a bounded binary Protobuf payload can produce **many distinct byte sequences that all decode to the same semantic message** (by padding varints with redundant continuation bytes, reordering fields, or appending duplicate field occurrences). Just as ECDSA's `(r, s)` and `(r, n-s)` both `ecrecover` to the same address, these distinct byte sequences all deserialize to an equal `Message` (per generated `equals()`/`Equals()` methods), even though the raw bytes differ.

### Impact Explanation
This has no fixed impact inside Protobuf itself — Protobuf is not a signature or replay-protection library. The impact is transferred exactly like the original report frames it: **if any consuming application uses the raw serialized bytes of a Protobuf message as a security-relevant identity** — e.g., as a cache/dedup key, a replay-detection nonce, an audit fingerprint, or input to a MAC/signature computed over the wire bytes rather than over canonical/semantic content — an attacker can submit a semantically-identical-but-byte-distinct payload to bypass that check (duplicate submission, cache-bust, or evade a byte-level blocklist), while the parsed/decoded message that downstream logic acts on is unchanged. This mirrors the report's own caveat: the malleability is currently "mitigated ... specifically to prevent replays" at the application layer, and "if any application logic changes, it might make signature malleability a risk" — Protobuf's docs give the same warning, verbatim, for byte-level canonicalization.

### Likelihood Explanation
High likelihood of the *underlying condition* being exploitable in any application that violates Protobuf's own documented guidance (treating serialized bytes as canonical), and low/no likelihood of it being a defect in Protobuf itself, since Protobuf explicitly disclaims canonical serialization and instructs users needing canonical form to implement their own canonicalization via reflection APIs. This is analogous to the original finding being rated informational because the actual application already tracks/cancels accepted offers rather than relying on signature-byte identity.

### Recommendation
No change is warranted in Protobuf's core wire format (accepting non-canonical varints and "last-wins" duplicate-field merging are required for forward/backward compatibility and are intentionally documented, per `docs/field_presence.md` and the `CodedOutputStream` API docs). The applicable guidance — parallel to "use OpenZeppelin's ECDSA library" — is: consuming applications must never treat raw Protobuf wire bytes as a canonical identity for security decisions (dedup keys, replay nonces, signatures-over-bytes). Where canonical fingerprints are required, use `Deterministic`/`useDeterministicSerialization()` only within a single build/language as documented, or better, canonicalize via the reflection APIs as the docs recommend, or hash the semantically-decoded message rather than its wire bytes.

### Proof of Concept
Using the existing test helper `EncodeInt32Value`/`AddNonCanonicalBytes` logic in `src/google/protobuf/message_unittest.inc` (lines 1855-1946), an attacker can pad any varint-encoded field with up to 9 extra `0x80`-continuation bytes while it still decodes to the identical field value — producing byte-distinct-but-semantically-identical serialized messages, verified by the `TestInt32Parsers`/`TestBoolParsers`/`TestEnumParsers` suites (`src/google/protobuf/message_unittest.inc:2186-2249`) which iterate `non_canonical_bytes` from 0 to 9 and assert the decoded value is unchanged in every case. This is a minimal, local, trusted-schema reproduction (no crash, no memory-safety issue) demonstrating multiple valid byte encodings for one decoded value — the exact "malleable representation" precondition the ecrecover analog requires.

```text
  // case, the continuation bit of ptr[8] already set the top bit of res3
  // correctly, so all we have to do is check that the expected case is true.
  if (ABSL_PREDICT_TRUE(next() == 1)) goto done2;

  if (ABSL_PREDICT_FALSE(last() & 0x80)) {
    // If the continue bit is set, it is an unterminated varint.
    return nullptr;
  }

  // A zero value of the first bit of the 10th byte represents an
  // over-serialized varint. This case should not happen, but if does (say, due
  // to a nonconforming serializer), deassert the continuation bit that came
  // from ptr[8].
  if (kIs64BitVarint && (last() & 1) == 0) {
    static constexpr int bits = 64 - 1;
#if defined(__GCC_ASM_FLAG_OUTPUTS__) && defined(__x86_64__)
    // Use a small instruction since this is an uncommon code path.
    asm("btc %[bits], %[res3]" : [res3] "+r"(res3) : [bits] "i"(bits));
#else
    res3 ^= int64_t{1} << bits;
#endif
```

```text
// Adds `non_canonical_bytes` bytes to the varint representation at the tail of
// the buffer.
// `buf` points to the start of the buffer, `p` points to one-past-the-end.
// Returns the new one-past-the-end pointer.
uint8_t* AddNonCanonicalBytes(const uint8_t* buf, uint8_t* p,
                              int non_canonical_bytes) {
  // varint can have a max of 10 bytes.
  while (non_canonical_bytes-- > 0 && p - buf < 10) {
    // Add a dummy byte at the end.
    p[-1] |= 0x80;
    p[0] = 0;
    ++p;
  }
  return p;
}
```

```markdown
-   When deserializing, duplicate field values may be handled in different ways
    depending on the field definition.
    -   Duplicate `repeated` fields are typically appended to the field's API
        representation. (Note that serializing a *packed* repeated field
        produces only one, length-delimited value in the tag stream.)
    -   Duplicate `optional` field values follow the rule that "the last one
        wins."
-   `oneof` fields expose the API-level invariant that only one field is set at
    a time. However, the wire format may include multiple (tag, value) pairs
    which notionally belong to the `oneof`. Similar to `optional` fields, the
    generated API follows the "last one wins" rule.
```
