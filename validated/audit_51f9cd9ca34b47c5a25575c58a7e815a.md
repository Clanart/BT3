## Title
Anyone can steal leftover/dust reward token balances from `ManualCompound` via permissionless `compound()` - (File: `rewards/ManualCompound.sol`)

### Summary
`ManualCompound.compound()` is an unprivileged, permissionless function that, after claiming rewards on behalf of the caller through `MasterMagpie.multiclaimOnBehalf`, sweeps reward token balances using `IERC20(token).balanceOf(address(this))` rather than tracking the amount actually received during that call. Because both the "non-compoundable reward" sweep and the "compoundable reward" sweep operate on the full current contract balance, and because the caller fully controls the `_lps`/`_rewards` arrays (including specifying tokens/pools where they have zero actual claimable amount), any wallet can drain any leftover token balance sitting in `ManualCompound` to itself. This mirrors the reported `Swapper`/`UniswapV3Swapper` bug class: a contract that is not supposed to hold balances between transactions, but whose swap/claim function trusts `balanceOf(address(this))` instead of the exact delta transferred in, letting anyone claim leftover funds.

### Finding Description
`compound()` has no access control (no `onlyOwner`/allow-list) — it's callable by any wallet: [1](#0-0) 

After `multiclaimOnBehalf` claims MasterMagpie rewards for `msg.sender` into the `ManualCompound` contract, the "non-compoundable" reward loop transfers `IERC20(_rewards[i][j]).balanceOf(address(this))` — the entire current token balance of the contract, not the amount actually claimed by this specific call — to `msg.sender`: [2](#0-1) 

The second loop, over the registered `rewards` array (state, not caller input), does the same thing for "compoundable" tokens, moving `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` out via a convertor/locker/helper or a direct transfer to `msg.sender`: [3](#0-2) 

Because `_lps`/`_rewards` are fully attacker-controlled parameters, an attacker can call `compound()` specifying a staking token pool where they have zero (or negligible) actual pending rewards, together with `_rewards[i] = [tokenToSteal]`. `IMasterMagpie(masterMagpie).multiclaimOnBehalf` will legitimately claim ~0 for that pool/token via `_claimBaseRewarder` → `rewarder.getRewards(...)`, but the subsequent sweep in `compound()` still reads and transfers the entire current `balanceOf(address(this))` for `tokenToSteal`. Any pre-existing balance of that token in the contract — leftover dust from a prior `compound()` call (e.g., rounding remainders not fully consumed by `IConverter.convertFor`, `ILocker.lockFor`, or `ISimpleHelper.depositFor`), or tokens mistakenly/otherwise sent to the contract — is swept entirely to the attacker instead of to whichever user it actually belonged to.

This is functionally identical to the reported `Swapper` issue: a shared helper contract that is expected to hold no balance between calls exposes a permissionless entry point that acts on `balanceOf(address(this))`, so any leftover balance becomes available to be claimed by an arbitrary caller.

### Impact Explanation
Any unclaimed dust/leftover reward tokens sitting in `ManualCompound` — which represents unclaimed yield belonging to other users who previously compounded through this contract — can be stolen by any unprivileged wallet by simply invoking `compound()` with a token list that includes the token to steal. This is a direct theft of other users' unclaimed yield held by the compounding helper contract.

### Likelihood Explanation
Likelihood depends on `ManualCompound` actually accumulating leftover token balances between calls (rounding dust from `convertFor`/`lockFor`/`depositFor`, or a stray/accidental transfer). Given `compound()` places no restriction on `_lps`/`_rewards` contents (they need not correspond to real claimable amounts), the exploit requires only a single normal transaction once any dust exists, at zero cost or risk to the attacker.

### Recommendation
Compute and move only the amount actually received during the current `compound()` invocation (e.g., snapshot `balanceOf` before `multiclaimOnBehalf` and use the delta), rather than sweeping the full `balanceOf(address(this))`. Alternatively, ensure `ManualCompound` never holds any residual balance across transactions and restrict `_rewards`/`_lps` combinations to only tokens/pools with a positive, freshly-claimed amount for `msg.sender`.

### Proof of Concept
1. Some dust of reward token `X` remains in `ManualCompound` from a prior `compound()` call (e.g., rounding leftover from `IConverter.convertFor`), or the token is registered as compoundable and dust accumulates in `rewards[i].tokenAddress` balance.
2. Attacker (who has no meaningful stake/claim) calls `compound(_lps, _rewards, 0, 0, false)` with `_lps`/`_rewards` referencing pool(s)/token `X` for which they have ~0 real pending reward.
3. `multiclaimOnBehalf` claims ~0 of token `X` for the attacker into `ManualCompound`.
4. The sweep logic at [4](#0-3)  (or the compoundable-token loop at lines 139-160) reads `IERC20(X).balanceOf(address(this))`, which includes the pre-existing dust, and transfers/converts/locks the entire balance to the attacker.
