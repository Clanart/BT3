### Title
Reverse pointer registry key collision via truncated CW bech32 address in `PointerReverseRegistryKey` lookup — ([File: x/evm/keeper/pointer.go])

### Summary
The `x/evm` pointer/pointee reverse registry stores *all* CW⇄EVM pointer directions in a single shared keyspace (`PointerReverseRegistryPrefix`), keyed only by a 20-byte `common.Address`. For the `CW20/CW721/CW1155 -> ERC20/ERC721/ERC1155` direction, that key is derived not from an actual EVM address but from `common.BytesToAddress([]byte(cwBech32Address))`, which truncates the bech32 string to its last 20 bytes. Two different CosmWasm contract addresses whose string tails collide in those 20 bytes produce the *same* reverse-registry key, exactly analogous to `vti6_tnl_lookup()` matching unrelated tunnels that hash to the same bucket without validating that the candidate is actually the wildcard/exact match intended.

### Finding Description
`SetCW20ERC20PointerWithVersion`, `SetCW721ERC721PointerWithVersion`, and `SetCW1155ERC1155PointerWithVersion` write the reverse registry entry with: [1](#0-0) 

The lookup/gating helpers `cwAddressIsPointer` and `GetERC20Pointee`/`GetERC721Pointee`/`GetERC1155Pointee` derive the exact same collision-prone key from a CW bech32 string with no verification that the resolved entry actually corresponds to the queried address: [2](#0-1) [3](#0-2) 

`common.BytesToAddress` (go-ethereum) truncates any input longer than 20 bytes to its *last* 20 bytes. A Cosmos bech32 contract address (e.g. `sei1...`, typically far more than 20 ASCII characters) is passed directly as `[]byte(addr)` — the same field used to key the reverse-registry entry that is also read back by `cwAddressIsPointer` at pointer-creation time (used to enforce "cannot create a pointer to a pointer", `ErrorPointerToPointerNotAllowed`) and by `GetERC20/721/1155Pointee` at query time. Because the reverse registry is shared across all pointer directions and keyed purely on this truncated 20-byte tail, an attacker who deploys or instantiates (an attacker fully controls CW20/CW721/CW1155 instantiation, including salt/label, i.e. it's a normal user-reachable action) a CosmWasm contract whose bech32 address happens to share the same last-20-byte tail as an already-registered pointer's reverse key will:
- silently overwrite/alias the existing reverse-registry entry (last write wins, since `setPointerInfo` just does a `store.Set`), corrupting the pointee resolution for the pre-existing, legitimate pointer, and/or
- cause `cwAddressIsPointer` to falsely report `true`/`false` for the attacker's or the victim's contract, bypassing or triggering the anti "pointer-to-pointer" check `ErrorPointerToPointerNotAllowed`.

This mirrors the CVE root cause precisely: a fallback/derived lookup key is shared across semantically distinct classes of registry entries in one hash-keyed store, and the code never validates that the entry actually corresponds to the exact address/type being queried before trusting it — just as vti6_tnl_lookup() never verified wildcard-candidate tunnels actually matched before using them.

### Impact Explanation
The reverse registry is consulted by user-facing precompiles (`AddCW20Pointer`/`AddNativePointer` in `precompiles/pointer`) and by the `Pointee` gRPC/query surface exposed to public RPC clients: [4](#0-3) 
An attacker controlling the timing/address of CW20/CW721/CW1155 instantiation can corrupt the CW↔ERC pointer identity mapping that CosmWasm contracts and EVM clients rely on to resolve "which ERC20 pointer belongs to token X". Silent corruption of this bridge mapping — the pointee/pointer identity used to route CW20/721/1155 token interoperability — can result in an ERC pointer being mis-associated with the wrong CW contract, and RPC/precompile consumers acting on the wrong mapping. This qualifies as a fund-relevant integrity issue in the pointer bridge because holders and integrators (DEXes, wallets) rely on `Pointee`/`AddCW20Pointer` return values to route transfers to the correct pointer contract.

### Likelihood Explanation
Exploitability requires an attacker to find/grind a CW20/CW721/CW1155 contract address whose ASCII bytes' last-20-byte tail collides with a target reverse-registry key. Because contract addresses on Sei/CosmWasm are derived deterministically from the instantiating account, code ID, and a salt the instantiator fully controls, an attacker can brute-force many salts (cheap, off-chain grinding, no protocol restriction) until a colliding tail is found, then instantiate that contract and register it as a CW20/CW721/CW1155 pointer target through the standard, permissionless `AddCW20Pointer`/`RegisterPointer` path. This is entirely reachable by an unprivileged CosmWasm/EVM user, requiring no validator or node compromise — but it does require non-trivial grinding effort per collision, and the collision is bounded to the truncated-key namespace rather than being deterministic/instant, so likelihood is moderate rather than trivial.

### Recommendation
- Do not derive `PointerReverseRegistryKey` from a truncated hash/byte-slice of a CW bech32 address; instead use the full CW address bytes (or a full-length hash of it) as the key, and namespace reverse-registry keys by pointer direction/type so entries for different pointer classes cannot collide.
- After any reverse-registry lookup (`GetAnyPointerInfo`), always re-derive and compare the candidate's canonical address/string against the value stored, rejecting mismatches — mirroring the upstream fix's explicit wildcard/exact re-validation.
- Add regression tests that instantiate two CW20 contracts with addresses colliding in their last 20 bytes and assert the reverse registry does not conflate them.

### Proof of Concept
1. Attacker computes, off-chain, two candidate CW20 instantiation salts `S1`, `S2` such that the resulting bech32 contract addresses `cwA`, `cwB` satisfy `common.BytesToAddress([]byte(cwA)) == common.BytesToAddress([]byte(cwB))` (last 20 ASCII bytes match).
2. Victim (or attacker) instantiates CW20 contract at `cwA` and registers it via the `pointer` precompile `addCW20Pointer(cwA)`, which calls `SetERC20CW20Pointer(ctx, cwA, erc20A)`, writing `PointerReverseRegistryKey(erc20A) -> cwA` and, more importantly for the collision, any code path using `common.BytesToAddress([]byte(cwA))` (e.g. the `cwAddressIsPointer` check applied to `cwA`) now shares a bucket with `cwB`.
3. Attacker instantiates `cwB` and calls `addCW20Pointer(cwB)`. Because `cwAddressIsPointer(cwB)` reads the same collided key as `cwA`'s entry from a `CW20->ERC20` pointer registration elsewhere, the anti-"pointer-to-pointer" check can be spuriously triggered/bypassed, or a subsequent `SetCW20ERC20Pointer`/`SetERC20CW20Pointer` call for `cwB` overwrites the reverse-registry slot previously used for `cwA`.
4. Querying `Pointee(PointerType_ERC20, cwA)` or `Pointee(PointerType_ERC20, cwB)` via gRPC now returns incorrect/aliased pointer information, demonstrating the corrupted mapping is externally observable and exploitable to redirect CW⇄ERC pointer identity resolution.

Note: I was not able to fully verify, within available tooling, whether any additional downstream consumer (e.g., a bank-transfer or mint/burn authorization path) trusts `GetERC20Pointee`/`cwAddressIsPointer` results for fund-moving decisions beyond pointer registration and the `Pointee` query API; if such a path exists it would elevate this from a data-integrity/DoS issue to direct fund-loss, but the `codebase_search` results returned only the pointer registration/precompile and query-layer call sites shown above.
