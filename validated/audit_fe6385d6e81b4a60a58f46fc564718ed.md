### Title
Unvalidated `ReceivedOutput` deserialization lets injected bytes claim unspendable/nonexistent outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The BunkerWeb bug class — improper input validation of attacker-controlled fields that are consumed by a downstream component — maps onto `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`. `read` deserializes a scalar `offset`, an arbitrary `TxOut` (script_pubkey + value), and an arbitrary `OutPoint` from an untrusted byte stream, performing zero validation that (a) the output's `script_pubkey` actually corresponds to `key + offset*G`, (b) the `outpoint` references a real on-chain output, or (c) the claimed `value` matches the actual UTXO. The resulting object is then consumed as "funds received" by `SignableTransaction::new` (balance/fee accounting at lines 175-176) and by the signing machine.

### Finding Description
`ReceivedOutput` is the wallet's representation of a spendable input: an `offset` (scalar such that the spending key is `key + offset*G`), an `output` (`TxOut` carrying `value` and `script_pubkey`), and an `outpoint` (`txid:vout`) [1](#0-0) . `ReceivedOutput::read` accepts all three fields verbatim from a `Read` source with only encoding-level checks — canonical scalar, decodable `TxOut`, decodable `OutPoint` [2](#0-1) .

The only consistency check in the entire flow lives inside `SignableTransaction::multisig`, which verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` [3](#0-2) . Critically, this check binds the `TxOut`'s script to the *claimed* offset — it never binds the `TxOut`/`value`/`outpoint` to the actual blockchain. The attacker knows all registered offsets in the honest deployment (`hash_to_F(KEY_DST, b"branch"|"change"|"forward")` and zero), so they can compute the exact `script_pubkey` that `multisig` will accept for any offset they choose. By supplying `offset = BRANCH_OFFSET`, a `TxOut` with the matching P2TR script and an arbitrary `value`, plus a fabricated `outpoint`, the attacker produces a `ReceivedOutput` that passes every check while referencing a UTXO that does not exist (or whose value is inflated).

`SignableTransaction::new` then treats `output.value` as real spendable balance for the funds-sufficiency test (`input_sat < payment_sat + needed_fee`) and commits those fabricated prevouts into the Taproot sighash via `Prevouts::All` [4](#0-3) [5](#0-4) .

### Impact Explanation
An unprivileged party who can cause attacker-crafted bytes to reach `ReceivedOutput::read` (the explicitly in-scope untrusted-bytes sink) can cause funds to be reported received that are not spendable: the instance credits a balance backed by a nonexistent or inflated UTXO. If downstream accounting releases value against that balance (a withdrawal/payment up to the fabricated amount passes `NotEnoughFunds`), the multisig signs a transaction spending real inputs plus the phantom input — or, when mixed with real inputs, produces a transaction whose total claimed inputs cover payments the real UTXOs cannot fund, burning honest inputs into signatures for a transaction that is either invalid (fabricated outpoint) or mispriced (wrong `value` in `Prevouts::All` produces sighashes that mismatch the chain and invalidate all inputs' signatures). This is an integrity violation on signing inputs plus a crediting-theft/DoS primitive, directly analogous to the CVE's improper neutralization of user input in a downstream component.

### Likelihood Explanation
Reachability is granted by the scope rules: `ReceivedOutput::read` consumes untrusted bytes. Exploitation requires no cryptographic break — only knowledge of public offsets (`hash_to_F` with the public `KEY_DST` and fixed labels) and the group key, both public. The only requirement is that fabricated bytes reach the deserialization path before an on-chain existence check that simply does not exist anywhere in this crate.

### Recommendation
At minimum, `ReceivedOutput` construction (both `read` and any future constructors) should validate `p2tr_script_buf(key + offset*G) == output.script_pubkey` — equivalently, store only `outpoint` + `offset` and fetch/verify the `TxOut` from chain. Ideally, mark scanner-produced outputs as authenticated and require the read path to re-verify the outpoint against the chain (or a trusted output store) before the value enters `input_sat`/`prevouts`, since `Prevouts::All` commits these attacker-influenced amounts directly into the signed message.

### Proof of Concept
```rust
// Attacker knows the multisig group key K (public) and the public
// BRANCH_OFFSET = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")
let offset = BRANCH_OFFSET;
let fake_script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset)).unwrap();

// Fabricated TxOut: correct script (passes `multisig`'s check), arbitrary value
let fake_output = TxOut {
    value: Amount::from_sat(100_000_000_000), // 1000 BTC never received
    script_pubkey: fake_script,
};
// Fabricated outpoint referencing a tx the attacker controls / a nonexistent txid
let fake_outpoint = OutPoint::new(attacker_txid, 0);

// Serialize as ReceivedOutput::read expects: F || consensus(TxOut) || consensus(OutPoint)
let mut bytes = offset.to_bytes().to_vec();
bytes.extend(serialize(&fake_output));
bytes.extend(serialize(&fake_outpoint));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// `forged` now carries offset/script that `multisig` accepts and a 1000-BTC value
// that `SignableTransaction::new` counts as spendable balance in `input_sat` and
// commits into Prevouts::All sighashes.
```

    let output;
    let outpoint;
