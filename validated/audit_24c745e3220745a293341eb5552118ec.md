### Title
Native ERC pointer contracts (CW20/CW721/CW1155/native-token pointers) are code-swapped in place with no storage-layout compatibility guard, risking storage corruption on pointer version upgrades - ([File: x/evm/keeper/pointer_upgrade.go])

### Summary
The Sei EVM "pointer" contracts (ERC20/ERC721/ERC1155 wrappers around native/CW20/CW721/CW1155 assets, generated from Solidity sources under `contracts/src/`) are upgraded not through a proxy pattern but by directly overwriting the deployed contract's bytecode at the same address via `k.SetCode`, while leaving the existing account storage untouched.

### Finding Description
When a pointer for a token already exists, `UpsertERCPointer` re-runs the constructor logic through `evm.GetDeploymentCode` and then persists the new bytecode in place with `k.SetCode(writeCtx, contractAddr, ret)`, keeping the contract address and all of its previously-written EVM storage slots (balances, allowances, approvals, owners, etc., inherited from OpenZeppelin's `ERC20`/`ERC721` base contracts) intact: [1](#0-0) 

This is functionally equivalent to an upgradeable-proxy pattern (same address, new logic, preserved storage) but with none of the safeguards a proxy pattern normally requires — specifically, no `__gap` reservation or any storage-layout compatibility check between the old and new pointer contract version. The pointer Solidity sources (e.g. `contracts/src/CW20ERC20Pointer.sol`) declare their own state variables directly on top of the inherited `ERC20` storage with no gap: [2](#0-1) 

If a future pointer version adds, removes, or reorders state variables (including inherited OpenZeppelin base-contract variables across OZ version bumps), the new bytecode's storage-slot assignments will not line up with the data already written by the previous version. Any slot whose meaning changes (e.g. a balance mapping's base slot shifting) will read/write to the wrong data when the new logic executes against the old storage.

This mirrors the reported bug class (`SolverVaults.sol` — no storage gap for upgradability) exactly: an upgradable contract lacking a reserved storage buffer, where inheriting/adding new variables can corrupt existing storage. Here the "upgrade" is chain-driven (any user's `MsgRegisterPointer` transaction triggers `RegisterPointer` in `x/evm/keeper/msg_server.go`, or a precompile call triggers `UpsertERCPointer`) rather than owner-controlled, but the storage-collision risk is the same class of issue, and it is triggered as part of normal user-invoked pointer creation/upgrade flow, not by any privileged/admin operation: [3](#0-2) 

### Impact Explanation
If a pointer-version bump changes storage layout without an explicit migration, every pre-existing pointer contract that gets code-swapped in place would have its balances/allowances/ownership records silently reinterpreted under the new layout. Because pointer contracts represent real user balances of the underlying CW20/CW721/CW1155/native assets (bridged value), a layout mismatch could cause funds to become unreadable, credited to the wrong holder, or duplicated — i.e., concrete fund loss or freezing for real token holders relying on the ERC pointer of their asset.

### Likelihood Explanation
This is not exploitable by an attacker directly forging arbitrary storage collisions today (current pointer source files across versions appear structurally similar), but the codebase has an explicit versioning/upgrade mechanism (`CurrentVersion`, `UpsertERCPointer`, `legacy/v552`, `v555`, `v562`, `v580`, `v600` pointer implementations) that is designed to evolve pointer contract logic over chain upgrades, and it relies purely on manual developer discipline to keep storage layouts compatible — there is no compiler-enforced or gap-based safety net. This makes storage corruption a real risk on any future pointer-version upgrade that adds/reorders fields, and the same lack-of-gap issue also exists in the underlying Solidity sources of the pointer contracts themselves, which extend `ERC20` and could be inherited/extended by future pointer implementations without any protective buffer.

### Recommendation
Add explicit storage-layout compatibility guarantees for any contract whose bytecode is swapped in place at a fixed address:
- Reserve `uint256[50] private __gap;` (or an equivalent namespaced-storage pattern, as already used by `ProxyERC20Storage`/`StrategyVaultStorage` in the test fixtures under `integration_test/load_generator/contracts/fixtures/`) in each pointer Solidity source under `contracts/src/` so future versions can add fields without shifting existing slots.
- Add an automated storage-layout diff check (e.g. via `solc --storage-layout` comparison) between pointer contract versions as part of the pointer-upgrade release process, failing CI if a slot's type/offset changes incompatibly.
- Document and enforce that any new field for pointer contracts must be appended after existing fields (or placed inside the reserved gap), never inserted before or between existing declarations.

### Proof of Concept
Not directly exploitable with current code (all present pointer-version sources are storage-compatible by inspection); the vulnerability is latent and would manifest the first time a pointer contract version adds/reorders a state variable and gets deployed via `UpsertERCPointer`'s `k.SetCode` path against existing pointer contract instances, causing the new bytecode to misinterpret already-stored balance/allowance data at the same contract address.

func (server msgServer) RegisterPointer(goCtx context.Context, msg *types.MsgRegisterPointer) (*types.MsgRegisterPointerResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	if server.GetRegisterPointerDisabled(ctx) {
		return nil, fmt.Errorf("registering CW->ERC pointers has been disabled")
	}
	var existingPointer sdk.AccAddress
	var existingVersion uint16
	var currentVersion uint16
	var exists bool
	switch msg.PointerType {
	case types.PointerType_ERC20:
		currentVersion = erc20.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW20ERC20Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC721:
		currentVersion = erc721.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW721ERC721Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC1155:
		currentVersion = erc1155.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW1155ERC1155Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	default:
		panic("unknown pointer type")
	}
	if exists && existingVersion >= currentVersion {
		return nil, fmt.Errorf("pointer %s already registered at version %d", existingPointer.String(), existingVersion)
	}
