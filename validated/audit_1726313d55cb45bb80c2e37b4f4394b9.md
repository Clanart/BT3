## Title
NFT royalty payments can be evaded via integer-division rounding to zero on low trade prices - (File: chia/wallet/nft_wallet/nft_wallet.py)

## Summary
Chia's NFT ownership-layer/royalty mechanism intends to pay the NFT creator a percentage-based royalty (`royalty_percentage`, basis points out of `MAX_ROYALTY_BASIS_POINTS = 10000`) whenever a royalty-enabled NFT changes hands through an offer. The royalty amount is computed with plain integer division (`amount // ... * percentage // MAX_ROYALTY_BASIS_POINTS`), which — exactly like the referenced Primitive Protocol bug — truncates to zero whenever the trade price times the percentage is smaller than 10000. This lets an offer counterparty settle a trade for a royalty-bearing NFT while paying zero royalty to the creator, even though the NFT's royalty percentage is nonzero.

## Finding Description
The royalty computation is performed in `compute_royalty_amount()`: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
royalty = uint64(amount)
```

The same rounding-to-zero pattern is used for royalty *summaries* in `royalty_calculation()`: [2](#0-1) 

Critically, the on-chain enforcement path in `NFTWallet.make_nft1_offer()` mirrors this same arithmetic when deciding which `trade_prices_list` entries to pass into the settlement puzzle/solution, explicitly filtering out any trade price whose computed royalty rounds to zero: [3](#0-2) 

```
trade_prices_list=[
    list(price)
    for price in trade_prices
    if price[0] * offered_royalty_percentages[asset] // MAX_ROYALTY_BASIS_POINTS != 0
],
```

This filter is a tacit acknowledgment that the underlying NFT ownership/transfer-program puzzle (curried with `royalty_percentage`, constructed via `puzzle_for_transfer_program()`/`NFT_TRANSFER_PROGRAM_DEFAULT`) itself computes `royalty = trade_price * percentage // 10000` in CLVM and only requires a `CREATE_COIN` to the royalty address for that computed value: [4](#0-3) 

Because the royalty requirement is a *derived* condition baked into the settlement solution rather than an independent, unconditional on-chain assertion, any spend-bundle submitter constructing the offer/acceptance directly (i.e., not going through the standard wallet's `make_nft1_offer` logic, or deliberately picking a low nominal trade price) can choose a `trade_price` for the fungible asset such that `trade_price * royalty_percentage // 10000 == 0`. In that case the puzzle enforces no royalty `CREATE_COIN` at all, and the settlement completes with the royalty-bearing NFT changing hands while the royalty recipient receives nothing — even though the NFT's royalty percentage is nonzero.

## Impact Explanation
The royalty recipient (NFT creator/curator) is the party economically harmed: they are entitled to a percentage of every settled trade of their royalty-enabled NFT, but a counterparty can structure the offer/acceptance trade price so the CLVM-computed royalty rounds to zero, silently bypassing the payment obligation the ownership-layer puzzle is designed to enforce. This is a direct value-extraction bug analogous to the referenced fee-evasion finding, reachable purely from a submitted offer/spend bundle without any privileged access.

## Likelihood Explanation
Likelihood is elevated for any pairing of low `royalty_percentage` and low fungible trade amounts (e.g., percentage under 100 basis points combined with trade prices/CAT amounts below a few hundred/thousand units), and increases further whenever tokens with fewer decimals are used as the fungible asset in the trade, similar to the USDC (6-decimal) scenario cited in the original report. A maker/taker pair colluding to route the "real" price off-chain while presenting a low nominal on-chain trade price can reliably drive the computed royalty to exactly zero.

## Recommendation
- Require that the ownership-layer/transfer-program puzzle reject settlements (or round up rather than truncate) when the computed royalty for a nonzero `royalty_percentage` would be zero for a nonzero trade price, so the intended fee is never silently skipped.
- On the wallet side, do not merely filter zero-royalty trade prices out of `trade_prices_list` (as done at `chia/wallet/nft_wallet/nft_wallet.py:1027-1032`); instead surface/reject trades where royalty rounds to zero, or enforce a minimum trade-price-to-percentage ratio.
- Clearly document and test the exact rounding semantics so integrators are aware low-value trades can bypass royalty payment, consistent with the recommendation in the referenced report.

## Proof of Concept
1. Create/curry an NFT ownership-layer puzzle with a nonzero `royalty_percentage`, e.g. `50` basis points (0.5%), using `create_ownership_layer_puzzle()` / `puzzle_for_transfer_program()`.
2. Construct (or accept) an offer/trade whose requested fungible amount (CAT or XCH) for that NFT is small enough that `trade_price * 50 // 10000 == 0` (e.g., any `trade_price < 200` mojos/CAT-units).
3. Settle the trade via a directly crafted spend bundle (bypassing `NFTWallet.make_nft1_offer`'s filtering) so the ownership-layer puzzle's computed royalty condition evaluates to `0`.
4. Observe the NFT transfers to the buyer while no `CREATE_COIN` is required/created to the royalty address — the royalty recipient receives nothing despite the NFT carrying a nonzero royalty percentage, reproducing the same integer-division fee-evasion class described in the referenced report.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
