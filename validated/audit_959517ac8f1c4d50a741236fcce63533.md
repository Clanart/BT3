## Analysis

The externally reported bug is a **TOCTOU (time-of-check-to-time-of-use) race**: the contract computes a price based on state read at call time, but that state can be mutated by another transaction before the computed action is finalized, letting an attacker profit from stale data. The broken invariant is: *"the value acted upon is guaranteed to be the same value that was inspected."*

GitHub Desktop has a structurally identical TOCTOU pattern in its **partial-commit staging pipeline**, where the diff a user reviews/selects lines from is not the diff actually used to build the patch applied to the index.

### Broken invariant located

`createCommit()` stages files, then for any file with a partial selection calls `applyPatchToIndex()`: [1](#0-0) 

`applyPatchToIndex()` re-fetches the diff **fresh from the working directory at commit time**, and then formats a patch by testing the user's previously-recorded line `selection` (a `DiffSelection` keyed by line index) against this newly fetched diff: [2](#0-1) [3](#0-2) 

Crucially, the `DiffSelection` bitmap the user interacted with in the UI was computed against a diff loaded earlier, in `updateChangesWorkingDirectoryDiff()`, which is only refreshed when file selection changes and is explicitly aware that "the diff might have changed dramatically since last we loaded it": [4](#0-3) 

That staleness-mitigation logic only re-maps *selectable* line indices when the Changes view re-renders — it is never re-validated against the diff actually consumed by `applyPatchToIndex` at commit time, because `_commitIncludedChanges` passes the `selection` straight through without re-diffing first: [5](#0-4) 

### Why this is a TOCTOU race, not a benign edge case

Between the moment a diff is rendered/selected (check) and the moment `applyPatchToIndex` regenerates the diff and blindly indexes into it by line number (use), the working tree content for that file can change out from under the app — e.g. via a repository-shipped Git hook (`post-checkout`, `post-merge`, `fsmonitor-watchman`) or a clean/smudge filter defined in `.gitattributes`/`.git/config` of a cloned/fetched repository, both of which Desktop executes automatically as part of routine operations: [6](#0-5) [7](#0-6) 

If such a hook/filter rewrites the file's content or line structure between the user's diff review and the async commit flow's `stageFiles` → `applyPatchToIndex` step, the numeric line indices in `file.selection` (computed against the old diff) get reinterpreted against the new hunk structure of the freshly-fetched diff. `DiffSelection.isSelected(absoluteIndex)` has no semantic knowledge of line content — it is a pure index lookup — so the resulting patch can silently include lines the user never reviewed/approved, or drop lines the user intended to commit, none of which is surfaced to the user before `git commit` executes.

### Title
Stale line-index reuse across re-diffed working directory allows silent corruption of partial commits - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` regenerates the working-directory diff for a file at commit time and reuses the `DiffSelection` line-index bitmap that was computed against a possibly-stale, earlier diff shown to the user. If the file's on-disk content changes between the UI diff render and the commit's staging step (e.g. due to a repository-controlled Git hook or clean/smudge filter), the index-based selection is silently reapplied to structurally different hunks, producing a commit whose content does not match what the user reviewed and approved.

### Finding Description
`createCommit()` → `stageFiles()` → `applyPatchToIndex()` fetches a brand-new diff via `getWorkingDirectoryDiff(repository, file)` [8](#0-7)  and builds the patch to apply with `formatPatch(file, diff)`, which walks the *new* diff's hunks and tests `file.selection.isSelected(absoluteIndex)` [9](#0-8) . The `file.selection` object, however, was populated by the UI against the diff loaded in `updateChangesWorkingDirectoryDiff()` when the user interacted with the Changes view [4](#0-3) . There is no check anywhere in `_commitIncludedChanges` that the diff underlying the current selection is still identical to the diff that will actually be staged [5](#0-4) . Desktop's own hooks/filters infrastructure (executed automatically for repo-provided hooks such as `post-checkout`/`post-merge`, or Git clean/smudge filters configured via a cloned repo's `.gitattributes`) can mutate the working tree asynchronously and outside of user interaction [6](#0-5) , creating the TOCTOU window.

### Impact Explanation
This matches "silent corruption of what the user commits or pushes": a user who intentionally excludes sensitive or incomplete lines from a partial commit can have unintended lines silently included (or approved lines silently dropped) without any warning dialog, because the commit path never re-validates the selection against the diff it actually uses to build the patch.

### Likelihood Explanation
Exploitation requires an attacker-controlled cloned/fetched repository that ships a hook or filter capable of asynchronously rewriting tracked files during normal Desktop operations (checkout, merge, fsmonitor triggers), combined with a user performing a partial/line-level commit shortly after such content mutation. This does not require local/physical access, admin rights, or prior host compromise — only that the user opens/uses a malicious repository, which is within Desktop's normal trust boundary of "attacker controls a cloned/fetched repository."

### Recommendation
Before calling `applyPatchToIndex`/`stageFiles` in `createCommit`, re-diff each partially-selected file and verify its content/hash matches what was used to compute `file.selection`; abort or re-prompt the user if a mismatch is detected instead of silently remapping indices onto a different diff.

### Proof of Concept
1. Attacker publishes a repository with a `post-checkout` (or `fsmonitor-watchman`) hook that appends/edits lines in a tracked file shortly after checkout.
2. Victim clones the repo in Desktop, edits the file, and in the Changes view selects only specific lines to commit (partial selection), leaving other lines unselected.
3. Before the victim clicks "Commit", the hook fires (or race window otherwise elapses) and shifts/changes the file's hunk structure.
4. Victim commits; `applyPatchToIndex` re-fetches the diff and reapplies the stale `file.selection` indices, producing a commit that includes content the victim never approved for that commit, with no warning shown.
