### Title
Deterministic cached FROST preprocess is reused across multiple `share`/`complete` invocations for the same context, enabling nonce reuse and validator key recovery if distinct `key_pair`/preprocess sets are ever signed under one DKG attempt — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives the FROST signing machine from a seed cached in the DB keyed only by `context` (`(b"DkgConfirmer", attempt)`). Every call to `share_internal` — reached by both `DkgConfirmer::share` and `DkgConfirmer::complete` — re-executes `machine.sign(preprocesses, msg)` with the *same* nonce seed. Nonce-reuse safety therefore rests entirely on the assumption that `(participants, serialized_preprocesses, msg)` are identical across every invocation for a given attempt. `msg` is derived from the attacker-influenced `key_pair` argument, and `preprocesses` from on-chain data; if two distinct `key_pair` values (or distinct preprocess sets) are ever presented under the same attempt — which the code's own safety comment admits is possible via "a logical flaw" or divergence of received messages — the same binomial nonce `d + ρ·e` signs two different challenges, allowing algebraic recovery of this validator's Ristretto secret key.

### Finding Description
- `Crypto/frost` documents that a `CachedPreprocess` "MUST only be used once. Reuse will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:83-92`).
- `preprocess_internal` loads/creates one seed per `context` and deterministically rebuilds nonces via `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:123-147`).
- `share_internal` calls `machine.sign(preprocesses, msg)` each time (`signing_protocol.rs:150-180`), and `DkgConfirmer::complete` invokes `share_internal` *again* to rebuild the machine (`signing_protocol.rs:321-326`), so `sign` is re-executed with the same nonces whenever `share`/`complete` are called more than once per attempt.
- The binding-factor transcript binds `group_key`, `hash_msg(msg)`, and the commitments (`crypto/frost/src/sign.rs:361-379`), so any change to `msg` (different `KeyPair`) or the peer preprocess set changes the challenge while the nonce stays fixed — the exact precondition for Schnorr/FROST nonce-reuse key extraction: `s1 − s2 = (c1 − c2)·λ·x_i`.
- The file's own header acknowledges the hazard: nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again", and lists a `TODO` to verify on-chain commitments match presumed nonces before publishing shares (`signing_protocol.rs:25-54`). Like the curl bug, data cached under one security context is re-trusted after additional inputs arrive, without re-establishing that the inputs are unchanged.

### Impact Explanation
If any path causes `share_internal` to run twice for one `(b"DkgConfirmer", attempt)` with different `key_pair` or preprocess maps, an observer of the two published 32-byte shares can solve for the coordinator validator's MuSig/Ristretto secret key. That key is the validator's root-of-trust key used to confirm DKG results on Substrate — recovering it enables forging set-keys confirmations in this and future contexts, a full validator-key compromise (High impact on key secrecy).

### Likelihood Explanation
Triggering requires the coordinator to `sign` twice with differing inputs under one attempt. Because Tributary ordering is BFT, honest execution yields identical inputs, making the exploit conditional — hence Medium rather than High likelihood. However, the defense relies on an *unimplemented* check (the on-chain-preprocess-matches-presumed-preprocess `TODO`), and `complete()` unconditionally re-executes `share_internal`, so any edge case producing a second distinct `key_pair` (e.g., competing generated key pairs within an attempt, or the acknowledged partial-rebuild/logical-flaw scenarios) silently reuses the nonce. An unprivileged party cannot force this alone, but they control the `key_pair`/preprocess bytes that are fed in, and need only wait for a divergence.

### Recommendation
Before producing or publishing a share, verify the preprocess derived from the cached seed equals the preprocess already committed/published on-chain for this context, and store the `(msg, preprocesses)` digest alongside `CachedPreprocesses`, refusing to sign if a subsequent call presents different values. Implement the noted TODO binding the share to the on-chain preprocess.

### Proof of Concept
1. For attempt `A`, `share(preprocesses_P, key_pair_1)` is executed: `preprocess_internal` loads seed `s`, producing fixed nonces; `share_internal` signs `msg_1 = set_keys_message(set, removed, key_pair_1)`, publishing share `σ_1 = nonce + c_1·λ·x`.
2. Later, `complete(preprocesses'_P, key_pair_2, shares)` (or a second `share` call under a divergent-but-accepted view) calls `share_internal` again; the same seed `s` regenerates the identical nonce, but `msg_2 ≠ msg_1` (or the preprocess set differs) yields `c_2 ≠ c_1` via `hash_msg`/`rho` binding (`crypto/frost/src/sign.rs:361-379`), publishing `σ_2 = nonce + c_2·λ·x`.
3. Compute `x = (σ_1 − σ_2) / ((c_1 − c_2)·λ)` using the public Lagrange coefficient `λ` — recovering the validator's secret key share in full.
