### Title
DID recovery attestation signature (`AGG_SIG_UNSAFE`) is not bound to the recovering DID's coin id, permitting cross-DID attestation replay - (File: chia/wallet/did_wallet/did_wallet_puzzles.py)

### Summary
`create_recovery_message_puzzle` builds the "attestment" that a backup DID uses to authorize recovery of a lost DID. The `AGG_SIG_UNSAFE` condition it emits signs only `newpuz` (the new owner puzzle hash) — it never includes the `recovering_coin_id` (the DID being recovered) inside the signed message, unlike every `AGG_SIG_*` opcode used elsewhere in the codebase which is domain-separated by coin id/parent/puzzle/amount via `pkm_pairs_for_conditions_dict` / `agg_sig_additional_data`. [1](#0-0)  This is structurally the same flaw as the reported Rigor `updateProjectHash` bug: the signed payload lacks a reference to the specific "container" (project address there, DID coin id here) it is meant to authorize, so a signature produced for one context can be replayed in another.

### Finding Description
`create_recovery_message_puzzle(recovering_coin_id, newpuz, pubkey)` returns a quoted program that emits two conditions when spent:
```
(CREATE_COIN_ANNOUNCEMENT recovering_coin_id)
(AGG_SIG_UNSAFE pubkey newpuz)
``` [1](#0-0) 

The `AGG_SIG_UNSAFE` message is only `newpuz`; `recovering_coin_id` is *not* part of the signed data. `AGG_SIG_UNSAFE` is, by design, not bound to any coin (unlike `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc., whose messages are extended with coin-specific suffixes by `pkm_pairs_for_conditions_dict` / `make_aggsig_final_message`). [2](#0-1)  Consensus only forbids `AGG_SIG_UNSAFE` messages that collide with the reserved `AGG_SIG_*_ADDITIONAL_DATA` suffixes; it does nothing to bind the message to a coin. [3](#0-2) 

Because the backup DID's signature over `newpuz` alone is a valid `AGG_SIG_UNSAFE` witness regardless of which coin/puzzle it is attached to, an attacker who observes a previously-broadcast attestation spend (signature + pubkey + message are all public once the transaction is confirmed or even just seen in the mempool) can construct a *new* `create_recovery_message_puzzle`/`create_spend_for_message` coin with a different `recovering_coin_id` but the same `pubkey`/`newpuz`, and reuse the *same* signature to satisfy that coin's `AGG_SIG_UNSAFE` condition. The `CREATE_COIN_ANNOUNCEMENT recovering_coin_id` is emitted from the *same* quoted puzzle at spend time and does not require any additional signature — it is not itself authenticated by the backup key, so it can be freely rewritten to target any `recovering_coin_id` the attacker chooses.

The requirement that ultimately gates this is only that the DID inner puzzle's recovery mode checks the backup pubkeys against its own `backup_ids` list (`did_wallet_puzzles.uncurry_innerpuz` / `create_innerpuz` curry backup_ids_hash). [4](#0-3)  If the same backup DID pubkey is listed as a recovery backup for two or more distinct DIDs (a supported and expected configuration — the same trusted third party/backup service is commonly reused across many DIDs), a signature the backup DID produced to legitimately attest recovery for DID A can be replayed to attest recovery for DID B, redirecting DID B's ownership to `newpuz` without the backup operator's consent for DID B, as long as the attacker also controls/chooses the same `newpuz` value (which is fully attacker-controlled, since it names the destination puzzle hash they want the DID's ownership transferred to).

### Impact Explanation
This breaks the DID recovery trust model: a backup/guardian's authorization, intended to be scoped to one specific DID coin needing recovery, is not cryptographically bound to that DID at the CLVM/consensus layer. An attacker who has ever observed one attestation signature from a shared backup key can forge a valid attestation for any other DID that lists the same backup key, redirecting that DID's ownership/control to a puzzle hash of the attacker's choosing. Since DIDs anchor profiles, NFT royalty/ownership, VC "authorized provider" identities, and CR-CAT approvals in this codebase, hijacking a DID this way constitutes unauthorized coin/asset-ownership transfer — a concrete impact matching the "unsigned or unauthorized coin movement" acceptance criterion.

### Likelihood Explanation
Exploitation requires: (1) a DID owner configured with `num_of_backup_ids_needed >= 1` recovery backups, (2) that at least one backup DID pubkey is shared/reused across the victim DID and another DID for which the attacker can obtain (or induce) a legitimate attestation spend, and (3) the attacker being able to choose/know the `newpuz` used in that other attestation (trivial, since `newpuz` is just an address the requester supplies to the backup). Reusing backup identities across multiple DIDs is a normal, supported usage pattern (a backup/guardian service naturally serves many DIDs), and any attestation spend broadcast to the mempool or chain is public, so signature/message extraction is straightforward. This makes the likelihood realistic in any deployment relying on shared backup DIDs, though it is not a "sign one message, drain everything" universal attack — it is gated by backup-list overlap.

### Recommendation
Bind the `AGG_SIG_UNSAFE` message in `create_recovery_message_puzzle` to the specific recovering coin (and ideally the specific DID's launcher id / current coin id), e.g. sign `sha256(recovering_coin_id || newpuz)` or switch to a coin-bound opcode such as `AGG_SIG_ME`/`AGG_SIG_PARENT` for the message coin so the signature cannot be lifted from one attestation and replayed against a different `recovering_coin_id`. This mirrors the general fix recommended for the Rigor finding: always include the "container" identity (project address there, DID coin id here) inside the signed payload.

### Proof of Concept
Conceptual replay (cannot be executed here, but derivable from the driver code):
1. Backup DID `B` (pubkey `P`) legitimately signs `sig = Sign(sk_B, newpuz)` to help recover DID `A` (coin id `id_A`), producing puzzle `create_recovery_message_puzzle(id_A, newpuz, P)` and spend `create_spend_for_message(parent, id_A, newpuz, P)`. [5](#0-4) 
2. This spend (and thus `sig`, `P`, `newpuz`) becomes public once pushed to mempool/chain.
3. Attacker identifies DID `V` (victim) that also lists pubkey `P` as a backup (a realistic scenario when a guardian/backup service is reused).
4. Attacker builds a new `create_recovery_message_puzzle(id_V, newpuz, P)` and spends a fresh coin with that puzzle using the *same* `sig` from step 1 — the `AGG_SIG_UNSAFE (P, newpuz)` check passes because it is identical to the previously verified pair, independent of `id_V`.
5. Attacker completes DID `V`'s recovery inner-puzzle spend (mode 0/recovery) using this forged attestation coin's announcement (`CREATE_COIN_ANNOUNCEMENT id_V`) plus enough other genuine/forged attestations to reach `num_of_backup_ids_needed`, redirecting DID `V`'s ownership to `newpuz`, which the attacker controls.

This part of the analysis (the exact recovery-mode CLVM solution format that consumes these attestation announcements) could not be fully traced to the underlying `DID_INNERPUZ` chialisp source in this session — the tool search for the recovery-mode solving code (`create_new_did_wallet_from_recovery`/`did_wallet.recovery_spend`) returned no results, so the precise gating logic (how many attestations combine and whether any other coin-binding exists in the recovery solution) is inferred from the puzzle-hash construction (`create_innerpuz` currying `backup_ids_hash`) rather than directly confirmed by reading the recovery-mode solve function. A Devin session with full repository access should verify the exact recovery-mode CLVM/solution code before treating this as fully confirmed.

def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)

def pkm_pairs_for_conditions_dict(
    conditions_dict: dict[ConditionOpcode, list[ConditionWithArgs]],
    coin: Coin,
    additional_data: bytes,
) -> list[tuple[G1Element, bytes]]:
    ret: list[tuple[G1Element, bytes]] = []

    data = agg_sig_additional_data(additional_data)

    for cwa in conditions_dict.get(ConditionOpcode.AGG_SIG_UNSAFE, []):
        validate_cwa(cwa)
        for disallowed in data.values():
            if cwa.vars[1].endswith(disallowed):
                raise ConsensusError(Err.INVALID_CONDITION)
        ret.append((G1Element.from_bytes(cwa.vars[0]), cwa.vars[1]))

    for opcode in [
        ConditionOpcode.AGG_SIG_PARENT,
        ConditionOpcode.AGG_SIG_PUZZLE,
        ConditionOpcode.AGG_SIG_AMOUNT,
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT,
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT,
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE,
        ConditionOpcode.AGG_SIG_ME,
    ]:
        for cwa in conditions_dict.get(opcode, []):
            validate_cwa(cwa)
            ret.append((G1Element.from_bytes(cwa.vars[0]), make_aggsig_final_message(opcode, cwa.vars[1], coin, data)))
```
