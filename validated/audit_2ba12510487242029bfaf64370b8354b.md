### Title
Server-Side Request Forgery via unsanitized DataLayer mirror/subscribe URLs enabling intranet port scanning - (File: chia/data_layer/download_data.py)

### Summary
Any wallet user can spend a small amount of XCH to create a "mirror" coin tagging an arbitrary, attacker-chosen URL to *any* DataLayer store id — including stores they do not own — via `DataLayerWallet.create_new_mirror()`/`dl_new_mirror` RPC. The `DataLayer` service's periodic sync loop (`fetch_and_validate`) reads these on-chain mirror URLs through `update_subscriptions_from_wallet()` and later issues unauthenticated outbound HTTP GET requests to them via `http_download()` in `chia/data_layer/download_data.py`, with no validation that the URL does not point to loopback/private/link-local addresses. This mirrors the CVE-2020-21122 SSRF bug class: a remote, unprivileged party can cause a victim node to make server-side HTTP requests to attacker-chosen internal network addresses and infer open intranet ports from response timing/errors.

### Finding Description
`create_new_mirror()` builds a standard coin spend whose memo encodes `[launcher_id, *urls]` with no check that `launcher_id` is owned by the caller: [1](#0-0) 

The RPC entry point `dl_new_mirror` / `DataLayerRpcApi.add_mirror` performs no URL validation beyond non-emptiness: [5](#0-4) 

Any DataLayer node that is running (owner or any node that has subscribed/tracks the launcher) periodically calls `update_subscriptions_from_wallet()`, which pulls these attacker-controlled mirror URLs straight from chain state and merges them into the local subscription server list with only trailing-slash stripping: [3](#0-2) 

`fetch_and_validate()` (invoked from the periodic `periodically_manage_data()` loop) then iterates these server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an unrestricted `aiohttp` GET to `server_info.url + "/" + filename`: [2](#0-1) 

There is no allowlist/denylist for scheme, hostname, or IP range (no rejection of `127.0.0.1`, `169.254.169.254`, RFC1918 ranges, etc.), and the existing tests explicitly exercise `http://127.0.0.1/...` URLs as valid mirror server URLs: [6](#0-5) 

Because outcomes differ observably (fast connection error/timeout for closed ports vs. HTTP status/response for open ports, logged and exposed via failure counters in `ServerInfo`/subscription state), an attacker can use this mechanism as an SSRF-based port scanner against the victim node's local network, exactly matching the referenced CVE's "detect intranet device ports" impact.

### Impact Explanation
This lets any unprivileged actor who can construct a spend bundle for their own DataLayer wallet (i.e., any wallet holder, not necessarily the store owner) force a victim's DataLayer daemon to make outbound HTTP requests to arbitrary attacker-chosen destinations, including internal-only services (localhost, cloud metadata endpoints, other daemon RPC ports on the LAN). This is a network-reconnaissance/SSRF primitive against the operator's own infrastructure — it does not directly cause fund loss, consensus divergence, or unauthorized coin movement, keeping severity at Medium, consistent with the CVSS 5.3 rating of the reference CVE.

### Likelihood Explanation
Likelihood is moderate-to-high for any operator running the DataLayer service with mirror-following/subscriptions enabled: creating a mirror coin only costs a small `amount`+`fee` transaction fee that any wallet holder can afford, and no authorization on the target `launcher_id` is enforced. The periodic sync loop (`periodically_manage_data`) runs continuously and automatically consumes chain-published mirror URLs without human review.

### Recommendation
- Validate mirror/subscription URLs before they are persisted or fetched: enforce `http(s)` scheme, resolve and reject loopback/link-local/private/multicast IP ranges (and re-check after redirects), and consider an explicit opt-in allowlist for mirror hosts.
- Rate-limit and randomize/delay retries so failure timing cannot be used to distinguish open vs closed ports.
- Consider requiring the store owner (or an explicit user opt-in per store id) before automatically following externally-published mirror URLs pulled via `update_subscriptions_from_wallet()`.

### Proof of Concept
1. Attacker wallet, with no relationship to `store_id` (any DataLayer launcher id, even one they don't own), calls `dl_new_mirror(DLNewMirror(launcher_id=store_id, amount=1, urls=["http://169.254.169.254/latest/meta-data/"], fee=...))`, per `chia/wallet/wallet_rpc_api.py:3255-3274`.
2. Once confirmed on-chain, any DataLayer node subscribed/tracking `store_id` runs its periodic loop; `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`) pulls the mirror URL from `dl_get_mirrors` and adds it as a subscription server.
3. `fetch_and_validate()` (`chia/data_layer/data_layer.py:642-694`) picks the malicious server URL and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298-323`), which issues `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` from the victim node.
4. By observing success/failure/timeout of subsequent mirror-fetch cycles (exposed indirectly through repeated `server_misses_file` failure counts / logs), attacker infers whether the target intranet host/port is reachable — reproducing the SSRF port-scanning behavior described in CVE-2020-21122.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
```
