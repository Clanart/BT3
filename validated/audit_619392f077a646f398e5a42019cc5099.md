### Title
Silent fund loss on escrow settlement via unchecked low-level `.transfer()` return value in Tron `IntentGatewayV2._withdraw`/`withdraw` and `onAccept` SweepDust - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway settles escrow (`withdraw()`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and the `SweepDust` branch) by making a raw low-level `.call` with the ABI-encoded `IERC20.transfer` selector and only checking that the **call did not revert**, never decoding/checking the returned boolean: [1](#0-0) 

This is the same bug class as the Cooler `claimDefaulted()` finding: a critical value-moving step (`MINTR.burnOhm`/`OHM.burnFrom` there, `IERC20.transfer` here) is invoked without the safety guarantee the codebase relies on elsewhere (there: an `approve` before `burnFrom`; here: `SafeERC20.safeTransfer`, which reverts on a `false` return). Both are cases of dropping a required safety wrapper around a token-moving call, but here the omission causes *silent settlement acceptance without actual fund movement* rather than a full revert.

### Finding Description
`withdraw()` first marks the order permanently settled:
`_filled[body.commitment] = beneficiary;` and decrements the internal escrow accounting `_orders[body.commitment][token] -= amount;` [2](#0-1) 

It then attempts the actual token payout with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted — it does **not** decode the returned `bool` from a standards-compliant ERC-20 `transfer` that returns `false` on failure instead of reverting (a well-known real-world token pattern, and TRC-20 tokens on Tron in particular are inconsistent about revert-vs-return-false semantics). If the token returns `false` (e.g., due to a paused/blacklisted state, an internal transfer restriction, or non-standard implementation), `success` is still `true`, the `if (!success)` check passes, and the function proceeds as if the beneficiary was paid — while `_filled` and `_orders` have already been mutated to mark the commitment as fully and irrevocably settled.

Contrast this with the identical logic in the shared/base contract `IntentsBase.sol`, which imports and applies `SafeERC20` (`using SafeERC20 for IERC20;`) throughout the shared codebase [3](#0-2) , and other IntentGateway paths use `IERC20(token).safeTransferFrom(...)` for equivalent transfers [4](#0-3) . The Tron file diverges from this convention by hand-rolling the low-level call and losing the `safeTransfer`/`safeTransferFrom` return-value check that the rest of the protocol relies on to guarantee "transfer either succeeds or reverts."

The same unchecked pattern also appears in the `SweepDust` `onAccept` branch of the same file: [5](#0-4) 

### Impact Exp lanation
This is a direct fund-loss / false-state-acceptance bug reachable through the normal, unprivileged settlement path (`RedeemEscrow`/`RefundEscrow` delivered via `onAccept`, or `SweepDust`):
- `_filled[commitment]` is set and `_orders[...][token]` is decremented **before/regardless of** whether the token transfer actually delivered funds.
- If the token silently fails (returns `false` without reverting), the commitment becomes permanently marked as settled (`Filled()` guard elsewhere prevents any retry), the escrow accounting is zeroed out, and `EscrowReleased`/`EscrowRefunded` is emitted — but the beneficiary (solver or user) never receives the tokens.
- The result is a one-time, unrecoverable loss of the escrowed input tokens: they remain stuck in the gateway contract with no accounting path pointing back to them, since `_orders` was already decremented and `_filled` already finalized. This is fund loss/lock, not just a DoS.
- No malicious relayer, prover, governance actor, or leaked key is required — the trigger is solely the ERC-20/TRC-20 token's own transfer semantics, which is outside attacker or Hyperbridge control and can occur under conditions the token operator controls (pause, blacklist, insufficient internal balance flags, etc. depending on token implementation).

### Likelihood Explanation
Likelihood depends on whether any token integrated with this Tron IntentGateway instance can return `false` from `transfer` instead of reverting. This is common among TRC-20/older ERC-20-style tokens (many do not follow the strict "revert on failure" convention), so for any deployment accepting third-party or blacklist/pausable tokens as escrow inputs, the condition is realistically triggerable without any privileged actor — e.g. an input token temporarily pausing transfers, or a blacklist hit on the beneficiary address, at the exact moment of settlement.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` and the `SweepDust` branch of `onAccept`) with `SafeERC20.safeTransfer` (the file already imports `SafeERC20` and declares `using SafeERC20 for IERC20;`), matching the convention used in `IntentsBase.sol` and the main EVM `IntentGatewayV2.sol`. This ensures a `false` return causes an actual revert, so `_filled`/`_orders` state mutations only persist alongside a token transfer that is either guaranteed to have succeeded or that has reverted the whole settlement (allowing retry rather than silent, permanent fund loss).

### Proof of Concept
1. Deploy a TRC-20/ERC-20-style token whose `transfer()` returns `false` (rather than reverting) when the recipient is blacklisted or the contract is paused — this is a standard, spec-legal token behavior, not a malicious modification.
2. Place a cross-chain order with this token as an input on the Tron `IntentGatewayV2`, and have a solver fill it on the destination chain, triggering a `RedeemEscrow` message back to the Tron source chain.
3. Before the `onAccept` settlement message arrives, pause the token or blacklist the solver's beneficiary address (an action fully within the token owner's/operator's normal, non-privileged-to-Hyperbridge control).
4. `onAccept` → `withdraw()` executes: `_filled[commitment] = beneficiary` and `_orders[commitment][token] -= amount` are committed, `token.call(...)` returns `success = true` (call didn't revert) but internally transferred `0`/failed, `EscrowReleased` is emitted.
5. The beneficiary's on-chain balance is unchanged, the escrowed tokens remain trapped in the gateway, and the commitment can never be retried (`Filled()` guard) — permanent loss of the escrowed funds, confirmed by comparing the beneficiary's token balance before/after step 4 against the emitted `EscrowReleased` event.
