## Analysis: Local analog found in IntentGatewayV2 cross-chain cancellation path

### Title
Excess native-token payment on cross-chain order cancellation is silently trapped in `EvmHost` — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The Dexter report's core invariant is: *entry points that accept a native-currency payment must validate or refund any amount beyond what the function actually needs, or callers permanently lose the surplus.* Hyperbridge's `IntentGatewayV2` implements exactly this protection in `placeOrder` and `_fillCrossChain` (both track `msgValue`, subtract what was actually consumed, and explicitly refund the remainder to `msg.sender`). The cross-chain cancellation paths, `_cancelFromSource` and `_cancelFromDest`, do not implement this same protection — they forward the caller's entire `msg.value` to `EvmHost.dispatch()` without ever computing or refunding unused native token.

### Finding Description
`_cancelFromSource` (an unprivileged, user-callable path reachable once `options.height > order.deadline`) and `_cancelFromDest` (callable by *anyone* once the deadline has passed) both do: [1](#0-0) [2](#0-1) 

Both simply do `if (msg.value > 0) IDispatcher(hostAddr).dispatch{value: msg.value}(request);` with no tracking of how much of `msg.value` is actually required and no refund step afterward, unlike every other value-forwarding function in the same contract (`_fillCrossChain` explicitly computes `msgValue -= options.nativeDispatchFee` and refunds the remainder): [3](#0-2) 

On the receiving side, `EvmHost.dispatch()` only swaps enough ETH to cover the exact fee via `swapETHForExactTokens`: [4](#0-3) 

`IUniswapV2Router02.swapETHForExactTokens` refunds any unused ETH to its caller — but that caller is `EvmHost` itself (since `EvmHost.dispatch` is the one invoking the router with `{value: msg.value}`), not the original user who called `cancelOrder`. `EvmHost` has no logic in `dispatch()` to forward that refunded ETH back to `_msgSender()`/`post.payer`. The surplus therefore accumulates permanently in the `EvmHost` contract's balance with no recorded owner and no withdrawal path tied to the overpaying caller.

### Impact Explanation
Any user (or a relayer acting on their behalf, since `_cancelFromDest` is callable by anyone post-deadline) who overestimates the relayer fee and sends excess native token when cancelling a cross-chain order permanently loses that excess — it becomes stuck in `EvmHost`. This is a direct "loss of funds" / fund-lock scenario matching the bounty's impact gate (funds moving to an unintended destination — the host contract — rather than back to the rightful payer), reachable by a normal unprivileged user through a legitimate, documented entry point (order cancellation), with no malicious relayer, prover, or admin required.

### Likelihood Explanation
Likelihood is realistic but not universal: it requires the caller to send `msg.value` that exceeds the actual native-token cost of the fee swap during cancellation — a natural user/integrator error, especially since the SDK/documentation elsewhere emphasizes exact quoting (`quoteOrderFees`) but the cancellation code path has no such safeguard or revert-on-excess check, unlike the sibling `placeOrder`/`_fillCrossChain` functions in the same codebase which the developers clearly designed with refund logic. The asymmetry between these functions increases the odds that this particular path was simply overlooked.

### Recommendation
- **Short term:** In `_cancelFromSource` and `_cancelFromDest`, mirror the pattern used in `_fillCrossChain`: track `msg.value`, only forward what `dispatch()` needs, and explicitly refund any residual native token back to `msg.sender` after the dispatch call.
- **Long term:** Add a generic refund-of-unused-`msg.value` guard at the `EvmHost.dispatch()` level (or require an explicit revert if `msg.value` exceeds what's needed), so that all current and future callers of `dispatch()` throughout the codebase are protected uniformly rather than relying on each caller re-implementing the refund logic correctly.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder`, escrowing input tokens.
2. Order expires without being filled on the destination chain.
3. User calls the public `cancelOrder` entry point (which routes to `_cancelFromSource` for a source-chain-initiated cancellation), supplying `order.destination` GET-request relayer fee via `options.relayerFee` and sending `msg.value` intentionally or mistakenly higher than what `swapETHForExactTokens` needs to cover `options.relayerFee` in fee-token terms (e.g., due to price volatility between quote and execution, or simple overpayment).
4. `_cancelFromSource` forwards the full `msg.value` to `IDispatcher(hostAddr).dispatch{value: msg.value}(request)`.
5. `EvmHost.dispatch()` performs `swapETHForExactTokens{value: msg.value}(post.fee, ...)`; the Uniswap router refunds the unspent ETH to `EvmHost` (its direct caller), not the user.
6. The user's escrow is eventually refunded via `RefundEscrow`, but the excess native token they sent for the cancellation-fee-dispatch never returns to them — it is now indistinguishable from and merged into `EvmHost`'s general balance, permanently unrecoverable by the original caller.
