### Title
Recursive clone disables Git's clone-protection safeguard, allowing a malicious repository to execute code during clone - (File: `app/src/lib/git/clone.ts`)

### Summary
The external report's broken invariant is: a state-modifying operation is performed on attacker-influenced input (pool initial price) with a known safety mechanism deliberately left unused, letting an unprivileged attacker corrupt the operation's outcome before the victim can react. The GitHub Desktop analog is `clone()` in `app/src/lib/git/clone.ts`, which explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while performing a `git clone --recursive` of an attacker-supplied `url`. `GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to enforce the fixes for the 2024 clone/submodule remote-code-execution class of vulnerabilities (symlinked/aliased `.git` directories and nested-repository hook smuggling during recursive clone). By forcing it to `'false'`, Desktop deliberately turns off the very protection meant to stop a maliciously crafted repository (or one of its submodules) from executing code as a side effect of `git clone --recursive`. [1](#0-0) 

### Finding Description
`clone()` builds the clone environment via `envForRemoteOperation(url)` merged with a hard override:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [2](#0-1) 

and then runs `git clone --recursive -- <url> <path>`: [3](#0-2) 

`url` here is fully attacker-controlled from the caller's perspective — it can be an arbitrary user-entered URL, an "Open in Desktop" deep-link URL (`x-github-client://...`, handled in `app/src/main-process/main.ts`), or a URL supplied via `openOrCloneRepository` in `app/src/ui/dispatcher/dispatcher.ts`. The remote repository (and, because `--recursive` is used, any nested submodule it points to) is therefore attacker-controlled content, analogous to the "pool" in the smart-contract report whose initial state an attacker sets before the legitimate party can react.

Git's clone/submodule protections (enforced through `GIT_CLONE_PROTECTION_ACTIVE`) exist specifically to reject clones where a nested repository directory is a symlink, or where a `.git`/hooks path resolves outside the expected tree, both of which can be abused to get an executable hook run automatically during recursive clone/submodule update. Desktop unconditionally disables this check for every clone it performs, meaning the one guard Git ships to stop this exact bug class is not in effect when Desktop clones anything, including a fully untrusted URL from a link or search result.

This mirrors the report's "missing initialize()" pattern exactly: a safety check that the underlying primitive supports (`initialize`/`GIT_CLONE_PROTECTION_ACTIVE`) is skipped by the wrapping application layer (`AlgebraFactory.createPool` / Desktop's `clone()`), leaving a window where attacker-supplied content sets the resulting state unchecked.

### Impact Explanation
If the disabled protection is what stands between a crafted repository and code execution during clone (which is its documented purpose upstream in Git), then cloning any attacker-supplied or attacker-influenced repository/URL through Desktop's clone flow reintroduces that RCE surface even on Git versions that ship the fix, because Desktop actively opts out of it via `GIT_CLONE_PROTECTION_ACTIVE=false`. This satisfies the "attacker controls a cloned/fetched repository ... and the result is code execution" impact bar in the report's Valid Impact criteria.

### Likelihood Explanation
Likelihood is high for exposure but the practical exploitability depends on the installed Git/dugite version's exact handling of `GIT_CLONE_PROTECTION_ACTIVE=false` (i.e., whether disabling it fully reverts to pre-fix behavior or only relaxes a subset of checks) — this codebase does not show what Git version dugite bundles, so I could not verify from the index alone whether a concrete PoC payload (crafted submodule with a malicious hook) succeeds end-to-end. Every clone path in the app (Clone dialog, CLI `--cli-clone`, protocol-handler `open-repository`/`clone-url` deep links) funnels through this single `clone()` function, so the disabled guard is universal and triggered by ordinary, unprivileged user actions (clicking a clone link or entering a URL) — no local access, admin rights, or prior compromise needed.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Determine why it was disabled (likely to avoid noisy warnings/failures on legitimate nested worktrees) and instead handle the specific legitimate case, keeping protection active by default. At minimum, gate the override behind a narrow, verified condition rather than unconditionally disabling it for every clone of arbitrary, untrusted URLs, and add a regression test asserting the environment variable is not set to `'false'` for standard clones of external URLs.

### Proof of Concept
Not able to construct a working end-to-end PoC from the indexed code alone, because verifying the exploit requires knowing the exact vendored Git/dugite version's behavior when `GIT_CLONE_PROTECTION_ACTIVE=false` and constructing a crafted submodule payload against it — this exceeds what the code index exposes. Conceptually: an attacker hosts/publishes a repository with a submodule entry crafted to alias its `.git` metadata (or hooks path) outside the expected submodule directory (the class of payload the upstream Git protection blocks); a victim clones that URL through Desktop's Clone dialog or an `x-github-client://` deep link; because `clone()` sets `GIT_CLONE_PROTECTION_ACTIVE=false` for the `git clone --recursive` invocation, Git's guard against this payload is inactive, potentially allowing hook execution during the clone/submodule-init step. ```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)
```
