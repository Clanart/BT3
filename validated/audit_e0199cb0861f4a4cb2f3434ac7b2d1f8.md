### Title
Malformed condition list items from the hand-rolled frontmatter parser silently produce always-false conditions, letting `Rule.from_dict`/`Condition.from_dict` turn a "block" rule into a permanent no-op - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter`'s hand-written YAML-like parser only accepts multi-line `conditions:` dict-item continuations when their indentation is strictly greater than 2 spaces; any continuation line indented at exactly 2 spaces (a very plausible style for both LLM-generated `/hookify` output and hand-authored repo rule files) is silently dropped instead of raising an error. `Condition.from_dict` then fills the missing keys with silent defaults (`field=''`, `pattern=''`), and `Rule.from_dict` treats the mere presence of a non-empty `conditions` list as sufficient to skip the more robust legacy `pattern:` fallback entirely. The resulting `Condition` with `field=''` always resolves to `field_value=None` in `RuleEngine._check_condition`, which is unconditionally `False`, so the whole AND-chain in `_rule_matches` never matches — a rule that looks like a valid, effective `block` rule in the markdown source silently never fires.

### Finding Description
The parse chain reachable on every hook invocation is `load_rules()` → `load_rule_file()` → `extract_frontmatter()` → `Rule.from_dict()` → `Condition.from_dict()` [1](#0-0) , and this runs fresh (no persistence of parsed rules) on every tool call via `glob.glob('.claude/hookify.*.local.md')` [2](#0-1) .

In `extract_frontmatter`, a list-item continuation is only merged into the current dict item when `indent > 2`: [3](#0-2) 
Any continuation line written with an indentation of ≤2 spaces (a plausible/common style, e.g. `- field: command` followed by `  operator: contains` at 2-space indent) fails all three branches of the parser loop and is silently discarded, rather than erroring — producing a truncated dict like `{'operator': 'contains'}` with the `field` key missing.

`Condition.from_dict` never validates required keys and defaults `field` and `pattern` to empty strings: [4](#0-3) 

`Rule.from_dict` treats presence of a non-empty `conditions` list as authoritative and skips the legacy `pattern` conversion entirely, even though the parsed conditions may be corrupted: [5](#0-4) 

Downstream, `RuleEngine._check_condition` returns `False` whenever the extracted field value is `None` (which is what happens when `condition.field == ''`, since no branch of `_extract_field` matches an empty field name): [6](#0-5) 
and `_rule_matches` requires **all** conditions to match: [7](#0-6) 

So a single malformed condition item (caused purely by an indentation quirk in the frontmatter) makes the entire rule permanently non-matching, while the visible markdown still reads as a legitimate, well-formed `action: block` rule. This is exactly the legacy-vs-explicit differential described: the same semantic rule expressed via the simple top-level `pattern:` field (parsed on a single line, robust) works correctly, while the "advanced" `conditions:` list form (recommended by the README/SKILL docs for multi-field rules, and generated by `/hookify` per `hookify.md`'s "Step 3: Generate Rule Files") [8](#0-7)  can be silently neutralized by a formatting detail an attacker fully controls when the rule file is repo-shipped or influenced via prompt injection during `/hookify` generation.

### Impact Explanation
This is a Security-control bypass that silently disables a blocking rule. A rule file committed to a repository (e.g., a "recommended security template" a victim copies into `.claude/hookify.*.local.md`) or generated by `/hookify` can be crafted (or accidentally produced) so that its `conditions:` list loses the `field` key on one entry. The rule continues to load without error (`load_rule_file` only logs a warning on `IOError`/parsing exceptions, not on this silent corruption) and appears in the loaded rule set as `enabled: true`, `action: block`, giving the victim false confidence that dangerous Bash commands, file edits, or Stop conditions are being enforced, when in fact `RuleEngine.evaluate_rules` will never place it in `blocking_rules` and the dangerous operation proceeds unblocked.

### Likelihood Explanation
No special privilege is required — only the ability to place a `.claude/hookify.*.local.md` file with a specific (but innocuous-looking) indentation style, either by shipping it in a repository that users adopt as a security guardrail, or by influencing `/hookify`'s generated frontmatter (which follows the exact list-item format shown in `hookify.md`/`SKILL.md`, using developer-typical 2-space indentation that this parser mishandles). The bug is deterministic and repeatable: every hook invocation re-parses the file from disk and reproduces the same silent drop.

### Recommendation
Replace the hand-rolled frontmatter parser with a real YAML parser (e.g. `yaml.safe_load`) to eliminate indentation-sensitivity bugs. Additionally, make `Condition.from_dict` and `Rule.from_dict` fail loudly (raise `ValueError`) when a condition dict is missing required keys (`field`, `pattern`) instead of silently defaulting to `''`, and make `load_rule_file` treat such validation errors as "reject the rule" rather than silently returning a partially-functional `Rule`. Also add a unit/invariant test asserting that a legacy `pattern:` rule and its equivalent `conditions:` rule produce identical match results for the same input corpus.

### Proof of Concept
Unit test to add to `plugins/hookify/core/` test suite:
```python
from hookify.core.config_loader import extract_frontmatter, Rule
from hookify.core.rule_engine import RuleEngine

frontmatter_md = """---
name: block-dangerous-rm
enabled: true
event: bash
action: block
conditions:
  - field: command
  operator: regex_match
  pattern: rm\\s+-rf
---

Blocked dangerous rm!
"""

fm, msg = extract_frontmatter(frontmatter_md)
rule = Rule.from_dict(fm, msg)

# Expectation if parser worked correctly: condition has field='command'
assert rule.conditions and rule.conditions[0].field == 'command', rule.conditions

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"}
})

# Expectation: dangerous command must be blocked
assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", result
```
Running this against current code shows `rule.conditions[0].field == ''` (not `'command'`) and `result == {}` — the `rm -rf /` command is **not** blocked despite the rule file explicitly declaring `action: block` for exactly that pattern, confirming the silent bypass.

def load_rule_file(file_path: str) -> Optional[Rule]:

    try:
        with open(file_path, 'r') as f:

            return None
