### Title
Unvalidated PR head `clone_url` from GitHub API is passed straight into `git remote add`/`fetch`, enabling argument/transport injection - (File: app/src/lib/stores/app-store.ts, app/src/lib/git/remote.ts)

### Summary
When a user opens a pull request from a fork (via the "Open in Desktop" deep link flow or the in-app PR checkout action), Desktop takes the `clone_url` and `ref` returned by the GitHub API for `pull_request.head.repo` and feeds them directly into `git remote add` and `git fetch` with no scheme/format validation, mirroring the seed report's core defect: an externally supplied value (there, lien `rate`/`duration`/`liquidationInitialAsk`; here, a remote URL) is trusted and acted on without any bound/allow-list check.

### Finding Description
`dispatcher.openPullRequestFromUrl` takes `pullRequest.head.repo.clone_url` straight from the API response and forwards it to `_checkoutPullRequest`: [1](#0-0) 

`AppStore._checkoutPullRequest` forwards `headCloneUrl` unchanged into `_findPullRequestBranch`: [2](#0-1) 

`_findPullRequestBranch` uses that value directly as a remote URL, calling `addRemote(repository, forkRemoteName, headCloneUrl)` and then fetching it, with no check that `headCloneUrl` is a well-formed `https://` or `ssh://`/`git@` URL: [3](#0-2) 

`addRemote` passes the URL to the `git` CLI unsanitized: [4](#0-3) 

The same unvalidated value is used elsewhere for the same purpose (cherry-pick from PR, direct PR checkout), so every call site inherits the missing bound: [5](#0-4) [6](#0-5) 

Git itself treats certain remote URL forms specially — most notably the `ext::<command>` transport helper (arbitrary command execution) and leading-dash URLs that can be interpreted as CLI options by `git remote add`/`git fetch`. Because Desktop never restricts `clone_url` to an allow-listed scheme (`https://`/`ssh://`/`git@`) before calling `addRemote`/`fetch`, none of the existing guards (the deep-link URL parser's regex checks in `parseAppURL`, or `remote-parsing.ts`'s `parseRemote`/`sanitizeCloneName`) apply to this code path at all — those only validate the top-level repo URL used for cloning, not the PR's `head.repo.clone_url` fetched afterward from the API.

### Impact Explanation
If an attacker can influence the value returned for `head.repo.clone_url` (e.g., a malicious/compromised GitHub Enterprise Server the user has signed into, or a man-in-the-middled API response to a self-hosted GHES instance without strict certificate pinning), Desktop will pass that value unfiltered to `git remote add` and `git fetch`. Depending on the git version's handling of `ext::` remote helpers or argument-injection-style URLs, this can result in arbitrary command execution on the user's machine — squarely within the "attacker controls a GitHub API object... result is code execution" valid-impact category.

### Likelihood Explanation
The path is reached automatically whenever a user opens or checks out a pull request from a fork (a very common Desktop workflow, including via the "Open in Desktop" browser deep link and the PR checkout/cherry-pick UI), and requires no unusual user action beyond opening a normal-looking PR. The main constraint is the requirement that the `clone_url` field itself be attacker-influenced, which is realistic mainly against custom GHES endpoints or a network position capable of tampering with the API response; on api.github.com the field is server-generated and not attacker-writable.

### Recommendation
Before calling `addRemote`/fetching, validate `headCloneUrl` (and any other API-sourced remote URL) against an explicit allow-list of protocols (`https://`, `http://`, `ssh://`, `git@host:`) and reject values containing `ext::`, leading `-`, or other characters that git could interpret as options or transport helpers — analogous to the bound/allow-list check the original report recommends for lien parameters.

### Proof of Concept
1. Point Desktop at a controlled/malicious GitHub Enterprise Server endpoint (or intercept the API response for a PR lookup).
2. Have the API return a pull request object whose `head.repo.clone_url` is `ext::sh -c "touch /tmp/pwned"` (or a URL beginning with `-`, e.g. `--upload-pack=touch /tmp/pwned;`).
3. From Desktop, trigger "Open in Desktop" for that PR, or select the PR's branch for checkout in the app.
4. `AppStore._findPullRequestBranch` calls `addRemote(repository, forkRemoteName, 'ext::sh -c "touch /tmp/pwned"')` and subsequently fetches it, causing git to execute the embedded command. [7](#0-6)

/** Add a new remote with the given URL. */
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
