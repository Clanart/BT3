## Finding: Reward-Sandwiching via Permissionless `harvest()` and Unrestricted `deposit()`/`withdraw()` in WombatStaking/MasterMagpie/BaseRewardPool

### Title
Attackers can sandwich the permissionless `WombatStaking.harvest()` call with instant `deposit()`/`withdraw()` in `MasterMagpie` to steal a disproportionate share of freshly-harvested WOM rewards - (File: `wombat/WombatStaking.sol`, `rewards/MasterMagpie.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`WombatStaking.harvest()` is a fully permissionless, unprivileged-callable function that pulls pending WOM rewards and immediately provisions them into a `BaseRewardPool`/`BaseRewardPoolV2` pro-rata over the pool's *current* `totalStaked()`. Because `MasterMagpie.deposit()`/`withdraw()` have no cooldown, lock-up, or time-weighting, any wallet can deposit a large stake, trigger `harvest()`, and withdraw immediately afterward, capturing an outsized share of rewards that were actually accrued to long-term stakers — the exact "distribute/harvest MEV" bug class described in the report, but reachable purely through ordinary user-facing entry points.

### Finding Description
`WombatStaking.harvest()` has no owner/manager restriction: [1](#0-0) 

It calls `_toMasterWomAndSendReward(_lpToken, 0, true)`, which is the same internal path invoked by `deposit()`/`depositLP()`/`withdraw()`: [2](#0-1) 

This routes newly harvested rewards into `queueNewRewards`/`_provisionReward`, which distributes rewards proportionally to `totalStaked()` **at the moment of the call**, with no streaming/vesting delay: [3](#0-2) 

Meanwhile, `MasterMagpie.deposit()` and `withdraw()` are unrestricted, callable by any wallet, and take effect immediately with no lock-up or minimum staking duration: [4](#0-3) 

The pool-helper wrappers (`WombatPoolHelper.deposit()`/`harvest()`/`withdraw()`) expose the same permissionless flow to end users, staking receipt tokens into `MasterMagpie` and calling `WombatStaking.harvest()` directly: [5](#0-4) 

Because `_toMasterWomAndSendReward` provisions rewards based on `totalStaked()` at call time and `BaseRewardPoolV2._earned` computes each user's share from their current balance times `rewardPerTokenStored` (no time-weighting or vesting), a staker who is present in `totalStaked()` only for the instant of the `harvest()` call captures a full pro-rata share of the entire batch of harvested rewards, even though other stakers accrued exposure over a much longer period.

### Impact Explanation
This is a direct theft of yield from legitimate long-term stakers: an attacker can inflate `totalStaked()` immediately before `harvest()` is called (by anyone, since `harvest()` is public) and withdraw immediately after, extracting a share of rewards proportional to their momentary stake rather than their time-weighted contribution. This dilutes/misappropriates unclaimed rewards belonging to real depositors — theft of unclaimed yield.

### Likelihood Explanation
`harvest()` on `WombatStaking`/`WombatPoolHelper` is callable by any address with no restriction beyond `whenNotPaused`/`_onlyActivePool`, and `MasterMagpie.deposit()`/`withdraw()` are similarly unrestricted with immediate effect. No admin, governance, or privileged role is required — an ordinary wallet (optionally combined with a flash-loaned amount of the underlying deposit/LP token) can execute the full stake → harvest → unstake sequence in a single transaction, or via transaction-ordering control when `harvest()` is triggered by any third party (e.g., as a side effect of another user's `deposit()`/`withdraw()`).

### Recommendation
- Make `WombatStaking.harvest()` (and the internal `_toMasterWomAndSendReward` reward-provisioning path) either restricted or throttled so it cannot be triggered to align with an attacker-controlled deposit/withdraw window.
- Introduce a minimum staking duration or time-weighted average balance for reward eligibility in `BaseRewardPoolV2`/`MasterMagpie` so momentary stakes cannot capture full-period rewards.
- Consider streaming newly harvested rewards over time rather than crediting them instantly to `rewardPerTokenStored` based on the current snapshot of `totalStaked()`.

### Proof of Concept
1. Attacker takes a flash loan of the pool's deposit token (or otherwise acquires a large amount).
2. Attacker calls `WombatPoolHelper.deposit()` → internally calls `MasterMagpie.depositFor()`, immediately increasing the attacker's staked balance with no lock-up: [6](#0-5) [7](#0-6) 
3. Attacker (or any other party) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest()` → `_toMasterWomAndSendReward` → `queueNewRewards`, crediting `rewardPerTokenStored` based on `totalStaked()` which now includes the attacker's inflated stake: [8](#0-7) [9](#0-8) 
4. Attacker calls `WombatPoolHelper.withdraw()` → `MasterMagpie.withdrawFor()` → `_harvestAndUnstake()` which claims rewards via `_harvestBaseRewarder` before fully exiting, and repays the flash loan: [10](#0-9) 

The net effect: the attacker receives a pro-rata share of the entire harvested reward batch for a stake held only momentarily, diluting the rewards owed to genuine long-term stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
