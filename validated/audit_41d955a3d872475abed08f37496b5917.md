### Title
`GeneratorPromotion::complete` panics on a malformed proof map, enabling remote DoS - (File: crypto/dkg/promote/src/lib.rs)

### Summary
CVE-2017-16942 is a divide-by-zero in `wav_w64_read_fmt_chunk()` triggered by crafted input bytes, causing a crash/DoS. The Serai analog is an unvalidated-map panic: `GeneratorPromotion::complete` indexes an attacker-influenced `HashMap` of promotion proofs with `.unwrap()`, so an unprivileged participant can crash the promoting node by omitting any required participant's proof while padding the map with a bogus entry.

### Finding Description
`GeneratorPromotion::complete` validates only that `proofs.len() == params.n() - 1` and that every key satisfies `u16::from(i) <= params.n()`: [1](#0-0) 

It never checks that the map's keys cover exactly `1 ..= n` minus `params.i()`. In particular, a `Participant` key equal to `params.i()` (the promoter's own index) is accepted by the loop, since the only bound checked is `i > n`. The completion loop then unconditionally unwraps every other index: [2](#0-1) 

If any `i` in `1 ..= params.n()` (other than `params.i()`) is absent from `proofs`, `proofs.get(&i).unwrap()` at line 146 panics. Because `proofs` is a `HashMap`, duplicate keys can't inflate the count, so the crash is triggered simply by substituting the promoter's own index — or any duplicate/out-of-set-but-in-range index — for a missing participant. The `GeneratorProof` values are attacker-controlled bytes parsed via `GeneratorProof::read`, so the entire input is reachable by an unprivileged peer participating in the promotion ceremony.

### Impact Explanation
A single malicious (or even merely buggy) participant aborts the generator promotion for the victim by crashing it mid-`complete`, denying availability of the key-promotion flow. Like the CVE, this is an availability-only failure reachable purely from crafted protocol input — no secret leakage, no invalid signature. Medium severity per the engagement rules (reachable panic on public input).

### Likelihood Explanation
Triggering requires only sending a `GeneratorProof` map keyed under `params.i()` (or omitting one participant while including a duplicate-effect entry such as the promoter's own index). The checks at lines 125–136 pass (correct count, all keys `<= n`), and the panic fires at line 146 deterministically whenever the missing index is reached in the `1 ..= n` iteration.

### Recommendation
Before the unwrap loop, verify the key set exactly: `proofs.keys().collect::<HashSet<_>>() == (1..=n).filter(|i| *i != params.i()).map(Participant)`. Reject with a new `PromotionError` variant (e.g., `InvalidParticipantSet`) rather than indexing with `.unwrap()`. Alternatively, replace `proofs.get(&i).unwrap()` with `.ok_or(PromotionError::MissingProof(i))?`.

### Proof of Concept
```rust
// In a t-of-n promotion, victim participant v calls complete with:
let mut proofs = HashMap::new();
// Attacker supplies n-1 entries whose keys include the victim's own index
// and omit some other participant j:
proofs.insert(victim_i, attacker_proof);       // key == params.i(), passes `i <= n` check
for k in 1..=n { if k != victim_i && k != j { proofs.insert(k, some_proof); } }
// proofs.len() == n - 1, all keys <= n -> validation passes
promotion.complete(&proofs); // panics at proofs.get(&j).unwrap()
```

Confidence note: the panic site and missing coverage check are directly verified in `crypto/dkg/promote/src/lib.rs`; I did not exhaustively audit `multiexp/src/batch.rs` unwraps or other unwrap sites, so additional panic-on-input paths may exist, but this one is sufficient and directly reachable from `GeneratorProof::read` bytes supplied by an untrusted participant.
