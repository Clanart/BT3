## Analysis

The seed bug's core broken invariant: a mapping/identity that is treated as write-once truth for a critical check (`isUserExist`/root-of-tree) is instead silently overwritten by a legitimate, unprivileged/administrative code path, corrupting downstream authorization decisions.

The closest local analog is in the IntentGatewayV2 cross-chain intent settlement logic. `_filled[commitment]` is the single on-chain record of "has this order already been finalized" — it's what `_cancelFromSource`'s Hyperbridge GET proof relies on (`onGetResponse` reverts with `Filled()` if the slot is non-empty) to decide whether escrow can be refunded. But the two destination-side functions that are supposed to *set* this record, `_fillCrossChain` and `_cancelFromDest`, never *check* it first before overwriting it. [1](#0-0) [2](#0-1) 

Both functions unconditionally do `_filled[commitment] = <address>` with no `if (_filled[commitment] != address(0)) revert Filled();` guard, even though the `Filled` error and the exact semantics for this check already exist elsewhere in the same contract family: [3](#0-2) [4](#0-3) 

The comment on `_cancelFromDest` explicitly documents the intended invariant ("Marks the order as filled (to prevent future fill attempts)") but the code that is supposed to enforce "prevent future fill attempts" is missing on the fill side — a solver can call `_fillCrossChain` on an order that a canceller already finalized via `_cancelFromDest` (or vice versa, post-deadline, since anyone may trigger cancellation after the deadline per lines 226-231), and each path independently dispatches its own settlement message (`RedeemEscrow` or `RefundEscrow`) to the source chain for the same `commitment`. [5](#0-4) 

### Title
Missing `_filled` finalization check lets an order be independently filled and cancelled, producing duplicate cross-chain settlement dispatches for one escrow — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_filled[commitment]` is IntentGatewayV2's sole record of order finalization, consulted by the cross-chain-cancel GET-proof path (`onGetResponse`) to gate refunds. However, the two functions that are supposed to set it — `_fillCrossChain` (solver fill) and `_cancelFromDest` (destination-side cancel) — never check its current value before overwriting it, unlike the seed report's `phenomanelTree`, where a role assumed fixed (`root == owner`) was silently changed by a separate legitimate action, corrupting later invariant checks (`isUserExist`).

### Finding Description
`_fillCrossChain` sets `_filled[commitment] = msg.sender` as its very first state change, with no prior read/guard on the existing value [1](#0-0) . `_cancelFromDest` similarly writes `_filled[commitment] = address(uint160(uint256(order.user)))` unconditionally, and its own doc comment states anyone may call it after the order deadline passes [6](#0-5) . Because neither function reads `_filled[commitment]` first, both can be invoked back-to-back (or in either order) for the same commitment near/after the order deadline: a solver fills the order (paying the beneficiary out-of-pocket and dispatching a `RedeemEscrow` request), and separately a canceller calls `_cancelFromDest` for the same commitment (overwriting the `_filled` record and dispatching a competing `RefundEscrow` request) — or vice versa. Both dispatches target the same escrow commitment and reach `_withdraw` on the source chain, which is the only place that actually gates double-payout, via `_orders[commitment][token] == 0 → revert UnknownOrder()` [7](#0-6) . This means the destination-chain accounting itself (the `_filled` mapping) can be corrupted/overwritten between a genuine fill and a genuine (or premature) cancellation, and two conflicting cross-chain settlement messages for a single commitment can be dispatched — exactly the "duplicate settlement" class the bounty targets, and precisely the same root cause pattern as the seed report: a value treated as fixed-once-set (`_filled`, analogous to `rootOfTree`) is mutated by a second, unrelated but reachable code path without validating the existing state first.

### Impact Explanation
This falls under "duplicate settlement" / "logic attack" categories from the bounty scope: the destination-side finalization record for an order can be overwritten after legitimate fill, and duplicate `RedeemEscrow`/`RefundEscrow` messages for the same commitment can be dispatched to the source chain. Even where the source-side `_orders` balance check prevents literal double payout by reverting the second `_withdraw`, the destination's own bookkeeping (`_filled`) is left in an inconsistent state (showing "cancelled to user" when a solver already paid out, or overwriting the solver-of-record), which can desynchronize the two chains' views of who was actually made whole for a given order and can cause `onAccept` to revert on the source chain for the message that loses the race — a state a solver who already paid the beneficiary directly out of pocket has no recourse against.

### Likelihood Explanation
No privileged actor, relayer, or prover compromise is required. `_fillCrossChain` is reachable by any solver who is willing to front the output tokens, and `_cancelFromDest`'s deadline-based "anyone may call" path is explicitly documented as open to any caller once `order.deadline` has passed [8](#0-7) . The two calls only need to land in either order around the order's deadline boundary, which is a normal, unprivileged interaction pattern rather than a contrived attack requiring a malicious peer or governance actor.

### Recommendation
Add an explicit `if (_filled[commitment] != address(0)) revert Filled();` guard at the top of both `_fillCrossChain` and `_cancelFromDest`, mirroring the check already performed in `onGetResponse`, so that a commitment can only be finalized (filled or cancelled) exactly once on the destination chain.

### Proof of Concept
1. User places a cross-chain order with a near-term `deadline`.
2. A solver calls `fillOrder` → `_fillCrossChain(order, options, commitment)`; this sets `_filled[commitment] = solver` and dispatches `RedeemEscrow` to the source chain [9](#0-8) .
3. Once `order.deadline` is reached, any address calls `cancelOrder` → `_cancelFromDest(order, options, commitment)`; since there is no check on the existing `_filled[commitment]` value, this succeeds, overwrites `_filled[commitment]` to `order.user`, and dispatches a competing `RefundEscrow` to the source chain for the same commitment [10](#0-9) .
4. Whichever message lands first at the source chain's `onAccept`/`_withdraw` succeeds and zeroes `_orders[commitment][token]`; the second reverts with `UnknownOrder` [7](#0-6) , leaving the destination's `_filled` record pointing to the loser of the race while the solver who already paid the beneficiary directly is left without reimbursement, and two conflicting settlement messages having been generated for one escrowed order.

Note: I was unable to retrieve `IntrinsicIntents.sol` (the file exposing the public `fillOrder`/`cancelOrder` entry points and `onPostRequestTimeout`) within available search iterations, so the exact revert/timeout handling path on the source chain after the losing message's `onAccept` reverts is not fully confirmed from local code — this is worth confirming in a full session before treating the finding as complete, though the missing `_filled` guard itself is directly visible and confirmed in `ExtrinsicIntents.sol`.

        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();

                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))

            )

            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,

            payer: msg.sender

    /**
     * @dev Initiates cancellation of a cross-chain order from the destination chain.
     *
     * If the order deadline has not yet passed, only the order creator may cancel.
     * After the deadline, anyone may trigger the cancellation (e.g., a relayer acting
     * on behalf of the user).
     *
     * Marks the order as filled (to prevent future fill attempts) and dispatches a
     * RefundEscrow message via Hyperbridge to the source chain to release the escrowed
     * tokens back to the original user.
     *
     * @param order The order to cancel.
     * @param options Cancel options including the relayer fee.
     * @param commitment The keccak256 hash of the ABI-encoded order.
     */
    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
