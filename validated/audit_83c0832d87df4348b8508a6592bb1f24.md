### Title
Attacker-controlled `WWW-Authenticate` realm spoofing tricks Desktop's credential helper into launching a GitHub/Enterprise sign-in flow against an untrusted host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Desktop's git credential helper trampoline decides whether a remote host is "GitHub-like" (and therefore should trigger Desktop's built-in GitHub/Enterprise sign-in and stored-account credential logic) partly by trusting the `WWW-Authenticate` realm string that the *remote server itself* returns during HTTP authentication. Because this string is fully attacker-controlled (any git HTTP remote can send `WWW-Authenticate: Basic realm="GitHub"` on a 401), a malicious/untrusted remote can force Desktop to classify itself as `'enterprise'` and pop the native "Sign in to GitHub Enterprise" dialog pointed at the attacker's own host, instead of a neutral generic-git-credential prompt.

### Finding Description
This mirrors the report's root cause pattern: a value that should only be derived from a trusted source is instead derived (even partially) from attacker-supplied, unvalidated input, and that misclassification is used to drive privileged behavior before any real verification happens.

In `getEndpointKind`, the classification order is:
1. `isGist`/`isDotCom`/`isGHE` — safe, hostname-based checks. [1](#0-0) 
2. **Unverified `wwwauth[]` realm sniffing** — if any captured `WWW-Authenticate` header value contains `realm="GitHub"`, the endpoint is immediately classified as `'enterprise'`: [2](#0-1) 
3. Only *after* that shortcut fails does the code fall back to an actual network check, `isGitHubHost(endpoint)`. [3](#0-2) 

The `wwwauth[...]` keys come straight from Git's credential protocol, which forwards any `WWW-Authenticate` response header value it receives from the remote server verbatim to the credential helper (`app/src/lib/git/credential.ts` `parseCredential`, `formatCredential`) [4](#0-3) . Nothing sanitizes or verifies this value against the actual identity of the host — it's just a string the attacker's HTTP server chose to send.

Once `getEndpointKind` returns `'enterprise'` for an arbitrary attacker-controlled `endpoint`, `getCredential` executes: [5](#0-4) 
Since no stored `Account` has `endpoint === apiEndpoint` for this random host, it calls `ui.promptForGitHubSignIn(endpoint)`, which for any non-`github.com` hostname calls `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with `origin` equal to the **attacker's own domain**: [6](#0-5) 

This is the corrupted value: `endpointKind` and, downstream, the sign-in `origin` used to build the GitHub Enterprise authentication flow, both derive from attacker-supplied header text rather than a verified GitHub identity check.

Existing guards do not stop this because:
- The hostname-based checks (`isDotCom`, `isGHE`, `isGist`) can't be spoofed, but they simply don't apply to an attacker's arbitrary domain, so the code moves on to the spoofable check.
- The one check that *would* validate the host, `isGitHubHost(endpoint)` (a real network probe), is only reached if the `wwwauth` shortcut fails — meaning the spoof pre-empts the legitimate verification entirely.
- No allow-list or certificate/identity pinning exists tying `realm="GitHub"` claims to Desktop's trusted `Account` list.

### Impact Explanation
A user who adds/clones/fetches from any HTTPS git remote (including generic/self-hosted Git servers, forks, or "clone via URL" deep-link targets) controlled by an attacker can be shown a native "Sign in to GitHub Enterprise" dialog whose target endpoint is the attacker's own server. If the user completes the resulting sign-in (basic auth or the enterprise OAuth flow) believing it's a legitimate GitHub prompt (Desktop labels this UI as GitHub sign-in, and the whole point of the `wwwauth` heuristic is to make this look official), their GitHub credentials/OAuth code/token can be sent to, or captured by, the attacker's endpoint. This satisfies "unauthorized OAuth or account binding" / credential exfiltration triggered purely by an attacker-controlled remote/proxy response, with no local access, malware, or leaked credentials required.

### Likelihood Explanation
Moderate-to-high. The only external precondition is that the attacker controls an HTTP git remote (trivial — any self-hosted or malicious "clone this repo" link works) and returns a crafted `WWW-Authenticate` header on a 401, which is a single line of server config, no exploitation of Git internals required. The user only needs to attempt to fetch/clone/push against the attacker's URL — an ordinary git operation Desktop performs automatically (e.g. via "Clone in Desktop" deep links, `x-github-client://openRepo/...`, or manually adding a generic remote) as seen in `app/src/lib/parse-app-url.ts`. No unusual/unnatural steps beyond normal use of the "Clone repository" / "Open in Desktop" flow are required.

### Recommendation
Do not let `wwwauth[]` realm content alone determine `'enterprise'` classification. Either:
- Drop the `wwwauth` heuristic entirely and always fall back to `isGitHubHost(endpoint)`'s network verification, or
- Treat a `wwwauth` "GitHub" realm hint only as a soft signal that additionally requires `isGitHubHost(endpoint)` (or equivalent identity confirmation) to pass before switching into the GitHub Enterprise sign-in UI, and otherwise fall through to the generic-git-authentication prompt (which does not imply GitHub trust) for unknown hosts.

### Proof of Concept
1. Stand up an HTTP git server on `https://attacker.example` that, on any authentication challenge for `git-upload-pack`/`git-receive-pack`, responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In Desktop, use "Clone repository" (or `x-github-client://openRepo/https://attacker.example/foo.git`) to clone/fetch this URL.
3. Git captures the `WWW-Authenticate` header and invokes Desktop's credential helper trampoline (`git/credential.ts` → `trampoline-credential-helper.ts`) with `wwwauth[0]=Basic realm="GitHub"`.
4. `getEndpointKind` matches the regex/`includes('realm="GitHub"')` branch and returns `'enterprise'` for `attacker.example`. [7](#0-6) 
5. `getCredential` finds no stored account for `attacker.example` and calls `promptForGitHubSignIn('https://attacker.example')`, which opens the "Sign in to GitHub Enterprise" dialog with `setSignInEndpoint('https://attacker.example')`. [8](#0-7) 
6. The user, seeing a Desktop-native GitHub-branded sign-in prompt, enters GitHub credentials or completes OAuth against the attacker-controlled endpoint, exfiltrating credentials/tokens.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

import { exec as git } from 'dugite'

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
