### Title
Silent origin-remote hijack via unvalidated GitHub API `clone_url` in `updateRemoteUrl` - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically rewrites a repository's local git remote URL whenever the associated GitHub repository's `clone_url` (fetched from the GitHub API) differs from the current remote. The function's safety checks only compare URL *protocol/scheme* and use `urlMatchesRemote` to detect whether the remote is unchanged from its last known value — it never re-validates that the *new* URL's hostname is the same trusted host as before. This is the same class of bug as the MarinateV2 `setScale` report: a derived/propagated value (`SCALE` there, the git remote URL here) is updated from an external input without re-checking the invariants that all downstream calculations/consumers depend on.

### Finding Description
`updateRemoteUrl` ( [1](#0-0) ) is invoked from `repositoryWithRefreshedGitHubRepository` every time Desktop refreshes GitHub metadata for the current repository (on app focus, account changes, repo selection, etc.): [2](#0-1) 

The decision to call `gitStore.setRemoteURL(...)` is gated by three conditions:
1. `protocolsMatch` — only compares `URL.parse(old).protocol === URL.parse(new).protocol` (e.g. `"https:" === "https:"`). It says nothing about hostname.
2. `remoteUrlUnchanged` — uses `urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)`, which checks the *current* remote against the *previously stored* clone URL (hostname-checked, but against the old, not the new, value).
3. `!urlsMatch` — `urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)` is false, i.e., the *new* URL differs from what's currently configured.

Crucially, nothing in this logic requires the **new** `apiRepo.clone_url` to share the same hostname as the repository's original/trusted host. `urlMatchesRemote` ( [3](#0-2) ) does perform a hostname check, but it is only ever applied to the *old* URL pairing, not to constrain what the *new* URL is allowed to be. As long as the scheme matches (e.g. both `https:`), an entirely different host in `apiRepo.clone_url` will satisfy all three conditions and Desktop will call `gitStore.setRemoteURL`, which shells out to `git remote set-url` with no further validation ( [4](#0-3) ).

This satisfies the "attacker controls ... a git remote/proxy response" primitive from the Valid Impact scope: any actor able to influence the `clone_url` field of the GitHub API response consumed here (a malicious/compromised GitHub Enterprise Server the user has added an account for, or a network-level MITM/proxy sitting in front of the API endpoint) can cause Desktop to silently repoint the user's `origin` remote to an attacker-controlled git host — without any user prompt, diff, or confirmation dialog, unlike the explicit remote-URL editing flow in Repository Settings ( [5](#0-4) ) where the user consciously edits and submits the URL.

### Impact Explanation
Once the remote is silently rewritten, every subsequent `fetch`/`pull`/`push` the user performs targets the attacker's server instead of their real GitHub repository:
- **Silent corruption of what the user pushes**: commits/pushes are sent to an attacker-controlled endpoint instead of the intended remote — directly matching the accepted impact category.
- **Potential credential exposure**: depending on the git credential helper configuration, an HTTPS push to the new host may trigger credential prompts/reuse that could leak tokens to the attacker's server.
- The user has no visual indication in the UI that their remote changed — the repository still shows the same GitHub association metadata; only `git remote -v` would reveal the swap.

### Likelihood Explanation
This path is reached automatically and repeatedly during normal Desktop usage (`repositoryWithRefreshedGitHubRepository` is called on repository refresh/account changes without user action), so exploitation only requires the attacker to control one refreshed API response for the repository in question. The explicit accepted attacker vectors (compromised GitHub Enterprise instance, malicious proxy/MITM on the API path) are exactly what the Valid Impact rules permit as in-scope. No local access, admin rights, or social engineering step beyond normal app usage is required. Likelihood is moderated by the need for control over the API response path itself, but no additional guard in the code (e.g., pinning the previously trusted hostname) exists to stop it once that precondition is met.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, explicitly validate that the parsed hostname of `updatedRemoteUrl` matches the parsed hostname of the *current* `gitStore.defaultRemote.url` (or the account's configured endpoint host). Reject/skip the automatic rewrite — and instead surface a confirmation prompt to the user — whenever the API-reported `clone_url` would change the remote's host, not just when the owner/name path changes. This closes the gap the same way the referenced fix closed the `SCALE` gap: by removing the ability to change a security-relevant derived value without re-validating everything that depends on it.

### Proof of Concept
1. Add a GitHub Enterprise account in Desktop pointing to `https://git.evil-corp.example` (attacker-controlled or MITM'd server), and clone a repository from it, e.g. `origin = https://git.evil-corp.example/acme/widgets.git`.
2. Attacker (controlling the server/proxy) responds to Desktop's `GET /repos/acme/widgets` API call with a full repository payload where `clone_url` is set to `https://attacker.example/acme/widgets.git` (same scheme, different host) while leaving other fields consistent with the previously cached `gitHubRepository.cloneURL`.
3. On the next periodic refresh (`repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`), `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true` (current remote still matches the old, previously-trusted `cloneURL`), and `urlsMatch` is `false` (new URL points to a different host) — all three conditions needed to trigger the rewrite are satisfied.
4. `gitStore.setRemoteURL('origin', 'https://attacker.example/acme/widgets.git')` executes, silently repointing `origin`.
5. The next `git push` performed by the user via Desktop sends commits to `attacker.example` instead of `git.evil-corp.example`.

Note: I could not fully trace credential-helper behavior for cross-host HTTPS pushes within this index (git credential manager config is largely outside the indexed source), so the credential-exfiltration sub-claim should be treated as a secondary, unconfirmed risk; the primary, confirmed impact is the silent remote-URL rewrite and resulting push/fetch redirection.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
