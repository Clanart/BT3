### Title
`SignableTransaction` will pay arbitrary, potentially unspendable `script_pubkey`s, permanently burning funds - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The analog of "collateral sent to a contract that does not support NFTs" in Serai's Bitcoin wallet is paying to a `script_pubkey` that cannot ever be spent. `SignableTransaction::new` accepts payment destinations as raw `ScriptBuf`s and only validates the payment **amount** (`>= DUST`). It never validates that the destination script is a standard, spendable output type. A payment to an unspendable script (e.g., an `OP_RETURN`-carrying output with a nonzero value, a provably-unspendable script, or a nonstandard/oversized script) produces a transaction the threshold group will sign, after which the funds are irretrievably burned — the exact "asset stuck forever" shape of the Teller finding.

### Finding Description
In `SignableTransaction::new`, payments are taken as `&[(ScriptBuf, u64)]` and converted verbatim into `TxOut`s:

- `send.rs:152` — `payments: &[(ScriptBuf, u64)]`
- `send.rs:165-169` — the only per-payment check is `*amount < DUST -> DustPayment`
- `send.rs:188-191` — `tx_outs.push(TxOut { value: Amount::from_sat(payment.1), script_pubkey: payment.0.clone() })` with no script validation

Contrast with the OP_RETURN `data` path, which explicitly forces `value: Amount::ZERO` (`send.rs:194-201`), showing the codebase knows an OP_RETURN output must not carry funds — yet a caller-supplied payment `ScriptBuf` that is `OP_RETURN`-prefixed (or otherwise unspendable/nonstandard) is allowed to carry an arbitrary nonzero amount.

Bitcoin consensus permits funding outputs with any script, but `OP_RETURN` outputs are provably unspendable and nonstandard scripts won't even relay. `TransactionMachine`/`TransactionSignMachine` (`send.rs:270-318`, `send.rs:401-428`) will then produce a validly signed transaction paying to that output. Once confirmed, no signature from the FROST group — or anyone — can ever spend it.

Reachability: payment destinations are ultimately derived from user-initiated withdrawal requests (payment `(address, amount)` pairs passed in by the caller, e.g., `processor`'s `make_signable_transaction` maps `payment.address` straight through to this constructor with no script-type filtering). An unprivileged requester who supplies a destination encoding an unspendable script causes the threshold wallet to sign a transaction sending real funds into a black hole — economically equivalent to withdrawing funds the protocol then loses.

### Impact Explanation
Funds paid to an unspendable `script_pubkey` are permanently locked; they cannot be recovered by the threshold key, by the recipient, or by anyone. This is direct loss of user funds, identical in effect to the NFT stuck in a non-supporting contract in the source report. Because the transaction is legitimately signed by the FROST group, it is final and consensus-valid — there is no recovery path.

### Likelihood Explanation
Requires the payment-destination pipeline (integrator/UI or request parsing) to allow an unspendable or nonstandard script through to `SignableTransaction::new`. The library provides the caller no assistance in detecting this: it accepts raw `ScriptBuf` rather than a typed `Address`, and there is no `is_op_return`/standardness/`is_unspendable` check anywhere in the constructor. Whether an external caller can reach it depends on upstream address parsing, but the wallet primitive itself — the last line of defense, analogous to `transferFrom` vs `safeTransferFrom` — performs no validation, so any upstream gap translates directly into burned funds.

### Recommendation
Validate payment scripts in `SignableTransaction::new` before constructing the transaction, and reject unspendable/nonstandard destinations, e.g.:

```rust
// In SignableTransaction::new, alongside the dust check
for (script, amount) in payments {
  if script.is_op_return() || *amount < DUST {
    Err(TransactionError::UnspendablePayment)?; // or reuse DustPayment/NoOutputs
  }
}
```

Stronger: accept a typed destination (e.g., `bitcoin::Address` restricted to standard output types — P2TR/P2WPKH/etc.) instead of an arbitrary `ScriptBuf`, so unspendable scripts are unrepresentable. This mirrors the report's recommendation of `safeTransferFrom`: push the "can this destination actually receive the asset" check into the primitive rather than relying on every caller to enforce it.

### Proof of Concept
```rust
// Attacker supplies a payment whose script is OP_RETURN-prefixed (unspendable).
let unspendable = ScriptBuf::new_op_return(
    PushBytesBuf::try_from(vec![0xde, 0xad]).unwrap(),
);
// Or any provably-unspendable / nonstandard script.

let payments = [(unspendable, 10_000u64)]; // >= DUST, so only check passes

// Succeeds: no script validation exists.
let tx = SignableTransaction::new(
    vec![input],           // a real ReceivedOutput controlled by the threshold key
    &payments,
    None,
    None,
    fee_per_vbyte,
).unwrap();

// The FROST group signs this normally.
let signed = sign(&keys, &tx);

// Once broadcast and confirmed, `tx.output[0]` pays 10_000 sats to an
// OP_RETURN output: provably unspendable, funds burned forever.
```
The constructor emits the same `TxOut` as a normal payment (`send.rs:188-191`), so there is nothing downstream — not `multisig` (which only checks the *inputs'* prevout scripts at `send.rs:277`), not the sign machine, not consensus — that prevents the burn. [1](#0-0) [2](#0-1) [3](#0-2)
