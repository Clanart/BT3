### Title
NFT bridge mints via unsafe `_mint` on cross-chain value transfer, permanently locking NFTs sent to non-ERC721Receiver contracts - ([File: contracts/service_chain/bridge/BridgeTransferERC721.sol])

### Summary
When a bridge operates in mint-burn mode, `handleERC721Transfer` mints the bridged NFT on the destination chain by calling `ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI)`, whose implementation uses the unsafe ERC721 `_mint` primitive rather than `_safeMint`. The destination address `_to` is fully attacker/user-controlled, being supplied by an unprivileged caller of the public `requestERC721Transfer` function on the source chain.

### Finding Description
`requestERC721Transfer` is a `public` function that any unprivileged EOA or contract can call, specifying an arbitrary `_to` recipient address for the destination chain: [1](#0-0) 

That `_to` value is propagated through the bridge relay/vote mechanism into `handleERC721Transfer`, which, in `modeMintBurn`, mints the NFT to `_to` via `mintWithTokenURI`: [2](#0-1) 

`mintWithTokenURI` calls the internal `_mint` function of `ERC721`: [3](#0-2) 

The underlying `_mint` implementation performs no `onERC721Received` callback or receiver-interface check, unlike `safeTransferFrom`/`_checkOnERC721Received`: [4](#0-3) [5](#0-4) 

Because `_to` originates entirely from the unprivileged requester's own transaction on the source chain (not validated to be an EOA or a compliant ERC721 receiver contract), a user can unintentionally (or a bridge relayer's automated flow could inadvertently) route an NFT to a smart-contract address on the destination chain that has no logic to manage/transfer ERC721 tokens (e.g., a plain multisig, vault, or any contract not implementing `IERC721Receiver`). Since `_mint` is used instead of `_safeMint`, the mint succeeds silently and the token becomes permanently stuck at that address.

### Impact Explanation
This is a genuine value-loss bug reachable by an ordinary bridge user: NFTs transferred cross-chain in mint-burn mode can be irrecoverably locked if the destination address is a contract lacking ERC721 receiver support. Because the source-chain NFT is burned as part of `_requestERC721Transfer` (`ERC721Burnable(_tokenAddress).burn(_tokenId)`), the asset is destroyed on the source chain and effectively unrecoverable on the destination chain, representing permanent supply/asset loss - a concrete unauthorized/irrecoverable value-movement outcome rather than a purely cosmetic issue.

### Likelihood Explanation
Likelihood is moderate: it requires the requester to specify (or be tricked/misconfigure into specifying) a `_to` address on the destination chain that is a non-receiver-compliant contract. This is plausible in practice for cross-chain bridging where recipient addresses across different chains/environments are commonly copy-pasted or programmatically derived without receiver-capability verification, and the bridge contract enforces no such check.

### Recommendation
Replace the unsafe internal `_mint` call path used by `mintWithTokenURI` with a safe-mint variant that performs the `onERC721Received` callback check (mirroring `_checkOnERC721Received` in `ERC721.sol`), or add an explicit `to.isContract()` + interface-support check in `handleERC721Transfer`/`ERC721MetadataMintable.mintWithTokenURI` before minting, so that mints to non-compliant contracts revert rather than permanently lock the NFT.

### Proof of Concept
1. Bridge is deployed in `modeMintBurn = true` for an ERC721 token.
2. Attacker (or any unprivileged user) calls `requestERC721Transfer(tokenAddress, badContract, tokenId, extraData)` where `badContract` is a deployed contract with no `onERC721Received` implementation (e.g., a simple non-payable multisig or vault contract).
3. `_requestERC721Transfer` burns the NFT on the source chain: `ERC721Burnable(_tokenAddress).burn(_tokenId)` — see `contracts/service_chain/bridge/BridgeTransferERC721.sol` lines 90-92.
4. Operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer` on the destination chain with `_to = badContract`.
5. `ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(badContract, _tokenId, _tokenURI)` succeeds (calls `_mint`, no receiver check), permanently minting the NFT to `badContract`, which has no means to transfer it out.
6. The NFT is now permanently locked in `badContract` and cannot be recovered.

    /**
     * @dev Internal function to mint a new token.
     * Reverts if the given token ID already exists.
     * @param to The address that will own the minted token
     * @param tokenId uint256 ID of the token to be minted
     */
    function _mint(address to, uint256 tokenId) internal {
        require(to != address(0), "ERC721: mint to the zero address");
        require(!_exists(tokenId), "ERC721: token already minted");

        _tokenOwner[tokenId] = to;
        _ownedTokensCount[to].increment();

        emit Transfer(address(0), to, tokenId);
    }

    function _checkOnERC721Received(address from, address to, uint256 tokenId, bytes memory _data)
        internal returns (bool)
    {
        if (!to.isContract()) {
            return true;
        }

        bytes4 retval = IERC721Receiver(to).onERC721Received(msg.sender, from, tokenId, _data);
        return (retval == _ERC721_RECEIVED);
    }
