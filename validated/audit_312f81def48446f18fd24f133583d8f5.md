## Analog Found

### Title
Path-containment check in `resolveWithin` uses an unanchored string prefix, allowing an "Open in Desktop" deep link to reveal files in a sibling directory outside the cloned repository - (File: `app/src/lib/path.ts`)

### Summary
The Curve report shows a guard (`_checkReentrancyContext`) that is supposed to confine an operation to a safe state but is implemented in a way that breaks for a specific, foreseeable input shape, defeating the protection it was meant to provide. GitHub Desktop's `resolveWithin` helper has the same class of flaw: it is the single security boundary used to keep externally‑supplied, potentially attacker‑influenced relative paths (from `x-github-client://openRepo/...?filepath=...` deep links, and from Copilot conflict‑resolution file paths) confined to the repository's working directory. Its final containment check is a plain string prefix test rather than a path‑boundary test, so a resolved path in a *sibling* directory that merely shares the repository directory name as a prefix passes the check.

### Finding Description
`_resolveWithin` in [1](#0-0)  computes:

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path separators. If the repository lives at `.../GitHub/Hello-World` and there is a sibling directory `.../GitHub/Hello-World-private`, then `'.../GitHub/Hello-World-private/secret.env'.startsWith('.../GitHub/Hello-World')` evaluates to `true`, even though the resolved file is not inside the repository at all. The existing unit tests only cover `..`/`../..` and symlink escapes [2](#0-1) ; none of them exercise the "sibling directory sharing a name prefix" case, so this gap is unguarded.

This function is the sole containment check used when handling the `filepath` parameter of the `open-repository-from-url` deep-link action, which is attacker-controlled input arriving via a link the user clicks:

```
if (filepath !== null) {
  if (isAbsolute(filepath)) { ... return }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } ...
}
``` [3](#0-2) 

`filepath` itself is only checked for being non-absolute in `parseAppURL`/`openRepositoryFromUrl`, with no `..`-segment filtering [4](#0-3) , so the entire traversal-safety burden rests on `resolveWithin`'s flawed prefix comparison.

`resolveWithin` is also relied on to bound where Copilot conflict-resolution content gets written to disk [5](#0-4)  and where conflict file contents are read from disk [6](#0-5) , so any bypass of this single guard has multiple downstream consequences.

### Impact Explanation
GitHub Desktop's default clone location places all repositories as siblings under one folder (e.g. `~/Documents/GitHub/<repo-name>`), and it is common for users to have adjacently-named repositories/directories (`Hello-World`, `Hello-World-private`, `Hello-World-old`, forks, etc.). An attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo-url>?filepath=../<sibling-dir>/<secret-file>` link (e.g. embedded in a webpage, README, or issue comment) can cause Desktop to reveal (via `shell.showItemInFolder`) a file located in a directory that is not the opened repository, because the path-containment check only compares string prefixes and not path segment boundaries. This is an attacker-controlled deep link resulting in disclosure of a file location outside the intended repository — matching the "link/deep link the user clicks ... result is ... read outside the repo" impact category. The same flawed primitive underlies the file-write path used for Copilot conflict resolutions, which could similarly write content to a sibling directory rather than the intended repository if a resolution path were crafted to exploit the same prefix collision.

### Likelihood Explanation
Exploitation requires only: (1) the victim has GitHub Desktop and at least one other directory whose name is a superstring of a repository name they've opened, and (2) the victim clicks an attacker-supplied `x-github-client://openRepo/...` link — both realistic scenarios given Desktop's protocol handler is globally registered and deep links are a designed, low-friction entry point. No local access, no admin rights, and no prior compromise are needed.

### Recommendation
Change the containment check in `_resolveWithin` to verify a real path boundary rather than a raw string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests covering sibling directories that share the root directory's name as a prefix (e.g. `repo` vs `repo-private`) for both POSIX and Windows path variants.

### Proof of Concept
1. Victim has two repositories cloned side by side:
   - `~/Documents/GitHub/Hello-World` (public, benign)
   - `~/Documents/GitHub/Hello-World-secrets` (contains a `.env` or credentials file)
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/octocat/Hello-World?filepath=..%2FHello-World-secrets%2F.env`
3. `parseAppURL` accepts `filepath=../Hello-World-secrets/.env` (not absolute, so it passes the only check) [4](#0-3) .
4. `openRepositoryFromUrl` opens `Hello-World` and calls `resolveWithin('.../Hello-World', '../Hello-World-secrets/.env')` [3](#0-2) .
5. Inside `_resolveWithin`, `realResolved` = `.../Hello-World-secrets/.env`, `realRoot` = `.../Hello-World`; `realResolved.startsWith(realRoot)` is `true` because `"Hello-World-secrets"` starts with `"Hello-World"` [7](#0-6) .
6. The check incorrectly passes, and `shell.showItemInFolder(resolved)` reveals `.env` from the unrelated `Hello-World-secrets` directory to the attacker's chosen link handler flow.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
