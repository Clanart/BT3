### Title
Operator Reimbursement Theft via SIGHASH_SINGLE|ANYONECANPAY Front-Running of Payout Transaction OP_RETURN - (`core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

---

### Summary

The payout transaction uses `SIGHASH_SINGLE|ANYONECANPAY` for the user's withdrawal signature. This sighash type commits only to the input being signed and the output at the same index (output 0, the user's payout output). It does **not** commit to the OP_RETURN output (output 2/3) that encodes the operator's xonly public key. An attacker who observes the operator's payout transaction in the mempool can extract the user's signature, construct a competing transaction with an identical user payout output but a different OP_RETURN (containing the attacker's own xonly pubkey or garbage), and broadcast it with a higher fee. If the attacker's transaction is mined, the verifier's `update_finalized_payouts` reads the tampered OP_RETURN and attributes the payout to the wrong operator (or to no operator). The legitimate operator's `PayoutCheckerTask` never finds an unhandled payout attributed to them, so they cannot initiate the kickoff/reimburse flow and permanently lose the `bridge_amount` BTC they fronted.

---

### Finding Description

**Payout transaction structure and sighash scope**

`create_payout_txhandler` builds the payout transaction with three outputs:

```
Output 0: user payout TxOut          ← covered by SIGHASH_SINGLE|ANYONECANPAY
Output 1: anchor output              ← NOT covered
Output 2: OP_RETURN(operator_xonly_pk) ← NOT covered
``` [1](#0-0) 

The user's signature is placed on input 0 with `set_p2tr_key_spend_witness`, and the sighash is computed using whatever `sighash_type` the user provides (expected to be `SinglePlusAnyoneCanPay`): [2](#0-1) 

The proto explicitly documents this sighash type: [3](#0-2) 

`SIGHASH_SINGLE|ANYONECANPAY` (BIP 341) commits to: the single input being signed, and the output at the same index as that input. It does **not** commit to any other output. Therefore the OP_RETURN at output index 2 (or 3 after `fund_raw_transaction` inserts a change output at position 1) is entirely outside the signature's scope.

**How the operator is identified from the payout transaction**

When a block is processed, `update_finalized_payouts` in `verifier.rs` reads the first OP_RETURN output of the confirmed payout transaction and parses the 32-byte operator xonly pubkey from it: [4](#0-3) 

This value is written to `withdrawals.payout_payer_operator_xonly_pk` in the database. If it is `NULL` or belongs to a different operator, the legitimate operator's `PayoutCheckerTask` will never find the row, because it queries: [5](#0-4) 

**Attack path**

1. User creates a withdrawal UTXO on Bitcoin and signs the payout transaction with `SIGHASH_SINGLE|ANYONECANPAY`, sending the signature to operator A via the `Withdraw` RPC.
2. Operator A calls `fund_raw_transaction` (adding their own inputs and change) and broadcasts the funded, signed payout transaction.
3. Attacker observes the transaction in the mempool, extracts the user's Schnorr signature from witness input 0.
4. Attacker constructs a new v3 transaction:
   - Input 0: same withdrawal UTXO, same user Schnorr signature (still valid — SIGHASH_SINGLE|ANYONECANPAY does not cover other outputs)
   - Input 1+: attacker's own funding UTXOs
   - Output 0: identical user payout TxOut (amount and script_pubkey unchanged)
   - Output 1: attacker's change
   - Output 2: anchor
   - Output 3: OP_RETURN containing attacker's xonly pubkey (or random bytes)
5. Attacker broadcasts with a higher fee rate. The user's signature remains valid because the signed portion (input 0, output 0) is unchanged.
6. Attacker's transaction is mined. `update_finalized_payouts` reads the tampered OP_RETURN and stores the attacker's xonly pubkey (or NULL) as `payout_payer_operator_xonly_pk`.
7. Operator A's `PayoutCheckerTask` queries for payouts attributed to operator A's xonly pubkey — finds none. Operator A cannot start the kickoff/reimburse flow. [6](#0-5) 

**Bridge circuit impact**

The bridge circuit also reads the OP_RETURN of the payout transaction to derive `operator_xonlypk` for the `deposit_constant`: [7](#0-6) 

If the OP_RETURN is tampered, the circuit would bind the wrong operator pubkey into the deposit constant, making it impossible for the legitimate operator to produce a valid proof for reimbursement even if they attempted to do so manually.

---

### Impact Explanation

The legitimate operator fronted `bridge_amount` BTC (the full bridge deposit value) to pay the user. After the attack:
- The user receives their BTC (output 0 is unchanged).
- The operator's payout is attributed to the attacker or to no one.
- The operator's `PayoutCheckerTask` never triggers the kickoff/reimburse sequence.
- The operator permanently loses `bridge_amount` BTC with no recovery path through the normal protocol flow.
- The bridge circuit cannot be used to prove the legitimate operator's payout because the on-chain OP_RETURN does not contain their pubkey.

This is a direct, permanent loss of bridged BTC from the operator's collateral/wallet — matching the "theft or permanent lock of bridged BTC or operator collateral" impact gate.

---

### Likelihood Explanation

- The attack requires only a Bitcoin node and the ability to pay a higher fee than the operator.
- The user's signature is publicly visible in the mempool the moment the operator broadcasts the payout transaction.
- No privileged access, no key compromise, and no cooperation from any bridge participant is required.
- The attack is profitable whenever `bridge_amount` minus the attacker's transaction fee exceeds zero (always true for any realistic bridge amount).
- The attacker does not need to be a registered operator; they only need BTC to fund the competing transaction.

---

### Recommendation

1. **Bind the OP_RETURN inside the user's signature.** Change the protocol so the user signs with `SIGHASH_ALL|ANYONECANPAY` over a transaction that already includes the operator's xonly pubkey in the OP_RETURN at a fixed output index. The operator's xonly pubkey must be communicated to the user before signing, and the operator cannot add a change output after the fact (use CPFP via the anchor output for fee bumping instead of RBF with additional inputs).

2. **Alternatively, derive operator identity from the funding inputs, not the OP_RETURN.** Record which operator funded the payout transaction by checking which operator's wallet address appears in the funding inputs (inputs 1+), rather than trusting the OP_RETURN. Since the operator signs their own inputs with `SIGHASH_ALL`, those inputs cannot be reused in a competing transaction.

3. **Short-term mitigation:** Use private mempool submission (e.g., out-of-band block template submission or a trusted miner) to prevent the signed payout transaction from being visible to attackers before confirmation.

### Proof of Concept

```
# Setup: operator A has fronted bridge_amount BTC for withdrawal_id=0
# User's SIGHASH_SINGLE|ANYONECANPAY signature: <user_sig>
# Withdrawal UTXO: <txid>:<vout>
# User payout output: value=bridge_amount-fee, script=<user_script>

# Step 1: Operator A broadcasts legitimate payout tx (visible in mempool)
# Tx structure:
#   vin[0]: <txid>:<vout>  witness=[<user_sig>]
#   vin[1]: <operator_A_utxo>  witness=[<operator_A_sig>]
#   vout[0]: value=bridge_amount-fee  script=<user_script>
#   vout[1]: value=change  script=<operator_A_change>
#   vout[2]: value=330sat  script=OP_RETURN <operator_A_xonly_pk>

# Step 2: Attacker extracts <user_sig> from vin[0].witness

# Step 3: Attacker constructs competing tx:
#   vin[0]: <txid>:<vout>  witness=[<user_sig>]   # same user sig, still valid
#   vin[1]: <attacker_utxo>  witness=[<attacker_sig>]
#   vout[0]: value=bridge_amount-fee  script=<user_script>  # identical output 0
#   vout[1]: value=change  script=<attacker_change>
#   vout[2]: value=330sat  script=OP_RETURN <attacker_xonly_pk>  # tampered

# Step 4: Attacker broadcasts with fee_rate > operator_A_fee_rate
# Bitcoin validates: user_sig covers (vin[0], vout[0]) only → VALID
# Attacker's tx mines first.

# Step 5: update_finalized_payouts reads OP_RETURN → attacker_xonly_pk
# DB: withdrawals.payout_payer_operator_xonly_pk = attacker_xonly_pk

# Step 6: Operator A's PayoutCheckerTask queries:
#   WHERE payout_payer_operator_xonly_pk = operator_A_xonly_pk → 0 rows
# Operator A cannot reimburse. bridge_amount BTC permanently lost.
```
