### Title
Attacker-controlled `allowFileProtocol` submodule init allows `file://` submodule URLs to read/write arbitrary paths outside the repository - ([File: app/src/lib/git/submodule.ts])

### Summary
The external report's core pattern is: a security check exists to stop untrusted, attacker-controlled content from reaching a sensitive operation, but the check can be bypassed because the attacker fully controls a value that flows into that operation without independent verification. In GitHub Desktop, the analogous pattern appears in submodule handling: `git`'s default `protocol.file.allow=user` restriction (meant to stop cloned/fetched repositories from using `.gitmodules` `file://` submodule URLs to read files or clone arbitrary local paths) is explicitly disabled by Desktop passing `-c protocol.file.allow=always` whenever the caller sets `allowFileProtocol = true`.

### Finding Description
`updateSubmodulesAfterOperation` in [1](#0-0)  builds its `git submodule update --init --recursive` invocation and conditionally prepends `-c protocol.file.allow=always` when `allowFileProtocol` is `true`. This is a direct override of Git's own hardening (`protocol.file.allow=user`) that was introduced upstream specifically to prevent a cloned repository's `.gitmodules` file from pointing a submodule URL at `file:///etc/passwd`, `file://C:/Users/victim/.ssh/id_rsa`, or another arbitrary local path, which `git submodule update` would then try to "clone" — either exfiltrating file contents into the working tree or writing into other local directories depending on git's clone behavior.

`checkoutBranch` and `checkoutCommit` in [2](#0-1)  and [3](#0-2)  both accept `allowFileProtocol` as a plain boolean parameter and forward it unconditionally into `updateSubmodulesAfterOperation`. The `.gitmodules` file and any submodule URLs it contains are themselves part of the tracked, attacker-controlled content of a cloned/fetched repository — exactly the "attacker controls a cloned/fetched repository" primitive called out as in-scope.

The broken invariant is: Git's own default file-protocol restriction is the last line of defense against malicious `file://` submodule URLs baked into `.gitmodules` by a hostile repository owner; Desktop unconditionally disables that defense whenever any caller passes `allowFileProtocol = true`, and that flag is threaded from UI-level checkout flows down into the git plumbing without any re-validation of the submodule URLs against the flag at the point of use.

### Impact Explanation
If a caller path allows `allowFileProtocol` to become `true` for a checkout of an untrusted, attacker-supplied branch/commit (e.g. checking out a branch from a fork or PR that a user did not author), `git submodule update --init --recursive -c protocol.file.allow=always` will honor `file://` URLs in `.gitmodules`. This can be used to have Git treat arbitrary local files/directories as clone sources, which can copy sensitive local file contents into the submodule's working tree (later visible/committable/pushable by the user) — matching the "silent corruption of what the user commits/pushes" and "file read outside the repo" impact categories. Severity is High if reachable from an untrusted checkout path, since it turns passive fetch/checkout of a hostile repo into local file disclosure.

### Likelihood Explanation
Likelihood is Medium: it requires confirming which UI-level call sites (in `app-store.ts` / `dispatcher.ts`) actually set `allowFileProtocol = true` and under what trust conditions (e.g. only after an explicit one-time user consent per repo, vs. automatically for any checkout). The index available here shows the plumbing (`checkout.ts`, `submodule.ts`) unconditionally forwards the flag, but does not show a runtime allow-list or path/URL validation that filters submodule URLs before the flag is applied — the check is entirely a boolean short-circuit at the git-invocation layer, not a validation of the actual submodule content.

### Recommendation
Do not rely on a caller-supplied boolean alone to gate `protocol.file.allow=always`. Before honoring `allowFileProtocol`, parse `.gitmodules` submodule URLs and reject/require extra confirmation for `file://` (and other local-path-like) URLs, or scope any allowed `file://` submodule sources to paths known to be inside the user's already-trusted repository set. At minimum, ensure `allowFileProtocol` can only become `true` after explicit, per-repository user consent tied to the exact repository being checked out, and audit all call sites in `app-store.ts`/`dispatcher.ts` to confirm none pass `true` for content originating from an untrusted/forked branch checkout without such consent.

### Proof of Concept
1. Attacker creates and publishes a repository containing a `.gitmodules` entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = file:///Users/victim/.ssh
   ```
2. Victim clones/fetches this repository in Desktop and checks out the malicious branch/commit through a code path that invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol = true` [4](#0-3) .
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, and Git treats the local `file://` path as a clone source into `leak/`, materializing the victim's local files inside the tracked working tree [5](#0-4) .
4. Those materialized files can now be staged, committed, and pushed by the user (or simply read from disk), demonstrating exfiltration/disclosure of local files outside the intended repository boundary.

**Uncertainty**: I could not fully trace, within the indexed portions of `app-store.ts` and `dispatcher.ts`, every call site that sets `allowFileProtocol = true` to confirm whether user consent is always required first or whether some path (e.g. automatic post-clone/post-pull submodule init) sets it unconditionally for untrusted content. Confirming this requires reading the full, non-truncated contents of those files, which are only partially covered by the code index — a full Devin session with repository access would be needed to verify the exact trust gating at each call site before treating this as a confirmed, exploitable vulnerability versus a defense-in-depth gap.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
