### Title
Merge/rebase-induced status reclassification silently resets a deliberately-excluded file's commit selection to "Include All" - (File: app/src/lib/git/status.ts, app/src/lib/stores/updates/changes-state.ts)

### Summary
GitHub Desktop tracks per-file commit inclusion (`DiffSelection`) keyed by a derived `FileChange.id` that encodes the file's *status kind* (`New`, `Modified`, `Renamed`, `Conflicted`, etc.), not just its path. When a fetch/merge/rebase against an attacker-controlled remote branch changes a locally dirty file's status kind for the same path (e.g. `Modified` → `Conflicted`, or `Modified` → `Renamed`/`New` via rename detection), the file's `id` changes. The selection-preservation logic that keeps track of files a user explicitly excluded from the next commit only matches by `id`, so it silently loses the user's previous exclusion and the file falls back to the hard-coded default of `DiffSelectionType.All`, i.e. "include in next commit." This mirrors the Backd `StakerVault` bug class: a derived/cached value (`strategiesTotalStaked`/`_poolTotalStaked` there, `DiffSelection` here) is not correctly carried over when the underlying "category" (strategy membership there, `AppFileStatusKind` here) changes for the same underlying entity.

### Finding Description
`FileChange.id` is computed as `${status.kind}+${path}` (plus `oldPath` for renames/copies): [1](#0-0) 

When `git status` is parsed, `buildStatusMap` builds a brand-new `WorkingDirectoryFileChange` for every status entry and assigns a selection based purely on the *current* status kind, defaulting to `DiffSelectionType.All` for essentially everything except the narrow "modified submodule without a committed change" case: [2](#0-1) 

The only place a previous, user-chosen selection (e.g. `None`/`Partial`, meaning "don't commit this") is carried forward across a refresh is `updateChangedFiles`, and it does so by looking the new file up in a map keyed by the *old* `id`: [3](#0-2) 

Because `id` embeds `status.kind`, any transition that changes the reported kind for the same path (e.g. `Modified` → `Conflicted` after a merge/rebase brings in conflicting upstream content, or `Modified`/`New` ⇄ `Renamed`/`Copied` as git's rename detection score shifts) makes `filesByID.get(file.id)` miss, discarding the previously-selected `DiffSelection` and falling back to the default computed in `buildStatusMap` (`DiffSelectionType.All`). There is no fallback lookup by `path` alone to recover a prior exclusion when only the *kind* changed.

This is structurally the same invariant violation as the Backd finding: a per-entity accounting/state value (`strategiesTotalStaked` vs `_poolTotalStaked`, keyed on "is this a strategy") is not migrated when the entity's category changes; here `DiffSelection` (keyed implicitly on status kind via `id`) is not migrated when a file's status kind changes, even though the file (by path) is the same entity the user already made a deliberate choice about.

### Impact Explanation
The corrupted value is `WorkingDirectoryFileChange.selection` (a `DiffSelection`), which directly controls whether a file's changes are staged into the next `git commit` created by Desktop's UI. If this resets from `None`/`Partial` to `All` without the user's knowledge, content the user explicitly chose to keep out of the next commit (e.g. leftover secrets, local-only debug edits, credentials in a config file) can be silently staged and then committed/pushed by the user's next "Commit" action, which they believe only includes the files they see checked. This falls squarely under "silent corruption of what the user commits or pushes" since it happens without any explicit re-selection by the user and without a clear on-screen warning tied to the cause (a status-kind flip caused by merge/rebase against untrusted content).

### Likelihood Explanation
The trigger condition — a fetched/merged branch causing a locally dirty file to become conflicted, or rename-detection scores shifting a file between `Modified`/`New` and `Renamed`/`Copied` for the same path — is a normal side effect of pulling or merging a branch, something GitHub Desktop performs automatically/semi-automatically when interacting with any remote, including one entirely controlled by an attacker (e.g., a malicious collaborator's branch or PR the victim fetches and merges/rebases in Desktop). No local/physical access, admin rights, or prior host compromise is required; the victim only needs to perform an ordinary fetch+merge/rebase of attacker-authored content while they have local, deliberately-excluded working directory edits. I was not able to fully verify, with certainty, exactly which git-status transitions in practice (e.g., specific rename-similarity thresholds, or the precise sequencing needed to produce a `Modified→Conflicted` transition for a purely unstaged edit) are reliably reproducible without additional git-level nuance (e.g., whether git will even allow the merge to proceed rather than aborting due to the dirty file). This uncertainty affects confidence in a fully weaponized, deterministic PoC, though the core code-level flaw — selection keyed by kind-inclusive `id` rather than stable `path`, with an "include by default" fallback — is clearly present and independently confirmed in the cited files.

### Recommendation
- Preserve `DiffSelection` by matching on the file's stable identity (`path`, and `oldPath` when applicable) rather than the full `FileChange.id`, so a status-kind change alone does not discard a previously chosen selection.
- Change the default fallback in `buildStatusMap`/`updateChangedFiles` for files whose kind changed but who were previously known: instead of defaulting to `DiffSelectionType.All`, default to the previous exclusion state (or explicitly re-prompt the user) when a file's status kind changes unexpectedly (e.g., due to a merge/rebase), especially transitioning into `Conflicted`.
- Surface a UI warning when a merge/rebase causes previously-excluded files to become newly "included" in the pending commit, so users can catch unintended inclusion before committing/pushing.

### Proof of Concept
Conceptual reproduction (exact git-level trigger needs verification in a live Desktop build):
1. Victim has a tracked file `secret.txt` with local, uncommitted edits; in Desktop they explicitly uncheck it (`DiffSelection` → `None`), intending to keep it out of the next commit.
2. Victim fetches and merges/rebases a branch from an attacker-controlled remote/collaborator that causes `secret.txt`'s git-status kind to change for the same path — e.g., the merge introduces conflicting changes to `secret.txt` (kind `Modified` → `Conflicted`), or rename-detection reclassifies it (kind `Modified`/`New` ⇄ `Renamed`/`Copied`).
3. On the next status refresh, `buildStatusMap` (app/src/lib/git/status.ts:297-349) creates a new `WorkingDirectoryFileChange` for `secret.txt` with a new `id` reflecting the new kind.
4. `updateChangedFiles` (app/src/lib/stores/updates/changes-state.ts:32-116) looks up the old selection via `filesByID.get(file.id)`; the lookup misses because `id` changed, so the file keeps the default `DiffSelectionType.All` assigned in step 3.
5. The victim, seeing other files still correctly excluded, proceeds to commit and push, unaware that `secret.txt`'s content is now included because its exclusion was silently dropped.
