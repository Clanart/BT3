### Title
`KeyMachine::calculate_share` returns a blame proof revealing the ECDH shared key before the message's proof-of-possession is verified, letting an attacker recover other participants' decryption keys - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The external report (CWE-209: sensitive information disclosed via an error response) maps onto Serai's PedPoP DKG: when an incoming encrypted secret share fails field deserialization, `calculate_share` returns `PedPoPError::InvalidShare` carrying an `EncryptionKeyProof` that publicly reveals the ECDH shared key — even though the sender's proof-of-possession on that message was only *queued* into a `BatchVerifier` and never verified, because the error short-circuits before `batch.verify_with_vartime_blame()` runs. An attacker who replays an honest participant's per-message key point obtains a decrypt-key oracle and can recover that participant's secret share to the victim.

### Finding Description
In `KeyMachine::calculate_share`, each share is processed in a loop: `Encryption::decrypt` (a) queues the message's Schnorr PoP into `batch` under `BatchId::Decryption(l)`, and (b) immediately performs ECDH decryption and returns an `EncryptionKeyProof` containing `key = ecdh(self.enc_key, msg.key)` together with a DLEq proof binding it to the recipient's long-term encryption key [1](#0-0) . Back in `calculate_share`, if the decrypted bytes fail `C::F::from_repr`, the function returns early with `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` — before reaching `batch.verify_with_vartime_blame()` on line 493, which is the only place the PoP is ever checked [2](#0-1) .

The PoP exists precisely to prevent this disclosure: the code comments state that without it, "Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob" [3](#0-2) . The early `?` return bypasses that protection: the blame proof is produced and returned for a message whose PoP was never verified. This error propagates to the coordinator, where the blame bytes are published on the tributary (`Transaction::InvalidDkgShare { share, blame }` → `VerifyBlame`) [4](#0-3) , making `proof.key` publicly readable via `EncryptionKeyProof::read`/`serialize` [5](#0-4) .

An attacker participating in (or able to inject into) a DKG round copies an honest sender Alice's `EncryptedMessage` `key`/`pop` fields (key point `K_A`) into their own share message to victim Bob, but supplies garbage ciphertext. Bob's `decrypt` computes `key = enc_key_Bob · K_A` — the same shared key that protects Alice's real share to Bob — wraps it in an `EncryptionKeyProof`, and since the garbage decrypts to a non-canonical scalar (~15/16 probability per attempt for a 32-byte field element), the early return leaks it. The attacker then decrypts Alice's share to Bob. The downstream `blame_internal` check does verify the PoP and correctly blames the attacker [6](#0-5) , but the key was already published in the error.

### Impact Explanation
The attacker recovers the ECDH shared key for an honest participant's encrypted share without knowing the discrete log. Since `cipher` derives the ChaCha20 key solely from `context || ecdh` [7](#0-6) , possessing `proof.key` fully decrypts Alice's secret share to Bob. Repeated across participants, an attacker can collect enough DKG shares to reconstruct or bias the threshold secret — i.e., key share recovery, an accepted impact class. More generally, Bob's error acts as a static-DH oracle revealing `enc_key_Bob · P` for attacker-chosen points `P`.

### Likelihood Explanation
Triggering requires only sending a malformed share message during a DKG round — an ordinary untrusted-input path, reachable by any participant or party able to feed `EncryptedMessage::read` output to `calculate_share`. Success per attempt is the probability the keystream-mangled plaintext is a non-canonical scalar, which is high (~15/16), and failed attempts still abort the protocol, giving retries across attempts.

### Recommendation
Verify the PoP before returning the blame proof — e.g., only attach `Some(blame)` to `InvalidShare` after the batch (or at least that participant's `BatchId::Decryption` statement) has been verified, or split decryption so the `EncryptionKeyProof` is constructed only on the verified-failure path in `batch.verify_with_vartime_blame`. Alternatively, check `msg.pop.verify` synchronously inside `decrypt` before computing/returning the ECDH proof.

### Proof of Concept
1. Observe Alice's share message to Bob: extract `(key = K_A, pop)` from her `EncryptedMessage`.
2. In a DKG attempt, send Bob a message with `key = K_A`, `pop` copied verbatim, and random `msg` bytes.
3. Bob's `decrypt` queues the (invalid, wrong-`from`) PoP, computes `key = ecdh(enc_key_Bob, K_A)`, applies the keystream to the garbage ciphertext.
4. With ~15/16 probability the result is a non-canonical scalar; `calculate_share` returns `InvalidShare { blame: Some(proof) }` before the batch ever runs — `proof.key` decrypts Alice's real share ciphertext to Bob.
5. Retry on subsequent DKG attempts if the plaintext happened to decode.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}

pub struct EncryptionKeyProof<C: Ciphersuite> {
  key: Zeroizing<C::G>,
  dleq: DLEqProof<C::G>,
}

impl<C: Ciphersuite> EncryptionKeyProof<C> {
  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<Self> {
    Ok(Self { key: Zeroizing::new(C::read_G(reader)?), dleq: DLEqProof::read(reader)? })
  }

  pub fn write<W: io::Write>(&self, writer: &mut W) -> io::Result<()> {
    writer.write_all(self.key.to_bytes().as_ref())?;
    self.dleq.write(writer)
  }

  pub fn serialize(&self) -> Vec<u8> {
    let mut buf = vec![];
    self.write(&mut buf).unwrap();
    buf
  }
