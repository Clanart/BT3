### Title
Payout OP_RETURN operator attribution is unsigned, allowing witness-replay to corrupt `payout_payer_operator_xonly_pk` and falsely mark an honest operator's kickoff as malicious - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout tx input with `SIGHASH_SINGLE|ANYONECANPAY`, which commits only to input 0 and output 0 (the user payout output), leaving the OP_RETURN output (containing `operator_xonly_pk`) completely unsigned. An unprivileged party who observes the mempool transaction can replay the exact witness in a new transaction with an attacker-chosen OP_RETURN value and get it mined via fee-bumping, corrupting the `payout_payer_operator_xonly_pk` recorded by `update_finalized_payouts`.

### Finding Description
The binding claimed to hold is: `operator_credited (payout_payer_operator_xonly_pk stored in DB) == operator_who_actually_funded_the_payout`.

`create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the payout transaction with the user's key-spend witness set via `set_p2tr_key_spend_witness(&user_sig, 0)`, where `user_sig.sighash_type` is required to be `SinglePlusAnyoneCanPay` (enforced in `Operator::withdraw`, core/src/operator.rs:630-637). Under BIP341 rules, `SIGHASH_SINGLE|ANYONECANPAY` commits only to the single signed input and the output at the same index (output 0, the user payout output) — it does **not** cover output 2, the OP_RETURN carrying `operator_xonly_pk.serialize()` (operator_reimburse.rs:418, 432).

Because ANYONECANPAY permits adding/removing other inputs and SIGHASH_SINGLE leaves all outputs beyond index 0 unconstrained, an attacker who observes the honest operator's broadcast/mempool payout transaction can copy the witness for input 0, keep output 0 byte-for-byte identical (required to satisfy the sighash), and construct a new transaction that adds their own fee-paying input and a completely different OP_RETURN value (any 32 bytes, not tied to any real operator key). If this attacker transaction is confirmed first (e.g., via higher fee/RBF), `update_finalized_payouts` (core/src/verifier.rs:2283-2353) parses the OP_RETURN from whichever transaction actually confirms and stores it via `update_payout_txs_and_payer_operator_xonly_pk` — the only validation performed is that the bytes parse as a valid `XOnlyPublicKey` format (verifier.rs:2319-2321); there is no check against `current_operator_xonly_pks` or any registered-operator list at storage time.

Downstream, `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1857-1915) and `Operator::send_asserts` (core/src/operator.rs:1275-1295) both compare the stored `payout_op_xonly_pk` against `kickoff_data.operator_xonly_pk` (the real operator's own key, taken from their own kickoff). Since the stored value is now the attacker's fabricated key, this comparison fails: `is_kickoff_malicious` returns `true` ("Operator xonly pk for the payout does not match with the kickoff_data"), and `send_asserts` returns an error refusing to proceed. This causes verifiers to treat the real, honest operator's legitimate kickoff as malicious/invalid even though they genuinely fronted the withdrawal — with no reconciliation path that re-derives or re-verifies the true funder.

None of the existing guards catch this: `SECP.verify_schnorr` only validates input 0/output 0 per the sighash it was given; `is_deposit_valid`/`verify_storage_proofs`/`SPV::verify` validate deposit and withdrawal existence, not OP_RETURN authenticity; there is no presigned-transaction constraint on this output since it is added at broadcast time by whichever party constructs the final transaction.

### Impact Explanation
The attacker does not steal bridge funds directly (the payout output itself is protected by the sighash), but they can corrupt the operator-attribution record for a real withdrawal, causing the actual operator who fronted the withdrawal to be marked malicious and denied reimbursement (`send_asserts` errors out; `is_kickoff_malicious` flags them for challenge). This matches the Critical category "an honest operator permanently unable to be reimbursed" (and potentially collateral loss if the flagged kickoff triggers a challenge/disprove cycle the operator cannot win, since they cannot produce a payout OP_RETURN matching the now-corrupted DB record). This is repeatable per withdrawal/payout transaction and does not require the attacker to hold any protocol role, key share, or collateral — only mempool visibility and fee-bumping capability.

### Likelihood Explanation
Preconditions: an honest operator must broadcast (or have in mempool) a payout transaction whose OP_RETURN attribution the attacker wants to corrupt, and the transaction's fee/replaceability must allow the attacker's competing version to confirm first. The attacker's cost is only the marginal fee needed to out-bid the original transaction, well within reach of any unprivileged party who can broadcast Bitcoin transactions and monitor the mempool. No key compromise, no majority hashrate, and no privileged access is required — this fits squarely within the stated attacker capabilities.

### Recommendation
Bind the OP_RETURN operator attribution into the signed sighash. Options: (1) commit to the operator's `xonly_pk` inside the SIGHASH_SINGLE-covered output (output 0) via a separate covenant/tapscript path rather than an unsigned OP_RETURN, or (2) require operators to sign the full payout transaction (including the OP_RETURN) with an additional operator-controlled signature/input using a sighash that covers all outputs (e.g., SIGHASH_ALL for at least one operator-owned input), so the OP_RETURN value cannot be altered without invalidating a signature the attacker cannot forge. Additionally, add a validation step in `update_finalized_payouts` that rejects/nulls any parsed `operator_xonly_pk` not present in `current_operator_xonly_pks`, and add a reconciliation mechanism so an operator can prove they funded a payout independent of the (currently spoofable) OP_RETURN.
