## Analysis

This maps onto a checks-effects-interactions gap in the same-chain intent settlement path of `IntentGatewayV2`, not to the paymaster (which is explicitly treasury-gated) or bandwidth pallet (no user-controlled external call mid-accounting).

### Title
Reentrant `cancelOrder` during `fillOrder`'s native-token payout enables double-settlement of escrowed input tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` pays the order's native-token output to `order.output.beneficiary` via a raw `.call{value:}` **before** the escrow balance for the order's *inputs* is decremented (decrement only happens later, inside `_withdraw`). `_fillSameChain` does set `_filled[commitment] = msg.sender` up front, which blocks a reentrant `fillOrder`, but `_cancelSameChain` performs **no check of `_filled[commitment]` at all** — it only checks `order.user == msg.sender` and reads the still-untouched `_orders[commitment][token]` balances directly. A user who places an order with themselves as a malicious beneficiary contract can therefore reenter `cancelOrder()` from the `receive()` hook fired by the solver's ETH payout, and pull the full input escrow a second time while the fill also completes.

### Finding Description
`_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`) sends the output token to `beneficiary` with a low-level call: [1](#0-0) 
This happens before `_withdraw()` is invoked at line 134, i.e. before the escrow mapping `_orders[commitment][token]` for the order's *inputs* is touched at all.

`_filled[commitment]` is set at the very top of the function: [2](#0-1) 
which is exactly the guard the repo's own `IntrinsicIntentsReentrancyTest.sol` proves blocks a reentrant `fillOrder` call.

However, `_cancelSameChain` (same file, lines 161-187) never consults `_filled[commitment]`: [3](#0-2) 
It only checks `order.user == msg.sender` and the source chain, then reads the live `_orders[commitment][token]` balances and calls `_withdraw(body, true, true)` to refund them to `order.user`.

Because the order creator can set `order.output.beneficiary` to a contract they control (the same address as `order.user`), the ETH `.call` in `_fillSameChain`'s output loop hands control to attacker code *before* the input escrow has been decremented and *before* `_cancelSameChain` has any way to know the order is mid-fill (no `_filled` check). The reentrant `cancelOrder()` call reads the still-full `_orders[commitment][token]` and withdraws it back to the attacker, while the outer `_fillSameChain` call subsequently still delivers the solver's payment and attempts its own `_withdraw()` against the same escrow.

### Impact Explanation
This is a double-settlement of the escrowed input tokens: the attacker (as `order.user`/beneficiary) receives the solver's output payment **and** reclaims the original input escrow via the reentrant cancel, at the solver's expense. This is a direct loss-of-funds / duplicate-settlement bug reachable by any unprivileged user placing a self-beneficiary order — it requires no malicious relayer, prover, or admin, matching the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories.

### Likelihood Explanation
High for same-chain ETH-output orders: the attacker fully controls order construction (self-beneficiary, self-user) and only needs a solver to fill it, which is the expected/incentivized flow for solvers. The existing `IntrinsicIntentsReentrancyTest.sol` shows the team already hardened `fillOrder` reentrancy via the `_filled` guard, but did not extend the same guard to `_cancelSameChain`, leaving this specific reentry vector open.

### Recommendation
Add a `_filled[commitment] == address(0)` (or equivalent "not currently filling/filled") check at the top of `_cancelSameChain`, mirroring the CEI fix already applied to `_fillSameChain`/`_fillCrossChain`, so a cancel cannot execute against an order whose fill is in progress or already completed.

### Proof of Concept
1. Attacker deploys a contract `Evil` with a `receive()` that calls `intentGateway.cancelOrder(order, commitment)`.
2. Attacker calls `placeOrder` with `order.user = Evil`, `order.output.beneficiary = Evil`, output asset = native ETH, escrowing input tokens (e.g. USDC).
3. A solver calls `fillOrder{value: ETH}(order, options)`.
4. Inside `_fillSameChain`, the ETH `.call{value: beneficiaryTotal}("")` to `Evil` triggers `receive()`, which calls `cancelOrder()` → `_cancelSameChain()`.
5. `_cancelSameChain` sees `_orders[commitment][usdc]` still fully populated (untouched by the outer call, which hasn't reached `_withdraw` yet) and refunds the full USDC escrow to `Evil`.
6. Execution returns to `_fillSameChain`, which proceeds to also call `_withdraw()` releasing (or attempting to release) the same escrow to the solver, and the order is marked filled — `Evil` has now received both the refunded input escrow and the solver-delivered ETH output.

Note: I could not fully trace `_withdraw`'s implementation in `IntentsBase.sol` (not retrieved in this session) to confirm the exact underflow/revert behavior on the second decrement; the core finding — that `_cancelSameChain` omits the `_filled` reentrancy guard present in the fill functions and reads escrow state before it is decremented — is confirmed directly from the cited source.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
