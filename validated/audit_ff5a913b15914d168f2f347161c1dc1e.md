Audit Report

## Title
Block-revenue-sharing commission (`UpdateCommissionBps`/`CommissionKind::BlockRevenue`) can be set to 100% immediately before reward distribution, unlike inflation-rewards commission which is epoch-delayed — allowing a last-minute "commission rug" against delegated stakers - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

## Summary
`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` imposes no timing restriction on `CommissionKind::BlockRevenue` updates, and `vote_processor.rs` gates this instruction only on feature flags, not on any epoch-position rule. [1](#0-0) [2](#0-1)  Meanwhile, `calculate_stake_rewards_and_commissions` feeds `calculate_block_reward` the live `cached_vote_accounts.distribution_epoch_vote_accounts` rather than an epoch-delayed snapshot, in contrast to the inflation-rewards path which explicitly reads from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` when `delay_commission_updates` is active specifically "to prevent last minute commission rugs." [3](#0-2) [4](#0-3) [5](#0-4) 

## Finding Description
The withdrawer authority of a vote account can call `update_commission_bps` with `CommissionKind::BlockRevenue` and no timing restriction, as confirmed by the comment "No commission update rule, per SIMD-0249 and SIMD-0291" in `programs/vote/src/vote_state/mod.rs`. [1](#0-0)  The dispatch site in `programs/vote/src/vote_processor.rs` enforces only feature-gate checks (`commission_rate_in_basis_points`, `delay_commission_updates`), not any epoch-position check. [2](#0-1)  This contrasts with the legacy `UpdateCommission` path, which is explicitly documented as imposing "a minimum delay of one full epoch before the new commission rate takes effect," specifically to prevent commission rugs. [6](#0-5) 

For inflation rewards, the commission used at reward-calculation time is read from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` (an epoch-old snapshot) when `delay_commission_updates` is set. [3](#0-2)  However, `calculate_block_reward` is invoked with `cached_vote_accounts.distribution_epoch_vote_accounts`, which per its own doc comment represents "Vote account state from the end of the rewarded epoch / beginning of the distribution epoch" — i.e., current/live state, not an epoch-delayed snapshot. [5](#0-4) [4](#0-3) 

I was unable to fully locate and inspect the body of `calculate_block_reward` itself within available search results (only its call site was found), so I could not directly confirm the exact internal mechanics of how `block_revenue_commission_bps` is read and applied inside that function. However, the call site unambiguously shows the *account view* passed in (`distribution_epoch_vote_accounts`) is the live/current one and not a delayed snapshot, which is the crux of the reported inconsistency between the two commission paths, and the doc comment on `CachedVoteAccounts` corroborates that this represents current state.

## Impact Explanation
If confirmed, this would divert block-revenue-sharing rewards that delegated stakers are economically entitled to toward the validator's commission, constituting fund loss for delegators via a legitimately-signed but economically abusive instruction sequence — no privileged access, no malicious peer/validator assumption, and no compromised keys required, satisfying the "unprivileged... runtime... fund theft/loss" scope. The withdrawer authority is a normal, unprivileged (from a protocol-security standpoint) participant who is expected to act in the stakers' interest but currently has an unguarded lever to divert value during exactly the reward-computation window.

## Likelihood Explanation
The withdrawer authority need only know the public epoch/slot schedule to time an `UpdateCommissionBps{kind: BlockRevenue}` transaction shortly before block-revenue reward calculation and revert it afterward, since the code path has "No commission update rule" and consumes live vote-account state at reward time. [1](#0-0) [4](#0-3)  This is repeatable every distribution window with no on-chain penalty, cooldown, or lock.

## Recommendation
Apply the same epoch-delay protection used for inflation-rewards commission to the block-revenue-sharing commission field: have `calculate_block_reward` consult a commission value sourced from `snapshot_epoch_vote_accounts` (or an equivalently epoch-old snapshot) rather than `distribution_epoch_vote_accounts`, mirroring the pattern in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` lines 703-724. Alternatively, reinstate a minimum-delay/epoch-half restriction specifically for `CommissionKind::BlockRevenue` updates in `update_commission_bps` (`programs/vote/src/vote_state/mod.rs`) and its dispatch in `vote_processor.rs`.

## Proof of Concept
1. Withdrawer authority observes (via public epoch/slot schedule) that block-revenue reward calculation for the current distribution window is imminent.
2. It submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }`, accepted unconditionally per the dispatch/handler code cited above. [2](#0-1) [1](#0-0) 
3. `calculate_stake_rewards_and_commissions` computes `calculate_block_reward` using `cached_vote_accounts.distribution_epoch_vote_accounts` (live state), attributing nearly all block revenue to the validator's commission. [4](#0-3) 
4. After distribution, the withdrawer authority resets the commission to a normal value, with no cooldown preventing repetition.

A reproducible test would construct a bank at the relevant reward-distribution boundary, call `update_commission_bps` with `BlockRevenue` and `commission_bps = 10000` immediately prior, assert that `calculate_block_reward`/`calculate_stake_rewards_and_commissions` attributes the elevated commission to that window, then verify no epoch-delay snapshot mechanism intervenes (unlike the `delay_commission_updates` branch for inflation rewards).

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
