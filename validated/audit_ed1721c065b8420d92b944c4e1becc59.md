### Title
Unauthenticated `kaia_decodeAccountKey` RPC allows unbounded recursive RLP decoding of attacker-controlled data, enabling node-crashing DoS - (File: `blockchain/types/accountkey/account_key_role_based.go`, `api/api_kaia.go`)

### Summary
The public, unauthenticated JSON-RPC method `KaiaAPI.DecodeAccountKey` accepts arbitrary attacker-supplied bytes and RLP-decodes them into an `AccountKeySerializer`/`AccountKeyRoleBased` structure with no depth, nesting, or recursion limit enforced during decoding. This mirrors the GitLab bug class (parsing arbitrary attacker-supplied input without authorization, leading to a DoS), reachable here by any public RPC caller rather than requiring a valid signed transaction.

### Finding Description
`DecodeAccountKey` takes `hexutil.Bytes` directly from the caller and calls `rlp.DecodeBytes` into an `accountkey.AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a key type and dispatches to `NewAccountKey`, then recursively decodes into that key type: [2](#0-1) 

Crucially, when the type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings and, for **each element**, constructs a brand-new `AccountKeySerializer` and recursively calls `rlp.DecodeBytes` on it — which can itself be another `AccountKeyRoleBased`, ad infinitum: [3](#0-2) 

Unlike the consensus/transaction-execution path, where `CheckInstallable`/`checkAccountKeyZeroValues` reject a `RoleBased` key nested inside another `RoleBased` key at one level of nesting: [4](#0-3) [5](#0-4) 

...the `DecodeAccountKey` RPC **never calls** `CheckInstallable` or `checkAccountKeyZeroValues` — it just decodes and returns the serializer. There is no limit on how many levels of nesting an attacker can encode, and each level triggers a fresh Go function-call chain (`DecodeRLP` → `s.Decode` → `DecodeRLP` → ...). A crafted, deeply nested RLP payload (e.g., thousands of nested single-element `RoleBased` keys) can be encoded compactly (a few bytes of RLP list/header overhead per level), well within any HTTP/WS request size caps (`common.MaxRequestContentLength`), while producing tens of thousands of recursive stack frames.

### Impact Explanation
Go's growable goroutine stacks eventually hit the runtime-enforced maximum stack size; exceeding it results in a **fatal, unrecoverable runtime error** ("goroutine stack exceeds ... limit") that is not caught by `recover()` and crashes the entire node process. Because `DecodeAccountKey` is exposed as a standard public RPC method (no special privileges required beyond RPC access), any unauthenticated caller with public RPC access can crash a full node/validator RPC process with a single call, causing a denial of service. This is consistent in class with the report's "parsing files without authorization" DOS: a public-facing endpoint parses attacker-controlled structured input with unbounded recursive cost/depth and no authorization or resource bound.

### Likelihood Explanation
High. `kaia_decodeAccountKey` is a standard namespace API typically enabled on public RPC endpoints (`kaia` namespace) for reading/decoding account-key data. No special caller privilege, on-chain state, gas payment, or valid signature is required — it operates purely on user-provided bytes before touching any blockchain state. Constructing a deeply nested `RoleBased` RLP payload is straightforward using the existing `AccountKeyRoleBased.EncodeRLP` logic.

### Recommendation
- Enforce the same nesting/composite-type restriction used at the consensus layer (`errKeyLengthZero`/`ErrNestedCompositeType`/`checkAccountKeyZeroValues`) inside `AccountKeyRoleBased.DecodeRLP` itself, or track and reject decode depth greater than 1 (RoleBased must not contain RoleBased).
- Add an explicit maximum decode depth counter into the shared `rlp.Stream`/decode context so that any custom `Decoder` recursion (not only structural RLP nesting) is bounded.
- Validate/size-limit the raw input to `DecodeAccountKey` before invoking RLP decoding and reject inputs that structurally imply more nesting than `RoleLast` (3) role levels.

### Proof of Concept
1. Recursively construct a malicious `AccountKeySerializer` byte string of depth *N* (e.g. N = 50,000), where each level is a `RoleBased` account key (`AccountKeyTypeRoleBased`, tag `5`) whose single role-key element is itself another RLP-encoded `RoleBased` `AccountKeySerializer` (using the same encoding logic as `AccountKeyRoleBased.EncodeRLP`, `blockchain/types/accountkey/account_key_role_based.go:110-118`, but bypassing `CheckInstallable`/`checkAccountKeyZeroValues` since encoding does not invoke them).
2. Hex-encode the resulting bytes; ensure total size stays under `common.MaxRequestContentLength`.
3. Call the public RPC method: `kaia_decodeAccountKey(<hex-encoded payload>)`.
4. The recursive `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` chain executes N times, consuming the goroutine's stack; at sufficient depth this triggers a fatal Go runtime stack-overflow error, crashing the entire kaia node process and denying service to all users of that RPC endpoint.

func (s *KaiaAPI) DecodeAccountKey(encodedAccKey hexutil.Bytes) (*accountkey.AccountKeySerializer, error) {
	dec := accountkey.NewAccountKeySerializer()
	if err := rlp.DecodeBytes(encodedAccKey, &dec); err != nil {

	}

}

	}

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
