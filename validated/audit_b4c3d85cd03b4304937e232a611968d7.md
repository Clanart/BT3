### Title
Late "receiver balance == 0" safety check in `IBCReceivePacketCallback` is checked *after* state is committed, allowing IBC-received tokens to become permanently stuck in an unrecoverable isolated address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
This is the same bug class as the C4 Auction.sol finding: a critical invariant (`newRatio >= minIbRatio` / here, "isolated receiver balance must be zero") is evaluated *after* the state mutation it is supposed to guard against has already been committed, so a failure of the check cannot undo the harmful effect — it can only report it. In `x/ibc/callbacks/keeper/keeper.go`'s `IBCReceivePacketCallback`, the cached EVM execution (ERC20 `approve` + contract callback) is committed via `writeFn()` at [1](#0-0)  and only afterward is the "receiver has no remaining tokens" invariant checked at [2](#0-1) , whose own comment states the tokens "would become irretrievable" if this ever fails.

### Finding Description
`IBCReceivePacketCallback` implements the destination-side IBC callback used to let a smart contract atomically consume ERC20-representation tokens that an incoming IBC transfer sent to a deterministic, keyless "isolated address" [3](#0-2) .

The flow is:
1. A `cachedCtx` is created via `ctx.CacheContext()` [4](#0-3) .
2. The isolated address `approve`s the target contract for the full transferred amount, executed on `cachedCtx` [5](#0-4) .
3. The target contract's callback (arbitrary calldata, chosen by the IBC-transfer sender via memo) is invoked, also on `cachedCtx`, and is expected to `transferFrom` the *entire* amount out of the isolated address [6](#0-5) .
4. `writeFn()` is called, **permanently committing** all of the above EVM state changes (approve + whatever the arbitrary contract did) into the real `ctx` [1](#0-0) .
5. Only now is the safety invariant checked: the isolated address's ERC20 balance must be exactly zero, otherwise an error is returned [2](#0-1) .

Because step 5 happens strictly after step 4's commit, a failure of the invariant cannot be un-done: whatever balance is left in the isolated address is exactly the scenario the check's own comment says should "prevent funds from getting stuck" — yet the check only fires after the fact. The isolated address is a deterministically generated address with no known private key [7](#0-6) , so any residual ERC20 balance left there is permanently unrecoverable by any party — the funds are frozen forever.

This mirrors the Auction.sol root cause precisely: the guarding `require`/check is placed after the point where reversal is still possible, turning a "protective invariant" into a "post-mortem error message" with no remediation path.

Additionally, per the standard ibc-go v10 callbacks-middleware (ADR-8) design that this `ContractKeeper` implements, callback execution failures are intentionally isolated from the underlying packet's acknowledgement — i.e., an error returned from `IBCReceivePacketCallback` does not cause the packet's `OnRecvPacket` to fail or turn into an error acknowledgement, and does not cause the token mint/transfer to the isolated address (performed earlier, outside this cached scope, by the transfer/erc20 keepers) to be rolled back. This reinforces that the check at line 236 has no recovery effect whatsoever once triggered.

### Impact Explanation
Any contract invoked via an IBC destination callback that does not `transferFrom` the *exact full* approved amount (due to a bug, rounding, fee-on-transfer semantics, partial-fill logic, or a contract that is intentionally malicious/lured with a plausible-looking integration) causes the remaining token balance in the isolated address to become permanently and unconditionally locked, with no owner, no key, and no protocol-level recovery mechanism. This is a critical, permanent freezing/loss of user funds (the transferred ERC20-represented value), matching the in-scope "permanent freezing, locking ... of user funds ... escrowed assets" impact category.

### Likelihood Explanation
This is triggerable by any unprivileged user: the attacker (or any ordinary user) only needs to send a standard `MsgTransfer` / ICS20 transfer with a destination callback memo pointing at a contract that doesn't fully drain its approved allowance. No privileged role, governance action, or malicious relayer/validator is required — it can happen accidentally with any imperfect integration, and can be weaponized deliberately by publishing a contract address for users to "interact with" via IBC callback memos that intentionally leaves a dust (or larger) remainder.

### Recommendation
Move the invariant check before the commit boundary, or make the commit conditional on the invariant:
- Perform the "receiver balance must be zero" check against `cachedCtx` (pre-`writeFn()`), and only call `writeFn()` if the check passes.
- Alternatively, if the check fails, explicitly reverse the harmful effects (e.g., forcibly transfer any residual balance in the isolated address back to `data.Sender`/the original owner) before returning the error, rather than leaving the balance stranded in an address nobody controls.
- Ensure that whatever remediation is chosen also accounts for ibc-go's ADR-8 semantics, under which returning an error from this callback does not roll back the underlying packet's acknowledgement or the funds already delivered to the isolated address.

### Proof of Concept
1. Deploy (or induce a user to point their destination-callback memo at) a contract `C` whose fallback logic performs `transferFrom(isolatedAddr, C, amount - 1)` instead of the full `amount` (e.g., due to a fee-calculation bug, or deliberately).
2. User A sends an ICS20 `MsgTransfer` to this chain with `receiver` set to the isolated address derived from `(destChannel, senderAddr)` and memo containing a destination callback pointing at contract `C`.
3. On receipt, `IBCReceivePacketCallback` runs:
   - `approve(C, amount)` succeeds on `cachedCtx`.
   - `C`'s callback executes `transferFrom(isolatedAddr, C, amount-1)`, leaving `1` unit of tokens in the isolated address.
   - `writeFn()` commits both of these state changes to `ctx` permanently [1](#0-0) .
   - The post-check at [8](#0-7)  finds `receiverTokenBalance == 1 != 0` and returns an error.
4. Per ibc-go callbacks-middleware semantics, this error does not revert the packet's success/ack or the already-committed approve/transferFrom state — the `1` unit of tokens remains permanently stuck in the isolated address, which has no corresponding private key, making the funds unrecoverable forever.
