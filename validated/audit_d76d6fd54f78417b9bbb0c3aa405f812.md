### Title
Incorrect price attached to stSTXbtc / zstSTXbtc collateral (uses STX feed instead of BTC feed) - ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
`get-asset-price` in `mainnet/contracts/utility/v0-1-data.clar` prices the `stSTXbtc` and `zstSTXbtc` assets using the **STX** Pyth price feed instead of the **BTC** feed, despite the code comments explicitly stating "BTC price". This is the same bug class as the reported `StableSwapOperatorV1` issue — a value that should be priced with one reference is instead priced (or summed) with a mismatched reference, producing a systematically wrong USD valuation that is fed straight into the account's collateral/debt USD totals, LTV, and liquidation health verdict.

### Finding Description
`get-asset-price` computes the USD price (8-decimal) for every asset type recognized by the market/vault system: [1](#0-0) 

```clarity
;; stSTXbtc - BTC price (liquid staked STX with BTC yield)
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
;; zstSTXbtc - stSTXbtc price x liquidity index
(if (is-eq aid zstSTXbtc)
    (let ((btc-price (default-to u0 (get-pyth-price PYTH-STX)))
          (lindex (get-vault-liquidity-index stSTXbtc)))
      (mul-div-down btc-price lindex INDEX-PRECISION))
```

The comments say `stSTXbtc` and `zstSTXbtc` should be priced from the BTC feed (`PYTH-BTC`), matching how `sBTC`/`zsBTC` are priced elsewhere in the same function using `PYTH-BTC` [2](#0-1) . Instead, both branches call `get-pyth-price PYTH-STX`, the same feed already used for `STX`/`zSTX`/`stSTX` pricing a few lines above [3](#0-2) . STX and BTC prices diverge by orders of magnitude, so this is not a rounding-level discrepancy like the referenced report — it is a complete mispricing of the asset.

This mispriced value feeds directly into `sum-collateral-usd` / `sum-debt-usd`, which aggregate USD-denominated collateral and debt totals used to compute `current-ltv`, `health-factor`, and `is-liquidatable`: [4](#0-3)  and [5](#0-4) .

### Impact Explanation
Because STX price is typically far below BTC price, `stSTXbtc`/`zstSTXbtc` collateral value computed by this helper would be understated by roughly the STX/BTC price ratio (potentially by tens of times). Any consumer relying on this contract's `current-ltv`/`health-factor`/`is-liquidatable` output (e.g., liquidation bots, monitoring/alerting, or any downstream contract call that trusts this health verdict) would see accounts holding `stSTXbtc`/`zstSTXbtc` collateral as far riskier or safer than reality, depending on direction, leading to wrong liquidation triggers — either premature/unjustified liquidation of solvent positions (theft of collateral from users) or failure to flag genuinely undercollateralized positions (protocol insolvency / bad debt) if the numbers were reversed. This lands in the Critical impact bucket (protocol insolvency / fund loss) if this health/LTV computation gates real liquidation or borrowing decisions.

### Likelihood Explanation
The bug is deterministic and triggers on every price query for any account holding `stSTXbtc` or `zstSTXbtc` — no attacker action or price manipulation is required, only the presence of this specific collateral type in a position and normal read access to this contract's public/read-only health functions.

### Recommendation
Fix `get-asset-price` to use `PYTH-BTC` (consistent with `sBTC`/`zsBTC` handling) for both the `stSTXbtc` and `zstSTXbtc` branches, matching the existing comments' intent.

### Proof of Concept
1. Register/hold `stSTXbtc` (or `zstSTXbtc`) as collateral in an account.
2. Call any read path that invokes `sum-collateral-usd`/`sum-debt-usd` → `get-asset-price` for that asset (e.g., the position/health-factor query in `v0-1-data.clar`).
3. Observe the returned collateral USD value uses the STX price rather than the BTC price, producing a materially wrong `current-ltv`/`health-factor`/`is-liquidatable` result compared to the asset's real BTC-denominated value.

Note: I was unable to fully confirm within the available iterations whether this `v0-1-data.clar` "utility" contract's health-verdict output is consumed by the core market's actual enforcement path (borrow/withdraw/liquidate gating in `market/v0-4-market.clar`, which resolves prices per-asset via the `assets` registry) or is purely an informational/reporting helper for off-chain consumers (dashboards, liquidation bots). If it is purely informational, the direct on-chain fund-impact would be lower than stated above; if any liquidation or borrow decision relies on this contract's output, the Critical impact stands. This distinction should be verified against `market/v0-4-market.clar`'s liquidation/borrow code paths and the asset oracle registration for `stSTXbtc` in `mainnet/contracts/proposals/mainnet/v0-init.clar` before final severity assignment.
