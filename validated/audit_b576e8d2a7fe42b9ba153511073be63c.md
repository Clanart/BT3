Found: `validateResolutionPaths` in `app/src/lib/copilot-conflict-resolution.ts` does strictly validate the model's returned paths against `expectedFiles` (the actual conflicted files) at parse time [1](#0-0) . However, that validation happens once, at generation time, against the file list that was conflicted *when the resolution was requested*. The write path, `_applyCopilotConflictResolutions`, re-reads `state.changesState.workingDirectory.files` **at write time** (a different, later point) only to decide whether to *skip* a file that was resolved externally — it never re-validates that `resolution.path` is still an actual member of the current conflict set, nor that `multiCommitOperationState.step.kind` is still the Copilot-review step for that same operation, before calling `writeFile` [2](#0-1) .

### Title
Stale/cross-operation Copilot conflict resolutions can be silently written after the guarded review step has been left - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated file content and stages it based solely on `multiCommitOperationState.copilotResolutions !== null`, without checking that the current `multiCommitOperationState.step.kind` is still `ShowCopilotConflicts`/`ConfirmAbort`-from-that-step for the *same* merge/rebase/cherry-pick operation that produced those resolutions.

### Finding Description
`_startCopilotConflictResolution` correctly gates entry into the AI-resolution flow on `step.kind === ShowCopilotConflictsLoading` [3](#0-2) , and the async completion handler re-checks `ownsCurrentRun()` and the current step before storing `copilotResolutions` [4](#0-3) . This mirrors the "require Trading state" pattern the report calls for.

The write/apply step does not repeat that check. `_applyCopilotConflictResolutions` only bails if `multiCommitOperationState === null` or `copilotResolutions` is empty [5](#0-4) . It does not verify `step.kind` equals `ShowCopilotConflicts` (it merely *uses* `manualResolutions` from that step if present, defaulting to an empty map otherwise) [6](#0-5) . It then loops over every stored `copilotResolutions` entry and, for entries that are not in the working directory's current conflicted-file list, falls straight through to `writeFile` and stages the path — the "skip if resolved externally" check only fires when the path *is* found in `workingDirectory.files` [7](#0-6) .

Because `copilotResolutions` is repository-state that persists in `multiCommitOperationState` across intermediate UI transitions (loading → ShowCopilotConflicts → ConfirmAbort → back), and the guard that clears/re-validates it is only enforced at the *generation* boundary (`_startCopilotConflictResolution`/`validateResolutionPaths`) and not at the *apply* boundary, `applyCopilotConflictResolutions` can be invoked (via the dispatcher call from `copilot-conflicts-dialog.tsx`'s `onContinue`) after the underlying working-directory/operation state has moved on — e.g., the user aborted the AI-resolved merge, started a different merge/rebase, or the conflict set changed — while `copilotResolutions` from the prior run are still cached in `multiCommitOperationState` and get re-applied blindly.

### Impact Explanation
This corrupts what the user actually commits: content generated by an LLM in response to one (attacker-influenced) conflict context can be written to disk and `git add`-ed for a different operation/working tree state than the one it was validated against, without the user reviewing it against the currently displayed diff. Because the conflict text fed to Copilot (commit messages, PR descriptions, file diffs) originates from a cloned/fetched repository the attacker controls, this is squarely in the "attacker controls a cloned/fetched repository ... resulting in ... silent corruption of what the user commits or pushes" category. The missing re-validation at the write boundary is the direct analog of `applyCover`'s missing `Trading`-state check: a stateful, security-relevant action (`applyCover` / `writeFile`+`git add`) is permitted to run again without reconfirming the precondition (`Trading` state / "these paths are still today's conflicted files under the currently displayed step").

### Likelihood Explanation
Reaching this requires the normal Copilot-conflict-resolution UI flow (feature-flagged) plus a user who aborts/re-triggers conflict resolution or has overlapping multi-commit operations, so it is not a one-click remote exploit — but no local/admin/malware assumptions are needed and the entry point (crafted repo content driving Copilot's output) is fully attacker-influenced.

### Recommendation
In `_applyCopilotConflictResolutions`, before writing each resolution, re-verify (a) `multiCommitOperationState.step.kind` is still one of the expected Copilot-conflict steps for the *same* operation (e.g. compare `conflictState`/operation identity, not just non-null `copilotResolutions`), and (b) `resolution.path` is still present in the current `workingDirectory.files` conflicted-file set, rejecting/skipping paths that aren't, mirroring `validateResolutionPaths`'s allow-list check but applied again at write time.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick against a crafted branch whose conflicting content is designed to make Copilot volunteer a resolution for `path: "unrelated/tracked-file.ts"` (only bounded by `validateResolutionPaths` matching the *initial* conflicted-file set — an attacker controls the conflict text and can widen what files show as "conflicted" via crafted diffs/renames across the batched chunks feeding `expectedFiles`).
2. Let Copilot resolution complete (`_startCopilotConflictResolution` → `copilotResolutions` populated, step becomes `ShowCopilotConflicts`).
3. Abort the merge or otherwise leave the `ShowCopilotConflicts` step (e.g. via `ConfirmAbort` then cancel-abort path, or start a new operation) without the app clearing `copilotResolutions`.
4. Re-invoke `dispatcher.applyCopilotConflictResolutions(repository)` (reachable via the dialog's `onContinue` if the dialog/step is re-entered) — `_applyCopilotConflictResolutions` finds `copilotResolutions` non-null and writes/stages the stale content for `unrelated/tracked-file.ts` even though it is no longer part of the tracked conflict resolution flow, silently altering what gets staged for the next commit.

**Uncertainty**: I could not fully trace the runtime reachability of step (3)/(4) (i.e., every UI path that could re-invoke `applyCopilotConflictResolutions` without the guard resetting `copilotResolutions`) within the tool budget available; verifying whether `endMultiCommitOperation`/`_abortCopilotConflictResolution` always clears `copilotResolutions` on every exit path would require reading those functions in full, which I was not able to do before running out of iterations.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  public async _applyCopilotConflictResolutions(
    repository: Repository
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    const { multiCommitOperationState } = state
    if (multiCommitOperationState === null) {
      return
    }

    const { copilotResolutions, step } = multiCommitOperationState
    if (copilotResolutions === null || copilotResolutions.length === 0) {
      return
    }

    // Respect any manual overrides the user chose in the result dialog
    const manualResolutions =
      step.kind === MultiCommitOperationStepKind.ShowCopilotConflicts
        ? step.conflictState.manualResolutions
        : new Map<string, ManualConflictResolution>()

    this.statsStore.increment('copilotConflictResolutionAcceptedCount')
    if (manualResolutions.size > 0) {
      this.statsStore.increment('copilotConflictResolutionWithOverridesCount')
    }

    const pathsToStage: string[] = []

    for (const resolution of copilotResolutions) {
      if (manualResolutions.has(resolution.path)) {
        continue
      }

      // Delete-vs-modify conflicts are resolved by setting a manual
      // resolution (ours/theirs) rather than writing file content.
      // The existing stageManualConflictResolution flow handles the
      // actual git checkout --ours/--theirs and staging at commit time.
      if (resolution.deleteConflictAction !== undefined) {
        const file = state.changesState.workingDirectory.files.find(
          f => f.path === resolution.path
        )
        if (file === undefined) {
          continue
        }
        const deletedSide = getDeletedSideFromStatus(file)
        if (deletedSide === undefined) {
          continue
        }
        // "keep" → choose the non-deleted side, "delete" → choose the deleted side
        const manualChoice =
          resolution.deleteConflictAction === 'keep'
            ? deletedSide === 'ours'
              ? ManualConflictResolution.theirs
              : ManualConflictResolution.ours
            : deletedSide === 'ours'
            ? ManualConflictResolution.ours
            : ManualConflictResolution.theirs
        this._updateManualConflictResolution(
          repository,
          resolution.path,
          manualChoice
        )
        continue
      }

      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(
          `Copilot resolution skipped: path outside repository: ${resolution.path}`
        )
        continue
      }

      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      // This mirrors how the manual conflicts dialog determines a file is
      // resolved (`hasUnresolvedConflicts`).
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }

      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
      pathsToStage.push(resolution.path)
