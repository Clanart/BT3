## Analog Found: Positional (Order-Based) Conflict-Marker Splicing Lets a Crafted File Silently Corrupt Copilot-Resolved Merge Commits

### Title
Attacker-crafted conflict-marker lookalikes cause `reassembleResolvedFile` to misalign resolutions and silently corrupt committed content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's "Resolve with Copilot" feature reassembles AI-resolved merge/rebase/cherry-pick conflicts by scanning the on-disk file for git conflict-marker patterns with a plain regex and splicing per-hunk model output into them **by encounter order, not by verified git conflict location**. A branch/PR authored by an attacker (i.e., content the victim clones/fetches and merges) can contain literal text that matches the marker regex (`<<<<<<<` / `=======` / `>>>>>>>`) without being a real git conflict block. This shifts the ordinal alignment between the model's hunk resolutions and the real conflict blocks, causing the wrong resolved content to be written into a real conflict site. The resulting file is then written to disk and staged automatically when the user clicks "Continue Merge," with no diff review forcing function — silently corrupting what the user commits.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file content line-by-line and treats *any* line matching `^<{7}` as the start of a conflict block, provided a later `=======` and `>>>>>>>` are found: [1](#0-0) [2](#0-1) 

Critically, hunk resolutions are matched to marker blocks purely by array index (`hunkIndex`), not by git's own record of where the actual conflict is: [3](#0-2) 

The function's own doc comment acknowledges this design: "matched by order, not by line number" [4](#0-3) . If a file contains a well-formed decoy block that isn't an actual git-recorded conflict (e.g., a code comment, markdown documentation snippet, or string literal that happens to contain all three marker lines in order), the scanner still counts it as hunk #`n`, consuming a resolution slot meant for the real conflict and shifting every subsequent real hunk's resolved content by one position.

The write path then persists this misaligned reassembly straight to disk and stages it for commit: [5](#0-4) 

The existing guards at this call site only check that the resolved path stays within the repository (`resolveWithin`) and that the file wasn't already externally resolved (`hasUnresolvedConflicts`) — neither guard validates that the reassembled content was spliced into the *correct* conflict location: [6](#0-5) 

### Impact Explanation
An attacker who controls a branch, fork, or pull request that the victim merges/rebases/cherry-picks (a fully attacker-controlled Git object, satisfying the "attacker controls a cloned/fetched repository" criterion) can plant decoy marker-like text in a file that also has a real conflict elsewhere. When the victim uses "Resolve with Copilot," the reassembly step can misassign the AI's resolved content to the wrong conflict location. The victim then clicks "Continue Merge," the corrupted file is written and `git add`-ed automatically, and the corrupted content is committed and potentially pushed — without the user seeing an accurate diff, because the app never re-validates the spliced result against the actual conflict boundaries before staging.

### Likelihood Explanation
Exploitation requires only that the victim (a) enables and clicks "Resolve with Copilot" on a merge/rebase/cherry-pick that includes a file authored (in whole or part) by the attacker, and (b) the attacker's file contains both a real conflicting hunk and one decoy marker-shaped block earlier in the file. No local access, admin rights, or social engineering beyond "attacker gets their branch/PR merged/rebased against" is required — this is a normal collaborative workflow. The main constraint is that the feature must be actively used (opt-in AI-assisted conflict resolution), which limits but does not eliminate the practical likelihood.

### Recommendation
Match Copilot's per-hunk resolutions to conflict blocks using positional/content anchors derived from git's own conflict metadata (e.g., hunk start/end offsets or a hash of the exact marker+ours+theirs text) rather than pure encounter order. Additionally, validate that the number and content of scanned marker blocks in `reassembleResolvedFile` matches the number of conflicts git itself reports for the file before writing, and refuse to write/stage the file if there is a mismatch.

### Proof of Concept
1. Attacker prepares a feature branch with a file `notes.py` containing, in the *same file*, a real conflicting change plus an unrelated decoy string/comment such as:
   ```
   doc = """
   <<<<<<< example
   old text
   =======
   new text
   >>>>>>> example
   """
   ```
   placed *before* the actual conflicting section in the file.
2. Victim merges this branch, producing a real git conflict in `notes.py` further down in the file (after the decoy text).
3. Victim clicks "Resolve with Copilot." The model returns one hunk resolution intended for the real conflict.
4. `reassembleResolvedFile` scans top-to-bottom, matches the *decoy* block first (well-formed per the regexes), consumes `hunkResolutions[0]` (the model's real resolution) and splices it into the decoy location, then treats the real conflict block afterward with `hunkIndex` now out of range — leaving the real conflict either unresolved-looking or filled from a stale/incorrect slot.
5. `_applyCopilotConflictResolutions` writes this corrupted content to disk and runs `git add`, and the user commits/pushes the corrupted, un-reviewed result [7](#0-6) .

```typescript
// Conflict markers used by reassembleResolvedFile to locate marker blocks.
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
```

```typescript
  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
```
