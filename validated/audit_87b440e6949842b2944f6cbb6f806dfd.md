### Title
Line-based diff selection is re-applied to a freshly re-fetched working-directory diff during partial commit, allowing a stale/attacker-modified file to have its lines mis-mapped and silently committed - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop implements partial/line-level staging as a two-step process, the same TOCTOU pattern described in the SteadeFi report: a `DiffSelection` (which lines the user wants included) is captured against a diff snapshot rendered earlier in the Changes UI, and is only turned into an actual patch later, at commit time, in `applyPatchToIndex`. At that point Desktop re-fetches the diff from disk (`getWorkingDirectoryDiff`) rather than reusing the diff the selection was made against, and then re-applies the old line indices to this brand-new diff via `formatPatch`. There is no check that the newly fetched diff still matches the diff the selection indices were computed from. [1](#0-0) 

### Finding Description
The `WorkingDirectoryFileChange.selection` object (`DiffSelection`) stores only line indices (`divergingLines: Set<number>`), with no reference to the content or hash of the diff it was computed against: [2](#0-1) 

When the user actually commits, `_commitIncludedChanges` in `app-store.ts` takes the file objects (and their `selection`) straight from the cached `changesState.workingDirectory.files` — a snapshot that may be stale relative to the current file on disk: [3](#0-2) 

That flows into `stageFiles` → `applyPatchToIndex`, which does not reuse the diff that produced the on-screen selection. Instead it independently re-computes the diff at execution time: [4](#0-3) 

and then builds the actual patch by indexing into this *new* diff with the *old* selection's absolute line indices: [5](#0-4) 

If the tracked file's content on disk changes between the moment the user made their line selection (in the UI) and the moment `applyPatchToIndex` runs — e.g., because a git hook (`post-checkout`, `post-merge`, `pre-commit` with auto-formatting) or a clean/smudge filter defined by a cloned/fetched (attacker-controlled) repository rewrites the file, or the file is regenerated by a build step triggered from an untrusted `package.json`/hook that ships with the repo — the hunk boundaries and absolute line offsets in the newly fetched diff no longer correspond to what the user actually saw and selected in the UI. Because `DiffSelection` only stores bare integer indices, the same indices are silently reinterpreted against the new hunk layout, so `formatPatch` can select and stage completely different lines than the ones the user reviewed and clicked on. There is no re-validation step (e.g., comparing the diff's hunk headers/oids before vs. after) analogous to the missing "before/after" comparisons called out in the original SteadeFi report (`lpAmtBefore` vs. actual amount received).

This mirrors the reported bug class precisely: state is saved at "step 1" (the selection, made against a diff snapshot in the renderer), an attacker-influenced external actor (a malicious repository's hook/filter/build tooling) mutates the underlying resource between step 1 and step 2, and "step 2" (`applyPatchToIndex`) blindly trusts the step-1 state was still valid, with no guard that would catch the mismatch (`GMXChecks.afterWithdrawChecks`'s analog would be: verify the diff generation/hash used for the selection is unchanged before applying it).

### Impact Explanation
The practical impact is silent corruption of what the user commits: content the user never selected (or never intended to include) can end up staged and committed, while content they did select can be dropped. This can leak or introduce unreviewed lines into a commit (e.g., secrets, unrelated code, or content injected by an untrusted post-checkout hook) without any warning to the user, and the corrupted commit can then be pushed upstream. This matches the "silent corruption of what the user commits or pushes" impact class explicitly called out as valid for this task.

### Likelihood Explanation
Exploitation requires only ordinary Desktop usage of a cloned/fetched repository that ships a hook or filter capable of mutating tracked working-tree files (a capability already exercised elsewhere in the codebase, e.g. `updateSubmodulesAfterOperation` executing `git submodule update --init --recursive`, and hook execution paths referenced in `onHookProgress`/`onHookFailure` in `_commitIncludedChanges`). The race window is the time between the user visually selecting lines in the Changes/diff view and clicking "Commit," which for a large diff or a slow machine can be non-trivial, and no local/admin privileges or prior compromise of the host are needed — only that the user opens/clones a hostile repository and does a normal partial commit.

### Recommendation
Before applying a cached `DiffSelection` to a file in `applyPatchToIndex`, recompute or store a content fingerprint (e.g., hash of the raw diff/hunks) at selection time, and compare it against the diff fetched at commit time in `getWorkingDirectoryDiff`. If they differ, abort the partial commit and force the user to re-review the diff, rather than silently reinterpreting stale line indices against new hunk boundaries — analogous to the SteadeFi recommendation of comparing captured lpAmt/depositValue against actual post-callback values instead of trusting pre-callback state.

### Proof of Concept
Not independently executable from the index alone (would require a live Desktop instance + a crafted repository with a `post-checkout`/`smudge` hook), but the vulnerable code path is fully traceable from local evidence:
1. User opens a partial-diff selection in the Changes view for `file.md`; `DiffSelection` records selected line indices against the diff rendered at that time.
2. A hook/filter belonging to the attacker's repository (triggered by an unrelated background git operation, e.g. an auto-fetch-triggered `post-merge`) rewrites `file.md`, shifting/adding hunks.
3. User clicks Commit → `_commitIncludedChanges` (`app-store.ts:3681`) passes the stale `file.selection` to `createCommit`/`stageFiles`/`applyPatchToIndex` (`apply.ts:12`).
4. `applyPatchToIndex` re-fetches the diff (`apply.ts:60`) and calls `formatPatch` (`patch-formatter.ts:129`), which maps the old indices onto the new hunks via `file.selection.isSelected(absoluteIndex)` (`patch-formatter.ts:157`), producing a patch that stages different content than what the user selected, with no validation anywhere in this path that the diff used for the selection still matches the diff being patched. export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
