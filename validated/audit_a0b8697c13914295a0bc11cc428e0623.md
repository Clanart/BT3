### Title
Duplicate Bitcoin inputs are counted multiple times, allowing unfunded payment transactions - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` treats every supplied `ReceivedOutput` as distinct spendable value, but never checks that their `OutPoint`s are unique. An attacker can provide the same UTXO twice, causing its value to be counted twice in `input_sat` and enabling payments that exceed the actual funds available. The resulting transaction is signed normally because each Schnorr machine only verifies that the claimed previous output script corresponds to the offset key, not that the referenced outpoints are distinct or backed by distinct real UTXOs. [1](#0-0) [2](#0-1) 

### Finding Description
The constructor sums `input.output.value` across all entries and separately constructs one transaction input per `input.outpoint`; there is no duplicate-outpoint validation or deduplication between those operations. [1](#0-0) 

It then compares that inflated `input_sat` against `payment_sat + needed_fee`. With two copies of one 10,000-satoshi UTXO, `input_sat` is 20,000 while the transaction can consume only 10,000 actual satoshis. [3](#0-2) 

Untrusted serialized inputs are a reachable source for this state because `ReceivedOutput::read` accepts the offset, claimed `TxOut`, and claimed `OutPoint` without verifying that the claimed output exists on-chain or that it is unique within a future input list. [4](#0-3) 

During multisig creation, each input independently passes the script check if it claims the script produced by the correct offset; a duplicated entry therefore passes twice. [2](#0-1) 

Signing then commits to every input index using `Prevouts::All`, so the duplicate inputs are included in the Taproot signature messages rather than rejected. [5](#0-4) 

### Impact Explanation
This reproduces the same accounting defect as the report: available funds are calculated without accounting for the fact that part of those funds has already been obligated earlier in the same transaction. The transaction builder and signers can therefore accept and produce signatures for a payment set that the real UTXO set cannot settle. The completed transaction contains duplicate inputs and is invalid under Bitcoin consensus rules, so any payment represented by it is not actually spendable. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
An unprivileged caller that can supply or relay `ReceivedOutput` records only needs to serialize the same legitimate received output twice. No validator compromise, malformed curve point, leaked key, or malicious Bitcoin RPC response is required; the byte stream itself is sufficient when passed to `ReceivedOutput::read`, followed by `SignableTransaction::new`. [8](#0-7) [9](#0-8) 

### Recommendation
Reject duplicate `OutPoint`s in `SignableTransaction::new` before calculating `input_sat`. A `HashSet<OutPoint>` or sorted duplicate check should ensure every claimed input refers to a distinct UTXO. Ideally, `ReceivedOutput` ingestion should also verify the referenced prevout against blockchain data, but uniqueness validation is the minimum needed to prevent the same UTXO from backing multiple obligations in one transaction. [10](#0-9) 

### Proof of Concept
```rust
// `received` is one real output worth 10_000 sats.
let duplicate = received.clone();
let inputs = vec![received, duplicate];

// `payment` is greater than 10_000 sats but less than 20_000 sats,
// after accounting for the calculated fee.
let tx = SignableTransaction::new(
    inputs,
    &[(payment_script, payment_amount)],
    None,
    None,
    fee_per_vbyte,
)?;

// Accepted because input_sat counts the same UTXO twice.
let machine = tx.multisig(&keys).unwrap();
```

The signing flow produces witnesses for both inputs, but the completed transaction repeats the same `previous_output`, making it invalid and leaving the represented payment unsettled. [11](#0-10) [7](#0-6)
