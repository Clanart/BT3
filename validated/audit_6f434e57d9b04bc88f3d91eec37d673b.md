## Cross-domain signature replay between `withdraw()` and `accumulate()` beneficiary redirect — `modules/pallets/relayer/src/withdrawal.rs` / `modules/pallets/relayer/src/accumulate.rs`

### Title
Shared nonce + identical signed payload lets a beneficiary-redirect signature be replayed to steal the full accumulated relayer fee balance - (File: modules/pallets/relayer/src/accumulate.rs)

### Summary
`pallet-relayer` derives the signed message for two functionally different authorizations from the exact same tuple `(nonce, StateMachine, beneficiary_bytes)`, and both consume the **same** `Nonce<T>` storage entry keyed by `(address, StateMachine)`. Because the SCALE encoding of `Vec<u8>` and `&[u8]` is identical, `withdrawal::message()` and `accumulate::beneficiary_message()` produce byte-identical Keccak-256 hashes for the same inputs. A signature a relayer authorizes for one narrow purpose (tagging a beneficiary for a specific fee-accumulation batch) is therefore also a valid signature for the unrelated `withdraw()` extrinsic, which immediately drains the relayer's entire currently accumulated `Fees` balance for that chain to the named beneficiary.

`withdraw()` builds its authorization hash as: [2](#0-1) 

Both hash `(nonce, StateMachine, beneficiary)` with no domain tag distinguishing "this authorizes a beneficiary redirect for a future fee credit" from "this authorizes an immediate withdrawal of the current balance." Both call sites also read and increment the **same** `Nonce<T>` map keyed by `(address, StateMachine)`: [3](#0-2) [4](#0-3) 

Since a relayer's `beneficiary_details` signature (submitted inside an unsigned `accumulate` extrinsic together with a state proof) is public the moment it hits the transaction pool/block, and since `withdraw()` only checks `signature.verify(&msg, None)` against the current `Nonce` value with no context binding it to "accumulate" vs "withdraw", the exact same `(nonce, chain, beneficiary)` signature can be submitted to `withdraw()` instead. `withdraw()` never re-derives or checks the delivery address from a state proof — it trusts whatever address the signature recovers to — so it will pay out `Fees::<T>::get(dest_chain, address)` (the *entire currently accumulated balance*, not just the fee amount the relayer intended to redirect) to the attacker-observed beneficiary, and zero the relayer's balance: [5](#0-4) 

Because whichever call (accumulate or withdraw) lands first consumes the shared nonce, this is a race on the same signed artifact rather than a benign duplicate: the relayer signed one action expecting a bounded, proof-gated credit, but the identical bytes authorize an unconditional, proof-free withdrawal of the account's whole current balance.

### Impact Explanation
This breaks the "funds move exactly once and only to the rightful beneficiary and amount" invariant for relayer rewards. A relayer intending to redirect the fee earned from one specific delivery batch (via `accumulate`'s `beneficiary_details`) can have their entire withdrawable balance for that chain siphoned to the same address through `withdraw()` using the identical signature, potentially before or instead of the intended narrow credit — loss of relayer funds and unauthorized-transaction execution.

### Likelihood Explanation
No privileged role, relayer collusion, or governance action is required — `accumulate` is an unsigned, permissionless extrinsic (`ensure_none(origin)`) and any beneficiary-redirect signature it carries is visible on-chain/in the mempool. Any party monitoring `accumulate` submissions (or the relayer itself, or a competing relayer, depending on who front-runs) can submit the observed signature to `withdraw()` before the intended `accumulate` call is included, since both consume the same nonce and hash the same tuple.

### Recommendation
Domain-separate the two signed payloads (e.g., prefix each message with a distinct constant such as `b"ACCUMULATE_BENEFICIARY"` vs `b"WITHDRAW"`) and/or use independent nonce counters for `accumulate`'s beneficiary redirection and `withdraw`'s balance withdrawal, so a signature valid for one action can never be replayed as authorization for the other.

### Proof of Concept
1. Relayer R delivers messages and calls `Pallet::accumulate` with `beneficiary_details = Some((B, sig))`, where `sig` is R's signature over `beneficiary_message(nonce_N, chain, B)` — intended only to redirect the fee from *this batch* to B.
2. Before this `accumulate` extrinsic is included, an observer extracts `sig` from the mempool/pending block.
3. The observer submits `Pallet::withdraw` with `WithdrawalInputData { signature: sig, dest_chain: chain, beneficiary: Some(B) }`. Because `message(nonce_N, chain, Some(B))` produces the identical hash `beneficiary_message(nonce_N, chain, B)` computes, `withdraw()`'s signature verification succeeds and recovers address R.
4. `withdraw()` reads `Fees::<T>::get(chain, R)` — the relayer's *entire* current balance, not just the pending batch's fee — dispatches a withdrawal of that full amount to beneficiary B, increments `Nonce(R, chain)`, and zeroes `Fees(chain, R)`.
5. The original `accumulate` call now fails/no-ops on the beneficiary nonce check (stale nonce) or, if it lands first, the sequence still lets a single relayer-issued signature drain the whole balance instead of only the intended per-batch fee. [6](#0-5)

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
