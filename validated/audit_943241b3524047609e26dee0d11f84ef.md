### Title
Persistent, unscoped `safe.directory` trust exception is never revoked, allowing later attacker-controlled content at the same path to be silently trusted - (File: `app/src/lib/git/config.ts`)

### Summary
GitHub Desktop's "Trust Repository" flow permanently whitelists a filesystem path in the user's **global** git config via `addSafeDirectory` whenever the user dismisses an "unsafe/dubious ownership" warning. This exception is written once and is never removed — not when the repository is removed from Desktop, not when it's deleted, and not when its ownership subsequently changes. Because the trust decision is bound only to a raw path string rather than to the specific repository/content the user reviewed at the time, an attacker who later gains control of content at that same path (shared machine, mapped/synced network drive, container mount, restored/re-provisioned path, etc.) inherits the user's earlier trust decision with no re-prompt and no ownership re-validation — mirroring the reported bug class where a delegated authority (`proposedOwner`) is granted once and never invalidated on a state change, letting it be redeemed later by whoever now controls it.

### Finding Description
When Desktop detects a repository with "dubious ownership" (git's own safety check, surfaced via `getRepositoryType` returning `{ kind: 'unsafe', path }` in `app/src/lib/git/rev-parse.ts:57-63`), the UI offers the user a "Trust Repository" action: [1](#0-0) [2](#0-1) 

Both call into: [3](#0-2) 

`addSafeDirectory` adds the path to the **global** `safe.directory` git config permanently (`addGlobalConfigValueIfMissing('safe.directory', path)`), which tells git to stop performing the ownership check for that exact path forever. There is no corresponding `removeSafeDirectory` function anywhere in the codebase, and the repository-removal code paths (`_removeRepository` in `app-store.ts`, `dispatcher.removeRepository`) never touch this config. The trust grant is:
- **Path-scoped only** — not tied to the repository identity (remote URL, initial commit, or the specific file contents the user reviewed).
- **Never expired or revoked** — even when the user removes the repository from Desktop, deletes the folder, or the underlying volume/mount is unmounted and later reassigned to different content.

This is structurally the same defect as the reported `proposedOwner` bug: a privileged state (`proposedOwner` / `safe.directory` entry) is set once, and none of the state-transition paths (`renounceOwnership`/`transferOwnership` vs. repository removal/relocation) reset it, so the stale grant can be redeemed later by whoever now controls the associated key (the proposed-owner address / the filesystem path).

### Impact Explanation
Any content an attacker manages to place at a path the victim previously trusted (e.g., a shared/multi-user machine, a network share, a cloud-sync folder, a container bind-mount reused across sessions, or a re-imaged drive letter) will silently bypass git's dubious-ownership protection the next time Desktop or the user's own git CLI operates on that path. Git's `safe.directory` mechanism exists specifically to prevent execution of repo-local configuration (hooks, `core.fsmonitor`, filters, etc.) supplied by an untrusted owner; once the exception is permanently registered, it defeats that protection indefinitely for anyone who later controls that path — enabling local code execution primitives normally blocked by the ownership check, without any renewed consent from the user.

### Likelihood Explanation
The attacker does not need prior malware or admin rights on the victim's primary account — they need only to end up controlling filesystem content at a path the victim once trusted (e.g., a compromised/attacker-writable network share, a shared workstation, or a synced folder scenario), which is exactly the threat model `safe.directory` was designed to defend against. Because Desktop's trust action is a one-click flow with no expiry, no path/repo binding beyond the raw string, and no cleanup on repository removal, the window during which a stale trust grant remains exploitable is unbounded.

### Recommendation
- Scope the trust exception to something that changes when repository identity/content changes (e.g., prompt again if the previously-recorded remote URL or initial commit hash no longer matches what's on disk), rather than trusting the bare path forever.
- Remove the corresponding `safe.directory` entry when the repository is removed from Desktop (mirror `_removeRepository`/`removeRepository` with a `removeSafeDirectory` call), and re-validate ownership/trust on every "Missing Repository" recovery rather than only on first encounter.
- Consider surfacing a periodic or on-relocate re-confirmation for previously trusted-but-currently-unsafe paths instead of a permanent, silent bypass.

### Proof of Concept
1. Victim uses Desktop on a machine where a directory `/shared/project` is (at that time) owned by another OS user; Desktop shows the "Trust Repository" warning.
2. Victim clicks "Trust repository" → `onTrustDirectory` → `addSafeDirectory('/shared/project')` → git's global config now contains `safe.directory=/shared/project` permanently.
3. Victim later removes the repository from Desktop (or the directory is deleted/unmounted). The `safe.directory` entry is **not** removed — confirmed by the absence of any `removeSafeDirectory`/cleanup call in `app-store.ts`'s `_removeRepository` or `repositories-store.ts`.
4. At a later time, an attacker (a different account on the shared machine, or whoever now controls that share/mount point) places a malicious git repository (with attacker-controlled hooks/config) at `/shared/project`.
5. When Desktop or git operates on that path again, git's ownership check is skipped entirely because the path is still in `safe.directory`, so the attacker's repository-local configuration/hooks execute without the "dubious ownership" warning ever reappearing. [4](#0-3)

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
