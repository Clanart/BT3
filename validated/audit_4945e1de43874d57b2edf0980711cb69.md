### Title
Integer division used as exponent in `calc-liq-factor-exp` truncates fractional liquidation curve exponents, producing an incorrect (overstated) graduated liquidation factor - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` implements the "apply curve exponent" step of graduated liquidation by computing `factor^(exp/BPS)` using Clarity's integer `pow`/`/`. It first performs `(/ exp BPS)` (an integer division) and then uses that truncated result as an exponent in a subsequent `pow`/multiplication chain. This is the same root-cause pattern as the reported `FluxToken.getClaimableFlux` bug — a division is carried out first and its truncated result is then fed into further multiplication/exponentiation — causing loss of precision that is baked into a financial outcome (here, the liquidation curve factor) rather than a harmless rounding of the final result.

### Finding Description
`calc-liq-factor-exp` is defined as: [1](#0-0) 

```clarity
;; Apply curve exponent for graduated liquidation
;; liq-factor = liq-factor^alpha
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

`exp` is the `LIQ-CURVE-EXP` egroup parameter, a bps-scaled continuous exponent (documented as "Exponent for graduated penalty curve", with examples such as `10000` = 1.0 and values `>10000` described as "Aggressive curve"): [2](#0-1) 

For the `exp > BPS` branch, the code computes `(/ exp BPS)` — an **integer division that truncates any fractional exponent** — and then uses that truncated integer as the actual exponent passed to `pow`. Any `exp` value that is not an exact multiple of `BPS` (10000) — e.g. `12000` (1.2), `15000` (1.5), `17500` (1.75) — has its fractional part silently discarded. E.g. for `exp = 15000`, `(/ exp BPS)` = `1` (should be `1.5`), so the function returns `factor^1` instead of `factor^1.5`.

This mirrors the report's exact bug class: division is performed before it is combined with further multiplication/exponentiation, so the loss of precision from the division propagates into (and dominates) the final computed value, rather than being a harmless least-significant-bit rounding of an already-final quantity.

This function feeds directly into the liquidation pricing path via `calc-liquidation-params`: [3](#0-2) 

`liq-pct-scaled` (the output of `calc-liq-factor-exp`) is then used to compute both `max-debt-usd` (via `calc-liq-debt-repay`, capping how much debt may be liquidated) and `liq-penalty` (via `calc-liq-factor-bound`, the liquidator's bonus/penalty), which are consumed inside the `liquidate` public function to determine actual debt repaid and collateral seized: [4](#0-3) 

### Impact Explanation
**Direction of error:** For `factor` (a fraction ≤ `BPS`, i.e. ≤ 1.0) and any `exp` strictly between two multiples of `BPS` (i.e., a non-integer alpha > 1), the mathematically correct `factor^alpha` is **smaller** than `factor` (since raising a fraction <1 to a power >1 decreases it). Because the code truncates `alpha` down to the next lower integer, it returns a value **larger** than the true `factor^alpha`. Concretely, for `exp=15000` (alpha=1.5) the code returns `factor^1 = factor` instead of the true `factor^1.5`, which for `factor=5000` (0.5) means the code returns `5000` instead of the true `≈3535`.

**Who profits / who loses:** An inflated `liq-pct-scaled` increases both `max-debt-usd` (more debt eligible for liquidation in one call) and `liq-penalty` (the liquidator's bonus percentage applied to collateral seized via `calc-liq-collateral-repay`). This means the **liquidator** extracts more collateral relative to debt repaid than the graduated curve is designed to allow, and the **borrower being liquidated** loses more collateral than intended by the egroup's configured curve. Since `LIQ-CURVE-EXP` is documented as a general continuous bps parameter (not restricted to multiples of 10000) and the design explicitly supports "aggressive" (>10000) curves as a normal configuration choice, this is a latent code defect reachable under legitimate (non-misconfigured) DAO parameter settings, not a registry-configuration accident.

### Likelihood Explanation
The bug triggers deterministically whenever an egroup's `LIQ-CURVE-EXP` is set to any value `> BPS` that is not an exact multiple of `BPS` (e.g., 11000, 12500, 15000, 17500, 19999). It does not require any oracle manipulation, DAO compromise, or misconfiguration — it is a pure arithmetic defect in the curve implementation that manifests for any position undergoing graduated (partial) liquidation while such an exponent is configured. I could not confirm from the indexed proposal files whether any currently deployed mainnet egroup uses a non-multiple-of-BPS exponent (the egroups I found in `mainnet/contracts/proposals/mainnet/v0-init.clar` and test proposals use `u20000`, an exact multiple, which does not trigger the bug), so likelihood under the *current* live configuration is uncertain; likelihood for any *future* egroup using a fractional curve exponent (a documented, intended use case) is high.

### Recommendation
Rework `calc-liq-factor-exp` to avoid using integer-divided `exp/BPS` as a `pow` exponent. Either:
- Restrict `LIQ-CURVE-EXP` to only accept exact multiples of `BPS` (validate at `egroup.insert`/update time) and document this restriction, or
- Implement a fixed-point exponentiation (e.g., a bps-based `pow-bps` using repeated squaring on a fixed-point base) that correctly handles fractional exponents rather than truncating them, keeping all division as late as possible in the computation.

### Proof of Concept
```clarity
;; illustrating the truncation with exp=15000 (alpha = 1.5), BPS = u10000
(define-constant BPS u10000)

;; buggy: (/ exp BPS) truncates 1.5 -> 1
(calc-liq-factor-exp u5000 u15000)
;; => (pow u5000 (/ u15000 u10000)) / (pow u10000 (- (/ u15000 u10000) u1))
;; => (pow u5000 u1) / (pow u10000 u0)
;; => u5000 / u1 = u5000

;; correct factor^1.5 for factor=0.5 (u5000/BPS) is ≈ 0.3535 => ≈ u3535 (bps-scaled)
```
The buggy path returns `u5000` while the mathematically correct graduated value is `≈ u3535` — a ~41% overstatement of `liq-pct-scaled`, which is then propagated into `max-debt-usd` and `liq-penalty`, inflating the collateral seized from the borrower during a partial liquidation whenever an egroup's `LIQ-CURVE-EXP` is a non-multiple of `10000` above `10000`.
