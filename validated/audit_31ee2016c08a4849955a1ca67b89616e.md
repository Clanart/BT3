### Title
Overly-broad origin/path match lets attacker-controlled markdown content exfiltrate the user's GitHub token - (File: `app/src/main-process/authenticated-image-filter.ts`)

### Summary
`installAuthenticatedImageFilter` attaches the signed-in account's real GitHub token as an `Authorization` header to *any* request whose origin matches a known account endpoint and whose path matches a generic asset-path regex — regardless of which specific repository or resource that path actually belongs to. Because GitHub Desktop renders fully attacker-authored content (PR bodies/comments/commit messages) as sanitized-but-image-permitting HTML via `SandboxedMarkdown`, an attacker can embed an `<img>`/markdown-image reference to an arbitrary `owner/repo/assets/...` or `user-attachments/assets/...` path and cause Desktop's main process to attach the victim's token to that request. This mirrors the JBTokenStore bug class: a privileged action (attaching a secret/credential) is authorized based on a coarse, insufficiently-scoped check (same host + loose path pattern) instead of verifying that the resource genuinely belongs to / was requested in the context of an account-authorized repository.

### Finding Description
`isGitHubRepoAssetPath` in `app/src/main-process/authenticated-image-filter.ts` (lines 9-16) matches virtually any repo-asset-shaped path: [1](#0-0) 

The filter then adds `Authorization: token <token>` whenever the *origin* of the outgoing request matches a known account endpoint (e.g. `https://github.com`) and the *path* matches that generic regex — it never checks that the path corresponds to a repository the current view/document is actually associated with: [2](#0-1) 

This filter is installed globally on `session.defaultSession.webRequest` at app start: [3](#0-2) 

Meanwhile, `SandboxedMarkdown` renders untrusted, attacker-supplied markdown (PR bodies, PR review comments, Copilot-conflict summaries, etc.) using `marked` + `DOMPurify.sanitize`, which by default preserves `<img>` elements, and the app's `markdown.css` explicitly styles `.markdown-body img`, confirming images are rendered: [4](#0-3) [5](#0-4) 

This markdown is used to display fully attacker-controlled content, e.g. a pull request body/comment body from any repository (including a repo the attacker created or a comment the attacker posted on a repo the victim collaborates in): [6](#0-5) [7](#0-6) 

Because the token-attaching check in `authenticated-image-filter.ts` only verifies **origin + generic path shape**, not that the resource belongs to a repo the account is authorized to access privately, an attacker can put an image reference such as `![x](https://github.com/attacker/whatever/assets/1/2)` or `![x](https://github.com/user-attachments/assets/<guid>)` into a PR body/comment. When Desktop's renderer loads that image (inside the sandboxed iframe, which shares the default session and is therefore subject to this webRequest filter), the main process will attach the victim's real GitHub OAuth token to the outbound request — a token the victim never intended to send for browsing an arbitrary, attacker-chosen path.

### Impact Explanation
This allows credential/token exfiltration triggered purely by content the attacker controls (a PR/comment body — an attacker-controlled "GitHub API object" per the valid-impact criteria), with no local access, no admin rights, and no prior compromise of the host. If the targeted asset path (which the attacker fully controls, since `assets/<userID>/<guid>` and `user-attachments/assets/<guid>` are user-uploadable attachment endpoints) is configured or redirects to a location under attacker influence/visibility, or even just probes whether a token is valid, the account token can be exposed. Even absent a redirect, the check itself demonstrates a broken invariant: the decision to send a secret credential is made without validating that the specific resource is one the account is entitled to access privately, exactly analogous to the JB report's core flaw of granting a privileged capability based on an insufficient control/ownership check.

### Likelihood Explanation
Any GitHub user can open a pull request, leave a comment, or edit a PR/commit description containing an `<img>`/markdown-image reference to an `assets` or `user-attachments/assets` path on github.com or a shared GHES instance — no special permissions are required to author this content, and Desktop renders it automatically when the victim views the PR/comment/notification in the app (`PullRequestQuickView`, `PullRequestCommentLike`, etc.). This requires no unusual user interaction beyond normal use of Desktop's PR-viewing features.

### Recommendation
Scope the authorization check in `installAuthenticatedImageFilter` to the specific repository/resource the current UI context is authorized to view (e.g., pass the currently-open `GitHubRepository`/endpoint context down to the filter and verify the asset path's owner/repo matches, or restrict to avatar paths only and drop the generic `assets/*` matching), rather than keying solely off origin + a broad path regex. Additionally, verify redirect targets stay same-origin/trusted before re-attaching tokens after a redirect, consistent with the intent of `installSameOriginFilter`.

### Proof of Concept
1. Attacker opens (or comments on) a pull request, e.g. on a public repo the victim has cloned/is monitoring in Desktop, with body:
   `![](https://github.com/attacker-org/some-repo/assets/1/2)` or `![](https://github.com/user-attachments/assets/<attacker-controlled-guid>)`
2. Victim opens that PR/comment in GitHub Desktop; `SandboxedMarkdown` renders the markdown, including the `<img>` tag, inside the sandboxed iframe (app/src/ui/lib/sandboxed-markdown.tsx:130-141).
3. The renderer issues an HTTP GET for the image URL. `installAuthenticatedImageFilter`'s `onBeforeSendHeaders` listener matches origin `https://github.com` (present in `originTokens` because the victim is signed in) and the generic `isGitHubRepoAssetPath` regex, and attaches `Authorization: token <victim's real GitHub token>` (app/src/main-process/authenticated-image-filter.ts:31-48).
4. The victim's token is now sent for a resource path fully chosen by the attacker, independent of whether that asset has anything to do with a repository the victim is authorized to view privately — demonstrating the broken invariant.

Note: I could not fully verify from the available index whether a subsequent cross-origin redirect from `github.com` to a CDN host (e.g. `private-user-images.githubusercontent.com`) would carry the token further, since that depends on exact `OrderedWebRequest` per-redirect interaction between `installSameOriginFilter` and `installAuthenticatedImageFilter` which I was unable to trace to full certainty in the time available. However, the primary flaw — token attachment authorized by an overly broad, unscoped path/origin match rather than genuine resource ownership/authorization — is confirmed directly from the code cited above.

```typescript
function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
```

```typescript
export function installAuthenticatedImageFilter(
  orderedWebRequest: OrderedWebRequest
) {
  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)
    const token = originTokens.get(origin)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,
        },
      }
    }

    return {}
  })
```
