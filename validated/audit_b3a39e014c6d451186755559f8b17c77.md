### Title
Quadratic work/memory amplification in MuSig binding-factor transcript permits remote denial of service - (File: crypto/dkg/musig/src/lib.rs)

### Summary
The CVE class is amplification: a small attacker-controlled input (an XML document with nested entities) causing exponentially disproportionate work during parsing/processing. The Serai analog lives in `musig_key_multiexp` / `musig` in `crypto/dkg/musig/src/lib.rs`. For every key in the caller-supplied key list, the code clones the entire binding-factor transcript — a buffer whose length is itself proportional to the number of keys — and then hashes the result. An attacker who supplies a key list of length `n` forces `O(n²)` bytes of copying and hashing from an `O(n)`-sized input, a linear-in-`n` amplification factor where a ~2 MB input produces ~137 GB of memcpy plus the same amount of Blake2/keccak hashing per `hash_to_F` call.

### Finding Description
`binding_factor_transcript` builds a `Vec<u8>` of size `context (32) + 2 + n * point_size` — roughly `32·n` bytes for a 32-byte-point ciphersuite [1](#0-0) . `musig_key_multiexp` then clones that whole vector inside the per-key loop and feeds each clone to `C::hash_to_F`, which hashes the entire buffer [2](#0-1) . The identical pattern is repeated in `musig`, which builds the transcript once more and clones it per key a second time [3](#0-2) .

`check_keys` bounds the list at `u16::MAX` (65 535) entries [4](#0-3) , so an attacker supplying a maximal list of 65 535 valid encoded points (~2 MB on the wire) causes:

- `binding_factor_transcript`: ~2 MB allocation,
- `musig_key_multiexp` loop: 65 535 clones of a ~2 MB vector ≈ 137 GB copied, plus 65 535 `hash_to_F` invocations each hashing ~2 MB ≈ 137 GB hashed,
- `musig`: the same again, ≈ 274 GB total work.

This is reachable from public inputs: `musig` and `musig_key_vartime` are public functions taking `keys: &[C::G]` — untrusted public keys proposed by an unprivileged counterparty for an n-of-n multisig / generator-promotion DKG context. A single party that can influence the key list (e.g., by registering many keys, or by the integrator aggregating keys supplied by participants) forces every honest party running `musig`/`musig_key_vartime` over that list into the quadratic computation before any signature or key-confirmation step can proceed. No threshold collusion, malicious node, or leaked key is required — only public keys the attacker causes to be processed.

### Impact Explanation
Denial of service against every honest participant performing MuSig aggregation over the attacker-influenced key set. One ~2 MB message yields on the order of 10¹¹ byte-copies and an equivalent volume of hashing, stalling the victim's DKG/signing pipeline (and, in a validator context, halting key generation or signing for the affected set) for a cost to the attacker of sending a single bounded message. This is the same class as CVE-2015-9541 — small input, disproportionate resource consumption — mapped onto Serai's actual attack surface.

### Likelihood Explanation
Medium. Exploitation requires the attacker to get a large key list into a victim's `musig`/`musig_key_vartime` call. Where the key set is fixed by a small validator set, the bound `n ≤ t` participants keeps `n` small and the impact minor; where keys are aggregated from untrusted registrants (e.g., open key-registration or Bitcoin wallet offset-registration flows built on these primitives), an unprivileged party can drive `n` toward the `u16::MAX` cap. The bug is deterministic and requires no race, no malformed encoding (all points are valid), and no special privileges.

### Recommendation
Do not clone the transcript per key. Either:
- Build the transcript once and append the 2-byte index `i` in place (extend, hash, truncate), or
- Use a streaming `Transcript`/digest: hash the shared prefix once into a reusable hasher state, clone the hasher (constant-size state) per key, and only extend it with `i.to_le_bytes()`.

This reduces the work from `O(n²)` to `O(n)` — one `hash_to_F`-sized hashing pass over the transcript plus `n` two-byte updates.

### Proof of Concept
```rust
// crypto/dkg/musig — conceptual PoC
// Any C: Ciphersuite with 32-byte GroupEncoding (e.g. Ristretto).
let context = [0u8; 32];

// Attacker supplies u16::MAX distinct valid public keys.
// Encoded size on the wire: 65535 * 32 bytes ~= 2 MB.
let keys: Vec<C::G> = (0 .. u16::MAX)
    .map(|i| C::generator() * C::hash_to_F(b"poc", &i.to_le_bytes()))
    .collect();

// Honest party aggregates the key set. Inside musig_key_multiexp:
//   for i in 1 ..= 65535 {
//     binding_factor(transcript.clone(), i)   // clones + hashes ~2 MB each iteration
//   }
// => ~137 GB copied and ~137 GB hashed inside musig_key_multiexp,
//    and again inside `musig`'s own loop (~274 GB total).
let _ = musig_key_vartime::<C>(context, &keys);   // quadratic DoS
```

The amplification factor equals `n`: input `O(n)`, work `O(n²)` — the structural analog of entity-expansion blowup, bounded only by the `u16::MAX` key cap rather than by any work limit proportional to input size.

fn check_keys<C: Ciphersuite>(keys: &[C::G]) -> Result<u16, MusigError<C>> {
  if keys.is_empty() {
    Err(MusigError::NoKeysProvided)?;
  }

  let keys_len = u16::try_from(keys.len())
    .map_err(|_| MusigError::TooManyKeysProvided { max: u16::MAX, provided: keys.len() })?;

  let mut set = HashSet::with_capacity(keys.len());
  for key in keys {
    let bytes = key.to_bytes().as_ref().to_vec();
    if !set.insert(bytes) {
      Err(MusigError::DuplicatedParticipant(*key))?;
    }
  }

  Ok(keys_len)
}

fn binding_factor_transcript<C: Ciphersuite>(
  context: [u8; 32],
  keys_len: u16,
  keys: &[C::G],
) -> Vec<u8> {
  debug_assert_eq!(usize::from(keys_len), keys.len());

  let mut transcript = vec![];
  transcript.extend(&context);
  transcript.extend(keys_len.to_le_bytes());
  for key in keys {
    transcript.extend(key.to_bytes().as_ref());
  }
  transcript
}

fn musig_key_multiexp<C: Ciphersuite>(
  context: [u8; 32],
  keys: &[C::G],
) -> Result<Vec<(C::F, C::G)>, MusigError<C>> {
  let keys_len = check_keys::<C>(keys)?;
  let transcript = binding_factor_transcript::<C>(context, keys_len, keys);
  let mut multiexp = Vec::with_capacity(keys.len());
  for i in 1 ..= keys_len {
    multiexp.push((binding_factor::<C>(transcript.clone(), i), keys[usize::from(i - 1)]));
  }
  Ok(multiexp)
}
