## Analog Found: Silent, Unconfirmed Rewrite of the `origin` Remote URL Based on GitHub API Data

### Title
Silent auto-rewrite of local `origin` remote URL from untrusted GitHub API `clone_url` with no user confirmation - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The external report's core complaint is that privileged state changes (fee updates) take effect **immediately, with no warning or time-lock**, so users can't be sure what a future action will do. GitHub Desktop has a direct analog: `updateRemoteUrl` silently overwrites the local repository's `origin` remote URL whenever the associated GitHub API repository object reports a different `clone_url`, with **no confirmation dialog, no notice, and no opportunity to review**, unlike the very similar "upstream remote" flow in the same codebase, which does prompt the user via `UpstreamAlreadyExists`.

### Finding Description
`updateRemoteUrl` is invoked automatically from `repositoryWithRefreshedGitHubRepository`, which runs during ordinary background operations — selecting a repository, adding a repository, and periodic refreshes — not from an explicit "change my remote" user action: [1](#0-0) 

The update function itself only checks that the URL *scheme* matches (`https` vs `ssh`) and that the previously-stored remote matched the old API-supplied clone URL — it does **not** verify the hostname/owner/repo stays the same before rewriting: [2](#0-1) 

Compare this to the sibling "upstream remote" flow (`updateExistingUpstreamRemote` / `ensureUpstreamRemoteURL`), which is gated behind an explicit dialog requiring user consent before the remote is changed: [3](#0-2) [4](#0-3) 

No such gate exists for the `origin` remote path — `gitStore.setRemoteURL` is called directly and unconditionally once the (weak) heuristic passes: [5](#0-4) [6](#0-5) 

The API repository object (`apiRepo`) that supplies the new `clone_url` is fetched using the owner/name/host derived from the *existing* remote via `matchGitHubRepository`, so the query target itself isn't attacker-chosen, but the **response content (`clone_url`) is fully attacker-influenced** whenever the underlying GitHub/GHES account or repository is under attacker control (e.g., a compromised or malicious GitHub Enterprise Server the user has added as an account, or a repository transfer/ownership change engineered by a malicious collaborator/owner): [7](#0-6) 

### Impact Explanation
Because the check is scheme-only (not host/owner/repo-only), an attacker-controlled `clone_url` with a matching protocol can redirect the user's `origin` remote to an entirely different host. Once corrupted, all subsequent `fetch`/`pull`/`push` operations the user performs through Desktop are silently redirected — this can result in:
- The user's next `push` sending proprietary/private commits to an attacker-controlled repository (data exfiltration).
- The user's next `fetch`/`pull` merging attacker-controlled history into their working copy (supply-chain/code-injection risk).
- Credential exposure if HTTPS credential helpers replay stored tokens against the new attacker host.

This directly matches the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" categories in the valid-impact scope, driven entirely by an attacker-controlled GitHub API object — no local access, admin rights, or social engineering step is required beyond the attacker's own control of a GHES account/repo object the user already trusts.

### Likelihood Explanation
The rewrite path fires automatically as part of routine, unprompted background refresh cycles (`_refreshRepository`, `_selectRepositoryRefreshTasks`, `_addRepositories`) rather than requiring any unusual user action: [8](#0-7) 

This makes the trigger conditions realistic (any time the app talks to the associated GitHub/GHES endpoint and gets back a differing `clone_url` for the matched owner/name), and the missing host-equality check means the "same protocol" guard is insufficient to prevent redirection to a different host.

### Recommendation
Apply the same explicit-confirmation pattern already used for the upstream remote flow (`UpstreamAlreadyExists`) to the `origin` remote auto-update path: never call `setRemoteURL` silently. Instead, when `updateRemoteUrl` detects a change, surface a dialog showing the current vs. proposed remote URL and require explicit user approval before applying it. Additionally, strengthen `updateRemoteUrl`'s heuristic to require host equality (not just protocol equality) before ever considering an automatic update, and treat cross-host changes as always requiring confirmation, analogous to introducing a "notice, then commit" two-step change for administrative settings as recommended in the original report.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop and clones a repository from it; Desktop stores `origin` pointing at `https://ghes.example.com/org/repo.git`.
2. The GHES instance (compromised, or an attacker with rename/transfer rights on that repo) is queried by Desktop's routine refresh (`repositoryWithRefreshedGitHubRepository` → `api.fetchRepository(owner, name)`), and returns an `IAPIFullRepository` whose `clone_url` is set to `https://attacker.example.com/org/repo.git` (same `https` scheme).
3. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (local remote still matches the previously known clone URL), and `urlsMatch === false` (new host differs) — the three conditions all evaluate as required, so it calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')` with zero user prompt.
4. The user's next "Push" or "Fetch" in Desktop silently targets `attacker.example.com`, exfiltrating their commits or importing attacker-controlled history, exactly matching the report's "administrators can make changes without warning" bug class, but reachable purely through an attacker-controlled API response object rather than any local/admin access. [9](#0-8)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
