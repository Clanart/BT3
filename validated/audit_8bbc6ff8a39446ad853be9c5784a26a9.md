### Title
Instant-dilution attack on `_provisionReward` allows front-running deposits to steal freshly queued rewards - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool._provisionReward` (invoked by `queueNewRewards`/`donateRewards`) distributes new rewards by dividing `_amountReward` by `totalStaked()` at the exact moment the reward is provisioned, then adding that per-token value to the global `rewardPerTokenStored`. Since `earned()`/`_updateFor` only look at a user's current `balanceOf()` and the stored index, a user who deposits a large amount of `stakingToken` immediately before a manager's `queueNewRewards` call captures a full pro-rata share of the reward instantly, with zero accrual time, diluting long-term stakers.

### Finding Description
`rewardPerTokenStored` is a single global accumulator updated only when `_provisionReward` runs: [1](#0-0) 

It computes `_amountReward * 10**decimals / totalStaked()` using `totalStaked()` at call time — not any time-weighted or checkpointed stake. `earned()` computes reward purely from current `balanceOf(_account)` multiplied by the delta between the global index and the user's last-paid index: [2](#0-1) 

`_updateFor` (called via the `updateReward` modifier on `getReward`, and callable directly via public `updateFor`) simply snapshots `earned()` into `userRewards` and sets `userRewardPerTokenPaid` to the current index: [3](#0-2) 

There is no mechanism that:
- Locks/streams rewards over time (e.g., a linear vesting rate as in Synthetix-style `rewardRate`/`periodFinish`), or
- Tracks per-block/per-second stake duration to weight rewards by time-of-holding.

Exploit flow:
1. Attacker observes a pending `queueNewRewards(largeAmount, token)` (or `donateRewards`) transaction in the mempool.
2. Attacker front-runs with `MasterMagpie.deposit(hugeAmount)` of `stakingToken` (self-funded or flash-loaned, since `stakingToken` for many of these pools, e.g. LP/receipt tokens, can be flash-borrowed or minted/burned atomically depending on the underlying protocol).
3. The manager's transaction executes `_provisionReward`, computing `rewardPerTokenStored` using the now-inflated `totalStaked()` — the attacker's huge deposit is already counted, so they get a share equal to `hugeAmount / totalStaked()` of the entire new reward, despite holding for effectively zero time.
4. Attacker calls `withdraw(hugeAmount)` on `MasterMagpie` right after (no cooldown/lockup enforced by `BaseRewardPool`) and then `getReward()` to claim `userRewards[token][attacker]`, which was fixed at withdrawal-time balance times the index delta.
5. Existing long-term stakers, whose balances didn't change, see their proportional share of the same reward pool diluted because a large portion of `_amountReward` was allocated to the attacker's newly-added, ephemeral balance.

No modifier (`updateReward`, `nonReentrant`, etc.) prevents this because reward accrual is index-based on instantaneous balance, not time-weighted; `deposit`/`withdraw` in `MasterMagpie` are normal unprivileged calls with no cooldown gating reward eligibility.

### Impact Explanation
This is a direct theft of unclaimed yield from legitimate long-term stakers. An attacker with access to a large amount of `stakingToken` (self-capital or via flash loan/mint against an LP/receipt token) can capture a disproportionate, near-instant share of every `queueNewRewards`/`donateRewards` reward injection, at the expense of all other depositors, repeatably for every future reward distribution. This matches the Immunefi impact class "theft of unclaimed yield" / "direct theft of user funds."

### Likelihood Explanation
Feasibility depends on:
- Whether `stakingToken` can be acquired in large size atomically (flash loan, flash mint, or large existing capital) — plausible for many LP/wrapper tokens used across the Magpie reward pools.
- Ability to front-run the manager's `queueNewRewards`/`donateRewards` transaction in the same block — feasible on public mempools (or via MEV/searcher infra), and `donateRewards` is completely permissionless (callable by anyone), making the "manager" precondition unnecessary for that variant — any attacker could self-trigger the front-run/back-run around a whale's `donateRewards` call or wait for a scheduled `queueNewRewards`.
- No cooldown or minimum holding period exists on `deposit`/`withdraw` at the `BaseRewardPool`/`MasterMagpie` level to prevent this, so it is repeatable every time new rewards are queued.

### Recommendation
Introduce time-weighted reward accrual instead of instantaneous-balance-weighted distribution, e.g.:
- Stream new rewards over a fixed duration (Synthetix-style `rewardRate` + `periodFinish`, updated per `lastUpdateTime`) rather than crediting the entire `_amountReward` to the current instantaneous `totalStaked()` in one shot.
- Alternatively, enforce a minimum staking duration / cooldown before a deposit's balance is eligible for freshly queued rewards (checkpoint balances and only count balances that existed prior to the reward-queuing block).
- Consider snapshotting `totalStaked()` and per-user balances at the start of a reward epoch rather than at the reward-injection instant.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (with `stakingToken`, a reward token, and a manager), fund several "long-term" stakers who `deposit(smallAmount)` and let several blocks pass (no rewards yet).
2. Simulate attacker: in the same block/transaction sequence,
   a. `attacker` calls `MasterMagpie.deposit(hugeAmount)` (mint/transfer `hugeAmount` of `stakingToken` to attacker beforehand to simulate flash loan availability).
   b. `manager` calls `rewardPool.queueNewRewards(rewardAmount, rewardToken)`.
   c. `attacker` calls `MasterMagpie.withdraw(hugeAmount)`.
   d. `attacker` calls `getReward()`/`updateFor(attacker)` and reads `earned(attacker, rewardToken)`.
3. Assert: `earned(attacker, rewardToken)` ≈ `rewardAmount * hugeAmount / totalStakedAtProvisionTime`, i.e., a large, non-trivial share of the total reward, despite the attacker holding stake for exactly one block/transaction.
4. Assert: long-term stakers' `earned()` amounts are less than what they would have received had the attacker's deposit not occurred (i.e., `rewardAmount * smallAmount / (totalStaked_without_attacker)` vs. the diluted actual value), demonstrating measurable dilution/theft of yield.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
