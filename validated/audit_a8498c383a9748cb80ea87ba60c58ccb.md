### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s, causing constructed spends to be unexecutable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The Governor report describes an approved action that cannot be executed because a required resource (ETH) cannot be supplied at execution time, producing unexpected failures only when execution is attempted. The Serai analog lives in `networks/bitcoin/src/wallet/mod.rs`: `Scanner::scan_block` scans every transaction in a block, including `txdata[0]` — the coinbase transaction. Outputs from coinbase transactions are bound by Bitcoin's 100-block maturity rule and are not spendable until maturity. Yet `scan_block` wraps them in `ReceivedOutput`, a type documented as "A spendable output", indistinguishable from normally spendable outputs. Downstream, `SignableTransaction::new` and `SignableTransaction::multisig` will happily build and fully sign a transaction spending an immature output, which Bitcoin consensus then rejects — the exact shape of the Governor bug: everything succeeds until execution, which fails for a reason invisible at proposal/scan time.

### Finding Description
`ReceivedOutput` is defined as "A spendable output" carrying the scalar `offset`, the `TxOut`, and the `OutPoint` needed to spend it (mod.rs:88–97). `Scanner::scan_transaction` credits any output whose `script_pubkey` matches a registered script (mod.rs:199–213) with no regard to which transaction in the block produced it. `Scanner::scan_block` then iterates `block.txdata` from index 0 (mod.rs:221–227), so the coinbase transaction's outputs are returned as `ReceivedOutput`s alongside spendable ones.

Bitcoin consensus requires coinbase outputs to mature for 100 blocks (BIP-30 / consensus rule `COINBASE_MATURITY`). A `ReceivedOutput` referencing an immature coinbase outpoint feeds directly into `SignableTransaction::new` (send.rs:150), which validates amounts, fees, and dust — none of which detect immaturity — and into `TransactionSignMachine::sign` (send.rs:355), which produces valid signatures over it. The resulting transaction is rejected by the network only at broadcast/inclusion time.

Notably, the in-scope code itself acknowledges the hazard only in a doc comment (mod.rs:216–220: "If received outputs must be immediately spendable, a post-processing pass is needed"), and `processor/src/networks/bitcoin.rs` already works around it by iterating `block.txdata[1 ..]` instead of calling `scan_block`. But `scan_block` remains a public API returning mislabeled, non-spendable outputs, and `ReceivedOutput` carries no marker distinguishing immature coinbase outputs.

### Impact Explanation
Any consumer using `scan_block` as documented (the natural API for block scanning) receives outputs it believes are spendable. Plans built on them consume FROST signing rounds — `multisig`, `preprocess`, `sign`, `complete` all execute successfully — and produce a transaction that cannot be included in any block until maturity. Depending on the caller's error handling, this either silently discards a "received" balance from usable inputs or permanently wedges a spend that references the immature outpoint. This matches the Governor consequence: an approved/constructed action whose required precondition (mature inputs, deposited ETH) is absent at execution.

### Likelihood Explanation
The trigger requires only that a miner pay the scanned Taproot script via a coinbase output, or that a block be scanned containing a coinbase paying the key — an event fully controlled by an unprivileged external party (any miner) rather than by the Serai operator. It does not require malicious validators, collusion, or leaked keys; it requires only an ordinary on-chain transaction (the coinbase) that any mining party can cause to exist. Severity is Medium: it is a correctness/availability fault for funds handling — reported-received funds that are not spendable — not a forgery or key recovery.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (or return coinbase outputs in a separately tagged form), and/or add an `is_coinbase`/maturity flag on `ReceivedOutput` so callers cannot treat immature outputs as spendable. Alternatively, return `None`/`Err` from `scan_block` and expose only `scan_transaction`, forcing callers to make the coinbase decision explicitly — mirroring the Governor fix's caveat that the funding requirement must be visible at the point the action is constructed, not discovered at execution.

### Proof of Concept
```rust
// networks/bitcoin — conceptual, against regtest
let scanner = Scanner::new(key).unwrap();

// A miner (or `generatetoaddress` in regtest) pays the scanned script
// via the coinbase transaction.
rpc.rpc_call::<Vec<String>>(
  "generatetoaddress",
  serde_json::json!([1, Address::from_script(&p2tr_script_buf(key).unwrap(),
                     Network::Regtest).unwrap()]),
).await.unwrap();

let block = rpc.get_block(&rpc.get_block_hash(1).await.unwrap()).await.unwrap();
let outputs = scanner.scan_block(&block); // includes block.txdata[0] — the coinbase
assert_eq!(outputs.len(), 1); // a "spendable" ReceivedOutput for an immature output

// Building and signing a spend succeeds entirely:
let tx = SignableTransaction::new(
  outputs, &[(p2tr_script_buf(key).unwrap(), 1000)], None, None, FEE,
).unwrap(); // Ok — immaturity never checked
let signed = sign(&keys, &tx); // valid signatures produced

// Broadcast fails: consensus rejects spending an immature coinbase output.
rpc.send_raw_transaction(&signed).await.unwrap_err(); // "bad-txns-premature-spend-of-coinbase"
```

The asymmetry is already visible in-tree: `processor/src/networks/bitcoin.rs:691` deliberately uses `block.txdata[1 ..]` rather than `scan_block` precisely because the latter returns the maturity-burdened coinbase — confirming `scan_block`'s return values are not actually spendable as `ReceivedOutput` claims.
