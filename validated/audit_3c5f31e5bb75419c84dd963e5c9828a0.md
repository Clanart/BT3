## Analysis

The Connext report's broken invariant is: **a privileged capability (token allowance) is handed out based on a coarse, attacker-influenceable match, and nothing scopes it to the specific transaction it was meant for** — the executor grants an allowance sized for the whole `_args.amount` to `_args.to`, and nothing constrains how much of it that untrusted recipient can actually consume, so callers can walk away with more than intended.

The same broken-invariant shape exists in GitHub Desktop's credential trampoline. Desktop's own stored GitHub credential is handed out to *any* URL whose **origin** matches a signed-in account's endpoint — with no check that the URL corresponds to the specific remote or repository the user actually intended to operate on, and, for known GitHub accounts, **without any confirmation prompt**.### Title
Silent, unscoped disclosure of stored GitHub credentials to attacker-chosen same-origin URLs via submodule/LFS remotes - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`, `app/src/lib/trampoline/find-account.ts`)

### Summary
The Connext finding boils down to: a capability (token allowance) is granted based on a coarse match to an untrusted call, with no verification that the actual consumer is the one the grant was meant for, and nothing bounds how it gets used. The Desktop analog is the trampoline credential helper's `getGitHubCredential`, which authorizes any git credential request whose **origin** matches a signed-in account's endpoint (e.g. `github.com`), regardless of which repository/path is being requested and regardless of whether that request was even initiated by the operation the user intended. Because this match is silent (no user prompt) for known GitHub accounts, and because the trampoline's credential-helper env vars (`DESKTOP_TRAMPOLINE_TOKEN`, `GIT_CONFIG_PARAMETERS` setting `credential.helper=desktop`) are propagated to the whole process tree of a git operation — including submodule fetches and LFS filter subprocesses — a cloned/fetched repository can steer Desktop into silently attaching the user's real GitHub token to a fetch targeting an arbitrary path under the matched origin that the repository author controls (via `.gitmodules` or `.lfsconfig`), not the repository the user actually opened.

### Finding Description
`getGitHubCredential` in `app/src/lib/trampoline/trampoline-credential-helper.ts` (lines 50-57) is invoked for every `git credential fill` request coming from any git subprocess during a Desktop-initiated operation:

```ts
async function getGitHubCredential(cred: Credential, store: AccountsStore) {
  const endpoint = `${getCredentialUrl(cred)}`
  const account = await findGitHubTrampolineAccount(store, endpoint)
  if (account) {
    info(`found GitHub credential for ${endpoint} in store`)
  }
  return credWithAccount(cred, account)
}
```

`findGitHubTrampolineAccount` (`app/src/lib/trampoline/find-account.ts` lines 20-29) matches purely on URL **origin**:

```ts
export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
```

If a match is found, `credWithAccount` immediately returns the real account credential (login + OAuth token) — see `getCredential` (lines 93-135), where `if (ghCred) return ghCred` short-circuits with **no user prompt**, unlike the generic-credential path (`promptForCredential`, lines 59-65) which does prompt.

This credential helper is wired into every git subprocess through `withTrampolineEnv` (`app/src/lib/trampoline/trampoline-environment.ts` lines 93-147), which deliberately sets `GIT_CONFIG_PARAMETERS` (rather than a `-c` argument) specifically so that **filters** such as Git LFS inherit the credential-helper configuration, per the comment at lines 127-133:

> "we want commands invoked by filters (i.e. Git LFS) to be able to pick up our configuration. Arguments passed to git commands are not passed down to filters."

The same environment is inherited by `git submodule` subprocesses spawned during `git pull --recurse-submodules` (`app/src/lib/git/pull.ts`) and `git fetch` with submodule recursion (`app/src/lib/git/fetch.ts`).

The broken invariant: **the credential grant is not scoped to the remote/URL the user actually intended to operate on** — it is scoped only to "same origin as a known account," and the origin/path actually contacted is determined by content inside the cloned/fetched repository (`.gitmodules` submodule URLs, or `.lfsconfig`/`.gitattributes` LFS remote URLs), which is fully attacker-controlled. Nothing in `getGitHubCredential` checks that `endpoint` corresponds to the repository's configured `origin` remote, nor does it ask the user to confirm before handing out the real token to a different path under the same host.

### Impact Explanation
A malicious public repository can declare a submodule (`.gitmodules`) or an LFS remote (`.lfsconfig`) pointing at `https://github.com/<victim-org>/<private-or-unrelated-repo>.git`. When the victim clones/pulls the malicious repo with Desktop (which recurses submodules by default and auto-invokes the LFS filter for any attributes-tagged file), git will issue a credential request for that attacker-chosen URL. Since its origin is `github.com`, `getGitHubCredential` silently supplies the victim's real signed-in GitHub token as Basic Auth to fetch/authenticate against a repository the victim never intended to touch — with no dialog, confirmation, or indication to the user. This can be used as an authorization oracle (does the fetch/LFS handshake succeed or fail against a target repo — revealing whether the victim has access to a private repository they didn't ask to interact with) and, depending on the operation triggered by the crafted `.gitmodules`/`.lfsconfig` (e.g. LFS "lock" or object-upload semantics), could result in unintended authenticated write actions being performed against unrelated repositories using the victim's credentials — all without the victim clicking through any credential prompt, matching the "unprivileged issue where attacker controls a cloned/fetched repository … credential/token exfiltration" impact category.

### Likelihood Explanation
This requires no special local access or social engineering beyond the normal act of cloning or pulling a repository in Desktop — an action Desktop actively facilitates (submodule recursion is on by default in `pull`/`fetch`, and LFS filter invocation happens automatically for tracked files). The attacker only needs to publish a public repository with a crafted `.gitmodules`/`.lfsconfig`; no interaction beyond "clone/open this repo" is needed from the victim. The lack of a confirmation prompt for GitHub-matched credentials (in contrast to the generic-credential path, which does prompt) removes the one guard that would otherwise surface this to the user.

### Recommendation
- Scope `getGitHubCredential`/`findGitHubTrampolineAccount` to the repository's actual configured remote(s) (or an explicit allow-list per trampoline session) rather than matching on host origin alone.
- Require explicit user confirmation before releasing a stored GitHub token to any URL not matching the repository's own `origin`/tracked remotes, especially for URLs sourced from repository-controlled files such as `.gitmodules` or `.lfsconfig`.
- Consider tagging the trampoline token/session with the specific remote(s) the operation was launched for, and reject credential requests for other hosts/paths unless the user is prompted.

### Proof of Concept
1. Attacker publishes a public GitHub repository `attacker/lure` containing:
   - `.gitmodules` with a submodule URL `https://github.com/victim-org/private-repo.git`, or
   - `.gitattributes` marking a tracked file with `filter=lfs` and an `.lfsconfig` setting `[lfs] url = https://github.com/victim-org/private-repo.git/info/lfs`.
2. Victim, signed into GitHub Desktop with an account that has some standing relationship to `github.com`, clones or pulls `attacker/lure` (Desktop recurses submodules per `app/src/lib/git/pull.ts`/`fetch.ts`, and auto-invokes LFS smudge filters for attributed files).
3. Git (or the git-lfs filter subprocess, inheriting `GIT_CONFIG_PARAMETERS`/`DESKTOP_TRAMPOLINE_TOKEN` from `withTrampolineEnv`) issues a `git credential fill` request for `https://github.com/victim-org/private-repo.git`.
4. `getGitHubCredential` → `findGitHubTrampolineAccount` matches origin `github.com` against the victim's signed-in account and returns the real token/login with no prompt (`trampoline-credential-helper.ts` lines 50-57, 93-99).
5. The victim's token is transparently used to authenticate against `victim-org/private-repo` — a repository unrelated to `attacker/lure` — revealing access/existence information (via success/failure) or performing whatever action the crafted submodule/LFS request triggers, without any user-visible confirmation.
