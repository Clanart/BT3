## Title
Payout OP_RETURN operator attribution is unauthenticated, allowing reimbursement credit to be assigned to an operator who never funded the payout - ([File: core/src/builder/transaction/operator_reimburse.rs])

## Summary
The `create_payout_txhandler` function embeds the "fronting" operator's x-only public key in an `OP_RETURN` output of the payout transaction, but this output is not covered by the withdrawing user's signature. The verifier's block-sync logic (`update_finalized_payouts`) later reads this `OP_RETURN` value verbatim and stores it as the authoritative "payer" for that withdrawal, with no check that the named operator actually signed or funded the transaction. This breaks the custody binding "the operator credited versus the party that paid."

## Finding Description
`create_payout_txhandler` builds the payout transaction with a single input (the user's withdrawal UTXO) and three outputs: the user payout, an anchor, and an `OP_RETURN` carrying `operator_xonly_pk`: [1](#0-0) 

The only signature attached to the transaction is the user's key-spend signature on input 0 (`set_p2tr_key_spend_witness(&user_sig, 0)`). Callers of `withdraw` are explicitly required to use `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`: [2](#0-1) 

Under `SINGLE|ANYONECANPAY`, the user's signature only commits to input 0 and the single output at the same index (the payout output). The anchor output and, critically, the `OP_RETURN` output containing `operator_xonly_pk` are **not** covered by the signature at all. This means anyone in possession of a valid `in_signature`/`in_outpoint` pair (which, by design, is shared "off-chain" with the operator set so that any operator may race to service a withdrawal, and which is visible to anyone who observes a payout transaction being relayed/broadcast) can construct their own version of the payout transaction, keep the user output unchanged (satisfied by `SIGHASH_SINGLE`), and put an **arbitrary operator's `xonly_pk`** — including one belonging to a different, unrelated, honest operator — into the `OP_RETURN`.

The verifier then reads this unauthenticated field directly from the mined transaction and persists it as ground truth for who is owed reimbursement: [3](#0-2) [4](#0-3) 

Downstream, reimbursement/kickoff validation only checks that the kickoff's `operator_xonly_pk` matches this stored value — never that the named operator actually broadcast or funded the payout: [5](#0-4) [6](#0-5) 

This is structurally the same class of bug as the referenced `Manager.addToken` finding: an entry in a custody-relevant mapping (`withdrawal_idx -> payer operator`) can be written/overwritten by an unauthenticated party without any check binding it to the true source of value, corrupting the "who actually paid" bookkeeping that later custody decisions (reimbursement) rely on.

## Impact Explanation
Because the operator attribution is not cryptographically bound to the actual broadcaster/funder of the payout, an attacker who is not a registered operator (or a party unrelated to the actual funding) can name any legitimate, registered operator as the payer of a withdrawal they never funded. That named operator can subsequently submit a kickoff and be reimbursed by the bridge (via BitVM circuit verification and verifier bookkeeping) for a payout it never made — this is exactly the Critical impact category "an operator reimbursed for a payout it never funded." Conversely, it also permanently corrupts the payer record for that withdrawal (`withdrawals.payout_payer_operator_xonly_pk`), which can make it impossible for the real, honest operator who actually funded the withdrawal to be reimbursed for it (their kickoff will always mismatch the recorded payer and be treated as malicious), matching "an honest operator permanently unable to be reimbursed."

## Likelihood Explanation
Exploitation requires only the ability to construct and broadcast a Bitcoin transaction using a validly obtained `(in_signature, in_outpoint)` pair for a pending withdrawal — no verifier, operator, watchtower, or other privileged role is needed to perform the substitution itself, since the `OP_RETURN` is not protected by any signature. The user's `SIGHASH_SINGLE|ANYONECANPAY` signature is, by protocol design, distributed to the operator set (and observable once any payout attempt reaches the mempool) specifically so that multiple parties can race to satisfy a withdrawal, making a mismatched/malicious `OP_RETURN` substitution straightforward for anyone who obtains it.

## Recommendation
Bind the fronting operator's identity to the payout transaction cryptographically rather than via an unsigned `OP_RETURN`: require the operator to co-sign the payout transaction (e.g., an additional operator signature over the whole transaction, or hashing the operator pubkey into the sighash that the user signs), or otherwise ensure the sighash flags cover the `OP_RETURN` output so it cannot be altered by a third party. Additionally, `update_payout_txs_and_payer_operator_xonly_pk` should validate that a claimed operator has authorized/funded the specific payout before recording it as the payer of record.

## Proof of Concept
1. User creates a withdrawal on Citrea and produces `in_signature` over the withdrawal input using `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, shared off-chain with the operator set (as intended by protocol design) or observed once broadcast to the mempool.
2. An attacker (or any operator) builds their own payout transaction using `create_payout_txhandler` with the same `input_utxo`, `output_txout`, and `user_sig`, but sets `operator_xonly_pk` to a different, honest, registered operator `O`'s x-only pubkey rather than their own.
3. Because `SIGHASH_SINGLE|ANYONECANPAY` only commits to input 0 and output 0, the modified `OP_RETURN` (output 2) does not invalidate the user's signature; the transaction is valid and confirms on-chain.
4. `update_finalized_payouts` in `core/src/verifier.rs` parses the `OP_RETURN`, extracts `O`'s pubkey, and stores it via `update_payout_txs_and_payer_operator_xonly_pk` as the payer for that withdrawal.
5. Operator `O` (or anyone controlling `O`'s key) later submits a kickoff; `is_kickoff_malicious` and `send_asserts` validate only that the kickoff's operator matches the stored payer pubkey, which it does — `O` is reimbursed for a payout `O` never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
