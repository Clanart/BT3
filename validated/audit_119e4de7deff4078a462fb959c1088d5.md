### Title
`ThresholdKeys::read` accepts attacker-crafted, semantically inconsistent key shares — deserialized secret share is never verified against verification shares or group key - (File: crypto/dkg/src/lib.rs)

### Summary
The extlib bug class is *unrestricted casts of attacker-controlled strings*, i.e. a deserializer that accepts untrusted input and instantiates an object whose semantic type/consistency is never checked (YAML/Symbol object injection). The Serai analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs:574-632`: it reconstructs a full `ThresholdKeys` from raw untrusted bytes — curve ID, `t`, `n`, `i`, interpolation variant and coefficients, `secret_share`, and all `n` verification shares — and `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) performs only structural checks (count, index range, `t == n` for Constant interpolation). It never verifies the fundamental invariant `verification_shares[i] == secret_share * G`, nor that the shares interpolate to any particular group key. The group key is simply *derived* from whatever shares were supplied (`crypto/dkg/src/lib.rs:376-378`).

### Finding Description
`ThresholdKeys::read` parses, in order:

1. `C::ID` — checked only against the expected curve, not against any expected key identity (`lib.rs:578-588`).
2. `t, n, i` — validated by `ThresholdParams::new` only for `t <= n`, `i <= n`, non-zero (`lib.rs:591-602`).
3. Interpolation tag 0/1, with `n` unchecked-coefficient scalars for `Constant` (`lib.rs:604-616`).
4. `secret_share` — a raw scalar, accepted unconditionally (`lib.rs:618`).
5. `n` verification-share points — each only checked for canonical encoding (`lib.rs:620-623`).

`ThresholdKeys::new` then computes `group_key` as the interpolation of shares `1..=t` (`lib.rs:376-378`) and stores everything in `ThresholdCore`. Nowhere is `secret_share` cross-checked against `verification_shares[i]`. This is directly acknowledged downstream: `AlgorithmSignatureMachine::complete` contains a fallthrough error for "everyone had a valid share yet the signature was still invalid", whose only documented cause is "to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs:491-494`) — the codebase knows the deserialized object can be internally inconsistent but does not prevent it.

Two attacker-useful constructions:

- **Group-key substitution**: the attacker picks a secret `x` they know, sets every `verification_shares[j] = x_j * G` with `Lagrange` interpolation so the interpolated `group_key` has a discrete log known to the attacker, and sets `secret_share` / `verification_shares[i]` consistently so the victim's own share verification passes. The victim then runs FROST believing they sign for the real multisig key while actually producing valid signatures under an attacker-known key — and, more critically, any deposit/output-scanning keyed off `group_key()` (e.g. `p2tr_script_buf` / `register_offset` in `networks/bitcoin/src/wallet`) attributes outputs to a key the group cannot spend from but the attacker can.
- **Silent share poisoning**: `verification_shares[i] != secret_share * G` causes every signature share the victim produces to fail `verify_share`, inducing persistent denial of signing while appearing to be a valid key blob.

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` (the prompt's own reachable-sink list includes `ThresholdKeys::read`; key blobs are transported/restored across provisioning, backup, and coordinator hand-off flows) obtains a confused object the rest of the stack treats as authoritative. `view()`/`group_key()` (`lib.rs:445-447`, `523-533`) then drive signing-set formation and Bitcoin output scanning under the substituted key. Consequence: concrete signing under an attacker-chosen group key and funds reported received that are not spendable by the group — matching the required impact classes.

### Likelihood Explanation
Requires delivering a crafted serialization to a deserializing party rather than merely a network message, which lowers likelihood versus pure-remote bugs. However the format is fully attacker-controlled field-by-field, needs no secret knowledge to construct (any `x` works), and no checksum, MAC, or integrity tag exists in `write`/`read` (`lib.rs:538-562`) to detect substitution. The resulting failure mode (unattributable-to-attacker key) gives the attacker plausible deniability.

### Recommendation
In `ThresholdKeys::new` (or `read`), verify `verification_shares[params.i()] == C::generator() * secret_share` and reject otherwise. Where the expected group key is known to the caller (it is, in Serai's flows), compare `group_key()` against the expected key after deserialization. Optionally MAC/sign serialized key blobs.

### Proof of Concept
```rust
// Attacker builds a blob where the group key's discrete log is known to them
let x = C::F::random(rng);                    // attacker-known group secret
let n = 2u16; let t = 2u16;                   // e.g. Constant interpolation
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes()); blob.extend(n.to_le_bytes());
blob.extend(1u16.to_le_bytes());              // victim is participant 1
blob.push(0);                                 // Interpolation::Constant
for _ in 0 .. n { blob.extend(C::F::ONE.to_repr().as_ref()); } // coeffs
blob.extend(x.to_repr().as_ref());            // secret_share = x
for _ in 0 .. n { blob.extend((C::generator() * x).to_bytes().as_ref()); }
// ThresholdKeys::read succeeds; group_key() == 2*x*G whose dl attacker knows
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// keys passes all structural checks; victim will sign under attacker-controlled key
```
Self-consistency (`verification_shares[i] == secret_share*G`) is satisfied here, so even a share-consistency check alone would not catch it — the group key must additionally be authenticated against the expected value.
