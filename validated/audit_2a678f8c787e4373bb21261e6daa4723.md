## Finding: Stale, index-based partial-commit line selections silently survive a working-directory refresh and can include unintended content

### Title
Partial-commit line selections are reused by line index (not content) across working-directory refreshes, causing silent inclusion of unreviewed diff content in a commit - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
This is the same bug class as the audited `withdraw_reserve_amount` issue: an operation mutates the real underlying state (a `git diff`), but a cached, derived value (`DiffSelection`, keyed by *line index*) is not re-validated against the new state before being trusted for a security/integrity-sensitive action — here, deciding exactly which bytes get written into a Git commit.

### Finding Description
When the user partially selects lines in a diff to commit, Desktop stores the selection as a set of *line indices* in `DiffSelection` [1](#0-0) , not as a content-addressed selection. That `DiffSelection` is later replayed against the diff purely by absolute index when the patch is built: `file.selection.isSelected(absoluteIndex)` [2](#0-1) .

The working directory is periodically refreshed (after fetch, checkout, background status polls, etc.) via `updateChangedFiles`, which explicitly preserves each file's existing (possibly partial) `DiffSelection` object whenever `clearPartialState` is `false`, regardless of whether the file's on-disk diff has changed shape in the meantime: `return file.withSelection(existingFile.selection)` [3](#0-2) . `_refreshRepository`, which fires after fetch/pull/merge/checkout, explicitly calls this path with `clearPartialState: false` [4](#0-3) .

When the diff is subsequently reloaded, `updateChangesWorkingDirectoryDiff` only recomputes the *set of selectable line indices* from the new hunks and reapplies the old (index-based) selection on top of them — the code comment itself acknowledges this is a known gap: "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [5](#0-4) .

Because the selection is never re-validated by content, if the diff for the selected file shifts (new hunks inserted earlier in the file, hunk boundaries change, etc.) between the time the user reviewed and checked specific lines and the time the commit patch is generated, the *same line indices* can now correspond to *different, unreviewed content*. The integrity check that the reserve-details bug lacked — "does the cached value still match reality after the state-changing operation?" — is likewise missing here for partial selections.

### Impact Explanation
This breaks the core invariant users rely on when doing partial/line-level commits in a GUI Git client: what you visually selected is what gets committed. If the working tree content shifts between selection and commit — e.g., due to a background refresh, an external process, a smudge/clean filter, or a checkout/merge hook triggered by fetching from an attacker-controlled remote — the user can unknowingly commit and push lines they never reviewed or explicitly excluded (or vice versa, omit lines they intended to include). This is "silent corruption of what the user commits," one of the explicitly in-scope impact categories, without any local/physical access or malware required beyond the attacker controlling the fetched repository's content/hooks.

### Likelihood Explanation
Requires a specific ordering: the user must have a *partial* selection on a file, and the working-directory diff for that same file must change shape (not just content) before the commit is executed, while the file remains selected via the same file ID. `clearPartialState: false` is the normal, everyday code path for background/foreground repository refreshes (fetch, checkout, `_refreshRepository`), so the window is not contrived. A malicious repository could deliberately arrange for a post-checkout/post-merge hook or filter to rewrite the working tree file precisely to exploit index misalignment while a partial selection is outstanding, making exploitation feasible without unnatural user steps (the user is simply doing a normal partial commit while Desktop performs one of its many automatic background refreshes).

### Recommendation
Re-validate partial `DiffSelection` state against actual diff *content* (not just line count/position) whenever the working-directory diff is reloaded, similar to a content hash or line-text comparison per hunk, and clear/renegotiate the partial selection (falling back to "select none" or re-prompting the user) whenever the underlying diff content for previously selected lines can no longer be matched with confidence — rather than only updating the "selectable lines" set as done today in `app-store.ts`'s `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has a diff with several hunks; select (via line clicks) only specific lines from one hunk to commit (leaving the rest unselected) — do not commit yet.
2. While the partial selection is pending, trigger a working directory refresh in a way that reshapes the same file's diff without changing the selected file's identity — e.g. run a `post-checkout`/`post-merge` hook (or clone a repository whose remote content/hooks rewrite the file) that inserts new lines earlier in the file, shifting subsequent line numbers, then let Desktop's `_refreshRepository`/background poll run (`clearPartialState: false`).
3. Observe that Desktop still shows the same "N lines selected" indicator carried over from `updateChangedFiles`'s `file.withSelection(existingFile.selection)`.
4. Commit. Inspect the resulting commit's patch and confirm that the committed lines (chosen by `file.selection.isSelected(absoluteIndex)` in `patch-formatter.ts`) no longer correspond to the content the user actually reviewed and checked before the refresh — different/unintended lines were included or excluded because the selection was replayed by index against a changed diff.
