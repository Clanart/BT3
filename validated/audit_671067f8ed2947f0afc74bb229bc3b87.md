### Title
`operator_acks_vec` Allocated with Deposit-Specific Watchtower Count While `validate_assertions_for_additional_script` Expects MAX_NUMBER_OF_WATCHTOWERS (160) Entries, Permanently Blocking the Disprove Path - (File: `core/src/verifier.rs`)

### Summary

In `verify_additional_disprove_conditions`, the `operator_acks_vec` is allocated with `deposit_data.get_num_watchtowers()` entries (e.g., 4 for a 4-verifier, 0-extra-watchtower deployment), but the additional disprove script is built with `create_additional_replacable_disprove_script_with_dummy` which pads the challenge-ack hash slots to `MAX_NUMBER_OF_WATCHTOWERS` (160). When `validate_assertions_for_additional_script` iterates over all 160 script slots and indexes into `operator_acks_vec`, it panics on any index ≥ `num_of_watchtowers`. This permanently blocks the additional disprove path, allowing a fraudulent operator to escape slashing and steal bridged BTC.

### Finding Description

In `verify_additional_disprove_conditions` (`core/src/verifier.rs`), the vector that carries operator challenge-ack preimages is allocated based on the deposit-specific watchtower count:

```rust
let num_of_watchtowers = deposit_data.get_num_watchtowers();
let mut operator_acks_vec: Vec<Option<[u8; 20]>> = vec![None; num_of_watchtowers];
``` [1](#0-0) 

`get_num_watchtowers()` returns `get_num_verifiers() + actors.watchtowers.len()`. In a standard 4-verifier, 0-extra-watchtower deployment this is 4. [2](#0-1) 

The additional disprove script is constructed in `get_replaceable_additional_disprove_script` using `create_additional_replacable_disprove_script_with_dummy`, which receives the deposit-specific `challenge_ack_hashes` (also `num_watchtowers` entries) but pads the remaining slots to 160 with dummy values — the "with_dummy" suffix is the padding mechanism:

```rust
let challenge_ack_hashes = self.get_challenge_ack_hashes().await?.to_vec();
let script = create_additional_replacable_disprove_script_with_dummy(
    bridge_circuit_constant,
    bitvm_keys.bitvm_pks.0[0].to_vec(),
    bitvm_keys.latest_blockhash_pk.to_vec(),
    bitvm_keys.challenge_sending_watchtowers_pk.to_vec(),
    challenge_ack_hashes,   // num_watchtowers entries, padded to 160 internally
);
``` [3](#0-2) 

The test suite confirms that `validate_assertions_for_additional_script` always receives exactly 160 entries:

```rust
let dummy_challenge_preimages_final: [Option<[u8; 20]>; 160] = [None; 160];
let resulting_witness = validate_assertions_for_additional_script(
    script, ..., dummy_challenge_preimages_final.to_vec(),
);
``` [4](#0-3) 

When `verify_additional_disprove_conditions` calls `validate_assertions_for_additional_script` with an `operator_acks_vec` of only `num_of_watchtowers` (e.g., 4) entries, the function internally iterates over all 160 script slots and accesses `operator_acks_vec[i]` for `i ≥ 4`, causing an index-out-of-bounds panic:

```rust
let additional_disprove_witness = validate_assertions_for_additional_script(
    additional_disprove_script.clone(),
    g16_public_input_signature.clone(),
    payout_blockhash_new.clone(),
    latest_blockhash_new.clone(),
    challenge_sending_watchtowers_signature.clone(),
    operator_acks_vec.clone(),   // only num_of_watchtowers entries, not 160
);
``` [5](#0-4) 

The existing bounds check at line 2551 only guards the *filling* loop (preventing `operator_acks_vec` from being written out of bounds), not the subsequent call to `validate_assertions_for_additional_script`: [6](#0-5) 

### Impact Explanation

When a fraudulent operator sends a malicious kickoff and the verifier's state machine reaches `disprove_if_ready` and calls `send_disprove`, the call chain reaches `verify_additional_disprove_conditions`, which panics. The disprove transaction is never broadcast. After the `disprove_timeout_timelock` expires, the operator can claim the reimbursement output, effectively stealing the bridged BTC amount. The operator's collateral is not slashed. This is a permanent liveness and safety failure of the challenge-response game for any deployment where `num_of_watchtowers < 160` (i.e., every realistic deployment). [7](#0-6) 

### Likelihood Explanation

This is triggered in every production deployment. The standard configuration uses 4 verifiers and 0 extra watchtowers (`num_of_watchtowers = 4`). Any operator who initiates a fraudulent kickoff and reaches the assert phase will benefit from this bug. No special privileges are required beyond being a registered operator. The trigger is the normal challenge-response flow. [8](#0-7) 

### Recommendation

Allocate `operator_acks_vec` with `MAX_NUMBER_OF_WATCHTOWERS` (160) entries instead of `num_of_watchtowers`:

```rust
// Before (buggy):
let num_of_watchtowers = deposit_data.get_num_watchtowers();
let mut operator_acks_vec: Vec<Option<[u8; 20]>> = vec![None; num_of_watchtowers];

// After (fixed):
let mut operator_acks_vec: Vec<Option<[u8; 20]>> = vec![None; MAX_NUMBER_OF_WATCHTOWERS];
```

This matches the 160-entry expectation of `validate_assertions_for_additional_script` and the 160-slot script produced by `create_additional_replacable_disprove_script_with_dummy`. The existing bounds check at line 2551 already prevents `operator_acks` indices from exceeding `num_of_watchtowers`, so no additional guard is needed for the filling loop.

### Proof of Concept

1. Deploy Clementine with 4 verifiers and 0 extra watchtowers (`num_of_watchtowers = 4`).
2. Operator sends a fraudulent kickoff transaction.
3. Verifiers send watchtower challenges; operator sends challenge acks and assert transactions.
4. Verifier's state machine reaches `disprove_if_ready` → `send_disprove` → `verify_additional_disprove_conditions`.
5. `operator_acks_vec` is allocated with 4 entries.
6. `validate_assertions_for_additional_script` accesses `operator_acks_vec[4]` → index-out-of-bounds panic.
7. The disprove transaction is never sent.
8. After `disprove_timeout_timelock` blocks, the operator claims the reimbursement output.
9. Bridged BTC is stolen; operator collateral is not slashed. [1](#0-0) [5](#0-4) [9](#0-8)
