### Title
Hidden bidirectional-Unicode ("Trojan Source") files bypass Desktop's warning and are silently committable when the diff exceeds `MaxDiffBufferSize` - (File: `app/src/lib/git/diff.ts`)

### Summary
Desktop detects hidden bidirectional-Unicode control characters in diffs and shows a security warning (`DiffContentsWarning`) so users don't unknowingly commit/review code that renders differently than it executes. That detection only happens if the raw diff buffer is parsed by `DiffParser`. `buildDiff` in `app/src/lib/git/diff.ts` never parses the diff at all when the buffer is larger than the hardcoded `MaxDiffBufferSize` constant, short-circuiting to `DiffType.Unrenderable`. This is the same class of bug as the Moonwell report: a single hardcoded constant (`70e6`/`1 ether`) is assumed to be a reasonable universal threshold, but it silently breaks the invariant ("every diff the user can commit has been checked for hidden characters") once real-world inputs (an attacker-crafted file in a cloned/fetched repo) exceed it.

`diffFromRawDiffOutput` calls `DiffParser.parse`, and it is exclusively inside `DiffParser.parse` that `hasHiddenBidiChars` is computed via `HiddenBidiCharsRegex.test(text)`: [3](#0-2) 

When `isValidBuffer` returns `false`, `buildDiff` returns `{ kind: DiffType.Unrenderable }` and returns immediately — `diffFromRawDiffOutput`/`DiffParser.parse` is never invoked, so `hasHiddenBidiChars` is never computed for that file, ever. The UI for `DiffType.Unrenderable` simply shows "The diff is too large to be displayed", with no "Show anyway" affordance (unlike `DiffType.LargeText`, which does let the user force-render and still carries `hasHiddenBidiChars` through): [4](#0-3) 

`DiffContentsWarning` (the bidi-char alert) is rendered only from a fully-parsed `ITextDiff`, so it can never fire for an `Unrenderable` file: [5](#0-4) 

Nothing else in the commit path gates on `hasHiddenBidiChars` or on whether a diff was renderable. The only other size-based guard, `getLargeFilePaths` in `app/src/lib/large-files.ts`, only warns for files over a separate, unrelated 100MB threshold and is about performance, not content review: [6](#0-5) 

So the working-directory file remains fully selectable and stageable; the "Commit to <branch>" flow has no dependency on the diff having been rendered or scanned for hidden Unicode.

### Impact Explanation
An attacker who controls a cloned/fetched repository (e.g. a PR branch, a fork the victim adds as a remote, or any tracked file the victim edits) can ship a text file whose diff buffer is larger than 70MB but embeds `HiddenBidiCharsRegex`-matching characters (`U+202A`–`U+202E`, `U+2066`–`U+2069`) that visually reorder code to hide malicious logic ("Trojan Source" style attack, cf. CVE-2021-42574). Because the diff buffer exceeds `MaxDiffBufferSize`, Desktop skips `DiffParser.parse` entirely, so:
- The bidi-character warning banner never appears for that file, in any view.
- The user is not blocked from staging/committing the file — they simply see a generic "too large" placeholder.

The result is that a user can be induced to commit and push code containing invisible/reordered malicious content while Desktop's designated hidden-Unicode safeguard silently never runs — a supply-chain-relevant "silent corruption of what the user commits" scenario, directly analogous to the seed report's core defect (a single hardcoded threshold value assumed universally safe, which breaks an important invariant once attacker-controlled input scale differs from what was assumed).

### Likelihood Explanation
No privileged access is required — only that the victim has a working copy containing an attacker-authored file (e.g. from a branch/fork/PR they check out), a routine, everyday Desktop workflow. Files in the tens-of-megabytes range are not unusual (minified bundles, generated code, data files, vendored dependencies), so crossing the 70MB threshold is plausible without looking overtly suspicious, especially since Desktop's own 100MB "large file" warning is a separate, higher bound. This is essentially the same failure mode already publicly known for git-diff/GitHub web hidden-bidi detection tools that only scan rendered diffs — no exotic conditions or race required.

### Recommendation
Decouple hidden-Unicode/bidi-character scanning from diff renderability: run the `HiddenBidiCharsRegex` check (or an equivalent streaming scan) over the raw buffer/file contents independently of `isValidBuffer`/`MaxDiffBufferSize`, and surface the `DiffContentsWarning` (or a dedicated "Unrenderable but contains hidden characters" banner) even when `DiffType.Unrenderable` is returned. At minimum, gate the ability to stage/commit an `Unrenderable` file on this scan completing, so a user is never able to silently commit content that was never checked.

### Proof of Concept
1. In a test repository, create a text file containing a legitimate-looking line followed by padding so the resulting `git diff` output exceeds 70,000,000 bytes (e.g. pad with ~70MB of repeated benign text/whitespace), and embed a hidden bidi override character (e.g. `U+202E`) around a small, security-relevant substring (e.g. reordering `isAdmin = false` to visually read `isAdmin = true`).
2. Open the repository in Desktop; the file shows as changed in Changes.
3. Select the file: because `buffer.length > MaxDiffBufferSize` (`app/src/lib/git/diff.ts:74-76,861-864`), `buildDiff` returns `{ kind: DiffType.Unrenderable }` and the UI renders `renderUnrenderableDiff()` ("The diff is too large to be displayed") with no "Show Diff" option and no bidi warning (`app/src/ui/diff/index.tsx:196-203`, `app/src/ui/diff/diff-contents-warning.tsx`).
4. Stage the file and click "Commit to <branch>" — nothing in the commit flow inspects `hasHiddenBidiChars` (it was never computed) or blocks commit based on `DiffType.Unrenderable`; the commit succeeds and can be pushed, with the hidden bidi content undetected by Desktop's own safeguard.

import { WorkingDirectoryStatus } from '../models/status'
import { DiffSelectionType } from '../models/diff'
import { Repository } from '../models/repository'
import { stat } from 'fs/promises'
import { join } from 'path'

const ReceiveLimit = 100 * 1024 * 1024 // 100 MiB

/**
 * Retrieve paths of working directory files that are larger than a given Megabyte size.
 *
 * @param repository        - The repository from which the base file directory will be retrieved.
 * @param workingDirectory  - The collection of changed files, from which the selected files will
 *                            be determined.
 * @param maximumSizeMB     - The size limit (in Megabytes) at which an exceeding file size will
 *                            result in it's path being retrieved.
 */
export async function getLargeFilePaths(
  repository: Repository,
  workingDirectory: WorkingDirectoryStatus
) {
  const fileNames = new Array<string>()
  const workingDirectoryFiles = workingDirectory.files
  const includedFiles = workingDirectoryFiles.filter(
    file => file.selection.getSelectionType() !== DiffSelectionType.None
  )

  for (const file of includedFiles) {
    const filePath = join(repository.path, file.path)
    try {
      const fileStatus = await stat(filePath)
      const fileSizeBytes = fileStatus.size
      if (fileSizeBytes > ReceiveLimit) {
        fileNames.push(file.path)
      }
    } catch (error) {
      log.debug(`Unable to get the file size for ${filePath}`, error)
    }
  }

  return fileNames
