### Title
Diff-splitting on raw "diff --git " substring lets attacker-controlled file content smuggle malicious hunks past security review - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`parse_diff_into_files` (and its sibling `extract_file_paths_from_diff`) split the raw `git diff` text on the literal substring `"diff --git "` with no line-anchoring, so a source line that merely *contains* that text (which appears in the diff as an ordinary `+`-prefixed content line) is treated as a new file-header boundary. Because `_is_reviewable_source` blocklists certain extensionless basenames (e.g. `license`), an attacker who controls file content can redirect all subsequent hunk lines into a synthetic "file" that gets filtered out, silently dropping real malicious code from the diff review payload.

### Finding Description
`parse_diff_into_files` does: [1](#0-0) 

The split key is `"diff --git "` [2](#0-1) , applied to the entire raw diff text with `str.split`, not a line-anchored regex. A real `git diff` line for an *added* source line is emitted verbatim after a leading `+`. If the attacker's file content contains a line whose text is exactly `diff --git a/license b/license`, the diff will contain the line `+diff --git a/license b/license`. That line still contains the substring `diff --git `, so `split()` cuts there — even though it's `+`-prefixed content data, not a real diff header.

The resulting spurious chunk starts with `a/license b/license`, which matches the header regex `^a/(.+?) b/(.+)$` [3](#0-2) , producing `file_path = "license"`. `_is_reviewable_source("license")` returns `False` because `"license"` is in `NON_SOURCE_EXTENSIONLESS_BASENAMES` [4](#0-3) [5](#0-4) , so the loop `continue`s and drops that whole chunk [6](#0-5) .

Critically, that dropped chunk contains **all lines from the injected marker up to the next legitimate `diff --git ` boundary** — i.e. every hunk line that follows the marker within the same file's diff, including genuinely malicious added code (e.g. `+os.system(user_input)`). That code is therefore never included in the `(file_path, diff_content)` tuples returned to the LLM-based reviewers.

`parse_diff_into_files` feeds the Stop-hook diff review, the commit-review, and push-sweep flows in `security_reminder_hook.py` (imported and called there) [7](#0-6) . None of those callers re-validate that the concatenation of parsed chunks reconstructs the full diff, so the dropped content is simply invisible to `analyze_code_security`/`agentic_review`.

Note this only evades the **LLM diff-review layer**. The separate PostToolUse pattern-based check (`check_patterns`) operates directly on the raw `Write`/`Edit` tool input content [8](#0-7) , not on parsed diff chunks, so regex-based warnings for that specific edit still fire. The bypass is scoped to the git-diff-based Stop/commit/push review passes.

### Impact Explanation
This is a trust-boundary bypass of the plugin's core safety mechanism: the Stop-hook / commit-review / push-sweep LLM security scan is supposed to catch vulnerabilities in code Claude just wrote or committed. By embedding one crafted line of text in a file, an attacker (e.g., via a poisoned issue/PR description that Claude is asked to implement, or any repository content Claude copies verbatim) can cause subsequently-added malicious lines in the same file to be excluded from the diff sent to the LLM reviewer, so no finding is ever raised and the Stop hook never exits with code 2 to force remediation. This degrades the plugin's detection guarantee without any admin privilege, key leakage, or social engineering of Claude Code internals — only ordinary "content Claude writes/reviews" is needed.

### Likelihood Explanation
Preconditions are minimal: the attacker needs the ability to get one attacker-chosen line of text (e.g. `diff --git a/license b/license`) into a file that will later be diffed by the plugin, immediately before or interleaved with the actual malicious payload lines in the same hunk/file. This is plausible whenever Claude is instructed (via prompt injection from repository content, an issue, or a task description) to add such a line as filler/comment/string before the real payload. The exploit is fully deterministic and reproducible — it depends only on pure string parsing in `gitutil.py`, not on race conditions or environment state.

### Recommendation
Replace the naive `str.split("diff --git ")` with line-anchored parsing: split only on lines that start with `diff --git ` (e.g. `re.split(r'(?m)^diff --git ', diff_output)` or iterate `diff_output.splitlines()` and only treat a line as a new file boundary when `line.startswith("diff --git ")` at the start of a physical line). Apply the same fix to `extract_file_paths_from_diff`, which shares the identical flaw.

### Proof of Concept
Unit test against `parse_diff_into_files` in `gitutil.py`:

```python
from gitutil import parse_diff_into_files

diff_output = (
    "diff --git a/evil.py b/evil.py\n"
    "index 0000000..1111111 100644\n"
    "--- a/evil.py\n"
    "+++ b/evil.py\n"
    "@@ -0,0 +1,3 @@\n"
    '+print("hello")\n'
    "+diff --git a/license b/license\n"
    "+os.system(user_input)  # malicious injected code\n"
)

files = parse_diff_into_files(diff_output)

# Expected (secure) behavior: the malicious line should still be present
# somewhere in the parsed output for evil.py.
combined = "\n".join(content for _, content in files)
assert "os.system(user_input)" in combined, (
    "malicious line was dropped by the diff-header injection — "
    f"parsed files: {files}"
)
```

With the current implementation this assertion fails: `files` contains only an `evil.py` entry missing the `os.system(user_input)` line, because that line was swallowed into a synthetic `license` chunk filtered out by `_is_reviewable_source`. After applying the line-anchored split fix, the assertion passes.

```python
def parse_diff_into_files(diff_output):
    """
    Parse unified diff output into a list of (file_path, diff_content) tuples.
    Only includes files with source code extensions.
    """
    if not diff_output or not diff_output.strip():
        return []

    files = []
    file_diffs = diff_output.split("diff --git ")

    for file_diff in file_diffs:
        if not file_diff.strip():
            continue

        # Extract filename from first line: "a/path/to/file b/path/to/file"
        lines = file_diff.split('\n')
        header_match = re.match(r'^a/(.+?) b/(.+)$', lines[0])
        if not header_match:
            continue

        file_path = header_match.group(2) or header_match.group(1) or ''

        # Filter to source code files only
        if not _is_reviewable_source(file_path):
            continue

        # Extract the diff content (from first @@ onwards)
        diff_lines = []
        in_hunks = False
        for line in lines[1:]:
            if line.startswith('@@'):
                in_hunks = True
            if in_hunks:
                diff_lines.append(line)

        if diff_lines:
            files.append((file_path, '\n'.join(diff_lines)))

    return files
```

def extract_content_from_input(tool_name, tool_input):
    """Extract content to check from tool input based on tool type."""
    if tool_name == "Write":
        return tool_input.get("content", "")
    elif tool_name == "Edit":
        return tool_input.get("new_string", "")
    elif tool_name == "MultiEdit":
        edits = tool_input.get("edits", [])
        if edits:
            return " ".join(edit.get("new_string", "") for edit in edits)
