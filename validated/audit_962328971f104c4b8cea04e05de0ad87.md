## Finding

### Title
Bundled multi-token escrow release can be permanently bricked by a single misbehaving input token, locking all inputs in `IntentGatewayV2` withdrawals - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_withdraw()` in `IntentsBase.sol` releases *all* of an order's escrowed input tokens in a single loop, calling `safeTransfer` for each token sequentially. If a single token in that list reverts on transfer (e.g. a blacklist-capable stablecoin, a pausable token, or any token that can later refuse a specific recipient), the entire `_withdraw` call reverts — which reverts the whole `onAccept`/`onGetResponse` callback that invoked it. Because the ISMP host retries failed callbacks indefinitely (deleting the receipt on failure so the message can be replayed), a persistently-reverting token in the bundle makes the withdrawal *permanently unexecutable*, locking every other (otherwise-healthy) token escrowed for that same order commitment. This mirrors the assimilator bug: one misbehaving external asset among several bundled together blocks release of the whole batch, and there is no per-token isolation or partitioned fallback (unlike the resolution the external report recommends).

### Finding Description
`_withdraw` iterates `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each entry, decrementing escrow balances *before* transferring: [1](#0-0) 

This is invoked from both cross-chain settlement paths:
- `onAccept` (RedeemEscrow / RefundEscrow), called by the Host on `dispatchIncoming`: [2](#0-1) 
- `onGetResponse`, the cancel-from-source path: [3](#0-2) 

The Host's incoming dispatch swallows a callback revert and deletes the receipt so the message can be resubmitted: [4](#0-3) 

This retry mechanism is exactly the protocol's answer to the "external call may revert" problem described in the external report — but it only helps if the underlying cause of the revert is transient. If one of the tokens in `body.tokens` deterministically reverts (e.g. its issuer blacklists `beneficiary`, or the token is paused/frozen), every retry of the settlement message fails identically, forever. Since `_withdraw` has no per-token try/catch or skip-and-continue logic, and no "partitioned" fallback that lets the beneficiary claim the *other*, still-transferable tokens independently, the entire multi-token escrow for that order commitment becomes permanently stuck.

Order `inputs` (the token list that ends up in `body.tokens`) are chosen by the order creator at placement time and are not filtered by an allowlist at the protocol layer, so an attacker fully controls which tokens get bundled into a given commitment.

### Impact Explanation
An unprivileged order creator can craft an order whose `inputs` include a token they know will later be able to refuse the target beneficiary (any token with a blacklist/pause/freeze admin function, which is common among major stablecoins and many ERC-20s). Once a solver fills the order and the destination dispatches `RedeemEscrow` back to source, `_withdraw` will attempt to move *all* escrowed input tokens to the solver in one atomic loop. If the malicious token later blocks a transfer to that solver (or the order was deliberately built to include a token that will simply never allow transfer to an arbitrary/blacklisted address), the solver's genuinely-earned escrow — including entirely unrelated, healthy tokens bundled in the same order — becomes permanently unclaimable. The same applies to the refund path for a legitimate user if a bad token is combined with good ones. This is a direct loss/lock of funds reachable without any relayer, prover, or governance compromise — solely by picking adversarial input tokens at order placement, a fully public entrypoint.

### Likelihood Explanation
Order placement and token selection are unrestricted user actions; there is no token allowlist/denylist enforced at the `IntentGateway` level for `inputs`. Any token with a blacklist, pause, or fee-related revert condition targeting a specific address is sufficient to trigger this permanently, and such tokens (USDC/USDT-style blacklisting, pausable OZ tokens) are common on EVM chains that Hyperbridge integrates. The condition is deterministic (not a race or timing issue) and requires no privileged actor.

### Recommendation
Make `_withdraw` resilient to a single failing token instead of atomically reverting the whole batch:
- Wrap each token transfer in a try/catch (or use low-level `.call` with per-token success bookkeeping) so a failing transfer does not roll back the release of the other tokens.
- Persist per-token "pending" balances for tokens that fail to transfer so the beneficiary (or anyone) can retry that specific token later, rather than blocking the whole commitment.
- Consider an explicit escape-hatch analogous to the "partitioned end-of-life" mechanism the Loihi fix introduced: allow independent, per-token claims keyed by `(commitment, token)` instead of requiring the full token list to succeed together.

### Proof of Concept
1. Order creator places a cross-chain order with `inputs = [tokenA (healthy), tokenB (blacklist-capable)]`, `beneficiary`/solver-to-be = `S`.
2. A solver fills the order on the destination chain, delivering the required outputs, and the destination dispatches `RedeemEscrow{ commitment, tokens: [tokenA, tokenB], beneficiary: S }` back to source via `ExtrinsicIntents._authenticate` + `_withdraw` path (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:289-295`).
3. Before the settlement message lands, `tokenB`'s issuer blacklists `S` (or `tokenB` is simply a token engineered to always revert transfers to non-allowlisted addresses).
4. `onAccept` → `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-410`) transfers `tokenA` successfully, then reverts on `tokenB`'s `safeTransfer`, reverting the whole call.
5. `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:809-816`) catches the revert, deletes the request receipt, allowing the message to be resubmitted — but every resubmission hits the same `tokenB` revert.
6. `tokenA` (fully healthy, unrelated token) along with `tokenB` remain escrowed in the gateway forever; solver `S` can never claim either, despite having delivered real value on the destination chain.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

                if (!sent) revert InsufficientNativeToken();

            }
        }
