### Title
Re-enabling `protocol.file.allow=always` for submodule updates during checkout of attacker-controlled refs permits local file/path disclosure via crafted `.gitmodules` — ([File: app/src/lib/git/submodule.ts])

### Summary
The external report's broken invariant is: a victim contract assumes a resource (a Uniswap pool) is in a known/expected initial state before acting on it, but an attacker can pre-set that state, causing the victim's trusted operation to produce a corrupted, exploitable outcome. The closest reachable analog in GitHub Desktop is the reintroduction of `protocol.file.allow=always` for `git submodule update` when checking out branches/commits, controlled by the `allowFileProtocol` flag threaded through `checkoutBranch`/`checkoutCommit` into `updateSubmodulesAfterOperation`.

### Finding Description
`updateSubmodulesAfterOperation` builds its `git submodule update --init --recursive` arguments and conditionally prepends `-c protocol.file.allow=always` when `allowFileProtocol` is `true`: [1](#0-0) 

This flag is threaded from `checkoutBranch` and `checkoutCommit`: [2](#0-1) [3](#0-2) 

`protocol.file.allow=always` deliberately overrides git's own hardened default (`protocol.file.allow=user`), which was introduced upstream specifically to stop automatic/recursive operations (like `submodule update --init`) from silently following `file://` (or bare local-path) submodule URLs — this is the exact protection added for CVE-2022-39253. By re-enabling `always` whenever Desktop decides a submodule needs (re)initialization during a checkout, Desktop undoes that protection for any `.gitmodules` content that ships inside a cloned/fetched, attacker-controlled repository (or one of its branches). A malicious repository can commit a `.gitmodules` entry whose `url` is a `file://` path to an unexpected location, or a branch that (re)introduces such an entry, so that once Desktop performs a normal, user-triggered checkout with `allowFileProtocol: true` (the same code path exercised in `checkout-test.ts` for "initializes an uninitialized submodule when checking out a branch"), the submodule is cloned/checked out from that local path instead of the network — corrupting the on-disk state and re-enabling data-exfiltration-via-clone attacks that the underlying git fix was meant to block. [4](#0-3) 

This mirrors the report's core defect: Desktop treats the submodule graph produced by cloning/fetching a repository as trustworthy input and unconditionally relaxes a security guard rather than validating the attacker-supplied `.gitmodules` content before doing so.

### Impact Explanation
If exploitable, this would allow a malicious repository owner or anyone who can get a victim to check out a crafted branch (including via forks/PRs, which Desktop fetches and checks out through this same code path) to redirect submodule population to a local `file://` path, which — depending on git version, attacker knowledge of local paths, and submodule name/`--recurse-submodules` interactions — can leak or copy local repository contents into the attacker's own submodule tree, or otherwise smuggle in local filesystem content that ends up materialized as tracked files, i.e., silent corruption of what the user has on disk and potentially commits/pushes afterward.

### Likelihood Explanation
The trigger requires only that the victim clone/fetch a repository and check out a branch or commit containing a crafted `.gitmodules`, which is exactly the "attacker controls a cloned/fetched repository" primitive in scope. It does not require local/physical access, admin rights, prior malware, or leaked credentials — it's an in-band consequence of ordinary "check out this branch" behavior. Likelihood is tempered because it depends on the attacker guessing/targeting a useful local path and on the exact git version's remaining safeguards around `file://` submodules, which I could not fully verify from the indexed subset of the codebase (production call sites that set `allowFileProtocol: true` outside of the test file were not conclusively located).

### Recommendation
Do not blanket re-enable `protocol.file.allow=always` for submodule updates originating from untrusted/attacker-provided repository content. Instead, validate submodule URLs parsed from `.gitmodules` before allowing `file://`/local-path submodules (e.g., only allow it for submodules the user explicitly added locally, never for those introduced by a fetched/cloned branch), or scope `protocol.file.allow` more narrowly using an explicit safelist tied to the top-level repository's own filesystem location rather than `always`.

### Proof of Concept
Not independently reproduced against a running Desktop build; this analysis is based on static code review of `app/src/lib/git/submodule.ts`, `app/src/lib/git/checkout.ts`, and `app/test/unit/git/checkout-test.ts`, which together show the flag being set to `true` for a normal branch checkout that "initializes an uninitialized submodule." Full verification of every production call site that supplies `allowFileProtocol: true` was not possible with the available indexed code, so a Devin session with full repository access is recommended to trace all callers (e.g., pull-request checkout, fetch flows) and confirm end-to-end exploitability before treating this as confirmed rather than a plausible analog.

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
```

```typescript
    it('initializes an uninitialized submodule when checking out a branch', async t => {
      const repository = await setupRepositoryWithUninitializedSubmodule(t)

      if (branchWithSubmodule == null) {
```
