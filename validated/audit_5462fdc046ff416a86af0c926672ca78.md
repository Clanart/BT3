Based on the investigation, the closest structural analog to the oracle bug in this repo is in the submodule-update path, where a single "is this safe/local" decision is used to grant a git-level trust exception (`protocol.file.allow=always`) that is then applied unconditionally to every submodule processed in a recursive, multi-item operation — mirroring the original bug's pattern of "check once, then apply the consequence blindly to a batch of independently-controlled items."

### Title
Recursive submodule update enables `protocol.file.allow=always` for all nested submodules from a single trust decision - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` accepts a single boolean `allowFileProtocol` and, when true, appends `-c protocol.file.allow=always` to a `git submodule update --init --recursive` invocation. [1](#0-0) 
This one flag is applied to the entire recursive submodule tree in a single git invocation, so every submodule (and nested submodule-of-a-submodule) discovered during that walk inherits the same file-protocol exception, regardless of what URL each individual `.gitmodules` entry actually specifies.

### Finding Description
Git added `protocol.file.allow` protections (default `user`, effectively disabled for automated/submodule operations) specifically to stop a malicious repository from declaring a submodule with a `file://` URL pointing at an arbitrary path on the victim's filesystem, which git would then read/copy into the working tree during `submodule update --init --recursive` (the class of issue fixed upstream as CVE-2022-39253). Here, `allowFileProtocol` is decided once per top-level operation (checkout/pull) and is then propagated as a single `-c protocol.file.allow=always` flag into a recursive command that processes an attacker-controlled `.gitmodules` file the user did not author. [2](#0-1) 
Because `--recursive` walks nested `.gitmodules` files that come from the fetched/cloned content itself, a single upfront "this looks like a local/trusted clone" determination is reused for every subsequently-discovered submodule URL, including ones an attacker adds deep in the submodule tree that were never part of the original trust decision. This is structurally the same flaw as the oracle report: a validity check performed once (per top-level repository/remote) is silently relied upon for a batch of subsequent, independently-attacker-controlled entries (each submodule) without re-validating each one. [3](#0-2) 

### Impact Explanation
If `allowFileProtocol` is derived from a coarse-grained signal (e.g., "the remote itself is a local path") rather than validated per-submodule, a cloned or fetched repository — content fully controlled by an attacker — can declare a `file://` submodule URL pointing outside the repository (e.g., a sensitive path on the user's disk or a location reachable via symlink). With `protocol.file.allow=always` in effect for the whole recursive walk, git will follow that submodule and copy/checkout its contents into the user's working directory, resulting in local file read/exfiltration or planting of unexpected files without any additional per-item validation — a data-exfiltration/read-outside-repo primitive matching the "attacker controls a cloned/fetched repository" impact category.

### Likelihood Explanation
Exploitability depends entirely on how `allowFileProtocol` is computed by callers in `app/src/lib/git/checkout.ts` (4 references were found but not fully inspected in this session due to tool budget limits) — if it is set to `true` for any path where the repository content itself is attacker-supplied (e.g., any local clone, or any operation on a repo added via "Clone" from an untrusted source), then simply adding a crafted submodule anywhere in a multi-level submodule tree is sufficient to trigger the behavior on the user's next checkout/pull, requiring no elevated privileges. This is a plausible but not fully confirmed path; the exact conditions under which `checkout.ts` sets `allowFileProtocol: true` need to be reviewed directly (the index used here has size limits and I was unable to pull the full content of `checkout.ts` before running out of iterations).

### Recommendation
Re-validate the file-protocol exception per submodule URL rather than once for the whole recursive tree — e.g., resolve the list of submodule URLs first, reject/prompt on any `file://` (or path-traversal) targets that fall outside the repository's own directory, and only then invoke `git submodule update` with `--recursive`; alternatively drop `--recursive` and process one level at a time, re-checking `allowFileProtocol` eligibility at each level as new `.gitmodules` content is discovered.

### Proof of Concept
1. Attacker creates a public repository with a `.gitmodules` entry pointing to a nested submodule that itself contains another `.gitmodules` entry with `url = file:///path/on/victim/disk` (or a path traversal via a relative `file://` URL combined with symlinks).
2. Victim clones or adds this repository in GitHub Desktop and the app performs a checkout/pull that calls `updateSubmodulesAfterOperation` with `allowFileProtocol: true` (as determined by the top-level clone/remote check). [4](#0-3) 
3. `git -c protocol.file.allow=always submodule update --init --recursive` executes, walking into the nested `.gitmodules` and fetching/checking out the `file://` target without re-validating that specific submodule URL.
4. Contents from the victim's local path are copied into the repository's working directory, where they become visible in the Desktop UI (and could subsequently be committed/pushed by the unsuspecting user, achieving the "silent corruption of what the user commits" impact as well).

Note: I could not fully confirm the exact conditions under which `checkout.ts` sets `allowFileProtocol` to `true` due to tool-call limits in this session — verifying that logic directly in the repository would be necessary to confirm end-to-end exploitability with full certainty.

export async function updateSubmodulesAfterOperation<T extends Progress>(
  repository: Repository,
  remote: IRemote | null,
  progressCallback: ((progress: T) => void) | undefined,
  progressKind: T['kind'],
  title: string,
  targetOrRemote: string,
  allowFileProtocol: boolean
): Promise<void> {
  const opts: IGitStringExecutionOptions = {
    env: await envForRemoteOperation(
      getFallbackUrlForProxyResolve(repository, remote)
    ),
    expectedErrors: AuthenticationErrors,
  }

  const args = [
    ...(allowFileProtocol ? ['-c', 'protocol.file.allow=always'] : []),
    'submodule',
    'update',
    '--init',
    '--recursive',
  ]

  if (!progressCallback) {
    await git(args, repository.path, 'updateSubmodules', opts)
    return
  }
