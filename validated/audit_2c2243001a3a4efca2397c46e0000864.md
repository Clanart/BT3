The exact local analog exists in Hyperbridge's Intent Gateway escrow-release/refund path, and it shares the same broken invariant as the referenced marketplace bug: a push-style ERC-20 `transfer`/`safeTransfer` to an attacker- or externally-controlled beneficiary that can be blacklisted (USDC/USDT-style) will revert, and the code has no fallback, causing escrowed bridge funds to become permanently stuck.

### Title
Escrow release/refund permanently DoS'd and locked by a single non-transferable (blacklisted) beneficiary token in `_withdraw`/`withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` (and its Tron/IntentGatewayV2 twin `withdraw()`) releases every escrowed token in a `WithdrawalRequest` to a single `beneficiary` in one loop, using an unguarded `IERC20.safeTransfer`/low-level `transfer` call for each token [1](#0-0) . If any one of those transfers reverts — e.g. the beneficiary is blacklisted by USDC/USDT for one of the escrowed tokens — the entire function reverts, rolling back the release/refund of *every* token in the request, not just the blocked one.

### Finding Description
`onAccept()` dispatches `RedeemEscrow` (beneficiary = the solver who filled the order) and `RefundEscrow` (beneficiary = the original order user) requests to `_withdraw(body, isRefund, true)` [2](#0-1) . Inside `_withdraw`, each `body.tokens[i]` is transferred to `beneficiary` via `IERC20(token).safeTransfer(beneficiary, amount)` with no try/catch and no per-token isolation [3](#0-2) . The Tron variant does the same with a raw low-level call, reverting with `TransferFailed()` on any failure [4](#0-3) .

Because `onAccept` is invoked by `EvmHost.dispatchIncoming` via a low-level `.call()`, a revert inside `_withdraw` causes the host to simply delete the request receipt "so it can be retried" and return, rather than reverting the whole batch [5](#0-4) . This "retry" mechanism assumes the failure is transient. But if the beneficiary is durably blacklisted for one of the escrowed tokens (the exact scenario from the referenced report), every future retry attempt will fail identically — the message can never be delivered successfully, so the commitment is never marked filled/refunded, and the escrowed tokens for that commitment (including any *other*, non-blacklisted tokens bundled in the same multi-asset order) remain locked in the gateway contract forever. There is no admin/DAO rescue path, no per-token skip-and-continue, and no "claim later" mechanism as recommended in the original report.

This affects both cross-chain settlement (`RedeemEscrow`/`RefundEscrow` via `onAccept`) and the same-chain fill/cancel paths in `IntrinsicIntents.sol`, which call the identical `_withdraw` helper [6](#0-5) .

### Impact Explanation
This is a direct, permanent loss/lock of bridged escrow funds — squarely matching the bounty's "stealing or loss of funds" and stuck-escrow pivot ("Bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount"). A solver that has already irrevocably delivered output tokens to the user on the destination chain can be permanently denied their escrowed input tokens on the source chain if they are blacklisted for even one of the input tokens in the order, and — because `_withdraw` reverts the whole loop — any other tokens in that same order become unrecoverable too. Symmetrically, a user's `RefundEscrow` can never land if the user's own address becomes blacklisted for one of the escrowed input tokens, permanently trapping the entire escrow (not just the blacklisted token) with no recovery mechanism.

### Likelihood Explanation
Multi-token orders (`order.inputs` with more than one asset, or an order paired with fee-token release) are a supported, ordinary feature of the Intent Gateway, and USDC/USDT are explicitly expected/likely input assets given the protocol's stablecoin-centric design (the fee token itself is typically DAI/a stablecoin). Any beneficiary (solver or user) that is later blacklisted by a token issuer — a realistic, externally-triggered event outside the protocol's control, exactly as in the cited report — permanently disables settlement for that commitment with no code path to work around it.

### Recommendation
Do not let a single token-transfer failure block release of the other escrowed tokens or permanently prevent settlement. Wrap each per-token transfer in a try/catch (or use a low-level call and check success individually), and for any that fail, credit the amount to a per-beneficiary/per-token "pending withdrawal" mapping instead of reverting, with a separate public `claim()`/`sweep`-style function the beneficiary (or governance, mirroring the "Cantina Managed" fix of forwarding to a treasury) can use to retrieve funds later once the block is resolved. This still finalizes the order (marks `_filled`) and emits `EscrowReleased`/`EscrowRefunded` for the tokens that were successfully transferred, rather than making the whole withdrawal atomic-or-nothing.

### Proof of Concept
1. User places a cross-chain order on the source chain with `order.inputs = [USDC(1000), DAI(500)]`.
2. A solver fills the order on the destination chain, delivering the required outputs to the user, and the gateway dispatches a `RedeemEscrow` `WithdrawalRequest{tokens: [USDC, DAI], beneficiary: solver}` back to the source chain.
3. Before the message is delivered/retried on the source chain, the solver's address is added to the USDC blacklist (e.g., due to an unrelated compliance action).
4. `onAccept()` → `_withdraw()` executes: the DAI transfer would succeed, but the loop reaches the USDC transfer first (or regardless of order) and `IERC20(usdc).safeTransfer(solver, 1000)` reverts.
5. The entire `_withdraw` call reverts; `EvmHost.dispatchIncoming` catches this, deletes `_requestReceipts[commitment]` "so it can be retried" [7](#0-6) , and any relayer can resubmit indefinitely — every attempt reverts the same way.
6. Both the 1000 USDC and 500 DAI remain locked in the `IntentGateway` contract permanently: the order is never marked filled, there is no alternate claim path, and the solver (who already paid out the destination-side output) can never recover its escrowed compensation.
