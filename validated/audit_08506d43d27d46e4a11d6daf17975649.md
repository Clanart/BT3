Found a strong candidate analog. Let me verify the call site and whether small outputs are filtered before `instruction_from_output`.### Title
Dust outputs smaller than `2 * COST_TO_AGGREGATE` underflow the scanned balance, crashing the processor or crediting a near-`u64::MAX` balance - (File: processor/src/multisigs/mod.rs)

### Summary
The GMX finding concerns an external value falling outside its assumed domain (a negative Chainlink price) hitting a bare `revert`/`require` that the error-handling taxonomy didn't account for, so the failure path took the worst branch (order canceled) instead of a safe one. Serai's `instruction_from_output` has the same shape: it unconditionally subtracts `2 * N::COST_TO_AGGREGATE` from an on-chain output's value, assuming every external output is worth more than the flat aggregation fee. An unprivileged sender can deposit an output below that bound, and the subtraction is neither rejected as a "skip this output" case nor made safe — it either panics (halting block processing, canceling all pending work) or wraps to ~`u64::MAX` (crediting the attacker a colossal `sriBTC`/`sriX` balance).

### Finding Description
`scanner_event_to_multisig_event` iterates every `OutputType::External` output scanned in a Bitcoin block and calls `instruction_from_output::<N>(&output)` (processor/src/multisigs/mod.rs:934) and again during `ForwardFromExisting` (processor/src/multisigs/mod.rs:859). Inside `instruction_from_output` (processor/src/multisigs/mod.rs:40-93), the only validation performed on the untrusted output is:

1. `data.len() <= MAX_DATA_LEN`
2. `Shorthand::decode` succeeds
3. `RefundableInInstruction::try_from` succeeds

Then, at processor/src/multisigs/mod.rs:87:

```rust
let mut balance = output.balance();
// Deduct twice the cost to aggregate to prevent economic attacks by malicious miners against
// other users
balance.amount.0 -= 2 * N::COST_TO_AGGREGATE;
```

`balance.amount.0` is a `u64` (`SubstrateAmount`, substrate/primitives/src/amount.rs:21-38, whose `Sub` impl uses `checked_sub(...).unwrap()`), and `N::COST_TO_AGGREGATE` is 800 sats on Bitcoin (processor/src/networks/bitcoin.rs:646), so the threshold is 1600 sats. The output value is fully attacker-controlled: anyone can send a Bitcoin transaction paying the Serai multisig's `external`/branch address with a value of e.g. 1000 sats (above Bitcoin's relay dust limit, so it confirms) and attach a valid `Shorthand::Raw` `OP_RETURN`. Nothing upstream filters outputs by amount — the `DUST` checks in `processor/src/networks/mod.rs` and `scheduler/utxo.rs` only apply to *outgoing* payments, not scanned inbound balances.

Two failure modes, mirroring the GMX split between "revert classified" and "revert not classified":

- **Debug / overflow-checks builds**: `u64` underflow panics. The scanner/handler aborts mid-`scanner_event_to_multisig_event`, so the block's `HandledEvent`/`seen` bookkeeping is never committed — every retry re-panics on the same output. The processor permanently halts scanning for that network, stalling batches, sign attempts, and payments — the analog of "orders get canceled" rather than the output being skipped.
- **Release builds (overflow-checks off)**: the subtraction wraps, producing `balance ≈ u64::MAX - 1600 + value`. The resulting `InInstructionWithBalance` is pushed into `instructions`, packed into a `Batch`, and threshold-signed. Substrate then mints ~1.8e19 `sriBTC` to the attacker's `Transfer` destination — funds that do not exist, enabling the attacker to redeem/drain the entire multisig.

This is exactly the reported class: a legitimate domain violation (`value < 2*COST_TO_AGGREGATE`, like `price < 0`) is not treated as an ignorable/skip case; it propagates as a panic or a silently wrong result into a path that commits consequences (signed batch instruction crediting the sender).

### Impact Explanation
- Release build: an attacker deposits ~1000 sats and receives a signed `InInstructionWithBalance` crediting ~`u64::MAX` balance — effectively unlimited `sriBTC` minted against nothing, fully draining the bridge multisig. Critical.
- Even if wrapped arithmetic is excluded, the panic permanently freezes all processing for that network (the poisoned output rescans forever), locking user funds — analogous to the GMX impact of canceled close-orders causing losses.

### Likelihood Explanation
Trivially reachable by any unprivileged party: craft a standard Bitcoin transaction to the multisig's known external address (derivable from the group key) with output value in `(0, 1600)` sats plus an `OP_RETURN` carrying a valid `Shorthand::Raw(RefundableInInstruction { instruction: InInstruction::Transfer(attacker_addr) })`. It confirms at minimal fee and is scanned on the next block. No miner collusion, validator misbehavior, or trusted-party compromise is needed.

### Recommendation
Replace the bare subtraction with a bounds check that treats the output as a skip, consistent with the existing "invalid data → return `None`" pattern:

```rust
let mut balance = output.balance();
balance.amount.0 = balance.amount.0.saturating_sub(2 * N::COST_TO_AGGREGATE);
if balance.amount.0 < N::DUST { return (presumed_origin, None); }
```

The same pattern should be applied to the second untrusted subtraction at processor/src/multisigs/mod.rs:884 (`instruction.balance.amount.0 -= tx.0.fee()`), where a forwarding fee exceeding the output value underflows identically. More broadly, inbound scanned values should be validated against the minimum economically-meaningful amount before any arithmetic, mirroring the report's recommendation to classify the out-of-domain case as a benign/empty error rather than letting it hit a generic abort.

### Proof of Concept
1. Serai's Bitcoin multisig exists; `COST_TO_AGGREGATE = 800` so the panic threshold is 1600 sats.
2. Attacker broadcasts a TX with `TxOut { value: 1000, script_pubkey: <multisig external address> }` and an `OP_RETURN` pushing `Shorthand::Raw(RefundableInInstruction { origin: None, instruction: InInstruction::Transfer(attacker_serai_addr) }).encode()`.
3. Scanner picks the output up after `CONFIRMATIONS` blocks; `output.kind() == OutputType::External`, `data` decodes, `try_from` succeeds.
4. `balance.amount.0 = 1000 - 1600`:
   - debug: panic in `instruction_from_output` → processor aborts; block is rescanned and re-panics → permanent stall (analog of canceled orders).
   - release: wraps to `18446744073709550016`; instruction enters `instructions` → `Batch` → threshold-signed `ProcessorMessage::Batch` → Substrate mints ~`u64::MAX` `sriBTC` to `attacker_serai_addr`.
5. Attacker burns the minted `sriBTC` for real BTC from the multisig.
