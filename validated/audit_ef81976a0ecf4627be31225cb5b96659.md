### Title
PedPoP returns ECDH-revealing blame proof on error path before verifying the message's proof of possession - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The upstream bug class is a resource released too late / leaked on an early error path (`of_node_put` skipped when `kcalloc` fails). The Serai analog lives in `KeyMachine::calculate_share`: an `EncryptionKeyProof` containing the ECDH shared key is generated and returned as blame on an early `?` error path **before** the batched proof-of-possession (PoP) for that message is ever verified. The PoP exists specifically to prevent this disclosure (see the comment at `crypto/dkg/pedpop/src/encryption.rs:84-90`), but the ordering in `calculate_share` bypasses it.

### Finding Description
In `calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-492):

```rust
for (l, share_bytes) in shares.drain() {
  let (mut share_bytes, blame) =
    self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
  let share =
    Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
      PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
    })?);
  ...
}
batch.verify_with_vartime_blame().map_err(|id| { ... })?;
```

`Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:469-501) does two things: it *queues* the PoP `SchnorrSignature` into the `BatchVerifier` (line 479-485, not yet verified), and it *eagerly computes* `ecdh(&self.enc_key, msg.key)` and packages that shared key into an `EncryptionKeyProof` (lines 487-499).

If the decrypted share bytes fail `C::F::from_repr` — trivially arranged since `SecretShare::read` accepts arbitrary 32 bytes (lib.rs:263-268) — the function returns `Err(PedPoPError::InvalidShare { blame: Some(blame) })` at line 481-482, returning the ECDH key-revealing proof to the caller. `batch.verify_with_vartime_blame()` at line 493 is never reached, so the queued PoP verification is abandoned. There is no check that the sender actually owned `msg.key` — exactly the check the PoP was added for.

### Impact Explanation
The comment at encryption.rs:84-90 documents the precise attack: Eve copies Alice's per-message encryption key `X` (observed on the authenticated/broadcast DKG channel) into her own `EncryptedMessage` to Bob. Without a PoP check, Bob's blame mechanism reveals `bX` — the ECDH shared key — which lets Eve decrypt Alice's actual ciphertext to Bob (which Eve also observed), recovering Alice's secret share destined for Bob. The PoP was intended to make this impossible; because `calculate_share` emits the blame proof on the `from_repr` error path *before* the batched PoP verification runs, the protection is bypassed.

An unprivileged DKG participant (only needs the ability to send an `EncryptedMessage` to a victim and observe channel traffic) forces the victim to produce a blame proof that reveals the ECDH shared key for a message the attacker does not own. If the caller publishes the blame — the designed purpose of `PedPoPError::InvalidShare.blame` — the attacker obtains decryption of another party's secret share, i.e. disclosure of DKG share material the protocol explicitly treats as secret. This maps to a Medium-severity confidentiality break of threshold key material reachable entirely from public/untrusted inputs (`EncryptedMessage::read` bytes).

### Likelihood Explanation
The trigger is fully deterministic: any participant can construct `EncryptedMessage { key: victim_msg.key, pop: arbitrary deserializable SchnorrSignature, msg: bytes that deserialize to a non-canonical scalar }` (e.g., all-`0xFF` share bytes, as `invalidate_share_serialization` does at encryption.rs:217-239). Decryption produces garbage, `from_repr` fails, and the victim returns blame for an unverified message. The only conditions outside the library are (a) the attacker observes the victim-message `key` field on the channel and (b) the integrator publishes returned blame — both consistent with PedPoP's documented channel assumptions.

### Recommendation
Do not return the `blame` proof before the PoP has been verified. Either:

- Run `batch.verify_with_vartime_blame()` (or a standalone `msg.pop.verify`) for the message before emitting `InvalidShare { blame: Some(blame) }` on the `from_repr` failure path, or
- Return `blame: None` (like the `BatchId::Decryption` arm at lib.rs:494-496) whenever the PoP has not been confirmed, since blame proving content is only meaningful once possession of the key is established.

### Proof of Concept
1. Alice (`Participant i=1`) runs `generate_secret_shares`, sending Bob (`i=2`) an `EncryptedMessage` with ephemeral `key = x·G`; the ciphertext and `key` are visible on the authenticated channel.
2. Eve (`i=3`) constructs `EncryptedMessage::<C, SecretShare<C::F>> { key: x·G (Alice's), pop: SchnorrSignature::read of any structurally valid signature Eve controls or fabricates, msg: SecretShare([0xFF; 32]) }` and sends it to Bob as her share.
3. Bob's `calculate_share` calls `self.encryption.decrypt`, queuing Eve's invalid PoP and computing `proof.key = b·(x·G)` (Bob's enc private key `b` times Alice's `x·G`).
4. `apply_keystream` yields garbage; `C::F::from_repr([0xFF; 32])` returns `None`; Bob returns `Err(InvalidShare { participant: 3, blame: Some(EncryptionKeyProof { key: b·x·G, dleq }) })`.
5. The caller publishes the blame. Eve reads `proof.key = b·x·G`, re-derives `cipher(context, proof.key)`, and decrypts the copied ciphertext of Alice's message to Bob — recovering Alice's secret share to Bob without ever proving ownership of `x·G`.

The fix commit's invariant — "release the resource/handle before returning on the error path" — maps here to "do not release the ECDH-key-bearing proof before the verification that justifies releasing it."
