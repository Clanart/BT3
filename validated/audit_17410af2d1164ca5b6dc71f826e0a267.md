### Title
Instant, non-time-weighted reward accounting in `BaseRewardPool` allows front-running/sniping of bribe and staking rewards - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool._provisionReward()` credits newly queued rewards to `rewardPerTokenStored` **instantly and proportionally to the pool's current `totalStaked()`**, with no time-weighted streaming/vesting of rewards (unlike a Synthetix-style `rewardRate`/`periodFinish` model). Combined with the fact that stake/vote entry points (`WombatBribeManager.vote()`, `MasterMagpie.deposit()`/`depositFor()`) and reward-triggering entry points (`WombatBribeManager.castVotes()`, `harvestSinglePool()`) are all permissionless and composable in a single transaction, an unprivileged wallet can stake/vote immediately before a reward-queuing call and immediately withdraw/claim afterward, capturing a disproportionate share of rewards that should accrue to long-standing stakers/voters — the same "instant-majority, same-block extraction" bug class described in the referenced report.

### Finding Description
`_provisionReward()` in `rewards/BaseRewardPool.sol` updates the global reward index the moment new rewards arrive: [1](#0-0) 

Because `rewardInfo.rewardPerTokenStored` is bumped by `_amountReward * 10**decimals / totalStaked()` at the instant `queueNewRewards`/`donateRewards` is called, whoever holds the largest stake **at that exact moment** claims the largest share of `_amountReward` — there is no minimum holding period, no linear vesting, and no protection against staking right before the call and withdrawing right after.

The entry points that trigger `queueNewRewards` on a `BribeRewardPool`/`BaseRewardPool` are permissionless:
- `WombatBribeManager.castVotes()` and `harvestSinglePool()` are `public`/external with no access control, and internally call `wombatStaking.vote()`, which harvests bribes from Wombat and calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)`. [2](#0-1) [3](#0-2) [4](#0-3) 

- `WombatBribeManager.vote()`/`unvote()` allow any vlMGP holder to stake/unstake into a `BribeRewardPool` at will, using their current votable balance (`getUserVotable`), with no lockup on the vote position itself: [5](#0-4) [6](#0-5) 

An attacker who already holds (or acquires) sufficient vlMGP can, in a single atomic transaction:
1. Call `vote()` to stake a large `_delta` of vlMGP into a target bribe pool's `rewarder` right before rewards are queued.
2. Call `castVotes()`/`harvestSinglePool()` himself (permissionless), which harvests pending Wombat bribes for that pool and immediately credits `rewardPerTokenStored` based on the now-inflated `totalStaked()` that includes the attacker's fresh stake.
3. Call `claimBribe()`/`getReward()` to withdraw his disproportionate share of the just-harvested rewards.
4. Call `unvote()` to withdraw his staked vlMGP from the pool.

This mirrors the report's root cause exactly: state (voting power / stake weight) that determines entitlement to a distribution is mutated and then immediately consumed for payout within the same transaction, with no cooldown between "becoming eligible" and "extracting value," allowing an attacker to dilute/steal rewards that should have accrued to genuine long-term stakers/voters. `donateRewards()` in the same contract is fully permissionless and reachable by anyone, reinforcing that the reward-crediting mechanism has no protection against snapshot manipulation. [7](#0-6) 

### Impact Explanation
This results in **theft of unclaimed yield** from genuine long-term vlMGP voters/stakers: an attacker can extract a share of bribe/reward tokens proportional to a stake he only holds for the duration of a single transaction, at the direct expense of users who kept their vlMGP locked/voted for the entire epoch. Repeated sniping around every `castVotes()`/`harvestSinglePool()` call can materially and permanently divert protocol-distributed yield away from legitimate participants.

### Likelihood Explanation
`castVotes()` and `harvestSinglePool()` are unauthenticated and callable by anyone at any time, and `vote()`/`unvote()` are freely available to any vlMGP holder with no cooldown, making the full attack sequence executable atomically by any ordinary wallet holding (or briefly acquiring) enough vlMGP. The only friction is needing vlMGP balance, which is obtainable via `VLMGP` locking of freely tradeable `MGP`.

### Recommendation
Introduce time-weighted (streamed) reward accrual instead of instant crediting, e.g., adopt a `rewardRate`/`periodFinish` linear-release model (Synthetix `StakingRewards` pattern) so that newly queued rewards are distributed gradually over a duration rather than instantly to the current `totalStaked()` snapshot. Additionally, add a minimum stake/vote duration (cooldown) before a position becomes eligible for `getReward()`/`claimBribe()`, preventing same-block or same-transaction stake-then-claim-then-withdraw sequences.

### Proof of Concept
Conceptual sequence (single transaction, unprivileged wallet):
1. Attacker holds/acquires vlMGP (via `VLMGP` lock of MGP).
2. `WombatBribeManager.vote(lps, deltas)` — attacker stakes a large delta into `pool.rewarder` (a `BribeRewardPool` extending `BaseRewardPool`), inflating `totalStaked()` for that pool right before harvest. [8](#0-7) 
3. Attacker calls `WombatBribeManager.harvestSinglePool([lp])` (or `castVotes`), which triggers `WombatStaking.vote()` → `IBribeRewardPool(rewarder).queueNewRewards(rewardAmount, token)` → `BaseRewardPool._provisionReward()`, instantly crediting `rewardPerTokenStored` based on the inflated `totalStaked()`. [9](#0-8) [10](#0-9) 
4. Attacker calls `claimBribe([lp])` to receive his disproportionate share. [11](#0-10) 
5. Attacker calls `unvote(lp)` to withdraw his staked vlMGP from the rewarder in the same transaction. [6](#0-5) 

I was not able to fully verify within the available context whether `VLMGP.lock()` grants vlMGP balance/voting power instantaneously upon locking (which determines exactly how large a stake an attacker can mobilize in a single transaction) since `VLMGP.sol`'s lock implementation details were not retrieved in full; this would need to be confirmed to size the practical severity of the attack, but the core reward-accounting flaw in `BaseRewardPool._provisionReward()` and the permissionless nature of `vote()`/`unvote()`/`castVotes()`/`harvestSinglePool()` are confirmed directly from the code.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {

                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
