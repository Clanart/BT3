## Title
`checkoutIndex()` accepts git's exit code 1 as unconditional success, silently swallowing checkout failures during Discard Changes - (File: `app/src/lib/git/checkout-index.ts`)

### Summary
The reported Notional bug is a case of a boolean/status value returned by a critical external operation being unconditionally accepted rather than checked, letting a failed operation continue as if it had succeeded. The Desktop analog is `checkoutIndex()`, which forces `git checkout-index` to be treated as successful whenever its exit code is `0` **or** `1`, without inspecting which paths failed or why. This function backs the "Discard Changes" feature, so a checkout-index failure caused by attacker-influenced repository state (e.g. Git LFS/clean-smudge filters wired up by Desktop itself and driven entirely by attacker-controlled `.gitattributes` in a cloned/fetched repository) can be silently absorbed, leaving the working directory out of sync with what Desktop believes was reverted.

### Finding Description
`checkoutIndex()` is defined as: [1](#0-0) 

```
const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    ...
```

`git()`'s core exec wrapper treats any exit code contained in `successExitCodes` as unconditionally acceptable and returns normally — no stderr inspection, no per-path verification — while any code *not* in that set throws: [2](#0-1) 

The doc comment for `checkoutIndex()` claims exit code 1 only happens for "paths that don't exist in the index (-q)": [3](#0-2) 

but `-q` only suppresses the specific warning for missing index paths — it does not scope exit code 1 to that case. `git checkout-index` also returns non-zero when it cannot materialize a path's content, e.g. when the blob must go through a `clean`/`smudge` filter (such as the `filter=lfs` filter that Desktop itself globally installs via `installGlobalLFSFilters`/`installLFSHooks`) and that filter fails (missing/corrupt LFS object, network error, oversized object, etc.). Since `.gitattributes` (which assigns `filter=lfs` to paths) is fully attacker-controlled content inside a cloned/fetched repository, a hostile repo can force checkout-index to fail for a specific path while `checkoutIndex()` reports success regardless.

This function is invoked from `GitStore.discardChanges()`, the implementation backing Desktop's "Discard Changes" feature, whose entire job is to guarantee the working directory is put back in sync with the index/HEAD for the files the user asked to discard: [4](#0-3) 

Because the whole operation is wrapped in `performFailableOperation` and `checkoutIndex()` never surfaces the failure, `discardChanges()` completes without error even when the working tree was not actually restored to the committed content for the affected path(s).

### Impact Explanation
"Discard Changes" is a trust-critical operation: users explicitly invoke it to eliminate specific local content before committing/pushing something else. If `checkout-index` silently fails for a path (via an attacker-primed filter path) while Desktop reports the discard as complete, the stale/local file content remains in the working directory even though the UI and any subsequent workflow (staging "Include all", committing) proceed as if the file matches HEAD. This is a silent-corruption-of-what-the-user-commits scenario driven purely by attacker-controlled repository content (`.gitattributes` + a filter Desktop itself wires up), without requiring local/physical access, admin rights, or prior malware — matching the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
The attacker only needs to get the victim to interact with a hostile repository (clone, add a remote/branch, or fetch) that declares `filter=lfs` (or another filter Desktop supports) on a target path and serves a broken/oversized/corrupt LFS object for it, then get the victim to use "Discard Changes" on a modification to that file. Because `successExitCodes` for `checkoutIndex()` accepts exit code 1 unconditionally rather than differentiating "no-op missing-path" cases from genuine filter/checkout failures, no existing guard catches this — `git()`'s generic error path (`core.ts` lines 322–353) is specifically bypassed by this widened `successExitCodes` set.

### Recommendation
Do not blanket-accept exit code 1 for `checkout-index`. Instead:
- Run without swallowing all exit-1 cases, and parse stderr to confirm the only reported condition is the benign "not in index"/"does not exist" case documented for `-q`.
- Alternatively, drop `-q` and explicitly filter out only the expected "pathspec did not match" messages while still failing (and surfacing an error to the user) for any other stderr content, mirroring the more careful pattern already used in `createDesktopStashEntry` in `app/src/lib/git/stash.ts` (lines 161–199), which inspects stderr for an `error:` prefix before deciding an exit code of 1 was actually benign.
- After `checkoutIndex()`, verify the resulting working-directory status for the affected paths matches the expected post-discard state before reporting success to the caller.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitattributes` entry `secret.txt filter=lfs diff=lfs merge=lfs -text`, and an LFS pointer for `secret.txt` that references an object which the attacker's LFS server will fail to serve (e.g., returns 500/empty) when the victim's smudge filter requests it.
2. Victim clones the repository with Desktop (LFS filters are globally installed by Desktop via `installGlobalLFSFilters`, so smudge/clean filters are already wired for any repository).
3. Victim edits `secret.txt` locally and then chooses "Discard Changes" in Desktop.
4. `GitStore.discardChanges()` calls `resetPaths()` then `checkoutIndex()`; `git checkout-index -f -u -q --stdin -z` attempts to smudge `secret.txt` via the `lfs` filter, which fails, producing an overall non-zero (1) exit code.
5. Because `checkoutIndex()` sets `successExitCodes: new Set([0, 1])`, `git()` returns normally instead of throwing; `performFailableOperation` sees no error; Desktop reports the discard as successful and refreshes status.
6. The working copy of `secret.txt` was never actually replaced with the index/HEAD content — the discard silently failed, and depending on the exact content state, the file's local (pre-discard) contents can be picked up in a later commit/push the user believes only contains reviewed, discarded-clean state.

```typescript
export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
```
