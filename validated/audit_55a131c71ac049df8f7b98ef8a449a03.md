## Title
Relayer fee withdrawal to Substrate destinations silently truncates `U256` accumulated fees to `u128`, permanently burning any balance above `u128::MAX` — (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::<T>::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads a relayer's accrued fee balance as a `U256` from the `Fees` storage map, but when the withdrawal destination is a Substrate chain it converts that value with `.low_u128()` before packing it into the outbound `WithdrawalRequest.amount: u128` field, then unconditionally zeroes the full `U256` balance in storage. This mirrors the Harpie `reduceERC721Fee` bug class exactly: an unbounded value (there `uint256` NFT id, here `U256` fee balance) is force-narrowed into a smaller fixed-width type (`uint128`/`u128`) before being acted upon, and any portion above the smaller type's range is silently discarded rather than rejected.

### Finding Description
`Fees<T>` is declared as a `StorageDoubleMap<..., U256>` [1](#0-0) , i.e. a full 256-bit accumulator with no cap, fed continuously by `accumulate_fees` every time a relayer's delivered requests are proven on Hyperbridge.

In `withdraw`, the amount actually dispatched to a Substrate destination is computed as: [2](#0-1) 

Specifically:
```rust
let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());
...
Message::WithdrawRelayerFees(WithdrawalRequest {
    amount: available_amount.low_u128(),
    ...
}).encode(),
```
`low_u128()` takes only the low 128 bits of the `U256`, wrapping (not saturating, not erroring) if `available_amount > u128::MAX`. Immediately afterward, regardless of the truncation:
```rust
Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
```
the entire on-chain balance is zeroed — including the portion that was never included in the dispatched `WithdrawalRequest.amount`. The EVM-destination branch, by contrast, correctly uses `available_amount.into()` (a lossless `U256`→ABI conversion) with no truncation, showing the Substrate branch is the outlier.

The struct being packed, `WithdrawalRequest`, deliberately types `amount` as `u128` [3](#0-2) , and the destination-side `HyperbridgeWithdrawalModule::on_accept` transfers exactly that truncated `u128` amount to the beneficiary — there is no reconciliation step anywhere that recovers the discarded high bits.

### Impact Explanation
If a relayer's accumulated `Fees` balance for a Substrate destination ever exceeds `u128::MAX`, the withdrawal silently pays out only `amount mod 2^128` while the storage record — the sole source of truth for what is owed — is wiped to zero in the same call. The excess is neither transferred nor recoverable: it is unconditionally destroyed. This is a direct "loss of funds" outcome matching the bounty's fund-loss category, arising purely from an unguarded type-narrowing cast in the reward/fee-settlement path (no relayer/prover/admin compromise required — this fires for any legitimately accrued balance that crosses the threshold, e.g. via prolonged high-volume relaying or governance-set large per-message rewards feeding the same `Fees` map through `accumulate_fees`).

### Likelihood Explanation
Reaching a `U256` value above `2^128` (~3.4×10^38) in ordinary fee-token units is extreme relative to realistic token supplies, so triggering this in the near term is unlikely under normal fee-token economics. However — exactly as in the seed report, where NFT `tokenId` values above `uint128::max` are technically valid per the ERC-721 standard even though "never seen in practice" — nothing in this pallet's types or logic prevents `Fees` from growing past `u128::MAX` over time (no cap is enforced when crediting fees), and the withdrawal path performs no bounds check before truncating and zeroing. The bug is a structural narrowing defect, not a probability-bounded one; likelihood should be read as "low today, guaranteed once the threshold is crossed," which is the same posture the original report and its confirmed fix were judged under.

### Recommendation
- Reject (rather than truncate) any withdrawal where `available_amount > U256::from(u128::MAX)`, or split it into multiple `u128`-sized withdrawal messages so no value is dropped.
- Alternatively, widen `WithdrawalRequest.amount` (and the corresponding ABI/pallet message type) to `U256`/`u256` end-to-end, matching what the EVM-destination branch already does via `.into()`, and remove the `.low_u128()` conversion entirely.
- At minimum, add an explicit `ensure!(available_amount <= U256::from(u128::MAX), Error::<T>::AmountOverflow)` guard before constructing the `WithdrawalRequest`, so the balance is preserved in storage (not zeroed) until it can be withdrawn in full.

### Proof of Concept
1. Let a relayer accrue fees for deliveries destined to/attributed on a Substrate `dest_chain` via repeated `accumulate_fees` calls (or via a large governance-configured `OutboundConsensusDeliveryReward`/`OutboundRequestDeliveryReward`) until `Fees::<T>::get(dest_chain, relayer) > U256::from(u128::MAX)`, e.g. `U256::MAX - 1`.
2. Call `withdraw_fees` with a valid signature for that relayer, targeting the Substrate `dest_chain`.
3. Inside `withdraw`, `available_amount.low_u128()` returns `available_amount % 2^128`, a value far smaller than the true balance.
4. The `WithdrawalRequest { amount: <truncated value>, .. }` message is dispatched and eventually pays the beneficiary only the truncated amount on the destination chain.
5. `Fees::<T>::insert(dest_chain, relayer, U256::zero())` executes unconditionally in the same call — the un-paid remainder (`available_amount - truncated_amount`) is now nowhere in storage and cannot ever be withdrawn. [4](#0-3)
