### Title
`SubWei` bypasses vesting/locked-coin checks, allowing gradual unauthorized transfer of locked `usei` balance via EVM wei-denominated transfers - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
`BaseSendKeeper.SubWei` implements the "wei" (sub-usei precision) balance debit used by the EVM `StateDB` and the bank precompile's `sendNative`. Unlike `SubUnlockedCoins`, which always checks `LockedCoins` before reducing an account's `usei` balance, `SubWei` falls back to directly calling `k.setBalance` on the full `usei` balance whenever the requested wei amount exceeds the account's stored wei dust — with no `LockedCoins`/vesting check whatsoever.

### Finding Description
The GMX report's underlying bug class is that a value is keyed/tracked using one representation (initial collateral token) while the actual accounting/liquidity check is performed against a different, decoupled representation (short token), allowing a technically-backed value to be mishandled. sei-chain has a directly analogous split: native token balances are represented in two coupled units, `usei` (bank `Coins`) and sub-usei `wei` dust (a separate KV store), reconciled via `SplitUseiWeiAmount`/`OneUseiInWei`.

`SubUnlockedCoins`, the normal bank debit path, correctly computes `spendable := balance - LockedCoins(addr)` before allowing a debit [1](#0-0) . However, `SubWei` — invoked from the EVM `StateDB.SubBalance` for the fractional wei component of every EVM value transfer, and from the bank precompile's `sendNative`/`HandlePaymentUseiWei` path — does not consult `LockedCoins` at all: [2](#0-1) 

When the requested wei amount exceeds the account's current wei dust, it computes `currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)` using the account's **total** `usei` balance (via `k.GetBalance`), not its spendable (unlocked) balance, and then unconditionally calls `k.setBalance` to write the new (lower) `usei` balance. This means an account with a vesting/locked `usei` balance can have its otherwise-untouchable `usei` reduced by up to 1 `usei` per call, entirely bypassing the vesting lock enforced everywhere else in the bank module.

`SubBalance` in the EVM `StateDB` reflects this split explicitly: the whole-`usei` portion goes through the lock-respecting `SubUnlockedCoins`, but the sub-usei remainder goes through the lock-blind `SubWei`: [3](#0-2) 

The same duplicated implementation exists in `giga/deps/xbank/keeper/send.go`: [4](#0-3) 

And it is reachable from the bank precompile's native-send entrypoint used by any EVM contract or EOA: [5](#0-4) 
via `HandlePaymentUseiWei`, which calls `SendCoinsAndWei` (internally exercising the same `SubWei`/`AddWei` pair): [6](#0-5) 

### Impact Explanation
Any address holding a vesting/locked `sei-cosmos/x/auth/vesting` account balance that has also been associated with an EVM address can issue ordinary EVM transactions carrying a small `value` (fractional-usei/wei amounts) — e.g., plain value transfers or calls into the bank precompile's `sendNative` — to repeatedly force `SubWei` down the "insufficient wei dust" branch. Each such call decrements the account's raw `usei` balance by up to 1 `usei`, without any regard to `LockedCoins`, effectively laundering locked/vesting funds into a spendable/transferable form one `usei` unit at a time. Executed iteratively (a fully automatable, unprivileged process requiring only gas), this permits gradual unauthorized transfer of funds that should remain frozen under a vesting schedule, undermining the fund-freezing guarantee vesting is meant to provide.

### Likelihood Explanation
The path is reachable by any unprivileged EVM transaction sender or contract caller — no special privileges, precompile authority, or validator/consensus access are required. The only precondition is that the sender's Sei address has locked (vesting) coins and an EVM-address association; both are standard, attacker-controllable conditions. Because the primitive frees at most ~1 `usei` (1e-6 SEI) per transaction, an attacker needs to submit many transactions to meaningfully drain a large locked balance, which is a rate-limiting factor, but the exploit is fully deterministic, requires no race condition or validator collusion, and is trivially scriptable given Sei's low gas costs.

### Recommendation
Update `SubWei` (in both `sei-cosmos/x/bank/keeper/send.go` and its `giga/deps/xbank/keeper/send.go` counterpart) to compute the fallback aggregated balance using the account's **spendable** `usei` balance (`GetBalance(...) - LockedCoins(...)`) rather than the raw `GetBalance` total, mirroring the check already performed in `SubUnlockedCoins`. Alternatively, route the fallback path for the whole-`usei` portion through `SubUnlockedCoins` instead of a direct `setBalance` call, so vesting/lock invariants are enforced consistently regardless of whether a debit originates from the `usei` or `wei` accounting path.

### Proof of Concept
1. Create/fund a vesting (e.g., continuous or delayed) account `A` with a locked `usei` balance (e.g., 1,000,000 `usei`, fully locked, 0 unlocked, 0 wei dust) and associate it with EVM address `evmA` via `utils/helpers/associate.go`.
2. From `evmA`, repeatedly send EVM transactions with a nonzero `value` field expressed such that `SplitUseiWeiAmount(value)` yields `usei = 0, wei = 1` (i.e., set `value` to `1` wei), targeting any recipient (a plain EOA transfer, or a call to the bank precompile's `sendNative`).
3. Each such transaction triggers `StateDB.SubBalance` → `SubWei(ctx, A, 1)`. Since `A`'s stored wei dust is `0`, `amt.LTE(currentWeiBalance)` is false, so the code falls into the branch that reads `GetBalance(A, "usei")` (the full 1,000,000, entirely locked) and calls `setBalance` to write a reduced `usei` balance (999,999), with `weiBalance` set to `OneUseiInWei - 1`.
4. Observe that `A`'s bank balance in `usei` decreases despite `LockedCoins(ctx, A)` still reporting the full locked amount — no `ErrInsufficientFunds`/lock violation is raised, even though `SubUnlockedCoins` would have rejected an equivalent debit.
5. Repeating this process (or issuing a single larger wei value close to `OneUseiInWei` per transaction to accelerate the drain) will progressively reduce `A`'s on-chain `usei` balance below the amount `LockedCoins` says should remain untouchable, and the freed `usei` is now spendable/transferable by `A`, confirming the vesting-lock bypass.

func (k BaseSendKeeper) SubWei(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Int) (err error) {
	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiSpentEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	if amt.LTE(currentWeiBalance) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, currentWeiBalance.Sub(amt))
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)
	postAggregatedbalance := currentAggregatedBalance.Sub(amt)
	if postAggregatedbalance.IsNegative() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%swei is smaller than %swei", currentAggregatedBalance, amt)
	}
	useiBalance, weiBalance := SplitUseiWeiAmount(postAggregatedbalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), useiBalance), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}

func (p Precompile) sendNative(ctx sdk.Context, method *abi.Method, args []interface{}, caller common.Address, callingContract common.Address, value *big.Int, readOnly bool, hooks *tracing.Hooks, evm *vm.EVM) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call sendNative from staticcall")
	}
	if caller.Cmp(callingContract) != 0 {
		return nil, errors.New("cannot delegatecall sendNative")
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, err
	}
	if value == nil || value.Sign() == 0 {
		return nil, errors.New("set `value` field to non-zero to send")
	}

	senderSeiAddr, ok := p.evmKeeper.GetSeiAddress(ctx, caller)
	if !ok {
		return nil, errors.New("invalid addr")
	}

	receiverAddr, ok := (args[0]).(string)
	if !ok || receiverAddr == "" {
		return nil, errors.New("invalid addr")
	}

	receiverSeiAddr, err := sdk.AccAddressFromBech32(receiverAddr)
	if err != nil {
		return nil, err
	}

	usei, wei, err := pcommon.HandlePaymentUseiWei(ctx, p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address), senderSeiAddr, value, p.bankKeeper, p.evmKeeper, hooks, evm.GetDepth())
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei); err != nil {
		return nil, err
	}

func HandlePaymentUseiWei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Int, sdk.Int, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoinsAndWei(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, usei, wei); err != nil {
		return sdk.Int{}, sdk.Int{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return usei, wei, nil
}
