### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/fee/standardness accounting, so `needed_fee()` and the `TooLargeTransaction` check report values for a smaller transaction than the one actually signed - (networks/bitcoin/src/wallet/send.rs)

### Summary
The audit finding is a view function (`maxWithdraw`) that computes a limit from an accounting figure (`totalAssets()`) which does not reflect the constraint actually enforced on the spend path (`totalReleasedAssets -= amount`), so it reports a withdrawable amount that reverts when used. The direct analog in Serai is `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: the transaction actually emitted includes an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data`, but every accounting computation — the virtual-size estimate, the `needed_fee` reported to callers, the `NotEnoughFunds` sufficiency check, and the `MAX_STANDARD_TX_WEIGHT` standardness check — is performed by `calculate_weight_vbytes`, which reconstructs the transaction using only `payments` and `change` and never includes the OP_RETURN output. The function therefore reports feasibility/fee figures for a strictly smaller transaction than the one that gets signed and broadcast.

### Finding Description
In `SignableTransaction::new`, when `data` is `Some`, an `OP_RETURN` `TxOut` is pushed onto `tx_outs` (lines 194–202). However, weight accounting is computed by `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and later `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (lines 225–226). Inside `calculate_weight_vbytes` (lines 62–127), the dummy transaction's `output` vector is built *only* from `payments` plus an optional `change` output — the OP_RETURN output is never represented. Consequently:

1. `vbytes` is underestimated by up to ~80+ bytes of serialized output (9-byte value + compactsize length + script bytes) whenever `data` is supplied.
2. `needed_fee = fee_per_vbyte * vbytes` (line 206) is under-reported — the value returned by `needed_fee()` (lines 133–135) and propagated through `Network::needed_fee` in `processor/src/networks/bitcoin.rs` (lines 803–815) is lower than the fee actually required to achieve `fee_per_vbyte` on the final transaction.
3. The `TooLowFee` minimum-relay-fee check (line 211) can pass for a transaction whose real feerate is below `DEFAULT_MIN_RELAY_TX_FEE`.
4. The `NotEnoughFunds` check (line 215) uses the underestimated `needed_fee`.
5. The `MAX_STANDARD_TX_WEIGHT` check (line 241) is computed on `weight` that excludes the OP_RETURN output, so a transaction that is actually non-standard can be accepted, signed by the whole FROST flow (`TransactionSignMachine::sign`, lines 355–398), and then be rejected by the Bitcoin network.

This is the same bug shape as the original: the "report" side (`calculate_weight_vbytes`) and the "execution" side (`tx_outs` actually committed into `self.tx.output`) disagree about what is in the transaction, so values the caller relies on (`needed_fee`, and the implicit guarantee that the produced transaction is standard and adequately funded) are computed on a different object than the one signed.

### Impact Explanation
An integrator following the documented flow — call `needed_fee`, fund accordingly, then `signable_transaction` — produces a signed transaction paying a lower feerate than requested, potentially below the minimum relay feerate or the node's mempool requirements, or exceeding `MAX_STANDARD_TX_WEIGHT` without triggering `TooLargeTransaction`. The threshold-signed transaction is then unbroadcastable/stalls despite all checks having passed, mirroring the original report's "withdrawal amount reported by `maxWithdraw` reverts when actually used." Inputs committed as `prevouts` (line 253) are locked into a sighash-committed transaction (`Prevouts::All`, line 375) that the network will not accept, stranding the plan.

### Likelihood Explanation
The bug triggers whenever `data` is `Some(..)` in `SignableTransaction::new` — a public caller-controlled parameter. In the bundled processor (`processor/src/networks/bitcoin.rs`, line 450) `None` is always passed, so the deployed processor doesn't hit it; it affects integrators of the `bitcoin-serai` wallet library using the `data` feature. The miscalculation is deterministic (no race or adversarial timing needed), but the practical effect — relay rejection — additionally depends on the resulting feerate/weight crossing a policy boundary, which caps severity around Medium.

### Recommendation
Include the OP_RETURN output in `calculate_weight_vbytes`: pass the serialized `data` (or the already-built `tx_outs`/`TxOut` list) into the weight reconstruction so `weight`, `vbytes`, `needed_fee`, the `TooLowFee` check, the `NotEnoughFunds` check, and the `MAX_STANDARD_TX_WEIGHT` check are all computed over the exact output set that will appear in `self.tx.output`. Alternatively, add a `debug_assert`/`assert` after construction that `self.tx.weight()` equals the estimated `weight`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Conceptual PoC — using the public API:

let inputs = vec![received_output];                    // funds the TX
let payments = vec![(payment_script, payment_amount)]; // >= DUST
let data = vec![0u8; 80];                              // max allowed

let tx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte)
  .unwrap();                                           // passes all checks

// The real transaction contains the OP_RETURN output
assert_eq!(tx.transaction().output.len(), payments.len() + 1);

// But needed_fee was computed on a tx WITHOUT the OP_RETURN output:
// actual vsize > vbytes used internally, so
//   tx.fee() < fee_per_vbyte * tx.transaction().vsize()
// i.e. the achieved feerate is strictly below `fee_per_vbyte`, and can
// fall under DEFAULT_MIN_RELAY_TX_FEE despite the TooLowFee check passing.
```
Concretely: `calculate_weight_vbytes` (send.rs:85–93) builds `tx.output` only from `payments` plus `change` (lines 95–99), while the OP_RETURN `TxOut` pushed at lines 194–202 is absent from that reconstruction yet present in the final `Transaction` at lines 246–251, so every fee/weight figure is computed on a different transaction than the one signed by `TransactionSignMachine::sign` (lines 373–397).
