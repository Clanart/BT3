### Title
Verifier silently skips challenge on mainnet/testnet4 for malicious kickoffs, enabling unchallenged fraudulent reimbursement — (File: core/src/verifier.rs)

---

### Summary

On `bitcoin::Network::Bitcoin` (mainnet) and `bitcoin::Network::Testnet4`, `handle_kickoff` detects a malicious kickoff and returns `is_malicious = true`, which causes the state machine to mark the round as "challenged." However, no challenge transaction is actually queued. The operator's pre-queued `ChallengeTimeout` transaction then fires after the timelock, allowing the operator to collect a full reimbursement for a fraudulent payout without ever being challenged.

---

### Finding Description

In `core/src/verifier.rs` lines 1998–2016, `handle_kickoff` explicitly gates challenge submission behind a network check:

```rust
// do not automatically send challenge txs on mainnet or testnet4
if !challenged_before
    && !matches!(
        self.config.protocol_paramset().network,
        bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
    )
{
    #[cfg(feature = "automation")]
    self.tx_sender
        .add_tx_to_queue(dbtx, TransactionType::Challenge, &challenge_tx, ...)
        .await?;
}
```

The function still returns `Ok(is_malicious)` — `true` — regardless of whether the challenge was queued. That return value flows directly into the state manager in `core/src/states/event.rs` lines 376–390:

```rust
DutyResult::CheckIfKickoffMalicious { challenged } => {
    if challenged && !was_challenged_before {
        round_machine.handle_with_context(
            &RoundEvent::SetChallenged { round_idx: kickoff_data.round_idx },
            context,
        ).await;
    }
}
```

So on mainnet/testnet4 the round is marked as `challenged = true` in the DB even though zero challenge bytes were broadcast. The `challenged_before` guard then suppresses any future challenge attempt for the same round.

Meanwhile, the operator's automation path in `queue_relevant_txs_for_new_kickoff` (`core/src/operator.rs` lines 2482–2503) unconditionally queues `ChallengeTimeout` for every new kickoff:

```rust
TransactionType::ChallengeTimeout | ... => {
    self.tx_sender.add_tx_to_queue(...).await?;
}
```

`ChallengeTimeout` spends the `Challenge` UTXO via `ScriptSpend(1)` with a relative timelock of `operator_challenge_timeout_timelock` blocks (`core/src/builder/transaction/challenge.rs` lines 371–388). Because no challenger spent that UTXO first, the operator's `ChallengeTimeout` confirms after the timelock, spending the `KickoffFinalizer` and closing the kickoff as if it were honest. The operator then collects the full bridge amount via the `Reimburse` transaction.

**Attack path (mainnet/testnet4):**

1. Operator fronts a payout for deposit D, records a fraudulent `payout_blockhash` in the kickoff witness (wrong block or wrong chain).
2. Verifier calls `is_kickoff_malicious` → `true`; logs a warning; does **not** queue `Challenge`.
3. State machine sets `challenged_rounds` for this round → `true` (no further challenge attempts will be made).
4. Operator's `ChallengeTimeout` fires after `operator_challenge_timeout_timelock` (144 blocks ≈ 1 day on mainnet).
5. `KickoffFinalizer` is spent; kickoff transitions to `Closed`.
6. Operator sends `ReadyToReimburse` → `Reimburse`, recovering the full `bridge_amount` (1 BTC = 1 000 000 000 sat in the production config) from the `MoveToVault` UTXO.

The depositor's BTC is permanently lost; the operator's collateral is never burned.

---

### Impact Explanation

Direct theft of bridged BTC equal to `bridge_amount` per fraudulent kickoff. With `num_kickoffs_per_round = 100` and `num_round_txs = 200` (production `run.sh` values), a single operator can drain up to 200 × 100 = 20 000 BTC across all pre-signed rounds before collateral is exhausted. The `CollateralInRound` UTXO is never touched because no `Disprove` or `OperatorChallengeNack` is ever sent.

---

### Likelihood Explanation

The condition is trivially reachable on any mainnet or testnet4 deployment: the operator simply commits a wrong blockhash in the kickoff witness. The verifier's detection logic (`is_kickoff_malicious`, lines 1859–1914) will flag it, but the challenge suppression fires unconditionally for those two networks. The only mitigation is out-of-band human monitoring that manually broadcasts the challenge transaction within 144 blocks — a hard real-time constraint with no automated fallback in the codebase.

---

### Recommendation

Remove the network-gated suppression or replace it with a manual-approval queue that still guarantees timely submission. At minimum, the `challenged` flag returned to the state machine must reflect whether a challenge was **actually queued**, not merely whether the kickoff was detected as malicious. Returning `true` when no challenge was sent causes the state machine to permanently suppress future challenge attempts for the same round, compounding the liveness failure into a safety failure.

---

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}
