### Title
ReDoS heuristic bypass via bounded `{m,n}` quantifiers in user `security-patterns.yaml` regex — `_has_redos_structure()` fails to flag catastrophic-backtracking patterns, enabling hook-blocking DoS on every Write/Edit - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_has_redos_structure()` only detects nested repetition/alternation shapes that use the literal characters `+`, `*`, or `?` (`_REDOS_SHAPES`, `_ALT_UNDER_REP`). A regex that achieves the exact same nested-quantifier catastrophic-backtracking structure using bounded `{m,n}` repetition instead of `+`/`*` is not matched by either static check, so `_validate_pattern()` accepts it and it is compiled into a rule used by `check_patterns()` on every subsequent `Write`/`Edit`/`MultiEdit` PostToolUse invocation for the session.

### Finding Description
`_REDOS_SHAPES` requires a literal `[+*]` inside the group and `[+*?]` immediately after the closing paren: [1](#0-0) 
`_ALT_UNDER_REP` only fires on `(...|...)[+*]` alternation shapes. Neither construct recognizes `{m,n}` bounded quantifiers as repetition operators. A regex such as `(a{1,25}){1,25}` (or, more perniciously, `(\s{1,30}){1,30}$`, which targets ordinary indentation/whitespace runs present in normal code) is structurally identical to the classic nested-quantifier ReDoS shape `(a+)+` but contains no `+`/`*`/`?` characters at all, so:

- `_REDOS_SHAPES` regex 1 doesn't match (no `+`/`*` inside the parens, no `+*?` suffix — it's `{1,25}`).
- `_REDOS_SHAPES` regex 2 doesn't match (no `.*`).
- `_ALT_UNDER_REP` doesn't match (no `|`).

`_has_redos_structure()` returns `False`, `_validate_pattern()` proceeds to `re.compile(regex)` (which succeeds — the regex is syntactically valid) and stores it as `rule["regex"]`: [2](#0-1) 
This rule is loaded once per session via `_load_user_patterns()`/`load_for_session()` and merged into every pattern check: [3](#0-2) 
`re.search(pattern["regex"], content)` has no timeout, size cap, or backtracking guard — it runs synchronously inside the PostToolUse hook process for every `Write`/`Edit`/`MultiEdit` call, on the exact content the victim (or Claude) writes: [4](#0-3) 
The `hooks.json` PostToolUse entry for `Edit|Write|MultiEdit|NotebookEdit` has no explicit timeout override, so it relies on Claude Code's default hook timeout, but every subsequent edit will re-trigger the same expensive `re.search` call, effectively stalling or repeatedly failing the file-edit hook for the remainder of the session: [5](#0-4) 

### Impact Explanation
Once loaded, the malicious rule is evaluated against the content of every `Write`/`Edit`/`MultiEdit` tool call for the rest of the session because it is unconditionally appended to `SECURITY_PATTERNS` inside `check_patterns()`. If the crafted regex's catastrophic-backtracking trigger condition (e.g., a moderately long run of whitespace or a repeated character) is commonly present in ordinary source content — not just attacker-supplied content — nearly every edit in the session can hang the PostToolUse hook for extended periods, degrading or blocking the workspace/session's file-editing availability. This matches a denial-of-service / hook-availability impact: the pattern-based guard enforcement effectively becomes unusable (hangs) for the session, and legitimate edits are delayed or fail due to hook timeout.

### Likelihood Explanation
Preconditions are modest and match the threat model: an unprivileged attacker only needs to get a `.claude/security-patterns.yaml` (or `.json`) file merged into a repository the victim later opens with Claude Code — no privilege escalation, no secret leakage, and no special content control is required if the trigger pattern (e.g., whitespace runs) is common in real code. The bypass is deterministic and repeatable: the two static heuristics in `_has_redos_structure()` are pure syntactic checks against `+`/`*`/`?`/alternation and never consider `{m,n}` quantifiers, so any crafted `{m,n}`-based nested-repetition regex reliably slips through on every load.

### Recommendation
Extend `_has_redos_structure()` to normalize `{m,n}`, `{m,}`, and `{0,}`/`{1,}` quantifiers (including trivial `{1,1}` no-ops around literals) to the same repetition class as `+`/`*` before applying `_REDOS_SHAPES` and `_ALT_UNDER_REP` (e.g., pre-process the regex string to replace `{n,m}` tokens with a canonical `*`/`+` marker, or extend the shape regexes to also match `\{[0-9]*,[0-9]*\}` after a group). More robustly, do not rely solely on static heuristics: enforce a hard wall-clock/CPU timeout around each `re.search()` call in `check_patterns()` (e.g., via a worker thread/process with `concurrent.futures` and a timeout, or an per-call `signal.alarm`/`SIGALRM` on POSIX, or run the compiled user regexes once against a small corpus of adversarial strings — long repeated-char runs — at load time and reject any that exceed a time budget), so that even an undetected catastrophic regex cannot stall the hook.

### Proof of Concept
Unit/fuzz test to add near `_has_redos_structure` tests:
```python
import re, time
from extensibility import _has_redos_structure

def test_bounded_quantifier_redos_bypass():
    evil = r"(\s{1,30}){1,30}$"
    assert _has_redos_structure(evil) is False  # bypasses heuristic

    content = " " * 40 + "X"  # ordinary-looking whitespace run + non-match tail
    start = time.monotonic()
    re.search(evil, content)
    elapsed = time.monotonic() - start
    assert elapsed > 2.0  # demonstrates catastrophic backtracking despite "safe" verdict
```
Integration variant: place `evil` as `regex` in `.claude/security-patterns.yaml`, call `extensibility.load_for_session(cwd)`, then invoke `security_reminder_hook.check_patterns(file_path, content)` with `content` containing a realistic indentation/whitespace run, and assert the call exceeds a defined wall-clock bound (e.g., 1s), demonstrating the PostToolUse hook would hang on an ordinary edit.
