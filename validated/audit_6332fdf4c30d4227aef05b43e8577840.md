### Title
Integer overflow in Bitcoin fee calculation signs transactions at an unintended fee rate - ([File: `networks/bitcoin/src/wallet/send.rs`](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` multiplies a caller-supplied `fee_per_vbyte` by the transaction's virtual size using unchecked `u64` arithmetic. A sufficiently large fee rate wraps modulo `2^64`, causing `needed_fee` to become a small attacker-selected value while the resulting transaction is still accepted and signed. This produces a valid Bitcoin transaction paying a materially different fee from the requested construction parameters. [1](#0-0) [2](#0-1) 

### Finding Description

The transaction builder accepts `payments`, `change`, and `fee_per_vbyte` as inputs and computes `needed_fee` with `fee_per_vbyte * vbytes`. Neither the multiplication nor the subsequent `payment_sat + needed_fee` addition uses `checked_mul` or `checked_add`. In release builds without overflow checks, these operations wrap modulo `2^64`. [1](#0-0) [3](#0-2) 

For a transaction with an even virtual size `vbytes`, choosing `fee_per_vbyte = 2^63 + 1` makes the multiplication wrap to `vbytes`:

```text
vbytes * (2^63 + 1) mod 2^64 = vbytes
```

The wrapped value equals the default minimum relay fee calculation of approximately one satoshi per vbyte, so it passes the minimum-fee check. The insufficient-funds check then compares inputs against the wrapped fee rather than the requested astronomical fee. [4](#0-3) 

The same unchecked multiplication is repeated when calculating `fee_with_change`, so transactions containing a change output are affected as well. [5](#0-4) 

### Impact Explanation

An unprivileged party who can submit a transaction proposal or influence its fee-rate parameter can cause the threshold signer to authorize a transaction whose actual fee is completely different from the requested fee. The resulting transaction is consensus-valid if its outputs remain funded by the supplied inputs, but it may pay only the minimum relay fee despite the signing request specifying an enormous fee rate. Because the signed sighash commits to the final outputs and prevouts rather than the caller's intended `fee_per_vbyte`, the signature authorizes this altered transaction. [6](#0-5) [7](#0-6) [8](#0-7) 

This can cause signed payments to remain unconfirmed or otherwise violate the economic parameters authorized by the transaction initiator. The issue does not allow an attacker to redirect the payment outputs directly through this arithmetic alone, so the concrete impact is signing an unintended valid transaction rather than direct theft of the payment amount. [9](#0-8) [7](#0-6) 

### Likelihood Explanation

The vulnerability is deterministic whenever an attacker-controlled or externally supplied `fee_per_vbyte` is large enough to wrap the multiplication. No race, malformed encoding, invalid curve point, or malicious validator is required. The only prerequisite is that the signing flow accepts transaction-construction parameters from an untrusted proposal or service before invoking `SignableTransaction::new`. [1](#0-0) [4](#0-3) 

### Recommendation

Use `checked_mul` for both fee calculations and `checked_add` for every sum of payments and fees. Reject overflow with `TransactionError::TooLowFee` or a new explicit arithmetic-overflow error. Also enforce a documented maximum supported fee rate and compute the exact actual fee as `sum(inputs) - sum(outputs)` with checked arithmetic before constructing the `SignableTransaction`. [10](#0-9) [11](#0-10) 

### Proof of Concept

For any payment set whose no-change virtual size `vbytes` is even, construct one input with:

```text
input_value = payment_total + vbytes
fee_per_vbyte = 2^63 + 1
```

Inside `SignableTransaction::new`, the calculation becomes:

```text
needed_fee
  = vbytes * (2^63 + 1) mod 2^64
  = vbytes
```

The minimum-fee check accepts this value, and the funds check succeeds because `input_value == payment_total + needed_fee`. The returned transaction has only the requested payment output and therefore pays `input_value - payment_total = vbytes` sats, or one satoshi per vbyte, despite requesting `2^63 + 1` sats per vbyte. [12](#0-11) [7](#0-6) 

If an odd virtual size is encountered, adjust the payment count, script sizes, or input count to obtain an even size, or solve the equivalent modular equation `vbytes * fee_per_vbyte ≡ desired_fee (mod 2^64)` for an attacker-controlled `fee_per_vbyte`.
