## Analysis

The reported class of bug — a governance-controlled asset/config address being changed while transfers are mid-flight, breaking the refund/claim path and stranding funds — has a direct, stronger analog in `pallet-hyper-fungible-token`, and it lacks the safety check that `EvmHost.updateHostParams` already has for its own analogous case (`CannotChangeFeeToken`, which requires the old fee-token balance to be zero before the address can change).

### Title
`update_token` can permanently strand or destroy in-flight cross-chain transfers by remapping/removing the `ContractToAsset` reverse lookup used by `on_timeout` — (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::send` escrows or burns a user's local asset and dispatches a cross-chain ISMP `PostRequest` to the `TokenContracts` address configured for the destination chain at that moment [1](#0-0) . If that request times out, `on_timeout` refunds the escrow (or re-mints) by looking up the asset from `ContractToAsset::<T>::get(dest, &to)`, where `to` is the destination contract address baked into the original request [2](#0-1) .

`update_token` (callable by `CreateOrigin` at any time, with no check for in-flight requests) rewrites `TokenContracts` for a chain to a new contract address and **removes** the old `ContractToAsset` reverse mapping entirely: [3](#0-2) 

Unlike `EvmHost.updateHostParams`, which explicitly guards against changing the fee token while a nonzero balance is still owed (`CannotChangeFeeToken` in `evm/src/core/EvmHost.sol` lines 617-621), `update_token`/`register_token` has no equivalent invariant: there is exactly one live `(chain, asset)` → contract mapping, and the reverse mapping is unconditionally deleted the moment governance points the chain at a new (or removed) contract.

### Finding Description
1. A user calls `send`, which escrows (native asset) or burns (non-native asset) their tokens and dispatches a `DispatchPost` to the current `TokenContracts[dest, asset]` address ("contract A") [4](#0-3) .
2. Before the request is delivered/relayed (still within its challenge/timeout window), `CreateOrigin` calls `update_token` to migrate the token contract for that chain to a new address ("contract B") — e.g., a routine contract redeployment/migration, exactly the kind of legitimate operational action the original report's `setStablecoin` represents. This removes `ContractToAsset[dest, A]` [5](#0-4) .
3. The original request to contract A subsequently times out. `on_timeout` looks up `ContractToAsset::<T>::get(dest, &to)` where `to == A`. Since that entry no longer exists, the lookup fails with `HftError::UnknownContractOnTimeout` and the whole timeout dispatch errors out [6](#0-5) .
4. Because the refund transfer/mint never executes, the user's escrowed tokens remain locked in `pallet_account()` forever (native asset custody model) or are simply gone with no compensating re-mint (non-native/burn model) — an unrecoverable loss of user funds with no admin function to reconcile it, since `TokenContracts`/`ContractToAsset` only ever holds the single current mapping per chain.

The same broken invariant also affects the inbound path: `on_accept` authenticates incoming messages via `ContractToAsset::<T>::get(source, &from)` [7](#0-6) ; if governance updates the peer contract address for a chain while an EVM-side transfer to this pallet is already burned/locked on the remote side and in flight, the pallet will reject it as `UnknownSourceContract` and the corresponding funds are lost on the sending chain as well.

### Impact Explanation
This is a direct loss-of-funds bug: user assets that were legitimately escrowed or burned by `send` can become permanently unrecoverable purely as a side effect of a normal governance maintenance action (token contract migration), with no code path to reconcile old in-flight commitments against the new mapping. This matches the required impact "stealing or loss of funds" and reflects exactly the invariant violated in the seed report — a single mutable global address binding that in-flight obligations implicitly depend on, with no draining/quiescence check analogous to `CannotChangeFeeToken` in `EvmHost`.

### Likelihood Explanation
`update_token`/`register_token` are ordinary, expected operational calls (e.g., re-registering a chain after a contract redeploy, or adding decimal/precision fixes) rather than adversarial governance actions, and pending in-flight `send` requests are the normal, expected state for any active token given ISMP's finality/challenge-period latency. No attacker action, malicious relayer, or compromised key is required — only ordinary use of `update_token` racing with ordinary in-flight transfers, which will occur naturally over the token's operational lifetime.

### Recommendation
Before allowing `update_token`/`register_token` to overwrite or remove a `(chain, asset)` contract mapping, either: (a) retain the old `ContractToAsset` reverse-mapping entries indefinitely (or until explicitly swept) so `on_timeout`/`on_accept` can still resolve historical in-flight commitments, or (b) require the chain's mapping to remain drainable/quiescent (e.g., track and require zero outstanding un-settled requests for that `(chain, asset)` pair) before allowing the contract address to change, mirroring the `CannotChangeFeeToken` invariant already enforced in `EvmHost.updateHostParamsInternal`.

### Proof of Concept
1. Register asset `X` as native (escrowed) with `TokenContracts[Evm(1), X] = A`.
2. User calls `send(asset_id=X, destination=Evm(1), amount=100, timeout=T)` → 100 units of `X` moved into `pallet_account()`; `DispatchPost` sent with `to = A`.
3. Before the request is relayed/times out, governance calls `update_token` with `add_chains = {Evm(1): {token_contract: B, decimals: d}}`. This deletes `ContractToAsset[Evm(1), A]` and inserts `ContractToAsset[Evm(1), B]`.
4. The original request eventually times out (or was never delivered/expired). `on_timeout` is invoked with `to = A`, calls `ContractToAsset::<T>::get(Evm(1), A)` → `None` → returns `Err(HftError::UnknownContractOnTimeout)`.
5. The refund never executes; the user's 100 units of `X` remain stuck in `pallet_account()` permanently, with no extrinsic available to release them back to the sender.
