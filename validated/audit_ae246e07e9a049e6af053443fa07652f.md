## Finding

Reducing the Compound bug to its core: a **security guardian meant to gate a sensitive state-mutation is explicitly disabled/bypassed at the exact call site that performs the sensitive operation**, and no other code path re-enforces it. The GitHub Desktop analog is the same pattern applied to Git's own clone-time safety mechanism.

### Title
Clone operation forcibly disables Git's own clone-protection guardian (`GIT_CLONE_PROTECTION_ACTIVE=false`) while cloning attacker-controlled repositories with `--recursive` - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in [1](#0-0)  explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before invoking `git clone --recursive` against a URL that is fully attacker-controlled (any remote/deep-link URL the user opens or types in). `GIT_CLONE_PROTECTION_ACTIVE` is Git's own internal "we are actively cloning, be extra defensive" sentinel, used by Git's checkout/read-tree machinery to detect and refuse writes that would escape the working tree (e.g. via symlinked `.git` directories, case-insensitive filesystem collisions with `.git`, and similar tricks used to smuggle files like hooks or config outside the intended checkout root during a clone). By pinning this flag to `'false'` unconditionally, Desktop turns off that guardian for every clone it performs, including the automatic `--recursive` submodule clone, at precisely the moment an attacker-controlled repository's content is being written to disk.

### Finding Description
The `clone()` function does perform one guard — `isClonePathSensitive()` — which checks the *destination* path against a hard-coded blocklist (home dir, `.ssh`, `.gnupg`, `.config/git`, etc.) at [2](#0-1) . That guard only protects against the destination itself being a sensitive directory; it does nothing about files being written *inside* the destination tree via symlink/traversal tricks that Git's native clone-protection logic exists to catch.

Immediately after that check, the code builds the environment for the git subprocess and hard-codes the protection flag off: [3](#0-2) 

...then runs `clone --recursive` against the attacker-supplied `url`, which will also process any submodules and their own nested clones, all without the protection active: [4](#0-3)  and [5](#0-4) 

There is no other location in the codebase that re-sets or re-enables `GIT_CLONE_PROTECTION_ACTIVE`; a repo-wide search found only this single occurrence, so nothing downstream compensates for the disabled guardian.

This is the same broken-invariant shape as the Compound report: a protective check that is supposed to be enforced during a state-changing operation (there: crediting limits while paused; here: writing files to disk while cloning) is turned off exactly at the site that performs the operation, and no other check fills the gap.

### Impact Explanation
If an attacker can get a victim to clone or "Open in Desktop" a crafted repository (a git remote fully under attacker control — satisfies the "attacker controls a cloned/fetched repository" impact class), the clone runs with Git's own clone-time file-write protections disabled. Depending on the underlying Git version's specific protections this flag guards, this can enable writing files outside the intended working directory during clone/recursive-submodule-clone (e.g. via symlink or case-collision tricks targeting `.git`), which is the class of bug the flag exists to stop. That corresponds to "file write... outside the repo" and potentially code execution if the escaped write lands in a location Git or the OS will later execute (hooks, shell profile files, etc.).

### Likelihood Explanation
High reachability: `clone()` is invoked from the standard "Clone repository" UI flow, the `x-github-client://openRepo/...` deep-link handler (`open-repository-from-url` → `openOrCloneRepository` → clone dialog, see [6](#0-5) ), and the CLI `--cli-clone` argument ( [7](#0-6) ). All of these accept a URL that is either typed by the user or embedded in a link/deep-link an attacker can craft, matching the "link or deep link the user clicks" / "git remote" attacker profile in scope. No local access, admin rights, or prior compromise is required — only that the victim clones or opens the attacker's repository/link, which is the normal, expected use of the "Clone repository" and "Open in Desktop" features.

### Recommendation
Remove the hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in [3](#0-2)  so Git's native clone-protection guardian remains active for both the top-level clone and the `--recursive` submodule clone. If the override was added to work around a specific compatibility issue, it should be scoped narrowly (e.g., only for trusted/local operations) rather than applied unconditionally to every clone of an arbitrary, attacker-suppliable URL, and should be paired with an explicit justification/comment and test coverage proving the protection can't be silently disabled for untrusted remotes.

### Proof of Concept
1. Attacker hosts a malicious Git repository (or a repository with a malicious submodule) that relies on a technique Git's clone-protection is designed to block (e.g., a submodule/`.git` entry using a symlink or case-collision path to write outside the checkout root during clone).
2. Attacker sends the victim a link such as `x-github-client://openRepo/<attacker-repo-url>` or simply shares the clone URL.
3. Victim clicks the link (handled by `handleAppURL` → `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository`, see [8](#0-7)  and [6](#0-5) ) or pastes the URL into "Clone repository."
4. Desktop calls `clone()` in [1](#0-0)  with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` and `--recursive` enabled, running the clone (and any submodule clones) with Git's protective checks disabled — the same disabled state that the existing `isClonePathSensitive` destination check does not detect or prevent, since that check only inspects the top-level destination path, not writes performed during the clone itself.

Note: I was not able to execute this against a live Git binary to confirm the exact CVE/version-specific behavior gated by `GIT_CLONE_PROTECTION_ACTIVE` in the bundled Git version, since I only have read access to the indexed source, not a runtime environment. A Devin session with terminal access could confirm the precise write-outside-tree PoC against the bundled `dugite`/Git version.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

      this.doesRepositoryMatchUrl(r, url)
