### Title
Reward double-counting via mWomSV unlock/relock bypasses unused `bracketRewarded` tracking - (File: wombat/ArbWomUp3.sol)

### Summary
`incentiveDeposit`'s lock-mode reward calculation subtracts `calDoubledCounted(_account)`, which derives the "already rewarded" correction from the attacker-controlled, mutable `mWomSV.getUserTotalLocked(_account)` balance instead of the permanent `bracketRewarded` mapping that exists in storage for exactly this purpose but is explicitly marked "not in use". [1](#0-0)  Because a user can call `mWomSV.startUnlock`/`unlock` to reduce their locked balance and then relock via `incentiveDeposit`, the live-balance-based correction can be made to disagree with what was truly already rewarded, allowing the same tier range to be paid out multiple times.

### Finding Description
In `getRewardAmount`, when `_lock` is true (i.e. `_mode == 2`), the reward for the incremental tier progress is computed as:
```
mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
``` [2](#0-1) 

`calDoubledCounted` recomputes the tiered reward using the **current live** `mWomSV.getUserTotalLocked(_account)` value as the "already accounted for" amount:
```
function calDoubledCounted(address _account) public view returns (uint256) {
    uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
    ...
}
``` [3](#0-2) 

The contract declares `mapping(address => uint) public bracketRewarded;   // not in use` [1](#0-0)  — a dedicated ledger intended to record how much reward has actually been distributed per user/bracket — but it is never written to or read anywhere in the contract. Instead, the "correction" basis is the live, externally-mutable `mWomSV` locked balance.

`mWomSV.getUserTotalLocked` is not an append-only record; it decreases whenever a user calls `mWomSV.startUnlock` (moves funds into cooldown) followed by `mWomSV.unlock` after `coolDownInSecs`, which reduces the amount tracked in `MasterMagpie` and hence `getUserTotalLocked`. [4](#0-3) 

Exploit flow for an unprivileged attacker:
1. Call `incentiveDeposit(X, ratio, false, 2)` to lock `X` WOM-derived `mWom` into `mWomSV`, jumping through several reward tiers and receiving the full incremental `mgpReward` for going from `0 → X` locked (correct on this first call, since `calDoubledCounted` returns `0`).
2. Wait out `coolDownInSecs`, call `mWomSV.startUnlock`/`unlock` to withdraw all (or most) of the just-locked `mWom`, reducing `getUserTotalLocked(attacker)` back toward `0`.
3. Call `incentiveDeposit` again with a small `_amount`. Because `calDoubledCounted` now reads the reduced live balance rather than a persistent record of rewards already paid, the "correction" is understated (or zero), and the tier-based `rewardAmount` calculation re-grants reward for the same tier range that was already paid out in step 1.
4. Repeat steps 1–3 to repeatedly harvest reward for the same nominal amount of `mWom`, draining `IERC20(mgp)` held by the contract via `vlMGP.lockFor(rewardToSend, msg.sender)` at `ArbWomUp3.sol:101-102`.

The only backstop is `uint256 mgpleft = IERC20(mgp).balanceOf(address(this)); return mgpReward > mgpleft ? mgpleft : mgpReward;` [5](#0-4) , which caps a single call's payout at the contract's MGP balance but does nothing to prevent repeated draining across multiple calls/cycles — it only stops a single call from over-paying beyond what's currently held. Nothing in `incentiveDeposit` checks `bracketRewarded`, so the intended reconciliation invariant ("the stored record of what has been rewarded must be the single basis of the correction") is not enforced at all; the mapping is dead code.

### Impact Explanation
This allows direct theft of the MGP tokens held by `ArbWomUp3` (which are meant to be distributed once per unit of qualifying `mWom` locked) by repeatedly cycling small locks and unlocks through `mWomSV` to keep re-triggering tier-based rewards for balances that were already rewarded. This matches "Critical - Direct theft of user funds/protocol funds," since the MGP intended for legitimate depositors can be drained by an attacker who never permanently commits new capital equal to the reward received.

### Likelihood Explanation
Preconditions: `mWomSV` must permit unlocking after `coolDownInSecs` (it does, via `startUnlock`/`unlock`), and there must be sufficient MGP balance in `ArbWomUp3` to pay out repeated rewards (per the question's stated precondition, MGP balance is below twice the capped reward, which still allows partial repeat draining, and the attacker can repeat the cycle over time as the pool is refilled). No privileged role is required — `incentiveDeposit`, `startUnlock`, and `unlock` are all public/external functions available to any account. The attack is capital-light: the attacker only needs the WOM/mWom being cycled and time to wait through `coolDownInSecs`, making it repeatable indefinitely as long as the contract holds MGP.

### Recommendation
Use `bracketRewarded[_account]` as the actual, monotonically-increasing ledger of "reward-qualifying mWom locked" per user, updated inside `incentiveDeposit` after each successful reward payout, and have `calDoubledCounted` (or an equivalent correction) read from `bracketRewarded` instead of the live, unlock-able `mWomSV.getUserTotalLocked` balance. Ensure `bracketRewarded` is only ever increased, never decreased by unlocking, so previously rewarded tier ranges cannot be re-claimed by cycling `mWomSV` lock/unlock.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `mgp`, set tiers/multipliers via `setMultiplier`, fund the contract with MGP such that `IERC20(mgp).balanceOf(address(this)) < 2 * cappedReward`.
2. As attacker EOA, approve WOM and call `incentiveDeposit(X, ratio, false, 2)`; record `rewardToSend_1` from the `VLMGPRewarded` event and snapshot `IERC20(mgp).balanceOf(ArbWomUp3)` before/after.
3. Advance time past `coolDownInSecs`; call `mWomSV.startUnlock(X_locked)` then `mWomSV.unlock(slotIndex)` to withdraw the locked `mWom` back to the attacker.
4. Call `incentiveDeposit` again with a small `_amount` and mode `2`; capture `rewardToSend_2`.
5. Assert `rewardToSend_2 > 0` even though the attacker's net new `mWom` contribution corresponds to a tier range already paid for in step 2, and assert the cumulative MGP paid to the attacker (`rewardToSend_1 + rewardToSend_2 + ...`) exceeds what a single, correctly-tracked cumulative-lock reward calculation would allow (i.e., exceeds the reward for locking `X` once, un-inflated by repeated cycles) — demonstrating `rewardToSend` no longer reconciles with a single, non-repeatable basis and the attacker's net token balance increased without proportional new locked capital.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
