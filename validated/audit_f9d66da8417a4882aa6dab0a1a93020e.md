# Analog Found: Full-token-balance sweep on any-leg completion in `IntrinsicIntents._fillSameChain`

### Title
Same-chain partial fill grabs the entire aggregated per-token escrow instead of the leg's proportional share when multiple output legs share an input token - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The Panoptic bug skipped a ratio-based validation exactly at a boundary condition (`netLiquidity == 0`), letting a buyer avoid paying premium because the code fell back to an unguarded branch that assumed a relationship (liquidity accounting per position) that didn't hold in that edge case. `IntrinsicIntents._fillSameChain` has the same class of flaw: a "boundary" branch (`amountFilled == totalRequired`, added specifically to fix rounding dust) assumes that `_orders[commitment][token]` holds exactly the escrow attributable to the *current output leg*, when in fact `_orders` is aggregated by `(commitment, token address)` across the *entire order*. If two output legs are backed by the same input token address, completing either leg first sweeps the whole aggregated escrow balance for that token, not just the completing leg's fair share.

### Finding Description
`_orders` is declared as a flat per-(commitment, token) balance, summed across all of an order's inputs at placement time: [1](#0-0) 

In `_fillSameChain`, for a normal partial fill the escrow released is computed proportionally per leg:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
```
But the branch added to eliminate rounding dust on the *final* fill of a leg instead reads the entire live balance for that token: [2](#0-1) 

This is correct only if `_orders[commitment][token]` contains solely the escrow tied to leg `i`. Nothing in `placeOrder`/`_orders` accounting enforces a 1:1 mapping between output-leg index and input-token bucket — a user's `order.inputs` array can legitimately list the *same* token address at two different indices (e.g., `inputs = [ {tokenA, 600}, {tokenA, 400} ]` funding two different output legs, `output.assets[0]` and `output.assets[1]`). At `placeOrder` time both entries are summed into the single bucket `_orders[commitment][tokenA] = 1000`.

When a solver completes leg 0 in a single fill (`amountFilled == totalRequired` for leg 0), the code does not compute `600` (leg 0's own share) — it reads `_orders[commitment][tokenA]`, which is still `1000` because leg 1 hasn't been touched. That entire `1000` is passed to `_withdraw`, which decrements `_orders[commitment][tokenA] -= 1000` and transfers the full `1000` to the leg-0 solver: [3](#0-2) 

The order is left with `_orders[commitment][tokenA] == 0`. When a second solver later fills leg 1 (which is entitled to its own `400`), `_withdraw` reads `escrowed = 0`, and reverts with `UnknownOrder()` — the second leg can never be filled/settled, permanently locking the user's remaining escrow accounting and denying the honest second-leg filler payment; meanwhile the first solver has already received input tokens far in excess of the value of the output they actually provided.

### Impact Explanation
This directly matches the bounty's "unauthorized transaction/execution," "logic attack," and "loss of funds" categories:
- A solver that structures (or opportunistically completes) a single-leg full fill on an order whose `inputs` array has a duplicated token address receives escrow that includes funds earmarked for a different, unfilled leg — an unentitled beneficiary receiving an unentitled amount.
- The remaining leg becomes permanently unfillable (its proportional escrow no longer exists in the ledger), locking the user's funds and blocking legitimate settlement — a state where funds cannot move to the rightful beneficiary at all.
- No relayer, prover, governance actor, or malicious peer is required; `fillOrder` is a fully public, unprivileged entrypoint and the only trigger condition is an order whose `inputs` list repeats a token address across legs, which the contract neither rejects nor accounts for correctly.

### Likelihood Explanation
Orders with duplicate input-token entries across output legs are not prevented anywhere in `placeOrder` or order validation — the contract has no uniqueness constraint on `order.inputs[].token`. Any user (or a solver colluding with/acting as the order's own placer) can construct such an order, then have a solver fully complete the smallest leg first to trigger the over-release. This requires no special privileges, only crafting order data and a normal `fillOrder` call — well within an unprivileged attacker's reach.

### Recommendation
Do not key escrow release on the raw live balance of `_orders[commitment][token]`. Either:
1. Track escrow per `(commitment, output-leg index)` rather than aggregated by token address, so each leg's release is bounded by its own committed input amount, or
2. When collapsing to a full-balance release on the "last fill" branch, first assert that no other unfinished leg still claims a portion of the same token bucket (e.g., sum the remaining `totalRequired - alreadyFilled` across all legs sharing that token and only release `_orders[...]` in full once every leg referencing that token is fully filled).

### Proof of Concept
1. User places an order with `inputs = [{token: USDC, amount: 600}, {token: USDC, amount: 400}]`, `outputs = [{DAI, 100}, {WBTC, 1}]` (two legs, same input token USDC, `_orders[commitment][USDC] = 1000` after placement).
2. Solver A calls `fillOrder` providing the full `100 DAI` for leg 0 in one transaction. `alreadyFilled(leg0) == 0`, `fillAmount = 100 = totalRequired`, so `amountFilled == totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 1000` (not `600`). Solver A receives all `1000 USDC`; `_orders[commitment][USDC]` becomes `0`.
3. Solver B later calls `fillOrder` providing `1 WBTC` for leg 1. `_withdraw` reads `escrowed = _orders[commitment][USDC] = 0` and reverts `UnknownOrder()`. Leg 1 can never be filled — Solver B cannot claim its rightful `400 USDC`, and the user's escrow accounting for that leg is permanently broken while Solver A walked away with `400 USDC` beyond its entitlement.
