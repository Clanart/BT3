### Title
OP_RETURN data is excluded from transaction fee and weight bounds - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends an attacker-influenced `OP_RETURN` output to the transaction, but calculates both the required fee and maximum standard transaction weight using only `payments` and optional `change`. The resulting signed transaction can therefore have a lower effective fee rate than requested and can exceed `MAX_STANDARD_TX_WEIGHT` despite passing the local bound check.

### Finding Description
`data` is converted into a zero-value `OP_RETURN` output and appended to `tx_outs` before sizing is calculated. Both calls to `calculate_weight_vbytes` pass `payments`, not `tx_outs`, so the temporary transaction used for measurement omits the `OP_RETURN` output:

- Initial fee/weight calculation: `calculate_weight_vbytes(tx_ins.len(), payments, None)`
- Change-aware calculation: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`

Consequently, `needed_fee = fee_per_vbyte * vbytes` is based on a smaller transaction than the one later stored and signed. The same omitted output is also excluded from the `weight > MAX_STANDARD_TX_WEIGHT` check.

### Impact Explanation
An unprivileged caller controlling transaction data can cause the multisig path to produce a transaction whose actual virtual size is up to roughly the size of the added `OP_RETURN` output larger than the measured size. This causes:

- The effective fee rate to fall below `fee_per_vbyte`.
- The minimum relay fee check to be evaluated against an undersized transaction.
- The standardness bound to accept a transaction that can exceed `MAX_STANDARD_TX_WEIGHT` once the `OP_RETURN` output is included.
- A signed transaction that may be rejected for standard relay despite being produced by `SignableTransaction`.

### Likelihood Explanation
The issue is deterministic whenever `data` is `Some`. The caller only needs to provide otherwise valid inputs, payments, change, and up to 80 bytes of data. No malicious validator, leaked key, or invalid curve input is required; the discrepancy comes entirely from sizing a different transaction than the one being constructed.

### Recommendation
Calculate weight and virtual size over the exact output set that will be placed in the final transaction. In particular, pass the populated `tx_outs`—or explicitly include the `OP_RETURN` `TxOut`—into `calculate_weight_vbytes`, and perform the same complete-output calculation when evaluating the change-output variant. The `MAX_STANDARD_TX_WEIGHT` check should use the final transaction weight, including all outputs.

### Proof of Concept
```rust
let inputs = vec![received_output];
let payments = vec![(payment_script, DUST)];
let data = vec![0u8; 80];

let signable = SignableTransaction::new(
    inputs,
    &payments,
    Some(change_script),
    Some(data),
    fee_per_vbyte,
)
.unwrap();

// The returned transaction includes payments, the OP_RETURN output, and change.
assert_eq!(signable.transaction().output.len(), 3);

// `needed_fee()` was computed from only payments + change.
// The actual transaction virtual size additionally includes the OP_RETURN output.
assert!(
    signable.transaction().vsize() as u64 * fee_per_vbyte >
        signable.needed_fee()
);
```

A boundary transaction can similarly be constructed so that the measured weight is at most `MAX_STANDARD_TX_WEIGHT`, while `signable.transaction().weight()` exceeds it after the `OP_RETURN` output is added.
