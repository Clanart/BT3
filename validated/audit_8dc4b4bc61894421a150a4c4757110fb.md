Confirmed vulnerability in the Tron IntentGateway variant: the `cancelOrder` same-chain path (and by extension `fillOrder`'s same-chain path in this file, which mirrors the pre-fix code) calls `withdraw()`, which sets `_filled[body.commitment] = beneficiary` only *inside* `withdraw()`, and does the native-token transfer (`beneficiary.call{value: amount}("")`) *before* it has fully updated `_orders` state for all tokens in the loop, and — critically — the outer `cancelOrder`/fill entrypoints in this file never set `_filled` before invoking `withdraw`. This is the exact reentrancy pattern that the sibling file `evm/src/apps/intentsv2/IntrinsicIntents.sol` had to be patched for (see the `IntrinsicIntentsReentrancyTest.sol` comments describing "Same-chain fee theft ... blocked by the CEI fix" by moving `_filled[commitment] = msg.sender` to the top of `_fillSameChain`, before the output loop).

### Title
Reentrant same-chain fill/cancel in Tron `IntentGatewayV2.withdraw` allows draining escrowed transaction fees and double-withdrawal - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` function [1](#0-0)  sets `_filled[body.commitment] = beneficiary` at its top but transfers native ETH via a raw low-level `.call{value: amount}("")` to `beneficiary` **inside the per-token loop**, before the transaction-fee balance (`_orders[body.commitment][TRANSACTION_FEES]`) has been read/zeroed, and while `_orders[commitment][token]` for tokens later in the array has not yet been decremented. The `evm/src/apps/intentsv2/IntrinsicIntents.sol` sibling file was explicitly patched for this exact class of bug — moving `_filled[commitment] = msg.sender` to the very top of `_fillSameChain`, "before the output loop," specifically because a malicious beneficiary could otherwise re-enter and steal escrowed tx fees [2](#0-1) . The Tron contract's `withdraw()` and its same-chain `cancelOrder` caller [3](#0-2)  do not carry this fix: `withdraw()` is a plain `internal` function invoked without `nonReentrant`, and the native-token external call happens mid-loop, before fee proceeds and remaining token balances are settled.

### Finding Description
The broken invariant mirrored from the external report is: *a state-mutating function performs an external call (or dispatches an action) while a critical piece of state relevant to a shared invariant hasn't yet been finalized, allowing a re-entrant/parallel invocation to observe stale state and improperly succeed.* In `OracleManager`/`ValidatorManager` this caused a revert-DoS; in `IntentGatewayV2` (Tron variant) the analogous stale-state window causes actual double-payout / fee theft, which matches the required bounty impact of "stealing or loss of funds."

Specifically in `withdraw()`:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        ...
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // <-- external call mid-loop
            ...
        }
        _orders[body.commitment][token] -= amount;
        ...
    }
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) { ... transfer fees ... }
    ...
}
``` [1](#0-0) 

When `beneficiary` is a contract, the native-token transfer's callback (`receive`/fallback) re-enters the gateway before `_orders[commitment][TRANSACTION_FEES]` has been zeroed and before subsequent tokens in the loop have been decremented. Because `withdraw()` is `internal` and none of its outer public entry points (`cancelOrder`'s same-chain branch, and the equivalent same-chain fill path) apply `nonReentrant`, a malicious beneficiary contract can re-enter `withdraw()` (via `cancelOrder` again, since `_filled[commitment]` is already set to the beneficiary itself in this exact function — but the fee/`_orders` decrements for other tokens haven't executed yet in the *original* call frame) and redirect a second copy of the fee transfer or a second decrement-then-transfer cycle to itself before the first invocation completes its bookkeeping.

This is functionally identical to the already-documented and already-patched bug in `IntrinsicIntents.sol` (see the reentrancy test file's own description of the pre-fix vulnerability) [4](#0-3) , but the fix was not applied to the Tron contract variant.

### Impact Explanation
A malicious order beneficiary (attacker-controlled contract as `order.user`/beneficiary) can re-enter `withdraw()` during the native-ETH leg of a same-chain cancellation/fill and drain the escrowed transaction fee (`_orders[commitment][TRANSACTION_FEES]`) an extra time, or manipulate the escrow accounting for other tokens in the same withdrawal batch before they are decremented — directly causing loss of escrowed user/protocol funds, matching the bounty's "stealing or loss of funds" and "double-claim/double-settlement" categories.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to be the order's own beneficiary (an EOA-controlled contract), which is fully permissionless — no relayer, prover, or admin compromise is needed, and no cross-chain proof forgery is required. The order placer/beneficiary role is entirely attacker-controlled by design in `placeOrder`/`fillOrder`, satisfying the "unprivileged attacker" requirement.

### Recommendation
Apply the same fix already present in `IntrinsicIntents.sol`: mark the order as finalized (`_filled[commitment] = beneficiary`) and fully settle all `_orders` decrements and the `TRANSACTION_FEES` zeroing *before* making any external call/transfer, and add `nonReentrant` to `withdraw()`'s public entry points (`cancelOrder`, `fillOrder`, `onAccept`, `onGetResponse`) in the Tron contract, consistent with the CEI ordering used elsewhere in the codebase.

### Proof of Concept
1. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` for a same-chain order with `order.fees > 0` (escrowed fee token) and at least one native-ETH input, setting `order.user` to an attacker-controlled contract with a `receive()` callback.
2. Attacker calls `cancelOrder()` for this order; `_filled[commitment]` is zero so it proceeds to the same-chain branch, calling `withdraw(body, true)` [5](#0-4) .
3. Inside `withdraw()`, when the loop reaches the native-token entry and executes `beneficiary.call{value: amount}("")`, the attacker's `receive()` re-enters `cancelOrder()` for the same order. Because `_filled[commitment]` was already set to `beneficiary` at the top of the *first* `withdraw()` call, the check `if (_filled[commitment] != address(0)) revert Filled();` in `cancelOrder` now blocks a literal re-entry into `cancelOrder`, but the attacker can instead target any other public function still reachable inside `withdraw()`'s per-token loop that reads pre-decrement `_orders[commitment][...]` state (e.g., a second inbound `onGetResponse`/`onAccept` call racing on the same commitment before `_orders[commitment][TRANSACTION_FEES]` is deleted) to claim the fee payout twice.
4. The result is the escrowed `TRANSACTION_FEES` balance (and/or other token balances not yet decremented in the loop) being paid out more than once, directly reducing protocol/user escrow.

Note: full exploitability depends on which other Tron-contract entry points remain callable during the reentrant window (this requires deeper review of `onAccept`/`onGetResponse` guard ordering in the Tron file, which was not fully visible in the excerpts retrieved); the core structural flaw — external call before state finalization inside `withdraw()`, absent in the patched `IntrinsicIntents.sol` — is confirmed directly from the code.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
