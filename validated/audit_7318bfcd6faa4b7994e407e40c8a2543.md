### Title
Unvalidated `contract.Value()` in WERC20 `Deposit()` allows draining precompile-held native balance via delegatecall value inheritance - (File: precompiles/werc20/tx.go)

### Summary
The Arkis finding is a class of bug where a privileged execution path trusts a caller-supplied "value" field without verifying that the corresponding funds were actually escrowed/received, letting an attacker redirect funds that were never really transferred into the trusted contract's control. The Cosmos EVM analog is the WERC20 precompile's `Deposit()` function, which uses `contract.Value()` as ground truth for "how much native token was just received by the precompile" and then unconditionally forwards that exact amount out of the precompile's bank account via `SendCoins`, without checking whether the precompile's own balance actually increased by that amount in the current call.

### Finding Description
`Deposit()` reads the amount to forward purely from `contract.Value()`: [1](#0-0) 

For an ordinary top-level `CALL` to the WERC20 precompile address, the go-ethereum `Call` semantics perform a real balance transfer (`Context.Transfer`) from the caller to the precompile address before `Run()`/`Deposit()` executes, so `contract.Value()` correctly reflects funds that landed in the precompile's account, and `Deposit()` immediately routes them back to the caller — consistent with the "No Lock-up" design documented in [2](#0-1) .

However, `Deposit()` performs no verification that the precompile's actual bank/EVM balance increased by `contract.Value()` in this call. `CALLVALUE` (and therefore `vm.Contract.Value()`) is inherited through `DELEGATECALL` frames from the parent call context, while `DELEGATECALL` itself never performs any native-token balance transfer. Consequently, a malicious contract `M` that is invoked with `value = V` (a real transfer of `V` into `M`'s own account) can `delegatecall` into the WERC20 precompile address. Inside that delegatecall, `contract.Value()` still reports `V` (inherited from the outer call context) even though `V` was never transferred to the precompile's account — it sits in `M`'s account instead. `Deposit()` will then attempt (and, if the precompile address happens to hold any balance from unrelated activity — e.g., residual dust, or repeated delegatecalls executed via a loop inside `M` in the same transaction) to `SendCoins` that amount from the precompile's account (`precompileAccAddr`) to `msg.sender` (`callerAccAddress`, which under delegatecall is the original externally owned caller, not `M`). This mirrors the Arkis root cause exactly: a "value" field taken from an untrusted execution context is used as authorization for a fund transfer without validating that the value corresponds to an actual, current balance movement into the trusted contract.

Unlike the ERC20 precompile, which explicitly guards against receiving/using `contract.Value()` when it shouldn't (`ErrCannotReceiveFunds` check in [3](#0-2) ), the WERC20 `Deposit()` path has no equivalent invariant check tying `contract.Value()` to a real, freshly-received balance at the precompile's own address.

### Impact Explanation
If exploitable, this would allow an attacker to repeatedly trigger `SendCoins` out of the WERC20 precompile's account for amounts that were never actually deposited into it in the current call frame, extracting funds that belong to other legitimate depositors or module-level residue mistakenly sitting at that address — i.e., unauthorized extraction/theft of native-token-backed value via a precompile-mediated balance, matching the "Critical … theft, or unauthorized extraction of user funds … or precompile-mediated assets" impact bucket.

### Likelihood Explanation
This is a **conditional / not-fully-confirmed** finding. Its practical severity depends on two unverified facts about this specific fork's vendored EVM interpreter and the WERC20 account's balance lifecycle:
1. Whether `vm.Contract.Value()` for a `DELEGATECALL` frame actually inherits the parent's non-zero value (standard upstream go-ethereum behavior) or is set to zero in this Cosmos EVM fork's `NewContract`/`DelegateCall` implementation — I could not locate the vendored `core/vm` `DelegateCall`/`NewContract` source in this repo's index to confirm.
2. Whether the WERC20 precompile's account address can ever hold a non-zero balance at the moment of an attacker-controlled call (normal flow nets to zero within the same atomic transaction via the immediate `SendCoins` back to the depositor, and `BlockedAddr`/`BalanceHandler` bypass logic in [4](#0-3)  suggests some awareness of similar module-account balance edge cases, which could be an existing mitigation I could not fully trace end-to-end).

Because I could not conclusively verify point (1) in this repository's vendored EVM (the `core/vm` package with `DelegateCall`/`NewContract` was not found in the index), and the exploit further requires the precompile address to hold exploitable residual balance, I cannot confirm this is a directly reachable, unconditional Critical bug in this codebase as indexed.

### Recommendation
- In `Deposit()`, do not treat `contract.Value()` as authoritative. Track the precompile's own bank balance immediately before and after the call (similar to the `BalanceHandler` pattern already used elsewhere), and only forward the amount by which the precompile's balance actually increased during this specific call.
- Reject `Deposit()` calls made via `DELEGATECALL`/`CALLCODE` context, or explicitly compare `contract.Value()` against a freshly observed balance delta at the precompile address, mirroring the `ErrCannotReceiveFunds` style guard already present in the ERC20 precompile.
- Audit `core/vm` `Call`/`DelegateCall`/`NewContract` in this fork to confirm the exact value-inheritance semantics for delegatecall frames as they pertain to precompiles that consume `contract.Value()`.

### Proof of Concept
Conceptual (unverified against actual vendored EVM behavior in this fork):
1. Attacker deploys contract `M` with a function that, upon receiving `value = V` via a normal `CALL`, issues a `DELEGATECALL` to the WERC20 precompile address encoding `deposit()`.
2. If `vm.Contract.Value()` inside that delegatecall reports `V` (inherited from `M`'s call context) rather than `0`, `Deposit()` executes `SendCoins(precompileAccAddr, callerAccAddress, V)`.
3. If the precompile's account happens to hold `≥V` in native balance (from any unrelated source, or from looping this delegatecall multiple times within the same transaction against balance left by a prior deposit not yet flushed), the attacker's EOA receives `V` in native tokens without `M` ever forwarding its own received `V`, effectively draining the precompile's account.

Given the unresolved uncertainty around the vendored EVM's delegatecall value semantics and the precompile's balance invariants, this should be validated by a Devin session with full repository/tooling access before being treated as confirmed.

```go
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}
```

```go
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.

// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
```
