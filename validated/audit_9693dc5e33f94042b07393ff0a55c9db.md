### Title
Missing future-timestamp validation in `oracle-timestamp-fresh` lets a future oracle publish-time bypass staleness checks and permanently poison the monotonic `last-update` state, freezing price resolution for an asset feed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` computes the staleness delta by clamping to `u0` whenever the incoming oracle timestamp `ts` is greater than `stacks-block-time`, instead of rejecting timestamps that lie in the future. Any oracle update whose `publish-time` is ahead of the chain's own clock is therefore treated as maximally fresh and accepted, and that future value is then written into the per-feed `last-update` map. Because `price-resolve` also enforces `(>= ts prev)` as a monotonicity guard, this future value becomes a floor that every subsequent, genuinely-current update must clear — but a legitimately-timed update can have `ts < prev` until `stacks-block-time` itself catches up to the poisoned value, so `ERR-ORACLE-INVARIANT` fires and price resolution for that asset reverts.

### Finding Description
In `mainnet/contracts/market/v0-4-market.clar`:

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 

When `ts > stacks-block-time` (the feed's timestamp is in the future relative to the chain), `delta` is forced to `u0`, which always satisfies `(<= delta max-staleness)`. There is no analogous check to the beacon-spec `on_block` rule ("blocks cannot be in the future") that the external report highlights — the code never asserts `ts <= stacks-block-time` (the local-node equivalent of "current slot").

`price-resolve` then persists this accepted future timestamp:
```clarity
(if (> timestamp last-update-time)
    (map-set last-update key timestamp)
    false)
``` [2](#0-1) 

Once a future timestamp is stored as `last-update-time`/`prev` for that `{type, ident}` key, every later call to `price-resolve` for the same feed must satisfy `(>= ts prev)`. If a subsequent legitimately-timed Pyth/DIA update reports a `publish-time` that is genuinely current (i.e., less than the previously-recorded future value, which is entirely possible since the future value was only accepted due to the missing check, not because it reflects real elapsed time), the monotonicity assertion fails and `ERR-ORACLE-INVARIANT` is raised. This mirrors the reported bug's mechanism precisely: an unvalidated "value from the future" is accepted and stored, and once stored, all correctly-timed follow-up operations for that state slot/feed are rejected until wall-clock/chain time actually advances past the poisoned value.

### Impact Explanation
`price-resolve` is called by every path that needs the affected asset's USD price — borrowing, withdrawing, health-factor/LTV computation, and liquidation via `price-multi-resolve`/`iter-price-multi`. Once a feed's `last-update` is poisoned with a future timestamp, all operations requiring that asset's price revert with `ERR-ORACLE-INVARIANT`, freezing borrow/withdraw/liquidate flows involving that asset until the chain's `stacks-block-time` naturally advances past the erroneous future value. This is a freezing-of-funds impact (users cannot withdraw/borrow/be liquidated against that asset), qualifying as at least temporary freezing of funds; if the poisoning timestamp is far enough in the future, it can persist for an extended period, and during that window liquidations relying on this asset's price also cannot execute, risking insolvency exposure for the protocol.

### Likelihood Explanation
The trigger only requires one price update (Pyth or DIA) with a `publish-time` ahead of the Stacks chain's own block time to be relayed and accepted — no privileged access or DAO compromise is needed, since anyone can relay a validly-signed Pyth VAA and DIA updates flow through the same `resolve-price-feed`/`price-resolve` path. Because Pythnet/DIA clocks run independently of Stacks block production, timestamp values ahead of `stacks-block-time` can occur, and the code has no explicit rejection of them, unlike the monotonicity and staleness-lower-bound checks that already exist.

### Recommendation
Reject timestamps that are in the future relative to `stacks-block-time` instead of clamping the delta to zero, e.g.:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)              ;; reject future timestamps
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This prevents any future-dated oracle timestamp from being accepted or written into `last-update`, eliminating the possibility of poisoning the monotonic floor for a feed.

### Proof of Concept
1. An asset's oracle feed (Pyth or DIA) is updated on-chain with a `publish-time`/`timestamp` value greater than the current `stacks-block-time` (e.g., due to clock skew or a relay submitting a validly-signed update whose timestamp is ahead of the chain's block-time).
2. `resolve-pyth`/`resolve-dia` returns this future `timestamp` to `price-resolve`. [3](#0-2) 
3. `oracle-timestamp-fresh` computes `delta = u0` because `ts > stacks-block-time`, so the freshness assertion trivially passes and the update is accepted. [1](#0-0) 
4. `last-update` is set to this future `timestamp` since it's greater than the prior recorded value. [2](#0-1) 
5. On the next legitimate oracle update for the same feed, if its real, current `publish-time` is less than the stored future value, `(>= ts prev)` fails, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every subsequent operation (borrow/withdraw/liquidate) needing that asset's price, until `stacks-block-time` itself advances past the poisoned future value.
