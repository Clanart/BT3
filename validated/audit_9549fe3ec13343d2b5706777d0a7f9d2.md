### Title
Static dust floor creates change outputs that cannot fund their own spend - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` treats the fixed 546-sat `DUST` constant as proof that a change output is economically viable, even though the later cost to spend that output scales with the transaction's fee rate. At attainable fee rates, the function can create a valid change output whose value is lower than the fee required to spend it, and `Scanner` will subsequently report that output as spendable.

### Finding Description
The wallet defines `DUST` as a fixed `546` sat threshold. [1](#0-0)  Outgoing payments are rejected only when their amount is below that fixed value. [2](#0-1) 

For change, the code calculates `fee_with_change = fee_per_vbyte * vbytes_with_change`, subtracts it from the input remainder, and then appends the change output whenever the remaining `value >= DUST`. [3](#0-2)  The comparison does not account for the future fee needed to spend that new output, despite `fee_per_vbyte` being available at construction time. [3](#0-2) 

The transaction model used for weight estimation fixes each spend as a Taproot input containing a 36-byte outpoint, empty script, sequence, and a 64-byte witness signature. [4](#0-3)  This is approximately 57 virtual bytes per input, so once the fee rate exceeds roughly `546 / 57 ≈ 9.6` sat/vB, even a 546-sat output costs more to spend than it contains.

`Scanner::scan_transaction` then classifies every output matching a registered script as a `ReceivedOutput` without checking whether its amount can pay for its own future input. [5](#0-4)  This contradicts `ReceivedOutput`'s definition as a spendable output. [6](#0-5) 

### Impact Explanation
An otherwise valid transaction can leave the multisig with a confirmed change output that is economically unspendable: its value is less than the fee consumed by the input needed to redeem it. `Scanner` reports that output as funds received, but spending it either fails for lack of funds or reduces the value available from other inputs. Repeated triggering of this condition can accumulate stranded UTXOs and leak wallet value, analogous to a liquidation that makes a position less healthy rather than healthier.

### Likelihood Explanation
The condition only requires the active fee rate to exceed the point at which a Taproot input costs more than the fixed 546-sat floor. A payment requester can also steer the leftover change amount into the vulnerable range by selecting the payment amount. The impact is bounded to value stranded through uneconomical outputs rather than key compromise or signature forgery, making this a medium-severity economic correctness issue.

### Recommendation
Replace the fixed `DUST` check with a fee-aware spendability threshold. For each candidate output, require at least `output_value >= estimated_input_vbytes * target_fee_per_vbyte` plus a safety margin, while still enforcing the consensus/policy dust rule for the specific script type. Apply the same or a conservative threshold when scanning received outputs, or mark outputs below it as economically unspendable instead of returning them as ordinary `ReceivedOutput`s.

### Proof of Concept
Consider a transaction with one Taproot input, one 546-sat payment, a Serai P2TR change address, and `fee_per_vbyte = 100`. Let `fee_with_change` be the deterministic fee calculated for that shape by `calculate_weight_vbytes`; for a normal one-input/two-output Taproot transaction this is on the order of 15,000 sats. Construct the input value as:

```text
input_sat = 546 + fee_with_change + 600
```

`SignableTransaction::new` computes `value = input_sat - (546 + fee_with_change) = 600`, accepts it because `600 >= DUST`, and appends the change output. [3](#0-2)  At the same 100 sat/vB rate, spending that output later adds an approximately 57-vB input, costing about 5,700 sats—more than eight times the output's value. The transaction therefore succeeds while leaving behind a scanner-visible output that cannot pay for its own redemption. [5](#0-4)
