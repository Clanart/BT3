### Title
Forged `ReceivedOutput` prevout values are trusted for change/fee accounting, causing silent overpayment of miner fees (loss of funds) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` and `SignableTransaction::multisig` trust the `TxOut` carried inside each `ReceivedOutput` for all value accounting, while `multisig` only verifies that the claimed prevout's `script_pubkey` matches `key + offset`. Because `ReceivedOutput::read` deserializes the offset, the full `TxOut` (including `value`), and the `OutPoint` from untrusted bytes, an attacker can supply an output whose `outpoint` references a real vault UTXO of value `V` but whose embedded `TxOut` claims a smaller value `V'`. The transaction builder computes change from `V'`, yet the real input is worth `V`, so the difference `V - V'` is silently burned as miner fee. This is the Serai analog of the reported Tokemak issue (paying via two channels / paying more than intended): the signer "pays" once through the intended outputs and again through an unbounded, unintended fee, and the signer's own validation never catches it.

### Finding Description
`Scanner::scan_transaction` produces `ReceivedOutput`s where `outpoint` and `output` are taken verbatim from the scanned transaction [1](#0-0) . However, `ReceivedOutput` also exposes a public deserializer, `ReceivedOutput::read`, which reconstructs the struct — offset, `TxOut`, and `OutPoint` — entirely from caller-supplied bytes with no consistency check that the `TxOut` matches what the `outpoint` actually contains on chain [2](#0-1) .

In `SignableTransaction::new`, `input_sat` is summed directly from `input.output.value` and `prevouts` are taken verbatim from the `ReceivedOutput`s [3](#0-2) [4](#0-3) . The change output is then computed as `input_sat - payment_sat - fee_with_change` based on those claimed values [5](#0-4) .

When the multisig is constructed, the only sanity check is `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — the *value* and *outpoint* of each claimed prevout are never validated against the real UTXO [6](#0-5) . The sighash then commits to `Prevouts::All` containing the forged amounts [7](#0-6) , which is precisely what makes the understated-value variant produce a *valid, broadcastable* transaction rather than a rejected one.

### Impact Explanation
If a `ReceivedOutput` is obtained from an untrusted channel via `ReceivedOutput::read` (e.g., outputs relayed/serialized between components rather than scanned directly), an attacker sets `TxOut.value` to `V' < V` where `V` is the real value of the referenced outpoint, keeping the correct vault `script_pubkey`. The builder then:

- computes `input_sat = V'`,
- creates change of `V' - payments - fee`,
- produces a transaction whose real input (`V`) exceeds its outputs by `V - payments - fee`.

The transaction is consensus-valid (Taproot sighash commits to the *claimed* prevout amounts, and the forged prevout is what is signed), gets signed by the threshold multisig, and the excess `V - V'` is irrevocably paid to miners — a direct loss of vault funds, mirroring the "double cost" impact of the original report where the user paid via both ETH and `pullToken`.

### Likelihood Explanation
Exploitation requires an attacker to feed forged bytes to `ReceivedOutput::read` such that the result is used as a `SignableTransaction` input. All fields of `ReceivedOutput` are private, so forgery is only possible through `read` (or a compromised scanner source). When the scanning pipeline is the sole source of `ReceivedOutput`s, the forged `TxOut` cannot be introduced; the finding's severity therefore hinges on whether serialized `ReceivedOutput`s cross a trust boundary — which the `read` API explicitly supports. Reachable via untrusted input bytes; the loss mechanism itself is deterministic once a forged output is accepted.

### Recommendation
- In `SignableTransaction::multisig`, verify not just `prevouts[i].script_pubkey` but the entire `prevouts[i]` against the outpoint's real output — at minimum, treat the `TxOut` inside `ReceivedOutput` as untrusted and have the entity resolving outpoints supply the verified `TxOut` separately.
- Alternatively, store only `(offset, outpoint)` in `ReceivedOutput` and fetch the `TxOut` from the chain/RPC at transaction-building time, removing the attacker-controlled value from the trust domain.
- Document on `ReceivedOutput::read` that the deserialized `output` is unverified and must not be used for fee/change accounting without validation.

### Proof of Concept
```rust
// Attacker observes a real vault UTXO: outpoint P, script S = p2tr(key + offset),
// real value V = 100_000 sats. Attacker crafts a ReceivedOutput via read() with:
//   offset   = correct offset (passes the multisig script_pubkey check)
//   outpoint = P (real)
//   output   = TxOut { value: 10_000, script_pubkey: S }   // understated by 90_000
//
// SignableTransaction::new(vec![forged], payments=[], change=Some(vault_change), ..., fee)
//   input_sat = 10_000  -> change = 10_000 - fee
//   tx outputs total ~10_000, real input is 100_000
//
// multisig() passes because prevouts[0].script_pubkey == S == p2tr_script_buf(offset key)
// Signing commits to Prevouts::All(&[TxOut{value:10_000,...}]) — a valid sighash
// Result: broadcastable tx paying ~90_000 sats to miners; vault loses the difference.
```
The asymmetry that enables the bug: understating `value` yields a valid signed transaction (silent fee burn), while the code gives the builder no way to detect it because nothing ever compares the embedded `TxOut` to the on-chain output at `outpoint`.
