### Title
Silent rewrite of the local git remote URL to an attacker-controlled host via an untrusted GitHub API `clone_url` field, with no hostname pinning - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-fetches repository metadata from the GitHub API and, if certain conditions are met, silently overwrites the local `origin` remote URL with whatever `clone_url` value the API response contains. The function that performs this rewrite checks that the *protocol* (`https`/`ssh`) of the old and new URL match, and that the user hasn't manually customized the remote, but it never verifies that the *host* of the new URL matches the host of the existing remote (or of the account's configured endpoint). A GitHub Enterprise Server (or any endpoint Desktop is configured to talk to) that returns a `clone_url` pointing at a different host causes Desktop to reconfigure `origin` to that host without any user prompt, confirmation, or diff — silently redirecting all future pushes/fetches for that repository.

### Finding Description
`updateRemoteUrl` decides whether to auto-update the local remote: [1](#0-0) 

The three gating conditions are:
- `protocolsMatch`: only the scheme (`https:` vs `git@...:` treated as null) needs to line up.
- `remoteUrlUnchanged`: the *current* remote must still match the previously-known GitHub `cloneURL` (i.e., the user hasn't hand-edited it).
- `!urlsMatch`: the new API URL differs from the current remote.

None of these checks constrain the new URL's **hostname**. `urlMatchesRemote`/`urlsMatch` are only used to detect whether values are equal, not to pin the new value to the old host: [2](#0-1) 

This function is invoked automatically as part of routine, unprompted background refresh flows — e.g. every time a repository is selected, after publishing a repo, or when the signed-in account changes — via `repositoryWithRefreshedGitHubRepository`, which fetches `apiRepo` straight from the API and passes it in: [3](#0-2) 

If `apiRepo.clone_url` (attacker-controlled, e.g. via a compromised/malicious GitHub Enterprise Server response, MITM'd proxy, or any tampered API payload for the endpoint Desktop trusts) points at a different host than the current `origin`, Desktop calls `gitStore.setRemoteURL`, which shells out to `git remote set-url` and rewrites `origin` in `.git/config` with no user-visible warning: [4](#0-3) 

The unit tests for this function only assert host-preserving scenarios (rename within the same host) and never exercise/guard against a cross-host `clone_url`: [5](#0-4) 

### Impact Explanation
Once `origin` is silently repointed to an attacker-controlled host, every subsequent `git push`/`git fetch`/`git pull` the user performs through Desktop targets that host instead of the repository the user believes they're working with. This is a direct instance of "silent corruption of what the user commits or pushes": the user's code, history, and commit metadata are transparently exfiltrated to (or polluted from) an attacker's git server, with no diff/confirmation dialog shown, and the UI continues to display the same repository name/association. Because the operation runs unattended on ordinary app usage (opening/selecting the repository, or on account refresh), it requires no unusual user action beyond normal Desktop use.

### Likelihood Explanation
This requires the attacker to control (or MITM) the API response for a repository lookup on an endpoint the user's Desktop instance already trusts (most plausibly a GitHub Enterprise Server the user has added an account for, or a compromised/spoofed proxy in front of github.com's API). That is within the allowed threat model ("a GitHub API object ... or a git remote/proxy response"), and does not require local/physical access, admin rights, prior malware, or leaked credentials — the compromise is on the server/response side, not the client. The remaining friction is that GitHub.com itself is unlikely to serve attacker-controlled data, so the most realistic path is a malicious/compromised GHES instance; that keeps likelihood moderate rather than trivial.

### Recommendation
Pin the hostname: only apply the auto-update in `updateRemoteUrl` if the new `clone_url`'s hostname matches the hostname of the existing `origin` remote (or the account's configured endpoint hostname). Any change to a different host should require explicit user confirmation (a dialog similar to what Repository Settings shows for manual remote edits), and ideally should be logged/surfaced instead of applied silently.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing at `https://ghe.example.com`, and clone/associate a repository from it so `origin` is `https://ghe.example.com/org/repo.git`.
2. Compromise or MITM the `GET /api/v3/repos/org/repo` response from that GHE instance (or from a proxy in the network path) so that `clone_url` in the JSON payload is `https://attacker.example.com/org/repo.git` (same `https` protocol, different host).
3. Trigger any routine refresh that calls `repositoryWithRefreshedGitHubRepository` (e.g., select the repository in the sidebar, or switch/refresh the signed-in account) — see `app/src/lib/stores/app-store.ts:4890-4907`.
4. Because `protocolsMatch` is true and the user has not manually edited `origin` (`remoteUrlUnchanged` is true) and the new URL differs (`!urlsMatch`), `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')`, rewriting `.git/config` with no prompt.
5. The next push/fetch performed through Desktop's UI silently goes to `attacker.example.com` instead of `ghe.example.com`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
