### Title
Cached FROST preprocess is reused whenever `share`/`complete` run under the same context, enabling secret-share recovery if the preprocess set or message differs — ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` derives signing nonces deterministically from a `CachedPreprocess` seed stored in the DB, keyed only by `context`. For `DkgConfirmer`, `context` is `(b"DkgConfirmer", attempt)` — it does **not** bind the message (`set_keys_message` output, which depends on `key_pair` and `removed`), nor the set of preprocesses/participants. Any path that reaches `share_internal` twice under the same `attempt` with different `preprocesses` or a different `key_pair` causes the same FROST nonce `r` to be used with a different challenge `c`, directly leaking the validator's MuSig secret share — a private-key-share recovery, the exact failure mode the comments warn about.

### Finding Description
- `preprocess_internal` loads or creates `CachedPreprocesses[context]` and rebuilds the sign machine via `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`, so the nonces are a deterministic function of `(context, key)` only [1](#0-0) .
- The context is `(b"DkgConfirmer", self.attempt)`; neither the message nor the received preprocesses participate in nonce derivation [2](#0-1) .
- `share()` calls `share_internal`, which re-executes `preprocess_internal` and then `machine.sign(preprocesses, msg)` where `preprocesses` are attacker/participant-supplied bytes parsed by `read_preprocess` [3](#0-2) .
- In FROST, the per-participant challenge `c` binds the other parties' preprocesses via the `preprocesses` transcript entry [4](#0-3) . Two `sign` calls with the same nonce but different preprocess sets (or different `msg`) yield `s1 = r + c1·share` and `s2 = r + c2·share`, giving `share = (s1 − s2)/(c1 − c2)`.
- The file's own header admits safety rests entirely on a BFT assumption and notes a missing check ("we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)", and the analogous TODO for processor preprocesses) [5](#0-4) . `DkgConfirmer::complete` unconditionally re-runs `share_internal`, so any divergence between the `preprocesses`/`key_pair` observed at `share` time versus `complete` time — or two confirmation items in the same attempt — reuses the nonce.

### Impact Explanation
Reuse of a deterministic nonce across two Schnorr/FROST shares with distinct challenges is a textbook secret-share disclosure: anyone observing the two published `[u8; 32]` shares recovers the coordinator's MuSig secret share for the validator set, the root-of-trust key used to confirm DKG results on-chain.

### Likelihood Explanation
Exploitation requires a second signing pass under the same `(b"DkgConfirmer", attempt)` context with differing inputs — e.g., a partial rebuild/re-execution, or confirmation data resolved to a different preprocess map or `key_pair` within one attempt. The code explicitly assumes BFT finality prevents this and documents the accepted bound plus an unimplemented on-chain commitment check; it is a conditional rather than unconditional leak, consistent with Medium.

### Recommendation
Include the message (or its hash) and the commitment to the preprocess set in the `CachedPreprocesses` key, or store the signed-message digest alongside the cache and refuse to sign a different `msg`/preprocess set under the same context. Implement the noted TODO: verify the on-chain preprocess commitments match the cached-deterministic preprocess before publishing a share.

### Proof of Concept
1. Attempt `a`: coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair)` → publishes `s1 = r + c1·share` where `r` derives from `CachedPreprocesses[("DkgConfirmer", a)]`.
2. Via re-execution/rebuild or a second confirmation item in the same attempt, `share(preprocesses_B, key_pair)` (or a different `key_pair`) runs; the same seed regenerates identical nonces `r`, but `preprocesses_B` produces `c2 ≠ c1` through the `preprocesses` transcript field.
3. Observer computes `share = (s1 − s2)·(c1 − c2)⁻¹` mod the Ristretto group order, recovering the validator's MuSig secret share.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }
