### Title
Attacker front-runs an honest forwarding transaction to consume `ForwardedOutputDb` instruction credit, orphaning the real forwarded funds - (File: processor/src/multisigs/mod.rs)

### Summary
The SymmIO issue class is an unprivileged party front-running a state transition so that the victim's subsequent, otherwise-valid action reverts/produces nothing. Serai's multisig rotation logic has the same shape: `ForwardedOutputDb` is keyed solely by output amount, and the first on-chain output of that amount sent to the new multisig's `Forwarded` address consumes the saved `InInstruction`. An attacker who observes the pending forwarding plan can send their own transaction paying the exact post-fee amount to the deterministic `Forwarded` address in an earlier confirmed block. The instruction is then attached to the attacker's output, and when the honest forwarded output arrives it finds no saved instruction and is silently dropped from all further handling.

### Finding Description
During rotation, `scanner_event_to_multisig_event` processes `ScannerEvent::Block` outputs. For each output of `OutputType::Forwarded`, it calls `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` — matching purely on the output's balance, not on the txid or any binding to the plan that produced it (processor/src/multisigs/mod.rs, `if let Some(instruction) = ForwardedOutputDb::take_forwarded_output(txn, output.balance())`). After this loop, all remaining outputs that are not `OutputType::External` are discarded via `outputs.retain(|output| output.kind() == OutputType::External)`.

The `Forwarded` address is publicly computable: it is `key + GENERATOR * hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` (adjusted to even Y by `Scanner::register_offset`), reachable via `Bitcoin::forward_address` in processor/src/networks/bitcoin.rs. The forwarding amount is also predictable, since the instruction balance is decremented by the forwarding TX fee (`instruction.balance.amount.0 -= tx.0.fee()`) before `ForwardedOutputDb::save_forwarded_output` is called.

An unprivileged attacker therefore knows both the destination address and the exact credited amount. By broadcasting their own transaction paying that amount to the `Forwarded` address and getting it confirmed before the multisig's forwarding transaction, they cause `take_forwarded_output` to return `Some(instruction)` for their output. When the honest forwarded output later confirms, `take_forwarded_output` returns `None`, so no instruction is emitted; the output is then removed by the `retain` to `External`-only and is never added to the scheduler's UTXO set.

### Impact Explanation
The honest forwarded output — real BTC spendable by the new multisig — is never inserted into the scheduler's UTXO pool nor reported as an instruction. It becomes untracked funds sitting at the multisig's forward address: never scheduled, never credited, effectively frozen (recoverable only by manual intervention outside the normal flow). The attacker pays an equal amount (minus the asymmetry that their deposit is credited to the victim's instruction context), making this a griefing burn: attacker burns ~X sats to orphan ~X sats of the protocol's/user's funds. This matches the source bug's impact class — a front-run that flips a one-shot state entry so the legitimate party's action resolves to nothing — and qualifies as a Medium analog.

### Likelihood Explanation
Requirements: a multisig rotation in progress (`step == RotationStep::ForwardFromExisting`), a pending `save_forwarded_output` entry whose amount and destination are derivable from public data (the forwarding TX must be observable in the mempool or the instruction value predictable from the prior deposit and known fee), and the attacker must land a transaction paying that exact amount to the forward address in an earlier confirmed block. The amount-matching is a single u64 equality, so no collision difficulty exists. Bitcoin block cadence makes mempool front-running feasible but not guaranteed; success is probabilistic per rotation, and the window is bounded by the rotation period. Repeated attempts are cheap relative to the griefed amount.

### Recommendation
Bind forwarded-output matching to more than the amount. In processor/src/multisigs/db.rs, key `ForwardedOutputDb` entries by `(expected_amount, expected_txid_or_outpoint)` where the forwarding plan's transaction is known, or by instruction ID plus amount, so an arbitrary third-party payment cannot satisfy it. If exact-txid binding is impossible because the txid isn't fixed until signing, store the set of plausible amounts together with a nonce/plan index embedded in the `data` field consumed by `extract_serai_data`, and require the matching forwarded output's transaction to carry that marker. At minimum, when `take_forwarded_output` returns `None` for a `Forwarded`-kind output, push it into the scheduler UTXO set (`add_outputs`) instead of letting `outputs.retain(... External)` drop it, so front-running degrades to an attribution anomaly rather than orphaned funds.

Supporting code: `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` consumes on amount equality only, and `outputs.retain(|output| output.kind() == OutputType::External)` then drops the unmatched real output (processor/src/multisigs/mod.rs:824-837). The saved instruction balance is publicly predictable since it is the deposit amount minus the deterministic forwarding fee (processor/src/multisigs/mod.rs:883-901).
