## Title
Missing type/shape validation of GitHub API repository objects lets a malicious API host inject a hostile remote URL into `git remote add` - (File: `app/src/lib/git/remote.ts`)

### Summary
The Solidity finding is about a constructor trusting that addresses handed to it are "the right type" without any runtime check. The closest verified Desktop analog is the same class of bug at a different layer: JSON objects returned by the GitHub API (which can be a GitHub Enterprise Server the user has added as an account, i.e. attacker-controlled server-side data) are cast to TypeScript interfaces without any runtime validation of their shape or content, and the `clone_url`/`ssh_url` string fields from those objects are then fed straight into a `git remote add` invocation that lacks the `--` argument-terminator, so a value that doesn't actually look like a URL is not rejected.

### Finding Description
`parsedResponse`/`deserialize` in `app/src/lib/http.ts` explicitly documents that it performs no shape validation: [1](#0-0) [2](#0-1) 

Every API call (`fetchRepositoryCloneInfo`, pull-request fetches, etc.) does `await parsedResponse<IAPIRepository>(response)` and then trusts fields such as `repo.clone_url` / `repo.ssh_url` as if they were guaranteed, well-formed URL strings: [3](#0-2) 

That untyped/unvalidated `clone_url` flows, via `IAPIPullRequest.head.repo.clone_url`, into `AppStore._findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` whenever Desktop can't find an existing remote for the PR's fork: [4](#0-3) 

`addRemote` itself builds the git command with the URL as a bare positional argument, with **no `--` separator** to stop git from interpreting it as an option: [5](#0-4) 

Contrast this with `clone()` in `app/src/lib/git/clone.ts`, which does use `'--', url, path` to defensively terminate options before the attacker-influenced URL: [6](#0-5) 

So the exact same "server-controlled string treated as a validated URL" pattern is handled safely in one call site (`clone`) and unsafely in another (`addRemote`), because there is no shared, enforced type/shape validation on the `clone_url` value coming out of the API layer — mirroring the Astaria bug where some constructor parameters are validated as the right "shape" and others aren't.

### Impact Explanation
If a user has added an account for a GitHub Enterprise Server that is malicious, compromised, or sitting behind a hostile TLS-terminating proxy, that server can serve a pull-request or repository JSON payload where `clone_url` is not a normal URL but a string starting with `-` (a git option) — since `deserialize<T>` never checks that the field is actually URL-shaped. Because `addRemote` passes this value to `git remote add <name> <url>` without a `--` terminator, git will parse it as an option to `remote add` rather than a positional URL argument. Depending on the exact option string smuggled in, this can corrupt the repository's `.git/config` (e.g. forcing unexpected remote/fetch settings) or otherwise silently corrupt what the user later fetches/pushes to — which is the same "silent corruption of what the user commits/pushes" impact class called out as in-scope. This is triggered purely by the user clicking "Open PR from Desktop" / checking out a pull request from a repository hosted on that server; the attacker never needs local access, admin rights, or pre-existing malware.

### Likelihood Explanation
Likelihood is moderate: it requires the user to have an account on (or be pointed at) a GitHub Enterprise Server that returns attacker-influenced `clone_url` data, and it requires that string to survive as a git-option-shaped value. I was not able to fully verify, within the available tooling, exactly which git option-strings are reachable/exploitable through `remote add`'s option parser, nor whether Desktop's git protocol allow-list (only explicitly widened for `.gitmodules` via `protocol.file.allow=always` in `app/src/lib/git/submodule.ts`) would additionally restrict any resulting `ext::`/`file://` remote from being fetched later. That residual uncertainty should be resolved with local testing/a Devin session, since it affects whether the ultimate impact is limited to config corruption or extends to command execution via a smuggled `ext::` remote helper.

### Recommendation
- Add a `--` separator before the URL argument in `addRemote` (and any other call to `git remote ...` that takes a server-supplied URL), exactly as `clone()` already does.
- Add minimal runtime validation of API-derived fields that are subsequently used as git command arguments or filesystem paths (e.g., reject `clone_url`/`ssh_url` values that don't parse via `parseRemote`/a URL parser, or that start with `-`), rather than relying purely on the `IAPIRepository`/`IAPIPullRequest` TypeScript types, which give no runtime guarantee.

### Proof of Concept
1. Add a GitHub Enterprise Server account pointing at a server controlled by the attacker (or intercept/compromise a legitimate GHES instance).
2. Have that server return a pull request JSON payload where `head.repo.clone_url` is set to an option-shaped string (e.g. `--upload-pack=...` or similar) rather than a real URL.
3. In Desktop, trigger "Open PR from Desktop" / checkout of that PR (`AppStore._checkoutPullRequest` → `_findPullRequestBranch`): [7](#0-6) 
4. Because no existing remote matches, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)`, which runs `git remote add <name> <headCloneUrl>` with no `--` terminator, letting git interpret the attacker-controlled string as an option instead of a URL: [5](#0-4)

export async function parsedResponse<T>(response: Response): Promise<T> {
  if (response.ok) {
    return deserialize<T>(response)
  } else {
    let apiError: IAPIError | null
    // Deserializing the API error could throw. If it does, we'll throw a more
    // general API error.
    try {
      apiError = await deserialize<IAPIError>(response)
    } catch (e) {
      throw new APIError(response, null)
    }

    throw new APIError(response, apiError)
  }
}
