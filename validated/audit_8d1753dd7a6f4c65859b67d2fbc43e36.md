Based on the local evidence gathered, the strongest analog to the C4 report's "fee accounted before/without corrected state validation → double payment" is in `EvmHost.dispatchIncoming` for GET responses, where relayer-fee payout is not gated by any one-time-consumption check on `_requestCommitments[commitment].fee`.

### Title
Unbounded re-payment of GET-request relayer fee on repeated `dispatchIncoming(GetResponse,...)` calls - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` pays the relayer fee stored in `_requestCommitments[commitment].fee` every time it successfully executes, but never deletes or zeroes that fee entry, and never checks whether `_responseReceipts[commitment]` was already populated by a prior successful delivery before overwriting it and proceeding.

### Finding Description
In the GET-response delivery path: [1](#0-0) 

The function unconditionally writes `_responseReceipts[commitment]` at the top (not gated by `if (_responseReceipts[commitment].relayer != address(0)) revert`), invokes the destination app's `onGetResponse`, and — on success — transfers `_requestCommitments[commitment].fee` to `relayer` via `safeTransfer`. Crucially, `_requestCommitments[commitment]` is never deleted or zeroed after the payout on this success path.

Compare this to the sibling timeout path in the same contract, which does delete the fee record before/at dispatch: [2](#0-1) 

Because the fee metadata backing the payout is left intact after a successful `dispatchIncoming(GetResponse,...)` call, any subsequent call that re-verifies membership/state proofs for the same (or a re-derived) `commitment` and reaches the handler-restricted `dispatchIncoming` entrypoint again will re-read the same non-zero `fee` value and transfer it again — this mirrors the C4 finding's root cause: a monetary value (`_feeAmount` there, `fee` here) is used/paid out based on stale accounting state that is never adjusted/cleared to reflect that it has already been consumed once.

I was not able to fully verify, within available iterations, whether `HandlerV2.sol` (the caller of `dispatchIncoming`) independently enforces a hard "already delivered" gate before invoking this function for a given response commitment — `HandlerV2.sol` does reference `_responseReceipts` in several places, which could plausibly serve as an anti-replay check upstream. This is the key open uncertainty for this finding: if `HandlerV2` unconditionally rejects re-submission of a `GetResponse` whose commitment already has a receipt, this issue is not exploitable; if it does not (or if it only checks `_requestReceipts` for POST but not `_responseReceipts` for GET before calling into `dispatchIncoming`), the fee can be re-claimed on each resubmission of a valid state/membership proof, since Merkle/state proofs for a still-retained state commitment remain independently re-verifiable and re-submittable by design (unlike a nonce-based signature).

### Impact Explanation
If the upstream handler does not itself block re-delivery of an already-delivered GET response, a relayer (or any submitter who structures the same proof again) can drain the fee-token balance held by the host contract by resubmitting the same GET response proof multiple times, each time collecting `_requestCommitments[commitment].fee` again. This is fund loss/leakage from the host contract's fee reserves to a single relayer beyond what was actually owed — directly matching the bounty's "stealing or loss of funds" / "double-claim" impact class.

### Likelihood Explanation
Medium — this requires either (a) `HandlerV2.sol` lacking a hard idempotency check gating calls into `dispatchIncoming(GetResponse,...)`, or (b) any other restricted caller path that re-invokes it for an already-serviced commitment. This could not be conclusively confirmed against `HandlerV2.sol`'s full logic within this investigation, so likelihood is contingent on that unverified upstream gate.

### Recommendation
- Delete or zero `_requestCommitments[commitment]` immediately after paying the fee in `dispatchIncoming(GetResponse,...)`, mirroring the pattern already used in `dispatchTimeOut`.
- Additionally guard the top of `dispatchIncoming(GetResponse,...)` with an explicit check that `_responseReceipts[commitment].relayer == address(0)` (revert or no-op otherwise) rather than unconditionally overwriting it, so replayed proofs cannot re-trigger `onGetResponse` or fee payment even if an upstream caller fails to deduplicate.

### Proof of Concept
1. A GET request with a non-zero `fee` is dispatched and a valid `GetResponse` + membership/state proof pair becomes available while the referenced state commitment remains stored in `_stateCommitments`.
2. `dispatchIncoming(GetResponse, relayerA)` is called (via the handler) once — succeeds, pays `fee` to `relayerA`, but does **not** clear `_requestCommitments[commitment].fee`. [3](#0-2) 
3. If the handler does not track/reject an already-serviced response commitment, the same (still valid) state/membership proof is resubmitted, again reaching `dispatchIncoming(GetResponse, relayerB)`.
4. `_responseReceipts[commitment]` is simply overwritten; `onGetResponse` is invoked again; `fee` (still non-zero in storage) is transferred again — the host contract has now paid the same fee twice for one delivered response.

```text
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```
