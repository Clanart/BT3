### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` allows CPU/stack exhaustion from a single transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key of a role-based account key by re-invoking `AccountKeySerializer.DecodeRLP` → `NewAccountKey`/`s.Decode(serializer.key)`, and if that sub-key is itself of type `AccountKeyTypeRoleBased`, this chain calls back into `AccountKeyRoleBased.DecodeRLP` again. The "nested composite type is not allowed" check (`ErrNestedCompositeType`) is only enforced afterward, inside `CheckInstallable`/`CheckUpdatable`. This is structurally the same bug class as the pypdf advisory: recursively walking an attacker-supplied nested structure to completion before any depth/cost limit is applied, causing long runtimes / high memory or stack usage.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an array of encoded sub-keys and, for each entry, decodes it via a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and then recursively decodes the key value using `NewAccountKey` + `s.Decode(serializer.key)`: [2](#0-1) 

If the encoded key type is `AccountKeyTypeRoleBased` again, `NewAccountKey` returns another `AccountKeyRoleBased`, and `s.Decode` calls `AccountKeyRoleBased.DecodeRLP` a second time — recursing indefinitely as long as the attacker keeps nesting `RoleBased` arrays inside `RoleBased` arrays in the raw RLP bytes: [3](#0-2) 

The check that rejects nested composite keys (`ErrNestedCompositeType`) does not run during decoding — it only runs afterward, in `CheckInstallable`/`CheckUpdatable`, and only checks the *immediate* children of the top-level `RoleBased` key, not deep chains produced during decode: [4](#0-3) 

There is a runtime test (`account_key_test.go`) confirming that nesting is rejected functionally at the tx-processing layer, but this rejection happens only after decoding is fully complete — there is no depth counter or recursion limit inside `DecodeRLP` itself: [5](#0-4) 

Because RLP decoding of the `AccountKeyRoleBased` value happens as part of ordinary transaction/RLP-body decoding (e.g. for `TxTypeAccountUpdate` and fee-delegated variants), an attacker can submit a single, moderately sized transaction whose account-key field contains a deeply nested chain of `RoleBased` wrappers. This causes the decode path to recurse very deeply (bounded only by the maximum transaction/RLP payload size, not by any explicit depth limit), consuming large stack space and CPU before the eventual `ErrNestedCompositeType` rejection is even reached.

### Impact Explanation
This is directly analogous to the pypdf outline-traversal issue (CWE-405/CWE-834): unbounded recursive traversal of a nested, attacker-controlled structure performed eagerly during parsing/decoding, before any cheap validation or cost accounting can short-circuit it. In Kaia, this decode path is reachable by any unprivileged transaction sender submitting a crafted `TxTypeAccountUpdate` (or fee-delegated account-update) transaction to a public RPC node / tx pool, causing excessive CPU consumption or a stack-exhaustion crash while decoding the transaction, i.e. a resource-exhaustion (DoS) condition triggerable from a single submitted transaction.

### Likelihood Explanation
Any node that accepts and decodes such a transaction (via `eth_sendRawTransaction`/`klay_sendRawTransaction` or p2p tx propagation, both ultimately reachable from an unprivileged public RPC caller) would trigger the recursive decode before the nested-type validation runs. The attack requires only crafting the raw RLP bytes for the transaction's account-key field; no special privileges, prior state, or on-chain funds beyond what's needed to submit a transaction are required for it to reach the vulnerable decode path (though the actual state-transition application, if reached, would still reject it afterward via `ErrNestedCompositeType`).

### Recommendation
Add an explicit recursion/depth counter (or an iteration limit) to `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP` that rejects the input as soon as a nested `AccountKeyTypeRoleBased` (or any composite type) is encountered while decoding, matching the intent already enforced by `IsCompositeType()`/`ErrNestedCompositeType`, so the recursion is aborted immediately rather than after a full deep decode.

### Proof of Concept
Conceptually (cannot execute in this environment): craft an RLP-encoded `AccountKeySerializer` value whose `keyType == AccountKeyTypeRoleBased` and whose inner array element is itself an `AccountKeySerializer` with `keyType == AccountKeyTypeRoleBased`, repeated N times (nested chain), within a `TxTypeAccountUpdate` transaction's account-key field. Feed this transaction to `rlp.DecodeBytes`/tx pool decoding. Each nesting level costs only a few bytes, so N can be made very large within the max transaction size, causing deep recursive calls through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` before `ErrNestedCompositeType` is ever evaluated.

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
```

```go
func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
```
