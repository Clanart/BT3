## Title
Path traversal in `getWorkingDirectoryImage` allows reading files outside repository scope via crafted git status path - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` builds the file path to read for image-diff rendering using unguarded string concatenation instead of the codebase's standard traversal-safe helper, unlike equivalent code paths elsewhere in the app.

### Finding Description
`getWorkingDirectoryImage` resolves the on-disk path for a working directory file with: [1](#0-0) 
This performs `Path.join(repository.path, file.path)` and passes the result directly to `readFile`, with no call to `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` and no validation that the resolved path stays under `repository.path`. `file.path` originates from `FileChange`/`WorkingDirectoryFileChange`, whose `path` field is populated from git status output (or a rename's new path) — this is attacker-influenceable content because a malicious repository can control file names, including renamed/tracked path strings, that end up in status entries.

This is inconsistent with the rest of the codebase, where every other place that turns an attacker-influenced repository-relative path into a filesystem path explicitly guards against traversal using `resolveWithin`:
- `buildConflictContext` in `copilot-conflict-context.ts` uses `resolveWithin(workingDirectory, file.path)` and rejects null/outside-repo results. [2](#0-1) 
- The Copilot conflict resolution writer in `app-store.ts` uses `resolveWithin(repository.path, resolution.path)` before calling `writeFile`. [3](#0-2) 
- The deep-link "open file" handler in `dispatcher.ts` explicitly checks `isAbsolute` and calls `resolveWithin(repository.path, filepath)` before using `shell.showItemInFolder`. [4](#0-3) 

`resolveWithin` (in `app/src/lib/path.ts`) is specifically designed to defend against `../` sequences and symlink-based escapes by normalizing, resolving, and comparing the `realpath` of the result against the `realpath` of the root. [5](#0-4) 

`getWorkingDirectoryImage` does not use this helper at all, so a `FileChange.path` value containing `../` segments (e.g., `../../../../etc/passwd`) would cause `Path.join(repository.path, file.path)` to resolve outside `repository.path`, and `readFile` would return the out-of-repo file's bytes as if it were repository content.

### Impact Explanation
If reachable, this would let a malicious repository image-diff entry cause Desktop to read and base64-encode arbitrary files reachable from the process (subject to filesystem permissions) and display them as "image" content in the diff view — disclosing local user data (e.g., SSH keys, config files) to whatever surface renders that image (UI, and potentially further flows that export/share the diff).

### Likelihood Explanation
This depends entirely on whether `file.path` on a `WorkingDirectoryFileChange`/`FileChange` object can actually contain literal `../` traversal sequences by the time it reaches `getImageDiff`/`getWorkingDirectoryImage`. I was not able to fully verify this within the available context:
- I could not load the contents of `app/src/lib/status-parser.ts` or `app/src/models/status.ts` in this session (the search results for path parsing/decoding logic in `status-parser.ts` were truncated/not returned), so I cannot confirm whether git status entries are validated, unescaped, or otherwise constrained before becoming `FileChange.path`.
- Git normally rejects `..` path components inside a tracked tree, and paths returned by `git status -z` are relative to the repo root, which would make literal `../` segments unusual for genuine git-tracked paths — but I could not confirm from the code whether any normalization/rejection happens explicitly in Desktop's parser, nor whether other status kinds (e.g., untracked entries with unusual names, or rename source/destination pairs) could smuggle a `..` sequence past git's own protections.
- Because of the missing `resolveWithin` guard, *if* such a path can reach this function, the read would succeed without any check — this part of the claim is confirmed by the code shown above.

### Recommendation
Add the same `resolveWithin` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) guard used elsewhere in the codebase to `getWorkingDirectoryImage`, rejecting/skip-rendering when the resolved path falls outside `repository.path`, for consistency with `copilot-conflict-context.ts`, `app-store.ts`, and `dispatcher.ts`.

### Proof of Concept
Not fully verifiable from the available index. A conclusive PoC requires:
1. Reading `app/src/lib/status-parser.ts` and `app/src/models/status.ts` in full to determine whether `FileChange.path`/`WorkingDirectoryFileChange.path` can literally contain `../` sequences from a git status entry (via untracked file names, renames, or otherwise).
2. If so, a fixture repository with such a status entry, followed by a call to `getWorkingDirectoryImage(repository, file)` and an assertion that the resulting `Image` bytes match a file outside `repository.path`.

Given the confirmed absence of the `resolveWithin` guard at the sink [1](#0-0) , but the unresolved question of whether git status can actually produce a traversal path that reaches this function, I recommend this be treated as a **hardening gap / defense-in-depth issue** rather than a fully confirmed exploitable vulnerability without further investigation into `status-parser.ts`. I could not verify file contents there due to index limitations; a Devin session with full filesystem access would be needed to conclusively confirm or rule out reachability.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
