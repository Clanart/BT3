## Finding Analysis

I traced the path and can confirm the argument-injection mechanics described are technically present in the code, but the practical delivery mechanism needs an important caveat.

### The vulnerable path

`getRebaseSnapshot` reads `.git/rebase-merge/onto` and `.git/rebase-merge/orig-head` verbatim (only `.trim()` is applied, no validation) and stores them as `baseBranchTip`/`originalBranchTip`: [1](#0-0) 

These are passed straight into `getCommitsBetweenCommits`: [2](#0-1) 

which builds the range as a single concatenated string with no escaping: [3](#0-2) [4](#0-3) 

and `getCommitsInRange` places that string in the argv array **before** the `--` terminator: [5](#0-4) 

If `onto` = `--output=/tmp/evil`, the resulting single argv token becomes `--output=/tmp/evil..<originalBranchTip>`. Git's long-option parser matches on the `--output=` prefix and treats everything after `=` (including the `..` and the rest of the range) as the literal filename value, so `git rev-list` will attempt to write output to that attacker-influenced path. Since `orig-head` is *also* attacker-controlled, the trailing portion of the filename is likewise attacker-chosen (e.g. setting `orig-head` to an empty value minimizes trailing noise). `--output` is a legitimate `git rev-list` option for writing output to a file instead of stdout, so this is a real argument-injection sink, not a hypothetical one.

`getRebaseSnapshot` is exercised on the "external rebase in progress" detection path, e.g. from `continueRebase`'s progress-tracking branch: [6](#0-5) 

### Why this is likely NOT exploitable via a normal `git clone`

The question's premise is that the attacker delivers `.git/rebase-merge/onto` and `orig-head` "via a cloned/extracted repository." This doesn't hold for an ordinary `git clone`: `.git/rebase-merge` is local, ephemeral rebase state — it is never part of the object database or refs transferred by the git wire protocol (fetch/clone only exchange objects and refs, not arbitrary files under `.git/`). A plain `git clone <malicious-remote>` cannot plant files under `.git/rebase-merge` on the victim's disk.

The only realistic delivery vectors are:
- The victim extracts an archive/zip that directly contains a fabricated `.git` directory (including a `rebase-merge` subfolder) and then adds that folder as an "existing repository" in GitHub Desktop, or
- Some other mechanism giving the attacker write access to files under `.git/` in a repository the victim already has (which would itself typically already be attacker-controlled local content, bordering on "local access").

This is a materially different (narrower) delivery path than "clone a malicious repo," even though the question frames it as such.

## Title
Argument Injection via Crafted `.git/rebase-merge/onto` Leading to Arbitrary File Write through `git rev-list --output=` - (File: `app/src/lib/git/rev-list.ts`)

### Summary
`getRebaseSnapshot`/`getRebaseInternalState` read `.git/rebase-merge/onto` and `.git/rebase-merge/orig-head` without validation and pass their content into `revRange`, which is placed in the `git rev-list` argv array before the `--` terminator, allowing an option like `--output=<path>` to be interpreted as a Git flag instead of a revision.

### Finding Description
`getRebaseSnapshot` reads `onto` and `orig-head` and forwards them to `getCommitsBetweenCommits` → `revRange` → `getCommitsInRange`, which constructs `['rev-list', range, '--reverse', '--oneline', '--no-abbrev-commit', '--']`. Because `range` (attacker-controlled) sits before `--`, a value beginning with `--output=` is parsed by Git as the `--output` option rather than as a revision, letting Git write its rev-list output to an attacker-influenced filesystem path. [5](#0-4) [7](#0-6) 

### Impact Explanation
If reached, this allows writing an attacker-influenced file to an arbitrary path outside the repository (file write/overwrite outside the repo, in scope per the bounty's valid-impact list).

### Likelihood Explanation
Low-to-moderate. It requires the attacker to control the literal contents of `.git/rebase-merge/onto` and `orig-head` on disk. This state is never populated by the standard git clone/fetch wire protocol, so it cannot be delivered by a normal "malicious remote clone." It requires the victim to extract/open an archive that already contains a fabricated `.git/rebase-merge` directory and add it as a repository in Desktop — a more unusual, though not impossible, delivery path than a simple clone.

### Recommendation
Always append `--` immediately after the range/revision argument and before any other flags is not sufficient by itself since `--output` still precedes `--`; the fix should be to validate that `onto`/`orig-head` (and any other file-derived rev values) look like valid SHAs/refs (reject values starting with `-`) before using them to build `rev-list` arguments, and/or insert `--` immediately after the potentially-attacker-controlled range token rather than at the end of the argv array.

### Proof of Concept
1. Create a directory with a `.git` folder that has a valid `HEAD`/object store plus `REBASE_HEAD`, and a `rebase-merge` subdirectory containing:
   - `onto` = `--output=/tmp/evil`
   - `orig-head` = `` (or any string)
   - `head-name` = `refs/heads/some-branch`
   - `msgnum` = `1`
   - `end` = `1`
2. Add/open this folder as an existing repository in GitHub Desktop, triggering a code path that calls `getRebaseSnapshot` (e.g. the app's mid-rebase detection, or `continueRebase` with a progress callback).
3. Observe that `git rev-list --output=/tmp/evil..<value> --reverse --oneline --no-abbrev-commit --` is invoked and a file is created at (or near) `/tmp/evil...` outside the repository.

**Note:** I was unable to fully verify, within the available search budget, every automatic call site in `app-store.ts`/`dispatcher.ts` that triggers `getRebaseSnapshot` without an explicit user "continue rebase" action, which would materially affect whether this is exploitable purely by opening the folder versus requiring an in-app rebase-continuation click. This should be confirmed before treating likelihood as anything beyond low-to-moderate.
