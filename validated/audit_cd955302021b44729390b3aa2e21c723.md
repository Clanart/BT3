Confirmed: `RegisterERC20` is permissionless when `params.PermissionlessRegistration` is true, meaning any unprivileged user can register an arbitrary, attacker-controlled ERC20 contract as a native token pair. [1](#0-0)  Combined with `convertERC20IntoCoinsForNativeToken`, this creates a viable analog to the `pricePerShare` finding: the keeper trusts a self-reported value from potentially malicious/untrusted contract code with only an internal-consistency check, not an external ground-truth check.

### Analysis of the analog

In `convertERC20IntoCoinsForNativeToken`, the keeper calls the token pair's own `balanceOf`/`transfer` functions on the module address before and after doing an EVM `transfer` call, and only checks that the delta matches `msg.Amount`: [2](#0-1) 

The mint amount for the native bank coin is **not** derived from the actual, verified transfer amount — it is derived from `coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}`, i.e., the user-supplied `msg.Amount`. [3](#0-2)  The "invariance check" (`balanceTokenAfter.Cmp(expToken)`) only verifies that the contract *reports* a consistent state before/after its own call — it does not verify against any independent source of truth. Because the contract itself is attacker-deployed and attacker-controlled (arbitrary bytecode registered permissionlessly), the attacker can make `balanceOf` and `transfer` return whatever values are needed to satisfy this self-consistency check without ever escrowing real value, then have the keeper mint real bank coins (`k.bankKeeper.MintCoins`) backed by nothing.

This mirrors the `pricePerShare` bug's root cause exactly: a critical accounting decision (how many "real" units to release/mint) is derived from a value read from an entity (an oracle in ibBTC; an arbitrary registered ERC20 contract here) that has no external sanity/backing check, only a self-referential check.

### Title
Permissionless ERC20 registration + self-reported balance checks in `ConvertERC20` allow unbacked native coin minting - (File: `x/erc20/keeper/msg_server.go`)

### Summary
When `params.PermissionlessRegistration` is enabled, any user can register an arbitrary ERC20 contract as a native token pair via `RegisterERC20`. [4](#0-3)  `ConvertERC20` → `convertERC20IntoCoinsForNativeToken` then mints native bank coins in an amount equal to `msg.Amount`, gated only by a balance check performed against the *same* malicious contract's own `balanceOf` function. [5](#0-4) 

### Finding Description
The keeper's invariant check compares `balanceToken` (pre-call) and `balanceTokenAfter` (post-call), both obtained via `k.BalanceOf`, which internally performs an EVM `staticcall`/`call` to the token contract's own `balanceOf` method. [6](#0-5) [7](#0-6)  Since the contract code is entirely attacker-supplied (no code review, no owner/whitelist gate when permissionless registration is on), the attacker can implement `balanceOf` and `transfer` to report an arbitrary self-consistent delta (e.g., always reporting `balanceToken + msg.Amount` regardless of whether tokens were actually moved), defeating the "invariance" check entirely. The subsequent `k.bankKeeper.MintCoins(ctx, types.ModuleName, coins)` then mints real, spendable native coins for the attacker with no economic backing. [8](#0-7) 

### Impact Explanation
This directly matches the "Critical unauthorized minting... irreversible accounting corruption of spendable user value across native balances" impact class. An attacker can mint unlimited native coins denominated as `pair.Denom` by registering a malicious contract and repeatedly calling `MsgConvertERC20`, inflating the real, spendable bank-module supply without any backing, which can then be transferred, staked, or used elsewhere in the chain economy — an unauthorized, permanent, and irreversible supply/accounting corruption.

### Likelihood Explanation
Requires `params.PermissionlessRegistration = true` (a governance-configurable, module-level parameter) to be enabled for the permissionless path; if `false`, registration requires `k.validateAuthority`, requiring a privileged authority signer. [9](#0-8)  Given that many EVM-compatible chains built on this SDK enable permissionless ERC20 registration to allow open token listing (a documented, intended user-facing feature), this is a realistic and directly triggerable unprivileged flow, not a privileged-key or malicious-validator scenario.

### Recommendation
Do not rely solely on the pair contract's self-reported `balanceOf` delta as the sole invariant. Instead:
1. Cross-check the transfer event logs (`Transfer(from, to, value)`) emitted by the contract against expected addresses/amounts as an independent signal, and require them to be present and consistent even when a return value exists.
2. Consider requiring additional validation/sandboxing at registration time (e.g., verifying standard ERC20 bytecode patterns, disallowing arbitrary/proxy contracts, or requiring a bond/vetting period) before allowing `IsNativeERC20()` token pairs to mint bank coins.
3. Cap or rate-limit per-pair minting for newly, permissionlessly-registered token pairs until additional confirmations (e.g., time-locked or governance-reviewed) are established.

### Proof of Concept
1. Enable `PermissionlessRegistration` (or use a chain where it's already enabled).
2. Deploy a malicious ERC20 contract where `transfer(to, amount)` is a no-op returning `true`/emitting a fake `Transfer` event, and `balanceOf(account)` returns a value that increases by `amount` on each call regardless of actual token movement (e.g., tracked via an internal counter unrelated to real balances).
3. Call `MsgRegisterERC20` with this contract address; `k.registerERC20` creates a native-ERC20 token pair (verify no bytecode/behavior validation blocks this).
4. Call `MsgConvertERC20` with an arbitrary `Amount`. The pre/post `BalanceOf` check passes because the malicious contract reports the expected synthetic delta. [10](#0-9) 
5. Observe `k.bankKeeper.MintCoins` mints real native coins of `pair.Denom` to the module and sends them to the attacker's receiver — verify these coins are genuinely spendable/transferable elsewhere in the bank module, confirming unbacked minting.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}
