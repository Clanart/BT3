**Analysis:** The concern describes a non-issue given Rust's error-propagation semantics. In `verify_parachain_headers_with_grandpa_finality_proof`, the `verified_parachain_headers: BTreeMap<u32, Vec<H>>` is a purely local variable built up across the `for (hash, proof) in parachain_headers` and inner `for (key, para_id) in keys` loops [1](#0-0) . If `result.remove(&key).flatten().ok_or(Error::ParachainHeaderNotFound)?` fails for any `para_id` (e.g., a later one after an earlier `para_id` succeeded), the `?` operator triggers an early `return Err(...)` from the entire function [2](#0-1) .

Because the function's return type is `Result<(ConsensusState, BTreeMap<u32, Vec<H>>), Error>`, there is no code path that returns a partially-built `verified_parachain_headers` — the `Ok((consensus_state, verified_parachain_headers))` line is only reached if every iteration completes without error [3](#0-2) . On any error, the local `verified_parachain_headers` (and the mutations already applied to it) is simply dropped when the function unwinds; it is never exposed to the caller.

The only caller, `GrandpaConsensusClient::verify_consensus`, also uses `?` on this call: `let (consensus_state, parachain_headers) = verify_parachain_headers_with_grandpa_finality_proof(consensus_state, headers_with_finality_proof)?;` [4](#0-3) . If the inner call errors, `verify_consensus` itself returns `Err`, and none of the state-commitment insertion logic downstream (which would persist `intermediates`/`StateCommitmentHeight`s into runtime storage) ever executes [5](#0-4) . No partial or corrupted map is observable or usable by any caller — there is no mechanism for a "partially mutated" `BTreeMap` to leak out of an all-or-nothing `Result`-returning function in Rust. The proof idea does not identify an actual state-corruption or false-acceptance path; it misattributes a language-level guarantee (atomic `Result` returns) as a vulnerability.
