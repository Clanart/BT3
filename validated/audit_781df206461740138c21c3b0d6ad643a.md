### Title
Attacker-controlled `n` in serialized `ThresholdKeys` triggers quadratic Lagrange-interpolation work, enabling CPU-exhaustion DoS - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts an untrusted byte stream containing the participant count `n` as a raw `u16`. It reads `n` scalars and `n` group elements, then calls `ThresholdKeys::new`, which computes the group key by evaluating a full Lagrange interpolation factor for each of the `t` participants — an `O(t²)` (up to `O(n²)`) sequence of field operations. A single crafted serialization of a few megabytes therefore expands into billions of scalar multiplications, the same amplification pattern as the CBOR "billion laughs" reference-expansion advisory: a small input is expanded into work orders of magnitude larger during a routine decode-and-use path.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the reader, then iterates `1 ..= n` deserializing verification shares and reads `n` coefficient scalars for `Interpolation::Constant` [1](#0-0) . Validation of `n` happens only afterward inside `ThresholdKeys::new`/`ThresholdParams::new` [2](#0-1) .

Inside `ThresholdKeys::new`, the group key is computed as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [3](#0-2) 

Each `interpolation_factor` call under `Interpolation::Lagrange` loops over every entry in `included`, performing field multiplications per element [4](#0-3) . Total cost is therefore `t × t` field multiplications plus `t` point-scalar multiplications. With the attacker-controlled maximum `t = n = 65535`, that is ~4.3 billion field multiplications, triggered by a serialized blob of roughly 2–4 MB (65535 encoded points + scalars). The same quadratic pattern recurs in `view()`, which computes an interpolation factor per included signer [5](#0-4) .

There is no upper bound on `t`/`n` other than `t <= n <= u16::MAX` [6](#0-5) , and no pre-allocation or pre-validation that would let a caller cheaply reject oversized inputs before the quadratic work begins.

### Impact Explanation
Any component that feeds untrusted bytes to `ThresholdKeys::read` — explicitly listed as a reachable untrusted-bytes sink — can be forced into sustained CPU exhaustion on a single ~MB-scale message. Because `n` is read before validation and the expensive interpolation runs unconditionally in `ThresholdKeys::new`, the caller cannot avoid the cost. Realistic Serai multisigs have `n` in the low hundreds; a `t = n = 65535` payload is malformed for any legitimate deployment yet is fully accepted by the decoder. Repeated submissions amplify this into a full denial of service of the decoding endpoint. This maps directly onto the advisory's class: input expansion during decode/serialization yielding orders-of-magnitude resource consumption, though here it is CPU rather than memory.

### Likelihood Explanation
Requires an exposed path where an unauthenticated or low-privilege party can submit serialized `ThresholdKeys` bytes (e.g., processor/coordinator key-loading or RPC surfaces). Wherever such a surface exists, exploitation is deterministic, requires no secrets, and needs only a modest upload. Severity is bounded by the `u16` cap on `n`, so the amplification is quadratic within a fixed ceiling rather than truly unbounded — consistent with Medium severity rather than the advisory's High.

### Recommendation
- Validate `t`/`n` against a protocol-sane maximum before performing any allocation or interpolation (e.g., reject `n` above the multisig's configured bound or a hard cap aligned with deployment limits).
- Compute `ThresholdParams::new(t, n, i)` immediately after reading the header and reject before the `read_G` loop, not after all shares are deserialized.
- Replace the naive per-participant Lagrange evaluation with an `O(t)`-ish scheme (prefix/suffix products) or memoized interpolation so the group-key derivation is linear in `t`.

### Proof of Concept
1. Craft a `ThresholdKeys` serialization for any curve (e.g., `Secp256k1`): valid `C::ID` prefix, `t = 0xFFFF`, `n = 0xFFFF`, `i = 1`, interpolation tag `1` (Lagrange), followed by a nonzero scalar encoding and 65535 copies of a valid point encoding (~2–4 MB total).
2. Feed the bytes to `ThresholdKeys::<C>::read`.
3. `ThresholdKeys::new` executes `interpolation_factor` 65535 times, each iterating 65535 participants — ~4.3 billion field multiplications — before returning, pinning a CPU core on a single untrusted input.
