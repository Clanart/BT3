## Finding

Tron's `IntentGatewayV2.placeOrder()` lacks the reentrancy guard present in the canonical EVM contract, and reuses a shared `CallDispatcher` whose escrowed-amount accounting is based on the dispatcher's *total* token balance rather than a per-order delta — reproducing the exact "balance snapshot assumed to belong to one actor" flaw described in the external Vault report.

### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder()` allows predispatch-triggered reentrancy to corrupt shared CallDispatcher escrow accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The reference EVM implementation guards `placeOrder` with `nonReentrant` [1](#0-0) [2](#0-1) . The Tron port of the same contract defines `placeOrder` without any reentrancy protection [3](#0-2) .

### Finding Description
`placeOrder` optionally routes input tokens through a shared `CallDispatcher` contract (`_params.dispatcher`) to run attacker-supplied `order.predispatch.call` calldata before escrowing funds [4](#0-3) . After the predispatch call executes, the gateway sweeps tokens back from the dispatcher by reading its **entire current balance**, not a before/after delta:

```
balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)});
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [5](#0-4) 

This is structurally identical to the reported Vault bug: it assumes the dispatcher's balance belongs solely to the order currently being processed, exactly as the Vault assumed `balanceOf(vault)` reflected only the caller's just-sent deposit. Because `placeOrder` is a public entrypoint with no `nonReentrant` guard on Tron, the attacker-controlled `order.predispatch.call` (dispatched via `ICallDispatcher(dispatcher).dispatch(...)`) can call back into `placeOrder` (or any other state-mutating function on the shared gateway/dispatcher) before the outer call's sweep step runs. A nested `placeOrder` invocation can push additional tokens onto the same dispatcher in the window between the outer order's "transfer to dispatcher" and "sweep whole balance back," so the outer sweep pulls in tokens that belong to the nested/second order while crediting escrow with a fixed `reducedInputs[i].amount` unrelated to what was actually swept. This produces the same class of fund misattribution as the source report: escrow credited to the wrong order/commitment, or one order's assets consumed by another's accounting.

### Impact Explanation
This directly matches the bounty's "logic attacks" and "wrong beneficiary or amount" criteria: an unprivileged caller can construct an order whose predispatch calldata reenters the same public `placeOrder` entrypoint, exploiting the whole-balance sweep to redirect or duplicate-credit escrowed tokens on the shared `CallDispatcher`, resulting in loss of user funds or protocol-level accounting corruption without needing any relayer, prover, or admin.

### Likelihood Explanation
The attack requires only the attacker's own order with attacker-controlled `predispatch.call` and `predispatch.assets` — a fully public, unprivileged flow. No malicious peer, relayer, or governance actor is required; it exploits standard EVM-compatible reentrancy against a single missing modifier, which is a concrete, easily verifiable code difference from the audited/guarded EVM sibling contract.

### Recommendation
Add `nonReentrant` (or the transient-storage reentrancy guard already used in the EVM version) to Tron's `placeOrder`, and change the CallDispatcher sweep logic to record `balanceBefore`/`balanceAfter` deltas per order rather than sweeping the dispatcher's total balance, mirroring the fix already present in `evm/src/apps/IntentGatewayV2.sol` (lines 229–280).

### Proof of Concept
1. Attacker deploys a malicious contract `M` and constructs `orderA` with `predispatch.call` = calldata that calls back into `IntentGatewayV2.placeOrder(orderB, ...)` on the same gateway/dispatcher, where `orderB` also uses `predispatch.assets`/`predispatch.call`.
2. Attacker calls `placeOrder(orderA, ...)`. Execution enters the `if (predispatch...)` branch [4](#0-3) , transfers `orderA`'s assets to `dispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(orderA.predispatch.call)`.
3. Inside that call, `M` reenters `placeOrder(orderB, ...)` (no guard blocks this on Tron), which also moves tokens onto `dispatcher` and performs its own sweep/escrow bookkeeping, mutating shared dispatcher balance and `_orders` state before `orderA`'s own sweep step runs.
4. Control returns to `orderA`'s flow, which reads `balanceOf(dispatcher)` (now including leftover/inflated amounts from the nested call) and credits `_orders[commitmentA][token] += reducedInputs[i].amount` while sweeping the combined balance to the gateway — misattributing funds between `orderA` and `orderB`.

Confirmation of the missing guard (compare to the EVM contract's `nonReentrant` modifier) is direct from the source; the exact exploitability of the nested `placeOrder` state interaction depends on additional runtime details (e.g., whether the reentered call reverts elsewhere) that would need to be validated with a live fork/PoC test, which is outside what static code reading can fully confirm here.
