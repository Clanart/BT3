**Why the claimed TOCTOU does not exist:**

`freeze_code_object` first marks all packages of the target `code_object` as immutable, and then — within the very same function, still inside the same atomic transaction execution — calls `check_dependencies(code_object_addr, &pack)` for each package to re-validate the dependency policies against the *current* on-chain state of every dependency's `PackageRegistry`: [1](#0-0) 

`check_dependencies` freshly borrows each dependency's `PackageRegistry` and asserts `dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy`, aborting with `EDEP_WEAKER_POLICY` otherwise: [2](#0-1) 

Both the "read" (marking the caller's own packages immutable) and the "assertion" (checking dependency policy) happen inside a single Move transaction execution, which Aptos's execution engine (Block-STM) treats as an atomic unit operating on a consistent snapshot of global storage. There is no yield point within a Move transaction where another transaction's write-set can be interleaved mid-function. Block-STM's optimistic concurrency control detects read/write conflicts between transactions and re-executes/aborts a transaction if a conflicting write from another transaction (e.g., a dependency's downgrade) is committed before it in the serialization order — it does not allow a transaction to observe a torn/partial view where the dependency's policy changes mid-execution of `freeze_code_object`. So the two orderings are:

- Downgrade commits before freeze in the block's serialization order → `check_dependencies` inside `freeze_code_object` reads the weakened policy and aborts with `EDEP_WEAKER_POLICY` (confirmed by the existing test `freeze_code_object_fail_when_having_mutable_dependency`, which exercises exactly this abort path): [3](#0-2) 
- Freeze commits before downgrade → freeze succeeds against the still-valid (stronger) policy, and the dependency's subsequent downgrade is a separate, independent state transition that does not retroactively corrupt the already-committed immutable package.

There is no code path where `freeze_code_object`'s own read of the dependency's policy and its assertion diverge within one execution — they are the same `borrow_global` call used immediately by the assertion in `check_dependencies`. The proposed "TOCTOU window" would require the Move VM to suspend a transaction mid-function and let another transaction interleave its effects into the same in-progress function frame, which is not how Aptos transaction execution or Block-STM's serializable scheduling works.
