### Title
Empty aggregate Schnorr signature is accepted as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` checks that the encoded nonce count matches `keys_and_challenges.len()`, but it does not require the count to be non-zero. An aggregate containing zero nonces and a zero `s` scalar therefore verifies against an empty public-key/challenge list, even though `SchnorrAggregator::complete` explicitly refuses to produce an empty aggregate. [1](#0-0) [2](#0-1) 

### Finding Description
`SchnorrAggregate::read` accepts an untrusted four-byte nonce count of zero followed directly by a canonical scalar `s`. [3](#0-2)  During verification, the length equality check passes for an empty `keys_and_challenges`, no statement pairs are generated inside the loop, and the only remaining pair is `(-s, G)`. [1](#0-0)  Setting `s = 0` makes that statement the group identity, so `multiexp_vartime(...).is_identity()` returns true and the forged aggregate is accepted. [4](#0-3) 

The production aggregator treats an empty aggregation as invalid and returns `None`, confirming that an empty aggregate is outside the intended domain rather than a meaningful signature over zero messages. [2](#0-1) 

### Impact Explanation
A caller that accepts an attacker-supplied serialized aggregate, and then calls `verify` with an empty signer/challenge set, accepts a signature that no signer produced. This is a forged signature acceptance caused by an omitted boundary check: the verifier validates `Rs.len() == keys_and_challenges.len()` but permits `0 == 0`, making the verification equation degenerate. [1](#0-0) 

### Likelihood Explanation
The attacker only needs to submit a short canonical serialization: a zero `u32` count followed by the canonical encoding of scalar zero. No private key, nonce, valid signature, malicious validator, or protocol collusion is required because `SchnorrAggregate::read` and `verify` operate directly on the supplied bytes and caller-provided statement list. [3](#0-2) [1](#0-0) 

Exploitation requires the consuming code path to invoke verification with zero expected statements; a caller that independently enforces a non-empty signature set is not affected. Since deserialization itself does not establish that invariant, the library API remains unsafe for consumers treating `verify` as a complete validation routine.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` before checking equality and constructing the multiexp. For defense in depth, also reject `self.Rs.is_empty()` in `read`, matching the producer-side invariant already enforced by `SchnorrAggregator::complete`. [1](#0-0) [2](#0-1) 

```rust
if self.Rs.is_empty() || self.Rs.len() != keys_and_challenges.len() {
  return false;
}
```

### Proof of Concept
For a ciphersuite with a 32-byte canonical scalar encoding, the malicious serialized aggregate is:

```rust
let mut forged = Vec::new();
forged.extend_from_slice(&0u32.to_le_bytes()); // zero Rs
forged.extend_from_slice(&[0u8; 32]);         // s = 0

let aggregate =
  SchnorrAggregate::<Ed25519>::read(&mut forged.as_slice()).unwrap();

assert!(aggregate.verify(b"application DST", &[]));
```

The empty `keys_and_challenges` slice passes the length check, the loop adds no weighted statements, `s = 0` leaves only the identity term, and `multiexp_vartime` reports success. [1](#0-0)
