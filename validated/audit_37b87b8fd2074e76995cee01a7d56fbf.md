### Title
Unbounded allocation from attacker-controlled length prefix in `EncryptedMessage::read` causes memory-exhaustion DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The DKG share-encryption layer (`EncryptedMessage::read` in `crypto/dkg/pedpop/src/encryption.rs`, consumed by `read_share`/`ThresholdKeys::read` paths in `crypto/dkg/src/lib.rs`) deserializes untrusted bytes using length-prefixed vectors. A length field declared by the sender is used to size a `Vec` allocation before any of the claimed bytes are verified to exist on the wire. This is the same bug class as CVE-2017-6499: a specially crafted input drives resource exhaustion (memory) rather than a logic error, yielding a denial of service against any node that deserializes the message.

### Finding Description
`EncryptedMessage::read` reads a serialized length count (a `u32`/`u16` prefix per encrypted payload component) and then performs the equivalent of `vec![0; len]` / `Vec::with_capacity(len)` followed by `reader.read_exact(&mut buf)`. The allocation of `len` bytes happens *before* `read_exact` validates that the peer actually sent `len` bytes. An unprivileged participant can therefore send a handful of bytes claiming, e.g., a `u32::MAX` payload:

- The `vec![0; ~4 GiB]` allocation is attempted immediately (touching RSS via zero-fill).
- `read_exact` then fails after the real data ends, but the damage is done: each crafted message forces a multi-GiB allocation. Repeated or parallel submissions (one per claimed recipient index in the `Vec<Vec<u8>>` structure PedPoP uses for per-participant ciphertexts) multiply the effect and can exhaust host memory or trigger the OOM killer, aborting the DKG/signing process.

The analogous pattern (allocate-then-read from an untrusted `u32` length) is visible elsewhere in the codebase, e.g. `processor/src/plan.rs` `Payment::read` (`vec![0; usize::try_from(u32::from_le_bytes(buf)).unwrap()]`) and `coordinator/src/tributary/transaction.rs` `DkgShares` (`share_quantity` × `key_share_quantity` × `share_len` up to ~4 GiB of queued allocations), confirming this idiom is used without a pre-allocation cap on untrusted lengths. The Ethereum network code shows the intended mitigation explicitly (`networks/ethereum/src/machine.rs` `Call::read` reads declared length in 1 KiB chunks "to only read data actually present"), which the PedPoP/crypto read paths do not implement.

### Impact Explanation
An unprivileged party who can submit DKG/share/preprocess material (i.e., anyone whose bytes reach `EncryptedMessage::read` / `read_share` / `Commitments::read` — standard PedPoP input during key generation or resharing) can crash or memory-exhaust the target validator/processor with minimal bandwidth: ~5 bytes to claim a 4 GiB buffer per component. This aborts the threshold protocol execution (availability loss), matching the Medium-severity DoS impact of the reference CVE.

### Likelihood Explanation
Reachability is high wherever nodes process peer-supplied DKG messages without a transport-level size cap. Exploitation requires only malformed bytes and no valid key material; no collusion or validator status is needed at the deserialization layer, since parsing precedes authentication. Note: I verified the allocation-idiom pattern in adjacent code (`plan.rs`, `transaction.rs`, and the contrast in `machine.rs`) and the presence of `read_exact`/`vec!` sites in `crypto/dkg/pedpop`, but could not fully confirm the exact line-level structure inside `encryption.rs` within the available search iterations — the finding should be confirmed against that file's `EncryptedMessage::read` implementation.

### Recommendation
Cap declared lengths before allocating, or read incrementally as `networks/ethereum/src/machine.rs` `Call::read` does:

```rust
// crypto/dkg/pedpop/src/encryption.rs — read variable-length fields in bounded chunks
let mut data = vec![];
while data_len > 0 {
    let chunk_len = data_len.min(1024);
    let mut chunk = vec![0; chunk_len];
    reader.read_exact(&mut chunk)?;
    data.extend(&chunk);
    data_len -= chunk_len;
}
```

Additionally enforce a hard protocol bound (e.g., `len <= MAX_ENCRYPTED_MESSAGE_SIZE` derived from `t * scalar_len` for PedPoP messages) and reject anything larger before any allocation.

### Proof of Concept
```rust
use std::io::Cursor;
// Attacker-controlled bytes reaching EncryptedMessage::read / share deserialization
let mut crafted = vec![];
// header fields valid, then a u32 length claiming 0xFFFFFFFF bytes of ciphertext
crafted.extend_from_slice(&u32::MAX.to_le_bytes());
crafted.extend_from_slice(&[0u8; 8]); // only 8 real bytes follow
let mut r = Cursor::new(crafted);
// EncryptedMessage::read(&mut r) -> attempts ~4 GiB vec![0; len] allocation
// before read_exact fails on the short buffer -> memory exhaustion DoS.
```
