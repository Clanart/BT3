### Title
Unhandled `uint64` underflow exception on malformed spend bundles in mempool fee computation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` before any check that `removal_amount >= addition_amount` has been performed. If a submitted spend bundle creates coins whose total value exceeds the value of the coins it spends (an "inflation" attempt), this subtraction is negative and the `uint64()` constructor raises an uncaught `ValueError`, mirroring the reported Solidity bug class where an unsigned-subtraction result is cast to a signed/typed value only *after* the underflow has already occurred.

### Finding Description
In the reported issue, `int256(currentPrice - lastPrices[_protocolId])` computes the unsigned subtraction first and casts afterward, so any case where the subtrahend exceeds the minuend reverts instead of producing the intended negative value.

The same "compute value difference on unsigned-shaped intermediate, then cast" pattern occurs in the mempool admission path: [1](#0-0) 

`removal_amount` and `addition_amount` are plain Python ints accumulated from coin amounts elsewhere in the function, and the guard that would reject a bundle where additions exceed removals (`Err.MINTING_COIN`) only exists in the *full block* validation path, not in per-spend-bundle mempool admission: [2](#0-1) 

Nothing in `validate_spend_bundle()` prevents `addition_amount` from exceeding `removal_amount` before the `uint64(...)` cast is evaluated — an unprivileged submitter fully controls the puzzle reveal/solution of the coin(s) being spent and can trivially instruct a puzzle to emit `CREATE_COIN` conditions summing to more than the coin's own amount (CLVM execution does not enforce conservation of value; only the higher-level fee/removal-vs-addition check does, and that check happens too late here). The `uint64` type used throughout the codebase raises `ValueError`/`OverflowError` on negative values rather than wrapping, as demonstrated by: [3](#0-2) 

An identical pattern also exists in the trusted-side helper `compute_block_fee`: [4](#0-3) 

### Impact Explanation
If the `ValueError` raised by `uint64(removal_amount - addition_amount)` in `validate_spend_bundle()` is not caught by an enclosing exception handler, an unprivileged peer can submit a single malformed (value-inflating) spend bundle to a full node's mempool manager and cause an unhandled exception during transaction processing, instead of the intended clean `Err` rejection path. This matches the "spend-triggered transaction-processing halt" impact category: a single crafted spend bundle disrupts normal mempool/transaction-processing flow on any node that receives it, rather than being cleanly rejected with a validation error.

### Likelihood Explanation
Constructing a spend bundle whose `CREATE_COIN` conditions sum to more than the spent coin's amount requires no special privileges — any standard puzzle reveal/solution can be crafted to emit such conditions, and submitting the resulting spend bundle to a full node's `respond_transaction`/mempool ingestion path is available to any wallet or unauthenticated peer that can push a transaction. The only open question (not verifiable from the indexed code alone) is whether a broader `try/except` wraps the call site of `validate_spend_bundle()` in the full node's transaction handler, which would downgrade this from a processing halt to a logged/swallowed error. This uncertainty should be resolved by tracing all callers of `validate_spend_bundle()`.

### Recommendation
Add an explicit non-negative check before casting to `uint64`, mirroring the recommendation in the original report — compute the difference on plain (or explicitly `int`) types and validate `removal_amount >= addition_amount` (returning a proper `Err.MINTING_COIN`-style rejection) prior to `uint64(...)` conversion, in both `mempool_manager.py` and `compute_block_fee`.

### Proof of Concept
1. Construct a coin spend for a standard-owned coin of amount `N` whose solution instructs the puzzle to emit a `CREATE_COIN` condition (or several) totaling `> N`.
2. Submit the resulting `SpendBundle` to a full node (e.g., via the wallet protocol / RPC transaction submission path reachable by any peer).
3. In `MempoolManager.validate_spend_bundle()`, `addition_amount` (sum of created coin amounts) exceeds `removal_amount` (sum of spent coin amounts) at: [5](#0-4) 
4. `uint64(removal_amount - addition_amount)` raises `ValueError`, analogous to the Solidity underflow revert, before the higher-level minting check (which only exists later, in block-body validation) has a chance to reject the bundle cleanly.

Note: I was unable to fully trace every caller of `validate_spend_bundle()` to confirm whether a top-level exception handler ultimately swallows this `ValueError` (which would reduce impact to a logged rejection rather than a genuine processing halt); this should be verified directly in the full node's transaction-handling call sites before treating this as confirmed-exploitable.

def compute_block_fee(additions: Sequence[Coin], removals: Sequence[Coin]) -> uint64:
    removal_amount = 0
    addition_amount = 0
    for coin in removals:
        removal_amount += coin.amount
    for coin in additions:
        addition_amount += coin.amount
    return uint64(removal_amount - addition_amount)
