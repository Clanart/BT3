## Analysis

`getWorkingDirectoryImage` in `app/src/lib/git/diff.ts` builds the file path with a plain `Path.join` and reads it with Node's `fs.readFile`, which transparently follows symlinks — it does **not** use the app's own `resolveWithin` path-confinement helper that exists specifically to prevent this class of bug. [1](#0-0) 

Compare this to `app/src/lib/path.ts`, which implements `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` precisely to resolve a repo-relative path and reject (via `realpath` comparison) anything that escapes the root — but this helper is used elsewhere in the app (`dispatcher.ts`, `app-store.ts`, `copilot-conflict-context.ts`), not in `diff.ts`. [2](#0-1) 

`getWorkingDirectoryImage` is only reachable via `getImageDiff`, which is only called from `convertDiff` when git reports `diff.isBinary === true` **and** the file extension is in the known image-extension allowlist: [3](#0-2) [4](#0-3) 

This gating matters for exploitability: a freshly-added tracked symlink (`AppFileStatusKind.New`/`Untracked`) has, from git's point of view, textual content (the symlink target string), so `git diff --no-index` will not classify it as binary, and the naive PoC described ("create a tracked symlink and view its diff image preview") will likely render as a **text** diff, not an image diff — `getWorkingDirectoryImage` would never be invoked in that exact scenario. A more contrived precondition — the path was previously committed as a real binary image (so the "old" side already contains NUL bytes and git's binary heuristic flags the pair as binary), and the working tree then has an *uncommitted* replacement of that path with a symlink to a sensitive host file (e.g. mid-merge/mid-conflict state where the file is "Modified" but not yet committed) — would satisfy `diff.isBinary` and route into `getImageDiff` → `getWorkingDirectoryImage`, at which point `readFile` would follow the symlink and disclose the arbitrary host file's bytes, base64-encoded and rendered as an `<img>` in the diff pane.

I could not fully verify from the indexed portion of the file (it was truncated) whether any earlier symlink/lstat check exists upstream of this call (e.g. in `status.ts` filtering symlinked entries before they reach `FileChange`), so this can't be ruled out with full certainty from what's indexed.

### Title
Symlink-following file read in working-directory image diff preview - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` joins the repository path with a git-reported file path and reads it via `fs.readFile` without validating that the resolved path stays inside the repository or that the entry isn't a symlink, unlike other file-path handling in the codebase which routes through `resolveWithin`.

### Finding Description
`getWorkingDirectoryImage(repository, file)` computes `Path.join(repository.path, file.path)` and calls `readFile` on it directly. `fs.readFile` follows OS-level symlinks, so if the working-tree entry at `file.path` is a symlink whose target resolves outside the repository, the bytes actually returned are those of the external target, not of anything inside the repo. Unlike `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` in `app/src/lib/path.ts`, which explicitly `realpath`-check that a resolved path stays under the repository root, no such check is applied here (or in the sibling `getResolutionDiff`, which has the same pattern).

### Impact Explanation
If reached, this discloses the content of an arbitrary file readable by the OS user running Desktop into the renderer as a base64 data URI rendered in the diff view — an out-of-repo file read, matching the "read outside the repo"/disclosure impact category.

### Likelihood Explanation
Likelihood is constrained by an upstream gate: `getImageDiff`/`getWorkingDirectoryImage` is only invoked when `convertDiff` determines `diff.isBinary === true` for that path. A plain newly-tracked symlink is textual content from git's diff-binary-detection perspective and would normally be rendered as a text diff, not routed to the image path. Triggering the vulnerable code path realistically requires a scenario where the *previously committed* content at that path was already binary/image-like (so git's binary detection still fires) while the working tree currently holds a symlink to the external target and the change is left uncommitted (e.g., during a multi-file merge/conflict that the user hasn't finished committing). This is a plausible but non-trivial precondition, not the simple "add a tracked symlink and view it" case suggested by the naive PoC.

### Recommendation
In `getWorkingDirectoryImage` (and `getResolutionDiff`'s equivalent `readFile` call), resolve the target path with `resolveWithin(repository.path, file.path)` (or `lstat` the entry first and reject symlinks / verify the resolved real path is inside `repository.path`) before reading file contents, mirroring the protection already used elsewhere in the codebase (`app/src/ui/dispatcher/dispatcher.ts`, `app/src/lib/stores/app-store.ts`).

### Proof of Concept
1. Repository has a committed binary PNG at `assets/logo.png` on the base branch.
2. Attacker's branch/PR replaces `assets/logo.png` with a symlink (mode `120000`) targeting an absolute sensitive path (e.g. `~/.ssh/id_rsa`), while also introducing a genuine conflicting change in another file to force the merge into an uncommitted, conflicted state.
3. Victim merges the branch in Desktop; the merge stops on the conflict, leaving `assets/logo.png` listed as a "Modified" change in the working directory (uncommitted).
4. Victim clicks the file in the Changes list to preview its diff; because the old (HEAD) blob is binary, `diff.isBinary` is true and the `.png` extension routes through `getImageDiff` → `getWorkingDirectoryImage`, whose `readFile(Path.join(repository.path, 'assets/logo.png'))` follows the on-disk symlink and returns the contents of `~/.ssh/id_rsa`, rendered as an image/base64 blob in the diff pane.

*Note: this precondition (pre-existing binary content at that path plus an uncommitted merge/conflict state) is required for `diff.isBinary` to be true; a bare new/untracked symlink alone will typically be treated as a text diff and will not reach `getWorkingDirectoryImage`.*

export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
