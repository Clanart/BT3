### Title
`clone()` explicitly disables Git's recursive-clone hook protection via `GIT_CLONE_PROTECTION_ACTIVE=false` - ([File: app/src/lib/git/clone.ts])

### Summary
Reducing the external report to its core primitive: an attacker-controlled input is processed through a path whose safety depends on a protection mechanism, and that protection is bypassed, letting the attacker corrupt state the victim didn't authorize. In the xsubmit() report the broken invariant was "in-order, non-reentrant execution of untrusted-triggered calls." The closest concrete Desktop analog is not a JS-level reentrancy bug, but an explicit disabling of Git's own anti-exploitation guard for recursive/submodule clones, which restores a known attacker-controlled code-execution primitive during `git clone --recursive`.

### Finding Description
`clone()` builds the environment for the clone operation and explicitly sets: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
args.push('-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive')
``` [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is an internal Git safety flag introduced to mitigate arbitrary-code-execution issues that occur when Git recurses into submodules during `clone --recursive` (the class of vulnerabilities fixed upstream around Git 2.45.x, e.g. GHSA/CVE fixes for hooks-path/hardlink confusion during recursive clone). Git itself sets this variable internally when it re-invokes itself for submodule recursion, to guard against a maliciously crafted repository/submodule tree tricking Git into treating an attacker-supplied directory as the top-level `.git` (and thus its `hooks` directory), which would let a hook shipped inside the cloned/submodule content execute automatically.

By force-setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every `clone --recursive` invocation, Desktop overrides/suppresses that upstream guard for all clones performed through the app, regardless of the bundled Git version's own judgement about when the protection is needed. This directly matches the "attacker controls a cloned/fetched repository" precondition in the Valid Impact list.

### Impact Explanation
If the bundled dugite/Git version relies on this environment variable being unset (or true/1) to activate its recursive-clone hook safety checks, forcing it to `'false'` reintroduces the exact vulnerability class the flag exists to prevent: a specially crafted public repository with a malicious submodule/hooks layout could achieve arbitrary code execution the moment an unsuspecting user clones it with GitHub Desktop (which always clones with `--recursive`, see the `args.push(... 'clone', '--recursive')` line). This satisfies the "code execution" impact bucket in the Valid Impact list and requires no local access, no admin rights, and no prior compromise — only that the victim clone an attacker-hosted repository through Desktop's normal UI flow.

### Likelihood Explanation
Every clone performed by Desktop goes through this single `clone()` function and always passes `--recursive`, so the override is unconditional and always in effect — there is no opt-out. The only variable is whether the specific dugite-bundled Git version's vulnerable code path is still reachable when this flag is forced false; this cannot be fully confirmed from the JS source alone since it depends on the internal C implementation of the vendored Git binary and its exact version, which is outside what the indexed source shows.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` (or set it to `'true'`/leave it unset) so Desktop does not suppress Git's own recursive-clone/submodule hook protections. If the override was added to work around a specific compatibility problem, that workaround should be re-validated against the bundled Git version and scoped as narrowly as possible (e.g., only for trusted/local clones), rather than applied unconditionally to every remote clone.

### Proof of Concept
1. Confirm the bundled dugite/Git version's release notes/source to determine whether `GIT_CLONE_PROTECTION_ACTIVE=false` reactivates the recursive-clone hook-execution bug (this step could not be completed from the indexed JS/TS sources alone).
2. If reachable, host a public repository containing a crafted submodule structure designed to place an executable hook where Git will invoke it during `git clone --recursive` when the protection is inactive.
3. Have a victim clone that repository through GitHub Desktop's "Clone repository" UI, which invokes `clone()` in `app/src/lib/git/clone.ts` with the vulnerable environment override, achieving code execution as the victim without any further user interaction beyond the clone.

**Uncertainty note:** I was not able to verify, from the indexed source alone, the exact bundled Git/dugite version or its C-level handling of `GIT_CLONE_PROTECTION_ACTIVE`, nor find commit history/PR context explaining why this override was added (the repository's history is squashed to a single "Initial commit"). Confirming actual exploitability requires testing against the specific vendored Git binary. If you want authoritative confirmation of impact, a Devin session with terminal access to build/run the bundled Git binary and attempt the crafted-submodule PoC would be needed.
