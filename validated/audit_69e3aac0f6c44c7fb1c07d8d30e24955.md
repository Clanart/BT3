### Title
Unbounded signature count in `SchnorrAggregate::read`/`verify` enables resource-exhaustion DoS from untrusted bytes - (File: crypto/schnorr/src/aggregate.rs)

### Summary

The bug class in the external report is "no limit on the number of elements in an attacker-controlled structure, causing disproportionate resource consumption in parsing/verification." Serai's aggregate Schnorr implementation has the same shape: `SchnorrAggregate::read` accepts a `u32` element count with no upper bound and then performs a full elliptic-curve point decompression per element, and `SchnorrAggregate::verify` subsequently performs a `weight()` transcript expansion plus a multiexponentiation term per element. A single attacker-controlled byte stream therefore drives attacker-chosen amounts of point decompression, transcript hashing, and multiexp work.

### Finding Description

`SchnorrAggregate::read` reads a 4-byte little-endian count and then loops `C::read_G(reader)` that many times with no sanity bound on the count [1](#0-0) . For curves such as `dalek-ff-group`'s Ristretto/ed25519 or `kp256`'s Secp256k1, each `read_G` performs a full point decompression (field inversion / square root / parity checks), which is one of the most expensive per-byte operations exposed by these crates. Then `SchnorrAggregate::verify` iterates every element, calling `weight::<_, C::F>(&mut digest)` — which runs a `DigestTranscript` challenge and reduces `F::NUM_BITS + 128` bits into a scalar via repeated u64 loads and doublings — and pushes two multiexp statements per element [2](#0-1) . The `weight` loop itself runs multiple challenge squeezes per signature [3](#0-2) .

Contrast with the rest of the codebase, which does bound attacker-controlled counts: `Commitments::read` in PedPoP allocates and reads exactly `params.t()` points [4](#0-3) , FROST's `Commitments::read` reads exactly `generators.len()` nonce tuples fixed by the algorithm [5](#0-4) , and the coordinator transaction format caps `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating. `SchnorrAggregate::read` has no equivalent cap: the count is `u32`, so up to ~4.3 billion point reads are attempted from whatever byte stream the caller supplies.

### Impact Explanation

Any code path that parses a `SchnorrAggregate` from untrusted bytes (the type is `pub` and `read`/`serialize`/`verify` are the public API) performs per-element point decompression, transcript challenges, and scalar wide-reduction proportional to an attacker-chosen `u32`. Even though each element consumes its encoded size from the reader, the per-byte cost is the most expensive primitive in the stack (point decompression + subsequent `weight()` derivation + multiexp per element in `verify`), letting a compact message pin CPU in decompression/verification loops and, via `vec![]` growth plus `Vec::with_capacity((2 * len) + 1)` in `verify`, drive memory allocation. This is a remote, unprivileged resource-exhaustion (denial of service) against any service deserializing/verifying attacker-supplied aggregate signatures — the same "single message forces disproportionate server/client work" class as the Mastodon poll-option advisory.

### Likelihood Explanation

Reachability requires a caller that feeds attacker-controlled bytes to `SchnorrAggregate::read`/`verify` without imposing its own size limit. The aggregate type exists to be transmitted between parties (it has `serialize`), so a P2P/RPC-delivered aggregate signature is the natural carrier. The parser itself does no rate-limiting, count capping, or cheap pre-check; the only defense is an external message-size cap, which the library neither enforces nor documents. Likelihood is therefore moderate: it depends on integrator transport limits, but the vulnerable primitive is reachable from a single public-input byte buffer.

### Recommendation

- Bound the element count in `SchnorrAggregate::read` (e.g., reject counts exceeding a sane maximum such as the maximum plausible signer/batch size) before entering the `read_G` loop.
- Have `read` take an explicit `expected: usize`/`max: usize` parameter so callers bind the count to the known number of signatures being verified, matching the `params.t()`/`generators.len()` pattern used in `crypto/dkg/pedpop/src/lib.rs` and `crypto/frost/src/nonce.rs`.
- In `verify`, reject early if `self.Rs.len()` (or `keys_and_challenges.len()`) exceeds the bound before allocating `Vec::with_capacity(2 * len + 1)` and running `weight()` per element.
- Document the maximum in the type's doc comment so integrators know framing is enforced by the library, not delegated to transport limits.

### Proof of Concept

Conceptual PoC against `SchnorrAggregate::read`/`verify` (e.g., over `Ristretto`):

```rust
// Attacker-serialized aggregate claiming u32::MAX elements.
let mut buf = Vec::new();
buf.extend_from_slice(&u32::MAX.to_le_bytes());
// Followed by as many valid point encodings as bandwidth allows.
// Each 32-byte encoding forces a full point decompression in read_G.
for _ in 0 .. 1_000_000 {
    buf.extend_from_slice(<Ristretto as Ciphersuite>::generator().to_bytes().as_ref());
}
// s
buf.extend_from_slice(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref());

let agg = SchnorrAggregate::<Ristretto>::read(&mut buf.as_slice()).unwrap();
// agg.Rs now holds 1M decompressed points (~each a sqrt + inversion).
// verify then derives a weight() per element and builds a 2M-term multiexp:
let keys_and_challenges: Vec<_> =
    (0 .. agg.Rs().len()).map(|_| (Ristretto::generator(), <Ristretto as Ciphersuite>::F::ONE)).collect();
let _ = agg.verify(b"dst", &keys_and_challenges);
```

Each attacker-supplied ~32-byte element triggers one point decompression on read, and on verify one transcript `weight()` derivation plus two multiexp terms — CPU work per input byte orders of magnitude above trivial parsing, with no upper bound enforced anywhere in `crypto/schnorr/src/aggregate.rs`.

fn weight<D: Send + Clone + SecureDigest, F: PrimeField>(digest: &mut DigestTranscript<D>) -> F {
  let mut bytes = digest.challenge(b"aggregation_weight");
  debug_assert_eq!(bytes.len() % 8, 0);
  // This should be guaranteed thanks to SecureDigest
  debug_assert!(bytes.len() >= 32);

  let mut res = F::ZERO;
  let mut i = 0;

  // Derive a scalar from enough bits of entropy that bias is < 2^128
  // This can't be const due to its usage of a generic
  // Also due to the usize::try_from, yet that could be replaced with an `as`
  #[allow(non_snake_case)]
  let BYTES: usize = usize::try_from((F::NUM_BITS + 128).div_ceil(8)).unwrap();

  let mut remaining = BYTES;

  // We load bits in as u64s
  const WORD_LEN_IN_BITS: usize = 64;
  const WORD_LEN_IN_BYTES: usize = WORD_LEN_IN_BITS / 8;

  let mut first = true;
  while i < remaining {
    // Shift over the already loaded bits
    if !first {
      for _ in 0 .. WORD_LEN_IN_BITS {
        res += res;
      }
    }
    first = false;

    // Add the next 64 bits
    res += F::from(u64::from_be_bytes(bytes[i .. (i + WORD_LEN_IN_BYTES)].try_into().unwrap()));
    i += WORD_LEN_IN_BYTES;

    // If we've exhausted this challenge, get another
    if i == bytes.len() {
      bytes = digest.challenge(b"aggregation_weight_continued");
      remaining -= i;
      i = 0;
    }
  }
  res
}

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
