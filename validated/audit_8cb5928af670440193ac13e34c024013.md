### Title
Malicious preprocess keyed under `Participant(0)` panics `AlgorithmSignMachine::sign` via `ThresholdKeys::view().unwrap()` — remotely triggerable DoS of a signer - (File: crypto/frost/src/sign.rs)

### Summary

`AlgorithmSignMachine::sign` validates the set of included participants before calling `self.params.keys.view(included.clone()).unwrap()`. The validation bounds the *maximum* index (`included[last] > n`) and rejects duplicates, but never rejects `Participant(0)`. Since `included` is sorted ascending, a `Participant(0)` contributed via a remote `Preprocess` message sits at `included[0]` and slips past both checks. `ThresholdKeys::view` rejects the invalid signing set by returning `None` (valid indexes are `1..=n`), and the unconditional `.unwrap()` panics, crashing the signing thread/process.

### Finding Description

In `crypto/frost/src/sign.rs` (`AlgorithmSignMachine::sign`):

```rust
included.sort_unstable();

// Included < threshold
if included.len() < usize::from(multisig_params.t()) { ... }
// OOB index
if u16::from(included[included.len() - 1]) > multisig_params.n() { ... }
// Same signer included multiple times
for i in 0 .. (included.len() - 1) {
  if included[i] == included[i + 1] { ... }
}

let view = self.params.keys.view(included.clone()).unwrap();
```

An unprivileged counterparty reaches this path by sending a `Preprocess` message (read via `read_preprocess` → `Commitments::read`) inserted into the `preprocesses` map under key `Participant(0)`. The checks only verify:

1. `included.len() >= t` — satisfied by including enough legitimate peers.
2. `included.last() <= n` — `Participant(0)` sorts to the front and is never the max.
3. No adjacent duplicates — `0` is unique.

Because `ThresholdKeys::view` only accepts participants `1..=n` and returns `Option::None` for an out-of-range index such as 0, the `unwrap()` on the result panics. This is a reachable panic on fully attacker-controlled input — the exact "low-privileged network attacker causes hang or repeatable crash" bug class of CVE-2021-2020.

### Impact Explanation

A single malformed preprocess message deterministically panics any FROST signer that incorporates it into a signing session. Repeating the message makes the crash repeatable and permanently prevents the victim from completing signatures — a complete denial of service of the signing node (and, since sessions abort, of the multisig's liveness) with no special privileges beyond the ability to deliver preprocess bytes to the signer, which every cothority/peer in the protocol has.

### Likelihood Explanation

Likelihood is high: the attacker only needs to participate in or relay into a signing session — the same trust level assumed for any non-threshold participant. The crash is deterministic (no race or probabilistic condition), requires a single 2-byte participant index of `0`, and bypasses every existing validation check because the bounds check examines only the largest sorted index.

### Recommendation

Add an explicit lower-bound check before `view()`:

```rust
if included[0].0 == 0 {
  Err(FrostError::InvalidParticipant(multisig_params.n(), included[0]))?;
}
```

or fold it into the existing OOB check. Additionally, replace `.unwrap()` with a propagated `FrostError::InternalError`/`InvalidSigningSet` so an invariant violation in `view` can never panic on remote input.
