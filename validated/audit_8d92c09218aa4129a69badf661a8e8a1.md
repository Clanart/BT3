## Title
Unbounded CLVM execution when parsing untrusted offers causes RPC-reachable DoS - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer._get_offered_coins()` and `Offer.get_cancellation_coins()` execute every coin-spend's (inner) puzzle with `cost_left = INFINITE_COST` instead of a bounded cost, exactly mirroring the Nibiru `TraceTx` bug class: an attacker-controlled, unbounded amount of user-supplied data is fed into unmetered CLVM execution on a path reachable by an ordinary local RPC caller (a wallet owner loading/inspecting an offer from an untrusted counterparty).

### Finding Description
`Offer.__post_init__` bounds most CLVM work to `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` when computing additions/hints [1](#0-0) . However `_get_offered_coins()`, which is invoked by `get_offered_coins()`/`get_offered_amounts()`/`summary()`/`to_valid_spend()`/`get_primary_coins()`, deliberately sets `cost_left = INFINITE_COST` and runs `inner_puzzle.run_with_cost(cost_left, inner_solution)` for every coin spend in the offer with no upper bound on total execution: [2](#0-1) .

Similarly, `get_cancellation_coins()` runs `run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)` per coin spend, again unbounded: [3](#0-2) .

These summary/validation helpers are reached directly from wallet RPC endpoints that accept an attacker/counterparty-supplied offer blob before any on-chain fee/cost is paid:
- `WalletRpcApi.get_offer_summary()` calls `request.parsed_offer.summary()` (and `get_dl_offer_summary`) [4](#0-3) .
- `WalletRpcApi.check_offer_validity()` / `take_offer()` parse and act on the same offer object [5](#0-4) .
- The CLI `take_offer` path also computes `offer.summary()` before any confirmation prompt [6](#0-5) .

An attacker can craft an `Offer` whose coin-spend puzzle reveals contain extremely expensive (but syntactically valid) CLVM programs — since `INFINITE_COST` removes the normal `MAX_BLOCK_COST_CLVM`/mempool cost ceiling that every other execution path in the codebase enforces (see `compute_additions_with_cost`, `Offer.conditions()`, mempool validation) [7](#0-6) [8](#0-7) . When the victim's wallet (via `get_offer_summary`, `check_offer_validity`, or `take_offer` RPC, or the CLI `take` command) parses that offer, it will run the malicious puzzle(s) to completion with no cost limit, tying up the wallet process.

### Impact Explanation
This is directly analogous to the reported `TraceTx` finding: an unprivileged caller (any offer counterparty, or anyone who can get a wallet operator to load an offer file/string) can force unbounded CLVM execution through a local RPC/CLI surface explicitly in scope ("offers and trades"). A sufficiently expensive puzzle reveal can hang or exhaust CPU/memory on the wallet service, denying service to the wallet RPC (and by extension any automation depending on it), without spending any fee or ever broadcasting a transaction.

### Likelihood Explanation
Likelihood is high for anyone who can produce or receive offer files, which is the normal, low-privilege wallet workflow (offer exchange between untrusted parties is a core supported feature). No signature, on-chain fee, or special permission is required to trigger the vulnerable code path — only an `Offer` object with a crafted puzzle reveal.

### Recommendation
Replace `INFINITE_COST` in `Offer._get_offered_coins()` and `Offer.get_cancellation_coins()` with a bounded cost (e.g., `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, consistent with `__post_init__` and `conditions()`), track remaining cost budget across the loop, and fail fast with a `ValidationError` (as already done elsewhere in the class) once the budget is exceeded. Consider adding an explicit wall-clock timeout around offer-parsing RPC endpoints (`get_offer_summary`, `check_offer_validity`, `take_offer`) as a defense-in-depth measure, mirroring the suggested `DefaultGethTraceTimeout` mitigation in the original report.

### Proof of Concept
1. Construct a `WalletSpendBundle` whose `coin_spends` include a settlement-payment-adjacent puzzle (matched by `match_puzzle`) whose *inner puzzle* is a CLVM program designed to consume massive cost (e.g., deeply nested/recursive quoted-list operations) while still returning syntactically valid conditions.
2. Wrap it into an `Offer` (`Offer.from_spend_bundle` / `Offer.to_bech32`) and send it to a victim wallet operator, or submit it via `get_offer_summary` RPC with `advanced=True` (bypassing the `get_dl_offer_summary` short-circuit) so `Offer.summary()` → `get_offered_amounts()` → `get_offered_coins()` → `_get_offered_coins()` is invoked [4](#0-3) .
3. Observe that `inner_puzzle.run_with_cost(INFINITE_COST, inner_solution)` [9](#0-8)  runs the crafted puzzle without any cost ceiling, consuming CPU for an attacker-chosen duration and blocking the wallet RPC service (single-threaded async loop) from serving other requests, achieving the same class of DoS described in the `TraceTx` finding.
