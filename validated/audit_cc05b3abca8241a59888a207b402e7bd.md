### Title
Unauthenticated `internal_get_emergency_stop_tx` leaks emergency-stop transaction commitments when `client_verification=false` - ([File: core/src/rpc/interceptors.rs])

### Summary
`only_aggregator_and_self` in `core/src/rpc/interceptors.rs` enforces that `Internal*`-prefixed gRPC methods (like `internal_get_emergency_stop_tx`) can only be called by a peer presenting the aggregator's own client certificate. However, this check is entirely bypassed when the deployment sets `client_verification=false`, in which case `Interceptors::Noop` is installed instead of `OnlyAggregatorAndSelf`, and `Noop::call` simply returns `Ok(req)` for every request with no certificate or identity check whatsoever.

### Finding Description
The binding the code intends to enforce is: `caller_of(internal_get_emergency_stop_tx) == self(aggregator's own client cert)`, implemented via `leaf_cert == our_cert` in `only_aggregator_and_self` [1](#0-0) .

This binding is only wired in when `config.client_verification == true`, at which point `create_grpc_server` builds `OnlyAggregatorAndSelf { aggregator_cert, our_cert }` and wraps the service in `InterceptedService` with TLS client-cert verification enabled via `ServerTlsConfig::new().identity(...).client_ca_root(...)` [2](#0-1) . If `client_verification` is `false`, the server is built with `Interceptors::Noop`, and TLS is configured with `ServerTlsConfig::new().identity(server_identity)` only (no client CA root, no client-cert requirement) [3](#0-2) . `Noop::call` performs no identity check at all: `Interceptors::Noop => Ok(req)` [4](#0-3) .

With `Noop` active, an unprivileged attacker can connect to the aggregator's public gRPC port without ever presenting a client certificate and invoke `internal_get_emergency_stop_tx` with an arbitrary list of `txids` (e.g., move-to-vault txids enumerated from the Bitcoin blockchain), and the aggregator will build and return `encrypted_emergency_stop_txs` for every requested deposit, since there is no per-request authorization check inside `internal_get_emergency_stop_tx` itself — the only gate was the interceptor, which is a no-op in this configuration.

### Impact Explanation
This premature disclosure of the emergency-stop transaction (a security-council-controlled recovery/kill-switch path) to an unauthenticated, unprivileged party before its intended reveal matches the "premature disclosure of a protocol commitment" High-severity category. It does not by itself move BTC or forge a signature — the response is described as "encrypted" emergency-stop transactions, and whether that encryption meaningfully protects the payload before an authorized council trigger determines the realistic follow-on risk (front-running/racing the legitimate emergency-stop broadcast). This is repeatable for every deposit/move-txid the attacker can enumerate on-chain, so the blast radius scales with the number of active deposits.

### Likelihood Explanation
The precondition is that the deployment runs with `client_verification=false` on the aggregator — this is an explicit, attacker-uncontrollable operator/deployment configuration choice, not a universal default guaranteed by the code. If a deployment enables `client_verification=true` (which is presumably the recommended/production configuration, and the code even logs a warning `"Client verification is enabled on aggregator gRPC server"` when it is on [5](#0-4) ), the `OnlyAggregatorAndSelf` interceptor fully blocks this call for any peer not holding the aggregator's own private key. The attack costs nothing beyond scanning the Bitcoin blockchain for move-to-vault txids and sending a plaintext/TLS-without-client-auth gRPC request — trivial and repeatable if the precondition holds.

### Recommendation
Do not rely solely on deployment configuration (`client_verification`) to gate `Internal*` methods; enforce that "Internal"-prefixed methods (including `internal_get_emergency_stop_tx`) always require self-authentication regardless of `Noop`/`client_verification` setting, or reject `Internal*` calls entirely when `client_verification=false` rather than silently allowing them through.
