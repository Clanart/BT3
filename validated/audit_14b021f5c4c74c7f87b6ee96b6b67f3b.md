## Analysis

The dhowden/tag dependency itself is not used in this codebase [1](#0-0) , so the analog must be found by mapping the underlying bug class — **out-of-bounds slice/index access on unvalidated, attacker-supplied byte data, causing a panic** — to a reachable Kaia code path.

I found exactly this pattern in the auction bid signature verification helper.

### Title
Auction bid signature verification panics on short `SearcherSig`/`AuctioneerSig` due to missing length check before slice indexing - (File: `kaiax/auction/bid.go`)

### Summary
`getSigner`, used by `Bid.ValidateSearcherSig` and `Bid.ValidateAuctioneerSig`, indexes into the caller-supplied signature byte slice (`copiedSig[crypto.RecoveryIDOffset]`, `copiedSig[0:32]`, `copiedSig[32:64]`) without first checking that the slice is the required 65-byte length. A `Bid` (containing `SearcherSig`/`AuctioneerSig`) is attacker-controlled data submitted by an unprivileged auction bidder/searcher, so a short or empty signature field causes an unrecovered `index out of range` panic.

### Finding Description
`BidData.SearcherSig` and `BidData.AuctioneerSig` are plain `[]byte` fields decoded directly from a submitted bid (via RLP `DecodeRLP`) [2](#0-1) . When validating a bid, `ValidateSearcherSig`/`ValidateAuctioneerSig` pass these fields straight to `getSigner`: [3](#0-2) 

`getSigner` clones the raw signature and immediately indexes `copiedSig[crypto.RecoveryIDOffset]` (index 64), then slices `copiedSig[0:32]` and `copiedSig[32:64]` — all before any length validation. Unlike other signature-handling call sites in the codebase, which check `len(sig) != crypto.SignatureLength` first (e.g. `api/api_personal.go` `EcRecover` [4](#0-3)  and `api/api_kaia_transaction.go` `RecoverFromMessage` [5](#0-4) ), `getSigner` performs no such check. Any `SearcherSig`/`AuctioneerSig` shorter than 65 bytes (including empty/nil) triggers a Go runtime `slice bounds out of range` or `index out of range` panic — the exact bug class described in the dhowden/tag advisory (improper bounds checking on parsing of user-supplied input leading to panic).

### Impact Explanation
This function is on the path that validates bids submitted by unprivileged auction searchers/bidders, one of the explicitly in-scope actors. An attacker can submit a `Bid` with a truncated `SearcherSig` or `AuctioneerSig` (e.g., 0–64 bytes) to trigger a panic during bid validation. If this panic is not recovered somewhere up the call stack in the node/mempool bid-processing pipeline, it crashes the node process handling the bid — a denial-of-service against any node (validator, RPC endpoint, or auction processor) that validates bids, satisfying the CWE-129/CVSS "Availability: High" characterization of the original advisory.

### Likelihood Explanation
Likelihood is high for any code path that constructs/deserializes a `Bid` from external input and calls `ValidateSearcherSig`/`ValidateAuctioneerSig`: no signature-length precondition exists anywhere before the vulnerable indexing, and RLP decoding of `BidData.SearcherSig` (a plain `[]byte`) accepts arbitrary lengths. I was not able to fully trace, within the tool-call budget, the exact caller that first receives an externally submitted bid (e.g. a `submitBid`-style RPC handler) and confirm whether a top-level `recover()` wraps that specific call; this should be verified before finalizing severity, as a `recover()` wrapper elsewhere could downgrade this from crash to error.

### Recommendation
Add an explicit length check (`len(sig) != crypto.SignatureLength`) at the start of `getSigner` in `kaiax/auction/bid.go`, returning `ErrInvalidSignature` (or similar) instead of proceeding to slice/index the raw bytes, mirroring the pattern already used in `api/api_personal.go` and `api/api_kaia_transaction.go`.

### Proof of Concept
1. Construct a `Bid`/`BidData` with `SearcherSig` set to a short byte slice, e.g. `[]byte{}` or `[]byte{0x01, 0x02}`.
2. Submit/decode this bid so that `ValidateSearcherSig` (or `ValidateAuctioneerSig` with a short `AuctioneerSig`) is invoked.
3. Execution reaches `getSigner(b.SearcherSig, digest)` at `kaiax/auction/bid.go:142`, where `copiedSig[crypto.RecoveryIDOffset]` (or the subsequent `copiedSig[0:32]`/`copiedSig[32:64]`) indexes past the end of the short slice, causing an unrecovered runtime panic.

**Uncertainty**: I could not confirm within the available searches (a) the exact public entry point (RPC method or bundle/bid gossip handler) that first constructs a `Bid` from unprivileged input and calls into `ValidateSearcherSig`/`ValidateAuctioneerSig`, and (b) whether a `recover()` exists somewhere in that call chain that would catch this panic before it crashes the process. These should be confirmed to establish the precise blast radius (single-request DoS vs. full node crash).

func getSigner(sig, digest []byte) (common.Address, error) {
	// Manually convert V from 27/28 to 0/1
	copiedSig := slices.Clone(sig)
	if copiedSig[crypto.RecoveryIDOffset] == 27 || copiedSig[crypto.RecoveryIDOffset] == 28 {
		copiedSig[crypto.RecoveryIDOffset] -= 27
	}

	v := copiedSig[crypto.RecoveryIDOffset]
	r := new(big.Int).SetBytes(copiedSig[0:32])
	s := new(big.Int).SetBytes(copiedSig[32:64])
	if !crypto.ValidateSignatureValues(v, r, s, true) {
		return common.Address{}, ErrInvalidSignature
	}
