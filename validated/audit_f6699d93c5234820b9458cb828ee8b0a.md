### Title
Missing zero-check on high-order coefficients in `RecoverPolynomialCoefficients` allows over-degree data to be silently mis-recovered - (`internal/erasure_code/erasure_code.go`)

### Summary
`RecoverPolynomialCoefficients` computes the exact interpolating quotient polynomial `Q(x)` from the supplied cell data and then truncates it to `dr.numScalarsInDataWord` coefficients without ever checking that the discarded, higher-order coefficients are zero. When a caller supplies more cells than the minimum required for reconstruction (i.e., more than half of `CellsPerExtBlob`), and the supplied cell values do not correspond to evaluations of a true degree`<numScalarsInDataWord` polynomial, the truncation discards non-zero terms of `Q(x)`, causing the returned "recovered" polynomial to no longer interpolate the attacker's own supplied cell values at the corresponding `cellIDs[i]`.

### Finding Description
The broken equality is: for every supplied `cellIDs[i]`, `recovered[cellIDs[i]] == cells[i]` (i.e., re-evaluating the returned polynomial at the supplied cell positions must reproduce the caller's input) and the recovered polynomial must have degree `< ScalarsPerBlob` (`numScalarsInDataWord`).

The code path is `Context.RecoverCellsAndComputeKZGProofs` → `ctx.recoverPolynomialCoeffs` (api_eip7594.go:97-146) → `ctx.dataRecovery.RecoverPolynomialCoefficients` (internal/erasure_code/erasure_code.go:110-148). The function:
1. Builds a vanishing polynomial `zX` whose roots are exactly the *missing* cell positions [1](#0-0) 
2. Computes `D(x)`, the unique degree`<N` interpolant of `data[i]*zX_eval[i]` over the full extended domain [2](#0-1) 
3. Recovers `Q(x) = D(x)/zX(x)` via a coset-FFT trick — this quotient exactly matches the supplied `data[i]` at every *present* index, regardless of whether the data is an evaluation of a true low-degree polynomial, because `D(i) = data(i)*zX(i)` and `zX(i) ≠ 0` at present points, so `Q(i) = data(i)` always holds [3](#0-2) 
4. Truncates `Q(x)` to the first `numScalarsInDataWord` coefficients and returns it, with **no check that the higher coefficients are zero**: [4](#0-3) 

`Q(x)` is mathematically guaranteed to have degree `< N - deg(zX)`, where `deg(zX)` equals the number of missing indices. When the caller supplies exactly the minimum number of cells (`NumBlocksNeededToReconstruct()`), `deg(zX) = N - numScalarsInDataWord`, so `deg(Q) < numScalarsInDataWord` is forced by the math and the truncation is lossless. However, `recoverPolynomialCoeffs` only enforces a **lower bound** on the number of supplied cells, not an exact count: [5](#0-4) . This means an attacker can supply **more** cells than the minimum (up to all `CellsPerExtBlob`, i.e., zero missing indices), shrinking `deg(zX)` and thereby allowing `deg(Q)` to exceed `numScalarsInDataWord`. If the attacker crafts cell values that are not evaluations of a true degree`<numScalarsInDataWord` polynomial, the higher-order coefficients of `Q` become non-zero and are silently dropped by the truncation on line 146, producing a "recovered" polynomial whose forward-evaluation (via `computeCellsFromPolyCoeff`/`computeKZGProofsFromPolyCoeff`) no longer matches the attacker's own supplied cells at `cellIDs[i]`.

None of the existing guards catch this: `isAscending`, the `cellID < CellsPerExtBlob` check, and `NumBlocksNeededToReconstruct()` (a lower bound only) all pass; there is no code path that re-evaluates the truncated polynomial at the supplied cell indices and compares against the input, nor any check that `cosetQuotientEval[dr.numScalarsInDataWord:]` are all zero before discarding them.

### Impact Explanation
This causes the library to accept a "recovery" request and emit cells/proofs derived from a polynomial that is inconsistent with the very cells the caller supplied — a divergence from the semantics of `recover_cells_and_kzg_proofs` as specified (which the consensus-spec test vectors, e.g. `recover_cells_and_kzg_proofs_case_valid_no_missing`, encode as the "no missing" case where the recovered output must equal input exactly). Reference implementations (c-kzg / consensus-specs) that additionally verify degree/consistency, or that reject "no erasure but not a low-degree word" inputs by other means, would diverge from go-eth-kzg's silent truncation, producing a client split: one implementation accepts and emits cells/proofs for such input while another rejects it or emits different data for the same call. This matches the "High" severity category — a disagreement between this library and the spec/c-kzg on accepted input and emitted commitment/proof/cell/recovered data.

### Likelihood Explanation
Preconditions: the attacker needs to call `RecoverCellsAndComputeKZGProofs` (or `RecoverCells`) with `cellIDs` covering more cells than the strict minimum (`NumBlocksNeededToReconstruct()`), ideally the full complement of 128 cells with zero missing indices, and craft `cells` values whose underlying "polynomial" (as if degree `< numScalarsInDataWord`) is not actually of that degree. This requires no special privileges — any caller of the public API can supply arbitrary cell byte content (each cell simply deserializes to field elements via `deserializeCell`), and the attack is fully repeatable and deterministic per call, at negligible cost (a single API call).

### Recommendation
After computing `cosetQuotientEval`, explicitly verify that all coefficients at index `>= dr.numScalarsInDataWord` are zero (or equivalently, re-evaluate the truncated polynomial at all supplied `cellIDs` and compare against the caller-supplied `cells`) before returning success; return an error such as `ErrPolynomialNotDegreeCompliant` otherwise. This restores the invariant that `recovered[cellIDs[i]] == cells[i]` for all supplied indices and that the recovered polynomial has degree `< ScalarsPerBlob`.
