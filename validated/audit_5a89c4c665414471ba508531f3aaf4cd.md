### Title
Gasless swap users are exposed to sandwich-style value extraction via stale, mempool-visible `minAmountOut` and guaranteed KIP-249 back-run placement - (File: `kaiax/gasless/impl/tx_pool.go`)

### Summary
The Kaia gasless-swap flow (KIP-247) validates a user's `swapForGas` transaction (`token`, `amountIn`, `minAmountOut`, `amountRepay`, `deadline`) against the AMM's *current* spot price at tx-pool admission time only, while the actual swap is executed later during block building, after a proposer-generated `LendTx` is prepended and after any other transactions the proposer/searcher chooses to place earlier in the same block. Because `minAmountOut` is a fixed, publicly visible value (broadcast in the tx pool, and also submitted in the clear via the `auction_submitBid` RPC as `targetTxRaw`), and because the KIP-249 auction module gives a winning bidder a *protocol-guaranteed* transaction slot immediately after any chosen target transaction, an attacker (or the block-producing proposer itself) can move the AMM pool price against the victim just enough that the swap still clears the fixed `minAmountOut` floor on-chain, extracting the difference as MEV — the same "manipulate spot price around a fixed-boundary transaction" pattern described in the AeraVaultV1 sandwich report, but here the victim's boundary check is enforced against a stale price rather than a real-time invariant.

### Finding Description
`GaslessModule.checkBalanceForSwap` performs the *only* protocol-level admission check on a gasless swap: [1](#0-0) 

This uses `routerContract.GetAmountIn(nil, token, minAmountOut)` — i.e. the **current on-chain reserves at the moment of tx-pool validation** — to confirm the user supplied enough `amountIn` for their declared `minAmountOut`. It does not re-verify this relationship at the time the transaction is actually included and executed in a block. The user-supplied `minAmountOut` only needs to satisfy `minAmountOut >= amountRepay` (the amount owed back to the proposer for lending gas): [2](#0-1) 

`SwapArgs`/`decodeSwapTx` show that `minAmountOut` is a plain, unencrypted parameter of the swap calldata, fully visible to anyone observing the transaction: [3](#0-2) [4](#0-3) 

The transaction (and its exact swap parameters) is also disclosed in full via the auction RPC, since `auction_submitBid` decodes and forwards `targetTxRaw` before adding the bid: [5](#0-4) 

The KIP-249 auction module then guarantees the highest bidder a transaction slot immediately following any target transaction of their choosing — including a victim's gasless swap — by construction of the bundle in `ExtractTxBundles`: [6](#0-5) 

Because block assembly is entirely controlled by the proposer/builder (who also decides bundle ordering via `IncorporateBundleTx`/`coordinateTargetTxHash`), nothing prevents inserting an attacker-controlled swap on the same underlying AMM pool immediately *before* the victim's gasless swap in the same block, shifting the pool's spot price unfavorably, and then using the KIP-249 auction slot (or simple ordering control) to back-run and capture the arbitrage — the classic front-run/victim-tx/back-run sandwich pattern, except here the "boundary check" being circumvented is the user's `minAmountOut`, which was computed against a stale, pre-attack price and is only checked against the *current* reserves at pool-admission time, not at execution time inside the eventual block.

### Impact Explanation
Gasless-swap users repay lent gas fees out of the swap's proceeds (`lendAmount`/`repayAmount` in `kaiax/gasless/impl/getter.go:346-367`). A successfully sandwiched swap still satisfies `minAmountOut >= amountRepay` (the repay floor), so the transaction does not revert and the user still repays the proposer — but the user's net token/KAIA proceeds beyond the repay amount can be reduced toward zero, with the difference captured by the attacker. This is a concrete value-extraction/settlement-theft vector against KIP-247 gasless users, amplified by the KIP-249 auction module's built-in guaranteed back-run mechanism, which effectively hands attackers a protocol-native sandwich primitive with no additional infrastructure needed.

### Likelihood Explanation
Likelihood is high in an adversarial mempool/auction environment: any observer of the public mempool, or any auctioneer-relayed `targetTxRaw` submitted via `auction_submitBid`, can see the exact `token`, `amountIn`, and `minAmountOut` of a pending gasless swap before it lands on-chain, and can win the KIP-249 auction for that target transaction hash to guarantee adjacent placement, or simply rely on general block-builder MEV extraction since bundle placement is proposer-controlled. No special node privilege, validator collusion, or peer-manipulation is required — only a normal transaction sender/bidder interacting with public RPC and the standard auction flow, which is within the allowed threat surface.

### Recommendation
- Tighten the on-chain/off-chain relationship between `minAmountOut` and execution-time pricing: require a shorter, block-scoped `deadline`, and/or add an execution-time re-check inside `swapForGas` (or in `checkBalanceForSwap`) that rejects swaps if the effective price has moved beyond a bounded tolerance since the tx-pool admission check, rather than relying solely on the user's static `minAmountOut`.
- Consider preventing arbitrary third-party trades against the same pool from being placed immediately before a pending gasless swap within the same block (e.g., via same-block ordering constraints or price-impact caps enforced by `GaslessSwapRouter`).
- For the auction module, consider whether allowing a bidder to target *any* transaction hash (including third-party gasless swaps unrelated to their own bid) for guaranteed back-run placement should be restricted, or at least require disclosure/limits when the target is a KIP-247 gasless transaction, to reduce the built-in sandwich primitive.
- Document and monitor for `minAmountOut` values that are only marginally above `amountRepay`, since such swaps have effectively zero slippage protection margin and are maximally exploitable.

### Proof of Concept
1. Attacker monitors the public mempool (or receives `targetTxRaw` via `auction_submitBid`) and observes a pending `GaslessSwapTx` calling `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` where `minAmountOut` is only slightly above `amountRepay` (see `checkBalanceForSwap`, `kaiax/gasless/impl/tx_pool.go:115-120`).
2. Attacker submits their own swap on the same underlying AMM pool ahead of the victim's swap in the same block (via normal fee/priority ordering, or by becoming the block proposer/builder), shifting the pool's spot price unfavorably to the victim.
3. The victim's `GaslessSwapTx` executes; because on-chain admission only checked `amountIn >= gsr.GetAmountIn(token, minAmountOut)` against the pre-attack reserves (`kaiax/gasless/impl/tx_pool.go:128-141`), and the contract-level check only needs `minAmountOut` to be met at execution (not the pre-attack rate), the swap still succeeds but yields output just above `amountRepay`, leaving the user with reduced (or none) of the surplus they expected.
4. Attacker back-runs with a reverse swap to restore the pool price and realize the arbitrage profit; alternatively, attacker wins the KIP-249 auction for the victim's swap tx hash (`kaiax/auction/impl/builder.go:29-70`) to guarantee this back-run transaction is placed immediately after the victim's swap.
5. Net effect: attacker captures the price-impact spread that should have gone to the gasless-swap user, using only public mempool/tx-pool/RPC access — no special node role required.

Note: The Solidity source of `GaslessSwapRouter` (only Go bindings for its ABI were found in the index) was not available to fully confirm whether the on-chain `swapForGas` implementation adds any additional execution-time price-staleness protection beyond what the tx-pool's `checkBalanceForSwap` enforces off-chain. If a Devin session with full repository access can inspect the actual `GaslessSwapRouter.sol` implementation, this should be verified to confirm the precise on-chain guarantees.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}

var _ kaiax.TxBundlingModule = (*AuctionModule)(nil)

func (a *AuctionModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	bundles := []*builder.Bundle{}
	curBlock := a.Chain.CurrentBlock()
	if curBlock == nil || atomic.LoadUint32(&a.bidPool.running) == 0 {
		return bundles
	}

	miningBlock := curBlock.NumberU64() + 1
	bidTargetMap := a.bidPool.GetTargetTxMap(miningBlock)
	if len(bidTargetMap) == 0 {
		return bundles
	}

	for _, tx := range txs {
		txHash := tx.Hash()
		bid, ok := bidTargetMap[txHash]
		if !ok {
			continue
		}
		b := builder.NewBundle(
			builder.NewTxOrGenList(a.GetBidTxGenerator(tx, bid)),
			txHash,
			true,
		)

		isConflict := false
		for _, prev := range append(prevBundles, bundles...) {
			if prev.IsConflict(b) {
				isConflict = true
				break
			}
		}
		if isConflict {
			continue
		}
		bundles = append(bundles, b)
	}

	return bundles
}
