## Finding confirmed [1](#0-0) 

The `!_lock` branch of `getRewardAmount` is the crux: for `_mode != 2` ("stake" mode) deposits, the reward is computed as `_amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR` with **no** `calDoubledCounted` subtraction at all, unlike the `_lock == true` branch which does subtract it.

`getUserTier` and `calDoubledCounted` both derive tier/baseline purely from `mWomSV.getUserTotalLocked(_account)` [2](#0-1) , and `mWomSV` is a shared, permissionless `ILocker` that can be populated entirely outside `ArbWomUp3` — e.g. via `SmartWomConvert.convert(..., _mode=2)` / `smartConvert`, which calls `mWomSV.lockFor(obtainedmWomAmount, _for)` directly for any caller [3](#0-2) . ### Title
Uncapped full-amount reward multiplication using externally-inherited mWomSV tier in ArbWomUp3.getRewardAmount's stake branch - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount`'s non-lock ("stake", `_mode==1`) branch multiplies the entire freshly deposited `_amountToConvert` by `rewardMultiplier[getUserTier(_account)]`, where `getUserTier` reads `mWomSV.getUserTotalLocked(_account)` — a balance that can be built up entirely outside ArbWomUp3 via `SmartWomConvert`'s permissionless `lockFor` calls. Unlike the lock branch, this branch never calls `calDoubledCounted`, so there is no deduction for the fact that the tier-qualifying balance was never routed through ArbWomUp3's own accounting.

### Finding Description
`incentiveDeposit` computes `_lock = (_mode == 2)` and calls `getRewardAmount(_amount, msg.sender, _lock)` [4](#0-3) . For `_mode == 1` (stake), `_lock` is `false`, so:
```
mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
```
with no baseline subtraction [5](#0-4) . `getUserTier` looks purely at `mWomSV.getUserTotalLocked(_account)` [6](#0-5) , a value coming from a shared `ILocker` (`mWomSV`) that any unprivileged user can populate directly via `SmartWomConvert._convertFor` mode 2 (`mWomSV.lockFor(obtainedmWomAmount, _for)`), completely bypassing `ArbWomUp3` [3](#0-2) . Meanwhile, `_deposit` for `_mode == 1` merely deposits WOM into `mWom` and stakes it via `smartWomConvert.depositFor`, which does not touch `mWomSV` at all [7](#0-6) . Thus the tier used to price the "stake" reward is completely decoupled from the deposit that reward is paid for, and it is never decremented for the externally-sourced balance. An attacker can:
1. Lock enough mWom into `mWomSV` through `SmartWomConvert` (mode 2) to reach the top `rewardTier` bracket — a real cost, but unrelated to and reusable across other Magpie products, and not "spent" against this specific ARB/WOM-up campaign.
2. Repeatedly call `incentiveDeposit(_amount, _ratio, false, 1)` — each call multiplies the *entire* fresh `_amount` by the top-tier multiplier, capped only by `IERC20(mgp).balanceOf(address(this))`.

This is qualitatively different from the marginal (`F(accumulated) - F(existing)`) computation used correctly in the `_lock == true` branch, which is at least bounded to the newly-added units. Here the multiplier applies to the full stake amount on every call, so it can be repeated to drain the whole MGP reward reserve.

### Impact Explanation
Direct theft of unclaimed MGP yield reserved for this program: an attacker who never contributed WOM/tier-qualifying deposits through `ArbWomUp3` can drain `mgp` balance from the contract at the highest reward multiplier for arbitrary "stake" deposits, exhausting funds intended for legitimate `ArbWomUp3` participants. This matches the "theft of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
Fully reachable by any unprivileged EOA: `SmartWomConvert.convert`/`smartConvert` with `_mode == 2` are public and permissionless, and `incentiveDeposit` has no restriction requiring the tier balance to originate from this contract. The only "cost" is acquiring/locking mWom in `mWomSV`, which is a normal, permissionless product action, not gated in any way — and it is reusable capital (still owned/locked by the attacker, benefiting from other mWomSV-linked rewards too), so the marginal cost of the exploit is low relative to the repeatable extraction from `ArbWomUp3`'s finite `mgp` reserve.

### Recommendation
In the `!_lock` branch of `getRewardAmount`, do not use the shared `mWomSV.getUserTotalLocked` balance as the tier baseline for rewards on deposits unrelated to that lock. Track ArbWomUp3-specific cumulative WOM routed through this contract (as `ArbWomUp2` does with `userWOMDeposited`), and apply the same marginal `F(accumulated) - F(existing)` / `calDoubledCounted` logic consistently to both the stake and lock branches, so tier credit is always backed by WOM actually processed by this contract.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
