### Title
Unbounded `n` in `ThresholdKeys::read` enables quadratic-CPU deserialization DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `u16` participant count `n` with no sanity bound, then deserializes `n` scalars and `n` group elements and constructs `ThresholdKeys::new`, which computes the group key via `interpolation_factor` — an O(t) loop invoked once per participant — yielding O(t²) field arithmetic plus `n` point decompressions. This is the Serai analog of the reported "unbounded whitelist loop → gas exhaustion/DoS" bug: an attacker-sized list drives unbounded victim compute.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the stream (lines 591–602), then loops `0 .. n` for `Interpolation::Constant` coefficients (lines 607–613) and `1 ..= n` reading a `read_G` per participant (lines 620–623). `n` is a `u16`, so an attacker can declare up to 65,535 participants. The real amplification lands in `ThresholdKeys::new`: it builds `t = 1..=t` and computes `group_key` as a sum over `verification_shares[i] * interpolation_factor(*i, &t)` (lines 376–378). `interpolation_factor` (lines 226–249) iterates over the whole `included`/`t` slice performing a scalar multiply per element — for both `Constant` (single index) and `Lagrange` (num/denom product over all `t` shares) paths, the Lagrange path being O(t) per call. Result: O(t²) scalar operations — ≈4.3×10⁹ multiplications for `t = 65535` — plus 65,535 point decompressions via `read_G`, all triggered by ~4 MB of serialized input. [1](#0-0) [2](#0-1) [3](#0-2) 

The same quadratic pattern repeats in `ThresholdKeys::view`, which calls `interpolation_factor` once per `included` signer (lines 500–507), though `included` there is locally constructed. The reachable public-input path is `ThresholdKeys::read`.

### Impact Explanation
An unprivileged party supplying crafted bytes to `ThresholdKeys::read` (key-import/restore path, or any context where serialized threshold keys cross a trust boundary) forces the victim to burn seconds-to-minutes of CPU on O(t²) interpolation and tens of thousands of point decompressions, stalling signing/verification work — a remote resource-exhaustion DoS directly mirroring the reported `buyPosition` gas-exhaustion vector, where a growable, unbounded list drives victim cost. Unlike `SchnorrAggregate::read` (linear in bytes supplied), this offers ~65,535× amplification of declared-count over honest work.

### Likelihood Explanation
Medium: exploitation requires only delivering ~4 MB of well-formed serialized bytes (each of the `n` shares must deserialize, i.e., valid scalar/point encodings — trivially generated identity/random encodings suffice since `read_F`/`read_G` accept them and `ThresholdKeys::new` only checks counts and index bounds, not share correctness). No key material or privileged position is needed wherever `ThresholdKeys::read` is reachable on untrusted input.

### Recommendation
Enforce a protocol-level maximum on `n` before allocating/looping in `read` (e.g., reject `n` exceeding a documented `MAX_PARTICIPANTS`), matching the report's recommendation to bound list size. Additionally, derive `t`/`n` consistency checks before interpolation and consider computing `group_key` without per-participant O(t) factors (e.g., a single multiexp with precomputed coefficients).

### Proof of Concept
```rust
// Serialize a ThresholdKeys blob with t = n = 65535, i = 1,
// Interpolation::Constant(0), then n valid F reprs and n valid G encodings.
// Feeding it to ThresholdKeys::<C>::read triggers:
//   - 65,535 read_F + 65,535 read_G (point decompression each)
//   - ThresholdKeys::new: 65,535 calls to interpolation_factor,
//     each O(t) -> ~4.3e9 field multiplications for the group_key sum.
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&65535u16.to_le_bytes()); // t
buf.extend(&65535u16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(0);                         // Interpolation::Constant
for _ in 0 .. 65535 { buf.extend(<C::F as PrimeField>::ONE.to_repr().as_ref()); }
buf.extend(<C::F as PrimeField>::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. 65535 { buf.extend(C::generator().to_bytes().as_ref()); }
let _keys = ThresholdKeys::<C>::read(&mut &buf[..]); // quadratic CPU burn
```
Note `ThresholdKeys::new` will still reject (t/n bounds, missing participants) only *after* the expensive reads/interpolation; with `t = n`, Constant interpolation is permitted and the full O(t²) group-key computation executes before any later failure.
