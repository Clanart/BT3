### Title
Payout transaction's operator-attribution OP_RETURN is unauthenticated and malleable via `SIGHASH_SINGLE|ANYONECANPAY`, allowing reimbursement credit to be stripped from the honest fronting operator - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction with the user's withdrawal signature covering only the input being spent and the output at the same index (user payout, output index 0), consistent with the `SinglePlusAnyoneCanPay` sighash type used throughout the withdrawal flow. The anchor output (index 1) and, critically, the OP_RETURN output carrying the fronting operator's x-only pubkey (index 2) are *not* covered by that signature. This OP_RETURN value is the sole mechanism used later to attribute "who fronted this payout" for reimbursement purposes (`update_finalized_payouts`, `is_kickoff_malicious`, `validate_payer_is_operator`). Because the signature does not bind these outputs, any party that observes the unconfirmed payout transaction (or the raw signature) can rebuild a transaction with the same input/output-0 pair but a different (or missing) OP_RETURN attribution and different fee-funding input, and get it confirmed instead - breaking the binding "operator credited == operator that actually funded the payout."

### Finding Description
`create_payout_txhandler` at `core/src/builder/transaction/operator_reimburse.rs:407-436` constructs:
- input 0: the user's presigned withdrawal UTXO, spent via `SpendPath::KeySpend` with `user_sig`
- output 0: the user's payout
- output 1: a non-ephemeral anchor (`NON_EPHEMERAL_ANCHOR_AMOUNT`)
- output 2: an OP_RETURN containing `operator_xonly_pk`, i.e. whichever operator called `withdraw()` with their own key [1](#0-0) 

The witness for input 0 is set from `user_sig`, a taproot signature that (per the withdrawal flow's documented and enforced `SinglePlusAnyoneCanPay` sighash type) commits only to input 0 and output 0. [2](#0-1) 

Downstream, the protocol relies entirely on this OP_RETURN value to attribute the payout to a specific operator for reimbursement:
- `update_finalized_payouts` parses the OP_RETURN from the *mined* payout tx and stores it as `payout_payer_operator_xonly_pk` in the DB. [3](#0-2) 
- `is_kickoff_malicious` requires the kickoff's `operator_xonly_pk` to match this stored payer pubkey, or else the kickoff is treated as malicious. [4](#0-3) 
- `validate_payer_is_operator` requires the calling operator's own key to equal the stored payer pubkey before it will proceed with reimbursement-related flows. [5](#0-4) 
- `send_asserts` hard-errors if no payer operator pubkey is recorded for the move txid. [6](#0-5) 

Because the OP_RETURN and anchor outputs are outside the signature's commitment, an unprivileged third party who sees the unconfirmed payout transaction (e.g. in the mempool, or via any leak of the raw `user_sig`) can construct an alternative transaction that:
- spends the same input 0 with the same `user_sig` (still valid, since ANYONECANPAY/SINGLE only pin input 0/output 0),
- keeps the identical output 0 (so the user still receives the correct payout - this is not a fund-theft attack against the user),
- but substitutes output 2 with an arbitrary or absent OP_RETURN, and substitutes/adds its own fee-paying input/anchor,

and gets this variant confirmed instead of the original operator's broadcast (via RBF/fee outbidding or a race in propagation, since both spend the same coin). Only one of the two competing transactions can ultimately be mined (single-spend), so this is not a duplication of reimbursement, but it does break the "operator credited == operator that paid" binding: the operator whose fee-funded transaction was replaced/out-raced never gets recorded as the payer, permanently losing the ability to claim reimbursement for a withdrawal it fronted (`send_asserts` will fail; `validate_payer_is_operator` will reject any of its future reimbursement attempts, since `payer_xonly_pk` in DB is now `None` or someone else's key).

### Impact Explanation
This maps to the report's core custody binding - "the operator credited versus the party that paid" - but in the reverse direction: an honest operator that actually fronts BTC to the withdrawing user via the payout transaction can be denied its reimbursement credit because the attribution mechanism (OP_RETURN) is not cryptographically bound to the transaction that actually gets confirmed. Per the rules this constitutes "an honest operator permanently unable to be reimbursed" - a Critical-severity impact, since `send_asserts`/`validate_payer_is_operator` will permanently reject that operator's reimbursement path for the affected withdrawal once a different payout tx (with different/no OP_RETURN attribution) confirms.

### Likelihood Explanation
Exploitation requires an unprivileged party to observe the unconfirmed operator payout transaction (mempool visibility, or knowledge of the raw `user_sig`/UTXO once it is broadcast) and win a fee/propagation race by rebuilding a variant with a different OP_RETURN/anchor/fee-input before the original confirms. This is feasible for any network participant monitoring the mempool with sufficient fee-bumping capability, and does not require any privileged role (verifier, operator, watchtower, aggregator). It is a signature-malleability class issue rooted in the choice of `SIGHASH_SINGLE|ANYONECANPAY` for the user's withdrawal authorization, which by design leaves all outputs after index 0 and all additional inputs unauthenticated.

### Recommendation
Bind the operator-attribution OP_RETURN (and ideally the anchor output) to the signed commitment, e.g. by having the aggregator/verifiers co-sign a specific full payout transaction template (input, output 0, and OP_RETURN pinned together) rather than relying on a mutable/unauthenticated third output, or by moving payer attribution off-chain into a database record created by the operator's RPC call *before* broadcast, with the chain-observed transaction only used as confirmation of payment to output 0 rather than as the sole source of payer identity.

### Proof of Concept
Not applicable/executable from static analysis alone; the exploit is a mempool-level transaction-malleability race (fee-bump replace) requiring live network conditions to demonstrate the final confirmation outcome. This aspect (whether Bitcoin Core's RBF/mempool policy or the `TxSender`'s CPFP/RBF logic in `crates/clementine-tx-sender/src/{cpfp,rbf}.rs` fully prevents third-party replacement in practice) could not be fully verified with the available read-only tooling and would benefit from a live regtest reproduction by a Devin session with repository and node access.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
