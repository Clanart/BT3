## Finding [1](#0-0) 

`revealInFileManager()` builds the target path with a plain `Path.join(repository.path, path)` and calls `shell.showItemInFolder()` directly — it performs **no containment check** at all, despite the doc comment two lines above the underlying `showItemInFolder` explicitly warning "Do not use this method with non-validated paths." Compare this to the guarded pattern used elsewhere in the codebase, `resolveWithin()`, which normalizes, resolves, and `realpath`-verifies that the result stays under the root before it is used [2](#0-1) . That helper is consistently applied for other externally‑sourced paths, e.g. deep‑link `filepath` handling in the dispatcher [3](#0-2)  and Copilot conflict‑resolution paths [4](#0-3) , but it is **not** used in `revealInFileManager`.

`revealInFileManager` is invoked with `path` values that come from `CommittedFileChange`/PR file lists, i.e. attacker‑influenced GitHub API objects, from the "Reveal in Finder/Explorer" context menu in `pull-request-files-changed.tsx` (imports `revealInFileManager` and wires it to `CommittedFileChange.path`) [5](#0-4) , and similarly from the changes/history views (`sidebar.tsx`, `selected-commits.tsx`, `filter-changes-list.tsx`, `repository.tsx`) which all call the same unguarded `showItemInFolder`/`revealInFileManager` primitive.

## Impact Explanation

Because the diff/PR file-path strings are parsed from diff text (numstat/diff headers) rather than validated against real git tree entries, an attacker who controls the PR diff/file listing (a GitHub API object) can supply a path containing `../` segments. `Path.join()` will happily collapse such a path into a location outside the repository, and since there is no `resolveWithin`/`realpath` check, `shell.showItemInFolder` will open the OS file manager pointed at (or preselecting) a file anywhere on the user's disk — e.g. `../../../../../.ssh`. This is a path‑traversal read/disclosure primitive: it doesn't write bytes, but it discloses the existence/location of sensitive files and opens a native file-manager window scoped to an attacker-chosen absolute path, which is a real containment violation of "stay inside the repo" that the rest of the codebase (path.ts guard, its own doc comment, and existing tests in `path-test.ts`) explicitly designed to prevent for exactly this class of API.

## Likelihood Explanation

Moderate. It requires no local access, no credentials, and no unusual user step beyond a normal one — right-clicking a file in the "Files changed" pane of an untrusted pull request and selecting "Reveal in Finder/Explorer," which is a completely ordinary Desktop workflow when reviewing a PR from a fork. The main uncertainty (not fully verified from index alone) is whether the diff parser / GitHub API deserialization for PR file paths strips `..` segments before they reach `CommittedFileChange.path`; I was not able to locate an explicit sanitization step for this specific field in the parts of the diff parser/PR file model I could inspect.

## Recommendation

Route `path` in `revealInFileManager` (and any other call site that receives repository-relative paths derived from PR/diff data) through `resolveWithin(repository.path, path)` before calling `shell.showItemInFolder`, mirroring the pattern already used in `dispatcher.ts` for deep-link `filepath` handling and in `app-store.ts` for Copilot conflict resolutions. Reject (`log.error` + no-op) when the resolved value is `null`.

## Proof of Concept

1. Open (or preview) a pull request from an untrusted fork whose diff includes a crafted file entry, e.g. a diff hunk with header `+++ b/../../../../../../.ssh/id_rsa` (feasible if the diff/PR file list rendering path is derived from raw diff text rather than a validated git tree entry).
2. In "Files changed," right-click that entry and choose "Reveal in Finder"/"Show in Explorer."
3. `revealInFileManager(repository, '../../../../../../.ssh/id_rsa')` computes `Path.join(repository.path, '../../../../../../.ssh/id_rsa')`, which resolves outside the repository, and `shell.showItemInFolder` opens the file manager at that external location — with no `resolveWithin` guard rejecting it, unlike every other untrusted-path code path in the app.

**Caveat**: I could not confirm from the indexed code whether upstream diff/PR-file parsing already strips `..`/absolute segments before `CommittedFileChange.path` is populated; if such sanitization exists elsewhere, this reduces to a defense-in-depth gap rather than an exploitable bug. Given the size limits on the index, a full trace of the diff-parsing pipeline for PR file lists may need to be done in a Devin session with full repo access.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
