### Title
Debt-to-USD normalization rounds down instead of up, understating a borrower's debt in health/LTV checks - (File: `mainnet/contracts/utility/v0-1-data.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Analogous to Notional's `convertFromStorage()` bug — where a negative `storedCashBalance` (debt) is converted using `.div()` which truncates toward zero instead of rounding up, understating what the debtor owes — Zest's debt-to-USD conversion for LTV/health computations uses `mul-div-down`/`normalize(..., round-up: false)` when it should round up so any dust rounds in the protocol's favor.

### Finding Description
`sum-debt-usd` in `mainnet/contracts/utility/v0-1-data.clar` computes `actual` scaled debt via `mul-div-down` and then divides by `(pow u10 decimals)` using plain integer division (rounding down) when accumulating `debt-usd`: [1](#0-0) 

This `debt-usd` feeds directly into `current-ltv` and `health-factor` computed with `mul-div-down`: [2](#0-1) 

Similarly, `find-and-resolve-asset-value` / `get-asset-value` in `v0-4-market.clar`, used to resolve debt value from token amount to USD via `normalize`, take an explicit `round-up` parameter but callers in the liquidation and health paths pass `false` for debt valuation (`process-debt-asset`): [3](#0-2) 

Rounding debt USD value down (instead of up) means the computed debt is silently smaller than the true debt, which is the same directional error as the Notional finding: for debt-side conversions, rounding toward the borrower loses value for the protocol.

### Impact Explanation
Because `debt-usd` is rounded down, `current-ltv` and `health-factor` are computed slightly favorable to the borrower — a position that is truly at or slightly above the liquidation threshold can be reported as marginally healthier than it is. This is a dust-level rounding bias that accumulates across many positions/blocks, systematically favoring borrowers at the protocol's expense, consistent with Notional's classification (loss of "dust" amounts, potentially accumulative). It does not, on its own, constitute a large single-shot theft, so it best matches a temporary/low-severity value leakage rather than a Critical insolvency event.

### Likelihood Explanation
This triggers on every single debt valuation used for LTV/health/liquidation eligibility checks, i.e., extremely high likelihood of occurring, but the magnitude per instance is limited to integer-division dust (bounded by 1 unit of the smallest USD precision per computation).

### Recommendation
Use round-up division for the debt side of every USD conversion feeding into health/LTV/liquidation math (analogous to Notional's fix): change `sum-debt-usd`, `build-debt-entry`, and `process-debt-asset`'s `debt-usd` computation to round up (`mul-div-up` / `normalize(..., round-up: true)`), while keeping collateral-side conversions rounded down, so that any dust always favors the protocol rather than the borrower.

### Proof of Concept
Given `actual = scaled * borrow-index / INDEX_PRECISION` computed with `mul-div-down`, and then `debt-usd += (actual * price) / 10^decimals` also truncated down: for `actual = 999999999999999999`, `price = 1`, `decimals = 18`, the true fractional value truncates to a strictly lower integer than the borrower's real obligation, repeated across every position and every accrual, causing systematic under-reporting of `debt-usd` used in the health-factor / LTV gate. (define-private (sum-debt-usd (entry { aid: uint, scaled: uint }) (acc uint))
  (let ((aid (get aid entry))
        (scaled (get scaled entry))
        (asset-data (unwrap-panic (contract-call? .v0-assets get-status aid)))
        (decimals (get decimals asset-data))
        (borrow-index (get-vault-borrow-index aid))
        (actual (mul-div-down scaled borrow-index INDEX-PRECISION))
        (price (get-asset-price aid)))
