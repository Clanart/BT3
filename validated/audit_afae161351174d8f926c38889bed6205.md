### Title
ThresholdKeys serialization writes the FROST secret share unencrypted, so any party who can read the serialized bytes recovers the secret share - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::write` / `ThresholdKeys::serialize` emit the FROST secret share (`secret_share`) as a raw canonical field-element encoding, with no encryption or access control, alongside public data (params, interpolation, verification shares). This mirrors CVE-2026-57302's class: a credential-equivalent secret persisted in cleartext, recoverable in full by anyone able to read the serialized blob — a strictly weaker privilege than participating in signing, analogous to Jenkins "Extended Read"/filesystem-read permission on `config.xml`.

### Finding Description
`ThresholdCore` holds `secret_share: Zeroizing<C::F>` (crypto/dkg/src/lib.rs:263). `ThresholdKeys::write` serializes it verbatim:

```rust
let mut share_bytes = self.core.secret_share.to_repr();
writer.write_all(share_bytes.as_ref())?;
share_bytes.as_mut().zeroize();
```

(crypto/dkg/src/lib.rs:553-555). `serialize()` produces the same plaintext `Vec<u8>` (lib.rs:567-571). `Zeroizing` only scrubs the in-memory buffer; the bytes written out are the raw scalar. `ThresholdKeys::read` (lib.rs:574-632) then reconstructs a fully usable `ThresholdKeys` from those bytes — it re-derives `group_key` from the verification shares via `ThresholdKeys::new` (lib.rs:376-378) but stores the attacker-readable `secret_share` unchanged. There is no MAC, encryption, or even a doc warning that the output is secret-bearing; the doc comment only notes the scalar/offset are excluded (lib.rs:535-537).

Contrast with `EncryptedMessage`/`SecretShare` handling in PedPoP, where shares in transit are ECDH-encrypted per recipient (crypto/dkg/pedpop/src/encryption.rs:95-167) — the at-rest serialization path has no equivalent protection.

### Impact Explanation
Whoever obtains the serialized `ThresholdKeys` blob obtains the participant's complete secret share. Combined with the threshold structure, t such blobs yield full group-key (private key) recovery — i.e., direct key-share recovery, one of the accepted impact classes. It also enables a single leaked share to be used to sign within any coalition the attacker can assemble, and since `view()` interpolates from `secret_share` (lib.rs:494-498), a recovered share functions identically to the live key material.

### Likelihood Explanation
Serialization is the documented, supported persistence mechanism for key shares produced by the DKG (`BlameMachine::complete` → `ThresholdKeys`). Shares are long-lived secrets; persisting them via `write`/`serialize` is the natural usage. Any lower-privileged reader of the storage medium — backups, logs, another process/user on the host, a copied buffer — obtains the secret without ever participating in or observing the DKG/signing protocols. No active attack on the cryptography is required; the exposure exists purely because the secret is stored in cleartext, exactly matching the CVE's low-privilege-read precondition.

### Recommendation
Encrypt the serialized form under a storage key (e.g., AEAD keyed by a node-held secret), or split `write` into a public portion and a separately-encrypted secret portion so callers cannot accidentally persist `secret_share` in cleartext. At minimum, rename/document the API so the plaintext-secret-bearing nature is unmistakable, and avoid round-tripping raw shares through byte buffers the way `ThresholdKeys::read`/`write` currently encourage.

### Proof of Concept
```rust
// Owner side: persist keys
let keys: ThresholdKeys<Ristretto> = /* result of PedPoP DKG */;
let blob = keys.serialize(); // plaintext
std::fs::write("keys.bin", &*blob).unwrap();

// Low-privilege reader side: no protocol participation needed
let blob = std::fs::read("keys.bin").unwrap();
let recovered = ThresholdKeys::<Ristretto>::read(&mut blob.as_slice()).unwrap();
// recovered.original_secret_share() == keys.original_secret_share()
assert_eq!(recovered.original_secret_share().to_repr(),
           keys.original_secret_share().to_repr());
// recovered can produce valid FROST signature shares via view()/AlgorithmMachine
```
