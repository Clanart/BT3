### Title
Unbounded atom length-prefix read in `is_atom_canonical` causes an unhandled `IndexError` during spend-bundle admission - (File: `chia/full_node/mempool_manager.py`)

### Summary
The ALPINE-CVE-2017-7960 report describes `cr_input_new_from_uri` reading past a heap buffer because it trusted an attacker-controlled length field in a crafted CSS file without validating it against the actual remaining input size. `chia/full_node/mempool_manager.py`'s `is_atom_canonical()`/`is_clvm_canonical()` has the same bug-class root cause: it walks a length-prefixed CLVM atom encoding using the length-prefix byte count decoded from untrusted, attacker-supplied bytes, and reads that many following bytes from the buffer with `clvm_buffer[offset]` **without ever checking that `offset` stays within `len(clvm_buffer)`**.

### Finding Description
`is_atom_canonical()` decodes a CLVM atom header whose leading byte determines how many additional length-prefix bytes follow (`prefix_len` 0–5): [1](#0-0) 

The loop `for i in range(prefix_len): ... offset += 1; atom_len |= clvm_buffer[offset]` blindly indexes into `clvm_buffer` for `prefix_len` more bytes with no length check against `len(clvm_buffer)`. Contrast this with the sibling parser in `chia/full_node/full_block_utils.py`, where every length-prefixed field (`skip_bytes`, `skip_list`, the generator-buffer/refs parsing) explicitly checks `if n > len(buf): raise ValueError(...)` before consuming bytes: [2](#0-1) [3](#0-2) 

`is_clvm_canonical()` is called directly with attacker-supplied bytes on every coin spend in a submitted spend bundle, before any other bounds/format validation of that specific atom occurs: [4](#0-3) 
that call sits inside `MempoolManager.validate_spend_bundle()`, which is on the mempool admission path for any spend bundle a remote peer or wallet RPC submits (`add_spend_bundle` → `validate_spend_bundle`).

A crafted `puzzle_reveal` or `solution` whose final atom starts a multi-byte length prefix (e.g. byte `0xF8`, which declares 4 additional prefix bytes) but is truncated before those bytes exist causes `clvm_buffer[offset]` to index past the end of the bytes object. In CPython this raises `IndexError`, i.e., the read is safely bounds-checked by the interpreter and does not corrupt memory — but the C analog is the same defect class: a length field taken from untrusted input is used to walk further into a buffer than the buffer's own declared/available size, with no explicit bound check performed by the vulnerable code itself.

### Impact Explanation
Because `is_clvm_canonical()` is invoked unconditionally on every `coin_spend.puzzle_reveal` and `coin_spend.solution` in `validate_spend_bundle()` before the surrounding code appears to guard for that specific exception type, a single malformed/truncated puzzle-reveal or solution submitted in a spend bundle can raise an unhandled `IndexError` mid-admission. This is a spend-triggered halt of mempool transaction-processing for that call path (denial of service against admission of that bundle, and potentially the calling task, depending on what wraps `validate_spend_bundle()` higher up the call stack). This does not, on its own, produce a memory-safety exploit in Python, but is the direct code-pattern analog of the reported CVE's missing bounds validation on an attacker-controlled length field before it is used to read further bytes.

### Likelihood Explanation
High reachability: any unprivileged spend-bundle submitter can trigger this by including a puzzle reveal or solution CLVM blob whose trailing bytes end mid-way through a multi-byte atom length prefix. No signature or special privileges are required to reach `validate_spend_bundle()`'s canonical-CLVM check, since it runs before signature/condition semantics are otherwise consulted for that atom.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` mirroring the pattern already used in `chia/full_node/full_block_utils.py`: before indexing `clvm_buffer[offset]` in the length-prefix loop (and before the initial `clvm_buffer[offset]` read in `is_clvm_canonical()`'s main loop), verify `offset < len(clvm_buffer)` and raise/return a controlled `False`/error instead of allowing the raw index to run off the end of the buffer. Ensure callers of `is_clvm_canonical()` treat any decoding failure (including out-of-range atom headers) as "not canonical"/`INVALID_COIN_SOLUTION` rather than letting an exception propagate uncaught.

### Proof of Concept
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xF8 declares a 4-byte-prefix atom (prefix_len=4), but the buffer
# contains only this single byte - is_atom_canonical() will index
# clvm_buffer[1] on a 1-byte buffer.
truncated_atom = bytes([0xF8])
is_clvm_canonical(truncated_atom)  # raises IndexError instead of returning False
```
Submitting a `CoinSpend` whose `puzzle_reveal` or `solution` ends with such a truncated multi-byte atom header inside a `SpendBundle` reaches `MempoolManager.validate_spend_bundle()`'s `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` / `is_clvm_canonical(bytes(coin_spend.solution))` call and triggers the same unhandled exception during mempool admission.

*Note: I was unable to fully verify, within the available iterations, whether an outer `try/except` around `validate_spend_bundle()`'s caller (e.g. `add_spend_bundle()`) catches generic exceptions and gracefully converts them to a mempool rejection error rather than propagating/crashing the processing task. This would affect whether the ultimate impact is a per-bundle rejection (low severity) versus a broader processing halt. A background Devin session with full repository access should confirm the exact exception-handling wrapper around `MempoolManager.validate_spend_bundle()` and `add_spend_bundle()` to determine the precise blast radius.*

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
```
