### Title
`Commitments::read`/`SchnorrSignature::read` accept the identity element, letting a PedPoP participant bypass proof-of-possession and inject null/cancelling commitments - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The upstream bug class is a required-authentication check that is "enabled" but configured with a truthy-but-wrong value (`cert_reqs = True` instead of `ssl.CERT_REQUIRED`), so verification silently becomes permissive. The direct analog in Serai: the identity-rejection requirement exists in `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131), but `Commitments::read` in PedPoP and `SchnorrSignature::read` call `Ciphersuite::read_G`, which only enforces canonical encoding and accepts the identity point (crypto/ciphersuite/src/lib.rs:91-101). The strict variant exists but the permissive one is used — the same "required check option set to the wrong constant" shape.

### Finding Description
`Commitments::read` reads `params.t()` generator points via `C::read_G` (crypto/dkg/pedpop/src/lib.rs:115-127) and then reads the proof-of-possession signature via `SchnorrSignature::read` (crypto/schnorr/src/lib.rs:51-53). Both paths accept the identity element:

- `Ciphersuite::read_G` only checks canonical encoding (`point.to_bytes() == encoding`), not `is_identity` — the identity check lives solely in `frost::curve::Curve::read_G`, which PedPoP cannot use because it is generic over `Ciphersuite`, not `Curve`.
- `SchnorrSignature::read` therefore accepts `R = identity`, and `SchnorrSignature::verify` computes `R + c·A − s·G == 0` via `multiexp_vartime` (crypto/schnorr/src/lib.rs:88-110). With `R = identity`, `s = 0`, and a key `A = identity`, the equation reduces to `0 == 0` and the proof of possession verifies for *any* challenge.

An untrusted party feeding bytes to `Commitments::read` (an explicitly in-scope read API) can therefore submit `t` identity commitments together with the trivially-valid signature `(R = identity, s = 0)`. The PoP signature binds to the commitments via `challenge(context, l, R, Am)` (crypto/dkg/pedpop/src/lib.rs:86-94), but because the verification equation degenerates, the challenge value is irrelevant — the "required" authentication of the commitments is bypassed exactly as in the advisory.

Additionally, because identity commitments correspond to a contribution of zero/known coefficients, and PedPoP never rejects identity or duplicate commitment sets (the doc-comment at pedpop/src/lib.rs:98-101 explicitly leaves duplicate detection to the caller), a malicious participant in an asynchronous round — who sees honest commitments `C_i` before broadcasting — can publish commitments `C_mal = −Σ C_i` (or identity after observing), cancelling the honest contributions and biasing the resulting `group_key` toward a value whose discrete log they know.

### Impact Explanation
Forged proof of possession: the Schnorr PoP in `Commitments` is the only thing proving the sender knows the discrete logs underlying their commitments; with `R = identity, s = 0` it verifies unconditionally when the summed commitment point is identity, granting a forged proof. Concretely this enables a rogue-commitment/cancellation attack on the DKG: the attacker forces the final `group_key` to a known or attacker-influenced value, defeating the purpose of the distributed key generation — equivalent in effect to recovering the group's signing capability. Reachable entirely by untrusted bytes supplied to `Commitments::read` by any peer in the DKG round; no valid key share or collusion required for the PoP forgery.

### Likelihood Explanation
Requires the attacker to be a registered participant index in the DKG session (or to have their bytes routed into a victim's `Commitments::read`), and to observe honest commitments before broadcasting — standard in asynchronous networks. The PoP bypass itself is deterministic: `identity + c·identity − 0·G = 0` always holds. Severity is bounded by the fact that a threshold of honest participants still contributes entropy, so full key control requires the attacker to be the *last* contributor influencing the sum, i.e., a Medium/High practical severity rather than unconditional key recovery.

### Recommendation
Reject the identity element wherever `Ciphersuite::read_G` is used on adversary-supplied points in PedPoP: in `Commitments::read` check `point.is_identity()` after decoding, and in `SchnorrSignature::read` (or at the PedPoP call site) reject `R.is_identity()`. Equivalently, make PedPoP generic over `frost::curve::Curve` so the strict `Curve::read_G` is used. Also reject duplicate/`is_identity` aggregate commitments when summing each participant's commitment vector.

### Proof of Concept

// Attacker crafts Commitments bytes:
//   t × identity point encodings  ||  R = identity  ||  s = 0
let t = params.t();
let mut buf = Vec::new();
for _ in 0..t {
    buf.extend(<C as Ciphersuite>::G::identity().to_bytes()); // canonical identity
}
buf.extend(<C as Ciphersuite>::G::identity().to_bytes()); // sig.R = identity
buf.extend(<C as Ciphersuite>::F::ZERO.to_repr());          // sig.s = 0

let comms = Commitments::<C>::read(&mut buf.as_slice(), params).unwrap();
// Commitments::read accepts: Ciphersuite::read_G only checks canonical encoding

// multiexp_vartime returns identity ⇒ SchnorrSignature::verify returns true

Key contrast: the same bytes passed through `frost::curve::Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) are rejected with `"identity point"` — proving the strict requirement exists but the permissive option was selected, mirroring `cert_reqs = True` vs `ssl.CERT_REQUIRED`.
