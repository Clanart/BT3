### Title
Hookify `RuleEngine._extract_field` inconsistently normalizes tool-input fields across Edit/Write/MultiEdit, letting a block rule be silently bypassed - (`plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` maps generic condition fields (`new_text`, `old_text`, `content`) to the actual keys present in `tool_input`, but the mapping is incomplete and inconsistent across the three tools that the plugin's own documentation says share the same `file` event (`Edit`, `Write`, `MultiEdit`). As a result, a block rule written against `new_text` or `old_text`—which correctly denies a dangerous `Edit`—silently fails to extract any value (or extracts an empty string) when the logically equivalent operation is performed via `Write` or `MultiEdit`, so the same protected content change goes through undetected.

### Finding Description
`_rule_matches` → `_check_condition` → `_extract_field` is the enforcement chain: if `_extract_field` returns `None` (or an empty string that fails the pattern), the condition is treated as not matched and the rule is silently skipped, even though the rule's `tool_matcher`/`event: file` was intended to cover it [1](#0-0) .

The field-mapping logic has two concrete gaps:

1. **`Write` + `new_text`/`new_string`**: `tool_input` for `Write` only contains `file_path` and `content` (no `new_string` key), yet the code does `tool_input.get('new_string', '')`, which always returns `''` for `Write` regardless of what was actually written [2](#0-1) . A block rule such as `field: new_text, operator: contains, pattern: API_KEY` matches an `Edit` call but is bypassed if the same content is introduced via `Write`.

2. **`MultiEdit` + `old_text`/`old_string`**: the `MultiEdit` branch only handles `file_path` and `new_text`/`content` (concatenating each edit's `new_string`); it never inspects `old_string`, and `old_string` is not a top-level `tool_input` key for `MultiEdit` (it's nested inside the `edits` list), so the earlier direct-field check (`if field in tool_input`) also misses it. The function falls through and returns `None` [3](#0-2) [4](#0-3) . A block rule guarding against removal of security-critical code (`field: old_text, operator: contains, pattern: SECURITY_CHECK`) that correctly denies an `Edit` is completely inert against the same removal performed via `MultiEdit`.

The plugin's own skill documentation tells rule authors that `event: file` uniformly covers "Edit, Write, MultiEdit tools" and that the available field options are `file_path`, `new_text`, `old_text`, `content` [5](#0-4) [6](#0-5) , so a reasonably-configured rule using these fields is expected to reliably deny the operation across all three tools, but the implementation does not honor that for two of the three.

Both `PreToolUse` and `PostToolUse` hooks route `Edit`, `Write`, and `MultiEdit` to the same `event='file'` rule set and the same `RuleEngine.evaluate_rules` call [7](#0-6) , so any content that reaches Claude (e.g., via prompt injection from an untrusted file, PR, or tool result) that steers the agent to prefer `Write` or `MultiEdit` over `Edit` for a specific dangerous change will silently evade a block rule that the operator believed applied uniformly.

### Impact Explanation
This is a security-control bypass: a `hookify` block rule intended to deny dangerous file mutations (e.g., stripping a security check, writing secrets, injecting `eval(`) can be routed around merely by using a different but functionally-equivalent tool call (`Write` instead of `Edit`, or `MultiEdit` instead of `Edit`), with no error or warning surfaced—`evaluate_rules` returns `{}` (allow) as if no rule existed [8](#0-7) . This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries," since the user/operator has no indication their protection rule failed to fire.

### Likelihood Explanation
No special privilege is required. The condition is: (1) an operator has configured a hookify `event: file` block rule using `new_text` or `old_text` fields as documented, and (2) the tool-choosing agent (potentially influenced by content the agent reads, such as prompt-injected instructions in a repository/PR) performs the equivalent edit via `Write` or `MultiEdit` instead of `Edit`. Both tools are ordinary, frequently-used Claude Code tools, and the bypass is fully deterministic and reproducible given the same rule and differing tool choice.

### Recommendation
In `_extract_field`, normalize `new_text`/`new_string` for `Write` to fall back to `content` (mirroring the existing `content` field's `or` fallback), and extend the `MultiEdit` branch to aggregate `old_string` across all `edits` for `old_text`/`old_string` fields, so that `new_text`/`old_text`/`content` extraction is consistent across `Edit`, `Write`, and `MultiEdit` as documented. Add regression tests asserting identical block outcomes for equivalent `Edit`, `Write`, and `MultiEdit` payloads.

### Proof of Concept
Unit test against `RuleEngine`:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-remove-security-check", enabled=True, event="file", action="block",
    tool_matcher="Edit|MultiEdit",
    conditions=[Condition(field="old_text", operator="contains", pattern="SECURITY_CHECK")],
    message="Blocked removal of security check"
)
engine = RuleEngine()

# Case 1: Edit tool -> correctly blocked
edit_input = {"tool_name": "Edit", "tool_input": {
    "file_path": "app.py", "old_string": "# SECURITY_CHECK\nverify()", "new_string": ""}}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Case 2: MultiEdit tool performing the identical removal -> NOT blocked (bypass)
multiedit_input = {"tool_name": "MultiEdit", "tool_input": {
    "file_path": "app.py",
    "edits": [{"old_string": "# SECURITY_CHECK\nverify()", "new_string": ""}]}}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}  # demonstrates the bypass: dangerous edit is silently allowed
```
Expected (fixed) behavior: both cases should yield a `deny`/block response; the current code yields `{}` for the `MultiEdit` case, confirming the bypass.
