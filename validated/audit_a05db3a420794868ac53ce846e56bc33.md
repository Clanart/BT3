## Analysis



The GitHub API-driven auto-rewrite of a repository's `origin` remote URL is a strong analog: it lets an untrusted/attacker-influenced API response silently redirect where Desktop pushes and fetches code, with insufficient validation of the new value.

### Title
Silent Remote URL Hijack via Unvalidated GitHub API `clone_url` in `updateRemoteUrl` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`repositoryWithRefreshedGitHubRepository` refreshes a repository's associated GitHub metadata by calling `api.fetchRepository(owner, name)` and then feeds the resulting `apiRepo.clone_url` into `updateRemoteUrl`, which can silently overwrite the local `origin` remote URL via `gitStore.setRemoteURL` — with no check that the new URL's hostname is the same trusted host the user originally configured. [1](#0-0) 

### Finding Description
`updateRemoteUrl` decides whether to overwrite the local remote based on three conditions: protocol equality, whether the *previous* remote still matched the *previously cached* `gitHubRepository.cloneURL`, and whether the new API `clone_url` differs from the current remote. None of these conditions verify that the new `clone_url`'s **hostname** matches a trusted/expected host (e.g., the account's configured endpoint host) — they only compare owner/name/hostname structurally against the *old* cached value, not against an allow-list of trusted hosts. [2](#0-1) 

Once these loose conditions are met, the app calls `gitStore.setRemoteURL`, which shells out to `git remote set-url` and persists the new URL without any user confirmation dialog. [3](#0-2) [4](#0-3) 

This refresh path is invoked automatically and silently on ordinary user actions — selecting a repository and on account changes — not just on explicit user request: [5](#0-4) [6](#0-5) 

The broken invariant: Desktop trusts the `clone_url` field of a GitHub API repository object as sufficiently validated simply because it corresponds to the same `owner/name` pair the user already had linked, without pinning it to the same host. If the API response comes from an attacker-controlled or on-path-compromised source (e.g., a malicious/compromised GitHub Enterprise Server endpoint the user has added an account for, or a spoofed response due to a compromised/misconfigured endpoint), the attacker can set `clone_url` to an arbitrary host with a different hostname while keeping the same owner/name and protocol, and Desktop will rewrite the trusted `origin` remote to that attacker host without any prompt.

### Impact Explanation
Once `origin` is silently repointed to an attacker-controlled host, all subsequent Desktop-initiated `git push`/`git fetch`/`git pull` operations for that repository target the attacker's server instead of the user's real remote. This satisfies "silent corruption of what the user commits or pushes" — the user believes they are pushing to their real repository (the UI still shows the same repository name/owner), but their code (potentially including secrets in the diff) is sent to a server the attacker controls, and any code fetched back (e.g., via `git pull`) can be attacker-supplied without the user's awareness, since the origin change happens without any visible confirmation step.

### Likelihood Explanation
This requires the user to have configured an account against an attacker-influenced GitHub API endpoint (e.g., a malicious/compromised on-prem GitHub Enterprise Server, or a network position capable of tampering with API responses to a configured endpoint) — it does not require local/physical access, admin rights, leaked credentials, or unnatural user steps; simply selecting the repository in the normal course of use triggers the refresh path. The likelihood is bounded by the need for such an endpoint/response to be attacker-influenced, which is a realistic threat model for enterprise/self-hosted Git endpoints supported by Desktop.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, additionally verify that the new `clone_url`'s hostname matches the hostname of the account's configured endpoint (or the existing remote's hostname) — reject/prompt instead of silently rewriting when the hostname differs. Consider surfacing a confirmation dialog to the user whenever the remote URL host changes, similar to other security-relevant remote changes.

### Proof of Concept
1. User has an account configured against a GitHub Enterprise endpoint (or the endpoint is later compromised/spoofed via an on-path attacker).
2. User opens/selects a repository they previously cloned from `https://ghe.example.com/org/repo.git`; this triggers `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`. [5](#0-4) 
3. `api.fetchRepository(owner, name)` returns (from the compromised/attacker-controlled endpoint) an `IAPIFullRepository` object whose `clone_url` is `https://attacker.example.com/org/repo.git` (same owner/name, same `https` protocol, different host). [7](#0-6) 
4. `updateRemoteUrl` finds `protocolsMatch === true` and `remoteUrlUnchanged === true` (current remote still equals the last cached `cloneURL`), and `urlsMatch === false` (URLs differ) — so it calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')` with no hostname check and no user prompt. [8](#0-7) 
5. Origin is now silently repointed; the user's next push/fetch from the Desktop UI (which still shows the same "org/repo" name) is silently redirected to the attacker's host.

  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
