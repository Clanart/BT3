### Title
Attacker-Controlled `_to` Address Causes Permanent DoS of KLAY Bridge Value-Transfer Processing via Unconditional Revert on Failed Native Transfer - (File: contracts/service_chain/bridge/BridgeTransferKLAY.sol)

### Summary
`BridgeTransferKLAY.handleKLAYTransfer()` performs all its state-mutating bookkeeping (nonce advancement, vote closing, deletion of pending vote/nonce records, and event emission) **before** attempting to send the KLAY value to `_to` via a low-level `.call.value()`, and then `require(ok, ...)` on that call's result. Since `_to` is an arbitrary address chosen entirely by the unprivileged party who originally called `requestKLAYTransfer()`/the bridge fallback (`_requestKLAYTransfer`), any user can supply a `_to` that is a contract designed to always revert (or intentionally exhaust gas) on receiving native value. When the bridge operator later calls `handleKLAYTransfer()` for that request, the mandatory `require(ok, ...)` at [1](#0-0)  reverts the entire transaction, undoing the nonce bookkeeping that had just been performed in the same call. Because nonce processing is strictly sequential and windowed via `_updateHandleNonce`/`_lowerHandleNonceCheck`, this un-processable nonce permanently blocks handling of that and all subsequent value-transfer nonces in the window, DoSing all other users' pending KLAY withdrawals on that bridge instance.

### Finding Description
`requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData)` is a fully public, unprivileged entry point that lets any caller pick an arbitrary `_to` and increments the sequential `requestNonce`: [2](#0-1) 

On the counterpart chain, the bridge operator is expected to relay this request by calling `handleKLAYTransfer`, which is `onlyOperators`-gated but processes attacker-chosen `_to` and `_value` supplied in the original request: [3](#0-2) 

Critically, the function order is:
1. `_lowerHandleNonceCheck` / vote counting
2. `_setHandledRequestTxHash`
3. `handleNoncesToBlockNums[...] = ...` and `_updateHandleNonce(_requestedNonce)` — this **advances `lowerHandleNonce`/`upperHandleNonce` and deletes bookkeeping for the processed window** at [4](#0-3) 
4. `emit HandleValueTransfer(...)`
5. Only **after** all that, the actual value transfer: `(bool ok, ) = _to.call.value(_value)(""); require(ok, "handleKLAYTransfer: transfer failed");`

Because step 5's `require` reverts the whole transaction if `_to` rejects the KLAY, the state advances made in steps 2-4 are also rolled back. Since nonce advancement (`_lowerHandleNonceCheck`) requires nonces to be handled in order (`lowerHandleNonce <= _requestedNonce`, see [5](#0-4) ), a single un-processable nonce (created by an attacker requesting a transfer to a reverting contract) permanently blocks `lowerHandleNonce` from advancing past it, thereby preventing the processing of every subsequent value-transfer request in the queue — a durable DoS of the bridge's withdrawal functionality for all users, not just the attacker.

This is the analog bug class described in the report: the operator's forwarded `.call{value}("")` to an untrusted, caller-controlled recipient reverts on failure instead of degrading gracefully, causing complete transaction failure and — in this case — persistent, queue-wide denial of service rather than a one-off failed reward payout.

### Impact Explanation
- Any unprivileged user can permanently jam the KLAY handling queue of a service-chain bridge by requesting a transfer to a maliciously crafted contract `_to` that always reverts on `receive()`.
- Because handle-nonce processing is strictly ordered and windowed (`lowerHandleNonce` must advance sequentially), this blocks **all subsequent users'** KLAY withdrawals through this bridge instance indefinitely, until an admin intervenes (bridge owner would need to use governance/administrative recovery, if any exists) — a Medium/High-severity availability and value-movement impact, since legitimate users' funds become unwithdrawable and value transfers pile up unprocessed.
- This is a self-inflicted, permanent freeze of bridge liquidity/withdrawal processing triggerable by a single low-cost unprivileged transaction (`requestKLAYTransfer` to a reverting contract), matching the "state divergence / acceptance-blocking" and "fee/value movement abuse" categories in scope.

### Likelihood Explanation
High likelihood: the attack requires only one call to the public, unprivileged `requestKLAYTransfer` function with a contract address that reverts on `receive()`/fallback (trivial to deploy), and no special privileges, timing, or race conditions are needed. The operator is expected to eventually process every nonce in order, so the DoS is guaranteed to manifest whenever the operator's automated relaying script attempts to process the malicious nonce.

### Recommendation
- Do not perform mandatory bookkeeping state changes (`_updateHandleNonce`, vote closing, event emission) in the same atomic path as an unconditional `require` on an externally-controlled call's success.
- Replace the pattern with a low-level call that does not revert the whole transaction on failure: capture `(bool ok, )` and, on failure, either (a) hold the KLAY in an internal per-`_to` balance for later `pull`-based withdrawal (pull-over-push pattern), or (b) emit a `HandleValueTransferFailed` event and mark the nonce processed regardless of transfer success, so the nonce window can still advance.
- Cap the gas forwarded on the low-level call and avoid copying arbitrary `returndata` into memory, consistent with the reported recommendation.
- Consider allowing nonce skipping/retry via governance so a malicious `_to` cannot cause a permanent, unrecoverable liquidity/withdrawal freeze.

### Proof of Concept
1. Attacker deploys `MaliciousReceiver` with:
   ```solidity
   contract MaliciousReceiver {
       receive() external payable { revert("no"); }
   }
   ```
2. Attacker calls `bridge.requestKLAYTransfer(address(maliciousReceiver), value, "")` (or triggers the payable fallback), consuming the next sequential `requestNonce` (say nonce N). See [6](#0-5) .
3. The counterpart bridge operator later calls `handleKLAYTransfer(txHash, attacker, maliciousReceiverAddr, value, N, blockNum, extraData)`.
4. Inside the call, `_lowerHandleNonceCheck`, vote-closing, `_updateHandleNonce`, and the `HandleValueTransfer` event all execute, but the final `_to.call.value(_value)("")` to `maliciousReceiverAddr` reverts (its `receive()` always reverts), triggering `require(ok, "handleKLAYTransfer: transfer failed")` and reverting the entire transaction — including the nonce advancement performed above. See [7](#0-6) .
5. Because `lowerHandleNonce` never advances past N (`_lowerHandleNonceCheck` in [5](#0-4)  keeps failing/blocking on retries of nonce N, or the operator is forced to keep retrying and failing on N), no operator can process any handle nonce ≥ N for any other legitimate user, freezing the bridge's KLAY value-transfer processing.
