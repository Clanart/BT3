### Title
Coinbase outputs are reported as spendable received funds despite being immature, locking deposits for 100 blocks - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates every transaction in a block, including the coinbase transaction (`block.txdata[0]`), and `Scanner::scan_transaction` emits a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script, without distinguishing coinbase outputs from ordinary ones. A coinbase output is consensus-immature for 100 blocks; any transaction spending it is rejected by the network. The scanner therefore reports funds as received that cannot actually be spent, mirroring the referenced issue where deposited funds cannot be withdrawn while a precondition (epoch start / coinbase maturity) is unmet.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:221-227`, `scan_block` calls `scan_transaction` on `block.txdata` in full. `scan_transaction` (lines 199-214) pushes a `ReceivedOutput` for every output paying to a script in `self.scripts` — including the coinbase. The only acknowledgement is a doc comment (lines 216-220) stating "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed." There is no programmatic guard: nothing in `ReceivedOutput` records that the output is immature, and `SignableTransaction::new`/`scan_transaction` provide no maturity filter. An attacker who mines a block (an unprivileged party producing public on-chain data the scanner consumes) can craft the coinbase so one of its outputs pays to the vault's P2TR script (e.g., the base `key` script registered at `Scanner::new`, or an offset script). The scanner then reports that output as a received deposit.

### Impact Explanation
If the consumer treats scanner results as spendable inputs (the default behavior — the "post-processing pass" is only a doc-comment suggestion, not enforced), it will select the immature coinbase `ReceivedOutput` as an input to `SignableTransaction`, produce a signed transaction spending it, and have that transaction rejected by Bitcoin consensus (BIP-113/COINBASE_MATURITY rule). The reported balance is unusable: the funds counted as received cannot be withdrawn until the output matures (~100 blocks), and any aggregated spend transaction built on it fails outright, blocking the withdrawal batch containing it. This satisfies "funds reported received that are not spendable."

### Likelihood Explanation
Likelihood depends on a miner choosing to pay the vault's script in a coinbase. Any miner can do this at no cost beyond the coinbase amount itself (which returns to them after maturity only if they keep the keys — here they deliberately pay the vault's script, effectively a dust/griefing deposit). Alternatively, it can occur innocuously if any coinbase ever pays the vault script. Once scanned and acknowledged, the output sits in the received set; if wallet selection is FIFO or value-based and picks it, the withdrawal transaction is invalid. Impact is bounded (temporary lock / failed spend rather than permanent loss), matching Medium severity.

### Recommendation
Track maturity in the scanner. Either:
- Have `scan_block` skip `block.txdata[0]` (as the doc comment already suggests) and expose a separate method for coinbase-aware scanning, or
- Add an `is_coinbase`/`matures_at` flag to `ReceivedOutput` when the containing transaction is a coinbase, so callers constructing `SignableTransaction` inputs can exclude immature outputs programmatically rather than relying on a doc-comment caveat.

At minimum, filter coinbase outputs inside `scan_block` before emitting `ReceivedOutput`s, since nothing downstream can distinguish them today.

### Proof of Concept
1. Build a `Scanner` via `Scanner::new(even_key)`, which registers the base `p2tr_script_buf(key)` at `Scalar::ZERO` (mod.rs:162-166).
2. A miner mines a block whose coinbase transaction contains an output with `script_pubkey = p2tr_script_buf(key)`.
3. Call `scanner.scan_block(&block)`. `scan_transaction` matches `output.script_pubkey` in `self.scripts` (mod.rs:205-211) and returns a `ReceivedOutput` indistinguishable from a normal deposit.
4. Pass that `ReceivedOutput` to `SignableTransaction::new` and sign. The resulting transaction spends a coinbase output before COINBASE_MATURITY and is rejected by every full node — the "received" funds cannot be withdrawn.
