### Title
Empty `SchnorrAggregate` verifies as a valid aggregate signature - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures as valid whenever the aggregate scalar `s` is zero, because the only remaining multiexp pair is `(-s, G)`, which is the identity when `s == 0`. Combined with `SchnorrAggregate::read`, which happily deserializes a length-prefixed empty `Rs` vector from attacker-supplied bytes, an unprivileged party can produce a serialized aggregate (`u32(0) || F::ZERO`) that passes `verify` for an empty `keys_and_challenges` list — a "successful" verification that attests to nothing.

### Finding Description
The Olympus issue is a boundary-case bug: a derived quantity (a moving average) is computed over too few samples and silently degenerates to a misleading but "valid-looking" result, with no minimum-sample enforcement. The analog in Serai is a boundary case where an aggregate verification over too few (zero) statements degenerates to a vacuously true check:

- `SchnorrAggregator::complete` returns `None` when no signatures were aggregated (`crypto/schnorr/src/aggregate.rs:175-178`), so the *honest* construction path refuses to produce an empty aggregate.
- However, `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`) reads a `u32` length and then that many points — zero is accepted, yielding `SchnorrAggregate { Rs: [], s }`.
- `verify` (`crypto/schnorr/src/aggregate.rs:127-146`) only checks `self.Rs.len() == keys_and_challenges.len()`. With both empty, the loop appends no pairs, and the final `pairs.push((-self.s, C::generator()))` leaves a single pair. `multiexp_vartime(&[(-s, G)]).is_identity()` holds iff `s == 0`.

So `SchnorrAggregate::read(&[0,0,0,0] || repr(0))` followed by `verify(dst, &[])` returns `true`. The transcript digest over `dst || "signatures"` is computed but never consumed by `weight()`, so no Fiat–Shamir weight is even sampled — the check reduces to a trivial identity.

The same degenerate-acceptance shape exists in `DLEqProof::verify` (`crypto/dleq/src/lib.rs:160-180`) and `MultiDLEqProof::verify` (`crypto/dleq/src/lib.rs:264-294`): with `generators.is_empty() && points.is_empty()`, no statements are transcripted, and the challenge is over a transcript containing only the `b"dleq"`/`b"multi_dleq"` domain separator. An attacker computes that public challenge, supplies it as `c` with an arbitrary `s` via `DLEqProof::read`, and `verify` returns `Ok(())` — a "valid" DLEq proof binding no points.

### Impact Explanation
Any consumer that treats `SchnorrAggregate::verify(...) == true` as authorization (e.g., "an aggregate of validator signatures approved this message") accepts a forged aggregate from an unprivileged party using only public data — the byte string is a constant requiring no secret knowledge. Likewise, a caller that requires a `DLEqProof` to verify before acting (e.g., PedPoP-style key confirmation, generator promotion) will accept a proof asserting nothing if the statement lists are built from attacker-influenced, possibly-empty collections. This is a forged-signature/forged-proof acceptance at a boundary case, mirroring how the Olympus MA silently returns a "price" that isn't a real average.

### Likelihood Explanation
The trigger requires the verifying side to reach `verify` with an empty `keys_and_challenges`/`generators` slice — for example, when the statement list is built dynamically from a signer/generator set that a peer can empty out, or when an aggregator outputs are filtered. Serai's own `complete()` and `prove()` never produce these objects, so exploitation depends on deserialization (`read`) of untrusted bytes — which is exactly the documented input surface (`SchnorrAggregate::read`, `DLEqProof::read` are public). Reachable but contingent on integrator call patterns, consistent with Medium.

### Recommendation
Reject degenerate inputs at the verification boundary, as the report recommends requiring ≥2 observations:
- In `SchnorrAggregate::verify`, return `false` when `keys_and_challenges.is_empty()` (equivalently `self.Rs.is_empty()`); optionally reject empty `Rs` in `read`.
- In `DLEqProof::verify` and `MultiDLEqProof::verify`, return `Err(DLEqError::InvalidProof)` when `generators.is_empty()` (and for multi, when any inner `generators[i]`/`points[i]` is empty), since a proof over zero statements proves nothing.

### Proof of Concept
```rust
// crypto/schnorr — empty aggregate verifies
let mut bytes = vec![0, 0, 0, 0]; // u32 len = 0
bytes.extend(C::F::ZERO.to_repr().as_ref());
let agg = SchnorrAggregate::<C>::read(&mut &bytes[..]).unwrap();
assert!(agg.verify(b"some_dst", &[])); // true: only pair is (-0, G) == identity

// crypto/dleq — empty DLEq proof verifies
let mut t = SomeTranscript::new(b"ctx");
t.domain_separate(b"dleq");
let c: F = challenge(&mut t.clone()); // public computation
let proof = DLEqProof { c, s: F::random(rng) }; // or via read
let mut vt = SomeTranscript::new(b"ctx");
assert!(proof.verify(&mut vt, &[], &[]).is_ok()); // Ok(()): c == challenge of empty transcript
```

Both cases succeed because verification reduces to a check over zero statements — the degenerate analogue of a moving average computed from a single observation.
