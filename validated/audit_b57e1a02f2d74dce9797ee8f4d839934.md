### Title
Attacker-controlled `WWW-Authenticate` realm forces GitHub Enterprise sign-in flow to bind to an untrusted origin - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential-class bug in `CoverReassurance` (`retrieveReassurance`) let anyone move funds using an *account* value supplied by the caller instead of validating that the caller was the actual owner of that allowance — a "trusted arbitrary identifier" flaw. The closest reachable analog in this GitHub Desktop checkout is in the git-credential trampoline: `getEndpointKind()` derives the *trust classification* of a remote host (`'enterprise'` vs `'generic'`) from a `WWW-Authenticate` response header that is entirely controlled by whatever server/proxy Git is talking to, and that classification is then used to open Desktop's real "Sign in to GitHub Enterprise" flow bound to the attacker's own origin.

### Finding Description
When Git needs credentials for a remote it invokes Desktop's credential helper, which calls `getCredential()` → `getEndpointKind()`: [1](#0-0) 

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [2](#0-1) 

The `wwwauth[]` entries in the credential map come verbatim from the `WWW-Authenticate` HTTP header returned by the git server Desktop is connecting to. That header content is fully attacker-controlled — any malicious or compromised remote/HTTP proxy that Git is pointed at (a cloned repo's `origin`, a submodule URL, an `insteadOf` rewrite, or a plain HTTP MITM) can answer with `WWW-Authenticate: Basic realm="GitHub"` regardless of the actual host. This check runs *before* and short-circuits the only real verification available further down the same function — the network probe `isGitHubHost(endpoint)`: [3](#0-2) 

Once classified as `'enterprise'` and no matching stored account exists for that origin, `getCredential()` calls: [4](#0-3) 

`ui.promptForGitHubSignIn(endpoint)`, where `endpoint` is the credential URL built directly from attacker-supplied `protocol`/`host`/`path` fields (`getCredentialUrl`): [5](#0-4) 

`promptForGitHubSignIn` then unconditionally treats any non-`github.com` hostname as a GitHub Enterprise instance and binds Desktop's real sign-in machinery to it: [6](#0-5) 

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
this.dispatcher.showPopup({ type: PopupType.SignIn, isCredentialHelperSignIn: true, credentialHelperUrl: endpoint })
```

The corrupted value here is `endpointKind`/`endpoint`: it is meant to represent "a host that is verifiably a GitHub/GHE instance," but it is instead derived from an unauthenticated, attacker-supplied header and origin. No guard exists between this classification and the point where the real sign-in flow (OAuth authorize URL construction, or basic-auth credential prompt) is bound to that origin — `isGitHubHost()`, the one check that performs an actual `/meta`-style verification, is bypassed entirely once the header match succeeds.

### Impact Explanation
A malicious or compromised git server/proxy — reachable simply by the user cloning, fetching, or pushing to a repository whose remote (or submodule/`insteadOf` rewrite) points at it — can cause Desktop to open its native "Sign in to GitHub Enterprise" dialog pre-bound to the attacker's origin, in the middle of what looks like an ordinary git operation the user just initiated. Because the popup is Desktop's own trusted sign-in UI (`PopupType.SignIn`, `isCredentialHelperSignIn: true`), a user has no strong signal that the endpoint it's about to authenticate against is untrusted. If the user completes sign-in, credentials (basic auth) or the OAuth exchange are directed to the attacker's host rather than a real GitHub Enterprise deployment, resulting in credential/token capture and an account binding to an attacker-controlled endpoint inside the user's Desktop accounts store.

### Likelihood Explanation
Setting a fake `WWW-Authenticate: ... realm="GitHub"` header requires nothing beyond running a basic HTTP server, and the victim only needs to perform a routine git operation (clone/fetch/push) against a URL the attacker controls — no local access, no admin rights, no pre-existing malware, no unnatural steps. This matches the "attacker controls ... a git remote/proxy response" class explicitly called out as valid. The main mitigating factor is that the sign-in dialog does display the endpoint URL, so a very attentive user could notice the mismatch, which keeps likelihood at medium rather than high.

### Recommendation
Do not classify a host as `'enterprise'` based solely on a self-reported `WWW-Authenticate` realm string. Always perform the authoritative `isGitHubHost(endpoint)` check (or otherwise verify against the known/allow-listed set of accounts' endpoints) before short-circuiting into `'enterprise'`, and surface a clear, hard-to-miss warning in the sign-in popup whenever the endpoint was inferred from an unauthenticated header/redirect rather than from an already-registered account or explicit user action.

### Proof of Concept
1. Host an HTTP server at `http://evil.example` that responds to any git-http request with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone or add a remote pointing at `http://evil.example/foo.git` (e.g., via a repository whose `.git/config` was set up this way, or a submodule URL).
3. Trigger a fetch/push; Git invokes Desktop's credential helper with `wwwauth[0]=Basic realm="GitHub"`.
4. `getEndpointKind()` returns `'enterprise'` for `evil.example` without any real verification.
5. `getCredential()` finds no stored account for `evil.example` and calls `ui.promptForGitHubSignIn('http://evil.example/...')`, which calls `beginEnterpriseSignIn` + `setSignInEndpoint('http://evil.example')` and shows Desktop's native GitHub Enterprise sign-in popup bound to the attacker's origin. const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
