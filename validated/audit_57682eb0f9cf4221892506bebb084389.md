### Title
Missing precompile-address exclusion check on EIP-7702 `SetCodeAuthorization.Address` allows an unprivileged sender to delegate an EOA to a reserved precompile address - (File: `blockchain/state_transition.go`)

### Summary
The reported bug class is a "reserved identifier not excluded" collision: a namespace of privileged/reserved values (function selectors, with `0x00000000` reserved for `ROOT`) is not excluded when a new, attacker-influenced value is admitted into that same namespace. In Kaia, the analogous reserved namespace is the range of precompiled-contract addresses (`0x01`–`0x3FF`), which every other transaction path that accepts a user-supplied destination address explicitly excludes. The EIP-7702 authorization-list processing path (`applyAuthorization`) is the one exception: it installs a delegation designator at an arbitrary attacker-chosen `auth.Address` without ever checking that this target is not a reserved precompile address.

### Finding Description
Kaia enforces a project-wide invariant that ordinary externally/authority-controlled address fields must not collide with the precompiled-contract address range. This is checked explicitly in:
- `TxInternalDataEthereumAccessList.Validate` [1](#0-0) 
- `TxInternalDataEthereumBlob.Validate` [2](#0-1) 
- `TxInternalDataValueTransfer.Validate` [3](#0-2) 
- contract-deploy transaction types (create address collision check) [4](#0-3) 
- and even `TxInternalDataEthereumSetCode.Validate` itself, which checks the top-level `Recipient` field of the very same transaction type [5](#0-4) 

However, the `AuthorizationList` entries carried by the same `TxTypeEthereumSetCode` transaction are processed separately in `StateTransition.applyAuthorization`, and that function performs no equivalent check on `auth.Address` — the address that becomes the delegation target written into the authority account's code via `AddressToDelegation`: [6](#0-5) 

`AddressToDelegation`/`ParseDelegation` simply wrap the target address with the `0xef0100` prefix with no restriction on which address may be used: [7](#0-6) 

Because `SetCodeAuthorization` is signed by the authority itself and submitted by any transaction sender in a normal `TxTypeEthereumSetCode` transaction, an unprivileged sender (or the authority signing their own authorization) can set `auth.Address` to any of the precompile addresses (`0x1`…`0x9`, `0x3fd`, `0x3fe`, `0x3ff`, or higher such as `0x0a`–`0x11` for BLS-related precompiles in Prague), which is exactly the class of "reserved namespace value" that every sibling validation path deliberately excludes. This mirrors the auth-collision report's root cause: a supposedly-unique/reserved identifier space (function selectors there, precompile addresses here) is not defended against attacker-chosen values entering the same space through a secondary, less-scrutinized code path (`_moduleCall` there, the EIP-7702 authorization list here).

The precompile-guard logic elsewhere in the EVM (`evm.Call`) assumes precompile addresses never hold delegation designators and treats calls to those addresses specially, creating an account object and dispatching to `RunPrecompiledContract`: [8](#0-7) 

Allowing an EOA to acquire a delegation designator pointing at a precompile address breaks this assumption for any code path that resolves delegation code before/independently of the precompile-address fast-path check, creating an inconsistency between "this address is precompiled" (`common.IsPrecompiledContractAddress`, a static range check [9](#0-8) ) and "this address's code (or delegated code) is that of a precompiled contract" that the rest of the validation layer was designed to prevent from ever occurring.

### Impact Explanation
This breaks an invariant relied upon throughout the transaction-validation and EVM layers that ordinary/authority addresses cannot exist inside the reserved precompile address range. Depending on how `resolveCode`/`resolveCodeHash` and future protocol logic (fork-gated precompile activation, `IsPrecompiledContractAddress` static range vs. fork-specific active precompile maps in `blockchain/vm/precompiles.go`) interact with a delegated EOA whose designator now points into that reserved space, this can produce state/behavior divergence between client implementations or between different hard-fork configurations that treat "is this a precompile" differently for a delegated account — the same category of impact the rules require ("state divergence between honest nodes" / "acceptance of an invalid transaction"). It is reachable by a single submitted `TxTypeEthereumSetCode` transaction from any unprivileged sender, matching the report's requirement that the exploit path requires no special node/validator/governance privilege.

### Likelihood Explanation
The path is trivially reachable: any account can sign a `SetCodeAuthorization` naming its own address as authority and pick `auth.Address` freely, then have anyone submit the enclosing `TxTypeEthereumSetCode` transaction. No governance, no module deployment, and no special permission is required — only the will to construct the authorization tuple, which is orders of magnitude easier than the referenced report's brute-forcing of a 4-byte selector, since the precompile address space is a small, publicly known, fixed list.

### Recommendation
Add the same `common.IsPrecompiledContractAddress` (and ideally the fork-aware active-precompile check from `blockchain/vm/precompiles.go`) rejection to `StateTransition.validateAuthorization`/`applyAuthorization` for `auth.Address`, mirroring the checks already present in `TxInternalDataEthereumSetCode.Validate`, `TxInternalDataValueTransfer.Validate`, and the smart-contract-deploy `Validate` functions, so that a delegation designator can never be installed pointing at a reserved precompile address.

### Proof of Concept
1. Attacker (or any authority) signs a `SetCodeAuthorization{ChainID: <chainID>, Address: common.BytesToAddress([]byte{9}) /* blake2F precompile */, Nonce: <authority's current nonce>}` using `types.SignSetCode`.
2. Any sender submits a `TxTypeEthereumSetCode` transaction whose `AuthorizationList` includes this tuple, targeting an arbitrary `Recipient`.
3. `StateTransition.TransitionDb` → `applyAuthorization` (`blockchain/state_transition.go:762-794`) processes the tuple: `validateAuthorization` only checks chain ID/nonce/signature/existing-code, not that `auth.Address` avoids the precompile range, so `st.state.SetCodeToEOA(authority, types.AddressToDelegation(auth.Address), rules)` installs `0xef0100 || 0x0000...0009` as the authority's code — a state neither `TxInternalDataEthereumSetCode.Validate` (which only checks `Recipient`, not `AuthorizationList` entries) nor any other guard rejects.
4. The authority account now carries a delegation designator into the reserved precompile address space, an outcome that is explicitly disallowed for every other address-accepting field in the codebase (`ErrPrecompiledContractAddress`), demonstrating the missing check.

// DelegationPrefix is used by code to denote the account is delegating to
// another account.
var DelegationPrefix = []byte{0xef, 0x01, 0x00}

// ParseDelegation tries to parse the address from a delegation slice.
func ParseDelegation(b []byte) (common.Address, bool) {
	if len(b) != 23 || !bytes.HasPrefix(b, DelegationPrefix) {
		return common.Address{}, false
	}
	var addr common.Address
	copy(addr[:], b[len(DelegationPrefix):])
	return addr, true
}

// AddressToDelegation adds the delegation prefix to the specified address.
func AddressToDelegation(addr common.Address) []byte {
	return append(DelegationPrefix, addr.Bytes()...)
}

func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}

	// Update nonce and account code.
	st.state.IncNonce(authority)
	delegation := types.AddressToDelegation(auth.Address)
	if common.EmptyAddress(auth.Address) {
		// Delegation to zero address means clear.
		st.state.SetCodeToEOA(authority, []byte{}, rules)
		return nil
	}

	// Otherwise install delegation to auth.Address.
	// We treat EOA and SCA as separate objects and therefore need to use
	// distinct methods.
	st.state.SetCodeToEOA(authority, delegation, rules)

	return nil
}
