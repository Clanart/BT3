## Analysis

The Lyra vault bug's core broken invariant is: **a safety guard meant to block new risky state-increasing actions is also applied to a pure refund/close-out path, which carries no additional risk and should never be blocked.** The strongest local analog in Hyperbridge is the `whenNotPaused` modifier on `onPostRequestTimeout()` in the `HyperFungibleToken` / `WrappedHyperFungibleToken` (and their Upgradeable variants) apps.

### Title
Paused HyperFungibleToken apps block `onPostRequestTimeout` refunds, locking already-burned/escrowed user funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` burns (or `WrappedHyperFungibleToken.send()` locks) a user's tokens immediately and dispatches a cross-chain POST request. If that request times out, the only way to recover the user's funds is via `onPostRequestTimeout()`, which re-mints or releases the escrowed tokens back to the original sender [1](#0-0) . This function, however, is gated by `whenNotPaused` in every variant of the app: `HyperFungibleToken` [2](#0-1) , `HyperFungibleTokenUpgradeable` [3](#0-2) , `WrappedHyperFungibleToken` [4](#0-3) , and `WrappedHyperFungibleTokenUpgradeable` [5](#0-4) .

### Finding Description
`pause()` is designed to stop *new* risky operations that create fresh cross-chain obligations or mint new balances without verified proof - `send()` and `onAccept()` are correctly gated this way, since `onAccept` mints new tokens on unverified trust in a relayed message [6](#0-5) . `onPostRequestTimeout`, in contrast, is a pure refund of funds the user already had committed/burned - the host has already cryptographically proven via a non-membership proof that the destination never processed the request [7](#0-6) , and the host layer itself performs the callback with no pause check of its own (`EvmHost.dispatchTimeOut`) [8](#0-7) . There is no legitimate reason for a returning-of-already-escrowed-funds action to require the same risk gate as new fund creation - this exactly mirrors the Lyra report's core complaint that `closeLoan`/`increaseCollateralAmount` should not be blocked by a check meant only to prevent new mispriced risk.

Because `EvmHost.dispatchTimeOut` uses a low-level `.call()` and does not bubble up the revert, a paused app's reverted `onPostRequestTimeout` does not revert the relayer's `handlePostRequestTimeouts` transaction; it simply re-stores the request commitment (`_requestCommitments[commitment] = meta;`) so it can be retried later, and skips the relayer fee refund [9](#0-8) . This means every relayer attempt while paused wastes gas and fails silently, and the user's tokens remain locked/unminted for the entire duration the contract owner keeps the app paused - which is unbounded and solely at the discretion of a role that is not the affected user.

### Impact Explanation
While the pause is active (which, unlike the challenge period, has no maximum duration and is purely owner-discretionary), any user whose `send()` request has already timed out cannot recover their funds. This is a direct parallel to "frozen assets" in the Lyra finding: funds that were already debited from the user (burned/locked) are stuck with no available recovery path, even though the underlying operation (returning money to its rightful, already-verified owner) requires no price/state validation and poses no risk that pausing is meant to prevent.

### Likelihood Explanation
This triggers under normal, non-malicious operating conditions: any legitimate reason to pause the app (e.g. an incident with `onAccept`/mint path) coincides with in-flight `send()` transfers timing out, which is a routine, expected occurrence in ISMP given the timeouts subsystem exists precisely for liveness failures on the destination side [10](#0-9) . No attacker action, malicious relayer, or compromised key is required - simply an already-paused contract plus a naturally occurring timeout.

### Recommendation
Remove `whenNotPaused` from `onPostRequestTimeout()` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol` (or use a distinct modifier gating only new-money-creation entry points such as `send`/`onAccept`, not refund paths), so refunds of already-committed/proven-untimely-delivered requests can always be processed regardless of pause state.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`; tokens are burned and a POST request is dispatched.
2. Owner calls `pause()` for an unrelated incident affecting `onAccept`/mint logic.
3. The request times out on the destination chain; a relayer submits the timeout proof via `HandlerV2.handlePostRequestTimeouts` -> `EvmHost.dispatchTimeOut` -> `HyperFungibleToken.onPostRequestTimeout()`.
4. `onPostRequestTimeout` reverts due to `whenNotPaused`; `dispatchTimeOut`'s `.call()` returns `success = false`, so the commitment is restored and no refund/re-mint occurs [11](#0-10) .
5. The user's burned tokens remain unrecoverable for as long as the owner keeps the contract paused, even though no additional risk arises from processing this specific refund.

```text
    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) external override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
```

```text
    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```

```text
Blockchains may become incapable of processing transactions for a vareity of reasons. These might include _liveness failures_, which can occur when the state transition function becomes unable to produce new blocks, consensus faults, transaction fee spikes that make transaction execution unprofitable, or a doomsday scenario such as a nation state sanctioned attack.

Regardless of the reason, if the destination becomes incapable of processing incoming ISMP requests, the framework provides a timeout mechanism. This feature allows for the safe reversion of state changes on the source chain that were executed prior to dispatching the request, as if no issue ever occurred.

`PostRequest` and `GetRequest` both have the ability to time out due to their `timeout_timestamp` value. This value stipulates the lifespan of a message. A `PostRequest` will time out when its destination's `host.timestamp()` surpasses the `timeout_timestamp`. This asserts that the destination has indeed not processed the relevant messages. Conversely, a `GetRequest` times out when its source's `host.timestamp()` surpasses the sending chain's `timeout_timestamp`.
```
