## Finding: Unvalidated URL scheme passed to `shell.openExternal` via the `open-external` IPC channel

### Summary
The `open-external` IPC channel accepts an arbitrary string `path` from the renderer and forwards it to Electron's `shell.openExternal` in the main process, with no scheme allow-list (`http:`/`https:` only) anywhere along the traced call chain. Since `GitHubRepository.htmlURL` is persisted verbatim from GitHub/GHE API responses by `RepositoriesStore._upsertGitHubRepository` and later surfaced through "View on GitHub"-style actions, a malicious or compromised GitHub API/GHE server can supply a dangerous custom URI scheme in `htmlURL` that ends up being opened unchecked by the OS.

### Finding Description
- The renderer-side proxy for opening external links is a plain IPC passthrough with no validation:
`export const openExternal = invokeProxy('open-external', 1)` [1](#0-0) 
- `IAppShell.openExternal` in `app-shell.ts` simply re-exports this proxy without any URL/scheme sanitization: [2](#0-1) 
- `RepositoriesStore._upsertGitHubRepository` persists `htmlURL`/`cloneURL` fields taken directly from API responses into the local repositories database, with 3 references in that file confirming `htmlURL` is written from the API object without scheme validation. [3](#0-2) 
- I was not able to retrieve the exact body of the `ipcMain.handle('open-external', ...)` registration inside `app/src/main-process/main.ts` within the available tool budget (only the import header was inspected); I confirmed via `grep_search` that `main.ts` references `open-external`/`openExternal` three times, but could not view the handler implementation itself to confirm whether a scheme check exists there. This is a gap in my verification.

### Impact Explanation
If the main-process handler does not restrict schemes, a persisted `htmlURL` containing a non-`http(s)` scheme (e.g., a Windows search/URI handler scheme, a custom protocol registered by another installed application, or `file:`) could be invoked by the OS shell when the user clicks a "View on GitHub"-style action, potentially leading to code execution via a vulnerable protocol handler or local file exposure. This matches the "Valid Impact" criteria for an attacker-controlled GitHub API object leading to code execution / file access outside the intended scope.

### Likelihood Explanation
Requires a malicious or compromised GitHub Enterprise/API endpoint (or a MITM'd API response) to set `htmlURL` to a dangerous value, and requires the user to click a resulting "View on GitHub" or similar link. This is a plausible but non-trivial attack chain — it depends on the user trusting/adding a malicious GHE server or an attacker being able to tamper with API responses.

### Recommendation
- Confirm and, if missing, add scheme validation (allow only `http:`/`https:`) in the `open-external` handler in `app/src/main-process/main.ts` before calling `shell.openExternal`.
- Additionally validate/sanitize `htmlURL`/`cloneURL` at ingestion time in `RepositoriesStore._upsertGitHubRepository` (`app/src/lib/stores/repositories-store.ts`) to reject non-`http(s)` values from API responses.

### Proof of Concept
Not fully verified — requires confirming the actual `ipcMain.handle('open-external', ...)` implementation in `app/src/main-process/main.ts`, which I could not inspect due to tool-call budget limits. The conceptual PoC: have a (malicious/compromised) GitHub/GHE server return a repository object whose `html_url` is a dangerous custom URI (e.g., `some-app:payload`), let `_upsertGitHubRepository` persist it, then trigger the "View on GitHub" action to see whether `shell.openExternal` is invoked without a scheme check.

**Caveat:** Given I could not view the actual `ipcMain.handle('open-external', ...)` body in `main.ts` (only its imports and reference counts), I cannot state with full certainty whether a scheme check exists there already. This should be verified directly in the file before treating this as a confirmed, unmitigated vulnerability — a Devin session with full file access would be needed to inspect the exact handler code and settle this conclusively.
