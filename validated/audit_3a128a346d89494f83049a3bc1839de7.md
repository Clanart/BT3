### Title
Attacker-supplied OP_RETURN data is omitted from Bitcoin fee accounting - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` adds an OP_RETURN output to the transaction but calculates virtual size, weight, required fee, and change using only the payment outputs. A data-bearing transaction therefore receives signatures for the full transaction while paying a fee calculated for a smaller transaction.

### Finding Description
After validating up to 80 bytes of caller-controlled data, `SignableTransaction::new` appends it as a zero-value OP_RETURN output. [1](#0-0)  The subsequent `calculate_weight_vbytes` call passes only `payments`, omitting the OP_RETURN output already present in `tx_outs`. [2](#0-1)  The same omission occurs when sizing the transaction with a change output, causing both `needed_fee` and the change amount to be based on a transaction smaller than the one being built. [3](#0-2)  The returned transaction nevertheless contains the OP_RETURN output, and signing later commits to that complete transaction through `taproot_key_spend_signature_hash`. [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged party who causes transaction data to be included can deterministically make the threshold signers authorize a transaction paying less than the requested fee rate. At a requested rate equal to the relay minimum, the omitted OP_RETURN bytes can make the resulting transaction fall below the minimum relay fee and fail propagation; the signatures still commit to the unintended, underfunded transaction. This is a concrete signing-of-unintended-transaction impact rather than a parser crash.

### Likelihood Explanation
Any non-empty `data` argument triggers the issue because the OP_RETURN output is always appended but never represented in either sizing call. Reachability requires only that an attacker can influence the data attached to a transaction being constructed and signed; no malformed encoding, invalid curve point, privileged access, or threshold collusion is needed.

### Recommendation
Calculate transaction weight and virtual size from the complete output list, including the OP_RETURN output, or pass an explicit representation of that output into `calculate_weight_vbytes` for both the change and no-change paths. Add a regression test asserting `needed_fee == fee_per_vbyte * transaction().vsize()` for transactions with 1-byte and 80-byte OP_RETURN outputs.

### Proof of Concept
```rust
// `received` is a spendable ReceivedOutput obtained by Scanner::scan_transaction
// or ReceivedOutput::read.
let payment_script = p2tr_script_buf(key).unwrap();
let data = vec![0x42; 80];

let tx = SignableTransaction::new(
  vec![received],
  &[(payment_script, DUST)],
  None,
  Some(data),
  1, // requested 1 sat/vbyte
)
.unwrap();

// The OP_RETURN output is included in the signed transaction.
assert_eq!(tx.transaction().output.len(), 2);

// But the fee was calculated without that output.
let actual_fee = tx.fee();
let actual_vbytes = u64::try_from(tx.transaction().vsize()).unwrap();

assert_eq!(actual_fee, tx.needed_fee());
assert!(actual_fee < actual_vbytes);
```

The transaction is therefore signed at less than 1 sat/vbyte even though `needed_fee` was supposed to represent the fee necessary for the requested rate.
