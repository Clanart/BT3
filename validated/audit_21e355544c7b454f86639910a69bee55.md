## Analysis

The H‑24 report's core broken invariant: a fund/state‑mutating function performs its side effect (transfer + balance mutation) trusting that a *different* piece of state has already been checked/updated, instead of gating the mutation on its own idempotency record before writing it.

The closest local analog in this repo is in `EvmHost.dispatchIncoming(GetResponse, address relayer)`. It labels a state write as "replay protection" but never actually checks the existing value before overwriting it, and it pays out the relayer fee without ever clearing the source of that fee.

### Title
Unconditional relayer-fee payout in `dispatchIncoming(GetResponse)` without checking or clearing prior receipt/fee state - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` writes `_responseReceipts[commitment]` unconditionally (comment says "replay protection" but no `require`/read-before-write guard exists), then, on a successful callback, transfers `_requestCommitments[commitment].fee` to `relayer` — without ever deleting or zeroing `_requestCommitments[commitment]`. [1](#0-0) 

### Finding Description
Compare the two `dispatchIncoming` overloads:
- `dispatchIncoming(PostRequest, relayer)` stores `_requestReceipts[commitment] = relayer` and deletes it on callback failure so the request can be retried, mirroring the lend-audit pattern of "delete state on one path, forget the other." [2](#0-1) 
- `dispatchIncoming(GetResponse, relayer)` does the same store/delete-on-failure dance for `_responseReceipts`, but additionally reads `_requestCommitments[commitment].fee` and transfers it to `relayer` on success — and that fee entry is never deleted anywhere in this function. [3](#0-2) 

The exact corrupted value is `_requestCommitments[commitment].fee`: it is read and paid out but the mapping entry is never zeroed after payment. Nothing in `EvmHost.sol` itself prevents a second call to `dispatchIncoming(GetResponse,...)` for the same `commitment` (e.g., the handler processing the message again, a resubmitted batch, or any code path that re-invokes this `restrict(_hostParams.handler)` function with the same response) from paying the fee a second time to a second `relayer` argument — the function has no `require(_responseReceipts[commitment].relayer == address(0))` guard before it overwrites the receipt, unlike a true check-then-effect pattern. This is structurally identical to the H‑24 root cause: `repayBorrowInternal()` mutates a balance without ever touching (or checking) the related cross-chain bookkeeping that should have gated it, so the same underlying value can be acted on twice through two different call paths.

Because the guard exists only at the caller (the handler contract that is expected to reject a state proof it has already used), and not as an intrinsic invariant inside `EvmHost` on the fee-bearing storage itself, this is a single point of failure: any bug or gap in the handler's own duplicate-detection (a different contract, out of scope for this file) turns directly into a double payout of the exact same fee from `EvmHost`'s feeToken balance.

### Impact Explanation
If `dispatchIncoming(GetResponse,...)` is invoked twice for the same `commitment` — via any handler-level gap, a race in batched processing, or a legitimately-finalized response being resubmitted through a still-valid state commitment — `EvmHost` pays the relayer fee twice out of its own feeToken balance to whatever `relayer` address is supplied in the second call. This is a direct "double-claim / repeated settlement of a relayer reward," draining `feeToken()` balance that belongs to other requests/relayers. It matches the bounty's explicit "replay/double-claim/double-settlement" and "loss of funds" categories.

### Likelihood Explanation
The likelihood depends entirely on whether the calling handler enforces uniqueness of `commitment` across all response deliveries; `EvmHost.sol` provides no defense-in-depth of its own, since the fee source (`_requestCommitments[commitment]`) is never cleared and the receipt write is unconditional. I could not fully verify the handler-side (`Handler`/`HandlerV2.sol`) duplicate-submission checks within the available tool budget, so it is uncertain whether an unprivileged caller can currently reach a second `dispatchIncoming(GetResponse,...)` call for the same commitment through the public message-submission entrypoint. This uncertainty should be resolved before treating this as a confirmed, exploitable bug — it is reported here as the strongest local structural analog found, not a proven end-to-end PoC.

### Recommendation
Add an explicit idempotency check inside `EvmHost.dispatchIncoming(GetResponse,...)` itself (`require(_responseReceipts[commitment].relayer == address(0), "AlreadyDelivered")`) before writing the receipt, and delete/zero `_requestCommitments[commitment]` immediately after the fee transfer succeeds, so the fee cannot be paid a second time regardless of what the calling handler does.

### Proof of Concept
Could not be completed to a full working PoC within the available iterations — this requires confirming whether the external handler contract that calls `dispatchIncoming(GetResponse,...)` allows re-submission of an already-delivered response commitment (e.g., due to a missing membership check on `_responseReceipts` before invoking the host, or a batch-processing path that can invoke the same commitment twice). This should be verified directly against `evm/src/handlers/HandlerV2.sol` (or equivalent) in a follow-up session before treating this as confirmed-exploitable; the vulnerability described above is the local structural analog to H‑24 with exact file/line evidence, but end-to-end reachability by an unprivileged actor is unconfirmed.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
