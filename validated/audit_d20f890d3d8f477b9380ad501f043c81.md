### Title
Scanner credits coinbase outputs before maturity, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is an unsafe default around how many confirmations are required before funds are treated as final. The Serai analog lives in the Bitcoin `Scanner`: `Scanner::scan_block` iterates over every transaction in `block.txdata`, including `block.txdata[0]` (the coinbase), and emits `ReceivedOutput`s for it. Coinbase outputs are consensus-unspendable for 100 blocks (BIP-30 / COINBASE_MATURITY), which far exceeds the `N::CONFIRMATIONS` depth the processor's scanner uses before declaring a block finalized (`processor/src/multisigs/scanner.rs` uses `latest.saturating_sub(N::CONFIRMATIONS - 1)` and panics on any later reorg of a scanned block). The code's own documentation concedes this: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed to remove those outputs." [1](#0-0) 

### Finding Description
`Scanner::scan_transaction` matches any `tx.output` whose `script_pubkey` is in `self.scripts` and wraps it into a `ReceivedOutput` with a valid offset — with no distinction between coinbase and regular transactions. [2](#0-1)  `scan_block` then calls it on all of `block.txdata`, txdata[0] included. [3](#0-2) 

Downstream, the processor's block-scanning loop feeds each `network.get_outputs(&block, key)` result (amount ≥ `N::DUST`) into `ScannerEvent::Block`, which triggers a `Batch` crediting the deposits, and the schedulers subsequently use those `ReceivedOutput`s as inputs to outbound `SignableTransaction`s. [4](#0-3) [5](#0-4)  Nothing in the in-scope wallet code filters coinbase transactions or enforces the 100-block maturity window; the only protection is a doc comment telling callers to do a "post-processing pass" themselves — an unsafe default identical in shape to shipping `confirmations: 1` in a config. (I was not able to fully verify whether `processor/src/networks/bitcoin.rs::get_outputs` performs that post-processing pass before exhausting tool iterations; the unsafe primitive and its documented contract are confirmed regardless.)

### Impact Explanation
Any miner can craft a coinbase paying the multisig's P2TR `script_pubkey` (a public value — anyone can compute it from the group key). The scanner treats it as a confirmed deposit: it is emitted in a `Block` event, saved via `save_outputs`, acked into a `Batch`, and becomes schedulable. The output cannot actually be spent for 100 blocks, so a `SignableTransaction` spending it is consensus-invalid and will be rejected by the Bitcoin network — funds are reported received that are not spendable. Worse, a real coinbase output matching the script sits in `ram_outputs`/`seen`, so if the processor later re-encounters the same outpoint after maturity it hits `panic!("scanned an output multiple times")` or produces a `Batch` for an already-consumed outpoint. [6](#0-5) 

### Likelihood Explanation
Reachable by an unprivileged party with public inputs only: any miner (or, on low-hashrate/test networks, anyone) can include an output to the multisig's known `script_pubkey` in their coinbase. No malicious validator, RPC, or leaked key is required. It does not enable theft, but reliably produces invalid spend transactions / scanner panics once triggered — a Medium-severity availability/correctness issue, not a key-compromise one.

### Recommendation
Enforce the safe default inside the primitive, not via doc-comments: `scan_block` should skip `block.txdata[0]` (or take the block height and suppress coinbase-matched outputs until `height + 100`), so no reachable caller can accidentally credit immature outputs. If coinbase outputs are ever legitimately expected, gate them on maturity explicitly rather than leaving a mandatory post-processing step to every consumer.

### Proof of Concept
1. Multisig key `K` is tweaked and registered; `Scanner::new(K)` stores `p2tr_script_buf(K) -> Scalar::ZERO`. [7](#0-6) 
2. A miner builds a coinbase transaction whose `tx.output[0].script_pubkey` equals that P2TR script and mines it at height `h`.
3. Once `h` reaches depth `N::CONFIRMATIONS` (≪ 100), the processor calls `scan_block`/`get_outputs`; `scan_transaction` matches the coinbase output and returns `ReceivedOutput { offset: 0, outpoint: (coinbase_txid, 0) }`. [8](#0-7) 
4. The output enters a `Batch` and the scheduler builds a `SignableTransaction` spending `(coinbase_txid, 0)`; the transaction fails Bitcoin consensus validation (immature coinbase spend), leaving credited funds unspendable and the spend path stalled until the output matures — or, on rescan after maturity, `panic!("scanned an output multiple times")`.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```

```rust
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
```
