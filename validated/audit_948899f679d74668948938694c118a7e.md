### Title
`ReceivedOutput::read` deserializes untrusted bytes into a "spendable" output without binding `offset`, `output`, or `outpoint` to on-chain reality - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Ludwig pickle deserialization bug (CWE-502: attacker-controlled bytes instantiated as trusted objects without validation), `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` reconstructs a `ReceivedOutput` — the type the wallet layer treats as a confirmed, spendable deposit — purely from supplied bytes. It validates only that `offset` is a canonical scalar and that `TxOut`/`OutPoint` are consensus-decodable; it never checks that the `outpoint` exists on-chain, nor that `output.script_pubkey` is actually the P2TR script derived from the multisig key plus `offset`. Any byte source feeding this function can fabricate an output that downstream code treats as received, spendable funds.

### Finding Description
`ReceivedOutput::read` performs only syntactic validation:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;              // only canonicality checked
    output = TxOut::consensus_decode(&mut buf_r)?;   // only decodability checked
    outpoint = OutPoint::consensus_decode(&mut buf_r)?;
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

The three fields are deserialized independently with no consistency check between them. Contrast with the honest construction path, `Scanner::scan_transaction` (same file, lines 199-214), where `offset` is guaranteed to correspond to `output.script_pubkey` because the script was looked up in `self.scripts` (a map populated only via `register_offset`, lines 180-196) and `outpoint` is computed from the real transaction. `ReceivedOutput::read` strips this invariant: a deserialized `ReceivedOutput` is indistinguishable from a scanned one.

The semantic damage manifests downstream: `Output::key()` (processor/src/networks/bitcoin.rs:112-122) derives the spendable key as `read_G(script_pubkey_key) - GENERATOR * offset`, and the signing path uses `offset` to tweak the threshold key share for that input. If `offset` does not match the script (impossible to detect post-deserialization), the derived key is wrong and the output is unspendable; if the `outpoint` is fabricated or belongs to an unrelated transaction, the processor reports a deposit that does not exist at all.

### Impact Explanation
An attacker who can supply bytes to `ReceivedOutput::read` (e.g., a relayed/claimed output fed into the processor pipeline, which lists `ReceivedOutput::read` as an accepted untrusted-bytes sink) can cause **funds to be reported as received that are not spendable**:

- A fabricated `outpoint` + the victim multisig's real P2TR `script_pubkey` + `offset = 0` yields a phantom deposit: the processor credits `value()` sats (processor/src/networks/bitcoin.rs:128-130) for an input that does not exist, or that exists but pays someone else.
- A real on-chain output paying `key + o·G` paired with a mismatched `offset ≠ o` yields an output that scans/spends under the wrong key derivation, producing invalid signatures at spend time after funds have been credited.

### Likelihood Explanation
Exploitation requires an attacker-controlled byte stream reaching `ReceivedOutput::read` — plausible wherever serialized outputs cross a trust boundary (relayed outputs, imported scans, peer-synced state). No key material, collusion, or malformed encodings are needed; all fields deserialize cleanly. Within the wallet model, this is reachable with purely public inputs.

### Recommendation
Bind the three fields on deserialization, or stop trusting `read` entirely:

1. After decoding, verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)` for the expected base key (requires threading the scanner key into `read`, or a `verify_for(&Scanner)` method), and
2. Confirm the `outpoint` resolves to the claimed `TxOut` via an authenticated chain view before crediting `value()`.

Short-term, restrict `ReceivedOutput::read` to trusted internal persistence and treat externally sourced claims as requiring re-scan via `Scanner::scan_transaction`, which enforces the script↔offset binding by construction.

### Proof of Concept
```rust
use bitcoin_serai::wallet::{ReceivedOutput, p2tr_script_buf};
use bitcoin_serai::bitcoin::{
  consensus::Encodable, OutPoint, TxOut, Amount, Txid, hashes::Hash,
};
use ciphersuite::{group::ff::Field, Ciphersuite};
use k256::{ProjectivePoint, Scalar};
use serai_frost::curve::Secp256k1;

// victim multisig group key -> script
let group_key = ProjectivePoint::GENERATOR * Scalar::from(12345u64);
let script = p2tr_script_buf(group_key).unwrap();

// Craft a phantom deposit: arbitrary offset, victim's script, fake outpoint
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes()); // offset = 0, matches script trivially
TxOut { script_pubkey: script, value: Amount::from_sat(1_000_000_000) }
    .consensus_encode(&mut buf).unwrap();
// OutPoint pointing to a txid that never paid this script (or doesn't exist)
OutPoint::new(Txid::from_byte_array([0xAA; 32]), 0)
    .consensus_encode(&mut buf).unwrap();

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.value() == 1_000_000_000 is reported as received funds;
// the outpoint is fabricated, so the deposit is unspendable/nonexistent.
assert_eq!(forged.value(), 1_000_000_000);
```

Deserialization succeeds because `read` checks only scalar canonicality and consensus-decodability — the exact analog of `pandas.read_pickle()` accepting any syntactically valid blob, with the resulting object trusted as a genuine deposit downstream.
