## Title
Copilot conflict resolution silently deletes conflicting code instead of failing when the model's hunk count doesn't match the file's actual conflict markers - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted merge-conflict resolution feature extracts conflict hunks from a file, sends them to the model, and then splices the model's per-hunk responses back into the original on-disk content via `reassembleResolvedFile`. The splicing is matched purely by **positional order**, not by content or line-number identity, and there is no check that the number of resolved hunks returned by the model equals the number of conflict marker blocks actually present in the file. When these counts diverge — plausible whenever the conflicting content originates from an attacker-influenced branch/PR that triggers truncation, skip-on-size logic, or unusual marker patterns — trailing conflict blocks are deleted from the file with **both sides' content dropped entirely** and no error surfaced to the user, then written to disk and staged as if fully resolved.

### Finding Description
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` walks the raw file content line-by-line, and for every well-formed `<<<<<<< / ======= / >>>>>>>` block it consumes one entry from `hunkResolutions` in order: [1](#0-0) 

Critically, `hunkIndex` is incremented on every conflict block regardless of whether a corresponding resolution exists:
```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  ...
}
hunkIndex++
```
If `hunkResolutions.length` is smaller than the number of conflict blocks actually found in the file, every extra block is simply skipped — its `<<<<<<<`/`=======`/`>>>>>>>` markers **and both "ours" and "theirs" content** are entirely dropped from the output, leaving no trace and no warning.

There are two structural reasons this mismatch is reachable:
1. **Independent marker parsers.** Extraction (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts`, using `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker`) and reassembly (`reassembleResolvedFile`, using its own locally-defined `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) are two separate regex-based scanners over the same file. [2](#0-1) [3](#0-2)  Nothing guarantees they agree on hunk count for all inputs (e.g. malformed/near-malformed marker sequences, or content near the `MAX_CONFLICT_LINE_LENGTH` / `MAX_CONFLICT_CONTENT_SIZE` skip thresholds that can cause some hunks to be omitted from what's sent to the model while still being present in the on-disk file). [4](#0-3) 
2. **No count validation before write.** `reassembleResolutions` calls `reassembleResolvedFile(ctx.rawContent, raw.hunks)` directly and returns whatever comes out, with no assertion that `raw.hunks.length` matches the number of conflict blocks in `ctx.rawContent`: [5](#0-4) . The only validation performed on the model's JSON (`parseCopilotConflictResolution`) checks types/non-emptiness and absence of leftover conflict markers inside a resolved hunk — it never cross-checks hunk *count* per file against the extracted context. [6](#0-5) 

The result of `reassembleResolutions` is written straight to disk and staged when the user clicks "Continue Merge": [7](#0-6) 

This is the closest analog to the referenced Illuminate finding: an operation that is supposed to fully "settle" its output (mint iPTs / fully resolve conflicts) silently omits part of the expected result (no iPTs / dropped conflict content) while the surrounding flow reports success.

### Impact Explanation
This causes **silent corruption of what the user commits or pushes**, one of the explicitly valid impact categories. A user resolving a merge/rebase/cherry-pick conflict with Copilot assistance can end up committing a file where an entire conflicting section — both the "ours" and "theirs" code — has vanished, with no error, no warning banner distinct from normal operation, and a UI that presents the merge as successfully resolved. Because the attacker (or the source of the "theirs" branch/PR being merged) controls the conflicting content, they influence which files/hunks are large, malformed-looking, or borderline the size/line-length skip thresholds, increasing the likelihood of triggering a hunk-count mismatch on merges involving their branch. The corrupted commit can then be pushed, silently removing code (e.g., a security check, validation, or business logic) that a reviewer would expect to still be present, without the user or reviewer having any indication content was dropped.

### Likelihood Explanation
This requires no elevated privileges, no local/physical access, and no user action beyond the normal, expected workflow of using the shipped "Resolve with Copilot" feature on a conflicted merge from a repository/branch/PR the attacker influences — squarely within the "attacker controls a cloned/fetched repository" and "unprivileged" criteria. The precise triggering conditions (getting the model to return fewer hunks than the extractor counted, or hitting a skip/size boundary asymmetrically between extraction and reassembly) require crafting specific conflict content, so likelihood is not "always fires on any conflict" but "reliably reachable via crafted repository content," which is a realistic bar for this bug class.

### Recommendation
- After reassembly, validate that `hunkIndex === hunkResolutions.length` (i.e., every model-provided hunk was consumed) *and* that the number of conflict blocks found equals the count that was sent to the model for that file; throw a `CopilotValidationError` on mismatch instead of silently dropping content.
- Reuse a single shared marker-scanning implementation (or shared regexes) between `extractConflictHunks` and `reassembleResolvedFile` so the two logically-linked steps can never disagree on hunk boundaries.
- When a hunk is skipped (missing separator/closing marker or count mismatch), never delete file content — treat it as a hard failure that routes the file into `ICopilotSkippedFile` for manual resolution instead of writing a "successful" resolution.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
