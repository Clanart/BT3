### Title
Unauthenticated broadcast of arbitrary transactions via `AggregatorServer::internal_send_tx` when `client_verification` is disabled - (File: core/src/servers.rs)

### Summary
`create_grpc_server` in `core/src/servers.rs` selects the `Noop` interceptor whenever `config.client_verification` is `false`, and `Noop::call` returns `Ok(req)` unconditionally without ever invoking `is_internal` or checking peer certificates. Since the "Internal" method authorization check lives exclusively inside `only_aggregator_and_self` (which is skipped entirely under `Noop`), any unauthenticated caller who can reach the aggregator's public gRPC port can invoke `InternalSendTx` and have arbitrary attacker-chosen `raw_tx` bytes forwarded into the aggregator's broadcast pipeline.

### Finding Description
The intended binding is: `caller_of_Internal*_method == aggregator_itself_or_self_cert_holder`, enforced by `is_internal(&req)` inside `only_aggregator_and_self` at [1](#0-0) . That check is only reached from the `OnlyAggregatorAndSelf` variant of the interceptor [2](#0-1) .

`create_grpc_server` chooses the interceptor based on `config.client_verification`: if true it builds `OnlyAggregatorAndSelf` with loaded certs, otherwise it uses `Noop` [3](#0-2) . `Interceptors::Noop => Ok(req)` bypasses all certificate and `is_internal` checks [4](#0-3) .

Since `create_aggregator_grpc_server` merely emits a `tracing::warn!` when `client_verification` is enabled, and does not itself force it on [5](#0-4) , whenever the aggregator is deployed with `client_verification = false`, `InternalSendTx` (and any other `Internal*`-prefixed RPC) is reachable directly by any anonymous TCP client, with no certificate and no `is_internal` gate applied at all — because `is_internal` is never called under `Noop`.

### Impact Explanation
This matches the "High - an unauthenticated state-changing or broadcasting call" category: an unprivileged attacker can submit an arbitrary raw Bitcoin transaction through `internal_send_tx` and have the aggregator's fee-paying/broadcast infrastructure relay it. Depending on what UTXOs/inputs the attacker controls or can reference, this could conflict with or interfere with the aggregator's own pending protocol transactions (e.g., competing for the same fee-wallet inputs), degrading the availability/correctness of protocol transaction broadcasting. This is a genuine authentication-bypass on a state-changing/broadcasting endpoint, contingent entirely on the deployment running with `client_verification = false`.

### Likelihood Explanation
The vulnerability is fully deployment-config-gated: it exists only when the aggregator's `client_verification` setting is `false`, at which point the bypass is trivial (no TLS certs, no keys, no special privileges needed — just network access to the aggregator's gRPC port and a well-formed `InternalSendTx` request). If `client_verification = true` (the recommended/warned-about production setting), `OnlyAggregatorAndSelf` is used and the binding holds correctly. Whether production deployments actually run with `client_verification = false` could not be confirmed from the code inspected (only test/testnet4 config samples were located, not necessarily production defaults), so likelihood depends on operational configuration not fully verifiable from this repo alone.

### Recommendation
Do not allow `Noop` to skip the `is_internal` check. Either (a) always enforce the "Internal"-prefix authorization check regardless of `client_verification`/interceptor variant (i.e., check `is_internal` unconditionally and reject unauthenticated internal calls even under `Noop`), or (b) disallow disabling `client_verification` for the aggregator's internal RPCs, e.g. by making the aggregator refuse to start `InternalSendTx`-capable services unless TLS client verification is enabled, or by binding internal RPCs to a loopback/internal-only listener separate from the public gRPC port.
