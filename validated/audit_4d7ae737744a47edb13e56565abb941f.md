## Analysis

This repo (`Ellentat/claude-code--007`) is a plugin/skills marketplace for Claude Code, not the core CLI engine. Within it, the `hookify` plugin implements the actual command-approval-relevant trust boundary the rules permit ("hook bypass"). I traced the same "single bad item halts/corrupts the whole batch" bug class into hookify's rule evaluation pipeline and found a reachable analog.

### Title
Single malformed rule crashes `evaluate_rules`, silently bypassing ALL other blocking hook rules (fail-open) - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`evaluate_rules()` iterates every loaded hookify rule in one unguarded loop with no per-rule try/except [1](#0-0) . A single rule whose `tool_matcher` frontmatter value is coerced to a Python `bool` (e.g. `tool_matcher: true`) causes an uncaught `AttributeError` deep in `_matches_tool` [2](#0-1) , which propagates out of the entire `evaluate_rules` batch. The only safety net is the hook script's outer `except Exception`, which does not preserve any blocking decision and always `exit(0)` [3](#0-2) . The net effect is that ALL other configured blocking rules for that PreToolUse/PostToolUse/Stop event are silently skipped for that tool call — not just the malformed one.

### Finding Description
The parser in `extract_frontmatter`/`Rule.from_dict` coerces any simple top-level frontmatter key whose value is the literal string `"true"`/`"false"` into a Python `bool` [4](#0-3) . This coercion is applied generically to all keys, including `tool_matcher`, which is then stored on the `Rule` object without type validation [5](#0-4) .

When `evaluate_rules()` runs, for each rule it calls `_rule_matches()` [1](#0-0) , which checks `if rule.tool_matcher: if not self._matches_tool(rule.tool_matcher, tool_name)` [6](#0-5) . `_matches_tool` unconditionally calls `matcher.split('|')` [7](#0-6) . If `matcher` is `True`/`False` (a `bool`, not a `str`), this raises `AttributeError: 'bool' object has no attribute 'split'`.

This exception is not caught anywhere in `_rule_matches`, `_check_condition`, or the `evaluate_rules` loop — there is no per-rule isolation, mirroring the report's "atomicity failure" pattern (`aggregate3`/Solidity loop with no per-entry fallback). It bubbles up to `pretooluse.py`/`posttooluse.py`/`stop.py`'s single outer `try/except`, which — by explicit design comment "ALWAYS exit 0 - never block operations due to hook errors" — prints a `systemMessage` and exits 0 without returning any `permissionDecision: deny` or `decision: block` [8](#0-7) . Because Claude Code's PreToolUse hook contract treats the absence of a deny decision as implicit allow, every other rule that would have blocked the operation (e.g. a rule blocking `rm -rf`, `.env` edits, secret exfiltration commands, etc.) is silently skipped for that single tool invocation.

### Impact Explanation
A single crafted/broken hookify rule file dropped into a project's `.claude/hookify.*.local.md` (e.g. by a malicious repository contributor, a compromised dependency's setup script, or simple misconfiguration) disables the entire local guardrail layer for that tool call, without any visible block — the user only sees a generic "Hookify error" system message rather than a clear blocking decision. This is a concrete approval-bypass / hook-bypass: dangerous Bash commands or file edits that other configured rules were meant to block execute anyway. Unlike the original oracle report (fail-closed, causing settlement delay), this is fail-open, which is more severe from a security-control-bypass perspective.

### Likelihood Explanation
Reachability requires only that a rule file define `tool_matcher: true` or `tool_matcher: false` (or any other boolean-coercible top-level value passed into a code path expecting a string) — a plausible, easy-to-make authoring mistake (a user might intuitively write `tool_matcher: true` thinking it enables the matcher, since the parser already treats `true`/`false` specially for `enabled:`). It requires no special privileges beyond the ability to add a `.claude/hookify.*.local.md` file to a project, which is the same "project config" attack surface the rules permit under prompt/frontmatter parsing and hook bypass trust boundaries.

### Recommendation
1. Add per-rule isolation in `evaluate_rules()`: wrap each `self._rule_matches(rule, input_data)` call in `plugins/hookify/core/rule_engine.py` in a `try/except`, log the offending rule, and `continue` to the next rule rather than letting the exception escape the batch.
2. Validate `tool_matcher` (and other rule attributes) type at load time in `Rule.from_dict`/`Condition.from_dict` in `plugins/hookify/core/config_loader.py`, coercing to `str` or rejecting the rule with a warning (matching the existing per-file try/except pattern already used in `load_rules`).
3. Change the hook scripts' outer exception handler in `pretooluse.py`/`posttooluse.py`/`stop.py` to fail closed (or at least surface a clear, unmissable warning) instead of unconditionally `exit(0)` when rule evaluation errors, so a broken rule cannot silently disable all other rules.

### Proof of Concept
1. Create `.claude/hookify.evil.local.md` in a project:
   ```
   ---
   name: broken-rule
   enabled: true
   event: bash
   tool_matcher: true
   pattern: "harmless"
   ---
   This rule is broken but shouldn't matter.
   ```
2. Also configure a legitimate blocking rule in the same or another `.claude/hookify.*.local.md`, e.g. one that blocks `rm -rf` via `action: block`.
3. Run any Bash tool call, e.g. `rm -rf /important/data`.
4. `load_rules()` loads both rules successfully (parsing itself doesn't fail — `tool_matcher` is just a bool value stored on the `Rule`). [9](#0-8) 
5. `evaluate_rules()` iterates rules; when it reaches `broken-rule`, `_rule_matches` calls `_matches_tool(True, "Bash")`, raising `AttributeError`. [10](#0-9) 
6. The exception propagates out of `evaluate_rules` uncaught, then out of `main()` in `pretooluse.py`, hitting only the outer `except Exception`, which prints a system message and `exit(0)` — no block decision returned. [11](#0-10) 
7. Result: the `rm -rf` command is NOT blocked by the legitimate rule, even though it should have been — the entire rule batch was bypassed by the one broken rule.

```python
    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```
