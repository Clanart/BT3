### Title
Unbounded attacker-controlled vector growth in untrusted deserialization paths enables memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The analog of CVE-2024-22368 (unbounded memoization growth driven by a crafted input) in Serai is deserialization routines that let an unprivileged counterparty dictate, via a length field inside bytes they supply, how many elements get pushed into in-memory vectors with no protocol-level cap. The clearest instance is `SchnorrAggregate::read`, which trusts a 4-byte count and pushes one group element per iteration into a `Vec` with no upper bound [1](#0-0) . The same pattern recurs across the in-scope DKG/FROST stack (`crypto/dkg/pedpop`, `crypto/dkg/dealer`, `crypto/frost/src/nonce.rs`, `crypto/frost/src/sign.rs`, `crypto/dkg/src/lib.rs`), all of which contain `vec![0; len]` / `Vec::with_capacity` / `for _ in 0 .. len` loops driven by bytes an untrusted peer supplies to `read_preprocess` / `EncryptedMessage::read` / `Commitments::read` style entry points [2](#0-1) .

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` and then loops `0 .. u32::from_le_bytes(len)` calling `C::read_G(reader)?`, pushing each parsed point into `Rs` [1](#0-0) . A count of up to ~4.29 billion is accepted unconditionally; nothing in the read path cross-checks the declared count against the number of keys the verifier will actually aggregate (`verify` only compares `self.Rs.len()` to `keys_and_challenges.len()` *after* the allocation and parsing already happened [3](#0-2) ). Unlike `Call::read` in `networks/ethereum`, which was explicitly hardened to chunk reads precisely because "a valid DoS would be to claim a 4 GB data is present" [4](#0-3) , the cryptographic read paths do no such bounding and no `MAX_*` style cap exists on element counts for aggregate signatures, preprocess batches, commitment lists, or shares. This mirrors the XLSX memoize flaw: the parser's internal data structure grows proportional to attacker-declared repetition, not to any protocol-meaningful bound.

### Impact Explanation
A remote, unprivileged participant in a signing or DKG session can submit a crafted preprocess/share/aggregate byte blob with a maximal count field, forcing the victim node to allocate and populate a multi-gigabyte (or attacker-sized) vector of group elements before any signature verification rejects it. Repeated submissions exhaust memory and crash the validator/coordinator process, halting threshold signing and DKG completion — an availability loss (CVSS A:H analog) consistent with the reported medium severity.

### Likelihood Explanation
These `read` functions are exactly the documented ingestion surface for peer-controlled bytes: preprocess and share messages from other signers flow through `read_preprocess`, `EncryptedMessage::read`, `Commitments::read`, and `SchnorrAggregate::read`. Any participant in a multisig set — or anyone who can get their bytes routed into a signing session — can trigger the path. No authentication or validity check precedes the allocation, since the count is consumed before any proof/signature verification.

### Recommendation
Enforce a protocol-level maximum element count in every untrusted `read` before iterating: for `SchnorrAggregate::read`, reject `len` exceeding the maximum number of signers (e.g., `MAX_KEY_SHARES_PER_SET`-style bound already used elsewhere [5](#0-4) ); apply the same cap to preprocess, commitment, share, and encrypted-message vectors in `crypto/frost`, `crypto/dkg/pedpop`, `crypto/dkg/dealer`, and `crypto/dkg`. Alternatively, read incrementally and stop at the first malformed element rather than pre-committing to the declared count.

### Proof of Concept
Construct a `SchnorrAggregate` byte stream: `FF FF FF FF` (count = 4,294,967,295) followed by as many valid `C::G` encodings as the transport permits, terminated by a 32-byte scalar. Feeding this to `SchnorrAggregate::read` — e.g., as the aggregated-signature portion of a peer message a validator parses during signing — drives the loop at aggregate.rs:83 to allocate/push group elements for the entire supplied payload, and the declared `u32` count sets the expectation with no cap. A minimal frame forcing large allocation:

```python
payload = (0xFFFFFFFF).to_bytes(4, 'little') + valid_G_encoding * N + scalar_32_bytes
# pass to SchnorrAggregate::<C>::read(&mut io::Cursor::new(payload))
```

Note: because the loop pushes per element actually read (rather than `with_capacity` on the count), peak memory is proportional to bytes delivered, so the practical attack ships a large blob of valid point encodings — still a parsing-time memory blowup of the same class as the memoize exhaustion, and the declared count itself is never validated. I was unable to confirm the exact line numbers for the analogous `vec![0; len]` allocations in `crypto/frost/src/nonce.rs` and `crypto/frost/src/sign.rs` within the available iterations; grep confirms length-driven allocation/loop constructs exist there and warrant the same fix.

    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {

    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
  }
