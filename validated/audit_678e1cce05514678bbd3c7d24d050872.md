## Analysis

The Sherlock report's core broken invariant: an attacker/user can grow an on-chain array to a size where a *later, mandatory* state-transition function (withdraw) must iterate over the full array in a single transaction, and the resulting gas cost can exceed the destination chain's block gas limit — permanently reverting that path and locking the escrowed asset, with no external/malicious-actor precondition beyond the initial array-growing action itself.

The local Hyperbridge analog is in `IntentGatewayV2.withdraw()`, which is the sole exit path for escrowed order funds (both `RedeemEscrow` and `RefundEscrow` flows dispatched via `onAccept`): [1](#0-0) 

This loops over `body.tokens`, performing a native/ERC20 external transfer per element with no cap on `len`. `body` is a `WithdrawalRequest` decoded from the cross-chain message body, and its token list traces back to `Order.inputs`, which is a caller-supplied, unbounded `TokenInfo[]`: [2](#0-1) 

`onAccept()` dispatches straight into `_withdraw`/`withdraw` for `RedeemEscrow`/`RefundEscrow` kinds with no bound check on the decoded body's token array: [3](#0-2) 

I was not able to locate (within the indexed content available to me) an explicit `MAX_TOKENS_PER_ORDER`-style cap enforced when an order is originally placed/escrowed — the grep for such a constant across the `IntentGatewayV2.sol` variants returned no bound constant, only the `Order`/`TokenInfo` struct definitions and the unbounded `withdraw` loop. Given index size limits, I could not fully confirm the order-creation entrypoint (`newOrder`/`placeOrder`) code path that populates `Order.inputs`, so I cannot state with certainty whether there is a length check elsewhere that I didn't surface. A Devin session with full repo access should verify the order-placement function directly.

### Title
Unbounded `Order.inputs`/`WithdrawalRequest.tokens` array in `IntentGatewayV2.withdraw()` can permanently lock escrowed funds via gas-limit DOS - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` iterates over `body.tokens` (sourced from the user-supplied `Order.inputs` array) with one external token transfer per entry and no array-length cap. If an order is created with a sufficiently large number of input tokens, the gas required to execute the resulting `RedeemEscrow`/`RefundEscrow` withdrawal (triggered via `onAccept` from an incoming Hyperbridge post-request) can exceed the destination/source chain's block gas limit, making `withdraw()` unexecutable and permanently locking the escrowed assets — the same class of hardcoded/unbounded-array DOS described in the VotingEscrow `MAX_DELEGATES` report.

### Finding Description
`Order` contains `TokenInfo[] inputs` with no maximum length enforced in the struct or (as far as could be confirmed) at order-creation time: [2](#0-1) 

The redemption/refund path decodes a `WithdrawalRequest` from the incoming cross-chain message and calls `withdraw`, which loops over `body.tokens` performing a native-value `call` or an ERC20 `transfer` per element: [4](#0-3) 

`onAccept` routes `RedeemEscrow`/`RefundEscrow` requests directly into this loop with no size gate: [3](#0-2) 

Since the settlement/withdrawal call must process the entire array atomically (per-token external calls cannot be split across transactions), a sufficiently large `inputs`/`tokens` array makes the single settlement transaction unminable on any chain whose block gas limit is below the cost of the full loop — exactly the mechanism in the source report, just with escrow token transfers instead of delegate-array traversal.

### Impact Explanation
This falls squarely within the "bridged assets, order escrow ... must move exactly once and only to the rightful beneficiary" pivot: it does not just fail to move funds, it can make funds *permanently unmovable* because `withdraw()` is the only settlement/refund entrypoint for escrowed order inputs. This is loss/lock of user funds without needing a malicious relayer, prover, or admin — purely a consequence of the order's own array size versus the chain's gas ceiling.

### Likelihood Explanation
Likelihood is moderate-to-high on lower-gas-limit EVM chains (the intended multi-chain deployment target for Hyperbridge, per the docs referencing IOTA EVM and general EVM compatibility, mirrors the exact "any EVM-compatible chain" framing in the source report). Triggering it requires only that a user (or an order griefing itself/another beneficiary) create an order with many input tokens; no privileged actor, relayer collusion, or protocol proof forgery is needed.

### Recommendation
Enforce a maximum length on `Order.inputs` (and on `SweepDust.outputs`, `PaymentInfo.assets`, `DispatchInfo.assets`) at order-creation/dispatch time, sized so that the worst-case `withdraw()` gas cost stays well under the gas limit of the lowest-gas-limit supported destination/source chain. Reject any order or dust-sweep request whose token array exceeds this cap before it is committed/escrowed.

### Proof of Concept
1. User calls the order-creation entrypoint with `Order.inputs` populated with, e.g., several thousand distinct dummy `TokenInfo` entries (each pointing at cheap/no-op ERC20 tokens the user controls), escrowing minimal amounts per token.
2. Order is dispatched cross-chain and later a `RedeemEscrow`/`RefundEscrow` request is delivered back, invoking `onAccept` → `_withdraw`/`withdraw`.
3. `withdraw()`'s loop over `body.tokens` performs one external call per token; measure gas consumption scaling linearly with array length (analogous to the reported `testDelegateLimitAttack` PoC pattern).
4. On a chain with a block gas limit below the loop's total cost (e.g., ~10-17M gas chains referenced in the source report), the transaction can never be included, and the escrowed funds behind that order commitment become permanently unredeemable.

     * @notice Withdraws the escrowed tokens for a request body.
     * @dev This function is marked as internal.
     * @param body The request body containing commitment, tokens, and beneficiary.
     * @param isRefund Whether this is a refund (true) or a successful fill (false).
     */
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
