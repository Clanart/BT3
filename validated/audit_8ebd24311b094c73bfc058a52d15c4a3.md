### Title
Unvalidated `ReceivedOutput` deserialization permits fabricated or duplicated UTXOs to reach threshold signing - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the output exists, belongs to a registered scanner script, or is unique. [1](#0-0)  The transaction constructor then treats each supplied `ReceivedOutput` as spendable value and copies its claimed `TxOut` into the Taproot `Prevouts::All` commitment. [2](#0-1) [3](#0-2) 

### Finding Description
The scanner-derived script check is syntactic rather than a proof of ownership or UTXO existence: `multisig` only verifies that the claimed previous output’s `script_pubkey` equals the script derived from the group key and supplied offset. [4](#0-3)  An attacker can therefore serialize a `ReceivedOutput` containing a scanner script, an arbitrary value, and a nonexistent, mismatched, or already-used outpoint. [5](#0-4) 

`SignableTransaction::new` sums the claimed input values without checking whether two entries reference the same outpoint or whether the referenced prevouts match chain state. [2](#0-1)  During signing, the forged `prevouts` vector is committed through `Prevouts::All`, so the threshold group signs the attacker’s fabricated prevout data rather than data proven to match confirmed UTXOs. [6](#0-5) 

### Impact Explanation
A forged deposit can be represented as spendable balance and cause the threshold group to produce a fully formatted Bitcoin transaction for an input that is nonexistent, already spent, duplicated within the transaction, or associated with a different amount on-chain. [2](#0-1)  Bitcoin consensus rejects the resulting transaction because its actual UTXO and prevout commitment do not match, while the local wallet has already reported the fabricated value as received and consumed signing resources. [6](#0-5) 

### Likelihood Explanation
The input path is reachable through untrusted bytes passed to `ReceivedOutput::read`, and no secret, validator compromise, malformed point, or invalid consensus encoding is required. [1](#0-0)  The attacker only needs a scanner-controlled Taproot script, which is publicly derivable from the group key and offset, and can then choose the outpoint and amount freely. [7](#0-6)  Exploitation requires the caller to accept externally supplied `ReceivedOutput` values or a duplicated input list, but the affected APIs provide no local defense against either condition. [8](#0-7) 

### Recommendation
Do not treat deserialization as proof that a `ReceivedOutput` is spendable. [1](#0-0)  Before constructing a `SignableTransaction`, resolve each `OutPoint` against confirmed chain state and require the returned `TxOut` to equal the claimed value and script exactly. [2](#0-1)  Reject duplicate outpoints before summing inputs and before creating `tx.input`, since duplicate inputs both inflate the apparent balance and make the transaction invalid. [2](#0-1)  Prefer a constructor or verifier type that can only produce a spendable `ReceivedOutput` from scanner output plus confirmed UTXO data, and reject immature coinbase outputs at that boundary. [9](#0-8) 

### Proof of Concept
Conceptually, construct bytes containing a scalar offset, a consensus-encoded `TxOut` with an inflated amount and the scanner’s Taproot script, and a consensus-encoded nonexistent `OutPoint`. [1](#0-0) 

```rust
let offset = Scalar::ZERO;
let script = p2tr_script_buf(group_key).unwrap();
let fake_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: script,
};
let fake_outpoint = OutPoint::default();

let mut encoded = offset.to_bytes().to_vec();
encoded.extend(bitcoin::consensus::encode::serialize(&fake_txout));
encoded.extend(bitcoin::consensus::encode::serialize(&fake_outpoint));

let received = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
let signable = SignableTransaction::new(
  vec![received],
  &payments,
  change,
  None,
  fee_per_vbyte,
).unwrap();

let machine = signable.multisig(&keys).unwrap();
```

The `multisig` construction succeeds because the script matches the offset-derived group key even though the outpoint and amount were never authenticated. [4](#0-3)  Completing the FROST flow signs `Prevouts::All` containing the forged amount, producing a transaction that cannot be accepted against real Bitcoin UTXO state. [6](#0-5)
