### Title
Deserialized `ReceivedOutput` fields are trusted without verification, enabling fee-inflation and unspendable-fund signatures - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` deserializes three attacker-controlled fields — the `offset` scalar, the full `TxOut` (including `script_pubkey` and `value`), and the `OutPoint` — and performs no consistency check between them or against the on-chain UTXO set. This is the direct analog of the Parity `KeyFile.address` bug: a stored/serialized field is treated as ground truth even though the cryptographically relevant facts are derivable or verifiable. `SignableTransaction::new` then uses the claimed `value` for change/fee math and the claimed `TxOut` as the sighash `Prevouts::All` commitment, while only `script_pubkey` is ever checked (inside `multisig`).

### Finding Description
`ReceivedOutput::read` returns `ReceivedOutput { offset, output, outpoint }` straight from the byte stream with no validation:

- `offset` is read via `Secp256k1::read_F` (`mod.rs:123`).
- `output` (`TxOut`: `value` + `script_pubkey`) and `outpoint` are consensus-decoded (`mod.rs:128-131`).

Downstream, `SignableTransaction::new` consumes these fields without verification:

- `input_sat` is the sum of the *claimed* `input.output.value`s (`send.rs:175`), and `offsets` are taken verbatim (`send.rs:176`).
- `prevouts` (used for the BIP-341 `Prevouts::All` sighash commitment) are the claimed `TxOut`s (`send.rs:253`, `send.rs:375`).
- The only consistency check anywhere is `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` in `multisig` (`send.rs:277`). The claimed `value` and the claimed `outpoint` are never checked — they cannot be checked locally, which is exactly why trusting the serialized form is dangerous.

Consequences for a tampered `ReceivedOutput`:

1. **Fee inflation (loss of funds).** If `output.value` is understated relative to the real UTXO, `input_sat` shrinks, the change output shrinks by the difference, and `fee()` (`send.rs:138-141`, computed from the claimed prevouts) understates the true on-chain fee. The real fee paid is `real_input_value - outputs`, so the difference is burned to miners. The threshold group signs this transaction without any participant seeing the discrepancy.
2. **Unspendable/invalid transaction (fund freeze).** If `outpoint` points to a nonexistent or already-spent output, or `value` is overstated, the group signs a transaction committing (via `Prevouts::All`) to false input data — the resulting signed transaction can never confirm, yet it consumes a FROST signing session and any associated one-time state.
3. **Wrong-output redirection via offset.** Although `multisig` binds `script_pubkey` to `key + offset·G`, an attacker who supplies serialized outputs can choose an `offset` such that the prevout pays to a *different registered offset* of the group key than intended (offsets are surjective, see `register_offset` docs, `mod.rs:168-180`), causing the group to consolidate/spend an input it did not mean to spend at that position.

### Impact Explanation
The threshold multisig signs a Bitcoin transaction whose committed input amounts differ from reality, producing either a permanently invalid transaction (signed message that can never confirm, wasting a signing session and potentially stalling withdrawal flow) or a valid transaction that silently burns the amount difference as miner fees. In the Serai architecture, processor nodes exchange/store serialized `Output`/`ReceivedOutput` objects (see `processor/src/networks/bitcoin.rs:145-166` `Output::read`, which calls `ReceivedOutput::read`), so a party able to supply or corrupt these bytes — a malicious coordinator, or an attacker who tampers with the data another participant signs over — causes the honest threshold group to sign an unintended transaction. This matches the report's exploit shape: the *displayed/used* value differs from the cryptographically-derived truth, and the user/signers do not notice.

### Likelihood Explanation
Reachability requires an attacker to feed crafted bytes to `ReceivedOutput::read` — e.g., a malicious peer/coordinator distributing output sets, or filesystem/DB tampering with persisted outputs, analogous to the report's KeyFile modification. It does not require compromising any signer or the Bitcoin network. The signing path (`SignableTransaction::new` → `multisig` → `sign`) accepts the value unconditionally; only `script_pubkey` consistency is enforced. Because the check that would catch the fraud (comparing claimed prevout data to the actual chain UTXO) does not exist anywhere in the wallet crate, a single corrupted record reliably produces a mis-signed transaction. Likelihood is moderate — it needs write access to the serialized output channel — so Medium overall.

### Recommendation
Mirror the report's recommendation: do not trust deserialized `ReceivedOutput` fields.

- Re-derive or verify the `script_pubkey` against `key + offset·G` at `ReceivedOutput::read`/`SignableTransaction::new` time, not only inside `multisig` (which can return `None` after fees/change were already computed).
- Before signing, validate each input's `outpoint` and `value` against a confirmed on-chain UTXO (RPC lookup in `Scanner`/`rpc.rs` flow), so the `Prevouts::All` commitment reflects reality.
- Detect duplicate/overlapping `outpoint`s across inputs and reject outputs whose claimed value differs from the chain-observed value.
- Treat any inconsistency as a hard error rather than `None`, so mis-signing is loudly attributable.
