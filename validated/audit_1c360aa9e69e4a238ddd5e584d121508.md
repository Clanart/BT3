## Finding

The codebase already hardened several path-derived actions with `resolveWithin()` (a symlink- and traversal-safe join, see `app/src/lib/path.ts:36-71`) — e.g. `openRepositoryFromUrl` in the deep-link handler [1](#0-0)  and the Copilot conflict file reader/writer [2](#0-1) [3](#0-2) . However, `revealInFileManager` — the function invoked from every "Show in Explorer/Finder" and "Open with Default Program" context-menu entry for working-directory and committed files — never received this guard.

### Title
Missing repository-boundary check before revealing/opening a git-status file path - (File: app/src/lib/app-shell.ts)

### Summary
`revealInFileManager` builds the target path with a plain `Path.join(repository.path, path)` and hands it straight to the OS shell, with no check that the resolved path stays inside the repository, unlike the `resolveWithin` guard applied to structurally similar untrusted-path flows elsewhere in the same codebase.

### Finding Description
`revealInFileManager` is the single implementation backing "Reveal in Finder/Explorer" for both working-directory changes and committed-file changes: [4](#0-3) 

Its own doc-comment on the interface explicitly warns "Do not use this method with non-validated paths" [5](#0-4) , yet every call site passes an unvalidated `file.path` straight through: [6](#0-5) [7](#0-6) [8](#0-7) 

The "Open with Default Program" path is worse: `onOpenItem`/`openFile` builds the same unvalidated `Path.join(repository.path, path)` and passes it to `shell.openExternal('file://' + fullPath)` [9](#0-8) [10](#0-9) , which lets the OS decide how to execute/open the resolved file.

`file.path` for `CommittedFileChange` comes from parsing `git log --name-status` output [11](#0-10)  — i.e., it is derived from tree-entry names inside a commit, which is data an attacker fully controls if the user fetches/clones from or checks out a commit contributed by that attacker (a fork, a malicious remote, a crafted branch/PR). None of the code that turns those tree paths into `CommittedFileChange.path`/`WorkingDirectoryFileChange.path` applies `resolveWithin`, `isAbsolute` rejection, or `sanitizeCloneName`-style component sanitization the way the URL deep-link handler and the Copilot conflict resolver do.

This is the exact "no address/ownership check before acting on an externally supplied identifier" pattern from the seed report: the NFT `flashAction` trusted the caller-supplied `collateralId`/`addr` without verifying provenance before performing a privileged transfer; here, Desktop trusts an attacker-influenced `file.path` string without verifying it resolves inside the repository before performing a privileged OS action (reveal-in-shell / open-with-default-program, which can execute the file).

### Impact Explanation
If a crafted commit/tree entry (or a rename/copy entry whose reported name is built from data outside Desktop's control) yields a `file.path` containing traversal segments (e.g. `../../../../Library/LaunchAgents/x.plist` or `..\..\..\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\x.exe`), then:
- "Reveal in Finder/Explorer" would open a file-manager window pointed outside the repository, and
- "Open with Default Program" would invoke `shell.openExternal('file://...')` on a path outside the repository, letting the OS default handler execute/open it.

This maps to file write/read outside the repo and potential code execution triggered purely by normal usage (browsing changed/committed files and clicking a context-menu item) after fetching attacker content — squarely in the accepted impact categories (attacker controls a cloned/fetched repository → code execution/file access outside the repo).

### Likelihood Explanation
Requires: (1) modern git's fsck/tree-entry validation to not fully block such a path from being represented as a `CommittedFileChange`/`WorkingDirectoryFileChange.path` in Desktop's own parsing layer, and (2) the user to interact with the context menu item after fetching/checking out the attacker's ref. I could not fully verify from local code alone whether dugite/libgit2's own checkout-time or log-parsing safeguards would already strip or reject `..`-containing tree paths before they ever reach `log.ts`/`status.ts` — that verification requires running the actual dugite/git binaries, which is outside the scope of static code inspection. What is verifiable and concrete is that `app-shell.ts`'s `revealInFileManager` and the "Open with Default Program" flow contain **no application-level defense-in-depth** comparable to `resolveWithin`, despite the file's own doc-comment demanding validated input — this is an inconsistency with the rest of the codebase's established mitigation pattern for this exact bug class, regardless of whether a particular git-level bypass currently exists.

### Recommendation
Add a `resolveWithin(repository.path, path)` check (mirroring `copilot-conflict-context.ts` and `dispatcher.ts`'s `openRepositoryFromUrl`) inside `revealInFileManager` and inside `onOpenItem`/`openFile`'s callers before constructing `fullPath`, refusing to reveal/open/execute anything that resolves outside the repository root, and treat any such occurrence as a hard error rather than a silent fallback.

### Proof of Concept
Not independently reproducible from static analysis alone (requires crafting a git commit whose tree entry survives dugite's fsck/log parsing with a `../`-laden name and confirming it flows unmodified into `CommittedFileChange.path`) — this would need to be validated in a running Desktop instance/background agent session with real git tooling, which I don't have access to here.

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}

/**
 * Map the raw status text from Git to an app-friendly value
 * shamelessly borrowed from GitHub Desktop (Windows)
 */
function mapStatus(
  rawStatus: string,
  oldPath: string | undefined,
  srcMode: string,
  dstMode: string
): PlainFileStatus | CopiedOrRenamedFileStatus | UntrackedFileStatus {
  const status = rawStatus.trim()
  const submoduleStatus = mapSubmoduleStatusFileModes(status, srcMode, dstMode)

  if (status === 'M') {
    return { kind: AppFileStatusKind.Modified, submoduleStatus }
  } // modified
  if (status === 'A') {
    return { kind: AppFileStatusKind.New, submoduleStatus }
  } // added
  if (status === '?') {
    return { kind: AppFileStatusKind.Untracked, submoduleStatus }
  } // untracked
  if (status === 'D') {
    return { kind: AppFileStatusKind.Deleted, submoduleStatus }
  } // deleted
  if (status === 'R' && oldPath != null) {
    return {
      kind: AppFileStatusKind.Renamed,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: false,
    }
  } // renamed
  if (status === 'C' && oldPath != null) {
    return {
      kind: AppFileStatusKind.Copied,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: false,
    }
  } // copied

  // git log -M --name-status will return a RXXX - where XXX is a percentage
  if (status.match(/R[0-9]+/) && oldPath != null) {
    return {
      kind: AppFileStatusKind.Renamed,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: status !== 'R100',
    }
  }

  // git log -C --name-status will return a CXXX - where XXX is a percentage
  if (status.match(/C[0-9]+/) && oldPath != null) {
    return {
      kind: AppFileStatusKind.Copied,
      oldPath,
      submoduleStatus,
      renameIncludesModifications: false,
    }
  }

  return { kind: AppFileStatusKind.Modified, submoduleStatus }
}
