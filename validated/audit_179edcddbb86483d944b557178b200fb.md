### Title
BEEFY consensus supermajority check counts raw vote entries instead of unique authority indices, allowing signature duplication to fake a 2/3+1 quorum - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` derives the supermajority participation threshold from `relayProof.signedCommitment.votes.length` without ever checking that the `authorityIndex` values inside those votes are distinct.

### Finding Description
`checkParticipationThreshold(sigLen, authoritySet.len)` at [1](#0-0)  gates BEEFY consensus acceptance on `sigLen >= 2/3*len + 1`, where `sigLen = relayProof.signedCommitment.votes.length` — the raw count of `Vote` structs supplied in calldata. This mirrors the reported bug class: an array-derived quantity is trusted for a security-critical check without validating an implicit invariant across the array's contents (here, uniqueness of `authorityIndex` rather than mere array length, but the same "unchecked array assumption" root cause).

Each vote is then turned into a `MerkleMultiProof.Leaf{index: vote.authorityIndex, hash: keccak256(authority)}` at [2](#0-1) , and the resulting `authorities` array (still of length `sigLen`, with no dedup) is passed into `MerkleMultiProof.VerifyProof`. Nothing in this function, nor in `checkParticipationThreshold`, rejects two (or many) `Vote` entries that carry the same `authorityIndex`/same signature. If a single authority's one valid signature is repeated `k` times in the `votes` array, `sigLen` is inflated by `k` while the number of distinct authorities that actually attest to the commitment stays the same. An attacker who has captured just over 1/3 of valid authority signatures (a normal, non-adversarial situation right at the safety boundary) can pad the `votes` array with duplicates of the signatures they already have to artificially cross the `2/3+1` threshold and get `handleConsensus`/`verify` to accept the state update.

By contrast, the reference off-chain implementation of the same protocol in this repo, `modules/consensus/beefy/verifier/src/lib.rs`, computes `authority_indices` the same unguarded way (also no uniqueness check) — so this is not a one-off Solidity slip but a shared unchecked-array assumption in both the EVM and off-chain BEEFY verifiers: [3](#0-2) . The Merkle multi-proof only proves each attested authority is a member of the authority set; it enforces nothing about vote uniqueness, so it cannot compensate for the missing dedup.

### Impact Explanation
This directly hits the "false remote state acceptance" pivot: `EcdsaBeefy.verify` is the consensus client used by `HandlerV2.handleConsensus` to update `stateMachineCommitment`, which every downstream request/response/timeout handler in `HandlerV2.sol` trusts via Merkle proofs against the stored `overlayRoot`/`stateRoot` (see `handlePostRequests`, `handleGetResponses` at [4](#0-3) ). If a state update can be pushed through with sub-quorum real signatures, an attacker gains the ability to commit a forged/malicious state root, which can then be used to fabricate valid-looking membership proofs for arbitrary requests/responses, leading to unauthorized dispatch, fund loss, or double-settlement on the destination host.

### Likelihood Explanation
Requires the attacker to hold or observe valid signatures from at least ~1/3 of the current relay-chain authority set (a realistic scenario near the safety boundary of any BFT quorum, not requiring a malicious relayer/prover or admin key) and then simply resubmit those same signatures multiple times with different array slots to inflate `sigLen`. Since `votes` is fully attacker-supplied calldata and no on-chain code enforces distinct `authorityIndex` values, exploitation only requires crafting the calldata array — no privileged role, front-running, or off-chain collusion beyond obtaining signatures that are already circulating for a legitimate near-threshold commitment.

### Recommendation
Enforce uniqueness of `vote.authorityIndex` (and/or recovered `authority` address) before computing `sigLen`/the participation check — e.g., require votes sorted by `authorityIndex` with strict monotonic increase, or track a bitmap/seen-set of indices and revert on duplicates. Apply the equivalent fix to `verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs` to keep both verifiers consistent.

### Proof of Concept
1. Assume authority set size `N = 100`; quorum threshold is `67`.
2. Attacker (or anyone monitoring gossip) collects `34` genuine signatures for a commitment (just over 1/3, below quorum).
3. Attacker builds `relayProof.signedCommitment.votes` with `34` unique `Vote`s plus `33` duplicate entries reusing the same `authorityIndex`/`signature` pairs already collected, making `votes.length == 67`.
4. `sigLen = 67` passes `checkParticipationThreshold(67, 100)` (`67 >= 2*100/3+1 = 67`).
5. The `authorities` Merkle-multi-proof leaves are duplicated accordingly; since each duplicated leaf corresponds to a genuinely valid authority-set member, `MerkleMultiProof.VerifyProof` succeeds against `authoritySet.root` with a valid (if redundant) proof.
6. `verifyMmrUpdateProof` returns successfully and `EcdsaBeefy.verify` accepts the state update with only 34 real independent signers, well under the intended 67-signer safety threshold.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
