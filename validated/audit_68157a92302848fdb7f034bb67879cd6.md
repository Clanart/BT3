## Analysis

The C4 bug's core pattern is: a **shared accounting pool keyed independently of the entity that "owns" a slice of it**, where one actor's action against the pool can drain value that was meant to still back another actor's claim, causing wrong-beneficiary payout / fund loss. I found a structurally identical pattern in Hyperbridge's `IntentGatewayV2` same-chain partial-fill/escrow accounting.

### Title
Same-chain partial-fill escrow drain via shared input-token pool keyed by token, not by output index - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_orders[commitment][token]` is a single running balance per `(commitment, token)`, populated at `placeOrder` and drained in `_withdraw`. `placeOrder` explicitly rejects duplicate **output** tokens using transient-storage dedup [1](#0-0) , but it never rejects duplicate **input** tokens across `order.inputs[]`, nor enforces `inputs.length == output.assets.length`. `_fillSameChain` assumes a strict 1:1 positional mapping between `order.output.assets[i]` and `order.inputs[i]` when computing and releasing escrow [2](#0-1) .

### Finding Description
When an output pair `i` reaches `amountFilled == totalRequired` (its "final" fill), the contract does not release the proportional slice for index `i` — it releases **the entire current balance** of `_orders[commitment][inputs[i].token]`:
```
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

If two output-asset entries `i` and `j` are backed by the **same input token** (allowed, since only output-token duplicates are rejected at placement), the shared `_orders[commitment][token]` balance covers both legs. Whichever output leg is *completed first* triggers the "full balance" branch and drains the entire pooled escrow for that token — including the portion economically earmarked for the other, still-unfilled leg — to the first solver.

`_withdraw` confirms the pool is keyed purely by `(commitment, token)` with no per-index bookkeeping: it decrements `_orders[body.commitment][token]` by whatever amount is requested and reverts with `UnknownOrder()` only if the stored balance is already zero [4](#0-3) . There is no mechanism keeping the "final-fill" release capped to the index's fair share.

### Impact Explanation
An unprivileged solver reachable through the public `fillOrder` entrypoint can extract more escrowed input tokens than the order's economics justify, at the expense of whichever party (the order creator, or another solver settling the remaining leg) was still owed that escrow. When the second leg is later filled, `_orders[commitment][token]` is now short, and the withdrawal for that leg reverts with `UnknownOrder()` — turning the remaining fill into either a DoS on the honest solver/beneficiary or, depending on fill ordering, a direct wrong-beneficiary/wrong-amount fund transfer. This satisfies the bounty's "stealing or loss of funds" / "transaction manipulation" impact classes via a public entrypoint with no privileged actor involved.

### Likelihood Explanation
No malicious peer, relayer, or governance action is required — only a normal `Order` with two output-asset entries sharing one input token (nothing in `placeOrder` prevents this) and two ordinary `fillOrder` calls from independent solvers, exactly the kind of interaction the partial-fill feature is designed to support. The existing partial-fill test suite only exercises the single-input/single-output-pair case (e.g. `testPartialFill_RoundingDustReleasedToFinalSolver`) and never a multi-output-pair order sharing one input token, so this path is untested.

### Recommendation
Track escrow release per `(commitment, outputToken-index)` rather than per raw `_orders[commitment][inputToken]` balance, or explicitly reject orders where the same input token backs more than one output-asset entry (mirroring the existing duplicate-output-token check). Alternatively, cap the "final fill" release to the proportional share still attributable to index `i` (`totalRequired`'s contribution), never to the full pooled balance.

### Proof of Concept
1. User places an order with `output.assets = [ {DAI, 100}, {USDT, 100} ]` and `inputs = [ {USDC, 100}, {USDC, 100} ]` (same input token, `USDC`, backing both legs) — accepted, since only output-token duplicates are checked. `_orders[commitment][USDC]` accumulates to 200 USDC.
2. Solver A calls `fillOrder` supplying only the DAI leg (`i=0`) with the full 100 DAI. `amountFilled == totalRequired` for `i=0`, so `escrowedAmount = _orders[commitment][USDC]` = 200 (the *entire* pool), which is transferred to Solver A instead of the fair 100.
3. `_orders[commitment][USDC]` is now 0.
4. Solver B later fully fills the USDT leg (`i=1`, 100 USDT) expecting 100 USDC in return; `_withdraw` finds `_orders[commitment][USDC] == 0` and reverts `UnknownOrder()`, leaving Solver B unable to collect the input tokens they are entitled to despite having delivered output tokens to the beneficiary.

**Note:** I did not have access to the exact `placeOrder` code that populates `_orders[commitment][token]` from `order.inputs[]` (the read was truncated before that section), so the exact summation behavior for duplicate input tokens at placement time is inferred from the consistent `(commitment, token)`-keyed accumulator pattern used everywhere else (`_withdraw`, `_cancelSameChain`). A Devin session with full file access should confirm this before treating the PoC numbers as exact.
