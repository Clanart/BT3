### Title
Tokenfactory denom allow-list update can permanently freeze holders' balances with no exit path - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
A tokenfactory denom admin can call `MsgUpdateDenom` (or set an allow list at `MsgCreateDenom` time) to install a `DenomAllowList` that omits an existing holder's address. Because bank transfer logic (`IsInDenomAllowList`) gates both sending and receiving for `factory/`-prefixed denoms, and the tokenfactory `MsgBurn` handler only allows the *admin* to burn (not the holder itself), an excluded holder's balance becomes permanently unmovable and unburnable — exactly the "supported token removed, existing balance can no longer be withdrawn" pattern described in the referenced Biconomy finding.

### Finding Description
`MsgUpdateDenom` lets the denom admin freely rewrite the `DenomAllowList` for their factory denom at any time via `server.bankKeeper.SetDenomAllowList`, with no restriction preventing removal of addresses that already hold a balance: [1](#0-0) 

The bank module enforces this allow list on every `MsgSend`/`MsgMultiSend` for both the sender and the receiver: [2](#0-1) 

`IsInDenomAllowList` returns `false` for any address not explicitly present in a non-empty allow list, which blocks the transfer entirely: [3](#0-2) 

Crucially, unlike a normal ERC20/CW20 holder who can always self-redeem or burn their own tokens, tokenfactory's `MsgBurn` only allows the **denom admin** to burn, and it burns from the admin's own address, not an arbitrary holder's: [4](#0-3) 

So once a holder is excluded from the allow list:
- They cannot `Send`/`MultiSend` the coins to any address (blocked by `IsInDenomAllowList`).
- They cannot burn the coins themselves (no self-burn path in the tokenfactory module).
- The only escape is if the same admin who excluded them chooses to add them back — there is no protocol-level safeguard analogous to the Biconomy report's recommendation ("allow withdrawals even if the token was unsupported").

This directly mirrors the reported bug class: a privileged party (TokenManager owner / here, the tokenfactory denom admin) retroactively revokes support for a token/denom, and users who already hold balances acquired while the denom was unrestricted have no way to reclaim or move their funds.

### Impact Explanation
Any holder of a `factory/{admin}/{subdenom}` balance can have their funds permanently frozen at the sole discretion of the denom admin, with no built-in recovery mechanism (no self-burn, no allow-list bypass, no timelock/grace period). This is a permanent freezing of user funds, matching the "permanent freezing" impact bar for this scan.

### Likelihood Explanation
The action requires only the tokenfactory denom admin (an in-scope "tokenfactory denom creator" actor per this scan's allowed entities) to submit a single `MsgUpdateDenom` transaction. No governance, no consensus-level compromise, and no multi-party coordination is required — an admin can trivially exclude a specific address (accidentally via misconfiguration, or deliberately) after that address has already accumulated a balance.

### Recommendation
- Allow any holder to burn their own factory-denom balance directly (independent of the denom admin and independent of the allow list), giving users an exit path even if excluded from the send allow list, mirroring the Biconomy mitigation of "allow withdrawals even if unsupported."
- Alternatively/additionally, prevent `SetDenomAllowList` from silently revoking transfer rights from addresses that already hold a non-zero balance of that denom, or require a delay/notice period before an allow-list update takes effect for existing holders.

### Proof of Concept
1. Denom admin `A` creates `factory/A/X` via `MsgCreateDenom` with no allow list (or a permissive one), then mints/sends coins to holder `B` via ordinary transfers.
2. `A` calls `MsgUpdateDenom` with `AllowList = {Addresses: [A]}` (excluding `B`), invoking `server.bankKeeper.SetDenomAllowList(ctx, "factory/A/X", allowList)` (`x/tokenfactory/keeper/msg_server.go:80-85`).
3. `B` attempts `MsgSend` of their `factory/A/X` balance to any address; `k.IsInDenomAllowList(ctx, B, ...)` returns `false` and the tx fails with `"B is not allowed to send funds"` (`sei-cosmos/x/bank/keeper/msg_server.go:42-45`).
4. `B` attempts to escape by burning; `MsgBurn` requires `msg.Sender == authorityMetadata.GetAdmin()` (`x/tokenfactory/keeper/msg_server.go:136-138`), so `B` (not the admin) is rejected with `ErrUnauthorized`.
5. `B`'s balance of `factory/A/X` is now permanently stuck: it cannot be sent, received elsewhere, or burned by `B`, with recovery possible only if admin `A` unilaterally decides to re-add `B` to the allow list.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil

func (server msgServer) Burn(goCtx context.Context, msg *types.MsgBurn) (*types.MsgBurnResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Amount.GetDenom())
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	err = server.burnFrom(ctx, msg.Amount, msg.Sender)
	if err != nil {
		return nil, err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgBurn,
			sdk.NewAttribute(types.AttributeBurnFromAddress, msg.Sender),
			sdk.NewAttribute(types.AttributeAmount, msg.Amount.String()),
		),
	})

	return &types.MsgBurnResponse{}, nil
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}
