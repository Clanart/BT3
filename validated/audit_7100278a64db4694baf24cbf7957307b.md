### Title
`x/epoch` module never registers its transaction `MsgServer`, silently dropping all Epoch module messages - ([File: x/epoch/module.go])

### Summary
The `x/epoch` module defines a full protobuf `Msg` service (`tx.pb.go`) with a concrete implementation in `x/epoch/keeper/msg_server.go`, but its `RegisterServices` callback only wires up the `QueryServer`, never the `MsgServer`. This is the exact same bug class as the referenced canto `x/govshuttle` finding: a module that can emit transactional messages but never binds them to baseapp's `MsgServiceRouter`.

### Finding Description
`AppModule.RegisterServices` for the epoch module only calls `types.RegisterQueryServer`: [1](#0-0) 

However, the module ships a real gRPC `Msg` service definition and server implementation: [2](#0-1) [3](#0-2) 

The module's interfaces are registered as a `Msg` service via `msgservice.RegisterMsgServiceDesc`, which is exactly how Cosmos SDK identifies protobuf `sdk.Msg` types that must be routed through the `MsgServiceRouter`: [4](#0-3) 

Because `RegisterServices` never calls `types.RegisterMsgServer(cfg.MsgServer(), keeper.NewMsgServerImpl(...))`, baseapp's `MsgServiceRouter` (`sei-cosmos/baseapp/msg_service_router.go`) has no registered handler entry for any `Msg` defined in `x/epoch/types/tx.pb.go`. Any transaction containing one of these epoch messages will fail to route at execution time with an "unrecognized message" / "no handler" style error, exactly mirroring the `x/govshuttle` `MsgLendingMarketProposal` / `MsgTreasuryProposal` bug where a module keeps a legacy `Route()`/`NewHandler` wiring (`x/epoch/handler.go`) but never registers the modern `MsgServer`, so the primary protobuf message dispatch path is dead code.

### Impact Explanation
Any unprivileged or privileged actor submitting a transaction that includes an `x/epoch` `Msg` (as defined in `x/epoch/types/tx.pb.go` and handled in `x/epoch/keeper/msg_server.go`) will have that message fail to execute — the transaction either errors out entirely or the specific message silently fails to reach its intended handler, depending on how it interacts with any surviving legacy `Route()` fallback. This breaks the functional guarantee of the module: message-based state transitions the module was designed to support become unreachable. This matches the "Mid" severity classification given to the original `govshuttle` finding — no funds are directly at risk, but a whole category of the module's core functionality (its transactional message-handling path) is non-functional.

### Likelihood Explanation
This is deterministic and always reproducible: any transaction targeting `x/epoch`'s `Msg` service will hit this missing registration on every node running this exact code, with no special conditions or race required.

### Recommendation
Add the missing `RegisterMsgServer` call in `x/epoch/module.go`'s `RegisterServices`, mirroring the pattern used correctly elsewhere (e.g. `sei-cosmos/x/auth/vesting/module.go`):
```go
func (am AppModule) RegisterServices(cfg module.Configurator) {
    types.RegisterMsgServer(cfg.MsgServer(), keeper.NewMsgServerImpl(am.keeper))
    types.RegisterQueryServer(cfg.QueryServer(), am.keeper)
}
```

### Proof of Concept
1. Construct and broadcast a transaction wrapping any `Msg` type defined in `x/epoch/types/tx.pb.go` (implemented by `x/epoch/keeper/msg_server.go`).
2. Because `cfg.MsgServer()` is never passed to `types.RegisterMsgServer` in `x/epoch/module.go`, baseapp's `MsgServiceRouter` has no route table entry for this message type.
3. Submit the transaction to a running node; observe that the message fails to be routed/executed as intended, confirming the module's `Msg` service is unreachable via the standard transaction execution path. [1](#0-0) [4](#0-3)
