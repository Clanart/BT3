### Title
Integer overflow in payment/fee arithmetic lets crafted amounts bypass the `NotEnoughFunds` check and produce an unspendable signed transaction (or panic) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums input and payment amounts into `u64` and adds the computed fee using unchecked wrapping arithmetic. Overflow wraps the comparison value, defeating the `NotEnoughFunds` check — the analog of the SIXEL decoder's signed-integer overflow during size arithmetic, mapped onto Serai's satoshi-amount math over values derived from attacker-influenced inputs.

### Finding Description
In `SignableTransaction::new`, all amounts are `u64` satoshis and are combined with plain `+` / `sum()` arithmetic:

- `input_sat` = `sum::<u64>()` over each `ReceivedOutput`'s value (line 175) [1](#0-0) 
- `payment_sat` = `sum::<u64>()` over the requested payments (line 187) [2](#0-1) 
- The solvency check `if input_sat < (payment_sat + needed_fee)` uses unchecked addition (line 215) [3](#0-2) 
- `fee()` later computes `sum(inputs) - sum(outputs)` with a bare subtraction that panics on underflow (lines 139–140) [4](#0-3) 

Each individual payment amount is only checked against `DUST` (546 sats); there is no upper bound and no check on the *count* of payments (lines 165–169). A payment set whose amounts sum to more than `u64::MAX` (e.g. three payments of ~`1.8e19` sats) makes `payment_sat` wrap to a small value in release builds (Rust's default `overflow-checks = off`), so `payment_sat + needed_fee` is small and the `input_sat < payment_sat + needed_fee` check passes even though the declared outputs vastly exceed the inputs. The resulting `SignableTransaction` is handed to `TransactionSignMachine::sign`, which has the whole threshold set sign a `taproot_key_spend_signature_hash` for a transaction Bitcoin consensus will never accept (outputs > inputs and > 21M BTC), and any subsequent call to `fee()` underflows and panics. The same unchecked pattern exists in `fee_per_vbyte * vbytes` (line 206) and `fee_per_vbyte * vbytes_with_change` (line 227), where a wrapped product makes `needed_fee` collapse toward zero, and in the change path's `payment_sat + fee_with_change` (line 228) [5](#0-4) .

### Impact Explanation
An unintended/invalid transaction is carried through the full FROST signing pipeline: `multisig()` builds per-input `AlgorithmMachine`s, `sign()` produces shares over `Prevouts::All` sighashes, and `complete()` assembles witnesses for a transaction that is consensus-invalid and unbroadcastable (lines 273–285, 373–397, 417–428) [6](#0-5) . This stalls the signing plan for those inputs and, via the underflowing `fee()` subtraction, gives a panic-based denial of service on any code path that inspects the constructed transaction. Where payments/amounts originate from user-initiated send instructions, an unprivileged party supplying crafted amounts reaches this path through transaction data they cause to be signed.

### Likelihood Explanation
The arithmetic is straightforwardly reachable: no bound other than `DUST` is applied to individual payment amounts or to `payments.len()`, and the summation/ addition uses primitive `u64` ops with no `checked_*` guards. Exploitation requires a plan carrying absurd amounts that are still ≥ dust — there is no consensus-validity cap enforced in this code, so nothing in the function rejects them. The primary caveat is that the exact upstream path feeding `payments` is integrator/plan-driven; the bug is real in the in-scope code, but the attacker-controllability of `payments` depends on how callers populate it. In debug builds the overflow panics instead of wrapping, still a DoS.

### Recommendation
Use `checked_add`/`checked_sum` (e.g. `iter().try_fold(0u64, u64::checked_add)`) for `input_sat` and `payment_sat`, `checked_mul` for `fee_per_vbyte * vbytes`, and `checked_add` for `payment_sat + needed_fee` and `payment_sat + fee_with_change`, mapping `None` to `TransactionError::NotEnoughFunds`/`TooMuchData`. Make `fee()` use `checked_sub` or store the fee computed at construction.

```rust
    (script1, u64::MAX - 10),                          // each >= DUST, passes check
    (script2, u64::MAX - 10),
];
// payment_sat wraps to u64::MAX - 22 → still huge; use 3 payments of ~6.15e18
// so payment_sat wraps below input_sat:
let payments = vec![
    (script1, 6_150_000_000_000_000_000u64),
    (script2, 6_150_000_000_000_000_000u64),
    (script3, 6_150_000_000_000_000_000u64),
];
// payment_sat = 18.45e18 wraps to ~7.7e3 < input_sat
// `input_sat < payment_sat + needed_fee` is false → NotEnoughFunds skipped
// SignableTransaction is built; outputs (~u64::MAX range) >> inputs.
// tx.fee() then underflows: 1_000_000 - huge_sum -> panic.
// TransactionSignMachine::sign still produces shares signing the invalid TX.
```

Note: I verified the wrapping arithmetic and missing bounds directly in `send.rs`, but did not have iterations remaining to trace the exact caller path that populates `payments` from user-submitted send plans; the finding is solid as an arithmetic-overflow/DoS in the in-scope wallet code, with attacker reachability contingent on the plan pipeline accepting unbounded payment amounts.
