This confirms the finding. Key facts established:

- The payout tx (`create_payout_txhandler` at `core/src/builder/transaction/operator_reimburse.rs:407-436`) has three outputs: user payout (index 0), anchor (index 1), and an `op_return_txout` (index 2) that embeds `operator_xonly_pk.serialize()` — the identifier used later to determine which operator "fronted" the withdrawal and is eligible for reimbursement.
- The user's signature uses `TapSighashType::SinglePlusAnyoneCanPay`, enforced at `core/src/rpc/parser/operator.rs:182-187`. This sighash type, per BIP341 semantics (confirmed by the code path in `circuits-lib/src/bridge_circuit/mod.rs:801-810` which explicitly skips committing to `sha_outputs` when sighash is `Single`/`None`, wait actually `Single` still commits output at same index) — the signature legally only commits to input 0 (ANYONECANPAY) and output 0 (SIGHASH_SINGLE covers only the output at the same index as the signed input). Outputs 1 and 2 (anchor, and critically the **OP_RETURN with `operator_xonly_pk`**) are **not covered by the signature at all**.
- The wallet-funding path in `crates/clementine-tx-sender/src/rbf.rs` (`create_funded_psbt`) explicitly preserves arbitrary existing outputs including OP_RETURN (lines 183-190) while adding funding inputs — the tx structure with attacker-chosen trailing outputs survives funding/broadcast.

Because the OP_RETURN operator-attribution output is unauthenticated (not covered by the withdrawer's `SinglePlusAnyoneCanPay` signature), any party who obtains the signed withdrawal data (given "off-chain to operators" per the doc comment, and necessarily visible once broadcast/relayed in the mempool before confirmation) can rebroadcast a competing version of the same payout transaction with the identical signed input/output-0 but a **different OP_RETURN naming an arbitrary registered operator's xonly pubkey** as the payer — front-running the legitimate operator's broadcast. If the substituted transaction confirms first, the framework misattributes the payout to the named operator, letting that (uninvolved) operator's automated `PayoutCheckerTask` proceed to kick off and be reimbursed via `create_reimburse_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:341-385`) from the vault's `bridge_amount`, even though they never fronted the withdrawal — matching the report's "value transferred/attributed to the wrong/unintended party" bug class, but here breaking the "operator credited versus the party that paid" binding explicitly called out as in-scope.

### Title
Unsigned OP_RETURN operator-attribution output in payout transactions allows misattributing reimbursement credit to an operator who never fronted the withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` embeds the fronting operator's x-only public key in an `OP_RETURN` output that is outside the coverage of the withdrawer's `SinglePlusAnyoneCanPay` signature. The signature only binds input 0 and output 0 (the user's payment), leaving the OP_RETURN (and anchor) output fully malleable by any third party who has seen the signed data.

### Finding Description
`core/src/builder/transaction/operator_reimburse.rs:407-436` builds `create_payout_txhandler` with three outputs: the user payout (index 0), an anchor (index 1), and `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))` (index 2). The single witness attached is the user's `SinglePlusAnyoneCanPay` signature over input 0 (`txhandler.set_p2tr_key_spend_witness(&user_sig, 0)`).

`core/src/rpc/parser/operator.rs:182-187` strictly enforces this sighash type on the incoming `WithdrawParams.input_signature`. Under BIP341 `SIGHASH_SINGLE | ANYONECANPAY`, the signature commits to: (a) the specific input being spent, and (b) only the output at the same index as that input (index 0). It provides **no commitment whatsoever** over any other outputs, including the OP_RETURN carrying `operator_xonly_pk`.

`core/src/operator.rs:620-637` builds this handler with `self.signer.xonly_public_key` and verifies only that the user's signature is valid for input 0/output 0 — it never authenticates that the OP_RETURN correctly reflects the actual broadcasting operator. The RBF funding path (`crates/clementine-tx-sender/src/rbf.rs`, `create_funded_psbt`) preserves the OP_RETURN output verbatim while adding funding inputs.

Once mined, `core/src/verifier.rs:2313-2342` (`update_finalized_payouts`) parses this OP_RETURN from the confirmed transaction and treats its content as authoritative "who paid" data, persisting it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) into `withdrawals.payout_payer_operator_xonly_pk`. This value then gates:
- `is_kickoff_malicious` (`core/src/verifier.rs:1887`) — determines whether a kickoff by a given operator is considered fraudulent.
- `send_asserts` (`core/src/operator.rs:1290`) — requires the payer field to match the kicking-off operator.
- `validate_payer_is_operator` (`core/src/operator.rs:1711`) and `get_reimbursement_txs`/`PayoutCheckerTask` (`core/src/task/payout_checker.rs:41-47`) — automatically drives an operator's own reimbursement pipeline (Round → Kickoff → Reimburse) for whichever withdrawal DB says they paid.

Because the OP_RETURN is unauthenticated, any party who has visibility of the signed withdrawal data (which, per the protocol design comment, is handed "off-chain to operators" and would additionally become visible to anyone the moment it is broadcast/relayed pre-confirmation) can construct and race-broadcast an alternate payout transaction reusing the identical signed input/output-0, but substituting a different, arbitrary registered operator's x-only public key into the OP_RETURN. If this variant confirms, the bridge's ground-truth record of "who fronted this withdrawal" becomes wrong, permanently and irreversibly (this data drives the entire disprove/challenge/reimbursement machinery downstream).

This breaks the exact binding called out in the rules: "the operator credited versus the party that paid."

### Impact Explanation
If a party substitutes a legitimate/uninvolved operator's key into the OP_RETURN, that operator's own automation (`PayoutCheckerTask`) will subsequently believe it fronted a withdrawal it never paid, and will proceed to send Round/Kickoff/Reimburse transactions to claim `bridge_amount` from the corresponding move-to-vault UTXO — resulting in "an operator reimbursed for a payout it never funded," one of the explicitly listed Critical impacts. Equally, the operator who actually paid the withdrawal loses their ability to be reimbursed for that payout since the DB record no longer points to them (`validate_payer_is_operator` will reject their reimbursement attempts, since `payer_xonly_pk != self.signer.xonly_public_key`), matching "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
Exploitability requires only visibility of a valid signed withdrawal (available to the honest operator broadcasting it, and to anyone monitoring the mempool prior to confirmation, since this is a normal, non-privileged network position) and the ability to race-broadcast a variant transaction with a modified OP_RETURN before the honest operator's version confirms — well within reach of an unprivileged attacker with modest transaction-relay/mempool visibility and RBF/fee-bumping capability, and does not require any operator, verifier, or other privileged role.

### Recommendation
Bind the fronting operator's identity to the signed portion of the payout transaction — e.g., have the operator/OP_RETURN commitment covered by a signature (or MuSig aggregate) that is authenticated as belonging to the specific operator, or require `SIGHASH_ALL` (or an equivalent commitment covering all outputs) for the component identifying the payer, so that no third party can alter payer attribution post-signing. Alternatively, do not rely on the OP_RETURN content alone; require the broadcasting operator to separately prove (e.g., via a per-operator signed acknowledgment tied to the exact payout txid) that they are the payer before crediting reimbursement eligibility.

### Proof of Concept
1. An operator `A` obtains from the aggregator/user a valid `WithdrawParams` with `input_signature` of type `SinglePlusAnyoneCanPay` covering `input_outpoint`/`output_script_pubkey`/`output_amount` (`core/src/rpc/parser/operator.rs:161-203`).
2. Operator `A` calls `withdraw`/`internal_withdraw` (`core/src/rpc/operator.rs:168-190`), which builds and broadcasts a payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) with OP_RETURN = `A`'s xonly pubkey.
3. Before this transaction confirms, an unprivileged attacker (or any node observing the mempool) constructs an alternate transaction reusing the identical signed input (index 0) and output (index 0) — both valid under `A`'s signature since only these are committed to — but replaces output 2 (OP_RETURN) with a different registered operator `B`'s xonly pubkey, and independently funds/fee-bumps this variant to outcompete `A`'s broadcast (e.g., via a higher-fee RBF replacement or by winning the race in relay/mempool).
4. The attacker's variant confirms. `core/src/verifier.rs:2313-2342` parses the confirmed tx's OP_RETURN, extracting operator `B`'s pubkey, and `update_payout_txs_and_payer_operator_xonly_pk` records `B` (not `A`) as `payout_payer_operator_xonly_pk` for this withdrawal.
5. Operator `B`'s automated `PayoutCheckerTask` (`core/src/task/payout_checker.rs:41-47`) subsequently picks up this "unhandled payout" attributed to itself and proceeds through `handle_finalized_payout` → Kickoff → Reimburse, receiving `bridge_amount` from the corresponding move-to-vault UTXO, despite never having fronted any funds to the withdrawing user. Operator `A`, who actually paid the user, is now blocked from reimbursement by `validate_payer_is_operator` (`core/src/operator.rs:1711`), since the DB no longer attributes the payout to them. pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}
