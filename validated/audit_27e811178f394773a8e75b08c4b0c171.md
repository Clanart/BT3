### Title
`validate_payer_is_operator` trusts unauthenticated OP_RETURN payer attribution, letting an attacker force a victim operator's automation to claim reimbursement for a payout it never funded - (File: `core/src/operator.rs`)

### Summary
`Operator::validate_payer_is_operator` (core/src/operator.rs:1687-1740) enforces `payer_xonly_pk == self.signer.xonly_public_key` using a value that originates solely from an unauthenticated OP_RETURN output in the payout transaction, written by `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2352). Because the OP_RETURN pubkey is not covered by the user's `SinglePlusAnyoneCanPay` signature and not checked against who actually funded/broadcast the payout, an attacker who fronts their own withdrawal can attribute it to a victim operator, and that operator's automation (`PayoutCheckerTask` / `handle_finalized_payout`) will treat the payout as its own and proceed toward reimbursement.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk_recorded == xonly_pk_that_actually_broadcast_and_funded_the_payout_tx`.

- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the payout tx with a single keyspend input (the user's committed withdrawal UTXO, signed by the user with `SinglePlusAnyoneCanPay`) and appends an `op_return_txout(operator_xonly_pk)` output that is **not covered by that sighash flag** (it only commits to input 0 / output 0).
- `Operator::withdraw` (core/src/operator.rs:560-637) shows any caller who owns the withdrawal UTXO's key can supply `in_signature`, `in_outpoint`, `out_script_pubkey`, `out_amount` via the `WithdrawParams` gRPC message and have any operator's `self.signer.xonly_public_key` embedded in the OP_RETURN — this same construction is reachable by an attacker broadcasting their own crafted payout transaction directly to Bitcoin without going through any operator at all, since the OP_RETURN byte content is fully attacker-chosen.
- `Verifier::update_finalized_payouts` (core/src/verifier.rs:2313-2342) parses that OP_RETURN with `parse_op_return_data` / `XOnlyPublicKey::from_slice` and writes whatever pubkey it finds into `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:198-251) — with no signature or funding-source check.
- `Operator::validate_payer_is_operator` (core/src/operator.rs:1692-1719) later reads this value via `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` (core/src/database/verifier.rs:315-346) and only compares it to `self.signer.xonly_public_key`; it has no independent way to verify the payout tx's funding inputs.
- `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111) selects unhandled payouts filtered by `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` — the same forged column — and calls `handle_finalized_payout`, driving the victim operator's automation toward kickoff/reimbursement.
- `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1914) uses the identical `payout_info.operator_xonly_pk_opt` column to decide whether a kickoff is malicious, so it offers no independent cross-check against the forged attribution — the same root-cause data poisons both the operator-side gate and the verifier-side gate.

Because both the operator's own guard and the verifier's malicious-kickoff check derive from the same forgeable database column populated straight from OP_RETURN bytes, an attacker who funds and broadcasts their own payout transaction (fronting a legitimate Citrea withdrawal with their own BTC) but stamps a victim operator's x-only pubkey in the OP_RETURN can make the victim's automation believe it fronted the payout.

### Impact Explanation
The victim operator's automation is driven, without its consent or action, into the kickoff/reimbursement path for a payout it never funded. If this proceeds to completion, the operator is reimbursed (from the round/collateral or bridge deposit funds) for money it did not spend — matching the Critical category "an operator reimbursed for a payout it never funded." This is repeatable per withdrawal/deposit and can target any operator whose x-only pubkey is public (all operator pubkeys are public protocol data), so the blast radius spans every operator and every withdrawal processed by the bridge.

### Likelihood Explanation
Preconditions: the attacker must be able to withdraw on Citrea for a UTXO they control and broadcast a Bitcoin payout transaction — both explicitly within the unprivileged attacker capabilities (deposit, withdraw, choose UTXO/signature/sighash flag, broadcast transactions). Cost is limited to the fee-fronted withdrawal amount the attacker itself chooses to pay out (they are paying the user leg themselves) plus Bitcoin fees; no operator or verifier key material is needed. The attack is fully repeatable across deposits/withdrawals and requires no race condition beyond normal chain confirmation, making it straightforward to reproduce deterministically in a regtest/test environment.

### Recommendation
Do not derive payer attribution solely from the OP_RETURN payload. Bind the payout's operator attribution to something authenticated, e.g.: require the payout's fee-input(s)/change output to be provably controlled by the claiming operator's wallet, or have the operator co-sign/commit to the payout via a mechanism that Verifiers and the operator's own `validate_payer_is_operator` can cryptographically verify (rather than trusting arbitrary OP_RETURN bytes), and reject payouts whose attributed operator cannot be corroborated by such authenticated data.
