### Title
Path‑containment check uses raw string `startsWith` instead of path‑boundary comparison, allowing sibling‑directory escape - (File: app/src/lib/path.ts)

### Summary
The Pyth‑oracle report is a "boundary/scale invariant is computed incorrectly" bug: an off‑by‑exponent calculation silently breaks the guarantee that the output value stays within the intended magnitude. The direct analog in `desktop--014` is `resolveWithin()` in `app/src/lib/path.ts`, whose containment guarantee ("resolved path is guaranteed to reside at, or underneath this path") is enforced with a raw string prefix check that has no path‑separator boundary, so it silently accepts paths that merely share a *textual* prefix with the root rather than actually being underneath it.

### Finding Description
`_resolveWithin` computes the final decision with: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a pure character comparison with no notion of path segment boundaries. If the repository's root directory name is itself a prefix of a sibling directory name (a very common real‑world pattern: `repo` / `repo-secrets`, `app` / `app-backup`, `project` / `project.bak`, `test` / `test-credentials`), then a relative path containing `..` segments that walks up one level and back down into that sibling directory will produce a `realResolved` value that textually starts with `realRoot` even though it is a completely different directory tree.

Example: `rootPath = "/Users/victim/Documents/GitHub/repo"`, and a caller-supplied relative segment `"../repo-secrets/id_rsa"`. `path.resolve` produces `/Users/victim/Documents/GitHub/repo-secrets/id_rsa`, which is **not** under `repo`, yet `"...repo-secrets/id_rsa".startsWith("...repo")` is `true`, so the function returns the escaped path as "safe."

This is the same class of bug as the oracle report: a guard that is supposed to bound a value to a scale/region uses an incomplete formula (missing boundary term — here, a missing separator check), so it silently lets out‑of‑range values (here, out‑of‑repo paths) pass validation.

The existing regression tests in `app/test/unit/path-test.ts` only cover `..`-then-back-into-the-same-root cases and symlink escapes, not this sibling‑prefix case, so nothing currently exercises or catches it: [2](#0-1) 

`resolveWithin` is treated as a security boundary and used to gate several attacker‑influenced paths:
- Copilot merge‑conflict context builder, which reads arbitrary repository‑tracked file paths and feeds their contents to an AI model / uses them to reconstruct files after resolution: [3](#0-2) 
- Deep‑link handling for `x-github-client://openLocalRepo` style URLs, where an attacker‑crafted link can supply an arbitrary relative `filepath` (absolute paths are explicitly rejected, but relative `..`-based ones are not, and then routed through `resolveWithin` before revealing the resolved file to the user): [4](#0-3) 

### Impact Explanation
`resolveWithin`'s contract is relied on to keep both file **reads** (Copilot conflict context reads file content from disk and sends it off to an external Copilot backend) and file **reveals** (`shell.showItemInFolder`) confined to the current repository. Because the boundary check can be defeated with an ordinary `..` relative path when a sibling directory happens to share a name prefix with the repository directory — a condition an attacker can often engineer by choosing where the user is enticed to clone/open a repository, or simply relying on common naming conventions — a malicious repository (crafted conflicted file paths) or malicious deep link (crafted `filepath` query param) can cause the app to read and exfiltrate file content, or reveal file locations, from directories outside the repository that the user did not intend to expose. This matches the "file read outside the repo" impact class in the report's scope; the attacker only needs to control repository content or a link the user clicks — no local/physical access is required.

### Likelihood Explanation
Exploitability depends on the resolved sibling path both existing and its name textually extending the root's name, which is a realistic but not universal directory‑naming pattern (e.g., users who keep `repo` and `repo-old`, `repo-backup`, `repo.bak`, `repo2`, etc. next to each other, or an org that clones repos under `org/project` and `org/project-internal`). Given how the check is used from two different attacker‑reachable surfaces (deep-link `filepath`, and repository-controlled conflict file paths), and the complete absence of a boundary check or corresponding test, likelihood is non-trivial though condition-dependent, rather than universally exploitable on any host.

### Recommendation
Fix `_resolveWithin` to enforce a real path-boundary comparison instead of a raw string prefix check, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator for the `win32`/`posix` variants), and add regression tests covering the sibling-directory-with-shared-prefix case for both POSIX and Windows separators, mirroring the existing `clone-path-safety-test.ts` boundary tests.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'

// Assume /tmp/repo and /tmp/repo-secrets both exist, with
// /tmp/repo-secrets/id_rsa containing sensitive data.
const escaped = await resolveWithin('/tmp/repo', '../repo-secrets/id_rsa')
// BUG: escaped === '/tmp/repo-secrets/id_rsa' instead of null,
// because '/tmp/repo-secrets/id_rsa'.startsWith('/tmp/repo') is true.
```
This same relative-path shape (`../<sibling-that-prefixes-root>/...`) can be supplied as the `path` of a conflicted file surfaced during a merge (feeding `buildConflictContext`) [5](#0-4)  or as the `filepath` parameter of an `x-github-client://openLocalRepo` deep link [6](#0-5) , both of which trust `resolveWithin`'s `null`/non-null result as the sole containment guard.
