## Finding: Confirmed — Non-Atomic `ConvertCoinNativeERC20` in IBC Timeout/Ack Path Permanently Strands Refunded Funds

The specific exploit framed in the question (refund + ERC20 view desync) isn't quite how the bug manifests, but tracing the actual code confirms a related, more severe underlying defect: **`ConvertCoinNativeERC20` is not atomic, and the IBC callback path swallows its errors, allowing a partially-executed conversion to commit and permanently strand user funds in the module account.**

### Title
Non-atomic `ConvertCoinNativeERC20` combined with error-swallowing in `ConvertCoinToERC20FromPacket` permanently strands refunded IBC coins in the erc20 module account - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoinNativeERC20` performs three sequential, non-cache-wrapped state mutations: (1) escrow the native coin from sender to the `erc20` module account via `bankKeeper.SendCoinsFromAccountToModule`, (2) transfer the equivalent ERC20 tokens from the module address to the receiver via `evmKeeper.CallEVM`, (3) burn the escrowed coin. [1](#0-0) 

Step (2)'s EVM call is internally protected by its own `ctx.CacheContext()` — if the call reverts, only the EVM-side changes are discarded; the bank escrow from step (1), already applied directly to the outer `ctx`, is **not** rolled back. [2](#0-1) 

When this function is called from the normal `MsgConvertCoin` handler, an error here propagates all the way to `baseapp`, which discards the entire cached transaction multistore — so atomicity is preserved by the outer tx-level rollback, not by the function itself. [3](#0-2) 

However, in the IBC timeout/ack path, `ConvertCoinToERC20FromPacket` deliberately **swallows** any error from `ConvertCoinNativeERC20` and returns `nil`: [4](#0-3) 

Because this `nil` propagates up through `OnAcknowledgementPacket`/`OnTimeoutPacket` to the top-level packet-processing message handler, `baseapp` sees a successful transaction and **commits** all state mutations made so far — including the already-executed bank escrow from step (1), even though the compensating ERC20 transfer in step (2) never completed and nothing was burned.

### Finding Description
The code comments explicitly assume atomic failure: *"If the ERC20 conversion fails for whatever reason... the user receives the corresponding bank token from the TokenPair instead. A user may then manually re-attempt the conversion."* [5](#0-4) 

This assumption is false when the failure occurs *after* the bank-side escrow in `ConvertCoinNativeERC20` has already succeeded and only the EVM transfer reverts (e.g., a paused/blacklisting ERC20 token pair, or a contract that legitimately reverts transfers to certain addresses). In that case:
- The sender's native coin balance has already moved to the `erc20` module account (`types.ModuleName`).
- The ERC20 transfer to the receiver never happened.
- The escrowed coin is never burned.
- The overall IBC ack/timeout transaction still commits successfully because the error was swallowed before reaching the tx handler.

Result: the user ends up with **zero native coin balance and zero ERC20 balance** for the affected amount — the funds are stuck in the module account with no exposed recovery path (no sweep/reclaim message exists in `x/erc20`).

### Impact Explanation
This is a permanent loss/freezing of user funds triggered through an ordinary, unprivileged flow: an IBC transfer of a native-ERC20-backed token pair that later times out or receives an error acknowledgement. Any real-world ERC20 with pause/blacklist functionality (common in stablecoins) can trigger this — either accidentally (legitimate pause during an in-flight transfer) or deliberately, since a token-pair's contract owner (who is "unprivileged" from the chain's protocol perspective, not a validator/relayer/governance actor) can time a pause/blacklist action to coincide with a victim's packet timeout/ack, permanently trapping that victim's refunded coins in the module account.

### Likelihood Explanation
Requires: (1) a native-ERC20 token pair (registrable permissionlessly via `MsgRegisterERC20` when `PermissionlessRegistration` is enabled) [6](#0-5) 
, (2) an IBC transfer of that token that fails/times out, and (3) the ERC20 transfer step reverting at exactly that moment. The token owner (an unprivileged external actor relative to chain consensus) fully controls condition (3) via ordinary contract features (pause/blacklist), making deliberate exploitation practical against any user of that token pair.

### Recommendation
Wrap all of `ConvertCoinNativeERC20`'s state mutations in a single `ctx.CacheContext()` and only commit if every step succeeds, so a mid-function failure leaves no partial escrow. Additionally, `ConvertCoinToERC20FromPacket` should not swallow errors that occurred after irreversible state mutations without first verifying (or ensuring) full rollback of those mutations.

### Proof of Concept (conceptual)
1. Attacker deploys a pausable/blacklistable ERC20 contract and permissionlessly registers it as a native-ERC20 token pair.
2. A user (or the attacker) converts coins to this ERC20 and sends them cross-chain via `MsgTransfer`; the coin is escrowed on the sending chain.
3. The packet times out (or receives an error ack) on the counterparty; the base ICS20 module refunds the sender, then `OnTimeoutPacket`/`OnAcknowledgementPacket` invokes `ConvertCoinToERC20FromPacket`.
4. Immediately before/during this callback's execution, the token owner pauses the contract, causing `CallEVM`'s transfer to revert inside `ConvertCoinNativeERC20` — after `SendCoinsFromAccountToModule` has already succeeded.
5. `ConvertCoinToERC20FromPacket` swallows the error and returns `nil`; the IBC timeout/ack transaction commits.
6. Assert: sender's native coin balance and ERC20 balance are both now less than before, with the missing amount permanently held in the `erc20` module account balance with no path to recovery — confirming stranded funds rather than the invariant-preserving fallback the code comments claim.

	// parent gas meter. On success we commit the cache and charge the actual
	// gas used; on revert we discard the cache and leave the parent meter
	// untouched (matching DerivedEVMCallWithData semantics).

	res, err := k.ApplyMessage(tmpCtx, msg, nil, commit, true)
	if err != nil {
		return nil, err
	}

	if res.Failed() {
		return res, errorsmod.Wrap(types.ErrVMExecution, res.VmError)
	}

	commitState()
	ctx.GasMeter().ConsumeGas(res.GasUsed, "apply evm message")

	return res, nil
}
