## Analysis

Tracing `send` in `modules/pallets/hyper-fungible-token/src/lib.rs` confirms the described flaw exists in the code. [1](#0-0) 

`register_token` only fetches local decimals transiently to validate `config.decimals >= local_decimals`, and never persists the local decimals value — `Precisions` only stores the remote/erc decimals per `(AssetId, StateMachine)`. [2](#0-1) 

Then, in `send`, `erc_decimals` is read from the frozen `Precisions` map, but the local `decimals` value is re-read live from the asset's mutable metadata (`fungibles::metadata::Inspect::decimals`) on every call: [3](#0-2) 

`convert_to_erc20` then computes `value * 10^(erc_decimals.saturating_sub(local_decimals))`: [4](#0-3) 

If `local_decimals` is lowered between registration and a subsequent `send` call, the exponent `erc_decimals - local_decimals` grows, inflating `erc20_amount` for the exact same escrowed/burned raw `params.amount`. The escrow/burn itself (`NativeCurrency::transfer`, `Assets::transfer`, or `Assets::burn_from`) operates on raw balance units and is unaffected by decimals changes, so the amount actually locked on the source chain is decoupled from the amount encoded into the outbound `Message` and dispatched to the destination contract.

Whether this is exploitable by a fully unprivileged attacker depends on who can mutate an already-registered asset's `decimals` metadata (typically the asset's `Issuer`/team via `pallet_assets::set_metadata`, not the pallet's `CreateOrigin`). For any asset whose metadata-mutation rights remain with an account that isn't equally trusted as the bridge governance (e.g., a permissionlessly created asset later registered for bridging), that account can perform this attack without touching any privileged bridge extrinsic — it only calls the underlying asset pallet's own metadata-update call plus this pallet's public `send` extrinsic.

### Title
Local asset decimals are re-read live instead of frozen at registration, allowing precision-based amount inflation in `send` - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`Precisions` freezes only the *remote* (erc) decimals per chain at `register_token`/`update_token` time, but the *local* decimals used in the same conversion are fetched live from the asset's metadata inside `send`, every call. If the local asset's decimals metadata can be lowered after registration, `convert_to_erc20` produces an `erc20_amount` far larger than what corresponds to the amount actually escrowed/burned on the source chain.

### Finding Description
In `send`, source-side custody is enforced using `params.amount` raw units via `NativeCurrency::transfer`/`Assets::transfer`/`Assets::burn_from`. Immediately after, `decimals` is fetched fresh via `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(params.asset_id.clone())` and combined with the registration-time-frozen `erc_decimals` from `Precisions` to compute `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)`. Because `local_decimals` was never snapshotted into storage at registration (it's used only inline in `register_token`/`update_token` for the `ErcDecimalsBelowLocal` check), any subsequent decrease of the asset's decimals metadata increases the scaling exponent `erc_decimals.saturating_sub(local_decimals)`, inflating the `Message.amount` encoded and dispatched to the destination `token_contract`, without any corresponding increase in the amount escrowed/burned on the source chain.

### Impact Explanation
The destination-side ERC20 contract will mint/release/settle based on the inflated `Message.amount`, exceeding what was actually locked or burned on the source chain — a direct source of unauthorized value creation / destination-custody drain, consistent with the "wrongful asset movement" and "wrong amount" categories in the impact gate.

### Likelihood Explanation
Requires the ability to lower the registered asset's decimals metadata via the underlying asset pallet's own admin/issuer call (not this pallet's privileged `CreateOrigin`). For any asset whose metadata-mutation rights are held by an account distinct from (and less trusted than) the bridge's `CreateOrigin`, this is directly reachable without any privileged bridge action, only the public `send` extrinsic plus a standard `pallet-assets` metadata update. Registered assets whose metadata is truly immutable or governed identically to bridge governance are not exposed.

### Recommendation
Persist the local decimals used for each asset at `register_token` time (e.g., add a `LocalDecimals` storage map or store the tuple in `Precisions`), and use that frozen value inside `send` instead of re-reading `fungibles::metadata::Inspect::decimals` live. Reject or re-validate if the asset's live decimals ever diverge from the frozen value.

### Proof of Concept
1. Register an asset with `local_decimals = 18`, `erc_decimals (config.decimals) = 18` via `register_token`.
2. As the asset's metadata admin, call `pallet_assets::set_metadata` (or equivalent) to lower the asset's `decimals` to `0`.
3. Call `send` with `params.amount = X` (raw units) for that asset.
4. Observe: escrow/burn moves `X` raw units, but `erc20_amount = X * 10^18` is encoded into `Message.amount` and dispatched — vastly exceeding the value actually escrowed, while `Precisions` (erc-side) was never touched and no privileged bridge call was used.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
