### Title
Payout OP_RETURN operator identity is unauthenticated, allowing any party to forge which operator gets reimbursed - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` embeds `operator_xonly_pk` in output index 2 (OP_RETURN) while the user's withdrawal authorization signature uses `SinglePlusAnyoneCanPay`, which under BIP341 only commits to the output whose index equals the input index (index 0). Outputs 1 (anchor) and 2 (OP_RETURN operator identity) are never covered by the signature, so anyone able to complete and broadcast the payout transaction (which only requires funding output 0 — fixed by the withdrawal commitment) can set the OP_RETURN to name an arbitrary operator, and that operator's own reimbursement automation will treat it as a genuine self-fronted payout with no additional verification.

### Finding Description
The broken binding: `op_return_operator_xonly_pk (embedded in payout tx output 2)` **should equal** `the operator whose own capital funded output 0 of the payout tx`, but nothing enforces this equality.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk.serialize())`, and signs only input 0 with the user's `taproot::Signature` (`txhandler.set_p2tr_key_spend_witness(&user_sig, 0)`).
- `Operator::withdraw` (`core/src/operator.rs:620-637`) verifies this signature via `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` and `SECP.verify_schnorr`. When `in_signature.sighash_type == SinglePlusAnyoneCanPay`, `calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-262`) computes the sighash using `Prevouts::One(txin_index, ...)` and passes the sighash type straight to `taproot_key_spend_signature_hash`. Per BIP341, `SIGHASH_SINGLE` only commits the output at the same index as the input (index 0); it does **not** commit outputs 1 or 2. `ANYONECANPAY` further excludes commitment to other inputs.
- Consequently, a valid `SinglePlusAnyoneCanPay` signature over a payout transaction remains valid for **any** choice of `operator_xonly_pk` in output 2 (and any anchor script/value in output 1), as long as output 0 (script_pubkey/amount) matches what the withdrawing user originally committed to on Citrea.
- Downstream, the protocol treats the on-chain OP_RETURN value as ground truth for operator attribution with no further cryptographic check:
  - `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) parses the OP_RETURN via `parse_op_return_data`/`XOnlyPublicKey::from_slice` and stores it directly as `payer_operator_xonly_pk` in the DB.
  - `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks `operator_xonly_pk (from OP_RETURN) == kickoff_data.operator_xonly_pk`; if an attacker names operator B, and B legitimately submits a kickoff with `operator_xonly_pk = B`, this check passes (`Ok(false)`, i.e. not malicious).
  - `Operator::validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:31-111`, using `get_first_unhandled_payout_by_operator_xonly_pk`) drive an operator's own automation to detect "its" payouts purely by matching the OP_RETURN pubkey against `self.signer.xonly_public_key` — there is no check that the operator itself constructed, funded, or broadcast that specific payout transaction.

Exploit flow: an unprivileged attacker calls `withdraw` on the Citrea Bridge contract for their own withdrawal, obtaining a `SinglePlusAnyoneCanPay` signature over their own withdrawal UTXO/output. They construct their own payout transaction (paying output 0 to themselves — no net cost besides fees, since they are the withdrawal recipient), attach an arbitrary anchor and an OP_RETURN naming a targeted, uninvolved operator B's public x-only key, and broadcast/fund it themselves, using nothing but the publicly-known signature and B's publicly-known pubkey. `SECP.verify_schnorr` succeeds because output 0 is what's actually committed. Once mined, `update_finalized_payouts` records operator B as the payer. Operator B's own `PayoutCheckerTask` then autonomously initiates a kickoff and eventually a `Reimburse` transaction, and `is_kickoff_malicious`/verifiers do not flag it as malicious since the OP_RETURN matches B's kickoff identity — B is reimbursed from the bridge's move-to-vault UTXO for a payout it never funded.

Existing guards fail because they all trust the *unauthenticated* OP_RETURN content rather than verifying that the named operator actually broadcast/funded the specific payout transaction (e.g., via an operator signature covering that output, or a local record correlating the operator's own broadcast to the on-chain txid).

### Impact Explanation
An operator can be reimbursed from a move-to-vault UTXO for a withdrawal it never fronted, i.e. bridge value (`bridge_amount`) is paid out to the falsely-credited operator without a genuine matching fronted payout — this is explicitly listed as a Critical impact category ("an operator reimbursed for a payout it never funded"). This is repeatable for every withdrawal an attacker initiates (attacker only needs to be a legitimate Citrea withdrawer), and the targeted operator can be any known, currently-registered operator xonly public key, so the blast radius spans all operators and all withdrawals.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be a Citrea user who can call `withdraw`, obtain their own `SinglePlusAnyoneCanPay` signature (which they legitimately control, since they are the withdrawer), and race to broadcast a self-funded payout tx with a forged OP_RETURN before the intended honest operator's payout lands (or simply target a withdrawal request before any operator has picked it up). The attacker's Bitcoin cost is only the withdrawal amount to themselves (zero net cost since they receive it back) plus transaction fees — no BTC is permanently lost by the attacker. This is fully attacker-controlled and does not require any privileged role, key compromise, or majority hashrate, making it highly feasible and repeatable across deposits/withdrawals.

### Recommendation
Bind the operator identity output cryptographically to the same signature that authorizes the spend, e.g., by using `SIGHASH_ALL|ANYONECANPAY` (or a dedicated commitment) instead of `SIGHASH_SINGLE|ANYONECANPAY` so all outputs (including the OP_RETURN and anchor) are committed by the user's authorization, or alternatively require the fronting operator to separately sign/attest to the payout txid with their own key before their automation treats it as their own fronted payout (rather than trusting on-chain OP_RETURN content alone). Additionally, `PayoutCheckerTask`/`validate_payer_is_operator` should cross-check against a locally-originated record that the operator itself broadcast that specific payout transaction, not merely that the OP_RETURN parses to their own key.
