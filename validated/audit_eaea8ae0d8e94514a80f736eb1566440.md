## Analysis Result

### Title
`VLMGP::expectedPenaltyAmount()` divides before multiplying (squaring) the unlock factor, causing early-unlock users to receive less MGP than entitled — (File: VLMGP.sol)

### Summary
`VLMGP.expectedPenaltyAmount()` computes a squared time-based `unlockFactor` used to determine how much of a user's cooling-down MGP they receive when force-unlocking early. The computation truncates (divides) an intermediate ratio before squaring it and dividing again, discarding precision at two points instead of one, systematically rounding the factor down and shifting extra tokens from the user to the penalty pool.

### Finding Description
The vulnerable code is: [1](#0-0) 

Specifically:
```solidity
uint256 unlockFactor = 1e12;
if((block.timestamp - slot.startTime) <= (slot.endTime - slot.startTime))
    unlockFactor = ((block.timestamp - slot.startTime) * 1e12 / (slot.endTime - slot.startTime)) ** 2 / 1e12;

uint256 unlockAmount = waitingAmount * unlockFactor / 1e12;
```
This mirrors exactly the reported bug class: an intermediate ratio `(elapsed * 1e12 / duration)` is truncated to an integer *before* being squared, and the squared result is truncated again by `/ 1e12`. Multiplying before dividing (e.g. computing `elapsed^2 * 1e12 / duration^2` in a single step, or at minimum delaying the first division) would preserve precision that is otherwise permanently lost, exactly as in the referenced `FluidLocker::_getUnlockingPercentage()` root cause of dividing before multiplying.

This function is invoked directly by `forceUnLock()`, reachable by any ordinary wallet with a cooling-down slot: [2](#0-1) 

### Impact Explanation
Every time an unprivileged user calls `forceUnLock()` to prematurely exit a cool-down slot, the truncated `unlockFactor` causes `amountToUser` to be computed as slightly less than the mathematically correct entitlement, with the difference silently added to `penaltyAmount`, which flows to `totalPenalty` and is later swept to `penaltyDestination`: [3](#0-2) 
This is a direct, permanent loss of user funds (dust siphoned into the penalty pool on every force-unlock) — the same fund-loss mechanism as the referenced report, just applied to VLMGP's early-exit/forfeit accounting instead of FluidLocker's vesting-based unlock percentage. Because `forceUnLock` is a normal, frequently-used user action (no privileged role or special precondition needed), the loss recurs across the user base and accumulates over time, analogous to the original finding's "loss accumulates" argument.

### Likelihood Explanation
Any locker who chooses to force-unlock before their cool-down slot fully matures triggers this path unconditionally — no attacker setup, governance action, or external dependency is required. This is a routine, expected user interaction with `VLMGP`, so the likelihood of occurrence is high; the only variable is the magnitude of loss per call, which is small but systematic and unavoidable.

### Recommendation
Restructure the calculation to multiply before dividing, deferring all division to the very last step, e.g.:
```solidity
uint256 elapsed = block.timestamp - slot.startTime;
uint256 duration = slot.endTime - slot.startTime;
unlockFactor = (elapsed * elapsed * 1e12) / (duration * duration);
```
This avoids the intermediate truncation of `(elapsed * 1e12 / duration)` prior to squaring, preserving precision and ensuring `amountToUser` reflects the correct, non-truncated share.

### Proof of Concept
Given `slot.startTime = 0`, `slot.endTime = 1000`, and `block.timestamp = 333`:
- Current code: `(333 * 1e12 / 1000) ** 2 / 1e12 = (333000000000)^2 / 1e12` → truncation of `333 * 1e12 / 1000 = 333000000000` (exact here, but for non-exact ratios e.g. `block.timestamp = 1` of `1000`, `1 * 1e12 / 1000` truncates any remainder before squaring), which for larger prime-like durations discards fractional precision that the "multiply-first" formula (`elapsed² * 1e12 / duration²`) would retain.
- The discarded precision reduces `unlockFactor`, reducing `unlockAmount` and thus `amontToUser`, while `penaltyAmount = coolDownAmount - amontToUser` increases correspondingly — funds move from the user to `totalPenalty` purely due to rounding, replicating the reported bug's mechanism in `VLMGP`'s forfeit path.

```text
    function expectedPenaltyAmount(uint256 _slotIndex) public view returns(uint256 penaltyAmount, uint256 amontToUser) {
        UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];

        uint256 coolDownAmount = slot.amountInCoolDown;
        uint256 baseAmountToUser = slot.amountInCoolDown / 5;
        uint256 waitingAmount = coolDownAmount - baseAmountToUser;

        uint256 unlockFactor = 1e12;
        if((block.timestamp - slot.startTime) <= (slot.endTime - slot.startTime))
            unlockFactor = ((block.timestamp - slot.startTime) * 1e12 / (slot.endTime - slot.startTime)) ** 2 / 1e12;

        uint256 unlockAmount = waitingAmount * unlockFactor / 1e12;
        amontToUser = baseAmountToUser + unlockAmount;
        penaltyAmount = coolDownAmount - amontToUser;
    }
```
