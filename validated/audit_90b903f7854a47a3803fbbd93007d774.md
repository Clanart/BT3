### Title
Unauthenticated `SendMoveToVaultTx` RPC lets any caller make the aggregator fund and broadcast an attacker-chosen transaction - (File: `core/src/rpc/aggregator.rs`)

### Summary
The Aggregator's gRPC server does not enforce mTLS client-certificate authentication (only Verifier/Operator servers do), so `ClementineAggregator::send_move_to_vault_tx` is reachable by any network caller. Inside the handler, the only checks performed are on the transaction's *output* shape (count, value, script pubkeys); it never verifies that `movetx.input[0].previous_output` actually equals the caller-supplied `deposit_outpoint`. The aggregator then unconditionally queues the caller-supplied raw transaction for CPFP fee-bumping and broadcast via its own tx-sender, using its own wallet funds.

### Finding Description
`docs/usage.md` states explicitly: "The aggregator does not enforce client certificates but does use TLS for encryption," which is confirmed by `create_aggregator_grpc_server` in `core/src/servers.rs:293-317`, which never constructs an `OnlyAggregatorAndSelf` interceptor for the aggregator service the way `create_verifier_grpc_server`/`create_operator_grpc_server` do via `config.client_verification`. [1](#0-0) [2](#0-1) 

`send_move_to_vault_tx` (`core/src/rpc/aggregator.rs:1973-2102`) parses an arbitrary raw transaction and a `deposit_outpoint` from the request, and validates only:
- input/output counts,
- output[0] value equals `bridge_amount` and output[1] value is 0,
- output script pubkeys match the deterministic (publicly derivable) N-of-N + security-council taproot address and anchor script.

It never checks that `movetx.input[0].previous_output == deposit_outpoint`, i.e. that the supplied transaction actually spends the claimed deposit UTXO: [3](#0-2) 

After these checks pass, the handler unconditionally calls `self.tx_sender.insert_try_to_send(...)` with `FeePayingType::CPFP` and the attacker-controlled `deposit_outpoint` as metadata, then commits: [4](#0-3) 

Because outputs 0/1 (bridge script pubkey, bridge amount, anchor script/amount) are fully deterministic and public (derived from public verifier keys and the public security council configuration), any unauthenticated caller can construct a syntactically valid "movetx" whose outputs satisfy every check performed, regardless of what real UTXO (if any) `input[0]` references. This lets an unauthenticated party get the aggregator to accept and queue the transaction for CPFP fee-funding/broadcast attempts and to persist an attacker-chosen `deposit_outpoint → TransactionType::MoveToVault` association in the tx-sender database, bypassing the intended binding that a move-to-vault record should only ever be created for a transaction that genuinely spends that deposit outpoint.

This is the same class of defect as the report's `requestTransfer`: a state-changing method meant to be invoked only as part of a controlled protocol flow (analogous to `requestTransfer` being intended to be admin-gated) is instead reachable by anyone, letting the caller overwrite/insert privileged bookkeeping state (`$.pendingTransfer` ↔ `TxMetadata{deposit_outpoint, tx_type: MoveToVault}`) with attacker-chosen values.

### Impact Explanation
This is an unauthenticated, state-changing/broadcasting call reachable without any operator/verifier/aggregator role or key compromise (the aggregator server simply does not authenticate callers). At minimum it lets an outside party:
- force the aggregator to spend its own wallet funds (CPFP fee bumping) fronting fee payments for transactions it did not originate, and
- insert/overwrite `deposit_outpoint`-keyed `MoveToVault` bookkeeping records in the aggregator's database with values chosen by the attacker rather than the entity that actually funded the movetx.

I was not able to fully trace, within the remaining time/tool budget, every downstream consumer of the `TxMetadata.deposit_outpoint`/`TransactionType::MoveToVault` record (e.g. in `core/src/tx_sender_queue.rs`, `core/src/builder/transaction/creator.rs`) to conclusively prove that this metadata confusion alone produces a Critical-tier custody loss (an attacker cannot forge the N-of-N/taproot witness needed to actually move real BTC without the input's real spending key, so the on-chain funds themselves cannot be stolen this way). The concretely provable impact is the unauthenticated ability to reach a state-changing/broadcasting aggregator method and corrupt/duplicate its `deposit_outpoint` bookkeeping, which maps to the report's "High - an unauthenticated state-changing or broadcasting call" category rather than a proven Critical fund-loss primitive.

### Likelihood Explanation
High likelihood of reachability: no credentials, TLS client certificate, or special role are required to call the aggregator's public gRPC endpoint per the documented configuration (`client_verification` gates the Operator/Verifier servers but the aggregator explicitly does not enforce it). Constructing a request that passes the output-shape checks only requires public information (verifier public keys, security council configuration, protocol paramset amounts).

### Recommendation
- Verify `movetx.input[0].previous_output == deposit_outpoint` before accepting the transaction in `send_move_to_vault_tx`.
- Gate `SendMoveToVaultTx` (and any other aggregator RPC that queues transactions for fee-funding/broadcast or writes bookkeeping metadata) behind the same mTLS/client-certificate authentication used for Verifier/Operator servers, rather than leaving the aggregator server unauthenticated.
- Additionally verify that the deposit outpoint corresponds to a deposit this aggregator actually processed (e.g. cross-check against `NewDeposit` records) before inserting `TxMetadata`.

### Proof of Concept
1. Query any verifier's public key set and the security council configuration (public config data) to derive the deterministic bridge taproot script pubkey and anchor script pubkey, exactly as `send_move_to_vault_tx` does internally. [5](#0-4) 
2. Craft a 1-input/2-output Bitcoin transaction whose `output[0]` = `(bridge_amount, bridge_script_pubkey)` and `output[1]` = `(0, anchor_script_pubkey)`, with `input[0].previous_output` set to any outpoint (does not need to match a real deposit).
3. Without any TLS client certificate/authentication, call the Aggregator's `SendMoveToVaultTx` RPC with this raw transaction and an arbitrary `deposit_outpoint` value of choice.
4. Observe that all checks in `core/src/rpc/aggregator.rs:2019-2073` pass (they only check output shape), and the aggregator commits a `TxMetadata{ deposit_outpoint, tx_type: MoveToVault }` record and queues the transaction via `insert_try_to_send(..., FeePayingType::CPFP, ...)` for fee funding/broadcast, at `core/src/rpc/aggregator.rs:2075-2098`, using the aggregator's own funds — all without ever proving the caller controls, or that the transaction spends, the claimed `deposit_outpoint`.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
