### Title
Recursive/nested precompile calls share overwritten `BalanceHandler.prevEventsLen`, causing native bank balances to desync from EVM StateDB balances - (File: precompiles/common/balance_handler.go)

### Summary
The Basket report is a "check-then-effect across an interrupted external-call sequence" bug: a permission/ownership check is made once, then a loop performs several external calls, and state relevant to that check is mutated mid-loop by a reentrant call, so the final state diverges from what the checks assumed. The Cosmos EVM analog is in the precompile `BalanceHandler`, which records an event-log "checkpoint" (`prevEventsLen`) before native execution and later uses that checkpoint to translate bank events into StateDB balance deltas. When a precompile call recursively/nestedly triggers another precompile call on the same EVM execution context, this checkpoint bookkeeping can be clobbered, producing an accounting mismatch between the native `x/bank` state and the EVM `StateDB` balance view used by the rest of the transaction (and by any contract reading `balanceOf`/native balance mid-transaction).

### Finding Description
Every precompile's `Run` method wraps execution in `RunNativeAction` → `runNativeAction` (`precompiles/common/precompile.go:57-126`). This method:
1. Takes a KV-store snapshot (`stateDB.MultiStoreSnapshot()`).
2. Creates a `BalanceHandler` via `p.BalanceHandlerFactory.NewBalanceHandler()`, and calls `BeforeBalanceChange(ctx)`, which sets `bh.prevEventsLen = len(ctx.EventManager().Events())` (`precompiles/common/balance_handler.go:46-48`).
3. Executes the native action (`action(ctx)`), which may internally call EVM code (`k.evmKeeper.CallEVM`/`CallEVMWithData`, e.g. in `x/erc20/keeper/msg_server.go`), which may itself invoke *other* precompiles or the *same* precompile recursively, each spawning its own `runNativeAction` context sharing the same underlying `ctx.EventManager()`.
4. After the action returns, calls `AfterBalanceChange(ctx, stateDB)`, which replays `events[bh.prevEventsLen:]` and calls `stateDB.AddBalance`/`SubBalance` for each `CoinSpent`/`CoinReceived`/fractional-balance event since the recorded checkpoint (`precompiles/common/balance_handler.go:68-136`).

The repository's own integration test explicitly documents this exact bug class: `evmd/tests/integration/balance_handler/balance_handler_test.go:23-25` states "*tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB.*" The associated `TestRecursivePrecompileCallsWithDebugPrecompile` test drives a contract that recursively calls back into a precompile (`callerContract.ABI.Pack("callback", ...)`) and asserts on the resulting event/telemetry counts, confirming this is a live, tracked concern for the same call-tree structure that the Basket exploit relies on (check recorded once, then external/reentrant calls performed, with the checkpoint used afterward regardless of what happened in between).

This mirrors the Basket vulnerability precisely:
- Basket: ownership checked once at the top of `withdrawMultipleERC721`, then a loop makes multiple external calls; an external call mid-loop can shift the "true" state (NFT ownership) out from under the invariant the rest of the loop still trusts.
- Cosmos EVM: `prevEventsLen` is captured once at the top of `runNativeAction`, then the native action can trigger nested precompile invocations (each of which also emits bank events and may reset/interleave the shared `EventManager`'s event index), and `AfterBalanceChange` still trusts the original checkpoint to slice "new" events — potentially applying wrong deltas, double-applying deltas already consumed by an inner precompile call, or skipping deltas that were emitted between the outer checkpoint and inner-precompile bookkeeping.

### Impact Explanation
If the event-index bookkeeping is corrupted across nested precompile calls, the EVM `StateDB` balance for an address can diverge from the actual native `x/bank` balance for the duration of (and potentially beyond) the transaction. Since `StateDB` balance is what `balanceOf`, EVM `CALL` value-transfer accounting, and gas refund logic observe, this can let a contract observe (and act on) an inflated or deflated balance relative to the real bank-module balance — enabling unauthorized extraction of value, double-spending appearing balance, or corrupting the invariant that "1 native coin == 1 EVM balance unit" that the rest of the system relies on. This falls under the allowed "irreversible accounting corruption of spendable user value across native balances / EVM balances" and "unauthorized extraction of user funds" impact categories.

### Likelihood Explanation
Reachability requires an unprivileged user to deploy/call a contract that triggers a precompile call whose native action itself performs a nested EVM call that reaches another (or the same) precompile — a pattern the repository's own test suite (`ERC20RecursiveNonRevertingPrecompileCall.sol`, `StakingReverter.sol`, `DistributionCaller.sol`, `InterchainSenderCaller.sol`, and the dedicated `balance_handler_test.go`) demonstrates is both possible and already exercised in-repo. This significantly raises confidence that the trigger path is real and reachable by ordinary transactions, not a privileged/hypothetical setup.

### Recommendation
Scope the `BalanceHandler`/event-index tracking per precompile-call-frame rather than relying on a single shared, mutable `ctx.EventManager()` position that can be advanced or reset by nested precompile invocations. Concretely: (1) snapshot and restore the event slice boundaries symmetrically with the `MultiStoreSnapshot`/journal mechanism already used for revert handling, so each nested call's `AfterBalanceChange` only ever consumes the events it itself produced; (2) add an invariant check (e.g., in tests or via an assertion in `AfterBalanceChange`) that the sum of applied StateDB deltas equals the actual bank balance delta for every touched address at the end of the outer-most precompile call; (3) extend `evmd/tests/integration/balance_handler/balance_handler_test.go` with balance-equality assertions (native bank balance vs. StateDB balance) instead of only event counts, to catch silent desync.

### Proof of Concept
The repository already contains a reproducible harness for this exact class of issue at `evmd/tests/integration/balance_handler/balance_handler_test.go`: it registers a debug precompile, deploys a caller contract that recursively invokes the precompile via `callback(0)`, funds the caller contract, and sends an EVM tx that triggers the recursive precompile call chain, then inspects the resulting event log to detect the described desync behavior. A concrete exploit PoC (crafting an ERC20/staking/distribution precompile combination where a nested call moves bank balance out from under the outer call's `prevEventsLen` checkpoint, then reading `balanceOf`/StateDB balance immediately after to show it disagrees with the bank-module balance) was not fully constructed/verified within the scope of this investigation — the analog and root cause are established from the code paths and the repository's own bug-tracking test, but exact numeric divergence was not empirically reproduced here.
