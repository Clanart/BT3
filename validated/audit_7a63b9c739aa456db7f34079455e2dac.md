### Title
Untrusted `ReceivedOutput` can bind any Bitcoin output to any spend offset - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary

`ReceivedOutput::read` deserializes a scalar offset, `TxOut`, and `OutPoint`, then directly constructs a supposedly spendable wallet output without checking that `output.script_pubkey` corresponds to the scanner’s public key plus that offset. [1](#0-0) [2](#0-1) 

The trusted construction path is `Scanner::scan_transaction`, which only creates a `ReceivedOutput` after finding `output.script_pubkey` in the registered `scripts` map. [3](#0-2)  Deserialization bypasses that authorization/ownership check and creates an implicit offset-to-output binding.

### Finding Description

`Scanner` maintains a map from authorized Taproot scriptPubKeys to the scalar offsets needed to spend them. [4](#0-3)  `register_offset` inserts a script only after calculating `key + offset * G` and converting it to the corresponding P2TR script. [5](#0-4)  Scanning therefore normally proves that a returned output belongs to the scanner’s key and records the correct offset. [6](#0-5) 

`ReceivedOutput::read` accepts attacker-controlled bytes and never performs this check. [7](#0-6)  An attacker can serialize an output paying to an unrelated script while claiming any offset, or claim a real wallet output with the wrong offset. The resulting object exposes the forged values through `offset()`, `output()`, and `outpoint()` as if it had been produced by `Scanner`. [8](#0-7) 

### Impact Explanation

If an application accepts serialized `ReceivedOutput` values from an untrusted file, peer, cache, IPC endpoint, or synchronization mechanism, an attacker can cause arbitrary Bitcoin outputs to be reported as received wallet funds. Because the declared offset is not bound to the output’s scriptPubKey, downstream spending can either target an output the wallet never controlled or apply the wrong offset to a wallet-controlled output. In both cases, the reported funds are not spendable by the threshold key.

This is the Serai analogue of the NATS flaw: an implicit object is accepted without passing through the intended authorization mapping. Here, the intended mapping is the scanner’s registered script-to-offset table, but `ReceivedOutput::read` creates the authorized-looking result directly. [3](#0-2) [7](#0-6) 

### Likelihood Explanation

The attack requires only control of bytes passed to `ReceivedOutput::read`; it does not require a validator key, threshold cooperation, malformed curve encodings, or consensus misbehavior. A single forged record is sufficient to corrupt the recipient/output association. The practical impact depends on whether deployments treat serialized `ReceivedOutput` values as trusted scanner results, but the exposed API itself provides no integrity protection or ownership validation.

### Recommendation

Treat `ReceivedOutput::read` as an untrusted representation rather than a scanner result. Add an authenticated constructor such as `ReceivedOutput::read_for_key(reader, key)` which:

1. Reads the claimed offset and output.
2. Computes `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)`.
3. Rejects the record unless the computed script equals `output.script_pubkey`.

Alternatively, authenticate serialized scanner outputs at the storage/IPC boundary, or serialize and verify the registered script-offset mapping alongside the output. Merely checking scalar canonicity is insufficient because the current failure is the missing semantic binding between `offset` and `TxOut`. [7](#0-6) 

### Proof of Concept

```rust
use bitcoin::{
  consensus::encode::serialize,
  hashes::Hash,
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use k256::Scalar;

// K is the scanner's base key. Offset 0 should only authorize the script
// p2tr_script_buf(K). Instead, we bind offset 0 to an unrelated script.
let unrelated_script = ScriptBuf::from_bytes(vec![0x6a]); // OP_RETURN
let output = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: unrelated_script.clone(),
};

let txid = Txid::from_raw_hash(bitcoin::hashes::sha256d::Hash::all_zeros());
let outpoint = OutPoint::new(txid, 0);

let mut bytes = Scalar::ZERO.to_bytes().to_vec();
bytes.extend(serialize(&output));
bytes.extend(serialize(&outpoint));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The object is accepted and reports the unrelated output as spendable.
assert_eq!(forged.offset(), Scalar::ZERO);
assert_eq!(forged.output().script_pubkey, unrelated_script);
assert_eq!(forged.value(), 100_000);
```

For a scanner key `K`, the legitimate offset-0 script would be `p2tr_script_buf(K)`, not the attacker’s `OP_RETURN` script. [9](#0-8) [10](#0-9)
