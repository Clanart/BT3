### Title
SignableTransaction ignores the OP_RETURN data output when calculating weight, so the committed fee is below the requested/valid rate - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
Analogous to `changeTreasury()` writing the stored `treasury` instead of the passed `_treasury`, `SignableTransaction::new` computes the transaction weight and `needed_fee` from the `payments` slice — a different variable than the `tx_outs` vector actually placed into the transaction. The `data` OP_RETURN output is appended to `tx_outs` before the weight calculation but is never included in `calculate_weight_vbytes`, which is only ever fed `payments`.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs):

1. `tx_outs` is built from `payments` and then an additional `TxOut` carrying the `data` OP_RETURN script is pushed onto it (lines 193–202).
2. The weight/vbyte calculation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — using `payments`, not `tx_outs`. The OP_RETURN output just added is absent from the transaction template inside `calculate_weight_vbytes` (lines 85–99), which builds `output` solely from `payments` plus optional `change`.
3. The same wrong variable is used again for the change path at line 226 (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`), so `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check at line 241 all omit the OP_RETURN output (~92 bytes for a maximal 80-byte push).
4. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay-fee check (line 211) are therefore computed against a smaller transaction than the one signed and broadcast. `TransactionSignMachine::sign` then commits signatures (via `taproot_key_spend_signature_hash` with `Prevouts::All`, lines 373–390) to the larger real transaction, so the discrepancy cannot be corrected post-hoc — the signed fee is `input_sat - sum(tx_outs)`, fixed at construction.

### Impact Explanation
The effective fee rate of the resulting transaction is `needed_fee / actual_vsize`, strictly less than the `fee_per_vbyte` the caller requested. When `fee_per_vbyte` is at or near the relay minimum (the code path explicitly targets `DEFAULT_MIN_RELAY_TX_FEE`), the produced transaction falls below the minimum relay fee once the ~92-vbyte OP_RETURN output is counted, causing Bitcoin nodes to reject it from the mempool. This stalls payments/change from the threshold wallet (funds are not stolen, but outputs are tied up in an unrelayable transaction and the `NotEnoughFunds`/change logic was decided on wrong numbers). This is a reachable, unintended-transaction-construction bug: the bytes placed on-chain differ from the bytes used for the fee/safety computation.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(..)` (e.g., OP_RETURN metadata attached to payments/forwards) hits this unconditionally — no attacker sophistication needed, just a nonzero-length data field, which the API explicitly supports. The magnitude is bounded by the 80-byte data cap, but at low fee rates the impact is transaction rejection rather than a mere discount.

### Recommendation
Compute weight from the actual output list. Pass `tx_outs` (or build the template `Transaction` once and reuse it) into `calculate_weight_vbytes` instead of `payments`, for both the no-change and change calls at lines 204 and 226, so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check reflect the transaction that will actually be signed.

### Proof of Concept
```rust
// networks/bitcoin context; any ReceivedOutput works
let inputs = vec![received_output_with_value(100_000)];
let payments = vec![(p2tr_script_buf(key).unwrap(), 50_000)];
let data = Some(vec![0xaa; 80]); // max allowed, passes the len check

let tx = SignableTransaction::new(inputs, &payments, None, data, 1).unwrap();

// tx now has payments.len() + 1 outputs, but needed_fee was priced for
// a tx without the ~92-byte OP_RETURN output.
let actual_vbytes = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < actual_vbytes * 1); // effective rate < 1 sat/vb
// => below DEFAULT_MIN_RELAY_TX_FEE despite passing the TooLowFee check
```
