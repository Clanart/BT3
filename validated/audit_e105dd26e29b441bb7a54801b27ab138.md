### Title
Unbounded `Vec::with_capacity` on attacker-controlled participant count in `ThresholdKeys::read` enables memory-exhaustion DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::<C>::read` reads a u16 `n` from an untrusted byte stream and immediately allocates `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector — before `ThresholdParams::new` validates `n` and before confirming any of the claimed data exists in the stream. This is a direct analog of CVE-2021-3479: a crafted input causes memory allocation disproportionate to the bytes actually supplied, impacting availability.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` parses `t`, `n`, and `i` from three raw u16s (lines 591–602), then reads an interpolation tag. For tag `0` (Constant), it executes `Vec::with_capacity(usize::from(n))` and loops `n` times calling `C::read_F` (lines 607–613). It then reads `n` group elements into a `verification_shares` `HashMap` (lines 620–623). Only afterwards — at line 626 — does `ThresholdParams::new(t, n, i)` validate that `n` is sane.

Two compounding defects:
- `n` is attacker-controlled up to `0xFFFF` (65535). `with_capacity(65535)` reserves ~2 MiB (65535 × `C::F` ~32 bytes, more for Ed448/wide fields) after the attacker supplies only ~10 bytes of header.
- If the backing reader is a blocking stream (network socket), the `read_F`/`read_G` loop blocks holding the over-reserved `Vec` and partially populated `HashMap` for as long as the peer stalls, or iterates up to 65535 `read_G` decompressions — CPU burn — on supplied data.

The same pattern of unvalidated lengths driving allocation/allocation-sized loops appears in `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-87`), which iterates a u32 count of `read_G` calls.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (listed reachable surface) can force each call to reserve up to ~2 MiB and perform up to 65535 point decompressions from a ~10-byte payload — a large memory/CPU amplification. Concurrent or stalled reads multiply the held memory, exhausting node memory and denying service, matching the CVE's availability impact.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API for keys distributed/restored in multisig flows. Any transport that accepts remote serialized `ThresholdKeys` without a size cap reaches this path directly; no cryptographic validity is needed — only the curve ID prefix must match, which is public.

### Recommendation
Validate `t`/`n`/`i` via `ThresholdParams::new` (or a hard bound such as `MAX_KEY_SHARES_PER_SET`) *before* allocating or looping; replace `Vec::with_capacity(n)` with incremental `push` so memory grows only with bytes actually delivered; apply the same defensive ordering to `SchnorrAggregate::read` (reject implausible counts early, cap at a protocol maximum).

### Proof of Concept
```rust
use std::io::Read;
use dkg::{ThresholdKeys, ThresholdParams};
use ciphersuite::Secp256k1;

// Bytes: u32 id_len + C::ID + t(2) + n(2) + i(2) + interpolation tag 0
let mut buf = vec![];
buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
buf.extend(Secp256k1::ID);
buf.extend(1u16.to_le_bytes());          // t
buf.extend(u16::MAX.to_le_bytes());      // n = 65535, unchecked
buf.extend(1u16.to_le_bytes());          // i
buf.push(0);                             // Interpolation::Constant

// A blocking reader that returns the header then stalls holds the
// ~2 MiB with_capacity allocation for the duration of the hang.
// A truncated stream forces allocation then 65535 attempted reads.
let _ = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice());
// Allocation of 65535 * size_of::<F>() occurred before any bounds check.
