### Title
Direct asset donation to `StreamingYieldVault` bypasses the vesting gate and lets an attacker manipulate the share/asset ratio against depositors - (File: `sdk/packages/core/contracts/vaults/StreamingYieldVault.sol`)

### Summary
`StreamingYieldVault.totalAssets()` is defined as `asset.balanceOf(vault) - lockedYield` [1](#0-0) . `lockedYield` is only updated when yield enters through the owner-gated `addYield()`/`onTransferReceived()` path [2](#0-1) . Any plain `IERC20.transfer(vault, amount)` — a call available to any unprivileged address — increases `asset.balanceOf(vault)` without ever touching `_vestingAmount`/`_vestingStart`, so it is counted in `totalAssets()` immediately, in the same block. This is exactly the "donation" primitive from the external report: a value that feeds a share-ratio's `totalAssets` side can be pumped by a party who is not required to mint shares through the sanctioned path.

### Finding Description
The vault's own documented security invariant is: "No instant jump. Adding yield never moves `totalAssets` in the same block; it only raises the price as the tranche vests" [3](#0-2) . That guarantee is enforced only for the `addYield`/`onTransferReceived` code paths, both of which gate on `msg.sender == owner()`/`from == owner()` [4](#0-3) [5](#0-4) . Nothing prevents an arbitrary caller from bypassing that gate entirely by calling `asset.transfer(address(vault), amount)` directly. Because `totalAssets()` reads live `balanceOf`, that donated amount is recognized instantly — with none of the `VEST`/`MIN_WINDOW` vesting delay, and none of the owner authorization.

This reproduces the exact bug class from the external report: the vault's share-ratio numerator (`totalAssets`) can be inflated through a channel other than the one that mints shares (`deposit`/`mint`), which is the precondition for the classic first-depositor/donation exploit — deposit a small amount to get a nonzero share balance, donate a large amount to skew the ratio, then have a subsequent depositor's shares round down, capturing their principal on redeem.

The contract's own docs acknowledge the underlying attack is only "mitigated" (not eliminated) by OpenZeppelin's virtual-share decimals offset, and separately call out that a manual "seed-and-burn at deployment is still recommended" to fully close it [6](#0-5) [7](#0-6) . The decimals offset is not a contract-enforced invariant closing the donation channel — it only raises the cost/difficulty of the attack, and the seed-and-burn step is an optional deployment action that depends on the deployer following the runbook. The contract itself does nothing to stop a bare transfer from instantaneously moving `totalAssets`, which is the root defect: the documented "no instant jump" property is false for any caller who is not the owner.

This vault is shipped as a solver liquidity primitive: the simplex filler config treats configured ERC-4626 vaults, including this one, as a "stablecoin treasury: fills source missing balance from these vaults atomically" [8](#0-7) , meaning solver-side fund safety and available liquidity for cross-chain intent fills depend on `convertToAssets`/`redeem` returning the correct, undonated exchange rate.

### Impact Explanation
An attacker with no privileged role can donate tokens directly to the vault to instantaneously and unconditionally move the vault's per-share asset value, in violation of the vault's documented invariant that only the owner-gated `addYield` can move `totalAssets`. Combined with a pre-positioned small deposit, this reproduces the classic ERC-4626 donation/inflation exploit, causing other depositors' shares to round down and letting the attacker redeem more assets than they contributed — a direct loss of user/solver funds from the vault used for cross-chain fill liquidity.

### Likelihood Explanation
Low-to-moderate. The decimals offset (`DECIMALS_OFFSET = 6`) raises the bar for the classic "1 wei deposit + huge donation" first-depositor attack, and if the deployer performs the recommended seed-and-burn the attack becomes materially harder. However, neither of these is enforced by the contract; nothing prevents a bare `transfer` at any point in the vault's lifetime (e.g., immediately after a large `redeem` drains supply back down, or on any freshly-deployed vault instance before seed-and-burn is completed), and the attack requires no relayer, prover, or admin — only a plain ERC-20 transfer.

### Recommendation
Enforce the "no instant jump" invariant in code rather than relying on an operational seed-and-burn recommendation:
- Track a vault-internal `totalDeposited` accounting variable updated only by `deposit`/`mint`/`addYield`/`withdraw`/`redeem`, and compute `totalAssets()` from that variable instead of live `balanceOf`, the same way solmate-style vaults avoid donation by not trusting `balanceOf` directly — or,
- Make the seed-and-burn step mandatory at construction time (mint and burn the initial virtual shares in the constructor) so every deployed instance is protected from block one, removing the dependency on the deployer following the runbook correctly.

### Proof of Concept
1. Deploy `StreamingYieldVault` (no seed-and-burn performed yet, or after a `redeem` has driven `totalSupply` low).
2. Attacker calls `vault.deposit(smallAmount, attacker)`, receiving a small nonzero share balance.
3. Attacker calls `asset.transfer(address(vault), largeAmount)` directly — no `approve`+`addYield`, no owner role required.
4. `totalAssets()` immediately reflects `balanceOf(vault)` including `largeAmount` (since `_lockedYield()` never accounted for it), inflating `convertToAssets`/`previewDeposit` in the same block, contradicting the "no instant jump" invariant documented at `docs/content/developers/evm/streaming-yield-vault.mdx:27`.
5. A subsequent depositor's `deposit()` shares round down against the inflated ratio; attacker's `redeem()` extracts a disproportionate share of the pooled assets.

        _startVesting(value);

    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
    
    /// @notice Add a new yield tranche, pulled from the caller. Reverts unless the previous
    ///         tranche has fully vested, which guarantees tranches never overlap and no yield
    ///         is ever left permanently locked.
    /// @param amount The amount of `asset` to stream in over `VEST`.
    function addYield(uint256 amount) external onlyOwner {
        // Pull the funds first so `balanceOf` already reflects `amount` before it is marked
        // locked; otherwise `totalAssets` would transiently underflow when a tranche exceeds
        // the current backing (e.g. the very first `addYield` on a near-empty vault).
        IERC20(asset()).safeTransferFrom(msg.sender, address(this), amount);

        _startVesting(amount);
    }

    /// @dev Arms a new tranche after validating the no-overlap / deposit-window guards. The caller
    ///      must have already moved `amount` of `asset` into the vault (so `balanceOf` reflects it
    ///      before `_vestingAmount` is set, avoiding a transient `totalAssets` underflow).
    function _startVesting(uint256 amount) private {
        if (amount == 0) revert ZeroAmount();

        uint256 start = _vestingStart;
        if (start != 0) {
            if (block.timestamp < start + VEST) revert YieldStillVesting(start + VEST);
            // Hold off until the guaranteed deposit window has elapsed, so new capital always has
            // a chance to enter between tranches regardless of how promptly the keeper runs.
            if (block.timestamp < start + VEST + MIN_WINDOW) revert DepositWindowOpen(start + VEST + MIN_WINDOW);
        }

        _vestingAmount = amount;
        _vestingStart = block.timestamp;

        emit YieldAdded(amount, block.timestamp);
    }
