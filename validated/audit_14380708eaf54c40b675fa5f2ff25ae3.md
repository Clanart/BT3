### Title
Change outputs between `wallet::DUST` (546) and `Bitcoin::DUST` (10,000) are created but never scanned, stranding funds — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Serai's Bitcoin code uses two different minimum-output thresholds on two different paths — mirroring the Mai `lotSize` vs `tradingLotSize` mismatch. `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` emits a change output whenever the leftover is `>= DUST = 546` satoshis, while the processor's scanner only registers outputs with `amount >= N::DUST`, where `Bitcoin::DUST = 10_000`. Any change output valued in `[546, 9_999]` sats is therefore created on-chain but silently ignored by the scanner, leaving funds at a Serai-controlled address that the protocol never accounts for or spends.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the wallet-level dust constant is `pub const DUST: u64 = 546` (line 32). When a change address is provided, the constructor pushes a change output if the leftover value satisfies `value >= DUST` (lines 224–234).

In `processor/src/networks/bitcoin.rs`, the network-level threshold is `const DUST: u64 = 10_000` (line 638), justified by an economic-spendability argument. In `processor/src/multisigs/scanner.rs` lines 564–566, scanned outputs are only pushed for registration when `output.balance().amount.0 >= N::DUST`.

`make_signable_transaction` (`processor/src/networks/bitcoin.rs` lines 446–451) calls `BSignableTransaction::new` with the multisig's change address. Because the change check inside `SignableTransaction::new` uses the wallet constant (546) rather than the network constant (10,000), a change output of 546–9,999 sats is produced, yet the scanner drops it as sub-dust. There is also an explicit compile-time assertion in `processor/src/tests/literal/mod.rs` line 53 that `Bitcoin::DUST >= bitcoin_serai::wallet::DUST`, confirming the two constants are intended to differ but no code reconciles the gap on the change path.

Additionally, `processor/src/networks/mod.rs` line 589 applies the same mismatch in reverse from the planner's side: change below `Self::DUST` (10,000) is merely tabulated as an `operating_cost` — but the transaction builder still emits the output down to 546 sats.

### Impact Explanation
An unprivileged user sending Bitcoin to a Serai multisig address controls the input values. The scheduler's choice of inputs plus the payment amounts determines the leftover. Whenever inputs − payments − fee lands in `[546, 9_999]`, a change output is created at the multisig's change address that the scanner will never register. Those funds are neither credited nor spendable through the protocol's normal flow — permanently stranded (or requiring manual out-of-band recovery). This is the analog of "left-over position not a multiple of tradingLotSize that cannot be closed": a residual below the operational threshold created by a path that only enforces the lower threshold.

### Likelihood Explanation
The window is 9,454 sats wide. Since change magnitude is determined by arbitrary user deposit amounts and median-fee-driven fee estimates, hitting the gap requires no special timing or privilege — only an input/payment/fee combination whose residue falls in the range. Aggregation and consolidation transactions with change make this plausible in ordinary operation. Severity is bounded (a sub-10,000-sat loss per occurrence), so Medium.

### Recommendation
Make `SignableTransaction::new` take the change-emission threshold as a parameter (or reuse the network's `DUST`) so that change is only created when `value >= Bitcoin::DUST`; otherwise let the residue roll into the fee, matching the planner's accounting in `processor/src/networks/mod.rs`.

### Proof of Concept
Sketch against `networks/bitcoin/tests/wallet.rs` / `processor` tests:

1. Fund the multisig address with a single `ReceivedOutput` of value `V`.
2. Call `Bitcoin::make_signable_transaction` with a payment of `P` such that `V - P - fee_with_change = 5_000` sats (≥ `wallet::DUST` 546, < `Bitcoin::DUST` 10,000).
3. The resulting `SignableTransaction` contains a change `TxOut` of 5,000 sats to `change_address(key)`.
4. After signing and broadcasting, the scanner at `processor/src/multisigs/scanner.rs:564` filters the change output (`5_000 < 10_000`) — it is never emitted as an output, never enters the scheduler's input set, and the 5,000 sats are stranded despite residing at a Serai-controlled key.
