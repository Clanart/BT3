## Title
Symlink escape via unvalidated `Path.join(repository.path, path)` in file-open/reveal actions bypasses the app's own `resolveWithin` sandboxing, enabling read/exposure of files outside the repo - (File: `app/src/lib/app-shell.ts`)

### Summary
GitHub Desktop has a dedicated, tested utility, `resolveWithin` (`app/src/lib/path.ts`), that resolves a repo-relative path with `realpath` and rejects it if it escapes the repository root — explicitly to defend against symlink-based directory-traversal from untrusted repository content (see `app/test/unit/path-test.ts:65-101`, which specifically tests "fails for paths that use a symlink to traverse outside of the root"). This guard is used in some newer code paths (e.g. Copilot conflict resolution: `app/src/lib/copilot-conflict-context.ts:390-407`, `app/src/lib/stores/app-store.ts:7233-7239`, and `app/src/ui/dispatcher/dispatcher.ts:1957-1971` for deep-link file opening), but several older, everyday user-facing actions still build the path with a plain `Path.join`/`Path.resolve` and hand it straight to Electron's shell APIs without ever checking whether the resolved target stays inside the repository.

### Finding Description
The double-counting bug in the report is really "a value that should be re-derived/validated at a trust boundary is instead trusted from a stale/attacker-influenced source, and no code path re-checks it." The Desktop analog: `file.path` values populated from `git status`/`git show` parsing (`app/src/lib/git/status.ts`, `app/src/lib/status-parser.ts`) are attacker-influenced content coming straight from a cloned/fetched repository. A malicious repo can legitimately (no ".." components required, so Git's own tree-path sanitization doesn't help) contain a **symlink** file, e.g. `notes.txt -> ../../../../.ssh/id_rsa` or pointing at browser credential stores, etc. When the user checks out/views this repo, Desktop happily lists it as a normal working-directory or committed file change.

Several context-menu / open actions then resolve that path with plain `Path.join(repository.path, path)` and pass the result to Electron's shell without ever calling `resolveWithin`:

- `revealInFileManager` — [1](#0-0) 
- `onOpenInExternalEditor` in the main app view — [2](#0-1) 
- Context menus in `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, and `unmerged-file.tsx` all call `revealInFileManager(repository, file.path)` / `Path.join(repository.path, relativeFilePath)` and pass the result to `openFile`, `dispatcher.openInExternalEditor`, or `shell.showItemInFolder` — [3](#0-2) [4](#0-3) 

None of these call sites re-derive/verify that the symlink target actually stays inside `repository.path`, unlike the newer `resolveWithin`-guarded flows. The `IAppShell.openPath`/`showItemInFolder` docstring itself flags this ("Do not use this method with non-validated paths") — [5](#0-4)  — confirming the developers know the guard is required but it isn't applied uniformly.

### Impact Explanation
An attacker who controls a cloned/fetched repository (matches the accepted threat model) can plant a symlink that resolves outside the working directory. When the victim right-clicks that entry in the Changes list, History, or a Pull Request diff and chooses "Reveal in Finder/Explorer," "Open in <editor>," or "Open with Default Program," Desktop opens/reveals the real target of the symlink — a file/directory outside the repository, potentially containing credentials (SSH keys, `.netrc`, cloud credential files) or other sensitive data. This is a file-read/exposure-outside-repo primitive triggered purely by normal repository interaction, matching the accepted impact category.

### Likelihood Explanation
Medium. It requires the victim to interact with the specific file via the context menu (not silent/automatic), but that's a completely ordinary workflow (reviewing changes, browsing history, reviewing a PR) and the entry looks like any other tracked file — nothing in the UI currently flags it as a symlink pointing outside the repo. On platforms where symlinks are checked out by default (macOS/Linux, and Windows in Developer Mode or with the relevant privilege), this requires no special local access, admin rights, or social engineering beyond opening a malicious/compromised repository, which is squarely the accepted attacker model.

### Recommendation
Route every path that is joined with `repository.path` and then handed to shell/editor APIs (`revealInFileManager`, `onOpenInExternalEditor`, `onOpenItem`/`openFile` handlers, the `unmerged-file.tsx` overflow menu, `pull-request-files-changed.tsx`, `selected-commits.tsx`) through `resolveWithin` (or an equivalent `realpath`-based containment check) before calling into `shell.showItemInFolder`, `shell.openPath`, or launching an external editor, mirroring what `copilot-conflict-context.ts` and `dispatcher.ts`'s `openRepositoryFromUrl` already do. If the resolved real path escapes the repository root, refuse the action and surface a clear "path outside repository" error instead of silently opening/revealing it.

### Proof of Concept
1. Attacker creates a public repo containing a symlink `evil -> ../../../../.ssh/id_rsa` (or on Windows, a directory junction pointing at `%USERPROFILE%`), committed normally (Git permits symlinked blobs; no ".." occurs in the tree path itself, only in the symlink's target).
2. Victim clones/fetches this repo in GitHub Desktop and views it (e.g., in History or the PR "Files changed" view, or simply checks it out so it appears as a working directory entry).
3. Victim right-clicks `evil` and selects "Reveal in Finder/Explorer" or "Open in <configured editor>" or "Open with Default Program."
4. `revealInFileManager`/`onOpenInExternalEditor` computes `Path.join(repository.path, 'evil')`, which the OS resolves through the symlink to `~/.ssh/id_rsa` (or another out-of-repo path), and Desktop calls `shell.showItemInFolder`/`shell.openPath`/the editor launcher on that resolved target — revealing/opening a file that is not part of, and was never intended to be part of, the repository. /**
 * Reveals a file from a repository in the native file manager.
 *
 * @param repository The currently active repository instance
 * @param path The path of the file relative to the root of the repository
 */
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
