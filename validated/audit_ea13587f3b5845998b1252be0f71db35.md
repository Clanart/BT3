### Title
CachedPreprocess seed is not bound to the signing set or keys, enabling deterministic nonce reuse across distinct FROST sessions and secret-share recovery - (File: crypto/frost/src/sign.rs)

### Summary
Analogous to the AppFlowy-Cloud flaw — where a session was bound to a "workspace" without validating the session's membership/context — `AlgorithmSignMachine::from_cache` resurrects a FROST sign machine from a bare 32-byte seed without binding that seed to the `ThresholdKeys`, participant set, or session it was created for. The nonces are derived deterministically from the seed alone, so invoking `from_cache` + `sign` twice with the same `CachedPreprocess` under different signing sets (different `included`, different binding factors, different messages) reuses identical FROST nonces `(d, e)`. Two shares produced with the same nonces but different binding factors/challenges yield two linear equations that recover `d`, `e`, and the signer's secret share `x_i`.

### Finding Description
`seeded_preprocess` derives all nonce material solely from the cached seed: `ChaCha20Rng::from_seed(*seed.0)` feeds `Commitments::new`, which calls `C::random_nonce(secret_share, rng)`. Nothing in this derivation incorporates the participant set, group key, message, or a session identifier, and `from_cache` performs no check that the supplied `keys` are the ones the cache was created under (`crypto/frost/src/sign.rs:121-145`, `:268-274`; `crypto/frost/src/nonce.rs:53-72`).

Downstream, `sign` computes per-participant binding factors `rho_l` from a transcript over `group_key`, `hash_msg(msg)`, and the preprocesses challenge (`sign.rs:361-371`), then forms the effective nonce as `base + actual * rho` (`sign.rs:386-396`). If the same seed is ever used for a second `sign` call — which the API does not prevent; `CachedPreprocess` is a plain `Zeroizing<[u8; 32]>` (`sign.rs:91-92`) and `from_cache` re-derives the same `nonces` and the same published `Preprocess` commitments — an observer obtains two shares:

- `s_1 = d + rho_1 * e + lambda_1 * x_i * c_1`
- `s_2 = d + rho_2 * e + lambda_2 * x_i * c_2`

with `d`, `e` identical across both. With `rho_1 != rho_2` or `c_1 != c_2` (guaranteed whenever the participant set or message differs), these are two independent equations; combined with the published commitments `D = d*G`, `E = e*G`, solving yields `d`, `e`, and then `x_i` — the victim's FROST secret share.

This is the exact "cross-workspace session binding" shape: the sign machine binds the session (the cached preprocess) to whatever `keys`/`preprocesses`/`msg` are handed to it, with no membership/context check tying the cached nonce material to a single authorized signing instance. The library's own warning comments acknowledge reuse leaks the share but place the entire burden on callers, while the type system and API actively make silent reuse possible — `cache()` returns the seed, `from_cache` accepts any `(algorithm, keys, cache)` triple, and there is no session-attempt binding, consumed flag, or keys-fingerprint check anywhere in `crypto/frost`.

### Impact Explanation
Recovery of a validator's FROST secret share `x_i`. Combined with `t-1` other compromised or cooperatively-recovered shares, or used in share-forgery/credential-mixing attacks against the threshold scheme, this breaks the confidentiality of the threshold key material. Even short of full key reconstruction, a leaked share enables signature-share forgery attributed to the victim participant. Reachable whenever a deployment reuses a cached preprocess across a retried signing attempt whose participant set or message differs — a retry-with-different-set flow is precisely the scenario caching exists for (crash recovery mid-sign), so the unsafe state is one misordered coordinator retry away rather than exotic.

### Likelihood Explanation
Medium. Exploitation requires the victim to call `sign` twice from the same `CachedPreprocess` under differing `included` sets or messages. The deterministic derivation makes any such double-use fatal — there is no randomness left to save it — but inducing it requires influencing the victim's signing orchestration (e.g., forcing a signing attempt to abort after `preprocess` dissemination and restart with a different elected set). The code provides no defense-in-depth: `seeded_preprocess` could cheaply mix `keys.params()`/`group_key()` into the nonce derivation or reject `from_cache` with mismatched keys, and does neither.

### Recommendation
Bind cached preprocesses to their context at the cryptographic layer:

- In `seeded_preprocess`, derive the ChaCha20 seed as `H(seed || keys.params().encode() || keys.group_key().to_bytes())` so the same `CachedPreprocess` under a different `ThresholdKeys` produces unrelated nonces.
- Have `from_cache` verify the cached material was generated for the supplied `keys` (store/commit to a keys fingerprint alongside the seed) and error on mismatch rather than silently re-deriving.
- Consider making `CachedPreprocess` single-use by construction (consume-on-`from_cache` wrapper or an external nonce-usage counter transcripted into the RNG seed).

### Proof of Concept
```rust
// Conceptual PoC against crypto/frost
// 1. Victim caches a preprocess under signing set A.
let (machine_a, our_preprocess) =
    AlgorithmMachine::new(alg.clone(), keys.clone()).preprocess(&mut rng);
let cache: CachedPreprocess = machine_a.cache();

// 2. Session A: victim signs msg_a with preprocesses for set A.
let (m1, share1) =
    AlgorithmSignMachine::from_cache(alg.clone(), keys.clone(), CachedPreprocess(Zeroizing::new(*cache.0)))
        .0
        .sign(preprocesses_set_a, msg_a).unwrap();

// 3. Session B ("different workspace"): same seed, different elected set or message.
//    from_cache re-derives identical (d, e) because only the seed drives ChaCha20Rng.
let (m2, share2) =
    AlgorithmSignMachine::from_cache(alg.clone(), keys, CachedPreprocess(Zeroizing::new(*cache.0)))
        .0
        .sign(preprocesses_set_b, msg_b).unwrap();

// 4. share1 = d + rho1*e + lam1*x*c1 ; share2 = d + rho2*e + lam2*x*c2
//    rho, lambda, c are all publicly derivable from the transcripts and participant sets.
//    Two equations, unknowns (d, e, x): with rho1*c1*lam1 vs rho2*c2*lam2 distinct,
//    solve the linear system (with D = d*G, E = e*G as consistency checks) to recover x,
//    the victim's secret share.
```

The victim's published `Preprocess` in both sessions contains identical `Commitments` (`D`, `E` per generator), making reuse externally observable and confirming the two shares are solvable before attempting recovery.
