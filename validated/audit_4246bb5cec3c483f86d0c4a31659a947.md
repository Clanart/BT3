### Title
Distribution precompile's `rewards()` view accepts and permanently strands attached native value - (File: `precompiles/distribution/distribution.go`)

### Summary
The `rewards` method of the distribution precompile (address `0x0000000000000000000000000000000000001007`) is dispatched without a non-payable guard, unlike all its sibling query methods. A caller can attach `usei`/`wei` value to a `rewards(...)` call; the EVM state-transition will debit the caller and credit the precompile's module account balance before the precompile logic runs, but the precompile logic never processes or refunds that value.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` [1](#0-0)  with no `value` parameter and no call to `pcommon.ValidateNonPayable(value)`. Every other query-style handler in the same file enforces this via `validateInput`, which explicitly rejects non-zero `value`: [2](#0-1) . The `rewards` function itself only validates argument length and never touches `value`: [3](#0-2) .

Because the distribution precompile address is not present in `payablePrecompiles` (only `bank`, `staking`, `gov`, `wasmd` are listed) [4](#0-3) , value sent to it is not expected/handled by the payment-refund machinery (`HandlePaymentUsei`/`HandlePaymentUseiWei`) that other payable precompile methods use to route the debited usei back to the correct beneficiary [5](#0-4) . Since `rewards()` bypasses the `ValidateNonPayable` guard that would otherwise reject the call outright, a value-bearing call to `rewards()` succeeds, the state transition still moves the attached `usei`/`wei` from caller to the precompile module account (standard EVM CALL value-transfer semantics), and the precompile code path never issues any corresponding `SendCoins` refund because it doesn't call `HandlePaymentUsei` at all.

This exact quirk is called out in the project's own integration test comments: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds), so this spec deliberately has no 'view rejects value' test." [6](#0-5) 

### Impact Explanation
A user or contract that mistakenly (or via a buggy integrating contract) attaches `msg.value` to a `rewards()` call to the distribution precompile permanently loses that value: the funds are debited from the caller's EVM balance and land in the distribution precompile's associated account, with no method exposed to withdraw/refund them back to the sender. This is a direct, permanent loss of user funds analogous to the UXDController `receive()` issue, though here it's worse because it's a silently-succeeding "view" call (returns valid reward data) rather than an obviously fund-only transfer, making it easier for calling contracts/wallets to trigger unintentionally (e.g., a contract that forwards `msg.value` indiscriminately to every call it proxies, as seen in `PrecompileCaller.callTarget`) [7](#0-6) .

### Likelihood Explanation
Likelihood is moderate: it requires a caller to explicitly set non-zero `value` on a call to the `rewards` selector on the distribution precompile. This wouldn't happen with the precompile's own generated `Distribution.sol` interface bindings under normal, correct usage patterns, but any generic call-forwarding contract, misconfigured SDK, or user directly crafting a raw transaction with value set can trigger it. It's a straightforward, single-transaction, unprivileged action requiring no special setup.

### Recommendation
Add the same non-payable guard used by the other view methods to `RewardsMethod` dispatch, e.g., call `pcommon.ValidateNonPayable(value)` (or route through `validateInput`) before invoking `p.rewards`, so that a value-bearing call reverts instead of silently stranding funds.

### Proof of Concept
1. Associate an EOA address with a Sei account and ensure it has delegated to a validator (so it has queryable rewards).
2. Call the distribution precompile at `0x0000000000000000000000000000000000001007` with the `rewards(address)` selector and non-zero `value` (e.g., `1000000000000000000` wei) attached, either directly or via a call-forwarding contract such as `PrecompileCaller.callTarget`.
3. Observe the call succeeds and returns valid reward data (no revert), while the caller's EVM balance is decremented by the attached value.
4. Observe there is no subsequent balance credit back to the caller; the value is now held by the precompile's associated module account with no exposed method to reclaim it — matching the finding described in the codebase's own test comment at `integration_test/precompile_tests/precompiles/distribution.spec.ts:1-12`.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
