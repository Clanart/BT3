### Title
`ValPaused` validators are never re-promoted to `ValActive` after winning the top-N stake competition, permanently excluding them from reward eligibility - ([File: kaiax/valset/impl/transition_context.go])

### Summary
`kaiax/valset`'s `applyEpochTransition` re-evaluates the top-N stake competition every epoch and is supposed to admit qualifying validators into the reward-eligible `ValActive` state. However, the code explicitly skips this promotion for validators that are currently in `ValPaused`, even when they win a top-N slot. Since block-reward eligibility is gated strictly on `NodeState == ValActive` (`IsRewardEligible()`), a validator stuck in `ValPaused` keeps losing rewards indefinitely, mirroring the Munchables `transferToUnoccupiedPlot` bug where a "dirty"/ineligible flag is never reset after the account returns to a state that should qualify for rewards again.

### Finding Description
`IsRewardEligible()` defines reward eligibility purely by state: [1](#0-0) 

During the epoch transition, `ValPaused` validators are grouped with `ValActive`/`ValReady`/`CandTesting` into `activeValCompetitors` and re-ranked by stake: [2](#0-1) 

When a competitor wins a top-N slot (`idx < MaxValActivePausedCount`), the promotion logic explicitly excludes anyone whose current state is `ValPaused`: [3](#0-2) 

```go
for idx, potentialActiveVal := range activeValCompetitors {
    if uint64(idx) < ctx.MaxValActivePausedCount {
        if potentialActiveVal.State != valset.ValPaused {
            potentialActiveVal.State = valset.ValActive
            potentialActiveVal.IdleTimeout = time.Time{}
            potentialActiveVal.PausedTimeout = time.Time{}
        }
    } else {
        ...
    }
}
```

This is structurally identical to the Munchables bug: the transition path that is supposed to restore a validator to an eligible state (`ValActive`) after it "qualifies again" (top-N stake) does not reset the disqualifying flag (`State == ValPaused`). The only other place `ValPaused` is left is `applyTimeoutTransition`, which demotes it to `ValInactive` after `PauseTimeout` expires — there is no code path that promotes a `ValPaused` validator back to `ValActive`: [4](#0-3) 

Consequently, once a validator is paused (e.g. via a PFS minor-violation transition, see `applyViolationTransition`): [5](#0-4) 
increasing its stake and re-winning a top-N slot does not restore reward eligibility. It remains `ValPaused` (non-reward-eligible) until the fixed `PauseTimeout` elapses and it is demoted to `ValInactive`, rather than becoming `ValActive` again despite having sufficient/competitive stake.

### Impact Explanation
An affected validator continues to lose the block/staking rewards it should be entitled to under `kaiax/reward` (`assignStakingRewards`/`ConsolidatedNodes`, which only count `ValActive` reward recipients), and the reward budget that should have gone to that validator is instead redistributed among the remaining active validator set. This is a reward-redirection/misallocation issue: honest, well-staked validators are denied earned rewards while others (who did not increase relative stake) receive a larger share, for the duration of the pause window (and effectively longer than intended, since the validator cannot self-heal by staking more before the timeout).

### Likelihood Explanation
This path is reachable purely through standard, permissionless actions: a validator gets `ValPaused` due to a PFS minor violation during normal consensus operation, and its operator (or delegators) subsequently increases the staking amount via ordinary staking transactions to try to re-qualify. This requires no privileged access, malicious peer, or consensus-message manipulation — only routine staking transactions and epoch-boundary block processing, which happens automatically. The likelihood of validators encountering pause states over time is realistic, especially under the vrank/PFS liveness-scoring mechanism this module implements.

### Recommendation
In `applyEpochTransition`'s top-N promotion loop, remove the special-casing that skips `ValPaused` validators: if a currently-paused validator wins a top-N stake slot, it should be transitioned to `ValActive` (clearing `PausedTimeout`/`IdleTimeout`) just like any other competitor, consistent with the stated intent that `MaxValActivePausedCount` competitors regain active/reward-eligible status. If ValPaused is intended to enforce a mandatory minimum wait rather than be liftable by stake, that behavior should be explicit and documented, and the reward/eligibility model should account for it (e.g., partial reward accrual) rather than silently and permanently forfeiting rewards.

### Proof of Concept
1. A validator (call it V) with `State = ValActive` incurs a PFS minor violation in a block where `PfReport` is non-empty and `0 < PFS[V] < PfsThreshold`; `applyViolationTransition` moves it to `ValPaused` (kaiax/valset/impl/transition_context.go:372-379).
2. Before `PauseTimeout` elapses, V's stake is increased via a normal staking transaction so that at the next epoch boundary V ranks within the top `MaxValActivePausedCount` stakers (`activeValCompetitors`, transition_context.go:188-225).
3. In the promotion loop (transition_context.go:226-239), because `potentialActiveVal.State == valset.ValPaused`, the `if` branch is skipped — V's state remains `ValPaused`.
4. `IsRewardEligible()` returns `false` for `ValPaused` (types.go:60-63), so `kaiax/reward`'s staking-reward assignment continues to exclude V from `ConsolidatedNodes`/staker rewards every subsequent block until `PauseTimeout` finally expires and V is demoted to `ValInactive` (transition_context.go:406-414) — never regaining `ValActive` through the stake-competition path despite having re-qualified.

Note on uncertainty: I could not find, within the indexed portion of the repository, any other code path (e.g., an explicit unpause/resume RPC or AddressBookV2 call) that promotes `ValPaused` back to `ValActive` outside of this epoch-transition logic. If such a path exists elsewhere in the codebase (e.g., in system contracts not covered by the index), the severity of this finding would need to be reassessed; I recommend confirming this in a full Devin session with complete file access.
