### Title
Unvalidated `clone_url` from the GitHub API silently rewrites the local `origin` remote - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` compares the locally configured `origin` remote against a `clone_url` field taken from a `GitHubRepository`/`IAPIFullRepository` object fetched from the GitHub API, and if a loose heuristic match passes, it calls `gitStore.setRemoteURL` to rewrite the remote with **no user confirmation and no ownership/identity re-verification** beyond a same-protocol check.

### Finding Description
`updateRemoteUrl` is invoked whenever Desktop refreshes GitHub-associated repository metadata. It performs the following checks before mutating the remote: [1](#0-0) 

The only real gates are: (1) the *previously cached* `clone_url` still matches the current remote (`remoteUrlUnchanged`), and (2) the URL protocol (`http:`/`https:`/`ssh:`) of the old and new URL are the same. Crucially, `urlMatchesRemote` (used for `remoteUrlUnchanged` and for the `urlsMatch` check) only compares hostname/owner/name of parsed URLs — it never confirms that the *new* `updatedRemoteUrl` still points to the same owner/repo as the one the user originally cloned: [2](#0-1) 

Once the loose check passes, the code calls `gitStore.setRemoteURL`, which shells out directly to `git remote set-url`: [3](#0-2) [4](#0-3) 

The `clone_url` value ultimately comes from a `GitHubRepository` object built from GitHub/GHE API responses (`IAPIFullRepository`), i.e., attacker-influenced data if the GitHub Enterprise server the user is pointed at is malicious/compromised, or if an on-path/API response is manipulated (a "GitHub API object" per the task's allowed attacker classes). There is no allow-list, no re-validation that the new `owner`/`name` matches what the user originally added, and no user prompt — this mirrors the original report's core flaw: a downstream critical value (`Registry.timelock` / here, the git remote URL) is written based on unvalidated upstream input, and the consuming code (`setRegistry` / here, `setRemoteURL`) has no independent sanity check to reject an implausible value.

### Impact Explanation
If exploited, the user's `origin` remote silently points to an attacker-controlled host while the UI continues to show the repository as connected to the expected GitHub project. Any subsequent `git push` sends the user's code (and, depending on transport, credentials via the corresponding credential helper flow in `app/src/lib/trampoline/trampoline-credential-helper.ts`) to the attacker's endpoint instead of the intended repository — this is "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes.

### Likelihood Explanation
Likelihood is constrained by the same-protocol requirement and by the fact that `remoteUrlUnchanged` must hold (i.e., the user hasn't manually customized their remote), and this code path only runs against data returned by a GitHub.com/GHE API endpoint the user has already authenticated against — so exploitation practically requires a malicious or compromised GHE server (a scenario explicitly permitted under the task's "attacker controls…a GitHub API object" criterion) rather than any local/host compromise. I could not fully trace every call site that feeds `updateRemoteUrl` in `app-store.ts` within my remaining search budget, so I cannot state with certainty every UI trigger path (e.g., background refresh vs. explicit user action) that invokes it — this should be verified with a full read of `app/src/lib/stores/app-store.ts` around its `updateRemoteUrl(` call site.

### Recommendation
Before calling `setRemoteURL` in `updateRemoteUrl`, re-verify that the new `clone_url`'s owner/name still matches the `GitHubRepository` the user originally associated with (not just protocol), and surface a user-visible confirmation/diff when the remote host or owner actually changes, rather than rewriting it silently.

### Proof of Concept
1. User adds/authenticates against a GitHub Enterprise server (attacker-controlled or compromised) and clones a repo, so `origin` = `https://ghe.example.com/org/repo.git`.
2. The malicious GHE server later returns an `IAPIFullRepository` object for that same `owner/name` combination but with `clone_url` pointing to `https://ghe.example.com-evil.com/org/repo.git` sharing the same protocol.
3. On the next repository metadata refresh, `updateRemoteUrl` passes `remoteUrlUnchanged` and `protocolsMatch`, finds `urlsMatch` false, and calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com-evil.com/org/repo.git')` with no prompt, per `app/src/lib/stores/updates/update-remote-url.ts:42-44`.
4. The user's next `git push` from Desktop's UI silently goes to the attacker's server.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
