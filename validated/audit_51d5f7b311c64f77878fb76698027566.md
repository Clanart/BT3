## Title
Unsanitized filenames with embedded `\n`/`\t` in `formatPatchHeaderForFile` allow diff-header injection into `git apply --cached` - ([File: app/src/lib/patch-formatter.ts])

### Summary
`formatPatchHeaderForFile` builds the `--- `/`+++ ` header lines for a patch that is later piped to `git apply --cached -` via stdin, using the raw `file.path` value with no escaping of control characters such as newline or tab.

### Finding Description
`getStatus` in `app/src/lib/git/status.ts` invokes `git status --porcelain=2 -z`, and the parser explicitly documents that in `-z` mode "filenames containing special characters are not specially formatted; no quoting or backslash-escaping is performed" [1](#0-0) . This is directly confirmed by an existing unit test that shows a path containing a literal embedded newline is parsed verbatim into `IStatusEntry.path` [2](#0-1) . That raw path is stored unmodified into `WorkingDirectoryFileChange` [3](#0-2) .

When staging a partial commit for a new/untracked file, `formatPatch` calls `formatPatchHeaderForFile(file)`, which for `AppFileStatusKind.New`/`Untracked` calls `formatPatchHeader(null, file.path)` [4](#0-3) . `formatPatchHeader` interpolates the path directly into the header line with no sanitization: `` `--- ${fromPath}\n+++ ${toPath}\n` `` [5](#0-4) . If `file.path` contains a literal `\n`, the single `+++ b/<path>` header line is split into two lines when written to the patch text body, and if it contains a `\t`, the tab could be misinterpreted as the (optional) timestamp field delimiter that real Git diff headers use.

The resulting patch string is passed as raw stdin to `git apply --cached --unidiff-zero --whitespace=nowarn -` [6](#0-5) , so `git apply`'s own parser processes whatever line structure ends up in the header block, not just what Desktop intended as a single header entry. Real Git itself is aware of this exact hazard: when git itself constructs diff/status output, it C-style quotes filenames containing tabs, newlines, or backslashes (independent of `core.quotePath`) precisely to prevent this kind of header ambiguity. Desktop's `formatPatchHeader`/`formatPatchHeaderForFile` does not replicate this quoting — it performs no escaping of the path at all.

### Impact Explanation
If an attacker can get a victim to clone/fetch a repository (or otherwise cause an untracked file to appear on disk) whose filename contains a raw newline or tab — which several filesystems and Git itself can represent via `-z`/tree entries — and the victim performs a partial (line-level) stage/commit of that file in Desktop, the crafted header could be parsed by `git apply --cached` as containing an extra/second file path token in the header. This falls in the "silent corruption of what the user commits" impact category described in the bounty scope, since the user's index could be mutated to reference a path other than the one intended, or the patch could fail/behave in an unexpected way not visible to the user.

### Likelihood Explanation
Exploitation requires: (1) a filename with an embedded literal newline/tab actually reaching Desktop's status entry unmangled (confirmed possible via `-z` porcelain parsing per the test at `app/test/unit/status-parser-test.ts:95-107`), and (2) the user choosing to do a **partial** stage (selecting less than the whole file) on that specific untracked/new file, since whole-file staging goes through `git add`, not `formatPatch`/`git apply`. I was not able to fully verify within this session whether `git apply`'s own header parser would actually treat an embedded raw `\n` inside the `+++ b/<path>` line as a syntax/parse error (likely, since `git apply` expects the line to end right after the path or a tab-delimited timestamp) versus silently accepting a "two-line" header as a legitimate second entry. This directly affects whether `git apply --cached` would error out (safe, but still a functional bug) or successfully act on an attacker-chosen second path (the higher-severity outcome alleged in the question). This distinction needs to be verified experimentally/empirically (e.g., in a Devin session with a shell) rather than through static code reading alone.

### Recommendation
- Add filename quoting/escaping (matching Git's `quote_c_style` behavior: quote and escape any path containing control characters like `\n`, `\t`, `"`, or `\\`) inside `formatPatchHeader`/`formatPatchHeaderForFile` in `app/src/lib/patch-formatter.ts` before interpolating into the `--- `/`+++ ` lines.
- Alternatively/additionally, reject or refuse partial-stage operations on files whose `file.path` contains control characters, surfacing an error to the user instead of silently constructing a patch.

### Proof of Concept
Conceptual PoC (not fully verified against real `git apply` behavior in this session — recommend confirming via a Devin session with shell access):
1. On a filesystem/Git setup that allows creating a tracked or untracked file whose name contains a literal newline (e.g. via a crafted tree object cloned from a malicious remote, since Git blobs/trees can store arbitrary byte sequences in path names), have the victim clone that repository.
2. In GitHub Desktop's Changes list, select the file and use partial line-selection staging (not "select all"), which routes through `applyPatchToIndex` → `formatPatch` → `formatPatchHeaderForFile` → `git apply --cached`.
3. Inspect the exact bytes sent to `git apply` on stdin (`app/src/lib/git/apply.ts:80-81`) to confirm whether the embedded `\n` in the header causes `git apply` to parse a second/different file path, versus simply erroring out. [7](#0-6) [8](#0-7) [9](#0-8)

function formatPatchHeader(from: string | null, to: string | null): string {
  // https://en.wikipedia.org/wiki/Diff_utility
  //
  // > At the beginning of the patch is the file information, including the full
  // > path and a time stamp delimited by a tab character.
  // >
  // > [...] the original file is preceded by "---" and the new file is preceded
  // > by "+++".
  //
  // We skip the time stamp to match git
  const fromPath = from ? `a/${from}` : '/dev/null'
  const toPath = to ? `b/${to}` : '/dev/null'

  return `--- ${fromPath}\n+++ ${toPath}\n`
}
