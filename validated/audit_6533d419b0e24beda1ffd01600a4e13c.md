### Title
Clawback puzzle decorator drops REMARK metadata for multi-output sends, permanently locking swept funds - (File: chia/wallet/puzzles/clawback/puzzle_decorator.py)

### Summary
This maps to the same bug class as the ERC1155 report: a "reply/metadata encoding" step uses the wrong condition (or omits it) relative to what the puzzle-hash-construction step actually produced, so the message needed to recover/settle the funds never gets attached, and the resulting coin becomes unrecoverable. In Chia's wallet, `ClawbackPuzzleDecorator.decorate_target_puzzle_hash()` unconditionally wraps *every* requested output into a `P2_1_OF_N` clawback merkle puzzle hash [1](#0-0) , but `ClawbackPuzzleDecorator.solve()` only emits the `REMARK`/`ClawbackMetadata` condition that records `time_lock`, `sender_puzzle_hash`, and `recipient_puzzle_hash` when there is exactly **one** primary output [2](#0-1) .

### Finding Description
`Wallet._generate_unsigned_transaction()` builds two parallel lists per output: `decorated_target_puzzle_hashes` (the actual on-chain puzzle hash, produced by `decorate_target_puzzle_hash`, which is applied per-output regardless of count) and `target_primaries` (the un-decorated `CreateCoin` list passed straight into `decorator_manager.solve(...)`) [3](#0-2) .

`PuzzleDecoratorManager.decorate_target_puzzle_hash` loops over every requested `newpuzzlehash` independent of how many outputs there are, so a multi-output spend (e.g. paying two or more addresses in one transaction) with the Clawback decorator enabled will still create *every* coin as a real `P2_1_OF_N` clawback merkle-puzzle coin [4](#0-3) . But `PuzzleDecoratorManager.solve` is fed `target_primaries`, which contains one `CreateCoin` per requested output; when the count is anything other than 1, `ClawbackPuzzleDecorator.solve()`'s `if len(primaries) == 1:` guard is false, so no `REMARK` condition (and hence no `ClawbackMetadata`) is ever inserted into the coin's spend [2](#0-1) .

This `REMARK` condition is the *only* mechanism the wallet uses to recover `time_lock`, `sender_puzzle_hash`, and `recipient_puzzle_hash` for a clawback coin: `match_clawback_puzzle()` parses conditions from the spend looking specifically for this `REMARK`, and if it's absent, returns `None` (no metadata) [5](#0-4) . `ClawbackManager.identify()` requires this same `ClawbackMetadata` to classify a coin as `CoinType.CLAWBACK` and to look up sender/recipient derivation records; without it, the coin is invisible to clawback tracking/auto-claim logic [6](#0-5) . Both the eventual claim (`spend_clawback_coins`) and manual claw-back paths (`generate_clawback_spend_bundle`) need `metadata.time_lock`, `metadata.sender_puzzle_hash`, and `metadata.recipient_puzzle_hash` to reconstruct the exact merkle tree/proof required to spend the `P2_1_OF_N` puzzle [7](#0-6) , [8](#0-7) . If this metadata was never recorded anywhere (not in the spend, and consequently not in the wallet DB), no party — sender or recipient — has enough on-chain or off-chain information to rebuild the merkle proof and inner puzzle needed to spend the coin, since the actual `time_lock` value used server-side is only known from wallet config (which a different wallet instance, or after config change, would not have) and the exact merkle tree structure requires exact preimages of both `sender_ph` and `recipient_ph`.

### Impact Explanation
This is a direct token-loss bug reachable purely from normal wallet-user actions: enabling the Clawback puzzle decorator and sending to more than one destination in a single `send_transaction`/`create_signed_transaction` call (a totally ordinary CLI/RPC operation) silently mis-encodes the accompanying metadata condition relative to the puzzle hash actually chosen for the coin — mirroring the ERC1155 "wrong selector for the reply path" bug exactly: the on-chain artifact (coin puzzle hash) is correctly constructed for one flow (clawback-protected payment) while the auxiliary information needed to complete/recover that flow (the metadata condition) is built for a different assumption (single-output) and silently dropped. The result can be coins locked under a `P2_1_OF_N` puzzle that neither the wallet UI, the recipient, nor the sender can identify or reconstruct a valid solution for, permanently freezing the swept funds.

### Likelihood Explanation
Any wallet user who configures the Clawback puzzle decorator (a first-class, user-facing feature exposed via RPC `puzzle_decorator_override`/config) and issues a multi-output transaction (multiple `additions`, which is fully supported by `CreateSignedTransaction`/`send_transaction`) triggers this mismatch deterministically — no attacker or malicious peer is required.

### Recommendation
Make `ClawbackPuzzleDecorator.solve()` emit one `REMARK`/`ClawbackMetadata` condition per primary output (looping over all `primaries`, not just requiring `len(primaries) == 1`), matching the per-output wrapping already performed by `decorate_target_puzzle_hash`. Add integration tests covering multi-output Clawback-enabled transactions to confirm every resulting coin's metadata can be independently recovered and spent (both claim and claw-back paths).

### Proof of Concept
1. Configure the wallet to always apply the `CLAWBACK` puzzle decorator with some `clawback_timelock`.
2. Call `send_transaction`/`create_signed_transaction` with **two or more** `additions` (multiple destination puzzle hashes) in a single call, so `newpuzzlehashes` (and thus `target_primaries`) has length > 1.
3. Observe in `Wallet._generate_unsigned_transaction` that `decorated_target_puzzle_hashes` still wraps each output into a `P2_1_OF_N` merkle-puzzle hash via `decorate_target_puzzle_hash`, but `decorator_manager.solve(inner_puzzle, target_primaries, solution)` is called with `len(target_primaries) > 1`, so `ClawbackPuzzleDecorator.solve()`'s `if len(primaries) == 1` branch is skipped and no `REMARK` clawback-metadata condition is added.
4. Push the resulting spend bundle. The created coins have puzzle hashes matching real clawback merkle puzzles, but no wallet (sender's or recipient's) can call `match_clawback_puzzle` successfully on the parent spend to recover `time_lock`/`sender_puzzle_hash`/`recipient_puzzle_hash`, so `ClawbackManager.identify` never classifies/tracks them and neither `spend_clawback_coins` (claim) nor `generate_clawback_spend_bundle` (claw back) can be invoked with correct parameters — the coins become unspendable.

```python
        self, inner_puzzle: Program, primaries: list[CreateCoin], inner_solution: Program
    ) -> tuple[Program, Program]:
        # Append REMARK condition [1, "CLAWBACK", TIME_LOCK, SENDER_PUZHSAH, RECIPIENT_PUZHSAH]
        if len(primaries) == 1:
            recipient_puzhash = primaries[0].puzzle_hash
            metadata = ClawbackMetadata(self.time_lock, inner_puzzle.get_tree_hash(), recipient_puzhash)
            remark_condition = Program.to(
                [
                    ConditionOpcode.REMARK.value,
                    RemarkDataType.CLAWBACK,
                    bytes(VersionedBlob(ClawbackVersion.V1.value, bytes(metadata))),
                ]
            )
            # Insert the REMARK condition into the condition list
            conditions = remark_condition.cons(inner_solution.rest().first().rest())
            conditions = inner_solution.rest().first().first().cons(conditions)
            inner_solution = inner_solution.replace(rf=conditions)
        return self.decorate(inner_puzzle), inner_solution
```

```python
def create_merkle_puzzle(timelock: uint64, sender_ph: bytes32, recipient_ph: bytes32) -> Program:
    merkle_tree = create_clawback_merkle_tree(timelock, sender_ph, recipient_ph)
    puzzle: Program = P2_1_OF_N.curry(merkle_tree.calculate_root())
    return puzzle


def create_merkle_solution(
    timelock: uint64,
    sender_ph: bytes32,
    recipient_ph: bytes32,
    inner_puzzle: Program,
    inner_solution: Program,
) -> Program:
    """
    Recreates the full merkle tree of a p2_1_of_n clawback coin. It uses the timelock and each party's
    puzhash to create the tree.
    The provided inner puzzle must hash to match either the sender or recipient puzhash
    If it's the sender, then create the clawback solution. If it's the recipient then create the claim
    solution.
    Returns a program which is the solution to a p2_1_of_n clawback.
    """
    merkle_tree = create_clawback_merkle_tree(timelock, sender_ph, recipient_ph)
    inner_puzzle_hash = inner_puzzle.get_tree_hash()
    if inner_puzzle_hash == sender_ph:
        cb_inner_puz = create_p2_puzzle_hash_puzzle(sender_ph)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_p2_puzzle_hash_solution(inner_puzzle, inner_solution)
    elif inner_puzzle_hash == recipient_ph:
        condition = [80, timelock]
        cb_inner_puz = create_augmented_cond_puzzle(condition, inner_puzzle)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_augmented_cond_solution(inner_solution)
    else:
        raise ValueError("Invalid Clawback inner puzzle.")
    solution: Program = Program.to([merkle_proof, cb_inner_puz, cb_inner_solution])
    return solution
```

```python
def match_clawback_puzzle(
    unknown_puzzle: UnknownPuzzle,
    inner_puzzle: Program | SerializedProgram,
    inner_solution: Program | SerializedProgram,
) -> ClawbackMetadata | None:
    # Check if the inner puzzle is a P2 puzzle
    if MOD != unknown_puzzle.mod:
        return None
    if not isinstance(inner_puzzle, SerializedProgram):
        inner_puzzle = inner_puzzle.to_serialized()
    if not isinstance(inner_solution, SerializedProgram):
        inner_solution = inner_solution.to_serialized()
    # Fetch Remark condition
    conditions = conditions_for_solution(
        inner_puzzle,
        inner_solution,
        DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM // 8,
    )
    metadata: ClawbackMetadata | None = None
    new_puzhash: set[bytes32] = set()
    if conditions is not None:
        for condition in conditions:
            if (
                condition.opcode == ConditionOpcode.REMARK
                and len(condition.vars) == 2
                and int.from_bytes(condition.vars[0], "big") == RemarkDataType.CLAWBACK
            ):
                try:
                    metadata = ClawbackMetadata.from_bytes(VersionedBlob.from_bytes(condition.vars[1]).blob)
                except Exception:
                    # Invalid Clawback metadata
                    log.error(f"Invalid Clawback metadata {condition.vars[1].hex()}")
                    return None
            if condition.opcode == ConditionOpcode.CREATE_COIN:
                new_puzhash.add(bytes32.from_bytes(condition.vars[0]))
    # Check if the inner puzzle matches the coin puzzle hash
    if metadata is None:
        return metadata
    puzzle: Program = create_merkle_puzzle(
        metadata.time_lock, metadata.sender_puzzle_hash, metadata.recipient_puzzle_hash
    )
    if puzzle.get_tree_hash() not in new_puzhash:
        # The metadata doesn't match the inner puzzle, ignore it
        log.error(
            f"Clawback metadata {metadata} doesn't match inner puzzle {inner_puzzle.get_tree_hash().hex()}"
        )  # pragma: no cover
        return None  # pragma: no cover
    return metadata
```
