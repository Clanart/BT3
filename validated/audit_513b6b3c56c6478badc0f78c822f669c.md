### Title
`ReceivedOutput::read` accepts an arbitrary scalar offset unbound to the output's `script_pubkey`, allowing unspendable "received" outputs to be injected - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to Dexible's `selfSwap` accepting a user-supplied router address it never verified on-chain, `ReceivedOutput::read` accepts a user-supplied `(offset, TxOut, OutPoint)` triple and never verifies the offset actually derives the public key committed by `output.script_pubkey`. Bytes that `Scanner::scan_transaction` could never legitimately produce are accepted as spendable received funds.

### Finding Description
`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` map where every entry is only inserted by `register_offset`, which derives the script via `p2tr_script_buf(self.key + GENERATOR * offset)` (mod.rs:180-196). `scan_transaction` therefore only ever emits `ReceivedOutput`s where the offset provably maps the group key to the output's `script_pubkey` (mod.rs:199-214).

`ReceivedOutput::read`, however, deserializes the offset scalar, `TxOut`, and `OutPoint` independently over the wire with no consistency check:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output = TxOut::consensus_decode(&mut buf_r)...;
  let outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

An unprivileged party who can feed bytes into `ReceivedOutput::read` can submit a real on-chain `TxOut`/`OutPoint` (e.g., a payment paying to themselves, or a dust output with an arbitrary script) paired with any scalar. The object is then structurally indistinguishable from a scanner-produced deposit and reports `value()` as spendable balance.

The only downstream guard is `SignableTransaction::multisig` (send.rs:273-285), which checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` and returns `None` on mismatch — meaning the false input is caught only at spend time, after the output has already been recorded as received funds, and causes transaction construction to fail entirely.

### Impact Explanation
- **Funds reported received that are not spendable**: a crafted `ReceivedOutput` causes the wallet layer to account for a deposit whose claimed key path does not exist. If credited, the deposit is unrecoverable by the signer set (the offset produces a key unrelated to the script) — funds effectively burned while reported as held.
- **DoS / batch stall**: because `multisig` returns `None` for the whole `SignableTransaction` when any single input's offset mismatches (send.rs:277-279), one injected output poisons an entire withdrawal/batch transaction built over the UTXO set.
- Conversely, an attacker can choose an offset deliberately so the check passes but the `OutPoint`/`TxOut` reference an output never sent to Serai, shaping the sighash and signed transaction around inputs of their choosing.

### Likelihood Explanation
Reachable whenever `ReceivedOutput`s cross a trust boundary via serialization (network messages, coordinator-supplied plans, or storage that an attacker can influence) — precisely the deserialization-reachable surface in scope. It requires no validator compromise, no collusion, and only the ability to supply malformed bytes to `read`. Exploitation additionally requires the receiving component to credit the output before the spend-time check, which is the natural producer/consumer split between scanning and signing.

### Recommendation
In `ReceivedOutput::read` (or a dedicated `verify`/`new` constructor), re-derive the expected script: compute `p2tr_script_buf(key + GENERATOR * offset)` for the scanner's key and require it to equal `output.script_pubkey`, rejecting otherwise — mirroring the check `multisig` performs, but at ingest time so invalid outputs can never enter the UTXO set. Alternatively, store only the `OutPoint` and recover the offset/output exclusively from `Scanner` state.
