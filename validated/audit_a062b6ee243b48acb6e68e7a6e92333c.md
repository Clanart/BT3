## Title
`SimplexPaymaster` charges gas fees using Chainlink prices without checking `minAnswer`/`maxAnswer` bounds - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` validates a Chainlink `latestRoundData()` answer only for positivity and staleness, but never checks that the returned `answer` lies strictly between the underlying aggregator's `minAnswer` and `maxAnswer`. When a Chainlink feed reaches its price floor/ceiling it continues to report the clamped bound as a fresh, positive answer, which this contract will accept as truth and use to compute the ERC‑20 amount charged to users for gas.

### Finding Description
`_getOraclePrice` in `SimplexPaymaster.sol` is: [1](#0-0) 

It reverts only on `answer <= 0` or excessive staleness — there is no bound check against the aggregator's configured `minAnswer`/`maxAnswer`. This value feeds directly into `_tokenPrice`, which is used by `_fetchDetails` (called on every `_validatePaymasterUserOp`) to compute the ERC‑20 amount charged for gas: [2](#0-1) [3](#0-2) 

The same unvalidated price also drives `amountOutMin` in the fee-recycling swap: [4](#0-3) 

If either the `nativeOracle` or a registered token's `tokenOracle` (both intended to be Chainlink-style `AggregatorV3Interface` feeds per the contract's own docstring, "accepts ERC-20 stablecoins... with a Chainlink feed") hits its aggregator-configured minimum price during a market crash, the feed keeps returning the clamped minimum as a valid, fresh, positive `answer`. `_getOraclePrice` accepts it unconditionally, so `_tokenPrice` computes a token/gas conversion rate that no longer reflects the real market price.

### Impact Explanation
Any unprivileged user submitting a UserOp through this paymaster is charged `erc20Cost = weiCost * tokenPrice / 1e18`, where `tokenPrice` is derived from the clamped feed. Depending on which side of the ratio is clamped (native/USD or token/USD), users are systematically over- or under-charged relative to true market value — a direct loss of funds for either the user or the protocol/treasury, with no code path to detect or reject the clamped condition. This is a public, permissionless entry point (`_validatePaymasterUserOp` → `_fetchDetails`) reachable by any account submitting an ERC-4337 UserOp, not requiring a malicious relayer, prover, or governance actor.

### Likelihood Explanation
This requires only that a real-world asset (the configured native asset or a registered ERC‑20) trade below the Chainlink aggregator's preset floor — a documented and previously observed Chainlink behavior (e.g., during the depegging events cited in the external report), not an exotic or attacker-controlled condition. Given the contract explicitly targets Chainlink-style feeds, this is a realistic operational scenario rather than a theoretical one.

### Recommendation
Extend `_getOraclePrice` to fetch and cache each aggregator's `minAnswer`/`maxAnswer` (from the underlying `AggregatorV2V3Interface`/proxy `aggregator()` accessor) and revert when `answer <= minAnswer || answer >= maxAnswer`, mirroring the mitigation recommended for the underlying `PriceFeed` bug. Apply the same guard to both `nativeOracle` and every `tokenOracle` used in `_tokenPrice` and `swapAndDeposit`.

### Proof of Concept
1. Register a token whose `tokenOracle` is backed by a Chainlink aggregator with `minAnswer = X`.
2. Market price of the token falls below `X`; the aggregator's `latestRoundData()` continues returning `answer = X` with a fresh `updatedAt` (standard Chainlink clamp behavior).
3. A user submits a UserOp using this token in `paymasterData`; `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts `X` as valid since it is positive and not stale.
4. The user is charged `erc20Cost` computed from the stale clamped price `X` instead of the true (lower) market price, resulting in an incorrect (and exploitable) gas charge with no revert or safeguard.

    /// @dev Returns the token to charge and its price relative to native gas.
    ///
    ///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
    ///      so tokenPrice must be token base units per wei, scaled by 1e18:
    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
