Confirmed: `purchase()` in `BandwidthManager.sol` lets any caller specify an arbitrary `app` (bytes) for any `chain`, and the pallet credits the `(app_chain, app)` bucket keyed purely by that payload, not by `msg.sender`/`request.from` identity of the buyer. This is the "shared forwarder" analog — many independent payers can push subscriptions into the *same* `(chain, app)` FIFO bucket, and the bucket enforces a hard cap with oldest-first eviction that anyone can trigger.

### Title
Unprivileged attacker can grief a bandwidth app's prepaid, unconsumed subscription via FIFO eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `Allowance` storage is a per-`(app_chain, app)` FIFO list capped at `MAX_SUBSCRIPTIONS = 1024` [1](#0-0) . Any address on any registered source chain can call `BandwidthManager.purchase(app, tier, months, chain)` and credit that shared bucket, because the `app` field is caller-supplied bytes, not tied to `msg.sender` [2](#0-1) . `on_accept` in the pallet keys storage purely by the decoded `app`/`chain` fields from the message body [3](#0-2) . When the FIFO list is full, the next push evicts the oldest entry regardless of its size or who paid for it [4](#0-3) .

### Finding Description
This is the local analog of the Remora "shared forwarder" bug: instead of a shared payout-forwarding address whose accumulated balance can be wiped by an unrelated party's action, here a shared `(app_chain, app)` bandwidth ledger can have a legitimately-purchased, unconsumed subscription evicted by an unrelated third party who is not the beneficiary app and derives no benefit from the eviction other than harming the app.

The corrupted value is the FIFO-ordered `Allowance::<T>` entry for a targeted `(app_chain, app)` — specifically, whichever `Subscription` sits at index 0 when the list reaches the 1024-entry cap. `push_subscription` unconditionally evicts `list.remove(0)` once `list.len() == MAX_SUBSCRIPTIONS`, with no check on the evicted entry's remaining value, purchaser, or elapsed time [5](#0-4) .

No malicious relayer, prover, or admin is required — `purchase()` is a fully public entrypoint that dispatches a `timeout: 0`, `fee: 0` ISMP POST that self-delivers and skips the bandwidth gate (`is_purchase_message` bypass) [6](#0-5) . An attacker who wants to grief a specific app simply repeats cheap `purchase()` calls (the smallest configured tier, e.g. the $50/100KB tier referenced in the docs) targeting the same `app`/`chain` pair as the victim, until the queue is at 1024 entries, then pushes one more purchase to evict whichever entry currently sits at the front — which, depending on timing, may be a large, recently purchased, still-mostly-unconsumed legitimate subscription belonging to the target app or one of its sponsors.

### Impact Explanation
This is a fund-loss bug matching the bounty's "stealing or loss of funds" and "bandwidth balances must move exactly once and only to the rightful beneficiary" criteria: the evicted subscription's `remaining_bytes` are permanently destroyed (only `SubscriptionEvicted` is emitted; there is no refund path back to whoever paid for it) [7](#0-6) . The victim (the app, or whoever sponsored it) paid real fee-token value for bytes it never got to use, and that value is unrecoverable — same end state as the Remora report's "unclaimed payouts get lost" impact, just applied to prepaid bandwidth instead of dividend payouts.

### Likelihood Explanation
Reaching the 1024-entry cap requires paying for 1024 minimum-tier purchases, which is not free but is a bounded, attacker-controlled cost against an unbounded potential victim loss (a large multi-month purchase can be evicted by a bucket of cheap 1-month purchases). The docs themselves flag this as a known, if considered "pathological," scenario: "In practice this only happens under pathological repeat-buy behavior" [8](#0-7) , meaning it was anticipated as theoretically possible but not blocked. It requires no privileged position, no relayer collusion, and no proof forgery — any account with the fee token can execute it end-to-end using only public contract calls.

### Recommendation
- Scope eviction economically: instead of unconditional FIFO eviction, reject new purchases (or require an explicit governance/self-service top-up path) once the list is full, or evict based on remaining-value/expiry rather than pure insertion order.
- Consider keying purchases so only the app itself (or an explicitly authorized sponsor list) can push into its bucket, removing the fully-permissionless sponsorship surface, or rate/cost-limit pushes per `(app_chain, app)` per block/window.
- At minimum, make `SubscriptionEvicted` carry enough data (and consider a refund mechanism via `dispatch_withdraw`) so evicted value can be economically reconciled instead of silently destroyed.

### Proof of Concept
1. Governance registers `BandwidthManager` for `EVM-1` and configures `TierOne` (smallest/cheapest tier) via `set_tier` + `dispatch_set_tiers` [9](#0-8) .
2. Victim (or a legitimate sponsor) calls `BandwidthManager.purchase(appBytes, TierFour, 12, "EVM-8453")` — a large, expensive, long-duration purchase landing in the `(EVM-8453, appBytes)` bucket via `on_accept` → `push_subscription` [10](#0-9) .
3. Attacker, an unrelated account with no relationship to the app, calls `purchase(appBytes, TierOne, 1, "EVM-8453")` 1024 times, using the *same* `app`/`chain` targeting the victim's bucket. Nothing in `purchase()` or `on_accept` restricts who can credit `appBytes`'s bucket [11](#0-10) .
4. On the attacker's next (1025th) purchase, `push_subscription` evicts index 0 of the FIFO list — the victim's large `TierFour` subscription if it was inserted early enough or is still the oldest live entry — emitting `SubscriptionEvicted` with the victim's `lost_bytes`, permanently destroying the paid-for, unconsumed allowance [5](#0-4) .
5. The victim app can no longer dispatch messages up to the evicted byte amount and cannot recover the fee-token value it spent; no error, admin action, or relayer misbehavior was involved.

        external
        returns (bytes32 commitment)

        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
