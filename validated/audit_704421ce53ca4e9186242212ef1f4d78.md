## Title
DID recovery list persists across `transfer_did` sale, letting a malicious seller retain covert recovery rights over a sold DID/NFT bundle - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
The Footium report shows that `FootiumEscrow.approve()` lets a seller pre-authorize an arbitrary address before selling a club asset, so the buyer inherits an asset that the attacker can still drain. The structurally equivalent pattern in this codebase is Chia's DID (`DIDWallet`) recovery mechanism: `backup_ids` / `num_of_backup_ids_needed` act as a standing "approval" that survives an ownership transfer unless the seller explicitly clears it, and the code itself documents this as caller-responsibility rather than an enforced invariant.

### Finding Description
`DIDWallet.transfer_did` (chia/wallet/did_wallet/did_wallet.py, ~L805-857) builds the new DID inner puzzle for the buyer while explicitly reusing the seller's existing `backup_ids` and `num_of_backup_ids_needed`: [1](#0-0) 

The related helper `get_innerpuz_for_new_innerhash` documents this exact hazard in a comment, but does not enforce a fix — it is left as the caller's responsibility to remember to clear the recovery list before selling: [2](#0-1) 

Because the DID inner puzzle (`DID_INNERPUZ_MOD`) is curried with `backup_ids_hash` and `num_of_backup_ids_needed` [3](#0-2) 
these values are baked into the puzzle hash and are consensus-enforced conditions of the coin, not merely wallet-side bookkeeping. If a seller does not clear the recovery list (or worse, deliberately sets it to include an address they control) before completing a sale, the resulting DID coin that the buyer receives still recognizes the seller's backup ID(s) as valid recovery signers under the standard recovery/"lost key" flow (`find_lost_did`, `create_new_did_wallet_from_recovery`, etc.), which drives DID puzzle reconstruction directly from `recovery_list_hash`/`num_verification` recovered from chain state: [4](#0-3) 

This is directly analogous to the Footium bug: an unprivileged party (the seller, prior to being paid) can leave a standing authorization/approval mechanism attached to an asset, which activates *after* the asset is transferred to a new owner, allowing the original party to regain control (recover the DID and everything it owns/controls, including any NFTs whose ownership layer is tied to that DID) without further consent from the buyer.

### Impact Explanation
A DID coin can be the root of trust for arbitrarily many NFTs (ownership-layer NFTs reference a DID as `current_owner`) and for CR-CAT/VC credential flows. If a malicious seller sells a DID (or a DID-controlled bundle of NFTs) while leaving themselves (or a colluding party) in `backup_ids` with `num_of_backup_ids_needed` satisfiable by that colluding set, they retain a channel to seize the DID (and by extension anything gated on DID ownership) from the legitimate buyer at any later time via the standard recovery spend path. This is an unauthorized/unsigned-by-current-owner mechanism to redirect control of a coin/asset, which matches the "concrete unsigned or unauthorized coin movement" bar for validity.

### Likelihood Explanation
Exploitation requires the seller to act maliciously (keep or seed the backup list) at time of sale — this is entirely under the control of an unprivileged wallet user constructing and broadcasting their own transfer transaction; no special network position or privileged access is required. The main practical constraint is that the buyer/marketplace tooling must fail to notice/verify that the recovery list was cleared, similar to the reasonable assumption in the original Footium report that buyers evaluate the sale price based on the assets, not on an escrow's internal approvals. The codebase's own comment acknowledging this exact risk ("In a selling case, the seller should clean the recovery list then transfer to the new owner") indicates this is a known but unenforced footgun rather than a purely theoretical concern.

### Recommendation
- Make `transfer_did` clear the recovery list (`backup_ids=[]`, `num_of_backup_ids_needed=0`) by default when transferring to a puzzle hash that does not belong to the current wallet, requiring an explicit opt-in flag to preserve recovery settings across a transfer.
- At minimum, surface a clear warning/confirmation in the RPC/CLI transfer path (`did_transfer_did`) when `backup_ids` is non-empty at the time of a transfer, and expose the resulting recovery configuration so wallets/marketplaces can verify it before accepting payment.
- Consider making buyers' wallets/tooling verify that a purchased DID's `recovery_list_hash`/`num_of_backup_ids_needed` do not contain unknown/untrusted identities before treating the transfer as final.

### Proof of Concept
1. Attacker creates a DID wallet and sets `backup_ids = [attacker_backup_did]`, `num_of_backup_ids_needed = 1` (a backup DID they also control).
2. Attacker mints/attaches valuable NFTs owned by this DID (ownership layer `current_owner` = DID launcher id).
3. Attacker lists/sells the DID (and its NFTs) via an offer; buyer pays based on the value of the DID + NFTs.
4. Attacker calls `transfer_did` to send the DID coin to the buyer's puzzle hash — per [5](#0-4) , `backup_ids` is carried over unchanged into the new inner puzzle curried into the coin sent to the buyer.
5. After the sale is confirmed, the attacker initiates the standard DID recovery flow using `attacker_backup_did` to satisfy `num_of_backup_ids_needed`, producing a valid recovery spend that reassigns the DID's `p2_puzzle` (and thus control of the DID and any NFTs relying on it) back to an address the attacker controls — without any signature or consent from the buyer, who is now the rightful (but powerless) owner.

```python
def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )

```
