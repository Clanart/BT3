### Title
Cached FROST nonce seed reused across distinct `sign()` invocations in the DKG confirmation protocol, enabling validator key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates the FROST `AlgorithmSignMachine` from a single cached 32-byte seed stored under the context `(b"DkgConfirmer", attempt)` (`CachedPreprocesses`, lines 123–145). The seed is written once and **never deleted or rotated** after use. `DkgConfirmer::share` and `DkgConfirmer::complete` each independently call `share_internal` → `preprocess_internal` → `machine.sign(...)`, meaning the same nonce pair `(d, e)` is used to produce a released signature share **twice** per attempt — a direct analog of the reported "resource used again after it was logically released" double-free class. The file's own header (lines 25–48) acknowledges "it is explicitly unsafe to reuse nonces across signing sessions."

### Finding Description
In `crypto/frost/src/sign.rs` `AlgorithmSignMachine::sign` (lines 386–398), each share is computed as `s = d + ρ·e + c·λ·x` where `d, e` derive from the cached seed, `ρ` is the binding factor over the participants' preprocesses/message, and `c` is the Schnorr challenge over the message.

`DkgConfirmer::share` (lines 288–310) signs `set_keys_message(set, removed, key_pair)`, and `DkgConfirmer::complete` (lines 312–327) calls `share_internal` **again** on the same seed before aggregating shares. The signed message embeds the `removed` validator list (`removed_as_of_dkg_attempt`, line 271) and the preprocess map re-read for each call. If any of these inputs differ between the two calls — e.g., a validator is removed mid-attempt, or `complete` is invoked over a different (attacker-influenced) preprocess/superset — the same `(d, e)` is bound under different `ρ` and `c`.

An unprivileged participant who supplies preprocess bytes that reach `read_preprocess`/`sign` and observes both released shares obtains two equations `s₁ = d + ρ₁e + c₁λx` and `s₂ = d + ρ₂e + c₂λx` over the same `d, e`, which are solvable for the victim validator's Ristretto secret key share `x`. This is precisely the nonce-reuse key-recovery attack FROST's `CachedPreprocess` documentation warns against ("Reuse will enable third-party recovery of your private key share", `crypto/frost/src/sign.rs` lines 84–87).

### Impact Explanation
Recovery of a validator's MuSig/FROST secret key share lets the attacker forge that validator's DKG-confirmation signature shares and any other protocol signatures under that key, breaking the root-of-trust assumption for key-set confirmation on Substrate. The share itself is a high-value secret whose exposure invalidates the threshold assumption.

### Likelihood Explanation
The second `sign()` with the same seed is unconditional — `complete()` always re-signs. Leakage requires the second signing context (message or participant set) to differ from the first, which occurs when `removed` changes between `share` and `complete` (validator removals are handled during an attempt) or when differing preprocess sets are passed. An attacker controlling preprocess bytes can also influence `ρ`. Reachability through public messages (`read_preprocess`, `sign`) is satisfied; the residual uncertainty is whether production call flow guarantees identical inputs across both invocations — the code contains no check that they match (the header at lines 50–54 even lists a TODO to verify on-chain commitments match presumed ones before publishing shares).

### Recommendation
- Delete/burn the `CachedPreprocesses` entry in the same DB transaction that first produces a share (make the seed single-use, mirroring the "free exactly once" fix of CVE-2024-42069).
- Alternatively, cache the *produced* signature share and `AlgorithmSignatureMachine` state instead of re-deriving the machine from the seed in `complete`, so no second `sign()` ever runs.
- Implement the noted TODO: verify the received preprocesses/message are identical to those used when the share was first published before re-signing.

### Proof of Concept
```text
Context (b"DkgConfirmer", attempt=A):
1. generated_key_pair -> share(preprocesses_P, key_pair) -> sign() emits s1
   with seed-derived nonces (d, e), binding rho1, challenge c1.
2. A validator-removal (or distinct preprocess set P') is committed for the
   same attempt before shares are aggregated.
3. complete(preprocesses_P', key_pair, shares) -> share_internal re-derives
   the SAME machine from CachedPreprocesses[(b"DkgConfirmer", A)] and emits
   s2 = d + rho2*e + c2*lambda*x over the same (d, e).
4. Attacker solves the two-share linear system for (d, e, x):
   s1 - s2 = (rho1 - rho2)*e + (c1 - c2)*lambda*x, etc.
   => validator's secret share x recovered from publicly broadcast shares.
```
No memory corruption is needed — the "freed" resource (the one-time nonce seed at `crypto/frost/src/sign.rs` line 92, consumed via `from_cache`/`seeded_preprocess`) is simply used again because it is never invalidated on or after first use.
