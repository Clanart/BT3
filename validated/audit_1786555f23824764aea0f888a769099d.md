### Title
App proxy signature does not bind to param structure, allowing repeated-key/comma-joined value substitution under a replayed signature - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`calculated_signature` normalizes every value with `Array(v).join(",")` before hashing, so a query with a single key holding a comma-joined string and a query with the same key repeated multiple times produce byte-for-byte identical signed input and thus the same HMAC. Because the controller action itself receives its `params` from Rails' own query parser rather than from the `Rack::Utils.parse_query` hash used only for signature checking, and those two parsers treat repeated non-bracketed keys differently, an attacker can take a signature captured on one encoding and replay it on the other encoding, causing the controller to see different, unsigned data while the HMAC check still passes.

### Finding Description
`query_string_valid?` builds its verification hash with `Rack::Utils.parse_query(query_string)`, which accumulates repeated keys into an `Array` (e.g. `k=v1&k=v2` → `{"k"=>["v1","v2"]}`), and `calculated_signature` then does `Array(v).join(",")`, collapsing both `{"k"=>"v1,v2"}` and `{"k"=>["v1","v2"]}` into the identical string `"k=v1,v2"` before hashing: [1](#0-0) 

The controller action that actually consumes the request, however, does not use this Rack-parsed hash for its business logic — it uses Rails' standard `params`, which are built from `ActionDispatch`'s query parsing (`Rack::Utils.parse_nested_query` semantics), where a **repeated, non-bracketed key does not accumulate into an array**; each occurrence overwrites the previous one (last value wins). This divergence means:
- If Shopify originally signs `k=v1,v2&signature=SIG` (single value), an attacker can resend `k=v1&k=v2&signature=SIG`. `calculated_signature` computes the same `"k=v1,v2"` string and the HMAC still validates via `ActiveSupport::SecurityUtils.secure_compare`, but the controller's `params[:k]` now resolves to `"v2"` only (last-wins), silently dropping `"v1"`.
- Conversely, if Shopify originally signs a legitimately repeated key `ids=1&ids=2&signature=SIG`, an attacker can resend `ids=1,2&signature=SIG` with the same signature, but the controller now receives `params[:ids] == "1,2"` (a String) instead of an Array — any code written for an Array (e.g., membership checks, iteration, `.include?` semantics) behaves differently against a comma-joined String, creating logic/type-confusion opportunities.

Only `verify_proxy_request` gates this; there is no other check that binds the HMAC to the specific repeated-key vs. joined-string structure Rails will ultimately parse: [2](#0-1) 

### Impact Explanation
This allows a forged/restructured app-proxy request to pass HMAC verification while presenting the controller with different effective parameter values/types than what Shopify actually signed — a forged signed request accepted (Shopify HackerOne class: "forged app proxy request" / signature verification bypass leading to parameter/data integrity violation). Concrete impact depends on the specific app's proxy controller logic (e.g., dropped values via last-wins overwrite, or Array→String type confusion in access-control or lookup logic), but the underlying guarantee — "the signature protects the exact structure of the request" — is broken.

### Likelihood Explanation
Exploitability requires only that an attacker (unprivileged, e.g., a browser client or network intermediary) can observe/capture one legitimately Shopify-signed proxy request and resubmit it with the query string restructured (comma-joined ↔ repeated key) but the same `signature` value — no secret, session, or insider access is needed. This is straightforward and fully repeatable for any app-proxy endpoint using `ShopifyApp::AppProxyVerification`, such as the generated `AppProxyController`: [3](#0-2) 

### Recommendation
Make signature validation reject query strings whose parsed structure could differ from what Rails will parse for `params`. Concretely: use the same parser for verification as the one Rails uses for `params` (e.g., derive `query_hash` from `request.query_parameters` instead of `Rack::Utils.parse_query`), or explicitly reject query strings containing duplicate non-bracketed keys before computing/comparing the signature, so that a given signature can only be valid for one canonical parameter structure.

### Proof of Concept
```ruby
class AppProxyVerificationController < ActionController::Base
  include ShopifyApp::AppProxyVerification
  def basic; head(:ok); end
end

# Both query strings hash to "k=v1,v2..." internally and thus produce
# the SAME calculated_signature, despite different param structures:
qs_joined   = "k=v1,v2&signature=SIG"
qs_repeated = "k=v1&k=v2&signature=SIG"

# query_string_valid?(qs_joined) == true
# query_string_valid?(qs_repeated) == true   <-- same SIG accepted for a different structure

# But downstream, Rails' own params parsing differs:
Rack::Utils.parse_nested_query("k=v1,v2")       # => {"k"=>"v1,v2"}
Rack::Utils.parse_nested_query("k=v1&k=v2")     # => {"k"=>"v2"}  (last-wins, "v1" silently lost)
```
Expected (secure) behavior: `query_string_valid?` should return `false` for one of the two encodings, since only one matches what Shopify actually signed and what the controller will actually parse into `params`.

```ruby
    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
