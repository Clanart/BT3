### Title
Silent corruption of partially-committed content due to re-diffing against a stale line-index selection - ([File: app/src/lib/git/apply.ts])

### Summary
The Loans report's broken invariant is: a security-relevant value (the borrow index) is recomputed/reset by an operation without validating that it is consistent with the state the caller reasoned about (the previously-computed interest), letting the state diverge silently. The closest structural analog in GitHub Desktop is in the partial-commit ("stage selected lines") pipeline: `applyPatchToIndex` re-fetches a *fresh* diff from disk at staging time and blindly applies a `DiffSelection` (a set of absolute line indices) that was computed against a *different, earlier* diff shown in the Changes view, with no check that the two diffs still agree line-for-line.

### Finding Description
When a user reviews a diff and selects/deselects individual lines for a commit, Desktop stores that selection as a `DiffSelection` keyed by absolute line index within the hunk (see `absoluteIndex = hunk.unifiedDiffStart + lineIndex` in `formatPatch`) [1](#0-0) . This selection is computed once, against the diff object that was loaded and rendered in `updateChangesWorkingDirectoryDiff` [2](#0-1) .

When the user actually commits, `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` is invoked [3](#0-2) [4](#0-3) [5](#0-4) . Critically, `applyPatchToIndex` does **not** reuse the diff object that the UI selection was built against — it calls `getWorkingDirectoryDiff(repository, file)` again, re-running `git diff` on the file at commit time:

```ts
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
``` [6](#0-5) 

`formatPatch` then walks this newly-fetched diff and tests `file.selection.isSelected(absoluteIndex)` using the **old** line-index selection [7](#0-6) . There is no equality/hash check between the diff used to build the selection and the diff used to build the patch. `app-store.ts` acknowledges this class of drift only for the *display* selection (pruning "selectable lines" so stale UI selections don't reference lines that no longer exist), explicitly noting the limitation:

```ts
// The diff might have changed dramatically since last we loaded it.
// Ideally we would be more clever about validating that any partial
// selection state is still valid ...
``` [8](#0-7) 

This staleness-tolerant UI reconciliation, however, is not enforced at commit time in `applyPatchToIndex`/`formatPatch`, which is the actual point that decides what bytes get staged into the index — exactly analogous to `repay_borrow_internal` resetting `borrow_index` without reconciling accrued interest: a downstream computation (`current_balance_from_snapshot` / `formatPatch`) trusts a snapshot value (`borrow_index` / `absoluteIndex` selection) that is silently out of sync with the freshly recomputed source of truth (accrued interest / current diff).

### Impact Explanation
If the on-disk content of the file changes between the moment the diff was rendered/selected and the moment `applyPatchToIndex` re-diffs it, the absolute line indices in the stored `DiffSelection` no longer correspond to the same logical lines in the new diff. `formatPatch` will then silently include or exclude the wrong lines when building the patch handed to `git apply --cached`, meaning the commit created can contain content the user never reviewed or explicitly excluded content the user meant to keep out — i.e., silent corruption of what the user commits, which is explicitly listed as a valid impact category. Because this happens inside the patch-application pipeline with no validation, there is no error, warning, or diff-mismatch message to alert the user; the commit simply proceeds with the wrong hunks.

### Likelihood Explanation
Triggering this requires the working copy of the selected file to change between the diff render and the staging call — a window that exists on every partial commit (any file save from an external editor/build tool/formatter, or a working-tree-modifying git hook/filter driven by content of a cloned repository, running in this interval) can shift line numbers. Because a git repository can carry `.gitattributes`/build tooling that legitimately triggers such background mutation (e.g., an autoformat-on-save workflow, linter, or generated file that a user edits alongside), and because Desktop performs no diff-identity check before applying the stored selection, the precondition is realistic without any local/privileged access, purely from repository/content behavior the attacker/repo can shape (e.g., a repository whose build/format tooling non-deterministically reformats a tracked file). It does not require malware, credentials, or unnatural user steps beyond the normal "select some lines, then commit" workflow.

### Recommendation
- Short term: In `applyPatchToIndex`/`formatPatch`, verify that the diff fetched at staging time is structurally equivalent (e.g., same hunk headers/line counts, or hash of diff content) to the diff the selection was computed against; if it differs, abort staging that file and force the UI to reload the diff and selection before allowing commit, rather than silently applying stale indices.
- Long term: Track selections against stable line identities (e.g., content-hash or old/new-file line numbers) instead of transient absolute indices into a specific diff snapshot, and add unit tests that mutate the working file between diff computation and `createCommit` to assert the partial commit either matches the reviewed selection or fails loudly (mirroring the report's recommendation to add edge-case tests such as the zero-amount repay scenario).

### Proof of Concept
1. In a repository, modify `modified-file.md` and open it in Desktop's Changes view so a diff is rendered and cached in `changesState.selection.diff`.
2. Deselect a specific line (e.g., line 6) via the UI, producing a `DiffSelection` keyed on the current diff's absolute indices, as shown in the equivalent test setup in `app/test/unit/git/commit-test.ts` [9](#0-8) .
3. Before pressing "Commit," externally rewrite the file so that lines shift (e.g., insert a line above the hunk, simulating an autoformatter/build step touching the tracked file).
4. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-diffs the file via `getWorkingDirectoryDiff` [10](#0-9)  and applies the old `DiffSelection` indices to the new diff in `formatPatch` [1](#0-0) .
5. Inspect the resulting commit: because the indices no longer align with the same logical lines, the committed hunk includes/excludes different content than what the user selected in step 2, with no error surfaced.
