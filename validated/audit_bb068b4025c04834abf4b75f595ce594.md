The `checkConsistency` function in header vote verification also does not add any special-case check for `Kip71GasTarget`, just falls into the generic no-op pass-through case [2](#0-1) , meaning a governance vote setting `GasTarget=0` will be accepted without rejection.

### Title
Governance-settable `Kip71GasTarget=0` causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
The KIP-71 (Magma) base fee calculation `NextMagmaBlockBaseFee` divides by `kc.GasTarget` in two branches without ever checking it for zero, while the governance parameter `Kip71GasTarget` has no non-zero format check, unlike its sibling parameter `Kip71BaseFeeDenominator` which is explicitly guarded.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget := kc.GasTarget` as a divisor whenever `parentGasUsed != gasTarget`: [3](#0-2) [4](#0-3) 

Note the explicit defensive pattern used just above for `BaseFeeDenominator`: [5](#0-4) 

No equivalent guard exists for `gasTarget`. If `GasTarget == 0`, then whenever `parentGasUsed != 0` (i.e., almost every block with any transaction), the code takes the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics (`big.Int` division by zero panics in Go's `math/big`).

The governance parameter table defines `Kip71GasTarget` with `noopFormatChecker`, i.e., no bounds or non-zero check, while the denominator parameter is properly checked: [6](#0-5) 

Governance votes for this parameter are accepted through the general "no more checks here" case in `checkConsistency`, alongside other same-treatment parameters: [7](#0-6) 

This means a validator/governing node vote (or governance-mode-driven update) that sets `governance.kip71.gastarget = 0` will pass all header/vote verification and get applied as the active `ParamSet`, subsequently used to build `KIP71Config` via `ToKip71Config()`: [8](#0-7) 

Once active, `NextMagmaBlockBaseFee` is called on every block header preparation/verification path (both `VerifyMagmaHeader` for block validation and header preparation for the proposer), so essentially every node processing any subsequent block with nonzero gas usage panics/crashes.

### Impact Explanation
This causes a chain halt / node crash (denial of service) across every full node and validator that processes a block once `GasTarget=0` becomes the effective governance parameter, because `NextMagmaBlockBaseFee` — invoked from `VerifyMagmaHeader` — is on the mandatory consensus block-verification path. This is a state-divergence/liveness-breaking condition: honest nodes crash rather than continuing to build/verify the chain, and the impact is unauthorized-in-effect halting of the network (severe availability impact), matching the "Medium, division-by-zero panic reachable via a governance-controlled numeric parameter" bug class in the reference CVE.

### Likelihood Explanation
Reaching this requires a governance vote to set `Kip71GasTarget` to `0`. This is gated by governance permissions (only council members / governing node in single mode can cast votes, per `VerifyVote`), so it is not directly reachable from an arbitrary unprivileged transaction sender. However, unlike `BaseFeeDenominator`, there is no defense-in-depth format check preventing an operator error or a malicious/compromised governance participant from setting this value, and the codebase's own comment ("To avoid panic, set the fluctuation range small") shows the developers were aware of and specifically guarded against the same failure mode for the sibling `BaseFeeDenominator` parameter but omitted the equivalent guard for `GasTarget`.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` requiring `v != 0` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-check inside `NextMagmaBlockBaseFee` (similar to the `BaseFeeDenominator == 0` fallback) before using `gasTarget` as a divisor.

### Proof of Concept
1. Governance council votes to set `governance.kip71.gastarget` to `0` (passes `checkConsistency` since it falls into the no-op branch, and `noopFormatChecker` in `kaiax/gov/param.go` accepts any `uint64` including 0).
2. The vote is included and finalized at the epoch boundary via `getExpectedGovernance`/`VerifyGov`.
3. On the next block after the parameter takes effect, if `parentHeaderGasUsed != 0` (essentially any block containing transactions), `VerifyMagmaHeader` → `NextMagmaBlockBaseFee` executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics in Go's `math/big` package, crashing block verification for every node on the network.
