### Title
Externally-sent Bitcoin to internal offset addresses is misattributed to the multisig and permanently dropped — depositor never credited - (File: processor/src/networks/bitcoin.rs)

### Summary
In the SiloGateway report, a gateway performs an action "on behalf of" the user but the protocol attributes the collateral/debt to the caller (the gateway), permanently locking the user's funds. Serai's Bitcoin scanner has the same shape: the classification of a received output is derived **solely from which registered offset script it pays to**, not from who sent it. `Bitcoin::get_outputs` maps `output.offset()` through a fixed `kinds` table (`External = 0`, `Branch`, `Change`, `Forwarded`), so any unprivileged third party who sends BTC to a Branch/Change/Forwarded address has their funds classified as the multisig's own internal funds instead of as an external deposit attributable to them.

### Finding Description
- The offset addresses are deterministic and publicly computable: `key + G * hash_to_F(b"Serai Bitcoin Output Offset", kind)` for `branch`/`change`/`forward` [1](#0-0) .
- `get_outputs` scans each tx with `Scanner::scan_transaction`, looks up `kinds[offset_repr]`, and stamps that kind onto the output — no provenance check distinguishes an internal change output from an arbitrary external send [2](#0-1) . `data`/`presumed_origin` are only populated for `OutputType::External` [3](#0-2) .
- Downstream, `scanner_event_to_multisig_event` only turns `Forwarded` outputs into instructions when a matching `ForwardedOutputDb` entry exists (absent for an external send) and then **retains only `OutputType::External`** outputs for instruction/refund handling [4](#0-3) . An externally-sent `Branch`/`Change`/`Forwarded` output is recorded by `ScannerDb::save_outputs` [5](#0-4)  yet never generates an `InInstruction`, never credits any depositor, and never produces a refund — the `refund` path is only reached for outputs with instructions [6](#0-5) .
- Because output IDs are marked `seen` and re-scanning panics ("scanned an output multiple times") [7](#0-6) , the funds are permanently unaccounted: spendable by the multisig key `key + G*offset` but never scheduled, mirroring FraxLend's permanently-locked collateral.

### Impact Explanation
Value sent to these addresses is credited to the wrong party — the multisig/protocol rather than the sender — exactly the reported bug class. Any depositor (or anyone a sender is tricked into paying via a Branch/Change/Forwarded address, which are valid P2TR addresses indistinguishable from `external_address`) loses their funds permanently: no `InInstruction` is emitted, no refund plan is created, and the output is consumed by the multisig's internal accounting as if it were its own change. This is a Medium/High-severity misattribution and permanent fund-locking issue reachable with only a public Bitcoin transaction.

### Likelihood Explanation
An unprivileged attacker or mistaken depositor needs only the multisig's group key (public, it's the deposit address key) and `Secp256k1::hash_to_F` with the public `KEY_DST` to derive the internal addresses; no validator cooperation, leaked keys, or malformed encodings are required. The reachable path is `send tx -> scan_transaction -> kinds[offset] -> kind != External -> dropped from instruction/refund flow`.

### Recommendation
Distinguish provenance, not just destination: treat any output whose transaction is not a multisig-constructed transaction (no matching eventuality/instruction/preimage in `ForwardedOutputDb` or the scheduler's change records) as `External` regardless of offset, or refuse to classify `Branch`/`Change`/`Forwarded` outputs that appear in transactions the multisig itself did not create. Alternatively, generate refund instructions for all received outputs using `presumed_origin`.

### Proof of Concept
1. Obtain the multisig group key `K` and compute `forward_addr = address_from_key(K + G * hash_to_F(KEY_DST, b"forward"))` using the same constants as `scanner()`.
2. Send BTC from any wallet to `forward_addr`; it confirms in block `B`.
3. `get_outputs` scans it via `scan_transaction`, resolves `kinds[offset] = OutputType::Forwarded`, and emits it.
4. `scanner_event_to_multisig_event`: `ForwardedOutputDb::take_forwarded_output` returns `None`, no instruction is pushed; the output is then filtered out by `outputs.retain(|o| o.kind() == OutputType::External)`.
5. Result: funds are received and spendable by the multisig but never credited, never refunded, and re-scanning is blocked by the duplicate-ID panic — permanently locked, identical in effect to the FraxLend collateral lock-up.

static BRANCH_OFFSET: OnceLock<Scalar> = OnceLock::new();
static CHANGE_OFFSET: OnceLock<Scalar> = OnceLock::new();
static FORWARD_OFFSET: OnceLock<Scalar> = OnceLock::new();

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );
