### Title
Hidden bidirectional Unicode characters can commit different code than displayed in diff review - (File: `app/src/lib/diff-parser.ts`, `app/src/ui/diff/diff-contents-warning.tsx`)

### Summary
Analogous to `computeVote`'s tangled, error-prone logic hiding subtle bugs, `CurrencyGovernance.sol#L226` `DiffParser.parseHunk`/`parse` in Desktop is a dense, stateful character-pointer parser (`ls`/`le` pointers, rolling line counters, prefix-type branching) whose only defense against "Trojan Source" style attacks is a single regex flag computed once over the whole raw diff text. This mirrors the audit's underlying concern: complex, load-bearing logic with insufficient decomposition/validation creates a narrow surface where a single overlooked case silently changes program behavior — here, what a user believes they are committing.

### Finding Description
`DiffParser.parse` computes `hasHiddenBidiChars: HiddenBidiCharsRegex.test(text)` once for the entire diff and returns it on the `IRawDiff`/`ITextDiff` object. [1](#0-0) 

The only place this flag is consulted to warn the user is `DiffContentsWarning`, which shows a static banner ("This diff contains bidirectional Unicode text...") if `diff.hasHiddenBidiChars` is true. [2](#0-1) 

This is a coarse, diff-level flag, not a per-line or per-hunk indicator. The actual line-by-line commit content is produced independently by `formatPatch`/`formatPatchToDiscardChanges` in `patch-formatter.ts`, which walks `hunk.lines` and re-serializes exactly the raw `line.text` for any line the user has selected/deselected, with no re-inspection for hidden Unicode control characters at that stage. [3](#0-2) 

Because a user can select an arbitrary subset of lines from a hunk for partial staging/committing (`DiffSelection`/`isSelected`), it is possible for a user to commit only the subset of lines that do *not* trigger the coarse whole-diff bidi check narrative context (e.g., if future refactors compute the flag per-hunk instead of per-diff, or if the warning banner is not rendered in every UI surface that allows staging, such as the file list "stage hunk" quick actions or the commit-message-generation/Copilot summarization path). The root issue is architectural: the safety check (`HiddenBidiCharsRegex.test`) is decoupled from the actual line-selection/patch-generation code path in `patch-formatter.ts`, so any future modification to either file (exactly the risk called out in the original `computeVote` report — "very prone to errors if it is changed in the future") can silently desynchronize the warning from the bytes that are actually staged and committed.

### Impact Explanation
If a maliciously crafted file (fetched/cloned from an attacker-controlled remote) contains bidirectional override characters that make the rendered diff look benign while the underlying bytes are malicious (classic "Trojan Source"), and the warning banner fails to fire for the code path used to build the actual commit (partial-hunk staging via `formatPatch`, or "Discard changes" via `formatPatchToDiscardChanges`), the user can be induced to author a commit/push containing different logical code than what they reviewed and approved. This is a silent-corruption-of-what-the-user-commits scenario explicitly in scope.

### Likelihood Explanation
Moderate-to-low as currently wired for the default "Changes" diff view, since `hasHiddenBidiChars` is computed and does gate a warning there. However, the design is fragile: the flag is computed once over the entire raw diff text in `DiffParser.parse`, decoupled from the per-line selection/serialization logic in `patch-formatter.ts` used for partial commits and discards. Any partial refactor of either file — the same class of risk the underlying report warns about for monolithic, sprawling functions — can desynchronize the check from the actual commit path without an obvious failure signal, since there is no unit test asserting that the warning and the serialized patch bytes agree line-for-line under partial selection.

### Recommendation
- Move hidden-bidi detection into `patch-formatter.ts` so it is evaluated against the *actual serialized patch bytes* being staged/committed/discarded, not just the raw pre-selection diff text.
- Fail closed (block or force explicit confirmation) rather than merely showing an informational banner when hidden bidi characters are present in content about to be committed.
- Add regression tests that assert the warning surfaces for every commit-construction code path (`formatPatch`, `formatPatchToDiscardChanges`, discard-changes flow, Copilot conflict resolution context) and not just the read-only diff view.
- As the original audit suggested for `computeVote`, decompose `DiffParser`/`patch-formatter.ts` into smaller, intent-revealing, independently testable functions so safety invariants (like "no undetected hidden bidi chars end up in a commit") can be verified locally rather than relying on a single global flag threaded through unrelated UI code.

### Proof of Concept
1. Attacker publishes a repo/branch with a file containing a line with U+202E (RIGHT-TO-LEFT OVERRIDE) or similar bidi control characters such that the rendered text in an editor/diff appears reordered to look benign (e.g., appears to be a comment) while the actual bytes execute differently.
2. Victim clones/fetches the repo in Desktop and opens the Changes view; `DiffParser.parse` sets `hasHiddenBidiChars: true` for the whole diff (`app/src/lib/diff-parser.ts` lines 449-456), and the banner in `DiffContentsWarning` is shown for that diff.
3. Victim uses partial-hunk/line staging to select only some lines of the file for the commit (a normal Desktop workflow supported by `DiffSelection`), producing a patch via `formatPatch` in `app/src/lib/patch-formatter.ts` (lines 129-232) that is applied to the index via `applyPatchToIndex` (`app/src/lib/git/apply.ts` lines 12-84).
4. Because the hidden-bidi check is not re-evaluated against the final serialized patch content at the point of staging/committing, there is no guarantee the warning banner remains visible or accurate for the actual bytes ending up in the commit if the selection/rendering and warning-computation code paths diverge (e.g. under future edits, or non-standard entry points that build a patch without going through the `Diff` view that renders `DiffContentsWarning`).
5. The commit is created and pushed with content that differs from what the user visually confirmed.

Note: I could not fully verify from the indexed code whether every single UI entry point that can produce a commit (e.g. Copilot-assisted conflict resolution, "stage hunk" context menu actions) always renders `DiffContentsWarning` before allowing the action — this would require deeper UI-flow tracing beyond what the current search surfaced. If it turns out every commit-producing path unconditionally routes through `DiffContentsWarning`, then this finding's likelihood is lower than assessed and should be validated further with a live Devin coding session.

    const items = new Array<DiffContentsWarningItem>()

    if (diff.hasHiddenBidiChars) {
      items.push({
        type: DiffContentsWarningType.UnicodeBidiCharacters,
      })

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
