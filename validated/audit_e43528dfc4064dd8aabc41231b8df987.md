## Title
Unescaped `Any.type_url` Injected Raw into TextFormat Output, Enabling Structural Injection into Serialized Text - (File: `src/google/protobuf/text_format.cc`, `java/core/src/main/java/com/google/protobuf/TextFormat.java`, `python/google/protobuf/text_format.py`)

## Summary
When TextFormat's Any-expansion feature prints a `google.protobuf.Any` message, the `type_url` string field — which is attacker-controlled data coming directly off the wire in a parsed message — is written **verbatim, with no escaping**, into the bracketed `[type_url] { ... }` syntax that TextFormat uses to represent expanded `Any` values. Every other string field printed by TextFormat's printer is routed through an escaping function that neutralizes control characters, quotes, and other syntax-breaking bytes; `type_url` bypasses that path entirely.

## Finding Description
The external report's failed invariant is: a value that gets embedded into a structured, line/token-delimited text protocol must be validated/escaped for the protocol's own metacharacters (CRLF for HAProxy V1) before being written; Netty validates this correctly for IPv4/IPv6 but not for `AF_UNIX`, letting an attacker inject a second `PROXY` line.

Protobuf's TextFormat is a comparable structured text serialization: normal `STRING`/`BYTES` field values are always wrapped in quotes and escaped (`\r`, `\n`, `"`, `\`, control bytes) before being written, in every implementation checked:
- C++: `FastFieldValuePrinter::PrintString` calls `ContainsCharactersToCEscape` / `absl::CEscape` [1](#0-0) 
- Java: `TextFormatEscaper.escapeText` replaces `\n`, `\r`, `"`, `\\`, etc. [2](#0-1) 
- Python: string/bytes fields go through `text_encoding.CEscape` [3](#0-2) 

However, the special-cased handling of `google.protobuf.Any` expansion writes `type_url` directly, without going through any of these escaping routines:
- Java `printAny()`: `generator.print("["); generator.print(typeUrl); generator.print("]");` — `typeUrl` is printed with the raw `print()` call, not `printFieldValue`/`escapeText`. [4](#0-3) 
- Python `_TryPrintAsAnyMessage()`: `self.out.write('%s[%s]%s ' % (self.indent * ' ', message.type_url, colon))` — a raw `%s` substitution of `message.type_url`, with zero escaping. [5](#0-4) 
- C++ `Printer::PrintAny()`: `generator->PrintString(type_url);` — this calls `BaseTextGenerator::PrintString`, a raw pass-through write method, **not** the field-value printer's escaping `PrintString` (that name collision is between two distinct classes: `TextFormat::FastFieldValuePrinter::PrintString` which escapes, vs. `TextFormat::BaseTextGenerator::PrintString` which is a raw sink write). [6](#0-5) 

`type_url` is attacker-reachable: it is a normal `string` field (field number 1) inside any message that embeds an `Any` submessage, populated by ordinary binary-protobuf parsing (`Any::MergeFrom`/`ParseFrom*`) of untrusted input — no privileged access or hostile schema needed, matching the consuming-application exposure model (an app that logs, dumps, or forwards `TextFormat::PrintToString()` output of received messages). The C++ parser does enforce a syntactic type-URL grammar on **parse** (percent-encoding checks, identifier validation) [7](#0-6) , but that grammar check only applies when the type URL is read *back* from `TextFormat` input; it is never applied to arbitrary `type_url` strings that arrive via binary/ProtoJSON parsing and are then re-serialized to TextFormat — there is no equivalent validation on the printer/write path shown above.

## Impact Explanation
If a downstream consumer treats the `TextFormat` output as trusted text (logs parsed later, generates config files, or, in the worst case, re-parses the debug string with `TextFormat::Parse`), an attacker-controlled `type_url` containing `]`, `{`, `}`, embedded quotes, or newlines can break out of the `[type_url] { ... }` construct and inject additional (attacker-chosen) field/message syntax into the printed text — structurally the same "second line/record injected into a bounded text protocol" impact described in the Netty report (there, a spoofed second `PROXY` header; here, spoofed/duplicated fields or malformed structure in a `TextFormat` dump). This is a `CWE-93`-class output-neutralization gap. It does not by itself cause memory corruption or code execution; the impact is confined to text-format debug/serialization integrity, and is Medium severity, consistent with the referenced advisory's own severity rating.

## Likelihood Explanation
Likelihood is limited by two factors: (1) it requires `SetExpandAny(true)` (C++) or the default Any-expansion path (Java/Python `printer().printToString()`, which enables Any-expansion by default) to be active, and (2) it requires the application to treat printed `TextFormat` output as anything other than opaque debug text (e.g., feeding it back into a parser, or into another delimiter-sensitive log/consumer). Given `TextFormat` is widely used for debug-string logging and diffing, and `Any` fields are common in production schemas (e.g., wrapping arbitrary payloads), the attacker-controlled precondition (control over `type_url` via ordinary parsing) is easily satisfiable.

## Recommendation
Route `type_url` through the same string-escaping function used for ordinary `STRING` fields before writing it between `[` and `]` in all three affected implementations:
- C++: replace `generator->PrintString(type_url);` in `TextFormat::Printer::PrintAny` with a call through `FastFieldValuePrinter`'s escaping `PrintString`/`HardenedPrintString`, or explicitly `absl::CEscape` the value before writing.
- Java: replace the two raw `generator.print(typeUrl)` calls in `printAny()` with `TextFormatEscaper.escapeText(typeUrl)` (or reuse `printFieldValue`'s STRING branch).
- Python: escape `message.type_url` with `text_encoding.CEscape` before interpolating it into the `[%s]` format string in `_TryPrintAsAnyMessage`.
Additionally, consider rejecting/escaping `type_url` values containing control characters (`\r`, `\n`, `[`, `]`, `{`, `}`, `"`) at the point where `Any` is parsed from binary/JSON, to prevent the corrupted value from propagating to any output format.

## Proof of Concept
I could not run this in the current environment (read-only ask mode); the reproduction described below is derived directly from the cited source and mirrors the structure of the reported PoC.

```java
// Java
Any evil = Any.newBuilder()
    .setTypeUrl("type.googleapis.com/x]\n  injected_field: 1\n#") // control chars/brackets unescaped
    .setValue(SomeMessage.getDefaultInstance().toByteString())
    .build();
String text = TextFormat.printer()
    .usingTypeRegistry(TypeRegistry.newBuilder().add(SomeMessage.getDescriptor()).build())
    .printToString(Wrapper.newBuilder().setAny(evil).build());
// `text` now contains a `]` and injected-looking lines/newlines inside what should be
// a single bracketed type-url token, because generator.print(typeUrl) at
// TextFormat.java:460 performs no escaping (contrast with printFieldValue's STRING
// case at TextFormat.java:633-640, which does escape).
```

The same unescaped write is present in the Python (`text_format.py:439`) and C++ (`text_format.cc:2565`, via `BaseTextGenerator::PrintString`) implementations, confirming this is a cross-implementation gap rather than an isolated bug in one language binding.

  static {
    REPLACEMENT_CHARS = new String[128];
    for (int i = 0; i <= 0x1f; i++) {
      REPLACEMENT_CHARS[i] = String.format("\\%03o", i);
    }
    REPLACEMENT_CHARS[0x7f] = "\\177";
    REPLACEMENT_CHARS['\"'] = "\\\"";
    REPLACEMENT_CHARS['\''] = "\\\'";
    REPLACEMENT_CHARS['\\'] = "\\\\";
    REPLACEMENT_CHARS['\t'] = "\\t";
    REPLACEMENT_CHARS['\b'] = "\\b";
    REPLACEMENT_CHARS['\n'] = "\\n";
    REPLACEMENT_CHARS['\r'] = "\\r";
    REPLACEMENT_CHARS['\f'] = "\\f";
    REPLACEMENT_CHARS[0x07] = "\\a";
    REPLACEMENT_CHARS[0x0b] = "\\v";
  }

  /** Like {@link #escapeBytes(ByteString)}, but escapes a text string. */
  static String escapeText(String input) {
    int len = input.length();
    StringBuilder builder = null;
    int last = 0;
    for (int i = 0; i < len; i++) {
      char c = input.charAt(i);
      // If there are any characters outside of ASCII range (> 127) we eagerly convert to UTF and
      // escape on those bytes (including quotes as well). Note that escaping to UTF8 bytes instead
      // of \\u sequences is itself somewhat nonsensical, but JavaProto has behaved this way for a
      // long time, and changing the behavior would be disruptive.
      if (c > 127) {
        return escapeBytes(input.getBytes(StandardCharsets.UTF_8));
      }
      String replacement = REPLACEMENT_CHARS[c];
      if (replacement == null) {
        continue;
      }
      if (builder == null) {
        builder = new StringBuilder(len + 16);
      }
      if (last < i) {
        builder.append(input, last, i);
      }
      builder.append(replacement);
      last = i + 1;
    }
    // If builder is null, we made it through the entire input without needing any escaping,
    // so we can return the original string verbatim with zero allocations.
    if (builder == null) {
      return input;
    }
    if (last < len) {
      builder.append(input, last, len);
    }
    return builder.toString();
  }
