### Title
Silent error-swallowing in ERC20 IBC-refund conversion permanently strands escrowed Coins in the erc20 module account when the token-side transfer fails - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
When an ICS20 transfer of a "native ERC20" token pair fails or times out, the erc20 IBC middleware attempts to refund the sender by re-converting the refunded bank `Coin` back into the ERC20 representation via `ConvertCoinNativeERC20`. That helper first moves the sender's `Coin` into the `x/erc20` module account (`bankKeeper.SendCoinsFromAccountToModule`) and only afterwards attempts to `transfer` the equivalent ERC20 tokens out of the module account to the sender via `CallEVM`. If that second step fails for any reason a receiving/refund address cannot accept the token (blacklist, pause, `require` in `_beforeTokenTransfer`, hook revert, etc.), the caller (`ConvertCoinToERC20FromPacket`) deliberately swallows the error and returns `nil`, which lets the whole `OnAcknowledgementPacket`/`OnTimeoutPacket` chain succeed. Because the Coin-escrow step already ran directly against the real (non-cached) `ctx`, it is never rolled back, while the compensating ERC20 transfer never lands. The result is a Coin permanently trapped in the erc20 module account with no error surfaced anywhere and no path for the user to recover it — an analog of the reported "blacklisted participant permanently locks funds" bug class, reachable by an ordinary IBC transfer/timeout flow rather than a privileged actor.

### Finding Description
The vulnerable helper is `ConvertCoinNativeERC20`: [1](#0-0) 

It performs two non-atomic operations on the *same* `ctx`:
1. `k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins)` — escrows the Coin immediately on the live context.
2. `k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())` — attempts to unescrow/transfer the corresponding ERC20 token to `receiver`.

`CallEVM` only protects EVM-internal state via its own `ctx.CacheContext()`: [2](#0-1) 

If `res.Failed()` (e.g. the token's `transfer` reverts because the recipient is blacklisted/paused/hook-reverting), only the EVM sub-state is discarded — the bank-level `SendCoinsFromAccountToModule` performed a moment earlier on the *outer* `ctx` is not part of that cache and is **not** rolled back.

This function is invoked from the IBC refund path: [3](#0-2) 

Note the explicit swallow: on failure, an event is emitted and `return nil` is executed — the function reports success to its caller even though the sender's Coin was consumed without the token transfer succeeding. This propagates up through `OnAcknowledgementPacket` / `OnTimeoutPacket` and finally through the middleware wrapper, which forwards the (nil) result verbatim: [4](#0-3) 

Because these keeper calls execute within the enclosing `MsgAcknowledgement`/`MsgTimeout` transaction's own (uncached) `ctx`, and the overall handler chain returns no error, the whole branch — including the now-orphaned bank escrow — is committed to state as part of normal transaction success.

Contrast this with the user-initiated `MsgConvertERC20` path (`ConvertERC20` → `convertERC20IntoCoinsForNativeToken`), where a failure from `CallEVMWithData` propagates as a real error to the top of the message handler, causing the SDK message router to discard the whole branch atomically: [5](#0-4) 

That path is safe by virtue of ordinary Cosmos SDK message-handler atomicity. The IBC ack/timeout refund path intentionally breaks this atomicity by swallowing the error so the IBC callback itself always "succeeds" — but the code does so without wrapping the two dependent operations (escrow + unescrow-transfer) in their own `CacheContext`, so a partial failure leaves state inconsistent instead of leaving it untouched.

### Impact Explanation
Any ordinary user who sends an ICS20 transfer of a registered "native ERC20" token pair and whose transfer subsequently times out or is acknowledged with an error will trigger this refund path. If that user's EVM address cannot receive the ERC20 token at that moment (token blacklist/pause list, a paused ERC20, a token with transfer hooks that revert under some condition, or even a token that has been deregistered/self-destructed mid-flight causing the `transfer` call to revert), the user's refunded Coin is moved into the `x/erc20` module account and is never returned to them in either form (Coin or ERC20). No error is surfaced to the relayer, the user, or on-chain event logs beyond a silent `erc20_callback_failure`-style event; the acknowledgement/timeout processing reports success. This is a permanent, irreversible loss/freezing of user funds triggered entirely through the ordinary, unprivileged IBC transfer + timeout/error-ack flow — matching the "Critical permanent freezing/locking of user funds" impact category.

### Likelihood Explanation
The trigger requires only:
1. A token pair registered as `IsNativeERC20()`.
2. A user's ICS20 transfer of that token that fails or times out (this can happen for many mundane relayer/liveness reasons, not just malice).
3. The user's own EVM address (which is the refund destination) being unable to accept an ERC20 `transfer` at that moment — plausible for any compliance-gated stablecoin-like native ERC20 token pair, or any token with a transfer hook/pausable feature.

None of these require a privileged actor; any user of a paused/blacklist-capable native ERC20 token pair can be affected, and it can also be triggered by an attacker who front-runs a blacklist action, or simply by a token owner pausing/blacklisting after the transfer is in flight but before the timeout/ack is processed. Likelihood is realistic for any deployment that registers compliance-gated tokens as native ERC20 pairs, which the referenced report explicitly anticipates ("only vetted tokens" like USDC are expected to be used).

### Recommendation
Make the refund conversion atomic and safe against partial failure:
- Wrap the entire escrow + unescrow-transfer sequence inside `ConvertCoinNativeERC20` in its own `ctx.CacheContext()`, and only invoke the `commit`/write function if the ERC20 `transfer` succeeds; otherwise, discard the cache and leave the sender's Coin balance untouched.
- In `ConvertCoinToERC20FromPacket`, when `ConvertCoinNativeERC20` fails, do not merely swallow the error — verify (or make it structurally guaranteed) that the sender's Coin has not left the sender's account, so that the fallback "user receives the bank token instead" behavior documented in the code comments actually holds.
- Add unit/integration tests around `OnAcknowledgementPacket`/`OnTimeoutPacket` for the native-ERC20 case where the ERC20 `transfer` reverts (e.g., blacklist/pausable mock token), asserting that the sender retains their Coin balance and no funds land unrecoverably in the erc20 `ModuleAccount`.

### Proof of Concept
1. Register a native ERC20 token pair for a mock ERC20 contract that supports a blacklist (`transfer` reverts if `to` is blacklisted), analogous to USDC.
2. User A holds Coins of that pair's denom and sends an ICS20 `MsgTransfer` to chain B.
3. Before the packet is acknowledged/times out, blacklist User A's EVM address on the mock ERC20 contract (or otherwise force the token pair contract's `transfer` to revert for that address, e.g. via pause).
4. Trigger `OnTimeoutPacket` (or receive an error acknowledgement) for the packet — this invokes `x/erc20/keeper.Keeper.ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
5. Observe:
   - `bankKeeper.SendCoinsFromAccountToModule` succeeds, moving User A's refunded Coin into the `types.ModuleName` account.
   - `CallEVM`'s `transfer` call reverts (`res.Failed()`), so `ConvertCoinNativeERC20` returns an error.
   - `ConvertCoinToERC20FromPacket` swallows the error and returns `nil`; `OnTimeoutPacket`/`OnAcknowledgementPacket` report success.
   - Final state: User A's Coin balance was decreased and never restored, User A received no ERC20 tokens, and the Coin remains permanently in the `x/erc20` module account with no user-facing recovery mechanism.

Note: I could not execute this scenario in a live node from this environment; the trace above is based on static analysis of `x/erc20/keeper/msg_server.go`, `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/ibc_middleware.go`, and `x/vm/keeper/call_evm.go`, tracing the exact control flow and context (cached vs. non-cached) at each step. A background Devin session with test-execution ability would be needed to fully confirm this end-to-end with a concrete blacklist-capable mock ERC20 contract.

func (k Keeper) ConvertERC20(
	goCtx context.Context,
	msg *types.MsgConvertERC20,
) (*types.MsgConvertERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Error checked during msg validation
	receiver := sdk.MustAccAddressFromBech32(msg.Receiver)
	sender := common.HexToAddress(msg.Sender)

	pair, err := k.MintingEnabled(ctx, receiver, msg.ContractAddress)
	if err != nil {
		return nil, err
	}

	// Check ownership and execute conversion
	if pair.IsNativeERC20() {
		// Remove token pair if contract is suicided
		acc := k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())
		if acc == nil || !acc.HasCodeHash() {
			k.DeleteTokenPair(ctx, pair)
			k.Logger(ctx).Debug(
				"deleting selfdestructed token pair from state",
				"contract", pair.Erc20Address,
			)
			// NOTE: return nil error to persist the changes from the deletion
			return nil, nil
		}

		return k.convertERC20IntoCoinsForNativeToken(ctx, pair, msg, receiver, sender) // case 2.1
	} else if pair.IsNativeCoin() {
		return nil, types.ErrNativeConversionDisabled
	}

	return nil, types.ErrUndefinedOwner

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Use a cache context so that a reverting EVM call does not corrupt the
	// parent gas meter. On success we commit the cache and charge the actual
	// gas used; on revert we discard the cache and leave the parent meter
	// untouched (matching DerivedEVMCallWithData semantics).

	res, err := k.ApplyMessage(tmpCtx, msg, nil, commit, true)
	if err != nil {
		return nil, err
	}

	if res.Failed() {
		return res, errorsmod.Wrap(types.ErrVMExecution, res.VmError)
	}

	commitState()
	ctx.GasMeter().ConsumeGas(res.GasUsed, "apply evm message")

	return res, nil

func (im IBCMiddleware) OnAcknowledgementPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	acknowledgement []byte,
	relayer sdk.AccAddress,
) error {
	var ack channeltypes.Acknowledgement
	if err := transfertypes.ModuleCdc.UnmarshalJSON(acknowledgement, &ack); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet acknowledgement: %v", err)
	}

	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnAcknowledgementPacket(ctx, channelVersion, packet, acknowledgement, relayer); err != nil {
		return err
	}

	return im.keeper.OnAcknowledgementPacket(ctx, packet, data, ack)
}

// OnTimeoutPacket implements the IBCModule interface.
// It refunds the token transferred and then automatically converts the
// Cosmos Coin to their ERC20 token representation.
func (im IBCMiddleware) OnTimeoutPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) error {
	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnTimeoutPacket(ctx, channelVersion, packet, relayer); err != nil {
		return err
	}

	return im.keeper.OnTimeoutPacket(ctx, packet, data)
}
