### Title
Sandwiching `queueNewRewards` lets an attacker capture a pro-rata share of the entire queued reward for a single block of stake - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` (invoked by `queueNewRewards`) instantly bakes the whole `_amountReward` into `rewardPerTokenStored` based on `totalStaked()` at that exact block, with no time-weighting/streaming. An attacker can `depositLP` immediately before the manager's `queueNewRewards` transaction is mined and `withdraw` immediately after, capturing a `balanceOf(attacker)/totalStaked()` share of the entire reward despite holding stake for a single block.

### Finding Description
`_provisionReward` computes:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
``` [1](#0-0) 
This is a one-shot injection, not a `rewardRate`/`periodFinish` streaming model. `earned()` derives directly from the current `rewardPerTokenStored` vs. the account's `userRewardPerTokenPaid` snapshot: `(balanceOf(_account) * (rewardPerToken - paid)) / 10**decimals + userRewards`. [2](#0-1) 

Because `balanceOf` and `totalStaked` read live values from `MasterMagpie.stakingInfo`/token balance rather than a time-weighted average, and there is no minimum staking duration, cooldown, or checkpoint delay before `rewardPerTokenStored` is snapshotted for a new depositor, the following sandwich is possible:

1. Attacker sees manager's pending `queueNewRewards(_amountReward, _rewardToken)` transaction in the mempool.
2. Attacker front-runs with `WombatPoolHelper.depositLP` → `WombatStaking.depositLP` → `MasterMagpie.depositFor` → `BaseRewardPool.updateFor` (via `_harvestBaseRewarder`), which sets `userRewardPerTokenPaid[attacker] = rewardPerTokenStored` (pre-reward value) and increases `totalStaked()` and `balanceOf(attacker)`. [3](#0-2) [4](#0-3) 
3. Manager's `queueNewRewards` executes, updating `rewardPerTokenStored` for the whole pool using the post-deposit `totalStaked()` (which now includes the attacker's fresh stake), diluting existing stakers' effective allocation and giving the attacker a proportional share of that increment. [5](#0-4) 
4. Attacker back-runs with `WombatPoolHelper.withdraw` → `MasterMagpie.withdrawFor` → `_harvestAndUnstake`, which calls `_harvestBaseRewarder`/`getReward` to realize `earned()` computed from the now-updated `rewardPerTokenStored`, capturing the reward, then exits the position in the same or next block. [6](#0-5) [7](#0-6) 

No modifier (`nonReentrant`, `whenNotPaused`) or reward-index mechanism prevents this: `nonReentrant`/`whenNotPaused` only guard against reentrancy/pausing, not against instantaneous stake-then-claim; and `updateFor`/`_updateFor` merely checkpoint `rewardPerTokenStored` at whatever block they are called, with no vesting curve.

### Impact Explanation
This results in **theft of unclaimed yield from other stakers**: the attacker extracts a share of the queued reward proportional to `attackerStake/totalStaked` at the moment of injection, without having contributed to the accrual period that the reward is meant to compensate. Legitimate long-term stakers receive a diluted share of `rewardPerTokenStored` increment. This matches the "theft of unclaimed yield" impact class in the prompt's scope.

### Likelihood Explanation
Feasibility is high for pools that batch/queue rewards in discrete transactions (`queueNewRewards` is a plain public/manager-restricted call, but the target transaction is visible in the mempool prior to inclusion). The attacker needs: (a) mempool visibility of the manager's `queueNewRewards` call, (b) capital sufficient to significantly move the `attackerStake/totalStaked` ratio for the block in question, and (c) gas/MEV capability to land the front-run/back-run atomically or across two consecutive blocks around the manager's transaction. This is repeatable every time `queueNewRewards`/`donateRewards` is called (the latter is even permissionless and callable by anyone, though it doesn't add new registration, its reward math has the same issue). Profitability is highest for pools with low `totalStaked()` and/or large periodic reward injections relative to pool size.

### Recommendation
Replace the instant lump-sum injection with a time-streamed reward model (e.g., Synthetix-style `rewardRate` + `periodFinish` + `lastUpdateTime`, updating `rewardPerTokenStored` incrementally based on elapsed time since `lastUpdateTime` rather than crediting the full `_amountReward` in one step). Alternatively, introduce a minimum stake duration / withdrawal cooldown, or checkpoint `balanceOf` snapshots based on time-weighted average balance over the reward accrual window so that a single-block depositor cannot capture a full pro-rata share of previously-queued-but-undistributed rewards.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or `BaseRewardPoolV2`), `WombatStaking`, and `WombatPoolHelper` wired together with a mock Wombat pool/LP token and a mock reward token, following existing test fixtures.
2. Seed an initial "long-term" staker (Alice) who deposits LP and holds for N blocks before any reward is queued, to establish a baseline `totalStaked()`.
3. Have the manager prepare (but not yet send) `rewarder.queueNewRewards(amountReward, rewardToken)`.
4. In the same test block/transaction batch (simulate via `hre.network.provider.send("evm_setAutomine", [false])` and manually mining), have the attacker call `WombatPoolHelper.depositLP(lpAmount)` before the manager's `queueNewRewards`, then mine the manager's tx, then immediately call `WombatPoolHelper.withdraw(lpAmount, minAmount)` for the attacker.
5. Assert: `rewarder.earned(attacker, rewardToken)` right after step 4 is > 0 and approximately `amountReward * attackerStake / (aliceStake + attackerStake)`, despite the attacker having held stake for only one block, while Alice, who held stake for the entire accrual period, receives a diluted `earned()` relative to a naive expectation of getting the full reward.
6. Compare attacker's realized reward (via `getReward`) against a "fair" pro-rata-by-time metric to quantify the disproportionate extraction, confirming the Conservation invariant is broken.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
