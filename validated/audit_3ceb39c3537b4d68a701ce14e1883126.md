### Title
Forwarded-output matching by exact amount lets an attacker desynchronize pending `InInstruction`s, permanently uncrediting deposits — (File: processor/src/multisigs/db.rs, processor/src/multisigs/mod.rs)

### Summary
The external report describes a cross-chain transfer that assumes the received amount exactly equals an expected amount (slippage = 0), causing reverts/loss whenever reality deviates. Serai contains the same bug class: during multisig rotation, outputs forwarded from the old multisig to the new multisig are matched to their `InInstruction`s solely by the exact `ExternalBalance` (coin + amount) expected to land on-chain. Any unprivileged user can send a Bitcoin transaction paying the publicly derivable `Forwarded` address with a colliding amount, consuming the victim's recorded instruction so the victim's real forwarded output is never credited.

### Finding Description
When the prior multisig must forward an `External` output to the new multisig (`RotationStep::ForwardFromExisting`), `scanner_event_to_multisig_event` computes a forwarding TX, subtracts its fee, and records the user's `InInstructionWithBalance` keyed by the exact expected post-fee balance via `ForwardedOutputDb::save_forwarded_output` [1](#0-0) . The DB key is literally `(balance: ExternalBalance)` [2](#0-1) .

Later, when the scanner reports a `Forwarded`-kind output, the code pops the pending instruction by exact amount equality: `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` [3](#0-2) , [4](#0-3) . The code comment acknowledges outputs are identified only by "an amount associated with an InInstruction which was forwarded" [5](#0-4) .

The `Forwarded` address is deterministic and public: `forward_address(key)` derives it from `key + G * offsets[&OutputType::Forwarded]` [6](#0-5) , and `scan_transaction`/`get_outputs` accept any on-chain output paying that script, regardless of sender [7](#0-6) . There is no binding to the source output, the forwarding TXID, or any authentication — the sole "slippage-free" invariant is exact amount equality, which an attacker can forge.

### Impact Explanation
An attacker observes (or guesses) a pending expected forwarded balance and broadcasts a Bitcoin TX paying the new multisig's `Forwarded` address for exactly that amount. When that output is scanned, `take_forwarded_output` returns `Some(victim_instruction)`, which is pushed into the batch and executed against the attacker's dust-sized funding — and, crucially, the DB entry is consumed. When the victim's genuine forwarded output later confirms, `take_forwarded_output` returns `None`; the output is kind `Forwarded`, so it is skipped by the `outputs.retain(... == OutputType::External)` filter [8](#0-7)  and never reported to Serai. The victim's coins sit in the new multisig key with no associated instruction: the deposit is never minted/refunded — funds are effectively locked (not spendable via any reported instruction). This is a "funds reported/received but not creditable" impact reachable purely by sending a public Bitcoin transaction. Even without malice, two distinct forwards that coincidentally produce the same post-fee amount in the same window are ambiguous, and an attacker can also inject colliding fake outputs to force instruction/amount mis-association during periods of fee volatility.

### Likelihood Explanation
Medium. Exploitation requires the forwarding window to be active (`RotationStep::ForwardFromExisting`, a ~6-hour rotation window per spec [9](#0-8) ) and knowledge of the expected amount — which an attacker can infer by sending their own deposit to the old multisig during forwarding and observing the deterministic fee math, or by grinding amounts across the dust range to cover candidate values. The forward address is constant and public, so no validator/node compromise is needed.

### Recommendation
Don't key forwarded instructions solely by exact amount. Options: (a) allow a tolerance/set-membership check (e.g., match any pending instruction whose expected balance is within a fee-variance band), (b) commit the expected outpoint/txid of the forwarding transaction into the eventuality and match on that, or (c) embed the instruction data in the forwarding TX itself (the alternative already contemplated in the spec) so matching doesn't rely on amount. At minimum, treat unmatched `Forwarded` outputs as recoverable (queue them for instruction-less crediting or refund) instead of silently dropping them.

### Proof of Concept
1. Wait for `RotationStep::ForwardFromExisting`; send a deposit of amount `A` with an `InInstruction` to the old multisig's external address, and note the expected forwarded amount `A' = A - fee` the processor will record (`instruction.balance.amount.0 -= tx.0.fee()` [10](#0-9) ).
2. Broadcast a Bitcoin TX paying `forward_address(new_key)` exactly `A'` (attacker funds), timed to confirm before or alongside the real forwarding TX.
3. Scanner reports it as `OutputType::Forwarded`; `take_forwarded_output(txn, A')` returns the attacker's own (or a victim's) pending instruction and deletes the DB entry.
4. The real forwarded output of `A'` later scans, `take_forwarded_output` returns `None`, no instruction is emitted, and the deposit is never credited — permanent loss of crediting despite the coins sitting in the new multisig.

  pub fn take_forwarded_output(
    txn: &mut impl DbTxn,
    balance: ExternalBalance,
  ) -> Option<InInstructionWithBalance> {
    let outputs = Self::get(txn, balance)?;
    let mut outputs_ref = outputs.as_slice();
    let res = InInstructionWithBalance::decode(&mut outputs_ref).unwrap();
    assert!(outputs_ref.len() < outputs.len());
    if outputs_ref.is_empty() {
      txn.del(Self::key(balance));
    } else {
      Self::set(txn, balance, &outputs);
    }
    Some(res)
  }
