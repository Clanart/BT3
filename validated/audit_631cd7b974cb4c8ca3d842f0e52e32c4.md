### Title
Attacker-controlled participant count causes disproportionate memory allocation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
The Privoxy CVE-2021-20209 is an unauthenticated memory-exhaustion flaw: a remote peer triggers server-side memory growth with trivial input. The analog in Serai is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs`, one of the explicitly-listed untrusted-byte sinks. A two-byte length field (`n`, attacker-controlled `u16`) drives a `Vec::with_capacity(usize::from(n))` allocation for `Interpolation::Constant` *before* a single scalar is read or `t <= n` is validated, and drives a `1 ..= n` loop that allocates and inserts into a `HashMap` of group elements.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`):

1. `t`, `n`, `i` are read as raw `u16`s from the stream (`crypto/dkg/src/lib.rs:591-602`).
2. If the interpolation tag byte is `0`, the code executes `Vec::with_capacity(usize::from(n))` (`crypto/dkg/src/lib.rs:607-613`). With `n = 0xFFFF`, this reserves `65535 * size_of::<C::F>()` — roughly 2 MB for 32-byte fields, ~3.7 MB for ed448's 56-byte field, ~4 MB for 64-byte fields — triggered by roughly a dozen bytes of attacker input (4-byte ID len + curve ID + 6 bytes params + 1 tag byte). The allocation happens before any `ThresholdParams::new` validation (`crypto/dkg/src/lib.rs:626`), which only runs at the end.
3. Independently of the tag, the loop `for l in (1 ..= n)` (`crypto/dkg/src/lib.rs:620-623`) inserts up to 65,535 entries into a `HashMap<Participant, C::G>`. Each iteration requires a valid point encoding in the stream, so the HashMap growth is proportional to input size, but the `with_capacity` Vec allocation is not — it is pure amplification.
4. The allocated vector is only released after a `read_F` fails, so repeated concurrent or serialized `ThresholdKeys::read` calls on attacker-supplied buffers cause multi-MB allocation bursts per ~15-byte message. Under sustained input this produces allocator pressure and memory exhaustion of the host process, analogous to the per-request leak in the Privoxy `show-status` handler.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (key-share blobs, recovery data, or any protocol message deserialized through it) can force ~2–4 MB heap allocations per message with ~15 bytes of input — an amplification factor over 100,000x on allocation size versus input size. Sustained messages cause memory exhaustion / OOM abort (`Vec::with_capacity` aborts on allocation failure), denying service to the signing/DKG node. This matches the CVE's class: remote, unauthenticated, availability-only (C:N/I:N/A:H-style) impact.

### Likelihood Explanation
Reachability depends on integrators deserializing `ThresholdKeys` from untrusted sources, which the scope rules treat as a valid attack surface. The trigger requires no valid signature, proof, or participant status — only the interpolation tag `0` and `n = 0xFFFF`. Every malicious message yields the allocation before failure, so cost to the attacker is negligible. Severity is Medium: pure amplification DoS, bounded per message (~4 MB) but repeatable and unauthenticated, with no secret leakage.

### Recommendation
- Do not preallocate based on the untrusted `n` in `ThresholdKeys::read`. Replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` (or a modest capped capacity) so memory grows only as bytes are actually consumed.
- Validate `ThresholdParams::new(t, n, i)` immediately after reading `t, n, i` — before the interpolation and verification-share loops — so an `n` exceeding `t` semantics or zero values are rejected before any allocation.
- Optionally impose a protocol-level `MAX_N` well below `u16::MAX` to bound per-message allocation for legitimate multisigs.
- The same pattern audit should cover `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`), which trusts a `u32` count (though it does not preallocate, so its amplification is limited to iteration cost).

### Proof of Concept
```rust
// ~15-byte payload triggering a ~4 MB allocation inside ThresholdKeys::read
let mut buf = vec![];
// curve ID length + ID matching the target curve C::ID
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
// t = 1, n = 0xFFFF, i = 1
buf.extend(1u16.to_le_bytes());
buf.extend(u16::MAX.to_le_bytes());
buf.extend(1u16.to_le_bytes());
// interpolation tag 0 => Interpolation::Constant => Vec::with_capacity(65535)
buf.push(0u8);
// Stream ends here: read_F fails, but only after the n-element Vec was allocated.
let _ = ThresholdKeys::<C>::read(&mut &buf[..]); // allocates ~n * size_of::<C::F>() bytes
```
Each invocation reserves `65535 * size_of::<C::F>()` bytes of heap before erroring. Repeating this from an unauthenticated byte stream exhausts memory, mirroring CVE-2021-20209's per-request memory-growth DoS.
