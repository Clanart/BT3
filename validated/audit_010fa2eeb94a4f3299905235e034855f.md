### Title
`SignableTransaction::new` computes `needed_fee` over a transaction that omits the OP_RETURN output, so the minimum-relay check and reported fee use a smaller vsize than the transaction actually signed — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`calculate_weight_vbytes` builds a mock transaction containing only the payment outputs (plus optional change) and returns its vsize. `SignableTransaction::new` multiplies `fee_per_vbyte` by that vsize to obtain `needed_fee` and to enforce the `TooLowFee` minimum-relay check — but the real `tx_outs` may also contain an OP_RETURN output carrying `data`, which is never included in the measured transaction. The result is a fee computed and validated against the wrong "scale" of the transaction: a vsize smaller than what will actually be broadcast.

### Finding Description
Analogous to `getPriceFromUnderlying` assuming `PRICE.getPrice` returns in `outputDecimals`, `SignableTransaction::new` assumes the vsize returned by `calculate_weight_vbytes` describes the transaction it is constructing, when it does not:

- `tx_outs` gets the OP_RETURN pushed at [1](#0-0) , while the vsize used for `needed_fee` and the `TooLowFee` check is computed from `payments` only at [2](#0-1) .
- The same omission occurs on the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again excludes the data output at [3](#0-2) .

Each OP_RETURN output adds at least `8 (value) + 1 (script len) + 1 (OP_RETURN) + 1 (push opcode) + len(data)` bytes — up to ~92 vbytes for the maximum allowed 80-byte payload — none of which is priced.

### Impact Explanation
- `needed_fee()` over-reports the achieved feerate: the transaction commits `fee = input_sat - payment_sat - change` sats of fee but is larger than measured, so the effective sat/vbyte is below the requested `fee_per_vbyte`.
- More importantly, the `TooLowFee` guard passes whenever `fee_per_vbyte * vbytes_measured >= DEFAULT_MIN_RELAY_TX_FEE * vbytes_measured / 1000`, yet the real transaction is larger, so its effective feerate can fall below the default minimum relay fee. The produced transaction is fully signed and well-formed but non-relayable under default policy — a spend that cannot confirm, burning the fee budget logic the API promises.
- `needed_fee` is also what `NotEnoughFunds` reports and what callers rely on, so downstream accounting is understated.

### Likelihood Explanation
Reachable by an unprivileged party whenever transaction `data` fed into `SignableTransaction::new` is attacker-influenced (any protocol flow that embeds caller-supplied OP_RETURN data, e.g. the `Option<Vec<u8>>` in `SignableTransaction::new` at [4](#0-3) ). Combined with a low requested `fee_per_vbyte` near the relay minimum, the signed transaction systematically lands under the relay floor. No internal access or validator collusion is required — only causing a transaction with a data payload to be built and signed.

### Recommendation
Pass the already-built `tx_outs` (or the OP_RETURN output) into `calculate_weight_vbytes` so the measured transaction is identical to the transaction actually signed and broadcast — i.e., measure the vsize of the real output set (payments + OP_RETURN + optional change) rather than assuming it equals `payments` alone. This is the direct analog of using the PRICE module's actual decimals rather than assuming `outputDecimals`.

### Proof of Concept
1. Call `SignableTransaction::new` with inputs totalling `payment + fee`, `payments = [(script, DUST)]`, `change = None`, `data = Some(vec![0u8; 80])`, and `fee_per_vbyte` chosen so `fee_per_vbyte * vbytes_measured` exactly equals `DEFAULT_MIN_RELAY_TX_FEE * vbytes_measured / 1000` (e.g. `fee_per_vbyte = 1` sat/vbyte).
2. The `TooLowFee` check at [5](#0-4)  passes because `needed_fee` is computed on a tx without the OP_RETURN output.
3. The signed transaction (`TransactionMachine`/`complete`) contains the extra ~92-vbyte OP_RETURN output, so its actual feerate is `needed_fee / vbytes_actual < 1` sat/vbyte — below `DEFAULT_MIN_RELAY_TX_FEE` — and default-policy nodes will reject it, even though the API guaranteed the fee was adequate.
