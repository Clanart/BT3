### Title
Out-of-bounds slice read (panic) in `IsGzip`/`IsWasm` when checking short WASM byte code - ([File: sei-wasmd/x/wasm/ioutils/utils.go])

### Summary
`IsGzip` and `IsWasm` in `sei-wasmd/x/wasm/ioutils/utils.go` slice their input to a fixed prefix length (`input[:3]` and `input[:4]`) without first checking that `len(input)` is at least that long, causing a runtime out-of-bounds slice panic when a shorter byte slice is passed.

### Finding Description
`IsGzip` reads `input[:3]` and `IsWasm` reads `input[:4]` unconditionally: [1](#0-0) 

Unlike `CreateChecksum` in `sei-wasmvm/lib_no_cgo.go`, which explicitly checks `len(wasm) < 4` before slicing: [2](#0-1) 

`IsGzip`/`IsWasm` have no equivalent length guard. This is the same bug class as the reported FreeRDP ZGFX decoder issue: a fixed-length header/magic-bytes read performed without validating that the buffer is long enough, leading to an out-of-bounds read (in Go, this manifests as a runtime panic rather than silent OOB memory access, since Go slicing is bounds-checked).

I was unable to fully confirm, within the remaining investigation budget, every call site that passes attacker/user-controlled byte code into `IsGzip`/`IsWasm` without a prior length check (e.g., whether the `MsgStoreCode` handler in `sei-wasmd/x/wasm/keeper/keeper.go` or the CLI/REST tx builders in `sei-wasmd/x/wasm/client/cli/tx.go` and `sei-wasmd/x/wasm/client/rest/tx.go` validate length before calling these functions). The `IsGzip`/`IsWasm` calls are also referenced from `evmrpc/simulate.go`, `x/evm/keeper/msg_server.go`, `evmrpc/send.go`, and multiple `precompiles/wasmd/*` files, which are more directly reachable from EVM transactions/precompile calls than the native `MsgStoreCode` path — but I could not verify within budget whether any of those specific call sites pass a byte slice shorter than 4 bytes without a preceding length check, which is required to actually trigger the panic.

### Impact Explanation
If a call site reachable from an unprivileged actor (contract deployer via `MsgStoreCode`, or a CosmWasm-related EVM precompile call) passes wasm bytecode/input bytes shorter than 4 bytes to `IsWasm` (or shorter than 3 bytes to `IsGzip`) without a prior length check, the node would panic. Depending on whether that panic is recovered by an ante-handler/msg-handler `recover()` wrapper or propagates to crash the process, this could range from a rejected transaction (no impact) up to a node crash / block-processing halt (validator halt), which is the qualifying impact class for this scan. Given uncertainty over exact reachability and panic-recovery behavior at each call site, this should be treated as a **potential** issue requiring verification, not a confirmed critical bug.

### Likelihood Explanation
Likelihood is uncertain: it depends entirely on whether any of the multiple call sites found (`sei-wasmd/x/wasm/client/cli/tx.go`, `sei-wasmd/x/wasm/client/rest/tx.go`, `evmrpc/simulate.go`, `x/evm/keeper/msg_server.go`, `evmrpc/send.go`, `precompiles/wasmd/*`) invoke `IsGzip`/`IsWasm` on a byte slice that can be attacker-controlled and shorter than the required prefix length, and whether standard Cosmos SDK message handling wraps execution in a panic-recover (which would downgrade this from a crash to a rejected tx). I could not confirm this chain end-to-end within the remaining budget.

### Recommendation
Add explicit length checks to `IsGzip` and `IsWasm` before slicing (mirroring the pattern already used in `sei-wasmvm/lib_no_cgo.go`'s `CreateChecksum`), e.g. return `false` if `len(input) < 3` (`IsGzip`) or `len(input) < 4` (`IsWasm`), rather than relying on every caller to pre-validate length.

### Proof of Concept
Not independently verified end-to-end due to tool budget exhaustion. Conceptually: call `ioutils.IsWasm([]byte{0x00})` or `ioutils.IsGzip([]byte{})` directly, or trigger any reachable code path (e.g. `MsgStoreCode` with a 0–3 byte `WASMByteCode` field, if such a path calls `IsWasm`/`IsGzip` before length-checking the code) — this panics with "slice bounds out of range".

func CreateChecksum(wasm []byte) (Checksum, error) {
	if len(wasm) == 0 {
		return Checksum{}, fmt.Errorf("wasm bytes nil or empty")
	}
	if len(wasm) < 4 {
		return Checksum{}, fmt.Errorf("wasm bytes shorter than 4 bytes")
	}
	// magic number for Wasm is "\0asm"
	// See https://webassembly.github.io/spec/core/binary/modules.html#binary-module
	if !bytes.Equal(wasm[:4], []byte("\x00\x61\x73\x6D")) {
		return Checksum{}, fmt.Errorf("wasm bytes do not not start with Wasm magic number")
	}
