Confirmed. The Tron variant of `IntentGatewayV2.sol` imports `SafeERC20` and even declares `using SafeERC20 for IERC20;`, but in `withdraw()` and the `SweepDust` handling inside `onAccept()`, it deliberately bypasses `SafeERC20` and uses a raw low-level `.call` that only checks the boolean `success` of the call itself, never decoding/validating the ERC20 return data.

### Title
Escrow withdrawal accepts failed ERC20 transfers as successful due to unchecked raw `.call` return data - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron `IntentGatewayV2` release escrowed tokens using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only check that the low-level call itself did not revert (`success`), never decoding the returned `bool`. This is the exact bug class from the referenced report: a token whose `transfer` executes successfully (no revert) but returns `false` to indicate failure will be treated by this code as a fully successful transfer.

### Finding Description
In `withdraw()`: [1](#0-0) 
the function sets `_filled[body.commitment] = beneficiary`, and unconditionally decrements `_orders[body.commitment][token] -= amount` after the raw call, regardless of whether the ERC20 `transfer` actually moved funds — it only branches on `success` from the `.call`, never on the ABI-decoded return value.

The same unchecked pattern appears in the `RequestKind.TransactionFees` payout at lines 707-714, and in the `SweepDust` handler: [2](#0-1) 

Per EIP-20 / the "weird-erc20" catalogue referenced in the seed report, several deployed tokens return `false` on failed transfer rather than reverting (e.g. insufficient balance/blacklist checks implemented to return false). Against such a token, `token.call(...)` succeeds at the EVM level (`success == true`) even though no tokens moved, because the low-level `call` only reflects "did the callee revert", not "what did the callee return". The code never inspects the returned `bytes` for the encoded `bool`, so it cannot detect this failure mode.

This directly contrasts with the sibling contract `evm/src/apps/intentsv2/IntentsBase.sol`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`: [3](#0-2) 
`SafeERC20.safeTransfer` decodes the return data and reverts if it is `false`, closing this gap. The Tron `IntentGatewayV2` even imports `SafeERC20` and applies `using SafeERC20 for IERC20;` at the top of the file, and uses it correctly elsewhere (`safeTransferFrom`), but the withdrawal/sweep paths were written with the unsafe raw-call pattern instead.

### Impact Explanation
Once `withdraw()` marks `_filled[commitment] = beneficiary` and zeroes out `_orders[commitment][token]`, the escrow accounting for that commitment is permanently closed — there is no retry path (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();` guards re-entry into the same withdrawal, and the order is recorded as filled/refunded via `EscrowReleased`/`EscrowRefunded` events). If the escrowed asset is a token that returns `false` instead of reverting on failed transfer, the beneficiary receives nothing while the protocol's internal state (and the source-chain settlement/refund flow that consumes these events) believes the funds were paid out. This is a direct, unauthorized loss of escrowed user/solver funds with no recovery mechanism — an unrecoverable fund loss for the rightful beneficiary, which the escrow was supposed to guarantee.

### Likelihood Explanation
This triggers whenever the order/escrow's input or fee token is configured to a non-reverting ERC20 (a known category of real, deployed tokens). No malicious relayer, prover, or admin is required — the withdrawal path is reached through the normal `onAccept`/`withdraw`/`SweepDust` message flow once such a token is used as an order's input or fee token, which is fully within the reach of any user creating an order with that token, or an admin configuring a `SweepDust`/fee-token that happens to behave this way.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()`, the `TransactionFees` payout, and `SweepDust` handling with `IERC20(token).safeTransfer(beneficiary, amount)` (the contract already has `using SafeERC20 for IERC20;` available), matching the pattern already used correctly in `IntentsBase.sol`.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer` function returns `false` on failure conditions (e.g., insufficient allowance to a hook, or simply hard-coded `return false;` to simulate a non-compliant token) instead of reverting.
2. Create and escrow an order on `IntentGatewayV2` (Tron variant) using this token as an input, following the normal `send`/escrow flow.
3. Trigger the cross-chain `RedeemEscrow`/`RefundEscrow` flow so `onAccept` → `withdraw(body, ...)` is invoked with `body.tokens` containing this token and `amount` greater than what the mock allows to actually transfer (simulate the false-return condition).
4. Observe: `token.call(...)` returns `success == true` (no revert) even though the mock token internally does not update balances and returns `false`; `withdraw()` proceeds to set `_filled[commitment] = beneficiary`, decrement `_orders[commitment][token] -= amount`, and emit `EscrowReleased`/`EscrowRefunded`.
5. Confirm the beneficiary's token balance did not increase, while the contract's internal accounting shows the escrow as fully settled with no way to retry or reclaim the funds.
