## Analysis

The external report's core broken invariant is: **a state-changing transfer result is trusted without properly validating the return value**, allowing a token that reports failure differently than the code expects to have its actual outcome misinterpreted, causing the protocol's internal accounting to diverge from real token balances.

The direct local analog is not the `require(...)` pattern from the report — the tron fork already migrated deposits to `SafeERC20.safeTransferFrom`. The analog is the inverse defect introduced on the payout side of the same contract: `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` use a raw low-level `.call` and only check that the call itself did not revert (`success`), never inspecting/decoding the returned boolean, unlike `SafeERC20.safeTransfer` (which the file already imports and uses on the deposit path) that would revert if `returndata` decodes to `false`. ### Title
Escrow release/refund accepts a failed ERC20 `transfer` as success due to unchecked boolean return value - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and from `onGetResponse` for cancellations) and the `SweepDust` handler perform payouts via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the raw call did not revert. They never decode/validate the returned `bool`. Meanwhile, deposits in the very same contract use `IERC20(token).safeTransferFrom(...)` (via `using SafeERC20 for IERC20;`), which does validate the return value. This asymmetry means a token whose `transfer()` call succeeds (no revert) but returns `false` will be treated by the withdraw path as a successful payout, while the beneficiary receives nothing. ### Finding Description
`placeOrder` accepts an arbitrary ERC20 address as an order's escrowed `input.token`, controlled entirely by the unprivileged user who places the order. That token is escrowed via `safeTransferFrom` (which will revert if the token misbehaves on deposit), so the user can only escrow tokens that behave correctly for `transferFrom`. However, nothing prevents a malicious token contract from behaving correctly on `transferFrom` but returning `false` (without reverting) on `transfer()` when the caller is the `IntentGatewayV2` contract — e.g. a conditional/blocklist-style token that returns a boolean failure flag instead of reverting.

When the order is filled/refunded/cancelled, `withdraw()`:
1. Marks `_filled[body.commitment] = beneficiary` (order permanently finalized),
2. Calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks `success` (i.e., the low-level call didn't revert) — it never inspects the ABI-decoded boolean return value,
3. Unconditionally does `_orders[body.commitment][token] -= amount`, permanently zeroing the escrow record.

If the malicious token's `transfer()` executes without reverting but returns `false`, `success == true`, the `if (!success) revert TransferFailed();` guard does not fire, the escrow accounting is decremented as if the transfer succeeded, and the order is marked filled/refunded — while the beneficiary (a legitimate solver in `RedeemEscrow`, or the user in `RefundEscrow`) receives zero tokens. There is no retry path: `_filled` and `_orders` are already mutated, and `UnknownOrder()` will be thrown on any later attempt to re-withdraw since `_orders[...][token] == 0`.

This is exactly the class of bug the external USDT-style report warns about, but expressed as the false-success acceptance of a failed transfer, which the Hyperbridge pivots explicitly call out: cross-chain settlement/escrow paths "must move exactly once and only to the rightful beneficiary and amount," and this path lets state finalize (`_filled`, decremented `_orders`) without the beneficiary actually receiving funds.

### Impact Explanation
A solver who has already delivered real output tokens to the user on the destination chain (per `fillOrder`) can have the corresponding `RedeemEscrow` payout on the source chain silently fail while the contract still marks the order `Filled` and zeroes the escrow — the solver receives nothing for value already delivered, and the funds are stranded (locked, unrecoverable via that commitment) in the gateway holding the escrowed poison token. This is a direct loss-of-funds condition triggered from an unprivileged, public entrypoint (`placeOrder`), requiring no malicious relayer, prover, or admin.

### Likelihood Explanation
The attacker only needs to deploy a standard-looking ERC20-compatible token whose `transfer()` returns `false` (instead of reverting) under attacker-chosen conditions and use it as an order's input token via the public `placeOrder()` call — no privileged role, front-running, or compromised infrastructure is needed. The deposit-side `safeTransferFrom` check does not prevent this since only the withdrawal-side `transfer()` needs to misbehave.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout pattern in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer` (already imported and used for deposits in this same file), so both successful-call-but-false-return and non-standard-return-value tokens are handled consistently and any failed transfer reverts the whole state update instead of silently finalizing escrow.

### Proof of Concept
1. Deploy `EvilToken`, an ERC20 whose `transferFrom` always succeeds and returns `true`, but whose `transfer` returns `false` (no revert) whenever `msg.sender == IntentGatewayV2 address` (or after a first successful transfer, to simulate a blocklist/pausable token).
2. Attacker (order user) calls `placeOrder` with `input.token = EvilToken`, escrowing `amount` — deposit succeeds via `safeTransferFrom`.
3. Solver fills the cross-chain order on the destination chain, delivering real output tokens to the user, per `_fillCrossChain`.
4. `RedeemEscrow` message arrives on the source chain; `onAccept` -> `withdraw()` calls `EvilToken.call(transfer(solver, amount))`. `EvilToken.transfer` returns `false` without reverting, so `success == true`; the `TransferFailed` revert does not fire.
5. `_orders[commitment][EvilToken] -= amount` succeeds (already escrowed), `_filled[commitment] = solver`, `EscrowReleased` event emitted.
6. Assert: `EvilToken.balanceOf(solver) == 0` (solver got nothing) while the order is irreversibly marked `Filled` and escrow accounting shows zero remaining — the solver's already-delivered output value is unrecoverable through this contract.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
