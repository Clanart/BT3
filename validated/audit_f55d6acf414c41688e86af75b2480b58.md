## Title
Discard-changes flow silently succeeds when `git checkout-index` fails to update some files, corrupting the working directory without informing the user - (File: `app/src/lib/git/checkout-index.ts`)

### Summary
The External Report's broken invariant is: an operation whose success/failure is not properly validated is nonetheless trusted as fully successful, causing silent state corruption for the user (unsafe ERC20 `transfer()`/`transferFrom()` calls whose boolean return value is discarded). The closest verifiable analog in this GitHub Desktop codebase is `checkoutIndex()` in [1](#0-0) , which explicitly widens the accepted "success" outcomes of `git checkout-index` to include exit code `1` and then returns without inspecting `stdout`/`stderr` to determine whether individual requested paths actually failed to update.

### Finding Description
`checkoutIndex()` calls `git(['checkout-index', '-f', '-u', '-q', '--stdin', '-z'], ...)` with `successExitCodes: new Set([0, 1])` [2](#0-1) . Because `1` is accepted as a success exit code, the wrapper `git()` in `core.ts` will not throw a `GitError` for this call as long as the exit code is 0 or 1 [3](#0-2) . Git's `checkout-index` returns a non-zero exit status when one or more of the requested paths could not be checked out (e.g. because of a working-tree conflict, permission issue, or an unexpected filesystem state caused by attacker-influenced content in a cloned repository, such as symlinked paths or case-colliding names). The function's caller, `GitStore.discardChanges()`/`discardChangesFromSelection()` flow in `app-store.ts`/`git-store.ts` [4](#0-3) , never inspects the returned `IGitResult` for `exitCode === 1` or parses `stdout`/`stderr` to determine which of the requested paths were *not* restored. It simply resolves the promise and proceeds to treat the discard operation as fully completed, updating in-memory working-directory state and re-rendering the UI as if every requested file had been reverted to the index/HEAD version.

This mirrors the reported bug class precisely: an underlying primitive can signal partial/complete failure through a return channel (exit code, in this case, rather than a boolean return value), and the caller widens/ignores that signal and continues as though the operation fully succeeded.

### Impact Explanation
If `checkout-index` partially fails (exit code 1) while discarding selected changes or restoring paths after a reset, the application will believe the working directory now matches the index for those files when it may not. This is a form of "silent corruption of what the user commits or pushes": the user could believe unwanted local edits were discarded, then stage and commit/push the directory in a state they did not intend, or conversely believe discarded changes were successfully removed when stale content remains on disk. Because Desktop's UI re-reads status afterward, in most benign cases the discrepancy would eventually surface in the status view, but in the interim (and depending on which specific paths partially failed) it is possible for the app to display a "clean" state despite unresolved content, especially for paths whose presence/absence is being toggled as part of a broader multi-file discard operation.

### Likelihood Explanation
Exploitability requires that `git checkout-index` return exit code 1 for at least one of the requested paths, which is a normal Git behavior for various working-tree conditions (not exclusively attacker-controlled), so this is more a defensive/correctness gap than a directly attacker-triggerable RCE. The scenario is much more plausible when the paths involved originate from data in a cloned/fetched repository (e.g. entries reported by `git status` for a hostile repo with unusual filenames, case collisions, or filesystem-specific quirks), which does fit the "attacker controls a cloned/fetched repository" requirement, but I could not find in the indexed code a step that maps the discarded stdout/stderr of `checkout-index` back to a per-file success/failure list, so I cannot confirm the exact conditions under which exit code 1 is reachable purely from adversarial repository content versus benign local filesystem race conditions. This uncertainty should be resolved by a deeper, full-repository review (not limited by index coverage) of how `resetChangedFiles`/`discardChanges` construct the path list and whether any of those paths can be attacker-influenced.

### Recommendation
- After calling `checkoutIndex()`, inspect the `IGitResult` (`exitCode`, `stdout`, `stderr`) even when `exitCode === 1`, and surface/parse which specific paths failed to update.
- Do not silently treat exit code 1 as full success; instead propagate a partial-failure result to the caller so the UI can inform the user which files were not discarded/restored, and avoid marking the operation as fully complete.
- Apply the same audit to the other locations found with `successExitCodes: new Set([0, 1])` (e.g. `config.ts`, `diff.ts`, `fetch.ts`, `merge-tree.ts`, `show.ts`, `tag.ts`) to confirm each one correctly distinguishes "expected non-fatal" cases from "operation partially failed but was reported as fully successful."

### Proof of Concept
I was not able to construct or verify an end-to-end reproduction within the indexed code (this requires exercising `git checkout-index` against a real working directory to produce a genuine exit code 1, which is outside what static code search can confirm). A concrete PoC would need to:
1. Set up a repository where a `discardChangesFromSelection`/discard-changes call targets multiple files, one of which is made un-checkout-able (e.g. by removing write permission on its target directory, or via a path collision case on a case-insensitive filesystem).
2. Trigger the discard through the Desktop UI/dispatcher.
3. Observe that `checkoutIndex()` resolves without error despite one file failing to update, and that the UI reports the discard as fully successful, while the corresponding file's contents remain unchanged/corrupted relative to the assumed "clean" index state.

Due to index-size limits, I could not fully trace every caller of `checkoutIndex()`/`resetPaths()` to confirm whether any downstream path-list construction is attacker-influenced from cloned repository content; a Devin session with full repository access would be needed to complete that trace and build a working PoC.

```typescript
export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
```
