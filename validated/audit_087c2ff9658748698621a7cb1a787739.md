## Title
Swapped hunk-header parameters in `formatPatchToDiscardChanges` corrupt discard-change patches for asymmetric hunks - (File: `app/src/lib/patch-formatter.ts`)

### Summary
`formatHunkHeader` has the declared signature `(oldStartLine, oldLineCount, newStartLine, newLineCount, sectionHeading?)`, mirroring the standard GNU unified-diff convention used consistently by `formatPatch` (which calls it with `hunk.header.oldStartLine, oldCount, hunk.header.newStartLine, newCount`). However `formatPatchToDiscardChanges` invokes the exact same function with the start-line arguments transposed — `hunk.header.newStartLine` first and `hunk.header.oldStartLine` third — while the accompanying `oldCount`/`newCount` locals are computed with inverted semantics relative to `formatPatch`. This is the same bug class as the Tempus report: a call site passes arguments into a shared function whose parameter order/semantics don't match what the caller assumes, producing a value written into the wrong "slot".

### Finding Description
`formatHunkHeader` at [1](#0-0)  defines its parameters explicitly as old-line-then-new-line pairs, documented at [2](#0-1) .

`formatPatch` calls it correctly: [3](#0-2) 

`formatPatchToDiscardChanges`, used by `discardChangesFromSelection` (the code path that generates the patch applied via `git apply` when a user discards selected lines from the working directory, see `app/src/lib/git/apply.ts` lines 102-120), calls the same function with the two start-line arguments swapped: [4](#0-3) 

Note also that inside this function the line-counting is inverted relative to `formatPatch`: an `Add` line (rewritten as a `-` line) increments `newCount`, and a `Delete` line (rewritten as a `+` line) increments `oldCount` — the opposite of the "-lines count toward old, +lines count toward new" convention used everywhere else in the file, including `formatPatchHeaderForFile`/`formatPatch`. The call at line 320 then feeds `hunk.header.newStartLine` paired with `newCount` as the "old" pair and `hunk.header.oldStartLine` paired with `oldCount` as the "new" pair to a function whose parameters are strictly `(oldStartLine, oldLineCount, newStartLine, newLineCount)`.

This coupling of an inverted-semantics local variable pairing with a swapped positional call only produces a correct header when the hunk is symmetric enough that `hunk.header.oldStartLine`/`hunk.header.newStartLine` and the internally-tracked `oldCount`/`newCount` happen to line up with what `git apply` expects for the *reversed* hunk. For asymmetric hunks — where the number of added lines differs from the number of removed lines within a partial selection, or where the original hunk's old/new start lines diverge non-trivially (e.g. earlier hunks in the same diff already changed the line-count delta) — the header's line-count/starting-line values do not correctly describe the actual `-`/`+` content that follows in `hunkBuf`.

### Impact Explanation
`git apply` uses the `@@ -l,s +l,s @@` header purely as a hint for locating context ("fuzz" search) and validating hunk boundaries; when the header's counts/starts don't match the actual `-`/`+` lines that follow, `git apply` can either reject the hunk (fail-safe, low impact) or, more dangerously, apply it against the wrong offset in a file that contains repeated/similar content (e.g. multiple lines with the same text), silently discarding or restoring unrelated lines. Because `discardChangesFromSelection` operates on the user's working directory before a commit, an attacker who can influence diff content (e.g. via a crafted file introduced by a cloned/fetched malicious repository with repetitive or specially-crafted line patterns) can cause the user's "discard selected changes" action to silently corrupt unrelated parts of the file rather than the lines the user intended to discard — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires: (1) a working-directory diff with a partial-line selection that is asymmetric enough to produce mismatched header values (readily achievable, e.g. discarding an added line without discarding an adjacent deleted line in the same hunk), and (2) content with sufficient repetition/ambiguity for `git apply`'s fuzzy-context matching to land at the wrong offset instead of failing outright. The first condition is common in real editing workflows (partial-hunk discards); the second condition is less common but plausible in generated/data files or files with repeated boilerplate lines, which is realistic for a malicious/crafted repository designed to trigger this specific defect. I was not able to fully verify with a concrete adversarial reproduction (no test/tool execution in this environment) whether `git apply` always rejects the mismatched header outright rather than silently misapplying it — this is the main open uncertainty and would need to be confirmed by running `discardChangesFromSelection` against a crafted asymmetric hunk.

### Recommendation
Rewrite `formatPatchToDiscardChanges` to track `oldCount`/`newCount` using the same convention as `formatPatch` (i.e., name the counters to reflect what they actually represent after the add/delete inversion, or invert them explicitly before calling `formatHunkHeader`), and call `formatHunkHeader` with `(hunk.header.oldStartLine, oldCount, hunk.header.newStartLine, newCount)` consistent with its documented signature — matching the pattern already used correctly in `formatPatch`. Add a unit test asserting the exact `@@ -l,s +l,s @@` output for an asymmetric discard selection (differing add/remove counts) to catch regressions, mirroring the existing `formatPatch` tests in `app/test/unit/patch-formatter-test.ts`.

### Proof of Concept
Conceptual repro (not executed in this environment due to tool limitations):
1. Create a file with a hunk containing both an added line and a removed line at different relative offsets, e.g. lines that read identically in two places in the file (to allow fuzzy match ambiguity).
2. Stage a modification producing a diff where `hunk.header.oldStartLine !== hunk.header.newStartLine` and the discard selection includes only a subset of lines (e.g. select only the added line to discard, not the deleted line).
3. Call `discardChangesFromSelection(repository, filePath, diff, selection)` (`app/src/lib/git/apply.ts` lines 102-120), which internally calls `formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts` lines 251-335).
4. Inspect the generated patch's `@@ ... @@` header against the actual `-`/`+` lines that follow — with an asymmetric selection, the header's counts computed from the swapped/inverted values will not match the true line counts, unlike the output of `formatPatch` for the equivalent non-discard case.

Because I could not execute `git apply` in this session to confirm whether it rejects such a mismatched hunk outright or silently misapplies it against ambiguous content, this should be validated with a live Devin session/test run before being treated as a confirmed exploitable corruption (as opposed to a functional bug caught by `git apply`'s validation).
