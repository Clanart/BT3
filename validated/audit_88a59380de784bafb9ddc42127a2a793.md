### Title
Payout tx output ordering is not covered by SIGHASH_SINGLE|ANYONECANPAY, letting an unprivileged attacker strip the OP_RETURN and cause `is_kickoff_malicious` to treat the honest fronting operator as malicious - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds the Payout tx with the user's withdrawal-UTXO input signed under `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP341 only commits to the spent input's own prevout and to the single output at the same index (index 0). The anchor output and the OP_RETURN output (which records the fronting operator's xonly pubkey) are not covered by that signature, so anyone observing the mempool can rebroadcast a modified transaction with the same input 0 and output 0 but with the OP_RETURN removed, get it mined first, and cause `Verifier::is_kickoff_malicious` to record `operator_xonly_pk = None` for that withdrawal and treat the true, honest fronting operator's later kickoff as malicious.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` for withdrawal `i` == the xonly pubkey of the operator whose funds actually paid `output[0]` of the transaction that spends withdrawal UTXO `i`. This binding is meant to be established at `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which appends `op_return_txout(operator_xonly_pk)` as output 2, and is later read back by `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) via `get_first_op_return_output`.

The signature that authorizes spending input 0 (the user's withdrawal UTXO) is required to use `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:174-187`) and verified against that exact sighash in `Operator::withdraw` (`core/src/operator.rs:630-637`). Per BIP341/`taproot_encode_signing_data_to_with_annex_digest` (mirrored in `circuits-lib/src/bridge_circuit/mod.rs:801-862`), `SIGHASH_SINGLE|ANYONECANPAY` commits only to: this input's own previous outpoint/value/scriptPubkey/sequence, and to the single output whose index equals the input's index (output 0). It does **not** commit to any other outputs, so the anchor output (index 1) and OP_RETURN output (index 2) are entirely unauthenticated by the user's signature, and no other input/output count is fixed either.

Exploit flow:
1. Honest operator O calls `withdraw()`, builds and broadcasts a Payout tx: input 0 = withdrawal UTXO (user sig, `SinglePlusAnyoneCanPay`), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(O's xonly pk). O funds fees with `fund_raw_transaction` (own additional inputs/change, `core/src/operator.rs:652-673`).
2. An attacker observing the mempool copies input 0 (including its witness, which remains valid because it doesn't commit to any other outputs) and constructs a replacement transaction with only input 0 (or input 0 plus the attacker's own fee-paying input) and output 0 unchanged, dropping the anchor and OP_RETURN outputs entirely.
3. Attacker broadcasts this stripped tx with a competitive/higher fee and it gets mined instead of (or in place of) O's original tx.
4. `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) processes this block, calls `get_first_op_return_output`, finds `None`, and stores `operator_xonly_pk = None` via `update_payout_txs_and_payer_operator_xonly_pk`.
5. When O later sends the kickoff for this withdrawal, `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) reads `payout_info`, sees `operator_xonly_pk_opt = None`, logs "No operator xonly pk found ... assuming malicious" and returns `Ok(true)` (`core/src/verifier.rs:1882-1885`) — even though O is the party who genuinely fronted the withdrawal.
6. `handle_kickoff` (`core/src/verifier.rs:1969-2026`) treats this as malicious and (off mainnet/testnet4) queues a Challenge tx, feeding into the Disprove/ChallengeNACK path against O's collateral.

No existing guard prevents this: `Operator::withdraw`'s signature check only verifies the `SinglePlusAnyoneCanPay` sighash matches (`core/src/operator.rs:630-637`), which is exactly the sighash that permits this malleability; `update_finalized_payouts` has no fallback to attribute a payout to an operator by any other means (e.g., by whose additional funding inputs paid the fee) once the OP_RETURN is missing; and `is_kickoff_malicious` treats a missing xonly pk as an unconditional "malicious" signal with no distinction from actual fraud.

### Impact Explanation
The false-malicious classification against a genuinely honest operator that fronted a withdrawal is exactly the "Critical: an honest operator's collateral burned" category, since a resulting Challenge → Disprove/ChallengeNACK sequence spends the operator's Round/Kickoff collateral outputs punitively despite legitimate behavior. The attack is repeatable per withdrawal and per operator - any withdrawal payout broadcast by any operator is vulnerable while unconfirmed, so the blast radius covers every operator and every withdrawal, not a single instance. Note that automatic Challenge tx sending is explicitly disabled by `handle_kickoff` on `bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4` (`core/src/verifier.rs:1998-2004`), so on mainnet/testnet4 deployments the immediate automated consequence (challenge broadcast) is suppressed by this gate; on other network configurations (regtest/signet/testnet3) the Challenge tx is queued automatically. Regardless of the challenge-broadcast gate, the underlying misattribution (`payout_payer_operator_xonly_pk = None`, `is_kickoff_malicious => true`) is recorded on every deployment and directly corrupts the state used for `send_asserts`/reimbursement flow.

### Likelihood Explanation
The attacker only needs to observe the mempool for a broadcast (unconfirmed) Payout transaction spending a registered withdrawal UTXO, which is public information, and race it with a lower-output but higher/competitive-fee replacement transaction using the same witness for input 0. Because the withdrawal-UTXO input is required to use `SinglePlusAnyoneCanPay` (enforced protocol-wide, `core/src/rpc/parser/operator.rs:182-187`), this malleability is present for every operator payout, not a rare misconfiguration. Feasibility depends on standard Bitcoin mempool/relay rules for accepting a conflicting/replacement transaction (e.g., RBF signaling on the original tx or being first to a miner), which is a realistic and well-understood transaction-relay race condition, not requiring majority hashrate or any protocol privilege — fully consistent with the stated unprivileged attacker capabilities (broadcast transactions, choose signatures/sighash flags/OP_RETURN/witness).

### Recommendation
Change the payout output commitment so the OP_RETURN (and ideally full output set) is authenticated by the same signature that authorizes spending the withdrawal UTXO — e.g., have the user sign with `SIGHASH_ALL` (or `AllPlusAnyoneCanPay`) instead of `SinglePlusAnyoneCanPay`, or otherwise commit the operator xonly pk / output structure into data that is covered by a signature the attacker cannot forge or reuse across a malleated transaction. Alternatively, require additional out-of-band or on-chain attribution (e.g., tie the payout back to the operator via the additional funding inputs actually spent, which are operator-signed) rather than relying solely on an unauthenticated OP_RETURN output.
