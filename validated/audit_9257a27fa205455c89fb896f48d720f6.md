Based on my investigation, I found a real analog: the `SubmoduleDiff` component renders an "Open Repository"/link element built directly from attacker-controlled `.gitmodules` content, and it is passed unsanitized to `shell.openExternal` via `LinkButton`.

### Title
Attacker-controlled submodule URL in `.gitmodules` is passed unsanitized to `shell.openExternal`, enabling URI-scheme abuse when the user clicks the submodule link - (File: `app/src/ui/diff/submodule-diff.tsx`)

### Summary
When a user opens or fetches a repository containing a submodule, Desktop reads the submodule's `url` straight from the repository's git config (ultimately sourced from `.gitmodules`, which is attacker-controlled content in a cloned/fetched repo) and renders it as a clickable link. Clicking it invokes Electron's `shell.openExternal` with that raw, attacker-supplied string with no scheme allow-listing beyond an `http(s)` logging check performed elsewhere in the codebase (which doesn't even block non-http schemes).

### Finding Description
`buildSubmoduleDiff` in `app/src/lib/git/diff.ts` reads the submodule URL directly from git config: [1](#0-0) . This value comes from `submodule.${path}.url`, which git populates from the repository's `.gitmodules` file — content fully controlled by whoever authored the cloned/fetched repository.

That URL is then handed to `SubmoduleDiff`, which parses it and constructs a link the user can click ("Open this submodule on GitHub Desktop"): [2](#0-1) . The `renderOpenSubmoduleAction` also creates a clickable "Open Repository" suggested action tied to `diff.url` when it's non-null: [3](#0-2) .

The click handler in `LinkButton` calls `shell.openExternal(uri)` directly with no validation of the scheme or target: [4](#0-3) . `shell.openExternal` ultimately maps to Electron's `shell.openExternal`, which will happily hand off arbitrary URI schemes to the OS shell (e.g. `file://`, `search-ms:`, custom app-registered protocol handlers, or Windows `\\host\share` UNC paths embedded in file URIs) — a well-known Electron/Windows exploitation primitive, since OS shell handlers for certain schemes can lead to code execution or credential leakage (e.g. Windows `search-ms:`/`ms-search:` handlers, or SMB path coercion via `file://\\attacker\share` triggering NTLM hash leaks).

Compare this to the report's root cause: an all-or-nothing / unchecked "external value" is trusted and passed through without validating its shape/scheme, and the only guard that exists elsewhere in the codebase — the `http(s)` prefix check — is not applied here at all: [5](#0-4)  shows the pattern used for the app's `open-external` IPC handler, which merely *logs* on `http(s)` prefixes but still calls `shell.openExternal(path)` unconditionally for any other scheme — i.e., even Desktop's own "checked" path doesn't reject non-http(s) schemes.

### Impact Explanation
If an attacker crafts a public repository with a submodule entry whose `.gitmodules` URL is a malicious non-`https` URI (e.g., a `file://` UNC path, a registered custom protocol handler that executes code, or a search-ms query), then convinces a victim to clone/open that repository in Desktop and view the submodule's diff, clicking "Open this submodule on GitHub Desktop" / the submodule link will cause Electron to hand the raw attacker string to the OS shell via `shell.openExternal`. Depending on OS and installed handlers this can lead to local file execution, SMB-based credential leakage, or invocation of arbitrary installed URI-scheme handlers — all without any additional local access, admin rights, or pre-existing malware, purely from cloning/opening a crafted repo and one click.

### Likelihood Explanation
Likelihood is moderate: it requires user interaction (a click) and a specific OS/handler configuration to achieve code execution or credential exfiltration, but the setup cost for the attacker is trivial — a single `.gitmodules` entry — and the trigger path (view submodule diff → click "Open Repository") is a normal, expected workflow rather than an unnatural step. The existing "guard" (the `http(s)`-prefix log statement in `main.ts`) does not actually block anything, so there is no effective mitigation in the code today.

### Recommendation
Validate/allow-list the URL scheme before calling `shell.openExternal` (restrict to `https:`/`http:` and reject `file:`, `search-ms:`, or unknown custom schemes) both in `LinkButton.onClick` and in the `open-external` IPC handler in `app/src/main-process/main.ts`. Additionally, sanitize/validate `submodule.*.url` values retrieved from `.gitmodules` before using them to build any UI affordance, since they originate from untrusted repository content.

### Proof of Concept
1. Attacker creates a public repository with a `.gitmodules` file containing a submodule whose `url` is set to a malicious URI, e.g. `file://attacker-host/share/payload` or a registered custom scheme like `search-ms:query=...&crumb=location:\\attacker-host\share`.
2. Victim clones/fetches this repository with GitHub Desktop and views the working-directory changes for the submodule path, which triggers `getWorkingDirectoryDiff` → `buildSubmoduleDiff`, reading the malicious URL straight from config: [6](#0-5) .
3. Desktop renders the "Open this submodule on GitHub Desktop" suggested action / repository link using this URL: [3](#0-2) .
4. Victim clicks the link/button; `LinkButton.onClick` calls `shell.openExternal(uri)` unconditionally: [7](#0-6) .
5. Electron passes the raw URI to the OS shell, which resolves the scheme handler (e.g., SMB share access leaking NTLM credentials, or a locally installed app protocol handler), all without any additional validation in the codebase.

I could not verify from the index whether `parseRepositoryIdentifier` (in `app/src/lib/remote-parsing.ts`) performs any scheme filtering before the `renderSubmoduleInfo` path constructs its own `https://` string (that specific code path does look safer since it always prefixes `https://`), but the `renderOpenSubmoduleAction`/`diff.url` path passes the raw, unvalidated URL straight through — this is the exploitable path. Due to index size limits, I was unable to fully inspect `app/src/lib/remote-parsing.ts` or the main-process `shell.ts`/`main-process-proxy.ts` implementations of `openExternal` for additional sanitization; starting a Devin session would allow full inspection of these files to confirm whether any scheme filtering exists deeper in the Electron main process.
