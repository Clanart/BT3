### Title
Missing `num_signed_kickoffs <= num_kickoffs_per_round` validation in `ProtocolParamset` permanently breaks all deposit processing — (`crates/clementine-config/src/protocol.rs`, `core/src/config/protocol.rs`)

---

### Summary

`ProtocolParamset` accepts `num_signed_kickoffs > num_kickoffs_per_round` with no validation. When this misconfiguration is present, `get_kickoff_utxos_to_sign` silently returns fewer kickoff indices than the protocol expects, and the verifier rejects every deposit with a count-mismatch error. The bridge becomes completely non-functional for deposits: all user BTC sent to deposit addresses is frozen until the `user_takes_after` timelock expires.

---

### Finding Description

`get_kickoff_utxos_to_sign` builds a candidate pool of exactly `num_kickoffs_per_round` indices, shuffles it, then calls `.take(num_signed_kickoffs)`:

```rust
let mut numbers: Vec<usize> = (0..paramset.num_kickoffs_per_round).collect();
numbers.shuffle(&mut rng);
numbers.into_iter().take(paramset.num_signed_kickoffs).collect()
``` [1](#0-0) 

When `num_signed_kickoffs > num_kickoffs_per_round` (e.g., 15 vs 10), `.take(15)` on a 10-element iterator silently yields only 10 elements — no error, no panic. The sighash stream therefore emits kickoff-txid markers for only `num_kickoffs_per_round` kickoffs.

The verifier then enforces the expected count:

```rust
if kickoff_txids[operator_idx][round_idx].len()
    != self.config.protocol_paramset().num_signed_kickoffs
{
    return Err(eyre::eyre!(
        "Number of signed kickoff utxos for operator: {}, round: {} is wrong. Expected: {}, got: {}",
        ...
    ).into());
}
``` [2](#0-1) 

Because the sighash stream always produces `num_kickoffs_per_round` txids but the check demands `num_signed_kickoffs`, the check **always fails** for every operator and every round. Every deposit is rejected at the verifier's `deposit_finalize` step.

Neither loading path validates this constraint. `from_env()` checks only `finality_depth >= 1`: [3](#0-2) 

`from_toml_file()` applies the identical single check: [4](#0-3) 

`check_general_requirements()` validates `genesis_chain_state_hash`, `start_height >= genesis_height`, and `finality_depth >= 1` — but not the kickoff relationship: [5](#0-4) 

A grep across the entire repository confirms there is no cross-field validation of `num_signed_kickoffs` against `num_kickoffs_per_round` anywhere in production code.

---

### Impact Explanation

Once the bridge starts with `num_signed_kickoffs > num_kickoffs_per_round`:

1. Every deposit UTXO sent on-chain by a user is accepted by the deposit address but cannot be processed by the bridge — the verifier rejects the signing session unconditionally.
2. Users' BTC is frozen in the deposit taproot address until the `user_takes_after` CSV timelock (default 200 blocks, ~33 hours on mainnet) allows the recovery key path to be spent.
3. The bridge is completely non-functional for deposits until it is restarted with a corrected paramset — but restarting with a different paramset breaks compatibility with any partially-processed deposits already in the database, since the paramset governs transaction construction and pre-signed sighashes.

This breaks bridge liveness with direct, measurable fund impact on every depositor.

---

### Likelihood Explanation

The constraint `num_signed_kickoffs <= num_kickoffs_per_round` is an implicit protocol invariant that is not documented in the struct field comments, not enforced at parse time, and not caught by `check_general_requirements()`. An operator tuning throughput (e.g., increasing `num_signed_kickoffs` for security without proportionally increasing `num_kickoffs_per_round`) can trivially violate it. The `.take()` call provides no warning — it silently truncates — so the misconfiguration is not caught until the first live deposit attempt fails.

---

### Recommendation

Add an explicit cross-field validation in both `from_env()` (in `core/src/config/protocol.rs`) and `from_toml_file()` (in `crates/clementine-config/src/protocol.rs`), immediately after the existing `finality_depth` check:

```rust
if config.num_signed_kickoffs > config.num_kickoffs_per_round {
    return Err(BridgeError::ConfigError(format!(
        "num_signed_kickoffs ({}) must be <= num_kickoffs_per_round ({})",
        config.num_signed_kickoffs, config.num_kickoffs_per_round
    )));
}
if config.num_signed_kickoffs == 0 {
    return Err(BridgeError::ConfigError(
        "num_signed_kickoffs must be >= 1".to_string(),
    ));
}
```

The same check should be added to `check_general_requirements()` in `core/src/config/mod.rs` so that runtime startup validation also catches the condition.

---

### Proof of Concept

1. Set `NUM_SIGNED_KICKOFFS=15` and `NUM_KICKOFFS_PER_ROUND=10` in the environment (or equivalently in a TOML paramset file).
2. Start all bridge actors (aggregator, verifiers, operators).
3. Send a valid deposit UTXO to the bridge deposit address on-chain.
4. Trigger deposit processing via the aggregator RPC.
5. `get_kickoff_utxos_to_sign` returns 10 indices (not 15) for every operator/round combination.
6. The verifier's count check fires: `"Number of signed kickoff utxos for operator: <pk>, round: 1 is wrong. Expected: 15, got: 10"`.
7. The deposit is rejected; the user's BTC remains locked in the deposit address until the `user_takes_after` (200-block) CSV timelock allows recovery.
8. Every subsequent deposit attempt produces the identical failure — the bridge is permanently non-functional for deposits under this configuration.
