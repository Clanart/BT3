### Title
Rebasing/interest-bearing escrow tokens permanently lock accrued rewards in `IntentGatewayV2` due to snapshot-based escrow accounting - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` already defends against fee-on-transfer tokens by measuring `balanceOf` deltas before crediting escrow, but the escrow ledger itself (`_orders[commitment][token]`) is a fixed snapshot taken once at `placeOrder`/`fillOrder` time. Withdrawal (`_withdraw`) always transfers exactly the stored snapshot `amount`, never the contract's live token balance. For rebasing or interest-accruing ERC-20s (e.g. stETH, aTokens) escrowed by the gateway, any balance increase that accrues to the gateway's holdings between escrow and redemption is never recorded anywhere and can never be withdrawn — it is permanently stranded in the contract, exactly the broken invariant described in the external report.

### Finding Description
`_orders[bytes32 commitment][address token]` is the sole record of how much of a token is owed to a beneficiary for a given order commitment: [1](#0-0) 

Escrow is populated as a static amount at `placeOrder` time (already balance-delta corrected for fee-on-transfer at deposit, e.g. in `IntentGatewayV2.sol`'s `placeOrder`/`fillOrder` flow), but from that point forward it is never re-derived from `balanceOf(address(this))`: [2](#0-1) 

Release of escrow in `_withdraw` transfers precisely the stored snapshot `amount` and decrements the ledger by that same amount — it never consults or reconciles against the token's actual current balance held by the contract: [3](#0-2) 

If the escrowed `token` is rebasing (balance grows autonomously via `rebase()`/interest accrual while sitting in the gateway between `placeOrder` and the eventual `RedeemEscrow`/fill/cancel), the additional balance accrued during that custody window is never captured by `_orders`, is not part of `reducedInputs`/`DustCollected` accounting (which only fires on the deposit-time fee delta), and has no corresponding withdrawal or sweep path referencing live balance. It sits in the contract forever with no mapping key pointing to it and no `SweepDust`/`RequestKind` operation that can recover it (the existing `SweepDust`/dust-sweep flows only ever look at dispatcher-side sweeps during predispatch, not at the gateway's own post-escrow balance growth).

### Impact Explanation
This is a permanent, unrecoverable loss of value for any user or solver whose order escrows a rebasing/yield-bearing token in `IntentGatewayV2`. Unlike the fee-on-transfer case (correctly handled via balance-delta measurement at deposit), there is no mechanism anywhere in the escrow lifecycle that re-measures balance at withdrawal time, so accrued yield becomes stuck protocol-owned dust with no owner and no sweep entrypoint tied to it. Given intents/orders are a core, unprivileged, user-facing entrypoint of the bridge (not a malicious-relayer or governance scenario), this qualifies as fund loss under the bounty's "stealing or loss of funds" category.

### Likelihood Explanation
Any user can trigger this simply by placing/filling an order (`placeOrder`/`fillOrder`) whose input or output asset is a rebasing ERC-20, with no privileged actor, malicious relayer, or governance action required. The longer an order sits in escrow (e.g. undelivered cross-chain fills, contested cancellations, or long timeout windows), the larger the stranded rebase amount grows.

### Recommendation
Track escrow as shares of the token's total balance (or record a per-token rebase index at deposit and rescale on withdrawal) rather than an absolute snapshot amount, so that `_withdraw` releases a beneficiary's proportional share of the live balance. As a minimal mitigation, maintain an explicit denylist/registry restricting `IntentGatewayV2` order inputs/outputs to non-rebasing tokens, or add a per-token "post-fill balance reconciliation" sweep that credits any residual balance in excess of outstanding `_orders` sums back to a designated beneficiary.

### Proof of Concept
1. Token `RBT` is a rebasing ERC-20 whose `balanceOf` increases for all holders periodically (e.g. daily rebase of +0.01%).
2. User calls `placeOrder` with `RBT` as an input asset, amount `1000e18`; `_orders[commitment][RBT] = 1000e18` is recorded exactly as escrowed (see `IntentsBase.sol:334-343` equivalent flow in `IntentGatewayV2.sol`).
3. Before the order is filled/redeemed, `RBT` rebases upward; `IntentGatewayV2`'s actual `RBT.balanceOf(address(this))` is now `1005e18` (the extra `5e18` accrued to the gateway's holdings from the rebase).
4. Order is eventually filled/refunded via `_withdraw`, which reads `_orders[commitment][RBT] == 1000e18` and calls `IERC20(RBT).safeTransfer(beneficiary, 1000e18)`, then sets `_orders[commitment][RBT] = 0`.
5. The `5e18` rebase surplus remains in the gateway contract with no `_orders` entry referencing it and no sweep call ever targeting it — it is permanently locked, unrecoverable by the user, solver, or protocol governance through any existing entrypoint.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
