### Title
`SignableTransaction` excludes the OP_RETURN output from weight/fee calculation, so a signed transaction can pay less than the minimum relay fee for its actual size and never confirm — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
Analogous to the reported issue (an action's real cost exceeds what was budgeted for it, breaking the mechanism), `SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of user data to the transaction's `tx_outs`, but `calculate_weight_vbytes` is only ever called with `payments` — the `data` output is never included in the size estimate. `needed_fee` is therefore computed over a smaller virtual transaction than the one that is actually signed and broadcast.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- The OP_RETURN output is pushed into `tx_outs` when `data` is `Some` [1](#0-0) 
- `calculate_weight_vbytes` builds a mock transaction whose outputs come **only** from `payments` plus optional `change`; it has no parameter for the data output [2](#0-1) 
- Both call sites pass `payments` and omit the data: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` [3](#0-2) 
- `needed_fee = fee_per_vbyte * vbytes` uses the underestimated `vbytes` [4](#0-3) 
- The minimum-relay-fee guard `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` also uses the underestimated `vbytes` [5](#0-4) 
- The `MAX_STANDARD_TX_WEIGHT` check uses the same underestimated `weight` [6](#0-5) 

An 80-byte OP_RETURN output adds roughly 90+ vbytes (~360 WU: 8-byte amount + ~83-byte script + output overhead) that are never accounted for.

### Impact Explanation
When a change output is present, the change value is set to `input_sat - payment_sat - fee_with_change` [7](#0-6) , so the **actual** fee paid equals `fee_with_change` exactly, while the real transaction is ~90 vbytes larger. The effective fee rate is therefore materially lower than the requested `fee_per_vbyte`. At low fee rates (e.g., near `DEFAULT_MIN_RELAY_TX_FEE`), the produced transaction falls below the minimum relay fee for its true size: it is rejected by the mempool, the FROST-signed inputs are never spent, and the multisig's outputs remain locked until a corrected transaction is re-signed — a liveness/fund-availability failure produced from transaction data supplied to the builder. When no change exists, the leftover still becomes fee, but the reported `needed_fee()`/`fee()` accounting and the `TooLowFee`/`TooLargeTransaction` policy checks are all computed on the wrong size, so `needed_fee()` understates the requirement for downstream callers (e.g., `needed_fee` in `processor/src/networks/bitcoin.rs` uses it to price plans [8](#0-7) ).

### Likelihood Explanation
The defect triggers deterministically whenever `data` is `Some` — the size estimate is wrong for every such transaction, not just edge cases. Whether it causes a relay failure depends on the fee rate and data size, but the miscalculation itself is unconditional. Medium likelihood: requires the wallet's `data` path to be exercised with a low-enough `fee_per_vbyte`.

### Recommendation
Include the OP_RETURN output in the size estimation — e.g., extend `calculate_weight_vbytes` to accept the `data: Option<&[u8]>` (or the constructed `ScriptBuf`) and append the corresponding `TxOut` to the mock transaction before computing `weight`, mirroring how `change` is handled [9](#0-8) .

### Proof of Concept
```rust
// In SignableTransaction::new, with data = Some(vec![0; 80]):
// tx_outs gains an OP_RETURN output (send.rs:194-202), but
// vbytes = calculate_weight_vbytes(inputs, payments, None) ignores it.
let data = vec![0u8; 80];
let st = SignableTransaction::new(inputs, &payments, Some(change), Some(data), 1 /* sat/vb */)?;
// needed_fee = 1 * vbytes(smaller tx)
// actual vsize of st.tx is ~vbytes + 93
// actual fee paid (with change) = needed_fee
// effective rate = needed_fee / real_vsize < 1 sat/vb < DEFAULT_MIN_RELAY_TX_FEE/1000
// → passes the TooLowFee check at send.rs:211 yet is unrelayable.
```
The `TooLowFee` check at `send.rs:211` divides by the same underestimated `vbytes`, so it cannot catch this case.

    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
