### Title
Unvalidated attacker-controlled offset registration produces deposits spendable by an arbitrary script path - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report concerns a publicly reachable `Set` method that mutates a security-relevant parameter with no authorization check and no value validation. The analog in Serai's in-scope code is `Scanner::register_offset`, which accepts an arbitrary caller-supplied `Scalar` offset and registers the resulting Taproot output key as a deposit destination — with no validation that the offset was securely derived. The function's own documentation concedes the hazard: arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)". An unprivileged party who can cause an offset to be registered for a deposit (e.g., an HDKD offset attached to their deposit) can craft an output the scanner credits as received but which is spendable via an attacker-controlled script path — funds reported received that are not spendable by the validator set.

### Finding Description
`Scanner` maps `ScriptBuf → Scalar` offsets and `scan_transaction` marks any output whose `script_pubkey` matches as a `ReceivedOutput` spendable by `group_key + offset`. `register_offset` at `networks/bitcoin/src/wallet/mod.rs:180` takes `offset: Scalar` directly and loops `p2tr_script_buf(self.key + GENERATOR * offset)` until an even point is found, incrementing the offset on odd points, then inserts `scripts[script] = offset`.

Two defects combine:

1. **No provenance/validation on `offset`.** The scalar is unauthenticated input, exactly like the D-Bus `MaxConcurrentOperations` setter: any caller can register any value. The only "validation" is the even-Y loop, which is a encoding constraint, not a security constraint.
2. **Surjective, collision-prone mapping.** Because odd points force `offset += 1`, distinct requested offsets collapse onto the same script; the doc notes offsets are "surjective, not bijective" and ordering-dependent. An attacker can pre-register a script that collides with, or is equivalent to, a later honest registration — or register an offset under which `self.key + offset*G` corresponds to an internal key the attacker controls relative to a chosen script tree, making the deposit output script-path spendable.

When `scan_transaction` later matches the registered `script_pubkey`, it emits a `ReceivedOutput` with the stored offset, which Serai treats as spendable funds under `tweak_keys`/`send.rs` signing. But an output whose internal key was attacker-constructed can be spent via the attacker's script path, so the credited deposit is stealable (or unspendable) by the group.

### Impact Explanation
An attacker registers a maliciously chosen offset, causes an honest payer to deposit to the resulting `script_pubkey`, the scanner credits the funds as received by Serai, and the attacker spends the UTXO via the injected script path. Serai reports received funds that are not spendable by the threshold key — equivalent to minting credit against unspendable/stolen collateral. This satisfies the "funds reported received that are not spendable" acceptance criterion and parallels the report's unauthenticated-parameter-set causing a security loss.

### Likelihood Explanation
Medium likelihood, matching the Medium severity of the source advisory. Exploitation requires (a) a code path where external users can request/register an offset for deposit addresses (the standard HDKD deposit flow), and (b) the attacker choosing rather than receiving the scalar. No threshold collusion, malicious validator, or leaked key is needed — the attacker only supplies untrusted bytes (`Scalar`) to a public registration API, which is within the permitted reachability model.

### Recommendation
Authenticate offset registration: derive offsets via a deterministic hash-to-scalar over `(group_key, deposit_index/context)` rather than accepting raw scalars, so the discrete log of the offset is unknown to any party; or require a proof/transcript binding the offset to approved deposit metadata. Reject `register_offset` calls where the caller supplies the scalar directly, and document that the current API is `unsafe` unless offsets are securely generated.
