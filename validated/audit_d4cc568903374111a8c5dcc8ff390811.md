### Title
Unprotected internal WOM→mWOM swap due to hardcoded zero slippage parameter in `ArbWomUp3._deposit` (mode 2) - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.incentiveDeposit` lets any unprivileged wallet deposit WOM with `_mode == 2`, which routes half of the deposited WOM through `SmartWomConvert.convert` to be swapped for mWOM via the Wombat router. `ArbWomUp3` hardcodes the `_minRec` slippage-protection parameter to `0` on this call, so the swap executes with no minimum-output guarantee, exposing the user to sandwich attacks — the exact bug class described in the JOJO `FlashLoanLiquidate.JOJOFlashLoan` report (missing `minReceive` enforcement around a swap).

### Finding Description
In `ArbWomUp3._deposit`, when `_mode == 2`, half the user's WOM is sent to `SmartWomConvert.convert` with the `_minRec` argument hardcoded to `0`: [1](#0-0) 

`SmartWomConvert.convert` forwards this straight to `_convertFor`, which performs the actual token swap via `IWombatRouter.swapExactTokensForTokens` with the router-level `amountOutMin` hardcoded to `0` regardless of the caller-supplied `_minRec`, and only checks the *total* output against `_minRec` afterward: [2](#0-1) 

Because `ArbWomUp3` always passes `_minRec = 0` for this path, the post-swap check `convertAmount + amountRec < _minRec` at line 204 can never revert (any non-negative value satisfies `>= 0`), meaning the swap has zero effective slippage protection. An attacker can sandwich the underlying Wombat pool swap (front-run to move the WOM/mWOM price, let the victim's swap execute at a bad rate, back-run to restore price and capture the difference), directly stealing value from the depositing user. This mirrors the JOJO finding precisely: one code path (`GeneralRepay`/`FlashLoanRepay` analog = `SmartWomConvert.convert` when called directly by a user with a real `_minRec`) enforces slippage, while another path reachable by an ordinary user (`ArbWomUp3._deposit` mode 2) discards that protection by hardcoding the parameter to zero.

### Impact Explanation
Any ordinary wallet calling `ArbWomUp3.incentiveDeposit(..., _mode = 2)` has 50% of its deposited WOM swapped with no slippage floor. A sandwiching MEV bot can extract value directly from the victim's swap, resulting in the user receiving materially less mWOM (and thus less locked value in `mWomSV`) than the fair-market rate — a direct theft of user funds proportional to pool depth and trade size.

### Likelihood Explanation
Likelihood is high: `incentiveDeposit` is a normal user-facing function with no privileged access control, and `_mode == 2` is a documented supported mode. Any user (or MEV searcher watching the mempool) can trigger and exploit this path deterministically once WOM/mWOM liquidity exists.

### Recommendation
`ArbWomUp3._deposit` should accept and forward a genuine caller-supplied `_minRec` for the `smartWomConvert.convert` call (instead of hardcoding `0`), and/or `SmartWomConvert._convertFor` should pass a computed minimum output (derived from `_minRec` and the buyback/convert split) directly to `IWombatRouter.swapExactTokensForTokens` rather than `0`, so the router itself enforces slippage on the swap leg, not just an ineffective post-hoc total check.

### Proof of Concept
1. Attacker monitors mempool for calls to `ArbWomUp3.incentiveDeposit(amount, convertRatio, bullMode, 2)`.
2. Attacker front-runs with a large WOM→mWOM (or mWOM→WOM) swap on the same Wombat pool (`womMWomPool`), skewing the price.
3. Victim's transaction executes: `_deposit` swaps `toSwap` WOM for mWOM via `smartWomConvert.convert(toSwap, _convertRatio, 0, 0)` → `_convertFor` → `IWombatRouter.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)`, receiving an unfavorable `amountRec` with no minimum enforced (`_minRec = 0` trivially satisfies the check at `SmartWomConvert.sol:204`).
4. Attacker back-runs to restore the pool price, capturing the spread as profit extracted from the victim's swap.
