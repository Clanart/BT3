### Title
Crafted `ThresholdKeys<Ed448>` deserialization admits identity verification shares, yielding an identity `group_key` that panics on serialization (DoS) - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::<C>::read` reconstructs threshold keys from attacker-controlled bytes using `<C as Ciphersuite>::read_G`, which — unlike `frost::Curve::read_G` — does **not** reject the identity point. For the Ed448 ciphersuite, an attacker can supply verification shares whose Lagrange-interpolated sum is the identity, producing `ThresholdKeys` whose `group_key` is the point at infinity. Any subsequent `to_bytes()` on that point panics at `z.invert().unwrap()` in `Ed448`'s `Point::to_bytes`, crashing the process. This mirrors CVE-2026-20054: improper error checking on decompression/deserialization of crafted input causing a denial of service.

### Finding Description

Two layered defects:

1. **Identity not rejected on the deserialization path used by `ThresholdKeys::read`.** `Ciphersuite::read_G` only checks canonicity of the encoding, not identity [1](#0-0) . `Curve::read_G` (used by FROST) does reject identity [2](#0-1) , but `ThresholdKeys::read` reads its `n` verification shares through `C::read_G`, i.e., the *Ciphersuite* impl [3](#0-2) . For Ed448, the identity encoding (`y = 1`, sign bit 0) is canonical and passes `from_bytes` — `is_torsion_free` is satisfied and `not_negative_zero` holds since the sign bit is 0 [4](#0-3) .

2. **`group_key` is computed by interpolation without an identity check.** `ThresholdKeys::new` computes `group_key` as the weighted sum of `verification_shares[1..=t]` [5](#0-4) . An attacker crafting the byte stream fully controls these shares and can make the sum the identity: e.g., `t = 2` with shares `v1 = G`, `v2 = 2·G` yields `group_key = 2·v1 − v2 = identity` under Lagrange factors `{1: 2, 2: −1}`.

3. **Serializing the identity Ed448 point panics.** `Point::to_bytes` calls `self.z.invert().unwrap()`; the identity has `z = 0`, `invert` returns `CtOption::none`, and `unwrap` panics [6](#0-5) . `group_key().to_bytes()` is invoked on the FROST signing path when binding `rho` (`append_message(b"group_key", ...)`) [7](#0-6) , so merely attempting to sign with the deserialized keys crashes.

### Impact Explanation

An unauthenticated party who can feed crafted bytes to `ThresholdKeys::read` (permitted threat surface for this scan) causes a deterministic panic — an availability failure equivalent to the Snort engine crash in the referenced advisory. Because the panic occurs inside `sign`/serialization, it crashes the hosting process rather than returning an `io::Error`, bypassing all error handling around `read`.

### Likelihood Explanation

The trigger requires only byte-level control: no discrete logs, no valid shares, no threshold collusion. Constructing `v1, v2` for an identity `group_key` is trivial arithmetic on public generators. The crash is deterministic (not probabilistic) once the keys are used in any code path that encodes `group_key`.

### Recommendation

- Reject identity points in `Ciphersuite::read_G`, or at minimum in `ThresholdKeys::read`/`ThresholdKeys::new` (check each verification share *and* the computed `group_key` with `is_identity`).
- Make `ed448::Point::to_bytes` total: never `unwrap` on `z.invert()` — handle the identity encoding explicitly.

### Proof of Concept

Conceptual byte stream fed to `ThresholdKeys::<Ed448>::read`:

1. `C::ID` length + ID matching Ed448.
2. `t = 2`, `n = 2`, `i = 1` (valid `ThresholdParams`).
3. `interpolation = 1` (Lagrange).
4. `secret_share = read_F` — any canonical scalar (e.g., zero).
5. `verification_shares`: `v1 = G` (canonical encoding of the generator), `v2 = 2·G`.

`ThresholdKeys::new` then computes `group_key = λ₁·v1 + λ₂·v2 = 2·G − 2·G = identity`, accepted without error. Any subsequent `keys.group_key().to_bytes()` — e.g., inside `AlgorithmSignMachine::sign`'s `rho_transcript.append_message(b"group_key", ...)` — panics at `self.z.invert().unwrap()` in `crypto/ed448/src/point.rs`, crashing the process.
