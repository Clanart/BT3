### Title
Hardcoded storage-slot assumption for `_filled` used in cross-chain proof verification, with no `__gap`/layout enforcement - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The core `__gap` problem in the external report is that reserved-slot bookkeeping in upgradeable storage layouts is untracked and inconsistently sized, so a layout change can silently shift a variable into a slot another part of the system depends on. The local analog in Hyperbridge is not `__gap` itself (no `__gap` reservation exists in `IntentsBase.sol`), but the same underlying invariant: **a raw, hardcoded storage slot number is depended upon by the cross-chain proof-verification path, with only a code comment and a single unit test protecting it — no compiler-level or `__gap`-style layout guarantee.**

### Finding Description
`IntentsBase.sol` declares: [1](#0-0) 

This constant is a raw byte-encoding of storage slot `2`, and the comment states it is "used to construct storage proof keys for cross-chain cancel verification." The `_filled` mapping itself is declared as: [2](#0-1) 

`IntentGatewayV2` composes this base through a diamond inheritance (`IntentsBase` / `IntrinsicIntents` / `ExtrinsicIntents` plus `EIP712`, `ReentrancyGuardTransient`, `Initializable`): [3](#0-2) 

The only thing enforcing that `_filled` actually lives at slot 2 in the final linearized proxy storage layout is a regression test: [4](#0-3) 

This mirrors exactly the pattern flagged in the external report: instead of a documented, `__gap`-tracked storage map that a compiler/layout tool can verify, the protocol relies on a manually maintained constant (`FILLED_SLOT_BIG_ENDIAN_BYTES`) plus a single Foundry assertion to keep a security-critical cross-chain proof key correct. There is no `__gap` in any base contract in this inheritance chain (`IntentsBase`, `IntrinsicIntents`, `ExtrinsicIntents`), and no automated storage-layout diff check ties future PRs to the assumed slot. Any of the following — adding a new storage variable to `IntentsBase` above `_filled`, adding a new inherited mixin with storage before `IntentsBase` in the linearization, or reordering the `is` list in `IntentGatewayV2` — would silently move `_filled` off slot 2 without any compile-time error, since Solidity storage layout composition is purely positional and unchecked by the compiler across separately-authored base contracts.

Because `FILLED_SLOT_BIG_ENDIAN_BYTES` is used to build the storage proof key for a remote chain's state root during cross-chain order cancellation, a silent slot shift would make the destination-chain verifier read the *wrong* storage slot value as "the fill/cancel status of the order." Depending on what that slot happens to contain post-shift (e.g., `_nonce`, part of `_params`, or zero/uninitialized storage from a newly added variable), a state proof for an unrelated value could be misinterpreted as "order filled" or "order not filled," enabling a double-refund/double-cancel (fund duplication) or a false negative that lets an already-filled order be refunded again — a direct violation of the "one-time receipt handling" and "false proof/state acceptance" bounty categories.

### Impact Explanation
If the assumed slot for `_filled` ever diverges from the deployed contract's actual layout (which nothing but a manual test currently prevents), the cross-chain cancellation state-proof verification would authenticate against the wrong storage cell. This can cause the contract to accept a false "filled"/"not filled" state for an order commitment, which directly enables double-settlement of escrowed funds (refund an order that was already filled, or fill an order that was already refunded) — matching the "replay/double-claim/double-settlement" and "false proof/state acceptance" impact categories.

### Likelihood Explanation
This is a latent/systemic risk rather than an exploit reachable by an unprivileged attacker against the *current* deployed bytecode without any code change — today's layout is pinned by `testFilledMappingStaysAtSlotTwo`, so no currently-provable unprivileged exploit path against the live contract was found in the code available for review. The risk materializes only on future edits (new storage variables, added mixins, or inheritance reordering) analogous to the historical `across-protocol/contracts` PR #991 pattern cited in the report, where a `__gap` was resized while a variable was removed. This is precisely the class of change the original report warns is "dangerous" because it can silently create an exploitable mismatch after the next upgrade.

### Recommendation
- Replace the hardcoded `FILLED_SLOT_BIG_ENDIAN_BYTES` constant with a storage-layout enforcement mechanism: either use OpenZeppelin's namespaced storage (ERC-7201) with a fixed, hash-derived slot for `_filled` that is independent of declaration order, or add automated CI tooling (e.g., `forge inspect --storage-layout` diffing) that fails the build if `_filled`'s slot changes.
- Explicitly document, next to every base contract in the `IntentsBase` / `IntrinsicIntents` / `ExtrinsicIntents` / `IntentGatewayV2` inheritance chain, the full storage layout and slot numbers, the way `__gap` variables are supposed to be documented per the external report's recommendation.
- Add a CI-enforced storage-layout regression check (not just a single Foundry test) that runs on every PR touching these contracts, verifying `_filled`'s slot and any other slot referenced by hardcoded proof-key constants.

### Proof of Concept
No concrete, currently-triggerable proof-of-concept against the live bytecode was established — the only path to actually observing a wrong-slot read requires a future storage-layout-breaking code change (e.g., inserting a new state variable before `_filled` in `IntentsBase`, or adding a storage-bearing mixin ahead of it in `IntentGatewayV2`'s inheritance list). At that point, calling the cross-chain cancellation entrypoint that builds a storage proof key from `FILLED_SLOT_BIG_ENDIAN_BYTES` would read the shifted slot's contents instead of the true `_filled[commitment]` value, causing the proof verifier to accept a false fill/cancel state for that commitment.

        (bytes32 filledCommitment,,,) = _seedUpgradeState();

        // _filled is `mapping(bytes32 => address)` declared at storage slot 2. The cross-chain
        // cancel proof (FILLED_SLOT_BIG_ENDIAN_BYTES) depends on this exact slot.
