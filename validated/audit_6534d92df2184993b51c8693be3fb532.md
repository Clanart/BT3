### Title
Unbounded CLVM execution during offer cancellation causes wallet CPU exhaustion - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_cancellation_coins()` re-executes every non-addition coin spend's `puzzle_reveal`/`solution` in the offer with `run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)` to discover announcement/dependency conditions, with no cost ceiling applied. This mirrors the CVE-2017-11188 bug class: a "large loop"/expensive-parse operation is performed on attacker-supplied data with no bound (there, an EOF/size check was missing in `ReadDPXImage`; here, the CLVM cost limit is missing before executing untrusted puzzle reveals from an offer file).

### Finding Description
When a wallet user receives an `Offer` (e.g., a `.offer`/bech32 blob from an untrusted counterparty) and calls into cancellation logic, `get_cancellation_coins()` iterates over the coin spends and runs each puzzle reveal with `INFINITE_COST`: [1](#0-0) 

Unlike mempool admission (`get_name_puzzle_conditions`) and block validation, which enforce `MAX_BLOCK_COST_CLVM`/generator cost limits before executing any CLVM program (as seen in the mempool tests exercising cost-bounded execution of malicious generators), this offer-inspection code path executes attacker-controlled `puzzle_reveal`+`solution` pairs with no cost limit at all: [2](#0-1) 

An offer author fully controls every `puzzle_reveal` and `solution` in the coin spends that make up an `Offer` (since offers are never required to pass mempool admission before being shared/parsed locally). A malicious counterparty can craft a puzzle reveal that is cheap to construct but extremely expensive to run under CLVM (e.g., using the same large-string/duplication technique used in the malicious-generator regression tests such as `SINGLE_ARG_INT_COND`/`SINGLE_ARG_INT_LADDER_COND`, which are specifically designed to blow up CLVM execution cost while staying compact on the wire): [3](#0-2) 

Because `get_cancellation_coins()` calls `run_with_cost` with `INFINITE_COST` rather than a bounded cost such as `MAX_BLOCK_COST_CLVM`, this crafted puzzle reveal will run to completion (or until process/host resource limits are hit) instead of failing fast with a cost-exceeded error, unlike every other path in the codebase that runs untrusted CLVM (mempool admission, block validation) which always caps cost.

### Impact Explanation
This is a spend-triggered transaction-processing halt reachable by an unprivileged offer counterparty: simply sending a crafted offer file to a wallet user (or having the wallet load/inspect it, e.g. for cancellation UX) can pin a CPU core indefinitely, denying service to that wallet process without the attacker needing to broadcast anything to the mempool or interact with any node. Because the execution is unbounded (`INFINITE_COST`), the usual mempool/consensus cost-limit defenses that protect every other CLVM execution path in this codebase (full node mempool admission, block body validation) do not apply here.

### Likelihood Explanation
Likelihood is high for any wallet workflow that inspects/cancels offers from untrusted sources: constructing a compact-but-expensive puzzle reveal using known CLVM cost-amplification techniques (documented in this codebase's own "malicious generator" test suite) is straightforward and requires no signature or on-chain interaction — the attacker only needs to produce an `Offer` blob and get the victim to load/cancel it.

### Recommendation
Replace `INFINITE_COST` in `get_cancellation_coins()` (and any other `run_with_cost` call operating on offer-supplied `puzzle_reveal`/`solution` pairs in `chia/wallet/trading/offer.py`) with a bounded cost constant consistent with consensus limits (e.g., `MAX_BLOCK_COST_CLVM` or a smaller wallet-appropriate cap), and handle the resulting cost-exceeded error by treating the offending coin as un-cancelable/invalid rather than letting execution run unbounded.

### Proof of Concept
1. Construct coin spends for an `Offer` where at least one non-addition coin's `puzzle_reveal` is a CLVM program built with the doubling/large-string technique from `SINGLE_ARG_INT_COND`/`SINGLE_ARG_INT_LADDER_COND` (small on-disk size, but requires very high CLVM execution cost to run), paired with a matching `solution`.
2. Package these coin spends into a `WalletSpendBundle`/`Offer` object (e.g., serialize via `Offer.from_bech32`/`Offer.from_bytes`, as done in `Offer.from_bech32`) and deliver it to a victim wallet. [4](#0-3) 
3. Have the victim wallet call `Offer.get_cancellation_coins()` (reachable via `TradeManager`'s cancel-offer flow) — the crafted puzzle reveal is executed via `run_with_cost(..., INFINITE_COST, ...)` with no cost ceiling, consuming CPU indefinitely and stalling the wallet process.
