Confirmed: `query_string_valid?` only validates the HMAC signature and never checks the `timestamp` value against current time.### Title
App proxy request replay accepted indefinitely due to missing timestamp freshness check - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`query_string_valid?` in `ShopifyApp::AppProxyVerification` only verifies the HMAC signature over the query parameters and never checks the `timestamp` parameter's age against the current time. As a result, any previously captured valid app-proxy query string (including its signature) remains accepted forever, regardless of how old it is.

### Finding Description
The `verify_proxy_request` before_action calls `query_string_valid?(request.query_string)`, which parses the query string, extracts and removes `signature`, then recomputes the signature over the remaining parameters (including `timestamp`) and compares it via `ActiveSupport::SecurityUtils.secure_compare`. [1](#0-0)  `timestamp` is treated purely as one more field folded into the HMAC input in `calculated_signature`, not as a freshness token that is independently validated against `Time.now`. [2](#0-1)  Since the signature is deterministic given the same parameter set and shared secret, an attacker who observes one legitimate app-proxy request (e.g., via network capture, browser history, referer/access logs, or a shared proxy log) can replay the identical query string (`shop`, `path_prefix`, `timestamp`, `signature`) at any point in the future and it will pass verification, because the check only re-derives and compares the HMAC — it performs no comparison of `timestamp` to the current request time or any staleness window. The test suite confirms this: `basic_query_string` and `query_string_complex_args` tests pass fixed, years-old timestamps (`1466106083`, i.e., 2016) and successfully validate against a static test secret. [3](#0-2) 

### Impact Explanation
This allows an unauthenticated attacker to submit forged/replayed requests to any controller/action that only relies on `ShopifyApp::AppProxyVerification` for authorization, indefinitely after the original request was issued. This matches the Shopify HackerOne "forged app-proxy request" impact class — an attacker can invoke app-proxy actions on behalf of a shop without any live session, as long as they've observed a single legitimate request once (even from years prior). If any app-proxy action performs state-changing behavior or returns shop-specific/sensitive data keyed off the replayed `shop` parameter, this is directly exploitable for unauthorized action execution or data exposure under the guise of the captured shop.

### Likelihood Explanation
The attacker only needs to observe one full valid app-proxy query string once (e.g. captured from a browser's `Referer` header, proxy/CDN access logs, browser history, or network traffic) — this is a passive, unprivileged capture, not something requiring app secret or session compromise. Since there is no timestamp expiration check, the captured query string is valid forever, making the replay trivially repeatable at any later time with no rate or freshness constraint.

### Recommendation
In `query_string_valid?`, after confirming signature validity, additionally parse `query_hash["timestamp"]` and reject the request if it falls outside an acceptable freshness window (e.g., reject if `Time.now.to_i - timestamp.to_i` exceeds a configurable threshold, such as a few minutes). This should be enforced before or alongside the signature comparison in `lib/shopify_app/controller_concerns/app_proxy_verification.rb`.

### Proof of Concept
```ruby
test "old but validly-signed query string is still accepted (no freshness check)" do
  with_test_routes do
    # Same as the "valid signature" test, but timestamp is from 2016 (captured long ago)
    valid_params = {
      shop: "some-random-store.myshopify.com",
      path_prefix: "/apps/my-app",
      timestamp: "1466106083", # far in the past
      signature: "f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd",
    }
    get :basic, params: valid_params
    # Expected if freshness were enforced: :forbidden
    # Actual behavior: :ok  -> demonstrates unlimited replay window
    assert_response :ok
  end
end
```
This reuses the exact fixture from the existing `"request with a valid signature should pass"` test [4](#0-3) , which already demonstrates a decade-old `timestamp` being accepted as valid — confirming no freshness enforcement exists.

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
