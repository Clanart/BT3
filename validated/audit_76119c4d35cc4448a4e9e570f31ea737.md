### Title
Missing recipient/beneficiary zero-address and format validation in IntentGatewayV2 escrow release - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`burnAndBridge` lost the audit for skipping two checks before moving funds: (1) whitelisting the destination chain id, (2) validating the recipient address is non-zero/well-formed. Hyperbridge's `IntentGatewayV2` intents stack repeats the second half of that pattern: every code path that releases escrowed tokens truncates a user-supplied `bytes32 beneficiary` field straight into an `address` with no zero-address or high-bits check, and the value is never bound to a signer or fixed at order-acceptance time in a way that prevents a wrong or empty value from being used to release funds.

### Finding Description
`_withdraw` — the single function that actually moves escrowed input tokens and fee-token balances out of the contract — takes the beneficiary directly from the (attacker/solver-controlled at fill time, network-message-controlled at settlement time) `WithdrawalRequest.beneficiary` field: [1](#0-0) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
```

There is no `if (beneficiary == address(0)) revert(...)` guard, and no check that the upper 96 bits of the `bytes32` are zero (i.e., that the value really encodes a 20-byte EVM address rather than e.g. a 32-byte Substrate account id that got passed through unmodified on a Substrate↔EVM route). Any code path that can populate `WithdrawalRequest.beneficiary` with `bytes32(0)` or a mis-encoded value causes ERC20 `safeTransfer`/native `.call{value:}` to burn the escrowed funds to `address(0)` or a garbage address, with no revert and no recovery path — the same "funds sent to invalid/incorrect address" outcome flagged in the report.

The same truncation-without-validation pattern is repeated at every fill site that computes a beneficiary from order data before paying out: [2](#0-1) [3](#0-2) 

For comparison, the destination-chain half of the original bug class (whitelisting) *is* handled elsewhere in this contract via `_instance()`, which reverts with `UnknownInstance` if a state machine has no registered gateway: [4](#0-3) 

That shows the team is aware of the "validate before moving funds" principle for chain ids, but the analogous guard for the beneficiary/recipient address was never added to `_withdraw`.

### Impact Explanation
If a `WithdrawalRequest.beneficiary` of `bytes32(0)` (or a non-EVM-shaped value) ever reaches `_withdraw` — whether via a crafted cross-chain `RedeemEscrow`/`RefundEscrow` message body decoded in `onAccept`, or via an order whose `output.beneficiary` was left as `bytes32(0)` and then propagated through `_cancelFromDest`/`_cancelFromSource` (`beneficiary: order.user`) — the escrowed input tokens and any accumulated fee-token balance are transferred to `address(0)` or an unintended address and permanently lost, matching the "loss of funds" bounty category.

### Likelihood Explanation
`onAccept` does authenticate that the `PostRequest` came from the registered peer gateway instance (`_authenticate`), but it does not re-validate the *contents* of the decoded `WithdrawalRequest` — specifically it never checks `body.beneficiary != bytes32(0)` before calling `_withdraw`. Since `beneficiary` values are round-tripped through `abi.decode` from cross-chain calldata and from user-supplied `order.user`/`order.output.beneficiary` fields at order-placement time, a zero or malformed value can be introduced either by a buggy caller/integration or by a user who mis-populates their own order — the same "self-inflicted but catastrophic" trigger condition that made the original `burnAndBridge` finding valid.

### Recommendation
Add an explicit guard in `_withdraw` (and ideally in `placeOrder`/`fillOrder` validation of `order.output.beneficiary`/`order.user`) rejecting `bytes32(0)` beneficiaries and, where the target chain is known to be EVM, rejecting values whose upper 96 bits are non-zero, before any token transfer is attempted.

### Proof of Concept
Not independently verified in this pass — I was unable to fetch `placeOrder`/`fillOrder` in `evm/src/apps/IntentGatewayV2.sol` before the tool budget ran out, so I cannot confirm with certainty whether `order.output.beneficiary == bytes32(0)` is rejected upstream at order-placement time. The vulnerable sink (`_withdraw` in `IntentsBase.sol:390-392`) and the un-guarded beneficiary truncation in both fill paths are confirmed directly from source, but full confirmation of an end-to-end unprivileged exploit path (rather than a self-inflicted misconfiguration) would require reading `IntentGatewayV2.sol`'s `placeOrder`/`fillOrder` entrypoints, which is the remaining unverified piece.
