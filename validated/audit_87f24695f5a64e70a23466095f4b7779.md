## Analysis

The reassembly logic in `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) splices AI-generated per-hunk resolutions into the file **by positional order of `<<<<<<<` markers found on disk at write time**, not by any identity/content check against the hunks that were actually sent to and analyzed by the model. The model's context is captured once in `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:376-461`), an asynchronous, potentially long-running network round trip elapses, and then `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7169-7269`) writes `resolution.resolvedContent` straight to disk as long as git status still shows the file "conflicted" — it never re-verifies that the on-disk conflict hunks are the same ones the model reasoned about. This is structurally the same invariant break as the Halborn finding: a value is validated/computed once (slippage bounds / conflict hunk content) but the action that depends on it (order match / file write) is executed later against unexamined *current* state, with only a coarse status flag (in range vs not / still-conflicted vs not) standing in as the guard.

I was not able to fully trace whether `git status` (and thus `hasUnresolvedConflicts`) is re-read between hunk analysis and write within the same operation, or whether a user-triggered `fetch`/`pull` from an attacker-controlled remote during the LLM round trip could alter `--ours`/`--theirs` blobs while conflict markers persist unchanged in the working tree (making the check pass while `rawContent` is now stale relative to the repo's actual merge state). This would need to be verified in a live/dynamic session (e.g., instrumenting `_applyCopilotConflictResolutions` and racing a `git fetch` during the Copilot round trip) since the index has no way to confirm actual timing behavior or whether the merge state (`MERGE_HEAD`) is re-validated elsewhere in the flow I couldn't inspect (truncated file, `app-store.ts` copilot flow spans thousands of lines and dispatcher glue not fully read).

### Title
Stale Copilot conflict resolutions written to disk without re-validating current merge/hunk state - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` writes AI-computed resolution content for a conflicted file whenever git status still reports it as "conflicted," without verifying that the hunks the model resolved are still the actual current conflict content on disk.

### Finding Description
`buildConflictContext` reads the conflicted file content and conflict-marker hunks at the start of the flow [1](#0-0) . This snapshot (`rawContent`/`hunks`) is sent to a remote Copilot session, and only after that asynchronous round trip completes does the app splice the model's `resolvedContent` back into the file positionally by marker order via `reassembleResolvedFile` [2](#0-1) . When the user accepts, `_applyCopilotConflictResolutions` resolves the path with `resolveWithin` (a legitimate path-traversal guard) but the only staleness check performed is whether `onDiskFile` is still `isConflictedFileStatus` and has `hasUnresolvedConflicts` — a coarse boolean, not a comparison against the exact hunk content that was analyzed [3](#0-2) . If the working tree's conflicted content changes between the read and the write (e.g., a `fetch`/`pull` updates the merge base while the file remains marked conflicted, or a background process alters `--theirs`/`--ours` blobs from an attacker-influenced remote), the previously computed model resolution is still written and staged unconditionally, exactly like the report's pattern where slippage bounds are checked at order-creation time but never re-verified at match/execution time.

### Impact Explanation
If exploitable, this allows silent corruption of the content the user commits: the code actually staged and later pushed could differ from both the current base and incoming branch state without the user being warned, meeting the report's "silent corruption of what the user commits or pushes" criterion, since the write path in `app-store.ts:7258` unconditionally persists the stale resolution.

### Likelihood Explanation
This requires a specific timing window (the Copilot round trip) plus an attacker-controlled remote/fork whose commits are being merged and whose content changes mid-flight, and I could not confirm from static inspection alone whether `MERGE_HEAD`/hunk content is independently re-validated elsewhere before commit. This uncertainty should be resolved with dynamic testing rather than asserted as confirmed.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the file and recompute/compare its current conflict hunks (or a content hash captured alongside `rawContent` in `IFileConflictContext`) against what was sent to the model; if they differ, discard the stale resolution and route the file back to manual conflict resolution instead of writing it.

### Proof of Concept
Not verifiable from static code alone — this needs a live Desktop session: start a merge/rebase on a repo with a remote controlled by the tester, trigger Copilot conflict resolution, then during the model round trip perform a `fetch`/update that alters the underlying conflicted blob while conflict markers remain present, and observe whether `_applyCopilotConflictResolutions` still writes the stale resolution instead of detecting the mismatch.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
