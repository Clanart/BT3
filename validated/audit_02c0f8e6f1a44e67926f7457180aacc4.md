### Title
`updateEndRemainingAllocation()` has no one-shot guard, allowing the bonus denominator to be re-snapshotted after claims begin - (rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, carries no access control and no "already set" guard beyond a fresh read of the mutable `totalRemainingAllocation`. Since `totalRemainingAllocation` is decremented on every `claim()`, anyone can re-invoke this function after some users have already claimed to shrink the bonus denominator, letting a later claimer (in particular the attacker, if they hold the largest remaining allocation) capture a share of `totalBonus` that is inconsistent with the shares already paid to earlier claimers, causing the pool invariant `sum(allocations paid) == totalBonus` (and ultimately `aidropToken.balanceOf(this)` solvency) to break.

### Finding Description
`getBonusAmount()` computes each user's share of the forfeited-token pool `totalBonus` as: [1](#0-0) 

The denominator `totalEndRemainingAllocation` is meant to be a fixed snapshot, taken exactly once, of the total allocation still outstanding when period 4 ends, so that `sum_over_all_remaining_claimers(bonusAmount) == totalBonus` exactly. However, the snapshot function has no guard against being called more than once: [2](#0-1) 

`claim()` only auto-triggers this snapshot the very first time (`if (totalEndRemainingAllocation == 0)`), but does nothing to prevent it from being called again directly and unconditionally afterward: [3](#0-2) 

Because `totalRemainingAllocation` is reduced by `userAllocation` on every `claim()` call, calling `updateEndRemainingAllocation()` again after some users have already claimed re-snapshots the denominator to a smaller value (the allocation that's left, excluding those who already claimed). Any account that then claims uses this smaller denominator, inflating its own `bonusAmount` relative to the fixed `totalBonus` pool that early claimers already drew against using the original, larger denominator. `totalBonus` itself is never decremented as it is paid out, so the sum of bonuses actually paid out across the full life of the contract can exceed the single fixed `totalBonus` value, meaning the contract disburses more airdrop-token bonus than was ever forfeited into the pool.

An attacker holding the largest remaining allocation can wait for other users to claim (shrinking `totalRemainingAllocation`), call `updateEndRemainingAllocation()` themselves right before claiming, and thereby claim a bonus computed against an artificially small denominator — extracting a disproportionate share of `totalBonus` at the expense of tokens that are needed to pay the remaining (not-yet-claimed) allocation holders in full, or causing `claim()` to revert for later users via `InsufficientBalance` once the contract's real token balance is exhausted.

### Impact Explanation
This breaks the core accounting invariant that the bonus denominator is fixed once for all participants sharing `totalBonus`. The result is either (a) direct theft of funds by the attacker who extracts more bonus than their pro-rata entitlement, depleting tokens owed to other allocation holders, or (b) permanent freezing of other users' unclaimed principal/bonus allocation once the contract's `aidropToken` balance is insufficient to cover legitimate downstream `claim()` calls (which revert with `InsufficientBalance` and have no retry path other than the 9-month-later `withdrawDust()` sweep to the owner). This matches "Critical – Direct theft of user funds" (and/or theft/permanent freezing of unclaimed yield).

### Likelihood Explanation
No privileged role is required — `updateEndRemainingAllocation()` is `public` and callable by anyone at any time once `block.timestamp >= periodsEndTime[4]`. The attacker needs no capital beyond their existing allocation entry and simply needs to time one extra transaction (a plain call to `updateEndRemainingAllocation()`) relative to when other users call `claim()`. This is fully repeatable by any observer of the mempool/period-4 window, and worsens with more claim activity between re-snapshots.

### Recommendation
Add a one-shot guard so the snapshot can only ever be taken once, e.g. track a boolean or check strictly against an unset sentinel that cannot be re-triggered, and make the function internal/only auto-invoked from `claim()`:
```solidity
bool public endRemainingAllocationSet;

function updateEndRemainingAllocation() public {
    if (!endRemainingAllocationSet && block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
        endRemainingAllocationSet = true;
    }
}
```
Additionally, `totalBonus` should be decremented as it is paid out (or the pro-rata math redesigned) so the invariant `sum(bonusAmount paid) == totalBonus initially snapshotted` holds under all call orderings.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, fund the contract with `aidropToken` equal to `sum(allocations)`.
2. `register()` 3 users: Alice, Bob, Attacker, with allocations e.g. 100e18, 100e18, 500e18.
3. Warp to before `periodsEndTime[4]`; have Alice call `claim()` early (partial claim) so some allocation is forfeited into `totalBonus` (`totalBonus > 0`).
4. Warp to `>= periodsEndTime[4]`.
5. Run A (baseline, single snapshot): Bob calls `claim()` first (this triggers the one-time internal `updateEndRemainingAllocation()` since `totalEndRemainingAllocation == 0`), then Attacker calls `claim()` using the same denominator. Record final `aidropToken.balanceOf(address(this))` and sum of bonuses paid.
6. Run B (split/attacker-manipulated): Bob calls `claim()` (triggers first snapshot). Then Attacker directly calls `updateEndRemainingAllocation()` again (re-snapshotting `totalEndRemainingAllocation = totalRemainingAllocation`, now smaller since Bob already claimed). Attacker then calls `claim()`.
7. Assert: in Run B, Attacker's `bonusAmount` is strictly greater than in Run A for the identical `totalBonus` and `attackerAllocation`, and that `sum(bonusAmount paid across all claimers)` in Run B exceeds the original `totalBonus`, demonstrating the divergence between total allocations paid and `aidropToken.balanceOf(address(this))`/`totalBonus` invariant.

        }

        if(claimableAmount == 0) revert NothingToClaim();

        allocations[msg.sender] = 0;

            totalBonus += forfeited;
        }
