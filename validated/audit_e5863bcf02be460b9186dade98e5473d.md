## Title
Discard Changes builds trash/delete paths from git status without the traversal/symlink guard used elsewhere in the codebase - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The report's underlying pattern is: a security check (lock-period validation) was added to some entry points that perform a sensitive operation but omitted from other, structurally identical entry points that perform the same operation, letting an attacker reach the unguarded path. The codebase has an established, explicit analog to this pattern: `resolveWithin()` in `app/src/lib/path.ts` is used specifically to "Guard against path traversal and symlink escapes (cross-platform)" before touching the filesystem with an attacker-influenced repository-relative path. [1](#0-0) [2](#0-1) 

However, `GitStore.discardChanges()` — which also turns a repository-relative `file.path` (sourced from `git status`/working-directory parsing) into an absolute filesystem path for a destructive operation — does **not** go through `resolveWithin`. It uses raw `Path.resolve`/`Path.join`: [3](#0-2) 

### Finding Description
`resolveWithin` was introduced (and is unit-tested) specifically to stop two classes of escape when turning a repository-relative path into a real filesystem path: (1) `..`-style traversal segments and (2) symlink-based escapes, by comparing `realpath()` of the resolved target against `realpath()` of the repo root. [2](#0-1) 
It is deliberately applied in `buildConflictContext` before reading AI-conflict-resolution file content, with an explicit comment calling out the threat model it defends against. [1](#0-0) 

`GitStore.discardChanges()` performs an analogous but more dangerous operation — deleting or trashing a filesystem entry — using the *same kind* of input (`file.path`, a path derived from working-directory status of a cloned/fetched repository) but with none of that hardening:
```ts
await this.shell.moveItemToTrash(
  Path.resolve(this.repository.path, file.path)
)
...
await rm(Path.join(this.repository.path, file.path))
``` [3](#0-2) 
`Path.resolve`/`Path.join` will happily collapse `..` segments and does not check whether the resolved path is still inside the repository, nor whether any path component is a symlink pointing outside the repository (the exact class of check `resolveWithin` exists to perform). Unlike the ERC777 case where every state-changing entry point needed the same override, here every code path that turns git-status/diff-provided repository-relative paths into real filesystem paths for destructive operations needs the same containment guard, and this one is missing it.

### Impact Explanation
If an attacker-controlled cloned/fetched repository can cause a working-directory entry to resolve (via a tracked symlink component or similar) outside the repository root, `discardChanges()`'s unmoved-to-trash fallback (`rm(Path.join(...))`) or `moveItemToTrash` call could act on a path outside the intended repository, resulting in deletion of an arbitrary file/directory reachable through that symlink when the user performs the ordinary "Discard changes" action. This matches the class of "silent corruption of what the user commits/discards, or file write/delete outside the repo" called out as valid impact.

### Likelihood Explanation
This requires the attacker's repository to check out a symlinked path component under the working directory that git (and Desktop) is willing to surface as a working-directory change, and for the user to invoke "Discard Changes" (a completely ordinary, expected user action requiring no unnatural steps). I was not able to fully verify, within the available indexed code, whether Desktop's own working-tree checkout/symlink handling (as opposed to git's) could produce such an entry that survives into `WorkingDirectoryFileChange.path`, since `git`'s own checkout logic and `status-parser.ts`'s exact normalization were not fully inspectable from the index. This is the main uncertainty in confirming exploitability end-to-end.

### Recommendation
Route the path construction in `GitStore.discardChanges()` (both the `shell.moveItemToTrash` call and the `rm` fallback) through `resolveWithin(this.repository.path, file.path)` (and reject/skip the operation if it returns `null`), mirroring the guard already applied in `buildConflictContext`, so every destructive filesystem operation driven by repository-relative, potentially attacker-influenced paths is consistently protected.

### Proof of Concept
Conceptual (not fully verified against git's own tree/symlink validation, hence flagged as uncertain above):
1. Attacker crafts a repository containing a tracked symlink entry, e.g. `link -> ../../../../some/sensitive/target`, committed and pushed/shared.
2. Victim clones/fetches the repository in GitHub Desktop; the symlink is checked out into the working directory as `repoRoot/link`.
3. A subsequent modification (attacker- or victim-caused) makes `link` (or a path traversing through it) appear as an Untracked/Modified entry in the Changes list.
4. Victim selects "Discard Changes" on that entry. `discardChanges()` computes `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` and calls `moveItemToTrash`/`rm` on it without verifying the resolved real path stays under the repository root — unlike the equivalent guard in `buildConflictContext`. [3](#0-2)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
