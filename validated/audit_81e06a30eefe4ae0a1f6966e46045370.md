### Title
Partial-commit line selection is re-applied to a freshly re-fetched diff without revalidation, allowing silent corruption of what the user commits - (File: app/src/lib/git/apply.ts)

### Summary
This is the closest Desktop analog to the "missing checkpoint before allowing a new state-mutating action" bug class: an action (`stake`) is executed against a value (`availableRewards`) that was computed from stale state instead of being refreshed immediately beforehand. In Desktop, the analogous broken invariant is that `applyPatchToIndex` re-fetches the working-directory diff for a file at staging time, but then applies the user's *previously computed* line-selection (`DiffSelection`, based on absolute line indices into the diff the UI showed the user) to that fresh diff, with no revalidation that the line indices still refer to the same content the user reviewed.

### Finding Description
When a user reviews a partial diff and selects specific lines/hunks to include in a commit, the selection (`DiffSelection`) is stored as a set of "diverging" absolute line indices relative to the diff object that was last loaded into the UI state (see `updateChangesWorkingDirectoryDiff`, `app/src/lib/stores/app-store.ts:3404-3497`). [1](#0-0) 

When the user clicks "Commit", `_commitIncludedChanges` takes the files (and their selections) straight from `state.changesState.workingDirectory.files` — a snapshot that can be arbitrarily older than the moment the commit actually executes — and passes them into `createCommit`/`stageFiles`. [2](#0-1) 

For partially-selected files, staging goes through `applyPatchToIndex`, which does **not** reuse the diff the user reviewed. Instead it calls `getWorkingDirectoryDiff(repository, file)` again, right before formatting the patch: [3](#0-2) 

The freshly-fetched diff is then fed into `formatPatch`, which walks the new diff's hunks and decides whether to include each line purely based on `file.selection.isSelected(absoluteIndex)` — i.e., the old, already-stale index positions: [4](#0-3) 

There is no check comparing the new diff to the diff the selection was computed against (no hash/oid comparison, no re-validation that the hunks/line count are unchanged). Contrast this with `updateChangesWorkingDirectoryDiff`, which *does* perform a staleness check before updating UI-only state (`changesState.selection.selectedFileIDs` comparison, `app/src/lib/stores/app-store.ts:3456-3470`) — but that guard only protects what is *displayed*, not what is *staged/committed*. The staging path (`_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex`) has no equivalent guard.

This is directly analogous to the reported Olas issue: an operation (`stake` / "commit selected lines") consults and mutates protocol/repo state (`availableRewards` / index & commit) using a value (available rewards / diff+selection) that should have been recomputed ("checkpoint" / re-diffed-and-revalidated) immediately before use, but instead an older cached value is combined with fresh state, producing a result inconsistent with what the actor actually intended.

### Impact Explanation
If the working-directory file content changes between the time the diff was loaded into the UI (and the user made a partial line selection) and the time `_commitIncludedChanges` actually executes `applyPatchToIndex`, the absolute line indices in `DiffSelection` no longer correspond to the same textual content in the newly-fetched diff. Because `formatPatch` blindly reapplies the old indices to the new hunk lines, the resulting patch can:
- Include lines the user never reviewed or intended to commit (e.g., attacker/tool-injected content added to the file concurrently with the commit action), or
- Silently drop/alter lines the user explicitly selected, producing an incomplete or different commit than what the user believed they authored.

This falls under "silent corruption of what the user commits or pushes" from the valid impact list, since the user's confirmed selection is applied against different underlying content without any warning, confirmation, or re-diff/re-render.

### Likelihood Explanation
The window is small under normal single-user conditions, but it is realistically triggerable: any process that touches the working tree between diff-load and commit-click can widen or exploit this window — e.g., an IDE/editor autosave, a file-watcher/build tool, a pre-existing background `git` operation, or (most relevant to the "attacker controls a cloned/fetched repo" threat model) a Git hook or tool invoked as part of Desktop's own workflow that runs against attacker-supplied repository content (e.g., a smudge/clean filter, `post-checkout`/`post-merge` hook shipped in a malicious repo) that rewrites tracked files asynchronously while the Changes view is open. Since Desktop does not gate the partial-commit staging step behind a diff-identity check, likelihood is moderate rather than purely theoretical, and no special privileges beyond normal repository use are required.

### Recommendation
Before staging a partially-selected file in `applyPatchToIndex` (`app/src/lib/git/apply.ts`), verify that the diff fetched for staging matches the diff the user's `DiffSelection` was computed against (e.g., by comparing hunk headers/line counts or an oid/hash of the diff), and abort/refresh-and-reprompt the commit if it has changed, rather than silently applying stale line indices to new content.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, producing a diff with hunks A and B.
2. In the Changes view, select only specific lines from hunk B to include in the commit (the UI computes `DiffSelection` against this diff, per `updateChangesWorkingDirectoryDiff`, `app/src/lib/stores/app-store.ts:3404-3497`).
3. Before clicking "Commit", have another process (e.g., a background tool, editor autosave, or a git hook shipped in the repo) modify `file.txt` such that the line count/content of hunk B shifts (e.g., inserts a line above the previously selected lines) but the file remains "modified" so the working directory file is still selectable.
4. Click "Commit". `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3693`) passes the stale `WorkingDirectoryFileChange` (with its old `DiffSelection`) to `createCommit` → `stageFiles` → `applyPatchToIndex`, which re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the old line-index selection to it via `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`).
5. Inspect the resulting commit: it contains different lines than what the user visually selected in step 2, with no warning shown to the user that the underlying diff had changed since selection. [3](#0-2) [4](#0-3) [2](#0-1)
