### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight calculation, producing transactions that underpay the requested feerate — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends the `data` (OP_RETURN) output to `tx_outs` before computing the transaction weight, but `calculate_weight_vbytes` is only ever called with `payments` — never including the data output. Every fee and weight figure the caller sees (`needed_fee`, the `TooLowFee` check, `MAX_STANDARD_TX_WEIGHT` check, and the change-output decision) is computed on a smaller transaction than the one actually produced.

### Finding Description
In `SignableTransaction::new`:

- The OP_RETURN output is pushed to `tx_outs` at `send.rs:194-202`.
- The weight/vbytes used for `needed_fee` are then computed from `payments` only at `send.rs:204`: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and again for the change case at `send.rs:225-226`.
- `calculate_weight_vbytes` (`send.rs:62-127`) rebuilds a transaction containing only `payments` plus optional `change` — it has no parameter for a data output, so the OP_RETURN output's size (roughly `9 + len(data)` bytes, up to ~90 bytes for the permitted 80-byte payload) is excluded from `weight` and `vbytes`.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` underestimates the fee required to achieve the requested `fee_per_vbyte` rate on the final transaction. The actual fee (`inputs - outputs`, see `fee()` at `send.rs:138-141`) equals this underestimated amount, so the broadcast transaction's true feerate is strictly below `fee_per_vbyte`.
- The `TooLowFee` check at `send.rs:211` compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction can pass the check while paying less than the minimum relay feerate for its actual size.
- The `weight > MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` similarly uses the underestimated weight.
- The change decision at `send.rs:228-233` uses `fee_with_change` derived from the underestimated vbytes, so change can be created with a feerate below what was requested.

### Impact Explanation
A caller that attaches data (e.g., the 80-byte Serai `InInstruction` payloads this API was designed for) receives a transaction that pays a lower feerate than requested. In the worst case — `fee_per_vbyte` at or near the 1 sat/vbyte minimum and a maximal data payload — the transaction's real feerate falls below `DEFAULT_MIN_RELAY_TX_FEE`, so Bitcoin nodes reject it from relay/mempool despite `new` succeeding and the `TooLowFee` guard passing. The funds are not burned, but the signed transaction is unusable and any `needed_fee`-based accounting is wrong — the wallet reports/allocates a fee that does not correspond to the transaction actually signed, analogous to fee value being untracked relative to what the contract claims.

### Likelihood Explanation
The `data` parameter is a public input to `SignableTransaction::new`; any caller supplying `Some(data)` triggers the underestimation deterministically on every transaction. Whether it causes relay rejection depends on the chosen `fee_per_vbyte` and payload size, but the fee misreporting occurs unconditionally whenever `data` is set.

### Recommendation
Include the data output in `calculate_weight_vbytes` (e.g., accept a `data_len: usize` or push an OP_RETURN `TxOut` into the template transaction before calling `tx.weight()`), and use the corrected vbytes for `needed_fee`, the `TooLowFee` check, the change calculation, and the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
```rust
// Conceptual PoC against networks/bitcoin/src/wallet/send.rs
// data of 80 bytes adds ~90 bytes (~360 WU, ~90 vbytes) not counted in the fee.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![received_output],                 // input worth payment + fee
  &[(payment_script, 10_000)],
  Some(change_script),
  Some(data),
  1,                                     // fee_per_vbyte = minimum relay rate
).unwrap();
// tx.transaction().vsize() > (tx.needed_fee() / 1)
// => real feerate < 1 sat/vbyte => fails DEFAULT_MIN_RELAY_TX_FEE despite
//    the TooLowFee check at send.rs:211 having passed.
```
