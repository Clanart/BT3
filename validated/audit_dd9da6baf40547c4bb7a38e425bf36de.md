### Title
LLM gating step in dedupe.md skips deduplication based on unauthenticated text pattern match instead of verified comment author - ([File: .claude/commands/dedupe.md])

### Finding Description
Step 1 of `.claude/commands/dedupe.md` instructs an agent to decide whether to proceed with deduping by checking, among other things, whether the issue "already has a duplicates comment that you made earlier" [1](#0-0) . The only tool available to the agent for inspecting issue state is `./scripts/gh.sh issue view <n> --comments`, which is restricted to plain read-only output and carries no structured/authenticated signal distinguishing "real bot comment" from "arbitrary text" [2](#0-1) [3](#0-2) . The actual bot-authored comment is generated by `scripts/comment-on-duplicates.sh`, which appends a fixed, publicly-known footer string `"🤖 Generated with [Claude Code](https://claude.ai/code)"` to the comment body before posting via `gh issue comment` [4](#0-3) . Because this footer text is static and publicly visible in the repo, any GitHub user who can comment on the target issue can post a comment reproducing that same body/footer text before the dedupe workflow runs. Since the gating decision in step 1 is made purely by an LLM interpreting the textual issue/comment content returned by `gh.sh` — with no instruction or mechanism to verify the comment's actual GitHub API author field (e.g., `login == github-actions[bot]` or similar bot identity) — the agent has no verified signal to distinguish a genuine automation-authored comment from an attacker-forged lookalike.

### Impact Explanation
An attacker who can comment on an issue (unprivileged, public repo interaction) can forge the bot's footer text to make the step-1 agent believe deduping already happened, causing the workflow to skip legitimate duplicate-comment posting ("if so, do not proceed") [1](#0-0) . This is an automation-state-confusion / denial bypass: it suppresses correct automation behavior (duplicate detection and closure workflow) without any privilege beyond posting an issue comment. It maps to a trust-boundary bypass in the Claude Code automation pipeline, where an LLM-driven side-effect gate is controlled by attacker-supplied issue content rather than an authenticated API field.

### Likelihood Explanation
Feasible and repeatable: the footer string is checked into the repo in plain text at `scripts/comment-on-duplicates.sh` line 90, so any attacker can read and reproduce it exactly [5](#0-4) . The only precondition is the ability to comment on (or edit) the target issue before the dedupe workflow executes, which is true for any GitHub user on a public issue tracker such as `anthropics/claude-code` (the hardcoded `REPO` in the script) [6](#0-5) . No existing check in `gh.sh` or `dedupe.md` verifies comment authorship against a bot identity.

### Recommendation
Do not rely on LLM text-pattern matching to detect prior bot comments. Instead:
1. Extend `gh.sh`'s `issue view --comments` support (or add a dedicated allowed flag) to emit structured JSON including `author.login` and `authorAssociation`, and instruct the step-1 agent (or better, enforce it in code, not prompt) to only treat a comment as "already deduped" if `author.login` equals the known automation account/bot identity.
2. Alternatively, track "already deduped" state out-of-band (e.g., via a label applied by the same workflow that posts the duplicate comment, applied atomically with the comment) rather than inferring it from freeform text content that is fully attacker-influenceable.
3. Explicitly document in `dedupe.md` that the gating check must be based on a verified author/bot field, not comment body text, to remove ambiguity that leaves this decision to LLM judgment over untrusted content.

### Proof of Concept
Integration test plan:
1. Create two test issues in a sandbox repo.
2. On issue A, run the real flow: post a duplicate comment via `scripts/comment-on-duplicates.sh --potential-duplicates <x>` so the comment is authored by the actual automation identity (e.g., `github-actions[bot]`).
3. On issue B, as an unprivileged test user, manually post a comment containing the exact same body text (including the `🤖 Generated with [Claude Code](https://claude.ai/code)` footer) but authored by a different (non-bot) account.
4. Run the step-1 gating logic (either the LLM agent instructions verbatim, or a mocked harness that only receives the same text `gh.sh issue view --comments` would emit today) against both issues.
5. Assert expected/actual behavior:
   - Expected (fixed): gate result differs — issue A is correctly skipped (has a verified bot comment), issue B is correctly NOT skipped (comment is attacker-authored, not from the verified bot identity).
   - Actual (current code): because `gh.sh` output and the `dedupe.md` instructions provide no verified author field/check, the gate decision for issue B may be identical to issue A (skip), demonstrating the forged-footer denial bypass.
