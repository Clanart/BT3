## Title
Attacker-controlled `WWW-Authenticate` header can force GitHub Desktop into an "Enterprise sign-in" OAuth flow scoped to an attacker's domain, leaking the app's OAuth client secret and enabling account-binding phishing - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
This is the same bug class as the paymaster report: a trust decision that should require strong verification is instead made from data supplied by the untrusted party itself, and that decision is consumed later by a step that assumes it was already validated. In GitHub Desktop, `getEndpointKind()` classifies a remote as a "GitHub" host based on a `WWW-Authenticate: ... realm="GitHub"` header that comes straight from the remote git server's HTTP response — data fully controlled by whoever operates the remote/proxy. That classification then routes the credential request into the Enterprise OAuth sign-in flow, using the attacker's own host as the OAuth `endpoint`, and the app's static `ClientSecret` is subsequently POSTed to that attacker-chosen host.

### Finding Description
`createCredentialHelperTrampolineHandler` handles the git credential `get` command and calls `getCredential()`, which in turn calls `getEndpointKind()`: [1](#0-0) 

The comment makes the design intent explicit: `WWW-Authenticate` headers (which git captures from the remote's HTTP 401 response and forwards to the credential helper as `wwwauth[...]` fields) are used as a "happy-path" to decide a host is GitHub **without making a verifying network request**. Any git server the user clones from, fetches from, or is redirected/proxied to can simply answer authentication challenges with `WWW-Authenticate: Basic realm="GitHub"` and be classified as `'enterprise'`.

That classification feeds directly into `getCredential()`: [2](#0-1) 

Since the attacker's host normally has no matching `Account.endpoint` in the store, this branch is taken and `ui.promptForGitHubSignIn(endpoint)` is invoked with `endpoint` equal to the attacker's own URL.

`promptForGitHubSignIn` treats any non-`github.com` hostname as an Enterprise host and immediately sets the sign-in store's endpoint to that attacker-controlled origin: [3](#0-2) 

If the user proceeds with "Continue with browser" (a normal, expected step of GHE sign-in, not an unnatural action), `authenticateWithBrowser()` opens the system browser to an OAuth authorize URL built from that same attacker-controlled endpoint: [4](#0-3) 

When the OAuth callback returns (the attacker fully controls this since they operate the "authorization server"), `resolveOAuthRequest()` calls `requestOAuthToken(endpoint, code)`: [5](#0-4) 

`requestOAuthToken` builds the token endpoint from the (attacker) `endpoint` and POSTs the app's static `ClientID`/`ClientSecret` to it: [6](#0-5) 

`getHTMLURL()` falls back to a raw parse of whatever hostname is in `endpoint` for non-dotcom/non-ghe.com hosts, with no allowlist or verification step: [7](#0-6) 

The invariant that is broken: the only real verification of "is this actually a GitHub host" is `isGitHubHost()`, which does an authenticated-free network probe (`/meta`, checks `x-github-request-id`): [8](#0-7) 

but that check is *skipped* whenever the remote supplies a spoofed `WWW-Authenticate` realm, exactly analogous to the paymaster case where `isPaymasterEnabled` was checked in the wrong phase and could be bypassed by data available earlier in the flow. Here, the “allowlist check” (`isGitHubHost`) is bypassed by trusting attacker-supplied header content earlier in `getEndpointKind()`.

### Impact Explanation
This satisfies the "credential/token exfiltration" and "unauthorized OAuth or account binding" categories:
- The app's OAuth `ClientSecret` (a shared static secret baked into the Desktop binary) is sent via HTTPS POST to a host chosen entirely by whoever controls the git remote/proxy the user is fetching from — not a host the user manually typed into the GHE sign-in field, but one silently derived from a credential negotiation during a routine `git fetch`/`clone`/`push`.
- The subsequent "successful" OAuth completion is entirely under the attacker's control (they run the fake authorize/token endpoints), so the resulting `Account` object (login, avatar, token) returned to Desktop is attacker-supplied, letting an attacker bind an arbitrary/malicious account into the user's Desktop account store, or use a convincing "Sign in to your organization's GitHub Enterprise" dialog for phishing.
- No local access, admin rights, or unnatural user steps are required beyond doing normal git operations against a repository/remote the attacker controls, and clicking the same "Continue with browser" button a legitimate GHE sign-in would present.

### Likelihood Explanation
The trigger requires only that a remote git server (or a MITM/corporate proxy sitting in front of one) return a crafted `WWW-Authenticate: ... realm="GitHub"` header during any git-over-HTTPS authentication challenge for a repo the user has added/cloned/fetched from — something entirely within an attacker's control when they operate the remote. The comment in `getEndpointKind()` confirms this shortcut is intentional and unauthenticated by design ("without having to resort to making a request ourselves"), so this isn't a narrow edge case but the documented normal code path for any host that isn't already `github.com`/`*.ghe.com` or a previously known account endpoint.

### Recommendation
Do not let the `wwwauth[...]` realm string alone decide that a host is trustworthy enough to initiate the Enterprise OAuth flow (which sends `ClientSecret`) or to skip `isGitHubHost()`'s verifying request. At minimum:
- Always perform the `isGitHubHost()` verification (or an equivalent host-based verification independent of attacker-suppliable headers) before classifying an endpoint as `'enterprise'`.
- Require explicit, out-of-band user confirmation (the same as manual "Sign in to GitHub Enterprise" URL entry) before opening a browser-based OAuth flow whose `endpoint` was derived automatically from a git credential negotiation with an unfamiliar host.

### Proof of Concept
1. Attacker hosts a generic git server (or MITM proxy) at `https://evil.example.com/some/repo.git` and gets the victim to add/clone/fetch it in GitHub Desktop (e.g., as a normal repository or submodule remote).
2. When Desktop/git attempts HTTPS authentication, the attacker's server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. Git forwards this as `wwwauth[0]=Basic realm="GitHub"` to Desktop's credential helper; `getEndpointKind()` returns `'enterprise'` for `https://evil.example.com` without any real verification.
4. `getCredential()` finds no matching account for that endpoint and calls `promptForGitHubSignIn('https://evil.example.com/...')`, which shows a "Sign in" dialog and sets the sign-in endpoint to `https://evil.example.com`.
5. Victim clicks "Continue with browser"; Desktop opens `https://evil.example.com/login/oauth/authorize?client_id=<real_client_id>&...` in the system browser, which the attacker fully controls.
6. Attacker's fake authorize page redirects back to Desktop's OAuth callback with an attacker-chosen `code`; `resolveOAuthRequest` calls `requestOAuthToken('https://evil.example.com', code)`, which POSTs `client_id` **and `client_secret`** to `https://evil.example.com/login/oauth/access_token`, exfiltrating the app's OAuth secret and allowing the attacker to return any account/token they wish, which Desktop then treats as an authenticated `Account`.

export function getHTMLURL(endpoint: string): string {
  if (envHTMLURL !== undefined) {
    return envHTMLURL
  }

  // In the case of GitHub.com, the HTML site lives on the parent domain.
  //  E.g., https://api.github.com -> https://github.com
  //
  // Whereas with Enterprise, it lives on the same domain but without the
  // API path:
  //  E.g., https://github.mycompany.com/api/v3 -> https://github.mycompany.com
  //
  // We need to normalize them.
  if (endpoint === getDotComAPIEndpoint() && !envEndpoint) {
    return 'https://github.com'
  } else {
    if (isGHE(endpoint)) {
      const url = new window.URL(endpoint)

      url.pathname = '/'

      if (url.hostname.startsWith('api.')) {
        url.hostname = url.hostname.replace(/^api\./, '')
      }

      return url.toString()
    }

    const parsed = URL.parse(endpoint)
    return `${parsed.protocol}//${parsed.hostname}`
  }
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}

/**
 * Attempts to determine whether or not the url belongs to a GitHub host.
 *
 * This is a best-effort attempt and may return `undefined` if encountering
 * an error making the discovery request
 */
export async function isGitHubHost(url: string) {
  const { hostname } = new window.URL(url)

  const endpoint =
    hostname === 'github.com' || hostname === 'api.github.com'
      ? getDotComAPIEndpoint()
      : getEnterpriseAPIURL(url)

  if (isDotCom(endpoint) || isGHE(endpoint)) {
    return true
  }

  if (isKnownThirdPartyHost(hostname)) {
    return false
  }

  // github.example.com,
  if (/(^|\.)(github)\./.test(hostname)) {
    return true
  }

  // bitbucket.example.com, etc
  if (/(^|\.)(bitbucket|gitlab)\./.test(hostname)) {
    return false
  }

  if (getEndpointVersion(endpoint) !== null) {
    return true
  }

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}
