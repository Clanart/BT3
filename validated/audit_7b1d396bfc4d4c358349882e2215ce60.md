### Title
Out-of-bounds access (panic) in PedPoP blame evaluation via unvalidated Participant indexes - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
The `blame`/`blame_internal` path in PedPoP indexes `HashMap`s with attacker-chosen `Participant` values (`sender`/`recipient`) without checking they belong to the DKG set (`1..=n`). `Participant::new` accepts any nonzero `u16`, so an index like `n+1` or `65535` reaches `self.enc_keys[&decryptor]` (encryption.rs) or `self.commitments[&sender]` (lib.rs), both of which use the panic-on-missing `map[&key]` indexing syntax. This is a direct analog of the Exiv2 OOB read (CWE-125): untrusted length/index data drives an unchecked access, causing a crash — availability impact only, matching the advisory's A:H severity profile.

### Finding Description
In `crypto/dkg/src/lib.rs`, `Participant::new` validates only that the index is nonzero; there is no upper bound [1](#0-0) . In `BlameMachine::blame` / `AdditionalBlameMachine::blame`, the caller supplies `sender` and `recipient` as arbitrary `Participant`s [2](#0-1) . `blame_internal` then calls `decrypt_with_proof`, which evaluates `self.enc_keys[&decryptor]` — a `HashMap` indexing expression that panics when the key is absent [3](#0-2) . If a valid PoP signature is supplied (the attacker can produce one, since `EncryptedMessage`/`SchnorrSignature` are attacker-controlled inputs), execution proceeds to `self.commitments[&sender]`, which likewise panics on a `sender` that was never a registered DKG participant [4](#0-3) .

The required attacker input is minimal: `EncryptedMessage::read` consumes attacker bytes (`C::read_G`, `SchnorrSignature::read`, `E::read`) with no semantic validation [5](#0-4) , and the `sender`/`recipient` arguments are plain deserialized `u16`s in downstream callers (e.g., `InvalidDkgShare` transactions deserialize `accuser`/`faulty` via `Participant::new` alone) [6](#0-5) .

### Impact Explanation
Any node/validator evaluating a blame accusation with `sender` or `recipient` set to a `Participant` index not in `1..=n` panics (unwinding across the calling task / aborting the process depending on panic strategy). This is an unauthenticated, remotely-triggerable denial of service reachable from public protocol messages, matching the CWE-125 class: untrusted index data produces an access outside the valid range of the committed key sets.

### Likelihood Explanation
An unprivileged participant (or anyone able to submit a blame/accusation message referencing arbitrary indexes) can trigger this with a single crafted input. They must either supply an `EncryptedMessage` with a valid PoP (trivially constructible, since PoP verification only proves knowledge of the ephemeral key) to reach the `commitments[&sender]` panic, or use a valid-proof path where `decryptor` is unregistered to hit the `enc_keys[&decryptor]` panic first. Note the PoP check happens before the `enc_keys` lookup, so reaching the second panic requires a valid signature — still fully attacker-producible.

### Recommendation
In `blame_internal` and `decrypt_with_proof`, replace `map[&key]` indexing with `map.get(&key)` and return a deterministic blame outcome (e.g., blame `recipient`/`accuser` for an out-of-set index) instead of panicking. Also validate `sender` and `recipient` against the DKG participant set (`u16::from(p) <= n`) at the top of `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `Decryption::decrypt_with_proof`.

### Proof of Concept
```rust
// After a DKG completes with params (t, n), producing a BlameMachine:
let attacker_sender = Participant::new(n + 1).unwrap(); // valid Participant, not in the set
// msg: any EncryptedMessage<SecretShare> whose `pop` verifies under its `key`
// (attacker can build one via `encrypt` with their own key)
let (_machine, _faulty) = blame_machine.blame(attacker_sender, recipient, msg, proof);
// -> panics inside blame_internal at `self.commitments[&sender]` (index not found)
```
Equivalently, calling `AdditionalBlameMachine::blame` with `recipient = Participant::new(n + 1)` and a valid `EncryptionKeyProof` panics at `self.enc_keys[&decryptor]` in `decrypt_with_proof`.

Caveat: I was unable to fully trace whether the coordinator's `InvalidDkgShare` handler passes `accuser`/`faulty` into `blame` without additional bounds checks; if it does not, reachability relies on the public pedpop `blame` API being called with deserialized participant indexes, which is the documented usage.
