### Title
Pointer precompile registers ERC20/ERC721/ERC1155 pointers for arbitrary CosmWasm contracts without validating the target implements the real interface, enabling spoofed pointer tokens - (File: `precompiles/pointer/pointer.go`)

### Summary
The `AddCW20Pointer`, `AddCW721Pointer`, and `AddCW1155Pointer` precompile methods let any caller register a permanent EVM "pointer" contract for an arbitrary sei-bech32 address they supply. The only validation performed is that a `QuerySmart`/`QuerySmartSafe` call against that address for `{"token_info":{}}` (or `{"contract_info":{}}`) succeeds and returns JSON containing `name`/`symbol` fields. There is no check that the target is a genuine, spec-compliant CW20/CW721/CW1155 contract, analogous to the Escher factories accepting an arbitrary `sale.edition` address without verifying it was deployed by the legitimate `Escher721Factory`.

### Finding Description
`AddCW20` in `precompiles/pointer/pointer.go` (and its legacy variants in `precompiles/pointer/legacy/v552`, `v555`, `v562`, `v66`, `v67`, `v610`, `v630`) takes a caller-supplied `cwAddr` string, converts it to an `sdk.AccAddress`, and issues a smart query for `token_info`/`contract_info`: [1](#0-0) 

The code then extracts `name`/`symbol` straight from the untrusted JSON response and uses them as constructor args when deploying the ERC20/ERC721/ERC1155 pointer contract via `evm.Create`: [2](#0-1) 

The only structural guard is the reverse-registry "no pointer-to-pointer" check in `x/evm/keeper/pointer.go`, and a check that no existing pointer already exists for that same address/version: [3](#0-2) 

There is no check that:
- the target contract actually implements the full CW20/CW721 message set (`transfer`, `transfer_from`, `balance`, `allowance`, etc.) correctly,
- the contract's `name`/`symbol` are not deliberately spoofed to impersonate a legitimate, well-known token,
- the address was deployed through any canonical/trusted factory or code ID.

Once registered, the pointer address is discoverable via `GetERC20CW20Pointer`/`GetERC721CW721Pointer` and the reverse registry, and the deployed `CW20ERC20Pointer.sol`/CW721 pointer wrapper simply forwards `transfer`/`transferFrom`/`approve` calls (and any attached `usei` value through the wasmd `execute` path) to the attacker-controlled wasm contract: [4](#0-3) 

Any EVM contract/dApp/user that trusts a registered pointer address (surfaced by `name()`/`symbol()`) as a canonical, standards-compliant bridge to a real CosmWasm token — the same trust model the Escher report describes for `sale.edition` — can be misled into sending real funds (`usei`/tokens) or performing swaps/approvals against a fake, attacker-controlled CW20/CW721/CW1155 contract that never delivers the promised balance/NFT.

### Impact Explanation
This does not directly break protocol-level invariants (existing pointers for legitimate tokens cannot be overwritten, and pointer-to-pointer chaining is blocked), but it allows a single unprivileged transaction sender to permanently register an on-chain, protocol-blessed "pointer" for a spoofed token/NFT contract that mimics the `name`/`symbol` of a legitimate asset. Since downstream integrators (wallets, DEX front-ends, other contracts) commonly treat "has a pointer" as a signal of a canonically-bridged CW20/CW721 asset, this enables fund-loss phishing: users transacting against the spoofed pointer, or an EVM contract that resolves counterpart addresses via `GetERC20CW20Pointer`/`GetERC721CW721Pointer` without further validation, can send funds that are captured by the attacker's wasm contract instead of the real token logic.

### Likelihood Explanation
Likelihood is moderate: any address (unprivileged tx sender) can deploy a minimal CosmWasm contract that answers `token_info`/`contract_info` queries with attacker-chosen `name`/`symbol`, then call `AddCW20Pointer`/`AddCW721Pointer`/`AddCW1155Pointer` directly with no special permissions, gas cost, or governance approval required (registration is only disableable in the CW→EVM `MsgRegisterPointer` direction, not in this EVM→CW direction).

### Recommendation
Before deploying a pointer contract, validate that the target CW20/CW721/CW1155 contract's code corresponds to a known/trusted code ID (or a whitelist of code IDs), and/or perform deeper interface validation (e.g., exercise a `balance`/`transfer`/`ownerOf` round trip, verify `cw2` contract-info matches the expected standard) rather than trusting a single `token_info`/`contract_info` query response. Additionally, surface the pointer's underlying `cwAddr`/code ID prominently wherever pointer metadata (`name`/`symbol`) is displayed so integrators cannot mistake a spoofed pointer for the canonical one.

### Proof of Concept
1. Attacker deploys a CosmWasm contract `Fake` whose `token_info` query handler returns `{"name":"USD Coin","symbol":"USDC","decimals":6,"total_supply":"1000000000000"}` while its `transfer`/`balance` handlers are fully attacker-controlled (e.g., always report success without moving funds, or divert attached `usei`).
2. Attacker calls `POINTER_CONTRACT.addCW20Pointer(Fake)` from `precompiles/pointer/pointer.go`; the precompile only checks the query succeeds and parses `name`/`symbol`, then deploys an ERC20 pointer wrapper via `evm.Create`.
3. The new pointer is registered in `GetERC20CW20Pointer`/reverse registry as if it were a legitimate bridged token named "USD Coin"/"USDC".
4. A victim (user, wallet, or dApp) resolves the pointer, sees the spoofed `name()`/`symbol()`, and calls `transfer`/sends `usei` value expecting real USDC-like behavior; funds are instead captured by the attacker's wasm contract logic.
