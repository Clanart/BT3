### Title
Quadratic-blowup DoS in OCC multi-version store iterator setup causes block-processing time explosion — ([File: sei-cosmos/store/multiversion/store.go])

### Summary
`Store.CollectIteratorItems` in the OCC (optimistic concurrency control) multi-version store is called every time any transaction in a block opens a KVStore `Iterator`/`ReverseIterator` while the store is under OCC execution. It performs a full `O(index)` scan over `txWritesetKeys` for *every prior transaction in the block* on *every single iterator open*. Since almost any Cosmos SDK message handler (bank sends, staking ops, wasm/EVM operations that touch prefix-iterated state such as denom metadata, validator power index, EVM storage tries via pointer registries, etc.) opens at least one KVStore iterator, an attacker who simply floods a block with many cheap, ordinary transactions can force this scan to run repeatedly, turning per-block execution cost from linear to quadratic in the number of transactions — with no bound tied to gas metering of the scan itself.

### Finding Description
Sei-chain executes transactions within a block using OCC (`ProcessTXsWithOCCGiga`/`ExecuteTxsConcurrently`), backed by a shared `multiversion.Store` [1](#0-0) . Each transaction's execution context is wrapped by a `VersionIndexedStore` keyed by its `transactionIndex` in the block [2](#0-1) .

Whenever code running inside a transaction opens a range `Iterator`/`ReverseIterator` on this store, `VersionIndexedStore.iterator()` calls `store.multiVersionStore.CollectIteratorItems(store.transactionIndex)` to build a merged view of all writes made by *earlier* transactions in the same block [3](#0-2) .

`CollectIteratorItems` implements this by looping over every index `0..transactionIndex-1` and loading that transaction's writeset keys from a `sync.Map`:

```go
func (s *Store) CollectIteratorItems(index int) *db.MemDB {
	sortedItems := db.NewMemDB()
	for i := 0; i < index; i++ {
		writesetAny, found := s.txWritesetKeys.Load(i)
		...
	}
	return sortedItems
}
``` [4](#0-3) 

This is `O(transactionIndex)` work per call, and it is invoked once per `Iterator()`/`ReverseIterator()` call made by *any* transaction, not once per block or once per transaction. Since a single transaction can (and commonly does) open multiple iterators (e.g. a bank send that must iterate account balances/denom metadata, a wasm/EVM call touching a contract's prefix store, staking/validator-index lookups, tokenfactory/pointer-registry lookups), and since this cost applies transaction-by-transaction as the block is filled, the aggregate cost of processing a block of `n` transactions each performing `m` iterator opens is `O(n² · m)` rather than `O(n · m)`.

Critically, this scan is **not gas-metered** the way EVM/CosmWasm execution is — it is Go-level book-keeping performed by the OCC scheduler infrastructure itself, outside the per-message gas meter that would normally cause a single expensive transaction to simply revert with "out of gas." Because the cost is amortized across many *cheap, individually valid* transactions (each of which pays only its own small gas fee), no single transaction can be rejected for excessive gas use, yet the cumulative CPU cost of `ProcessBlock`/`ExecuteTxsConcurrently` scales quadratically with block-fill. This is directly analogous to the reported Sherlock issue: an unprivileged user can cheaply grow an "active/pending" set (there: active protections in an array; here: per-tx writesets accumulated across the block) that is then fully rescanned on every subsequent operation, eventually making the aggregate operation (there: `lockCapital`; here: `ProcessBlock`) unable to complete within its available budget (there: block gas limit; here: the consensus round's 2.5s target).

### Impact Explanation
An attacker who submits a large number of ordinary, individually-cheap transactions that each perform at least one KVStore iteration (trivial to trigger — e.g. bank `MsgSend` iterating denom metadata/balances, or a wasm/EVM call to any pointer/precompile that iterates a prefix store) into the same block forces `CollectIteratorItems` to be re-run with an ever-growing `index` bound for each subsequent transaction in that block. The resulting quadratic CPU cost in block execution can push block processing time well beyond the network's target block time, causing validators to miss their round deadlines — i.e., a block-delay/liveness degradation beyond the accepted 2.5-second threshold, and in the worst case repeated across blocks, a sustained chain-wide slowdown. This matches the "block delay beyond 2.5 seconds" acceptance criterion for validity.

### Likelihood Explanation
Likelihood is high in terms of reachability (any account can submit ordinary transactions; no special privilege, precompile, or governance action is required, and the mechanism is triggered by completely mundane transaction types that legitimately need to iterate state), but the practical severity depends on block gas limits, the number of transactions a proposer will admit per block, and how many iterators typical transaction types actually open. Because the scan cost is decoupled from the gas fee paid per transaction (it's infrastructure bookkeeping, not gas-metered VM/query execution), an attacker paying normal fees for many small transactions can impose disproportionate CPU cost on block producers without a corresponding gas cost, which is the core of the DoS concern.

### Recommendation
Avoid a full `O(index)` rescan of `txWritesetKeys` on every iterator open. Options:
- Maintain an incrementally-updated sorted structure (e.g., a persistent/immutable sorted tree or a per-key version index) so `CollectIteratorItems` can be answered in `O(log n + k)` (k = number of matching keys) instead of `O(index)`.
- Cache the merged "prior-writes" view per transaction index and invalidate/update it incrementally as new writesets are added, rather than recomputing it from scratch on every call.
- Charge (or count) this iterator-setup cost against the requesting transaction's gas meter so that transactions which trigger expensive scans pay for the resource they consume, restoring the invariant that no unbounded/uncompensated work can be forced onto validators by unprivileged senders.

### Proof of Concept
Conceptual PoC (cannot be executed without deploying to a running sei-chain testnet):
1. Submit `N` ordinary `MsgSend` (or any message type whose handler performs at least one `Iterator`/`ReverseIterator` call, e.g., touching bank denom metadata, tokenfactory `CreatorPrefixStore`, or an EVM/wasm call reading a contract's prefix-iterated storage) transactions targeting the same block, each from independent (or the same) low-value accounts, so they all get included by the block proposer.
2. As the block is executed under OCC (`ProcessTXsWithOCCGiga`/`ExecuteTxsConcurrently`), each transaction's `VersionIndexedStore.iterator()` call triggers `CollectIteratorItems(transactionIndex)`, whose cost is proportional to `transactionIndex` [4](#0-3) .
3. Measure `EndBlock`/`ProcessBlock` duration (already instrumented via `endBlockDuration`/`moduleEndBlockDuration` metrics) as `N` grows; the observed processing time should grow super-linearly (quadratically) with `N`, demonstrating that block execution time can be pushed past the network's block-time budget purely by flooding a block with cheap, ordinary, iterator-triggering transactions.

// CollectIteratorItems implements MultiVersionStore. It will return a memDB containing all of the keys present in the multiversion store within the iteration range prior to (exclusive of) the index.
func (s *Store) CollectIteratorItems(index int) *db.MemDB {
	sortedItems := db.NewMemDB()

	// get all writeset keys prior to index
	for i := 0; i < index; i++ {
		writesetAny, found := s.txWritesetKeys.Load(i)
		if !found {
			continue
		}
		indexedWriteset := writesetAny.([]string)
		// TODO: do we want to exclude keys out of the range or just let the iterator handle it?
		for _, key := range indexedWriteset {
			// TODO: inefficient because (logn) for each key + rebalancing? maybe theres a better way to add to a tree to reduce rebalancing overhead
			_ = sortedItems.Set([]byte(key), []byte{})
		}
	}
	return sortedItems
}
