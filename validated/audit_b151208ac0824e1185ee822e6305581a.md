### Title
Stale Light Client Proof Permanently Locked Per Deposit Silences Reorg-Driven Block-Hash Mismatch, Permanently Disabling Operator Assert — (`core/src/database/operator.rs`, `core/src/citrea.rs`)

---

### Summary

`insert_lcp_for_assert` stores the RISC Zero `Receipt` (light client proof) for a deposit using `ON CONFLICT (deposit_id) DO NOTHING` with **no mismatch check**. Once any LCP is written for a `deposit_id`, it is permanently frozen. `fetch_validate_and_store_lcp` — the only caller — silently returns the cached receipt and ignores the `payout_block_height` argument on every subsequent call. After a Bitcoin reorg that moves the payout transaction into a different block, the operator's bridge-circuit proof will always panic on the L1-block-hash assertion, making it impossible to disprove a challenge and causing permanent loss of operator collateral.

---

### Finding Description

**Root cause — `insert_lcp_for_assert`** [1](#0-0) 

The SQL is `ON CONFLICT (deposit_id) DO NOTHING`. Unlike every other "if-not-exists" helper in the same file (`insert_operator_if_not_exists`, `insert_operator_kickoff_winternitz_public_keys_if_not_exist`, `insert_bitvm_setup_if_not_exists`, `insert_operator_challenge_ack_hashes_if_not_exist`), this function performs **no equality check** on the stored value after a conflict. The new receipt is silently discarded.

**Propagation — `fetch_validate_and_store_lcp`** [2](#0-1) 

The function accepts `payout_block_height: u64` but, on the early-return path (lines 337–340), returns the cached receipt **without comparing it to `payout_block_height`**. The height parameter is only used when no receipt exists yet.

**Consumption — `send_asserts`** [3](#0-2) 

The returned `lcp_receipt` is fed directly into the bridge-circuit host. The bridge circuit then enforces: [4](#0-3) 

If the cached LCP was generated for block `H` but the payout transaction now sits in block `H′` (after a reorg), `lc_l1_block_hash != spv_l1_block_hash` and the circuit panics. Proof generation fails; the operator cannot submit a valid disprove transaction.

---

### Impact Explanation

An operator whose first `send_asserts` call stores an LCP for block `H` is permanently bound to that receipt for the lifetime of the deposit. Any subsequent reorg that moves the payout transaction to block `H′` makes every future assert attempt fail at the bridge-circuit level. The operator cannot disprove the challenge, the challenge succeeds, and the operator's entire collateral UTXO is slashed. This is a direct, permanent loss of operator collateral — a bridge-controlled fund — with no recovery path short of manual DB surgery.

---

### Likelihood Explanation

Bitcoin reorgs of 1–2 blocks occur several times per year on mainnet and are routine on testnet/signet. The window is: (a) `send_asserts` is called and the LCP is written, (b) the assert transaction is not yet confirmed or fails to propagate, (c) a reorg reorganizes the payout block.
