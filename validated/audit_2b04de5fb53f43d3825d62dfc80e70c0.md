### Title
Unvalidated DataLayer mirror URLs cause SSRF-style outbound requests to attacker-chosen hosts during subscription sync - (File: chia/data_layer/download_data.py)

### Summary
The CVE describes an unauthenticated call that lets an attacker supply parameters causing the server to make an outbound request to an attacker-chosen destination (SSRF). Chia's DataLayer has an analogous pattern: any DL store owner can publish arbitrary mirror URL strings on-chain via a DL mirror coin, and any node that subscribes to that store (including automatic "owned store" pseudo-subscription and periodic sync) will have its DataLayer service issue outbound HTTP requests to those attacker-supplied URLs with no host/scheme validation.

### Finding Description
`DataLayer.add_mirror()` forwards a caller-supplied `urls: list[str]` straight into a wallet RPC call that publishes a DL mirror coin on-chain, with no validation of scheme or destination: [1](#0-0) 

Those URLs are later read back by any node tracking the singleton via `update_subscriptions_from_wallet()`, which pulls `mirror.urls` unmodified from wallet RPC and stores them as subscription server URLs: [2](#0-1) 

During the periodic sync loop, `fetch_and_validate()` iterates the stored server list and calls `insert_from_delta_file()` / `download_file()` with `server_info.url` taken directly from the on-chain mirror data: [3](#0-2) 

`http_download()` then performs a raw `aiohttp` GET against `server_info.url + "/" + filename` with no allow-list, scheme check, or private-network exclusion: [4](#0-3) 

Because the mirror-coin creation path (`add_mirror` → `dl_new_mirror`) only requires the caller to own/spend a coin to fund the mirror coin and does not restrict URL contents to `http(s)://`, a hostile store creator can register a mirror URL pointing at internal infrastructure (e.g. `http://169.254.169.254/...`, `http://127.0.0.1:<port>/...`, internal service hostnames), and every DataLayer node that later syncs/subscribes to that store's singleton — which happens automatically for owned stores and via `periodically_manage_data()` for subscribed ones — will issue an outbound HTTP GET to that destination.

### Impact Explanation
This lets an untrusted store owner (Data Layer client) turn any subscriber's DataLayer node into a proxy that makes outbound requests to arbitrary internal/local addresses on their behalf, similar in class to the iTop SSRF: no authentication or interaction beyond normal subscription/sync is required from the victim node, and the destination/port is fully attacker-controlled. It can be used to probe internal network topology, hit cloud metadata endpoints, or interact with local-only services listening on the victim's host, and the request path (delta-file GET, subsequently parsed) also expands attack surface into the delta-file parser/plugin JSON responses.

### Likelihood Explanation
Reaching this requires only creating a DataLayer store/mirror coin — a normal Data Layer client action available to any wallet user with DL support enabled — and having a victim node subscribe to (or already own/track) that store, which is the expected DataLayer usage pattern (subscription and mirror sync are core, automatic features). No special privilege beyond being a DL participant is needed, making this readily reachable in normal Data Layer client flows.

### Recommendation
Validate mirror/server URLs at the point of both publication (`add_mirror`) and consumption (`update_subscriptions_from_wallet` / `fetch_and_validate` / `http_download`): restrict schemes to `http`/`https`, resolve and reject private/loopback/link-local/metadata IP ranges before connecting (or route all mirror fetches through a proxy/sandbox that enforces this), and consider requiring an explicit user opt-in/allow-list for new mirror hosts rather than automatic sync.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror` with `urls=["http://169.254.169.254"]` (or `http://<victim-internal-host>:<port>`), funding the mirror coin so it is accepted on-chain. [1](#0-0) 
2. A victim runs a DataLayer node and subscribes to (or otherwise tracks) the attacker's store id, e.g. via `subscribe` RPC, or the store is auto-tracked as owned.
3. On the next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` pulls the malicious URL into the subscription's server list. [2](#0-1) 
4. `fetch_and_validate()` selects that server and `http_download()` issues an outbound GET directly to the attacker-chosen host/port with no validation. [4](#0-3)

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
