### Title
Cached FROST preprocess seed is reused across multiple `sign` calls under the same context, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's `SigningProtocol::preprocess_internal` persists a FROST `CachedPreprocess` (the ChaCha20 seed from which all signing nonces are deterministically derived) in the DB keyed only by `context` — `(b"DkgConfirmer", attempt)` — and never deletes or rotates it. Every invocation of `preprocess_internal` / `share_internal` for the same context reconstructs the *same* nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)`. Consequently, any two distinct `sign` executions under one context (e.g., `share()` followed by `complete()`, or repeated handling of the same DKG-confirmation attempt with different preprocess sets or different `key_pair`s) produce signature shares computed with reused nonces — the classic Schnorr/FROST nonce-reuse failure that allows third-party recovery of the signer's secret share. This mirrors the CVE-2022-45869 class: a lifecycle/reuse flaw where a value that must be single-use is consumed more than once.

### Finding Description
In `preprocess_internal` (signing_protocol.rs:123-147):

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  let mut cache = machine.cache();
  ... // XOR-encrypt with key derived from context || self.key
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

The entry is `set` once and read on every call; it is never cleared after `sign` consumes it. `from_cache` feeds the seed into `ChaCha20Rng::from_seed` inside `AlgorithmMachine::seeded_preprocess` (crypto/frost/src/sign.rs:127-133), so nonces `(d, e)` are a pure function of `seed || original_secret_share` — identical every time the same context is used.

The context is only `(b"DkgConfirmer", self.attempt)` (signing_protocol.rs:275). Yet multiple `sign` executions occur under it:

- `DkgConfirmer::share()` calls `share_internal` → `preprocess_internal` + `machine.sign(preprocesses, msg)` (signing_protocol.rs:288-310, 170).
- `DkgConfirmer::complete()` calls `share_internal` **again** (signing_protocol.rs:321-324) — a second `sign` with the same seed-derived nonces.
- `msg` is `set_keys_message(set, removed, key_pair)` where `key_pair` is caller-supplied (signing_protocol.rs:296-301), and `preprocesses` is the caller-supplied map of other validators' commitments.

FROST's documentation in this repo states the requirement explicitly: "Reusing preprocesses would enable a third-party to recover your private key share. Accordingly, you MUST not reuse preprocesses" (spec/cryptography/FROST.md:51-55; sign.rs:85-87, 211-219). `from_cache`'s own doc says "After this, the preprocess must be deleted so it's never reused" — and `CachedPreprocesses::set`/`get` never delete.

A FROST share is `s_i = d_i + e_i·ρ_i + λ_i·c·x_i`. Two shares produced from the same `(d_i, e_i)` but with either a different message (different challenge `c`) or a different included-participant/preprocess set (different binding factor `ρ_i` and Lagrange coefficient `λ_i`) yield a linear system solvable for the secret share `x_i`. Since `share()` is invoked when the coordinator emits its share and `complete()` re-executes `share_internal` to rebuild the machine (potentially with a different `key_pair` or different preprocess map than at share time), the second `sign` deterministically reuses the nonces.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret share for the validator-set key. With `t` compromised shares the threshold key is fully recoverable; even a single leaked share reduces the security margin and, combined with the shares' public verification data, enables targeted attacks on the threshold signature protecting Substrate-set key confirmation (`set_keys_message` authorizes the validator set's `KeyPair`). The cryptographic library itself explicitly classifies this as secret-share recovery.

### Likelihood Explanation
The second `sign` under one context is not hypothetical: `complete()` unconditionally re-runs `share_internal` (signing_protocol.rs:322). Whether a *different* message or preprocess set is signed under the same context depends on caller behavior in `coordinator/src/tributary/handle.rs` (which I could not fully trace within the iteration budget). However, additionally:

- Any retry/re-handling of the same DKG-confirmation attempt (e.g., after reboot — the cache exists precisely to survive reboots, and the encryption comment at lines 104-106 confirms persistence is intentional) with a different `key_pair` or a different validator preprocess set reuses the nonces.
- The seed is keyed only on `(static tag, u32 attempt)` — not on the message, participant set, or `key_pair` — so nothing binds the cached nonces to a single signing instance.

If every reuse happened to be byte-identical (same msg and same preprocess map), the shares would be identical and harmless; but the code provides no enforcement of that invariant, and the `complete` path accepts caller-supplied `preprocesses`/`key_pair` independently of what `share` saw. Exploitability hinges on an unprivileged validator influencing the preprocess map or the confirmed `key_pair` across the two calls — plausible via tributary message timing, but not fully verified end-to-end.

### Recommendation
Delete (or rotate) `CachedPreprocesses[context]` in the same DB transaction that produces the signature share — i.e., burn the seed when `share_internal` performs `sign`, per the `from_cache` contract ("the preprocess must be deleted so it's never reused"). If `complete` needs the machine, return/retain the `AlgorithmSignatureMachine` from `share` (in memory, keyed by attempt) rather than re-deriving nonces from the persisted seed. Alternatively, mix the message hash and included-participant set into the cache key *and* still delete after use, so any divergence yields a fresh seed rather than reuse.

### Proof of Concept
Conceptual (no test harness available in ask-only mode):

1. During DKG confirmation attempt `a`, the coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair_1)`. Internally `preprocess_internal` stores seed `S` under `("DkgConfirmer", a)` (first call) and produces share `s1 = d + e·ρ_A + λ·c1·x` over `msg1 = set_keys_message(set, removed, key_pair_1)`.
2. Later, `DkgConfirmer::complete(preprocesses_B, key_pair_2, shares)` re-runs `share_internal` → `preprocess_internal` reads the *same* `S` → `from_cache` → `seeded_preprocess` regenerates identical `(d, e)` via `ChaCha20Rng::from_seed(S)` (crypto/frost/src/sign.rs:127-133).
3. If `key_pair_2 != key_pair_1` or `preprocesses_B != preprocesses_A` (different included set → different `ρ`, `λ`, `c`), the second `sign` emits `s2 = d + e·ρ_B + λ'·c2·x` with the same `(d, e)`.
4. An observer collecting `s1, s2` and the public preprocesses/group data solves the two linear equations for `x`, the coordinator's secret share.

The concrete divergence of `key_pair`/`preprocesses` between the `share` and `complete` calls in `coordinator/src/tributary/handle.rs` could not be fully confirmed within the tool-call budget; the root cause (non-deleted, context-only-keyed nonce seed feeding multiple `sign` executions) is directly evidenced in signing_protocol.rs:123-147 and sign.rs:264-274.
