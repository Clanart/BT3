### Title
Ed448 `is_torsion_free` check is vacuous, so `read_G`/`from_bytes` accepts torsioned (non-prime-order) points - (File: crypto/ed448/src/point.rs)

### Summary
The CRS bug is a validation check bypassed because the input was never normalized before evaluation (whitespace padding defeats the extension regex). The Serai analog is a validation check that mathematically can never reject anything: `Point::is_torsion_free` in the Ed448 ciphersuite computes `(*self * -1) + self` — which is the identity for every group element — so `GroupEncoding::from_bytes` accepts points with torsion components. Every consumer that reads Ed448 points from untrusted bytes (`Ed448::read_G`, `Commitments::read`, `SchnorrSignature::read`, `ThresholdKeys::read`, MuSig key lists) therefore admits non-torsion-free points despite an explicit check intended to exclude them.

### Finding Description
`crypto/ed448/src/point.rs` defines:

```rust
impl Point {
  fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
  }
}
```

`self * (-1) + self` is `self - self = identity` unconditionally. `is_torsion_free` always returns true. This result gates decoding:

```rust
CtOption::new(point, not_negative_zero & point.is_torsion_free())
```

so `from_bytes` (and hence `Ciphersuite::read_G`, which additionally performs a canonical re-encoding round-trip) accepts any canonically-encoded point including ones lying outside the prime-order subgroup. Ed448 has cofactor 4; the decoder's own framing ("rejects non-canonical/torsioned points") is thus bypassed by inputs that are canonical bytes but semantically non-prime-order — the same shape as the CRS regex that sees canonical text but fails to normalize before matching.

Reachable public-input paths: `Ed448::read_G` in `crypto/frost/src/curve/mod.rs` (used for FROST `Commitments`, preprocesses, signature `R`), `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs`, `check_keys`/`musig` in `crypto/dkg/musig/src/lib.rs` (MuSig key lists), and `ThresholdKeys::read` verification shares in `crypto/dkg/src/lib.rs`.

### Impact Explanation
A torsioned point `P' = P + T` (T of order 2 or 4) is accepted wherever a prime-order point is required:

- FROST Ed448: a participant can submit nonce commitments `D, E` containing torsion components via `Commitments::read`. The binding factor `rho` binds the canonical encoding, but the aggregated nonce `R = D_i + rho_i*E_i` accumulates an attacker-controlled torsion term, altering the signed `R` away from what the nonce scalars imply — corrupting or enabling manipulation of the final Schnorr signature's `R`.
- MuSig/`musig_key`: `check_keys` deduplicates on `to_bytes`, so `A` and `A + T` are distinct entries; a rogue-key variant is possible where a malicious key's torsion component shifts the aggregate `musig_key` while the attacker controls the prime-order part, producing a group key/signature relationship not bound to the intended set.
- Schnorr signature verification (`SchnorrSignature::verify` → `batch_statements` → `multiexp`): with a torsioned public key or `R`, the equation `R + cA - sG = 0` holds modulo the prime-order part while the torsion term is unverified arithmetic — the verifier accepts signatures over a key that is not in the intended subgroup, enabling key-substitution/forgery classes documented for cofactor-4 curves.

This matches the accepted impact categories: incorrect verifier formula (the torsion gate never runs) and forged/substituted keys reaching signing and verification paths.

### Likelihood Explanation
Any party that supplies Ed448-encoded points to a Serai protocol (DKG participant broadcasting `Commitments`, a signer broadcasting a `Preprocess`, an entry in a MuSig key list, a submitter of a `SchnorrSignature`) can compute `P + T` trivially — torsion points on Ed448 are low-order and easy to construct. No collusion, malicious validator set, or broken BFT is required; it is reachable purely through public byte inputs to `read_G`-based decoders. Exploitation specifics (extracting secret material vs. key substitution/invalid signature) depend on the surrounding protocol, but the class is a well-known real-world EdDSA/cofactor attack surface.

### Recommendation
Implement an actual torsion check in `Point::is_torsion_free`, e.g. multiply by the prime subgroup order `r` (or by `r*h/…` appropriately) and require identity, or multiply by the cofactor and require the result is *not* identity and lies in the prime subgroup. The standard approach: `self * Scalar::from(cofactor)` should be checked against subgroup membership, or multiply by the group order and compare. Then re-run `ff-group-tests`/`test_encoding` plus a test asserting `A + T` (a known torsioned encoding) is rejected by `Ed448::read_G` and `Point::from_bytes`.

Supporting code: `crypto/ed448/src/point.rs` (`is_torsion_free`, `from_bytes` gate), consumers at `crypto/frost/src/curve/mod.rs` (`read_G`), `crypto/dkg/pedpop/src/lib.rs` (`Commitments::read`), `crypto/dkg/musig/src/lib.rs` (`check_keys`), `crypto/dkg/src/lib.rs` (`ThresholdKeys::read`).

One caveat I could not fully verify without execution: whether `Scalar` on Ed448 uses the subgroup order such that `self * (order-related value)` — the source as shown computes `self * -1 + self`, which is unconditionally the identity for any group; unless the `Mul` implementation is overridden non-standardly, the check is vacuous. A quick unit test asserting rejection of a known torsioned encoding would confirm.
