### Title
Unbounded participant count in `ThresholdKeys::read` causes quadratic deserialization DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` participant count and `t` threshold directly from serialized input, reads `n` verification shares, then invokes `ThresholdKeys::new`. For Lagrange interpolation, `ThresholdKeys::new` calculates an interpolation factor for each of the first `t` participants. Each factor calculation iterates over all `t` included participants, producing `O(t²)` scalar multiplication/inversion work.

An unprivileged party can therefore submit a syntactically valid serialized key with `n = u16::MAX` and a large `t`, causing a small input to consume disproportionate CPU time.

### Finding Description
The deserializer reads `t`, `n`, and `i` from the input, then reads the requested interpolation variant without imposing a practical limit on either parameter. [1](#0-0) 

For every participant index from `1` through `n`, it reads a group element and inserts it into the verification-share map. [2](#0-1) 

`ThresholdKeys::new` validates that `t <= n`, but does not impose a lower bound on computational complexity beyond the `u16` representation limit. [3](#0-2) 

For `Interpolation::Lagrange`, `ThresholdKeys::new` constructs the group key by evaluating `interpolation_factor` for each participant `1..=t`. [4](#0-3) 

Each `interpolation_factor` call iterates over the complete `included` set, which initially contains `t` participants, and performs a field inversion. [5](#0-4) 

Thus, serialized input of roughly `n * encoded_point_len` bytes triggers approximately `t²` scalar operations. With `n = 65_535` and `t = 32_768`, this requires more than one billion scalar multiplications/subtractions, plus over thirty thousand field inversions and group operations, from an input of only a few megabytes.

### Impact Explanation
A service that accepts serialized `ThresholdKeys` from an untrusted source can be stalled by a single maliciously parameterized object. Because the expensive work occurs after only bounded input-size reads, conventional message-size limits may not prevent the amplification.

This can deny service to key-loading, key-recovery, or validator startup paths that deserialize remote or persisted key material. Repeated submissions can keep worker threads busy with scalar operations proportional to `t²` rather than the submitted byte count.

### Likelihood Explanation
The attacker only needs to reach `ThresholdKeys::read` with controlled bytes. The object can remain structurally valid: `t <= n`, `i <= n`, all participant indexes are generated internally as `1..=n`, and each point can be a repeated canonical encoding.

No malformed scalar, duplicate participant ID, invalid point, private-key access, or protocol participation is required. The issue is the absence of a computational bound before `ThresholdKeys::new` performs quadratic Lagrange interpolation.

### Recommendation
- Enforce a protocol-level maximum `n` and `t` before allocating or reading `n` verification shares.
- Reject serialized parameters exceeding that limit in `ThresholdKeys::read`.
- Prefer storing and deserializing a precomputed group key where possible, rather than recomputing `O(t²)` Lagrange factors during untrusted deserialization.
- If reconstruction is required, calculate the public polynomial evaluation with an algorithm whose cost is linear or `O(t log² t)`, or defer expensive validation until after rate limiting/authentication.
- Add fuzz/regression coverage for large-but-valid `(t, n)` values and measure worst-case CPU consumption.

### Proof of Concept
Construct a serialized `ThresholdKeys<Secp256k1>` object with:

```text
id_len          = len(Secp256k1::ID), little-endian u32
id              = Secp256k1::ID
t               = 32768, little-endian u16
n               = 65535, little-endian u16
i               = 1, little-endian u16
interpolation   = 1 // Lagrange
secret_share    = canonical encoding of scalar 1
verification    = n copies of the canonical generator encoding
```

Then feed the bytes to:

```rust
ThresholdKeys::<Secp256k1>::read(&mut input.as_slice())
```

Deserialization succeeds syntactically, but `ThresholdKeys::new` evaluates `interpolation_factor` for participants `1..=32768`. Each evaluation scans all `32768` included participant IDs, resulting in approximately `1,073,741,824` scalar field operations before the call returns or fails.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
