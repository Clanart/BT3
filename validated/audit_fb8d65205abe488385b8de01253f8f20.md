### Title
Mempool block-building crashes on divide-by-zero when a fully-deduplicated spend bundle drives `item_cost` to zero - (File: chia/full_node/mempool.py)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for each mempool item being folded into a block, where `cost` is the item's full CLVM cost and `cost_saving` is the amount of cost eliminated by the fast-forward/dedup engine (`IdenticalSpendDedup.get_deduplication_info`). Immediately after computing `item_cost`, the code performs an unguarded `fee / item_cost` division in a logging call. If a mempool item's entire cost is eliminated by deduplication (`cost_saving == cost`), `item_cost` becomes `0` and the division raises an uncaught `ZeroDivisionError`, analogous to the libtiff `JPEGSetupEncode` divide-by-zero crash pattern (unchecked denominator derived from attacker-influenced input).

`cost` is `item.conds.cost`, the total CLVM cost of the mempool item (guaranteed non-zero at admission time by the `cost == 0` check in `MempoolManager.validate_spend_bundle`) [2](#0-1) . However, `cost_saving` is computed later, at block-building time, from `IdenticalSpendDedup.get_deduplication_info`, which subtracts out the cost of any coin spends in the item that duplicate (identical coin ID, puzzle, and solution) spends already committed by a higher fee-rate item earlier in this same block. If every coin spend in an item is fully redundant with spends already included from other mempool items (e.g., a single-spend bundle that is itself deduplicated), `cost_saving` can equal `cost` exactly, driving `item_cost` to `0` before any downstream guard runs. The `fee / item_cost` expression is evaluated eagerly as an argument to `log.info(...)`, so the division happens unconditionally and raises `ZeroDivisionError`, regardless of whether the item would otherwise be skipped by the following cost/spend/atom/pair checks.

This routine is reached whenever the full node assembles a block from the mempool (`create_bundle_from_mempool_items`, used by the simulator/legacy block-building path and exercised whenever transactions must be selected for a candidate block), which happens automatically as part of normal transaction processing after a spend bundle is admitted to the mempool via `MempoolManager.validate_spend_bundle` (i.e., reachable purely from submitting a spend bundle, no privileged access required).

### Impact Explanation
An unhandled `ZeroDivisionError` inside the block-building routine is an uncaught exception in a hot path of the full node's transaction-processing pipeline. Depending on how call sites handle exceptions from this method, this can abort in-progress block assembly, repeatedly fail block creation attempts, or otherwise disrupt the node's ability to process pooled transactions—matching the "spend-triggered transaction-processing halt" impact category. It does not directly cause fund loss or invalid state acceptance, keeping severity at Medium, consistent with the underlying libtiff advisory's DoS/crash characterization.

### Likelihood Explanation
Triggering this requires only that an attacker submit (or arrange for) two spend bundles to the mempool where one bundle's item consists entirely of coin spends that duplicate (same coin ID, puzzle reveal, and solution as) spends already present in a higher fee-rate item — a scenario the dedup subsystem is explicitly designed to detect and "fully eliminate." No privileged access, malicious peer/node behavior, or protocol-level trust is required — any unprivileged spend-bundle submitter can attempt this. The exact conditions needed to reach `cost_saving == cost` for an entire item (rather than partial dedup) depend on internal accounting in `IdenticalSpendDedup.get_deduplication_info`, which was not fully re-derived here; this introduces some uncertainty about how easily a single item can have *all* of its cost eliminated versus only some of it.

### Recommendation
Guard the division: compute `fee_per_cost` only when `item_cost > 0`, and treat `item_cost <= 0` as a signal to skip the item (log a zero or `N/A` fee-rate) rather than evaluating `fee / item_cost` unconditionally. Apply the same defensive check to the parallel accounting path in `create_block_generator2` if a similar computation exists there.

### Proof of Concept
Conceptual repro (verification requires running the mempool integration tests):
1. Submit spend bundle A containing coin spend `S` (coin `C`, puzzle `P`, solution `Sol`) with a high fee.
2. Submit spend bundle B, also spending coin `C` with identical puzzle `P` and solution `Sol` (bundle B is a single-spend bundle so its entire item cost equals the deduplicatable spend's cost), with a lower fee such that it doesn't replace A but remains a separate FF/dedup-eligible mempool item.
3. Trigger block building via `Mempool.create_bundle_from_mempool_items()` (e.g., through the simulator's `farm_block` / legacy block-creation path) while both items are present.
4. When item B is processed after item A has already claimed the dedup credit for spend `S`, `cost_saving` for B equals its full `cost`, making `item_cost == 0` and raising `ZeroDivisionError` at [3](#0-2) .

Note: I was unable to fully trace `IdenticalSpendDedup.get_deduplication_info` in `chia/full_node/eligible_coin_spends.py` within the available investigation budget to confirm the exact minimal conditions under which `cost_saving` equals an entire item's `cost` (versus only part of it). This should be verified against that function's implementation before treating the PoC steps above as final/confirmed.
