### Title
Multisig pubkey `Threshold = 0` bypasses signature verification entirely - ([File: sei-cosmos/crypto/keys/multisig/multisig.go])

### Summary
The Halborn/Chiliz finding is about a relayer `_relayerThreshold` that can be set with no minimum-quorum validation, allowing a proposal to pass with fewer votes than intended. The same root-cause bug class — a threshold/quorum value that is never bounded to `>= 1` on the enforcement path — exists in sei-cosmos's `LegacyAminoPubKey` (k-of-n multisig) implementation. The `Threshold` guard only lives in the constructor helper `NewLegacyAminoPubKey`, not in the actual verification function `verifyMultisignature`, which is the code path exercised for every real transaction.

### Finding Description
`NewLegacyAminoPubKey` panics if `threshold <= 0`: [1](#0-0) 

But this constructor is only used when a client tool builds a fresh multisig pubkey locally (e.g. CLI `keys add --multisig`). When a `LegacyAminoPubKey` arrives as part of a transaction (e.g. via the account's `PublicKey` field decoded from protobuf/`Any`, as happens the first time an account signs and `SetPubKeyDecorator` records its pubkey), the struct's `Threshold` field is populated directly by proto unmarshaling — the constructor and its `threshold <= 0` panic are never invoked.

The actual signature check reads `m.Threshold` with no lower-bound validation: [2](#0-1) 

If `m.Threshold == 0`, the check `nSigs < int(m.Threshold)` becomes `nSigs < 0`, which is always false — so **zero signatures satisfy the requirement**. The companion structural check `ValidateSignatureDataStructure` only requires `len(sig.Signatures) == nTrue` (number of `true` bits in the bit array): [3](#0-2) 

An attacker can submit a `MultiSignatureData` with a bit array of the correct size but **all bits false** (`nTrue = 0`), requiring zero `Signatures`. The verification loop in `verifyMultisignature` then iterates over the bit array, finds no set bits, verifies nothing, and returns `nil` — a full success with no cryptographic signature check performed at all.

### Impact Explanation
Any address whose registered public key is a `LegacyAminoPubKey` with `Threshold = 0` can be drained by anyone submitting a transaction with an all-false bit array and no signatures — a complete authentication bypass for that account. This mirrors the report's "lack of quorum definition" impact: a threshold value with no enforced minimum lets a decision (here, fund transfer authorization) be approved without any real participants. Because module/vesting/bridge accounts can be configured to require multisig ownership, an account created (or reconfigured) this way represents concrete, permanent fund loss for whoever funds it, believing it to be a legitimate k-of-n account.

### Likelihood Explanation
An attacker fully controls the crafting of a `LegacyAminoPubKey` (any user/deployer can construct one off-chain and derive its address), so getting `Threshold = 0` recorded on-chain only requires that pubkey to be used once as a transaction signer's public key (the normal path by which the SDK ante-handler persists an account's pubkey). No governance, validator, or operator privilege is needed — this is directly reachable by an ordinary unprivileged transaction sender.

### Recommendation
Enforce `Threshold >= 1` and `Threshold <= len(pubKeys)` inside `verifyMultisignature` (and/or `ValidateSignatureDataStructure`) itself, not only in the `NewLegacyAminoPubKey` constructor, so that no code path — including protobuf-deserialized pubkeys arriving from an untrusted transaction — can bypass the quorum requirement.

### Proof of Concept
1. Craft a `LegacyAminoPubKey{Threshold: 0, PubKeys: [pkA, pkB, pkC]}` directly (bypassing `NewLegacyAminoPubKey`) and derive its bech32 address.
2. Get any counterparty to send funds to that address, believing it is a normal 2-of-3 (or similar) multisig.
3. Submit a transaction spending from that address with a `MultiSignatureData{BitArray: CompactBitArray(size=3, all false), Signatures: []}`.
4. `ValidateSignatureDataStructure` passes (`nTrue == len(Signatures) == 0`); `verifyMultisignature` passes (`nSigs(0) < Threshold(0)` is false, and the verification loop verifies nothing) — the transaction succeeds with zero valid signatures, draining the account. [2](#0-1) [4](#0-3)

func (m *LegacyAminoPubKey) verifyMultisignature(getSignBytes multisigtypes.GetSignBytesFunc, sig *signing.MultiSignatureData) error {
	bitarray := sig.BitArray
	sigs := sig.Signatures
	size := bitarray.Count()
	pubKeys := m.GetPubKeys()
	// ensure bit array is the correct size
	if len(pubKeys) != size {
		return fmt.Errorf("bit array size is incorrect, expecting: %d", len(pubKeys))
	}
	nSigs := len(sigs)
	// ensure at least k signatures are set
	if nSigs < int(m.Threshold) {
		return fmt.Errorf("not enough signatures set, have %d, expected %d", nSigs, int(m.Threshold))
	}

func validateMultiSignatureDataStructure(sig *signing.MultiSignatureData) error {
	if sig == nil {
		return fmt.Errorf("multi signature data is required")
	}
	if sig.BitArray == nil {
		return fmt.Errorf("bit array is required")
	}
	if err := sig.BitArray.ValidateBasic(); err != nil {
		return err
	}
	size := sig.BitArray.Count()
	if size == 0 {
		return fmt.Errorf("bit array size is incorrect %d", size)
	}
	nTrue := sig.BitArray.NumTrueBitsBefore(size)
	if len(sig.Signatures) != nTrue {
		return fmt.Errorf("signature size is incorrect: have %d, expected %d", len(sig.Signatures), nTrue)
	}
	for i, child := range sig.Signatures {
		if err := ValidateSignatureDataStructure(child); err != nil {
			return fmt.Errorf("signature data at index %d: %w", i, err)
		}
	}
	return nil
}
