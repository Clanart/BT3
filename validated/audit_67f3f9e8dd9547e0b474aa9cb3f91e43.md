### Title
`StateManager::process_block_parallel` halts all bridge automation on any single state-machine error — (File: `core/src/states/mod.rs`)

### Summary
`StateManager::process_block_parallel` iterates over every active kickoff and round state machine in parallel. If any single machine emits an error via `capture_error`, the function collects all errors and returns a combined failure. Because the enclosing DB transaction is rolled back on failure, the triggering block event is never archived from the pgmq queue. The `MessageConsumerTask` retries the same block event indefinitely. Any persistent per-machine error therefore freezes the entire automation layer — no watchtower challenges, operator asserts, or disprove transactions can be dispatched for any deposit until the broken machine is manually removed or the root cause is fixed.

### Finding Description
In `core/src/states/mod.rs`, `process_block_parallel` runs all kickoff and round state machines against each new finalized block:

```rust
// Merge and handle errors
let mut all_errors = Vec::new();
for ctx in kickoff_contexts.iter_mut().chain(round_contexts.iter_mut()) {
    all_errors.extend(std::mem::take(&mut ctx.errors));
}

if !all_errors.is_empty() {
    return Err(eyre::eyre!(
        "Multiple errors occurred during state processing: {:?}",
        all_errors
    ));
}
``` [1](#0-0) 

A single machine error causes the whole function to return `Err`. The caller in `core/src/states/event.rs` propagates it with `?`:

```rust
self.process_block_parallel(&mut context).await?;
``` [2](#0-1) 

`MessageConsumerTask::run_once` in `core/src/states/task.rs` only archives the queue message and commits the DB transaction **after** `handle_event` succeeds:

```rust
self.inner.handle_event(message, arc_dbtx.clone()).await?;
// ...
self.inner.queue.archive_with_cxn(&self.queue_name, msg_id, &mut *dbtx).await?;
dbtx.commit().await?;
``` [3](#0-2) 

When `handle_event` returns `Err`, the `?` short-circuits before `archive_with_cxn` and `commit`. The DB transaction is dropped (rolled back) and the pgmq message remains visible. The `RecoverableTask` implementation only reloads state machines from DB:

```rust
async fn recover_from_error(&mut self, _error: &BridgeError) -> Result<(), BridgeError> {
    self.inner.reload_state_manager_from_db().await
}
``` [4](#0-3) 

Because the DB transaction was rolled back, the reloaded state is identical to the state before the failed attempt. The same block event is dequeued again, the same machine fails again, and the loop repeats indefinitely. The `into_buffered_errors(10, 3, Duration::from_secs(10))` wrapper only adds a back-off delay; it never discards the stuck event or skips the broken machine. [5](#0-4) 

The state manager is used by both `Verifier` and `Operator` to drive all time-sensitive protocol duties: [6](#0-5) 

### Impact Explanation
The state manager is the sole automation engine for:
- **Watchtower challenges** (`Duty::WatchtowerChallenge`) — verifiers must submit these within a fixed block window after a kickoff; missing the window lets a malicious operator proceed unchallenged.
- **Operator asserts** (`Duty::SendOperatorAsserts`) — operators must post assert transactions within a deadline; missing it forfeits collateral.
- **Disprove transactions** (`Duty::VerifierDisprove`) — verifiers must disprove within a deadline; missing it allows a fraudulent payout to be reimbursed.
- **Unspent kickoff connectors** (`Duty::NewReadyToReimburse`) — verifiers must spend these to prevent operator collateral from being locked.

A permanently stuck state manager means none of these duties are ever dispatched for any deposit, across all operators and all kickoffs, not just the one whose machine is broken. This breaks bridge liveness and, in the watchtower-challenge and disprove cases, directly enables theft of bridged BTC or operator collateral.

### Likelihood Explanation
The number of active state machines grows with every new operator and every new kickoff. Any persistent error in any single machine — a missing DB record, a failed RPC call to the Bitcoin node, a logic error in a state transition triggered by an unexpected on-chain witness — is sufficient to freeze the entire layer. The `capture_error` mechanism is explicitly designed to collect such errors: [7](#0-6) 

As the bridge scales to more operators and more concurrent kickoffs, the probability that at least one machine encounters a persistent error increases monotonically.

### Recommendation
Errors from individual state machines should be isolated so that a broken machine is skipped (and logged/alarmed) while all other machines continue processing. Concretely:

1. In `process_block_parallel`, instead of collecting all errors and returning a combined failure, log each per-machine error and continue processing the remaining machines.
2. Optionally quarantine the broken machine (remove it from the active set, persist a `broken` flag to DB) so it does not block future blocks.
3. Expose a monitoring metric / alert when a machine is quarantined so operators can investigate and manually recover.

This mirrors the fix recommended for `RootManager.propagate`: use per-item error isolation (try-catch / `address.call`) rather than letting one failure abort the entire batch.

### Proof of Concept
1. Bridge is running with N operators and M active kickoffs; the state manager has N round machines and M kickoff machines.
2. One kickoff machine enters a state where its next duty (`WatchtowerChallenge` or `SendOperatorAsserts`) calls `handle_duty`, which fails persistently (e.g., the required kickoff txid is absent from `deposit_signatures` due to a DB inconsistency, returning `Err` from `get_kickoff_txid_from_deposit_and_kickoff_data`). [8](#0-7) 

3. The error is stored in `ctx.errors` via `capture_error`.
4. `process_block_parallel` sees `!all_errors.is_empty()` and returns `Err`. [9](#0-8) 

5. `handle_event` propagates the error; the DB transaction is rolled back; the block event is not archived.
6. `recover_from_error` reloads state machines from DB — the broken machine is reloaded in the same broken state.
7. The next poll dequeues the same block event; step 2–6 repeats forever.
8. All N×M other machines are also frozen: no watchtower challenges, no asserts, no disproves are dispatched for any deposit from this point forward.

    /// -- Round state duties --
    /// This duty is sent after a new ready to reimburse tx is sent by the corresponding operator.
    /// used_kickoffs is a set of kickoff indexes that have been used in the previous round.
    /// If there are unspent kickoffs, the owner can send a unspent kickoff connector tx.

        used_kickoffs: HashSet<usize>,

    /// It includes the txid in which the utxo was spent, so that the owner can verify if this is an actual kickoff sent by operator.
    /// Witness is also sent as if tx is an actual kickoff, the witness includes payout blockhash.

        txid: Txid,
        block_height: u32,
        witness: Witness,
    },

    /// It includes the relevant data so that the owner can check if the kickoff is malicious.

        challenged_before: bool,

    /// For operators, this queues transactions like ChallengeTimeout.

        kickoff_data: KickoffData,

        kickoff_data: KickoffData,
