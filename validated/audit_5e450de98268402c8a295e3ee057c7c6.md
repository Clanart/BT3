## Analysis

The Sherlock finding's broken invariant is: **a "match" is bound to a mutable, attacker-controlled identifier (name/nonce) instead of to immutable content**, so the party who controls that identifier can silently redirect what the counterparty's action actually operates on after the match/approval step.

The closest real analog in this repository is GitHub Desktop's pull-request checkout flow, where the PR's `head` ref is matched by **branch name** and a **loosely-normalized clone URL comparison**, never by the commit SHA that was actually reviewed/displayed to the user.

### Title
Pull request checkout resolves the fork's branch **by name**, not by the reviewed commit SHA, letting the fork owner silently redirect what gets checked out - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user reviews and then checks out a pull request from Desktop, the app fetches and checks out whatever commit currently sits at `headRefName` on the fork/remote matched via `urlMatchesRemote`. The `PullRequestRef.sha` recorded when the PR was fetched from the API [1](#0-0)  is never compared against the SHA that ends up checked out, and the remote lookup itself is a loose, case-insensitive hostname/owner/name string match rather than an exact, pinned reference [2](#0-1) .

### Finding Description
`_checkoutPullRequest` / `_findPullRequestBranch` take only `headRepoOwner`, `headCloneUrl`, and `headRefName` — the branch *name* — and never the `head.sha` that was used to compute the PR's diff/mergeability shown to the user: [3](#0-2) 

Inside `_findPullRequestBranch`, the remote is found by fuzzy URL matching (`remotes.find(r => urlMatchesRemote(headCloneUrl, r))`), explicitly allowing reuse of "an existing remote (regardless if set up by us or outside of Desktop)": [4](#0-3) 

The branch that ends up checked out is resolved purely from the remote-tracking ref for `headRefName` at the moment of checkout — freshly fetched if not already present — with no verification against any previously observed SHA: [5](#0-4) 

Because the PR's head repository is a fork the attacker (the PR author) fully controls, they can force-push new commits to the same branch name at any time between:
1. the moment the victim reviews the PR (diff/mergeability computed from the `head.sha` recorded by `pull-request-store.ts` at fetch time) [6](#0-5) , and
2. the moment the victim clicks "Checkout this PR" and Desktop performs `_fetchRemote` + branch resolution by name.

Desktop has no mechanism analogous to a nonce/version check that would detect this swap — the "match" (PR ↔ local `pr/<number>` branch) is keyed on the mutable ref name, exactly like the report's `Order` being keyed on a mutable `nonce`/`premium` that the maker can silently replace after another party has already committed to the earlier version.

### Impact Explanation
The victim believes they are checking out and building/running the exact commit they reviewed (diff, CI checks, mergeability all computed against the original `head.sha`), but Desktop silently checks out whatever the fork owner has since pushed to that branch, with no warning or diff re-confirmation. This is a "silent corruption of what the user commits/pushes/checks out" primitive driven entirely by content the attacker controls (their own fork/branch), matching the accepted impact category of "attacker controls a cloned/fetched repository ... and the result is ... silent corruption of what the user commits or pushes."

### Likelihood Explanation
- The attacker only needs push access to their own fork (trivial, low privilege) — no admin rights, no local access, no leaked credentials.
- No unnatural user steps are required beyond the normal Desktop workflow: view PR → click checkout, which is the intended, expected way to interact with pull requests in Desktop.
- Time-of-check/time-of-use windows between a user reviewing a PR and clicking "Checkout" are realistic (minutes to days), especially for PRs left open in the branch list.

### Recommendation
- Thread the reviewed `head.sha` through `checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch`.
- After fetching, verify that the remote-tracking branch's tip SHA matches the expected `head.sha`; if it has changed, warn the user (similar to existing "PR author has deleted their branch" error path) instead of silently checking out newer/different content.
- Alternatively/additionally, fetch and checkout the specific SHA (`refs/pull/<n>/head@{sha}` or explicit SHA checkout) rather than resolving by mutable branch name alone.

### Proof of Concept
1. Attacker opens a PR from `fork/branch` with commit `A` (benign diff).
2. Victim opens Desktop, views the PR list; Desktop stores `head.sha = A` via `storePullRequests` [6](#0-5) , and reviews/approves the diff for `A`.
3. Before the victim clicks "Checkout", the attacker force-pushes commit `B` (malicious payload, e.g. modified build scripts/hooks) to the same `fork/branch`.
4. Victim clicks "Checkout this PR". `checkoutPullRequest` calls `_checkoutPullRequest` with only `headRefName` (no SHA) [7](#0-6) ; `_findPullRequestBranch` fetches the remote and resolves `pr/<n>` to whatever is currently at `fork-remote/branch` — now commit `B` [5](#0-4) .
5. Desktop checks out `B` with no diff-mismatch warning; the victim now has malicious code checked out believing it is the reviewed commit `A`.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
