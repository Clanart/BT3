### Title
Prefix-only host check in `githubAssetVideoRegex` allows authority confusion via subdomain-suffix and userinfo payloads - (File: `app/src/lib/markdown-filters/video-url-regex.ts`)

### Summary
`githubAssetVideoRegex` is built by string-concatenating `escapeRegExp('https://user-images.githubusercontent.com')` with `.+` and a video-extension alternation, instead of parsing the candidate URL and comparing `new URL(x).hostname` to the exact string `user-images.githubusercontent.com`. Because the pattern only anchors the *start* of the string and never asserts a boundary (end-of-host, `/`, or end-of-string) after the literal domain, any suffix that keeps the literal prefix intact — including strings that make the *real* authority a different host — will still match.

### Finding Description [1](#0-0) 

The regex source ends up equivalent to:
```
^https://user-images\.githubusercontent\.com.+(mp4|webm|ogg|mov|qt|avi|wmv|3gp|mpg|mpeg|)$
```
(case-insensitive, `escapeRegExp` only escapes `. * + ? ^ $ { } ( ) | [ ] \`, it does not escape `-`, `:`, `@`, or `/`).

This regex is used to gate what is allowed to become a `<video>` element `src` in rendered markdown: [2](#0-1) [3](#0-2) 

The comment states the invariant that is supposed to be enforced: "If the url for the src does NOT match the pattern of a github user asset, we remove the video tag" — i.e., the *host* must be `user-images.githubusercontent.com`. But the check tested is on `el.src` / `node.firstChild.href`, which are DOM-normalized full URL strings, and the regex only verifies a literal *prefix*, not the parsed hostname. Because `.+` requires no boundary character after `.com`, several authority-confusion payloads keep the exact prefix `https://user-images.githubusercontent.com` while the real network authority is attacker-controlled:

- `https://user-images.githubusercontent.com.evil.com/x.mp4` — real hostname is `user-images.githubusercontent.com.evil.com`; matches regex because prefix + `.evil.com/x.mp4` satisfies `.+` and ends in `mp4`.
- `https://user-images.githubusercontent.com@evil.com/x.mp4` — per the URL/WHATWG spec, `user-images.githubusercontent.com` becomes *userinfo* and `evil.com` becomes the real host; the serialized `href`/`src` string is unchanged, so it still matches the regex.
- `https://user-images.githubusercontent.com:evil.com/x.mp4` — this one does **not** succeed in practice: a non-numeric value after `:` is an invalid port per the URL spec, so the browser's URL parser rejects the string outright, and the resulting `href`/`src` DOM property will not equal the attacker's malformed string (it fails to set / is normalized away). This payload is therefore not a working bypass.

So the `.evil.com` suffix and `@evil.com` userinfo confusion both defeat the intended "host must equal `user-images.githubusercontent.com`" invariant, while the `:` payload is blocked by browser URL parsing before it ever reaches the regex.

### Impact Explanation
A successful bypass lets an attacker who controls markdown content (PR/issue/comment body, commit message, etc. rendered by Desktop) get an arbitrary attacker-controlled URL accepted as a `<video src>` in the rendered HTML, defeating the allowlist that is supposed to restrict video sources to GitHub's own user-content CDN. I was not able to find any Content-Security-Policy (`media-src`) restriction elsewhere in the codebase that would act as a second layer of defense for the markdown-rendering webview — searches for `Content-Security-Policy`/`media-src` in `app/src` did not surface any policy applied to the markdown/PR-description renderer, so this filter appears to be the primary control, and its bypass removes that control. That said, the resulting impact is bounded: it allows loading/rendering an arbitrary remote video resource in the sandboxed markdown webview (a `<video>` tag load, not script execution), similar in class to a hostile external image URL. It does not, by itself, achieve code execution, IPC escape, or credential exfiltration, so it does not clearly meet the "Valid Impact" bar defined in the prompt.

### Likelihood Explanation
Low-to-moderate. The attacker only needs to control markdown text that Desktop renders (e.g., a PR/issue body or commit message from a hostile remote), and craft an `<a href>` or `<video src>` string with one of the two working payloads above. No special privileges are required.

### Recommendation
Replace the string-concatenation regex with actual URL parsing and a strict hostname comparison, e.g.:
```ts
function isGithubAssetVideoUrl(candidate: string): boolean {
  try {
    const url = new URL(candidate)
    return (
      url.protocol === 'https:' &&
      url.hostname === 'user-images.githubusercontent.com' &&
      videoExtensionRegex.test(url.pathname)
    )
  } catch {
    return false
  }
}
```
This eliminates prefix/suffix and userinfo confusion because `URL.hostname` is the spec-normalized authority, independent of `@`, `:`, or trailing-dot tricks.

### Proof of Concept
```js
const { githubAssetVideoRegex } = require('./video-url-regex')

console.log(githubAssetVideoRegex.test('https://user-images.githubusercontent.com.evil.com/x.mp4')) // true (should be false)
console.log(githubAssetVideoRegex.test('https://user-images.githubusercontent.com@evil.com/x.mp4'))  // true (should be false)
console.log(githubAssetVideoRegex.test('https://user-images.githubusercontent.com:evil.com/x.mp4'))  // browser rejects the URL before reaching this test; not a working bypass
```
Embedding either working payload in markdown (`<video src="https://user-images.githubusercontent.com.evil.com/x.mp4">` or as an auto-linked `<a href>`) will pass `VideoTagFilter`/`VideoLinkFilter` and render with the attacker's real host as the media source. [4](#0-3)

```typescript
import escapeRegExp from 'lodash/escapeRegExp'

const user_images_cdn_url = 'https://user-images.githubusercontent.com'

// List of common video formats obtained from
// https://developer.mozilla.org/en-US/docs/https://developer.mozilla.org/en-US/docs/Web/Media/Formats/Video_codecs/Media/Formats/Video_codecs
// The MP4, WebM, and Ogg formats are supported by HTML standard.
const videoExtensionRegex = /(mp4|webm|ogg|mov|qt|avi|wmv|3gp|mpg|mpeg|)$/

/** Regex for checking if a url is a github asset cdn video url */
export const githubAssetVideoRegex = new RegExp(
  '^' + escapeRegExp(user_images_cdn_url) + '.+' + videoExtensionRegex.source,
  'i'
)
```

```typescript
export class VideoTagFilter implements INodeFilter {
  /**
   * Video link filter matches on video tags that src does not match a github user asset url.
   */
  public createFilterTreeWalker(doc: Document): TreeWalker {
    return doc.createTreeWalker(doc.body, NodeFilter.SHOW_ELEMENT, {
      acceptNode: function (el: Element) {
        return !isElement(el, 'video') || githubAssetVideoRegex.test(el.src)
          ? NodeFilter.FILTER_SKIP
          : NodeFilter.FILTER_ACCEPT
      },
    })
  }
```
