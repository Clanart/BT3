### Title

Deposits to derived internal addresses (branch/change/forward) are misclassified as internal outputs and their `InInstruction` data is silently dropped — ([File: processor/src/networks/bitcoin.rs](https://github.com/blackvul/serai--002/blob/next/processor/src/networks/bitcoin.rs), [File: networks/bitcoin/src/wallet/mod.rs](https://github.com/blackvul/serai--002/blob/next/networks/bitcoin/src/wallet/mod.rs))

### Summary

Analogous to `eth::most::receiveRequest` using `_destTokenAddress == wethAddress` as the discriminator that silently switches a user's deliverable from "WETH tokens" to "native ETH", Serai's Bitcoin scanner discriminates the *semantic kind* of a received output purely by which registered `script_pubkey` it pays to. `Scanner::register_offset` derives publicly computable internal addresses (`Branch`, `Change`, `Forwarded`), and `Bitcoin::get_outputs` only attaches the user's `InInstruction` data (the Serai-side credit/destination instruction) to outputs classified `OutputType::External`. Any unprivileged party can send a Bitcoin transaction paying to one of the non-External scripts — the output is reported as received by the multisig, but its attached data is discarded, so the depositor is never credited and the funds sit under a classification the scheduler treats as internal.

### Finding Description

`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` map from script to scalar offset; `scan_transaction` returns a `ReceivedOutput` for *any* output whose `script_pubkey` matches, with no check on the sender's intent: [1](#0-0) 

The processor's `scanner()` registers four output types against one key — `External` (offset zero) plus `Branch`, `Change`, and `Forwarded` derived via `hash_to_F(b"Serai Bitcoin Output Offset", ...)`. Since the group key and the domain separator are public, anyone can compute all four addresses: [2](#0-1) 

In `get_outputs`, each scanned output is typed via `kinds[offset_repr]`, and the Serai `InInstruction` data extracted from the transaction is only attached when `kind == OutputType::External`: [3](#0-2) 

This mirrors the WETH confusion exactly: the *destination encoding* (token address vs. WETH sentinel; here, external script vs. internal-offset script) selects the handling path, and the "wrong" path silently delivers something different from what the sender asked for — a `Change`/`Forwarded`-typed output with empty `data` instead of an `External` deposit carrying the `InInstruction`. Note also that `register_offset` is surjective and order-dependent (an odd-parity point causes `offset += Scalar::ONE` until even), so the offset the depositor's funds are keyed under is not necessarily the semantic offset they intended — an additional layer of the same ambiguity: [4](#0-3) 

### Impact Explanation

- **Loss of credit for depositors.** A user who constructs an `InInstruction` transaction paying to the `Forwarded`/`Branch`/`Change` address of the active set (or whose wallet/tool derives the wrong address) has their BTC locked into the multisig but `data` is empty, so no Serai-side mint/credit occurs. The funds are received but unattributable — the same "received ETH instead of WETH, contract can't use it" shape.
- **Misrouted forwarding.** Outputs classified `OutputType::Forwarded` enter the forwarding pipeline with no attached instruction data, producing forwards with incorrect/missing routing information rather than a normal deposit.
- **Unprivileged reachability.** Triggering requires only publishing an ordinary Bitcoin transaction — no validator status, no collusion, no malformed encodings.

### Likelihood Explanation

The internal addresses are deterministically derivable by anyone (`external_address`/`branch_address`/`change_address`/`forward_address` are public functions of the group key, and `KEY_DST` + labels are constants). The mistake requires a user or integrated frontend to pick the wrong derived address — plausible whenever the four addresses are displayed or constructed client-side — or to deliberately grief by paying a `Forwarded`/`Change` script. There is no on-chain check that an `InInstruction`-bearing transaction paid the *External* script specifically; classification is purely positional on the script. Likelihood is moderate: it needs user-side error or adversarial deposit construction, but nothing prevents it.

### Recommendation

- Treat any output on a non-`External` script that carries a parseable `InInstruction` in the transaction as an error/explicitly-attributed deposit rather than silently dropping `data` — i.e., attach `data` based on the presence of the instruction, not on `kind`, or reject/credit-flag transactions where `kind != External` and `data` is non-empty.
- Have `branch_address`/`change_address`/`forward_address` marked clearly internal-only, and consider embedding the `OutputType` discriminants in a way that cannot collide with a user-intended deposit (analogous to the report's suggestion of a dedicated sentinel instead of overloading `wethAddress`).
- Reject or flag `register_offset` normalizations (`offset += 1`) when the resulting script could be ambiguous, so the semantic offset and the spend offset cannot diverge unnoticed.

### Proof of Concept

1. From the active validator-set group key `key`, any observer computes `Change`/`Forwarded`/`Branch` addresses via `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change"|"forward"|"branch")` and `p2tr_script_buf(key + G*offset)`, exactly as `processor/src/networks/bitcoin.rs::scanner` does.
2. The depositor publishes a normal Serai deposit transaction — an `InInstruction` embedded in input 0's witness (per `extract_serai_data`) — but sets the output `script_pubkey` to the `Forwarded` (or `Change`) script instead of the external P2TR script.
3. `Bitcoin::get_outputs` scans it: `scanner.scan_transaction` matches `output.script_pubkey`, `kinds[offset]` yields `OutputType::Forwarded`, and the `if output.kind == OutputType::External` guard skips attaching `data`. The output is emitted to the scheduler as an internal-type output with empty data.
4. Result: the BTC is under multisig control (spendable), but the depositor's instruction is discarded — no mint/credit is attributable, identical in effect to the report's "user expected WETH, received ETH they cannot use". Recovery would require operator intervention, matching the original finding's "loss of funds, recoverable by owner" impact.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );

    OutputType::Change,
