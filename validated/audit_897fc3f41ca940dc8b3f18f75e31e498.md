### Title
Silent commit/discard corruption from stale line-selection indices after diff hunk expansion - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The reported Sublime bug is a "unit confusion" flaw: a value computed under one indexing scheme (`_principalWithdrawable`, denominated in borrow-asset amount) is reused as if it were denominated in a different scheme (shares), silently producing the wrong withdrawal amount. The closest verified analog in this codebase is in the diff hunk-expansion logic used for partial staging/commit and discard-changes: `expandTextDiffHunk` in [1](#0-0)  inserts new context lines into a hunk without shifting the hunk's `unifiedDiffStart`, while the rest of the app (line-selection bitset, `formatPatch`, `formatPatchToDiscardChanges`) continues to compute a line's absolute selection index as `hunk.unifiedDiffStart + lineIndex`.

### Finding Description
Line selection in Desktop is tracked purely by absolute integer index (`DiffSelection`), computed everywhere as `hunk.unifiedDiffStart + lineIndex` (relative position within the hunk's `lines` array), e.g. in `formatPatch` [2](#0-1)  and `formatPatchToDiscardChanges` [3](#0-2) .

When a hunk is expanded "up" (`expandTextDiffHunk`, kind `'up'`), new context `DiffLine`s are *prepended* to the hunk's existing lines while `hunk.unifiedDiffStart` for that hunk is left unchanged: [4](#0-3) 

This means every existing `Add`/`Delete` line in that hunk is now at a higher relative index within `hunk.lines`, so its "absolute index" (`unifiedDiffStart + lineIndex`) shifts forward by `numberOfLinesToAdd`, even though `unifiedDiffStart` itself never changed. The `DiffSelection` object, however, still stores selection state keyed by the *pre-expansion* absolute indices (there is no re-indexing/remapping step performed on the selection when a hunk is expanded — only `selectableLines` is refreshed elsewhere, on full diff reload, via `withSelectableLines` in `app-store.ts` [5](#0-4) , not on interactive expansion of a currently-loaded diff).

As a result, after an "expand up" action:
- The Add/Delete line the user selected before expansion is now at a *different* absolute index than the one recorded in `DiffSelection`, so `selection.isSelected(absoluteIndex)` for that line silently returns the *default* state instead of the user's actual choice.
- Conversely, the old (now-stale) index the user selected may point at one of the newly-inserted context lines, which is harmless for `formatPatch` (context lines are always included) but confirms the index mapping is broken.

This value — the mapping between a diff line's *position in the currently rendered/expanded hunk* and its *absolute selection index* — is exactly analogous to the Sublime bug's unit confusion: an index computed under the "post-expansion" line layout is used as if it were still valid under the "pre-expansion" `unifiedDiffStart`-relative addressing scheme that `DiffSelection` was built against.

### Impact Explanation
`formatPatch` is used by `applyPatchToIndex` to build the exact patch that is `git apply --cached`'d into the index for partial commits [6](#0-5) , and `formatPatchToDiscardChanges` builds the patch used to discard specific lines from the working directory. Because the selection-to-line mapping can silently desync after a user expands hunk context (a normal, encouraged UI action when reviewing a diff before committing), a user could:
- Believe they deselected a sensitive/incorrect line, but that line still gets included in the commit (or vice versa), or
- Discard a different line than the one they intended to discard, permanently losing working-directory changes they meant to keep.

This is a silent corruption of what the user commits/pushes or discards — matching the "Valid Impact" criteria in the task (silent corruption of committed/pushed content) without requiring any attacker-controlled repository content beyond a diff shape that includes hunk boundaries encouraging expansion (which is normal, not adversarial). Note: this issue does not require a malicious remote; any repo with hunks separated by more than `DefaultDiffExpansionStep` (20) lines of unchanged content is sufficient, so it is broader than the "attacker controls remote" framing in the task, but it directly matches the underlying bug class (misused index/unit) and the "silent corruption of commits" impact bucket.

### Likelihood Explanation
Expanding hunk context ("expand up"/"expand down") is a core, commonly used UI feature for reviewing changes before partial staging, so the preconditions (expand a hunk, then toggle/verify selection of a line whose relative position shifted) are easily reached through completely ordinary interactive use — no local/admin access or malware needed. However, I was not able to fully trace, within the remaining investigation budget, whether the `Diff`/`side-by-side-diff.tsx` component recomputes and reissues a corrected `DiffSelection` immediately after every `expandHunk` call (i.e., whether there is a compensating remap I didn't locate). The `onDiscardChanges` handler explicitly forwards `this.props.diff` (the *original*, non-expanded diff) rather than the expanded one specifically to avoid this class of mismatch [7](#0-6) , which suggests the developers are aware of the expanded-vs-original index mismatch risk for discard, but I could not confirm the equivalent safeguard exists for the commit/`formatPatch` path or for the "expand up" index-shift scenario specifically.

### Recommendation
- Ensure hunk expansion always updates `unifiedDiffStart`/`unifiedDiffEnd` for all lines that shift position, or alternatively re-derive absolute indices strictly from line identity (e.g., `originalLineNumber`) rather than from `unifiedDiffStart + relative position`, so a `DiffSelection` recorded before expansion remains valid afterward.
- Add an explicit remap/reconciliation step for `DiffSelection` whenever `expandTextDiffHunk` changes the relative offsets of existing lines within a hunk, analogous to the `withSelectableLines` reconciliation already done on full diff reload.
- Add regression tests that select specific Add/Delete lines, perform an "expand up" operation, and assert that `formatPatch`/`formatPatchToDiscardChanges` still act on the originally-intended lines.

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end due to tool-call limits):
1. Open a modified file whose diff has two hunks separated by more than 20 unchanged lines (so `DiffHunkExpansionType` is `Both`/`Short` rather than merge-only).
2. In the second hunk, select (for commit) a specific `Add` line, e.g. at absolute index `N`.
3. Click "Expand Up" on that hunk enough times that at least one new block of context lines is inserted above the previously-selected line (this triggers the `isExpandingUp` branch in `expandTextDiffHunk`, which prepends `newLineDiffs` before `allHunkLinesButFirst` while keeping `hunk.unifiedDiffStart` unchanged) [8](#0-7) [9](#0-8) .
4. Commit the partial selection. `applyPatchToIndex`/`formatPatch` compute `absoluteIndex = hunk.unifiedDiffStart + lineIndex` against the now-shifted `hunk.lines` [10](#0-9) , using the same `DiffSelection` object that was built against pre-expansion indices, and the previously selected line's new absolute index no longer matches any entry recorded in `DiffSelection`.
5. Inspect the resulting commit/patch: the line the user intentionally selected before expansion is missing (or an unintended line is included), demonstrating silent corruption of the committed content.

If a Devin agent with full repo/build access is available, this PoC should be executed against a real fixture repo (mirroring the pattern in `app/test/unit/patch-formatter-test.ts`) to confirm whether existing UI code compensates for this shift; I could not fully confirm this within the current investigation.
