### Title
Identity (point-at-infinity) public keys accepted by `ThresholdKeys::read`/`ThresholdKeys::new` and other `C::read_G` consumers, enabling universally forgeable Schnorr/FROST signatures - (File: crypto/dkg/src/lib.rs, crypto/ciphersuite/src/lib.rs)

### Summary
The external report concerns `pub_of_octets` accepting the encoding of the point at infinity as a public key, making signatures forgeable without a private key. Serai has the identical bug class. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91`) validates only canonical encoding and subgroup membership — it never rejects `G::identity()`. The FROST `Curve::read_G` wrapper (`crypto/frost/src/curve/mod.rs:125`) *does* reject identity ("identity point"), proving the authors know the check is required — but every deserialization path that goes through `Ciphersuite::read_G` directly (which is all of the DKG, PedPoP, promote, schnorr, and generic ciphersuite `read_G` callers listed in scope) accepts the identity point as a "public key".

### Finding Description
`Ciphersuite::read_G` decodes a point, checks it is in the prime-order subgroup and canonically encoded, and returns it — identity included:

```rust
// crypto/ciphersuite/src/lib.rs:91-101
fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
  ...
  let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
    .ok_or_else(|| io::Error::other("invalid point"))?;
  if point.to_bytes().as_ref() != encoding.as_ref() { Err(...) }
  Ok(point)   // identity is a valid, canonical, prime-order point
}
```

Reachable in-scope consumers that treat the decoded point as a verification key or share:

- `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:620-623`) reads `n` verification shares via `<C as Ciphersuite>::read_G`, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`). `new` computes `group_key` as the interpolated sum of `verification_shares[1..=t]` (`lib.rs:376-378`) with **no identity check on either the shares or the resulting `group_key`**.
- `SchnorrSignature::read`/`verify` (`crypto/schnorr/src/lib.rs:51-53`, `108-110`) verifies `R + c·A − s·G == 0`. When the public key `A` is the identity, `c·A` vanishes for *every* challenge `c`, so `(R, s)` verifies iff `R = s·G` — trivially forgeable for any message/challenge.
- `PedPoP Commitments::read` (`crypto/dkg/pedpop/src/lib.rs:109-128`) reads `t` commitment points via `C::read_G` with no identity rejection; the Schnorr PoK embedded in `Commitments` verifies against `commitments[0]` — an identity `commitments[0]` makes the PoK forgeable and injects a zero constant term into the key-generation polynomial.
- `EncryptedMessage::read` (`crypto/dkg/pedpop/src/encryption.rs:171-177`) reads `key` via `C::read_G`; `decrypt`/`decrypt_with_proof` verify the per-message `pop` signature against that key (`encryption.rs:374-378`). An identity `key` accepts a forged PoP, defeating the exact defense the PoP was added for (comments at `encryption.rs:84-90`).
- `EncryptionKeyMessage::read` (`encryption.rs:57-59`) accepts an identity encryption key; every `ecdh(private, identity)` then yields the fixed, publicly-known point `identity`, so ciphertexts to that key use a publicly derivable ChaCha20 keystream (`cipher`, `encryption.rs:101-133`) — shares "encrypted" to it are readable by anyone.

### Impact Explanation
A crafted `ThresholdKeys` serialization (or a DKG transcript in which the interpolated verification shares sum to identity) yields `group_key() == G::identity()` — `group_key()` returns `core.group_key * scalar + G*offset` (`dkg/src/lib.rs:445-447`), which is identity whenever `core.group_key` is identity and `offset == 0`. Under FROST/Schnorr verification, the group key is the public key `A` in `R + c·A − s·G == 0` (`schnorr/src/lib.rs:88-100`); with `A = identity` any `(R = s·G, s)` pair verifies for every message, so an unprivileged party can produce valid signatures for the group key without any secret share — a complete forgery identical in shape to the reported ECDSA bug (the "s=1" repro maps to `R = s·G` here). For PedPoP, identity `commitments[0]`/identity `msg.key` bypass the knowledge-of-secret and anti-key-reuse proofs respectively, and identity encryption keys leak every share encrypted to them (key-share disclosure).

### Likelihood Explanation
All of these paths are reached purely by untrusted bytes fed to listed read APIs (`ThresholdKeys::read`, `Commitments::read`, `EncryptedMessage::read`, `EncryptionKeyMessage::read`) — `C::read_G` succeeds on the canonical identity encoding (`0x01`/`0x00…` for Ristretto/Ed25519-type suites, `0x00` SEC1-style encodings for kp256 suites). Forging under an identity key requires only choosing `s` and setting `R = s·G`; the challenge value is irrelevant. The one caveat: reaching `ThresholdKeys::read` with attacker-controlled bytes requires the caller to deserialize key material from an untrusted source, and forcing a zero sum via the DKG requires controlling the polynomial commitments — but the missing validation itself is unconditional, and the PedPoP identity-commitment path is reachable from a single protocol message.

### Recommendation
Reject the identity point in `Ciphersuite::read_G` (mirroring `Curve::read_G` at `crypto/frost/src/curve/mod.rs:125-131`), or at minimum reject identity in `ThresholdKeys::new` (each verification share and the computed `group_key`), in `Commitments::read`, `EncryptedMessage::read`, `EncryptionKeyMessage::read`, and `GeneratorProof::read`. Additionally, `ThresholdKeys::new` should assert `!group_key.is_identity()` after the interpolation sum at `crypto/dkg/src/lib.rs:376-378`.

### Proof of Concept
Conceptual (Serai, Ristretto):

```rust
// Ristretto identity encodes canonically as 32 zero bytes.
let id_bytes = [0u8; 32];

// 1) Accepted as a verification share / group-key contributor:
let share = <Ristretto as Ciphersuite>::read_G(&mut id_bytes.as_ref()).unwrap();
assert!(bool::from(share.is_identity())); // no rejection

// 2) ThresholdKeys::read accepts a serialization whose interpolated
//    verification shares sum to identity => group_key() == identity.
//    (construct t=1,n=1 keys with a single identity verification share)

// 3) Forged signature under the identity group key:
let s = Scalar::from(7u64);
let sig = SchnorrSignature::<Ristretto> { R: Ristretto::generator() * s, s };
let c = /* any challenge, e.g. hash binding key+R+msg */;
assert!(sig.verify(Ristretto::identity(), c)); // verifies for ANY message

// 4) PedPoP: EncryptedMessage { key: identity, pop: (R = sG, s), msg } passes
//    the PoP check in decrypt_with_proof without knowing a discrete log.
```

Uncertainty note: the strongest impact (forged FROST group signatures) depends on an attacker being able to install or trigger a `ThresholdKeys` with identity group key; the unconditional missing-validation itself is confirmed in the cited code, and the identical check in `Curve::read_G` confirms the codebase treats identity rejection as required.
