### Title
Attacker floods a Serai Bitcoin multisig address with barely-above-dust outputs that are credited as received funds but cost more to spend than their value - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The Bitcoin `Scanner` accepts every transaction output paying to a registered `script_pubkey`, and the processor's `get_outputs` filter only checks `output.balance().amount.0 >= N::DUST`, a fixed dust constant — not the economic cost of spending the output. An unprivileged party can therefore flood the multisig's deposit address with many outputs whose value is at or marginally above `N::DUST`. These outputs are reported to the coordinator as real, spendable `External`/`Branch` funds, yet each P2TR key-spend input costs ~57.5 vB in fees; at normal fee rates, spending such an output consumes more than it is worth. This is the in-scope analog of CVE-2021-38429: unauthenticated crafted traffic (on-chain transactions instead of network packets) that floods the victim and creates a denial-of-service / value-extraction condition.

### Finding Description
`Scanner::scan_transaction` matches solely on `output.script_pubkey` and pushes a `ReceivedOutput` for any value [1](#0-0) . `scan_block` scans every transaction, and the only maturity caveat is documented for the coinbase [2](#0-1) . The processor-side wrapper accepts any scanned output with `amount >= N::DUST` and pushes it into the outputs pipeline [3](#0-2) . These outputs are then saved and emitted as `ScannerEvent::Block` for scheduling [4](#0-3) .

On the spend side, `SignableTransaction`/`TransactionSignMachine` commit to all inputs with `Prevouts::All` and compute a fee of `vsize * FEE` with a single change output [5](#0-4) . There is no per-input economic check: each included input unconditionally adds its signature weight to the fee. The change math (`input_value - payments - fee`) is plain subtraction, so an input set dominated by dust-value outputs either produces a change output below the dust limit (silently burned as extra fee) or drives the subtraction to/through zero.

### Impact Explanation
An attacker who sends `k` outputs of value `v` (where `N::DUST <= v < ~57.5 vB * feerate`) to the published multisig address causes those outputs to be reported as received funds. Any plan that spends them loses `(input_fee - v)` per input; if the scheduler must consolidate them (e.g., during multisig rotation/forwarding via `PlanFromScanning::Forward` [6](#0-5) ), the loss is forced. Alternatively, `scan_block` credited funds that cannot actually be spent economically — "funds reported received that are not spendable". The attacker only pays `v` per output, which remains on-chain; the griefing cost is the resulting fee drain, matching the CVE's traffic-flooding DoS shape.

### Likelihood Explanation
Reachable by any unprivileged party: the multisig's `External` (and `Forwarded`/`Branch`) P2TR addresses are public, and depositing outputs to them requires no authentication. It requires the scheduler to actually include the dust outputs in a `SignableTransaction` (or for rotation forwarding to be triggered); whether the scheduler deduplicates/refuses uneconomical inputs was not fully verified — the in-scope wallet layer itself has no such check, so the finding holds at the scanning/reporting layer and where forced forwarding applies.

### Recommendation
Filter scanned outputs by economic spendability, not a static dust constant: compare `output.balance().amount` against `input_vsize * current_fee_rate` in `get_outputs`/`scan_transaction` before reporting them as received. Additionally, in `SignableTransaction::new`, drop change outputs that would fall below the dust limit and use checked arithmetic on the change computation so a deficit errors instead of underflowing or silently burning value as fee.

### Proof of Concept
1. Obtain the multisig's external P2TR address (public information derived from `p2tr_script_buf(group_key)`).
2. Broadcast one Bitcoin transaction creating, e.g., 100 outputs of `N::DUST` sats each to that address.
3. `Scanner::scan_transaction` returns 100 `ReceivedOutput`s; `get_outputs` keeps all of them since each `>= N::DUST`, and they are emitted via `ScannerEvent::Block`.
4. When the scheduler later consolidates or forwards these outputs, `SignableTransaction`/`TransactionSignMachine` must include all of them under `Prevouts::All`; at a fee rate where the per-input cost exceeds `N::DUST` sats, the transaction pays more in fees than the outputs contribute, or the change computation `input_value - payments - needed_fee` underflows/yields a below-dust change output, burning the difference as fee — a direct value loss / stall of the signing pipeline caused entirely by attacker-sent transactions.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
