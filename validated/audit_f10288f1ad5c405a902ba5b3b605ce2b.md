### Title
Spoofed `WWW-Authenticate` realm header lets a malicious git remote/proxy impersonate GitHub and trigger a misdirected sign-in/credential prompt - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
Desktop's git credential helper decides how to treat an authenticating host based in part on the `WWW-Authenticate` HTTP header returned by that host during a `git fetch`/`clone`/`push`. If the header's `realm` claims `"GitHub"`, Desktop unconditionally classifies the endpoint as `enterprise` and routes the user into the full "Sign in to GitHub Enterprise" UI flow for that (attacker-controlled) URL, rather than the neutral "generic git credentials" prompt. This is directly analogous to the reported Fraxlend bug: a value coming from an unverified conversion/response (`WWW-Authenticate` header vs. redeemed-share amount) is trusted as ground truth for a downstream security decision without independent verification, and the existing verification path (`isGitHubHost`, which makes an actual HEAD request and checks for the `x-github-request-id` response header) is bypassed entirely.

### Finding Description
In `getEndpointKind()` [1](#0-0) , Desktop attempts to classify a git remote host in order of a series of increasingly strong checks: `isGist`, `isDotCom`, `isGHE`. When none of these built-in checks match, Desktop falls back to a heuristic based on the credential's captured `wwwauth[...]` fields (the raw `WWW-Authenticate` header Git captured from the server's HTTP 401 response):

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```

This header value is fully attacker-controlled: it originates from whatever HTTP server (or man-in-the-middle proxy) is answering the `git fetch/clone/push` request for the remote URL the user is interacting with. Unlike the legitimate `isGitHubHost()` verification path [2](#0-1) , which performs an actual network probe against `/meta` and validates the presence of the `x-github-request-id` response header before concluding a host is GitHub, the `wwwauth[...]` realm check performs **no verification at all** - it simply trusts the string content of a header supplied by the same untrusted server that is asking to be authenticated.

Once `getEndpointKind()` returns `'enterprise'` and no matching stored account exists for that endpoint, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) , which in turn invokes `dispatcher.beginEnterpriseSignIn` and shows the full "Sign in to GitHub Enterprise" dialog scoped to the attacker's URL [4](#0-3) . This is a materially different (and more trusted-looking) UI/UX than the neutral `promptForGenericGitAuthentication` dialog that would otherwise be shown for an unknown/generic host [5](#0-4) .

The broken invariant: "an endpoint is classified as a genuine GitHub/GHE host" is supposed to be established either by (a) a fixed, hardcoded set of known Desktop endpoints (`isDotCom`/`isGHE`/`isGist`), or (b) an actively-verified network probe (`isGitHubHost`). The `wwwauth[...]` realm heuristic instead lets the server itself assert its own identity with an unverified string, exactly like the Fraxlend bug lets an unverified conversion result (redeemed lendingPair shares) stand in for a value that should have been independently computed/verified (`_borrowAmtNeededToSwap`) before being used in a security/financial-critical decision.

### Impact Explanation
A malicious git host, or a MITM/rogue proxy sitting in front of a legitimate-looking git remote the user is fetching/cloning/pushing to, can respond to Git's HTTP authentication challenge with `WWW-Authenticate: Basic realm="GitHub"`. This causes Desktop to present the "Sign in to GitHub Enterprise" experience pointed at the attacker's arbitrary URL instead of the more cautious generic-credentials prompt. This increases the chance a user will treat the prompt as a legitimate GitHub authentication event and proceed to authenticate (via username/password or by launching the OAuth browser flow) against a host they did not intend to trust as GitHub, potentially exposing enterprise or personal credentials/tokens to the attacker-controlled endpoint. This qualifies as unprivileged, attacker-triggered credential exfiltration/phishing surface reachable purely by the user fetching/cloning from (or being redirected/proxied through) a repository the attacker controls - no local access, malware, or unnatural user steps beyond normal git operations are required.

### Likelihood Explanation
Medium. The attacker precondition is simply controlling the HTTP responses for a git remote URL the victim clones/fetches/pushes to (a self-hosted "enterprise-like" git server, a compromised/malicious proxy, or a spoofed clone URL shared with the victim) - well within the "attacker controls ... a git remote/proxy response" class explicitly listed as valid impact. It requires the victim to be in a state without a matching stored Desktop account for that endpoint (common for a first-time clone of a "new enterprise" repo) and to proceed through the resulting sign-in prompt, which is a normal, expected interaction rather than an unnatural step.

### Recommendation
Do not use the unauthenticated `WWW-Authenticate` realm string alone to classify a host as GitHub/Enterprise. Either drop the `realm="GitHub"` heuristic entirely, or treat it only as a weak signal that must still be confirmed by the existing `isGitHubHost()` network verification (the same check already used for the final fallback case) before routing the user to the GitHub-branded sign-in flow instead of the generic credentials prompt.

### Proof of Concept
1. Attacker stands up an HTTP server (or MITM proxy) at `https://evil.example.com/repo.git` that responds to unauthenticated Git HTTP requests with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote in an existing repository, or clones it, inside GitHub Desktop (a normal, unprivileged action).
3. Git invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`) with the captured `wwwauth[...]` header value containing `realm="GitHub"`.
4. `getEndpointKind()` [6](#0-5)  returns `'enterprise'` without any network verification of `evil.example.com`.
5. Since no Desktop account matches `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, presenting the victim with the "Sign in to GitHub Enterprise" dialog scoped to the attacker's domain [4](#0-3) .
6. If the victim completes sign-in (basic auth or OAuth-style flow) believing they are authenticating to a legitimate GitHub Enterprise instance, their credentials/token are sent to the attacker's server.

Note: I was unable to fully trace whether Desktop's Enterprise sign-in flow always forces OAuth-only ("Continue with browser") versus also permitting direct username/password submission in all code paths, since the relevant UI component code was not found in the indexed portion of the repository. This does not change the core finding (unverified host classification leads to a misleading, GitHub-branded credential prompt for an attacker-controlled endpoint), but it may affect the precise mechanism of credential exposure (direct password submission vs. OAuth authorization against a spoofed domain) and should be verified against the full source in a Devin session, since index size limits may exclude some file contents.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'

/**
 * Attempts to determine whether or not the url belongs to a GitHub host.
 *
 * This is a best-effort attempt and may return `undefined` if encountering
 * an error making the discovery request
 */
export async function isGitHubHost(url: string) {
  const { hostname } = new window.URL(url)

  const endpoint =
    hostname === 'github.com' || hostname === 'api.github.com'
      ? getDotComAPIEndpoint()
      : getEnterpriseAPIURL(url)

  if (isDotCom(endpoint) || isGHE(endpoint)) {
    return true
  }

  if (isKnownThirdPartyHost(hostname)) {
    return false
  }

  // github.example.com,
  if (/(^|\.)(github)\./.test(hostname)) {
    return true
  }

  // bitbucket.example.com, etc
  if (/(^|\.)(bitbucket|gitlab)\./.test(hostname)) {
    return false
  }

  if (getEndpointVersion(endpoint) !== null) {
    return true
  }

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}

    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)

        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)

    })
