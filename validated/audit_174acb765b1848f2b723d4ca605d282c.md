### Title
Git Argument Injection via Unsanitized `remote.name` in `fetchTagsToPush` (and related push/fetch commands) - (File: `app/src/lib/git/tag.ts`)

### Summary
`fetchTagsToPush` builds a `git push` argv where the remote name is inserted as a raw positional argument, with no validation and no `--` end-of-options separator. Since `remote.name` originates from the repository's `.git/config` (which is part of "repository content" and can be attacker-crafted), a remote whose name begins with `-` will be interpreted by `git` as a command-line option rather than a remote/repository argument.

### Finding Description
`fetchTagsToPush` constructs the `push` argv directly from `remote.name`: [1](#0-0) 

`remote.name` is populated by `getRemotes()`, which parses the output of `git remote -v` with a permissive regex that captures whatever string git prints for the remote's name: [2](#0-1) 

Because this comes straight from a config subsection header (`[remote "<name>"]`), it can contain characters that would never survive `git remote add`'s own name validation — including a leading `-`/`--`. A repository can be cloned/opened with such a crafted `.git/config` without ever going through `addRemote()`. When Desktop later calls `fetchTagsToPush(repository, remote, branchName)`, `remote.name` is placed as the second element of `args`, immediately after `'push'` and before `branchName`, with no `--` separator to force git to treat it as a positional value: [3](#0-2) 

If `remote.name` is a string like `--upload-pack=<cmd>`, git will parse it as the `--upload-pack` option rather than the remote argument, shifting `branchName` into the "remote/repository" positional slot. `--upload-pack`/`--receive-pack` let the caller specify an arbitrary program that git invokes to "talk" to the target when the target resolves to a local path or certain transports — this is the same argument-injection primitive used in publicly known git-based RCE write-ups. The same unsanitized pattern (`remote.name` inserted as a bare positional arg, no `--`) exists in the sibling commands `push()` and `fetch()`/`fetchRefspec()`, so this is not unique to `tag.ts`: [4](#0-3) [5](#0-4) 

No validation of remote names (e.g., rejecting names starting with `-`) was found anywhere in the reviewed git-command wrappers or `IRemote` model.

### Impact Explanation
If exploitable, this allows argument/option injection into `git push`/`git fetch`, which — depending on the injected option (`--upload-pack=`, `--receive-pack=`, `--exec=`, `-o`/`--config`) and the resolved "repository" argument — can lead to local command execution when the user performs an otherwise-normal push/fetch/pull on a hostile repository. This would satisfy the "code execution" impact bar for this program.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires that the malicious remote name actually reach `fetchTagsToPush`/`push`/`fetch` as `remote.name`, which in turn requires the app to have enumerated it from `.git/config` via `getRemotes()`. I was not able to fully confirm within this review whether: (a) git's own `remote -v` output will faithfully echo a config subsection name beginning with `-`/`--` without mangling or erroring, and (b) whether any earlier stage of Desktop's onboarding/clone flow filters or refuses such remotes before they are surfaced in the UI/store. These are testable but require running actual `git` (config parsing/quirks) and exercising the full app flow, which is outside what static code reading in this session can settle with certainty.

### Recommendation
- Terminate the option list with `--` before any positional remote/branch/refspec arguments in `push()`, `fetch()`, `fetchRefspec()`, and `fetchTagsToPush()`, e.g. `['push', '--follow-tags', '--dry-run', '--no-verify', '--porcelain', '--', remote.name, branchName]`.
- Additionally validate `remote.name` (and any other remote-derived values that get positioned as argv, e.g. in `remote.ts`) against a strict allow-list (reject leading `-`) before ever using it in a `git` argv, regardless of where the name came from (added interactively vs. read from an on-disk config).

### Proof of Concept
1. Craft a repository whose `.git/config` contains a remote section with a hostile name, e.g.:
   ```
   [remote "--upload-pack=touch /tmp/pwned;true"]
       url = https://example.com/some/repo.git
       fetch = +refs/heads/*:refs/remotes/x/*
   ```
2. Have the victim open/clone this repository in GitHub Desktop so that `getRemotes()` surfaces the malicious name as `remote.name`.
3. Trigger any Desktop workflow that calls `fetchTagsToPush`/`push` with that remote (e.g. pushing a branch), producing an argv of the form `['push', '--upload-pack=touch /tmp/pwned;true', branchName, '--follow-tags', '--dry-run', ...]`.
4. Verify (once step (a)/(b) above are confirmed against real `git` and the app's remote-enumeration flow) that the injected option is parsed by git rather than treated as the remote name.

Note: This PoC's end-to-end exploitability (particularly whether `git remote -v`/config parsing preserves such a name, and whether Desktop's UI/store lets it flow unmodified into `fetchTagsToPush`) could not be fully validated through static code review alone in this session and should be confirmed by actually running the scenario.

```typescript
export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}
```
