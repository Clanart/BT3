### Title
Unchecked u64 accumulation of payment amounts overflows, bypassing the not-enough-funds check and producing an unspendable transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts into `payment_sat` and later computes `payment_sat + needed_fee` with plain `u64` arithmetic. With multiple large payments, the sum wraps modulo 2^64 (release) or panics (debug), defeating the `NotEnoughFunds` check at line 215 and yielding a transaction whose outputs exceed its inputs — an invalid, unbroadcastable transaction the FROST multisig still signs. This is the direct Serai analog of CVE-2018-5727: integer overflow over untrusted count/size data causing denial of service.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:187`, payment amounts are summed without checked arithmetic:

```rust
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
```

Each `payment.1` is a `u64` and is only validated against `DUST` (line 165–169); there is no `MAX_MONEY`/total-supply bound and no `checked_add`. The balance check at line 215 relies on this wrapped value:

```rust
if input_sat < (payment_sat + needed_fee) { Err(NotEnoughFunds) }
```

Both `payment_sat` itself and `payment_sat + needed_fee` can overflow. When `payment_sat` wraps to a small value:

1. The `NotEnoughFunds` guard is bypassed.
2. The change path at line 224–235 computes `input_sat.checked_sub(payment_sat + fee_with_change)` with the wrapped sum, so it produces a change output that implicitly claims nearly all inputs.
3. The resulting `Transaction` has outputs summing far above `input_sat` (the individual `TxOut` values retain their true ~2^62+ values). It is consensus/policy-invalid: `taproot_key_spend_signature_hash` still succeeds, all `AlgorithmSignMachine`s produce valid Schnorr shares, and `complete` assembles signatures for a transaction that will never relay or confirm.

Additionally, `fee()` at line 139 computes `sum(prevouts) - sum(outputs)` with a bare subtraction; for a transaction built this way it underflows and panics, and in debug builds the `payment_sat + needed_fee` addition panics outright — both denial-of-service paths reachable purely from `payments`, which encode user withdrawal requests (transaction data an unprivileged party causes to be signed).

### Impact Explanation
A crafted set of payments causes the threshold signing pipeline to consume preprocesses and signature shares to produce a transaction that is permanently unbroadcastable: inputs are effectively locked against that plan and the session must be torn down/blamed. In debug builds (and on the `fee()` path in any build) the overflow/underflow is a hard panic — a crash of the signing task. This is a real denial of service triggered by attacker-supplied amounts, matching the CVE class (overflow in size arithmetic → DoS), with the added consequence that honest signers expend one-use FROST nonces on an invalid message.

### Likelihood Explanation
Reachability requires `payments` totalling ≥ 2^64 sat — economically absurd as real value, but nothing in `SignableTransaction::new` constrains amounts to `MAX_MONEY` (21M BTC); the only per-payment check is `>= DUST`. Any integrator path that forwards untrusted payment vectors without an upper bound exposes this. Because the failure is a deterministic arithmetic wrap/panic triggered by input values alone, likelihood is conditional on callers trusting payment magnitudes — hence Medium rather than High.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:

- Accumulate `payment_sat` and `input_sat` with `checked_add`/`try_fold`, rejecting on overflow.
- Compute `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Bound each payment by `bitcoin::Amount::MAX_MONEY` (or `MAX` as appropriate) in addition to the `DUST` lower bound.
- Make `fee()` use `checked_sub` and return `Result`/`Option` instead of panicking.

### Proof of Concept
Conceptual, against `SignableTransaction::new`:

```rust
// inputs: a single ReceivedOutput worth, say, 1_000_000 sats
let payments: Vec<(ScriptBuf, u64)> = vec![
    (spk_a.clone(), u64::MAX - 1000),   // passes `>= DUST`
    (spk_b.clone(), u64::MAX - 1000),   // payment_sat wraps to ~u64::MAX - 2001
    (spk_c.clone(), 10_000),            // sum wraps to a small value
];
// payment_sat = (2*(u64::MAX-1000) + 10_000) mod 2^64 = 8000 - 2 = small
// check: input_sat (1_000_000) < payment_sat + needed_fee (~8_000 + fee) → false → no error
SignableTransaction::new(inputs, &payments, Some(change_spk), None, fee_per_vbyte)?;
// Result: tx whose outputs sum to ~2^65 sats against 1_000_000 sats of inputs.
// multisig() → sign() → complete() all succeed; the signed tx is invalid and unbroadcastable.
// tx.fee() underflows (1_000_000 - huge) → panic.
```
