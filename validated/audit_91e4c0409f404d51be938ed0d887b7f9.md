### Title
OP_RETURN transaction data is excluded from Bitcoin fee and weight accounting - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Medium: `SignableTransaction::new` accepts up to 80 bytes of caller-controlled OP_RETURN data and appends it to the signed transaction, but estimates transaction weight, virtual size, required fee, and the standardness check using only `payments` and optional change. [1](#0-0) [2](#0-1) 

### Finding Description
`SignableTransaction::new` converts `data` into an additional zero-value `TxOut` at `tx_outs` construction time. [3](#0-2)  However, `calculate_weight_vbytes` receives only `inputs`, `payments`, and optional change, then constructs its estimate transaction solely from those payment outputs. [4](#0-3)  Both the no-change and with-change estimates therefore omit the already-created OP_RETURN output. [5](#0-4)  The omitted output is nevertheless included in the final `SignableTransaction` and in the transaction whose Taproot sighashes are signed. [2](#0-1) [6](#0-5) 

For 80 bytes of data, the serialized OP_RETURN script is 83 bytes and the containing `TxOut` is 92 bytes, contributing 368 weight units that are absent from both `weight` and `vbytes`. [7](#0-6) [3](#0-2)  The discrepancy can increase by another two non-witness bytes when adding the OP_RETURN output crosses the CompactSize output-count boundary at 253 outputs. [8](#0-7) 

### Impact Explanation
An unprivileged party supplying transaction data can cause Serai to create and sign a transaction whose actual fee rate is lower than the requested `fee_per_vbyte`, because `needed_fee` is calculated from an underestimated virtual size. [9](#0-8)  The `MAX_STANDARD_TX_WEIGHT` check also operates on the underestimated weight, so a crafted transaction near the policy boundary can become non-standard only after the unaccounted OP_RETURN output is added. [10](#0-9)  The resulting signed transaction can be rejected by standard relay policy or remain unconfirmed despite the wallet believing it paid the requested or minimum relay fee. [11](#0-10) 

This maps the PostgreSQL encoding-growth class onto Serai’s concrete data path: a bounded attacker-controlled input is validated independently, then expands the serialized transaction after the sizing and policy calculations have already been performed. [1](#0-0) 

### Likelihood Explanation
The discrepancy is deterministic for every non-empty `data` value because the data output is never represented in either call to `calculate_weight_vbytes`. [12](#0-11) [13](#0-12)  Any caller able to cause a Bitcoin transaction containing OP_RETURN data to be constructed can trigger underpricing without needing malformed cryptographic encodings, compromised peers, or an invalid curve input. [14](#0-13)  Producing a relay-visible failure requires choosing `fee_per_vbyte`, output count, or input count so that the omitted approximately 92 vbytes crosses a policy boundary. [15](#0-14) 

### Recommendation
Calculate weight and virtual size from the exact candidate output vector rather than reconstructing outputs only from `payments`. [4](#0-3)  Refactor `calculate_weight_vbytes` to accept `&[TxOut]` containing payments, the OP_RETURN output when present, and the candidate change output when applicable. [16](#0-15)  Recompute both `fee` and `tx.weight()` after assembling the final transaction, and add boundary tests for an 80-byte OP_RETURN output and for crossing the 253-output CompactSize boundary. [17](#0-16) 

### Proof of Concept
The size discrepancy can be demonstrated arithmetically from the code path:

```rust
let data = vec![0u8; 80];

// Added to the real transaction:
// value(8) + script_len(1) + OP_RETURN(1) + PUSHDATA1(1) + len(1) + data(80)
let omitted_txout_bytes = 8 + 1 + 1 + 1 + 1 + data.len(); // 92
let omitted_weight = omitted_txout_bytes * 4;             // 368 WU

// calculate_weight_vbytes is called with payments only:
let (_, estimated_vbytes) =
    SignableTransaction::calculate_weight_vbytes(inputs, payments, None);

// The final transaction contains payments + OP_RETURN.
// Actual vbytes = estimated_vbytes + 92.
```

With `fee_per_vbyte == 1`, `needed_fee` equals only the estimated virtual size, while the broadcast transaction is approximately 92 vbytes larger and therefore pays less than one sat/vbyte. [18](#0-17)  Likewise, if the estimated transaction weight is `MAX_STANDARD_TX_WEIGHT - 368`, the check succeeds even though adding the permitted 80-byte data output produces a transaction at the standard-policy limit; a slightly higher baseline produces a signed transaction above it. [19](#0-18)

    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();
