[1](#0-0) ### Title
Unbounded aggregate-signature deserialization enables memory exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts an attacker-controlled 32-bit element count and decodes that many group elements into an in-memory vector without a protocol-level or absolute size limit. [1](#0-0) 

### Finding Description
The first four serialized bytes are interpreted as a little-endian `u32`, and the implementation loops that many times while pushing each decoded `C::G` into `Rs`. [2](#0-1) 

Each element is read by `C::read_G`, so repeated canonical encodings such as the generator encoding are sufficient; the elements do not need to represent valid signatures. [3](#0-2) 

The only consistency check between the aggregate and its expected verification inputs occurs later in `verify`, after deserialization has already allocated and populated the attacker-sized vector. [4](#0-3) 

### Impact Explanation
An unprivileged party supplying serialized aggregate-signature bytes can announce up to 4,294,967,295 elements and keep feeding valid point encodings, causing memory usage to grow with every accepted element and keeping the verifier occupied while the stream continues. [5](#0-4) 

If the resulting aggregate reaches `verify`, the implementation additionally allocates `2 * keys_and_challenges.len() + 1` multiexp pairs and performs hashing plus group operations proportional to the attacker-controlled input size. [6](#0-5) 

This is a concrete remote availability failure when aggregate signatures are accepted from untrusted peers before authentication or size enforcement. [1](#0-0) 

### Likelihood Explanation
The attacker only needs control over the serialized aggregate input and the ability to stream enough canonical point bytes; no private key, valid signature, malformed encoding, or collusion is required. [1](#0-0) 

The attack is practical whenever the surrounding protocol does not impose a sufficiently small maximum serialized length or expected signature count before calling `read`. [1](#0-0) 

### Recommendation
Change `SchnorrAggregate::read` to accept a caller-provided `expected_count` or `max_signatures`, reject encoded counts above that bound before entering the loop, and enforce a serialized-byte limit at the protocol boundary. [1](#0-0) 

The `verify` length check should remain as defense in depth, but it cannot be the primary mitigation because it runs only after the oversized `Rs` vector has already been constructed. [4](#0-3) 

### Proof of Concept
This representative Rust reader emits the attacker-controlled `u32::MAX` count followed by an endless sequence of canonical Ed25519 generator encodings, causing `SchnorrAggregate::read` to continue decoding and growing `Rs` until memory or the caller is exhausted. [1](#0-0) 

```rust
use std::io::{self, Read};

use ciphersuite::{Ciphersuite, group::GroupEncoding};
use dalek_ff_group::Ed25519;
use schnorr::aggregate::SchnorrAggregate;

struct EndlessAggregate {
  header: [u8; 4],
  header_pos: usize,
  point_pos: usize,
}

impl EndlessAggregate {
  fn new() -> Self {
    Self { header: u32::MAX.to_le_bytes(), header_pos: 0, point_pos: 0 }
  }
}

impl Read for EndlessAggregate {
  fn read(&mut self, out: &mut [u8]) -> io::Result<usize> {
    let point = <Ed25519 as Ciphersuite>::generator().to_bytes();
    let point = point.as_ref();
    let mut written = 0;

    while written < out.len() {
      if self.header_pos < self.header.len() {
        out[written] = self.header[self.header_pos];
        self.header_pos += 1;
      } else {
        out[written] = point[self.point_pos];
        self.point_pos = (self.point_pos + 1) % point.len();
      }
      written += 1;
    }

    Ok(written)
  }
}

let mut bytes = EndlessAggregate::new();
let _aggregate = SchnorrAggregate::<Ed25519>::read(&mut bytes);
```
