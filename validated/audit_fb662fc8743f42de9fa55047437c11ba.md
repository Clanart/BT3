## Analog Found

### Title
Permanent freezing of matured unbonding delegations when `CompleteUnbonding` fails during `EndBlock` - (File: `sei-cosmos/x/staking/keeper/val_state_change.go`)

### Summary
The staking module's `BlockValidatorUpdates` EndBlock routine dequeues all matured unbonding delegations from the `UBDQueue` and then calls `CompleteUnbonding` for each one. If `CompleteUnbonding` returns an error, the code simply `continue`s without re-inserting the entry into the queue, permanently stranding the delegator's principal, mirroring the EigenLayer "queued withdrawal" DoS pattern where a revert on completion permanently blocks pending funds.

### Finding Description
`Undelegate` records a pending withdrawal by writing an `UnbondingDelegation` entry and inserting a `DVPair` into the `UBDQueue` for the maturity timestamp [1](#0-0) . This is exactly analogous to EigenLayer's `queueWithdrawal`, which similarly marks a withdrawal pending and stores its hash for later completion.

At `EndBlock`, `BlockValidatorUpdates` dequeues *all* matured `DVPair`s via `DequeueAllMatureUBDQueue` (which deletes the timeslice from the store) and then attempts to complete each one by calling `k.CompleteUnbonding`: [2](#0-1) 

`CompleteUnbonding` performs the fund transfer via `k.bankKeeper.UndelegateCoinsFromModuleToAccount`, returning an error if the transfer fails: [3](#0-2) 

Crucially, once `DequeueAllMatureUBDQueue` has already removed the timeslice entry from `UBDQueue`, that `DVPair` will never be examined again by any subsequent `EndBlock`. If `CompleteUnbonding` errors for any reason (e.g., the bank keeper's recipient check rejects the delegator address), the `continue` statement drops the pair with no re-queuing mechanism, while the `UnbondingDelegation` object itself remains in state (since `RemoveUnbondingDelegation`/`SetUnbondingDelegation` is only reached inside `CompleteUnbonding`, which already returned before reaching that code on error). This is confirmed directly by the repository's own regression test, `TestEndBlockRetainsUnbondingForInvalidRecipient`, which sets up a delegator address whose recipient check (`CanSendTo`) fails, runs `EndBlocker`, and asserts that: the pool balance is unchanged, the delegator's balance is still zero, the `UnbondingDelegation` record is *retained* in state, and the `UBDQueueIterator` for that maturity time is now empty (i.e., it will never be processed again): [4](#0-3) 

The recipient check that can cause this failure is `BaseSendKeeper.CanSendTo`, which runs a list of pluggable `recipientCheckers` (e.g., EVM address-association validators) — any one of which returning `false` blocks the transfer: [5](#0-4) 

This is the same root cause class as the EigenLayer bug: a batch/queued completion step that, upon a single failure, is dequeued/marked-processed without a compensating retry path, permanently freezing the user's principal that was already debited from the bonded/not-bonded pool accounting.

### Impact Explanation
Any delegator whose account trips a bank `recipientChecker` (for example, becoming associated with an EVM address in a state the checker rejects, as exercised by the shipped unit test) at the exact moment their unbonding delegation matures will have that unbonding entry **permanently stuck**: the principal is never returned to their balance, and because the timeslice was already deleted from `UBDQueue`, no future `EndBlock` will ever retry the transfer. This is a permanent freezing of user funds reachable purely by a normal `MsgUndelegate` transaction (or the staking precompile's `undelegate` call) followed by ordinary chain progression to the maturity block — no malicious validator, governance action, or privileged actor is required.

### Likelihood Explanation
The likelihood depends on how easily a legitimate delegator address can end up failing `CanSendTo` at maturity time (e.g., transient/derived EVM-association states). The codebase's own test demonstrates this is a reachable state for the address checkers currently registered, and the fact that engineers wrote a dedicated regression test for "EndBlock retains unbonding for invalid recipient" indicates this was a real, previously-encountered condition rather than a purely theoretical one. The window is any block where an unbonding delegation matures while the delegator address is in a check-failing state.

### Recommendation
When `CompleteUnbonding` (or the analogous redelegation path) fails during `BlockValidatorUpdates`, re-insert the `DVPair`/entry back into the `UBDQueue` for retry on a subsequent block (or a dedicated retry queue) instead of silently dropping it after `continue`. Alternatively, provide an explicit, permissionless "claim"/"redirect withdrawal address" recovery path so a delegator whose default address becomes unpayable can still retrieve funds, similar in spirit to indices-to-skip in the EigenLayer mitigation.

### Proof of Concept
The existing repository test is itself the proof of concept: it inserts a matured `UnbondingDelegation`/`UBDQueue` entry for a delegator address that fails `CanSendTo`, runs `staking.EndBlocker`, and asserts the unbonding delegation is retained in state while the maturity timeslice has already been dequeued (`iterator.Valid()` is `false`), demonstrating that this specific entry can never be completed by any future `EndBlock`: [4](#0-3)

func TestEndBlockRetainsUnbondingForInvalidRecipient(t *testing.T) {
	_, app, ctx := createTestInput(t)
	maturity := time.Unix(1, 0).UTC()
	ctx = ctx.WithBlockTime(maturity)
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	delegator := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, delegator, evmAddr)
	app.EvmKeeper.SetAddressMapping(
		ctx,
		sdk.AccAddress(common.HexToAddress("0x4444444444444444444444444444444444444444").Bytes()),
		evmAddr,
	)
	validator := sdk.ValAddress(seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(10000))[0])
	amount := sdk.NewInt(40)
	bondDenom := app.StakingKeeper.BondDenom(ctx)
	notBondedPool := app.StakingKeeper.GetNotBondedPool(ctx)
	coins := sdk.NewCoins(sdk.NewCoin(bondDenom, amount))

	require.NoError(t, apptesting.FundModuleAccount(
		app.BankKeeper,
		ctx,
		notBondedPool.GetName(),
		coins,
	))

	unbonding := types.NewUnbondingDelegation(delegator, validator, 0, maturity, amount)
	app.StakingKeeper.SetUnbondingDelegation(ctx, unbonding)
	app.StakingKeeper.InsertUBDQueue(ctx, unbonding, maturity)
	require.False(t, app.BankKeeper.CanSendTo(ctx, delegator))

	poolBalanceBefore := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.NotPanics(t, func() {
		staking.EndBlocker(ctx, app.StakingKeeper)
	})

	poolBalanceAfter := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.Equal(t, poolBalanceBefore, poolBalanceAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, delegator, bondDenom).IsZero())
	retained, found := app.StakingKeeper.GetUnbondingDelegation(ctx, delegator, validator)
	require.True(t, found)
	require.Equal(t, unbonding, retained)

	iterator := app.StakingKeeper.UBDQueueIterator(ctx, maturity)
	require.False(t, iterator.Valid())
	require.NoError(t, iterator.Close())
}

func (k BaseSendKeeper) RegisterRecipientChecker(rc RecipientChecker) {
	*k.recipientCheckers = append(*k.recipientCheckers, rc)
}

func (k BaseSendKeeper) CanSendTo(ctx sdk.Context, recipient sdk.AccAddress) bool {
	for _, rc := range *k.recipientCheckers {
		if !rc(ctx, recipient) {
			return false
		}
	}
	return true
}
