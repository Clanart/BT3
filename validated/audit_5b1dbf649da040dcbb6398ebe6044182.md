### Title
SignableTransaction undercounts weight/vbytes when an OP_RETURN data output is present, producing a transaction that pays below the minimum relay fee and cannot be broadcast - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output to `tx_outs` when `data` is specified, but computes the transaction's weight and vbytes via `calculate_weight_vbytes`, which only includes `payments` (and optionally `change`) — never the data output. The fee and the `TooLowFee`/`TooLargeTransaction` checks are therefore computed against a smaller transaction than the one actually signed, so a transaction carrying data can be produced that pays less than `DEFAULT_MIN_RELAY_TX_FEE` (or exceeds `MAX_STANDARD_TX_WEIGHT`) and will be rejected by the Bitcoin mempool — the signed transaction is unbroadcastable and the funds it would move are stuck at their inputs until an entirely new transaction is constructed and re-signed.

### Finding Description
`calculate_weight_vbytes` builds a template transaction whose outputs are derived only from `payments`, plus an optional `change` output: [1](#0-0) 

However, `SignableTransaction::new` pushes the `OP_RETURN` output into `tx_outs` *before* fee estimation, and then calls `calculate_weight_vbytes` with `payments` — which does not include the data output: [2](#0-1) 

Both fee computations (`needed_fee` at line 206 and `fee_with_change` at line 227) reuse the same `payments`-only estimator, and the `TooLowFee` check at line 211 compares the underestimated fee against a minimum computed from the same underestimated `vbytes`, so it cannot detect the shortfall. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the same underestimated `weight`. The final signed transaction (including the OP_RETURN output) can therefore be larger than what the fee was computed for by up to ~90+ vbytes.

This mirrors the reported bug class: the contract/transaction pipeline accepts and commits funds to a form from which they cannot be moved as intended. Here, the multisig signs a concrete transaction (`Prevouts::All` commits to the exact prevouts) that fails standard relay policy, leaving the transferred funds unable to reach their destination.

### Impact Explanation
Any caller that attaches `data` (up to the 80-byte limit) while specifying a fee rate at or near the minimum relay rate will produce a transaction whose *actual* fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`. Bitcoin nodes will reject it from the mempool (`mempool rejection: min relay fee not met`), so the transaction can never confirm. Because the sighash commits to all inputs and outputs, the inputs cannot be spent by this transaction and a corrected transaction requires a fresh signing round — funds are effectively stuck in the wallet's UTXOs for the duration. Similarly, a near-limit transaction with data can silently exceed `MAX_STANDARD_TX_WEIGHT` despite passing the internal check, again yielding an unbroadcastable transaction.

### Likelihood Explanation
The trigger requires only that `data` be specified to `SignableTransaction::new` — a public input supported by the API (`data: Option<Vec<u8>>`), used to embed instructions/metadata — combined with a low specified `fee_per_vbyte`. Any party able to cause a withdrawal/transaction to carry OP_RETURN data (e.g., deposit/transfer instructions echoed into `data`) while the operator uses a minimal fee rate can produce an unbroadcastable signed transaction. No key material or validator collusion is needed.

### Recommendation
Include the data output in the weight/vbytes estimation: either push the `OP_RETURN` `TxOut` into the template built by `calculate_weight_vbytes`, or pass `tx_outs` (the post-data output list) instead of `payments` to both `calculate_weight_vbytes` calls at `networks/bitcoin/src/wallet/send.rs:204` and `send.rs:226`. Alternatively, compute the fee against the fully assembled transaction's actual `weight()`/`vsize()` before finalizing `SignableTransaction`.

### Proof of Concept
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

1. Call with `payments = [(addr, 1000)]`, `change = None`, `data = Some(vec![0u8; 80])`, `fee_per_vbyte = 1` (the minimum relay rate).
2. `tx_outs` gains an `OP_RETURN` output of ~92 serialized bytes, but `calculate_weight_vbytes` only accounts for the single payment output, so `vbytes` is short by the full size of the data output (~80+ vbytes once weight is considered).
3. `needed_fee = 1 * vbytes` passes the `TooLowFee` check because the minimum is computed from the same underestimated `vbytes` (line 211).
4. After signing via `TransactionMachine`, `tx.fee() / tx.vsize()` < 1 sat/vB. Broadcasting the resulting transaction via `send_raw_transaction` is rejected by Bitcoin Core with a min-relay-fee error — the signed transaction cannot move the funds, exactly as with ether locked in `MarginTrading`: value was committed to a form it cannot leave.
