## Title
Floating-point precision loss in Tower BFT stake-ratio threshold checks can silently corrupt vote-lockout, switch-fork, and duplicate-confirmation decisions - ([File: core/src/consensus.rs, core/src/consensus/vote_stake_tracker.rs, ledger/src/blockstore_processor.rs, core/src/repair/repair_weight.rs])

### Summary
The classic (non-Alpenglow) Tower BFT consensus code computes stake-ratio thresholds by dividing `u64` lamport stake values as `f64` (`fork_stake as f64 / total_stake as f64`), then compares against a threshold constant (`SWITCH_FORK_THRESHOLD`, `VOTE_THRESHOLD_SIZE`, `DUPLICATE_THRESHOLD`, `SUPERMINORITY_THRESHOLD`). `f64` can only represent integers exactly up to 2^53 (~9.007×10^15); Solana lamport stake totals routinely exceed this (total network stake is on the order of hundreds of millions of SOL × 1e9 lamports/SOL, i.e. > 10^17). This is the same class of precision-loss bug described in the Suzaku report — a numeric division that silently truncates/rounds a value that is then compared against a pass/fail threshold, and the truncated remainder is unrecoverable.

### Finding Description
Multiple threshold checks in the pre-Alpenglow ("Tower") consensus path perform naive `f64` division of `u64` stake values instead of exact integer/fixed-point arithmetic:

- `check_vote_stake_threshold` computes `let lockout = *fork_stake as f64 / total_stake as f64;` then compares `lockout > threshold_size` [1](#0-0) 
- `make_check_switch_threshold_decision` computes `(locked_out_stake as f64 / total_stake as f64) > SWITCH_FORK_THRESHOLD` twice [2](#0-1) 
- `VoteStakeTracker::add_vote_pubkey` computes `let threshold_stake = (total_stake as f64 * threshold) as u64;` [3](#0-2) 
- `supermajority_root` (used for computing the supermajority-confirmed root during blockstore replay) computes `total as f64 / total_epoch_stake as f64 > VOTE_THRESHOLD_SIZE` [4](#0-3) 
- `get_popular_pruned_forks` computes `((min_total_stake as f64) * DUPLICATE_THRESHOLD) as u64` for duplicate-confirmation detection during repair [5](#0-4) 
- `update_slot_propagated_threshold_from_votes` compares `propagated_validators_stake as f64 / total_epoch_stake as f64 > SUPERMINORITY_THRESHOLD` [6](#0-5) 

Critically, the codebase itself demonstrates and acknowledges this exact class of bug: `votor-messages/src/fraction.rs` introduces an exact-integer `Fraction` type specifically to avoid `f64` rounding, with a regression test proving the failure mode:

```rust
let total_stake = NonZeroU64::new(100_000_000_000_000_000).unwrap();
let stake = 60_000_000_000_000_001u64; // 60% + 1
let f64_ratio = stake as f64 / total_stake.get() as f64;
assert!(f64_ratio <= 0.6); // wrong!
assert!(Fraction::new(stake, total_stake) > Fraction::from_percentage(60));
``` [7](#0-6) 

This proves that for realistic mainnet-scale stake magnitudes, `f64` division can incorrectly report a stake ratio as being *below* a threshold when it is mathematically *above* it (or vice versa). The `Fraction` type was adopted for the new votor/Alpenglow consensus pool threshold checks (`is_safe_to_notar`, `is_safe_to_skip`) [8](#0-7)  and even partially in `core/src/consensus.rs` for `GENESIS_VOTE_THRESHOLD` [9](#0-8) , but the classic Tower BFT threshold checks (`check_vote_stake_threshold`, `check_switch_threshold`, `VoteStakeTracker`, `supermajority_root`, repair's duplicate-threshold, and leader-propagation superminority check) were never migrated and still use raw `f64` comparisons.

Unlike the Suzaku bug (which loses time silently with no downstream detection), this is not attacker-exploitable in the sense of an adversary crafting a single malicious value — it is a systemic, deterministic rounding error present in every validator's computation because all validators compute the same `f64` operations on the same inputs (IEEE-754 division is deterministic). That means all validators can be *uniformly and consistently wrong* about whether a threshold has been crossed, since the corrupted value (the `f64` ratio) is the same everywhere.

### Impact Explanation
Because the error is uniform across all validators (same inputs → same IEEE-754 result), it does not by itself cause validators to diverge from one another (no fork-inducing consensus split). However, it can cause the *entire network* to systematically miscompute whether a stake threshold (switch-fork proof, vote-lockout threshold, duplicate-confirmation threshold, or superminority propagation threshold) has been reached, at stake magnitudes that are entirely realistic on mainnet (> 2^53 lamports, i.e. > ~9 million SOL of total stake, far below current total delegated stake). A systematic false-negative on `check_switch_threshold` can prevent validators from generating a legitimate switching proof; the code explicitly warns this failure mode can stall the network:

> "Imagine 90% of validators voted on slot 4, but only 9% landed. If everybody that fails the switch threshold abandons slot 4 to build on slot 8 ... then there will be no blocks to include the votes for slot 4, and the network halts because 90% of validators can't vote" [10](#0-9) 

Similarly, a false result from `supermajority_root` affects root advancement (`wait_for_supermajority` / boot-time root discovery) and duplicate-confirmation detection in repair (`get_popular_pruned_forks`), both of which gate liveness-critical decisions. This falls under the accepted impact category of "consensus halt" / "false rooting" via a non-malicious-actor, non-RPC path.

### Likelihood Explanation
Likelihood is low-to-moderate. In practice, `f64`'s relative precision error is ~2.22×10⁻¹⁶, so for a decision to actually flip, the true stake ratio would need to sit within that razor-thin margin of the threshold boundary — an event whose probability under organically-evolving stake distributions is very small, though not zero given continuously changing delegations, tens of millions of lamports of "noise" at mainnet stake scale, and threshold checks re-evaluated on every slot/vote. It requires no malicious behavior, single-node compromise, or privileged access — simply naturally occurring stake amounts near a threshold boundary, which is a legitimate/unprivileged network condition. Existing guards (integer stake arithmetic, checked math) do not protect this specific comparison because the conversion to `f64` happens immediately before the comparison, discarding the exact-integer representation that was otherwise carefully maintained throughout the surrounding stake-accounting code.

### Recommendation
Replace all remaining `f64`-based stake-ratio threshold comparisons in the classic Tower BFT path with the exact-integer `Fraction` type (or equivalent `u128` cross-multiplication) that has already been adopted for votor/Alpenglow and for `GENESIS_VOTE_THRESHOLD`:
- `check_vote_stake_threshold` / `check_switch_threshold` / `make_check_switch_threshold_decision` in `core/src/consensus.rs`
- `VoteStakeTracker::add_vote_pubkey` in `core/src/consensus/vote_stake_tracker.rs`
- `supermajority_root` in `ledger/src/blockstore_processor.rs`
- `get_popular_pruned_forks` (`DUPLICATE_THRESHOLD`) in `core/src/repair/repair_weight.rs`
- `update_slot_propagated_threshold_from_votes` (`SUPERMINORITY_THRESHOLD`) in `core/src/replay_stage.rs`

Comparisons should be done via cross-multiplication (`stake * denominator_threshold` vs `total_stake * numerator_threshold` in `u128`) rather than converting to `f64`.

### Proof of Concept
Using the existing test already present in the repo, adapted to the Tower BFT threshold pattern:
```rust
// core/src/consensus.rs pattern: lockout = fork_stake as f64 / total_stake as f64; lockout > threshold_size
let total_stake: u64 = 100_000_000_000_000_000; // ~100M SOL in lamports, realistic mainnet-scale
let fork_stake: u64 = 38_000_000_000_000_001;    // SWITCH_FORK_THRESHOLD (0.38) + 1 lamport

let lockout = fork_stake as f64 / total_stake as f64;
assert!(lockout <= 0.38); // WRONG: fork_stake is mathematically > 38% of total_stake by 1 lamport,
                          // but f64 rounding reports it as not exceeding the threshold.
```
This mirrors the codebase's own `test_f64_precision_loss` in `votor-messages/src/fraction.rs` [7](#0-6) , which was written precisely because this rounding behavior was identified as incorrect for the new consensus path — but the equivalent fix was never backported to `check_vote_stake_threshold` / `check_switch_threshold` in the classic Tower BFT code that remains active in this codebase [11](#0-10) .

**Note on confidence**: I could not fully verify, within the available tool budget, the exact current mainnet magnitude of `total_stake`/`total_epoch_stake` values passed into these functions, nor whether any downstream mitigation (e.g., pre-rounding stake to a coarser granularity before comparison) exists elsewhere in the call chain. I also could not confirm whether the classic Tower path is still reachable in produced/active clusters versus only exercised in tests, given this repo appears to include in-progress Alpenglow migration code. These are areas a deeper/live investigation (e.g., via a Devin session with full repo and build access) would need to confirm before treating this as a fully confirmed exploitable defect rather than a systemic precision-hygiene issue.

fn supermajority_root(roots: &[(Slot, u64)], total_epoch_stake: u64) -> Option<Slot> {
    if roots.is_empty() {
        return None;
    }

    // Find latest root
    let mut total = 0;
    let mut prev_root = roots[0].0;
    for (root, stake) in roots.iter() {
        assert!(*root <= prev_root);
        total += stake;
        if total as f64 / total_epoch_stake as f64 > VOTE_THRESHOLD_SIZE {
            return Some(*root);
        }
        prev_root = *root;
    }

    None
}
