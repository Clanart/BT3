### Title
SignableTransaction computes the fee and weight limit over a transaction that omits the OP_RETURN data output, undercharging fees and bypassing the standard-weight check - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` validates the minimum-relay fee and the `MAX_STANDARD_TX_WEIGHT` limit against a vbyte/weight measurement of a transaction that never includes the OP_RETURN output carrying user-supplied `data`. The actual signed transaction does contain that output, so the checked quantities (fee paid, weight) are measured against a smaller transaction than the one produced — the same class as the reference bug, where a limit denominated in one quantity (assets) is compared against a different, systematically smaller quantity (shares).

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the flow is:

1. The OP_RETURN output is pushed to `tx_outs` when `data` is provided (lines 193–202).
2. `(weight, vbytes)` are computed via `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), where `payments` is the caller-supplied `&[(ScriptBuf, u64)]` slice — which does **not** include the data output or its up-to-80-byte payload.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (line 211) use this underestimated `vbytes`.
4. The change-branch recomputation `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226) still omits the data output.
5. The `weight > MAX_STANDARD_TX_WEIGHT` check (line 241) uses the underestimated `weight`.
6. The final `Transaction` is built with `output: tx_outs`, which *does* include the OP_RETURN output (line 250).

So every limit check is evaluated on a phantom transaction missing `data.len() + overhead` bytes (OP_RETURN prefix + pushdata opcode + up to 80 bytes of data + the 9-byte output header). Since the fee actually paid equals `needed_fee` (change absorbs `input - payment - fee_with_change`), the real transaction systematically pays `fee_per_vbyte * (real_vbytes - vbytes)` less than the intended rate.

### Impact Explanation
- Any caller attaching `data` produces a transaction paying below the requested `fee_per_vbyte` rate; with `fee_per_vbyte` at/below ~1–3 sat/vB the missing ~90–110 vbytes can push the real fee rate under `DEFAULT_MIN_RELAY_TX_FEE`, yielding a non-relayable transaction even though the `TooLowFee` check passed.
- With `data` and enough inputs, the real transaction can exceed `MAX_STANDARD_TX_WEIGHT` while the check at line 241 passes, producing a transaction no standard node will relay — outputs committed to it are unspendable via that tx.
This is reachable purely from public inputs (`data` is caller-supplied transaction data), requires no keys or validator collusion, and the failure is silent (the constructed tx is signed and broadcast-ready but rejected by the network).

### Likelihood Explanation
Triggered whenever `data.is_some()`. In serai's usage OP_RETURN data outputs are used for protocol metadata (e.g., `TransactionMachine` signable transactions), so this is not an exotic path — any data-carrying spend underestimates size by a fixed ~90+ vbytes. The severity of the fee shortfall scales with how low `fee_per_vbyte` is; at minimum relay rates the tx is non-standard. The weight-limit bypass requires many inputs plus data, which is plausible for a consolidator spending many `ReceivedOutput`s.

### Recommendation
Include the data output in the size measurement. Either pass the full output list to `calculate_weight_vbytes` (e.g., construct a `Vec<TxOut>`/script list including the OP_RETURN script before measuring), or add `tx_outs`'s serialized size to the computed weight:

```rust
// after pushing the OP_RETURN output, measure with it included
let outputs_for_measure: Vec<(ScriptBuf, u64)> = payments
    .iter()
    .cloned()
    .chain(data_out_script.clone().map(|s| (s, 0)))
    .collect();
let (weight, vbytes) =
    Self::calculate_weight_vbytes(tx_ins.len(), &outputs_for_measure, change.as_ref());
```

Apply the same corrected measurement to the change-branch recomputation and to the `MAX_STANDARD_TX_WEIGHT` comparison.

### Proof of Concept
```rust
// Conceptual: fee_per_vbyte = 1 (satisfies TooLowFee only because vbytes is underestimated)
let data = vec![0u8; 80];
let stx = SignableTransaction::new(
    inputs,                 // e.g., one P2TR ReceivedOutput
    &[(payment_script, payment_amt)],
    Some(change_script),
    Some(data),             // ~89 extra bytes in the real tx
    1,
).unwrap();

// stx.needed_fee() == 1 * vbytes(payments-only tx)
// real tx is ~89+ bytes larger, so real fee rate < 1 sat/vB < DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB)
// => signed tx fails relay despite passing the TooLowFee check

// With ~360+ inputs and Some(data), real weight > MAX_STANDARD_TX_WEIGHT
// while `weight` (computed without the OP_RETURN output) may stay under the limit.
```

Root cause location: `networks/bitcoin/src/wallet/send.rs` lines 193–204, 224–234, and 241 — `calculate_weight_vbytes` is always called with `payments` (no data output) while the built transaction includes it.
