### Title
Unbounded recursive CLVM-to-Python conversion during wallet memo computation can crash transaction processing on deeply nested spend output - (`chia/wallet/util/compute_memos.py`)

### Summary
`compute_memos_for_spend()` runs an attacker-influenced puzzle/solution pair and then recursively walks the resulting CLVM condition tree via `Program.as_python()` with no depth limit, unlike the codebase's other tree-walking primitive (`sha256_treehash`) which is deliberately implemented iteratively to avoid Python recursion-limit crashes on deeply nested CLVM structures.

### Finding Description
`compute_memos_for_spend()` executes the coin's puzzle reveal against its solution and then iterates `result.as_python()` to look for `CREATE_COIN` conditions and their memo lists: [1](#0-0) 

`result` is the `Program` returned by CLVM execution of an attacker/counterparty-controlled puzzle and solution — a full node/wallet has no control over how deeply nested the *output* of that execution is; a puzzle can be trivially built to return an arbitrarily deep nested list as its condition output (e.g., `(a (a (a ... ())))`), which will be present in the executed result even though the total CLVM cost stays low, because deep nesting of small conses is cheap in cost terms while still being expensive to convert into Python objects.

`Program.as_python()` (inherited from the underlying s-expression library) walks this tree and materializes it into nested Python lists/tuples. This is the same bug class as the reported jackson-databind issue: a deeply nested tree structure is walked recursively when converting to a "flat"/materialized representation, and sufficiently deep nesting exhausts the call stack (`RecursionError` / interpreter stack overflow) rather than failing gracefully.

This contrasts directly with the codebase's own documented mitigation pattern for this exact class of bug: `sha256_treehash()` is explicitly implemented as an iterative stack-machine specifically "so we don't have to worry about blowing out the python stack" on deeply nested CLVM: [2](#0-1) [3](#0-2) 

`compute_memos_for_spend()`/`compute_memos()` have no equivalent protection, and are called from wallet transaction-processing paths (`chia/wallet/wallet_state_manager.py`, `chia/wallet/clawback_manager.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`, `chia/wallet/wallet_rpc_api.py`) whenever a wallet observes/processes a spend bundle containing a coin it cares about.

### Impact Explanation
Because `compute_memos` is invoked while a wallet processes incoming/observed spend bundles (coin state updates), an attacker who crafts a coin spend whose puzzle emits a deeply nested condition/memo output can trigger a Python-level `RecursionError` during `as_python()` conversion. This aborts the calling coroutine partway through wallet state processing for that transaction, which is a spend-triggered transaction-processing halt — the wallet fails to finish handling the transaction/coin update instead of cleanly rejecting or skipping it, denying service to the wallet's synchronization/transaction pipeline.

### Likelihood Explanation
Any unprivileged party who can get a coin spend observed by a wallet — e.g., by sending a coin to that wallet's puzzle hash, or via an offer/trade counterparty spend — can control the puzzle reveal and solution and thus the shape of the executed output that reaches `as_python()`. Building deeply nested (thousands of levels) but cheap CLVM output is straightforward and does not require large cost or size, since CLVM cons cells are inexpensive; this makes the trigger low-cost and easy to construct, similar to the 2kB/1000-level nested-array PoC in the referenced jackson-databind advisory.

### Recommendation
Replace the recursive materialization of the executed CLVM result in `compute_memos_for_spend()` with an iterative tree walk (mirroring the pattern already used in `sha256_treehash()`), or bound recursion depth explicitly and reject/skip conditions that exceed a sane nesting depth before calling `as_python()`. Alternatively, wrap the `as_python()` call and treat `RecursionError` as a non-fatal, per-spend failure so a single malicious/oddly-shaped spend cannot abort broader wallet transaction processing.

### Proof of Concept
Conceptually:
1. Construct a puzzle that, given any solution, returns a condition list where one condition's trailing element is a deeply right-nested cons chain (e.g., `(51 ph amount (a1 (a2 (a3 ... nil))))`) many thousands of levels deep — cheap in CLVM cost since it is just small conses.
2. Spend a coin with that puzzle/solution as part of an ordinary spend bundle sent to or observed by a victim wallet (e.g., paid to the victim's address, or included in an offer).
3. When the victim wallet processes the resulting coin/transaction update, `compute_memos_for_spend()` calls `result.as_python()` on the deeply nested output, causing a Python recursion/stack failure that aborts memo computation for that transaction, per `chia/wallet/util/compute_memos.py:14-25`. def compute_memos_for_spend(coin_spend: CoinSpend) -> dict[bytes32, list[bytes]]:
    _, result = run_with_cost(coin_spend.puzzle_reveal, INFINITE_COST, coin_spend.solution)
    memos: dict[bytes32, list[bytes]] = {}
    for condition in result.as_python():
        if condition[0] == ConditionOpcode.CREATE_COIN and len(condition) >= 4:
            # If only 3 elements (opcode + 2 args), there is no memo, this is ph, amount
            coin_added = Coin(coin_spend.coin.name(), bytes32(condition[1]), uint64(int_from_bytes(condition[2])))
            if type(condition[3]) is not list:
                # If it's not a list, it's not the correct format
                continue
            memos[coin_added.name()] = [mem for mem in condition[3] if isinstance(mem, bytes)]
    return memos
