### Title
`ThresholdKeys::read` trusts a self-declared participant index and verification-share map, letting supplied key bytes adopt any participant identity and an attacker-defined group key - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2016-2860 is an identity-mishandling bug: OpenAFS's `newEntry` trusted the caller-asserted creator ID instead of deriving it from the authenticated principal, letting an authenticated-but-unprivileged user create groups "as" an administrator. The Serai analog is in `ThresholdKeys::read` / `ThresholdKeys::new`: deserialization accepts a fully self-asserted `Participant` index `i`, an arbitrary `secret_share`, and an arbitrary `verification_shares` map, and `ThresholdKeys::new` never checks that `C::generator() * secret_share == verification_shares[i]` nor anchors the group key to anything outside the supplied bytes. The resulting `group_key` is computed purely from the first `t` attacker-controlled verification shares.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation variant, the secret share, and `n` verification shares entirely from the input bytes, then calls `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` only checks the count of verification shares and that no index exceeds `n`; it never verifies that the claimed identity `params.i()` actually owns the supplied `secret_share` (i.e., `verification_shares[i] == generator() * secret_share`), and it derives `group_key` as an interpolation over `verification_shares[1..=t]` taken verbatim from the input [2](#0-1) . Like the OpenAFS creator ID, the participant identity and the "group" (the group key) are self-asserted by whoever supplies the byte stream, not bound to any authenticated source. Downstream, `group_key()` is returned directly by `ThresholdView` and used for `rho` binding and signature verification [3](#0-2) , and in bitcoin-serai the group key determines the output descriptors/`Scanner` matching.

### Impact Explanation
An unprivileged party who can get a node to load supplied `ThresholdKeys` bytes (key migration, recovery, or any peer/tool-delivered key blob — `ThresholdKeys::read` is an in-scope untrusted-bytes entry point) can make that node adopt:

- An arbitrary participant index `i` it does not own — the same "asserted creator ID" primitive as the CVE.
- An attacker-defined `group_key` derived from attacker-chosen verification shares. Any wallet/scanner logic that treats `keys.group_key()` as the multisig's key will report funds received at outputs controlled by the *attacker's* key material — funds reported received that the validator set cannot spend — or cause the node to sign sessions whose signatures only verify under the attacker's fabricated key.
- False blame: signing with an `i`/`secret_share`/`verification_shares` triple that is internally inconsistent produces shares that fail `verify_share` in `complete()`, and the failure is attributed by participant index [4](#0-3) . The code itself acknowledges semantically-invalid deserialized keys are reachable (`InternalError("...deserialize a semantically invalid FrostKeys")`).

### Likelihood Explanation
Medium. Exploitation requires feeding crafted serialized keys to a node rather than just a protocol message, so it is weaker than a pure on-wire attack, but `ThresholdKeys::read` performs no semantic binding (no `secret_share ↔ verification_shares[i]` check, no group-key commitment), making any recovery/backup/tooling path that accepts key bytes a concrete trigger. The construction is trivial — the attacker picks `i`, picks any `secret_share`, and supplies verification shares of their own key shares.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject keys that fail. Additionally, bind accepted keys to an externally committed roster/group-key fingerprint (e.g., require the caller to supply the expected `group_key` and compare), so a deserialized key cannot silently redefine which group the node acts for.

### Proof of Concept
```rust
// crypto/dkg context: craft serialized ThresholdKeys claiming identity i
// with an attacker-defined group key.
let attacker_scalar = C::F::random(&mut OsRng);
let attacker_share_point = C::generator() * attacker_scalar;

let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());            // t = 1
buf.extend(1u16.to_le_bytes());            // n = 1
buf.extend(1u16.to_le_bytes());            // i = Participant(1): self-asserted index
buf.push(1);                               // Interpolation::Lagrange
buf.extend(C::F::ZERO.to_repr().as_ref()); // secret_share = 0 (does NOT match share point)
buf.extend(attacker_share_point.to_bytes().as_ref()); // verification_shares[1]

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
// keys.group_key() == attacker_share_point, fully attacker-controlled,
// and params().i() == 1 despite secret_share * G != verification_shares[1].
assert_eq!(keys.group_key(), attacker_share_point);
assert_eq!(keys.params().i(), Participant::new(1).unwrap());
// Any consumer using keys.group_key() as the multisig identity (e.g., bitcoin
// Scanner descriptor) now tracks an attacker-owned key, and signing sessions
// built on these keys emit shares inconsistent with the claimed identity.
```
