### Title
Non-diff-based ledger accounting in MasterMagpie deposit/withdraw breaks for rebasable staking tokens, enabling insolvency on withdrawal - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie._deposit` and `_withdraw` maintain a strict 1:1 internal ledger (`user.amount`, `user.available`) against the exact `_amount` parameter passed in, rather than measuring the contract's actual token balance delta. Unlike other contracts in the same codebase (e.g. `wombat/WombatStaking.sol` and the various `WombatPoolHelper*` contracts), which correctly compute received amounts via `balanceOf` diffing before/after a transfer, `MasterMagpie` simply trusts `_amount` as ground truth for both crediting deposits and debiting withdrawals.

### Finding Description
In `_deposit`: [1](#0-0) 
`user.amount` and `user.available` are incremented by the nominal `_amount`, and `safeTransferFrom` pulls exactly `_amount` of `pool.stakingToken`. In `_withdraw`/`_harvestAndUnstake`: [2](#0-1) 
`user.amount`/`user.available` are decremented by `_amount` and the contract transfers out exactly `_amount` via `safeTransfer`.

This design assumes the staking token's balance held by `MasterMagpie` always equals the sum of all users' recorded `amount`. For any staking token whose balance can change independently of transfers in/out of this specific contract — i.e., a rebasing token (positive or negative rebase) — this invariant breaks: the sum of `user.amount` ledger entries can exceed (after a negative rebase/slashing) or diverge from `IERC20(stakingToken).balanceOf(address(this))`. This mirrors exactly the reported bug class in `LOB`/`OnchainLOB.sol`, where recorded balances are not reconciled against actual token balance/total supply.

Other pool-facing contracts in this repo (`wombat/WombatStaking.sol` deposit/withdraw, `wombat/WombatPoolHelper.sol`, `WombatPoolHelperV2.sol`, `AnkrBNBPoolHelper.sol`) explicitly guard against this class of issue by using before/after balance diffs: [3](#0-2) 
`MasterMagpie`, which is the central accounting hub reached by every staking/locking/reward pathway (`WombatPoolHelper`, `AnkrBNBPoolHelper`, `SmartWomConvert`, `VLMGP`, `mWomSV`, `ManualCompound` all call into `depositFor`/`withdrawFor`), does not apply the same protection.

### Impact Explanation
If any pool's `stakingToken` registered in `MasterMagpie` is a rebasing or balance-adjusting token (or is itself an LP/receipt token wrapping a rebasing underlying), a negative rebase after deposits are recorded would leave the aggregate `user.amount` ledger higher than the actual token balance held by `MasterMagpie`. Later withdrawers calling `withdraw`/`withdrawFor` would have their `safeTransfer(address(msg.sender), _amount)` revert due to insufficient balance, permanently freezing funds for the affected users (protocol insolvency / permanent freeze of user funds), matching the accepted impact categories (protocol insolvency, permanent freezing of funds).

### Likelihood Explanation
Likelihood depends on whether any current or future `stakingToken` registered via `MasterMagpie.add()`-style pool creation is a rebasing token or an LP/receipt token that itself is subject to rebase-driven balance changes (e.g., `WombatStaking` receipt tokens wrapping Wombat LP assets that can themselves rebase from underlying pool cash/liability rebalancing, or any future integration of a rebasing reward/staking asset). Given the protocol's core design principle of using diff-based accounting everywhere else (`WombatStaking`, pool helpers) to guard against exactly this class of discrepancy, `MasterMagpie`'s ledger-only approach is an inconsistent gap that would manifest as soon as a non-standard/rebasing token is onboarded as a staking token, which is an ordinary-wallet-reachable path (deposit then withdraw) requiring no privileged action.

### Recommendation
Adopt the same before/after balance-diffing pattern used elsewhere in the codebase (see `WombatStaking.deposit`/`depositLP`) for `MasterMagpie._deposit`, crediting `user.amount`/`user.available` with the actual received balance delta rather than the nominal `_amount`. For withdrawals, either cap `_amount` transferred to the contract's actual current `stakingToken` balance proportionally, or explicitly disallow onboarding of rebasing/balance-mutable tokens as `stakingToken` in pool configuration, and document/enforce this restriction at pool-add time.

### Proof of Concept
1. Governance/owner adds a pool to `MasterMagpie` with a rebasing ERC20 as `stakingToken` (no privileged-admin exploit needed thereafter — this step only establishes the precondition, not the attack itself).
2. User A deposits 1000 tokens via `depositFor` → `_deposit` credits `user.amount[A] = 1000` and pulls 1000 tokens into `MasterMagpie` [1](#0-0) .
3. User B deposits 1000 tokens similarly → `user.amount[B] = 1000`, contract balance now 2000.
4. A negative rebase occurs on the token, reducing `MasterMagpie`'s actual balance to 1500, while `user.amount[A] + user.amount[B]` ledger still totals 2000.
5. User A withdraws in full: `_withdraw` calls `safeTransfer(A, 1000)` [4](#0-3) , succeeding since balance (1500) ≥ 1000, leaving only 500 for User B.
6. User B attempts to withdraw their recorded 1000: `safeTransfer(B, 1000)` reverts because actual balance is only 500, permanently freezing User B's recorded funds despite `user.amount[B]` showing 1000 owed.
