### Title
Stale working-directory diff reused after status refresh can cause line-selection commits to be built from mismatched diff content - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateChangedFiles` decides whether to reuse a previously loaded diff purely by comparing the selected file's `id` before and after a `git status` refresh, not by validating that the file's underlying content/blob is unchanged. When it is not reused it just becomes `null`, but when the same file id is still selected across a refresh, the *old* diff object (with its old hunk boundaries/line numbers) is kept in state and displayed while the working tree content may have already changed, e.g. from an external process, a smudge/clean filter, or a hook that Desktop itself invokes (`GITHUB_DESKTOP=1` hook execution described in `app/src/lib/hooks/hooks-proxy.ts`).

### Finding Description
`updateChangedFiles` computes: [1](#0-0) 
The reuse condition only checks `selectedFileIDs[0] === selectedFileIDs[0]` (same file id, single selection) — it does not compare any content signature (blob SHA, mtime, or file size) between the old and new `WorkingDirectoryStatus`. `WorkingDirectoryFileChange.id` is derived from the file path (and status kind), so a file whose *content* changes between two `git status` polls, but whose *path* stays the same, is treated as "the same file" and its previously fetched diff is kept alive in `ChangesWorkingDirectorySelection.diff`.

Separately, `updateChangesWorkingDirectoryDiff` in `app-store.ts` re-fetches the diff asynchronously and guards against a *selection* change race using `arrayEquals` on `selectedFileIDs`, again not validating diff content identity: [2](#0-1) 

When the user then edits line selections and commits, `applyPatchToIndex` re-fetches a *fresh* diff via `getWorkingDirectoryDiff` to build the patch: [3](#0-2) 
but the `DiffSelection` bit-set the user edited was built against line indices from whichever diff was rendered in the UI at interaction time. If that rendered diff was stale (kept alive by the `updateChangedFiles` reuse path) while the actual working tree/hunks have since shifted (lines added/removed upstream of the hunk the user touched by e.g. a hook or filter running between polls), `DiffSelection.isSelected(absoluteIndex)` in `formatPatch` (`app/src/lib/patch-formatter.ts:157`) applies the user's selected line indices to the *new* hunk layout, not the one they visually reviewed.

### Impact Explanation
This breaks the invariant "what the user visually approves in the diff view is what gets committed/pushed." An attacker who can influence file content between Desktop's periodic status polls and diff refresh (via a crafted git hook, smudge/merge driver, or race with a background tool the repo is configured to run) can cause Desktop to silently stage/commit different line content than what the user selected, without any error being surfaced — matching the report's "silent corruption of what the user commits" impact bucket.

### Likelihood Explanation
This requires a specific timing window: content must change between two status refreshes while the same file id remains selected, and the user must interact with line-level (partial) selection during that window. This is a real but narrow race condition; I could not confirm from the index whether `WorkingDirectoryFileChange.id` incorporates anything beyond path/status (I was unable to fully verify the `id` getter/constructor before running out of tool calls), which is necessary to be certain the reuse-guard is bypassable purely through content changes with a stable path. This uncertainty should be resolved by inspecting `app/src/models/status.ts`'s `WorkingDirectoryFileChange` class definition (id computation) in a follow-up session.

### Recommendation
- Invalidate the cached `diff` in `updateChangedFiles`/`updateChangesWorkingDirectoryDiff` whenever the underlying file's content signature (e.g., git status's reported blob OIDs, or mtime/size) differs from what was used to produce the cached diff, not just when the file id/selection changes.
- Before calling `formatPatch`/`applyPatchToIndex`, re-validate that the `DiffSelection` being applied was derived from a diff whose hunk layout matches the diff just fetched for patch generation; if not, refuse to stage/commit and force a UI refresh.

### Proof of Concept
Due to index limitations I could not fully trace `WorkingDirectoryFileChange`'s `id` implementation to build a fully verified reproduction; a Devin session with full repo access is recommended to confirm whether `id` is content-independent and to build a concrete end-to-end repro (e.g., a repository with a `post-checkout`/merge driver that rewrites a tracked file's content between two `git status --porcelain=2` polls while Desktop has that file selected with a partial line selection in progress).
