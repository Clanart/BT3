### Title
`WombatStaking.depositLP()` mints receipt tokens 1:1 against the nominal input amount instead of the amount actually received/staked, causing insolvency/DoS - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.deposit()` correctly measures the actual LP tokens obtained from the underlying Wombat pool by comparing balances before and after the external call, and only mints the receipt token for that verified amount. `WombatStaking.depositLP()`, which handles the "already-have-LP" deposit path used by all pool helpers, does not apply this same safety pattern: it mints the receipt token for the exact `_lpAmount` argument supplied by the caller, without verifying that this same amount was actually transferred in and successfully staked.

### Finding Description
In `deposit()`, the contract explicitly guards against amount mismatches between the nominal deposited amount and the actual LP received: [1](#0-0) 

In contrast, `depositLP()` transfers `_lpAmount` from the caller, immediately routes that nominal amount to `_toMasterWomAndSendReward()`, and mints the receipt token for the same nominal `_lpAmount`, without ever checking what the contract's LP balance actually increased by: [2](#0-1) 

This is the same root-cause pattern as the Tapioca finding: a function assumes that the amount passed in/transferred is exactly the amount that ends up custodied/staked, and mints a claim token (receipt token, analogous to the minted mtOFT) based on that unchecked assumption rather than the actually-realized amount. If the LP token behaves in any way where the transferred-in amount differs from what is retained/stakeable (fee-on-transfer, rebasing, or a deposit-time deduction on the underlying Wombat asset/staking call within `_toMasterWomAndSendReward`), the receipt token minted to the pool helper (and subsequently to the end user via `IMasterMagpie.depositFor`) will not be backed 1:1 by the LP actually held/staked by `WombatStaking`.

All `PoolHelper` contracts (`WombatPoolHelper.sol`, `WombatPoolHelperV2.sol`, `AnkrBNBPoolHelper.sol`) call `depositLP()` on behalf of ordinary users and blindly forward whatever balance they observe, so they cannot detect or correct this mismatch: [3](#0-2) 

### Impact Explanation
Because receipt tokens are minted for the nominal `_lpAmount` rather than the amount actually custodied/staked, the accounting invariant "total receipt token supply == LP actually held/staked by WombatStaking" can be broken. This can manifest as:
- Reverting deposits/withdrawals (DoS) if the internal staking call in `_toMasterWomAndSendReward()` attempts to approve/stake more LP than the contract actually holds.
- Under-collateralization of receipt tokens: later users who try to `withdraw()` (which burns receipt tokens and pulls real LP from the underlying Wombat pool via `masterWombat`) may find the pool short of real LP, permanently freezing the funds of the last withdrawer(s) in that pool — a protocol insolvency scenario, consistent with the "permanent freezing of funds" impact bar.

### Likelihood Explanation
This path is reachable directly by any ordinary wallet through the public `depositLP()` functions on `WombatPoolHelper`/`WombatPoolHelperV2`/`AnkrBNBPoolHelper`, requiring no privileged role. The likelihood that it manifests depends on whether any onboarded pool's LP asset or the underlying staking call can produce a transferred/staked amount smaller than the nominal amount; the same class of risk was severe enough that the developers already patched exactly this scenario for the sibling `deposit()` function, indicating this is a known, real-world category of behavior for these tokens/pools rather than a purely theoretical one.

### Recommendation
Apply the same before/after balance-diff pattern used in `deposit()` to `depositLP()`: measure the actual increase in `poolInfo.lpAddress` balance (and/or the actual amount successfully staked via `_toMasterWomAndSendReward`) and mint the receipt token only for that verified amount, e.g.:
```solidity
uint256 beforeBalance = IERC20(poolInfo.lpAddress).balanceOf(address(this));
IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);
uint256 lpReceived = IERC20(poolInfo.lpAddress).balanceOf(address(this)) - beforeBalance;
_toMasterWomAndSendReward(_lpAddress, lpReceived, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived);
```

### Proof of Concept
1. A pool is configured in `WombatStaking` whose `lpAddress` (or the staking step performed inside `_toMasterWomAndSendReward`) can yield an actual custodied/staked amount smaller than the nominal `_lpAmount` passed by the caller.
2. A user calls `WombatPoolHelper.depositLP(_lpAmount)`, which calls `IWombatStaking(wombatStaking).depositLP(lpToken, _lpAmount, msg.sender)`.
3. Inside `depositLP()`, `WombatStaking` transfers in and stakes `_lpAmount` nominally, but the real balance retained/staked is `_lpAmount - delta`, yet mints `_lpAmount` receipt tokens to the caller: [4](#0-3) 
4. Receipt token supply now exceeds the real LP backing held by `WombatStaking` for that pool.
5. When users later call `withdraw()`, which burns receipt tokens 1:1 and pulls the corresponding real LP amount from `masterWombat`/the Wombat pool, the last withdrawer(s) for that pool cannot be fully repaid because the underlying LP has been exhausted, permanently freezing their funds.
