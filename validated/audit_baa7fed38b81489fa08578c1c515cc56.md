### Title
Secret-share decryption and blame-key disclosure occur before the per-message proof-of-possession is verified — ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` decrypts each `EncryptedMessage` and interprets the plaintext as a scalar share *before* the queued batch verification of the message's proof-of-possession (PoP) runs. If the decrypted bytes fail `C::F::from_repr`, the function returns early with `PedPoPError::InvalidShare { blame: Some(..) }`, skipping `batch.verify_with_vartime_blame()` entirely. The returned blame is an `EncryptionKeyProof` containing the ECDH shared key for the attacker's message — a message whose `msg.key` was never authenticated. This re-enables exactly the attack the PoP exists to prevent: an attacker who copies the per-message encryption key `X` from a victim's encrypted share can coerce the recipient into publishing `b·X`, revealing the victim's secret share ciphertext.

### Finding Description
In `calculate_share`, each peer's `EncryptedMessage` is passed to `Encryption::decrypt`, which only *queues* the PoP Schnorr signature into a `BatchVerifier` and then immediately applies the ChaCha20 keystream, returning both the decrypted bytes and an `EncryptionKeyProof` (the ECDH shared key `enc_key * msg.key`) [1](#0-0) .

Back in `calculate_share`, the decrypted bytes are converted with `C::F::from_repr`; on failure the function returns `PedPoPError::InvalidShare` carrying `blame: Some(blame)` — before `batch.verify_with_vartime_blame()` at line 493 is ever reached [2](#0-1) . The PoP is therefore never checked on this error path, and the blame proof is emitted anyway.

The code comments explicitly describe the threat this ordering reintroduces: an observer who reuses another party's per-message key `X` would cause the recipient to "create a blame argument against Eve… they'd reveal bX, revealing Alice's message to Bob" — which is why the PoP was added [3](#0-2) . The spec documents the same mitigation [4](#0-3) .

This is the direct analog of the TLS bug class: a record's payload is processed (decrypted, decoded, and a key-revealing blame artifact produced) before the authentication/encryption-level boundary (the PoP verification) for that record has been crossed.

### Impact Explanation
An unprivileged participant (or network-local observer who saw the victim's round-2 ciphertext, which includes `X` in plaintext) constructs an `EncryptedMessage` with `key = X`, an arbitrary parseable `pop` signature (it will not verify, but it is never verified on this path), and a ciphertext of the correct length. With overwhelming probability the keystream output of `cipher(context, enc_key·X)` is a non-canonical scalar encoding (for Ristretto255/ed25519 only ~1/16 of 32-byte strings are canonical; the attacker can simply repeat with slightly modified ciphertexts). The victim's `calculate_share` returns `InvalidShare` with `blame = Some(EncryptionKeyProof { key: enc_key·X, dleq })`. When this blame is broadcast (e.g., via `ProcessorMessage::InvalidShare` in `processor/src/key_gen.rs` lines 419–425), everyone learns `b·X` and can decrypt the victim's originally sent share ciphertext via `decrypt_with_proof` [5](#0-4) . A participant's secret share for the DKG is disclosed, breaking DKG confidentiality and enabling key-share recovery by anyone who collects enough material.

### Likelihood Explanation
Reachable by any unauthenticated party able to send bytes to `EncryptedMessage::read`/`calculate_share` during the share-collection round — a public-input path explicitly in scope. The trigger requires no valid PoP, no knowledge of any secret, and succeeds with probability ≈ 1 − (field order / 2^256…repr space) per attempt; it is deterministic in structure and only probabilistic in whether one particular ciphertext decodes non-canonically. Repeatable until success since each round-2 message is independently processed.

### Recommendation
Verify the PoP *before* decrypting and before returning any blame material. Concretely: in `Encryption::decrypt`, either perform `msg.pop.verify(...)` synchronously and refuse to produce the `EncryptionKeyProof` on failure, or in `calculate_share` run the `BatchId::Decryption` checks (or a standalone PoP check) to completion before calling `C::F::from_repr` and before attaching `blame`. At minimum, the early `from_repr` error path must first drain/verify the queued PoP statement so a blame proof is never issued for an unauthenticated `msg.key`.

### Proof of Concept
1. Victim A runs `generate_secret_shares`, producing `EncryptedMessage { key: X, pop: valid_pop_for_X, msg: C_A→B }` for recipient B.
2. Attacker E observes (or is sent) A's ciphertext and copies `X`. E builds `EncryptedMessage { key: X, pop: SchnorrSignature{ R: arbitrary_point, s: arbitrary_scalar }, msg: C' }` where `C'` is any `SecretShare`-sized string. E does not know `dlog(X)`, so `pop` cannot be valid — but it is only queued, not checked.
3. E sends this to B as E's share. B's `calculate_share` calls `encryption.decrypt`, computing `share_bytes = C' XOR keystream(enc_key_B·X)` and generating `EncryptionKeyProof{ key: enc_key_B·X }`.
4. With ~15/16 probability (Ristretto), `share_bytes` is a non-canonical `Scalar` repr → `from_repr` fails → function returns `InvalidShare{ blame: Some(proof) }` before `batch.verify_with_vartime_blame()` runs; the invalid PoP is never evaluated.
5. B's processor broadcasts `blame.serialize()`. Any observer runs `Decryption::decrypt_with_proof(sender=A, recipient=B, msg=A's original ciphertext, proof)`; the DLEq verifies (it genuinely proves `enc_key_B·X`), yielding the keystream that decrypts A's secret share to B — share disclosed without B ever validating E's PoP.

While key reuse by a participant is considered as them revealing the messages
themselves, and therefore out of scope, there is an attack where a malicious
adversary claims another participant's encryption key. They'll fail to encrypt
their message, and the recipient will issue a blame statement. This blame
statement, intended to reveal the malicious adversary, also reveals the message
by the participant whose keys were co-opted. To resolve this, a
proof-of-possession is also included with encrypted messages, ensuring only
those actually with per-message keys can claim to use them.
