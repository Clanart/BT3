Based on my research, I found a genuine analog in the deep-link "Open in Desktop" file-path validation logic, which shares the same bug class as the Sherlock report: a boundary/containment check that is subtly incomplete (a missing "correct term" in the comparison), letting a value slip past a guard that looks correct at first glance.

### Title
Prefix-only containment check in `resolveWithin()` allows deep-link `filepath` to resolve to a sibling directory outside the repository - (File: `app/src/lib/path.ts`)

### Summary
The Sherlock report's root cause is a check that compares a computed value against an incomplete reference amount (`amount` instead of `amount + revokedAmount`), letting a value "pass" a guard that appears correct. GitHub Desktop's `_resolveWithin()` helper has the same class of defect: it validates that a resolved path is "inside" a repository root using a raw string-prefix comparison instead of a path-boundary-aware comparison.

### Finding Description
`_resolveWithin()` is the guard used to sanitize the `filepath` parameter of the `x-github-client://openRepo/...?filepath=...` deep link (and other CLI/clone flows). It computes: [1](#0-0) 

The final check `realResolved.startsWith(realRoot)` is a pure string comparison with no separator boundary enforcement. If `realRoot` is e.g. `/Users/alice/Projects/myrepo` and the resolved path is `/Users/alice/Projects/myrepo-secrets/config.json`, the `startsWith()` call returns `true` even though `myrepo-secrets` is a completely different directory tree, not a subdirectory of `myrepo`. The same defect applies on Windows to case-insensitive filesystem paths that happen to share the same string prefix.

This guard is invoked directly from the deep-link dispatcher when handling an attacker-supplied `filepath` from an `open-repository-from-url` action: [2](#0-1) 

The `filepath` itself originates from a URL that any website/webmail/document can trigger via the registered `github-mac://`/`x-github-client://` protocol handler, parsed with only light validation (absolute paths and rejection are blocked, but relative traversal segments are allowed through `normalize`/`join`/`resolve`): [3](#0-2) 

### Impact Explanation
If a directory whose name shares the repository's directory name as a string prefix exists on disk (e.g., a repository cloned by the user at `.../myrepo` alongside another folder `.../myrepo-old`, `.../myrepo.bak`, or a second clone at `.../myrepo (1)`), a crafted deep link with `filepath=../myrepo-old/some/file` will pass the containment check and cause Desktop to call `shell.showItemInFolder()` on a path outside the intended repository, revealing/opening arbitrary file locations elsewhere on the user's disk without further prompting. This matches the report's required impact class: "attacker controls ... a deep link the user clicks ... and the result is ... file read outside the repo."

### Likelihood Explanation
The check itself is unconditionally wrong (no separator normalization) for any path pair where one directory name is a literal string-prefix of another sitting in the same parent folder — a common real-world occurrence (backup folders, renamed clones, versioned checkouts like `repo`, `repo-2`, `repo.bak`). No local/physical access or prior malware is required; only a single click on an attacker-supplied `x-github-client://openRepo/...` link is needed, which is the exact "user clicks a link" primitive the task requires. Because `openRepositoryFromUrl` requires an existing (or newly cloned) local repository, the attacker needs the victim to already have (or agree to clone) a repository whose directory name is a prefix-colliding sibling of another folder on disk — this narrows but does not eliminate practical exploitability.

### Recommendation
Change the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to enforce a real path boundary rather than a string prefix, e.g.:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the platform-appropriate separator for the `options` variant in use (`join`/`normalize`/`resolve` already parameterize POSIX vs Win32).

### Proof of Concept
1. Victim has two local folders: `/Users/victim/Projects/myrepo` (a GitHub Desktop-tracked repo) and `/Users/victim/Projects/myrepo-secrets/passwords.txt` (unrelated folder that happens to share the `myrepo` prefix).
2. Attacker hosts a page with a link:
   `x-github-client://openRepo/https://github.com/some/existing-repo?filepath=../myrepo-secrets/passwords.txt`
3. Victim clicks the link; Desktop parses it via `parseAppURL` into an `open-repository-from-url` action and calls `openRepositoryFromUrl`.
4. `resolveWithin(repository.path, filepath)` normalizes/resolves the `../myrepo-secrets/passwords.txt` segment to `/Users/victim/Projects/myrepo-secrets/passwords.txt`, and `realResolved.startsWith(realRoot)` (`realRoot = /Users/victim/Projects/myrepo`) evaluates `true` due to the shared string prefix.
5. Desktop calls `shell.showItemInFolder(resolved)`, revealing/opening the unrelated file outside the intended repository, confirming the boundary check does not stop the path.

I was not able to fully verify additional exploitation vectors (e.g., whether other callers of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` have stronger validation layered on top, or whether Windows short-path/8.3 name aliasing could widen the collision surface) due to index size limits; a full Devin session with repo access would be needed to audit every call site of these functions for additional impact.
