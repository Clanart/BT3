## Analog Identified: Case-Insensitive Filesystem Aliasing Treated as Distinct Repositories

### Title
Repository Identity Confusion on Case-Insensitive/Case-Preserving Filesystems Leads to Divergent, Stale Local State — (File: `app/src/lib/repository-matching.ts`)

### Summary
The external report's broken invariant is: *a single underlying storage location can be addressed by more than one "identifier," and the application incorrectly assumes identifier uniqueness maps 1:1 to storage uniqueness.* In GitHub Desktop, `matchExistingRepository` is the function responsible for deciding whether a given filesystem path refers to a `Repository` the app already tracks. It only applies case-insensitive normalization when running on Windows, and does a case-sensitive `Path.normalize` comparison everywhere else: [1](#0-0) 

macOS ships by default with a case-insensitive, case-preserving filesystem (APFS/HFS+), and many Linux setups mount case-insensitive volumes (e.g., exFAT/NTFS network shares, some CIFS/SMB mounts). On such systems, `/Users/x/Projects/Repo` and `/Users/x/Projects/repo` are the exact same inode/directory on disk, but Desktop's identity check treats them as two distinct repositories because it only lowercases paths when `__WIN32__` is true.

### Finding Description
`matchExistingRepository` is the single chokepoint Desktop uses to decide "is this path already one of my tracked repositories":
- Called from `dispatcher.ts` when opening a repository via CLI, drag-and-drop, "Add Existing Repository", and when locating a shared worktree's main repository.
- Called from `app-store.ts` for similar deduplication logic before creating a new `Repository` record.

Because the case-fold only happens for `__WIN32__`, any path variant differing only in case on a case-insensitive-but-case-preserving filesystem (default macOS) will fail the `needle === normalize(r.path)` check and be treated as "not found," letting the app create a second, independent `Repository` row in the repositories database pointing at the same on-disk git directory: [2](#0-1) 

This is architecturally the same class of bug as the report: the app assumes a single string form is a unique key for the underlying resource (a token contract address in the original report; a filesystem path here), and relies on that key for tracking ownership/state (`balanceOf` there; git status/HEAD/index caching via `GitStoreCache` here), when in fact the underlying storage (ERC20 ledger there; the `.git` directory and worktree files here) can be reached through more than one valid identifier.

The consequence: Desktop can end up running two independent `GitStore` instances, each polling/mutating the *same* `.git` directory and worktree concurrently, unaware of each other, because each is keyed off a different `Repository.id`/path-cased string rather than the resolved canonical filesystem identity (e.g., a real path/inode).

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes":
- Two `GitStore`/`Repository` entries backed by the same working directory can independently cache stale HEAD/branch/index state, race on writing the index (`git add`), race on `.git/COMMIT_EDITMSG`, or trigger concurrent `git commit`/`git checkout`/stash operations against the same repository from two UI tabs/selections.
- A user could, for example, stage/commit changes visible in one tracked entry while the other tracked entry (which the UI treats as a distinct, "clean" repository) shows stale status, leading the user to unintentionally push a commit missing files they believed were included, or to overwrite work with a checkout performed from the "other" duplicate.
- Because the two `Repository` rows share physical git storage but not app-level locking, this does not require the attacker to have local/physical access — it can be triggered any time the disk is case-insensitive (the OS default on macOS) combined with a natural workflow: cloning/opening the same repo folder via two different casings (e.g., a case-varying symlink, a build tool, or a case-different reference from `Finder`, CI cache restore, or a network share), which is a normal and expected filesystem behavior Desktop fails to account for.

### Likelihood Explanation
High on default macOS installs, since case-insensitivity is the out-of-the-box filesystem behavior (APFS default), not an edge case requiring unusual configuration. Any code path that adds/matches a repository by raw string path — CLI open, drag-and-drop `AddRepository`, and worktree/main-worktree resolution in `app-store.ts` (`_relocateRepository`, `switchWorktree`) — is exposed, since they all route through `matchExistingRepository` with the same Windows-only normalization gate.

### Recommendation
- Normalize paths for identity comparisons using the actual filesystem's case sensitivity, not the OS name — e.g., resolve real casing via `fs.realpath`/`fs.realpathSync` (which recovers the on-disk canonical casing) before comparing, instead of gating solely on `__WIN32__`.
- Alternatively/additionally, key repository identity off a stable filesystem identifier (e.g., resolved real path, or device+inode) rather than the raw path string the user/OS happened to supply.
- Add regression tests for macOS-style case-insensitive-but-case-preserving matching in `repository-matching-test.ts`, mirroring the existing Windows-specific test coverage.

### Proof of Concept
1. On macOS (default APFS, case-insensitive), clone a repository to `/Users/dev/Projects/MyRepo` and add it in Desktop (creates `Repository` #1, `path = /Users/dev/Projects/MyRepo`).
2. From the CLI, run `open -a "GitHub Desktop" /users/dev/projects/myrepo` (or use "Add Existing Repository" and type the same physical folder with different casing, which macOS Finder/Terminal will happily accept and resolve to the identical directory).
3. `dispatchCLIAction`/`openOrAddRepository` calls `matchExistingRepository(repositories, path)` at [3](#0-2)  with the lower-cased path; since `__WIN32__` is false, `normalize` performs no case-folding, `needle !== normalize(r.path)`, so no existing repository is found.
4. Desktop adds a **second** `Repository` record (via `AddRepository` popup) pointing at the identical `.git` directory as `Repository` #1.
5. Perform commits/stashes/checkouts alternately from the two entries in the sidebar; both operate on the same physical `.git`/index, producing state divergence (e.g., one entry's cached "clean" status while the other has staged/committed changes), risking an unintended commit/push from stale cached state. export function matchExistingRepository<T extends { readonly path: string }>(
```typescript
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}
```
