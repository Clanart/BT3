### Title
PedPoP commitments PoK does not bind `enc_key`, allowing an intermediary to redirect encrypted secret shares and recover a participant's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The confused-deputy bug class maps onto PedPoP's `EncryptionKeyMessage`: each participant's round-1 message carries a signed `Commitments` payload plus an unsigned `enc_key` used by every other party to encrypt that participant's secret shares. The Schnorr proof-of-knowledge covering the message authenticates only the commitments bytes (`cached_msg`) and the participant index — never `enc_key` — so an attacker positioned as a message intermediary can swap the encryption key while preserving a fully valid, verifiable message. All other participants then encrypt shares-for-the-victim to the attacker's key, letting the attacker recover the victim's entire secret share while the victim simply fails decryption.

### Finding Description
In `generate_coefficients`, the PoK is computed as `challenge(context, i, nonce, cached_msg)` where `cached_msg` is only the concatenation of the t commitment points [1](#0-0) . The `EncryptionKeyMessage` serialization writes the `Commitments` struct and then `enc_key` separately [2](#0-1)  — `enc_key` lies outside the signed region.

On receipt, `verify_r1` registers the (attacker-modifiable) `enc_key` via `Decryption::register` and batch-verifies only the PoK over `msg.cached_msg` [3](#0-2) . Nothing binds `msg.enc_key` to `l` or to the signature. `Decryption::register` stores it unconditionally [4](#0-3) .

`generate_secret_shares` then encrypts `f_i(l)` to `enc_keys[l]` for every participant `l` [5](#0-4) , and `encrypt` performs ECDH directly against the registered point [6](#0-5) . The per-message PoP inside `EncryptedMessage` only proves knowledge of the *ephemeral* key — it says nothing about the registered key's legitimacy [7](#0-6) .

### Impact Explanation
A deputy/intermediary (relay, aggregator, or any party able to present participant l's commitment bytes under a modified `enc_key`) causes every honest participant to encrypt `f_i(l)` to an attacker-known ECDH secret. The attacker decrypts all n-1 shares sent to l and sums them — that is exactly the operation `KeyMachine::calculate_share` performs for the victim [8](#0-7)  — recovering l's threshold secret share. This is key-share recovery: combined with the attacker's own share (or other compromises), it reduces the threshold security of the group key. The victim and the group otherwise see a valid commitment set; the attack is only detectable as a decryption failure at `calculate_share`, by which point the shares are already exposed.

### Likelihood Explanation
Requires an intermediary able to alter the round-1 commitment message in transit while keeping the signed portion intact — precisely the "unintended intermediary" precondition of the confused-deputy class. The protocol comments explicitly note the per-message keys "have no root of trust other than their existence in the assumed-to-exist external authenticated channel" [9](#0-8) , yet a channel that authenticates *sender identity* but not message integrity field-by-field still permits this swap, since the cryptographic binding (the PoK) itself omits `enc_key`. Any deployment where commitment messages pass through a relay/broadcast service rather than direct authenticated channels is exposed.

### Recommendation
Include `enc_key` in the PoK. Either move `enc_key` inside `Commitments` so it becomes part of `cached_msg`, or extend `challenge`/`pop_challenge` to append `b"enc_key"` so the Schnorr PoK covers `context || l || R || commitments || enc_key` [10](#0-9) . Alternatively, add a per-participant Schnorr PoP over `enc_key` in `EncryptionKeyMessage` so registration of a key requires proof of its discrete log, which would also let honest parties reject redirected keys before encrypting to them.

### Proof of Concept
1. Participant l broadcasts `EncryptionKeyMessage { Commitments{commitments, cached_msg, sig}, enc_key_l }`.
2. Interceptor replaces `enc_key_l` with `e*G` for attacker-known scalar `e`, leaving the signed `Commitments` untouched. `EncryptionKeyMessage::read` and `verify_r1` accept it — `sig` verifies over `cached_msg`, which does not include `enc_key`.
3. Every honest participant executes `generate_secret_shares` and sends `EncryptedMessage`s encrypting `f_i(l)` to `e*G` via `ecdh(ephemeral, e*G)`.
4. Attacker computes each shared key as `ecdh(e, msg.key)` — i.e. `e * msg.key` — and applies `cipher(context, key)` to recover every `f_i(l)` in the clear.
5. Attacker sums the shares: `s_l = Σ_i f_i(l)`, obtaining the victim's full FROST secret share before `calculate_share` even runs for the victim.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}

  pub(crate) fn register<M: Message>(
    &mut self,
    participant: Participant,
    msg: EncryptionKeyMessage<C, M>,
  ) -> M {
    assert!(
      !self.enc_keys.contains_key(&participant),
      "Re-registering encryption key for a participant"
    );
    self.enc_keys.insert(participant, msg.enc_key);
    msg.msg
  }
