### Title
PedPoP DKG encryption keys are unauthenticated, allowing share interception by a man-in-the-middle - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2022-33683 (an internal client that fails to authenticate its peer, exposing confidential traffic to MITM), `EncryptionKeyMessage` in PedPoP appends the recipient's ECDH public key (`enc_key`) *outside* the Schnorr-signed region of the round-1 commitments message. The proof-of-knowledge signature covers only the commitments (`cached_msg`), so anyone who can relay, rewrite, or deliver the untrusted `EncryptionKeyMessage::read` bytes can substitute an arbitrary `enc_key`. All dealers then encrypt that victim's secret shares to the attacker's key, leaking every share and enabling group secret key recovery.

### Finding Description
`Commitments::read` builds `cached_msg` solely from the `t` commitment points, and `challenge()` binds the Schnorr PoK to `context || participant || R || commitments` only — `enc_key` is absent. [1](#0-0) [2](#0-1) 

`EncryptionKeyMessage::read` then reads `enc_key` as a trailing, unsigned field; `Decryption::register` stores it under the sender's `Participant` index with no PoP, no signature, and no binding to `msg`. [3](#0-2) [4](#0-3) 

`verify_r1` batch-verifies `msg.sig` against `msg.commitments[0]` and `msg.cached_msg` — the already-registered `enc_key` is never covered by any check. [5](#0-4) 

`encrypt` then ECDH's the fresh per-message key against `enc_keys[participant]` and ChaCha20-encrypts the secret share; whoever knows the discrete log of the substituted `enc_key` derives the identical stream key from the broadcast `msg.key` and decrypts the share. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who replaces victim `j`'s `enc_key` with `K_a = a·G` learns the shared key `key_i·K_a` for every dealer `i`'s encrypted share to `j` (the per-message public key `key_i·G` is in the clear), decrypting each `SecretShare` in transit. The ciphertext need only be observed, not blocked. Collecting the `n-1` shares addressed to `j` — or enough substituted recipients' shares — reconstructs the polynomials and yields the threshold group's secret key, i.e. full key-share/secret recovery, the most severe outcome for a DKG. The code itself acknowledges the channel is unauthenticated ("This still doesn't mean the DKG offers an authenticated channel", encryption.rs:300), and unlike the per-message `pop` which binds `sender`, the registration key has no binding whatsoever.

### Likelihood Explanation
Any party positioned between participants — a relay/coordinator aggregating `EncryptionKeyMessage`s, or a network MITM — performs the substitution by rewriting the trailing `enc_key` bytes after the signature; no discrete-log knowledge or collusion is needed. The attack also produces a covert variant: blame proofs (`decrypt_with_proof`) publish the ECDH key, but by then the attacker already holds the plaintext. Detection is possible only because the victim's share verification fails, yet the secret is already compromised.

### Recommendation
Bind `enc_key` into the round-1 authentication: include `enc_key.to_bytes()` in `cached_msg`/`challenge()` so the Schnorr PoK signs it, or add a per-registration Schnorr PoP over `(context, participant, enc_key)` verified in `verify_r1` before `Decryption::register`. Additionally consider a MAC on the ChaCha20 ciphertext so tampering is attributable rather than silently producing gibberish.

### Proof of Concept
1. Victim `j` broadcasts `EncryptionKeyMessage { Commitments{...sig}, enc_key = b·G }`.
2. Attacker on the delivery path (or a malicious relay) rewrites the trailing bytes to `enc_key' = a·G` where `a` is known; `Commitments` and `sig` are untouched, so `verify_r1`'s batch check still passes.
3. Every dealer `i` calls `self.encryption.encrypt(rng, j, share)`, computing `key_i·(a·G)` and publishing `key_i·G` inside `EncryptedMessage`.
4. Attacker computes `a·(key_i·G)`, derives the ChaCha20 key via `cipher(context, ecdh)`, and decrypts `j`'s `SecretShare` from each dealer — reconstructing `j`'s share polynomial and ultimately the group secret key once `t` shares across substituted victims are obtained.

pub struct EncryptionKeyMessage<C: Ciphersuite, M: Message> {
  msg: M,
  enc_key: C::G,
}

// Doesn't impl ReadWrite so that doesn't need to be imported
impl<C: Ciphersuite, M: Message> EncryptionKeyMessage<C, M> {
  pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
    Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })
  }

  pub fn write<W: io::Write>(&self, writer: &mut W) -> io::Result<()> {
    self.msg.write(writer)?;
    writer.write_all(self.enc_key.to_bytes().as_ref())
  }
