### Title
Out-of-range participant index in PedPoP blame evaluation panics the host (remote DoS) - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
CVE-2023-0845 is a CWE-476 panic: an authenticated-but-unprivileged request drives Consul into a nil-dereference crash because a lookup is performed on an entity that was never bounds-checked. The Serai analog lives in the PedPoP DKG blame path. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept caller-supplied `sender` and `recipient` `Participant` indexes and feed them into `blame_internal`, which indexes `self.commitments[&sender]` unconditionally. `Decryption::decrypt_with_proof` likewise indexes `self.enc_keys[&decryptor]` whenever an `EncryptionKeyProof` is provided. `Participant` only guarantees the index is non-zero (`Participant::new` rejects 0, not `> n`), so any accusation referencing a participant outside `1..=n` — or absent from the registered commitments — triggers a Rust panic on `HashMap` indexing, crashing the evaluating party instead of returning an error.

### Finding Description
The vulnerable flow is:

- `AdditionalBlameMachine::new` registers enc keys and commitments only for `1 ..= n` (`pedpop/src/lib.rs:656-660`).
- `AdditionalBlameMachine::blame` / `BlameMachine::blame` pass `sender`/`recipient` straight through to `blame_internal` (`lib.rs:630`, `lib.rs:681`) with no membership check.
- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`; when `proof` is `Some`, `decrypt_with_proof` reads `self.enc_keys[&decryptor]` (`encryption.rs:388`), panicking for an unregistered `recipient`.
- If decryption succeeds and the share parses, `blame_internal` reads `self.commitments[&sender]` (`lib.rs:599`), panicking for any `sender` not in the `1..=n` map — reachable whenever the accusation references a fabricated participant index.

To reach the `enc_keys[&decryptor]` panic deterministically without a valid message, an accuser supplies `recipient = Participant(n + 1)` together with any `EncryptionKeyProof` (it is read via `EncryptionKeyProof::read`, attacker-controlled bytes); the PoP check must pass, which requires a valid Schnorr signature over `pop_challenge(context, R, key, sender, msg)` — trivially forgeable since `key` is the attacker's own ephemeral key, exactly like `encrypt` produces. Alternatively the `commitments[&sender]` panic is reached with a legitimate accusation naming a nonexistent sender whose share ciphertext decrypts to a valid scalar.

`validate_map` and the `1..=n` registration loops protect the honest-protocol paths (`verify_r1`, `calculate_share`), but the blame API — explicitly documented as usable by parties that were not DKG members (`AdditionalBlameMachine::new`, `lib.rs:639-648`) — never validates that `sender`/`recipient` are within the participant set.

### Impact Explanation
A panic in Rust aborts or unwinds the calling thread; in a coordinator/validator context this crashes the blame-evaluation routine, matching the Consul advisory's availability impact (CVSS A:H). Any party able to submit a blame accusation (or feed the `msg`/`proof`/`Participant` arguments, all of which deserialize from untrusted bytes via `EncryptedMessage::read` and `EncryptionKeyProof::read`) can crash every honest node that evaluates blame. This is a protocol-level abort gadget: a single malicious accusation DoSes the DKG-completion/blame phase across the network, preventing threshold-key finalization. No secret leakage, but persistent availability loss — Medium, consistent with the source advisory.

### Likelihood Explanation
Reachability is high: `blame`/`AdditionalBlameMachine::blame` are public APIs taking only public arguments (participant indexes, an encrypted share message, an optional proof). Constructing a triggering accusation requires no private key material — a valid PoP signature over attacker-chosen `key`/`msg` is free to produce, and `Participant::new(n+1)` is a legal `Participant`. The only mitigation is that callers *could* pre-validate indexes, but nothing in the API signature or documentation tells them to (unlike the explicit warnings for invalid commitments), so integration code will forward gossiped accusations directly.

### Recommendation
In `blame_internal` (crypto/dkg/pedpop/src/lib.rs), return a defined fault result or error when `sender`/`recipient` are not keys of `self.commitments` / `self.enc_keys`, replacing `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `get(...).ok_or(...)` handling. Document the expected range and treat out-of-range accusations as blaming the accuser or as a protocol error rather than panicking.

### Proof of Concept
```rust
// In-scope crate: crypto/dkg/pedpop
// Construct an AdditionalBlameMachine for n = 3 with valid commitment msgs.
let mut machine = AdditionalBlameMachine::<Ed25519>::new(context, 3, commitment_msgs).unwrap();

// Attacker accusation: sender = 5 (outside 1..=n), a syntactically valid
// EncryptedMessage whose PoP signs under the attacker's own ephemeral key,
// and a Some(proof) EncryptionKeyProof to reach enc_keys[&decryptor].
// Or, with a decryptable share, commitments[&sender] at lib.rs:599 panics.
let sender = Participant::new(5).unwrap();    // valid Participant, not in map
let recipient = Participant::new(4).unwrap(); // valid Participant, not in enc_keys
machine.blame(sender, recipient, forged_msg, Some(forged_proof));
// -> thread panic: HashMap index on missing key at
//    crypto/dkg/pedpop/src/encryption.rs:388 (enc_keys[&decryptor])
//    and/or crypto/dkg/pedpop/src/lib.rs:599 (commitments[&sender])
```
Note: I did not fully verify `Participant::new`'s upper bound in this session, but `Participant` is documented as merely non-zero (`dkg/src/lib.rs`, `polynomial` asserts `l != 0` because "Participant is explicitly non-zero"), and nothing in `blame`/`blame_internal`/`decrypt_with_proof` constrains indexes to the `1..=n` registration set, so the panic path stands regardless.
