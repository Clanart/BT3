Based on my research, I found a valid analog in the sei-chain codebase within the EVM module's parameter accessors.

### Title
EVM module's `Params` query exposes raw zero-valued `SeiSstoreSetGasEip2200` while gas accounting silently substitutes a different effective value - (File: x/evm/keeper/params.go)

### Summary
The x/evm module keeper stores an override for the SSTORE gas cost (`SeiSstoreSetGasEip2200`) that can be zero for blocks/params created before the field existed or before it was explicitly set. The keeper's actual gas-accounting logic reads this field and, if it is zero, silently substitutes a hardcoded legacy constant instead. Any client (JSON-RPC user, contract deployer, or public RPC consumer) that queries the module's params directly sees the raw stored value (`0`), not the effective value (`20000`) actually applied to their transaction's gas cost — the same "displayed vs. used" parameter mismatch as the reported Sherlock finding for `UniV3OracleImpl.getPairOverrides`.

### Finding Description
`Keeper.GetSstoreSetGasEIP2200` is the effective-value accessor used during EVM execution: it reads the raw params value and falls back to `LegacySstoreSetGasEIP2200` (`20000`) when the stored value is `0`. [1](#0-0) 

This mirrors the general pattern seen across the same file for many other params (`GetMaxDynamicBaseFeeUpwardAdjustment`, `GetTargetGasUsedPerBlock`, `GetDeliverTxHookWasmGasLimit`, `GetRegisterPointerDisabled`, etc.), all of which apply upgrade-height-gated defaults rather than the raw stored struct field when the raw value is absent/zero for a given chain height/version. [2](#0-1) [3](#0-2) 

Meanwhile, `Keeper.GetParams`/`GetParamsIfExists` simply reads the raw param-set with no substitution: [4](#0-3) 

The module's gRPC/query-server `Params` endpoint (`x/evm/keeper/grpc_query.go`), which is what public RPC/CLI/dApp clients call to inspect current EVM parameters, is built on top of `GetParams`/`GetParamsIfExists` rather than on the per-field effective getters like `GetSstoreSetGasEIP2200`. As a result, a caller querying EVM params sees the raw struct (possibly `SeiSstoreSetGasEip2200 == 0`), while the state transition logic that actually prices SSTORE operations uses `20000` for that same block. This is functionally identical to the reported bug class: "the pair parameters being used and the pair parameters that the user can see are different," because a zero/override sentinel is resolved only in the internal execution path, not in the externally-visible getter.

### Impact Explanation
A dApp, gas estimator, or off-chain tooling that queries EVM params to compute or display expected gas costs for `SSTORE` operations will compute costs based on the raw (possibly `0`) value instead of the effective `20000` actually charged, leading to systematically wrong gas estimates and mispriced transactions (over/under-estimation of gas), and potential transaction failures (`out of gas`) for end users who trust the queried params. This is a state-inconsistency/misleading-information class issue rather than a direct fund-loss primitive, matching the Medium severity of the original report.

### Likelihood Explanation
Any unprivileged RPC client, contract deployer, or wallet/gas-estimation service can trigger this simply by querying EVM module params through the standard gRPC/REST/CLI query path — no special privilege is required, and the divergence is deterministic whenever the stored `SeiSstoreSetGasEip2200` is zero (which is the state on any chain upgraded from pre-v6.3.0 params that has not explicitly set this param via governance).

### Recommendation
Update the EVM params query path (`x/evm/keeper/grpc_query.go` `Params` handler) to return effective values by routing zero/unset fields (in particular `SeiSstoreSetGasEip2200`, and any other fields with similar "0 means fallback" semantics used by the per-field getters in `x/evm/keeper/params.go`) through the same default-substitution logic (`GetSstoreSetGasEIP2200`, etc.) rather than exposing the raw stored struct directly, so the value returned to a querying client always matches what will be applied during execution.

### Proof of Concept
1. Deploy/upgrade chain state such that `types.Params.SeiSstoreSetGasEip2200` is `0` (e.g., pre-migration state, per `x/evm/migrations/migrate_sstore_gas.go`).
2. Call the EVM module's `Params` query (via gRPC/REST/CLI) — the response shows `SeiSstoreSetGasEip2200: 0`.
3. Submit an EVM transaction that performs an `SSTORE`; the keeper's gas accounting internally calls `GetSstoreSetGasEIP2200`, which substitutes `20000` instead of the queried `0`. [5](#0-4) 
4. Off-chain gas estimation based on the queried param diverges from the actual gas charged on-chain.

// LegacySstoreSetGasEIP2200 is the original hardcoded SSTORE gas cost used before
// the SSTORE parameterization was introduced (pre-v6.3.0). For blocks created before
// the SeiSstoreSetGasEIP2200 param existed, we fall back to this value.
const LegacySstoreSetGasEIP2200 = uint64(20000)

// GetSstoreSetGasEIP2200 returns the SSTORE gas cost for the given context.
// If the param is not set (0), it falls back to the legacy hardcoded value of 20000.
// This ensures consistent gas accounting for blocks created before the param existed.
func (k *Keeper) GetSstoreSetGasEIP2200(ctx sdk.Context) uint64 {
	sstore := k.GetParams(ctx).SeiSstoreSetGasEip2200
	if sstore == 0 {
		return LegacySstoreSetGasEIP2200
	}
	return sstore
}
