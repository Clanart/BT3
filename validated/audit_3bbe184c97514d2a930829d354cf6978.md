### Title
Duplicate-Key Validation Bypass via Field-Name Aliasing in `json_format.Parse` — ([File: python/google/protobuf/json_format.py])

### Summary
The Fastify bug is a **parser/validator differential**: one code path (`ContentType`) normalizes a header before dispatch, while a second, independent code path (`getEssenceMediaType`) tokenizes the same raw header differently, so the value used to *select/skip a validator* diverges from the value used to *parse the body*, silently disabling an enforced schema check. The closest analog surface in Protobuf that has the same shape — one code path enforcing a duplicate/uniqueness invariant on a raw key string while a second, independent code path resolves that key through an *aliasing* transform (json_name / camelCase / snake_case) — is Python's ProtoJSON parser, `google.protobuf.json_format`.

### Finding Description
`json_format.Parse` first loads the raw JSON text with `object_pairs_hook=_DuplicateChecker`, which rejects the payload only if two keys are **byte-for-byte identical**: [1](#0-0) 

The loaded dict is then handed to `ParseDict`, which resolves each JSON key to a `FieldDescriptor` using the field-name/`json_name` alias tables (the same tables that let `"int32Value"` and `"int32_value"` resolve to the identical field). Because the duplicate check operates on the literal string key from `_DuplicateChecker`, while field assignment operates on the resolved-descriptor identity, two *differently spelled* keys that alias to the same field are treated as distinct by the "reject duplicates" invariant and are silently accepted and merged, exactly like the Fastify case where the security check consumed a differently-derived value ('' vs `application/json`) than the value the parser actually acted on. This is reproduced and explicitly acknowledged as unintended in the project's own test: [2](#0-1) 
and the same aliasing/collision root cause (json_name vs. default camelCase mapping) is documented as an accepted, unresolved design gap in Protobuf's own edition-zero design notes: [3](#0-2) 

The C++ JSON parser (`json/internal/parser.cc`) has the equivalent "reject a field that has already been seen" check (`SeenState::kFieldAlreadySeen`), but that check is keyed on the *resolved field*, not the raw string, so it is not affected the same way; the aliasing bypass is specific to the Python binding's separate `_DuplicateChecker`/`ParseDict` split: [4](#0-3) 

### Impact Explanation
Unlike the Fastify report — where the bypassed check enforced numeric bounds, required-field, and `additionalProperties` constraints, letting arbitrary attacker data through untyped — the Protobuf analog does **not** bypass per-field type/range/UTF-8 validation; every value is still validated by the field setter regardless of which alias key wrote it. The only consequence is nondeterministic "last write wins" between two spellings of the same field/map key, which the project already classifies as a known, low-impact, non-spec quirk rather than a security control bypass. There is no path here to disclosure, memory corruption, or complete circumvention of a declared validation schema as in the original report.

### Likelihood Explanation
Any caller of `google.protobuf.json_format.Parse`/`ParseDict` on attacker-supplied JSON containing two spellings of the same field (default name and `json_name`, or snake_case/camelCase for the same field) can trigger this trivially and deterministically, as shown by the existing regression tests — reachability is easy, but the affected invariant is presentational (which value wins), not a bypassed security constraint.

### Recommendation
If this class of ambiguity is to be hardened, `_DuplicateChecker` in `python/google/protobuf/json_format.py` should perform duplicate detection using the *resolved* field/json_name (post-alias) rather than the raw literal JSON key, mirroring how `json/internal/parser.cc`'s `SeenState` tracks field identity instead of the raw text key. This is a low-severity correctness fix, not a critical security patch, and matches the project's own edition-zero JSON-handling proposal to unify duplicate/conflict detection.

### Proof of Concept
Using the existing project test (documented behavior, not a novel exploit):
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb

msg = pb.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
print(msg.int32_value)  # -> 2, no "duplicate key" error raised
``` [5](#0-4) 

Given the limited security relevance of this differential (no bypass of type/range/UTF‑8 enforcement, and the behavior is already known/accepted upstream), this analog should be treated as **Low/Medium** at most, not a valid High-severity transfer of GHSA-247c-9743-5963's schema-validation bypass. No stronger Critical/High analog (e.g., a check whose *skipping* would allow malformed/oversized/mistyped data past validation entirely) was found in the binary or ProtoJSON parse paths across C++/Java/Python/C#/upb during this review — the `Any` type-URL slash-splitting logic (C++, C#, upb, PHP, Java) was also inspected and found consistent (all use "last `/`" semantics) with no parser/validator divergence.

def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result
```
