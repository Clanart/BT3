### Title
`InitializeNonceAccount` allows unprivileged front-running of a System-Program-created nonce account, letting an attacker seize the nonce authority - ([File: programs/system/src/system_processor.rs])

### Summary
The System Program's `InitializeNonceAccount` handler performs no signer check on the account being initialized, unlike the sibling `allocate`/`assign` handlers which explicitly require `address.is_signer(signers)`. Any account that is already owned by the System Program, sized/rent-exempt for `nonce::State`, and still `State::Uninitialized` can be initialized by *any* transaction, with an attacker-chosen `authorized` pubkey, regardless of who created or funded the account.

### Finding Description
`initialize_nonce_account` only checks that the target account is writable and `Uninitialized`, then unconditionally writes `State::Initialized(Data::new(*nonce_authority, ...))` using whatever `nonce_authority` pubkey was supplied in the instruction data: [1](#0-0) 

The processor dispatch for `SystemInstruction::InitializeNonceAccount` passes the instruction-supplied `authorized` straight through, with no requirement that the nonce account (or its intended owner) be a signer of this instruction: [2](#0-1) 

This is in stark contrast to `allocate`, in the same file, which explicitly enforces that the target address must sign before any state is written: [3](#0-2) 

Because account creation (`CreateAccount`/`Allocate`+`Assign`, which does require the new account's key to sign) and nonce initialization (`InitializeNonceAccount`) are separate System Program instructions, they can be submitted in separate transactions. Once a nonce-account-shaped account exists on-chain in the `Uninitialized` state, the invariant "only the intended creator/owner determines the initial `authorized` (nonce authority)" is not enforced by any check in `initialize_nonce_account` or its caller — exactly the broken invariant described in the external report ("anyone can set the initial pool/owner address immediately after account creation").

### Impact Explanation
The nonce authority is the sole gatekeeper for `AdvanceNonceAccount`, `WithdrawNonceAccount`, and `AuthorizeNonceAccount` — all of which check the caller against the stored authority before allowing state changes or lamport withdrawals. If an attacker wins the race to call `InitializeNonceAccount` with their own pubkey as `authorized`, they become the sole controller of that account and can subsequently withdraw its lamports down to the rent-exempt minimum, or repeatedly invalidate the durable nonce (denial-of-service against whatever protocol depends on it), all without ever having signed the original account creation. This is direct fund theft / unauthorized control of an on-chain account by an unprivileged party, matching the reported bug class (unauthorized party sets privileged initial state right after instantiation).

### Likelihood Explanation
Exploitability depends entirely on an integrator creating and initializing a nonce account in two separate transactions (rather than atomically in one transaction/instruction batch), which is a documented pitfall for durable-nonce usage. Any consumer that follows a "create-then-initialize-later" pattern is exposed the moment the created, uninitialized account lands on-chain, since mempool/gossip visibility lets anyone race in an `InitializeNonceAccount` instruction before the legitimate initialization transaction confirms.

### Recommendation
Require the nonce account itself (or a designated payer/authority passed at `CreateAccount` time) to be a signer of `InitializeNonceAccount`, mirroring the `is_signer` check already present in `allocate`, or otherwise bind the allowed `authorized` value to information verified at account-creation time so a third party cannot supply an arbitrary `authorized` pubkey for an account they did not create.

### Proof of Concept
1. Victim submits `CreateAccount`/`Allocate`+`Assign` to create account `N`, sized for `nonce::state::State`, owned by the System Program (does not yet call `InitializeNonceAccount`).
2. Attacker observes account `N` on-chain in `State::Uninitialized` (or observes the pending creation transaction) and submits their own `InitializeNonceAccount(attacker_pubkey)` instruction targeting `N` before the victim's initialize transaction lands.
3. `initialize_nonce_account` succeeds because it only checks `Uninitialized` state, writability, and rent-exemption — [4](#0-3)  — with no signer requirement tying the call to `N` or its creator.
4. The victim's subsequent `InitializeNonceAccount` call now fails with `InstructionError::InvalidAccountData` since the account is already initialized.
5. Attacker, now the recorded `authorized` nonce authority, calls `WithdrawNonceAccount`/`AdvanceNonceAccount`/`AuthorizeNonceAccount` to drain lamports or permanently deny use of the durable nonce.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
