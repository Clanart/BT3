## Binding examined

`payout_payer_operator_xonly_pk` stored for withdrawal `idx` == the xonly pubkey of the party whose Bitcoin funds actually paid the withdrawal output. This binding is **broken**: the value comes solely from an unsigned `OP_RETURN` output that anyone constructing the winning transaction can set to any value, with no check tying it to who actually supplied the funds.

### Title
Unauthenticated `OP_RETURN` operator attribution in payout tx lets anyone reassign withdrawal-payout credit to an arbitrary operator - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
`create_payout_txhandler` signs only the withdrawal input and its paired output (`SIGHASH_SinglePlusAnyoneCanPay`), leaving the transaction's `OP_RETURN` (which encodes the "fronting operator" xonly pubkey) and the additional funding input(s) completely unsigned/uncommitted. Because the withdrawal-input signature is `ANYONECANPAY`, any unprivileged party can build and race their own version of the payout transaction, paying the exact required output while stamping any xonly pubkey (including a legitimate operator's) into the `OP_RETURN`. `Verifier::update_finalized_payouts` and `Operator::handle_finalized_payout`/`is_kickoff_malicious` trust this `OP_RETURN` value as the true funder, with no verification that the named operator's own signature/funds were used.

### Finding Description
The broken equality is: `withdrawals.payout_payer_operator_xonly_pk` (as read by `get_first_unhandled_payout_by_operator_xonly_pk` and `get_payout_info_from_move_txid`) == "the operator whose funds actually paid the withdrawal UTXO."

Path:
1. `create_payout_txhandler` builds a payout tx with: input 0 = withdrawal UTXO (`SpendPath::KeySpend`), output 0 = user payout, output 1 = anchor, output 2 = `OP_RETURN(operator_xonly_pk)`. The only witness set is the user's signature on input 0. [1](#0-0) 
2. `Operator::withdraw` verifies the user's signature has sighash `SinglePlusAnyoneCanPay` and validates it only against `calculate_sighash_txin(0, ...)` — i.e. only input 0/output 0 are committed by any signature; the `OP_RETURN` and anchor outputs are not covered by anything. [2](#0-1) [3](#0-2) 
3. Since `ANYONECANPAY` lets anyone add extra funding inputs, any unprivileged party (the withdrawing user is naturally in possession of this signature since they created it via Citrea's `withdraw()` call) can construct and broadcast a rival transaction spending the same withdrawal UTXO — fully valid — while placing an arbitrary xonly pubkey (e.g. a real, uninvolved operator's public key) in the `OP_RETURN`.
4. `Verifier::update_finalized_payouts` (called from `handle_finalized_block`) takes whichever tx first spent the withdrawal UTXO in a finalized block via `get_payout_txs_for_withdrawal_utxos` (first-spender wins, no funder check), extracts the `OP_RETURN` pubkey, and writes it as `payout_payer_operator_xonly_pk` with zero verification that the named operator actually constructed or funded that transaction. [4](#0-3) [5](#0-4) 
5. `PayoutCheckerTask::run_once` for that named operator queries `get_first_unhandled_payout_by_operator_xonly_pk` matching its own key, finds the withdrawal, and calls `handle_finalized_payout`, initiating a kickoff/reimbursement using its own collateral/kickoff connector — trusting the DB attribution unconditionally. [6](#0-5) 
6. The verifier-side guard `is_kickoff_malicious` only checks that the operator who *sent the kickoff* equals the `payout_payer_operator_xonly_pk` recorded in the DB — it never checks that this recorded pubkey is who actually paid the withdrawal output. [7](#0-6)  Since the framed operator's own kickoff naturally matches the DB-stored (attacker-forged) pubkey, this check passes and the reimbursement is approved as non-malicious.

Existing guards (`is_deposit_valid`, `SECP.verify_schnorr` on the withdrawal signature, `is_kickoff_malicious`) validate only that the *withdrawal input signature* and *kickoff-sender-vs-DB-value* are self-consistent; none verify that the operator credited in `OP_RETURN` supplied the funds. This decouples the txid's true funder from its recorded funder exactly as claimed.

### Impact Explanation
An unprivileged attacker (the withdrawing user, or anyone who reconstructs the public `ANYONECANPAY`-signed withdrawal payout tx) can front a withdrawal payment out of their own funds and attribute it, via the unsigned `OP_RETURN`, to any operator's xonly pubkey. That operator's own automated `PayoutCheckerTask`/`handle_finalized_payout` will then trigger a kickoff and get reimbursed from the bridge's escrowed deposit funds (`bridge_amount`) for a payout it never funded, and `is_kickoff_malicious` will not flag this as malicious since it only compares the kickoff sender to the (forged) DB attribution. This is a direct match to the Critical category "an operator reimbursed for a payout it never funded" — bridge escrow value is released without the credited operator having incurred the fronting cost, and the process is repeatable for every open withdrawal against every operator whose xonly pubkey is public (all operator keys are public via `fetch_operator_keys`/config).

### Likelihood Explanation
Preconditions are minimal: a withdrawal must be registered on Citrea (attacker can trigger this themselves by calling `withdraw()`), and the attacker only needs to win the race to have their own transaction (paying the required output, embedding a forged `OP_RETURN`) confirm before any competing legitimate payout tx. Attacker cost is exactly the withdrawal amount plus fees (BTC they must front to satisfy the fixed, signed output) — no privileged key material, no majority hashrate, and no protocol/verifier compromise is required. This is fully repeatable across every withdrawal and every operator.

### Recommendation
Bind the `OP_RETURN` operator attribution cryptographically to the actual funder, e.g. by requiring the operator's own signature/commitment to cover the `OP_RETURN` output (change sighash coverage or add a second, operator-signed input/commitment that the `OP_RETURN` pubkey must correspond to), or by having `is_kickoff_malicious`/`update_finalized_payouts` verify that the party who funded the transaction (e.g. via an operator-signed change/funding input recognizable on-chain) matches the claimed `OP_RETURN` pubkey, rather than trusting unsigned `OP_RETURN` data as authoritative.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
