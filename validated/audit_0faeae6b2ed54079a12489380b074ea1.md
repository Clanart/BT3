### Title
`ThresholdKeys::read`/`new` never validates `secret_share` against `verification_shares`, permitting a semantically invalid key set whose group key locks all received funds - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to `initialize` accepting a zero `feeRecipient` (an unchecked critical parameter that permanently disables withdrawal), `ThresholdKeys::new` — and therefore `ThresholdKeys::read`, which is fed untrusted bytes — performs syntactic checks (count of shares, participant indexes `<= n`, interpolation applicability) but never verifies the two values that actually determine usability of the wallet: that `C::generator() * secret_share == verification_shares[i]`, and that the interpolated `group_key` is not degenerate/attacker-chosen. A crafted `ThresholdKeys` blob therefore deserializes successfully into a wallet whose group key bears no relation to the holder's secret share, so every output the `Scanner` attributes to it is unspendable.

### Finding Description
`ThresholdKeys::new` at `crypto/dkg/src/lib.rs:349-391` validates only:

- `verification_shares.len() == params.n()` [1](#0-0) 
- every participant index `<= n` [2](#0-1) 
- `Constant` interpolation only when `t == n` [3](#0-2) 

It then derives `group_key` purely from the supplied `verification_shares`:

```rust
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [4](#0-3) 

No check ties `secret_share` to `verification_shares[params.i()]` — compare `dealer::key_gen`, which `debug_assert_eq!`s the consistency only in debug builds [5](#0-4) , and `musig`, which only `debug_assert_eq!`s `our_pub_key == verification_shares[&params.i()]` [6](#0-5) . In release builds neither relationship is enforced anywhere.

`ThresholdKeys::read` at `crypto/dkg/src/lib.rs:574-632` reads `t, n, i`, the interpolation, `secret_share` and all `n` verification shares straight from the byte stream and hands them to `ThresholdKeys::new` [7](#0-6) , so an attacker who can influence the serialized key material loaded by a processor (the same channel through which key-gen results and test vectors flow — see `vectors_to_multisig_keys` [8](#0-7) ) fully controls `group_key` while leaving `secret_share` meaningless.

The failure mode mirrors the report exactly: downstream Bitcoin code trusts `group_key` as the wallet's receiving key — `tweak_keys` applies the BIP-341 tweak to it [9](#0-8)  and `SignableTransaction::multisig` only catches mismatch per-input-offset, not an inconsistent core [10](#0-9) . Signing then silently produces shares that fail at `complete`, which even comments that the only known cause is "deserializing a semantically invalid FrostKeys" [11](#0-10)  — acknowledging the gap exists but returning an opaque `InternalError` only after funds are already committed to the bad key.

### Impact Explanation
Every output scanned to the corrupted `group_key` is received-but-unspendable: FROST shares verify against `view.verification_share(i)` (interpolated from the attacker-supplied shares), never against the victim's `secret_share`, so either the aggregate verify fails or individual blame fails, and no valid signature is ever produced. Like sending fees to `address(0)`, the funds are permanently locked with no recovery path — `recover_key` would even "succeed" on `t` corrupted copies since it only checks `G * res == group_key` across keys sharing the same corrupt parameters [12](#0-11) .

### Likelihood Explanation
Requires an attacker (or storage corruption) to substitute the `ThresholdKeys` bytes a node loads — a narrower reachability window than a public on-chain parameter, but the read API is explicitly in scope for untrusted bytes, and all consistency guarantees are debug-only, so the condition is never caught at runtime. Severity is Medium: permanent fund lockup on the affected set, contingent on key-material substitution rather than freely reachable from a public message.

### Recommendation
In `ThresholdKeys::new` (so `read`, `dealer`, `musig`, `promote::complete` and `GeneratorPromotion::complete` all inherit it), add runtime checks:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::SecretShareMismatch)?; // new variant
}
if bool::from(group_key.is_identity()) {
  Err(DkgError::InvalidGroupKey)?;
}
```

This is the direct analog of `require(newFeeRecipient != address(0))`: reject the degenerate parameter at construction instead of discovering locked funds at withdrawal/signing time.

### Proof of Concept
```rust
// Attacker-craft serialized ThresholdKeys for participant 1 of a 2-of-3 Lagrange set:
// - n = 3 random verification shares Y1..Y3 (any points, e.g. interpolating to an
//   attacker-known or identity group key),
// - secret_share = random scalar unrelated to Y1.
let bytes = /* C::ID || t=2 || n=3 || i=1 || interp=1 || s_bad || Y1 || Y2 || Y3 */;
let keys = ThresholdKeys::<Secp256k1>::read(&mut &bytes[..]).unwrap(); // succeeds today
// keys.group_key() is well-formed and used by tweak_keys() as the deposit address.
// Scanner attributes deposits; SignableTransaction::multisig may pass the per-input
// script_pubkey check, yet complete() always fails: secret_share never matches
// view.verification_share(1), so no valid spend can ever be produced -> funds locked.
```
A correct implementation must reject this blob in `ThresholdKeys::new` because `G * s_bad != Y1`.

pub fn tweak_keys(keys: ThresholdKeys<Secp256k1>) -> ThresholdKeys<Secp256k1> {
  // Adds the unspendable script path per
  // https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki#cite_note-23
  let keys = {
    use k256::elliptic_curve::{
      bigint::{Encoding, U256},
      ops::Reduce,
      group::GroupEncoding,
    };
    let tweak_hash = TapTweakHash::hash(&keys.group_key().to_bytes().as_slice()[1 ..]);
    /*
      https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki#cite_ref-13-0 states how the
      bias is negligible. This reduction shouldn't ever occur, yet if it did, the script path
      would be unusable due to a check the script path hash is less than the order. That doesn't
      impact us as we don't want the script path to be usable.
    */
    keys.offset(<Secp256k1 as Ciphersuite>::F::reduce(U256::from_be_bytes(
      *tweak_hash.to_raw_hash().as_ref(),
    )))
  };

  let needs_negation = needs_negation(&keys.group_key());
  keys
    .scale(<_ as subtle::ConditionallySelectable>::conditional_select(
      &Scalar::ONE,
      &-Scalar::ONE,
      needs_negation,
    ))
    .expect("scaling keys by 1 or -1 yet interpreted as 0?")
}
