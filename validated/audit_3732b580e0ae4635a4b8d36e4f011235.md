### Title
Aggregate Schnorr signature forgery via weights that fail to bind attacker-controlled nonces/keys - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` computes the per-signature aggregation weight `z_i` from a transcript over only the verifier-supplied challenges (`b"signatures"` domain + each `challenge`), never appending the attacker-controlled `Rs` or the public keys. Because the weights are fully predictable before the attacker chooses `Rs`, an attacker can set each `R_i = r_i*G - c_i*P_i` and `s = Σ z_i*r_i`, producing an aggregate signature that verifies for arbitrary victim public keys and challenges the victims never signed for. The bug class of the external report — a missing bound/check on an attacker-supplied value, allowing value extraction/forgery that an honest party assumed was constrained — maps here as the missing binding of the adversary-supplied signature components in the weight derivation.

### Finding Description
In the half-aggregation scheme this code follows (eprint 2021/350), the per-signature weight must be unpredictable with respect to the aggregated nonces — either random or a hash binding the aggregate contents. Here, `weight(&mut digest)` (crypto/schnorr/src/aggregate.rs:22) is called inside the verify loop after only the challenges were transcripted:

- `digest` is seeded with the DST and `b"signatures"`, then each `challenge.to_repr()` is appended (aggregate.rs:132-136).
- For each `i`, `z_i = weight(&mut digest)` is computed, and the pairs `(z_i, Rs[i])`, `(z_i * challenge_i, key_i)` are queued into `multiexp_vartime`, with `(-s, generator)` (aggregate.rs:138-145).

`Rs` and `s` come straight from `SchnorrAggregate::read` (aggregate.rs:77-88), i.e., fully attacker-controlled bytes. Since `z_i` depends on nothing the attacker supplies, the attacker computes all `z_i` offline, picks arbitrary scalars `r_i`, sets `R_i = r_i*G - c_i*P_i` and `s = Σ_i z_i*r_i`. The verification equation

`s*G = Σ z_i*(R_i + c_i*P_i) = Σ z_i*r_i*G`

then holds, so `multiexp_vartime` returns identity and `verify` returns `true` — even for `(key, challenge)` pairs belonging to victims who never produced a signature. The analogous defense in the codebase exists elsewhere (e.g., FROST's `rho_transcript` binds `group_key`, `message`, and all commitments before deriving binding factors in crypto/frost/src/sign.rs:362-371); aggregate verification lacks the equivalent binding.

### Impact Explanation
Any protocol path that accepts a `SchnorrAggregate` as proof that a set of `(public key, challenge/message)` pairs were signed accepts a forgery: an unprivileged party can claim any victim key signed any message, or append/remove signatures from an aggregate without the signers' participation. This defeats the non-repudiation/cost-saving purpose of half-aggregation entirely. Severity: High — forged signature accepted by `verify` from purely public inputs.

### Likelihood Explanation
The attack requires no private state, no victim cooperation, and no network position: the attacker only needs the DST (a `'static` public constant chosen by the caller) and the list of `(key, challenge)` pairs being verified, all public. The deterministic weight schedule is trivially reproducible since `DigestTranscript` challenges are public. Any verifier that batches Schnorr signatures via this API is exploitable with probability 1 per attempt.

### Recommendation
Bind the aggregated signature components into the weight transcript: after domain-separating, append each `key.to_bytes()`, each `Rs[i].to_bytes()`, and each challenge before deriving the corresponding weight (e.g., append all `R` commitments up front, or derive `z_i = H(transcript || R_i || key_i || challenge_i)`), matching the commitment-binding structure used for FROST binding factors in `crypto/frost/src/sign.rs`. Alternatively make weights verifier-random per batch. `SchnorrAggregator::complete` must be updated in lockstep since the signer-side weight derivation in `aggregate()`/`complete()` (aggregate.rs:169-186) shares the same transcript.

### Proof of Concept
```rust
// PoC: forge a SchnorrAggregate that verifies for a victim key/challenge
// without the victim signing. Run against crypto/schnorr.

use transcript::{Transcript, DigestTranscript};
use ciphersuite::{Ciphersuite, group::{ff::Field, Group, GroupEncoding}};
use schnorr::aggregate::SchnorrAggregate; // conceptually; weight() replicated below

fn forge<C: Ciphersuite>(
  dst: &'static [u8],
  keys_and_challenges: &[(C::G, C::F)], // victim keys + verifier-chosen challenges
) -> SchnorrAggregate<C> {
  // 1) Reconstruct the verifier's transcript: weights depend only on challenges.
  let mut digest = DigestTranscript::<C::H>::new(dst);
  digest.domain_separate(b"signatures");
  for (_, c) in keys_and_challenges {
    digest.append_message(b"challenge", c.to_repr());
  }

  // weight() is private; reimplement: it only consumes digest.challenge(...) output,
  // which is already fully determined at this point (no R/key terms appended).
  let weight_at = |i: usize| -> C::F {
    let mut d = DigestTranscript::<C::H>::new(dst);
    d.domain_separate(b"signatures");
    for (_, c) in &keys_and_challenges[.. i] {
      d.append_message(b"challenge", c.to_repr());
    }
    // replicate weight::<_, C::F>(&mut d): read (NUM_BITS + 128)/8 bytes of
    // challenge stream via b"aggregation_weight"/b"aggregation_weight_continued"
    weight_clone::<C>(&mut d)
  };

  // 2) Attacker chooses arbitrary r_i and cancels each victim's key term.
  let mut rs = vec![];
  let mut s = C::F::ZERO;
  for (i, (key, c)) in keys_and_challenges.iter().enumerate() {
    let z = weight_at(i);
    let r = C::F::random(&mut rand_core::OsRng);
    // R_i = r_i*G - c_i*P_i  =>  z_i*R_i + z_i*c_i*P_i = z_i*r_i*G
    rs.push(C::generator() * r - *key * *c);
    s += z * r;
  }
  // Serialized via write()/read() — all points are canonical, passing read_G.
  SchnorrAggregate::from_parts(rs, s) // verifies true via multiexp_vartime
}
```

For every `i`, the queued pairs sum to `z_i*r_i*G`; the `(-s, G)` pair cancels `Σ z_i*r_i*G`, so `verify` returns `true` for victim `(key, challenge)` pairs with no signature ever produced. The fix's regression test should assert that mutating any `R_i` (or appending an extra `(key, challenge)` with a self-canceling `R`) changes the accepted result — today it does not, because `R_i` is never transcripted before `weight()` is drawn.

Uncertainty note: `weight` is a private function, so a PoC replicates its logic (as sketched); the exploitability rests on the verified fact that only challenges — never `Rs` or keys — are appended to `digest` before each `weight()` call in `verify` (aggregate.rs:132-145).
