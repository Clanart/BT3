Found a concrete analog in the Kaia gasless (KIP-247) module: the proposer (block builder) pre-funds gas via `LendTxGenerator`/`repayAmount` based on a fixed lend/repay schedule computed purely from tx fee fields, while the actual repayment happens inside `GaslessSwapRouter.swapForGas`, whose ERC20 `token` is user-supplied and only checked against a whitelist maintained by governance-updatable state — not against the token's actual (post-fee) transfer semantics.

### Title
Gasless module lend/repay accounting does not account for fee-on-transfer/deflationary tokens, allowing proposer fee-advance loss - ([File: kaiax/gasless/impl/getter.go], [File: kaiax/gasless/impl/tx_pool.go])

### Summary
The KIP-247 gasless flow has the proposer advance gas fees to a user via a synthetic `LendTx` (`GetLendTxGenerator`) before the user's `GaslessSwapTx` executes and is expected to atomically repay the proposer inside `GaslessSwapRouter.swapForGas` using `AmountRepay`/`AmountIn` computed off-chain by the sender and validated only against nominal `balanceOf`/`allowance` figures, not against actual post-transfer-fee receipts.

### Finding Description
`checkBalanceForSwap` validates the swap purely with nominal ERC20 view-function values: `token.allowance(sender, router) >= amountIn` and `token.balanceOf(sender) >= amountIn` [1](#0-0) . These are pre-transfer balance/allowance snapshots; they do not simulate what the router will actually receive after `transferFrom`, which for a fee-on-transfer/rebasing ERC20 would be less than `amountIn`.

Separately, the proposer is committed to lending the full computed fee amount before the swap runs: `GetLendTxGenerator` builds a `LendTx` transferring `lendAmount(approveTxOrNil, swapTx)` KAIA to the swap sender unconditionally, and the expected on-chain repayment (`repayAmount`) is derived purely from static gas-price arithmetic, independent of what the router will actually be able to collect from the token [2](#0-1) . The bundle ordering guarantees `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` runs atomically as a unit [3](#0-2) , but nothing in the Go-side admission/building logic accounts for a token whose `transfer`/`transferFrom` delivers fewer tokens than the nominal `amountIn`, since the actual repay/output enforcement lives entirely inside `GaslessSwapRouter.swapForGas` (compiled bytecode only, not reviewable in this index) and is only reachable if that specific token is on the `allowedTokens` whitelist read from `MultiCallGaslessInfo` [4](#0-3) .

Because whitelisting of `allowedTokens` is a governance/registry-controlled list rather than something enforced to exclude fee-on-transfer tokens by protocol invariant, the analogous root cause from the Connext report (naive full-amount accounting instead of accounting for the token's actual delivered amount) is structurally present in the Go admission path: `checkBalanceForSwap`'s allowance/balance checks assume `amountIn` sent equals `amountIn` received, exactly the assumption that failed in the original bug.

### Impact Explanation
If a fee-on-transfer or rebasing ERC20 is ever whitelisted (intentionally or via a compromised/careless governance update), a submitted `GaslessSwapTx` can pass the tx-pool's nominal balance/allowance checks in `checkBalanceForSwap` yet the router receives less than `amountIn` when the token applies its transfer fee, causing either (a) the swap to revert after the proposer has already unconditionally paid out `LendTx` (block-level fee still spent, proposer's gas advance not recovered because the LendTx and SwapTx execute within the same bundle but LendTx transfer to the user is irreversible), or (b) if the router's `swapForGas` doesn't correctly re-check actual received balance, a shortfall of collateral is used to satisfy `amountRepay`, undercollateralizing the proposer's fee-delegation repayment. This is a fee-delegation/gasless-settlement value-movement risk squarely in scope (gasless module, unprivileged sender-reachable).

### Likelihood Explanation
Likelihood is constrained by the fact that `allowedTokens` is whitelist-gated by governance/registry, so exploitation requires a fee-on-transfer token to be present in that whitelist — this is a meaningful precondition, but the code contains no defense-in-depth check (e.g., verifying `balanceOf(router)` delta after `transferFrom`) visible from the Go-side admission logic, and nothing in `checkBalanceForSwap` protects against this token class if it slips into the whitelist.

### Recommendation
Add an explicit invariant check in `checkBalanceForSwap` (or, more robustly, in `GaslessSwapRouter.swapForGas`) to verify actual received token amount via before/after `balanceOf(router)` deltas rather than trusting nominal `transferFrom(amountIn)` semantics, and reject GaslessSwapTx when the delivered amount is less than the declared `amountIn`. Additionally, gate the `allowedTokens` addition process with an on-chain or governance-level check that rejects fee-on-transfer/rebasing tokens (e.g., by probing a test transfer) before whitelisting.

### Proof of Concept
1. Governance/registry whitelists a fee-on-transfer ERC20 `T` (10% fee) into `GaslessSwapRouter.allowedTokens`.
2. User submits `GaslessApproveTx` approving `T` to the router for `MaxUint256`, then `GaslessSwapTx` with `amountIn = 100`, `minAmountOut = amountRepay = X`.
3. `checkBalanceForSwap` passes because `balanceOf(sender) = 100 >= amountIn` and `allowance = MaxUint256 >= amountIn` [1](#0-0) .
4. Block builder prepends `LendTxGenerator`, unconditionally paying the user `lendAmount` in KAIA [5](#0-4) .
5. `swapForGas` calls `transferFrom(sender, router, 100)`, but router only receives 90 `T` due to the transfer fee; if the router assumes it holds 100 for computing swap output/repay, the proposer's `amountRepay` is undercollateralized or the swap reverts after the KAIA lend has already been paid out, since the lend and swap are only atomically bundled, not conditioned on actual token receipt correctness at the Go admission layer.

**Uncertainty note**: The Solidity source of `GaslessSwapRouter.swapForGas` is not present in this repository's index (only the compiled bytecode/Go bindings are available), so I could not confirm whether the contract itself already performs a `balanceOf`-delta check internally that would neutralize this risk. This should be verified directly against the KIP-247 `GaslessSwapRouter.sol` source, which is out of reach of the current index.

// MakeLendTx creates a transaction with following properties:
// L1. LendTx.type = 0x7802 (TxTypeEthereumDynamicFee)
// L2. LendTx.from = proposer
// L3. LendTx.to = SwapTx.from
// L4. LendTx.value = LendAmount(approveTxOrNil, swapTx)
func (g *GaslessModule) GetLendTxGenerator(approveTxOrNil, swapTx *types.Transaction) *builder.TxOrGen {
	var src []byte
	if approveTxOrNil != nil {
		src = append(src, approveTxOrNil.Hash().Bytes()...)
	}
	src = append(src, swapTx.Hash().Bytes()...)
	bundleHash := crypto.Keccak256Hash(src)

	gen := func(nonce uint64) (*types.Transaction, error) {
		var (
			chainId = g.InitOpts.ChainConfig.ChainID
			signer  = types.LatestSignerForChainID(chainId)
			key     = g.InitOpts.NodeKey
		)

		to, err := types.Sender(signer, swapTx)
		if err != nil {
			return nil, err
		}

		tx, err := types.NewTransactionWithMap(types.TxTypeEthereumDynamicFee, map[types.TxValueKeyType]interface{}{
			types.TxValueKeyNonce:      nonce,
			types.TxValueKeyTo:         &to,
			types.TxValueKeyAmount:     lendAmount(approveTxOrNil, swapTx),
			types.TxValueKeyData:       common.Hex2Bytes("0x"),
			types.TxValueKeyGasLimit:   params.TxGas,
			types.TxValueKeyGasFeeCap:  swapTx.GasFeeCap(),
			types.TxValueKeyGasTipCap:  swapTx.GasTipCap(),
			types.TxValueKeyAccessList: types.AccessList{},
			types.TxValueKeyChainID:    chainId,
		})
		if err != nil {
			return nil, err
		}

		err = tx.Sign(signer, key)
		return tx, err
	}

	return builder.NewTxOrGenFromGen(gen, bundleHash)
}

func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter

	g.allowedTokens = map[common.Address]bool{}
	for _, addr := range tokens {
		// all tokens are allowed if nil
		if g.GaslessConfig.AllowedTokens == nil {
			g.allowedTokens[addr] = true
		}
		for _, allowed := range g.GaslessConfig.AllowedTokens {
			if addr == allowed {
				g.allowedTokens[addr] = true
			}
		}
	}

	return nil
}

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

func getGaslessInfo(bc backends.BlockChainForCaller, header *types.Header) (common.Address, []common.Address, error) {
	statedb, err := bc.StateAt(header.Root)
	if err != nil {
		return common.Address{}, nil, err
	}

	// If Registry is not installed, do not query GaslessSwapRouter contract.
	if statedb.GetCode(system.RegistryAddr) == nil || bc.Config().IsRandaoForkBlockParent(header.Number) {
		return common.Address{}, nil, nil
	}

	caller, err := system.NewMultiCallContractCaller(statedb, bc, header)
	if err != nil {
		return common.Address{}, nil, err
	}

	opts := &bind.CallOpts{BlockNumber: header.Number}
	info, err := caller.MultiCallGaslessInfo(opts)

	return info.Gsr, info.Tokens, err
}

### Block building rules

Upon detection of GaslessTxs, the following logics are executed:

- Per sender, if exists, GaslessApproveTx is relocated before GaslessSwapTx.
- LendTxGenerator is prepended before GaslessApproveTx.
- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.
