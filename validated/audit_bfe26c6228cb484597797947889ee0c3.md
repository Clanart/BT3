### Title
Scanner reports immature coinbase outputs as spendable, enabling construction of consensus-invalid spends - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The external report concerns a protocol crediting itself funds it did not actually receive in a usable form (fee-on-transfer tokens reduce the real balance below the accounted amount, breaking accounting and withdrawals). The analog in bitcoin-serai is `Scanner::scan_block`, which returns `ReceivedOutput`s for coinbase-transaction outputs. Coinbase outputs are unspendable for 100 blocks by consensus rule, so the scanner reports "received" funds that are not actually spendable — the same class of "accounted value ≠ spendable value" bug. These indistinguishable `ReceivedOutput`s can be fed directly into `SignableTransaction::new`/`multisig`, which will produce and threshold-sign a transaction that spends an immature coinbase output. That transaction is consensus-invalid and will never confirm; the attempted spend's other real inputs are not burned (the tx is rejected), but any downstream accounting that marked those funds as available is corrupted, and the signing round itself consumes a nonce set on an unspendable intent.

### Finding Description

`Scanner::scan_block` iterates over every transaction in the block, including `block.txdata[0]` (the coinbase), via `scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:221-227`, `199-214`). `scan_transaction` matches solely on `output.script_pubkey` and wraps any match into a `ReceivedOutput` carrying the offset, `TxOut`, and `OutPoint` — with no flag distinguishing a coinbase output from a normal one.

A `ReceivedOutput` is the direct input type of `SignableTransaction::new` (`send.rs:150-256`), which builds `TxIn`s from `input.outpoint` and sums `input.output.value` toward `input_sat`. Neither `SignableTransaction::new` nor `TransactionSignMachine::sign` checks whether an input's outpoint originates from a coinbase transaction or whether that coinbase has reached 100-block maturity. `multisig` (`send.rs:273-285`) only verifies the script_pubkey matches the offset key, which it will for a coinbase output paying to the tweaked group key.

The only mitigation is a doc comment on `scan_block` stating "If received outputs must be immediately spendable, a post-processing pass is needed" (`mod.rs:218-220`). The type system and all downstream APIs treat these outputs identically to spendable ones; a caller that uses `scan_block` — the natural API for block scanning — gets poisoned inputs with no marker to filter on other than re-implementing `tx.is_coinbase()`/`block.txdata[0]` checks externally.

### Impact Explanation

An unprivileged external party can reach this: miners create coinbase outputs, but more generally, anyone can get a coinbase-like constraint only via mining — however the reachable trigger is simply that a scanned block's coinbase pays to a registered offset script (or an integrator scans `block.txdata` wholesale). More importantly, the value accounting is corrupted for any coinbase output: `ReceivedOutput::value()` returns the full amount which `SignableTransaction` will count toward `input_sat`, so the wallet/protocol treats funds as available balance that cannot move. A spend built on such an input is signed (burning a FROST preprocess/signing round and producing a valid-looking signature share set) yet the resulting transaction is consensus-invalid (BIP-30/COINBASE_MATURITY rule), so it can never be relayed or confirmed — the attempted withdrawal/settlement silently fails, mirroring the original report's "withdrawal becomes useless" impact.

### Likelihood Explanation

Medium-low. It requires a coinbase output to pay to one of the scanner's registered script_pubkeys (i.e., a miner directing the coinbase reward to the threshold key, or test/federated setups where this is plausible), plus a consumer of the library that uses `scan_block` and treats returned outputs as immediately spendable — exactly what the API shape encourages. No malicious validator or key compromise is required; the inputs (blocks) are untrusted public data.

### Recommendation

- In `scan_block`, skip `block.txdata[0]` (or check `tx.is_coinbase()` inside `scan_transaction`), since coinbase outputs can never be spent in the same block's context and the scanner has no height/maturity information to gate them correctly.
- Alternatively, add a `coinbase`/`immature` flag to `ReceivedOutput` and have `SignableTransaction::new` reject immature inputs, so the unspendability is enforced at the type/constructor level rather than in a doc comment.

### Proof of Concept

```rust
// networks/bitcoin context
// Given: a Block whose coinbase tx has an output paying to
// p2tr_script_buf(scanner_key) (offset 0 script).

let mut scanner = Scanner::new(group_key).unwrap();

// scan_block returns the coinbase output indistinguishably
let received = scanner.scan_block(&block);
assert_eq!(received.len(), 1);
let coinbase_output = received[0].clone(); // outpoint points into block.txdata[0]

// SignableTransaction happily counts it toward input_sat
let stx = SignableTransaction::new(
  vec![coinbase_output],
  &[(payment_script, DUST)],
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap(); // succeeds — no coinbase/maturity check

// multisig + preprocess + sign produce a threshold-signed transaction
let machine = stx.multisig(&keys).unwrap();
// ... FROST signing completes, yielding a Transaction spending an
// immature coinbase outpoint — rejected by every Bitcoin node
// (bad-txns-coinbase / COINBASE_MATURITY). Funds were "received"
// per the Scanner but were never spendable.
```

The flawed line is the unconditional loop in `scan_block` (`networks/bitcoin/src/wallet/mod.rs:221-227`) combined with the absence of any coinbase/maturity check in `SignableTransaction::new` (`send.rs:150-256`).
