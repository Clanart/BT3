### Title
`ReceivedOutput::read` accepts an offset/script_pubkey pair without verifying consistency, letting attacker-crafted bytes report unspendable outputs as belonging to a multisig key — ([File: networks/bitcoin/src/wallet/mod.rs:122-134](networks/bitcoin/src/wallet/mod.rs))

### Summary
CVE-2024-41075 was fixed by adding consistency checks so a completion message can only satisfy the request/object it actually corresponds to (the `fd`/`req` binding check). The analog in Serai's in-scope code is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`: it deserializes an `offset` scalar, a `TxOut`, and an `OutPoint` from untrusted bytes and returns a `ReceivedOutput` claiming "an output paying `key + G*offset` exists at `outpoint`" — yet it performs no check that `output.script_pubkey` is actually `p2tr_script_buf(key + G*offset)` for any key, nor that the outpoint/txid corresponds to a real on-chain output containing that `TxOut`. A `ReceivedOutput` is a claim; nothing in `read` validates the claim's internal consistency.

### Finding Description
`ReceivedOutput::read` reads three independent fields and stitches them together:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Contrast with the honest construction path, `Scanner::scan_transaction` (`mod.rs:199-214`), which only produces a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` yields the offset previously bound to that script — i.e., the `offset ↔ script_pubkey ↔ outpoint` triple is consistent by construction. The deserialization path drops this invariant entirely.

Downstream, `Output::key()` (`processor/src/networks/bitcoin.rs:112-122`) recomputes the implied group key as `script_key - G*offset`. With an honest `ReceivedOutput`, this returns the multisig key. With a crafted one, an attacker can make `key()` return *any* point: pick the victim's group key `K`, pick an arbitrary real `TxOut` paying someone else, and set `offset` such that `script_key - G*offset == K`. The processor then reports funds "received" under multisig `K` that `K` cannot spend — the literal "funds reported received that are not spendable" condition.

The `SignableTransaction::multisig` check (`send.rs:273-285`, `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`) prevents actually signing for such an input, but that converts the bug into a poisoned-UTXO: the false output can be registered/reported as a deposit before any spend attempt, corrupting accounting, and then bricks the spend path with `None`.

### Impact Explanation
An unprivileged party who can feed bytes into `ReceivedOutput::read`/`Output::read` (serialized network or coordinator messages carrying outputs) can fabricate deposit claims: outputs attributed to a threshold key they don't control and which are unspendable by it, or phantom outpoints entirely. This matches the CVE's class — completing a "request" (deserialization of an ownership claim) for an object it isn't bound to — and satisfies the "funds reported received that are not spendable" acceptance condition.

### Likelihood Explanation
Reachability depends on whether serialized `ReceivedOutput`/`Output` blobs cross a trust boundary (validator/processor messages, coordinator-supplied data). Within the wallet library alone, `read` is a public API on untrusted bytes per its signature; the missing check is unconditional. Exploitation requires only the ability to supply the bytes — no key material or collusion.

### Recommendation
Either (a) make `ReceivedOutput` construction private and add a checked constructor `new(scanner_key, output, outpoint)` that verifies `p2tr_script_buf(key + G*offset) == output.script_pubkey`, or (b) have `read` take the expected group key and reject offsets that don't reproduce the decoded `script_pubkey`. Additionally verify the claimed `outpoint` actually resolves to the decoded `TxOut` when a chain view is available.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
