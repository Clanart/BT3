### Title
OP_RETURN `data` output is omitted from fee/vsize calculation, producing transactions that underpay and can fall below the minimum relay fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` into `tx_outs`, but both `calculate_weight_vbytes` call sites compute the transaction weight/vbytes from `payments` (and `change`) only — the data output is never included. The analog of the reference bug (an accounting path that silently mis-handles value attached to an operation) is a fee-accounting error: the wallet commits to a fee (`needed_fee`) that does not correspond to the transaction actually constructed and signed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
// line 194-202: the OP_RETURN output is added to the real TX
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}

// line 204: but weight/vbytes are computed WITHOUT the data output
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (lines 62-127) builds a mock `Transaction` whose `output` vector contains only `payments` and optionally `change`. The `OP_RETURN` output (~11 + len(data) bytes, up to ~91 bytes / ~91 vbytes) is absent, so:

1. `needed_fee = fee_per_vbyte * vbytes` is short by up to `91 * fee_per_vbyte` sats. The actual signed transaction pays `fee() = input_sat - payment_sat` sats over a vsize larger than `vbytes`, so the *effective* fee rate is strictly below the caller-requested `fee_per_vbyte`.
2. The `TooLowFee` guard (line 211) checks `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the understated `vbytes`. A transaction whose true vsize is ~91 bytes larger can pass this check yet have an actual fee rate below the minimum relay fee, making it non-standard and un-relayable.
3. The change branch (lines 224-235) repeats the same omission: `vbytes_with_change` also excludes the data output, so `fee_with_change` and the change amount are computed against an incorrect fee.

Unlike the no-change leftover burn (which is documented at lines 145-147), nothing documents that specifying `data` silently invalidates the fee-rate contract.

### Impact Explanation
Any caller that supplies `data` receives a `SignableTransaction` that the threshold group then signs via `TransactionSignMachine::sign` (lines 355-398), committing all inputs under `Prevouts::All`. The resulting transaction:

- pays a fee rate below the requested `fee_per_vbyte` (silent mischarge / degraded confirmation), or
- in the boundary case, is below `DEFAULT_MIN_RELAY_TX_FEE` and cannot be broadcast at all, leaving the inputs unusable through this path — funds the wallet believes were spent are not spendable via the produced transaction.

This is a concrete incorrect-formula defect reachable purely through the public `SignableTransaction::new` API via the untrusted `data` parameter, matching the accepted "incorrect verifier/fee formula" and "funds reported received that are not spendable" criteria.

### Likelihood Explanation
Deterministic whenever `data: Some(_)` is passed. Every byte of OP_RETURN data inflates the real vsize while `needed_fee` stays fixed, so any non-empty `data` produces a fee rate below what was requested; near the min-fee boundary it produces a non-relayable transaction.

### Recommendation
Include the data output in the weight/vbytes accounting. Either pass a `data: Option<&[u8]>` (or its serialized output length) into `calculate_weight_vbytes` and append a `TxOut` with the real `OP_RETURN` `script_pubkey` to the mock transaction, or compute `vbytes` as `calculate_weight_vbytes(...) + serialized_op_return_len` at both call sites (lines 204 and 225-226). Perform the `TooLowFee` and `NotEnoughFunds` checks against the corrected fee.

### Proof of Concept
Conceptual, using the public API:

```rust
// one confirmed P2TR input worth `value` sats, one payment
let inputs = vec![received_output];
let payments = vec![(dest_script, 1000u64)];
let data = Some(vec![0u8; 80]); // max allowed, passes the <= 80 check

let tx = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();

// tx.needed_fee() = fee_per_vbyte * vbytes_without_op_return
// actual tx.vsize()  = vbytes_without_op_return + ~91
// effective rate   = tx.fee() / tx.vsize()  <  fee_per_vbyte
assert!(tx.fee() < tx.needed_fee() + fee_per_vbyte * 91); // rate shortfall
```

Choose `fee_per_vbyte` such that `needed_fee` just clears `(DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000`; the real transaction's fee rate then falls below the relay minimum and the fully-signed transaction is rejected by the network.
