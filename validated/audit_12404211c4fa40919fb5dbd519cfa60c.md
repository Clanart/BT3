## Title
`handleGetResponses()` never checks for an already-delivered response, unlike `handlePostRequests()`'s duplicate-receipt guard - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequests()` explicitly rejects any leaf whose request has already been delivered by checking `host.requestReceipts(leaf.request.hash()) != address(0)` before calling `dispatchIncoming`. The parallel `handleGetResponses()` function performs no equivalent check against `responseReceipts` — its per-leaf loop only verifies that the request is "known" (`meta.sender != address(0)`), which stays true forever since the source-side request commitment is never cleared for GET flows. This mirrors exactly the reported bug class: a replay/duplicate guard exists on one code path (POST) but was not carried over to the structurally identical sibling path (GET), letting a previously-delivered leaf be re-submitted. ### Finding Description
In `handlePostRequests`, the second loop is the concrete "duplicate check" analog to `StreamingNFT`'s missing blacklist check:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    // duplicate request?
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [1](#0-0) 

`handleGetResponses` performs the equivalent membership-proof verification against a Merkle Mountain Range root (which, once stored, remains valid forever and can be re-proven repeatedly), but its per-leaf loop only checks that the originating request is "known":
```solidity
for (uint256 i = 0; i < responsesLength; ++i) {
    GetResponseLeaf memory leaf = message.responses[i];
    // don't check for timeouts because it's checked on Hyperbridge
    // known request? also serves as source check
    FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
    if (meta.sender == address(0)) revert UnknownMessage();
    leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
}
``` [3](#0-2) 

There is no `host.responseReceipts(...) != address(0)) revert DuplicateMessage()` check here, even though `EvmHost` maintains exactly such a receipt map for GET responses (`_responseReceipts`), symmetric to `_requestReceipts` used for POST:
```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    // replay protection
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({
        relayer: relayer,
        responseCommitment: response.hash()
    });
    ...
    uint256 fee = _requestCommitments[commitment].fee;
    if (fee != 0) {
        IERC20(feeToken()).safeTransfer(relayer, fee);
    }
    emit GetRequestHandled({commitment: commitment, relayer: relayer});
}
``` [4](#0-3) 

Because `_responseReceipts[commitment]` is unconditionally overwritten rather than checked-then-set, and `_requestCommitments[commitment]` (which holds the `fee`) is never deleted on the GET path, a relayer can call `handleGetResponses` multiple times with the same already-delivered leaf: the proof re-verifies successfully against the same historical MMR root, `meta.sender` is still non-zero (source commitment untouched), and `dispatchIncoming` re-invokes `onGetResponse` on the destination `IApp` and re-pays the relayer fee out of the host's fee-token balance every time the callback succeeds.

### Impact Explanation
This is a false/duplicate-acceptance and repeated-payout bug at the core host/handler layer, matching the bounty categories of "replay/double-claim/double-settlement" and "stealing or loss of funds":
- The relayer fee for a GET response is paid on every successful replay, not just the first delivery, directly draining `feeToken()` balances held by `EvmHost` for anyone (any relayer) who resubmits an already-included leaf.
- Any destination `IApp` module whose `onGetResponse` implementation is not independently idempotent will have its accept/response logic re-executed, an unauthorized re-execution of application logic that the ISMP host contract is supposed to guarantee happens exactly once (this is the entire purpose of `requestReceipts`/`responseReceipts`).

### Likelihood Explanation
The call is unprivileged: `handleGetResponses` is a public/external entrypoint on `HandlerV2`, callable by any relayer, requiring only a valid (already-once-used) MMR inclusion proof, which by definition remains valid forever once the corresponding overlay root is committed. No malicious peer, prover, or governance actor is needed — a completely honest relayer's original calldata can simply be resubmitted by anyone who observed it on-chain.

### Recommendation
Add the same duplicate-receipt guard used in `handlePostRequests` to `handleGetResponses`, checking `host.responseReceipts(leaf.response.hash())` (or an equivalent commitment-keyed receipt) before adding the leaf to the proof set / before dispatching, and revert with `DuplicateMessage` on a hit. Additionally, delete or mark `_requestCommitments[commitment]` as consumed once its fee has been paid in `EvmHost.dispatchIncoming(GetResponse, ...)` so a second successful delivery (if ever reached) cannot pay out the fee twice.

### Proof of Concept
1. Relayer submits a valid `GetResponseMessage` containing leaf `L` for a previously-dispatched GET request; `handleGetResponses` verifies the MMR proof, calls `EvmHost.dispatchIncoming(L.response, relayer)`, which succeeds, pays `fee`, and sets `_responseReceipts[commitment]`.
2. The same relayer (or anyone) resubmits an identical `GetResponseMessage` with leaf `L` and the same `request.proof.height`/root.
3. `handleGetResponses` re-verifies the same MMR proof against the still-stored `overlayRoot` (line succeeds), checks `meta.sender != address(0)` (still true, `_requestCommitments` untouched) — no rejection occurs.
4. `dispatchIncoming` is invoked again: `_responseReceipts[commitment]` is overwritten (not checked), `onGetResponse` is called again on the destination module, and if it returns success, `fee` is transferred to the relayer a second time. [2](#0-1) [4](#0-3) 

**Note on completeness:** the tool context I retrieved for `handleGetResponses` was truncated right after the `InvalidProof` check (line 239-240); I did not see the exact final dispatch loop that calls `host.dispatchIncoming(leaf.response, ...)`. This is inferred by strong structural symmetry with `handlePostRequests`'s two-loop pattern (verify-then-dispatch) and by the absence of any `responseReceipts`/duplicate check anywhere in the visible portion of the function. A Devin session with full file access should confirm the exact final loop body in `handleGetResponses` before finalizing a fix, but the missing-check pattern itself is clearly evidenced by the codebase.

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
