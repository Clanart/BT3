### Title
Payout OP_RETURN `operator_xonlypk` is unauthenticated due to `SinglePlusAnyoneCanPay` sighash, letting anyone front a withdrawal under a false operator's name - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/rpc/parser/operator.rs`, `circuits-lib/src/bridge_circuit/mod.rs`)

### Summary
The binding claimed by `deposit_constant`/`journal_hash` is: `operator_xonlypk` (hashed into the circuit output) == the operator who actually funded the payout to `user_wd_outpoint`'s owner. This binding is false: the mandatory `TapSighashType::SinglePlusAnyoneCanPay` sighash used for the user's withdrawal signature does not commit to the OP_RETURN output (index 2) or to any additional funding inputs, so anyone who obtains the user's signature can build their own payout transaction, fund it themselves, and stamp an arbitrary (real) operator's x-only pubkey into the OP_RETURN.

### Finding Description
`create_payout_txhandler` builds the payout tx with input[0] = the user's withdrawal UTXO (key-spend), output[0] = user payout, output[1] = anchor, output[2] = OP_RETURN(`operator_xonly_pk`) [1](#0-0) . The user's signature over input[0] is required to use `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` [2](#0-1)  and verified again by `Operator::withdraw` [3](#0-2) .

`SIGHASH_SINGLE` only commits to the *single output at the same index as the signed input* (output[0] here); combined with `ANYONECANPAY` it also excludes all other inputs from the commitment. Consequently the signature places **no constraint** on output[2] (the OP_RETURN naming the operator) nor on any additional funding inputs added via `fund_raw_transaction` [4](#0-3) . Any party holding the user's `SinglePlusAnyoneCanPay` signature (obtained e.g. by being the withdrawing user themselves, or by observing it once submitted to the aggregator's public gRPC `withdraw`/`optimistic_payout` endpoints [5](#0-4) ) can construct and broadcast their own version of the payout transaction: same input[0]/output[0], but their own funding inputs and an arbitrary `operator_xonlypk` in the OP_RETURN.

Downstream, `bridge_circuit` reads the operator key straight from this attacker-controllable OP_RETURN with no ownership check:
```
let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)...
let deposit_constant = deposit_constant(operator_xonlypk, ..., *move_txid, ...);
``` [6](#0-5) . The only assertions made are that the payout tx's input[payout_input_index] matches `user_wd_outpoint`/`vout` from the storage proof [7](#0-6) ; nothing checks that the named operator actually supplied the funding inputs.

The verifier-side guard, `Verifier::is_kickoff_malicious`, likewise only checks that the OP_RETURN operator matches the kickoff's operator and that the committed payout blockhash matches — it never checks who funded the additional inputs of the payout tx [8](#0-7) . And `update_finalized_payouts` blindly stores whatever pubkey is parsed from OP_RETURN as `payout_payer_operator_xonly_pk` [9](#0-8) , which then drives the operator's own automation: `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered by *its own* `signer.xonly_public_key` and, if it finds a match, automatically calls `handle_finalized_payout` to start a kickoff and claim reimbursement — with no verification that this operator ever spent money on that payout [10](#0-9) , [11](#0-10) .

Exploit flow:
1. A user (attacker) requests a Citrea withdrawal and obtains their own valid `SinglePlusAnyoneCanPay` signature over `(withdrawal_utxo -> payout_output)`.
2. Instead of letting the intended honest operator front the payout, the attacker (or anyone who intercepts this signature before confirmation) builds their own payout transaction reusing input[0]/output[0], adds their own fee-paying inputs, and sets OP_RETURN to name an arbitrary *other*, real, uninvolved operator's x-only pubkey.
3. The attacker broadcasts/wins the race to spend the withdrawal UTXO first.
4. The named operator's own `PayoutCheckerTask` sees the payout credited to itself in the DB and automatically kicks off the reimbursement flow via `handle_finalized_payout`, claiming bridge-funded reimbursement for a payout it never funded.
5. `bridge_circuit` computes `deposit_constant`/`journal_hash` from this attacker-supplied OP_RETURN with no check that the named operator's UTXO/kickoff round actually paid the withdrawal, so the false attribution is accepted by the whole SPV-gated pipeline.

### Impact Explanation
An operator can be induced to spend its own round/collateral flow to claim reimbursement for a withdrawal it never funded, i.e., "an operator reimbursed for a payout it never funded" (Critical). This is repeatable across any withdrawal for which an attacker can obtain/race the user's `SinglePlusAnyoneCanPay` signature, and across any operator, since any valid x-only pubkey can be placed in the OP_RETURN. In the milder variant (naming a nonexistent/uninvolved key or one that no operator claims), the legitimate withdrawal UTXO is irreversibly consumed by the attacker's transaction, permanently preventing the intended operator from ever fronting/being reimbursed for that withdrawal ("an honest operator permanently unable to be reimbursed").

### Likelihood Explanation
No special privilege is needed beyond being the withdrawing user (or observing/racing a `SinglePlusAnyoneCanPay` signature before it confirms) and paying normal Bitcoin fees to win the race for spending the withdrawal UTXO — both squarely within the unprivileged attacker capabilities defined (broadcast transactions, choose signature/sighash flag, choose OP_RETURN, call the aggregator's public `withdraw`/`optimistic_payout` gRPC). The cost is limited to Bitcoin transaction fees; the attack is deterministic once the race is won, and repeatable per withdrawal.

### Recommendation
Bind the OP_RETURN `operator_xonlypk` (and ideally all funding inputs) to the same sighash commitment as the withdrawal UTXO spend — e.g., require the user's signature to use `TapSighashType::All` (or `AllPlusAnyoneCanPay`) so it commits to all outputs including the OP_RETURN, or otherwise cryptographically bind the payout's declared operator to the transaction before it can be considered valid for reimbursement purposes, and add an explicit check in `is_kickoff_malicious`/`update_finalized_payouts` that the funding inputs of the payout tx are attributable to the operator named in the OP_RETURN.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
