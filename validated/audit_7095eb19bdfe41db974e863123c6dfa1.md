### Title
Attacker-funded payout tx can frame an arbitrary operator by writing that operator's key into the unsigned OP_RETURN, causing the vault UTXO to be reimbursed to an operator that never funded the payout - (File: circuits-lib/src/bridge_circuit/mod.rs, core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
The withdrawer's `SinglePlusAnyoneCanPay` signature over the payout transaction only commits to input 0 and output 0 (the user's payout output); every other input/output — including the OP_RETURN that names the fronting operator's `operator_xonly_pk` — is unconstrained. Since bridge-circuit host code (`host_deposit_constant`/`deposit_constant`) and on-chain trackers (`update_finalized_payouts`, `is_kickoff_malicious`) trust "the operator named in the first OP_RETURN" as "the operator that funded the payout," any unprivileged withdrawer can self-fund the entire payout transaction and put a targeted, real operator's `xonly_pk` in the OP_RETURN, causing that operator's own automation to later claim reimbursement (unlocking the deposit's move-to-vault UTXO) for a payout it never made.

### Finding Description
The claimed binding is: `operator_xonlypk_in_op_return == operator_that_actually_funded_and_broadcast_the_payout_tx`.

- `create_payout_txhandler` builds the payout tx with a fixed output layout `[user payout, anchor, OP_RETURN(operator_xonly_pk)]` and only signs input 0 with the withdrawer's key using `SinglePlusAnyoneCanPay`: [1](#0-0) .
- The operator's own `withdraw` handler verifies only that this specific sighash (which is `SIGHASH_SINGLE|ANYONECANPAY`) is valid for input 0/output 0, then funds the rest via `fund_raw_transaction` with `add_inputs: true`: [2](#0-1) . Nothing prevents a third party from doing the exact same thing with their own funds and their own choice of OP_RETURN pubkey, because `SinglePlusAnyoneCanPay` explicitly does not cover the anchor output, any additional funding inputs, or the OP_RETURN output.
- Downstream, the verifier's chain scanner blindly extracts "the payer" from the first OP_RETURN with no check that the named operator actually contributed any input to the transaction: [3](#0-2) .
- The operator's own automated `PayoutCheckerTask` picks up any payout in the DB attributed to its own `xonly_pk` and immediately proceeds to build/submit a kickoff and claim reimbursement: [4](#0-3) .
- The only verifier-side guard, `is_kickoff_malicious`, checks that the operator *submitting the kickoff* matches the operator named in the OP_RETURN — a self-consistency check, not a funding-attribution check: [5](#0-4) .
- The bridge circuit itself derives `deposit_constant` purely from `get_first_op_return_output`/`parse_op_return_data` with no reconciliation against who signed/funded the transaction: [6](#0-5)  and [7](#0-6) .

Exploit flow: the attacker (an ordinary withdrawer) calls Citrea's withdraw with their own dust UTXO and signs it with `SinglePlusAnyoneCanPay` as usual. Instead of waiting for an operator to front the payout, the attacker themselves constructs and broadcasts the completed payout transaction — self-funding the output (paying themselves) and inserting a real, targeted operator X's public `xonly_pk` (obtainable via `GetXOnlyPublicKey`/`fetch_operator_keys`) into the OP_RETURN. Operator X never signed, broadcast, or funded anything, but the verifier's chain sync and Operator X's own `PayoutCheckerTask` interpret this as "operator X fronted this withdrawal," and Operator X's automation proceeds to submit a kickoff, pass `is_kickoff_malicious` (trivially, since the submitting key matches the OP_RETURN key), and claim reimbursement — unlocking the deposit's move-to-vault UTXO collateral without operator X ever having fronted BTC for it.

### Impact Explanation
This breaks the Critical guarantee that reimbursement is tied to an operator that actually fronted a withdrawal: the deposit's move-to-vault UTXO collateral is released as reimbursement to an operator that never funded the payout ("an operator reimbursed for a payout it never funded" / vault BTC released "without a matching fronted withdrawal" by that operator). The attack is repeatable across any deposit/withdrawal for which the withdrawer is willing to self-fund the payout (recoverable at near-zero net cost, since they pay themselves), and can target any registered operator whose public key is discoverable. This can also be weaponized to force an unwanted kickoff/round cycle onto a targeted operator, consuming its kickoff connectors and rounds.

### Likelihood Explanation
No collusion, key compromise, or privileged role is required — only capabilities explicitly granted to the unprivileged attacker (broadcast a Bitcoin transaction, call withdraw on the Citrea bridge contract, choose a Schnorr signature/sighash flag, choose an OP_RETURN). The attacker must front the withdrawal amount out of pocket to their own output, but recovers it entirely since they are also the withdrawal's beneficiary; only Bitcoin fees are a net cost. This is straightforward to demonstrate deterministically without requiring watchtower challenges, disprove races, or timing games.

### Recommendation
Bind the OP_RETURN operator key to the actual funder cryptographically, e.g., require the operator to sign the full payout transaction (or at least the OP_RETURN output and all non-withdrawer inputs) with a signature verifiable in `bridge_circuit`, or require the operator's registered key to correspond to one of the transaction's other inputs. Alternatively, have `is_kickoff_malicious`/chain sync additionally verify that the operator claimed in the OP_RETURN actually authorized/produced that specific broadcast, not merely that it is self-consistent with the kickoff submitter.

### Proof of Concept
`cargo test` plan (circuits-lib and/or core):
1. Build a payout tx per `create_payout_txhandler` semantics: input 0 = withdrawer's dust UTXO with `SinglePlusAnyoneCanPay` signature; output 0 = withdrawer's payout output; add an attacker-funded extra input and anchor output; set OP_RETURN to operator A's `xonly_pk`.
2. Verify the withdrawer's `in_signature` still validates against `calculate_sighash_txin(0, SinglePlusAnyoneCanPay)` for this modified tx (proving the signature doesn't cover the OP_RETURN/extra inputs).
3. Call `deposit_constant(...)` twice: once using operator A's `xonly_pk` (from the crafted OP_RETURN) and once using the real funding key (attacker's own key/any other value) — assert the two `DepositConstant` values differ, and assert both are consistent with the same `payout_spv`/`user_wd_outpoint`/`move_txid`, showing the circuit cannot distinguish "named operator" from "actual funder."
4. (Integration) Run the `PayoutCheckerTask` simulation against a DB row where `payout_payer_operator_xonly_pk` is operator A but the corresponding on-chain payout tx's non-signed inputs were not funded by operator A; assert `handle_finalized_payout` proceeds to build/submit a kickoff for operator A, and `is_kickoff_malicious` returns `false` (not malicious) despite operator A having contributed no funds.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}
