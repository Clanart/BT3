### Title
Attacker-controlled `presumed_origin` causes Serai to "refund" deposit outputs to an arbitrary address - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary

Like `onlyEOAEx()` relying on `EXTCODESIZE` to authenticate the caller's nature — a property the caller does not actually control — `Bitcoin::get_outputs` determines a deposit's origin from an on-chain heuristic (`tx.input[0]`'s spent `script_pubkey`) rather than from authenticated data. That heuristic is fully attacker-malleable, and the resulting `presumed_origin` is trusted as the refund destination for deposits that cannot be turned into instructions.

### Finding Description

When scanning blocks, every output paying a Serai-controlled address is stamped with a `presumed_origin` taken from the script of the *first input's* spent output:

```rust
// processor/src/networks/bitcoin.rs
let spent_output = { let input = &tx.input[0]; ... };
Address::new(spent_output.script_pubkey)
...
for output in &mut outputs {
  ...
  output.presumed_origin.clone_from(&presumed_origin);
}
``` [1](#0-0) 

The multisig layer then consumes this as the refund identity for any external output whose `data` fails to decode into a `RefundableInInstruction` (oversized `data`, invalid `Shorthand`, or non-convertible shorthand all short-circuit to returning `presumed_origin` with `None` instruction):

```rust
let presumed_origin = output.presumed_origin().map(|address| { ... });
...
instruction.origin.or(presumed_origin)
``` [2](#0-1) 

A transaction's first input is not proof of who funded a specific output. In a multi-input transaction (CoinJoin/PayJoin, batch spends, wallet consolidation), `tx.input[0]` can belong to a different party than the value flowing into Serai's output — or the attacker can simply arrange input ordering so input[0] is whichever of their own or a victim's script they choose. The `onlyEOA` analog holds exactly: Serai infers "who sent this" from a property (`input[0]` script, like `msg.sender` being a contract under construction) that does not actually establish the identity it assumes.

### Impact Explanation

When `presumed_origin` is used as the refund origin for a failed/uninstructioned deposit, Serai signs a Plan paying the *full output balance* to the attacker-chosen address. In a PayJoin/CoinJoin-style construction, the attacker contributes a small input, places it (or a chosen script) as `tx.input[0]`, and has the joint transaction pay Serai's `External` offset address with no/invalid instruction data. Other participants' inputs fund the Serai output; Serai "refunds" the entire output value to `input[0]`'s address — i.e., to the attacker — even though the attacker only supplied a fraction of the value. This is a concrete "signing of an unintended message / unspendable-or-misdirected funds" impact: the multisig signs a payout to an address that never deposited that value.

### Likelihood Explanation

Reachable by any unprivileged Bitcoin user: they only need to construct a valid Bitcoin transaction paying a Serai deposit address, which the `Scanner` in `networks/bitcoin/src/wallet` will match by `script_pubkey`. No malicious validator, no collusion threshold, no leaked keys — the attacker's degrees of freedom are just standard Bitcoin transaction construction. The code even acknowledges the heuristic is imperfect ("This may identify the P2WSH output *embedding the InInstruction* as the origin... TODO"), confirming it is an assumed-not-proven property, precisely the class of the original `EXTCODESIZE` bug.

### Recommendation

Stop treating `tx.input[0]`'s script as the authenticated origin for refunds. Either require the origin to be explicitly committed inside the instruction data (a `RefundableInInstruction` that both parses and binds an origin), or decline automatic refunds for any transaction whose inputs cannot be unambiguously attributed to a single sender (e.g., skip refund when the transaction has multiple inputs with distinct input `script_pubkey`s). The `instruction.origin.or(presumed_origin)` fallback should only fire when the origin is cryptographically attributable, not merely presumed.

### Proof of Concept

1. Attacker arranges a multi-input transaction (e.g., joins/constructs a CoinJoin or crafts a tx spending an input they control plus an input whose script is an attacker-controlled reuse/vanity address) such that `tx.input[0]`'s prevout script resolves to address `A`, and an output pays Serai's `External`-offset address for amount `V`.
2. The transaction carries no valid `OP_RETURN`/witness data (or oversized/invalid `data`), so `extract_serai_data`/`Shorthand::decode` fails and `instruction_from_output` returns `(Some(A), None)`.
3. `Bitcoin::get_outputs` stamps `presumed_origin = A`; the refund path builds a Plan paying `V` to `A`.
4. The multisig signs and publishes a transaction paying `V` to `A`, despite `A` having contributed less than `V` (or nothing) to the deposit.
