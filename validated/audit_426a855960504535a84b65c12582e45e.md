### Title
Unbounded recursive decoding of `AccountKeyRoleBased` in AccountUpdate transactions can cause a stack-overflow panic (DoS) - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` recursively decode account-key data without any depth limit or a check that a `RoleBased` key does not itself contain another `RoleBased` key. An attacker can craft an `AccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction whose account-key payload nests `AccountKeyRoleBased` values many times, driving unbounded Go-level recursion during RLP decoding of the transaction. Since a Go stack overflow cannot be recovered from a `panic`/`recover`, this crashes the node processing the transaction — the same bug class as Helm's `strvals` stack-overflow DoS (GHSA-6rx9-889q-vv2r), where attacker-controlled, self-referential input drives recursive structure construction until the stack overflows.

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes a key type tag and then recursively decodes the corresponding `AccountKey` implementation: [1](#0-0) 

When the decoded type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` reads a list of RLP-encoded blobs and, for each element, invokes `AccountKeySerializer.DecodeRLP` again via `rlp.DecodeBytes`: [2](#0-1) 

This mutual recursion (`AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → …) has no depth guard: nothing prevents an `AccountKeyRoleBased` from containing another `AccountKeyRoleBased` as one of its role keys, so the nesting can be repeated as many times as fits in the transaction payload.

The only place in the codebase that explicitly rejects a nested `RoleBased` key is `checkAccountKeyZeroValues` in the JSON-RPC helper `EncodeAccountKey`, which is a client-side convenience API, not part of consensus-critical transaction validation: [3](#0-2) 

Because this nesting check lives only in an RPC helper (and is documented as a UX-level constraint — see the test comment "Nested RoleBasedKey is not allowed in Kaia" at [4](#0-3) ), it does not protect the actual on-chain decode path exercised when an `AccountUpdate` transaction is RLP-decoded from the network/tx pool/block body (`TxInternalDataSerializer.DecodeRLP` → the specific `TxInternalDataAccountUpdate`-family decoder → `AccountKeySerializer.DecodeRLP`, ultimately reaching the same recursive `AccountKeyRoleBased` decoder).

### Impact Explanation
An unprivileged transaction sender can submit (or broadcast) a single crafted `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction whose account-key field encodes deeply nested `AccountKeyRoleBased` structures. When any node (mempool ingestion, block validation, or RPC decoding) RLP-decodes this transaction, the recursive decoder can exhaust the goroutine stack and panic with a stack overflow, which Go cannot recover from. This can crash the affected node process — a Denial of Service impacting any node that receives or processes the transaction, matching the "Medium" DoS classification of the referenced advisory (CWE-400, CVSS AV:N/AC:L/PR:N/UI:N/A:L).

### Likelihood Explanation
Likelihood is moderate: the attacker needs only to construct a raw RLP-encoded `AccountUpdate` transaction (no special permissions, no need for it to be included in a block — decoding alone, e.g. during tx-pool admission, can trigger the crash) with a deeply nested `AccountKeyRoleBased` value. Building such a payload is mechanical (repeated wrapping), and the RLP size/list rules do not prevent arbitrarily deep, only arbitrarily wide, nesting for a bounded input size — but since each RoleBased-key encoding layer adds only a small fixed overhead, a moderately sized transaction can achieve enough nesting depth to overflow the stack, similar to how compact `strvals` array syntax achieved deep nesting cheaply in the Helm case.

### Recommendation
Enforce a maximum recursion/nesting depth (or explicitly reject `AccountKeyRoleBased` values that contain another `AccountKeyRoleBased`) inside `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` themselves — i.e., in the consensus-critical decode path — not merely in the `EncodeAccountKey` RPC helper. This mirrors the "roleBasedKey cannot contains a roleBasedKey" rule already present in `api_kaia.go`, but it must be applied uniformly wherever account keys are deserialized from transactions, blocks, or state.

### Proof of Concept
1. Construct an `AccountKeyPublic` (or any non-RoleBased leaf key) as the base key.
2. RLP-encode an `AccountKeySerializer` wrapping an `AccountKeyRoleBased` whose single element is itself an `AccountKeySerializer` wrapping another `AccountKeyRoleBased`, and repeat this nesting N times (N in the tens/hundreds of thousands, depending on available stack size).
3. Embed the resulting bytes as the account-key field of an `AccountUpdate` transaction and RLP-encode the full transaction per `TxInternalDataSerializer.DecodeRLP`.
4. Submit/broadcast the transaction, or call `rlp.DecodeBytes` on it directly (e.g., via `DecodeAccountKey` RPC or tx-pool ingestion) to trigger recursive decoding through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, exhausting the goroutine stack and panicking the process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
