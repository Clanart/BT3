## Title
Unsanitized `checkRun.htmlUrl` from GitHub API check-run object flows into `shell.openExternal` without scheme allow-listing - (File: `app/src/main-process/main.ts`, `app/src/lib/ci-checks/ci-checks.ts`)

### Summary
`getCheckRunStepURL` builds a URL by directly interpolating `checkRun.htmlUrl` — a value taken verbatim from the GitHub API's check-run `html_url` field — into a template literal, with no scheme validation. This string is passed through `dispatcher.openInBrowser` to the renderer's `openExternal` IPC proxy, and finally to the main process's `open-external` handler, which calls `shell.openExternal(path)` unconditionally for any scheme.

### Finding Description
`getCheckRunStepURL` in `app/src/lib/ci-checks/ci-checks.ts` builds the URL with no scheme check: [1](#0-0) 

`checkRun.htmlUrl` originates from the raw API response field `html_url` via `apiCheckRunToRefCheck`, with no sanitization: [2](#0-1) 

The button that triggers this is user-clickable ("View on GitHub" / job step external-view icon): [3](#0-2) 

Call sites pass the resulting URL straight to `dispatcher.openInBrowser` without any scheme check: [4](#0-3) [5](#0-4) 

`_openInBrowser` in `app-store.ts` (used by `Dispatcher.openInBrowser`) forwards directly to Electron's `shell.openExternal`: [6](#0-5) 

Finally, `main.ts`'s `open-external` IPC handler only *logs* when the scheme is `http://`/`https://`; it does not reject any other scheme before calling `shell.openExternal`: [7](#0-6) 

This confirms the claim in the question: there is no scheme allow-listing anywhere along this path — `getCheckRunStepURL` → `dispatcher.openInBrowser` → IPC `open-external` → `shell.openExternal`.

For comparison, the codebase does have a scheme-validation utility (`validateURL`) elsewhere for GitHub Enterprise server addresses, showing the team is aware of protocol-restriction needs in some flows but did not apply the same discipline to check-run URLs: [8](#0-7) 

### Impact Explanation
Electron's `shell.openExternal` hands the string to the OS's native URL/file launcher rather than executing it inside the app's Chromium context, so schemes like `javascript:` are not expected to execute script within Desktop's process. However, unrestricted scheme handling is a documented Electron anti-pattern (see Electron's own security guidance: "do not use openExternal with untrusted content") because:
- `file://` URLs (including UNC paths like `file://attacker-host/share/x`) can trigger local file access or force SMB authentication attempts that leak NTLM credentials on Windows.
- Arbitrary OS-registered custom protocol handlers (`mailto:`, vendor-specific schemes, etc.) can be invoked with attacker-chosen arguments, which historically has enabled RCE in other applications when the target handler itself mishandles arguments.

Since GitHub Desktop's own IPC handler performs no allow-listing, this class of unintended external-process invocation is reachable if a malicious/compromised CI provider (a GitHub App with Checks API access, or a legacy commit-status provider) sets an arbitrary `html_url`/`target_url` on a check run/status for a PR the victim views.

### Likelihood Explanation
Exploitation requires: (1) an attacker-controlled CI/Check-run/Status API object with a crafted `html_url`/`target_url`, and (2) the victim to click the "View on GitHub" / job-step external link button — i.e., a user-initiated click on attacker-influenced content, which fits the scope's "clicked links" category. It does not require local access, malware, or leaked credentials. The severity of the ultimate impact depends on the OS and installed protocol handlers, which is outside Desktop's control, so real-world impact is variable but the missing scheme check itself is a genuine gap.

### Recommendation
Enforce an `http:`/`https:` scheme allow-list before calling `shell.openExternal`, ideally in the `open-external` IPC handler in `main.ts` (rejecting/no-op for any other scheme), and/or validate `checkRun.htmlUrl` (and `repository.htmlURL`) against an `http(s)` allow-list in `getCheckRunStepURL` / `onViewCheckDetails` before invoking `dispatcher.openInBrowser`.

### Proof of Concept
1. Construct/mock an `IRefCheck` with `htmlUrl: 'file://attacker-host/share/x'` (or any non-http(s) scheme) as would result from a malicious check run's `html_url`.
2. Trigger `onViewJobStepExternally` on `CICheckRunActionsJobStepListItem` (`app/src/ui/check-runs/ci-check-run-actions-job-step-item.tsx:27-29`), which flows to `getCheckRunStepURL` producing `file://attacker-host/share/x/#step:1:1`.
3. This is passed to `dispatcher.openInBrowser` → IPC `open-external` → `main.ts:581-597`, where `shell.openExternal(path)` is called unconditionally for the non-http(s) URL, since the handler's `if` block only logs and never returns/rejects for other schemes. [7](#0-6) [9](#0-8)

export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
