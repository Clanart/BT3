### Title
Cached FROST preprocess seeds are persisted indefinitely and reused across repeated `sign` executions, enabling nonce reuse and secret key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The external report describes an authorization that is granted once and can never be revoked, leaving the grant exposed to any future change in the authorized party's behavior. In Serai's coordinator, the FROST preprocess seed is written to `CachedPreprocesses` keyed only by `context`, is never deleted or rotated, and is reloaded to deterministically regenerate the same nonces every time `preprocess_internal` runs. `share()` and `complete()` each trigger a full `machine.sign(...)` execution with those identical nonces. If the preprocess set or message presented to `sign` ever differs between those re-executions, the same FROST nonces sign two distinct challenges, which permits recovery of the validator's MuSig secret key — the exact consequence the file's own header warns about.

### Finding Description
`SigningProtocol::preprocess_internal` encrypts and stores a `CachedPreprocess` (the ChaCha20 seed) under `CachedPreprocesses: (context) -> [u8; 32]` on first use and thereafter always rebuilds the `AlgorithmSignMachine` via `AlgorithmSignMachine::from_cache` from that stored seed (coordinator/src/tributary/signing_protocol.rs:123-145). Because `seeded_preprocess` derives nonces deterministically from the seed (`crypto/frost/src/sign.rs:127-141`), every machine rebuilt from the same context has identical nonces and identical commitments.

Three call sites reuse this machine:

- `DkgConfirmer::preprocess` → `preprocess_internal`
- `DkgConfirmer::share` → `share_internal` → `preprocess_internal` + `machine.sign(preprocesses, msg)` (lines 150-181, 288-310)
- `DkgConfirmer::complete` → `share_internal` (line 321-324) → a second `machine.sign(...)`, then `complete_internal`

There is no code path that deletes or rotates the `CachedPreprocesses` entry; the grant of the seed is irrevocable for the lifetime of the context, mirroring the un-revokable approval. The safety of the design rests entirely on the assumption (documented in the header comment, lines 25-54) that `sign` is never re-executed over distinct received preprocesses or a distinct message. Both the preprocess map and the message (`set_keys_message`) are constructed from externally supplied, on-chain-transaction data — `preprocesses` come from other participants' published preprocess transactions and are fed through `read_preprocess`, and `key_pair`/`removed` come from chain state. The set passed to `complete` is whatever has accumulated on-chain at completion time, not necessarily the identical map `share` signed with; a preprocess transaction finalized between the share and complete executions changes the signing set, and therefore the per-participant binding factors and the FROST `rho`/challenge, while our nonces stay fixed.

### Impact Explanation
FROST nonce reuse across two different challenges (different signing set ⇒ different binding factor `rho`, or different `msg` ⇒ different challenge) allows an observer with both signature shares to solve for the signer's secret share linearly. Here the leaked secret is the coordinator validator's MuSig key share — the root-of-trust key used to confirm validator set keys on Substrate via `set_keys_message`. Recovery of that share degrades the security of the supermajority confirmation mechanism, and combined with threshold-many compromises enables forgery of set-key confirmations. This is concrete key share recovery, not merely a hardening concern: `spec/cryptography/FROST.md:51-55` and the header comment both acknowledge reuse enables third-party private key share recovery.

### Likelihood Explanation
The trigger does not require a cryptanalytic break or a malicious counterparty in the approval sense — it requires that the coordinator re-execute `share_internal` with a preprocess map or message differing from a prior execution under the same `(b"DkgConfirmer", attempt)` context. The natural candidate is `complete` re-signing with the final accumulated preprocess set versus `share` signing with the set present when the share transaction was produced; any rebroadcast/deduplication edge, a late-arriving preprocess, or a `removed`/`key_pair` delta between invocations produces the divergence. Since the seed is irrevocably cached, any such divergence — however it arises — is fatal rather than recoverable: there is no mechanism to revoke the cached preprocess and force fresh nonces the way a fresh `preprocess(&mut OsRng)` would. I could not fully trace `coordinator/src/tributary/handle.rs` (iteration limit) to confirm the exact share-vs-complete set divergence, so likelihood hinges on whether those two calls can ever observe different finalized preprocess sets; the caching layer itself provides no defense if they can.

### Recommendation
- Store, alongside the cached seed, a binding hash of the preprocess set and message actually signed (e.g., `Blake2s256(sorted_participants || preprocess_bytes || msg)`), and refuse to `sign` — or regenerate a fresh preprocess — if a subsequent `share`/`complete` execution under the same context is presented different inputs.
- Alternatively, delete/`remove` the `CachedPreprocesses` entry after the first successful `sign` for the context and require an explicit fresh preprocess for any further signing, making reuse impossible by construction rather than by BFT assumption.
- Implement the TODO noted at line 51-54: before publishing a share, verify the locally generated commitments match the commitments the coordinator previously published on-chain for that context.

### Proof of Concept
Conceptual trace against coordinator/src/tributary/signing_protocol.rs:

1. Context `C = (b"DkgConfirmer", attempt)`. First call to `share(preprocesses_A, key_pair)`:
   - `preprocess_internal` stores seed `s` under `C` (line 134), rebuilds machine with nonces `N` derived from `s` via `ChaCha20Rng::from_seed` (crypto/frost/src/sign.rs:127).
   - `machine.sign(preprocesses_A, msg_A)` emits share `σ_A` over nonces `N` with binding factors computed from set `A`.
2. A preprocess transaction from an additional validator is finalized, or `complete` is invoked with the full accumulated set `preprocesses_B ⊋ A`.
3. `complete(preprocesses_B, key_pair, shares)` calls `share_internal` again (line 322): `preprocess_internal` reloads the same seed `s` (line 137), regenerates identical nonces `N`, and `machine.sign(preprocesses_B, msg)` produces share `σ_B` over the same `N` but a different challenge/binding-factor linear combination.
4. Given `σ_A` and `σ_B`, solve the two-share linear system to recover the validator's MuSig secret share — the same share-recovery consequence documented as the reuse hazard in spec/cryptography/FROST.md:51-62 and sign.rs:84-87.

The structural parallel to the external report: just as the max-`uint256` approval to `LendingPool` persists with no revocation path and becomes exploitable if the counterparty's behavior changes, the cached seed persists with no revocation path and becomes exploitable the moment the signed-over inputs change — and nothing in the storage layer (`CachedPreprocesses` has no delete call anywhere in the crate) prevents it.
