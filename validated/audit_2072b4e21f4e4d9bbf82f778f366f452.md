### Title
Repo-relative Read/Grep/Glob scope in agentic commit review allows symlink-based disclosure of files outside the diff/repo boundary - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_investigate_prompt` explicitly tells the reviewing agent it "may Read these and any other file in the repo," and the accompanying `AGENTIC_INVESTIGATE_SYSTEM` prompt instructs it to "USE THEM AGGRESSIVELY" with Read/Grep/Glob [1](#0-0) [2](#0-1) . Scoping to "the repository" is enforced only by prompt text, not by a technical path/symlink guard visible in `review_api.py`; if a tracked path in the repo is a symlink to a file outside the repo (e.g. `~/.ssh/id_rsa`), the model's Read tool can dereference it and the resulting content can be quoted verbatim into a finding's `vulnerableCode`/`explanation` field, which is rendered into the guidance text returned to the user/commit flow via `format_findings` [3](#0-2) .

### Finding Description
The investigate-stage prompt is built with an unrestricted file scope: `touched_paths` (the actual diff) is listed, but the instructions say the model "may Read these and any other file in the repo," and separately the system prompt for the agent grants it Read/Grep/Glob "scoped to the repository" and orders it to "USE THEM AGGRESSIVELY" and to explore beyond the diff for cross-file taint tracing [4](#0-3) . There is no code in `review_api.py` (or in the portion of `llm.py` inspected) that canonicalizes/resolves symlinks or checks that a Read/Grep/Glob target's *realpath* stays under the repo root before or after the tool call — the boundary is asserted only in natural-language instructions to the model, which is not an enforceable security control.

The refute-stage prompt in the same file is aware that "workspace path jails" are a legitimate LLM-agent boundary and explicitly forbids treating a workspace-jail bypass as a "no privilege boundary" false positive, because "the model is the attacker, the user is the victim" [5](#0-4) . This confirms the codebase's own threat model recognizes symlink/workspace-jail escapes as a real class of finding, yet the investigate-stage prompt for this very reviewer grants unrestricted repo-wide Read/Grep/Glob without a corresponding technical guard.

Exploit flow: an attacker with ordinary (non-privileged) contribution access commits a tracked symlink at a path with a benign-looking name pointing outside the repo working tree (or to another sensitive file reachable by the same OS user, e.g. `~/.ssh/id_rsa`, `~/.aws/credentials`). When a legitimate user later runs `/commit-push-pr` on an unrelated change, `commit-push-pr.md` triggers the git-commit flow that invokes the agentic reviewer, whose system prompt tells it to explore beyond the diff "aggressively." If the model reads/greps the planted symlink, the target's content can flow into a `vulnerableCode` or `explanation` field, which `format_findings` renders verbatim into the guidance text shown to the user [6](#0-5) . Because the surrounding command (`commit-push-pr.md`) subsequently pushes and opens a PR (`gh pr create`) [7](#0-6) , if the leaked content is echoed into the commit message or PR body by the agent, it can exit the local machine entirely and land in a remote/shared/public repository — a boundary the "diff-only consent" model was meant to prevent.

### Impact Explanation
Confirmed impact is local-file-content disclosure beyond the reviewed diff, scoped to files readable by the invoking OS user (not privilege escalation to another user/root). The severity escalates from "annoyance" to "credential/secret disclosure to third parties" specifically because this reviewer's output can be woven into the commit message/PR description that `commit-push-pr.md` pushes and publishes via `gh pr create`, exposing private key material or credentials to remote collaborators/public repositories that never should have seen it. This matches the CWE-200/532-style "data exposure — who reads the sink" impact category the refute prompt itself calls a valid, non-refutable finding.

### Likelihood Explanation
Requires: (1) attacker has ordinary contribute/PR access to a repo the victim will later run `/commit-push-pr` against (or pushes to a shared branch the victim later commits on top of), and (2) the victim's OS-level Read permissions allow the symlink target to be read (true by default for the victim's own dotfiles/keys). No admin/maintainer privilege, leaked keys, or social engineering is required — planting a tracked symlink via a normal PR is a standard, low-effort action. Reachability depends on the model actually electing to Glob/Read the planted path during its "explore aggressively" instructions, which is plausible but non-deterministic (model-driven), and on the model quoting the symlink content into a finding rather than filtering it as irrelevant. This is a real but probabilistic (LLM-dependent) trigger, not a guaranteed 100%-repeatable mechanical bug.

### Recommendation
Add an explicit technical guard in the tool layer that spawns `Read`/`Grep`/`Glob` for the agentic reviewer: resolve the realpath of every tool target and reject/deny any path whose realpath falls outside `repo_root` (i.e., enforce a workspace jail with symlink-dereference checks), independent of the prompt-text instructions. Additionally, have `format_findings`/the investigate prompt refuse to surface raw quoted content for any `filePath` not in `touched_paths` unless a diff-line citation justifies it, per the invariant described in the question.

### Proof of Concept
Integration test:
1. Create a temp repo; commit a symlink `configs/settings.link -> ../../../../home/victim/.ssh/id_rsa` (or a same-user path outside the repo working tree) alongside an unrelated tracked diff.
2. Invoke `review_api.build_investigate_prompt` / the full `agentic_review` flow with `touched_paths` limited to the unrelated diff files (not including the symlink).
3. Mock/stub the model's Read tool call to resolve the symlink and return `id_rsa`'s content when asked to Read `configs/settings.link`.
4. Assert: the returned `findings` (via `format_findings`) never contain the literal `-----BEGIN OPENSSH PRIVATE KEY-----` marker or any content whose source file is not in `touched_paths`, unless the finding cites a specific diff line justifying the excursion.
5. Expected current behavior (bug): no guard blocks the symlink Read, and if the model quotes it, the assertion fails, demonstrating the leak path is technically unguarded (though model-dependent for triggering).

def format_findings(findings: list[dict[str, Any]]) -> str:
    """Render findings as the same text block the CC plugin emits to Claude."""
    by_file: dict[str, list[dict[str, Any]]] = {}
    for v in findings:
        by_file.setdefault(v.get("filePath", "unknown"), []).append(v)
    lines = [
        "Security Review: Potential vulnerabilities detected",
        "",
        f"Affected files: {', '.join(by_file)}",
        "The following issues were flagged by automated security review. "
        "Address each, or briefly note why it doesn't apply. Valid reasons "
        "to proceed without changes: the user explicitly asked for this and "
        "you've already surfaced the security tradeoffs, or the pattern "
        "isn't actually exploitable in this context. Do not dismiss "
        "findings solely because the service is internal-only — internal "
        "services are common SSRF/IDOR targets:",
        "",
    ]
    n = 1
    for fp, vs in by_file.items():
        lines.append(f"  {fp}:")
        for v in vs:
            sev = (v.get("severity") or "medium").upper()
            lines.append(
                f"    {n}. [{sev}] [{v.get('category', 'Unknown')}] "
                f"{v.get('vulnerableCode', 'N/A')}"
            )
            lines.append(f"       Suggested fix: {v.get('fix', 'N/A')}")
            lines.append("")
            n += 1
