### Title
Stale diff line-index reuse in partial-commit patch generation causes silent mis-staging of content - ([File: app/src/lib/git/apply.ts])

### Summary
`applyPatchToIndex()` re-fetches a **fresh** working-directory diff at apply/commit time via `getWorkingDirectoryDiff()`, but then formats the patch using `file.selection` — a `DiffSelection` whose selected line indices were computed earlier against the diff the user actually *saw* in the Changes view. If the working tree content changes between "diff shown to user" and "diff fetched at apply time", the positional line indices no longer correspond to the same content, and `formatPatch()` will silently select/deselect the wrong lines.

### Finding Description
The partial-commit flow works as follows:
1. The UI loads and caches a diff for the selected file and lets the user pick lines to include, recording the choice as `DiffSelection` keyed by **absolute line index** in that diff (`app/src/lib/stores/app-store.ts` `updateChangesWorkingDirectoryDiff`, and `app/src/ui/diff/side-by-side-diff.tsx` `onLineNumberCheckedChanged`, which calls `selection.withLineSelection(lineBefore/lineAfter, isSelected)`).
2. `app-store.ts` even acknowledges the diff can go stale: `updateChangesState` recomputes `selectableLines` from a newly-fetched diff and remaps the selection (`app/src/lib/stores/app-store.ts:3478-3497` "The diff might have changed dramatically since last we loaded it... just settle on updating the selectable lines").
3. However, at the moment of actually staging the patch, `applyPatchToIndex()` in `app/src/lib/git/apply.ts:60` calls `getWorkingDirectoryDiff(repository, file)` **again**, producing a brand-new `IDiff` object independent of whatever diff the remap logic in step 2 last synchronized against.
4. This freshly-fetched diff, together with the *old* `file.selection`, is passed straight to `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129`), which decides inclusion purely by `file.selection.isSelected(absoluteIndex)` where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` (`app/src/lib/patch-formatter.ts:144,157`).

The broken invariant: the "cursor" used to decide which lines are staged (the selection's line indices) is bound to the diff the user reviewed, but the code applies it against a different, later-fetched diff — analogous to using `oldUserPoint.ts` (a stale timestamp/reference) instead of `weekCursor` (the current one) in the audited contract. There is no content/hash check ensuring the diff used for selection and the diff used for patch construction are the same snapshot. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
If the working-directory file content is modified between the time the diff is rendered/selected (e.g., a build tool, linter/formatter, git hook, background sync process, or any process spawned from within the repository that touches tracked files) and the time the user clicks "Commit", the absolute-index-based selection can map to unrelated lines in the newly generated hunks. This causes **silent corruption of what the user commits**: lines the user explicitly deselected could be staged and committed/pushed, or lines they intended to include could be silently dropped — with no warning to the user, since Desktop shows a diff that is not the one actually applied. This falls squarely under the accepted impact category of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires attacker-controllable content changes in the repository's working tree occurring in the window between diff rendering and commit execution (e.g., via a repository-provided build/watch script, editor auto-format-on-save triggered by a malicious repo config, or any tool that mutates tracked files asynchronously) — a scenario consistent with the allowed threat model ("attacker controls a cloned/fetched repository"). It does not require local/physical access, admin rights, or social engineering beyond the user opening/committing in a repository containing such tooling. I was not able to fully trace the exact call path from `createCommit` (`app/src/lib/git/commit.ts`) back through the dispatcher to confirm whether any additional guard re-validates diff identity immediately before `applyPatchToIndex` is invoked in the current commit flow, since I ran out of tool-call budget before reading `commit.ts` in full — this is a gap in verification, and a background agent should confirm whether such a guard exists.

### Recommendation
Ensure the diff used to build the selection and the diff used to construct the patch are the exact same object/snapshot: pass the already-loaded (or freshly re-validated) diff from the Changes state into `applyPatchToIndex` instead of re-fetching a new one, or compare a content hash/mtime of the file between selection time and apply time and abort/re-diff-and-warn on mismatch, mirroring the reasoning already partially applied in `updateChangedFiles`'s selectable-line remap.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has two independent hunks.
2. In the Changes view, select only specific lines in hunk #1 for partial commit (deselect hunk #2 entirely).
3. Before clicking "Commit", have another process (e.g., a script the repository triggers, or manually edit the file rapidly) alter the file so that hunk boundaries shift (add/remove lines above the previously selected hunk).
4. Click "Commit". `applyPatchToIndex` calls `getWorkingDirectoryDiff` again, obtaining hunks with shifted `unifiedDiffStart` offsets, while `file.selection` still holds indices from the old diff.
5. Inspect the resulting commit: lines from the new diff at the old absolute indices get included/excluded, not matching what was visually selected by the user, confirming silent mis-staging.
