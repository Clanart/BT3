### Title
Copilot conflict-resolution reassembly trusts positional hunk order without verifying the AI's hunks match the on-disk conflict blocks it is spliced into — (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Axelar report's root cause is a **count/shape check that stands in for a full semantic-equivalence check**: the protocol validates that a `TokenId` matches, but never verifies that the decimals (the actual value interpretation) agree between sender and receiver, so a bridged amount gets silently reinterpreted and corrupted. GitHub Desktop's AI merge-conflict resolution feature has the same structural weakness applied to a different value: it validates that the *number* of resolved hunks returned by Copilot matches the *number* of conflict blocks found on disk, but it never verifies that hunk *N* returned by the model actually corresponds to conflict block *N* in the file. The mapping is done purely by array position (`hunkIndex`), across two independently-written marker parsers.

### Finding Description
`buildConflictContext` extracts conflict hunks from the on-disk file using `extractConflictHunks` (regexes `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` in `app/src/lib/copilot-conflict-context.ts:122-279`) and sends them to Copilot, numbered "Conflict 1 of N", "Conflict 2 of N", etc. (`app/src/lib/copilot-conflict-context.ts:560-590`).

The model's response is checked only for **count** parity per file: [1](#0-0) 

It is never checked that hunk `i` in the model's array actually corresponds to conflict block `i` in the file — there is no content fingerprint, hash, or marker-anchor tying a resolution to the specific `ours`/`theirs` text it was generated from.

`reassembleResolvedFile` then re-scans the same raw file content with a **second, independently maintained** marker parser (`reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) and splices in resolutions purely by walking order: [2](#0-1) 

Two independent implementations of the same "conflict marker protocol" exist in the codebase (`app/src/lib/copilot-conflict-context.ts:122-279` vs `app/src/lib/copilot-conflict-resolution.ts:523-599`), and notably the reassembly parser has no `baseMarker` (`|||||||`) handling at all, unlike the extraction parser (`app/src/lib/copilot-conflict-context.ts:123`). Any divergence between what the two parsers consider a well-formed conflict block — for example a file (arriving via a merged/fetched branch, which is attacker-controlled content) containing a malformed or nested marker sequence that one parser treats as a droppable malformed block and the other treats as valid, or that shifts hunk boundaries while keeping the total count identical — results in `validateResolutionPaths` passing (counts match) while the actual splice pairs the wrong `resolvedContent` with the wrong conflict block.

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes." Because resolution is order-matched rather than content-matched, and validation only checks array length, a crafted conflicting file from an attacker-controlled branch could cause Copilot's correct resolution for hunk A to be spliced into the location of hunk B (and vice versa), producing a file that looks resolved (no conflict markers remain) but silently contains the wrong logic at the wrong location — e.g. swapping which side's security check, permission logic, or dependency version wins at two different conflict sites in the same file. The user, seeing "conflicts resolved" with no markers left, is likely to accept and commit/push the corrupted result.

### Likelihood Explanation
This requires the user to run the Copilot conflict-resolution feature on a merge/rebase/cherry-pick involving attacker-influenced content (e.g. merging a malicious PR branch) that contains conflicting text engineered to desynchronize the two marker parsers while preserving hunk count. This is a plausible but non-trivial "attacker controls a cloned/fetched repository" scenario per the valid-impact criteria — it needs no local access, admin rights, or social engineering beyond the normal act of merging a branch, which is core Desktop functionality. Exploiting the exact parser-divergence deterministically would require crafting input that both scanners disagree on structurally while agreeing on count, which is a real but non-guaranteed condition — I was not able to fully construct or verify a concrete such input from static reading alone within this session, so likelihood should be treated as moderate-but-unconfirmed until a working PoC input is built and run against both `extractConflictHunks` and `reassembleResolvedFile`.

### Recommendation
Replace positional hunk matching with content-anchored matching: when reassembling, re-derive hunk boundaries from the same single implementation used for extraction (share the parser, don't duplicate it), and additionally verify that each resolution corresponds to its intended block — e.g. by having the model echo back a stable per-hunk identifier/marker-line snippet, or by hashing the original `ours`/`theirs` content per hunk at extraction time and re-validating that hash against the block being replaced during reassembly, aborting (falling back to manual resolution) rather than silently splicing on any mismatch.

### Proof of Concept
Not independently verified in this session — a concrete PoC would require constructing a conflicted file where `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) parse a different set of hunk boundaries from the same raw content while still agreeing on total hunk count (e.g. via a malformed/nested marker sequence near two adjacent conflict blocks), then confirming that `validateResolutionPaths` passes and the wrong `resolvedContent` is spliced at the wrong location. This should be built and run against the two functions directly (as in `app/test/unit/copilot-conflict-context-test.ts` and the corresponding resolution tests) to confirm exploitability before treating this as fully validated.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
