### Title
Bridge Circuit Accepts Operator Chain With Equal Work to Watchtower — Strict `>` Required but `<` Allows Equality - (File: `circuits-lib/src/bridge_circuit/mod.rs`)

---

### Summary

The `bridge_circuit` function in `circuits-lib/src/bridge_circuit/mod.rs` uses a strict `<` comparison to check whether the operator's total accumulated proof-of-work exceeds the maximum watchtower work. This allows the circuit to pass when the operator's work **equals** the watchtower's maximum work, violating the protocol's documented invariant that the operator must prove **strictly greater** work than any challenger.

---

### Finding Description

In `bridge_circuit`, after computing `max_total_work` from all valid watchtower Groth16 proofs, the operator's chain work is extracted from the last 16 bytes of the 32-byte big-endian `total_work` field of the header chain proof (HCP):

```rust
let total_work: TotalWork = input.hcp.chain_state.total_work[16..32]
    .try_into()
    .expect("Cannot fail");

// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

The condition `total_work < max_total_work` panics only when the operator's work is **strictly less than** the watchtower's maximum work. When `total_work == max_total_work`, the circuit proceeds without panicking.

The protocol documentation and inline comments explicitly state the required invariant is **strictly greater than**:

- `docs/bridge-circuit.md` line 33: *"Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers."*
- `docs/bridge-circuit.md` line 65: *"The Operator must provide a HCP with **more** work compared to the WOP with maximum Work."*
- The inline comment at line 132: *"If `max_total_work` given by watchtowers is **greater than** `hcp.chain_state.total_work`."* [2](#0-1) 

Both values are 128-bit truncations of the full 256-bit accumulated work. The operator's value is `total_work[16..32]` (lower 128 bits of the big-endian 256-bit value), and the watchtower's value is produced by `work_only_circuit` via `work_conversion`, which also extracts the lower 128 bits. [3](#0-2) 

---

### Impact Explanation

The bridge circuit is the ZK proof an operator submits when challenged via the BitVM2 protocol. The work comparison is the core security invariant: the operator must demonstrate their claimed Bitcoin chain has **strictly more** accumulated proof-of-work than any watchtower's chain. This is how the canonical chain is determined.

When `total_work == max_total_work`, the operator's chain and the watchtower's chain have the same 128-bit work representation. This means:

1. The two chains could be distinct forks with equal (or colliding-in-128-bit) accumulated work.
2. The operator's chain is not provably the canonical one — Bitcoin's tie-breaking is first-seen, which is non-deterministic and not verifiable in-circuit.
3. The operator can pass the bridge circuit check and receive reimbursement for a payout made on a non-canonical fork, effectively stealing bridged BTC.

The 128-bit truncation (lower half of 256-bit work) compounds the issue: two chains with different 256-bit total work values whose lower 128 bits collide would also pass the equality check, expanding the attack surface beyond exact work equality.

---

### Likelihood Explanation

On mainnet, two chains having exactly equal 128-bit truncated work is extremely rare under honest mining. However:

- On regtest/testnet environments (used for testing and potentially staging), work values are small and controllable, making exact equality trivially engineerable.
- A sophisticated attacker who can influence mining (e.g., a miner colluding with a malicious operator) could target a fork where the 128-bit work values collide.
- The 128-bit truncation means the effective collision space is `2^128`, which is large but not infinite, and the truncation itself introduces a systematic information loss that the protocol's security model does not account for.

Likelihood: **Low** on mainnet under normal conditions, **Medium** in adversarial/testnet scenarios.

---

### Recommendation

Change the comparison from strict `<` to `<=` so that equality also causes a panic:

```rust
// Before (incorrect — allows equal work):
if total_work < max_total_work {
    panic!(...);
}

// After (correct — requires strictly greater work):
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: operator work must be strictly greater than watchtower max work. \
         Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [4](#0-3) 

This aligns the code with the documented invariant in `docs/bridge-circuit.md` and the inline comment at line 132.

---

### Proof of Concept

1. A malicious operator initiates a kickoff for a withdrawal on a Bitcoin fork `F` that has the same 128-bit truncated total work as the canonical chain `C` (or a watchtower's chain).
2. A watchtower challenges the operator, submitting a work-only proof for chain `C` with `max_total_work = W`.
3. The operator submits a bridge circuit proof for fork `F` with `total_work = W` (equal, not greater).
4. The circuit evaluates `if total_work < max_total_work` → `if W < W` → `false` → **no panic, circuit passes**.
5. The operator's fraudulent payout on the non-canonical fork `F` is accepted, and they receive reimbursement for BTC they did not legitimately front on the canonical chain.
