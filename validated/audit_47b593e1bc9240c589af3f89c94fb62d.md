### Title
`clone()` explicitly disables Git's clone-time hook/config protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) while doing a recursive clone of an attacker-controlled repository - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` helper deliberately sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` before invoking `git clone --recursive` on a URL the user supplies (which, in the "clone URL"/"open with GitHub Desktop" flows, is fully attacker-controlled).

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the safety switch upstream Git introduced to mitigate CVE‑2024‑32004: a maliciously crafted repository (via nested/symlinked `.git` directories, crafted submodules, or embedded hook files reached during a recursive checkout) can get its hooks or configuration executed during `git clone`. Modern Git versions refuse such clones unless the caller explicitly opts back into the old, unsafe behavior via this variable. GitHub Desktop's `clone()` function does exactly that: [1](#0-0) 

The clone is also run with `--recursive`, meaning nested attacker-controlled submodules are fetched and checked out automatically in the same operation, which is precisely the scenario Git's protection is meant to guard against: [2](#0-1) 

The only defenses present in this file are path-based: `isClonePathSensitive()` blocks cloning *into* well-known sensitive directories such as `~/.ssh` or `~/.gnupg`: [3](#0-2) 

That check constrains only the destination directory chosen by the user — it does nothing to validate or sanitize the *content* of the attacker-supplied repository being cloned, so it provides no protection against the hook/config-execution attack that `GIT_CLONE_PROTECTION_ACTIVE` exists to stop.

Separately, Desktop does have an opt-in hook-interception mechanism (`withHooksEnv`/`getRepoHooks` in `app/src/lib/hooks/`) that proxies hook execution for some git operations, but this mechanism only activates when the caller passes `interceptHooks` in the execution options: [4](#0-3) 
`clone()` does not pass `interceptHooks`, so hooks embedded in the attacker's repository during a protection-disabled recursive clone are not intercepted, filtered, or sandboxed by this system at all — the two mechanisms simply don't overlap for this code path.

### Impact Explanation
Cloning is a low-friction, unprivileged action a victim performs on demand — clicking "Clone repository" for any URL, or using a deep-link/"Open with GitHub Desktop" URL that an attacker controls. If a crafted repository relies on the class of Git hook/config-execution bugs that `GIT_CLONE_PROTECTION_ACTIVE` was created to block, Desktop's explicit opt-out reintroduces that path and can result in arbitrary command/hook execution on the victim's machine during what should be a purely data-fetching operation, satisfying the "attacker controls a cloned/fetched repository ... result is code execution" impact category.

### Likelihood Explanation
The trigger is a normal, expected user action (cloning any attacker-supplied URL) with no unusual steps, no local/physical access, no leaked credentials, and no social engineering beyond "the user clones a repository," which is the core intended use of the application. The only barrier to exploitation is whether the underlying Dugite/Git binary bundled with Desktop is otherwise safe against the specific hook-execution technique the flag was designed to prevent — Desktop's own code takes no independent precaution and actively disables Git's own guard, so the residual risk is fully dependent on the vendored Git version's other protections, which this code path bypasses one of.

### Recommendation
- Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` unless there is a concrete, currently-necessary compatibility reason recorded for it; if a workaround is required for some environments, gate it narrowly (e.g., only for local trusted clones) rather than unconditionally for every remote clone.
- If clone protection cannot be re-enabled unconditionally (e.g., due to a compatibility break), route clone operations through the existing hook-interception (`interceptHooks`) machinery in `app/src/lib/hooks/` so hooks introduced by a freshly cloned/recursively-checked-out repository are proxied/sandboxed the same way other git operations are.
- Add regression tests asserting that cloning a repository containing hook payloads reachable via the CVE‑2024‑32004 class of attack (nested `.git`, malicious submodule hook, etc.) does not result in hook execution.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable directly from the code path):
1. Attacker hosts a git repository crafted per the CVE‑2024‑32004 technique — e.g., a submodule or nested working-tree structure whose recursive checkout causes Git to run a hook/script from repository content rather than trusted local config.
2. Attacker shares the clone URL (or a `x-github-client://` / "Clone repository" deep link) with the victim.
3. Victim clones the URL through GitHub Desktop's normal "Clone repository" flow, which calls `clone()` in `app/src/lib/git/clone.ts`.
4. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` and `--recursive` is used, Git's built-in refusal to perform the unsafe clone/checkout is bypassed, and the embedded hook/script executes on the victim's machine during the clone.

Note: I was not able to find any additional runtime check elsewhere in the indexed codebase (config validation, git version gating, or a `--recursive`-specific sanitizer) that would re-add the protection this environment variable removes; if such a mitigation exists in a file outside the indexed coverage, a full-repository review via a Devin session would be needed to confirm.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
