### Title
Silent Commit Corruption via Stale Line-Index Diff Selection in `applyPatchToIndex()` - ([File: app/src/lib/git/apply.ts])

### Summary
`DiffSelection` stores which lines a user chose to stage purely as a set of positional integers ("diverging lines"), decoupled from the diff content those positions were computed against. When a partial commit is staged, `applyPatchToIndex()` re-fetches a *fresh* working-directory diff and then reapplies the old, positionally-indexed selection to it, with no check that the new diff has the same shape as the diff the user actually reviewed. If the tracked file's content changes between the moment the user reviews/selects lines in the UI and the moment `git commit` triggers staging, the stale line indices can silently select the wrong lines from the new diff, producing a commit that does not match what the user saw and approved on screen.

### Finding Description
Partial staging in Desktop works in two disconnected steps:

1. The renderer loads a diff and lets the user select lines. Selection state is kept as `DiffSelection`, which records only integer line indices ("diverging lines") relative to whatever diff was loaded at selection time — it holds no reference to the diff's content or hash: [1](#0-0) [2](#0-1) 

2. When the commit is actually created, `createCommit()` calls `stageFiles()`, which for any file with a partial selection calls `applyPatchToIndex()`: [3](#0-2) [4](#0-3) 

`applyPatchToIndex()` does **not** reuse the diff object the UI rendered. It fetches a brand-new diff straight from disk and blindly combines it with the old `file.selection` object by absolute line index: [5](#0-4) 

`formatPatch()` then walks the *new* diff's hunks and, for every non-context line, asks `file.selection.isSelected(absoluteIndex)` — purely a numeric lookup with no correlation to the actual text of the line at that index in the new diff: [6](#0-5) 

There is no guard anywhere in this path (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`) that compares the diff used for selection against the diff used for patch construction, and no revalidation that the file's content/hash still matches what was displayed when the user made their selection: [7](#0-6) 

By contrast, the renderer's own diff-viewing code (`_changeFileSelection`/`updateChangesWorkingDirectoryDiff`) is careful to re-check that the selection/shas haven't changed before applying a freshly loaded diff to the UI state — but that staleness check exists only for *rendering*, not for the *staging/patch-construction* path that actually determines what gets committed: [8](#0-7) 

The broken invariant: "the set of selected line indices is only meaningful relative to the exact diff it was computed from" is violated the moment the on-disk diff shape changes (hunks reflowed, lines added/removed, whitespace/EOL differences) between selection time and stage time, because `applyPatchToIndex` substitutes a new diff underneath an old selection without any equivalence check.

### Impact Explanation
This allows silent corruption of what the user actually commits/pushes — one of the explicitly in-scope impacts. A cloned/fetched repository under attacker influence (e.g. content that legitimately changes on disk shortly after the diff is computed — via a background process the app itself triggers, a slow filesystem/network mount, or content that mutates between Desktop's status refresh and the user's click of "Commit") can cause the hunk layout to shift. When that happens, `isSelected(absoluteIndex)` walks the *new* hunk's lines using *old* offsets, so lines the user never reviewed or explicitly deselected can end up included in the applied patch, or lines the user intended to commit can be silently dropped/altered — all without any error, since `git apply --cached` will happily accept a syntactically valid (if semantically wrong) patch. The result is a commit (and eventual push) whose content diverges from what the user believed they reviewed and approved, with no indication to the user that anything went wrong.

### Likelihood Explanation
The window between diff-selection and staging in Desktop is not instantaneous — status is polled/refreshed periodically, diffs are loaded asynchronously, and the user can leave the Changes view open with a partial selection for an extended period before clicking "Commit". Any external mutation of the selected file's on-disk content during that window (which Desktop does not prevent, and does not detect at staging time) triggers the mismatch deterministically, because `applyPatchToIndex` always re-fetches the diff rather than validating it against the one that produced the selection. This does not require local/physical access, admin rights, or credential compromise — only that the working tree content differs at commit-time from what it was at selection-time, a condition attacker-influenced or automatically-changing repository content can produce.

### Recommendation
Before building the patch in `applyPatchToIndex()`, verify that the freshly fetched diff is structurally equivalent (e.g., matching hunk boundaries/line counts, or a content hash) to the diff that produced `file.selection`. If it differs, refuse to stage that file's partial selection and force the UI to reload the diff and require the user to re-confirm their selection, rather than silently reapplying stale line indices to a new diff.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, partially select only some added/deleted lines (e.g., select just hunk #2), leaving hunk #1 unselected. This creates a `DiffSelection` with diverging line indices tied to the currently rendered diff (`app/src/models/diff/diff-selection.ts:205-282`).
3. Before clicking "Commit", change the file on disk in a way that shifts hunk boundaries (e.g., another process appends/removes lines near the top of the file, changing the offsets of subsequent hunks) without the UI's cached diff/selection being invalidated.
4. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`) re-fetches the diff via `getWorkingDirectoryDiff` and applies the *old* selection's line indices to the *new* hunk layout via `formatPatch` (`app/src/lib/patch-formatter.ts:129-206`).
5. Inspect the resulting commit: it contains different lines than what was visually selected in step 2 — demonstrating silent corruption of the committed content with no error or warning surfaced to the user.

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
```
