### Title
`accumulate`'s `beneficiary_message` signature omits an amount/commitment bound, letting a captured relayer authorization redirect fees far beyond the intended batch - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Pallet::accumulate` lets a relayer redirect accrued fees to a `beneficiary_address` by supplying a signature over `beneficiary_message(nonce, state_machine, beneficiary)` inside `WithdrawalProof.beneficiary_details`. [1](#0-0)  The signed payload binds only the relayer's per-`state_machine` nonce, the destination `state_machine`, and the beneficiary — it never binds which commitments, or how much fee, the redirect applies to. [2](#0-1)  Because `accumulate` is a permissionless, unsigned extrinsic that accepts an arbitrary `commitments` batch supplied by the caller (not the signer), anyone who observes a relayer's beneficiary signature can attach it to a different, larger batch of that same relayer's unclaimed deliveries and redirect the whole (larger) `total_fee` to the beneficiary in one call — exactly the missing-upper-bound pattern from the external report, here applied to relayer fee redirection instead of agent-bond registration.

### Finding Description
`accumulate` verifies a `WithdrawalProof` batch of request commitments delivered by a single relayer (`delivery_address`), sums the source-chain fees for the batch into `total_fee`, and then either credits `delivery_address` directly, or — if `beneficiary_details` is present — verifies a signature and credits a different `beneficiary_address` instead: [2](#0-1) 

The signed message is:
```rust
pub fn beneficiary_message(nonce: u64, state_machine: StateMachine, beneficiary: &[u8]) -> [u8; 32] {
    sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
``` [3](#0-2) 

Only `(nonce, state_machine, beneficiary)` are covered — no commitment set, no amount, no cap. Replay across calls is blocked by the nonce increment, but the signature is fully agnostic to the size or content of the batch it gets attached to *for that one call*. The `commitments` field of `WithdrawalProof`, and therefore `total_fee`, is chosen entirely by whoever submits the call — the accumulate extrinsic has no relayer-identity origin check and is designed to be triggered by any relaying party. [4](#0-3) 

Attack sketch:
1. Relayer R has delivered many small requests over time on chain X, each individually eligible for accumulation into `Fees[X][R]`; none are yet claimed (`RequestCommitments::claimed == false`).
2. R signs `beneficiary_message(nonce, X, B)` intending to redirect the fee from a specific small batch of commitments they are about to submit (e.g. one delivery worth 1 unit) to beneficiary B (e.g. their own hot wallet on a different chain-format).
3. Before R's transaction lands, an observer (or R's own counterparty who was handed the signature off-chain) submits `accumulate` first with a `WithdrawalProof` whose `commitments` field includes *every* unclaimed request R has ever delivered on X, reusing R's signature and the same nonce.
4. All checks pass: `delivery_address` still resolves to R for every commitment in the enlarged batch (`ensure!(entries.next().is_none(), MixedDeliveryAddressesInBatch)` only rejects mixed-relayer batches, not oversized ones), the nonce still matches (nobody else has consumed it yet), and the signature verifies against `(nonce, X, B)`, which says nothing about batch size.
5. The entire accumulated `total_fee` — potentially many times what R intended to redirect — is credited to `Fees[X][B]` instead of `Fees[X][R]`, and R's nonce is bumped so their own intended-narrower submission now fails/replay-protected out.

This mirrors the report's core defect: a signed authorization is scoped only by identity/nonce, not by an upper bound on the financial consequence, so a party controlling the timing/content of on-chain settlement (here: the caller choosing the `commitments` batch) can attach the same authorization to a much larger value transfer than the signer approved.

### Impact Explanation
This causes relayer funds (accrued cross-chain delivery fees, an economic asset the protocol pays out from the fee/treasury flow) to be redirected to an address the relayer only meant to authorize for a smaller, specific amount. Because `beneficiary_address` can differ from `delivery_address` and the "beneficiary" recipient is whoever the redirect message names, an attacker who can front-run or otherwise capture/republish a relayer's beneficiary signature (e.g. it circulates in a mempool, or is handed to a specific counterparty for one small settlement) can inflate the batch to sweep all of that relayer's currently-unclaimed fee revenue to the named beneficiary in a single call. This is a fund-diversion issue against a legitimate protocol participant (the relayer), fitting the bounty's "stealing or loss of funds" / "logic attack" / "false... acceptance of unintended amount" categories.

### Likelihood Explanation
Likelihood requires the ability to observe or otherwise obtain a relayer's signed `beneficiary_message` before it is consumed and to have knowledge of the relayer's other unclaimed deliveries (both queryable from public chain state: `RequestCommitments` and delivery receipts are public). No malicious peer, prover, or governance actor is needed — `accumulate` is explicitly an unsigned/permissionless extrinsic that any caller can submit with any commitments batch. The main precondition is that the relayer's signature must not yet have been consumed (nonce still current) and enough of the relayer's deliveries must be unclaimed to make the batch meaningfully larger than intended, which is realistic for a relayer that batches/accumulates infrequently.

### Recommendation
Bind the `beneficiary_message` (and equivalently the outbound-consensus/outbound-request delivery messages, which already scope by specific identifiers) to the exact scope of funds it authorizes: include either the full commitment set being claimed (e.g. a hash of the `commitments` vector) or an explicit maximum/exact `total_fee` amount in the signed payload, and enforce that the accumulated total for the call does not exceed that bound. This closes the gap between what the relayer signed and what the extrinsic is allowed to redirect, analogous to adding a maximum-bond parameter to the `ServiceManager` signature in the original report.

### Proof of Concept
Conceptual reproduction using the existing pallet-relayer test harness (`modules/pallets/testsuite/src/tests/pallet_ismp_relayer.rs`), mirroring the pattern of `test_withdrawal_fees_evm` but for `accumulate`:
1. Register N unclaimed request commitments delivered by relayer R on `StateMachine::Evm(X)`, each with a small fee `f`, via `RequestCommitments` + matching source/dest receipt fixtures (same fixture helpers used in `evm_destination_pays_relayer`/`register_request`). [5](#0-4) 
2. Have R sign `beneficiary_message(nonce=0, X, B)` intending it for only commitment `c1` (fee `f`).
3. Instead, submit `Pallet::accumulate` with `WithdrawalProof.commitments = [c1, c2, ..., cN]` (all delivered by R, all unclaimed) and `beneficiary_details = Some((B, signature))`.
4. Assert the call succeeds and `Fees::<Test>::get(X, B) == N * f`, not `f`, and `Nonce` for R on X is now `1`, blocking R's originally intended narrower submission.

Note: this analysis is based on statically reading `accumulate.rs`, `withdrawal.rs`, and `lib.rs`; I did not execute the pallet's test suite to empirically confirm the exact assertion outcome, so the PoC above is a construction from the verified code paths rather than a run test.

		let mut seen = alloc::collections::BTreeSet::new();
		for key in withdrawal_proof.commitments.iter() {
			ensure!(seen.insert(key.encode()), Error::<T>::DuplicateCommitment);
