### Title
Shared `BalanceHandler.prevEventsLen` is overwritten during recursive/nested precompile calls, causing missed bank events and balance desync between `x/bank` and the EVM `StateDB` - (File: `precompiles/common/balance_handler.go`)

### Summary
`BalanceHandler` records a single mutable `prevEventsLen` field via `BeforeBalanceChange` and consumes it in `AfterBalanceChange` to slice the SDK event log and translate `x/bank`/`x/precisebank` events into `StateDB.AddBalance`/`SubBalance` calls. When a precompile call recurses into another precompile call using the *same* `BalanceHandler` instance, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, discarding the outer call's original event-window start. This is structurally the same class of bug as the reported `_owners` shadowing issue: a single mutable piece of state that is supposed to be scoped/authoritative for one context gets clobbered by a nested/overlapping use, and a downstream accounting function (`exists()` in the original report, `AfterBalanceChange` here) silently reads the wrong value.

### Finding Description
`BalanceHandler` is the bridge that keeps the EVM `StateDB` balance view consistent with actual `x/bank` (and `x/precisebank`) coin movements performed by precompiles [1](#0-0) . The pattern is:

1. `BeforeBalanceChange(ctx)` snapshots `len(ctx.EventManager().Events())` into `bh.prevEventsLen`.
2. The precompile method executes bank operations, emitting `CoinSpent`/`CoinReceived`/`EventTypeFractionalBalanceChange` events.
3. `AfterBalanceChange(ctx, stateDB)` re-reads `ctx.EventManager().Events()` and only processes `events[bh.prevEventsLen:]`, applying deltas to `stateDB` via `AddBalance`/`SubBalance` [2](#0-1) .

This design assumes each `BeforeBalanceChange`/`AfterBalanceChange` pair is strictly non-overlapping (no reentrancy). The repository's own integration test explicitly documents and reproduces the violation of that assumption: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [3](#0-2) 

Concretely, when a caller contract triggers a precompile call that itself invokes another (nested/recursive) precompile call sharing the same `BalanceHandler` instance:
- Outer call: `BeforeBalanceChange` sets `prevEventsLen = N`.
- Inner (nested) call: `BeforeBalanceChange` overwrites `prevEventsLen = M` (M > N, after the outer's own bank events have already been emitted).
- Inner call finishes, `AfterBalanceChange` runs correctly for its own slice `[M:]`.
- Outer call's `AfterBalanceChange` now also reads `bh.prevEventsLen`, which has been left at `M` by the inner call instead of the outer's original `N`. Any bank events the outer call itself emitted between `N` and `M` are silently skipped and never translated into `StateDB.AddBalance`/`SubBalance` calls.

The reproduction test confirms this happens under ordinary (unprivileged) EVM contract execution — a contract simply calling a precompile that recursively re-enters a precompile call — with no privileged setup required [4](#0-3) .

### Impact Explanation
This breaks the core `x/vm` invariant that `StateDB` balances (used for all subsequent EVM-level balance checks, transfers, and gas/value accounting within the same transaction) must stay 1:1 consistent with actual `x/bank`/`x/precisebank` coin movements performed via precompiles. If a `CoinSpent` or `CoinReceived` event from the outer precompile call is dropped from the window:
- A `CoinReceived` event being skipped means a user's real (committed, spendable) bank balance increases, but the EVM `StateDB` balance used within the same call frame does not reflect it — subsequent EVM logic in that transaction (e.g., checking `balanceOf`/`msg.value`-driven flows or transferring the "known" balance in the same tx) can under- or mis-account funds, and on `Commit()` the state divergence can persist since `Commit()` writes stateObjects derived from `StateDB`, not from the true bank ledger balance directly for every account.
- Conversely, a `CoinSpent` event being skipped means the EVM-visible balance is not decremented even though the coins actually left the account in `x/bank`, or vice versa — enabling a double-counted / phantom balance state in `StateDB` that can be leveraged by a contract to perform further transfers based on incorrect balances within the same transaction, i.e., balance duplication/creation of spendable value not backed by actual reserves.

This matches the "Critical unauthorized … duplication … or irreversible accounting corruption of spendable user value across native balances, EVM balances, … precompile-mediated assets" impact class, since the trigger requires only an ordinary unprivileged contract call chaining two precompile invocations (e.g., via a caller contract as demonstrated in the test).

### Likelihood Explanation
The bug is triggerable by any unprivileged user/contract that causes a precompile call to recursively invoke another precompile call while both share the same `BalanceHandler` instance — this is exactly what the project's own test (`TestRecursivePrecompileCallsWithDebugPrecompile`) exercises using a simple caller contract and the debug precompile, with no special permissions [5](#0-4) . Real-world analogs would be any composable precompile flow where one precompile method (e.g., ERC20/staking/distribution precompile) internally calls back into another precompile (e.g., via a `Call`/`DelegateCall` opcode path or nested precompile dispatch) sharing the handler instance from a common EVM call context.

### Recommendation
- Do not store `prevEventsLen` as instance state shared across nested calls. Instead, make `BeforeBalanceChange`/`AfterBalanceChange` pass the snapshot value explicitly (return it from `BeforeBalanceChange` and require it as a parameter to `AfterBalanceChange`), or use a stack/counter that pushes/pops per call depth so nested calls cannot clobber the outer call's window.
- Alternatively, instantiate a new `BalanceHandler` per call frame (verify `BalanceHandlerFactory.NewBalanceHandler()` is actually invoked per nested precompile call rather than being reused across the recursive chain) and ensure each frame processes its own exclusive event slice.
- Add regression coverage asserting the exact `StateDB` balance and post-commit bank balance are equal after nested/recursive precompile calls (the existing test only asserts event counts, not final balances) — extend `TestRecursivePrecompileCallsWithDebugPrecompile` to assert `GetBalance` equality between `x/bank` and `StateDB` after the call.

### Proof of Concept
The repository already contains a working PoC: `TestRecursivePrecompileCallsWithDebugPrecompile` deploys a caller contract, registers a debug precompile, and invokes `callback(0)`, which recursively re-enters the precompile call chain [6](#0-5) . The test's own docstring confirms the exact root cause and observable symptom (shared instance, overwritten `prevEventsLen`, balance desync) [3](#0-2) . Extending this test to compare `stateDB.GetBalance` (or the EVM-queried balance via `Keeper.Balance`) against the ground-truth `x/bank`/`x/precisebank` balance for the involved accounts after the nested call would concretely demonstrate the value mismatch.

// BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
