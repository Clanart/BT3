### Title
cancelUnlock() fails to call updateTotalFactor() while startUnlock() does, causing ReferralStorage.totalBoostFactor to diverge from real locked weight - (File: VLMGP.sol)

### Summary
`cancelUnlock()` reduces `totalAmountInCoolDown` and zeroes `slot.amountInCoolDown`, which immediately increases the caller's `getUserTotalLocked()` result (since `getUserTotalLocked = amountInMasterMagpie - getUserAmountInCoolDown`), but unlike `startUnlock()`, it never calls `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)`. This leaves `userInfo.factor` and the global `totalBoostFactor` stale relative to the user's actual locked balance.

### Finding Description
`startUnlock()` explicitly refreshes the caller's boost factor after changing their locked/cooldown split: [1](#0-0) 

`cancelUnlock()` performs the symmetric, opposite state change (moving MGP back from cooldown into "locked" as seen via `getUserTotalLocked`) but omits the corresponding `updateTotalFactor` call: [2](#0-1) 

`getUserTotalLocked` derives directly from `getUserAmountInCoolDown`, which sums `amountInCoolDown` across all of the user's unlock slots, so it changes the instant `cancelUnlock` zeroes `slot.amountInCoolDown`: [3](#0-2) 

`ReferralStorage.updateTotalFactor` recomputes `userInfo.factor = sqrt(getUserTotalLocked(_account))` and adjusts the global `totalBoostFactor` accordingly: [4](#0-3) 

Because `cancelUnlock` never triggers this refresh, a user who has activated the referral feature (`userInfo.myCode != 0`) can raise their effective locked balance via `cancelUnlock` without their `factor`/`totalBoostFactor` ever being updated to reflect it, until some other action (e.g. a subsequent `startUnlock`) happens to call `updateTotalFactor` again. In the interim, `totalBoostFactor` understates the true sum of locked weight, which mechanically inflates `_calBoosted()` for every other referrer since it divides `BoostPoint * userInfo.factor` by a stale (smaller) `totalBoostFactor`: [5](#0-4) 

### Impact Explanation
This is a real accounting inconsistency confined to `ReferralStorage`'s boost-factor bookkeeping: `totalBoostFactor` can diverge from the sum of live per-user factors because `cancelUnlock` doesn't call `updateTotalFactor`. This can distort the split of `trigger()`-driven referral rewards among referrers who have registered a code, inflating or shrinking their share of the boosted MGP reward pool relative to what their true locked balance should entitle them to.

However, the specific chain asserted in the question — a divergence between `userTotalVotedInVlmgp(user)` in `WombatBribeManager` and `getUserTotalLocked(user)` caused by `cancelUnlock` — could not be substantiated from the code examined. `WombatBribeManager`'s vote accounting is driven by explicit user `vote()` calls, not automatically re-derived from `getUserTotalLocked()` on every `VLMGP` state change, and I found no code path linking `cancelUnlock` to `WombatBribeManager`'s vote bookkeeping. I was unable to fully review `wombat/WombatBribeManager.sol` in this session (tool budget exhausted before reading its `vote`/`userTotalVotedInVlmgp` logic in detail), so I cannot confirm or rule out a connection there with full confidence.

### Likelihood Explanation
The missing `updateTotalFactor` call in `cancelUnlock` is unconditionally reachable by any unprivileged user with an active unlock slot and a registered referral code — no special capital or privilege is required, only calling `startUnlock` then `cancelUnlock`. This part of the finding is highly likely/reproducible. The broader "theft of unclaimed yield via `WombatBribeManager`" framing in the question is not confirmed by the code reviewed and should be treated as unverified.

### Recommendation
Add `if (referralStorage != address(0)) IReferralStorage(referralStorage).updateTotalFactor(msg.sender);` at the end of `cancelUnlock()` (and `forceUnLock()`, which has the same gap), mirroring the call already present in `startUnlock()`, so `totalBoostFactor` and each user's `factor` stay synchronized with `getUserTotalLocked()` after every state transition that changes cooldown/locked balances.

### Proof of Concept
Hardhat plan:
1. Deploy `VLMGP`, `ReferralStorage`, register two referrers A and B each with a referral code, and have them lock MGP amounts `L_A` and `L_B`.
2. Call `updateTotalFactor` (via a locking action) for both so `totalBoostFactor = sqrt(L_A) + sqrt(L_B)`.
3. Have A call `startUnlock(x)` (this updates A's factor to reflect reduced locked amount) then immediately `cancelUnlock(slotIndex)` (this restores A's `getUserTotalLocked` to `L_A` but does not call `updateTotalFactor`).
4. Assert `ReferralStorage.userInfos(A).factor` still equals `sqrt(L_A - x)` (stale) while `VLMGP.getUserTotalLocked(A)` equals `L_A` (restored), and that `totalBoostFactor` is less than `sqrt(L_A) + sqrt(L_B)`.
5. Trigger a referral reward event via `trigger()` for a referee under B and confirm B's `_calBoosted` share is higher than it would be with a correctly refreshed `totalBoostFactor`.

Note: this PoC validates the `ReferralStorage` boost-factor divergence only; it does not establish the `WombatBribeManager` vote-tracking divergence claimed in the question, which requires further investigation of `wombat/WombatBribeManager.sol`'s vote accounting that was not completed in this session.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);

        totalBoostFactor += userInfo.factor;
