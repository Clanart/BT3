### Title
Integer underflow in `AccountKeyWeightedMultiSig.SigValidationGas` via signed subtraction cast to `uint64` - ([File: blockchain/types/accountkey/account_key_weighted_multi_sig.go])

### Summary
`SigValidationGas` computes the gas required to validate a WeightedMultiSig account's signatures. Post-Istanbul, it computes `uint64(numSigs-1) * params.TxValidationGasPerKey` where `numSigs` is a signed `int` parameter equal to `len(pubkey)` derived from the number of ECDSA signatures recovered from the submitted transaction. [1](#0-0) 

### Finding Description
`numSigs` originates from `len(pubkey)` in `Transaction.ValidateSender`/`ValidateFeePayer`, which is fully attacker-controlled: it is derived directly from the recovered public keys of the signatures attached to a transaction submitted by any unprivileged sender. [2](#0-1) [3](#0-2) 

If `numSigs` is `0` (e.g., a transaction with zero signatures reaching this code path, or any other caller passing `0`), the subtraction `numSigs-1` is performed in signed `int` arithmetic, producing `-1`. This negative value is then cast to `uint64`, which — exactly like the CVE-2024-35827 root cause ("casting a value that could go negative to an unsigned type before an overflow check defeats the check") — wraps around to `math.MaxUint64` (18446744073709551615). Multiplying this value by `params.TxValidationGasPerKey` (15000) overflows uint64 arithmetic and wraps modulo 2^64 to an essentially unpredictable, attacker-uninfluenced but incorrect gas value, rather than erroring out.

This is structurally identical to the io_uring bug: a length/count value that is unsigned in nature (`numSigs` should never be negative) is handled with signed subtraction and then coerced to an unsigned type without a bounds/underflow check, defeating the very "size" invariant the surrounding code depends on.

By contrast, the pre-Istanbul path and other similar gas functions in the codebase correctly guard against `numKeys == 0` before subtracting. [4](#0-3) 

### Impact Explanation
The wrapped, incorrect `gasKey` value returned by `SigValidationGas` feeds directly into `sigValidationGas`/`intrinsicGas` computation, which is then used to determine whether a transaction has purchased enough gas (`ErrIntrinsicGas` check) and to charge fees in `StateTransition.TransitionDb`. [5](#0-4) [6](#0-5) 

Depending on the exact wraparound value produced, this could cause the required intrinsic gas for a WeightedMultiSig-controlled account's transaction to become abnormally small or large, potentially allowing a transaction to be admitted/executed while paying dramatically less signature-validation gas than intended (fee/gas accounting abuse), or causing valid transactions to be rejected (availability impact / state divergence risk if nodes disagree on whether the check passes due to platform-dependent behavior). Because gas correctness underlies fee charging and DoS protection, this qualifies as a fee-accounting integrity issue.

### Likelihood Explanation
Reaching `numSigs == 0` specifically through `ValidateSender`/`ValidateFeePayer` requires `len(pubkey)` to be zero, which depends on upstream signature-recovery logic (`SenderPubkey`/`SenderFeePayerPubkey`) potentially rejecting zero-signature transactions before this point — this call chain could not be fully traced in the available index. I cannot confirm with full certainty whether `numSigs=0` is reachable in the production path today, but the function itself contains no defensive check against `numSigs <= 0` (unlike the `numKeys == 0` guard just above it in the same function), which is the same class of missing-guard root cause as the CVE. Given the ambiguity, likelihood should be treated as Medium pending confirmation of whether zero-signature invocation is reachable end-to-end.

### Recommendation
Add an explicit guard `if numSigs <= 0 { return 0, kerrors.ErrZeroLength }` (or equivalent) before computing `uint64(numSigs-1)` in `AccountKeyWeightedMultiSig.SigValidationGas`, mirroring the existing `numKeys == 0` check just above it, so a negative or zero `numSigs` cannot be silently coerced into a huge `uint64` value.

### Proof of Concept
1. Construct or directly unit-test `AccountKeyWeightedMultiSig.SigValidationGas(currentBlockNumber, RoleTransaction, 0)` on an Istanbul-enabled chain (`isIstanbul == true`).
2. Observe the returned gas value: `uint64(0-1) * params.TxValidationGasPerKey` = `math.MaxUint64 * 15000 mod 2^64`, an incorrect, wrapped value instead of an error.
3. If reachable via `Transaction.ValidateSender` with `len(pubkey) == 0`, this wrapped gas value is propagated into `intrinsicGas`/`sigValidationGas` used for both tx-pool admission and state-transition gas accounting. [7](#0-6)

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
