### Title
`WombatPoolHelperV2::depositFor` (and `AnkrBNBPoolHelper`'s equivalent) hardcodes zero slippage protection, exposing depositors to sandwich attacks - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor` forwards a hardcoded `_minimumLiquidity` of `0` to the internal deposit path, unlike the standard `deposit`/`depositNative` functions which let the caller specify a slippage-protection value. Any unprivileged wallet calling `depositFor` therefore has no way to protect itself against Wombat pool cash/liability ratio manipulation, mirroring the exact bug class described in the external report (missing slippage controls in a deposit/mint-style function).

### Finding Description
`WombatPoolHelperV2.deposit` and `depositNative` accept a caller-supplied `_minimumLiquidity` and forward it down to `WombatStaking.deposit`, which in turn passes it to the underlying `IWombatPool.deposit` as the `minimumLiquidity` guard [1](#0-0) . However, `depositFor` — a fully public, unprivileged entry point — hardcodes this parameter to `0`: [2](#0-1) 

That `0` is then propagated all the way to `WombatStaking.deposit`, which calls `IWombatPool(poolInfo.depositTarget).deposit(depositToken, _amount, _minimumLiquidity, ...)` [3](#0-2) , i.e. the underlying Wombat pool's `minimumLiquidity` check is effectively disabled for any call routed through `depositFor`. The same pattern exists in `AnkrBNBPoolHelper._deposit`, which is reachable through the analogous batch/LP deposit paths using pre-set `_minimumLiquidity` values of `0` in some code paths as well [4](#0-3) .

This is functionally identical to the reported `AuraVault::deposit`/`mint` issue: the vault/pool-helper computes shares/liquidity to mint from the current pool state without allowing the caller to bound the acceptable output, so any change in the underlying Wombat pool's cash/liability ratio between transaction submission and execution (e.g., via a large swap) can result in significantly fewer LP/receipt tokens minted than the depositor expects.

### Impact Explanation
A user (or any address depositing on their behalf) calling `depositFor` receives zero slippage protection. An attacker monitoring the mempool can sandwich the `depositFor` transaction: front-run it with a trade that skews the Wombat pool's cash/liability ratio unfavorably, let the victim's deposit mint fewer LP tokens for the same input amount, then back-run to reverse the price and capture the difference. This is a direct extraction of value from the depositor's funds — a concrete, exploitable theft vector reachable by any ordinary wallet with no special privileges.

### Likelihood Explanation
`depositFor` is `external` and unauthenticated (any address can call it) [2](#0-1) . It is a normal, expected user flow (e.g., for contracts or relayers depositing on behalf of another address), so the exposure is not a contrived edge case. Sandwiching Wombat pool deposits is generally profitable and low-cost for an MEV searcher whenever pool liquidity is thin relative to the deposit size, making exploitation realistic whenever this function is used with any meaningful deposit size.

### Recommendation
Expose `_minimumLiquidity` as a caller-supplied parameter in `depositFor` (and any other internal callers hardcoding `0`), instead of hardcoding it to `0`, so depositors routed through this path can specify their own slippage tolerance, consistent with the `deposit`/`depositNative` functions:

```solidity
function depositFor(uint256 _amount, uint256 _minimumLiquidity, address _for) external {
    IERC20(depositToken).safeTransferFrom(msg.sender, address(this), _amount);
    IERC20(depositToken).safeApprove(wombatStaking, _amount);
    _deposit(_amount, _minimumLiquidity, _for, address(this));
}
```

### Proof of Concept
1. Alice wants to deposit 10,000 units of `depositToken` on behalf of a contract `_for` via `WombatPoolHelperV2.depositFor(10000, _for)`, expecting to receive LP-equivalent staking tokens proportional to current pool ratios.
2. An attacker observes Alice's pending transaction in the mempool and front-runs it with a large swap against the same Wombat pool, skewing the cash/liability ratio unfavorably for deposits.
3. Alice's `depositFor` call executes with `_minimumLiquidity = 0` hardcoded — [2](#0-1)  — so the transaction cannot revert regardless of how unfavorable the resulting liquidity/shares minted are.
4. The attacker back-runs with the reverse swap, restoring the pool state and pocketing the difference extracted from Alice's deposit, while Alice (or `_for`) receives fewer staking/receipt tokens than expected for the 10,000 units deposited.
