### Title
Payout tx malleability under SIGHASH_SINGLE|ANYONECANPAY lets anyone strip the OP_RETURN and permanently freeze a deposit's move-to-vault UTXO - (File: core/src/verifier.rs)

### Summary
`create_payout_txhandler` signs the withdrawal input with `SinglePlusAnyoneCanPay`, which under BIP341 only commits to input0 and output0 [1](#0-0) . An unprivileged party (the withdrawer themselves, per the threat model) can therefore build and broadcast a transaction that reuses that same input0/output0/signature but omits the OP_RETURN output entirely, causing `update_finalized_payouts` to record `payout_payer_operator_xonly_pk = NULL` for that withdrawal exactly as it would for a legitimate verifier-cosigned optimistic payout [2](#0-1) . Because `validate_payer_is_operator`/`is_kickoff_malicious` require a non-NULL matching operator pubkey to proceed, this permanently blocks any operator from ever reimbursing this specific deposit through the regular BitVM flow, while the optimistic flow is also blocked because the withdrawal UTXO is already spent, leaving the deposit's move-to-vault funds unreachable.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk IS NULL` ⇔ "this withdrawal's payout was serviced via the verifier-cosigned `Aggregator::optimistic_payout` MuSig2 ceremony" [3](#0-2) . This binding is broken because `update_finalized_payouts` derives the NULL/non-NULL value purely from whether the mined payout transaction happens to contain a parsable OP_RETURN with a valid xonly pubkey, with no check that a MuSig2 optimistic-payout signature was ever produced [2](#0-1) .

`create_payout_txhandler` signs input0 with `SinglePlusAnyoneCanPay` [4](#0-3) , and `parse_withdrawal_sig_params`/`Operator::withdraw` enforce that this exact sighash type is used [5](#0-4) . Under this sighash flag, only input0 and output0 are committed; any additional inputs and any outputs after index 0 (the anchor, the OP_RETURN) are unconstrained. An attacker who controls the withdrawal UTXO's private key (the withdrawer role in the threat model) already possesses a valid `SinglePlusAnyoneCanPay` signature over input0+output0. They can construct an entirely new transaction: same input0 (with the copied/known signature), same output0 (the committed payout output), their own additional funding input(s), and an anchor-only second output — omitting the OP_RETURN. This transaction is valid Bitcoin consensus-wise and can be broadcast/mined without any operator or verifier cooperation, and without ever invoking `get_participating_verifiers`/the MuSig2 optimistic-payout signing flow.

Once mined, `update_finalized_payouts` scans the tx, finds no OP_RETURN, sets `operator_xonly_pk = None`, and calls `update_payout_txs_and_payer_operator_xonly_pk` storing NULL [6](#0-5) , logging it as indistinguishable from a real optimistic payout [7](#0-6) . Subsequently:
- `Operator::validate_payer_is_operator` requires `payer_xonly_pk` to be `Some` and equal to the operator's own key before a kickoff can be built; with NULL stored, this always fails for every operator for this deposit [8](#0-7) .
- `Verifier::is_kickoff_malicious` treats a `None` operator pubkey in the payout info as malicious for any operator's kickoff attempting this move_txid [9](#0-8) .
- A real optimistic payout can never subsequently be co-signed by verifiers because they check `is_utxo_spent(&input_outpoint)` first and refuse if already spent [10](#0-9) .

The move-to-vault UTXO for this deposit can only be spent by `create_reimburse_txhandler` (via a validated kickoff) or `create_optimistic_payout_txhandler` (via verifier MuSig2) [11](#0-10) [12](#0-11) ; both paths are now permanently closed for this specific deposit's move-to-vault UTXO, since the attacker's forged tx never touches (and cannot touch, lacking N-of-N/security-council keys) the move-to-vault output itself.

### Impact Explanation
No bridge funds are directly stolen (the attacker must fund output0 with their own additional inputs), but the specific deposit's move-to-vault UTXO becomes permanently unreachable through any in-protocol path: no operator can ever be credited/reimbursed for that withdrawal (`validate_payer_is_operator` always fails), and no verifier will ever co-sign a real optimistic payout for it (UTXO already spent). This matches the Critical category "a move-to-vault UTXO permanently frozen." The attack is repeatable once per withdrawal/deposit (each successful forgery permanently freezes exactly the move-to-vault UTXO tied to that withdrawal's deposit), and is not operator-specific — it works against whichever deposit backs the targeted withdrawal, regardless of which operator would have serviced it.

### Likelihood Explanation
Preconditions are minimal and match the standard threat model: the attacker only needs to be the party that owns the withdrawal UTXO's private key and its `SinglePlusAnyoneCanPay` signature — both of which the withdrawer legitimately possesses from calling Citrea `withdraw`/submitting `WithdrawParams`. No verifier, operator, or aggregator cooperation, TLS certs, or majority hashrate are needed. Cost is only Bitcoin transaction fees plus self-funding output0 (which can be minimal, or even paid to the attacker's own address if they are the withdrawer). This is fully reproducible offline with `cargo test` against the transaction-building code without any live Citrea or mainnet dependency.

### Recommendation
Do not rely solely on the presence/absence of a parsable OP_RETURN to distinguish "regular payout" from "optimistic payout" in `update_finalized_payouts`. Instead, positively verify optimistic payouts by checking that the mined transaction structurally matches `create_optimistic_payout_txhandler`'s expected shape (specifically that it spends the move-to-vault output via input index 1 with the N-of-N script), and only treat a payout as a legitimate optimistic payout if that second input is present and correctly spends the deposit's move-to-vault UTXO. Any payout tx lacking both a valid operator OP_RETURN and a move-to-vault input should be treated as an anomalous/unauthorized event rather than silently defaulting to NULL/"optimistic."

    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )

            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,

            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
