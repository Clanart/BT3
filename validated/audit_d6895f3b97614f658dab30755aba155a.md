<Title>
Stale per-path manual conflict resolutions silently carried across successive commits and conflict kinds in multi-commit operations - (File: app/src/lib/stores/updates/changes-state.ts)

Summary
The rebase/merge/cherry-pick conflict state machine models "the user resolved this conflict" as a single persistent `Map<path, ManualConflictResolution>` attached to `ConflictState`, rather than as a state transition scoped to the specific commit/step being applied. Like the Minipool's `Destroyed`/`Finalised` pseudo-states, `manualResolutions` survives transitions that should be treated as fresh states (moving to the next commit in a multi-commit rebase, or switching conflict kind entirely), causing an old "ours"/"theirs" decision to be silently re-applied to an unrelated, later conflict on the same file path.

Finding Description
`updateConflictState` seeds every new `ConflictState` from the previous one's `manualResolutions`, unconditionally: [1](#0-0) 

That map is only cleared when the conflict disappears entirely (`prevConflictState == null`). It is *not* reset when the rebase/cherry-pick advances from one commit to the next (`REBASE_HEAD`/`currentTip` changes but the state `kind` stays `'rebase'`), nor is it re-validated against the new conflict's actual content: [2](#0-1) 

`getConflictState` then passes this same map straight through into the new state object regardless of which files are now conflicted: [3](#0-2) 

During an in-progress multi-commit operation, `updateMultiCommitOperationConflictsIfFound` pushes this same `manualResolutions` map into the active step whenever new conflicts are detected for a later commit: [4](#0-3) 

When the user clicks "Continue", the dispatcher pulls `manualResolutions` straight out of `RebaseConflictState` and hands it to git: [5](#0-4) 

`continueRebase`/`stageManualConflictResolution` apply the resolution purely by file path, with no check that it corresponds to the *current* conflict instance, and `checkoutConflictedFile` performs `git checkout --ours/--theirs -- <path>` against whatever is presently on disk: [6](#0-5) [7](#0-6) [8](#0-7) 

Concretely: if a user resolves `config.json` as "theirs" (incoming) while rebasing commit #1 of a multi-commit range, and commit #2 later in the *same* rebase operation also conflicts on `config.json` (different hunks, different content), Desktop reuses the stale `theirs` decision for commit #2 without ever surfacing that file as needing review — the file is auto-staged and committed with whatever the incoming side of *that* conflict is, silently, with no conflict-markers UI shown for it.

Impact Explanation
An attacker who controls the branch/PR being rebased onto, or the incoming commit range, can deliberately construct a sequence of commits that repeatedly touch the same file path so that each commit in the range produces a fresh conflict there. Once the victim manually picks "theirs" once (a very common one-click action to "accept incoming"), every subsequent conflict on that path within the same operation is auto-resolved the same way and silently committed — without ever displaying the new diff to the user. This is a silent corruption of what the user commits/pushes: the final rewritten history can contain attacker-supplied content (e.g. build scripts, CI config, dependency manifests) that the user never reviewed or explicitly approved for that specific commit, and which they subsequently push to a shared branch.

Likelihood Explanation
Requires no local/privileged access — only that the victim performs a normal rebase/cherry-pick against an attacker-influenced branch/PR containing multiple conflicting commits on the same path, and resolves one conflict manually. Multi-commit rebases with several conflicting commits on the same file are a realistic, unremarkable workflow, and "accept theirs" is an ordinary one-click UI action, not an unnatural user step.

Recommendation
Scope `manualResolutions` to the specific commit/step being applied instead of persisting it across the whole multi-commit operation and across conflict-kind transitions: clear or re-key the map whenever `currentTip`/`originalCommitSha` changes or the conflict `kind` changes, and require the working-directory content to still match what the resolution was recorded against (e.g., hash the conflicted blob at the time of resolution) before silently re-applying `--ours`/`--theirs` on a subsequent conflict for the same path.

Proof of Concept
1. Attacker prepares a feature branch/PR with two commits, both modifying `config.json` so each will conflict when rebased onto `main`.
2. Victim rebases the branch in Desktop; commit #1 conflicts on `config.json`; victim picks "Incoming" (`theirs`) to accept it.
3. Victim clicks Continue; rebase advances and commit #2 also conflicts on `config.json` with entirely different (malicious) content.
4. Because `manualResolutions` from commit #1 is reused verbatim (`app/src/lib/stores/updates/changes-state.ts:263-279`, `app/src/lib/stores/app-store.ts:3127-3164`), Desktop auto-stages commit #2's version via `git checkout --theirs -- config.json` without showing the user the second conflict, and the rebase completes.
5. Victim pushes the rebased branch, unknowingly shipping the attacker's second, unreviewed payload in `config.json`.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }
