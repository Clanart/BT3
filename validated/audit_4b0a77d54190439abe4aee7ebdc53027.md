### Title
Copilot merge-conflict reassembly silently drops/corrupts unresolved conflict content when embedded conflict-marker-like text is present — ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` splices per-hunk AI resolutions into the on-disk file "by order, not by line number," as the function's own doc comment states. Its well-formedness scan and the independent hunk-parsing pass in `extractConflictHunks()` (`app/src/lib/copilot-conflict-context.ts`) both terminate their look-ahead at the *first* line that looks like a `=======`/`>>>>>>>` marker, without validating structural nesting. A repository/file whose "ours" or "theirs" region legitimately contains marker-look-alike lines (7 `=`/`>` characters at column 0 — plausible in documentation, ASCII art, or any file that itself discusses/tests git conflict markers, including this very codebase's own conflict-marker test fixtures) causes both functions to be fooled identically into treating that embedded fake block as the entire conflict, truncating the hunk early. The remainder of the true conflict (real separator, real "theirs" text, real closing marker) is then copied through verbatim as ordinary file content by the outer loop in `reassembleResolvedFile()`, ending up baked into the "resolved" file that Copilot claims to have fully resolved.

### Finding Description
The report's broken invariant — a count/index computed under one assumption (`auctionAverageLookback`) being reused as the divisor for a differently-sized data set (`count`), silently producing a wrong downstream numeric result that is trusted without re-validation — maps onto Desktop's conflict-splicing pipeline as follows:

- `extractConflictHunks()` walks the raw file text and, per hunk, collects "ours" lines until it hits **the first** line matching `baseMarker` or `separatorMarker` (`^\|{7}` / `^={7}$`), then collects "theirs" lines until **the first** line matching `theirsMarker` (`^>{7}`). It never re-checks for a nested `oursMarker` or validates that the block it just parsed is truly a single, unnested conflict region. [3](#0-2) 

- `reassembleResolvedFile()` performs an analogous look-ahead: starting after a real `<<<<<<<` line, it scans forward, setting `hasSeparator = true` on **any** `=======`-looking line (without breaking), and stops at the **first** `>>>>>>>`-looking line, treating that as the block's close. [4](#0-3) 

Both routines are driven by the identical regexes (`oursMarker`/`reassemblyOursMarker`, `separatorMarker`/`reassemblySeparatorMarker`, `theirsMarker`/`reassemblyTheirsMarker`) and both stop at the first marker-look-alike line rather than the structurally-correct one. If the true conflict's "ours" or "theirs" side contains text that itself contains a `=======`/`>>>>>>>`-shaped line (7 repeated characters at the start of a line — a realistic occurrence in Markdown horizontal rules, ASCII banners, license headers, or files that document/test Git conflict markers), both `extractConflictHunks()` and `reassembleResolvedFile()` are fooled the same way: they agree on a truncated hunk boundary, so the hunk *count* still matches (passing `validateResolutionPaths()`'s count check), but the truncation point is wrong. The genuine remainder of the conflict block — the real `=======`, the real "theirs" text, and the real `>>>>>>>` marker — is never recognized as part of any conflict hunk by either function. `reassembleResolvedFile()`'s outer loop then copies these leftover lines through verbatim as if they were ordinary, already-resolved file content. [5](#0-4) 

The net effect: Copilot's AI resolution is spliced in for only the truncated fake sub-block, while the real, unresolved conflicting code from both branches — including literal stray `=======`/`>>>>>>>` marker text — is silently written into the file that the UI presents as "fully resolved" and that the user is invited to stage/commit.

### Impact Explanation
This corrupts *what the user commits*: a merge/rebase/cherry-pick conflict that Copilot claims to have resolved can, in fact, contain leftover unresolved code from both sides plus literal conflict-marker text, spliced silently into place. Depending on the language, this can produce code that still compiles incorrectly, silently reintroduces logic that was supposed to be dropped by one side, or leaves stray git-conflict-marker strings physically embedded in shipped source — all committed and potentially pushed without the user noticing, since the tool's UI shows this as a clean, model-approved resolution. This satisfies the "silent corruption of what the user commits or pushes" impact category from an attacker-controlled repository (a crafted commit/branch merged by the victim) without any local access, privilege, or unnatural user step beyond normal use of the Copilot conflict-resolution feature.

### Likelihood Explanation
Triggering the specific look-alike pattern requires a file whose real conflict content contains a line of exactly 7 `=` or `>` characters at the start of a line — plausible for Markdown files (`=======` is a common ATX-style underline/rule), ASCII banners, changelogs, or any file (including test fixtures or documentation) that itself illustrates Git conflict markers. An attacker who controls one side of a merge (e.g., a malicious upstream branch/PR that a victim merges locally and then hands to Copilot to resolve) can deliberately engineer this content. This is a realistic, low-effort primitive but requires the victim to specifically invoke the Copilot conflict-resolution feature on the affected file, so likelihood is moderate rather than trivial.

### Recommendation
Make hunk boundary detection structurally sound and keep `extractConflictHunks()` and `reassembleResolvedFile()` provably in lock-step, rather than relying on two independently-written "first marker wins" scans:
- Reject (treat as malformed/skip) any candidate conflict block whose "ours"/"theirs" region contains a line that matches `oursMarker`/`theirsMarker`/`baseMarker` before the expected closing marker is found, instead of silently treating it as ordinary body text.
- Have `reassembleResolvedFile()` re-use the exact same parsing routine (`extractConflictHunks()`, or a shared low-level tokenizer) instead of a second, independently maintained regex scan, so the two passes cannot diverge in their notion of "one hunk."
- After reassembly, run a post-condition check that the output contains zero lines matching the conflict-marker regexes; if any remain, fail closed (surface the file as unresolved) instead of writing a "resolved" file that may still contain literal marker text or duplicated/rebased content.

### Proof of Concept
1. Create a merge conflict in a file whose "ours" content includes a line that is exactly seven `=` characters, e.g.:
```
<<<<<<< HEAD
Notes
=======
this looks like a separator but is legitimate content
>>>>>>> feature
Real note continues here
=======
Real theirs content
>>>>>>> feature
```
   (Structurally this is a single, real conflict block whose "ours" side contains an embedded fake separator+closer pair as legitimate prose/documentation content — plausible in a README/CHANGELOG describing merge markers.)
2. `extractConflictHunks()` parses this as one hunk with `oursContent = "Notes\n<<<<<<< HEAD ... "`-truncated at the first fake `=======`/`>>>>>>>` pair, and returns only that truncated hunk to the model; `rawContent` (the full original text, including the real trailing `=======`/`Real theirs content`/`>>>>>>>`) is stored unchanged as `ctx.rawContent`. [6](#0-5) 
3. When the model's single-hunk resolution is spliced back via `reassembleResolvedFile(ctx.rawContent, raw.hunks)`, the outer loop's look-ahead likewise locks onto the first fake `=======`/`>>>>>>>` pair, splices in the model's resolution there, and then copies the trailing "Real note continues here / ======= / Real theirs content / >>>>>>> feature" through verbatim as ordinary file content. [7](#0-6) 
4. The final file written to disk (and subsequently offered for staging/commit) contains literal residual conflict-marker text and unresolved duplicate content, despite the dialog reporting the file as fully resolved.

Note: I was not able to fully trace the exact write-to-disk/commit call sites (`copilot-store.ts`, `app-store.ts`, `dispatcher.ts`) within the available context due to index truncation of `copilot-conflict-resolution.ts` and time constraints on further tool calls; a full session with file access is recommended to confirm the exact point where `resolvedContent` is written to the working directory and whether any post-write marker-scan safety net already exists there.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
