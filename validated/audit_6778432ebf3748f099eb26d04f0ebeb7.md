### Title
Flash-loan sandwich of `queueNewRewards` lets an attacker capture a disproportionate share of newly queued rewards with zero holding time - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` credits an entire newly queued reward amount instantly and in full to `rewardPerTokenStored`, using the current, spot value of `totalStaked()` (i.e., `IERC20(stakingToken).balanceOf(operator)`) rather than distributing rewards linearly over time. Because `totalStaked()` and `balanceOf(account)` are read live from `MasterMagpie`'s aggregate stake and per-user stake, an attacker who deposits a large flash-loaned amount immediately before a manager's `queueNewRewards`/`donateRewards` transaction, and withdraws right after, captures a proportional share of the whole reward for effectively zero real staking duration, at the expense of long-term stakers.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPool.sol` computes: [1](#0-0) 
```
rewardInfo.rewardPerTokenStored =
    rewardInfo.rewardPerTokenStored +
    (_amountReward * 10**stakingDecimals()) /
    this.totalStaked();
```
This is a one-shot, full-amount update of `rewardPerTokenStored`, unlike a Synthetix-style `StakingRewards` contract that streams the reward linearly over a duration via a `rewardRate` and `lastUpdateTime`. There is no time-weighting whatsoever: whoever's `balanceOf()` is largest at the exact moment `_provisionReward` executes gets a proportional slice of the *entire* reward.

`totalStaked()` and `balanceOf(_account)` are both derived from MasterMagpie's live balances: [2](#0-1) 

The attack path:
1. Attacker observes a pending `queueNewRewards` (or `donateRewards`) transaction from a `manager` in the mempool.
2. Attacker front-runs it with a large, flash-loan-funded `MasterMagpie.deposit(_stakingToken, hugeAmount)`. Inside `_deposit`, `_harvestBaseRewarder` calls `rewarder.updateFor(_account)` which snapshots `userRewardPerTokenPaid[_account]` to the **pre-update** `rewardPerTokenStored` value: [3](#0-2) [4](#0-3) 
3. The manager's `queueNewRewards` executes next, now dividing the reward by a `totalStaked()` inflated by the attacker's flash deposit, but the attacker's own `balanceOf()` is a large fraction of that inflated total, so `earned(attacker) = balanceOf(attacker) * (rewardPerTokenStored_new - userRewardPerTokenPaid_old) / 10**decimals` is large and disproportionate to the attacker's real economic time-at-risk (zero).
4. Attacker calls `MasterMagpie.withdraw` (triggers `_harvestBaseRewarder` → `updateFor` again, which locks in `userRewards[token][attacker] = earned(...)` as a fixed claimable balance independent of subsequent balance changes) and then claims via `getReward`/`multiclaim`, receiving the reward tokens, and repays the flash loan.

No modifier, `nonReentrant` guard, or time-lock prevents this: `deposit`/`withdraw` only guard against reentrancy, not against same-block deposit+withdraw sandwiching a reward injection. `queueNewRewards` is restricted to `onlyManager`, but the attacker does not need manager rights — they only need public `deposit`/`withdraw`/`getReward` calls and the ability to observe/front-run a manager's transaction, which is within the "unprivileged attacker" threat model (front-running is explicitly allowed per the rules).

### Impact Explanation
This results in theft of unclaimed yield: legitimate long-term stakers get a diluted `rewardPerTokenStored` increment relative to what they should receive had rewards been distributed proportionally to time staked, while the attacker extracts reward tokens funded almost entirely by other stakers' expected yield, using capital held for a single transaction/block. This matches the "theft or permanent freezing of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
Feasibility is high: the attacker needs (a) mempool visibility of a `queueNewRewards`/`donateRewards` transaction (a routine, recurring operational action performed by reward managers), (b) access to a flash loan of the staking token (readily available for most LP/staking tokens via Aave/Balancer/etc.), and (c) no special privileges. The attack is repeatable every time a reward is queued and is purely a function of attacker capital size relative to existing `totalStaked()`, making it economically attractive and reproducible across all pools using this reward-pool pattern (also present in `BaseRewardPoolV2.sol` and `mWOMSVBaseRewarder.sol`, which share the identical `_provisionReward` logic).

### Recommendation
Replace the instantaneous full-amount `rewardPerTokenStored` update with a time-weighted/streamed distribution model (e.g., Synthetix `StakingRewards`-style `rewardRate` + `lastUpdateTime`, streaming over a fixed duration), so that a snapshot of stake taken at a single instant cannot capture a full reward tranche. Alternatively, snapshot `totalStaked()`/user shares over an averaged window, or add a minimum holding/vesting period before newly queued rewards become claimable by newly deposited balances.

### Proof of Concept
Foundry test plan (`BaseRewardPoolFlashSandwich.t.sol`):
1. Deploy `MasterMagpie`, a staking token, and a `BaseRewardPool` with a reward token; register a `manager`.
2. Long-term staker LT deposits `1000e18` staking tokens and lets time pass (irrelevant here since no time-weighting exists, but included to model "long-term" intent).
3. Record `LT.earned()` baseline before any reward queue.
4. In the same block/transaction:
   a. Attacker contract takes a flash loan of `1_000_000e18` staking tokens.
   b. Attacker calls `MasterMagpie.deposit(stakingToken, 1_000_000e18)`.
   c. Manager calls `rewardPool.queueNewRewards(rewardAmount, rewardToken)`.
   d. Attacker calls `MasterMagpie.withdraw(stakingToken, 1_000_000e18)`.
   e. Attacker calls `MasterMagpie.multiclaim`/`getReward` to pull reward tokens, then repays the flash loan.
5. Assertions:
   - `attacker.earned(rewardToken)` (captured/claimed) is nonzero and approximately `rewardAmount * 1_000_000e18 / (1_000_000e18 + 1000e18)`, despite zero net holding time.
   - `LT.earned(rewardToken)` after the sandwich is materially lower than in a baseline run without the attacker's flash deposit (`rewardAmount * 1000e18/1000e18` baseline vs. diluted result), quantifying the yield stolen from the long-term staker. [5](#0-4)

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
