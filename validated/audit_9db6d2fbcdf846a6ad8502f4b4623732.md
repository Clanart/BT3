### Title
Integer division truncation in `_provisionReward` permanently freezes donated reward tokens when `totalStaked() > 0` - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.donateRewards` is a public, unprivileged entry point that forwards directly into `_provisionReward`, which computes `rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked()`. When `totalStaked()` is large relative to `_amountReward`, this division truncates to zero, yet the tokens have already been pulled via `safeTransferFrom` and `historicalRewards` is incremented, permanently stranding the transferred tokens with no accounting path to recover them.

### Finding Description
`donateRewards` has no access control beyond `isRewardToken[_rewardToken]` and calls `_provisionReward` exactly like the manager-only `queueNewRewards`: [1](#0-0) 

Inside `_provisionReward`, the queued-rewards fallback only triggers when `totalStaked() == 0`; when `totalStaked() > 0` but the reward is small enough for the division to truncate to zero, the branch that would preserve the leftover for a future distribution is never taken: [2](#0-1) 

Concretely: `IERC20(_rewardToken).safeTransferFrom(...)` pulls `_amountReward` tokens into the contract, `rewardInfo.historicalRewards` increases by the full amount, but if `(_amountReward * 10**stakingDecimals()) / totalStaked() == 0`, then `rewardInfo.rewardPerTokenStored` does not change. No user's `earned()` value ever reflects this donation because `earned` is entirely derived from `rewardPerTokenStored`: [3](#0-2) 

Since `stakingToken` balances used for `totalStaked()` are typically 18-decimal-scaled raw balances, any staked amount ≥ 1 token (i.e., `totalStaked() > 10**18`) makes `_amountReward = 1` (smallest unit) truncate to zero every single call, regardless of how many times it's repeated. There is no manager/owner sweep or recovery function in `BaseRewardPool.sol` for tokens stuck this way, so the dust is permanently unattributed and unclaimable by anyone.

### Impact Explanation
Each truncated call leaves `_amountReward` tokens locked in the contract's balance while not incrementing `rewardPerTokenStored`, so no staker's `earned()` ever accounts for it. Repeated indefinitely (e.g., in a loop or over time by any unprivileged caller, or even inadvertently by legitimate small donations/managers calling `queueNewRewards` with small dust amounts relative to a large pool), this results in permanent freezing of donated/queued reward funds with no code path in `BaseRewardPool.sol` to recover or re-attribute them — matching the "permanent freezing of unclaimed yield / funds frozen ≥24h" impact class.

### Likelihood Explanation
No special privileges are required — `donateRewards` is a plain external function. The only precondition is a staking pool with `totalStaked()` large enough (common for any actively used pool with an 18-decimal staking token) relative to the reward amount, which is trivially satisfiable by donating the smallest token unit (`1`) repeatedly. This is fully repeatable and requires only minimal capital (dust-sized token amounts) per call.

### Recommendation
Change `_provisionReward` to always accumulate into `queuedRewards` when the computed per-token increment would be zero (or when residual remainder exists), instead of gating the queued-rewards logic solely on `totalStaked() == 0`. E.g., compute the increment first, and if it truncates to zero, add `_amountReward` to `rewardInfo.queuedRewards` instead of silently dropping it; alternatively track and carry forward the integer-division remainder every time so it compounds into future donations rather than being lost.

### Proof of Concept
Foundry test outline:
1. Deploy `BaseRewardPool` with an 18-decimal staking token and a reward token; register attacker/staker via `MasterMagpie` such that `totalStaked() = 10 * 10**18` (or any value making `1 * 10**18 / totalStaked() == 0`).
2. Have an unprivileged attacker call `donateRewards(1, rewardToken)` N times (approving/minting 1 wei of reward token each time).
3. Assert `rewards[rewardToken].rewardPerTokenStored == 0` after all N calls while `rewards[rewardToken].historicalRewards == N`.
4. Assert `IERC20(rewardToken).balanceOf(address(pool)) == N` (tokens physically present) but sum of `earned(staker, rewardToken)` across all stakers `== 0`.
5. Assert there is no external/public function in `BaseRewardPool.sol` reachable by an unprivileged address that can reclaim or re-attribute this stuck balance, demonstrating permanent freezing.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
