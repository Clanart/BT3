## Analysis

I've confirmed the local analog: the Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows the *nominal* order amount rather than the *actually received* balance when a token is used, while the mainline EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) was deliberately fixed to measure balance deltas for exactly this reason (see its own comment: *"For fee-on-transfer tokens, the gateway receives less than the requested amount... We mutate order.inputs to reflect actual received"*).

### Title
Escrow bookkeeping in Tron IntentGatewayV2.placeOrder credits nominal amount instead of actual received balance, causing insolvent/over-credited escrow with fee-on-transfer or deflationary ERC20 tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, both the direct-transfer path (lines 444-463) and the predispatch path credit `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived purely from `order.inputs[i].amount` (the user-specified/nominal amount minus protocol fee) — without ever checking the gateway's actual `balanceOf` delta after `safeTransferFrom`. This is precisely the bug class described in the external report: bookkeeping trusts the requested/transferred amount instead of the amount actually received, which breaks for any ERC20 with non-standard transfer semantics (fee-on-transfer/deflationary tokens, and similar rebasing behavior).

### Finding Description
`placeOrder`'s non-predispatch branch: [1](#0-0) 

does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally adds `reducedInputs[i].amount` to the escrow ledger, where `reducedInputs[i].amount = originalAmount - protocolFee` and `originalAmount = order.inputs[i].amount` (the full nominal amount, not what the contract actually holds): [2](#0-1) 

If `token` deducts a transfer fee (deflationary token) or otherwise delivers less than the requested amount, the gateway's real token balance increases by less than `reducedInputs[i].amount`, but `_orders[commitment][token]` is credited as if the full amount arrived. The predispatch path has the same defect at line 435: it stores `reducedInputs[i].amount` in escrow even though the measured `balance`/`dust` calculation on lines 415-432 is only used to detect *excess* dust, not shortfall — a `balance < requiredAmount` check exists for the predispatch sweep, but `requiredAmount` there is `order.inputs[i].amount` (pre-fee-deduction on the *first* leg), so the deflationary-fee loss at the *second* transfer leg (dispatcher → gateway) is silently absorbed into escrow bookkeeping with no reconciliation against the fee-reduced actual amount.

By contrast, the mainline EVM contract explicitly guards against this: [3](#0-2) [4](#0-3) 

and is validated by dedicated tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, etc.): [5](#0-4) 

The Tron contract lacks this reconciliation entirely.

### Impact Explanation
This is not merely economic loss for the depositing user — it corrupts the shared escrow ledger used by `withdraw`/`fillOrder` for every order using that token pool. Because `_orders[commitment][token]` is a per-commitment credit but the underlying ERC20 balance is a single shared pool, over-crediting one order's escrow with tokens that were never actually received depletes real balance available to *other* orders' legitimate `withdraw()` calls. A solver/user filling or refunding an earlier order can be paid out in full (matching the inflated ledger entry) while draining the actual token balance that later orders' beneficiaries are entitled to — resulting in fund loss/lock for other users once real balance runs short, and a system-wide accounting mismatch that no existing guard (protocol-fee dust calculation, `safeTransferFrom` return check, or state proof pipeline) catches, since none of them compare intended amount against actual balance delta on the receiving side.

### Likelihood Explanation
Any unprivileged user can trigger this by placing an order on Tron's IntentGatewayV2 with a fee-on-transfer or otherwise non-standard ERC20 as an input token — no relayer, prover, or admin involvement is required. The condition depends on the deployment actually listing such a token as a supported input asset; the mainline EVM contract's parallel fix and dedicated test suite indicate the project is aware fee-on-transfer tokens are a real, expected input class for this gateway, making the Tron variant's omission a genuine regression/gap rather than an out-of-scope "malicious token" assumption.

### Recommendation
Mirror the mainline EVM fix in the Tron contract: after each `safeTransferFrom` (and after the predispatch sweep), measure the gateway's actual token balance delta and use that measured value — reduced by protocol fee — as the amount credited to `_orders[commitment][token]`, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 198-298. The order's `inputs[i].amount` should be mutated to the actually-received value before the commitment hash is computed, so the on-chain escrow ledger and the commitment always agree with real custody.

### Proof of Concept
1. Governance/admin lists a 1%-fee-on-transfer ERC20 token as a valid input asset on the Tron `IntentGatewayV2`.
2. User Alice calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}`, no protocol fee for simplicity.
   - `reducedInputs[0].amount = 1000e18` (no protocol fee deducted).
   - `safeTransferFrom(alice, gateway, 1000e18)` executes; due to the 1% fee, gateway's actual balance only increases by `990e18`.
   - `_orders[commitment][FOT] += 1000e18` — the ledger now claims 1000e18 escrowed, but only 990e18 physically exists.
3. User Bob places a second order with the same FOT token, `inputs[0] = {amount: 500e18}`; gateway physically receives `495e18`, but ledger records `+500e18`. Total ledger: `1500e18`; total physical balance: `1485e18`.
4. Alice's order is filled/cancelled first; `withdraw()` transfers the full `1000e18` recorded in her order's `WithdrawalRequest` (computed from the original commitment inputs) to the solver/refund beneficiary — the contract's actual FOT balance drops from `1485e18` to `~485e18` (minus another 1% fee on the outbound transfer).
5. When Bob's order is later filled/cancelled, `withdraw()` attempts to transfer `500e18` but the gateway now holds less than that, causing either a revert (locking Bob's funds indefinitely, since his `_orders` entry still shows `500e18` owed with no way to reduce it) or, if enough balance remains, an under-collateralized payout that silently draws down balance that should never have existed — demonstrating the ledger/physical-balance mismatch introduced solely by the missing balance-delta reconciliation.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
