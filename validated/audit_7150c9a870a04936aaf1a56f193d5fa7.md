### Title
Insufficient escaping in `escapeGitSpecialCharacters` allows newline injection to append attacker-chosen `.gitignore` rules beyond the intended path - (File: `app/src/lib/git/gitignore.ts`)

### Summary
The `.gitignore` special-character escaper used by `appendIgnoreFile` only strips the meaning of six characters (`[`, `]`, `!`, `*`, `#`, `?`) and never escapes or rejects newline characters. Since Git file paths reported through porcelain status can legitimately contain embedded `\n` bytes, an attacker-controlled repository can ship an untracked/changed file whose name contains a newline plus an attacker-chosen suffix. When the victim uses the normal "Ignore file (Add to .gitignore)" context-menu action on that entry, the resulting `.gitignore` write contains not one but two (or more) lines, the second of which is fully attacker-controlled and can express any pattern that doesn't use the six escaped characters (e.g. an entire directory, `src/`, or any literal file/extension name).

### Finding Description
`escapeGitSpecialCharacters` (`app/src/lib/git/gitignore.ts:103-109`) only escapes:
```
const specialCharacters = /[\[\]!\*\#\?]/g
``` [1](#0-0) 

It does not touch `\n`, `\r`, or `\\`. `appendIgnoreFile` (`app/src/lib/git/gitignore.ts:86-100`) escapes the caller-supplied path(s) and passes them straight to `appendIgnoreRule`, which joins them with `\n` and writes them verbatim to `.gitignore` via `formatGitIgnoreContents`/`saveGitIgnore` — no further sanitization occurs. [2](#0-1) [3](#0-2) 

The path that reaches `appendIgnoreFile` originates from `WorkingDirectoryFileChange.path`, which comes directly from `git status --porcelain=2 -z` output parsed by `parsePorcelainStatus`. That parser splits only on NUL bytes and explicitly supports (and is unit-tested for) paths containing raw newlines: [4](#0-3) 

The UI entry point is the "Ignore File (Add to .gitignore)" context-menu action in the Changes list, wired to `onIgnoreFile` → `dispatcher.appendIgnoreFile` → `git/gitignore.ts:appendIgnoreFile`: [5](#0-4) [6](#0-5) 

Because a file's actual name (not a synthetic UI string) is used verbatim as the "escaped" pattern, an attacker who controls the repository content can create a file whose real name is, e.g., `harmless.log\nsrc/` (a `\n` byte is a legal character in POSIX filenames and is preserved through Git's plumbing). Selecting "Ignore file" on this single entry produces a `.gitignore` with two lines:
```
harmless.log
src/
```
i.e., the write covers the intended file plus one arbitrary attacker-chosen pattern, not "the single intended path". Note the escaping of `!`, `#`, `[`, `]`, `*`, `?` does correctly prevent the injected line from being interpreted as a negation (`!path`), a comment (`#`), or a widened glob, because those characters get a leading backslash wherever they occur in the string, including right after the injected newline — so the specific "unignore `.gitattributes` via negation" variant described in the question is not achievable. The real, exploitable gap is that the second line can still be an arbitrary literal path/directory pattern chosen by the attacker (anything not using those 6 characters), which is a genuine scope-expansion beyond the single file the user intended to ignore.

### Impact Explanation
A user performing a routine, expected UI action (right-click → "Ignore file") on a file inside an attacker-supplied cloned/fetched repository can be made to silently add an unrelated, attacker-chosen ignore rule (e.g., an entire source directory or a specific sensitive file name) to `.gitignore`. Future files created under that directory/name will stop appearing as changes in Desktop's Changes list and will not be staged or committed by the user, which is a form of silent corruption of what gets committed — the developer believes they ignored one log/temp file, but in fact hides an entire directory from version control going forward, without any further confirmation dialog showing the actual bytes written.

### Likelihood Explanation
Requires only: (1) the attacker fully controls repository content, including filenames, which is in-scope; (2) the victim performs the standard, foreseeable "Ignore file" context-menu action on a file from the attacker's repo — a normal, expected step, not an unnatural one. It does not require negation-character abuse (which is otherwise blocked), only an embedded newline, which is straightforward to place in a filename on POSIX systems and is explicitly supported by Desktop's own status parser.

### Recommendation
In `escapeGitSpecialCharacters`, also escape/neutralize `\n` and `\r` (or reject/strip them and refuse the "Ignore file" action for filenames containing control characters), and/or ensure `appendIgnoreRule`/`appendIgnoreFile` validate that each resulting entry corresponds to exactly one line before writing to `.gitignore`.

### Proof of Concept
1. Attacker publishes/pushes a repository containing (or a commit that creates upon checkout/apply) a file whose literal name is `harmless.log\nsrc/` (raw `0x0A` byte embedded in the filename, followed by `src/`).
2. Victim clones/fetches the repo and opens it in GitHub Desktop; the file shows up as an untracked/changed entry with that name in the Changes list (`app/src/lib/status-parser.ts` correctly parses this embedded-newline path, as its own unit test at `app/test/unit/status-parser-test.ts:95-107` demonstrates).
3. Victim right-clicks the entry and selects "Ignore file (Add to .gitignore)" (`app/src/ui/changes/filter-changes-list.tsx:698-706` → `app/src/ui/changes/sidebar.tsx:269-271`).
4. `appendIgnoreFile` escapes only `[]!*#?`, leaving the embedded `\n` intact, and writes the pattern to `.gitignore` (`app/src/lib/git/gitignore.ts:86-100`, `:62-79`).
5. Inspecting `.gitignore` afterward shows two lines were added — `harmless.log` and `src/` — even though the user selected only one file to ignore.

/** Add the given pattern or patterns to the root gitignore file */
export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}

export async function appendIgnoreFile(
  repository: Repository,
  filePath: string | string[]

  if (filePath instanceof Array) {
    const escapedFilePaths = filePath.map(path =>
      escapeGitSpecialCharacters(path)
    )

    return appendIgnoreRule(repository, escapedFilePaths)

  return appendIgnoreRule(repository, escapedFilePath)
}

/** Escapes a string from special characters used in a gitignore file */
export function escapeGitSpecialCharacters(pattern: string): string {
  const specialCharacters = /[\[\]!\*\#\?]/g

  return pattern.replaceAll(specialCharacters, match => {
    return '\\' + match
  })
}
```
