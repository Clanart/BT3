### Title
Stale positional line-selection is silently re-applied to a freshly re-fetched diff during partial commits, allowing a changed working-directory file to corrupt what actually gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit (line-by-line staging) feature encodes the user's selection as a set of **positional** line indices (`DiffSelection`), computed against the diff that was rendered in the UI. When the commit is actually created, `applyPatchToIndex` re-fetches a **fresh** diff of the file and blindly re-applies the old positional selection to it, assuming the two diffs have the same line layout. If the file's diff shape changes between the moment the user made their selection and the moment the commit is staged, this positional assumption is violated and the wrong lines are silently included in, or excluded from, the commit — analogous to the Nibiru bug, where a static 1:1 relationship between an earlier-recorded value (bank coin amount) and a later-queried value (escrowed ERC-20 balance) was assumed to hold, but external changes (rebasing) broke that invariant.

### Finding Description
`DiffSelection` tracks selected lines purely by numeric index, with no notion of the line's content: [1](#0-0) 

That selection is created against a specific diff object rendered earlier by `updateChangesWorkingDirectoryDiff` (the diff shown to the user in the UI): [2](#0-1) 

When the user actually commits, `createCommit` → `stageFiles` → `applyPatchToIndex` runs, and critically **re-fetches a brand new diff** of the file right before formatting the patch: [3](#0-2) 

That freshly-fetched diff is then fed into `formatPatch`, which decides what to include using `file.selection.isSelected(absoluteIndex)` — i.e., the **old, positional** selection object is checked against the **new** diff's hunk/line layout: [4](#0-3) 

There is no verification anywhere in this path that the newly fetched diff has the same hunk boundaries, line counts, or content as the diff the selection was originally computed from. The code comments in `changes-state.ts` acknowledge this general class of problem only for the "selectable lines refresh on file-list update" case, not for the commit-time re-fetch: [5](#0-4) 

The invariant being assumed — "the line at absolute index N in the diff the user looked at is still the same logical line at index N in the diff we're about to patch" — is exactly the kind of static 1:1 assumption that the Nibiru report warns about, and it can be broken by anything that makes `git diff` non-deterministic or time-varying for the same file across two invocations, including:
- A malicious/cloned repository's `.gitattributes` referencing a `clean`/`smudge` filter (e.g. `filter=lfs`) whose driver fetches from a remote LFS/proxy endpoint. Since a `git remote`/proxy response can be attacker-controlled and can legitimately differ between two smudge/clean invocations (e.g. serving different bytes, or a server-side pointer update mid-operation), the two `getWorkingDirectoryDiff` calls (initial UI render vs. the one inside `applyPatchToIndex`) can observe different content for the same file.
- Any content-affecting normalization (`text=auto`, `eol=lf`) declared in the repository's committed `.gitattributes`, combined with content mutation of the file between the two diff computations.

In either case, `formatPatch`/`applyPatchToIndex` apply `--cached --unidiff-zero --whitespace=nowarn` (`app/src/lib/git/apply.ts:52-58`) blindly, with no re-validation of the selection's continued validity, so `git apply` will happily patch whatever lines fall at the recorded indices in the new diff.

### Impact Explanation
This causes **silent corruption of what the user commits**: the actual staged/committed content can differ from what the user visually selected in the diff viewer, without any error or warning. Depending on the shift in diff layout, this can mean:
- Lines the user explicitly deselected are committed anyway.
- Lines the user selected for inclusion are silently dropped or truncated (`git apply` may also outright fail if the hunk context no longer matches, but with `--unidiff-zero` unified context is skipped, increasing the chance of a "successful" but wrong application).
This directly matches the reported bug class' impact category: staged/escrowed state silently diverging from the value the user/app believes it represents, leading to unintended committed content — a repository-integrity issue introduced through a value assumed to be static but which changed via an externally influenced process.

### Likelihood Explanation
This requires a file whose diff can meaningfully change between the diff being rendered for user line-selection and the moment `createCommit` is invoked, driven by repository-declared attributes/filters that route through a remote-controlled backend (e.g. Git LFS smudge/clean over an attacker-controlled or proxied server) — a scenario explicitly named as valid in this task ("a git remote/proxy response"). It does not require local/physical access, admin rights, prior malware, or leaked credentials, and doesn't rely on unnatural user steps — a user simply opens a partial diff, selects a subset of lines, and commits, which is standard Desktop usage.

### Recommendation
Before applying `file.selection` to a newly-fetched diff in `applyPatchToIndex`, validate that the diff structure has not changed since the selection was created (e.g., compare hunk headers/line counts, or better, key the selection by diff/content hash instead of raw positional index). If the diff has changed, refuse the partial commit and force the user to re-review the diff, rather than silently re-mapping the stale selection onto new content.

### Proof of Concept
1. Clone a malicious repository that declares in `.gitattributes`: `data.txt filter=lfs -text` (or any content-affecting attribute whose backing filter driver fetches from a remote/proxy under attacker control).
2. Modify `data.txt` in the working directory and open the Changes view in Desktop; the diff is computed via `getWorkingDirectoryDiff` and rendered (`app-store.ts` `updateChangesWorkingDirectoryDiff`, lines 3444-3448).
3. Select a subset of lines to include in the commit (builds a `DiffSelection` keyed by absolute line index, per `diff-selection.ts`).
4. Before the user presses "Commit", have the attacker-controlled LFS/proxy backend return different smudged content for the same pointer on the next `git diff`/`git apply` invocation (or otherwise cause the file's diff layout to shift, e.g. via an .gitattributes-driven renormalization race).
5. Press "Commit". `applyPatchToIndex` re-fetches the diff (`apply.ts:60`) and applies the old selection's indices (`patch-formatter.ts:157`, `diff-selection.ts:122-136`) to the new diff via `git apply --cached` (`apply.ts:52-58`).
6. Inspect the resulting commit with `git show`: it contains different line content than what was visually selected in step 3, with no error or warning shown to the user.
