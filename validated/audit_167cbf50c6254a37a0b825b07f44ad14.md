### Title
Instant reward-per-token snapshot in `_provisionReward` allows unstaked-time-free reward sniping via stake→queueNewRewards→unstake sequencing - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.queueNewRewards`/`_provisionReward` distributes newly queued rewards by immediately increasing `rewardPerTokenStored` proportional to the current `totalStaked()`, with no time-based vesting (no `rewardRate`/`periodFinish` streaming). Because `earned()` is computed purely from `balanceOf(_account)` at query time versus the stored `userRewardPerTokenPaid` checkpoint, any account that is staked at the exact moment `_provisionReward` executes captures its full pro-rata share of the reward instantly, regardless of how long it was staked.

### Finding Description
`earned()` computes reward as `balanceOf(_account) * (rewardPerToken(token) - userRewardPerTokenPaid[token][_account]) / 10**decimals + userRewards[token][_account]` [1](#0-0) . The checkpoint `userRewardPerTokenPaid` is only updated inside `_updateFor`, invoked via the `updateReward` modifier on `getReward`, or implicitly during deposit/withdraw through `_harvestBaseRewarder` [2](#0-1) .

`_provisionReward` (called from `queueNewRewards`, restricted to `onlyManager`) does not stream rewards over time; it directly mutates `rewardPerTokenStored` in one shot: `rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked()` [3](#0-2) . There is no `rewardRate`/`periodFinish`/linear-vesting mechanism gating this increase to accrue only to stakers over the elapsed staking duration.

Attack flow:
1. Attacker observes (via mempool) a pending manager transaction calling `queueNewRewards(reward, token)` on a given pool's `BaseRewardPool`.
2. Attacker front-runs by calling `MasterMagpie.deposit(stakingToken, X)` with a large capital amount (e.g., flashloan-funded LP tokens). This triggers `_deposit`, which calls `_harvestBaseRewarder` (checkpointing existing balance) then sets `user.amount += X` and `user.available += X` [4](#0-3) . At this point, `balanceOf(attacker)` in `BaseRewardPool` reflects the newly staked `X`, and `userRewardPerTokenPaid` was checkpointed at the pre-reward `rewardPerTokenStored`.
3. Manager's transaction executes `queueNewRewards` → `_provisionReward`, bumping `rewardPerTokenStored` for the full staked pool (including attacker's freshly-added `X`).
4. Attacker calls `MasterMagpie.withdraw(stakingToken, X)`, which triggers `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward`, computing `earned()` using the *current* (post-reward) `rewardPerTokenStored` against `balanceOf(attacker)` which still includes `X` (checkpoint decrement happens after harvest) [5](#0-4) . The attacker receives the full pro-rata share of the newly queued reward attributable to `X`, despite holding the stake for zero meaningful duration.
5. Attacker repays the flashloan.

No existing modifier stops this: `onlyManager` on `queueNewRewards` only restricts *who can inject* rewards, not *who benefits* from the resulting `rewardPerTokenStored` bump; `nonReentrant`/`whenNotPaused` on `MasterMagpie.deposit`/`withdraw` do not prevent sequential same-block stake→claim→unstake; there is no minimum-stake-duration or linear-vesting check anywhere in `_provisionReward` or `earned()`.

### Impact Explanation
This is a direct theft-of-yield vulnerability: value intended for genuine long-term stakers is diverted to a temporary, capital-flush attacker who holds no meaningful economic exposure to the pool. This matches the Immunefi impact class "theft of unclaimed yield" and constitutes direct fund loss for legitimate stakers, since the same finite reward pot is now diluted among a larger `totalStaked()` denominator that briefly included the attacker's inflated stake, permanently reducing what honest long-term stakers receive.

### Likelihood Explanation
Preconditions are attacker-feasible: the attacker needs only capital to acquire/flashloan the staking token (or underlying LP) temporarily, and visibility into the manager's `queueNewRewards` transaction in the mempool to front-run it, or — if the reward manager (e.g., a harvest-triggering contract in the Wombat integration) permissionlessly calls `queueNewRewards` on a predictable schedule/condition — the attacker doesn't even need to front-run a specific tx, just time their stake/unstake around any predictable reward injection. This is repeatable every time a manager injects rewards, and is entirely mechanical (no oracle manipulation, no privileged role needed). I was unable to fully verify within available context whether the reward-manager role that calls `queueNewRewards` in production (e.g., `WombatStaking`) is itself permissionlessly triggerable by any EOA, which would make the attack even easier (self-triggered instead of front-run); this should be confirmed by inspecting `WombatStaking.harvest`/reward-manager wiring in the full checked-out repo.

### Recommendation
Introduce time-weighted reward distribution: replace the instant `rewardPerTokenStored += _amountReward / totalStaked()` update with a streaming/vesting model (e.g., Synthetix-style `rewardRate`/`periodFinish`, or Convex `BaseRewardPool`'s duration-based release) so that rewards accrue continuously over a fixed duration rather than being fully credited to whoever is staked at the exact injection block. Additionally, consider requiring a minimum staking duration before a deposit is eligible for freshly queued rewards, or checkpoint `userRewardPerTokenPaid` at deposit time to the value **at deposit**, excluding rewards queued before the deposit's own harvest checkpoint from being retroactively earned in the same block.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, a staking token, and `BaseRewardPool` with the staking token and a manager address (test manager EOA).
2. Fund a long-term staker (Alice) who deposits `100e18` staking tokens well before any reward injection, and lets several blocks pass with no reward queued yet (`rewardPerTokenStored == 0`).
3. Simulate flashloan-funded attacker (Bob) minting/acquiring `10000e18` staking tokens.
4. In a single test transaction batch (or same block via `evm_setAutomine(false)` + manual mining), sequence:
   - `masterMagpie.connect(bob).deposit(stakingToken, 10000e18)`
   - `rewardToken.mint(manager, reward)`; `baseRewardPool.connect(manager).queueNewRewards(reward, rewardToken)`
   - `masterMagpie.connect(bob).withdraw(stakingToken, 10000e18)`
5. Assert: `rewardToken.balanceOf(bob)` after step 4 withdraw's implicit harvest (or explicit `getReward` call) is > 0 and approximately `reward * 10000/10100` (Bob's disproportionate share despite zero elapsed staking time), while Alice's claimable earned amount reflects only `reward * 100/10100` despite having staked far longer.
6. Compare Bob's captured reward to a time-weighted expectation (which should be ~0 since Bob held the position for 0 blocks of "real" duration) — the mismatch demonstrates the sniping vulnerability and quantifies the stolen yield.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
