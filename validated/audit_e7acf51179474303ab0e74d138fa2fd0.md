### Title
Missing zero-value validation for `Kip71GasTarget` governance parameter causes division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`)

### Summary
The KIP-71 (Magma) base fee formula divides by the governance-controlled `GasTarget` parameter without any zero-guard, while the sibling divisor parameter `BaseFeeDenominator` is explicitly protected both at the governance-parameter validation layer and inside the formula itself. If `governance.kip71.gastarget` is ever set (or defaults) to `0`, every node computing the next block's base fee will panic.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next base fee by dividing intermediate values by `gasTarget` directly: [1](#0-0) [2](#0-1) 

Unlike `BaseFeeDenominator`, which has an explicit safety fallback: [3](#0-2) 

`gasTarget := kc.GasTarget` at line 77 has no equivalent zero-check before being used as a `big.Int` divisor at lines 102 and 120 (`x.Div(x, new(big.Int).SetUint64(gasTarget))`). A `big.Int.Div` call with a zero divisor panics at runtime in Go.

Critically, the governance parameter registry treats these two related divisor parameters inconsistently. `Kip71BaseFeeDenominator` enforces `v != 0` via its `FormatChecker`: [4](#0-3) 

But `Kip71GasTarget` uses a `noopFormatChecker`, meaning no validation at all is performed on the value before it is accepted as a governance parameter: [5](#0-4) 

Since `parentGasUsed == gasTarget` is only true when both are `0` (i.e., an empty block with GasTarget=0), any block with nonzero gas usage under a `GasTarget = 0` configuration falls into the `parentGasUsed > gasTarget` branch, which divides by `gasTarget` and panics.

### Impact Explanation
This computation happens for every block after the Magma hardfork on the base-fee/gas-price code path exercised by every full node (`VerifyMagmaHeader`/`NextMagmaBlockBaseFee`), and also propagates cross-chain via the service-chain bridge handler that forwards `KIP71Config` to child chains: [6](#0-5) 

If `GasTarget` is ever governed to `0` (accepted without any FormatChecker rejection), all nodes that process a block with nonzero gas usage will panic simultaneously, effectively halting the entire network — a consensus-breaking Denial of Service triggered purely by an accepted, unvalidated governance parameter value, analogous to the reported issue where unvalidated/unset fee parameters caused core protocol functions to always revert.

### Likelihood Explanation
Likelihood depends on a governance vote/parameter update reaching `0` for `governance.kip71.gastarget`, which is a legitimate, currently-supported governance parameter path (see `Kip71GasTarget` in the parameter table) but which — unlike its sibling `BaseFeeDenominator` — has no validation preventing the zero value from being accepted. This makes it reachable purely through the standard governance parameter voting mechanism without needing any other privilege escalation, and the missing check is a clear, provable inconsistency versus the adjacent, correctly-guarded parameter.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and any other KIP71 divisor-like parameters used unconditionally in `NextMagmaBlockBaseFee`) requiring `v != 0`, matching the pattern already used for `Kip71BaseFeeDenominator`. Additionally, add a defensive zero-check/fallback directly inside `NextMagmaBlockBaseFee` for `gasTarget`, mirroring the existing `BaseFeeDenominator == 0` fallback, so that a malformed or legacy chain config cannot crash nodes.

### Proof of Concept
1. Set chain governance parameter `governance.kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, per `kaiax/gov/param.go` lines 324-334).
2. Produce/process any post-Magma block whose `parentHeaderGasUsed > 0` (the common case).
3. `BlockChain` header validation or state transition calls `KIP71Config.NextMagmaBlockBaseFee`, which takes the `parentGasUsed > gasTarget` branch (since `0` gas used only equals `gasTarget` for genesis/empty blocks) and executes `x.Div(x, new(big.Int).SetUint64(0))`, causing a runtime panic on every full node evaluating that block, per `params/kip71_config.go` lines 99-103.
