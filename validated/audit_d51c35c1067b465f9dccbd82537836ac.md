## Analysis

The external report's core issue is: **unsafe/unchecked ERC20 transfer patterns that don't verify actual transfer success**, causing either reverts on non-standard tokens or, worse, silent state corruption when a token returns `false` instead of reverting on failure.

Searching the Hyperbridge intents code for the exact analog turned up a divergence between two parallel implementations of the same escrow-withdrawal logic:

- `evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw()` uses `IERC20(token).safeTransfer(beneficiary, amount)` [1](#0-0) 
- `evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()` — the Tron port of the same escrow-release logic — instead uses a raw low-level `.call()` with the `IERC20.transfer` selector, checking only that the call itself did not revert: [2](#0-1) 

### Title
Unchecked raw ERC20 `transfer` return-data in `IntentGatewayV2.withdraw()` allows silent transfer failure and permanent escrow loss - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2.withdraw()` function, invoked from the ISMP-authenticated `onAccept()` handler for `RedeemEscrow`/`RefundEscrow` messages, releases escrowed tokens using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks whether the low-level call reverted, never decoding/verifying the boolean return value. [3](#0-2)  The same fee-redemption path has the identical pattern. [4](#0-3) 

### Finding Description
For any ERC20 that signals failure by returning `false` rather than reverting, `success` from the low-level `.call()` will still be `true` (the call executed without throwing), so `if (!success) revert TransferFailed();` never triggers. Execution proceeds to decrement the escrow accounting and mark the order filled/refunded regardless of whether tokens actually reached the beneficiary: `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` are set unconditionally after the unchecked call. [5](#0-4) 

This directly mirrors the audited pattern in `Pool.removeLiquidity`/`rescue`/`skim` flagged in the external report — using unsafe transfer instead of `SafeTransferLib`/`safeTransfer` — but here the consequence is worse than a revert: it is a silent no-op transfer combined with irreversible state finalization (`_filled` is set, escrow is deducted), permanently locking the beneficiary out of their entitled funds because the withdrawal is already marked complete and cannot be retried.

The sibling EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol` already fixed this exact class of bug by using `safeTransfer`, confirming this is a known-and-remediated-elsewhere issue that was not ported to the Tron contract.

### Impact Explanation
This is a genuine loss-of-funds bug reachable through the normal, proof-verified `onAccept` path (authenticated via `authenticate()` checking the request source instance, not requiring any malicious relayer/prover) — an unprivileged user's escrowed order funds can become permanently unretrievable if the destination token has non-standard transfer semantics, since the contract believes the withdrawal succeeded and finalizes state (`_filled`), while the beneficiary never received tokens.

### Likelihood Explanation
Likelihood is medium: it requires interacting with a token whose `transfer()` returns `false` on failure without reverting. This is a real subset of ERC20 tokens in production (rather than a purely theoretical edge case), and no additional privileged or malicious actor is needed — a legitimate cross-chain escrow settlement on such a token triggers the bug deterministically.

### Recommendation
Replace the raw `.call()` + selector pattern in `withdraw()` (both the escrow release and the `TRANSACTION_FEES` redemption branch) and in the `SweepDust` handler with `SafeERC20.safeTransfer` / `SafeTransferLib.safeTransfer`, matching the already-corrected implementation in `evm/src/apps/intentsv2/IntentsBase.sol`, so that failed transfers always revert before escrow state is mutated.

### Proof of Concept
1. An order is placed on the source (Tron) chain with `inputs` denominated in a token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (a valid ERC20 pattern per EIP-20).
2. Destination-chain fill/cancellation dispatches a `RedeemEscrow`/`RefundEscrow` `PostRequest` back to the source chain, which is delivered and proof-verified by the host, then routed to `IntentGatewayV2.onAccept()` → `withdraw()`. [6](#0-5) 
3. Suppose token `T`'s `transfer` returns `false` for this call (e.g., contract-specific restriction, blacklist, or paused state) rather than reverting.
4. `token.call(...)` succeeds (`success == true`) since the EVM call itself doesn't revert; the `if (!success) revert TransferFailed();` check passes silently. [7](#0-6) 
5. `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` execute, marking the order permanently settled. [8](#0-7) 
6. The beneficiary never received the tokens, and since the order is now `_filled`, no further redemption/refund attempt can succeed — the escrowed funds are permanently stuck in the contract.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
