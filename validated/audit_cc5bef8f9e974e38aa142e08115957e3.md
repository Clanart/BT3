### Title
Silent ERC20/TRC20 transfer failure in `IntentGatewayV2.withdraw()` on Tron causes permanent loss of escrowed funds without reverting - (`File: evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses raw low-level `.call()` with the `IERC20.transfer` selector and only checks the boolean `success` returned by `call()` (i.e. that the call did not revert), never decoding and validating the ABI-encoded `bool` return value the ERC20/TRC20 `transfer` function is supposed to return. This is the exact bug class from ETRP-1 (unsafe `transfer`/`transferFrom` usage), but manifested on the payout side instead of the deposit side: for a non-compliant token that returns `false` on failure instead of reverting, the gateway will treat the transfer as successful, decrement the escrow accounting, and never actually deliver the tokens to the beneficiary — permanently losing/locking the escrowed funds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the `withdraw()` function (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests) releases escrowed tokens using: [1](#0-0) 

```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The same unsafe pattern also appears in the transaction-fee payout right after, and in the `SweepDust` handler: [2](#0-1) [3](#0-2) 

Only `success` (whether the external call reverted) is checked; the returned bytes (which should encode a `bool`) are discarded (`(bool success,) = ...`). Per the ERC20/TRC20 standard, `transfer` can return `false` without reverting on failure — a pattern explicitly called out as unsafe in the external report (ETRP-1) for `deposit`. This contract's rest of the codebase is aware of the risk and correctly uses `SafeERC20.safeTransferFrom`/`safeTransfer` for all deposit-side and escrow-input transfers (e.g. `evm/tron/contracts/apps/IntentGatewayV2.sol:399`, `453`, `478`), and `IntentsBase.sol`'s `_withdraw` on the standard EVM path also correctly uses `IERC20.safeTransfer` (`evm/src/apps/intentsv2/IntentsBase.sol:408`). Only the Tron `withdraw()`/`onAccept(SweepDust)` payout paths regressed to the unsafe raw `.call()` pattern with an unchecked return value.

Because `_orders[body.commitment][token] -= amount;` executes unconditionally after the `success` check passes (which it will, even if the token internally returned `false`), the escrow bookkeeping is decremented as though the beneficiary was paid, while the tokens remain stranded in the `IntentGatewayV2` contract with no accounting path left to reclaim them for that beneficiary.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "logic attacks" categories. A solver/user beneficiary who is owed escrowed input tokens (on `RedeemEscrow`) or a refund (on `RefundEscrow`) can have their entitled tokens silently not delivered while the contract's internal accounting (`_orders[...]`) is decremented as if payment succeeded. The `EscrowReleased`/`EscrowRefunded` event still fires, giving a false signal of settlement. This is not contingent on a malicious relayer, prover, or admin — it only requires that the escrowed `token` be a real-world, non-standard-compliant ERC20/TRC20 that returns `false` rather than reverting on transfer failure (e.g. due to blacklist, paused state, or insufficient contract balance from unrelated causes), which is common and permissionless to select at order-placement time.

### Likelihood Explanation
Likelihood is moderate: the attacker/affected party does not need any privileged role — any user can place/fill an order denominated in an arbitrary ERC20/TRC20 token address of their choosing (`order.inputs[i].token`, `order.output.assets[i].token`), and there is no allow-list restricting escrowed tokens to well-behaved ones (the code already anticipates fee-on-transfer and other nonstandard tokens elsewhere, e.g. `evm/tron/contracts/apps/IntentGatewayV2.sol` predispatch dust-accounting logic). Triggering the exact failure condition requires a token whose `transfer` returns `false` instead of reverting under some internal condition (blacklists, pausing, transient balance issues) — a known and non-exotic category of tokens.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` occurrences in `withdraw()` and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(beneficiary, amount)` from OpenZeppelin's `SafeERC20` (already imported and used elsewhere in this same file via `using SafeERC20 for IERC20;`). This ensures both call-revert failures and boolean-`false` return values are treated as failures and revert the whole transaction, keeping the escrow accounting and actual token movement atomic and consistent.

### Proof of Concept
1. Deploy a TRC20/ERC20-like token `MaliciousToken` whose `transfer(address,uint256)` function returns `false` (without reverting) whenever the recipient is blacklisted or under some triggerable internal condition, while its `transferFrom` behaves normally (so `placeOrder`'s `safeTransferFrom` succeeds and the token is escrowed normally).
2. User places an order with `MaliciousToken` as an input, successfully escrowing tokens into `IntentGatewayV2` (`_orders[commitment][token] += amount`).
3. Order is cancelled/refunded (or filled), and `onAccept` dispatches `withdraw(body, ...)` with `beneficiary` set to the blacklisted/triggering address.
4. In `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (call did not revert) but the encoded return data is `false`.
5. `if (!success) revert TransferFailed();` does not trigger since `success == true`; `_orders[body.commitment][token] -= amount;` proceeds, and `EscrowReleased`/`EscrowRefunded` is emitted — but `beneficiary` never actually received the tokens, which remain stuck in the `IntentGatewayV2` contract with no remaining accounting path to redeem them.
