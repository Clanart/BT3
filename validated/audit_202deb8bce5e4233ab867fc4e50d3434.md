### Title
`Scanner::register_offset` permanently denies later offsets that collide with an earlier registration, yielding funds that scan under the wrong offset and are unspendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The reported bug class is a front-run/in-order binding failure: an earlier registration claims an identifier such that a later, legitimately distinct object can never be bound to it, causing a permanent denial of service for that object. The exact analog lives in `Scanner::register_offset`, which maps scalar offsets to P2TR `script_pubkey`s surjectively and order-dependently, and returns `None` on collision rather than advancing to the next usable offset. [1](#0-0) 

### Finding Description
`register_offset` increments the requested offset until `key + offset*G` produces an even-Y point, then looks up `self.scripts` **by script**. If that script is already present it executes `None?` — aborting the whole registration — instead of continuing to increment to the next candidate: [2](#0-1) 

Two distinct requested offsets `o1 < o2` can therefore converge on the same script (e.g., `o2` is odd-Y and increments to `o2+1`, whose script was already claimed by an earlier registration). The earlier registration wins purely by ordering — structurally identical to the attacker's `createPool` winning the `poolId` the victim's strategy was bound to. The doc comment itself concedes "offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets." [3](#0-2) 

The consequences compound in `scan_transaction`, which identifies outputs solely by `script_pubkey` and reports the stored offset: [4](#0-3) 
If a caller proceeds under the failed/`None` registration — or re-registers and gets a different offset than the one the depositor derived their address from — an incoming Bitcoin output is matched to `self.scripts[script]` = the *other* offset. Spending requires offsetting the threshold keys by the recorded scalar (`ReceivedOutput::offset`), so the wallet attributes the funds to a key path that doesn't correspond to the intended deposit identity — funds reported received that are not spendable under the intended offset. [5](#0-4) 

### Impact Explanation
- Permanent DoS of any offset whose parity-adjusted script collides with a previously registered script — the registration can never succeed, no retry path exists.
- Because scanning keys on `script_pubkey` alone, a collision silently aliases two logical deposit addresses to one stored offset, causing funds to be credited/scanned under the wrong scalar — the "funds reported received that are not spendable" accept criterion.

### Likelihood Explanation
Offset space per script is effectively halved (only even-Y results are usable), and each ~50% parity increment makes a fresh offset land on an already-claimed point with non-trivial probability as the registration count grows. The trigger requires only ordering — an earlier registration wins — which is exactly the unprivileged front-run mechanism of the source report: whichever offset registers first permanently captures the script. (I could not confirm whether in `processor/src/networks/bitcoin.rs` the requested offsets are derived from attacker-influenced instruction data; if they are, the collision can also be induced deliberately by grinding.)

### Recommendation
- On script collision, continue the `offset += Scalar::ONE` loop (still skipping odd-Y results) instead of returning `None`, so distinct requested offsets deterministically map to distinct scripts.
- Alternatively, key `scripts` by the requested offset as well as the script, and fail loudly upstream so a caller can never proceed with an offset different from the one used to derive the deposit address — i.e., bind offset generation and address derivation into one step, mirroring the report's "bind create strategy inside createPool" recommendation.

### Proof of Concept
```rust
// networks/bitcoin Scanner behavior
let key = ProjectivePoint::GENERATOR * Scalar::from(7u64);
let mut scanner = Scanner::new(key).unwrap();

// Attacker/earlier registrant claims an offset first
let o1 = scanner.register_offset(Scalar::from(100u64)).unwrap();

// Victim requests an offset whose parity increment lands on a script
// already claimed. Pick o2 such that key + o2*G is odd-Y and
// key + (o2+1)*G equals a script already in scanner.scripts
// (e.g., o2 + 1 == o1's stored offset).
// register_offset returns None instead of trying o2 + 2:
assert_eq!(scanner.register_offset(o2), None); // permanent DoS for o2

// A deposit to the victim's derived address still scans — but under
// the earlier registrant's offset:
let outs = scanner.scan_transaction(&tx_to_victim_script);
assert_eq!(outs[0].offset(), o1); // wrong offset -> unspendable as intended
```

Uncertain: I did not verify the call sites in `processor/src/networks/bitcoin.rs` to confirm whether requested offsets are attacker-influenced, so the deliberate-front-run variant is plausible but not proven; the ordering/aliasing defect itself is fully supported by the code above.

```rust
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
```

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
