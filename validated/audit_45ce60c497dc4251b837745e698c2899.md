### Title
Unbounded pool-reward claim in `PlotNFT2Wallet.claim_rewards` can grow beyond block cost limits, permanently blocking reward claims - (File: chia/wallet/plotnft_wallet/plotnft_wallet.py)

### Summary
`PlotNFT2Wallet.claim_rewards` fetches **all** unclaimed pool-reward coins for a PlotNFT and builds a single, unbounded `SpendBundle` containing one coin spend per reward plus the singleton spend. Unlike the legacy `PoolWallet.claim_pool_rewards`, which explicitly caps the number of reward coins bundled into a single transaction via `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`, the new PlotNFT2 code has no such cap. If a PlotNFT accumulates enough unclaimed pool-reward coins (e.g., because a farmer/pool operator delays claiming, or a pool sends many small reward payouts over time), the resulting spend bundle's CLVM execution cost can exceed `MAX_BLOCK_COST_CLVM`, making the transaction permanently unincludable in any block. This is directly analogous to the reported "Unbounded loops in `claimRewards`" issue: an ever-growing collection (pool reward coins here, instead of internal/external reward tokens) is iterated without bound when a user tries to claim, risking DoS and loss of the ability to claim rewards.

### Finding Description
`PlotNFT2Wallet.claim_rewards` retrieves the full list of pool rewards for the PlotNFT with no limit: [1](#0-0) 

It then passes the entire, unbounded `rewards_to_claim` list into `PlotNFT.claim_pool_rewards`, which builds one `SendMessage` condition per reward in the singleton's delegated puzzle and one additional `CoinSpend` per reward coin: [2](#0-1) 

Both the singleton's inner-puzzle execution cost (which scales with the number of `SendMessage` conditions/reward coins) and the aggregate spend bundle's coin-spend count grow linearly and unboundedly with the number of accumulated reward coins, with no cap anywhere in `claim_rewards`.

By contrast, the legacy `PoolWallet.claim_pool_rewards` explicitly protects against this by capping spends per transaction: [3](#0-2) 

The mempool/full node enforces a hard cost ceiling per spend bundle (`max_tx_clvm_cost`, tied to `MAX_BLOCK_COST_CLVM`): [4](#0-3) 

If a PlotNFT accumulates enough unclaimed reward coins (through normal pool payouts over time, analogous to the admin adding reward tokens in the original report), a call to `claim_rewards` will build a bundle that exceeds this cost ceiling and be rejected by every honest node, with no fallback batching logic to split the claim into smaller chunks.

### Impact Explanation
Once the reward-coin count for a given PlotNFT grows large enough that the resulting `claim_pool_rewards` spend bundle exceeds `MAX_BLOCK_COST_CLVM`, the wallet can no longer construct a valid claim transaction for that PlotNFT at all — `claim_rewards` always attempts to bundle every outstanding reward coin in one transaction. This causes a denial of service on reward claiming and can result in permanent loss of access to those farmed/pooled rewards, mirroring the "Users could lose all their rewards" impact in the original report. This qualifies as Medium severity: it is a spend-triggered transaction-processing halt reachable purely from a legitimate wallet action (claiming rewards), not requiring any malicious peer or privileged actor.

### Likelihood Explanation
Likelihood is moderate: it requires the number of unclaimed pool-reward coins for a single PlotNFT to grow large (e.g., due to infrequent claiming, small/frequent pool payouts, or a user intentionally delaying claims), which is a normal and expected usage pattern for pooling, not an attacker-controlled edge case. The test suite even demonstrates a scenario of accumulating multiple unclaimed rewards ("RECEIVE REWARDS (while pooling)" / "LOSE REWARDS" in `test_plotnft_wallet.py`), showing this is an anticipated but only partially mitigated state. [5](#0-4) 

### Recommendation
Add a bound to `PlotNFT2Wallet.claim_rewards` analogous to `PoolWallet.claim_pool_rewards`'s `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`: cap the number of reward coins claimed per transaction (e.g., via a `max_spends_in_tx` parameter), truncate `rewards_to_claim` to that cap, and allow/require multiple `claim_rewards` calls (or automatic chunked batching) to fully drain a large backlog of pool rewards, mirroring the safeguard already present in the legacy pool wallet code path.

### Proof of Concept
1. Join a pool with a PlotNFT2 (`PlotNFT2Wallet.join_pool`).
2. Farm many blocks to the PlotNFT's `p2_singleton_puzzle_hash` so that a large number of pool-reward coins accumulate unclaimed (as done for `EXTRA_POOLING_REWARDS` in `test_plotnft_wallet.py`, but scaled up to hundreds/thousands of reward coins instead of 2).
3. Leave the pool so `claim_rewards` becomes callable.
4. Call `PlotNFT2Wallet.claim_rewards`; observe that `rewards_to_claim` (from `plotnft2_store.get_pool_rewards`) contains all accumulated reward coins with no truncation, and the constructed `WalletSpendBundle`'s CLVM cost (one `SendMessage` + one `CoinSpend` per reward) grows linearly until it approaches/exceeds `MAX_BLOCK_COST_CLVM`, at which point `pre_validate_spendbundle`'s cost check in `mempool_manager.py` (lines 571-576) will reject the transaction outright, leaving the user permanently unable to claim those rewards in a single call and with no batching fallback implemented.
