### Title
Out-of-range participant index in blame handling causes `HashMap` index panic (node DoS) - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The PedPoP DKG blame path indexes `self.commitments` with a `Participant` value taken directly from the accusation arguments, without checking that the participant is within `1 ..= n`. `Participant::new` only rejects `0`, so any non-zero `u16` (e.g. `n + 1`, or `65535`) passes parsing. When `blame_internal` evaluates `self.commitments[&sender]`, the `HashMap` indexing operator panics on the missing key — a Rust analog of the CVE-2018-6249 NULL-pointer-dereference class (missing validation of an externally supplied index → crash/DoS).

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender` and `recipient` as `Participant` and pass them to `blame_internal`, which verifies the accused share:

```rust
// crypto/dkg/pedpop/src/lib.rs
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],   // line ~599: panics if sender not in map
    Zeroizing::new(share),
  ))
  .is_identity(),
)
```

`self.commitments` only ever contains keys `1 ..= n` (it is populated from `params.all_participant_indexes()` in `verify_r1`, or from `1 ..= n` in `AdditionalBlameMachine::new`). Nothing in `blame`, `blame_internal`, or `AdditionalBlameMachine::blame` bounds-checks `sender`/`recipient` against `n`. `Participant::new` merely enforces non-zero (`crypto/dkg/src/lib.rs:29-35`), so a deserialized accusation carrying `sender = Participant(0xFFFF)` or `n + 1` is accepted at the parsing layer (e.g. `Transaction::read` for `InvalidDkgShare` builds `accuser`/`faulty` via `Participant::new`, rejecting only zero) and reaches `blame_internal`, where `self.commitments[&sender]` panics.

The same class of unchecked indexing does not exist on the honest path — `calculate_share` validates its map via `validate_map` before indexing `self.commitments[&l]` (line ~490), and `view()` bounds `included` against `n` before `verification_shares[i]` — the blame handler is the gap.

### Impact Explanation
Any party able to submit a blame/invalid-share accusation (in Serai's deployment, a `DkgShares`/`InvalidDkgShare`-style message naming an arbitrary `Participant`) can crash the evaluating node/process. Since these messages are consumed by coordinator/processor code that `unwrap`s or directly indexes, the panic aborts the key-generation/blame evaluation and can take down the validator handling it — a remote, unprivileged denial of service matching the CVE's "NULL pointer dereference → denial of service" shape.

### Likelihood Explanation
Triggering requires only submitting an accusation whose `sender` (or a `recipient` referenced through flows that index by it) is a non-zero `u16` outside `1 ..= n` — no valid keys, threshold coalition, or cryptographic work is needed. The `EncryptedMessage`/`proof` arguments do not need to verify, since the panic at `self.commitments[&sender]` is reached only after the share checks — actually, note the panic occurs inside the final verification branch (`share_verification_statements`), i.e. after `decrypt_with_proof` succeeds and the share deserializes; an accuser referencing a non-existent `sender` may hit it earlier via paths that look up commitments before those checks depending on caller ordering. If `decrypt_with_proof` fails first, the function returns `sender`/`recipient` without indexing, so a caller must reach the final block — this requires a well-formed `msg`/`proof` pair, which a real DKG participant (the accuser) can supply by relaying a genuine encrypted share while naming a bogus `sender`. That remains fully within an unprivileged participant's capability.

### Recommendation
In `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal`, validate `sender` and `recipient` against the known participant set (`self.commitments.contains_key(...)`, or bounds-check `u16::from(p) <= n` and non-zero) and return an error/sentinel instead of indexing. Replace `self.commitments[&sender]` with `self.commitments.get(&sender)` plus an explicit fault decision (e.g. blame the accuser or reject the accusation). Similarly, `AdditionalBlameMachine::new` should verify each registered `Commitments` vector has length `t` (currently only `n` is taken), since `blame_internal` later assumes well-formed per-sender commitment vectors.

### Proof of Concept
```rust
// crypto/dkg context: assume a completed BlameMachine `bm` for params n = 5.
// An accuser relays a valid EncryptedMessage + EncryptionKeyProof that decrypts
// to a canonical scalar, but names a non-existent sender.

let bogus_sender = Participant::new(6).unwrap();   // n == 5; only nonzero is checked
let recipient    = Participant::new(1).unwrap();

// msg/proof: a genuine EncryptedMessage<SecretShare> + ECDH proof produced during
// the real DKG (decrypt_with_proof succeeds, share parses as C::F).
// blame_internal reaches:
//   share_verification_statements(recipient, &self.commitments[&bogus_sender], share)
// which evaluates HashMap::index on a missing key:
//   panic: "no entry found for key"
bm.blame(bogus_sender, recipient, msg, Some(proof));
```

Equivalent trigger for a non-participant observer via `AdditionalBlameMachine::new(context, n, commitment_msgs).unwrap().blame(bogus_sender, recipient, msg, proof)`.
