## Analysis

`_cancelFromSource` in `ExtrinsicIntents.sol` treats `commitment` and `order` as independent, unauthenticated inputs — the function never re-derives or checks that `commitment == keccak256(abi.encode(order))`. [1](#0-0) 

The only ownership check is `order.user != msg.sender`, which is trivially satisfiable since the attacker fully controls the `order` struct fields (including `user`) and only needs to supply a real `commitment` value plus matching token addresses to pass the escrow-existence check: [2](#0-1) 

The `WithdrawalRequest` context built for the GET request uses the attacker-supplied `order.user` as `beneficiary` and `order.inputs` as the token amounts to release, bound only by the real `commitment`: [3](#0-2) 

Once `onGetResponse` confirms the destination `_filled[commitment]` slot is empty, it decodes this attacker-controlled context and calls `_withdraw`, which pays `body.beneficiary` (attacker) out of `_orders[commitment][token]` (the victim's real escrow): [4](#0-3) [5](#0-4) 

Note that `_withdraw`'s `escrowed - amount` uses Solidity 0.8 checked arithmetic, so an attacker cannot inflate the refund beyond the actually-escrowed balance (over-withdrawal reverts) — but **redirecting the entire refund to an arbitrary beneficiary is possible**, since `_orders` is keyed only by `(commitment, token)` with no stored owner, and `commitment` values plus their input token/amount fields are public (emitted in `OrderPlaced`), letting anyone reconstruct a valid `commitment` → real-escrow linkage without needing the true order struct. [6](#0-5) [7](#0-6) 

I was unable to fully retrieve the public entry-point wrapper in `evm/src/apps/IntentGatewayV2.sol` that calls `_cancelFromSource` (tool budget exhausted), so I cannot 100% confirm whether that outer function independently recomputes/validates `commitment` from `order` before calling into `_cancelFromSource`. If it does, this finding is moot. Based on the internal function's logic alone, and the fact that `commitment` is passed as a bare parameter never hashed or cross-checked against `order` anywhere in `ExtrinsicIntents.sol`/`IntentsBase.sol`, the vulnerability appears real at this layer. A Devin session with full repo access should verify the entry-point wrapper before treating this as fully confirmed.

### Title
Unauthenticated commitment/order binding in `_cancelFromSource` allows refund redirection to arbitrary beneficiary - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromSource` accepts `order` and `commitment` as independent parameters without verifying `commitment == keccak256(abi.encode(order))`. The only access check (`order.user == msg.sender`) is satisfiable by anyone submitting a fabricated `order` with their own address as `user`. If the associated real `commitment` (public via `OrderPlaced`) has an unfilled escrow, the attacker can trigger `onGetResponse` → `_withdraw` to pay the escrow to themselves instead of the true order creator.

### Finding Description
- `_orders[commitment][token]` stores escrow amounts keyed only by `commitment` and `token`, with no stored owner field.
- `_cancelFromSource` builds `WithdrawalRequest.beneficiary = order.user`, trusting the caller-supplied `order` rather than the order that was actually escrowed under `commitment`.
- The GET-request storage-proof key is derived purely from `commitment` (via `_calculateCommitmentSlotHash`), so it correctly verifies the destination-chain fill status of the *real* order, but the beneficiary/token data used for the payout comes from the attacker's *fabricated* `order`.
- `_withdraw`'s checked subtraction prevents amount inflation beyond the true escrowed balance, but does not prevent redirecting the full escrowed balance to an unauthorized beneficiary.

### Impact Explanation
Any unprivileged party who knows a target `commitment` (publicly derivable from the `OrderPlaced` event) can steal the entire refund of any expired, unfilled cross-chain order by fabricating a matching `order` struct with themselves as `user`/beneficiary. This directly violates the requirement that escrow refunds move "exactly once and only to the rightful beneficiary."

### Likelihood Explanation
High, assuming the outer public entry point does not independently bind `commitment` to `order` via hashing before calling `_cancelFromSource`. Exploitation requires only public on-chain data (order fields from `OrderPlaced`) and a single unprivileged transaction after `order.deadline`.

### Recommendation
Derive `commitment` internally as `keccak256(abi.encode(order))` inside `_cancelFromSource` (and `_cancelFromDest`) rather than accepting it as a caller-supplied parameter, ensuring the beneficiary/token data used for withdrawal always matches the actual escrowed order.

### Proof of Concept
1. Victim places order O on source chain, escrowing `_orders[C][tokenA] = N` where `C = keccak256(abi.encode(O))` (C is derivable from the emitted `OrderPlaced` event fields).
2. After `O.deadline` passes, attacker (unprivileged) calls the public cancel-from-source entry point with a fabricated `order'` where `order'.user = attacker`, `order'.inputs = [{tokenA, N}]`, `order'.destination = O.destination`, `order'.deadline = 0`, but passes the real `commitment = C`.
3. `_cancelFromSource` passes the `order.user == msg.sender` and `_orders[C][tokenA] != 0` checks, then dispatches a GET request keyed on the real `_filled[C]` slot on the destination chain.
4. If O was never filled, `onGetResponse` confirms the slot is empty and calls `_withdraw` with `beneficiary = attacker`, transferring N of tokenA from the victim's escrow to the attacker.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
