## Summary

The reported bug class — a governance-controlled allowlist (`selectedApplications`) that exists in storage but is never actually checked in the execution/settlement path — has a direct local analog in `IntentGatewayV2`'s cross-chain peer-authentication logic. The "list" here is the `_instances` mapping of known/registered `IntentGatewayV2` deployments per source chain, which is supposed to gate which cross-chain messages are trusted when releasing escrowed funds (`RedeemEscrow` / `RefundEscrow`). In the Tron variant of the contract, the lookup helper silently falls back to trusting the local contract's own address for **any state machine that was never registered**, instead of rejecting it — defeating the purpose of the allowlist exactly as in the reported bug.

### Title
Unregistered-chain fallback in `IntentGatewayV2.instance()`/`authenticate()` bypasses the peer-gateway allowlist, allowing forged cross-chain escrow release — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Finding Description
`IntentGatewayV2` (and its `HyperApp` peers) settle cross-chain fills by dispatching a `RedeemEscrow`/`RefundEscrow` `PostRequest` back to the source chain. When that message arrives, `onAccept` calls `authenticate(request)` before releasing escrowed tokens: [1](#0-0) 

`authenticate()` calls the public `instance()` helper to resolve the trusted gateway address for `request.source`: [2](#0-1) 

`instance()` is defined so that an **unregistered** chain (i.e., `_instances[keccak256(stateMachineId)] == address(0)`) silently resolves to `address(this)` rather than being rejected:

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
```

This is the direct analog of the `selectedApplications` bug: the `_instances` map is the "list" that is supposed to enforce which cross-chain peers are trusted, populated only via `NewDeployment` governance messages or the deploy-time `peerChains` argument (bound to `address(this)`) — see the initializer's intent documented on the primary EVM contract: [3](#0-2) 

That comment states the intended behavior is that `_instance` should **revert** with `UnknownInstance` for any chain not explicitly registered. The Tron contract instead defaults to `address(this)`, so the allowlist check degenerates into "is `from` equal to my own address" for every chain that hasn't yet had a `NewDeployment` governance message processed for it.

Because `IntentGatewayV2` is deployed deterministically via CREATE2 (the docs explicitly note the address is "identical across chains under deterministic CREATE2"), `address(this)` is the same well-known address across every EVM/EVM-like chain the protocol targets. An attacker who can dispatch (or cause to be dispatched) an ISMP `PostRequest` whose `from` field is that same well-known address — from any chain Hyperbridge already relays consensus/state proofs for but that governance has not yet explicitly registered via `NewDeployment` for the *victim* gateway — passes `authenticate()` on the victim gateway with no real governance decision ever having whitelisted that peer.

### Impact Explanation
`authenticate()` gates `withdraw()`, which releases the escrowed input tokens (and stored fees) for a `WithdrawalRequest.commitment`/`tokens`/`beneficiary` triple supplied entirely inside the incoming request body: [4](#0-3) 

Once authentication is bypassed for any not-yet-registered chain, an attacker who can get a message with a forged/self-controlled `from` accepted from such a chain can trigger `RedeemEscrow`/`RefundEscrow` and drain escrowed tokens to an attacker-controlled beneficiary — a direct "stealing or loss of funds" / "false proof/state acceptance" / "unauthorized execution" outcome matching the bounty's required impact classes, and structurally identical to the original report's "rewards distributed to applications never enforced against the whitelist."

### Likelihood Explanation
Exploitability hinges on the attacker being able to get Hyperbridge to accept and deliver a `PostRequest` whose `source` is a chain not yet present in the victim gateway's `_instances` map and whose `from` equals the shared CREATE2 address. This is plausible in the deployment lifecycle every rollout naturally passes through (new EVM-compatible chains are frequently added to Hyperbridge's supported state machines before every existing `IntentGatewayV2` deployment has processed a corresponding `NewDeployment` governance call for that new chain), and does not require a malicious relayer, prover, or admin — only a genuine, permissionless contract deployment on the newly-connected chain at the deterministic address before/instead of the official gateway. I was not able to fully re-verify, within the available tool budget, whether `withdraw()`/`_withdraw()` cross-checks the claimed `tokens`/amounts against a previously recorded escrow amount for the commitment (this needs the body of `_withdraw` in the same file, which I did not get to read before running out of iterations) — that check, if present and if it forces `_filled[commitment]` to have already been set by a genuine `placeOrder`, would reduce the sensitivity to needing the attacker to also match a real, unfilled commitment. Given the code in front of me, I cannot rule this in or out with certainty; it should be verified directly, and I am flagging it explicitly as unconfirmed.

### Recommendation
Change `instance()`/`authenticate()` (Tron and any other divergent copies of `IntentGatewayV2`) to match the documented behavior of the primary EVM contract: revert with `UnknownInstance` (or equivalent) when `_instances[keccak256(stateMachineId)] == address(0)`, instead of defaulting to `address(this)`. Audit all copies of `IntentGatewayV2` (`evm/src`, `evm/tron`, `sdk/packages/core/contracts`) for this same fallback pattern and make the "known instance" check fail-closed rather than fail-open for any unregistered chain.

### Proof of Concept
1. Identify a state machine `X` that Hyperbridge already supports (has a live consensus client / can produce valid state proofs) but for which the victim `IntentGatewayV2` deployment on chain `V` has not yet received a `NewDeployment` governance message (i.e., `_instances[keccak256(X)] == address(0)` on `V`).
2. On chain `X`, deploy (or otherwise arrange for) a contract at the same CREATE2 address as the canonical `IntentGatewayV2` deployment, capable of dispatching an ISMP `PostRequest` with `from = address(this)`.
3. From that contract on `X`, dispatch a `PostRequest` to `V`'s `IntentGatewayV2` with body `[RequestKind.RedeemEscrow, abi.encode(WithdrawalRequest{ commitment: <arbitrary/forged>, tokens: <attacker-chosen amounts>, beneficiary: <attacker address> })]`.
4. A relayer delivers the message; Hyperbridge's proof verification is legitimate for chain `X` (since `X` is a real supported chain), so the ISMP layer accepts it as genuinely originating from `X`.
5. On `V`, `onAccept` → `authenticate(request)` computes `instance(X)`, which returns `address(this)` because `X` is unregistered; since `request.from == address(this)` (same CREATE2 address on `X`), `module == instance(source)` and authentication succeeds.
6. `withdraw()` executes, transferring the specified `tokens` to the attacker's `beneficiary` — funds are released without any real corresponding escrow settlement having been authorized by governance's peer-gateway allowlist.

     * @dev Checks that the request originates from a known instance of the IntentGateway.
     */
    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
