### Title
Diff-selection state is not remapped after hunk expansion, causing silent inclusion/exclusion of unintended lines in a commit - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The reported issue is a class of bug where two related quantities (`_referrerConfig.basisPoints` and `_clientConfig.basisPoints`) are combined without a consistency check, so a value that is individually valid becomes invalid once combined, silently breaking an invariant the rest of the code assumes holds. The Desktop analog is the coupling between the **absolute line index space** used by `DiffSelection` (`app/src/models/diff/diff-selection.ts`) and the **unified-diff index space** produced by hunk parsing/expansion (`app/src/lib/diff-parser.ts`, `app/src/ui/diff/text-diff-expansion.ts`). These two index spaces are assumed to stay in sync, but nothing enforces or re-validates that assumption when a hunk is expanded, and no check exists to keep them consistent.

### Finding Description
`DiffSelection` tracks per-line commit/discard selection purely as a `Set<number>` of raw absolute indices (`divergingLines`), with no knowledge of what hunk or diff those indices came from: [1](#0-0) [2](#0-1) 

That absolute index is computed as `hunk.unifiedDiffStart + lineIndex` when building the commit patch: [3](#0-2) 

When a user expands a hunk (loads more context via "Expand up/down"), `expandTextDiffHunk` recomputes the `unifiedDiffStart`/`unifiedDiffEnd` of *every hunk after* the expanded one, and also changes the internal line layout of the expanded hunk itself (new context lines are prepended when expanding up, or the hunk is merged with an adjacent hunk): [4](#0-3) [5](#0-4) 

This produces a brand-new set of hunks with shifted absolute indices, but the `DiffSelection` object attached to the `WorkingDirectoryFileChange` is not touched or remapped anywhere in this path — it keeps the same `divergingLines` Set computed against the *old* index layout. The only place indices are ever reconciled is `withSelectableLines`, which filters out indices no longer present, but does not shift/remap indices that are still "valid" numbers yet now correspond to a different line: [6](#0-5) 

So the broken invariant is: *"index N in `DiffSelection.divergingLines` refers to line N in the current diff hunks"* — this holds only until a hunk is expanded/merged, after which index N silently refers to a different (often adjacent, added/deleted) line, with no guard rejecting or recomputing the stale selection.

### Impact Explanation
Because `formatPatch`/`formatPatchToDiscardChanges` trust `file.selection.isSelected(absoluteIndex)` unconditionally when building the patch that is staged and committed, a stale/misaligned selection means the wrong lines can be silently committed or silently excluded from the commit — with no error, warning, or diff-review indication that the applied patch no longer matches what the user intended to select. This falls under "silent corruption of what the user commits or pushes." A crafted file (e.g., one engineered so a normal review/expand workflow shifts a security-sensitive added/removed line into a stale selected/deselected slot) served from a cloned/fetched attacker-controlled repository could cause a developer to unknowingly commit content they had explicitly excluded (or vice versa), without any UI signal of the mismatch.

### Likelihood Explanation
This requires no privileged access — it only requires an attacker-influenced repository whose file structure makes the ordinary "expand hunk" UI interaction (an entirely normal, commonly-used Desktop feature for partial commits) desirable/likely, combined with the user having already made a partial line selection before expanding. The bug is triggered purely through the standard commit-review UI flow (`side-by-side-diff.tsx` invoking `expandTextDiffHunk`), not through unusual or unnatural steps. However, I could not fully trace the entire call path from `side-by-side-diff.tsx`'s expand handlers back into `IChangesState`/selection persistence within the available context, so I cannot confirm with certainty whether some intermediate step re-derives selection from scratch (which would mitigate this) rather than reusing the stale `DiffSelection` instance. This uncertainty should be resolved by tracing `onExpandHunk`/`onDiffExpand` in `app/src/ui/diff/side-by-side-diff.tsx` through to where `WorkingDirectoryFileChange.selection` is updated after an expansion completes.

### Recommendation
- When hunks are expanded or merged (`expandTextDiffHunk`, `getTextDiffWithBottomDummyHunk`), remap the `DiffSelection`'s `divergingLines` set to the new absolute index space (e.g., by carrying an explicit line-identity, not a positional index, or by recalculating offsets alongside the hunk shift), or
- At minimum, recompute `selectableLines` and validate that stored diverging-line indices still correspond to the same line content/type before using them in `formatPatch`, aborting or resetting the selection instead of silently proceeding.
- This mirrors the report's own recommendation of adding a cross-check between two coupled values before use, rather than trusting a value that was valid in isolation but invalid once combined.

### Proof of Concept
Full exploitation requires runtime tracing I could not complete from static code inspection alone (specifically confirming whether `WorkingDirectoryFileChange.selection` is refreshed anywhere between an "Expand hunk" action and the next `formatPatch` call). Based on the static evidence:
1. Open a file with two hunks separated by collapsed context.
2. Individually deselect one "+"/"-" line inside the second hunk (adds its absolute index to `divergingLines`).
3. Click "Expand up" on the second hunk so it merges with the first (triggers `mergeDiffHunks` / index renumbering in `expandTextDiffHunk`).
4. Commit the partial selection.
5. Inspect the actual committed patch content (`git show`) versus what was visually unchecked in the UI before commit — the line excluded in the diff review may not match the line actually excluded from the produced patch, because `formatPatch` recomputed `absoluteIndex` against the new hunk layout while `divergingLines` still holds pre-expansion indices.     } else if (this.defaultSelectionType === DiffSelectionType.None) {

  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
