### Title
Attacker-controlled Participant indexing in PedPoP encryption/blame path causes panic-based denial of service — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The external report (improper finite-state handling → denial of service) maps onto Serai's PedPoP DKG encryption layer, which uses explicit panics (`assert!`, `HashMap[...]` indexing) instead of error returns when confronted with participant-indexed data it did not expect. Three sites in `crypto/dkg/pedpop/src/encryption.rs` will panic rather than return an error when the attacker-influenced participant set does not match the locally tracked `enc_keys` map:

- `Decryption::register` — `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")` (encryption.rs, lines 356–360)
- `Decryption::decrypt_with_proof` — `self.enc_keys[&decryptor]` (encryption.rs, line 388)
- `Encryption::encrypt` — `self.decryption.enc_keys[&participant]` (encryption.rs, line 466)

These functions sit directly on the path that consumes `EncryptionKeyMessage::read` / `EncryptedMessage::read` output — i.e., messages deserialized from bytes supplied by other DKG participants, who are unprivileged remote parties.

### Finding Description
`Encryption`/`Decryption` maintain `enc_keys: HashMap<Participant, C::G>`, populated by `Decryption::register` as each peer's `EncryptionKeyMessage` is processed. The indexing operations assume the caller has perfectly synchronized the registered key set with the set of participants it will later encrypt to (`encrypt`) or decrypt on behalf of (`decrypt_with_proof`):

- `register` panics on any duplicate participant registration rather than rejecting it.
- `encrypt` panics with `HashMap` index-out-of-key if asked to encrypt to a `Participant` whose `EncryptionKeyMessage` was never registered.
- `decrypt_with_proof` panics when the `decryptor` argument has no entry in `enc_keys`.

The `decryptor`/`participant` values and the registration order derive from the DKG commitment/share messages other participants broadcast — public, attacker-controlled inputs within the documented threat model (untrusted bytes fed to `EncryptedMessage::read` / `EncryptionKeyMessage::read` / `Commitments::read` and to the PedPoP `complete`-style APIs). A malicious participant who can get their commitments processed twice (e.g., by inducing a re-registration across an attempt boundary or by supplying a participant set whose keys were not registered) transitions the receiving node's encryption state machine into a state the code assumes is unreachable and converts that into a `panic!` instead of a `Result` error.

This is the direct software analog of the CVE's class: improper handling of a state transition (duplicate/missing registration in the per-participant key table) escalates to availability loss rather than a recoverable error.

### Impact Explanation
A panic in `Encryption::encrypt`, `Decryption::register`, or `Decryption::decrypt_with_proof` aborts the task/thread processing DKG messages on an honest node. In the Serai deployment these calls run inside the processor's key-generation/share-handling path, so crashing it kills the node's DKG/signing availability (denial of service), matching the Medium-severity DoS profile of the reference advisory. No secret material is leaked and no invalid signature is produced; the impact is availability only.

### Likelihood Explanation
The panics are reachable only at specific state-machine points: a duplicate `register` for the same `Participant`, an `encrypt`/`decrypt_with_proof` referencing a `Participant` absent from `enc_keys`. Whether a single malicious validator's commitment messages can force these states depends on how the callers in `crypto/dkg/pedpop/src/lib.rs` order registration vs. encryption against attacker-supplied participant sets — I was unable to fully trace those call sites (the `validate_map` pre-check may filter some paths). Within the crypto crate in isolation the panic is unconditional once the precondition is violated; the uncertainty is in the caller-level reachability, hence Medium likelihood rather than High.

### Recommendation
Replace panic semantics with error returns on this boundary:

- In `Decryption::register`, return `Err` (or idempotently ignore) on duplicate registration instead of `assert!` (encryption.rs:356–360).
- In `decrypt_with_proof` and `Encryption::encrypt`, use `enc_keys.get(&participant).ok_or(...)` and propagate an error (encryption.rs:388, 466).
- More broadly, audit the PedPoP caller in `crypto/dkg/pedpop/src/lib.rs` so that every participant-indexed lookup driven by deserialized peer messages returns `PedPoPError` rather than indexing.

### Proof of Concept
Conceptually:

```rust
// crypto/dkg/pedpop/src/encryption.rs
// Site 1: duplicate registration panic
let mut d = Decryption::<C>::new(context);
d.register(p1, msg1.clone());
d.register(p1, msg1); // assert! fires -> panic

// Site 2: blame path with unregistered decryptor
d.decrypt_with_proof::<E>(from, p_unregistered, msg, Some(proof));
// -> self.enc_keys[&p_unregistered] panics

// Site 3: encrypt to unregistered participant
enc.encrypt(&mut rng, p_unregistered, share); // enc_keys[&participant] panics
```

Each panic is triggered purely by which `Participant` indexes the peer-supplied messages reference, satisfying the "unprivileged party with public inputs" scope rule. Caveat: full end-to-end reachability depends on caller behavior in `crypto/dkg/pedpop/src/lib.rs`, which I could not completely verify within the available search iterations — the in-crate panic sites themselves are confirmed at encryption.rs lines 356–360, 388, and 466.
