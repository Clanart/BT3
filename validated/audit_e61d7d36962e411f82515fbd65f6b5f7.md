### Title
Unbounded recursive puzzle-driver matching on untrusted offer puzzle reveals enables a spend/offer-triggered resource-exhaustion crash - ([File: chia/wallet/outer_puzzles.py])

### Summary
Loading an untrusted offer file (via `Offer.from_bech32()`/`Offer.from_bytes()`) walks every `CoinSpend.puzzle_reveal` through `match_puzzle()`, which recursively descends into nested "also" puzzle layers (CAT, singleton, ownership, metadata, CR) with no depth limit and no CLVM cost accounting. A counterparty can construct a `puzzle_reveal` with an arbitrarily deep chain of curried outer-puzzle layers so that simply examining or taking the offer drives Python recursion to exhaustion, crashing the wallet process/RPC worker before any mempool/consensus cost limits are ever consulted. This mirrors the phpseclib ASN1 issue (CVE-2024-27355/GHSA-f2qx-66wf-wvvx): parsing attacker-supplied nested/length-prefixed structure with no bound on nesting depth or resource consumption (CWE-400), reachable purely from receiving untrusted data.

### Finding Description
`Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend in the untrusted bundle: [1](#0-0) 

`match_puzzle()` in turn dispatches to one of several outer-puzzle drivers (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`), each of which recognizes its own layer and then unconditionally recurses into `self._match(UnknownPuzzle(known_program=inner_puzzle))` to keep peeling off "also" layers: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

None of these `match()` implementations, nor the top-level `match_puzzle()` dispatcher, impose any bound on how many nested layers may be traversed. Each layer of nesting costs one additional Python stack frame across `match_puzzle()` → driver `.match()` → `self._match()` → `match_puzzle()` again. A `puzzle_reveal` built as CAT(CAT(CAT(...many thousands of times...(ACS)))) (or any other supported "also"-chaining outer puzzle nested deeply) will drive this call chain until Python's interpreter recursion limit is hit, raising `RecursionError`, or in CPython builds with a deep-enough limit, exhausting the C stack and crashing the interpreter outright.

Critically, this walk happens purely from `Offer.from_bytes()`/`Offer.from_bech32()` construction (invoked, e.g., by `TakeOffer.parsed_offer`, `check_offer_validity`, and the `take_offer` CLI/RPC path) — *before* any CLVM execution, cost metering, or mempool admission occurs: [6](#0-5) [7](#0-6) [8](#0-7) 

Unlike CLVM program execution (which is metered by `MAX_BLOCK_COST_CLVM` and guarded by explicit atom-length overflow checks, as verified by `test_overflow_atoms`), this pure-Python puzzle-driver recursion has no cost or depth guardrail at all: [9](#0-8) 

### Impact Explanation
Any wallet user who receives an offer file/bech32 string from an untrusted counterparty and merely examines it (`take_offer --examine-only`, `check_offer_validity` RPC, GUI offer preview) or attempts to take it triggers `Offer.from_bech32()`, which unconditionally parses every coin spend's puzzle reveal through the unbounded recursive `match_puzzle()` walk. A malicious offer can therefore crash the wallet's RPC service process (a local, unauthenticated-from-the-attacker's-perspective spend-triggered transaction-processing halt), disrupting the victim's ability to process transactions/offers until restarted. This satisfies the "spend-triggered transaction-processing halt" impact category via CWE-400 uncontrolled resource consumption, matching the underlying bug class of the phpseclib advisory.

### Likelihood Explanation
Likelihood is high: crafting a deeply nested outer-puzzle chain (e.g., stacking `CAT_MOD` curries) requires no special privileges, no valid signature, and no on-chain funds — the attacker only needs to distribute a crafted offer bech32 string/file to the victim, which is the normal offer-sharing workflow (file, chat, marketplace). The victim's wallet parses and interprets the puzzle structure immediately upon loading the offer, prior to any signature or cost checks.

### Recommendation
Add an explicit maximum recursion/nesting depth (and/or convert the recursive "also" traversal into an iterative loop with a hard cap) in `match_puzzle()` and each outer-puzzle driver's `match()`/`get_inner_puzzle()`/`construct()`/`solve()` methods in `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/*_outer_puzzle.py`, and `chia/wallet/vc_wallet/cr_outer_puzzle.py`. Reject (raise a clear `ValueError`) puzzle reveals whose outer-layer nesting exceeds a sane bound (e.g., matching the maximum number of layers any legitimate Chia asset type can produce) before recursing further, and apply the same bound when `Offer.from_spend_bundle()`/`Offer.from_bytes()` first walks untrusted coin spends.

### Proof of Concept
1. Construct a `Program` `p0 = Program.to(1)` (ACS).
2. Iteratively wrap it N times (e.g., N = 5000) using `construct_cat_puzzle(CAT_MOD, tail_hash, p_i)` to build `p_{i+1}`, producing a puzzle with N nested CAT "also" layers (see the double-nesting pattern already exercised in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py`, generalized to many layers).
3. Build a `CoinSpend` whose `puzzle_reveal` is this deeply nested puzzle and place it in a `WalletSpendBundle`.
4. Serialize via `Offer(...).to_bech32()` (or hand-construct the equivalent bytes) and pass it to `Offer.from_bech32()` (as done by `take_offer`/`check_offer_validity`/`TakeOffer.parsed_offer`).
5. Observe that `Offer.from_spend_bundle()` → `match_puzzle()` recursion raises `RecursionError` (or crashes the process) well before any CLVM execution or cost check occurs, confirming the unbounded-recursion DoS.
