## Finding

### Title
Webhook `shop_domain` Is Not Bound to the HMAC Signature, Enabling Cross-Shop Webhook Spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` (built on `ShopifyApp::PayloadVerification`) validates only the **raw request body** against the app's shared secret. The `shop_domain` value it exposes to consuming controllers is read straight from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, which is never included in the HMAC computation. This is exactly the "N-to-1 identifier aliasing" bug class described in the report: the verification step (`hmac_valid?`) proves the *body* is authentic for *some* installation of the app, but the identifier (`shop_domain`) used afterward to decide *which tenant* the data belongs to is completely decoupled from what was actually verified — any shop_domain value can be paired with any correctly-signed body.

### Finding Description
`hmac_valid?` in [1](#0-0)  computes `OpenSSL::HMAC.digest(digest, secret, data)` where `data = request.raw_post` — the header block, including `X-Shopify-Shop-Domain`, is never part of the signed input.

`WebhookVerification#verify_request` only checks this body-only HMAC before allowing the request through, and separately exposes an unauthenticated `shop_domain` accessor: [2](#0-1) .

The gem's own documentation instructs developers to build custom webhook controllers using exactly this pattern — trusting `shop_domain` for tenant dispatch immediately after HMAC verification passes: [3](#0-2) .

Because the app secret is a single, global value shared across *every* shop that has the app installed (it is not a per-shop key), a valid HMAC only proves "this body was produced by holder of the app secret for some installation" — it says nothing about which shop the payload is "for." An attacker who controls any shop with the app installed can legitimately obtain a body + valid HMAC pair from Shopify, then replay that exact pair to the same endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `hmac_valid?` still returns true because the header is not part of `data`, and the resulting job is dispatched under the attacker-chosen `shop_domain`.

This mirrors the reported bug class precisely: the verified data (body/HMAC) and the identifier used for authorization/tenant-scoping decisions (`shop_domain`) are not 1:1 bound — multiple distinct "logical requests" (different target shops) collapse onto the same accepted, verified representation, exactly as multiple distinct `bytes32` ids collapsed onto the same `address` in `_getAddressFromId`.

### Impact Explanation
Any custom webhook controller built using the documented `ShopifyApp::WebhookVerification` pattern (and any downstream job relying on the `shop_domain` value passed to it) processes attacker-controlled webhook payloads under an arbitrary victim shop's identity. Depending on what the job does with `shop_domain` (e.g. loading the shop's stored offline token via `SessionRepository.retrieve_shop_session_by_shopify_domain`, writing/deleting shop-scoped records, or triggering privileged Admin API calls), this enables cross-shop data corruption, unauthorized actions performed against a victim's store using the app's own privileges, or injection of attacker-controlled webhook content attributed to a shop the attacker does not control.

### Likelihood Explanation
High for any app author following the officially documented custom-webhook pattern. No special privilege beyond installing the app on one's own store (a normal, unprivileged onboarding action available to anyone) is required to obtain a valid signed body/HMAC pair; replaying it with a modified header requires only basic HTTP tooling.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` as an authenticated value. Either:
- Derive the shop from the verified webhook payload body itself where Shopify includes shop identification in the JSON (and cross-check it against a known, previously-authorized shop record), or
- Bind the shop domain into the HMAC computation input (as `ShopifyAPI::Webhooks::Registry.process` effectively does internally by deriving shop context safely), and update `PayloadVerification`/`WebhookVerification` and the documentation example so `shop_domain` cannot be supplied unauthenticated to job dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (unprivileged, self-service).
2. Attacker triggers any subscribed webhook topic (e.g. updates a cart/product on their own store) and captures the resulting POST that Shopify sends to the app's custom webhook endpoint: raw JSON body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC-SHA256(secret, B)`).
3. Attacker replays body `B` and header `H` unchanged to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(B)`, which succeeds because it only checks `B` against the secret — the shop-domain header is irrelevant to the check, per [1](#0-0) .
5. The documented controller pattern then executes `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` per [4](#0-3) , dispatching attacker-controlled webhook content tagged as belonging to `victim-shop.myshopify.com`.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
