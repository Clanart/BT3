### Title
Reward-multiplier double-count guard resets on unlock/withdraw, allowing repeated tier-based MGP over-claim - ([File: wombat/ArbWomUp3.sol])

### Summary
`getRewardAmount`/`calDoubledCounted` in `ArbWomUp3.sol` compute the "already rewarded" baseline by querying `mWomSV.getUserTotalLocked(_account)` live, instead of tracking a persisted cumulative-locked ledger. Because a user can independently call `mWomSV` (which exposes `startUnlock`/`unlock`/`withdraw`, per `wombat/mWomSV.sol`) to fully exit their lock outside of `ArbWomUp3`, the "counted" baseline collapses to a lower value (down to 0), letting the same tier-based bonus be claimed again on a subsequent `incentiveDeposit` call for previously already-rewarded amounts.

### Finding Description
`getRewardAmount` for `_lock == true` computes: [1](#0-0) 
where `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)`, and the "already counted" amount is subtracted via `calDoubledCounted(_account)`: [2](#0-1) 

Both `accumulated`'s second term and `calDoubledCounted` derive from the *same live call* `mWomSV.getUserTotalLocked(_account)`. This design implicitly assumes that a user's currently-locked balance in `mWomSV` only ever grows via this contract's own `_deposit` → `mWomSV.lockFor(...)` path: [3](#0-2) 

However, `mWomSV` (`wombat/mWomSV.sol`) exposes its own public unlock/withdraw flow (`startUnlock`, `unlock`, `withdraw`) that any lock owner can call directly, independent of `ArbWomUp3`. Since the user, not `ArbWomUp3`, owns the lock position in `mWomSV`, nothing prevents them from unlocking and withdrawing the entire position after receiving a reward.

Exploit flow:
1. Attacker calls `incentiveDeposit(X, ..., mode=2)`. At this point `getUserTotalLocked == 0`, so `accumulated = X`, `calDoubledCounted = 0`, and the attacker receives `mgpReward = f(X)` (doubled per `rewardToSend * 2` for mode 2) locked into `vlMGP`.
2. Attacker calls `mWomSV.startUnlock(...)` then, after cooldown, `mWomSV.unlock()`/`withdraw()` directly on `mWomSV`, fully removing their `mWom` position. `getUserTotalLocked(attacker)` now returns 0 again.
3. Attacker calls `incentiveDeposit(X, ..., mode=2)` again. Since `calDoubledCounted` re-reads the now-zero `getUserTotalLocked`, `accumulated = X` and `calDoubledCounted = 0` again — identical to step 1 — so the attacker receives the **same** tier-based reward `f(X)` a second time for locking an amount that was already rewarded once.
4. This lock → unlock → withdraw → relock cycle can be repeated indefinitely (bounded only by cooldown duration and the contract's MGP balance), each time re-earning the full tier reward for the same nominal WOM/mWom amount.

The double-counting protection is bypassed because it relies on a **live, mutable** external balance (`getUserTotalLocked`) rather than an internal monotonic ledger of "total amount ever rewarded for this account." Nothing in `incentiveDeposit`'s modifiers (`_checkAmount`, `whenNotPaused`, `nonReentrant`) prevents this, since the attacker's manipulation happens entirely outside `ArbWomUp3`, on `mWomSV` directly, between calls.

### Impact Explanation
This allows an unprivileged attacker to repeatedly drain the contract's MGP reward balance (`IERC20(mgp).balanceOf(address(this))`, capped per call by `mgpleft`) by re-claiming tier-based bonuses for the same underlying deposited WOM amount, each time locking freshly minted `vlMGP` for themselves. This is a direct theft of protocol-held reward funds (MGP) beyond what the tiered incentive schedule intends to pay out — a protocol insolvency / fund-drain issue affecting the `ArbWomUp3` reward pool.

### Likelihood Explanation
Feasibility is high: the attacker needs only (a) enough WOM to perform an initial deposit/lock, (b) ability to call `mWomSV`'s public unlock functions directly (no special privilege required, since they own their lock position), and (c) patience to wait out any cooldown period between `startUnlock` and `withdraw`. The attack is fully repeatable, limited only by cooldown duration and available MGP in the contract, and requires no flash loans, reentrancy, or governance access — it is a self-service repeatable exploit for any address holding WOM.

### Recommendation
Replace the live `mWomSV.getUserTotalLocked(_account)`-based double-count check with an internal, monotonically increasing ledger per account (e.g., `mapping(address => uint256) public totalRewardedLockAmount`) that is updated only inside `ArbWomUp3`'s own `_deposit`/`incentiveDeposit` flow and never decreases, mirroring the pattern already used correctly in `ArbWomUp.sol`/`ArbWomUp2.sol` (`userWOMDeposited` / `claimedReward`). `calDoubledCounted` and `getRewardAmount` should reference this internal ledger instead of an externally mutable balance, so that unlocking/withdrawing from `mWomSV` outside this contract cannot reset the reward baseline.

### Proof of Concept
Foundry test outline:
1. Deploy `ArbWomUp3`, `mWomSV`, `vlMGP`, `mWom`, and mock `WOM`/`MGP` tokens; fund `ArbWomUp3` with MGP; set `rewardTier`/`rewardMultiplier` via `setMultiplier`.
2. As attacker: call `incentiveDeposit(X, ratio, false, 2)`; record MGP locked into `vlMGP` for attacker (`claim1`).
3. As attacker: call `mWomSV.startUnlock(...)` for the full locked `mWom` amount from step 2; advance time past cooldown; call `mWomSV.unlock()`/`withdraw()` to fully exit the position; assert `mWomSV.getUserTotalLocked(attacker) == 0`.
4. As attacker: call `incentiveDeposit(X, ratio, false, 2)` again with the same `X`; record MGP locked (`claim2`).
5. Assert `claim2 == claim1` (or `claim1 + claim2` exceeds the reward a single continuous lock of `2X` would have yielded via one `incentiveDeposit(2X, ...)` call), demonstrating that cycling lock/unlock/relock lets the attacker double-claim the tier bonus instead of only receiving the marginal reward for the incremental `X` on top of an already-tiered `X`.
6. Repeat steps 2–4 in a loop `n` times and assert cumulative claimed MGP grows linearly with `n` for a fixed underlying `X`, confirming unbounded repeatable over-claim versus the intended one-time tiered payout.
