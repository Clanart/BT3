## Finding: Shared `BalanceHandler` state causes EVM/bank balance desynchronization on nested precompile calls

### Title
Shared BalanceHandler instance in recursive/nested precompile calls corrupts EVM StateDB balance accounting — (File: `precompiles/common/balance_handler.go`, `testutil/testdata/debug/debug.go`)

### Summary
The reported bug pattern is a *stale/shared mutable bookkeeping cursor that is overwritten before it is consumed*, letting state that should have been isolated leak or vanish. In `LocalCache`, `sets_since_last_gc`/`expire_at` bookkeeping was shared across calls without re-validation. In this codebase, the analogous invariant lives in `precompiles/common/balance_handler.go`: `BalanceHandler.prevEventsLen` is a mutable cursor into `ctx.EventManager().Events()` that is written in `BeforeBalanceChange` and consumed in `AfterBalanceChange`. When the *same* `BalanceHandler` instance is reused/shared across nested or recursive precompile invocations within a single EVM call (as happens through the `debug` precompile's `p.GetBalanceHandler()` pattern, in contrast to `precompiles/common/precompile.go`'s `runNativeAction`, which correctly allocates a *fresh* handler per call via `p.BalanceHandlerFactory.NewBalanceHandler()`), an inner call's `BeforeBalanceChange` overwrites `prevEventsLen` before the outer call's `AfterBalanceChange` runs.

### Finding Description
`BalanceHandler` is the bridge that keeps the EVM `StateDB` balance view in sync with actual `x/bank` (and `x/precisebank`) balance changes performed by a precompile's native action: [1](#0-0) 

`BeforeBalanceChange` records `bh.prevEventsLen = len(ctx.EventManager().Events())`, and `AfterBalanceChange` later replays only the events emitted after that recorded index (`events[bh.prevEventsLen:]`) into `stateDB.AddBalance`/`SubBalance`: [2](#0-1) 

The correct/safe pattern is demonstrated in `precompiles/common/precompile.go`, where a brand-new `BalanceHandler` is created for every precompile invocation: [3](#0-2) 

However, other precompile entry points (such as the debug precompile) call a shared handler obtained via `p.GetBalanceHandler()` instead of creating a new one per call: [4](#0-3) 

If a contract triggers a nested/recursive precompile call before the outer call's `AfterBalanceChange` executes (e.g., an EVM call into the precompile that itself calls back into a contract which re-enters the same precompile — the callback/EVM-call flow inside `Run` demonstrates exactly this shape, since `CallEVM`/contract execution happens between the balance snapshot and the balance replay), the inner call's `BeforeBalanceChange` overwrites the shared `prevEventsLen` with a *later* index. When the outer call's `AfterBalanceChange` subsequently runs, it uses the now-advanced `prevEventsLen`, silently skipping the bank events that belong to the outer call. This is confirmed as an actual, reproduced bug by the project's own regression test: [5](#0-4) [6](#0-5) 

The result is exactly the "resurrection/desync" class from the source report: the `x/bank` keeper (source of truth) applies a coin transfer, but the EVM `StateDB` — which is what subsequent opcodes/precompile calls and the final `Commit()` use to persist balances — never gets the corresponding `AddBalance`/`SubBalance` call (or gets it applied against the wrong event window), producing a balance value in EVM state that diverges from the actual spendable bank balance.

### Impact Explanation
This breaks the "Asset-representation path" invariant required to hold 1:1 between native coins and EVM-visible balances. Because `StateDB.Commit()` writes `obj.account` (including `Balance`) back to the keeper via `SetAccount`, a stateDB balance that has drifted from the real bank balance due to skipped/duplicated event processing can be committed as authoritative, i.e., the corrupted number becomes the new persisted account balance. Depending on which direction the drift goes, this can (a) allow the EVM view of a user's balance to reflect coins that were never actually credited to them by the bank keeper (spendable-value duplication), or (b) leave a legitimate bank-side credit invisible to the EVM balance forever (fund freezing). Both map directly to the Critical impact gate: "unauthorized... duplication... of spendable user value across native balances, EVM balances" and "permanent freezing... of user funds."

### Likelihood Explanation
This is triggerable by any unprivileged EVM user: it only requires deploying/calling a contract that causes a precompile which uses the shared-handler pattern (e.g. via a callback contract as demonstrated by the project's own `TestRecursivePrecompileCallsWithDebugPrecompile` test) to be invoked recursively within a single transaction. The bug is already confirmed to reproduce in the project's test suite, which materially raises confidence and lowers the bar for exploitation; the only open question is which production (non-test/non-debug) precompiles use the shared-`GetBalanceHandler()` pattern versus the safe per-call `BalanceHandlerFactory.NewBalanceHandler()` pattern used in `precompile.go`. I was not able to fully enumerate every production precompile's wiring in the time available — this should be verified with a full Devin session that has file-system access to grep all `GetBalanceHandler` implementations/usages and confirm whether any non-test precompile registered in production chains shares handler state across nested calls.

### Recommendation
- Ensure every precompile entry point allocates a fresh `BalanceHandler` per top-level EVM call (or per re-entrant call) rather than sharing/caching one on the `Precompile` struct, mirroring the safe pattern already used in `precompiles/common/precompile.go`'s `runNativeAction`.
- Make `BalanceHandler.prevEventsLen` re-entrancy safe, e.g. by using a stack of cursors (push on `BeforeBalanceChange`, pop on `AfterBalanceChange`) instead of a single mutable field, so nested calls cannot clobber an outer call's bookmark.
- Add an invariant check post-commit comparing the sum of EVM `StateDB` balances touched in a tx against the net bank balance deltas recorded in emitted events, and reject/panic the transaction if they diverge.

### Proof of Concept
The project's own integration test demonstrates the mechanism end-to-end: it registers the debug precompile, deploys a caller contract that invokes the precompile recursively (`callback`), and documents that this causes `prevEventsLen` to be overwritten, producing "balance desync between native bank keeper and EVM stateDB": [7](#0-6)

// BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())

	// Pack the input for callback(0)
