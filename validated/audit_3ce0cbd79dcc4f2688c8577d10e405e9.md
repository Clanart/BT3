### Title
Unauthenticated panic in PedPoP blame evaluation via unregistered Participant indexes - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys` with the caller-supplied `decryptor` participant index using `HashMap`'s `Index` operator, which panics on a missing key. `BlameMachine::blame_internal` / `AdditionalBlameMachine::blame` accept arbitrary `sender`/`recipient` `Participant` values from an untrusted blame statement, so an unauthenticated party can crash the host process with a crafted blame claim — a direct analog of CVE-2020-20813 (remote denial of service via a crafted control-channel packet).

### Finding Description
`Decryption::register` only inserts into `enc_keys` for participants whose `EncryptionKeyMessage` was actually processed (participants `1..=n` in `AdditionalBlameMachine::new`, or the registered peers inside `SecretShareMachine::verify_r1`). However, `decrypt_with_proof` indexes the map unconditionally when evaluating a proof:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
if let Some(proof) = proof {
  proof
    .dleq
    .verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],
    )
```

`self.enc_keys[&decryptor]` panics when `decryptor` is absent. The `decryptor` argument is the `recipient` parameter of `blame_internal`, which is supplied by the caller alongside an attacker-constructed `EncryptedMessage` and `EncryptionKeyProof`:

```rust
// crypto/dkg/pedpop/src/lib.rs:575-588
fn blame_internal(&self, sender, recipient, msg, proof) -> Participant {
  let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) { ... }
```

`AdditionalBlameMachine::new` explicitly documents that it "creates a machine capable of evaluating blame regardless of if the caller was a member in the DKG protocol," so blame evaluation is intended to be driven by externally supplied accusations — i.e., untrusted inputs. A `Participant` value beyond `n`, or any index whose key-registration message was dropped, is never range-checked before reaching the `HashMap` index.

A secondary panic of the same shape exists at `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599): if the attacker crafts a valid `EncryptedMessage` (they control `key`, `pop`, and the ciphertext, and can compute the `cipher` keystream from their own `proof.key`), a canonical decrypted share reaches `share_verification_statements` with `self.commitments[&sender]`, panicking when `sender` was never registered.

Both panic sites are reachable purely from bytes the attacker feeds to `EncryptedMessage::read` / `EncryptionKeyProof::read` plus the `sender`/`recipient` fields of a blame request, matching the CVE's model of a crafted packet crashing a remote peer.

### Impact Explanation
Any node evaluating a blame statement panics and aborts. In a DKG/blame-arbitration context this lets a single unauthenticated message permanently kill the process adjudicating faults, preventing completion of key generation and enabling an attacker to selectively DoS honest validators' blame processing. Under Rust's default panic behavior this is a full process abort (DoS, availability impact — matching the CVE's A:H rating).

### Likelihood Explanation
The attacker needs only to submit a blame tuple `(sender, recipient, msg, Some(proof))` where `recipient` is a `Participant` index not present in `enc_keys` (e.g., `Participant(n + 1)` or any index filtered out earlier). No valid proof is needed — the `HashMap` index is evaluated as an argument to `dleq.verify` before verification occurs, so the panic fires regardless of proof validity. `Participant` is a `u16` newtype with no upper bound tied to the set size at this layer, so arbitrary indexes are expressible.

### Recommendation
Replace map indexing with fallible lookups in `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal`:
- `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`
- `self.commitments.get(&sender)` returning `sender` (or a distinct fault) when absent.
- Optionally bound `sender`/`recipient` to `1..=params.n()` before any lookup, since blame about non-members is meaningless.

### Proof of Concept
```rust

let n = 3u16;
```
