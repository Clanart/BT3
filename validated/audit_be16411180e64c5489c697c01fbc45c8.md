### Title
Silent remote-URL repointing to attacker-controlled host via unverified GitHub API `clone_url` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's `origin` remote URL using the `clone_url` field returned by the GitHub/GHES API, but it never verifies that the new URL's **hostname** matches the trusted endpoint. It only compares protocol scheme, leaving the door open for the "critical variable changed without a permanence/consistency guard" class of bug (analogous to the Solidity report's mutable Dutch-auction parameters) applied to a security-critical value: the git remote that receives the user's future pushes.

### Finding Description
`updateRemoteUrl` decides whether to silently call `gitStore.setRemoteURL` based on three checks: `protocolsMatch`, `remoteUrlUnchanged`, and `!urlsMatch` [4](#0-3) . `protocolsMatch` only compares the URL scheme (`http:`/`https:`/etc.), not the hostname [5](#0-4) . `urlMatchesRemote`, used to compute `urlsMatch`, correctly checks hostname/owner/name equality between the *new* URL and the *current* remote [6](#0-5) , but that check is only used to detect that a change occurred (i.e., `!urlsMatch` must be true to trigger the update) — a mismatched hostname on the incoming API value doesn't block the update, it's exactly the condition that satisfies "the URL changed" and lets the rewrite proceed.

The `apiRepo` fed into this function comes from `api.fetchRepository(owner, name)` against the account's configured endpoint [7](#0-6) . If that endpoint's response can be attacker-influenced (a compromised or malicious GitHub Enterprise Server, a network/TLS-terminating proxy in front of it, or any other way the JSON body is not exactly what GitHub.com would return), the attacker fully controls `clone_url`, including its hostname. No existing guard in `updateRemoteUrl` rejects a new hostname that differs from the currently configured trusted remote's hostname — the code only preserves consistency of *protocol*, not of *host*.

### Impact Explanation
If exploited, `gitStore.setRemoteURL` is invoked, performing `git remote set-url origin <attacker-url>` on disk without any user prompt, confirmation dialog, or visible warning [8](#0-7) . Subsequent `git push` operations from GitHub Desktop's UI would silently transmit the user's commits (and potentially credentials via the trampoline credential helper, which resolves credentials by endpoint host [9](#0-8) ) to the attacker-controlled remote instead of the legitimate one. This is a silent corruption of where the user's commits go — matching the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact categories.

### Likelihood Explanation
This requires an attacker-controlled GitHub API response — realistic on GitHub Enterprise Server deployments with compromised/malicious servers, or on networks where the GHES certificate/host can be interposed (a documented threat model for GHES/proxy environments). It does not require local access, admin rights, prior malware, leaked credentials, or unnatural user steps: the check runs automatically on ordinary fetch/pull/push/repository-selection actions [10](#0-9) .

### Recommendation
In `updateRemoteUrl`, require that the new `clone_url`'s hostname match the hostname of `gitHubRepository.endpoint` (or the current remote's hostname) before allowing an automatic rewrite; if hostnames differ, either reject the update or route it through an explicit user-confirmation dialog (similar to the pattern intended by "shouldn't be changed after they're set" — the remote host, once trusted, should not be silently swapped).

### Proof of Concept
1. User has `origin` pointed at `https://ghes.company.com/org/repo.git`, associated `GitHubRepository.cloneURL` matching.
2. A compromised/malicious GHES instance (or a MITM in front of it) responds to `GET /repos/org/repo` with `clone_url: "https://attacker.example.com/org/repo.git"` (same protocol, different host).
3. On the next fetch/pull/push or repository selection, `repositoryWithRefreshedGitHubRepository` fetches this API object and calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [1](#0-0) .
4. `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true (remote wasn't manually edited), `urlsMatch` is false (hostname differs) → condition `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is satisfied [11](#0-10) .
5. `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')` executes silently, rewriting `origin` with no user notification.
6. The next push from Desktop's UI goes to `attacker.example.com`.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
