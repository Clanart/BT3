### Title
Divergent conflict-marker parsers let a crafted merge conflict leave live `<<<<<<<`/`=======`/`>>>>>>>` markers in a file that Copilot conflict resolution reports as fully resolved - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted merge-conflict resolution feature uses two independently written parsers over the same untrusted conflict-marker text: `extractConflictHunks` (in `app/src/lib/copilot-conflict-context.ts`) builds the hunk list sent to Copilot, while `reassembleResolvedFile` (in `app/src/lib/copilot-conflict-resolution.ts`) splices Copilot's per-hunk answers back into the original file. The two parsers disagree on what counts as a well-formed hunk when a `>>>>>>>`-shaped line appears before the real `=======` separator. This lets an attacker who controls one side of a merge (a cloned/fetched branch) craft a conflict that Copilot resolves "successfully" (hunk counts match, validation passes) while `reassembleResolvedFile` silently treats the block as unparseable and copies the raw, still-conflicted text — including live git conflict markers — straight through to the file that gets written to disk and `git add`ed.

### Finding Description
`extractConflictHunks` [1](#0-0)  collects "ours" content by scanning forward only for a base marker (`|||||||`) or the separator (`=======`) — it never checks for a `>>>>>>>`-shaped line while inside the ours section, so such a line is simply absorbed as literal ours content.

`reassembleResolvedFile`, however, independently re-parses the same raw file to decide where to splice Copilot's answer back in [2](#0-1) . Its lookahead loop breaks out as soon as it sees a line matching `^>{7}(?:\s|$)`, regardless of whether a `=======` separator was already seen: [3](#0-2) 

If a line that looks like a closing marker (`>>>>>>> ...`) appears inside the "ours" region *before* the genuine separator, `extractConflictHunks` still counts this as exactly one valid hunk (so the model is asked to resolve it and returns exactly one `resolvedContent`, satisfying `validateResolutionPaths`'s hunk-count check at `app/src/lib/copilot-conflict-resolution.ts:509-520`). But `reassembleResolvedFile` finds `hasSeparator === false` at the point it hits that embedded `>>>>>>>`-line, classifies the whole hunk as "malformed", and falls into the "copy through unchanged" branch: [4](#0-3) 

Because the main walking loop only re-triggers hunk detection on a `<<<<<<<`-line, the subsequent genuine `=======` and `>>>>>>>` lines from the *real* end of that hunk are then copied through as ordinary text in the `else` branch of the loop [5](#0-4) . The result: the "resolved" file still contains live git conflict markers, but the app has already validated the resolution as complete.

This reassembled, still-broken content is written directly to disk with no marker re-check and staged: [6](#0-5) 

The only marker check anywhere in the pipeline is on the *model's own* `resolvedContent` string inside `parseCopilotConflictResolution` [7](#0-6) , which cannot catch corruption introduced later by the reassembly step operating on the original file content, not the model's output.

### Impact Explanation
A malicious branch/fork author can craft a file so that merging/rebasing/cherry-picking it against a victim's branch produces a conflict block containing a spurious `>>>>>>>`-shaped line inside the "ours" hunk region. If the victim uses Desktop's "Resolve with Copilot" feature and clicks "Continue Merge", the corrupted invariant ("hunk boundaries agreed upon by context-extraction and reassembly") is broken: Desktop reports the file as fully AI-resolved, writes it to disk with live conflict markers still embedded, and stages it with `git add`. This is a silent corruption of what the user commits/pushes — the committed file is not what the user believes was resolved, and depending on language, may break builds, hide malicious payloads inside what looks like conflict scaffolding, or ship syntactically-broken/security-relevant code without the developer noticing since the UI presented it as a clean, reviewed resolution.

### Likelihood Explanation
Exploitation only requires the attacker to control content on one side of an ordinary merge (a fetched/cloned branch or PR) — no special access to the victim's machine, no social engineering beyond a normal branch merge, and it triggers on Desktop's advertised AI conflict-resolution workflow. The crafted trigger is a single line starting with exactly seven `>` characters, which is plausible to embed in code, test fixtures, or generated diff-like content without looking obviously malicious. The main uncertainty is confirming the AI model's behavior is deterministic enough in practice (Copilot must actually return a plausible single-hunk resolution for the crafted block, which is likely given the hunk look s well formed to the context extractor) — this is a model-output-dependent, not certain, step.

### Recommendation
Make `reassembleResolvedFile` use the exact same hunk-boundary algorithm as `extractConflictHunks` (ideally refactor to share one parser), so both agree on what constitutes ours/base/separator/theirs boundaries, including not treating an embedded `>>>>>>>`-shaped line found before a genuine `=======` as a premature closing marker. Additionally, after reassembly and before `writeFile`/`git add` in `_applyCopilotConflictResolutions`, re-scan the final `resolvedContent` for residual conflict-marker lines (`^<{7}`, `^={7}$`, `^>{7}`) and refuse to write/stage (or force manual resolution) if any are found — mirroring the check already applied to the model's raw hunk output.

### Proof of Concept
```
line before
<<<<<<< HEAD
some_call(">>>>>>> not-a-real-marker")
=======
their change
>>>>>>> feature
line after
```
- `extractConflictHunks` parses this as ONE hunk: `oursContent = 'some_call(">>>>>>> not-a-real-marker")'`, `theirsContent = 'their change'` — sent to Copilot, which returns exactly one `resolvedContent`, satisfying `validateResolutionPaths`.
- `reassembleResolvedFile(raw, [{ resolvedContent: 'merged result' }])`: on the ours-marker line it scans forward, hits `some_call(">>>>>>> not-a-real-marker")` which matches `reassemblyTheirsMarker` before any `=======` is seen, sets `closingIndex` with `hasSeparator === false`, and takes the "malformed — copy through" branch. The subsequent real `=======`, `'their change'`, and `>>>>>>> feature` lines are then copied verbatim by the outer loop's `else` branch.
- Final written/staged file:
```
line before
<<<<<<< HEAD
some_call(">>>>>>> not-a-real-marker")
=======
their change
>>>>>>> feature
line after
```
despite the UI reporting the file as "resolved by Copilot" and staging it via `git add`.
