### Title
Pointer precompile bypasses governance `RegisterPointerDisabled` kill-switch, allowing CW↔EVM pointer creation after it has been disabled - ([File: precompiles/pointer/pointer.go])

### Summary
The `x/evm` module exposes a governance-controlled parameter, `RegisterPointerDisabled`, intended to globally disable the creation of new CW20/CW721/CW1155↔ERC pointer contracts. The Cosmos message handler `RegisterPointer` in `x/evm/keeper/msg_server.go` correctly checks this flag and rejects the request when it is set. However, the equivalent functionality reachable through the EVM precompile at address `0x100b` (`precompiles/pointer/pointer.go`, methods `AddNative`, `AddCW20`, `AddCW721`, `AddCW1155`) never calls `GetRegisterPointerDisabled` and unconditionally proceeds to call `UpsertERCNativePointer` / `UpsertERCCW20Pointer` / `UpsertERCCW721Pointer` / `UpsertERCCW1155Pointer`. This is directly analogous to the Mattermost CVE-2024-5270 class of bug: a security-relevant configuration switch is enforced on one interface (SAML vs. email switch endpoint) but not on a functionally equivalent alternate interface (a different code path providing the same capability).

### Finding Description
- `x/evm/keeper/msg_server.go`'s `RegisterPointer` explicitly gates pointer creation on the config flag: [1](#0-0) 
- `x/evm/keeper/params.go` defines the accessor for this governance parameter, which operators/governance can flip to `true` (and `x/evm/migrations/disable_register_pointer.go` shows it is explicitly set via a chain upgrade migration, confirming it is meant to be a hard, chain-wide disable): [2](#0-1) [3](#0-2) 
- The EVM precompile version of the same capability — reachable by any EVM contract or EOA via a normal `eth_sendRawTransaction`/`eth_call` to `0x000000000000000000000000000000000000100b` — performs no such check: [4](#0-3) [5](#0-4) 
- A grep across the entire `precompiles/` tree confirms `RegisterPointerDisabled`/`GetRegisterPointerDisabled` is never referenced there, and the pointer-creation keeper functions (`UpsertERCCW20Pointer`, etc., in `x/evm/keeper/pointer_upgrade.go`) also do not enforce it — the check exists solely in the Cosmos message-server path.

### Impact Explanation
Once operators/governance disable pointer registration (e.g., because a pointer contract template has a known bug, or to freeze cross-VM asset bridging for security/compliance reasons), any unprivileged EVM caller can still invoke the pointer precompile to create new CW20/CW721/CW1155↔ERC pointer contracts, completely undermining the intended chain-wide freeze. Since pointers mediate token transfers/balances between the Cosmos and EVM execution environments, continuing to allow pointer creation when this was deliberately disabled can lead to unauthorized bridging of otherwise-frozen asset classes and inconsistent/duplicate pointer state, which the disable flag was meant to prevent.

### Likelihood Explanation
High reachability: no privileges are required, and the call is a single EVM transaction to a well-known precompile address — the same action any dApp or user is already permitted to invoke through the primary interface. The only precondition is that governance has set `RegisterPointerDisabled=true` (a state that must be assumed reachable, since a migration to set it exists in-repo).

### Recommendation
Add the same `p.evmKeeper.GetRegisterPointerDisabled(ctx)` check at the top of `AddNative`, `AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go` (and any legacy precompile versions still active for replay/backwards compatibility), mirroring the check already present in `x/evm/keeper/msg_server.go`'s `RegisterPointer`, so the kill-switch is enforced uniformly across both the Cosmos message path and the EVM precompile path.

### Proof of Concept
1. Governance/chain upgrade sets `RegisterPointerDisabled = true` via `x/evm/keeper/params.go`'s `SetParams` (as done by `MigrateDisableRegisterPointer`).
2. Confirm the intended block: submitting `MsgRegisterPointer` via `x/evm/keeper/msg_server.go` now fails with `"registering CW->ERC pointers has been disabled"`.
3. From any EVM account, send a transaction calling `addCW20Pointer(cwAddress)` (or `addNativePointer`, `addCW721Pointer`, `addCW1155Pointer`) on precompile `0x000000000000000000000000000000000000100b`.
4. Observe the call succeeds and a new ERC20 pointer contract is deployed/registered via `UpsertERCCW20Pointer`, despite `RegisterPointerDisabled` being `true` — demonstrating the bypass.

func (k *Keeper) GetRegisterPointerDisabled(ctx sdk.Context) bool {
	if !ctx.IsTracing() {
		return k.GetParams(ctx).RegisterPointerDisabled
	}
	switch {
	case semver.Compare(ctx.ClosestUpgradeName(), "v6.0.6") < 0:
		// Not present in pre-5.8.0 params; use default
		return types.DefaultRegisterPointerDisabled
	default:
		return k.GetParams(ctx).RegisterPointerDisabled
	}
}

func (p PrecompileExecutor) AddCW20(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	cwAddr := args[0].(string)
	cwAddress, err := sdk.AccAddressFromBech32(cwAddr)
	if err != nil {
		return nil, 0, err
	}
	res, err := p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))
	if err != nil {
		return nil, 0, err
	}
	formattedRes := map[string]interface{}{}
	if err := json.Unmarshal(res, &formattedRes); err != nil {
		return nil, 0, err
	}
	name := formattedRes["name"].(string)
	symbol := formattedRes["symbol"].(string)
	contractAddr, err := p.evmKeeper.UpsertERCCW20Pointer(ctx, evm, cwAddr, utils.ERCMetadata{Name: name, Symbol: symbol})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
