### Title
`on_accept` panics on a malformed EVM sender length in unsigned cross-chain calldata execution - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in the `hyper-fungible-token` pallet decodes an ISMP `PostRequest` body into a `Message` struct and, when optional calldata is attached without a signature, derives the substrate "acting origin" from the EVM sender bytes with an unchecked slice operation `from_bytes[from_bytes.len() - 20..]`. Every other place in the same function (and in the sibling `on_timeout` handler) that converts an attacker-supplied byte vector into a fixed-size account first checks the length is exactly 20 or 32 bytes and returns a typed error otherwise. This one branch is missing that check, so a `from` field shorter than 20 bytes triggers a `usize` subtraction underflow followed by a guaranteed out-of-bounds slice panic — the same "unchecked invariant from untrusted external data → panic" bug class described in the seed report, just relocated from `SystemStateChanges::apply_changes` to the ISMP module callback that executes cross-chain calldata.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, `on_accept` decodes the incoming request body: [1](#0-0) 

Note the explicit length validation used for `message.to` — 32 or 20 bytes, else `HftError::InvalidRecipientLength`. The same discipline is applied later for the *signed* refund/timeout path in `on_timeout`: [2](#0-1) 

However, in the *unsigned* optional-calldata branch of `on_accept` — reached when `message.data` is non-empty and `substrate_data.signature` is `None` — the sender origin is derived without any length check: [3](#0-2) 

`from_bytes.len() - 20` is a `usize` subtraction on a length that is fully attacker-influenced by the abi-decoded `Message.from` field carried inside the request body. If `from_bytes.len() < 20`, the subtraction underflows. This either panics immediately on overflow (Substrate runtimes are typically built with overflow checks enabled) or, even without overflow checks, wraps to a huge index and the subsequent slice `from_bytes[huge_index..]` panics on out-of-bounds indexing — there is no path that returns cleanly. This mirrors the report's core broken invariant exactly: a hand-rolled precondition on untrusted, remotely-supplied data is enforced with `assert`/`expect`-equivalent unchecked operations instead of a validated `Result`, and a single malformed message reaches this code from an ordinary, unprivileged, public message-delivery entrypoint (`IsmpModule::on_accept`, invoked from the standard incoming-message handler once ISMP proof verification succeeds).

### Impact Explanation
A panic inside `on_accept` during the ISMP incoming-message dispatch aborts execution of that extrinsic/block-import path in the runtime — the same "malicious payload → replica/runtime panic" impact class as the seed report, here landing in a production pallet callback reachable by any relayer delivering an ISMP message from a registered source/`from` pair rather than in a sandboxed VM. Because the trigger is a single malformed field inside message content (not a cryptographic forgery), it can be produced cheaply once any message from the registered source contract/module can carry attacker-influenced bytes in this field, and it doesn't require a malicious relayer, prover, or governance actor — only a relayer delivering an otherwise validly-proven message whose body content is malformed.

### Likelihood Explanation
This code path executes whenever a `PostRequest` targets `hyper-fungible-token`, carries non-empty `data`, and the embedded `SubstrateCalldata.signature` is `None` (the "convert from EVM sender" fallback, intended for messages sent directly by the EVM sender rather than pre-signed for a chosen substrate account). All the length-guarding logic present elsewhere in this exact file demonstrates the developers were already aware this exact class of length mismatch is possible and dangerous (see the very deliberate checks at lines 63-71 and 224-233) — this one branch was simply missed. I could not fully verify from the available index whether the paired Solidity dispatch contract (`HyperFungibleToken.sol` / `WrappedHyperFungibleToken.sol`) constrains `Message.from` to always be exactly 20 bytes (e.g., always set to `msg.sender`) before ISMP dispatch, which would gate how easily an attacker can produce a short `from`; I was not able to retrieve and read that Solidity `Message` encoding logic before the session ended, so this should be confirmed against the EVM-side dispatch function before treating this as fully exploitable end-to-end.

### Recommendation
Add the same length validation used elsewhere in this file before the `from_bytes.len() - 20` slice:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    if from_bytes.len() < 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    let mut account = [0u8; 32];
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    account.copy_from_slice(from_bytes);
    account.into()
}
```
More broadly, audit every `IsmpModule::on_accept`/`on_timeout`/`on_response` implementation across the pallets for slice/array conversions performed directly on ABI-decoded, cross-chain-sourced byte fields, since this file shows the pattern was fixed inconsistently within a single function.

### Proof of Concept
1. Deploy/observe a `hyper-fungible-token` pallet instance with a registered `(source, from)` → `local_asset_id` mapping in `ContractToAsset`, and a valid `Precisions` entry for that asset/source (both required to reach the vulnerable branch, and both are legitimate governance-set config, not attacker-controlled).
2. Craft (or have a compliant/compromised sender construct) a `PostRequest` whose ABI-encoded body decodes to a `Message` where:
   - `message.to` is a valid 20 or 32-byte recipient (passes the first length check),
   - `message.amount` is any valid value,
   - `message.data` is non-empty and decodes to a `SubstrateCalldata` with `signature: None` and any well-formed `runtime_call`,
   - `message.from` is fewer than 20 bytes (e.g., empty or 5 bytes).
3. Deliver this request through the normal ISMP relayer path with a valid consensus/state proof for `source`/`from` (no proof forgery needed — proof only attests the request/body bytes were dispatched, not their internal field shapes).
4. When `pallet_ismp` routes the request to `HyperFungibleToken::on_accept`, execution reaches the `source.is_evm()` unsigned branch, computes `from_bytes.len() - 20` on a length `< 20`, and panics on the underflow or the subsequent out-of-bounds slice — aborting the extrinsic/block-processing rather than returning `Err(HftError::...)`.
