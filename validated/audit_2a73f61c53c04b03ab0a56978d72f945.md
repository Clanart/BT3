## Analysis

The report's broken invariant is: **an admin-initiated state transition can be blocked by an attacker-controlled "pending" counter that a check treats as authoritative but which any unprivileged party can inflate.** The Agave analog is not literal mempool front-running of a peer's transaction, but a structurally identical unprivileged-griefing path in the vote program's `Withdraw`/`DepositDelegatorRewards` instructions (SIMD-0123).

`withdraw()` blocks a full vote-account close whenever `pending_delegator_rewards > 0`: [1](#0-0) 

That field can be incremented by *anyone*, not just the vote account's own delegators/authorities: `deposit_delegator_rewards` only requires that the `source_address` (the depositor) sign for its own funds — there is no check that the depositor is a delegator to that vote account, no minimum-deposit floor, and it operates on any V4 vote account the caller names: [2](#0-1) 

The instruction is permissionless as long as the required features are enabled and the vote account is V4: [3](#0-2) 

The partial-withdraw path also reserves `pending_delegator_rewards` out of the withdrawable balance, so even non-close withdrawals are throttled by this attacker-controllable value: [4](#0-3) 

Tests confirm the exact blocking behavior for both partial and full withdrawal once `pending_delegator_rewards > 0`: [5](#0-4) [6](#0-5) 

I was not able to fully verify from the available index whether/how `pending_delegator_rewards` is ever decremented outside of a full-balance `Withdraw` (e.g., whether epoch-boundary reward distribution in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` reduces it, or whether it is only ever paid out via `Withdraw` itself, which is the exact function being blocked). This is a meaningful gap in my analysis: if the runtime periodically drains `pending_delegator_rewards` to delegators automatically, the griefing window would be bounded to at most one epoch and the severity would be lower than described below.

### Title
Unprivileged `DepositDelegatorRewards` deposits let anyone permanently block a vote account's withdrawer from closing/fully withdrawing the account - (File: programs/vote/src/vote_state/mod.rs)

### Summary
`VoteInstruction::DepositDelegatorRewards` lets any signer transfer lamports into an arbitrary V4 vote account and bump its `pending_delegator_rewards` counter, with no relationship check between the depositor and the vote account. The `withdraw()` function treats `pending_delegator_rewards > 0` as a hard block on fully closing the vote account (and as a reserve subtracted from what's withdrawable). This mirrors the reported `AuthorizationModule` bug: a state-mutating, admin/owner-gated operation (`deauthorizeAccount` / vote-account close) is silently vetoed by a "pending" value that an unrelated, unprivileged party can set at will.

### Finding Description
`deposit_delegator_rewards` requires only that the caller sign for their own `source_address`; it performs a plain System Program transfer of `deposit` lamports (which can be as small as 1) into the named vote account and then calls `add_pending_delegator_rewards(deposit)`: [7](#0-6) 

Nothing ties this to the vote account's actual delegators, its authorized voter, or its withdrawer. The vote account owner has no way to reject or "opt out" of these deposits — the transfer executes unconditionally as part of the instruction.

Later, `withdraw()` uses `pending_delegator_rewards` as an authoritative gate:
- Full close is rejected outright if `pending_delegator_rewards > 0`.
- Partial withdrawals must leave `min_rent_exempt_balance + pending_delegator_rewards` in the account. [8](#0-7) 

The corrupted/controlling value is `VoteStateV4::pending_delegator_rewards`, which is externally, permissionlessly writable (upward) via `DepositDelegatorRewards`, yet is relied upon by `withdraw()` — the only privileged, authorized-withdrawer-gated instruction — to decide whether the account may be closed or how much may be withdrawn. This is the same class of flaw as the Trail-of-Bits finding: a legitimate admin/owner action is conditioned on state that an unrelated unprivileged actor can manipulate, defeating the intended access-control outcome without ever compromising a key.

### Impact Explanation
An attacker who wants to prevent a validator's withdraw authority from closing (or fully draining) a vote account can send a `DepositDelegatorRewards` instruction with `deposit = 1` (or any nonzero amount) targeting that vote account. This sets `pending_delegator_rewards` to a nonzero value, which:
1. Permanently blocks `Withdraw(lamports)` calls that would zero out the account (`InstructionError::InsufficientFunds`), and
2. Reduces the amount withdrawable in partial withdrawals by reserving the deposited amount.

This is a denial-of-service against the legitimate withdraw authority's control over their own vote account — an unprivileged, non-owning actor can indefinitely griefing-lock funds/close rights on someone else's vote account for the cost of a single lamport transfer plus transaction fees, repeatable at will and cheaply re-appliable if ever cleared.

### Likelihood Explanation
Likelihood is high assuming SIMD-0123/0291/0232/block-revenue-sharing features are active (V4 vote accounts): the attack requires no privileged role, no key compromise, and no race condition — it is a single, always-available instruction call with trivial cost (1 lamport + fee). It does not require front-running any particular transaction; the attacker can proactively "poison" the `pending_delegator_rewards` field for any V4 vote account at any time before the owner attempts to close it.

### Recommendation
Restrict `DepositDelegatorRewards` so the depositor must be an authorized party for the target vote account (e.g., a recognized delegator/stake account for that vote pubkey), or require the vote account's withdraw/commission-collector authority to acknowledge/opt in to accepting such deposits. Alternatively, decouple the close/withdraw eligibility check from an externally-inflatable field: e.g., let the withdraw authority sweep or force-settle `pending_delegator_rewards` to delegators (or to a system-owned holding account) as part of the close instruction, rather than unconditionally rejecting the operation whenever the counter is nonzero.

### Proof of Concept
1. Attacker (any funded keypair, no relationship to the vote account) submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` naming the victim's vote account as the destination and themselves as the signer/source, per the accounts layout validated in `vote_processor.rs`: [9](#0-8) 
2. This succeeds and sets `pending_delegator_rewards = 1` on the victim's vote account, as demonstrated by the existing unit test: [10](#0-9) 
3. Victim's authorized withdrawer later attempts `Withdraw(all_lamports)` to close the account; it now fails with `InstructionError::InsufficientFunds` purely because of the attacker's 1-lamport deposit, exactly as reproduced in the test harness: [6](#0-5)

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
