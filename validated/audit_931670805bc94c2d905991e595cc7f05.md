### Title
OP_RETURN data is excluded from Bitcoin fee and weight accounting, producing underpriced or oversized transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts up to 80 bytes of public `data` and appends it as an `OP_RETURN` output, but calculates `needed_fee`, the minimum-relay check, and the maximum-weight check using only `payments`. [1](#0-0) [2](#0-1)  The resulting signed transaction can therefore pay less than the requested fee rate, fall below Bitcoin's minimum relay fee, or exceed standard transaction weight despite construction succeeding. [3](#0-2) [4](#0-3) 

### Finding Description
`calculate_weight_vbytes` builds its sizing transaction from `payments` and an optional change output only. [5](#0-4)  In `SignableTransaction::new`, the `OP_RETURN` output is added to `tx_outs` before sizing, but the sizing call receives `payments`, not `tx_outs`, and has no `data` parameter. [6](#0-5)  Consequently, `needed_fee = fee_per_vbyte * vbytes` uses a virtual size that omits every byte of the data output. [7](#0-6) 

The same omission occurs when recalculating with a change output. [8](#0-7)  The final transaction nevertheless serializes `tx_outs`, including the previously added `OP_RETURN` output. [9](#0-8) 

### Impact Explanation
A signed transaction carrying `data` can have an actual virtual size greater than the size used to derive its fixed fee. [10](#0-9) [11](#0-10)  At `fee_per_vbyte = 1`, the minimum-relay check passes against the underestimated size while the signed transaction's effective fee rate is below 1 sat/vbyte, making it non-relayable under the policy enforced by the check. [3](#0-2)  Likewise, a transaction near `MAX_STANDARD_TX_WEIGHT` can pass the size check before accounting for the additional output and then exceed the standard weight limit once signed. [12](#0-11) 

This is a Medium availability analog: the produced spend cannot be executed as signed even though the API accepted the requested fee rate and returned a transaction. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The bug is reachable whenever public transaction construction supplies `Some(data)` of at most 80 bytes. [15](#0-14) [16](#0-15)  Existing tests explicitly exercise an 80-byte payload and a data-only transaction, but they do not compare the signed transaction's actual virtual size with `needed_fee`. [17](#0-16) [18](#0-17) 

### Recommendation
Calculate weight and virtual size from the complete output set, including the `OP_RETURN` output and any candidate change output. [19](#0-18) [2](#0-1)  Use that complete size for `needed_fee`, the minimum-relay check, change-output selection, and `MAX_STANDARD_TX_WEIGHT`; a regression test should assert `tx.fee() / tx.transaction().vsize() >= fee_per_vbyte` for a data-bearing transaction. [3](#0-2) [4](#0-3) 

### Proof of Concept
Using the existing test setup's funded `output`, an even Taproot `key`, and sufficient change:

```rust
let tx = SignableTransaction::new(
  vec![output],
  &[],
  Some(p2tr_script_buf(key).unwrap()),
  Some(vec![0; 80]),
  1, // 1 sat/vbyte
)
.unwrap();

let actual_vbytes = u64::try_from(tx.transaction().vsize()).unwrap();

// The OP_RETURN output is present, but was not included in needed_fee.
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));
assert!(tx.fee() < actual_vbytes);
```

`SignableTransaction::new` succeeds because its minimum-fee check uses the smaller no-data virtual size, while `tx.fee()` is committed as the actual input-minus-output difference for the larger serialized transaction. [7](#0-6) [20](#0-19)
