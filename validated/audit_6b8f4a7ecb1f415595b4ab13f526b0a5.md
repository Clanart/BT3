## Title
DID recovery attestation signature (`AGG_SIG_UNSAFE`) is not bound to the recovering coin, allowing replay across DID recovery spends - (File: `chia/wallet/did_wallet/did_wallet_puzzles.py`)

### Summary
`create_recovery_message_puzzle()` builds the "attestation" a backup DID uses to vouch for a lost/compromised DID's recovery to a new inner puzzle hash. The attestation's cryptographic authorization is expressed as `AGG_SIG_UNSAFE` with message `newpuz` only, while the binding to the specific DID being recovered is expressed only via a `CREATE_COIN_ANNOUNCEMENT` on an unrelated, throwaway coin. This mirrors the external report's root cause exactly: a verifier's signature is checked against too little context (only a subset of the data that should scope the authorization), enabling the signature to be replayed for a different transaction/coin than the one it was originally meant to authorize.

### Finding Description
`create_recovery_message_puzzle()`:
```python
def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
``` [1](#0-0) 

The BLS signature the backup DID's key produces over `newpuz` is emitted as `AGG_SIG_UNSAFE`. Unlike `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc., `AGG_SIG_UNSAFE` messages are *not* automatically suffixed with any coin-derived data (coin id, parent id, puzzle hash, amount) or network-specific additional data — the raw message is signed and verified as-is: [2](#0-1) [3](#0-2) 

The only place `recovering_coin_id` is asserted at all is a `CREATE_COIN_ANNOUNCEMENT` on a throwaway zero-value coin created purely to carry the attestation (`create_spend_for_message`): [4](#0-3) 

That announcement is only useful if the DID's actual recovery inner-puzzle solution independently asserts the matching `ASSERT_COIN_ANNOUNCEMENT` for *that specific* attestation coin, and the `newpuz` value must correspond one-to-one with the coin that actually gets created. Because the `AGG_SIG_UNSAFE` signature itself is only over `newpuz` — nothing else about the DID coin being recovered — a valid backup-key signature obtained for one legitimate DID recovery to a puzzle hash `newpuz` is fully reusable as a valid `AGG_SIG_UNSAFE` witness for *any other* spend bundle where an attacker can freely construct their own throwaway coin (any parent, since only the coin's puzzle/solution determine the announcement, not a signature) that emits `AGG_SIG_UNSAFE` + the same pubkey + the same `newpuz` message, satisfying `pkm_pairs`/`pkm_pairs_for_conditions_dict`'s check with the exact same signature.

This is the direct analog to the external report: "a signature from the verifier account is not properly validated ... allowing for potential signature replays," because it "only verifies [a subset of parameters]" instead of binding the full authorization context (the specific DID coin id) into the signed message.

### Impact Explanation
The severity is bounded by the requirement that `num_of_backup_ids_needed` DIDs must sign, and by the fact that the DID puzzle also requires the `ASSERT_MY_COIN_ID`/`ASSERT_COIN_ANNOUNCEMENT` linking to `my_id` as part of on-chain recovery logic executed by the DID inner puzzle (not shown fully in this Python driver but referenced by tests such as `test_did_tp` failing with `ASSERT_MY_COIN_ID_FAILED` when a wrong coin id is passed) — so the practical exploitability depends on whether the on-chain DID recovery puzzle itself, independent of the loose signature, cross-checks the recovering coin id against the attestation announcement in a way that can't be satisfied by an attacker-fabricated announcement coin. Given the signature carries no coin binding, if an attacker can also satisfy any remaining announcement/ID checks with self-constructed coins (which the DID_INNERPUZ chialisp source was not directly inspected in this pass), a captured/leaked backup-DID attestation for `newpuz` could be replayed to redirect a *different* DID (sharing the same backup DID as an authorized recoverer and threshold) to the same attacker-controlled `newpuz`, resulting in unauthorized DID ownership transfer.

### Likelihood Explanation
Likelihood is low-to-moderate: the attestation must first be captured (e.g. an off-chain relay of the backup signature, a nosy mempool observer, or a compromised communication channel used to relay recovery attestations between the recovering wallet and backup DID holders), and the attacker must control or influence a second DID that also lists the same backup DID with a satisfiable threshold, or must find another path where the coin-announcement binding can be bypassed. This mirrors the "low risk" rating given to the original Zyfi finding, since real-world exploitation requires specific preconditions (signature exposure, applicable second target, and full satisfaction of any on-chain coin-binding checks not audited here).

### Recommendation
Bind the DID recovery attestation signature to the recovering coin's identity rather than relying solely on an announcement from an unrelated coin. Concretely, change `create_recovery_message_puzzle()` to sign the message `recovering_coin_id + newpuz` (or use `AGG_SIG_ME`/`AGG_SIG_PARENT` bound to the attestation coin, plus a `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` pair that itself commits to `recovering_coin_id` in the signed message, not just in an unauthenticated announcement). This closes the gap where the cryptographic signature alone can be replayed independent of coin identity.

### Proof of Concept
Conceptual replay (not fully executed against the on-chain DID_INNERPUZ chialisp validation logic, which was not available to inspect in this pass):
1. Backup DID `B` signs a legitimate recovery attestation for DID coin `A`, producing `AGG_SIG_UNSAFE(pubkey_B, newpuz_X)` via `create_recovery_message_puzzle(A.name(), newpuz_X, pubkey_B)`.
2. This attestation (message `newpuz_X` + signature) is observed/captured by an attacker (e.g., via mempool, logs, or a compromised relay channel).
3. Attacker owns/controls DID coin `C`, which also lists `B` as an authorized backup DID with a satisfiable `num_of_backup_ids_needed` threshold.
4. Attacker constructs their own throwaway coin spend emitting `CREATE_COIN_ANNOUNCEMENT(C.name())` + `AGG_SIG_UNSAFE(pubkey_B, newpuz_X)`, reusing the *same* captured signature (since the signed message `newpuz_X` never included `A`'s or `C`'s identity).
5. If the DID recovery inner-puzzle solve path for `C` accepts this self-fabricated announcement/signature pairing as satisfying its backup-DID recovery threshold, `C` is redirected to `newpuz_X` without a fresh authorization from `B` for `C` specifically.

Confirming step 5 requires reading `DID_INNERPUZ`'s Chialisp recovery-spend logic (compiled bytecode referenced via `chia_puzzles_py.programs.DID_INNERPUZ`), which was not retrievable in this investigation; this is called out explicitly as an open item for a full confirmation of exploitability.

def pkm_pairs(conditions: SpendBundleConditions, additional_data: bytes) -> tuple[list[G1Element], list[bytes]]:
    ret: tuple[list[G1Element], list[bytes]] = ([], [])

    data = agg_sig_additional_data(additional_data)

    for pk, msg in conditions.agg_sig_unsafe:
        ret[0].append(pk)
        ret[1].append(msg)

    for spend in conditions.spends:
        condition_items_pairs = [
            (ConditionOpcode.AGG_SIG_PARENT, spend.agg_sig_parent),
            (ConditionOpcode.AGG_SIG_PUZZLE, spend.agg_sig_puzzle),
            (ConditionOpcode.AGG_SIG_AMOUNT, spend.agg_sig_amount),
            (ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT, spend.agg_sig_puzzle_amount),
            (ConditionOpcode.AGG_SIG_PARENT_AMOUNT, spend.agg_sig_parent_amount),
            (ConditionOpcode.AGG_SIG_PARENT_PUZZLE, spend.agg_sig_parent_puzzle),
            (ConditionOpcode.AGG_SIG_ME, spend.agg_sig_me),

def pkm_pairs_for_conditions_dict(
    conditions_dict: dict[ConditionOpcode, list[ConditionWithArgs]],
    coin: Coin,
    additional_data: bytes,
) -> list[tuple[G1Element, bytes]]:
    ret: list[tuple[G1Element, bytes]] = []

    data = agg_sig_additional_data(additional_data)

    for cwa in conditions_dict.get(ConditionOpcode.AGG_SIG_UNSAFE, []):
        validate_cwa(cwa)
        for disallowed in data.values():
            if cwa.vars[1].endswith(disallowed):
                raise ConsensusError(Err.INVALID_CONDITION)
        ret.append((G1Element.from_bytes(cwa.vars[0]), cwa.vars[1]))
