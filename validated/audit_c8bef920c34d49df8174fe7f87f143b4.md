### Title
Unbounded Lagrange threshold deserialization causes quadratic CPU exhaustion - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t`, `n`, and participant-index fields up to `u16::MAX`, then eagerly constructs `ThresholdKeys` with the selected interpolation method. [1](#0-0) 

For Lagrange interpolation, `ThresholdKeys::new` calculates an interpolation factor for every participant in `1..=t`, while each factor loop iterates over the same included-participant list, producing `O(t²)` scalar-field work. [2](#0-1) [3](#0-2) 

### Finding Description
The deserializer reads unbounded 16-bit threshold parameters directly from the input stream and reads `n` verification shares before validating the completed object through `ThresholdKeys::new`. [1](#0-0) 

`ThresholdParams::new` permits the maximum valid configuration `t = n = i = 65535`, because it only rejects zero values, `t > n`, and `i > n`. [4](#0-3) 

`ThresholdKeys::new` then evaluates `interpolation_factor` once for each of those 65,535 participants. [3](#0-2) 

Each Lagrange `interpolation_factor` call loops over every other included participant and performs field multiplication, subtraction, and a field inversion. [5](#0-4) 

Therefore, a serialized `ThresholdKeys` object containing roughly 65,535 encoded points causes approximately 4.29 billion inner-loop iterations during deserialization. [6](#0-5) [3](#0-2) 

### Impact Explanation
An unprivileged party who can cause a service to call `ThresholdKeys::read` on attacker-controlled bytes can make that service consume excessive CPU inside a single deserialization call. [7](#0-6) 

The malicious input is only about 2.1 MiB for a 32-byte point encoding, excluding the small header and scalar, while triggering billions of field operations and 65,535 field inversions. [6](#0-5) [8](#0-7) 

This is a remotely reachable availability failure in any production component that accepts serialized threshold keys from peers, clients, recovery data, transactions, or protocol messages. [7](#0-6) 

### Likelihood Explanation
The required bytes are structurally valid: nonzero `t` and `n`, `t <= n`, a nonzero participant index no greater than `n`, the Lagrange interpolation tag, one canonical scalar, and `n` canonical group encodings. [4](#0-3) [1](#0-0) 

Canonical scalar and point readers only reject malformed or non-canonical encodings, so they do not impose a protocol-level participant bound. [9](#0-8) 

The expensive computation occurs after all bytes are parsed, so the attack does not depend on malformed cryptography or invalid signatures. [10](#0-9) [3](#0-2) 

### Recommendation
Enforce a conservative protocol maximum for `t` and `n` in `ThresholdKeys::read` before allocating or decoding the `n` verification shares. [1](#0-0) 

Apply the same bound in `ThresholdParams::new` or another mandatory constructor layer so programmatic construction cannot bypass the deserialization limit. [4](#0-3) 

If large thresholds must remain supported, replace the per-participant naive Lagrange calculation with a bounded or subquadratic implementation and cap total deserialization work before calling `ThresholdKeys::new`. [2](#0-1) [3](#0-2) 

### Proof of Concept
The following Rust-style generator constructs a structurally valid Ristretto `ThresholdKeys` encoding with `t = n = i = 65535` and passes it to the vulnerable deserializer:

```rust
use dalek_ff_group::Ristretto;
use frost::{Ciphersuite, ThresholdKeys};
use group::{ff::PrimeField, GroupEncoding};

fn malicious_threshold_keys() -> Vec<u8> {
  let mut bytes = Vec::new();

  // Ciphersuite identifier.
  bytes.extend_from_slice(&(Ristretto::ID.len() as u32).to_le_bytes());
  bytes.extend_from_slice(Ristretto::ID);

  // t = n = i = u16::MAX.
  bytes.extend_from_slice(&u16::MAX.to_le_bytes());
  bytes.extend_from_slice(&u16::MAX.to_le_bytes());
  bytes.extend_from_slice(&u16::MAX.to_le_bytes());

  // Interpolation::Lagrange.
  bytes.push(1);

  // Canonical secret-share scalar.
  bytes.extend_from_slice(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref());

  // n canonical verification shares.
  let point = Ristretto::generator().to_bytes();
  for _ in 0..u16::MAX {
    bytes.extend_from_slice(point.as_ref());
  }

  bytes
}

let encoded = malicious_threshold_keys();
let _ = ThresholdKeys::<Ristretto>::read(&mut encoded.as_slice());
```

`ThresholdKeys::read` accepts the three 16-bit parameters, consumes all 65,535 points, and calls `ThresholdKeys::new`. [1](#0-0) 

`ThresholdKeys::new` then requests 65,535 interpolation factors, and each Lagrange factor scans the same 65,535-member set. [5](#0-4) [3](#0-2)

  /// The interpolation factor for this participant, within this signing set.
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
