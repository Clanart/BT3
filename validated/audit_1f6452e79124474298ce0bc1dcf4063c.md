## Title
Unauthenticated `WWW-Authenticate` response header spoofs GitHub host classification and triggers automatic Enterprise sign-in prompts - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git credential helper trampoline decides whether a remote host should be treated as a trusted GitHub/GitHub Enterprise endpoint partly by trusting the unauthenticated `WWW-Authenticate` HTTP header echoed back by the remote git server itself, rather than relying solely on TLS-verified identity or a pre-configured allow-list. A malicious or MITM'd git remote can forge this header to make Desktop believe an arbitrary host is a GitHub Enterprise server, causing Desktop to automatically surface a "Sign in to GitHub Enterprise" flow scoped to the attacker's URL during an otherwise ordinary `fetch`/`pull`/`clone`/`push`.

### Finding Description
The `getEndpointKind` function classifies the credential's target host using several heuristics, one of which is entirely attacker-controlled: [1](#0-0) 

```
const getEndpointKind = async (cred: Credential, store: Store) => {
  ...
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
  ...
```

Git forwards any `WWW-Authenticate` response header it receives from the remote server verbatim to the configured `credential.helper` (which for Desktop is this trampoline, wired up in `app/src/ui/index.tsx`) [2](#0-1) . This header is fully controlled by whatever server answers the HTTP request for the configured remote URL — i.e., it is attacker content, not something Git or Desktop authenticates or verifies against the endpoint's real identity (unlike, say, a valid TLS certificate chain).

The classification result directly drives whether Desktop treats the remote as a first-party GitHub endpoint and, if no matching account is on file, proactively invokes the sign-in UI: [3](#0-2) 

```
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)
  if (ghCred) { return ghCred }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()
  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) { ... return undefined }
    const account = await ui.promptForGitHubSignIn(endpoint)
    ...
    return credWithAccount(cred, account)
  }
  ...
```

Because `endpoint` here is derived straight from `getCredentialUrl(cred)` — the exact remote URL Git is talking to — an attacker who controls that remote (a self-hosted git server, a compromised proxy, or a MITM position on an insecure/misconfigured connection) can simply answer any HTTP request with `WWW-Authenticate: Basic realm="GitHub"` to force `endpointKind = 'enterprise'`. Since no account exists yet for that attacker-chosen host, Desktop calls `ui.promptForGitHubSignIn(endpoint)` automatically, presenting the user with what looks like a legitimate "Sign in to GitHub Enterprise" dialog pre-populated with the attacker's URL — without the user having taken any unusual action beyond performing a normal fetch/clone/push against a repository they added.

### Impact Explanation
This breaks the invariant that credential-release decisions (and, more importantly, decisions to solicit GitHub credentials/OAuth flows) should be based on verified endpoint identity, not on unauthenticated content supplied by the remote itself. The practical outcomes are:
- **Unauthorized OAuth/account-binding surface**: A benign-looking git remote can spontaneously trigger Desktop's built-in "Sign in to GitHub Enterprise" flow pointed at an attacker-chosen URL during a routine fetch/push, which the user may complete believing it is a legitimate Desktop-initiated prompt, handing GitHub-style credentials or an OAuth code to the attacker's server.
- **Credential/token exfiltration risk**: If similar host-classification confusion causes an existing stored GitHub/GHE account credential to be considered a match (dependent on the exact matching semantics of `findGitHubTrampolineAccount`, which could not be fully verified within available context), it could result in leaking a real GitHub access token to an unintended host.

This is a Medium-severity issue: it requires the user to interact with an attacker-controlled or attacker-influenced git remote (already a normal part of Desktop's threat model — cloned/fetched repository or remote/proxy response), and the resulting phishing-style prompt still needs the user to enter credentials, but that prompt is triggered automatically by Desktop itself rather than requiring any unnatural or out-of-band step from the user.

### Likelihood Explanation
Any git server the user points Desktop at (a coworker's self-hosted instance, a compromised or spoofed corporate git server, or a MITM proxy on an unauthenticated HTTP/HTTPS connection) can trivially return a crafted `WWW-Authenticate` header on a normal HTTP 401 response — this requires no special access to Desktop's host, no admin rights, and no pre-existing malware; it is purely a property of the git remote/proxy response, matching the specified valid impact category directly.

### Recommendation
Do not use the unauthenticated `WWW-Authenticate` realm string as a basis for classifying a host as "GitHub"/"enterprise". At minimum, gate this heuristic behind an explicit user-configured allow-list of GHE endpoints (as already exists via stored `Account.endpoint` values) rather than treating an as-yet-unknown host as GitHub Enterprise purely because it echoed back a realm string. If the header is to be used as a hint at all, it should only ever narrow down *which already-known* account to try, never trigger a new, automatic sign-in flow for a previously untrusted URL.

### Proof of Concept
1. Set up an HTTP(S) git remote (or a MITM proxy in front of one) that, for any request, responds with `WWW-Authenticate: Basic realm="GitHub"` on a 401.
2. In GitHub Desktop, add or clone a repository pointing at that remote (no existing account configured for this host).
3. Perform a normal `Fetch`/`Pull`/`Push`. Git invokes the credential helper trampoline, which calls `getCredential` → `getEndpointKind`.
4. Because the forged header matches `realm="GitHub"`, `getEndpointKind` returns `'enterprise'`, and since `accounts.some(a => a.endpoint === apiEndpoint)` is false, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)` automatically, surfacing an unsolicited "Sign in to GitHub Enterprise" dialog scoped to the attacker's remote URL — evidenced at [4](#0-3) .

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
