### Title
Symlink/path-traversal escape when opening PR/commit file entries in external editor or default program - ([File: app/src/ui/open-pull-request/pull-request-files-changed.tsx])

### Summary
GitHub Desktop has two independent code paths that turn a repository-relative file path into an absolute filesystem path before acting on it: the "Open Repository from URL" deep-link handler, which explicitly re-validates the resolved path with `resolveWithin()` and rejects absolute paths, and the changed-file context menus (PR files-changed view, commit file list, changes list), which simply do `Path.join(repository.path, file.path)` with no re-validation against symlink or traversal escapes. The `file.path` value in the second path originates from a git tree entry of a **fetched/checked-out branch** (e.g., a PR from a fork), which is attacker-controlled content. Because only one of the two structurally similar sinks enforces the "stay inside the repo" invariant, the second one can be used to act on a path outside the repository root when the checked-out tree contains a symlink.

### Finding Description
The deep-link handler in `app/src/ui/dispatcher/dispatcher.ts` treats a file path coming from a remote-triggered action as untrusted and defends against escape with two checks: rejecting absolute paths and calling `resolveWithin(repository.path, filepath)`, which resolves symlinks via `realpath` and rejects any result that escapes the root: [1](#0-0) [2](#0-1) 

By contrast, the context menu handler for a file shown in the PR "Files changed" view builds the on-disk path with a plain `Path.join` and performs no symlink-aware containment check before wiring it into "Open in external editor", "Open with default program", and "Reveal in Finder" actions: [3](#0-2) 

`file.path` for this view is a path taken from `CommittedFileChange`/PR diff data for a branch that Desktop has fetched from a remote (potentially a fork, in the pull-request preview flow that fetches and checks out PR branches). Git trees can contain symlink entries (mode `120000`) whose target is arbitrary attacker-controlled text, and a symlinked path component that is checked out into the working directory will cause `Path.join(repository.path, file.path)` to point to a location outside the repository once the filesystem resolves the symlink at open time — `Path.join`/`pathExists`/`launchExternalEditor` do not call `realpath` or otherwise detect this, unlike `resolveWithin`.

The same unguarded `Path.join(repository.path, path)` pattern that feeds `openInExternalEditor` is also present in the general "open file" flow in `app.tsx`: [4](#0-3) 

This is the same class of broken invariant as M-13: two nearly identical operations (resolve-a-repo-relative-path-and-act-on-it) exist in the codebase, one is hardened with the correct containment check (`resolveWithin`) and the other, which is reachable from attacker-supplied repository content (a checked-out PR/fork branch), is not.

### Impact Explanation
An attacker who controls a repository or a pull-request branch that a user fetches/checks out in GitHub Desktop can commit a symlink whose target points outside the working directory (e.g., to a file in the user's home directory, `.ssh` folder, or a shell/profile/startup file, or a downloaded executable if targeting an "Open with default program" action). When the victim opens "Files changed" for that PR (a common and expected workflow before merging) and uses "Open in external editor"/"Open with default program"/"Reveal in Finder" on the symlinked entry, Desktop resolves and opens a path outside the intended repository sandbox. Depending on OS file-association behavior, "Open with default program" on a symlink to an executable/script/`.desktop`/`.cmd` file can result in code execution instead of just disclosure; at minimum, it enables the read/exfiltration and exposure of file content outside the repo. This satisfies the impact bar: attacker-controlled fetched-repository content leading to file access outside the repo (and potentially execution), without any local/physical access, admin rights or social engineering beyond normal PR review.

### Likelihood Explanation
Reviewing PR files-changed content and clicking a context-menu action on a listed file is a normal, expected Desktop workflow (not an "unnatural user step"), so the trigger requires no unusual user behavior beyond opening a PR. Git natively supports symlink tree entries, so crafting the malicious commit requires no exotic tooling. The only missing piece from full confirmation is verifying at the OS/file-open layer exactly how each platform's shell "open" API treats a symlinked path (this determines whether the outcome is limited to file disclosure or extends to execution), which could not be fully confirmed from the indexed source alone.

### Recommendation
Route the path used in `onFileContextMenu` (and the equivalent flows in `app.tsx`, `selected-commits.tsx`, `sidebar.tsx`, `stash-diff-viewer.tsx`, wherever a committed/PR file path is turned into a full path) through the same `resolveWithin()` containment check already used by the deep-link handler, rejecting or refusing to act when the resolved real path escapes `repository.path`. Treat file paths originating from fetched/checked-out branches as untrusted input consistently across all sinks, rather than only in the URL-triggered code path.

### Proof of Concept
Conceptual PoC (not executed, derived from code):
1. Attacker forks the target repo and adds a commit containing a symlink entry, e.g. `evil -> ../../../../.ssh/id_rsa` (or, on Windows/macOS, a symlink to an executable/script to test "Open with default program").
2. Attacker opens a pull request against the victim's repository.
3. Victim, using GitHub Desktop, opens "Preview Pull Request" and views "Files changed" for the PR (this fetches/checks out the fork's branch locally).
4. Victim right-clicks the `evil` entry and selects "Open in external editor" / "Open with default program".
5. `onFileContextMenu` computes `fullPath = Path.join(repository.path, 'evil')` with no symlink/containment validation and passes it to `dispatcher.openInExternalEditor(fullPath)`, which spawns the editor process against the resolved symlink target outside the repository: [5](#0-4) [6](#0-5)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
