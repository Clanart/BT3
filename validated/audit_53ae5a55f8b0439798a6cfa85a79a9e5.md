### Title
Unreachable-by-invariant `enc_keys` HashMap indexing / re-registration `assert!` panics on attacker-influenced PedPoP flow — remote denial of service - (crypto/dkg/pedpop/src/encryption.rs)

### Summary
The CVE-2017-14642 bug class is "attacker-controlled input reaches a dereference of a value that was assumed non-null, crashing the process." In Serai's in-scope code, the analog is `Decryption` in the PedPoP DKG encryption layer, which trusts that every `Participant` index it is asked to use has a registered encryption key. Two reachable crash sites exist:

- `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (encryption.rs:388). The `decryptor` is a `Participant` index supplied along the accusation/blame path; if no `EncryptionKeyMessage` was ever registered for that index, the `HashMap` index panics.
- `Decryption::register` asserts `!self.enc_keys.contains_key(&participant)` (encryption.rs:356-359), so a counterparty that delivers a second `EncryptionKeyMessage` for the same participant index triggers an unconditional panic rather than an error.
- Similarly, `Encryption::encrypt` indexes `self.decryption.enc_keys[&participant]` (encryption.rs:466), panicking if encrypt-to is requested for a participant that never registered. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`EncryptionKeyMessage::read` accepts an arbitrary attacker-supplied `enc_key` point (`C::read_G`, which does not even reject identity at the `Ciphersuite` level) [4](#0-3) . Registration state is tracked only inside `Decryption.enc_keys`, keyed by `Participant`. Nothing in this layer enforces that (a) a participant registers exactly once, or (b) `decrypt_with_proof`/`encrypt` are only invoked for registered participants — both are enforced by `assert!`/indexing panics instead of `io::Error`/`DecryptionError`.

Contrast with the deserialization layer, which is carefully error-returning (`M::read`, `C::read_G`, `DLEqProof::read`, `SchnorrSignature::read` all return `io::Result`) [5](#0-4) . The crash surfaces only after parsing succeeds, exactly like Bento4's `AP4_HdlrAtom` null deref: valid-format input, invalid protocol state.

### Impact Explanation
A panic in a Rust library called across an unwinding boundary aborts or unwinds the calling task. A DKG counterparty can therefore crash a participant's processor/coordinator during the PedPoP shares/accusation phase — denying service and potentially aborting an in-progress signing/key-generation session. This matches the CVE's impact class (remote denial of service, CVSS 6.5 → Medium).

Caveat on reachability: the exploit path assumes the caller (PedPoP in `crypto/dkg/pedpop/src/lib.rs`) routes a blame/accusation naming an arbitrary `decryptor`, or processes a duplicate `EncryptionKeyMessage`, before deduplicating. The `Commitments` docs explicitly note the library "does not handle networking" and cannot detect duplicate messages — that responsibility is delegated to the caller [6](#0-5) , so a second registration message reaching `register` is plausible. I could not fully trace the PedPoP caller's dedup logic within the available iterations, so the duplicate-registration path is the more certain trigger; the `enc_keys[&decryptor]` path depends on the accusation flow accepting an unregistered index.

### Likelihood Explanation
Medium. Triggering requires only sending a malformed protocol sequence (duplicate key registration, or a blame message referencing a participant with no registered key) during a DKG the attacker legitimately participates in. No cryptographic break is needed — just message sequencing the library explicitly declines to police.

### Recommendation
- In `Decryption::register`, return a `Result`/`io::Error` (or silently ignore duplicates after equality-checking `enc_key`) instead of `assert!`.
- In `decrypt_with_proof` and `Encryption::encrypt`, replace `self.enc_keys[&participant]`/`self.enc_keys[&decryptor]` with `.get(&participant).ok_or(DecryptionError::InvalidProof)?`-style lookups.
- Audit the same pattern: `BindingFactor::binding_factors`/`bound` in `crypto/frost/src/nonce.rs` also index `self.0[&l]` and unwrap `binding_factors` [7](#0-6)  — currently safe only because `sign`/`complete` pre-populate every `included` entry via `validate_map` [8](#0-7) ; worth converting to checked lookups for defense in depth.
