### Title
Quoted `git commit` bypasses `_GIT_COMMIT_RE` while satisfying the hooks.json `if` matcher, silently skipping the commit-security review - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The PostToolUse commit-review hook is gated twice: first by Claude Code's own `"if": "Bash(git commit:*)"` matcher in `hooks.json`, then defensively re-checked inside the script by `_GIT_COMMIT_RE.search(command)`. The regex is a naive, non-shell-aware pattern that requires the literal substring `commit` to immediately follow whitespace after `git`, with no quote-stripping. A trivially shell-legal, functionally identical command such as `git "commit" -m "msg"` (or `git commi''t -m msg`) is executed by the real shell exactly as `git commit -m msg`, and Claude Code's own bash-argument matcher (which handles quoting/tokenization per the CHANGELOG's documented bash-parsing fixes) is expected to still classify it under `Bash(git commit:*)`, but `_GIT_COMMIT_RE` does not match it, so `handle_commit_review_posttooluse` hits its "defensive" `sys.exit(0)` fast-path and the LLM security review of the commit never runs.

The comment above the regex explicitly states the intent is to "mirror Claude Code's own commit detection," and the comment at the call site explicitly frames `hooks.json`'s `"if": "Bash(git commit:*)"` as "the real gate" while this regex is described as only a defensive re-check for the case where "CC's command matching fails open and spawns the hook anyway" — i.e., the authors only considered the false-positive direction (hook spawned unnecessarily), not the false-negative direction (hook spawned correctly by CC's matcher, but the script's own regex fails to recognize the command as a commit).

`_GIT_COMMIT_RE = re.compile(r'\bgit\s+commit(?:\s|$)')` performs plain text matching with no shell tokenization or quote removal. Any command where the literal token `commit` is not immediately adjacent (as raw bytes) to a preceding `git\s` will not match, even though the POSIX shell treats quoted words identically to unquoted ones when they contain no special characters. Concretely:

- `git "commit" -m "fix"` — a completely ordinary, shell-legal invocation a developer or an LLM might emit — is executed by the shell as `git commit -m fix`. The character immediately following `git ` in the raw string is `"`, not `c`, so `_GIT_COMMIT_RE.search()` returns `None`.
- Similar effects are achievable via empty-string quote splicing (`git commi''t`), backslash escaping (`git comm\it`), or `$@`/`${x}` expansions that reduce to the literal word `commit` at shell-execution time but not in the raw argv text the regex scans.

Claude Code's bash command matcher (used to evaluate `"if": "Bash(git commit:*)"`) is a shell-aware tokenizer — this is evidenced throughout `CHANGELOG.md` by repeated fixes to bash-prefix/permission matching for quoting, escaping, and subcommand extraction (e.g., "Fixed a security issue where a backslash-escaped flag could be auto-allowed", "Improved bash command parsing by switching to a native module", "Fixed bash command prefix extraction to correctly identify subcommands after global options"). Because quote-handling is basic, expected shell semantics that any correct command matcher must support (otherwise ordinary quoted commit messages like `git commit -m "fix bug"` would misclassify), it is reasonable that CC's matcher normalizes `git "commit"` to the token `commit` and matches the `Bash(git commit:*)` `if` rule, spawning the hook. The hook then immediately exits via the regex's fast-path, and `commit_succeeded` is never computed — the LLM review, dedup bookkeeping, and `asyncRewake` guidance are all skipped.

Because the review-skip is silent (`sys.exit(0)` with no user-visible signal, and the `asyncRewake`/`rewakeMessage` UI never fires), the user has no indication that the "commit security review found issues" gate was bypassed — they will believe the standard commit-review flow ran, when in fact the shell's actual `git commit` succeeded unreviewed.

### Impact Explanation
This breaks the "deny means deny" / block-hook enforcement invariant: a compound command that is functionally a real `git commit` (and is, by the security model's own comment, expected to be caught by `Bash(git commit:*)`) reaches actual git-commit execution while the security-guidance plugin's automated review is silently skipped due to a parser differential between Claude Code's shell-aware `if` matcher and the plugin's naive regex. In practice this means any code path that constructs the commit command with quoted or escaped subcommand tokens — including a prompt-injected instruction embedded in repo content (e.g., a malicious `CLAUDE.md`, README, or issue text telling Claude "always commit with `git \"commit\" -m ...`") — can get unreviewed vulnerable code committed while the user is told (or believes) the security review gate is active. This matches the class of "block hooks bypassable via parser differential" bounty impact: unauthorized skip of a security-relevant gating mechanism.

### Likelihood Explanation
- Preconditions: the attacker only needs to influence the literal Bash command text that ends up executed (e.g., via prompt injection in repository content, or a user/agent habitually quoting arguments) — no privileged access is required.
- Feasibility: quoting a subcommand token (`git "commit" ...`) is extremely common, unremarkable shell syntax that a model could easily produce without any obfuscation intent, meaning the bypass could occur even accidentally, not only via deliberate attack — increasing repeatability.
- Repeatable: the differential is deterministic — any command matching this class will always execute as a real commit while always failing `_GIT_COMMIT_RE`, as long as Claude Code's own matcher continues to be shell/quote-aware (which the CHANGELOG evidence strongly suggests, and which the code comment even implicitly assumes).

Note: exact confirmation of Claude Code's closed-source `if`-matcher tokenization behavior is not directly inspectable in this repository; the conclusion that it recognizes quoted tokens is inferred from CHANGELOG entries describing its bash-parsing/quoting fixes, not from reading its source directly.

### Recommendation
Replace the naive `_GIT_COMMIT_RE` textual regex with a shell-aware check that mirrors actual command semantics rather than raw byte adjacency:
- Parse the command with a POSIX-compliant tokenizer (e.g. Python's `shlex.split` per top-level `&&`/`;`/`|` segment, with quote removal) and check whether the first token is `git` (optionally preceded by recognized global flags) and the next non-flag token is `commit`.
- Alternatively, broaden the regex to tolerate quote/escape characters between tokens (e.g., strip quote characters before matching, or match token boundaries after a lightweight tokenization pass) so it stays a true superset of Claude Code's own matcher rather than a stricter, byte-literal check.
- Add a regression test asserting `_GIT_COMMIT_RE`-equivalent logic accepts common quoted/escaped forms (`git "commit"`, `git commi''t`, `git comm\it`) that a POSIX shell resolves to `git commit`.

### Proof of Concept
Differential unit test comparing shell execution semantics against `_GIT_COMMIT_RE`:
```python
import subprocess
from security_reminder_hook import _GIT_COMMIT_RE

candidates = [
    'git commit -m "msg"',
    'git "commit" -m "msg"',
    "git commi''t -m msg",
    'git comm\\it -m msg',
]

for cmd in candidates:
    # Ground truth: what the real shell resolves the command to.
    argv = subprocess.run(["bash", "-c", f'printf "%s\\n" {cmd!r}'],
                           capture_output=True, text=True)
    executes_as_commit = "commit" in subprocess.run(
        ["bash", "-c", f"set -- {cmd}; echo \"$1 $2\""],
        capture_output=True, text=True).stdout

    regex_detects = bool(_GIT_COMMIT_RE.search(cmd))

    assert executes_as_commit, f"harness sanity check failed for {cmd!r}"
    # This assertion is expected to FAIL for the quoted/escaped variants,
    # demonstrating the parser differential:
    assert regex_detects, (
        f"_GIT_COMMIT_RE failed to detect a real `git commit` invocation: {cmd!r}"
    )
```
Expected result: the first candidate passes; `git "commit" -m "msg"`, `git commi''t -m msg`, and `git comm\it -m msg` all fail the final assertion, proving `_GIT_COMMIT_RE` under-detects commands that a real shell (and, per CC's documented quote-aware bash matching, Claude Code's own `if` matcher) treats as `git commit`. An integration-level PoC would additionally invoke `handle_commit_review_posttooluse` with `tool_input.command = 'git "commit" -m "msg"'` and a `tool_response.stdout` containing a real `[branch sha] msg` + `N files changed` block, asserting that `emit_metrics` is called with `skip_reason=21` (review skipped) despite a successful commit having occurred.
