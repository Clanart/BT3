## Finding

### Title
`CallDispatcher.dispatch` is a fully unauthenticated function that lets anyone grant infinite ERC20 approvals from the shared dispatcher, enabling theft of any token dust it later holds - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The external report's root cause is that a bridge contract grants an ERC20 `approve()` to an attacker-controlled address taken directly from unvalidated user input, letting the attacker later drain any token balance the contract holds via `transferFrom`. Hyperbridge's `CallDispatcher` contract reproduces the same broken invariant: its `dispatch()` entrypoint has **no access control at all**, so any unprivileged caller can make the dispatcher itself execute `IERC20.approve(attacker, type(uint256).max)`. Because `CallDispatcher` is a single, shared, reusable piece of infrastructure invoked by unrelated flows in `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, any token balance it later holds (even transiently, or as unswept dust) becomes stealable through that pre-planted allowance.

### Finding Description
`CallDispatcher.dispatch` takes an ABI-encoded `Call[]` and executes each call with no restriction on `msg.sender`: [1](#0-0) 

Any account can call this function directly and supply a `Call{to: TOKEN, value: 0, data: approve(attacker, type(uint256).max)}`. Since the call is executed by the dispatcher itself (`to.call{value: call.value}(call.data)`), the resulting allowance is `allowance(dispatcher, attacker) = type(uint256).max` for any ERC20 the attacker chooses — this is functionally identical to the `LibAsset.approveERC20` bug where a contract grants an infinite allowance to a caller-controlled address.

The dispatcher is shared, canonical infrastructure — the docs point to a small set of "Existing `CallDispatcher` deployments" that both `IntentGatewayV2` and `HyperFungibleToken`/`WrappedHyperFungibleToken` route tokens through: [2](#0-1) 

`IntentGatewayV2` explicitly acknowledges the dispatcher can be left holding tokens and sweeps them back after every predispatch/postdispatch execution: [3](#0-2) 

However, `HyperFungibleToken`/`WrappedHyperFungibleToken`'s calldata-execution path only documents that a revert rolls back the whole `onAccept`, with no mention of an automatic post-execution sweep of leftover token balance on the dispatcher: [4](#0-3) 

The docs even warn that senders should use exact approvals in their own `Call[]` "since the dispatcher contract holds tokens temporarily during execution" — confirming the dispatcher's balance is not always zero between calls, and that any dust left there (from slippage, partial swaps, or a sender's incomplete call sequence) persists as a stealable balance once a malicious approval is pre-staged.

### Impact Explanation
Because `dispatch()` is public and unauthenticated, an attacker can, at zero cost and at any time, pre-plant an infinite allowance from the shared `CallDispatcher` to themselves for any ERC20 token. Any subsequent dust, slippage remainder, or interrupted multi-call sequence left on the dispatcher by an unrelated, legitimate user's HFT/WrappedHFT bridge-and-swap operation becomes immediately stealable via a plain `TOKEN.transferFrom(dispatcher, attacker, amount)` call on the ERC20 contract — no interaction with Hyperbridge's ISMP, proofs, or governance is required. This is unauthorized transaction execution and direct fund loss for whichever user's residual tokens land on the dispatcher after the attacker's allowance is in place.

### Likelihood Explanation
Likelihood is high for the precondition (planting the approval) since it costs one unprivileged transaction and no special permissions, matching the report's "no whitelist, trust user input" pattern exactly. The likelihood of a triggering balance depends on how often the CallDispatcher is left holding non-zero token balances across transaction boundaries for the HFT/WrappedHFT calldata path, which the current design does not guarantee to be zero (unlike `IntentGatewayV2`, which sweeps explicitly).

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by the trusted callers that are supposed to use it (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), e.g. via an allowlist/`onlyAuthorizedCaller` modifier, rather than leaving it fully public.
- Add an explicit sweep of any residual token balance held by the `CallDispatcher` at the end of every HFT/WrappedHFT `onAccept` calldata-execution path, mirroring the dust-sweep already implemented in `IntentsBase._execute`.
- Alternatively, deploy a fresh, single-use `CallDispatcher` per message/order instead of reusing one shared instance across all senders, eliminating the cross-user fund-commingling risk entirely.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly — no relationship to any order or bridge message is required, since `dispatch` has no caller restriction.
2. `allowance(CallDispatcher, attacker)` for USDC is now `type(uint256).max`.
3. A legitimate user bridges USDC via `HyperFungibleToken.send(...)` with `data` set to mint tokens directly to the `CallDispatcher` and swap them (per the documented transfer-and-swap pattern) — if the resulting swap leaves any USDC dust on the dispatcher (e.g., due to slippage or a partial `Call[]`), that dust is not automatically swept back.
4. Attacker calls `USDC.transferFrom(CallDispatcher, attacker, dustAmount)` directly on the token contract using the pre-planted allowance, stealing the residual funds — with no relayer, prover, or admin compromise involved.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.

        Call[] memory sweepCalls = new Call[](outputsLen);

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }

                uint256 balance = IERC20(token).balanceOf(dispatcher);

                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)

                    sweepCount++;
                    emit DustCollected(token, balance);

                ++i;
            }

                }
