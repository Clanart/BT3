### Title
Front-running the Payout tx's `SIGHASH_SINGLE|ANYONECANPAY` signature to rewrite the OP_RETURN attribution and steal reimbursement credit - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs only input 0 and output 0 of the Payout transaction with `SinglePlusAnyoneCanPay`, leaving the OP_RETURN output (which records which operator gets credit for fronting the withdrawal) completely unsigned. Any unprivileged party who observes an operator's unconfirmed Payout tx in the mempool can rebroadcast a variant that reuses the signed input/output but substitutes an arbitrary operator's xonly-pubkey in the OP_RETURN, winning the race to be mined and hijacking the reimbursement credit that `Verifier::update_finalized_payouts` records.

### Finding Description
The broken binding is: `operator_xonly_pk_recorded(withdrawal_idx) == xonly_pk_of_party_whose_wallet_funded_output_0(withdrawal_idx)`.

`create_payout_txhandler` builds the Payout tx with input 0 = the user's withdrawal UTXO, output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(operator_xonly_pk) [1](#0-0)  . The witness set on input 0 is the user's `SinglePlusAnyoneCanPay` signature [2](#0-1) , and `Operator::withdraw` verifies that signature only covers input 0/output 0 via `calculate_sighash_txin(0, sighash_type)` before funding the tx with the operator's own additional inputs/change through `fund_raw_transaction` [3](#0-2) . Because `SIGHASH_SINGLE|ANYONECANPAY` signs nothing about other inputs, the anchor output, or the OP_RETURN output, anyone who sees this transaction (broadcast, unconfirmed) can build a variant that keeps input 0 + output 0 byte-for-byte (so the same valid signature applies), replaces the funding input(s) with their own fee-paying input, and rewrites the OP_RETURN to name a different operator xonly-pubkey. Whichever transaction actually gets mined determines the final txid that spends the withdrawal outpoint.

`Verifier::update_finalized_payouts` finds the winning payout tx purely via the outpoint match in `get_payout_txs_for_withdrawal_utxos` (join on `bitcoin_syncer_spent_utxos.txid/vout == withdrawals.withdrawal_utxo_txid/vout`), with no cross-check that the "extra" funding inputs belong to the named operator [4](#0-3) . It then parses whatever OP_RETURN happens to be in the mined tx and writes that xonly-pubkey as `payout_payer_operator_xonly_pk` [5](#0-4) . `PayoutCheckerTask` and `is_kickoff_malicious` both trust this DB field: the former lets an operator claim any unhandled payout credited to its own xonly-pk via `get_first_unhandled_payout_by_operator_xonly_pk` [6](#0-5) [7](#0-6) ; the latter only checks that the DB-recorded payer equals the kickoff's self-declared operator, not that the payer actually funded the output [8](#0-7) . None of `is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `SPV::verify`, or the presigned tx graph constrain the OP_RETURN contents, since the user signature never covers it.

Exploit flow: operator A broadcasts its Payout tx for withdrawal index i (paying from A's own change/fee input, OP_RETURN = A). An unprivileged attacker copies input 0 + output 0 (valid under the ANYONECANPAY signature), adds their own fee input, sets OP_RETURN = B's public xonly-pk, and broadcasts with a competitive fee/RBF so it gets mined instead of A's version (a plain double-spend race on the shared withdrawal outpoint — no signature forgery needed). Once mined, `update_finalized_payouts` records payer = B for index i. B's own (unmodified) `PayoutCheckerTask` will then autonomously pick up this "unhandled payout" and drive `handle_finalized_payout` → kickoff → `create_reimburse_txhandler`, ultimately spending the move-to-vault UTXO to B's `operator_reimbursement_address`, even though B contributed nothing and A (who actually funded output 0's excess/fees) gets no credit and can never claim reimbursement for that index.

### Impact Explanation
This is Critical: BTC leaves a move-to-vault UTXO to an operator (B) that never funded the corresponding payout, while the operator who actually fronted the withdrawal (A) is permanently unable to be reimbursed for that index (the withdrawal is marked handled once B's flow completes). It is repeatable per-withdrawal and requires no cooperation from B — the attacker only needs B's public xonly-pubkey, which is protocol-public information. The blast radius spans every Payout transaction sent through `create_payout_txhandler`/`Operator::withdraw`, across all deposits and all operators, since the vulnerability is structural to how the OP_RETURN attribution field sits outside the signed message.

### Likelihood Explanation
Preconditions: a Payout tx must be visible unconfirmed (public mempool or even just known ahead of confirmation), and the attacker needs enough BTC to cover a competitive fee for the replacement transaction — a small, one-time cost, no bridge collateral or stake required. The race is a standard "whoever gets mined first" double-spend contest on the shared withdrawal UTXO input, feasible with normal fee-bumping/RBF or same-block competition, and repeatable on every future payout as long as the tx construction and signature scope remain unchanged.

### Recommendation
Sign the OP_RETURN (payer attribution) output under the same commitment as the payout, e.g. change the payout's signing/sighash structure so the OP_RETURN output is covered by a signature scoped to the operator (not just the user's `SinglePlusAnyoneCanPay` signature on output 0), or otherwise bind payer attribution to something unforgeable by third parties (e.g., have the operator's fee-input signatures also cover/commit to the OP_RETURN output, or move the operator-identity commitment into the kickoff-time cryptographic proof rather than trusting a mutable Bitcoin output).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash

             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
