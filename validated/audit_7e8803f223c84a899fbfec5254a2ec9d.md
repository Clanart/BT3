### Title
Payout `OP_RETURN` operator attribution is unauthenticated, letting anyone front a withdrawal and credit a different operator's reimbursement - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the `payout_tx` with an `OP_RETURN` output carrying an arbitrary `operator_xonly_pk` argument that is never cryptographically bound to the transaction. The only signature checked over the transaction is the withdrawing user's `SinglePlusAnyoneCanPay` signature on input 0 [1](#0-0) . Because the sighash type is `SinglePlusAnyoneCanPay`, *anyone* who learns this signature can add funding inputs and finish/broadcast the transaction — the identity of whoever actually funds the payout is decoupled from the `operator_xonly_pk` written into `OP_RETURN`.

### Finding Description
The verifier's block scanner attributes a withdrawal's payout to an operator purely by parsing the `OP_RETURN` push-data of the confirmed `payout_tx`, with zero signature or membership check on that pubkey: [2](#0-1) 

That `operator_xonly_pk` is persisted as `payout_payer_operator_xonly_pk` and is later used as the sole "did-you-pay" credential:
- `PayoutCheckerTask` picks up the "first unhandled payout" **by operator_xonly_pk** and automatically drives that operator's kickoff/reimbursement flow: [3](#0-2)  and [4](#0-3) .
- `validate_payer_is_operator` only checks that the DB-recorded payer pubkey equals the local operator's own key — it never checks that the same operator actually broadcast/funded the transaction: [5](#0-4) .
- `is_kickoff_malicious` also only compares the OP_RETURN pubkey against `kickoff_data.operator_xonly_pk`, again a pure data comparison: [6](#0-5) .

The `payout_tx` itself only requires the withdrawing user's signature over input 0, which is explicitly `SinglePlusAnyoneCanPay`: [7](#0-6) [8](#0-7) 

`ANYONECANPAY` means the signature only commits to input/output 0; any party can attach additional funding inputs (their own BTC) to complete and pay the fixed user output, and can freely choose *any* value — including any real operator's public `x-only` pubkey — for the `OP_RETURN` push data, since `create_payout_txhandler` places it unsigned: [9](#0-8) 

`operator_xonly_pk` values are public (they are the registered operators' public keys shared via `fetch_operator_keys`/`DepositData.actors.operators`, cf. their use in `AggregatorWithdrawalInput`/`current_operator_xonly_pks` checks: [10](#0-9) ), so no secret is required to pick a victim operator to credit.

The user's `input_signature` needed to complete the transaction is not kept secret to a single trusted operator either — the aggregator's `Withdraw` RPC by design can forward the same `WithdrawParamsWithSig` (including `input_signature`) to *all* registered operators when the caller's `operator_xonly_pks` list is empty: [11](#0-10) . Any one of those operators (or anyone who otherwise obtains the broadcast/relayed signature) can build and fund a competing `payout_tx` naming an arbitrary other operator in the `OP_RETURN`, since nothing in `create_payout_txhandler` verifies that the constructing/funding party's identity matches the `operator_xonly_pk` argument.

This is the direct analog of the EIP-2981 report's core defect: one path (the intended operator-front-and-reimburse flow) is meant to bind "the party credited with reimbursement" to "the party that actually paid," but a parallel/bypassable path (anyone funding the same `payout_tx` with `ANYONECANPAY` and choosing their own OP_RETURN data) breaks that binding entirely, exactly matching the listed bridge-custody equality: "the operator credited versus the party that paid."

### Impact Explanation
An attacker (not necessarily a registered operator) who obtains the user's `SinglePlusAnyoneCanPay` withdrawal signature can front the withdrawal using their own funds while writing a legitimate, unrelated operator's `x-only` pubkey into the `OP_RETURN` output. The verifiers' automated payout tracking (`update_finalized_payouts` → `get_first_unhandled_payout_by_operator_xonly_pk` → `PayoutCheckerTask` → `handle_finalized_payout`) then credits and drives reimbursement for the *named* operator, who receives the vault's `bridge_amount` reimbursement via the standard round/kickoff/reimburse machinery, despite having fronted nothing. This is a misattributed reimbursement — funds intended to compensate the actual funder are instead awarded to an operator that never paid, directly matching the Critical impact category "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
Reachable by an unprivileged actor with no special role: the only prerequisite is knowledge of a user's already-issued `SinglePlusAnyoneCanPay` withdrawal signature and public `x-only` pubkeys of registered operators (both are either broadcast to multiple operators by design, or become public once the withdrawal transaction propagates on the Bitcoin network). No verifier/operator/watchtower privilege, key compromise, or misconfiguration is required — the `OP_RETURN` attribution is unconditionally unauthenticated in `create_payout_txhandler`.

### Recommendation
Cryptographically bind the `operator_xonly_pk` committed in the payout transaction's `OP_RETURN` to the actual funder, e.g. by requiring the operator to sign a commitment over the `OP_RETURN` data (or over the whole payout tx) with their registered key, and have verifiers validate that signature during `update_finalized_payouts` before recording `payout_payer_operator_xonly_pk`. Alternatively, require the additional funding inputs added via RBF/PSBT to be provably controlled by the operator whose key appears in the `OP_RETURN` (e.g., verifying that funding UTXOs come from that operator's registered wallet address) before attributing the payout.

### Proof of Concept
1. Attacker obtains a pending withdrawal's `WithdrawParams` (input_signature, input_outpoint, output_script_pubkey, output_amount) — e.g. by being one of several operators the aggregator's `Withdraw` RPC broadcasts to (`operator_xonly_pks` empty case), or by observing it once relayed/broadcast.
2. Attacker (who is not the intended operator, or is even a completely different unprivileged party who anyone can complete an ANYONECANPAY tx) builds a `payout_tx` per `create_payout_txhandler`, using the honest user's signature on input 0 (`SpendPath::KeySpend`), adding a funding input of their own to cover `output_amount` + fees, and setting `operator_xonly_pk` in the `OP_RETURN` to `OperatorV`'s (victim's) registered public key instead of their own. [1](#0-0) 
3. Attacker broadcasts this transaction to Bitcoin; it confirms.
4. Verifiers' `update_finalized_payouts` scans the block, parses the `OP_RETURN`, and records `payout_payer_operator_xonly_pk = OperatorV` [12](#0-11) .
5. `OperatorV`'s `PayoutCheckerTask` (running with automation enabled) picks up this "unhandled payout" attributed to itself [3](#0-2) , and drives `handle_finalized_payout` → kickoff → reimburse, ultimately paying `OperatorV` the vault's `bridge_amount`, even though `OperatorV` never funded the withdrawal.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
