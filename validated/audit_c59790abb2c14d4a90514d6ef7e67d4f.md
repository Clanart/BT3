## Analysis

The reported bug-class ("some ERC20 tokens like USDT don't revert or return values consistently on `transfer()`/`transferFrom()` — use OpenZeppelin's `SafeERC20`") has a direct, provable local analog in the **Tron variant of `IntentGatewayV2`**, where the escrow-redemption path still performs raw low-level `.call()` transfers and checks only that the *call itself* didn't revert, never checking the ERC20's returned boolean success value — despite the contract already importing and partially using `SafeERC20` elsewhere.

### Title
Escrow withdrawal accepts ERC20 `transfer()` calls that return `false` without reverting, permanently locking escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (Tron contracts variant) and its `onAccept` `SweepDust` handler move escrowed tokens to the beneficiary using a raw low-level call to the `transfer` selector, checking only the `success` boolean of the low-level `call` (i.e., that the call did not revert) — not the ERC20 return-data boolean that indicates whether the transfer itself actually succeeded. This is precisely the class of bug the external report flags: ERC20 tokens that return `false` on failure instead of reverting (or otherwise don't strictly follow the standard) will be silently treated as a successful transfer.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` releases escrowed tokens: [1](#0-0) 

and its `SweepDust` handler in `onAccept`: [2](#0-1) 

Both do:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only verifies that the external call did not revert. It never decodes/checks the returned `bool` value that `transfer()` is supposed to return. A token whose `transfer()` returns `false` on failure (without reverting) — the exact ERC20-noncompliance case the SafeERC20 report calls out — will make `success == true` even though no tokens moved.

Crucially, the state is mutated *before* this check has any real bite: `_filled[body.commitment] = beneficiary` is set unconditionally at the top of `withdraw()`, and each token's escrow balance is decremented (`_orders[body.commitment][token] -= amount`) right after the no-op "successful" transfer: [1](#0-0) 

The contract does import `SafeERC20` and even uses `safeTransferFrom` for escrow intake (`evm/tron/contracts/apps/IntentGatewayV2.sol:399`), so the library is available — it is simply not applied consistently to the outbound `withdraw()`/`SweepDust` paths, unlike the equivalent EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol:408`, `evm/src/apps/intentsv2/IntentsBase.sol:416`) which uses `IERC20(token).safeTransfer(...)` for the exact same operation.

### Impact Explanation
Once `withdraw()` runs against a non-standard ERC20 (e.g., a token that returns `false` instead of reverting on a blacklist/pause/insufficient-balance condition), the contract:
1. Marks the order as filled/refunded (`_filled[commitment] = beneficiary`) and emits `EscrowReleased`/`EscrowRefunded`.
2. Decrements `_orders[commitment][token]` to zero, even though the beneficiary received nothing.

Because `_orders[commitment][token]` is now zero, any retry attempt reverts with `UnknownOrder()` on the next `withdraw()` call for that commitment/token. The escrowed tokens remain stuck in the `IntentGatewayV2` contract with no code path left to release them to the rightful beneficiary — a direct, unauthorized loss/lock of user or solver funds, matching the bounty's "stealing or loss of funds" impact class.

### Likelihood Explanation
This requires no malicious relayer, prover, or governance actor — it is triggered purely by using (or being forced to use, since token choice for `order.inputs`/fees is set by the order-placing user) any ERC20 whose `transfer()` can return `false` without reverting under some condition (blacklist checks, paused states, insufficient balance guarded internally, etc.). This is realistic on many chains/tokens and is exactly the scenario OpenZeppelin's `SafeERC20` guidance exists to prevent, which the project has already acknowledged and partially fixed elsewhere (main EVM `IntentsBase.sol`) but not in this Tron contract copy.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)` (the library is already imported and used via `using SafeERC20 for IERC20;`), consistent with the pattern already applied in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with escrow token `T` that implements `transfer()` to return `false` (not revert) whenever the recipient is on an internal denylist, or under some balance/pause condition — a valid, non-malicious ERC20 implementation choice.
2. User places a cross-chain order escrowing `T` as an input; solver fills the order on the destination chain, triggering a `RedeemEscrow` request back to source.
3. Source-chain `onAccept` calls `withdraw()`, which calls `T.call(transfer(beneficiary, amount))`; `T.transfer` returns `false` without reverting (e.g., beneficiary transiently denylisted, or a race with a pause) → `success == true` from the low-level call.
4. `_orders[commitment][T]` is decremented to 0, `_filled[commitment]` set, `EscrowReleased` emitted — but `beneficiary`'s `T` balance did not change.
5. Any later attempt to redeem/refund this commitment for `T` reverts with `UnknownOrder()`; the escrowed `T` tokens are permanently stuck in the `IntentGatewayV2` contract. [3](#0-2) [4](#0-3)
