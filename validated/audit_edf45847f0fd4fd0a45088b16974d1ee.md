Audit Report

## Title
Unbounded per-epoch iteration over attacker-growable `Stakes::stake_delegations` set enables validator-wide compute exhaustion at epoch boundaries - (File: `runtime/src/stakes.rs`)

## Summary
`Stakes::stake_delegations` is only pruned when a stake account's lamports reach exactly zero, as implemented in `StakesCache::check_and_store` [1](#0-0)  . Every validator, on every epoch boundary, unconditionally collects and fully iterates this entire map via `stake_delegations_vec()`, `calculate_activated_stake()`, and `calculate_delegated_stakes()` with no upper bound on set size [2](#0-1) [3](#0-2) [4](#0-3)  . An unprivileged actor can create stake accounts, delegate the required minimum, deactivate, and optionally withdraw the delegated amount back out — leaving only the rent-exempt reserve locked — while the account entry persists indefinitely in `stake_delegations`, since deactivation and partial withdrawal do not trigger removal.

## Finding Description
`StakesCache::check_and_store` calls `remove_stake_delegation` only in the `account.lamports() == 0` branch [1](#0-0)  . A deactivated stake account that still holds its rent-exempt reserve balance (non-zero lamports) is never removed from the map. This is corroborated by the test at `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` (`test_adjust_delegation_for_prestaked_vote_account`), which demonstrates a stake account with `delegation.stake == 0` after deactivation still existing as a live account entry with non-zero lamports [5](#0-4)  .

The minimum-delegation guard (`get_minimum_delegation`, currently 1 SOL) is enforced only at delegate time in client tooling (e.g., `cli/src/stake.rs::process_delegate_stake` checks `stake_account_lamports < minimum_total_lamports` before submitting the `DelegateStake` instruction) [6](#0-5)  and in `stake_utils::get_minimum_delegation` [7](#0-6)  . Nothing in `check_and_store`, `calculate_activated_stake`, or `calculate_delegated_stakes` enforces a cap on `stake_delegations.len()`; the minimum-delegation invariant only gates the *active* delegated amount, not continued account/map membership after deactivation.

At every epoch boundary, `Bank::compute_new_epoch_caches_and_rewards` collects the full map into a `Vec` and passes it into `calculate_activated_stake`, which does an O(N) parallel fold/reduce with no bound [8](#0-7) [3](#0-2)  . Epoch reward computation performs an equivalent full-set walk, and the code's own comment acknowledges N can exceed 1,000,000 without imposing a cap [9](#0-8)  .

## Impact Explanation
Growing `stake_delegations` unboundedly increases the fixed per-epoch computational cost every validator must pay synchronously during epoch-boundary bank processing, which is on the critical path for producing/validating the first block(s) of a new epoch. Because the cost scales with total network-wide account count rather than any single validator's resources, an unprivileged attacker paying only the rent-exempt reserve per "ghost" stake account (rather than the 1 SOL minimum delegation, which is not required to remain delegated at that minimum once deactivated) can force this cost to grow for the entire validator fleet indefinitely, with no cap and no automatic pruning mechanism besides the account owner voluntarily closing the account.

## Likelihood Explanation
The attack requires no special privilege — only ordinary `CreateAccount`/`DelegateStake`/`Deactivate`/`Withdraw` instructions against the stake program — and the marginal cost per retained "ghost" entry is bounded by the stake-account rent-exempt reserve (`StakeStateV2::size_of()` minimum balance). It is a slow, capital-scaling attack: reaching a scale where per-epoch iteration cost becomes materially disruptive requires creating and funding a very large number of accounts, which costs real (if individually small) SOL and consumes blockspace/fees to submit, making it a real but currently unmitigated design gap rather than an immediately catastrophic exploit.

## Recommendation
- Impose an explicit upper bound on the number of stake-delegation entries retained globally or per validator, rejecting new delegations once the cap is reached.
- Require the minimum-delegation invariant to also apply to inactive/deactivated stake accounts after a grace period, or make rent-exempt-only, zero-effective-stake accounts eligible for lazy pruning from `stake_delegations` without requiring an explicit close instruction.
- Alternatively, maintain a secondary index of only currently-delegated, non-zero-effective-stake accounts so that growth of closed/deactivated ghost accounts does not inflate the hot-path iteration cost in `calculate_activated_stake`/`calculate_delegated_stakes`.

## Proof of Concept
1. Repeat N times with fresh keypairs: `CreateAccount` a stake account funded with `rent_exempt_reserve + minimum_delegation`, `DelegateStake` to any active vote account, wait one epoch, then `Deactivate`, optionally followed by `Withdraw` of the delegated 1 SOL, leaving only the rent-exempt reserve.
2. None of these accounts are removed from `Stakes::stake_delegations` because `StakesCache::check_and_store` only removes on `lamports() == 0` [1](#0-0)  .
3. On every subsequent epoch boundary, `Bank::compute_new_epoch_caches_and_rewards` calls `stakes.stake_delegations_vec()` then `stakes.calculate_activated_stake(...)`, both iterating the full, inflated set [8](#0-7)  .
4. Measure epoch-boundary processing time as N grows; cost scales linearly with attacker-controlled N with no enforced cap.
