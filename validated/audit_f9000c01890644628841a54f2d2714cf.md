### Title
NULL pointer dereference in `SetCodeTx.AsEthereumData()` when `To` field is empty - ([File: x/evm/types/ethtx/set_code_tx.go])

### Summary
Analogous to the OpenSSL CMS bug (dereferencing an optional ASN.1 field without checking presence), `SetCodeTx` (EIP-7702) treats its `To` address as optional during validation but then unconditionally dereferences the nil pointer that `GetTo()` returns for that case.

### Finding Description
`SetCodeTx.Validate()` only checks the format of `tx.To` *if it is non-empty*: `if tx.To != "" { ValidateAddress(tx.To) }` [1](#0-0) . It never requires `To` to be present, so a `SetCodeTx` with an empty `To` string passes `Validate()`.

`GetTo()` returns a **nil** `*common.Address` when `tx.To == ""`: [2](#0-1) 

`AsEthereumData()` unconditionally dereferences that pointer: `To: *tx.GetTo()`: [3](#0-2) 

This is exactly the CMS bug pattern: an "optional" field is not checked for presence before being dereferenced, causing a NULL/nil pointer panic. Note the sibling type `BlobTx.GetTo()` correctly guards against this by returning `&common.Address{}` instead of `nil` when `To` is empty [4](#0-3) , confirming `SetCodeTx` is the inconsistent/vulnerable case.

`MsgEVMTransaction.ValidateBasic()` unpacks the `Any`-encoded `TxData` and calls `txData.Validate()` for any non-`AssociateTx` type [5](#0-4) , which — as shown — accepts a `SetCodeTx` with empty `To`. Later, numerous call sites unconditionally invoke `AsEthereumData()`/`AsTransaction()` on the unpacked `TxData`, e.g. `MsgEVMTransaction.AsTransaction()` [6](#0-5) , the ante-handler signature/preprocessing paths (`ethtypes.NewTx(txData.AsEthereumData())`) in `PreprocessUnpacked` [7](#0-6)  and `CheckAndDecodeSignature` [8](#0-7) , and RPC transaction encoding paths such as `getEthTxForTxBz` [9](#0-8) . Any of these paths reached with a crafted `SetCodeTx` with an empty `To` field triggers the nil-pointer panic.

### Impact Explanation
A nil-pointer panic in `AsEthereumData()` is reached by `PreprocessUnpacked`/`CheckAndDecodeSignature` inside the ante-handler pipeline that runs for every submitted transaction (CheckTx, DeliverTx/FinalizeBlock, and RPC simulate paths). If unrecovered on a critical path, this can crash node processing of a block or a `CheckTx`/RPC request, i.e. a public-RPC/validator DoS from an unprivileged sender submitting a single crafted EVM transaction (SetCodeTx / EIP-7702 type with `To` unset).

However, several of these call sites are wrapped with `recover()` (e.g. `App.GetEVMMsg` [10](#0-9) , `DecodeTransactionsConcurrently` [11](#0-10) , `GetTxPriorityHint` [12](#0-11) ), which appear specifically designed to guard against exactly this class of DoS. I was not able to fully trace, within the remaining budget, whether the FinalizeBlock/DeliverTx execution path that calls `PreprocessUnpacked` -> `AsEthereumData()` is itself wrapped in an equivalent panic recovery, or whether it would propagate to a full node crash (block-processing halt) versus a per-tx rejection.

### Likelihood Explanation
An unprivileged EVM transaction sender can construct a `MsgEVMTransaction` wrapping a `SetCodeTx` payload directly (bypassing normal go-ethereum tx encoding, since Sei EVM transactions are wrapped as Cosmos `Any` messages) with `To == ""`. Since `Validate()` does not require `To` and EIP-7702 semantically requires `To` to be the tx's target address, this is a plausible/simple crafted-input attack, directly analogous to the CMS "optional field silently absent then dereferenced" bug class.

### Recommendation
In `x/evm/types/ethtx/set_code_tx.go`:
1. Make `SetCodeTx.Validate()` require `tx.To != ""` (EIP-7702 requires a `to` address; it should not be treated as optional), matching the semantics enforced elsewhere for required fields, or
2. Make `GetTo()` defensively return `&common.Address{}` instead of `nil` when `tx.To == ""`, consistent with `BlobTx.GetTo()`, so `AsEthereumData()`'s dereference cannot panic regardless of upstream validation gaps.

### Proof of Concept
1. Construct a `SetCodeTx{GasTipCap: <valid>, GasFeeCap: <valid>, To: "", V/R/S: <valid 32-byte values>, ChainID: <valid>}` (all required-by-`Validate()` fields populated, `To` left empty).
2. Wrap it via `NewMsgEVMTransaction(txData)` into a `MsgEVMTransaction`, encode as a Cosmos tx, and submit via `broadcast_tx`/CheckTx or directly via the mempool/RPC.
3. `MsgEVMTransaction.ValidateBasic()` calls `txData.Validate()`, which passes because `To == ""` skips the address check [1](#0-0) .
4. When the ante pipeline or RPC path calls `txData.AsEthereumData()` (e.g. via `PreprocessUnpacked` [7](#0-6)  or `CheckAndDecodeSignature` [8](#0-7) ), `*tx.GetTo()` dereferences the nil pointer, causing a Go runtime panic.

I could not fully confirm within this session whether all reachable call paths from `CheckTx`/`FinalizeBlock` are protected by an enclosing `recover()`, which is necessary to determine whether the ultimate impact is "graceful tx rejection" (low severity) or "node/block-processing crash" (the higher severity implied by the CMS analog). This should be verified with a live reproduction against `EvmCheckTxAnte`/`EvmDeliverTxAnte` before treating this as a confirmed high-severity DoS.
