### Title
Unsanitized `{rule-name}` substitution in `/hookify` file-write path enables `.claude/` directory traversal - ([File: plugins/hookify/commands/hookify.md])

### Summary
The `/hookify` slash command instructs Claude to substitute an attacker-influenceable `rule-name` value directly into the literal path template `.claude/hookify.{rule-name}.local.md` when invoking the Write tool, without any instruction to validate or sanitize the name. Because `rule-name` is derived from `$ARGUMENTS` or from conversation content processed by the `conversation-analyzer` sub-agent, an attacker who controls either can attempt to make Claude choose a `rule-name` containing path traversal sequences, causing the resulting Write path to resolve outside the project's `.claude/` directory.

### Finding Description
`plugins/hookify/commands/hookify.md` defines the entire `/hookify` workflow as natural-language instructions executed by the LLM agent, not as deterministic code with path-resolution guards. Step 1 explicitly feeds `$ARGUMENTS` and/or recent conversation text into the rule-generation flow (lines 19-26), and Step 3/Step 4 tell Claude to pick a `{rule-name}` ("Use kebab-case", "Be descriptive") and then invoke the `Write` tool with the literal template `.claude/hookify.{name}.local.md` (lines 84, 135-137). Nowhere in this file, nor in `plugins/hookify/skills/writing-rules/SKILL.md`, is there an explicit instruction to reject rule names containing `/`, `..`, or absolute-path characters — the "kebab-case" guidance is only a stylistic convention, not an enforced constraint, and there is no supporting deterministic code (e.g., in `plugins/hookify/hooks/*.py`) that validates the rule name before the Write call occurs. Because the Write path is built purely through prompt-driven string substitution performed by the model itself, a sufficiently crafted `$ARGUMENTS` string or injected conversation content (read by the `conversation-analyzer` general-purpose sub-agent) could induce Claude to choose a `rule-name` such as `../../../etc/cron.d/x`, producing a Write target of `.claude/hookify.../../../etc/cron.d/x.local.md`, which normalizes outside the intended `.claude/` directory.

### Impact Explanation
If successful, this could allow an unprivileged prompt-injection attacker (via slash-command arguments or planted conversation content) to cause an arbitrary file write outside the project workspace, breaking the WORKSPACE_CONFINEMENT invariant. Depending on the underlying OS file permissions and what path is targeted (e.g., cron directories, shell rc files, other project directories), this could lead to persistence or code execution outside the intended `.claude/` sandbox.

### Likelihood Explanation
Exploitability depends entirely on whether the underlying Write tool (part of Claude Code core, not visible in this repository) performs its own path-confinement/allowlist checks independent of what this markdown file instructs. This repository only contains the plugin-level prompt instructions; it does not contain the actual Write-tool implementation, so I cannot confirm from this codebase alone whether Claude Code's core Write tool already blocks path traversal outside the working directory (which is a common baseline protection in coding agents). Because of this missing piece, and because exploitation also requires successfully steering the LLM's free-text rule-name choice via prompt injection (not a guaranteed deterministic outcome), the likelihood is moderate/uncertain rather than confirmed.

### Recommendation
Add an explicit, enforced constraint in `plugins/hookify/commands/hookify.md` (and the `writing-rules` skill) requiring the rule name to match a strict allowlist regex (e.g. `^[a-z0-9-]+$`) before it is used in the Write path template, and instruct Claude to reject/re-prompt if the name contains `/`, `\`, `..`, or is empty. Since this command has no deterministic enforcement code, consider adding a lightweight pre-write validation hook (similar to `plugins/hookify/hooks/pretooluse.py`) that inspects Write calls targeting `.claude/hookify.*.local.md` and rejects any resolved path whose `realpath` is not a descendant of `{cwd}/.claude`.

### Proof of Concept
Unit/integration test plan (to be run against whatever component ultimately resolves and executes the Write call, e.g. a hook or the Write tool wrapper, since this repo only defines the prompt template):
1. Simulate the Step 3/Step 4 template substitution: `path = ".claude/hookify.{}.local.md".format(rule_name)` for `rule_name = "../../../etc/cron.d/x"`.
2. Assert that `os.path.realpath(os.path.join(cwd, path))` is NOT a descendant of `os.path.realpath(os.path.join(cwd, ".claude"))` — demonstrating the escape is possible given the current unsanitized template.
3. Add a fuzz test enumerating rule names containing `../`, absolute paths (`/etc/x`), and null-byte/URL-encoded traversal sequences, asserting that after the recommended validation regex is applied, all such inputs are rejected before reaching the Write call.
4. Because the actual Write-tool enforcement lives outside this repository, this PoC can only conclusively validate the *prompt template's lack of sanitization*; confirming exploitability end-to-end requires testing against the live Claude Code Write tool to see whether it independently enforces workspace confinement.
