### Title
Malformed `clone_url` bypasses the URL-equality guard in `updateRemoteUrl`, causing the local git remote to be silently rewritten with attacker-controlled data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` is meant to only rewrite the local git remote's URL when the GitHub API's `clone_url` genuinely differs from what's already configured (`!urlsMatch`), and only when the user hasn't manually diverged their remote from the previously known `cloneURL` (`remoteUrlUnchanged`). Because `urlMatchesRemote` treats *any* unparseable URL as "not matching" rather than as "unknown," an attacker-influenced `clone_url` value that `parseRemote` cannot parse will always satisfy `!urlsMatch`, defeating the intended guard.

### Finding Description
`updateRemoteUrl` computes: [1](#0-0) 

`urlMatchesRemote` parses both sides with `parseRemote` and returns `false` whenever either side fails to parse, rather than signaling "indeterminate": [2](#0-1) 

`parseRemote` only recognizes a small set of GitHub-style URL shapes (owner/name pairs); any other well-formed-looking URL string (e.g. missing the owner/name path segments) returns `null`: [3](#0-2) 

The rewrite condition and call site: [4](#0-3) 

Walking through with a `clone_url` such as `"https://evil.example.com/pwned"` (has a scheme, so `URL.parse` still extracts `protocol: "https:"`, but has only one path segment, so `parseRemote`'s regex `^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$` fails to match):

- `urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)` → `parseRemote` returns `null` for the malformed side → function returns `false` → `urlsMatch = false`.
- `protocolsMatch` is computed via Node's legacy `URL.parse`, not `parseRemote`, so it only checks that both strings have the same URI scheme (`https:`); this is independent of whether `parseRemote` can extract owner/name, and remains `true` if the existing remote is also `https`.
- `remoteUrlUnchanged` compares the *previously stored* `gitHubRepository.cloneURL` (a known-good value from an earlier successful fetch) against the current local remote — it has nothing to do with the new, malformed `apiRepo.clone_url`, so in the normal case (remote untouched by the user) it evaluates `true`.
- The overall condition `protocolsMatch && remoteUrlUnchanged && !urlsMatch` becomes `true`, and `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` executes with the unparseable, attacker-influenced string.

This confirms the proof idea: supplying a `clone_url` that `parseRemote` cannot parse causes `urlMatchesRemote` to conservatively report "no match," which — combined with the unrelated `remoteUrlUnchanged` check — always satisfies `!urlsMatch` and forces `setRemoteURL` to run with the malformed value.

### Impact Explanation
The `clone_url` field originates from an `IAPIRepository` object returned by a GitHub API response. Per the review scope, an attacker-controlled "API object" (e.g., a malicious/compromised GitHub Enterprise Server the user has added as an account, or a MITM'd/spoofed API response) is a valid attacker vector. Successfully forcing `setRemoteURL` to run with an attacker-chosen string means the user's local `origin` (or other default remote) can be silently repointed to an attacker-controlled host without any of the intended "did this actually change" safety check applying. Subsequent `git fetch`/`git push` operations against that remote would then silently target the attacker's infrastructure — this is a "silent corruption of what the user commits or pushes" per the accepted impact categories, since the user believes they are still interacting with their legitimate GitHub remote.

I was not able to fully verify, within the available context, whether the raw string is passed to the underlying `git remote set-url` invocation without a `--` separator (which would additionally open a git argument-injection vector if the string begins with `-`). That final sink (`app/src/lib/git/remote.ts`) should be reviewed to determine whether this also enables git flag/argument injection, which would elevate the impact further.

### Likelihood Explanation
The only precondition is that the attacker (or a compromised/rogue GitHub Enterprise Server, or a MITM of an API response the app trusts) can return a `clone_url` value that doesn't match the strict `parseRemote` regexes while still sharing the same URL scheme as the existing remote. This is straightforward to produce and requires no unusual user interaction beyond the app performing its normal periodic API-driven remote-URL reconciliation.

### Recommendation
Change `urlMatchesRemote` (or its caller) to distinguish "confirmed mismatch" from "unparseable/indeterminate," and treat unparseable `clone_url` values as *not eligible* for automatic remote rewriting (i.e., skip the update rather than defaulting to "no match"). Alternatively, in `updateRemoteUrl`, add an explicit `parseRemote(updatedRemoteUrl) !== null` check before allowing `!urlsMatch` to authorize the `setRemoteURL` call.

### Proof of Concept
1. Have a repository whose GitHub-tracked remote (`gitStore.defaultRemote.url`) is `https://github.com/owner/repo.git`, with `gitHubRepository.cloneURL` matching that same URL (so `remoteUrlUnchanged` is `true`).
2. Have the API return (or be made to return, e.g. via a malicious/compromised endpoint) an `IAPIRepository` whose `clone_url` is `https://evil.example.com/pwned` — same scheme (`https:`), but not matching the `owner/name` regex in `parseRemote`.
3. In `updateRemoteUrl`:
   - `urlMatchesRemote("https://evil.example.com/pwned", defaultRemote)` → `false` (`parseRemote` fails) → `urlsMatch = false`.
   - `protocolsMatch` → `true` (`https:` === `https:`).
   - `remoteUrlUnchanged` → `true` (based on prior known-good `cloneURL`, unrelated to the malformed value).
4. `gitStore.setRemoteURL(defaultRemote.name, "https://evil.example.com/pwned")` is invoked, rewriting the local remote to the attacker-controlled URL despite it never having been validated as a legitimate GitHub clone URL. [5](#0-4)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
