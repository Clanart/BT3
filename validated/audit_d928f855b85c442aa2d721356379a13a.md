### Title
WERC20 precompile `Deposit`/`Withdraw` trust `contract.Value()`/`contract.Caller()` without rejecting `DELEGATECALL`/`CALLCODE` context, breaking native/ERC20 balance parity - (File: `precompiles/werc20/tx.go`)

### Summary
This is the same bug class as the ZKsync `DefaultAccount` fallback issue: a system contract that is supposed to behave consistently regardless of how it is invoked (EOA-like / WETH-like) instead trusts EVM call-frame values (`msg.sender`, `msg.value`) that are *inherited* rather than freshly supplied when the contract is reached via `DELEGATECALL`/`CALLCODE`. In Cosmos EVM, the WERC20 precompile's `Deposit` and `Withdraw` transactions read `contract.Caller()` and `contract.Value()` directly and use them to move real bank-module coins, without ever checking that the call is a genuine top-level/`CALL` invocation.

Under a normal `CALL` with value, `contract.Value()` and `contract.Caller()` correctly reflect the actual native coin amount transferred to the precompile's address and the immediate sender. Under `DELEGATECALL` (and `CALLCODE`), the EVM does **not** move any native balance to the callee, yet by EVM design (EIP-7 delegatecall semantics) the delegated frame still reports the *inherited* `msg.value` and `msg.sender` of the outer call — exactly the discrepancy the ZKsync report describes for `DefaultAccount.fallback()`. `werc20.Execute` dispatches to `Deposit` for the `fallback`/`receive`/`deposit` selectors without any guard against this call type: [2](#0-1) 

By contrast, the plain ERC20 precompile at least performs a *partial* mitigation by rejecting any nonzero `contract.Value()` on `Execute` (since ERC20 has no legitimate payable method), but it likewise does nothing to distinguish `CALL` from `DELEGATECALL` for `msg.sender`-based checks such as `Transfer`/`Approve`/`TransferFrom`, which use `contract.Caller()` as the implicit `msg.sender`: [3](#0-2) 

Similarly, the staking precompile's transaction methods (`Delegate`, `Undelegate`, `Redelegate`) validate `msgSender := contract.Caller()` against the message's declared delegator, again without excluding delegatecall/callcode framing: [4](#0-3) [5](#0-4) 

I found integration test coverage showing that the staking precompile explicitly disallows *transactions* via `delegatecall`/`staticcall` at a higher, generic dispatch layer (`expTxPass: false` for `"delegatecall"`), which suggests some existing protection exists somewhere in the precompile invocation path for staking-style precompiles: [6](#0-5) 

However, I was **not able to locate the exact enforcement point** in the reachable code (e.g., in `x/vm` keeper's precompile-call dispatch or `RunNativeAction`) that performs this delegatecall rejection, nor could I confirm within the available tool budget whether this same protection is applied uniformly to the WERC20/ERC20 precompiles' `Deposit`/`Transfer`/`Approve` paths, or only to the staking module's own dispatcher. I also could not verify, from the vendored `core/vm` fork used by this repo, the exact mechanics of `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` in `precompiles/common/precompile.go` (`RunNativeAction`) to determine whether real bank-module coins are moved based on `contract.Value()` irrespective of call type — this is the detail that determines whether the discrepancy is merely a "wrong caller is credited" bug or an actual mintable/duplicable value bug: [7](#0-6) 

### Impact Explanation
If the delegatecall/callcode guard the staking test suite implies is *not* uniformly enforced for the WERC20/ERC20 precompiles' value- and caller-sensitive transaction methods, the consequences are Critical and directly in scope:
- `Deposit` could pay out bank-module coins from the precompile's account to an attacker-chosen `caller` address based on an inherited, non-authoritative `msg.value`, with no corresponding real native-token transfer having occurred — an unauthorized extraction/duplication of spendable value.
- `Transfer`/`TransferFrom`/`Approve` and staking `Delegate`/`Undelegate` authorization checks that compare `contract.Caller()` to a user-supplied "owner"/"delegator" address could be satisfied using an inherited `msg.sender` from an outer frame that the real caller does not control, enabling unauthorized transfers/approvals or unauthorized staking operations on behalf of another account.

### Likelihood Explanation
`DELEGATECALL`/`CALLCODE` to arbitrary addresses, including precompile addresses, is unprivileged and freely available to any contract deployer; the staking test suite's existence of `delegatecall`/`callcode` calling-convention tests confirms this is a well-understood and exercised code path in this codebase, matching the "custom account delegate-calls a default account" scenario from the seed report. The severity/likelihood of this specific analog is **unconfirmed** because I could not verify (within the tool budget) whether the same protective dispatch-layer check demonstrated for staking transactions is also applied to `werc20.Deposit`/`erc20.Transfer`/`erc20.Approve`, nor could I confirm the exact bank-coin movement semantics inside `RunNativeAction`'s `BalanceHandler`.

### Recommendation
- Explicitly reject `DELEGATECALL`/`CALLCODE` framing for all precompile transaction methods that rely on `contract.Caller()` as an implicit `msg.sender` or on `contract.Value()` as an implicit `msg.value` (mirroring the recommended `ignoreInDelegateCall`-style modifier from the seed report), ideally centralized in `cmn.Precompile.RunNativeAction`/`SetupABI` so all precompiles inherit the guard uniformly rather than relying on ad hoc per-precompile checks.
- Audit `precompiles/common/precompile.go`'s `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` to confirm bank-coin movements are gated on the call actually being a value-transferring `CALL`, not merely on `contract.Value()` being nonzero.

### Proof of Concept
Conceptual PoC (root cause confirmed; end-to-end fund-movement impact NOT fully verified against `RunNativeAction`'s balance handler, which I could not fully trace):
1. Attacker deploys contract `X` and sends it a `CALL` with `value = V` native coins (real balance now held by `X`).
2. `X` executes `address(WERC20_PRECOMPILE).delegatecall(abi.encodeWithSignature("deposit()"))`.
3. Inside the delegatecall frame, `contract.Value()` reports `V` (inherited from `X`'s call context per EVM delegatecall semantics) and `contract.Caller()` reports `X`'s original caller — despite no native coins having actually moved to the precompile's address in this frame.
4. `werc20.Deposit` (`precompiles/werc20/tx.go:28-57`) issues `BankKeeper.SendCoins(precompileAccAddr, callerAccAddress, V)` based on these inherited/unauthoritative values. [8](#0-7)

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch {
	case method.Type == abi.Fallback,
		method.Type == abi.Receive,
		method.Name == DepositMethod:
		bz, err = p.Deposit(ctx, contract, stateDB)
	case method.Name == WithdrawMethod:
		bz, err = p.Withdraw(ctx, contract, stateDB, args)
	default:
		// ERC20 transactions and queries
		bz, err = p.HandleMethod(ctx, contract, stateDB, method, args)
	}

	return bz, err
}

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	// ERC20 precompiles cannot receive funds because they are not managed by an
	// EOA and will not be possible to recover funds sent to an instance of
	// them.This check is a safety measure because currently funds cannot be
	// received due to the lack of a fallback handler.
	if value := contract.Value(); value.Sign() == 1 {
		return nil, fmt.Errorf(ErrCannotReceiveFunds, contract.Value().String())
	}

	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	return p.HandleMethod(ctx, contract, stateDB, method, args)
}
