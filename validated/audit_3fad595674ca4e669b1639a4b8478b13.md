Let me look at the key files for the strongest candidate analogs.### Title
`ReceivedOutput::read` accepts an arbitrary scalar offset as an unauthenticated alias for the output's spending key, letting a crafted output shadow its true identity and rendering it unspendable - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The HedgeDoc bug class is "an attacker-chosen alias that is accepted as an identifier and shadows the canonical identifier, causing lookups/spends to resolve against the wrong object." In Serai's Bitcoin wallet, `ReceivedOutput` carries exactly such an alias: a scalar `offset` that declares which tweaked key (`group_key + G·offset`) can spend the associated `TxOut`. `ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` from untrusted bytes without checking that `offset` actually corresponds to `output.script_pubkey`, so an attacker can bind a forged offset to an output and produce a received output that cannot be spent.

### Finding Description
`Scanner` is the authoritative source of `offset`: `Scanner::new`/`register_offset` build `scripts: HashMap<ScriptBuf, Scalar>` mapping each P2TR script to the offset whose tweaked key produced it, and `scan_transaction` only emits `ReceivedOutput`s whose `offset` was recovered from that map (`networks/bitcoin/src/wallet/mod.rs:153-213`). The `offset` is therefore a security-critical alias for the output's spending key.

`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) reconstructs this struct from raw bytes:

- `offset` is read via `Secp256k1::read_F(r)` — any scalar the attacker supplies.
- `output` and `outpoint` are consensus-decoded — the attacker fully controls `output.script_pubkey`.
- No check ties `offset` to `output.script_pubkey` (e.g., re-deriving `p2tr_script_buf(key + G·offset)` and comparing).

The offset is later consumed as ground truth when spending: `SignableTransaction`/`TransactionSignMachine` produce one Schnorr sign machine per input (`networks/bitcoin/src/wallet/send.rs:321-398`), and the per-input machines are re-keyed by each input's offset so that `taproot_key_spend_signature_hash` signatures are produced for `group_key + G·offset`. If the declared offset doesn't match the script's real offset, the resulting signature is for the wrong tweaked key — Bitcoin will reject the spend, and the output is permanently unspendable under this wallet despite being reported as received.

This mirrors CVE-2023-38487: HedgeDoc stored an attacker-supplied `<ALIAS>` that shadowed an existing note's ID without verifying correspondence; here, deserialization accepts an attacker-supplied `offset` that shadows the output's true spending-key identity without verifying correspondence to `script_pubkey`.

### Impact Explanation
Any consumer that obtains `ReceivedOutput`s through `ReceivedOutput::read` rather than `Scanner::scan_transaction` (database reloads, coordinator/peer-provided output sets, scheduled-plan inputs) can be handed outputs whose declared offset aliases a key that doesn't own the `script_pubkey`. Consequences:

- Funds reported as received are not spendable: signing with the wrong per-input offset yields an invalid BIP-340 signature for the real output key, so the input can never be spent through this wallet — an effective loss/freeze of the reported balance.
- Shadowing: a forged `ReceivedOutput` for a real outpoint but bogus offset causes the spend attempt to fail, hiding the genuinely spendable output behind an unusable record (the analog of the note being "effectively hidden").

Severity: Medium — no key material is leaked and no data is destroyed (the UTXO still exists on chain), but availability of funds is lost for any flow trusting the serialized offset.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary: the explicit scope allows untrusted bytes into `ReceivedOutput::read`, and the format (`write`/`serialize`/`read` round-trip) is a plain wire/storage encoding with no integrity tag binding `offset` to `script_pubkey`. Exploitation requires only that an attacker influence the serialized bytes (e.g., a peer-supplied or tampered output record); no private keys, validator status, or collusion is needed. It is not exploitable through `scan_transaction` itself, which derives `offset` internally — hence Medium rather than High.

### Recommendation
Make the offset a verified claim rather than trusted data:

- In `ReceivedOutput::read`, require the caller's base key (or a verification context) and recompute `p2tr_script_buf(key + G·offset)`, rejecting the input unless it equals `output.script_pubkey`; or
- Store/transport only the outpoint and `TxOut`, and re-derive the offset via `Scanner`'s `scripts` map on load, so the alias can never diverge from the canonical identity.

### Proof of Concept
```rust
// Attacker-controlled bytes for ReceivedOutput::read.
// key: the wallet's group key. legit_offset: the true offset for the script.
let key = scanner_base_key();                      // even-Y ProjectivePoint
let legit_offset = Scalar::from(2u64);             // suppose even result
let script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * legit_offset)).unwrap();

let forged = ReceivedOutput {
    offset: Scalar::ZERO,                          // alias: claims external key owns it
    output: TxOut { value: Amount::from_sat(50_000), script_pubkey: script },
    outpoint: OutPoint::new(real_txid, 0),
};
let bytes = forged.serialize();

// Victim deserializes untrusted bytes:
let recv = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(recv.offset(), Scalar::ZERO);           // accepted — no script check

// by offset == 0, producing a signature for `key` instead of `key + G*legit_offset`.
// The taproot key-spend signature fails verification on-chain:
// the output was "received" but is unspendable — the forged alias shadowed it.
```
