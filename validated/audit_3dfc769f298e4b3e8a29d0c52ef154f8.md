### Title
GitHub Desktop explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard during recursive clones, reopening the CVE-2024-32002-class RCE via malicious submodules - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) . This is the exact protection flag that upstream Git introduced to block the `CVE-2024-32002` clone RCE class, where a maliciously crafted repository (case-confusable or symlinked paths inside a nested/submodule `.git` directory) can trick a recursive clone into writing files (including executable hook scripts) outside the intended worktree. By forcing this flag off, Desktop removes the guard for every "Clone from URL" operation and for every recursive submodule fetch triggered from the app, restoring the exact class of attack Git's own maintainers shipped a fix for.

### Finding Description
Git's clone protection (`clone.protectNTFS`/`clone.protectHFS` predecessors, unified as `GIT_CLONE_PROTECTION_ACTIVE` in the CVE-2024-32002 fix) rejects paths during clone/checkout that could resolve, via case-insensitive filesystem tricks or embedded symlinks, to a location outside the repository root — most dangerously, a location inside `.git/hooks` or another repo's `.git` directory reached through a malicious submodule. Desktop's `clone()` function passes `--recursive` (auto-fetching all submodules the remote repository defines) while simultaneously forcing `GIT_CLONE_PROTECTION_ACTIVE=false` in the child git process's environment [2](#0-1) . That means:

- The attacker fully controls the remote repository content (a public repo the victim is enticed to clone via a link/deep-link, or a fork/PR the victim opens through Desktop's "clone" flow).
- The attacker can define a submodule (or a nested tree with a crafted case-only-differing path) that, absent the protection, resolves outside the intended target directory.
- Desktop's own path-traversal guard, `isClonePathSensitive` [3](#0-2) , only validates the *top-level clone destination* the user chose — it does nothing to constrain how git resolves symlinked/case-confusable paths for files written *during* the recursive clone/checkout, which is precisely what `GIT_CLONE_PROTECTION_ACTIVE` is designed to police. The `resolveWithin` protections seen elsewhere in the codebase (e.g. Copilot conflict resolution, `openRepositoryFromUrl`) are likewise not invoked as part of the low-level `clone`/submodule checkout path, so there is no equivalent safety net at this layer [4](#0-3) .

This directly parallels the report's "broken invariant" bug class: a protective check that the underlying primitive (Uniswap's gas-limit guard / Git's clone-protection guard) is *supposed to enforce unconditionally* is instead disabled/insufficient in the caller, letting attacker-supplied input (a malicious position/subscriber contract vs. a malicious repository) drive the system into a state the guard exists specifically to prevent.

### Impact Explanation
If exploitable end-to-end (git version dependent — the protection is opt-in via env var specifically so callers can decide, and Desktop chose to always turn it off), a victim who clones or fetches-with-submodules a malicious repository through Desktop could have arbitrary files written outside the intended repository directory, including into another repository's `.git/hooks`, which git will subsequently execute — i.e., attacker-controlled code execution on the victim's machine purely from an unprivileged, attacker-controlled git remote. This matches the valid-impact bar: attacker controls a cloned/fetched repository, result is code execution / file write outside the repo.

### Likelihood Explanation
Every "Clone repository" action and every recursive submodule fetch in Desktop passes through this code path, and the disabling is unconditional (not feature-flagged, not limited to trusted hosts) [5](#0-4) . No additional user action beyond cloning a repository or opening a shared clone URL (which Desktop supports via `x-github-client://` deep links, see `openRepositoryFromUrl`) is required — this is a normal, expected user workflow, not an "unnatural step."

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default (protection enabled) for `clone --recursive`, and if a legitimate compatibility reason exists for disabling it (e.g. a specific dugite/git version bug), gate the override behind a verified need and add Desktop-side path validation for every file materialized during recursive submodule checkout (mirroring the `resolveWithin` guard already used in `copilot-conflict-context.ts` and `openRepositoryFromUrl`) so that submodule-introduced paths are also confined to the clone destination.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule (or `.gitmodules` entry) engineered to exploit case-insensitive or symlink path confusion against `.git`-adjacent locations (the same payload shape documented in the public CVE-2024-32002 advisory/PoC).
2. Attacker sends the victim a link to clone this repository through GitHub Desktop (e.g. "Open in Desktop" or a raw clone URL).
3. Victim clicks "Clone" in Desktop; Desktop invokes `git … clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set [1](#0-0) .
4. Because the protection is disabled, git performs the recursive submodule checkout without validating the crafted paths, allowing the malicious payload to land outside the intended repository directory (e.g., into a hooks directory that later executes).

Note: I was not able to execute an actual git clone against dugite's bundled git version to confirm the currently-bundled version is still vulnerable to the underlying CVE-2024-32002 payload shapes (this depends on the exact git version dugite ships and whether it retained the vulnerable code path when the protection is toggled off) — this would need to be verified in a live environment/dugite version check, which is outside what static code search can confirm.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
