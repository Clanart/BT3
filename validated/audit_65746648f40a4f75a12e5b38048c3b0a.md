Confirmed: `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` straight to disk with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages it with `git add` [1](#0-0) , with no check that the reassembled content is free of leftover conflict-marker text. That confirms the sink for the desync bug identified below.

### Title
Desynchronized conflict-marker parsing between `extractConflictHunks` and `reassembleResolvedFile` lets a crafted repo file smuggle stray git conflict-marker text into a Copilot-resolved commit - ([File: app/src/lib/copilot-conflict-context.ts / app/src/lib/copilot-conflict-resolution.ts])

### Summary
Like the VADER oracle, which independently derived `totalUSD` and `totalUSDV` from the same pair data using two different, incompatible aggregation passes and combined them without verifying unit consistency, GitHub Desktop's Copilot conflict-resolution pipeline parses the *same* on-disk file content twice with two independently maintained marker-scanning routines — `extractConflictHunks` (used to build the prompt) and `reassembleResolvedFile` (used to splice the model's per-hunk answers back into the file) — and stitches their outputs together "by order, not by line number" with no cross-check that the two passes agree on hunk boundaries. A crafted conflicted file can make the two scanners disagree, causing the model's resolution for one hunk to be spliced past a decoy marker while the real trailing conflict-marker line is preserved verbatim in the file that gets written to disk and `git add`-ed.

### Finding Description
`extractConflictHunks` locates the "theirs" close of a hunk by scanning forward for **the first** line matching `^>{7}(?:\s|$)` [2](#0-1) . `reassembleResolvedFile` re-parses the identical raw text independently, using its own copy of the same marker regexes, also stopping at **the first** `^>{7}(?:\s|$)` line found after a `=======` [3](#0-2) . Both routines are naive first-match scanners with no verification that the "theirs" content itself is free of marker-shaped lines, and no cross-check ties the number/boundaries of hunks the model was shown to the boundaries used when splicing its answer back in.

If a conflicted file's "theirs" content contains a line that itself matches `^>{7}(?:\s|$)` (e.g. a decoy `>>>>>>> BOGUS` line placed by whoever authored the incoming branch/commit), both `extractConflictHunks` and `reassembleResolvedFile` will treat that decoy line as the hunk's closing marker. Everything after the decoy — including the real trailing content and the *actual* `>>>>>>> feature` marker — falls outside the recognized hunk in both passes and is copied through as ordinary, unmodified file content in `reassembleResolvedFile`'s "else" branch [4](#0-3) . The model only ever saw and resolved the truncated hunk (`extractConflictHunks` never surfaces the trailing real content as a hunk, only as `contextAfter` for display) [5](#0-4) , so nothing in the pipeline flags that a genuine `>>>>>>> feature` marker is about to be committed.

The only marker-scrubbing safeguard, `parseCopilotConflictResolution`, checks *only* the model's own `resolvedContent` string for embedded markers [6](#0-5)  — it never re-validates the fully reassembled file produced by `reassembleResolvedFile`/`reassembleResolutions` [7](#0-6) . The reassembled content is then written directly to disk and staged with no further inspection [1](#0-0) .

### Impact Explanation
This is exactly the "silent corruption of what the user commits or pushes" impact category. The victim clicks "Resolve with Copilot" → "Continue Merge", the UI reports the conflict as fully resolved, but the resulting file that gets committed and potentially pushed contains a real, un-scrubbed `>>>>>>> <ref>` git conflict-marker line embedded in otherwise normal code — silently, without any warning, diff review by the user, or validation error. Beyond just breaking builds/parsers, an attacker who controls the "theirs" branch content (e.g., a malicious PR the victim merges, or a compromised remote/fetch source) can deliberately plant the decoy marker line to make the automatic reassembly desynchronize from the true marker boundaries, causing arbitrary trailing content on that side of the conflict to bypass model review and land in the final commit unexamined.

### Likelihood Explanation
The trigger is a single, purely textual line (`>>>>>>>` followed by any word or nothing, at column 0) inside the "theirs" content of a real conflict — fully attacker-controlled from a cloned/fetched branch, requiring no local access, no admin rights, and no unusual user action beyond the normal "resolve with Copilot" flow that Desktop already promotes for merge conflicts. The existing unit tests only cover markers embedded *mid-line* (not at column 0) and simple non-adjacent hunks [8](#0-7) , so this specific decoy-at-line-start, cross-function desync scenario is unverified and unguarded.

### Recommendation
- Have `reassembleResolvedFile` consume the exact hunk boundaries already computed by `extractConflictHunks` (e.g., pass hunk start/end line indices through the pipeline) instead of independently re-deriving them with a second regex scanner.
- After reassembly, run a final validation pass over the *entire* reassembled file content checking for any remaining `^<{7}`, `^={7}$`, or `^>{7}` lines and refuse to write/stage the file if any are found, surfacing it as a skipped/failed file instead.
- Add tests where the "theirs" (or "ours"/base) content of a real conflict itself contains a column-0 `>>>>>>>`/`=======`/`<<<<<<<`-shaped line, asserting the reassembled output is bit-for-bit correct and marker-free.

### Proof of Concept
Conflicted file on disk before resolution:
```
<<<<<<< HEAD
real ours line 1
=======
attacker theirs content that includes a bogus marker line:
>>>>>>> BOGUS
more theirs content that should have been part of the conflict
>>>>>>> feature
```
1. `extractConflictHunks` (see `app/src/lib/copilot-conflict-context.ts:228-242`) closes the hunk at the `>>>>>>> BOGUS` line; `theirsContent` sent to the model is only `"attacker theirs content that includes a bogus marker line:"`, and `"more theirs content..."` plus the real `>>>>>>> feature` marker are never included as hunk content (only as unreviewed `contextAfter`).
2. The model returns one resolution for the single hunk it was shown.
3. `reassembleResolvedFile` (see `app/src/lib/copilot-conflict-resolution.ts:559-591`) independently re-scans the same file, also stops at `>>>>>>> BOGUS`, splices in the model's resolution there, then copies `"more theirs content..."` and the literal `>>>>>>> feature` line straight through unchanged.
4. `_applyCopilotConflictResolutions` writes this result to disk and `git add`s it [1](#0-0) , so the committed file silently contains a stray `>>>>>>> feature` conflict-marker line that the UI never flagged as unresolved.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
