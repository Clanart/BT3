### Title
Unauthenticated `internal_send_tx` allows premature broadcast of any queued time-sensitive transaction, breaking `CALLER_AUTHORITY` - ([File: core/src/servers.rs], [File: core/src/rpc/interceptors.rs])

### Summary
When `client_verification` is `false` (the documented default aggregator deployment mode), `create_grpc_server` installs `Interceptors::Noop` instead of `OnlyAggregatorAndSelf`, so no peer-certificate check is ever performed on the aggregator's gRPC port. `internal_send_tx` (and any `Internal*` method) is therefore reachable by anyone who can open a TCP connection to the port, with no TLS client certificate at all.

### Finding Description
The binding the codebase intends: caller of `internal_send_tx` == a party holding `our_cert` (i.e., only the aggregator/self can invoke `Internal*` RPCs), enforced by `only_aggregator_and_self` checking `is_internal(&req)` against `leaf_cert == our_cert` [1](#0-0) .

That check is only wired in when `config.client_verification` is `true`; otherwise `create_grpc_server` uses `Interceptors::Noop`, which unconditionally passes every request through with no certificate inspection at all [2](#0-1) . The only signal about this misconfiguration is a `tracing::warn!` emitted when verification is *enabled* — there is no warning, error, or refusal-to-start when it is *disabled* [3](#0-2) .

Given `client_verification=false`, the equality "caller == holder of our_cert" degenerates to "caller == anyone", because `Interceptors::Noop::call` returns `Ok(req)` unconditionally [4](#0-3) . Any attacker with network access to the aggregator's gRPC port can therefore invoke `internal_send_tx` (and other `Internal*`/state-changing RPCs) without a TLS certificate. If an operator has queued a deadline-bound tx (challenge, disprove, timeout) for broadcast at a specific block height/time via the tx-sender/aggregator pipeline, and its serialized bytes are observable (e.g., from a prior broadcast attempt visible on the P2P network, replayed request logs, or captured wire bytes when no TLS/mTLS is enforced), an attacker can resubmit those exact bytes through the unauthenticated `internal_send_tx` path ahead of the intended schedule, forcing early confirmation.

### Impact Explanation
This matches the High-severity category: "an unauthenticated state-changing or broadcasting call" and "a deadline-bound challenge/disprove/timeout transaction made unconfirmable by attacker-shaped chain data." Forcing early confirmation of a deadline-bound tx can desynchronize the presigned transaction graph's timing assumptions (e.g., causing a challenge/disprove to land before its intended CSV/timelock window relative to other transactions), which can disrupt an honest operator's Reimburse path. The blast radius scales with however many `Internal*`/state-mutating RPCs are exposed on the aggregator port under this configuration, across all deposits/operators served by that aggregator instance.

### Likelihood Explanation
This requires the specific deployment precondition `client_verification=false`, which the repo's own comments and warning logic indicate is a real, documented configuration path (the warning only fires for the *enabled* case, implying disabled is treated as normal/expected) [3](#0-2) . No key, certificate, or privileged role is needed by the attacker — only network reachability to the aggregator's TCP port and the ability to observe or reconstruct a `SendTxRequest`'s bytes. This is repeatable per queued transaction and per deposit/operator using the same misconfigured aggregator.

### Recommendation
Do not allow `Noop` to ever cover `Internal*` methods regardless of `client_verification`. At minimum: (1) fail server startup (not just warn) when `client_verification=false` for the aggregator/operator/verifier gRPC servers, since this is the setting that removes all caller authentication for `Internal*` RPCs; (2) always enforce the `is_internal` leaf-certificate check independent of the `client_verification` toggle, so `Internal*` methods require `our_cert` even when general client verification is relaxed; (3) add non-TLS-based binding (e.g., a shared internal token or mTLS-independent authorization) for `Internal*` RPCs like `internal_send_tx`, `InternalGetEmergencyStopTx` so they cannot regress silently.

### Proof of Concept
```
cargo test proof plan (core/src/servers.rs / interceptors.rs, exercised via aggregator RPC harness):

1. Construct a BridgeConfig with client_verification = false, spin up create_aggregator_grpc_server(config).
2. Assert server-side interceptor installed is Interceptors::Noop (via create_grpc_server code path assertion / instrumentation), i.e. LHS = "caller of internal_send_tx" is unconstrained, RHS = "party holding our_cert" is a fixed identity -> LHS != RHS.
3. From a bare tonic Channel with NO client certificate/identity configured, connect to the aggregator port and call internal_send_tx with a captured/replayed SendTxRequest (raw tx bytes of a legitimate operator's queued challenge/disprove/timeout tx).
4. Assert the call succeeds (Status::Ok) despite no certificate being presented — demonstrating CALLER_AUTHORITY (only_aggregator_and_self) is bypassed.
5. Contrast with client_verification = true: repeat step 3 and assert Status::Unauthenticated("Failed to verify peer certificate, is TLS enabled?") is returned, confirming the binding holds only under the non-default toggle and is otherwise broken.
```

impl Interceptor for Interceptors {

    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
