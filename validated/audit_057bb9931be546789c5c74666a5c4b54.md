### Title
`open-external` IPC handler in main process calls `shell.openExternal` on arbitrary renderer-supplied strings without protocol allow-listing - ([File: app/src/main-process/main.ts])

### Summary
The external report flags `Cover.deploy` for lacking an authorization guard (`onlyOwner`) on a privileged operation, letting any caller invoke it. The closest analog in GitHub Desktop is the `open-external` IPC handler registered in the privileged main process: it accepts any string from the renderer and hands it straight to Electron's `shell.openExternal`, with no scheme allow-list, even though the codebase demonstrates elsewhere (`app/src/ui/lib/enterprise-validate-url.ts`, the BYOK URL validator, and the markdown link interceptor) that the team knows this class of input needs restricting to `http(s):`.

### Finding Description
`main.ts` registers:
```
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (pathLowerCase.startsWith('http://') || pathLowerCase.startsWith('https://')) {
    log.info(`opening in browser: ${path}`)
  }
  try {
    await shell.openExternal(path)
    return true
  } catch (e) { ... }
})
``` [1](#0-0) 

The `http/https` check here is only used to decide whether to write a log line — it is **not** a gate. Any string, including `file://`, custom-protocol URIs (`ms-search:`, vendor-registered handlers), or OS-specific dangerous constructs, is passed unconditionally to `shell.openExternal(path)`.

This handler is reached from the renderer via `app-shell.ts`'s `openExternal` (proxied through `main-process-proxy.ts`), which is the single implementation backing `IAppShell.openExternal` used throughout the UI — e.g. `LinkButton.onClick` calls `shell.openExternal(uri)` for whatever `uri` prop it is given [2](#0-1) , and `dispatcher._openInBrowser`/`app-store.ts` `_openInBrowser` forward arbitrary URLs the same way [3](#0-2) .

Elsewhere the app explicitly recognizes that untrusted, remote-controlled strings must be scheme-restricted before being treated as navigable links:
- The Enterprise sign-in flow requires `https:` and rejects anything else via `validateURL` [4](#0-3) .
- The sandboxed markdown renderer's link interceptor only forwards clicks whose `a.protocol` matches `/^https?:/` before invoking `onMarkdownLinkClicked`, which itself calls `shell.openExternal` [5](#0-4) [6](#0-5) .

None of that protocol validation exists at the actual trust boundary — the main-process IPC handler that performs the privileged `shell.openExternal` call. Just as the Solidity report's `deploy` lacked the `onlyOwner` check that other privileged functions presumably had, this main-process handler lacks the scheme check that sibling code paths in the same codebase already implement, leaving the privileged sink itself unguarded and dependent entirely on renderer-side discipline (which is a compromised or attacker-influenced trust boundary in Electron's threat model, since IPC senders are only validated for identity, not for the content/URL of `open-external` payloads) — see `isTrustedIPCSender` guard, which validates *who* can call the channel but says nothing about *what* is passed [7](#0-6) .

### Impact Explanation
`shell.openExternal` with an uncontrolled path/URI is a well-known Electron sink: passing `file://` paths, custom protocol handlers registered by third-party software, or OS-specific URI schemes (e.g., Windows `search-ms:`/`ms-search:` payloads, or crafted UNC-like strings) can result in launching arbitrary local files/applications or triggering credential-leaking network requests, outside the renderer sandbox and beyond what "open a web page" implies. Because any renderer code path that surfaces attacker-influenced text as a clickable/`openExternal`-invoked value (e.g., data rendered from a cloned repository or a GitHub API object that a UI component treats as a "URL" and threads through `LinkButton`/`shell.openExternal` without first restricting to `http(s):`) can reach this handler, the missing allow-list at the IPC boundary converts what should be "open a web link" into "run whatever the OS resolves for this string."

### Likelihood Explanation
The likelihood is moderate: the direct, most heavily used paths (Enterprise URL entry, markdown link clicks) already validate scheme before calling `openExternal`, which mitigates the most obvious routes. However, this defense is enforced only in scattered call sites in the renderer, not once at the trusted main-process chokepoint. Any current or future UI code path that builds a `uri`/`path` value from repository- or API-derived data and passes it to `shell.openExternal` (via `LinkButton`, `dispatcher._openInBrowser`, or a future feature) without independently re-validating the scheme will bypass all existing protections, because the actual privileged action has no enforcement of its own. This "defense only at the edges, not at the sink" pattern is exactly the class of bug the external report describes: a sensitive/privileged operation missing its own authorization/validation check, relying on callers to have already done the right thing.

### Recommendation
Add scheme allow-listing directly inside the `open-external` IPC handler in `app/src/main-process/main.ts`, rejecting (returning `false`/throwing) for anything that isn't `http:` or `https:` (with a narrow, explicit exception list if other schemes are genuinely required, e.g. `mailto:`). This mirrors adding `onlyOwner` at the function itself rather than trusting all call sites to have already checked authorization — enforce the guard at the privileged sink (`shell.openExternal`), not only in select renderer call paths.

### Proof of Concept
1. In the renderer, invoke the exposed IPC call directly (as any code with access to `main-process-proxy.ts`'s `openExternal` can do, e.g. from a UI component rendering repository-derived data as a `LinkButton` `uri`, or by future code that forgets the scheme check that other components already apply):
   ```ts
   import { openExternal } from '../ui/main-process-proxy'
   await openExternal('file:///C:/some/malicious/path/evil.exe') // or a registered custom-scheme handler URI
   ```
2. This reaches `ipcMain.handle('open-external', ...)` in `main.ts`, which performs no scheme check and calls `shell.openExternal(path)` unconditionally [1](#0-0) .
3. Because the only existing protocol restriction (`/^https?:/` in `sandboxed-markdown.tsx`) lives in a different, non-enforced call path, any renderer code that doesn't route through that specific markdown interceptor bypasses it entirely, demonstrating that the privileged sink itself provides no guarantee.

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
```
