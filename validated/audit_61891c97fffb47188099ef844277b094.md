### Title
Unvalidated `updated_at` timestamps from PR API responses allow a malicious/compromised GitHub Enterprise remote to poison the local "last updated" watermark and silently freeze pull request tracking - (File: app/src/lib/stores/pull-request-store.ts)

### Summary
`PullRequestStore.fetchAndStorePullRequests` uses `db.getLastUpdated(repo)` as the sole gate to decide whether to do a full open-PR fetch or an incremental "since" fetch, and the watermark it persists is derived directly from attacker-controlled `updated_at` values in the API response, with no validation against the local clock or monotonicity guarantees.

### Finding Description
`fetchAndStorePullRequests` reads the last stored watermark and branches purely on its presence: [1](#0-0) 

If a watermark exists, it calls `fetchAndStoreUpdatedPullRequests`, which passes `lastUpdatedAt` as the `since` parameter to the API: [2](#0-1) 

The watermark itself (`mostRecentlyUpdated`) is computed by taking the maximum `pr.updated_at` string across whatever PRs the server chose to return, with no sanity check that it is not in the future or otherwise implausible: [3](#0-2) 

That value is then persisted unconditionally via `db.setLastUpdated`: [4](#0-3) [5](#0-4) 

Because ISO8601 timestamps are compared as raw strings (`pr.updated_at > mostRecentlyUpdated`) with no upper bound or clock-skew check, a single malicious response containing a PR with a far-future `updated_at` will be persisted as the new watermark. All subsequent `since`-filtered requests will use that future timestamp. On a legitimate GitHub/GHE server, `since` is honored as a lower bound filter, so any real update with an actual (earlier) `updated_at` will be excluded from the response until real time passes the injected value — the client has no other mechanism to discover the update, since `fetchAndStoreOpenPullRequests` (the only path that ignores the watermark) is only invoked when there is no watermark at all or when the incremental fetch fails with `MaxResultsError`/`APIError`.

### Impact Explanation
This causes silent corruption of the locally cached view of pull requests — specifically stale/incorrect PR head SHAs, titles, or states can persist indefinitely (until the poisoned future timestamp elapses) even though the user believes the PR list is being refreshed every 30 minutes by `PullRequestUpdater`. This is a "silent corruption of what the user commits or pushes"-adjacent issue in that a developer relying on the desktop client's PR panel (e.g., to check out or compare against a PR's head SHA) may act on stale data without any error or indication that a refresh failed.

### Likelihood Explanation
Exploitation requires the attacker to control at least one API response returned to the victim's GitHub Desktop client for a given repository — consistent with the stated threat model (a compromised/malicious GitHub Enterprise remote, or a MITM-capable proxy sitting in the request path). No user interaction beyond having the repository already added to Desktop and periodic PR refresh occurring (which happens automatically via `PullRequestUpdater`) is required. This is a single crafted response, not a sustained compromise, since only one response needs to include the future-dated PR before control of the channel is lost.

### Recommendation
Clamp any `updated_at` value used to compute `mostRecentlyUpdated` to no later than the client's current time (e.g., `Math.min(parsedUpdatedAt, Date.now())`) before persisting it via `db.setLastUpdated`, and/or reject PR objects whose `updated_at` is implausibly in the future. Consider also bounding how far in the future a `since` watermark can push subsequent queries, or periodically forcing a full `fetchAndStoreOpenPullRequests` refresh independent of the stored watermark to bound the staleness window.

### Proof of Concept
1. Point Desktop at a GitHub Enterprise remote controllable by the attacker (or interpose on the API responses).
2. On the first PR refresh, respond to `fetchAllOpenPullRequests` with a PR whose `updated_at` is set far in the future (e.g., year 2099).
3. `storePullRequests` computes `mostRecentlyUpdated` = that future date and persists it via `db.setLastUpdated` (app/src/lib/stores/pull-request-store.ts:241-273, 341-350).
4. On the next refresh cycle, Desktop calls `fetchUpdatedPullRequests(owner, name, sinceFutureDate)` (app/src/lib/stores/pull-request-store.ts:114-121).
5. Restore the remote to a legitimate/non-malicious server (or have the legitimate server return the real, corrected PR with a real, earlier `updated_at`, e.g., a new commit pushed to the PR branch).
6. Because `since` is a future date, the legitimate server's `since` filter excludes the real update from the response; the local PR record and cached head SHA are never updated, verifying the freeze.

Note: I was not able to view `app/src/lib/api.ts`'s `fetchUpdatedPullRequests` implementation in full (file appears truncated/excluded from the index beyond line 1), so I could not directly confirm the exact `since` query-parameter construction and whether any additional clamping exists there. If precise confirmation of that implementation is needed, a full-repository session (e.g., a Devin run) would be required to inspect `app/src/lib/api.ts` in its entirety.
