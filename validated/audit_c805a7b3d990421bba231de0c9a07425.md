### Title
Ed448 point decoding accepts small-order (torsion) points due to a vacuous `is_torsion_free` check, enabling Schnorr proof/signature forgery - ([File: crypto/ed448/src/point.rs](crypto/ed448/src/point.rs))

### Summary
The CVE-2021-32802 analog class is "untrusted bytes fed to a decoder/component not suited for untrusted content." In Serai, every `read_G`/`from_bytes` path decodes attacker-controlled point encodings. The Ed448 implementation's torsion check is a tautology — it computes `P*(-1) + P`, which is always the identity — so `Point::from_bytes` never actually rejects non-prime-subgroup points. Ed448 has cofactor 4, so non-identity order-2 and order-4 points are accepted as canonical public keys, nonces, and commitments by `Ciphersuite::read_G`, `SchnorrSignature::read`, `Commitments::read`, `EncryptionKeyMessage::read`, and `ThresholdKeys::read`.

### Finding Description [1](#0-0) 

`is_torsion_free` evaluates `(*self * (Scalar::ZERO - Scalar::ONE)) + self`, i.e. `P*(-1) + P`, which is identically the identity point for every `P`. `from_bytes` ANDs this always-true value into its validity condition, so the torsion check is dead code: [2](#0-1) 

Contrast with the comment in `SchnorrSignature`, which states the library relies on strict canonical prime-group decoding so the RFC 8032 cofactor workaround (`8R = 8s - 8cX`) is unnecessary — that assumption is false for Ed448: [3](#0-2) 

The reachable decoders all accept these points because `Ciphersuite::read_G` only enforces canonical encoding, not subgroup membership: [4](#0-3) 

Concrete reachability: PedPoP's `Commitments::read` reads `t` points via `C::read_G` plus an attacker-supplied `SchnorrSignature`, and `verify_r1` uses `commitments[0]` as the PoK public key in batch verification: [5](#0-4) 

### Impact Explanation
A Schnorr signature under a pure-torsion public key `A = T` (order 4, no prime-subgroup discrete log) is forgeable in ~4 expected hash evaluations. Verification checks `R + cA - sG == 0`: [6](#0-5) 

An attacker sets `s = 0`, picks `R = t·T` for `t ∈ {0,1,2,3}` (all accepted by `read_G`), computes the challenge `c`, and succeeds whenever `c ≡ -t (mod 4)` — probability 1/4 per attempt, so trivially iterated. The result is a `SchnorrSignature`/`EncryptionKeyProof`/PedPoP proof-of-knowledge that verifies for a public key for which *no secret key exists* — a forged proof under the stated acceptance criteria. This directly voids the PedPoP PoK's purpose (binding `commitments[0]` to a known coefficient) and the per-message encryption proof-of-possession. Additionally, torsion components accepted into `Commitments`/`ThresholdKeys::read` verification shares pollute `group_key`/verification shares with order-4 components, making subsequent Schnorr/FROST signature equations hold only probabilistically (`c·τ` vanishes with probability 1/4) — an incorrect verifier formula and liveness break.

### Likelihood Explanation
The flaw is deterministic (the check can never fail) and requires only standard attacker-controlled inputs: a PedPoP participant broadcasting a `Commitments` message, or any byte stream fed to `SchnorrSignature::read`/`read_G` for Ed448. Exploitation of the proof forgery requires no secrets and only ~4 offline hash computations. The constraint is scope: it applies only to deployments using the Ed448 ciphersuite, and within the DKG the practical gain beyond "a forged proof verifies" is bounded (the attacker commits to a known-torsion value rather than a usable secret share), so real-world severity is Medium–High rather than Critical. `Curve::read_G` in FROST rejects the identity but still not order-2/4 points, so it does not mitigate this. [7](#0-6) 

### Recommendation
Implement a real torsion check in `is_torsion_free`: verify `[l]P == identity` after clearing the cofactor, i.e. check `self * Scalar::from(4)` (or multiply by the prime subgroup order and compare against the expected result) rather than the tautological `P*(-1) + P`. Until fixed, any Ed448 consumer should treat decoded points as potentially having order-4 components; `read_G` for Ed448 could additionally multiply decoded points by the cofactor and require the result to be non-identity torsion-free. Note the batch verifier's first statement weight of `ONE` (`crypto/multiexp/src/batch.rs:46-47`) makes deterministic acceptance of a single forged statement unavoidable once torsion points are admitted.

### Proof of Concept
1. Instantiate `Ed448` as ciphersuite `C`.
2. Construct `T`, a non-identity point of order 4 (e.g., `P4 = [h]·base` style construction via `from_bytes` of a known order-4 encoding; `is_torsion_free` returns true for it).
3. Forgery under public key `A = T`, message context `m`:
   - For each `t` in `0..4`: set `R = t*T` (canonical encoding passes `read_G`), compute `c = challenge(R, A, m)`; keep the pair where `c + t ≡ 0 (mod 4)`.
   - Emit `SchnorrSignature { R, s: 0 }`. Verification computes `R + cA - 0·G = (t + c)T = identity` → accepted.
4. In PedPoP, broadcast `EncryptionKeyMessage<Commitments>` with `commitments[0] = T`, the forged `sig`, and remaining commitments arbitrary; `verify_r1` batch verification accepts the forged PoK (line `msg.sig.batch_verify(..., msg.commitments[0], challenge(...))`), proving "knowledge" of a coefficient that does not exist.

Caveat: I did not fully trace `crypto/dkg/pedpop/src/encryption.rs`'s ECDH/proof flow; whether a torsion `enc_key` additionally leaks or corrupts share confidentiality is unverified, but the forged-proof and incorrect-verifier-formula impacts stand on the cited code alone.
