### Title
Missing Reward Pool Sync in `emergencyWithdraw` Causes Permanent Loss of Unclaimed Yield - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.emergencyWithdraw` reduces a user's `user.amount`/`user.available` and transfers out the staking token, but never calls `_harvestBaseRewarder` (i.e. `rewarder.updateFor(_account)`) before changing the user's balance. Because the linked `BaseRewardPool.balanceOf()` reads the user's staking balance live from `MasterMagpie` rather than from an internally cached, correctly-snapshotted value, this omission causes the user's already-accrued but unclaimed reward to be permanently mis-calculated (undercounted) using their post-withdrawal (now much smaller) balance the next time rewards are synced.

### Finding Description
`emergencyWithdraw` mutates `user.amount` and `user.available` directly without first calling `_harvestBaseRewarder`, unlike the normal deposit/withdraw paths: [1](#0-0) 

Compare with the normal `_harvestAndUnstake` flow used by `withdraw`/`withdrawFor`, which always calls `_harvestBaseRewarder` (which calls `rewarder.updateFor(_account)`) *before* `user.amount`/`user.available` are decremented: [2](#0-1) 

The reward pool (`BaseRewardPool`) computes a user's staked balance on demand, live from `MasterMagpie`, rather than maintaining its own independently-updated balance: [3](#0-2) 

Reward accrual snapshotting (`_updateFor`) relies on `earned()`, which multiplies the *current* `balanceOf(_account)` by the delta in `rewardPerToken` since the account's last snapshot: [4](#0-3) 

Because `emergencyWithdraw` changes `user.amount` without invoking this snapshot beforehand, the next time `_updateFor`/`earned()` runs for that account (e.g. on a subsequent deposit or claim), it will apply the accumulated `rewardPerToken` delta (which reflects rewards earned by the pool while the user held their *original, larger* balance) against the user's *new, reduced* balance. The reward legitimately earned during the pre-withdrawal period, proportional to the user's original balance, is permanently lost — it is neither paid to the user nor returned to the pool for other stakers.

### Impact Explanation
This is a direct, permanent loss of a legitimate unprivileged user's own already-accrued, unclaimed yield, triggered purely by that user calling a normal (non-privileged) function of the protocol (`emergencyWithdraw`, callable by any staker while the contract is paused). No admin or governance action is required to trigger the loss — the affected user's own transaction causes it. This matches the accepted "theft or permanent freezing of unclaimed yield" impact category.

### Likelihood Explanation
The bug triggers deterministically any time a user has un-harvested rewards accrued in a `BaseRewardPool`-backed pool and calls `emergencyWithdraw` for part of their `available` balance while the protocol is paused, which is the sanctioned way for users to exit under emergency conditions. Given `emergencyWithdraw` is explicitly documented as usable by any user in an emergency (pause) scenario, the conditions for triggering this loss are realistic and low-effort.

### Recommendation
Call `_harvestBaseRewarder(_stakingToken, msg.sender)` (and ideally `_harvestMGP`, consistent with the rest of the codebase's pattern) at the start of `emergencyWithdraw`, before `user.amount`/`user.available` are mutated, so that the reward pool snapshots the user's rewards using their correct, pre-withdrawal balance: [5](#0-4) 

### Proof of Concept
1. User deposits `X` staking tokens into a pool wired to a `BaseRewardPool` rewarder via `MasterMagpie.deposit`; this sets `user.amount = X`.
2. Time passes; the reward pool accrues `rewardPerToken` increases for the pool proportional to `X` staked by the user (no `updateFor` call happens in between).
3. Contract is paused and user calls `emergencyWithdraw(stakingToken)`, withdrawing `available = X` tokens. `user.amount` and `user.available` are set to `0` directly — `_harvestBaseRewarder` is never called, so the reward pool's `userRewardPerTokenPaid[account]` is never advanced to reflect the rewards owed for the period the user held balance `X`.
4. User later calls `getReward()`/`multiclaim`, which triggers `_updateFor`/`earned()` in the `BaseRewardPool`. Because `balanceOf(account)` is now `0` (post-withdrawal), `earned()` computes `0 * (rewardPerToken - paid) + userRewards[account]` — the reward accrued during step 2, proportional to the user's original stake `X`, is permanently unrecoverable.

    ///         Locked Token can not be emergent withdraw.
    /// @param _stakingToken Staking token of the pool
    /// @dev withdrawFor of the rewarder with the third param at false is an emergency withdraw
    function emergencyWithdraw(address _stakingToken) external whenPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][msg.sender];
        uint256 availableaAmount = user.available;
        user.available = 0;
        IERC20(pool.stakingToken).safeTransfer(address(msg.sender), availableaAmount);
        emit EmergencyWithdraw(msg.sender, _stakingToken, availableaAmount);
        user.amount = user.amount - availableaAmount;
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;
    }
