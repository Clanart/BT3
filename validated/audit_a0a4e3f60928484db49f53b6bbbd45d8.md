## Analysis Result [1](#0-0)  and [2](#0-1)  together reproduce the exact bug-class from the report — a mutable parameter that determines a user's reward share is read at *claim time* and applied retroactively to the *entire* accumulated reward balance, instead of being checkpointed per accrual period. Unlike the original report (which required an admin transaction), here the mutable input (`getRewardablePercentWAD`) is fully controlled by an **ordinary unprivileged wallet** via the free, unrestricted `cancelUnlock` function, making this a valid unprivileged-wallet analog.

### Title
Reward-forfeiture percentage is computed on-demand from mutable lock state and can be manipulated via `cancelUnlock`, allowing users to retroactively erase forfeitures owed to other stakers - (File: `rewards/vlMGPBaseRewarder.sol`)

### Summary
`vlMGPBaseRewarder._sendReward` forfeits a portion of a user's *entire accumulated* pending reward based on `VLMGP.getRewardablePercentWAD(_account)`, a value computed live from the caller's current locked/cooldown state. Because `cancelUnlock` lets a user instantly restore "fully locked" status with no cooldown or fee, a user can zero out this forfeiture immediately before harvesting, then re-enter cooldown right after, capturing rewards that should have been redirected to other vlMGP holders.

### Finding Description
`_calExpireForfeit` determines how much of a user's accrued reward is forfeited: [3](#0-2) 
It multiplies the **entire** pending `userRewards[...][_account]` balance (accumulated possibly over many prior reward-emission periods, per `_earned`/`_updateFor`) by `rewardablePercentWAD`, a value read at the moment of `getReward()`: [4](#0-3) [5](#0-4) 

`getRewardablePercentWAD` is derived purely from the account's current `VLMGP` lock/cooldown composition: [2](#0-1) 

Crucially, a user can freely and instantly manipulate this input via `cancelUnlock`, which has no cooldown, fee, or time restriction — it simply zeroes the `amountInCoolDown` on a slot and restores the tokens to "fully locked": [6](#0-5) 

This mirrors precisely the root cause described in the report: a parameter that feeds into the reward-multiplier math (`fractionOfMaxMultiplier`/`maxMultiplier` there, `rewardablePercentWAD` here) is not checkpointed per accrual period, so changing it retroactively re-prices *all* previously accrued, unclaimed rewards. The difference is that here the "parameter" is entirely within an ordinary user's control (their own `VLMGP` lock state), not an admin setting.

### Impact Explanation
Any forfeited amount is redistributed to other vlMGP stakers as bonus reward via `_queueNewRewardsWithoutTransfer`, which increases `rewardPerTokenStored` for all remaining holders: [7](#0-6) 
By calling `cancelUnlock` immediately before `getReward`/`multiclaimFor`, and `startUnlock` immediately after to re-enter cooldown, a user who has kept part of their vlMGP in cooldown for a long time (accumulating rewards that should be partially forfeited) can claim those rewards with 0% forfeiture. This diverts yield that legitimately belongs to other, honest lockers (theft of unclaimed yield from other users), while leaving the underlying protocol accounting unaware that a manipulation took place.

### Likelihood Explanation
The manipulation only requires two ordinary, unprivileged, gas-cheap calls (`cancelUnlock` then `startUnlock`) bracketing a normal `getReward`/harvest call, all within the same transaction or same block. There is no cooldown, fee, or access restriction blocking `cancelUnlock`. Any user who keeps a meaningful amount in cooldown across multiple reward-emission cycles and wants to periodically harvest without losing the forfeit penalty can perform this pattern repeatedly, at the cost of resetting their own withdrawal cooldown timer (a self-inflicted, non-blocking cost), making it realistically exploitable by rational actors seeking higher net yield.

### Recommendation
Do not compute `_calExpireForfeit` against the entire lifetime-accumulated `userRewards` balance using a live/instantaneous `rewardablePercentWAD`. Instead, checkpoint the forfeitable/rewardable split at the time rewards accrue (e.g., track `rewardablePercentWAD` per reward-per-token snapshot interval in `_updateFor`, similar to how `rewardPerTokenStored` is snapshotted), so that later changes to a user's own lock/cooldown composition cannot retroactively change the forfeiture treatment of rewards already earned under a different lock state.

### Proof of Concept
1. User locks MGP in `VLMGP`, accruing vlMGP balance and staking rewards via `vlMGPBaseRewarder`.
2. User calls `startUnlock(amount)` to move a portion into cooldown; `getRewardablePercentWAD` now returns < 100%.
3. Reward emissions continue to accrue in `vlMGPBaseRewarder` (`rewardPerTokenStored` increases) over an extended period while the user remains partially in cooldown.
4. Just before harvesting, user calls `cancelUnlock(slotIndex)` — this is free, instant, with no penalty — restoring 100% "fully locked" status and thus `getRewardablePercentWAD == 1e18`.
5. User (or `MasterMagpie.multiclaimFor` on their behalf) calls `getReward`, which computes `_calExpireForfeit` using the now-100% rewardable percent, so `forfeitAmount == 0` even though a large portion of the accrued reward period the user was actually in cooldown.
6. User calls `startUnlock(amount)` again immediately afterward to resume cooldown for eventual withdrawal.
7. Net effect: the user has captured reward that should have been partially forfeited and redistributed via `_queueNewRewardsWithoutTransfer` to other vlMGP stakers, at the cost of merely resetting their own cooldown clock.

        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;

    function _earned(address _account, address _rewardToken, uint256 _userVlmgpShare) internal view returns (uint256) {
        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**vlMGPDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
