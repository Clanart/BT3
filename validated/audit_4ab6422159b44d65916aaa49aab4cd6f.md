### Title
Truncated integer exponent in `calc-liq-factor-exp` produces incorrect graduated-liquidation percentage - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`calc-liq-factor-exp` computes the graduated liquidation curve `liq-factor^alpha`, where `alpha` is expressed in BPS. For non-BPS-multiple exponents, the code truncates `(/ exp BPS)` to an integer before using it as the exponent in `pow`, silently rounding a fractional exponent down. For the sub-1.0 branch it does not even use `exp` at all — it hardcodes an assumed square-root (`factor^0.5`) regardless of the configured value. This mirrors the reported Numa bug class: an integer-truncated value meant to represent a fractional percentage/exponent is used directly in a price/percentage-changing calculation, producing a materially wrong result instead of the intended one.

### Finding Description [1](#0-0) 

```clarity
;; Apply curve exponent for graduated liquidation
;; liq-factor = liq-factor^alpha
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

`exp` (`LIQ-CURVE-EXP`, an egroup parameter set via DAO proposal, e.g. `mainnet/contracts/proposals/mainnet/v0-init.clar`) is expressed in BPS, i.e. `10000` = exponent `1.0`. When `exp > BPS` and is not an exact multiple of `10000` (e.g. `15000` = exponent `1.5`), `(/ exp BPS)` performs integer division and truncates to `1`, so the formula collapses to `(pow factor 1) / (pow BPS 0) = factor`, discarding the fractional part of the exponent entirely. For `exp < BPS` the code doesn't even attempt a generic fractional-exponent calculation — it unconditionally computes `sqrti(factor * BPS)`, i.e. always assumes exponent `0.5`, no matter what `exp` actually is (e.g. `3000` = `0.3` would still be computed as if it were `0.5`).

This computed value, `liq-pct-scaled`, feeds directly into:
- `calc-liq-factor-bound` → `liq-penalty` [2](#0-1) 
- `calc-liq-debt-repay` → `max-debt-usd`, the USD cap on how much debt can be liquidated in one call [3](#0-2) 

Both values are subsequently used in `liquidate` to size the actual debt repaid and collateral seized, including the liquidator bonus: [4](#0-3) 

### Impact Explanation
Because `factor <= BPS` (`factor` represents a fraction ≤ 1.0 in bps), raising it to a *smaller* exponent than intended always yields a *larger* result (`x^0.3 > x^0.5` for `0<x<1`, and `x^1 > x^1.5`). So truncation systematically pushes `liq-pct-scaled` — and therefore both `liq-penalty` (via `calc-liq-factor-bound`) and `max-debt-usd` (the cap on liquidatable debt, via `calc-liq-debt-repay`) — higher than the graduated curve intended for any `LIQ-CURVE-EXP` value that is not an exact multiple of `10000` (for `exp>BPS`) or exactly `5000` (for `exp<BPS`). A larger `liq-penalty` and a larger `max-debt-usd` directly translate into more collateral being seized and a bigger liquidator bonus paid out of the borrower's position than the configured curve intends, at the moment of liquidation — this is a wrong-magnitude liquidation caused by a computation bug in the market contract's own health/penalty arithmetic (not third-party oracle data, not a DAO misconfiguration of the registry — the registry value is valid, it is `calc-liq-factor-exp`'s handling of it that is wrong). This results in borrowers losing more collateral than the protocol's own liquidation curve is supposed to allow, i.e. theft of user funds beyond the intended penalty/amount — falling under the Critical/High impact bucket for direct loss of user funds via an incorrect health/liquidation-percentage calculation.

### Likelihood Explanation
This triggers deterministically whenever an egroup is configured with `LIQ-CURVE-EXP` that is not an exact multiple of `10000` for values above `10000`, or any value other than exactly `5000` below `10000` — i.e., any curve configuration other than the trivial linear (`10000`) or exact integer powers. Since the DAO is expected to be able to tune this curve per-egroup (that's the entire purpose of exposing `LIQ-CURVE-EXP` as a parameter), any reasonably "graduated" curve (e.g. `1.5x`, `2.5x`, `0.3`) silently produces incorrect results on every liquidation for that egroup, with no revert or warning — this is a code defect, not a misconfiguration, because the contract accepts and appears to process the parameter correctly while actually computing something different.

### Recommendation
Do not use integer truncation of `exp/BPS` as the exponent. Either:
1. Restrict `LIQ-CURVE-EXP` to only the supported exact values (e.g. `5000`, `10000`, `20000`, `30000`, ...) and validate this at egroup-creation/update time, or
2. Implement a proper fixed-point exponentiation (e.g. exponentiation by squaring combined with a fractional correction via `sqrti`/binary exponent decomposition) so arbitrary bps-scaled exponents between `0` and some max are computed with bounded precision loss, analogous to increasing precision before taking `Math.sqrt`/`pow` in the referenced Numa fix.

### Proof of Concept
Assume an egroup configured with `LIQ-CURVE-EXP = u15000` (intended exponent 1.5, a valid "steeper than linear" curve a DAO could reasonably choose) and `factor = u8100` (0.81, i.e., linear liquidation factor already computed by `calc-liq-factor`):

- Intended: `liq-pct-scaled = factor^1.5 = 0.81^1.5 ≈ 0.729` → `7290` bps
- Actual code: `(/ exp BPS)` = `(/ u15000 u10000)` = `u1` (integer division truncates 1.5 → 1)
  `(pow factor 1) / (pow BPS 0)` = `8100 / 1` = `8100` bps

Result: the contract computes `liq-pct-scaled = 8100` instead of the intended `~7290` — roughly 11% larger than intended. This inflated value is passed to `calc-liq-factor-bound` (raising `liq-penalty` toward the max faster than the curve intends) and to `calc-liq-debt-repay` (raising `max-debt-usd`), both of which increase the amount of debt liquidated and collateral seized (with bonus) in `liquidate` beyond what the configured 1.5-exponent curve was meant to allow at that LTV. ;; Scale penalty between min and max using liquidation factor
;; liq-penalty = liq-penalty-min + (liq-factor * (liq-penalty-max - liq-penalty-min) / BPS)
;; Capped at bound-max to handle cases where liq-factor > BPS
(define-private (calc-liq-factor-bound (liq-factor uint) (bound-min uint) (bound-max uint))
  (min bound-max (+ bound-min (mul-bps-down liq-factor (- bound-max bound-min)))))

;; Calculate debt to repay based on liquidation factor
;; debt-repay = liq-factor * debt / BPS
(define-private (calc-liq-debt-repay (debt uint) (liq-factor uint)) 
  (mul-bps-down liq-factor debt))

;; Calculate collateral to seize (includes liquidator bonus)
;; collateral-repay = debt-repay * (BPS + liq-penalty) / BPS
(define-private (calc-liq-collateral-repay (debt-repay uint) (liq-penalty uint)) 
  (mul-bps-down debt-repay (+ BPS liq-penalty)))

;; Calculate actual debt repayment when collateral is capped
;; debt-repay-real = (collateral-amount-usd * BPS) / (BPS + liq-penalty)
(define-private (calc-liq-debt-repay-real (collateral-amount-usd uint) (liq-penalty uint)) 
  (div-bps-down collateral-amount-usd (+ BPS liq-penalty)))

;; Graduated liquidation parameter calculation
;; Combines the 4-step liquidation factor calculation into a single helper
;; Returns: { liq-pct-scaled: uint, liq-penalty: uint, max-debt-usd: uint }
(define-private (calc-liquidation-params
  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)
  (curve-exponent uint)
  (total-debt-usd uint))
  
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    {
      liq-pct-scaled: liq-pct-scaled,
      liq-penalty: liq-penalty,
