### Title
Unchecked `payment_sat + fee` overflow in `SignableTransaction::new` can bypass the `NotEnoughFunds` check and produce an unspendable/locked transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is an arithmetic difference that was assumed to be safe because "later cumulative values are always larger," yet underflows/overflows once wrapped values are possible, permanently locking funds. The same class exists in `networks/bitcoin/src/wallet/send.rs`: `SignableTransaction::new` assumes `payment_sat + needed_fee` and `payment_sat + fee_with_change` fit in `u64`. The sums are computed with plain `+`, so an attacker-supplied payment amount near `u64::MAX` wraps the sum, bypasses the `input_sat < payment_sat + needed_fee` check, and causes a change output of nearly the entire input value to be committed alongside an invalid `u64`-overflowing payment output.

### Finding Description
`SignableTransaction::new` validates funds with:

```rust
if input_sat < (payment_sat + needed_fee) {      // line 215
  Err(TransactionError::NotEnoughFunds { .. })?;
}
```

and computes change with:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {  // line 228
```

`payment_sat` is `payments.iter().map(|p| p.1).sum::<u64>()` (line 187), where each `payment.1` is an unconstrained `u64` taken directly from the caller (only `>= DUST` is enforced at lines 165-169). There is no cap tying payment amounts to actual BTC supply or to `input_sat` before the addition.

If `payment_sat + needed_fee` overflows `u64`:
- In debug builds (or with overflow checks), it panics — a liveness failure equivalent to the Maia revert: the multisig's `Plan` can never be converted into a `SignableTransaction`.
- In release builds, wrapping semantics make `input_sat < wrapped` false, so `NotEnoughFunds` is not raised. Then `payment_sat + fee_with_change` wraps to a small value, `input_sat.checked_sub(small)` succeeds, and a change output of `~input_sat - epsilon` is appended while a payment output with an absurd value (e.g. `u64::MAX`) is committed into `tx_outs`. The resulting transaction is invalid on the Bitcoin network (output exceeds the 21M cap / outputs exceed inputs), yet `SignableTransaction` is successfully constructed, signed by FROST, and its fee accounting (`fee()` at lines 138-141, itself an unchecked subtraction `sum(inputs) - sum(outputs)`) becomes meaningless. The plan's inputs are consumed/assigned to a transaction that can never confirm, locking the bridged funds exactly as the Maia LP position was locked in `UniswapV3Staker`.

An unprivileged party reaches this path through payment amounts in bridge plans (`PlanFromScanning`/`prepare_send` in `processor/src/networks/mod.rs` feed user-derived `payment.balance.amount.0` values into `SignableTransaction::new`), so no validator privileges are needed to inject a malicious `payment.1`.

### Impact Explanation
High/Medium. Either a persistent panic (funds never movable through this plan, analogous to `unstakeToken` reverting forever) or a successfully produced `SignableTransaction` that is unbroadcastable/invalid, consuming the plan's inputs while never paying out — user funds locked, plus fee accounting and `needed_fee`/`fee()` become incorrect (silent underflow at line 139-140 in release mode).

### Likelihood Explanation
Requires only that a `u64` payment amount close to `u64::MAX` propagates into `payments`. Amounts originate from user instructions and are not bound-checked against realistic ranges or `input_sat` before the additions at lines 187, 215, and 228, making the trigger cheap and deterministic.

### Recommendation
Use checked arithmetic throughout: compute `payment_sat` with `try_fold`/checked addition, replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, reject `payment_sat > input_sat` before fee math, and bound payment amounts to a sane maximum (≤ 21M * 10^8). Mirror the upstream fix's spirit — make the arithmetic wrap-safe — but prefer explicit `checked_*` + error over `unchecked` since the values here are genuinely attacker-controlled.
