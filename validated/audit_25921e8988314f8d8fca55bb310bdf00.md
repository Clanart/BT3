### Title
`get_first_op_return_output` selects the wrong OP_RETURN output when an attacker-controlled sighash flag leaves trailing payout-tx outputs unsigned - ([File: circuits-lib/src/bridge_circuit/mod.rs], [File: core/src/verifier.rs], [File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` always places the operator's attribution OP_RETURN at a fixed position (output index 2, after the user-payout output and the anchor output), but `get_first_op_return_output` — used both for `deposit_constant` computation and in `Verifier::update_finalized_payouts` — blindly returns the *first* OP_RETURN-scripted output it finds in the mined payout transaction, with no check on index or uniqueness. Because the user's payout signature only needs to commit to the input and its own payout output, an attacker who controls that signature's sighash flag can insert a spurious OP_RETURN output ahead of the genuine one, causing the wrong `operator_xonly_pk` to be attributed to the payout.

### Finding Description
The binding that must hold is:
`operator_xonly_pk (parsed by get_first_op_return_output + parse_op_return_data)` == `kickoff_data.operator_xonly_pk` (the value the true operator embedded at output index 2 in `create_payout_txhandler`).

`create_payout_txhandler` builds the canonical payout transaction as: output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN containing `operator_xonly_pk.serialize()`: [1](#0-0) 

Only the input and (by taproot key-spend semantics) the output paired to it need to be committed to by the signature that authorizes spending the withdrawal UTXO; nothing in this code path pins the number or position of the trailing outputs (anchor, OP_RETURN) once a sighash flag that excludes them (e.g. SIGHASH_SINGLE|ANYONECANPAY) is used for that signature.

`get_first_op_return_output` is then relied upon downstream to recover the attributed operator key, both for `deposit_constant` (via `host_deposit_constant`) and for `Verifier::update_finalized_payouts`: [2](#0-1) 

Because this helper walks the transaction's outputs and returns the *first* one whose script is an OP_RETURN, without validating that it sits at output index 2 or that it is the only OP_RETURN output, an attacker who can produce/replace a competing spend of the same withdrawal UTXO (permitted by the loosely-committed sighash) can insert a decoy OP_RETURN before the genuine one. `parse_op_return_data` will then extract the attacker's chosen 32 bytes as `operator_xonly_pk` instead of the true operator's key.

Downstream, `Verifier::update_finalized_payouts` uses this parsed value to record which operator is credited for the withdrawal; a mismatch against `kickoff_data.operator_xonly_pk` in `is_kickoff_malicious` results in the honest operator's legitimate reimbursement attribution being broken, which can lead to a Challenge/Disprove path burning the operator's collateral for a payout it genuinely and correctly made.

### Impact Explanation
If exploited, the honest operator that funded the payout can be flagged as having an invalid/malicious kickoff (because the recorded `operator_xonly_pk` from the payout transaction no longer matches their own kickoff data), leading to the operator's collateral being burned via Challenge/Disprove despite them behaving correctly. This is a Critical-class impact ("an honest operator's collateral burned") per the defined severity categories, and is repeatable across any withdrawal/payout for any operator, since the flaw is structural in `get_first_op_return_output` and not tied to a specific deposit or operator instance.

### Likelihood Explanation
Exploitability is gated entirely on whether the signature authorizing the withdrawal UTXO spend can be produced/accepted with a sighash flag (e.g. SIGHASH_SINGLE|ANYONECANPAY) that leaves the transaction's outputs beyond the paired payout output unconstrained. The threat model explicitly grants the attacker the capability to "choose... a Schnorr signature and its sighash flag" for withdrawal-related transactions, which is consistent with this precondition being attacker-satisfiable. Given that, the attacker only needs to broadcast (or race to have mined) a variant payout transaction that keeps output 0 identical (satisfying the committed portion of the signature) but injects an additional OP_RETURN output before the genuine attribution output — a cost of ordinary transaction fees, with no privileged access required. I was not able to directly confirm, within this investigation, the exact TapSighashType used when the withdrawal signature is produced/verified in `core/src/actor.rs`/`core/src/verifier.rs`, so full confirmation of this precondition depends on that code, which I did not have the opportunity to inspect in full detail.

### Recommendation
In `get_first_op_return_output`, do not return the first OP_RETURN output encountered. Instead:
- Pin the expected output index (index 2, as fixed by `create_payout_txhandler`) rather than scanning for "the first" OP_RETURN.
- Additionally validate that there is exactly one OP_RETURN output in the transaction, rejecting/erroring if more than one is present, to remove any ambiguity introduced by attacker-inserted decoy outputs.
- Ensure the signature scheme used to authorize the withdrawal UTXO spend commits to the full set of outputs (e.g., disallow SIGHASH_SINGLE/ANYONECANPAY for this signature, or otherwise pin the exact output structure) so the transaction shape cannot be mutated post-signing.

### Proof of Concept
`cargo test` plan (in `circuits-lib` or `core`, non-mainnet/non-live):
1. Build a payout transaction using `create_payout_txhandler` with a real `operator_xonly_pk`, producing the canonical layout (output 0 = payout, output 1 = anchor, output 2 = OP_RETURN with the real operator's key).
2. Construct a mutated variant of the same transaction that reuses the same input and output 0, but inserts an extra OP_RETURN output (containing attacker-chosen 32 bytes) at index 1, before the genuine OP_RETURN (which shifts to index 2 or later).
3. Call `get_first_op_return_output` on both transactions and assert:
   - On the canonical transaction: `parse_op_return_data(get_first_op_return_output(tx).script_pubkey) == real_operator_xonly_pk.serialize()`.
   - On the mutated transaction: `parse_op_return_data(get_first_op_return_output(mutated_tx).script_pubkey) == attacker_chosen_bytes`, NOT `real_operator_xonly_pk.serialize()`.
4. Feed the mutated transaction through `Verifier::update_finalized_payouts` and assert the recorded operator key equals the attacker's bytes rather than `kickoff_data.operator_xonly_pk`, demonstrating the attribution break.
