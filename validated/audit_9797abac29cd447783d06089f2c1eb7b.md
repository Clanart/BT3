## Analysis

The Bera Bitcoin report's root cause is a **security control implemented in one code path (`transfer`'s `notBlacklisted` modifier) but omitted from other paths that operate on the same trusted/untrusted boundary (`custodianMint`, `excessStakeMint`, `redeem`)**. GitHub Desktop has the exact same class of defect: a path-containment guard (`resolveWithin`, which uses `realpath` to defeat symlink traversal — see its dedicated test) is applied to the one file-open flow that was clearly flagged as attacker-reachable (`openRepositoryFromUrl`'s `filepath` deep-link parameter), but is **not** applied to the numerous other UI code paths that turn an attacker-controlled, repository-relative file path (from `git status`/`git diff`/PR file lists) into a filesystem path to open, reveal, or launch.

### Title
Symlink-escape path-containment guard (`resolveWithin`) applied to deep-link file opening but omitted from context-menu file actions (Reveal in File Manager / Open in External Editor / Open with Default Program) — ([File: app/src/lib/app-shell.ts])

### Summary
`resolveWithin()` in [1](#0-0)  resolves a repo-relative path and uses `realpath()` on both the root and the resolved target to guarantee the result cannot escape the repository root even via a symlink. This exact guard is used only in the deep-link handler `openRepositoryFromUrl`: [2](#0-1)  explicitly rejects absolute paths and calls `resolveWithin(repository.path, filepath)` before calling `shell.showItemInFolder`. A dedicated regression test confirms the symlink-escape scenario this guard defends against: [3](#0-2) .

However, the equivalent, far more commonly used functions that take a *repository-relative file path originating from committed/working-directory diff data* (which is fully attacker-controlled when the user views a cloned repo, a fetched branch, or a pull request's changed files) build the filesystem path with a plain `Path.join`/`join` and never validate containment:

- `revealInFileManager`: [4](#0-3) 
- `onOpenInExternalEditor` in the main app window: [5](#0-4) 
- PR "Files Changed" context menu ("Reveal in File Manager", "Open in External Editor", "Open with Default Program"): [6](#0-5) 
- Commit history file context menu: [7](#0-6) 
- Merge/rebase conflict resolution file menu: [8](#0-7) 
- Copilot conflict resolution overflow menu: [9](#0-8) 
- Changes list context menu: [10](#0-9) 

All of these ultimately call `shell.showItemInFolder`, `shell.openPath`/`launchExternalEditor`, or `shell.openExternal('file://...')` (via `openFile`, [11](#0-10) ) with a path built by naive concatenation of `repository.path` and an attacker-supplied relative `path`/`file.path` string, with no `resolveWithin`/`realpath` check.

### Finding Description
The broken invariant is: *"any filesystem path derived by joining the repository root with an attacker-influenced repo-relative path must be verified (post-symlink-resolution) to still reside inside the repository before being handed to a shell/file API."* The Desktop team already recognizes and enforces this invariant for one input vector (the `x-github-client://openRepo/...?filepath=` deep link) using `resolveWithin`, but the invariant is not enforced for the same class of input arriving through a different vector: a `path`/`file.path` string sourced from `git status`, commit diffs, or a GitHub pull request's changed-file list — all of which are populated from content that an attacker fully controls by crafting a malicious repository/branch/PR.

Because a tracked or working-tree entry in a git repository can be a symlink, an attacker can commit a symlink such as `evil -> ../../../../` (or, on Windows, a junction) at the current HEAD, and separately ensure a *different reachable commit or PR diff* references a nested path under that name (e.g., `evil/secrets.txt`) as changed/added. When the user browses that commit/PR in Desktop's UI and invokes "Reveal in File Manager", "Open in External Editor", or "Open with Default Program" on that entry, Desktop performs `Path.join(repository.path, 'evil/secrets.txt')`. Because the currently checked-out `evil` path on disk is a symlink pointing outside the repository, the OS resolves the joined path through the symlink to an arbitrary location outside the repo boundary — exactly the scenario the `resolveWithin` symlink test at [3](#0-2)  demonstrates is otherwise defended against.

### Impact Explanation
Successful exploitation lets a malicious repository/PR author cause Desktop to reveal, launch, or read a file (via the OS default-application handler, the external editor, or the file manager) outside the intended repository sandbox, purely by the victim interacting with normal, expected UI affordances (browsing history/PR files and using a context-menu action) on content the attacker fully controls. Depending on the target file/location and the launched program, this can lead to disclosure of sensitive files or, if the external editor/OS handler executes content based on file type, code execution — matching the "file write or read outside the repo" and "code execution" impact categories for a cloned/fetched-repository attacker.

### Likelihood Explanation
Likelihood is moderate-to-high for the "unprivileged, no local access" bar: the attacker only needs to author or contribute a repository/PR that gets cloned or reviewed (a routine, expected Desktop workflow), and the victim only needs to perform an ordinary action (open a PR's changed files, browse history, right-click → Reveal/Open). No admin rights, prior malware, or unnatural steps are required. The only complexity is git/OS-specific symlink semantics (POSIX symlink support differs from Windows), which is why the existing regression test in `path-test.ts` is itself gated on `!__WIN32__`, but macOS/Linux users remain squarely exposed.

### Recommendation
Route every repo-relative `path`/`file.path` value used by `revealInFileManager`, `onOpenInExternalEditor`, `openFile`, and all context-menu "Open"/"Reveal" handlers through `resolveWithin(repository.path, path)` (the same primitive already used in `dispatcher.ts`'s `openRepositoryFromUrl`), rejecting the action (with a log message, mirroring the existing `"Prevented attempt to open path outside of the repository root"` pattern) whenever the resolved path is `null`.

### Proof of Concept
1. Attacker crafts a repository where the current HEAD contains a symlink `evil -> ../../../../` (escaping several directory levels above the eventual clone location) committed as a normal tree entry.
2. Attacker creates another commit/branch (or opens a PR) where a file `evil/secret.txt` is shown as added/modified relative to HEAD, without ever checking that commit out (Desktop only needs to display it as a diff/PR file entry — it doesn't need to be the checked-out state).
3. Victim clones the repository or opens the PR in Desktop and browses to that commit's "Files Changed"/History view.
4. Victim right-clicks `evil/secret.txt` and selects "Reveal in File Manager" (or "Open in External Editor" / "Open with Default Program").
5. Desktop computes `Path.join(repository.path, 'evil/secret.txt')`. Because `evil` is a real, currently-checked-out symlink pointing outside the repository, the OS resolves the join through the symlink, and Desktop invokes `shell.showItemInFolder`/editor/`shell.openExternal` on a path outside the intended repository boundary — with no `resolveWithin` check to stop it, unlike the equivalent `filepath` deep-link handler in `dispatcher.ts`.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
