## #Vulnerability found

### Title
Missing remote-URL transport allowlist enables `ext::` shell execution via `git fetch` - (File: `app/src/lib/git/fetch.ts`, `app/src/lib/git/remote.ts`)

### Summary
`fetch()` in [1](#0-0)  never inspects `remote.url`'s scheme; it only forwards `remote.name` as the argv sink for `git fetch <name>`. Git itself then resolves `<name>` to the URL stored in `.git/config`, invoking whatever transport helper the URL's scheme designates. Nowhere in the remote lifecycle (`addRemote`, `setRemoteURL`, `getRemotes` in [2](#0-1) ) or in the git invocation helpers (`environment.ts`, `core.ts`) is the URL scheme validated or restricted, and GitHub Desktop never sets `GIT_ALLOW_PROTOCOL` to constrain git to safe transports (`http`, `https`, `ssh`, `git`). If a `remote.url` of the form `ext::sh -c id` is ever persisted as a remote's URL, a subsequent `git fetch <remotename>` will cause git's own `ext` transport to execute the embedded shell command — independent of any argv-injection concerns.

### Finding Description
`fetch()` builds args via `getFetchArgs(remote.name, ...)` [3](#0-2)  and runs `git(args, repository.path, 'fetch', opts)` [1](#0-0) . The URL is used only to compute environment variables for proxy resolution (`envForRemoteOperation`/`envForProxy`) [4](#0-3) , which only recognizes `http(s)://` and silently ignores everything else — no rejection or scheme allowlist occurs.

The actual URL used by `git fetch <name>` comes from whatever was stored via `git remote add`/`git remote set-url`: [5](#0-4) [6](#0-5) 

Neither `addRemote` nor `setRemoteURL` validate the `url` argument. Callers such as `_findPullRequestBranch` in `app-store.ts` add remotes using URLs sourced from data like `headCloneUrl` (e.g., a PR's fork clone URL), without scheme validation: [7](#0-6) 

`updateRemoteUrl` also writes a remote URL sourced from `apiRepo.clone_url` (an API-provided value) after only checking that URL *protocols* between old/new match via `URL.parse`, which does not reject non-standard schemes like `ext:`: [8](#0-7) 

There is no `GIT_ALLOW_PROTOCOL` (or equivalent) environment variable set anywhere in the git-invocation environment (`app/src/lib/git/environment.ts`, `app/src/lib/git/core.ts`), which is the standard mitigation upstream Git recommends for exactly this class of issue (git's `ext::`, `fd::`, and other helper transports executing arbitrary commands).

Git's own documentation for the `ext` transport explicitly warns that a URL like `ext::sh -c id` executes an arbitrary command, so this is git's expected/known behavior for that scheme — it's Desktop's job to keep such URLs from being written into `.git/config` or resolved for fetch/push/etc.

### Impact Explanation
If a malicious `remote.url` value reaches `addRemote`/`setRemoteURL` (e.g., a hostile fork's `clone_url` from a GitHub API response, or a repository whose `.git/config` an attacker can influence such as through a submodule or a crafted PR head repo), a subsequent `fetch()`, `_findPullRequestBranch`, or any other user-triggered fetch/pull will execute an attacker-chosen shell command via git's `ext::` transport — full unprivileged remote code execution.

### Likelihood Explanation
Exploitation requires the attacker to get a hostile URL persisted as a remote's URL (via API-controlled clone URLs or a hostile repository configuring/tricking Desktop into calling `addRemote`/`setRemoteURL`), and for Desktop or the user to subsequently trigger a fetch on that remote — a common, low-friction action (auto-background fetch, "Fetch origin", or PR review flow). No local access, admin rights, or unnatural user steps are needed beyond normal usage of a malicious repository or PR.

### Recommendation
- Validate and allowlist the scheme of any `IRemote.url` before it is written via `addRemote`/`setRemoteURL` or used to build `envForRemoteOperation`, rejecting anything outside `https:`, `http:` (if intentionally supported), `ssh:`, `git:`, and the `git@host:` SCP-like syntax.
- Set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or similarly restrictive) in the environment used for all git invocations (`app/src/lib/git/environment.ts` / `core.ts`) so that even if a hostile URL is present in `.git/config`, git itself refuses to use `ext::`/`fd::`/other unexpected transports.

### Proof of Concept
```ts
import { addRemote, fetch } from '../../src/lib/git'
// simulate an attacker-controlled clone URL, e.g. from a hostile fork's PR head.repo.clone_url
const remote = await addRemote(repository, 'evil', 'ext::sh -c id')
await fetch(repository, remote) // git fetch evil -> resolves ext:: transport -> executes `sh -c id`
```
Because neither `addRemote` nor `fetch`/`environment.ts` validate the scheme, and no `GIT_ALLOW_PROTOCOL` restriction is configured anywhere in the codebase, this reaches git's `ext` transport and executes the shell command.

export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}

/** Add a new remote with the given URL. */
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
