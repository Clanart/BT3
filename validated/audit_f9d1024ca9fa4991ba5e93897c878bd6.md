## Title
Discard Changes follows attacker-planted symlinks to delete/trash files outside the repository - (`app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges()` builds the on-disk path to remove with plain `Path.resolve`/`Path.join` against the repository root and the file path reported by `git status`, then hands that path directly to `shell.moveItemToTrash()` or `fs.rm()`. Unlike other file-touching code paths added later in this codebase (e.g. `resolveWithin` in `copilot-conflict-context.ts` and `dispatcher.ts`), this path is never validated to actually resolve inside the repository. A malicious/cloned repository that ships a symlinked directory can make a `git status` entry whose path component walks through that symlink, causing Desktop to trash or permanently delete a file located outside the user's repository when the user simply clicks "Discard changes".

Here `Path.resolve(this.repository.path, file.path)` and `Path.join(this.repository.path, file.path)` are lexical, string-based joins — they do not follow the filesystem to check whether any path segment is a symlink pointing outside the repository. If `file.path` is `some-symlinked-dir/leftover.txt` and `some-symlinked-dir` is a symlink checked into the repo (or created as a side effect of a build/hook the attacker's repo runs) that points to e.g. `../../../../.ssh` or an arbitrary user directory, the OS-level `moveItemToTrash`/`unlink` call will actually operate on the real target outside the repository, not inside it.

This project already recognizes and guards against exactly this class of bug elsewhere:
- `resolveWithin()` in `app/src/lib/path.ts` uses `realpath` on both the root and the resolved path and rejects anything that doesn't stay under the real root: [2](#0-1) 
- It is explicitly used to guard reading/writing files influenced by external content (Copilot conflict resolution, deep-link file opening): [3](#0-2) [4](#0-3) 
- Unit tests in this repo prove the symlink-escape scenario is real and specifically what `resolveWithin` was built to stop: [5](#0-4) 

`discardChanges()` (and the `rm(Path.join(...))` fallback path used when trashing fails) never calls `resolveWithin`/`realpath`, so the same class of attack that the newer code explicitly defends against is still reachable through the much older, high-privilege "Discard Changes" feature.

### Impact Explanation
Similar to the Astaria finding — where a destructive state-wipe (`settleAuction`/`payDebtViaClearingHouse`) could be triggered without the invariant (an actual completed auction) being true because of a missing/incorrect guard — here a destructive filesystem operation (trash/delete) can be triggered on a path outside the intended scope (the repository) because the code never verifies the resolved path is contained within the repository root, the same invariant `resolveWithin` enforces elsewhere. The result is file deletion or "trashing" outside the user's repository, driven entirely by content in a cloned/fetched repository the attacker controls (a symlink and a status entry pointing through it). Depending on the symlink target, this can destroy user files, config, or (in the `rm()` fallback branch, when the user has previously opted into "always discard permanently") permanently delete them with no trash recovery.

### Likelihood Explanation
Exploitation requires only that the victim clone/open an attacker-authored repository containing a symlink and then run the ordinary "Discard Changes" action (including "Discard All") on a file whose reported path traverses that symlink — no local access, admin rights, or social engineering beyond "open this repo" is needed. This is a normal, expected Desktop workflow, and the `moveItemToTrash` fallback to `rm()` is reachable once a user has previously answered the "discard permanently" confirmation, which many users do.

### Recommendation
Route the trash/delete path in `discardChanges()` (and its `rm()` fallback) through `resolveWithin(this.repository.path, file.path)` (or `resolveWithinPosix`/`Win32` as appropriate) before calling `shell.moveItemToTrash` or `rm`, refusing to operate (and surfacing a `DiscardChangesError`) whenever the resolved real path escapes the repository root — mirroring the guard already used in `copilot-conflict-context.ts` and `dispatcher.ts`.

### Proof of Concept
1. Attacker creates a repository containing a symlink `payload -> ../../../../home/victim` (or a Windows junction equivalent) and commits it.
2. Victim clones the repository in GitHub Desktop.
3. Through some interaction (e.g., an untracked file dropped by a build script, or simply having modified content nested under `payload/`), `git status` reports a changed/untracked file such as `payload/.ssh/id_rsa` or `payload/some-file`.
4. Victim selects that file (or "Discard All Changes") in the Changes list and confirms the Discard Changes dialog.
5. `GitStore.discardChanges()` computes `Path.resolve(repository.path, 'payload/some-file')` and calls `shell.moveItemToTrash(...)` (or `rm(...)` if trash fails and the user previously chose to discard permanently), which the OS resolves through the symlink and removes the file at the real, out-of-repository location — with no containment check ever performed.
