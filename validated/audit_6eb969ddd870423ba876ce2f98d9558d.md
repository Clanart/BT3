### Title
Independent per-vote consistency checks for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` allow an inverted (Lower > Upper) KIP-71 base-fee bound to be committed - (File: kaiax/gov/headergov/impl/header.go)

### Summary
`checkConsistency` validates a `Kip71LowerBoundBaseFee` vote against the *currently active* `UpperBoundBaseFee`, and a `Kip71UpperBoundBaseFee` vote against the *currently active* `LowerBoundBaseFee`, but it never validates a vote against another vote that is pending in the same epoch. Because governance votes accumulated within an epoch are only applied together at the next epoch boundary, two individually-valid votes cast in the same epoch can combine into an inconsistent final state where `LowerBoundBaseFee > UpperBoundBaseFee`. This mirrors the Surge `Factory.setFeeMantissa`/`setFeeRecipient` bug class: each setter/vote enforces a one-sided invariant against stale state, so sequencing two calls bypasses the intended invariant.

### Finding Description
`checkConsistency` handles the two KIP-71 bound votes as follows: [1](#0-0) 

```
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) > params.UpperBoundBaseFee { return ErrLowerBoundBaseFee }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) < params.LowerBoundBaseFee { return ErrUpperBoundBaseFee }
```

`h.GetParamSet(blockNum)` returns the *committed* parameter set from the last processed epoch, not a value reflecting any other vote already cast within the current (not-yet-committed) epoch. Votes accumulated during an epoch are batched and only take effect together in `getExpectedGovernance`/`VerifyGov` at the next epoch boundary: [2](#0-1) [3](#0-2) 

`VerifyGov` only checks that the committed `Governance` bytes exactly match the votes collected in the previous epoch (structural/format equality); it performs no cross-parameter consistency re-check of the final combined `ParamSet` before accepting the block.

Exploit sequence within a single epoch (assume current state `Lower=5, Upper=50`):
1. Vote A: `Kip71LowerBoundBaseFee = 40` → checked against stale `Upper=50` → `40 <= 50` passes.
2. Vote B (later in the same epoch, e.g. a different proposer block or same governing node in "single" mode): `Kip71UpperBoundBaseFee = 30` → checked against stale `Lower=5` (vote A hasn't taken effect yet) → `30 >= 5` passes.
3. At the next epoch boundary, both votes are committed together, yielding the final state `Lower=40, Upper=30`, i.e. `Lower > Upper`, which was never directly validated as a pair.

### Impact Explanation
`LowerBoundBaseFee`/`UpperBoundBaseFee` are the KIP-71 governance bounds that clamp the dynamically-computed base fee each block. Committing an inverted bound (`Lower > Upper`) corrupts the KIP-71 base-fee clamping logic used for gas pricing and transaction-pool admission across the network, which can cause abnormal fee computation, inconsistent admission behavior between honest nodes if they diverge in how they clamp an invalid range, and disruption of the transaction market — matching the "KIP-71 pricing" scope explicitly called out as reachable and impactful.

### Likelihood Explanation
The vote is reachable via the public `governance_vote` RPC, gated only by council membership (or the single governing node in "single" governance mode) — no special node/validator privilege beyond being a valid voter for the chain's configured governance mode is required: [4](#0-3) 
Executing the sequence requires only two votes within one epoch, which any eligible voter (or, in "single" mode, the governing node alone, which is the described operator-analog in the reported bug) can trivially arrange by ordering the two calls.

### Recommendation
When validating a `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` vote in `checkConsistency`, resolve the *effective* opposing bound by also checking any already-collected pending vote for the other parameter within the current epoch (via `getVotesInEpoch`/`groupedVotes`) rather than only the last-committed `ParamSet`. Additionally, `VerifyGov` should re-validate the fully-combined governance parameter set for such cross-parameter invariants (e.g. `Lower <= Upper`) before accepting an epoch's governance payload, rather than relying solely on individual, sequentially-stale per-vote checks.

### Proof of Concept
1. Start an epoch with `Kip71LowerBoundBaseFee=5`, `Kip71UpperBoundBaseFee=50`.
2. Within the same epoch, submit `governance_vote("kip71.lowerboundbasefee", 40)` — passes since `40 <= 50` (stale `Upper`).
3. Later in the same epoch, submit `governance_vote("kip71.upperboundbasefee", 30)` — passes since `30 >= 5` (stale `Lower`).
4. At the epoch boundary, `getExpectedGovernance` aggregates both votes and `VerifyGov` accepts the header since it only performs a structural equality check against the vote-derived map — no invariant re-check is performed.
5. Result: the chain's active KIP-71 `ParamSet` now has `LowerBoundBaseFee(40) > UpperBoundBaseFee(30)`, an unvalidated inverted bound governing subsequent base-fee computation.

// VerifyGov checks the following:
// (1) governance must be empty in non-epoch block,
// (2) if there are no votes in the previous epoch, governance must be empty,
// (3) if any vote exists in the previous epoch, governance must not be empty,
// (4) the json must not contain unknown fields,
// (5) the parsed json must exactly match the map derived locally from the previous epoch's votes.
func (h *headerGovModule) VerifyGov(header *types.Header) error {
	// (1)
	if header.Number.Uint64()%h.epoch != 0 {
		if len(header.Governance) > 0 {
			logger.Error("governance is not allowed in non-epoch block", "num", header.Number.Uint64())
			return ErrGovInNonEpochBlock
		} else {
			return nil
		}
	}

	// (2), (3)
	expected := h.getExpectedGovernance(header.Number.Uint64())
	if len(header.Governance) == 0 {
		if len(expected.Items()) != 0 {
			return ErrGovVerification
		}

		return nil
	}

	// (4)
	var gb headergov.GovBytes = header.Governance
	actual, err := gb.ToGovData()
	if err != nil {
		logger.Error("DeserializeHeaderGov error", "num", header.Number.Uint64(), "governance", gb, "err", err)
		return err
	}

	// (5)
	if !reflect.DeepEqual(expected, actual) {
		logger.Error("Governance mismatch", "expected", expected, "actual", actual)
		return ErrGovVerification
	}

	return nil
}

// The blockNum's epoch index must be greater than 0. That is, it must be blockNum >= epoch.
func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}

func (api *headerGovAPI) Vote(name string, value any) (string, error) {
	var (
		voter     = api.h.nodeAddress
		nextBlock = api.h.Chain.CurrentBlock().NumberU64() + 1
		gp        = api.h.GetParamSet(nextBlock)
		gMode     = gp.GovernanceMode
	)

	if gMode == "single" && voter != gp.GoverningNode {
		return "", ErrVotePermissionDenied
	}

	vote := headergov.NewVoteData(voter, name, value)
	if vote == nil {
		return "", ErrInvalidKeyValue
	}

	if gov.DeprecatedAt(vote.Name(), api.h.ChainConfig.Rules(new(big.Int).SetUint64(nextBlock))) {
		return "", ErrDeprecatedVote
	}

	err := api.h.checkConsistency(nextBlock, vote)
	if err != nil {
		return "", err
	}

	// TODO-kaiax: add removevalidator vote check

	api.h.PushMyVotes(vote)
	return "(kaiax) Your vote is prepared. It will be put into the block header or applied when your node generates a block as a proposer. Note that your vote may be duplicate.", nil
}
