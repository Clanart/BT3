Based on my research, I found a concrete, already-documented instance of exactly this bug class inside Hyperbridge's own `IntentGatewayV2` contract — and evidence that a second, independently-maintained copy of the same contract for Tron may not carry the fix.

### Title
Partial-fill rounding-dust truncation can permanently lock/lose escrowed funds in `IntentGatewayV2` — risk of un-patched exposure in the Tron fork - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core invariant is: *integer-division rounding in a proportional-release calculation must never let a portion of the pooled/escrowed principal become permanently stuck or steal-able*. Hyperbridge's mainline `IntentGatewayV2.sol` contains exactly this bug class in its partial-fill escrow release math, and it required an explicit fix (tracked in the test suite as "Finding #4"). `evm/tron/contracts/apps/IntentGatewayV2.sol` is a separately maintained, near-duplicate copy of the same intent-settlement contract (different code style for the same operations, e.g. commitment computation), and it is not proven to carry the same fix.

### Finding Description
When a solver partially fills an intent order, the gateway releases escrowed input tokens to the solver proportionally to the fraction of the requested output the solver supplied:

```
release = (escrowedInputAmount * solverOutputAmount) / requestedOutputAmount
```

This is integer division, and with amounts like `input = 100e6`, `output = 3e18`, three sequential 1-DAI fills each truncate to `33333333` instead of `33333333.33...`, leaving `1` unit of escrow undistributed after all fills complete — the same class of rounding error described in the LP report, just applied to order escrow instead of LP share minting. [1](#0-0) 

The mainline contract's regression tests (`testPartialFill_RoundingDustReleasedToFinalSolver`, `testPartialFill_RoundingDustReleasedToFinalSolver_NativeETH`) explicitly exercise and confirm a fix: the **final** solver that completes an order receives the gateway's *remaining balance* rather than the truncated proportional share, so no dust is left locked. [2](#0-1) 

`evm/tron/contracts/apps/IntentGatewayV2.sol` is a distinct source file for the Tron/TVM deployment of the same `IntentGatewayV2` logic — its `placeOrder` implements the identical fee-reduction/commitment flow but with different internal structuring (it duplicates `order.inputs` into a local `originalInputs` and temporarily swaps it, rather than building `reducedInputs` directly as the mainline EVM version does), confirming it is hand-maintained separately rather than symlinked/shared. [3](#0-2) 

A `grep` of that file confirms it implements the same `_orders[...]`-keyed escrow accounting and proportional/partial-fill/`remainingAmount`/`solverAmount` release logic as the mainline contract (16 matches for these identifiers), meaning it is exposed to the same rounding-truncation math — but I could not verify from the available index content whether its fill-release function was updated with the "final solver gets the remaining balance" guard that the mainline contract needed.

### Impact Explanation
If the Tron copy's fill-release logic still divides `escrowedAmount * solverOutput / requestedOutput` without directing leftover dust to the last fill, then every multi-solver partial fill on that chain permanently strands a small amount of the user's escrowed principal in the contract — unauthorized loss of user funds with no recovery path, matching the bounty's "stealing or loss of funds" and "logic attacks" categories. This is a public-entrypoint issue (`fillOrder`), reachable by any solver with no special privileges, and requires no malicious relayer/prover/admin assumption.

### Likelihood Explanation
Medium-to-low confidence pending confirmation of the exact release-calculation code in the Tron file (which the available tooling did not surface in full). The bug pattern is proven to exist and to have required a dedicated fix in the sibling contract, and the Tron contract is confirmed to duplicate the vulnerable computation surface (escrow, proportional release, `_orders` mapping) independently. Multi-solver partial fills of an order are a normal, expected usage pattern (not an edge case), so if unpatched, the bug would trigger under ordinary conditions, not just adversarial ones.

### Recommendation
Diff `evm/tron/contracts/apps/IntentGatewayV2.sol`'s partial-fill release function against the patched mainline `_fillSameChain`/`_fillCrossChain` logic in `evm/src/apps/IntentGatewayV2.sol` and confirm it applies the same "release remaining escrow balance to the fill that completes the order" guard rather than a raw truncated proportional computation. Add the same Foundry regression tests (`testPartialFill_RoundingDustReleasedToFinalSolver*`) to the Tron test suite so future changes to either copy cannot silently reintroduce the rounding-dust bug. More generally, since these two contracts are maintained as independent copies rather than a single shared source, establish a CI check that diffs their core settlement logic to prevent fix drift.

### Proof of Concept
Using the same scenario proven against the mainline contract (input escrow = 100 USDC, requested output = 3 DAI, three solvers each filling 1 DAI):
1. Solver 1 fills 1 DAI → receives `(100e6 * 1e18) / 3e18 = 33333333` USDC (truncated).
2. Solver 2 fills 1 DAI → receives another `33333333` USDC.
3. Solver 3 fills the final 1 DAI, completing the order.
4. If the Tron contract computes solver 3's release the same truncated way instead of paying out the gateway's remaining balance, `1` unit of USDC (and proportionally more for larger/odder ratios) remains stuck in the contract forever, unrecoverable by the user or any solver — this is exactly the pattern the mainline contract's dedicated "Finding #4" tests were written to prevent. [4](#0-3) 

**Caveat:** I was unable to read the specific fill-release computation inside `evm/tron/contracts/apps/IntentGatewayV2.sol` within the available tool budget to confirm definitively whether the fix is present or absent there — this should be verified directly against that file's `_fillSameChain`/`_fillCrossChain`-equivalent code before treating this as confirmed-exploitable.
