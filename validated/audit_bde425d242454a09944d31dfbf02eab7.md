### Title
Reward-tier double counting via `mWomSV.startUnlock` manipulation of `calDoubledCounted` - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount`/`calDoubledCounted` in `ArbWomUp3.sol` compute the "already rewarded" portion of a user's incentive tier purely from the live, mutable value `mWomSV.getUserTotalLocked(_account)` [1](#0-0) . Because that balance can be reduced at will by the user (e.g. via `mWomSV.startUnlock`, moving locked mWOM into cooldown), the "subtract what was already counted" logic can be defeated, allowing the same tier bracket to be paid out multiple times.

### Finding Description
In `incentiveDeposit`, when `_mode == 2` (lock path), the reward is computed by `getRewardAmount(_amount, msg.sender, true)` **before** `_deposit` locks the new tokens into `mWomSV` [2](#0-1) . Inside `getRewardAmount`, the incremental reward is:
```
accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)
rewardAmount = f(accumulated)   // tier walk
mgpReward = rewardAmount/DENOMINATOR - calDoubledCounted(_account)
```
where `calDoubledCounted(_account)` recomputes `f(mWomSV.getUserTotalLocked(_account))` from the account's *current* locked balance [3](#0-2) .

This design assumes `mWomSV.getUserTotalLocked` only increases over time (i.e., it is a monotonic proxy for "total amount ever rewarded"). It is not: mWOM lockers typically support `startUnlock`/`cooldown` mechanics that reduce the locked total when a user begins unlocking. Once a user's locked total decreases, `calDoubledCounted` returns a smaller number than the reward actually already paid for that bracket. A subsequent `incentiveDeposit(_mode=2)` call recomputes the deduction from the lowered balance, so the same tier range (already paid once) is paid out again when the accumulated total climbs back through it.

Note the contract does contain a `bracketRewarded` mapping that appears intended to be the fix for exactly this problem (a monotonic, stored record of rewards already paid), but it is explicitly annotated `// not in use` and is never read or written anywhere in the contract [4](#0-3) . This confirms the deduction is only ever derived from the live balance, with no persisted/monotonic accounting to fall back on.

Existing guards (`nonReentrant`, `whenNotPaused`, `_checkAmount`) do not address this because the exploit does not depend on reentrancy or a zero amount — it depends purely on the state of `mWomSV.getUserTotalLocked` being manipulable between two `incentiveDeposit` calls.

### Impact Explanation
An attacker can repeatedly claim MGP incentive rewards for the same WOM-lock tier bracket by cycling: lock → `startUnlock` (reduce recorded locked total) → deposit again to cross the same tier thresholds. Each cycle drains additional MGP from the contract's reward balance (`vlMGP.lockFor(rewardToSend, msg.sender)`), even though `mgpReward` is capped by `IERC20(mgp).balanceOf(address(this))` [5](#0-4) . This is a direct theft of the protocol's MGP reward reserve funded from the contract balance, disproportionate to any net new WOM actually locked — matching a Critical, direct-theft-of-funds impact class.

### Likelihood Explanation
Requires only: (1) the attacker's own WOM/mgp-convertible tokens purchased on market, (2) the ability to call `mWomSV.startUnlock` on their own locked position (a normal, permissionless user action), and (3) repeated calls to `incentiveDeposit` with `_mode == 2`. No privileged role is needed, and the cycle is repeatable across multiple accounts/transactions, limited only by available reward MGP balance and cooldown timing constraints of `mWomSV`. Exact feasibility (e.g., whether cooldown period blocks re-locking before the tier reward can be re-triggered, or whether `getUserTotalLocked` includes cooling-down amounts) depends on `mWomSV.sol`'s cooldown implementation, which could not be fully inspected in this session — this is a caveat on precise timing/repeatability, not on the existence of the flaw itself.

### Recommendation
Replace the live-balance-derived deduction with a persisted, monotonically increasing record of rewards paid per account (e.g., actually use and update the existing `bracketRewarded` mapping, incrementing it by `mgpReward` on every successful `incentiveDeposit`, and using `bracketRewarded[_account]` instead of `calDoubledCounted(_account)` as the "already rewarded" subtrahend). Do not derive already-rewarded amounts from any balance that the user can independently decrease (`mWomSV.getUserTotalLocked`).

### Proof of Concept
Hardhat/Foundry test plan (fork test):
1. Deploy/point to `ArbWomUp3`, `mWomSV`, `mWom`, `wom`, `mgp`, `vlMGP`, `smartWomConvert` per `__arbWomUp_init`; fund the contract with MGP and set up `rewardTier`/`rewardMultiplier` via `setMultiplier`.
2. Attacker acquires enough WOM to cross tier 1 threshold; calls `incentiveDeposit(amount1, ratio, false, 2)`. Assert MGP reward locked into `vlMGP` for attacker equals `f(tier1)/DENOMINATOR * 2` (mode-2 doubling) and record `mWomSV.getUserTotalLocked(attacker)`.
3. Attacker calls `mWomSV.startUnlock(...)` to move some/all of the locked mWOM into cooldown, reducing `mWomSV.getUserTotalLocked(attacker)`.
4. Attacker calls `incentiveDeposit(amount2, ratio, false, 2)` with a small `amount2` sufficient to push `accumulated` back past the same tier threshold crossed in step 2.
5. Assert: total MGP rewarded to attacker across steps 2 and 4 exceeds `f(amount1+amount2)/DENOMINATOR * 2` (i.e., the bracket between the reduced balance and the original locked total is paid twice), and that `bracketRewarded[attacker]` (if it were used) would show no growth reconciling with `calDoubledCounted(attacker)`, confirming the missing monotonic accounting.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
