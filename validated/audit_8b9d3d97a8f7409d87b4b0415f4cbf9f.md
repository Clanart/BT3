### Title
Integer-overflow/sign-truncation in `ParseDelimitedFromCodedStream` disables intended message boundary, letting parser consume/merge bytes belonging to subsequent records - ([File: src/google/protobuf/util/delimited_message_util.cc])

### Summary
`google::protobuf::util::ParseDelimitedFromCodedStream()` (and its wrapper `ParseDelimitedFromZeroCopyStream()`) reads an attacker-controlled length prefix with `CodedInputStream::ReadVarint32()` and passes it to `PushLimit()` via a raw `static_cast<int>(size)`. If the wire-encoded length is in `[0x80000000, 0xFFFFFFFF]` (i.e. > `INT_MAX`), the cast produces a negative `int`. `CodedInputStream::PushLimit()` explicitly rejects negative limits and silently *does not install the intended boundary*, leaving the previous (effectively unbounded) limit in effect. `MergeFromCodedStream()` then parses past the intended record boundary into whatever comes next in the stream (e.g., subsequent delimited records), merging their fields into the caller's message object, before a downstream consistency check finally rejects the call. This is analogous to the RAUC bug: an integer-overflowed/truncated size computation silently disables the intended coverage boundary, and data outside the (mis-)computed boundary is trusted/processed before any check catches the mismatch.

### Finding Description
`ParseDelimitedFromCodedStream` is implemented as: [1](#0-0) 

Key steps and the failure:
1. `input->ReadVarint32(&size)` reads an unsigned 32-bit length prefix. `ReadVarint32` is documented to *truncate to 32 bits without error* rather than reject values that don't fit — it is explicitly the wrong primitive for reading a "size", as the library's own guidance states: [2](#0-1) 

The comment for `ReadVarintSizeAsInt` explicitly warns: "when we are parsing a size from the wire, truncating the value would result in us misparsing the payload" — yet `ParseDelimitedFromCodedStream` uses `ReadVarint32`, not `ReadVarintSizeAsInt`, for exactly this size-reading purpose.

2. The 32-bit unsigned `size` (which can legally be up to `0xFFFFFFFF`, i.e. up to ~4 GiB) is narrowed with `static_cast<int>(size)` and handed to `PushLimit`. For any `size > INT_MAX` this cast yields a negative value.

3. `CodedInputStream::PushLimit()` has an explicit "security" check for exactly this case: [3](#0-2) 

Because `byte_limit >= 0` is false, the branch is not taken: `current_limit_` is left **unchanged** (i.e., whatever the enclosing/outer limit was — typically the stream's default, effectively unbounded within `INT_MAX`/`total_bytes_limit_`). The intended per-record boundary is silently never installed — the “signature check equivalent” (the boundary that is supposed to make the parser trust only the bytes belonging to this record) is bypassed.

4. `message->MergeFromCodedStream(input)` now parses using the old, much larger limit. Because there is no functional boundary at the intended record end, a well-formed subsequent delimited record (or any subsequent bytes that happen to parse as valid tags/values for the same message type) will be consumed and merged into `*message` as if they belonged to the current record.

5. Only *after* this merge has already mutated `message`, the function performs two integrity checks:
   - `input->ConsumedEntireMessage()` (checks the state of `legitimate_message_end_`, tied to `current_limit_`)
   - `input->CurrentPosition() - position_after_size != static_cast<int>(size)`

Because `size` was cast to a negative int, the second check almost always fails (an actual, positive byte count cannot equal a wrapped-negative value), and the function does return `false`. However, by this point `MergeFromCodedStream` has already run and populated `*message` with fields drawn from data that was never intended to be part of this record (potentially spanning into the next delimited record in the stream). This mirrors RAUC's flaw precisely: a length value is subjected to narrower-than-necessary integer arithmetic, the resulting boundary/coverage silently diverges from the true intended boundary, and data outside the true boundary is processed/trusted before the mismatch is (eventually, but too late) detected.

### Impact Explanation
An "ordinary client" producing a bounded stream of concatenated, length-delimited protobuf messages (a common, publicly documented use case for `SerializeDelimitedTo*`/`ParseDelimitedFrom*`, e.g. logging pipelines, message queues, gRPC-adjacent framing) can craft one record whose length prefix is in `[0x80000000, 0xFFFFFFFF]`. This disables the intended per-record boundary for that call. The immediate practical consequence is a merge-field-confusion / cross-record data-integrity failure: fields intended for record N+1 (or beyond) get merged into the `Message` object the caller believes represents record N, even though the function ultimately returns `false`. Applications that (as documented protobuf semantics permit, but many do in practice) inspect a partially-populated message after a failed parse, or that don't fully discard/reset the message object on failure, can be misled into acting on attacker-mixed field data. This is an integrity failure of the record-boundary mechanism, matching a Medium-severity “data can be tampered with outside the verified/trusted boundary” class, analogous to RAUC's signature-scope truncation. It stops short of memory corruption/RCE since all reads remain governed by the underlying `total_bytes_limit_`/stream bounds and normal wire-format decoding rules.

### Likelihood Explanation
Reaching the vulnerable path requires only calling the fully public `ParseDelimitedFromCodedStream`/`ParseDelimitedFromZeroCopyStream` APIs on attacker-supplied bytes — a common pattern for length-delimited message streams — and crafting one 5-byte varint length prefix with the top bit pattern in the affected range. No privileged access, hostile schema, or huge (multi-GB) input is required; the record's declared length just needs to exceed `INT_MAX` (2^31−1) while the actual bytes present can be arbitrarily small (the mismatch/negative-cast happens purely from the *declared* length, not from actually needing to send billions of bytes). This makes the trigger condition easy to construct with a small, bounded payload.

### Recommendation
In `ParseDelimitedFromCodedStream` (src/google/protobuf/util/delimited_message_util.cc), replace `input->ReadVarint32(&size)` + `PushLimit(static_cast<int>(size))` with the overflow-safe `CodedInputStream::ReadVarintSizeAsInt()`, which rejects (returns `false`) any declared size that does not fit in a non-negative `int`, before any limit is pushed or any merge is attempted. This mirrors the safety property already implemented and documented for `ReadVarintSizeAsInt` and used correctly elsewhere (e.g. `WireFormatLite::ReadPackedPrimitive`). Additionally, consider having `PushLimit`'s "limit not applied" branch surface an explicit error to the caller rather than silently retaining the old limit, since silent no-ops on malformed/negative limits are what allowed the subsequent merge to proceed unbounded.

bool ParseDelimitedFromCodedStream(MessageLite* message,
                                   io::CodedInputStream* input,
                                   bool* clean_eof) {
  if (clean_eof != nullptr) *clean_eof = false;
  int start = input->CurrentPosition();

  // Read the size.
  uint32_t size;
  if (!input->ReadVarint32(&size)) {
    if (clean_eof != nullptr) *clean_eof = input->CurrentPosition() == start;
    return false;
  }

  // Get the position after any size bytes have been read (and only the message
  // itself remains).
  int position_after_size = input->CurrentPosition();

  // Tell the stream not to read beyond that size.
  io::CodedInputStream::Limit limit = input->PushLimit(static_cast<int>(size));

  // Parse the message.
  if (!message->MergeFromCodedStream(input)) return false;
  if (!input->ConsumedEntireMessage()) return false;
  if (input->CurrentPosition() - position_after_size != static_cast<int>(size))
    return false;

  // Release the limit.
  input->PopLimit(limit);

  return true;
}

CodedInputStream::Limit CodedInputStream::PushLimit(int byte_limit) {
  // Current position relative to the beginning of the stream.
  int current_position = CurrentPosition();

  Limit old_limit = current_limit_;

  // security: byte_limit is possibly evil, so check for negative values
  // and overflow. Also check that the new requested limit is before the
  // previous limit; otherwise we continue to enforce the previous limit.
  if (ABSL_PREDICT_TRUE(byte_limit >= 0 &&
                        byte_limit <= INT_MAX - current_position &&
                        byte_limit < current_limit_ - current_position)) {
    current_limit_ = current_position + byte_limit;
    RecomputeBufferLimits();
  }

  return old_limit;
}
