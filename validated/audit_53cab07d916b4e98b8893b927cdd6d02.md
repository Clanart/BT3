### Title
Unregistered-participant index in blame decryption panics (`self.enc_keys[&decryptor]`), a remotely-triggerable DoS — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The bug class in CVE-2020-14799 is an unauthenticated-adjacent denial of service: input reaching a crypto/encryption code path causes a hang or crash of the process. The analog in Serai is `Decryption::decrypt_with_proof` in `crypto/dkg/pedpop/src/encryption.rs`, which indexes the `enc_keys` HashMap with an attacker-influenced `decryptor` participant index. `HashMap` indexing (`map[&key]`) panics when the key is absent, so a blame/accusation message naming a `decryptor` participant whose encryption key was never registered aborts the process instead of returning an error.

### Finding Description
`Decryption` maintains `enc_keys: HashMap<Participant, C::G>` populated by `register`, which inserts one entry per participant message (`encryption.rs:351-361`). During the blame path, `decrypt_with_proof` verifies the accused's per-message PoP and then checks the accuser's `EncryptionKeyProof` DLEq against `self.enc_keys[&decryptor]` (`encryption.rs:381-389`):

```rust
// crypto/dkg/pedpop/src/encryption.rs
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // panics if `decryptor` never registered
  )
  .map_err(|_| DecryptionError::InvalidProof)?;
```

The `decryptor` parameter is a `Participant` value derived from the accusation being processed — bytes the accusing party controls (it determines whose registered key the DLEq must match). `Participant::new` only enforces `1 <= p <= u16::MAX`-style bounds; nothing requires `decryptor` to have had an `EncryptionKeyMessage` registered in `enc_keys`. A valid-but-unregistered index causes `HashMap`'s `Index` impl to panic, unwinding/aborting the DKG participant rather than returning `DecryptionError`.

The same file contains a second panic-prone assertion on the registration path: `register` asserts `!self.enc_keys.contains_key(&participant)` ("Re-registering encryption key for a participant", `encryption.rs:356-359`), which converts a duplicate registration into a panic rather than an error — a related liveness hazard if a participant's encryption-key message is ever replayed or processed twice by the caller.

### Impact Explanation
A crash in the PedPoP DKG share-verification/blame path halts the node's DKG session, which under CVSS terms is an availability impact (complete DoS of the affected component). Because the panic occurs while processing accusation material supplied by another party, an attacker can selectively crash honest participants who process their malformed blame — delaying or aborting key generation and, in threshold systems, forcing expensive restart/abort handling.

### Likelihood Explanation
Medium likelihood: the attacker must be able to get an honest node to run `decrypt_with_proof` on an accusation where `decryptor` does not correspond to a registered encryption key. That is attacker-reachable whenever the accuser controls which decryptor index the message claims (the function takes `decryptor` as an argument with no membership check), but it requires triggering the blame/decryption flow rather than the common path, which lowers the likelihood below a trivially reachable parser panic.

### Recommendation
Replace the `HashMap` index with a checked lookup:

```rust
let Some(decryptor_key) = self.enc_keys.get(&decryptor).copied() else {
  return Err(DecryptionError::InvalidProof);
};
```

and use `decryptor_key` in the DLEq statement list. Similarly, in `register`, return an error (or drop the duplicate) instead of `assert!`-ing on re-registration, since duplicate handling is dictated by peer input timing, not by a local invariant the caller can guarantee. Audit `encrypt` (`self.decryption.enc_keys[&participant]`, `encryption.rs:466`) for the same unchecked-index pattern.

### Proof of Concept
1. Set up `ThresholdParams`/`Decryption::new(context)` for ciphersuite `C`.
2. Register encryption keys for some subset of participants via `register(participant, EncryptionKeyMessage)` such that participant `P` is **not** in `enc_keys`.
3. Call `decrypt_with_proof::<E>(from, P, msg, Some(proof))` where `msg` carries a valid PoP (so the early `InvalidSignature` branch is skipped) and `proof` is any `EncryptionKeyProof`.
4. Execution reaches `self.enc_keys[&decryptor]` with `decryptor == P` absent → `HashMap` index panic (`thread panicked at 'key not found'`), crashing the participant instead of yielding `DecryptionError`.

Note: the exact reachability depends on the caller permitting an arbitrary `decryptor` index into `decrypt_with_proof`; I could not fully trace the pedpop blame caller within the available iterations, so the trigger path is inferred from the function's public-in-crate signature. If callers already constrain `decryptor` to registered participants, this degrades to defense-in-depth rather than an exploitable crash.
