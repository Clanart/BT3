### Title
Bitcoin deposits below `N::DUST` are silently discarded by the scanner — received funds are never reported, never credited, and are permanently unspendable - (File: processor/src/multisigs/scanner.rs)

### Summary
Analogous to the Yearn report's "losses at an inner layer are never reported to the parent vault and never reconciled," the processor's block scanner silently drops any Bitcoin output matched to a multisig script whose value is below `N::DUST` (10,000 satoshis for Bitcoin). The output was genuinely received on-chain at a Serai-controlled address, but no event is emitted, the outpoint is never recorded, and no recovery path exists. The protocol's reported balance permanently diverges from its actual on-chain balance, and the depositor's funds are stranded.

### Finding Description
In the scanner's block-processing loop, each output returned by `network.get_outputs(&block, key)` is gated on a dust check before being pushed into the emitted `outputs` vector:

```rust
// processor/src/multisigs/scanner.rs
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
``` [1](#0-0) 

For Bitcoin, `Bitcoin::DUST` is defined as `10_000` satoshis — roughly 18× the actual spendability threshold the code itself computes (57 vbytes/input × 5 sat/vbyte ≈ 285 sats; padded to ~1,000 sats even under extreme size assumptions). [2](#0-1) 

Dropped outputs escape every tracking mechanism: they are not emitted in `ScannerEvent::Block`, so `ack_block` never returns them; they are not inserted into `ram_outputs` or the `seen` DB set (that loop only iterates the filtered `outputs`), so they are not even remembered; and no manual rebalancing/recovery function exists — precisely the "losses are never fixed" defect from the reference report. [3](#0-2) 

The wallet layer confirms such outputs *are* spendable: `SignableTransaction::new` only enforces `DUST = 546` on *payments it creates*, and imposes no minimum on `inputs` — an input of 9,999 sats is a perfectly valid, profitable input at normal fee rates. [4](#0-3) 

### Impact Explanation
Any Bitcoin transaction paying a registered Serai address (external, branch, change, or forward — all reachable via `scanner(key)` offsets) with `330 <= value < 10_000` sats is received but never credited and never spendable through the protocol. This is a direct balance-sheet loss: the vault "reports" fewer assets than it holds, with no mechanism to reconcile, mirroring the report's underreported-loss / unreconciled-debt bug class. Losses accumulate unboundedly across deposits; griefing aside, ordinary users making small deposits silently lose 100% of funds.

### Likelihood Explanation
Fully reachable by an unprivileged party with a public input: any Bitcoin user can broadcast a transaction paying the public multisig address with an amount under 10,000 sats. No validator collusion, key access, or protocol misuse is required — the sender isn't even "at fault," since nothing on-chain or in the address format communicates a minimum. Note the check is per-output, so a large transaction containing one small output to Serai still loses that output.

### Recommendation
Emit dropped outputs as a distinct event (or record their outpoints as "seen") so they are accounted for and can later be aggregated once economical; or lower `Bitcoin::DUST` to the code's own computed spendability bound (~1,000 sats); or provide a manual recovery path allowing the scheduler to consolidate sub-`DUST` outputs — the analog of the report's recommended "rebalance debt/collateral to make reported funds equal available funds."

### Proof of Concept
1. Retrieve the Serai multisig external address for the active group key (`external_address`/`address_from_key`, `processor/src/networks/bitcoin.rs:578`).
2. Broadcast a Bitcoin transaction paying, e.g., 5,000 sats to that P2TR script; wait for `CONFIRMATIONS` (6) blocks.
3. `get_outputs` returns the `Output` (the script matches via `Scanner::scan_transaction`), but `output.balance().amount.0 < N::DUST`, so it is dropped at `processor/src/multisigs/scanner.rs:564`.
4. Observe: no `ScannerEvent::Block` contains the output, the outpoint is absent from `ram_outputs`/DB, and the scheduler never sees it — the 5,000 sats are permanently uncredited and unspendable despite being a valid, economically spendable UTXO.
