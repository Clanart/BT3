Based on the investigation, the strongest analog to the "check exists but doesn't actually validate/gate the operation" bug class is in the `open-external` IPC handler in the Electron main process.

### Title
`open-external` IPC handler logs but never enforces an HTTP(S)-only allowlist before calling `shell.openExternal()` - (File: `app/src/main-process/main.ts`)

### Summary
GitHub Desktop's main process exposes an `open-external` IPC handler that renderer code (link buttons, markdown link clicks, "open in browser" actions, etc.) calls whenever the user clicks a link rendered from data the app displays — including content that ultimately originates from a cloned/fetched repository or the GitHub API (e.g., PR/issue/commit descriptions rendered as markdown, or submodule/remote-derived URLs). The handler contains code that *looks* like a protocol check but is purely cosmetic logging, and unconditionally forwards the raw string to Electron's `shell.openExternal()`.

### Finding Description
The handler is: [1](#0-0) 

```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

The `if` block only decides whether to emit an informational log line — there is no `else { return false }`, no early exit, and no restriction of `path` to `http(s)` schemes. Regardless of the outcome of the check, `shell.openExternal(path)` is always invoked with the raw, unvalidated string. This is the direct structural analog of the reported bug: a guard is present in the source that gives the *appearance* of enforcing a safe invariant (only http/https URLs get opened), while the actual code path performs the unsafe operation on all inputs, including ones that don't fit the assumed shape.

This handler is reachable from renderer-side UI components that render attacker-influenced strings as clickable links, e.g.: [2](#0-1) 

`LinkButton.onClick` calls `shell.openExternal(uri)` (which proxies to this same IPC channel via `app-shell.ts` / `main-process-proxy.ts`) for any `uri` prop it is given, and `renderSubmoduleInfo()` in the submodule diff view demonstrates that these URIs can be derived from repository-controlled data (a submodule's `url` config value parsed out of an attacker-supplied `.gitmodules`/`.git/config` in a cloned repository): [3](#0-2) 

Similarly, markdown rendered from GitHub API content (release notes, and by extension any other markdown-rendering surface that reuses the same click handler pattern) forwards the raw href straight to `shell.openExternal`: [4](#0-3) 

### Impact Explanation
`shell.openExternal()` in Electron does not restrict the scheme it will invoke — it will happily hand `file://`, `smb://`, custom-registered protocol handlers (e.g., Office/PDF viewer schemes, `search-ms:` style handlers on Windows), or other OS-level URI schemes to the operating system's default handler. This class of "unrestricted `shell.openExternal`" issue is a well-documented Electron anti-pattern that can lead to local file execution or triggering arbitrary installed protocol handlers with attacker-controlled arguments, purely by the user clicking a link that Desktop renders from repository- or API-sourced content. Because the invariant the code appears to enforce ("only open http/https links") is not actually enforced, any code path that trusts this handler as a safety boundary is silently unprotected — mirroring how the `require(transferFrom(...))` pattern gave a false sense of safety while not actually handling the non-conforming case.

### Likelihood Explanation
Likelihood is moderate: it requires a user to click a link rendered by Desktop, sourced from content the attacker controls (a malicious repository's `.gitmodules`, a crafted PR/issue/commit description, or other renderer-displayed content that flows through `LinkButton`/markdown click handlers). No local access, admin rights, or pre-existing malware are required — only that the victim opens/clones a malicious repository or views attacker-supplied API content and clicks the resulting link, which is the "user clicks a link/deep link" primitive explicitly listed as in-scope.

### Recommendation
Make the existing check authoritative instead of decorative: if the URL does not start with `http://` or `https://`, reject the request (return `false`/throw) instead of merely skipping the log line. Consider using the `URL` constructor to parse and validate the protocol explicitly before calling `shell.openExternal`, and apply the same allowlist at the point renderer code constructs `uri` props (e.g., `LinkButton`, submodule diff view, markdown link handlers) so there is defense in depth rather than a single, ineffective gate in the main process.

### Proof of Concept
1. Clone or open a maliciously crafted repository containing a `.gitmodules`/submodule config entry whose `url` is not a genuine GitHub remote but is rendered through `renderSubmoduleInfo()`'s `LinkButton` (or, more directly, embed a non-`http(s)` URI as the `href` in any markdown content Desktop renders through a component that reuses `shell.openExternal`, e.g., a PR/commit body if such a markdown surface reuses this pattern).
2. Craft the value so that after Desktop's URL parsing (`parseRepositoryIdentifier`/`parseRemote`) it does not fit the assumed `owner/name` shape, or directly supply a `file://` or other custom-scheme string to a component that forwards `uri` unmodified to `shell.openExternal` (bypassing the reconstruction step used in `renderSubmoduleInfo`).
3. When the victim clicks the rendered link, the renderer invokes the `open-external` IPC channel with the raw string.
4. `ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts` performs no rejection for non-`http(s)` schemes and calls `shell.openExternal(path)` unconditionally, causing the OS to invoke whatever handler is registered for that scheme (e.g., opening a local file path, or a dangerous custom protocol handler) — all from clicking a link sourced from a cloned/fetched repository.
