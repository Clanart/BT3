### Title
Shared token-keyed escrow bucket lets a single-leg fill drain another leg's escrow in `IntrinsicIntents._fillSameChain` - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The UniswapV3 report's core broken invariant is: a shared pool of value gets redistributed by an operation that only checks the finishing condition of one part of that operation, while the redistribution amount is read from an aggregate/pooled balance rather than the amount that specific part is entitled to. The same class of bug exists in Hyperbridge's `IntentGatewayV2` same-chain fill path: escrow is tracked per `(commitment, token address)` in a single aggregate mapping, not per output "leg," so completing one leg of a multi-output order that shares an input token with another leg releases the *entire* pooled escrow for that token — not just the fraction owed to the completed leg.

### Finding Description
Escrow is stored in `IntentsBase._orders`, keyed only by `(commitment, token)`: [1](#0-0) 

In `_fillSameChain`, when a leg `i` becomes fully filled, the amount of escrow to release is *not* computed as the proportional share belonging to that leg — it is read directly from the whole token-keyed bucket: [2](#0-1) 

This is safe only when every input token address in `order.inputs` is unique per order. But nothing in `placeOrder`, `fillOrder`, or `_fillSameChain` enforces uniqueness of `order.inputs[i].token` across the array — an order can legitimately (or maliciously) specify the same input token backing two different output legs (e.g., `inputs = [USDC:100, USDC:150]` funding `output[0]` and `output[1]` respectively). At placement time both amounts are summed into the same `_orders[commitment][USDC]` bucket because the mapping has no per-index dimension.

When a solver fully fills only `output[0]` (providing just the tokens for that leg), `amountFilled == totalRequired` becomes true for index `0`, and the code releases `_orders[commitment][USDC]` in full — i.e., 250, not the 100 actually owed to leg 0 — to that solver via `_withdraw`: [3](#0-2) 

`_withdraw` blindly decrements and transfers whatever amount it's given per token, with no cross-check against how much of that token bucket "belongs" to the specific leg being completed: [4](#0-3) 

Since the order is not fully filled (leg 1 is still outstanding), `isFullyFilled` is false, `_filled[commitment]` is deleted, and the order remains open — but leg 1's backing escrow has already been drained to zero. Any subsequent attempt to fill leg 1 will read `_orders[commitment][USDC] == 0` and, when `_withdraw` is invoked for it, revert with `UnknownOrder` (or simply refund zero on cancellation), meaning leg 1's beneficiary never receives their entitled tokens and the user's funds are unrecoverable.

### Impact Explanation
This is a direct, unauthorized loss of escrowed user funds and wrong-amount release to an unprivileged solver — exactly the "stealing or loss of funds" / "transaction manipulation" impact class the bounty targets. No malicious relayer, prover, or governance actor is required: any ordinary solver calling the public `fillOrder`/`_fillSameChain` path can trigger it simply by choosing to complete the smaller leg of a multi-leg order that happens to share an input token, extracting escrow that was earmarked for the other leg.

### Likelihood Explanation
Likelihood depends on orders being constructed with duplicate input-token entries across different output legs. Nothing in `IntentGatewayV2`/`IntentsBase` validates or rejects this structure, and multi-output orders funded from a common source token (e.g., splitting one USDC deposit across two different output assets) are a natural, legitimate usage pattern for the Intent Gateway's multi-asset order format — so the precondition is plausible without any attacker-controlled setup beyond normal order placement, and the exploit itself requires only a single ordinary `fillOrder` call.

### Recommendation
Track escrow per output leg (e.g., `mapping(commitment => amount[])` indexed by the position in `order.inputs`/`order.output.assets`, or a mapping keyed by `(commitment, token, legIndex)`) instead of aggregating purely by `(commitment, token)`. Alternatively, when a leg completes, release only the proportional amount `order.inputs[i].amount - alreadyReleased[i]` computed from that leg's own accounting, never the entire token-level bucket balance.

### Proof of Concept
1. User places a same-chain order with `order.inputs = [{token: USDC, amount: 100}, {token: USDC, amount: 150}]` and `order.output.assets = [{token: TOKEN_X, amount: A}, {token: TOKEN_Y, amount: B}]`. Placement escrows 250 USDC total into `_orders[commitment][USDC]`.
2. A solver calls `fillOrder` providing only `options.outputs[0] = A` (leg 0's exact requirement) and `options.outputs[1] = 0`.
3. In `_fillSameChain`, for `i = 0`: `alreadyFilled = 0`, `fillAmount = A_total = totalRequired`, so `amountFilled == totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 250` (not 100).
4. `_withdraw` transfers all 250 USDC to the solver and zeroes `_orders[commitment][USDC]`.
5. `isFullyFilled` is false (leg 1 unfilled) → `_filled[commitment]` is deleted, order stays open.
6. A later attempt to fill leg 1, or the user's attempt to cancel/refund, finds `_orders[commitment][USDC] == 0` — leg 1's 150 USDC is gone; the solver received 250 USDC while only delivering the value of leg 0.
