### Title
Conflict-marker regex divergence between `extractConflictHunks` and `reassembleResolvedFile` desynchronizes hunk indices, silently misapplying AI merge-conflict resolutions to the wrong code block - (File: `app/src/lib/copilot-conflict-resolution.ts`, `app/src/lib/copilot-conflict-context.ts`)

### Summary
The external report's bug class is "two calculations that are supposed to represent the same quantity are computed with different, incompatible assumptions, and nothing cross-checks them" (asset decimals vs. a fixed 1e8 scale). The Desktop analog is structurally identical: the Copilot conflict-resolution feature extracts conflict hunks with one marker-parsing function to build the AI prompt, then splices the AI's per-hunk answers back into the file with a **second, independently written** marker-parsing function. The two parsers use near-identical but not equivalent regexes/termination logic, so a conflict whose "ours"/"theirs" content merely contains a line that matches the `>>>>>>>` marker pattern desynchronizes the hunk count between the two passes. The result is that a model resolution meant for one conflict is spliced into a different one, with no validation that the counts match.

### Finding Description
Hunks are extracted in `extractConflictHunks`: [1](#0-0) 
This function terminates the "theirs" collection loop only when it sees a line matching `theirsMarker`, and it never treats an interior `>>>>>>>`-shaped line inside "ours" content specially (it only watches for `baseMarker`/`separatorMarker` while collecting ours content): [2](#0-1) 

Later, after the model responds, `reassembleResolvedFile` re-scans the *same raw file content* with a second, separately declared set of marker regexes to find where to splice each hunk resolution: [3](#0-2) 
Its lookahead loop breaks on the **first** line matching `reassemblyTheirsMarker`, regardless of whether a `=======` separator has already been seen, and if no separator was seen yet it treats the whole block as malformed and only advances by one line (not past the "conflict"): [4](#0-3) 

If the real "ours" region of a conflict happens to contain a line that matches `^>{7}(?:\s|$)` (e.g. leftover markers from a prior bad merge, a markdown/ASCII block quote, or a documentation/test fixture line — this very codebase's own test fixtures contain literal `>>>>>>> feature` strings, per `app/test/unit/copilot-conflict-resolution-test.ts`), `extractConflictHunks` still extracts the conflict correctly as one hunk (its ours-loop doesn't terminate on that pattern), but `reassembleResolvedFile`'s independent scan matches that embedded line as the "closing marker" before it has seen the real `=======`, decides the block is malformed, does **not** consume the block, and — critically — does **not** increment `hunkIndex`. Every subsequent real conflict hunk in the file is then matched against the wrong entry in `hunkResolutions` (`reassembleResolvedFile`, lines 585-591), applying content generated for one merge conflict to a different, unrelated one.

### Impact Explanation
The attacker precondition matches the "valid impact" bar: the attacker only needs to control a branch/fork/PR that the victim merges, rebases, or cherry-picks locally (a normal git operation against attacker-influenced content), i.e. a "cloned/fetched repository" scenario — no local access, no malware, no leaked credentials, no social engineering beyond a normal merge. Because `reassembleResolvedFile` output is written straight to disk and staged in `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts`, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` then `git add`), a hunk-index desync results in **silent corruption of what the user commits**: code intended for conflict N ends up in the file at the location of conflict N+1 (or vice versa), producing a resolved file that differs from what the AI actually reasoned about and what the user believes they approved. In security-sensitive files (auth checks, permission logic, dependency manifests) this can silently reintroduce vulnerable code, drop a fix, or splice unrelated logic into the wrong branch of an if/else, and the corrupted result is then committed and can be pushed.

### Likelihood Explanation
This requires two independently-maintained regex-based parsers over the same conflict marker syntax to actually diverge in a real file. The precondition (a line matching `^>{7}(?:\s|$)` appearing inside a conflict's "ours"/"theirs" content, before the true `=======`/`>>>>>>>` for that hunk) is uncommon but realistic: nested/leftover conflict markers from an earlier bad resolution, ASCII-art dividers, or documentation/example content containing git-conflict-marker-shaped text are all things real repositories contain (the project's own fixtures include such literal strings). No warning or count-consistency check exists between `extractConflictHunks`'s hunk count and `reassembleResolvedFile`'s `hunkIndex` walk, so nothing in the code path would catch or flag the divergence before the file is written and staged.

### Recommendation
- Use a single shared marker-parsing implementation for both extraction (building the prompt) and reassembly (splicing the response), instead of two hand-copied regex sets (`oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` in `copilot-conflict-context.ts` vs. `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` in `copilot-conflict-resolution.ts`).
- Have `extractConflictHunks` return structural positions (line ranges) for each hunk instead of re-deriving them, so `reassembleResolvedFile` can splice by explicit line index rather than re-scanning and re-matching markers.
- Add an assertion/validation step that the number of hunks found by reassembly equals the number sent to the model for that file, and refuse to write the file (surfacing an error to the user) if they don't match, rather than silently proceeding.

### Proof of Concept
1. Create a repository where a merge will conflict on `file.ts`, and where the "ours" side's conflicting region legitimately contains a line consisting of 7+ `>` characters (e.g., a leftover/nested marker from a previous manual merge, such as `>>>>>>> old-branch`), followed later by the real `=======` and `>>>>>>> theirs` markers, e.g.:
```
<<<<<<< HEAD
realOursCode();
>>>>>>> old-branch
=======
realTheirsCode();
>>>>>>> feature
```
2. Trigger "Resolve with Copilot" on a merge/rebase that produces this conflict alongside at least one more conflict later in the same file.
3. `extractConflictHunks` extracts this as a single well-formed hunk (its ours-loop only stops at `baseMarker`/`separatorMarker`), so the model is asked to resolve one hunk here, plus the later hunk(s) — total N hunks, returned as `hunkResolutions[0..N-1]`.
4. In `reassembleResolvedFile`, the lookahead for the first `<<<<<<< HEAD` immediately hits the embedded `>>>>>>> old-branch` line first, without having seen `=======` yet (`hasSeparator` still `false`), so it falls into the "malformed marker" branch, does not consume the block, and does not advance `hunkIndex`.
5. The real closing markers for this conflict (and any subsequent conflicts) are now walked individually; the resolution meant for this hunk is applied at the location of the *next* real conflict block instead, and vice versa — verifiable by asserting on `reassembleResolvedFile`'s output for the crafted input above and comparing against the intended per-hunk mapping in `app/test/unit/copilot-conflict-resolution-test.ts`.
