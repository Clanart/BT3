### Title
Zero-value / unspendably-small Bitcoin outputs are reported as received funds with no minimum-value check - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The USSD bug class is "a value calculation/acceptance path can yield effectively zero output for non-zero input, with no check on the resulting amount." In `bitcoin-serai`'s wallet, `Scanner::scan_transaction` accepts any `TxOut` matching a registered `script_pubkey` and returns it as a `ReceivedOutput` without checking `output.value` at all — no zero check, no dust check. `ReceivedOutput::read` likewise accepts any `TxOut` value. `SignableTransaction::new` then consumes these inputs, summing `input.output.value.to_sat()` into `input_sat` while charging ~57 vbytes of fee per input.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) matches outputs solely on `script_pubkey` and pushes a `ReceivedOutput` regardless of `value`. `ReceivedOutput::read` (lines 122-134) decodes any `TxOut` from consensus serialization, again with no value check. A 0-satoshi P2TR output is consensus-valid Bitcoin (non-standard for relay, but miners accept out-of-band transactions), and outputs below `DUST = 546` or below the marginal spend cost (~`57 * fee_per_vbyte` sats) are trivially mineable.

When `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) is given these inputs, it adds them to `tx_ins` (lines 175-185), counts their value into `input_sat` (line 175), and pays the extra vbytes they add via `calculate_weight_vbytes` (line 204). An input worth less than its marginal fee is net-negative: it increases `needed_fee` by more than it contributes, draining value from legitimate inputs — the direct analog of USSD taking a real deposit and minting effectively nothing in return.

### Impact Explanation
- Funds are reported received (`ReceivedOutput` in `scan_transaction`/`scan_block`/`read`) that are not economically spendable: a zero-value or sub-fee output can never yield value — it only burns it. This matches the accepted "funds reported received that are not spendable" impact.
- If such inputs reach `SignableTransaction::new`, each one destroys `57 * fee_per_vbyte - value` sats of co-spent UTXO value, and the signature is produced over a transaction paying that excess fee.
- An unprivileged party reaches this purely by sending a Bitcoin transaction — a listed public input — or by feeding crafted bytes to `ReceivedOutput::read`.

### Likelihood Explanation
Creating a sub-546-sat or 0-sat P2TR output requires a miner or out-of-band submission (non-standard), which is achievable at negligible cost on Bitcoin. Once mined, it is automatically matched by `script_pubkey` in `scan_transaction`; no other condition gates it. Any integration that trusts `ReceivedOutput::value()` as credited balance (the reported balance in tests, `wallet.rs` line 70 uses `scanned.value()`) credits the attacker's deposit while the funds are worthless or net-negative.

### Recommendation
- In `Scanner::scan_transaction`, require `output.value.to_sat() >= DUST` (and ideally `>= marginal spend cost`) before yielding a `ReceivedOutput`.
- In `ReceivedOutput::read`, reject `TxOut`s with `value < DUST` after `consensus_decode`.
- In `SignableTransaction::new`, drop or reject inputs whose `value` is below the per-input fee cost (`57 * fee_per_vbyte`).

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
