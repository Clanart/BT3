### Title
Double-mint via IBC/ERC20 middleware: `OnRecvPacket` returns error acknowledgement after the ICS20 transfer has already minted/unescrowed funds - ([File: x/erc20/ibc_middleware.go])

### Summary
This is the closest reachable analog to the ZKsync `MessageRoot`/`Bridgehub` report: two enforcement points that should be treated as a single atomic operation are actually decoupled, so a failure in the *second* check does not undo the effects of the *first*. In the ZKsync report, `_registerNewZKChain` bypasses `MAX_NUMBER_OF_ZK_CHAINS` but `MessageRoot._addNewChain` does not, so a supposedly-permitted operation silently fails after partial state has already changed. In Cosmos EVM's IBC + ERC20 middleware, the analogous decoupling is between the core ICS20 `OnRecvPacket` (which mints/unescrows the voucher coin to the receiver) and the `x/erc20` middleware layer that runs afterward to auto-convert/register the coin as an ERC20 (`x/erc20/ibc_middleware.go:53-67`, `x/erc20/keeper/ibc_callbacks.go:35-154`). If the second step fails and returns an error acknowledgement, the first step's balance mutation is **not rolled back**, while the counterparty chain will still process the error ack as a full failure and refund the sender - resulting in duplicated value.

### Finding Description
`IBCMiddleware.OnRecvPacket` first calls the underlying ICS20 module's `OnRecvPacket`, which performs the actual mint/unescrow of the transferred coin into the receiver's bank balance on the same `sdk.Context` (no `CacheContext` branching is used): [1](#0-0) 

Only after that state mutation has been applied does the code invoke `im.keeper.OnRecvPacket`, which performs the auto-conversion / dynamic-precompile registration logic in `x/erc20/keeper/ibc_callbacks.go`: [2](#0-1) 

For an unregistered `ibc/...` denom, this calls `RegisterERC20Extension` → `CreateNewTokenPair` → `SetToken`, all of which can fail (`ErrTokenPairAlreadyExists`) if the deterministically-derived ERC20 address for that denom (`utils.GetIBCDenomAddress`, a pure hash of the denom string) already has an entry in `ERC20Map`, `DenomMap`, or has EVM code deployed at that address: [3](#0-2) [4](#0-3) 

The project's own integration tests confirm that these collisions cause the middleware to return an **error acknowledgement** (`ackSuccess: false`) even though the underlying transfer already succeeded and credited the bank balance: [5](#0-4) 

Because there is no `ctx.CacheContext()`/branch-and-discard pattern around the combined "transfer + convert" operation, an error returned from the ERC20-conversion step does not undo the bank mint that the core ICS20 module already committed to the multistore in the same transaction. When the destination chain returns this error acknowledgement, the source chain's `OnAcknowledgementPacket` will treat the transfer as failed and refund/unescrow the original amount back to the sender there — while the receiver on the destination chain has already been credited. The net effect is duplicated value: the sender is refunded on chain A and the receiver retains newly-minted coins on chain B.

This mirrors the report's root cause exactly: a secondary enforcement/registration step (`MessageRoot._addNewChain` / here, `RegisterERC20Extension`/`SetToken`) is not consistent with (or coupled atomically to) the primary operation it depends on (`Bridgehub._registerNewZKChain` / here, the core ICS20 mint), so a legitimate/expected failure path in the secondary step corrupts the invariant that the primary step assumed would be rolled back together.

### Impact Explanation
This falls squarely under the allowed "Critical unauthorized minting/duplication ... across native balances ... IBC escrows" impact. The mechanism produces genuine double-spend of transferred value across two chains: the destination chain keeps the minted/unescrowed coins in the receiver's account while the source chain refunds the sender, without requiring any privileged actor, malicious relayer, or validator collusion — a normal relayer simply delivering a normal packet triggers it once the collision/registration-failure condition exists.

### Likelihood Explanation
The registration failure can be triggered in ways that don't require breaking cryptographic hash preimages:
- A denom can hit `IsDenomRegistered`/`IsERC20Registered` collisions through legitimate governance/registration lifecycle races (e.g., a token pair for the same derived ID being deleted and concurrently in-flight IBC packets for the same denom), or
- An attacker-influenced multi-hop IBC path/denom trace (the denom string used for hashing is attacker-influenced via source port/channel/hop composition in multi-hop IBC transfers) colliding with metadata/state already present from a related, legitimately registered pair.

This needs to be validated more concretely for a fully deterministic unprivileged trigger (e.g., proving a specific attacker-constructed multi-hop denom that reliably produces a `GetIBCDenomAddress` collision with an account that already has code, without requiring hash preimage computation). I was not able to fully trace whether the underlying ICS20 `OnRecvPacket` in this fork writes through a branched store internally (which would neutralize the bug) — the `im.Module.OnRecvPacket` call at `x/erc20/ibc_middleware.go:59` delegates to `ibc.NewModule(app)`, and I could not fully inspect that wrapper's internals within the available search budget to conclusively rule out an internal cache-context rollback.

### Recommendation
Wrap the combined "ICS20 receive + ERC20 auto-conversion/registration" flow in a single branched context (`ctx.CacheContext()`), and only commit (`writeCache()`) if both the core transfer and the ERC20 middleware step succeed. If the ERC20-side registration/conversion fails, discard the branch entirely and fall back to just the (uncached) core ICS20 mint so the acknowledgement returned matches the actual on-chain effect — i.e., either both succeed and the ack is success, or the ERC20 conversion silently degrades to "receive plain bank coin" (as the code comments claim is the intended behavior) rather than issuing an error ack after committing the mint.

### Proof of Concept
1. Attacker/relayer submits an ICS20 packet for a denom `ibc/<hash>` that has not yet been registered as an ERC20 token pair, to a Cosmos EVM chain running the `x/erc20` IBC middleware.
2. Prior to or concurrently with this packet, the address derived by `utils.GetIBCDenomAddress(denom)` becomes populated in `ERC20Map`/`DenomMap` or gets EVM code deployed at it (project's own tests at `tests/integration/x/erc20/test_ibc_callback.go:188-243` demonstrate this exact collision scenario and confirm it yields `ackSuccess: false`).
3. `im.Module.OnRecvPacket` executes first and commits the mint/unescrow of the transferred coin to the receiver's bank balance on the live `ctx`.
4. `im.keeper.OnRecvPacket` then fails in `RegisterERC20Extension`/`SetToken` and returns `channeltypes.NewErrorAcknowledgement(err)`.
5. The source chain observes the error acknowledgement and refunds/unescrows the sender's original amount via its standard ICS20 acknowledgement handling.
6. Result: receiver on the destination chain retains the credited coins from step 3, and the sender on the source chain is also refunded — value has been duplicated. (I could not execute this end-to-end in a live environment within this session; the trigger mechanics are inferred from the code paths and confirmed unit-test fixtures cited above.)

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)

// CreateNewTokenPair creates a new token pair and stores it in the state.
func (k Keeper) CreateNewTokenPair(ctx sdk.Context, denom string) (types.TokenPair, error) {
	pair, err := types.NewTokenPairSTRv2(denom)
	if err != nil {
		return types.TokenPair{}, err
	}
	account := k.evmKeeper.GetAccount(ctx, pair.GetERC20Contract())
	if account != nil && account.HasCodeHash() {
		return types.TokenPair{}, errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for token %s", pair.Erc20Address)
	}
	err = k.SetToken(ctx, pair)
	if err != nil {
		return types.TokenPair{}, err
	}
	return pair, nil
}

// SetToken stores a token pair, denom map and erc20 map.
func (k *Keeper) SetToken(ctx sdk.Context, pair types.TokenPair) error {
	if k.IsDenomRegistered(ctx, pair.Denom) {
		return errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for denom %s", pair.Denom)
	}
	if k.IsERC20Registered(ctx, pair.GetERC20Contract()) {
		return errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for token %s", pair.Erc20Address)
	}
	k.SetTokenPair(ctx, pair)
	k.SetDenomMap(ctx, pair.Denom, pair.GetID())
	k.SetERC20Map(ctx, pair.GetERC20Contract(), pair.GetID())
	return nil
}

// GetIBCDenomAddress returns the address from the hash of the ICS20's Denom Path.
func GetIBCDenomAddress(denom string) (common.Address, error) {
	if !strings.HasPrefix(denom, "ibc/") {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s does not have 'ibc/' prefix", denom)
	}

	if len(denom) < 5 || strings.TrimSpace(denom[4:]) == "" {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s is not a valid IBC voucher hash", denom)
	}

	// Get the address from the hash of the ICS20's Denom Path
	bz, err := ibctransfertypes.ParseHexHash(denom[4:])
	if err != nil {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrap(err.Error())
	}

	return common.BytesToAddress(bz), nil
}
