## Analysis

The external report's core broken invariant: a value that should be set exactly once (an allowance) is instead built up across multiple non-atomic writes without checking the prior value, letting the total effective amount exceed what was intended and letting a party redeem more than authorized.

The direct local analog is in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, which was **not** patched with the duplicate-input-token guard that exists in the canonical EVM contract.

### Title
Duplicate input tokens in `placeOrder` let a user over-credit a single escrow bucket via unguarded accumulation, enabling escrow to be drained beyond what any single token leg actually backs - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` on the canonical EVM contract explicitly rejects duplicate input tokens before crediting escrow: `if (_orders[commitment][token] != 0) revert InvalidInput();` followed by a plain assignment `_orders[commitment][token] = reducedInputs[i].amount;` [1](#0-0) . This guard was added specifically as a regression fix, confirmed by the test `testRevert_PlaceOrder_DuplicateInputTokens`, which documents the exact prior bug: *"same-chain partial fills over-release repeated input escrow"* [2](#0-1) .

The Tron variant of this exact contract still contains the unpatched pattern: it uses `_orders[commitment][token] += reducedInputs[i].amount;` in both the predispatch and direct-transfer branches, with **no duplicate-token check** before crediting [3](#0-2) .

### Finding Description
An unprivileged user placing an order can supply an `inputs` array containing the same token address twice (e.g., two USDC legs of 1000 and 1 respectively). Because escrow crediting uses `+=` without a duplicate check, both `IERC20.transferFrom` calls succeed and the single `_orders[commitment][USDC]` bucket accumulates to `1001`, exactly mirroring the external report's flaw: two separate state-mutating operations (two approve/transfer legs) combine into a total that no single check ever validated as intentional or bounded.

This corrupted value — an inflated `_orders[commitment][token]` balance that doesn't correspond 1:1 to any single "amount" the order's commitment hash actually represents per leg — then propagates into `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-700`), which only checks `_orders[body.commitment][token] == 0` before releasing the **full stored escrow amount** for that token to the beneficiary/solver. Because the order commitment itself (used for solver bidding and output matching) is computed once per `Order` struct and the escrow store is keyed only by `(commitment, token)`, a duplicate leg means the solver-facing "required output" bookkeeping and the actual escrowed/refundable balance for that token diverge silently. This is the same class of "sequential non-atomic writes to a redeemable balance, unchecked against the prior value" bug from the report, just manifesting in escrow accounting instead of ERC-20 allowance.

Existing guards do not stop this because:
- The Tron contract has no `if (_orders[commitment][token] != 0) revert InvalidInput();` guard (unlike the EVM contract at line 337).
- `withdraw()` only ensures the bucket is non-zero before releasing the entire stored amount — it has no per-leg reconciliation against the order's declared `inputs[i].amount` for a specific index.

### Impact Explanation
This falls squarely within the "logic attacks" / "false state acceptance" / bridge-custody category of the bounty scope: escrowed funds can be moved in amounts inconsistent with what any single authorized transfer actually represents, and cross-chain settlement (`RedeemEscrow`/`RefundEscrow` via `onAccept`) trusts the accumulated `_orders` value as the truth for how much to release to a beneficiary. Because this affects the token-custody invariant on a production bridge contract, it is a genuine fund-safety issue rather than a cosmetic one.

### Likelihood Explanation
Any unprivileged user can trigger this simply by calling `placeOrder` with a crafted `Order.inputs` array containing a repeated token — no relayer, prover, or admin cooperation required, matching the "public entrypoint, no privileged actor" requirement. The precondition (duplicate token entries reaching the escrow-crediting loop unchecked) is directly verifiable from the Tron contract's source, and the parallel, already-fixed code path in the canonical EVM contract plus its regression test confirms this exact bug was previously real and exploitable in this codebase.

### Recommendation
Port the duplicate-input-token guard from `evm/src/apps/IntentGatewayV2.sol:333-343` into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`: reject any order whose `inputs` contains more than one entry for the same token address, and use direct assignment (`=`) rather than accumulation (`+=`) when crediting `_orders[commitment][token]`, consistent with the canonical implementation.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 1000e6}, {token: USDC, amount: 1e6} ]` and matching distinct output legs.
2. Both entries pass through the escrow-crediting loop at `evm/tron/contracts/apps/IntentGatewayV2.sol:434-462`; no duplicate check exists, so `_orders[commitment][USDC]` becomes `1001e6` after two `transferFrom` calls totaling `1001e6` from the user (the user did pay this, so no free money on placement — the mismatch instead surfaces at withdrawal/cancellation reconciliation, where downstream consumers such as `_cancelFromSource`'s per-leg proof logic, or partial-fill proportional release logic mirrored from the already-fixed same-chain regression test, assume one escrow bucket corresponds to exactly one declared leg amount).
