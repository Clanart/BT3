### Title
`SignableTransaction::new()` computes the fee/weight on a transaction that omits the OP_RETURN data output, so the signed transaction pays a lower fee rate than requested - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

In `SignableTransaction::new`, the transaction weight/vbytes used to derive `needed_fee` is calculated with `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, passing the raw `payments` slice. However, the actual outputs pushed into `tx_outs` additionally include the OP_RETURN `data` output (up to 80 bytes). The real transaction therefore has one more output than the transaction the fee was computed on, so the actual fee rate is strictly lower than `fee_per_vbyte` whenever `data` is specified. The same discrepancy exists for the change-output weight calculation at line 225-226, which also omits the OP_RETURN output. Analogous to the M-21 report (open interest registered on pre-fee margin while the position is created on post-fee margin), the accounting value here is computed on a different, smaller transaction than the one actually built and signed.

### Finding Description [1](#0-0) 

At `networks/bitcoin/src/wallet/send.rs:194-202`, the OP_RETURN output is pushed onto `tx_outs` when `data` is `Some`. But at line 204, `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` is called with `payments` — which does not include the data output — so the returned `vbytes` and `weight` are for a smaller transaction than the one constructed at lines 246-251 (which uses `tx_outs`).

The same omission occurs in the change branch at `networks/bitcoin/src/wallet/send.rs:225-226`, where `vbytes_with_change`/`weight_with_change` are again computed from `payments` only, and `fee_with_change = fee_per_vbyte * vbytes_with_change` undercounts.

Consequences:
- `needed_fee` (line 206 / 232) is too small by `fee_per_vbyte * vsize_of_opreturn_output`.
- The minimum-fee check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the underestimated `vbytes`, so a transaction that should fail the min-relay-fee check can pass it.
- The final weight sanity check at line 241 uses the underestimated `weight`, so `TooLargeTransaction` can be missed for a transaction that actually exceeds `MAX_STANDARD_TX_WEIGHT`.

Any caller producing a transaction with `data` (an OP_RETURN payload is caller-supplied public input) gets a signed transaction whose real fee rate is lower than the `fee_per_vbyte` they specified — a deterministic miscalculation of the declared fee, exactly the "registered value ≠ actual value" class from the report.

### Impact Explanation

The produced transaction underpays relative to the caller-specified fee rate by `fee_per_vbyte × (OP_RETURN output vsize)` (roughly `fee_per_vbyte × ~10-90` vbytes). With up-to-80-byte data this underpayment can be material, and at the boundary it can drop the transaction below the minimum relay fee (since the check at line 211 evaluated the smaller transaction), producing a signed transaction that will not relay/confirm — effectively freezing the spent outputs until the transaction is reconstructed. Additionally, `weight` used for the `MAX_STANDARD_TX_WEIGHT` guard is understated, allowing an oversized (non-standard) transaction to be signed.

### Likelihood Explanation

The bug triggers deterministically whenever `data.is_some()` — no attacker cooperation or validator misbehavior is needed; the `data` field is ordinary public input to `SignableTransaction::new`. Every such transaction is under-fee'd relative to its specification.

### Recommendation

Compute the weight from the actual outputs. Either pass `tx_outs`-equivalent data to `calculate_weight_vbytes` (e.g., a slice including the OP_RETURN `TxOut`), or push the OP_RETURN output before the fee computation and have `calculate_weight_vbytes` take `&[TxOut]` directly. Apply the same fix in both the no-change and with-change weight calculations, and perform the min-fee and max-weight checks against those same values.

### Proof of Concept

Conceptual reproduction (mirroring the existing tests in `networks/bitcoin/tests/wallet.rs`):

```rust
let tx = SignableTransaction::new(
  vec![output],                 // one input
  &[],                          // no payments
  Some(change_addr),            // change
  Some(vec![0u8; 80]),          // OP_RETURN data output
  FEE,
).unwrap();

// The signed transaction will contain 2 outputs (OP_RETURN + change), but
// needed_fee was computed on a transaction containing only the change output.
assert_eq!(tx.transaction().output.len(), 2);
let actual_fee_rate = tx.fee() / u64::try_from(tx.transaction().vsize()).unwrap();
assert!(actual_fee_rate < FEE); // underpays vs requested rate by FEE * vsize(OP_RETURN output)
```
