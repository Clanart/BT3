Confirmed: `RegisterERC20` allows permissionless registration of arbitrary ERC20 contracts (when `PermissionlessRegistration` param is enabled) with no check on transfer semantics (fee-on-transfer, rebasing, pausable, or blocklist behavior), and `registerERC20`/`CreateCoinMetadata` in [1](#0-0)  only validate name/symbol/decimals metadata, never actual transfer-amount fidelity.

### Title
Permanent freezing of bridged value in x/erc20 Coin↔ERC20 conversion due to unconditional 1:1 balance-invariance assumption for non-standard ERC20 tokens - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertERC20`/`convertERC20IntoCoinsForNativeToken` and `ConvertCoin`/`ConvertCoinNativeERC20` in [2](#0-1)  and [3](#0-2)  hard-assume that transferring `amount` tokens to/from the module escrow always changes the on-chain ERC20 balance by exactly `amount`, reverting with `ErrBalanceInvariance` otherwise. This is the same "assumes 1:1, no allowance for legitimate loss" pattern as the Sense PT redemption bug: any token pair backed by a non-standard ERC20 (fee-on-transfer, rebasing/deflationary, or one whose behavior legitimately changes after registration) can permanently deadlock the Coin↔ERC20 conversion path for that pair once the assumption breaks.

### Finding Description
`RegisterERC20` supports fully permissionless registration of any ERC20 contract address as a native token pair when `params.PermissionlessRegistration` is true [4](#0-3) . The only validation performed is `CreateCoinMetadata`, which reads `name`, `symbol`, `decimals` from the contract and validates bank `Metadata` — it never validates that `transfer`/`transferFrom` behave as a standard fixed-supply, non-fee, non-rebasing ERC20 [5](#0-4) .

Once such a token is registered as `OWNER_EXTERNAL` (`IsNativeERC20()`), users can freely convert between the ERC20 and the wrapped Cosmos coin:
- `convertERC20IntoCoinsForNativeToken` escrows `msg.Amount` ERC20 tokens into the module account, then requires that the module's ERC20 balance increased by *exactly* `msg.Amount`, else it reverts the whole transaction with `ErrBalanceInvariance` [6](#0-5) .
- `ConvertCoinNativeERC20` first burns/escrows the Cosmos coin, then unescrows (`transfer`s) `amount` ERC20 tokens from the module account to the receiver, requiring the receiver's balance to have increased by *exactly* `amount`, else revert [7](#0-6) .

For a token with any transfer-fee, negative rebase, or other supply-adjusting mechanic that legitimately makes 1 escrowed unit ≠ 1 redeemable unit, this invariant will *always* be violated for every subsequent `ConvertCoinNativeERC20` call once the module's actual on-chain ERC20 holdings fall short of the sum of coins that were previously minted 1:1 and are backed by that ERC20 balance. Because the check is a hard revert rather than a graceful "distribute pro-rata" fallback (unlike Sense's `Divider`, which the original report cites as correctly anticipating settlement losses), once the discrepancy exists the ERC20 side of the token pair becomes permanently un-redeemable: any Coin holder attempting `ConvertCoin` will have their `SendCoinsFromAccountToModule` escrow succeed, then the `CallEVM` "unescrow" step succeed at the ERC20 level, but the balance check will revert the entire transaction (including the coin escrow) forever, for every wallet, with no code path to recover the shortfall. The same mechanism arises symmetrically on the ERC20→Coin path if the token takes a fee before crediting the module escrow account.

This directly parallels the reported Sense pattern: PT/underlying (here, Coin/ERC20) is assumed to always be exchangeable 1:1 and any deviation is treated purely as malicious-adapter behavior to be reverted, rather than a legitimate scenario (fee-on-transfer, rebase) to be accounted for. The consequence is loss/freezing of user value that was already bridged in good faith when the token was "well-behaved" at registration time, but drifts out of 1:1 backing later.

### Impact Explanation
Coin holders backed by a native ERC20 pair permanently lose the ability to redeem their Cosmos-coin representation for the underlying ERC20 token once any transfer-fee/rebase/deflationary discrepancy manifests — this is an unprivileged, permanent freezing of bridged user value (the Cosmos coin becomes stuck, unable to be converted back to the ERC20 asset it represents, which may itself be the economically meaningful asset e.g. used in DeFi, IBC transfers via `x/ibc/transfer/keeper/msg_server.go` `Transfer`, which auto-invokes `ConvertERC20` [8](#0-7) ). This matches the "Critical permanent freezing... of user funds... or token-pair-backed balances" allowed-impact category.

### Likelihood Explanation
Triggering requires only: (1) `PermissionlessRegistration` enabled (a supported, documented governance parameter, not a privileged-attacker assumption) or a governance-approved registration of a legitimately fee-bearing/rebasing token, and (2) ordinary unprivileged users calling `MsgConvertERC20`/`MsgConvertCoin`/`MsgTransfer`. No malicious validator, relayer, or admin is required — any ERC20 whose `transfer` doesn't move tokens exactly 1:1 (a real, common ERC20 pattern) suffices.

### Recommendation
Do not hard-revert on balance mismatch for legitimate non-malicious causes. Either (a) reject registration of tokens that fail a fee-on-transfer/rebase probe at `RegisterERC20` time, or (b) track actual received/sent amounts (as many DeFi integrations do) and mint/burn/transfer coins based on the *actual* delta rather than the nominal `amount`, so that losses are distributed rather than causing permanent reverts once a shortfall exists.

### Proof of Concept
1. Deploy an ERC20 contract that charges a 1% fee on `transfer` (fee sent to a fee-collector, remaining 99% credited to recipient).
2. Governance/permissionless-register this contract via `MsgRegisterERC20` — `CreateCoinMetadata` only inspects `name/symbol/decimals`, so registration succeeds [9](#0-8) .
3. User A converts 1000 ERC20 → Coin via `MsgConvertERC20`. Because `transfer` to the module only nets 990 tokens actually held, but the escrow-balance check in `convertERC20IntoCoinsForNativeToken` compares `balanceTokenAfter` to `balanceToken + msg.Amount` (1000) [6](#0-5) , the transaction reverts with `ErrBalanceInvariance` — the conversion is simply blocked (no coin ever minted), demonstrating the module cannot even onboard such tokens gracefully; however, if the fee logic instead only reduces `transfer`-out amounts (fee taken on withdrawal, not deposit), deposits succeed and coins are minted 1:1, while later `ConvertCoinNativeERC20` calls will revert at line 292-297 because `balanceTokenAfter` will be `amount - fee`, not `amount`, permanently blocking every subsequent redemption for all coin holders sharing that token pair, even though their coins remain nominally spendable but functionally unbacked/unredeemable.

func (k Keeper) registerERC20(
	ctx sdk.Context,

	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}

// CreateCoinMetadata generates the metadata to represent the ERC20 token on
// evmos.
func (k Keeper) CreateCoinMetadata(
	ctx sdk.Context,
	contract common.Address,
) (*banktypes.Metadata, error) {
	strContract := contract.String()

	erc20Data, err := k.QueryERC20(ctx, contract)
	if err != nil {
		return nil, err
	}

	// Check if metadata already exists
	_, found := k.bankKeeper.GetDenomMetaData(ctx, types.CreateDenom(strContract))
	if found {
		return nil, errorsmod.Wrap(
			types.ErrInternalTokenPair, "denom metadata already registered",
		)
	}

	if k.IsDenomRegistered(ctx, types.CreateDenom(strContract)) {
		return nil, errorsmod.Wrapf(
			types.ErrInternalTokenPair, "coin denomination already registered: %s", erc20Data.Name,
		)
	}

	// base denomination
	base := types.CreateDenom(strContract)

	// create a bank denom metadata based on the ERC20 token ABI details
	// metadata name is should always be the contract since it's the key
	// to the bank store
	metadata := banktypes.Metadata{
		Description: types.CreateDenomDescription(strContract),
		Base:        base,
		// NOTE: Denom units MUST be increasing
		DenomUnits: []*banktypes.DenomUnit{
			{
				Denom:    base,
				Exponent: 0,
			},
		},
		Name:    types.CreateDenom(strContract),
		Symbol:  erc20Data.Symbol,
		Display: base,
	}

	// only append metadata if decimals > 0, otherwise validation fails
	if erc20Data.Decimals > 0 {
		nameSanitized := types.SanitizeERC20Name(erc20Data.Name)
		metadata.DenomUnits = append(
			metadata.DenomUnits,
			&banktypes.DenomUnit{
				Denom:    nameSanitized,
				Exponent: uint32(erc20Data.Decimals), //#nosec G115 -- int overflow is not a concern here
			},
		)
		metadata.Display = nameSanitized
	}

	if err := metadata.Validate(); err != nil {
		return nil, errorsmod.Wrapf(
			err, "ERC20 token data is invalid for contract %s", strContract,
		)
	}

	k.bankKeeper.SetDenomMetaData(ctx, metadata)

	return &metadata, nil

// convertERC20IntoCoinsForNativeToken handles the erc20 conversion for a native erc20 token
// pair:
//   - escrow tokens on module account
//   - mint coins on bank module
//   - send minted coins to the receiver
//   - check if coin balance increased by amount
//   - check if token balance decreased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}
