Audit Report

## Title
Unstaked/zero-stake peers can drain the shared repair-serving bandwidth budget on par with staked peers - ([File: core/src/repair/serve_repair.rs])

## Summary
`ServeRepair::run_listen` maintains a single, global `data_budget: &TokenBucket` used to rate-limit outbound repair response bytes across all requesters, and `handle_requests`/`decode_requests` consume from this shared pool via `max_response_cost = request.max_response_bytes() * byte_cost_multiplier` without weighting by requester stake. Stake is only used as a statistics tag and as a tie-breaker sort key applied solely when the number of decoded requests in a ~1-second iteration exceeds `MAX_REQUESTS_PER_ITERATION` (1024), confirmed at [1](#0-0) . Below that threshold — the common, cheaply-attainable case for a distributed low-and-slow attacker — no stake gating occurs at all before token consumption, so zero-stake requesters draw from the exact same bucket as staked validators.

## Finding Description
`decode_request` looks up `stake` from `epoch_staked_nodes` purely for bookkeeping [2](#0-1) . `decode_requests` uses stake only to increment `handle_requests_unstaked`/`handle_requests_staked` counters, not to gate or throttle [3](#0-2) . The single stake-aware control point is the truncation/sort in `run_listen`, which activates only `if decoded_requests.len() > MAX_REQUESTS_PER_ITERATION` [1](#0-0) . The `data_budget` token bucket is passed into `run_listen` as a single shared instance and into `handle_requests` for actual per-request cost consumption [4](#0-3) [5](#0-4) , and its `consume_tokens` implementation makes no distinction between callers [6](#0-5) .

I was able to confirm the decode/truncation/consumption path exactly as described in the claim, but I was not able to locate or inspect (within available iterations) the actual `handle_requests` consumption loop, the `TokenBucket` construction/refill-rate parameters for `data_budget`, or the ping-cache/per-IP throttling logic that gates entry into `requests_receiver`. Those pieces determine whether an attacker can practically sustain sub-1024/iteration traffic from enough distinct identities/addresses to meaningfully exhaust the budget, and whether ping-cache liveness checks or other upstream socket-level controls (e.g., per-IP connection limits) already mitigate this. This is a materially relevant gap: the severity of the claim rests on the assumption that no independent per-requester or per-IP cap exists elsewhere in the pipeline, which the claim's own "Note on confidence" explicitly flags as unverified.

## Impact Explanation
If accurate as described, this would constitute non-RPC remote resource exhaustion on a validator's repair-serving capacity — an allowed impact category (non-RPC remote exhaustion/crash) — since the shared bandwidth budget could be starved by unprivileged, low-stake/no-stake actors, causing legitimate stake-weighted repair requests to be dropped (`dropped_requests_outbound_bandwidth`). This matches the target scope of causing degradation to a validator's repair service without requiring the attacker to be a validator, be staked, or hold any privileged role.

## Likelihood Explanation
The likelihood cannot be conclusively assessed from the code paths reviewed. The claim itself acknowledges the key uncertainty: whether ping-cache checks, per-IP/per-connection socket-level rate limits, or the `TokenBucket` refill rate (none of which were inspected in this pass) already bound the practical exhaustion window tightly enough to make this a low-severity or non-issue in practice. Repair request ingestion requires passing `is_well_formed_repair_request` and `verify_signed_packet` (sig-verify) before reaching `decode_request`, and a `ping_cache` liveness check is referenced as a parameter to `handle_requests`/`run_listen`, but the actual gating logic and cost of satisfying it per-identity was not confirmed.

## Recommendation
Introduce stake-weighted or per-requester sub-budgets in the actual `handle_requests` token-consumption path (not just the rare truncation branch), e.g., a separate, smaller token bucket allocation for zero/low-stake requesters, similar to QUIC's unstaked connection throttling. Before implementing, first verify via code (not present in this review) what independent per-IP/per-connection/ping-cache mitigations already exist in the receive path, since the incremental benefit of this fix hinges on that answer.

## Proof of Concept
Not independently verified; the claim provides only a static code-path argument (confirmed for `decode_request`, `decode_requests`, and the truncation logic in `run_listen`) and explicitly defers a runtime PoC and the ping-cache/per-IP analysis to further investigation, which was not completed in this session either.

    /// Attempts to consume tokens from bucket.
    ///
    /// On success, returns Ok(amount of tokens left in the bucket).
    /// On failure, returns Err(amount of tokens missing to fill request).
    #[inline]
    pub fn consume_tokens(&self, request_size: u64) -> Result<u64, u64> {
        let now = self.time_us();
        self.update_state(now);
        match self.tokens.fetch_update(
            Ordering::AcqRel,  // winner publishes new amount
            Ordering::Acquire, // everyone observed correct number
            |tokens| {
                if tokens >= request_size {
                    Some(tokens.saturating_sub(request_size))
                } else {
                    None
                }
            },
        ) {
            Ok(prev) => Ok(prev.saturating_sub(request_size)),
            Err(prev) => Err(request_size.saturating_sub(prev)),
        }
    }
