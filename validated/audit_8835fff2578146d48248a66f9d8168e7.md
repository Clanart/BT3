### Title
Cross-Context Signature Replay Between `beneficiary_message` (accumulate) and `message` (withdraw) Due to Identical Encoding and Shared Nonce - (File: modules/pallets/relayer/src/withdrawal.rs, modules/pallets/relayer/src/accumulate.rs)

### Summary
`pallet_ismp_relayer` exposes two unprivileged, unsigned entrypoints — `accumulate_fees` and `withdraw_fees` — that both authenticate a relayer-signed message and both draw from the same per-`(account, state_machine)` `Nonce` counter. The two message constructors produce byte-identical preimages when a beneficiary is present, so a signature crafted for one call is also a valid signature for the other, allowing an unprivileged submitter to redirect a relayer's fee balance through the "wrong" call path.

### Finding Description
`withdraw`'s signed payload is built by: [1](#0-0) 

`accumulate`'s beneficiary-redirect payload is built by: [2](#0-1) 

Both functions hash `(nonce: u64, state_machine: StateMachine, beneficiary: Vec<u8>/&[u8]).encode()`. SCALE-encoding `&[u8]` and `Vec<u8>` produces identical bytes, so for the same `(nonce, chain, beneficiary)` triple, `message(nonce, chain, Some(beneficiary))` and `beneficiary_message(nonce, chain, beneficiary)` are the exact same 32-byte keccak digest. There is no domain separator (e.g., a call-specific tag/prefix) distinguishing "authorize a withdraw_fees payout" from "authorize an accumulate beneficiary redirect".

Compounding this, both flows consume the *same* `Nonce::<T>` storage entry keyed by `(address, state_machine)`: [3](#0-2) [4](#0-3) 

Both entrypoints are permissionless (`ensure_none`): [5](#0-4) 

Consequence: if a relayer signs a `(nonce, chain, beneficiary)` payload intending it to be consumed exclusively via `accumulate_fees` (redirecting a *specific proven batch* of newly-accumulated fees to `beneficiary`), that same signature bytes-for-bytes also satisfies the verification check in `withdraw_fees`. Because `withdraw_fees` is a completely different operation — it drains the *entire current* `Fees::<T>` balance for `(address, dest_chain)` to `beneficiary` immediately, rather than the specific batch amount the signer intended to redirect — an unprivileged party who obtains this signature (e.g., it was published in a prior block, since Substrate extrinsics/events are public) can submit it via `withdraw_fees` to trigger an operation the signer never authorized in that form: an immediate full-balance withdrawal to `beneficiary`, consuming the nonce and blocking the originally-intended `accumulate_fees` call.

This directly violates the target invariant that "each withdrawal or payee redirection signature must be single-use and bound to the exact destination chain and beneficiary" — bound to chain/beneficiary yes, but not bound to *which pallet call/operation* it authorizes, enabling cross-context reinterpretation.

### Impact Explanation
An attacker who can observe a relayer's `beneficiary_message` signature (published on-chain as part of a legitimate `accumulate_fees` call, or intercepted before inclusion) can replay it through `withdraw_fees` to force an early, full-balance disbursement of the relayer's accrued fees to the signed beneficiary — potentially before the relayer intended, and for a larger amount than the specific batch the relayer meant to redirect. This is a wrongful/duplicate settlement of protocol-tracked relayer fee balances, matching the "stealing or loss of funds" / "replay / false proof acceptance" impact categories.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid `(nonce, chain, beneficiary)` signature that a relayer produced for the `accumulate_fees` beneficiary-redirect flow. Since Substrate transactions and events are public once submitted/included, an attacker monitoring the chain or mempool can extract this signature and race it into `withdraw_fees` before the intended `accumulate_fees` call lands (both consume the same nonce, so only one succeeds). This has some overlap with front-running/mempool-observation conditions, but the root defect — identical message encodings across two semantically distinct unprivileged calls — is independent of front-running and constitutes a genuine domain-separation flaw.

### Recommendation
Add a distinct domain separator/tag to each signed payload (e.g., prefix `message()` and `beneficiary_message()` with different constants like `b"WITHDRAW"` vs `b"ACCUMULATE_REDIRECT"`) so signatures cannot be reused across the two call paths, and consider using independent nonce counters (or a single nonce space validated against the specific call type) to further prevent cross-call replay.

### Proof of Concept
1. Relayer signs `msg = beneficiary_message(nonce=N, chain=C, beneficiary=B)` (per `modules/pallets/relayer/src/accumulate.rs:309-315`) intending to submit it inside a `WithdrawalProof.beneficiary_details` via `accumulate_fees`.
2. Because `message(N, C, Some(B))` in `modules/pallets/relayer/src/withdrawal.rs:192-197` hashes the identical `(N, C, B).encode()` bytes, the same signature also passes verification in `withdraw`.
3. An attacker observing this signature (from a pending/prior transaction) submits `withdraw_fees(origin=None, WithdrawalInputData { signature, dest_chain: C, beneficiary: Some(B) })` before the relayer's intended `accumulate_fees` call lands.
4. `withdraw` succeeds: it verifies the (reused) signature, increments `Nonce::<T>::get(address, C)` to `N+1`, zeroes `Fees::<T>` for `(C, address)`, and dispatches a payout of the *entire* current balance to `B` — not the batch-specific amount the relayer intended — per `modules/pallets/relayer/src/withdrawal.rs:116-184`.
5. The relayer's original `accumulate_fees` call, when it lands, now fails signature verification because the nonce has already advanced, confirming the intended operation was pre-empted and reinterpreted by the replayed signature.
