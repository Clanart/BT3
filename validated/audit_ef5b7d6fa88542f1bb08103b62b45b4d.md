### Title
`whenNotPaused` on `onPostRequestTimeout` permanently strands already-burned funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken`/`HyperFungibleTokenUpgradeable` gate `send()`, `onAccept()`, and `onPostRequestTimeout()` all behind the same `whenNotPaused` modifier. `send()` burns tokens immediately and only re-mints them (refund) via `onPostRequestTimeout`, or delivers them via `onAccept` on the destination chain. If the contract is paused between the burn and the timeout/delivery callback, both recovery paths revert, and the burned tokens can become permanently unrecoverable — the exact failure class described in the external report: an emergency/administrative "disable" flag blocking the internal `_mint()` path that a cross-chain flow depends on to complete or roll back a transfer.

### Finding Description
`send()` burns tokens from the caller on the source chain and dispatches an ISMP POST request: [1](#0-0) 

The only two paths that can ever restore/settle those burned tokens are `onAccept` (mint to beneficiary on the destination chain) and `onPostRequestTimeout` (mint refund back to sender on the source chain if the message times out): [2](#0-1) 

Both are declared with `onlyHost whenNotPaused`. Since `pause()` is a normal owner-callable emergency function (not a compromise or malicious actor scenario), it can legitimately be invoked between the time a `send()` burns tokens and the time the corresponding `onAccept`/`onPostRequestTimeout` callback is delivered by the host (an event fully outside the pauser's control, since delivery timing depends on relayers and cross-chain proof submission, not the token contract). During that window:
- If the message is delivered while paused, `onAccept` reverts — the destination-chain mint never happens for that delivery attempt.
- If the message times out while paused, `onPostRequestTimeout` reverts — the refund mint never happens either.

There is no other code path that can re-mint the burned amount. `unpause()` only re-enables future calls; it does not automatically re-drive failed callback dispatches, and whether the ISMP host retries an `onAccept`/`onPostRequestTimeout` delivery after a module-side revert (vs. marking the commitment/receipt as consumed regardless of app-level success) determines whether the tokens are permanently lost or merely delayed — but even in the best case, the recipient/sender has no funds during the entire pause window despite the source-side burn already being final and irreversible.

This mirrors the `isMintEnabled` bug precisely: burning/committing on one side is unconditional, but the corresponding internal `_mint()` used to complete or unwind the transfer is gated by an "emergency" flag that was not designed with in-flight cross-chain state in mind.

### Impact Explanation
Funds that have already been burned/committed on the source chain can become stuck or lost with no way to reclaim them while the flag is set, and potentially permanently if the underlying ISMP host does not retry module calls that reverted (this repo's `HandlerV2` request/timeout handling records receipts independent of the app callback's success/failure in comparable paths, e.g. `state-coprocessor`'s `store_response_receipt` pattern, suggesting the same non-retriable-commitment risk applies here). This falls squarely under "Bridged assets ... must move exactly once and only to the rightful beneficiary and amount" — here they can fail to move at all despite already being debited, which is a direct loss-of-funds scenario for the end user.

### Likelihood Explanation
`pause()`/`unpause()` are legitimate, expected operational functions (not a compromised key or malicious governance scenario) intended for emergencies; any real-world incident that triggers an owner to pause the contract while user transfers are in flight will trigger this exact scenario. Because in-flight cross-chain messages can take minutes to hours to be delivered or time out, the race window between "send() succeeded" and "callback delivered" is realistically large, and pause events are precisely the kind of event operators reach for during active incidents — increasing the likelihood that in-flight transfers exist at pause time.

### Recommendation
Decouple the pause control used for `send()`/`transfer()`/`transferFrom()` (which can safely reject new user-initiated actions) from the callbacks that settle or refund already-debited value (`onAccept`, `onPostRequestTimeout`). These two callbacks should not be blocked by the same `whenNotPaused` flag used for outbound initiation — or, if pausing incoming settlement is required for genuine emergencies (e.g., a compromised bridge), the contract must provide a guaranteed, permissioned "manual settle/refund" path once unpaused so debited value is never left stranded.

### Proof of Concept
1. User calls `send()` on chain A with amount X; `_burn(user, X)` executes and an ISMP POST request is dispatched. [1](#0-0) 
2. Before the request is delivered/times out, the owner calls `pause()` for an unrelated emergency reason. [3](#0-2) 
3. The request times out; the host later attempts to deliver `onPostRequestTimeout(incoming)` to refund the user — this reverts because the contract is paused. [4](#0-3) 
4. The user's X tokens remain burned with no successful refund and no destination-side mint (the delivery path also would revert under the same pause via `onAccept`), leaving the funds stuck/lost for the duration of the pause — or permanently, depending on whether the host retries a reverted module callback.

**Note:** I could not fully verify within the available tool calls whether `HandlerV2`'s post-request-timeout dispatch marks the ISMP request/timeout receipt as consumed even when the downstream `onPostRequestTimeout` call reverts (which would make the loss permanent rather than merely delayed until `unpause()`). Confirming this exact retry/receipt-consumption semantics in `evm/src/core/HandlerV2.sol` would be necessary to fully establish permanent-vs-temporary loss.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) external override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
