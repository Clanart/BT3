### Title
Forfeit mechanism can be bypassed by claiming rewards in many small increments - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder._calExpireForfeit` forgives (rounds to zero) any forfeit amount smaller than 0.1% of the reward being claimed. Because a user fully controls how often they call claim, they can always claim tiny amounts of reward, keeping the computed forfeit below this dust threshold on every single call, and thereby bypass the forfeit mechanism entirely regardless of their actual `rewardablePercentWAD`.

### Finding Description
When a partially-unlocked (or unlocking) vlMGP holder claims rewards, `_sendReward` computes how much of the claimed reward must be forfeited based on the user's rewardable percentage: [1](#0-0) 

The forfeit itself is computed in `_calExpireForfeit`: [2](#0-1) 

The line `if (forfeitAmount < (_amount / 1000)) { forfeitAmount = 0; ... }` is a "dust forgiveness" shortcut intended to save gas on negligible forfeits. However, it operates on the *ratio* of forfeit to the amount being claimed in a single call, not on an absolute/fixed threshold. Since `_amount` here is the reward accrued and claimed in that single transaction (which the user fully controls by choosing when/how often to call claim/multiclaim through `MasterMagpie`), a user can always trigger this branch by claiming very small chunks of reward at a time — the forfeit fraction of a tiny claim will always be smaller than the dust threshold relative to that same tiny claim, since it scales proportionally with `_amount` (the rewardable percentage is fixed at claim time via `getRewardablePercentWAD`, from `VLMGP.sol`): [3](#0-2) 

By calling claim frequently with small intervals (e.g., every block or every few seconds) instead of allowing rewards to accrue and claiming a lump sum, the forfeit computed on each individual small claim rounds to zero every time, while the un-forfeited "waiting" reward that should have been redistributed to other stakers (via `_queueNewRewardsWithoutTransfer`, invoked only when `forfeitAmount > 0`) is instead kept in full by the claiming user.

### Impact Explanation
This is a direct theft of yield that is meant to be redistributed to other fully-vested vlMGP/mWomSV stakers. An attacker who has not fully waited out their unlock/vote-lock period is supposed to forfeit a proportional share of rewards to the pool; by looping small claims, the attacker keeps 100% of rewards, permanently depriving other reward-pool participants of the yield that should have been queued as `ForfeitRewardAdded`. This is a direct theft of unclaimed yield belonging to other users, matching the accepted impact class.

### Likelihood Explanation
Any ordinary wallet holding vlMGP/mWomSV in an unlocking or partially-locked state can trigger this simply by calling the public claim path (`MasterMagpie.multiclaimFor`/`multiclaimOnBehalf`) at high frequency instead of once. No privileged role, admin action, or external protocol dependency is required — it is purely a function of transaction frequency, which is entirely user-controlled. The only cost to the attacker is gas, which is explicitly the incentive the original dust-forgiveness logic assumed would deter grinding, but which does not scale with the magnitude of the bypassed forfeit when repeated.

### Recommendation
Do not forgive forfeit based on a ratio of the current claim amount. Instead:
- Track and forgive dust based on an absolute token amount threshold (e.g., a fixed minimum wei amount), not a percentage of the current call's claim size, or
- Accumulate/track forfeit debt across calls per user rather than resetting the ratio check on every individual small claim, or
- Round the forfeit calculation up rather than down (`forfeitAmount = _amount - rewardableAmount`, ensure this doesn't shrink toward zero disproportionately for small claims), consistent with the general fix pattern in the referenced report (round fee/forfeit calculations up, not down).

### Proof of Concept
1. User A holds vlMGP with `rewardablePercentWAD` < 100% (i.e., currently unlocking, so a portion of rewards should be forfeited per `expectedPenaltyAmount`/`_calExpireForfeit`).
2. Instead of waiting and calling `claim` once for a large accrued reward, User A calls `MasterMagpie.multiclaimFor` for the vlMGP rewarder every block (or with minimal delay) so that `userRewards[_rewardToken][_account]` (the `_amount` in `_calExpireForfeit`) is always very small.
3. For each tiny claim, `forfeitAmount = _amount - rewardableAmount` is computed, and because `forfeitAmount < _amount/1000` triggers on essentially every small division-rounded result, `forfeitAmount` is set to `0` and `rewardableAmount = _amount` on every single call — see [4](#0-3) .
4. Over many iterations, User A receives 100% of all accrued rewards via `_sendReward`'s `toSend = userRewards[...] - forfeitAmount` (forfeitAmount always 0), never contributing anything to `_queueNewRewardsWithoutTransfer` for other stakers, whereas a single lump-sum claim of the same total reward would have forfeited a meaningful, non-dust amount.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
```
