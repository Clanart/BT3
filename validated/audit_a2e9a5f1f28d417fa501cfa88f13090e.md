### Title
Cross-session OAuth account binding via stale `this.state` read after `await` in `resolveOAuthRequest` - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.resolveOAuthRequest()` validates the CSRF `state` parameter against `this.state.oauthState` *before* awaiting the network calls that exchange the OAuth `code` for a token and fetch the user, but then resolves the flow by reading `this.state.oauthState.onAuthCompleted` *again, after the `await`*, instead of using a value captured at validation time. If the sign-in session changes while the token exchange is in flight (a new sign-in is started, e.g. to a different endpoint), the account fetched for the *original* endpoint gets bound to the *new* session's completion callback.

### Finding Description [1](#0-0) 

```
public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) return
    if (!this.state.oauthState) return
    if (this.state.oauthState.state !== action.state) { ... return }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)   // <-- await point

    if (token) {
      const account = await fetchUser(endpoint, token)             // <-- another await
      this.state.oauthState.onAuthCompleted(account)                // <-- re-reads live `this.state`
    } else {
      this.state.oauthState.onAuthError(...)
    }
}
```

The CSRF check (`this.state.oauthState.state !== action.state`) correctly validates the *current* live session at the top of the function, but that check is only meaningful for the moment it executes. `endpoint` is captured by value before the `await`, but `oauthState` (which holds `onAuthCompleted`/`onAuthError`, i.e. the promise resolvers tied to the specific `SignInStore.authenticateWithBrowser()` invocation) is **not** captured. After the two `await`s (`requestOAuthToken`, `fetchUser`), the code dereferences `this.state.oauthState` again. If, during those awaits, the store's mutable `state` field has been replaced — e.g. the user cancelled and started a new sign-in flow (`reset()` → `beginDotComSignIn()`/`beginEnterpriseSignIn()` → `authenticateWithBrowser()`, all of which call `setState(...)` and thereby swap `this.state.oauthState`) — then `this.state.oauthState` now belongs to the *new* session, while `account`/`token` were derived from the *old* session's `endpoint`.

The result: `onAuthCompleted(account)` — the resolver of the **new** session's pending Promise in `authenticateWithBrowser()` — is invoked with an `Account` object obtained from the **old** endpoint's OAuth exchange. `authenticateWithBrowser()`'s `.then()` handler only checks `this.state.kind === SignInStep.Authentication` (not which specific oauthState/csrfToken produced the account), so it will happily call `this.emitAuthenticate(account)` and transition to `Success`, completing the *new*, user-visible sign-in flow with an account that was never validated against that flow's endpoint or CSRF token.

Contrast with the `.catch()` handler for the same promise in `authenticateWithBrowser()` (lines 318-329), which explicitly re-validates `this.state.oauthState?.state === csrfToken` before touching `this.state` — i.e. the developers were aware that `this.state` can change out from under an in-flight OAuth completion, but this specific guard is missing on the success path in `resolveOAuthRequest`.

### Impact Explanation
This is an unauthorized OAuth/account-binding bug. The trigger for the stale/old exchange is a `x-github-client://oauth?code=...&state=...` deep link, which is exactly the kind of attacker-controlled input this task's valid-impact criteria call out ("a link or deep link the user clicks"). An attacker who operates a slow or deliberately delayed GitHub Enterprise-like OAuth endpoint (or who can otherwise trigger `resolveOAuthRequest` for a stale/slow first flow while the user starts a second, legitimate sign-in during the delay) can cause the Desktop app to silently complete a *different*, currently-active sign-in dialog (e.g. one the user believes is being done against github.com) using an account/token pair obtained from the attacker-controlled endpoint. This corrupts the app's authentication state and can result in the wrong account/token being bound into `AccountsStore`, without any endpoint/state cross-check at the point the account is actually accepted.

### Likelihood Explanation
Exploitation requires a timing window where a second sign-in flow is initiated while an earlier OAuth code exchange for a different endpoint is still pending — plausible if an attacker's OAuth/enterprise server intentionally delays its `/login/oauth/access_token` or user-fetch response, combined with the user cancelling/retrying sign-in (a realistic user action after apparent "stuck" or slow enterprise sign-in). No leaked credentials, local access, or malware are required — only network-timing control on a server the user is attempting to authenticate against and normal UI actions (cancel & retry sign-in) by the user, both of which are within the "unprivileged, attacker-controlled remote endpoint" threat model.

### Recommendation
Capture the relevant `oauthState` object (and/or a session identifier / the `csrfToken`) into a local variable at the top of `resolveOAuthRequest`, before any `await`, and use that captured reference — not `this.state` — to invoke `onAuthCompleted`/`onAuthError`. Additionally, re-validate after each `await` that `this.state?.oauthState === capturedOauthState` (or that the CSRF token still matches) before accepting the fetched account, mirroring the check already present in the `.catch()` branch of `authenticateWithBrowser()`.

### Proof of Concept
Conceptual reproduction (network-timing driven, no local file/tool access needed to demonstrate the logic):
1. User starts Enterprise sign-in to `https://evil-ghe.example` (attacker controlled) via `authenticateWithBrowser()`; store state becomes `Authentication` with `oauthState.state = S1`, `oauthState.endpoint = evil-ghe`.
2. Browser redirects to `x-github-client://oauth?code=C1&state=S1`, causing `resolveOAuthRequest({code:C1, state:S1})` to be invoked; state check passes; `requestOAuthToken('https://evil-ghe.example', C1)` begins — the attacker's server delays this response indefinitely/for a long time.
3. Before that promise resolves, the user cancels and starts a new sign-in to `https://github.com` via `beginDotComSignIn()`/`authenticateWithBrowser()`; this calls `reset()` (which does NOT resolve/complete anything problematic yet) then `setState(...)` with a fresh `oauthState.state = S2`, `oauthState.endpoint = api.github.com`.
4. The user completes the legitimate `github.com` OAuth in the browser; but before the second flow's own `resolveOAuthRequest` call for `S2` is triggered, the attacker's delayed response for step 2 finally arrives.
5. `resolveOAuthRequest`'s continuation executes `fetchUser('https://evil-ghe.example', tokenFromStep2)` then calls `this.state.oauthState.onAuthCompleted(account)` — but `this.state.oauthState` is now the *dotcom* session's resolver (`S2`'s `onAuthCompleted`), which resolves the dotcom `authenticateWithBrowser()` promise with the attacker's account, causing `emitAuthenticate(account)` and transition to `Success` for the github.com flow using an attacker-supplied account.

Note: I was not able to execute this scenario in a live app instance (no runtime/browser access in this environment); the analysis is based on static tracing of `resolveOAuthRequest`, `authenticateWithBrowser`, and `setState`/`reset` in `app/src/lib/stores/sign-in-store.ts`, confirming the missing re-validation after the `await` points.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
