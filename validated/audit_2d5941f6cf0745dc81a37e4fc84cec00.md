Based on my research, I found a concrete gap in GitHub Desktop's deep-link URL parsing that structurally mirrors the Ammplify bug: an attacker-controlled input (a clicked `x-github-client://`/`github-mac://` deep link) is accepted and partially trusted without validating one specific field, while sibling fields in the same parser *are* validated — the same "selective validation" pattern that caused the smart-contract bug (`pool` wasn't checked while other maker parameters were).

### Title
Unsanitized `filepath` query parameter in deep-link `open-repository-from-url` action allows path traversal outside the target repository - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL` in [1](#0-0)  validates the `branch` parameter with `testForInvalidChars` and the `pr` parameter with a strict `^\d+$` regex before constructing an `IOpenRepositoryFromURLAction`, but the `filepath` parameter is read via `getQueryStringValue(query, 'filepath')` and passed through completely unchecked: [2](#0-1) 

### Finding Description
This is the Desktop analog of the Ammplify root cause: an attacker-supplied value that reaches a sensitive downstream operation is not verified even though structurally similar sibling values in the same function are verified. Here, `filepath` is documented as "the file to open after cloning the repository" [3](#0-2)  and is consumed later in `dispatcher.ts` (6 references) to open a file relative to the freshly cloned repository. Because `filepath` is never checked for traversal sequences (`../`), a malicious `github-mac://openRepo/...&filepath=../../../../some/sensitive/path` or `x-github-client://openRepo/...` deep link could cause Desktop to resolve and open a path outside the intended repository directory when the user clicks an "Open in Desktop" style link.

I was not able to fully trace the exact join/open call in `dispatcher.ts` within the available tool budget, so I cannot confirm with certainty whether the consuming code re-validates or normalizes the path before use (e.g., with a `path.join` + prefix check) — this is the main open question for this finding.

### Impact Explanation
If the downstream consumer does not re-validate the resolved path stays within the cloned repository, this could cause GitHub Desktop to open (and display, via whatever external editor/handler is configured) an arbitrary file on the user's filesystem outside the repo, driven entirely by an attacker-controlled deep link the user clicks — matching the "attacker controls...a link or deep link the user clicks" and "file...read outside the repo" categories in scope.

### Likelihood Explanation
Medium-to-low confidence: the parsing-side gap is concretely verified (asymmetric validation of `branch`/`pr` vs. `filepath`), but exploitability depends entirely on unverified code in `dispatcher.ts` that consumes `filepath`. If that code already does path normalization/containment checks, there is no vulnerability. Given the note here is not fully confirmed, this should be treated as a lead requiring one more verification step (reading the `dispatcher.ts` filepath-handling code) rather than a confirmed finding.

### Recommendation
In `parse-app-url.ts`, sanitize `filepath` the same way other identifiers are sanitized elsewhere in the codebase (e.g., reuse the traversal-rejection logic already implemented for clone names in `sanitizeCloneName`, `app/src/lib/remote-parsing.ts:88`, which explicitly strips `..` segments). Reject the action (return `unknown`) if `filepath` contains `..` path segments, is absolute, or resolves outside the repository root once joined. Additionally, wherever `filepath` is eventually joined with the repository path in `dispatcher.ts`, add a `path.resolve` + prefix-containment assertion as defense in depth.

### Proof of Concept
Not executable without confirming the `dispatcher.ts` sink; conceptually:
```
github-mac://openRepo/https://github.com/octocat/Hello-World?branch=master&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa
```
would pass `parseAppURL` validation unchanged (no check applied to `filepath`) and, if the consumer does not sanitize it, would resolve to a path outside the intended repository.

**Caveat:** Because I could not verify the actual file-open/path-join logic in `app/src/ui/dispatcher/dispatcher.ts` before running out of tool calls, this should be verified further (start a Devin session or read those specific lines) before treating this as a confirmed, exploitable vulnerability rather than a plausible lead based on the asymmetric-validation pattern found in the parser.

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown
}
