Based on this analysis, this is a legitimate analog to the reported bug class - a verification (HMAC signature) that does not bind all the fields it should, permitting a forged/misattributed authenticated request.

### Title
Webhook HMAC verification does not bind the shop domain, enabling cross-shop forged webhook requests - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only that `request.raw_post` matches the `X-Shopify-Hmac-Sha256` header using the app's shared client secret [1](#0-0)  via `PayloadVerification#hmac_valid?` [2](#0-1) . The `shop_domain` helper, which downstream jobs use to attribute the payload to a specific shop, simply reads the `X-Shopify-Shop-Domain` request header with no verification and is not part of the HMAC-signed data [3](#0-2) .

### Finding Description
The HMAC secret used in `hmac_valid?` is `ShopifyApp.configuration.secret` (the app's API/client secret), which is identical for every shop that has the app installed - it is not shop-specific [4](#0-3) . Because the signature only covers `request.raw_post` and never the shop-domain header, a party with legitimate access to their own shop's genuine webhook (a `(body, HMAC)` pair that is valid under the shared secret) can replay that exact body and HMAC directly to the app's webhook endpoint while freely setting the `X-Shopify-Shop-Domain` header to name a different, victim shop. `verify_request` will still pass because it never inspects or ties the header to the signed body [1](#0-0) .

Documented and generated usage patterns feed this unverified `shop_domain` directly into background jobs that act on shop data, e.g. `CartsUpdateJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` [5](#0-4) , and the generated declarative webhook controller does the same with `webhook_request.shop` (also header-derived) [6](#0-5) .

This mirrors the referenced bug class: a security check that is correctly enforced in the "normal" case but has an unguarded path (here, the shop-attribution header) that isn't covered by the same integrity check as the rest of the request, letting an attacker supply an unauthenticated value that downstream logic implicitly trusts as authenticated.

### Impact Explanation
An attacker who controls (or merely uses) any shop with the target app installed can forge webhook deliveries that are accepted as authentic for an arbitrary victim shop domain, because the shop attribution is not covered by the signature. Depending on the app's job implementations (per the documented pattern), this can inject attacker-controlled webhook body content tagged as belonging to a victim shop, corrupting that shop's derived data, triggering unintended side effects (e.g., re-processing "orders/create" or "app/uninstalled"-style logic) against a shop the attacker does not own, and enabling cross-shop data confusion.

### Likelihood Explanation
Exploitation requires only: (1) the app being installed on a shop the attacker controls (any developer/merchant account is sufficient) to obtain a valid `(body, HMAC)` pair, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a custom `X-Shopify-Shop-Domain` header, which is trivial. No secret knowledge or cryptographic break is needed, only knowledge of the (documented, not secret) HMAC construction and use of a self-obtained valid pair.

### Recommendation
Bind the shop attribution to the verified payload instead of trusting a separate header: verify that `X-Shopify-Shop-Domain` corresponds to a shop with a currently valid, stored session/installation record before dispatching jobs, and/or include the shop domain in the value that is HMAC-verified (e.g., derive the shop from the webhook body when the topic includes it, or maintain a per-shop webhook secret if available). At minimum, `WebhookVerification#verify_request` should reject requests where the `shop_domain` header does not match an installed/known shop for this app, closing the gap where signature validity and shop attribution are decoupled.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., `carts/update`) so Shopify sends a genuine webhook `(raw_body, X-Shopify-Hmac-Sha256)` pair to the app's endpoint.
2. Attacker captures this `(raw_body, hmac)` pair (e.g., via their own proxy/logging on infra they control, or by using an app-proxy/dev store they control to intercept it).
3. Attacker sends a new POST directly to the same webhook endpoint, reusing the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because the body and shared secret are unchanged [1](#0-0) .
5. The controller/job proceeds using `shop_domain` read from the forged header [3](#0-2) , causing the attacker's webhook body to be processed as if it belonged to `victim-shop.myshopify.com`.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
