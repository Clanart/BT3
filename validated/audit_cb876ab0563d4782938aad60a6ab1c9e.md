## Title
CW20ERC20Pointer.approve() computes an allowance delta from live state, making it front-runnable to double-spend allowances - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer.approve()` does not directly overwrite the underlying CW20 allowance. Instead it reads the current allowance and issues an `increase_allowance`/`decrease_allowance` message for the delta between the current and requested values. This still allows the classic ERC20 approve front-running attack: a spender can drain the existing allowance before the owner's `approve()` transaction lands, and the pointer contract will unconditionally top up the allowance by the newly requested amount on top of the already-spent balance, letting the spender extract `old + new` tokens instead of just `new`.

### Finding Description
`approve()` in `CW20ERC20Pointer.sol` queries the live allowance and only pushes the delta to the underlying CW20 contract: [1](#0-0) 

Trace of the exploit:
1. Owner has previously approved `spender` for `N` tokens via the pointer (which maps to `increase_allowance` on the CW20 contract).
2. Owner submits a new `approve(spender, M)` transaction intending to reduce/change the allowance to `M`.
3. `spender` front-runs by calling `pointer.transferFrom(owner, attacker, N)` — this reaches the underlying CW20's `transfer_from`, draining the full existing allowance to `0`.
4. Owner's `approve(spender, M)` transaction executes. It re-queries `allowance(msg.sender, spender)` (now `0` due to the front-run drain) and, since `0 < M`, calls `increase_allowance(spender, M)` — unconditionally adding `M` on top of the already-spent `N`.
5. `spender` then calls `transferFrom(owner, attacker, M)` and receives `M` additional tokens.

Total drained: `N + M`, exceeding what the owner ever intended to approve at any single point in time. This is functionally identical to the classic ERC20 approve race described in the report, except the pointer's delta-computation logic actively recomputes based on post-frontrun state rather than protecting against it, so the same exploit primitive applies unmodified to Sei's CW20→ERC20 pointer bridge.

### Impact Explanation
This lets any spender with a nonzero allowance on a `CW20ERC20Pointer` steal tokens beyond the intended approved amount whenever the owner adjusts the allowance, resulting in direct fund loss for the CW20 token owner routed through the EVM pointer. This falls squarely under "unauthorized transfer via precompile or pointer," one of the accepted impact categories, and is reachable purely by an unprivileged EVM transaction sender racing another user's `approve` call.

### Likelihood Explanation
The attack requires only that the victim ever changes an existing nonzero allowance (a very common allowance-management operation) and that the spender/attacker is watching the mempool to front-run with a higher gas price transaction — both trivially achievable by any public RPC client with no special privileges. No admin or validator collusion is needed.

### Recommendation
Follow the same two-step safe-approval pattern recommended by OpenZeppelin: require `approve()` to only succeed when either the requested amount is `0` or the existing on-chain allowance is `0`, and expose explicit `increaseAllowance`/`decreaseAllowance` entry points that atomically read-and-modify the allowance instead of computing/transmitting a delta computed from a value that can change between submission and inclusion of the transaction.

### Proof of Concept
```
// underlying CW20 allowance(owner, spender) = N
1. attacker (spender) sees owner's pending tx: pointer.approve(spender, M)
2. attacker front-runs: pointer.transferFrom(owner, attacker, N)   // drains N, allowance -> 0
3. owner's tx executes: approve() queries allowance()=0, calls increase_allowance(spender, M) -> allowance = M
4. attacker calls pointer.transferFrom(owner, attacker, M)          // drains M more
// attacker total received: N + M, exceeding owner's ever-intended single allowance M
``` [1](#0-0)

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
