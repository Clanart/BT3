### Title
`build_refute_prompt` truncates the diff to a fixed 8000-char prefix, causing its own "PRE-EXISTING" refutation rule to discard real in-diff findings whose evidence falls after the cutoff - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` (and the structurally identical inline `refute_prompt` construction in `agentic_review`) embeds the diff shown to the adversarial adjudication stage with a hard `diff_text[:8000]` character slice, independent of where in the diff a flagged candidate's evidence actually lives. Because the refute prompt itself instructs the model to REFUTE any candidate whose `vulnerableCode` "does NOT appear on any + line in the DIFF block above," a candidate that is genuinely introduced by the change but whose diff hunk falls after byte 8000 of the concatenated diff will be refuted purely due to this truncation artifact, not because it is actually pre-existing or safe.

### Finding Description
`cap_diff_for_prompt` allows up to 80,000 bytes per file and 400,000 bytes total for the diff shown to the Stage-1 investigate pass [1](#0-0) , and `tag_diff_anchor` classifies candidates as `in_diff`/`off_diff` against that full (untruncated) diff text [2](#0-1) . However, when the same diff is re-embedded for Stage 2 adjudication, `build_refute_prompt` slices it down to only the first 8000 characters with no relation to where the flagged candidate's `vulnerableCode` actually sits: `"\n\nDIFF:\n" + diff_text[:8000]` [3](#0-2) . The identical pattern is duplicated inline in `agentic_review`'s self-refute branch [4](#0-3) .

The refute prompt then explicitly instructs the model to REFUTE a candidate if its cited code "does NOT appear on any + line in the DIFF block above — it is unchanged context in a touched file. The diff did not introduce it" [5](#0-4) . Since the DIFF block visible to the model is an arbitrary 8000-character prefix of the concatenated per-file diff (built as `"=== DIFF: {fp} ===\n{content}"` blocks, in file order) rather than the specific hunk relevant to each candidate, any candidate whose actual `+` line appears beyond that prefix is indistinguishable, from the model's point of view, from a pre-existing/unrelated finding — triggering the PRE-EXISTING refutation rule even though the change is real and in-diff.

An attacker who controls repository content that ends up in the reviewed diff (e.g., a large file touched earlier in the change, many touched files, or simply placing the dangerous edit in a file that sorts/iterates after enough bulk content) can push the actual malicious hunk past the 8000-character boundary while keeping the dangerous file within the 80,000/400,000-byte caps that Stage 1 investigate still sees and flags. Stage 1 still reports the candidate (its prompt is not truncated to 8000 chars), but Stage 2's adversarial refuter, working from the truncated view, follows its own explicit instruction to discard it as "not appearing in the diff." This lets untrusted repo content suppress review of a genuinely dangerous change, which is exactly the invariant the question asks about.

### Impact Explanation
The self-refute stage is the plugin's precision gate for the agentic commit reviewer; a finding it refutes is dropped from the final output entirely (`survived = [c for i, c in enumerate(candidates) if i in surv_idx]`) [6](#0-5) . Suppressing a real, correctly-flagged, in-diff vulnerability via a truncation artifact defeats the security-guidance plugin's core purpose of warning about dangerous changes before they land — i.e., a diff containing a genuine security-impacting change (RCE, SSRF, auth bypass, secret exfiltration, etc.) can be pushed through without any warning to the operator/agent, purely by controlling the ordering/size of unrelated content in the same commit.

### Likelihood Explanation
This requires only that the attacker (or attacker-influenced Claude session output) control the composition of the diff being reviewed — no shell access, no credentials, and no changes to hook enforcement are needed. Padding a commit with additional touched files or a moderately large legitimate-looking file before the dangerous edit is trivial and fully within normal commit/PR authoring capability. The 8000-character cutoff is small relative to the 80,000/400,000-byte caps that Stage 1 still honors, so triggering the divergence between what Stage 1 sees and what Stage 2 sees is easy to reach deterministically.

### Recommendation
Do not truncate `diff_text` to a fixed global prefix in `build_refute_prompt`. Instead, either (a) include only the diff hunks relevant to each candidate's `filePath`/`vulnerableCode` (already computed by `tag_diff_anchor`), or (b) apply the same per-file/total byte-cap logic (`cap_diff_for_prompt`) used for Stage 1 so the same diff view is available to Stage 2, or (c) if a hard cap is required, prioritize keeping the hunks that back each candidate in `candidates` before falling back to prefix truncation, and explicitly tell the model when the DIFF block is a filtered/partial view so it cannot invoke the PRE-EXISTING rule based on that omission.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/` test suite:
1. Construct `candidates = [{"filePath": "danger.py", "vulnerableCode": "os.system(user_input)", "category": "...", ...}]`.
2. Construct `diff_text` as `"=== DIFF: padding.py ===\n" + ("x" * 8500) + "\n=== DIFF: danger.py ===\n+os.system(user_input)\n"` so the real `+` line for `danger.py` sits past offset 8000.
3. Call `prompt = build_refute_prompt(candidates, diff_text)`.
4. Assert failure: `"+os.system(user_input)" not in prompt.split("DIFF:\n", 1)[1][:8000]` — i.e., the evidence the PRE-EXISTING rule needs is not present in the DIFF block actually sent to the model, even though the candidate is a legitimate in-diff finding. This demonstrates the "Fast validation" check from the prompt ("assert the dangerous file or path remains present and correctly anchored after truncation") fails: the dangerous line is silently dropped by the fixed-length slice, independent of anchoring to the flagged candidate.
