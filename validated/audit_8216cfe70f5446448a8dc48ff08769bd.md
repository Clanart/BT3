### Title
SSRF via attacker-controlled DataLayer mirror URLs in `http_download` - (File: `chia/data_layer/download_data.py`)

### Summary
DataLayer subscriptions fetch delta/full-tree files from mirror URLs that are read directly from on-chain mirror coins published by the owner of a DataLayer singleton. Any Data Layer client that subscribes to a store (`dl subscribe` / `subscribe_cmd`, reachable via local RPC/CLI) will have its DataLayer service periodically issue outbound HTTP GET requests to those attacker-supplied URLs with no host/scheme validation, mirroring the PinchTab `/download?url=` SSRF pattern (unsanitized `url` passed straight into an outbound network fetch).

### Finding Description
`DataLayer.update_subscriptions_from_wallet()` populates `ServerInfo.url` values straight from `dl_get_mirrors()` mirror coin data with only `rstrip("/")` applied, no scheme or host allow-listing: [1](#0-0) 

`fetch_and_validate()` iterates these `servers_info` entries and calls `insert_from_delta_file()`/`download_file()` using `server_info.url` untouched: [2](#0-1) 

`download_file()` (when no downloader plugin is configured) delegates to `http_download()`, which performs `session.get(server_info.url + "/" + filename, ...)`: [3](#0-2) 

No validation rejects `localhost`, RFC1918/link-local addresses (e.g. `169.254.169.254`), or non-`http(s)` schemes before this request is issued. Mirror URLs are published on-chain via `dl_new_mirror` (`DataLayer.add_mirror`) and are visible/subscribable by any Data Layer participant: [4](#0-3) 

Any store owner can therefore publish a mirror URL pointing at an internal service or cloud metadata endpoint, and any other DataLayer client that subscribes to that store id (a normal, unprivileged Data Layer operation) will have its node issue that outbound request during periodic sync (`update_subscription()` → `fetch_and_validate()`).

Unlike the PinchTab bug, the downloaded content is not returned verbatim to the attacker: `insert_from_delta_file()` requires the fetched bytes to reconstruct the wallet-advertised Merkle root before being committed, and mismatched data is discarded (file unlinked, `server_misses_file` recorded) rather than exposed back to the malicious store owner. So this is a confirmed CWE-918 SSRF (the victim node's DataLayer process makes attacker-directed outbound requests to arbitrary hosts/ports/schemes), but it does not achieve full response exfiltration to the attacker the way the PinchTab report describes.

### Impact Explanation
An attacker who controls a DataLayer store (trivial — anyone can create one) can force any subscribing peer's node process to make outbound HTTP requests to arbitrary internal hosts, local services, or cloud metadata endpoints, enabling internal network reconnaissance/port-scanning and potential side effects on internal-only HTTP endpoints (confused-deputy SSRF). Response bodies are not exfiltrated back to the attacker due to the Merkle-root validation gate, which limits impact compared to the original PinchTab CVE (no `C:H` equivalent). This is a genuine but partial analog — SSRF request forgery without confirmed data exfiltration.

### Likelihood Explanation
Reachable by any unprivileged Data Layer client action: subscribing to a store id is a normal, low-privilege operation (`dl subscribe`, `DataLayerRpcApi` `subscribe`), and mirror URLs are attacker-controlled on-chain data requiring no special permission to publish. The periodic `periodically_manage_data()` loop automatically triggers the vulnerable fetch for all subscribed stores, so exploitation requires no further victim interaction beyond a one-time subscribe.

### Recommendation
Validate/allow-list mirror server URLs before use in `http_download()`/`download_file()`: reject non-`http`/`https` schemes, resolve and block loopback/link-local/private-network/metadata IP ranges, and consider requiring explicit user opt-in (e.g., a config flag) before a subscription's node makes requests to mirror URLs sourced purely from untrusted on-chain data.

### Proof of Concept
1. Attacker creates a DataLayer store and publishes a mirror pointing at an internal target, e.g. `dl add_mirror --id <store_id> --urls http://169.254.169.254 --amount 1 --fee 0` (via `DataLayer.add_mirror` → `dl_new_mirror`).
2. Victim runs `dl subscribe --id <store_id>` (or the DataLayer RPC `subscribe` endpoint) to follow the attacker's store — a routine, unprivileged Data Layer action.
3. On the victim's next `periodically_manage_data()` cycle, `update_subscription()` → `fetch_and_validate()` picks the attacker's mirror URL from `get_available_servers_for_store()` and calls `http_download()`, causing the victim's node process to issue `GET http://169.254.169.254/<filename>` — reaching internal-only/metadata infrastructure that the attacker cannot otherwise reach directly.     async def update_subscriptions_from_wallet(self, store_id: bytes32) -> None:
        mirrors: list[Mirror] = (await self.wallet_rpc.dl_get_mirrors(DLGetMirrors(launcher_id=store_id))).mirrors
        urls: list[str] = []
        for mirror in mirrors:
            urls += mirror.urls
        urls = [url.rstrip("/") for url in urls]
