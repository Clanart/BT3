### Title
Silent remote-URL rewrite trusts unvalidated `clone_url` from GitHub/GHES API responses, allowing an attacker-controlled server (proxy/MITM) to redirect future pushes and fetches - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl()` automatically rewrites a repository's local git remote URL whenever the GitHub API's `clone_url` for the matched `owner/name` no longer matches the current remote. The only checks performed are that the URL's protocol scheme is unchanged and that the current remote still equals the last-known `cloneURL` cached in the local database — there is **no check that the new hostname matches the account's configured endpoint**. Because this "oracle" (the GitHub/GHES API response) can be manipulated by anyone controlling that server or the network path to it (compromised GHES instance, MITM proxy, DNS hijack), an attacker can cause Desktop to silently repoint the user's `origin` remote to an attacker-controlled git host without any user interaction, corrupting where future commits are pushed and where future code is fetched from.

### Finding Description
The vulnerable logic: [1](#0-0) 

`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)` and feeds the raw API response directly into the URL-rewrite decision: [2](#0-1) 

This refresh path runs automatically and silently every time a repository is selected, added, or has its account context refreshed: [3](#0-2) [4](#0-3) 

The three guards in `updateRemoteUrl` are:
1. `protocolsMatch` — only compares the URL scheme (`https:` vs `https:`), not the host.
2. `remoteUrlUnchanged` — verifies the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL` (proving the user hasn't manually retargeted the remote).
3. `!urlsMatch` — the new `clone_url` differs from the current remote.

None of these validate that the new `clone_url`'s hostname is consistent with the account's endpoint (`repository.gitHubRepository.endpoint`) or with the previous hostname. `urlMatchesRemote`/`parseRemote` only compare the two URLs being diffed against each other, not against a trusted anchor: [5](#0-4) 

If it passes, `gitStore.setRemoteURL` executes `git remote set-url` unconditionally with the attacker-supplied value: [6](#0-5) 

This is the direct structural analog of the reported Oracle bug: a value pulled from an external, attacker-influenceable source (`clone_url` from an API/proxy response) is trusted and used to make a consequential state change (rewriting the remote used for all future pushes/fetches) with an insufficient validation window — exactly the "stale/manipulable oracle value drives a state transition without adequate invariant checks" pattern from the report, mapped onto "a git remote/proxy response" as the attacker-controlled input named in the valid-impact list.

### Impact Explanation
If an attacker controls the git server referenced by an account's endpoint (a malicious/compromised GitHub Enterprise Server, or a network position able to MITM/proxy responses to `repos/{owner}/{name}`), they can return a `clone_url` pointing to an entirely different host while keeping the same scheme. Desktop will then execute `git remote set-url` on the user's real local repository, silently changing where `git push`/`git fetch` operate:
- Future user commits get pushed to the attacker's infrastructure instead of the intended repository (silent corruption of what the user pushes — data exfiltration/loss of provenance).
- Future fetches/pulls bring in attacker-controlled history/content into a repo the user believes is legitimate, which can lead to supply-chain injection into the working tree.

This satisfies the "silent corruption of what the user commits or pushes" and "attacker controls...a git remote/proxy response" criteria in the valid-impact list.

### Likelihood Explanation
The refresh path (`repositoryWithRefreshedGitHubRepository`) runs unconditionally in the background whenever a repository is selected/added or the account context changes, so no explicit user action beyond normal app usage is required once the malicious/compromised endpoint is reachable. The precondition is that the attacker controls (or can intercept traffic to) the GitHub Enterprise endpoint the account is configured against — this is squarely within the "git remote/proxy response" attacker model named as valid, and does not require local/physical access, admin rights, or pre-existing malware. I could not fully verify from the indexed code whether TLS pinning or additional endpoint validation exists elsewhere in the HTTP client layer (`app/src/lib/api.ts` request plumbing) that might mitigate a pure network MITM; a compromised/malicious GHES server scenario, however, is not mitigated by any code path found.

### Recommendation
In `updateRemoteUrl`, additionally require that the new `clone_url`'s hostname matches the hostname of the account's configured `endpoint` (or the previous remote's hostname) before rewriting. Reject silently (or prompt the user) if the hostname changes, treating a hostname change as equivalent to a protocol change in the existing guard logic.

### Proof of Concept
1. User has a GitHub Desktop account configured against a GitHub Enterprise endpoint `https://ghe.attacker-controlled.example` (attacker compromises this server, or performs a MITM/malicious-proxy attack against it).
2. User has a repository cloned from `https://ghe.attacker-controlled.example/acme/widgets` with local `origin` set accordingly; Desktop caches `gitHubRepository.cloneURL` as this value.
3. Attacker (controlling the server/proxy) modifies the JSON response to `GET repos/acme/widgets` so that `clone_url` is `https://evil.example/acme/widgets` (same `https:` protocol, different host).
4. Next time the user selects the repository, adds it, or Desktop performs its periodic account/repo refresh, `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` runs: `protocolsMatch` is true, `remoteUrlUnchanged` is true (remote still equals the cached `cloneURL`), `urlsMatch` is false — so `gitStore.setRemoteURL('origin', 'https://evil.example/acme/widgets')` executes silently, no dialog or confirmation shown to the user.
5. Subsequent `git push`/`git fetch` operations in Desktop silently target `evil.example`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function repositoryMatchesRemote(
  gitHubRepository: GitHubRepository,
  remote: IRemote
): boolean {
  return (
    urlMatchesRemote(gitHubRepository.htmlURL, remote) ||
    urlMatchesRemote(gitHubRepository.cloneURL, remote)
  )
}

export async function setRemoteURL(

  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')

}
