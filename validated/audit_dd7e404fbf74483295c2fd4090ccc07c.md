### Title
Ed448 point decoding accepts non-prime-order torsion points - (File: crypto/ed448/src/point.rs)

### Summary
`Ed448::read_G` accepts attacker-controlled encodings whose decoded points are on the Ed448 curve but outside the prime-order subgroup. The intended torsion check in `Point::is_torsion_free` is vacuous because it computes `P * -1 + P`, which is always the identity. Untrusted torsion points can therefore flow into Schnorr proofs, PedPoP commitments, FROST preprocessing, and other verification paths that assume `C::G` is a prime-order group element.

### Finding Description
`GroupEncoding::from_bytes` recovers an Edwards x-coordinate from the encoded y-coordinate, so it does verify that the decoded coordinates satisfy the curve equation. It then attempts to reject non-prime-order points with `point.is_torsion_free()` [1](#0-0) .

The torsion predicate is incorrect:

```rust
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

For every `P`, this evaluates `(-P) + P`, which is always identity [2](#0-1) . Consequently, the encoding accepts every decodable on-curve point, including Ed448’s non-identity torsion points. `Ciphersuite::read_G` relies on `GroupEncoding::from_bytes` for validity and canonicality, but does not perform an independent subgroup check [3](#0-2) .

This affects public-input paths throughout the in-scope cryptography. For example, `SchnorrSignature::read` deserializes its nonce point through `C::read_G` [4](#0-3) , and verification uses the unmultiplied equation `R + cA - sG == 0` [5](#0-4) . PedPoP likewise reads commitment points through `C::read_G` and treats the first commitment as the public key for a Schnorr proof of knowledge [6](#0-5) [7](#0-6) .

### Impact Explanation
A torsion point is accepted where the `PrimeGroup` abstraction promises a prime-order element. This invalidates proof and verification statements whose soundness requires all public points to be in the prime-order subgroup.

For example, a PedPoP participant can use a non-identity order-4 Ed448 point `T` as its first polynomial commitment. For any selected scalar `s`, the participant can form:

```text
R = sG - cT
```

where `c` is the transcript challenge. The Schnorr verifier accepts:

```text
R + cT - sG = 0
```

without proving knowledge of a scalar `a` satisfying `aG = T`. Such a scalar generally does not exist because `T` is outside the prime-order subgroup. This is therefore a forged proof of knowledge against a semantically invalid commitment accepted by deserialization.

The same invalid points can be placed in signature nonces, DKG commitments, verification shares, and other externally supplied group elements. `Curve::read_G` only rejects identity, not torsion, so even FROST-specific decoding does not restore the missing subgroup invariant [8](#0-7) .

### Likelihood Explanation
Any unprivileged protocol participant or remote input source able to provide an Ed448 point encoding can reach this behavior through `Ed448::read_G`, `Commitments::read`, `SchnorrSignature::read`, `ThresholdKeys::read`, or related APIs. Constructing the input only requires encoding a valid low-order Ed448 point; no private key, malformed curve coordinates, validator privileges, or internal access are needed.

The issue is deterministic rather than probabilistic: the torsion predicate returns true for every point. The main practical limitation is that exploitation requires a protocol path where accepting a non-prime-order commitment or key materially affects verification, rather than merely causing a local abort.

### Recommendation
Implement a real subgroup-membership check for Ed448. Since Ed448 has cofactor 4, multiplication by the prime subgroup order, or an equivalent complete torsion test, should be used; the current formula cannot detect torsion. For example, check `[l]P == identity` using the scalar-field modulus `l`, rather than checking `P - P`.

The test suite should deserialize encodings of all non-identity order-2 and order-4 points and assert rejection. A serialized torsion-point regression test should cover `Ed448::read_G`, `SchnorrSignature::read`, and PedPoP `Commitments::read`.

### Proof of Concept
The defect can be demonstrated directly by constructing an on-curve low-order point, serializing it, and observing that `Point::from_bytes` accepts the encoding:

```rust
use group::{Group, GroupEncoding};
use minimal_ed448::{Point, Scalar};

// Obtain a non-identity point T of order 4, for example by multiplying a
// known full-curve point by the prime-order subgroup order. Point::from_bytes
// must reject it, but currently accepts it.
let t: Point = /* non-identity order-4 Ed448 point */;
let encoding = t.to_bytes();

// Succeeds today because is_torsion_free() computes T - T == identity.
assert!(bool::from(Point::from_bytes(&encoding).is_some()));
```

The root cause is also self-contained in this expression:

```rust
((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
```

`Scalar::ZERO - Scalar::ONE` is `-1`, so this computes `-self + self`, which is always identity for every curve point and therefore cannot distinguish prime-order points from torsion points [2](#0-1) .
