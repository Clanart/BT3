### Title
Unbounded, attacker-influenceable fee rate lets a single high-fee Bitcoin transaction inflate Serai's `median_fee` and burn multisig funds as fees - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
The reported bug class is an owner-controlled fee parameter (`setFee`) whose only protection is a bound — manipulation (or a missing/too-lenient bound) causes funds to be burned as fees. In Serai, the analogous parameter is `fee_per_vbyte` passed to `SignableTransaction::new`. It is set from `median_fee()`, which computes the median feerate over `block.txdata` — transactions any unprivileged party can create — and `SignableTransaction::new` enforces only a *lower* bound (`TooLowFee`), never an upper bound. A crafted high-fee transaction included in a block therefore raises Serai's fee rate arbitrarily, causing the threshold wallet to sign transactions paying an attacker-chosen fee.

### Finding Description
`Bitcoin::median_fee` in `processor/src/networks/bitcoin.rs:388-415` collects `(in_value - out) / tx.vsize()` for every non-coinbase transaction in the most recent block, sorts, and picks `fees[fees.len() / 2]`, clamped only to a minimum of 1 sat/vbyte. `make_signable_transaction` (`processor/src/networks/bitcoin.rs:430-431`) feeds this directly as `fee.0` into `BSignableTransaction::new` (`send.rs:150-256`), which computes `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227). The only fee-rate check is `needed_fee < min_relay` → `TooLowFee` (lines 211-213); there is no `fee_per_vbyte <= MAX` bound anywhere. For blocks with few transactions (common on low-congestion periods and guaranteed on regtest-like conditions), `fees.len() / 2` selects a single transaction's feerate, so one attacker transaction with an enormous fee sets the rate for all Serai outputs scheduled against that block. Even on congested blocks the attacker only needs to control half the transactions.

### Impact Explanation
When the inflated fee still leaves `input_sat >= payment_sat + needed_fee`, Serai's multisig signs a transaction donating `fee_per_vbyte * vbytes` to miners — direct, unbounded theft/burn of vault funds routed through whoever mines the block (the attacker's own high fee is reimbursed through the block reward if they mine or collude with a miner, but even without that, Serai's overpayment is real loss). When the fee exceeds inputs, `NotEnoughFunds`/`NoOutputs` is returned and `make_signable_transaction` returns `Ok(None)` (lines 457-458), so payments are silently dropped — user withdrawals fail or are indefinitely delayed while their inputs' value is consumed as "operating cost". Additionally `fee_per_vbyte * vbytes` can overflow u64 for astronomical feerates, panicking the processor.

### Likelihood Explanation
Reachable by any unprivileged party that can broadcast a Bitcoin transaction — exactly the allowed input class. On blocks containing only the coinbase plus a handful of transactions, a single self-created transaction paying e.g. a 1 BTC fee on a 200-vbyte tx yields `median_fee = 5,000,000 sat/vbyte`. The window repeats every block that Serai schedules against, since `make_signable_transaction` re-reads the latest block each call (with a `TODO2` noting fee caching is unimplemented).

### Recommendation
Cap `fee_per_vbyte` in `SignableTransaction::new` (e.g., reject or clamp above a sanity bound like 1000 sat/vbyte, analogous to the `TooLowFee` check) and/or clamp `median_fee` to a hardcoded maximum in `processor/src/networks/bitcoin.rs:414`, e.g. `Ok(Fee(fee.clamp(1, MAX_REASONABLE_FEE)))`. Prefer a robust estimator (e.g., trimmed mean or mempool estimate) over a median dominated by few transactions.

### Proof of Concept
1. Attacker broadcasts a small transaction paying a 1 BTC fee; it is mined in block B alongside only the coinbase (or as the median of few txs).
2. Serai scheduler calls `make_signable_transaction(block_number_of_B, ...)`; `median_fee` returns `Fee(1_000_000_000 / vsize)` ≈ 5,000,000 sat/vbyte.
3. `SignableTransaction::new` accepts it (no upper bound): `needed_fee = 5e6 * ~200 vbytes = 1e9 sats`.
4. If a queued withdrawal's inputs total ≥ payments + 1e9 sats, the threshold signs a TX burning ~1 BTC to miners; otherwise it returns `NotEnoughFunds` and the plan is dropped each attempt, DoS-ing withdrawals at zero cost to the attacker after B. [1](#0-0) [2](#0-1) [3](#0-2)

  async fn median_fee(&self, block: &Block) -> Result<Fee, NetworkError> {
    let mut fees = vec![];
    if block.txdata.len() > 1 {
      for tx in &block.txdata[1 ..] {
        let mut in_value = 0;
        for input in &tx.input {
          let mut input_tx = input.previous_output.txid.to_raw_hash().to_byte_array();
          input_tx.reverse();
          in_value += self
            .rpc
            .get_transaction(&input_tx)
            .await
            .map_err(|_| NetworkError::ConnectionError)?
            .output[usize::try_from(input.previous_output.vout).unwrap()]
          .value
          .to_sat();
        }
        let out = tx.output.iter().map(|output| output.value.to_sat()).sum::<u64>();
        fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
      }
    }
    fees.sort();
    let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);

    // The DUST constant documentation notes a relay rule practically enforcing a
    // 1000 sat/kilo-vbyte minimum fee.
    Ok(Fee(fee.max(1)))
  }
