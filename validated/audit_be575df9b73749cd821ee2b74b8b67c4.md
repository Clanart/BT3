### Title
Front-runnable instant reward distribution in `BaseRewardPool._provisionReward`/`queueNewRewards` allows an attacker to steal newly harvested WOM/bonus rewards from long-term stakers - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `wombat/WombatStaking.sol`)

### Summary
`BaseRewardPool._provisionReward` adds the entire newly harvested reward to `rewardPerTokenStored` in a single lump-sum step based on `totalStaked()` at the exact moment `queueNewRewards` is called, rather than streaming it over time. Because `MasterMagpie.deposit`/`withdraw` have no cooldown, lock period, or minimum holding duration, an attacker can inflate `totalStaked()` immediately before `WombatStaking._sendRewards` calls `queueNewRewards`, capture a large share of the reward, and withdraw right after, diluting/stealing yield that should have accrued to genuine long-term stakers.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPool.sol` (and identically in `BaseRewardPoolV2.sol`/`mWOMSVBaseRewarder.sol`) updates the global index in one shot: [1](#0-0) 
This means whoever is staked (via `MasterMagpie`) at the instant `queueNewRewards` executes captures reward proportional to their balance relative to `totalStaked()` at that instant — there is no time-weighting of who accrued the reward.

`queueNewRewards` is only gated by `onlyManager`, and it is invoked from `WombatStaking._sendRewards`, itself called from `_toMasterWomAndSendReward`, which runs on every stake/unstake interaction with `MasterWombat` (i.e., on ordinary user harvest-triggering actions): [2](#0-1) [3](#0-2) 
This call is publicly triggerable (e.g., via `WombatPoolHelper.harvest()` / any user deposit/withdraw through the pool helpers) and its exact block is predictable/front-runnable from mempool.

Meanwhile, `MasterMagpie.deposit`/`withdraw` have no cooldown or minimum staking duration — only `whenNotPaused`/`nonReentrant`: [4](#0-3) [5](#0-4) 

To obtain the receipt/staking token needed to deposit into `MasterMagpie`, the attacker deposits the underlying asset into the Wombat pool via `WombatPoolHelper.deposit`/`depositLP`, which mints receipt tokens 1:1 and auto-stakes into `MasterMagpie`: [6](#0-5) [7](#0-6) 

Exploit flow:
1. Attacker observes a pending transaction (or calls it themselves) that will trigger `_toMasterWomAndSendReward` → `_sendRewards` → `queueNewRewards` for a given pool's rewarder.
2. Attacker front-runs by depositing a large amount of the underlying deposit token via `WombatPoolHelper.deposit`, minting receipt tokens auto-staked into `MasterMagpie`. Since `_deposit` in `MasterMagpie` calls `_harvestBaseRewarder` first (via `updateReward` modifier), the attacker's `userRewardPerTokenPaid` is set to the pre-reward `rewardPerTokenStored`.
3. The harvest transaction executes, `_provisionReward` adds the reward to `rewardPerTokenStored`, computed against the now-inflated `totalStaked()` (which includes the attacker's large deposit).
4. Attacker calls `withdraw` on the pool helper, which triggers `MasterMagpie.withdraw` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `getReward`, paying out `earned()` based on the attacker's balance times the index delta, i.e., a share of the just-added reward proportional to the attacker's momentary balance versus total staked — despite having held the position for essentially zero blocks.

Because the increment `rewardPerTokenStored += amountReward / totalStaked()` is computed with the attacker's inflated `totalStaked()` in the denominator, existing long-term stakers' share of the reward shrinks (`s_i * amountReward / (S + A)` instead of `s_i * amountReward / S`), while the attacker captures `A * amountReward / (S + A)`, approaching the entire reward as `A` grows. No modifier, reentrancy guard, or receipt-token accounting prevents this since the design intentionally allows staking/unstaking at any block boundary with instantaneous, non-time-weighted reward crediting.

### Impact Explanation
This is a direct theft-of-unclaimed-yield vulnerability: capital that has not been at risk/staked during the period the reward was earned can capture most or all of a harvested reward batch, diluting or effectively expropriating yield that should accrue to long-term `MasterMagpie` stakers of the affected Wombat pool's receipt token. This matches the Immunefi impact class "theft of unclaimed yield" / "direct theft of user funds."

### Likelihood Explanation
The attack requires only unprivileged actions (deposit/withdraw through public pool-helper and `MasterMagpie` functions) and capital equal to the desired inflated stake for the duration of one transaction bundle (can be obtained via flash loan of the underlying deposit token if a flash-loan source exists for it, or via attacker's own capital held for a single block). The harvest trigger (`_sendRewards`/`queueNewRewards`) is called from routine user interactions and is visible/predictable in the mempool, making front-running straightforward on any chain without private mempools. This is fully repeatable on every harvest event.

### Recommendation
Replace the lump-sum `rewardPerTokenStored` update with a time-weighted/streamed reward distribution model (e.g., Synthetix-style `rewardRate` accrued linearly over a `rewardsDuration`, using `lastUpdateTime`/`periodFinish`), so that reward accrual is proportional to the duration a user's stake was actually deposited rather than their balance at the single moment `queueNewRewards` executes. Alternatively, enforce a minimum staking duration/cooldown in `MasterMagpie.withdraw` for pools with an active rewarder, or snapshot eligibility using a time-weighted average balance.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool`, mock Wombat pool/`WombatStaking`, and a receipt token; register the pool as in `WombatStaking.registerPool`.
2. Seed the pool with a normal long-term staker `Alice` who deposits `100e18` receipt tokens into `MasterMagpie` and waits several blocks.
3. Simulate an upcoming harvest: fund `WombatStaking` with WOM rewards such that the next `harvest()` call will push `1000e18` WOM into `queueNewRewards`.
4. In the block/transaction immediately before harvest, have attacker `Mallory` deposit `100000e18` (obtained via a flash loan of the underlying deposit token or pre-funded) into the Wombat pool via `WombatPoolHelper.deposit`, auto-staking receipt tokens into `MasterMagpie`.
5. Call `WombatPoolHelper.harvest()` (or trigger via deposit/withdraw) so `_sendRewards`/`queueNewRewards` executes, updating `rewardPerTokenStored`.
6. Immediately have `Mallory` call `MasterMagpie.withdraw` for her full receipt-token balance (and repay flash loan if used).
7. Assert `earned(Mallory, WOM)` (or `IBaseRewardPool.allEarned`) is approximately `100000/100100 * 1000e18 ≈ 999e18`, i.e., nearly the entire reward, while `Alice`'s `earned()` for the same reward drops to roughly `100/100100 * 1000e18 ≈ 1e18` instead of the ~`1000e18` she would have gotten pro-rata to her sole long-term stake, demonstrating that claims exceed the accrual period actually held and that yield is stolen from the long-term staker.

        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlmgp) {
            user.available = user.available + _amount;

        }
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)
            if (!_isVlmgp)
                emit Deposit(_account, _stakingToken, _amount);
            else
                emit DepositNotAvailable(_account, _stakingToken, _amount);
    }

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
