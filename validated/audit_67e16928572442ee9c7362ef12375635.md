### Title
Sandwichable swap in `SmartWomConvert.smartConvert`/`_convertFor` due to zero-slippage router call and mis-specified aggregate `_minRec` - ([File: wombat/SmartWomConvert.sol])

### Summary
`SmartWomConvert.sol` performs the WOM→mWOM "buyback" swap through the Wombat router with **no per-swap slippage protection** (`0` passed as `minAmountOut`), relying instead on a post-hoc aggregate check against `_minRec`. When called via `smartConvert`, `_minRec` is hard-coded to the full input amount (`_amountIn`) rather than to the actual expected swap output (which can be queried on-chain via `IWombatRouter.getAmountOut`). This mirrors the reported Alchemix `RevenueHandler` bug class: the "minimum amount out" argument passed to the AMM does not reflect the real expected exchange rate, so it fails to prevent sandwich/front-running extraction of value while the AMM call itself is unprotected.

### Finding Description
`smartConvert` computes a `convertRatio` splitting `_amountIn` between a direct 1:1 mint path and a "buyback" swap path, then calls: [1](#0-0) 

which forwards to `_convertFor` with `_minRec = _amountIn`: [2](#0-1) 

Inside `_convertFor`, the actual swap through the Wombat router is executed with a hard-coded `0` minimum-out argument: [3](#0-2) 

Only after the swap and the direct mint are both executed does the contract check the *aggregate* result against `_minRec`: [4](#0-3) 

Because the buyback path is only triggered when `currentRatio()` (mWOM priced in WOM) is below `buybackThreshold` (i.e., the pool is expected to give a *favorable* rate for buying mWOM with WOM), the design intent is that `amountRec` from the swap should exceed the 1:1 `buybackAmount`. However:

- The router call itself has **zero slippage protection** (`0` passed in), so an attacker can sandwich this specific swap and push the execution price down to the worst point that just barely satisfies the final aggregate check `convertAmount + amountRec >= _amountIn`.
- The final check does not compare against `getAmountOut`/`estimateTotalConversion` (which is exposed as a view function but never used inside `_convertFor`) — it only guarantees no *nominal* loss relative to `_amountIn`, not that the caller receives anything close to the fair/expected favorable rate.
- This is functionally the same root cause as the reported Alchemix bug: the "minimum amount to receive" parameter passed to the AMM (`0`) does not correspond to a proper on-chain price quote, and the substitute aggregate check uses an unrelated reference value (`_amountIn`) instead of the actual expected output, defeating the anti-sandwich purpose of the min-out parameter.

`smartConvert` is documented as intended to be used by `WombatStaking` when routing collected WOM through the buyback/convert flow, and is also externally callable (`convert`/`convertFor` also allow caller-supplied `_minRec`, but `smartConvert` — the path used for automatic/keeper-style buybacks — hard-codes it), so any unprivileged actor who is a Wombat pool participant/searcher can construct or trigger sandwiches around calls into this flow.

### Impact Explanation
Because the intra-swap `minAmountOut` is `0`, an attacker can sandwich the buyback swap to capture the favorable spread that the protocol/its depositors were designed to accumulate through the buyback mechanism, extracting MEV that should have flowed to converted mWOM holders. Since the post-swap check only requires the total to not fall below the plain 1:1 `_amountIn`, the attacker has wide latitude to extract almost the entire expected favorable premium without causing a revert, resulting in a **permanent loss of yield/value** for WOM depositors going through the convert flow, rather than reverted transactions. This is a protocol value-extraction ("theft of unclaimed yield") vulnerability reachable by an ordinary unprivileged wallet/MEV searcher observing the mempool.

### Likelihood Explanation
Likelihood is moderate-to-high: `smartConvert`/`_convertFor` executes a real, sizeable on-chain AMM swap with fully permissive slippage (`0` min out) whenever the buyback threshold condition is met, which occurs naturally during normal peg-restoring cycles. Any searcher monitoring pending transactions calling into this flow (directly or via `WombatStaking`) can sandwich it with standard front-run/back-run bundles, requiring no privileged access or unusual preconditions.

### Recommendation
- Do not hard-code `0` for the Wombat router swap; compute an actual expected output via `IWombatRouter.getAmountOut` (already available and used in `estimateTotalConversion`/`currentRatio`) and pass a properly slippage-tolerant `minAmountOut` to `swapExactTokensForTokens`.
- In `smartConvert`, derive `_minRec` from the expected quoted output (with an acceptable tolerance), not from `_amountIn`, so the post-swap check actually enforces protection against sandwich extraction rather than only guarding against nominal loss.
- Consider adding a caller-supplied slippage parameter to `smartConvert` (with a safe on-chain quote-based default) rather than fully hard-coding values.

### Proof of Concept
1. Observe a pending transaction that triggers `SmartWomConvert.smartConvert(_amountIn, _mode)` (e.g., via `WombatStaking`'s WOM-processing flow) while `currentRatio() < buybackThreshold`, meaning a buyback swap will occur.
2. Front-run with a large WOM→mWOM swap on the same Wombat pool to consume the favorable price, then let the victim's swap execute inside `_convertFor` with `minAmountOut = 0` at the now-worse price.
3. Back-run by swapping mWOM→WOM to restore the pool and capture the price difference as profit.
4. The victim transaction still succeeds because `convertAmount + amountRec >= _amountIn` (the check compares against the input amount, not the pre-sandwich fair quote from `getAmountOut`), so no revert occurs, and the extracted value (the favorable buyback premium) is a permanent loss to depositors and the protocol.     function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
