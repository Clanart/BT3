Confirmed: `CommitMentionLinkFilter` is wired into `SandboxedMarkdown.applyFilters` via `buildCustomMarkDownNodeFilterPipe`, and this pipe runs on markdown rendered from GitHub API content (PR bodies, PR comments, commit messages) inside `app/src/ui/lib/sandboxed-markdown.tsx`. This confirms attacker-controlled reach: any GitHub user who can post a PR description, PR comment, or commit message containing a crafted autolinked URL controls the input to this filter.

### Title
Uncaught TypeError panic in `CommitMentionLinkFilter.getRefFromComparePath` on malformed compare URL - (File: app/src/lib/markdown-filters/commit-mention-link-filter.ts)

### Summary
`getRefFromComparePath` assumes a `compare/<sha1>...<sha2>` URL always yields two elements after splitting on `...`, but never validates the lower bound of `shas.length`, only the upper bound.

### Finding Description
The `comparePath` regex `^compare\/(?<range>.+)$` matches any non-empty string after `compare/`, not just a valid `sha...sha` range [1](#0-0) . `getRefFromComparePath` then does `range.split('...')` and only rejects the case where more than 2 pieces are produced (`shas.length > 2`), but never checks for the `shas.length < 2` case: [2](#0-1) 

If `range` does not contain the `...` delimiter (e.g. `compare/1234567` with no second sha), `range.split('...')` returns a single-element array, so `shas[1]` is `undefined`. The very next line calls `shas[1].indexOf('/')`, which throws `TypeError: Cannot read properties of undefined (reading 'indexOf')`.

The outer `commitMentionUrl` regex used by the tree-walker's `acceptNode` to decide whether an anchor is a commit-mention link does not require the `...` separator either — it only requires `(commit|pull|compare)/` followed by `(\d+/commits/)?` and one hex sequence of 7-40 characters, then a word boundary: [3](#0-2) . So a link like `https://github.com/<owner>/<repo>/compare/1234567` (single hash, no `...secondsha`) both passes the tree-walker acceptance test and reaches `getRefFromComparePath`, since `getRefFromCommitPath` (checked first) requires the path to start with `commit/` and won't match, falling through to the compare-path branch [4](#0-3) .

This filter is invoked from `SandboxedMarkdown.applyFilters`, which runs the full `buildCustomMarkDownNodeFilterPipe` (including `CommitMentionLinkFilter`) over rendered markdown HTML whenever a document loads in the sandboxed markdown iframe: [5](#0-4) . The pipe is built with `CommitMentionLinkFilter` whenever a `repository` is supplied [6](#0-5) , which is the case for PR bodies, PR comments, and commit message rendering throughout the app.

### Impact Explanation
An unhandled exception thrown inside `applyFilters` (an `async` function invoked from `onDocumentDOMContentLoaded` without a try/catch) is analogous to the btcd panic: attacker-controlled content (a GitHub API object — PR body/comment/commit message text containing a plain URL that gets autolinked by `marked`) causes Desktop's renderer-side markdown rendering pipeline to throw. Depending on how the promise rejection propagates, this can manifest as a broken/incomplete render (remaining filters like `VideoTagFilter`/`VideoLinkFilter` never execute, and any downstream node mutations `docMutated`/`refreshHeight` calls for later filters are skipped) or an unhandled promise rejection surfacing in the renderer process. This is a denial-of-view / rendering-corruption bug in a security-relevant sanitization pipeline (the filter pipe runs after DOMPurify and is part of link normalization), not remote code execution, but it does allow any external, unprivileged GitHub user (PR author or issue/PR commenter) to reliably break the rendering path for that PR/commit/comment.

### Likelihood Explanation
High likelihood of triggering: `marked` autolinks bare URLs into `<a>` tags whose `href` equals `innerText`, which is exactly the condition the tree-walker checks (`el.href !== el.innerText`) at [7](#0-6) . A comment body containing a bare URL such as `https://github.com/owner/repo/compare/abcdef1` (a single 7+ character hex string, no `...` range) is trivial for any GitHub user to post, requires no special privileges, and will be rendered by Desktop the next time a maintainer or contributor views that PR/commit/comment in the app.

### Recommendation
In `getRefFromComparePath`, validate that `shas.length === 2` (reject when `< 2` as well as `> 2`) before indexing `shas[1]`, mirroring the exact fix pattern from the btcd commit: bound the index operation by the actually available size rather than assuming a fixed shape.

### Proof of Concept
1. As any GitHub user, post a PR comment (or PR/commit description) containing the bare URL: `https://github.com/<owner>/<repo>/compare/1234567` (no `...second-sha`).
2. In GitHub Desktop, open that PR/commit view so the comment/body is rendered through `SandboxedMarkdown`.
3. `marked` autolinks the bare URL into `<a href="...">...</a>` with `href === innerText`; the `CommitMentionLinkFilter` tree-walker accepts the node because `commitMentionUrl` matches (single hex sha after `compare/` satisfies the regex).
4. `filter()` calls `getRefFromCommitPath` (no match, path doesn't start with `commit/`) then `getRefFromComparePath`, which computes `shas = ['1234567']`, then executes `shas[1].indexOf('/')` on `undefined`, throwing `TypeError` and aborting the remaining filter pipeline for that render pass [8](#0-7) .
