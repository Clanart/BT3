## Title
Unchecked zero `GasTarget` governance parameter causes division-by-zero panic in KIP-71 base fee calculation - (File: `params/kip71_config.go`)

## Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without ever checking it for zero, unlike the adjacent `BaseFeeDenominator`, which explicitly guards against a zero value. Because the governance parameter validation pipeline for `Kip71GasTarget` uses a no-op format checker, a governance vote can set `GasTarget = 0` and pass all validation, causing a runtime panic the moment a block with any gas usage is verified or produced.

## Finding Description
In `NextMagmaBlockBaseFee`, the developer explicitly protects the `BaseFeeDenominator` divisor from being zero: [1](#0-0) 

But no equivalent protection exists for `gasTarget`, which is used directly as a divisor twice, once in the "gas used above target" branch and once in the "gas used below target" branch: [2](#0-1) 

If `gasTarget == 0` and `parentGasUsed == 0`, the function takes the early-return branch (`parentGasUsed == gasTarget`) and is safe. But as soon as any block uses gas (`parentGasUsed > 0 = gasTarget`), execution falls into the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `big.Int.Div`.

The root cause is that the governance parameter `Kip71GasTarget` accepts any `uint64` value, including `0`, with no format validation: [3](#0-2) 

and the header-vote consistency checker (`checkConsistency`) explicitly lists `gov.Kip71GasTarget` among parameters requiring no additional consistency checks beyond the format checker: [4](#0-3) 

This is confirmed by the test suite, where the only invalid `Kip71GasTarget` votes tested are those with a wrong Go type (`int` instead of `uint64`, or `bool`), never a value-based rejection of zero: [5](#0-4) 

`NextMagmaBlockBaseFee` is invoked during block header verification (`VerifyMagmaHeader`), consensus header validation, and fee-history / block-assembly base fee computation: [6](#0-5) [7](#0-6) 

## Impact Explanation
Once a governance vote sets `kip71.gastarget = 0` and the vote is finalized (passes `NewVoteData`'s format check and `checkConsistency`, both of which accept it unconditionally), every node — including the block proposer computing the next header's `BaseFee` and every validator/full node verifying that header — will panic inside `big.Int.Div` as soon as a block with `GasUsed > 0` is produced after the parameter takes effect. This crashes the consensus-critical code path on all nodes simultaneously (identical deterministic panic), effectively halting the chain. This is a severe availability/consensus-liveness issue reachable purely through the standard on-chain governance parameter mechanism, with no code deployment or off-chain compromise needed.

## Likelihood Explanation
The only prerequisite is that a governance vote for `kip71.gastarget = 0` is submitted and passes the epoch voting threshold — a governance action explicitly listed as in-scope ("governance parameters"). There is no format or consistency check preventing this value, and the vote-testing code in this very repo evidences that only type mismatches are rejected for this parameter, not zero values. Because `GasTarget` is a "gauge parameter" that a governing node/council can plausibly set for various tuning reasons, an accidental or malicious zero setting is realistically reachable, not merely theoretical.

## Recommendation
Add the same defensive guard used for `BaseFeeDenominator` to `GasTarget` in `NextMagmaBlockBaseFee`, e.g., treat `gasTarget == 0` as an invalid/degenerate case (fall back to a safe default, or return `lowerBoundBaseFee`/`upperBoundBaseFee` deterministically) before performing any division. Additionally, add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` at vote-submission time, consistent with how `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` are cross-validated in `checkConsistency`.

## Proof of Concept
1. Submit and pass a governance vote (or genesis/hardfork configuration) setting `kip71.gastarget = 0` — this passes `NewVoteData` (no format check) and `checkConsistency` (explicitly falls through to `return nil` for `Kip71GasTarget`).
2. Once the parameter is active, any block whose `GasUsed > 0` (virtually guaranteed) causes:
   - the block proposer to panic while computing `header.BaseFee` for the next block via `NextMagmaBlockBaseFee`, or
   - every validating node to panic in `BlockValidator.validateHeader` → `VerifyMagmaHeader` → `NextMagmaBlockBaseFee` when dividing `x.Div(x, new(big.Int).SetUint64(0))`.
3. The panic occurs deterministically on all nodes, halting block production/verification network-wide.
