### Title
DataLayer mirror URLs allow unvalidated outbound SSRF via `http_download` - (File: `chia/data_layer/download_data.py`)

### Summary
Chia's DataLayer subsystem lets any owner of a DataLayer singleton publish "mirror" URLs on-chain via a `create_mirror_puzzle()` coin whose memos encode `[launcher_id, url1, url2, ...]`. Any node tracking that `launcher_id` picks up the mirror coin, stores the attacker-chosen URLs without any validation, and later the DataLayer sync loop performs raw outbound HTTP GET requests to those URLs — the same bug class as the Recurly `Resource.get` SSRF (CWE-918): a resource identifier fully controlled by an untrusted, remote party is dereferenced by the server with no scheme/host allow-listing.

### Finding Description
A mirror coin is created via `DataLayerWallet.create_new_mirror()`, which puts `[launcher_id, *urls]` directly into `CreateCoin` memos with no URL validation: [1](#0-0) 

This is exposed to any local RPC caller (and effectively any chain participant who owns/creates a DL singleton) through `dl_new_mirror`: [2](#0-1) 

When any node that tracks the corresponding `launcher_id` (e.g. another DL wallet subscribed to the same store, or simply an interested party) observes the mirror coin on-chain, `DataLayerWallet.coin_added()` parses out the launcher id and URL list and stores them **without validating scheme or host**: [3](#0-2) 

The DataLayer service (`DataLayer.update_subscriptions_from_wallet()`) then pulls these attacker-supplied URLs from the wallet mirror table straight into the local subscription table with no filtering: [4](#0-3) 

During the periodic sync loop, `fetch_and_validate()` iterates these server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs a bare `aiohttp` GET to `server_info.url + "/" + filename` with no scheme restriction, no private/loopback IP blocking, and no allow-list: [5](#0-4) [6](#0-5) 

The project's own internal documentation explicitly flags mirror/plugin URLs as an "external trust input," confirming this is a recognized, still-open trust boundary rather than a hardened one: [7](#0-6) 

### Impact Explanation
Any chain participant who creates (or already owns) a DataLayer singleton can publish a mirror with a URL pointing at internal-only services (e.g. `http://127.0.0.1:<port>/...`, cloud metadata endpoints such as `http://169.254.169.254/...`, or other addresses only reachable from the victim node's network) for a nominal on-chain fee. Any other Chia node that becomes a DL wallet peer for/tracks that launcher id (which happens automatically for any node subscribing to or co-owning the store) will have its DataLayer service issue outbound HTTP requests to that attacker-chosen destination on a recurring background schedule (`periodically_manage_data()`), with no operator interaction required. This is a full server-side request forgery: it can be used to probe/scan a victim's internal network topology and services, hit local-only HTTP APIs/RPC endpoints reachable from the DataLayer process, or attempt to reach cloud instance-metadata services to extract credentials. Response/error timing (visible via mirror ban/backoff state exposed through `dl_get_mirrors`/`get_subscriptions` RPCs) provides an oracle for whether targeted internal hosts/ports are reachable, which is itself sensitive network-reconnaissance information leakage.

### Likelihood Explanation
The bar to trigger this is low: creating/owning a DataLayer singleton and publishing a mirror coin (`chia data add_mirror` / `dl_new_mirror`) is a normal, unprivileged wallet operation costing only a small on-chain transaction fee. No special permissions on the target node are required — the target only needs to be running the DataLayer service and syncing/tracking the affected store, which is the expected mode of operation for DL participants and mirror consumers.

### Recommendation
- Validate mirror/subscription URLs before persisting or dereferencing them: enforce an `http`/`https` scheme allow-list, and reject or require explicit opt-in for loopback, link-local (including `169.254.169.254`), and RFC1918 private-network destinations in `DataLayerWallet.coin_added()` and/or `DataStore.update_subscriptions_from_wallet()`.
- Apply the same validation in `http_download()`/`download_file()` in `chia/data_layer/download_data.py` as a defense-in-depth check immediately before issuing the request, independent of how the URL entered the subscription table.
- Consider making DNS resolution SSRF-safe (resolve-then-validate, disable redirects to disallowed hosts) since hostname-based allow/deny lists can be bypassed via DNS rebinding.
- Provide a config option to require manual approval of URLs derived from on-chain mirror data (`from_wallet=1` subscriptions) rather than auto-trusting them, keeping manually configured `chia data subscribe -u` URLs on a separate, explicitly-trusted path.

### Proof of Concept
1. Attacker creates a DataLayer store and gets it into a state where a victim node tracks/subscribes to its `launcher_id` (e.g., publish it and have the victim add it as a subscription, which is the normal DL usage pattern for both DL clients and any node co-owning/watching the singleton).
2. Attacker calls `dl_new_mirror` (or `chia data add_mirror -i <store_id> -u http://169.254.169.254/latest/meta-data/ -a 1`) to publish a mirror coin whose memos are `[launcher_id, b"http://169.254.169.254/latest/meta-data/"]`, per `chia/data_layer/data_layer_wallet.py:687-703`.
3. Victim's `DataLayerWallet.coin_added()` (`chia/data_layer/data_layer_wallet.py:775-799`) observes the mirror coin, decodes the URL, and stores it via `dl_store.add_mirror()` with no host/scheme check.
4. Victim's `DataLayer.update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`) copies the URL into the local `subscriptions` table.
5. On the next `periodically_manage_data()` cycle, `fetch_and_validate()` (`chia/data_layer/data_layer.py:642-706`) selects this server and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298-319`), which issues `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` — an outbound request to the attacker-chosen internal/metadata address originating from the victim's node.
6. The attacker observes success/failure/backoff behavior via `chia data get_subscriptions` / `dl_get_mirrors` on the victim (or via a listener they control at a routable target instead) to confirm reachability, demonstrating the SSRF oracle.

        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:

                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
