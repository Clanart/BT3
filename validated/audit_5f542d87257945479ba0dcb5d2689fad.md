### Title
`ReceivedOutput::read` deserializes an offset/`TxOut`/`OutPoint` triple without verifying the output is actually spendable under the claimed offset key — forged "received" outputs are accepted as spendable (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external finding is a **missing existence/validity check on a retrieved object**: `refundExpiredSubmitClaimRequest` looked up a struct in a mapping, never verified the entry existed (all fields zero), skipped amount binding (hardcoded `bondsNeededToStartDispute` instead of `submitClaimRequest.bond`), and acted on it — burning funds for a claim that was never real.

The analog in Serai is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`. `ReceivedOutput` is documented as "A spendable output" (`wallet/mod.rs:88`), yet its only semantic guarantee — that `output.script_pubkey == p2tr(key + offset·G)` — is established exclusively inside `Scanner::scan_transaction` (`wallet/mod.rs:199-214`), which only constructs `ReceivedOutput`s for script_pubkeys it registered. `ReceivedOutput::read` accepts arbitrary bytes and reconstructs the struct with **no binding check whatsoever**: the `offset` is never verified against `output.script_pubkey`, and the `outpoint` is never verified against anything. Any consumer that trusts a deserialized `ReceivedOutput` as spendable-by-the-multisig is trusting an attacker-forgeable claim, exactly as `HATArbitrator` trusted the zero-valued `SubmitClaimRequest`.

### Finding Description
```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output = TxOut::consensus_decode(&mut buf_r)...;
      outpoint = OutPoint::consensus_decode(&mut buf_r)...;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

Weaknesses mirroring the report:

1. **No existence/validity check on the retrieved object.** `scan_transaction` constructs `ReceivedOutput` only when `self.scripts.get(&output.script_pubkey)` succeeds, i.e., only when the script was derived from `key + offset·G` with an even-parity tweak (`register_offset`, `wallet/mod.rs:180-196`). `read` drops this invariant entirely — it will happily produce a `ReceivedOutput` whose `offset` has no relationship to `output.script_pubkey`, or whose `outpoint` references a nonexistent UTXO.
2. **Fields are individually well-formed but semantically unbound** — the equivalent of the Solidity bug's zeroed-but-accepted struct. Each of `read_F`, `TxOut::consensus_decode`, `OutPoint::consensus_decode` passes, yet the combination is meaningless.
3. **The security-critical value is not recomputed.** Where the fix was to use `submitClaimRequest.bond` and validate `submitter != 0`, the fix here is to recompute `p2tr_script_buf(key + offset·G)` against `output.script_pubkey` — which `read` cannot do because it doesn't take the key, and no caller-facing API re-derives it. The type's own docstring ("A spendable output") asserts a property deserialization never establishes.
4. **Parity is never checked.** `register_offset` guarantees an even (valid P2TR) tweaked key; `read` accepts offsets yielding odd keys, which `p2tr_script_buf` rejects (`wallet/mod.rs:80-86`) — i.e., provably unspendable.

This mirrors the prompt's explicit reachability allowance for untrusted bytes fed to `ReceivedOutput::read`.

### Impact Explanation
A deserialized `ReceivedOutput` is treated downstream as a spendable deposit: it carries `value()`/`outpoint()`/`offset()` accessors, is fed to `SignableTransaction::new` / the scheduler (see `processor/src/tests/wallet.rs:86-105` building payments from scanned outputs), and its offset is applied to the threshold key for signing. An attacker who can supply serialized `ReceivedOutput` bytes to a component (relay, resync, DB restoration, peer message) can cause:

- **Funds reported received that are not spendable** (an accepted impact class): an output with a large `value`, a real-looking `TxOut`, and an offset that does not match the script_pubkey — or matches a key the attacker controls — is indistinguishable from a genuine deposit. The multisig credits value it can never sign for, or spends an outpoint that doesn't exist, stalling/breaking the signing plan.
- Worse, if any path uses `offset` for key derivation without re-checking the script (`key + offset·G` is the signing target), an attacker-chosen offset steers which key is expected to sign — a confusion vector over the threshold key.

### Likelihood Explanation
Requires a path where `ReceivedOutput::read` consumes attacker-controlled bytes. `read`/`serialize` are public, std-gated APIs intended for persistence/transport (used in tests at `networks/bitcoin/tests/wallet.rs:73`); any storage or replication path (DB rows, processor state sync, rescan data) that round-trips these bytes is exposed, and the prompt enumerates this reader as an intended untrusted-input surface. Within `scan_transaction`-only flows it is unreachable, so the exploitability hinges on the integrator/processor path — hence Medium rather than High.

### Recommendation
Either remove the public `read`/`serialize` API from `ReceivedOutput` (forcing construction through `Scanner` which enforces the binding), or make `read` take the scanning key and verify `p2tr_script_buf(key + GENERATOR·offset) == Some(output.script_pubkey)`, rejecting on mismatch — the direct analog of reverting when `submitter == address(0)`/`bond == 0` and paying out `submitClaimRequest.bond` instead of the hardcoded constant. At minimum, document that a deserialized `ReceivedOutput` is unverified and must be re-validated against the scanner before being treated as spendable.

### Proof of Concept
```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, Transaction, TxOut, Txid,
  hashes::Hash,
};
use bitcoin_serai::wallet::{ReceivedOutput, Scanner};
use k256::ProjectivePoint;
use serai_client::primitives::... // Scalar via Secp256k1 ciphersuite
use std::io::Write;

// Build byte stream: arbitrary offset (attacker's choice), a TxOut paying to a
// script_pubkey NEVER registered with the Scanner, and a fabricated outpoint.
let mut buf = vec![];

// offset: e.g. a scalar the attacker knows the discrete log of against the
// multisig key is irrelevant — the point is it doesn't match the script.
buf.extend_from_slice(&attacker_offset.to_bytes()); // Secp256k1::F repr

let forged_txout = TxOut {
  value: Amount::from_sat(1_000_000_000),               // "received" 10 BTC
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
      TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly)),
};
buf.extend_from_slice(&bitcoin::consensus::serialize(&forged_txout));

let fake_outpoint = OutPoint { txid: Txid::all_zeros(), vout: 0 };
buf.extend_from_slice(&bitcoin::consensus::serialize(&fake_outpoint));

// Accepted without error:
let output = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(output.value(), 1_000_000_000);      // credits 10 BTC
// Yet Scanner::new(multisig_key).unwrap().scan_transaction(...) over a real tx
// with this script_pubkey would return [] — the output is not spendable by the
// multisig, but nothing in `read` distinguishes it from a genuine deposit.
```

The forged object passes every accessor (`value`, `outpoint`, `offset`) exactly as the zeroed `SubmitClaimRequest` passed the timestamp check — individually-valid fields, semantically invalid object, accepted.
