### Title
Shared `BalanceHandler` instance across recursive/nested precompile calls causes StateDB/bank balance desync - ([File: precompiles/common/balance_handler.go])

### Summary
The reported `_reCalFs` bug is a case where a stateful helper (`balanceOf`/`prevEventsLen`-style bookkeeping) is read using a stale or shared reference point instead of a value that is correctly scoped to the current computation, corrupting downstream accounting. The Cosmos EVM analog is `BalanceHandler.prevEventsLen`, which is used as the "high-water mark" that separates events already applied to the EVM `StateDB` from new bank events produced by the current precompile call. When a precompile call recursively/nestedly triggers another precompile call (contract → precompile A → EVM call → precompile A/B again), and both calls end up operating on a `BalanceHandler` instance whose `prevEventsLen` gets overwritten by the inner call, `AfterBalanceChange` no longer processes the correct slice of `ctx.EventManager().Events()` for each call. This causes bank-emitted `coin_spent`/`coin_received`/precisebank fractional-balance events to be mis-attributed: either double-applied to the `StateDB` or dropped, producing balances in `StateDB` that no longer match the real `x/bank` balances.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` as `prevEventsLen`, and `AfterBalanceChange` only looks at `events[bh.prevEventsLen:]` to translate bank events into `StateDB.AddBalance`/`SubBalance` calls:

The repository itself contains an integration test explicitly documenting this as a known bug class: recursive precompile calls sharing a single `BalanceHandler` instance overwrite `prevEventsLen`, leading to desync between the native bank keeper and the EVM `StateDB`: [3](#0-2) 

The debug precompile in the test harness reproduces this by calling `p.GetBalanceHandler()` directly on the precompile struct (a shared/singleton-style accessor) rather than creating a fresh, call-scoped handler for each nested invocation, unlike the "proper" path in `precompiles/common/precompile.go` `runNativeAction`, which does call `p.BalanceHandlerFactory.NewBalanceHandler()` per call: [4](#0-3) [5](#0-4) 

Even where `NewBalanceHandler()` is used correctly, the root invariant being relied upon — "the event slice recorded at `BeforeBalanceChange` for this call correctly bounds the events belonging to this call only" — is fragile in any code path where a precompile calls back into the EVM which in turn re-enters a precompile (nested calls), because `ctx.EventManager()` is a single, ever-growing event log shared across the whole transaction. If any precompile in the call chain does not follow the strict "create-new-handler-per-call, snapshot-length, process-only-new-slice" discipline (as the debug precompile demonstrates), the length markers get corrupted and the wrong event range gets translated into `StateDB.AddBalance`/`SubBalance`.

### Impact Explanation
`StateDB` balances are the values ultimately committed back to `x/bank`/`x/precisebank` via `StateDB.Commit()` (`x/vm/statedb/statedb.go` `commitWithCtx`, `s.keeper.SetAccount`). If `AfterBalanceChange` double-applies a `coin_received` event (because `prevEventsLen` was rolled back or not advanced due to nested-call overwrite) it fabricates ERC20/native EVM balance for an account beyond what was actually credited in `x/bank`, i.e. unauthorized duplication of spendable value in the EVM balance view — a Critical accounting-corruption impact matching the allowed impact gate (irreversible accounting corruption / unauthorized duplication of spendable balances). Conversely, if events are skipped, funds effectively vanish from the EVM-visible balance while still present in `x/bank`, which is a freezing/loss-of-access impact for the affected balance in EVM-facing tooling (wallets, DeFi contracts reading `balanceOf`/`address.balance`).

### Likelihood Explanation
Exploitability depends on being able to reach a genuinely nested precompile-call chain from ordinary (unprivileged) contract execution, where the intermediate call also invokes a precompile that performs bank balance-changing operations (e.g., a contract calling `distribution`/`staking`/`bank`/`werc20` precompiles that in turn make EVM calls back into precompiles, or `ERC-20 <-> IBC` conversion flows chaining through multiple precompile-mediated balance updates). The existence of a dedicated regression test (`TestRecursivePrecompileCallsWithDebugPrecompile`) in the repo strongly suggests this scenario is already known and actively guarded against/being tracked by the Cosmos EVM team, but I could not confirm from the available index whether the production precompiles (`staking`, `distribution`, `erc20`, `werc20`, `ics20`) can currently be chained in a way that reproduces the corrupted `prevEventsLen` bug outside of the debug-only precompile, since `debug.Precompile` deliberately bypasses `runNativeAction`'s per-call `NewBalanceHandler()` factory pattern used by all real precompiles.

### Recommendation
- Ensure every precompile implementation obtains its `BalanceHandler` exclusively via a freshly-constructed, call-scoped instance (as `runNativeAction` already does via `BalanceHandlerFactory.NewBalanceHandler()`), and never via a method that returns a handler stored on the (potentially shared) `Precompile` struct.
- Add an invariant check/assertion that `prevEventsLen` recorded in `BeforeBalanceChange` is monotonic and matches the exact call frame, e.g. by snapshotting and restoring it around nested precompile invocations, or by using a call-stack of markers instead of a single scalar.
- Extend `TestRecursivePrecompileCallsWithDebugPrecompile`-style regression coverage to all production precompiles that can be reached in a nested-call chain (staking, distribution, erc20/werc20, ics20), verifying `StateDB` balances always equal `x/bank`/`x/precisebank` balances after such flows.
