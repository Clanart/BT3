Based on the investigation, the strongest reachable analog to the reported bug class is in the Giga OCC EVM execution path in `app/app.go`, where receipt-store failure is handled inconsistently with the standard (V2) EVM path.

### Title
Giga executor commits EVM state changes (fee debit/execution effects) even when receipt persistence fails, unlike the standard V2 path which reverts on the same failure - (File: app/app.go)

### Summary
`executeEVMTxWithGigaExecutor` pre-charges gas and applies EVM execution effects via `stateDB.Finalize()` *before* attempting to persist the transaction's receipt. If `WriteReceipt` (or `Finalize`) fails, the function returns an `abci.ExecTxResult{Code: 1, ...}` paired with a `nil` Go `error`, rather than propagating a real error the way the standard V2 msg-server path does.

### Finding Description
In the standard EVM transaction path (`x/evm/keeper/msg_server.go`), a receipt-write failure sets the named return `err = rerr`, which is a genuine Go error returned out of `EVMTransaction`: [1](#0-0) . Cosmos SDK's per-message branched store semantics revert all state written during that message when a real error is returned, so a receipt-write failure safely undoes the balance/state changes made by `stateDB.Finalize()`.

The Giga executor path in `executeEVMTxWithGigaExecutor` does not follow this pattern. It first pre-charges the gas fee directly against the sender's balance in the live `stateDB`: [2](#0-1) . It then executes the transaction and calls `stateDB.Finalize()`, which "captures surplus (fee deduction + execution balance changes)" — i.e., applies the balance/state mutations: [3](#0-2) . Only after these mutations are applied does it attempt `WriteReceipt`; on failure it returns:

```go
receipt, rerr := app.GigaEvmKeeper.WriteReceipt(ctx, stateDB, evmMsg, uint32(ethTx.Type()), ethTx.Hash(), execResult.UsedGas, vmError, false)
if rerr != nil {
    return &abci.ExecTxResult{
        Code: 1,
        Log:  fmt.Sprintf("failed to write receipt: %v", rerr),
    }, nil
}
``` [4](#0-3) 

Note the second return value is `nil` — a well-formed Go error is never produced. This result flows back through the OCC batch scheduler and is merged into the block's final `ExecTxResult` list purely by copying the `Code`/`Log` fields: [5](#0-4) . Whether this per-tx branch is discarded depends on whether the OCC scheduler's commit logic inspects the ABCI `Code` field or only a genuine Go `error` returned from the task function; the code observed here returns `nil` as the error, which is the same shape used for a normal *successful* result elsewhere in this function (e.g., the `Finalize` failure case at lines 1973-1978 uses the identical `Code:1, err:nil` pattern). This is the opposite convention from the V2 path, where any receipt/finalize failure is surfaced as a genuine `error` to trigger the standard atomic-tx revert.

This is structurally analogous to the reported bug: a side-channel persistence step (Redis `PENDING_TRANSACTIONS` entry / here, the EVM receipt store) can fail independently of the primary state-changing action (the ETH-side unlock / here, the sender's fee debit and EVM execution effects on `stateDB`), and the code path that handles that failure does not guarantee the primary action is reverted — it only marks the externally-visible result as failed (`Code: 1`) while the underlying balance mutation may still be committed to the giga store.

### Impact Explanation
If the per-tx OCC branch is committed regardless of `Code`, this results in gas fees being debited (and/or EVM state/balance changes from execution) with no receipt ever recorded for the transaction. From the chain's/user's perspective, the transaction "did not happen" (no receipt is retrievable, callers/relayers relying on receipts to confirm execution will see nothing), yet the sender's funds were moved — a silent fund-loss condition for the sender, and a state-corruption risk (executed EVM effects untethered to any receipt/log/bloom entry, breaking receipt-log invariants relied on by RPC clients and downstream systems). This matches the "fund loss / permanent freezing due to state accounted differently than a receipt/record implies" pattern in the external report.

### Likelihood Explanation
Triggering `WriteReceipt` or `Finalize` failure requires an underlying store/backend failure (e.g., the litt receipt store hitting a write error), which is a legitimate operational condition documented elsewhere in the codebase as something the system must guard against (see the receipt store's own internal tests asserting writes must not silently advance past a failed block: [6](#0-5) ). A transaction sender cannot directly force this failure, but it is a realistic operational fault (disk/backend issue) reachable without any privileged access, and the Giga path is the default hot path for ordinary EVM transactions.

### Recommendation
Make the Giga executor's failure handling for `Finalize`/`WriteReceipt` consistent with the V2 path: return a genuine Go `error` (not `nil`) so the OCC scheduler/branched-store commit logic discards this transaction's `stateDB` mutations exactly as the standard msg-server path does. Alternatively, verify explicitly (with a dedicated test) that the OCC scheduler discards a task's writes whenever `ExecTxResult.Code != 0`, and if it does not, add that check before merging `evmBatchResult` into the committed block state.

### Proof of Concept
Not independently reproducible from static analysis alone — verifying actual fund loss requires confirming, in `sei-cosmos/tasks` scheduler code, whether a per-tx branch commit is gated on the returned Go `error` only or also on `ExecTxResult.Code`. This exact point could not be fully confirmed within the available search budget; if the scheduler commits per-tx writes whenever the returned error is `nil` (regardless of `Code`), the flow above (gas pre-charge at `app/app.go:1934` → `stateDB.Finalize()` at `app/app.go:1972` → `WriteReceipt` failure at `app/app.go:2003-2009` returning `nil` error) directly produces the fund-loss condition described.

// TestWriteFailureHoldsTheHeadAgainstAQueuedBlock covers what a failed write owes the blocks queued
// behind it: applying one would publish a head above the block that never landed. The follower is
// queued while the failing commit is held, since SetReceipts refuses blocks once the failure shows.
func TestWriteFailureHoldsTheHeadAgainstAQueuedBlock(t *testing.T) {
	s, closeStore := setupLittCtxStore(t)
	defer closeStore()

	addr := common.HexToAddress("0xfa11")
	topic := common.HexToHash("0xfa12")

	index := &failingIndex{
		KeyValueDB: s.index,
		entered:    make(chan struct{}),
		release:    make(chan struct{}),
	}
	s.index = index

	// Block 1 lands, so there is a real head for the failure to hold.
	writeOneReceipt(t, s, 1, addr, topic)
	requireReceiptVersion(t, s, 1)

	// Block 2 reaches its commit and stops there, still holding the writer.
	index.failing.Store(true)
	writeOneReceipt(t, s, 2, addr, topic)
	<-index.entered

	// Block 3 would commit cleanly and carry a marker naming it the head. Queued now, while block 2
	// is mid-commit, it is past the refusal in SetReceipts and only the writer can hold it back.
	index.failing.Store(false)
	writeOneReceipt(t, s, 3, addr, topic)

	close(index.release)

	// Close drains, so the writer has decided about block 3 by the time this returns.
	require.ErrorIs(t, s.Close(), errIndexCommit)
	require.Equal(t, int64(1), s.LatestVersion(),
		"the head must not move past a block whose receipts were never written")
}
