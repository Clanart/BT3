This is the exact analog: `_fillSameChain` in `IntrinsicIntents.sol` has the same "both zero" gap the CREAM report describes.

### Title
Zero-amount fill on an unset output pair lets a solver mark a same-chain order fully filled and drain escrow without paying the beneficiary - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` skips an output leg whenever `remaining == 0 || solverAmount == 0`, mirroring the CREAM bug pattern where two independent amounts (here: `remaining` computed from order state, and attacker-supplied `solverAmount`) are checked with an OR instead of being jointly validated. `remaining == 0` is meant to represent "already fully filled," but it is reached identically when `totalRequired == 0` from the start (a zero-amount output leg in the order), which is never rejected on `placeOrder`. Combined with `solverAmount == 0`, this lets a solver skip an output entirely — paying nothing — while `isFullyFilled` stays true, and the input escrow for that leg is still released to the solver in full.

### Finding Description
`_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:66-124`) processes each output leg:
```solidity
uint256 totalRequired = order.output.assets[i].amount;
uint256 solverAmount = options.outputs[i].amount;
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
if (remaining == 0 || solverAmount == 0) {
    if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
    continue;
}
``` [1](#0-0) 

If `totalRequired == 0` (a leg the user's order lists with a zero output amount, `alreadyFilled` also 0, so `remaining == 0`) and the solver supplies `solverAmount == 0` for that leg, the branch is taken, the leg is skipped, and — critically — `isFullyFilled` is **not** set to `false`, because the guard `if (solverAmount == 0 && remaining > 0)` requires `remaining > 0`. The loop then computes the escrow release for that leg:
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
}
``` [2](#0-1) 
Since `amountFilled` (still 0) equals `totalRequired` (0), this branch is taken and the **entire escrowed input balance for that token** is queued for release to the solver via `_withdraw`, even though the solver paid the beneficiary nothing for that leg. There is no check in `placeOrder`/order validation elsewhere that a `TokenInfo.amount` in `order.output.assets` must be non-zero — unlike the cross-chain path (`ExtrinsicIntents.sol`), which explicitly reverts with `InvalidInput` when an input amount is zero (`evm/src/apps/IntentGatewayV2.sol:283`), the same-chain output leg has no equivalent floor. `TokenInfo` used for `output.assets` is fully attacker/user chosen at `placeOrder` time.

### Impact Explanation
This is unauthorized fund extraction from bridge escrow: a solver can construct/collude on an order with a zero-amount output leg (alongside legitimate legs), submit `solverAmount = 0` for that leg, and receive the escrowed input tokens for that leg for free while the order is marked `OrderFilled` (`isFullyFilled = true`), finalizing `_filled[commitment]` and releasing associated transaction fees. This is a direct loss-of-funds / wrong-beneficiary-and-amount scenario matching the bounty's "stealing or loss of funds" and "logic attacks" categories, reachable by any unprivileged user/solver through the public `fillOrder` entrypoint with no relayer, prover, or admin involvement.

### Likelihood Explanation
Likelihood is high for a self-interested solver: the order itself is placed by a user calling public `placeOrder`, and nothing prevents a colluding user/solver pair (or a solver front-running with its own order) from including a `TokenInfo{amount: 0}` leg. The exploit requires only ordinary calls to `placeOrder` and `fillOrder` with attacker-chosen `FillOptions.outputs[i].amount = 0`, no proof forgery or governance access needed.

### Recommendation
Reject zero-amount output legs at order-placement time (mirroring the `if (order.inputs[i].amount == 0) revert InvalidInput();` check already used for cross-chain inputs), and/or tighten the same-chain skip condition so it cannot be satisfied by a still-zero `totalRequired`/`amountFilled` pair, e.g.:
```solidity
if (totalRequired == 0) revert InvalidInput(); // at placeOrder/validation time
```
or in `_fillSameChain`, explicitly distinguish "leg already fully filled" (`totalRequired > 0 && remaining == 0`) from "leg was never funded" (`totalRequired == 0`), and refuse to mark such a leg as contributing to `isFullyFilled`/escrow release.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [{token: USDC, amount: 1000e6}]` and `order.output.assets = [{token: DAI, amount: 0}]` (zero-amount output leg), escrowing 1000 USDC.
2. Solver calls `fillOrder(order, FillOptions{outputs: [{token: DAI, amount: 0}]})`.
3. In `_fillSameChain`: `totalRequired = 0`, `alreadyFilled = 0`, `remaining = 0`, `solverAmount = 0` → skip branch taken, `isFullyFilled` stays `true` (guard `remaining > 0` fails).
4. `amountFilled (0) == totalRequired (0)` → `escrowedAmount = _orders[commitment][USDC] = 1000e6`.
5. `_withdraw` releases the full 1000 USDC escrow to the solver; `OrderFilled` is emitted; the user receives 0 DAI. [3](#0-2)

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

        // Orders carrying output calldata must be filled completely in a single fill.
        // The attached call is only executed on a full fill, so a partial fill would
        // leave the intended side effect unexecuted while releasing proportional escrow.
        if (order.output.call.length > 0 && !isFullyFilled) revert PartialFillNotAllowed();

        WithdrawalRequest memory body = WithdrawalRequest({
            commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
        });
        _withdraw(body, false, isFullyFilled);

        if (isFullyFilled) {
            _execute(order, outputsLen);
            emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        } else {
            delete _filled[commitment];
            emit PartialFill({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }
