### Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo()` allows attacker-crafted coin memo to crash wallet/PlotNFT sync via Python `RecursionError` - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody/`MofN` puzzle tree from an untrusted `Program` memo attached to a `CREATE_COIN` condition. When the memo indicates "further branching" (an `MofN` node), the method recurses into itself once per member, with no depth or size bound. Any coin creator can embed a memo with thousands of nested `MofN` members, and any client that parses that memo (wallet history sync, PlotNFT state resolution) will exhaust the Python recursion stack, raising an unhandled `RecursionError` and crashing the parsing process — a direct analog to the trust-dns-proto uncontrolled-recursion advisory (CWE-674), where attacker-controlled nested/self-referential input drove unbounded recursive parsing.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses the CHIP-0043 custody memo format directly from a CLVM `Program`: [1](#0-0) 

Key issue: when `further_branching_prog != Program.to(None)`, the code parses an `MofNHint` and recursively calls `PuzzleWithRestrictions.from_memo(memo)` for *every* member in `m_of_n_hint.member_memos`, without any limit on nesting depth or member count:

```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

There is no cap on recursion depth in this parser, unlike the deliberately-iterative `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py` (which the codebase explicitly documents as non-recursive "so we don't have to worry about blowing out the python stack" — see `.cursor/context/types.md:45`). The memo `Program` itself is fully attacker-controlled: it is embedded as the memo on a `CREATE_COIN` condition inside any spend bundle's puzzle output, and is not validated or size/depth-limited by consensus before being handed to `from_memo()`.

The consuming call site, `PlotNFT.get_next_from_coin_spend()`, only guards against `ValueError`: [2](#0-1) 

A `RecursionError` is not a `ValueError`, so it propagates uncaught through this function and crashes whatever process is walking PlotNFT/pool coin history (wallet daemon plotNFT sync, pool participant tooling), matching the CVE-2018-20994 bug class: unbounded recursive parsing of attacker-controlled structured input leading to a stack-exhaustion crash of the consuming software.

### Impact Explanation
Any user (spend-bundle submitter) can create a coin whose memo encodes a deeply nested `MofN` custody structure. Once that coin exists on-chain (or even just broadcast in a spend bundle that gets accepted into a block), any wallet or pool-participant/plotNFT client that later processes that coin's memo via `PuzzleWithRestrictions.from_memo()` (directly, or transitively through `PlotNFT.get_next_from_coin_spend()`) will hit Python's default recursion limit and raise an unhandled `RecursionError`, crashing the local process. This is a spend-triggered denial-of-service against wallet/plotNFT-processing software for any party that later inspects the crafted coin — satisfying the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
High. Constructing the malicious memo requires no special privilege — just crafting a `CREATE_COIN` condition with a deeply nested list as its memo argument, which any spend-bundle author can do. The memo content is not validated for depth or well-formedness by consensus/mempool rules, only interpreted lazily by downstream custody-aware wallet/pool code. No signing keys, network position, or coordination with other peers is required.

### Recommendation
Rewrite `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program()`) to use an iterative, explicit-stack-based traversal instead of unbounded Python recursion, mirroring the pattern already used in `sha256_treehash()`. Additionally, enforce a maximum nesting depth and a maximum member count while parsing memos, and ensure callers such as `PlotNFT.get_next_from_coin_spend()` catch and convert any parsing failure (including `RecursionError`) into the existing `GetNextPlotNFTError` rather than letting it propagate as an unhandled crash.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose memo is `Program.to(("CHIP-0043", [0, [], 1, [1, [<memo_1>, <memo_2>, ...]]]))`, where each `<memo_i>` is itself another nested `MofNHint`-shaped memo (`further_branching=1`) referencing further nested members, repeated to a depth of ~2000 (comfortably exceeding Python's default recursion limit of 1000).
2. Submit a spend bundle that creates a coin with this memo attached (any standard coin spend with a `CREATE_COIN ... memo` condition suffices — no special puzzle is required, since `from_memo` is invoked by downstream consumers, not by consensus).
3. Any client that later calls `PuzzleWithRestrictions.from_memo()` on this memo (e.g., `PlotNFT.get_next_from_coin_spend()` when it hits the "look for the memos" fallback path) will recurse once per nesting level and raise `RecursionError`, which is not caught by the surrounding `except ValueError:` block, crashing the client process.
