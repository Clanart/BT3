### Title
Oversized `--max-iterations` value bypasses bash arithmetic bounds, causing max-iteration termination guard to silently fail and the Ralph loop to run unbounded - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`setup-ralph-loop.sh` validates `--max-iterations` only with the regex `^[0-9]+$`, which accepts arbitrarily long digit strings with no upper bound check [1](#0-0)  . `stop-hook.sh` re-validates the stored value with the same unbounded regex and then performs bash integer arithmetic comparisons on it [2](#0-1)  . A value exceeding bash's 64-bit signed integer range makes `[[ $MAX_ITERATIONS -gt 0 ]]` throw a "value too great for base" arithmetic error, which evaluates as a non-zero (false) exit status rather than aborting the script (because it sits inside an `if` condition, which `set -e` explicitly does not treat as fatal). This silently disables iteration-limit enforcement, turning an intended bounded loop into an unbounded one.

### Finding Description
`setup-ralph-loop.sh` accepts `--max-iterations <n>` and only checks `[[ "$2" =~ ^[0-9]+$ ]]` before storing it verbatim into `.claude/ralph-loop.local.md`'s YAML frontmatter as `max_iterations: $MAX_ITERATIONS` [3](#0-2)  . There is no upper bound or length cap, so a value like `99999999999999999999` (20 digits, far beyond `INTMAX_MAX` ≈ 9.2×10^18) passes validation.

`stop-hook.sh` reads this field back from the frontmatter and validates it again with the same unbounded regex `^[0-9]+$` [4](#0-3)  , which still passes for the oversized value. It then performs the termination check:
```
if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]; then
``` [5](#0-4) 
Bash's `[[ ]]` arithmetic comparison uses native (64-bit) integer evaluation. When `MAX_ITERATIONS` exceeds the representable range, bash raises `value too great for base (error token is "...")` and the `[[ ]]` command reports failure (non-zero exit) instead of a true/false comparison result. Because this `[[ ]]` sits as the condition of an `if`, bash's `set -e` (`errexit`) does not treat this failure as fatal — commands in `if`/`while` conditions are exempt from `errexit` propagation. The `if` body is simply skipped, exactly as if `MAX_ITERATIONS` were `0` (the documented "unlimited" sentinel), so the max-iteration guard never fires for any iteration count, and the loop-blocking logic later in the script (`decision: block`) continues indefinitely.

This defeats the loop-termination invariant that `--max-iterations` is supposed to guarantee, silently converting a bounded loop into the "runs forever" mode without any warning to the user, and without the script crashing loudly.

### Impact Explanation
The Ralph loop's core safety mechanism against runaway execution is the `--max-iterations` bound; the README explicitly warns "This loop cannot be stopped manually" other than via `--max-iterations` or `--completion-promise`. An oversized-but-syntactically-valid value silently removes that bound, causing the stop hook to keep blocking session exit and re-feeding prompts indefinitely — unbounded automated command/prompt execution, excessive API usage/cost, and inability for the user to regain control except by manually deleting the state file. This matches a resource-exhaustion / safety-guard-bypass class of impact (denial-of-service via unbounded loop continuation) rather than remote code execution or credential leakage.

### Likelihood Explanation
The precondition is simply supplying a sufficiently large digit string to `--max-iterations` (via direct user invocation of `/ralph-loop`, or via untrusted repository/prompt content that induces Claude to run this command with an attacker-chosen value, which the rules permit as a slash-command input vector). No special privileges are required, the regex validation in both scripts explicitly permits arbitrarily long numeric strings, and the behavior is deterministic/reproducible on any bash version using native 64-bit arithmetic.

### Recommendation
Bound `--max-iterations` to a sane maximum (e.g., reject values above `2^63-1` or a much smaller practical ceiling like 100000) in both `setup-ralph-loop.sh`'s validation and `stop-hook.sh`'s re-validation, and treat any value failing a safe-range check as corrupted state (stop the loop, as already done for non-numeric values) rather than silently falling through the `if`.

### Proof of Concept
1. Run `setup-ralph-loop.sh "test task" --max-iterations 99999999999999999999`; confirm it passes validation and writes `max_iterations: 99999999999999999999` into `.claude/ralph-loop.local.md`.
2. Craft a transcript file with an assistant text message lacking the completion promise.
3. Set `iteration: 5` in the state file and invoke `stop-hook.sh` with hook input pointing at that transcript.
4. Assert: the script does NOT error out or halt the loop; it proceeds past the `if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]` check (i.e., stderr shows `value too great for base` but the script continues to emit `{"decision":"block", ...}` and increments the iteration), for any `ITERATION` value including ones far exceeding any reasonable intended cap — demonstrating the guard never fires regardless of iteration count, unlike the expected behavior of halting once `ITERATION >= MAX_ITERATIONS`.
