## Analysis Summary

I searched for stale-snapshot / stale-authorization-window bugs (the Olympus analog: a recorded value becomes inconsistent with state that changes during the same overall operation). The closest production analog in this repo is in the precompile balance-accounting bridge between the Cosmos SDK bank module and the EVM `StateDB`.

### Title
Overlapping/stale `prevEventsLen` event windows in `BalanceHandler` cause double-application of bank balance deltas to the EVM `StateDB` during nested precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler.BeforeBalanceChange` records a snapshot (`prevEventsLen`) of the current length of `ctx.EventManager().Events()` before a precompile executes its native action, and `AfterBalanceChange` later replays all events emitted *after* that snapshot to update `StateDB` balances via `AddBalance`/`SubBalance` [1](#0-0) . This is structurally the same "stale recorded value vs. changed live state" pattern as the Olympus `userVotesForProposal` bug: a snapshot taken once is later compared/consumed against a total that has moved on due to intervening activity.

### Finding Description
Each call to a stateful precompile creates a fresh `BalanceHandler` via `BalanceHandlerFactory.NewBalanceHandler()` inside `runNativeAction` [2](#0-1) , and at the end of the call, `AfterBalanceChange` drains `events[bh.prevEventsLen:]` [3](#0-2) . The `ctx.EventManager()` is shared and monotonically growing across the whole transaction/call stack, not scoped per precompile invocation. If a precompile's native action (or the contract it interacts with) triggers a *nested* stateful-precompile call before the outer action returns, the inner call's own `BalanceHandler` will consume and apply its slice of `[innerPrevEventsLen:end]` to `StateDB`. When the outer call finishes and its own `AfterBalanceChange` runs, its window `[outerPrevEventsLen:end]` still includes all events already consumed and applied by the inner call, so those bank events get parsed and applied to `StateDB.AddBalance`/`SubBalance` a second time.

The repository itself has a committed regression test explicitly describing and reproducing this exact defect class: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten... leads to balance desync between native bank keeper and EVM stateDB" [4](#0-3) . The demonstrated PoC uses a caller contract that recursively invokes a stateful precompile (`callback`), causing nested `Run` invocations over the same growing event log [5](#0-4) .

### Impact Explanation
If reachable through production precompiles (staking, distribution, erc20, gov, ics20, slashing — all of which use the same `BalanceHandlerFactory`/`runNativeAction` machinery [6](#0-5) ), double-processing of `CoinSpent`/`CoinReceived`/fractional-balance events would cause `StateDB.AddBalance`/`SubBalance` to be invoked twice for the same underlying bank transfer. This directly corrupts the EVM-visible balance relative to the actual native bank balance — i.e., duplication or destruction of spendable value in the EVM view of an account, which is a Critical unauthorized-duplication/accounting-corruption impact per the allowed-impact gate.

### Likelihood Explanation
The core defect (window-based delta tracking against a globally shared, ever-growing event log) is present in production code (`precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`), independent of whether the `BalanceHandler` instance itself is shared — even fresh per-call instances have overlapping windows once calls nest. However, I was not able to fully confirm within the available time whether any of the *production* (non-debug/test) precompiles can trigger a genuinely nested `RunNativeAction` invocation (i.e., one stateful precompile's native action causing another/same precompile's `Run` to execute and complete before the outer one finishes) purely through unprivileged user-controlled contract logic. The only concrete, currently-working reproduction in the codebase relies on the `debug` precompile, which is explicitly test-only ("Package debug defines test utilities... and *not* for use in production") and thus out of scope on its own. This uncertainty should be resolved before treating this as a confirmed Critical finding against production precompiles.

### Recommendation
Make the event window robust to nesting: either (a) have `AfterBalanceChange` truncate/remove the events it has already consumed from the shared event manager, or (b) track and skip event ranges already claimed by an inner call (e.g., via a monotonically-consumed cursor stored on `ctx` rather than a local field reset per call), or (c) disallow/detect precompile-call nesting within `RunNativeAction` and revert if a nested stateful-precompile call is detected mid-action.

### Proof of Concept
The repository's own integration test is a working demonstration of the mechanism: `evmd/tests/integration/balance_handler/balance_handler_test.go`'s `TestRecursivePrecompileCallsWithDebugPrecompile` deploys a caller contract that recursively invokes a stateful precompile, and asserts on the resulting event/log counts that show the desynchronized processing [7](#0-6) . Confirming a production-only (non-debug) nested-call path would require constructing a similar contract that chains calls between two in-scope stateful precompiles (e.g., erc20 → ics20 or staking → distribution) within a single top-level EVM call.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
