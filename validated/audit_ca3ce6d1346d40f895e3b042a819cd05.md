### Title
Tron `IntentGatewayV2` drops the `nonReentrant` guard present in the canonical EVM contract, allowing reentrant escrow manipulation via attacker-supplied predispatch calldata - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Algorand report's core broken invariant is: a custody-affecting transaction path lacked a guard (`RekeyTo == 0`) that the design implicitly relied on, letting the vault owner corrupt custody state mid-flow and extract escrowed value the accounting still believed was locked. The direct Hyperbridge analog is a real code divergence between the canonical EVM `IntentGatewayV2` and its Tron port: the canonical contract explicitly guards `placeOrder` and `cancelOrder` with `nonReentrant` [1](#0-0) [2](#0-1) , while the Tron port of the same functions carries no `nonReentrant` modifier anywhere in the file [3](#0-2) [4](#0-3) .

### Finding Description
`placeOrder` on Tron credits the `_orders[commitment][token]` escrow ledger based on the `dispatcher`'s token balance *after* invoking `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — an execution of calldata fully controlled by the order creator: [5](#0-4) 

The predispatch `call` field lets the order creator route arbitrary external calls (e.g., through a malicious/callback-bearing token) before the gateway measures `IERC20(token).balanceOf(dispatcher)` and credits `_orders[commitment][token] += reducedInputs[i].amount`. Because there is no `nonReentrant` lock on `placeOrder` (unlike the EVM original at line 162), that user-controlled external call can re-enter the gateway — e.g. calling `cancelOrder` against a separate, already-placed order — and drain that other order's `_orders` escrow via `withdraw()` [6](#0-5)  while the outer `placeOrder` call is still mid-flight and has not yet finalized its own escrow bookkeeping or `_nonce`/commitment state. The same absence of a lock applies to `cancelOrder`, which also dispatches value-bearing external calls (`IDispatcher(hostAddr).dispatch{value: msg.value}(request)`) [7](#0-6)  without any guard preventing a nested call back into `placeOrder`/`cancelOrder`/`withdraw` for the same or another commitment.

This is structurally identical to the report's bug class: the canonical implementation relies on a specific guard (`RekeyTo` check / `nonReentrant`) to keep custody state consistent across a multi-step operation, and the deployed variant (Tron) silently omits it, letting an unprivileged actor interleave calls to corrupt the escrow ledger (`_orders[commitment][token]`) — the exact value that gates how much every legitimate `withdraw()` call is allowed to pay out.

### Impact Explanation
`_orders[commitment][token]` is the sole source of truth for how much of a token is custodied per order and is what `withdraw()` decrements before paying beneficiaries/solvers [6](#0-5) . A reentrant path that lets a caller trigger `withdraw()`/`cancelOrder` on one commitment while another `placeOrder`/`cancelOrder` call is unwound mid-execution can cause double-settlement of the same escrowed input tokens or crediting of escrow amounts that were never durably transferred to the gateway — directly matching the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories for a production bridge-asset-custody contract.

### Likelihood Explanation
Likelihood is high in principle because both entrypoints (`placeOrder`, `cancelOrder`) are public, unprivileged, and already perform external calls with attacker-influenced data (arbitrary predispatch calldata, arbitrary ERC-20/native transfers) before all state is finalized — the exact precondition reentrancy protection exists to close, and the canonical EVM implementation demonstrably added `nonReentrant` for this reason. The concrete cross-function chain (reenter via a malicious predispatch token/call target into a second `cancelOrder`/`withdraw` on an unrelated commitment) is plausible from the code read but the full `fillOrder` implementation on the Tron variant was not reachable within the available search budget, so the exact reentrant call graph and whether any other implicit protections exist (e.g., transient-storage locks elsewhere) could not be fully confirmed.

### Recommendation
Add `nonReentrant` (or an equivalent transient-storage reentrancy lock, consistent with the pattern already used for duplicate-output-token detection in the EVM `placeOrder`) to every state-mutating, externally-callable entrypoint in `evm/tron/contracts/apps/IntentGatewayV2.sol` — at minimum `placeOrder`, `cancelOrder`, `onAccept`, and any `fillOrder`-equivalent function — mirroring the guards already present in `evm/src/apps/IntentGatewayV2.sol`. Audit all Tron-specific contracts for parity with the canonical EVM implementation's security modifiers before deployment.

### Proof of Concept
Conceptual PoC (exact reentrant target function on the Tron `fillOrder` path could not be fully verified in this session):
1. Attacker places OrderA normally, escrowing tokens, obtaining `commitmentA`.
2. Attacker places OrderB via `placeOrder` with `predispatch.assets`/`predispatch.call` pointing at a malicious ERC-20/callback contract as one of the predispatch assets.
3. During `placeOrder`'s `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` step (line 408), the malicious token's transfer hook re-enters the `IntentGatewayV2` contract and calls `cancelOrder(OrderA, ...)`, which invokes `withdraw()` and pays out/decrements `_orders[commitmentA]` while the outer `placeOrder` call for OrderB is still unwound.
4. Because no `nonReentrant` guard exists, both calls complete successfully, and depending on shared state paths this can be leveraged to have escrow accounting credited or paid out inconsistently with actual token balances held by the gateway — producing double-settlement/fund-loss on production bridge custody.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
