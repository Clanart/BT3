## Analysis

The core of the NFTX bug is: an external call made *during* a distribution loop lets the receiver re-enter the un-finished operation and pull funds meant for other parties, because the guard (the receiver's own callback) executes before the surrounding state is fully settled and nothing prevents that re-entry.

The structural analog in GitHub Desktop is the **trampoline** mechanism: for the whole duration of one git network operation, Desktop keeps a single trampoline token valid and exposes a local TCP socket that any process can talk to as long as it presents that token. The token is requested once and only revoked when the *outer* `fn` (the whole git command) completes: [1](#0-0) 

That token, together with `DESKTOP_PORT`, is injected into the git process environment for the entire operation: [2](#0-1) [3](#0-2) 

The socket server accepts *any* command carrying that valid token, with no binding to a specific git subprocess, remote URL, or single-use semantics — only membership in a `Set` is checked: [4](#0-3) 

### Title
Trampoline credential-helper token is valid for the full git-operation lifetime, allowing an attacker-controlled repository hook/filter to re-enter and exfiltrate the signed-in GitHub token - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`withTrampolineEnv`/`withTrampolineToken` mint one trampoline token and keep it valid for the *entire* duration of a git network operation (clone, fetch, pull, push), not just for a single askpass/credential prompt. Any process that can read that token/port from the environment — including a git hook, `clean`/`smudge` filter, or Git LFS custom transfer agent defined by the very repository being cloned/fetched — can independently connect to the trampoline TCP server before the outer operation finishes and request credentials for an arbitrary host (e.g. `github.com`) via the `CredentialHelper` `get` command. This mirrors the NFTX pattern of re-entering a not-yet-finished distribution: the "distribution" here is credential release, and the "receiver" is attacker-controlled repository content executed mid-operation.

### Finding Description
`withTrampolineEnv` requests a trampoline token and passes it (with the trampoline server's port) into the environment for the whole git invocation: [2](#0-1) [3](#0-2) 

The token stays valid until the *outer* git command resolves or rejects: [1](#0-0) 

The trampoline server accepts a `CredentialHelper` `get` command from *any* connecting socket that supplies this still-valid token — there is no check that the requester is the original git process, that only one credential request is allowed per token, or that the requested host corresponds to the actual remote of the operation in progress: [4](#0-3) 

The `get` handler resolves credentials purely by matching the requested URL's origin against a signed-in account, with no linkage to what remote/command originated the outer operation: [5](#0-4) [6](#0-5) 

Because the token remains "live" for the full lifetime of the git operation, a repository fetched/cloned by the user can define a git hook (e.g. `post-checkout`, `post-merge`), a `.gitattributes`-driven `clean`/`smudge` filter, or a Git LFS custom transfer agent that spawns a process during that window. That process inherits `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`, and can open its own connection to the trampoline server — re-entering the credential-fetch flow independently of, and before, the outer git command that originally requested the token has finished — and request `get` credentials for `https://github.com`. This releases the signed-in user's OAuth token via `getGitHubCredential`/`findGitHubTrampolineAccount` with no user prompt, exactly as the NFTX receiver's reentrant `donate()` pulls funds meant for later distribution steps before the outer `distribute()` call completes.

### Impact Explanation
A successful re-entry exfiltrates the user's GitHub OAuth token (or generic git credential) associated with the account signed into Desktop, without any prompt or user interaction, directly from a process spawned by content in an attacker-controlled repository the user merely cloned or fetched. This matches the "credential/token exfiltration" impact class from an attacker who "controls a cloned/fetched repository."

### Likelihood Explanation
The attacker only needs the victim to clone or fetch a repository containing a hook/filter/LFS transfer agent (all of which git executes automatically without extra confirmation during clone/fetch/checkout in Desktop's normal flow). The trampoline token and port are unconditionally present in the environment for the whole operation, and the server performs no per-command consumption or origin binding, so no unnatural user steps or local/admin access are required.

### Recommendation
Scope trampoline tokens to a single command/request rather than the whole git operation lifetime (issue a fresh, single-use token per socket transaction, or bind the token to the specific subprocess PID that spawned it), and validate that credential requests originate from the process tree of the git command that requested the token before releasing GitHub account credentials.

### Proof of Concept
1. Attacker publishes a repository containing a `post-checkout` hook (or `clean` filter / LFS custom transfer agent) whose script does:
   ```sh
   #!/bin/sh
   echo -e "get\nprotocol=https\nhost=github.com\n\0" | nc 127.0.0.1 "$DESKTOP_PORT"
   ```
2. Victim, signed in to GitHub in Desktop, clones this repository.
3. During the clone, Desktop runs the outer git operation inside `withTrampolineEnv`, which has already set `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` in the environment [3](#0-2) .
4. Git executes the malicious `post-checkout` hook while the token is still valid (the outer operation hasn't finished/revoked it yet, per `withTrampolineToken` [1](#0-0) ).
5. The hook's own TCP connection reaches `processCommand`, passes the `isValidTrampolineToken` check, and is routed to `createCredentialHelperTrampolineHandler` [4](#0-3) [7](#0-6) .
6. `getGitHubCredential` finds the signed-in GitHub account and returns username/token to the hook [8](#0-7) , which the hook script then exfiltrates over the network.

  private async processCommand(socket: Socket, command: ITrampolineCommand) {
    if (!isValidTrampolineToken(command.trampolineToken)) {
      throw new Error('Tried to use invalid trampoline token')
    }

    const handler = this.commandHandlers.get(command.identifier)

    if (handler === undefined) {
      socket.end()
      return
    }

    const result = await handler(command).catch(e =>
      log.error('Error processing trampoline command', e)
    )

    if (result !== undefined) {
      socket.end(result)
    } else {
      socket.end()
    }
  }

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string

  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)

    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
