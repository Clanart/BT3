### Title
Wallet RPC Uncontrolled Resource Consumption via Unauthenticated Offer Parsing - (File: chia/wallet/trading/offer.py)

### Summary
Any string that decodes as a bech32m `Offer` — including a completely unsigned, unbroadcastable spend bundle — is parsed by constructing an `Offer` object, whose `__post_init__` unconditionally executes every coin spend's CLVM puzzle/solution to compute hints and additions [1](#0-0) , and whose `conditions()` method separately re-executes every coin spend's CLVM again [2](#0-1) . Both paths budget CLVM execution against `MAX_BLOCK_COST_CLVM` (~11 billion cost units, a full block's worth of compute) per `Offer` object, and both run synchronously, in-process, on the wallet RPC event loop, with no timeout and no signature or fee requirement. This is reachable from an unauthenticated network party (an "offer counterparty") simply by sending a crafted offer string to a wallet operator, who triggers parsing via `check_offer_validity`, `get_offer_summary`, `take_offer` (even in examine-only mode), or any CLI/RPC command that loads an offer file.

### Finding Description
`Offer.from_bech32()` decodes and decompresses attacker-supplied bytes and immediately constructs an `Offer` via `Offer.from_bytes()` → `Offer.from_spend_bundle()` → dataclass `__init__` → `__post_init__` [3](#0-2) [4](#0-3) . `__post_init__` loops over every `CoinSpend` in the (unsigned) bundle and calls `compute_spend_hints_and_additions()`, which runs the puzzle reveal against the solution using `run_with_cost()` up to a shared `max_cost = MAX_BLOCK_COST_CLVM` budget [5](#0-4) . This is a real CLVM interpreter execution, not a cheap deserialization step — an attacker only needs a puzzle/solution pair (no valid BLS signature, no coin ownership, no fee) that spends close to the full per-object cost budget to force near-block-cost CPU work purely by having the string parsed.

`Offer.conditions()` — used by `valid_times()`, `absolute_valid_times_ban_relatives()`, and offer-summary code paths — does the same thing again over every coin spend with a fresh `MAX_BLOCK_COST_CLVM` budget [2](#0-1) .

The wallet RPC endpoints that reach this parsing are directly exposed to any offer-sending peer: `check_offer_validity` and `take_offer` in `wallet_rpc_api.py` call `Offer.from_bech32(request.offer)` / access `request.parsed_offer` synchronously inside the RPC handler [6](#0-5) , and `TakeOffer.parsed_offer` performs the same parse as a cached property [7](#0-6) .

Contrast this with the mempool's spend-bundle validation, which is the codebase's own hardened analog for executing untrusted CLVM: `pre_validate_spendbundle()` offloads execution to a separate worker process pool, applies `max_tx_clvm_cost` (half of `MAX_BLOCK_COST_CLVM`), and explicitly rejects any validation whose wall-clock `duration > self.validation_timeout`, with additional ns/cost anomaly detection [8](#0-7) . The offer-parsing path in `chia/wallet/trading/offer.py` has none of these mitigations: no process isolation, no wall-clock timeout, and it runs at up to double the mempool's per-spend-bundle cost allowance (full `MAX_BLOCK_COST_CLVM` vs. `max_tx_clvm_cost`).

### Impact Explanation
Because `run_with_cost()` is synchronous and executes on the same asyncio event loop the wallet RPC service uses, a single malicious offer string that is expensive to execute (but well within the `MAX_BLOCK_COST_CLVM` budget) will block that loop for the duration of the CLVM run. An attacker (any offer counterparty, e.g., someone posting offer files to a marketplace or DMing them to a wallet operator) can repeatedly submit such offers to `check_offer_validity`/`take_offer`(examine-only)/`get_offer_summary`, each one consuming CPU time proportional to a full block's worth of CLVM cost, with no fee paid and no valid signature required. This can render the wallet RPC (and by extension wallet management actions — sending transactions, checking balances, canceling offers) unresponsive, which is the direct analog of the referenced Open WebUI advisory where a single unauthenticated, low-cost-to-submit input field caused the admin panel to become unresponsive for legitimate administrative actions.

### Likelihood Explanation
High reachability: no authentication, no valid signature, no on-chain funds, and no fee are required to construct a spend bundle that maximizes CLVM cost per coin spend. The only requirement is a syntactically valid `CoinSpend` (arbitrary puzzle reveal/solution) wrapped in the offer's requested-payment structure, which is well documented/public. The attack can be repeated indefinitely and cheaply since generating expensive-but-valid-to-parse CLVM is a known technique (the codebase's own `TestMaliciousGenerators` fixtures in `chia/_tests/core/mempool/test_mempool.py` demonstrate exactly this style of crafted-cost CLVM payload) [9](#0-8) .

### Recommendation
- Run offer parsing/CLVM execution (`__post_init__`'s hint computation and `conditions()`) in a bounded worker pool or with an enforced wall-clock timeout, mirroring `MempoolManager.pre_validate_spendbundle()`'s `validation_timeout` and process-isolation model.
- Cap the CLVM cost budget for previewing/examining an untrusted, unsigned offer to something well below `MAX_BLOCK_COST_CLVM` (e.g., the mempool's `max_tx_clvm_cost`) rather than reusing the full block-cost allowance per `Offer` object.
- Rate-limit or require minimal proof-of-validity (e.g., basic structural/signature-less sanity checks) before running full CLVM execution on offer contents reachable from unauthenticated RPC calls such as `check_offer_validity` and `get_offer_summary`.

### Proof of Concept
Not independently executed in this analysis (index-only review); the mechanism is demonstrated by the codebase's own malicious-generator cost/time-based test fixtures (`SINGLE_ARG_INT_LADDER_COND`, etc., in `chia/_tests/core/mempool/test_mempool.py`) which show how a small program can be crafted to consume cost/time approaching the max block cost budget [10](#0-9) . Conceptually: (1) craft a `CoinSpend` whose puzzle reveal/solution consumes cost close to `MAX_BLOCK_COST_CLVM` using such a technique; (2) wrap it as the sole "requested payment" `CoinSpend` (with `parent_coin_info == bytes32.zeros`) of an `Offer`, with no valid aggregated signature; (3) serialize/compress/bech32m-encode via `Offer.compress()`/`to_bech32()`; (4) send the resulting string to a victim's wallet RPC via `check_offer_validity` or `take_offer` (examine-only); (5) observe that CLVM execution in `Offer.__post_init__`/`conditions()` consumes CPU time proportional to the crafted cost, on the wallet's event loop, blocking further RPC processing.

    async def pre_validate_spendbundle(
        self,
        spend_bundle: SpendBundle,
        spend_bundle_id: bytes32 | None = None,
        bls_cache: BLSCache | None = None,
        *,
        fee_per_cost: float = 0.0,
    ) -> SpendBundleConditions:
        """
        Errors are included within the cached_result.
        This runs in another process so we don't block the main thread
        """

        if spend_bundle.coin_spends == []:
            raise ValidationError(Err.INVALID_SPEND_BUNDLE, "Empty SpendBundle")

        assert self.peak is not None

        self._worker_queue_size += 1
        try:
            flags = get_flags_for_height_and_constants(self.peak.height, self.constants)
            sbc: SpendBundleConditions
            sbc, new_cache_entries, duration = await self.pool.run_in_loop(
                validate_clvm_and_signature,
                spend_bundle,
                self.max_tx_clvm_cost,
                self.constants,
                flags | MEMPOOL_MODE,
                nice=(5, -fee_per_cost),
            )
        # validate_clvm_and_signature raises a ValueError with an error code
        except ValueError as e:
            # Convert that to a ValidationError
            if len(e.args) > 1:
                error = Err(e.args[1])
                raise ValidationError(error)
            else:
                raise ValidationError(Err.UNKNOWN)  # pragma: no cover
        finally:
            self._worker_queue_size -= 1

        if sbc.num_atoms > sbc.cost * 60_000_000 / self.constants.MAX_BLOCK_COST_CLVM:
            raise ValueError("too many atoms")

        if sbc.num_pairs > sbc.cost * 60_000_000 / self.constants.MAX_BLOCK_COST_CLVM:
            raise ValueError("too many pairs")

        if spend_bundle_id is None:
            spend_bundle_id = spend_bundle.name()

        if duration > self.validation_timeout:
            self._maybe_log_timeout_spend_bundle(spend_bundle_id, spend_bundle)
            raise ValueError(f"timeout {duration:0.4} s")

        cost = sbc.execution_cost + sbc.condition_cost
        if cost == 0 or (duration > 0.1 and duration * 1e9 / cost > self.validation_timeout * 5.0):
            self._maybe_log_timeout_spend_bundle(spend_bundle_id, spend_bundle)
            raise ValueError(f"timeout ({duration * 1e9 / cost:0.4} ns/cost)")

        if bls_cache is not None:
            bls_cache.update(new_cache_entries)

        log.log(
            logging.DEBUG if duration < self.validation_timeout else logging.WARNING,
            f"pre_validate_spendbundle took {duration:0.4f} seconds {duration * 1e9 / cost:0.4} ns/cost "
            f"for {spend_bundle_id} (queue-size: {self._worker_queue_size})",
        )
        return sbc
