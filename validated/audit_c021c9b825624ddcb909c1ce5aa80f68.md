### Title
Scanner reports economically unspendable dust outputs as received funds — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report concerns a protocol that assumes an external call costs zero fees; when the fee becomes non-zero, the accounting breaks. The Serai analog lives in `bitcoin-serai`'s wallet: `Scanner` credits any output paying to a watched script as a spendable `ReceivedOutput` with no minimum-value check, and `SignableTransaction::new` never verifies that an input's value exceeds the fee required to spend it. Any unprivileged party can send the Serai key a tiny output (e.g., 1 sat; dust limits are relay policy, not consensus, so such outputs are creatable via any miner or non-standard broadcast). That output is reported as received funds, yet the ~57-vbyte witness cost of spending it exceeds its value at any viable fee rate — including it in a transaction burns it as fee and reduces the value available for payments.

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` matches outputs solely on `script_pubkey` and pushes a `ReceivedOutput` without inspecting `output.value`. There is no floor analogous to the `DUST` constant (546) that `SignableTransaction::new` enforces on *payments* in `networks/bitcoin/src/wallet/send.rs:165-169`. Inputs are accepted unconditionally: `input_sat` is summed at `send.rs:175` and every `ReceivedOutput` passed in becomes a `TxIn` at `send.rs:177-185` regardless of whether its value covers the ~57 vbytes it adds to the transaction weight (computed per-input at `send.rs:71-84`). A sub-fee input silently converts itself into extra fee: `fee()` is defined as `sum(inputs) - sum(outputs)` at `send.rs:138-141`. The dust/spendability threshold is itself fee-rate-dependent relay policy that can rise over time — exactly the "external fee can change" shape of the original bug — yet the code hardcodes a single 546-sat constant and applies it only to outputs, never to received inputs.

### Impact Explanation
An attacker can pollute the wallet's input set with dust outputs that are reported as received balance but are net-negative when spent. When such inputs are aggregated into a transaction, their value is destroyed as miner fee rather than contributing to payments, corrupting the protocol's accounting (balance reported > balance spendable). At scale this is a griefing/donation-of-loss vector against any plan that consumes scanned outputs, satisfying the "funds reported received that are not spendable" criterion.

### Likelihood Explanation
Any Bitcoin user can craft outputs paying the Serai key's known script_pubkey with arbitrarily low values; dust relay rules do not prevent a miner or direct submission from confirming them. Registering/scanning such outputs requires no privilege. The only mitigating factor is that downstream input-selection policy (outside this crate) may choose not to spend them, but nothing in the in-scope code prevents or even detects the condition.

### Recommendation
Enforce a minimum value on `ReceivedOutput`s: either in `Scanner::scan_transaction` (reject outputs whose value is below a spendability floor derived from the marginal input weight and a conservative fee rate) or in `SignableTransaction::new` (reject or skip inputs where `value < input_vbytes * fee_per_vbyte`). Document that `DUST` should be computed against the fee rate rather than fixed at 546.

### Proof of Concept

// Attacker sends a 1-sat P2TR output to the victim's scanned script_pubkey.
// In scanner code:
let outputs = scanner.scan_transaction(&attacker_tx); // returns 1 ReceivedOutput
assert_eq!(outputs[0].value(), 1); // credited as received funds

// Victim builds a spend:
let stx = SignableTransaction::new(
    vec![dust_output],                 // 1-sat ReceivedOutput
    &payments,                         // any payment
    None, None,
    fee_per_vbyte,                     // e.g. 10 sat/vB
);
// SignableTransaction::new never rejects the dust input; the input adds ~57 vB
