Found: the Tron `IntentGatewayV2.sol` contract's `instance()` function contains a fallback that isn't present in the EVM version — this is a genuine, locally-provable authentication bypass analog to the Mochi factory bug (a trust check that silently accepts an unregistered/attacker-controlled value as valid).

### Title
`instance()` fallback in Tron IntentGatewayV2 lets unregistered source chains authenticate as the gateway itself - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Mochi bug allowed anyone to have an arbitrary, unvetted contract accepted as a "valid vault" because the validity check only compared addresses without verifying provenance. The Tron port of `IntentGatewayV2` has the same class of flaw in its `instance()` lookup, which is the function `_authenticate`/`onAccept` relies on to decide whether an incoming cross-chain message is coming from a trusted, registered peer gateway.

### Finding Description
On the canonical EVM `IntentGatewayV2` (`evm/src/apps/intentsv2/IntentsBase.sol`), `_instance()` reverts with `UnknownInstance` when no gateway has been registered for a given `stateMachineId`: [1](#0-0) 

This strict revert is what makes `_authenticate()` safe: [2](#0-1) 

But in the Tron variant, `instance()` silently falls back to `address(this)` for any state machine ID that hasn't been registered, instead of reverting: [3](#0-2) 

This same `instance()` function is used both to authenticate incoming settlement messages and to build the `to` field of outgoing `RedeemEscrow`/`RefundEscrow` requests: [4](#0-3) [5](#0-4) 

Because `instance(unregisteredChain)` returns `address(this)` rather than reverting, `authenticate()` accepts a spoofed `PostRequest` whose `request.source` is *any arbitrary/unregistered state machine identifier*, as long as `request.from` is encoded as `address(this)` (the gateway's own address). Since ISMP's `onlyHost` modifier only guarantees the message was relayed through the legitimate Hyperbridge host with a valid state proof from *some* chain — it does not restrict which state machine ID that proof is for — an attacker who controls (or can get a message accepted from) any state machine ID not yet explicitly registered in `_instances` can produce a `PostRequest` with `source = <unregistered chain>` and `from = address(this-encoded-as-20-bytes)`, and it will pass `authenticate()` as if it came from a real, governance-registered peer gateway.

This mirrors the Mochi vault bug precisely: the "is this a valid/trusted peer" check (`instance(...) != module`) degrades from an allow-list comparison into a default-accept comparison for any key not in the allow-list, exactly like Mochi's factory-deployed-vault being wrongly recognized as valid because the check only compared computed vs. actual addresses without asserting the caller was privileged.

### Impact Explanation
If reachable (i.e., if an ISMP proof for an unregistered/attacker-influenced state machine can be delivered through the host — for example a standalone/test chain, a chain id collision, or any state machine not yet in `_instances`), this allows an attacker to forge a `RedeemEscrow` or `RefundEscrow` message that the gateway treats as authentic. `withdraw()` releases real escrowed user funds (input tokens, fees) to an attacker-chosen beneficiary: [6](#0-5) 

This is a direct "stealing/loss of funds via false proof/state acceptance" impact matching the bounty scope.

### Likelihood Explanation
Exploitability is gated on whether an attacker can get the ISMP host to accept a POST request whose `source` field is a state machine ID never explicitly registered in `_instances` (e.g., a state machine Hyperbridge onboards later, or one with default/uninitialized behavior). This is plausible on Tron, which is a newer/lower-scrutiny deployment target relative to EVM mainnet, and the divergence from the audited EVM logic (which reverts) strongly suggests this fallback was an unintentional regression introduced when porting to Tron, rather than a deliberate design choice.

### Recommendation
Make `instance()` on Tron behave identically to the EVM version — revert with `UnknownInstance` (or equivalent) when no gateway is registered for the given state machine ID, instead of defaulting to `address(this)`. Then re-audit every caller of `instance()` (`authenticate`, `cancelOrder`, `_fillCrossChain`, etc.) to confirm none of them rely on the fallback behavior for legitimate functionality.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with `_instances` populated only for the chains it has explicitly been configured for (no entry for state machine `"X"`).
2. Craft a `PostRequest` with `source = "X"`, `from = abi.encodePacked(address(intentGatewayV2))`, `body = bytes.concat(RequestKind.RedeemEscrow, abi.encode(WithdrawalRequest{ commitment: <victim's real order commitment>, tokens: <victim's escrowed tokens>, beneficiary: <attacker> }))`.
3. Get this request relayed through the legitimate ISMP host with a valid state/consensus proof for state machine `"X"` (any chain not yet registered as a peer instance).
4. `onAccept` is called by the host (`onlyHost` passes since the host itself validated the underlying proof), `authenticate()` calls `instance("X")`, which returns `address(this)` instead of reverting, so `module == address(this)` matches and authentication incorrectly succeeds.
5. `withdraw()` executes, transferring the victim's escrowed tokens/fees to the attacker-controlled beneficiary.
