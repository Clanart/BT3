### Title
Payout OP_RETURN operator-attribution output is unauthenticated, allowing reimbursement credit to be misattributed away from the fronting operator - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction that fronts a user's withdrawal. The only signature on this transaction is the user's own signature over the withdrawal input, explicitly required to use the `SinglePlusAnyoneCanPay` sighash type. That sighash flag covers only input 0 and the single corresponding output (output 0, the user payout). The transaction's third output — the OP_RETURN carrying the `operator_xonly_pk` that the whole reimbursement bookkeeping (`payout_payer_operator_xonly_pk` in the `withdrawals` table, `validate_payer_is_operator`, `is_kickoff_malicious`, `send_asserts`) relies on to decide *which* operator gets reimbursed — is not covered by that signature at all.

### Finding Description
The payout tx is constructed in `create_payout_txhandler`: [1](#0-0) 

It has three outputs: the user payout (index 0), an anchor (index 1), and an OP_RETURN with the `operator_xonly_pk` (index 2). The user's witness is verified with `SinglePlusAnyoneCanPay`: [2](#0-1) 
and the RPC doc comment explicitly states the sighash type used: [3](#0-2) 

`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` only binds the signer's input to the single output at the same index (output 0). It places no constraint whatsoever on outputs 1 (anchor) and 2 (OP_RETURN operator pubkey). Consequently, whoever ultimately completes, funds, and broadcasts the transaction is free to substitute an arbitrary `operator_xonly_pk` in the OP_RETURN output while keeping the exact same user-signed input and payout output — the signature stays valid because it never touched that byte range.

This value flows directly into the custody-attribution binding the protocol depends on: the verifier syncer parses this exact OP_RETURN field to decide which operator is credited as payer: [4](#0-3) 
That `payout_payer_operator_xonly_pk` is what `validate_payer_is_operator` checks equals the local operator's own key before it is willing to advance a kickoff for reimbursement: [5](#0-4) 
and what `is_kickoff_malicious` uses to decide whether a competing operator's kickoff, which claims reimbursement for this exact withdrawal, is honest: [6](#0-5) 

The binding that should hold is: *the operator named in the payout tx OP_RETURN == the operator whose funds actually left their own inputs to complete/fund the payout.* Because the OP_RETURN is outside the only signature on the transaction, this equality is not enforced by the protocol at the Bitcoin-transaction level — it is trusted metadata that any entity able to observe/reconstruct the payout transaction (e.g., in the mempool, or via `GetReimbursementTxs`/RBF resubmission flows) can freely rewrite before the transaction confirms.

### Impact Explanation
If a party (a competing operator, or anyone with access to the propagated/mempool transaction and standard node/wallet operations to re-fund and rebroadcast a replacement) swaps the OP_RETURN to name themselves (or a third operator) as the payer while an honest operator's funding inputs still cover the withdrawal, the reimbursement-tracking database will record the wrong operator as the payer of that withdrawal (`update_payout_txs_and_payer_operator_xonly_pk`). The operator who genuinely fronted the funds is subsequently unable to obtain reimbursement — `validate_payer_is_operator` will reject their `get_reimbursement_txs`/kickoff attempts because the on-chain-observed payer no longer matches their own key — while another operator can attempt to claim the reimbursement path for a payout they did not fund. This is exactly the "operator credited versus the party that paid" custody-attribution break called out as in-scope: an honest operator can be permanently unable to be reimbursed for BTC they actually sent to the user, and a false claim of payer identity can be proved to the verifiers/circuit that never actually happened.

### Likelihood Explanation
Exploitation only requires access to information that is inherently public before finality: the unconfirmed payout transaction (visible in the mempool, or obtainable from `GetReimbursementTxs`/RBF resend flows), and the ability to construct and broadcast a modified version with a different OP_RETURN and equal/higher fee — no verifier, operator, or aggregator privilege is required, and no signature needs to be forged, since the OP_RETURN was never signed. Any unprivileged network participant who can observe the mempool and run standard Bitcoin tooling can attempt this before the honest operator's version confirms.

### Recommendation
Cover the operator-attribution OP_RETURN output (and the anchor output) under the signed data by either (a) having the operator co-sign the transaction (not just the user), with a sighash that binds all outputs (e.g., `SIGHASH_ALL` on an operator-controlled input), or (b) deriving the credited operator identity from something that is bound to the actual spending input(s) that fund the diff (e.g., requiring the operator's funding input(s) to be present and covered by a full-transaction signature), rather than trusting an unauthenticated OP_RETURN payload as the sole source of payer attribution in `update_finalized_payouts`/`is_kickoff_malicious`.

### Proof of Concept
Conceptual (repo-only, no external tooling required to reason about it):
1. Honest Operator A observes an eligible withdrawal, builds the payout tx via `create_payout_txhandler` with `operator_xonly_pk = A`, funds it via `fund_raw_transaction`, and broadcasts/queues it (`core/src/operator.rs:620-673`).
2. Before confirmation, any observer takes the propagated transaction, keeps input 0 (the user's `SinglePlusAnyoneCanPay`-signed withdrawal input) and output 0 (user payout) unchanged, but replaces output 2's OP_RETURN payload with `operator_xonly_pk = B` (or removes/mangles it), and supplies their own additional funding input to cover fees, matching or exceeding A's fee — the user's signature remains valid because SIGHASH_SINGLE|ANYONECANPAY never covered outputs 1/2.
3. If this variant confirms first, `update_finalized_payouts` (`core/src/verifier.rs:2312-2342`) records payer `B` for this withdrawal instead of `A`.
4. `validate_payer_is_operator` (`core/src/operator.rs:1703-1729`) subsequently rejects Operator A's reimbursement attempts ("Payer is not own operator for deposit"), while Operator B can pursue the kickoff/reimbursement path attributed to them by `is_kickoff_malicious` (`core/src/verifier.rs:1871-1890`), despite not having fronted the funds.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
