### Title
OP_RETURN outputs are omitted from Bitcoin fee and weight accounting - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` adds an OP_RETURN output to the transaction before calculating its weight and virtual size, but calls `calculate_weight_vbytes` using only `payments`, without the OP_RETURN output. The resulting `needed_fee` and standard-weight check are therefore calculated for a smaller transaction than the one returned and signed.

### Finding Description
When `data` is supplied, `tx_outs` receives a zero-value OP_RETURN output. However, the initial fee calculation uses `payments` rather than `tx_outs`, so the added output is excluded from both `weight` and `vbytes`. The same omission occurs when calculating the size with change. Consequently, the returned transaction can have a larger actual vsize than the size used for `needed_fee`, and can exceed `MAX_STANDARD_TX_WEIGHT` despite passing the check.

The discrepancy is directly visible in the ordering of operations: the OP_RETURN output is pushed at lines 193–202, while the fee-size calculation at line 204 passes `payments`, which does not contain that output. The actual transaction returned at lines 245–251 does contain `tx_outs`, including the OP_RETURN output. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
The transaction pays `fee_per_vbyte * estimated_vbytes`, not `fee_per_vbyte * actual_vbytes`. With the maximum 80 bytes of caller-supplied data, the actual transaction is roughly 90 vbytes larger than estimated, depending on output serialization. The effective fee rate can therefore fall below the requested rate and potentially below the node’s minimum relay fee. The transaction can also bypass the standard-weight validation because the check uses the underestimated weight.

This can cause a signed transaction to be rejected by Bitcoin relay policy despite `SignableTransaction::new` accepting it, or to confirm later than intended because it pays a lower fee rate than requested.

### Likelihood Explanation
Any caller that supplies the supported `data` argument triggers the discrepancy. Up to 80 bytes are explicitly permitted by `SignableTransaction::new`, making the size underestimation deterministic rather than dependent on malformed data or exceptional chain conditions. [4](#0-3) [5](#0-4) 

### Recommendation
Include every output that will appear in the final transaction when estimating weight and vbytes. `calculate_weight_vbytes` should accept the complete output list, including OP_RETURN, or accept a separate `data`/`op_return` output parameter. Both the no-change and with-change calculations must use identical output sets to the returned transaction. The standard-weight check should also use the final transaction’s actual weight or an equivalent estimate covering all outputs.

### Proof of Concept
```rust
use bitcoin_serai::wallet::{SignableTransaction, ReceivedOutput, Scanner};
use bitcoin_serai::bitcoin::{ScriptBuf, Transaction};

// Assume `input` was produced by scanning a transaction paying the scanner's key.
let input: ReceivedOutput = todo!();
let payment = (ScriptBuf::new_p2tr_tweaked(tweaked_key), 10_000);
let data = Some(vec![0u8; 80]);
let fee_per_vbyte = 10;

let signable = SignableTransaction::new(
    vec![input],
    &[payment],
    Some(change_script),
    data,
    fee_per_vbyte,
).unwrap();

let actual_vbytes = signable.transaction().vsize() as u64;
let quoted_fee = signable.needed_fee();
let actual_fee = signable.fee();

// The OP_RETURN output was excluded from `needed_fee`, so:
assert!(quoted_fee < actual_vbytes * fee_per_vbyte);

// The actual fee remains determined by inputs minus outputs.
assert_eq!(actual_fee, quoted_fee);
```

The decisive invariant is that `calculate_weight_vbytes` is called with `payments`, while the final transaction contains `payments + OP_RETURN + optional change`. Because an 80-byte OP_RETURN increases the actual vsize but not the estimated vsize, `needed_fee` necessarily under-prices the transaction.
