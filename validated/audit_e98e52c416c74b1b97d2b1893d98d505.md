## Confirmed via Git's credential-helper protocol (`wwwauth[]` keys come straight from the remote server's `WWW-Authenticate` header and are passed by Git into the credential map unauthenticated).

### Title
Attacker-controlled `WWW-Authenticate` realm spoofing causes GitHub Desktop to misclassify a hostile remote as GitHub Enterprise and hand it a real account token - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The trampoline credential helper decides whether a remote host is a first-party GitHub endpoint using a cheap heuristic: if the `WWW-Authenticate` header of a 401 response contains `realm="GitHub"`, it is trusted as an "enterprise" GitHub host without any further verification. This is directly analogous to the `UniV3Decomposer` bug: a component is treated as "supporting" a trusted interface merely because it claims to (constructor flag / header string) instead of a real, unspoofable check (ERC165 `supportsInterface` / an actual API round-trip to `/meta` with `x-github-request-id`). Because the "happy path" check is attacker-suppliable, a malicious or compromised git remote/proxy can force Desktop to run its GitHub Enterprise sign-in flow against the attacker's own origin and then hand the resulting account credentials/token straight back to that same attacker origin via `git credential fill`.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies the remote that Git is currently authenticating against: [1](#0-0) 

```
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```

The `wwwauth[]` entries are values copied verbatim by Git from the `WWW-Authenticate` HTTP header returned by whatever server the current git operation is talking to (any git remote, an HTTP(S) proxy interposed on the connection, or a redirect target). This value is fully attacker-controlled and is used as ground truth for `endpointKind === 'enterprise'` **without ever contacting the real GitHub API** — unlike the fallback path a few lines later (`isGitHubHost`), which performs an actual HEAD request and only trusts the response if it carries the `x-github-request-id` header: [2](#0-1) 

When `getEndpointKind` returns `'enterprise'` and the user has no existing account for that endpoint, `getCredential` immediately triggers a full "sign in to GitHub Enterprise" flow pointed at the attacker's own origin: [3](#0-2) 

```
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    ...
    const account = await ui.promptForGitHubSignIn(endpoint)
    ...
    return credWithAccount(cred, account)
  }
```

`promptForGitHubSignIn` binds the sign-in endpoint directly to the attacker-supplied `origin`: [4](#0-3) 

```
    const { hostname, origin } = new URL(endpoint)
    if (hostname === 'github.com') {
      this.dispatcher.beginDotComSignIn(cb)
    } else {
      this.dispatcher.beginEnterpriseSignIn(cb)
      await this.dispatcher.setSignInEndpoint(origin)
    }
```

If the user completes this (looks-legitimate, "Sign in to GitHub Enterprise") flow, the resulting `Account` (login + OAuth/PAT token) is merged into the credential map and returned to Git's credential-fill request: [5](#0-4) 

```
const credWithAccount = (c: Credential, a: IGitAccount | undefined) =>
  a && new Map(c).set('username', a.login).set('password', a.token)
```

Since `cred` still targets the original (attacker) host/protocol/path from Git's `fill` request, this credential (containing the freshly-obtained real GitHub token) is handed straight to Git, which sends it as an HTTP `Authorization: Basic` header to the attacker's server on the very next request.

### Impact Explanation
This directly maps to two of the listed valid-impact categories: **credential/token exfiltration** and **unauthorized OAuth or account binding**. A hostile git remote/proxy can:
1. Respond to Desktop's git HTTP request with `WWW-Authenticate: Basic realm="GitHub"`.
2. Cause Desktop to believe the attacker's server is a GitHub Enterprise instance and open the real "Sign in to GitHub Enterprise" popup bound to the attacker's origin.
3. If the user completes sign-in (a normal-looking flow they've seen before for legitimate GHE remotes), Desktop stores a new Account bound to the attacker's endpoint and immediately relays that account's token back to the attacker's server as Basic-auth credentials, exfiltrating it.

Unlike the Solidity report where the bug's ultimate effect is a revert (functionality-only), here the equivalent "unsafe fallback" (relying on the identifying signal alone, without verification) does not fail closed — it fails open, delivering a real secret to the attacker. There is no additional guard: `getEndpointKind`'s `wwwauth` short-circuit runs before the safer `isGitHubHost` network round-trip and before any TLS/cert-based origin pinning, so nothing stops the spoof.

### Likelihood Explanation
No local access, no malware, no leaked credentials, and no unnatural user steps are required beyond the ordinary user action of adding/using a remote that resolves to attacker infrastructure (a malicious fork remote, a compromised/MITM proxy per `docs/technical/proxies.md`, or a redirect target during fetch/push/clone). The attacker only needs to control the HTTP response headers of that connection, which is exactly the class of "git remote/proxy response" attacker model in scope. The one user action required — completing the GHE sign-in dialog — is a normal, expected interaction for anyone who legitimately uses GitHub Enterprise remotes, not a contrived step.

### Recommendation
Do not treat the `wwwauth[]`/`WWW-Authenticate` realm string as sufficient proof that a host is GitHub/GHE. Require the same verified check used elsewhere (`isGitHubHost`, which validates via an authenticated round trip and the `x-github-request-id` response header) before allowing `endpointKind` to become `'enterprise'`, or at minimum before invoking `promptForGitHubSignIn`/binding a new account to an arbitrary attacker-supplied origin. If a fast heuristic must be kept for UX reasons, it should only ever be used to *offer* a sign-in prompt with a clear warning of the unverified origin, and the resulting token must never be handed back to that same unverified endpoint without the stronger verification succeeding first — mirroring the fix recommended in the Solidity report (replace "claims support" with a real, spoof-resistant support check).

### Proof of Concept
1. Set up a server (or MITM/corporate proxy per `docs/technical/proxies.md`) that answers Git's HTTP requests with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim add this server as a remote (e.g., `https://evil.example.com/foo/bar.git`) or point an existing remote/proxy at it, and perform any git operation Desktop drives through the trampoline credential helper (fetch/push/clone).
3. Git captures the header and forwards `wwwauth[0]=Basic realm="GitHub"` to Desktop's `credential fill` handler.
4. `getEndpointKind` returns `'enterprise'`; since no account exists for `evil.example.com`, Desktop calls `ui.promptForGitHubSignIn('https://evil.example.com')`, opening a "Sign in to GitHub Enterprise" dialog bound to that origin.
5. Victim completes sign-in (thinking it's a legitimate GHE instance they're adding). A real Account + token is created.
6. `credWithAccount` merges `{username: login, password: token}` into the credential map still targeting `evil.example.com`, and Git sends this as `Authorization: Basic <base64(login:token)>` to the attacker's server on the next request — exfiltrating the token. [6](#0-5)

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
