## Title
Clone flow explicitly disables Git's built-in clone-time RCE protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

## Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every `git clone --recursive` invocation and hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the process env, alongside an unrelated, purely local "sensitive destination path" allow/deny check (`isClonePathSensitive`). [1](#0-0) [2](#0-1) 

## Finding Description
The bug-class in the source report is: a security control that is correctly enforced on the "normal" path (pool status checks in `require_action_allowed`) is silently absent/disabled on an alternate, attacker-reachable path (flash loans), letting the attacker reach the same dangerous effect while bypassing the guard.

The same shape appears here. GitHub Desktop's own comment frames `isClonePathSensitive` as "a backstop against path traversal attacks where a crafted URL tricks the UI into deriving a clone path outside the intended base directory" — i.e., Desktop is aware that a remote-controlled clone (URL comes from a deep link / "Clone repository" flow / `open-repository-from-url` action, see `app/src/lib/parse-app-url.ts` and `openOrCloneRepository` reachable via `dispatcher.ts`'s `dispatchURLAction`) is attacker-influenced input. [3](#0-2) [4](#0-3) 

Despite treating the clone *path* as untrusted, the same function explicitly forces off `GIT_CLONE_PROTECTION_ACTIVE`, which is Git's own environment-variable circuit breaker for symlink/case-collision attacks embedded in a cloned repository's tree and submodules (the class of clone-time-RCE bug fixed upstream in Git 2.45.1/2.42.4-class advisories, where a malicious repository's `.git`/submodule layout can cause files to be written outside the intended working tree via case-insensitive or symlink tricks during a recursive clone). Git ships this protection *on by default* specifically because clone targets are attacker-controlled data; Desktop's clone wrapper unconditionally turns it off for every clone it performs, including clones whose URL originates from an untrusted deep link. [5](#0-4) 

This mirrors the report's root cause exactly: the developer added one guard (`isClonePathSensitive`, analogous to `require_action_allowed`) but the *other* pre-existing safety mechanism that Git itself provides for the same untrusted-input scenario is deliberately disabled on this path, re-opening the exact class of issue the pool-status check (here, Git's clone protection) was meant to prevent. Unlike the flash-loan bug, this isn't a missing call — it's an active override that defeats an upstream-supplied guard.

## Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` genuinely disables Git's clone-time protections against malicious repository content (crafted submodule/`.git` symlink or case-collision layouts), then any attacker who can get a Desktop user to clone their repository — via `x-github-client://openRepo/<attacker-url>` deep links, "Clone a repository" with a pasted URL, or "Open in Desktop" buttons on third-party sites — can potentially write files outside the intended repository directory during the `--recursive` clone, leading to file write outside the repo and potentially code execution (e.g., overwriting a shell rc file, an editor config, or a hook), which is exactly the outside-repo file-write / RCE category called out as valid impact in this task.

## Likelihood Explanation
The clone URL is fully attacker-controlled in the `open-repository-from-url` flow and requires no privileged access, just a user clicking a link or pasting a URL, matching the "unprivileged, deep-link/GitHub-API-object-controlled" threat model. The clone always runs with `--recursive`, so any malicious submodule content in the attacker's repository is fetched and checked out under the disabled protection. The main uncertainty (not fully verifiable from static code alone) is whether the *currently pinned* `dugite`/Git binary version bundled with Desktop is new enough for `GIT_CLONE_PROTECTION_ACTIVE` to have any protective effect to disable in the first place, and whether Desktop's `--recursive` submodule handling combined with disabling this flag actually reaches the vulnerable write path on the OS/filesystem in use (case-insensitive filesystems like default macOS/Windows are the primary risk surface). This should be confirmed by checking the bundled Git/dugite version and reproducing the clone-time write-outside-tree PoC against it.

## Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Let Git's default (protection enabled) apply for all clones, especially those originating from untrusted URLs (deep links, pasted URLs). If the override exists to work around a UX/behavior issue, gate it narrowly and document why it is safe, and add the same kind of check to the recursive submodule fetch path that `isClonePathSensitive` performs for the destination path, so both known attacker-controlled inputs (destination path AND repository content) are defended.

## Proof of Concept
1. Register/host a Git repository containing a submodule or tree structure crafted to trigger the case-insensitive/symlink `.git` clone-time write-outside-tree condition addressed by Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard.
2. Send the victim a link of the form `x-github-client://openRepo/https://attacker.example/evil.git` (parsed by `parseAppURL` into an `open-repository-from-url` action) or have them paste the URL into Desktop's "Clone a repository" dialog.
3. Desktop routes this to `dispatcher.openRepositoryFromUrl` → `openOrCloneRepository` → `clone()` in `app/src/lib/git/clone.ts`, which spawns `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` in the environment. [6](#0-5) 
4. Because Git's protection is disabled, the malicious clone content is allowed to write outside the intended working directory during checkout, whereas with the default (protection-enabled) behavior the clone would abort or sanitize the dangerous entries.
5. Verify by comparing file-system state after cloning the same crafted repository with `GIT_CLONE_PROTECTION_ACTIVE` unset (default) vs. explicitly `false`, as Desktop's own code does.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
