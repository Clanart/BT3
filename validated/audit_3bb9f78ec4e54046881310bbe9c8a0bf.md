### Title
Bonus reward tokens that revert on zero-value approvals permanently brick `WombatStaking` pool deposits, withdrawals and harvests - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking._sendRewards` resets ERC20 allowances to `0` via `safeApprove(..., 0)` before setting a new allowance, exactly like the pattern flagged in the referenced report. If any bonus reward token or the WOM/mWOM fee-receiving tokens flowing through this function reverts on a zero-value approval, every call path that harvests rewards for that pool (`deposit`, `depositLP`, `withdraw`, `harvest`) reverts, permanently freezing both the pool's yield and, transitively, users' ability to deposit/withdraw.

### Finding Description
`_sendRewards` is invoked from `_toMasterWomAndSendReward` for the WOM reward and for every bonus token registered via `addBonusRewardForAsset`: [1](#0-0) 

Inside `_sendRewards`, allowances are unconditionally zeroed out before being re-set, both for fee recipients and for the final rewarder call: [2](#0-1) 

The `smartWomConverter`/`mWom` fee path does the same pattern: [3](#0-2) 

`safeApprove` (OZ's `SafeERC20.safeApprove`) performs a raw `approve` call under the hood; it does not special-case tokens that revert when approving `0` (the "revert on zero value approval" weird-ERC20 trait, e.g. Binance-Peg BNB on Ethereum, as cited in the source report). Any such token registered as a bonus reward (via the owner-only but ordinary `addBonusRewardForAsset`) or received as a fee token will cause `_sendRewards` — and therefore `_toMasterWomAndSendReward` — to revert as soon as its balance changes and a reward disbursement is attempted.

Because `_toMasterWomAndSendReward` is called unconditionally from `deposit`, `depositLP`, `withdraw`, and `harvest`: [4](#0-3) [5](#0-4) 

any ordinary, unprivileged wallet's call to `deposit`, `withdraw`, or `harvest` on the affected pool will revert once the problematic token accrues a nonzero bonus balance — bricking the entire pool for all users, not just fee/harvest flows.

### Impact Explanation
This causes a permanent, protocol-level denial of service: users cannot deposit into, withdraw from, or harvest rewards from the affected `WombatStaking` pool. Principal already staked and any accrued-but-unclaimed WOM/bonus rewards become permanently locked, since every transaction path routes through the reverting `safeApprove(..., 0)` call and there is no fallback or removal mechanism inside `_sendRewards` itself. This satisfies both "permanent freezing of funds" and "permanent freezing of unclaimed yield."

### Likelihood Explanation
The trigger condition — a bonus reward token (or wom/mWom fee-recipient interaction) that reverts on zero-value approvals — is a known and documented weird-ERC20 trait (as in the referenced report's BNB example). Once such a token is registered as a bonus reward for a pool (a routine, expected admin action to support additional Wombat pool incentives, not a malicious governance action), any ordinary user transaction against that pool triggers the permanent freeze. The likelihood depends on such a token being used as a bonus reward, which is plausible given Wombat pools support varied bonus tokens across chains.

### Recommendation
Replace `safeApprove` resets with `forceApprove` (OpenZeppelin's variant that first checks/handles nonzero-to-nonzero transitions safely) or restructure to avoid unconditional zero-then-nonzero approvals — e.g., only reset to zero when the current allowance is nonzero, or use `safeIncreaseAllowance`/exact-amount transfer patterns that don't require a zero-value approval step at all.

### Proof of Concept
1. Owner registers a bonus reward token `T` for pool `_lpToken` via `addBonusRewardForAsset`, where `T.approve(spender, 0)` reverts (mirroring BNB's `0xB8c77482e45F1F44dE1745F52C74426C631bDD52` behavior).
2. Wombat pool accrues a nonzero balance of `T` as harvestable bonus reward for `_lpToken`.
3. Any user calls `deposit`/`withdraw`/`harvest` for `_lpToken`; `_toMasterWomAndSendReward` computes `bonusBalanceDiff > 0` and calls `_sendRewards(_lpToken, T, poolInfo.rewarder, bonusBalanceDiff)`.
4. `_sendRewards` executes `IERC20(T).safeApprove(feeInfo.to, 0)` or `IERC20(T).safeApprove(_rewarder, 0)`, which reverts, reverting the entire user transaction and permanently bricking the pool. [6](#0-5)

    function _sendRewards(
        address _lpToken,
        address _rewardToken,
        address _rewarder,
        uint256 _amount
    ) internal {
        if (_amount == 0) return;
        uint256 originalRewardAmount = _amount;

        if (!isPoolFeeFree[_lpToken]) {
            for (uint256 i = 0; i < feeInfos.length; i++) {
                Fees storage feeInfo = feeInfos[i];

                if (feeInfo.isActive) {
                    address rewardToken = _rewardToken;
                    uint256 feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR;
                    _amount -= feeAmount;
                    uint256 feeTosend = feeAmount;

                    if (feeInfo.isMWOM && rewardToken == wom) {
                        if (smartWomConverter != address(0)) {
                            IERC20(wom).safeApprove(smartWomConverter, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IConverter(smartWomConverter).smartConvert(feeAmount, 0);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        } else {
                            IERC20(wom).safeApprove(mWom, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IMWom(mWom).deposit(feeAmount);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        }
                    }

                    if (!feeInfo.isAddress) {
                        IERC20(rewardToken).safeApprove(feeInfo.to, 0);
                        IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
                        IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
                    } else {
                        IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
                        emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
                    }
                }
            }
        }

        IERC20(_rewardToken).safeApprove(_rewarder, 0);
        IERC20(_rewardToken).safeApprove(_rewarder, _amount);
        IBaseRewardPool(_rewarder).queueNewRewards(_amount, _rewardToken);
    }
