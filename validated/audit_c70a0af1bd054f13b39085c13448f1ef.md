Confirmed: `PreAddTx` and `IsReady` in `kaiax/gasless/impl/tx_pool.go` enforce `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` using node-wide counters (`g.knownTxs.numQueue()`, `g.knownTxs.numExecutable()`) that aggregate bundle txs from **all senders**, not per-sender. This is the direct analog of the reported bug class (shared/global cap instead of per-user cap).

### Title
Global (not per-sender) gasless bundle-tx cap lets one sender exhaust `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` and block all other gasless users - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The gasless module enforces two configured resource limits, `MaxBundleTxsInQueue` and `MaxBundleTxsInPending`, meant to bound the resources consumed by the gasless (approve+swap) bundling feature in the node's tx pool. These limits are checked against `g.knownTxs`, a single map shared across **all senders**, rather than per-sender counters. Exactly like the reported `SolverVaults::currentDeposit` issue — where a shared counter for a "cap" is incremented/checked globally instead of per-user — a single gasless user (or a small set of colluding/malicious accounts) can fill up the shared `knownTxs` queue/pending counters and cause all subsequent, unrelated gasless senders' transactions to be rejected or never promoted.

### Finding Description
`PreAddTx` rejects an incoming bundle tx globally once the shared queue counter is reached, with no accounting keyed by sender: [1](#0-0) 

`IsReady` similarly gates promotion into `pending` using the aggregate `numExecutable()` count across all known bundle txs from all senders, again with no per-sender bookkeeping: [2](#0-1) 

The underlying `knownTxs` type is a flat `map[common.Hash]*knownTx` with aggregate counting helpers `numQueue()`, `numPending()`, `numExecutable()` that iterate the entire map regardless of sender: [3](#0-2) 

The config documents these as global "max number of gasless bundle txs in pending/queue" values (default 100/200), confirming the intended semantics are a node-wide safety valve, but nothing prevents one address from unilaterally consuming the entire allowance by repeatedly submitting `approve`+`swapForGas` gasless bundle pairs (each counts as a bundle tx in `IsBundleTx`/`IsModuleTx`): [4](#0-3) [5](#0-4) 

### Impact Explanation
Once the global `MaxBundleTxsInQueue` (default 200) count is reached, `PreAddTx` returns `ErrBundleTxQueueFull` for every other gasless sender's approve/swap transactions node-wide, i.e., unrelated users' legitimate gasless transactions are denied admission to the pool purely because one sender saturated the shared counter. Similarly, `IsReady`'s pending cap can stall promotion of other senders' bundle txs even though those senders individually never approached any limit. This is a straightforward availability/fairness violation of the gasless feature reachable by any public transaction submitter with token balance sufficient to build repeated approve/swap gasless bundles (no special privileges needed), matching the "gasless module" and "unprivileged transaction sender/gasless user" reachable class in scope.

### Likelihood Explanation
Likelihood is high: the attack requires only submitting ordinary `approve`+`swapForGas` gasless transaction pairs (which are cheap to construct, especially if the balance/allowance checks are configured at lower `BalanceCheckLevel`, or even fail balance checks after being counted while `TxStatusQueue`) repeatedly until `numQueue()` reaches `MaxBundleTxsInQueue`. No coordination with validators or the auctioneer is needed; any RPC endpoint accepting pooled transactions and running the gasless module is affected. Because `PreAddTx` counts the tx as soon as it enters the queue (before nonce ordering/executability is confirmed), an attacker doesn't even need txs to become pending to exhaust the queue-side counter.

### Recommendation
Track queue/pending bundle-tx counts per sender (e.g., `map[common.Address]int` alongside or instead of the flat aggregate), and enforce `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` as per-sender caps (optionally in addition to a node-wide ceiling to still bound total memory/resource usage). At minimum, cap the number of bundle txs a single sender can have in `knownTxs` with status `TxStatusQueue`/`TxStatusPending` independently of other senders' usage.

### Proof of Concept
1. Configure a node with default `--gasless.max-bundle-txs-in-queue=200`.
2. From a single attacker-controlled address (or a set of addresses with minimal token balance/allowance so the approve/swap bundle is well-formed per `isApproveTx`/`isSwapTx` checks), submit 200+ `approve(spender=SwapRouter, amount=MaxUint)` + `swapForGas(...)` transaction pairs to the pool in quick succession.
3. Each such tx passes `IsBundleTx` → `IsModuleTx` → `IsApproveTx`/`IsSwapTx` and is admitted into `g.knownTxs` with `TxStatusQueue` via `PreAddTx` (`kaiax/gasless/impl/tx_pool.go:38-53`), incrementing the shared `numQueue()` count.
4. Once `numQueue() >= MaxBundleTxsInQueue` (200), any other legitimate, unrelated gasless user's approve/swap transaction sent afterward is rejected with `ErrBundleTxQueueFull` in `PreAddTx`, even though that user never exceeded any individual limit — demonstrating the shared-state-not-per-user flaw analogous to the reported `SolverVaults::deposit` issue.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

// Check promotion condition and enforce pending pool flow control.
func (g *GaslessModule) IsReady(txs map[uint64]*types.Transaction, next uint64, ready types.Transactions) bool {
	g.knownTxsMu.Lock()
	defer g.knownTxsMu.Unlock()

	tx, ok := txs[next]
	if !ok {
		return false
	}

	if !g.isReady(txs, next, ready) {
		return false
	}

	if g.IsBundleTx(tx) {
		// If prev tx is bundle tx, there's no need to check the knownTxs limit because it has been checked in the previous `IsReady()` execution.
		isPrevTxBundleTx := len(ready) != 0 && g.IsBundleTx(ready[len(ready)-1])
		if isPrevTxBundleTx {
			g.knownTxs.add(tx, TxStatusPending)
			return true
		}

		maxBundleTxsInPending := g.GetMaxBundleTxsInPending()
		if maxBundleTxsInPending != math.MaxUint64 {
			numExecutable := uint(g.knownTxs.numExecutable())

			numSeqTxs := uint(1)
			for i := next + 1; i < next+uint64(len(txs)); i++ {
				if tx, ok := txs[i]; ok && g.IsBundleTx(tx) {
					numSeqTxs++
				} else {
					break
				}
			}

			// false if there is possibility of exceeding max bundle tx num
			if numExecutable+numSeqTxs > maxBundleTxsInPending {
				logger.Trace("Not promoting a tx because of exceeding max bundle tx num", "tx", tx.Hash().String(), "numExecutable", numExecutable, "maxBundleTxsInPending", maxBundleTxsInPending)
				return false
			}
		}

		g.knownTxs.add(tx, TxStatusPending)
	}

	return true
}

func (k knownTxs) numPending() int {
	num := 0
	for _, knownTx := range k {
		if knownTx.status == TxStatusPending {
			num++
		}
	}
	return num
}

func (k knownTxs) numExecutable() int {
	num := 0
	for _, knownTx := range k {
		if knownTx.status == TxStatusPending && !knownTx.tx.IsMarkedUnexecutable() {
			num++
		}
	}
	return num
}

func (k knownTxs) numQueue() int {
	num := 0
	for _, knownTx := range k {
		if knownTx.status == TxStatusQueue {
			num++
		}
	}
	return num
}
