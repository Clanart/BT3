### Title
Improper order of operations in `withdraw()` (Tron `IntentGatewayV2`) exposes escrow accounting to a CEI violation — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` reintroduces the exact bug class described in the external report (`cancelLock`): the internal escrow-accounting update is performed **after** the external token transfer instead of before it. This is a direct CEI-ordering regression relative to the canonical EVM implementation (`IntentsBase.sol::_withdraw`), which already applies the correct check-effects-interactions ordering.

### Finding Description
In the canonical EVM contract, `_withdraw` in [1](#0-0)  decrements `_orders[body.commitment][token]` **before** making the external call/transfer — the correct CEI pattern.

The Tron variant's `withdraw()` does the opposite: it performs the external call/transfer first and only decrements the escrow mapping afterward: [2](#0-1) 

Concretely:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");   // interaction FIRST
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;                // effect AFTER
    ...
}
```

This is precisely the pattern flagged in the external report for `cancelLock`: the accounting mutation (`delete locks[lockId]` / decrement escrow) is moved after the external call, meaning the escrow balance for `(commitment, token)` remains stale (non-decremented) for the duration of the external call.

`withdraw()` is reachable from the unprivileged, unguarded entry point `cancelOrder()` [3](#0-2) , which has **no `nonReentrant` modifier** (unlike the EVM `IntentGatewayV2.cancelOrder`, which is `nonReentrant`, per `docs/content/developers/evm/intent-gateway/cancelling-orders.mdx`). The only guard against same-commitment double-spend is `_filled[body.commitment] = beneficiary`, set as the first statement inside `withdraw()` — which blocks a reentrant call to `cancelOrder` for the *same* order (it reverts at the `_filled[commitment] != address(0)` check). However, the guard does **not** cover the per-token escrow field itself: since `_orders[commitment][token]` is still non-zero during the external call, any code path that reads or re-validates that mapping mid-call (e.g. a future/composed integration, or a token with reentrant hooks that can trigger a second withdrawal path for the same token/commitment before the decrement lands) observes stale escrow accounting rather than the CEI-safe post-transfer state guaranteed on the canonical EVM contract.

### Impact Explanation
Medium: this is a genuine order-of-operations defect matching the bounty's "logic attacks / transaction manipulation / stealing or loss of funds" class in the bridge's intent-settlement custody logic. It is structurally identical to the already-known and separately-fixed reentrancy issue in `IntrinsicIntents.sol` (see `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), confirming this bug class is actively tracked and remediated elsewhere in the codebase — but the Tron fork was not brought into parity with that fix.

### Likelihood Explanation
Medium-Low under the standard-ERC20 assumption (same caveat as the original report): with a compliant, non-callback ERC20/native transfer the reentrancy surface is closed by the `_filled` guard being set first. It becomes actively exploitable if a fee/input token with transfer callbacks (ERC777-style, or a token with `transfer` hooks) is escrowed, or if any additional code path is added that reads `_orders[commitment][token]` without also being blocked by `_filled`.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the CEI pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` immediately after the zero-balance check and **before** issuing the native/ERC20 transfer. Additionally, add `nonReentrant` to `cancelOrder()` in the Tron variant to match the hardening already present in the canonical `IntentGatewayV2.cancelOrder`.

### Proof of Concept
Not independently exploitable through the indexed code alone under standard-ERC20 assumptions, since `_filled[commitment]` is set before the vulnerable loop and blocks reentrant same-commitment cancellation. Exploitability requires either (a) an escrowed fee/input token with a transfer callback, or (b) a future change that reads/relies on `_orders[commitment][token]` without the `_filled` gate — at which point the sequence `token.call(...transfer...)` (line 693–699) → attacker callback → `_orders[commitment][token] -= amount` (line 701) would allow the attacker to observe/act on stale (non-decremented) escrow state during the callback window, exactly mirroring the `cancelLock` primitive from the source report.
