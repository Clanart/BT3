### Title
Path-containment check in `resolveWithin()` uses prefix `startsWith()` without a path-separator boundary, allowing escape into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` is the single security boundary that Desktop relies on to guarantee a user- or attacker-influenced relative path (e.g. the `filepath` query parameter of an `x-github-client://openrepo` deep link) stays inside a repository's working directory before the resolved path is passed to filesystem/shell APIs. The final containment check is a bare string `realResolved.startsWith(realRoot)` [1](#0-0)  with no trailing path-separator normalization, so any sibling directory whose name happens to share the repository directory name as a string prefix (e.g. root `…/myrepo` vs. sibling `…/myrepo-secrets`) is incorrectly treated as "inside" the root, exactly analogous to the Setup.sol report where a single incomplete boolean condition let a value that should have satisfied *two* constraints together pass with only one satisfied.

### Finding Description
`resolveWithin()` (and its `resolveWithinPosix`/`resolveWithinWin32` variants) is documented as guaranteeing "the resolved path... resides at, or underneath, the root path" [2](#0-1) . The implementation normalizes and resolves the path, then performs the final safety decision purely with:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`String.prototype.startsWith` has no concept of path segment boundaries. If `realRoot` is `/Users/alice/Documents/GitHub/myrepo` and the resolved path is `/Users/alice/Documents/GitHub/myrepo-private/secret.txt`, the latter string literally starts with the former string, so the function returns the escaped path as "safe" even though `myrepo-private` is a completely different directory. There is no check that the next character after the prefix is a path separator (or that the strings are exactly equal).

This is the same bug class as the report: the intended invariant requires two conditions to both hold (the resolved path must be under root — normally: prefix match *and* segment boundary), but the code implements only the weaker single condition (prefix match), so values that should be rejected slip through.

The existing test suite covers `..` traversal, absolute paths, and symlink escapes [3](#0-2)  but contains no test for the sibling-directory-prefix case, confirming the gap is unguarded.

### Impact Explanation
`resolveWithin` is used from `Dispatcher.openRepositoryFromUrl`, which is reached when a user clicks an `x-github-client://openrepo?...&filepath=...` deep link — a value fully controlled by whoever crafts the link:

```ts
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(...)
}
``` [4](#0-3) 

The `isAbsolute(filepath)` guard [5](#0-4)  only blocks absolute paths; relative `..`-traversal paths that resolve to a sibling directory sharing a name prefix with the current repository bypass the `resolveWithin` guard and are handed to `shell.showItemInFolder`, revealing the existence and location of files outside the intended repository boundary (e.g. another checked-out project, or an attacker-named clone the user was tricked into creating nearby). The same primitive is reused for reading file contents into an LLM prompt in `buildConflictContext()` [6](#0-5) , where a resolved path that escapes the working directory into a same-prefixed sibling would have its content read and sent as conflict-resolution context — a stronger read/exfiltration primitive than the deep-link case, since it isn't just "reveal in Finder" but actual file content disclosure of a file outside the repo.

### Likelihood Explanation
Exploitation requires: (1) a victim clicking a crafted GitHub Desktop deep link (the standard "attacker controls a link the user clicks" primitive explicitly allowed by the task's valid-impact criteria), and (2) the existence of a sibling path on disk whose name has the repository's directory name as a prefix. Because GitHub Desktop's default clone location groups all cloned repos under one parent folder (e.g. `~/Documents/GitHub/`), and developers frequently keep multiple related/forked/private checkouts with similar prefixed names (`repo`, `repo-private`, `repo2`, `repo.wiki`, etc.) side by side, this precondition is realistic without any additional local access or malware. No credentials or admin rights are needed.

### Recommendation
Fix the containment check to require an exact match or a path-separator boundary immediately after the prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the same fix in both the POSIX and Win32 code paths (using the appropriate separator for each), and add a regression test asserting that a sibling directory sharing a name prefix (e.g. `root` vs. `root-evil`) is rejected by `resolveWithin`.

### Proof of Concept
1. Victim has cloned a repository to `~/Documents/GitHub/myrepo` and also has an unrelated folder `~/Documents/GitHub/myrepo-secrets` (or another checkout with a prefixed name) in the same parent directory.
2. Victim opens `myrepo` in GitHub Desktop, then clicks an attacker-supplied deep link:
   `x-github-client://openrepo/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fpassword.txt`
3. `parseAppURL` extracts `filepath = "../myrepo-secrets/password.txt"` [7](#0-6) ; `isAbsolute` check passes because the path is relative.
4. `resolveWithin(repository.path, filepath)` resolves to `~/Documents/GitHub/myrepo-secrets/password.txt`, and because that string starts with `~/Documents/GitHub/myrepo`, the flawed `startsWith` check returns it as "safe" instead of `null`.
5. `shell.showItemInFolder(resolved)` opens the file manager pointed at `password.txt` outside the repository, disclosing its existence/location to the deep-link opener's expectations; in the `buildConflictContext` path the equivalent escape results in the file's contents being read and forwarded to the Copilot prompt-building pipeline.
