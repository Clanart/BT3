### Title
`ReceivedOutput::read` deserializes attacker-supplied `(offset, output, outpoint)` tuples without verifying the offset actually binds the output's `script_pubkey` to the scanner's key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the CtrlPanel issue (privileged-data endpoints reachable without authorization checks), `ReceivedOutput::read` accepts untrusted bytes and returns a `ReceivedOutput` that asserts ownership of a Bitcoin output without performing the one check that proves ownership: that `p2tr_script_buf(scanner_key + offset * G) == output.script_pubkey`. The honest constructor `Scanner::scan_transaction` guarantees this invariant by construction, but `read` bypasses it entirely, so a `ReceivedOutput` produced from untrusted bytes is unauthenticated.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` where each script is derived as `key + offset*G` and required to be even-Y (`p2tr_script_buf`) before registration. `scan_transaction` only yields a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` hits, so the returned offset provably satisfies the spendability relation.

`ReceivedOutput::read` (lines 122–134) reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns them as a bundle. There is no verification that:

- `offset` corresponds to the `script_pubkey` (i.e., the output is spendable by `key + offset*G`),
- the `script_pubkey` is a P2TR output the scanner would ever match,
- the `outpoint` references the transaction containing `output`.

Because the type gives no way to re-derive or check the key↔offset↔script relation after deserialization, any consumer of `ReceivedOutput::read` on untrusted bytes (the prompt's in-scope surface) treats a fabricated claim of receipt as authoritative.

### Impact Explanation
A malicious counterparty supplying crafted bytes to `ReceivedOutput::read` can cause an output to be "reported received that is not spendable": the encoded `output.script_pubkey` can lock funds to an arbitrary key (or no valid key), while the claimed `offset` bears no relation to it. Downstream accounting/crediting logic that trusts `ReceivedOutput` will credit funds the Serai multisig can never sign for, and may further attempt to build `SignableTransaction`s spending a nonexistent or foreign UTXO. This is the crypto analog of "authenticated users reaching data/actions intended only for admins": the deserialized object asserts a privileged claim (ownership of funds) with no check.

### Likelihood Explanation
Reachable whenever serialized `ReceivedOutput`s transit an untrusted boundary (peer-supplied bytes, RPC-delivered data, or cross-process messages using `read`). The exploit requires only choosing arbitrary `offset`/`TxOut`/`OutPoint` bytes — no key knowledge needed — matching the low-privilege profile of the source advisory. Impact is bounded to accounting/spendability confusion rather than direct key compromise, consistent with Medium.

### Recommendation
Either bind the offset into the check at deserialization time — requiring `read` to take the scanner/`ProjectivePoint` and asserting `self.scripts`/`p2tr_script_buf(key + offset*G) == output.script_pubkey` before returning — or mark `ReceivedOutput::read` as trusted-inputs-only and route untrusted data through `Scanner::scan_transaction` on a verified `Transaction`/block instead, so ownership is proven by derivation rather than asserted by the sender.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs
// Construct bytes no Scanner would ever emit:
let fake_offset = Scalar::random(&mut OsRng);            // unrelated to our key
let fake_out = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    TweakedPublicKey::dangerous_assume_tweaked(x_only(&ProjectivePoint::random(&mut OsRng))),
  ),                                                      // locked to a stranger's key
};
let fake_outpoint = OutPoint::null();                     // references nothing

let mut bytes = fake_offset.to_bytes().to_vec();
bytes.extend(serialize(&fake_out));
bytes.extend(serialize(&fake_outpoint));

let claimed = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(claimed.value(), 1_000_000);   // "received" 1M sats
// claimed.offset() does not satisfy p2tr_script_buf(key + offset*G) == script_pubkey,
// so the output is unspendable — yet nothing rejected it.
```

Note: I was unable to fully trace every consumer of `ReceivedOutput::read` within the remaining scope, so the exact call sites feeding it untrusted bytes could not be enumerated; the vulnerability exists at the deserialization layer regardless, since `read` accepts the ownership claim without any verification.
