But at commit time, `applyPatchToIndex` in `app/src/lib/git/apply.ts` (lines 12-84) independently re-runs `getWorkingDirectoryDiff(repository, file)` (line 60) to build a *fresh* diff, and then calls `formatPatch(file, diff)` using the *stale* selection object against this newly computed diff — it never re-validates that the selection's line indices still correspond to the same content the user reviewed.

### Title
Stale line-selection re-applied to a freshly recomputed diff lets working-directory content changed between diff-render and commit be silently included/excluded from a partial commit - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop's partial-commit feature lets a user select individual lines/hunks of a file's diff to stage. The `DiffSelection` object records *which absolute diff-line indices* are selected, not the actual line content. The diff that these indices refer to is computed once, when the file is opened in the Changes view (`updateChangesWorkingDirectoryDiff`, [1](#0-0) ). When the user commits, `stageFiles` → `applyPatchToIndex` recomputes the diff from scratch via `getWorkingDirectoryDiff(repository, file)` [2](#0-1)  and feeds this brand-new diff, together with the old `file.selection` index set, straight into `formatPatch` [3](#0-2) . There is no re-validation step at that point comparing the newly fetched diff to the diff the user actually reviewed.

### Finding Description
The invariant that is broken is: "the bytes staged/committed for a partially-selected file must be exactly the bytes the user visually reviewed and selected." `formatPatch` walks `diff.hunks` and, for each line, calls `file.selection.isSelected(absoluteIndex)` [4](#0-3)  — it trusts that `absoluteIndex` still means the same thing it meant when the selection was made. If the working-directory file content changes between the time the diff was rendered in the UI (and the user picked specific lines) and the time `applyPatchToIndex` re-fetches the diff for staging, the hunk boundaries and line ordering can shift. The stale index-based selection is then applied to different lines than the ones the user actually approved, so lines the user never inspected can be silently staged and committed (or vice versa, lines the user wanted committed get silently dropped).

A parallel and existing acknowledgment of this exact risk exists in `updateChangesWorkingDirectoryDiff`, which explicitly notes: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines" [5](#0-4) , i.e. the UI itself only defends against showing stale UI state, not against staging/committing content the user never saw. That same recompute-and-reuse-stale-selection pattern is not guarded at all in the actual commit path (`apply.ts`).

The attacker primitive here is "attacker controls a cloned/fetched repository" combined with anything that can modify tracked working-directory content in the background between the render of the diff and the click of the "Commit" button — e.g., a repository-provided watch/build script (npm scripts, husky/lint-staged hooks invoked through `.git/hooks` populated from `core.hooksPath` committed in the repo, or a build tool configured in the project) that rewrites a tracked file shortly after checkout. Since Desktop does not force a synchronous, atomic "diff you approved == diff you commit" guarantee, this is a path by which the content that lands in the user's commit differs from what they explicitly reviewed and chose to include, which is exactly the "silent corruption of what the user commits" impact category.

### Impact Explanation
This can cause a user to unknowingly commit and push content they never reviewed or approved — the analog of "later withdrawals absorbing the loss" from the original report, here manifesting as "the committer absorbing hidden/unreviewed content" while believing the commit reflects only what they selected in the diff view. Depending on what the injected content is, this ranges from broken code being silently pushed to more serious supply-chain-style tampering.

### Likelihood Explanation
Exploitation requires a window between diff render and commit click during which the working directory is externally mutated, and requires the repository/tooling to trigger such a mutation (e.g. through project build scripts a user would run while working in the repo). This is a real but narrower race-condition-style path, not a fully deterministic single-click attack, so likelihood is moderate rather than trivial.

### Recommendation
Before applying `formatPatch`'s stale selection to a freshly fetched diff in `applyPatchToIndex`, verify the newly fetched diff (`getWorkingDirectoryDiff` at [2](#0-1) ) is unchanged (e.g. compare a content hash/hunk fingerprint) relative to the diff that produced `file.selection`. If it differs, abort the commit for that file and force the UI to refresh and re-prompt the user to re-review/re-select before staging, rather than silently re-applying old line indices to new content.

### Proof of Concept
1. Modify a tracked file, open it in the GitHub Desktop Changes view so the diff is rendered and cached in `changesState.selection.diff`.
2. Select only specific lines/hunks for inclusion (partial `DiffSelectionType.Partial`).
3. Before clicking "Commit", have a background process controlled by the repository (e.g. a `post-checkout`/watch script from `package.json` executed automatically) rewrite the same file, shifting or altering hunks (e.g. inserting lines above the previously selected hunk).
4. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now different) and applies the old line-index selection to it via `formatPatch`.
5. Inspect the resulting commit: it contains content from lines the user never saw/selected in the UI, while the UI still displayed the original (pre-mutation) diff as "what will be committed."
