### Title
Forwarded outputs are matched to their stored instructions solely by `(coin, amount)`, so a same-value forwarded output claims the wrong `InInstruction` - ([File: processor/src/multisigs/mod.rs])

### Summary
Serai's Bitcoin output scanning assigns identity/meaning to funds the same way Footium's `claimERC20Prize` assigns prizes: by a weak identifier that does not uniquely identify the rightful claimant. In Footium the prize leaf binds `_to`, and the intended owner (the club escrow) can never satisfy `msg.sender == _to`. In Serai, when the coordinator forwards an output during multisig rotation it stores the associated `InInstruction` under `ForwardedOutputDb`, and later retrieves it with `ForwardedOutputDb::take_forwarded_output(txn, output.balance())`, i.e. keyed only by `ExternalBalance { coin, amount }` — not by the outpoint or any output-unique identifier. Any forwarded output with the same coin and amount "claims" the stored instruction, regardless of which actual output it belonged to.

### Finding Description
During rotation, `ScannerEvent::Block` handling iterates outputs of kind `OutputType::Forwarded` and resolves each one's instruction via:

```rust
// processor/src/multisigs/mod.rs
for output in &outputs {
  if output.kind() != OutputType::Forwarded { continue; }
  if let Some(instruction) = ForwardedOutputDb::take_forwarded_output(txn, output.balance()) {
    instructions.push(instruction);
  }
}
```

`output.balance()` is `ExternalBalance { coin: ExternalCoin::Bitcoin, amount: Amount(value) }` (`processor/src/networks/bitcoin.rs:128-130`). Nothing in this lookup binds the instruction to the output's `OutPoint`, the scanning offset, or `Output::id()` — even though `Output::id()` exists precisely to uniquely identify an output (`processor/src/networks/bitcoin.rs:92-104`) and the code deliberately notes Monero uses the output key as ID "to ensure we won't be susceptible to the burning bug" (`processor/src/networks/monero.rs:57`).

The Forwarded address is publicly derivable by any unprivileged party: `forward_address` computes `key + G * hash_to_F("Serai Bitcoin Output Offset", "forward")` (`processor/src/networks/bitcoin.rs:308-344, 671-674`), so an attacker can craft a Bitcoin transaction paying the Forwarded script any amount they choose. `scan_transaction` will classify it as `Forwarded` purely from the `script_pubkey` match (`networks/bitcoin/src/wallet/mod.rs:199-214`), and `get_outputs` maps it via `kinds[offset]` (`processor/src/networks/bitcoin.rs:686-700`).

Because `take_forwarded_output` matches only on `(coin, amount)`, an attacker who broadcasts a forwarded output with the same satoshi value as a legitimate pending forward causes a collision: whichever forwarded output is processed first in `outputs` iteration order consumes the stored `InInstruction`, and the other output's `take` returns `None`, so no instruction is emitted for it.

### Impact Explanation
The legitimate forwarded output is permanently disassociated from its `InInstruction` — e.g., the embedded transfer/refund/mint semantics the depositor encoded are never emitted to the protocol, while the attacker's identically-valued output executed an instruction that was never theirs. This is the direct analog of Footium's bug class: value arrived at the right vault but its claim was bound to an identifier (here: the amount) that fails to distinguish the rightful claimant. The victim's forwarded funds are swept to the new multisig with no instruction, producing a received-but-unactionable state (loss of the instruction's effect, e.g. a refund never issued or a mint never credited).

### Likelihood Explanation
Medium likelihood: exploitation requires a pending forwarded output whose amount the attacker can observe (amounts are public on-chain / in the plan that registered the instruction), plus broadcasting a matching-amount payment to the publicly-computable Forwarded address before or in the same block. Both steps require only standard Bitcoin transactions from public inputs. During rotation windows (`RotationStep::ForwardFromExisting`, `processor/src/multisigs/mod.rs:843-899`), multiple forwards are processed together, making equal-amount collisions plausible even without an attacker when two users forward identical amounts.

### Recommendation
Key `ForwardedOutputDb` by the output's unique identity (`Output::id()` / outpoint) rather than `ExternalBalance`, and store a pending-instruction marker at registration so duplicate `(coin, amount)` forwarded outputs cannot silently steal or drop another output's instruction. At minimum, the DB should reject or disambiguate registration of two forwards with identical balances.

### Proof of Concept
1. A coordinator enters `RotationStep::ForwardFromExisting`. A legitimate deposit output O1 (amount `v`) is forwarded; `ForwardedOutputDb` stores `InInstruction` I under key `{Bitcoin, v}`.
2. Attacker observes `v` and the Forwarded address (computable from `hash_to_F(KEY_DST, b"forward")` and the public group key), and broadcasts a TX paying `v` to the Forwarded script — creating O2 with identical `balance()`.
3. `get_outputs` returns both O1 and O2 as `OutputType::Forwarded`. In `scanner_event_to_multisig_event`, the first-processed output `take`s I; the second's `take_forwarded_output` returns `None` — so I is emitted once (potentially bound to the attacker's output) and the legitimate output's instruction is silently dropped, leaving O1's forwarded funds with no associated instruction.

Note: I verified the `take_forwarded_output(txn, output.balance())` call site and the balance/`id`/scanning plumbing; I could not read `ForwardedOutputDb`'s internal key type in the remaining iterations, so the collision relies on the observable fact that only `output.balance()` is passed as the lookup key.
