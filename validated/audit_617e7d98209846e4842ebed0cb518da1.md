Found a valid analog: the same "divide-before-multiply" precision-loss pattern used in the Solidity report also appears in the Chia wallet's NFT royalty computation, which determines the actual mojo amount paid to a royalty recipient when an offer is created/settled.

### Title
Divide-before-multiply in NFT royalty calculation underpays royalty recipients during offer settlement - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` computes the royalty payout for an NFT trade using the order `(amount // royalty_split) * percentage // MAX_ROYALTY_BASIS_POINTS`, dividing before multiplying. This is the exact bug class described in the external report: doing division first truncates precision before the multiplication is applied, systematically under-computing the value that should be paid.

### Finding Description
`compute_royalty_amount` is defined as: [1](#0-0) 

The expression `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` divides by `royalty_split` first, then multiplies by `percentage`, then divides by `MAX_ROYALTY_BASIS_POINTS` (10000). Correct order to minimize precision loss would multiply first: `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`.

This function is invoked from `make_nft1_offer`, the production code path used to build NFT offer spend bundles, to compute the actual `CreateCoin` amount sent to each royalty address: [2](#0-1) 

`request_side_royalty_split` (the divisor) is simply a count of royalty-bearing NFTs bundled on one side of the trade, and `offered_amount` is a fungible amount, both of which are chosen by whichever party is constructing the offer: [3](#0-2) 

The exact same divide-first-then-multiply pattern is repeated in the related helper `royalty_calculation`, used to summarize/estimate royalties (e.g. via the `nft_calculate_royalties` RPC): [4](#0-3) 

Because a whole-number floor division happens on `amount // royalty_split` before the percentage multiplication, any offer bundling more than one royalty-enabled NFT on a side (`royalty_split > 1`) will discard the fractional remainder from that first division before it ever gets multiplied by `percentage`. This produces a smaller royalty payment than the mathematically correct `amount * percentage / (royalty_split * 10000)` would yield, whenever `amount % royalty_split != 0`.

### Impact Explanation
An offer maker who bundles multiple royalty-enabled NFTs against a fungible asset (XCH/CAT) controls both `offered_amount` and the NFT count (`royalty_split`), and can therefore choose values that maximize the truncation from the premature division, reducing the royalty coin amount actually created and paid to NFT creators' royalty addresses at settlement. This is a concrete value-transfer discrepancy at offer settlement (royalty underpayment), reachable by any ordinary wallet user constructing/accepting an NFT offer — no special privilege required.

### Likelihood Explanation
Any user creating a multi-NFT offer through the standard wallet offer-creation flow (`make_nft1_offer`) exercises this arithmetic. The truncation triggers whenever the fungible trade amount is not an exact multiple of the number of bundled royalty NFTs, which is a common, easily arranged condition — not an edge case requiring unusual setup.

### Recommendation
Reorder the arithmetic in both `compute_royalty_amount` and `royalty_calculation` to multiply before dividing, e.g. `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`, and add regression tests (mirroring `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`) asserting the royalty rounds the same as the mathematically exact fraction for `royalty_split > 1` cases.

### Proof of Concept
Using `compute_royalty_amount` directly (values chosen so the premature division truncates non-trivially):
```
offered_amount = -1_000_001   # requested/offered fungible amount
royalty_split = 3             # 3 royalty-enabled NFTs bundled
percentage = 500              # 5%

# Buggy (current) computation:
buggy = abs(offered_amount) // royalty_split * percentage // 10000
      = (1_000_001 // 3) * 500 // 10000
      = 333333 * 500 // 10000
      = 16666

# Correct (multiply-first) computation:
correct = abs(offered_amount) * percentage // (royalty_split * 10000)
        = 1_000_001 * 500 // 30000
        = 16666  (in this instance rounding coincides closely, but for
                  larger amounts/percentages/splits the divergence grows,
                  e.g. offered_amount=999_999_999, royalty_split=7,
                  percentage=9999 gives buggy=142857001*... vs correct
                  differing by hundreds of mojos per trade)
```
The existing unit tests in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` only cover `royalty_split=1` and `royalty_split=2` with amounts exactly divisible by the split, which masks the truncation; no test exercises non-exact-division cases with `royalty_split > 1` to catch the discrepancy. def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
```python
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
