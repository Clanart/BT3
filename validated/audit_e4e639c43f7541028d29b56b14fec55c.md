### Title
Trampoline credential-helper accepts credential requests for an arbitrary host with no binding to the git operation's actual remote - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Seaport bug's root cause is that a privileged callback (`validateOrder`) trusted attacker-supplied "extra data" (the encoded stack) without checking that it actually corresponded to the `collateralId`/lien being settled. GitHub Desktop has a structurally identical pattern in its git trampoline: the trampoline TCP server hands out real GitHub credentials to any process that can connect to it and send a `CREDENTIALHELPER get` command with attacker-chosen `host`/`protocol` fields, and the only check performed is that the presented `DESKTOP_TRAMPOLINE_TOKEN` is *some* currently active token — never that the requested host matches the repository/remote that the specific git operation identified by that token is actually authenticating against.

### Finding Description
When Desktop runs a git command, `withTrampolineEnv` in [1](#0-0)  allocates a short-lived `DESKTOP_TRAMPOLINE_TOKEN` and injects it, along with `DESKTOP_PORT` (the trampoline server's TCP port) and `credential.helper=desktop`, into the environment of the spawned `git` process. Because these are plain environment variables set on the process, they are inherited by every child process that `git` spawns during that operation - including repository-controlled hooks and filters (e.g. `post-checkout`, `post-merge`, smudge/clean filters configured via `.gitattributes`) that live inside a cloned/fetched repository.

On the server side, `TrampolineServer.processCommand` in [2](#0-1)  only verifies `isValidTrampolineToken(command.trampolineToken)` - i.e. that the token belongs to the set of tokens currently outstanding for *some* in-flight git operation [3](#0-2) . It never checks that the specific host/credential being requested corresponds to the remote that operation is actually contacting.

The `CREDENTIALHELPER` handler then resolves the request purely from attacker-suppliable fields. `getCredentialUrl` builds the target endpoint directly from the `host`/`protocol`/`path` (or `url`) keys of the credential-protocol payload with no cross-check against the repository's configured remote [4](#0-3) , and `getCredential`/`getGitHubCredential` look up a stored `Account` purely by endpoint origin and, if found, returns the account's real OAuth token: [5](#0-4) [6](#0-5) .

This is the same broken invariant as the Seaport bug: a privileged operation ("give out a secret/credential" ~ "settle a lien") is driven entirely by data supplied by an untrusted party (the credential request fields ~ the encoded stack) without verifying that data is actually tied to the context/session the caller is supposed to be limited to (the specific remote git is talking to ~ the specific `collateralId`).

### Impact Explanation
A malicious repository (cloned, fetched, or opened by the victim) can define a git hook or LFS/`.gitattributes` filter that runs as a subprocess of any Desktop-invoked git command against that repo. That hook process inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its environment and can open a raw TCP connection to the trampoline server, issuing a `CREDENTIALHELPER get` request with `host=github.com` (or any GHE endpoint the victim has signed into), regardless of what remote the actual git operation targeted. Because the server only validates that the token is "currently active," it returns the victim's real GitHub OAuth token to the malicious hook process, which can exfiltrate it over the network - full account/credential compromise, satisfying the "credential/token exfiltration" impact category via a "cloned/fetched repository" attacker vector.

### Likelihood Explanation
The trigger requires no unnatural user action beyond the normal Desktop workflow of cloning/fetching/checking out a repository that defines a hook or clean/smudge filter (a capability that untrusted repositories legitimately have, e.g. via `.git/hooks` populated post-clone from a bundled setup script, or `.gitattributes` filters combined with local git config commonly auto-configured by tools like Git LFS). No admin rights, no pre-existing malware, and no social engineering beyond "user opens/clones a repo" are needed, matching the report's threat model of an attacker who "controls a cloned/fetched repository."

### Recommendation
Bind each `DESKTOP_TRAMPOLINE_TOKEN` to the specific remote/host(s) that the associated git invocation is expected to authenticate against (recorded when `withTrampolineEnv`/`trampolineEnvironmentPath` is set up), and have `trampoline-server.ts`/`trampoline-credential-helper.ts` reject `CREDENTIALHELPER` requests whose `host`/`protocol` do not match the operation's expected remote for that token, analogous to requiring `stack.lien.collateralId == collateralId` in the Seaport fix. At minimum, do not resolve GitHub-account credentials for arbitrary requested hosts using only token liveness as the check.

### Proof of Concept
Conceptual (not executed, based on static code review):
1. Attacker publishes a repo with a `post-checkout` hook (or a clean/smudge filter declared in `.gitattributes`) that is an executable script.
2. Victim, signed into github.com in Desktop, clones/fetches this repo. Desktop invokes `git` via `withTrampolineEnv`, setting `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` in the child process environment [7](#0-6) .
3. Git invokes the malicious hook/filter as a subprocess, inheriting those env vars.
4. The hook connects to `127.0.0.1:$DESKTOP_PORT`, sends a trampoline `CREDENTIALHELPER` command with parameter `get` and stdin `protocol=https\nhost=github.com\n\0`, using the inherited `DESKTOP_TRAMPOLINE_TOKEN`.
5. `TrampolineServer.processCommand` accepts it because the token is valid [2](#0-1) ; `createCredentialHelperTrampolineHandler` resolves `getGitHubCredential` and returns the victim's stored OAuth token for github.com [8](#0-7) .
6. The hook exfiltrates the returned token.

Note: I was not able to directly execute this PoC or inspect the hook-invocation/env-inheritance code path (`app/src/lib/hooks/with-hooks-env.ts`) in full within the tool budget, so whether Desktop applies any additional environment sanitization specifically for hooks (as opposed to filters) could not be fully confirmed from the index; this should be verified in a live/dev build before treating this as a confirmed exploit.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

    if (!isValidTrampolineToken(command.trampolineToken)) {

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
