### Title
Governance-privileged `onAccept` branches in `IntentGatewayV2`/`ExtrinsicIntents` authenticate only `request.source`, not `request.from`, allowing any Hyperbridge-runtime pallet to forge `UpgradeContract`/`SweepDust`/`UpdateParams`/`NewDeployment` — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` gates its privileged branches (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`) with a single check: `keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())`. This mirrors the RestrictionManager bug pattern — it validates only one side of the sender identity (the chain, i.e., "source") and never validates the other side (the specific module/pallet, i.e., "from") that is supposed to be the sole authority allowed to issue these commands.

### Finding Description
`_authenticate()` (used for `RedeemEscrow`/`RefundEscrow`) correctly checks both `request.source` (chain) *and* `request.from` (module address) against the registered gateway instance: [1](#0-0) 

But the privileged branch that follows checks only the chain identity: [2](#0-1) 

`request.source` is guaranteed by the ISMP host to equal the dispatching chain's own `host_state_machine()` — it is not, and cannot be, forged by a module. However `request.from` is fully attacker-controlled by whichever pallet calls `dispatch_request`, because `pallet-ismp`'s dispatcher copies `dispatch_post.from` through unchanged: [3](#0-2) 

Any pallet on the Hyperbridge/Nexus or Gargantua runtime that has a `dispatch_request` capability (this is a generic, non-privileged capability exposed to arbitrary pallets, as demonstrated by `pallet-demo`'s `dispatch_to_evm`) can set `from` to any bytes it likes: [4](#0-3) 

Since `ExtrinsicIntents.onAccept`'s governance gate never inspects `request.from`, a message dispatched from *any* pallet on the Hyperbridge chain — not just the intended TokenGovernor/governance module — satisfies `request.source == hyperbridge()` and is treated as an authenticated governance instruction. This lets an unprivileged pallet (or, on Gargantua/other permissionless demo runtimes, potentially any signed extrinsic routed through such a pallet) forge:
- `UpgradeContract` → arbitrary implementation takeover of the proxy (`ERC1967Utils.upgradeToAndCall`),
- `SweepDust` → drain accumulated protocol dust to an attacker beneficiary,
- `UpdateParams` → rewrite fee/host parameters,
- `NewDeployment` → register a malicious "gateway instance" for a chosen state machine, which then passes `_authenticate()`'s `from`-check for future `RedeemEscrow`/`RefundEscrow` messages, enabling theft of all escrowed order inputs on that chain pair.

### Impact Explanation
`UpgradeContract` gives complete code-execution/ownership takeover of the `IntentGatewayV2` proxy — the contract that custodies user order escrow across every configured EVM chain. `NewDeployment` further compounds into unauthorized settlement: once a forged "gateway instance" is registered for a target chain, subsequent `RedeemEscrow`/`RefundEscrow` messages that pass `_authenticate()` will release real escrowed user funds to an attacker-chosen beneficiary. This satisfies the bounty's "unauthorized execution," "false state acceptance," and "stealing or loss of funds" categories, and requires no compromised relayer, prover, or admin key — only an unprivileged pallet's ability to call the standard `dispatch_request` API, which is broadly available runtime-wide.

### Likelihood Explanation
Likelihood depends on whether any deployed runtime (Nexus, Gargantua, or a future parachain integration) exposes a pallet with unrestricted `dispatch_request` access to end users/permissionless callers alongside `IntentGatewayV2`/`ExtrinsicIntents` deployments trusting `hyperbridge()`-only checks. `pallet-demo` in this repo demonstrates the pattern is already present and callable by any signed origin (`ensure_signed`) with attacker-chosen `from`. If any similarly permissive pallet coexists on the same chain configured as the IntentGateway's registered `hyperbridge()` coprocessor/source chain, the attack is directly reachable by an unprivileged, unsigned-by-governance actor.

### Recommendation
Change the governance authentication in `ExtrinsicIntents.onAccept` to validate both fields, mirroring `_authenticate()`: require `request.from` to equal the specific, registered TokenGovernor/governance module ID/address on the Hyperbridge chain, in addition to `request.source == hyperbridge()`. Additionally, restrict `IsmpDispatcher::dispatch_request` at the runtime level so that only privileged/whitelisted pallets can set `from` to reserved governance module identifiers, or have the host itself stamp `from` based on the calling pallet's own account/module ID rather than trusting caller-supplied bytes.

### Proof of Concept
1. Deploy any generic pallet with `dispatch_request` access on the same runtime configured as the `hyperbridge()` coprocessor for a deployed `IntentGatewayV2`/`ExtrinsicIntents` instance (e.g., `pallet-demo`'s `dispatch_to_evm`, or any custom pallet using `T::IsmpHost::dispatch_request`).
2. Craft a `DispatchPost` with:
   - `dest`: the EVM chain hosting the target `IntentGatewayV2` proxy,
   - `to`: the `IntentGatewayV2` proxy address,
   - `from`: arbitrary bytes (no restriction enforced),
   - `body`: `bytes1(uint8(RequestKind.UpgradeContract)) || abi.encode(maliciousImpl, initCalldata)`.
3. Dispatch via any signed extrinsic; the host sets `source = host_state_machine()` (the Hyperbridge/Nexus chain), satisfying the only check in `onAccept`.
4. Once relayed and delivered, `onAccept` executes `ERC1967Utils.upgradeToAndCall(maliciousImpl, initData)` because `keccak256(request.source) == keccak256(hyperbridge())` — full contract takeover achieved without any governance approval.
