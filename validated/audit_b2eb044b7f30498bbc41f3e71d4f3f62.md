### Title
Panic on out-of-range Participant index in PedPoP blame evaluation causes node crash / DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2024-38477 (a malicious request reaching an unhandled null dereference and crashing the server), Serai's PedPoP blame/decryption path performs unchecked `HashMap` indexing with attacker-influenced `Participant` values. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]`; both panic on a missing key. `Participant::new` only rejects zero, so any nonzero `u16` — including indexes `> n` — is accepted, and an accusation naming a non-existent participant crashes the process instead of returning an error.

### Finding Description
- `AdditionalBlameMachine::blame` / `BlameMachine::blame` accept `sender` and `recipient` directly from an accusation (an authenticated message whose *contents* — the two indexes and the ciphertext/proof — are supplied by the accusing party). No bounds check against `params.n` or the registered sets is performed.
- In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:582`), `decrypt_with_proof(sender, recipient, msg, proof)` is called; inside it (`crypto/dkg/pedpop/src/encryption.rs:388`) the DLEq verification uses `self.enc_keys[&decryptor]`. `enc_keys` only contains the participants registered in `Decryption::register` (indexes `1..=n`); a `decryptor` outside that set panics on `HashMap` index.
- If a proof is absent, or the earlier PoP verification fails, `blame_internal` later evaluates `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) with `sender` fully attacker-chosen — same panic for `sender ∉ 1..=n`.
- `Participant::new` only enforces non-zero, so `Participant(n + 1)`, `Participant(0xFFFF)`, etc. all deserialize cleanly and reach these indexes.
- This is a reachable panic (Rust's analog of the null dereference): instead of returning `PedPoPError`/`DecryptionError`, the thread panics, aborting the DKG/blame evaluation and crashing the host process handling accusations.

### Impact Explanation
A participant (or anyone able to submit an accusation carrying `sender`/`recipient` fields) can deterministically crash every node that evaluates the blame claim by naming a participant index outside `1..=n`. In a validator/coordinator setting this is a remote, single-message denial of service against nodes processing blame proofs — matching the High-severity crash-DoS class of the reference advisory.

### Likelihood Explanation
The blame API is explicitly public (`AdditionalBlameMachine::new` is usable even by non-members) and takes the attacker-supplied indexes verbatim. Triggering requires only choosing an out-of-range `Participant`, which is a one-field change to an otherwise normal accusation message. No race, timing, or collusion is needed.

### Recommendation
Validate `sender` and `recipient` against the registered set (or `params.n`) at the top of `blame`, `blame_internal`, and `decrypt_with_proof`, returning a `PedPoPError`/`DecryptionError` (or a defined "accuser is faulty" verdict) instead of indexing. Replace `map[&p]` lookups with `map.get(&p).ok_or(...)` so malformed accusations can never panic.

### Proof of Concept
```rust
// Conceptual: DKG ran with n participants; an accusation arrives naming
// recipient = Participant(n + 1) (or sender = Participant(0xFFFF)).
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();
let bad = Participant::new(n + 1).unwrap(); // only zero is rejected
machine.blame(good_sender, bad, msg, Some(proof));
// -> panics at encryption.rs:388 on self.enc_keys[&decryptor]
// or, without a valid PoP, at lib.rs:599 on self.commitments[&sender]
```
