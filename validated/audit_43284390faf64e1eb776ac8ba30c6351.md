### Title
Missing authorization check in output scanning allows unprivileged parties to inject outputs classified as internal protocol outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Jenkins bug (CVE-2023-46652, CWE-862) is a missing permission check that lets an unprivileged party enumerate internal identifiers (credentials IDs) and weaponize them. The analog in Serai: the Bitcoin `Scanner` classifies every transaction output solely by `script_pubkey`, with no check that the paying transaction is a protocol-authorized one. The internal "identifier space" — the Branch, Change, and Forwarded offset scripts — is fully enumerable by anyone who knows only the public group key, because the offsets are deterministic: `Secp256k1::hash_to_F("Serai Bitcoin Output Offset", b"branch"/"change"/"forward")`. An unprivileged attacker can therefore craft a transaction paying directly to a reserved internal script, and `Scanner::scan_transaction` / `get_outputs` will report it as a received output of that internal `OutputType`.

### Finding Description
`Scanner::new` and `Scanner::register_offset` build a `scripts: HashMap<ScriptBuf, Scalar>` map keyed purely by the P2TR script. `scan_transaction` reports any output whose `script_pubkey` is in that map, unconditionally:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
``` [1](#0-0) 

The reserved internal scripts are registered with deterministic, publicly computable offsets: [2](#0-1) 

Since `hash_to_F` over a constant DST and constant labels applied to the *public* group key requires no secret, any observer of the Serai deposit address can enumerate all reserved script identifiers and produce outputs matching them. `get_outputs` then labels the attacker-created output with the corresponding `OutputType` (`kinds[offset_repr_ref]`): [3](#0-2) 

There is no check — analogous to the missing permission check — that an output claiming an internal kind was produced by a transaction the protocol itself authorized (e.g., an actual rotation branch output or actual change), nor any contextual binding (amount, sibling outputs, in-transaction data) distinguishing legitimate internal outputs from attacker-injected ones.

### Impact Explanation
Attackers can inject outputs that Serai reports as internal protocol outputs rather than external deposits. Concretely: a crafted payment to the Forwarded offset script is reported as an `OutputType::Forwarded` output, triggering forwarding/accounting logic for funds the protocol never authorized as forwards; a payment to the Branch script is reported as a rotation branch output, corrupting the set of outputs attributed to key rotation. This produces outputs "received" under false classification — funds reported under an internal category that the downstream spend/rotation logic will attempt to consume under wrong assumptions (e.g., a fake Branch output mixes with genuine rotation funds, or a fake Forwarded output triggers a forward with attacker-influenced provenance). It mirrors the Jenkins flaw: unauthenticated enumeration of an internal identifier space followed by injection that downstream logic treats as authorized.

### Likelihood Explanation
The attack requires only the public group key (visible in the deposit address) and the ability to send a standard P2TR Bitcoin transaction — a low-privilege, fully public-input attack. Success is deterministic since the offsets are fixed constants per key.

### Recommendation
Bind internal-kind outputs to protocol-authorized context: e.g., require that outputs resolving to the Branch/Change/Forwarded offsets only be accepted from transactions the protocol initiated (track expected txids/script+amount pairs), or derive per-transaction/per-purpose randomized offsets (as `register_offset` already supports and its docs warn must be "securely generated") instead of globally enumerable constant offsets. At minimum, authenticate forwarded/branch outputs against expected internal state before classification.

### Proof of Concept
1. Observe Serai's group key `K` from its P2TR deposit address.
2. Compute `forward_offset = hash_to_F("Serai Bitcoin Output Offset", b"forward")` (incremented for even-Y parity per `register_offset`) and derive `forward_script = p2tr_script_buf(K + G*forward_offset)` — no secret required.
3. Broadcast a transaction paying ≥ dust to `forward_script`.
4. `Bitcoin::get_outputs` scans the block, `scanner.scan_transaction` matches the script, `kinds[offset]` resolves to `OutputType::Forwarded`, and the attacker's output is emitted as a protocol-internal forwarded output — despite the transaction never being authorized by Serai. The same applies to `b"branch"` and `b"change"`.

Caveat: the exact downstream harm depends on how the processor consumes `OutputType::Branch`/`Forwarded` outputs (code in `processor/src` was outside the in-scope crates); the demonstrated, in-scope fact is the missing authorization check that lets unauthenticated transactions mint internally-classified `ReceivedOutput`s, which is the direct analog of the reported bug class.
