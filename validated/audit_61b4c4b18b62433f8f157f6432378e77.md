### Title
`ReceivedOutput::read` accepts attacker-crafted `(offset, TxOut, OutPoint)` triples with no consistency check, reporting unspendable/mismatched outputs as owned funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The referenced CVE class is "attacker-controlled data drives unintended behavior due to missing validation at a trust boundary." The analog in `bitcoin-serai` is `ReceivedOutput::read`, which deserializes an `offset` scalar, a `TxOut`, and an `OutPoint` from untrusted bytes and returns a `ReceivedOutput` that is treated as a spendable output owned by the multisig — without ever verifying that `output.script_pubkey` equals `p2tr_script_buf(key + G*offset)` for the wallet's key, or that the outpoint/output pair correspond to anything real. [1](#0-0) 

### Finding Description
`ReceivedOutput` is the value type the wallet uses to represent a spendable output. Its invariants are normally established by `Scanner::scan_transaction`, which only constructs a `ReceivedOutput` after matching `output.script_pubkey` against registered `script -> offset` entries, guaranteeing the output pays to `key + G*offset`. [2](#0-1) 

`ReceivedOutput::read` bypasses this entirely. It performs `Secp256k1::read_F` for the offset and `consensus_decode` for the `TxOut` and `OutPoint`, then constructs the struct with no cross-field validation. [3](#0-2)  Any attacker who can feed bytes into this reader (e.g., a relayed/persisted output record, an untrusted payload in the processing pipeline) can fabricate a `ReceivedOutput` claiming arbitrary value and arbitrary ownership.

The spending path then trusts the stored `offset`: `SignableTransaction` derivation signs with `key.offset(output.offset())`, and the produced signature is only valid if the input's `script_pubkey` matches the tweaked key. A crafted `(offset, script_pubkey)` mismatch produces an output the system believes it owns and will try to spend, but whose witness will never verify — or worse, an output at a real outpoint belonging to a third party that gets counted as received balance.

### Impact Explanation
Funds can be reported as received that are not spendable: the library will carry the forged output's `value()` into balance accounting and attempt to spend it, but the crafted script/offset pairing makes the spend impossible. Conversely, a fabricated `ReceivedOutput` naming an honest outpoint but a wrong `offset` causes signing failures or signing under a key that does not match the input — deadlocking funds or corrupting accounting. This matches the accepted impact class "funds reported received that are not spendable" without requiring malicious validators or leaked keys — only attacker-controlled bytes reaching `ReceivedOutput::read`.

### Likelihood Explanation
Reachability is bounded by wherever serialized `ReceivedOutput` records cross a trust boundary (replicated state, message passing, recovery from storage populated from external data). No secret material is required from the attacker, and no cryptographic hardness assumption is broken — the defect is a pure missing-invariant check at deserialization, directly mirroring the CVE's "crafted input → unintended behavior" class. Rated Medium: integrity of received-funds reporting is corrupted, but no key or nonce material is exposed.

### Recommendation
`ReceivedOutput` should carry (or be reconstructible against) the owning key, and deserialization should re-derive `p2tr_script_buf(key + G*offset)` and reject bytes whose `script_pubkey` does not match, restoring the invariant `Scanner::scan_transaction` enforces. If the key is unavailable at read time, add a separate `verify(key)` step that callers must run before treating a deserialized output as spendable.

### Proof of Concept
1. Craft bytes: `offset = Scalar::ZERO`, `TxOut { value: 21_000_000_000_0000, script_pubkey: <attacker's P2TR script> }`, `outpoint` = any confirmed outpoint.
2. `ReceivedOutput::read` returns `Ok` with `value()` reporting the full amount and `offset()` `ZERO`. [3](#0-2) 
3. Passing it to `SignableTransaction::new(vec![forged], ...)` signs with `key.offset(ZERO)` = the untweaked multisig key, which does not control the attacker's script — the input is permanently unspendable yet was booked as received funds.

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
