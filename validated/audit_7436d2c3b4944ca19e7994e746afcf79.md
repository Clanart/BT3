## Analysis

The Curve report's broken invariant is: **user-supplied swap "route" data is executed in a shared custody context without being restricted to the tokens that belong to that specific operation, so any token balance sitting in that shared context can be swept out by an unrelated, unprivileged actor.**

The local analog in Hyperbridge is the Intent Gateway's `CallDispatcher`-based calldata execution for order outputs.

`order.output.call` is arbitrary, user-supplied calldata (set at `placeOrder` time by the order creator) that gets executed from a **single, governance-configured, shared** `CallDispatcher` contract (`_params.dispatcher`), used by every order on the gateway: [1](#0-0) 

`CallDispatcher.dispatch` places no restriction whatsoever on the target contract or the calldata selector — it only checks that `to` has code, then blindly executes `to.call{value: call.value}(call.data)`: [2](#0-1) 

Because the dispatcher is shared and persistent across all orders/users (it's a single deployment referenced by `_params.dispatcher`, not a fresh per-order contract), and because `_execute`'s own sweep only collects dust for tokens explicitly listed in `order.output.assets` for that particular fill — the code's own comment acknowledges "any residual token balances left on the dispatcher are swept back" as an expected, recurring condition: [3](#0-2) 

This mirrors the Curve bug exactly: the vault's reward tokens sit in a context that the trade adaptor doesn't validate is scoped to `trade.sellToken`; here, whatever token balance transiently or permanently sits on the shared `CallDispatcher` isn't validated to belong to the calling order, and the calldata that runs there is completely unconstrained.

### Title
Unrestricted arbitrary calldata execution from the shared IntentGateway CallDispatcher allows a malicious order to plant a persistent token approval and drain dust/residual balances belonging to other orders - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._execute` runs attacker-controlled `order.output.call` bytes through a single, gateway-wide `CallDispatcher` instance shared by every user/order on the IntentGateway. `CallDispatcher.dispatch` performs `to.call(data)` with no allowlist of targets or selectors. A malicious order creator can embed a call that grants themselves an unlimited ERC20 `approve` from the `CallDispatcher`'s own address. Because the dispatcher is a long-lived shared contract, any token balance that later lands on it — including dust intentionally left behind by other orders' composable calldata (per the code's documented "residual token balances" sweep pattern) — becomes freely drainable by the attacker via a plain `transferFrom`, with no relayer, prover, or privileged role involved.

### Finding Description
1. `placeOrder` lets any user supply `order.output.call`, executed later by `_execute` via `ICallDispatcher(dispatcher).dispatch(order.output.call)` [4](#0-3) .
2. `dispatcher` is read from `_params.dispatcher`, a single governance-configured address shared by all orders on the gateway — not scoped per order or per user.
3. `CallDispatcher.dispatch` executes each `Call{to, value, data}` with only an `extcodesize(to) != 0` check; there is no restriction that `to` be a known router/DEX or that `data` avoid state-mutating approval/transfer selectors [5](#0-4) .
4. An attacker's order can therefore include `Call{to: TOKEN, data: approve(attacker, type(uint256).max)}`. Since the call is made `from` the `CallDispatcher` (msg.sender = dispatcher), this grants the attacker a persistent allowance to pull `TOKEN` out of the dispatcher at any future time.
5. `_execute`'s own sweep step only sweeps balances for tokens listed in **that order's** `order.output.assets` array, back to the gateway (`address(this)`), not to the attacker [6](#0-5) . Any token balance the dispatcher accumulates that isn't one of that specific order's declared output tokens is left unswept indefinitely on the shared dispatcher.
6. Combined with the pre-planted unlimited approval, the attacker can later call `TOKEN.transferFrom(dispatcher, attacker, balance)` directly (no interaction with the IntentGateway needed) to steal whatever residual/dust balance of that token accumulates on the dispatcher from any other order's calldata execution over time.

This is a direct structural analog to the Curve `EXACT_IN_BATCH` bug: an unvalidated, user-supplied execution payload (`data.route` / `order.output.call`) runs inside a shared custody context that also holds tokens unrelated to the caller's own operation, and nothing restricts the payload to only touching the caller's own designated tokens.

### Impact Explanation
This allows an unprivileged, malicious order creator to permanently compromise a shared protocol contract (`CallDispatcher`) and later steal ERC20 tokens that accumulate on it from completely unrelated orders/users — unauthorized transfer of funds that do not belong to the attacker, matching the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" categories. No malicious relayer, prover, or admin is required — the entire attack is executed through the public `placeOrder`/`fillOrder` entrypoints available to any address.

### Likelihood Explanation
Likelihood depends on the CallDispatcher actually accumulating meaningful dust from legitimate composable fills (the docs explicitly describe solvers "routing through DEXes, lending protocols, or other DeFi primitives" via this same dispatcher, and the code's own comments treat residual dispatcher balances as an expected, recurring event). Given that composability is an advertised feature of `order.output.call`, and the dispatcher's `dispatch` function has no allowlisting, planting an approval is trivial and low-cost (one `placeOrder` call with a single-output, low-value order to keep escrow costs minimal).

### Recommendation
- Restrict `CallDispatcher.dispatch` targets to a governance-maintained allowlist of routers/contracts, and/or disallow `approve`/`increaseAllowance`-style selectors entirely.
- Deploy a fresh, ephemeral `CallDispatcher` (e.g., via `CREATE2` per order/fill) instead of a single shared instance, so no state or approvals can persist across unrelated orders.
- In `_execute`, revoke any approvals the dispatcher may have granted during `order.output.call` before returning control, or snapshot and diff the dispatcher's full token/ETH balance instead of only sweeping tokens declared in `order.output.assets`.

### Proof of Concept
1. Attacker calls `placeOrder` with a minimal, cheap order whose `output.call` contains a single `Call`: `{to: TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)}`.
2. Attacker (or any solver) calls `fillOrder` for this order; `_fillSameChain`/`_fillCrossChain` invokes `_execute`, which calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` — executing the `approve` from the dispatcher's context [4](#0-3) .
3. At any later time, when `TOKEN` balance accumulates on the shared `dispatcher` from any other order's composable `output.call` execution (and that balance isn't part of the triggering order's own `output.assets`, so `_execute`'s sweep skips it), attacker calls `TOKEN.transferFrom(dispatcher, attacker, TOKEN.balanceOf(dispatcher))` directly — no interaction with the IntentGateway required — draining funds that belong to the protocol/other users.

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
