### Title
Attacker-controlled beneficiary can permanently block cross-chain escrow settlement in `IntentGatewayV2` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` pays out escrowed native tokens with a raw `.call{value: amount}("")` and reverts the entire withdrawal (including any co-bundled ERC20 releases and fee payout) if that call fails. This is the exact bug class from the external report: an attacker who controls the `beneficiary` address of an ISMP-delivered `RedeemEscrow`/`RefundEscrow` message can pre-deploy a contract with a togglable `receive()`, let escrow accumulate against it, then flip the contract to reject ether right before a relayer submits the proof that triggers payout — bricking settlement of that commitment.

### Finding Description
`_withdraw` is the shared internal function used by both `IntrinsicIntents` and `ExtrinsicIntents` to release escrow to a `beneficiary` derived from an untrusted `WithdrawalRequest.beneficiary` field (attacker-supplied `order.user`, or the filler's own address for `RedeemEscrow`): [1](#0-0) 

For native-token entries (`token == address(0)`), a failed `.call` immediately reverts with `InsufficientNativeToken()`, unwinding the *entire* loop — including any other tokens already scheduled for release in `body.tokens` and the transaction-fee payout that follows. This is invoked cross-chain via the `RedeemEscrow` path in `ExtrinsicIntents.sol` (filler becomes the beneficiary receiving back their own escrowed input) and via `RefundEscrow` (order creator becomes the beneficiary on cancellation): [2](#0-1) [3](#0-2) 

Critically, the codebase already demonstrates the correct mitigation elsewhere: `WrappedHyperFungibleToken.sol`'s `onAccept`/`onPostRequestTimeout` explicitly falls back to re-wrapping and delivering an ERC20 transfer when a native push to the beneficiary fails, so a hostile receiver cannot block settlement: [4](#0-3) 

`IntentsBase._withdraw` has no such fallback — it simply reverts, reintroducing the exact vulnerability the sibling contract was designed to avoid. The same unguarded pattern is duplicated on the Tron deployment's `withdraw()`: [5](#0-4) 

### Impact Explanation
An attacker who is either the order creator (for `RefundEscrow`, triggered on cancellation) or the filler (for `RedeemEscrow`, triggered after a legitimate solver fills an order) can force `_withdraw` to permanently revert by toggling their contract's `receive()` after escrow has been posted but before the cross-chain settlement message is delivered. Because the revert unwinds the whole function, it blocks release of ERC20 assets and protocol fees bundled in the same commitment as well, not just the attacker's own native share. This locks escrowed bridge funds for that order/commitment and prevents legitimate settlement, matching the "bridged assets... must move exactly once and only to the rightful beneficiary" and fund-loss/lock criteria in the bounty scope.

### Likelihood Explanation
Likelihood is medium: it requires the attacker to be a participant in the intent flow (order creator or filler) with a native-token leg, and to deploy a simple togglable-`receive()` contract — no privileged role, relayer collusion, or governance access is needed, matching the "unprivileged attacker" requirement.

### Recommendation
Mirror the mitigation already present in `WrappedHyperFungibleToken.sol`: on a failed native `.call` to `beneficiary`, wrap the native asset (e.g., via WETH) and deliver it as an ERC20 transfer instead of reverting, so a hostile beneficiary cannot block settlement of escrowed funds. Apply this fix to `IntentsBase._withdraw` (and the duplicated `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`).

### Proof of Concept
1. Attacker deploys a contract `Evil` with a `receive()` that can be toggled between accepting and reverting.
2. Attacker places (or fills) an order on `IntentGatewayV2` with a native-token (`address(0)`) input/output leg and sets `Evil` as `order.user` (for cancel/`RefundEscrow`) or fills as `msg.sender = Evil` (for `RedeemEscrow`), with `Evil` initially accepting ether.
3. A relayer detects the eligible cross-chain message (cancel timeout reached, or fill completed) and begins delivering the ISMP proof that will trigger `onAccept`/`onGetResponse` → `_withdraw`.
4. Before/at delivery, attacker calls `Evil.setReverting(true)`.
5. `_withdraw`'s `beneficiary.call{value: amount}("")` fails, `InsufficientNativeToken()` reverts the whole withdrawal, including any other tokens or fees in the same commitment, blocking settlement of the escrow indefinitely.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
