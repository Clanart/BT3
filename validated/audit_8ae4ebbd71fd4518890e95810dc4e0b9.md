### Title
Unauthenticated OP_RETURN operator-attribution in payout txs lets anyone attribute reimbursement to an arbitrary (uninvolved) operator - ([File: core/src/verifier.rs], [File: core/src/database/verifier.rs])

### Summary
`update_finalized_payouts` in `core/src/verifier.rs` parses the payout tx's OP_RETURN as a bare 32-byte xonly pubkey with no signature or ownership proof, and stores it via `update_payout_txs_and_payer_operator_xonly_pk` in `core/src/database/verifier.rs`. Because the user's mandatory `SinglePlusAnyoneCanPay` signature on the payout tx only commits to input 0 and output 0, anyone funding the rest of the transaction (including the withdrawing user themselves) can put an arbitrary operator's xonly pubkey in the OP_RETURN. `get_first_unhandled_payout_by_operator_xonly_pk` later returns this row as a legitimate unhandled payout for that operator's own `PayoutCheckerTask`, causing an operator who never funded the payout to be automatically driven into the kickoff/reimburse flow and reimbursed from the bridge vault.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk` (DB) == the xonly key of the party that actually funded/broadcast the payout tx to the user. This binding is never enforced.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a 3-output tx: user output (0), anchor (1), OP_RETURN with `operator_xonly_pk` (2), spending a single input via key spend.
- The withdrawal UTXO (`input_utxo`) is a small **dust UTXO owned by the withdrawing user's own key** (see `generate_withdrawal_utxo`, `core/src/test/common/setup_utils.rs:480-497`, 550 sats), and the user's signature is enforced to use `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:161-187`, `WithdrawParams` proto comment `core/src/rpc/clementine.proto:242-244`).
- `SinglePlusAnyoneCanPay` commits **only** to input 0's prevout (`Prevouts::One`, `core/src/builder/transaction/txhandler.rs:222-229`) and only to output 0 (`circuits-lib/src/bridge_circuit/mod.rs:850-862`, the SIGHASH_SINGLE branch only encodes `tx.output[input_index]`). The anchor output and the OP_RETURN output are **not covered** by this signature.
- The real payout amount is funded separately: `Operator::withdraw` (`core/src/operator.rs:620-674`) calls `fund_raw_transaction(..., add_inputs: true, ...)`, i.e. additional inputs/outputs are added after the user's signature is already fixed. Nothing prevents any party (not just an operator) possessing the user's `SinglePlusAnyoneCanPay` signature — trivially the withdrawing user themselves — from independently adding their own funding inputs and broadcasting the tx directly to Bitcoin with **any 32-byte value** in the OP_RETURN, bypassing every operator/aggregator/verifier gRPC entirely.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) extracts this OP_RETURN via `parse_op_return_data`/`XOnlyPublicKey::from_slice` with **no check that the key belongs to a registered operator or that the tx's other inputs are attributable to that operator's wallet**, then calls `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) to persist it unconditionally.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-47`) queries `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` (`core/src/database/verifier.rs:282-313`) — a pure equality match on the DB column, with no cross-check against the payout tx's actual funding source — and if matched, drives `handle_finalized_payout` (`core/src/operator.rs:839-...`), which allocates a kickoff connector, builds/signs a Kickoff tx, and eventually the Reimburse tx, releasing bridge collateral to that operator.
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that `operator_xonly_pk` from the DB equals `kickoff_data.operator_xonly_pk` and that the committed blockhash matches — it never checks that the named operator's own funds paid the withdrawal. So this guard does not stop the divergence; it only prevents a *different* operator from claiming a kickoff whose OP_RETURN doesn't name them.

Attacker flow: the attacker is simply the withdrawing user (unprivileged, per the threat model, they can call `withdraw()` on the Citrea Bridge contract and broadcast Bitcoin transactions). They build the payout tx themselves: input 0 = their own dust withdrawal UTXO (their own `SinglePlusAnyoneCanPay` signature), add their own extra funding input(s)/fee, output 0 = their own destination (must match the committed value for the signature to validate), output 2 = OP_RETURN containing a real, registered operator's public xonly pubkey that never touched this withdrawal. Broadcast directly to Bitcoin. No aggregator/operator/verifier RPC call is required.

### Impact Explanation
Once mined, this causes an uninvolved, honest operator's automation to be misled into believing it fronted a payout it never funded, and to spend a kickoff connector + collateral cycle and ultimately receive the Reimburse-tx payout from the vault-committed bridge funds for that deposit — i.e. bridge value (move-to-vault-equivalent reimbursement) is released to a party that did not perform the corresponding action, matching the Critical category "an operator reimbursed for a payout it never funded." The attack is repeatable per withdrawal and can target any operator whose xonly pubkey is public (trivially discoverable, e.g. via `GetEntityStatuses` or on-chain kickoff/round outputs), so blast radius spans every deposit/withdrawal and every operator running automation. It can also be used to consume an operator's limited per-round kickoff slots against their will (a secondary griefing effect, out of scope on its own, but demonstrates the binding is broken).

### Likelihood Explanation
No special privileges are required beyond what an ordinary withdrawing user already has: control of their own withdrawal UTXO's private key, the ability to add their own extra funding input to cover fees/amount, and the ability to broadcast a Bitcoin transaction (all explicitly in-scope attacker capabilities). The `SinglePlusAnyoneCanPay` sighash restriction is enforced only on the parser (`parse_withdrawal_sig_params`), it does not, and cannot by BIP-341 semantics, constrain outputs beyond index 0. No mainnet/live-Citrea state is required to demonstrate the storage/matching bug at the database layer, which is fully reproducible with `cargo test` against the local Postgres test harness already used in `core/src/database/verifier.rs`'s own test module.

### Recommendation
Do not treat the OP_RETURN payload as an authenticated claim of "who fronted this payout." Either (a) require the payout tx to also carry a signature from the named operator's key over the whole transaction (e.g., committing operator identity via a script-path/co-signed input rather than an unauthenticated OP_RETURN), or (b) additionally verify, before marking a payout "unhandled"/reimbursable for a given operator, that the payout tx's non-dust funding input(s) are attributable to that operator (e.g., verifying an operator-controlled input/signature exists in the tx), or (c) require verifiers/aggregator to co-sign/attest the payout (similar to the optimistic-payout musig2 flow) instead of trusting a bare push in an OP_RETURN parsed post-hoc by `update_finalized_payouts`.

### Proof of Concept
In `core/src/database/verifier.rs`'s existing test module (`mod tests`), extend `update_get_payout_txs_from_citrea_withdrawal` (or add a new `#[tokio::test]`):
1. Set up a withdrawal row exactly as in the existing test (`insert_block_info`, `insert_txid_to_block`, `insert_spent_utxo`, `upsert_move_to_vault_txid_from_citrea_deposit`, `update_withdrawal_utxo_from_citrea_withdrawal`).
2. Generate an `operator_xonly_pk` via `generate_random_xonly_pk()` that is **not** registered as any operator (simulating a security-council/aggregator/watchtower/arbitrary key, or equally a real but uninvolved operator's key for the stronger claim).
3. Call `db.update_payout_txs_and_payer_operator_xonly_pk(Some(&mut dbtx), vec![(index, txid, Some(operator_xonly_pk), block_hash)])`.
4. Call `db.get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), operator_xonly_pk)`.
5. Assert the equality-breaking result: `assert!(result.is_some())` and `assert_eq!(result.unwrap().0, index)` — i.e., the DB returns this payout as a legitimate unhandled payout for `operator_xonly_pk`, despite `operator_xonly_pk` having no relationship whatsoever to the actual funder of the payout transaction (in this test, no operator funded anything — the row was inserted directly, standing in for the unauthenticated OP_RETURN parse in `update_finalized_payouts`). This demonstrates the two sides of the binding (`payout_payer_operator_xonly_pk` vs. actual funder identity) diverge with no downstream check catching it before `PayoutCheckerTask` would act on it.
