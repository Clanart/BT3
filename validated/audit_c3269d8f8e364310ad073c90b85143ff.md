### Title
Unconditional 2x reward multiplier in `incentiveDeposit` mode 2 is unbacked by real `mWomSV` lock amount due to reward calculation using nominal input rather than actual post-conversion output - ([File: wombat/ArbWomUp3.sol])

### Summary
`incentiveDeposit` computes and doubles the MGP reward for `_mode == 2` using `getRewardAmount`, which assumes the full raw `_amount` (in WOM) is added to the caller's `mWomSV` locked balance. However, `_deposit` only sends half of `_amount` directly to `mWom` (1:1), and routes the other half through `SmartWomConvert.convert()`, whose "buyback" leg swaps WOM for mWom through an AMM pool subject to swap fees/slippage, meaning the actual mWom amount locked can be less than the nominal amount used in the reward/tier calculation. The unconditional `rewardToSend * 2` doubling is applied on top of this already-unverified nominal reward, and no check exists afterward to confirm the real `mWomSV.getUserTotalLocked` increase matches what was assumed.

### Finding Description
In `incentiveDeposit` [1](#0-0) , the reward is computed and doubled **before** `_deposit` executes and before any verification of the resulting lock:
```
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2) rewardToSend = rewardToSend * 2;
_deposit(msg.sender, _convertRatio, _amount, _mode);
IERC20(mgp).safeApprove(address(vlMGP), rewardToSend);
vlMGP.lockFor(rewardToSend, msg.sender);
```

`getRewardAmount` with `_lock == true` computes:
```
uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
``` [2](#0-1) 

This treats `_amountToConvert` (the raw WOM `_amount` the caller supplied) as if it will be added 1:1 to `mWomSV`'s locked balance. But `_deposit` for `_mode == 2` only:
1. Deposits `_amount/2` directly to `mWom` (1:1) and
2. Routes the remaining half through `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)`, then locks whatever mWom balance results [3](#0-2) 

Inside `SmartWomConvert._convertFor`, the caller-controlled `_convertRatio` splits `toSwap` into a `convertAmount` (minted 1:1 via `IMWom.deposit`) and a `buybackAmount` that is swapped through the Wombat AMM pool (`womMWomPool`) via `IWombatRouter.swapExactTokensForTokens`, which is subject to slippage/fees and pool coverage-ratio pricing rather than a guaranteed 1:1 conversion [4](#0-3) . The attacker fully controls `_convertRatio` (0–DENOMINATOR), and by directing more of `toSwap` through the AMM buyback leg, the resulting `obtainedmWomAmount` (and thus the mWom balance ultimately locked into `mWomSV`) can end up smaller than the nominal `_amount` that was used in `getRewardAmount`'s tier/accumulation calculation.

Because `rewardToSend` is fixed and doubled **before** `_deposit` runs, and there is no post-`_deposit` check comparing the actual `mWomSV.getUserTotalLocked(msg.sender)` delta to the nominal amount assumed by the tier formula, the doubled MGP reward gets locked into `vlMGP` for the caller regardless of whether the real backing materialized. This is a genuine accounting mismatch independent of any admin/oracle misconfiguration — it only requires normal AMM swap fee/slippage behavior in the underlying Wombat pool, which is a standard, expected characteristic of any AMM swap, not a manipulated or externally-privileged condition.

### Impact Explanation
This allows an unprivileged attacker to extract MGP rewards from the finite `mgp` balance held by `ArbWomUp3` (`IERC20(mgp).balanceOf(address(this))`, capped only by the contract's current MGP balance) that are not fully backed by the corresponding `mWomSV` lock the tier system assumes. Each such call doubly inflates the mismatch (once through nominal-vs-actual accounting, once through the unconditional `* 2`), draining the reward budget faster than the intended lock-based incentive schedule and effectively front-running/depleting rewards other genuine lockers would have received. This matches the "theft/permanent loss of unclaimed yield" and "protocol insolvency of the reward budget" impact classes.

### Likelihood Explanation
The attack requires only holding WOM tokens and calling the public `incentiveDeposit` function with `_mode = 2` and a `_convertRatio` skewed toward the AMM buyback path, which is fully attacker-controlled input with no privileged role needed. It is repeatable as long as the `ArbWomUp3` contract holds an MGP balance, and the magnitude of the mismatch scales with normal AMM swap fee/slippage in the `womMWomPool`, which does not require flash loans or price manipulation to exist — attacker capital requirements are minimal (just enough to cross into a nonzero `rewardTier` bracket).

### Recommendation
Compute (or re-verify) the reward based on the actual post-`_deposit` increase in `mWomSV.getUserTotalLocked(msg.sender)` rather than the pre-conversion nominal `_amount`. Specifically, call `_deposit` first, measure the real delta in locked balance, and feed that real delta into `getRewardAmount`'s `accumulated` calculation before applying any multiplier. Additionally, reconsider whether the unconditional `rewardToSend * 2` (100% bonus, despite the comment stating "50% more bonus") is intended, and ensure it is applied only to reward amounts that are provably backed by verified lock increases.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `SmartWomConvert`, mock `mWom`/`wom`/AMM pool with a small swap fee (e.g., simulate `IWombatRouter.swapExactTokensForTokens` returning less than input for the buyback leg).
2. Fund `ArbWomUp3` with MGP and set `rewardTier`/`rewardMultiplier` via `setMultiplier`.
3. As an attacker EOA, approve WOM and call `incentiveDeposit(amount, convertRatio=0, false, mode=2)`, forcing the entire `toSwap` half through the AMM buyback leg.
4. Record `rewardToSend` value emitted in `VLMGPRewarded` (doubled amount).
5. After the call, read `mWomSV.getUserTotalLocked(attacker)` and compute the actual increase from this transaction.
6. Recompute what `getRewardAmount` (undoubled, using tier formula) would output if given the *actual* locked increase instead of nominal `_amount`.
7. Assert `rewardToSend` (the doubled, nominal-based reward actually locked into `vlMGP`) exceeds `2 * <tier-reward computed from actual locked delta>`, demonstrating the doubled MGP payout is not backed by the real qualifying mWomSV lock.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

                rewardAmount +=

                    rewardMultiplier[i - 1];
                i++;
            }
