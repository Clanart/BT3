### Title
Malformed conflict markers in a merged/rebased file cause Copilot conflict resolution to misattribute resolved hunks, silently corrupting committed content - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`reassembleResolvedFile` splices the model's per-hunk resolutions into the original conflicted file purely by *positional order* of `<<<<<<<`/`=======`/`>>>>>>>` marker blocks it detects in the raw file, not by any content-derived anchor. An attacker who controls one side of a merge/rebase (a branch, a fork's PR, or a crafted file that is merged into the repo) can shape the *literal text* of a file so that Desktop's lightweight marker scanner (`reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) miscounts or misaligns conflict blocks relative to what the model was actually shown, causing the wrong `IHunkResolution` to be spliced into the wrong location — all while the tool reports a normal successful AI-assisted resolution and stages/commits the result.

### Finding Description
`reassembleResolvedFile` ( [1](#0-0) ) walks the raw on-disk file text line by line using three simple regexes to find conflict boundaries: [2](#0-1) 

For every `<<<<<<<` line found, it scans forward for the *first* `=======` and the *first* subsequent `>>>>>>>`, and if both are found it splices `hunkResolutions[hunkIndex]` in — advancing `hunkIndex` regardless of whether the block it just consumed corresponds to the same conflict the model actually reasoned about. This "matched by order, not by line number" design (explicitly called out in the docstring) assumes the number and position of real Git conflict blocks in the working tree is stable and matches what was sent to the model in the prompt. It is not validated against that assumption after the fact.

Because the scanner only pattern-matches on marker-shaped lines and doesn't verify structural well-formedness beyond "is there a `=======` before the next `>>>>>>>`", a file whose *content* (not the git-generated conflict) happens to contain marker-like text — e.g. a source file, README, or test fixture that legitimately contains literal `<<<<<<<`/`=======`/`>>>>>>>` sequences (common in files documenting Git conflict resolution, in test fixtures like `app/test/fixtures/`, or deliberately introduced by a malicious commit on the branch being merged) — can cause the scanner to detect a different number/position of "conflict blocks" than the model was shown in its prompt context, or to swallow real, non-conflicted code between two blocks into what it treats as a single conflict region. This desynchronizes `hunkIndex` from the resolutions array, so a resolution intended for one part of the file gets written over an unrelated part, or attacker-adjacent content is preserved as "resolved" without ever being reviewed as such.

`validateResolutionPaths` ( [3](#0-2)  ) only checks that the *number of hunks per file* returned by the model matches the number of hunks Desktop originally extracted from context — it does not, and cannot, verify that `reassembleResolvedFile`'s later re-scan of the raw file lines up positionally with that same set of hunks. The malformed-marker fallback (`!hasSeparator || closingIndex === -1` → copy through as regular content) is a good defense against outright dropped conflicts, but it does not protect against *miscounting real conflicts due to attacker-controlled surrounding text that itself looks marker-shaped*.

The result is then written directly to disk and staged without further diffing against the pre-image, once the user clicks "Continue Merge": [4](#0-3) 

The dialog does show the resolved file per path, but the underlying data being reviewed is already the corrupted reassembly — a user trusting Copilot's summary/diff view has no independent signal that the splice points were wrong.

### Impact Explanation
This falls into the "silent corruption of what the user commits or pushes" category. The user is an unprivileged victim; the attacker's control is limited to shaping the *content* of a branch/PR/commit that ends up on one side of a merge, rebase, or cherry-pick that the victim later resolves with Copilot. If the reassembly desyncs, code the model never actually reasoned about (or the wrong resolution for a different hunk) can end up silently included in the commit that gets pushed — potentially reintroducing removed vulnerable code, dropping a security fix, or injecting attacker-authored text disguised as ordinary file content that isn't part of any real Git conflict but is misread as one.

### Likelihood Explanation
Exploitation requires: (1) the victim to have Copilot conflict resolution enabled and to hit a real conflict against a repository/branch the attacker influences, and (2) the attacker to craft file content containing marker-shaped text near a real conflict block so the positional scan miscounts. This is a non-trivial but realistic scenario — it does not require local access, admin rights, or social engineering beyond ordinary open-source collaboration (a PR/branch merge). The dependency on a specific text-shaping trick and on the feature flag `enableCopilotConflictResolution` being on somewhat limits likelihood, but the "matched by order, not by line number" design explicitly acknowledged in the source comments confirms the underlying assumption is a real, not merely theoretical, weakness.

### Recommendation
Anchor each hunk resolution to the exact original marker block it was derived from (e.g., by hashing or snapshotting the raw `<<<<<<<...>>>>>>>` byte ranges captured when building `IFileConflictContext`, and validating during reassembly that the block text at each detected position matches what was originally extracted) rather than relying purely on ordinal position. Additionally, re-run `getFilesWithConflictMarkers`/`git diff --check`-equivalent validation on the *reassembled* output to confirm no conflict markers remain and that the line count outside spliced regions is unchanged, surfacing a hard error/dialog instead of silently writing the file when a mismatch is detected.

### Proof of Concept
1. Attacker pushes a branch that both introduces a real merge conflict in `src/example.ts` and also includes, elsewhere in the same file (outside the real conflict, e.g. in a comment/test string), literal lines of the form:
   ```
   <<<<<<< decoy
   irrelevant
   =======
   irrelevant
   >>>>>>> decoy
   ```
2. Victim (with Copilot conflict resolution enabled) merges/rebases onto this branch, hits the conflict, and clicks "Resolve with Copilot".
3. Desktop extracts hunk context for the *real* conflict and sends it to the model, which returns one resolution for that one real hunk.
4. When `reassembleResolvedFile` re-scans the raw file to splice the resolution back in, it encounters the decoy marker-shaped block first (or interleaved with the real one) and applies `hunkResolutions[0]` at the wrong position, since matching is purely positional (`app/src/lib/copilot-conflict-resolution.ts` lines 549-599).
5. The victim clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the corrupted content to disk and stages it (`app/src/lib/stores/app-store.ts` lines 7233-7260) without any structural re-validation, and the corrupted file is committed/pushed.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
