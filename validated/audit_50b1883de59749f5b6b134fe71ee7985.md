### Title
Missing `chain_id`, Nonce, and Deadline in EIP-712 Withdrawal Authorization Domain Enables Cross-Network Replay and Irrevocable Authorizations — (File: `core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate withdrawal authorization signatures (`OptimisticPayoutMessage` / `OperatorWithdrawalMessage`) omits `chain_id`, `verifying_contract`, a per-request nonce, and an expiry deadline. Because the domain hash is therefore identical on every network where the same aggregator key is deployed, a `verification_signature` produced on testnet is cryptographically indistinguishable from one produced on mainnet. Additionally, once signed, the authorization can never be selectively revoked: it remains valid indefinitely and can be replayed any number of times.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

Neither `chain_id` nor `verifying_contract` is present. The config already carries `citrea_chain_id` (e.g. `5655` on mainnet, `5115` in `run.sh`) but it is never fed into the domain: [2](#0-1) 

The two message structs contain no `nonce` or `deadline` field: [3](#0-2) 

The `verification_signature` is the authorization gate that both verifiers and operators check before executing bridge-fund-spending operations:

- **Verifier** (`sign_optimistic_payout`): checks the signature before producing a MuSig2 partial signature over the `opt_payout_txhandler`, which spends the bridge-controlled `move_tx` output (input index 1). [4](#0-3) 

- **Operator** (`withdraw` RPC): checks the signature before executing the payout transaction. [5](#0-4) 

`aggregator_verification_address` is set by default in `BridgeConfig::default()` and in `.env.example`, so the check is active in standard deployments: [6](#0-5) 

---

### Impact Explanation

**Cross-network replay.** If the same aggregator ECDSA key is used on testnet and mainnet (a common operational pattern during staged rollouts), a `verification_signature` produced on testnet is byte-for-byte valid on mainnet. An attacker who captures a testnet authorization (e.g., by monitoring the aggregator's `optimistic_payout` gRPC endpoint) and who can supply matching `withdrawal_id` + `input_outpoint` values that exist in the mainnet DB can replay it. The verifier will accept it and produce a partial signature over the optimistic payout transaction, which spends the bridge-controlled `move_tx` UTXO — a direct loss of bridged BTC.

**Irrevocable authorization.** Because there is no deadline, a `verification_signature` is valid forever. If the aggregator/Citrea signs an authorization and later detects fraud or a protocol error, it cannot invalidate that specific signature without rotating the entire aggregator key (which revokes all outstanding authorizations simultaneously). An attacker who has saved a previously issued `verification_signature` can submit it at any future time.

**No nonce.** Without a per-request nonce tracked in the DB, the same `verification_signature` can be submitted to multiple operators or verifiers concurrently, or re-submitted after a partial failure, without any replay guard at the message level.

The optimistic payout path is the highest-impact surface: verifiers sign the MuSig2 partial signature over `opt_payout_txhandler` input index 1 (the `move_tx` deposit output), which is a bridge-controlled UTXO holding the full 10 BTC bridge denomination: [7](#0-6) 

---

### Likelihood Explanation

**Cross-network replay** requires the same aggregator key on two networks and matching DB state — plausible during testnet→mainnet migration or parallel deployments. **Irrevocable authorization** is a guaranteed property of the current design: every signed authorization is permanently valid, making fraud-response impossible without a full key rotation. The `aggregator_verification_address` is enabled by default, so the check — and therefore the vulnerability — is active in all standard deployments.

---

### Recommendation

1. **Add `chain_id` to the EIP-712 domain.** Use `citrea_chain_id` from `BridgeConfig`, which is already available at signing time:
   ```rust
   let domain = alloy_sol_types::eip712_domain! {
       name: "ClementineVerification",
       version: "1",
       chain_id: config.citrea_chain_id as u64,
   };
   ```

2. **Add a `deadline` field** to `OptimisticPayoutMessage` and `OperatorWithdrawalMessage`. Verifiers and operators must reject requests where `current_time > deadline`.

3. **Add a `nonce` field** and track consumed nonces in the database. Reject any `verification_signature` whose nonce has already been used, preventing replay even within the same network and time window.

---

### Proof of Concept

1. On testnet (Citrea `chain_id = 5115`), call the aggregator's `optimistic_payout` gRPC endpoint with valid withdrawal params. Observe the `verification_signature` in the request (or intercept it if the endpoint is accessible without mTLS).

2. On mainnet (Citrea `chain_id = 5655`), find a deposit whose `withdrawal_id` and `input_outpoint` are recorded in the mainnet DB (both are public on-chain).

3. Call the mainnet aggregator's `optimistic_payout` with the mainnet `withdrawal_id`, the mainnet `input_outpoint`, a valid user Schnorr `input_signature` (obtainable from the Bitcoin mempool/chain), and the **testnet** `verification_signature`.

4. `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` recomputes the EIP-712 hash using `CLEMENTINE_EIP712_DOMAIN` (no `chain_id`), recovers the same aggregator address, and the check passes. [8](#0-7) 

5. The aggregator collects verifier partial signatures over the optimistic payout transaction and broadcasts it, spending the bridge-controlled `move_tx` UTXO on mainnet.

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
