### Title
OP_RETURN `data` output is excluded from weight/vbytes and fee accounting in `SignableTransaction::new`, causing underpaid fees and potentially non-relayable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a `data` parameter and appends an OP_RETURN output to the transaction, but computes the transaction's weight, vbytes, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check from `payments` alone — before the OP_RETURN output is accounted for. Analogous to the `flash()` payable bug (input value accepted but not credited in the function's accounting), the OP_RETURN output's bytes are part of the final signed transaction yet contribute nothing to its fee calculation.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150`):

1. The OP_RETURN output is pushed to `tx_outs` at lines 194–202.
2. `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 builds a mock transaction from `tx_ins` and `payments` only — the OP_RETURN output is never passed in.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` (line 211) therefore use a vbyte count missing the OP_RETURN output (~11 + data_len bytes, up to ~91 weight units... actually ~350+ WU for 80 bytes of data plus output overhead).
4. The change-fee calculation at lines 225–227 likewise calls `calculate_weight_vbytes(..., payments, Some(&change))`, still omitting the OP_RETURN output.
5. The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses the same undercounted weight.

The result: the signed transaction is larger than what was priced, so its effective fee rate is strictly below the requested `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed.

### Impact Explanation
When a transaction carries `data` (up to 80 bytes permitted), the produced transaction:
- pays a lower fee rate than the caller specified via `fee_per_vbyte`;
- may dip below the Bitcoin Core default minimum relay fee, making the signed transaction non-relayable — threshold-signed funds locked into a transaction the network will not propagate until a new transaction is constructed and re-signed;
- can marginally evade the `MAX_STANDARD_TX_WEIGHT` standardness bound.

The size of the discrepancy grows with `data` length and number of bytes, so it is deterministic, not negligible.

### Likelihood Explanation
The bug triggers on every `SignableTransaction` built with a non-`None` `data` argument; no adversarial condition is required. Reachability depends on the integrator exposing `data` in transactions (Serai uses OP_RETURN payloads for protocol metadata), so it is a conditional-but-deterministic accounting error rather than an attacker-controlled edge case. Severity is Medium: it does not enable theft or forgery, but it silently violates the fee-rate contract and can produce a transaction that fails relay policy despite all internal checks passing.

### Recommendation
Include the OP_RETURN output in the mock transaction used by `calculate_weight_vbytes` — e.g., extend `payments`/`tx_outs` passed to it with the OP_RETURN `TxOut` (or pass `data` through) before computing `vbytes`, `needed_fee`, the minimum-fee check, and the change-delta calculation. Alternatively, compute weight from the final `tx_outs` vector after all outputs (payments, OP_RETURN, change) are assembled.
