### Title
Uncaught `OverflowError` in `_record_usage` cost computation from oversized (but digit-limit-valid) token counts crashes the security-review call path - ([File: plugins/security-guidance/hooks/_base.py])

### Summary
`_record_usage` wraps only the `int(...)` parsing of `usage` fields in a `try/except (TypeError, ValueError)`, but the subsequent cost calculation (`i * pin + o * pout + ...`) is unprotected. A spoofed/MITM'd Anthropic API response with a large-but-valid numeric string (e.g. ~300+ digits, well under Python's 4300-digit `int()` conversion limit) for `input_tokens`/`output_tokens`/etc. parses successfully into a huge `int`, but then raises an uncaught `OverflowError` when Python tries to convert that int to a `float` during `i * pin`.

### Finding Description
In `plugins/security-guidance/hooks/_base.py`: [1](#0-0) 
the `int()` conversions at lines 119-122 are guarded, but the cost formula at line 132 (`cost_usd = (i * pin + o * pout + cr * pin * 0.1 + cw * pin * 1.25) / 1_000_000`) executes outside that `try/except` block whenever `cost_usd` is `None` (the default for the raw-HTTP path). `pin`/`pout` are Python floats from `_PRICE_PER_MTOK`. Multiplying a Python `int` by a `float` forces an implicit `int.__float__()` conversion; if the int magnitude exceeds `~1.8e308` (roughly 309+ decimal digits), this raises `OverflowError: int too large to convert to float`. Since Python's `int(str)` global digit-count safety limit defaults to 4300 digits, an attacker-controlled numeric string with, say, 320 digits parses fine at line 119-122 but still overflows at line 132.

This is reachable via `plugins/security-guidance/hooks/llm.py`, where `_call_claude` parses the raw HTTP JSON response and calls: [2](#0-1) 
`_record_usage(response_data.get("usage") or {}, response_data.get("model") or payload["model"])` — no `cost_usd` is passed, so the vulnerable computation branch executes. The surrounding `try/except` in `_call_claude` (lines ~448-487) only catches `urllib.error.HTTPError`, `urllib.error.URLError`, and `TimeoutError`, so the `OverflowError` is not caught there either and propagates up through `_call_claude_dual_or` (via `ThreadPoolExecutor.result()`), into `analyze_code_security`, and further up into the Stop-hook handler.

### Impact Explanation
An MITM'd or spoofed API/gateway response (precondition explicitly allowed: "attacker controls or MITMs a tool/API response consumed by llm.py") can crash the security-review pipeline with an uncaught exception instead of a bounded, logged failure. Depending on whether an outer layer in `security_reminder_hook.py` swallows generic exceptions, this either (a) crashes the whole hook subprocess, or (b) is caught generically and treated as "review failed/skipped" — either way the intended security review output for that turn is suppressed, which is a hook-bypass side effect on the `DENY_MEANS_DENY` / fail-closed invariant the question targets. I was not able to fully confirm within tool-call budget whether `security_reminder_hook.py`'s top-level handlers wrap calls to `analyze_code_security`/`agentic_review` in a blanket `except Exception`, which would determine whether this manifests as a full process crash or a silent review-skip; either outcome, however, results in the review not being surfaced to the user for that invocation.

### Likelihood Explanation
Requires the attacker to control or MITM the `usage` object of an Anthropic-protocol response consumed by `_call_claude`/`_call_claude_via_sdk` (a stated precondition). No authentication bypass or additional privilege is needed beyond that MITM/spoof capability. Constructing the payload is trivial (a single JSON field with ~300-4300 numeric digits); the digit limit only needs to be under 4300 to survive `int()` parsing, and over ~309 digits to exceed float range at the multiplication step — an easy, reliable window. This is deterministically reproducible every time, not probabilistic.

### Recommendation
Wrap the entire cost computation (not just the `int()` parsing) in `_record_usage` in `try/except`, or clamp `i`, `o`, `cr`, `cw` to a sane maximum (e.g. cap at a large but float-safe bound such as `10**15`) immediately after parsing, before they are used in any float arithmetic. Also consider catching `OverflowError`/`Exception` broadly around the whole function body given it processes untrusted network data, consistent with the "must not fail open due to resource exhaustion/unhandled exceptions" invariant.

### Proof of Concept
Unit test in a Python file that imports `_base`:
```python
from _base import _record_usage, _USAGE, _USAGE_LOCK

def test_record_usage_overflow_does_not_raise():
    huge = "9" * 320  # < 4300 digit int() limit, > float max digit count (~309)
    usage = {"input_tokens": huge, "output_tokens": "0",
             "cache_read_input_tokens": "0", "cache_creation_input_tokens": "0"}
    # Expect this NOT to raise OverflowError uncaught.
    _record_usage(usage, "claude-sonnet-4-6")  # currently raises OverflowError
```
Expected (fixed) behavior: `_record_usage` returns normally (or logs and no-ops) without propagating `OverflowError`, and `_USAGE` accumulator state remains consistent/bounded. Currently, this call raises an uncaught `OverflowError`, and an integration-level fuzz test driving `_call_claude` with a mocked `urllib.request.urlopen` returning this `usage` payload demonstrates the exception propagating out of `_call_claude` uncaught, aborting the review call.
