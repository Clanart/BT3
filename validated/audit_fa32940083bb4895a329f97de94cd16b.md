### Title
Consumed FROST preprocess seed is never invalidated — replayed `share_internal`/`complete_internal` reuse identical nonces to sign a different message — (`coordinator/src/tributary/signing_protocol.rs`)

### Summary
The coordinator caches a FROST preprocess seed in `CachedPreprocesses` keyed by `context` (`(b"DkgConfirmer", attempt)`), decrypts it, and calls `AlgorithmSignMachine::from_cache` inside `share_internal` every time a share or complete is requested. Nothing ever deletes or invalidates the cached seed after `machine.sign(...)` consumes it. Any second invocation of `share_internal`/`complete` for the same `context` regenerates the exact same nonces and signs again — the same "deleted-but-not-invalidated identity replay" class as CVE-2026-50575, mapped onto Serai's consumed-preprocess identity. `sign.rs` explicitly documents "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share."

### Finding Description
`preprocess_internal` creates a fresh preprocess only if `CachedPreprocesses::get(txn, &context)` is `None`, stores it (XOR-encrypted under `Blake2s256("Cached Preprocess Encryption Key" || context || key)`), and on every call loads the same seed and calls `from_cache`, which deterministically regenerates `nonces` and `commitments` via `ChaCha20Rng::from_seed` (`seeded_preprocess`, `crypto/frost/src/sign.rs:127-145`).

`DkgConfirmer::share` calls `share_internal` once to emit a share; `DkgConfirmer::complete` calls `share_internal` **again** to rebuild the machine before `complete_internal` (`signing_protocol.rs:301`, `321-326`). Both calls rebuild the same `AlgorithmSignMachine` from the same cached seed because `CachedPreprocesses::set` is never followed by a delete. The message signed is `set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:296-300`), and the preprocess map is attacker-influenced: `preprocesses` arrive as untrusted bytes from other DKG participants, deserialized via `read_preprocess` (`signing_protocol.rs:165`).

Because `machine.sign(preprocesses, msg)` is a pure function of `(seed-derived nonces, preprocesses, msg)`, any pair of `share_internal` calls for the same `context` whose `(preprocesses, key_pair/removed)` differ produces two Schnorr shares under identical raw nonces `(d, e)`. With identical preprocess sets and different `msg` (different `key_pair`, e.g., a different reported DKG result across a reboot or retry path), the effective nonce `d + ρ·e` is identical while the challenge differs:

```
s1 = (d + ρe) + λ·k·c1
s2 = (d + ρe) + λ·k·c2
k  = (s1 − s2) / (λ·(c1 − c2))
```

yielding the validator's MuSig/Schnorrkel secret share `k` directly.

### Impact Explanation
Recovery of a coordinator/validator's signing secret share. Combined with the threshold structure this enables signature forgery and unauthorized `set_keys` confirmations — confidentiality and integrity loss consistent with the source advisory's C:H/I:H rating.

### Likelihood Explanation
The precondition — `share_internal` executing twice for one `context` with differing `msg` or preprocess set — is reachable: `share()` and `complete()` are distinct externally-triggered entry points (`signing_protocol.rs:304-326`), `complete` is invoked after reboot handling where `preprocessing` RAM state is lost (`signer.rs` reboot notes), and the DKG `key_pair`/preprocess bytes are produced by external participant inputs. Any divergence in `preprocesses` changes ρ but the base nonces are still reused; any divergence in `key_pair` alone is sufficient for the linear-algebra recovery above. No rate-limit, attempt guard, or post-`sign` deletion exists — the `Attempt`/`Completed` guards in `processor/` do not cover this coordinator-side cache.

### Recommendation
Delete `CachedPreprocesses` for `context` inside `share_internal` immediately after `machine.sign(...)` succeeds (or gate a second `sign` on a consumed-flag written atomically with the cache entry), so `from_cache` can never regenerate a consumed nonce set. `complete` should reuse the `AlgorithmSignatureMachine` returned by `share` rather than re-running `share_internal`.

### Proof of Concept
```rust
// Same context => same cached seed => identical (d, e, commitments)
let mut confirmer = DkgConfirmer::new(key, spec, txn, attempt).unwrap();

// First consume: share() signs set_keys_message(.., key_pair_A)
let share1 = confirmer.share(preprocesses.clone(), &key_pair_a).unwrap();

// Second consume: complete() calls share_internal again with a different
// key_pair (different DKG result) -> identical nonces, different challenge
let _sig = confirmer.complete(preprocesses, &key_pair_b, shares).unwrap();
// share2 is recomputed internally; both shares broadcast on the same nonces.

// s1 - s2 = lambda * k * (c1 - c2)  =>  secret share k recovered
```
Root cause: `CachedPreprocesses::get` at `signing_protocol.rs:137` always returns the live seed and no `delete` exists anywhere in the crate (`grep` shows only `get`/`set`), violating the `from_cache` contract at `crypto/frost/src/sign.rs:216-219`.
