### Title
Division-by-zero panic in KIP-71 base fee calculation via ungoverned `GasTarget=0` governance parameter - (File: params/kip71_config.go)

### Summary
The `Kip71GasTarget` governance parameter has no format validation preventing a zero value, unlike its sibling parameter `Kip71BaseFeeDenominator` which explicitly rejects zero. If `GasTarget` is set to `0` via governance, `KIP71Config.NextMagmaBlockBaseFee()` performs `big.Int.Div(x, gasTarget)` with a zero divisor, which in Go's `math/big` package causes a runtime panic (not a silent zero return like EVM opcodes), crashing every node that validates or produces a block.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee based on `parentGasUsed` vs `gasTarget`: [4](#0-3) 

When `parentGasUsed != gasTarget`, the code computes `gasUsedDelta` and then divides by `gasTarget` (`y := x.Div(x, new(big.Int).SetUint64(gasTarget))`) with no guard against `gasTarget == 0`, in contrast to `baseFeeDenominator`, which is explicitly defaulted to `64` when zero (line 71-76 of the same file). If governance sets `Kip71GasTarget` to `0`, and any block has `parentGasUsed != 0` (the near-universal case, since `gasTarget=0` means essentially all nonzero gas usage exceeds target), this line panics with a native Go division-by-zero.

The parameter validation for `Kip71GasTarget` uses `noopFormatChecker`, meaning any `uint64` value including `0` is accepted at the governance layer: [5](#0-4) 

This is directly analogous to the reported OneFlow `floor_divide()` bug class: an externally influenced parameter reaching a division operation without a zero-guard.

### Impact Explanation
`NextMagmaBlockBaseFee` is called during header validation on every Magma-enabled block via `VerifyMagmaHeader`, invoked from `BlockValidator.validateHeader`, which runs on all full nodes processing incoming blocks: [3](#0-2) 

A panic here crashes the node process (denial of service) network-wide, since every node performing header validation calls this same function on the same chain state, once the malicious `GasTarget=0` value is active via governance. This matches "state divergence/DoS" impact criteria — an unrecoverable crash affecting all honest nodes simultaneously, effectively halting the chain.

### Likelihood Explanation
This requires the `Kip71GasTarget` governance parameter to actually be set to `0`, which under Kaia's on-chain governance requires a governance vote/parameter change (via `kaiax/gov`) to pass — this is not a simple unprivileged single-transaction path like the analog's DoS trigger. Governance parameter changes are typically restricted to the governing node/council under `GovernanceMode` rules. I was unable to fully verify within available context whether any additional layer (e.g., a stricter format checker enforced elsewhere, or governance proposal validation) blocks a zero value from being accepted before it reaches `ChainConfigValue`/`ToKip71Config()`. This uncertainty affects whether an "unprivileged" actor (per the scope rules) could ever trigger this, or whether it is confined to a governance-only misconfiguration path — which would fall outside the requested scope of reachability from "a single submitted transaction, bundle, bid, or RPC call" by an unprivileged actor.

### Recommendation
Add a zero-check for `GasTarget` in `NextMagmaBlockBaseFee`, symmetric to the existing `BaseFeeDenominator` zero-guard, falling back to the `DefaultGasTarget` constant when `kc.GasTarget == 0`. Additionally, update the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` from `noopFormatChecker` to reject `v == 0`, consistent with `Kip71BaseFeeDenominator`.

### Proof of Concept
1. Via governance, set `governance.kip71.gastarget` (or the corresponding vote key) to `0`.
2. Once the parameter takes effect at the next epoch/governance interval, any subsequent block with `parentGasUsed != 0` (virtually guaranteed) triggers `NextMagmaBlockBaseFee`'s branch computing `y := x.Div(x, new(big.Int).SetUint64(0))`.
3. `math/big.Int.Div` panics with "division by zero" — crashing every node calling `BlockValidator.validateHeader` on that block, halting the network.

**Caveat:** Because triggering this requires a governance-parameter change rather than an unprivileged transaction/RPC call, I could not fully confirm within the scope constraints (which explicitly limit analogs to paths reachable by an unprivileged transaction sender/RPC caller) that this qualifies as in-scope. If governance-only misconfiguration paths are excluded per the rules, this finding may not meet the strict reachability requirement, and further clarification/verification of the governance parameter submission path would be needed.
