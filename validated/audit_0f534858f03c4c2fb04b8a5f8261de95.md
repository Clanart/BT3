## Analysis

The JOJO bug's core pattern is: **attacker-controlled data reaches a powerful "call any target" primitive with no allow-list**, letting the attacker redirect that call to their own target. The closest analog in GitHub Desktop is the `LinkButton` component's `uri` prop being passed straight into `shell.openExternal()` with **no scheme/protocol validation**, while GitHub API response objects (`user.html_url`, `comment.html_url`, `review.html_url`) are wired directly into that `uri` prop.

### Title
Unvalidated `LinkButton` `uri` from GitHub API objects reaches `shell.openExternal` with no protocol allow-list - (File: `app/src/ui/lib/link-button.tsx`)

### Summary
`LinkButton` opens whatever string is passed as `uri` via `shell.openExternal(uri)` on click, with zero validation of the URI scheme. [1](#0-0) 
Several PR/notification UI components feed this `uri` prop directly from fields returned by the GitHub API (`html_url`), without checking that the value is `http(s)`: [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`shell.openExternal` is proxied from renderer to main process via IPC: [5](#0-4) 
and the main-process handler passes the path straight to Electron's `shell.openExternal`, only *logging* (not enforcing) an `http(s)` prefix — any other scheme (`file:`, a registered custom protocol, or a Windows UNC-style path) is executed unconditionally: [6](#0-5) 

Elsewhere in the codebase, the app *does* apply exactly this kind of guard: `SandboxedMarkdown`'s link interceptor explicitly checks `/^https?:/.test(a.protocol)` before invoking the click callback that eventually calls `openExternal`: [7](#0-6) 
and the commit-message hyperlink tokenizer only creates a `Link` token if the text matches `^https?:\/\/`: [8](#0-7) 

`LinkButton`, however, has no such check — it's a generic component relying entirely on caller discipline. `IAPIIdentity.html_url`, `IAPIComment.html_url`, and pull-request review `html_url` are values returned by whatever GitHub endpoint (dotcom or a user-added GitHub Enterprise Server) the account is configured against. Since Desktop trusts these API response fields implicitly and forwards them straight to a `shell.openExternal`-backed sink with no scheme check, a malicious or compromised GitHub Enterprise Server (a "GitHub API object"/"proxy response" the attacker controls, per the accepted threat model) can return a comment/review/user object where `html_url` is set to a dangerous target instead of a normal `https://` URL, and the click ends up executing `shell.openExternal` on that target unfiltered.

### Impact Explanation
Depending on platform and installed handlers, an attacker-chosen `html_url` opened via `shell.openExternal` can:
- Point to a `file://` URI or local path, causing the OS to open/execute a local file with its default handler.
- Point to a UNC-style path (`\\attacker-host\share\...`) on Windows, triggering an implicit SMB/NTLM authentication handshake to the attacker's server — a well-known technique for **credential (NTLM hash) exfiltration** without any additional user action beyond the single click.
- Invoke another installed custom URI-scheme handler with attacker-supplied arguments, potentially achieving code execution in that other application.

This matches the Valid Impact categories: "a link ... the user clicks" plus "a GitHub API object" controlled by the attacker, resulting in "credential/token exfiltration" or worse.

### Likelihood Explanation
Requires: (1) the victim to have added/be using a GitHub Enterprise Server account that is malicious or has been compromised/MITM'd (a scenario explicitly in-scope, mirroring "git remote/proxy response" attacker control), and (2) the victim to click a link rendered from that server's PR comment/review notification. No local access, no prior malware, and no unnatural steps beyond a normal single click on a UI element that looks like "Open in Browser" are needed. The existing protocol-check pattern used in `sandboxed-markdown.tsx` and `text-token-parser.ts` shows the team is aware this class of risk exists, but it was not applied consistently to `LinkButton`, so there is no existing guard stopping this specific path.

### Recommendation
Enforce the same `^https?:` allow-list check inside `LinkButton.onClick` (and/or centrally inside `app-shell.ts`'s `openExternal` wrapper and the main-process `open-external` IPC handler) before calling `shell.openExternal`, rejecting any non-http(s) scheme regardless of caller.

### Proof of Concept
1. Victim adds a GitHub Enterprise Server account in Desktop pointing at a server the attacker controls (or MITMs a real GHES instance's TLS/DNS).
2. Attacker's server responds to the pull-request comments/reviews API with a JSON object where `html_url` (or `user.html_url`) is set to `file:///C:/Windows/System32/calc.exe` or `\\attacker-smb\share\x` instead of a normal `https://` GHES URL.
3. Desktop renders the PR-comment/review notification dialog, passing that field straight into `<LinkButton uri={comment.html_url}>` (`app/src/ui/notifications/pull-request-comment.tsx:128`).
4. Victim clicks "Open in Browser". `LinkButton.onClick` calls `shell.openExternal(uri)` unconditionally (`app/src/ui/lib/link-button.tsx:76-92`), which round-trips through the `open-external` IPC handler that does not block non-http(s) schemes (`app/src/main-process/main.ts:581-597`), causing the OS to act on the attacker-chosen URI/path — e.g. initiating an outbound SMB authentication attempt for credential capture.

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
