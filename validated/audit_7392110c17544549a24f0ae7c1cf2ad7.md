### Title
`ReceivedOutput::read` accepts an attacker-controlled offset/script binding, so a tampered offset makes a received output permanently unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The OpenQ bug class is an unauthenticated write to an identity/claim binding: `associateExternalIdToAddress` lets anyone overwrite `addressToExternalUserId[victim]`, and the claim path (`permissionedClaimTieredBounty`) then fails its binding check, so legitimately-won funds cannot be claimed.

Serai's analogous binding is `ReceivedOutput { offset, output, outpoint }` in `networks/bitcoin/src/wallet/mod.rs:90-97`. The `offset` is the scalar that maps the wallet's base Taproot key to the key that can actually spend `output.script_pubkey`. When produced by `Scanner::scan_transaction`, the `offset ↔ script_pubkey` binding is guaranteed by the `scripts` map built via `register_offset` (`networks/bitcoin/src/wallet/mod.rs:180-214`). However, `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes `offset`, `output`, and `outpoint` from raw bytes with no consistency check — and cannot check, since the base key isn't part of the encoding. Like OpenQ's setter, the deserialization "writes" an association (offset → output) supplied entirely by the byte provider, with no proof it is the correct binding.

The corrupted binding is then enforced downstream exactly like OpenQ's `require(closer == tierWinner)`: `SignableTransaction::multisig` recomputes `p2tr_script_buf(keys.offset(self.offsets[i]).group_key())` and returns `None` if it doesn't equal `self.prevouts[i].script_pubkey` (`networks/bitcoin/src/wallet/send.rs:273-285`). A `ReceivedOutput` carrying a wrong-but-well-formed scalar deserializes fine, is reported as a received output with correct value/outpoint, yet `multisig` refuses to build a signing machine for it — the funds are recognized as received but can never be claimed.

### Finding Description

1. `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) calls `Secp256k1::read_F` for `offset`, then consensus-decodes `TxOut` and `OutPoint`. Any canonical scalar is accepted; nothing binds it to `output.script_pubkey`. The `Scanner`-enforced invariant "offset is the discrete log such that `p2tr(key + offset·G) == script_pubkey`" exists only at scan time and is not encoded or re-validated on read.

2. `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) is the only path that produces a *correct* offset, since it looks the script up in the preregistered `scripts` map. Any `ReceivedOutput` materialized through `read` — e.g., an output record relayed between components, restored from an untrusted store, or supplied by a peer — carries an arbitrary offset.

3. `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-176`) trusts `input.offset` and stores it in `self.offsets`; `multisig` (`send.rs:273-285`) then treats a mismatch as "wrong keys" and returns `None`, making the transaction unconstructable. There is no second chance: a single tampered offset in any input poisons the whole `SignableTransaction` (`None` propagates), and because the offset is stored per-output, every spend attempt for that output fails identically.

4. Compounding this, `Output::key()`-style consumers recover the base key as `read_G(script_key) − offset·G` (cf. `processor/src/networks/bitcoin.rs:112-122`), so a forged offset additionally misattributes which key owns the output — the same "rebinding" shape as the OpenQ `addressToExternalUserId` overwrite.

### Impact Explanation

An attacker who can feed bytes to `ReceivedOutput::read` (or any `read` path embedding it, such as `processor`'s `Output::read` at `processor/src/networks/bitcoin.rs:145-166`) can attach a wrong offset to a real outpoint/`TxOut`. The output is still reported as received — correct value, correct outpoint, plausible script — but every `SignableTransaction::multisig` call returns `None` because the offset key doesn't match the `script_pubkey`. Result: funds reported received that are not spendable — a permanent denial of the claim on those funds, the exact impact class of the OpenQ report (winner cannot claim the bounty). Alternatively, an offset chosen so `key + offset·G` equals a *different* registered script causes misattribution of the output to the wrong sub-key.

### Likelihood Explanation

Reachability is per the in-scope threat model: `ReceivedOutput::read` is an explicitly enumerated untrusted-bytes sink. Exploitation requires only flipping/choosing the 32-byte scalar field of a serialized `ReceivedOutput` — no key material, no collusion, no validator privileges — mirroring how OpenQ's attacker only needed to call a public oracle-facing setter. The resulting failure is deterministic (a `None`/`CLAIMANT_NOT_TIER_WINNER`-style rejection at claim time), not probabilistic. It is capped at Medium–High rather than critical because it requires an untrusted deserialization path to be exercised and yields unspendable funds (DoS of the claim), not theft.

### Recommendation

Mirror the fix options from the OpenQ report onto the offset binding:

- **Re-validate on read/use**: where the base key is known (e.g., in `SignableTransaction::multisig` and in `Scanner`-aware consumers), assert `p2tr_script_buf(base + offset·G) == output.script_pubkey` and treat mismatch as a deserialization/integrity error on the *output record* — currently the check exists but only as a silent `None` indistinguishable from "wrong keys," so callers cannot tell a tampered record from a key mismatch. Surface it as an explicit `InvalidOffset` error instead of `Option::None`.
- **Bind at the source**: prefer receiving `ReceivedOutput`s exclusively from `Scanner::scan_*`; where untrusted bytes must be accepted, re-derive the offset by re-scanning `output.script_pubkey` against the scanner's `scripts` map rather than trusting the serialized scalar (analogous to OpenQ's "only allow association to non-associated addresses" / verify-instead-of-trust fix).
- **Make the encoding self-authenticating**: optionally include or separately authenticate the base key/expected script so `read` can reject inconsistent records.

### Proof of Concept

```rust
// networks/bitcoin context; requires `std` feature
use k256::{ProjectivePoint, Scalar};
use bitcoin::{
  hashes::Hash, Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use bitcoin_serai::wallet::{Scanner, ReceivedOutput, SignableTransaction, p2tr_script_buf};
use frost::{curve::Secp256k1, ThresholdKeys};
use dkg_dealer::key_gen;
use rand_core::OsRng;

#[test]
fn tampered_offset_makes_received_output_unspendable() {
  // Honest setup: threshold keys tweaked for Taproot, even-Y key
  let keys: HashMap<_, ThresholdKeys<Secp256k1>> = key_gen(&mut OsRng, 2, 3);
  let keys = keys.values().next().unwrap().clone();
  let keys = bitcoin_serai::wallet::tweak_keys(keys);
  let key = keys.group_key();
  let script = p2tr_script_buf(key).unwrap();

  // Legitimately received output, as produced by Scanner::scan_transaction
  let real = ReceivedOutput produced by scanning a TX paying `script`;
  let mut bytes = real.serialize(); // offset || TxOut || OutPoint

  // ATTACKER: overwrite the 32-byte offset field (the "address -> ID" mapping)
  // with a different scalar, exactly like overwriting addressToExternalUserId.
  let forged = Scalar::from(0xdeadbeefu64).to_bytes();
  bytes[.. 32].copy_from_slice(&forged);

  // Deserialization succeeds: no binding between offset and script is checked.
  let tampered = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
  assert_ne!(tampered.offset(), real.offset());
  assert_eq!(tampered.output(), real.output());   // same outpoint/value/script
  assert_eq!(tampered.outpoint(), real.outpoint());

  // The output is reported received (value/outpoint intact), but claiming it
  // via SignableTransaction::multisig fails — analog of CLAIMANT_NOT_TIER_WINNER.
  let stx = SignableTransaction::new(
    vec![tampered],
    &[(script.clone(), tampered_value - fee)],
    None, None, fee_per_vbyte,
  ).unwrap();
  for signer_keys in honest_threshold_shares {
    // Returns None: p2tr(key + forged_offset*G) != script_pubkey
    assert!(stx.clone().multisig(&signer_keys).is_none());
  }
  // No machine can ever be constructed => the received funds are unspendable.
}
```

The PoC shows: `read` accepts the overwritten binding without error; `multisig` deterministically rejects it (`send.rs:277` returns `None`); the output's value/outpoint remain indistinguishable from a valid receipt, so the funds sit reported-but-unclaimable — the same claim-blocking overwrite primitive as `associateExternalIdToAddress`, applied to Serai's `offset → script_pubkey` association.
