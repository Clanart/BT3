## Title
Predispatch escrow accounting sweeps the *entire* shared `CallDispatcher` balance instead of only funds contributed by the current order, allowing residual/dust balances to be misattributed as escrow — (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s predispatch path measures how much of each input token was "actually received" by taking the *full current token balance* of the shared `_params.dispatcher` contract (`IERC20(token).balanceOf(dispatcher)`), sweeping all of it into the gateway, and then diffing against a `balancesBefore` snapshot taken on the *gateway*, not on the *dispatcher*. This is the same broken pattern as the reported ERC4626 bug: a balance snapshot is used to infer "what was newly contributed in this operation," but the snapshot/sweep boundary does not exclude value that was already resident in the shared intermediary contract before this specific call began. Any token balance sitting on the dispatcher (dust left behind by a previous order's predispatch execution, or tokens directly sent to the dispatcher by any third party) gets folded into the current order's `received` amount and can be credited into that order's escrow (`_orders[commitment][token]`), even though it was never contributed by the current order's own transfer.

### Finding Description
In the predispatch branch of `placeOrder`: [1](#0-0) [2](#0-1) 

The gateway:
1. Sends the user's predispatch assets into `dispatcher`.
2. Runs the user-supplied `order.predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)`.
3. For each input token, reads `balance = IERC20(token).balanceOf(dispatcher)` — the dispatcher's *entire* current balance, not the delta produced by step 2 — and builds a `transfer(address(this), balance)` call that sweeps that whole amount back to the gateway.
4. Snapshots `balancesBefore[i]` on the *gateway* (`address(this)`), then after the sweep computes: [3](#0-2) 

`received` is the amount actually transferred into the gateway from the dispatcher's full balance. If `received <= order.inputs[i].amount`, the code trusts it completely and sets `order.inputs[i].amount = received`, which is then fee-adjusted and credited to escrow: [4](#0-3) 

The critical flaw is identical in kind to the external report: `balanceOf(dispatcher)` is read and swept as if it exclusively represents *this order's* contribution, but `dispatcher` (`_params.dispatcher`, a single contract instance shared across every `placeOrder` call and every user) can hold non-zero balances that did not originate from the current predispatch execution:
- A previous order's predispatch call may produce token balances on the dispatcher that are *not* part of that order's `order.inputs` list (e.g., swap/unwrap byproducts), leaving them stranded on the dispatcher after that order's sweep completes (the sweep only touches tokens enumerated in the *current* order's `inputs`).
- Anyone can transfer tokens directly to the dispatcher's address at any time.

Because the sweep is "whole balance," a later order that lists that same token as an input will have that stranded/donated balance folded into its own `received` computation with no way to distinguish it from genuinely-transferred order funds. This mirrors exactly the root cause described in the report: `_fees_underlying_totalBalances` (there) and `balanceOf(dispatcher)` (here) both conflate "balance currently sitting in the accounted contract" with "value freshly contributed by the current operation," and the surrounding logic (performance fee there, escrow crediting here) treats the whole reading as legitimate new value.

### Impact Explanation
This breaks escrow-accounting integrity, the core invariant IntentGatewayV2 must hold ("Bridged assets, order escrow, refunds ... must move exactly once and only to the rightful beneficiary and amount"). Concretely:
- An order's `commitment` (and hence its escrowed amount that solvers can claim) can be inflated using value that never came from that order's own caller-supplied transfer, but from stray balance left in the shared dispatcher by an unrelated prior order or a third party.
- Because `order.inputs[i].amount` feeds directly into the `commitment` hash and the `_orders[commitment][token]` escrow ledger, this is a case of "false state acceptance" of the deposited amount and a wrong-amount/wrong-attribution of escrowed funds — an unprivileged user can obtain escrow credit backed by funds they did not actually deposit for that order, at the expense of whichever prior transaction's residual balance is present at that moment.

### Likelihood Explanation
Exploitability depends on the dispatcher actually holding a spare balance of the exact token an attacker chooses as an input at the moment they call `placeOrder` with a predispatch call — a condition the attacker can also manufacture deterministically by simply sending tokens directly to the (publicly known, fixed) `_params.dispatcher` address immediately before calling `placeOrder`. Since `dispatcher` is a persistent, address-known, shared utility contract (not a per-order/per-transaction ephemeral instance), a caller can pre-fund it and then rely on the "whole balance sweep" to have those funds counted without going through the risk/logic of the predispatch call actually producing them. This is a fully permissionless, single-transaction-controllable primitive.

### Recommendation
Do not read/sweep the dispatcher's total balance. Instead, snapshot the dispatcher's per-token balance *before* the predispatch call executes and only sweep/credit the delta produced by that specific call (`balanceAfterPredispatch - balanceBeforePredispatch`), analogous to how the non-predispatch branch correctly diffs `address(this)` balance around its own `safeTransferFrom`. Any residual dispatcher balance not attributable to the current call should either be swept to a protocol-controlled sink on its own accounting path (not folded into a user order) or left untouched.

### Proof of Concept
Conceptual PoC (dispatcher/predispatch flow):
1. Order X is placed by user A with a predispatch call that unwraps an LP token, producing an unlisted byproduct token `T` on the dispatcher that isn't part of `order.inputs`. After Order X's sweep completes, some balance of `T` remains stuck on `dispatcher` (`balanceOf(dispatcher, T) > 0`), because the sweep only iterates over `order.inputs` tokens.
2. Attacker B calls `placeOrder` with `order.inputs` containing token `T` with `requiredAmount = R`, and a trivial/no-op predispatch call that transfers a smaller amount `r < R` of `T` into `dispatcher`.
3. At the sweep step, `balance = IERC20(T).balanceOf(dispatcher)` equals `r + (leftover from Order X)`, which can be `>= R` even though B only funded `r`.
4. `received = r + leftover`; since `received <= order.inputs[i].amount` (or exceeds it and gets counted as dust — either way B's `_orders[commitment][T]` escrow is credited using funds not exclusively contributed via B's own transfer), the commitment/escrow for B's order is backed partly by residual value not genuinely deposited by B for that order.

Because verifying the precise magnitude of exploitable dust in production (whether predispatch calldata realistically leaves non-listed-token residues, and whether `CallDispatcher.sol`'s full implementation permits arbitrary donation) requires reviewing `evm/src/utils/CallDispatcher.sol` in full — which the indexed context did not surface completely — a Devin session with full repo access should confirm the exact byproduct/residue conditions and reproduce this with a Foundry test before remediation.
