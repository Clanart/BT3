### Title
`SignableTransaction::new` omits the OP_RETURN output from fee and weight calculation, causing the transaction to pay a lower fee rate than requested - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The `data` parameter adds an OP_RETURN output to `tx_outs`, but `calculate_weight_vbytes` is invoked with only `payments` — never `tx_outs` — so the OP_RETURN output's weight (roughly `12 + data_len` vbytes, up to ~92 vbytes for 80 bytes of data) is excluded from `vbytes`/`vbytes_with_change` and therefore from `needed_fee`. This is the same bug class as the report: a fee computed before/without accounting for an adjustment made to the transaction. The change amount is then computed as `input_sat - payment_sat - fee_with_change`, absorbing the difference, so the on-chain fee rate is lower than `fee_per_vbyte` and can fall below the minimum relay fee.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes the OP_RETURN output onto `tx_outs` before the fee calculation, yet `calculate_weight_vbytes` reconstructs the transaction only from the `payments` slice and an optional `change` script:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
```

`calculate_weight_vbytes` builds its scratch `Transaction` solely from `payments` and `change`; the OP_RETURN output already committed to `tx_outs` is invisible to it. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` under-counts by `fee_per_vbyte * (OP_RETURN output vbytes)` (~up to 92 vbytes for the maximum 80-byte payload).
- When a change output is created, `change = input_sat - payment_sat - fee_with_change` over-allocates the change by the same omitted amount, and the actual fee paid (`sum(inputs) - sum(outputs)`, per `fee()`) equals the under-estimated `needed_fee` — the real transaction has a larger vsize, so its effective sat/vbyte is lower than `fee_per_vbyte`.
- The `weight` value compared against `MAX_STANDARD_TX_WEIGHT` also excludes the OP_RETURN output, so a transaction at the boundary can pass the check while exceeding the standard weight limit on the wire.

### Impact Explanation
Any caller that supplies `data` produces a transaction whose true fee rate is below the requested `fee_per_vbyte`. At low fee rates the effective rate can drop below `DEFAULT_MIN_RELAY_TX_FEE` (1 sat/vbyte), making the signed transaction unrelayable — payments that the signing set believed were broadcast never confirm, and the spent inputs remain locked until a replacement is signed. Additionally, the too-large-transaction check can be bypassed by up to ~92 vbytes (~368 weight units), yielding a non-standard transaction that peers will reject. The threshold signing machine (`TransactionMachine`) will faithfully sign this malformed/under-priced transaction, so the error surfaces only after broadcast failure — funds are reported sent but the transaction cannot propagate.

### Likelihood Explanation
The defect is deterministic and triggers on every call that passes `Some(data)` with a change output or tight input margins — no adversarial condition is needed, only a caller using the OP_RETURN facility. The impact magnitude grows with `data` length and `fee_per_vbyte`. Whether the resulting transaction is non-relayable depends on network fee conditions and how close `fee_per_vbyte` is to the relay minimum; at high fee rates the transaction still confirms but pays less than specified (or over-burns leftover funds when no change is used). This is a consistent accounting error rather than an edge case.

### Recommendation
Include the OP_RETURN output in the weight/fee calculation. The cleanest fix is to make `calculate_weight_vbytes` take the actual `tx_outs` (or compute vbytes from the real transaction being built) rather than from `payments`, e.g.:

```diff
-   let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
+   let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
```

with `calculate_weight_vbytes` mapping over the already-built `tx_outs` and pushing a placeholder change output only when needed. The change-branch recalculation must likewise include the OP_RETURN output. Alternatively, keep `payments` but pass a flag/extra output size so the OP_RETURN script's serialized length is added to the weight before deriving `vbytes` and `needed_fee`.

### Proof of Concept
Conceptual test for `networks/bitcoin/tests/wallet.rs`:

```rust
let payments = [(p2tr_script_buf(key).unwrap(), 10_000)];
let change_addr = p2tr_script_buf(change_key).unwrap();
let data = vec![0xAA; 80]; // max allowed OP_RETURN payload

let tx = SignableTransaction::new(
  vec![output], &payments, Some(change_addr), Some(data), fee_per_vbyte,
).unwrap();

// The real transaction has 3 outputs: payment, OP_RETURN, change
assert_eq!(tx.transaction().output.len(), 3);

// needed_fee was computed as if the OP_RETURN output did not exist
let actual_vsize = /* signed tx vsize */;
// The actual paid fee equals needed_fee, so effective rate < fee_per_vbyte
assert!(tx.needed_fee() < actual_vsize * fee_per_vbyte);
```

Because `calculate_weight_vbytes(tx_ins.len(), payments, ...)` never sees the OP_RETURN `TxOut`, `needed_fee` is short by `fee_per_vbyte * (op_return_vbytes)`, the change output absorbs the difference, and the broadcast transaction's true feerate is below `fee_per_vbyte` — matching the report's pattern of a fee computed before the adjustment it should have accounted for.
