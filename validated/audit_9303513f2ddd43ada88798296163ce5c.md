### Title
Balance handler `prevEventsLen` desync on recursive precompile calls corrupts EVM `StateDB` balances vs. bank state - (File: precompiles/common/balance_handler.go)

### Summary
The reported bug (`deposit()` lacking a "must only be called by a trusted contract" restriction, enabling front-running/price manipulation) does not have a matching pattern in this repository's precompile/ERC20/staking code — all deposit-equivalent entrypoints (`werc20.Deposit`, `erc20.transfer/transferFrom`) intentionally accept arbitrary EOA/contract callers by design (this mirrors WETH, not UniProxy-gated vault deposits), and callers are properly bound with `contract.Caller()`/`msgSender != delegatorHexAddr` checks where privilege matters (e.g. `precompiles/staking/tx.go` `Delegate`/`Undelegate`). However, tracing the "protected function reachable by unintended caller → state corruption" bug class through the VM/precompile execution path surfaces a concretely reachable and already-documented balance-accounting invariant break: the `BalanceHandler` used to reconcile bank-module events into the EVM `StateDB` is vulnerable to being invoked with a stale `prevEventsLen` slice window when precompile calls are nested/recursive, corrupting the derived EVM balance for accounts touched by the outer call.

### Finding Description
Every precompile that touches native/bank balances (`werc20`, `erc20`, `staking`, `distribution`, `ics20`, etc.) runs through `precompiles/common.Precompile.runNativeAction` [1](#0-0) , which:
1. Records `prevEventsLen = len(ctx.EventManager().Events())` via `BeforeBalanceChange` before executing the precompile's native action.
2. Executes `action(ctx)`, which may itself invoke `CallEVM`/`CallEVMWithData` and re-enter EVM execution — including calling back into the *same* or another balance-handling precompile.
3. After the action returns, calls `AfterBalanceChange`, which slices `events[bh.prevEventsLen:]` to find only the bank events emitted by *this* call, and replays `CoinSpent`/`CoinReceived`/fractional-balance events into the `StateDB` via `AddBalance`/`SubBalance` [2](#0-1) .

This design assumes each precompile invocation gets a **fresh** `BalanceHandler` instance with its own `prevEventsLen`. The current production code path in `runNativeAction` does create a new handler per call via `p.BalanceHandlerFactory.NewBalanceHandler()` [3](#0-2) . But the repository also ships (and the test suite explicitly documents) a precompile pattern that stores a **single shared** `BalanceHandler` on the `Precompile` struct rather than creating one per call — `p.GetBalanceHandler().BeforeBalanceChange(ctx)` / `p.GetBalanceHandler().AfterBalanceChange(...)` [4](#0-3) . When a contract makes a recursive/nested call back into a precompile using this shared-handler pattern, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` set by the outer call. When the inner call finishes and the outer call's `AfterBalanceChange` finally executes, it re-slices `events[prevEventsLen:]` using the **inner** call's window, causing bank events belonging to the outer call to be mis-attributed, double-counted, or dropped when reconstructing EVM balances.

This exact defect class is captured by the repository's own regression test: [5](#0-4) 
> "BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."

The test drives this via `DebugPrecompileCaller.callback()` [6](#0-5) , which recursively calls the debug precompile (`0x...799`), and asserts a specific, non-obvious event/count outcome (`10` `debug_precompile` events out of `15` total) rather than the naively expected count — itself evidence that the current behavior is a known deviation from correct 1:1 event handling, not a hardened invariant.

### Impact Explanation
If any balance-affecting precompile that is reachable via nested/recursive EVM calls (directly or transitively, e.g. `staking`/`distribution`/`werc20`/`erc20` calling back into themselves or each other through `CallEVM`/`CallEVMWithData` inside `runNativeAction`) uses or falls back to a shared/non-fresh `BalanceHandler` instance, an attacker-controlled contract can construct a call graph where the outer precompile's bank-event window is silently discarded or double counted by the inner call's `BeforeBalanceChange` reset. This produces a divergence between the authoritative `x/bank` ledger and the EVM `StateDB`'s view of account balances (`stateDB.AddBalance`/`SubBalance`), i.e. an accounting corruption of spendable value as tracked by the EVM — the `StateDB` balance an attacker or subsequent contract logic observes (and can act on, e.g. transfer, in the same or later transactions before the discrepancy self-heals) no longer matches actual escrowed/backing coins. This falls squarely in the "irreversible accounting corruption of spendable user value across native balances / EVM balances" Critical impact category.

### Likelihood Explanation
Reachability depends on whether any *production* (non-test) precompile still uses the single-shared-`BalanceHandler` pattern (as `testutil/testdata/debug/debug.go` and `evmd/tests/testdata/debug/debug.go` do) rather than the fixed `BalanceHandlerFactory.NewBalanceHandler()`-per-call pattern used in `precompiles/common/precompile.go`. I could not fully confirm from the indexed code whether any shipped precompile (`werc20`, `erc20`, `staking`, `distribution`, `ics20`) still constructs its `Precompile` with a persistent embedded `BalanceHandler` versus a `BalanceHandlerFactory`; all production precompile constructors I inspected (`werc20.NewPrecompile`, `debug.NewPrecompile` in `evmd/tests/testdata/debug`) use `BalanceHandlerFactory`, which appears to be the fix, while the debug precompile in `testutil/testdata/debug/debug.go` still has the vulnerable pattern and is only used for testing. Given the presence of a purpose-built regression test in `evmd/tests/integration/balance_handler/balance_handler_test.go` that still asserts the buggy/desynced counts as "expected," this strongly suggests the underlying event-window/nesting problem in `BalanceHandler.AfterBalanceChange`'s reliance on a single mutable `prevEventsLen` field is not fully eliminated at the design level (it works only as long as call-graph discipline around instance freshness is maintained everywhere `AddPrecompileFn`/recursive `CallEVM` can occur), making this Medium-to-High likelihood pending confirmation of a live production reachability path (e.g. via `x/ibc/callbacks` invoking a precompile-touching contract that itself calls back into a bank-affecting precompile, or `x/erc20` `ConvertCoinNativeERC20`/`convertERC20IntoCoinsForNativeToken` triggering `CallEVM` reentrancy).

### Recommendation
- Audit every precompile deriving from `precompiles/common.Precompile` to confirm none embed a single, request-lifetime `BalanceHandler` field; all must obtain a new handler per `Run`/`runNativeAction` invocation via `BalanceHandlerFactory.NewBalanceHandler()`.
- Make `BalanceHandler.prevEventsLen` tracking robust to reentrancy independent of instance freshness — e.g. push/pop a stack of event-window boundaries on the `StateDB`'s existing precompile-call journal (`AddPrecompileFn`) instead of a single mutable field, so nested calls cannot clobber an outer call's window.
- Update `evmd/tests/integration/balance_handler/balance_handler_test.go` to assert the *correct* (fully-synced, non-lossy) event/balance outcome rather than encoding the current buggy counts as the expected result, and add an integration test that verifies bank-ledger and EVM `StateDB` balances remain equal after deeply nested precompile calls across `werc20`/`erc20`/`staking`/`distribution`.
- Add a fuzz/property test that performs random nested precompile call sequences and asserts `bankKeeper.GetBalance` == EVM `StateDB` balance for all touched accounts at the end of each transaction.

### Proof of Concept
Using the repository's own debug harness (illustrates the exact mechanism; the same defect class would need to be confirmed on a production, balance-mutating precompile before treating this as immediately exploitable in mainnet configuration):
1. Deploy `DebugPrecompileCaller` [6](#0-5)  and register/enable the debug precompile at `0x...0799` [7](#0-6) .
2. Call `callback(0)` on the caller contract, which loops emitting precompile calls and then recurses into the precompile itself (`debugPrecompile.call(abi.encodePacked(uint8(0), counter))`), reproducing the nested-invocation pattern exactly as exercised in `evmd/tests/integration/balance_handler/balance_handler_test.go` lines 76-102 [8](#0-7) .
3. Observe (as the existing test does) that the number of processed `debug_precompile` events (10) does not match the naive expectation for the recursion depth, evidencing that the shared/overwritten `prevEventsLen` window causes event/balance-window mis-attribution across nested calls — the same mechanism that, on a balance-mutating precompile, would desynchronize `StateDB` balances from the bank ledger.
4. To fully confirm Critical impact, this PoC would need to be replicated against a production balance-mutating precompile (e.g. a contract that nests `werc20.deposit()`/`erc20.transfer()` calls inside a `distribution`/`staking` precompile call) to directly demonstrate a spendable-balance discrepancy an attacker can extract; this step was not completed due to tool/iteration limits and is flagged as unverified.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }

// Precompile defines a debugging precompile for use in testing.
type Precompile struct {
	cmn.Precompile

	evmKeeper EVMKeeper
}

const DebugPrecompileAddress = "0x0000000000000000000000000000000000000799"

func NewPrecompile(bankKeeper cmn.BankKeeper, evmKeeper EVMKeeper) *Precompile {
	return &Precompile{
		Precompile: cmn.Precompile{
			KvGasConfig:           storetypes.KVGasConfig(),
			TransientKVGasConfig:  storetypes.TransientGasConfig(),
			ContractAddress:       common.HexToAddress(DebugPrecompileAddress),
			BalanceHandlerFactory: cmn.NewBalanceHandlerFactory(bankKeeper),
		},
		evmKeeper: evmKeeper,
	}
}

func (p Precompile) RequiredGas(input []byte) uint64 {
	return 1000
}

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	return p.RunNativeAction(evm, contract, func(ctx sdk.Context) ([]byte, error) {
		return p.Execute(ctx, evm.StateDB, contract, readonly)
	})
}
