### Title
BIP-340 signing and wallet scanning cannot handle odd-parity group keys — funds sent to the x-only address are unspendable (networks/bitcoin/src/crypto.rs, networks/bitcoin/src/wallet/mod.rs)

### Summary
The Debita bug hardcodes `token1` as the supported position even though the token ordering in the pool is externally determined (sorted by address), so tokens that land in `token0` cannot be supported at all. The analogous shape in Serai is Bitcoin's externally-imposed parity requirement: BIP-340/Taproot x-only keys are implicitly even-Y, so a secp256k1 point sits in the equivalent of either the `token0` (even) or `token1` (odd) position with ~50% probability, and the signer cannot control which. The Bitcoin wallet code only supports the "even" position: `Scanner::new` returns `None` for odd keys, and the FROST `Schnorr` algorithm's `verify` never negates the key contribution for an odd group key, so any output receivable at the x-only address derived from an odd group key can never be signed for.

### Finding Description
`p2tr_script_buf` refuses to produce an address for odd keys, returning `None` when the point's compressed tag is not `CompressedEvenY` (`networks/bitcoin/src/wallet/mod.rs:80-86`). `Scanner::new` propagates that `None`, so no `ReceivedOutput` can ever be registered under an odd group key (`networks/bitcoin/src/wallet/mod.rs:162-166`). `register_offset` normalizes derived keys by incrementing the offset until the point is even, but performs no equivalent normalization for the base key itself (`networks/bitcoin/src/wallet/mod.rs:180-196`).

On the signing side, BIP-340 requires the effective secret key to correspond to the even-Y lift of the x-only public key — i.e., if the group key `A` is odd, the key contribution in `s = r + c·x` must be negated. `Hram::hram` hashes `x(A)` (parity-agnostic, correct), and `Schnorr::verify` only conditionally negates `s` based on the parity of `R`, never on the parity of `A` (`networks/bitcoin/src/crypto.rs:59-73`, `networks/bitcoin/src/crypto.rs:139-150`). `verify_share` similarly passes the verification share through unmodified (`networks/bitcoin/src/crypto.rs:152-159`). There is a `needs_negation` helper that is applied to `R` but never to the group key (`networks/bitcoin/src/crypto.rs:26-28`).

Consequently, for an odd group key `A`, the threshold signature verifies against the *unnegated* point, while Bitcoin verifies against the even lift `-A`, producing invalid signatures for a perfectly valid on-chain address.

### Impact Explanation
Medium. Any P2TR output paying to `x(A)` of an odd group key is accepted by the Bitcoin network but is unspendable by the multisig: the scanner refuses to track it, and even if forced through, the produced BIP-340 signature fails consensus verification because the key contribution is never negated. This mirrors the MixOracle report exactly — a core function (receiving/spending BTC) is silently broken for an externally-determined "position" (~50% of possible group keys) rather than for any cryptographic reason.

### Likelihood Explanation
Whether this is triggerable in the deployed system depends on whether callers upstream of `networks/bitcoin` guarantee even group keys (e.g., via `tweak_keys` in the processor, whose body I could not fully verify — if it applies an additive tweak, parity remains ~50%). Within the in-scope crates themselves there is no normalization, and `Scanner::new`'s `Option` return plus `register_offset`'s increment-until-even loop show the authors were aware of the parity constraint but only handled it for offset-derived keys, not the base key. An unprivileged party who learns the multisig's x-only address can send BTC to it regardless of parity; the unspendability then manifests on-chain.

### Recommendation
Do not reject odd keys. Either (a) negate the group key/secret-share contribution when `needs_negation(A)` is true — applying the negation inside `Hram`/`verify`/`verify_share` or as a scalar offset of `-1`-equivalent handling in the view — so the even-Y lift is always what is signed for, or (b) enforce even parity at key-generation/tweak time and assert it in `Scanner::new` callers. `register_offset`'s increment-until-even approach shows the codebase already tolerates parity normalization for derived keys; the same must hold for the base key.

### Proof of Concept
```rust
// networks/bitcoin: odd group key is unspendable
let key = loop { let k = ProjectivePoint::random(&mut OsRng);
  if needs_negation(&k).into() { break k } }; // odd Y

// 1. Scanner refuses it entirely
assert!(Scanner::new(key).is_none());           // wallet/mod.rs:162-166

// 2. Yet x(A) is a valid P2TR output key; anyone can fund it on-chain.
//    Signing with share a (for A) yields s = r + c*a which verifies
//    under A, but BIP-340 verifies under the even lift -A => invalid sig.
//    crypto.rs:145-148 negates s only on needs_negation(R), never on A.
```
A regtest PoC: generate `ThresholdKeys` until `group_key()` is odd, form the address via `x_only`, send an output to it on regtest, then attempt `SignableTransaction::new(...).multisig(&keys).sign(...)` — the resulting transaction fails `OP_CHECKSIG` verification because the signature's key component has the wrong sign.
