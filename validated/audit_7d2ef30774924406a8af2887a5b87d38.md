## Title
Copilot-generated conflict resolutions are written to disk and staged without verifying the path was an actual unresolved conflict - (`app/src/lib/stores/app-store.ts`)

## Summary
In `_applyCopilotConflictResolutions`, Desktop writes AI-produced file content to disk and stages it for commit using only a path-traversal check (`resolveWithin`) plus a check that skips files the user *already* resolved externally. It never validates that `resolution.path` corresponds to a file that was actually part of the current merge conflict set before writing `resolution.resolvedContent` to it and running `git add` on it.

## Finding Description
`_applyCopilotConflictResolutions` iterates the `copilotResolutions` array that was produced by the AI conflict-resolution flow and, for each non-delete resolution: [1](#0-0) 

1. Resolves `resolution.path` against the repo root and rejects only if it escapes the repository (`resolveWithin` returning `null`).
2. Looks up `onDiskFile` for that path in the *current* `workingDirectory.files` snapshot, but only uses it to **skip** writing when the file is a conflict that has already been resolved externally by the user. If `onDiskFile` is `undefined` (the path is not reported by `git status` as modified/conflicted at all, e.g. an untouched tracked file elsewhere in the working tree) or is a status that doesn't satisfy `isConflictedFileStatus && !hasUnresolvedConflicts`, execution falls straight through to the write.
3. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` overwrites that file's contents unconditionally.
4. The path is pushed to `pathsToStage` and later staged with `git add -- <paths>`.

There is no check anywhere in this function that `resolution.path` is a member of the set of files the multi-commit-operation actually flagged as conflicted (`conflictState`/`manualResolutions` keys are only consulted to *skip* a resolution, not to *validate* the whole list). The `copilotResolutions` array itself originates from an AI/LLM turn that reads repository content (including the very conflict markers an attacker controls in a crafted repository) and is stored as untrusted structured output in `multiCommitOperationState.copilotResolutions`.

## Impact Explanation
Because the write+stage path trusts `resolution.path`/`resolution.resolvedContent` pairs without cross-checking them against the actual conflict set, a manipulated or hallucinated resolution entry (e.g., from a prompt-injection payload embedded in conflict markers of an attacker-controlled merge, or from a tampered Copilot API response) can cause Desktop to silently overwrite and stage an unrelated, unmodified tracked file in the repository. The user only reviews the conflicts shown in the result dialog; a collateral file written and `git add`-ed this way is committed without the user ever seeing or approving that diff — a direct "silent corruption of what the user commits" scenario, analogous to the underlying report's use of an unvalidated value (`baseBalance`) instead of the intended, checked one (`amount`).

## Likelihood Explanation
This requires the user to be actively using the Copilot conflict-resolution feature during a merge/rebase and for the resolution list to contain an entry whose `path` does not match a currently-conflicted file (via a compromised/mismatched API response or a model led astray by attacker-crafted repository content). It does not require local access, elevated privileges, or pre-existing malware — the attacker's leverage is entirely through content that ends up in the repository/API response the AI reads and the model output Desktop trusts.

## Recommendation
Before writing/staging any `resolution`, cross-reference `resolution.path` against the authoritative set of conflicted files captured when the Copilot run started (e.g., `conflictState.conflictedFiles`), and reject/skip any resolution whose path is not in that set — in addition to the existing `resolveWithin` traversal check and the already-resolved-externally check.

## Proof of Concept
Not independently exploitable end-to-end without the Copilot backend/response format, but conceptually:
1. Trigger a merge/rebase that surfaces conflicts and enable the Copilot conflict-resolution flow.
2. Have `copilotResolutions` include a resolution entry for a path that is not among the files reported as conflicted by `git status` (e.g., an existing clean, tracked file elsewhere in the repo) with attacker-chosen `resolvedContent`.
3. Click "Continue Merge" — `_applyCopilotConflictResolutions` writes the attacker-chosen content to that unrelated file and stages it via `git add`, without ever displaying that file's diff to the user.

Note: I could not verify from the index whether `copilotResolutions` is filtered elsewhere (e.g., server-side or in an earlier reducer) to only contain paths from the original conflict set — this uncertainty affects the actual reachability of the bug and should be confirmed in a full checkout of the repository (the index has size limits and may not include every file/branch involved in the Copilot conflict-resolution feature).
