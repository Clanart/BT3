### Title
Inconsistent HTML/XSS-safe escaping of `<` and `>` in ProtoJSON string encoders (upb-based and PHP native `json_encode`) - ([File: upb/json/encode.c])

### Summary
Fleet's XSS report shows the failed invariant: attacker-influenced data reaches a browser/JS execution context without the escaping that the code elsewhere assumes is applied, because one code path (Windows MDM auth flow) fails to neutralize HTML/script metacharacters that another path relies on being neutralized. The Protobuf analog is a real, provable divergence between official ProtoJSON string encoders: some implementations explicitly escape `<`, `>` (and related characters) specifically "to prevent security bugs in JavaScript" when a string field is serialized to ProtoJSON, while other official implementations of the *same* ProtoJSON spec do not, silently emitting raw `<script>`-class payloads.

### Finding Description
The C++ `internal::json::writer.cc` encoder and the Java `JsonFormat.java` encoder both contain an explicit, intentional invariant: string field values are escaped so that HTML/JS metacharacters (`<`, `>`, and in Java's case also `&`, `=`, `'`) never appear unescaped in ProtoJSON output, with comments stating this is done "to prevent security bugs in JavaScript" / to avoid closing an embedded `<script>` tag: [1](#0-0) [2](#0-1) 

This is a deliberately-tested contract, confirmed by regression tests such as `testHtmlEscape` (referencing bug b/73832901, "Make sure html tags are escaped") and the C++ `JsonTest.HtmlEscape` test, both asserting that a string field containing `</script>` is emitted as `\u003c/script\u003e`: [3](#0-2) [4](#0-3) 

However, the upb-based JSON encoder — used natively by the PHP and Ruby C extensions (and by any upb-backed binding) — implements only the JSON-spec-mandated escapes (`\n \r \t \" \f \b \\` and control chars `< 0x20`) and never escapes `<` or `>`: [5](#0-4) [6](#0-5) [7](#0-6) 

The pure-PHP fallback encoder (`GPBJsonWire.php`) is even weaker: for `GPBType::STRING` it simply calls PHP's native `json_encode($value, JSON_UNESCAPED_UNICODE)` without the `JSON_HEX_TAG` flag, which by PHP semantics never escapes `<`/`>`: [8](#0-7) 

The invariant that transfers from the Fleet report is: "attacker-controlled string data that will be embedded into a browser/JS context must have HTML/script metacharacters neutralized by the layer the consuming application trusts to have already done so." Java/C++ codify and test this exact invariant for ProtoJSON. The upb C encoder and PHP's native-`json_encode` path are missing that check, so a consuming web application written against PHP, Ruby, or any upb-backed binding — one that (reasonably, given Java/C++'s documented and tested behavior) assumes ProtoJSON already neutralizes `<`/`>` before embedding a message's JSON representation into an HTML page or a `<script>` block — receives unescaped script-breaking sequences from those bindings.

### Impact Explanation
If a downstream application embeds ProtoJSON output of an untrusted string field (e.g., a device name, hostname, or user-supplied label) directly into an HTML document or inline `<script>` block — a common pattern, which is precisely why Java/C++ added the `<`/`>` escaping and its regression test — then:
- On Java/C++/C++-writer.cc-backed encoders, `</script><script>alert(1)</script>` is safely rendered as `\u003c/script\u003e...`, preventing script injection.
- On PHP (native encoder) and any upb-based encoder (PHP extension, Ruby extension, and other upb consumers), the same string is emitted with literal `<` and `>`, permitting the closing of an enclosing `<script>` tag and injection of attacker HTML/JS — the same CWE-79 class as the Fleet advisory, and with the same "compromise of an authenticated user session via reflected data" impact if the consuming app puts session-adjacent data through this path.

This does not affect binary wire-format security and requires a consuming application to embed ProtoJSON output unescaped in an HTML/JS context — consistent with the assumption stated in the rules that Protobuf itself has no public RPC endpoint and the exposure is via a consuming application.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) a consuming application using one of the affected bindings (PHP native path, or any upb-backed binding: PHP extension, Ruby extension) to serialize attacker-influenced string fields to ProtoJSON, and (b) that application to embed the resulting JSON text into an HTML/JS document without its own additional escaping. This mirrors exactly the pattern Java/C++ maintainers anticipated and hardened against (bug b/73832901), showing it is a realistic, previously-encountered usage pattern rather than a contrived one. It is lower likelihood than the original Fleet report only because it depends on the specific downstream binding and lack of additional app-level escaping, but the missing control is unconditional and always reachable within the affected encoders.

### Recommendation
- Align the upb JSON encoder (`upb/json/encode.c`, and its PHP/Ruby-embedded copies `php-upb.c`, `ruby-upb.c`) with the C++/Java/C# behavior by escaping `<` and `>` (and ideally `&`, `=`, `'` for parity) in `jsonenc_put_escaped_char`.
- Fix the pure-PHP `GPBJsonWire::stringifyValue`/STRING case to pass `JSON_HEX_TAG` (or perform manual `<`/`>` escaping) to PHP's `json_encode`, matching the Java/C++ documented ProtoJSON security contract.
- Add a cross-language conformance test (mirroring `testHtmlEscape` / `JsonTest.HtmlEscape`) to the shared conformance suite so this invariant is enforced consistently across all official ProtoJSON encoders (Java, C++, C#, upb/C, PHP, Ruby), rather than only in the language-specific test suites where it currently lives.
- Document explicitly in the ProtoJSON spec whether this escaping is a guaranteed cross-implementation contract; if it is not guaranteed, update the Java/C++ code comments (which currently imply a security guarantee) to avoid downstream teams building on an inconsistent assumption.

### Proof of Concept
Using a shared `.proto` schema with `optional string optional_string = 1;`, serialize the same value through two official encoders:

1. Java (`com.google.protobuf.util.JsonFormat.printer().print(...)`) or C++ (`google::protobuf::json::MessageToJsonString`) on a message with `optional_string = "</script><script>alert(1)</script>"`:
   - Output: `{"optionalString":"\u003c/script\u003e\u003cscript\u003ealert(1)\u003c/script\u003e"}` — safe, matches the asserted behavior in `testHtmlEscape`/`JsonTest.HtmlEscape`.
2. PHP (`(new Message())->serializeToJsonString()` via `GPBJsonWire::STRING` case) or any upb-backed binding, on the identical value:
   - Given `jsonenc_put_escaped_char`/`json_encode(..., JSON_UNESCAPED_UNICODE)` never special-case `<`/`>`, output is: `{"optionalString":"</script><script>alert(1)</script>"}` — the literal `</script>` closes an enclosing script block if the consuming page embeds this JSON string inline, reproducing the missing-check condition. This divergence is directly derivable from the cited encoder source (`upb/json/encode.c:268-311`, `GPBJsonWire.php:212-215`) versus the cited Java/C++ sources and their accompanying tests, without needing to execute code — the absence of any `<`/`>` case in the `MustEscape`-equivalent switch statements in the upb/PHP paths is the exact "check bypass" that lets the analog XSS payload through.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}
