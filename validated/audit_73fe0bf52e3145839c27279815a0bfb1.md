### Title
Deserialized Bitcoin outputs trust attacker-supplied value and outpoint without chain validation - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` directly from serialized input without proving that the referenced UTXO exists, has the claimed value, or is actually spendable by the expected group key. [1](#0-0)  The processor wrapper likewise accepts this embedded state through `Output::read`. [2](#0-1) 

### Finding Description
A scanned Bitcoin output is represented by a stored `offset`, serialized `TxOut`, and serialized `OutPoint`. [3](#0-2)  Deserialization reconstructs all three fields without deriving the output from chain data or checking the outpoint against a Bitcoin node. [1](#0-0) 

The processor reports the claimed `TxOut.value` as the output balance. [4](#0-3)  It derives the owning key from `script_pubkey - offset * G`, but an attacker can simply provide a real Serai Taproot script and offset `0`, causing the forged output to map to the expected key. [5](#0-4) 

That value is then used for scheduling and transaction construction. [6](#0-5)  `SignableTransaction::new` turns the supplied `ReceivedOutput`s into transaction inputs and prevouts, while `multisig` only checks that each stored script matches the offset group key, not that the outpoint exists or contains that value. [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged party who can supply serialized output bytes can cause Serai to report or schedule funds that were never received, or to inflate a real UTXO's value. The resulting spend is either based on a nonexistent outpoint or commits to the wrong Taproot prevout amount, producing signatures for a transaction Bitcoin will reject. [9](#0-8) 

### Likelihood Explanation
The attack requires only control over bytes passed to `Output::read` / `ReceivedOutput::read`; no validator key, malformed curve point, colluding threshold, or compromised Bitcoin node is required. Any deserialization boundary that restores outputs, active plans, refunds, forwards, or scheduler state can carry the forged fields into balance accounting and signing. [10](#0-9) [11](#0-10) 

### Recommendation
Do not treat serialized `ReceivedOutput` values as authoritative. Deserialize outputs into a checked scanner/RPC path that verifies the outpoint exists in the accepted chain, has the serialized `TxOut`, and has `script_pubkey == p2tr_script_buf(expected_key + offset * G)` before exposing its balance or using it as a transaction input. Alternatively, store only the outpoint and refresh the `TxOut` from the chain during validation. [12](#0-11) [13](#0-12) 

### Proof of Concept
Conceptually, for a known even group key `K`:

```rust
let forged = ReceivedOutput {
  offset: Scalar::ZERO,
  output: TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: p2tr_script_buf(K).unwrap(),
  },
  outpoint: OutPoint {
    txid: arbitrary_or_nonexistent_txid,
    vout: 0,
  },
};

let bytes = forged.serialize();
let restored = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
```

`restored.value()` reports `1_000_000` even though no such UTXO need exist. [14](#0-13)  Wrapping it in the processor's `Output` format causes `key() == K` and `balance().amount.0 == 1_000_000`, allowing the fake input to enter scheduling and signing flows. [15](#0-14)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
