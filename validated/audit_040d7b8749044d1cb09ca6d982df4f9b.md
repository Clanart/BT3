### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee weight calculation, silently under-charging the fee — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
The external report's class is "a designated amount/output the user is entitled to is never actually produced because the accounting omits it." In `bitcoin-serai`, `SignableTransaction::new` builds the final transaction's `tx_outs` including the OP_RETURN `data` output (line 194-202), but then calls `calculate_weight_vbytes` with only `inputs`, `payments`, and `change` — the helper reconstructs a mock transaction containing *only* payment outputs (and optionally change) to measure weight. The OP_RETURN output (up to 90 bytes) is never counted, so `needed_fee` is computed for a smaller transaction than the one actually produced. [1](#0-0) [2](#0-1) 

### Finding Description
`SignableTransaction::new` accepts a `data: Option<Vec<u8>>` parameter (up to 80 bytes), pushes a `TxOut` with `ScriptBuf::new_op_return` into `tx_outs`, and then computes `(weight, vbytes)` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — a signature that has no way to account for the data output. The same omission occurs in the change branch: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` under-prices the real transaction by roughly `(9 + data_len) vbytes * fee_per_vbyte` (output base + pushdata overhead + up to 80 bytes of payload). [3](#0-2) 
- The `TooLowFee` check compares this understated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, so a transaction whose *actual* fee rate falls below the minimum relay fee can pass validation.
- When `change` is supplied, the change amount is computed as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is also understated — the change output is slightly *over*-credited and the miner fee is under-paid relative to the requested `fee_per_vbyte`. [4](#0-3) 

The consumer-facing `fee()`/`needed_fee()` getters therefore report a fee commitment the constructed transaction does not satisfy.

### Impact Explanation
A `SignableTransaction` constructed with `data` advertises and is internally consistent around a fee that is lower than the caller-requested rate. In the worst case the true fee rate drops below the network minimum relay fee, so the signed transaction is rejected by the mempool — the inputs are committed to an eventuality (`txid()`) that cannot confirm until rebuilt, and any downstream logic relying on `needed_fee()` for accounting mis-prices the transaction. This is an incorrect fee/output-accounting formula, analogous to the report's "the amount owed is computed but never actually allocated to the output it belongs to."

### Likelihood Explanation
The bug is deterministic whenever `data` is `Some` — it does not depend on adversarial ordering or edge-case values, only on the public `data` parameter. The severity of the outcome scales with `data` length and how close the requested rate is to minimum relay. In-tree callers (the processor) currently pass `None` for `data`, which limits realized impact in the shipped composition, but the API is public and the defect is unconditional for any caller supplying data.

### Recommendation
Include the OP_RETURN output in the weight/size estimation. Either pass `tx_outs` (or the data payload) into `calculate_weight_vbytes`, or construct the mock transaction from the actual `tx_outs`/`tx_ins` already built so the estimated vbytes always matches the real transaction. Add a test asserting `needed_fee == vsize_of_final_tx * fee_per_vbyte` when `data` is `Some`.

### Proof of Concept
```rust
// Construct a tx with an 80-byte OP_RETURN payload.
let data = Some(vec![0u8; 80]);
let tx = SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte).unwrap();

// The real transaction includes the OP_RETURN output; needed_fee was computed
// from a mock transaction without it.
let real_vbytes = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < real_vbytes * fee_per_vbyte);
// Actual fee rate = fee() / real_vbytes < fee_per_vbyte, and may fall below
// the min relay fee even though TooLowFee was not returned.
```

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
