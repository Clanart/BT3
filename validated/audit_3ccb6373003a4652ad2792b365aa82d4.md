### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack exhaustion DoS - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes`/`AccountKeySerializer.DecodeRLP` for each embedded key without limiting nesting depth. The check that forbids a role-based key from containing another role-based key (`IsCompositeType` / `kerrors.ErrNestedCompositeType`) is only enforced afterward, in `CheckInstallable`/`CheckUpdatable`, i.e. after decoding has already completed. This mirrors CVE-2019-6293's root cause pattern: a decoder recurses on attacker-controlled nested structure before any bound/guard is applied, allowing stack exhaustion.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte-blobs and, for each blob, calls `rlp.DecodeBytes(b, &serializer)`, which dispatches to `AccountKeySerializer.DecodeRLP`: [1](#0-0) [2](#0-1) 

`AccountKeySerializer.DecodeRLP` reads the encoded `keyType`, constructs a fresh `AccountKey` via `NewAccountKey`, and if that type is again `AccountKeyTypeRoleBased`, it re-enters `AccountKeyRoleBased.DecodeRLP` — a mutually recursive call chain with no depth counter: [3](#0-2) 

The only nesting restriction in the codebase, `IsCompositeType()`/`ErrNestedCompositeType`, is checked in `CheckInstallable` and `CheckUpdatable` — both of which run *after* the full RLP tree has already been decoded into memory: [4](#0-3) [5](#0-4) 

The `rlp` package itself contains no nesting-depth limiter; the search for `maxNestingDepth`/depth counters in `rlp/*.go` returned no results, so decoding depth is bounded only by the size of the RLP payload and available call stack, not by any explicit sanity check.

This decode path is reachable directly from public, unprivileged surfaces:
- `KaiaAPI.DecodeAccountKey`, a public RPC method, calls `rlp.DecodeBytes(encodedAccKey, &dec)` directly on caller-supplied bytes with no size/nesting validation before decoding: [6](#0-5) 
- Any `TxTypeAccountUpdate` (or fee-delegated variants) transaction submitted via `eth_sendRawTransaction`/txpool `AddRemote` carries an RLP-encoded `AccountKey` field that is decoded during transaction deserialization, before pool/tx semantic validation (which is where `ErrNestedCompositeType` is ultimately raised) runs.

### Impact Explanation
Because the recursive decode occurs before the nested-composite-type check, an attacker can craft a payload consisting of many levels of `AccountKeyRoleBased` wrapping (`type=RoleBased -> [type=RoleBased -> [type=RoleBased -> ...]]`), each level only costing a few RLP bytes, to drive the recursion depth arbitrarily high relative to payload size. This can exhaust the goroutine stack processing the RPC call or the transaction-pool/block-import goroutine, causing a process crash (denial of service). If triggered during block processing/transaction application on multiple nodes simultaneously (e.g., via a crafted transaction accepted into a block), it could cause a crash across honest nodes, which is more severe than a single RPC crash.

### Likelihood Explanation
The attack requires no special privileges — it can be triggered by:
1. Any public RPC caller invoking `kaia_decodeAccountKey` with crafted hex bytes, or
2. Any unprivileged transaction sender submitting a `TxTypeAccountUpdate`/fee-delegated account-update transaction with a crafted `AccountKey` payload via standard `eth_sendRawTransaction`.

The payload can be constructed entirely offline and the RLP encoding overhead per nesting level is small (a handful of bytes per level), so achieving thousands of nesting levels is inexpensive in terms of raw transaction size. This makes the likelihood of triggering the recursion straightforward, assuming Go's stack-growth behavior does not intervene gracefully (Go goroutines grow their stack up to a limit — typically 1GB by default — before triggering a fatal `runtime: goroutine stack exceeds limit` crash, which is unrecoverable via `recover()`).

### Recommendation
Add an explicit nesting-depth check to `AccountKeyRoleBased.DecodeRLP` (and/or `AccountKeySerializer.DecodeRLP`) that rejects any `AccountKeyRoleBased` value whose embedded keys are themselves composite types (i.e., reject during decode, not only during `CheckInstallable`/`CheckUpdatable`). Alternatively, thread a depth counter/limit through the decode call chain (similar to Go's `encoding/json` recursion guard) and return an error once a small maximum depth (e.g., 1, since role-based keys are documented to never legitimately contain role-based children) is exceeded. Apply the equivalent depth guard to `KaiaAPI.DecodeAccountKey` prior to calling `rlp.DecodeBytes`.

### Proof of Concept
1. Construct nested account-key RLP bytes recursively (conceptually, in Go):
```go
// buildNestedRoleBased(depth) returns RLP bytes of AccountKeySerializer
// whose "key" is an AccountKeyRoleBased containing another
// AccountKeySerializer of the same nested shape, `depth` levels deep.
func buildNestedRoleBased(depth int) []byte {
    inner := buildLegacyOrBase() // base case: any non-composite key
    for i := 0; i < depth; i++ {
        roleBased := accountkey.NewAccountKeyRoleBasedWithValues([]accountkey.AccountKey{
            mustDecodeKey(inner),
        })
        ser := accountkey.NewAccountKeySerializerWithAccountKey(roleBased)
        inner, _ = rlp.EncodeToBytes(ser)
    }
    return inner
}
```
2. Submit the resulting bytes to the public RPC method `kaia_decodeAccountKey(encodedAccKey)` (`KaiaAPI.DecodeAccountKey`, [6](#0-5) ) with a sufficiently large `depth` (e.g., tens of thousands of nesting levels).
3. Observe the RPC-serving goroutine recurse through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` ... until the goroutine stack is exhausted, crashing the node process (or, alternatively, submit the same payload as the `AccountKey` field of a signed `TxTypeAccountUpdate` transaction via `eth_sendRawTransaction` to trigger the same recursive decode during transaction ingestion).

*Note: I was unable to fully trace every call site that decodes `AccountKey` from raw transactions end-to-end (e.g., the exact `DecodeRLP` implementation of `TxInternalDataAccountUpdate`) within the available search iterations; confirming the exact code path from `eth_sendRawTransaction` to `AccountKeyRoleBased.DecodeRLP` would benefit from a full Devin session with direct repository access.*

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
