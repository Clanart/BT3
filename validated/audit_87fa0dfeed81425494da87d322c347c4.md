### Title
Untrusted `ReceivedOutput` bytes are never bound to the spend key, allowing outputs to be reported received that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an attacker-controlled scalar `offset`, `TxOut`, and `OutPoint` with no check that `output.script_pubkey` is the P2TR script derived from the group key plus `offset`. The Scanner is the only component that binds `script_pubkey → offset`, and that binding is lost on serialization. This is the analog of the Storm path traversal: untrusted input selects an internal resource (here, the derived spend key / credited deposit) that was never validated against the referenced object.

### Finding Description
`ReceivedOutput::read` reads `offset` via `Secp256k1::read_F` and then consensus-decodes an arbitrary `TxOut` and `OutPoint`, returning them as a unit with no consistency check [1](#0-0) . The only place a script is validated against an offset is `Scanner::scan_transaction`, which looks up `self.scripts.get(&output.script_pubkey)` [2](#0-1) . Once serialized via `ReceivedOutput::write`/`serialize` [3](#0-2) , that binding is gone: a consumer that later calls `read()` trusts whichever `offset`/`output`/`outpoint` triple the bytes claim.

### Impact Explanation
An unprivileged party supplying bytes to `ReceivedOutput::read` (e.g., a deposit claim submitted to a processor/coordinator) can claim an output was received under one offset while the embedded `TxOut` actually pays an unrelated script. The wallet treats it as a received output (`value()`, `output()`, `outpoint()` all reflect attacker data [4](#0-3) ), credits the deposit, but when it tries to spend, it applies `offset` to the threshold key — the resulting signature cannot satisfy the claimed `script_pubkey`. Result: funds reported received that are not spendable, breaking accounting and enabling deposit fraud where a counterparty is credited for a UTXO the group key cannot ever spend.

### Likelihood Explanation
Any flow where serialized `ReceivedOutput`s cross a trust boundary (processor submits scanned outputs to the coordinator, or outputs are persisted and re-read) exposes this. The format has no MAC, no key context, and `read()` cannot detect a swapped or fabricated `TxOut`/offset pair.

### Recommendation
Either re-derive and verify the binding at `read` time (store/check the scanner key and assert `output.script_pubkey == p2tr_script_buf(key + G*offset)`, rejecting odd-parity/mismatched outputs), or treat `ReceivedOutput` as untrusted until re-scanned and never serialize it as an authoritative claim.

### Proof of Concept
1. Attacker creates a real UTXO paying any P2TR script they control (or a random script), with `TxOut T` and `OutPoint P`.
2. Attacker serializes `ReceivedOutput { offset: 0, output: T, outpoint: P }` — i.e., `Scalar::ZERO.to_bytes() || serialize(T) || serialize(P)` — and submits it where the wallet calls `ReceivedOutput::read`.
3. `read` succeeds [1](#0-0) ; wallet reports a deposit of `T.value`.
4. Spend attempt: signing derives `group_key + 0*G`, producing a BIP-340 signature for the wallet's own key, which does not match `T.script_pubkey`; the spend is invalid and the credited funds are unspendable.

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
