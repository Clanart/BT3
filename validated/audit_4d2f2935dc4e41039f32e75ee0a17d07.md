### Title
Shared `BalanceHandler` instance causes `prevEventsLen` to be overwritten on recursive precompile calls, silently dropping balance-change events and desyncing StateDB from x/bank - ([File: precompiles/common/balance_handler.go])

### Summary
This is a direct structural analog of the reported `TroveManager.openTrove` bug: a "before" snapshot value (`totalActiveDebtPre` / here `prevEventsLen`) is cached, an intermediate state-mutating operation is allowed to run and change the canonical counter, and the code that later consumes the cached snapshot uses a stale/overwritten value instead of the value that was valid when the snapshot was taken — silently erasing part of the recorded delta. In `TroveManager` this erased accrued interest; in Cosmos EVM's `BalanceHandler` this erases bank balance-change events, corrupting the sync between the canonical `x/bank`/`x/precisebank` balances and the EVM `StateDB` balances used for the remainder of the transaction and for final on-chain settlement.

### Finding Description
`BalanceHandler` records a single mutable field `prevEventsLen` that marks the position in the event log at the start of a precompile call: [1](#0-0) 

`AfterBalanceChange` later reads `ctx.EventManager().Events()[bh.prevEventsLen:]` to determine which bank events belong to *this* precompile call and applies the corresponding `AddBalance`/`SubBalance` mutations to the EVM `StateDB`: [2](#0-1) 

The `BalanceHandler` instance is obtained via `p.GetBalanceHandler()` inside `Precompile.Run`, and is the *same* instance reused across nested/recursive invocations of the same precompile within a single EVM execution: [3](#0-2) 

If an outer precompile call performs a bank operation (emitting events) and then, before calling `AfterBalanceChange`, execution re-enters the same precompile (e.g. via a contract callback/reentrancy triggered from within `Execute`, or a nested internal call), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` to a later index. When control returns to the outer call and it invokes `AfterBalanceChange`, it now reads from the *inner* call's `prevEventsLen`, not its own — exactly mirroring how `TroveManager.openTrove` overwrites `totalActiveDebt` with a value computed from a stale cached pre-state, erasing the interest accrued in between. Here, the events emitted by the outer call's own bank operations (between the outer `BeforeBalanceChange` and the inner `BeforeBalanceChange`) are permanently skipped and never applied to the `StateDB`.

This exact bug is acknowledged by the repository's own test: [4](#0-3) [5](#0-4) 

Recursive/reentrant calls into precompiles are reachable by unprivileged users through ordinary contract logic — e.g. an ERC-20 token with a `_beforeTokenTransfer`/`_afterTokenTransfer` hook that calls back into a precompile (staking/distribution/bank) during a transfer initiated through the ERC-20 precompile, a pattern already present as test fixtures in the repo: [6](#0-5) 

### Impact Explanation
The EVM `StateDB` balance is the value that gets written back to `x/bank`/`x/precisebank` at the end of the transaction via `SetBalance`, which computes a mint/burn delta against the current spendable coin balance: [7](#0-6) 

If `AfterBalanceChange` fails to apply legitimate `x/bank` events to the `StateDB` (because `prevEventsLen` was clobbered by a nested call), the `StateDB`'s view of an account's balance diverges from what `x/bank` actually holds. When this divergent `StateDB` balance is later persisted via `SetBalance`, the delta comparison against the *actual* spendable coin triggers an incorrect mint or burn, permanently corrupting account balances — i.e., unauthorized minting/burning or accounting corruption of spendable user value, matching the Critical impact class for this scope. Because `BlockedAddresses` (e.g. module/reserve accounts backing `x/precisebank`) are specifically excluded from `StateDB` sync and reconciled only through this event-windowing mechanism, the same flaw can also desynchronize the precisebank reserve backing, risking loss/duplication of backing funds.

### Likelihood Explanation
Reentrancy into precompiles from contract-level hooks (ERC-20 `_beforeTokenTransfer`/`_afterTokenTransfer`, callback contracts, etc.) is achievable by any unprivileged user deploying and calling a contract — no privileged role or validator/relayer collusion is required. The repository already contains dedicated fixtures (`ERC20RecursiveNonRevertingPrecompileCall.sol`) and an integration test explicitly built to reproduce "the balance handler bug" via recursive precompile calls, indicating the authors are aware the scenario is reachable through normal transaction/contract flow.

### Recommendation
Do not store `prevEventsLen` as shared mutable state on a long-lived `BalanceHandler` instance reused across nested calls. Instead:
- Create a fresh `BalanceHandler` (or push/pop a stack of `prevEventsLen` snapshots) per precompile invocation frame so that nested/recursive calls cannot clobber an outer call's starting offset, or
- Pass the "before" event-length snapshot explicitly as a value returned from `BeforeBalanceChange` and threaded through to the matching `AfterBalanceChange` call (avoiding shared mutable state entirely), analogous to fixing `openTrove` by using a value that is not overwritten by an intervening state change.

### Proof of Concept
The repository's own `TestRecursivePrecompileCallsWithDebugPrecompile` test demonstrates the mechanism: a caller contract invokes the debug precompile, which recursively calls back (`callback`), sharing one `BalanceHandler` instance and asserting specific (already-adjusted-for-the-bug) event counts: [8](#0-7) 

To construct a fund-impacting PoC on a real precompile (e.g. `bank`/`staking`/`distribution`), deploy an ERC-20 (or any contract) whose transfer hook re-enters a precompile call while a bank-mutating precompile method (e.g. `distribution.claimRewards`, `staking.delegate`) is mid-execution, then observe that the EVM `StateDB` balance for the account whose bank event was skipped diverges from its actual `x/bank` balance after the transaction commits, and that a subsequent transaction which forces a `SetBalance` reconciliation mints or burns funds to correct the divergence. Full exploit construction and confirmation of the mint/burn write-back path requires running the node with an instrumented precompile (unverified in this pass due to lack of a live execution environment); this should be validated end-to-end in a Devin session with a running `evmd` test network.

type BalanceHandler struct {

	prevEventsLen int

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)

				// Bypass blocked addresses

			}

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
