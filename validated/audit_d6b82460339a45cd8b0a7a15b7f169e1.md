### Title
Front-runnable `approve()` in the WSEI (Wrapped SEI) canonical token allows a spender to exceed an owner's intended allowance - ([File: contracts/src/WSEI.sol])

### Summary
The `WSEI` contract's `approve()` function directly overwrites the `allowance` mapping without accounting for the previously outstanding allowance, exactly mirroring the reported DODO GSP `_approve` bug class. `WSEI` is not a test fixture — it is the canonical Wrapped-SEI ERC20-style contract whose bytecode is embedded in the binary and deployable on-chain via a dedicated CLI command, and interacted with by any ordinary EVM transaction sender through `approve`/`transferFrom`.

### Finding Description
`WSEI.approve()` sets the allowance to the new value unconditionally: [1](#0-0) 

`transferFrom()` decrements the current allowance atomically at execution time: [2](#0-1) 

This is the textbook classic-ERC20 allowance front-running pattern: if owner `Bob` calls `approve(Alice, 5)` intending to lower a prior `approve(Alice, 10)`, and `Alice` submits `transferFrom(Bob, Alice, 10)` that lands (is ordered) before Bob's decreasing `approve`, Alice consumes the full original allowance of 10 and then Bob's transaction resets `allowance[Bob][Alice]` to 5 regardless of the intervening spend, letting Alice transfer a cumulative 15 instead of the intended 10.

The `WSEI` contract is compiled and shipped as a first-class, production-deployable artifact: [3](#0-2) 

and can be deployed on any Sei network by any account via the `seid tx evm deploy-wsei` CLI command, which is exactly the same code path an ordinary contract deployer would use to instantiate the canonical wrapped-native-token contract: [4](#0-3) 

Once deployed, any unprivileged EVM transaction sender can call `approve`/`transferFrom` on it exactly as described in the report, with no additional privilege required.

Note: the analogous `CW20ERC20Pointer.approve()` function computes the *diff* against the currently on-chain allowance at execution time and issues `increase_allowance`/`decrease_allowance` messages rather than a raw set, so it does not reproduce this bug class: [5](#0-4) 

### Impact Explanation
A spender who is granted an allowance and is later downgraded by the owner can, by front-running the owner's decreasing `approve` transaction with a `transferFrom` that consumes the old (larger) allowance, end up being able to move more tokens off the owner's balance than the owner ever intended to authorize at any single point in time. This is concrete fund loss for the owner of WSEI tokens, reachable purely through ordinary EVM transactions.

### Likelihood Explanation
This requires only two ordinary EVM transactions from an unprivileged sender/spender pair with standard transaction-ordering influence (higher gas price/fee, or being included first in the same block), which is trivially achievable on any EVM-compatible chain including Sei. No special privilege, precompile access, or validator collusion is required.

### Recommendation
Change `WSEI.approve()` (and any other canonical ERC20-style contracts distributed by the chain, e.g. `evmrpc/solidity/ERC20.sol`) to use `increaseAllowance`/`decreaseAllowance` semantics, or have `transferFrom` require an explicit reduction acknowledgment, consistent with the mitigation already used in `CW20ERC20Pointer.approve()`.

### Proof of Concept
1. Deploy `WSEI` via `seid tx evm deploy-wsei` (or use the existing on-chain deployment).
2. Bob deposits SEI to acquire WSEI balance, then calls `approve(Alice, 10)`.
3. Bob decides to lower the allowance and submits `approve(Alice, 5)`.
4. Alice, monitoring the mempool, submits `transferFrom(Bob, Alice, 10)` with higher gas/fee priority so it lands first.
5. Block execution order: Alice's `transferFrom` succeeds (allowance 10 → 0, Bob's balance −10), then Bob's `approve(Alice, 5)` executes and sets `allowance[Bob][Alice] = 5`.
6. Alice can now call `transferFrom(Bob, Alice, 5)` again, for a cumulative withdrawal of 15 from Bob, exceeding the 10 (or intended 5) Bob ever meant to authorize at any given moment.

        public
        returns (bool)
    {
        require(balanceOf[src] >= wad);

        if (src != msg.sender && allowance[src][msg.sender] != type(uint).max) {
            require(allowance[src][msg.sender] >= wad);
            allowance[src][msg.sender] -= wad;
        }

        balanceOf[src] -= wad;
        balanceOf[dst] += wad;

        emit Transfer(src, dst, wad);

        return true;
    }

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
