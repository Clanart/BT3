### Title
Scanner reports dust/zero-value outputs as received funds that are permanently unspendable or net-negative to spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The DODO `buyShares` bug class is: a function accepts a *partial* deposit (only one leg of the required input), credits it to protocol state (`_setReserve`), mints zero output, and the shortfall makes the funds permanently unrecoverable. The analog in Serai's in-scope code is `Scanner::scan_transaction`: it accepts any on-chain output paying to a registered `script_pubkey` — including zero-value and sub-dust outputs — and reports it as a `ReceivedOutput` (i.e., funds received by the vault), even though such an output can never be profitably or standardly spent. Like `buyShares`'s missing `require(quoteInput > 0)`, there is no check that the deposited amount meets the minimum needed for the deposit to be usable.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) matches `output.script_pubkey` against the registered `scripts` map and pushes a `ReceivedOutput` for every match, with no check on `output.value`:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

`ReceivedOutput::value()` (lines 115-118) then reports the amount to any consumer of this crate. The wallet's own constant `DUST = 546` exists in `networks/bitcoin/src/wallet/send.rs:32`, and `SignableTransaction::new` correctly rejects payments *below* dust (send.rs:165-169) and refuses to create sub-dust change (send.rs:228-234) — the crate clearly knows sub-dust amounts are unspendable, yet the receive path applies no equivalent floor.

An unprivileged party can send a transaction to the multisig's p2tr script (or any registered offset script) with `value` of 1 sat — or 0, which `TxOut`/`Amount` accept at the Bitcoin data layer. The scanner emits it as a legitimately received output. To spend it, `SignableTransaction::new` would include it in `input_sat` (send.rs:175) while paying the full per-input weight in fees (send.rs:204-211); a sub-dust input is guaranteed net-negative — the signature's ~16 vbytes cost more than the input is worth at any nonzero fee rate, so consuming it *destroys* vault funds. Ignoring it leaves a permanent ghost balance reported as received.

### Impact Explanation
- Funds are reported as received by the vault that are not economically spendable, permanently inflating the vault's apparent balance — matching the "funds reported received that are not spendable" criterion.
- If downstream scheduling aggregates such inputs, each one costs more in fees than it contributes, causing a real, attacker-caused net drain of vault funds. The attack costs the attacker only the dust amount per output.
- As in the original report, the deposit is credited to protocol state with no path to rejection or refund.

### Likelihood Explanation
Reachable by any unprivileged party with a Bitcoin transaction: the vault's external p2tr address is public, and sending an output to it requires no interaction. The only mitigating factor is that a consumer (`processor`) currently filters scanned outputs by `>= N::DUST` before acting on them — but that check lives outside this crate, so the in-scope `Scanner`/`ReceivedOutput` API itself violates the invariant its own spend path enforces. Medium severity: confirmed false reporting of unspendable received funds, with fund loss contingent on consumers trusting `ReceivedOutput`s.

### Recommendation
Apply the same minimum-value rule on the receive path that `SignableTransaction::new` applies to payments and change: in `scan_transaction`, skip outputs whose `output.value.to_sat() < DUST` (or accept a configurable threshold), so a `ReceivedOutput` is only ever produced for amounts that can actually be spent without a net loss.

### Proof of Concept
1. `Scanner::new(key)` for the vault key; optionally `register_offset`.
2. Attacker broadcasts a transaction with `TxOut { value: Amount::from_sat(1), script_pubkey: <vault p2tr script> }`.
3. `scanner.scan_transaction(&tx)` returns `vec![ReceivedOutput { offset, output(1 sat), outpoint }]` — reported as received.
4. Constructing `SignableTransaction::new(vec![that_output], payments, change, None, fee_per_vbyte)` shows `needed_fee` includes the input's weight while `input_sat` contributes only 1 sat — the input can never be spent at a profit; the recorded balance is permanently fictitious.
