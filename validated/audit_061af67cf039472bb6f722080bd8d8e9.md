### Title
`GASLIMIT` opcode returns zero instead of the block gas limit due to missing field assignment in `NewEVMBlockContext` - (File: blockchain/evm.go)

### Summary
In kaia's EVM integration, `vm.BlockContext.GasLimit` is the field that backs the `GASLIMIT` opcode, but `NewEVMBlockContext()` — the function used to build the block context for real block/transaction execution — never sets it, leaving it at its Go zero value (`0`).

### Finding Description
`vm.BlockContext.GasLimit` is documented as "Provides information for GASLIMIT" [1](#0-0) , and `opGasLimit` pushes `interpreter.evm.Context.GasLimit` directly onto the stack for the `GASLIMIT` (`0x45`) opcode [2](#0-1) .

However, `NewEVMBlockContext()` — the constructor used by the production code path (`StateProcessor.InitializeState`, `ApplyTransaction`, tracers, `state_accessor.go`, `multicall.go`, `rebalance.go`, etc.) — builds the `vm.BlockContext{}` literal without ever assigning `GasLimit`: [3](#0-2) 

Compare this to the test-only helpers (`vm_test_util.go`, `runtime/env.go`, `benchmarks_test_utils.go`, `state_test_util.go`) which explicitly set `blockContext.GasLimit` from a config/header value: [4](#0-3) [5](#0-4) 

Because `header.GasLimit` (or any block gas-limit value) is never copied into the `vm.BlockContext` in the real (non-test) code path, every EVM `BlockContext` built for actual block processing on kaia mainnet/testnet has `GasLimit == 0`. This is the same class of bug as the minievm report — the block gas limit is not correctly propagated into the EVM's `BlockContext` — except in kaia's case the value is not "transaction remaining gas" (as in minievm) but is unconditionally zero, which is a more severe manifestation of the same root cause (an omitted/incorrect assignment of `BlockContext.GasLimit`).

### Impact Explanation
Any Solidity contract executed on kaia that reads `block.gaslimit` (or uses the `GASLIMIT` opcode directly in assembly) will always observe `0` instead of the actual block gas limit. This breaks EVM compatibility exactly like the referenced report describes, and is reachable by any unprivileged transaction sender or contract deployer simply by deploying/calling a contract that uses `GASLIMIT`. Contracts that rely on `block.gaslimit` for gas-limit sanity checks, gas-based logic branching, or replicate patterns from Ethereum mainnet contracts (e.g., certain gas-griefing protections, legacy contracts assuming a nonzero gas limit) may behave incorrectly — potentially bypassing checks that assume a nonzero/realistic value, or causing reverts/logic errors for ported contracts. This is a correctness/EVM-equivalence bug reachable from any public transaction, matching the "acceptance of incorrect EVM semantics" class called out as in-scope.

### Likelihood Explanation
High likelihood of being triggered — any contract using the `GASLIMIT` opcode (compilers emit this for `block.gaslimit`) will hit this on every call, deterministically returning `0` on kaia while returning a nonzero value on any EVM-compatible chain. No special conditions, timing, or privileged access are required; it fires on every transaction that touches this opcode.

### Recommendation
Set `GasLimit` in `NewEVMBlockContext()` from `header.GasLimit` (or the equivalent block gas-limit field/parameter in kaia's header/governance parameters), mirroring what the test helpers already do:
```go
return vm.BlockContext{
    ...
    GasLimit: header.GasLimit, // or appropriate block gas limit source
    ...
}
``` [3](#0-2) 

### Proof of Concept
1. Deploy a contract containing inline assembly `gaslimit()` (e.g., the `GasLimit()` helper in `contracts/testing/computationcost/opcodeBench.sol`) [6](#0-5) .
2. Call it via a normal transaction; the transaction is processed through `StateProcessor.Process` → `ApplyTransaction` → `NewEVMBlockContext(header, ...)` [7](#0-6) .
3. Since `NewEVMBlockContext` never populates `GasLimit`, the resulting `vm.BlockContext.GasLimit` is `0`.
4. `GASLIMIT` opcode execution (`opGasLimit`) pushes this zero value onto the stack [2](#0-1) , so the call returns `0` for `block.gaslimit` regardless of the actual configured block gas limit.
