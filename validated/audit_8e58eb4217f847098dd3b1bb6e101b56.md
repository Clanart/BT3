### Title
Attacker-supplied preprocess points reaching the point-at-infinity panic in `x`/`Hram::hram` crash the FROST signing path instead of returning `FrostError` - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Node.js bug class is: attacker-controlled input fed into a callback (`pskCallback`/`ALPNCallback`) throws a synchronous exception that bypasses the normal error-handling path (`tlsClientError`/`error`), converting a bad-input condition into process termination or resource exhaustion. In Serai, the same shape exists where untrusted protocol inputs (preprocess commitments, i.e., curve points supplied by a counterparty via `read_preprocess` → `Commitments::read`) flow into `Hram::hram`, which unconditionally `expect`s its inputs to be non-infinity. There is no error return on this path — a malformed aggregate nonce or group key produces a panic, not a `FrostError`.

### Finding Description
`x()` extracts the x-coordinate of a `ProjectivePoint` and calls `encoded.x().expect("point at infinity")` [1](#0-0) . `x_only()` similarly `expect`s [2](#0-1) . Both are documented as "Panics on invalid input." `Hram::hram` calls `x(R)` and `x(A)` directly [3](#0-2) .

`hram` is invoked inside `FrostSchnorr::sign_share` / `verify` / `verify_share`, which are reached during `AlgorithmSignMachine::sign` (`self.params.algorithm.sign_share(&view, &Rs, nonces, msg)` at `crypto/frost/src/sign.rs:398`) and `AlgorithmSignatureMachine::complete` (`verify` at `crypto/frost/src/sign.rs:465`, `verify_share` at `crypto/frost/src/sign.rs:476`). The `Rs` bound nonces are built from `B.nonces(&nonces)` — a binding-factor-weighted sum of the counterparty-supplied `Commitments` points parsed via `read_preprocess`/`Commitments::read` (`crypto/frost/src/sign.rs:276-281`). These points come straight off the wire from another participant; nothing in the `sign()`/`complete()` signatures can return the panic — the `Result<_, FrostError>` error path is bypassed exactly like the Node.js TLS `error` event is bypassed by a synchronous throw.

The `Schnorr` algorithm docs acknowledge this: "This may panic if called with nonces/a group key which are the point at infinity" [4](#0-3) . The same trap exists in the `verify` wrapper via `needs_negation`/`serialize` on the produced `R` [5](#0-4) .

### Impact Explanation
A panic inside `sign`/`complete` aborts the caller's signing task/thread (or the process under `panic=abort`), which is a denial of service of the threshold signer reachable by any other protocol participant with only their public preprocess message — precisely the "synchronous exception escapes the error path → crash" class from the report. Additionally, a non-infinity aggregate `R` or `A` isn't required for harm in every context: an attacker who can steer `R`/`A` to infinity (e.g., by selecting commitment points so the rho-weighted sum collapses, or by influencing the group key via a malicious DKG contribution yielding an identity `group_key`/`verification_share`) deterministically triggers the panic rather than receiving `FrostError::InvalidPreprocess`.

### Likelihood Explanation
Requires a counterparty in a signing session to supply crafted preprocess commitments. Whether the identity point survives `C::read_G` for `Secp256k1` is the gating factor — I could not fully verify whether `kp256`/`read_G` rejects the identity encoding in this codebase snapshot. If it does, triggering infinity in `R` requires grinding a rho-weighted cancellation (infeasible since rho is bound to the commitments); if it does not (no identity check on deserialized group elements — consistent with the "may panic ... even with malicious participants present" caveat, which implies the authors consider it reachable but negligible), a malicious participant can force `R`/a verification share/`A` to infinity and deterministically panic the peer. Severity Medium–High DoS depending on that read-path check, which should be confirmed.

### Recommendation
- Verify/reject the identity point in `C::read_G`/`Commitments::read` and in `ThresholdView` construction so infinity can never reach `hram`.
- Make `x`/`x_only` return `Option`/`Result` and have `Hram::hram` callers propagate `FrostError::InvalidPreprocess`/`InvalidShare` instead of panicking, matching the `#[must_use]`/error-return convention of the surrounding `verify`/`complete` code.
- At minimum, check `R`/`A` for `is_identity()` before calling `hram` in `sign_share`, `verify`, and `verify_share`.

### Proof of Concept
1. Attacker participates in a FROST signing session using `bitcoin::crypto::Schnorr` as the `Algorithm`.
2. In the preprocess round, attacker sends a `Commitments` message whose points are chosen so the binding-factor-weighted aggregate `R` (or, via a poisoned DKG, `group_key`/`verification_share` `A`) is the point at infinity — straightforward if `Secp256k1::read_G` accepts the identity encoding (to be confirmed); otherwise requires the DKG-poisoning route.
3. Victim calls `machine.sign(preprocesses, msg)` (`crypto/frost/src/sign.rs:283`), which computes `Rs` from the malicious commitments (`sign.rs:383`) and calls `sign_share` → `Hram::hram` → `x(R)` → `expect("point at infinity")` (`crypto.rs:15`).
4. The panic unwinds past `Result<_, FrostError>` — no `InvalidPreprocess` is returned; the signing thread/process crashes. Repeatable on every attempt with the same poisoned preprocess, analogous to the repeated-handshake crash in the Node.js report.

Caveat: I was unable to confirm within this index whether `Secp256k1::read_G`/`Commitments::read` reject the identity point; if they do, the preprocess route is blocked and only the group-key/verification-share route (requiring malicious DKG contribution) remains, which reduces severity to Medium.
