### Title
Shared `BalanceHandler` instance in precompiles uses a stale `prevEventsLen` cursor across nested/recursive precompile calls, causing StateDB balance desync from the bank keeper - ([File: precompiles/common/balance_handler.go])

### Summary
This is a direct structural analog of the Symbiotic bug class: a value ("vault power"/stake) is snapshotted once and then used to compute an accounting result even though the underlying state has since changed within the same execution window. In Cosmos EVM, the `BalanceHandler` snapshots `len(ctx.EventManager().Events())` into `prevEventsLen` before a precompile's state-changing call, and later replays `events[prevEventsLen:]` to mirror bank-keeper balance changes into the EVM `StateDB`. When precompile calls are nested/recursive (a contract calls a precompile which calls back into a precompile, e.g. via `try/catch`, callbacks, or a caller contract invoking itself through a precompile), the same `BalanceHandler` instance's `prevEventsLen` cursor gets overwritten by the inner call before the outer call has consumed its own slice of events, corrupting which bank events get replayed to `StateDB` and when.

### Finding Description
`BalanceHandler.BeforeBalanceChange` and `AfterBalanceChange` maintain a single mutable cursor field: [1](#0-0) 

`AfterBalanceChange` slices `events[bh.prevEventsLen:]` to determine which `CoinSpent`/`CoinReceived`/fractional-balance events belong to the just-completed precompile call, and applies corresponding `StateDB.AddBalance`/`SubBalance` calls: [2](#0-1) 

Each precompile (`erc20`, `staking`, `distribution`, `gov`, `slashing`, `ics20`) holds/uses this handler on `Precompile` construction rather than creating a fresh instance scoped to each individual call: [3](#0-2) 

If a Solidity contract triggers a nested or recursive precompile call within the same top-level call (as demonstrated by the repository's own regression test using a "debug precompile caller" contract), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, so:
- The outer call's `AfterBalanceChange`, executing after the inner one returns, will use a cursor that no longer points to the start of the outer call's own bank events — it may replay events that the inner call already applied to `StateDB` (double counting a balance credit/debit), or skip its own genuinely new events (losing a balance update entirely).
- The existing integration test (`TestRecursivePrecompileCallsWithDebugPrecompile`) explicitly documents this exact bug: "recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB": [4](#0-3) [5](#0-4) 

This is the same invariant violation as the Symbiotic report: a cached/snapshotted value (`prevEventsLen`, analogous to "power weights at the start of the epoch") is used to compute a critical accounting delta (bank event replay for balance sync) after the underlying state (the event log length, analogous to "activeStake" after a mid-epoch slash) has already moved on due to nested execution.

### Impact Explanation
`StateDB` balances are what the EVM uses for all subsequent computation within the transaction (further transfers, `balanceOf` calls to precompiles/contracts, gas refund calculations) and are ultimately what gets committed. If the event cursor desyncs:
- Balances applied to `StateDB` can double-count a bank-level credit (effectively duplicating spendable value visible to the EVM caller), or
- Balances can be under-applied (a legitimate credit silently dropped from `StateDB` while the bank keeper still holds/moved the real coins), producing a permanent accounting divergence between the native bank ledger and EVM-visible balances.

Either direction is an accounting-corruption / unauthorized-duplication scenario across native and EVM balances, matching the in-scope "Critical unauthorized minting/duplication or irreversible accounting corruption of spendable user value across native balances or EVM balances" impact class.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a contract to trigger nested/recursive precompile execution within a single transaction (e.g., via callbacks, `try/catch` reentry into a precompile, or a caller contract that invokes a precompile from within another precompile-triggered call). This is achievable by any unprivileged user deploying and calling their own contract — no privileged role is required — and the repository's own dedicated regression test (`balance_handler_test.go`) was written specifically to reproduce this scenario, indicating the maintainers consider nested/recursive precompile calls a realistic and already-observed pattern.

### Recommendation
Scope `BalanceHandler` (and its `prevEventsLen` cursor) per individual precompile invocation rather than sharing one instance across nested/recursive calls — e.g., instantiate a new `BalanceHandler` for each `Run`/method dispatch (already partially supported via `BalanceHandlerFactory.NewBalanceHandler()`), or make the cursor stack-based so nested calls push/pop their own event-window boundaries instead of overwriting a single shared field. Add invariant checks (e.g., comparing total bank event balance deltas against `StateDB` deltas after commit) to catch any residual desync.

### Proof of Concept
The repository already contains a working PoC for this exact issue in `evmd/tests/integration/balance_handler/balance_handler_test.go`: a caller contract invokes a debug precompile in a way that triggers nested precompile calls sharing one `BalanceHandler`; the test asserts specific expected event/precompile-call counts to demonstrate the `prevEventsLen` overwrite behavior described in the test's own comments. // BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
```go
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}
```

```go
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```

```go
// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
```
