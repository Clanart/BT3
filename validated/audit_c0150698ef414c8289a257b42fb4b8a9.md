### Title
Conflict-marker detection relies on `git diff --check` diff-only heuristic, allowing already-staged conflict markers to be silently committed - (File: `app/src/lib/git/diff-check.ts`)

### Summary
Seaport's bug was that a validation (`numerator`/`denominator` sanity check) was skipped for one order type, so the recorded `OrderFulfilled` event no longer matched what actually happened. GitHub Desktop has an analogous "recorded state != actual content" gap: the only signal Desktop uses to decide whether a conflicted file still needs attention before a commit is created (`conflictMarkerCount`), computed via `git diff --check`, can read `0` even though the file's content on disk and in the index still contains literal `<<<<<<<`/`=======`/`>>>>>>>` conflict markers. Desktop then treats the file as "Resolved," skips the conflict-commit warning, and commits/pushes the marker text as normal source.

### Finding Description
`getFilesWithConflictMarkers` shells out to `git diff --check`, which only flags conflict markers that show up as *added lines in the diff between the working tree and the index*: [1](#0-0) 

The result of that scan is used to populate `conflictMarkerCount` per path, defaulting to `0` for any path git didn't report on: [2](#0-1) 

`hasUnresolvedConflicts`/`mapStatus` treat `conflictMarkerCount === 0` as "Resolved," with no independent re-scan of the actual file content: [3](#0-2) [4](#0-3) 

The break in the invariant: `git diff --check` only detects markers *introduced by the diff*. If a conflicted file's working-tree copy is already identical to what's staged in the index (i.e., the markers exist in both the index and the working tree, with no delta between them), `git diff --check` produces no output for that path at all, so `conflictCountsByPath.get(path)` misses and the code falls back to `|| 0`. Desktop's own merge-commit logic explicitly documents that git auto-stages files that are part of a merge, including in cases with no unresolved delta: [5](#0-4) 

Desktop's UI-level gate (`CommitConflictsWarning`) that is supposed to stop users from accidentally committing conflict markers is driven entirely by this same `conflictMarkerCount`/`hasUnresolvedConflicts` signal: [6](#0-5) 

Once that signal is wrong, nothing downstream re-validates content. `_commitIncludedChanges` simply filters files by selection state and calls `createCommit`: [7](#0-6) 

`createCommit`/`stageFiles` stage exactly what's in the working directory/index and run `git commit` — there is no marker re-scan at commit time: [8](#0-7) [9](#0-8) 

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits-and-pushes issue: a file that visually and semantically is reported by Desktop as "Resolved" (no warning dialog, commit button enabled without confirmation) can still contain raw git conflict-marker text (`<<<<<<< HEAD`, `=======`, `>>>>>>> branch`) in the actual committed blob. That corrupted content is then pushed to the remote and becomes part of permanent project history, potentially breaking builds/tests or introducing logic errors that neither the user nor code reviewers were warned about, since Desktop's own UI asserted the file had zero unresolved conflicts.

### Likelihood Explanation
The attacker primitive required is exactly one of the explicitly valid ones: control over a branch/remote content that the victim merges, fetches, or pulls into GitHub Desktop. By crafting merge input so that a conflicted path ends up staged with identical working-tree/index content (a scenario Desktop's own code comments acknowledge git does automatically for non-conflicting parts of a merge), the attacker can make `git diff --check` report no findings for a path that still holds literal marker text, without requiring local access, admin rights, or any unnatural interaction from the victim beyond a normal merge/pull and commit.

### Recommendation
Do not rely solely on `git diff --check` (a diff-based heuristic) to gate the "no unresolved conflicts" state. Independently scan the current *content* of every file previously flagged as conflicted (e.g., via `git grep` for the literal marker patterns, or scanning file contents directly) immediately before allowing a commit, regardless of whether `git diff --check` reported anything, mirroring the Seaport recommendation to hoist/duplicate the validation at the actual point of commitment rather than relying on an earlier/indirect signal.

### Proof of Concept
1. Set up a merge that will conflict on `file.txt`, where the conflicting hunk is not the last change applied to the working tree (e.g., a rename/rename or content/content conflict where git auto-stages the resulting merge blob because the "non-conflicting" surrounding hunks match, per the documented staging behavior in `_finishConflictedMerge`).
2. After the merge halts with conflicts, without editing `file.txt`, run `git add file.txt` (a very common — and Desktop-supported — "mark resolved" action) so that the index and working tree copies of `file.txt` become byte-identical while still containing `<<<<<<<`/`=======`/`>>>>>>>` text.
3. Desktop refreshes status; `getFilesWithConflictMarkers` (`git diff --check`) reports no findings for `file.txt` since index == working tree, so `conflictMarkerCount` defaults to `0` and `hasUnresolvedConflicts` returns `false`.
4. The Changes list marks `file.txt` "Resolved," `CommitConflictsWarning` is never shown, and the user commits/pushes `file.txt` still containing the literal conflict markers.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

export function mapStatus(status: AppFileStatus): string {
  switch (status.kind) {
    case AppFileStatusKind.New:
    case AppFileStatusKind.Untracked:
      return 'New'
    case AppFileStatusKind.Modified:
      return 'Modified'
    case AppFileStatusKind.Deleted:
      return 'Deleted'
    case AppFileStatusKind.Renamed:
      return 'Renamed'
    case AppFileStatusKind.Conflicted:
      if (isConflictWithMarkers(status)) {
        const conflictsCount = status.conflictMarkerCount
        return conflictsCount > 0 ? 'Conflicted' : 'Resolved'
      }

      return 'Conflicted'
    case AppFileStatusKind.Copied:
      return 'Copied'
    default:
      return assertNever(status, `Unknown file status ${status}`)
  }
}

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,
      // https://git-scm.com/docs/githooks/2.46.1
      interceptHooks: [
        'pre-commit',
        'prepare-commit-msg',
        'commit-msg',
        'post-commit',
        ...(options?.amend ? ['post-rewrite'] : []),
        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
  return parseCommitSHA(result)
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
