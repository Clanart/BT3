## Title
Opening a changed file from the Changes/PR view resolves attacker-controlled symlinked paths outside the repository, bypassing the app's own path-containment guard - (File: `app/src/ui/changes/sidebar.tsx`)

### Summary
The pattern behind the Krystal report is "a safety helper exists (`_safeResetAndApprove`) but the vulnerable code path doesn't call it, and instead does a naive operation (`_safeApprove(..., 0)`) that breaks/misbehaves for adversarial input." Desktop has the exact same structural bug: it has a purpose-built, realpath-based path-containment helper, `resolveWithin`, that verifies a repo-relative path cannot escape the repository root via symlinks or traversal, but several UI code paths that turn a *repository-tracked file path* (which is fully attacker-controlled content coming from a cloned/fetched repository or a PR diff) into a filesystem action instead just do a naive `Path.join(repository.path, path)` without ever calling `resolveWithin`.

### Finding Description
`app/src/lib/path.ts` defines `resolveWithin`, whose entire purpose is to protect against exactly this class of bug: [1](#0-0) 

It is correctly used for at least one attacker-influenced input, the `filepath` query parameter of a `x-github-client://` deep link: [2](#0-1) 

However, the "open file" flow triggered from the Changes list (`app/src/ui/changes/sidebar.tsx`) does not use it at all: [3](#0-2) 

and hands the raw joined path to `openFile`, which passes it straight to `shell.openExternal('file://' + fullPath)`: [4](#0-3) 

The equivalent "open binary file" component has the same pattern - plain `Path.join`, no containment check: [5](#0-4) 

The `path` value in both cases originates from `WorkingDirectoryFileChange`/`CommittedFileChange` entries produced from `git status`/`git diff`, i.e. content that is fully determined by whatever is checked out from a cloned or fetched repository (or a PR diff opened via `pull-request-files-changed.tsx`, which follows the same `Path.join` pattern without `resolveWithin`). While Git's tree format itself rejects literal `..` path components, a hostile repository can still make `Path.join(repository.path, path)` point outside the repository root on disk by including a working-tree entry that is a symlink whose target is outside the repo, with a nested tracked path underneath it (a symlinked-directory escape). Because these call sites build the string path only and never call `realpath`/`resolveWithin` to confirm the final resolved path is still contained within `repository.path`, the *syntactic* containment check that `resolveWithin` performs is never applied — the check exists in the codebase (just like `_safeResetAndApprove` existed in Common.sol) but simply isn't invoked on this path.

### Impact Explanation
If reachable (see Likelihood), opening a "changed file" whose path traverses a malicious symlink lets `shell.openExternal('file://...')` launch/open an arbitrary file outside the repository that the attacker controls the selection of, and `shell.showItemInFolder`/reveal-in-explorer analogs would reveal arbitrary filesystem locations. This is a "read/open outside the repo" primitive triggered purely by cloning/fetching or reviewing a PR from a hostile repository, matching the required impact class (file read/open outside repo, driven by an attacker-controlled cloned/fetched repository).

### Likelihood Explanation
This depends heavily on whether the underlying `git checkout`/`git status` on the user's platform and Git version will actually materialize a symlink pointing outside the working directory and then check out a nested regular file "through" it (this is the classic "malicious symlink directory" checkout attack that upstream Git has partially hardened against over the years, and Desktop may also rely on Git's own protections here). I could not confirm from the indexed code whether Desktop or the bundled Git configures `core.protectNTFS`/refuses such checkouts, so I cannot state with certainty that the symlink-escape precondition is actually exploitable end-to-end in this build. What is certain and verifiable from the code is the structural gap: `resolveWithin` is applied inconsistently — used for one attacker-controlled input (deep-link `filepath`) but not for functionally identical attacker-controlled inputs (tracked file paths from Changes/PR views), which is itself the direct analog of the "helper exists but not used" bug pattern in the source report.

### Recommendation
Route every file path that originates from repository content (Changes list `onOpenItem`, `BinaryFile.open`, PR files-changed viewer, stash diff viewer, seamless diff switcher "open file" actions) through `resolveWithin(repository.path, path)` before building the path passed to `openFile`/`shell.showItemInFolder`/`revealInFileManager`, exactly the same way `dispatcher.ts`'s `openRepositoryFromUrl` already does for the deep-link case, and refuse to open when `resolveWithin` returns `null`.

### Proof of Concept
Not independently executed (no filesystem/terminal access available in this environment); based on static code review:
1. Attacker creates a repository containing a working-tree symlink entry, e.g. `link -> /` (or another location outside the eventual clone directory), and a tracked file physically materialized at a path that would be nested under that symlink post-checkout, e.g. `link/secret`.
2. Victim clones/fetches and checks out this repository in GitHub Desktop; if the local Git allows the symlink+nested-file checkout, `git status`/diff surfaces `link/secret` as a changed/added file path.
3. Victim clicks "Open file in external program" (or the equivalent action) in the Changes sidebar or PR files-changed view.
4. `Path.join(repository.path, 'link/secret')` is passed unchecked to `openFile` → `shell.openExternal('file://...')`, which the OS resolves through the symlink to a location outside the repository, opening/executing whatever the attacker placed there — with no `resolveWithin` containment check ever performed, unlike the deep-link code path.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
