### Title
Hard-coded dust threshold produces non-relayable transactions for recipients with larger scriptPubKeys - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` enforces a single hard-coded dust limit of 546 satoshis for every payment output, regardless of the output's `script_pubkey`. Bitcoin's dust threshold is a function of the serialized output size and the spend cost, so for outputs with larger scripts (non-SegWit, bare multisig, or any script larger than the P2PKH baseline), an output value between the real threshold and 546+ sats passes Serai's check while producing a transaction that violates standard relay policy and will never propagate or confirm. This is the same defect class as the UniswapX `CurrencyLibrary` hard-coded 6900-gas transfer: a fixed resource/policy constant applied uniformly where correctness is context-dependent, silently disabling payments to certain classes of recipients.

### Finding Description
`send.rs` defines `pub const DUST: u64 = 546;` and applies it uniformly:

```rust
// networks/bitcoin/src/wallet/send.rs:32,165-169
pub const DUST: u64 = 546;
...
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

Bitcoin Core computes dust per output as roughly `3 * (serialized_output_size + spend_input_size) * minRelayTxFee`. The 546 figure is only correct for P2PKH-sized outputs spent by SegWit-influenced assumptions. For outputs with a larger `script_pubkey` — which `SignableTransaction::new` accepts freely since `payments` is `&[(ScriptBuf, u64)]` — the protocol-dust threshold is higher than 546. The same constant is also reused to decide whether a change output is emitted (`if value >= DUST`, line 229), so change at the Serai-fixed 546-boundary can likewise create a nonstandard output.

Additionally, dust is a relay-policy constant (like the 6900-gas assumption), not a consensus invariant. It has changed historically (minRelayTxFee has moved between 1000–5000 sat/kvB across nodes and versions), so a hard-coded value is fragile in exactly the way the reference report describes: correct today under one set of assumptions, wrong under others.

### Impact Explanation
A payment of, e.g., 600 satoshis to an address/script whose actual dust threshold is ~700 passes validation in `SignableTransaction::new`, gets signed by the threshold multisig, and is broadcast — only to be rejected by every relaying node as `dust`. The funds are burned into a nonstandard output that cannot enter the mempool, so the intended recipient never receives spendable funds while the protocol records a completed transfer. Because the transaction is committed (signed) before broadcast fails, retry logic operates on an invalid transaction rather than the payment being cleanly rejected. For a bridge user, that is a payment that appears processed but is undeliverable — unrecoverable without an out-of-band fix transaction.

### Likelihood Explanation
Reachable by any party able to submit a payment address with a non-trivial `script_pubkey` and a small amount — i.e., public transaction data. It requires no validator misbehavior, no leaked keys, and no collusion: it is purely a consequence of the constant-versus-context mismatch on inputs the API already accepts. Severity is bounded because the amounts involved are small (sub-dust-scale values) and because the failure mode is a rejected broadcast rather than consensus loss, placing it at Medium.

### Recommendation
Compute the dust threshold per output using `bitcoin::Amount`/`TxOut::minimal_non_dust()` (or replicate `GetDustThreshold` with the actual serialized output size and spend-input estimate for the script type) instead of the flat `DUST` constant. Apply the same per-script computation to the change-output check at line 229. Alternatively, if the intent is conservative standardness, document and bound the accepted script types for payments.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte)` accepts `payments` as arbitrary `(ScriptBuf, u64)` pairs and only checks `*amount < 546`. Construct a payment to a `script_pubkey` larger than 34 bytes — e.g., a bare 1-of-3 multisig (~105 bytes, dust ≈ 600+ sat) or any padded script — with value 600. The function returns `Ok(SignableTransaction)`; the resulting transaction, once signed via `transaction_machine` and broadcast, is rejected by Bitcoin Core's `CTxMemPool` dust check (`-reject dust`), so the payment never confirms despite Serai treating it as valid and committed.
