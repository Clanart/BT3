### Title
Uncontrolled Recursion in `PuzzleWithRestrictions.from_memo()` Parsing Untrusted CHIP-0043 Custody Memos - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
Chia's custody architecture (CHIP-0043 "MofN" puzzles) reconstructs a puzzle tree from an on-chain/off-chain memo `Program` via `PuzzleWithRestrictions.from_memo()`. This method recurses into itself once per `MofN` member with no depth or size limit, mirroring the same bug class as CVE-2025-1492 (Wireshark's Bundle Protocol/CBOR dissector uncontrolled recursion): parsing an attacker-supplied nested structure with unbounded Python recursion, causing a stack overflow / `RecursionError` crash.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses a `Program` (CLVM s-expression) memo and, when the "further branching" flag is set, treats the puzzle hint as an `MofNHint` whose `member_memos` is a list of further memos, each recursively parsed by calling `PuzzleWithRestrictions.from_memo()` again: [1](#0-0) 

```python
@classmethod
def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
    ...
    further_branching = further_branching_prog != Program.to(None)
    if further_branching:
        m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
        puzzle: MIPSComponent = MofN(
            m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
        )
    ...
```

There is no bound on:
- how many `member_memos` a single `MofNHint` may declare (fan-out), or
- how deeply nested the `further_branching` flag can force recursion (depth).

The memo `Program` this function consumes is untrusted, attacker-supplied CLVM data — it is the `.cursor/context` documentation's own description of this exact code path: *"`from_memo()` must reconstruct unknown members/restrictions, including recursive `MofN`, so later wallet code can fill known puzzle implementations by puzzle hash."* [2](#0-1) 

Unlike `sha256_treehash()` in the same codebase, which was deliberately rewritten as an iterative stack machine specifically "so we don't have to worry about blowing out the python stack" [3](#0-2) ,
`from_memo()` (and its sibling recursive helpers `MofN.unknown_puzzles`, `MofN.fill_in_unknown_puzzles`, and `MofNMerkleTree._m_of_n_proof`) were not given the same protection. A crafted memo with thousands of nested `further_branching=1` `MofN` levels (each level trivially small in CLVM byte size, since only a `further_branching` flag, an `m`, and a list of child memos are required per level) will drive unbounded Python-level recursion when the wallet decodes it.

### Impact Explanation
A wallet/RPC caller that decodes a custody memo supplied by a counterparty (e.g., during offer negotiation, DID/singleton-based custody coordination, or any flow that calls `PuzzleWithRestrictions.from_memo()` on data received from an untrusted third party) can be crashed by a `RecursionError`. Because `from_memo()` has no defensive `try/except` around the recursive call and no depth cap, a suffciently deep nesting will exceed Python's recursion limit and raise unhandled, potentially killing the wallet process thread that processes memos — a spend-triggered/data-triggered transaction-processing halt consistent with the report's "Uncontrolled Recursion" bug class and the required "spend-triggered transaction-processing halt" impact category. This is a Medium-to-High availability impact (denial of service against a wallet client), matching the CVSS profile of the underlying report (local/no-privilege, user-interaction required, high availability impact).

### Likelihood Explanation
Likelihood is moderate-to-high in principle: constructing a maliciously deep `MofN` memo costs the attacker only a small amount of CLVM data (each nesting level is a few bytes), so producing tens of thousands of nesting levels is cheap and does not require any privileged network position — it only requires getting the target wallet to call `from_memo()` on attacker-controlled data. However, I was not able to fully confirm, within the available indexed code, the exact upstream call sites and RPC-reachability of `from_memo()` beyond its definition and test usage; grep only surfaced it referenced in `custody_architecture.py` itself and `chia/_tests/clvm/test_custody_architecture.py`, plus one hit in `chia/pools/plotnft_drivers.py`. This suggests the CHIP-0043 custody feature may still be relatively new/limited in integration, so the full untrusted-attacker reachability chain (e.g., via wallet RPC endpoints, offer files, or DL sync) could not be exhaustively traced with the tools available. A background Devin session with full repository access would be needed to enumerate every caller of `from_memo()` and confirm whether it is reachable from a fully unauthenticated/unprivileged network peer versus only from local wallet-owner-initiated actions.

### Recommendation
- Add an explicit recursion-depth (and/or total-node-count) limit to `PuzzleWithRestrictions.from_memo()`, raising a `ValueError` when exceeded, mirroring the defensive posture already used for `sha256_treehash()`.
- Convert the recursive `from_memo` traversal into an iterative work-list/stack-based implementation (as already done for `sha256_treehash`) to remove the Python stack-depth dependency entirely.
- Apply the same fix to `MofN.unknown_puzzles`, `MofN.fill_in_unknown_puzzles`, and `MofNMerkleTree._m_of_n_proof`, which share the same unbounded-recursion pattern over attacker-influenced/attacker-provided structures.
- Bound the maximum accepted memo size and/or `MofN` fan-out/depth as part of memo validation before any parsing begins.

### Proof of Concept
Conceptual construction (cannot be executed in this read-only environment) using the documented memo `Program` shape from `PuzzleWithRestrictions.memo()`/`from_memo()`:

```python
from chia.types.blockchain_format.program import Program
from chia.wallet.puzzles.custody.custody_architecture import PuzzleWithRestrictions

def make_leaf_memo():
    # further_branching=0, MemberHint puzzle_hint
    member_hint = Program.to([b"\x00" * 32, Program.to(b"leaf")])
    return Program.to(("CHIP-0043", [0, [], 0, member_hint.to_program()]))

def make_branch_memo(child_memo, depth):
    # further_branching=1, MofNHint with a single member pointing to child
    m_of_n_hint = Program.to([1, [child_memo]])
    return Program.to(("CHIP-0043", [0, [], 1, m_of_n_hint]))

memo = make_leaf_memo()
for _ in range(100_000):          # cheap to construct, tiny CLVM bytes
    memo = make_branch_memo(memo, _)

# Triggers unbounded Python recursion -> RecursionError / process crash
PuzzleWithRestrictions.from_memo(memo)
```

Each nesting level adds only a handful of bytes to the memo, so an attacker can cheaply build a memo deep enough to exceed Python's default recursion limit (~1000) well before the memo becomes large, and hand it to a wallet flow that calls `from_memo()` on counterparty-supplied data.
