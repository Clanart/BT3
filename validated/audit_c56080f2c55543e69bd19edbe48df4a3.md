## Finding [1](#0-0) 

In `parseAppURL` (`app/src/lib/parse-app-url.ts`), the `open-repository-from-url` deep-link action validates two of its three optional parameters but not the third: [2](#0-1) 

- `pr` is checked with `/^\d+$/`.
- `branch` is checked with `testForInvalidChars` (imported from `sanitize-ref-name`).
- `filepath` — documented as *"the file to open after cloning the repository"* — is read straight out of the query string via `getQueryStringValue(query, 'filepath')` and passed into the returned `IOpenRepositoryFromURLAction` with **no sanitization whatsoever**.

This is the direct analog of the report's `M01` pattern: some inputs to an externally-triggerable entry point are validated while a sibling, security-relevant field is left completely unchecked, exactly like `_setImplementation` in the Solidity report still lacking checks after a "partial fix."

### Title
Unsanitized `filepath` parameter in `x-github-client://openRepo` deep link handler - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL` sanitizes `branch` and `pr` for the `open-repository-from-url` custom-protocol action but passes `filepath` through untouched, unlike its sibling parameters.

### Finding Description
The Desktop app registers a custom URL protocol handler that any external actor (a malicious webpage, email link, or another app) can invoke with attacker-controlled query parameters. `parseAppURL` is the single choke point meant to validate all fields of this untrusted input before they are handed to the dispatcher/UI layer to act on (cloning a repo and then opening a specific file inside it). The function explicitly guards `branch` with `testForInvalidChars` and `pr` with a numeric regex, showing the authors intended to enforce an allow-list on all fields — but `filepath` is returned as-is: `const filepath = getQueryStringValue(query, 'filepath')` with no traversal check, no character allow-list, and no bound on its content. [3](#0-2)  Downstream, `filepath` is referenced further in `app/src/ui/dispatcher/dispatcher.ts` as part of handling this action, but I was not able to fully trace and confirm the exact sink logic (e.g., whether it is joined with the cloned repo path via `Path.join` and passed to a file-open API) before running out of tool calls — this should be verified directly in that file.

### Impact Explanation
If `filepath` is later joined with the local clone directory without using a contained-path check (the kind of guard present elsewhere in this codebase, e.g. `_resolveWithin` in `app/src/lib/path.ts`), a value like `../../../../.ssh/id_rsa` or an absolute path could cause Desktop to open or otherwise act on a file entirely outside the freshly cloned repository, from a link the user simply clicked — matching the "file read/write outside the repo" impact class in the task's Valid Impact list.

### Likelihood Explanation
Medium-to-high if the downstream file-open sink lacks its own path-containment check: the vector requires only clicking an `x-github-client://openRepo?url=...&filepath=...` link, which is the standard "Open in Desktop" flow and needs no local access, admin rights, or prior compromise. The likelihood is contingent on confirming that `dispatcher.ts`'s consumer of `filepath` does not itself re-validate/contain the path — this could not be fully confirmed with the available tool budget.

### Recommendation
Apply the same allow-list/containment discipline already used elsewhere in the codebase (`testForInvalidChars` for refs, `_resolveWithin` for path containment in `app/src/lib/path.ts`) to `filepath` inside `parseAppURL`: reject values containing `..`, null bytes, or absolute-path prefixes, and/or re-validate with `_resolveWithin`/an equivalent containment check at the point where `filepath` is joined to the cloned repository path in `dispatcher.ts` before it is opened.

### Proof of Concept
1. Attacker publishes a link: `x-github-client://openRepo?url=https://github.com/attacker/repo&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim (with Desktop registered as the protocol handler) clicks the link.
3. `parseAppURL` parses this into `{ name: 'open-repository-from-url', url, branch: null, pr: null, filepath: '../../../../.ssh/id_rsa' }` with no rejection, unlike the equivalent malformed `branch` or `pr` values which would be turned into `unknown`.
4. If the consumer in `dispatcher.ts` joins this value to the local clone path and opens it (unconfirmed exact behavior — requires direct inspection of `dispatcher.ts`), the result is a file access outside the intended repository directory, driven entirely by attacker-supplied deep-link content.

**Note on confidence:** The unsanitized nature of `filepath` in `parse-app-url.ts` is confirmed directly from the code. The exploitability depends on how `dispatcher.ts` consumes this value, which I could not fully verify within the available tool calls — this file should be inspected directly to confirm whether a path-containment check exists downstream before treating this as a fully proven vulnerability versus a defense-in-depth gap.
