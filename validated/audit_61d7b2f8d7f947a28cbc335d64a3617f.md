Confirmed: `object::is_owner` checks only the **direct** owner (`object.owner() == owner`), while `object::root_owner` walks the ownership chain up through nested objects to the ultimate non-object owner. This is the key structural fact needed to evaluate the `init.move`/`code.move` lazy-init gate.

### Title
Direct-owner vs. root-owner mismatch lets a nested-object ownership change silently re-arm blocked self-init grants - (File: `aptos-move/framework/aptos-framework/sources/object_code_deployment.move`, `aptos-move/framework/aptos-framework/sources/code.move`, `aptos-move/framework/aptos-framework/sources/init.move`)

### Summary
`object_code_deployment::upgrade` authorizes an upgrade using `object::is_owner` (direct owner only) [1](#0-0) , but `code::publish_package` records and `init::assert_may_self_initialize` re-checks the *root* (transitive) owner via `object::root_owner()` [2](#0-1) [3](#0-2) . Because `is_owner` and `root_owner` are not equivalent for objects nested under another object, whoever holds the *direct* owner slot of the code object can force a `deploy_owner` re-record for an *unrelated root owner*, without that root owner's consent, purely by triggering an upgrade.

### Finding Description
`code::publish_package` re-records `deploy_owner` on every publish/upgrade — not just the first deployment — using the code object's **current root owner**: [2](#0-1) 

`object_code_deployment::upgrade` gates who may trigger this by checking only **direct** ownership of the code object: [4](#0-3) 

`object::is_owner` compares only the immediate `ObjectCore.owner` field: [5](#0-4) 

while `object::root_owner` walks up through any chain of nested objects to the final non-object owner: [6](#0-5) 

`init::assert_may_self_initialize` later authorizes self-minting a signer for the module's address by comparing the recorded `deploy_owner` against the **current root owner**: [7](#0-6) 

Scenario: a code object `C` is *directly* owned by another object `P` (a parent object), and `P`'s root owner is `R`. `C`'s package was published while `P`'s root owner was `R`, so `deploy_owner(C, m) = R`. If `P` is later transferred to a new root owner `R'` (a transfer of the parent, not of `C` itself), `C`'s direct owner (`P`) is unchanged, so:
- `object::is_owner(C, P)` is still true — meaning whoever controls `P` (now `R'`, the new parent owner) can still call `object_code_deployment::upgrade` on `C` and pass the `is_owner` check, because the caller can generate `P`'s signer and act as `P` to satisfy `is_owner(C, publisher_address)`... 

Actually the more direct and cleanly provable defect is simpler and does not require the caller to impersonate `P`: **the root-owner transfer of `P` alone silently invalidates `C`'s self-init gate without any action on `C`**, and conversely, **anyone with authority to re-publish/upgrade `C` (i.e., whoever is the current direct owner `P`, acting through its own governance) re-arms the `deploy_owner` record to the new root owner `R'` merely by calling `upgrade`**, using an authorization check (`is_owner`, direct) that is weaker than the invariant it is supposed to protect (root ownership). This breaks the code-safety invariant documented in `init.move`'s own comments — that self-init should be "gated to whoever owned it when the code was published" and that "a transfer of the object **or an ancestor** ... blocks self-init" [8](#0-7)  — because the write-path that re-establishes the gate (`publish_package`'s `record_deploy_owner` call) uses a different (root) notion of ownership than the read-path used to authorize *who is allowed to trigger that re-establishment* (`is_owner`, direct, in `object_code_deployment::upgrade`). Direct owner `P` can re-arm self-init for the new root owner `R'` without `R'`'s explicit action on `C`, and can do so repeatedly regardless of intervening root-ownership churn, since `upgrade` never re-validates `root_owner` itself, only direct ownership of `C`.

### Impact Explanation
This is a control-flow/authorization-consistency bug between two intentionally different ownership notions (`is_owner` vs `root_owner`) used across the publish (`code.move`), self-init (`init.move`), and object-code-deployment (`object_code_deployment.move`) modules. The practical impact is that the self-init "owner has not changed since deploy" guard — explicitly designed to prevent minting a signer for a module whose object has been transferred away from its original controller — can be re-armed for a *different* root owner by a party (the direct/parent-object owner) whose authority the guard was never meant to depend on. Any code that assumes "self-init only runs under the original deploying owner" can have its invariant reset by a nested-object transfer, potentially allowing a party who is not the module's original beneficial owner to obtain the module-address signer via `init::internal_maybe_initialize` after an ordinary, authorized upgrade of a sibling/child code object.

### Likelihood Explanation
This requires: (1) `LAZY_MODULE_INITIALIZATION` feature enabled, (2) a code object published via `object_code_deployment` that is itself owned by another object (nested object ownership, which the framework explicitly supports and tests, e.g. `object::create_object(parent_addr)`), and (3) a subsequent upgrade or ownership change of the parent. This is a non-trivial but realistic composition of supported framework features (object nesting + object code deployment + lazy module init), all reachable by unprivileged callers with no admin/governance assumptions.

### Recommendation
Make the authorization check in `object_code_deployment::upgrade`/`freeze_code_object` and the record/verify logic in `code.move`/`init.move` consistent: either (a) use `object::owns` (transitive) instead of `object::root_owner` equality when recording/verifying `deploy_owner`, matching the direct-owner check used to authorize upgrades, or (b) require `object_code_deployment::upgrade` to verify the caller against the same root-owner notion (`root_owner(code_object) == publisher_address`) that `init.move` relies on for its self-init invariant.

### Proof of Concept
Not independently executed; reasoning is based on static analysis of the cited code paths (`object::is_owner` vs `object::root_owner`, `code::publish_package`'s unconditional `record_deploy_owner` on every publish, and `object_code_deployment::upgrade`'s direct-owner check). I could not run the Move test harness in this session to confirm the exploit end-to-end, so this should be validated with a targeted e2e test (nested object, transfer parent, re-upgrade child, then attempt `internal_maybe_initialize` from both old/new root owners) before treating it as confirmed rather than a credible, code-supported analog.
