### Title
Unbounded, unrefunded native-to-feeToken swap in `EvmHost.dispatch`/`fundRequest` lets a sandwiching attacker permanently strand a victim's excess ETH in the host contract - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all let a caller pay for a request/fee-top-up in native ETH. When `msg.value > 0`, the host performs `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` with the *entire* `msg.value` as the implicit max input and no minimum-output/slippage argument at all, and — critically — never captures or refunds the leftover ETH that the router returns after the swap. ### Finding Description
This is a direct analog of the reported `dpnm_sc.sol` issue: a swap/price-dependent function with no slippage-protection argument, exposed to price manipulation around the trade. In `dpnm_sc.sol` the attacker manipulates price to harm the counterparty of the trade; here an attacker manipulates the WETH/feeToken Uniswap V2 pool to force `EvmHost`'s swap to consume far more of `msg.value` than the honest market price would require.

`swapETHForExactTokens(fee, path, to, deadline)` uses the caller-supplied `msg.value` as the maximum ETH to spend and refunds unspent ETH to `msg.sender` of the router call — which, in this design, is `EvmHost` itself, not the original dispatcher who called `dispatch()`/`fundRequest()`. Compare this to `IntentGatewayV2.placeOrder`, which performs the *same* Uniswap call pattern but correctly tracks `amounts[0]` and refunds the remainder of `msgValue` back to `msg.sender`: [4](#0-3) 

`EvmHost.dispatch`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` have no equivalent refund logic — after the swap call there is no `amounts[0]` capture, no `msgValue -=`, and no ETH sent back to `_msgSender()`: [5](#0-4) [6](#0-5) 

Because the swap's `deadline` is `block.timestamp` (a no-op deadline that always passes in the same block) and there is no `amountInMax`/slippage bound, an attacker can sandwich the victim's transaction: front-run with a large swap in the same pool to spike the ETH price of `feeToken`, let the victim's `dispatch{value: X}(...)` execute (consuming a much larger fraction, or potentially close to all, of `msg.value` to obtain the fixed `fee` output), then back-run to restore the pool price and capture the spread. Any dust that would normally be refunded is retained inside `EvmHost`'s native balance instead of being returned to the payer, and no function in `EvmHost` sweeps or redistributes that stranded native balance back to the original sender — it becomes permanently inaccessible to the victim.

### Impact Explanation
This matches the bounty's fund-loss/loss-of-funds class: an unprivileged attacker (no malicious relayer, prover, or admin required) can, purely by trading against a public AMM pool immediately before/after a victim's `dispatch`/`fundRequest` call, cause the victim's excess ETH beyond the true market cost of the fee to be siphoned by MEV and the un-refunded remainder to be locked inside `EvmHost` rather than returned. This is worse than a typical sandwich because even in the *non-adversarial* case any leftover ETH from `swapETHForExactTokens` is never returned to the caller — the vulnerability turns normal price movement into stranded funds, and sandwich manipulation maximizes the amount stranded/extracted.

### Likelihood Explanation
Every call to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with `msg.value > 0` is exposed. These are the documented, recommended "Native Token Payment" entrypoints for any app built on Hyperbridge's `EvmHost` (per `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx`), so the attack surface is the mainline fee-payment path used by ordinary dApp users, not an edge case. The precondition (a manipulable low/medium-liquidity WETH/feeToken pool such as the ones configured per chain in `config.mainnet.toml`) is realistic and requires no privileged access.

### Recommendation
- Track `amounts[0]` returned from `swapETHForExactTokens` in all three call sites and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already implemented correctly in `IntentGatewayV2.placeOrder`.
- Replace `block.timestamp` with a real, caller-supplied deadline to bound execution.
- Consider adding a caller-supplied `amountInMax`/slippage tolerance parameter (analogous to the `dpnm_sc.sol` recommendation) so a manipulated pool price causes a revert instead of overcharging the payer.

### Proof of Concept
1. Attacker identifies a chain's `EvmHost` configured with a low-liquidity `WETH/feeToken` Uniswap V2 pool (`_hostParams.uniswapV2`).
2. Victim calls `EvmHost.dispatch{value: X}(DispatchPost{..., fee: F, payer: victim})` intending to pay `F` feeTokens for a cross-chain message, expecting only a small fraction of `X` to be spent given current pool price.
3. Attacker front-runs with a large ETH→feeToken swap on the same pool, spiking the ETH price of the fee token.
4. Victim's transaction executes `swapETHForExactTokens{value: X}(F, [WETH, feeToken], address(this), block.timestamp)`; because the pool is temporarily skewed, the swap consumes a much larger portion of `X` than it should, and the small leftover refunded by the router lands in `EvmHost`'s own balance (not the victim's), with no code path to reclaim it.
5. Attacker back-runs to restore the pool and pocket the spread extracted from the victim's oversized swap.
6. Repeat against `dispatch(DispatchGet)` and `fundRequest` for the same effect.

Note: I did not find any `EvmHost` function that sweeps or forwards its native ETH balance back to depositors (no `receive()`-triggered accounting or native-ETH withdraw path was found in `EvmHost.sol`), which is why the stranded ETH described above is not merely temporarily illiquid but effectively lost to the payer; this absence should be double-checked against the full contract if a native-ETH admin sweep exists elsewhere that I did not locate via search.

     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
        emit PostRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: _msgSender(),
            to: abi.encodePacked(request.to),
            nonce: request.nonce,
            timeoutTimestamp: request.timeoutTimestamp,
            body: request.body,
            fee: post.fee
        });
    }

    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }
