### Title
Unrecovered `panic("balance overflow")` in EVM `GetBalance` when a Sei address has vesting-locked `usei` exceeding its liquid balance - (File: `x/evm/keeper/balance.go`, `x/evm/state/balance.go`)

### Summary
This is an analog of the Uniswap-V3 "checked math where the design implicitly relies on an unchecked/negative intermediate result" bug class. In the Solidity original, `getFeeGrowthInside` performs signed subtractions that are meant to be allowed to wrap, but Solidity ≥0.8 checked arithmetic makes them revert on legitimate, expected negative intermediates, breaking downstream consumers (liquidation). In sei-chain's EVM state bridge, `x/evm/keeper/balance.go#GetBalance` computes `usei := allUsei.Sub(lockedUsei)`, an operation that the Cosmos SDK vesting design (`sei-cosmos/x/auth/spec/05_vesting.md`, `VestingAccount.LockedCoins` docstring) explicitly notes can be negative ("the spendable balance can be negative"). That negative `*big.Int` is then fed into `uint256.FromBig` in `x/evm/state/balance.go#GetBalance`, which cannot represent negative numbers and reports `overflow=true`, triggering an unrecovered `panic("balance overflow")`.

### Finding Description
`x/evm/keeper/balance.go`:
```go
func (k *Keeper) GetBalance(ctx sdk.Context, addr sdk.AccAddress) *big.Int {
	denom := k.GetBaseDenom(ctx)
	allUsei := k.BankKeeper().GetBalance(ctx, addr, denom).Amount
	lockedUsei := k.BankKeeper().LockedCoins(ctx, addr).AmountOf(denom)
	usei := allUsei.Sub(lockedUsei)
	wei := k.BankKeeper().GetWeiBalance(ctx, addr)
	return usei.Mul(state.SdkUseiToSweiMultiplier).Add(wei).BigInt()
}
``` [1](#0-0) 

`sdk.Int.Sub` is a signed operation and will **not** panic when `lockedUsei > allUsei`; it silently returns a negative `Int`, exactly the scenario the Cosmos vesting spec documents as expected ("the spendable balance can be negative"): [2](#0-1) 

That negative `*big.Int` result then flows into `x/evm/state/balance.go#GetBalance`, which converts it to a `uint256.Int` via `uint256.FromBig`. `uint256` cannot represent negative numbers, so the conversion reports overflow, and the code panics unconditionally:
```go
func (s *DBImpl) GetBalance(evmAddr common.Address) *uint256.Int {
	...
	res, overflow := uint256.FromBig(s.k.GetBalance(s.ctx, seiAddr))
	if overflow {
		panic("balance overflow")
	}
	...
}
``` [3](#0-2) 

`DBImpl.GetBalance` implements the go-ethereum `StateDB.GetBalance` interface and is invoked on essentially every EVM opcode/precompile path that touches an account balance (the `BALANCE` opcode, value transfers, precompile balance checks, etc.), for **any** Sei address associated with an EVM address — including addresses whose underlying Cosmos account is a vesting account. Unlike the bank module's own `SpendableCoins`/`SafeSub` helpers, which explicitly clamp negative results to zero (`sei-cosmos/x/bank/keeper/view.go`): [4](#0-3) 
the EVM balance bridge performs no such clamping and instead treats the mathematically-valid negative intermediate as a fatal invariant violation, exactly mirroring the Uniswap V3 report's core defect: code that assumes a subtraction can never underflow, when the surrounding system's documented semantics say otherwise.

### Impact Explanation
Any EVM-reachable code path that queries the balance of an EVM address mapped to a Cosmos vesting account whose currently-locked `usei` amount exceeds its raw bank balance (a state that is reachable through ordinary vesting/lock lifecycle plus normal transfers/spends of the unlocked portion) will hit this unconditional `panic("balance overflow")` inside `DBImpl.GetBalance`. Because this call sits deep in the go-ethereum `StateDB` interface used during ordinary EVM execution (opcode dispatch, `core.StateTransition`, precompiles), and is not wrapped in the kind of `recover()`-based gas-panic handling used elsewhere in the precompile framework (`precompiles/common/legacy/*`), a triggering transaction crashes `DeliverTx` processing for that block, i.e., it can halt EVM block production/validator processing (comparable to the report's "operations revert unexpectedly" — but strictly worse, since Cosmos-SDK `panic` here is not gracefully converted into a reverted EVM call, unlike the `bank` precompile's guarded `recover()` pattern shown in `precompiles/bank/legacy/v620/bank.go`).

### Likelihood Explanation
Triggering requires an EVM-associated address whose Cosmos account is a `VestingAccount` (continuous/delayed/periodic) with `LockedCoins` momentarily exceeding the account's raw bank balance — a state combination that vesting + delegation + spending flows can produce (this is exactly the "can be negative" case that the SDK's own vesting spec calls out as expected behavior for `SpendableCoins`). Reaching the crash then just requires a single ordinary EVM transaction (e.g., a `BALANCE` opcode call, a native transfer, or a precompile balance check) targeting that address's associated EVM address — no privileged access, malicious validator, or governance action needed. The exact reachability (whether current vesting-account creation flows on Sei allow this exact state, and whether address association with EOAs of vesting accounts is common) could not be fully confirmed from the indexed code; this should be validated with a live-node/unit reproduction before treating it as fully confirmed.

### Recommendation
In `x/evm/keeper/balance.go#GetBalance`, clamp the intermediate `usei` computation to zero when `lockedUsei` exceeds `allUsei` (matching the pattern already used in `sei-cosmos/x/bank/keeper/view.go#SpendableCoins`), instead of allowing a negative value to propagate into the uint256 conversion in `x/evm/state/balance.go`. Additionally, consider hardening `DBImpl.GetBalance` so that an unexpected negative/overflowing balance degrades gracefully (e.g., treated as zero with an error/metric) rather than causing an unrecovered panic in the hot EVM execution path.

### Proof of Concept
1. Create a Cosmos vesting account (continuous or delayed) and associate it with an EVM address (via the standard EVM/Sei address-association flow).
2. Delegate/lock coins such that `LockedCoins(ctx, addr)` for the base denom exceeds the account's current raw bank balance of that denom (achievable through the vesting + delegation/undelegate + spend sequences documented in `sei-cosmos/x/auth/spec/05_vesting.md`, which explicitly allow the spendable amount to go negative).
3. Send any EVM transaction that queries the balance of that address's associated EVM address (e.g., a contract calling the `BALANCE` opcode, or a plain value transfer causing `StateDB.GetBalance` to be invoked on it).
4. `x/evm/keeper/balance.go#GetBalance` returns a negative `*big.Int`; `x/evm/state/balance.go#GetBalance` calls `uint256.FromBig` on it, gets `overflow=true`, and panics with `"balance overflow"`, aborting `DeliverTx` for that transaction/block instead of gracefully reverting.
