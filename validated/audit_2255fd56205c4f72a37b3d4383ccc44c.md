### Title
`ReceivedOutput::read` accepts an offset/script_pubkey pair violating the scanner's invariant, yielding reported-received outputs that can never be signed for - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The kernel bug class is "a reference obtained under one condition is used later after the underlying object may have changed, without re-validating the binding" (`sk_dst_get(sk)->dev` used after RTNL acquisition, by which time `dst->dev` may have been swapped and freed). The Serai analog is `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`): it deserializes `offset`, `output` (TxOut) and `outpoint` as three independent fields from untrusted bytes and never re-checks the invariant that the producer (`Scanner::scan_transaction`, `mod.rs:199-214`) guarantees — namely `p2tr_script_buf(key + G*offset) == output.script_pubkey`. The binding between offset and script exists only inside `Scanner.scripts` and is lost when a `ReceivedOutput` is reconstructed from bytes.

### Finding Description

`ReceivedOutput::read` performs:

```rust
let offset = Secp256k1::read_F(r)?;           // arbitrary scalar
output = TxOut::consensus_decode(...)?;       // arbitrary script_pubkey + value
outpoint = OutPoint::consensus_decode(...)?;  // arbitrary outpoint
Ok(ReceivedOutput { offset, output, outpoint })
``` [1](#0-0) 

There is no `key` context and no consistency check, so an attacker supplying the bytes can pick any `(offset, script_pubkey, outpoint)` triple — e.g., a TxOut paying to the victim's registered script paired with the wrong offset, or the victim's script at an outpoint belonging to a transaction the attacker will double-spend, or a TxOut paying to an attacker-controlled script with offset zero.

Downstream, `SignableTransaction::multisig` is the only place that re-validates the binding:

```rust
let offset = keys.clone().offset(self.offsets[i]);
if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
    None?;
}
``` [2](#0-1) 

So a `ReceivedOutput` whose `offset` does not match its `script_pubkey` is *reported as received* (it survived `read`, carries `value()`, `outpoint()`, `offset()` accessors all returning plausible data) yet `multisig` deterministically returns `None` for it — the output is recorded in balance/UTXO accounting but is unspendable, exactly like the kernel's dangling `dev` reference whose referent no longer matches what was fetched.

### Impact Explanation

Funds reported received that are not spendable. Any wallet/processor flow that (a) ingests `ReceivedOutput` blobs from an untrusted channel (peer messages, shared storage, a compromised output-feeder) via `ReceivedOutput::read`, and (b) credits `output.value()` to a balance or queues it for signing, will record funds that can never be spent: `SignableTransaction::multisig` rejects the forged `(offset, script_pubkey)` pair, or — worse for accounting — the fabricated `outpoint`/`script_pubkey` points at an output the multisig key does not control. This enables balance inflation and sign-queue poisoning (each poisoned input forces `None`, aborting the whole transaction construction).

### Likelihood Explanation

Reachable by an unprivileged party: `ReceivedOutput::read` is a public deserialization API explicitly fed untrusted bytes; the serialized form has no MAC or key binding. The attack requires only that an integrator trust deserialized outputs rather than re-deriving them via `Scanner::scan_transaction` — a realistic pattern since `serialize`/`read` exist precisely for cross-component transport. Impact is Medium (accounting corruption / unspendable-but-credited funds), not key recovery: the spend-time `multisig` check prevents an actual signature over the wrong key, so this fails closed rather than producing a forged spend.

### Recommendation

Bind the offset to the script at construction and read time. Options:
- Change `ReceivedOutput::read` to take the scanner key (or the `Scanner` itself) and reject bytes where `p2tr_script_buf(key + G*offset) != output.script_pubkey`, mirroring the check already in `multisig`.
- Alternatively, store the script only and re-derive `offset` via `scanner.scripts.get(&script_pubkey)` at read time, eliminating the attacker-controlled offset field entirely.

### Proof of Concept

```rust
// Attacker crafts bytes: valid scalar offset O, a TxOut paying to the
// victim's *other* registered script (or any script), arbitrary outpoint.
let mut buf = vec![];
buf.extend(wrong_offset.to_bytes());                 // offset for script A
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: script_for_offset_B,              // script for offset B != A
}));
buf.extend(serialize(&OutPoint { txid: real_txid, vout: 0 }));

let received = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted
// Wallet credits 100_000 sats at real_txid:0.

// Later, spending fails deterministically:
let tx = SignableTransaction::new(vec![received], &payments, None, None, 1).unwrap();
assert!(tx.multisig(&keys).is_none()); // offset/script mismatch -> unspendable
```

I was unable to fully verify all consumers of `ReceivedOutput::read` (processor/ coordinator code is out of scope), so the severity rests on this read API being fed untrusted bytes per the stated reachability rules.
