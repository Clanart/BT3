### Title
Dust outputs accepted as spendable inputs — funds reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Derby analog's bug class is: a routine operation proceeds without verifying the full value was recovered, leaving funds stranded with no control to distinguish "partial is acceptable" from "must be all or nothing." In bitcoin-serai, the same shape exists at the input boundary: `Scanner::scan_transaction` reports every output paying to a registered script as a spendable `ReceivedOutput`, and `SignableTransaction::new` accepts those as inputs with no minimum-value check. A third party can send a dust-valued output (≤ 546 sats, or a consensus-valid 0-value output) to a Serai address; it is reported as received balance yet cannot ever be spent profitably — its spend costs ~57+ vbytes of fee against a value that may not even cover relay dust rules. Funds are reported received that are not spendable, and there is no lever to reject them.

### Finding Description
`Scanner::scan_transaction` matches solely on `script_pubkey` and pushes a `ReceivedOutput` for any matching output regardless of `output.value` (`networks/bitcoin/src/wallet/mod.rs:199-214`). `ReceivedOutput` performs no dust validation on `read` either (`mod.rs:122-134`).

In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`), dust validation is applied only to *payments*:

```solidity
for (_, amount) in payments {
  if *amount < DUST { Err(TransactionError::DustPayment)?; }
}
```

No equivalent check exists for `inputs` (`send.rs:165-169` vs `send.rs:175-185`). Each input unconditionally adds a 230-weight-unit (~57 vbyte) witness spend to the transaction (`calculate_weight_vbytes`, `send.rs:62-127`). At `fee_per_vbyte` ≥ ~10 sat/vb, an input worth ≤ 546 sats costs more to spend than it contributes — it is a net-negative input that drains value from the other inputs/change. Below relay dust it cannot even be recovered into change. There is no threshold check and no option to reject, mirroring the Derby finding's missing "revert if withdrawn < expected" control.

Additionally, the analogous "leave-behind" case exists internally: when `input_sat - payment_sat - fee_with_change` is below `DUST`, the change output is silently dropped and the remainder is burned as excess fee (`send.rs:224-235`) rather than erroring — again proceeding on partial recovery with no caller opt-out.

### Impact Explanation
An unprivileged party sends a dust output to a scanned Serai address (public data — the address/script). The wallet reports it as a received, spendable output. When scheduled into a transaction, it consumes more in fees than its value (at moderate fee rates) or is permanently unspendable (below dust), i.e., funds reported received that are not spendable — the exact accepted impact class. The cumulative effect scales with repeated dust outputs.

### Likelihood Explanation
Sending a dust output costs the attacker only the dust amount plus fee, requires no privileges, and uses only public transaction data. Inclusion in a later `SignableTransaction` is automatic since input selection has no value floor.

### Recommendation
- In `Scanner::scan_transaction` (or `ReceivedOutput::read`), reject outputs whose `value` is below `DUST` (546) — they can never satisfy the spend-cost constraint.
- In `SignableTransaction::new`, verify each input's value exceeds the marginal fee for spending it (`fee_per_vbyte * ~57 vbytes`), and return an error rather than silently accepting net-negative inputs.
- When the computed change is below `DUST`, add an option/error to abort instead of silently donating the remainder to miners.

### Proof of Concept
1. Attacker learns a Serai P2TR script (`p2tr_script_buf(key)`) and broadcasts a transaction with an output paying it `value = 546` sats (or less via non-standard relay).
2. `Scanner::scan_transaction` returns a `ReceivedOutput` for it (`mod.rs:205-211`); balance reported increases by 546.
3. `SignableTransaction::new(vec![dust_output, ...], payments, change, None, fee_per_vbyte)` at `fee_per_vbyte = 50` adds ~57 vb of weight for the dust input: cost ≈ 2850 sats vs 546 contributed — a net burn of ~2300 sats from the vault's other funds, with no error raised.
