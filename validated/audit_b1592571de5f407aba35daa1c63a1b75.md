### Title
Relayer `Fees` balance is optimistically zeroed before cross-chain settlement, causing permanent loss of relayer rewards on destination-side transfer failure - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-ismp-relayer`'s `Pallet::withdraw` reads a relayer's `Fees` balance, immediately debits the on-chain ledger, and only *afterwards* dispatches a cross-chain ISMP POST request instructing the destination `HostManager`/`EvmHost` to actually transfer the funds. Settlement of the transfer is not atomic with the debit: it depends on a later message delivery and an ERC-20 `safeTransfer` on the destination chain that can revert if the host's actual fee-token balance is insufficient. This mirrors the `GlpStrategy`/`shouldBuyGLP` pattern in the external report exactly: an internal accounting value (`Fees`) is consumed/zeroed on the assumption that the backing asset will be available, but the actual payout path is conditioned on a separate, unguaranteed step (destination balance / delivery), so the accounting and the real backing asset can diverge — with no compensating re-credit path.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs`:
1. Reads `available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone())` [1](#0-0) 
2. Checks it against the minimum withdrawal threshold, increments the nonce, and builds a `WithdrawParams`/`WithdrawalRequest` body to dispatch to the destination's `HostManager` (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate) [2](#0-1) 
3. The pallet documentation itself states the design: *"The `Fees` entry is zeroed so the same balance cannot be withdrawn twice. ... The on-chain effect is just dispatching the message; the destination chain settles the payout when the ISMP request is delivered there."* [3](#0-2) 

On the destination side, `HostManager.onAccept` unconditionally forwards the withdrawal to `EvmHost.withdraw`, which does a plain `safeTransfer`/native `call` of the exact requested `amount` out of the host's own balance: [4](#0-3)  and [5](#0-4) . This reverts if the host does not hold `amount` of the fee token — a behavior explicitly exercised by `test_host_manager_insufficient_balance`, which asserts the call reverts when the host has no fee tokens [6](#0-5) .

The pallet's `Fees` ledger, however, is not itself backed 1:1 by an escrowed balance that is guaranteed present at settlement time — it is a bookkeeping value accumulated from proofs of past deliveries, decremented eagerly at withdrawal-request time on Hyperbridge, while the actual asset transfer happens later and elsewhere (a different chain, different balance, subject to timing/consumption by other withdrawals, `CannotChangeFeeToken`/param changes, or any other drain of the host's fee-token balance in between accumulation and settlement). If that destination-side transfer reverts, delivery of the ISMP request fails on that leg; the request "will not timeout" (per docs), meaning it can be retried indefinitely, but the pallet has already zeroed `Fees` with **no mechanism to re-credit the relayer** if the message is ultimately never deliverable at the amount originally computed. This is structurally the same invariant break as the GLP report: an accounting figure that assumes an asset is realizable is consumed before the realization step is guaranteed to succeed, and there is no fallback/partial-settlement logic.

### Impact Explanation
This is a loss-of-funds bug for relayers (a core protocol income stream), reachable by an ordinary unprivileged relayer simply calling `withdraw_fees` — no malicious peer, admin, or governance actor is required. If the destination host's fee-token balance is, at settlement time, less than the `Fees` amount already debited on Hyperbridge (e.g., because other relayers' withdrawals or governance's `HostManager` withdrawal drained it in the interim, or the fee token was swapped/changed), the relayer's accrued reward becomes permanently unrecoverable: `Fees` was already zeroed on Hyperbridge, and the destination-side transfer never completes.

### Likelihood Explanation
Medium: it requires a timing window where the destination host's actual fee-token balance drops below the sum of outstanding relayer claims before a specific pending withdrawal is delivered — plausible under concurrent relayer withdrawals or protocol fee-token administration (`dispatch_withdraw`/`HostExecutive::withdraw` draining protocol revenue) racing against relayer `withdraw_fees` calls, since both draw from the same host balance without a per-account escrow or balance-availability check on Hyperbridge before debiting `Fees`.

### Recommendation
Do not debit `Fees` unconditionally at request time. Either (a) hold the debited amount in a pending/escrow state until a delivery-success confirmation is observed on Hyperbridge (analogous to how `OutboundRequestsClaimed` gates one-time payout), with automatic re-credit of `Fees` on confirmed delivery failure/timeout, or (b) verify destination-chain fee-token balance sufficiency via a state proof before allowing the debit, or (c) make the destination-side transfer path itself track a claimable receipt so a failed transfer can be retried against the original claim rather than a bare "already zeroed" ledger entry.

### Proof of Concept
1. Relayer R accumulates `Fees[dest, R] = 1000` via `accumulate_fees` after proven deliveries [7](#0-6) .
2. Concurrently, the destination `EvmHost`'s actual fee-token balance is drawn down below `1000` by other relayers withdrawing, or by governance calling `HostExecutive::withdraw`/`dispatch_withdraw` on the same host [8](#0-7) .
3. R calls `withdraw_fees` on Hyperbridge; the pallet reads `available_amount = 1000`, passes the minimum-withdrawal check, increments nonce, and zeroes `Fees[dest, R]` as part of dispatching the ISMP withdrawal request [9](#0-8) .
4. When the request is delivered to `HostManager.onAccept` → `EvmHost.withdraw`, the `IERC20(token).safeTransfer(beneficiary, 1000)` reverts because the host's balance is now `< 1000`, exactly as demonstrated by `test_host_manager_insufficient_balance` [6](#0-5) .
5. R's `Fees` entry is already `0` on Hyperbridge; there is no code path shown in `withdrawal.rs`/`lib.rs` that re-credits `Fees` on a failed/reverted destination delivery, so R's reward of 1000 units is permanently lost despite having correctly earned it.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});

fn test_host_manager_insufficient_balance() {

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer

		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");

}

		/// Issues a call to withdraw the protocol fees from an evm chain
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(4)]
		pub fn withdraw(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			withdrawal_params: WithdrawalParams,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			ensure!(state_machine.is_evm(), Error::<T>::UnsupportedStateMachine);

			let HostParam::EvmHostParam(params) = HostParams::<T>::get(state_machine)
				.ok_or_else(|| Error::<T>::UnknownStateMachine)?;

			let data = withdrawal_params
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidBeneficiaryAddress)?;

			let post = DispatchPost {
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: params.host_manager.0.to_vec(),
				timeout: 0,
				body: data,
			};

			let dispatcher = <T as Config>::IsmpHost::default();

			// Account is not useful in this case
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

			Self::deposit_event(Event::<T>::Withdraw {
				address: sp_runtime::BoundedVec::truncate_from(
					withdrawal_params.beneficiary_address,
				),
				state_machine,
				amount: withdrawal_params.amount,
			});

			Ok(())
		}
