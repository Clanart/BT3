### Title
Authenticated image filter attaches user's GitHub token to any GitHub asset/avatar URL regardless of which repository or window the request originates from - ([File: app/src/main-process/authenticated-image-filter.ts])

### Summary
The Sherlock finding's broken invariant is: an object (an NFT/deposit receipt) is acted upon based only on a *global, loosely-scoped identifier check* (any `DepositReceipt` minted by the same contract), instead of verifying the caller/context actually owns or is entitled to that specific object. `Depositor#withdrawFromGauge` trusted any NFT id without validating it belonged to `msg.sender`'s own depositor.

The Desktop analog is `installAuthenticatedImageFilter` in `app/src/main-process/authenticated-image-filter.ts`. It attaches the signed-in user's real GitHub token to *any* outgoing request in the shared Electron session whose **origin** matches a known GitHub/GHES endpoint and whose **path** matches a generic regex for avatar/asset URLs — with no check that the specific owner/repo/asset in the URL has anything to do with the repository or content the user is currently viewing: [1](#0-0) [2](#0-1) 

### Finding Description
- The filter is installed once on `session.defaultSession.webRequest` at app startup and applies to every request across all rendered content in that session, not just requests belonging to the currently selected repository: [3](#0-2) 
- The gating logic only checks: (1) the request's `origin` is a known signed-in endpoint (`github.com`, `ghe.com`, or an enterprise host), and (2) the `pathname` matches a broad regex `^/[^/]+/[^/]+/assets/[^/]+/[^/]+/?$` (or the enterprise avatar prefix) — it never validates that `owner/repo` in the path corresponds to a repository the current window/content is displaying, nor that the token's account has any relationship to that specific asset: [4](#0-3) 
- Untrusted content is regularly rendered in the same session via `SandboxedMarkdown`, which renders PR bodies, PR/issue comments, and Copilot-generated summaries — content authored by third parties (any public repo contributor) — as an iframe with an `<img>` tag whose `max-width`/`height` styling is explicitly supported: [5](#0-4) [6](#0-5) 
- Because the sandboxed iframe is loaded via a `data:` URI (not an isolated session/partition) that still goes through Electron's default session and shares `session.defaultSession.webRequest`, an `<img src="https://github.com/<any-owner>/<any-repo>/assets/<id>/<guid>">` embedded in a PR description, PR comment, or issue comment authored by *any* third party will have the viewing user's real GitHub token silently attached by the main process filter — for an asset path completely unrelated to the repository being viewed. This is the same class of defect as the Sherlock bug: the check is "does this identifier match a known pattern globally" instead of "does this identifier belong to the context/owner that's acting on it."

### Impact Explanation
An attacker who can get their markdown rendered inside Desktop (a PR description/comment on any repo the victim has cloned, or a review comment) can embed asset URLs pointing at arbitrary `owner/repo/assets/...` paths. Since the filter blindly attaches the Authorization header for any URL matching the generic pattern under a known GitHub origin, this becomes an oracle: the attacker can measure success/failure (HTTP 200 vs 404/403 via image load/error events observable from the renderer, e.g. through `onImageError`/`onLoad` in `Avatar`/markdown rendering) to determine whether the victim's authenticated token can access a specific private repository's asset — leaking private-repo membership/authorization information cross-repository, using the victim's own credentials without their intent, driven entirely by attacker-controlled repository content.

### Likelihood Explanation
Medium: it requires the victim to view PR/issue/commit content (a routine action) authored by an untrusted party, and the URL pattern (`/owner/repo/assets/id/guid`) is exactly the format GitHub uses for uploaded image attachments, making it trivial to construct pointing at arbitrary owner/repo pairs. It does not require admin rights, local access, or leaked credentials — only rendering of attacker-supplied markdown, which is core normal usage of Desktop's PR/issue viewing features.

### Recommendation
Scope the authenticated-image filter to the repository context actually being displayed (e.g. pass the expected owner/repo alongside the render request and validate the path's `owner/repo` matches it) rather than matching only on origin + a generic path regex. Alternatively, isolate rendering of untrusted markdown (PR/issue bodies) into a separate session/partition that does not share `session.defaultSession`'s webRequest listeners, so the authenticated-image filter cannot be invoked from attacker-controlled content at all.

### Proof of Concept
1. Sign in to GitHub Desktop with an account that has access to a private repository `victim-org/private-repo`.
2. As an attacker, open a PR or issue comment (in any public repository the victim has cloned) containing:
   `![](https://github.com/victim-org/private-repo/assets/1/deadbeef-guid)`
3. When the victim views this PR/comment in Desktop, `SandboxedMarkdown` renders the `<img>` tag inside the iframe: [7](#0-6) 
4. The request for that image URL passes through `session.defaultSession.webRequest`, matches the origin (`github.com`) and the `isGitHubRepoAssetPath` regex, and `installAuthenticatedImageFilter` attaches `Authorization: token <victim's real PAT>` regardless of whether `victim-org/private-repo` is the repository being viewed: [2](#0-1) 
5. The attacker (via a controlled tracking pixel or by observing load success/failure in a shared PR they also review) can infer whether the victim's token can read that asset, revealing private-repo access without the victim's awareness or consent.

**Caveat / uncertainty**: I was not able to fully verify from the indexed code whether the sandboxed markdown iframe truly shares `session.defaultSession` (as opposed to a separate partition), which is the load-bearing assumption for this to be exploitable at all; the `sandboxed-markdown.tsx` file confirms rendering via a `data:` URI in a same-session iframe, but I could not confirm from local index contents whether Electron session partitioning is applied elsewhere (e.g. in `app-window.ts` webPreferences) that might isolate this. Given index size limits, some file contents (e.g. `app-window.ts` webPreferences/session setup) may not be fully available — starting a Devin session would allow verifying session partitioning and confirming exploitability end-to-end.

function isEnterpriseAvatarPath(pathname: string) {
  return pathname.startsWith('/api/v3/enterprise/avatars/')

function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
