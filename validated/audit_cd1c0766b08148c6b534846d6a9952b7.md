### Title
Spoofable `WWW-Authenticate` realm lets an attacker-controlled git remote force GitHub Desktop into the "enterprise/GitHub" credential/sign-in flow without real host verification - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`getEndpointKind` in `trampoline-credential-helper.ts` decides how Desktop's git-credential trampoline handles a request for credentials by classifying the target host as `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`. For arbitrary (non-github.com/non-known-GHE) hosts, this classification is derived from a `WWW-Authenticate` header value that git itself forwarded from the remote server's HTTP response, with no cryptographic or out-of-band verification: [1](#0-0) 
This is structurally the same broken invariant as the audit finding: the code is "forced" to trust a single, externally supplied signal (there, a single swap router; here, a single header echoed from whatever server the git remote points to) instead of validating against multiple/independent sources, and that signal is fully controlled by the counter-party.

### Finding Description
When Git performs an HTTP(S) authentication attempt against a remote, the server's `WWW-Authenticate` response header is captured and passed to Desktop's credential helper trampoline as `wwwauth[...]` entries. `getEndpointKind` treats a header containing `realm="GitHub"` as sufficient evidence that the host is a "GitHub Enterprise" endpoint: [2](#0-1) 
Any server the user clones/fetches from (or any node on the network able to answer the HTTP auth challenge, e.g. a malicious/compromised proxy sitting in front of a non-GitHub remote) can set this header verbatim - there is no TLS-bound or challenge/response check tying the claim to an actual GitHub Enterprise deployment. The fallback path, `isGitHubHost`, is only marginally stronger: it treats the presence of an `x-github-request-id` response header as proof of being a GitHub host, which is likewise just an attacker-settable HTTP header, not a verified identity property: [3](#0-2) 
This mirrors the audited bug's pattern: a single, unauthenticated/attacker-influenced signal is trusted to make a security-relevant routing decision (there: "which router to trust for a swap", here: "which trust class this git host belongs to").

The consequence of `getEndpointKind` returning `'enterprise'` (or `'github.com'`) instead of `'generic'` is that `getCredential` skips the generic/external credential-helper path entirely and instead invokes the GitHub-specific sign-in UI: [4](#0-3) 
It also suppresses `storeCredential`/`eraseCredential` for that host, since both early-return when `getEndpointKind(...) !== 'generic'`: [5](#0-4) 

### Impact Explanation
Because the host classification is spoofable purely from the remote/proxy's HTTP response, an attacker who controls the git server behind a cloned/fetched remote (a valid, in-scope primitive per the task's rules - "attacker controls ... a git remote/proxy response") can make GitHub Desktop believe an arbitrary, non-GitHub host is `'enterprise'`. This:
- Routes credential requests for that host into `ui.promptForGitHubSignIn(endpoint)` instead of the neutral generic-auth prompt, presenting the user with GitHub-branded sign-in/enterprise-auth UI for a host that is not actually GitHub, which is the enabling step for an unauthorized enterprise/OAuth sign-in flow being initiated against an attacker-controlled endpoint.
- Silently disables the normal generic credential store/erase path for that host (`storeCredential`/`eraseCredential` return early), so credentials a user might otherwise expect to be cached via the generic git-credential mechanism for that remote are dropped, an unexpected trust-classification side effect the user has no way to detect.

I was not able to fully verify, within the available tooling, whether `ui.promptForGitHubSignIn` can complete a full OAuth token exchange against an arbitrary attacker-supplied endpoint (this would require reading `trampoline-ui-helper.ts` and the enterprise sign-in flow in more depth than the remaining iterations allowed), so I cannot confirm actual token exfiltration - only that the trust-classification bypass and its UI/behavioral consequences are concretely demonstrated in the code above.

### Likelihood Explanation
Any user who clones or adds a remote pointing at a server the attacker controls (a common, low-friction interaction - no local access, no admin rights, no prior malware, and no unusual steps beyond normal cloning) will trigger a credential-helper "get" call against that host whenever Git needs to authenticate, at which point the attacker's HTTP response fully determines the `wwwauth[...]` value Desktop trusts. No user interaction beyond ordinary clone/fetch is required to trigger the misclassification itself.

### Recommendation
Do not treat the `WWW-Authenticate` realm string (or the `x-github-request-id` header) as authoritative proof of GitHub/GHE identity. At minimum:
- Require the `isGitHubHost` network check (or an equivalent independently verifiable signal, e.g. checking `/meta` response body/signature rather than a single spoofable header) even when a `wwwauth[...]` realm claims `"GitHub"`.
- Never let unauthenticated header content alone switch a host into the privileged `'enterprise'`/`'github.com'` credential-handling path; corroborate with at least one additional, harder-to-forge signal (e.g., a valid TLS certificate chain the user has previously trusted for that endpoint, or an existing verified account record) before disabling the generic credential store/erase path or surfacing GitHub-branded sign-in UI.

### Proof of Concept
1. Attacker stands up an HTTP git server (or a MITM/compromised proxy in front of any non-GitHub remote) that responds to Git's authentication probe with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote and runs `fetch`/`pull`/`clone` in GitHub Desktop, which shells out to `git` configured to use Desktop's credential-helper trampoline.
3. Git captures the header and forwards it to the trampoline as a `wwwauth[...]` credential field; `createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind` sees `v.includes('realm="GitHub"')` and returns `'enterprise'`: [6](#0-5) 
4. Since no account matches this bogus enterprise endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` for what is actually an arbitrary attacker host, and any generic credential store/erase for this remote is suppressed: [7](#0-6)

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

async function storeCredential(cred: Credential, store: Store, token: string) {
  if ((await getEndpointKind(cred, store)) !== 'generic') {
    return
  }

  return useExternalCredentialHelper()
    ? storeExternalCredential(cred, token)
    : setGenericCredential(
        urlWithoutCredentials(getCredentialUrl(cred)),
        forceUnwrap(`credential missing username`, cred.get('username')),
        forceUnwrap(`credential missing password`, cred.get('password'))
      )
}

const storeExternalCredential = (cred: Credential, token: string) => {
  const path = getTrampolineEnvironmentPath(token)
  return approveCredential(cred, path, getGcmEnv(token))
}

async function eraseCredential(cred: Credential, store: Store, token: string) {
  if ((await getEndpointKind(cred, store)) !== 'generic') {
    return
  }

  return useExternalCredentialHelper()
    ? eraseExternalCredential(cred, token)
    : deleteGenericCredential(
        urlWithoutCredentials(getCredentialUrl(cred)),
        forceUnwrap(`credential missing username`, cred.get('username'))
      )
}
