### Title
Quadratic CPU exhaustion in `ThresholdKeys::read` via Lagrange interpolation over attacker-controlled participant count - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` trusts the serialized `t`/`n`/`i` fields and then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for every participant `1..=t`. Under `Interpolation::Lagrange`, each `interpolation_factor` call performs an `O(t)` product plus a field inversion, so the whole read is `O(t²)` field multiplications, `t` inversions, and `t` point-scalar multiplications — all driven by two attacker-controlled bytes worth of `u16` fields and `n` encoded points.

### Finding Description

`ThresholdKeys::read` reads `t`, `n`, `i` directly from the byte stream with only `u16` bounds and the `ThresholdParams::new` consistency checks (nonzero, `t <= n`, `i <= n`) [1](#0-0) . It selects `Interpolation::Lagrange` from a single byte [2](#0-1) , reads `n` verification shares [3](#0-2) , then calls `ThresholdKeys::new` [4](#0-3) .

`ThresholdKeys::new` computes the group key as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` [5](#0-4) . For Lagrange, `interpolation_factor` iterates over the entire `included` set (size `t`) computing `num *= share; denom *= share - i_f` and finishes with `denom.invert().unwrap()` [6](#0-5) . Total work is therefore `Θ(t²)` field multiplications plus `t` field inversions and `t` point scalar multiplications.

With `t = n = 65535` (both fit in `u16`), the input is only ~2.1 MB (65535 × 32-byte points plus header), but the computation performs ~4.3 billion field multiplications, 65535 inversions, and 65535 scalar-point multiplications. `ThresholdKeys::read` is an explicitly supported entry point for untrusted bytes.

### Impact Explanation

Analogous to CVE-2026-14741 (polynomial backtracking on a short string), a modest attacker-supplied payload forces CPU work quadratic in the payload length — on the order of tens of seconds to minutes per read on a single thread. Any service that deserializes `ThresholdKeys` from untrusted input (or calls `ThresholdKeys::new`/`view` on attacker-influenced parameters) can be stalled indefinitely by repeated requests, a denial of service with no authentication required.

### Likelihood Explanation

Reachability depends on an integrator passing untrusted bytes to `ThresholdKeys::read`, but the API provides no defense: no cap on `n`/`t`, no incremental/cheaper group-key derivation, and the `O(t)`-per-element inversion is unavoidable in the current formulation. `ThresholdView::view` repeats the same `O(t²)` pattern on attacker-chosen `included` sets [7](#0-6) .

### Recommendation

- Cap `t`/`n` to a realistic protocol maximum (e.g., Serai's `MAX_KEY_SHARES_PER_SET`) inside `ThresholdParams::new`/`ThresholdKeys::read`.
- Compute Lagrange coefficients in `O(t)` total via prefix/suffix products with a single batch inversion (Montgomery trick), removing the per-participant `O(t)` loop and per-participant inversion.

### Proof of Concept

```rust
// crypto/dkg: deserialize a ThresholdKeys blob with t = n = u16::MAX
let n: u16 = u16::MAX;
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(n.to_le_bytes());            // t
buf.extend(n.to_le_bytes());            // n
buf.extend(1u16.to_le_bytes());         // i
buf.push(1);                            // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. n {
  buf.extend(C::generator().to_bytes().as_ref()); // verification_shares
}
// ~2.1 MB input triggers ~t^2 field muls + t inversions + t scalar-muls
ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_slice());
```
