### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s, enabling construction of non-broadcastable spends — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to M-03 — where a withdrawal path unconditionally performs an operation (`lock()`) that is invalid under an external protocol state (vlCVX shutdown), permanently DoSing withdrawals — `Scanner::scan_block` unconditionally treats every transaction in a block identically, returning `ReceivedOutput`s for coinbase outputs that Bitcoin consensus makes unspendable for 100 blocks. There is no maturity check and the `ReceivedOutput` type carries no flag distinguishing a mature output from an immature one, so any downstream consumer that feeds the scan results into `SignableTransaction::new` will produce and sign a transaction the network will reject. The code itself acknowledges the hazard only in a doc comment.

### Finding Description
`scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for any `script_pubkey` matching the scanner's registered scripts, with no notion of transaction position or coinbase status. `scan_block` calls `scan_transaction` over `block.txdata` including `txdata[0]` (the coinbase) [1](#0-0) . A `ReceivedOutput` records only `offset`, `output`, and `outpoint`; nothing encodes maturity [2](#0-1) . `SignableTransaction::new` accepts any `Vec<ReceivedOutput>` and builds prevouts/inputs without maturity validation [3](#0-2) , and `TransactionSignMachine::sign` produces valid FROST signature shares over sighashes committing to those prevouts [4](#0-3) . The only mitigation is the doc comment on `scan_block` telling callers to post-filter or scan `block.txdata[1 ..]` [5](#0-4) .

Notably, the in-repo consumer already learned this lesson: `Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs` explicitly skips `block.txdata[0]` "burdened by maturity" [6](#0-5)  — meaning the safe behavior had to be reimplemented at the call site because the library reports unspendable outputs as spendable.

### Impact Explanation
An unprivileged miner can send coinbase (block reward + fees) to any P2TR address, including a Serai multisig's external or offset-registered script. Any wallet/indexer built on this crate that calls `scan_block` (the natural API for scanning blocks) will report those outputs as received and spendable. A subsequent spend built via `SignableTransaction::new` succeeds, consumes a threshold-signing round (preprocess/sign/complete across participants), and yields a transaction that violates Bitcoin's coinbase-maturity consensus rule (`bad-txns-premature-spend-of-coinbase`); relay and inclusion fail. Like M-03's forced `lock()` reverting withdrawals, the spend path is bricked by an external state (maturity) the code never checks — and unlike a transient revert, the signed transaction can never become valid since its outpoint/inputs are fixed; the signing round and any fee planning around it are wasted, and naive callers may retry indefinitely.

### Likelihood Explanation
Triggering requires only that a miner direct a coinbase payout to a scanned script — trivially within miner's control — and that a consumer use `scan_block` rather than `scan_transaction(&block.txdata[1..])`. The wallet test itself demonstrates the trap: `send_and_get_output` scans `block.txdata[0]`'s coinbase and only works because it manually mines 100 blocks to maturity before spending [7](#0-6) . Severity is Medium: funds are not lost permanently (the output matures), but the reported-receivable vs. spendable mismatch directly causes invalid spends, matching the "funds reported received that are not spendable" impact class.

### Recommendation
Make maturity a property of `ReceivedOutput` rather than a doc-comment footgun:
- Have `scan_block` skip `block.txdata[0]` entirely (matching `processor/src/networks/bitcoin.rs`'s `get_outputs`), or accept a coinbase-maturity-aware path that marks returned outputs immature.
- Add a `mature`/`coinbase` field to `ReceivedOutput` (with `read`/`write` updated accordingly) and have `SignableTransaction::new` reject immature inputs, so an unspendable input fails locally instead of after a distributed signing round.
- At minimum, `TransactionMachine` construction should be the enforcement point, since the doc comment on `scan_block` is the only current guard.

### Proof of Concept
1. Register a `Scanner` for key `K`; a miner mines a block whose coinbase pays `p2tr_script_buf(K)`.
2. Call `scanner.scan_block(&block)` — it returns a `ReceivedOutput` for the coinbase `OutPoint` indistinguishable from a mature one.
3. Call `SignableTransaction::new(vec![output], &payments, change, None, fee)` — succeeds.
4. Run `preprocess` → `sign` → `complete` across threshold participants — a fully signed `Transaction` is produced.
5. Broadcast: the node rejects with `bad-txns-premature-spend-of-coinbase`; the transaction can never confirm because the input's outpoint is fixed, DoSing that spend and wasting the signing ceremony.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
