### Title
`restrict-assets?`/`as-contract?` fungible/NFT allowance check treats the user-choosable asset name `"*"` as a match-all wildcard, letting one allowance authorize movement of every other asset in a contract - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`check_allowances` in `clarity/src/vm/functions/post_conditions.rs` reserves the literal `AssetIdentifier { asset_name: "*" }` as an internal sentinel meaning "allowance applies to every fungible/non-fungible asset in this contract." But `"*"` is also a syntactically valid Clarity asset name (`CLARITY_NAME_REGEX_STRING` permits `^[-+=/*]$`), and the `with-ft` / `with-nft` allowance constructors (`eval_allowance`, same file, lines 159-249) accept any Clarity name the calling code supplies for the `asset-name` argument, without excluding `"*"`. A contract that defines (or that the calling contract references) an asset literally named `*` in `(with-ft <contract> "*" <amount>)` is indistinguishable, in the allowance map, from the wildcard sentinel that is supposed to cover *all* fungible tokens of that contract.

### Finding Description
`check_allowances` builds `ft_allowances`/`nft_allowances` as `HashMap<AssetIdentifier, ...>` keyed by `(contract_identifier, asset_name)` [1](#0-0) . When checking actual asset movement, for each moved asset it does an exact-match lookup plus a second lookup for the sentinel key `AssetIdentifier { contract_identifier: asset.contract_identifier.clone(), asset_name: ClarityName::from_literal("*") }`, and merges any entries found under that sentinel key into the allowance list for the moved asset [2](#0-1) [3](#0-2) .

This wildcard-key design assumes no legitimate on-chain asset is literally named `*`. That assumption is false: `ClarityName`'s validating regex explicitly allows the single character `*` (`^[-+=/*]$` alternative) [4](#0-3) , and the `with-ft`/`with-nft` allowance parser takes the asset name straight from a user-supplied Clarity string with no denylist for `"*"` [5](#0-4) [6](#0-5) .

Consequence: if a contract author writes `(with-ft some-contract "*" u100)` intending to authorize only movement of a real token literally named `*` up to `u100`, that allowance is silently merged into the allowance set for *every other fungible token in `some-contract`* — because the check code cannot distinguish "an explicit allowance for the token named `*`" from "the wildcard meaning all tokens." Symmetrically, and more dangerously, if the intended wildcard-granting call path is ever reused/copied by a contract that expects `"*"` to only cover a specifically named token (or if any tooling constructs allowances programmatically from token names harvested from user input), the equality the mechanism is supposed to enforce — "assets moved must be less than or equal to the amount explicitly allowed for that specific asset" — breaks down for any contract that mints/uses a token whose name happens to be `*`.

This is precisely the "user-controlled key collides with a privileged sentinel key" bug class in the Liferay report (a caller-controlled identifier is compared against/aliased with a different scope than intended), translated into the post-condition allowance-lookup mechanism, and it breaks the "asset moving past its post-conditions" equality that `restrict-assets?`/`as-contract?` are meant to guarantee.

### Impact Explanation
If a contract mistakenly (or an attacker deliberately) causes an allowance to be registered for the literal name `"*"`, any other fungible/non-fungible asset transfer of the same contract inside the same `restrict-assets?`/`as-contract?` scope is treated as covered by that allowance's amount/ID list, even though no such allowance was explicitly granted for that specific asset. This is an "asset moving past its post-conditions" scenario (Critical bucket per the report's impact classification), because the sandboxing guarantee `restrict-assets?`/`as-contract?` provide — that only explicitly allow-listed assets/amounts can move within the guarded body — is bypassed for any asset sharing a contract with an asset named `*`.

### Likelihood Explanation
Exploitability depends entirely on Clarity code (a contract) deliberately or accidentally using the asset name `"*"` as an argument to `with-ft`/`with-nft`. Since `"*"` is a valid, non-reserved Clarity name and the allowance-construction code path performs no reservation/escaping of it, any contract author who defines or references a token named `*` (unusual but fully legal) triggers this collision automatically without any special crafting beyond normal contract deployment. No privileged access, miner cooperation, or off-chain conditions are required — only a contract using `restrict-assets?`/`as-contract?` with a `with-ft`/`with-nft` allowance whose asset name is `*`.

### Recommendation
Reserve `"*"` as an allowance sentinel that cannot be produced by ordinary `with-ft`/`with-nft` calls: either (a) introduce a distinct, dedicated `Allowance` variant (e.g. `Allowance::FtAll(contract)`/`Allowance::NftAll(contract)`) built by dedicated native functions instead of encoding "all assets" as a magic asset name, or (b) explicitly reject/escape the literal name `"*"` when parsing `with-ft`/`with-nft` arguments in `eval_allowance` so it can never alias with the internal wildcard sentinel used by `check_allowances`.

### Proof of Concept
1. Deploy `token-a.clar` defining a fungible token literally named `*` (`(define-fungible-token * u1000000)`) alongside a second, unrelated fungible token `real-token` in the same contract.
2. Deploy a caller contract that executes:
   ```
   (restrict-assets? tx-sender ((with-ft .token-a "*" u1))
     (try! (ft-transfer? real-token u1000000 tx-sender 'SP000000000000000000002Q6VF78))
   )
   ```
3. Because `check_allowances` looks up the wildcard key `AssetIdentifier{contract: .token-a, asset_name: "*"}` for every moved asset in `.token-a` (`clarity/src/vm/functions/post_conditions.rs` lines 608-613), the `u1` allowance nominally granted only for the token named `*` is merged into the allowance list checked for `real-token`, permitting the `u1000000` transfer of `real-token` to pass with only a `u1` "allowance," despite no allowance for `real-token` having been declared.
