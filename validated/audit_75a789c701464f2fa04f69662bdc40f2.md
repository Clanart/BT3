### Title
Missing `request.from` module binding in `onAccept` lets any account on the Hyperbridge chain forge a `Withdraw` governance message and drain BandwidthManager's native balance - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.onAccept` only checks the ISMP `msg.sender == host()` (`onlyHost`) and `request.source == hyperbridge` chain id, but never validates `request.from` against `PALLET_BANDWIDTH_MODULE_ID`. This means any module/account capable of dispatching a POST request from the Hyperbridge chain to `BandwidthManager`'s address can impersonate `pallet-bandwidth` and trigger privileged `OnAcceptActions`, including the native-token `Withdraw` branch.

### Finding Description
`onAccept` is guarded like this: [1](#0-0) 

The function checks:
1. `msg.sender == host()` via the `onlyHost` modifier [2](#0-1) 
2. `request.source.equals(hyperbridge)` [3](#0-2) 

It never checks `request.from` (the source-chain module identity, defined in `PostRequest.from`) against `PALLET_BANDWIDTH_MODULE_ID` [4](#0-3) . The comment at the top of the contract even documents the module id specifically so it can be enforced on inbound messages [5](#0-4) , but that check is never actually performed in `onAccept`.

`request.source` only proves the message legitimately originated on the Hyperbridge chain (relayed/verified by the Host contract) — it does not prove which module/pallet on that chain authored the payload. Any module, pallet, or unprivileged actor able to dispatch an ISMP POST request from the Hyperbridge chain targeting `to = <BandwidthManager address>` can set `from` to an arbitrary value (since `from` is attacker-controlled application-layer data, not authenticated as `pallet-bandwidth` by the EVM-side app) and supply a body whose first byte selects `OnAcceptActions.Withdraw`, followed by an ABI-encoded `Withdrawal{token: address(0), beneficiary: <attacker>, amount: <balance>}`.

Because `onAccept` accepts this without checking `from`, it hits the native-withdraw branch: [6](#0-5) 

and unconditionally low-level-`call`s `w.amount` of native ETH to `w.beneficiary`, draining any native token balance the contract holds.

### Impact Explanation
This allows unauthorized execution of a privileged governance action (asset withdrawal) and theft of any native ETH balance held by `BandwidthManager`, moving funds to an attacker-chosen beneficiary rather than the rightful treasury/owner. This directly matches the bounty's "unauthorized execution" and "wrongful beneficiary/amount" impact categories. The same missing check also lets an attacker forge `SetTiers` messages to corrupt pricing, but the Withdraw path is the direct fund-loss vector.

### Likelihood Explanation
Exploitability depends entirely on whether any unprivileged actor on the Hyperbridge chain can dispatch an arbitrary ISMP POST request with a spoofed `from` field to a chosen EVM destination `to` address. Whether such dispatch is achievable by fully unprivileged accounts (vs. requiring some already-registered pallet identity) could not be confirmed from the EVM-side code alone; it depends on the ISMP router/dispatch authorization model on the Substrate side (`pallet-ismp` dispatch permissions), which is outside the files reviewed here. If the underlying ISMP router allows any pallet/module to dispatch with an arbitrary `from`, this is directly and trivially exploitable by any account capable of triggering a pallet-level dispatch; if the router itself authenticates `from` to the calling pallet's registered id, this specific instance would be blocked upstream. Given the EVM contract itself performs no such check and the surrounding code comments indicate the intent to enforce module id, this should be treated as a real gap in defense-in-depth at minimum, and a full compromise if the router-side origin binding is weaker than assumed.

### Recommendation
Add an explicit `from` check in `onAccept`, mirroring the `source` check:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
This binds the accepted message to both the correct chain and the correct module identity, consistent with the module-binding invariant required across request/response paths.

### Proof of Concept
1. Attacker (or any account able to trigger an ISMP dispatch from the Hyperbridge chain) crafts a POST request with:
   - `source = hyperbridge chain id` (satisfied trivially, since dispatch genuinely originates from that chain)
   - `to = address(BandwidthManager)` on the destination EVM chain
   - `from = <anything other than "BWMARKET">` (unchecked)
   - `body = abi.encodePacked(uint8(1), abi.encode(Withdrawal({token: address(0), beneficiary: attacker, amount: address(BandwidthManager).balance})))`
2. Host relays/verifies the request and calls `BandwidthManager.onAccept(incoming)`.
3. `onAccept` passes both existing checks (`onlyHost`, `request.source == hyperbridge`), decodes `action = OnAcceptActions.Withdraw`, and executes:
   `w.beneficiary.call{value: w.amount}("")`
4. Native ETH balance is transferred to the attacker-controlled `beneficiary`, with `Withdrawn` event emitted as if it were a legitimate governance withdrawal. [7](#0-6)

```text
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
```
