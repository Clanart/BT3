## Finding

Valid vulnerability related to `getRewardablePercentWAD` / `_calExpireForfeit` being trivially bypassable via a costless `cancelUnlock`, although the specific "front-run getReward with startUnlock" framing needs correction based on the actual code flow. Here's the accurate mechanism:

- `vlMGPBaseRewarder.balanceOf()` [1](#0-0)  reads `stakingInfo` from `MasterMagpie`, which for `vlMGP` equals `getUserTotalLocked + getUserAmountInCoolDown` [2](#0-1) . This value is unaffected by `startUnlock`, since `startUnlock` only moves an amount from "locked" to "in cool-down" bucket internally — it does not reduce the user's total staked balance in `MasterMagpie` (only `unlock()` finally calls `withdrawVlMGPFor` to reduce it) [3](#0-2) . So `_earned()` keeps accruing on the **full** balance regardless of cooldown status [4](#0-3) .
- The forfeiture penalty for being in cooldown is only applied at payout time, inside `_sendReward`, using the **current** `getRewardablePercentWAD(_account)` [5](#0-4) . `getRewardablePercentWAD` computes the rewardable share from `fullyInLock` vs `inCoolDown` state at call time, with cooldown amounts getting a decayed/partial share [6](#0-5) .
- Critically, `cancelUnlock` has **no fee, no cooldown-of-its-own, and no restriction on frequency** — it can be called any time before `endTime` to instantly zero out `amountInCoolDown` and move the amount back to "locked" [7](#0-6) . `startUnlock` can likewise be re-invoked at any time to re-enter cooldown [8](#0-7) , and it does not use "cool-down of cool-down" restart penalties besides resetting `startTime`.

Because forfeiture is calculated purely off the *state at claim time* rather than an integral of cooldown status over the accrual period, a user can:
1. Stay in cooldown to preserve optionality to withdraw MGP later, while still earning rewards on the full un-diminished `balanceOf`.
2. Immediately before triggering `getReward` (routed via `MasterMagpie.multiclaimFor`, which only requires `onlyMasterMagpie` on the rewarder — reachable by any EOA calling `MasterMagpie`), call `cancelUnlock` on their cooling-down slot, making `getRewardablePercentWAD` report 100% locked and thus zero forfeiture in `_calExpireForfeit`.
3. Call `startUnlock` again right after claiming to re-enter cooldown, at zero cost other than resetting the decay timer for eventual `unlock()`.

This lets a user permanently avoid the intended cooldown reward-forfeiture penalty at negligible cost (just gas + timer reset), defeating the purpose of `getRewardablePercentWAD`'s decay mechanic, which is designed to redistribute forfeited rewards back to the pool via `_queueNewRewardsWithoutTransfer` [9](#0-8) .

However, the specific mechanics asserted in the question — that `startUnlock` itself is used to "snapshot" a higher earned value that later gets protected by `cancelUnlock` — do not match the code: `startUnlock` calls `IMasterMagpie(masterMagpie).multiclaimFor` **before** updating `userUnlockings` [10](#0-9) , meaning any pending reward is paid out and forfeiture-calculated while the user is still 100% locked (i.e., no forfeiture applies at that specific moment regardless of manipulation) — so that step contributes no exploitable delta. The actual exploitable step is solely the cheap, unrestricted `cancelUnlock`-before-`getReward` pattern, decoupled from any interaction with `startUnlock` timing relative to `queueNewRewards`.

### Title
Reward forfeiture bypass via costless `cancelUnlock` before claim - ([File: VLMGP.sol, rewards/vlMGPBaseRewarder.sol])

### Summary
The vlMGP cooldown reward-forfeiture mechanic in `vlMGPBaseRewarder._calExpireForfeit`/`VLMGP.getRewardablePercentWAD` evaluates penalty based only on the state at claim time, not on cooldown exposure during the accrual period. Since `cancelUnlock` is free, uncooled-down, and callable at will, a user can always cancel their cooldown slot immediately before claiming rewards and restart it afterward, permanently avoiding the intended forfeiture while still accruing rewards on the undiminished full balance during cooldown.

### Finding Description
`vlMGPBaseRewarder.balanceOf` [1](#0-0)  and `earned`/`_earned` [11](#0-10) [4](#0-3)  accrue rewards on the user's total `vlMGP` (locked + in-cooldown) balance, which is never reduced by `startUnlock` — only the final `unlock()` call reduces it via `withdrawVlMGPFor` [12](#0-11) . To compensate for this over-accrual during cooldown, the protocol applies a forfeiture at claim time via `_calExpireForfeit`, using `getRewardablePercentWAD` [6](#0-5) , which decays the rewardable share for amounts sitting in cooldown.

The flaw is that `getRewardablePercentWAD` is evaluated only at the moment `_sendReward` runs (inside `getReward`), not integrated over the accrual window. `cancelUnlock` [7](#0-6)  has no fee and no waiting period of its own — it just requires the slot to still be within its cooldown window — so an attacker can zero out their `amountInCoolDown` right before calling `getReward` (via `MasterMagpie.multiclaimFor`), making `getRewardablePercentWAD` report 100% (fully locked), thus `forfeitAmount == 0` in `_calExpireForfeit` [13](#0-12) . Immediately after claiming, the attacker calls `startUnlock` again to re-enter cooldown (resetting only `startTime`/`endTime`, at no monetary cost).

No existing modifier or accounting update prevents this: `getReward` only checks `onlyMasterMagpie`, and reward accounting (`_updateFor`) simply snapshots `userRewards` based on current balance, oblivious to the cooldown-cancel timing games.

### Impact Explanation
This nullifies the economic purpose of the cooldown-forfeiture mechanism: users who intend to eventually withdraw (i.e., who cycle through cooldown) can indefinitely avoid the intended reward penalty by canceling right before every claim, at negligible gas cost. The forfeited amount that should be redistributed to remaining stakers via `_queueNewRewardsWithoutTransfer` [9](#0-8)  is instead retained by the manipulating user, reducing the yield that would otherwise accrue to honest long-term-locked participants. This is a quantifiable, repeatable loss of yield to the protocol's reward pool (Immunefi class: "theft/permanent loss of unclaimed yield" for other stakers, arising from bypass of intended fee/penalty logic).

### Likelihood Explanation
Fully unprivileged and highly feasible: requires only holding vlMGP and calling public functions `cancelUnlock`, `startUnlock`, and triggering `MasterMagpie.multiclaimFor`/`getReward`. No capital beyond normal vlMGP holdings, no flash loan, no special timing races against other users — it is entirely self-contained and repeatable every time the user wants to claim rewards.

### Recommendation
Compute forfeiture based on a time-weighted/integrated cooldown exposure recorded at the time rewards accrue (e.g., snapshot cooldown ratio at each `rewardPerTokenStored` update and accumulate weighted forfeiture), rather than using the instantaneous state at claim time. Alternatively, disallow `cancelUnlock` from restoring full "locked" reward-eligibility retroactively for the accrual period during which the funds were actually in cooldown — e.g., track cumulative time-in-cooldown per unlocking session that persists even after cancellation, and use that to compute forfeiture on any actually earned rewards.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` with a reward token; set a `coolDownInSecs` (e.g., 7 days).
2. User A locks `1000 MGP` via `VLMGP.lock`.
3. Queue rewards via `queueNewRewards` on the rewarder to build up `rewardPerTokenStored`.
4. Advance time; call `startUnlock(500)` for user A to enter cooldown for half the balance; advance time partway through the cooldown window (so `getRewardablePercentWAD` would normally show a decayed/partial rewardable percent if claimed now).
5. Baseline case: call `MasterMagpie.multiclaimFor` (triggering `getReward`) directly while still in cooldown — assert `forfeitAmount > 0` (i.e., `RewardPaid` amount < full `earned()`), confirming forfeiture is applied to the cooldown-affected reward.
6. Exploit case: reset state, repeat steps 1–4, but immediately before calling `multiclaimFor`, call `VLMGP.cancelUnlock(slotIndex)`; then call `multiclaimFor`; assert `toSend == full earned amount` (i.e., `forfeitAmount == 0`) despite having spent the accrual period in cooldown.
7. Immediately after claiming, call `startUnlock(500)` again to re-enter cooldown, showing the cycle is repeatable with `totalAmountInCoolDown` and `slot` reset, at only the cost of `startTime` resetting — demonstrating the user retains full future-unlock optionality while never paying the forfeiture.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
