### Title
`balance()`/`all_balances()` bank precompile view functions report locked (vesting) balances as if fully available, misleading external DeFi integrations - ([File: precompiles/bank/bank.go])

### Summary
The Sablier `refundableAmountOf()` bug class is: a public getter meant to represent an "amount usable/recoverable by the caller" omits a status/eligibility check (`isCancelable`) that governs whether that amount is actually obtainable, so external integrators (e.g., lending protocols) make incorrect decisions (e.g., liquidation sizing) based on a number that looks available but is not. The Sei bank precompile's `balance()` and `all_balances()` methods have the analogous flaw: they return the full account `GetBalance`/`GetAllBalances` amount without checking `LockedCoins`/`SpendableCoins`, so a caller (including any EVM contract, e.g. a lending/collateral protocol built on Sei) sees a balance that includes vesting-locked `usei` that cannot actually be transferred out via `SendCoins`.

### Finding Description
`PrecompileExecutor.balance()` and `PrecompileExecutor.all_balances()` in `precompiles/bank/bank.go` (and identically in every legacy version under `precompiles/bank/legacy/*`) simply call `p.bankKeeper.GetBalance(...)` / `p.bankKeeper.GetAllBalances(...)` and pack the raw total into the ABI response: [1](#0-0) [2](#0-1) 

Neither function consults `LockedCoins` (which returns non-zero for vesting accounts) or `SpendableCoins`, which is the Cosmos SDK's canonical "amount that can actually be moved" computation: [3](#0-2) 

This mirrors the Sablier defect exactly: `refundableAmountOf()` computed `deposited - streamed` without checking `isCancelable`, silently including funds that were not actually retrievable. Here, `balance()`/`all_balances()` compute the raw ledger balance without checking `LockedCoins`, silently including funds that are not actually transferable — an attempt to `SendCoins`/`sendNative` for the full reported amount from a vesting account would fail or be capped by `SubUnlockedCoins` semantics, since actual sends operate on spendable/unlocked balances, not the raw total exposed by this view.

### Impact Explanation
Any EVM contract calling the bank precompile's `balance`/`all_balances` view (e.g., a lending/collateral-management protocol built on Sei that uses these precompile calls to assess a borrower's usei holdings) will overstate the amount of native `usei` a vesting account genuinely has liquid. This can lead to fund-loss scenarios analogous to the report's "lending protocol liquidation" example: a protocol could under-collateralize or mis-price a position based on a balance figure that includes funds locked until a future vesting time, and when it later attempts to move/seize those funds it will find them unavailable, causing bad debt or failed liquidations. This satisfies the "fund loss" bar because on-chain financial decisions keyed to this value can result in an unauthorized transfer failure or a mis-valued position that a protocol cannot recover from.

### Likelihood Explanation
Likelihood is inherent to normal usage: any EVM caller — including any public-RPC client or unprivileged contract — can call the bank precompile's `balance`/`all_balances` methods on any address at any time, no special permission required. The only prerequisite for the misleading result to matter is that the queried address is a vesting account with a nonzero `LockedCoins` value, which is a normal, reachable Cosmos SDK account state (`x/auth/vesting`).

### Recommendation
Mirror the Sablier fix pattern: add the missing precondition check before reporting the amount as fully usable. Concretely, either:
1. Have `balance()`/`all_balances()` return `SpendableCoins`-derived amounts (subtracting `LockedCoins`) instead of the raw `GetBalance`/`GetAllBalances` total, or
2. If exact parity with `GetBalance` semantics is required for backward compatibility, expose a clearly documented separate "spendable" query (as `SpendableCoins` already exists in `BaseViewKeeper`) and update precompile ABI/documentation so integrators know `balance()` includes locked funds — but given DeFi integrators are the primary risk (as in the referenced report), the safer default is to make the externally exposed `balance`/`all_balances` reflect spendable amounts by default, matching the Sablier recommendation of gating the returned number on the eligibility flag (here, `LockedCoins == 0` for the relevant denom).

### Proof of Concept
1. Create a Cosmos vesting account (e.g., via `x/auth/vesting` `MsgCreateVestingAccount`) and fund it with `usei` such that most of the balance is subject to a future vesting/unlock schedule.
2. From any EVM contract or `eth_call`, invoke the bank precompile (address `0x1002`-equivalent) `balance(address,string)` or `all_balances(address)` for that account's associated EVM address, per `precompiles/bank/bank.go` `balance`/`all_balances`.
3. Observe the returned amount equals the full ledger balance (`GetBalance`/`GetAllBalances`), with no reduction for `LockedCoins`.
4. Attempt to actually move that full amount via `SendCoins`/the precompile's `sendNative` — the transfer of the locked portion will fail/behave differently from what the balance view implied, demonstrating the reported "available" amount was not actually obtainable, analogous to `refundableAmountOf()` reporting a nonzero refundable amount for a non-cancelable (unrefundable) stream.

Note: I was not able to fully trace whether `SubUnlockedCoins`/`SendCoins` in `sei-cosmos/x/bank/keeper/send.go` explicitly rejects sends that dip into locked coins (the file's relevant `SendCoins` body was not fully retrieved before the tool budget ran out), so the exact failure mode of a downstream transfer attempt is inferred from the `SubUnlockedCoins` interface method name and standard Cosmos SDK vesting semantics rather than directly confirmed in this session.

func (p PrecompileExecutor) all_balances(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) ([]byte, uint64, error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	addr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}

	coins := p.bankKeeper.GetAllBalances(ctx, addr)

	// convert to coin balance structs
	coinBalances := make([]CoinBalance, 0, len(coins))

	for _, coin := range coins {
		coinBalances = append(coinBalances, CoinBalance{
			Amount: coin.Amount.BigInt(),
			Denom:  coin.Denom,
		})
	}

	bz, err := method.Outputs.Pack(coinBalances)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

// LockedCoins returns all the coins that are not spendable (i.e. locked) for an
// account by address. For standard accounts, the result will always be no coins.
// For vesting accounts, LockedCoins is delegated to the concrete vesting account
// type.
func (k BaseViewKeeper) LockedCoins(ctx sdk.Context, addr sdk.AccAddress) sdk.Coins {
	acc := k.ak.GetAccount(ctx, addr)
	if acc != nil {
		vacc, ok := acc.(vestexported.VestingAccount)
		if ok {
			return vacc.LockedCoins(ctx.BlockTime())
		}
	}

	return sdk.NewCoins()
}

// SpendableCoins returns the total balances of spendable coins for an account
// by address. If the account has no spendable coins, an empty Coins slice is
// returned.
func (k BaseViewKeeper) SpendableCoins(ctx sdk.Context, addr sdk.AccAddress) sdk.Coins {
	total := k.GetBalance(ctx, addr, "usei").Amount
	locked := k.LockedCoins(ctx, addr).AmountOf("usei")

	spendable := total.Sub(locked)
	if spendable.IsNegative() {
		return sdk.NewCoins()
	}
	return sdk.NewCoins(sdk.NewCoin("usei", spendable))
}
