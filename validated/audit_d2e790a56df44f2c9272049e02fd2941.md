## Analysis

The strongSwan CVE describes a class-level flaw: a cloning routine treats a **zero-length-but-non-NULL** buffer as "nothing to clone," so the clone ends up sharing the exact same underlying storage as the original instead of receiving an independent copy. When the two independently-owned objects are later destroyed/freed on their own lifetimes, this aliasing turns into memory-safety corruption (double-free in strongSwan's case).

The function begins with a raw `memcpy` of the entire message body (which includes every field's `upb_StringView{data,size}` struct) from `src` into `dst`. For scalar string/bytes fields it then only performs an actual allocation-and-copy (`upb_Clone_StringView`) **when `str.size != 0`**. When `str.size == 0`, the code takes no action at all — `dst`'s field is left exactly as the initial `memcpy` set it, i.e. **byte-for-byte identical to `src`'s `StringView`, including whatever `data` pointer `src` happened to hold**, even if that pointer is non-NULL (e.g. it can be a stale/former allocation left over after a field was cleared to empty via `ClearNonDefaultToEmpty`/`ClearToEmpty`-style operations, or an arbitrary non-NULL sentinel produced by wire decode/accessor logic for a zero-length value).

This is precisely the strongSwan invariant failure transposed onto Protobuf's own explicit "make an independent clone" contract for `upb_Message_DeepClone`/`upb_Message_DeepCopy` (as opposed to `upb_Message_ShallowClone`, whose header explicitly documents that shallow clones intentionally alias the source and require it to outlive the clone): [3](#0-2) 

`DeepClone`/`DeepCopy` carry no such caveat — the test suite explicitly exercises the "clone survives after source arena is freed" guarantee: [4](#0-3) 

Here the test frees `string_in_arena`/`source_arena` right after cloning and expects `clone` to still read the correct data — this is only safe because the string was **non-empty**, hitting the `str.size != 0` clone path. There is no equivalent test for a string field whose `StringView.data` is non-NULL but `size == 0` — i.e. no test proves the "empty but non-NULL" case is defended, which is exactly the untested edge the CVE analog targets.

**Why this matters (impact) is limited but real:** because `upb_Arena` frees memory in bulk (block-list free), not per-object `free()`, this specific aliasing does not manifest as a literal C `free(ptr); free(ptr);` double-free the way strongSwan's chunk-based clone does. What it does produce is a **dangling-pointer aliasing violation**: `dst`'s "independent" clone silently retains a raw pointer into `src`'s arena/backing buffer for any zero-length string/bytes field whose `data` happens to be non-NULL. If the source arena is freed (which the whole point of `DeepClone` is to make safe) while the destination clone is retained, and any code path later reads `str.data` for that field (e.g., pointer-identity comparisons, `memcmp`/`memcpy` utilities that don't special-case `size==0`, or FFI/C bridges from Python/Ruby/Rust bindings that hand the raw pointer to native code without checking size), that dereferences freed/reused memory — a genuine "cloned-but-aliased" integrity violation matching the CVE's root cause exactly (empty-but-non-NULL not independently cloned).

**Why this is not a stronger/Critical finding:** in the normal decode paths used for attacker-controlled binary/ProtoJSON input, empty string/bytes fields are represented with `data == NULL, size == 0` (see `upb_StringView_FromDataAndSize(NULL, 0)` used as the default throughout `copy.c`), so in the common case this exact code path is benign. The non-NULL-but-empty state is reachable only through non-decode paths (accessor mutation followed by clear-to-empty, or FFI-set fields), which narrows likelihood.

## Title
Empty-but-non-NULL string/bytes fields are not independently cloned in `upb_Message_DeepClone`/`DeepCopy` — (`upb/message/copy.c`)

## Summary
`_upb_Message_Copy` (backing both `upb_Message_DeepClone` and `upb_Message_DeepCopy`) skips the clone-and-copy step for any scalar string/bytes field whose `StringView.size == 0`, relying solely on the initial raw `memcpy` of the message body. If the source field's `StringView.data` pointer is non-NULL despite `size == 0`, the destination "deep clone" ends up aliasing the exact same pointer as the source instead of receiving independently-owned storage, contradicting the documented and tested guarantee that deep clones survive freeing of the source arena.

## Finding Description
`upb_Clone_StringView` (`upb/message/copy.c:39-50`) and the scalar-field loop in `_upb_Message_Copy` (`upb/message/copy.c:264-273`) both gate the actual arena allocation/copy on `size != 0`. The enclosing function first does a blind `memcpy(dst + 1, src + 1, ...)` of the whole message struct (`upb/message/copy.c:246`), which copies every field's raw `{data, size}` StringView bytes verbatim, including string fields. For size==0 fields, no follow-up `upb_Message_SetString` call ever replaces that memcpy'd value, so `dst`'s field keeps `src`'s original `data` pointer unchanged. This transfers the strongSwan defect's exact invariant failure — "parsed identity encodings that are empty but non-NULL are not correctly cloned" — into upb's message-clone primitive: emptiness is used as a proxy for "nothing to own," which is false whenever the pointer is non-NULL leftover state.

## Impact Explanation
Impact is integrity/memory-safety (dangling pointer aliasing), not a literal double-`free()`, because upb arenas free in bulk rather than per-allocation. A `upb_Message_DeepClone` result can retain a pointer into a source arena/buffer for zero-length fields; once the source is freed independently (the exact scenario `DeepClone` is meant to make safe, and which the existing test suite validates for non-empty strings), any later dereference of that stale pointer on the "independent" clone is a use-after-free read. This is reachable from any consuming application/binding (Python, Ruby, Rust, hpb) that calls `DeepClone`/`DeepCopy`/`CopyFrom`/`MergeFrom`-equivalents on attacker-influenced messages containing empty string/bytes fields with non-NULL backing pointers.

## Likelihood Explanation
Moderate-to-low. Standard wire/JSON decode paths represent empty strings as `{NULL, 0}` (per the `empty_string` default used throughout `copy.c`), so the vulnerable state (`data != NULL, size == 0`) is not produced by ordinary parsing of a fresh message. It becomes reachable when a message is mutated to empty via clear/set-to-empty operations (leaving stale non-NULL pointers depending on the setter implementation) and then deep-cloned, or via language-binding FFI paths that construct StringViews directly. This is a plausible but non-default trigger path, and no existing test in `copy_test.cc` exercises this specific non-NULL-empty-string edge case.

## Recommendation
In `upb_Clone_StringView` and the scalar-field branch of `_upb_Message_Copy`, do not use `size == 0` as the sole gate for skipping the clone. Either (a) always overwrite the destination field with a canonical `{NULL, 0}` StringView when `size == 0` regardless of the source's `data` pointer (removing the aliasing memcpy remnant), or (b) always allocate/copy independent of size (as done unconditionally in `upb_Clone_MessageValue`'s array/map path at `upb/message/copy.c:64-76`, which has no such size==0 special case and is therefore not subject to this issue). Add a regression test in `copy_test.cc` that sets a string field to a non-NULL, zero-length `StringView`, deep-clones it, frees the source arena, and asserts the clone's field pointer is independent (e.g., NULL or arena-owned) rather than aliasing the freed source pointer.

static upb_StringView upb_Clone_StringView(upb_StringView str,
                                           upb_Arena* arena) {
  if (str.size == 0) {
    return upb_StringView_FromDataAndSize(NULL, 0);
