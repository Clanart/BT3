### Title
Attacker-controlled `t`/`n` in `ThresholdKeys::read` trigger quadratic Lagrange interpolation (O(t²) scalar ops + t field inversions) — CPU DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The `uri-template-lite` advisory is an algorithmic-complexity DoS: attacker-supplied input drives work superlinear in the input size. Serai's analog is in `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg`. Two attacker-controlled `u16` fields (`t`, `n`) size a Lagrange group-key computation whose cost is `O(t²)` scalar multiplications plus `t` field inversions, performed unconditionally during deserialization of untrusted bytes.

### Finding Description
`ThresholdKeys::<C>::read` reads `t`, `n`, `i` directly from the byte stream, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:591-631`). `ThresholdKeys::new` computes the group key as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [1](#0-0) 

For `Interpolation::Lagrange`, each `interpolation_factor` call iterates the full `included` list and performs a field inversion:

```rust
for l in included {
  if i == *l { continue; }
  num *= share;
  denom *= share - i_f;
}
num * denom.invert().unwrap()
``` [2](#0-1) 

So a single `read` performs `t` inversions plus `t*(t-1)` scalar multiplications, with `t` bounded only by `u16::MAX` (65535) and `ThresholdParams::new` checking `t <= n` (`crypto/dkg/src/lib.rs:166-179`). With `t = n = 65535`, deserialization of ~2 MB of input (65535 group encodings + scalars) produces ~4.3·10⁹ scalar multiplications and 65535 field inversions — minutes of CPU work per deserialization. The same quadratic cost recurs in `ThresholdKeys::view`, which calls `interpolation_factor` once per included participant (`crypto/dkg/src/lib.rs:500-507`), so any later `view(included)` with a large `included` set repeats it.

The reader also does no early bound check before allocating `Vec::with_capacity(n)` / looping `1..=n` on `read_G` (`crypto/dkg/src/lib.rs:604-623`), but that part is linear in bytes actually present; the amplification is the `O(t²)` interpolation inside `ThresholdKeys::new`.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as an untrusted entry point) can cause sustained CPU exhaustion with a ~2 MB payload. Repeated submissions can stall a signing node/processor. This is a pure availability attack: no key material is leaked, but threshold signing can be halted, matching the Medium-severity ReDoS class (CWE-1333 generalizes to algorithmic-complexity DoS).

### Likelihood Explanation
Reachability depends on an integration passing untrusted bytes into `ThresholdKeys::read` (e.g., key-share blobs received during DKG/reshare flows). `t`/`n` are fully attacker-controlled up to `65535`, the only constraint being `t <= n` and `i <= n`, plus enough bytes to satisfy the `read_F`/`read_G` loops. No protocol-level cap on `n` appears in this crate, so worst-case cost is achievable.

### Recommendation
- Enforce a protocol-appropriate upper bound on `n`/`t` in `ThresholdKeys::read` (or `ThresholdParams::new`) before interpolation, matching the real maximum validator set size.
- Alternatively, compute the group key via a single multiexp over `(factor, share)` pairs and reuse a batched/deduplicated Lagrange denominator computation (all denominators share the same products, computable in `O(t)` total with one inversion via prefix/suffix products), reducing `O(t²)` to `O(t)`.
- Add a regression test asserting `ThresholdKeys::read` with `t = n = u16::MAX` either errors early or completes in bounded time.

### Proof of Concept
Source-level (execution not run):

```rust
// Serialize a ThresholdKeys blob with t = n = 65535, Interpolation::Lagrange
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(65535u16.to_le_bytes()); // t
buf.extend(65535u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes());     // i
buf.push(1);                        // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. 65535 {
  buf.extend(C::generator().to_bytes().as_ref()); // verification_shares
}
// Each call performs ~4.3e9 scalar multiplications + 65535 inversions
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```

The panic path is avoided (all included indexes distinct, `i=1` valid), so the full quadratic interpolation in `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) executes.
