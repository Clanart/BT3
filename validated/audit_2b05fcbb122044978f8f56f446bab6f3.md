### Title
Just-in-time deposit before `queueNewRewards` lets an attacker capture rewards with zero time-weighted exposure - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool._provisionReward` distributes newly queued rewards by instantly bumping `rewardPerTokenStored` based on the *current* `totalStaked()` snapshot, with no time-weighting of individual balances. Because `MasterMagpie._deposit` calls `rewarder.updateFor(_account)` (which sets `userRewardPerTokenPaid` to the value *before* the new balance is added) before increasing `user.amount`, an attacker can deposit immediately before a manager's `queueNewRewards` call, receive a full pro-rata share of the newly queued reward for that single block, then withdraw right afterward via `getReward`/`_harvestAndUnstake`.

### Finding Description
`_provisionReward` computes: [1](#0-0) 
It updates `rewardPerTokenStored` proportional to `_amountReward * 1e_dec / totalStaked()` at the moment `queueNewRewards`/`donateRewards` executes — a point-in-time snapshot with no accrual-duration accounting.

`earned()` then attributes reward strictly by current balance times the delta since the account's last checkpoint: [2](#0-1) 

In `MasterMagpie._deposit`, the checkpoint (`rewarder.updateFor`) happens *before* `user.amount` is incremented: [3](#0-2) 
This means the attacker's `userRewardPerTokenPaid` is pinned to the pre-reward `rewardPerTokenStored`, but their newly deposited balance is already counted in `totalStaked()` for the subsequent `_provisionReward` call, since `totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` directly (live balance), not a time-weighted supply: [4](#0-3) 

Exploit sequence within the same block (front-run the manager's pending `queueNewRewards` tx with a higher-gas deposit tx):
1. Attacker calls `MasterMagpie.deposit(stakingToken, amount)`. This checkpoints `userRewardPerTokenPaid[attacker] = rewardPerTokenStored` (pre-bump) and increases `totalStaked()`.
2. Manager's `queueNewRewards` executes, bumping `rewardPerTokenStored` based on the now-inflated `totalStaked()` (attacker's deposit counted).
3. Attacker calls `MasterMagpie.withdraw(...)`, which triggers `_harvestAndUnstake` → `_harvestBaseRewarder`/`_claimBaseRewarder` → `BaseRewardPool.getReward`, paying out `earned(attacker) = balanceOf(attacker) * (rewardPerTokenStored_new - rewardPerTokenStored_old) / 1e_dec`, a nonzero share of the reward despite zero holding duration before the reward event.

No existing guard prevents this: `nonReentrant`/`whenNotPaused` only protect against reentrancy/pausing, not against same-block deposit-before-reward timing; there is no minimum staking duration, cooldown, or time-weighted average balance mechanism in `BaseRewardPool` or `MasterMagpie`.

### Impact Explanation
This is a real economic loss: the attacker's captured share is directly taken from the reward pool that would otherwise be distributed pro-rata to genuine long-term stakers (since `rewardPerTokenStored` is a shared global accumulator, adding a deposit that has done nothing to earn the reward dilutes everyone else's `rewardPerToken` growth). This matches the "theft of unclaimed yield" / "direct theft of user funds" impact class from other stakers' perspective.

### Likelihood Explanation
- Requires no privileged role — any EOA holding `stakingToken` can perform this.
- Requires visibility into the manager's pending `queueNewRewards` transaction in the mempool and the ability to front-run it with higher gas (or simply be lucky enough to land in the same block before it) — a standard, well-understood MEV/front-running technique, feasible on any public mempool chain.
- Fully repeatable every time a manager queues new rewards, as long as staking token can be deposited/withdrawn freely (no cooldown enforced by `MasterMagpie`/`BaseRewardPool`).
- Capital requirement scales with desired share of stolen reward; larger deposit relative to `totalStaked()` yields a proportionally larger share of the reward, bounded only by available capital and slippage/withdrawal fees (none evident here).

### Recommendation
Introduce time-weighted reward accrual (e.g., checkpoint balances against elapsed time similar to a `rewardRate`/`lastUpdateTime` streaming model as in Synthetix `StakingRewards`), or require a minimum staking duration before a deposit is eligible for a given `queueNewRewards` distribution (e.g., snapshot eligible balances prior to accepting the deposit into the current reward epoch). At minimum, `_provisionReward` should distribute rewards over a future time window rather than instantaneously crediting `rewardPerTokenStored` based on the point-in-time `totalStaked()`, closing the front-run window entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (as via `MasterMagpie.createRewarder`), register pool with `add(...)`.
2. Long-term staker `alice` deposits `100e18` stakingToken and waits (mine several blocks) accruing 0 reward yet (no rewards queued).
3. Manager prepares to call `queueNewRewards(1000e18, rewardToken)` but transaction is pending.
4. In the *same block* (use `vm.roll`/single block simulate ordering), attacker `bob` calls `MasterMagpie.deposit(stakingToken, 100e18)` immediately before manager's `queueNewRewards` executes.
5. Manager's `queueNewRewards(1000e18, rewardToken)` executes, bumping `rewardPerTokenStored` based on `totalStaked() = 200e18` (alice + bob).
6. In the same block, `bob` calls `MasterMagpie.withdraw(stakingToken, 100e18)`, triggering `getReward` payout.
7. Assert: `bob`'s received `rewardToken` balance ≈ `500e18` (50% of `1000e18` reward) despite holding stake for 0 elapsed time, while `alice`, who staked for the entire accrual period, only earns the other 50% — proving the reward is not time-weighted and can be captured by a zero-duration JIT deposit.
