Confirmed: `ValidateAccountKey` in `blockchain/types/accountkey/account_key.go` calls `accKey.Validate(...)` directly with no bound on `len(recoveredKeys)`, and this is the exact function invoked by the `VALIDATE_SENDER` precompile in `blockchain/vm/contracts.go`, bypassing the `SigValidationGas` / `MaxNumKeysForMultiSig` check that protects the normal transaction-validation path.

### Title
Unbounded signature count in VALIDATE_SENDER precompile bypasses MaxNumKeysForMultiSig, allowing gas-mismetered CPU/memory DoS - (File: blockchain/vm/contracts.go)

### Summary
The `VALIDATE_SENDER` precompiled contract accepts an arbitrary-length signature blob and derives `numSigs = len(input) / common.SignatureLength` with no upper bound, then loops calling `crypto.Ecrecover` for every signature and passes all recovered keys to `accountkey.ValidateAccountKey` → `AccountKeyWeightedMultiSig.Validate`, which itself loops over all supplied signatures and does an RLP-encode + map lookup per signature. Unlike the ordinary transaction sender/fee-payer validation path (`Transaction.ValidateSender`/`ValidateFeePayer`), which calls `AccountKey.SigValidationGas` first and rejects any account key with more than `MaxNumKeysForMultiSig` (10) keys before ever calling `Validate`, this precompile calls `ValidateAccountKey` unconditionally with no cap on `numSigs`.

### Finding Description
- `blockchain/vm/contracts.go` `validateSender.GetRequiredGasAndComputationCost` computes cost as `numSigs*params.ValidateSenderGas` / `numSigs*params.ValidateSenderPerSigComputationCost+Base`, i.e. proportional, but the underlying `Ecrecover` + RLP-encode-per-signature validation work is O(numSigs) with real elliptic-curve cryptography (`crypto/signature_nocgo.go` `Ecrecover`) — a much heavier per-unit cost than typical opcode gas pricing was calibrated for. [1](#0-0) 
- The `Run`/`validateSender` function loops `numSigs` times performing `crypto.Ecrecover` and `crypto.UnmarshalPubkey`, with `numSigs` bounded only by `len(ptr)/common.SignatureLength`, i.e. by the raw EVM call-data size (up to `MaxTxDataSize` for the outer tx, or larger if invoked via internal call from contract memory built at runtime rather than calldata directly). [2](#0-1) 
- The recovered keys are passed straight to `accountkey.ValidateAccountKey`, which has no length check at all. [3](#0-2) 
- For `AccountKeyWeightedMultiSig`, `Validate()` itself loops over every recovered key and RLP-encodes it into a map with a comment explicitly flagging poor performance ("TODO-Kaia: find another way for better performance"), and only checks `len(recoveredKeys) > len(a.Keys)` when `isIstanbul` is true — this rejects oversized input on Istanbul networks, but the RLP-encode-and-map-insert work for every entry in `recoveredKeys` happens before that check is reached for `numberOfValidAndUniqueSigs`/threshold logic, and the `Ecrecover` cost (the dominant cost) is already incurred by the precompile before `Validate` is even called. [4](#0-3) 
- In contrast, the legitimate transaction-signing path enforces the `MaxNumKeysForMultiSig` cap up front via `SigValidationGas`, before `ValidateAccountKey`/`Validate` is ever invoked: [5](#0-4) [6](#0-5) 

This is directly analogous to the Django formset bug: a "count" parameter (`max_num`/`numSigs`) that should be capped is instead used to size expensive per-item work (constructing many forms / recovering many ECDSA signatures) before the intended limit check is applied, letting a caller bypass the intended resource ceiling (`MaxNumKeysForMultiSig`=10) via a code path that doesn't enforce it.

### Impact Explanation
Any account (contract deployer or transaction sender) can call the `VALIDATE_SENDER` precompile from a smart contract with a large `input` buffer built in memory (not limited to calldata size — an attacker can construct arbitrarily large byte arrays in EVM memory, e.g. via `MSTORE` in a loop, subject only to gas for memory expansion and the precompile's own linear gas cost) to force the node to perform far more `Ecrecover` operations and per-signature account-key checks than a legitimately-capped multisig account (max 10 keys) would ever need. This creates a real EVM-block-processing cost multiplier per unit gas paid, disproportionate to intended design (`MaxNumKeysForMultiSig=10`), which can be used to slow down/degrade block processing/validation (a computation-cost metering bypass / DoS-style resource abuse), impacting all nodes that must re-execute the block. This aligns with the "EVM and computation-cost metering" and "state transition and gas/burn accounting" in-scope categories.

### Likelihood Explanation
High reachability: `VALIDATE_SENDER` is a standard, callable precompile reachable from any contract call by any unprivileged transaction sender — no special privileges are required, only gas to pay for the call. The only mitigating factor is that the caller still pays `numSigs * ValidateSenderGas`, so this is not "free" computation, but the disproportion between metered gas and actual cryptographic + validation work (per-signature Ecrecover, RLP encode+map insert per key) is the core of the bug class, exactly mirroring the Django advisory's characterization ("resource limits... bypass").

### Recommendation
Enforce an explicit upper bound (e.g. `accountkey.MaxNumKeysForMultiSig`) on `numSigs` inside `validateSender.validateSender` (and generally within `accountkey.ValidateAccountKey`/`AccountKeyWeightedMultiSig.Validate`) before performing any `Ecrecover` or per-signature loop work, returning an error immediately if exceeded — mirroring the check already performed by `SigValidationGas` for ordinary transactions. Additionally, recalibrate `ValidateSenderPerSigComputationCost`/`ValidateSenderGas` to reflect realistic worst-case Ecrecover + RLP + map-insertion cost per signature.

### Proof of Concept
1. Deploy a contract that builds a large `bytes` buffer in memory consisting of `N` (e.g., several hundred or thousand) 65-byte signature-shaped chunks (values don't need to be valid signatures, just correctly-sized so `Ecrecover` is attempted; even failing recoveries still consume CPU inside `crypto.Ecrecover`/`sigToPub`).
2. Concatenate `from(20 bytes) || msg(32 bytes) || N*signature(65 bytes each)` and `staticcall`/`call` the `VALIDATE_SENDER` precompile address with that input.
3. Observe that `validateSender.validateSender` (`blockchain/vm/contracts.go:879-916`) loops `N` times performing `crypto.Ecrecover`, and if `from`'s account key is `AccountKeyWeightedMultiSig`, `Validate` (`blockchain/types/accountkey/account_key_weighted_multi_sig.go:86-127`) further loops over all `N` recovered keys doing RLP encode + map operations — with no cap comparable to `MaxNumKeysForMultiSig=10` enforced anywhere in this call path, unlike the ordinary `ValidateSender`/`ValidateFeePayer` tx-signing path which rejects `numKeys > MaxNumKeysForMultiSig` via `SigValidationGas` before any `Validate` call.

func (c *validateSender) validateSender(input []byte, picker types.AccountKeyPicker, currentBlockNumber uint64) error {
	ptr := input

	// Parse the first 20 bytes. They represent an address to be verified.
	if len(ptr) < common.AddressLength {
		return errInputTooShort
	}
	from := common.BytesToAddress(input[0:common.AddressLength])
	ptr = ptr[common.AddressLength:]

	// Parse the next 32 bytes. They represent a message which was used to generate signatures.
	if len(ptr) < common.HashLength {
		return errInputTooShort
	}
	msg := ptr[0:common.HashLength]
	ptr = ptr[common.HashLength:]

	// Parse remaining bytes. The length should be divided by common.SignatureLength.
	if len(ptr)%common.SignatureLength != 0 {
		return errWrongSignatureLength
	}

	numSigs := len(ptr) / common.SignatureLength
	if numSigs == 0 {
		return errNoSignatures
	}
	pubs := make([]*ecdsa.PublicKey, numSigs)
	for i := range numSigs {
		p, err := crypto.Ecrecover(msg, ptr[0:common.SignatureLength])
		if err != nil {
			return err
		}
		pubs[i], err = crypto.UnmarshalPubkey(p)
		if err != nil {
			return err
		}
		ptr = ptr[common.SignatureLength:]
	}

	if a.Threshold == 0 {
		return false
	}
	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul

	// Validation 1. if isIstanbul is true, check whether the signature number exceeds key number
	if isIstanbul && len(recoveredKeys) > len(a.Keys) {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and number of signatures exceeds key number",
			"numSigs", len(recoveredKeys), "numKeys", len(a.Keys))
		return false
	}

	numberOfValidAndUniqueSigs := 0
	weightedSum := uint(0)

	// To prohibit making a signature with the same key, make a map.
	// TODO-Kaia: find another way for better performance
	pMap := make(map[string]*ecdsa.PublicKey)
	for _, bk := range recoveredKeys {
		b, err := rlp.EncodeToBytes((*PublicKeySerializable)(bk))
		if err != nil {
			logger.Warn("Failed to encode recovered public keys of the tx", "recoveredKeys", recoveredKeys)
			continue
		}
		pMap[string(b)] = bk
	}

	for _, k := range a.Keys {
		b, err := rlp.EncodeToBytes(k.Key)
		if err != nil {
			logger.Warn("Failed to encode public keys in the account", "AccountKey", a.String())
			continue
		}

		// if the registered key is included in one of the transaction signatures,
		// update weightedSum and validSigNum
		if _, ok := pMap[string(b)]; ok {
			weightedSum += k.Weight
			numberOfValidAndUniqueSigs++
		}
	}

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
