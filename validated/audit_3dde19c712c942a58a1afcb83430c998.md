### Title
ThresholdKeys deserialization accepts internally inconsistent key material, enabling attacker-defined group keys / unspendable-fund views - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation method, a `secret_share`, and `n` `verification_shares` purely from the input byte stream, then passes them to `ThresholdKeys::new`. `ThresholdKeys::new` only checks that the share map has exactly `n` entries and that indices are in-range — it never verifies that:

1. `secret_share` is non-zero.
2. `verification_shares[i]` actually equals `G * secret_share` (or any polynomial-consistent value).
3. The `verification_shares` points are non-identity — `read` uses `Ciphersuite::read_G`, which accepts identity points, not the identity-rejecting `Curve::read_G` used elsewhere in FROST. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description

The analogous bug class to CVE-2023-36177 (crafted request input trusted without validation, yielding unintended privileged behavior) maps onto untrusted-byte deserialization: a crafted `ThresholdKeys` blob is accepted verbatim. Because `group_key` is *computed* from the attacker-supplied `verification_shares` (`t.iter().map(|i| verification_shares[i] * interpolation_factor)`), an attacker fully controls the resulting `group_key()` while the holder's `secret_share` field is whatever the attacker chose.

Two concrete variants:

- **Identity verification shares**: supply all `verification_shares` as identity encodings (accepted by `Ciphersuite::read_G`, which only checks canonical encoding). `group_key` becomes identity; after `offset`, `group_key() = offset * G`, an attacker-known discrete log. Any downstream consumer (e.g., `read_keys`/`save_keys` in `processor/src/key_gen.rs`, which keys the DB by `group_key().to_bytes()`) treats a key whose discrete log the attacker knows as a valid group key.
- **Mismatched secret/verification shares**: supply `secret_share = s` (attacker-known) and `verification_shares[i] = G * s` for the victim's own index, with other shares attacker-chosen. `view()`/`sign()` will happily produce signature shares; the interpolated public key is attacker-defined, so the resulting signatures validate under an attacker-controlled group key rather than the group's real key.

There is also no marker/version binding the serialized keys to the DKG session/context that produced them — only a curve `C::ID` check — so blobs are freely interchangeable across sessions. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation

- An attacker who can feed crafted bytes into `ThresholdKeys::read` (key import/recovery path, a listed in-scope sink) causes the victim to adopt an attacker-known group key. Deposits attributed to `group_key()` are spendable by the attacker — "funds reported received that are not spendable" (by the group) in inverse form, and signatures get produced for a key the victim never agreed to.
- Identity verification shares additionally subvert `share_verification_statements`-style checks downstream, since `identity * λ` contributes nothing yet occupies a participant slot.

### Likelihood Explanation

Reachability depends on an integrator passing untrusted/restored bytes to `ThresholdKeys::read` (key backup/restore, coordinator-provided key packages). Within the crate itself the function performs zero provenance checks, so any such path is exploitable with trivially constructed bytes — no cryptographic break needed, just a structurally valid encoding.

### Recommendation

- In `ThresholdKeys::read` (or `ThresholdKeys::new`), reject `secret_share == 0` and identity `verification_shares` (use an identity-rejecting point read or explicit `is_identity` checks).
- Verify `verification_shares[params.i()] == C::generator() * secret_share` on deserialize, and for `Interpolation::Lagrange` consider spot-checking share consistency.
- Bind serialized keys to a session/context identifier so blobs can't be transplanted between DKG sessions.

### Proof of Concept

```rust
// Attacker crafts a blob for ThresholdKeys::<Ristretto>::read
let x = Scalar::random(OsRng);              // attacker-known "secret"
let mut buf = vec![];
buf.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(2u16.to_le_bytes());             // t = 2
buf.extend(3u16.to_le_bytes());             // n = 3
buf.extend(1u16.to_le_bytes());             // i = 1
buf.push(1);                                // Interpolation::Lagrange
buf.extend(x.to_repr().as_ref());           // attacker-known secret_share
// verification shares: identity accepted via Ciphersuite::read_G
buf.extend(Ristretto::generator().to_bytes());            // share for i=1 (could also be G*x)
buf.extend(EdwardsPoint::identity().compress().to_bytes()); // identity accepted
buf.extend(EdwardsPoint::identity().compress().to_bytes());

let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
// keys.group_key() is attacker-derived (identity contributions + attacker share);
// keys.original_secret_share() == x, known to the attacker.
```

Note: I verified `read`'s missing checks and the identity-accepting `Ciphersuite::read_G` path directly; I did not trace every upstream caller of `ThresholdKeys::read` in the in-scope crates, so the concrete injection path relies on the scan's premise that this sink receives untrusted bytes. If no such path exists in production, this reduces to a defense-in-depth gap rather than a live vulnerability.
