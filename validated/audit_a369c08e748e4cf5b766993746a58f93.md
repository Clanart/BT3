### Title
Reward calculation uses only the current `cost_per_block`, ignoring historical rate changes across the unpaid block span - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::calculate_reward` prices an entire unpaid height span (`latest_height - LastRewardedHeight` watermark) using a single, currently-configured `StateMachinesCostPerBlock` value. If governance updates `cost_per_block` while an unpaid span is outstanding, the whole span — including blocks that accrued before the rate change — gets priced at the *new* rate, not a blended rate reflecting when each block was actually finalized. This is the direct analog of the `HychainNodeKey.getPriceForQuantity` bug: a calculation that spans multiple "tiers" (here, time-varying reward rates) only looks at the endpoints/latest value and ignores the in-between rate regime.

### Finding Description
`calculate_reward` in [1](#0-0)  computes:

```
let blocks = latest_height - baseline;   // baseline = LastRewardedHeight watermark
reward = blocks * block_cost;            // block_cost = StateMachinesCostPerBlock::get() — read fresh, current value only
```

`block_cost` is read once, at call time, from `StateMachinesCostPerBlock::<T>::get(state_machine_id)` [2](#0-1) . There is no per-block or per-epoch price history — `update_cost_per_block` simply overwrites the map entry in place [3](#0-2) . The watermark `LastRewardedHeight` only tracks *how many* blocks are unpaid, not *what rate applied* to each sub-range of that span [4](#0-3) .

This mirrors the reported bug precisely: `getPriceForQuantity` only samples the price at the start and end of a quantity range and applies the wrong (endpoint) price to units that should have fallen under an intermediate tier. Here, the "tiers" are the successive values of `cost_per_block` over time, and the "quantity" is the block span `latest_height - baseline`. Only the *current* value is applied to the whole span — worse than the original bug in that it doesn't even use a start/end blend, just whatever the current rate is at claim time.

Because the reward-eligible span can be arbitrarily large (nothing forces frequent, small consensus updates — a relayer/prover simply calls `handle_unsigned` with a `ConsensusMessage` whose signer is recovered from an sr25519 signature over the proof [5](#0-4) ), the size of the mispriced span is fully controllable by whoever submits the update.

### Impact Explanation
This falls under "logic attacks" / "stealing or loss of funds" against the treasury:
- If governance raises `cost_per_block` (e.g., due to increased infrastructure cost for a state machine), any account able to submit a valid consensus proof for that chain can wait until *after* the increase to submit the update, and collect the new, higher rate for the entire unpaid span, including all the older, cheaper blocks. This directly overpays from `TreasuryAccount` [6](#0-5) .
- Conversely, if governance lowers the rate, the pallet underpays for blocks that occurred while the higher rate was in effect (loss for the honest relayer, no protocol harm but demonstrates the same fundamental correctness bug).
- The overpayment case is a genuine drain-the-treasury vector: the "profit" scales with the size of the accumulated unpaid span times the rate delta, and is fully controllable by the submitter's timing.

### Likelihood Explanation
Medium. This requires (a) governance to change `cost_per_block` for a state machine at some point (a normal, expected operational action per the pallet's documented purpose), and (b) a span of unrewarded blocks to exist across that change — which happens naturally any time consensus updates aren't submitted on every single block, or if a relayer intentionally delays submission around a scheduled parameter change. No malicious relayer/prover assumption is needed beyond ordinary economically-rational timing of a normal, permissionless action (constructing and submitting a `ConsensusMessage` with a valid signature over a real proof).

### Recommendation
Track cost-per-block changes with an effective height/timestamp (a small history list or an epoch-keyed schedule), and when computing a reward for span `[baseline, latest_height]`, sum `Σ (rate_i * blocks_in_epoch_i)` across all rate regimes that overlap the span, rather than applying only the currently active rate to the whole span. Alternatively, force `LastRewardedHeight` to be flushed against the current rate whenever `update_cost_per_block` is called (i.e., snapshot/settle all pending spans at the old rate before allowing the rate to change), so no span is ever priced under a rate that wasn't in effect when its blocks were produced.

### Proof of Concept
1. Governance sets `cost_per_block = 100` for `state_machine_id`.
2. Chain advances consensus commitments up to height 1000 with no consensus-incentive claim submitted (`LastRewardedHeight` stays at, say, 500 — 500 blocks unpaid).
3. Governance increases `cost_per_block` to `10_000` (e.g., due to rising infra cost).
4. Any account with a valid sr25519 keypair constructs a `ConsensusMessage` with a signature over a legitimate consensus proof for that state machine and submits it via `pallet_ismp::Pallet::handle_unsigned`.
5. `on_executed` → `process_message` → `calculate_reward` computes `blocks = 1000 - 500 = 500`, `reward = 500 * 10_000 = 5_000_000`, transferring that full amount from `TreasuryAccount` to the submitter's account, even though only the most recent portion of those 500 blocks (if any) occurred after the rate increase; the first 500 blocks should have been paid at the old `100`/block rate (`50_000` total) had a claim been made before the rate change.

This produces an overpayment of `500 * (10_000 - 100) = 4_950_000` extracted from the treasury purely by timing the claim after the rate increase — directly analogous to the original report's demonstrated price discrepancy from ignoring in-between pricing tiers (`400156250000000000000` vs the correct `347992250000000000000`).

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}
