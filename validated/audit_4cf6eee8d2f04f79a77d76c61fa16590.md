### Title
Unchecked output-value arithmetic permits signing a consensus-invalid Bitcoin transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary

`SignableTransaction::new` sums attacker-controlled payment amounts and adds the estimated fee using unchecked `u64` arithmetic. With optimized-build wrapping arithmetic, a single payment of `u64::MAX` can make `payment_sat + needed_fee` wrap to a small value, bypassing the insufficient-funds check and producing a transaction whose output exceeds both the input amount and Bitcoin's maximum money supply. [1](#0-0) 

### Finding Description

Payments are only checked against the dust lower bound; there is no maximum-money or per-payment upper bound. [2](#0-1) 

The total payment amount is calculated with `sum::<u64>()`, and the funding check evaluates `input_sat < (payment_sat + needed_fee)` without `checked_add` or `checked_sub`. [1](#0-0) 

For example, with an input worth `1_000` sats, one payment of `u64::MAX`, and an estimated fee of approximately `110` sats, `payment_sat + needed_fee` wraps to approximately `109`. The check then incorrectly concludes that `1_000` sats are sufficient. [3](#0-2) 

The constructor nevertheless stores the oversized `TxOut` and returns a `SignableTransaction`. [4](#0-3) [5](#0-4) 

That transaction can proceed to per-input FROST signature generation and Taproot sighash signing. [6](#0-5) [7](#0-6) 

### Impact Explanation

An attacker who can supply transaction outputs or payment data for signing can cause the threshold wallet to produce a fully signed transaction that Bitcoin consensus necessarily rejects. The signature is valid for the malformed sighash, but the transaction is not spendable or broadcastable because its output value exceeds its inputs and the allowable monetary range.

This satisfies the unintended-message-signing condition: the signer authorizes a transaction shape that the funding policy was intended to reject. In builds with overflow checks enabled, the same input instead causes an arithmetic panic; the exploitable wrapping behavior applies to optimized builds without `overflow-checks`.

### Likelihood Explanation

The trigger requires control over the payment amount and access to a transaction-signing path, which is within the permitted public-input model. The malformed request is a single payment with value `u64::MAX` and one otherwise valid spendable input.

The result depends on the build's arithmetic behavior: release builds normally wrap unless `overflow-checks` is enabled, while checked builds panic at the addition.

### Recommendation

Use checked arithmetic for all monetary aggregation and fee calculations:

- Accumulate `input_sat`, `payment_sat`, and output totals with `checked_add`.
- Calculate `payment_sat + needed_fee` with `checked_add`.
- Reject arithmetic overflow as `TransactionError::NotEnoughFunds` or a new invalid-amount variant.
- Reject individual payments and total outputs greater than Bitcoin's maximum valid money amount.
- Add regression tests for `u64::MAX`, sums near `u64::MAX`, and `input_sat` near `u64::MAX`.

### Proof of Concept

```rust
// input: a valid ReceivedOutput worth 1_000 sats
// attacker_script: any valid payment script
let payment = (attacker_script, u64::MAX);

let signable = SignableTransaction::new(
    vec![input],
    &[payment],
    None,
    None,
    1,
).unwrap();

// The funding check passed because:
// u64::MAX + needed_fee wrapped to needed_fee - 1.
assert_eq!(signable.transaction().output[0].value.to_sat(), u64::MAX);
```

Conceptually, if `needed_fee == 110`, then:

```text
u64::MAX + 110 ≡ 109 (mod 2^64)
input_sat = 1_000
1_000 < 109 == false
```

The insufficient-funds branch is skipped, after which `multisig` and `sign` can produce Taproot signatures for this consensus-invalid transaction.
