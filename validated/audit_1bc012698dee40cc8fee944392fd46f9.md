### Title
Unchecked ERC20 return value in escrow release lets a non-standard input token silently steal solver payouts — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order-input tokens using a raw low-level `.call` to the ERC20 `transfer` selector and only checks that the *call itself* did not revert (`success`), never decoding/validating the returned `bool`. This is the same bug class as the external report (non-standard token return-value handling breaking transfer accounting), but manifests as the opposite failure mode: instead of reverting on tokens with no return value, the contract now silently accepts tokens whose `transfer()` returns `false` on failure without reverting, marks the order settled, and never actually delivers funds.

### Finding Description
`withdraw()` (internal, reached via `onAccept` for `RedeemEscrow`/`RefundEscrow` and via `onGetResponse` for cancellations) releases escrowed input tokens like this: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

`success` only reflects whether the external call reverted — it says nothing about the ABI-decoded boolean many ERC20 tokens return to signal a *logical* failure without reverting (e.g. `return false;` instead of `revert`). The same unchecked pattern is used for `SweepDust` payouts and fee-token payouts in the same file: [2](#0-1) [3](#0-2) 

Critically, `order.inputs[].token` is attacker-controlled — any user placing an order chooses the input token address, and the file's own `placeOrder`/escrow path elsewhere correctly uses `SafeERC20.safeTransferFrom` for *inbound* transfers: [4](#0-3) 

But the *outbound* release path (`withdraw`) deliberately bypasses `SafeERC20` (imported and aliased via `using SafeERC20 for IERC20;` at the top of the file) and uses the raw-call pattern instead: [5](#0-4) 

An order creator can therefore escrow a custom malicious ERC20 as an input token (this passes fine through `safeTransferFrom` on deposit — the token can behave standard-compliantly on `transferFrom` while later returning `false` on `transfer` to a specific caller/beneficiary). A solver fills the order on the destination chain (delivering real output value), triggering the `RedeemEscrow` message back to the source chain. When `withdraw()` runs, the malicious token's `transfer()` call succeeds (no revert) but returns `false`; `success` is `true` so the `revert TransferFailed()` guard never fires. The function proceeds to:
- decrement `_orders[commitment][token]`,
- mark `_filled[commitment] = beneficiary`,
- emit `EscrowReleased`,

— all while the solver receives **zero** tokens. The order is now permanently marked filled/finalized, so there is no retry path: the solver has delivered real output on the destination chain but the source-chain reward is silently lost.

### Impact Explanation
This is a direct loss-of-funds primitive for solvers/fillers (the "rightful beneficiary" of escrow release never receives the amount, yet accounting treats the transfer as completed exactly once). It also affects `RefundEscrow` cancellations against the order owner and the transaction-fee payout to the beneficiary, using the identical unchecked pattern. Because settlement state (`_filled`, `_orders`) is updated unconditionally on `success` rather than on verified token receipt, this produces a false "settlement accepted" state divorced from actual asset movement — squarely inside the bounty's "stealing or loss of funds" / "false state acceptance" / "logic attacks" categories, and requires no relayer, prover, or admin compromise: only an ordinary user placing an order with a token they control.

### Likelihood Explanation
Reachable by any unprivileged user placing an order (`placeOrder`) with an arbitrary ERC20 they deploy as the input token — no special privileges, front-running, or malicious infrastructure roles needed. The only precondition is a solver filling the order without pre-validating the exact byte-for-byte behavior of the input token's `transfer()` function under all call contexts, which is realistic since tokens can behave correctly during quoting/simulation and only defect at settlement time (e.g., based on `msg.sender`, block number, or a toggle the attacker controls).

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` release path in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, the `SweepDust` handler, and the fee payout) with `IERC20(token).safeTransfer(...)`, consistent with the `safeTransferFrom` already used on the inbound/escrow side and with the mainline EVM `IntentGatewayV2.sol`/`IntentsBase.sol` (`_withdraw`, using `safeTransfer`). `SafeERC20` is already imported and aliased in this file, so this is a drop-in fix. Additionally consider a balance-delta check before finalizing state (mark `_filled`/decrement `_orders` only after confirming the beneficiary's balance increased by `amount`) to defend against tokens with fee-on-transfer or otherwise nonstandard accounting.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` returns `false` (without reverting) whenever called by the `IntentGatewayV2` contract address to the intended beneficiary, but behaves as a normal ERC20 for `transferFrom` during order placement.
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2`, escrowing `EvilToken` as `order.inputs[0]`; `safeTransferFrom` succeeds normally at `evm/tron/contracts/apps/IntentGatewayV2.sol:398-400`.
3. A solver observes a normal-looking order, fills it on the destination chain, delivering real output assets to the order beneficiary, and the cross-chain `RedeemEscrow` message is dispatched back to source.
4. On `onAccept`, `withdraw()` runs: `token.call(...transfer(solver, amount)...)` returns `(true, abi.encode(false))`; only `success` (the outer boolean) is checked, so no revert occurs — `evm/tron/contracts/apps/IntentGatewayV2.sol:696-699`.
5. `_orders[commitment][token]` is decremented, `_filled[commitment] = solver` is set, `EscrowReleased` is emitted — but `EvilToken.balanceOf(solver)` never increased.
6. The solver has delivered real value on the destination chain and receives nothing on the source chain, with no path to reclaim it since the order is already marked filled.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
