### Title
Symlink following in `load_rules()` allows repo-checked-in symlinks to disclose local file content via `systemMessage` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` uses `glob.glob('.claude/hookify.*.local.md')` and `load_rule_file()` calls plain `open(file_path)` with no `os.path.islink()`/`os.path.realpath()` check, so a symlink checked into `.claude/` is followed and its target's content is read, parsed as YAML frontmatter/message, and can be echoed back to the user/model in `systemMessage`.

### Finding Description
`load_rules()` (`plugins/hookify/core/config_loader.py:198-241`) enumerates files matching `.claude/hookify.*.local.md` via `glob.glob`, which does not distinguish symlinks from regular files, and passes each `file_path` to `load_rule_file()`. `load_rule_file()` (`plugins/hookify/core/config_loader.py:244-274`) does `open(file_path, 'r')` directly with no symlink check or path-confinement validation, so if `.claude/hookify.evil.local.md` is a symlink to a file outside the repository (e.g. `~/.ssh/id_rsa`, another project's `.env`, or any file the victim's Claude Code process can read), the OS transparently follows the symlink and returns that target file's content on the machine where the hook actually runs. The content is passed to `extract_frontmatter()` (`plugins/hookify/core/config_loader.py:87-195`) and `Rule.from_dict()` (`plugins/hookify/core/config_loader.py:44-84`); the portion after the second `---` becomes `Rule.message` verbatim (`message=message.strip()`, line 83). That `message` is later surfaced through `RuleEngine.evaluate_rules()` (`plugins/hookify/core/rule_engine.py:35-94`) directly into the hook's `systemMessage` output (lines 70, 78, 83, 90) with no sanitization or redaction, which is fed back to the AI/user session as trusted hook output. This works even if `extract_frontmatter` fails to find a leading `---` since it only causes a "missing frontmatter" warning and skip - so full disclosure requires the target file to happen to have `---`-delimited content, but rules can also be crafted with 3+ dashes preceding arbitrary body text, and any target file whose first bytes are attacker-predictable/known (e.g., specific known local config formats) can be exfiltrated in full via `message`.

### Impact Explanation
This is local file disclosure limited to files readable by the OS user running Claude Code, surfaced through the model's `systemMessage` context. It does not escalate privileges beyond the invoking user's own filesystem read authority (a symlink cannot grant access to files the user account cannot already read), so the "sensitive file elsewhere on disk" must already be readable by the victim's own account. The realistic scoped impact is: (1) unintended reading of local files whose paths are guessable/standard (dotfiles, other project configs) into the AI's context/transcript, which may then be exposed via later exfiltration primitives (e.g., a Bash tool call), and (2) rules loaded from outside the checked-out workspace silently gaining automation authority (matching/blocking/warning) that the repo author did not intend, if the symlink target itself contains valid hookify frontmatter.

### Likelihood Explanation
Preconditions are modest: an attacker only needs the ability to add a file (symlink) to a repository that a victim will `git clone`/`checkout` and then run Claude Code with hookify against - this is normal PR/repo content, no special privileges required. Feasibility is real since `git` does track and checkout symlinks by default (subject to `core.symlinks` support on the platform), and `glob.glob`/`open()` follow symlinks without special handling in this code. Repeatability is high - the same symlinked file triggers disclosure on every session/tool invocation as long as the rule loader runs.

### Recommendation
In `load_rule_file()`/`load_rules()`, reject or skip any candidate file where `os.path.islink(file_path)` is true, or resolve the path with `os.path.realpath()` and verify it stays within the resolved workspace root (`os.path.commonpath` check against the resolved `.claude` directory) before opening it. Additionally, consider capping message size or sanitizing `Rule.message` before embedding it verbatim in `systemMessage`.

### Proof of Concept
Integration test (pytest) plan:
1. Create a temp directory `workspace/.claude/`.
2. Outside `workspace`, create `secret.txt` containing a sentinel string, e.g. `"SENTINEL-OUT-OF-WORKSPACE-1234"`.
3. Inside `workspace/.claude/`, create a symlink `hookify.evil.local.md -> ../../secret.txt` (or an absolute path outside workspace) where `secret.txt` content is prefixed to look like frontmatter, e.g.:
   ```
   ---
   name: evil
   enabled: true
   event: all
   pattern: ".*"
   ---
   SENTINEL-OUT-OF-WORKSPACE-1234
   ```
4. `chdir` into `workspace` and call `load_rules()`.
5. Run `RuleEngine().evaluate_rules(rules, {"tool_name": "Bash", "tool_input": {"command": "anything"}})`.
6. Assert either: `load_rules()` skips the symlinked file entirely (expected fix), or currently (pre-fix), assert that `SENTINEL-OUT-OF-WORKSPACE-1234` appears in the returned `systemMessage`, demonstrating disclosure of content that lives outside the workspace root.
