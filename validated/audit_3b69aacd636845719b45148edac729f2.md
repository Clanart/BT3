### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` allows remote stack-overflow DoS via a single crafted transaction - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key by calling `rlp.DecodeBytes` on a nested `AccountKeySerializer`, which in turn can decode another `AccountKeyRoleBased`. There is no depth limit enforced during decoding; the "no nested composite key" rule (`ErrNestedCompositeType`) is only checked *after* decoding completes, in `CheckInstallable`/`CheckUpdatable`. This mirrors the uncontrolled-recursion bug class in `trust-dns-proto` (CVE-2018-20994/GHSA-369h-pjr2-6wrh), where recursive parsing of attacker-controlled, self-referential structures with no depth cap could exhaust the call stack and crash the process.

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes the key type, then dispatches to the concrete key's `DecodeRLP`: [1](#0-0) 

For `AccountKeyRoleBased`, `DecodeRLP` decodes an outer list of raw byte strings, and for **each element** calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which recurses back into `AccountKeySerializer.DecodeRLP` — and can again resolve to `AccountKeyRoleBased`, repeating the cycle: [2](#0-1) 

The only defense against nested `RoleBased` keys is `IsCompositeType()` checked in `CheckInstallable`/`CheckUpdatable`: [3](#0-2) 

Crucially, that check runs **after** the key has already been fully RLP-decoded (i.e., after the recursive parsing already happened). Decoding itself has no recursion/depth guard.

This decode path is reached directly from transaction decoding for `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate*`: [4](#0-3) [5](#0-4) 

which is invoked from generic transaction RLP decoding: [6](#0-5) 

which is reachable from the public RPC entry point that any unauthenticated caller can hit: [7](#0-6) 

Critically, the transaction size limit (`MaxTxDataSize`, 128KB) is enforced only inside `TxPool.validateTx`, which runs **after** `rlp.DecodeBytes(encodedTx, tx)` has already fully parsed (and recursed through) the transaction in `SendRawTransaction`: [8](#0-7) [9](#0-8) 

Because each nesting level of `AccountKeyRoleBased` only costs a handful of RLP-overhead bytes (key-type tag + short list/string headers), an attacker can pack many thousands of nesting levels into a payload bounded only by the JSON-RPC transport's request-size limit (not by `MaxTxDataSize`, since that check hasn't run yet). Each level of nesting adds multiple Go call frames (`AccountKeySerializer.DecodeRLP` → `rlp.Stream.Decode` → reflect-based decoder → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → ...), so sufficient nesting drives the goroutine stack toward Go's runtime stack limit, producing a fatal, unrecoverable `runtime: goroutine stack exceeds ... stack overflow` crash of the entire node process — analogous to the trust-dns compression-pointer recursion crash.

### Impact Explanation
A successful attack crashes the Kaia node process handling the RPC request (fatal Go runtime error, not a panic that can be recovered) purely from RLP-decoding a submitted transaction, without needing to pay gas, get the transaction into a block, or have a valid signature — the crash occurs during unmarshaling before any balance/signature/pool checks execute. If this endpoint is exposed on a full/consensus node's RPC or is relayed to peers/validators via `SendTx`, this is a remote, low-cost denial-of-service vector against public RPC nodes reachable by any unprivileged caller.

### Likelihood Explanation
High reachability: the only entry point required is a single `kaia_sendRawTransaction`/`sendRawTransaction` (or `SendRawTransactions`) call with a crafted `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate` payload — no authentication, no balance, no valid signature verification needed before the vulnerable decode executes. The severity of the resulting crash (whether it actually exceeds Go's growable-stack ceiling) depends on the effective maximum RLP payload size accepted by the JSON-RPC transport (`MaxRequestContentLength` in `networks/rpc/http.go`) and per-level recursion overhead, both of which I could not fully quantify with available tools — this is the primary source of remaining uncertainty in confirming actual stack exhaustion versus "merely" high CPU/memory consumption. I was not able to find an explicit depth-limit configuration; if the RPC content-length limit is large (multi-MB, as typically configured in Ethereum-derived nodes), the achievable nesting depth is very likely sufficient to trigger the crash.

### Recommendation
- Enforce `MaxTxDataSize` (or an early raw-size sanity check) *before* `rlp.DecodeBytes` is invoked on attacker-supplied transaction bytes in `SendRawTransaction`/`SendRawTransactions`.
- Add an explicit recursion-depth counter/limit to `rlp.Stream` (or thread a depth parameter through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP`) so that nested composite-key structures are rejected during decode, not only after decode completes via `IsCompositeType()`.
- Alternatively, disallow decoding a `RoleBased` key type from within `AccountKeySerializer.DecodeRLP` when already inside a nested decode context (mirrors the existing but too-late `ErrNestedCompositeType` check).

### Proof of Concept
1. Construct account key value `K0 = AccountKeyLegacy` (or any non-composite key).
2. Build `K1 = AccountKeyRoleBased{K0}` (a role-based key with a single role), RLP-encode via `AccountKeySerializer`.
3. Repeat: `K_{i+1} = AccountKeyRoleBased{K_i}` for i = 1..N, re-encoding at each step (each level adds only a few bytes of RLP overhead).
4. Continue until the total encoded size approaches the JSON-RPC transport's accepted request size (bounded by `MaxRequestContentLength`, not by the (not-yet-enforced) 128KB `MaxTxDataSize`).
5. Wrap `K_N` as the `Key` field of a `TxTypeAccountUpdate` transaction (nonce/gas fields can be arbitrary/invalid since decode happens before validation), RLP-encode the full transaction, and submit it via `kaia_sendRawTransaction`.
6. On the receiving node, `Transaction.DecodeRLP` → `TxInternalDataAccountUpdate.fromSerializable` → `AccountKeySerializer.DecodeRLP` recurses N times through `AccountKeyRoleBased.DecodeRLP`/`rlp.DecodeBytes`, driving the goroutine call stack toward the Go runtime's maximum stack size and crashing the process with a fatal "stack overflow" runtime error before any pool/signature/balance validation is reached.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
