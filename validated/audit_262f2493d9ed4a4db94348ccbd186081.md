## Analysis

The GitLab bug's root cause is: a URL taken from an untrusted/attacker-influenced source is handed straight to a git transport operation (`fetch_as_mirror`) after only a generic `UrlBlocker.validate!` call that does **not** restrict the URL *scheme*, so `file://` (and other unusual git transports) slip through and get executed by git.

Searching the Desktop codebase for the equivalent guard turns up **no scheme/protocol allow-listing anywhere** in the git remote-URL code path:

- `clone()` in `app/src/lib/git/clone.ts` only checks that the **destination path** isn't sensitive (`isClonePathSensitive`); the `url` parameter is pushed straight into the `git clone -- url path` argv with zero validation of its scheme. [1](#0-0) [2](#0-1) 

- `addRemote()` in `app/src/lib/git/remote.ts` builds `git remote add name url` from a raw `url` argument with no validation at all. [3](#0-2) 

- `fetch()` in `app/src/lib/git/fetch.ts` only resolves a proxy for `remote.url` (`envForRemoteOperation`) — again, no scheme check. [4](#0-3) 

- `_findPullRequestBranch` in `app-store.ts` takes `headCloneUrl` (derived from a `IAPIRepository`/PR head-repo object) and passes it directly into `addRemote(...)` and later fetches it — the exact "GitHub API object" pattern called out as in-scope, and there is no protocol allow-list applied to `headCloneUrl` before it becomes an actual git remote. [5](#0-4) [6](#0-5) 

- The deep-link handler `parseAppURL` (`app/src/lib/parse-app-url.ts`) builds an `open-repository-from-url` action whose `url` field is the raw string taken from an attacker-controlled `x-github-client://openRepo/<url>` link, with only branch/PR/filepath validated — the repo `url` itself is passed through unchecked, as shown by the test fixtures. [7](#0-6) 

None of `parseRemote`, `sanitizeCloneName`, or `urlsMatch` in `app/src/lib/remote-parsing.ts` / `app/src/lib/repository-matching.ts` enforce an `https`/`ssh`/`git` protocol allow-list — they only extract `owner`/`name`/`hostname` for matching and directory-name sanitization, they don't reject non-http(s)/ssh schemes such as `ext::` or `file://`. [8](#0-7) 

I was not able to fully trace `app/src/ui/dispatcher/dispatcher.ts`'s handling of the `open-repository-from-url` action before running out of tool calls, so I cannot confirm with certainty whether that specific deep-link path auto-clones or requires an extra "Clone this repository" confirmation click. That said, the underlying primitive — **no git URL scheme allow-list anywhere in the clone/fetch/addRemote call chain** — is directly confirmed from local code, and it is reachable from at least one attacker-controlled input (`headCloneUrl` from a GitHub API pull-request object) that flows into `addRemote` → `fetch` with no user "typing a URL" step required.

### Title
Missing git URL scheme validation before `clone`/`fetch`/`addRemote` allows attacker-controlled remote URLs to reach git's `ext::`/`file://` transports - (File: app/src/lib/git/clone.ts, app/src/lib/git/remote.ts, app/src/lib/git/fetch.ts, app/src/lib/stores/app-store.ts)

### Summary
`clone()`, `addRemote()`, and `fetch()` in Desktop's git wrapper layer accept a `url`/`remote.url` string and pass it directly to the `git` binary without ever validating the URL scheme. `_findPullRequestBranch` in `app-store.ts` feeds `headCloneUrl` — a value derived from a GitHub API pull-request/head-repo object — straight into `addRemote()` and then `_fetchRemote()`. If that value can be made to be anything other than a plain `https://`/`ssh://`/`git://` URL (e.g. because it is sourced from a GitHub Enterprise Server response, a proxy/MITM'd API response, or any other place an `IAPIRepository`-shaped object's `clone_url`/`ssh_url` is trusted), git itself will happily execute alternate transports such as `ext::` (arbitrary command execution via the external-command git helper) or read local paths via `file://`.

### Finding Description
- `clone(url, path, options)` only guards the destination `path` via `isClonePathSensitive`; the `url` argument is appended verbatim to `git clone --recursive ... -- url path`. [1](#0-0) [2](#0-1) 
- `addRemote(repository, name, url)` runs `git remote add name url` with no validation of `url` whatsoever. [3](#0-2) 
- `fetch(repository, remote, ...)` runs `git fetch remote.name` using the already-configured remote URL (set via `addRemote`/`setRemoteURL`), and only resolves a proxy for it — it performs no scheme check. [4](#0-3) 
- `_findPullRequestBranch(repository, prNumber, headRepoOwner, headCloneUrl, headRefName)` takes `headCloneUrl` and, if no existing remote matches it, calls `addRemote(repository, forkRemoteName, headCloneUrl)` and subsequently `_fetchRemote(...)`, all automatically as part of checking out a PR. [9](#0-8) 
- Nowhere in `remote-parsing.ts` / `repository-matching.ts` (the only URL-shape validation layer in the codebase) is a protocol allow-list enforced; `parseRemote`/`parseRepositoryIdentifier` simply try to extract `owner`/`name`/`hostname` and fall back to treating any unmatched string as an `owner/name` shortcut, they never reject dangerous schemes. [10](#0-9) 

This mirrors the broken invariant in the GitLab report exactly: a URL that ultimately reaches `git fetch`/`git clone`/`git remote add` is validated only for shape/ownership matching, never for *transport scheme*, so any git-supported scheme (`ext::`, `file://`, `ssh://user@host/-oProxyCommand=...` payloads, etc.) can reach the git process.

### Impact Explanation
If an attacker can influence the `clone_url`/`ssh_url`/`headCloneUrl` value that ends up in `addRemote`/`fetch`/`clone` (e.g. via a compromised/malicious GitHub Enterprise Server, a MITM'd API response, or any code path that treats an externally-supplied string as a `IAPIRepository`-like object), the consequence ranges from:
- Local file/repo disclosure via `file://` remotes (reading arbitrary local git repositories the Desktop process has access to, directly analogous to the GitLab report's local-repo import primitive), to
- Remote code execution via git's `ext::` transport helper, which spawns an arbitrary shell command supplied in the URL.

Both outcomes are unprivileged code-execution/file-read primitives explicitly called out as in-scope ("attacker controls ... a GitHub API object ... and the result is code execution, file write or read outside the repo").

### Likelihood Explanation
The most concrete, always-reachable path is `_findPullRequestBranch`, which is invoked automatically as part of Desktop's "checkout PR" flow and calls `addRemote`/`_fetchRemote` with `headCloneUrl` with no scheme check in between. The exact upstream boundary of trust for `headCloneUrl` (whether it can ever differ from a plain GitHub `https`/`ssh` URL for GitHub.com specifically, versus a GHES/enterprise or man-in-the-middled endpoint) could not be fully verified in the time available — I was unable to inspect `dispatcher.ts`'s full handling of the `open-repository-from-url` deep-link action before running out of tool budget, so I cannot rule in or out that specific vector with full confidence. What is confirmed with certainty from local code is that **no defense-in-depth scheme allow-list exists anywhere in the clone/fetch/addRemote call chain**, which is the exact missing control that caused the GitLab CVE.

### Recommendation
Add an explicit allow-list check (e.g. restrict to `https:`, `http:`, `ssh:`, `git:`, and `x-github-client:`-mediated schemes as appropriate) immediately before any `git clone`, `git fetch`, `git remote add`, or `git remote set-url` invocation that consumes a URL originating from: pull-request head-repo metadata, `IAPIRepository`/`IAPIRepositoryCloneInfo` objects, or the `x-github-client://openRepo/...` deep-link handler. Reject any URL whose scheme is not on the allow-list (in particular reject `ext::`, `fd::`, `file://` unless explicitly intended, and any URL containing `-o`/config-injection-style payloads) before it is ever passed to `addRemote`, `fetch`, or `clone`.

### Proof of Concept
Conceptual PoC (exact end-to-end trigger for the deep-link vector could not be fully confirmed due to incomplete inspection of `dispatcher.ts`):
1. Attacker crafts a malicious GitHub pull request (or controls a GHES/MITM'd API response) whose head-repo clone URL field is set to `ext::sh -c "touch /tmp/pwned"` instead of a normal `https://` URL.
2. Victim, using GitHub Desktop, opens/checks out that PR, triggering `_findPullRequestBranch(repository, prNumber, headRepoOwner, headCloneUrl, headRefName)`. [11](#0-10) 
3. Because no remote already matches `headCloneUrl`, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)`, writing the malicious `ext::` URL into `.git/config` as a real remote, then calls `_fetchRemote(...)` → `fetchRemote` → `fetchRepo`/`fetch()`, which shells out to `git fetch <remoteName>`. [6](#0-5) [4](#0-3) 
4. Git's `ext::` transport helper executes the embedded shell command on the victim's machine with the privileges of the GitHub Desktop process.

    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

/** Try to parse an owner and name from a URL or owner/name shortcut. */
export function parseRepositoryIdentifier(
  url: string
): IRepositoryIdentifier | null {
  const parsed = parseRemote(url)
  // If we can parse it as a remote URL, we'll assume they gave us a proper
  // URL. If not, we'll try treating it as a GitHub repository owner/name
  // shortcut.
  if (parsed) {
    const { owner, name, hostname } = parsed
    if (owner && name) {
      return { owner, name, hostname }
    }
  }

  const pieces = url.split('/')
  if (pieces.length === 2 && pieces[0].length > 0 && pieces[1].length > 0) {
    const owner = pieces[0]
    const name = pieces[1]
    return { owner, name, hostname: null }
  }

  return null
}
