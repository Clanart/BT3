### Title
Frozen Consensus Clients Do Not Invalidate Already-Stored State Commitments Used by Request/Timeout Handlers - ([File: modules/ismp/core/src/handlers/timeout.rs], [File: modules/ismp/core/src/handlers/consensus.rs])

### Summary
The external report's core broken invariant is: a security boundary (mass exit) is enforced by an "is this old enough" check, but that check is not cryptographically bound to the point where the validator set became compromised — so a forged-but-plausible "old" artifact signed by already-compromised validators is still trusted. The local analog in Hyperbridge is in the ISMP core message handlers: freezing a consensus client (the mechanism used when byzantine/fraudulent behavior is detected via `freeze_client`/`FraudProofMessage`) only gates the `update_client` path via `host.is_consensus_client_frozen()`. It is never checked again in the request, response, or timeout dispatch handlers, which instead trust whatever `StateCommitment` was already persisted to storage for a given `StateMachineHeight`, gated only by the challenge period having elapsed.

### Finding Description
`update_client` in `modules/ismp/core/src/handlers/consensus.rs` explicitly checks `host.is_consensus_client_frozen(msg.consensus_state_id)?` before accepting new consensus proofs: [1](#0-0) 

However, the timeout handler in `modules/ismp/core/src/handlers/timeout.rs` never performs this check. It only calls `validate_state_machine(host, timeout_proof.height)` and then reads the already-stored `state_machine_commitment`: [2](#0-1) 

The same pattern exists on the request path, and on the EVM handler side (`handlePostRequestTimeouts`, `handleGetRequestTimeouts`, `handleGetResponses` in `evm/src/core/HandlerV2.sol`), which only checks that the challenge period has elapsed against `stateMachineCommitmentUpdateTime`, then trusts `host.stateMachineCommitment(message.height)` unconditionally: [3](#0-2) 

In other words, once a fraudulent state commitment has been persisted for some height `H` under a consensus client (either because it was submitted before the fraud was detected, or during the challenge window before `freeze_client` fires), every downstream handler that processes requests/timeouts/responses anchored at height `H` continues to trust it — there is no re-validation that the consensus client backing that specific height is not currently frozen, and no hash-chain/continuity proof linking that stored commitment forward to the last-known-good state. This is structurally identical to the reported `TokenBridge._withdrawRequest()` bug: an "old enough" check (challenge period elapsed / block predates freeze) stands in for actual chain-of-custody validation, letting a commitment produced by since-compromised validators remain fully usable for fund-moving actions (timeout refunds, response delivery, request dispatch) after the compromise is known.

### Impact Explanation
If a consensus client is compromised long enough to get one fraudulent `StateCommitment` persisted (e.g., during the challenge period, before fishermen submit a `FraudProofMessage` to freeze it), that single stored commitment remains fully authoritative for all future request/response/timeout processing at that height. Attackers (or the compromised validators themselves) can use it to force `dispatchTimeOut`/`dispatchIncoming` with forged non-membership/membership proofs rooted in that state, triggering unauthorized fee refunds, response delivery, or module callbacks — i.e., false state acceptance and potential fund loss — even after the network has "detected and frozen" the byzantine consensus client. This matches the bounty's core class: false proof/state acceptance leading to unauthorized execution or fund movement.

### Likelihood Explanation
This requires only a transient compromise or misbehavior of a state machine's consensus client sufficient to get one fraudulent height accepted before it is frozen — no additional privileged actor, admin key, or governance action is needed by the exploiting party once that state exists. Given the challenge-period design intentionally allows time between commitment storage and usability, and fraud proofs are reactive, the window in which a forged commitment can be created and later consumed by an unprivileged relayer/caller (all of `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, `handleGetResponses`, and the Rust `timeout::handle` are permissionless) is realistic in the ISMP proof pipeline.

### Recommendation
Re-validate that the consensus client (and specifically the `consensus_state_id`/`StateMachineId` associated with the `StateMachineHeight`) is not frozen at the time requests/responses/timeouts are processed, not only at `update_client` time. Additionally, tie state commitment usability to a continuity/hash-chain proof to the latest trusted commitment, so a stored-but-later-repudiated commitment cannot be consumed by downstream handlers after a fraud proof invalidates its consensus client.

### Proof of Concept
1. A consensus client `C` for state machine `S` is compromised; malicious validators submit and get accepted a fraudulent `StateCommitment` at height `H` via `update_client` (passes because `is_consensus_client_frozen` is false at that time).
2. Before the challenge period elapses, fishermen detect the fraud and call `freeze_client` (via `FraudProofMessage`), setting `is_consensus_client_frozen(C) = true`. `update_client` will now reject new updates.
3. After the challenge period for height `H` elapses (measured only by `stateMachineCommitmentUpdateTime`/`store_state_machine_update_time`, independent of freeze status), a caller submits a `PostRequestTimeoutMessage`/`GetTimeoutMessage`/`TimeoutMessage::Post` referencing height `H`.
4. `handlePostRequestTimeouts`/`timeout::handle` verify only `ChallengePeriodNotElapsed`/`validate_state_machine` and the non-membership proof against the (fraudulent) `state.stateRoot` at `H` — neither checks `is_consensus_client_frozen(C)` — and dispatch `onTimeout`/refund logic using attacker-controlled proof content, exactly analogous to the original report's forged old `blockRid` bypassing mass-exit protections.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
