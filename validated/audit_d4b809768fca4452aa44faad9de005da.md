Confirmed: `handle_unsigned` in `modules/pallets/ismp/src/lib.rs` is a permissionless, unsigned extrinsic — "anyone execute ISMP messages for free, provided they have valid proofs" [1](#0-0) . It accepts an arbitrary `Vec<Message>` batch, executes them all in one call, and passes the combined `messages` and `events` to `FeeHandler::on_executed` as a single unit [2](#0-1) . `pallet-consensus-incentives::on_executed` then determines the reward recipient from only the *first* message in the batch, but pays out rewards for every distinct `StateMachineUpdated` event across the *entire* batch [3](#0-2) .

### Title
Consensus-incentive reward misattribution via batched `handle_unsigned` messages — attacker steals other relayers' consensus rewards - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` identifies the sole reward recipient by recovering a signature from `messages[0]` only [4](#0-3) , but iterates over *all* `StateMachineUpdated` events produced by the whole batch to compute and pay rewards [5](#0-4) . Because `handle_unsigned` is a permissionless, free, unsigned extrinsic that accepts any `Vec<Message>` [1](#0-0) , and because consensus proofs are public data that "can be generated by anyone, as they are freely provided by its connected chains" [6](#0-5) , an attacker can grab a legitimate, valid consensus proof for a high-value state machine that some other relayer is about to submit (it's public/gossiped) and bundle it into a batch with their own cheap, low-value/self-generated consensus message placed at index 0. The batch executes successfully (all sub-proofs are individually valid — no proof forgery needed), and `LastRewardedHeight` is advanced for the victim's chain too, so the honest relayer's later resubmission of that same proof pays zero reward (watermark already consumed) while the attacker's account collects the full `(latest_height - baseline) * cost_per_block` payout for that chain.

### Finding Description
The reward-attribution logic conflates "who signed the batch's first message" with "who is entitled to the reward for every state-machine advance in the batch." `calculate_reward` reads only globally-persisted heights (`latest_commitment_height`, `previous_commitment_height`, `LastRewardedHeight`) [7](#0-6)  — it has no way to check whether the *particular* message that advanced a given `state_machine_id` was actually authored/signed by `messages[0]`'s signer. The watermark (`LastRewardedHeight`) is monotonic and is bumped unconditionally for every state machine advanced in the batch, crediting the attacker's `relayer_account` [8](#0-7) [9](#0-8) .

Since `handle_unsigned` executes an arbitrary `Vec<Message>` supplied by any submitter with no signer/origin binding beyond `ensure_none` [2](#0-1) , nothing prevents an attacker from constructing `messages = [my_cheap_consensus_msg, victims_valid_consensus_msg_for_chain_B]`. Both consensus proofs verify (they are legitimately valid — no need to forge or corrupt any proof, satisfying the "no malicious peer/prover" constraint), `Self::execute(messages)` succeeds, and `on_executed` fires once for the whole batch, paying the attacker for both state machines' advances.

This directly parallels the seed bug's core primitive: a monotonically-advancing, block-derived quantity (`interest`/here, `block_cost`) is consumed/settled by whichever actor happens to trigger the state transition in a given transaction, regardless of who actually did the underlying work — enabling a free-riding attacker to intercept value that should accrue to someone else, on the very next opportunity to batch.

### Impact Explanation
This is direct loss of protocol treasury funds paid to the wrong beneficiary — a "wrong beneficiary or amount" and "reward theft" issue that matches the bounty's live impact criteria (stealing of funds via logic attack, no privileged/malicious-relayer assumption required — the attacker just observes public mempool/gossip data and repackages it). Treasury funds (`T::TreasuryAccount`) intended for the relayer that produced/discovered a given consensus proof are instead drained to an unrelated address, and the true submitter's later transaction becomes a no-op (reward already zeroed by the consumed watermark), permanently under-compensating them.

### Likelihood Explanation
High: the attack requires no special access — the attacker only needs to observe a soon-to-be-submitted (or already broadcast but not yet included) consensus proof for some `state_machine_id` (proofs are explicitly public, "freely provided by its connected chains") and prepend their own trivially-cheap consensus message (e.g., for a chain with `cost_per_block` configured but very low activity, or even a message that advances the state machine minimally) as `messages[0]`. `handle_unsigned` is free (unsigned, no fee), and the attack can be repeated every block against any state machine with a configured `StateMachinesCostPerBlock`.

### Recommendation
Reward attribution must be tied to the specific message/event that produced each `StateMachineUpdated`, not to `messages[0]` for the whole batch. Recover and verify the relayer signature per consensus message, and only credit the state machine(s) whose advance was actually caused by that specific signed message (e.g., match consensus message → `consensus_state_id` → `state_machine_id` it is entitled to update, or restructure `on_executed` to process one `(message, its own resulting events)` pair at a time instead of pooling all events against `messages[0]`'s signer).

### Proof of Concept
1. Observe a pending, valid `Message::Consensus` proof `P_victim` (publicly available/gossiped) that will advance `state_machine_id = B` from height 100 to 200, with `cost_per_block` configured for `B`.
2. Attacker crafts their own trivially valid `Message::Consensus` proof `P_attacker` for a state machine `A` (can be minimal/cheap, e.g., 1-block advance).
3. Attacker submits `handle_unsigned([P_attacker, P_victim])` before the victim's own submission lands.
4. `Self::execute` processes both, producing `StateMachineUpdated` events for both `A` and `B` [2](#0-1) .
5. `on_executed` recovers the relayer solely from `messages[0]` (`P_attacker`'s signer) [4](#0-3) , then pays rewards for both `A`'s and `B`'s highest-height advance to the attacker's account, and bumps `LastRewardedHeight` for both [10](#0-9) .
6. When the honest relayer later submits `P_victim` alone (or it was already consumed/rejected as duplicate by the transaction pool's `provides` tag keyed on `state_machine_id`), `calculate_reward` for `B` returns `0` since `LastRewardedHeight[B]` already equals 200 [11](#0-10) , so the honest relayer receives nothing despite having generated the actual proof.

Note: I could not fully verify within the available tool budget whether the transaction-pool's `provides` tag (`keccak256(state_machine_id.encode())`, priority = `latest_height`) [12](#0-11)  would cause the victim's original transaction to be dropped/superseded by the attacker's bundled one before or after inclusion — this affects whether the attack requires precise timing/front-running of block inclusion, but does not change the underlying reward-misattribution flaw itself.

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
