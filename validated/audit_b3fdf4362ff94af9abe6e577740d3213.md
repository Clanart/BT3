### Title
`WombatPoolHelperV2.depositFor()` hardcodes `_minimumLiquidity` to `0`, exposing depositors to front-run/sandwich slippage attacks - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor()` calls the internal `_deposit()` helper with a hardcoded `0` for `_minimumLiquidity`, unlike the sibling `deposit()` function which forwards a caller-supplied `_minimumLiquidity`. This removes slippage protection for any unprivileged wallet that deposits on behalf of another address (or itself, when routed via this entrypoint), mirroring the exact root cause described in the sNOTE `_mintFromAssets()` finding — `minimumBPT`/`minimumLiquidity` hardcoded to `0` in a liquidity-provisioning call.

### Finding Description
`deposit(uint256 _amount, uint256 _minimumLiquidity)` correctly forwards the user-supplied minimum to `_deposit`: [1](#0-0) 

But `depositFor(uint256 _amount, address _for)` hardcodes the minimum to `0`: [2](#0-1) 

This value is passed straight through `_deposit()` into `WombatStaking.deposit()`, which forwards it unchanged into `IWombatPool(poolInfo.depositTarget).deposit(...)` — the actual Wombat AMM pool join that mints LP based on pool cash/liability ratios (subject to price-impact/slippage): [3](#0-2) [4](#0-3) 

Because `_minimumLiquidity` is forced to `0`, the underlying `IWombatPool.deposit()` call (see interface) will accept any amount of LP/liability minted no matter how unfavorable, since the pool's own `minimumLiquidity` check becomes a no-op: [5](#0-4) 

`depositFor` is `external` with no access-control modifier, so any unprivileged wallet can call it (for itself or on behalf of another `_for` address) with no way to protect against pool-composition manipulation between transaction submission and execution.

### Impact Explanation
An attacker (e.g., a searcher/MEV bot) can front-run a `depositFor` call by manipulating the Wombat pool's cash/liability ratio (e.g., via a large imbalancing swap or a same-block/pre-block deposit/withdraw), causing the depositor's `_amount` to mint a materially smaller amount of LP/receipt tokens than expected, then reverse the manipulation afterward (sandwich attack) to capture the difference. This is a direct, concrete loss of user funds at deposit time — value that the depositor should have received as LP (and consequently receipt-token/staking value) is instead captured by the attacker, satisfying the "direct theft of user funds" impact bar.

### Likelihood Explanation
Likelihood is high: `depositFor` is a normal unprivileged entrypoint with no allowlist/authorization check, callable by anyone who holds `depositToken`, and the missing slippage parameter is unconditional (not a rare edge case) — every call through this path is exposed. The pattern is essentially identical to the referenced sNOTE finding, which was confirmed by the target project and multiple independent researchers as exploitable via front-running/sandwiching on Automated Market Maker-style pool joins.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor(uint256 _amount, address _for, uint256 _minimumLiquidity)` and forward it into `_deposit()` instead of the hardcoded `0`, mirroring the existing `deposit()` function. Ensure any other callers/wrappers of this helper are updated to supply a real slippage bound.

### Proof of Concept
1. Attacker observes a pending `WombatPoolHelperV2.depositFor(amount, victimOrSelf)` transaction in the mempool.
2. Attacker front-runs with a swap that skews the target pool's cash/liability ratio unfavorably for the deposit token.
3. Victim's transaction executes: `_deposit(_amount, 0, _for, address(this))` → `WombatStaking.deposit(...)` → `IWombatPool.deposit(token, amount, 0, ...)`, which accepts whatever (reduced) LP amount the manipulated pool state produces because `minimumLiquidity == 0` never reverts. [2](#0-1) [6](#0-5) 
4. Attacker back-runs, reversing their swap and extracting the value difference, leaving the victim's staked receipt-token balance permanently lower than it should be for the deposited `_amount`.
