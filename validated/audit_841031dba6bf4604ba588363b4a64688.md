### Title
Arbitrary File Write via Unsanitized `foldername` in DataLayer `add_missing_files` RPC - (File: `chia/data_layer/data_layer_rpc_api.py`)

### Summary
The DataLayer RPC endpoint `add_missing_files` accepts a raw, attacker-controlled `foldername` string from the request JSON and converts it directly into a `Path` object with no validation, canonicalization, or containment check against `server_files_location`. That path is then used as the base directory for writing DataLayer Merkle tree dump files (`.dat` files), including creating arbitrary parent directories. This mirrors the OpenEMR DICOM-zip bug class: a user-influenceable destination/path component is used to build a file write target without sanitizing path traversal (e.g. `../`) or absolute-path overrides, allowing writes outside the intended `server_files_location` directory.

### Finding Description
`DataLayerRpcApi.add_missing_files()` reads the `foldername` request field and blindly wraps it in `Path()`: [1](#0-0) 

This value is forwarded unchanged to the service method `DataLayer.add_missing_files()`, which substitutes it in place of the safe, configured `server_files_location` when it is non-`None`: [2](#0-1) 

That `server_files_location` (attacker-supplied) is then passed straight into `write_files_for_root()`, which computes concrete target file paths via `get_full_tree_filename_path()` / `get_delta_filename_path()`, creates any missing parent directories, and opens the resulting path for writing (`"wb"`/`"xb"` mode) with tree data supplied by the local `DataStore`: [3](#0-2) 

While the file-name suffix portion (`{store_id}-{node_hash}-full/delta-{generation}-v1.0.dat`) is deterministic and not attacker-controlled, the **directory prefix** (`foldername`) is fully attacker-controlled and is neither restricted to a subdirectory of the configured `server_files_location` nor checked for `..`/absolute-path escape. Because `Path.joinpath()` with an absolute string simply replaces the base, and because `mkdir(parents=True, exist_ok=True)` will create arbitrary intermediate directories, a caller can direct writes to any filesystem location the DataLayer process has permission to write to (e.g. `/root/.chia/mainnet/wallet/...`, systemd unit paths, or other locations under the daemon's write access), producing new `.dat` files there.

This differs from the file *download/validation* path (`is_filename_valid()` in `chia/data_layer/download_data.py`), which strictly validates filenames for `http_download`/plugin-downloaded files, but that validation does not apply to the locally-served `add_missing_files` "reconstruct from local DB" path, since here the file content is not downloaded from a remote peer — it's generated locally from `DataStore` and written to whatever `foldername` the caller specifies.

### Impact Explanation
An authenticated local RPC caller (anyone holding a valid DataLayer RPC client cert, which per the threat model here is treated as an "unprivileged/local RPC caller" role akin to a wallet or DataLayer client) can direct the DataLayer service to write files with attacker-influenced binary tree-dump contents to arbitrary filesystem paths outside `server_files_location`. This is an arbitrary file write primitive scoped to whatever privileges the DataLayer process has. Depending on deployment, this could overwrite configuration files, corrupt DataLayer/wallet database directories used by other services, or be leveraged toward further compromise if writable paths overlap with executable or auto-loaded config locations. This matches the "Medium" severity class described in the source report (arbitrary file write via unsanitized destination path).

### Likelihood Explanation
Likelihood is moderate: exploitation requires access to the DataLayer RPC (SSL client cert-authenticated), which is a "local RPC caller" per the accepted threat model, not a fully public/unauthenticated attack surface. No additional social engineering or privileged system access is needed beyond RPC access; the vulnerable code path is straightforward to trigger with a single `add_missing_files` request containing a crafted `foldername` (e.g., `/tmp/evil` or a relative `../../` path resolving outside the intended directory).

### Recommendation
- In `DataLayerRpcApi.add_missing_files()` (and correspondingly in `DataLayer.add_missing_files()`), resolve the supplied `foldername` against a fixed base directory and reject it if the resolved path is not contained within that base (e.g., using `Path.resolve()` plus a strict `is_relative_to()`/prefix check against `server_files_location` or a documented allow-list of directories).
- Reject inputs containing path traversal sequences or absolute path overrides unless explicitly intended and documented as an admin-only capability, and if so, gate it behind stronger authorization/config flags rather than accepting arbitrary paths from any RPC caller.
- Apply the same containment validation to any other RPC/CLI-supplied path parameters in `chia/data_layer/` that end up as write targets (e.g., `directory`/`foldername` options surfaced by `chia data add_missing_files`).

### Proof of Concept
1. Start a chia node with the DataLayer RPC service enabled and obtain a valid DataLayer RPC client certificate (a "local RPC caller").
2. Send an `add_missing_files` RPC request with a crafted `foldername`, e.g.:
```json
{
  "ids": ["<store_id_hex>"],
  "overwrite": true,
  "foldername": "../../../../tmp/dl_traversal_poc"
}
```
3. `DataLayerRpcApi.add_missing_files()` converts this directly to `Path("../../../../tmp/dl_traversal_poc")` with no containment check, and `DataLayer.add_missing_files()` uses it as `server_files_location` for `write_files_for_root()`, which creates the directory tree via `mkdir(parents=True, exist_ok=True)` and writes the resulting `.dat` file at that attacker-chosen location. [1](#0-0) [4](#0-3) 
4. Verify the `.dat` file was written outside the intended `server_files_location` directory.
