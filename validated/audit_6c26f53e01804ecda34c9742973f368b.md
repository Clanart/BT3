## Title
Quadratic/Cubic-Time DoS in `Offer.get_cancellation_coins()` via crafted offer announcement graph - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` process the coin-announcement dependency graph of an offer's coin spends using nested loops with no bound on the number of coins or announcements, and each spend's conditions are evaluated with `INFINITE_COST`. A malicious offer maker can craft an offer containing many small coin spends, each emitting many `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions, so that when the counterparty later tries to cancel the resulting trade, the wallet process performs a super-linear (quadratic-to-cubic) amount of work before it can build the cancellation transaction — mirroring the sqlparse `group_comments` pattern where an unbounded pre-guard scan is quadratic in attacker-controlled input size.

### Finding Description
`detect_dependent_coin()` is a triple-nested scan over `names` × `deps[name]` × `announcement_dict.items()`: [1](#0-0) 

It is invoked repeatedly inside `Offer.get_cancellation_coins()`'s outer `while True:` loop, and each outer iteration itself contains a second nested `while True:` loop scanning `dependencies.items()` again: [2](#0-1) 

Before any of this graph analysis happens, every non-addition coin spend in the offer bundle is run through CLVM with `INFINITE_COST` (no cost cap enforced at this stage), and every resulting condition is collected into the `dependencies`/`announcements` maps unconditionally: [3](#0-2) 

Just as `sqlparse.group_comments` walks the full remaining token list on every iteration of its `while` loop (and runs before the `MAX_GROUPING_TOKENS` guard), `get_cancellation_coins()`/`detect_dependent_coin()` walk the full remaining coin/dependency/announcement sets on every iteration, with no size limit applied to the number of coin spends, announcements, or outer-loop iterations. An attacker who controls the offer's coin-spend layout (as an untrusted offer maker) can shape the announcement/dependency graph so that each outer-loop pass removes only a small number of coins, forcing the full O(N²) (or worse, combined with the inner removal loop) `detect_dependent_coin` scan to repeat many times.

This code path is reached from `TradeManager.cancel_pending_offers()`: [4](#0-3) 

which is exposed via the wallet RPC endpoints `cancel_offer`/`cancel_offers` that a local RPC caller (or the wallet GUI/CLI on the user's behalf) invokes to cancel a previously accepted trade. Because `trade.offer` is the full aggregated offer bytes — including the coin spends contributed by the *counterparty* who made the offer — the pathological structure is attacker-supplied even though the DoS is triggered by the victim's own cancellation action.

### Impact Explanation
A crafted offer, once taken and later cancelled (a common recovery action when a trade stalls or the taker changes their mind), can cause the wallet process to spend disproportionate CPU time inside `get_cancellation_coins()`, stalling the `wallet_state_manager.lock`-protected cancellation flow and, by extension, other wallet RPC operations that share that lock. This is a spend-triggered transaction-processing halt in the wallet, directly analogous to the sqlparse DoS impact (processing halt from crafted comment-only input on the sanitizer path).

### Likelihood Explanation
Exploitation requires only that a victim wallet takes an offer crafted by an untrusted counterparty and subsequently attempts to cancel the resulting trade via `cancel_offer`/`cancel_offers` — a normal, expected user action. The attacker does not need any special privileges beyond being able to construct and distribute an offer file, which is the standard offer-exchange model in Chia (offer files are commonly shared out-of-band, e.g. via marketplaces).

### Recommendation
- Bound the number of coin spends / announcements processed by `get_cancellation_coins()` (e.g., reject offers whose spend count or announcement count exceeds a sane limit before running the dependency analysis).
- Replace the O(N) linear scan of `announcement_dict.items()` inside `detect_dependent_coin()`'s per-dependency loop with a reverse index (`announcement -> coin`) built once in O(N), reducing the overall complexity to near-linear.
- Enforce a real CLVM cost limit (not `INFINITE_COST`) when running each coin spend's puzzle inside `get_cancellation_coins()`, consistent with cost enforcement elsewhere in the mempool/consensus pipeline.

### Proof of Concept
1. As a malicious offer maker, construct an offer whose bundle contains `N` coin spends (e.g., N in the low thousands), where spend `i` asserts a coin announcement created by spend `i-1` (or a more adversarial pattern that maximizes remaining work after each `detect_dependent_coin` removal), each spend also emitting several extra `CREATE_COIN_ANNOUNCEMENT` conditions to inflate `D` (dependencies per coin).
2. Have the victim wallet take this offer via `respond_to_offer` (normal flow) and later call `cancel_offer`/`cancel_offers` on the resulting trade.
3. Observe `TradeManager.cancel_pending_offers()` → `Offer.get_cancellation_coins()` take disproportionately long (super-linear growth with `N`) compared to a well-formed offer of similar size, analogous to the `n=1000/2000/4000` timing curve in the sqlparse report.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
