## Title
TOCTOU symlink race in `resolveWithin()` allows reading files outside the repository during Copilot conflict-resolution — ([File: app/src/lib/path.ts])

### Summary
The Numa report's root cause is a guard that validates a condition (`currentCF > warningCF`) and then performs a state-changing action (mint) that can itself falsify the very condition the guard checked — the check happens before the effect, on stale state, so the invariant is not actually enforced at the time it matters. The Desktop analog is `resolveWithin()` in [1](#0-0) , which validates path safety via `realpath()` but returns the un-resolved path string to the caller, who performs the actual filesystem effect (`stat`/`readFile`) later. The safety check and the effect operate on two different moments in time and two different values, creating a check-then-use gap that a hostile repository can exploit.

### Finding Description
`_resolveWithin()` computes `resolved` (a plain, non-dereferenced `Path.resolve()` string) and separately computes `realResolved = await realpath(resolved)` purely to decide whether to allow the request: [2](#0-1) 

Critically, it returns `resolved` — not `realResolved` — to the caller. The safety guarantee ("this path, once symlinks are resolved, stays inside `rootPath`") is only true at the instant `realpath()` was executed. Any caller that later re-touches the filesystem at `resolved` (via `stat`, `readFile`, etc.) is trusting a promise about a filesystem state that may no longer hold.

The primary consumer of this pattern, `buildConflictContext()`, does exactly that: it calls `resolveWithin(workingDirectory, file.path)` once, then performs `stat(absolutePath)` and `readFile(absolutePath, 'utf8')` afterward, using the plain path string returned by the guard: [3](#0-2) 

This mirrors the Numa bug exactly: the guard (`resolveWithin`'s `realpath` check ≈ `notInWarningCF`) is evaluated *before* the effect (`readFile` ≈ `mintNuAsset`), and nothing re-validates the condition at the moment the effect actually occurs. If the on-disk entry at `file.path` is swapped for a symlink pointing outside `workingDirectory` in the window between the `realpath()` call inside `resolveWithin` and the subsequent `stat`/`readFile` call, the check that "passed" no longer describes reality, and the read follows the attacker's symlink target.

The attacker fully controls the input needed to win this race: a cloned/fetched repository can ship a merge/rebase/cherry-pick conflict together with a `post-checkout` or `post-merge` Git hook (both of which Desktop intercepts and executes through its hooks proxy, see `getRepoHooks`/`with-hooks-env.ts` [4](#0-3) ) that spawns a short-lived background process. That process waits until the conflicted file exists as a regular file (so it passes `resolveWithin`'s `realpath` check) and then swaps it for a symlink pointing at a sensitive path (e.g. `~/.ssh/id_rsa`, `~/.aws/credentials`) just before Desktop's Copilot conflict-resolution flow performs the `stat`/`readFile` calls that build the prompt sent to the Copilot SDK.

### Impact Explanation
A successful race results in the content of an arbitrary file on the user's machine (anything the Desktop process can read) being read and, in this specific consumer, packaged into `rawContent` and sent off-repo to the Copilot service as part of `formatConflictContextForPrompt()` [5](#0-4) . That satisfies "file read outside the repo" and potential "credential exfiltration" from the valid-impact list, since SSH keys, cloud credentials, or other secrets could be smuggled to a remote LLM endpoint under the guise of "resolving a conflict."

### Likelihood Explanation
This is a narrow race window (two back-to-back async filesystem calls), so it is not trivially reliable, but it is entirely automatable: the attacker's hook can poll/retry the swap in a tight loop for the brief interval between when the conflict-resolution UI is invoked and when `buildConflictContext` executes, and can repeat the attempt across multiple conflicted files to increase the chance of winning at least once. No additional user action beyond opening a maliciously crafted repository and triggering the normal "resolve conflicts with Copilot" flow (a supported, expected feature) is required — this fits within the "attacker controls a cloned/fetched repository" threat model without any local/physical access or pre-existing malware.

### Recommendation
Eliminate the check/use gap instead of trying to shrink the race window:
- Have `resolveWithin()` return the already-dereferenced `realResolved` path (or an open file descriptor obtained via `fs.open`) rather than the pre-realpath `resolved` string, so callers operate on the exact entity that was validated.
- In `buildConflictContext()`, open the file once (e.g., `fs.open` + `fstat` + `read`) using the descriptor obtained immediately after validation, rather than re-resolving the path string for `stat` and `readFile` as two separate operations.
- As defense in depth, reject (or explicitly refuse to follow) symlinks encountered anywhere along conflicted-file paths before ever reading their contents for an outbound AI request.

### Proof of Concept
1. Attacker publishes a repository with a branch that produces a merge conflict on a tracked file `notes.txt`, and includes a `.git/hooks/post-checkout` (installable via a `core.hooksPath` trick or by convincing the victim to run `git init`/`clone` such that hooks are trusted, or simply relying on Desktop's own hooks-proxy interception of `post-checkout`/`post-merge` for the operation already in progress).
2. The hook script, once triggered by the merge/rebase Desktop performs internally, starts a tight loop: `rm notes.txt; ln -s /Users/victim/.ssh/id_rsa notes.txt`, timed to race the moment the user clicks "Resolve with Copilot."
3. Desktop's `buildConflictContext()` calls `resolveWithin(workingDirectory, 'notes.txt')` — at that instant `notes.txt` is still a regular file, so `realpath()` succeeds and the check passes, returning the plain path `workingDirectory/notes.txt`.
4. Before the subsequent `stat`/`readFile` calls execute, the hook's loop swaps `notes.txt` for the symlink to `~/.ssh/id_rsa`.
5. `stat(absolutePath)` and `readFile(absolutePath, 'utf8')` now dereference the symlink and load the victim's private key into `rawContent`, which `formatConflictContextForPrompt()` then serializes and sends to the Copilot backend.

Note: I could not execute this PoC (no filesystem/terminal access here) to empirically measure the race's success rate; this is a code-level analysis based on the `resolveWithin`/`buildConflictContext` implementation shown above.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))
