## Title
Path-containment check in `resolveWithin` uses substring `startsWith` without a path-separator boundary, allowing a same-prefix sibling directory/symlink to be treated as "inside the repository" — ([File: app/src/lib/path.ts])

### Summary
The shared helper `resolveWithin`/`_resolveWithin`, which every "is this attacker-influenced path safely inside the repo?" guard in the app delegates to, decides containment with `realResolved.startsWith(realRoot)` and never checks that a path separator follows the prefix. A `git`-tracked symlink whose real target is a *sibling* directory that merely shares a string prefix with the repository's directory name (e.g. `app` vs `app-secrets`, `app.wiki`, `app-old`) will pass the check even though it lives entirely outside the repository tree.

### Finding Description
`_resolveWithin` in [1](#0-0)  resolves the candidate path, `realpath()`s both the root and the candidate to defeat symlinks, and then compares them with a bare `startsWith`:
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```
There is no trailing-separator normalization (e.g. `realRoot + Path.sep`), so `"/Users/victim/Projects/app-secrets/config.json".startsWith("/Users/victim/Projects/app")` evaluates to `true` even though `app-secrets` is a completely different directory than `app`.

Interestingly, the project's own clone-path safety check in [2](#0-1)  gets this right by explicitly appending `Path.sep` (`clonePath.startsWith(sensitive + Path.sep)`), showing the developers were aware of exactly this class of bug elsewhere but the fix was not applied to the shared `resolveWithin` primitive.

`resolveWithin` is the load-bearing guard for several places where the path comes from attacker-controlled input:
- `buildConflictContext` reads arbitrary conflicted-file content off disk and sends it to the Copilot backend, gated only by `resolveWithin(workingDirectory, file.path)`: [3](#0-2) 
- `_applyCopilotConflictResolutions` writes AI-generated resolved content back to disk, gated only by `resolveWithin(repository.path, resolution.path)`: [4](#0-3)  followed by the actual write at [5](#0-4) 
- `openRepositoryFromUrl` reveals a file via `shell.showItemInFolder` for a `filepath` taken from an attacker-crafted `x-github-client://openrepo/...` deep link, gated by the same `resolveWithin`: [6](#0-5) 

`file.path`/`resolution.path` values are themselves loosely constrained: `resolveWithin` accepts a repo-relative path (which git symlinks let point wherever the attacker wants, since Desktop checks out symlinks as stored), and none of the callers add a separator-aware secondary check.

### Impact Explanation
If a victim's local directory layout happens to contain a sibling path whose name is a superstring of the cloned repository's directory name (a common, unremarkable naming pattern: `app` / `app-secrets`, `app` / `app.bak`, `myrepo` / `myrepo-old`, forked/duplicated clones, `.wiki` companion repos, etc.), an attacker-controlled repository can commit a symlink that resolves to that sibling path. Any feature that relies on `resolveWithin` for containment will then:
- Read file contents from outside the repository and forward them to the Copilot backend (credential/secret exfiltration from adjacent directories), via `buildConflictContext`.
- Write AI-produced content to a file outside the repository, silently corrupting data the user never intended to touch, via `_applyCopilotConflictResolutions`.
- Reveal/open arbitrary sibling files via a clicked deep link, via `openRepositoryFromUrl`.

This satisfies the "file write or read outside the repo" and "silent corruption of what the user commits" impact classes: the attacker only needs to control the cloned repository's contents (a committed symlink) — no local/admin access, no leaked credentials, no social engineering beyond the normal "clone/open this repo" and "resolve conflicts with Copilot" workflow.

### Likelihood Explanation
Exploitation requires a coincidental (or attacker-nudgeable, since the attacker also picks the upstream repo name that seeds the local clone directory name via `sanitizeCloneName`) sibling-directory naming collision on the victim's filesystem. This is a real-world-plausible but not guaranteed precondition, so likelihood is moderate rather than certain — but the underlying code defect (missing separator check) is unconditional and trivially demonstrable, and the same codebase already treats this exact class of bug as security-relevant elsewhere (`clone.ts`), indicating the gap in `path.ts` is an inconsistency/regression rather than an accepted risk.

### Recommendation
Fix the containment check in `_resolveWithin` to require a path-separator boundary (or exact equality), mirroring the pattern already used in `clone.ts`:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply this for both the platform-specific and POSIX/Win32 variants (`resolveWithinPosix`, `resolveWithinWin32`), and add regression tests for sibling-directory-prefix collisions (both same-length-prefix symlink targets and `..`-based traversal that lands on a prefix-colliding sibling), analogous to the existing symlink-escape tests in `app/test/unit/path-test.ts`.

### Proof of Concept
1. Victim has two existing local directories: `/Users/victim/Projects/app` and `/Users/victim/Projects/app-secrets/config.json` (any pre-existing sibling whose name is a superstring of the repo's clone directory name).
2. Attacker publishes a repository that, when cloned to `/Users/victim/Projects/app` (the natural clone target for that repo name), contains a committed symlink `evil -> ../app-secrets`.
3. Attacker gets the victim to open a merge/rebase that produces a conflict touching `evil/config.json`, then invoke the Copilot conflict-resolution feature.
4. `buildConflictContext` calls `resolveWithin('/Users/victim/Projects/app', 'evil/config.json')`. Internally: `realRoot = '/Users/victim/Projects/app'`, `realResolved = '/Users/victim/Projects/app-secrets/config.json'`. `realResolved.startsWith(realRoot)` is `true`, so the guard passes and the file is read and sent off-repo to the model.
5. When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` performs the same (broken) check and calls `writeFile('/Users/victim/Projects/app-secrets/config.json', resolution.resolvedContent, 'utf8')`, overwriting a file entirely outside the repository.
