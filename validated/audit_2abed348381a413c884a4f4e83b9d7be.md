### Title
`verify-package` (`CachedPackageRegistry::verify`) never compares actual on-chain module bytecode — only self-reported metadata — ([File: aptos-move/cli/src/stored_package.rs])

### Summary
The Aptos CLI's package verification path, used by `aptos move verify-package` (documented as checking that "on-chain bytecode matches a local source tree" [1](#0-0) ), is implemented by `CachedPackageMetadata::verify()`. This function only compares fields of the on-chain `PackageMetadata` struct (name, deps, `modules`, manifest, upgrade policy, extension, source digest) against a locally rebuilt `PackageMetadata` — it never fetches and byte-compares the actual deployed module bytecode against the locally compiled `.mv` bytecode.

### Finding Description
`CachedPackageRegistry::create` can optionally fetch each module's raw on-chain bytecode into a `bytecode: BTreeMap<String, Vec<u8>>` map, exposed via `get_bytecode()` [2](#0-1) , and via `get_bytecode()` [3](#0-2) .

However, the actual verification entry point, `CachedPackageMetadata::verify()`, only performs struct-field comparisons on the `PackageMetadata` (name, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) between the on-chain registry entry and the locally-rebuilt metadata: [4](#0-3) . It never invokes `get_bytecode()` or otherwise compares the raw compiled module bytes (the bytes actually loaded and executed by the VM) against what the local toolchain compiles from source.

`ModuleMetadata` itself only carries `name`, a gzipped `source` text blob, a `source_map`, and an `extension` [5](#0-4)  — it does not carry a hash or digest of the compiled bytecode. So even a full-field match of `modules` only proves the *source text metadata* strings match; it says nothing about whether the bytecode actually stored under `0x1::code::PackageRegistry` for that account is the bytecode that would be produced by compiling that source.

Because the on-chain code-publishing invariant enforced by `aptos_framework::code::publish_package` (compatibility, ownership, upgrade-policy strength, dependency checks) is orthogonal to whether the submitted `code: vector<vector<u8>>` bundle was actually derived from the submitted/self-reported source metadata — nothing on-chain or in this CLI tool cross-validates that mapping — a package can be published (or upgraded) where the metadata's `source`/`manifest`/`source_digest` fields describe one thing while the actual executable module bytecode is materially different, and `verify-package` will still report success as long as the *metadata objects* match.

### Impact Explanation
This creates a mismatch between "verified bytes" (source/metadata a reviewer or auditor inspects and matches) and "committed module bytes" (the actual bytecode executed on-chain), which is explicitly one of the accepted Publish Impact categories. A user relying on `aptos move verify-package` for code review / reproducibility assurance before interacting with, depending on, or trusting a deployed package can be misled into believing the deployed bytecode matches the audited/reviewed source, when in fact the executing bytecode could differ.

### Likelihood Explanation
Likelihood is limited by the fact that this is a client-side auditing convenience tool rather than an on-chain enforcement mechanism — it cannot itself be used to gain unauthorized publish/upgrade/freeze/ownership capabilities, and exploiting it requires a party to have already published metadata whose declared source diverges from the actual bytecode (which is possible today since nothing forces `code` bytes to correspond to the declared `source`/`source_digest`). The bug is a documentation/implementation gap in a trust-establishing tool rather than a bypass of the core `code::publish_package` or `object_code_deployment` ownership/compatibility checks, which I verified are otherwise sound (owner checks via `object::is_owner` [6](#0-5) , compatibility/policy checks in `code::publish_package` [7](#0-6) ).

### Recommendation
Extend `CachedPackageMetadata::verify()` (or the `verify-package` command flow) to always fetch on-chain bytecode via `get_bytecode()` for every module and byte-compare (or hash-compare) it against the bytecode produced by locally rebuilding the package, in addition to the existing metadata-field comparison. Update the CLI documentation to accurately describe what is and is not checked until this is fixed.

### Proof of Concept
1. Publish a package on-chain where `PackageMetadata.modules[i].source` (gzipped) is set to a benign/expected Move source string and `source_digest` is computed to match that source, but the `code: vector<vector<u8>>` bundle stored alongside contains different (e.g., subtly malicious) compiled bytecode — nothing in `code::publish_package` (`aptos-move/framework/aptos-framework/sources/code.move`) cross-validates that `code` was compiled from `pack.modules[i].source`.
2. Run `aptos move verify-package` against this address with a locally checked-out "expected" source tree matching the benign source.
3. `CachedPackageMetadata::verify()` [4](#0-3)  compares only the `PackageMetadata` structs (which will match, since the local rebuild also produces the same `source`/`source_digest`/`manifest`/`modules` metadata) and returns `Ok(())`, reporting successful verification — while the deployed, executing bytecode differs from what was reviewed.

Note: I was not able to inspect the full `execute()` implementation of the `VerifyPackage` CLI command in `aptos-move/cli/src/commands.rs` within the available tool budget to confirm whether it separately performs any additional bytecode-hash comparison outside of `CachedPackageMetadata::verify()`; this should be checked to fully confirm whether any additional bytecode check exists elsewhere in that command's flow.
