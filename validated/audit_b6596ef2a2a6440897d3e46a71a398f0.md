### Title
Cached FROST preprocess seed outlives its signing context, causing nonce reuse across sessions - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The CVE's bug class — saving a handle to an object outside the synchronization domain so it can be used after its validity window has closed — maps onto Serai's `SigningProtocol`, which persists a FROST preprocess seed (`CachedPreprocesses`) in the DB keyed only by `(label, attempt)`. The saved seed is looked up and reused on every subsequent call, even though the signing context it was created under (validator set, message, counterparty commitments) may no longer exist. Exactly like binder's stale VMA pointer, nothing invalidates the cached value when its context goes away, and deterministic `from_cache`/`seeded_preprocess` regeneration means stale reuse produces identical nonces on different messages — enabling recovery of the validator's secret share from publicly published shares.

### Finding Description

`SigningProtocol::preprocess_internal` caches a freshly generated preprocess seed, encrypted under `key || context`, into the `CachedPreprocesses` DB table: [1](#0-0) 

The cache key `self.context` for `DkgConfirmer` is only `(b"DkgConfirmer", self.attempt)` — it does not include the tributary `genesis`, the validator `set`, the `session`, or any binding to the validator set's membership: [2](#0-1) [3](#0-2) 

Two properties combine into the vulnerability:

1. **The cache is never invalidated.** After `share()`/`complete()` consume the machine, the seed remains in the DB. `from_cache` → `AlgorithmMachine::seeded_preprocess` regenerates the *identical* nonces and commitments from the seed deterministically (`ChaCha20Rng::from_seed(*seed.0)`): [4](#0-3) [5](#0-4) 

2. **The documented safety argument is defeated by the persistence.** The file's own header justifies fixed nonces by claiming "Upon any complete rebuild, we'd re-decide nonces" — but the seed lives in `serai_db`, which *survives* rebuilds. After a rebuild onto a distinct chain history (the exact scenario the comment relies on re-randomizing for), `CachedPreprocesses::get` returns the old seed and the node silently reuses nonces: [6](#0-5) 

Concrete stale-reuse paths reachable without any Byzantine behavior:

- **Cross-validator-set reuse.** `DkgConfirmer` attempt counters restart at 0 for each DKG; the context key omits `genesis`/`set`, so a coordinator that participates in a second DKG confirmation at `attempt = 0` reloads the prior set's seed and signs a *different* `set_keys_message` (different `KeyPair`, different `removed`, different signers) with the same `(d, e)` nonces.
- **Re-run `share()` under one attempt.** `generated_key_pair` calls `DkgKeyPair::set` unconditionally and then `share()`; a second invocation under the same attempt with a distinct `key_pair` signs a distinct message reusing the same nonces: [7](#0-6) 

- **Rebuild / re-execution.** `share_internal` is re-executed by `complete()` and after process restarts; any path where finalized inputs differ from the first execution signs with the stale seed — the precise failure mode the header admits is unsafe.

All preprocesses and signature shares are published as tributary `Transaction::DkgShares`/`DkgConfirmed` data, so an unprivileged observer collects `(D_i, E_i, z_i)` tuples.

### Impact Explanation

FROST nonce reuse: each share is `z_i = d_i + e_i·ρ_i + λ_i·c·x_i`. When the same seed-derived `(d_i, e_i)` is reused across `k` sessions with distinct messages/commitment sets (distinct `ρ`, `λ`, `c`), an observer obtains `k` linear equations in three unknowns `(d_i, e_i, x_i)`. Three reused sessions suffice to solve for `x_i` — the validator's MuSig secret share — and fewer may suffice where `ρ` or `λ` coincide (e.g., identical counterparty preprocess sets, which are *also* deterministic since all honest validators run this same caching code). Recovering a validator's signing key share lets the attacker forge DKG confirmations / `set_keys` signatures, i.e., sign messages the validator never intended, potentially authorizing attacker-controlled key sets. This is secret-share recovery, a High-severity impact.

### Likelihood Explanation

Reuse does not require any malicious party: it is triggered by ordinary protocol events — a second DKG confirmation reusing `attempt` indices because `context` omits the set/session binding, a coordinator rebuild (explicitly contemplated by the header comment), or a repeated `generated_key_pair` under one attempt. Every coordinator running this code deterministically reuses its seed in these cases. The only mitigation is the documented-but-false assumption that rebuilds re-decide nonces.

### Recommendation

- Bind the cache key to the full session context: include `spec.genesis()` / `set` / `session` in `context` (e.g., `(b"DkgConfirmer", genesis, attempt)`).
- Delete the entry on consumption: after `share_internal` produces a share for a context, remove the `CachedPreprocesses` row so a re-execution cannot reuse it; store and compare the produced preprocess/commitments instead (the code's own TODO at line 50–54).
- On any state rebuild, regenerate nonces rather than trusting the persisted seed — i.e., store the *published preprocess bytes* (public) keyed by context, and abort/skip signing if the recomputed preprocess would differ, instead of deterministically re-signing.

### Proof of Concept

Conceptual trace (no private inputs needed):

1. Set rotation A: coordinator calls `dkg_confirmation_nonces(key, spec_A, txn, 0)` → seed `S` saved under `CachedPreprocesses[(b"DkgConfirmer", 0)]`; preprocess `P` published; later `generated_key_pair(..., key_pair_A, 0)` produces share `z_A` over `set_keys_message(set_A, removed_A, key_pair_A)` with nonces derived from `S`. All bytes appear on the tributary.
2. Set rotation B (or a rebuild / second `generated_key_pair` call): same coordinator, `attempt = 0`. `CachedPreprocesses::get` hits; `seeded_preprocess(S)` regenerates identical `(d, e)`; `share()` emits `z_B` over the distinct `set_keys_message(set_B, removed_B, key_pair_B)` using the same nonces.
3. After a third such reuse, an observer solves `z_j = d + e·ρ_j + λ_j·c_j·x` for the validator's secret share `x`, recovering the MuSig signing key. [8](#0-7) [9](#0-8)

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be

  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn preprocess_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
  ) -> (AlgorithmSignMachine<Ristretto, Schnorrkel>, [u8; 64]) {
    // Encrypt the cached preprocess as recovery of it will enable recovering the private key
    // While the DB isn't expected to be arbitrarily readable, it isn't a proper secret store and
    // shouldn't be trusted as one
    let mut encryption_key = {
      let mut encryption_key_preimage =
        Zeroizing::new(b"Cached Preprocess Encryption Key".to_vec());
      encryption_key_preimage.extend(self.context.encode());
      let repr = Zeroizing::new(self.key.to_repr());
      encryption_key_preimage.extend(repr.deref());
      Blake2s256::digest(&encryption_key_preimage)
    };
    let encryption_key_slice: &mut [u8] = encryption_key.as_mut();

    let algorithm = Schnorrkel::new(b"substrate");
    let keys: ThresholdKeys<Ristretto> =
      musig(musig_context(self.spec.set().into()), self.key.clone(), participants)
        .expect("signing for a set we aren't in/validator present multiple times")
        .into();

    if CachedPreprocesses::get(self.txn, &self.context).is_none() {
      let (machine, _) =
        AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);

      let mut cache = machine.cache();
      assert_eq!(cache.0.len(), 32);
      #[allow(clippy::needless_range_loop)]
      for b in 0 .. 32 {
        cache.0[b] ^= encryption_key_slice[b];
      }

      CachedPreprocesses::set(self.txn, &self.context, &cache.0);
    }

    let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
    let mut cached: Zeroizing<[u8; 32]> = Zeroizing::new(cached);
    #[allow(clippy::needless_range_loop)]
    for b in 0 .. 32 {
      cached[b] ^= encryption_key_slice[b];
    }
    encryption_key_slice.zeroize();
    let (machine, preprocess) =
      AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));

    (machine, preprocess.serialize().try_into().unwrap())
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

pub fn dkg_confirmation_nonces(
  key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  spec: &TributarySpec,
  txn: &mut impl DbTxn,
  attempt: u32,
) -> [u8; 64] {
  DkgConfirmer::new(key, spec, txn, attempt)
    .expect("getting DKG confirmation nonces for unknown attempt")
    .preprocess()
}

pub fn generated_key_pair<D: Db>(
  txn: &mut D::Transaction<'_>,
  key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  spec: &TributarySpec,
  key_pair: &KeyPair,
  attempt: u32,
) -> Result<[u8; 32], Participant> {
  DkgKeyPair::set(txn, spec.genesis(), attempt, key_pair);
  KeyToDkgAttempt::set(txn, key_pair.0 .0, &attempt);
  let preprocesses = ConfirmationNonces::get(txn, spec.genesis(), attempt).unwrap();
  DkgConfirmer::new(key, spec, txn, attempt)
    .expect("claiming to have generated a key pair for an unrecognized attempt")
    .share(preprocesses, key_pair)
}
