### Title
Re-enabling `protocol.file.allow=always` for submodule updates can let a malicious cloned/fetched repository read arbitrary local files during checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
Similar to the Auction bug — where a value (`auctionMultiplier`/`auctionDecrement`) that should be fixed/snapshotted for the duration of a sensitive operation can instead be freely manipulated to defeat the invariant that protects the operation (`tokensNeeded` staying non-trivial) — GitHub Desktop has a function, `updateSubmodulesAfterOperation`, that accepts a caller-supplied `allowFileProtocol` boolean and, when `true`, re-enables Git's `file://` protocol for submodule fetches via `-c protocol.file.allow=always`, overriding the safe default Git ships since the `protocol.file.allow` hardening (CVE-2022-39253 class of fix) that normally blocks submodules from being satisfied over `file://`.

### Finding Description
`updateSubmodulesAfterOperation` builds its `git submodule update --init --recursive` invocation like this: [1](#0-0) 

When `allowFileProtocol` is `true`, this instructs Git to trust any `.gitmodules` entry with a `url = file://...` (or a relative path Git resolves to a local path) that ships inside a repository the user has cloned or fetched from an untrusted source. Git's own protocol-restriction hardening exists specifically to stop a hostile repository from smuggling a `.gitmodules` submodule URL pointing at an arbitrary local path and having the client silently "clone" that local directory's `.git` contents into the submodule's working tree — which can be used to read files outside the intended repository (a local secrets repo, another checked-out project, etc.) and have their contents end up materialized inside the attacker-observed submodule checkout.

This function is invoked from `checkoutBranch` and `checkoutCommit`, both of which take `allowFileProtocol` as a parameter from their callers and forward it directly into the submodule update call: [2](#0-1) [3](#0-2) 

The invariant this hardening protects — "don't let a possibly-malicious repository's submodule config reach outside the repo boundary onto the local filesystem" — is exactly the kind of guard the Auction report describes being trivially bypassed by simply flipping a controlling parameter (`allowFileProtocol` here, `auctionMultiplier`/`auctionDecrement` there) without validating the trust/state of the object being operated on (an ongoing auction there, an attacker-supplied clone/fetch here).

### Impact Explanation
If `allowFileProtocol=true` is passed for a checkout/branch-switch operation on a repository that was cloned or fetched from an untrusted remote, an attacker who controls that repository's `.gitmodules` can point a submodule URL at an arbitrary local path (including via `file://../../../../some/local/path` traversal patterns Git accepts for local transports) and have Desktop silently populate the submodule directory with contents from outside the intended repository boundary. This is a "file read outside the repo" primitive, and depending on where the read data lands, it may also get staged and later committed/pushed by the user, matching the report's "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitability hinges entirely on whether any caller sets `allowFileProtocol=true` for checkouts performed against an attacker-supplied/untrusted repository (e.g., cloning a hostile repo, checking out a PR branch from a fork, or opening a deep link that triggers `openBranchNameFromUrl`/`openPullRequestFromUrl` in `dispatcher.ts`, which call into checkout flows). I found 8 references to `allowFileProtocol` in `app-store.ts` and 6 in `dispatcher.ts` but ran out of tool budget before reading each call site to confirm under what precise conditions (e.g., "is this the user's own local submodule that's already trusted" vs. "attacker-controlled fork/PR checkout") the flag is set to `true`. **This is the key unresolved question** — if it is only ever set `true` for submodules the user has already trusted/initialized locally, the path is not exploitable by a remote attacker; if it can be `true` for a first-time checkout of an untrusted cloned/forked repo, the analog is live.

### Recommendation
- Audit every call site in `app-store.ts` and `dispatcher.ts` that passes `allowFileProtocol=true` into `checkoutBranch`/`checkoutCommit`, and ensure it is never set for repositories/branches originating from an unverified clone, fork, or PR checkout flow reachable via `openBranchNameFromUrl` / `openPullRequestFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`.
- Prefer to only allow `file://` submodule resolution when the submodule path/URL has already been reviewed or matches a previously-trusted configuration, rather than trusting a boolean threaded through several layers of call stack.
- Consider not overriding `protocol.file.allow` at all for submodule updates triggered by remote-originated content (fetch/clone/checkout of foreign branches), deferring instead to Git's own default protections.

### Proof of Concept
Conceptual PoC (dependent on confirming a reachable `allowFileProtocol=true` call site for untrusted checkouts):
1. Attacker publishes a public repository with a `.gitmodules` file containing:
```
[submodule "evil"]
  path = evil
  url = file:///some/local/path/leaked-repo
```
2. Victim opens a GitHub Desktop deep link or clones/checks out this repository (or a PR branch from it) through a code path that ends up calling `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive` [4](#0-3) , which resolves the `file://` URL and populates the `evil` directory with the contents of the local path, exposing file contents outside the cloned repository's boundary into the victim's working tree.

**Caveat**: I could not verify, within the available tool budget, the exact conditions under which callers in `app-store.ts`/`dispatcher.ts` set `allowFileProtocol=true`. If it turns out this flag is only ever enabled for submodules the user has already explicitly configured/trusted locally (not reachable from a first-time clone/fetch/checkout of attacker content), this finding would not meet the "unprivileged, attacker controls a cloned/fetched repository" bar and should be downgraded to informational. A Devin session with full file access should trace all `allowFileProtocol` call sites in `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts` to confirm reachability from untrusted input before treating this as confirmed.
