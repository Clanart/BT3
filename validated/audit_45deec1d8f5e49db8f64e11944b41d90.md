Based on the code I traced, the closest legitimate GitHub Desktop analog to the DeFi report's core defect — *"a value is computed/mutated in one place but a dependent piece of state elsewhere is never reconciled to match, so the two silently diverge"* — is an index-desynchronization bug between diff-hunk expansion and per-line commit selection, that can silently corrupt what a user commits.

### Title
Line-selection state is not remapped after hunk expansion, causing silent corruption of partial commits - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
GitHub Desktop lets a user selectively stage/commit individual diff lines via `DiffSelection`, which stores selection state as a `Set<number>` of **absolute line indices** into the current diff [1](#0-0) . Independently, the diff-expansion feature ("Expand Up"/"Expand Down"/"Expand whole file") mutates the diff by inserting new context lines and re-indexing every hunk after the expansion point [2](#0-1) . The expansion path never touches or remaps the existing `DiffSelection`, so old absolute indices stay valid syntactically but now point at different, shifted lines.

### Finding Description
Selection state and diff-line addressing are two independently mutated values that must stay reconciled, and nothing enforces that:

- `isSelected(lineIndex)` and `withLineSelection(lineIndex, selected)` operate purely on raw line-number keys with no knowledge of the diff structure [3](#0-2) .
- When a hunk is expanded, hunks located after the expansion point get their `unifiedDiffStart`/`unifiedDiffEnd` shifted forward by `numberOfNewDiffLines`, and merged hunks get entirely new line arrays [4](#0-3) .
- The UI's expansion handler only swaps in the new diff into component state — it does not recompute or shift the `WorkingDirectoryFileChange.selection` that the parent maintains: `this.setState({ diff: updatedDiff })` [5](#0-4) .
- Line checkbox toggles record their selection using the currently-computed absolute index (`getDiffLineNumber`) via `onLineNumberCheckedChanged` [6](#0-5) , meaning any selection made *before* an expansion is keyed to indices that later shift out from under it.
- At commit time, `formatPatch` blindly trusts `file.selection.isSelected(absoluteIndex)` against the (now expanded/re-indexed) hunk lines to decide which lines go into the generated patch that is `git apply --cached`'d into the index [7](#0-6) [8](#0-7) .

So the sequence: (1) user partially deselects/selects specific lines in a hunk for a partial commit, (2) user expands a preceding hunk (adds context lines, shifting later hunks), (3) user commits — the selection is silently applied to the wrong lines because the index basis moved but the recorded selection did not. No error, warning, or diff-preview mismatch is guaranteed to stop this, because the currently rendered checkbox states derive from `isSelected(newAbsoluteIndex)` which will just report a different (wrong) answer for the shifted lines rather than failing.

### Impact Explanation
This is a "silent corruption of what the user commits" scenario: a user could unintentionally commit a line they explicitly excluded (e.g., a secret, credential, or debug statement they meant to keep out of history) or fail to commit a line they intended to include, all without any visible indication that the commit doesn't match their reviewed intent. Impact is Medium — it does not grant remote code execution or credential exfiltration by itself, but it can leak sensitive data into a permanent commit/push and corrupt repository history silently.

### Likelihood Explanation
Likelihood is Medium: the diff-expansion feature and partial line-selection ("stage this hunk"/"discard this line") are both standard, unprivileged, user-facing features that are commonly combined when reviewing large diffs before committing — no attacker-controlled repo content, admin rights, or unusual steps are needed beyond normal UI usage of expanding context and then adjusting checkboxes.

### Recommendation
When a hunk is expanded or merged (`expandTextDiffHunk`/`mergeDiffHunks`/`expandWholeTextDiff`), remap the associated `DiffSelection`'s diverging-line indices in lockstep with the index shift applied to hunks (i.e., shift all diverging line numbers ≥ the mutation point by the same `numberOfNewDiffLines` delta), or refactor `DiffSelection` to key off a stable identifier (e.g., original file line number) instead of diff-relative absolute indices that are invalidated by structural diff mutations like expansion/merging.

### Proof of Concept
1. Modify a file to produce a diff with at least two separated hunks (so a gap/dummy hunk exists between them), producing e.g. hunk A (lines 1–20) and hunk B (lines 100–200) as in `text-diff-expansion-test.ts` [9](#0-8) .
2. In the Desktop diff viewer, deselect one specific line in hunk B for exclusion from the commit (recorded as `divergingLines.has(absoluteIndexOfThatLine)`).
3. Click "Expand" on hunk A (or a gap above hunk B) to pull in context lines — this shifts hunk B's `unifiedDiffStart`/`unifiedDiffEnd` forward by `numberOfNewDiffLines` [10](#0-9)  without touching the file's `DiffSelection`.
4. Commit. `formatPatch` now evaluates `file.selection.isSelected(absoluteIndex)` against the new, shifted hunk-B line layout [7](#0-6) , so the deselected index now lands on a different line than the one the user intended to exclude — that unintended line is silently included in (or excluded from) the resulting patch applied via `git apply --cached` [8](#0-7) .

Note: I was not able to fully trace `app/src/lib/stores/app-store.ts`'s single `withSelectableLines` usage in the time available, which could plausibly be a place where selection is partially reconciled with selectable-line changes; I could not confirm whether it also handles the expansion-shift scenario described above. If it does perform remapping tied to expansion, this would mitigate (but the code inspected in `text-diff-expansion.ts`/`side-by-side-diff.tsx` shows no such remapping at the expansion call site itself).

      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {

        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`

async function prepareDiff(
  numberOfLines: number,
  linesChanged: ReadonlyArray<number>
): Promise<ITestDiffInfo> {
  const textLines = [...Array(numberOfLines).keys()].map(value =>
    value.toString()
  )
  const originalContents = textLines.join('\n')
  for (const line of linesChanged) {
    textLines.splice(line, 0, 'added line')
  }
  const modifiedContents = textLines.join('\n')

  const contentFolderPathPrefix = path.join(
    os.tmpdir(),
    'text-diff-expansion-test'
  )
  const contentFolderPath = await mkdtemp(contentFolderPathPrefix)

  await writeFile(path.join(contentFolderPath, 'original'), originalContents)
  await writeFile(path.join(contentFolderPath, 'changed'), modifiedContents)

  // Generate diff with 3 lines of context
  const result = await exec(
    [
      'diff',
      '-U3',
      path.join(contentFolderPath, 'original'),
      path.join(contentFolderPath, 'changed'),
    ],
    contentFolderPath
  )

  const parser = new DiffParser()
  const diff = parser.parse(result.stdout)
  const textDiff: ITextDiff = {
    kind: DiffType.Text,
    text: diff.contents,
    hunks: diff.hunks,
    maxLineNumber: diff.maxLineNumber,
    hasHiddenBidiChars: diff.hasHiddenBidiChars,
  }

  const resultDiff = getTextDiffWithBottomDummyHunk(
    textDiff,
    textDiff.hunks,
    numberOfLines,
    numberOfLines + linesChanged.length
  )

  return {
    textDiff: resultDiff ?? textDiff,
    newContentLines: textLines,
  }
}
