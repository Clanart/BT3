### Title
OP_RETURN data output excluded from fee/weight estimation, producing transactions below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds an `OP_RETURN` output carrying up to 80 bytes of externally supplied data to `tx_outs`, but computes `needed_fee` via `calculate_weight_vbytes`, which only accounts for `payments` and `change`. The data output's ~90+ vbytes are never included in the weight estimate, so the actual fee rate of the signed transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE`, making the transaction unbroadcastable and the inputs effectively locked — the same "funds received/held but not spendable" class as USDC locked in `JUSDBank`.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` before the fee is computed:

```rust
// networks/bitcoin/src/wallet/send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

But `calculate_weight_vbytes` builds its template transaction only from `payments` and an optional `change` output — the `data`/`OP_RETURN` output is never modeled (send.rs:85-99). The same omission occurs in the change path at send.rs:225-227. `data` is attacker-controlled bytes arriving via `InInstruction` (up to 80 bytes, checked at send.rs:171-173), i.e., a public input reaching this code path.

### Impact Explanation
With an 80-byte `OP_RETURN`, the real transaction is ~90+ vbytes larger than estimated. The `TooLowFee` check (send.rs:211-213) validates `needed_fee` against the underestimated vbytes, so it passes even though the actual fee rate can drop below `bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE`. The resulting signed transaction commits to its outputs via `Prevouts::All` sighash (send.rs:375, 386), so it cannot be amended — a Bitcoin node will reject it from relay/mempool, leaving the UTXOs unspendable through this transaction. This mirrors the report's impact: value is credited to a context (here, committed inside a transaction) from which it cannot actually be moved.

### Likelihood Explanation
Any user who attaches a large `InInstruction` payload triggers the underestimate. Whether the transaction actually falls under the relay minimum depends on `fee_per_vbyte` (at 1 sat/vB it does) and the change-margin. Even when relayable, the transaction systematically pays a lower fee rate than requested, degrading confirmation and potentially stalling under mempool pressure.

### Recommendation
Include the `OP_RETURN` output in the template transaction inside `calculate_weight_vbytes` (pass `data` or the already-built `tx_outs` into both call sites at send.rs:204 and send.rs:225), so `needed_fee` and `fee_with_change` reflect the true transaction weight. Re-run the `TooLowFee` and `NotEnoughFunds` checks against the corrected vbytes.

### Proof of Concept
1. Construct `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), 1)`.
2. The OP_RETURN adds ~91 serialized bytes (~91 vbytes) that `calculate_weight_vbytes` never counts; `needed_fee` = `vbytes_without_opreturn`.
3. `fee()` (actual: `sum(inputs) - sum(outputs)`) equals `needed_fee`, so actual fee rate ≈ `needed_fee / (vbytes + ~91)` < 1 sat/vB for typical sizes, while the `TooLowFee` guard passed against the smaller estimate.
4. `txid()`/sighash commit to all outputs, so the signed transaction is fixed; broadcasting yields a `min relay fee not met` rejection and the consumed `ReceivedOutput`s cannot be spent by this transaction — locked funds reachable from attacker-controlled `data` bytes.
