### Title
Unbounded `VestingPeriods` loop in `PeriodicVestingAccount.GetVestedCoins`/`GetVestingCoins` allows gas-griefing / permanent fee-payment DoS - ([File: sei-cosmos/x/auth/vesting/types/vesting_account.go])

### Summary
The reported pSTAKE bug is a class of "reward/vesting schedule history keeps growing, and a single state-changing call must iterate the *entire* history, so gas cost grows unboundedly and the operation can eventually run out of gas." The same shape exists in `sei-cosmos`'s vesting-account implementation: `PeriodicVestingAccount` stores an attacker/user-controlled `VestingPeriods` array, and `GetVestedCoins`/`GetVestingCoins` iterate the *whole* array on every call, exactly like `STokensV2._calculatePendingRewards` iterates every `_rewardRate` change.

### Finding Description
`PeriodicVestingAccount.GetVestedCoins` walks every entry in `pva.VestingPeriods` until it finds the period that has not yet elapsed: [1](#0-0) 

`GetVestingCoins`/`LockedCoins` call this same loop: [2](#0-1) 

`LockedCoins` (and thus `SpendableCoins`) is the function the `x/bank` `ViewKeeper` uses to determine how much of an account's balance is transferable, as documented for this exact vesting design: [3](#0-2) 

The `VestingPeriods` array is populated once at account-creation time from `MsgCreatePeriodicVestingAccount` (handled by `sei-cosmos/x/auth/vesting/msg_server.go`), which is a normal, permissionless transaction any account can submit — there is no cap on the number of `Period` entries beyond raw transaction/block size limits. Because each `Period` only needs a `Length` (int64) and an `Amount` (`sdk.Coins`), an attacker can pack a very large number of periods into a single transaction, cheaply, well within normal tx-size limits.

Once such an account exists, every subsequent operation that needs to know the account's spendable balance — bank sends, and (in the standard Cosmos SDK ante-handler pipeline) fee deduction for *every single transaction the account ever submits* — calls `LockedCoins`/`SpendableCoins`, which re-walks the full, unbounded `VestingPeriods` slice. This mirrors the pSTAKE `_calculatePendingRewards` bug precisely: a value that grows over time (rate-change history vs. vesting-period count) is fully re-scanned on every subsequent operation instead of using an O(1) or O(log n) cumulative/indexed structure.

### Impact Explanation
If the number of periods is large enough, the gas consumed by this loop alone can approach or exceed the gas available for ordinary operations (fee deduction in ante handling, bank sends, EVM value-transfer balance checks through the usei/wei StateDB bridge for the Sei-associated address). This can:
- Make sending funds from (or to, depending on account-creation semantics) the affected account prohibitively expensive.
- In the worst case, make every future transaction from that account fail with an out-of-gas condition during fee deduction, permanently freezing the funds held in that account, since no transaction from it can ever complete.

This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is High for self-inflicted misconfiguration (a user who creates their own periodic vesting account with an excessive period count bricks their own future transactions), and Medium for a griefing scenario where an attacker targets a not-yet-used address (e.g., a freshly generated / not-yet-associated Sei address) before its owner's first transaction, since account-creation for vesting accounts is typically only permitted against non-existent or plain base accounts. The exact ante-handler code path that reads `SpendableCoins`/`LockedCoins` for fee deduction was not independently re-verified line-by-line in this session (it follows the standard, well-known Cosmos SDK `DeductFeeDecorator` pattern using `bankKeeper.SpendableCoins`), so this should be confirmed against the actual `x/auth/ante` code in the repository before treating the fee-deduction DoS path as certain.

### Recommendation
- Cap the number of vesting periods allowed in `MsgCreatePeriodicVestingAccount.ValidateBasic()` (and/or reject creation above a configurable maximum), similar to how `MaxEntries` bounds unbonding/redelegation entries in `x/staking`.
- Alternatively, replace the linear scan in `GetVestedCoins`/`GetVestingCoins` with a precomputed cumulative-vesting-amount index (sorted by elapsed time) and binary search, so the cost per call is O(log n) rather than O(n) — the same fix pSTAKE applied for their reward-rate history.
- Add a gas-metered/iteration-count safety cap inside the loop itself so a single call cannot exceed a bounded amount of work regardless of how the account was created (defense in depth for any account created before the cap was enforced).

### Proof of Concept
1. Attacker (or a careless user) submits `MsgCreatePeriodicVestingAccount` targeting a fresh `ToAddress`, with `VestingPeriods` containing N (e.g., tens of thousands) entries, each with `Length: 1` and a minimal `Amount`. The message validates because there is no upper bound on period count (`sei-cosmos/x/auth/vesting/types/vesting_account.go` `Validate()`/`NewPeriodicVestingAccount` only checks that lengths/amounts are individually well formed).
2. The account `ToAddress` is now a `PeriodicVestingAccount` with N periods in state.
3. Any subsequent transaction sourced from `ToAddress` (a bank send, or a fee-paying transaction routed through the standard ante fee-deduction path, or an EVM transaction from its associated address) triggers `LockedCoins`/`SpendableCoins`, which iterates the full N-length `VestingPeriods` slice on every call.
4. As N grows, the gas cost of this iteration grows linearly; past a threshold it can exceed the gas budget available to the surrounding operation, causing the transaction (including fee deduction itself) to fail with an out-of-gas error — permanently preventing that account from transacting.

func (pva PeriodicVestingAccount) GetVestedCoins(blockTime time.Time) sdk.Coins {
	var vestedCoins sdk.Coins

	// We must handle the case where the start time for a vesting account has
	// been set into the future or when the start of the chain is not exactly
	// known.
	if blockTime.Unix() <= pva.StartTime {
		return vestedCoins
	} else if blockTime.Unix() >= pva.EndTime {
		return pva.OriginalVesting
	}

	// track the start time of the next period
	currentPeriodStartTime := pva.StartTime

	// for each period, if the period is over, add those coins as vested and check the next period.
	for _, period := range pva.VestingPeriods {
		x := blockTime.Unix() - currentPeriodStartTime
		if x < period.Length {
			break
		}

		vestedCoins = vestedCoins.Add(period.Amount...)

		// update the start time of the next period
		currentPeriodStartTime += period.Length
	}

	return vestedCoins
}

// GetVestingCoins returns the total number of vesting coins. If no coins are
// vesting, nil is returned.
func (pva PeriodicVestingAccount) GetVestingCoins(blockTime time.Time) sdk.Coins {
	return pva.OriginalVesting.Sub(pva.GetVestedCoins(blockTime))
}

// LockedCoins returns the set of coins that are not spendable (i.e. locked),
// defined as the vesting coins that are not delegated.
func (pva PeriodicVestingAccount) LockedCoins(blockTime time.Time) sdk.Coins {
	return pva.LockedCoinsFromVesting(pva.GetVestingCoins(blockTime))
}

### Transferring/Sending

At any given time, a vesting account may transfer: `min((BC + DV) - V, BC)`.

In other words, a vesting account may transfer the minimum of the base account
balance and the base account balance plus the number of currently delegated
vesting coins less the number of coins vested so far.

However, given that account balances are tracked via the `x/bank` module and that
we want to avoid loading the entire account balance, we can instead determine
the locked balance, which can be defined as `max(V - DV, 0)`, and infer the
spendable balance from that.

```go
func (va VestingAccount) LockedCoins(t Time) Coins {
   return max(va.GetVestingCoins(t) - va.DelegatedVesting, 0)
}
```

The `x/bank` `ViewKeeper` can then provide APIs to determine locked and spendable
coins for any account:

```go
func (k Keeper) LockedCoins(ctx Context, addr AccAddress) Coins {
    acc := k.GetAccount(ctx, addr)
    if acc != nil {
        if acc.IsVesting() {
            return acc.LockedCoins(ctx.BlockTime())
        }
    }

    // non-vesting accounts do not have any locked coins
    return NewCoins()
}
