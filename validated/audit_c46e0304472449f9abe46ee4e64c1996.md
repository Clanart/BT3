### Title
Missing zero-length guard in `_upb_mapsorter_cmpstr` map-key comparator during deterministic serialization - (File: `upb/message/map_sorter.c`)

### Summary
CVE-2018-18066 is a NULL-pointer dereference in Net-SNMP's `snmp_oid_compare`, which computes a `memcmp`-style comparison over two length-prefixed buffers without first checking for a zero/absent buffer before dereferencing it, reachable from untrusted network input. The closest structural analog in this checkout is the upb map-key string comparator used when serializing a `map<string,...>` or `map<bytes,...>` field deterministically: `_upb_mapsorter_cmpstr` in [1](#0-0)  calls `memcmp(a.data, b.data, common_size)` unconditionally, whereas the sibling equality routine `upb_StringView_IsEqual` explicitly guards the zero-length case (`!a.size || !memcmp(...)`) before touching the pointers, at [2](#0-1) . The related `upb_StringView_Compare` helper has the identical unguarded pattern at [3](#0-2) .

### Finding Description
`_upb_mapsorter_cmpstr` is the `qsort` comparator selected for `kUpb_FieldType_String`/`kUpb_FieldType_Bytes` map keys in the `compar[]` table, invoked from `_upb_mapsorter_pushmap` whenever a message containing a string/bytes-keyed map is serialized with the deterministic-output option (`upb_Encode` deterministic flag, exposed through Ruby/PHP/Python `SerializeToString(deterministic=True)` and C++'s `SetSingleLineMode`/`set_deterministic`) — a supported public serialization API, not a privileged or internal one. [1](#0-0) 

The comparator derives `upb_StringView a, b` for the two map keys via `_upb_mapsorter_getkeys`/`_upb_map_fromkey` and immediately calls `memcmp(a.data, b.data, common_size)` where `common_size = UPB_MIN(a.size, b.size)`, with no check that `common_size` (or either individual `size`) is non-zero before dereferencing `data`. [4](#0-3) 

The transferred invariant from the CVE is: "never dereference/compare an attacker-influenced pointer-plus-length pair without checking that the length is non-zero / the pointer is valid first." upb's own codebase already codifies this invariant for the equality path — `upb_StringView_IsEqual` short-circuits with `!a.size ||` before calling `memcmp` — but the map-key sort comparator and `upb_StringView_Compare` omit it. This is exactly the missing-check pattern described in the report: a comparison routine that skips the same zero-length guard its sibling routine already has.

Whether this is exploitable depends on whether an empty string/bytes map key can have a `NULL` `data` pointer in this backend. upb commonly represents an "unset"/default string as `{NULL, 0}`; a map key equal to the empty string ("") is the default proto3 key value and, if constructed via that default-value path rather than through arena-copied wire bytes, could plausibly carry a `NULL` data pointer with `size == 0`.

### Impact Explanation
If reachable, this would be a Denial-of-Service via `memcmp(NULL, NULL, 0)` (or `NULL, non-NULL, 0`) during deterministic serialization of an attacker-influenced message containing a map with an empty string/bytes key. This mirrors CVE-2018-18066's impact class (crash via NULL-pointer arithmetic in a comparator, not memory corruption or RCE).

However, I could not confirm an actual crash: passing a `NULL` pointer to `memcmp` with `size == 0` is technically undefined behavior per the C standard, but virtually all mainstream libc implementations (glibc, musl, Bionic, MSVCRT) short-circuit on `n == 0` before dereferencing the pointers, so this would not crash in practice on typical production platforms — it would only be caught by UBSan/ASan-style pointer-provenance checks, not as a genuine runtime fault. I was not able to run the code or a sanitizer in this environment to verify either the NULL-data-pointer precondition or an actual crash, so this cannot be confirmed as a live, remotely triggerable DoS with the same certainty as the Net-SNMP CVE (which had a demonstrated crash on real input).

### Likelihood Explanation
Low-to-Medium. The comparator is reachable only when (a) the trusted schema defines a `map<string,...>` or `map<bytes,...>` field, (b) the application explicitly opts into deterministic serialization, and (c) at least one map entry has an empty-string/bytes key whose `upb_StringView.data` is `NULL` rather than a valid (even zero-length) pointer into the arena/input buffer. Condition (c) is unverified in this pass.

### Recommendation
Add the same zero-length short-circuit used in `upb_StringView_IsEqual` to both `_upb_mapsorter_cmpstr` and `upb_StringView_Compare`, e.g. skip the `memcmp` call entirely when `common_size == 0`, so pointer validity is never assumed for empty buffers:
```c
size_t common_size = UPB_MIN(a.size, b.size);
int cmp = common_size ? memcmp(a.data, b.data, common_size) : 0;
```
This closes the invariant gap even if current libc behavior masks it, and eliminates the UB flagged by sanitizers.

static int _upb_mapsorter_cmpstr(const void* _a, const void* _b) {
  upb_StringView a, b;
  _upb_mapsorter_getkeys(_a, _b, &a, &b, UPB_MAPTYPE_STRING);

UPB_INLINE int upb_StringView_Compare(upb_StringView a, upb_StringView b) {
  int result = memcmp(a.data, b.data, UPB_MIN(a.size, b.size));
  if (result != 0) return result;
  if (a.size < b.size) {
    return -1;
  } else if (a.size > b.size) {
    return 1;
  } else {
    return 0;
