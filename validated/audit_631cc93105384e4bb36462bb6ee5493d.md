### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any token/native balance temporarily held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated function that executes arbitrary `Call[]` with the `CallDispatcher` contract itself as `msg.sender`/caller identity — directly analogous to `safeFunctionCall`'s core flaw: *"since the caller to the approved target is `address(this)`, any special privilege [or balance] granted to this consumer contract can be accessed by anyone using this function."* Here `address(this)` is the shared, singleton `CallDispatcher`, and any token or native balance it transiently holds (by design, per the documented "the dispatcher contract holds tokens temporarily during execution") can be swept by anyone who calls `dispatch()` directly, not just by the legitimate `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` flow that deposited the funds.

### Finding Description
`CallDispatcher.dispatch` has no access-control modifier at all: [1](#0-0) 

It performs raw `to.call{value: call.value}(call.data)` for each entry in an attacker-supplied `Call[]`, so any address can invoke it with arbitrary `to`/`data`/`value`.

This contract is not a per-call ephemeral helper — it is a shared, canonically-deployed singleton referenced across product lines: `HyperFungibleToken`/`WrappedHyperFungibleToken` mint/unlock tokens "to the `CallDispatcher` address" so it can spend them, and `IntentGatewayV2`/`IntentsBase` routes both predispatch and postdispatch order execution through the same `_params.dispatcher` address: [2](#0-1) 

The documentation itself confirms the balance-holding window that the flaw exploits: *"the dispatcher contract holds tokens temporarily during execution"* and *"any tokens remaining in the `CallDispatcher` are swept back to the gateway."* The sweep is a separate, later step performed by `_execute` only after `dispatch()` returns: [3](#0-2) 

Because `dispatch()` itself is a first-class, unauthenticated public entrypoint on the shared contract, any account can call it directly at any moment the dispatcher holds a nonzero balance — whether that balance results from an in-flight legitimate order/mint (window between token delivery to the dispatcher and the subsequent sweep-back), an ERC20/ERC777 with transfer hooks leaving unswept dust, or any stray direct transfer to the dispatcher address (which is a known, published address per the docs' "contract addresses" listing). The attacker's `Call` simply targets the resident token and calls `transfer(attacker, balance)`; since `dispatch` executes it as `msg.sender == CallDispatcher`, the token contract sees the CallDispatcher itself authorizing the transfer.

Existing guards do not stop this:
- There is no `onlyOwner`/`onlyGateway`/`onlyHost` restriction on `dispatch()`.
- There is no reentrancy guard, so `dispatch()` can even be re-entered mid-execution of a legitimate order's output calls (e.g., via a malicious/hooked output token) to drain funds before the caller's own sweep step runs.
- The sweep in `_execute` only runs *after* `dispatch()` returns, so any balance present at any earlier moment is unprotected.

### Impact Explanation
This directly matches the bounty's fund-theft/unauthorized-execution class: an unprivileged, non-relayer/non-prover attacker can steal tokens or native value that legitimately belong to bridge users, solvers, or the protocol dust pool, simply by racing or reentering the shared `CallDispatcher`. Since the dispatcher is reused across `HyperFungibleToken` mint/unlock flows and `IntentGatewayV2` order fills, the blast radius spans multiple product surfaces sharing one contract instance.

### Likelihood Explanation
The attack requires only observing/timing calls to a well-known, publicly-listed contract address and crafting an ABI-encoded `Call[]` — no privileged role, relayer collusion, or malicious prover is needed, satisfying the impact gate's "unprivileged attacker" requirement. The reentrant variant (hooked/callback-capable output token in an order's `output.assets`) requires no race at all — it deterministically fires within the same transaction as `_execute`, before the legitimate sweep executes.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be invoked by an authorized, per-call context — e.g., deploy a fresh minimal-proxy/ephemeral dispatcher per invocation (so no persistent shared balance ever exists), or require `dispatch()` to be called only via a trusted caller allowlist (`onlyGateway`/`onlyHFT`) combined with a reentrancy guard, and ensure no token/native balance is ever left resident on the shared contract between transactions or across reentrant calls within one.

### Proof of Concept
1. Any legitimate flow delivers ERC20 tokens to the shared `CallDispatcher` address before/while `dispatch()` executes (per docs: HFT mint "to the `CallDispatcher` address," or `IntentsBase._execute` at `evm/src/apps/intentsv2/IntentsBase.sol:438-443`).
2. Attacker deploys no contracts; they simply call `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls[0] = Call({ to: <token>, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, tokenBalanceOfDispatcher) })`.
3. `CallDispatcher.dispatch` (evm/src/utils/CallDispatcher.sol:44-61) executes `to.call(data)` unconditionally — the token contract observes `msg.sender == CallDispatcher` and transfers its entire resident balance to the attacker.
4. Alternatively, if an order's `output.assets` includes a token with a transfer/callback hook, the hook re-enters `CallDispatcher.dispatch()` with the attacker's own `Call[]` during the legitimate `_execute` call (`evm/src/apps/intentsv2/IntentsBase.sol:438-442`), draining the dispatcher's balance before the sweep at lines 444-480 runs.
