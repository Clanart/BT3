### Title
Duplicate fund creation via non-atomic `on_accept` failure in `hyper-fungible-token` module - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The ISMP request handler treats a module's `on_accept` failure as "never delivered" (it deletes the request receipt so the request becomes eligible for a timeout-triggered refund on the source chain), but it does **not** roll back any state mutations the module already performed before failing. The `hyper-fungible-token` pallet's `on_accept` implementation mints/transfers the bridged amount to the beneficiary *before* executing an optional attached call, and only fails afterward if that call fails. This lets an attacker mint funds on the destination and later collect a full refund of the escrowed amount on the source via the timeout path — a duplicate/double-spend of the same value, with no malicious relayer, prover, or validator required.

### Finding Description
`modules/ismp/core/src/handlers/request.rs` dispatches each `PostRequest` to its module with: [1](#0-0) 

Receipt handling is per-request and non-atomic at the batch/extrinsic level: the receipt is stored before `cb.on_accept(...)` runs (reentrancy guard), and if `on_accept` returns `Err`, the receipt is **deleted** so the request "can be timed out." Crucially, the individual `Result` is captured into a `Vec` (`.collect::<Vec<_>>()`) rather than propagated with `?`, so a failing `on_accept` does not abort/roll back the whole extrinsic — any storage writes `on_accept` already performed before erroring persist.

`hyper-fungible-token`'s `on_accept` performs the value-moving mint/transfer *before* the optional-calldata dispatch step that can fail: [2](#0-1) [3](#0-2) 

If the attacker crafts a `PostRequest.body` whose `message.data` decodes to a `SubstrateCalldata` that fails signature verification, decoding, filtering, or dispatch (e.g. `HftError::SignatureVerificationFailed`, `HftError::RuntimeCallDecodeError`, `HftError::CallFiltered`, `HftError::CallDispatchError`), the function returns `Err` *after* the mint/transfer to the beneficiary has already executed and persisted (since request.rs does not roll it back).

Because `on_accept` failed, `request.rs` deletes the request receipt for that commitment. Later, once the timeout window elapses, anyone can submit a legitimate non-membership proof for that (now genuinely absent) receipt via the timeout handler: [4](#0-3) 

This triggers the source-side `on_timeout`, which refunds the escrowed amount back to the original sender: [5](#0-4) 

Net effect: the beneficiary already received the minted/transferred funds on the destination chain (step 1), and the original sender receives a full refund of the same escrowed amount on the source chain (step 2) — the value exists twice.

### Impact Explanation
This is a direct "stealing or loss of funds" / "double-claim/double-settlement" primitive as defined by the bounty scope: a single bridged transfer results in funds being credited on the destination *and* refunded on the source, doubling the attacker-controlled value out of the bridge's/pallet's escrow. No relayer, prover, validator, or admin compromise is needed — the attacker only needs to control the content of their own outgoing `PostRequest` (the optional calldata field), which is a normal user-facing capability of the `hyper-fungible-token` message format.

### Likelihood Explanation
High. Constructing a `PostRequest` with a valid `Message` (amount, recipient) plus a deliberately failing `SubstrateCalldata` payload (e.g., wrong nonce/signature, or a `RuntimeCall` that the `BaseCallFilter` rejects) is entirely within an ordinary user's control and requires no privileged position, front-running, or off-chain collusion. The relayer only needs to deliver the message honestly, and later, submit (or have anyone submit) the routine timeout proof — both are normal protocol operations.

### Recommendation
- Make module dispatch atomic per-request: wrap the call to `cb.on_accept(...)` (and `on_timeout`/`on_response`) in a storage transaction (e.g. `frame_support::storage::with_transaction`) so that any state changes made before an internal failure are rolled back together with the failure, before deciding whether to delete the receipt.
- Alternatively, redesign `hyper-fungible-token::on_accept` so that the value-moving mint/transfer is the last fallible operation, performed only after all calldata validation/decoding has succeeded, mirroring the "verify effects before commit" pattern to avoid partial completion on error.
- Audit all other `IsmpModule::on_accept`/`on_timeout`/`on_response` implementations for the same "irreversible effect before possible failure" ordering, since the router-level per-request result is not extrinsic-atomic anywhere in `request.rs`/`timeout.rs`.

### Proof of Concept
1. Attacker on the source chain dispatches a `PostRequest` to `hyper-fungible-token` bridging amount `X` to `beneficiary`, with `message.data` set to a non-empty `SubstrateCalldata` containing a syntactically valid but intentionally-invalid signature (any `MultiSignature::Ed25519`/`Sr25519`/`Ecdsa` variant whose signature does not verify against `beneficiary`).
2. On delivery, `Pallet::on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:93-117`) executes the mint/transfer of `X` to `beneficiary` successfully.
3. Continuing in the same call, signature verification fails (`HftError::SignatureVerificationFailed`, line ~150), and `on_accept` returns `Err`.
4. `modules/ismp/core/src/handlers/request.rs:123-124` deletes the request receipt because the callback failed; the extrinsic still succeeds overall (result collected into a `Vec`, not propagated), so the mint/transfer from step 2 is **not** rolled back.
5. After the request's `timeout_timestamp` elapses, anyone submits a `PostRequestTimeoutMessage` with a genuine non-membership proof of the (deleted) receipt (`modules/ismp/core/src/handlers/timeout.rs:69-88`).
6. The timeout dispatches to the source-side `on_timeout` (`modules/pallets/hyper-fungible-token/src/module.rs:218-292`), which refunds escrowed amount `X` back to the original sender.
7. Result: `beneficiary` holds the minted `X` on the destination chain, and the original sender is refunded `X` on the source chain — the same value has been created twice from a single bridged transfer.
