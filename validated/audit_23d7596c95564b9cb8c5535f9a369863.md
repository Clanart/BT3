### Title
Deterministic CachedPreprocess reuse in `DkgConfirmer` signs distinct messages with identical FROST nonces — secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives the signing machine from a deterministic `CachedPreprocess` seed stored under `context = (b"DkgConfirmer", attempt)`. The cache is never deleted, and every `share()`/`complete()` call for the same `attempt` reconstructs the same machine with the same nonces via `from_cache` → `seeded_preprocess`. The message signed depends on the externally supplied `key_pair` (`set_keys_message(set, removed, key_pair)`), which is not part of the cache context. Two `share` invocations in the same DKG attempt for two different `key_pair`s therefore produce two Schnorr signature shares under an identical nonce over different challenges, allowing recovery of the confirmer's MuSig/FROST secret share — and with it, the validator key — by anyone observing the two shares.

### Finding Description
In `preprocess_internal`, the 32-byte RNG seed is fetched (or created) once per `context` and reused on every subsequent call for that context; there is no deletion or attempt-rotation after a share is produced:

- `coordinator/src/tributary/signing_protocol.rs:123-145` — `CachedPreprocesses::get(context)`; `from_cache(algorithm, keys, CachedPreprocess(cached))` reconstructs the identical machine.
- `coordinator/src/tributary/signing_protocol.rs:274-276` — `context = (b"DkgConfirmer", self.attempt)`; the `key_pair`/message is absent from the key.
- `coordinator/src/tributary/signing_protocol.rs:296-301` — `share_internal` signs `set_keys_message(&self.spec.set(), &removed, key_pair)`; `key_pair` is caller-supplied and can differ between calls at the same `attempt`.
- `crypto/frost/src/sign.rs:268-274` — `from_cache` → `seeded_preprocess` regenerates nonces deterministically from the seed.
- `crypto/frost/src/sign.rs:84-87` and `spec/cryptography/FROST.md:51-54` — the code itself documents that reusing a preprocess "will enable third-party recovery of your private key share".

Additionally, `complete()` (lines 312-327) re-runs `share_internal`, again reusing the same nonces; that specific re-use is harmless only because it re-signs the identical message.

The root cause mirrors the advisory's class: attacker-influenced persisted state (here a deterministic nonce seed scoped too coarsely) is silently trusted on reuse, turning a second signing request into nonce reuse rather than a fresh-preprocess failure.

### Impact Explanation
FROST/Schnorr share reuse of the same nonce `d + ρ·e` across two messages yields `s₁ − s₂ = λ·x·(c₁ − c₂)`, recovering the signer's secret key share `x` (Schnorrkel/Ristretto MuSig validator key used for `set_keys` confirmation). Compromise of this key lets an attacker forge the confirmer's contributions in subsequent validator-set/DKG-related signing, i.e. key-share recovery — a critical loss under the validation criteria.

### Likelihood Explanation
The leak triggers if the honest coordinator calls `share()`/`complete()` more than once within one DKG attempt for distinct `key_pair`s — e.g., if multiple valid `Commitments`/key-pair transactions or retried confirmation flows reach `DkgConfirmer::share`/`complete` for the same `attempt` (handle.rs drives these calls per received transaction). Because the context key intentionally excludes `key_pair` and the cache is never consumed, nothing prevents the reuse; safety rests solely on the unenforced assumption that at most one `key_pair` is ever signed per attempt. I could not fully verify within this session whether `handle.rs` guarantees only one `key_pair` per attempt reaches `share()`; if it does not, the bug is directly reachable by data in tributary transactions.

### Recommendation
Include the full message identity (`key_pair`, or a hash of `set_keys_message`) in the `CachedPreprocesses` context key, and/or delete the cached seed after the first successful `sign` so a second request in the same attempt generates a fresh preprocess. Alternatively, derive the nonce seed as `H(seed || msg)` so reuse across distinct messages cannot collide.

### Proof of Concept
Within one DKG `attempt`:

1. Coordinator stores `CachedPreprocesses[("DkgConfirmer", attempt)] = seed` on the first `preprocess()`.
2. A `share(preprocesses, key_pair_A)` call signs `m_A = set_keys_message(set, removed, key_pair_A)`, emitting share `s_A` with nonce `k` derived deterministically from `seed`.
3. A second call `share(preprocesses', key_pair_B)` (same attempt, `key_pair_B ≠ key_pair_A`, e.g. a competing valid Commitments transaction) reconstructs the identical machine and signs `m_B` with the same `k`, emitting `s_B`.
4. From `s_A = k + c_A·x` and `s_B = k + c_B·x` (with `c_A ≠ c_B` since `m_A ≠ m_B`), compute `x = (s_A − s_B)/(c_A − c_B)` (times the Lagrange coefficient), recovering the validator's secret share.
