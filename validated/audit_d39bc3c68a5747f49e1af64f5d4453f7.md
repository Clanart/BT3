## Analysis

Reducing the seed report to its core broken invariant: a cancellation/invalidation mechanism (Seaport's counter) exists, but the verifier authenticated an action against a **stale snapshot of that mechanism** (`counterAtLiquidation`) instead of the live, current value, letting a party act as if the canceled item were still valid.

The local analog is in `IntentGatewayV2`'s cross-chain cancel-from-source path. `_cancelFromSource` dispatches a Hyperbridge `GET` request that snapshots the `_filled` slot on the destination chain **at an arbitrary past height** (`options.height`, only constrained to be `> order.deadline`), and `onGetResponse` unconditionally refunds escrow to the user if that historical snapshot shows empty, without re-checking whether the order was filled afterward, closer to "now." ### Title
Stale-height GET proof in cross-chain order cancellation allows double payout of the same order — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromSource` proves non-fill using a caller-chosen `options.height` that only has to be greater than `order.deadline`, not the current/latest finalized destination height. `onGetResponse` trusts that single historical proof and refunds escrow unconditionally, with no re-check of the order's live fill status on the source chain before paying out.

### Finding Description
When a user cancels from the source chain, the contract emits a GET request keyed to `options.height`, a value fully controlled by the caller as long as it exceeds `order.deadline`: [3](#0-2) 

The `onGetResponse` handler only checks the *returned storage value at that historical height* and then immediately withdraws (refunds) escrow to the user with no further validation against current chain state: [2](#0-1) 

Because `_filled[commitment]` is only set at the moment a fill or destination-cancel transaction executes, a user can pick `options.height` equal to the earliest legal value (`order.deadline + 1`) and dispatch the cancel-from-source GET request immediately. If a solver's `fillOrder` call lands on the destination chain in a later block (still legitimately before/at the point the solver decides to fill — note `fillOrder` only rejects when `order.deadline < _blockNumber()`, so fills remain possible in blocks after `order.deadline` too, up to and including the deadline block itself, and race windows exist around it), the queried height's snapshot still shows an empty `_filled` slot even though the order gets filled shortly after. Hyperbridge's challenge-period/finality delay for GET responses widens this window further: the response is only delivered well after `options.height`, during which the destination-side fill can occur without ever being reflected in the proven snapshot.

The result: the solver executes `_fillCrossChain`, paying the beneficiary in full and dispatching a `RedeemEscrow` message expecting the source escrow, [4](#0-3)  while the source chain simultaneously (or subsequently) processes the stale GET response and refunds the *same* escrowed input tokens to the order's original user via `_withdraw`. Both `RedeemEscrow` and the GET-response refund draw from the same `_orders[commitment]` escrow balance for the same commitment — this is a double-settlement of the identical escrow: once to the solver (via RedeemEscrow) and once to the user (via the stale non-fill proof), since the check that gates the refund (`onGetResponse`'s "was it filled") reflects a historical, attacker-chosen point in time rather than current committed state.

Unlike the `cancelOrder`'s own guard `if (_filled[commitment] != address(0)) revert Filled();`, which only protects against *already recorded* fills at the moment `cancelOrder` is called, [5](#0-4)  nothing re-validates that guard at the time the GET response actually lands and pays out — mirroring exactly the Seaport analog where the check used a stale counter value instead of the live one at claim time.

### Impact Explanation
This is a direct, unauthorized double-settlement of escrowed funds: the same order's input escrow can be released both to the honest solver (as `RedeemEscrow`) and back to the original user (as a stale-proof refund), draining the gateway's balance beyond what a single order should ever release. This falls squarely within the bounty's "stealing or loss of funds" / "replay/double-claim/double-settlement" / "false proof acceptance" categories, since it requires only an unprivileged user (the order creator) picking cancel parameters, not a malicious relayer, prover, or admin.

### Likelihood Explanation
The attack requires no special privileges beyond being the order's own user (who is always entitled to call `cancelOrder`), and no cooperation from relayers or provers is needed beyond their normal, honest job of relaying the GET request/response — they are simply relaying an attacker-chosen `options.height` faithfully. The race window is bounded by normal Hyperbridge finality/challenge-period delays for GET responses, which are large enough in practice (multiple blocks to hours depending on chain) to give a solver ample opportunity to fill after the queried height but before the refund lands.

### Recommendation
Re-validate `_filled[commitment] == address(0)` on the **source chain** at the time `onGetResponse` executes (immediately before calling `_withdraw`), not merely trust the destination-chain snapshot from a stale height. Additionally, require `options.height` to correspond to the current/near-tip finalized destination height rather than an arbitrary value only bounded below by `order.deadline`, so the non-fill proof reflects the destination chain's *live* state at redemption time rather than an attacker-selected historical point.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At block `D+1` on the source chain, user calls `cancelOrder` → `_cancelFromSource` with `options.height = D+1`, dispatching a GET request for the destination `_filled` slot at that height.
3. Before the GET response challenge period elapses and is delivered back to the source, a solver calls `fillOrder` on the destination chain (this remains legal since the destination-side deadline check only requires `order.deadline >= _blockNumber()`, and even shortly after `D+1` the solver may still be racing to fill, or the fill lands in a block after `D+1` but the queried snapshot at `D+1` is already fixed and empty).
4. `_fillCrossChain` runs, paying the beneficiary and dispatching `RedeemEscrow` back to the source chain, which will later credit the solver from the same `_orders[commitment]` escrow.
5. Separately, the GET response for height `D+1` is delivered to the source chain; `onGetResponse` sees an empty `_filled` slot (as it existed before the fill) and calls `_withdraw(..., true, true)`, refunding the same escrow to `order.user`.
6. Both withdrawals succeed against the same commitment's escrow, resulting in double payout from a single order's escrowed funds.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
