### Title
Change outputs below the scanner's DUST threshold are created but never reported, permanently stranding funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` emits a change output whenever the leftover value is `>= DUST` (546 sats), but the network's output scanner only reports outputs `>= N::DUST` (10,000 sats for Bitcoin). A change output between 546 and 9,999 sats is silently created on-chain yet never surfaced to Serai as spendable — analogous to the reported bug where state is committed (the output exists, the inputs are consumed) while the "transfer" effectively fails and the value is unrecoverable.

### Finding Description
In `SignableTransaction::new`, the change branch only checks `value >= DUST` with the wallet-local `DUST = 546` before pushing the change output [1](#0-0) . The constant itself is defined locally as 546 [2](#0-1) .

Separately, the processor's `get_outputs` (the only path that turns on-chain data into `ReceivedOutput`s Serai can spend) drops any scanned output below `N::DUST`, which is 10,000 for Bitcoin [3](#0-2) [4](#0-3) . The scanner key/offset registration is correct — `register_offset` records the actual used offset and `multisig` re-derives and checks the script [5](#0-4) [6](#0-5)  — so the output is genuinely spendable by the key; it is simply never reported.

The mismatch (546 vs 10,000) means any change output in `[546, 10_000)` is committed into a signed transaction yet invisible to the network.

### Impact Explanation
Like `withdrawInsurance` decrementing `insuranceDeposited` while the token transfer silently fails, Serai consumes inputs and signs a transaction whose change residue lands in an output the system can never observe or spend. The sats are locked under the multisig's own change offset indefinitely — effectively burned. Per occurrence the loss is bounded by ~9,454 sats, but it is deterministic whenever `input_sat - payment_sat - fee_with_change` falls in that band, and payment amounts derive from user-submitted `OutInstruction`s, so an unprivileged user supplying a crafted payment amount can steer the change residue into the dead zone.

### Likelihood Explanation
Change is `input_sat - payment_sat - fee_with_change`. An external user who triggers a batch/payment can choose their payment amount; given knowledge (or guesses) of the inputs Serai aggregates and the fee rate, they can force the remainder into the gap. Even without deliberate targeting, ordinary aggregation flows will intermittently produce sub-10k change. Likelihood is moderate; impact per hit is small-but-real, fitting Medium.

### Recommendation
Make the wallet's emission threshold consistent with the network's observability threshold: raise the change check to `value >= N::DUST` (10,000) — i.e., replace `DUST` in the change branch with the network dust limit, or expose a `NETWORK_DUST` constant shared between `send.rs` and `processor/src/networks/bitcoin.rs`. Alternatively, when change would be below the scanner threshold, fold it into the fee deliberately and document that. Also consider asserting `payments` amounts aren't routed to Serai-owned scripts below the scanner threshold, though change is the concrete bug.

### Proof of Concept
```rust
// Conceptual: inputs = 50_000 sats, fee_with_change ~ 500 sats
// payment = 49_000 sats  ->  change = 50_000 - 49_000 - 500 = 500 sats (<546, dropped: OK)
// payment = 40_000 sats  ->  change = 50_000 - 40_000 - 500 = 9_500 sats
//   >= DUST(546)  -> change output created at 9_500 sats
//   <  N::DUST(10_000) -> processor get_outputs never reports it
// Result: tx valid, signed, broadcast; 9_500 sats stranded under
//         key + G*change_offset, forever unspendable by Serai.
```
Concretely, call `SignableTransaction::new(inputs, &[(script, 40_000)], Some(change_script), None, fee_rate)` such that the computed change is in `[546, 10_000)`; the returned transaction contains the change output, yet `Bitcoin::get_outputs` (via `processor`'s `output.balance().amount.0 >= N::DUST` filter) will never yield it.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
