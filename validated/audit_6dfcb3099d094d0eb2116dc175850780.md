Based on the investigation, I found a direct structural analog to the reported bug class in the ISMP relayer-fee withdrawal module.

### Title
Missing module/sender identity validation in `HyperbridgeWithdrawalModule::on_accept` allows arbitrary relayer-fee withdrawal - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
The original report's broken invariant is: a fund-moving entrypoint checks only a coarse-grained identity (that a message came from *a* trusted chain) without checking the specific contract/module identity that is supposed to be the only legitimate caller, letting an attacker use a different, unauthorized channel to trigger the same payout logic. `HyperbridgeWithdrawalModule::on_accept` in Hyperbridge exhibits the same class of gap: it validates that the request's `source` state-machine equals the configured `Coprocessor`, but never checks `request.from`, i.e., which specific module/pallet on that chain originated the message.

### Finding Description
`HyperbridgeWithdrawalModule::on_accept` is the `IsmpModule` callback invoked whenever an incoming ISMP `PostRequest` is routed to the well-known id `HYPERBRIDGE_MODULE_ID`: [1](#0-0) 

The only authorization check performed is:
```
let source = request.source;
if Some(source) != T::Coprocessor::get() {
    Err(...)?
}
```
This validates the *state machine/chain* the request came from, but does **not** validate `request.from` — the identifier of the specific pallet/account on that chain that constructed the message. Once the chain-level check passes, the decoded `Message::WithdrawRelayerFees { account, amount }` is trusted completely, and `T::Currency::transfer` moves funds from `RELAYER_FEE_ACCOUNT` to whatever `account` is embedded in the payload: [2](#0-1) 

Compare this to the legitimate, intended-caller path: `pallet_ismp_relayer::withdrawal::Pallet::withdraw` builds this exact message (`Message::WithdrawRelayerFees`) and dispatches it with `from: MODULE_ID` (the relayer pallet's own id), after it has independently verified a relayer's signature and consumed a nonce: [3](#0-2) 

Nothing in `on_accept` enforces that `request.from == MODULE_ID` (the relayer-fee pallet's identity on the coprocessor). Any other pallet or dispatch path on the coprocessor chain capable of invoking `IsmpDispatcher::dispatch_request` with an attacker-influenced `from` field would produce a wire-compatible request that this handler accepts and pays out, exactly as the CDP report's `liquidate_collateral` accepted calls from anyone because it never checked `info.sender == central_control`.

The generic dispatcher itself takes `from` verbatim from the caller without cross-checking it against the calling pallet's own identity: [4](#0-3) 

### Impact Explanation
If any code path on the coprocessor chain can be induced to dispatch a `PostRequest` with `to = HYPERBRIDGE_MODULE_ID`, `from` set to the expected relayer-module identifier, and a `WithdrawRelayerFees{account, amount}` body, `on_accept` will transfer `amount` from the shared `RELAYER_FEE_ACCOUNT` (funds belonging to all relayers, not just the caller) to an arbitrary `account`, with no signature or per-relayer balance check on the receiving side — that verification only exists in `pallet_ismp_relayer::withdraw`/`accumulate`, not in the receiving `on_accept`. This is a wrong-beneficiary/unauthorized-fund-movement outcome matching the required impact list (unauthorized execution / theft of pooled relayer funds).

### Likelihood Explanation
I could not fully confirm, within the available tool budget, whether an unprivileged user (versus only another pallet already built into the coprocessor runtime) can control the `from` field of a dispatched request reaching this handler — that would require enumerating every runtime pallet on the coprocessor (Nexus/Hyperbridge) that has access to `T::IsmpHost`/`IsmpDispatcher` and checking whether any of them let a caller set an arbitrary `from`. This is a real gap in defense-in-depth (module-level access control is missing where it exists everywhere else in the codebase, e.g. `onAccept` in the EVM apps explicitly check `keccak256(request.from) == keccak256(expectedSource)` in addition to chain checks — see `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:294-296`), but full remote reachability by a fully unprivileged actor was not proven with certainty.

### Recommendation
Add an explicit check in `HyperbridgeWithdrawalModule::on_accept` that `request.from == pallet_ismp_relayer::MODULE_ID` (or whatever the canonical relayer-fee pallet identifier on the coprocessor is), mirroring the pattern already used in the EVM token-gateway apps (`onAccept` checking `request.from` against `_supportedChains[source]`), so that only the intended module's messages can trigger a withdrawal.

### Proof of Concept
Not fully constructible without confirming a concrete attacker-reachable dispatch path with a controllable `from` field on the coprocessor chain; the code-level gap (chain-only check, no module/sender check) is demonstrated above by direct citation. [1](#0-0)

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
