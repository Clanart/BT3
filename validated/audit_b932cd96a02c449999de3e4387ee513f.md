### Title
Division-by-zero panic in `consolidatedNode.Split` during reward finalization when a proposer's CN and CL staking amounts are both rounded to zero - (File: kaiax/staking/staking_info.go)

### Summary
The reported Y2K bug is a division-by-zero (`mulDivDown` reverting on a zero denominator) that is reachable only through a value that a caller does not fully control, causing a view function to unexpectedly revert. The Kaia codebase contains an analogous unguarded division in `consolidatedNode.Split`, but here the function is invoked from consensus-critical, per-block reward-distribution code (`specWithProposerAndFunds` / `specWithProposerAndFundsFlex`) rather than a pure view function, so triggering it can crash block finalization on every full node rather than merely mis-displaying a value.

### Finding Description
`consolidatedNode.Split` divides by the sum of a validator's CN staking amount and its consensus-liquidity (CL) staking amount, with no zero-check: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount) // panics if totalAmount == 0
	...
}
```

`Split` is only guarded against `totalAmount == 0` when it is called from `assignStakingRewards`/`assignStakingRewardsFlex`, because those call sites first filter by `cn.StakingAmount >= minStake` (and only add excess when it's positive). However, the proposer-reward path does **not** apply that filter — it only checks whether the proposer's consolidated node has a `CLStakingInfo` entry at all: [2](#0-1) 

```go
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase {
        continue
    }
    if cn.CLStakingInfo == nil {
        break
    }
    cnAmount, clAmount := cn.Split(proposer)
    ...
}
```

This same unguarded pattern exists in the legacy (non-Flex) path: [3](#0-2) 

`StakingAmount` and `CLStakingAmount` are computed by truncating the raw KAIA balances of the staking/CL-pool contracts to whole KAIA units: [4](#0-3) 

```go
for i, a := range amounts {
    stakingAmounts[i] = big.NewInt(0).Div(a, big.NewInt(params.KAIA)).Uint64()
}
...
CLStakingAmount: big.NewInt(0).Div(clRes.StakingAmounts[i], big.NewInt(params.KAIA)).Uint64(),
```

If a proposer's CN staking-contract balance and its CL-pool balance are both driven below 1 KAIA (e.g. by withdrawing staking/CL funds, or via fee draining) at the moment the `StakingInfo` snapshot is taken, both `StakingAmount` and `CLStakingAmount` truncate to `0`, while the `CLStakingInfo` entry itself is still present (it is only removed from `CLRegistry` by an explicit unregistration action, not automatically when the balance drops to zero). When that validator later proposes a block, `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` calls `cn.Split(proposer)` with `totalAmount == 0`, causing a division by zero and a Go runtime panic during `FinalizeState`, which every full node executes deterministically when processing that block.

### Impact Explanation
`FinalizeState` runs on every node validating/importing the block. An unrecovered panic here crashes the node process for all correctly-configured full nodes and validators that reach this code path when finalizing the affected block, producing a consensus-halting/liveness failure network-wide rather than a localized issue for a single caller — a materially higher-severity variant of the same "unguarded zero-denominator division" root cause described in the reference report.

### Likelihood Explanation
The staking/CL-pool balance draining that produces a `StakingAmount`/`CLStakingAmount` of zero is achievable by the validator's own staking operator/staker (an "staker" role explicitly in scope) through ordinary withdrawal transactions against the CNStaking or CL-pool contracts, without needing any special privilege, as long as the corresponding `CLStakingInfo`/`AddressBook` entry is not simultaneously deregistered. Because reward computation (and thus this code path) executes on every block where such a validator is the proposer, the condition is reachable purely from a staker-controlled sequence of transactions.

### Recommendation
Guard `consolidatedNode.Split` against a zero denominator (mirroring the review comment on `previewWithdraw` in the original report): return `(amount, big.NewInt(0))` when `totalAmount.Sign() == 0`, and/or apply the same `StakingAmount + CLStakingAmount > 0` eligibility check in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` that is already used in `assignStakingRewards`/`assignStakingRewardsFlex` before invoking `Split`.

### Proof of Concept
1. A validator registers a CN in `AddressBook` and a CL pool in `CLRegistry` with a nonzero `CLPoolAddr`.
2. The staker withdraws funds from both the CNStaking contract and the CL pool contract until each contract's KAIA balance drops below `1 KAIA` (both round down to `0` via `big.NewInt(0).Div(a, big.NewInt(params.KAIA))` in `parseCallResult`/`parsePermissionlessCallResult`), while the CL entry remains registered in `CLRegistry`.
3. When this validator's node is later selected as block proposer (Prague/Kore/Flex active, `CLStakingInfo != nil` for its consolidated node), `FinalizeState` invokes `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`, which calls `cn.Split(proposer)` with `cn.StakingAmount == 0` and `cn.CLStakingInfo.CLStakingAmount == 0`.
4. `totalAmount = big.NewInt(0)`; `clAmount.Div(clAmount, totalAmount)` panics with a big.Int division-by-zero, crashing every node executing `FinalizeState` for that block.
