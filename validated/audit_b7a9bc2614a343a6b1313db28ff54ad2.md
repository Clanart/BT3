### Title
DkgConfirmer reuses a cached FROST preprocess seed across re-executions, enabling nonce reuse and validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Aimeos bug class — a consumed artifact's state is not reset, letting stale status persist into a new operation — maps onto Serai's tributary DKG-confirmation signing protocol. `SigningProtocol::preprocess_internal` deterministically regenerates the *same* FROST nonces for a given `context` from a seed stored in `CachedPreprocesses`, and neither `share` nor `complete` ever clears that cache entry. Because `DkgConfirmer::share` and `DkgConfirmer::complete` each re-run `share_internal` (and `complete` may run against a different preprocess set than `share`), the same nonce scalars can produce two signature shares under different binding factors / challenges, allowing algebraic recovery of the validator's private key share.

### Finding Description
`preprocess_internal` checks `CachedPreprocesses::get(txn, context)`; if absent it samples a seed, encrypts it, and stores it; then it unconditionally calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`, which feeds the seed into `ChaCha20Rng` so the nonces `d, e` are fully determined by `context` [1](#0-0) . The cache entry is never deleted after `sign` consumes it — the FROST API contract says the cached preprocess "must be deleted so it's never reused" [2](#0-1) .

`DkgConfirmer::share` and `DkgConfirmer::complete` both call `share_internal`, which calls `preprocess_internal` again and then `machine.sign(preprocesses, msg)` [3](#0-2) . The `preprocesses` map is supplied by the caller, and `sign` computes per-participant binding factors `rho` and the challenge from that set; the raw nonce scalars remain the cached `d, e`. If the participant set or any commitment differs between the two invocations, the two emitted shares satisfy `s_i = d_i + e_i·rho_i + λ_i·share·c_i` with identical `d_i, e_i` but different `rho_i, c_i` — two equations leaking `share` modulo the group order. The file's own header acknowledges the danger of fixed nonces and relies entirely on BFT finality and a still-missing check ("TODO: check the commitments generated from the decided nonces are in fact its commitments on-chain") [4](#0-3) .

### Impact Explanation
Two distinct signing rounds that reuse the same nonce scalars under different `included` sets or different `key_pair`/`msg` allow solving for the validator's MuSig private key share via linear algebra on the published `SignatureShare` scalars. This is secret-share/key recovery — the same consequence the FROST docs attribute to preprocess reuse [5](#0-4) . For the DKG confirmer the share is the validator's root-of-trust key, so recovery compromises subsequent sessions signed by that participant.

### Likelihood Explanation
The nonce reuse occurs whenever `share`/`complete` (or a `generated_key_pair` re-invocation) are executed more than once for the same `attempt` with differing inputs — e.g., `complete` being called with a preprocess map containing participants not present when `share` ran, a reboot-driven re-execution over rebuilt DB state, or a second `KeyPair` confirmation under the same attempt (the code overwrites `KeyToDkgAttempt`/`DkgKeyPair` rather than rejecting a second distinct `key_pair` [6](#0-5) ). Whether a *remote unprivileged* party can force differing preprocess inputs is partially mitigated by BFT ordering — preprocesses are finalized tributary messages — but the code itself notes the missing on-chain-vs-presumed-commitment check as a TODO, and re-execution divergence is an acknowledged design gap rather than a proven invariant. This is Medium: the leak requires the double-signing condition, which is plausible under reorg/rebuild/late-preprocess edge cases but not trivially triggered by any peer.

### Recommendation
Delete or invalidate the `CachedPreprocesses` entry the first time `share_internal` successfully calls `sign`, and persist a "share already published for this context + commitments-hash" marker. Before producing a share in `complete`, verify the stored seed's derived preprocess commitments exactly match this validator's preprocess already on-chain for the attempt; abort otherwise. Reject a second distinct `key_pair` for an attempt already signed.

### Proof of Concept
1. Attempt `a` for genesis `g`: validator V calls `generated_key_pair` → `DkgConfirmer::share(preprocesses_A, kp1)`. `preprocess_internal` creates seed `S` under context `(b"DkgConfirmer", a)`, deriving nonces `d, e`. Share `s_1 = d + e·rho_A + λ·k·c_1` is emitted.
2. Later, `DkgConfirmer::complete(preprocesses_B, kp1, shares)` runs, where `B` includes an additional participant's preprocess finalized after step 1. `share_internal` reloads `S` (entry never removed), re-derives identical `d, e`, and signs with `included = B ∪ {V} ≠ A`, producing `s_2 = d + e·rho_B + λ'·k·c_2`.
3. Anyone observing `s_1, s_2` (both published on tributary) solves the 2×2 linear system for `k`, V's private key share. Equivalently, a second `generated_key_pair` call with `kp2 ≠ kp1` yields the same reuse via `msg` differing while `rho` may even be identical.

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

pub fn generated_key_pair<D: Db>(
  txn: &mut D::Transaction<'_>,
  key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  spec: &TributarySpec,
  key_pair: &KeyPair,
  attempt: u32,
) -> Result<[u8; 32], Participant> {
  DkgKeyPair::set(txn, spec.genesis(), attempt, key_pair);
  KeyToDkgAttempt::set(txn, key_pair.0 .0, &attempt);
  let preprocesses = ConfirmationNonces::get(txn, spec.genesis(), attempt).unwrap();
  DkgConfirmer::new(key, spec, txn, attempt)
    .expect("claiming to have generated a key pair for an unrecognized attempt")
    .share(preprocesses, key_pair)
}
