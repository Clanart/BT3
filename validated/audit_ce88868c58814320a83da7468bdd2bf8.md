## Finding: Missing struct-declared-ability vs. field-ability consistency check in module verification pipeline

The specific mechanism the question proposes — a struct *without* `key` fooling `move_to`'s ability check via a "forged `AbilitySet`" distinct from the one used by resolution — does not hold up. `MoveTo`/`MoveToGeneric` in the paranoid runtime checker call `ty.paranoid_check_has_ability(Ability::Key)` on the type built from the struct handle, and ability resolution for `Struct(idx)`/`StructInstantiation` in `BinaryIndexedView::abilities` reads the ability bits directly off the *same* `struct_handle_at(idx).abilities` table entry used everywhere else (loader, verifier, `move_to`). [1](#0-0) [2](#0-1) 
There is no second, independently-derived `AbilitySet` that `move_to` consults — the struct-handle table is the single source of truth, so a struct lacking `key` cannot pass `has_key()` by "AbilitySet corruption" alone; bounds/duplication checking guarantees index consistency before any ability lookup happens.

However, investigation surfaced a real, adjacent gap: **the checker that validates a struct's declared abilities are actually consistent with its field types' abilities (`ability_field_requirements`) is commented out of the import list and is not invoked anywhere in `verify_module_with_config`**: [3](#0-2) [4](#0-3) 

The passes that do run — `signature_v2::check_ty` / `verify_struct_type_params` — only check that a *use site's required abilities* are a subset of a struct handle's *declared* abilities; they never check that the declared abilities are themselves justified by the struct's field types (e.g. that a `key`/`store` struct's fields all carry `store`): [5](#0-4) [6](#0-5) 

`RecursiveStructDefChecker` (`struct_defs.rs`) only rejects reference-typed fields and structural recursion; it does not check ability containment for non-reference fields such as `signer`: [7](#0-6) 

`I was unable to find, within the tool-call budget, any function actually named/behaving like `verify_fields_of_struct`/`ability_field_requirements` still wired into this codebase — it only appears in a brainstorming markdown doc, and it is explicitly commented out in `verifier.rs`.` This is a genuine limitation of my investigation: I cannot be 100% certain no equivalent check exists elsewhere in the pipeline (e.g., folded into `code_unit_verifier.rs` or `check_bounds.rs`, which I did not fully read), but the direct evidence (explicit `//ability_field_requirements,` comment-out, and its absence from the `verify_module_with_config` call chain) strongly suggests it is disabled.

### Title
Disabled ability–field-consistency verifier pass permits `key`/`store` structs whose fields lack required abilities to be published - (File: `third_party/move/move-bytecode-verifier/src/verifier.rs`)

### Summary
The bytecode verifier pass that enforces "a struct declared with `key` must have all fields with `store`, a struct declared with `store` must have all fields with `store`," etc. (`ability_field_requirements`) is commented out of `verifier.rs`'s import list and is not called anywhere in `verify_module_with_config`, the canonical entry point used by the publish path (`publish_package_txn` → `StagingModuleStorage` verification).

### Finding Description
An unprivileged publisher can hand-craft (not compiler-generated) module bytecode where a struct handle declares `abilities: key | store` while one of its fields is typed as `signer` (`AbilitySet::SIGNER = drop` only, no `store`) or another non-`store` type. `signature_v2.rs`'s `assert_abilities` checks are one-directional — they validate that a *use site* requiring some abilities is satisfied by the struct's *declared* abilities — but never validate the struct's own internal consistency between declared abilities and field types. `RecursiveStructDefChecker` only blocks reference fields, not other non-`store` types. With `ability_field_requirements` disabled, such a module can pass `BoundsChecker`, `DuplicationChecker`, `signature_v2::verify_module`, `RecursiveStructDefChecker`, and `CodeUnitVerifier`, and reach `StagingModuleStorage`.

### Impact Explanation
Once published, the module's `move_to`/`move_from`/`borrow_global` on the malformed struct is legal per the (correctly-reading) runtime paranoid checks, since those only check the struct's own `key` bit, not internal field consistency. This breaks the Move invariant "if a value has `key`, all values reachable inside it have `store`," letting a resource containing a non-serializable/non-storable value type (e.g. `signer`) be written into global storage/write sets for that address, corrupting the assumed storage layout contract relied upon elsewhere (BCS serialization of resources, indexers, and any code that assumes all fields of on-chain resources are `store`-able).

### Likelihood Explanation
Requires only permissionless module publishing with hand-assembled (non-standard-compiler) bytecode, which is within scope (unprivileged package/bytecode entry point). No prior code ownership or special privilege needed.

### Recommendation
Re-enable `ability_field_requirements` (or equivalent) in `verify_module_with_config`'s pass list in `third_party/move/move-bytecode-verifier/src/verifier.rs`, ensuring every struct definition's declared abilities are validated against the recursively-computed abilities of its field types before a module is accepted into `StagingModuleStorage`.

### Proof of Concept
Construct (via `move-binary-format` builders, bypassing the source compiler) a `CompiledModule` with:
- `StructHandle { abilities: Key | Store, ... }` for struct `Cap`
- `StructDefinition` for `Cap` with a single field of type `SignatureToken::Signer`
- An entry function taking `signer` and doing `pack Cap { s: signer }; move_to Cap`

Submit via the standard `publish_package_txn` path and confirm the module passes `verify_module_with_config` (no `ability_field_requirements`/equivalent invocation in `verifier.rs`'s pass sequence) and that `move_to` on `Cap` succeeds at runtime. [4](#0-3)

pub fn verify_module_with_config(config: &VerifierConfig, module: &CompiledModule) -> VMResult<()> {
    if config.verify_nothing() {
        return Ok(());
    }
    let prev_state = move_core_types::state::set_state(VMState::VERIFIER);
    let result = std::panic::catch_unwind(|| {
        // Always needs to run bound checker first as subsequent passes depend on it
        BoundsChecker::verify_module(module).map_err(|e| {
            // We can't point the error at the module, because if bounds-checking
            // failed, we cannot safely index into module's handle to itself.
            e.finish(Location::Undefined)
        })?;
        FeatureVerifier::verify_module(config, module)?;
        LimitsVerifier::verify_module(config, module)?;
        DuplicationChecker::verify_module(module)?;

        signature_v2::verify_module(config, module)?;

        InstructionConsistency::verify_module(module)?;
        constants::verify_module(module)?;
        friends::verify_module(module)?;

        RecursiveStructDefChecker::verify_module(module)?;
        InstantiationLoopChecker::verify_module(module)?;
        CodeUnitVerifier::verify_module(config, module)?;

        // Add the failpoint injection to test the catch_unwind behavior.
        fail::fail_point!("verifier-failpoint-panic");

        script_signature::verify_module(module, no_additional_script_signature_checks)
