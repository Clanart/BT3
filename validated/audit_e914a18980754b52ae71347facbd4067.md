### Title
Tron `IntentGatewayV2` reimplements the intent-fill logic without the `nonReentrant` guard fixed in the EVM version, reopening the escrow/fee-theft reentrancy path - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The main EVM `IntentGatewayV2` had a documented, previously-exploitable reentrancy bug in its same-chain fill path (`IntrinsicIntents._fillSameChain`), where `_filled[commitment]` was set only *after* the ETH output transfer to the beneficiary, letting a malicious beneficiary re-enter `fillOrder` during the `.call{value:...}("")` and steal escrowed fees/inputs before the order was marked filled. This was fixed with a CEI (checks-effects-interactions) pattern that moves `_filled[commitment] = msg.sender` to the top of `_fillSameChain`/`_fillCrossChain`, confirmed by the regression tests in `IntrinsicIntentsReentrancyTest.sol`.

However, `evm/tron/contracts/apps/IntentGatewayV2.sol` is a **separate, standalone contract** for the Tron chain — it does not inherit `IntrinsicIntents`/`ExtrinsicIntents` from `evm/src/apps/intentsv2/`, and it does not carry the `nonReentrant` modifier that the fixed EVM `IntentGatewayV2.sol` applies to `placeOrder`/`cancelOrder`. [1](#0-0) [2](#0-1) 

### Finding Description
The exact same "callback opens a window to move funds before the invariant is set" primitive from the UniswapV3 report applies here: the fill flow performs a low-level `.call{value: amount}("")` to an attacker-controlled `beneficiary` address before/alongside marking the order state as finalized. In the original (pre-fix) EVM implementation, the reentrant call landed inside `receive()` on the beneficiary and re-invoked `fillOrder` before `_filled[commitment]` was set, letting the attacker self-fill or drain escrow. [3](#0-2) 

The Tron variant reimplements `withdraw()` and its own fill path independently and does not have the `nonReentrant` protection the audited EVM contract now carries: [4](#0-3) [5](#0-4) 

I was unable to fully retrieve and confirm the body of the Tron contract's `fillOrder`/same-chain-fill function within the available tool budget — my last read/grep calls to inspect that specific function did not complete successfully. **This is a material gap**: whether the Tron deployment reproduces the vulnerable ordering (external ETH transfer to beneficiary before `_filled[commitment]` is set) or already applies the CEI fix independently could not be verified from the index. The `withdraw()` function I did retrieve does apply CEI correctly (`_filled[body.commitment] = beneficiary;` is set before transfers, evm/tron/contracts/apps/IntentGatewayV2.sol:684), which weakens confidence that the fill path is vulnerable, but does not rule it out since `withdraw()` is only the settlement handler, not the fill entrypoint itself.

### Impact Explanation
If the Tron fill entrypoint reproduces the unfixed ordering (transfer-then-mark-filled), an attacker beneficiary contract could re-enter during output delivery to self-fill or drain escrowed input tokens/fees before the order is marked filled, causing direct loss of user funds — matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
Medium-to-low confidence given the gap in verification above. The evidence that raises suspicion: (1) the Tron contract is a hand-maintained duplicate of security-sensitive logic rather than a shared/inherited implementation, so fixes to the canonical EVM path are not guaranteed to propagate; (2) the canonical EVM version required a dedicated CEI fix and a dedicated regression test suite for exactly this bug class, indicating the fill flow is inherently reentrancy-prone; (3) `placeOrder`/`cancelOrder` on the Tron contract lack the `nonReentrant` modifier present on the fixed EVM contract.

### Recommendation
Verify (with full file access, e.g., a Devin session) whether `evm/tron/contracts/apps/IntentGatewayV2.sol`'s fill function sets `_filled[commitment]` before any external `.call`/token transfer to the beneficiary, and whether `nonReentrant` is applied to `fillOrder`/`cancelOrder`/`placeOrder`. If not, apply the same CEI fix and reentrancy guard used in `evm/src/apps/intentsv2/{IntrinsicIntents,ExtrinsicIntents}.sol`, and add a Tron-specific regression test mirroring `IntrinsicIntentsReentrancyTest.sol`. More broadly, the Tron contract should be refactored to inherit the shared, audited intent-fill logic rather than maintaining a parallel copy, to prevent future security-fix drift between deployments.

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({
            token:  bytes32(uint256(uint160(address(usdc)))),
            amount: INPUT_USDC
        });

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(0), amount: OUTPUT_ETH});

        Order memory order = _sameChainOrder(inputs, outputAssets, TX_FEES);

        vm.startPrank(attacker);
        usdc.approve(address(intentGateway), INPUT_USDC);
        dai.approve(address(intentGateway), TX_FEES);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Reconstruct the stamped order for commitment computation.
        order.user   = bytes32(uint256(uint160(attacker)));
        order.source = host.host();
        order.nonce  = 0;

        bytes32 commitment = keccak256(abi.encode(order));

        // Sanity: confirm fees are escrowed.
        assertEq(intentGateway._orders(commitment, TRANSACTION_FEES), TX_FEES);

        // ── 2. Arm the malicious beneficiary ─────────────────────────────────
        //
        // The reentrant FillOptions passes amount=0 so the re-entered loop's
        // `remaining == 0 || solverAmount == 0` branch is taken — but this
        // code path is never reached because _filled[commitment] is already set.

        TokenInfo[] memory reentrantOutputs = new TokenInfo[](1);
        reentrantOutputs[0] = TokenInfo({token: bytes32(0), amount: 0});

        maliciousBeneficiary.arm(
            order,
            FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: reentrantOutputs})
        );

        // ── 3. Fill attempt reverts — reentrancy is blocked ──────────────────

        vm.expectRevert(ERR_INSUFFICIENT_NATIVE);
        vm.prank(legitimateSolver);
        intentGateway.fillOrder{value: OUTPUT_ETH}(
            order,
            FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: outputAssets})
        );

        // ── 4. State is completely rolled back ───────────────────────────────

        assertEq(
            intentGateway._orders(commitment, TRANSACTION_FEES),
            TX_FEES,
            "fees must still be escrowed after revert"
        );
        assertEq(
            intentGateway._filled(commitment),
            address(0),
            "order must not be marked filled after revert"
        );
        assertEq(
            dai.balanceOf(address(maliciousBeneficiary)),
            0,
            "malicious beneficiary must not receive stolen fees"
        );
        assertEq(
            usdc.balanceOf(legitimateSolver),
            0,
            "solver must not have received any escrow"
        );

        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
