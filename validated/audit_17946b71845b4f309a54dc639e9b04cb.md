### Title
Scanner reports immature coinbase outputs as spendable ReceivedOutputs, enabling inclusion of unspendable inputs into FROST-signed transactions - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The LFI report describes a system that resolves attacker-supplied identifiers into local resources without validating that the resolved object is authorized/usable. The Serai analog is `Scanner::scan_block`, which feeds an untrusted on-chain resource — every transaction in a Bitcoin block, including the coinbase — into `scan_transaction`, producing `ReceivedOutput` values that downstream code treats as immediately spendable wallet inputs, without checking coinbase maturity.

### Finding Description
`Scanner::scan_block` iterates `block.txdata` and returns `ReceivedOutput`s for any output whose `script_pubkey` matches a registered script (`networks/bitcoin/src/wallet/mod.rs`, lines 221–227 and 199–214). A `ReceivedOutput` carries only an `offset`, a `TxOut`, and an `OutPoint` — no maturity metadata (lines 90–97). The code itself acknowledges the gap in a comment: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" (lines 217–220).

Downstream, `SignableTransaction::new` consumes `ReceivedOutput`s directly as `TxIn`s and prevouts (send.rs lines 150–185, 253), and `multisig`/`sign` produce a fully-signed Taproot key-spend transaction over `Prevouts::All` (send.rs lines 273–285, 373–397). Nothing in this path verifies that a prevout's containing transaction is a coinbase old enough to be spent (the 100-block COINBASE_MATURITY rule). Any UTXO set built purely from `scan_block` can therefore contain inputs that no valid transaction can spend.

### Impact Explanation
An unprivileged party — any Bitcoin miner, or anyone whose transaction lands in a block — controls block contents, which are the public inputs to `scan_block`. If a coinbase output pays to a registered Serai script (e.g., miner fees/donations to a known deposit address, which are publicly visible on-chain), the scanner reports funds as received that are not spendable. A spend plan built on them produces a consensus-invalid transaction after a full FROST signing ceremony: the reported balance is wrong, fee/change math in `SignableTransaction::new` accounts the immature value as spendable, and the resulting broadcast fails — burning a signing session and misreporting wallet funds until the output matures or is manually excluded.

### Likelihood Explanation
Reachability is direct: `scan_block` is the intended API for ingesting blocks, and coinbase outputs paying arbitrary script_pubkeys are trivially creatable by miners (any miner can direct coinbase outputs to Serai's well-known P2TR script). Exploitation requires no keys and no collusion. Impact is bounded — the signatures produced are still correct for what they sign (the multisig script_pubkey check at send.rs line 277 still passes since the offset is genuinely registered), so no forgery occurs; the damage is funds misreported as spendable plus wasted threshold-signing rounds and invalid transactions. Medium severity.

### Recommendation
In `scan_block`, skip `block.txdata[0]` or tag `ReceivedOutput`s derived from the coinbase and reject them at `SignableTransaction::new`/plan-construction time unless maturity is proven. If maturity cannot be verified at scan time (no block height context), refuse coinbase outputs unconditionally in `scan_block` and require callers to use `scan_transaction` on `block.txdata[1 ..]` only — do not leave maturity enforcement as an undocumented post-processing responsibility. Track maturity state alongside the `OutPoint` (e.g., store the block height in `ReceivedOutput`) so planners can gate spendability.

### Proof of Concept
1. Register/watch a script: `let mut s = Scanner::new(group_key)`; the coinbase of a new block contains a vout paying `p2tr_script_buf(group_key)` (any miner can create this; deposits to the known script also occur naturally).
2. `s.scan_block(&block)` returns a `ReceivedOutput` for `OutPoint(coinbase_txid, vout)` with `offset = Scalar::ZERO` — indistinguishable from a mature UTXO.
3. Build `SignableTransaction::new(vec![that_output], payments, change, None, fee)` — succeeds; `multisig(&keys)` succeeds because `p2tr_script_buf(offset.group_key())` matches `prevout.script_pubkey`; `sign`/`complete` yield a signed transaction.
4. Broadcasting the transaction fails consensus validation (BIP-30/coinbase maturity: `bad-txns-premature-spend-of-coinbase`), and until maturity the wallet's reported balance includes value it cannot move.
