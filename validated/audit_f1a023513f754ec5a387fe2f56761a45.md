### Title
Un-zeroized copies of DKG secret share scalars left in memory during share verification and blame resolution - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analog of CVE-2023-2481 (compiler removal of buffer clearing → key material duplicated to RAM). In PedPoP's `calculate_share`/`blame_internal` flow, decrypted secret shares are copied into plain `C::F` temporaries that are never zeroized: `Zeroizing::new(share)` takes a `Copy` of the scalar in `blame_internal`, and `share_verification_statements` creates a `-share` temporary for the share-multiplication that is dropped without clearing. Both leave secret share material — knowledge of all of which reconstructs the group private key — resident in stack/heap memory after the operation completes.

### Finding Description
In `KeyMachine::calculate_share`, each incoming `EncryptedMessage<C, SecretShare<C::F>>` is decrypted to `share_bytes` (a `Zeroizing`), then converted to a scalar `share` in `Zeroizing` at `crypto/dkg/pedpop/src/lib.rs:479-484`. That `Zeroizing<C::F>` is passed by value into `share_verification_statements` (`lib.rs:430-449`). Inside that function, line 444 computes `C::generator() * -*share`: the `-*share` expression first derefs/copies the secret scalar into a plain `C::F` temporary, then negates it into another temporary. `share.zeroize()` at line 445 clears the `Zeroizing` wrapper, but neither temporary copy is overwritten — this is exactly the "clearing performed, but copies of the secret still exist in memory" pattern of the GSDK bug. The temporary persists in stack memory until reused.

The same gap exists on the blame path: `BlameMachine::blame_internal` (`lib.rs:590`) obtains `share` as a plain `C::F` from `C::F::from_repr(share_bytes.0)` and then calls `Zeroizing::new(share)` at line 600. Since `C::F` is `Copy`, the original `share` binding remains a live, un-zeroized copy of the secret share on the stack for the remainder of the function (and the `-*share` temporary inside `share_verification_statements` is duplicated again there).

This is reachable with public inputs: any DKG participant drives `calculate_share` simply by sending their encrypted `SecretShare` (fed through `EncryptedMessage::read` and `Encryption::decrypt`), and drives `blame_internal` by submitting a blame accusation via `BlameMachine::blame`/`AdditionalBlameMachine::blame`.

### Impact Explanation
Each execution leaves copies of every counterparty's decrypted secret share (and negated variants) in process memory. An attacker who later obtains a memory disclosure of the host (or reuses the freed stack/heap region) can recover the received secret shares; possessing a threshold of shares recovers the group private key, and a single share reveals that participant's contribution. This mirrors the CVE's impact: key material duplication to RAM without the caller's knowledge, despite the code's surface-level use of `Zeroizing`.

### Likelihood Explanation
The residue is created deterministically on every `calculate_share` and every `blame`/`blame_internal` invocation — no race or special input is needed. Exploitation requires a separate memory-read primitive, matching the Medium (5.3) severity of the source advisory rather than a remotely-triggerable key recovery.

### Recommendation
Avoid materializing the secret scalar outside `Zeroizing`: compute the negated share inside a `Zeroizing` (e.g., `let neg = Zeroizing::new(-*share);` and use `neg.deref()`), and in `blame_internal` wrap the `from_repr` result directly (`let share = Option::<C::F>::from(...).map(Zeroizing::new)`) so no bare `C::F` copy of the share exists. Note that explicit `zeroize()` calls on `Copy` temporaries are equally susceptible to compiler elimination as in CVE-2023-2481; keeping all secret values inside `Zeroizing`/`ZeroizeOnDrop` wrappers (as `SecretShare<F>` already does via its `Drop` impl at `lib.rs:256-261`) is the robust fix.

### Proof of Concept
```rust
// crypto/dkg/pedpop/src/lib.rs

// Path 1: calculate_share -> share_verification_statements
fn share_verification_statements<C: Ciphersuite>(
  target: Participant,
  commitments: &[C::G],
  mut share: Zeroizing<C::F>,
) -> Vec<(C::F, C::G)> {
  let mut values = exponential::<C>(target, commitments);
  // `-*share` creates an un-zeroized `C::F` temporary copy of the secret share
  let neg_share_pub = C::generator() * -*share;   // line ~444
  share.zeroize();                                // clears `share`, NOT the `-share` temp
  values.push((C::F::ONE, neg_share_pub));
  values
}

// Path 2: blame_internal
let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else { ... };
// `share` is a plain C::F (Copy) still holding the secret share...
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],
  Zeroizing::new(share),   // ...copied into Zeroizing; original `share` never zeroized
))
```

Both are exercised by ordinary protocol traffic: a counterparty's `EncryptedMessage<C, SecretShare<C::F>>` reaching `calculate_share`, or an accusation reaching `BlameMachine::blame`. Uncertainty: whether a given build leaves the temporaries in stack vs. registers is compiler-dependent — the same characteristic the original CVE exhibited, where intended clearing did not bound the lifetime of duplicated key material.
