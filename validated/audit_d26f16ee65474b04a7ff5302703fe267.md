## Finding

### Title
Partial-commit line selection is applied against a re-fetched diff instead of the diff it was computed from, allowing silent corruption of staged/committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual diff lines/hunks to include in a commit. The selection is stored as a set of *line indices* (`DiffSelection`) computed against a specific diff snapshot fetched when the Changes view loaded the file's diff. When the commit is actually built, `applyPatchToIndex` re-fetches the working-directory diff a second time and blindly reuses the old, disk-relative line indices against this new diff to build the patch. Any change to the file's on-disk content or its diff output (e.g. a `.gitattributes`-driven clean/smudge filter defined by the repository, or normal external modification of the working tree) between the two fetches causes the wrong lines to be included/excluded, silently corrupting what gets committed - directly analogous to the report's "gas snapshot taken too early" pattern, where a value (gas usage / here, line-selection-against-diff) is captured before other state-changing operations run and is then used without being refreshed.

### Finding Description
Selection state is created against a diff obtained in `updateChangesWorkingDirectoryDiff`: [1](#0-0) 

That diff's hunks are used to build `selectableLines`/`DiffSelection`, and `file.selection.isSelected(absoluteIndex)` is later consulted purely by numeric line index: [2](#0-1) 

When the user commits, `_commitIncludedChanges` takes a snapshot of these already-selected files from the in-memory state cache: [3](#0-2) 

`createCommit` then unstages everything and calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`: [4](#0-3) [5](#0-4) 

Critically, `applyPatchToIndex` does **not** reuse the diff the selection was made against - it fetches a brand-new diff of the working directory at commit time and feeds it straight into `formatPatch` together with the old `file.selection` indices: [6](#0-5) 

`formatPatch` trusts `file.selection.isSelected(absoluteIndex)` at face value against this freshly-fetched diff's hunk offsets: [7](#0-6) 

If the diff content/hunk layout differs even slightly between the time the user made their selection and the time `applyPatchToIndex` re-fetches the diff, the same numeric indices now point at different lines. There is no re-validation step (unlike `updateChangesWorkingDirectoryDiff`, which does re-map `selectableLines` when the UI diff changes) in the actual commit path - the stale selection is applied directly to the new diff.

### Impact Explanation
Because `formatPatch` builds the literal patch text applied via `git apply --cached`, a mismatch means the resulting commit can:
- Include lines/content the user explicitly deselected (potential leakage of secrets, debug code, or partially-typed content the user chose to exclude).
- Exclude lines the user selected, producing an incomplete/broken commit that is silently different from what was reviewed and gets pushed upstream.

This falls squarely under "silent corruption of what the user commits or pushes," since the app shows no warning - the commit succeeds and the diff shown afterwards is simply whatever `git` produced from the mismatched patch.

### Likelihood Explanation
The window between the diff the selection is based on (`updateChangesWorkingDirectoryDiff`) and the diff re-fetched in `applyPatchToIndex` at commit time is an inherent async gap in the architecture, not an edge case requiring privileged access:
- A cloned/fetched repository can define `.gitattributes` clean/smudge/diff filters that change output non-deterministically or based on external inputs, directly manipulating the diff `git diff`/`git apply` computes for a given file without any user action beyond opening/committing in that repo.
- Ordinary background activity (editor autosave, build tools, linters, file watchers) modifying the working tree while the user is reviewing/selecting lines and before they click "Commit" is a common, unprivileged occurrence and requires no attacker-controlled component at all - just an attacker-crafted repository with a filter that guarantees the race.

No local/physical access, admin rights, or pre-existing malware is required; the trigger is content within a repository the user has cloned or fetched, satisfying the valid-impact criteria.

### Recommendation
Do not decouple the diff used to compute `DiffSelection` line indices from the diff used to build the actual patch:
- Persist and reuse the exact diff (or its immutable byte content) that was current when the user made their line selection, and validate/recompute the patch against that exact diff instead of re-fetching a new one in `applyPatchToIndex`.
- If the working directory content or diff has changed since the selection was captured, refuse to build a partial patch and force the UI to refresh the diff/selection first, mirroring the staleness-check pattern already used in `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
1. Create a repository containing a text file and a `.gitattributes` entry that applies a `clean`/`smudge` filter (or simply a script run via a `post-checkout`/editor auto-format hook) which alters line content/spacing deterministically on each `git diff`/`git status` invocation.
2. In Desktop, open the Changes tab for that file; Desktop fetches diff A via `getWorkingDirectoryDiff` and the user selects a subset of lines (`DiffSelection` built from diff A's hunk offsets), e.g. deselecting a line containing a secret.
3. Before clicking Commit, let the filter/background process alter the file so that a subsequent `git diff` (diff B) has shifted hunk offsets/content relative to diff A (e.g., an extra blank line inserted earlier in the file).
4. Click Commit. `_commitIncludedChanges` passes the stale `file.selection` (based on diff A) to `createCommit` → `stageFiles` → `applyPatchToIndex`, which fetches diff B fresh at `app/src/lib/git/apply.ts:60` and calls `formatPatch(file, diffB)` using the diff-A-relative indices.
5. Inspect the resulting commit: it contains different lines than what the user selected in the UI (e.g., the deselected/secret line is now included, or a selected line is dropped) - with no warning shown to the user.
