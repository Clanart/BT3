### Title
Panic on out-of-range `Participant` in `Decryption::decrypt_with_proof` / `BlameMachine::blame_internal` — denial of service — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and their shared `blame_internal` accept arbitrary `sender`/`recipient` `Participant` values and index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with them. `Participant::new` only rejects zero; any index `> n` causes a `HashMap` index panic — the Rust analog of the CVE's unchecked-NULL dereference: attacker-influenced input crashes the evaluating process.

### Finding Description
`blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`. Inside `decrypt_with_proof`, when a `proof` is supplied, the code evaluates `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`). `enc_keys` only contains entries for registered DKG participants `1..=n`. If `recipient` is a valid nonzero `Participant` greater than `n`, the indexing panics. Likewise `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` panics for an unregistered `sender`.

`AdditionalBlameMachine` is explicitly designed for use by parties who were not DKG members ("capable of evaluating Blame regardless of if the caller was a member", `crypto/dkg/pedpop/src/lib.rs:639-642`), evaluating blame statements built from untrusted `EncryptedMessage::read` / `EncryptionKeyProof::read` bytes plus sender/recipient indices. In Serai's coordinator, blame/accusation transactions deserialize accuser and faulty indices via `Participant::new(u16)` with only a nonzero check (e.g. `coordinator/src/tributary/transaction.rs:346-353`), so an out-of-range index reaches this API. `Decryption::register` (`encryption.rs:356-359`) also `assert!`s against re-registration, though that is unreachable via the `HashMap` keyed maps.

### Impact Explanation
A panic aborts the thread processing the blame evaluation — a denial of service equivalent to the CVE's null-deref crash. For third-party blame auditors and any node code path feeding deserialized participant indices into `blame()`, a crafted accusation kills the process mid-protocol.

### Likelihood Explanation
Any party able to submit a blame statement naming a participant index `> n` (and `!= 0`) triggers it deterministically; no race, no cryptographic assumption needed. Reachability for a fully unprivileged party depends on the caller plumbing indices into `blame()` — within the in-scope crates the panic itself is certain once reached.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` returning `DecryptionError`/`PedPoPError`, or validate `sender`/`recipient` against `1..=n` at the top of `blame`/`blame_internal`.

### Proof of Concept
```rust
// After a DKG completes with n participants (e.g. n = 4):
let mut blame = AdditionalBlameMachine::new(context, 4, commitment_msgs).unwrap();
// Craft an accusation where the "recipient" is a nonzero Participant beyond n.
// Participant::new(5) succeeds (only zero is rejected).
let msg = EncryptedMessage::<C, SecretShare<C::F>>::read(&mut bytes, params).unwrap();
let proof = Some(EncryptionKeyProof::read(&mut proof_bytes).unwrap());
// Panics at encryption.rs:388 on `self.enc_keys[&decryptor]`
let _ = blame.blame(sender, Participant::new(5).unwrap(), msg, proof);
```

Caveat: I verified the panic sites and their guards directly, but did not fully trace the coordinator path that feeds deserialized accuser/faulty indices into `blame`; if the surrounding code already bounds indices to `n`, the reachable surface narrows to direct consumers of the public `blame` API.
