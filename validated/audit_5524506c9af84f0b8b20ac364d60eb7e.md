### Title
Attacker-controlled `n` in `ThresholdKeys::read` forces a disproportionate up-front allocation before input validation - (File: crypto/dkg/src/lib.rs)

### Summary
The GMX report describes an asymmetry where a user-chosen value (revert-string length) forces the keeper to burn ~3x the expected gas. The same class exists in Serai: `ThresholdKeys::read` trusts the serialized `n` field to pre-allocate a `Vec` of `n` field elements before verifying that the byte stream actually contains `n` elements, letting an unprivileged party force memory consumption wildly disproportionate to the bytes they supply.

### Finding Description
`ThresholdKeys::read` is an explicitly in-scope untrusted-bytes entry point. After reading the curve ID, it reads `t`, `n`, and `i` from the attacker-controlled stream:

- `crypto/dkg/src/lib.rs:591-602` — `n` is read as a raw `u16` from the reader with no bound.
- `crypto/dkg/src/lib.rs:604-613` — for `Interpolation::Constant`, it executes `Vec::with_capacity(usize::from(n))` and only then loops `for _ in 0 .. n` calling `C::read_F(reader)?`.
- `crypto/dkg/src/lib.rs:620-623` — a second loop then reads `n` verification shares (`read_G`) into a `HashMap` for `l in 1 ..= n`.

The `with_capacity` call commits `n * size_of::<C::F>()` bytes of memory immediately. With `n = 0xFFFF` and a 32-byte field element, a ~15-byte input forces a ~2 MB allocation, plus `n` attempted `read_F`/`read_G` iterations, before any error is returned. Only after all parsing does `ThresholdParams::new(t, n, i)` / `ThresholdKeys::new` validate `t`/`n`/`i` relationships — far too late to bound the resource cost.

Related reachable sink of the same shape: `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`) loops `for _ in 0 .. u32::from_le_bytes(len)` calling `C::read_G`; while it does not pre-allocate, the loop count is attacker-controlled up to 2^32 and each iteration performs group decompression work (which may itself allocate/fail slowly), again keyed to a claimed count rather than bytes actually present.

### Impact Explanation
Any component that calls `ThresholdKeys::read` (or `SchnorrAggregate::read`) on bytes an unprivileged party can supply — network messages, DB-originating blobs, or DKG artifacts — can be forced to allocate and churn memory orders of magnitude larger than the input provided. Repeated calls produce memory exhaustion / OOM of the processor or coordinator-side code path, i.e., the same "operator spends far more than attacker" asymmetry as the GMX gas-waste issue, mapped to memory/CPU instead of gas.

### Likelihood Explanation
Medium. `ThresholdKeys::read` and `SchnorrAggregate::read` are `pub` deserialization APIs intended to process externally-produced encodings (they are on the explicit untrusted-input list). The trigger is trivial: `n = 0xFFFF` in the header requires no valid field elements at all — the allocation is committed before the first `read_F` fails. The only mitigating factor is the `u16` cap (~2 MB per call for a 32-byte field), so denial of service requires repeated submissions rather than a single message.

### Recommendation
Bound before allocating:

- In `crypto/dkg/src/lib.rs`, validate `ThresholdParams::new(t, n, i)` immediately after reading `t`, `n`, `i` and reject `n` above a protocol maximum before `Vec::with_capacity`.
- Prefer incremental push (`Vec::new` + `push`) over `with_capacity(n)` so memory grows only with bytes actually consumed.
- In `crypto/schnorr/src/aggregate.rs`, cap `Rs` count to a sane maximum (e.g., the multisig threshold bound) before entering the `read_G` loop.

### Proof of Concept
```rust
// crypto/dkg: feed ThresholdKeys::<C>::read a header claiming n = 0xffff
// with no following elements.
let mut bytes = vec![];
// curve ID length + ID (valid C::ID)
bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
bytes.extend(C::ID.as_bytes());
// t = 1, n = 0xffff, i = 1
bytes.extend(1u16.to_le_bytes());
bytes.extend(0xffffu16.to_le_bytes());
bytes.extend(1u16.to_le_bytes());
// interpolation = Constant(0)
bytes.push(0);
// EOF here: read_F will fail on the first element,
// but Vec::with_capacity(65535) of C::F was already committed.
let res = ThresholdKeys::<C>::read(&mut bytes.as_slice());
assert!(res.is_err()); // error only after ~2 MB wasted allocation
```
Each invocation of a few dozen bytes forces a ~2 MB allocation plus up to 65,535 attempted deserializations; looping the call exhausts host memory — the analog of forcing the keeper to pay for gas the attacker never spent.
