### Title
Instant lump-sum reward credit in `BaseRewardPool`/`BaseRewardPoolV2` allows flash-deposit theft of accrued bonus rewards - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` distributes bonus reward tokens (e.g. harvested WOM) to `stakingToken` holders using a `rewardPerTokenStored` accumulator that is bumped by the *entire* newly-arrived reward amount in a single step, divided by the *current* `totalStaked()` at that instant [1](#0-0) . Unlike a streamed (`rewardRate * elapsed`) accumulator, this design lets anyone who deposits into the pool immediately before a `queueNewRewards`/harvest call, and withdraws immediately after, capture a share of rewards that accrued over the entire prior period (e.g. a week), diluting the users who were actually staked for that period — the same "instant deposit ratio instead of time-weighted position" bug class described in the report for RAAC's `StabilityPool`.

### Finding Description
`_provisionReward` in `BaseRewardPool.sol` performs:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
``` [2](#0-1) 
identical logic exists in `BaseRewardPoolV2._provisionReward` [3](#0-2) .

`totalStaked()` is read live at the moment the reward is queued, and the increment is applied to the entire staked pool as if every current staker (including one who deposited in the immediately preceding transaction) had been present for the whole period the newly-arrived reward represents.

When a new staker calls `stakeFor` (e.g., via `MasterMagpie.deposit`/`depositFor` → `BaseRewardPool.updateReward`/`BribeRewardPool.stakeFor`), the `updateReward`/`updateRewards` modifier snapshots `userRewardPerTokenPaid` at the pool's current `rewardPerTokenStored` [4](#0-3) [5](#0-4) . Because `rewardPerTokenStored` has not yet been bumped for the reward that is about to arrive, the new staker's snapshot doesn't exclude that upcoming lump-sum increase — the moment the reward is provisioned, the entire delta is credited proportionally to whatever `totalStaked()` is at that instant, including the newcomer's freshly-deposited balance. This mirrors the reported `StabilityPool.calculateRaacRewards()` flaw of `rewards = totalRewards * userDeposit / totalDeposits`, which used an instantaneous ratio rather than a time-integrated one.

Contrast this with `MasterMagpie`'s own MGP emission, which correctly streams emissions continuously via `lastRewardTimestamp`/`accMGPPerShare` updated on `updatePool` — that mechanism is not vulnerable to this exact issue because emissions accrue smoothly per second rather than being injected in a single lump sum tied to an external harvest event [6](#0-5) . The bonus-reward path through `BaseRewardPool`/`BaseRewardPoolV2`, which handles externally harvested tokens (e.g., WOM from `WombatStaking`), lacks this time-weighting and is exposed to the flash-deposit pattern.

### Impact Explanation
An attacker who deposits a large stake immediately before a `queueNewRewards` call (triggered by a harvest of externally accrued rewards) and withdraws immediately after can capture a disproportionate share of rewards that accrued while they held no position, directly stealing yield from legitimate long-term stakers. This is theft of unclaimed yield belonging to other users, repeatable every time new rewards are queued, and requires no privileged role — any wallet with sufficient capital for a single-transaction (or same-block) deposit/withdraw can execute it.

### Likelihood Explanation
Exploitability depends on (a) `queueNewRewards`/`_provisionReward` being triggered by a permissionless or predictable harvest call (e.g., from `WombatStaking.harvest`) rather than an admin-gated, unpredictable schedule, and (b) the absence of any deposit/withdraw cooldown or same-block restriction in `MasterMagpie`/`BribeRewardPool`. I was not able to fully confirm within the available tool calls whether `WombatStaking.harvest()` is permissionless/predictable enough for reliable front-running, or whether any cooldown exists on `MasterMagpie` deposit/withdraw flows, before the iteration budget was exhausted. This uncertainty should be resolved by a deeper review of `wombat/WombatStaking.sol`'s harvest function and `MasterMagpie`'s `_deposit`/`_withdraw` for any anti-flash-loan guard.

### Recommendation
Convert `_provisionReward` in `BaseRewardPool`/`BaseRewardPoolV2` to a streamed reward-rate model (as used in `BaseGauge`-style contracts referenced in the original report): track a `rewardRate` and `periodFinish`, accrue `rewardPerTokenStored` based on elapsed time since the last checkpoint rather than crediting the full amount instantly against the current `totalStaked()`. Alternatively, enforce a minimum staking duration or cooldown between deposit and withdrawal in `MasterMagpie`/`BribeRewardPool` to prevent same-block or near-instant deposit-then-withdraw sequences around reward provisioning events.

### Proof of Concept
Conceptual sequence (pattern analogous to the RAAC PoC), pending confirmation of harvest permissioning:
1. UserA stakes `stakingToken` via `MasterMagpie.deposit` and remains staked while `WombatStaking` accrues WOM rewards for a week.
2. Attacker observes/anticipates a harvest that will call `IBaseRewardPool.queueNewRewards(amount, WOM)`, and immediately before that call, stakes a large amount via `MasterMagpie.deposit`/`BribeRewardPool.stakeFor`.
3. Harvest fires, calling `_provisionReward`, which bumps `rewardPerTokenStored` using `totalStaked()` that now includes the attacker's large balance — diluting the increment attributable to UserA while still crediting the attacker fully for that increment.
4. Attacker immediately calls `withdraw`/`withdrawFor` (triggering `getReward`), claiming a large share of the week's rewards despite having staked for zero elapsed time, while UserA's `earned()` reflects only the diluted increment. [1](#0-0) [7](#0-6)

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
