### Title
Dust-value outputs are reported as received funds but are unspendable — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The `Scanner` reports any transaction output whose `script_pubkey` matches a registered script as a `ReceivedOutput`, without checking the output's value. An unprivileged party can send dust outputs (below `DUST` = 546 sats, or simply below the marginal fee cost of an input) to the multisig's address. These outputs are indistinguishable from genuine deposits to the scanner, yet they can never be spent: `SignableTransaction::new` treats every `ReceivedOutput` as spendable input value, and each input costs more in fees (each Taproot input adds ~57.5 vbytes) than a dust output contributes. The reported funds are frozen — analogous to an NFT minted into a contract that cannot handle it.

### Finding Description
The scanner's only acceptance criterion is the script:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-214
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    ...
    if let Some(offset) = self.scripts.get(&output.script_pubkey) {
      res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
    }
}
```

No check is made on `output.value`. `ReceivedOutput::value()` happily reports the amount (line 116-118), and the processor path (`get_outputs` in `processor/src/networks/bitcoin.rs:686-740`) forwards these as `Output`s with a `balance()`. On the spend side, `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) sums input values and only enforces dust limits on *payments*, never on inputs. A 1-sat input consumes ~57.5 vbytes of weight; at any non-zero `fee_per_vbyte` it contributes net-negative value, and since it is counted as received balance, an integrator may believe it holds spendable funds that are economically (or absolutely, when value = 0 and no other input covers it) unspendable. Unlike the coinbase maturity case — which is explicitly documented in `scan_block`'s doc comment and filtered by the processor skipping `txdata[0]` — dust filtering is neither performed nor documented.

### Impact Explanation
Any Bitcoin user can send a transaction paying dust (or even 0-value) outputs to a Serai multisig's P2TR script. The scanner reports these as received outputs with a corresponding `ExternalBalance`, crediting deposits that can never be recovered. In the worst case these outputs are committed into `SignableTransaction` inputs, permanently inflating transaction weight and fee cost for every spend that includes them; in the "funds received but not spendable" framing, the reported balance exceeds what can actually be moved, matching the frozen-asset bug class.

### Likelihood Explanation
Sending a dust output requires only a normal Bitcoin transaction to a publicly known multisig address — fully within an unprivileged party's reach. No collusion, no validator misbehavior, no leaked material. The only mitigation is the attacker's cost (the dust value plus fees), which is minimal.

### Recommendation
Filter outputs below `DUST` (or below the marginal fee cost per input at the configured fee rate) in `Scanner::scan_transaction`, or mark `ReceivedOutput`s with a spendability flag so `SignableTransaction::new` can exclude inputs whose value does not exceed their marginal weight cost. Document that sub-dust receipts are ignored.
