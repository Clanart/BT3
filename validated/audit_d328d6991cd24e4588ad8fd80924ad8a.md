### Title
`SchnorrAggregate::verify` accepts a forged aggregate signature over an empty statement set - (crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the Quicksilver "unchecked proof minting" bug, `SchnorrAggregate::verify` performs no check that the aggregate covers at least one signature, nor that `s` is bound to anything. An attacker who supplies `Rs = []` and `s = 0` produces a "proof" that satisfies the verification multiexp (`(-0)·G + nothing = identity`) for an empty `keys_and_challenges` list, even though `SchnorrAggregator::complete` can never honestly emit such an aggregate (it returns `None` when `sigs` is empty). The bytes are fully attacker-controlled via `SchnorrAggregate::read`.

### Finding Description
`SchnorrAggregate::verify` checks only `self.Rs.len() != keys_and_challenges.len()` and then builds the multiexp `Σ z_i·R_i + Σ z_i·c_i·P_i - s·G` [1](#0-0) . With zero entries, the multiexp degenerates to a single pair `(-s, G)` [2](#0-1) , and any `s = 0` makes it the identity. The honest producer path explicitly refuses to emit empty aggregates [3](#0-2) , so a verifying party only ever sees this shape from `SchnorrAggregate::read` on attacker bytes [4](#0-3) . The weights `z_i` derived in `weight()` are irrelevant in the empty case since no challenges were transcripted [5](#0-4) .

### Impact Explanation
This is a proof-system soundness hole: the verifier treats `Ok(true)` as "every listed (key, challenge) was signed", yet nothing was signed. Any integrator that aggregates Schnorr signatures and conditionally verifies - e.g., accepting an aggregate when there are zero expected signatures, or building `keys_and_challenges` dynamically from a message set the attacker can drive to empty - accepts a forged attestation (e.g., "no slashable events", "empty withdrawal batch authorized", "zero-vote tally verified") that honest aggregation could never produce. The same class in Quicksilver let forged proofs mint unbacked assets; here it lets forged aggregates attest statements never signed.

### Likelihood Explanation
Exploitation requires a verifier that invokes `verify` with an empty `keys_and_challenges` while treating the result as meaningful, which is a reachable-but-caller-dependent condition. Within the library itself the invariant "an aggregate exists ⇒ ≥1 signature" is enforced only on the producer side, not on deserialization/verification, so the burden is entirely on callers of a public, untrusted-bytes API. That justifies Medium.

### Recommendation
In `SchnorrAggregate::verify`, reject `self.Rs.is_empty()` (and/or `keys_and_challenges.is_empty()`) before evaluating the multiexp, mirroring the producer-side guard in `SchnorrAggregator::complete`. Optionally also assert `self.s` is canonical via `read_F` (already done) and document that `verify` must never be called with an empty statement set.

### Proof of Concept
```rust
// crypto/schnorr, with any Ciphersuite C
let mut buf = vec![];
// SchnorrAggregate::write layout: u32 len = 0 Rs, then s = 0
buf.extend(0u32.to_le_bytes());
buf.extend(C::F::ZERO.to_repr().as_ref());
let forged = SchnorrAggregate::<C>::read(&mut buf.as_ref()).unwrap();
// Verifier with an empty message/signature set:
assert!(forged.verify(b"some dst", &[])); // returns true; honest complete() returns None
```
The equivalent construction programmatically: `SchnorrAggregate { Rs: vec![], s: C::F::ZERO }.verify(dst, &[])` evaluates `multiexp_vartime(&[(-0, G)])` → identity → `true`.
