### Title
Flashloan-manipulable spot pricing in `SmartWomConvert` causes mispriced WOM→mWOM conversion, permanently misallocating harvested yield - (File: `wombat/SmartWomConvert.sol`)

### Summary
The reported bug class — a strategy trusting a single-block, on-chain-computable exchange rate (`balanceOfy3CRVinWant()`) that can be skewed by a flashloan-funded deposit/withdraw within the same transaction — has a direct analog in `SmartWomConvert.sol`. `currentRatio()` and `maxSwapAmount()` read live, single-block state from the Wombat WOM/mWOM pool (`womAsset.cash()/liability()` and `router.getAmountOut()` spot quote) with no TWAP, no minimum-liquidity check, and no external validation, and this value directly drives how harvested protocol yield (WOM) is split between market-swap and 1:1 mint when `smartConvert()` is invoked.

### Finding Description
`maxSwapAmount()` reads the live `cash`/`liability` of the Wombat WOM asset directly: [1](#0-0) 

`currentRatio()` reads a live spot quote from the WOM/mWOM Wombat pool via the router: [2](#0-1) 

`smartConvert()` uses these two single-block values to decide `convertRatio` — the split between swapping WOM for mWOM on the open market versus 1:1 minting mWOM — with no minimum/maximum bound derived from a time-weighted or otherwise-manipulation-resistant source: [3](#0-2) 

This function is reachable from an ordinary wallet's transaction without any privileged role: `WombatStaking._sendRewards()` calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` whenever a WOM reward fee is processed, and this is triggered from `_toMasterWomAndSendReward()`, which is invoked by the permissionless `harvest()` function (only gated by `_onlyActivePool`, not by any access-controlled role): [4](#0-3) [5](#0-4) 

Because `harvest()` (and `deposit`/`withdraw` via pool helpers, also unprivileged) can be called by any wallet, an attacker can, in the same transaction: (1) execute a large swap/liquidity operation on the Wombat WOM/mWOM pool to push `currentRatio()` and `cash`/`liability` to a favorable extreme, (2) call `WombatStaking.harvest()` (or trigger a deposit/withdraw) so that `smartConvert()` executes using the manipulated ratio, forcing either an unfavorable market swap (extracting value from the swap into the attacker's pocket) or forcing 1:1 minting when it should have market-swapped (permanently over/under-valuing the mWOM credited to the rewarder pool), and (3) reverse the pool manipulation, leaving the protocol's reward accounting permanently skewed since `queueNewRewards()` immediately bakes the resulting `mWom`/`wom` amount into `rewardPerTokenStored` for all stakers: [6](#0-5) 

### Impact Explanation
The amount of `mWom` credited to the reward pool (and thus to all vlMGP/mWomSV stakers) is permanently determined at the moment `smartConvert()` executes, based on a single-block manipulable price. This can permanently misallocate/reduce unclaimed yield delivered to stakers (some of it captured by the manipulator via the same-transaction swap), matching the "theft or permanent freezing of unclaimed yield" impact category. There is no revert path or slippage floor against this specific manipulation — `_minRec` in `smartConvert()` is set equal to `_amountIn`, but that only protects against unfavorable output value, not the ratio/split decision derived from the manipulated spot values themselves, so it doesn't prevent an unfavorable buyback price being locked in for the protocol.

### Likelihood Explanation
Requires a WOM/mWOM Wombat pool with sufficiently shallow liquidity relative to the attacker's flashloan capacity, and coordination of the swap with a harvest/deposit/withdraw call in the same transaction — all of which are permissionless and require no special privileges, only capital (typically obtainable via flashloan). This mirrors exactly the reported bug class (single-block AMM state read directly into a financial decision, unprotected against flashloan skew).

### Recommendation
Do not derive `convertRatio` from a single-block spot read of `cash()/liability()` or `router.getAmountOut()`. Use a time-weighted average price/ratio, or require that `smartConvert()` (and the harvest path that triggers it) be invoked only through mechanisms resistant to atomic manipulation (e.g., restricting the pool ratio input to values bounded by a moving average, or requiring the conversion be executed in a separate, delayed transaction rather than atomically alongside a harvest call).

### Proof of Concept
1. Attacker takes a flashloan and performs a large swap or cash/liability-shifting deposit/withdraw against the Wombat WOM/mWOM pool referenced by `womAsset`/`womMWomPool`, moving `currentRatio()` below `buybackThreshold` (or manipulating `maxSwapAmount()`).
2. In the same transaction, attacker calls `WombatStaking.harvest(_lpToken)` (permissionless), which internally triggers `_sendRewards` → `smartConvert()` on the harvested WOM fee using the manipulated `convertRatio`/`maxSwapAmount`, either forcing an unfavorable swap through the shallow pool (extracted by the attacker on the other side) or forcing straight 1:1 minting at a moment where market price favors the attacker's own swap.
3. Attacker reverses the initial swap/liquidity action and repays the flashloan, keeping the value extracted from the mispriced conversion, while the protocol's reward pool (`IBaseRewardPool(_rewarder).queueNewRewards`) permanently records the resulting (suboptimal) `mWom`/`wom` amount for all stakers.     function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
