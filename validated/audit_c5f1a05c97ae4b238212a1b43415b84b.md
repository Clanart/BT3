## Analysis

The Solana bug pattern is: a state invariant is enforced (or *should* be enforced) in one place, but the actual state-mutating action later doesn't re-check it — allowing accounting/state to drift from reality. The closest Desktop analog is in the GitHub Copilot AI conflict-resolution write path, where a value produced upstream by an LLM (`resolution.path`) is trusted at the point of the file-system write without re-validating it against the actual set of currently-conflicted files, and without excluding the repository's `.git` metadata tree from the allowed write area.

### Title
Copilot conflict-resolution write path accepts model-supplied paths without confirming they are conflicted repo files, permitting writes under `.git/` (e.g. hooks) - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated resolved file content to disk for every entry in `copilotResolutions`, using only `resolveWithin(repository.path, resolution.path)` as a safety check [1](#0-0) . `resolveWithin` only guarantees the resolved path is *within the repository root* — it does not exclude the `.git` directory, and does not require the path to correspond to a file that is actually part of the current merge/rebase/cherry-pick conflict [2](#0-1) .

### Finding Description
The function's own on-disk skip check is conditioned on the file already being present in `workingDirectory.files` and currently conflicted:

```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
``` [3](#0-2) 

If `onDiskFile` is `undefined` — i.e. `resolution.path` does not match *any* file Desktop currently tracks as changed/conflicted — the guard clause is false, so execution falls through to `writeFile` unconditionally. The only remaining gate is `resolveWithin`, which merely confirms the path stays under `repository.path`; it does not exclude `.git/` (hooks, config, etc.) or otherwise restrict the target to files that were part of the merge context. The `resolution.path` values ultimately originate from the Copilot model's JSON response (`path` field), parsed in `parseCopilotConflictResolution` and passed through `reassembleResolutions` [4](#0-3) . Attacker-controlled conflict content (the text of a branch/commit an attacker gets merged/fetched into the victim's repo, containing prompt-injection payloads inside conflict hunks) is exactly the material fed into the model as context for this resolution. There is an earlier `validateResolutionPaths(parsed.resolutions, expectedFiles)` call in `copilot-store.ts` intended to constrain paths to the conflicted-file set [5](#0-4) , but its implementation could not be located/verified in this pass, and — critically — `_applyCopilotConflictResolutions` does not re-apply that constraint at write time. Relying on a single upstream check with no defense-in-depth at the actual side-effecting write mirrors the reported bug class: state (here, "is this file actually one of the ones under conflict resolution") is validated once but not re-confirmed at the point where the consequential action (file write + `git add`) happens.

### Impact Explanation
If a resolved path escapes the "is this an actual conflicted file" constraint while still resolving under the repo root, Desktop will silently write model-controlled content into that path and stage it (`pathsToStage.push`, then `git add`) [6](#0-5) . Because `.git/` lives under `repository.path`, a path such as `.git/hooks/post-checkout` would pass `resolveWithin` and be written with attacker/model-influenced content, giving a code-execution primitive triggered by any subsequent `checkout`/`merge`/`rebase` in that repo — a severe escalation beyond "just wrong commit contents." Even absent hook write, corrupting arbitrary same-repo files that the user never intended to touch and having them silently staged/committed is a "silent corruption of what the user commits" impact.

### Likelihood Explanation
Exploitability hinges on whether `validateResolutionPaths` (not directly inspected in this session) strictly whitelists `resolution.path` to the exact set of conflicted file paths sent in the prompt. If that check is robust and applied on every response path, this specific vector may be mitigated upstream today — but the write path itself contains no independent enforcement, so any gap, retry-path skip, or future refactor of that upstream validation reintroduces the flaw with no local defense. Given the feature also requires social-engineering-free preconditions (an attacker-authored branch merged/fetched normally, plus the victim using the "Resolve with Copilot" feature), likelihood is moderate and directly tied to the strength of the unverified upstream check.

### Recommendation
In `_applyCopilotConflictResolutions`, before calling `writeFile`, explicitly require that `resolution.path` matches one of the file paths returned by `getConflictedFiles(state.changesState.workingDirectory, conflictState.manualResolutions)` for the *current* conflict state, and reject (skip + log) any path that does not. Additionally, harden `resolveWithin`/the call site to reject any resolved path whose relative component begins with `.git` (case-insensitively, accounting for path separators), so AI/model output can never target repository metadata regardless of upstream validation correctness.

### Proof of Concept
1. Attacker crafts a branch/commit whose conflicting hunks contain a prompt-injection payload designed to make the Copilot conflict-resolution model emit an additional `resolutions[]` entry with `"path": ".git/hooks/post-checkout"` and executable shell content as `resolvedContent`.
2. Victim clones/fetches this branch and merges it, hits conflicts, and selects "Resolve with Copilot."
3. If the model complies (whether because upstream `validateResolutionPaths` is looser than expected or is bypassed on a particular code path) and the user clicks "Continue Merge," `_applyCopilotConflictResolutions` writes the hook file since `onDiskFile === undefined` short-circuits the skip check, and `resolveWithin` only confirms it's under repo root [7](#0-6) .
4. Next `git checkout` in that repository executes the attacker's hook.

Note: I was not able to retrieve the implementation of `validateResolutionPaths` within the available tool budget, so I cannot confirm whether it currently blocks this exact scenario end-to-end; the structural gap in the write-path guard itself, however, is directly verified in the cited code.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
