## Analysis

**Bug-class reduction (M-17):** the broken invariant is *"the incentive/reward is granted for merely not reverting, while a costly late step can be silently skipped by starving it of gas via the EIP-150 63/64 rule, and the try/catch that isolates that step swallows the resulting revert."* The attacker primitive is: control the outer gas limit so only the *early*, cheap parts of a function succeed, while a later, expensive sub-call reverts from out-of-gas but gets caught rather than propagated, and reward eligibility is checked only against "did the outer call revert," not "did the real work happen."

**Local analog found:** `HyperbridgeLzEndpoint.onAccept()` [1](#0-0)  wraps the actual cross-chain delivery (`ILayerZeroReceiver.lzReceive`) in a `try/catch` that treats **any** revert — deterministic or out-of-gas — as a recoverable failure, storing the payload for later retry instead of propagating the failure. Crucially, the ISMP nonce is advanced **before** this try/catch, by design, so a reverting `lzReceive` never rolls it back.

This `onAccept` call is invoked from `EvmHost.dispatchIncoming(PostRequest, relayer)` via a bare low-level `.call()` [2](#0-1) . The delivery receipt `_requestReceipts[commitment] = relayer` is written **before** the call and is only deleted if the *outer* call to `onAccept` itself reverts. Since `HyperbridgeLzEndpoint.onAccept` catches the inner `lzReceive` failure and returns normally, `dispatchIncoming` always sees `success = true`, keeps the receipt, and emits `PostRequestHandled`.

That receipt (`RequestReceipts[commitment]`) is exactly the artifact the off-chain relayer-incentive pipeline uses as *proof of delivery* to pay out rewards — both the standard fee-accumulation flow and the newer `OutboundRequestDeliveryReward` claim path explicitly rely on "the address proven in `RequestReceipts[commitment]`" [3](#0-2) , with the design note that "the reward goes to the fastest deliverer" and is checked purely against that receipt slot [4](#0-3) .

### Title
Gas-griefed `onAccept` lets a relayer collect delivery reward while skipping actual message execution - (File: `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
A relayer submitting the `handlePostRequests` transaction controls the overall gas limit. By under-provisioning gas so that the inner `lzReceive` call in `HyperbridgeLzEndpoint.onAccept` runs out of gas, the relayer triggers the `catch` branch — which was designed only for deterministic application-level reverts — instead of the intended delivery. `onAccept` still returns successfully to `EvmHost.dispatchIncoming`, so the delivery receipt is retained and the relayer becomes eligible for the delivery reward, exactly as the M-17 report describes for `Upkeep.performUpkeep`.

### Finding Description
- `dispatchIncoming` sets `_requestReceipts[commitment] = relayer` before calling out, and only deletes it if the outer `.call()` to `onAccept` returns `false` [5](#0-4) .
- `HyperbridgeLzEndpoint.onAccept` advances the inbound nonce unconditionally, then wraps the real delivery (`lzReceive`) in `try/catch`, explicitly to prevent "a deterministic revert... from reverting `onAccept`" [6](#0-5) . The catch clause does not distinguish an intentional application revert from an out-of-gas revert caused by insufficient forwarded gas (EIP-150's 63/64 rule).
- A relayer can therefore size the transaction's gas limit precisely so `onAccept`'s bookkeeping (nonce advance, receipt retention) completes, while `lzReceive` — the step that actually performs the OApp's cross-chain effect — starves and reverts, landing in the swallow-and-store branch instead of failing the whole delivery.
- Because reward eligibility for relayers is derived purely from `RequestReceipts[commitment]` on the destination (per the outbound-request incentivization design) rather than from confirmation that the receiving OApp's logic actually ran, the relayer is paid for "delivering" a message that never really executed.

### Impact Explanation
This lets any permissionless relayer repeatedly collect delivery incentives (treasury-funded `OutboundRequestDeliveryReward` for hyperbridge-originated messages, or standard delivery fees for user messages) while systematically starving `lzReceive` of gas, at negligible cost to itself (it still controls/pays for its own gas budget). The genuine cross-chain effect is not executed and instead sits in `_inboundPayloadHashes`, requiring a separate, later `retryPayload` call to actually complete — a real analog of skipping the SALT-transfer step in the source report: the "task" that the reward is meant to compensate is skipped, but the reward is still paid.

### Likelihood Explanation
The attack requires no privileged role, no malicious relayer/prover collusion beyond the caller itself, and no proof forgery — only precise gas-limit tuning on a permissionless call to `handlePostRequests`/`dispatchIncoming`. EIP-150 gas forwarding behavior is deterministic and can be pre-computed/tested, making this practically reproducible by any relayer wishing to farm rewards cheaply.

### Recommendation
In `HyperbridgeLzEndpoint.onAccept`, forward an explicit, sufficiently large gas stipend to the `lzReceive` sub-call (or check `gasleft()` against a minimum threshold before attempting it) and treat gas-insufficiency distinctly from application-level reverts — e.g., revert the whole `onAccept` (and thus the receipt/reward) if there isn't enough gas left to plausibly complete `lzReceive`, mirroring the "check gas at the start" mitigation recommended for M-17.

### Proof of Concept
1. Relayer calls `HandlerV2.handlePostRequests` (which calls `EvmHost.dispatchIncoming`) with a crafted gas limit such that after paying for proof verification and `EvmHost`/`HyperbridgeLzEndpoint.onAccept` overhead, only a small remainder is forwarded to `ILayerZeroReceiver(receiverAddr).lzReceive(...)`.
2. `lzReceive` runs out of gas and reverts; `HyperbridgeLzEndpoint.onAccept`'s `catch` block executes, storing `_inboundPayloadHashes[...]` and emitting `InboundPayloadStored`, while the nonce was already advanced.
3. `onAccept` returns without reverting; `EvmHost.dispatchIncoming`'s `.call()` sees `success = true`, keeps `_requestReceipts[commitment] = relayer`, and emits `PostRequestHandled`.
4. The relayer later submits `claim_outbound_request_delivery_reward` / the standard fee-claim proving `RequestReceipts[commitment]` on the destination, and is paid — despite the OApp never having actually received the message.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        // Verify source is this adapter on another chain
        if (keccak256(request.from) != keccak256(abi.encodePacked(address(this)))) revert UnknownSource();

        // Decode the LZ message from the ISMP body
        (
            bytes32 guid,
            uint32 srcEid,
            bytes32 sender,
            uint64 nonce,
            bytes32 receiver,
            bytes memory message
        ) = abi.decode(request.body, (bytes32, uint32, bytes32, uint64, bytes32, bytes));

        // Reject `expectedEid == 0` so unconfigured sources don't collide with `srcEid = 0`.
        uint32 expectedEid = _stateMachineToEid[keccak256(request.source)];
        if (expectedEid == 0 || expectedEid != srcEid) revert UnknownSource();

        // Validate and advance the nonce. The nonce is committed BEFORE (and independently of)
        // OApp execution: a reverting `lzReceive` must not roll back this write. Otherwise the
        // message would be retried forever at the same nonce and every later nonce would be
        // permanently rejected, bricking the (receiver, srcEid, sender) channel.
        address receiverAddr = address(uint160(uint256(receiver)));
        uint64 expectedNonce = _inboundNonce[receiverAddr][srcEid][sender] + 1;
        if (nonce != expectedNonce) revert InvalidNonce(expectedNonce, nonce);
        _inboundNonce[receiverAddr][srcEid][sender] = nonce;

        // Deliver to the OApp. Isolate the external call so a deterministic revert (zero
        // recipient, over-cap mint, blocklisted recipient, malformed payload, paused OApp, etc.)
        // does not revert `onAccept`. On failure the payload is retained for later retry/recovery
        // via retryPayload/clear/skip/nilify/burn.
        Origin memory origin = Origin({srcEid: srcEid, sender: sender, nonce: nonce});
        try ILayerZeroReceiver(receiverAddr).lzReceive(origin, guid, message, address(0), "") {
            // delivered successfully
        } catch {
            bytes32 payloadHash = keccak256(abi.encode(guid, message));
            _inboundPayloadHashes[receiverAddr][srcEid][sender][nonce] = payloadHash;
            emit InboundPayloadStored(receiverAddr, srcEid, sender, nonce, payloadHash);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

## Open questions

1. **One commitment, one reward, regardless of message size.** The consensus claim is a flat per-destination value. Do we want the request claim flat too, or scaled by request body size? Flat is simpler and matches the creator's wording ("award BRIDGE tokens"). Recommend flat for v1 and revisit if operators report it under or overpaying.
2. **Payee account type.** Sr25519 only (matches consensus claim) or also support Ed25519 / EVM addresses on the payee side? Recommend Sr25519 only for v1.
3. **Claim ordering vs delivery race.** There is a first-wins race on the destination side: whichever relayer lands the delivery transaction first has its address written into `RequestReceipts[commitment]`, and every later delivery of the same commitment no-ops. The race winner is unambiguous because the receipt slot records exactly one address, and `process_outbound_request_delivery_claim` only pays the address proven in that slot, so a relayer that delivered second fails `OutboundRequestSignerMismatch`. Idempotency is automatic and no extra logic is needed, but operators should understand the reward goes to the fastest deliverer, not the first to claim.
4. **Treasury funding model.** The same `T::TreasuryPalletId` already used by the consensus claim. Governance tops it up. No new account.
