### Title
`governance_vote` RPC accepts unauthenticated votes as the node's own identity with no caller authorization - (File: kaiax/gov/headergov/impl/api.go)

### Summary
The `governance_vote` JSON-RPC method, registered with `Public: true` in `kaiax/gov/headergov/impl/api.go`, casts a governance vote attributed to the local node's own key (`api.h.nodeAddress`) with no check on *who* is making the RPC call. Any caller who can reach the node's HTTP/WS RPC endpoint on the `governance` namespace can invoke `governance_vote` and cause that node to queue a vote for arbitrary governance parameters (unit price, minting amount, reward ratio, KIP-71 parameters, etc.), which is exactly the "missing authentication for critical function" pattern in the reference Airflow advisory (unauthenticated write to a sensitive control-plane function). [1](#0-0) 

### Finding Description
`headerGovModule.APIs()` exposes the `governance` namespace as `Public: true`: [1](#0-0) 

The `Vote` handler does not derive the voter from any request-scoped credential (no signature over the RPC payload, no ACL, no token). It uses the node's fixed identity (`api.h.nodeAddress`) as the voter, and the only "authorization" check is whether that fixed node identity equals the configured `GoverningNode` when governance mode is `single` (the mode used on Mainnet/Kairos per the module's own README): [2](#0-1) 

Because the check is against the node's static identity rather than against the RPC caller's identity, the endpoint provides no actual caller authentication: whoever can reach the RPC port of the governing node (or of any node, though only the governing node's vote is ultimately effective in `single` mode) can invoke `governance_vote` and push a vote into `myVotes`, which then gets embedded in `header.Vote` once that node produces a block: [3](#0-2) 

This mirrors GHSA-h88f-r7cw-8fv3: a state-mutating, "critical" endpoint (there: variable import; here: governance parameter vote) is exposed without verifying the caller's authorization to invoke it, relying instead on an implicit assumption (there: that only trusted users reach the endpoint; here: that the governing node never exposes public RPC).

### Impact Explanation
If the governing node (the CN whose key equals `governance.governingnode`) exposes its `governance` RPC namespace over a network-reachable HTTP/WS endpoint — which the code does not prevent since `Public: true` makes it eligible for default/public API exposure — any unauthenticated network caller can queue votes on behalf of that node for parameters including `governance.unitprice`, `reward.mintingamount`, `reward.ratio`, `kip71.*` base-fee parameters, and `istanbul.committeesize`. Ratified votes directly alter fee levels, reward/inflation distribution, and consensus committee sizing network-wide, which is concrete governance-parameter and reward-distribution abuse per the validated impact categories (fee abuse, reward redirection, state divergence risk).

### Likelihood Explanation
Exploitation requires that the specific governing node's RPC be reachable by an untrusted caller on the `governance` namespace. Kaia's operational conventions typically restrict validator/CN admin-adjacent RPC exposure, but nothing in the code enforces this — the namespace is marked `Public: true` and registration only depends on the operator's `--rpc.api`/`--ws.api` module list, not on any additional in-code authentication of the caller. This differs from typical "operator misconfiguration only" bugs because the vulnerability is the total absence of a caller-authentication layer at the RPC-handler level (the check that exists authenticates the *node*, not the *caller*), which is squarely the missing-authentication root cause class from the reference CVE. Likelihood is rated Medium because it depends on the CN operator's RPC exposure choices, which some CN operators do enable for gasless/auction/monitoring integrations that share the same HTTP/WS listener.

### Recommendation
- Restrict `governance_vote` (and other state-mutating governance RPCs) to `IPCOnly: true` by default, or gate it behind explicit node-level authentication (e.g., signed RPC requests, mTLS, or a local-only unix-socket policy) rather than relying on operators to keep the RPC endpoint private.
- Add defense-in-depth: even if RPC is exposed, require the caller to supply a signature/credential proving the request is being made by (or with authorization from) the node operator, separate from the node's own consensus key.
- Document and enforce (e.g., via a startup warning or hard failure) that `governance` namespace write methods must never be enabled on public HTTP/WS listeners for the governing node.

### Proof of Concept
1. Identify a CN that is the current `governance.governingnode` and that exposes the `governance` namespace over public HTTP/WS RPC (e.g., `--http.api governance` without additional network restriction).
2. As an unauthenticated remote caller, send:
```
curl "http://<governing-node-host>:8551" -X POST -H 'Content-Type: application/json' --data '
  {"jsonrpc":"2.0","id":1,"method":"governance_vote","params":[
    "governance.unitprice",
    1
  ]}'
```
3. The call succeeds with `"(kaiax) Your vote is prepared..."` and the vote is queued in `myVotes` on that node with no verification that the HTTP caller had any right to direct that node's governance behavior.
4. When the governing node next proposes a block, the attacker-submitted vote is written into `header.Vote`, and at the next epoch boundary it can be ratified into `header.Governance`, altering unit price (or any other mutable governance parameter) network-wide.

Note: I could not fully verify (within available indexing) whether any deployment-level default (e.g. `cmd/utils/config.go` default RPC module list) universally excludes the `governance` namespace from default public HTTP/WS APIs — the default module-list constants were not found in the indexed portion of `cmd/utils/config.go`. This should be verified directly in a full checkout before finalizing severity/likelihood.

func (api *headerGovAPI) Vote(name string, value any) (string, error) {
	var (
		voter     = api.h.nodeAddress
		nextBlock = api.h.Chain.CurrentBlock().NumberU64() + 1
		gp        = api.h.GetParamSet(nextBlock)
		gMode     = gp.GovernanceMode
	)

	if gMode == "single" && voter != gp.GoverningNode {
		return "", ErrVotePermissionDenied
	}

**File:** kaiax/gov/headergov/README.md (L33-47)
```markdown
A vote is initiated by a governing member of the GC casting a vote.
The vote is cast by the `governance_vote` API, which is inscribed in the block header `header.Vote` when the node that received the API call becomes the proposer.
The voter casts a vote as a tuple `(parameter name, new value)`.
The vote is collected for the entire epoch.

At every epoch block (i.e., `k*epoch` blocks), the node that becomes the proposer will check if the vote has been ratified.
If the vote is ratified, the node will announce the ratification in the block header `header.Governance`.
In other words, `header.Governance` can contain data only at epoch blocks.
If there are no votes in an epoch, the next starting block of the epoch will have an empty `header.Governance`.
It contains a JSON object of `{name: value}` for each ratified parameter.

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.
```
