## Title
Attacker-controlled `.gitmodules` with `file://` URL can be force-enabled via `allowFileProtocol`, allowing a malicious repo to pull arbitrary local paths into the working tree - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` boolean that, when `true`, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. `protocol.file.allow=always` is the exact Git hardening flag that was introduced upstream (Git 2.35.2+/CVE-2022-39253-class fixes) specifically to stop `file://` submodule URLs from silently cloning arbitrary local filesystem paths into a repository's working tree. Forcing it back to `always` for any repository re-opens that class of issue for any repo where this flag is threaded through as `true`. [1](#0-0) 

### Finding Description
`checkoutBranch` and `checkoutCommit` both take an `allowFileProtocol` parameter (default `false`) and forward it unchanged into `updateSubmodulesAfterOperation`: [2](#0-1) [3](#0-2) 

Inside `updateSubmodulesAfterOperation`, when `allowFileProtocol` is `true`, the args array is built as:
```
['-c', 'protocol.file.allow=always', 'submodule', 'update', '--init', '--recursive']
``` [4](#0-3) 

This is the exact same flag Git's own security fix restricts by default (`protocol.file.allow=user` is the modern safe default), because a repository's `.gitmodules` file is attacker-controlled content: a cloned repo can declare a submodule with `url = file:///Users/victim/.ssh` (or any other path on the local disk). With `protocol.file.allow=always` forced, `git submodule update --init --recursive` will treat that local path as a valid remote and "clone" its contents into the submodule directory inside the user's repository working tree — without any confirmation. Because the resulting files land inside the repository, they become part of what the user subsequently stages, commits, and pushes, satisfying the "silent corruption of what the user commits or pushes" / credential-exfiltration impact categories: sensitive local files (SSH keys, config files, credentials) can be exfiltrated to a remote (e.g., a public fork) simply by the victim opening the branch/commit that carries the malicious `.gitmodules` entry, if Desktop's own code path invokes checkout/commit with `allowFileProtocol: true`.

The broken invariant mirrors the reentrancy report's core pattern: a security-relevant guard (there: burn-before-transfer; here: `protocol.file.allow` restriction) is bypassed by a flag whose state is not re-validated against the actual trust level of the object being processed (there: attacker-controlled contract re-entering before state update; here: attacker-controlled `.gitmodules` content processed under an explicitly-loosened protocol restriction). The `test-repo` fixtures in `app/test/helpers/repositories.ts` and various tests already need `-c protocol.file.allow=always` explicitly to add local submodules, confirming this flag is normally OFF and is the load-bearing control preventing file:// submodule abuse. [5](#0-4) 

### Impact Explanation
If a Desktop code path (e.g., `checkoutBranch`/`checkoutCommit` invoked with `allowFileProtocol: true` from a UI flow that doesn't distinguish "this is a submodule I already trust" from "this is an arbitrary attacker-supplied `.gitmodules`") is reachable when opening/checking out an attacker-authored branch or commit, the impact is:
- Silent disclosure of local files (SSH keys, credentials, git config) into the working tree of a repository the victim controls.
- Because the files land inside the tracked working directory, a subsequent normal `git add`/commit/push by the victim silently exfiltrates that local data to the (possibly public) remote — matching the accepted "silent corruption of what the user commits or pushes" / "credential/token exfiltration" impact class.

This would be High impact if reachable from an untrusted/attacker-controlled repository checkout flow, since it requires no unusual user action beyond checking out a branch/commit that a normal Desktop workflow would perform (fetch a branch → checkout → commit/push).

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, which call sites in `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts` pass `allowFileProtocol: true` to `checkoutBranch`/`checkoutCommit`, and under what conditions (e.g., only for Desktop's own already-initialized submodules vs. arbitrary untrusted checkouts). The grep results show 8–9 matching call sites in `app-store.ts` and 6 in `dispatcher.ts`, but I could not inspect their surrounding context before running out of iterations. This is the critical missing piece: if `allowFileProtocol: true` is only ever passed for submodules that were already explicitly initialized by the user with trusted URLs (not attacker-controlled `.gitmodules` content on first checkout of an untrusted branch), the practical likelihood is low. If it is passed unconditionally on generic branch/commit checkout regardless of provenance, likelihood is high.

### Recommendation
- Audit every call site passing `allowFileProtocol: true` in `app-store.ts`/`dispatcher.ts` and confirm it is only used for re-affirming already-trusted, previously-initialized submodule paths — never for the first-time processing of an untrusted `.gitmodules` from a freshly fetched/cloned branch or commit.
- Prefer Git's safer default `protocol.file.allow=user` (or omit the override entirely) unless the specific submodule URL has been explicitly allow-listed by the user, rather than blanket `=always`.
- Add a check that inspects `.gitmodules` for `file://` URLs (or bare local paths) before invoking `submodule update --init --recursive` with `allowFileProtocol: true`, and surface a confirmation prompt if any submodule URL resolves outside expected remote hosts.

### Proof of Concept
Because I could not verify the exact call sites in `app-store.ts`/`dispatcher.ts` that set `allowFileProtocol: true` (tool budget exhausted), I can only provide the conceptual PoC based on confirmed code paths:
1. Attacker creates a public repo with a `.gitmodules` entry: `[submodule "x"] path = x url = file:///home/victim/.ssh`.
2. Victim uses GitHub Desktop to fetch/checkout the branch or commit containing this `.gitmodules`, via a code path in `checkout.ts` that calls `updateSubmodulesAfterOperation(..., allowFileProtocol=true)`.
3. `git -c protocol.file.allow=always submodule update --init --recursive` executes, copying `/home/victim/.ssh` contents into the repo's working tree at path `x`.
4. Victim commits/pushes as part of normal workflow, exfiltrating the SSH keys to the attacker-visible remote.

This PoC's step 2 (confirming Desktop actually reaches `allowFileProtocol=true` for an *untrusted* checkout, not just for reinitializing known submodules) is the part that requires further investigation with full file access — a background Devin session with terminal/filesystem access should trace all callers of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` in `app-store.ts` and `dispatcher.ts` to confirm exploitability before treating this as a confirmed finding.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
