Based on the investigation, the strongest local analog to the "bailout" bug class (push-based fund transfer whose success is required to change protocol state, letting the transfer target block a state transition it shouldn't control) is in the Intent Gateway's cross-chain escrow release path.

### Title
Intent Gateway escrow release/refund permanently locks an entire order's funds if any single escrowed token transfer reverts, with no timeout-based recovery path - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s cross-chain settlement (`RedeemEscrow`/`RefundEscrow`) dispatches messages with `timeout: 0` (no expiry), and the destination-side `_withdraw()` handler pushes every escrowed token to the beneficiary in a single loop that reverts the whole call if any one transfer fails. Because `onAccept` failures are non-persistent retries in `EvmHost.dispatchIncoming` (it deletes the receipt and lets the relayer resubmit), a single permanently-blocking token in a multi-asset order (paused/blacklisted ERC20, a beneficiary that can't receive native ETH, etc.) makes the message undeliverable forever, and — because there is no timeout — it can never fall back to a timeout-refund path either. All other, otherwise-transferable assets in that same order become permanently unrecoverable, exactly mirroring the bailout report's root cause: a mechanism dependent on a **push transfer** succeeding is used to gate an unrelated state transition (fund release) that should not depend on the target's cooperation.

### Finding Description
`_cancelFromDest` and the cross-chain fill path both dispatch `DispatchPost` messages with `timeout: 0`: [1](#0-0) 

On the source chain, `onAccept` calls `withdraw()` → `_withdraw()`, which iterates over **all** of the order's escrowed tokens and pushes them to the single `beneficiary` in one loop: [2](#0-1) 

If any single token in `body.tokens` reverts on transfer (paused/blacklisted ERC20, or a native-ETH beneficiary without a `receive`/payable fallback), the entire `_withdraw` call reverts, so **no** token in the order is released — not even the ones that would have transferred fine.

`EvmHost.dispatchIncoming` treats an `onAccept` revert as "retry later": it deletes the just-written request receipt and returns without emitting a delivered event, rather than persisting partial progress: [3](#0-2) 

Because the underlying message was dispatched with `timeout: 0`, it can never be processed via the timeout path (`dispatchTimeOut`) as an alternative recovery route — the message is retryable indefinitely but never actually times out.

### Impact Explanation
This is a fund-loss/fund-lock defect inside core bridge custody logic (escrow release), not a peer/relayer/governance-trust issue. A single non-transferable asset among an order's escrowed tokens (which can arise from ordinary external events like a stablecoin issuer blacklisting an address, or a beneficiary contract that reverts on receiving ETH) permanently traps every other escrowed asset in that same order commitment, with no governance or user-triggered recovery path available because the underlying cross-chain message never times out.

### Likelihood Explanation
No relayer/prover/admin compromise is required — any order whose beneficiary interacts with a token that can later block transfers (blacklist, pause, or fee-on-transfer edge cases) or whose native-ETH beneficiary can't receive value hits this path through completely normal usage of `cancelOrder`/`fillOrder`. It's a design gap rather than a contrived attack, but it is directly reachable by the order's own on-chain conditions without any privileged actor.

### Recommendation
Make `_withdraw` resilient per-asset: use try/catch (or low-level call + fallback holding balance) around each token transfer so a single failing asset doesn't block release of the others, and/or set a non-zero timeout on `RedeemEscrow`/`RefundEscrow` dispatches so a permanently undeliverable settlement can fall back to the existing timeout-refund mechanism instead of being retried forever with no escape hatch.

### Proof of Concept
1. Place a cross-chain order whose `order.inputs` contains two ERC-20 tokens, `A` (well-behaved) and `B` (has an issuer-controlled blacklist).
2. After the order is escrowed, have `B`'s issuer blacklist `order.user` (a routine, non-malicious external event, e.g. compliance action) or use a token with a `transfer` that can be paused.
3. Cancel the order from the destination chain (`_cancelFromDest`), which dispatches the `RefundEscrow` `DispatchPost` with `timeout: 0`. [4](#0-3) 
4. The relayer delivers the message to the source chain; `onAccept` → `withdraw()` → `_withdraw()` attempts to transfer both `A` and `B` to `order.user`; the transfer of `B` reverts, reverting the whole `_withdraw` call. [2](#0-1) 
5. `EvmHost.dispatchIncoming` deletes the request receipt and returns, allowing indefinite retries, but since `timeout` was `0`, the message can never expire into the timeout-refund path. [3](#0-2) 
6. Result: token `A`, which was perfectly transferable, remains permanently locked in escrow alongside `B`, with no available recovery mechanism.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
