### Title
Tokenfactory `MsgChangeAdmin` performs an irreversible single-step admin transfer, allowing permanent loss of denom control from a single mistyped address - (File: x/tokenfactory/keeper/msg_server.go)

### Summary
The tokenfactory module's `ChangeAdmin` message handler reassigns the denom admin in a single atomic step, directly analogous to the reported `changeAdmin` bug class (ADM-1). There is no push/pull, no acceptance step by the new admin, and no validation that the destination address is reachable/controlled by anyone. A single incorrect `MsgChangeAdmin` transaction permanently and irrevocably transfers away all admin capabilities (mint, burn, set-metadata, further admin changes) for that tokenfactory denom.

### Finding Description
`msgServer.ChangeAdmin` in [1](#0-0)  checks only that the sender is the current admin and that the new admin differs from the current one, then calls `server.setAdmin` which unconditionally overwrites `AuthorityMetadata.Admin` with the caller-supplied string and persists it: [2](#0-1) . `MsgChangeAdmin.ValidateBasic` only checks that `NewAdmin` parses as a valid bech32 address; it does not verify that the address is controlled by any live account, nor does it implement any two-step confirmation: [3](#0-2) . This mirrors exactly the ADM-1 bug class: a privileged role (here, denom admin) can be errantly or maliciously transferred to the wrong address in one step, with no "pull"/acceptance step to catch mistakes, and — unlike a governance-controlled global admin — this is directly reachable by any ordinary user who created a tokenfactory denom, satisfying the "tokenfactory denom creator" reachable-actor class.

The denom's admin controls minting, burning, and metadata for that denom: [4](#0-3) . Once `ChangeAdmin` succeeds, the CLI/tests confirm the change takes full effect immediately and the old admin loses all authority, with no way to reclaim it: [5](#0-4) .

### Impact Explanation
If an admin submits `MsgChangeAdmin` with a mistyped, unreachable, or otherwise inaccessible `new_admin` address (a typo'd bech32 address, an address whose key was never generated, or a smart-contract address that cannot sign tokenfactory messages), admin control over that denom's mint/burn/metadata authority is permanently and irrecoverably lost — no further minting, burning, or admin changes can ever occur for that denom. This is a permanent freezing of privileged functionality for the affected denom, matching the "permanent freezing" impact class in scope. Given tokenfactory denoms can represent real economic value (wrapped/synthetic assets, pointer-bridged tokens, etc.), losing admin capability permanently prevents legitimate supply management for that asset.

### Likelihood Explanation
This requires no special privilege beyond being the current admin of a self-created tokenfactory denom — any user can create a denom via `MsgCreateDenom` and become its admin, then call `MsgChangeAdmin` themselves: [6](#0-5) . A single typo, copy-paste error, or supplying an address the caller does not actually control is sufficient to trigger irreversible loss — this class of user error is common in practice (as evidenced by the underlying report explicitly calling out `changeAdmin`-style transfers as error-prone enough to warrant a two-step process).

### Recommendation
Implement a two-step "push/pull" admin transfer for `MsgChangeAdmin`: store the proposed new admin as "pending" and require a separate `MsgAcceptAdmin`-style transaction signed by the new admin to finalize the transfer, mirroring the fix already adopted for the referenced GLOBAL-1/ADM-1 report. Optionally retain a direct-relinquish path (e.g., setting admin to `""`) as an explicit, clearly-named separate action.

### Proof of Concept
1. Create a tokenfactory denom: `seid tx tokenfactory create-denom mytoken --from alice` — Alice becomes admin (`CreateDenom` sets sender as admin).
2. Alice calls `seid tx tokenfactory change-admin factory/alice/mytoken sei1<mistyped-or-uncontrolled-address> --from alice`, as in the integration test pattern at [7](#0-6) .
3. `ChangeAdmin` succeeds in one step (`msg_server.go:156-186`), immediately overwriting `AuthorityMetadata.Admin`.
4. Alice (or anyone) can no longer call `Mint`, `Burn`, `ChangeAdmin`, or `SetDenomMetadata` for `factory/alice/mytoken`, because those handlers all check `msg.Sender != authorityMetadata.GetAdmin()` and the new admin never actually controls that address/key — permanently freezing the denom's admin functions with no recovery path.

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
