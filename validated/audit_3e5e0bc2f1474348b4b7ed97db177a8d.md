## Title
Overpaid native-token fee swaps in `EvmHost.dispatch()`/`fundRequest()` permanently strand the caller's refund in the host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the closest local analog to the "blind swap with no slippage protection" bug class in the external report. Where the Balancer report shows an unbounded-output swap that lets an attacker extract nearly all value, Hyperbridge's `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all perform an *exact-output* native swap (`swapETHForExactTokens`) directly against a Uniswap V2 router, with the token recipient hardcoded to `address(this)` and no handling of the ETH refund that the router sends back for any unused `msg.value`. ### Finding Description
In each of the three entry points, the pattern is identical:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` computes the exact ETH input needed to buy `post.fee` (or `get.fee`/`amount`) units of `feeToken()`, and — per the standard Uniswap V2 Router02 implementation — refunds any `msg.value` in excess of that computed input to `msg.sender`. Because `EvmHost` itself is the caller of the router (not the end user), that refund lands back on the `EvmHost` contract, not on `_msgSender()` (the actual fee payer). None of the three functions read or forward this refund; there is no `receive()`/refund-sweep logic tied to the caller in this code path, and the token recipient of the swap is fixed to `address(this)` rather than the payer.

Any caller who supplies `msg.value` larger than the exact ETH cost of the fee at execution time — which is the normal, expected client behavior since the docs explicitly warn "Will revert if enough native tokens are not provided," pushing integrators to send a buffer — has the excess silently absorbed by the contract instead of returned. This is functionally the same broken invariant as the seed report ("a swap wrapper with no protection for what the caller actually receives back"), just manifesting as a locked/lost refund instead of a sandwich-fed loss: the value that should return exactly once to the rightful beneficiary (the fee payer) does not.

### Impact Explanation
Every overpaid `dispatch()`/`fundRequest()` call using the native-token path permanently loses the excess ETH from the caller's perspective — the funds are not "moved exactly once to the rightful beneficiary," matching the bounty's fund-loss category. This is triggerable by any unprivileged user through a normal, public entry point (no relayer, prover, or admin involvement needed), and volatility or MEV activity around the router's pool (the same sandwich vector referenced in the seed report) makes the executed price differ from what the client estimated, increasing the size of the unreturned excess on every such call.

### Likelihood Explanation
High for occurrence, moderate for materiality per call: any integrator or user who pads `msg.value` above the exact quoted amount (a common defensive pattern, and effectively required given the "will revert if insufficient" warning) loses the difference on every dispatch/fundRequest call using the native path. It requires no attacker at all to trigger — only price movement or client-side over-estimation between quote and execution — and is deterministic given the exact-output/hardcoded-recipient swap plumbing shown above.

### Recommendation
- Pass the actual fee payer (`_msgSender()`) — or explicitly track pre/post native balance and refund the difference to `_msgSender()` — instead of implicitly relying on the router's refund to `msg.sender`, since that "msg.sender" is `EvmHost`, not the payer.
- Alternatively, snapshot `address(this).balance` before and after the swap in `dispatch()`/`fundRequest()` and forward any leftover ETH back to `_msgSender()` before returning, mirroring the refund pattern already used correctly in `evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol` (`swapETHForExactTokens`, which does refund `msg.sender` there because that wrapper is a standalone router substitute, not the host itself).
- Add a regression test asserting that a `dispatch()`/`fundRequest()` call with `msg.value` strictly greater than the on-chain quoted cost returns the delta to the caller's balance.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)`, or `fundRequest`) with `msg.value = X`, where `X` is intentionally or incidentally larger than the ETH required to buy `post.fee` fee-tokens at the current Uniswap V2 pool price.
2. `EvmHost` calls `IUniswapV2Router02.swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. The router computes `amounts[0] < X` as the exact ETH needed, executes the swap, delivers `post.fee` fee-tokens to `address(this)` (EvmHost), and refunds `X - amounts[0]` ETH to its immediate caller, which is `EvmHost` (`msg.sender` from the router's point of view).
4. `dispatch()`/`fundRequest()` returns without ever reading `address(this).balance` or forwarding anything to `_msgSender()`. The `X - amounts[0]` ETH remains in `EvmHost`'s balance, unaccounted for and not attributable back to the original caller through any code path in these functions.
5. Repeat across many calls/users — the accumulated stranded ETH is unrecoverable by the affected callers through the normal protocol flow. [1](#0-0) [3](#0-2)
