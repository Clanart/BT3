### Title
Reused `CachedPreprocesses` context across DKG attempts/sessions reuses FROST nonces, enabling private-key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The btrfs bug is a *zombie-state* class bug: a half-completed object (partially dropped subvolume) survived a lifecycle boundary that should have cleaned it up, and a later operation (balance/relocation) consumed it, failing only deep inside delayed-ref processing. The fix rejects such stale state at the earliest point.

Serai's `SigningProtocol::preprocess_internal` has the same shape: a FROST preprocess seed is persisted in `CachedPreprocesses` keyed only by `self.context`, and for `DkgConfirmer` that context is `(b"DkgConfirmer", attempt)` — with no `genesis`/session/set binding (coordinator/src/tributary/signing_protocol.rs:275). The entry is never deleted after the signature completes, so it survives the entire lifecycle of one validator set's DKG confirmation and is reloaded verbatim by the *next* set's DKG confirmation that reuses the same attempt number (e.g. attempt 0). The stale seed deterministically regenerates the same nonces via `seeded_preprocess`'s `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:127), and those nonces are then used to sign a *different* `set_keys_message` (different `set`, different `removed`, different `key_pair`) — classic Schnorr/MuSig nonce reuse across distinct messages.

### Finding Description

`preprocess_internal` caches the preprocess seed the first time a context is seen and reuses it forever:

```rust
// coordinator/src/tributary/signing_protocol.rs:123-145
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  ... encrypt seed ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
... decrypt ...
AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))
```

The cache key is `self.context.encode()`. For `DkgConfirmer`, `signing_protocol()` sets `context = (b"DkgConfirmer", self.attempt)` (signing_protocol.rs:275) — it does **not** include `spec.genesis()`, `spec.set()`, the session, or the participant set. `CachedPreprocesses` is a flat DB table keyed solely by that encoding, so `(DkgConfirmer, 0)` for validator-set session N collides with `(DkgConfirmer, 0)` for session N+1.

The seed wholly determines the preprocess: `seeded_preprocess` instantiates `ChaCha20Rng::from_seed(*seed.0)` and calls `Commitments::new` plus `preprocess_addendum` from that stream (crypto/frost/src/sign.rs:127-133). A reused seed therefore yields identical nonce scalars `d, e` and identical published commitments — but the message signed in `share_internal` is `set_keys_message(&self.spec.set(), &removed..., key_pair)` (signing_protocol.rs:296-300), which is different for the new set. Two Schnorrkel/MuSig shares `s = d + b·e + λ·a·c` produced under the same `(d, e)` but different challenges/messages yield the secret share `a` by linear elimination — third-party recovery of the validator's root-of-trust private key.

The header comment even states the precondition for this exact failure: "In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" (signing_protocol.rs:34-35) — and a new set's `set_keys_message` is precisely a distinct message signed a second time with the same cached nonce. The parallel to btrfs is exact: a completed DKG confirmation is the analogue of a dropped subvolume, yet its preprocess state was never cleaned up (no orphan/deletion), so the next lifecycle silently consumes the half-dead object.

### Impact Explanation

Any party observing the two published confirmation shares on the public tributary (or the processor↔coordinator message flow) can recover the validator's MuSig private key — the key that is the on-chain root of trust for the entire validator set, per the module docs (signing_protocol.rs:4-9). The published `confirmation_nonces` are also byte-identical across the two sessions, making the reuse externally detectable and the exploit deterministic once both shares exist. This is key-share/private-key recovery, squarely Critical per the accepted-impact list. It also matches the documented security invariant being violated: "a preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:85-87).

### Likelihood Explanation

Triggering requires no adversarial action beyond routine operation: each validator-set rotation runs a fresh DKG whose confirmation starts at `attempt = 0` (attempts are per-topic counters in `AttemptDb`, scoped by `genesis`, but the preprocess cache is *not* scoped by genesis). The first DKG confirmation attempt of every session therefore reuses the prior session's cached preprocess. The only mitigations are (a) the DB being wiped between sessions, which nothing in this code enforces — the cache is explicitly designed to survive re-execution/restarts — and (b) `DkgConfirmer::new` failing, which it won't since `removed_as_of_dkg_attempt` resolves for the new attempt. Note the same encryption key is also reused (it's derived from `context` + the unchanged validator key, signing_protocol.rs:107-113), so the stale ciphertext decrypts cleanly — there is no accidental safeguard. The one uncertainty: if every coordinator's DB is genuinely reset on set rotation in deployment, the collision disappears; nothing in the code guarantees that, and the caching design exists precisely to persist across restarts.

### Recommendation

Bind the cached preprocess to the full lifecycle identity and delete it on completion:

- Include `spec.genesis()` (or `spec.set().session`) in `DkgConfirmer`'s context tuple in `signing_protocol()` (coordinator/src/tributary/signing_protocol.rs:275), so preprocesses can never be shared across validator sets.
- Additionally, and matching the upstream fix's "reject early" approach: have `share_internal`/`complete` verify that the nonce commitments derived from the cached preprocess equal the commitments actually published for this attempt (the `TODO` acknowledged at signing_protocol.rs:50-54), and clear the `CachedPreprocesses` entry once the confirmation signature is produced.

### Proof of Concept

1. Session N: validators run DKG attempt 0. Coordinator calls `dkg_confirmation_nonces` → `DkgConfirmer::new(key, spec_N, txn, 0)` → `preprocess_internal` stores seed `S` under `CachedPreprocesses[(b"DkgConfirmer", 0).encode()]` and publishes commitments `C = (D, E)`.
2. `generated_key_pair` → `share(preprocesses, key_pair_N)` signs `m_N = set_keys_message(set_N, removed_N, key_pair_N)` with nonces derived from `S`; share `s_N` is published via `Transaction::DkgConfirmed`.
3. Session N+1 (new genesis, new validator set): DKG attempt 0 again. `preprocess_internal` finds `CachedPreprocesses[(b"DkgConfirmer", 0)]` already present, reloads `S` (same encryption key since context and `key` are unchanged), regenerates the identical nonces and identical commitments `C`.
4. `share(preprocesses', key_pair_{N+1})` signs `m_{N+1} = set_keys_message(set_{N+1}, removed_{N+1}, key_pair_{N+1})` — a distinct message — with the same nonces; share `s_{N+1}` is published.
5. Observer computes `a = (s_N − s_{N+1}) · (λ·(c_N − c_{N+1}))⁻¹` (per the aggregate's binding structure), recovering the validator's MuSig secret share — equivalent to recovering its private key under the n-of-n `Interpolation::Constant` aggregation used here.

Observable fingerprint without executing the attack: the 64-byte `confirmation_nonces` published for attempt 0 of two different sessions are byte-identical, proving nonce reuse.
