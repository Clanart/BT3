### Title
Attacker-controlled P2TR outputs to derivable Branch/Change/Forwarded offsets are misclassified as internal outputs, bypassing deposit crediting - (File: networks/bitcoin/src/wallet/mod.rs, processor/src/networks/bitcoin.rs)

### Summary
The analog to `?deleted=true` honoring the `is_public` scope: `Scanner` classifies a received output's *kind* solely by matching `script_pubkey` against a fixed table of registered offsets. The Branch/Change/Forwarded offsets are publicly derivable constants (`hash_to_F(KEY_DST, "branch"|"change"|"forward")`), so any unprivileged Bitcoin sender can craft a P2TR output that the scanner reports as an internal `Change`/`Forwarded`/`Branch` output rather than an `External` deposit. Just as the deleted-notes path kept the permissive `is_public` clause instead of restricting to the owner, the scanner keeps the "matches a registered offset" clause instead of restricting internal kinds to outputs the protocol itself produced.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) returns a `ReceivedOutput` for any output whose `script_pubkey` is in `self.scripts`, with `offset` set to the registered scalar. `register_offset` (lines 180-196) inserts scripts keyed purely by the script bytes — there is no binding to who created the output or why.

In `processor/src/networks/bitcoin.rs:686-740` (`get_outputs`), each scanned output is mapped to an `OutputType` via `kinds[offset_repr]`. The offsets registered are:
- `OutputType::Branch` → `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")`
- `OutputType::Change` → `hash_to_F(KEY_DST, b"change")`
- `OutputType::Forwarded` → `hash_to_F(KEY_DST, b"forward")`

These scalars are deterministic public values; anyone can compute `key + G*offset` (the group key is public) and produce the exact P2TR script the scanner matches. Critically, only `OutputType::External` outputs receive the `data` payload (`if output.kind == OutputType::External { output.data.clone_from(&data) }`, line 732-734) — i.e., only External outputs can carry the `InInstruction` that credits a deposit. An output sent to a Branch/Change/Forwarded script is misrouted into the internal-accounting path with no sender data.

### Impact Explanation
A Bitcoin user (or attacker) who sends funds to the publicly computable Change/Branch/Forwarded addresses of the active multisig has those funds reported by `get_outputs` as an internal `Output` rather than an external deposit. The deposited value is not credited via the `InInstruction`/external path; it is instead handled by logic intended for protocol-generated change/forward completions, meaning the sender's funds are received by the multisig but never attributed to the sender — funds "received" that are not spendable/credited to their depositor. This is a metadata-classification/authorization-scope bypass identical in shape to the note-mark bug: the "is this output internal" check (script match) is applied without verifying the output was actually produced by the protocol's own transaction flow.

### Likelihood Explanation
Reachable by any unprivileged party sending a Bitcoin transaction — no authentication, validator status, or collusion required. The attacker only needs the public group key and the three fixed offset scalars to construct `p2tr_script_buf(key + G*offset)`. Exploitation is trivially repeatable for each session's group key.

### Recommendation
Do not classify output kind by script match alone. `get_outputs` should only assign non-`External` `OutputType`s to outputs appearing in transactions the processor itself constructed (e.g., check `tx`'s inputs spend prior Serai-owned outputs, or maintain a DB of expected change/forward outpoints), and treat any output arriving on a non-external script in a third-party transaction as `External` (or reject it). Analogously, the fix in the report restricted the trash listing to `owner_id` only — here, internal kinds should be restricted to protocol-originated transactions only.

### Proof of Concept
1. Obtain the current multisig `group_key` (public).
2. Compute `forward_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` and adjust for even parity as `register_offset` does (increment until `p2tr_script_buf` returns `Some`).
3. Build `script = p2tr_script_buf(group_key + G*forward_offset)` and broadcast a transaction paying to `script`.
4. Once mined, `Bitcoin::get_outputs` scans the block, `scanner.scan_transaction` matches `output.script_pubkey` to `forward_offset`, `kinds[offset_repr]` yields `OutputType::Forwarded`, and the output is emitted without `data` — never processed as a deposit. The BTC sits at a spendable-by-the-set address but is credited to no one.

Note: the full crediting pipeline lives in `processor/` (outside the indexed crypto/bitcoin crates' strict scope), so the exact downstream handling of misclassified non-`External` outputs is inferred from `get_outputs` rather than fully traced; the misclassification root cause itself is fully verified in in-scope `Scanner` code.
