### Title
Fee and weight calculation omit the OP_RETURN output when a change address is present, producing underpriced/oversized transactions that will not relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight/vbytes used for the required fee and the `MAX_STANDARD_TX_WEIGHT` check via `calculate_weight_vbytes(inputs, payments, change)`. When a change output is requested, the function recalculates with `payments` — which excludes the OP_RETURN data output already pushed into `tx_outs`. As a result, `fee_with_change`, `weight`, and `needed_fee` are computed for a smaller transaction than the one actually built, so the constructed transaction underpays its intended fee rate (potentially below the minimum relay fee) and can exceed the standardness weight limit without being rejected. This is a data-validation/locking analog of the reference bug: a check performed against the wrong quantity causes legitimately constructed transactions to be stuck.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the OP_RETURN output is appended to `tx_outs` before the fee/weight calculation:

- `tx_outs.push(TxOut { value: ZERO, script_pubkey: op_return })` at send.rs:194-202
- The no-change estimate `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204 also omits the data output, but that path only matters when `data` alone creates the sole output.
- With change: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at send.rs:225-226 again passes `payments`, which does not include the OP_RETURN entry present in the final `tx.output`.

Consequences:

1. `fee_with_change` is too small, so `change value = input_sat - payment_sat - fee_with_change` over-credits change and the realized fee rate (`fee()/vsize`) is below `fee_per_vbyte` — potentially below `DEFAULT_MIN_RELAY_TX_FEE`, making the signed transaction non-relayable even though `SignableTransaction::new` succeeded.
2. `weight = weight_with_change` at send.rs:231 then feeds the `weight > MAX_STANDARD_TX_WEIGHT` check at send.rs:241, so a transaction that is actually over the standard weight limit is accepted, producing a `SignableTransaction` that signs successfully but cannot be broadcast.

Both flows are reachable purely from caller-supplied arguments (`payments`, `change`, `data`, `fee_per_vbyte`) — no trusted state required.

### Impact Explanation
A caller that combines a `data` payload with a `change` address receives a `SignableTransaction` whose advertised `needed_fee()` is understated and whose realized fee rate is lower than requested. At the margin the transaction falls under the minimum relay fee or the standard weight limit and is rejected by the network, leaving the inputs unspendable through this transaction (recoverable only by rebuilding with corrected accounting). Separately, even when relayable, change is over-credited and the effective fee diverges from `needed_fee`, which callers such as `processor/src/networks/bitcoin.rs::make_signable_transaction` rely on (`needed_fee` and dust logic assume the value returned is accurate).

### Likelihood Explanation
Medium. Triggering requires only the ordinary combination of `data: Some(..)` plus `change: Some(..)` with inputs/fees near a boundary; no adversarial chain state or validator misbehavior is needed. The dollar impact is bounded (stuck/underpriced transaction, misreported fee), so this maps to Medium rather than High.

### Recommendation
Compute weight/vbytes from the actual output set. Either pass the fully populated `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or add the data output's size to the estimate, in both the initial call (send.rs:204) and the change call (send.rs:225-226), so that `needed_fee`, the change-value check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
```rust
// In networks/bitcoin (e.g. appended to tests/wallet.rs)
// Construct: one input, one payment, an OP_RETURN data payload, and a change address.
let inputs = vec![output.clone()];                       // scanned ReceivedOutput
let payments = vec![(addr(), 1000)];
let data = Some(vec![0u8; 80]);                          // max allowed OP_RETURN
let change = Some(change_addr.clone());

let tx = SignableTransaction::new(inputs, &payments, change, data, FEE).unwrap();

// needed_fee was computed WITHOUT the OP_RETURN output in the tx:
//   calculate_weight_vbytes(inputs, payments, Some(change))  // send.rs:225-226
// but the real transaction includes 4 outputs (payment, OP_RETURN, change).
assert_eq!(tx.transaction().output.len(), 3);

// The realized fee rate is below the requested FEE:
let actual_fee = tx.fee();                               // inputs - outputs
let actual_vsize = tx.transaction().vsize() as u64;      // includes OP_RETURN
assert!(actual_fee < FEE * actual_vsize);                // underpriced vs. needed_fee
assert_eq!(tx.needed_fee(), FEE * (actual_vsize - /*op_return size*/));
// With FEE * actual_vsize > actual_fee, and near the min-relay boundary,
// the signed transaction is rejected by send_raw_transaction / standardness rules.
```

Root cause: `calculate_weight_vbytes` is invoked with `payments` instead of the true output list at `networks/bitcoin/src/wallet/send.rs:204` and `send.rs:225-226`, while the OP_RETURN output is added to `tx_outs` at `send.rs:194-202` and never accounted for in `fee_with_change`, `needed_fee`, or the weight check at `send.rs:241`.
