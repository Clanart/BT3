## Analysis

The SphereX report's core invariant: a system records "harmless" observations during a low-stakes window and later trusts that recorded data for high-value decisions, without vetting for adversarial injection while the window is open and stakes are low.

The closest local analog with concrete file/function evidence is Hyperbridge's **Phantom Order price-snapshot mechanism**, which "records" solver bids during a short bid window and later trusts the resulting liquidity-weighted median as the canonical market rate for pricing real user intents.

### Title
Liquidity-weighted phantom price snapshot can be skewed by a single well-funded solver, corrupting quotes used for real order pricing - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`pallet-intents-coprocessor` periodically opens a short "recording window" (`PhantomBidWindow`) during which any address that is EIP-7702-delegated to the chain's `SolverAccount` may submit a signed bid on a tiny, fixed-size phantom order (`standardAmount` = one unit of the input token). Once the window closes, `aggregatePhantomBids` reduces all verified bids into a single `weightedMedian(quotes)` price, weighted by each solver's on-chain token/vault balance — [1](#0-0)  — and this snapshot is later trusted by `PhantomSnapshotIntentQuoteStrategy.quote()` to price real, arbitrarily large user orders via `quoteIntent()` [2](#0-1) .

### Finding Description
The "recording phase" is the phantom bid window: it is cheap (one standard unit of input token), permissionless to anyone who delegates an EOA to `SolverAccount` via EIP-7702 [3](#0-2) , and admits bids from anyone: "Anyone can submit a bid to the coprocessor, and every accepted quote moves the weighted median the rest of the protocol prices intents against" — the code's own comment confirms this attack surface [3](#0-2) .

The only filter is signature/nonce-binding verification (`isVerifiedSolverBid`), not economic sanity or Sybil resistance [4](#0-3) . The weighting mechanism itself is the corruptible allow-listed "pattern": `weightedMedian` returns whichever price accumulates ≥50% of total weight, and the test suite explicitly documents that a single dominant-weight bid pulls the median entirely to its own price ("the high-liquidity solver pulls the median to its price") [5](#0-4) . Because weight is measured as the solver's own token/vault balance (self-reported by whoever they are, not tied to actually filling anything) [6](#0-5) , an attacker who acquires (even temporarily, e.g. via a flash-loan-funded vault deposit or simply holding a large balance of the output token) a balance exceeding the combined weight of all legitimate solvers can single-handedly set the recorded median to an arbitrary, self-favorable price during a cheap, low-stakes phantom auction.

This corrupted median then becomes the "trusted, recorded" data used by `quoteSnapshot()` to compute `amountOut`/`amountIn` for real orders that any user's SDK client requests via `quoteIntent()` [7](#0-6)  — precisely the SphereX pattern: hide/inject a malicious value into a cheap, low-volume "recording" process so it gets baked into data trusted for larger-value operations.

### Impact Explanation
`quoteIntent()` results are used directly to construct `order.inputs`/`order.output.assets` for real IntentGatewayV2 orders (the SDK docs state "Use the returned amounts directly ... no further adjustment required") [8](#0-7) . A skewed median directly causes users to escrow/receive the wrong amounts of real, bridged funds when they place orders priced against the manipulated snapshot — a logic/pricing attack leading to fund loss for whichever side (user or solver) trades against the corrupted rate, satisfying "transaction manipulation" / "logic attacks" / "stealing or loss of funds" from the bounty scope.

### Likelihood Explanation
Likelihood is moderate-to-high given: (1) the bid window and phantom order size are cheap by design (`standardAmount` = one unit) [9](#0-8) ; (2) becoming a "verified solver" only requires an EIP-7702 delegation to a public, non-privileged `SolverAccount` contract, not governance approval; (3) the weighting is entirely self-reported on-chain balance with no requirement that the balance be committed/locked at the moment of measurement, and the aggregation sweeps balances across multiple chains and ERC-4626 vaults, widening the surface for temporarily inflating measured weight. The main mitigating factor (and source of uncertainty) is that exploiting this in practice requires temporarily acquiring dominant weight in the specific output token/vault set at exactly the block the aggregator (indexer) reads balances — the exact economic cost/feasibility of doing so (e.g., whether a flash loan can inflate the measured balance, or whether balances are read at a bidding-window-close block that resists flash-loan timing) is not verifiable from the code inspected here and would need dynamic testing against `sweepSolverLiquidity`/`getTotalSolverBalance`.

### Recommendation
- Do not weight phantom-quote influence purely by self-reported/spot-read balances; require weight to be backed by escrowed/committed liquidity (e.g., a bond posted at bid time) so it cannot be transiently inflated.
- Cap the influence of any single solver's weight on the weighted median (e.g., clamp per-solver weight to some percentage of total observed weight across a rolling window) so no single actor can single-handedly set the price within one recording window.
- Aggregate over multiple recording windows/blocks before trusting a snapshot for real order pricing, rather than trusting a single window's result outright, mirroring the "sanitizing the recording phase data" mitigation the SphereX team applied.
- Consider requiring balance measurement at a randomized or delayed block (not the bid-window-close block) to defeat flash-loan-timed weight inflation.

### Proof of Concept
Conceptual (cannot be executed without a live testnet/simnode + funded accounts, so this is a code-traced scenario, not an executed exploit):
1. Attacker delegates an EOA to the chain's public `SolverAccount` via EIP-7702 (permissionless) [10](#0-9) .
2. During the next phantom order's bid window (`PhantomBidWindow`, a few blocks) for the USDC↔cNGN pair, attacker temporarily amasses (e.g. via a large but short-lived vault deposit) a cNGN balance far exceeding the combined balances of the legitimate solvers bidding in that window.
3. Attacker submits one signed bid quoting a favorable-to-self price for the phantom order's tiny `standardAmount`.
4. `aggregatePhantomBids` verifies the bid (valid signature/nonce/delegation) and computes `weightedMedian`, which — per the documented and tested behavior — collapses to the attacker's price because their weight alone exceeds 50% of total weight [5](#0-4) .
5. The resulting `PhantomOrderPriceSnapshot.medianPrice` is persisted and served by the indexer.
6. Any user calling `quoteIntent()` shortly after receives amounts computed against this corrupted median [7](#0-6)  and places a real order using those amounts, resulting in a mispriced trade that benefits the attacker (or a colluding solver) at the user's expense once the order is filled.

```typescript
// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing; if every weight is zero it falls back to the unweighted
// median so a price is still reported.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
```

```typescript
async function isVerifiedSolverBid(params: {
	userOp: PackedUserOperation
	commitment: string
	sessionKey: HexString
	chainId: bigint
	solverAccount: string
	evmRpcUrl: string
	recoverSigner: RecoverBidSigner
	bidNonceKey: BidNonceKeyFn
	logger?: AggregationLogger
}): Promise<boolean> {
	const { userOp, commitment, sessionKey, chainId, solverAccount, evmRpcUrl, recoverSigner, bidNonceKey, logger } =
		params
	const solver = userOp.sender

	const parsed = splitBidSignature(userOp.signature)
	if (!parsed) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: malformed userOp signature")
		return false
	}

	// Cheap early-out ONLY. The prefix sits inside userOp.signature, which userOpHash excludes, so it
	// is attacker-mutable and must never be what binds a bid to an order — the nonce key below is.
	if (parsed.commitment.toLowerCase() !== commitment.toLowerCase()) {
		logger?.warn(
			{ solver, commitment, signedFor: parsed.commitment },
			"Rejecting phantom bid: signed for another order",
		)
		return false
	}

	// The authoritative binding, mirroring SolverAccount.validateUserOp on-chain. The nonce IS
	// covered by userOpHash, so a solver signature stays valid only for the (order, sessionKey) pair
	// its nonce key was derived from. `sessionKey` is read from the bid's own calldata, which is also
	// covered by userOpHash — so every operand here is signed, leaving nothing for a replay to swap.
	if (BigInt(userOp.nonce) >> 64n !== bidNonceKey(commitment as HexString, sessionKey)) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: nonce does not bind order and session key")
		return false
	}

	// SolverAccount._rawSignatureValidation recovers over the bare userOpHash and requires the signer
	// to be the account itself, which under EIP-7702 is the sender EOA.
	const signer = await recoverSigner(userOp, ENTRY_POINT_V08_ADDRESS, chainId, parsed.solverSignature)
	if (!signer || signer.toLowerCase() !== solver.toLowerCase()) {
		logger?.warn({ solver, commitment, signer }, "Rejecting phantom bid: signature does not recover to the sender")
		return false
	}

	if (!(await isDelegatedToSolverAccount(evmRpcUrl, solver, solverAccount))) {
		logger?.warn({ solver, commitment, solverAccount }, "Rejecting phantom bid: sender is not a delegated solver")
		return false
	}

	return true
```

```typescript
	private quoteSnapshot(
		params: QuoteIntentParams,
		protocolFeeBps: bigint,
		snapshot: PhantomOrderPriceSnapshot,
	): PhantomSnapshotQuoteIntentResult {
		if (params.amountIn !== undefined) {
			const netAmountIn = deductProtocolFee(params.amountIn, protocolFeeBps)
			const amountOut = (netAmountIn * snapshot.medianPrice) / snapshot.standardAmount
			if (amountOut <= 0n) {
				throw new InvalidPhantomSnapshotError(snapshot.commitment, "quote rounds down to zero output")
			}
			return this.buildResult("EXACT_INPUT", params.amountIn, amountOut, protocolFeeBps, snapshot)
		}

		if (params.amountOut === undefined) throw new Error("Quote amount is missing after validation")
		const netAmountIn = divCeil(params.amountOut * snapshot.standardAmount, snapshot.medianPrice)
		const amountIn = grossUpForProtocolFee(netAmountIn, protocolFeeBps)
		return this.buildResult("EXACT_OUTPUT", amountIn, params.amountOut, protocolFeeBps, snapshot)
	}
```

```text
`amountIn` and `amountOut` already account for the IntentGateway protocol fee that the gateway deducts from order inputs. Exact-input quotes price the swap against the post-fee input, so `amountOut` is the snapshot-priced output; exact-output quotes return the gross `amountIn` required to produce the requested `amountOut`. Use the returned amounts directly as the order's `inputs` and `output.assets`—no further fee or slippage adjustment is required.

For an exact-input Phantom quote, the SDK deducts the gateway fee and computes `floor(netInput × medianPrice / standardAmount)`. For an exact-output quote, it computes `ceil(amountOut × standardAmount / medianPrice)` and grosses that input up for the gateway fee. A missing indexer, missing snapshot, or invalid snapshot throws an explicit error; the SDK does not silently switch price sources.
```

```typescript
	/**
	 * Sets up EIP-7702 delegation from the filler's EOA to the SolverAccount contract.
	 *
	 * Tries bundler path first (paymaster pays gas in ERC-20).
	 * Falls back to direct type-0x04 tx if bundler path fails.
	 */
	async setupDelegation(chain: string): Promise<boolean> {
		const solverAccountContract = this.configService.getSolverAccountContractAddress(chain)

		if (!solverAccountContract) {
			this.logger.error("solverAccountContractAddress not configured")
			return false
		}

		if (await this.isDelegated(chain)) {
			this.logger.info({ chain }, "EOA already delegated to SolverAccount")
			return true
		}

		// Try bundler path first (paymaster pays gas)
		if (hasPaymaster(chain, this.configService)) {
			const success = await this.setupDelegationViaBundler(chain)
			if (success) return true
			this.logger.info({ chain }, "Falling back to direct delegation tx")
		}

		// Fallback: direct type-0x04 transaction (requires native token)
		const publicClient = this.clientManager.getPublicClient(chain)
		const authority = this.signer.account.address as HexString

		// The direct tx pays gas in native ETH. If the EOA can't cover it, delegation fails
		// outright (the paymaster path already failed too) — surface the deficit explicitly.
		const [nativeBalance, gasPrice] = await Promise.all([
			publicClient.getBalance({ address: authority }),
			publicClient.getGasPrice(),
		])
		const requiredNative = DELEGATION_TX_GAS_FLOOR * gasPrice
		if (nativeBalance < requiredNative) {
			this.logger.error(
				{
					chain,
					authority,
					nativeBalance: formatEther(nativeBalance),
					requiredNative: formatEther(requiredNative),
				},
				"Delegation failed: insufficient native balance for direct EIP-7702 tx and paymaster path unavailable",
			)
			return false
		}

		try {
			this.logger.info(
				{ chain, authority, solverAccountContract, mode: this.signer.mode },
				"Setting up EIP-7702 delegation via direct tx",
			)

			const authorization = await this.buildAuthorization(chain, solverAccountContract)
			const hash = await this.sendDelegationTransaction(chain, authorization)

			this.logger.info({ chain, txHash: hash }, "Delegation transaction sent")

			const receipt = await publicClient.waitForTransactionReceipt({ hash })

			if (receipt.status === "success") {
				this.logger.info({ chain, txHash: hash, blockNumber: receipt.blockNumber }, "Delegation successful")
				return true
			}

			this.logger.error({ chain, txHash: hash, status: receipt.status }, "Delegation transaction failed")
			return false
		} catch (error) {
			this.logger.error({ chain, error }, "Failed to setup delegation")
			return false
		}
	}
```
