### Title
Reachable assertion abort when parsing a crafted/malicious Offer with duplicate coin spends - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.__post_init__()` in `chia/wallet/trading/offer.py` uses a bare Python `assert` to enforce that no coin is spent twice within an offer's underlying spend bundle. Because an `Offer` is constructed directly from attacker-controlled bytes (a bech32/hex offer file or blob) via `Offer.from_bech32()` → `Offer.try_offer_decompression()` → `Offer.from_bytes()` → `Offer.from_spend_bundle()`, a crafted offer containing a `CoinSpend` list with a duplicated `coin` can trigger this `assert` and raise an unhandled `AssertionError` rather than a normal, caught `ValueError`.

### Finding Description
`Offer.__post_init__()` populates the internal `_additions` cache by iterating over `self._bundle.coin_spends` and guards against processing the same coin twice with: [1](#0-0) 

```
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
    ...
```

This is a plain `assert`, which is a reachable-assertion pattern analogous to CVE-2017-15371's `sox_append_comment()` bug class: a crafted/malformed input reaches an `assert` used as a runtime invariant check instead of a handled validation error, causing a hard abort (`AssertionError`) rather than a graceful rejection.

The `Offer` object is instantiated straight from untrusted bytes supplied by any offer counterparty or CLI/RPC caller: [2](#0-1) 

`from_bech32()` decodes attacker-supplied bech32 text and hands it to `try_offer_decompression()` → `from_bytes()` → `WalletSpendBundle.from_bytes()` → `Offer.from_spend_bundle()`, which constructs the dataclass and runs `__post_init__()`. Nothing upstream de-duplicates `coin_spends` by coin before this point, and the SpendBundle deserializer does not itself reject duplicate coins in the list — that is left entirely to the `assert` in `__post_init__()`.

Downstream call sites that consume attacker-controlled offer text call directly into this path and only guard against `ValueError`, not `AssertionError`: [3](#0-2) 
```
try:
    offer = Offer.from_bech32(offer_hex)
except ValueError:
    print("Please enter a valid offer file or hex blob")
    return []
```
An `AssertionError` raised inside `__post_init__()` is not a `ValueError`, so it propagates unhandled through this call path (CLI `take_offer`, and by extension the analogous RPC/wallet endpoints such as `TakeOffer.parsed_offer` in `chia/wallet/wallet_request_types.py`, which likewise calls `Offer.from_bech32(self.offer)` with no exception handling at all): [4](#0-3) 

### Impact Explanation
An attacker-crafted offer file/blob (something a wallet user would typically share with or receive from an untrusted offer counterparty, or accept via RPC/CLI `take_offer`, `get_offer_summary`, etc.) can crash offer-processing code with an unhandled `AssertionError` instead of the intended, caught `ValueError`. This is a denial-of-service against wallet-side offer handling: the calling process/RPC request aborts ungracefully wherever `assert` is left uncaught (most acutely the RPC endpoint `TakeOffer.parsed_offer`, which has no exception handling at all around `Offer.from_bech32`). This matches the "spend-triggered transaction-processing halt" class explicitly listed as in-scope impact.

### Likelihood Explanation
Likelihood is moderate: constructing a `WalletSpendBundle`/`SpendBundle` with two `CoinSpend` entries that reference the exact same `Coin` (same parent id, puzzle hash, and amount) is straightforward for anyone crafting an offer file by hand or with a modified wallet client — no cryptographic break or special privilege is needed, only the ability to author/serialize a spend bundle and bech32-encode it as an "offer." The victim need only attempt to examine or take the offer (`take_offer`, offer summary display, or a wallet RPC call that resolves `TakeOffer.parsed_offer`).

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__()` with an explicit, raised exception type that untrusted-input callers already handle (e.g., raise `ValueError("Offer spends the same coin twice")` instead of using `assert`), and audit/catch `AssertionError` (or avoid emitting it) at all call sites that parse untrusted offer bytes, including `chia/wallet/wallet_request_types.py`'s `TakeOffer.parsed_offer` cached property and `chia/cmds/wallet_funcs.py`'s `take_offer()`. More broadly, `python -O` strips `assert` statements entirely, so relying on `assert` for security-relevant input validation on untrusted offer/spend-bundle data is unsafe regardless of exception-handling; all such invariant checks on attacker-controlled data should use explicit `raise` statements.

### Proof of Concept
Conceptual PoC (illustrative, not executed):
1. Construct two `CoinSpend` objects that reference the identical `Coin` (same `parent_coin_info`, `puzzle_hash`, `amount`), each with an arbitrary puzzle reveal/solution.
2. Build a `WalletSpendBundle([cs1, cs2], G2Element())` and bech32-encode it the way `Offer.to_bech32()` would (or simply hand-craft the compressed/uncompressed offer bytes so that `Offer.from_bytes()`/`Offer.from_spend_bundle()` sees a `coin_spends` list containing the duplicate coin).
3. Send this string as an "offer" to a victim wallet's `take_offer` CLI command or `TakeOffer` RPC endpoint (`self.offer` in `chia/wallet/wallet_request_types.py`).
4. `Offer.from_bech32()` → `Offer.from_spend_bundle()` → `__post_init__()` hits `assert cs.coin not in adds` on the second occurrence of the duplicated coin, raising `AssertionError`, which is uncaught by the RPC/CLI's `except ValueError` handling and aborts the request/process instead of returning a clean "invalid offer" error.

Note: I was unable to fully trace every RPC entry point (e.g., the full `wallet_rpc_api.py` take_offer handler) or confirm at runtime whether an outer generic `except Exception` somewhere higher in the RPC stack ultimately converts the `AssertionError` into a non-fatal RPC error response versus crashing the request; this could reduce the severity from a process crash to a single failed RPC call. This should be verified directly in a running instance before treating the impact as more severe than a single-request DoS.
