### Title
Fee and weight accounting omit the OP_RETURN data output, underpaying the intended fee rate and bypassing the standard-weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` measures the transaction cost (vbytes and weight) using only the inputs and `payments`, but the actual transaction also includes an OP_RETURN `data` output (up to ~80 bytes of attacker/plan-influenced data). Analogous to the Comet finding — where the measured "gas used" excluded real work performed by the transaction — the measured `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check both exclude a real output of the final transaction, so the accounting does not reflect the transaction's actual cost/size.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the fee is computed (send.rs:193-202), but `calculate_weight_vbytes` is then called with `payments` only — the `data` output is not included in the dummy transaction used for measurement (send.rs:204). The same omission applies to the change variant (send.rs:225-226). Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` is computed against a vbytes that excludes the OP_RETURN output (~3 + 80 bytes, plus output overhead ≈ up to ~92 vbytes short).
2. When `change` is present, the change value is set to `input_sat - payment_sat - fee_with_change`, so the *actual* fee paid equals the under-measured `fee_with_change` — the realized fee rate is strictly below the intended `fee_per_vbyte` (send.rs:228-233, `fee()` at send.rs:138-141).
3. The minimum-relay-fee check at send.rs:211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction can pass the local check while failing the node's actual minimum for its true size.
4. The standard-weight check at send.rs:241 uses `weight`, which also excludes the data output, so a transaction can pass locally while exceeding `MAX_STANDARD_TX_WEIGHT` in reality.

`needed_fee` is exactly the value reported upstream via `Bitcoin::needed_fee` → `signable.needed_fee()` (processor/src/networks/bitcoin.rs:803-816) and used by `prepare_send` for fee amortization over user payments (processor/src/networks/mod.rs:442-547), so the mis-measurement propagates into the protocol's fee accounting.

### Impact Explanation
When a change output exists (the common case — change is used to recoup operating costs), the signed transaction pays a lower effective sat/vbyte than the rate obtained from the fee estimator. If the true fee rate falls below the mempool minimum, `send_raw_transaction` rejects it and `publish_completion` panics (processor/src/networks/bitcoin.rs:844-852), halting that multisig's signing pipeline and leaving the plan's funds unspendable until manual intervention. Even short of rejection, the transaction confirms slower than priced, and the weight-check bypass can produce a non-standard transaction that can never be relayed. Because `data`/payment contents are derived from user-initiated instructions, an unprivileged user can maximize the gap (80-byte OP_RETURN) to push marginal-fee plans under relay minimums — a reachable, if bounded, fee-accounting/consensus-liveness flaw. Severity: Medium.

### Likelihood Explanation
Requires a Bitcoin plan carrying `data` plus a change output, and a `fee_per_vbyte` estimate close enough to the minimum relay fee that ~92 unaccounted vbytes matter. Fee estimates are typically well above minimum, so underpayment usually manifests only as a lower-than-intended fee rate rather than outright rejection; the weight-check bypass additionally requires a transaction already near `MAX_STANDARD_TX_WEIGHT`. Reachable through ordinary public burn/refund flows that produce `data`-carrying transactions, but the triggering conditions are situational — hence Medium, not High.

### Recommendation
Include the OP_RETURN output in the measurement: pass the already-built `tx_outs` (payments + data, and change when applicable) into `calculate_weight_vbytes` rather than reconstructing from `payments` alone, or add the data output's size to `vbytes`/`weight` explicitly. Recompute `vbytes`/`weight` after all outputs are finalized so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the actual signed transaction.

### Proof of Concept
From `networks/bitcoin/src/wallet/send.rs:193-243`:

```rust
// data output IS added to the real transaction
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...) });
}

// but the fee/size measurement only sees `payments`
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

Construct `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)`: the returned `tx` contains the OP_RETURN output while `needed_fee()` equals `fee_per_vbyte * vbytes(payments-only)`. The effective rate `fee() / actual_vsize < fee_per_vbyte`, and `weight` used in the `TooLargeTransaction` check under-reports the real weight by the full size of the OP_RETURN output.

Note: I verified the mis-measurement inside `send.rs` directly; I was unable to fully read `make_signable_transaction` in `processor/src/networks/bitcoin.rs` to confirm every call site that populates `data`, so the exact upstream paths feeding OP_RETURN data could not be exhaustively enumerated — though `needed_fee`/`signable_transaction` (bitcoin.rs:803-834) demonstrably consume the mis-measured value.
