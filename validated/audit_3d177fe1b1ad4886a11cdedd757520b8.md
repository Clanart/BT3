### Title
Identity encryption public key exposes DKG secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
PedPoP accepts an identity point as a participant's encryption public key. `EncryptionKeyMessage::read` uses `C::read_G`, which enforces canonical point encoding but does not reject identity. A malicious participant can therefore submit `enc_key = identity`; when an honest participant encrypts that party's secret share, ECDH produces the identity shared point, making the ChaCha20 stream key publicly derivable and exposing the secret share.

### Finding Description
`EncryptionKeyMessage::read` deserializes `enc_key` with `C::read_G(reader)` and performs no non-identity check. [1](#0-0)  The generic `Ciphersuite::read_G` rejects invalid and non-canonical encodings, but accepts the canonical identity encoding. [2](#0-1) 

The submitted key is registered for that participant without further validation. [3](#0-2)  During secret-share generation, PedPoP encrypts each recipient's share using that registered key. [4](#0-3) 

Encryption computes `ecdh = recipient_public_key * ephemeral_private_key`. [5](#0-4)  If `recipient_public_key` is identity, the shared point is always identity. The encryption key is then deterministically derived from the context and the serialized shared point, with a fixed IV. [6](#0-5) 

Although `EncryptedMessage::read` also accepts the public key with `C::read_G`, the critical unchecked input is the earlier advertised encryption key contained in `EncryptionKeyMessage`. [7](#0-6) 

### Impact Explanation
An unprivileged DKG participant can recover the secret share that an honest participant intended only for them. Because PedPoP uses a polynomial DKG, recovering shares for the attacker-controlled participants may contribute to reconstruction of the distributed secret if enough compromised positions are reached. Even absent full key reconstruction, this is direct secret-share leakage caused solely by attacker-controlled public input.

### Likelihood Explanation
The attack requires submitting a syntactically valid identity point as the encryption key. The parser explicitly accepts canonical points and does not invoke the stricter `frost::Curve::read_G`, which rejects identity. [8](#0-7)  No signature, proof, or discrete-log knowledge is required for the encryption key itself; the proof-of-possession applies to each per-message ephemeral key, not to the registered long-term `enc_key`. [9](#0-8) 

### Recommendation
Reject identity encryption keys in `EncryptionKeyMessage::read` and again in `Decryption::register` as defense in depth. Prefer a non-identity point-reading helper for all protocol public keys, similar to `Curve::read_G`, while retaining canonicality checks. Also reject identity for `EncryptedMessage.key` and `EncryptionKeyProof.key`, since identity keys do not establish meaningful ECDH possession.

### Proof of Concept
Let PedPoP run over any supported `Ciphersuite`.

1. Malicious participant `l` serializes an `EncryptionKeyMessage` containing:
   - structurally valid `Commitments<C>`,
   - `enc_key = C::G::identity().to_bytes()`.

2. Honest participant calls:
   - `EncryptionKeyMessage::<C, Commitments<C>>::read(...)`, which succeeds,
   - `generate_secret_shares(...)`, which registers `enc_key`,
   - `encrypt(..., l, SecretShare(x_l))`.

3. Inside `encrypt`, the code computes:
   - random ephemeral scalar `k`,
   - public message key `K = kG`,
   - ECDH point `S = k * identity = identity`.

4. The emitted `EncryptedMessage` contains:
   - `key = K`,
   - a valid PoP under `K`,
   - `msg = SecretShare(x_l) XOR ChaCha20(key(context, identity), fixed_iv)`.

5. Anyone observing the message reconstructs `S = identity`, serializes it into `cipher(context, S)`, regenerates the keystream, and recovers `x_l`.

The decisive flaw is that the advertised recipient key is never constrained to the non-identity subgroup element required for confidentiality.

  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce

  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
