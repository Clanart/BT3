### Title
Missing `finality_depth` Safety Enforcement in `check_mainnet_requirements` Allows 1-Confirmation Finality on Bitcoin Mainnet — (`File: core/src/config/mod.rs`)

---

### Summary

`check_mainnet_requirements` is the dedicated mainnet safety gate called at startup for every actor (Verifier, Operator, Aggregator). It enforces several invariants for `Network::Bitcoin` deployments but does **not** check `finality_depth`. The schema and env-var parsers only reject `finality_depth < 1`, meaning a value of `1` is accepted everywhere. With `finality_depth = 1` on mainnet Bitcoin, the tx-sender permanently marks bridge transactions as finalized after a single confirmation and never reprocesses them. A routine 1-block reorg then leaves the bridge in an irrecoverable inconsistent state, putting operator collateral and bridged BTC at risk.

---

### Finding Description

**Validation floor is 1, not a safe mainnet minimum.**

`ProtocolParamset::from_toml_file` and `from_env` both enforce only `finality_depth >= 1`: [1](#0-0) [2](#0-1) 

The field comment itself says "Minimum value should be 1", treating 1 as a valid production value: [3](#0-2) 

**`check_mainnet_requirements` does not check `finality_depth`.**

The function is called in `main.rs` for every actor on `Network::Bitcoin` and checks `client_verification`, `DISABLE_NOFN_CHECK`, Risc0 dev mode, and test-VK — but has no guard on `finality_depth`: [4](#0-3) 

`check_general_requirements` also only rejects `finality_depth < 1`: [5](#0-4) 

**Finalized state is irrevocable in the tx-sender.**

`sync_transaction_confirmations_via_rpc` marks a tx as `is_finalized = true` once `confirmations >= finality_depth`. The comment explicitly states "Once finalized, a row is never reprocessed": [6](#0-5) 

With `finality_depth = 1`, the chain tip itself satisfies `confirmations >= 1`, so every confirmed tx is immediately finalized. The reorg-handling arm only clears `seen_at_height` for rows that are **not yet finalized**: [7](#0-6) 

Once `is_finalized = true`, a subsequent reorg that removes the block is silently ignored.

**`is_block_finalized` with depth 1 treats the chain tip as final.** [8](#0-7) 

With `finality_depth = 1`, `chain_tip_height - block_height + 1 >= 1` is always true for any block at or below the tip, so every block — including the current tip — is considered finalized.

---

### Impact Explanation

With `finality_depth = 1` on mainnet Bitcoin:

1. **Deposit path**: The aggregator fetches the deposit block hash and verifiers sign the move-tx immediately after 1 confirmation. If the deposit block is reorged, the deposit UTXO no longer exists on the canonical chain, but the bridge DB has already advanced the deposit state. The move-tx cannot be broadcast (invalid input), and the bridge will not retry because the deposit is marked finalized. Bridged BTC is permanently locked.

2. **Kickoff/challenge path**: `validate_all_kickoff_finalizers_spent` checks `check_if_utxo_spending_tx_is_finalized` using `finality_depth`. With depth 1, a kickoff tx is finalized at the tip. A 1-block reorg removes the kickoff tx, but the bridge has already advanced the challenge state. The operator attempts to send the next tx in the challenge chain (which spends the now-absent kickoff tx), the broadcast fails, and the operator's challenge window expires — resulting in slashable exposure of operator collateral. [9](#0-8) 

3. **Tx-sender managed UTXOs**: Fee-payer UTXOs and round-tx outputs finalized at depth 1 are never re-evaluated after a reorg, leaving the tx-sender with stale UTXO state and potentially double-spending or failing to fund subsequent bridge transactions.

---

### Likelihood Explanation

Bitcoin mainnet experiences 1-block reorgs several times per year (documented in public chain data). An operator deploying on mainnet who follows the regtest docker example (`FINALITY_DEPTH=1` in `.env.regtest`) or the test paramset (`finality_depth = 1` in `protocol_paramset.toml`) would carry that value to mainnet without any startup rejection: [10](#0-9) [11](#0-10) 

The `check_mainnet_requirements` function is the only code-level gate for mainnet safety and it silently passes with `finality_depth = 1`.

---

### Recommendation

1. Add a minimum safe `finality_depth` check inside `check_mainnet_requirements` for `Network::Bitcoin` (standard practice is ≥ 6):

```rust
// in check_mainnet_requirements, after the network guard:
if self.protocol_paramset().finality_depth < 6 {
    misconfigs.push(format!(
        "finality_depth={} is unsafe for mainnet Bitcoin (minimum 6 recommended)",
        self.protocol_paramset().finality_depth
    ));
}
```

2. Update the `finality_depth` field comment to clarify that 1 is only appropriate for regtest and that mainnet requires ≥ 6.

3. Add a similar guard in `check_general_requirements` that warns (or errors) when `network == Bitcoin && finality_depth < 6`.

---

### Proof of Concept

1. Deploy Clementine on `Network::Bitcoin` with `finality_depth = 1` (copied from the regtest env template). Startup succeeds — `check_mainnet_requirements` passes without error.
2. A user submits a deposit. The deposit tx is mined in block N (1 confirmation). `is_block_finalized(N, N)` returns `true` (since `N - N + 1 = 1 >= 1`). The aggregator proceeds to sign the move-tx; verifiers sign; the deposit is marked finalized in the DB.
3. A competing miner produces a longer chain that does not include block N (a 1-block reorg). The deposit UTXO no longer exists on the canonical chain.
4. The tx-sender attempts to broadcast the move-tx; it is rejected by the Bitcoin node (missing input). Because `is_finalized = true`, `sync_transaction_confirmations_via_rpc` never re-evaluates this row. The deposit is permanently stuck — bridged BTC is locked with no recovery path in the bridge state machine.

    /// Checks various variables if they are correct for mainnet deployment.
    pub fn check_mainnet_requirements(&self, actor_type: cli::Actor) -> Result<(), BridgeError> {
        if self.protocol_paramset().network != Network::Bitcoin {
            return Ok(());
        }

        let mut misconfigs = Vec::new();

        if matches!(actor_type, cli::Actor::Verifier | cli::Actor::Operator)
            && !self.client_verification
        {
            misconfigs.push("CLIENT_VERIFICATION=false".to_string());
        }

        /// Checks if an env var is set to a non 0 value.
        fn check_env_var(env_var: &str, misconfigs: &mut Vec<String>) {
            if let Ok(var) = std::env::var(env_var) {
                if var == "0" || var.eq_ignore_ascii_case("false") {
                    return;
                }

                misconfigs.push(format!("{env_var}={var}"));
            }
        }

        check_env_var("DISABLE_NOFN_CHECK", &mut misconfigs);

        if is_dev_mode() {
            misconfigs.push("Risc0 dev mode is enabled (RISC0_DEV_MODE=1)".to_string());
        }

        if is_test_vk() {
            misconfigs.push("use-test-vk feature is enabled".to_string());
        }

        if !misconfigs.is_empty() {
            return Err(BridgeError::ConfigError(format!(
                "Following configs can't be used on Mainnet: {misconfigs:?}",
            )));
        }

        Ok(())
    }
