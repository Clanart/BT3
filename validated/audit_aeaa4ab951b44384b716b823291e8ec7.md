### Title
`SignableTransaction::new` omits the OP_RETURN data output from weight/fee and max-weight accounting, producing under-funded or consensus-invalid transactions (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes the `data` OP_RETURN output onto `tx_outs` before computing the transaction weight and required fee, but `calculate_weight_vbytes` is invoked only with `payments` (and later `change`). The OP_RETURN output's weight is never counted, so `needed_fee` is underestimated and the `MAX_STANDARD_TX_WEIGHT` check is bypassed. This is the Serai analog of the reported bug class — value/weight attached to a call is silently unaccounted — here causing funds to be committed to a transaction that is either under-paid (non-relayable) or outright invalid.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 193-202 [1](#0-0) . However, the weight/vbytes used for `needed_fee` are computed from `tx_ins.len()` and `payments` only — the data output is never passed in [2](#0-1) . Inside `calculate_weight_vbytes`, `tx.output` is built solely from `payments` plus an optional change output [3](#0-2) .

Consequences:

1. **Under-estimated fee.** `needed_fee = fee_per_vbyte * vbytes` excludes the OP_RETURN output (~9 + 80 bytes of script, plus output overhead → roughly 100+ real bytes, ~360+ weight units uncounted) [4](#0-3) . The change calculation `input_sat - payment_sat - fee_with_change` then assigns the unaccounted bytes' cost into the change output only by accident of subtraction — the *fee rate* the user requested is not achieved, and the minimum-relay check at line 211 is evaluated against the too-small `vbytes`, so a transaction that is actually below `DEFAULT_MIN_RELAY_TX_FEE` can pass validation.
2. **`TooLargeTransaction` bypass.** The `weight > MAX_STANDARD_TX_WEIGHT` check uses the underestimated `weight` [5](#0-4) , so a transaction near the limit plus an 80-byte OP_RETURN can be constructed that exceeds standard weight and will never be relayed or mined, while `needed_fee`/change accounting assumed it was valid.

Since `Schnorr`/`TransactionSignMachine::sign` sighashes commit to the real `self.tx.tx` (including the OP_RETURN), the signature is valid — the transaction itself is simply defective [6](#0-5) .

### Impact Explanation
An unprivileged caller of the public wallet API supplies `data` and receives a `SignableTransaction` whose declared `needed_fee` and weight do not reflect the actual transaction. Depending on margins, the signed transaction either (a) pays less than the requested/required fee rate and is rejected by relay policy while the protocol believes it validly funded, or (b) exceeds `MAX_STANDARD_TX_WEIGHT` and is consensus-nonstandard — the inputs, payments, and expected change output are all "stuck" on a transaction that cannot confirm, exactly mirroring the reported class of funds accepted by a function but never properly accounted for.

### Likelihood Explanation
The `data` parameter is part of the public constructor and is exercised by the crate's own tests (`Some(vec![0; 80])` is asserted to succeed), so the path is reachable with ordinary inputs — no malicious validator, leaked key, or misuse of documented requirements is needed [7](#0-6) . Triggering only requires passing any `data` plus a fee/change configuration where the missing ~360+ weight units matter (low fee rate, thin change margin, or near-max weight), which are routine operating conditions.

### Recommendation
Include the OP_RETURN output in the weight/vbytes calculation: build the output list inside `calculate_weight_vbytes` from `payments` plus the (already size-checked) `data` output and optional `change`, e.g. by passing `data: Option<&[u8]>` (or the constructed `TxOut`) into `calculate_weight_vbytes` at both call sites (lines 204 and 226). This makes `needed_fee`, the minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` check reflect the true transaction.

### Proof of Concept
```rust
// Networks/bitcoin regtest context per tests/wallet.rs
// 1. Create a funded ReceivedOutput `output` for `key`.
let data = vec![0u8; 80];
// 2. Build two transactions differing only in `data`:
let tx_no_data = SignableTransaction::new(
    vec![output.clone()], &payments, Some(change.clone()), None, FEE).unwrap();
let tx_data = SignableTransaction::new(
    vec![output], &payments, Some(change), Some(data), FEE).unwrap();
// 3. Both report the same needed_fee despite tx_data being ~90+ bytes larger:
assert_eq!(tx_no_data.needed_fee(), tx_data.needed_fee()); // BUG: equal
// 4. The real fee rate of tx_data is below FEE:
//    tx_data.fee() / tx_data.transaction().vsize() < FEE
// 5. Alternatively, craft payments so weight is just under
//    MAX_STANDARD_TX_WEIGHT without data; adding `data` still returns Ok(..)
//    while producing a transaction Bitcoin Core rejects as too large.
```
