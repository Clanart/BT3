### Title
Attacker-controlled `AccountInfo.data` pointer/length bypasses all CPI bounds checks when `syscall_parameter_address_restrictions` is inactive, enabling out-of-VM-region memory corruption - (File: program-runtime/src/cpi.rs)

### Summary
`CallerAccount::from_account_info` only validates the `AccountInfo.data` pointer against the server-computed `vm_data_addr`, and `CallerAccount::get_serialized_data` only clamps `len` to `original_data_len + MAX_PERMITTED_DATA_INCREASE`, when the feature `syscall_parameter_address_restrictions` is active. When that feature is inactive (its current default/pre-activation state), an unprivileged attacker's own BPF program can forge both the pointer and length of its own `AccountInfo.data` fat pointer in guest memory before issuing a CPI, causing `translate_slice_mut_for_cpi` to construct a mutable slice at an arbitrary attacker-chosen VM address with an arbitrary length, entirely outside the account's actual reserved region.

### Finding Description
`CallerAccount::from_account_info` [1](#0-0)  reads the `AccountInfo.data` fat pointer straight out of guest memory via `translate_type::<&[u8]>` and derives both `vm_data_addr = data.as_ptr()` and the `len` passed to `get_serialized_data`. Two independent checks are supposed to constrain these attacker-influenced values, but both are wrapped in `if syscall_parameter_address_restrictions`:

- The pointer-identity check `check_account_info_pointer(data.as_ptr(), account_metadata.vm_data_addr, "data")` only runs `if syscall_parameter_address_restrictions` [2](#0-1) . When disabled, `data.as_ptr()` (fully attacker-controlled) is used unchecked as `vm_data_addr`.
- The `len` passed into `get_serialized_data` is `*ref_to_len_in_vm` only `if syscall_parameter_address_restrictions`; otherwise it is simply `data.len()` — again fully attacker-controlled, with no comparison against `account_metadata.original_data_len` [3](#0-2) .

Inside `CallerAccount::get_serialized_data`, the bound `len > original_data_len.saturating_add(MAX_PERMITTED_DATA_INCREASE)` is likewise only enforced `if syscall_parameter_address_restrictions` [4](#0-3) . When the feature is off and `virtual_address_space_adjustments` is also off (its current default/pre-activation combination), execution falls into the unclamped branch that calls `translate_slice_mut_for_cpi::<u8>(memory_mapping, vm_addr, len as u64, false)` directly with the attacker-supplied `vm_addr`/`len` [5](#0-4) .

`translate_slice_mut_for_cpi` only validates that `[vm_addr, vm_addr+len)` lies within *some* registered `MemoryRegion` [6](#0-5) ; it has no concept of "this length belongs to this specific account." Critically, in the legacy (non-`virtual_address_space_adjustments`) serialization path, `Serializer::write_account` does **not** call `push_region()` per account — only the whole parameter buffer is pushed as a single region at `finish()` [7](#0-6) . This means every account's data, the instruction data, and the program id all live inside one contiguous `MemoryRegion`, so an attacker-forged `len` can span far past `original_data_len + MAX_PERMITTED_DATA_INCREASE` into neighboring accounts' serialized bytes — or, since the pointer itself is also unchecked, `vm_data_addr` can be redirected to an entirely different mapped region (e.g. stack/heap) while the mapping call still succeeds because it is region-bounds-valid, not per-account-valid.

The resulting oversized/mispositioned `serialized_data` slice is then propagated: `update_callee_account`'s legacy branch calls `callee_account.can_data_be_resized(caller_account.serialized_data.len())` followed by `set_data_from_slice(...)` [8](#0-7) . `can_data_be_resized` only checks the global `MAX_ACCOUNT_DATA_LEN` (10 MiB) and the transaction-wide `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` budget [9](#0-8)  — it does **not** enforce the per-CPI `MAX_PERMITTED_DATA_INCREASE` bound, which was supposed to be the job of the now-bypassed check in `get_serialized_data`. Symmetrically, `update_caller_account` writes callee data back into `caller_account.serialized_data` at the forged address/length [10](#0-9) , letting the callee write attacker-controlled bytes into whatever VM memory the forged pointer targets.

### Impact Explanation
This breaks MEMORY_ISOLATION inside the VM's own mapped address space: an unprivileged, self-deployed BPF program performing a self-CPI (or invoking any callee) with a forged `AccountInfo.data` fat pointer can (a) read adjacent serialized-parameter bytes belonging to other accounts / instruction data / program id into its own account's data, and (b) cause the callee's returned data to be copied into an attacker-chosen VM address (any writable region reachable by `translate_slice_mut_for_cpi`, e.g. neighboring accounts' serialized regions), corrupting data the top-level transaction never authorized as writable for that account. This matches the CPI/memory-isolation privilege-escalation category in scope.

### Likelihood Explanation
The only precondition is that `syscall_parameter_address_restrictions` (SIMD-0459) is inactive, which is its default/current state prior to cluster activation, so this is reachable on unmodified current code without any special configuration. The attacker only needs to deploy and invoke their own program with a forged `AccountInfo` struct in guest memory before calling `invoke`/`invoke_signed`, which is fully within the unprivileged attacker capability described.

### Recommendation
Remove the `syscall_parameter_address_restrictions` gating from the pointer-identity check (`check_account_info_pointer` for `data`) and from the `len` clamp in `CallerAccount::get_serialized_data`, making both checks unconditional so that `vm_data_addr` must always match `account_metadata.vm_data_addr` and `len` must always be bounded by `original_data_len + MAX_PERMITTED_DATA_INCREASE`, independent of feature activation state.

    let transaction_accounts =
        transaction_with_one_writable_instruction_account(b"foo".to_vec());
    let account = transaction_accounts[1].1.clone();
    mock_invoke_context!(
        invoke_context, transaction_context, b"instruction data",
        transaction_accounts, 0, &[1]
    );

    let config = Config { aligned_memory_mapping: false, ..Config::default() };
    let memory_mapping =
        unsafe { MemoryMapping::new(vec![], &config, SBPFVersion::V3).unwrap() };

    let forged_len = account
        .data()
        .len()
        .saturating_add(MAX_PERMITTED_DATA_INCREASE)
        .saturating_add(1_000_000); // wildly exceeds the per-account reserved space

    let result = unsafe {
        CallerAccount::get_serialized_data(
            &memory_mapping,
            true,             // check_aligned
            MM_INPUT_START,
            account.data().len(),
            forged_len,
            false,            // syscall_parameter_address_restrictions: DISABLED
            false,            // virtual_address_space_adjustments
            false,            // account_data_direct_mapping
        )
    };

    // EXPECTED (secure) behavior: Err(InstructionError::InvalidRealloc)
    // ACTUAL (vulnerable) behavior: falls through to translate_slice_mut_for_cpi
    // with the unclamped forged_len, only bounded by the underlying MemoryRegion,
    // not by the account's original_data_len + MAX_PERMITTED_DATA_INCREASE.
    assert!(
        result.is_err(),
        "get_serialized_data must reject over-length data regardless of feature gating"
    );
}

    fn write_account(
        &mut self,
        account: &mut BorrowedInstructionAccount<'_, '_>,
    ) -> Result<u64, InstructionError> {
        if !self.virtual_address_space_adjustments {
            let vm_data_addr = self.vaddr.saturating_add(self.buffer.len() as u64);
            self.write_all(account.get_data());
            if !self.is_loader_v1 {
                let align_offset =
                    (account.get_data().len() as *const u8).align_offset(BPF_ALIGN_OF_U128);
                self.fill_write(MAX_PERMITTED_DATA_INCREASE + align_offset, 0)
                    .map_err(|_| InstructionError::InvalidArgument)?;
            }
            Ok(vm_data_addr)
        } else {
            self.push_region();
            let vm_data_addr = self.vaddr;
            if !self.account_data_direct_mapping {
                self.write_all(account.get_data());
                if !self.is_loader_v1 {
                    self.fill_write(MAX_PERMITTED_DATA_INCREASE, 0)
                        .map_err(|_| InstructionError::InvalidArgument)?;
                }
            }
            let address_space_reserved_for_account = if !self.is_loader_v1 {
                account
                    .get_data()
                    .len()
                    .saturating_add(MAX_PERMITTED_DATA_INCREASE)
            } else {
                account.get_data().len()
            };
            if address_space_reserved_for_account > 0 {
                if !self.account_data_direct_mapping {
                    self.push_region();
                    let region = self.regions.last_mut().unwrap();
                    modify_memory_region_of_account(account, region);
                } else {
                    let new_region = create_memory_region_of_account(account, self.vaddr)?;
                    self.vaddr += address_space_reserved_for_account as u64;
                    self.regions.push(new_region);
                }
            }
            if !self.is_loader_v1 {
                let align_offset =
                    (account.get_data().len() as *const u8).align_offset(BPF_ALIGN_OF_U128);
                if !self.account_data_direct_mapping {
                    self.fill_write(align_offset, 0)
                        .map_err(|_| InstructionError::InvalidArgument)?;
                } else {
                    // The deserialization code is going to align the vm_addr to
                    // BPF_ALIGN_OF_U128. Always add one BPF_ALIGN_OF_U128 worth of
                    // padding and shift the start of the next region, so that once
                    // vm_addr is aligned, the corresponding host_addr is aligned
                    // too.
                    self.fill_write(BPF_ALIGN_OF_U128, 0)
                        .map_err(|_| InstructionError::InvalidArgument)?;
                    self.region_start += BPF_ALIGN_OF_U128.saturating_sub(align_offset);
                }
            }
            Ok(vm_data_addr)
        }
    }

    fn push_region(&mut self) {
        let range = self.region_start..self.buffer.len();
        let region_slice = self.buffer.as_slice_mut().get_mut(range.clone()).unwrap();
        self.regions
            .push(MemoryRegion::new(&raw mut region_slice[..], self.vaddr));
        self.region_start = range.end;
        self.vaddr += range.len() as u64;
    }

        self.push_region();
        debug_assert_eq!(self.region_start, self.buffer.len());
        (self.buffer, self.regions)

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
