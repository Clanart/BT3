### Title
Silent auto-rewrite of a repository's git remote URL from an attacker-influenced GitHub API `clone_url` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` is called whenever Desktop refreshes a repository's associated GitHub metadata (`repositoryWithRefreshedGitHubRepository` in `app-store.ts`), which happens on repository selection, background refresh, and account changes. This function compares the repository's currently-known `clone_url` (previously fetched and cached from the API) with a freshly-fetched `clone_url`, and if they differ while the local git remote still matches the previously cached value, it silently runs `git remote set-url` to point the local remote at the new URL - with no user confirmation.

### Finding Description
The relevant logic: [1](#0-0) 

The invariant "the remote a user configured is what they intended" is checked only against a *cached* `gitHubRepository.cloneURL` value (`remoteUrlUnchanged`), not against the user's actual intent. That cached value comes from `apiRepo.clone_url`, an attacker-influenceable field on the GitHub API repository object (e.g., after a rename, transfer, or repo-owner-controlled change of settings visible via `fetchRepository`): [2](#0-1)  shows `repositoryWithRefreshedGitHubRepository` fetching the repo via `api.fetchRepository(owner, name)` and, if a `gitHubRepository` association exists, directly calling `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` before the new API data is even persisted with `upsertGitHubRepository`.

The only checks are: (1) protocol match (`https` stays `https`, not compared to host) [3](#0-2) , and (2) that the local remote still equals the last known clone URL, via `urlMatchesRemote`, which only compares hostname/owner/name parsed from the URL [4](#0-3) . Nothing verifies that the *new* `clone_url` still points at the same repository identity (owner/name/host) as before, nor does it require any user approval - the mismatch (`!urlsMatch`) is precisely the trigger for the automatic rewrite.

This is the same broken invariant class as the report: a value (royalty terms / here, the API-reported `clone_url`) that determines a security-relevant outcome (revenue split / here, the destination of all future pushes and fetches) can be changed by another party between the time the local state was established and the time an automated process re-derives from it, and the code applies the new, attacker-influenced value without re-confirming user intent.

### Impact Explanation
If an attacker who influences a GitHub-hosted repository's `clone_url` (for example, a repo that gets renamed/transferred, or a malicious org owner who owns the upstream/parent repository referenced by a fork relationship) causes the API to return a different `clone_url` for a repository the victim already has open in Desktop, Desktop will silently repoint the victim's local `origin` remote via `gitStore.setRemoteURL` (`git remote set-url`). All subsequent pushes/fetches/pulls performed through the UI (which relies on `state.remote`/`defaultRemote`) would then silently go to the new destination without any dialog, warning, or diff shown to the user - this can redirect a user's future pushes (and their embedded credentials/tokens via the credential helper for that host) to an attacker-controlled repository, or, if the attacker points to a same-named repo on a different host of their choosing, exfiltrate git push traffic/credentials to that host. This is a silent corruption of what the user pushes and where, matching the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact classes.

### Likelihood Explanation
The attacker precondition is comparatively easy to reach for an unprivileged party in specific but realistic situations: repository transfer/rename events, or attacker control over an upstream/parent that a victim's fork association resolves against, are enough to change the `clone_url` returned by GitHub's API for the object Desktop already associated with a local checkout. No local access, admin rights, or social engineering step is needed beyond the victim continuing normal use of Desktop (refreshing/selecting the repository, which happens automatically on repository focus and periodic sync). The test suite in `app/test/unit/stores/updates/update-remote-url-test.ts` explicitly documents and exercises the "url changes automatically" code path, confirming this is intended, unconditioned behavior rather than a narrow edge case.

### Recommendation
Do not silently rewrite the git remote URL based solely on a delta between cached and freshly-fetched API `clone_url` values. At minimum:
- Require the new and old `clone_url` to resolve to the same verified repository `id` (GitHub's stable repository ID), not just a heuristic hostname/owner/name string comparison, before treating it as the "same repository, just renamed."
- Prompt the user for confirmation before altering `origin`'s URL, similar to how `RepositorySettings` treats manual remote edits.
- Treat cross-host changes (e.g., `github.com` → any other host) as always requiring explicit confirmation, since that is precisely the exfiltration vector.

### Proof of Concept
1. Victim clones `https://github.com/victim-org/repo` in Desktop; Desktop caches `gitHubRepository.cloneURL = https://github.com/victim-org/repo`.
2. Attacker (who has rename/transfer control of that repository, e.g. via a compromised or malicious collaborator/owner account, or via a repository being transferred to them) renames/transfers it so the GitHub API now returns `clone_url: https://github.com/attacker-org/repo` for the same repository ID that Desktop is tracking (GitHub keeps redirects working for renamed/transferred repos, so this is a supported, "legitimate" flow, not requiring elevated access to the victim's machine).
3. On the victim's next repository refresh (background refresh, switching to the repo, or account change), `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository` and passes the new `apiRepo` to `updateRemoteUrl` [5](#0-4) .
4. `updateRemoteUrl` finds `remoteUrlUnchanged === true` (local remote still matches old cached clone URL) and `urlsMatch === false` (new clone_url differs), so it calls `gitStore.setRemoteURL(...)` and rewrites `origin` to the attacker's URL with zero user prompt [6](#0-5) .
5. The victim's next push in Desktop's UI (which uses `state.remote`/`gitStore.defaultRemote`, now the attacker's URL) silently sends the victim's commits/credentials to the attacker-controlled repository.

  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
