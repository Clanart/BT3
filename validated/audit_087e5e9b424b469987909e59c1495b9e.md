### Title
Direct ERC20 donation to MasterMagpie inflates `_calLpSupply` / `BaseRewardPoolV2.totalStaked()`, permanently diluting reward-per-share accounting - (File: rewards/MasterMagpie.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`MasterMagpie._calLpSupply()` falls back to `IERC20(_stakingToken).balanceOf(address(this))` for every pool that is not the vlMGP/mWomSV pool, and `BaseRewardPoolV2.totalStaked()` independently returns the exact same raw `balanceOf(operator)` value. Because both denominators are the contract's raw token balance rather than an internally tracked sum of `UserInfo.amount`, any unprivileged actor can send staking tokens directly to `MasterMagpie` (a plain ERC20 `transfer`, bypassing `deposit()`), permanently inflating both denominators without crediting any account, which permanently dilutes `accMGPPerShare` and `BaseRewardPoolV2.rewardPerTokenStored` accrual for every real staker.

### Finding Description
`_calLpSupply()` is used as the divisor for MGP emission in `updatePool()`: [1](#0-0) 

For any pool other than vlMGP/mWomSV it simply reads the contract's raw token balance, which includes tokens that were never `deposit()`-ed and therefore never recorded in any `UserInfo.amount`. `updatePool()` divides the per-interval MGP reward by this inflated value: [2](#0-1) 

For a pool whose rewarder is a `BaseRewardPoolV2`, the same raw-balance pattern is repeated independently: `totalStaked()` returns `IERC20(stakingToken).balanceOf(operator)` (the MasterMagpie contract), while `balanceOf(_account)` returns the credited `UserInfo.amount` fetched via `IMasterMagpie(operator).stakingInfo(...)`: [3](#0-2) [4](#0-3) 

`_provisionReward()` (called on every `queueNewRewards`/`donateRewards`) divides the newly added reward by `totalStaked()`: [5](#0-4) 

Exploit flow:
1. Attacker `deposit()`s a normal amount `X` into a pool whose rewarder is `BaseRewardPoolV2` (crediting `UserInfo.amount = X`, `user.available = X`).
2. Attacker (or any unprivileged holder) executes a raw `IERC20(stakingToken).transfer(masterMagpie, Y)` — no call into `MasterMagpie` is required, so no `UserInfo` is ever updated for this `Y`.
3. From this point, `_calLpSupply()` and `BaseRewardPoolV2.totalStaked()` both permanently report `balanceOf(this) = X + Y` even though only `X` is attributable to any account via `stakingInfo`/`UserInfo.amount`.
4. Attacker calls `withdraw(_stakingToken, X)`. This is permitted because `_harvestAndUnstake` only checks `user.available < _amount` (bounded by the attacker's own credited `X`), so the withdrawal succeeds and removes exactly `X`, leaving the donated `Y` stranded in `MasterMagpie` forever — no `UserInfo` entry references it, so it can never be withdrawn by anyone through normal pool exits.
5. From then on, every subsequent `updatePool()` call divides newly minted MGP by the permanently inflated `lpSupply`, and every `_provisionReward()` call divides newly queued bonus rewards by the permanently inflated `totalStaked()`. Both `accMGPPerShare` and `rewardPerTokenStored` accrue at a deflated rate. The shortfall between reward tokens actually transferred into the rewarder/MGP emitted and what is attributable via `_earned`/`_calNewMGP` to real stakers (whose `balanceOf`/`user.amount` sum is strictly less than `totalStaked()`/`lpSupply`) is never recovered — it sits unclaimed and undistributable, satisfying "permanent freezing of unclaimed yield."

No existing check prevents this: `whenNotPaused`/`nonReentrant` on `withdraw()` do not validate that the pool's tracked balance equals the sum of `UserInfo.amount`, and there is no mechanism to sweep or reconcile donated dust back into the accounting.

### Impact Explanation
The invariant "MGP/reward emitted over an interval must be fully distributable to the sum of `UserInfo.amount`" is broken permanently: `sum(IBaseRewardPool(rewarder).balanceOf(user))` (backed by `UserInfo.amount`) becomes strictly less than `IBaseRewardPool(rewarder).totalStaked()` (raw balance) indefinitely, since the donated remainder is uncredited to any account and cannot be withdrawn through the normal `withdraw`/`withdrawFor` path (bounded by `user.available`). Every future reward/MGP distribution to that pool is computed against the inflated denominator, so a portion of every subsequent reward top-up is permanently undistributable/unclaimed by legitimate stakers — matching Immunefi's "High - Permanent freezing of unclaimed yield."

### Likelihood Explanation
This requires no privileges: any EOA holding (or able to acquire) the pool's staking/receipt token can execute a single `ERC20.transfer` to `MasterMagpie`, which is always callable and unguarded. Capital required is only the amount of tokens the attacker wishes to donate (can be as small as 1 wei to demonstrate the break, though larger amounts cause larger dilution). It is trivially repeatable against any pool using the default (non-vlMGP/non-mWomSV) branch of `_calLpSupply` with a `BaseRewardPoolV2` rewarder.

### Recommendation
Replace raw `balanceOf(address(this))`/`balanceOf(operator)` accounting with an internally tracked total (e.g., a `pool.totalStaked` state variable incremented/decremented only inside `_deposit`/`_withdraw`), so `_calLpSupply()` and `BaseRewardPoolV2.totalStaked()` reflect only tokens that are actually credited to some `UserInfo.amount`, making them immune to direct-transfer donations.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, an ERC20 staking token, and a `BaseRewardPoolV2` rewarder registered for that pool via `add()`.
2. Attacker account: `stakingToken.approve(masterMagpie, X)` then `masterMagpie.deposit(stakingToken, X)`.
3. Attacker executes `stakingToken.transfer(masterMagpie, Y)` directly (no MasterMagpie call).
4. Assert `IBaseRewardPool(rewarder).totalStaked() == X + Y` while `IBaseRewardPool(rewarder).balanceOf(attacker) == X` (via `stakingInfo`).
5. Manager calls `rewarder.queueNewRewards(R, rewardToken)`; assert `rewardPerTokenStored` increases by `R * 10**decimals / (X+Y)` instead of `R * 10**decimals / X`.
6. Attacker calls `masterMagpie.withdraw(stakingToken, X)` — succeeds (bounded by `user.available == X`).
7. Assert after withdrawal: `stakingToken.balanceOf(masterMagpie) == Y` (donated remainder stuck), `IBaseRewardPool(rewarder).totalStaked() == Y`, and no account's `UserInfo.amount`/`balanceOf` accounts for `Y` — the sum of all `balanceOf(user)` (0 after withdrawal) is permanently less than `totalStaked()` (`Y`), demonstrating the broken invariant and permanently diluted/stuck reward accrual for any future depositor.
