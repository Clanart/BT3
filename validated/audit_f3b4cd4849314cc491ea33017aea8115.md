## Analysis

The Exactly report describes a class of bug where **rewards that accrued while "unassigned" get fully captured by an attacker who becomes a stakeholder with a negligible (1-unit) position right before the reward is finally attributed**, instead of being distributed fairly over time to an accumulator.

MagpieXYZ has no maturity/lending/liquidation concept, so the report's literal mechanism (`Market.sol`, `FixedLib`, `canDiscount`, `earningsAccumulator`) does not exist here. However, `BaseRewardPool`/`BaseRewardPoolV2`'s `queuedRewards` mechanism reproduces the same root cause: rewards deposited while `totalStaked() == 0` are held as `queuedRewards` and are only converted into `rewardPerTokenStored` **at the next `_provisionReward` call, split over whatever `totalStaked()` is at that exact moment** — with no time-weighting or vesting. Any unprivileged wallet can therefore stake a dust amount right before triggering (or waiting for) the next reward provisioning and capture the entire backlog of queued/unassigned rewards.

### Title
Unassigned/queued rewards in BaseRewardPool can be stolen by staking a dust amount before the next reward provisioning - (File: rewards/BaseRewardPool.sol / rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPool._provisionReward` (and the identical logic in `BaseRewardPoolV2._provisionReward`) queues incoming rewards in `rewardInfo.queuedRewards` whenever `totalStaked() == 0`, and only folds that backlog into `rewardPerTokenStored` the next time a reward is provisioned, dividing it by whatever `totalStaked()` happens to be at that instant. [1](#0-0)  Because `donateRewards` is a **permissionless** function that anyone can call to force a provisioning event, [2](#0-1)  an attacker can stake a minimal amount (e.g. 1 wei of the pool's staking token via `MasterMagpie`) and then immediately call `donateRewards(0, rewardToken)` to crystallize the entire `queuedRewards` balance into `rewardPerTokenStored`, computed over their own dust `totalStaked()`, capturing 100% of previously-accrued, unassigned rewards meant to be shared with future/legitimate depositors.

### Finding Description
`_provisionReward` behaves as follows: [3](#0-2) 
- If `totalStaked() == 0`, incoming rewards are parked in `queuedRewards` with no owner attribution.
- The next time `_provisionReward` runs (via `queueNewRewards` from a manager, or `donateRewards` from **anyone**), the entire accumulated `queuedRewards` plus the new amount is divided by whatever `totalStaked()` is at that exact block, then added to `rewardPerTokenStored`.

Since `donateRewards` has no `onlyManager`/`onlyOwner` restriction — only a check that the token is already a registered reward token — an ordinary wallet can call it with `_amountReward = 0` and still trigger the settlement of the outstanding `queuedRewards` backlog. Because `_earned`/`earned` computes user rewards strictly from `rewardPerTokenStored` and the caller's current `balanceOf` share, [4](#0-3)  whoever holds the (possibly dust-sized) `totalStaked()` at the moment of that settlement receives the entire queued backlog, regardless of how briefly they've been staked or how large their stake is relative to future depositors.

This mirrors the Exactly root cause precisely: earnings that accrued while "unassigned" to any depositor are dumped onto whichever principal happens to be present at settlement time, rather than being smoothed via a time-based accumulator.

### Impact Explanation
An attacker can steal reward tokens that were queued for the pool's staker base but were never attributable to any specific staker (e.g., rewards pushed to a brand-new pool before the first depositor arrives, or a pool that temporarily empties to `totalStaked() == 0` and reward emissions continue to be queued via `queueNewRewards`/`donateRewards`). This is a direct theft of unclaimed yield belonging to the protocol/other stakers, satisfying the "theft or permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
The attack requires only an ordinary wallet interacting with public/permissionless functions (`MasterMagpie` deposit + `BaseRewardPool.donateRewards`). It naturally arises whenever a pool has zero stake while emissions/queued rewards accumulate (new pool bootstrap, or all LPs exiting a pool), a plausible and observable on-chain condition that an attacker can monitor and front-run cheaply with a 1-wei deposit.

### Recommendation
Do not allow an arbitrary depositor's `totalStaked()` at the instant of `_provisionReward` to absorb the entire historical `queuedRewards` backlog. Instead:
- Restrict `donateRewards` to authorized managers, and/or
- Distribute `queuedRewards` gradually via a time-based streaming/accumulator mechanism (similar to Synthetix-style `rewardRate`/`periodFinish`) rather than instantaneously crediting whoever is currently staked, and/or
- Require a minimum stake duration or minimum stake size before a depositor can claim a proportional share of previously queued rewards.

### Proof of Concept
1. Pool `P` has `totalStaked() == 0` (e.g., a freshly deployed `BaseRewardPool`, or all prior stakers have withdrawn).
2. A manager calls `queueNewRewards(amount, rewardToken)`, which is queued into `rewardInfo.queuedRewards` since `totalStaked() == 0`. [5](#0-4) 
3. Attacker deposits a dust amount (e.g., 1 wei) of the staking token through `MasterMagpie`, becoming the sole staker (`totalStaked() == 1`).
4. Attacker calls `donateRewards(0, rewardToken)` (permissionless, only requires `isRewardToken[_rewardToken]` to be true). [6](#0-5) 
5. Inside `_provisionReward`, since `totalStaked() != 0`, the full `queuedRewards` backlog is added to `_amountReward` (0) and divided by `totalStaked() = 1`, so `rewardPerTokenStored` jumps by the entire backlog. [7](#0-6) 
6. Attacker calls `getReward` (via `MasterMagpie`) to claim the entire queued reward, then withdraws their 1-wei stake.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
