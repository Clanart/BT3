Confirmed: `harvest(address _lpToken)` is a fully permissionless external function requiring only `whenNotPaused` and an active pool, callable by any attacker.### Title
Zero-slippage buyback swap in `SmartWomConvert.smartConvert`/`_convertFor` lets an attacker sandwich `WombatStaking.harvest` to steal protocol WOM fee revenue - ([File: wombat/SmartWomConvert.sol], [File: wombat/WombatStaking.sol])

### Summary
`WombatStaking._sendRewards` routes the `isMWOM` fee share through `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`, which (depending on `currentRatio()` vs `buybackThreshold`) may swap part of the WOM fee for mWOM through `IWombatRouter.swapExactTokensForTokens` in `SmartWomConvert._convertFor` with a hardcoded minimum output of `0`. Because `harvest(address _lpToken)` in `WombatStaking.sol` is permissionless and can be called by anyone, an attacker can manipulate the `womMWomPool` price immediately before calling `harvest`, causing the zero-slippage swap to execute at a manipulated rate, and then reverse the manipulation afterward to extract value that should have accrued as mWOM backing/rewards for depositors.

### Finding Description
- `WombatStaking.harvest` is `external` with only `whenNotPaused` and `_onlyActivePool` modifiers - any unprivileged address can call it at will: [1](#0-0) 
- `harvest` calls `_toMasterWomAndSendReward`, which harvests WOM rewards from Master Wombat and calls `_sendRewards` for the WOM harvested: [2](#0-1) 
- Inside `_sendRewards`, for any active fee entry flagged `isMWOM` with reward token `wom`, the code approves and calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`: [3](#0-2) 
- `SmartWomConvert.smartConvert` computes `currentRatio()` from `IWombatRouter(router).getAmountOut` on the `womMWomPool`, compares it to `buybackThreshold` (default 9000/10000), and decides how much of `_amountIn` gets swapped through the pool (`amountToSwap`, bounded by `maxSwapAmount()` which itself reads `IAsset(womAsset).cash()`/`.liability()`) versus minted 1:1 via `IMWom(mWom).deposit`: [4](#0-3) 
- The actual buyback swap in `_convertFor` calls the router with a hardcoded minimum-output of `0`, meaning **no slippage protection whatsoever** is applied to this internal swap: [5](#0-4) 

Because `currentRatio()` and `maxSwapAmount()` are both derived from live, manipulable pool state (`womMWomPool` price and `womAsset` cash/liability), and the resulting buyback swap has zero slippage protection, an attacker can:
1. Trade against `womMWomPool` (e.g., sell mWOM for WOM, or otherwise skew cash/liability) to depress the effective price of mWOM/inflate `maxSwapAmount()` just before calling `harvest`.
2. Call `WombatStaking.harvest(_lpToken)` (permissionless), triggering `_sendRewards` → `smartConvert` → `_convertFor`, whose `buybackAmount` swap executes at the manipulated, unprotected price via the pool, benefitting the attacker as the counterparty of that swap.
3. Reverse the initial trade to restore the pool state and realize the price-impact profit, extracted from the pool (and thus indirectly from the protocol fee amount that was meant to become mWOM backing/rewards for stakers).

Note: the resulting `obtainedmWomAmount` from `smartConvert` is transferred back to `_for = msg.sender` of `smartConvert`, which is `WombatStaking` itself (mode `0` in `_convertFor`), not to the attacker directly. So the attacker cannot directly redirect minted mWOM to themselves via this call; the loss to depositors is indirect - it comes from the attacker capturing the AMM swap's price impact/slippage as the counterparty in `womMWomPool`, meaning the fee-WOM converts to less mWOM value than it should, reducing what ultimately reaches `feeInfo.to` / rewarder for stakers. This is a real, quantifiable value leak driven by the absent slippage check, not merely a theoretical AMM MEV concern, because the code explicitly hardcodes `0` as `minAmountOut`.

### Impact Explanation
This causes theft of unclaimed protocol yield: the WOM fee revenue that should be converted into mWOM (protocol backing / staker rewards) at fair market rate is instead converted at an attacker-manipulated, slippage-unprotected rate, with the resulting value extracted by the attacker via the AMM pool trade. This matches the "theft of unclaimed yield" and "protocol insolvency/backing degradation" impact classes, since the fee mechanism is meant to distribute revenue fairly to all `WombatStaking` depositors via `IBaseRewardPool.queueNewRewards`, and the `Backing` invariant (WOM fee → mWOM 1:1-or-better) is violated for any manipulated harvest call.

### Likelihood Explanation
The attacker needs: (1) capital to move `womMWomPool`'s price/coverage ratio meaningfully within one or two transactions (feasible via flash loan or owned funds, since Wombat pools use bonded-curve pricing sensitive to trade size), and (2) the ability to call `harvest` (fully permissionless, no stake required) at the moment of manipulation. This is realistically executable by any sophisticated MEV searcher/bot, and is repeatable on every harvest event as long as `smartWomConverter` is set and the `isMWOM` fee is active, making it a high-likelihood, low-friction attack once the fee mechanism is in active use.

### Recommendation
Add proper slippage protection to `SmartWomConvert._convertFor`'s buyback swap by computing a `minAmountOut` (e.g., based on `estimateTotalConversion` or an oracle-free TWAP) instead of the hardcoded `0`, and/or restrict `harvest`-triggered `smartConvert` calls to use a conservative, pre-computed minimum receive amount. Consider also using a time-weighted or otherwise manipulation-resistant price source for `currentRatio()`/`maxSwapAmount()` rather than the instantaneous spot quote from `IWombatRouter.getAmountOut`, and/or restricting `harvest` to be callable only in ways that cannot be immediately sandwiched (e.g., via commit-reveal or keeper-only harvest with off-chain slippage checks).

### Proof of Concept
Foundry fork test plan:
1. Fork mainnet/BNB chain state at a block where `WombatStaking`, `SmartWomConvert`, and `womMWomPool` are live with pending WOM rewards to harvest on some active pool.
2. Record baseline: pool cash/liability of `womAsset`, `currentRatio()`, and expected mWOM output for the pending fee amount via `estimateTotalConversion`.
3. As attacker, execute a swap/trade against `womMWomPool` (buy/sell WOM↔mWOM) sized to shift `currentRatio()` below `buybackThreshold` and/or maximize `maxSwapAmount()`, using either owned capital or a flash loan.
4. Call `WombatStaking.harvest(_lpToken)` as the attacker (no special role required), triggering `_sendRewards` → `smartConvert` → `_convertFor`'s zero-slippage swap.
5. Immediately reverse step 3's trade to restore the pool.
6. Assert: (a) attacker's net WOM/mWOM balance increased (profit from the sandwich) and (b) the mWOM amount received by `WombatStaking` / forwarded to `feeInfo.to` in step 4 is measurably lower than `estimateTotalConversion`'s pre-manipulation baseline value for the same `feeAmount`, demonstrating value diverted from stakers to the attacker.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
