### Title
Submodule updates can enable `protocol.file.allow=always`, letting an attacker-controlled repo pull in local file:// git data - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag that, when true, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. [1](#0-0)  This mirrors the broken-invariant shape of the original report: an operation (here, submodule init/update) that trusts attacker-supplied configuration (`.gitmodules`, which is part of the cloned/fetched repository content) without an entry-point restriction that would normally be in force, effectively re-enabling a capability (`file://` submodule URLs) that git disables by default specifically because it lets one repository silently pull content from another local location the "vault" (repository) shouldn't be able to reach.

### Finding Description
Git disabled `file://` submodule URLs by default (`protocol.file.allow=user`, effectively deny for automated operations like submodule update) after a class of vulnerabilities where a malicious `.gitmodules` file could point a submodule at another local git repository/path on disk, causing git to read and incorporate that repository's objects into the attacker's repository during clone/checkout. Desktop's `updateSubmodulesAfterOperation` explicitly re-opens this path via an `allowFileProtocol` parameter that appends `-c protocol.file.allow=always` to the submodule update command. [2](#0-1)  The `.gitmodules` file (including submodule `url =` entries) is fully attacker-controlled content in a cloned or fetched repository — it is not something Desktop or the user authors. If this flag is set to `true` for repositories that a user simply clones/opens/checks-out (i.e., not for a narrowly scoped, already-trusted local operation), a malicious repo's `.gitmodules` could name a `file://` path to another local git repository or directory the victim has on disk (e.g. a private company repo, or a path containing sensitive git objects), and `git submodule update --init --recursive` would clone/pull its contents into the malicious repository's working tree, where they become part of what the user might subsequently stage, commit, and push back to the attacker's remote — an unprompted exfiltration path with no code-execution needed, since it's driven purely by git's own submodule machinery. This is used from `app/src/lib/git/checkout.ts`, which is one of the standard operations run against attacker-controlled clones/pulls. [3](#0-2) 

### Impact Explanation
If `allowFileProtocol` defaults to `true` (or is set to `true`) for checkout/pull flows on repositories the user just cloned/fetched from an untrusted remote, the attacker gains a read primitive into other local git repositories on the victim's filesystem, and — because the resulting objects land inside a repository the victim may push — a path to exfiltrate that data to an attacker-controlled remote. This matches the "credential/token exfiltration" / "silent corruption of what the user commits or pushes" impact categories called out as valid.

### Likelihood Explanation
Likelihood hinges entirely on whether Desktop passes `allowFileProtocol: true` unconditionally (or based on some insufficiently strict condition) for repositories obtained via clone/fetch from an untrusted remote versus only for repositories the user has explicitly configured to trust. I was not able to complete tracing every call site in `checkout.ts` within the available tool budget to confirm this distinction, so this should be treated as a **lead requiring verification**, not a confirmed exploitable bug.

### Recommendation
Verify every call site of `updateSubmodulesAfterOperation`/`allowFileProtocol` in `app/src/lib/git/checkout.ts` (and any pull/fetch flows) and ensure `protocol.file.allow=always` is never enabled for repositories sourced from an untrusted/attacker-controlled remote. If it must be enabled for legitimate local-repository interop scenarios, gate it on an explicit, user-approved allowlist rather than blanket enabling it based on repository state alone.
