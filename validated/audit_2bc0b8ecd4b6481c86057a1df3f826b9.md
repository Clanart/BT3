### Title
Griefing dust deposits to the deterministic isolated address permanently freezes IBC-callback transferred funds - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`ContractKeeper.IBCReceivePacketCallback` uses a "must be fully drained" balance check to decide whether the callback succeeded, exactly analogous to the report's "unregister vault only if balance == 0" pattern. Because the address being checked (`isolatedAddr`/`receiverHex`) is a value deterministically derivable from public information (`packet.GetDestChannel()` and `data.Sender`) *before* the packet is even relayed, an attacker can pre-fund that address with 1 wei of the corresponding ERC20 token. This guarantees the post-call balance check at [1](#0-0)  always fails, even when the target contract behaves perfectly and pulls out the full legitimately-transferred amount.

### Finding Description
`IBCReceivePacketCallback` computes a per-(channel, sender) isolated account with `types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)` [2](#0-1) , sets an ERC20 `approve` from that address to the target contract, then calls the target contract with the caller-supplied calldata inside a cached context [3](#0-2) [4](#0-3) . After `writeFn()` flushes the cached context, the code enforces:

```go
receiverTokenBalance := k.erc20Keeper.BalanceOf(ctx, erc20.ABI, tokenPair.GetERC20Contract(), receiverHex)
if receiverTokenBalance.Cmp(big.NewInt(0)) != 0 {
    return errorsmod.Wrapf(erc20types.ErrEVMCall, "receiver has %d unrecoverable tokens after callback", receiverTokenBalance)
}
``` [5](#0-4) 

This check is an absolute-balance check, not a delta check against the amount actually delivered by this packet. Because `isolatedAddr` is fully computable off-chain from `(destChannel, sender)` — both public before the packet is submitted — any third party can front-run the relay by sending 1 wei of the same ERC20 token directly to that isolated address using the ordinary, permissionless `transfer` function of the token contract. Since the isolated address has no controlling private key ("isolated address" is a generated pseudo-account, per its own doc comment), the dust can never be swept away by the legitimate flow, and this check will perpetually see a non-zero balance regardless of how correctly the target contract behaves.

Per the standard ADR-8 IBC-callbacks-middleware pattern that this module implements (`callbacktypes.ContractKeeper`), the caller of `IBCReceivePacketCallback` executes it against a cached context and only commits (`write()`) state changes made during the callback if no error is returned; on error the entire cached context — including the `approve` and the contract's `transferFrom` pull performed via `writeFn()` inside this function — is discarded. The actual token receipt into the isolated address (via `transfertypes`/`x/erc20` OnRecvPacket) happens independently and earlier, and is not rolled back. The net effect of the griefing dust: the contract's legitimate pull of funds is rolled back, but the previously-delivered IBC tokens remain parked at the isolated address, which by design has no private key — the funds become permanently unrecoverable, exactly as warned in the function's own comment ("since they would become irretrievable").

### Impact Explanation
This matches the Critical impact bar for "permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances." Any user who initiates an IBC transfer with a destination callback can have their entire transferred amount permanently locked in an unrecoverable isolated account, triggered purely by an unprivileged third party pre-funding a public, deterministically-computable address with a negligible amount of the same token — no validator/relayer collusion or privileged access required.

### Likelihood Explanation
High. Computing `GenerateIsolatedAddress(destChannel, sender)` requires only public information the attacker can observe from the sender's IBC transfer intent (destination channel is fixed per route, and sender is either the attacker's own address for self-griefing, or any address whose outgoing IBC-callback transfers the attacker wants to disrupt). Sending 1 wei to that address is a normal, permissionless ERC20 `transfer` call, requiring no special privileges, gas budget, or transaction ordering beyond "sometime before the callback executes" — it does not even need to be a front-run in the same block, since the dust can be deposited long in advance.

### Recommendation
Replace the absolute balance check with a delta/relative check: record `tokenPair` balance of `receiverHex` immediately before the approve/call sequence, and after the callback assert that the balance decreased by (at least) the amount of tokens delivered in this packet, rather than requiring the balance to be exactly zero. Alternatively, track and subtract any pre-existing balance so dust deposited prior to packet processing cannot affect the invariant used to gate committing the callback's fund movement.

### Proof of Concept
1. Attacker observes (or controls) `sender` address `S` and knows the destination channel `C` that a future/target IBC transfer with a destination callback will use.
2. Attacker computes `isolatedAddr = GenerateIsolatedAddress(C, S)` using the same deterministic derivation as `types.GenerateIsolatedAddress` [2](#0-1) .
3. Attacker sends 1 wei of the ERC20 representation of the token that will be transferred (`tokenPair.GetERC20Contract()`) directly to `isolatedAddr` via a normal `transfer` call — no special permission needed.
4. Victim submits an IBC transfer with a destination callback targeting a legitimate, correctly-implemented contract that fully drains the isolated address via `transferFrom`.
5. During `IBCReceivePacketCallback`, the approve and calldata call execute and successfully pull out the entire newly-delivered amount, but the post-check at [5](#0-4)  observes the attacker's residual 1 wei and returns an error.
6. Per the ADR-8 callback-middleware convention, the caller discards the cached context state changes on error (undoing the contract's fund pull), while the tokens already delivered to `isolatedAddr` by the earlier, independent OnRecvPacket transfer step remain there — permanently, since `isolatedAddr` has no private key to move funds out manually.

Note: I was not able to directly inspect the ibc-go v10 `callbacks` middleware's `ProcessCallback`/write-commit wiring in this index to fully confirm the exact commit/rollback boundary described in step 6; this is inferred from the standard ADR-8 pattern and the module's own documentation/comments about isolated addresses being irretrievable. Confirming the exact caller-side commit behavior would require inspecting the vendored `ibc-go` callbacks middleware source, which may not be fully covered by the current index — a full Devin session with repo access would be needed to verify this precisely.
