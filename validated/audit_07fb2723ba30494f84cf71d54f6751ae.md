### Title
Unbounded aggregate-signature nonce count enables remote resource exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` accepts an attacker-controlled 32-bit nonce-commitment count and deserializes that many curve points without imposing a protocol limit or comparing it against the expected verification set. [1](#0-0)  Successful parsing can be followed by `SchnorrAggregate::verify`, whose work and allocation also scale linearly with the attacker-controlled aggregate size. [2](#0-1) 

### Finding Description
The serialized format begins with a little-endian `u32` count, followed by that many `C::read_G` encodings and one `C::read_F` scalar. [3](#0-2)  The count is trusted directly in `0 .. u32::from_le_bytes(len)`, with no maximum aggregate size and no opportunity for the caller to provide the expected number of statements before parsing. [4](#0-3) 

A malicious serialized aggregate therefore causes the parser to retain every decoded point in `Rs`; even if verification later rejects the object, the deserialization cost and memory retention have already occurred. [5](#0-4)  If the attacker also controls or influences the verified statement set, verification allocates `2 * keys_and_challenges.len() + 1` pairs, derives a fresh aggregation weight for every statement, and performs a multiexponentiation over all supplied points. [6](#0-5) 

### Impact Explanation
An unprivileged party able to submit serialized aggregate signatures to this public parser can force CPU-intensive point decoding and memory growth proportional to the supplied count and payload, potentially exhausting process memory or repeatedly monopolizing verification workers. [1](#0-0)  At verification, each supplied statement additionally requires transcript processing, scalar arithmetic, vector growth, and a multiexponentiation, amplifying the cost after parsing. [7](#0-6)  This is a Medium-severity availability issue because exploitation requires an exposed caller that accepts aggregate-signature bytes or sufficiently large statement sets without an outer limit. [1](#0-0) 

### Likelihood Explanation
`SchnorrAggregate::read` is a public deserialization API over arbitrary `Read` input, so hostile signature bytes can directly control the advertised number of nonces. [1](#0-0)  `SchnorrAggregate::verify` is also public and performs unbounded linear work based on the supplied aggregate and verification list. [2](#0-1)  The vulnerability is reachable whenever these bytes originate from signatures or transaction data supplied by an unauthenticated party and no application-level size bound exists. [1](#0-0) 

### Recommendation
Require the expected aggregate length—or a hard protocol maximum—when reading an aggregate, reject a serialized count exceeding it before decoding any points, and reserve no attacker-controlled amount of memory. [1](#0-0)  Verification should similarly reject oversized `keys_and_challenges` lists before allocating `pairs` or deriving aggregation weights. [2](#0-1) 

### Proof of Concept
A hostile input sets the first four bytes to a large little-endian count and supplies repeated canonical point encodings followed by a canonical scalar; `read` stores every supplied point in `Rs`. [3](#0-2) 

```rust
// crypto/schnorr/src/aggregate.rs
use frost::curve::Ristretto;
use ciphersuite::{Ciphersuite, group::GroupEncoding};
use schnorr::SchnorrAggregate;

const COUNT: u32 = 1_000_000;

let mut encoded = Vec::new();
encoded.extend_from_slice(&COUNT.to_le_bytes());

let point = <Ristretto as Ciphersuite>::generator().to_bytes();
for _ in 0..COUNT {
    encoded.extend_from_slice(point.as_ref());
}

// Canonical zero scalar.
encoded.extend_from_slice(&[0u8; 32]);

// Retains one decoded Ristretto point per attacker-declared entry.
let aggregate =
    SchnorrAggregate::<Ristretto>::read(&mut encoded.as_slice()).unwrap();
assert_eq!(aggregate.Rs().len(), COUNT as usize);
```

If `verify` is invoked with a correspondingly large statement list, it additionally builds millions of scalar/point pairs and performs the final multiexponentiation over them. [7](#0-6)
