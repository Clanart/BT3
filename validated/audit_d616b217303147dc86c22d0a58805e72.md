### Title
Vote-locked boost factor is never decreased on unlock, permanently over-crediting referral yield share - (File: rewards/ReferralStorage.sol / VLMGP.sol)

### Summary
`ReferralStorage.updateTotalFactor()` is only invoked from `VLMGP._lock()` and `VLMGP.startUnlock()`, never from `VLMGP.unlock()`, `forceUnLock()`, or `cancelUnlock()`. As a result, once a referral-code holder locks MGP and gets a `userInfo.factor` baked into `totalBoostFactor`, fully withdrawing their MGP later does not reduce that factor, letting them keep an inflated share of the shared boost pool with zero locked MGP.

### Finding Description
`updateTotalFactor` recomputes `userInfo.factor = sqrt(IVLMGP(vlMGP).getUserTotalLocked(_account))` and adjusts `totalBoostFactor` accordingly [1](#0-0) . It is called from `_lock()` (on `lock`/`lockFor`) and from `startUnlock()` [2](#0-1) [3](#0-2) .

However, the actual withdrawal path `_unlock()` (invoked by both `unlock()` and `forceUnLock()`) only adjusts `totalAmountInCoolDown`/`totalAmount` and calls `withdrawVlMGPFor`; it never calls `IReferralStorage(referralStorage).updateTotalFactor` [4](#0-3) [5](#0-4) [6](#0-5) . `cancelUnlock()` similarly never touches the referral factor [7](#0-6) .

Note: the specific "repeated `startUnlock` in the same block causes compounding inflation via `totalBoostFactor -= ...; totalBoostFactor += ...`" mechanism described in the question does not hold up — `getUserTotalLocked` reflects the account's genuinely locked balance (which only changes via `lock`/`lockFor`/actual `unlock`, all `nonReentrant`), so re-invoking `updateTotalFactor` multiple times in the same block with an unchanged underlying locked amount is idempotent (subtract-then-add the same value nets to zero change). There is no "transient" inflated value to exploit via repeated calls.

The real, exploitable defect is the asymmetry: the factor is refreshed upward/recomputed on lock and on starting an unlock, but never refreshed on completing an unlock/force-unlock/cancel. An attacker who registers a referral code, locks a large amount of MGP (bumping `userInfo.factor` and `totalBoostFactor` up), then fully unlocks that MGP retains their inflated `userInfo.factor` in `totalBoostFactor` forever, since `_calBoosted` only reads `userInfo.factor / totalBoostFactor` and nothing ever re-syncs it downward [8](#0-7) .

### Impact Explanation
`trigger()` distributes referee-generated rewards to a referrer using `basic + boosted(_referer)`, where `boosted` is `BoostPoint * userInfo.factor / totalBoostFactor` [9](#0-8) . Because the attacker's stale, inflated `factor` remains counted in the `totalBoostFactor` denominator/numerator forever after withdrawing their MGP, they continue to receive a disproportionate share of the referral boost pool indefinitely while contributing zero locked capital, permanently diluting the boosted yield legitimately earned by other referrers who keep MGP locked. This is theft of unclaimed/ongoing yield from a shared pool (Immunefi: theft of unclaimed yield).

### Likelihood Explanation
Fully feasible with unprivileged actions: `registerCode()`, `lock()`/`lockFor()`, `startUnlock()`, and `unlock()` are all public/external and require no special role [10](#0-9) . The only cost is the temporary capital to lock and the cooldown wait before calling `unlock()`; the amount can be flash-loaned/borrowed briefly since it is withdrawn back in full (minus any penalty if force-unlocked). Any account with `myCode != bytes32(0)` can repeat this to keep inflating and freezing their share.

### Recommendation
Call `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` from `_unlock()` (covering both `unlock()` and `forceUnLock()`) and from `cancelUnlock()` as well, so the factor is always resynchronized to the account's current `getUserTotalLocked` value whenever locked balance changes in either direction.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, `MasterMagpie` mocks/fixtures; set `referralStorage` on `VLMGP`.
2. Attacker calls `registerCode()` to activate referral tracking.
3. Attacker calls `lock(largeAmount)` — assert `userInfo.factor == sqrt(largeAmount)` and `totalBoostFactor` increased accordingly.
4. Attacker calls `startUnlock(largeAmount)`, wait `coolDownInSecs`, then `unlock(slotIndex)` to fully withdraw all MGP back.
5. Assert `userInfo.factor` in `ReferralStorage` is still `sqrt(largeAmount)` (unchanged) and `totalBoostFactor` still includes it, even though the attacker's `getUserTotalLocked` is now `0`.
6. Call `trigger(referee, amount)` for a referee who used the attacker's code, and assert `boosted()`/`refererAmount` still reflects the stale inflated factor, proving indefinite over-crediting with zero locked capital.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
