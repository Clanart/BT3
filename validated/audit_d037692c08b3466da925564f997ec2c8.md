### Title
`ThresholdKeys::read` performs attacker-controlled pre-validation allocation and attacker-sized read loops, enabling per-call memory amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class in the report is unbounded memory growth driven by an attacker-controlled call: every `minify()` call leaks attacker-sized buffers, so a long-lived process that repeatedly invokes the function on public input grows until OOM. The Serai analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which trusts a u16 `n` taken directly from the untrusted byte stream to (a) pre-allocate `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` variant and (b) drive two `n`-iteration loops of `read_F`/`read_G`, all **before** `ThresholdParams::new(t, n, i)` validates `t`/`n`/`i` at the end of the function. `ThresholdKeys::read` is an explicitly in-scope entry point for untrusted bytes.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632):

```rust
let (t, n, i) = (read_u16()?, read_u16()?, Participant::new(read_u16()?)...);
...
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n { res.push(C::read_F(reader)?); }
  res
}),
...
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
ThresholdKeys::new(ThresholdParams::new(t, n, i)..., ...)
```

The ordering defect is that `n` is consumed structurally (allocation size + loop bounds) before any semantic validation. With `interpolation[0] == 0`, a header of ~12 bytes claiming `n = 0xFFFF` forces `Vec::with_capacity(65535)` of `C::F` elements (~2–3 MiB reserved for e.g. a 32–48-byte scalar type) plus a `HashMap` fill loop — regardless of whether that many elements actually follow. Like the CVE's early-return leak of the whole `NodeSet`, the capacity is committed up front and only torn down on error; on platforms/overloads where many such parses run concurrently (or where the reader is a streaming source that keeps the allocation alive), a small input repeatedly forces large resident allocations.

A secondary amplification exists even in the success path: `n` controls `n` scalar reads and `n` point decompressions with no cap other than `u16::MAX`, while a legitimate threshold set has a far smaller real `n` enforced only later by `ThresholdParams::new`.

### Impact Explanation
An unprivileged party feeding crafted bytes to `ThresholdKeys::read` (per the permitted attack surface) causes the host to reserve up to ~3 MiB and initiate up to 65,535 field/point decodings per call, from a tiny input. Repeated or concurrent calls produce sustained heap pressure and growth until memory exhaustion — the same denial-of-service shape as the reported per-call leak (attacker input → disproportionate memory footprint per invocation in a long-lived process). No secret is leaked; the impact is availability.

### Likelihood Explanation
Reachable wherever untrusted serialized `ThresholdKeys` are parsed (key-material handoff, recovery flows, or any endpoint accepting serialized keys/shares). The attacker needs only to set the `n` field to `0xFFFF` and select the `Constant` interpolation tag; no valid points, signatures, or protocol position are required to trigger the allocation. Exploitability is bounded by `u16` (max ~3 MiB amplification per call rather than the CVE's truly unbounded leak), which is why this rates Medium rather than High.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` **immediately after reading them** and before any `n`-sized allocation or loop. Additionally, avoid `Vec::with_capacity(n)` on untrusted lengths: either cap `n` at a protocol maximum first, or grow the vector incrementally (`Vec::new()` + `push`) so allocation is proportional to bytes actually present, matching the "only allocate as bandwidth is used" pattern already used elsewhere (e.g., chunked reads in `networks/ethereum/src/machine.rs`).

### Proof of Concept
```rust
use std::io;
use dkg::{ThresholdKeys, Participant};
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;

fn main() {
  // Craft a ThresholdKeys blob: valid curve ID, then n = 0xFFFF, interpolation = Constant
  let mut buf = vec![];
  let id = <Ristretto as Ciphersuite>::ID;
  buf.extend((id.len() as u32).to_le_bytes());
  buf.extend(id);
  buf.extend(1u16.to_le_bytes());        // t = 1
  buf.extend(0xFFFFu16.to_le_bytes());   // n = 65535 (unvalidated)
  buf.extend(1u16.to_le_bytes());        // i = 1
  buf.push(0u8);                         // Interpolation::Constant
  // No actual scalars follow — yet Vec::with_capacity(65535) already reserved ~2-3 MiB
  let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
  // Repeating this call (or running it concurrently) yields sustained ~3 MiB
  // allocations per ~15-byte input until the process exhausts memory.
}
```

Limitations of this analysis: I did not fully verify `ThresholdParams::new`'s internal bounds (if it rejects large `n`, the rejection still occurs only after the allocation) nor whether a concrete production endpoint pipes unauthenticated network bytes into `ThresholdKeys::read`; the finding rests on the stated attack-surface rule that untrusted bytes may reach `ThresholdKeys::read`.
