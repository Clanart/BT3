### Title
Silent auto-rewrite of git remote URL from unvalidated GitHub API `clone_url` enables repository hijack after rename/squat - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's local git `origin` remote URL using `clone_url` returned by the GitHub API, based only on string comparison of owner/name/protocol — never on a stable, unforgeable repository identifier. This mirrors the report's core defect class (a critical reference — contract owner / CCMP executor there, git remote destination here — being overwritten from an untrusted new value without validating it still denotes the same trusted principal/object).

### Finding Description
`updateRemoteUrl` is called from `repositoryWithRefreshedGitHubRepository` [1](#0-0)  which runs before essentially every push/pull/fetch via `withRefreshedGitHubRepository`. The flow:

1. Desktop looks up the stored `owner`/`name` pair for the repository via `matchGitHubRepository` and calls the GitHub API `api.fetchRepository(owner, name)` to get a fresh `apiRepo` object.
2. `updateRemoteUrl` then decides whether to overwrite the local remote: [2](#0-1) 
3. The only checks performed are: (a) the URL protocol didn't change, (b) the *previously recorded* remote still textually matches the previously known `cloneURL`, and (c) the new `clone_url` differs from the current remote. None of these validate that the API object being returned still refers to the *same* underlying repository the user originally cloned/added — the comparison is purely string/owner/name based via `urlMatchesRemote` [3](#0-2) , not a stable numeric repository id.
4. If the actual `owner/name` returned by the GitHub API for that slot now belongs to a different, attacker-controlled repository (e.g. after the original repo is renamed/deleted and the freed `owner/name` combination is re-registered/squatted by an attacker, or a malicious org repo is created under a name that later collides with a stale local record), `setRemoteURL` is invoked silently: [4](#0-3)  → [5](#0-4) , with no user prompt or confirmation dialog (unlike the manual settings-UI flow in `repository-settings.tsx` which does show the change to the user before applying it [6](#0-5) ).

This is exactly the pattern in the seed report: a privileged reference (contract owner / CCMP executor there, `origin` remote there / here) is reassigned to an attacker-influenced value coming from an external system (the caller / the GitHub API) with only superficial validation, and the guard that exists (`_enforceIsContractOwner` there, `protocolsMatch`/`remoteUrlUnchanged` here) does not verify the *identity* of the new target, only surface-level properties.

### Impact Explanation
If exploited, a user's next `git push` silently sends commits (potentially containing proprietary/private code) to an attacker-controlled repository instead of the intended one, and subsequent `git pull`/`fetch` operations bring in commits from the attacker's repository under the guise of the original, trusted repo — enabling supply-chain injection of malicious code that the user may then merge/build/run, believing it originated from their own trusted history. This satisfies "silent corruption of what the user commits or pushes" and potential credential/code exfiltration outlined as valid impact.

### Likelihood Explanation
Low-to-moderate. It requires an attacker to control (or successfully claim) the `owner/name` slot on GitHub that a victim's stale local `GitHubRepository` record points to — e.g. via repository deletion+recreation, org/user rename races, or repo-name squatting after a legitimate rename — combined with the victim performing a push/pull/fetch before Desktop's UI/user notices the discrepancy. No local access, admin rights, or social engineering beyond normal git usage is required, matching the report's "low likelihood due to privileged/gated call path but real if the referenced object changes hands" framing. I was unable to fully confirm within the available tooling whether `IAPIRepository`/`apiRepo` exposes a stable numeric GitHub `id` that could already be compared but isn't — this would strengthen or narrow the exploitability assessment and should be verified directly in `app/src/lib/api.ts`.

### Recommendation
- Pin repository identity by GitHub's immutable numeric repository `id` (already stored as `dbID` on `GitHubRepository`) rather than owner/name strings when deciding to auto-rewrite the remote URL.
- Before calling `gitStore.setRemoteURL`, verify `apiRepo.id === gitHubRepository.dbID` (or equivalent), not just that owner/name path components differ.
- At minimum, surface a non-blocking notification/confirmation to the user the first time Desktop auto-changes a remote URL, rather than silently rewriting it.

### Proof of Concept
1. Victim has Desktop tracking `origin` for `github.com/acme/widget`, backed by a local `GitHubRepository` record for owner `acme`, name `widget`.
2. The `acme/widget` repository is deleted or renamed away, freeing the `acme/widget` slug.
3. Attacker (who compromises or owns the `acme` org, or exploits a rename-then-recreate race) creates a new repository at `acme/widget` under their control.
4. On the victim's next push/pull/fetch, `repositoryWithRefreshedGitHubRepository` fetches `api.fetchRepository('acme','widget')`, which now returns the attacker's repo's `clone_url`.
5. `updateRemoteUrl`'s checks (protocol match, prior owner/name match, current mismatch) all pass since they only compare strings, and `gitStore.setRemoteURL` silently repoints `origin` to the attacker's clone URL [7](#0-6) .
6. The victim's next push sends their commits to the attacker's repository, and/or the victim starts pulling attacker-supplied history under the trusted local repo name/UI.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
