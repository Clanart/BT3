### Title
Post-merge/prepare-commit-msg hooks from an untrusted `pull()`/`fetch()`-merged repository run with the user's full shell environment before any "unsafe repository" trust prompt is shown - (File: `app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/hooks-proxy.ts`)

### Summary
The external report's broken invariant is that a single actor (the vault "owner"/"controller") is trusted to define a parameter (royalty %) that is supposed to be constrained/arbitrated by the protocol, and the app performs no bound-checking or timing separation before honoring that attacker-supplied value. The closest reachable analog in GitHub Desktop is the new git-hooks-execution feature: content that lives inside a repository the user merely pulls/merges/commits in (i.e., attacker-influenced, since hook files are read from whatever `core.hooksPath`/`.git/hooks` resolves to for that working tree) is executed with the user's real shell environment (`GIT_CONFIG_PARAMETERS`, full `PATH`, credentials in env, etc.), and the only "guard" Desktop has for untrusted repository content (the dubious-ownership / "Trust Repository" prompt in `add-existing-repository.tsx` / `missing-repository.tsx`) is not part of this hook-interception code path at all.

### Finding Description
`withHooksEnv()` is invoked from every `git()` call that sets `interceptHooks` (`app/src/lib/git/core.ts:276`), including `pull()` (`app/src/lib/git/pull.ts:48-56`, intercepting `pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-merge`, `pre-rebase`, `pre-commit`, `post-rewrite`) and `createCommit()`/`push()`. Inside `withHooksEnv`, `getRepoHooks(path, opts.interceptHooks)` (`app/src/lib/hooks/get-repo-hooks.ts:76-107`) resolves the hooks directory purely from repository-local config (`core.hooksPath`, falling back to `git rev-parse --git-path hooks`) and lists any file there matching a known hook name. On Windows, the executable-bit check is explicitly skipped ("we have to assume that any valid hook name is executable", lines 98-102), so any file simply named e.g. `post-merge` in that directory is treated as a hook to run.

Desktop then copies a `process-proxy` binary into a temp dir for each matched hook name and sets `core.hooksPath` to that temp dir via `GIT_CONFIG_PARAMETERS` (`with-hooks-env.ts:78-96`), so the real Git process transparently invokes Desktop's proxy, which in `createHooksProxy` (`app/src/lib/hooks/hooks-proxy.ts:144-264`) spawns the *actual* hook binary with `shellEnv.env` merged with the safe-prefixed Git env vars — i.e., the user's real, fully-loaded shell environment (`spawn(gitPath, args, { env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' } })`). This is by design meant to run the user's legitimate hooks (feature flag `enableHooksByDefault`, `app/src/lib/hooks/config.ts:1-12`), but nothing in this path checks whether the repository is one Desktop has flagged as having "dubious ownership"/unsafe. That check exists elsewhere in the app (`app/src/ui/add-repository/add-existing-repository.tsx:129-174`, `app/src/ui/missing-repository.tsx:62-134`) and is purely a one-time UI gate when *adding* a repository — it is never consulted by `git/core.ts`, `pull.ts`, `commit.ts`, or `push.ts` before hooks are intercepted and executed.

### Impact Explanation
Because hook execution happens with the user's real shell environment (not a sandboxed/minimal one), any hook script that ends up under the resolved hooks path for a repository the user interacts with (via `pull`, `commit`, or `push`, all of which set `interceptHooks`) executes with the same privileges and environment as GitHub Desktop and the user's shell, including any credentials or tokens exported into that shell environment. This satisfies the "code execution as a result of attacker-controlled repository/fetched content" impact class explicitly called out as valid.

### Likelihood Explanation
Likelihood is bounded by how hook files get into the resolved hooks directory for a given repository — normal `git clone`/`git fetch` does not transmit tracked files into `.git/hooks`, so the most direct vector requires either: (a) `core.hooksPath` being set to point at a directory the remote repository can populate (e.g., a path inside the working tree containing files, which is a config change, not something a plain clone injects on its own), or (b) opening/importing a directory (e.g., "Add Existing Repository", a downloaded/extracted archive, or a directory shared by a colleague) that already contains executable-looking files under its hooks path. I could not verify from the indexed code whether any Desktop or dugite/Git code path in this repository can itself write into `.git/hooks` or set `core.hooksPath` purely as a side effect of cloning/fetching a malicious remote (which would raise likelihood to "attacker fully controls the trigger"); that specific write-primitive is unconfirmed in the code I could inspect.

### Recommendation
Gate the hooks-interception feature (`withHooksEnv`/`getRepoHooks`) behind the same "repository trust" signal used by `add-existing-repository.tsx`/`missing-repository.tsx` (dubious ownership / unsafe path), and refuse to intercept or execute hooks for repositories that have not been explicitly trusted. Additionally, restore the executable-bit check on Windows instead of trusting any file with a known hook name, and avoid always merging the user's full shell environment into hook execution — only enable environment inheritance for hooks in repositories the user has explicitly trusted.

### Proof of Concept
Concrete PoC could not be fully constructed from the indexed code alone because the exact mechanism by which a cloned/fetched repository would populate `core.hooksPath` or the resolved `.git/hooks` directory without additional local action is not confirmed in this codebase snapshot. The reachable code path is:
1. User enables/has enabled hooks-env (default per `enableHooksByDefault`, `app/src/lib/hooks/config.ts:4`).
2. User adds/opens a repository whose `core.hooksPath` (local config) resolves to a directory containing a file named e.g. `post-merge` (or `pre-commit`), without ever seeing the "unsafe repository" prompt, since that prompt is unrelated to hook content.
3. User runs `git pull` in Desktop → `pull()` (`app/src/lib/git/pull.ts:48-56`) sets `interceptHooks: ['post-merge', ...]` → `withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts:29-96`) discovers the file via `getRepoHooks` and proxies its execution with the user's full shell environment via `hooks-proxy.ts:249-255`.

Given the residual uncertainty about the exact attacker-controlled write primitive into the hooks directory, this should be validated with a live Desktop session (e.g., testing whether a crafted repository — via submodule config injection, a shared `core.hooksPath`, or archive extraction — can populate the resolved hooks directory purely through clone/fetch/pull) before treating this as a fully confirmed, unprompted RCE.
