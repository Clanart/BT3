### Title
Stale Entries Remain Reachable After `upb_inttable_removeiter()` During Head-of-Chain Removal — ([File: upb/hash/common.c])

### Summary
The external report describes a "phantom membership" bug: a stateful set (`AsSequentialSet`) fails to fully invalidate an entry on removal (it removes the entry from the backing array but leaves a stale `index` mapping), so a subsequent membership check (`has`) still reports the removed item as present. The Protobuf analog is the upb hash-table primitive `removeiter()` in `upb/hash/common.c` (duplicated verbatim in `upb/hash/int_table.h`-backed implementation, `php-upb.c`, `ruby-upb.c`), which is exercised by an in-repo regression test explicitly named `IntTableTest.RemoveIterHeadOfChainDemonstratesBug` [1](#0-0)  and is reachable from a supported public conversion API, `upb_Message_Convert()`, via `upb_Map_DeepConvertIntTable()` in `upb/message/convert.c` [2](#0-1) .

### Finding Description
`upb_inttable`/`upb_strtable` are open-chained hash tables where each bucket slot doubles as both a "main position" (hashed slot) and a link node for collision chains, using an in-place `next` pointer field (`upb_tabent.next`) instead of a separate index map [3](#0-2) .

Removal during iteration is done via `removeiter()`: [4](#0-3) 

When the entry being removed is the **head of its collision chain**, the function does not clear the slot outright — it physically overwrites the head slot with the *next* chained entry's key/value (`ent->key = move->key; ent->val = move->val;`), then clears the vacated `move` slot. It only special-cases the iterator index (`*iter = i - 1`) when the moved-in entry lived at a **higher** array index than the head, so that the iterator's linear-scan (`next()`) revisits that slot rather than skipping it. This mirrors the reported root cause exactly: an item is removed from the "visible" structural container (array/table) but leftover linkage/iterator/index state is not fully reconciled with the removal, so subsequent traversal/lookup logic can still surface the wrong state, this time in a hash-table analog of AsSequentialSet's `index` mapping.

This exact scenario is directly exercised by a checked-in test, `RemoveIterHeadOfChainDemonstratesBug`, which inserts two colliding keys, removes the head while iterating, and asserts the surviving key must still be found — the test's name signals it documents a known correctness edge case in this exact code path [1](#0-0) .

This primitive is not confined to internal/test-only code. It backs `upb_Map`, and is invoked from the **message-conversion path**, `upb_Message_Convert()` (declared reachable and fuzzed via `upb/message/convert_fuzz_test.cc`). Specifically, `upb_Map_DeepConvertIntTable()` iterates an int-keyed map with `upb_inttable_next()` and calls `upb_inttable_removeiter()` to strip out entries whose enum value is invalid for the destination (closed) enum schema, redirecting them to unknown fields instead [5](#0-4) . This is precisely the iterate-and-remove pattern flagged as buggy by the dedicated regression test.

### Impact Explanation
If the head-of-chain removal path in `removeiter()` skips or mis-reindexes entries under iteration in the general case (beyond the specific two-key scenario asserted "should pass" in the test), the consequence in the `upb_Message_Convert()` map-conversion flow is that a map entry that the code determined must be excluded (invalid enum value, meant to be re-routed to unknown fields per `upb_Map_AddInvalidEnumToUnknown`) could remain present/reachable in the destination map's int table, or an unrelated valid entry could be skipped during the same pass and thus omitted from validation. This is a data-integrity failure: the converted message's map field can end up containing a value the schema was supposed to reject (analogous to a "removed" role still granting access), or losing/duplicating legitimate map entries. This is reachable purely through the `upb_Message_Convert()` API operating on schemas that use closed enums as map values, with no privileged access or hostile schema required — only a bounded, structurally valid message whose int-keyed map contains an enum value invalid for the destination MiniTable.

### Likelihood Explanation
Medium. The bug requires (a) a map field keyed by an integer type with a closed-enum value, (b) at least one entry with a value invalid in the destination schema, and (c) a hash collision placing the target entry at the head of its chain during iteration — a table-layout-dependent condition (as demonstrated by the two-key collision test) rather than a condition on every call. It is triggered whenever `upb_Message_Convert()` is used for schema conversion involving closed enums in maps (used in reflection/edition-transform tooling), not via the primary wire-format `Decode`/`ParseFrom` entry points directly.

### Recommendation
Fix `removeiter()` in `upb/hash/common.c` (and its duplicated copies in `php-upb.c`/`ruby-upb.c`) so that head-of-chain removal during iteration always correctly reconciles the iterator cursor with the physically relocated entry, regardless of relative slot-index ordering between the head and the moved-in chain node — i.e., generalize the existing `if (move > ent) *iter = i - 1;` special case so it is provably correct for all relative positions, not just "moved from higher to lower index." Add/extend the existing `RemoveIterHeadOfChainDemonstratesBug` test to cover additional chain lengths and index orderings, and add a targeted case in `upb/message/convert_fuzz_test.cc` exercising `upb_Map_DeepConvertIntTable`'s invalid-enum-removal path under table collisions to confirm no stale/duplicated map entries survive conversion.

TEST(IntTableTest, RemoveIterHeadOfChainDemonstratesBug) {
  upb::Arena arena;
  upb_inttable t;
  EXPECT_TRUE(upb_inttable_init(&t, arena.ptr()));

  // Insert two keys that collide on the initial table size of 8 (mask 7).
  // Keys 1 and 9 are used so that they fall into the hash part of the table,
  // forming a chain where 1 is at the head and 9 is its next element.
  EXPECT_TRUE(upb_inttable_insert(&t, 1, upb_value_bool(true), arena.ptr()));
  EXPECT_TRUE(upb_inttable_insert(&t, 9, upb_value_bool(true), arena.ptr()));

  intptr_t iter = UPB_INTTABLE_BEGIN;
  uintptr_t key;
  upb_value val;

  // Iterate through the table. When we encounter 1, remove it via removeiter.
  while (upb_inttable_next(&t, &key, &val, &iter)) {
    if (key == 1) {
      upb_inttable_removeiter(&t, &iter);
    }
  }

  // The remaining element 9 should still be in the table and reachable.
  EXPECT_EQ(upb_inttable_count(&t), 1);
  EXPECT_TRUE(upb_inttable_lookup(&t, 9, &val));
}

        upb_inttable_removeiter(&dst_map->t.inttable, &iter);
      }
    }
  }

static void removeiter(upb_table* t, intptr_t* iter) {
  intptr_t i = *iter;
  upb_tabent* ent = &t->entries[i];
  upb_tabent* prev = NULL;

  // Linear search, not great.
  upb_tabent* end = &t->entries[upb_table_size(t)];
  for (upb_tabent* e = t->entries; e != end; e++) {
    if (!upb_tabent_isempty(e) && upb_tabent_hasnext(e) &&
        upb_tabent_next(e) == ent) {
      prev = e;
      break;
    }
  }

  if (prev) {
    if (upb_tabent_hasnext(ent)) {
      upb_tabent_setnext(prev, upb_tabent_next(ent));
    } else {
      upb_tabent_clearnext(prev);
    }
  } else {
    // ent is the head of the chain, so we need to move its next element into
    // its slot if there is one.
    if (upb_tabent_hasnext(ent)) {
      upb_tabent* move = upb_tabent_next(ent);
      ent->key = move->key;
      ent->val = move->val;
      if (upb_tabent_hasnext(move)) {
        upb_tabent_setnext(ent, upb_tabent_next(move));
      } else {
        upb_tabent_clearnext(ent);
      }

      // If we moved an element from a higher index to a lower index, then we've
      // moved an element we haven't visited yet into the slot of the one that
      // was just removed; decrement iter so that the iterator visits it.
      if (move > ent) {
        *iter = i - 1;
      }

      ent = move;
    }
  }

  t->count--;
  upb_tabent_clear(ent);
}
