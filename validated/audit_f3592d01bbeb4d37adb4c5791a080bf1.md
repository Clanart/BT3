## Analog Found

### Title
Partial line-selection state (`DiffSelection`) becomes stale relative to on-disk content for files that are not currently being viewed, silently corrupting committed patches - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/git/update-index.ts`)

### Summary
The Sherlock report describes a class of bug where state is *recomputed fresh from an external enumeration each time it's needed* (`pendingRewards` re-derives the reward-token list from the pool every call), so if the underlying enumeration shrinks/changes between the time a user's entitlement was recorded and the time it's paid out, the stored intent silently no longer maps to anything and is lost. The same broken invariant — "position/index-based intent recorded against one version of an enumerable resource, later applied against a different version of that resource without revalidation" — exists in Desktop's partial-commit (line-by-line staging) pipeline.

### Finding Description
When a user does a partial commit, GitHub Desktop tracks *which lines* of a file to include using `DiffSelection`, which stores selection as a set of **absolute line indices** into a specific `ITextDiff` snapshot [1](#0-0) . These indices have no inherent meaning outside of the exact diff hunk layout they were computed against.

Desktop only revalidates this index-based selection for the **single file currently being viewed/diffed** in the Changes pane. `updateChangesWorkingDirectoryDiff` explicitly acknowledges the diff can change dramatically and only patches up `selectableLines` for the actively selected file, and says so in its own comment: [2](#0-1) 

Meanwhile, `updateChangedFiles` (called on every status refresh, e.g. after a fetch, checkout, or any background git operation) only preserves a file's existing `DiffSelection` object by file **ID** — it does **not** re-derive or invalidate the absolute line indices for files that are not the one currently open in the diff viewer: [3](#0-2) 

At actual commit time, `stageFiles` builds the index using this same stale `file.selection` object, applying `applyPatchToIndex` for any file with a `Partial` selection type: [4](#0-3) 

The patch is generated by walking a diff and checking `file.selection.isSelected(absoluteIndex)` for each line — again, no validation that these indices still refer to the same logical lines that the user actually reviewed/selected: [5](#0-4) 

### Impact Explanation
If the working-directory content of a file with an existing partial selection changes between the time the user made that selection and the time of commit (e.g., a background `git fetch`/checkout-triggered file rewrite, an external tool, a submodule update, or any process that alters tracked file content while the file is *not* the one currently displayed in the diff viewer), the previously recorded line indices no longer correspond to the same semantic lines. Because Desktop does not re-validate/re-map indices for non-visible files, `formatPatch`/`applyPatchToIndex` will apply the user's old selection to the new content positionally rather than semantically. This can silently stage/commit lines the user never reviewed or approved (or drop lines they intended to include), i.e. exactly the "silent corruption of what the user commits" category — the git-analog of "removed reward tokens are lost/misdirected because enumeration was recomputed fresh without preserving the original binding."

### Likelihood Explanation
This requires: (1) the user has made a partial (line-level) selection on a file, (2) that file is not the one currently open in the diff pane, and (3) the file's on-disk content changes (via any git operation, hook, or external process) before the user commits. Desktop performs background status refreshes and fetches routinely, and users frequently switch between files in the Changes list while leaving prior partial selections in place, making the precondition plausible without any unusual user action. However, triggering a specific *malicious* corruption (rather than a generic stale-selection glitch) would additionally require the attacker to control what changes in the file (e.g., via a crafted post-checkout/post-merge hook in a cloned/fetched repository) and to have some knowledge of/influence over line offsets, which lowers exploitability from "trivial" to "possible but requires a crafted repository."

### Recommendation
Revalidate every file's `DiffSelection` against a fresh diff (not just the currently-displayed file's) whenever the working directory status changes, or switch away from raw absolute-line-index selection to content-anchored selection (e.g., diffing against the line content itself, similar to the report's recommendation to key rewards by `tokenId` instead of by live pool enumeration). At minimum, `stageFiles`/`applyPatchToIndex` should re-fetch the diff immediately before staging and reject/clear any selection that can no longer be unambiguously mapped onto the new diff, rather than silently applying old indices to new content.

### Proof of Concept
Conceptual reproduction based on the code paths above (not independently executed):
1. Open Desktop on a repo with two modified tracked files, `A.txt` and `B.txt`.
2. In the Changes list, select `A.txt`'s diff and make a partial line selection (include only some lines) — this stores absolute-line-index state in `A.txt`'s `WorkingDirectoryFileChange.selection`.
3. Switch the diff viewer to `B.txt` (so `A.txt` is no longer the "currently selected file" per `updateChangesWorkingDirectoryDiff`).
4. Trigger a change to `A.txt`'s content without Desktop's diff viewer being active on it (e.g., a `post-checkout`/`post-merge` hook rewriting the file after a `git fetch`+background operation, or any external process appending/removing lines), altering the file's hunk layout while keeping it "Modified" so it still appears in Changes.
5. Commit including `A.txt`. `stageFiles` → `applyPatchToIndex` → `formatPatch` will apply the old absolute-line-index selection to the new hunk layout of `A.txt`, staging different, unintended lines than what the user actually reviewed and selected, with no warning to the user.

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
