### Title
`whenNotPaused` Modifier on `unlock()`/`cancelUnlock()` Blocks Users From Claiming Already-Processed Cooldown Funds - ([File: VLMGP.sol], [File: wombat/mWomSV.sol])

### Summary
`VLMGP.sol` and `mWomSV.sol` gate both the *entry* action of initiating a token lock/unlock cooldown and the *completion* action of finalizing an already-expired cooldown behind the same `whenNotPaused` modifier. This mirrors the reported bug class where a single boolean check is reused to gate both the start of a withdrawal process and its final claim step, so pausing the contract (a routine operational action, not a malicious one) freezes funds users have already earned the right to withdraw.

### Finding Description
In `VLMGP.sol`, `startUnlock()` begins a cooldown for a user's locked MGP, and after `coolDownInSecs` elapses the user must call `unlock()` to actually receive their MGP back: [1](#0-0) 

Both `startUnlock()` and the finalizing `unlock()` (as well as `cancelUnlock()` and `forceUnLock()`) share the exact same `whenNotPaused` modifier: [2](#0-1) [3](#0-2) 

The identical pattern exists in `mWomSV.sol` for mWOM lock slots: [4](#0-3) [5](#0-4) 

`unlock()` only transfers tokens for a slot whose cooldown has already fully elapsed (`slot.endTime <= block.timestamp`), i.e., funds that are already "processed" and rightfully claimable by the user. Because the same pause flag used to halt new locking/unlocking activity also blocks this final claim step, an admin pausing the contract for an unrelated, legitimate reason (e.g., an incident elsewhere in the protocol) prevents every user with an expired cooldown slot from retrieving their MGP/mWOM, exactly analogous to the reported `check_withdrawal_enabled()` bug gating both `request_withdrawal()` and the final `withdraw()`.

### Impact Explanation
Users who have already waited out their cooldown period (which can be a substantial duration set by `coolDownInSecs`) cannot retrieve their already-unlocked MGP/mWOM while the contract is paused, and also cannot use `cancelUnlock()` to abort and re-lock. If the pause persists (there is no time bound on `pause()`), this constitutes a freeze of user funds exceeding 24 hours, satisfying the funds-freezing impact bar.

### Likelihood Explanation
No malicious actor is required — this is triggered by ordinary operational use of the existing `pause()`/`_pause()` admin function, which is a standard, expected lever in the protocol (e.g., during incident response), combined with any user who happens to have a slot whose cooldown has already elapsed. The reachable path (`unlock()`/`cancelUnlock()`) is directly callable by any unprivileged wallet and reverts solely due to the shared pause flag.

### Recommendation
Split the `whenNotPaused` gating so that entry functions (`lock`, `lockFor`, `startUnlock`) can be paused independently from exit/completion functions (`unlock`, `cancelUnlock`, `forceUnLock`). At minimum, allow `unlock()` (and `cancelUnlock()`) to proceed even while the contract is paused for slots whose cooldown has already expired, since these represent funds the user is already entitled to.

### Proof of Concept
1. User calls `startUnlock(amount)` on `VLMGP` (or `mWomSV`), starting a cooldown slot with `endTime = block.timestamp + coolDownInSecs`.
2. Time passes beyond `endTime`, so the slot is fully unlockable per `getFullyUnlock()`/`unlock()`'s own checks. [6](#0-5) 
3. Admin calls `pause()` for any operational reason unrelated to this user's slot. [7](#0-6) 
4. User calls `unlock(slotIndex)` to claim their already-expired, already-earned MGP — the call reverts due to `whenNotPaused`, even though the funds are fully vested and owed to the user, freezing them for as long as the pause remains active.
