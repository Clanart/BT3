### Title
Permissionless native-ERC20 token pair registration allows attacker to permanently un-back circulating bank coins via arbitrary/rebasing ERC20 logic - ([File: x/erc20/keeper/msg_server.go])

### Summary
Sherlock M-5 describes lenders losing value because Sentiment's `LToken` assumes ERC20 `balanceOf()` is a static, reliable measure of value and does not account for rebasing/airdropped balance changes. The Cosmos EVM analog is the `x/erc20` Coin↔ERC20 conversion bridge, which escrows native ERC20 tokens 1:1 against minted bank coins and relies on point-in-time `balanceOf()` deltas during `ConvertERC20`/`ConvertCoin`, with **no mechanism ever re-verifying that total escrowed ERC20 balance still backs total outstanding bank-coin supply**. Combined with `PermissionlessRegistration: true` by default [1](#0-0) , any unprivileged user can register their own arbitrary ERC20 contract as a token pair via `MsgRegisterERC20` [2](#0-1) , and later drain/rebase/burn the module's escrowed balance out-of-band from any convert transaction, permanently stranding bank coins already distributed to victims.

### Finding Description
`ConvertERC20`/`convertERC20IntoCoinsForNativeToken` escrow ERC20 tokens on the module account and mint an equal amount of bank coin, verifying only the **delta** of the module's `balanceOf()` across that single EVM call [3](#0-2) . `ConvertCoinNativeERC20` performs the inverse: burn bank coin, unescrow ERC20 to the receiver, again checking only the delta for that one call [4](#0-3) .

These invariant checks only catch fee-on-transfer skew that happens *during* the specific transfer call itself. They do nothing to protect against the token contract's own logic changing the module's escrowed balance **outside** of a convert call — e.g., a "rebase", "adminBurn", or deflationary mechanism that the contract owner (the attacker, since they deployed it) can invoke at will. This is exactly the rebasing/airdrop class of accounting bug from the report: shares (bank coin) are treated as permanently equal to the ERC20 amount originally escrowed, regardless of subsequent changes to the underlying token's balance.

Critically, registering a completely attacker-controlled ERC20 contract as a token pair is not privileged: `DefaultParams()` sets `PermissionlessRegistration: true` [1](#0-0) , and `RegisterERC20` only enforces authority checks when that param is `false` [2](#0-1) . So the Sherlock team's own mitigation for the original bug class ("admins should not add rebasing/fee-on-transfer tokens to allow lists") is structurally unavailable here by default — there is no allowlist gate at all.

Attack outline:
1. Attacker deploys a malicious ERC20 contract they fully control (mint at will, and an owner-only function that can arbitrarily reduce/burn any address's balance, including the erc20-module escrow address).
2. Attacker calls `MsgRegisterERC20` (permissionless) to create a `TokenPair` for this contract, minting a corresponding native denom (`erc20/<address>`).
3. Attacker mints tokens to themselves and calls `MsgConvertERC20` to escrow N tokens on the module account, minting N bank coins to themselves [5](#0-4) .
4. Attacker distributes/sells/transfers those N bank coins to victims via ordinary bank sends or IBC transfers — the coins look identical to any other 1:1-backed token-pair denom.
5. Attacker then calls their contract's privileged function directly (not through any `x/erc20` code path) to reduce the module account's ERC20 balance to near zero.
6. When victims later attempt `MsgConvertCoin` to redeem their bank coins back to ERC20, the module's `CallEVM` "transfer" call to the drained contract will fail or return insufficient tokens; the delta check in `ConvertCoinNativeERC20` reverts with `ErrBalanceInvariance` (or the underlying ERC20 transfer itself reverts) [6](#0-5) . Victims' bank coins become permanently unredeemable — value is effectively destroyed/frozen because the corresponding backing asset can never be recovered.

### Impact Explanation
Victim bank-coin holders (who received the coin honestly, e.g., via P2P transfer or IBC) permanently lose the ability to redeem 1:1 backing ERC20 value, since nothing in the protocol ever re-checks or restores that outstanding coin supply equals actual escrowed ERC20 balance. This is a permanent freezing/loss of spendable user value backed by a token-pair, matching the Critical impact gate ("permanent freezing, locking, theft ... of ... token-pair-backed balances").

### Likelihood Explanation
High reachability: registration is permissionless by default, requiring only that the attacker deploy and control their own ERC20 contract — no governance or admin action needed. The exploit path uses only standard, publicly available message types (`MsgRegisterERC20`, `MsgConvertERC20`, `MsgConvertCoin`, ordinary bank/IBC sends). The only non-determinism is whether a given chain deployment keeps `PermissionlessRegistration=true` (the shipped default) — if operators disable it, this specific vector is closed, but the underlying invariant gap (no cross-time backing verification) remains latent for any token pair whose owner/contract can be manipulated post-registration (e.g., via `pair.IsNativeERC20()` external-owner tokens generally).

### Recommendation
- Do not ship `PermissionlessRegistration: true` as the default; require governance-vetted allowlisting for "native ERC20" (external-owner) token pairs, consistent with the Sherlock team's own stated mitigation for this bug class.
- For native-ERC20 token pairs, periodically (or on each convert operation) validate that the module's actual `balanceOf()` for the escrow account still equals or exceeds outstanding bank-coin supply for that denom, and reject/pause conversions if a discrepancy is detected, rather than only checking the delta of the current call.
- Consider disabling/pausing a token pair automatically if an anomalous balance change (unrelated to any `x/erc20`-issued transfer) is detected on the escrow account.

### Proof of Concept
Not independently executed against a live node; this is derived from static analysis of `x/erc20/keeper/msg_server.go` and `x/erc20/types/params.go`. A concrete PoC would: (1) deploy a minimal ERC20 with `mint(address,uint256)` and `forceBurn(address,uint256)` owner-only functions, (2) call `MsgRegisterERC20` with default params, (3) mint+`MsgConvertERC20` to create escrowed backing and bank coin, (4) transfer bank coin to a second test account, (5) call `forceBurn` on the module's escrow address directly via EVM tx, (6) attempt `MsgConvertCoin` from the second account and observe failure/permanent lock of its bank coin balance. I was not able to execute this in the current session; a background Devin session with repo/test-suite access would be needed to fully validate against the actual `ErrBalanceInvariance` revert behavior and confirm no other guard (e.g., a periodic invariant check elsewhere in the module) exists that I did not locate.

func (k Keeper) ConvertERC20(
	goCtx context.Context,
	msg *types.MsgConvertERC20,
) (*types.MsgConvertERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Error checked during msg validation
	receiver := sdk.MustAccAddressFromBech32(msg.Receiver)
	sender := common.HexToAddress(msg.Sender)

	pair, err := k.MintingEnabled(ctx, receiver, msg.ContractAddress)
	if err != nil {
		return nil, err
	}

	// Check ownership and execute conversion
	if pair.IsNativeERC20() {
		// Remove token pair if contract is suicided
		acc := k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())
		if acc == nil || !acc.HasCodeHash() {
			k.DeleteTokenPair(ctx, pair)
			k.Logger(ctx).Debug(
				"deleting selfdestructed token pair from state",
				"contract", pair.Erc20Address,
			)
			// NOTE: return nil error to persist the changes from the deletion
			return nil, nil
		}

		return k.convertERC20IntoCoinsForNativeToken(ctx, pair, msg, receiver, sender) // case 2.1
	} else if pair.IsNativeCoin() {
		return nil, types.ErrNativeConversionDisabled
	}

	return nil, types.ErrUndefinedOwner
}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}
