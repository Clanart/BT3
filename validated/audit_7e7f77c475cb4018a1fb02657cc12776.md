### Title
Unchecked `u64` arithmetic in `SignableTransaction::new` panics on overflow, DoSing transaction construction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` performs unchecked `u64` multiplication and summation on attacker-influenced values (`fee_per_vbyte`, the vbyte size derived from the payment count, and the `u64` payment amounts). Unlike the surrounding code which carefully uses `checked_sub` and `Result`-returning errors, the products `fee_per_vbyte * vbytes` and the sums `input_sat`, `payment_sat`, and `payment_sat + needed_fee` use plain arithmetic that panics on overflow in release builds (or wraps in debug), mirroring the `priceRange * currentStep` overflow in `MeritDutchAuction#getPriceAt` that renders the contract unusable. [1](#0-0) 

### Finding Description
Three unchecked operations exist on the reachable path:

1. `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` — `Iterator::sum::<u64>` panics on overflow. Each `payment.1` is a `u64` amount only checked to be `>= DUST` (send.rs:165-169), so two payments near `u64::MAX` overflow before the `NotEnoughFunds` check at line 215 ever runs. [2](#0-1) 
2. `let mut needed_fee = fee_per_vbyte * vbytes;` — unchecked `u64` multiply (send.rs:206).
3. `if input_sat < (payment_sat + needed_fee)` — unchecked `u64` add (send.rs:215), and identically `fee_with_change` at line 227 is only guarded for the subtraction, not `payment_sat + fee_with_change`. [3](#0-2) 

The vbyte size itself scales with the attacker-controlled `payments` list length (`calculate_weight_vbytes` builds an output per payment), so `fee_per_vbyte * vbytes` overflows with a large fee rate and many outputs. [4](#0-3) 

### Impact Explanation
An overflow panics inside `SignableTransaction::new` instead of returning a `TransactionError`. Since this is the transaction-construction entry point on the signing path — the produced `SignableTransaction` is what gets signed via `sign`/`calculate_share` — a panic aborts signing for that transaction, the exact "mint becomes unusable" impact of the reference finding. The payment amounts are attacker-influenced public inputs (withdrawal/output amounts requested through the protocol), so an unprivileged party can supply amounts crafted to overflow the sums, or a high observed `fee_per_vbyte` combined with many payments overflows the multiply.

### Likelihood Explanation
Reachable whenever `SignableTransaction::new` is invoked with externally influenced payment amounts or fee rates — no privileged position needed beyond requesting payments. Requires amounts near `u64::MAX` (larger than any realistic balance, so `NotEnoughFunds` would be the honest outcome) or a very large fee rate times a large payment count, so it's a DoS on the affected signing attempt rather than fund loss — consistent with Medium severity. The in-scope code clearly anticipates overflow elsewhere (`checked_sub` at line 228, `i64::try_from(...).unwrap()` at line 122) but missed these sites.

### Recommendation
Use checked/saturating arithmetic and return `TransactionError` variants instead of panicking:

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: 0 })?;
let mut needed_fee = fee_per_vbyte.checked_mul(vbytes)
  .ok_or(TransactionError::TooLowFee)?; // or a dedicated Overflow variant
if input_sat < payment_sat.saturating_add(needed_fee) { ... }
```

Apply the same treatment to `input_sat` (send.rs:175) and `payment_sat + fee_with_change` (send.rs:228).

### Proof of Concept
```rust
// Conceptual; assumes a valid ReceivedOutput in `inputs` and a
// change/payment script in `addr`.
let payments = vec![(addr(), u64::MAX), (addr(), u64::MAX)];
// panics inside Iterator::sum::<u64> at send.rs:187 before NotEnoughFunds
let _ = SignableTransaction::new(inputs.clone(), &payments, None, None, FEE);

// Or: overflow the fee multiplication at send.rs:206
let many = vec![(addr(), DUST); 1000];
let _ = SignableTransaction::new(inputs, &many, None, None, u64::MAX);
```

Note: the scan was time-limited; `fee_per_vbyte`'s origin is integrator-configured, so the strongest fully-attacker-controlled vector is the `payment_sat` sum overflow at send.rs:187, which panics before the existing `NotEnoughFunds` guard can fire.
