### Title
Deregistered bridge operators' votes remain counted toward the quorum, enabling unauthorized bridge value-transfer/configuration execution - ([File: contracts/service_chain/bridge/BridgeOperator.sol])

### Summary
`BridgeOperator.deregisterOperator()` removes an address from the `operators` mapping and `operatorList`, but it never clears that operator's previously cast vote from the `votes[voteType][nonce].voteCounts` tally. Because the vote-count check in `_voteCommon()` only compares the raw counter against `operatorThresholds`, a vote cast by an operator who has since been removed continues to count toward quorum, letting a stale/removed operator's vote combine with current operators to execute a value transfer or configuration change that the *current* operator set never actually approved.

### Finding Description
`BridgeOperator` implements a simple multi-operator voting scheme for bridge value transfers and configuration changes:
- `_voteCommon()` records `msg.sender`'s vote for a given `(voteType, nonce)` in `vote.voted[msg.sender]` and increments `vote.voteCounts[_voteKey]`. [1](#0-0) 
- The vote is considered ratified purely based on `vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]`, with no re-validation that all counted voters are still in the current `operators` set. [2](#0-1) 
- `deregisterOperator()` removes the address from `operators` and `operatorList`, but does **not** touch any in-flight `votes[...].voteCounts` or `votes[...].voted` entries for votes that operator already cast. [3](#0-2) 

The code even contains a self-acknowledged comment describing exactly this scenario: operator A votes, is deregistered, and operator B's vote then completes the quorum using A's stale vote, executing the request after A was removed. [4](#0-3) 

This is structurally identical to the audited `TestStake::setOwnersAndMinimumSignatures()` bug: when the voter/owner set changes mid-vote, stale votes from removed members are not purged, and the quorum check does not re-derive membership from the current set — it just counts raw tallies. The `_voteValueTransfer()` and `_voteConfiguration()` internal functions (used by the bridge's value-transfer and configuration functions) inherit this flaw directly. [5](#0-4) 

### Impact Explanation
Once quorum is reached using a stale vote from a removed operator, `_voteValueTransfer` marks the nonce as `closedValueTransferVotes[nonce] = true` and returns `true`, which the calling bridge transfer functions treat as authorization to execute the underlying token/KLAY transfer. This is a concrete "unauthorized value movement" per the validation criteria — a bridge value transfer (moving ERC20/KLAY across the bridge) can be executed with fewer *currently authorized* votes than `operatorThresholds` requires, effectively lowering the quorum below the intended security threshold. The same applies to `_voteConfiguration`, which can alter bridge configuration (e.g., operator thresholds themselves) using a stale vote.

### Likelihood Explanation
This requires the contract owner to legitimately deregister an operator while a vote from that operator is outstanding (unresolved) for some nonce — a normal operational sequence (e.g., rotating compromised or retiring operators) rather than an attack requiring privileged access beyond normal owner administration. Any operator that already voted before removal effectively retains "voting power" indefinitely until the vote for that specific nonce is separately resolved or overwritten. Because operator sets in service-chain bridges are expected to change over time (operator rotation, compromise response), this is a realistic and reachable condition, not a purely theoretical edge case, and the code comment confirms the developers were aware of but did not fully mitigate it.

### Recommendation
1. When `deregisterOperator()` removes an operator, iterate over any pending (unresolved) votes involving that operator and decrement `voteCounts[vote.voted[_operator]]`, then clear `vote.voted[_operator]`, mirroring the audit's recommendation to purge stale votes on membership change.
2. Alternatively, when checking quorum in `_voteCommon()`, recompute the count by iterating only over currently registered operators (`operatorList`) rather than trusting the persisted raw counter, ensuring quorum is always evaluated against the live operator set.
3. Consider invalidating/re-requiring re-votes for any in-flight nonce whenever the operator set or threshold changes, similar to the post-audit fix pattern of clearing `approvals`/`voted` on membership or proposal changes.

### Proof of Concept
1. Deploy the bridge with operators `{A, B, C}` and `operatorThresholds[ValueTransfer] = 2`.
2. Operator `A` calls a value-transfer function, internally invoking `_voteValueTransfer(nonce)` → `_voteCommon` records `A`'s vote; `voteCounts[voteKey] = 1` (below threshold, not yet executed). [6](#0-5) 
3. Owner calls `deregisterOperator(A)` — `A` is removed from `operators`/`operatorList`, but `votes[ValueTransfer][nonce].voteCounts[voteKey]` still equals `1`. [7](#0-6) 
4. Operator `B` (now one of only 2 remaining legitimate operators, `B` and `C`) calls the same value-transfer function with the same parameters/nonce → `_voteCommon` increments `voteCounts[voteKey]` to `2`, meeting `operatorThresholds[ValueTransfer] = 2`, and the transfer executes — despite only 1 of the 2 *current* operators (`B`) having actually approved it, using `A`'s stale, pre-removal vote to make up the quorum. [8](#0-7) 

This confirms unauthorized execution of a bridge value transfer using a vote from an operator no longer part of the authorized set.

    // _voteCommon handles common functionality for voting.
    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }

    // _voteValueTransfer votes value transfer transaction with the operator.
    function _voteValueTransfer(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;
            return true;
        }

        return false;
    }

    // _voteConfiguration votes contract configuration transaction with the operator.
    function _voteConfiguration(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(configurationNonce == _requestNonce, "nonce mismatch");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.Configuration, _requestNonce, voteKey)) {
            configurationNonce++;
            return true;
        }

        return false;
    }

    // deregisterOperator deregisters the operator.
    //
    // Note that outstanding votes by the deregistered operator are not revoked.
    // This enables a subtle counterintuitive scenario.
    //
    // Suppose there are two operators A, B and C with threshold 2.
    // 1. Operator A votes on nonce N
    // 2. Owner deregisters A
    // 3. Operator B votes on nonce N, thereby executing the request N.
    // In this case the request was executed with A's vote after A is deregistered.
    //
    // The Owner shall recognize this issue and expect that operator deregistration
    // takes some time to be fully effective.
    function deregisterOperator(address _operator)
    external
    onlyOwner
    {
        require(operators[_operator]);
        delete operators[_operator];

        for (uint i = 0; i < operatorList.length; i++) {
           if (operatorList[i] == _operator) {
               operatorList[i] = operatorList[operatorList.length-1];
               operatorList.length--;
               break;
           }
        }
        emit OperatorDeregistered(_operator);
    }
