### Title
Unbounded attacker-controlled participant count in `ThresholdKeys::read` causes amplified decoding work (denial of service) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in the `dkg` crate deserializes an attacker-supplied `n` (a `u16`) and then performs `n` scalar decodings plus `n` group-element decodings before any semantic validation of the parameters occurs. Because group-element decoding (canonical check + `from_bytes` + re-encoding comparison) is far more expensive per input byte than the bytes consumed, an unprivileged party can submit a small message (~2 MB) that forces tens of thousands of point decompression operations, amplifying CPU work per input byte — the same bug class as CVE-2023-27900 (missing limits on request part count enabling DoS).

### Finding Description
In `ThresholdKeys::read`, `t`, `n`, and `i` are read directly from the stream, with only `i` checked for being a valid `Participant` index. The interpolation arm then loops `0 .. n` reading scalars, and the verification-share loop inserts `n` group elements via `C::read_G` — all before `ThresholdParams::new(t, n, i)` is called to validate the parameters [1](#0-0) . `read_G` performs a full point decompression plus a canonical re-encoding comparison on every element [2](#0-1) . Only after the loops complete are the parameters validated via `ThresholdParams::new` [3](#0-2) .

The analogous pattern elsewhere in the crate is bounded: `Commitments::read` in PedPoP iterates only `0 .. params.t()` where `params` is already a validated `ThresholdParams`, not a raw attacker byte [4](#0-3) . `ThresholdKeys::read` lacks this bound — `n` can be up to 65535 regardless of the legitimate set size.

### Impact Explanation
Each `read_G` call costs a Ristretto/ed448 point decompression (field inversion/sqrt plus canonicality re-encode), on the order of tens of microseconds, while consuming only 32–57 bytes. A crafted input with `n = 65535` and that many valid encodings (~2–4 MB) forces ~65k decompressions — several seconds of CPU per message — plus a `Vec::with_capacity(n)` scalar allocation and a `HashMap` with 65535 entries [5](#0-4) . Reached via the in-scope `ThresholdKeys::read` API on untrusted bytes, this is a CPU/memory-amplification denial of service against any service deserializing `ThresholdKeys` from unauthenticated input.

### Likelihood Explanation
Reachability depends on an integrator feeding untrusted bytes to `ThresholdKeys::read` (a listed in-scope API). The cost is per-message and repeatable, requiring no threshold of parties, no valid shares, and no secrets — only a well-formed prefix (`C::ID`, `t`, large `n`, valid `i`, interpolation tag) followed by encodings. Impact is DoS only; no key material is exposed, and invalid encodings short-circuit early, bounding the per-message cost at the number of valid decodable points supplied.

### Recommendation
Validate `t`/`n` against protocol bounds before allocating or looping: reject `n` exceeding a sane maximum (e.g., the validator-set maximum `MAX_KEY_SHARES_PER_SET`) immediately after reading the header, and construct `ThresholdParams` before the `0 .. n` loops in `ThresholdKeys::read` [6](#0-5) . Alternatively, interleave reads with incremental validation so the work performed is proportional to a vetted parameter, not a raw wire value.

### Proof of Concept
Conceptual: serialize `C::ID.len()` || `C::ID` || `t=1` || `n=0xffff` || `i=1` || interpolation tag `0` (Constant, which reads `n` scalars) || one scalar || 65535 valid `G` encodings. Feeding this ~2–4 MB buffer to `ThresholdKeys::<C>::read` executes 65535 scalar reads and 65535 point decompressions before `ThresholdParams::new` rejects or accepts the parameters [7](#0-6) .

Caveat: I verified the read path and the absence of a pre-loop bound, but could not confirm whether all `ThresholdKeys::read` call sites in deployed services operate on authenticated data; if every caller only deserializes locally trusted key material, the practical severity drops accordingly.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
