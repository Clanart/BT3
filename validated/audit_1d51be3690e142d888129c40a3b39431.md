### Title
Attacker-controlled `n` in `ThresholdKeys::read` forces a large eager allocation from a 6-byte header — memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts a 2-byte `n` field read from untrusted bytes and immediately executes `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector — before any of the `n` scalars are actually present in the stream. A ~10-byte input therefore commits an allocation of up to `65535 × size_of::<C::F>()` (~2 MiB for 32-byte fields) plus subsequent loop overhead, an amplification of roughly five orders of magnitude. This is the same bug class as CVE-2010-5321: unprivileged input causing disproportionate memory allocation (DoS through memory consumption), mapped onto Serai's deserialization surface.

### Finding Description [1](#0-0) 

`read` parses `t, n, i` from raw `u16`s (lines 591-602), then on the `Interpolation::Constant` branch does `Vec::with_capacity(usize::from(n))` (line 608) unconditionally. `n` can be up to `u16::MAX = 65535`, so the allocator reserves `65535 * F::Repr`-sized elements (~2 MiB) on the basis of two attacker-supplied bytes, even if the stream ends immediately after. Each iteration then pushes `C::read_F(reader)?` (lines 609-611), but the capacity is committed up front.

The function only validates `n` afterwards, inside `ThresholdKeys::new` via `ThresholdParams::new(t, n, i)` (lines 625-631) — far too late; the oversized allocation already occurred. The same `n` then drives `verification_shares` insertion for `1 ..= n` (lines 620-623), a second attacker-sized structure.

This is reachable via `ThresholdKeys::read` over untrusted bytes (an explicitly in-scope input class), and the analogous pattern exists wherever untrusted counts size allocations before the backing data is verified (contrast `ethereum/src/machine.rs` `Call::read`, which deliberately chunked reads to avoid exactly this DoS — the in-scope crypto code has no equivalent guard).

### Impact Explanation
An unprivileged party repeatedly submitting a truncated `ThresholdKeys` blob (`id_len || id || t=1 || n=0xFFFF || i || interpolation=0`) forces the host to perform ~2 MiB committed heap allocations per call, paid for by a handful of input bytes. Repeated or concurrent invocations — e.g., feeding crafted bytes to any service path that deserializes `ThresholdKeys`/equivalent threshold structures from peers or transaction data — can exhaust process memory or trigger OOM-kill, denying service. The amplification (~10 bytes in → ~2 MiB committed) makes this effective even under bandwidth limits, mirroring CVE-2010-5321's repeated-mmap memory-consumption DoS. Severity: Medium — availability impact only, no secret leakage.

### Likelihood Explanation
Any code path passing unauthenticated bytes to `ThresholdKeys::read` (or generic `read_F`/`read_G`-driven container reads sized by declared counts) is reachable by unprivileged parties supplying serialized key material or DKG-related payloads. The trigger is trivial: a 6-byte header with `n = 0xFFFF` and `interpolation = 0`, then EOF. No valid proof, signature, or key knowledge is needed — the allocation precedes all validation. Exploitation requires only that deserialization be attempted, which is the normal first step of these APIs.

### Recommendation
Do not size allocations from untrusted length fields before the data is proven present. In `ThresholdKeys::read`:
- Validate `n` against plausible bounds (`ThresholdParams::new` / `MAX_PARTICIPANTS`) **before** allocating.
- Replace `Vec::with_capacity(n)` with incremental `push` (growth bounded by bytes actually consumed), or cap `with_capacity` at a small constant.
- Apply the same audit to other `read` paths that allocate from declared counts (`coordinator` `Block::read`'s `Vec::with_capacity(txs)` has the identical shape — `u32` count → up to 4 billion slots reserved from 4 bytes — though it is outside the crypto scope).

evil.extend(u16::MAX.to_le_bytes());      // n = 65535  <-- attacker field
evil.extend(1u16.to_le_bytes());          // i = 1
evil.push(0u8);                           // Interpolation::Constant
// EOF: no scalar data follows
// Result: Vec::with_capacity(65535) commits ~2 MiB before the first read_F fails.
// Looping this input in a handler exhausts memory.
