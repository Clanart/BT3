Based on my research, I found a concrete structural analog to the LooksRare "index-based winner determination lets a false completion state override the real one" bug, inside Hyperbridge's same-chain Intent Gateway partial-fill logic.

### Title
Same-chain partial-fill "final leg" escrow release drains funds reserved for other unfilled output pairs sharing the same input token - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` in `IntrinsicIntents.sol` releases escrow per output-pair index, but the escrow ledger `_orders[commitment][token]` is keyed only by `commitment` and token *address* — not by output-pair index [1](#0-0) . When the "last fill" of a given pair completes, the contract intentionally sweeps the *entire remaining balance* recorded under that token to avoid rounding dust, rather than the amount proportionally attributable to that specific output pair:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

This mirrors the LooksRare bug's root cause: a completion/"win" check (`amountFilled == totalRequired`, `activeAgents == 1`) is evaluated locally per-leg/per-agent-index, but the payout it triggers reaches into shared global state (the full remaining `_orders` balance / "first ID agent") that isn't actually exclusive to that leg's outcome.

### Finding Description
An `Order` can specify `inputs[]` and `output.assets[]` as parallel arrays of arbitrary length, matched by index [2](#0-1) . Nothing in the fill path re-keys escrow by pair index — deposits are accumulated per token address at placement time (`_orders[commitment][token] += reducedInputs[i].amount`) [3](#0-2) , and the "final fill" optimization in `_fillSameChain` reads back the *whole* balance under that token address [4](#0-3) .

If an order lists the same input token at two different indices (e.g., `inputs[0].token == inputs[1].token == USDC`, backing two different output legs — one in DAI, one in WETH), completing the DAI leg first triggers `amountFilled == totalRequired` for index 0. The code then hands that solver `_orders[commitment][USDC]` in full — which at that point still contains the USDC reserved for the *still-unfilled* WETH leg — rather than only the 50% share intended for the DAI leg. The second solver who later completes the WETH leg finds `_orders[commitment][USDC] == 0` and `_withdraw` reverts with `UnknownOrder()` [5](#0-4) , permanently losing their entitled input tokens, which were already paid out to the wrong (first) solver.

### Impact Explanation
This is a fund-loss / wrong-beneficiary-and-amount bug: escrow explicitly reserved to pay solver B for delivering output B is instead paid entirely to solver A upon completing an unrelated leg of the same order, purely because the ledger aggregates by token address instead of by order leg. This matches the required impact class ("stealing or loss of funds ... transaction manipulation") and requires no privileged role — any two ordinary, permissionless solvers filling the same public order trigger it.

### Likelihood Explanation
Likelihood depends on whether `placeOrder` rejects orders whose `inputs[]` contain duplicate token addresses at different indices. I was not able to confirm the presence or absence of such a dedup check within my remaining search budget — I read the escrow-accumulation and fill logic but did not locate an explicit "distinct input tokens" validation in `placeOrder`. This is the key open question for confirming exploitability; if no such check exists, the path is directly reachable by any user placing an order and any two competing solvers filling it, making likelihood high. If such a check exists elsewhere in `IntentsBase`/`ExtrinsicIntents` that I did not view, the issue would be neutralized for same-token-index cases but the same shared-balance design pattern still deserves review.

### Recommendation
Key escrow accounting per output-pair index (or a hash of `(commitment, index, token)`) instead of `(commitment, token)` alone, so that the "final fill sweeps remaining balance" optimization can never reach into escrow reserved for a different, still-open output leg. Alternatively, explicitly validate at `placeOrder` time that `inputs[]` contains no duplicate token addresses, and document/enforce this as an invariant so the per-token aggregation assumption in `_fillSameChain` holds.

### Proof of Concept
1. User places a same-chain `Order` with `inputs = [{USDC, 500}, {USDC, 500}]` and `output.assets = [{DAI, 1000}, {WETH, 1}]` (total escrow: 1000 USDC).
2. Solver A calls `fillOrder` providing `outputs[0] = {DAI, 1000}` (full DAI leg) and `outputs[1] = {WETH, 0}` (skip WETH leg). Per the loop logic, index 0 hits `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][USDC]` — the full 1000 USDC, not the 500 allotted to the DAI leg. Solver A receives 1000 USDC while only having delivered the DAI output; `isFullyFilled` is set false (WETH leg untouched with `solverAmount == 0`), so `_filled[commitment]` is deleted, leaving the order open.
3. Solver B later calls `fillOrder` providing `outputs[1] = {WETH, 1}` to complete the order. `_orders[commitment][USDC]` is now `0`; `_withdraw` reverts with `UnknownOrder()`, so Solver B cannot be paid for delivering WETH, and the user's WETH-leg escrow has already been drained to Solver A.     function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

        // Orders carrying output calldata must be filled completely in a single fill.
        // The attached call is only executed on a full fill, so a partial fill would
        // leave the intended side effect unexecuted while releasing proportional escrow.
        if (order.output.call.length > 0 && !isFullyFilled) revert PartialFillNotAllowed();

        WithdrawalRequest memory body = WithdrawalRequest({
            commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
        });
        _withdraw(body, false, isFullyFilled);

        if (isFullyFilled) {
            _execute(order, outputsLen);
            emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        } else {
            delete _filled[commitment];
            emit PartialFill({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }
    }
