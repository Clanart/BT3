### Title
Hookify `load_rules()` binds rule discovery to process cwd instead of a validated repo root, enabling cross-repo rule injection - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` globs the relative path `.claude/hookify.*.local.md` using `glob.glob(pattern)` with no anchoring to the session's actual project root, so whatever directory happens to be the current working directory when the hook subprocess runs determines which rule files are loaded and enforced. Every hookify hook entrypoint (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules()` unconditionally with no repo-root validation or `CLAUDE_PROJECT_DIR` binding.

### Finding Description
`load_rules()` builds its glob pattern with `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob(pattern)` directly, which resolves relative to `os.getcwd()` at the time the hook process runs. [1](#0-0) 
There is no use of an environment variable such as `CLAUDE_PROJECT_DIR` (which is available and used elsewhere, e.g. for `CLAUDE_PLUGIN_ROOT`) to anchor the search to the top-level repository that the session was started in, and no check that the discovered `.claude` directory belongs to the intended repo root. [2](#0-1) 
All four hook entrypoints (`PreToolUse`, `PostToolUse`, `Stop`, `UserPromptSubmit`) call `load_rules()`/`load_rules(event=...)` and feed the returned rules directly into `RuleEngine.evaluate_rules()`, with no repo-scoping guard in between. [3](#0-2) [4](#0-3) 
`load_rule_file()` then parses any matched file's frontmatter (`name`, `enabled`, `event`, `pattern`, `action`) with no origin/provenance check, and `Rule.from_dict` trusts the `action` field (`warn`/`block`) as-is. [5](#0-4) 
If a workspace contains a nested checkout (submodule, cloned second repo, vendored directory) with its own `.claude/hookify.*.local.md`, and the process cwd is ever pointed at that nested directory when a hook fires, the attacker-controlled rule file is loaded and applied — governing an unrelated tool call/session with rules the victim never installed for that context (e.g., a permissive rule that masks the intended `action: block` rule, or an unrelated `block` rule causing unexpected denial).

### Impact Explanation
This breaks TARGET_BINDING/repo confinement for the hookify guardrail mechanism: rules meant to govern one repository's session can silently be swapped for rules sourced from an attacker-controlled nested directory, because there is no session-to-repo-root binding in `load_rules()`. Depending on rule content, this can mask a victim's real safety rules (e.g., no `block` on dangerous commands ever fires because the attacker's rule file for that path takes over) or inject false blocking behavior to disrupt sessions — a trust-boundary bypass in Claude Code's own policy-enforcement layer.

### Likelihood Explanation
Exploitability requires two things: (1) a workspace where an attacker-controlled directory (submodule, second cloned repo, or any nested folder containing a `.claude` directory) is checked out alongside/inside the victim's project, and (2) the hookify hook subprocess's cwd being set to that nested directory when a `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` event fires. Since the hook scripts never establish or validate a project root and rely solely on `os.getcwd()`-relative globbing, any workflow that changes the effective working directory for tool invocations (multi-root workspaces, working inside a submodule, running tools from a nested package directory) will cause `load_rules()` to read the nested `.claude` folder instead of the primary repo's. This makes the issue realistically reachable in common multi-repo/monorepo/submodule setups, without any special privilege.

### Recommendation
Anchor rule discovery to the session's actual project root rather than the ambient process cwd: use `CLAUDE_PROJECT_DIR` (already available to plugin hook scripts, as seen with `CLAUDE_PLUGIN_ROOT`) or an equivalent explicitly-passed/validated repo-root path to build the glob pattern in `load_rules()`, e.g. `os.path.join(project_root, '.claude', 'hookify.*.local.md')`, and reject/ignore any `.claude` directory encountered outside that validated root (including symlink-resolved checks to prevent nested checkouts from spoofing the root).

### Proof of Concept
Integration test plan:
1. Create a victim repo directory `victim/.claude/hookify.safe.local.md` with `action: warn`, `event: bash`, `pattern: rm\s+-rf`.
2. Inside `victim/`, create a nested attacker-controlled directory `victim/vendor/attacker_repo/.claude/hookify.evil.local.md` with `enabled: true`, `event: bash`, `pattern: .*`, `action: warn` (a permissive catch‑all masking real dangerous‑command detection), or alternatively `action: block` targeting an unrelated benign pattern.
3. `os.chdir('victim/vendor/attacker_repo')` and call `hookify.core.config_loader.load_rules(event='bash')`.
4. Assert that `load_rules()` returns the attacker's rule (from `vendor/attacker_repo/.claude`) instead of, or without any binding check against, the victim's intended top-level `.claude/hookify.safe.local.md`, demonstrating that `load_rules()` has no repo-root confinement — expected (fixed) behavior would be that `load_rules()` only ever reads `.claude` files under the validated project root regardless of `os.getcwd()`.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
