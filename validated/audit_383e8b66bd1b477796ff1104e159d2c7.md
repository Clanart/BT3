### Title
Partial-commit staging applies stale line-selection indices to a freshly re-computed diff, silently staging/committing unintended lines - ([File: app/src/lib/git/apply.ts])

### Summary
The report's core defect is a mismatch between two values describing the same "amount": a stale, already-signed quantity (`SingleQuote.makerAmount`) is trusted and used instead of the current authoritative one, and nothing checks that they agree before the trade settles, so the taker gets less than they expect. The Desktop analog is a mismatch between two representations of the same "line selection": the UI records which diff lines the user selected as *absolute line indices* against the diff that was on screen, but when the commit is actually built, `applyPatchToIndex` fetches a brand-new diff of the file and blindly re-applies those old indices to it, with no check that the two diffs still agree.

### Finding Description
When a user stages a subset of changes in the "Changes" view, Desktop stores the choice in a `DiffSelection` keyed by absolute line index inside the *diff that was rendered at that time* [1](#0-0) . The code even acknowledges that a diff can change dramatically between renders and that stale selections may point at lines that "no longer exist," but only reconciles this for the *rendering* path via `withSelectableLines` [2](#0-1) .

The actual commit path does not go through this reconciliation. `applyPatchToIndex` re-fetches the diff independently right before building the patch: [3](#0-2) 
It then calls `formatPatch(file, diff)`, which walks the **new** `diff.hunks` and decides what to include per line using `file.selection.isSelected(absoluteIndex)` [4](#0-3) , where `absoluteIndex` is `hunk.unifiedDiffStart + lineIndex` computed from the freshly parsed diff, not the diff the selection was originally computed against.

If the working-directory file's diff shape changes between the moment the user made their line selection and the moment `createCommit`/`applyPatchToIndex` runs (e.g. a checkout/smudge/clean filter, a background process, a symlink target, or any tool that rewrites the file — all of which are attacker-influenceable in a cloned/fetched malicious repository via `.gitattributes` filters or hooks), the hunk boundaries and `unifiedDiffStart` offsets shift. The same absolute index that used to mean "line 5 of hunk 1, an added line the user reviewed and wanted to stage" can now resolve to a completely different line in a different hunk of the new diff. `formatPatch` has no defense against this: it never checks that `diff` corresponds to the diff the selection was derived from (no hash/timestamp/content comparison), and `applyPatchToIndex`'s comment about renames "possible that someone staged a rename and then recreated the original file" shows awareness of races but no mitigation for this specific mismatch [5](#0-4) . This produces a syntactically valid patch that `git apply --cached` will happily accept, since it's internally self-consistent (headers are recomputed from the lines actually collected) — the corruption is semantic, not structural, exactly like the "signed quote had less than the real amount but format was valid" root cause in the report.

### Impact Explanation
The result is that the user believes they reviewed and selected certain lines to commit, but the actual committed content can differ — potentially staging changes the user explicitly did not want to commit (or omitting ones they did), all without any error or warning. This is a silent corruption of what the user commits, which is one of the explicitly valid impact categories: "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires the file's diff to change between the time a partial selection is made and the time the commit executes. In a Desktop workflow this window is real (auto-save tools, editors, LFS smudge filters, or a repository-provided `.gitattributes` clean/smudge filter or `core.fsmonitor`/hook script from a maliciously crafted cloned repo can be timed to run in that window), and Desktop's own comments show the team is aware diffs can go stale between actions. However, reliably winning the race to alter the diff at the precise moment between selection and staging is nontrivial and not fully demonstrated end-to-end from local code alone (no test exercises this exact race), so this should be treated as a plausible but unverified-in-full analog rather than a confirmed exploit chain.

### Recommendation
Before building the patch in `applyPatchToIndex`/`formatPatch`, verify that the freshly fetched `diff` is unchanged (e.g., compare a hash of `diff.contents`/hunk headers, or the diff object reference/version used to create `file.selection`) versus the diff the selection was computed against; if they differ, refuse to stage/commit and force the UI to re-diff and re-prompt the user for selection instead of silently applying possibly-mismatched indices.

### Proof of Concept
Not independently reproduced; based on static analysis of the code path `app-store.ts:_selectWorkingDirectoryFiles/updateChangesWorkingDirectoryDiff` → `commit.ts:createCommit` → `apply.ts:applyPatchToIndex` → `patch-formatter.ts:formatPatch`, showing the fresh-diff/stale-selection mismatch with no reconciliation check at commit time. A full working exploit would require timing a file-content-changing operation (filter/hook/background writer) between selection and commit and is not confirmed here.
