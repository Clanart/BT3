## Title
`discardChanges` can move an entire submodule's working directory (including its own `.git`) to the OS trash because its submodule-exclusion check depends on a `git describe`-fragile regex that diverges from the porcelain-based submodule detection already used elsewhere — (File: `app/src/lib/stores/git-store.ts`)

## Summary
`GitStore.discardChanges` decides whether a changed path is a submodule (and must therefore be excluded from `shell.moveItemToTrash`) by calling `listSubmodules()` and checking `submodules.some(s => s.path === file.path)`, instead of trusting the `submoduleStatus` field that was already correctly derived from `git status --porcelain=2`'s `<sub>` field. `listSubmodules()` parses `git submodule status --` output with `statusRe = /^.([^ ]+) (.+) \((.+?)\)$/gm`, which *requires* a trailing `(describe)` group. `git submodule status` omits that parenthesized describe suffix whenever `git describe` cannot resolve a tag for the submodule's checked-out commit (a very common situation — most submodule commits are not exactly on a tag). For such submodules the status line has no parentheses, `statusRe` produces zero matches for that line, and the submodule silently disappears from the `submodules` array — while the same submodule is still correctly reported by `git status` (and hence appears in the Changes list) as a normal, non-Deleted entry (e.g. `AppFileStatusKind.Modified`).

## Finding Description [1](#0-0) 

`listSubmodules` builds its result purely from regex-matching `git submodule status --` lines:
```
const statusRe = /^.([^ ]+) (.+) \((.+?)\)$/gm
for (const [, sha, path, describe] of stdout.matchAll(statusRe)) {
  submodules.push(new SubmoduleEntry(sha, path, describe))
}
```
Per `git-submodule` semantics, each status line is `<prefix><sha> <path>` optionally followed by ` (<describe>)` *only if `git describe` succeeds* for that commit. When it fails (no reachable tag — the normal case for most submodule commits that don't happen to sit exactly on a tag), the line is emitted **without** the parenthesized part, e.g.:
```
 1eaabe34fc6f486367a176207420378f587d3b48 foo/submodule
```
`statusRe` cannot match this line at all (the trailing `\(...\)$` is mandatory), so `matchAll` yields nothing for it, and that submodule is silently dropped from the returned array — with no error, warning, or fallback.

Meanwhile, `discardChanges` in `git-store.ts` uses only this list to decide exclusion: [2](#0-1)

This is inconsistent with how `getStatus` already, independently and reliably, marks submodule entries: `mapStatus`/`mapSubmoduleStatus` set `submoduleStatus` on `WorkingDirectoryFileChange` directly from the porcelain `<sub>` field (`S[C.][M.][U.]`), regardless of whether `git describe` succeeds: [3](#0-2) 

Because `discardChanges` ignores that already-correct `submoduleStatus` and instead re-derives the exclusion set through the fragile `git describe`-dependent regex, a submodule whose checked-out commit is not describable will be treated exactly like a normal changed file and passed to `this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))`, which moves the **whole submodule directory** — including its own `.git` (history, refs, any local commits/stashes) — to the OS trash, rather than performing the intended non-destructive `resetSubmodulePaths` / `checkoutIndex` flow used for recognized submodules: [4](#0-3) 

## Impact Explanation
An attacker who controls a cloned/fetched repository can register a submodule pointing at a commit with no reachable tag (the default state for essentially any submodule commit that isn't exactly a tagged release). When the user opens the repository in Desktop, makes/observes a change to that submodule (or it's naturally shown modified, e.g., `commitChanged`/`modifiedChanges`/`untrackedChanges`), and clicks "Discard Changes" on that submodule row (a completely ordinary, expected use of the feature), Desktop will move the entire submodule working directory — including its independent `.git` object database — to the trash instead of performing a safe, index-based checkout/reset. This corrupts the local working copy's submodule linkage and can destroy unpushed submodule-local commits/branches/stashes that existed only in that nested `.git`. It also breaks the documented invariant (see `docs/technical/discard-changes.md`) that submodules are excluded from the trash-move path.

## Likelihood Explanation
Moderate-to-high: the missing-describe condition is not an exotic edge case — most submodule commits are not exactly on a git tag, so `git submodule status` frequently omits the `(describe)` suffix in real-world repositories. No special crafting beyond "have a submodule pointing at a non-tagged commit" (or one on a branch far from any tag) is required, which is the norm rather than the exception. The only user action needed is the ordinary "Discard Changes" click on a submodule entry that is legitimately shown as changed.

## Recommendation
Stop re-deriving submodule membership via `listSubmodules()`/`statusRe` inside `discardChanges`. Use the already-computed `file.status.submoduleStatus` (set from the porcelain `<sub>` field in `status-parser.ts`) as the source of truth for submodule exclusion, or at minimum make `statusRe` tolerant of the no-describe line format (e.g. `/^.([^ ]+) (\S+)(?: \((.+?)\))?$/gm`) so a submodule is never silently dropped from `listSubmodules`'s output.

## Proof of Concept
1. Create/clone a repository with a submodule whose checked-out commit has no reachable tag (e.g. an arbitrary commit on a feature branch), so `git submodule status` in that repo outputs a line without a trailing `(describe)`, e.g.:
   ```
   $ git -C outer-repo submodule status
    1eaabe34fc6f486367a176207420378f587d3b48 foo/submodule
   ```
2. Confirm `listSubmodules()` returns `[]` (or omits `foo/submodule`) for this repo because `statusRe` doesn't match the line — while `getStatus()` still reports `foo/submodule` as a changed/modified entry with `submoduleStatus` set.
3. In Desktop, make a change inside `foo/submodule` (e.g. modify a tracked file) so it shows in the Changes list with `AppFileStatusKind.Modified`.
4. Select "Discard Changes" on `foo/submodule`; observe that `GitStore.discardChanges` calls `this.shell.moveItemToTrash(Path.resolve(repoPath, 'foo/submodule'))`, moving the entire submodule directory (with its `.git`) to the OS trash, instead of resetting/checking out its content via `resetSubmodulePaths`.
