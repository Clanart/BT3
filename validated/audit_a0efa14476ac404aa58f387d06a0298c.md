### Title
PedPoP commitment proof does not bind the recipient encryption key, allowing share recovery - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`EncryptionKeyMessage` combines a `Commitments` object whose Schnorr proof authenticates the polynomial commitments with an `enc_key` that is appended but not included in the proof challenge. An unprivileged relay can preserve the valid commitment proof while replacing `enc_key` with a public key it controls. Subsequent encrypted secret shares are then encrypted to the substituted key, allowing the attacker to recover the victim participant’s DKG shares.

### Finding Description
`EncryptionKeyMessage::read` parses the commitment message and then independently reads `enc_key`; the latter has no proof-of-possession and is not cryptographically bound to the former. [1](#0-0) 

The PedPoP proof challenge covers only the context, sender index, Schnorr nonce, and serialized polynomial commitments. [2](#0-1)  The sender signs this challenge over `coefficients[0]`, but no encryption-key field is present in `cached_msg` or the challenge. [3](#0-2) 

During round-one verification, the participant-associated `EncryptionKeyMessage` is passed to `self.encryption.register`, which stores `msg.enc_key`; only the commitment Schnorr proof is batch-verified afterward. [4](#0-3)  `Decryption::register` inserts the supplied `enc_key` without checking that it was signed or otherwise authorized with the commitments. [5](#0-4) 

When shares are generated, `encrypt` derives the ECDH point from the registered `enc_key`, applies the ChaCha20 keystream to the share, and serializes that ciphertext inside `EncryptedMessage`. [6](#0-5)  `generate_secret_shares` uses `self.encryption.encrypt(rng, l, share_bytes)`, so the unauthenticated registered key directly controls who can decrypt the share intended for participant `l`. [7](#0-6) 

### Impact Explanation
An attacker who substitutes a victim participant’s `enc_key` can decrypt every PedPoP share sent to that victim’s participant index. Because each dealer independently encrypts the victim’s polynomial evaluation to the substituted key, the attacker obtains all components needed to reconstruct the victim’s resulting threshold secret share.

This is key-share recovery, not merely denial of service. Recovery of a participant’s `ThresholdKeys` secret share reduces the threshold security of the resulting multisig and can enable signature forgery when combined with other compromised shares or a sufficiently low threshold.

### Likelihood Explanation
The vulnerable field is supplied directly by network data parsed through `EncryptionKeyMessage::read` and `Commitments::read`. The attacker does not need to break Schnorr, solve a discrete logarithm, or possess an existing key share; they only need to relay or inject a syntactically valid message in which the authenticated `Commitments` are retained and the unauthenticated `enc_key` is replaced.

The library documents an assumption that callers provide authenticated channels. If the deployed transport authenticates the complete serialized `EncryptionKeyMessage`, that layer may prevent this substitution. The cryptographic message itself nevertheless fails to bind the security-critical key to the participant’s proof, so any channel that authenticates only the inner commitment proof or permits a relay to repackage the commitment is exploitable.

### Recommendation
Bind `enc_key` to the PedPoP commitment proof. The cleanest fix is to include `enc_key` in `cached_msg`/the challenge before signing the commitments, so `challenge()` commits to `(context, participant, nonce, commitments, enc_key)` rather than only the polynomial commitments.

A proof-of-possession for `enc_key` should also be required so an attacker cannot claim a public key whose discrete logarithm is unknown. Verification should reject a message unless both the commitment proof and encryption-key proof are valid under the participant index and context.

### Proof of Concept
1. Victim participant `l` produces a valid `EncryptionKeyMessage { msg: Commitments { .., sig }, enc_key }`.
2. Attacker constructs `enc_key' = k_attacker * G` for a scalar `k_attacker` they know.
3. Attacker returns `EncryptionKeyMessage { msg, enc_key: enc_key' }` for participant `l` to another participant’s `generate_secret_shares`.
4. `Decryption::register` stores `enc_key'`, while the original `sig` remains valid because `enc_key'` was never included in the PedPoP challenge.
5. Every dealer calls `encrypt` for `l`, producing shares encrypted under `ECDH(k_attacker, dealer_ephemeral_key)` rather than the victim’s key.
6. The attacker decrypts each `EncryptedMessage` using `k_attacker` and the public per-message key, recovering every share evaluation addressed to participant `l` and therefore recovering `l`’s final threshold secret share.
