## Analysis

The CVE-2017-10912 bug class is "privilege/ownership validation mishandled during a transfer operation, allowing an unprivileged actor to seize control of a resource." An analogous flaw exists in sei-chain's CW721↔ERC721 pointer bridge: the transfer-authorization check is completely missing at both layers that mediate NFT ownership transfers.

### Title
Missing sender-authorization check in CW721 pointer/wrapper `transfer_nft` allows any account to steal NFTs it does not own or control - (File: `contracts/src/CW721ERC721Pointer.sol`, `example/cosmwasm/cw721/src/contract.rs`)

### Summary
`CW721ERC721Pointer.transferFrom` in the Solidity pointer contract only checks that `from == ownerOf(tokenId)`; it never checks that `msg.sender` is `from`, is approved for the token, or is an approved operator, unlike the sibling `CW1155ERC1155Pointer.safeTransferFrom`, which explicitly enforces `msg.sender == from || isApprovedForAll(from, msg.sender)`. The corresponding CosmWasm-side `transfer_nft` helper used by the reference CW721 contract has the identical gap: it queries the real owner of the token and unconditionally builds a transfer payload moving that owner's token to the caller-supplied recipient, without ever validating that `info.sender` (the caller) is the owner or an approved spender/operator.

### Finding Description
`CW721ERC721Pointer.sol` `transferFrom`: [1](#0-0) 
only requires `from == ownerOf(tokenId)` — a condition that is trivially true for *any* real token id and is completely independent of who is calling. Compare this to the analogous `safeTransferFrom` in the ERC1155 pointer, which correctly gates the call: [2](#0-1) 

The gap is mirrored on the CosmWasm side. The shared `transfer_nft` helper used by `execute_transfer_nft`/`execute_send_nft` looks up the actual on-chain owner of the token and builds a delegatecall payload transferring that owner's token to an attacker-chosen recipient — using only `info.sender` to perform the *query*, never to authorize the action: [3](#0-2) [4](#0-3) 

`execute_approve`/`execute_approve_all` have the same defect — they build approval-changing payloads without ever checking that `info.sender` is the owner of the token or collection: [5](#0-4) 

The wasmd `execute` precompile path that dispatches these CW messages resolves the Sei-address sender from the actual EVM `caller` (not the pointer contract), so `info.sender` inside the CW721 contract genuinely reflects the real, unprivileged calling account: [6](#0-5) 

Because neither the Solidity pointer entrypoint nor the CosmWasm `transfer_nft`/`execute_approve` logic verifies that the caller is the owner or has been granted approval, an attacker can invoke `pointer.transferFrom(victim, attacker, tokenId)` for any token id they do not own, and the pointer will faithfully execute a `transfer_nft` (or `approve`) CosmWasm message that moves the real owner's NFT — this is precisely the "page/ownership transfer mishandled, allowing an unprivileged party to seize control of a resource" pattern in CVE-2017-10912, applied to the CW↔EVM NFT pointer bridge.

### Impact Explanation
Any account can call the ERC721 pointer's `transferFrom` (or the CW721 contract's `transfer_nft`/`approve` execute messages directly) to steal any NFT tracked through this pointer pattern, with no requirement for the real owner's signature, approval, or consent. This is unauthorized transfer of an asset via a Cosmos/EVM pointer — direct fund/asset loss for every holder of tokens exposed through a CW721 pointer or through a CW721 contract built on this reference pattern, satisfying the "unauthorized transfer via precompile or pointer" impact criterion.

### Likelihood Explanation
The exploit requires only a single ordinary EVM transaction from any account (no approval, no special privilege, no governance/validator/node involvement) targeting a deployed CW721 pointer contract for any NFT collection, or a single `MsgExecuteContract` against a CW721 contract instance using this reference implementation. Both the Solidity and Rust code are directly reachable by any transaction sender/contract deployer, making this trivially and reliably exploitable.

### Recommendation
Add explicit authorization checks:
- In `CW721ERC721Pointer.sol` `transferFrom`, require `msg.sender == from || getApproved(tokenId) == msg.sender || isApprovedForAll(from, msg.sender)` before calling `_execute`, mirroring the pattern already used in `CW1155ERC1155Pointer.safeTransferFrom`.
- In the CosmWasm `transfer_nft` helper and `execute_approve`/`execute_approve_all`, verify that `info.sender` equals the queried owner, or is an approved spender/operator for the token/collection, before constructing the `EvmMsg::DelegateCallEvm` transfer/approve payload.

### Proof of Concept
1. Victim owns `tokenId=5` in a CW721 collection exposed through `CW721ERC721Pointer`.
2. Attacker (unrelated account, no approval) calls `pointer.transferFrom(victim, attacker, 5)`.
3. `transferFrom` only checks `from == ownerOf(tokenId)` — true because `from=victim` genuinely owns token 5 — and proceeds to `_execute` a `transfer_nft` CosmWasm message with `recipient=attacker`. [1](#0-0) 
4. The CW721 contract's `execute_transfer_nft` → `transfer_nft` helper queries the real owner (`victim`) and unconditionally builds a transfer payload from `victim` to `attacker`, without checking that `info.sender` (attacker) was ever authorized. [3](#0-2) 
5. Token 5 is now owned by `attacker`, with no prior consent, approval, or signature from `victim`.

```rust
pub fn execute_approve(
    deps: DepsMut<EvmQueryWrapper>,
    info: MessageInfo,
    spender: String,
    token_id: String,
    approved: bool,
) -> Result<Response<EvmMsg>, ContractError> {
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let mut payload_spender = spender.clone();
    let mut action = "approve";
    if !approved {
        payload_spender = "".to_string();
        action = "revoke";
    }
    let payload = querier.erc721_approve_payload(payload_spender, token_id.clone())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("action", action)
        .add_attribute("token_id", token_id)
        .add_attribute("sender", info.sender)
        .add_attribute("spender", spender.clone())
        .add_message(msg);

    Ok(res)
}

pub fn execute_approve_all(
    deps: DepsMut<EvmQueryWrapper>,
    info: MessageInfo,
    to: String,
    approved: bool,
) -> Result<Response<EvmMsg>, ContractError> {
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc721_set_approval_all_payload(to.clone(), approved)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let mut action = "approve_all";
    if !approved {
        action = "revoke_all";
    }
    let res = Response::new()
        .add_attribute("action", action)
        .add_attribute("operator", to)
        .add_attribute("sender", info.sender)
        .add_attribute("approved", format!("{}", approved))
        .add_message(msg);

    Ok(res)
}
```

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
```
