### Title
Trusting an unsafe repository directory permanently and globally disables Git's owner-mismatch protection with no way to revoke it - (File: `app/src/lib/git/config.ts`)

### Summary
When GitHub Desktop encounters a repository whose directory is owned by a different user than the current process (Git's "dubious ownership" / unsafe-repository protection), the user is offered a "Trust Repository" action. That action calls `addSafeDirectory()`, which permanently appends the path to the **global** `safe.directory` Git config entry via `addGlobalConfigValueIfMissing('safe.directory', path)`. There is no corresponding function anywhere in the codebase to remove a path from `safe.directory` once added, mirroring the reported `OverlayV1Mothership` bug class where a state-changing "enable" action has no matching "disable" counterpart, permanently and irreversibly altering a security-relevant flag.

### Finding Description
Git's unsafe-directory check exists specifically to stop Git from parsing repository-local config and executing hooks/aliases in a directory that could belong to, or have been tampered with by, another party (e.g. a different local user, a re-created directory, or content dropped by another process). GitHub Desktop surfaces this check in `getRepositoryType()` results (`kind: 'unsafe'`) and offers users a one-click bypass in two UI locations: [1](#0-0) [2](#0-1) 

Both call into the shared helper: [3](#0-2) 

which appends to the entry via `addGlobalConfigValueIfMissing`, and there is no `removeSafeDirectory`/`unsetSafeDirectory` equivalent anywhere in the repository (confirmed by search). Once a path is trusted, `safe.directory=<path>` is written to the user's global `~/.gitconfig` and stays there forever — for the lifetime of the machine, independent of GitHub Desktop's own `Repository` records, independent of whether the repo is later removed from Desktop, and independent of what content later occupies that exact path.

This breaks the invariant Git's own protection relies on: "a path is only trusted while its ownership/content has been vetted by the user." Because Desktop's trust action is a one-way, global, path-keyed toggle with no expiry and no revoke path, any later attacker-controlled content that ends up at that same path (e.g., a network share directory being reused, a symlink pointed at a previously-trusted absolute path, or the same path being recreated after the original repository is deleted, all of which are directly reachable without any git/GitHub credentials and only require the attacker to write to a filesystem path the user once trusted) will be silently treated as safe and have its hooks/config honored by Git the next time Desktop or the user's own `git` CLI operates there.

### Impact Explanation
Git deliberately refuses to honor repository-local config (including `core.hooksPath`, `core.fsmonitor`, and other settings that lead to command execution) for unsafe/dubious-ownership repositories. Silently, permanently disabling this protection for a specific path — with no code path to undo it — means once a user has ever clicked "Trust Repository" for that path, any future content placed there by an attacker (who does not need git or GitHub credentials, only write access to that filesystem location, e.g., through a shared network mount or by refilling a deleted repository path) automatically regains the ability to have Git execute its hooks/config, which can lead to arbitrary code execution on the user's machine. This matches the impact class of "attacker controls a cloned/fetched repository... and the result is code execution" from the accepted scope.

### Likelihood Explanation
The trust action is a single click that many users will not think twice about, since the warning language ("owned by another user on your machine") reads like a benign environment quirk (e.g., WSL/network drives) rather than a persistent, irrevocable grant. The persistence is not obvious from the UI at all — nothing in Desktop indicates the exception is permanent, global to the OS user account, and has no "undo." This makes the broken invariant easy to trigger unintentionally and impossible to remediate through the app itself.

### Recommendation
Provide a way to revoke trust: implement a `removeSafeDirectory(path)` counterpart (e.g. `git config --global --unset-all safe.directory <path>`) and expose it in Desktop's settings (e.g. a list of trusted directories with a "Remove" action), similar to how `enableCollateral`/`disableCollateral` should be mirrored operations in the original report. At minimum, warn users explicitly that trusting a directory is a permanent, global exception that survives repository removal, and consider scoping trust decisions more narrowly (e.g., re-validating directory ownership/hash before reusing a previously-trusted path) rather than trusting the path unconditionally forever.

### Proof of Concept
1. Add an existing repository whose directory ownership differs from the current OS user (e.g., a network share, or a directory chowned to another account), triggering the `'unsafe'` `RepositoryType` in `add-existing-repository.tsx`.
2. Click "add an exception for this directory" → `onTrustDirectory` → `addSafeDirectory(repositoryUnsafePath)` → `safe.directory=<path>` is permanently appended to the user's global `~/.gitconfig`.
3. Remove the repository from GitHub Desktop (or let the directory be deleted/replaced).
4. An attacker with only filesystem write access (no git/GitHub credentials) recreates a Git repository at the exact same path, with malicious `core.hooksPath`/hooks configured.
5. The next time Desktop or `git` is invoked against that path, Git — and Desktop — treat it as fully trusted because of the stale `safe.directory` entry, honoring the attacker's hooks/config with no warning, no re-prompt, and no way for the user to have revoked the earlier trust grant. [3](#0-2)

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
