### Title
Unrecovered panic in parallel `debug_trace*` worker goroutines crashes the entire RPC node process - (File: evmrpc/block_trace_profiled.go)

### Summary
`profiledTraceBlockParallel` spawns per-tx tracer worker goroutines with no panic recovery of their own. A panic inside the worker loop but *outside* the inner `profiledTraceTx` call (which does have its own `defer recover()`) is never caught, propagates up the goroutine stack, and — because Go does not let a caller catch a panic from another goroutine — crashes the entire `seid`/EVM RPC process, analogous to the NULL-pointer crash of the whole Apache worker process in CVE-2017-7659.

### Finding Description
`profiledTraceBlockParallel` fans work out across `threads` goroutines that pull `*profiledTxTraceTask` items from a channel and call helper functions before ever entering `profiledTraceTx`: [1](#0-0) 

Only `profiledTraceTx` itself installs a `defer recover()` that converts panics into a synthetic error trace: [2](#0-1) 

But the surrounding worker goroutine body executes `core.TransactionToMessage(tx, signer, block.BaseFee())` and `api.backend.GetBlockContext(ctx, block, task.statedb, api.backend)` before calling `profiledTraceTx`, and neither of those calls, nor the goroutine itself, is wrapped in any `recover()`: [3](#0-2) 

If either call panics (e.g. a nil pointer dereference triggered by unusual/edge-case block or state data reachable at a caller-selected historical block height/hash), the panic is unrecovered in that goroutine. In Go, an unrecovered panic in any goroutine — even one spawned internally by request-handling code — terminates the whole process; it is not confined to the HTTP request goroutine and is not caught by the outer `recoverAndLogHandler`/`classifyRPCMetricError` machinery that guards the top-level JSON-RPC dispatch path (`evmrpc/metrics.go`, `sei-tendermint/rpc/jsonrpc/server/http_server.go`). This is a structural gap compared to the otherwise-consistent panic-recovery discipline elsewhere in `evmrpc/` (worker pool, subscription goroutines, WS `readRoutine`, etc., all shown to wrap goroutines with `recoverAndLog()`/`recover()`), which strongly suggests this parallel-tracing goroutine is a genuine oversight rather than an intentional unguarded path.

This is reached via the public `debug_traceBlockByNumber` / `debug_traceBlockByHash` JSON-RPC endpoints when `shouldUseProfiledBlockTrace` selects the profiled path (default tracer, i.e. no `config.Tracer` set) and the block contains enough transactions that `threads > 1`: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unhandled panic in a spawned goroutine crashes the entire Go process, taking down the EVM JSON-RPC server (and, since it runs in the same process as `seid`, potentially the validator/full node itself). This matches the "crash of default-configuration RPC nodes" acceptance criterion: any node exposing `debug_traceBlockByNumber`/`debug_traceBlockByHash` (this is the same node process serving consensus/validator duties in sei-chain's architecture) would go down, causing denial of service and potential block-production delay/halt if triggered against validator RPC endpoints.

### Likelihood Explanation
I could not fully verify, within available search budget, a concrete input that reliably triggers a nil-pointer/panic inside `core.TransactionToMessage` or `api.backend.GetBlockContext` for a *specific* historical block — these functions operate on already-committed, previously-validated transactions and state, which limits arbitrary attacker control over their inputs. The likelihood therefore hinges on whether some edge-case block/tx/state combination (e.g., synthetic transactions, unusual receipt data, or a block at an upgrade boundary) can produce a nil field consumed unguarded by these calls. This is a plausible but not concretely demonstrated trigger — flagging this as the main uncertainty in this analog.

### Recommendation
Wrap each `profiledTraceBlockParallel` worker goroutine body in its own `defer recover()` (mirroring the pattern already used in `evmrpc/worker_pool.go` and `evmrpc/subscribe.go`'s `recoverAndLog()`), converting any panic into a per-task trace error (e.g., via `profiledErrorTrace`) instead of letting it escape the goroutine, and ensure `pend.Done()` still runs via `defer` so `pend.Wait()` cannot deadlock after a recovered panic.

### Proof of Concept
Not concretely demonstrated. Conceptually: submit `debug_traceBlockByNumber`/`debug_traceBlockByHash` for a historical block with `tracedCount > 1` (so `profiledTraceBlockParallel` is used) and default tracer config, targeting a block/tx/state combination that causes `core.TransactionToMessage` or `Backend.GetBlockContext` to dereference a nil value inside the untracked worker goroutine — crashing the RPC process. Confirming an exact reproducible trigger requires deeper review of `Backend.GetBlockContext` and `core.TransactionToMessage` for nil-handling gaps, which was not completed within the available investigation scope.
