### Title
Webhook shop domain spoofing via unauthenticated `X-Shopify-Shop-Domain` header - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The C4 report describes a mismatch between what is *checked* (the approved allowance) and what is *actually consumed* (allowance + fee) in `transferFrom`. The `WebhookVerification` concern in `shopify_app` has the same class of bug: the HMAC check only covers the raw request body, but the `shop_domain` value that consumers are told to trust for attributing the webhook to a shop is read from an **unsigned** header and is never included in the HMAC computation.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes the HMAC only over `request.raw_post`: [1](#0-0) 

The concern separately exposes a `shop_domain` helper that simply reads the `X-Shopify-Shop-Domain` request header, with no cryptographic binding to the HMAC-verified body: [2](#0-1) 

`PayloadVerification#hmac_valid?` confirms the digest is calculated only over the `data` argument passed in (the raw body), never over any headers: [3](#0-2) 

The gem's own documentation instructs developers building a custom webhook controller to pass this unauthenticated `shop_domain` value directly into background jobs that act on behalf of "the shop": [4](#0-3) 

Because the app's webhook secret (`ShopifyApp.configuration.secret`) is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any actor who installs the app on their own shop will legitimately receive Shopify-signed webhook deliveries with a **valid HMAC** for their own shop's body. That attacker can then replay the exact same `body`/`HMAC` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g. a victim shop's domain). `hmac_valid?` will still return `true` because the header is not part of the signed payload, and the resulting job will be enqueued with the attacker-controlled `shop_domain`, exactly mirroring how the fee in the ERC-20 report is deducted based on unchecked additional data outside of what was actually verified/approved.

### Impact Explanation
Any consumer of `WebhookVerification#shop_domain` (as instructed by the gem's own documentation for custom controllers) will process attacker-supplied payloads while believing they originate from an arbitrary shop of the attacker's choosing. This enables cross-shop data confusion/injection: an attacker-controlled webhook body can be attributed to a victim shop, potentially triggering shop-scoped side effects (e.g. job processing, data writes, cache/record updates keyed by `shop_domain`) for a shop the attacker does not own or have any relationship with. This satisfies the "cross-shop access" / "accepted forged signed request" bar since the HMAC check passes for a payload/header combination that was never actually authorized as a unit by Shopify.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to (1) install the target app on their own shop to obtain at least one genuinely signed webhook body/HMAC pair, and (2) know/guess a victim `myshopify.com` domain (which is public/discoverable). No merchant-specific secret or privileged access is required beyond being any app installer, which fits the "unrelated-merchant" reachability bar. It also depends on the app developer following the gem's documented pattern of trusting `shop_domain` for authorization/attribution rather than deriving the shop strictly from signed body content.

### Recommendation
Bind the shop domain to the HMAC-verified payload rather than trusting the header independently — e.g., include the `X-Shopify-Shop-Domain` header in the HMAC computation, or require that any shop attribution be derived only from fields inside the HMAC-verified body (as Shopify's official webhook payloads typically include shop identifiers), and document clearly that `shop_domain` from `WebhookVerification` must never be used for authorization decisions without additional shop-session validation against the stored session for that shop.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds since it never checks the shop-domain header. [5](#0-4) 
4. Any custom controller/job written per the gem's documented pattern (`SomeJob.perform_later(shop_domain: shop_domain, ...)`) now processes attacker body `B` as if it were sent by `victim-shop.myshopify.com`. [6](#0-5)

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
