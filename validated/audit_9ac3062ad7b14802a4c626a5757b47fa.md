## Title
`CallDispatcher.dispatch` has no access control, letting anyone drain any token/ETH balance the dispatcher happens to hold — [File: evm/src/utils/CallDispatcher.sol]

## Summary
The external report's core broken invariant: a function that gathers arbitrary/unlisted tokens into a contract (`arbitraryCall`) leaves them untracked, and a second, unauthenticated function (`recoverTokens`) can then be raced to sweep those tokens to an attacker before the protocol claims them.

Hyperbridge has a structurally identical pattern. `CallDispatcher` is a shared, stateless contract used by `IntentGatewayV2`/`IntentsBase`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute arbitrary calldata (swaps, DeFi interactions) while holding tokens mid-flow. Its `dispatch` entrypoint has **zero access control**, so it is the exact analog of `recoverTokens` — a public function that can move any token/ETH the contract currently holds, to any address.

## Finding Description
`CallDispatcher.dispatch` is declared with no modifier at all: [1](#0-0) 

Any address can call it directly with an arbitrary `Call[]` array. Since the calls execute `to.call{value: call.value}(call.data)` from the `CallDispatcher`'s own context, an attacker can encode `token.transfer(attacker, CallDispatcher.balanceOf(token))` (or a raw ETH sweep) and pull out **any balance the dispatcher currently holds**, regardless of which app or order it belongs to.

The dispatcher legitimately accumulates un-swept balances in several flows:
- `IntentsBase._execute` only sweeps tokens explicitly listed in `order.output.assets`; any other token balance left on the dispatcher by the postdispatch call (e.g. a reward/airdrop token from a multi-hop swap, staking claim, or unexpected transfer) is never collected by the protocol: [2](#0-1) 

- `IntentGatewayV2.placeOrder`'s predispatch step transfers user funds to the dispatcher, dispatches arbitrary calldata, then sweeps only the specific input token amounts back — any other token/leftover ETH from that swap is not addressed here: [3](#0-2) 

- `HyperFungibleToken`/`WrappedHyperFungibleToken` route bridged tokens through `CallDispatcher.dispatch(message.data)` for arbitrary post-mint/unlock calldata, meaning the dispatcher is a common, shared execution surface across the whole protocol on a chain: [4](#0-3) 

Because `CallDispatcher` is a single canonical deployment reused by all of these apps, any token that lands on it — via a stray transfer, an unlisted swap-route output, an airdrop, or a partially-completed multi-call sequence — sits in a shared pool with **no owner-only withdrawal path and no permission check on `dispatch`**. This is precisely the "gathered but untracked, then freely stealable" pattern from the external report: `arbitraryCall`/`recoverTokens` ↔ arbitrary DeFi calldata routed through `CallDispatcher`/unauthenticated `dispatch`.

## Impact Explanation
Any unprivileged attacker who observes (via mempool or state polling) that `CallDispatcher` holds a nonzero ERC20 or native balance — from an airdrop, an unlisted swap-route byproduct, or any leftover from a legitimate app flow — can call `dispatch` directly and drain it to themselves. This is direct loss of funds with no need for a malicious peer, relayer, prover, or governance actor: the attacker only needs an ordinary transaction against a public, unauthenticated entrypoint.

## Likelihood Explanation
`dispatch` is `external` with no modifier, so the precondition (a nonzero balance sitting on the shared dispatcher) is the only thing standing between an attacker and the funds. Given `CallDispatcher` is intentionally used to hold tokens mid-execution across multiple apps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) and the existing sweep logic (`_execute`, `placeOrder`) only accounts for explicitly listed tokens, any unlisted token or airdrop landing on the dispatcher is realistically likely over the contract's lifetime, and once it lands it is trivially and immediately stealable by anyone monitoring the address.

## Recommendation
Restrict `CallDispatcher.dispatch` so it can only be invoked by the calling app in the same transaction (e.g., pass an authorized caller/owner set at construction, or make it a per-app, non-shared instance), and/or have each app that uses the dispatcher verify post-call that no non-designated token balance remains, sweeping any residual balance to the protocol treasury rather than leaving it on a permissionless, shared contract.

## Proof of Concept
1. Any token (airdrop, reward token from a DEX route, or accidental transfer) is sent to the deployed `CallDispatcher` address, or is left there after a legitimate `_execute`/`placeOrder` flow that only sweeps the tokens explicitly listed in `order.output.assets`/`order.inputs` [5](#0-4) .
2. An attacker (no special privileges) calls `CallDispatcher.dispatch(abi.encode(calls))` directly, with `calls[0] = Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(address(dispatcher)))})`.
3. Since `dispatch` has no access-control modifier [6](#0-5) , the call executes and transfers the entire token balance to the attacker, with no revert and no requirement to interact with any app, order, or governance path.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
