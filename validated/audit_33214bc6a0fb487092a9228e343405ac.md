### Title
`SignableTransaction::calculate_weight_vbytes` omits the OP_RETURN data output from the fee/weight estimate, causing underpayment of the actual transaction fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` into the real transaction's output list (`tx_outs`), but the weight/vbytes used to compute `needed_fee` and the change amount are derived from a template transaction built only from `payments` (and `change`). The data output is never included in the estimate, so the resulting transaction systematically pays a fee lower than `fee_per_vbyte * actual_vsize` whenever `data` is provided.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- The `OP_RETURN` data output is appended to `tx_outs` at lines 194–202:
  ```rust
  if let Some(data) = data {
    tx_outs.push(TxOut {
      value: Amount::ZERO,
      script_pubkey: ScriptBuf::new_op_return(...)
    })
  }
  ```
- The fee is then computed from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, which builds a template `Transaction` whose `output` list contains only `payments` (lines 85–93) plus an optional change output (lines 95–99). The `data`/`tx_outs` list is not passed in, so the OP_RETURN output's ~9 + 2 + data.len() bytes are excluded from `weight`/`vbytes`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) and the `TooLowFee` minimum-relay check (lines 211–213) are therefore evaluated against an understated vbytes.
- When `change` is provided, the change output value is `input_sat - payment_sat - fee_with_change` (lines 224–234), again with `fee_with_change` computed from the template that excludes the data output. The excess is credited to the change output, so the actual paid fee (`fee()` = inputs − outputs, lines 138–141) equals the underestimated `needed_fee`.

This is the same bug class as the external report: a formula (here, "fee = rate × transaction size") computed over an incorrect model of the protocol object — the real signed transaction contains an output the pricing model pretends doesn't exist.

### Impact Explanation
An 80-byte data payload produces an OP_RETURN output of roughly 90+ serialized bytes (~90 vbytes of weight that is entirely unaccounted for). For a small transaction (e.g., 1 input, 1 payment, 1 change ≈ ~200 vbytes), the paid fee rate can be ~30% below the requested `fee_per_vbyte`. If `fee_per_vbyte` was set near the minimum relay fee, the signed transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` for its actual size — the `TooLowFee` guard is defeated because it checks the underestimated vbytes. The result is a transaction that validates and is signed by the FROST multisig but will not relay/confirm, temporarily locking the spent inputs until a replacement plan is signed.

### Likelihood Explanation
Reachable whenever a caller supplies `data` to `SignableTransaction::new` — the same public transaction-construction/signing path used to produce spends. The miscalculation is deterministic (no edge-case probability); every transaction with a non-`None` data output underpays by the exact serialized size of the OP_RETURN output. In the current processor code path (`make_signable_transaction` passes `None` for `data`), the primitive is latent, but the library function is exposed for precisely this use and the error is baked into `needed_fee`, `fee()`, and the change amount.

### Recommendation
Include the OP_RETURN output in the weight/vbytes template — e.g., pass the fully-built `tx_outs` (or the data output) into `calculate_weight_vbytes` so the estimated transaction is byte-for-byte identical in structure to the one signed. Re-check `TooLowFee` against the corrected vbytes, and recompute the change value from the corrected `fee_with_change`.

    // Expand this a full transaction in order to use the bitcoin library's weight function

      lock_time: LockTime::ZERO,

          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here

          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),

      // the value is fixed size (so any value could be used here)

    }
