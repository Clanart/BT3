### Title
Stale `last-update` timestamp causes retroactive interest/liquidity-index inflation, corrupting zToken collateral prices via `resolve-ztoken` callcode transform - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalents; consumed by `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `points-ir` interest-rate curve default is `{util: u0, rate: u0}` [1](#0-0) , meaning at 0% utilization (no debt) the borrow rate resolves to `0`. When utilization is `0`, `next-index`/`next-liquidity-index` compute a `multiplier` of exactly `INDEX-PRECISION` (no change) [2](#0-1) , and the `accrue` function only advances `last-update` if `index` or `lindex` actually changed [3](#0-2) . Consequently, while a vault has no debt, `last-update` never moves forward. This is the same root cause described in the IonPool report: a monotonic per-vault timestamp is not incremented when there's no debt, so once debt (and thus a nonzero utilization/rate) appears, the very next accrual applies the new nonzero rate over the entire stale time-delta — including the period when there was no debt. The corrupted `lindex` (liquidity index) is then read directly by the oracle's callcode transform `resolve-ztoken`, which prices zTokens (zSTX/zUSDC/zUSDH/zSBTC/zstSTX/zstSTXbtc) used as collateral in the market, producing a wrong collateral price/valuation.

### Finding Description
Each vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks a borrow index (`index`) and a liquidity index (`lindex`), both anchored to a single `last-update` timestamp [4](#0-3) .

`next-index`/`next-liquidity-index` compute a time-based multiplier from `(- stacks-block-time (var-get last-update))` and the current `interest-rate` (derived from current `utilization`) [2](#0-1) . At `0` utilization, using the deployed default `points-ir` config (`util: u0, rate: u0`), `interest-rate` returns `0`, so the multiplier resolves to exactly `INDEX-PRECISION`, meaning `next == idx` and `nliq == lidx`.

Inside `accrue`, `last-update` is only bumped when the computed indexes actually differ from the stored ones:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [5](#0-4) 

This mirrors exactly the reported IonPool bug class: while there is no debt (or more generally whenever the computed rate yields no index change), the "per-ilk"/per-vault timestamp is left stale. Every vault operation (`system-borrow`, `system-repay`, deposit/withdraw flows) invokes `accrue` first [6](#0-5) , so once utilization becomes nonzero (first borrow), the immediately following `accrue` call (e.g., the next borrow, repay, or deposit) computes `time-delta = stacks-block-time - last-update` spanning back to whenever the vault last had a nonzero rate — which can include the entire idle, debt-free period — and applies the *current* nonzero rate to that whole stale interval when computing `next-index`/`next-liquidity-index`.

The corrupted `lindex` is not confined to the vault's internal accounting: it is consumed directly by the oracle's callcode transform in the market contract, `resolve-ztoken`, which reads the vault's cached `lindex` to price zTokens:
```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
``` [7](#0-6) 

This is invoked for every zToken-collateral price resolution via `resolve-callcode` (`CALLCODE-ZSTX`, `CALLCODE-ZSBTC`, `CALLCODE-ZUSDC`, `CALLCODE-ZUSDH`, `CALLCODE-ZSTSTXBTC`, and the composed `CALLCODE-ZSTSTX`) [8](#0-7) . Because `get-cached-indexes` returns the vault's `accrue` output verbatim (cached per block) [9](#0-8) , an inflated `lindex` directly inflates the USD value assigned to zToken collateral used in health-factor / LTV calculations and liquidation checks throughout the market.

### Impact Explanation
Direction of the error: `lindex` is inflated upward beyond the value that legitimately accrued, because a nonzero rate is retroactively applied over a period when the vault genuinely had zero debt/utilization (during which no liquidity yield should have accrued). This inflated `lindex` is fed straight into `resolve-ztoken`, causing the market to overvalue zToken collateral relative to its true backing.

Who profits / who is harmed: a user holding zToken collateral (e.g., zUSDC deposited as collateral) benefits from an inflated collateral valuation, allowing them to borrow more than their real collateral backs, or to avoid liquidation when they should be liquidated — this is a wrong health verdict stemming from a corrupted callcode-transform price. This can lead to under-collateralized positions and ultimately protocol insolvency/bad debt once the position is unwound, which the protocol/other depositors absorb. This lands in the Critical impact category (protocol insolvency / permanent freezing of funds via bad debt) since it directly distorts a price feeding health checks.

### Likelihood Explanation
The precondition — a vault sitting at zero utilization/debt for a period, followed by the first borrow after idle time — is an ordinary, easily reachable operational state (e.g., a freshly deployed vault, or a vault whose debt is fully repaid and stays empty for a while before the next borrow). No governance or oracle compromise is needed; a single user simply needs to be the first to interact with an idle vault, then trigger a subsequent accrual. This makes the bug straightforward to trigger unintentionally, and equally easy for an attacker to trigger deliberately (e.g., ensure a vault is drained to zero debt, wait, then re-borrow to intentionally inflate `lindex`, and use zToken collateral of that vault elsewhere in the market to over-borrow).

### Recommendation
Always advance `last-update` to `stacks-block-time` inside `accrue` whenever accrual logic runs (i.e., whenever `(get accrue states)` is `false`), regardless of whether `index`/`lindex` actually changed, mirroring the fix recommended for the IonPool report. This ensures `time-delta` used in the next accrual only spans genuinely-elapsed periods under the rate that was actually in effect, and prevents a stale timestamp from causing retroactive rate application once utilization changes. Apply this fix consistently across all vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Deploy/observe a vault (e.g., `v0-vault-usdc`) with `total-debt = 0` for an extended period `T` (no borrows), so `utilization = 0` and — with the default `points-ir = {util: u0, rate: u0}` — `interest-rate = 0`. Each call to `accrue` during this period computes `next == idx`, `nliq == lidx`, so `last-update` is never advanced (per [5](#0-4) ).
2. A user calls `system-borrow`, which invokes `accrue` first [6](#0-5)  — still with `last-update` stale from before period `T`, but `time-delta` still spans zero net change since utilization is still `0` pre-borrow, so this call itself does not yet inflate the index; it does, however, update `principal-scaled`/`total-borrowed`, making `utilization > 0` for the *next* accrual.
3. Any subsequent vault operation (another borrow, repay, or a market operation that calls `accrue`/`vault-accrue`) computes `time-delta = stacks-block-time - last-update`, which now spans the entire idle period `T` plus the time since the borrow, and applies the new nonzero `interest-rate` (based on the now-nonzero utilization) over that whole stale interval via `calc-multiplier-delta` [10](#0-9) . This inflates both `index` (over-charging the borrower's debt) and `lindex` (over-crediting depositor share value) far beyond what should have accrued in the actual borrowing period.
4. The inflated `lindex` is cached and returned by `get-cached-indexes` [9](#0-8)  and consumed by `resolve-ztoken` when any market participant's position holds the corresponding zToken as collateral, directly inflating that collateral's USD valuation used in LTV/health checks [7](#0-6) .

Note: I was unable to fully verify from the indexed code whether every deployed vault's `points-ir` remains at the shown default `{util: u0, rate: u0}` in production (DAO could reconfigure it via a setter not fully traced here), nor did I locate a corresponding fix/PR reference within this repo confirming remediation status, since the index has size limits and some configuration/deployment files may not be fully covered. If precise confirmation of the live on-chain curve configuration is required, a full-repository session (e.g., a Devin session with complete file access) would be needed.
