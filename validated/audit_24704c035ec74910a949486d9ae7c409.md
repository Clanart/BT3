### Title
Division-by-zero DoS in `DelegateVoteRewardPool._updateVote()` when `totalWeight` becomes zero - (File: `rewards/DelegateVoteRewardPool.sol`)

### Summary
`DelegateVoteRewardPool` computes a per-pool target vote by dividing by the aggregate `totalWeight` state variable every time a user's staked balance changes, but the contract allows `totalWeight` to be reduced to zero through normal admin configuration while `votePools` entries remain registered, and there is no guard against dividing by zero in that case.

### Finding Description
`_updateVote()` iterates over `votePools` and unconditionally computes:

```solidity
uint256 targetVote = (votingWeights[pool] * totalSupply) / totalWeight;
``` [1](#0-0) 

`totalWeight` is only ever mutated by the owner-only `updateWeight()` function, which allows setting an existing pool's `weight` to `0`:

```solidity
function updateWeight(address lp, uint256 weight) external onlyOwner {
    if (lp == address(this)) revert InvalidPoolTokenAddress();
    if (!isVotePool[lp]) {
        if (!IWombatBribeManager(operator).isPoolActive(lp))
            revert PoolNotActive();
        isVotePool[lp] = true;
        votePools.push(lp);
    }
    totalWeight = totalWeight - votingWeights[lp] + weight;
    votingWeights[lp] = weight;
}
``` [2](#0-1) 

There is no function in the contract that removes an entry from `votePools` or resets `isVotePool`. If the owner deprioritizes the only (or last remaining) registered pool by calling `updateWeight(lp, 0)` — a legitimate, non-malicious administrative action (e.g., temporarily zeroing a pool's weight instead of fully de-registering it, since no removal path exists) — `totalWeight` becomes `0` while `votePools.length` remains `> 0`.

From that point on, every call to `stakeFor()` or `withdrawFor()` unconditionally invokes `_updateVote()`:

```solidity
function stakeFor(address _for, uint256 _amount) external override onlyOperator updateRewards(_for, rewardTokens) {
    totalSupply = totalSupply + _amount;
    _balances[_for] = _balances[_for] + _amount;
    _updateVote();
    ...
}
``` [3](#0-2) 

These functions are called by the `operator` (the `WombatBribeManager`) from `vote()`/`unvote()`, which are reachable directly by any ordinary vlMGP holder who routes votes to the delegated pool:

```solidity
IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
...
IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
``` [4](#0-3) 

Because `totalWeight` is `0`, the division `votingWeights[pool] * totalSupply / totalWeight` in `_updateVote()` reverts with a panic (division by zero), causing `stakeFor`/`withdrawFor` — and therefore the user-facing `vote()`/`unvote()` calls in `WombatBribeManager` — to revert for every user interacting with this delegated reward pool.

### Impact Explanation
Once `totalWeight` is zero while `votePools` is non-empty, any unprivileged user attempting to vote, unvote, or withdraw their delegated voting stake through `WombatBribeManager.vote()`/`unvote()` targeting this pool will have their transaction revert. This freezes users' ability to reallocate or withdraw their vlMGP voting power and any associated bribe rewards accounted through this pool, persisting until the owner performs another `updateWeight` call with a non-zero weight — there is no self-healing or user-triggered recovery path. This matches a freezing-of-funds/voting-power condition caused purely by protocol logic, not by any malicious action.

### Likelihood Explanation
The trigger condition only requires the contract owner to call the already-exposed `updateWeight(lp, 0)` on the sole/last active vote pool — a plausible, legitimate configuration action given the absence of any pool-removal function — combined with any ordinary user calling `vote()`/`unvote()` afterward. No malicious admin behavior or governance manipulation is required; the zero-weight state is reachable through intended contract usage.

### Recommendation
Guard `_updateVote()` against `totalWeight == 0` (e.g., skip vote adjustment or set `targetVote = 0` when `totalWeight` is zero), and/or provide a proper pool-removal function that also removes the entry from `votePools` when its weight is set to zero, preventing stale entries from causing division by zero.

### Proof of Concept
1. Owner calls `updateWeight(lpA, 100)` — registers `lpA` in `votePools`, `totalWeight = 100`.
2. Owner later calls `updateWeight(lpA, 0)` — `totalWeight` becomes `0`, but `lpA` remains in `votePools` (`isVotePool[lpA]` stays `true`, no removal exists).
3. Any user calls `WombatBribeManager.vote()` (or `unvote()`) with a non-zero delta targeting the delegated pool.
4. This triggers `IBribeRewardPool(pool.rewarder).stakeFor()`/`withdrawFor()` on `DelegateVoteRewardPool`, which calls `_updateVote()`.
5. `_updateVote()` executes `votingWeights[lpA] * totalSupply / totalWeight` with `totalWeight == 0`, causing a Solidity division-by-zero panic and reverting the entire user transaction. [1](#0-0) [2](#0-1)
