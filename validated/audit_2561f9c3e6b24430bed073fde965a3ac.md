### Title
Lack of reentrancy protection in `CW20ERC20Pointer.approve()` allows atomic allowance manipulation via CW20→EVM callback through the wasmd bridge - (File: `contracts/src/CW20ERC20Pointer.sol`)

### Summary
`CW20ERC20Pointer.approve()` follows a classic check-then-act (TOCTOU) pattern with no reentrancy guard: it reads the current allowance via an external query, computes a delta, then issues an external state-changing call (`_execute`) to the underlying CosmWasm contract. Unlike a normal EVM-only setup where this pattern is merely a theoretical front-running risk, Sei's EVM↔CosmWasm bridge allows the underlying CW20 contract to synchronously call back into the EVM mid-execution when the top-level transaction targets the wasmd precompile directly, because the `EVMEntryViaWasmdPrecompile` guard is set once per-transaction and stays `true` for the whole call, not just for the top-level dispatch.

### Finding Description
`CW20ERC20Pointer.approve()` performs: [1](#0-0) 

It reads `currentAllowance` via a `WasmdPrecompile.query` call, computes the increase/decrease delta from stale state, and then calls `_execute`, which delegatecalls the wasmd precompile's `execute` method to run the underlying CW20 contract's `increase_allowance`/`decrease_allowance` handler: [2](#0-1) 

The wasmd precompile's `execute` handler actually invokes the CosmWasm contract synchronously via `p.wasmdKeeper.Execute`: [3](#0-2) 

The guard that is supposed to prevent CW contracts from calling back into the EVM (`sei does not support EVM->CW->EVM call pattern`) is only effective when `EVMEntryViaWasmdPrecompile()` is `false`: [4](#0-3) 

However, this flag is set to `true` for the *entire* top-level transaction whenever the transaction's destination is the wasmd precompile address, not scoped to a single hop: [5](#0-4) 

Consequently, if a user submits an EVM transaction whose `to` is the wasmd precompile (0x1002) calling `execute()` against a CW20 contract (directly, or via a pointer's `_execute()` delegatecall), and that CW20 contract's message handler issues an `EvmMsg::CallEvm`/`DelegateCallEvm` sub-message, the callback into the EVM is permitted mid-execution — the outer `CallEVM` guard is bypassed because `EVMEntryViaWasmdPrecompile()` remains `true` for the duration of the outer transaction. This lets a CW20 contract deployed by an attacker re-enter arbitrary EVM contracts — including the very `CW20ERC20Pointer` (or any other contract) that is mid-way through `approve()` — before the outer `_execute()` call returns.

### Impact Explanation
Because pointer registration (`AddCW20Pointer`) is permissionless, an attacker can register a pointer over a CW20 contract they fully control, whose `increase_allowance`/`decrease_allowance`/`transfer_from` handler contains a crafted `EvmMsg::CallEvm` callback. When a victim calls `approve()` on the resulting `CW20ERC20Pointer`, the read-then-execute sequence in `approve()` can be interleaved with a reentrant call (triggered from inside the CW20 contract's own handler) that acts on the stale allowance value before the outer `_execute()` finishes updating it. This reproduces the classic ERC20 "approve race condition" atomically within a single transaction rather than requiring a front-run across two blocks, enabling a spender to extract more tokens than the owner intended — an unauthorized transfer / fund-loss condition attributable to the missing reentrancy guard, directly analogous to the reported `CollateralEscrowV1` issue (external call before finalizing accounting, no `nonReentrant` protection).

### Likelihood Explanation
Reachable by any unprivileged EVM transaction sender: (1) deploy a malicious CW20 contract with a `CallEvm`/`DelegateCallEvm` hook in its allowance/transfer handlers, (2) register it via the permissionless pointer precompile, (3) get (or induce) a victim to `approve()` the pointer, (4) submit a single EVM transaction targeting the wasmd precompile's `execute()` to trigger the reentrant callback. All steps use standard, publicly available entry points (pointer precompile, wasmd precompile, EVM transactions) with no validator/operator/governance involvement.

### Recommendation
- Add a reentrancy guard (e.g., a transient/storage-based lock) to `CW20ERC20Pointer` (and the analogous `CW721ERC721Pointer`/`CW1155ERC1155Pointer`) around all state-mutating functions (`approve`, `transfer`, `transferFrom`) that call `_execute()`.
- Rework `approve()` to avoid the check-then-act pattern (e.g., always issue an authoritative `set_allowance`-style CW message instead of computing a delta from a possibly stale read), or re-validate the allowance after `_execute()` returns and revert on mismatch.
- Scope `EVMEntryViaWasmdPrecompile` more tightly than "for the entire top-level transaction that targeted the wasmd precompile" — e.g., clear/reset it once the initial `execute()` dispatch to the CW contract begins, so that a CW20/CW721/CW1155 contract's own message handling cannot re-enter the EVM mid-flight during the same transaction.

### Proof of Concept
1. Attacker deploys a CW20 contract `EvilCW20` whose `increase_allowance`/`decrease_allowance` (or `transfer_from`) handler returns a `SubMsg` containing `EvmMsg::CallEvm { to: <PointerOrVictimContract>, data: <reentrant call> }`.
2. Attacker calls the permissionless pointer precompile (`AddCW20Pointer`) to register `EvilCW20`, obtaining `CW20ERC20Pointer` address `P`. [6](#0-5) 
3. Victim calls `P.approve(attackerSpender, newAmount)`. Internally this reads `currentAllowance` then calls `_execute()` → wasmd precompile `execute()` → `EvilCW20`'s handler.
4. `EvilCW20`'s handler emits `CallEvm` back into `P` (or into a third contract relying on `P`'s allowance/balance), calling `transferFrom`/`approve` again using the not-yet-updated allowance state, since `ctx.EVMEntryViaWasmdPrecompile()` remains `true` for the whole top-level EVM transaction (originally addressed to the wasmd precompile), so `k.CallEVM`'s `EVM->CW->EVM` guard does not trigger. [4](#0-3) 
5. The nested call completes and returns control to `EvilCW20`'s handler, which then returns to the outer `_execute()`/`approve()` call, which finalizes the allowance based on the pre-reentrancy read — resulting in a higher effective spend than the victim authorized.

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
