### Title
Silent truncation of hookify YAML frontmatter on embedded '---' causes `action: block` rules to load as `warn`/no-op - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter()` locates the frontmatter boundary with a naive `content.split('---', 2)`, which treats any literal `---` occurring inside a field value (e.g. inside `pattern:`) as the closing delimiter. This causes fields declared after that point (such as `action: block` or `enabled: true`) to be silently dropped into the message body instead of the parsed frontmatter dict, so the `Rule` falls back to defaults (`action="warn"`) with no error or warning printed.

### Finding Description
`extract_frontmatter` at [1](#0-0) splits on the literal string `---` with `maxsplit=2`. It is not YAML-aware and does not require `---` to appear on its own line; any occurrence of the three-character substring anywhere before the intended closing delimiter (e.g., inside a regex `pattern:` value, which is very plausible content since `-` is a common shell/regex character, e.g., `rm ---force` or `--\s*-`) is consumed as the second delimiter. Everything textually after that point — including subsequent `action:` / `enabled:` lines that a human reviewer sees as still being inside the frontmatter block — ends up in `parts[2]` (the message), not `parts[1]` (the parsed frontmatter).

`Rule.from_dict` then reads `frontmatter.get('action', 'warn')` and `frontmatter.get('enabled', True)` [2](#0-1) , silently defaulting `action` to `"warn"` if the real `action: block` line got shifted into the message text. `load_rule_file` only prints a warning when `frontmatter` is completely empty [3](#0-2) ; when parsing partially "succeeds" (non-empty dict, but missing the intended keys), no diagnostic is emitted. Downstream, `RuleEngine.evaluate_rules` branches purely on `rule.action == 'block'` to decide whether to deny a tool call or merely display a systemMessage [4](#0-3) , so a rule authored/reviewed as blocking silently becomes a non-blocking warning at runtime.

### Impact Explanation
This breaks the "deny means deny" invariant for hookify security rules: a rule file that visually contains `action: block` (and would pass code review as an enforced deny-rule) is parsed as `action: warn` due to an incidental `---` earlier in the same frontmatter block, with the tool call being allowed to proceed instead of denied. Because `pretooluse.py`/`posttooluse.py`/`stop.py` gate command/file/session actions on `evaluate_rules`, this is a real, silent weakening of hook enforcement (bash command blocking, file-edit blocking, Stop blocking) without any error surfaced to the user or maintainer.

### Likelihood Explanation
This requires only that a rule file (`.claude/hookify.*.local.md`) checked into the repo contains a `---` substring anywhere in the frontmatter block before the real closing `---` — most plausibly inside a `pattern:` regex value, which is exactly the kind of content hookify rules are built around (matching dangerous flags/commands). This can occur unintentionally by any rule author, and could be deliberately hidden by a lower-trust contributor submitting a rule/PR that appears to enforce `action: block` in the diff while the actual runtime behavior silently degrades to warn-only. No special privilege beyond ordinary repository content/PR authorship is needed, and the bug is 100% deterministic/reproducible given the split logic.

### Recommendation
Replace the string-split delimiter detection with a line-based check requiring `---` to appear alone on its own line (e.g., using `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or splitting on `\n---\n`), and/or replace the ad-hoc line parser with a real YAML parser (`yaml.safe_load`) for the frontmatter block. Additionally, `load_rule_file` should validate that expected keys are internally consistent (e.g., warn if `action` is present in raw text but absent from the parsed dict) to avoid silent downgrade.

### Proof of Concept
Unit test in `config_loader.py`'s test module:
```python
content = '''---
name: block-force-flag
event: bash
pattern: "rm ---force"
action: block
enabled: true
---
This command is dangerous!
'''
fm, msg = extract_frontmatter(content)
# Expected (correct) parse:
assert fm.get('action') == 'block'
assert fm.get('enabled') is True
# Actual buggy behavior observed:
# fm == {'name': 'block-force-flag', 'event': 'bash', 'pattern': '"rm '}
# 'action: block' and 'enabled: true' end up inside `msg`, not `fm`.
rule = Rule.from_dict(fm, msg)
assert rule.action == 'warn'  # should be 'block' -> demonstrates silent downgrade
```
Fuzz/differential test plan: generate random frontmatter blocks containing an embedded `---` substring in a scalar value at varying positions, parse with both `extract_frontmatter` and `yaml.safe_load` (fed only the properly-delimited frontmatter text), and assert the two parsers agree on all keys (`action`, `enabled`, `pattern`, etc.). Any divergence, especially where `action`/`enabled` differ, confirms the invariant violation.
