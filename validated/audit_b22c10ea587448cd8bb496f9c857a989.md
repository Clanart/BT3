### Title
Gov deposit refunds can be permanently blocked/frozen for depositors using an unassociated EVM cast address - ([File: sei-cosmos/x/gov/keeper/deposit.go])

### Summary
`Keeper.RefundDeposits` in the governance module refunds proposal deposits back to depositors, but silently skips (and permanently retains) the refund for any depositor address that is a direct EVM-cast address whose backing EVM address later becomes associated with a *different* Sei address. This is directly analogous to the PirexGmx finding: a critical, otherwise-automatic state transition (`initiateMigration` / here, deposit refund) has an unprivileged, attacker-controllable precondition (`gmxVester`/`glpVester` balance == 0` / here, `CanSendTo` == true) that can be permanently poisoned by a third party, freezing funds with no recovery path short of a migration.

### Finding Description
`AddDeposit` lets any account, including a raw EVM-cast `sdk.AccAddress` (`sdk.AccAddress(evmAddr[:])`) that has never been associated, deposit funds on a governance proposal: [1](#0-0) 

When the proposal is finalized, `RefundDeposits` iterates deposits and sends funds back — but only if the recipient can currently receive funds: [2](#0-1) 

Whether a cast address `CanSendTo` depends on `CanAddressReceive`, which is keyed off Sei<->EVM address association state: [3](#0-2) 

A direct-cast address (`sdk.AccAddress(evmAddr[:])`) can only receive bank sends if the underlying EVM address is unassociated, or associated back to that exact cast address. If *any* account (not the depositor) subsequently associates that same EVM address with a **different** Sei address (via a normal EVM transaction/association flow reachable by any unprivileged sender, as covered by `x/evm/ante` preprocessing and `AssociationHelper.AssociateAddresses`), `CanAddressReceive`/`CanSendTo` for the original cast address becomes permanently `false`. This is exactly the precondition-poisoning pattern from the report: an unprivileged third party performs an action (associate the EVM address elsewhere) that permanently breaks a precondition (`CanSendTo`) another process depends on.

The existing test confirms this exact behavior — a cast-address depositor's refund is silently skipped and the deposit record is retained forever, backed only by module-account balance, with the code comment stating recovery "requires a migration": [4](#0-3) [5](#0-4) 

### Impact Explanation
Once a deposit is made from an unassociated EVM-cast address and an attacker (or even an innocent unrelated user) later associates that EVM address to a different Sei address, the deposit becomes permanently unrecoverable through normal chain operation — it is neither refunded nor burned, and just sits in the gov module account forever, with the on-chain `Deposit` record never cleared. This is a genuine permanent freezing of user funds, reachable purely by unprivileged transactions (an `AddDeposit`/`MsgDeposit` from the victim, followed by an EVM association transaction from any account, including the attacker), matching the "permanent freezing" impact category.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a depositor who deposits from a cast address before ever associating it (this is easy to trigger — e.g., any EVM account that funds itself and calls `MsgDeposit` via its Sei-cast address before sending its first EVM transaction), and (b) a subsequent association of that same EVM address to a *different* Sei key. An attacker who knows/controls a target's un-associated EVM address, or wants to grief any depositor, can proactively front-run association of arbitrary EVM addresses (association only requires proving control of the EVM private key for a signed message/tx, so an attacker cannot force association of someone else's EVM address without their key — but self-griefing, or a race with a target's own subsequent association from a different intended Sei key, is realistic, especially in wallets/tooling that don't guarantee 1:1 address usage before depositing).

### Recommendation
`RefundDeposits` should not silently retain deposits indefinitely with only a passive "requires a migration" fallback. Options:
- Track un-refundable deposits explicitly and expose a permissionless recovery path (e.g., a message that lets the depositor claim the refund to their currently-associated Sei address once resolved), rather than requiring a chain migration.
- Alternatively, disallow deposits from raw un-associated EVM-cast addresses at `AddDeposit` time, forcing association first, removing the possibility of the address later becoming unreceivable.

### Proof of Concept
The existing repository test demonstrates the freeze condition end-to-end: [4](#0-3) 
1. `validDepositor` and `castDepositor` (an unassociated EVM-cast address) both deposit on a proposal.
2. The EVM address behind `castDepositor` is then associated to a *different* Sei address.
3. `CanSendTo(ctx, castDepositor)` now returns `false`.
4. `RefundDeposits` is called; `validDepositor`'s deposit is refunded and cleared, but `castDepositor`'s deposit record and its share of the module-account balance remain permanently stuck, with no in-protocol way to reclaim it besides a manual migration.

// AddDeposit adds or updates a deposit of a specific depositor on a specific proposal
// Activates voting period when appropriate
func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func TestRefundDepositsLeavesInvalidRecipientPending(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})
	validDepositor := seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(100))[0]

	proposal, err := app.GovKeeper.SubmitProposal(ctx, TestProposal)
	require.NoError(t, err)

	evmAddr := common.HexToAddress("0x0000000000000000000000000000000000000001")
	castDepositor := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, castDepositor, evmAddr)
	require.NoError(t, app.BankKeeper.AddCoins(ctx, castDepositor, sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 100)), true))

	castDeposit := sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 40))
	validDeposit := sdk.NewCoins(sdk.NewInt64Coin(sdk.DefaultBondDenom, 30))
	_, err = app.GovKeeper.AddDeposit(ctx, proposal.ProposalId, castDepositor, castDeposit)
	require.NoError(t, err)
	_, err = app.GovKeeper.AddDeposit(ctx, proposal.ProposalId, validDepositor, validDeposit)
	require.NoError(t, err)

	app.EvmKeeper.SetAddressMapping(ctx, sdk.AccAddress(bytes.Repeat([]byte{2}, common.AddressLength)), evmAddr)
	require.False(t, app.BankKeeper.CanSendTo(ctx, castDepositor))

	app.GovKeeper.RefundDeposits(ctx, proposal.ProposalId)

	deposit, found := app.GovKeeper.GetDeposit(ctx, proposal.ProposalId, castDepositor)
	require.True(t, found)
	require.Equal(t, castDeposit, deposit.Amount)
	_, found = app.GovKeeper.GetDeposit(ctx, proposal.ProposalId, validDepositor)
	require.False(t, found)
	require.Equal(t, sdk.NewInt(100), app.BankKeeper.GetBalance(ctx, validDepositor, sdk.DefaultBondDenom).Amount)
	require.Equal(t, castDeposit, app.BankKeeper.GetAllBalances(ctx, app.AccountKeeper.GetModuleAddress(types.ModuleName)))
}
