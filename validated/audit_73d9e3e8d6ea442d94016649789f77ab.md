### Title
`updateEndRemainingAllocation()` is unguarded and re-callable, letting any late claimer shrink the bonus denominator to steal a disproportionate share of `totalBonus` - ([File: rewards/Airdrop.sol])

### Summary
`Airdrop.updateEndRemainingAllocation()` recomputes `totalEndRemainingAllocation = totalRemainingAllocation` every time it is invoked and has no internal guard preventing re-execution; only the call-site in `claim()` conditionally skips it via `if (totalEndRemainingAllocation == 0)`. Because it is `public`, any unprivileged address can call it directly at any time after `periodsEndTime[4]`, repeatedly shrinking the denominator used in `getBonusAmount()` as other users claim and reduce `totalRemainingAllocation`, letting the caller immediately follow with `claim()` to extract a bonus far larger than their fair share of `totalBonus`.

### Finding Description
`getBonusAmount()` computes each user's bonus as `userAllocation * totalBonus / totalEndRemainingAllocation`, [1](#0-0)  where `totalEndRemainingAllocation` is meant to be a one-time snapshot of the remaining allocation pool at the moment vesting fully ends, and `totalBonus` is the sum of amounts forfeited by users who claimed early (before period 4 ended) [2](#0-1) .

The intended invariant is: `sum(userAllocation_i)` over all users who have not yet claimed at the snapshot moment equals `totalEndRemainingAllocation`, so `sum(bonusAmount_i) == totalBonus` exactly once all of them claim — conservation holds.

The bug is in `updateEndRemainingAllocation()`:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
``` [3](#0-2) 
This function has no check that `totalEndRemainingAllocation == 0` before overwriting it — that guard exists only where `claim()` calls it: `if (totalEndRemainingAllocation == 0) { updateEndRemainingAllocation(); }` [4](#0-3) . Because the function is `public`, any unprivileged caller can invoke it directly at any point after `periodsEndTime[4]`, unconditionally resetting `totalEndRemainingAllocation` to the *current* (smaller) `totalRemainingAllocation`, since `totalRemainingAllocation` monotonically decreases as each user claims (`totalRemainingAllocation -= userAllocation`) [5](#0-4) .

Exploit flow:
1. Vesting period 4 ends; several users claim, each correctly paying out against the original (larger) `totalEndRemainingAllocation` fixed by the first post-period-4 claim.
2. Attacker, who still holds `allocations[attacker] > 0`, waits until other holders have claimed (shrinking `totalRemainingAllocation`), then directly calls `updateEndRemainingAllocation()`. This resets `totalEndRemainingAllocation` to the now much smaller remaining pool (potentially just the attacker's own allocation, or their allocation plus a few stragglers).
3. Attacker immediately calls `claim()`. Their `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` is now inflated because the denominator shrank while the numerator `totalBonus` (fixed since forfeiture cannot occur once bonus applies) stayed the same.
4. The attacker extracts a bonus far exceeding their proportional share of the total forfeited pool, consuming tokens that were implicitly reserved to pay whoever else has not yet claimed (or exceeding what the contract holds for them specifically), causing `InsufficientBalance()` reverts for legitimate remaining claimers.

Existing checks (`if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();`) only stop the attacker if the contract is completely out of funds; they do not prevent the underlying redistribution/theft from other legitimate claimants who have not yet claimed.

Note: contrary to the question's specific premise, `totalBonus` itself cannot keep growing after `totalEndRemainingAllocation` is first set — once bonus is applied, `claimableAmount` (full allocation + bonus) always exceeds `userAllocation`, so the `if (claimableAmount <= userAllocation)` forfeiture branch can no longer trigger. The real, exploitable root cause is the unguarded re-invocation of `updateEndRemainingAllocation()` shrinking the *denominator*, producing the same practical outcome: late/opportunistic claimers can extract disproportionately more than earlier claimers, breaking conservation between the funded pool and payouts.

### Impact Explanation
This breaks the conservation invariant `sum(bonusAmount_i) == totalBonus`: an attacker can extract more than their fair share of the forfeiture pool at the expense of other allocation holders who have not yet claimed, and can push the contract balance below what is required for the remaining rightful claimants, causing `InsufficientBalance()` reverts that freeze their funds. This is direct economic loss / theft of other users' bonus share and potential freezing of funds for the true remaining claimants.

### Likelihood Explanation
The attack requires only: (1) holding a nonzero `allocations[attacker]`, (2) waiting until `block.timestamp >= periodsEndTime[4]` and until other users have already claimed (naturally occurring over the airdrop's claim window), and (3) calling the fully public, unauthenticated `updateEndRemainingAllocation()` followed by `claim()` — both callable by any EOA with no special capital or privilege. This is straightforward and repeatable by any allocation holder who is not first to claim after vesting completes.

### Recommendation
Add an internal guard inside `updateEndRemainingAllocation()` itself so it can only ever set `totalEndRemainingAllocation` once (e.g., `if (totalEndRemainingAllocation == 0 && block.timestamp >= periodsEndTime[4]) { totalEndRemainingAllocation = totalRemainingAllocation; }`), removing reliance on the caller performing that check, and consider restricting who can trigger the first snapshot (or snapshotting automatically at exactly `periodsEndTime[4]` via a separate mechanism) so it cannot be timed/manipulated by any specific claimer.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with a `startTime`, register 3+ users with allocations (e.g., A=100, B=100, C=100), fund the contract with `totalRemainingAllocation` worth of `aidropToken`.
2. Warp past `periodsEndTime[1]`/`[2]` and have one user (D, separately registered) claim early with a partial allocation to generate `totalBonus > 0` via forfeiture.
3. Warp to `>= periodsEndTime[4]`. Have user A call `claim()` first — this triggers `updateEndRemainingAllocation()` internally, fixing `totalEndRemainingAllocation` to sum of remaining allocations (B + C + A, or B+C if A already excluded appropriately). Record A's `bonusAmount`.
4. Have user B call `claim()` normally, record `bonusAmount_B` (should match A's proportional bonus since denominator unchanged).
5. Before C claims, have C directly call `updateEndRemainingAllocation()` (publicly callable), then call `claim()`. Assert `bonusAmount_C` computed with the shrunk `totalEndRemainingAllocation` (now just C's remaining allocation) is disproportionately larger than `bonusAmount_A` and `bonusAmount_B` relative to equal allocations.
6. Assert `bonusAmount_A + bonusAmount_B + bonusAmount_C > totalBonus` (violates conservation), and/or that the contract's `aidropToken` balance goes negative/insufficient for a hypothetical 4th equal-allocation user, demonstrating fund freezing via `InsufficientBalance()`.
