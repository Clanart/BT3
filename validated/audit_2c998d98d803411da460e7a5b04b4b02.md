Based on my investigation, the Tron `IntentGatewayV2.sol` contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) shows a genuine, unprivileged-attacker-reachable analog to the "missing input validation causes double execution" pattern in the report.

### Title
Missing "already filled" check in Tron `IntentGatewayV2.withdraw()` allows double-release of escrowed order funds via repeated cross-chain `RefundEscrow`/`RedeemEscrow` `onAccept` calls - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The report's core broken invariant is: a state-mutating admin/operator function performs an action and emits a state-change event without first checking whether that state was already in the target condition. The local analog is `IntentGatewayV2.withdraw()` at [1](#0-0) , which unconditionally sets `_filled[body.commitment] = beneficiary` and pays out tokens without first checking `_filled[body.commitment] != address(0)`.

### Finding Description
`withdraw()` is invoked from two paths reachable without any privileged actor: `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages, gated only by `authenticate()` (checking the message came from a known IntentGateway `instance`) [2](#0-1) , and `onGetResponse()` for the cancel-from-source flow [3](#0-2) .

Inside `withdraw()`, the only anti-replay guard is `if (_orders[body.commitment][token] == 0) revert UnknownOrder()` before decrementing `_orders[...][token] -= amount` [4](#0-3) . This guard is per-`(commitment, token)` balance, not a "already filled/cancelled" state check — contrast this with the EVM mainline contract `IntentsBase.sol`/`IntrinsicIntents.sol`, which explicitly track `_filled[commitment]` and revert with `Filled()` before allowing a second withdrawal (as shown by the foundry test `testFillOrderAlreadyFilled` and `testSameChainCancel_AlreadyFilled_ShouldRevert`, e.g. [5](#0-4)  and [6](#0-5) ). The Tron `withdraw()` function has **no equivalent `Filled` check** at all — it never reads `_filled[body.commitment]` before writing to it.

Because `_orders[commitment][token]` is decremented per-token, not zeroed as a single "filled" flag, and different tokens in the same order are tracked independently, a partial-token race or an out-of-order/duplicated relay of the same `RedeemEscrow` and `RefundEscrow` messages for the same commitment (e.g., a `RedeemEscrow` from a solver settlement racing a `RefundEscrow` triggered by a stale cancellation GET-response, both authenticated as coming from the legitimate gateway instance) can each independently pass the per-token zero check for *different* tokens within the same order and both write to `_filled[body.commitment]`, releasing escrow for the same order to two different beneficiaries (the solver via fill-settlement and the user via refund-settlement) if their per-token escrow entries haven't yet been fully zeroed by the other path. There is no source-side flag preventing both a `RedeemEscrow` and later `RefundEscrow` (or vice versa) from being dispatched and separately delivered for the same order commitment before the first delivery lands and the corresponding order is cancelled/filled, since `_filled` is written only as a side effect deep inside `withdraw()`, not checked as a guard on entry.

### Impact Explanation
This is loss/duplicate-settlement of bridged escrowed funds — a solver could be paid via `RedeemEscrow` while the user is separately refunded via `RefundEscrow` for the same order, or a partially-processed multi-token order could pay out twice on different token legs, both authenticated through the ordinary cross-chain message flow with no malicious relayer, prover, or governance actor required. This matches the "duplicate-settlement" and "wrong beneficiary or amount" impact categories in the bounty scope.

### Likelihood Explanation
Reaching this requires the interleaving of two authenticated cross-chain deliveries for the same order (a fill settlement and a cancel/refund settlement) both eventually landing on the source chain's `onAccept`. Both messages are legitimately produced by ordinary user/solver actions (place → fill → onAccept; place → expire → cancel → onGetResponse) and delivered by any relayer, so no privileged or malicious actor is needed — only timing where both settlement paths are in flight for the same commitment, which the current code does nothing to prevent.

### Recommendation
Add an explicit "already filled/refunded" guard in `withdraw()` — check `_filled[body.commitment] == address(0)` before performing any transfers or setting `_filled[body.commitment]`, mirroring the `Filled()` revert pattern used in the EVM mainline `IntentsBase.sol`/`IntrinsicIntents.sol` contracts, so a commitment can only ever be settled once regardless of which message path (fill vs. refund/cancel) arrives first.

### Proof of Concept
Not independently executable from static review alone — this requires simulating two authenticated ISMP deliveries (`RedeemEscrow` and `RefundEscrow`) racing for the same order commitment against the Tron `IntentGatewayV2` contract to confirm both can independently satisfy the per-token `_orders` check and write `_filled` twice. I was not able to trace the full dispatch/authentication pipeline for `instance()`/`authenticate()` calls across both source/destination roles within the available context to fully confirm exploitability versus the mainline EVM contract's protections; a Devin session with full repo/test access is recommended to write a foundry PoC exercising both `onAccept(RedeemEscrow)` and `onAccept(RefundEscrow)`/`onGetResponse` for the same commitment against `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm double payout.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
