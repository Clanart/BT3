### Title
Payout OP_RETURN operator attribution is unauthenticated, letting anyone frame an uninvolved operator as payer of a self-funded withdrawal - (File: core/src/verifier.rs)

### Summary
`update_finalized_payouts` derives `operator_xonly_pk` for a completed withdrawal purely from an unsigned OP_RETURN data push in the on-chain payout transaction, with no check that the named operator actually supplied the funds. Since the payout transaction's only cryptographic constraint is the withdrawer's own `SIGHASH_SINGLE|ANYONECANPAY` signature over the withdrawal input and the user's output, anyone who controls the withdrawal UTXO (the withdrawer themselves, an unprivileged actor per the threat model) can add their own funding input(s), complete the transaction, and stamp any public operator xonly pubkey into the OP_RETURN.

### Finding Description
The binding the protocol implicitly assumes is:
`payout_payer_operator_xonly_pk (DB) == operator that actually supplied the extra funds in the payout tx output`

In practice the code only enforces:
`payout_payer_operator_xonly_pk (DB) == bytes embedded in the first OP_RETURN output of whichever tx spends the withdrawal UTXO`

This is set in `update_finalized_payouts`: [1](#0-0) 

The OP_RETURN payload is created by `create_payout_txhandler` as a bare data push of `operator_xonly_pk.serialize()` — it is not signed by, or otherwise bound to, the operator it names: [2](#0-1) 

The only signature the payout transaction requires is the withdrawer's key-path signature over the withdrawal input (`SinglePlusAnyoneCanPay` in the test helper, confirming ANYONECANPAY semantics that allow arbitrary additional inputs to be appended by anyone completing the transaction): [3](#0-2) 

Because the withdrawer already controls the withdrawal UTXO's spending key (it's their own withdrawal), they can complete and broadcast the payout transaction themselves — funding the output from their own wallet — and simply write an honest, uninvolved operator's public xonly pubkey into the OP_RETURN. `update_finalized_payouts` will record that operator as the payer, and `get_first_unhandled_payout_by_operator_xonly_pk` will surface it to that operator's own `PayoutCheckerTask`: [4](#0-3) [5](#0-4) 

The `PayoutCheckerTask` unconditionally calls `Operator::handle_finalized_payout` for any withdrawal attributed to its own `signer.xonly_public_key`, with no re-check that the operator itself actually broadcast or funded that specific payout transaction; it trusts the DB attribution that in turn trusts the unsigned OP_RETURN.

The only existing guard that touches `operator_xonly_pk` consistency, `is_kickoff_malicious`, checks the *payout's* recorded `operator_xonly_pk` against the *kickoff's own* `kickoff_data.operator_xonly_pk` — a self-consistency check, not a funding-provenance check: [6](#0-5) 

Since the forged payout's OP_RETURN pubkey is the victim operator's own real pubkey, and the victim's own kickoff naturally uses that same pubkey, this check trivially passes — it cannot detect that the victim never contributed funds to the payout.

### Impact Explanation
An unprivileged attacker can force an honest, completely uninvolved operator to treat an attacker-self-funded withdrawal as though that operator fronted it. This causes the victim operator's automation (`PayoutCheckerTask` → `handle_finalized_payout`) to consume one of its limited per-round kickoff connectors and enter the reimbursement flow for a payout it never made. Given the strict per-round kickoff connector cap (`num_kickoffs_per_round`), this can be repeated to exhaust an operator's kickoff slots for a round, and/or route bridge collateral reimbursement to that operator for a deposit it never fronted — both matching listed Critical categories: "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed" for genuine payouts once its kickoff connectors in that round are consumed. This is repeatable across every deposit/withdrawal and against every operator whose public xonly pubkey is known (all operator pubkeys are public information).

### Likelihood Explanation
The precondition is only that the attacker controls a withdrawal's spending path — true for any legitimate withdrawer, who is explicitly an unprivileged actor in this threat model. No verifier/operator/aggregator privilege, key compromise, or majority hashrate is needed; the attacker only needs to fund the transaction's non-witness-committed inputs (their own money) and pay Bitcoin fees. Given automation (`#[cfg(feature = "automation")]` `PayoutCheckerTask`) runs continuously and picks up any withdrawal attributed to the operator's own key, exploitation is straightforward and fully repeatable.

### Recommendation
Bind the OP_RETURN-embedded `operator_xonly_pk` cryptographically to actual fund provenance — e.g., require the additional funding input(s) in the payout transaction to be spent from a script/key uniquely tied to the named operator (so the operator's own signature is required to complete the payout), or require the operator to co-sign/attest the payout transaction (e.g. via a musig2 partial signature bound to the OP_RETURN payload) before `update_finalized_payouts` accepts the attribution. Do not treat an unsigned OP_RETURN data push as authoritative proof of who funded a transaction.

### Proof of Concept
```
cargo test broadcast_forged_payout_attribution -- --nocapture
```
Plan for the test:
1. Set up two operators, `victim_op` (never involved in this withdrawal) and no cooperating operator otherwise.
2. Register a deposit and withdrawal UTXO through Citrea as in existing e2e helpers (`generate_withdrawal_transaction_and_signature`), controlling the withdrawal UTXO's key as the "attacker".
3. Construct a payout transaction manually (bypassing `Operator::withdraw`): spend the withdrawal UTXO with the attacker's own `SinglePlusAnyoneCanPay` signature, add an attacker-funded extra input to cover the payout amount, and set the OP_RETURN to `victim_op.signer.xonly_public_key.serialize()`.
4. Broadcast and confirm the transaction; mine to finality depth.
5. Assert `victim_op`'s DB shows `payout_payer_operator_xonly_pk == victim_op.signer.xonly_public_key` via `get_payout_info_from_move_txid` — i.e., the DB-side of the binding now equals the attacker-forged value, while the funding-side of the binding (who actually paid) is the attacker, demonstrating the two sides of the equality no longer match.
6. Let `victim_op`'s `PayoutCheckerTask` run; assert it calls `handle_finalized_payout` and a kickoff connector is consumed (`used_kickoff_connectors` row inserted) for a payout `victim_op` never made.
7. (Optional, to demonstrate the exhaustion angle) Repeat until `num_kickoffs_per_round` kickoffs are consumed, then attempt to have `victim_op` service one genuine self-funded payout in the same round and assert it fails/cannot obtain a kickoff connector.

Note: I was unable to fully inspect the body of `Operator::handle_finalized_payout` (core/src/operator.rs) within the available tool budget, so the exact mechanics of kickoff-connector consumption and the reimbursement payment source could not be fully traced end-to-end; the root-cause defect (unauthenticated OP_RETURN-based attribution in `update_finalized_payouts`) is directly confirmed by code, but the precise downstream consequence (resource exhaustion vs. unwarranted reimbursement credit) should be validated with the PoC above before remediation prioritization.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
