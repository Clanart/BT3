## Analysis

The external report's core pattern: a per-entity cached config value (an address) becomes stale after an admin-driven update because the propagation logic that's supposed to keep it in sync doesn't actually reach every dependent instance — and the consuming code has no fallback, so it fails/misbehaves against the stale value.

The closest local analog is in the intents-coprocessor governance flow that keeps `IntentGatewayV2`'s cross-chain peer registry (`_instances`, keyed by state-machine ID) in sync across chains.

### Title
Faulty "same-address" skip in `add_deployment` leaves peer gateway registries unpopulated, permanently blocking cross-chain escrow release — ([File: modules/pallets/intents-coprocessor/src/lib.rs])

### Summary
`add_deployment` in the intents-coprocessor pallet is responsible for notifying every already-registered `IntentGatewayV2` instance whenever a new chain deployment is added, so each gateway's `_instances[keccak256(chain)]` mapping stays current [1](#0-0) . It skips the notification whenever the new gateway's address happens to equal an existing peer's address:

```rust
if existing_state_machine == state_machine
    || existing_gateway_info.gateway == gateway
{
    continue;
}
``` [2](#0-1) 

This assumes address-equality implies the peer "already knows" about the new chain, but `_instances` is keyed by **state-machine ID**, not by address [3](#0-2) . Under the documented deployment pattern, every `IntentGatewayV2` is deployed via CREATE2 with the same salt so all chains share one identical address [4](#0-3) . In that (intended/common) configuration, the skip condition is true for essentially every existing peer, so **no** peer ever receives the `AddDeployment` notification for the new chain, and `_instances[keccak256(newChain)]` stays at `address(0)` on all of them.

### Finding Description
Authentication of incoming cross-chain requests strictly requires an exact registered entry:
```solidity
function _authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (_instance(request.source) != module) revert Unauthorized();
}
``` [5](#0-4) 
and `instance()` reverts with `UnknownInstance` when nothing is registered for that chain (confirmed by the test suite, which expects a revert for an unregistered chain before `_addDeployment` runs) [6](#0-5) . The only writer of `_instances` is `_addDeployment`, invoked exclusively via a `NewDeployment` governance message [7](#0-6) [8](#0-7) . If the pallet never dispatches that message to a peer (because of the address-equality skip), that peer's `_instances` entry for the new chain is never populated — a stale/never-set reference analogous to the reused `RoyaltyManager` holding the outdated `swapProxy`.

Escrowed order inputs are released only through `RedeemEscrow`/`RefundEscrow` messages that pass `_authenticate` [9](#0-8) ; and outgoing dispatch to a peer is built from `_instance(order.source)` [10](#0-9) . With the entry missing, both directions fail for any order whose `source`/`destination` is the newly added chain, on every gateway that was skipped during propagation.

### Impact Explanation
Once a user's order is escrowed with `source` = the newly-added chain and it is later filled cross-chain, the solver's `RedeemEscrow` (or an expiry `RefundEscrow`) message targeting the source-chain gateway is rejected with `Unauthorized`/reverts, because the source chain's `_instances` mapping never learned the new chain's gateway address. There is no alternate function to force-release `_orders[commitment][token]`, so the user's escrowed tokens are permanently locked — this is a loss/lock-of-funds outcome, not merely a relayer/DoS nuisance, and it is triggered by the intended governance flow rather than by a malicious admin, relayer, or prover.

### Likelihood Explanation
Medium: this occurs under the codebase's own documented and default deployment pattern — identical CREATE2 addresses across all chains (as set up explicitly in `DeployIntentGateway.s.sol`) — meaning the flawed skip condition is the *common* case whenever governance onboards a new chain, not a rare edge case.

### Recommendation
Drop the `existing_gateway_info.gateway == gateway` shortcut, or replace it with a check keyed on whether the *specific* `(existing_state_machine, state_machine)` pair has already been synchronized — since the correctness-relevant identity in `_instances` is the state-machine ID, never the raw address. Always dispatch `AddDeployment` to every other registered gateway when a new deployment is added, regardless of address equality.

### Proof of Concept
1. Governance deploys `IntentGatewayV2` on Chain A and Chain B with the same CREATE2 salt, so both have address `G`; `add_deployment(ChainA, G, params)` registers Chain A with an empty peer set (no notification needed yet).
2. Governance later adds Chain C, also deployed at the same address `G`: `add_deployment(ChainC, G, params)`.
   - Pallet inserts `Gateways[ChainC] = {gateway: G, ...}`.
   - Loop reaches the Chain A entry: `existing_gateway_info.gateway (G) == gateway (G)` → `continue` — Chain A is never told about Chain C.
3. On Chain A's gateway, `_instances[keccak256(ChainC)]` remains unset.
4. A user places an order with `source = ChainA`, `destination = ChainC`; a solver fills it on Chain C, and Chain C's gateway dispatches `RedeemEscrow` back to Chain A.
5. On Chain A, `onAccept` → `_authenticate` calls `_instance(ChainC)`, which was never populated, so authentication fails and the message reverts.
6. The relayer cannot deliver `RedeemEscrow`; the user's escrowed input tokens on Chain A stay locked in `_orders[commitment][token]` with no available recovery path.

Note: I was not able to inspect the exact body of `_instance()` (only inferred its revert-on-unset behavior from the test suite) before running out of tool iterations, so I cannot 100% confirm whether it reverts with `UnknownInstance` or returns `address(0)` in this path — either way, `_authenticate` cannot match `module` and the request is rejected.

		pub fn add_deployment(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			gateway: H160,
			params: IntentGatewayParams,
		) -> DispatchResult {
			T::GovernanceOrigin::ensure_origin(origin)?;

			// Store gateway info
			let gateway_info = GatewayInfo { gateway, params };

			Gateways::<T>::insert(state_machine, gateway_info);

			// Notify all existing gateways about the new deployment
			// Only notify gateways with different addresses (same address automatically accepts)
			for (existing_state_machine, existing_gateway_info) in Gateways::<T>::iter() {
				// Skip if same state machine or same gateway address
				if existing_state_machine == state_machine
					|| existing_gateway_info.gateway == gateway
				{
					continue;
				}

				// Prepare cross-chain request to notify existing gateway
				let new_deployment =
					types::NewDeployment { chain: state_machine.to_string().into_bytes(), gateway };
				let request = RequestKind::AddDeployment(new_deployment);
				let body = request.encode_body();

				// Dispatch cross-chain message (ignore errors to not fail the whole operation)
				let _ = Self::dispatch(existing_state_machine, existing_gateway_info.gateway, body);
			}

			Self::deposit_event(Event::GatewayDeploymentAdded { state_machine, gateway });

			Ok(())
		}
