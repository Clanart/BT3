The bug class here is "insufficient policy enforcement allowing bypass of intended restrictions." Let me check the Bitcoin signing path and FROST preprocess handling for a reachable analog.### Title
Fee and standardness policy computed on a transaction omitting the OP_RETURN data output — an attacker-controlled `data` payload bypasses the minimum-fee and maximum-weight restrictions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` enforces Bitcoin relay policy (dust limits, `DEFAULT_MIN_RELAY_TX_FEE`, `MAX_STANDARD_TX_WEIGHT`) as "insufficient policy enforcement," directly analogous to CVE-2020-6432's bypassed navigation restrictions. The size/weight measurement in `calculate_weight_vbytes` is performed over `payments` only, while an `OP_RETURN` output carrying up to 80 bytes of externally influenced `data` is pushed into `tx_outs` before the measurement and never included in it. The resulting signed transaction is larger than measured, underpays its fee relative to the requested `fee_per_vbyte` and the minimum relay fee, and can exceed the standard transaction weight limit — producing a transaction the network will not relay or that gets stuck, leaving scanned funds unspendable.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 193–202, *before* `calculate_weight_vbytes(tx_ins.len(), payments, None)` is invoked at line 204. That function builds a fresh `Transaction` using only `payments` (plus optional change) — it never sees the data output [1](#0-0) .

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` at line 206 is computed on a vbytes value missing ~11 + 80 = ~91 vbytes (output base + script + pushdata) when `data` is present. The actual broadcast transaction therefore pays a lower effective fee rate than requested [2](#0-1) .
2. The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes`, again using the under-measured `vbytes`. A transaction whose true vsize pushes its fee below the relay minimum passes the check.
3. The same omission occurs in the change-aware recomputation at lines 224–235, which also calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — the OP_RETURN output is excluded there too, so `fee_with_change` is likewise understated.
4. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` from the same incomplete measurement, so a transaction whose true weight exceeds the standardness limit is accepted and signed [3](#0-2) .

The `data` field carries the Serai InInstruction payload, which is influenced by an unprivileged external depositor (their on-chain instruction bytes determine the refund/metadata content), so the size delta is attacker-influenced within the 80-byte cap checked at line 171.

### Impact Explanation
The policy checks exist to guarantee the produced transaction is standard and adequately fee'd. Because the OP_RETURN output is invisible to `calculate_weight_vbytes`, all three guarantees are violated simultaneously: the transaction can pay under the minimum relay fee, pay less than the caller-requested `fee_per_vbyte`, and exceed `MAX_STANDARD_TX_WEIGHT` — in every case yielding a signed transaction that Bitcoin nodes reject or indefinitely delay. Since the consumed prevouts remain committed (`Prevouts::All` in `TransactionSignMachine::sign`), the multisig has signed for an unbroadcastable spend of real UTXOs, and any replacement requires reconstructing/signing a new plan — funds are effectively frozen in the interim.

### Likelihood Explanation
Any `data` payload triggers the undercount; the impact scales with payload length up to 80 bytes. Reaching a non-standard or sub-minimum-fee transaction requires `data` of sufficient length to push the true vsize/weight across a boundary — deterministic once the caller supplies data near the cap. Inputs are reachable via transaction data an unprivileged party causes the system to carry (deposit InInstructions). Severity is Medium: no key recovery or forgery, but funds can be rendered unbroadcastable.

### Recommendation
Include the data output in the measurement: build the OP_RETURN `TxOut` first and pass all outputs (payments + data + optional change) into `calculate_weight_vbytes`, so `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check reflect the actual signed transaction. Alternatively, extend `calculate_weight_vbytes` to accept the final `tx_outs` vector.

### Proof of Concept
```rust
// networks/bitcoin: construct a SignableTransaction whose true vsize is
// ~91 vbytes larger than what the fee and weight checks measured.
let data = vec![0u8; 80]; // max permitted by the len check
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), fee_per_vbyte)?;

// tx.needed_fee() == fee_per_vbyte * vbytes(payments+change only)
// tx.transaction().weight() includes the OP_RETURN output and is strictly larger;
// the true fee rate is therefore below fee_per_vbyte, and can fall below
// DEFAULT_MIN_RELAY_TX_FEE or exceed MAX_STANDARD_TX_WEIGHT while passing all checks.
```
Specifically, choose `payments` such that `weight_without_opreturn == MAX_STANDARD_TX_WEIGHT`; the accepted transaction then violates standardness, or choose `fee_per_vbyte` so `needed_fee` meets the minimum on the measured vsize but not on the real one.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
