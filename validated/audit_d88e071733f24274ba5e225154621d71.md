## Finding

The CKB bug pattern is: an operation is built assuming a set of referenced objects (dep-cells) will still exist, and when the underlying set changes concurrently, the pool doesn't validate that every dependency is still present, silently degrading state instead of failing safely. GitHub Desktop's interactive-rebase-based `squash`/`reorder` git helpers show the same class of flaw against commit SHAs instead of cell deps.

### Title
Squash/Reorder silently drops selected commits when the underlying commit log changes between selection and execution - ([File: app/src/lib/git/squash.ts])

### Summary
`squash()` and `reorder()` build a git interactive-rebase "todo" file by matching a caller-supplied set of target commit SHAs (`toSquash`/`toMove`) against a freshly re-queried commit range (`getCommits(repository, revRange(lastRetainedCommitRef, 'HEAD'))`). The functions only validate that the "anchor" commit (`squashOnto` / `beforeCommit`) is present in that range; they never verify that every commit in `toSquashShas`/`toMoveShas` was actually matched and written to the todo file. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The commits to squash/reorder are captured in the UI at selection time (`commit-list.tsx`), then travel through an async, multi-step dispatcher flow that can include a `WarnForcePush` confirmation dialog before the actual git operation runs. [5](#0-4) 

Between commit selection and the eventual call into `squash()`/`reorder()`, the local repository's commit graph can legitimately change out from under the operation — most notably via Desktop's periodic `BackgroundFetcher`, which runs automatically while a repository is selected and can fast-forward or otherwise update local branch state as part of `_refreshRepository`/`fastForwardBranches`. [6](#0-5) [7](#0-6) 

When `squash()`/`reorder()` finally runs, it re-fetches the commit range and iterates it, adding a commit to the todo file only `if (toSquashShas.has(commit.sha))`. If one of the previously-selected commits is no longer present in the re-fetched range (its SHA changed or it was pruned/rewritten by the intervening operation), the loop simply never emits a `pick`/`squash` line for it — there is no assertion such as "all N commits in `toSquashShas` were consumed." Only the presence of the anchor commit (`squashOnto`/`beforeCommit`) is checked before proceeding: [8](#0-7) [9](#0-8) 

Because interactive rebase drops any commit not listed in the todo, the missing commit is permanently discarded from history the moment `rebaseInteractive` runs, while `result` still reports `RebaseResult.CompletedWithoutError` — this is functionally identical to CKB silently invalidating transaction A instead of surfacing/handling the broken dependency.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits path: a user-selected commit can vanish from history without any error dialog, warning, or opportunity to recover, because the success path (`RebaseResult.CompletedWithoutError`) is indistinguishable from the case where nothing went wrong. Since Desktop's flow for squash/reorder explicitly recommends `askForConfirmationOnForcePush`/`WarnForcePush` for pushing rewritten history, a user could then force-push a branch that is missing a commit they believed was preserved, propagating the loss to the remote.

### Likelihood Explanation
The race window is real but narrow: it requires local repository state affecting the specific SHAs in `toSquash`/`toMove` to change between the time the user selects commits in `commit-list.tsx` and the time `_squash`/`_reorder` actually executes (which includes an async `warnAboutRemoteCommits` check and possible confirmation dialog wait). Background fetching, a concurrent pull/rebase, or an external `git` operation on the same working copy performed while the operation is pending are all plausible triggers. There is no explicit lock preventing other refresh/fetch activity while the multi-commit-operation popup is open.

### Recommendation
In both `squash()` and `reorder()`, track how many of `toSquashShas`/`toMoveShas` were actually matched while walking `commits`, and if the count doesn't equal `toSquash.length`/`toMove.length` after the loop, throw (mirroring the existing `!foundSquashOntoCommitInLog`/`!foundBaseCommitInLog` guards) instead of silently proceeding to `rebaseInteractive`.

### Proof of Concept
1. Open a repository in Desktop with local commits `A, B, C` (oldest to newest) on a branch.
2. In the History view, select `A` and `C` to squash onto `B`, triggering the `WarnForcePush` confirmation dialog (`askForConfirmationOnForcePush` enabled).
3. While the dialog is open, from outside Desktop (or via a concurrent Desktop-triggered fetch/rebase) alter commit `A`'s SHA — e.g., `git rebase -i` it away or let a background pull rewrite it — so that by the time the dialog is confirmed, `A`'s original SHA is no longer part of the range returned by `getCommits(repository, revRange(lastRetainedCommitRef, 'HEAD'))`.
4. Confirm the dialog; `_squash` calls `squash()` in `app/src/lib/git/squash.ts`.
5. Observe: `squashOnto` (`B`) is still found, so no error is thrown; the loop only ever matches the still-present `C`, so the todo file contains just `pick B` and `squash C`. `A` is silently omitted and dropped by the interactive rebase, yet `RebaseResult.CompletedWithoutError` is returned and no warning is shown to the user.

export async function fastForwardBranches(
  repository: Repository,
  branches: ReadonlyArray<ITrackingBranch>
): Promise<void> {
  if (branches.length === 0) {
    return
  }

  const refPairs = branches.map(branch => `${branch.upstreamRef}:${branch.ref}`)

  await git(
    [
      'fetch',
      '.',
      // Make sure we don't try to update branches that can't be fast-forwarded
      // even if the user disabled this via the git config option
      // `fetch.showForcedUpdates`
      '--show-forced-updates',
      // Prevent `git fetch` from touching the `FETCH_HEAD`
      '--no-write-fetch-head',
      // Take branch refs from stdin to circumvent shell max line length
      // limitations (mainly on Windows)
      '--stdin',
    ],
    repository.path,
    'fastForwardBranches',
    {
      // Fetch exits with an exit code of 1 if one or more refs failed to update
      // which is what we expect will happen
      successExitCodes: new Set([0, 1]),
      env: {
        // This will make sure the reflog entries are correct after
        // fast-forwarding the branches.
        GIT_REFLOG_ACTION: 'pull',
      },
      stdin: refPairs.join('\n'),
    }
  )
}
