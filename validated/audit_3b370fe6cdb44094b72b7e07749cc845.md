### Title
Fee and weight estimated without the OP_RETURN output, underpaying the intended fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee` and the standardness `weight` via `calculate_weight_vbytes`, but passes the caller's `payments` slice instead of the actual output list `tx_outs`. When `data` is supplied, an OP_RETURN output is pushed onto `tx_outs` before the fee/size calculation, so the estimated vbytes exclude the OP_RETURN output entirely. The signed transaction is therefore larger than estimated and pays a lower effective fee rate than `fee_per_vbyte` specified — an estimate computed from only part of the real composition, the same class as estimating a liquidation reward from only one side of a pool.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs):

1. `tx_outs` is built from `payments`, then — if `data` is provided — an OP_RETURN `TxOut` carrying up to 80 bytes of attacker-influenced data is appended [1](#0-0) .
2. The fee estimate then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, using `payments` — which does **not** include the OP_RETURN output — instead of `tx_outs` [2](#0-1) .
3. The minimum-relay-fee check is likewise performed against the underestimated `vbytes` [3](#0-2) .
4. When `change` is present, the second estimate also uses `payments` rather than the output list containing the OP_RETURN [4](#0-3) .
5. The final `weight` used for the `MAX_STANDARD_TX_WEIGHT` check is the weight *without* the data output when no change is added [5](#0-4) .

Because the OP_RETURN output carries zero value, `sum(inputs) - sum(outputs)` still equals `needed_fee`, but the real vsize exceeds the estimated `vbytes`, so the effective sat/vbyte rate is strictly lower than the `fee_per_vbyte` the caller committed to.

### Impact Explanation
A `SignableTransaction` carrying a `data` payload is signed by the FROST machines in this same file (`TransactionSignMachine::sign`, lines 373–397) and broadcast at an effective fee rate below the requested `fee_per_vbyte`. Depending on the data length (up to 80 bytes → ~90 extra vbytes) and the margin between `fee_per_vbyte` and the mempool minimum, the resulting transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` in real terms or be purged/non-propagating in congested fee markets, leaving vault outputs unspendable/unconfirmed until an entirely new signing round is executed. The weight underestimation also means a transaction can pass the `MAX_STANDARD_TX_WEIGHT` check while actually exceeding it once the OP_RETURN is included, producing a non-standard transaction that relays nowhere — funds committed to a txid the network will never accept.

### Likelihood Explanation
Any code path that constructs a `SignableTransaction` with `data: Some(...)` triggers this unconditionally; the discrepancy is deterministic and grows with the data length. It does not require market manipulation — merely inclusion of a data payload — but the magnitude of underpayment is bounded (~83 bytes of output), so the practical risk is realized when the requested fee rate is near relay/minimum thresholds or the mempool is congested. Given that it can produce a transaction no node will relay while Serai believes a valid spend was signed (funds effectively stuck pending a re-sign), this is a Medium-severity correctness/availability issue.

### Recommendation
Base the fee and weight computation on the actual outputs: pass `tx_outs` (or compute `calculate_weight_vbytes` after the OP_RETURN push, using the real `TxOut` list) at both call sites (lines 204 and 225). Alternatively, add a sanity check after constructing `self.tx` asserting `tx.vsize() <= needed_fee / fee_per_vbyte` (or recomputing `needed_fee` from `tx.weight()`), so the committed fee rate is guaranteed against the true serialized transaction.

### Proof of Concept
```rust
// networks/bitcoin context: build a SignableTransaction with data
let data = Some(vec![0xAA; 80]); // max allowed
let tx = SignableTransaction::new(
    vec![output],                 // ReceivedOutput with enough value
    &payments,
    Some(change_addr),
    data,
    fee_per_vbyte,
).unwrap();

// The estimate omitted the OP_RETURN output:
let estimated_vbytes = tx.needed_fee() / fee_per_vbyte;
let actual_vsize = u64::try_from(tx.transaction().vsize()).unwrap();
assert!(actual_vsize > estimated_vbytes); // ~83+ vbyte gap
// Effective rate = needed_fee / actual_vsize < fee_per_vbyte
```
Reading the code directly confirms this without execution: `tx_outs` gains the OP_RETURN at lines 194–202 while `calculate_weight_vbytes` is invoked with `payments` at lines 204 and 225, so any `data.is_some()` construction underestimates vsize by the size of that output.
