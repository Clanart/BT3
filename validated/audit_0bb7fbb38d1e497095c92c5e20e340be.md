### Title
Data race in Python C-extension `CMessage::composite_fields` / `child_submessages` weak-value maps under free-threaded (No-GIL) builds causes concurrent map corruption analogous to EVerest's `evse_soc_map` race - ([File: python/google/protobuf/pyext/message.cc])

### Summary
EVerest's CVE-2026-26072 is a data race where an unsynchronized `std::map<std::optional<...>>` (`evse_soc_map`) is concurrently mutated by independent event-driven callbacks (SoC update thread vs. powermeter/session-finished thread), corrupting the map's internal structure. The consuming-application analog in this Protobuf checkout is the Python C-extension's per-message weak-value caches (`CMessage::composite_fields` and `CMessage::child_submessages`, both typed `PyWeakValueMap`, lazily created via `LazyUniquePtr`), which are looked up and populated by `cmessage::GetFieldValue`/`InternalGetSubMessage` on every field access and mutation. In Python's free-threaded (`Py_GIL_DISABLED`) build these accessors run without the GIL serializing them, and the maps are shared, mutable, per-message state reachable from ordinary, bounded field access on a message produced by a public parse API (`ParseFromString`/message construction) called from multiple threads — exactly the "concurrent access to a shared map during otherwise-independent operations" invariant that failed in EVerest.

### Finding Description
`CMessage` stores two lazily-initialized weak-value maps that cache Python wrapper objects for sub-fields: [1](#0-0) 

The lazy pointer to the underlying `PyWeakValueMap` is managed by `LazyUniquePtr<T>`, which explicitly documents a benign "lose the race, delete the duplicate object" pattern for *creating* the map itself in free-threaded builds: [2](#0-1) [3](#0-2) 

That comment/implementation only addresses safe *construction* of the map object (via atomic compare-exchange), not safe *concurrent mutation of the map's contents* afterward — the underlying `PyWeakValueMap` itself is a plain map data structure accessed through `Get()`, i.e. once created, insertions/lookups into it are not shown to be protected by any lock in this path. This mirrors the EVerest bug precisely: the *container* (`evse_soc_map`) itself is a bare `std::map` with no internal synchronization, and correctness depends entirely on callers coordinating access — which they fail to do when a SoC-update callback races with a powermeter/session-finished callback.

Protobuf's own test suite (`thread_safe_test.py`) documents this exact class of bug as already known/reproducible in the pyext backend: [4](#0-3) 
and a second, closely related lazy-unpack race on `LazyField`: [5](#0-4) 
plus descriptor-table races reachable purely through read-only concurrent access to a parsed message's descriptor: [6](#0-5) 

The attacker-controlled value/trigger here is indirect: an ordinary client supplies a bounded serialized message (binary or JSON) through the public parse API; the *application* embedding protobuf then accesses fields of the resulting message object from more than one thread (a supported, documented Python usage pattern once the GIL is removed), which is the same "two independent, otherwise-legitimate consumers touching the same shared map concurrently" pattern as EVerest's SoC/powermeter/session-finished handlers touching `evse_soc_map`.

### Impact Explanation
If the underlying weak-value map's insert/lookup path is not fully lock-protected in the free-threaded build (only object *creation* is CAS-protected by `LazyUniquePtr::Get`), concurrent field access after parsing can corrupt the `composite_fields`/`child_submessages` maps, leading to dangling/incorrect cached wrapper pointers, use-after-free of Python sub-message objects, or crashes — the C/C++ integrity+availability impact class matches CVSS AC:H/PR:N/UI:N/S:U/C:N/I:N/A:H used for the EVerest CVE (no confidentiality impact, but integrity/availability of the process). This does not constitute a memory-growth/resource-exhaustion issue and requires no privileged access — only ordinary multi-threaded consumption of parsed messages, consistent with the exclusion rules.

### Likelihood Explanation
This only manifests in the free-threaded (`Py_GIL_DISABLED`) CPython build, which is new/opt-in, and requires the embedding application to actually share and concurrently touch the same `CMessage` object/field from multiple threads without its own locking — a realistic but non-default pattern. Protobuf's own test file explicitly documents these races as observed/reproduced (`testConcurrentGetFieldValueRace`, `testConcurrentLazyUnpackAndRead`, `testConcurrentDescriptorFileAccessDataRace`), which is strong internal evidence the condition is real and already tracked, though I could not fully verify from the indexed slices whether the actual map-mutation call inside `PyWeakValueMap`'s `Get`/insert path (as opposed to only the outer `LazyUniquePtr` creation) has since been fully mutex-guarded — `message.cc`'s `GetFieldValue`/`InternalGetSubMessage` bodies and `weak_value_map.h`'s internals were not retrievable in full from the index in this session.

### Recommendation
Audit `python/google/protobuf/pyext/weak_value_map.h`/`.cc` and every call site in `message.cc` that inserts into or looks up `composite_fields`/`child_submessages` (`cmessage::InternalGetSubMessage`, `GetFieldValue`, `SetCompositeField`, `MaybeReleaseSubMessage`) to confirm all mutations under `Py_GIL_DISABLED` are protected by the same synchronization primitive (not just the outer `LazyUniquePtr` construction). Ensure the existing `thread_safe_test.py` races are asserted as fixed (not merely reproduced) with deterministic pass/fail assertions rather than best-effort loops, and extend coverage to concurrent `composite_fields`/`child_submessages` mutation under the free-threaded build specifically.

### Proof of Concept
Not independently executed in this session (read-only index access). The existing regression test constitutes the closest available in-repo reproduction and should be run under `Py_GIL_DISABLED` CPython: [4](#0-3) 
i.e., construct a message, then spin up N threads that concurrently access `msg.optional_nested_message` (which triggers `GetFieldValue` → `InternalGetSubMessage` → `composite_fields.Get()` insertion) via a `threading.Barrier` to maximize the race window, and check for corruption/crash under ThreadSanitizer or a free-threaded interpreter build. I was unable to retrieve the full body of `cmessage::GetFieldValue`/`InternalGetSubMessage` in `message.cc` or the internals of `PyWeakValueMap` within the available tool budget to confirm definitively whether a lock is already held around the map mutation itself — this should be verified directly against the full file contents (recommend a full Devin session with file-system access to `python/google/protobuf/pyext/message.cc` and `weak_value_map.h`/`.cc` for exact line-level confirmation) before treating this as a confirmed unresolved bug rather than a plausible, test-suite-documented analog.

// A unique pointer that is initialized on first access. In a free-threaded
// build, this lazy initialization is thread-safe.
//
// To avoid blocking, this class does not wait if anonther thread is
// initializing the object. When this race condition occurs, both threads will
// create the object, and whichever thread loses the race will delete the object
// it created. For this reason, the constructor and destructor of T must not
// have any meaningful side effects.
template <class T>
class LazyUniquePtr {
 public:
  LazyUniquePtr() = default;
  ~LazyUniquePtr();

  // Returns the pointer to the object if it has been initialized, otherwise
  // returns nullptr.
  //
  // Exercise caution when testing the return value against nullptr. Unless we
  // are being called from a mutating method (eg. msg.Clear()), this is a race
  // condition and the pointer could become non-null at any time.
  T* TryGet();

  // Returns the pointer to the object, initializing it if necessary.
  T* Get();

 private:
#ifdef Py_GIL_DISABLED
  std::atomic<T*> ptr_ = nullptr;
#else
  std::unique_ptr<T> ptr_ = nullptr;
#endif
};

template <class T>
T* LazyUniquePtr<T>::TryGet() {
  return ptr_.load(std::memory_order_acquire);
}

// Returns the pointer to the object, initializing it if necessary.
template <class T>
T* LazyUniquePtr<T>::Get() {
  T* instance = ptr_.load(std::memory_order_acquire);
  if (instance != nullptr) {
    return instance;
  }

  std::unique_ptr<T> obj(new T());
  return ptr_.compare_exchange_strong(instance, obj.get(),
                                      std::memory_order_release,
                                      std::memory_order_acquire)
             ? obj.release()
             : instance;
}

        threads.append(thread)
        thread.start()

  def testConcurrentDescriptorDeallocRace(self):
    """Tests descriptor cache interning under concurrent deallocation."""
    pool = descriptor_pool.DescriptorPool()
    file_proto = descriptor_pb2.FileDescriptorProto(name='race.proto')
    file_proto.message_type.add(name='RaceMessage')
    pool.Add(file_proto)

    barrier = threading.Barrier(10)
    errors = []

    def Worker():
      barrier.wait()
      for _ in range(500):
        try:
          d1 = pool.FindMessageTypeByName('RaceMessage')
          d2 = pool.FindMessageTypeByName('RaceMessage')
          if d1 is not d2:
            errors.append('Descriptor interning broken')
            break
          # Explicitly delete local references to trigger concurrent tp_dealloc
          del d1
          del d2

          errors.append(str(e))

    for t in threads:
      t.start()
    for t in threads:
