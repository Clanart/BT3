### Title
Attacker-controlled transactions trigger quadratic TXID recomputation during output scanning - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` recomputes the transaction’s TXID for every output matching a watched script, even though the value is constant for the transaction. [1](#0-0)  An attacker can send a transaction containing many outputs to a watched address, making scanning cost grow as `matching_outputs × transaction_size` rather than linearly with transaction size. [2](#0-1) 

### Finding Description
Inside the output loop, each matching `script_pubkey` constructs a `ReceivedOutput` using `OutPoint::new(tx.compute_txid(), vout)`. [2](#0-1)  `compute_txid` serializes and hashes the full transaction, so repeating it inside the loop makes the attacker-controlled output count multiply the cost of hashing the same attacker-controlled transaction. [3](#0-2)  `scan_block` accumulates these results across all transactions and returns them only after scanning completes, matching the delayed-burst resource-consumption pattern. [4](#0-3) 

### Impact Explanation
A transaction containing many outputs to a watched script can force an effectively quadratic amount of hashing work. [1](#0-0)  This can stall the scanning path and delay processing of the block’s accumulated outputs. [4](#0-3) 

### Likelihood Explanation
The attacker only needs to cause a scanned Bitcoin transaction to contain many outputs whose `script_pubkey` is already registered in `Scanner::scripts`; there is no per-output minimum-value check in this API before the expensive TXID calculation. [5](#0-4)  The attack scales directly with the number of matching outputs the attacker includes. [6](#0-5) 

### Recommendation
Compute the transaction ID once per transaction, lazily before the first `ReceivedOutput` is created or immediately before the output loop, and reuse that cached value for every matching `vout`. [2](#0-1)  This reduces scanning back to linear behavior without changing the returned `ReceivedOutput` values. [1](#0-0) 

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs

let watched_script = p2tr_script_buf(watched_key).unwrap();
let scanner = Scanner::new(watched_key).unwrap();

let tx = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![/* one valid input */],
  output: vec![
    TxOut {
      value: Amount::from_sat(1),
      script_pubkey: watched_script,
    };
    MATCHING_OUTPUTS
  ],
};

// Calls tx.compute_txid() once for every matching output.
let outputs = scanner.scan_transaction(&tx);
assert_eq!(outputs.len(), MATCHING_OUTPUTS);
```

Each iteration reaches `OutPoint::new(tx.compute_txid(), vout)`, so increasing `MATCHING_OUTPUTS` repeatedly hashes the same serialized transaction. [7](#0-6)

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
