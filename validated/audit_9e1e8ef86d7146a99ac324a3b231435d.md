### Title
Unbounded length-prefixed decode/re-encode loop in `SchnorrAggregate::read` enables remote CPU/memory denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::<C>::read` trusts a 32-bit little-endian length prefix and then loops that many times calling `C::read_G`, with no cap on the count, no check that the claimed count is consistent with the remaining input, and no streaming/early-abort bound. Each `read_G` call performs a full group decode (`G::from_bytes`) followed by a full re-encode (`to_bytes`) canonicality comparison — the exact "decode and re-encode without proper size limits" bug class from CVE-2026-73196 — and every decoded point is retained in a `Vec<C::G>`, so memory consumption grows linearly with the stream until exhaustion.

### Finding Description
The vulnerable code:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }

  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
``` [1](#0-0) 

Each iteration invokes `Ciphersuite::read_G`, which decodes the point and then re-encodes it for a canonicality check:

```rust
// crypto/ciphersuite/src/lib.rs:91-100
let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
  .ok_or_else(|| io::Error::other("invalid point"))?;
if point.to_bytes().as_ref() != encoding.as_ref() {
  Err(io::Error::other("non-canonical point"))?;
}
``` [2](#0-1) 

Notably, `read_G` performs two elliptic-curve operations per element: `from_bytes` (which internally decompresses/validates and re-computes the encoding) and `to_bytes` (a full affine conversion + serialization). So the attacker-purchased cost per 33 input bytes (secp256k1) is a point decompression plus a point recompression plus a heap `Vec` push that is never freed — a modest constant-factor CPU amplification and a ~4x memory amplification over the bytes received, with no upper bound other than `u32::MAX` iterations (~4 billion elements, hundreds of GiB of resident `C::G` values).

Contrast with the rest of the codebase, which was explicitly hardened against this class: `ThresholdKeys::read` bounds its loops by a `u16` participant count and validates `ThresholdParams` afterward [3](#0-2) , `Transaction::read` enforces `TRANSACTION_SIZE_LIMIT` before allocating [4](#0-3) , and `Call::read` in the Ethereum router chunks reads specifically noting "a valid DoS would be to claim a 4 GB data is present" [5](#0-4) . `SchnorrAggregate::read` is the one in-scope public deserializer accepting attacker-controlled bytes (`read`/`verify` API surface per the engagement scope) with a `u32` count and no limit.

### Impact Explanation
Any party that can cause a Serai-integrating verifier, coordinator, or processor to deserialize an untrusted `SchnorrAggregate` can degrade or kill the process:

- **Memory exhaustion**: `Rs` accumulates every decoded point for the lifetime of the read. For `Secp256k1`, each retained `ProjectivePoint` is ~112–144 bytes plus `Vec` overhead; a sustained malicious stream drives resident memory to OOM-kill levels. Unlike a one-shot oversized allocation (which `alloc` would fail fast), this is incremental growth that evades allocation-failure fast paths.
- **CPU exhaustion**: every element costs a decompression, subgroup/validity check, and a re-encode — expensive group arithmetic — proportional only to attacker-supplied bytes, with no pre-check that the input length is even plausible.
- Because `read` is `pub` and aggregate verification (`verify`, `multiexp_vartime` over `Rs`) also scales linearly in the retained vector, deserialization is not the only cost center — a successfully-read oversized aggregate then imposes a multiexp over millions/billions of pairs.

### Likelihood Explanation
- Reachability: `SchnorrAggregate::read` is a public deserialization API reachable wherever serialized aggregates transit an authenticated-but-untrusted channel — exactly the threat model the FROST/PedPoP pipeline assumes for all other `read_*` functions (every peer-supplied payload in the coordinator flows through `Read` impls). A single misbehaving or compromised signer, or any subsystem that persists/relays aggregate signatures, exposes it.
- No authentication, threshold collusion, or protocol position is required — only the ability to deliver a byte stream beginning with a large `u32` followed by valid (or even partially valid) point encodings.
- The issue is purely additive engineering debt: every sibling deserializer in the repo was given a bound; this one was not. Confidence is high that the unbounded loop exists; the residual uncertainty is whether the specific deployment path an attacker reaches it through (processor vs. coordinator vs. integrator) applies an outer message-size cap (e.g. `MAX_LIBP2P_REQRES_MESSAGE_SIZE` in `coordinator/src/p2p.rs` caps some transports). Where no outer cap applies, the flaw stands on its own.

### Recommendation
- Cap the aggregate size before reading: reject `len` exceeding a protocol-meaningful maximum (e.g., the number of co-signers in a transaction input, or a fixed constant like 2^16) before entering the loop, mirroring `TRANSACTION_SIZE_LIMIT` in `coordinator/src/tributary/transaction.rs`.
- Alternatively, pre-allocate with `Vec::with_capacity(len.min(SOME_SANE_CAP))` and fail fast if `len` exceeds the cap.
- Ideally, bound the read by actual remaining input (wrap the reader in `io::Read::take` with a computed byte budget: `len * size_of::<G::Repr>()`), so a lying length prefix cannot extend work beyond bytes actually transmitted.
- Apply the same audit to `verify`: reject `Rs.len() != keys_and_challenges.len()` early (already done) and consider an absolute cap on `keys_and_challenges.len()` before building the `multiexp` pair vector.

### Proof of Concept
```rust
use std::io;
use frost::curve::Secp256k1;
use schnorr::SchnorrAggregate;

// Attacker-controlled byte stream: u32 count prefix + repeated valid points.
// A single compressed generator encoding repeated for the claimed count.
fn malicious_stream() -> Vec<u8> {
    let mut buf = vec![];
    // Claim 4 billion Rs.
    buf.extend(u32::MAX.to_le_bytes());
    let g = {
        use ciphersuite::{group::GroupEncoding, Ciphersuite};
        <Secp256k1 as Ciphersuite>::generator().to_bytes()
    };
    // Even a modest number of real points forces read_G decode+re-encode
    // per element and grows Rs unboundedly; the loop only stops on read error.
    for _ in 0 .. 1_000_000 {
        buf.extend(g.as_ref());
    }
    buf
}

fn dos() -> io::Result<()> {
    let mut bytes = malicious_stream();
    let mut slice: &[u8] = &mut bytes;
    // Each iteration: 33 bytes in -> point decompress + recompress + Vec push.
    // With a streaming source (network reader), the vector grows until OOM.
    let _agg = SchnorrAggregate::<Secp256k1>::read(&mut slice)?;
    Ok(())
}
```

The 4-byte prefix permits up to `u32::MAX` iterations; nothing in `SchnorrAggregate::read` or `Ciphersuite::read_G` checks the claimed count against input size or a protocol bound, so an unprivileged sender who can stream bytes to this deserializer inflicts unbounded CPU (per-element decode + re-encode) and unbounded heap growth (retained `Vec<C::G>`), matching the CVE-2026-73196 pattern of resource exhaustion via unbounded decode/re-encode of attacker-sized input.
