## Finding: Confirmed

### Title
Hostname‑confusion in `parseRemote` lets an attacker‑crafted clone URL bind the user's signed‑in GitHub.com/Enterprise Account to a host git never actually contacts - (File: `app/src/lib/find-account.ts`)

### Summary
`findAccountForRemoteURL` trusts the `hostname` field produced by the hand‑rolled regex parser `parseRemote` [1](#0-0)  instead of a spec-compliant URL parser. Because the HTTPS regex uses `.` (which matches `/`) inside the greedy userinfo and host capture groups, a crafted URL can make the regex report a clean hostname such as `github.com` while the URI's real authority component — the part libcurl/git actually connects to — is a completely different attacker-controlled host.

### Finding Description
The HTTPS branch of the regex is:
```
'^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\\.git/?)?$'
``` [2](#0-1) 

`.` matches `/`, so both the optional userinfo group `(?:.+@)?` and the hostname group `(.+)` can span across path separators. For the input:

```
https://evil.com/@github.com/owner/repo.git
```

- Per RFC 3986/WHATWG URL rules, the authority ends at the **first** `/` after `//`. The real authority is `evil.com`; `/@github.com/owner/repo.git` is path, and the `@` inside it has no special meaning there. Git/libcurl will connect to `evil.com`.
- The regex, however, greedily matches `(?:.+@)?` as `evil.com/@` (up to the only `@` in the string), leaving `(.+)` to capture `github.com` as the "hostname" (with `owner`/`repo` correctly captured from the trailing two segments).

`parseRemote` therefore returns `{ hostname: 'github.com', owner: 'owner', name: 'repo' }` for a URL whose real target is `evil.com`.

`findAccountForRemoteURL` then does a strict comparison of this fabricated hostname against each signed-in account's endpoint hostname:
```js
allAccounts.find(a => {
  const htmlURL = getHTMLURL(a.endpoint)
  const parsedEndpoint = URL.parse(htmlURL)
  return parsedURL.hostname === parsedEndpoint.hostname
})
``` [3](#0-2) 

Since `parsedURL.hostname` is `github.com`, this matches the user's real, signed-in GitHub.com `Account` — even though the URL actually points at `evil.com`. This is the exact "wrong value" the review path asked to name: the function returns the GitHub.com `Account` object bound to a URL whose true authority is an unauthorized host.

### Impact Explanation
`findAccountForRemoteURL` is the mechanism `clone-repository.tsx` (and other callers) use to decide which stored account/token context to associate with a pasted or deep-linked clone URL [4](#0-3) . Any Desktop feature that trusts this result to determine "which endpoint this repository belongs to" (API calls, GitHubRepository association, autofill of an account for the URL) will be corrupted: the app believes the target is `github.com` while the resolved authority for actual git network operations is the attacker's host. Whether the OAuth token itself reaches the wrong host at the transport layer depends on the separate trampoline credential-helper path (`app/src/lib/trampoline/find-account.ts`, driven by `getCredentialUrl`/`new URL()` in `trampoline-credential-helper.ts` [5](#0-4) ), which parses the real authority correctly and was not shown to be affected by this same bug — I could not fully trace whether any code path feeds the `find-account.ts` result directly into credential injection without independent host validation, so I cannot confirm token exfiltration end‑to‑end, only the account/host binding corruption itself.

### Likelihood Explanation
The crafted string is a plain HTTPS URL a user could paste into "Clone repository" or receive via a link/deep link — no privileged action or local access is required, matching the in-scope attacker model (clicked link / attacker-controlled remote string).

### Recommendation
Replace the regex-based `parseRemote` HTTPS branch with parsing via the WHATWG `URL` class (or strictly anchor the userinfo/host groups to exclude `/`, e.g. `[^/@]+` for userinfo and `[^/]+` for host) so the extracted hostname always matches the true authority component that git will connect to, then re-run the existing hostname equality check in `findAccountForRemoteURL`.

### Proof of Concept
```ts
import { parseRemote } from '../../src/lib/remote-parsing'

const remote = parseRemote('https://evil.com/@github.com/owner/repo.git')
// remote.hostname === 'github.com'  (WRONG: real authority is evil.com)
// remote.owner === 'owner', remote.name === 'repo'
```
Feeding this string into `findAccountForRemoteURL` with a signed-in `github.com` account in `accounts` returns that account, even though `evil.com` is the actual host the resulting git operation will contact [6](#0-5) [7](#0-6) .
