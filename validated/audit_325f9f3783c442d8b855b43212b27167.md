Found a genuine bug: `stSTXbtc` and `zstSTXbtc` (asset IDs 10 and 11) are priced using the **STX/USD Pyth feed**, not a BTC/USD feed, despite `stSTXbtc` being a BTC-denominated liquid-staked token.

### Title
stSTXbtc and zstSTXbtc collateral/debt are priced off the STX/USD feed instead of BTC/USD - ([File: mainnet/contracts/proposals/mainnet/v0-init.clar])

### Summary
The asset registration for `stSTXbtc` (asset ID 10) and its vault receipt token `zstSTXbtc` (asset ID 11) in the mainnet init proposal wires their oracle `ident` to `STX-FEED-ID` (the STX/USD Pyth feed) instead of `BTC-FEED-ID`, even though `stSTXbtc` (ststxBTC) is a BTC-pegged/BTC-denominated liquid staking receipt token. The same wrong-feed wiring is mirrored in the `protocol-data.clar` read helper `get-asset-price`, which explicitly resolves `stSTXbtc`/`zstSTXbtc` prices via `PYTH-STX` with a comment claiming it is the "BTC price."

### Finding Description
In the mainnet initializer: [1](#0-0) 
asset ID 10 (`STSTXBTC-TOKEN`) and asset ID 11 (`.v0-vault-ststxbtc`, the zstSTXbtc vault token) are both inserted with `ident: STX-FEED-ID`, i.e. the STX/USD Pyth price feed, and `callcode: (some CALLCODE-ZSTSTXBTC)` for the vault token. There is no BTC feed or ratio transform applied anywhere in the callcode chain for this asset — `resolve-callcode` simply routes `CALLCODE-ZSTSTXBTC` straight to `resolve-ztoken p stSTXbtc`, multiplying the raw STX price by the vault's liquidity index: [2](#0-1) 

This is corroborated by the read-only helper in `protocol-data.clar`/`v0-1-data.clar`, which explicitly comments the STX feed as "BTC price" for this asset: [3](#0-2) 

Since STX and BTC have wildly different USD prices (BTC is orders of magnitude more valuable per unit), every USD notional computed for `stSTXbtc`/`zstSTXbtc` collateral and debt via `get-notional-evaluation` → `calculate-asset-notional-value` will use the STX price in place of the BTC price: [4](#0-3) 

### Impact Explanation
This is a "price attached to the wrong asset" bug in the pricing pipeline (mis-wired oracle `ident` for an asset, not a third-party oracle data problem — the STX feed itself is accurate, it is simply the wrong feed for a BTC-denominated asset). The direction of the error:
- `stSTXbtc`/`zstSTXbtc` collateral value is drastically **under-valued** in USD terms (STX price << BTC price), so users supplying this collateral get far less borrowing power than the true value of their BTC-denominated holdings — this is a freezing-of-funds/availability issue for depositors, not exploitable for profit by itself in that direction.
- However, if `stSTXbtc`/`USDC`/other assets can be **borrowed** against other collateral and repaid using this asset (or if `stSTXbtc` debt is valued this way), a borrower whose debt is denominated in `stSTXbtc` would have that debt valued using the (much lower) STX price instead of the true BTC price — massively understating their debt-to-collateral ratio and letting them borrow far more than their real BTC-denominated liability justifies, or evade liquidation entirely since `current-ltv` is computed from this wrong (deflated) debt-USD figure. This directly produces a wrong health verdict and enables theft of protocol funds by borrowing/keeping undercollateralized debt.

This lands on **Critical** (protocol insolvency / theft of funds at rest) if `stSTXbtc` is enabled as a debt asset, or at minimum a systemic mispricing that breaks health/liquidation logic for any position holding this asset as collateral or debt.

### Likelihood Explanation
This triggers automatically and deterministically on every price resolution for asset IDs 10/11 — no attacker action or oracle manipulation required beyond normal usage (supply/borrow/liquidate) of the `stSTXbtc` market once it is enabled with real liquidity. It is a configuration/wiring bug in the deployed init proposal rather than a runtime exploit primitive, but per the task's oracle-pricing-chain scope, it directly causes wrong USD prices feeding into health/liquidation verdicts.

### Recommendation
Wire `stSTXbtc` (asset ID 10) and `zstSTXbtc` (asset ID 11) to the correct BTC/USD Pyth feed (`BTC-FEED-ID`/`PYTH-BTC`) instead of `STX-FEED-ID`/`PYTH-STX` in both the mainnet init proposal and the `get-asset-price` helper, and add a governance-side/CI check that cross-references each registered asset's oracle `ident` against its expected underlying denomination to prevent this class of misconfiguration from being deployed again.

### Proof of Concept
1. Deploy/observe the mainnet init proposal registering asset 10 (`stSTXbtc`) and 11 (`zstSTXbtc`) with `ident: STX-FEED-ID`. [1](#0-0) 
2. Call `market.get-assets`/`price-resolve` for asset 10 or 11; observe the returned USD price equals `(STX/USD price) * liquidity-index`, not `(BTC/USD price) * liquidity-index`.
3. Supply `stSTXbtc` as collateral and observe `total-collateral-usd` computed in `get-notional-evaluation` is far lower than the true BTC-denominated value; conversely, if borrowing `stSTXbtc`/`zstSTXbtc` as debt is permitted, the resulting `total-debt-usd` and `current-ltv` are computed off the deflated STX price, allowing over-borrowing relative to the real BTC value of the debt without triggering `ERR-HEALTHY`/liquidation.

(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))

(define-private (resolve-callcode (p uint) (callcode (optional (buff 1))))
  (let ((cc (unwrap! callcode (ok p))))
    (if (is-eq cc CALLCODE-STSTX) (resolve-ststx p)
    (if (is-eq cc CALLCODE-ZSTX) (resolve-ztoken p STX)
    (if (is-eq cc CALLCODE-ZSBTC) (resolve-ztoken p sBTC)
    (if (is-eq cc CALLCODE-ZSTSTX) (resolve-ztoken (try! (resolve-ststx p)) stSTX)
    (if (is-eq cc CALLCODE-ZUSDC) (resolve-ztoken p USDC)
    (if (is-eq cc CALLCODE-ZUSDH) (resolve-ztoken p USDH)
