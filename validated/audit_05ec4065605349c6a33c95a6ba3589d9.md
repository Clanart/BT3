## Confirmed data flow

`applyPatchToIndex` (`app/src/lib/git/apply.ts`) fetches a **fresh** working-directory diff at commit time: [1](#0-0) 
and immediately builds the patch from that fresh diff combined with `file.selection`, an object whose diverging-line set is a set of raw **line indices** computed against whatever diff was loaded earlier in the UI: [2](#0-1) 

`formatPatch` never re-validates that those indices still correspond to the same textual content — it just asks `file.selection.isSelected(absoluteIndex)` for each line of the *newly fetched* diff: [3](#0-2) 

`DiffSelection` stores only integer line indices (`divergingLines: Set<number>`), with no binding to line content or hunk identity: [4](#0-3) [5](#0-4) 

`stageFiles` calls `applyPatchToIndex` per partially-selected file at commit time, using the `WorkingDirectoryFileChange` objects (with their UI-era selection) straight from the store: [6](#0-5) 

The store does try to prune stale selection indices, but only opportunistically when the Changes tab re-renders the diff (`updateChangesWorkingDirectoryDiff`), not at commit time, and only for the file currently selected in the UI: [7](#0-6) 
This reconciliation is skipped entirely for any file not currently open in the diff viewer, and there is no re-validation step inside `_commitIncludedChanges` before `createCommit`/`stageFiles` runs: [8](#0-7) 

### Title
Stale line-index reuse in partial-commit patch generation causes silent inclusion of unintended content - (File: app/src/lib/git/apply.ts)

### Summary
When a user stages only some lines of a file ("partial commit"), Desktop stores the selection as a set of line-index numbers, not as a binding to specific line content. At commit time, `applyPatchToIndex` re-runs `git diff` against the working directory and reuses those stale indices against whatever diff currently exists on disk. If the file's content changes between when the user made their line selection and when the commit executes — which an attacker who controls the working tree contents can trigger (e.g. via a `.gitattributes`-driven clean/smudge filter, a Git LFS hook, a `post-checkout`/`post-merge` hook shipped in a cloned/fetched malicious repository, or any background process editing the file) — the numeric line index selected by the user may now correspond to entirely different text.

### Finding Description
The invariant that should hold is: "the lines the user visually selected for commit are the lines actually included in the commit." This invariant is broken because `DiffSelection.isSelected()` operates purely on an integer offset within the unified diff (`app/src/models/diff/diff-selection.ts:121-136`), with no anchor to the underlying text. `formatPatch` (used for actual commits) and `applyPatchToIndex` blindly apply this stale selection to a diff that is fetched fresh from disk at staging time (`app/src/lib/git/apply.ts:60-61`, `app/src/lib/patch-formatter.ts:143-161`).

The only place Desktop attempts to keep selections consistent with diff content is `updateChangesWorkingDirectoryDiff` in `app-store.ts`, and it explicitly documents that it is *not* a full fix ("Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist") — it only recomputes the *selectable* set, and only for the single file currently displayed in the UI diff pane, on a background reload. It does nothing at commit time for files that are not the one currently open, and does nothing to re-map selection to content that shifted position (e.g. lines inserted above the previously selected region), only to lines that disappeared entirely.

A repository or file-content change controlled by an attacker — via `.gitattributes` filters, LFS smudge/clean scripts, or a git hook triggered by clone/checkout/merge — can rewrite tracked file contents on disk between the time the user reviews and checks specific diff lines in the Changes view and the time they click Commit. Because commit-time patch construction re-diffs the file but reuses old index-based selection state, the user's checked checkboxes end up applying to different content than what they visually reviewed.

### Impact Explanation
This breaks "silent corruption of what the user commits or pushes" — a listed valid impact category. A user can review and approve specific lines (e.g. excluding a secret or a malicious payload) in the diff viewer, but the actual commit created can include different lines than what was shown and approved, because the underlying working-tree content was altered by attacker-controlled tooling (filter/hook) in between. This can result in secrets or unintended lines being silently committed (and later pushed), or intended safety-relevant edits being silently dropped, without any error or warning to the user.

### Likelihood Explanation
This requires: (1) a repository under attacker influence that can rewrite tracked working-tree file content asynchronously (through `.gitattributes` clean/smudge filters, Git LFS pointers, or a hook executed on checkout/merge/fetch — all of which are legitimately part of a cloned/fetched repository's content, matching the described "attacker controls a cloned/fetched repository" primitive), and (2) a time window between the user selecting lines in the UI and clicking Commit, which is realistic in normal usage (the diff is loaded once per file-selection change; there's no re-diff triggered by every keystroke of hooks running in the background, e.g., during a slow smudge filter or an autosave triggered by another tool). Desktop does not re-validate selection content at commit time, so no user action beyond normal reviewing-then-committing is required, and no admin rights or local/physical access is needed.

### Recommendation
Bind `DiffSelection` to line content (e.g. a content hash or the actual line text) rather than raw numeric index, or re-diff and re-validate the selection immediately before staging/committing (not only on UI diff reload), rejecting or re-prompting the user if the diff has changed since the selection was made. At minimum, `_commitIncludedChanges` should re-fetch the diff for every file with a partial selection and confirm the previously-selected indices still refer to the same textual lines before calling `createCommit`.

### Proof of Concept
1. Attacker publishes a repository with a `.gitattributes` entry using a `filter.<name>.smudge` (or a `post-checkout`/`post-merge` hook) that rewrites `secret.txt` a few seconds after checkout/fetch, moving/inserting lines above the region the victim is about to review.
2. Victim clones the repo in Desktop, opens `secret.txt` in Changes, and selects a specific safe line to commit (unchecking a line containing a credential), using the diff line offset currently on screen.
3. Before the victim clicks "Commit", the filter/hook fires and rewrites the file content, shifting line offsets so that the previously-selected index now maps to the credential line instead of the safe line.
4. Victim clicks Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60-61`) re-diffs the now-changed file and `formatPatch` applies the stale index-based selection (`app/src/lib/patch-formatter.ts:143-161`), silently including the credential line the user believed was excluded.
5. The resulting commit (and any subsequent push) contains content the user never reviewed or approved, with no error shown by Desktop.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
