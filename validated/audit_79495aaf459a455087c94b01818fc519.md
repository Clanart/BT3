## Analysis

The external report's core pattern is: a code path that is supposed to be "safe" (either explicitly by fee schedule, or implicitly by expected invariant) skips the safe/guarded routine and lets an internal operation revert or execute out of order, breaking the invariant the caller relies on.

Searching for the closest local analog in fund-custody code, I found a concrete deviation between the canonical EVM Intent Gateway escrow-release logic and its Tron port.

**Canonical implementation** — `evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw()` decrements escrow accounting *before* making the external transfer (checks-effects-interactions): [1](#0-0) 

The docs also confirm the canonical `cancelOrder` entrypoint is `nonReentrant`: [2](#0-1) 

**Tron port** — `evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()` reverses this order: it performs the external `token.call(transfer(...))` (or native `.call{value:}`) *before* decrementing `_orders[commitment][token]`: [3](#0-2) 

Critically, `cancelOrder` on Tron is declared `public payable` with **no `nonReentrant` modifier**, unlike the canonical contract: [4](#0-3) 

And for same-chain orders, `cancelOrder` calls `withdraw()` directly — this is a **permissionless, non-host-gated** path (only `order.user == msg.sender` is checked), unlike the `RedeemEscrow`/`RefundEscrow` paths which are gated by `onlyHost`/`authenticate()`.

Because `order.inputs[].token` is an arbitrary, attacker-supplied address at `placeOrder()` time with no allowlist: [5](#0-4) 

an attacker can place a multi-asset order whose inputs include one legitimate token (e.g. USDC) and one malicious, attacker-authored "token" contract. When the attacker (as `order.user`) calls same-chain `cancelOrder`, execution enters `withdraw()`, which loops over `body.tokens`; on the malicious-token entry the external call transfers out funds and hands control to attacker code **before** `_orders[commitment][token]` is decremented for that entry, and **before the loop has even reached the other (real) token's decrement**. Because there is no `nonReentrant` guard anywhere in the Tron contract, this callback runs with the reentrancy lock absent — a structural regression from the canonical, audited implementation.

## Caveat

I verified the CEI-violation and the missing `nonReentrant` guard directly in code, and confirmed `_filled[commitment]` is set at the top of `withdraw()`, which blocks a *same-commitment* re-entry into `cancelOrder`/onAccept for that exact order. I was not able to fully trace, within the remaining budget, a second reachable function that reads/mutates `_orders[commitment][otherToken]` for the *same order* without checking `_filled`, which would be required to prove a full double-spend of the second (real) token within a single `withdraw()` call. This is the missing link between "confirmed reentrancy-guard regression + CEI violation" and "concretely proven fund drain," and it should be validated with a Foundry PoC against the Tron contract (deploy a malicious ERC20 as one order input alongside a real token, and attempt to re-enter any state-mutating function during the transfer callback) before treating this as fully proven.

### Title
Missing reentrancy guard and transfer-before-effects ordering in Tron IntentGatewayV2.withdraw() - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of the Intent Gateway's escrow-release routine (`withdraw`) sends tokens via a low-level external call before decrementing the corresponding `_orders[commitment][token]` escrow balance, and the public `cancelOrder` entrypoint that reaches this routine for same-chain orders carries no `nonReentrant` modifier — unlike the canonical EVM `IntentsBase._withdraw()`/`IntentGatewayV2.cancelOrder` (which decrement first and are `nonReentrant`).

### Finding Description
`withdraw()` sets `_filled[commitment]` first, then in a loop for each escrowed token performs `token.call(transfer(...))` (attacker-controlled if the input token is attacker-authored) and only afterward executes `_orders[commitment][token] -= amount`. Multi-asset orders (`order.inputs` is a `TokenInfo[]`) let an attacker pair one legitimate escrowed token with a self-authored malicious "token" contract in the same order. On self-initiated, same-chain cancellation (`cancelOrder`, callable directly by `order.user`, no `nonReentrant`), the malicious token's `transfer` implementation executes attacker code mid-`withdraw()`, while later entries in the same loop (including real-token balances) are still un-decremented and the reentrancy lock that the canonical contract relies on is absent entirely.

### Impact Explanation
This is a direct regression of a fund-safety invariant (checks-effects-interactions plus reentrancy guard) present in the reference implementation. Even where the most direct same-commitment re-entry is blocked by the early `_filled` write, the absence of `nonReentrant` combined with interaction-before-effects is a structural weakness in a contract that custodies user escrow, matching the bounty's "stealing or loss of funds" / "logic attacks" categories.

### Likelihood Explanation
Medium: the attacker needs only to author an arbitrary "token" contract and place a multi-asset order using it — both permissionless actions requiring no relayer, prover, or admin compromise. The remaining question is whether a second, unguarded state-mutating entrypoint can be reached during the callback window to realize a full fund drain, which requires further PoC work.

### Recommendation
Port the canonical pattern into the Tron contract: (1) add `ReentrancyGuard`/`nonReentrant` to `cancelOrder` and any other public entrypoint that can reach `withdraw()`, and (2) reorder `withdraw()` to decrement `_orders[commitment][token]` (and the `TRANSACTION_FEES` bucket) before making the external transfer call, matching `IntentsBase._withdraw()`.

### Proof of Concept
Not fully constructed within the available tool budget. Suggested PoC outline for a Devin session: deploy a malicious ERC20-like contract whose `transfer()` callback attempts to re-enter `IntentGatewayV2` (e.g. `placeOrder`, `select`, or a second `cancelOrder` on a different but related order); place a multi-input order pairing this token with a real ERC20; call `cancelOrder` as `order.user`; assert whether any state (`_orders`, `_filled`, dust/fee accounting) becomes inconsistent or whether funds can be extracted beyond the legitimately escrowed amount.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
