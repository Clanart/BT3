### Title

Unchecked Bitcoin amount arithmetic can panic or wrap when parsing/spending crafted `ReceivedOutput`s - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`ReceivedOutput::read` accepts an arbitrary consensus-encoded `TxOut`, including output amounts which are impossible on Bitcoin but valid within the decoder's `u64` representation. `SignableTransaction::new` then sums all provided output amounts without checked arithmetic. Crafted serialized `ReceivedOutput`s can therefore trigger integer overflow during transaction construction, causing a panic in checked builds or wrapped accounting in release builds.

### Finding Description

`ReceivedOutput::read` deserializes `output` directly with `TxOut::consensus_decode` and performs no monetary bound check before returning it. [1](#0-0)  `SignableTransaction::new` subsequently computes `input_sat` using `sum::<u64>()`, computes `payment_sat` the same way, and then adds `payment_sat + needed_fee` without checked arithmetic. [2](#0-1) [3](#0-2) 

This is the same class as the referenced ImageMagick issue: attacker-controlled extent/value arithmetic is consumed without checking that the arithmetic remains representable. Here, the unchecked domain is Bitcoin amounts rather than image offsets.

### Impact Explanation

A caller which accepts serialized `ReceivedOutput`s, or stores scanner/database-produced outputs and later reconstructs them through `ReceivedOutput::read`, can be crashed by a small crafted input containing values whose sum exceeds `u64::MAX`. In release builds where overflow wraps, the wrapped `input_sat` may also produce incorrect funding decisions rather than the intended `NotEnoughFunds` result. [4](#0-3) 

The result can be a transaction-construction denial of service or incorrect fee/funds accounting. Since real confirmed Bitcoin outputs cannot exceed consensus' money supply, exploitation through honestly validated chain outputs is not expected; the reachable case is untrusted serialized `ReceivedOutput` data accepted by the explicit `ReceivedOutput::read` API.

### Likelihood Explanation

The trigger is simple: provide at least two encoded `ReceivedOutput`s whose `TxOut.value` fields sum above `u64::MAX`, then pass them to `SignableTransaction::new`. No private key, validator cooperation, malformed curve encoding, or network privilege is required. However, deployment impact depends on the caller treating serialized `ReceivedOutput`s as attacker-controlled input rather than only accepting outputs obtained from `Scanner::scan_transaction` on validated Bitcoin blocks. [5](#0-4) 

### Recommendation

Use checked arithmetic for all monetary accumulation and fee calculations in `SignableTransaction::new`, including `input_sat`, `payment_sat`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and the minimum-fee multiplication. Return `NotEnoughFunds` or a dedicated overflow error on failure. Additionally validate decoded `TxOut` amounts against a protocol-appropriate bound if `ReceivedOutput::read` is intended for untrusted data rather than only previously validated chain data. [6](#0-5) 

### Proof of Concept

Conceptually, construct two serialized `ReceivedOutput` values with `offset = 0`, a valid `OutPoint`, and a `TxOut` whose `value` is `u64::MAX`. Parse each with `ReceivedOutput::read`, then call:

```rust
SignableTransaction::new(
  vec![received_0, received_1],
  &[(ScriptBuf::new(), 546)],
  None,
  None,
  1,
)
```

`input_sat` evaluates `u64::MAX + u64::MAX`, overflowing before funding checks execute. In checked builds this panics; in wrapping builds it produces `u64::MAX - 2`, allowing execution to continue using incorrectly wrapped input accounting. [7](#0-6)
