## Analog Found: Checks-Effects-Interactions violation in the Tron IntentGatewayV2 escrow withdrawal path

The Sandclock report's core primitive — an external call/callback firing *before* internal state is finalized, letting the same funds be pulled out again — has a direct, unfixed analog in the Tron fork of the intents contract.

### Title
Escrow double-withdrawal via reentrancy in `IntentGatewayV2.withdraw()` (Tron) — external transfer executed before escrow balance is decremented - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The main EVM intents implementation was hardened against reentrancy: `IntentsBase._withdraw` decrements the per-order escrow mapping *before* sending funds out. [1](#0-0) 
The `IntrinsicIntents._fillSameChain` fill path was also patched to write `_filled[commitment] = msg.sender` at the top of the function (CEI), specifically to close a reentrancy window during output token transfers, and a dedicated regression suite exists to prove it. [2](#0-1) [3](#0-2) 

However, the independently-maintained Tron variant of the same contract reverts to the vulnerable ordering: it performs the native/ERC20 transfer to `beneficiary` first, and only afterward decrements the escrow accounting.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the escrow release logic sends funds to the beneficiary via a raw `.call` (for both native ETH and ERC20, using low-level `token.call(...)` instead of `SafeERC20.safeTransfer`) and only decrements `_orders[body.commitment][token]` *after* that external call returns: [4](#0-3) 

Compare this to the corresponding function in the main EVM codebase, which correctly follows checks-effects-interactions: it sets `_orders[body.commitment][token] = escrowed - amount` *before* making the external `.call{value:}` or `safeTransfer`: [1](#0-0) 

Because the Tron version's `beneficiary` (or the ERC20 `token`, if it carries a transfer hook/callback) is attacker-influenced — beneficiaries are freely chosen by the order creator, and input/output tokens are arbitrary addresses supplied in the `Order` struct — a beneficiary contract can implement `receive()` (for native-token orders) or an ERC20-with-callback semantics, and reenter `withdraw`/`fillOrder`/`cancel` while `_orders[body.commitment][token]` still reflects the pre-transfer (undecremented) balance. Additionally, the guard at line 691 only checks `_orders[...][token] == 0` rather than validating `amount <= escrowed`, so a reentrant call can repeat the exact same withdrawal against the still-nonzero balance.

### Impact Explanation
An attacker who is the beneficiary of an escrowed order (a legitimate role in the protocol — beneficiaries of order outputs, refunds, or fee redemption) can re-enter the withdrawal path during the external transfer and drain the same escrowed token/native balance multiple times before `_orders[body.commitment][token]` is ever reduced. This is unauthorized extraction of bridge/escrow-held funds beyond what the attacker is entitled to — a direct fund-theft primitive, matching the "stealing or loss of funds" and "double-claim/double-settlement" categories in the bounty scope.

### Likelihood Explanation
This requires no privileged role, relayer, or prover compromise — any unprivileged user who places (or fills) an order and controls the beneficiary address (a normal, permitted configuration) can trigger it. The vulnerable pattern is a straightforward, un-guarded CEI violation identical in shape to the referenced Vault.sol bug, and the corresponding logic was already recognized as reentrancy-prone and fixed elsewhere in this same codebase, indicating the underlying invariant ("escrow balance must be zeroed before releasing it") is validated to matter in this protocol, but the Tron copy did not receive the fix.

### Recommendation
Apply the same checks-effects-interactions ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol`: decrement `_orders[body.commitment][token]` (and delete transaction fee entries) before performing any external call or token transfer in the Tron `withdraw` function. Additionally add a `nonReentrant` guard consistent with the fix pattern validated by `IntrinsicIntentsReentrancyTest.sol`, and replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer` for consistency and correctness on non-standard ERC20 return values.

### Proof of Concept
1. Attacker places/fills an order on the Tron-deployed `IntentGatewayV2` where `beneficiary` is a contract they control, and/or an input/output token is a token contract they control with a transfer callback.
2. When escrow release is triggered (`withdraw`), the contract calls `beneficiary.call{value: amount}("")` (native) or `token.call(transfer(...))` (ERC20) at [5](#0-4)  while `_orders[body.commitment][token]` still holds its pre-withdrawal value.
3. The attacker's `receive()`/callback re-enters the withdrawal entrypoint (or `fillOrder`/cancel path that routes into this same withdraw logic) before line 701 executes, and the `_orders[body.commitment][token] == 0` check at line 691 still passes because the balance has not yet been decremented.
4. The attacker repeats this to drain more of the escrowed token/native balance than was legitimately owed, before the single decrement at line 701 finally executes on unwind.

Note: I was unable to fully trace every call-site into this `withdraw` function (e.g., whether `fillOrder`/`cancelOrder` in the Tron contract also route through it with additional guards) before running out of investigation budget; the CEI-ordering flaw at lines 691–705 itself is directly confirmed from the code, but a complete call-graph confirmation of all reentry vectors would benefit from a deeper session.
