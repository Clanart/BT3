## Finding

### Title
Escrow ledger in `IntentGatewayV2.placeOrder` is not reconciled against actual token balance received, permanently locking escrow for fee‑on‑transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway credits `_orders[commitment][token]` with the *nominal* requested input amount (minus protocol fee) instead of the amount the contract actually received from `safeTransferFrom`. For any ERC-20 with transfer fees, deflationary/rebasing mechanics, or blacklist-style partial burns, the escrow ledger will record more tokens than the contract actually holds. This is the same broken invariant as the external report (`_amt` never checked against `_before`, the real available balance) — except here it corrupts a shared custody pool rather than a single strategy vault.

### Finding Description
In the non-predispatch escrow path of `placeOrder`: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`_orders[commitment][token]` is incremented by `reducedInputs[i].amount` — a value derived purely from the *nominal* `order.inputs[i].amount` the user asked to escrow — with no check of what the contract's balance actually changed by after `safeTransferFrom`. This is the exact “no check `_amt` value” bug class: the accounting value (`_amt`) is never capped to what the contract actually has available (`_before`/actual balance delta).

Contrast this with the fixed main-EVM version of the same contract, which explicitly guards against this: [2](#0-1) [3](#0-2) 

```solidity
// Phase 1: Transfer tokens and record actual received amounts.
// For fee-on-transfer tokens, the gateway receives less than the requested amount.
// We mutate order.inputs to reflect actual received so the commitment and escrow
// are consistent with what the gateway holds.
...
} else {
    uint256 balBefore = IERC20(token).balanceOf(address(this));
    IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
}
```

The main EVM contract measures the actual balance delta and re-derives the commitment/escrow from it, so the ledger can never exceed custody. The Tron contract skips this reconciliation entirely, so `sum(_orders[*][token])` can silently exceed `IERC20(token).balanceOf(address(this))` for any token that doesn't transfer 1:1.

Later, at settlement, `withdraw()` pays out strictly from the ledger without ever checking the contract's live balance: [4](#0-3) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
        _orders[body.commitment][token] -= amount;
```

There is no `if (amount > balanceOf(this)) amount = balanceOf(this)` guard analogous to the report's recommended `if (_amt > _before) { _amt = _before; }`.

### Impact Explanation
Because escrow is a shared pool (all commitments' balances for a given token live in the same contract balance), under-collateralization caused by fee-on-transfer tokens means the contract cannot ever fully honor every commitment's ledger entry for that token. Orders that settle earlier (`RedeemEscrow`/`RefundEscrow`/same-chain fill or cancel) drain real balance according to their full nominal ledger amount; orders that settle later for the same token can have their `withdraw()` calls permanently revert (`TransferFailed`/`InsufficientNativeToken`-style paths) once actual balance is depleted below their entitled amount — the funds become permanently locked with no recovery path, since `withdraw()` has no partial-payout or balance-capping fallback. This is a genuine, unprivileged, protocol-level fund-loss/lock condition, not merely a functional inconvenience — it requires no malicious relayer, prover, or admin, only an ordinary user placing an order with an off-the-shelf fee-on-transfer ERC-20 as `order.inputs[i].token`.

### Likelihood Explanation
`order.inputs[i].token` is fully attacker/user-controlled at `placeOrder` — any ERC-20 address can be specified, including fee-on-transfer, deflationary, or otherwise non-1:1-transfer tokens (a well-known and common token category). No special privileges, timing races, or cooperating relayers are needed; a single `placeOrder` call using such a token is sufficient to desynchronize the ledger from custody. The bug is deterministic and reproducible on every call involving such a token, and the main-EVM sibling contract's explicit fix (measuring `balanceOf` delta) confirms the maintainers were aware of and intended to guard against exactly this condition — but the guard was not carried over to the Tron implementation.

### Recommendation
Mirror the main EVM contract's fix in the Tron variant of `IntentGatewayV2.sol`: measure the actual token balance delta after every `safeTransferFrom` (and for native transfers, after any intermediate call-dispatcher hop) and use that measured amount — not the nominal requested amount — both to compute the order commitment and to credit `_orders[commitment][token]`. Additionally, as defense in depth, cap `withdraw()`'s per-token transfer amount to the contract's live balance for that token (analogous to the reported `if (_amt > _before) { _amt = _before; }` pattern) so that even any residual accounting drift degrades to a partial payout rather than an unrecoverable revert.

### Proof of Concept
1. Deploy (or pick) an ERC-20 token that charges a transfer fee, e.g. 5% burned/redirected on every `transfer`/`transferFrom`.
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FeeToken, amount: 1000}` and no predispatch. `safeTransferFrom(user, gateway, 1000)` only lands `950` tokens on the gateway (5% fee), but `_orders[commitment][FeeToken] += reducedInputs[0].amount` still credits the full (fee-bps-adjusted) nominal `1000`-based amount.
3. Repeat with a second, unrelated order using the same `FeeToken`, again crediting nominal amounts to `_orders[...]` while real balance accrues at only 95% of nominal.
4. Fill/cancel the first order — `withdraw()` successfully transfers its full nominal ledger amount, drawing down more of the contract's actual `FeeToken` balance than that order actually contributed.
5. Attempt to fill/cancel the second order — the gateway's real `FeeToken` balance is now insufficient to cover the second order's full nominal ledger amount; `token.call(transfer(...))` fails, `withdraw()` reverts with `TransferFailed`, and the second user's/solver's funds are permanently unrecoverable through the normal settlement path.
