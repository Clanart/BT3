### Title
`SignableTransaction::new` excludes the `OP_RETURN` data output from fee/vsize accounting, so attacker-controlled `data` can push the effective fee rate below the relay minimum and block the spend - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output carrying `data` (up to 80 bytes, attacker-influenced via InInstruction payloads) onto `tx_outs`, but calls `calculate_weight_vbytes` only with `payments` — which does not include the OP_RETURN output. The computed `needed_fee` therefore underestimates the real virtual size, and the effective fee rate of the signed transaction is lower than requested, potentially below `DEFAULT_MIN_RELAY_TX_FEE`, causing the transaction to be rejected by Bitcoin nodes' mempool policy. Analogous to the reported issue, a strict/incorrect requirement on a peripheral field silently breaks a core funds-movement path for reachable, attacker-controllable inputs.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` accepts `data: Option<Vec<u8>>` bounded to 80 bytes (`send.rs:171-173`) and appends `ScriptBuf::new_op_return(...)` to `tx_outs` (`send.rs:194-202`). However, both weight/vsize estimates — `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204` and the `fee_with_change` recomputation at `send.rs:225-227` — build their template `Transaction` only from `payments` and the optional change output (`send.rs:85-99`). The OP_RETURN output is never included in the template, so `vbytes` (and hence `needed_fee = fee_per_vbyte * vbytes`, `send.rs:206`) undercounts the final transaction's size by roughly `data.len() + ~11` bytes (~91 vbytes at the cap), nearly all of it non-witness weight.

The `TooLowFee` check at `send.rs:211` also uses this underestimated `vbytes`, so a transaction that will actually violate the minimum relay fee rate still passes validation. Since `fee()` is `sum(inputs) - sum(outputs)` (`send.rs:138-141`) and outputs are fixed before signing, there is no post-hoc correction: the signed transaction broadcasts a fee rate lower than `fee_per_vbyte` intended.

### Impact Explanation
Any consumer feeding a `data` payload into `SignableTransaction::new` produces a transaction whose real fee rate is below the requested `fee_per_vbyte`. When the processor operates near the minimum relay rate (e.g., `fee_per_vbyte = 1`), a ~90-vbyte discrepancy on a small transaction can drop the effective rate below `bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE`, so `send_raw_transaction` is rejected as non-standard and the spend is blocked — the vault's BTC becomes temporarily unmovable through normal relay, mirroring the "deposit functionality broken for non-conforming input" impact of the reference report.

### Likelihood Explanation
The `data` field is populated from user-supplied InInstruction payloads, so its length is attacker-influenced and can be maximized (80 bytes) at will. Whether the underestimate crosses the relay-fee boundary depends on the configured `fee_per_vbyte` and total transaction size; for small transactions (1 input, 1–2 outputs, ~150–200 vbytes) at low fee rates, ~90 vbytes is a 30–60% underestimate. The flaw is deterministic — no race or adversary timing is needed — but the security outcome (mempool rejection vs. merely overpaying change) depends on fee configuration, placing this at Medium.

### Recommendation
Include the `OP_RETURN` data output in the template transaction used by `calculate_weight_vbytes`. Concretely, pass the fully-constructed `tx_outs` (or the data length) into the weight calculation at `send.rs:204` and `send.rs:226`, so `needed_fee`, the `TooLowFee` check, and the change-amount computation at `send.rs:228-234` all account for the data output. Alternatively, compute `needed_fee` from the finalized `Transaction`'s `weight()`/`vsize()` after all outputs (payments, OP_RETURN, change) are assembled.

### Proof of Concept
```rust
// networks/bitcoin context
let inputs = vec![received_output];            // any spendable ReceivedOutput
let payments = [(payment_script, 10_000u64)];  // one small payment
let data = Some(vec![0xaa; 80]);               // max-size InInstruction payload

let tx = SignableTransaction::new(inputs, &payments, None, data.clone(), 1).unwrap();
// needed_fee was computed as 1 * vbytes(payments only)
// actual tx includes an extra OP_RETURN output of ~91 vbytes
let actual_vsize = tx.transaction().vsize() as u64;
assert!(actual_vsize > tx.needed_fee());
// effective fee rate = tx.fee() / actual_vsize < 1 sat/vB
// -> rejected under DEFAULT_MIN_RELAY_TX_FEE policy on broadcast
```

Limitations I could not fully verify within the available iterations: whether `processor`'s production call sites always pass `fee_per_vbyte` comfortably above the relay minimum (mitigating the mempool-rejection outcome to mere overpayment into fee), and how `data` length is bounded upstream of the processor's bitcoin network code. The size-accounting defect itself is confirmed directly in `send.rs:194-235`.
