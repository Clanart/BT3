### Title
`unvote()` incorrectly requires `pool.isActive == true`, permanently trapping user stake/votes once a pool is deactivated - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.unvote()` reverts with `PoolNotActive()` whenever `pool.isActive` is `false`, which is the exact opposite of its documented purpose ("Unvote from an inactive pool... doesn't block users from withdrawing"). Since `vote()` also requires `pool.isActive == true` to modify a user's position, and `BribeRewardPool.withdrawFor`/`stakeFor` are `onlyOperator` (only callable by `WombatBribeManager`), any user who voted for a pool that is later deactivated has no way to reduce `userVotedForPoolInVlmgp` or withdraw their staked position from the rewarder.

### Finding Description
`vote()` checks `if (!pool.isActive) revert PoolNotActive();` before modifying `userVotedForPoolInVlmgp` and calling `IBribeRewardPool(pool.rewarder).stakeFor`/`withdrawFor` [1](#0-0) . `unvote()` has the same check, but the intent (per the NatSpec comment) is to let users exit an inactive pool: `if(!pool.isActive) revert PoolNotActive();` reverts precisely when the pool is inactive, blocking the exit instead of enabling it [2](#0-1) .

The only functions that can reduce a user's staked balance in `BribeRewardPool` are `stakeFor`/`withdrawFor`, both gated by `onlyOperator` (the operator being `WombatBribeManager`) [3](#0-2) . There is no other public entry point in `BribeRewardPool` for a user to withdraw directly. Once `owner`/pool manager sets `pool.isActive = false` for a pool a user has already voted on, that user's `userVotedForPoolInVlmgp[user][lp]` and the corresponding `_balances[user]` in the rewarder become permanently unreachable: `vote()` reverts (can't reduce delta), and `unvote()` reverts (blocked by the same active check). The user's locked MGP remains counted in `userTotalVotedInVlmgp`, reducing their effective votable balance for other pools and freezing their bribe-pool stake indefinitely.

### Impact Explanation
This is a permanent freezing-of-funds bug: a user's voting-linked stake in `BribeRewardPool` (and thus eligibility for bribe rewards tied to that stake) becomes permanently locked with no code path to unwind it, once a pool they voted on is deactivated. This matches the Immunefi "permanent freezing of funds/unclaimed yield" impact class. It does not require attacker privilege — the trigger event (pool deactivation) is an ordinary owner/admin lifecycle action for pool management (e.g., decommissioning a delisted LP or changing a rewarder), not a malicious admin action, and once it occurs, the affected user (an ordinary voter) is trapped through no fault or extra action of their own.

### Likelihood Explanation
Preconditions: any user calls `vote()` to allocate `vlMGP` votes to a pool, and later the pool is set inactive through normal pool-management flow. This is a standard, expected lifecycle event, not a contrived attack. No special capital or unusual conditions are needed — any voter is at risk the moment a pool they've voted for is deactivated. The bug is deterministic and 100% reproducible.

### Recommendation
Invert the check in `unvote()` so it can be called for any pool regardless of `isActive` status, or explicitly require `pool.isActive == false` (or drop the check entirely) so that unvoting is always possible. This restores the documented intent — allowing users to exit a deactivated pool — while `vote()` correctly continues to require `isActive == true` for new/increased votes.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, add a pool `lp` with an active `BribeRewardPool` rewarder, set `vlMGP` lock for `user`.
2. `user` calls `vote([lp], [+X])` — assert `userVotedForPoolInVlmgp[user][lp] == X` and `BribeRewardPool.balanceOf(user) == X`.
3. Owner calls the pool-management setter to set `poolInfos[lp].isActive = false`.
4. `user` calls `vote([lp], [-X])` — assert revert `PoolNotActive()`.
5. `user` calls `unvote(lp)` — assert revert `PoolNotActive()`.
6. Assert `userVotedForPoolInVlmgp[user][lp]` remains `X` and `BribeRewardPool.balanceOf(user)` remains `X` indefinitely (advance time > 24h to confirm no other mechanism unwinds it), demonstrating permanent freezing.
