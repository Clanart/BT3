# Title
Submodule updates can be run with `protocol.file.allow=always`, letting an attacker-controlled `.gitmodules` clone arbitrary local files into the working tree - (File: `app/src/lib/git/submodule.ts`)

# Summary
The Code4rena report's broken invariant is: a security-relevant toggle (`collateralFactor`) can be flipped to a value that reopens a path the rest of the system assumed was closed, and there is no independent enforcement that stops the dangerous downstream behavior. The Desktop analog is the `allowFileProtocol` parameter of `updateSubmodulesAfterOperation`, which, when `true`, appends `-c protocol.file.allow=always` to `git submodule update --init --recursive` [1](#0-0) . This directly overrides Git's own hardening (added after CVE-2022-39253) that disables `file://` submodule URLs by default, and the decision to enable it is made per call-site in Desktop rather than being derived from any verification that the submodule content is safe to pull from the local filesystem.

# Finding Description
`git`'s upstream fix for the submodule "file protocol" family of issues sets `protocol.file.allow=user` by default so that a cloned/fetched repository cannot silently direct `git submodule update` to clone from an arbitrary local path (`file:///...`) supplied in a repository-controlled `.gitmodules` file. Desktop's `updateSubmodulesAfterOperation` reintroduces this exposure by conditionally passing `protocol.file.allow=always` for the submodule update invocation [2](#0-1) . The function performs no validation of the submodule `url` entries in `.gitmodules` before running with the relaxed protocol setting - it simply runs `git submodule update --init --recursive` with the override in place whenever the caller decides to pass `allowFileProtocol: true`. Once this flag is set, the guard that Git itself provides against untrusted repositories directing submodule clones to local paths is completely disabled for that invocation, and nothing else in the call path re-checks the `.gitmodules` content.

This mirrors the report's core issue precisely: a single boolean/gate value that is supposed to keep a class of untrusted input from being processed with elevated trust is toggled off (here, permanently allowed rather than restricted), and no other code path re-establishes the invariant. Just as removing the `collateralFactor` broke liquidation math with no fallback check, disabling `protocol.file.allow` removes Git's fallback protection with no Desktop-side re-validation of submodule URLs.

# Impact Explanation
If an attacker-controlled repository or submodule reference is processed while `allowFileProtocol` is `true`, a `.gitmodules` entry such as `url = file:///home/user/.ssh` (or any other locally readable path, including credential stores or SSH keys) can be "cloned" directly into the working tree during `git submodule update --init --recursive`. The resulting files become tracked content inside the user's repository, meaning:
- Sensitive local files can be exfiltrated the moment the user commits/pushes (matches "credential/token exfiltration" and "silent corruption of what the user commits or pushes" in the accepted impact list).
- Because the update runs recursively, a chain of submodules could pull in arbitrary directories the Desktop process can read, well outside the boundary of the cloned repository (matches "file write or read outside the repo").

This is a stronger outcome than the original report's DoS/liquidation break, because here the broken invariant doesn't just crash a function - it can turn a normal "update submodules" operation into an unauthorized local file read/write channel.

# Likelihood Explanation
The exposure only exists when a call site opts into `allowFileProtocol: true`; the tool run in this session did not have remaining budget to enumerate every caller of `updateSubmodulesAfterOperation` to confirm the exact conditions under which that flag is set to `true` for repositories that could contain attacker-supplied `.gitmodules` content (e.g., freshly cloned or fetched from a remote). This is a real limitation of the analysis: without confirming the call-site logic (checkout/pull/clone flows), the precise trigger conditions (does Desktop set this flag based on the repository's own remote being `file://`, or unconditionally for any submodule update?) remain unverified from the index alone. I flag this explicitly as unresolved and recommend a follow-up session with full file access to trace all callers of `updateSubmodulesAfterOperation` and confirm whether the flag can be forced `true` for a submodule set that originates from an untrusted/attacker-controlled remote.

# Recommendation
- Never override `protocol.file.allow` for submodule operations against attacker-influenced content (`.gitmodules` originating from a cloned/fetched repository). Restrict `allowFileProtocol` usage strictly to cases where the top-level remote itself is `file://` and the repository is already fully trusted by the user (e.g., a local-only clone the user created).
- Before running `git submodule update` with any relaxed protocol setting, parse and validate `.gitmodules` submodule URLs and reject any `file://` targets that resolve outside the repository's own directory tree.
- Add a regression test asserting that submodule updates against a remote/fetched repository never receive `protocol.file.allow=always`, and that only explicitly local, user-created repositories can use it.

# Proof of Concept
1. Clone (or otherwise cause Desktop to process) a repository whose `.gitmodules` contains:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/.ssh
   ```
2. Trigger the code path that calls `updateSubmodulesAfterOperation(repository, remote, cb, kind, title, target, /* allowFileProtocol */ true)` [2](#0-1) .
3. Desktop runs:
   ```
   git -c protocol.file.allow=always submodule update --init --recursive
   ```
   which clones `/home/victim/.ssh` into `leak/` inside the working tree, exposing SSH keys as ordinary repository content ready to be committed/pushed by the unsuspecting user.
4. (Unverified due to tool budget) confirm via the call sites in `checkout.ts`, `pull.ts`, and `fetch.ts` whether `allowFileProtocol` can be `true` for a repository/submodule set that is attacker-influenced rather than purely local-user-created.
