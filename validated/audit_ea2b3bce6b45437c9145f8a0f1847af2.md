### Title
Panic on identity aggregate nonce point in BIP-340 HRAm causes validator crash (DoS) - (File: networks/bitcoin/src/crypto.rs)

### Summary

The Bitcoin network crate's BIP-340 `Hram` calls `x(R)`, which unconditionally `expect`s that `R` is not the point at infinity (`networks/bitcoin/src/crypto.rs:13-16`). During a FROST Bitcoin signing round, `R` is the sum of nonce commitments supplied by all included participants via `Commitments::read`/`read_preprocess`. A malicious signer who submits their preprocess last can choose nonce commitments whose weighted contribution makes the aggregate `R` (or the per-participant binding factor applied to it) equal to the identity, causing a panic — not a clean `Err` — inside `sign_share`/`verify`, crashing the processor and aborting the signing round indefinitely.

### Finding Description

`x()` and `x_only()` document that they panic on the point at infinity:

- `x()`: `(*encoded.x().expect("point at infinity")).into()` at `networks/bitcoin/src/crypto.rs:15`
- `x_only()`: `expect("x_only was passed a point which was infinity or odd")` at `crypto.rs:22`
- `Hram::hram` calls `x(R)` and `x(A)` at `crypto.rs:65-66`, with the doc comment acknowledging: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`) and rationalizing it as "a negligible probability for a well-reasoned caller, even with malicious participants present" (`crypto.rs:78-80`).

That reasoning is incorrect. The aggregate nonce `R` in FROST is `sum_i (D_i + rho_i * E_i)` (per the IETF Schnorr algorithm in `crypto/frost/src/algorithm.rs`), where `D_i`, `E_i` come from each participant's `Preprocess`/`Commitments`, which are attacker-controlled bytes read via `read_preprocess`. `rho_i` is a public, computable binding factor (`rho over group_key, hash_msg and the 'preprocesses' challenge`). A signer who waits for the other participants' commitments can solve for `D_i`/`E_i` to force `R = identity`. There is no identity check on `R` before `hram` is invoked: `Schnorr::verify` calls `self.0.verify(group_key, nonces, sum)` (`crypto.rs:145`) which evaluates `hram(&R, &A, &m)`, and the same occurs in `sign_share` (`crypto.rs:128-136`). The panic also fires if `A` (the group key) is identity, though that requires a broken DKG.

This is the direct analog of CVE-2017-6498: untrusted input reaching a deserialization/verification path that performs an assertion (`expect`) instead of returning an error, yielding denial of service.

### Impact Explanation

A single malicious participant in a Bitcoin threshold signing set can crash every processor executing `Schnorr::sign_share`/`verify` for that plan by forcing the aggregate nonce to the identity point. Since preprocesses are exchanged over the tributary/coordinator channel and deserialized with `Commitments::read`/`read_preprocess` (public inputs per the rules), this is reachable by any validator participant. The panic aborts the signing round; repeating it each attempt gives a persistent liveness failure for Bitcoin withdrawals, i.e., funds frozen due to halted signing. Severity: Medium/High DoS matching the CVE's A:H.

### Likelihood Explanation

The attacker needs a key share in the multisig set and must submit their nonce commitments after learning other participants' commitments — feasible since preprocesses are broadcast and binding factors are public. No cryptographic assumption is broken; it is pure input-driven panic. The cost is one malicious preprocess per round.

### Recommendation

Check `R` (and `A`) for identity before computing the HRAm — return `None`/`Err` from `verify`/`sign_share` rather than panicking, e.g., guard `x()`/`x_only()` callers with `bool::from(point.is_identity())` and reject identity aggregate nonces in the FROST `sign`/`complete` path. Optionally add an identity check on aggregate `R` in `crypto/frost/src/sign.rs` so non-Bitcoin callers benefit too.

### Proof of Concept

Conceptual: in a Bitcoin FROST round with participants `{1, 2}`, participant 2 observes participant 1's `Preprocess` commitments `(D_1, E_1)`. Participant 2 computes the binding factors `rho_1, rho_2` over the transcript (`group_key`, `hash_msg`, encoded preprocesses) and chooses `D_2 = identity`, `E_2 = -(D_1 + rho_1 * E_1) / rho_2`, serializes via `Commitments::write`, and submits it. When `Algorithm::sign_share`/`verify` computes `R = D_1 + rho_1*E_1 + D_2 + rho_2*E_2 = identity`, `Hram::hram(&R, &A, &msg)` calls `x(&identity)` → `to_encoded_point` returns `None` for `x()` → `expect("point at infinity")` panics, unwinding the processor task.
