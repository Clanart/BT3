## Finding: `freeze_code_object` does not re-validate the `EDEP_WEAKER_POLICY` invariant for dependencies

### Summary
`code::freeze_code_object` only checks package existence and ownership before flipping `upgrade_policy` to `immutable`. It never calls `check_dependencies`, so a package can be frozen (declared immutable) while one or more of its dependencies remain `compat`/`arbitrary` (mutable) — violating the invariant enforced at `publish_package` time that a package's upgrade policy must never be weaker than its dependencies'.

### Finding Description
At publish time, `code::check_dependencies` enforces that every dependency's `upgrade_policy` is `>=` the publishing package's own policy, aborting with `EDEP_WEAKER_POLICY` otherwise: [1](#0-0) 

This is the mechanism that guarantees "an immutable package's dependencies must all be immutable too" — it is checked once, at publish/upgrade time, via `publish_package`'s call to `check_dependencies`: [2](#0-1) 

However, `freeze_code_object` — the function that converts an already-published, non-immutable package into `immutable` — performs only an existence check and an ownership check: [3](#0-2) 

It does not call `check_dependencies` (that function is only invoked from `publish_package`). The formal spec for `freeze_code_object` confirms this: its `aborts_if` conditions cover only object existence and ownership, with no dependency-policy condition at all: [4](#0-3) 

The public entry point that reaches this logic is `object_code_deployment::freeze_code_object`, which only forwards the owner-of-`code_object` check to `code::freeze_code_object`: [5](#0-4) 

Consequently, an attacker who owns a package `P` (with policy `compat`) that depends on another package `D` (also `compat`, owned by someone else and left mutable) can call `freeze_code_object` on `P`. This succeeds and sets `P.upgrade_policy = immutable` in the on-chain `PackageRegistry`, even though `D` — which `P`'s frozen bytecode still calls into — can still be upgraded by `D`'s owner at any time.

### Impact Explanation
Third-party integrators and auditors who rely on the `upgrade_policy` field of `PackageRegistry` (or on `UpgradePolicy::immutable()` as an audited guarantee that a package's entire code surface, including transitive dependencies, is frozen) receive a false assurance. The frozen package's direct bytecode is fixed, but its behavior can still change because a dependency it calls into is not fixed. This breaks the documented invariant behind `EDEP_WEAKER_POLICY` and can be leveraged to make audited/"immutable" contracts effectively mutable through a dependency, misleading downstream consumers (e.g., other protocols hard-coding trust in an "immutable" package).

### Likelihood Explanation
High likelihood of triggering: this requires no special privilege beyond owning the code object being frozen (a completely permissionless, self-serve action via `object_code_deployment::freeze_code_object`), and no cooperation from the dependency owner is needed. The only precondition is a compatible/mutable dependency chosen at publish time, which is normal and common (e.g., referencing a not-yet-immutable library package).

### Recommendation
`code::freeze_code_object` should re-run the equivalent of `check_dependencies` (or at minimum assert that every recorded `PackageDep`'s current on-chain `upgrade_policy` is `immutable`, or is policy-exempt) before allowing the transition to `immutable`. Alternatively, document explicitly that `immutable` only guarantees the package's own bytecode is frozen and does not extend transitively to dependencies, and update the `UpgradePolicy` semantics/spec accordingly so integrators do not assume a transitive guarantee that the code does not provide.

### Proof of Concept
1. Publish package `D` (e.g., containing a `fixed_point32`-consuming module) with `upgrade_policy = compat` under account `0xdead`.
2. Publish package `P` under an object address owned by the attacker, with `upgrade_policy = compat`, declaring a dependency on `D`. This succeeds because `check_dependencies` only requires `D.upgrade_policy >= P.upgrade_policy` (both are `compat`), per [1](#0-0) .
3. Call `object_code_deployment::freeze_code_object(attacker, P_object)`. This succeeds because the function only checks existence/ownership, per [3](#0-2) , setting `P.upgrade_policy = immutable` in `PackageRegistry`.
4. `D`'s owner (`0xdead`) can still call `publish_package` to upgrade `D` (it remains `compat`), changing behavior reachable from the supposedly "immutable" `P`.
5. This can be adapted from the existing test `object_code_deployment_freeze_code_object` in `aptos-move/e2e-move-tests/src/tests/object_code_deployment.rs` [6](#0-5)  by adding a mutable dependency package before calling `Freeze`, and asserting that `Freeze` succeeds (no `EDEP_WEAKER_POLICY` abort) while the dependency's `upgrade_policy` remains `compat`.

**Note on uncertainty:** the exact remaining lines of `code::freeze_code_object` beyond the ownership assertion (the loop that mutates `upgrade_policy` for each package in the registry) could not be retrieved from the index due to indexing/size limits. This does not affect the conclusion — the absence of any `check_dependencies` call or any dependency-related `aborts_if` in the formal spec is confirmed — but a Devin session with full file access is recommended to view the complete function body and write a concrete adapted test.

/// Tests the `freeze_code_object` object code deployment function.
#[test]
fn object_code_deployment_freeze_code_object() {
    let mut context = TestContext::new(None, None);
    let acc = context.account.clone();

    // First deploy the package to an object.
    assert_success!(context.execute_object_code_action(
        &acc,
        "object_code_deployment.data/pack_initial",
        ObjectCodeAction::Deploy,
    ));

    // Mark packages immutable.
    assert_success!(context.execute_object_code_action(&acc, "", ObjectCodeAction::Freeze));

    let registry = context
        .read_resource::<PackageRegistry>(&context.object_address, PACKAGE_REGISTRY_ACCESS_PATH)
        .unwrap();
    // Verify packages are immutable.
    for package in &registry.packages {
        assert_eq!(package.upgrade_policy, UpgradePolicy::immutable());
    }
}
