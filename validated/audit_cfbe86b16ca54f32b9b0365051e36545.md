### Title
Panic in `SchnorrkelHram::hram` on malformed/short message causes denial of service - (File: crypto/schnorrkel/src/lib.rs)

### Summary
`SchnorrkelHram::hram`, the HRAm used by the FROST Schnorrkel signing algorithm, parses the message to be signed as `u32 context_len || context || msg` but performs no length validation. Two unchecked slice operations panic: `m[0 .. 4]` when the message is shorter than 4 bytes, and `m[4 .. (4 + ctx_len)]` when the declared `ctx_len` exceeds the remaining buffer. This mirrors the advisory's bug class — incomplete validation of an input's shape leads to an assertion/panic, denying service. [1](#0-0) 

### Finding Description
In `crypto/schnorrkel/src/lib.rs`, `SchnorrkelHram::hram` executes:

```rust
let ctx_len =
  usize::try_from(u32::from_le_bytes(m[0 .. 4].try_into().expect("malformed message")))
    .unwrap();
let mut t = signing_context(&m[4 .. (4 + ctx_len)]).bytes(&m[(4 + ctx_len) ..]);
```

`hram` is invoked from `Schnorr::sign_share` via `H::hram(&nonce_sums[0][0], &params.group_key(), msg)` in `crypto/frost/src/algorithm.rs` line 208, where `msg` is the message being signed. In `Schnorrkel::sign_share` (lib.rs lines 110–129) the wire message is constructed as `[u32 context_len || context || msg]` and passed through `self.schnorr.sign_share`, so `hram` receives bytes whose declared length prefix is attacker-influenced transaction/sign data. No layer validates `m.len() >= 4` or `4 + ctx_len <= m.len()` before indexing. [2](#0-1) [3](#0-2) 

### Impact Explanation
An unprivileged party who can cause a message (or a share-verification path using the stored challenge) to be processed can craft sign data that is either shorter than 4 bytes or carries a `ctx_len` claiming more bytes than present. Both cases panic on out-of-bounds slicing inside signing, aborting the signing session and crashing the participant's signing task — a denial of service against the threshold-signing pipeline, matching the CVE's assertion-failure DoS impact. One honest caveat: I could not fully trace the upstream coordinator path that feeds `msg` into `Schnorrkel`, so reachability assumes sign-request data is attacker-influenced as the scope rules permit.

### Likelihood Explanation
Triggering requires only influencing the bytes of a message scheduled for Schnorrkel signing — e.g., a malformed or truncated payload. It requires no key material, no collusion, and no validator privileges. However, it depends on the Schnorrkel algorithm being selected and on callers not pre-validating message length, which tempers likelihood; hence Medium rather than High.

### Recommendation
Validate lengths before slicing in `SchnorrkelHram::hram`: return a defined error (or a fixed challenge/zero) when `m.len() < 4` or `m.len() < 4 + ctx_len`. If `Hram::hram`'s signature cannot return `Result`, clamp or substitute a canonical malformed-input value, but prefer restructuring so malformed messages are rejected before `sign_share` is invoked — e.g., enforce `msg.len() >= 4` and `ctx_len` bounds in `Schnorrkel::sign_share`.
