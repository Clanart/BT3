### Title
Unbounded, unmetered storage deletion on contract SELFDESTRUCT can stall block processing - (File: `x/evm/state/state.go`)

### Summary
The Xen CVE describes a lack of preemption when tearing down a large, guest-controlled collection (event channels) in one uninterruptible operation, allowing a single request to consume unbounded host CPU time. The closest reachable analog in sei-chain is the EVM `Finalize()` path that synchronously purges *all* storage slots of a self-destructed contract in a single, non-batched loop, triggered by one transaction containing `SELFDESTRUCT`.

### Finding Description
When an EVM transaction executes `SELFDESTRUCT`, `Finalize()` calls `clearAccountStateIfDestructed`, which for every destructed account calls `clearAccountState`, which in turn calls `s.k.PurgePrefix(s.ctx, types.StateKey(acc))` to delete the entire per-account storage key range in one pass [1](#0-0) . This is unlike the module's own zero-value storage slot cleanup, which the codebase explicitly documents and implements as "resumable, batched" — processing only `ZeroStorageCleanupBatchSize` (100) keys per `EndBlock` call and persisting a checkpoint across blocks [2](#0-1) , invoked from `EndBlock` explicitly to bound per-block work [3](#0-2) .

By contrast, `SELFDESTRUCT`'s storage purge has no such batching/limit and runs inline during the transaction's own `Finalize()`, not during a bounded end-of-block sweep. A contract can accumulate an arbitrarily large number of storage slots over many prior blocks (each `SSTORE` is gas-metered per write, but the *cumulative* count of slots is unbounded across the contract's lifetime and many transactions), while the single `SELFDESTRUCT` opcode that triggers the full-prefix delete has a fixed EVM gas cost (5000) unrelated to the number of slots that must be iterated and deleted.

### Impact Explanation
If `PurgePrefix` truly iterates and deletes every key under the account's storage prefix without any per-call cap, a single attacker-submitted transaction invoking `SELFDESTRUCT` against a contract with a very large storage footprint could force one transaction (and therefore one block) to perform an amount of KV-store deletion work proportional to the contract's entire accumulated storage — a "single guest request causes an almost unbounded delay" pattern, directly mirroring the Xen `evtchn_reset()`/`evtchn_destroy()` DoS class. This could push block processing time past the ~2.5 second consensus window, risking a validator/network-wide halt or slow-down (Denial of Service against block production), which matches the accepted impact class "block delay beyond 2.5 seconds."

### Likelihood Explanation
Exploitability depends on how cheaply an attacker can grow a contract's storage over time versus how much unmetered work `PurgePrefix` performs per stored key. Populating millions of storage slots requires paying `SSTORE` gas across many transactions/blocks (this is a real, non-trivial cost, but it is a one-time, amortized cost paid by the attacker over time, not paid at deletion time). I was unable to confirm from the available code whether `PurgePrefix` has any internal per-call key limit or gas metering tied to the number of deleted entries — this is the single biggest source of uncertainty in this finding, since I ran out of tool budget before reaching its definition in `x/evm/keeper/keeper.go`.

### Recommendation
- Inspect `PurgePrefix`'s implementation directly (in `x/evm/keeper/keeper.go`) to confirm whether it bounds the number of keys deleted per invocation or charges gas proportional to keys deleted.
- If unbounded, apply the same "resumable, batched" pattern already used for zero-storage-slot pruning (`x/evm/keeper/storage_cleanup.go`) to self-destructed account storage cleanup: defer full-prefix deletion to a checkpointed, per-block-capped `EndBlock` job rather than doing it synchronously inside the destructing transaction's `Finalize()`.
- Alternatively, charge EVM gas proportional to the number of storage slots being cleared at `SELFDESTRUCT` time (mirroring go-ethereum's post-EIP-6780 approach of not doing full storage clearing at all, and Xen's own upstream fix of adding preemption checkpoints to `evtchn_reset()`).

### Proof of Concept
Conceptual (not executed, due to tool limitations):
1. Deploy a contract and, across many transactions/blocks (respecting per-block gas limits), issue enough `SSTORE`s to non-zero values to accumulate a very large number of live storage slots (e.g., millions), paying the associated `SSTORE` gas over time.
2. In a single later transaction, call a function that triggers `SELFDESTRUCT` on that contract.
3. Observe whether `Finalize()` → `clearAccountStateIfDestructed` → `PurgePrefix` iterates and deletes all slots synchronously within that one transaction, and measure whether processing time for that block exceeds acceptable consensus timing given a sufficiently large slot count. const ZeroStorageCleanupBatchSize = 100

func (k *Keeper) GetZeroStorageCleanupCheckpoint(ctx sdk.Context) []byte {
	store := ctx.KVStore(k.storeKey)
	bz := store.Get(types.ZeroStorageCleanupCheckpointKey)
	if len(bz) == 0 {
		return nil
	}
	return append([]byte(nil), bz...)
}

func (k *Keeper) setZeroStorageCleanupCheckpoint(ctx sdk.Context, key []byte) {
	store := ctx.KVStore(k.storeKey)
	if len(key) == 0 {
		store.Delete(types.ZeroStorageCleanupCheckpointKey)
		return
	}
	store.Set(types.ZeroStorageCleanupCheckpointKey, key)
}

func (k *Keeper) PruneZeroStorageSlots(ctx sdk.Context, limit int) (int, int) {
	if limit <= 0 {
		return 0, 0
	}

	checkpoint := k.GetZeroStorageCleanupCheckpoint(ctx)
	store := k.PrefixStore(ctx, types.StateKeyPrefix)
	iterator := store.Iterator(checkpoint, nil)
	defer func() { _ = iterator.Close() }()

	processed := 0
	processedMetric := uint64(0)
	deleted := 0
	deletedMetric := uint64(0)
	var bytesPruned uint64
	skippedCheckpoint := len(checkpoint) == 0
	var lastKey []byte

	for ; iterator.Valid() && processed < limit; iterator.Next() {
		key := append([]byte(nil), iterator.Key()...)
		if !skippedCheckpoint {
			if bytes.Equal(key, checkpoint) {
				skippedCheckpoint = true
				continue
			}
			skippedCheckpoint = true
		}

		processed++
		processedMetric++
		lastKey = key

		val := store.Get(key)
		if val != nil && isZeroStorageValue(val) {
			store.Delete(key)
			deleted++
			deletedMetric++
			bytesPruned += uint64(len(key)) + uint64(len(val))
		}
	}

	if processed == 0 {
		// No keys were iterated, so the saved checkpoint already points to the end
		// of the iterator. Clear it so the next run restarts from the beginning
		// rather than resuming from an exhausted position.
		if len(checkpoint) != 0 && !iterator.Valid() {
			k.setZeroStorageCleanupCheckpoint(ctx, nil)
		}
		return 0, 0
	}

	if iterator.Valid() {
		k.setZeroStorageCleanupCheckpoint(ctx, lastKey)
	} else {
		k.setZeroStorageCleanupCheckpoint(ctx, nil)
	}

	evmKeeperMetrics.zeroStorageProcessedKeys.Add(ctx.Context(), int64(processedMetric)) //nolint:gosec

	if deleted > 0 {
		evmKeeperMetrics.zeroStoragePrunedKeys.Add(ctx.Context(), int64(deletedMetric)) //nolint:gosec
		evmKeeperMetrics.zeroStoragePrunedBytes.Add(ctx.Context(), int64(bytesPruned))  //nolint:gosec
		logger.Info("pruned zero storage slots", "processed", processed, "deleted", deleted, "bytes_saved", bytesPruned)
	}
	return processed, deleted
}
