## Analysis

The external report's core broken invariant is: **two independent code paths share a single authorization/state gate, and an action legitimately taken in the context of one path silently satisfies (or corrupts) the gate for the other path**, letting a signed/authorized action be consumed or replayed outside the context the signer intended.

In Hyperbridge's `pallet-relayer`, the same structural flaw exists between the fee-accumulation flow and the fee-withdrawal flow: they share one nonce counter and produce **identical signed message bytes** for the same `(nonce, state_machine, beneficiary)` tuple.

### Title
Cross-flow signature replay between `accumulate()`'s beneficiary redirect and `withdraw()`'s withdrawal message — (File: `modules/pallets/relayer/src/accumulate.rs` and `modules/pallets/relayer/src/withdrawal.rs`)

### Finding Description
`accumulate()` verifies an optional beneficiary redirect using: [1](#0-0) 

`withdraw()` verifies its own signed payload using: [2](#0-1) 

When a beneficiary is present in both flows, both functions hash `(nonce: u64, state_machine/dest_chain: StateMachine, beneficiary: bytes)` — a SCALE-identical byte sequence — and both flows read/increment the **same** `Nonce<T>` storage item, keyed by `(address, state_machine)`: [3](#0-2) [4](#0-3) 

There is no domain separator (e.g., a flow-tag byte) distinguishing "this signature authorizes a beneficiary redirect inside `accumulate`" from "this signature authorizes a full `withdraw`". A signature a relayer produces for one call is therefore a valid, unused credential for the other call as long as the nonce hasn't been consumed yet, because both `accumulate` and `withdraw` are dispatched as unsigned extrinsics whose authorization lives entirely in the embedded signature/nonce rather than in `frame_system` origin — this mirrors the pattern used elsewhere in this pallet (e.g. `claim_outbound_request_delivery_reward` is `ensure_none` and spam-protected only via `validate_unsigned`, per `modules/pallets/relayer/src/lib.rs:417-431`).

This is the direct structural analog of the Sherlock report: in the report, revoking slashing rights via one call (`recordLastStakeUpdateAndRevokeSlashingAbility`) silently altered the precondition checked by a *different* function (`Slasher.canWithdraw`) that a staker relied on to complete withdrawal — because both functions read the same shared piece of state (`stalestUpdateBlock`) without the two flows being properly reconciled. Here, two different pallet-relayer functions read/consume the same shared piece of state (`Nonce<T>`) and validate against the *same message bytes*, without a domain tag reconciling the two call contexts.

### Impact Explanation
Because `accumulate`'s `beneficiary_details` path credits `total_fee` to `beneficiary_address` and marks the relevant `RequestCommitments` as claimed, while `withdraw` dispatches the entire `Fees` balance to a beneficiary and zeroes it, an observer who captures a relayer's signed `(nonce, chain, beneficiary)` payload intended for one of these calls can submit it against the other before the intended transaction lands. Whichever call consumes the nonce first:
- Redirects that relayer's accrued fee balance for that `(address, state_machine)` pair to the attacker-observed beneficiary through a call the relayer never issued for that context, and
- Invalidates the relayer's own pending signed transaction (nonce mismatch), forcing resubmission — this is a genuine logic-level cross-domain replay (`Error::<T>::InvalidPublicKey`/`InvalidSignature` are bypassed because the bytes verify successfully; the flaw is the missing domain separation, not signature forgery).

This falls under the bounty's "replay/double-claim/double-settlement" and "logic attacks" categories: bandwidth/fee accounting between two pallet-relayer entry points fails to move the settlement exactly once to the intended context.

### Likelihood Explanation
Both `accumulate` and (per the sibling `claim_outbound_*` extrinsics' documented pattern) `withdraw` are unsigned, permissionless, mempool-visible extrinsics. Any relayer's signed payload broadcast for one purpose is public before inclusion, so any unprivileged third party can copy the signature bytes into the sibling call. No admin, governance, relayer-compromise, or malicious-peer assumption is required — only observation of a pending, otherwise-legitimate signed extrinsic, satisfying the "public-entrypoint, unprivileged attacker" requirement.

### Recommendation
Add a domain-separation byte/tag (e.g., `b"ACCUMULATE_BENEFICIARY"` vs `b"WITHDRAW"`) into both `beneficiary_message()` and `message()` so the same `(nonce, chain, beneficiary)` triple never produces identical signed bytes across the two call contexts, and/or use disjoint nonce namespaces per flow (e.g., separate `AccumulateNonce` / `WithdrawNonce` storage maps) so consuming one never desynchronizes the other.

### Proof of Concept
1. Relayer R has accrued fees on `state_machine = M` and wants to redirect a future `withdraw()` payout to beneficiary `B`. R signs `message(nonce=N, dest_chain=M, beneficiary=Some(B))`, i.e. `keccak256(encode((N, M, B)))`, and submits `withdraw()`.
2. Before that transaction is included, an unprivileged observer copies the signature/`(N, M, B)` triple out of the mempool and submits an `accumulate()` call with `withdrawal_proof.beneficiary_details = Some((B, signature))` for a valid, unrelated batch of proven request deliveries where `delivery_address == R`'s address and `state_machine == M`.
3. `accumulate()` computes `beneficiary_message(N, M, B) == keccak256(encode((N, M, B)))`, an identical hash to the one R signed for `withdraw()`; signature verification passes at `modules/pallets/relayer/src/accumulate.rs:110-126`, `Nonce::<T>` is incremented to `N+1` at lines 128-132, and the newly accumulated fee is credited to `B` instead of R's default address.
4. R's original `withdraw()` transaction, still carrying nonce `N`, now fails signature/nonce verification in `modules/pallets/relayer/src/withdrawal.rs:88-115`, forcing R to re-sign and resubmit — while the fee redirection for the unrelated batch has already gone through under R's signature but outside the transaction R actually authorized for that specific batch/context.

**Caveat:** I was not able to fully confirm the exact `frame_system` origin type (`ensure_none` vs `ensure_signed`) for `accumulate_fees` and `withdraw_fees` in `modules/pallets/relayer/src/lib.rs` before running out of tool calls — the grep for the call definitions returned only a match count, not their bodies. The sibling `claim_outbound_request_delivery_reward`/`set_outbound_request_delivery_reward` extrinsics in the same pallet are confirmed `ensure_none` with unsigned validation, and the doc comments on `withdrawal.rs` explicitly describe relayer-supplied signatures as the sole authorization mechanism, which strongly suggests the same unsigned pattern for `accumulate`/`withdraw`, but this should be verified directly in `modules/pallets/relayer/src/lib.rs` before treating this as fully confirmed.

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
