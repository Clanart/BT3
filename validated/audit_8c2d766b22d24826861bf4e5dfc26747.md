### Title
Fixed Bitcoin-block Assert/Disprove timelocks race against Citrea light-client-proof availability, allowing an honest operator's collateral to be burned during an L2 outage - (File: core/src/citrea.rs, core/src/operator.rs, core/src/builder/transaction/operator_assert.rs)

### Summary
Clementine's dispute-resolution path (Kickoff → Challenge → Assert → Disprove/DisproveTimeout, plus the sibling `LatestBlockhashTimeout` path) is timed purely in Bitcoin block counts, which is the correct mitigation for the "sequencer-time" flavor of the referenced bug. However, before an operator can broadcast the Assert transactions that satisfy this Bitcoin-side deadline, it must first obtain a Light Client Proof (LCP) from Citrea's off-chain light-client-prover service. If Citrea (the L2 whose sequencer/prover produces this LCP) is unavailable, delayed, or reorganized for long enough, an otherwise honest operator cannot obtain the LCP and therefore cannot build or broadcast its Assert transactions before the fixed `assert_timeout_timelock` (576 blocks / ~4 days) expires on Bitcoin. Once that Bitcoin-side deadline passes, a challenger can settle the dispute in the operator's favorless state (`AssertTimeout`) and, via the sibling connector paths that spend `CollateralInRound`, burn the honest operator's collateral — even though the operator did front the withdrawal and behaved correctly.

### Finding Description
The kickoff/dispute machinery defines a fixed number of Bitcoin blocks (not wall-clock time) as challenge/assert/disprove deadlines, e.g. `assert_timeout_timelock` (576 blocks) and `disprove_timeout_timelock` (720 blocks), all defined as pure block counts in `crates/clementine-config/src/protocol.rs` [1](#0-0) .

To construct the Assert transactions that satisfy this window, the operator's `send_asserts` flow must obtain a proof-carrying LCP from Citrea by calling `fetch_validate_and_store_lcp`, which in turn calls `get_light_client_proof` on Citrea's light-client-prover RPC: [2](#0-1) [3](#0-2) 

If the LCP cannot be fetched for the required L1 block height (Citrea down, LC prover behind, reorg, etc.), `fetch_validate_and_store_lcp` returns an error and the operator cannot proceed to build/sign/broadcast Asserts: [4](#0-3) 

Meanwhile, the Bitcoin-side `assert_timeout_timelock` / `disprove_timeout_timelock` clocks keep advancing regardless of Citrea's health, since they are enforced purely by `Sequence::from_height(...)` relative timelocks on Bitcoin, with no dependency on or gating by Citrea/L2 availability: [5](#0-4) 

The sibling `LatestBlockhashTimeout` transaction demonstrates the consequence concretely: it directly spends `CollateralInRound` — the operator's Bitcoin collateral — if the operator fails to act before its own block-based deadline: [6](#0-5) 

The `AssertTimeout` and `DisproveTimeout` transactions similarly gate the operator's ability to reach the `Reimburse` state; missing these windows forces the loss path (challenger wins the dispute / operator's collateral is put at risk) as referenced in `core/src/builder/transaction/creator.rs` [7](#0-6) .

This reproduces the exact structural flaw in the referenced report: a fixed on-chain countdown that assumes uninterrupted availability of an external system (there: Arbitrum sequencer for price discovery; here: the Citrea sequencer/light-client-prover for proof availability) the honest party does not control. The design intentionally avoids an oracle for auction pricing (good), but it does not avoid the dependency for the *data an honest operator needs to defend itself* within its own Bitcoin-enforced deadline.

### Impact Explanation
If Citrea's light-client-prover is unavailable or lagging for a duration comparable to `assert_timeout_timelock`/`disprove_timeout_timelock`, an operator who legitimately fronted a withdrawal (paid the user) can be unable to produce the LCP-dependent Assert proof in time. This falls under the accepted Critical impact class "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned," because the operator's `CollateralInRound` can be consumed via the timeout paths despite the operator having done nothing wrong — the value binding "operator credited == party that paid" is broken by an external L2-availability failure rather than by attacker action against Bitcoin.

### Likelihood Explanation
Likelihood is low-to-moderate and comparable to the original finding's debated severity: it requires a Citrea (L2 sequencer/light-client-prover) outage or proof-generation delay lasting on the order of days (close to the `assert_timeout_timelock`/`disprove_timeout_timelock` windows), which is an infrequent but not implausible occurrence. Unlike the original report where the fix was "define auction durations in number of blocks" (already done here for the Bitcoin-side windows), the residual coupling to Citrea's LCP pipeline as a hard prerequisite for meeting those windows was not addressed.

### Recommendation
Decouple the operator's ability to meet Bitcoin-enforced Assert/Disprove deadlines from Citrea light-client-prover availability, e.g. by: (1) allowing the operator to pre-fetch and cache the LCP for a payout well before the kickoff/challenge occurs (some caching already exists via `get_lcp_for_assert`/`insert_lcp_for_assert`, but there is no guarantee the LCP exists in time if Citrea itself stalls), (2) widening `assert_timeout_timelock`/`disprove_timeout_timelock` to account for worst-case Citrea proof-generation latency, or (3) providing a governance/grace mechanism that can extend or forgive missed deadlines caused by proven L2 unavailability, rather than allowing collateral to be burned automatically via `AssertTimeout`/`LatestBlockhashTimeout`.

### Proof of Concept
1. Operator honestly fronts a Citrea withdrawal (`Payout` tx) and gets challenged on Bitcoin (`Challenge` tx spent).
2. Operator's state machine reaches `on_challenged_entry` and attempts `send_operator_asserts_if_ready` → `send_asserts`, which calls `citrea_client.fetch_validate_and_store_lcp(payout_block_height, ...)` [8](#0-7) .
3. Citrea's light-client-prover is offline/delayed (analogous to sequencer outage) so `get_light_client_proof` keeps returning `None`/erroring [4](#0-3) .
4. `assert_timeout_timelock` (576 blocks) elapses on Bitcoin regardless, since it is a pure `Sequence::from_height` relative timelock unrelated to Citrea state [5](#0-4) .
5. Once elapsed, the timeout path (e.g. `AssertTimeout`/`LatestBlockhashTimeout`, which spends `CollateralInRound`) becomes spendable, allowing the operator's collateral to be consumed even though the operator behaved honestly and was only blocked by Citrea's unavailability [9](#0-8) .

```rust
    async fn fetch_validate_and_store_lcp(
        &self,
        payout_block_height: u64,
        deposit_index: u32,
        db: &Database,
        mut dbtx: Option<DatabaseTransaction<'_>>,
        paramset: &'static ProtocolParamset,
    ) -> Result<Receipt, BridgeError> {
        let saved_data = db
            .get_lcp_for_assert(dbtx.as_deref_mut(), deposit_index)
            .await?;
        if let Some(lcp) = saved_data {
            // if already saved, do nothing
            return Ok(lcp);
        };

        let lcp_result = self
            .get_light_client_proof(payout_block_height, paramset)
            .await?;
        let (_lcp, lcp_receipt, _l2_height) = match lcp_result {
            Some(lcp) => lcp,
            None => {
                return Err(eyre::eyre!(
                    "Light client proof could not be fetched found for block height {}",
                    payout_block_height
                )
                .into())
            }
        };

        // save the LCP for assert
        db.insert_lcp_for_assert(dbtx, deposit_index, lcp_receipt.clone())
            .await?;

        Ok(lcp_receipt)
    }
```

```rust
pub fn create_disprove_timeout_txhandler(
    kickoff_txhandler: &TxHandler,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler<Unsigned>, BridgeError> {
    Ok(TxHandlerBuilder::new(TransactionType::DisproveTimeout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            kickoff_txhandler.get_spendable_output(UtxoVout::Disprove)?,
            SpendPath::ScriptSpend(0),
            Sequence::from_height(paramset.disprove_timeout_timelock),
        )
        .add_input(
            NormalSignatureKind::DisproveTimeout2,
            kickoff_txhandler.get_spendable_output(UtxoVout::KickoffFinalizer)?,
            SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_partial(anchor_output(
            paramset.anchor_amount(),
        )))
        .finalize())
}
```

```rust
pub fn create_latest_blockhash_timeout_txhandler(
    kickoff_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler<Unsigned>, BridgeError> {
    Ok(
        TxHandlerBuilder::new(TransactionType::LatestBlockhashTimeout)
            .with_version(NON_STANDARD_V3)
            .add_input(
                NormalSignatureKind::LatestBlockhashTimeout1,
                kickoff_txhandler.get_spendable_output(UtxoVout::LatestBlockhash)?,
                SpendPath::ScriptSpend(0),
                Sequence::from_height(paramset.latest_blockhash_timeout_timelock),
            )
            .add_input(
                NormalSignatureKind::LatestBlockhashTimeout2,
                kickoff_txhandler.get_spendable_output(UtxoVout::KickoffFinalizer)?,
                SpendPath::ScriptSpend(0),
                DEFAULT_SEQUENCE,

            .add_input(
                NormalSignatureKind::LatestBlockhashTimeout3,
                round_txhandler.get_spendable_output(UtxoVout::CollateralInRound)?,

                DEFAULT_SEQUENCE,
            )
            .add_output(UnspentTxOut::from_partial(anchor_output(
```
