### Title
Scanner reports outputs created-and-spent within the same block as received, inflating tracked balance with unspendable outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`Scanner::scan_transaction` / `scan_block` identify received funds purely by matching `tx.output` scriptPubKeys, and never examine `tx.input`. An output created by transaction A and spent by transaction B within the same block is still returned in `Vec<ReceivedOutput>` as spendable. This mirrors the reported bug class: a "supply" of tracked outputs is computed by counting creations (mints) while ignoring destructions (spends/burns), so the reported set of spendable outputs over-counts.

### Finding Description

`scan_transaction` iterates only over `tx.output` and pushes a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts`:

- `networks/bitcoin/src/wallet/mod.rs:199-214`: matches `self.scripts.get(&output.script_pubkey)` and pushes `ReceivedOutput` keyed by `OutPoint::new(tx.compute_txid(), vout)`.
- `scan_block` (`networks/bitcoin/src/wallet/mod.rs:221-227`) simply concatenates `scan_transaction` over `block.txdata`, including in-block spend chains.

There is no pass that removes outpoints referenced by `tx.input` of later transactions in the same block. The only documented caveat is coinbase maturity (`mod.rs:218-220`); same-block spends are unhandled.

Downstream, these `ReceivedOutput`s are handed to `SignableTransaction::new` (`networks/bitcoin/tests/wallet.rs:161`) which treats each as a spendable UTXO, computes `input_value` from `output.value()`, and builds/signs a transaction spending those outpoints. Any transaction spending an already-spent outpoint is a consensus-invalid double-spend that will be rejected by the network.

### Impact Explanation

An unprivileged Bitcoin user can produce a transaction chain (A → B) inside one block where A pays a Serai scanner address and B spends that output. The scanner returns the dead output as received, so:

- The processor credits funds that are not spendable (balance inflation for a registered address/offset).
- Any `SignableTransaction` built from it is invalid; signing succeeds but broadcast fails, stalling legitimate withdrawals/change handling until the bad output is pruned out-of-band.

### Likelihood Explanation

Reachable by any party that can get transactions mined — public inputs only. In-block spend chains are normal Bitcoin behavior (e.g., a wallet consolidating, or a deliberate same-block spend targeting a known Serai deposit address). Likelihood is Medium: it requires the deposit to be spent within the same block, which an attacker can arrange via RBF-aware chaining or by sending to a known scanner script.

### Recommendation

In `scan_block` (and/or `scan_transaction` callers), collect all outpoints consumed by `tx.input` in the block and filter them out of the returned `ReceivedOutput`s — i.e., treat in-block spends as "burns" that decrement the reported set, rather than only counting creations. Equivalently, document and enforce that consumers must reconcile returned outpoints against spends before feeding them to `SignableTransaction::new`.

### Proof of Concept

Conceptual, against `networks/bitcoin/src/wallet/mod.rs`:

1. Register/derive scanner for key `K`; obtain `script = p2tr_script_buf(K)`.
2. Attacker mines a block with two txs:
   - `txA`: output `vout=0` paying `script`.
   - `txB`: input `OutPoint(txidA, 0)`, spending it elsewhere.
3. `scanner.scan_block(&block)` returns `ReceivedOutput{ outpoint: (txidA, 0), ... }` — asserted by the same logic tested in `send_and_get_output` (`tests/wallet.rs:65-69`), which never inspects `tx.input`.
4. `SignableTransaction::new(vec![that_output], &payments, change, None, FEE)` builds a transaction spending the dead outpoint; `send_raw_transaction` rejects it as a double-spend, while the scanner's accounting showed it as received value.
