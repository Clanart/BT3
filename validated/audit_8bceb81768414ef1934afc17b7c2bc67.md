## Title
Recursive clone disables Git's built-in clone-hook protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), enabling code execution from a malicious cloned repository - (File: `app/src/lib/git/clone.ts`)

## Summary
`clone()` in `app/src/lib/git/clone.ts` explicitly forces `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` while running `git clone --recursive` against an attacker-supplied URL. `GIT_CLONE_PROTECTION_ACTIVE` is the internal guard Git itself introduced (as part of the CVE-2024-32004 fix line of work) to stop a freshly-cloned, not-yet-trusted repository from running its own hooks/config during the recursive submodule-init phase of a clone. By setting the flag to `false` inside Desktop's clone path, the application actively disables Git's own safety valve for exactly the scenario the mitigation exists for — cloning something an attacker controls — mirroring the Beefy report's pattern of an owner/trusted action re-deploying based on unchecked external state while an existing "calm/safe" guard is bypassed.

## Finding Description
`clone()` builds the environment for the `git clone` invocation like this: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c', `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`url` is fully attacker/user-controlled (it comes straight from the Clone dialog, a CLI `--cli-clone` argument, or an `x-github-client://openRepo/...` deep link handled in `app/src/main-process/main.ts` and `app/src/ui/dispatcher/dispatcher.ts`'s `openOrCloneRepository`/`dispatchCLIAction` paths). Desktop performs the clone with `--recursive`, meaning submodules referenced by the attacker's repository (via `.gitmodules`) are fetched and initialized as part of the very first clone — before the user has ever inspected the repository's contents.

`GIT_CLONE_PROTECTION_ACTIVE` is not a Desktop invention; it is the env var Git itself sets/consults to prevent a not-yet-trusted, just-cloned repository from executing hook/config-driven behavior (such as `core.hooksPath`/`core.fsmonitor` settings pulled in transitively through recursive submodule initialization) until the initial clone completes safely. By pinning this to `'false'`, Desktop tells Git that this "protected clone" context does not apply, re-enabling the exact code path the upstream fix was designed to shut off.

This is the direct analog of the Beefy bug: a trusted operation (`setPositionWidth`/`unpause`, or here, cloning a repo the user asked for) re-derives/executes based on external, attacker-influenced state (`pool.slot0`, or here, `.gitmodules`/hook config from the untrusted repo) while an existing guard that exists specifically to prevent exploitation of that external state (`onlyCalmPeriods`, or here, Git's own `GIT_CLONE_PROTECTION_ACTIVE` check) is bypassed on this call path.

## Impact Explanation
If Git's clone-hardening mechanism relies on `GIT_CLONE_PROTECTION_ACTIVE` to gate hook execution/config trust during the submodule-init phase of a recursive clone, forcing it to `'false'` reopens a code-execution primitive triggered purely by cloning a malicious repository — something an attacker fully controls (a public repo, a link shared with the victim, or a crafted `x-github-client://openRepo/<attacker-url>` deep link that funnels straight into `clone()`). Successful exploitation would give the attacker code execution on the victim's machine at clone time, i.e., before the user has reviewed any code, which is squarely within the "attacker controls a cloned/fetched repository ... result is code execution" category called out as valid impact.

## Likelihood Explanation
The trigger requires nothing beyond normal Desktop usage: entering/following a URL to clone a repository (via the Clone dialog, the CLI, or a deep link). No local access, admin rights, or pre-existing compromise is needed — the attacker only needs to host a malicious repository with crafted submodule/hook configuration and get the victim to clone it through Desktop, which is Desktop's core intended workflow.

## Recommendation
Remove the explicit override of `GIT_CLONE_PROTECTION_ACTIVE` (or set it to the value Git expects when performing an initial, untrusted clone, i.e. leave it active/`true`/unset) in `clone()`. If a specific reason exists for overriding this variable (e.g., a Desktop-specific reimplementation of the same protection), verify that reimplementation actually enforces equivalent restrictions on hook execution and config trust during `--recursive` submodule initialization before allowing the override.

## Proof of Concept
1. Host a public repository whose `.gitmodules` references a submodule (or nested repository state) crafted to exploit the class of issue `GIT_CLONE_PROTECTION_ACTIVE` was introduced to close (hook execution / `core.hooksPath` trust during recursive submodule init).
2. Get a victim to clone it in GitHub Desktop, e.g. via `x-github-client://openRepo/<attacker-repo-url>` (handled by `handleAppURL` → `openOrCloneRepository` in `app/src/ui/dispatcher/dispatcher.ts`) or by pasting the URL into the Clone dialog.
3. `CloningRepositoriesStore.clone` → `cloneRepo` (`app/src/lib/git/clone.ts`) invokes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment: [2](#0-1) 
4. Because the protection is disabled for this call, the submodule-init phase of the recursive clone runs with the same trust level as an already-vetted repository, allowing the crafted hook/config content to execute as part of the clone itself. [3](#0-2) [4](#0-3)

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
