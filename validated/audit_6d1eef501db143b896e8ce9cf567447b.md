### Title
Uncontrolled Resource Consumption via unthrottled `auction_submitBid` RPC path bypassing bid-pool rate limiting - ([File: kaiax/auction/impl/api.go])

### Summary
The Kibana Timelion CVE describes an endpoint that performs unbounded expensive processing per external request, leading to resource-exhaustion DoS. The analogous reachable path in this codebase is the auction module's `auction_submitBid` RPC handler. Unlike the peer-to-peer bid ingestion path (`BidPool.HandleBid`), which is rate-limited per peer, the RPC path calls `BidPool.AddBid` directly and performs full transaction-pool insertion plus EIP-712/ECDSA signature verification on every call with **no rate limiting at all**.

### Finding Description
`AuctionAPI.SubmitBid` [1](#0-0)  is invoked per RPC request and, for every call:
1. Decodes and RLP-parses an arbitrary attacker-supplied `targetTxRaw` and injects it into the node's transaction pool via `api.a.Backend.SendTx(ctx, targetTx)` [2](#0-1) , which triggers full tx-pool admission logic (sender recovery, nonce/balance checks, pool bookkeeping).
2. Calls `bidPool.AddBid(bid)` directly [3](#0-2) , which runs `validateBid` including two expensive cryptographic signature verifications, `ValidateSearcherSig` and `ValidateAuctioneerSig` [4](#0-3) .

Contrast this with the P2P ingestion path `BidPool.HandleBid`, which explicitly rate-limits per peer at `bidsPerSecondPerPeer = 300` before any validation work is performed, and drops bids silently when the internal queue is full [5](#0-4) . The code comment on the RPC path even acknowledges the asymmetry: "We don't need to reserve for a bid here because the original bid will be sent from auctioneer through different channel (see #api.SubmitBid)" [6](#0-5) , i.e. the RPC path was assumed to be trusted/low-volume, but nothing in code enforces that assumption — any caller reaching the `auction` RPC namespace can call `SubmitBid` an unbounded number of times per second with cheaply-crafted (even ultimately-invalid) inputs, each of which forces full signature verification and a full tx-pool insertion attempt before being rejected.

Additionally, `bp.maxBidPoolSize` defaults to `math.MaxInt64` (effectively unlimited) unless the operator explicitly sets `--auction.max-bid-pool-size` [7](#0-6) [8](#0-7) , compounding the exposure for any deployment that relies on defaults.

This module only runs on Consensus Nodes (`nodeType != common.CONSENSUSNODE` forces `Disable = true`) [9](#0-8) , meaning the affected component sits directly on the block-production critical path.

### Impact Explanation
An RPC caller able to reach the `auction` namespace on a CN can repeatedly invoke `auction_submitBid` with crafted or garbage `targetTxRaw`/bid payloads. Each call forces:
- RLP decoding and a full `SendTx` attempt (sender ECDSA recovery + tx-pool logic), and
- Two independent EIP-712 signature verifications in `validateBid`,

with zero throttling, unlike the P2P bid-gossip path which explicitly limits to 300/sec/peer. Sustained flooding can consume CPU/goroutine time and mutex contention (`bidMu`, `auctionInfoMu`) on the CN, degrading its ability to process legitimate bids and potentially impacting block-building performance, since the auction module participates directly in bundle extraction for block assembly. This is a Denial-of-Service class impact analogous to the Kibana Timelion CWE-400 report.

### Likelihood Explanation
Likelihood depends on whether the `auction` RPC namespace is exposed to external/unprivileged callers on a given deployment (`Public: false` in the `rpc.API` registration means the namespace must be explicitly enabled via `--rpcapi`/config, not that callers are authenticated) [10](#0-9) . Where operators expose it (e.g., to accept bids from searchers/auctioneers as the module is designed to do), any caller that can reach it can flood the endpoint since no per-caller/method rate limit exists at the RPC handler level beyond the generic global `pendingRequestLimit`/concurrency-limit protections in `networks/rpc/handler.go`, which throttle total in-flight requests server-wide rather than this specific expensive-processing pattern.

### Recommendation
Apply the same per-caller rate limiting used in `BidPool.HandleBid` to the RPC path in `AuctionAPI.SubmitBid`, e.g., route RPC-submitted bids through `bidMsgCh`/`checkRateLimit` (keyed by caller identity or connection) before performing `SendTx` or `validateBid`, and enforce a sane default (non-`MaxInt64`) for `MaxBidPoolSize` and/or add lightweight cheap checks (data size, block range) prior to any signature verification or tx-pool insertion.

### Proof of Concept
1. Enable the `auction` RPC namespace on a CN (`--rpcapi=auction`) with default configuration (`auction.max-bid-pool-size` unset → `math.MaxInt64`).
2. From an unprivileged RPC client, repeatedly call `auction_submitBid` in a tight loop with distinct dummy `targetTxRaw` payloads and syntactically well-formed but cryptographically invalid `SearcherSig`/`AuctioneerSig` fields (64/65-byte filler satisfying the length check).
3. Observe each call triggers full `SendTx` tx-pool processing and two ECDSA/EIP-712 signature verifications with no rate limiting, unlike the P2P `handleBidMsg` path which is capped at 300 bids/sec/peer — sustained request volume degrades CN CPU availability with no built-in backpressure specific to this endpoint.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}

// checkRateLimit checks if the peer is within rate limit
func (bp *BidPool) checkRateLimit(peerID string) bool {
	bp.peerRateLimiterMu.Lock()
	defer bp.peerRateLimiterMu.Unlock()

	limiter, exists := bp.peerRateLimiter.Get(peerID)
	if !exists {
		// Create new rate limiter for this peer
		// Use burst equal to the rate limit (we only use rate limit, not the burst)
		limiter = rate.NewLimiter(rate.Limit(bidsPerSecondPerPeer), bidsPerSecondPerPeer)
		bp.peerRateLimiter.Add(peerID, limiter)
	}

	// It'll simply discard the bid if the rate limit is exceeded
	// We don't need to reserve for a bid here because the original bid will be sent from auctioneer through different channel (see #api.SubmitBid)
	return limiter.(*rate.Limiter).Allow()
}
