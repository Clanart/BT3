### Title
Improper Authentication in `addr` Precompile `associate()` — Replayable, Non-Domain-Separated Signature Enables Unauthorized Forced Association and Balance Migration - (File: precompiles/addr/addr.go)

### Summary
The `addr` precompile's `associate` method authenticates an EVM↔Sei address-linking request purely by checking that `(v, r, s)` recovers a valid ECDSA public key over an attacker/caller-supplied `customMessage`, with no requirement that the message equal a fixed, domain-separated association string, and no binding to chain ID, nonce, or transaction context. [1](#0-0)  Any third party who obtains a copy of a victim's valid signature over *any* message (not created for association purposes) can replay it through `associate()` to trigger an authenticated state-changing action — address association plus an immediate, irreversible balance sweep — on the victim's behalf, at a time the caller chooses, without the victim's present consent for that specific action.

### Finding Description
`associate()` recovers `evmAddr`, `seiAddr`, and `pubkey` solely from the supplied signature and an arbitrary `customMessage` hashed with `crypto.Keccak256Hash`: [2](#0-1)  There is no on-chain check that `customMessage` matches the canonical UX string ("Please sign this message to link your EVM and Sei addresses...") shown in the client-side test flow. [3](#0-2)  That canonical string is purely a front-end convention; the contract accepts a signature over literally any byte string.

Because ECDSA signatures are public once produced (visible in front-end network requests, other chains' mempools/blocks, logs, etc.), and this precompile has no nonce, timestamp, or Sei-specific domain separator, any signature the victim ever produced for an unrelated purpose (a login/"Sign-In" message, an off-chain order, a permit for a different chain, etc.) can be captured and resubmitted by an unrelated caller to `associate()`.

The consequence of successful replay is not merely metadata linkage — `associateAddresses` immediately calls `AssociateAddresses`, which unconditionally sweeps all spendable coins and locked-coin state from the "cast address" (`sdk.AccAddress(evmAddr[:])`) to the derived `seiAddr`, and removes the cast account if it has no locked coins: [4](#0-3)  This is a genuine state-changing, fund-moving operation gated only by possession of *any* previously produced signature, not by a signature specifically and freshly authorizing "associate my addresses now."

Notably, the codebase's own EIP-7702 authorization path explicitly recognizes and defends against this exact bug class — replay of a "publicly-visible... signed for another purpose/chain" credential to force an unwanted association and balance migration — by cross-checking chain ID, nonce, and code state before acting: [5](#0-4)  No equivalent domain/nonce/freshness protection exists for the `associate`/`associatePubKey` precompile entry points, which accept a bare, attacker-chosen message. This is the same bug class as CVE-2017-12610: a protocol accepts an out-of-context, replayable credential as sufficient authentication for a sensitive action, allowing an entity to trigger state changes that should require an in-context, freshly-scoped authorization.

### Impact Explanation
A caller who possesses a victim's signature over an unrelated message can force, at a time of their choosing, the association of the victim's EVM address with their Sei address and an immediate, unstoppable migration of all `usei` and wei balances (and removal of the base account) from the direct-cast address to the derived Sei address. This is a real "unauthorized transfer via precompile" trigger: the transfer/migration is executed by the precompile without a signature that specifically and currently authorizes that transfer, and can be forced by any relayer paying gas, not the account owner. It can also disrupt account state relied on by other systems (e.g., a custodial/bridge service or pending native Cosmos transaction expecting the cast address's account/sequence to remain untouched), since `RemoveAccount` resets account number/sequence when the cast address has no locked coins.

### Likelihood Explanation
Exploitation requires obtaining a copy of a victim's valid ECDSA signature over some message, which is a low bar in practice given the ubiquity of `personal_sign`/EIP-191 flows (logins, marketplace listings, permits, off-chain orders) across the EVM ecosystem; none of these need to be Sei-specific or even reference Sei, since the precompile does not check message content, chain ID, or purpose. No special privileges are required to submit the `associate` transaction — it is a public-RPC-reachable precompile call.

### Recommendation
Bind the `associate`/`associatePubKey` message to a fixed, versioned, Sei- and chain-ID-specific domain-separated string (and ideally a nonce or account-sequence value) enforced on-chain, rejecting any `customMessage` that does not match the required canonical format/prefix, mirroring the protections already implemented for EIP-7702 authorization replay in `AuthorityToPreAssociate`.

### Proof of Concept
1. Victim signs an ordinary EIP-191 `personal_sign` message for any dApp login/order flow with their EOA (unrelated to Sei), producing `(v, r, s)` over `message`.
2. Attacker observes this signature (e.g., via a public front-end request, another chain's tx pool, or any leaked signing artifact) and extracts `v, r, s, message`.
3. Attacker calls `addr.associate(v-27, r, s, message)` on Sei (paying their own gas), exactly as shown in the reference test flow, without needing the victim's private key or any Sei-specific consent: [1](#0-0) 
4. The precompile recovers the victim's real `evmAddr`/`seiAddr`/`pubkey` and calls `associateAddresses`, which immediately sweeps all coins from `sdk.AccAddress(evmAddr[:])` to `seiAddr` and may remove the cast account: [6](#0-5) 
5. This association and fund migration occurs at the attacker's chosen time, entirely outside the victim's control or awareness of it happening "now," despite the front-end's assurance that the sign-to-associate message "will not spend any SEI."

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
