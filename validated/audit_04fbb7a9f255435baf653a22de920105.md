Audit Report

## Title
Unbounded secondary-index pubkey enumeration before `scan_results_limit_bytes` check enables RPC resource exhaustion - (File: `accounts-db/src/accounts_db.rs`)

## Summary
`AccountsDb::index_scan_accounts` unconditionally materializes the full `Vec<Pubkey>` for a requested secondary-index key via `self.accounts_index.get_index_key_pubkeys(&index_key)` before the `config.is_aborted()`/`scan_results_limit_bytes` check has any opportunity to run. This lets an unprivileged client force O(total-index-membership) CPU/memory work on the RPC thread for a single `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByMint`-style request, independent of the validator-configured `scan_results_limit_bytes` cap.

## Finding Description
In `AccountsDb::index_scan_accounts`, the loop `for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key)` at [1](#0-0)  checks `config.is_aborted()` only inside the loop body — but the loop's iterator/collection expression, `get_index_key_pubkeys(&index_key)`, is fully evaluated before the loop body ever executes.

`get_index_key_pubkeys` at [2](#0-1)  dispatches to `SecondaryIndex::get`, defined at [3](#0-2) , which calls `inner_keys_map.keys()`. That implementation, `RwLockSecondaryIndexEntry::keys()` at [4](#0-3) , clones the entire underlying `HashSet<Pubkey>` for the given index key into a new `Vec<Pubkey>`.

The byte-limit protection, `scan_results_limit_bytes`, is implemented in `Accounts::load_by_index_key_with_filter` at [6](#0-5) : `config.abort()` is only called from inside the `scan_func` closure passed to `index_scan_accounts`, which is only invoked per successfully `do_load`-ed account — i.e., strictly after `get_index_key_pubkeys` has already returned the complete pubkey list. There is no size cap applied at the enumeration step itself: `AccountSecondaryIndexes::include_key`, at [5](#0-4) , defaults to including every key (`None => true, // include all keys`) unless the operator explicitly configured an include/exclude list, so no default cap on index-key membership size exists.

Consequently, the `do_load` loop that follows is correctly bounded (it checks `config.is_aborted()` before every `do_load`), but the antecedent enumeration/allocation step is not, and its cost scales with the total number of pubkeys ever mapped to that index key (e.g., all accounts owned by a given program, or all token accounts for a given mint/owner) — not with `scan_results_limit_bytes`.

## Impact Explanation
This falls under the single-client low-rate RPC degradation impact class. A validator operator running with a secondary index enabled (`--account-index program-id`/`spl-token-mint`/`spl-token-owner`) and `scan_results_limit_bytes` configured as a DoS mitigation would still be exposed: an unprivileged client can send a single `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByMint` RPC request naming a key with a very large index membership (e.g., a heavily used program id or popular mint/owner), forcing the RPC-serving thread to allocate and clone a potentially very large `Vec<Pubkey>` before the configured byte limit is ever consulted. This consumes CPU and memory proportional to total secondary-index membership for that key rather than the configured cap, degrading RPC/pubsub service for other clients on the node.

## Likelihood Explanation
The precondition (secondary index enabled + `scan_results_limit_bytes` configured as the operator's DoS mitigation) is a realistic, documented opt-in configuration, and large index-key membership sets (e.g., system/token program ids, popular mints) naturally exist on real clusters without any attacker action. The attacker needs no special privileges — a single public RPC call suffices, and it can be repeated at a low rate within normal client request limits to repeatedly trigger the uncapped allocation.

## Recommendation
Move the size/byte-limit (and abort) check into the pubkey-enumeration path itself — e.g., replace the eager `Vec<Pubkey>` collection in `SecondaryIndex::get`/`RwLockSecondaryIndexEntry::keys()` with a bounded/streaming iterator that `index_scan_accounts` can consult and short-circuit while enumerating (checking `config.is_aborted()` per enumerated pubkey rather than only per `do_load`), or add an explicit cap on the number of pubkeys enumerated per index key before proceeding to `do_load`, so a single request cannot force O(total-index-membership) allocation regardless of `scan_results_limit_bytes`.

## Proof of Concept
1. Start a validator with a secondary index enabled, e.g. `--account-index program-id`, and configure `scan_results_limit_bytes` to a small value (e.g. 4096 bytes) via `JsonRpcConfig`.
2. Populate the accounts index (or use an existing mainnet-scale index) such that one `program_id`'s secondary-index entry has a very large membership count, far exceeding `scan_results_limit_bytes` worth of accounts.
3. Issue a single `getProgramAccounts(program_id)` RPC call for that program id.
4. Measure CPU/memory: the RPC-processing thread performs an allocation/clone proportional to the total number of pubkeys indexed under that program id (`RwLockSecondaryIndexEntry::keys()` in `accounts-db/src/accounts_index/secondary.rs:104-106`) before `accumulate_and_check_scan_result_size`/`config.abort()` in `accounts-db/src/accounts.rs:396-433` is ever consulted — confirming the enumeration cost is unbounded by `scan_results_limit_bytes`, even though the subsequent `do_load` loop is correctly aborted shortly after the byte budget is exceeded.
