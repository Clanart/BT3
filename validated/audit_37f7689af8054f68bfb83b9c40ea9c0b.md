## Finding [1](#0-0) 

`getStatus()` invokes git with `--porcelain=2 -z` [2](#0-1)  and the parser comment explicitly documents that in `-z` mode git performs **no quoting/backslash-escaping of filenames**, relying only on the NUL byte as the field terminator [3](#0-2) . The path capture groups (`([\s\S]*?)$`) are permissive enough to swallow any byte sequence, including embedded `\n`, up to the NUL terminator [4](#0-3) . That raw path is stored verbatim on `WorkingDirectoryFileChange` [5](#0-4) .

That untrusted `file.path` is later interpolated, unescaped, directly into the unified-diff header used to build the patch fed to `git apply --cached` for partial-file staging and to `git apply` for discarding changes: [6](#0-5) [7](#0-6) 

### Title
Newline-containing filenames from an attacker-controlled repository can inject forged diff headers into `git apply` patches used for partial staging/discard - (File: app/src/lib/patch-formatter.ts)

### Summary
Git permits any byte except `/` and NUL in a tracked filename, including `\n`. GitHub Desktop's status parsing deliberately avoids the quoted/escaped path format (uses `--porcelain=2 -z`) and therefore stores such raw, newline-containing paths unmodified in `WorkingDirectoryFileChange.path`. This value is later spliced, without any sanitization, into the `--- a/…` / `+++ b/…` header lines that `formatPatchHeader` builds for the synthetic patches used when a user stages or discards individual lines. Because these patches are piped to `git apply` verbatim on stdin, an attacker who controls the contents of a cloned/fetched repository can plant a file whose name contains embedded newlines and diff-syntax sequences (`+++ b/`, `@@ … @@`, `---`), letting them inject fabricated header/hunk lines into the otherwise-trusted patch stream.

### Finding Description
- The broken invariant is: *"the string used to build a `git apply` patch header is a single, newline-free path component."* Desktop assumes this implicitly (it does string interpolation with no escaping) but the git-status parsing path used (`-z`, no quoting) is exactly the mode that does **not** guarantee it [3](#0-2) .
- `formatPatchHeader` builds the header purely via template strings on `from`/`to`, which ultimately come from `file.path`/`file.status.oldPath` with no validation for embedded control characters: [6](#0-5) , [8](#0-7) .
- `applyPatchToIndex` and `discardChangesFromSelection` pass the resulting text straight to `git apply` on stdin with no `--include=<path>` restriction, so git derives the target file purely from the `+++ b/…` line(s) present in the stream: [9](#0-8) , [10](#0-9) .
- Existing guards elsewhere in the codebase (`resolveWithin`, `sanitizeCloneName`, `testForInvalidChars`) only cover deep-link/clone-name inputs [11](#0-10) , [12](#0-11)  — none of them sanitize file paths coming from `git status` before they are used to build synthetic patches.

### Impact Explanation
If exploitable, a maliciously crafted repository could cause the patch text sent to `git apply --cached` to contain additional forged `--- a/…`/`+++ b/…`/`@@ … @@` sections, letting git target a file other than the one the user selected lines from. This would silently corrupt the contents actually staged and committed relative to what the user saw/selected in the UI — matching the "silent corruption of what the user commits" impact category, and is a strong structural analog of the seed bug (an internally-assembled, unsanitized data blob handed to a strict downstream parser/applier that interprets it in an unintended way).

### Likelihood Explanation
Exploitation requires that the victim clones/fetches a repository containing a file whose name embeds a newline followed by diff-syntax content, and then uses Desktop's line-level partial stage or discard feature on that file (a normal, expected user action, not requiring elevated privileges or local access). Creating such a filename requires the attacker to control repository content, which is explicitly in-scope per the valid-impact criteria.

### Recommendation
- Reject or escape filenames containing `\n`/`\r` (or other control characters) at the point `entry.path`/`oldPath` are captured in `status-parser.ts`, or switch away from raw `-z` parsing to the quoted/escaped mode and properly unescape.
- Defensively validate `file.path` and `file.status.oldPath` in `formatPatchHeader`/`formatPatchHeaderForFile` before use, rejecting any path containing a newline.
- Constrain `git apply`/`git apply --cached` invocations with an explicit path argument or `--include=<path>` so the applied header cannot redirect changes to an unintended file even if header text is corrupted.

### Proof of Concept
Conceptual PoC (cannot be executed here without a live checkout, and I was not able to verify end-to-end in a sandbox — this is inferred from the code path and documented git status behavior, not confirmed via a live run):
1. Attacker creates a repository containing a tracked file whose actual name is:
   `legit.txt\n+++ b/../../../outside/target.txt`
   (a single filename containing a literal newline followed by diff-syntax text — permitted since only `/` and NUL are forbidden in POSIX filenames).
2. Victim clones this repository in GitHub Desktop and modifies `legit.txt`, then uses the per-line staging UI to stage a subset of lines.
3. `getStatus()`/`parsePorcelainStatus()` (using `-z`, no escaping) returns the raw path including the embedded newline into `WorkingDirectoryFileChange.path` [4](#0-3) .
4. `formatPatch()` → `formatPatchHeaderForFile()` → `formatPatchHeader()` interpolates this raw path into the `--- a/…`/`+++ b/…` lines [6](#0-5) , producing a patch text containing an extra, attacker-controlled header line.
5. `applyPatchToIndex()` pipes this text to `git apply --cached -` [7](#0-6) , where git parses headers from the stream itself — the forged `+++ b/…` line can cause `git apply` to target a different file than the one the user intended to stage.

Given the reasoning-effort constraints of this session, I was unable to fully execute an end-to-end reproduction (creating an actual newline-containing filename via git plumbing and confirming `git apply`'s exact header-selection behavior with a forged embedded header). This should be validated empirically before treating it as a confirmed exploit chain.

function formatPatchHeader(from: string | null, to: string | null): string {
  // https://en.wikipedia.org/wiki/Diff_utility
  //
  // > At the beginning of the patch is the file information, including the full
  // > path and a time stamp delimited by a tab character.
  // >
  // > [...] the original file is preceded by "---" and the new file is preceded
  // > by "+++".
  //
  // We skip the time stamp to match git
  const fromPath = from ? `a/${from}` : '/dev/null'
  const toPath = to ? `b/${to}` : '/dev/null'

  return `--- ${fromPath}\n+++ ${toPath}\n`
}

function formatPatchHeaderForFile(file: WorkingDirectoryFileChange) {
  switch (file.status.kind) {
    case AppFileStatusKind.New:
    case AppFileStatusKind.Untracked:
      return formatPatchHeader(null, file.path)

    // One might initially believe that renamed files should diff
    // against their old path. This is, after all, how git diff
    // does it right after a rename. But if we're creating a patch
    // to be applied along with a rename we must target the renamed
    // file.
    case AppFileStatusKind.Renamed:
    case AppFileStatusKind.Deleted:
    case AppFileStatusKind.Modified:
    case AppFileStatusKind.Copied:
    // We should not have the ability to format a file that's marked as
    // conflicted without more information about it's current state.
    // I'd like to get to a point where `WorkingDirectoryFileChange` can be
    // differentiated between ordinary, renamed/copied and unmerged entries
    // and we can then verify the conflicted file is in a known good state but
    // that work needs to be done waaaaaaaay before we get to this point.
    case AppFileStatusKind.Conflicted:
      return formatPatchHeader(file.path, file.path)
    default:
      return assertNever(file.status, `Unknown file status ${file.status}`)
  }
}

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}
