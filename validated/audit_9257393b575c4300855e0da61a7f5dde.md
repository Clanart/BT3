### Title
Submodule updates unconditionally re-enable `file://` protocol, allowing a malicious repository to clone/read arbitrary local paths - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag; when true it prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. This deliberately overrides Git's own hardened default (Git ≥2.31 disallows `file://` submodule URLs by default, specifically to stop malicious repos from smuggling local-filesystem submodules — the fix for the "submodule remote code/data exfiltration" class of Git CVEs). This function is invoked from `app/src/lib/git/checkout.ts` when Desktop checks out a branch/PR that contains submodules. [1](#0-0) 

### Finding Description
A `.gitmodules` file is fully attacker-controlled content in any repository or branch a user opens, forks a PR from, or fetches (e.g. via `openPullRequestFromUrl`/`_checkoutPullRequest`, which fetches and checks out a fork's ref). If that `.gitmodules` declares a submodule URL using the `file://` scheme pointing at an arbitrary local path (e.g. another private repository elsewhere on the victim's disk, or a sensitive directory that happens to be a git repo), Git itself refuses this by default as a defense against this exact scenario. Desktop's `updateSubmodulesAfterOperation` re-enables it via `protocol.file.allow=always` when `allowFileProtocol` is true, and this is exercised from the checkout flow in `checkout.ts`. [2](#0-1) 

The rest of the codebase shows evidence that the maintainers are otherwise careful about "attacker-controlled repo/URL → local filesystem" issues (e.g., the explicit backstop in `clone.ts` against path traversal into `.ssh`/`.gnupg`/`.config`, and `resolveWithin` checks in `dispatcher.ts`'s `openRepositoryFromUrl` for the `filepath` deep-link parameter). No equivalent guard exists for `file://` submodule URLs — the check that upstream Git added specifically for this attack class is explicitly disabled instead of being preserved. [3](#0-2) [4](#0-3) 

### Impact Explanation
If exploitable along the checkout path with an attacker-authored branch/fork/PR, this lets a hostile repository force Desktop to run `git submodule update --init` against a `file://` URL, i.e., clone from an arbitrary local path on the victim's machine into the working tree of the untrusted repo — with no credential prompt and no confirmation that this is a local, not remote, source. Depending on what local path is targeted, this can read/copy the contents of other local git repositories (potentially private/sensitive) into the malicious repository's working directory, which the user may then unknowingly commit and push (data exfiltration / silent corruption of what gets committed), matching the "file read outside the repo" and "silent corruption of what the user commits" categories in the impact criteria.

### Likelihood Explanation
Likelihood depends on exactly which checkout paths pass `allowFileProtocol: true` and whether they run without additional gating — I could not fully confirm this from `checkout.ts` before the tool budget was exhausted. If it applies broadly to normal branch/PR checkout (as the function's design suggests, since it exists specifically to support "the app always wants submodules to work"), the likelihood is high because opening a PR from an untrusted fork or checking out an untrusted branch is a normal, expected Desktop workflow requiring no unusual user action.

### Recommendation
Do not pass `allowFileProtocol: true` for submodule operations triggered on repositories/branches whose content is not fully trusted (i.e., default to Git's hardened `protocol.file.allow` behavior). If local-path submodules must be supported for legitimate local development, gate `allowFileProtocol` behind an explicit, informed user opt-in per repository, and additionally validate/restrict the resolved submodule path with the same kind of traversal/sensitive-path checks already implemented in `isClonePathSensitive` (`app/src/lib/git/clone.ts`).

### Proof of Concept
Conceptual PoC (not independently executed, based on code inspection):
1. Attacker creates/forks a public GitHub repository and adds a `.gitmodules` entry: `[submodule "x"] path = x url = file:///Users/victim/some-other-local-repo`.
2. Attacker opens a pull request from this fork, or shares an "Open in Desktop" deep link / branch URL.
3. Victim, using GitHub Desktop, opens the PR/branch (`dispatcher.ts` → `openPullRequestFromUrl`/`openBranchNameFromUrl` → checkout flow).
4. Desktop's checkout path calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`, which runs `git -c protocol.file.allow=always submodule update --init --recursive`, cloning the victim's local path directly into the malicious repo's working tree instead of refusing per Git's hardened default. /**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
