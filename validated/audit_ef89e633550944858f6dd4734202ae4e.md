### Title
OP_RETURN data is excluded from Bitcoin fee and weight accounting, enabling underpriced transactions that can remain uncancellable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Medium. `SignableTransaction::new` appends caller-controlled OP_RETURN data to `tx_outs`, but both fee and maximum-weight calculations are performed on a transaction containing only `payments`, not the actual `tx_outs`. [1](#0-0) [2](#0-1) 

### Finding Description
The function adds the OP_RETURN output before calculating `vbytes`, but calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing `payments` rather than `tx_outs`. [3](#0-2)  The change-aware calculation repeats the same omission, so adding change does not account for the OP_RETURN output either. [2](#0-1) 

Consequently, `needed_fee` is `fee_per_vbyte * vbytes_without_data`, while the signed transaction includes up to 80 additional bytes of data plus output overhead. [4](#0-3)  The standardness check likewise uses `weight` calculated without the OP_RETURN output, allowing a transaction to pass `MAX_STANDARD_TX_WEIGHT` even though its actual weight exceeds the limit. [5](#0-4) 

All inputs are constructed with `Sequence::MAX`, so the transaction does not opt into BIP-125 replaceability under default policy. [6](#0-5) 

### Impact Explanation
A caller can obtain threshold signatures for a transaction whose actual fee rate is lower than requested and potentially below the relay minimum. [7](#0-6)  If the transaction is accepted but remains pending, the selected UTXOs are occupied by a non-RBF transaction with no dedicated cancellation path in `TransactionMachine` or `TransactionSignMachine`. [8](#0-7)  At the boundary, the omitted output can also make the signed transaction non-standard despite the explicit size check. [9](#0-8) 

### Likelihood Explanation
The bug is reachable whenever public transaction data is supplied through the `data` parameter, which is explicitly allowed up to 80 bytes. [10](#0-9) [11](#0-10)  The in-tree processor currently passes `None` for this parameter, so the exposed path is the production `bitcoin-serai` wallet API or integrations which forward transaction data into it. [12](#0-11) 

### Recommendation
Calculate `weight`, `vbytes`, `needed_fee`, and the standardness limit from the complete candidate transaction after appending payments, OP_RETURN data, and any change output. [13](#0-12)  At minimum, change `calculate_weight_vbytes` to accept the actual `tx_outs` rather than `payments`, and assert that `self.fee()` is at least `fee_per_vbyte` multiplied by the final transaction’s actual virtual size before returning `SignableTransaction`. [14](#0-13) 

### Proof of Concept
```rust
// Conceptual PoC for networks/bitcoin/src/wallet/send.rs.

// First determine the fee calculated without data.
let no_data = SignableTransaction::new(
    vec![received_output.clone()],
    &[(payment_script.clone(), 1_000)],
    None,
    None,
    1,
).unwrap();

let underpriced_fee = no_data.needed_fee();

// Spend the entire remainder so the actual fee equals `underpriced_fee`.
let payment = received_output.value() - underpriced_fee;
let with_data = SignableTransaction::new(
    vec![received_output],
    &[(payment_script, payment)],
    None,
    Some(vec![0; 80]),
    1,
).unwrap();

assert_eq!(with_data.fee(), underpriced_fee);
assert!(with_data.transaction().vsize() as u64 > underpriced_fee);
```

The second transaction’s actual virtual size includes the OP_RETURN output, while `needed_fee` and `fee()` still equal the value calculated for the transaction without that output. [1](#0-0)  A one-input transaction near the relay minimum can thereby be signed with an actual fee rate below the requested and minimum rates, while its `Sequence::MAX` inputs prevent ordinary BIP-125 replacement. [6](#0-5)
