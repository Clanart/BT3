### Title
Recursive precompile calls share a single `BalanceHandler` instance, corrupting the event window used to reconcile native bank balances into EVM StateDB - (File: precompiles/common/balance_handler.go)

### Summary
The Rubicon finding is a class of bug where a multi-step accounting process ("loop") fails to correctly account for one step's effect on collateral/balance, leaving a mismatch between the tracked collateral and actual exposure. The Cosmos EVM analog is the `BalanceHandler` used by stateful precompiles to reconcile Cosmos SDK `x/bank` events into the EVM `StateDB`. It records a single `prevEventsLen` cursor between `BeforeBalanceChange` and `AfterBalanceChange` [1](#0-0) , and then only processes `events[bh.prevEventsLen:]` in `AfterBalanceChange` [2](#0-1) . If a precompile call recursively/nestedly triggers another precompile call that shares the *same* `BalanceHandler` instance (rather than a fresh instance per call), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, corrupting the window the outer call later uses to reconcile bank events into StateDB balances.

### Finding Description
`RunNativeAction` in `precompiles/common/precompile.go` obtains a *new* `BalanceHandler` per invocation via `p.BalanceHandlerFactory.NewBalanceHandler()` [3](#0-2) , which is safe for nested calls. However several precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) instead expose/consume a single `balanceHandler` via `GetBalanceHandler()` used directly in their top-level `Run` entrypoint pattern, mirrored by `testutil/testdata/debug/debug.go`'s `Run`, which calls `p.GetBalanceHandler().BeforeBalanceChange(ctx)` ... `p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB)` around contract execution [4](#0-3) . If that handler is a field on the long-lived precompile object rather than freshly created per call, any nested/recursive precompile invocation within the same EVM transaction (e.g. a token's `_beforeTokenTransfer` hook calling `distribution.claimRewards` recursively, as built specifically to test this in `ERC20RecursiveRevertingPrecompileCall.sol` [5](#0-4) ) will reset `prevEventsLen` mid-flight for the outer call. This is exactly analogous to the Rubicon bug: the "last" segment of a multi-step accounting sequence (the outer call's remaining bank events) is left unreconciled (or double-reconciled) against StateDB, producing a real corruption between the bank module's ledger (source of truth for spendable native coins) and the EVM `StateDB` balances that determine what contracts can spend/transfer.

This exact scenario is directly documented and reproduced in-repo by two purpose-built regression tests:
- `evmd/tests/integration/balance_handler/balance_handler_test.go`, whose suite doc states: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [6](#0-5) 
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`, whose suite doc states: "Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [7](#0-6) , and which exercises both a reverting and non-reverting recursive precompile call path through an ICS20 transfer of a native ERC20 [8](#0-7) .

### Impact Explanation
If the corrupted `prevEventsLen` window causes bank-module `CoinSpent`/`CoinReceived` events to be skipped or replayed against `StateDB.AddBalance`/`SubBalance`, the EVM-visible balance of an account can diverge from its true bank-module balance. Because EVM contract logic (transfers, approvals, further precompile calls) acts on the `StateDB` balance, this can result in unauthorized duplication of spendable value (EVM side shows more than the bank module actually holds) or permanent loss/freezing (bank module holds funds no longer reflected in `StateDB`), i.e. spendable-value accounting corruption between native balances and EVM balances, matching the Critical impact criteria in scope for this repository.

### Likelihood Explanation
Triggering requires only an ordinary, unprivileged user to deploy a token contract with hooks (e.g. `_beforeTokenTransfer`) that make a nested call into a stateful precompile (distribution/staking/gov/ics20/erc20) during a transaction that itself is executing through a precompile call, then invoke a transfer that traverses this path (as shown by the already-existing PoC contract `ERC20RecursiveRevertingPrecompileCall.sol` and the dedicated `ICS20RecursivePrecompileCallsTestSuite`). No privileged role, validator collusion, or governance action is needed.

### Recommendation
Ensure every precompile entrypoint (not just `RunNativeAction`'s native-action path) constructs a fresh `BalanceHandler` per top-level `Run` invocation (mirroring the `BalanceHandlerFactory.NewBalanceHandler()` pattern already used in `precompile.go`), or otherwise make `prevEventsLen` re-entrancy-safe (e.g., a stack of cursors, or disallow nested precompile calls from mutating a handler owned by an outer, still-in-flight call). Add an invariant check that after `AfterBalanceChange`, the aggregate `StateDB` balance deltas for the involved denom equal the aggregate `x/bank` balance deltas for the same accounts within the transaction.

### Proof of Concept
The repository already contains a working PoC for this class of bug:
1. `contracts/solidity/ERC20RecursiveRevertingPrecompileCall.sol` overrides `_beforeTokenTransfer` to recursively call `claimRewardsAndRevert()` (a distribution precompile call) in a loop, then revert each nested call [5](#0-4) .
2. `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`'s `TestHandleMsgTransfer` deploys this contract, delegates/stakes from it, and then performs an ICS20 transfer of the resulting native ERC20 token through the precompile, asserting on distribution reward and event-count discrepancies caused by the balance-handler bug for both the reverting and non-reverting variants [9](#0-8) .

type BalanceHandler struct {
