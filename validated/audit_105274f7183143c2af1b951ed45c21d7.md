### Title
Quadratic-Time Offer Cancellation DoS via Crafted Coin Announcement Dependencies - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_cancellation_coins()` repeatedly calls `detect_dependent_coin()`, which walks every coin's dependency list against every other coin's announcement list in a triple-nested loop, and wraps that in an outer `while True` loop that removes coins one at a time. A counterparty can hand a wallet user an `Offer` (offer file) whose coin spends contain a large number of `CREATE_COIN_ANNOUNCEMENT` / `ASSERT_COIN_ANNOUNCEMENT` conditions and dependency chains, and the client-side complexity of resolving cancellation blows up superlinearly relative to spend/announcement counts, causing the wallet to hang. This is structurally analogous to Tornado's `_parseparam`: an attacker-controlled input drives an unbounded, nested nested-loop parsing/matching routine on a single request/action.

### Finding Description
`detect_dependent_coin()` is defined as: [1](#0-0) 

Its body iterates `for name in names: for dependency in deps[name]: for coin, announces in announcement_dict.items(): if dependency in announces ...` — an O(N·D·K·A) scan (N = coin count, D = deps per coin, K = number of coins in the announcement map, A = announces per coin), all of which are attacker-controllable by crafting an offer with many coin spends that each emit many `ASSERT_COIN_ANNOUNCEMENT` conditions referencing announcements from many other coins in the same bundle.

This function is invoked from `Offer.get_cancellation_coins()`, which builds `dependencies`/`announcements` maps from every non-addition coin spend in the offer by running each puzzle/solution and collecting `CREATE_COIN_ANNOUNCEMENT` (opcode 60) and `ASSERT_COIN_ANNOUNCEMENT` (opcode 61) conditions: [2](#0-1) 

It then runs an outer `while True:` loop that calls `detect_dependent_coin` repeatedly, and for each match performs an *inner* `while True:` loop scanning `dependencies.items()` against removed announcements: [3](#0-2) 

Because the outer loop can iterate up to N times (once per coin removed) and each iteration re-scans the full dependency/announcement structure, and the inner loop also rescans all `dependencies.items()`, the overall complexity for a maliciously constructed offer with many coins and many cross-referencing announcements per coin is quadratic or worse in the number of coin spends and announcements — not O(1) cost-bounded CLVM execution, but pure Python-side iteration performed once the conditions have already been extracted.

This is client-side, wallet-local processing that is not gated by the mempool's `MAX_BLOCK_COST_CLVM` per-spend-bundle CLVM cost limit or by the 1024-per-opcode announcement cap enforced during consensus/mempool validation (that cap applies to spends being validated for chain inclusion, not to an `Offer` object a wallet is merely inspecting/cancelling before ever submitting it). An attacker acting as an offer counterparty can send an `.offer` file containing many coin spends each producing many self-referential/interlinked announcement conditions; the victim wallet only needs to call `cancel_offer`-style functionality (which invokes `get_cancellation_coins()`) on the received, not-yet-accepted offer to trigger the pathological blowup.

### Impact Explanation
A single crafted offer file, once loaded and acted on (e.g., cancelled) by a wallet, can cause the wallet process to spend an extended, disproportionate amount of CPU time in Python-level nested loops, unresponsive to other wallet RPC calls during that time — a spend/action-triggered processing halt of the wallet component. This matches the CWE-400/algorithmic-complexity class from the reference advisory, translated to the wallet's offer-cancellation code path rather than an HTTP parser.

### Likelihood Explanation
Likelihood is dependent on how large/complex an offer a victim wallet is willing to load and how many distinct coin spends and announcement dependencies can be embedded in a single offer while staying under whatever practical constraints exist on offer size and CLVM cost when *constructing* — not cancelling — the offer's conditions. I was not able to fully confirm within the tool budget whether any additional cap (e.g., a limit on the number of coin spends per offer, or an earlier point where announcement counts are constrained before `get_cancellation_coins()` is reached) mitigates the worst-case blowup, nor did I see the remainder of `detect_dependent_coin()`'s body beyond line 60. This should be verified with a live reproduction (e.g., a crafted offer with thousands of coin spends and dense announcement cross-references, then timing `get_cancellation_coins()`), which I could not execute given the available tools.

### Recommendation
- Rework `detect_dependent_coin()`/`get_cancellation_coins()` to use hash-based lookups (e.g., building an announcement-to-coin index once) instead of repeated linear/triple-nested scans, so the amortized complexity is O(N) or O(N log N) instead of superlinear per outer-loop iteration.
- Enforce a sane upper bound on the number of coin spends and announcement conditions considered when computing cancellation coins for an `Offer` before doing the expensive dependency resolution, independent of consensus-side per-block limits.
- Add a benchmark/regression test (similar to `chia/_tests/wallet/test_offer_parsing_performance.py`) that specifically exercises `get_cancellation_coins()` with a pathological, densely cross-referenced offer to catch superlinear blowups.
