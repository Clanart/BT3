### Title
Flashloan-inflatable solver balance lets an attacker skew the liquidity-weighted `medianPrice` used to size real IntentGateway orders - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` computes a phantom order's settlement-reference price as a **liquidity-weighted median** of solver quotes, where each quote's weight is the solver's *live, self-controlled* ERC-20/ERC-4626 balance read via `eth_call` at aggregation time [3](#0-2) . Because "becoming a solver" only requires an unprivileged EIP-7702 delegation to the public `SolverAccount` contract [2](#0-1) , any attacker can flashloan/borrow the output token, temporarily inflate their own on-chain balance, submit one lowball (or extreme) bid, and have it dominate `weightedMedian` — exactly the ZivoeYDL-style "inflate totalSupply/weight right before the snapshot" primitive, just applied to a per-solver ERC-20 balance instead of a token's `totalSupply()`.

### Finding Description
`weightedMedian` weights each price purely by `weight` with no minimum holding period, no historical/TWAP balance, and no cap per solver [4](#0-3) . The weight itself is fetched with a single `eth_call({..., "latest"})` against the *live* head at aggregation time [5](#0-4) [6](#0-5) , so it captures whatever balance the solver happens to hold at that instant — including balance acquired via a same-block flashloan and returned immediately after. This snapshot is not merely informational: `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` feeds `snapshot.medianPrice` directly into the formula that sizes a *real* IntentGateway order's `amountIn`/`amountOut` (`amountOut = netAmountIn * medianPrice / standardAmount`, and the inverse for exact-output) [7](#0-6) . The docs confirm callers are told to use these amounts directly with no additional slippage adjustment [8](#0-7) .

Existing guards (signature-over-userOpHash binding, nonce-to-(commitment,session) binding, per-solver de-duplication, EIP-7702 delegation check) all verify *authenticity/uniqueness of the bid*, not the *economic weight* backing it [9](#0-8) . None of them prevent a genuinely-delegated solver from transiently ballooning its own balance for the single `eth_call` that measures `weight`.

### Impact Explanation
Since real users size their cross-chain `IntentGateway` orders (`inputs`/`output.assets`) off `medianPrice` with no other bound [10](#0-9) , an attacker-controlled "solver" can:
- Flashloan-inflate its own output-token balance right before the phantom order's bid window closes.
- Submit an extreme quote that, weighted by the inflated balance, dominates the weighted median.
- Force the snapshot's `medianPrice` far from the true competitive price for that window.
- Users (or the SDK on their behalf) then construct real escrowed orders against this skewed price, either overpaying input for a given output or receiving less output than fair value — a direct value-transfer/mispricing loss on production bridge order flow, matching the "false state acceptance / transaction manipulation" bounty category (here, false *price* acceptance driving fund-losing order construction).

### Likelihood Explanation
High feasibility, low cost: solver delegation is permissionless (any EOA, no bond/approval) [1](#0-0) ; the weight read is a single unprotected `eth_call` at `"latest"` with no averaging window [5](#0-4) ; and the aggregation is triggered deterministically off the `PhantomBidWindowExhausted` event, so an attacker can time the balance inflation to land exactly in the block the indexer/SDK reads [11](#0-10) . This is currently limited to the Phantom order pairs (USDC/USDT/cNGN on Base) [12](#0-11) , and would need the output token (or ERC-4626 vault backing it) to be flashloan-borrowable, which bounds — but does not eliminate — real-world exploitability.

### Recommendation
- Weight bids by a time-averaged or historical balance (e.g. min-balance-over-window, or balance snapshotted several blocks before the aggregation call) rather than a single `"latest"` read.
- Cap a single solver's influence on the weighted median (e.g. clamp weight to a governance-set ceiling) so no one bid, however well-funded momentarily, can dominate the median.
- Require solvers to demonstrate sustained balance (e.g. balance held for N blocks, or balance net of same-block inflow) before it counts toward weight.
- Consider requiring multiple independent snapshots across blocks and taking a median-of-medians to dampen single-block manipulation.

### Proof of Concept
1. Attacker deploys/controls EOA `A`, delegates it to the public `SolverAccount` via EIP-7702 (permissionless, no allowlist) — matches the real solver bootstrap flow in `evm/src/apps/intentsv2/SolverAccount.sol`.
2. Attacker watches for a phantom order's bid window; near its close, flashloans a large amount of the order's output token (or deposits into/withdraws from a configured ERC-4626 vault to spike `maxWithdraw`) into `A`.
3. Attacker submits one valid, correctly-signed, correctly-nonce-bound bid quoting an extreme price from `A`.
4. `handlePhantomOrderPrices` fires on `PhantomBidWindowExhausted`, calls `aggregatePhantomBids`, which reads `A`'s balance via `getTotalSolverBalance` — capturing the flashloan-inflated amount — and uses it as `weight` in `weightedMedian`, skewing `medianPrice` toward `A`'s quote [13](#0-12) .
5. Attacker repays the flashloan in the same transaction/block; `A`'s balance returns to ~0.
6. The skewed `PhantomOrderPriceSnapshot.medianPrice` is persisted and subsequently consumed by `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` to size real users' `amountIn`/`amountOut` for actual escrowed `IntentGateway` orders, without further validation [7](#0-6) .

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

/**
 * Whether a bid genuinely came from one of our solvers, and so may influence the snapshot.
 *
 * Anyone can submit a bid to the coprocessor, and every accepted quote moves the weighted median the
 * rest of the protocol prices intents against, so a bid is only counted if it clears both of the
 * checks SolverAccount would apply on-chain: the userOp carries a solver signature over this order's
 * userOpHash that recovers to the sender, and the sender is EIP-7702-delegated to the chain's
 * SolverAccount. Fails closed — a bid that cannot be read or verified is not counted.
 */
async function isVerifiedSolverBid(params: {
	userOp: PackedUserOperation
	commitment: string
	sessionKey: HexString
	chainId: bigint
	solverAccount: string
	evmRpcUrl: string
	recoverSigner: RecoverBidSigner
	bidNonceKey: BidNonceKeyFn
	logger?: AggregationLogger
}): Promise<boolean> {
	const { userOp, commitment, sessionKey, chainId, solverAccount, evmRpcUrl, recoverSigner, bidNonceKey, logger } =
		params
	const solver = userOp.sender

	const parsed = splitBidSignature(userOp.signature)
	if (!parsed) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: malformed userOp signature")
		return false
	}

	// Cheap early-out ONLY. The prefix sits inside userOp.signature, which userOpHash excludes, so it
	// is attacker-mutable and must never be what binds a bid to an order — the nonce key below is.
	if (parsed.commitment.toLowerCase() !== commitment.toLowerCase()) {
		logger?.warn(
			{ solver, commitment, signedFor: parsed.commitment },
			"Rejecting phantom bid: signed for another order",
		)
		return false
	}

	// The authoritative binding, mirroring SolverAccount.validateUserOp on-chain. The nonce IS
	// covered by userOpHash, so a solver signature stays valid only for the (order, sessionKey) pair
	// its nonce key was derived from. `sessionKey` is read from the bid's own calldata, which is also
	// covered by userOpHash — so every operand here is signed, leaving nothing for a replay to swap.
	if (BigInt(userOp.nonce) >> 64n !== bidNonceKey(commitment as HexString, sessionKey)) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: nonce does not bind order and session key")
		return false
	}

	// SolverAccount._rawSignatureValidation recovers over the bare userOpHash and requires the signer
	// to be the account itself, which under EIP-7702 is the sender EOA.
	const signer = await recoverSigner(userOp, ENTRY_POINT_V08_ADDRESS, chainId, parsed.solverSignature)
	if (!signer || signer.toLowerCase() !== solver.toLowerCase()) {
		logger?.warn({ solver, commitment, signer }, "Rejecting phantom bid: signature does not recover to the sender")
		return false
	}

	if (!(await isDelegatedToSolverAccount(evmRpcUrl, solver, solverAccount))) {
		logger?.warn({ solver, commitment, solverAccount }, "Rejecting phantom bid: sender is not a delegated solver")
		return false
	}

	return true
}
