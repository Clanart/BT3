### Title
DID transfer silently carries over the old owner's recovery configuration (`backup_ids`/`num_of_backup_ids_needed`), letting a colluding old owner retain covert control over the transferred DID - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
This is a plausible analog to the Ajna finding, but I could not fully verify the on-chain recovery-spend CLVM semantics (the `did_innerpuz.clsp`/compiled puzzle contents were not available in the index), so the exploitability claim below carries that caveat. The code-level pattern, however, is a direct match to the reported bug class: state controlled by the *old* owner (a DID's recovery/backup configuration) is copied unchanged into the *new* owner's puzzle during a transfer, with no validation and no requirement that the new owner consent to or reset it.

### Finding Description
When a DID is transferred to a new owner, `DIDWallet.transfer_did` builds the new owner's inner puzzle hash using the **current, old-owner-controlled** `backup_ids` and `num_of_backup_ids_needed` values verbatim: [1](#0-0) 

```
coin = await self.get_coin()
backup_ids = []
backup_required = uint64(0)
backup_ids = self.did_info.backup_ids
backup_required = self.did_info.num_of_backup_ids_needed
new_did_puzhash = did_wallet_puzzles.get_inner_puzhash_by_p2(
    p2_puzhash=new_puzhash,
    ...
```

These values are curried directly into the new coin's puzzle (`get_inner_puzhash_by_p2`), which computes the DID inner-puzzle hash from `p2_puzhash`, `recovery_list`/`recovery_list_hash`, and `num_of_backup_ids_needed`: [2](#0-1) 

The same pattern recurs in `get_innerpuz_for_new_innerhash`, which is explicitly documented as preserving the seller's backup list unless the seller manually clears it first: [3](#0-2) 
```

    """
    Get the inner puzzle for a new owner
    :param pubkey: Pubkey
    :return: Inner puzzle
    """
    # Note: the recovery list will be kept.
    # In a selling case, the seller should clean the recovery list then transfer to the new owner.
```

`DIDInfo.backup_ids` and `num_of_backup_ids_needed` are exactly the on-chain recovery configuration curried into `DID_INNERPUZ_MOD`: [4](#0-3) 

This mirrors the Ajna bug class precisely: on ownership transfer, a piece of state that is fully under the *previous* owner's control (`backup_ids`/`num_of_backup_ids_needed`, analogous to `depositTime`) is adopted unchanged by the new owner's coin/puzzle, without any validation or explicit new-owner acknowledgment. A malicious or careless seller (or an attacker colluding with the seller) can leave (or maliciously set) a recovery configuration — e.g., a low `num_of_backup_ids_needed` with an attacker-controlled DID in `backup_ids` — before transferring the DID. The buyer receives a coin whose puzzle hash was computed from those attacker-influenced parameters, and has no wallet-level signal that a recovery path with attacker-controlled backup IDs is baked into the puzzle they now hold.

### Impact Explanation
If the on-chain recovery mechanism curried into `DID_INNERPUZ_MOD` allows a listed backup DID to participate in producing a valid recovery/attestation spend for the coin (this is the documented purpose of `backup_ids`/`num_of_backup_ids_needed` in the DID puzzle), then an attacker DID left in the list by a colluding seller retains latent leverage over a DID coin the new owner believes they solely control. This could translate into unauthorized interference with, or hijacking of, the DID coin/identity after the transfer — a coin-identity/ownership integrity issue reachable purely through a standard wallet DID transfer (`transfer_did`), i.e., an unprivileged wallet action, with no node/network compromise required. I was not able to fully confirm the exact recovery-spend CLVM logic (e.g., whether recovery still requires the *current* p2 puzzle's cooperation, since `did_recovery_spend`/`did_update_recovery_ids` wallet RPCs were removed per `CHANGELOG.md`), so I cannot state with certainty whether this rises to unauthorized fund/coin movement without any current-owner action. That uncertainty should be resolved by inspecting the compiled `did_innerpuz` puzzle's recovery branch directly.

### Likelihood Explanation
This requires deliberate collusion (the seller intentionally leaves/sets a malicious recovery list before selling/transferring), similar to the Ajna report's threat model ("attacker could collude with the old owner"). It does not require any privileged access — any DID seller can trigger this via the ordinary `transfer_did` wallet flow, and buyers are not shown or prompted to validate the recovery configuration being inherited.

### Recommendation
- When transferring a DID (`transfer_did` / `get_innerpuz_for_new_innerhash`), require the new owner (or the transfer flow) to explicitly reset `backup_ids` to empty and `num_of_backup_ids_needed` to `0` by default, rather than defaulting to preserving the old owner's recovery configuration.
- At minimum, surface the inherited recovery configuration (`backup_ids`, `num_of_backup_ids_needed`) prominently to the new owner/buyer before accepting a DID transfer or offer, so it can be independently verified against the puzzle reveal rather than silently trusted.
- Consider deprecating/disallowing DID transfers that keep a non-empty backup list unless the new owner explicitly opts in.

### Proof of Concept
Conceptual (wallet-level) PoC, following the exact code path identified:
1. Old owner (colluding attacker) sets `did_info.backup_ids = [attacker_did]` and `num_of_backup_ids_needed = 1` on their DID (a supported, ordinary DID configuration).
2. Old owner calls `transfer_did(new_puzhash, fee, action_scope)` to sell/transfer the DID to a new owner. `transfer_did` computes `new_did_puzhash` using the attacker-controlled `backup_ids`/`num_of_backup_ids_needed` unchanged: [5](#0-4) 
3. The new owner accepts the transfer/offer, receiving a DID coin whose puzzle hash encodes the attacker's backup DID as a recovery participant, with no explicit warning or validation step in the wallet flow.
4. Whether this can be leveraged into unauthorized control of the coin depends on the exact recovery-spend semantics of `DID_INNERPUZ_MOD`, which I could not fully verify in this pass (the compiled puzzle source was not present in the indexed files). A background agent with full repository/file access should inspect `did_innerpuz.clsp` (or the compiled bytes referenced by `DID_INNERPUZ_MOD` in `chia/wallet/did_wallet/did_wallet_puzzles.py`) to confirm whether the recovery branch permits a listed backup DID to move/reassign the coin without the current p2 puzzle's cooperation.

```python
def get_inner_puzhash_by_p2(
    p2_puzhash: bytes32,
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list: list[bytes32] | None = None,
    recovery_list_hash: Program | None = None,
) -> bytes32:
    """
    Calculate DID inner puzzle hash based on a P2 puzzle hash
    :param p2_puzhash: P2 puzzle hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :return: DID inner puzzle hash
    """

    if recovery_list is None and recovery_list_hash is None:
        raise ValueError("Cannot construct DID inner puzzle without information about recovery list")

    # Allow both recovery_list and recovery_list_hash to be provided but
    # in that case the list is ignored and the hash is used
    # this matches the behaviour of create_innerpuz
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash.as_atom()
    else:
        assert recovery_list is not None
        backup_ids_hash = shatree_atom_list(recovery_list)

    # singleton_struct = (MOD_HASH . (LAUNCHER_ID . LAUNCHER_PUZZLE_HASH))
    singleton_struct = shatree_pair(
        SINGLETON_TOP_LAYER_MOD_HASH_TREE_HASH,
        shatree_pair(shatree_atom(launcher_id), SINGLETON_LAUNCHER_PUZZLE_HASH_TREE_HASH),
    )

    return curry_and_treehash(
        DID_INNERPUZ_MOD_HASH_QUOTED,
        p2_puzhash,
        shatree_atom(backup_ids_hash),
        shatree_int(num_of_backup_ids_needed),
        singleton_struct,
        metadata.get_tree_hash(),
    )
```
