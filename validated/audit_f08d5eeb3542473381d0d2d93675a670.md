### Title
Stale line-index selection is silently re-applied to a changed diff, allowing an attacker-controlled working-tree mutation (e.g. via a Git hook) to make Desktop commit/stage unintended content - (File: `app/src/lib/stores/app-store.ts`)

### Summary
This mirrors the seed bug's core flaw: a security/consistency-relevant piece of state (which specific line indices are "included") is carried forward from an old snapshot and blindly merged into a new one instead of being safely recomputed relative to the new state, on the assumption that the two snapshots describe the same underlying content. In the seed report, `stake_start_epoch` was kept from a stale computation (`max` of old/new) instead of being pinned to the next epoch. In GitHub Desktop, `DiffSelection`'s set of user-selected line *indices* (`divergingLines`) is preserved across a diff refresh by index alone, filtered only against the new selectable-line set, not against the actual textual content at those indices.

### Finding Description
When the working directory diff for the currently selected file is (re)loaded, `updateChangesWorkingDirectoryDiff` recomputes the new diff and then calls: [1](#0-0) 

It takes the *old* selection object (`currentlySelectedFile.selection`) and simply narrows it with `withSelectableLines(selectableLines)`: [2](#0-1) 

`withSelectableLines` only filters `divergingLines` (the set of line-index numbers whose selection diverges from the default) down to whichever indices still exist as "selectable" in the new diff - it does **not** verify that the line at a given index still contains the same text it did when the user selected/deselected it. If the working-tree file changes between the time the user made a partial selection and the time the diff is reloaded (e.g. a background process, an editor auto-format, or - most relevant to the "attacker controls a git object" impact class - a **Git hook** such as `post-checkout`/`post-merge`/`smudge` filter invoked during a checkout/pull/merge triggered from a cloned/fetched repository) in a way that shifts or rewrites lines at the same indices, Desktop will silently keep the old index-based selection and apply it to the new content.

Because `applyPatchToIndex` / `formatPatch` build the staged patch strictly from `file.selection.isSelected(absoluteIndex)` against the *new* diff's line list: [3](#0-2) 
the resulting partial commit can silently include lines the user never reviewed/approved, or exclude lines they intended to commit - i.e., corruption of "what the user commits" as called out in the impact criteria.

The code comment even acknowledges the limitation but treats it as a cosmetic issue rather than an integrity one:
```
// The diff might have changed dramatically since last we loaded it.
// Ideally we would be more clever about validating that any partial
// selection state is still valid by ensuring that selected lines still
// exist but for now we'll settle on just updating the selectable lines
``` [4](#0-3) 

The only other guard that clears partial selections, `updateChangedFiles`'s `clearPartialState` flag, is applied on *status refresh* (i.e. before/after committing) and only clears selection when the file's `getSelectionType()` was already `Partial`, and only when explicitly requested: [5](#0-4) 
It does nothing about `updateChangesWorkingDirectoryDiff`, which is the path that runs on every diff (re)load while the user is actively editing/selecting lines, and is not gated by content hashing.

### Impact Explanation
An attacker who can cause the working directory to mutate at the right moment relative to a user's partial-selection workflow (for example via commit hooks/smudge filters shipped in a cloned or pulled repository, which GitHub Desktop executes automatically) can cause the app to silently stage/commit lines that were never reviewed by the user, or drop lines the user intended to include. This is a "silent corruption of what the user commits or pushes" per the stated valid-impact class, without requiring local/physical access, admin rights, or pre-existing malware - the attacker's payload arrives purely as part of repository content (hooks/filters) that Desktop runs as part of normal git operations.

### Likelihood Explanation
The race window is narrow (diff must be reloaded between the user making a partial selection and clicking commit, and the hook/filter must fire in that exact window), which lowers likelihood relative to a fully deterministic bug, but Desktop's UI actively re-triggers `updateChangesWorkingDirectoryDiff` on many events (focus changes, background status polling, file-watcher events) while a partial selection is open, and hooks/filters commonly run on checkout/merge/pull, all of which are normal Desktop-driven operations against attacker-supplied repository content. No existing guard in `DiffSelection` or `updateChangedFiles` validates that indices still map to the same text, so nothing currently stops the corrupted state from reaching `applyPatchToIndex`.

### Recommendation
When recomputing selectable lines for a reloaded diff, do not carry forward `divergingLines` purely by index. Instead, invalidate (or recompute) the diverging-line set whenever the underlying diff content at those indices has changed - e.g. by comparing line text/hash at each previously-selected index between the old and new diff, similar to how `stake_start_epoch` should have been pinned to a safe forward-only value (`get_next_epoch`) rather than merged via `max`. Concretely, `withSelectableLines` (or its caller in `updateChangesWorkingDirectoryDiff`) should drop any diverging line whose associated diff line text differs from what it was when selected, and clear (or re-prompt for) the partial selection in that case rather than silently reusing it.

### Proof of Concept
1. In a cloned attacker-controlled repository, add a `post-checkout` (or a clean/smudge filter) hook that rewrites a tracked file's content whenever it runs, keeping the same number of lines but altering the text at fixed line indices.
2. In GitHub Desktop, open the repository, modify the file, and select only some lines for a partial commit (`DiffSelectionType.Partial`) via the Changes view.
3. Trigger any operation that causes Desktop to run the hook/filter and reload the working directory diff while the partial selection is still open (e.g., pull/checkout another branch and back, or let the background status refresh fire) - `updateChangesWorkingDirectoryDiff` will recompute the diff and reapply the old `divergingLines` indices via `withSelectableLines`.
4. Commit. The resulting patch, built by `formatPatch` from `file.selection.isSelected(absoluteIndex)`, includes/excludes lines based on the stale index set applied against the new (hook-rewritten) content, producing a commit whose staged content does not match what the user actually reviewed and selected.

Note: I was unable to fully verify the exact triggering conditions and timing of the file-watcher/background-refresh events that call `updateChangesWorkingDirectoryDiff` (that logic lives in files I did not have indexed content for), so the precise reproduction cadence should be validated in a live Desktop instance before treating this as a confirmed exploit rather than a design weakness.
