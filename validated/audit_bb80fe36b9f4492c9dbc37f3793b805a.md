### Title
Index-domain confusion drops the wrong participant's preprocess (or panics) when removed validators exist - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug class — an operation executed without a required translation/enablement step, causing a fault — maps onto `threshold_i_map_to_keys_and_musig_i_map`, which translates threshold participant indexes into MuSig participant indexes but then deletes "our" entry using the untranslated threshold index. Whenever the `removed` set shifts our index off its ordinal position, the function removes a *different* validator's preprocess (or panics), leaving our own dummy `vec![]` entry behind and driving `share_internal`/`complete` into `unreachable!()` fault paths.

### Finding Description
`threshold_i_map_to_keys_and_musig_i_map` inserts our own index into the input map keyed by *threshold* index (`our_threshold_i`), sorts, then re-keys every entry by enumeration order: `musig_i = raw_i + 1` [1](#0-0) . After this remap, the map keys are MuSig indexes — but the function then removes the dummy self-entry using the *threshold* index: `map.remove(&our_threshold_i).unwrap()` [2](#0-1) .

With a non-empty `removed` set, a validator's rank among remaining signers no longer equals its threshold index. Two failure modes result:

1. `our_threshold_i` equals some *other* validator's `musig_i`: that validator's real preprocess is deleted and our empty `vec![]` entry survives under our `musig_i`. In `share_internal`, `machine.sign` pushes our own `multisig_params.i()` into `included` and then `validate_map`/`read_preprocess` sees our own index twice (once as our pushed entry, once in the map) → `FrostError::DuplicatedParticipant` → `unreachable!("{e:?}")` panic [3](#0-2) .
2. `our_threshold_i` matches no key: `unwrap()` panics directly [2](#0-1) .

Either way the coordinator faults mid-signing — the same shape as the ARM cacheflush fault: a required precondition/translation was skipped before the privileged operation, and the operation faults on data it cannot handle.

### Impact Explanation
Any DKG confirmation performed while at least one validator is `removed` — a routine, externally observable on-chain condition (`removed_as_of_dkg_attempt` [4](#0-3) ) — deterministically panics the coordinator's `share`/`complete` path, or silently drops a validator's preprocess so the honest MuSig set is misattributed. This is a denial of service of the validator-set confirmation (signatures over `set_keys_message` cannot be produced), and in the non-panic edge it produces a signature share computed over a signing set different from the one the coordinator intended to attest to.

### Likelihood Explanation
The fault requires only that `removed` be non-empty and positioned such that `our_threshold_i` differs from our rank — precisely the scenario this function exists to handle (its whole purpose is remapping under removals). It does not depend on a malicious validator sending malformed input; it triggers on legitimately ordered, BFT-finalized preprocess data whenever removals precede our index. `share` and `complete` are both reached from ordinary protocol flow [5](#0-4) .

### Recommendation
Track our own MuSig index during the remap (the `raw_i` where `threshold_i == our_threshold_i`) and remove `Participant::new(our_musig_i)`, not `our_threshold_i`. Concretely, capture `our_musig_i` inside the enumeration loop and call `map.remove(&our_musig_i)`, or filter the dummy entry by its empty `Vec<u8>` value before re-keying.

### Proof of Concept
Setup: threshold set of 4 validators, validator at threshold index 1 is in `removed`. Our key is threshold index 3.

1. `spec.i(removed, our_key)` returns `our_threshold_i = Participant(3)`; `map.insert(Participant(3), vec![])` [6](#0-5) .
2. After sorting, remaining threshold indexes are `{2, 3, 4}`; enumeration assigns `musig_i` `{1, 2, 3}`. Our own entry (threshold 3, rank 1) gets `musig_i = 1`.
3. `map.remove(&Participant(3))` removes the validator whose `musig_i` is 3 (threshold index 4) — the wrong participant — leaving our `vec![]` under `Participant(1)` [7](#0-6) .
4. `share_internal` calls `machine.sign(preprocesses, msg)` where `included` contains our own index twice → `FrostError::DuplicatedParticipant(Participant(1))` → `unreachable!("{e:?}")` → panic and aborted DKG confirmation [8](#0-7) .

If instead `our_threshold_i` exceeds the count of remaining signers (e.g., we were the last index and earlier validators were removed), step 3 hits `map.remove(&our_threshold_i).unwrap()` on a nonexistent key and panics immediately — a fault identical in character to the unpermitted cache-maintenance access in the reference CVE.

*Uncertainty note: I verified the index-domain confusion directly in the code, but did not have remaining iterations to confirm whether `our_threshold_i` vs. `musig_i` can diverge under all `removed` configurations in `TributarySpec::i`; the divergence follows whenever a removed validator precedes us, which is the ordinary case the function was written for.*
