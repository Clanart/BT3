### Title
`SignableTransaction::new` sizes the fee/weight from a transaction that omits the `OP_RETURN` data output, so the "total" vbytes used for `needed_fee` undercounts what is actually signed - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Balancer finding (a "total" value that silently includes/excludes units which shouldn't/should be counted), `SignableTransaction::new` builds a size-estimation transaction whose `output` list contains only `payments` (and optionally `change`), while the real signed transaction additionally contains an `OP_RETURN` output carrying up to 80 bytes of attacker-influenced `data`. The fee and weight "totals" are therefore computed on a different (smaller) transaction than the one signed.

### Finding Description
`SignableTransaction::new` appends an `OP_RETURN` output to `tx_outs` when `data` is provided (send.rs:194-202), but `calculate_weight_vbytes` is only ever called with `payments` and `change` (send.rs:204, send.rs:226). The temporary transaction built inside `calculate_weight_vbytes` (send.rs:67-99) never includes the `OP_RETURN` output. Consequently:

- `vbytes` and `needed_fee` (send.rs:204-206) are computed for a smaller transaction than the one produced.
- The `TooLowFee` check (send.rs:211) and `NotEnoughFunds` check (send.rs:215) are evaluated against the undercounted `needed_fee`.
- When change is present, the change amount uses `fee_with_change` (send.rs:228-230), which is also computed without the `OP_RETURN` output, so the actual paid fee is again short by `fee_per_vbyte * vbytes(OP_RETURN output)` (~12-92 vbytes for 0-80 bytes of data).
- The `TooLargeTransaction` check (send.rs:241) uses `weight` that never accounts for the data output.

The `data` bytes and their length come from the caller constructing the plan/output being paid, i.e. public transaction data, so an unprivileged party triggering burns/withdrawals with data payloads reaches this path.

### Impact Explanation
Every transaction carrying an `OP_RETURN` output pays a fee rate strictly lower than the requested `fee_per_vbyte`. When `fee_per_vbyte` is at/near the minimum relay rate, the produced transaction's actual fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, so the signed transaction is rejected by relay policy and the payment is never made - the multisig's funds intended for that payment are not delivered/spendable via this transaction, and the signing session's product is unusable. This mirrors the original finding's class: a value that must reflect the full set (all outputs / circulating supply) is computed from a wrong set, producing a systematically wrong result used downstream for economic decisions.

### Likelihood Explanation
Any usage of the `data` field (up to 80 bytes) deterministically triggers the undercount - it is not probabilistic. The fee shortfall scales with both `fee_per_vbyte` and the data length, so under high-fee conditions the absolute underpayment is largest, and under low-fee conditions the transaction risks falling under the minimum relay fee entirely.

### Recommendation
Include the `OP_RETURN` output in the transaction constructed by `calculate_weight_vbytes` (i.e. pass the full intended output set, or the `data` length, into the size estimation), so that `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check are computed over the same outputs the signed transaction will contain.

### Proof of Concept
Conceptual trace in `networks/bitcoin/src/wallet/send.rs`:
1. Call `SignableTransaction::new(inputs, payments, change, Some(data), fee_per_vbyte)` with `data` of length 80.
2. `tx_outs` gains an `OP_RETURN` output at send.rs:194-202 (~90 extra serialized bytes in the final tx).
3. `calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204 builds a tx whose `output` is only `payments` - the returned `vbytes` is ~90 vbytes too small.
4. `needed_fee = fee_per_vbyte * vbytes` is short by `fee_per_vbyte * ~90`; `fee()` (send.rs:138-141) confirms the actual fee equals the undercounted `needed_fee`.
5. With `fee_per_vbyte` chosen so `needed_fee` just passes the `DEFAULT_MIN_RELAY_TX_FEE` check at send.rs:211, the real transaction's fee rate is below the relay minimum and is not accepted/broadcast, while `SignableTransaction::new` reported success - a signed transaction that cannot move the funds.
