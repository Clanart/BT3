## Analog Assessment for CVE-2016-4425 (Jansson deep recursion / stack overflow)

I found a plausible reachable analog but cannot fully confirm exploit feasibility (memo-size cost bound vs. required recursion depth) within available tool calls, so I present it with the caveats needed.

### Title
Unbounded recursive `PuzzleWithRestrictions.from_memo()` parsing of attacker-controlled coin memo can crash wallet coin-processing on `MofN` nesting - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively parses a `CREATE_COIN` memo blob into nested `MofN` structures with no depth limit, mirroring the class of bug in CVE-2016-4425 (deep-recursion stack exhaustion during untrusted structured-data parsing).

### Finding Description
`PuzzleWithRestrictions.from_memo()` [1](#0-0)  recurses into itself once per `MofN` member when `further_branching` is true, with no maximum-depth guard, unlike the deliberately-iterative `sha256_treehash()` [2](#0-1)  which the codebase's own documentation calls out as an explicit stack-safety property. This function is reachable from `PlotNFT.get_next_from_coin_spend()`, which extracts an inner puzzle from `singleton_create_coin.memo_blob` produced by any `CREATE_COIN` condition inside a spend bundle [3](#0-2) , and that method is invoked whenever a wallet is syncing a plotnft-shaped coin via `PlotNFT2Wallet.identify()` [4](#0-3) , i.e. driven by coin-state data originating from spends any party can submit to the chain.

### Impact Explanation
If reachable with sufficient nesting depth, this would cause a Python `RecursionError`/interpreter stack overflow inside wallet coin-processing (`coin_added`/sync path), which is a spend-triggered processing halt for the affected wallet — analogous to the "denial of service (deep recursion, stack consumption, crash)" described in CVE-2016-4425.

### Likelihood Explanation
Likelihood is uncertain and I could not fully validate it in the time available. The depth achievable is bounded by how much data an attacker can afford to spend (CLVM cost to construct a deeply-nested memo list inside a `CREATE_COIN` condition, and the mempool's `max_tx_clvm_cost`/`MAX_BLOCK_COST_CLVM` limits), and by whether `from_memo()` is only exercised for coins recognized as candidate PlotNFT singletons via `identify()`. I was not able to confirm within the available searches whether the recursion depth achievable under the cost ceiling is enough to exhaust the default Python recursion limit (typically ~1000), nor whether `identify()` is gated by additional puzzle-shape checks that would reject deeply-nested memos before reaching `from_memo()`.

### Recommendation
Convert `PuzzleWithRestrictions.from_memo()` (and the related `unknown_puzzles`/`fill_in_unknown_puzzles` recursive traversals) to an iterative, explicit-stack implementation, or add an explicit maximum nesting-depth check that raises a clean `ValueError` before Python's call stack is exhausted — consistent with the existing iterative pattern already used in `sha256_treehash()`.

### Proof of Concept
Not fully constructed — would require crafting a coin spend whose `CREATE_COIN` memo encodes a `MofN` hint nested to a depth sufficient to exceed Python's recursion limit, within the per-spend/per-block CLVM cost budget, and verifying that `PlotNFT2Wallet.identify()` routes such a coin to `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()` without a prior depth-limiting check. This step needs to be validated by an agent with code-execution/test access.

    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(

            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
