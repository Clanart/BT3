## Title
Assertion-failure DoS when parsing a crafted offer with a duplicate coin spend - ([File: chia/wallet/trading/offer.py])

### Summary
The BIND9 CVE (ALPINE-CVE-2024-4076) is an assertion-failure crash triggered by a client-controllable query pattern hitting an internal invariant that the server assumed could never be false. The closest reachable analog in this codebase is `Offer.__post_init__` in `chia/wallet/trading/offer.py`, which uses a bare `assert` to enforce an invariant ("no coin is spent twice in a bundle") on data that originates from an externally supplied, untrusted offer file/bech32 blob.

### Finding Description
`Offer` is a `Streamable`/dataclass that is constructed directly from attacker/counterparty-supplied data — offers are decompressed from bech32-encoded bytes and turned into an `Offer` object (`Offer.from_bytes`, `Offer.from_compressed`) before any semantic validation of their spend bundle occurs. `__post_init__` runs automatically on construction and iterates the coin spends in `self._bundle.coin_spends`, hitting: [1](#0-0) 

```
adds: dict[Coin, list[Coin]] = {}
...
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
```

This is a raw Python `assert` used as a correctness invariant against data that has not yet been validated by consensus code. Because `SpendBundle`/`WalletSpendBundle` places no restriction preventing the same `Coin` from appearing twice in `coin_spends` at construction time, a maliciously crafted offer containing two `CoinSpend`s for the identical `Coin` (same parent, puzzle hash, and amount) will hit this `assert` and raise a bare `AssertionError` instead of a handled `ValueError`/`ValidationError`.

### Impact Explanation
Any code path that constructs an `Offer` from external input — accepting an offer file over the wallet RPC (`take_offer`), inspecting an offer (`get_offer_summary`), or any GUI/CLI flow that parses an offer a counterparty sent — will crash with an unhandled `AssertionError` rather than being cleanly rejected. This matches the BIND9 bug class: a crafted, externally-supplied input drives an internal invariant to fail via `assert`, producing a processing halt/crash instead of a normal error path. In the RPC layer, `AssertionError` is caught generically and mapped to `INTERNAL_ERROR` [2](#0-1)  for HTTP paths, which may limit process-wide impact for the RPC endpoint itself, but any caller that inspects an offer outside the RPC error-wrapping layer (e.g., internal wallet code paths, tests, CLI tooling, or direct construction from `Offer.from_bytes`) can still crash on the bare assertion. This is a coin-set/processing halt rather than an asset-theft or inflation bug.

### Likelihood Explanation
Constructing a `SpendBundle` with a duplicate `Coin` entry in `coin_spends` requires no signature or fee to distribute — it only needs to be a syntactically valid, unsigned bundle serialized into an offer, since `Offer.__post_init__` runs before any signature or consensus validation. Any wallet user could receive such a file via out-of-band offer sharing (a normal, expected mechanism for Chia offers) and trigger the crash simply by having their wallet client parse/inspect it.

### Recommendation
Replace the bare `assert cs.coin not in adds` with an explicit check that raises a handled exception (e.g., `ValueError`/`ValidationError`) so that malformed/malicious offers are rejected through the normal error-handling path instead of raising an unguarded `AssertionError`. Audit other `assert` statements in `chia/wallet/trading/offer.py` and related driver code (e.g., `assert inner_puzzle is not None and inner_solution is not None`, `assert cost_left >= puzzle_cost` in `_get_offered_coins`) for the same untrusted-input-reaches-assert pattern, consistent with the general fragility note that "many asset recognizers and drivers depend on ... `assert`-style invariants" [3](#0-2) .

### Proof of Concept
1. Construct two `CoinSpend`s referencing the exact same `Coin` (identical `parent_coin_info`, `puzzle_hash`, `amount`), each with arbitrary puzzle reveal/solution.
2. Aggregate them into a `WalletSpendBundle`/`SpendBundle` with no valid signature required (this is pre-signing/pre-consensus construction).
3. Wrap this bundle into an `Offer(notarized_payments, spend_bundle, driver_dict)` or serialize/bech32-encode it as an offer file and hand it to a victim wallet for parsing (`Offer.from_bytes`/`Offer.from_compressed`).
4. `Offer.__post_init__` executes `assert cs.coin not in adds` at [4](#0-3) , and on the second occurrence of the duplicate coin the assertion fails, raising an unhandled `AssertionError` during offer parsing/inspection instead of a graceful rejection.

**Note on confidence**: I could not fully trace every call path from `Offer.from_bytes`/`from_compressed` through to RPC-level `take_offer`/`get_offer_summary` handlers due to tool budget limits in this session, so I cannot definitively confirm whether all call sites wrap this in exception handling that fully neutralizes the crash risk (e.g., some non-RPC internal callers may not catch `AssertionError` at all). This should be verified by tracing `Offer(` constructor call sites and `Offer.from_bytes`/`from_compressed` usage throughout `chia/wallet/` and `chia/cmds/` before treating this as a confirmed unguarded crash on every code path.
