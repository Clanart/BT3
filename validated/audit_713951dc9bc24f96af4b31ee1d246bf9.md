## Finding: Confirmed

The on-chain `code::publish_package` entry point performs no validation whatsoever of `PackageMetadata.source_digest` or `PackageMetadata.manifest` against the actual bytecode being published. Any account can submit a hand-crafted BCS blob with forged provenance fields and the transaction will succeed as long as the bytecode itself passes verifier/compatibility/dependency checks.

### Title
On-chain `code::publish_package` never verifies `source_digest`/`manifest` against the published bytecode, allowing forged provenance metadata - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`code::publish_package` accepts a caller-supplied `PackageMetadata` struct (including `source_digest` and `manifest`) and a separate `code: vector<vector<u8>>` payload. The on-chain function only checks upgrade policy, module coexistence/upgradability, and dependency constraints on the `code` payload — it never derives or compares a digest of the `code` bytes against `pack.source_digest`, nor validates that `pack.manifest` (the gzipped `Move.toml`) is consistent with the modules being deployed.

### Finding Description
In `publish_package`, the checks performed are:
- Upgrade policy must be stronger than `arbitrary` [1](#0-0) 
- `check_dependencies` on declared deps [2](#0-1) 
- `check_upgradability`/`check_coexistence` against module names [3](#0-2) 
- Bytecode-level verification happens later via `request_publish`/`request_publish_with_allowed_deps`, which is a native call operating on the raw `code` bytes and is entirely independent of `pack.source_digest`/`pack.manifest` [4](#0-3) 

Nowhere in this path — nor in the native `code.rs` helpers, nor in the loader/module-init/compatibility-check code — is a hash of `code` computed and compared to `pack.source_digest`. The `source_digest`/`manifest` fields are pure metadata, stored as-is into `PackageRegistry` on the destination address [5](#0-4) .

The only place a comparison exists is client-side, in the CLI's `VerifyPackage` command and `CachedPackageRegistry::verify`, which recompiles the package locally and compares the freshly computed `source_digest`/`manifest`/`modules` against what is stored on-chain [6](#0-5) [7](#0-6) . This is an off-chain, opt-in check that only protects a *downstream verifier* who chooses to run `aptos move verify-package`; it provides no on-chain guarantee.

Every code path that builds `metadata_serialized` in the repo (SDK helpers, benchmarks, fuzzers, e2e-tests) constructs it via `BuiltPackage::extract_metadata()` and simply BCS-serializes and submits it verbatim [8](#0-7)  — nothing on the Move or native side re-derives these fields from `code`, confirming there is no independent on-chain source of truth.

### Impact Explanation
This is a genuine provenance/metadata integrity gap, not a bytecode-safety gap: all verifier, compatibility, and dependency-allowlist checks on the actual bytecode still apply and are unaffected. The impact is limited to the `PackageMetadata.source_digest`/`manifest` fields (and by extension `ModuleMetadata.source`/`source_map`, since these are also caller-supplied and unchecked) potentially misrepresenting what source produced the deployed bytecode. This undermines the guarantee that `aptos move verify-package`/`CachedPackageRegistry::verify` is meant to provide for third parties trying to audit a package's claimed source, but it does not let an attacker change what bytecode is executed, bypass compatibility/upgrade-policy/dependency checks, or escalate any privilege.

### Likelihood Explanation
Trivial to trigger: any unprivileged account can hand-construct a `PackageMetadata` with an arbitrary `source_digest`/`manifest` and submit it via `code_publish_package_txn`, `object_code_deployment::publish/upgrade`, or the resource-account variants, since none of these entry points touch `source_digest`/`manifest` beyond passthrough storage [9](#0-8) .

### Recommendation
Given this is a metadata/provenance-only concern with no bytecode-safety or ownership implication, no framework change is strictly required for chain safety. If provenance integrity is desired, this is fundamentally unsolvable on-chain for `source_digest` (source is off-chain and unknowable to the VM), so the realistic mitigation is documentation-level: explicitly state (in `code.move` docs and CLI docs) that `source_digest`/`manifest`/module `source` fields are self-reported and not verified on-chain, and that `verify-package` only protects consumers who actively run it against their own trusted recompilation — it is not a chain-enforced guarantee.

### Proof of Concept
1. Build a legitimate package `A` and call `extract_metadata()` to get a valid `PackageMetadata`.
2. Mutate `source_digest` (or `manifest`) to an arbitrary/incorrect string/bytes, unrelated to the actual `code` bytes being submitted, mirroring the metadata-tampering pattern already used in `test_metadata_with_changes` for module metadata [10](#0-9) .
3. BCS-serialize the tampered `PackageMetadata` and submit via `aptos_stdlib::code_publish_package_txn(metadata_serialized, code)`.
4. Observe the transaction succeeds (assuming the bytecode itself is valid/compatible) and `PackageRegistry.packages[..].source_digest` on-chain does not match a hash of the actual `code` submitted — confirming no on-chain digest check exists.

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
