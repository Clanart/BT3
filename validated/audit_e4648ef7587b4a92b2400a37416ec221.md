### Title
Single unremovable/broken reward token permanently blocks principal withdrawal in MasterMagpie/BaseRewardPool - (File: rewards/MasterMagpie.sol, rewards/BaseRewardPool.sol, rewards/BaseRewardPoolV2.sol, rewards/mWOMSVBaseRewarder.sol)

### Summary
Every user withdrawal path in `MasterMagpie` unconditionally triggers a full reward harvest before releasing the staked principal. The harvest loop in `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder` iterates over *all* registered reward tokens for the pool and performs an unguarded `safeTransfer` for each one with a nonzero pending balance. If any single reward token in that list becomes non-transferable (blacklist, pause, revert-on-transfer, insufficient balance due to token quirks), the revert propagates all the way up and blocks withdrawal of the user's principal — with no bypass, no try/catch, and no way to remove the offending token from the array. This is the same bug class as the external report: one failing sub-call in a mandatory step permanently stalls the canonical, unprivileged user operation until manual/privileged intervention.

### Finding Description
The withdrawal call chain is:
`MasterMagpie.withdrawFor` → `_withdraw` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `rewarder.getReward(_account, ...)`. [1](#0-0) [2](#0-1) 

`_harvestBaseRewarder`/`_claimBaseRewarder` unconditionally calls into the pool's `IBaseRewardPool`, and this call is never wrapped in try/catch: [3](#0-2) 

Inside `BaseRewardPool.getReward`, the function loops over the full `rewardTokens` array and performs a plain `safeTransfer` for every token with a nonzero balance: [4](#0-3) 

The same unguarded pattern exists in `BaseRewardPoolV2.getReward`/`getRewards` (used by pool helpers for general staking tokens): [5](#0-4) 

and in `mWOMSVBaseRewarder.getReward`/`getRewards` (used for VLMGP/mWomSV lock-slot rewards): [6](#0-5) 

There is no `removeRewardToken` (or equivalent) function anywhere in the codebase to strike a broken token from the `rewardTokens` array, and no per-token isolation/try-catch exists in any of the reward-sending loops. The only escape hatch, `MasterMagpie.emergencyWithdraw`, is gated `whenPaused`, which is a privileged, owner-controlled state — an ordinary user cannot invoke it while the system is running normally: [7](#0-6) 

Pool helper contracts (`WombatPoolHelper`, `WombatPoolHelperV2`, `AnkrBNBPoolHelper`) all route ordinary user withdrawals through this same forced-harvest path with no alternative: [8](#0-7) [9](#0-8) 

### Impact Explanation
Because reward-token transfer failure reverts the entire withdrawal transaction, and there is no mechanism to skip/remove a broken reward token or to withdraw principal independently of harvesting, a single misbehaving reward token (blacklisting a specific address, being paused, having insufficient balance due to fee-on-transfer/rebasing behavior, or simply reverting) permanently freezes principal withdrawal for **every user staked in that pool**, not just the affected account, since `getReward`/`getRewards` iterate the shared `rewardTokens` array for the pool. This constitutes protocol-wide permanent freezing of user funds (well beyond 24 hours) until the team performs a manual/privileged fix (e.g., pausing the contract to allow `emergencyWithdraw`, or deploying a patched rewarder) — mirroring exactly the "stall situation until admin intervenes" outcome described in the external report.

### Likelihood Explanation
This does not require any malicious admin action. It can be triggered passively any time a reward token added via `queueNewRewards`/`addBonusRewardForAsset` later becomes untransferable (e.g., a stablecoin issuer blacklists the pool/rewarder address, a token is paused, or a non-standard ERC20 reverts under some balance condition). Since bonus/reward tokens are frequently third-party assets outside the protocol's control, and the reward token list only grows (no removal function), the likelihood of this occurring over the life of any actively used pool is non-trivial and entirely triggerable by ordinary protocol operation/ordinary wallets calling `withdraw`/`withdrawFor`.

### Recommendation
Isolate reward distribution from principal withdrawal: either (1) allow principal withdrawal to proceed independent of harvest success (e.g., wrap each token transfer in `getReward`/`getReward`-loops in a try/catch and record unpaid rewards for later retry, similar to the pattern already used for native-token overflow in `MultiRewarderPerSec.onReward`), or (2) add a permissionless/owner `removeRewardToken` function that lets a broken token be excluded from the mandatory harvest loop without blocking withdrawals, decoupling a single bad reward token from custody of the principal stake.

### Proof of Concept
1. Owner (or through normal operational flow) registers a reward token `T` for pool `P` via `queueNewRewards`, and users accrue nonzero `userRewards[T][user]` balances. [10](#0-9) 
2. Token `T` becomes non-transferable to the rewarder's holders (e.g., issuer blacklists the pool contract, or `T` is paused, or fee-on-transfer/rebasing causes `safeTransfer` to revert due to balance mismatch).
3. Any user calls `WombatPoolHelper.withdraw` (or `MasterMagpie.withdrawFor` directly), which internally calls `_harvestBaseRewarder` → `BaseRewardPool.getReward`. [8](#0-7) 
4. Inside `getReward`, the loop reaches token `T`, calls `IERC20(T).safeTransfer(_receiver, reward)`, which reverts. [11](#0-10) 
5. The revert propagates through `_harvestAndUnstake` → `_withdraw` → `withdrawFor`, causing the entire withdrawal transaction to fail. The user's staked principal (LP tokens) remains locked in `MasterMagpie`/`WombatStaking` indefinitely, and no user of pool `P` can withdraw until the team pauses the contract (enabling the privileged `emergencyWithdraw`) or deploys a fixed rewarder contract.

    ///         Locked Token can not be emergent withdraw.

    /// @dev withdrawFor of the rewarder with the third param at false is an emergency withdraw
    function emergencyWithdraw(address _stakingToken) external whenPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][msg.sender];
        uint256 availableaAmount = user.available;
        user.available = 0;
        IERC20(pool.stakingToken).safeTransfer(address(msg.sender), availableaAmount);
        emit EmergencyWithdraw(msg.sender, _stakingToken, availableaAmount);
        user.amount = user.amount - availableaAmount;
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;
    }
