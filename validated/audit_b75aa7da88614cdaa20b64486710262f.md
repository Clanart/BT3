### Title
Diff-expansion re-indexing lets checkbox selections apply to the wrong line at commit time, silently corrupting partial commits - ([File: app/src/ui/diff/text-diff-expansion.ts])

### Summary
This is the closest structural analog to the Lido report's bug class: a numeric offset/state value that is computed correctly for one context but then reused against a *different* context on a later operation, corrupting the final result. In the smart-contract report, `previousWithdrawnAmount` from a prior call is fed into a later calculation without accounting for the fee already netted out of it. In GitHub Desktop, the analogous "state that silently drifts" is the *absolute line index* used by `DiffSelection` to record which lines a user has checked/unchecked for a partial commit — an index that is only valid relative to the specific `DiffHunk[]` layout it was computed against.

### Finding Description
`DiffSelection` (app/src/models/diff/diff-selection.ts) stores selected/deselected lines purely as a `Set<number>` of **absolute line indices** (`divergingLines`), with no reference to which diff/hunk layout produced those indices: [1](#0-0) 

Those absolute indices are derived from `hunk.unifiedDiffStart + lineIndex`, and `unifiedDiffStart` is a property of the specific `DiffHunk` array currently being rendered: [2](#0-1) 

The diff a user actually interacts with in `SideBySideDiff` can be **locally expanded** via `expandHunk`, which calls `expandTextDiffHunk` and stores the result only in **component-level React state** (`this.setState({ diff: updatedDiff })`), not in the global `WorkingDirectoryFileChange`/store diff: [3](#0-2) 

`expandTextDiffHunk` recomputes hunk headers and, critically, re-indexes every hunk *after* the expanded one by `numberOfNewDiffLines`, and may also merge adjacent hunks, changing their `unifiedDiffStart`/`unifiedDiffEnd` boundaries: [4](#0-3) 

When the user then drags/clicks checkboxes to select lines, `onEndSelection` calls `selection.withLineSelection(line, isSelected)` using the line numbers from this locally-expanded, re-indexed diff: [5](#0-4) 

That resulting `DiffSelection` (a bare set of absolute indices) is what ends up attached to the `WorkingDirectoryFileChange` and is later used to build the commit patch. However, at commit time the patch is built from a **freshly fetched, non-expanded** diff — `applyPatchToIndex` re-invokes `getWorkingDirectoryDiff` rather than reusing the diff the user was actually looking at: [6](#0-5) 

`formatPatch` then walks this fresh diff's hunks and tests `file.selection.isSelected(absoluteIndex)` using the fresh (unexpanded) `hunk.unifiedDiffStart` values: [7](#0-6) 

Because hunk expansion shifts/merges hunk boundaries only in the transient UI diff, the absolute index the user "meant" (relative to the expanded view) and the absolute index actually tested at patch-build time (relative to the fresh, unexpanded diff) can diverge whenever hunks were expanded/merged before or during selection. This is exactly the report's broken invariant: a numeric state value computed in one context (post-fee-adjusted balance / post-expansion index) is silently reused as if it were still valid in a different context (pre-fee balance / pre-expansion index), producing a wrong result that "looks" internally consistent.

### Impact Explanation
If the mapping drifts, `formatPatch` can select/deselect the wrong `DiffLineType.Add`/`Delete` lines when building the `git apply --cached` patch. This means the user's partial-commit intent ("stage only these lines") is silently violated — the wrong hunk lines get staged and committed, i.e., the working-directory-to-commit path is corrupted without any error or warning to the user. This is a "silent corruption of what the user commits" outcome as defined by the impact scope.

### Likelihood Explanation
Uncertain/Medium at best. I could not, within the available iterations, fully trace whether `file.selection` object identity/validity checks (e.g., `selectableLines` recomputation seen in `app-store.ts:3466-3497`, which rebuilds `selectableLines` whenever a fresh diff is loaded) fully neutralize the mismatch before commit, or whether there is a diff-hash/identity guard that discards stale selections when the diff changes. The expansion feature is a normal, unprivileged UI action (no crafted repo needed beyond having a file with multiple separated hunks, which is trivial and common), so the *precondition* is easy to hit, but I was not able to confirm with certainty that a concrete keystroke/selection sequence reproduces a wrong-line commit rather than being silently corrected by `selectableLines` recomputation. This uncertainty should be resolved by a background agent with runtime access.

### Recommendation
- Never let `DiffSelection` absolute indices cross diff-layout boundaries: either (a) key selection state off of stable per-line identifiers (e.g., old/new line number pairs) instead of positional indices, or (b) invalidate/remap the `DiffSelection` whenever `expandTextDiffHunk`/`mergeDiffHunks` changes hunk boundaries, translating existing `divergingLines` indices to the new layout.
- Ensure the diff object used to build the commit patch (`applyPatchToIndex`/`formatPatch`) is always the exact diff object the selection indices were computed against, not a freshly re-fetched one, or explicitly remap indices between the two.
- Add a regression test that: builds a diff with 2+ separated hunks, expands the first hunk (shifting subsequent hunk indices), selects specific lines in the shifted hunk, then verifies the produced patch (via a freshly-fetched, unexpanded diff) stages exactly the intended lines.

### Proof of Concept
Not independently executable within this investigation; conceptual reproduction path:
1. Modify a tracked file so `git diff` produces at least two hunks with a gap large enough that they are not auto-merged (e.g., >20 lines apart, per `DefaultDiffExpansionStep`).
2. In Desktop's Changes view, open the file diff and click "Expand" on the first hunk (`expandHunk` → `expandTextDiffHunk`), which shifts `unifiedDiffStart`/`unifiedDiffEnd` of the second hunk by `numberOfNewDiffLines`. [8](#0-7) 
3. Select/deselect a specific added/deleted line inside the second hunk using its now-shifted row; this records an absolute index via `onEndSelection`. [5](#0-4) 
4. Commit the file (partial commit). `applyPatchToIndex` fetches a brand-new, unexpanded diff and calls `formatPatch`, which tests the recorded absolute index against the unexpanded hunk boundaries. [6](#0-5) [9](#0-8) 
5. Inspect the resulting commit: verify whether the staged/committed line corresponds to the line the user actually clicked in the expanded view, or a different line at the same index in the unexpanded layout.

I was unable to execute steps 3–5 against a live build to confirm the divergence empirically, so this should be treated as a code-reasoning-supported hypothesis requiring runtime confirmation, not a fully verified exploit.

export function diffHunkForIndex(
  hunks: ReadonlyArray<DiffHunk>,
