### Title
Unbounded Recursion in AccountKey RLP Decoding Enables Node Crash via Malicious AccountUpdate Transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each element of a role-based key by calling `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which in turn invokes `AccountKeyRoleBased.DecodeRLP` again if the nested key type is also `AccountKeyTypeRoleBased`. No recursion-depth or nesting check exists at decode time, so an attacker can nest `AccountKeyRoleBased` inside itself arbitrarily many times in a single RLP payload and exhaust the Go call stack, crashing the process — the same class of bug (missing `max_depth`/recursion bound in a recursive parser leading to stack-exhaustion DoS) described in the LlamaIndex advisory (CVE-2025-1752).

### Finding Description
`AccountKeyRoleBased.DecodeRLP` [1](#0-0)  decodes a list of byte strings and, for each element, calls `rlp.DecodeBytes(b, &serializer)` on a new `AccountKeySerializer`. `AccountKeySerializer.DecodeRLP` [2](#0-1)  reads the key type and dispatches to `NewAccountKey(serializer.keyType)` followed by `s.Decode(serializer.key)` — if the type is again `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, creating unbounded mutual recursion purely driven by attacker-controlled nesting in the RLP bytes.

Critically, this decoding happens unconditionally as part of ordinary transaction deserialization: `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)` [3](#0-2) , which is invoked before any semantic validation. The only place that rejects nested `AccountKeyRoleBased` is `CheckInstallable`/`CheckUpdatable` (`IsCompositeType()` checks) [4](#0-3) , which run **after** decoding has already completed — too late to prevent stack exhaustion during the decode itself. The codebase's own test confirms nested `AccountKeyRoleBased` is only rejected at the tx-pool/validation stage, not at decode time [5](#0-4) .

The same pattern applies to `FeeDelegatedAccountUpdate` and `FeeDelegatedAccountUpdateWithRatio` transaction types, and to the `AccountCreation` transaction type, all of which embed an `accountkey.AccountKey` decoded the same way, as well as to the public `kaia_decodeAccountKey` RPC [6](#0-5) .

### Impact Explanation
A single crafted transaction (or a raw RLP blob submitted via `eth_sendRawTransaction`, `kaia_sendRawTransaction`, gossiped p2p tx, or the `kaia_decodeAccountKey` RPC) containing a deeply nested `AccountKeyRoleBased` structure can trigger unbounded Go-level recursion during RLP decoding, exhausting the goroutine stack and crashing the node process. Since transaction decoding happens both at the RPC/tx-pool admission boundary and again during block/body decoding by every node validating a block, this can be used to crash multiple nodes on the network (each node independently decodes the same malicious data), constituting a Denial of Service against consensus-critical infrastructure — matching CWE-400/CWE-674 in the reference advisory. This meets the "unprivileged transaction sender ... reachable" and "gasless/fee-delegation counterparty" criteria via `TxTypeAccountUpdate` and `TxTypeFeeDelegatedAccountUpdate*`.

### Likelihood Explanation
High likelihood: RLP nesting for lists is cheap to construct (each nesting level just wraps the previous key's serialized bytes in another `AccountKeySerializer`-shaped RLP list), requires no special privileges, no funds beyond what's needed to submit a transaction (or none at all if only decoding via a read RPC / p2p relaying of the raw bytes is required), and no signature validity is needed for the recursion to be triggered (decoding happens before signature verification in most paths).

### Recommendation
Enforce an explicit maximum nesting/recursion depth (e.g., disallow any nested `AccountKeyRoleBased`, mirroring what `IsCompositeType()`/`CheckInstallable` already intend) directly inside `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP`, rejecting nested composite key types immediately at decode time rather than deferring the check to post-decode validation. Additionally, consider adding a global recursion-depth counter/guard shared across nested `DecodeRLP` calls for account keys, and apply the same fix to `AccountKeySerializer`/`AccountKeyRoleBased` usage in `TxInternalDataAccountCreation`, `TxInternalDataFeeDelegatedAccountUpdate`, `TxInternalDataFeeDelegatedAccountUpdateWithRatio`, and `KaiaAPI.DecodeAccountKey`.

### Proof of Concept
1. Construct `keyN = AccountKeyLegacy` (base case, RLP-encoded via `AccountKeySerializer`).
2. Construct `key(i) = AccountKeyRoleBased([key(i-1)])`, RLP-encoding it via `AccountKeySerializer` at each level (this is exactly what `AccountKeyRoleBased.EncodeRLP` / `NewAccountKeySerializerWithAccountKey` produce) [7](#0-6) .
3. Repeat nesting tens of thousands of times (each level only costs a few bytes of RLP list overhead, so millions of nesting levels are feasible within normal transaction/RPC payload size limits).
4. Embed the deeply-nested encoded key bytes as the `Key` field of a `TxTypeAccountUpdate` transaction, RLP-encode the full transaction, and submit it via `eth_sendRawTransaction`/p2p gossip, or pass the raw bytes directly to `kaia_decodeAccountKey`.
5. On any node that decodes this transaction/RPC payload, `AccountKeyRoleBased.DecodeRLP` recurses once per nesting level with no bound, exhausting the stack and crashing/panicking the process before `CheckInstallable`'s `IsCompositeType` rejection is ever reached.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
