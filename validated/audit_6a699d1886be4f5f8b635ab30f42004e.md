### Title
SchnorrAggregate::verify accepts an empty aggregate signature (zero Rs, s = 0) as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` checks that `self.Rs.len() == keys_and_challenges.len()` and then evaluates the multiexp equation `sum(z_i * R_i + z_i * c_i * A_i) - s*G == 0`. When `Rs` is empty and `s == C::F::ZERO`, the equation reduces to the empty sum plus `(-0) * G`, which is trivially identity, so `verify` returns `true` for an aggregate "signature" that binds no public key, no nonce, and no message. `SchnorrAggregate::read` places no lower bound on the length field, so a 4-byte `0x00000000` length followed by a zero scalar deserializes into a signature that passes verification against an empty key/challenge list.

### Finding Description
The verification logic at `crypto/schnorr/src/aggregate.rs:127-146`:

and the deserializer at `crypto/schnorr/src/aggregate.rs:77-88`:


There is no `Rs.is_empty()` rejection in either `read` or `verify`. Every signer in the intended aggregation protocol contributes `z*R + z*c*A` terms; with zero signers the only remaining term is `-s*G`, which vanishes for `s = 0`. This is the same bug class as CVE-2020-15988 (insufficient policy enforcement on attacker-supplied input that should have been rejected): a verifier policy that implicitly assumes at least one signer is not enforced, so attacker-controlled bytes satisfy a check they should never satisfy.

### Impact Explanation
Any caller that treats `SchnorrAggregate::verify(dst, keys_and_challenges) == true` as proof that *the signers represented by `keys_and_challenges` authorized something* can be satisfied by a signature over an empty set. In a flow where the verifier derives `keys_and_challenges` from attacker-presented data (e.g., a claimed signer set embedded in a message the attacker also supplies), an attacker who legitimately empties that set — or a caller that fails to separately enforce a minimum signer count — gets `true` without any secret key material, producing a forged aggregate authorization. The bytes required are minimal and fully attacker-controlled through the public `read`/`verify` API.

### Likelihood Explanation
Exploitation requires a caller that (a) runs aggregate verification over a signer/challenge list it does not independently constrain to be non-empty, and (b) accepts the resulting boolean as authorization. The crypto core itself computes the correct equation; the defect is the missing non-emptiness policy, so reachability depends on integrator usage rather than a math error. That keeps this at Medium rather than higher: it is a verifier-side policy gap reachable purely with public bytes, not a direct key-share recovery.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` (`if self.Rs.is_empty() { return false; }` before the length check) and/or in `SchnorrAggregate::read` (error on `len == 0`). Optionally also reject `R` points equal to identity in `read` for callers that don't use `Curve::read_G`, since an identity `R_i` contributes `z * 0` and lets a "signer" contribute nothing to the sum while still satisfying `s` via the `z*c*A` term only when the challenge is attacker-favorable — the empty-set check is the primary fix.
