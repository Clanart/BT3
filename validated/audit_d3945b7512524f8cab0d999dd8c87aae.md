### Title
`_calExpireForfeit` in `mWOMSVBaseRewarder` never forfeits rewards because it ignores the lock/cooldown state - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is supposed to compute a penalty ("forfeit") on rewards for accounts that are not fully in a rewardable lock state, mirroring the analogous mechanism in `vlMGPBaseRewarder`. In the vlMGP version, the forfeit is derived from the live lock state via `vlMGP.getRewardablePercentWAD(_account)`. In the `mWOMSVBaseRewarder` version, this call was never wired in - the function instead hardcodes the "rewardable" amount equal to the full amount, so the branch that should ever result in a nonzero forfeit is structurally unreachable, just like the dead comparison-against-wrong-constant bug in the external report.

### Finding Description
`vlMGPBaseRewarder._calExpireForfeit` correctly queries the live rewardable percentage from the locker contract before computing the forfeit: [1](#0-0) 

`mWOMSVBaseRewarder._calExpireForfeit`, which is meant to implement the same early-unlock/forfeit mechanic for `mWomSV` lock slots, instead sets `rewardableAmount = _amount` unconditionally, never consulting the locker's rewardable-percentage state: [2](#0-1) 

Because `rewardableAmount` is always set equal to `_amount`, `forfeitAmount = _amount - rewardableAmount` is always `0`, and the guard `if (rewardableAmount > _amount) revert InvalidRewardableAmount();` can never be true - this is structurally the same class of "dead branch caused by a mis-specified comparator/value" bug described in the external report, just applied to the mWomSV reward-forfeit path instead of a Solana `accrue_rewards` account-count comparator. `mWomSV.sol` does implement `getRewardablePercentWAD` (confirmed present in the contract), showing that the analogous on-chain state needed to compute a real forfeit exists but is never consulted here.

This dead code is reached from the reward-claiming path (`getReward`/`getRewards` → `_sendReward` → `_calExpireForfeit`): [3](#0-2) 

### Impact Explanation
The forfeit mechanism exists specifically to penalize users who claim mWomSV-pool rewards while not in a fully "locked"/rewardable state, with the forfeited portion being re-queued as rewards for the remaining, properly-locked stakers via `_queueNewRewardsWithoutTransfer`: [4](#0-3) 

Since `_calExpireForfeit` never returns a nonzero value in this contract, this redistribution never occurs: users who should be penalized keep 100% of their reward instead of forfeiting a share, and the honest, fully-locked stakers who are supposed to receive that forfeited/redistributed yield permanently never receive it. This is a direct, permanent loss of yield that should have been distributed to compliant stakers - any unprivileged account calling `getReward`/`getRewards` on this rewarder while in a state that should trigger forfeiture benefits, and the pool's other stakers are permanently deprived of that yield.

### Likelihood Explanation
This is triggered by ordinary, unprivileged reward-claim calls (`getReward`/`getRewards`) from any mWomSV staker; no privileged role, governance action, or external protocol dependency is required. The condition is deterministic and occurs on every single claim by an account in a state that should incur a forfeit, since the code path can never take another branch.

### Recommendation
- **Short term:** Update `mWOMSVBaseRewarder._calExpireForfeit` to query the actual rewardable percentage from `mWomSV` (e.g., via a `getRewardablePercentWAD`-equivalent function exposed on the `ILocker`/`mWomSV` interface), mirroring the logic in `vlMGPBaseRewarder._calExpireForfeit`, instead of hardcoding `rewardableAmount = _amount`.
- **Long term:** Add unit/integration tests asserting that `calExpireForfeit` returns a nonzero value for accounts in a non-fully-locked state, and add invariant checks so that logically-dead comparisons/branches (like `rewardableAmount > _amount` always being false) are caught in CI/static analysis.

### Proof of Concept
1. A user stakes `mWOM` into `mWomSV`, receives `mWomSV`, and stakes it into `MasterMagpie`'s mWomSV pool, accruing rewards via `mWOMSVBaseRewarder`.
2. The user enters a state that, per `mWomSV`'s intended design (mirrored by `vlMGP.getRewardablePercentWAD`), should reduce their rewardable percentage below 100% (e.g., early unlock/cooldown).
3. The user calls `getReward`/`getRewards` on `mWOMSVBaseRewarder`.
4. `_sendReward` → `_calExpireForfeit(_account, userRewards[...])` is invoked: [3](#0-2) 
5. Regardless of the account's actual lock/cooldown state, `_calExpireForfeit` always returns `forfeitAmount == 0` because `rewardableAmount` is hardcoded to `_amount`: [2](#0-1) 
6. The user receives 100% of rewards with no forfeiture, and `_queueNewRewardsWithoutTransfer` (which would redistribute the forfeited amount to remaining stakers) is never called, permanently denying that yield to compliant stakers.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**mWOMSVDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
```
