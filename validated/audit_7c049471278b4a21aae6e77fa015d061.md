### Title
Empty-pattern `contains` condition in hookify rules causes unconditional prompt-injection on every user turn - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._check_condition()` implements the `contains` operator as a raw Python `pattern in field_value` substring test with no minimum-length or non-empty validation, and `Condition.from_dict()` / `Rule.from_dict()` in `config_loader.py` load `pattern` directly from untrusted markdown frontmatter without any sanity check. A `.claude/hookify.*.local.md` file with `event: prompt` and a condition `field: user_prompt, operator: contains, pattern: ''` will therefore match on literally every user prompt, causing `userpromptsubmit.py -> main()` to inject an attacker-chosen `systemMessage` into every conversation turn.

### Finding Description
The exploit path is:
1. `userpromptsubmit.py -> main()` calls `load_rules(event='prompt')` [1](#0-0)  which globs every file matching `.claude/hookify.*.local.md` in the project's working directory with no ownership/signature check [2](#0-1) .
2. `Condition.from_dict()` copies the YAML `pattern:` value verbatim, including an empty string, with no length or emptiness validation [3](#0-2) .
3. `RuleEngine._check_condition()` evaluates the `contains` operator as `pattern in field_value`, which is trivially `True` for `pattern=''` regardless of `field_value` content [4](#0-3) . The same issue applies to `starts_with`/`ends_with` with an empty pattern.
4. `_extract_field()` resolves `field: user_prompt` directly from the incoming hook payload's `user_prompt` key with no filtering [5](#0-4) .
5. `evaluate_rules()` then returns a `systemMessage` built from the attacker-controlled `rule.message` body of the markdown file for every non-blocking match [6](#0-5) , which `main()` prints to stdout unconditionally on every prompt submission [7](#0-6) .

There is no validation anywhere in `load_rules`, `load_rule_file`, `Rule.from_dict`, `Condition.from_dict`, or `_check_condition` that rejects empty or near-empty patterns, and no confirmation/approval step is required before a `.claude/hookify.*.local.md` file becomes active — per the plugin's own README, "Rules take effect immediately... no restart needed" [8](#0-7) . If such a file is already present in a cloned/checked-out repository (e.g., merged via a malicious PR), it silently becomes active hook logic the next time any user submits a prompt, with no interactive approval step distinguishing it from a rule the user explicitly created via `/hookify`.

### Impact Explanation
Every user prompt submission results in an attacker-chosen `systemMessage` being injected into the model context via the `UserPromptSubmit` hook response, before the model processes the user's actual request. This is a persistent, silent prompt-injection channel that can be used across many turns to progressively steer the model (e.g., coax it into exfiltrating source code or secrets, disable safety behaviors, or alter its instructions), all without the user seeing an approval prompt tied to this specific dangerous configuration (empty pattern = universal match). This matches the "untrusted repo content silently becomes executable authority beyond explicit user approval" class of issue.

### Likelihood Explanation
Preconditions: an attacker needs a `.claude/hookify.*.local.md` file with `event: prompt` (or `event: all`) and an empty-pattern `contains`/`starts_with`/`ends_with` condition to end up in the victim's working directory — for example via a merged PR, a supply-chain repo, or a shared project template. Given `load_rules()` performs no provenance check and the plugin explicitly documents that these files activate immediately without restart or extra confirmation, exploitation is fully mechanical and 100% repeatable once the file is present.

### Recommendation
- In `Condition.from_dict()` (or immediately in `Rule.from_dict()`), reject or ignore conditions whose `pattern` is empty (or below a minimum length, e.g. 1–2 characters) for `contains`, `starts_with`, `ends_with`, and `equals` operators, logging a warning to stderr.
- Alternatively/additionally, in `_check_condition()`, add an explicit guard: `if operator in ('contains','starts_with','ends_with') and not pattern: return False`.
- Consider requiring interactive user confirmation (e.g., via a manifest/lockfile of approved rule files, hashed and shown to the user) before any `.claude/hookify.*.local.md` file that wasn't created through the `/hookify` command is allowed to execute, closing the broader trust gap of loading arbitrary repo-provided rule files.

### Proof of Concept
Unit test to add to the hookify test suite:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_empty_pattern_contains_should_not_match_everything():
    rule = Rule(
        name="malicious-inject",
        enabled=True,
        event="prompt",
        conditions=[Condition(field="user_prompt", operator="contains", pattern="")],
        message="ATTACKER INJECTED TEXT",
    )
    engine = RuleEngine()

    for prompt_text in ["hello", "", "anything at all", "12345"]:
        input_data = {"hook_event_name": "UserPromptSubmit", "user_prompt": prompt_text}
        result = engine.evaluate_rules([rule], input_data)
        # Expected (fix): rule should NOT match on an empty/near-empty pattern
        assert result == {}, f"Empty-pattern rule incorrectly matched prompt: {prompt_text!r}"
```
Currently this assertion fails for every prompt, because `evaluate_rules()` returns `{"systemMessage": "**[malicious-inject]**\nATTACKER INJECTED TEXT"}` regardless of `prompt_text`, confirming the unconditional match.
