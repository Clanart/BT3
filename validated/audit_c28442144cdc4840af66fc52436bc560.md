## Analysis

This maps to the same bug *class* as the Omnipool `totalDeposited` report: **a derived accounting value that is trusted as an authoritative signal for a critical decision, but whose computation can be desynchronized from ground truth by attacker-influenced input, causing a false "safe" state.**

In GitHub Desktop, the analog is `conflictMarkerCount`, computed by `getFilesWithConflictMarkers` in `app/src/lib/git/diff-check.ts`, and consumed by `hasUnresolvedConflicts` in `app/src/lib/status.ts` to decide whether a conflicted file is safe to treat as "resolved" (and therefore stageable/committable without further warning).

### Title
Conflict-marker count desync lets Desktop silently treat unresolved/corrupted merges as resolved - (File: app/src/lib/git/diff-check.ts)

### Summary
`getFilesWithConflictMarkers` derives the "number of remaining conflict markers" for a file purely by regex-parsing the stdout of `git diff --check` for the string `leftover conflict marker` [1](#0-0) . This count is the sole signal `hasUnresolvedConflicts` uses to decide a file is resolved (`conflictMarkerCount > 0` → unresolved) [2](#0-1) , and it also drives the UI label ("Conflicted" vs "Resolved") in `mapStatus` [3](#0-2)  and the resolved-file message shown to the user in `unmerged-file.tsx` [4](#0-3) . This is structurally identical to `totalDeposited`: a secondary counter, not the raw ground truth, is used as the safety gate.

### Finding Description
`getFilesWithConflictMarkers` does not itself parse or count `<<<<<<<`/`=======`/`>>>>>>>` markers in file content. It relies entirely on git's own `diff --check` heuristic output line format `"<path>:<line>: leftover conflict marker"` [5](#0-4) . `git diff --check`'s leftover-marker detection is itself a heuristic (it inspects lines that look like `<<<<<<<`, `=======`, `>>>>>>>` at the start of a line, similar to the independent regex-based detector in `app/src/lib/copilot-conflict-context.ts` which explicitly documents the marker shape as 7 repeated characters followed by whitespace/EOL) [6](#0-5) .

Because the "count" that gates the resolved/unresolved decision is derived from a separate, best-effort text scan rather than being tied atomically to the actual working-tree byte content at commit time, there is a class-level analog to the underflow bug: a value that is *supposed to* track "remaining conflicts" can go out of sync with the true state of the file. Concretely:

- A user (or an externally-fetched/checked-out branch containing attacker-crafted file content) can produce a working-tree file whose textual markers don't line up exactly with what `git diff --check`'s heuristic flags (e.g., markers with unusual trailing content, markers inside strings that happen to be excluded/included differently than expected, or a file where the git-check heuristic stops flagging lines after certain edits) while genuine `<<<<<<<`/`=======`/`>>>>>>>` conflict content remains in the file.
- Once `conflictMarkerCount` drops to `0` for such a file, `hasUnresolvedConflicts` returns `false` [7](#0-6) , `mapStatus` reports `'Resolved'` [8](#0-7) , and the Conflicts dialog shows "No conflicts remaining" / lets the user finish the merge/rebase and stage+commit the file as-is [9](#0-8) .
- `stageManualConflictResolution` in `app/src/lib/git/stage.ts` also gates on `status.conflictMarkerCount === 0` to decide it can skip further handling, assuming the user already fixed the file in an editor [10](#0-9) .

This is the same broken-invariant shape as `totalDeposited`: a bookkeeping counter used as a gatekeeping condition, disconnected from the authoritative source of truth (actual file bytes / actual balance), and reachable via content the user does not fully control review of (a merge/rebase against a remote branch, i.e., "a git remote/proxy response").

### Impact Explanation
If the count under- or mis-reports remaining conflicts, Desktop will silently let the user commit a file that still contains git conflict markers or unintended merged content, believing it is clean. This is "silent corruption of what the user commits or pushes" — the exact impact category called out as valid. The corrupted commit could contain conflict-marker text baked into source files (breaking builds) or, more subtly, incorrect merge resolution content that the user never had a chance to visually flag as unresolved because the dialog told them it was resolved.

### Likelihood Explanation
This requires no privileged access — only that the user is resolving a merge/rebase/cherry-pick against content from a remote or fetched branch (a normal, attacker-influenceable input per the valid-impact criteria). However, I could not fully verify, without running `git diff --check` against crafted inputs, an exact byte-for-byte case where its heuristic diverges from actual conflict-marker presence in a way that reaches `0`; this is a heuristic/reliance concern rather than a confirmed exploitable divergence I traced end-to-end in the git binary's own detection logic (which lives outside this repository, in git itself). I could not access git's own `diff --check` implementation from this codebase to confirm a concrete crafted-file case that produces a `0` count while markers remain.

### Recommendation
Do not rely solely on `git diff --check`'s heuristic count as a proxy for "conflict markers remaining." Cross-validate by directly scanning file content for the marker regex (as already implemented independently in `app/src/lib/copilot-conflict-context.ts`'s `isConflictMarker`/marker regexes) before allowing a file to be treated as resolved, or re-verify with a direct content scan immediately before staging/committing conflicted files.

### Proof of Concept
Could not be fully constructed without live git binary testing to find an exact string that `git diff --check` fails to flag as "leftover conflict marker" while genuine `<<<<<<<`/`=======`/`>>>>>>>` markers remain in the file. This would require experimentation against real `git diff --check` heuristics (e.g., testing marker lines with trailing whitespace variants, marker lines that are part of larger diff hunks not shown due to `--check`'s hunk-boundary heuristics, or extremely large files where `git diff --check` output gets truncated) which is out of scope for static code review alone.

```typescript
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
```
