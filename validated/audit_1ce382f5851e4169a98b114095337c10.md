Found the analog. It's in `EcdsaBeefy.sol`'s `verifyMmrUpdateProof`: the ECDSA-recovered signer authorities array is built and passed straight into a merkle multi-proof membership check, with no check that the recovered signer addresses (or their `authorityIndex` values) are unique.

### Title
Duplicate authority-index votes let a minority of signers satisfy the BEEFY supermajority threshold - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`checkParticipationThreshold` only compares `votes.length` to `2/3 * total + 1` of the authority set. It never verifies that each `Vote` corresponds to a distinct authority. A single colluding/compromised validator key (or a leaked/duplicated signature) can be repeated across the `votes` array with a fabricated but matching `authorityIndex`, inflating `sigLen` past the threshold without a real supermajority of distinct signers.

### Finding Description
In `verifyMmrUpdateProof` [1](#0-0) , `sigLen = relayProof.signedCommitment.votes.length` is checked against the threshold via `checkParticipationThreshold(sigLen, authoritySet.len)` at line 140, which is purely `len >= (2*total)/3 + 1` [2](#0-1) . The subsequent loop recovers an address per vote via `ECDSA.recover` and builds `MerkleMultiProof.Leaf` entries keyed by `vote.authorityIndex` [3](#0-2) , then verifies those leaves against the authority-set merkle root with `MerkleMultiProof.VerifyProof`. Nothing in this pipeline enforces that `authorityIndex` values are distinct across the `votes` array, nor that recovered addresses are distinct. If the merkle multi-proof library tolerates (or is not designed to reject) repeated leaf indices in its input array — which is plausible since its job is verifying inclusion of the supplied leaves, not uniqueness of the caller-supplied set — a proof can pad `votes` with N copies of one authority's valid signature over the same `commitmentHash`, satisfying `sigLen >= 2/3*total+1` while at most one (or a small colluding subset) of real signers actually attested to the commitment.

### Impact Explanation
This breaks the "consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted" pivot: a proof from far fewer than the required 2/3+1 real authorities could be accepted as a legitimate BEEFY commitment, allowing a minority of colluding/compromised validators to push a forged MMR root and finalize forged parachain headers/state commitments into Hyperbridge's trusted consensus state. Once a fabricated state commitment is stored via `handleConsensus`/`storeStateMachineCommitment` in `HandlerV2.sol` [4](#0-3) , it can be used to forge membership proofs for POST/GET requests and responses in `handlePostRequests`/`handleGetResponses`, leading to false proof/state acceptance, unauthorized message execution, and ultimately fund loss on any bridged asset or intent-settlement flow relying on that state machine.

### Likelihood Explanation
Exploitation requires only a minority of validator signing keys (fewer than the honest 2/3 supermajority) plus the ability to submit a permissionless `handleConsensus`/`verify` call — no relayer, prover, or admin privilege is needed to submit the crafted `RelayChainProof`; the vulnerability lies purely in on-chain input validation, not in trusting an honest-majority assumption being violated by a "malicious peer" (the guard should exist regardless of validator honesty). This satisfies the unprivileged-attacker requirement of the bounty gate, though full confirmation depends on whether `MerkleMultiProof.VerifyProof`'s underlying algorithm silently accepts duplicate indices/leaves — this detail lives in the external `@polytope-labs/solidity-merkle-trees` dependency and could not be directly inspected in this pass, so the precise exploitability (does the library dedupe internally) is uncertain and should be verified against that library's source before treating this as confirmed-exploitable.

### Recommendation
In `verifyMmrUpdateProof`, before or while building the `authorities` leaf array, track seen `authorityIndex` values (e.g., a bitmap or sorted-check) and revert with a new `DuplicateAuthorityIndex` error on any repeat, mirroring the duplicate-commitment defenses already used elsewhere in the codebase (e.g. `accumulate.rs`'s `seen.insert` dedup check [5](#0-4) ). This ensures `sigLen` only counts distinct authorities toward the supermajority threshold.

### Proof of Concept
Conceptual (cannot fully execute without the merkle-trees library source):
1. Obtain one valid authority signature `sig` over the commitment hash for a BEEFY commitment.
2. Construct `votes = [Vote(authorityIndex=k, signature=sig), Vote(authorityIndex=k, signature=sig), ...]` repeated `⌈2/3*total⌉+1` times, all pointing at the same real authority index `k`.
3. Submit this as `RelayChainProof.signedCommitment.votes` to `EcdsaBeefy.verify` via `HandlerV2.handleConsensus`.
4. `sigLen = votes.length` passes `checkParticipationThreshold`.
5. Each recovered leaf uses the same `(index=k, hash=keccak256(authority))`, so if `MerkleMultiProof.VerifyProof` validates this against `authoritySet.root` without rejecting repeated indices, the check at line 162 passes and a forged/attacker-influenced MMR root and parachain state commitments are accepted into `trustedState`.

    function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
        uint256 delay = block.timestamp - host.consensusUpdateTime();
        if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();

        bytes memory previousState = host.consensusState();
        (bytes memory verifiedState, IntermediateState[] memory intermediates, uint256 nextAuthoritySetId) =
            IConsensusV2(host.consensusClient()).verify(previousState, proof);

        if (keccak256(previousState) == keccak256(verifiedState)) return;
        host.storeConsensusState(verifiedState);

        uint256 intermediatesLen = intermediates.length;
        for (uint256 i = 0; i < intermediatesLen; i++) {
            IntermediateState memory intermediate = intermediates[i];
            uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
            if (latestHeight != 0 && intermediate.height > latestHeight) {
                StateMachineHeight memory stateMachineHeight =
                    StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
                host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
            }
        }

        // `nextAuthoritySetId` identifies the upcoming set; the relayer that delivered the proof
        // is credited as the relayer for the just-ended epoch (`nextAuthoritySetId - 1`).
        // If `nextAuthoritySetId == 0` no rotation has occurred, so there is nothing to record.
        if (nextAuthoritySetId == 0) return;
        uint256 epoch = nextAuthoritySetId - 1;
        if (epoch > host.currentEpoch()) {
            host.recordEpoch(epoch, _msgSender());
        }
    }
