### Title
Unauthenticated duplicate `EncryptionKeyMessage` triggers `assert!` panic (process crash) during PedPoP DKG - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Like CVE-2017-9223, where a crafted input file causes an invalid-memory-read crash, an attacker-controlled PedPoP protocol message can drive Serai's DKG code into a panic. `Decryption::register` enforces single-registration of a participant's encryption key with a bare `assert!`, so a participant who submits a second `EncryptionKeyMessage` (via `EncryptionKeyMessage::read` on attacker-controlled bytes) aborts the process instead of receiving a graceful error.

### Finding Description
`EncryptedMessage`/`EncryptionKeyMessage` payloads are deserialized from untrusted bytes via `EncryptionKeyMessage::read` / `EncryptedMessage::read`, which perform `C::read_G`, `SchnorrSignature::read`, and `M::read`/`E::read` and return `io::Result` for malformed input [1](#0-0) [2](#0-1) .

However, once a syntactically valid `EncryptionKeyMessage` is registered, the per-participant encryption key is stored in `Decryption.enc_keys`, and `register` panics if the same participant registers again:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(&mut self, participant: Participant, msg: EncryptionKeyMessage<C, M>) -> M {
    assert!(
      !self.enc_keys.contains_key(&participant),
      "Re-registering encryption key for a participant"
    );
    self.enc_keys.insert(participant, msg.enc_key);
    msg.msg
}
``` [3](#0-2) 

`Encryption::register` forwards directly to this without any deduplication or error path [4](#0-3) . The panic is also reachable through `encrypt`, which indexes `self.decryption.enc_keys[&participant]` (panics on missing key) [5](#0-4) , and `decrypt_with_proof`, which indexes `self.enc_keys[&decryptor]` [6](#0-5) .

This mirrors the parser-crash bug class: the deserializer is given attacker bytes, and a semantically-valid-but-hostile message sequence hits a panic rather than a `Result`. The same "index a map keyed by attacker-influenced `Participant`" pattern exists in `ThresholdKeys::new` (`verification_shares[i]` for participants `1..=t`) [7](#0-6)  and `ThresholdView` construction (`self.core.verification_shares[i]` over `included`) [8](#0-7) , which rely on every caller validating participant ranges beforehand — `ThresholdKeys::read` only guarantees keys `1..=n` are present when it calls `ThresholdKeys::new` [9](#0-8) .

### Impact Explanation
A single repeated `EncryptionKeyMessage` deterministically panics the host process (in release builds, `assert!` is still compiled in — only `debug_assert!` is elided). Since PedPoP drives threshold key generation for all validators, crashing one node during DKG aborts the key-generation session; crashing enough nodes prevents the validator set from being formed. This is a remote, low-cost denial of service — the analog of the FAAD2 crash — requiring only that the attacker can feed messages into the DKG read/registration path.

### Likelihood Explanation
Triggering requires only sending a second, otherwise-valid registration message — no forgeries, no timing. The only mitigating factor is whether the caller deduplicates messages per participant before calling `Encryption::register`; the PedPoP documentation explicitly states the library "does not handle networking" and puts duplicate-commitment detection on the caller [10](#0-9)  — but the `assert!` means a caller that fails to deduplicate (or an attacker able to inject before deduplication) crashes the process rather than getting a `Fault`/`Error` it can blame on the sender. Medium likelihood; Medium severity (DoS only, no secret leakage).

### Recommendation
Replace the `assert!` in `Decryption::register` with a fallible result (e.g., return `Result<M, DkgError>` and a `DuplicatedParticipant`-style error), and replace the `enc_keys[&participant]` / `enc_keys[&decryptor]` indexing in `encrypt`/`decrypt_with_proof` with `.get()` returning an error, so attacker-supplied message sequences can never panic. Similarly, audit map indexing in `ThresholdKeys::new`/`view` to ensure panics cannot be reached via `ThresholdKeys::read` on untrusted bytes.

### Proof of Concept
```rust
// Conceptual: two EncryptionKeyMessage payloads from the same Participant.
let msg_bytes_1 = ...; // EncryptionKeyMessage::serialize() output, participant P
let msg_bytes_2 = ...; // second registration for participant P (attacker-controlled bytes)

let m1 = EncryptionKeyMessage::<C, M>::read(&mut &msg_bytes_1[..], params).unwrap();
let m2 = EncryptionKeyMessage::<C, M>::read(&mut &msg_bytes_2[..], params).unwrap();

encryption.register(Participant::new(P).unwrap(), m1); // ok
encryption.register(Participant::new(P).unwrap(), m2); // panic! "Re-registering encryption key"
```
The second `register` hits the `assert!` at `crypto/dkg/pedpop/src/encryption.rs:356` and aborts the process — a crash driven entirely by bytes read via `EncryptionKeyMessage::read`.

Caveat: this finding assumes the integrating caller (e.g., the DKG session handler) forwards duplicate messages to `Encryption::register`; if a strict per-participant dedup layer exists upstream, reachability is reduced. The `assert!` remains a latent crash primitive reachable from attacker-parsed input regardless.
