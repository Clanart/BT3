### Title
Scanner accepts dust/zero-value outputs as `ReceivedOutput`, crediting funds that cannot economically be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The Derby finding is a precision/rounding issue: a user requests a withdrawal of an amount so small that `(_value * governanceFee) / 10_000` truncates to zero, letting them withdraw without paying the DAO fee. The general class is "small-value inputs bypass the cost check because the fee/cost computation rounds to zero or is not applied at all".

The analog in Serai's in-scope code lives in the Bitcoin wallet: `Scanner::scan_transaction` registers **any** transaction output whose `script_pubkey` matches a registered script as a spendable `ReceivedOutput`, with no minimum-value (dust) check — the only place a value floor exists in this codebase is on the *payment* side of `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), never on the receive side.

### Finding Description

In `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`), an output is turned into a `ReceivedOutput` purely on `self.scripts.get(&output.script_pubkey)` — the output's `value` is never inspected:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

The `DUST` constant (546 sats) and its enforcement exist only for outgoing payments in `SignableTransaction::new` (`send.rs:165-169`, and the change check at `send.rs:228-234`). Nothing prevents the scanner from crediting an output of 1 sat, or even a 0-value output, to the threshold wallet.

Spending a P2TR input costs roughly ~58 vBytes of transaction weight plus its share of the fixed overhead. At any non-trivial `fee_per_vbyte`, an input whose value is below the marginal fee it adds is a net loss: including it in `SignableTransaction::new` either causes `NotEnoughFunds` (`send.rs:215-221`) or silently increases `fee()` (`send.rs:138-141`) by more than the input contributes. The wallet has no way to refuse such an input once the scheduler hands it `inputs: Vec<ReceivedOutput>` — `SignableTransaction::new` treats all provided inputs as mandatory.

### Impact Explanation

An unprivileged party can send a dust (or zero-value) output to a registered Serai address. That output is scanned and reported as received balance, yet it is economically unspendable: it can never contribute net value to a withdrawal transaction. At best the scheduler must permanently track and exclude it; at worst, if the dust is selected as an input, the threshold wallet pays more in fees than the deposit was worth — i.e., the depositor moved value into the wallet's accounting while the *wallet* bears the cost, the mirror image of the Derby bug where the user withdraws while the DAO bears the missing fee. Repeated dusting forces perpetual fee loss or permanently unspendable credited funds.

### Likelihood Explanation

Sending dust to a P2TR output is fully permissionless: the attacker only needs the address, which is public on-chain. Each dust output is cheap to create (a single transaction can carry hundreds of outputs to the same address at near-marginal cost per output). Whether loss materializes depends on the UTXO scheduler selecting dust inputs, but the accounting/inflation-of-received-funds issue is deterministic — `scan_transaction` will always return them as `ReceivedOutput`s.

### Recommendation

Apply a minimum-value filter in `Scanner::scan_transaction` (or when constructing `ReceivedOutput`s), mirroring the `DUST` check already used for payments: ignore outputs with `output.value < DUST`, since such outputs are both non-standard to produce and uneconomical to spend. Alternatively/additionally, have `SignableTransaction::new` or the input-selection layer skip inputs whose value is less than the marginal fee their inclusion adds (input weight × `fee_per_vbyte`).

### Proof of Concept

1. Register an offset with `Scanner::register_offset`, producing a P2TR `script_pubkey`.
2. As an unprivileged third party, broadcast a transaction containing an output paying 1 sat (mined via direct miner submission to bypass relay dust rules; outputs with value below dust but ≥ 1 are consensus-valid) to that `script_pubkey`.
3. Call `Scanner::scan_transaction` on the confirmed transaction — it returns a `ReceivedOutput` crediting 1 sat (`mod.rs:199-214`), with no dust rejection.
4. Pass this `ReceivedOutput` into `SignableTransaction::new` alongside other inputs: the dust input adds ~58+ vBytes of weight, raising `needed_fee`/`fee()` (`send.rs:204-213`, `send.rs:138-141`) by far more than 1 sat, or triggers `NotEnoughFunds` at the margin — the credited funds can never be net-spent.

Relevant code: `networks/bitcoin/src/wallet/mod.rs:199-214` (no value check on receive), `networks/bitcoin/src/wallet/send.rs:32` (`DUST`), `send.rs:165-169` (dust enforced only for payments), `send.rs:215-221` (`NotEnoughFunds`), `send.rs:138-141` (actual fee = inputs − outputs).
