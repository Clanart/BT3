### Title
Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw()` allows escrow finalization without actual token transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` implements its own `withdraw()` function using raw low-level `.call()` to move ERC20 tokens instead of OpenZeppelin's `SafeERC20.safeTransfer` (which the canonical EVM contract uses). The function only checks that the low-level call itself did not revert, never inspecting the ABI-decoded boolean return value of `transfer()`. This is the exact same missing-check class as the Sherlock M-8 report: a call that returns `success = true` (because the EVM treats no-code/graceful-return as success) even though the intended action — moving tokens — never happened.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function (used by `onAccept` for `RedeemEscrow`/`RefundEscrow`, and by `onGetResponse`) releases escrowed tokens like this: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

This only checks whether the low-level `call` reverted — it does not decode/require the `bool` that `transfer()` is supposed to return. Any ERC20 implementation that returns `false` on failure instead of reverting (a well-known class of non-standard tokens) will make `success == true` even though no tokens moved. `_orders[commitment][token]` is decremented and, on the finalize path, `_filled[commitment]` is permanently set to the beneficiary before this call in `withdraw()`, so the order is irreversibly marked complete regardless of whether the transfer actually succeeded. [2](#0-1) 

By contrast, the canonical (non-Tron) `IntentsBase._withdraw()` correctly uses `IERC20(token).safeTransfer(beneficiary, amount);`, which reverts on both a `false` return value and on calls to non-contract addresses: [3](#0-2) 

The Tron file diverges from this safe pattern for both the token transfer and the fee-token transfer: [4](#0-3) 

### Impact Explanation
Because the withdrawal path never verifies the token's `transfer()` return value, an order can be marked `_filled[commitment] = beneficiary` (a one-way, non-retryable finalization) while the tokens never actually leave the gateway. This satisfies the bounty's "loss of funds" criterion: the rightful beneficiary permanently loses the ability to claim their escrow — `_filled` blocks any future fill/cancel/refund path for that commitment — while `_orders[commitment][token]` bookkeeping is already decremented, so tokens become permanently stranded in the gateway contract with no accounting trail pointing back to them. This applies to `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund after cancellation) flows driven through `onAccept`, both of which are reachable via the normal ISMP message-processing path (not requiring any malicious relayer or admin — the vulnerability lies in the destination contract's blind trust of the call's raw success bit).

### Likelihood Explanation
The trigger condition is that one of the order's `TokenInfo.token` addresses is a non-standard ERC20 that returns `false` on failed transfers rather than reverting. Users freely choose the input/output token addresses when placing an order (`Order.inputs`/`Order.outputs`), so this is directly reachable by any unprivileged order-placer choosing such a token, or when the gateway's token balance happens to be insufficient for reasons independent of the escrow accounting (e.g., fee-on-transfer tokens leaving the gateway short by a few wei). No relayer, prover, or admin compromise is required — the corrupted invariant is purely a missing check inside contract logic.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in the Tron `IntentGatewayV2.withdraw()` (and the equivalent dust-sweep code) with `SafeERC20.safeTransfer`/`safeTransferFrom`, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both a `false` return and a call to a non-contract address revert the transaction rather than silently succeeding.

### Proof of Concept
1. User places a cross-chain order with `inputs`/`outputs` containing a custom ERC20 token whose `transfer()` implementation returns `false` on internal failure instead of reverting (e.g., insufficient balance path deliberately coded to `return false;`).
2. A `RedeemEscrow` or `RefundEscrow` message reaches the Tron `IntentGatewayV2.onAccept()`, invoking `withdraw()`.
3. `_orders[commitment][token]` is decremented and, on finalize, `_filled[commitment]` is set to the beneficiary before/around the transfer call.
4. `token.call(...transfer...)` returns `success = true` (the call itself doesn't revert) even though the token's internal logic returned `false` and no balance moved.
5. The function completes normally, emitting `EscrowReleased`/`EscrowRefunded`; the order is now permanently finalized with `_filled[commitment] != address(0)`, yet the beneficiary's on-chain token balance is unchanged — the escrowed tokens are stuck in the gateway with no remaining code path to recover them.

**Note on verification limits:** I was unable to fully trace whether `_orders`/`_filled` accounting could additionally be exploited to fully drain other users' unrelated escrow (e.g., via cross-commitment interference), because the surrounding `select`/`fillOrder`/`placeOrder` logic in the Tron contract was not fully read in this session due to iteration limits. The core "missing check on ERC20 return value → false success → fund loss/lock" primitive is confirmed directly from the code shown above.
