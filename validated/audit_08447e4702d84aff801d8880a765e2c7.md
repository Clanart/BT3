## Finding: Missing HTML/XSS-unsafe-character escaping in Python (`json_format.py`) and upb-based (PHP/Ruby) ProtoJSON encoders

### Title
Inconsistent JSON HTML-unsafe-character escaping in Python `json_format.MessageToJson` and upb-based JSON encoder allows script-breakout when ProtoJSON output is embedded in HTML - (File: `python/google/protobuf/json_format.py`, `upb/json/encode.c`)

### Summary
The filebrowser advisory's root cause is that attacker-influenced string content is written into an HTML document using a renderer (`text/template`) that performs no context-aware escaping, letting `</title><script>...` break out of its enclosing tag. Protobuf's own C++, Java, and C# ProtoJSON encoders defend against the structurally identical risk — untrusted string field values being embedded into an HTML/`<script>` context after JSON serialization — by explicitly escaping `<`, `>`, `&`, `=`, and `'` in addition to standard JSON escapes. This defense is missing from the Python pure implementation of `MessageToJson`/`MessageToDict` and from the upb C JSON encoder shared by the PHP and Ruby bindings, creating an inconsistent, weaker escaping guarantee across officially supported Protobuf language runtimes for the exact same public ProtoJSON serialization API.

### Finding Description
Google's own C++, Java, and C# implementations treat `<`, `>`, `&`, `=`, and `'` as characters that must be escaped in ProtoJSON string output, specifically to prevent HTML/script-injection when JSON is embedded in an HTML page (a very common integration pattern, e.g. server-side rendering JSON into a `<script>` block for client hydration — the same pattern implicated in the filebrowser report).

- C++ JSON writer explicitly escapes `<`, `>`, and other HTML-unsafe characters: [1](#0-0) 
- Java's `JsonFormat` has an explicit regression test (`b/73832901`) asserting `<`, `>`, `&`, `=`, `'` are escaped as `\u003c`, `\u003e`, `\u0026`, `\u003d`, `\u0027`: [2](#0-1)  backed by the encoder's `replacementChars` table for `<>&='`: [3](#0-2) 
- C#'s `JsonFormatter` does the same via its `CommonRepresentations` table (`\u003c`, `\u003e`): [4](#0-3) 
- C++ core JSON test suite has the matching `HtmlEscape` test: [5](#0-4) 

In contrast:
- The pure-Python `json_format.py` implementation delegates string escaping entirely to Python's stdlib `json.dumps`, which does **not** escape `<`, `>`, `&`, `=`, or `'`: [6](#0-5)  This is confirmed by the project's own test, which asserts the literal (unescaped) characters `<` and `>` appear in the output rather than `\u003c`/`\u003e`: [7](#0-6) 
- The upb C JSON encoder (`jsonenc_put_escaped_char`), which is shared verbatim across the PHP extension and the Ruby extension, only implements the minimal JSON-spec escapes (`\n`, `\r`, `\t`, `\"`, `\f`, `\b`, `\\`, and control chars `< 0x20`) and passes `<`, `>`, `&`, `=`, `'` straight through unescaped: [8](#0-7)  The identical function is duplicated in the PHP extension: [9](#0-8)  and in the Ruby extension: [10](#0-9) 

The invariant that transfers from the filebrowser report is: *attacker-controlled string content must not be able to break out of the HTML/script context it will be embedded in once serialized*. Java/C#/C++ enforce this invariant inside the library itself (defense-in-depth, independent of what the consuming application does), as evidenced by the dedicated regression tests referencing a real historical bug (`b/73832901`). Python and the upb-based bindings (PHP, Ruby) do not enforce it, so a consuming application that follows the same pattern documented as risky in the filebrowser advisory — rendering ProtoJSON output into an HTML `<script>` block — is not protected by these three official Protobuf runtimes the way it is protected in C++, Java, and C#.

### Impact Explanation
An ordinary client that can set a string field's value through any supported ProtoJSON/binary parse path (e.g. `optional_string = "</script><script>...</script>"`) and cause the message to be re-serialized to JSON by a Python, PHP, or Ruby consuming application, and then have that JSON embedded into an HTML page (a widespread pattern for client-side hydration of server-rendered data — structurally identical to the branding-injection scenario in the filebrowser report) can break out of the enclosing `<script>` tag and inject arbitrary markup/script. This is a stored/reflected XSS-class impact affecting any consumer of these three official ProtoJSON encoders, whereas the same operation is safe in C++, Java, and C#.

### Likelihood Explanation
The escaping gap is deterministic and always reachable through the fully public, documented API (`json_format.MessageToJson`/`MessageToDict` in Python; the standard `serializeToJsonStream`/`toJsonString` PHP/Ruby APIs backed by upb). No malformed input, size limits, or special parser modes are required — a normal string field value containing `<`, `>`, `&`, `=`, or `'` is sufficient. The only precondition is that the consuming application embeds ProtoJSON output into an HTML/script context without its own additional escaping — exactly the assumption already validated as realistic by Java's own regression test for this exact class of bug.

### Recommendation
Align the Python pure implementation (`python/google/protobuf/json_format.py`) and the shared upb C JSON encoder (`upb/json/encode.c`, and by extension the PHP/Ruby generated copies) with the C++/Java/C# behavior: escape `<`, `>`, `&`, `=`, and `'` (in addition to the standard JSON escapes) when writing string field values, matching the `MustEscape`/`kEscapedRanges` logic already implemented in `src/google/protobuf/json/internal/writer.cc`. Update the corresponding test expectations (e.g. `testJsonEscapeString` in `python/google/protobuf/internal/json_format_test.py`) to require `\u003c`/`\u003e`/`\u0026`/`\u003d`/`\u0027` output, consistent with Java's `testHtmlEscape`.

### Proof of Concept
Using the existing test in the repository as a concrete demonstration of the gap (no modification needed to trigger — this is the current, passing behavior):
```python
# python/google/protobuf/internal/json_format_test.py:296-304
message.string_value = '&\n<"\r>\b\t\f\\\001/'
json_format.MessageToJson(message)
# => '{\n  "stringValue": "&\\n<\\"\\r>\\b\\t\\f\\\\\\u0001/..."\n}'
```
The literal `<` and `>` (and `&`) characters are emitted unescaped by Python's `MessageToJson`. Compare with Java's equivalent input in `JsonFormatTest.testHtmlEscape` (`java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:2028-2030`), which for the same characters produces `\u003c\u003e\u0026\u003d\u0027` — i.e., safely escaped. Embedding the Python (or PHP/Ruby, via `upb/json/encode.c`) output verbatim inside `<script>var data = {json_output};</script>` allows a string value of `</script><script>alert(1)</script>` to terminate the script block and execute injected JavaScript, mirroring the filebrowser `branding.name` breakout exactly.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
