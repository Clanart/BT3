### Title
CPU-exhaustion DoS via unbounded signature-recovery amplification during transaction sender validation - (File: blockchain/types/transaction.go)

### Summary
`tx.ValidateSender()` recovers a public key for **every** signature present in a Kaia-typed transaction's `TxSignatures` list via full secp256k1 `Ecrecover` operations, before checking how many signatures the target account's `AccountKey` actually requires or is willing to pay for. An attacker can craft a transaction with hundreds to thousands of extra, fully valid (but redundant) signatures from their own key, forcing every node that processes the transaction (via RPC submission or p2p propagation) to perform expensive elliptic-curve recovery for each one, while paying no additional gas.

### Finding Description
For any non-Ethereum-typed Kaia transaction, `Transaction.ValidateSender` calls `SenderPubkey(signer, tx)`, which invokes `RecoverTxPubkeys` → `TxSignatures.RecoverPubkey`, which loops over **all** elements of `t` and calls `crypto.Ecrecover` for each one [3](#0-2) . This recovery is unconditional and happens *before* any check on how many signatures the account actually supports:

```
pubkey, err := SenderPubkey(signer, tx)          // full EC-recover for every sig
...
gasKey, err := accKey.SigValidationGas(currentBlockNumber, GetRoleTypeForValidation(tx.Type()), len(pubkey))
...
if err := accountkey.ValidateAccountKey(currentBlockNumber, from, accKey, pubkey, ...); err != nil {
``` [4](#0-3) 

For an `AccountKeyPublic` account (the common single-key EOA type), `SigValidationGas` always returns `(1-1)*TxValidationGasPerKey = 0` regardless of how many signatures were submitted [1](#0-0) , and `Validate` only rejects the transaction *after* the fact, once `len(recoveredKeys) != 1` [2](#0-1) .

The only pre-decode gate is `SanityCheckSignatures`, invoked from `DecodeRLP`, which for Kaia-typed transactions calls `sigs.ValidateSignature()` — this is a cheap canonical bound-check (non-zero `r`/`s`, low-`s`, matching chain id) on every signature, **not** a full elliptic-curve recovery [5](#0-4) [6](#0-5) . The number of signatures is bounded only by `MaxTxDataSize` (128 KB) [7](#0-6) [8](#0-7) , which still permits well over a thousand valid ECDSA signatures (each ~68 bytes RLP-encoded) in a single transaction — all can be produced trivially by the attacker re-signing the same sighash with their own private key.

`tx_pool.go`'s `validateTx` calls `tx.ValidateSender` (line 898) essentially as the first substantive check, before nonce, balance, or intrinsic-gas checks are enforced [9](#0-8) , and this happens on every node that receives the transaction, whether via direct RPC submission or via `handleTxMsg` gossip propagation of pool-accepted transactions [10](#0-9) .

This mirrors the FOSUserBundle bug class: a cheap-looking, attacker-controlled request field (password length / here, extra signatures) forces the server to perform an expensive cryptographic computation (PBKDF2 / here, EC point recovery) proportional to attacker-chosen input size, disproportionate to the actual value or cost paid by the requester, before any rejection occurs.

### Impact Explanation
An attacker can submit a single transaction (basic value transfer, minimal gas) with ~1,000–1,900 redundant valid signatures. Every node performing mempool admission or receiving the propagated transaction must perform that many full secp256k1 `Ecrecover` calls (each notably more expensive than a hash operation) at essentially zero marginal gas cost to the attacker. Repeated submission of many such transactions (from different nonces/addresses to bypass "known tx" caching) can meaningfully degrade validator/full-node CPU availability, a network-wide resource-consumption impact reachable purely from an unprivileged transaction sender via public RPC — Medium severity, consistent with the CVE-2013-5750 classification (CWE-400, CPU consumption DoS).

### Likelihood Explanation
Likelihood is high for any attacker able to submit transactions to a public RPC endpoint: constructing a transaction with many self-signed, canonically-valid signatures requires only a single private key and standard ECDSA signing (no protocol privilege), and the size limit (`MaxTxDataSize` = 128 KB) still permits well over a thousand redundant signatures per transaction.

### Recommendation
Cap the number of signatures processed/recovered in `TxSignatures.RecoverPubkey` (and equivalently for fee-payer signatures) to `accountkey.MaxNumKeysForMultiSig` (or a similarly small bound) *before* performing any EC recovery, rejecting transactions that exceed the bound at cheap, pre-recovery validation (e.g., in `SanityCheckSignatures`/`DecodeRLP`) rather than only bounding stored `AccountKey.Keys` length after the recoveries already occurred.

### Proof of Concept
1. Generate a valid EOA with `AccountKeyPublic` (default account type).
2. Construct a basic `TxTypeValueTransfer` with normal fields.
3. Sign the transaction sighash ~1,800 times with the same private key using `crypto.Sign` (each call yields a distinct, canonically valid signature due to different ephemeral nonce `k`), and populate `TxSignatures` with all of them via `tx.SetSignature(txSignatures)` bypassing the normal single-signature helper.
4. Submit via `eth_sendRawTransaction` / txpool `AddRemote`.
5. Observe: `DecodeRLP`/`SanityCheckSignatures` accepts it (cheap bound checks only) [11](#0-10) ; `validateTx` → `ValidateSender` → `SenderPubkey` performs ~1,800 full `Ecrecover` calls [3](#0-2) ; the transaction is ultimately rejected only afterward by `AccountKeyPublic.Validate` (`len(recoveredKeys) != 1`) [2](#0-1) , but the CPU cost of the recoveries has already been incurred by the validating node.

// handleTxMsg handles transaction-propagating message.
func handleTxMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	// Transactions arrived, make sure we have a valid and fresh chain to handle them
	if pm.acceptTxs.Load() == 0 {
		return nil
	}
	// Transactions can be processed, parse all of them and deliver to the pool
	var txs types.Transactions
	if err := msg.Decode(&txs); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Only valid txs should be pushed into the pool.
	validTxs := make(types.Transactions, 0, len(txs))
	var err error
	for i, tx := range txs {
		// Validate and mark the remote transaction
		if tx == nil {
			err = errResp(ErrDecode, "transaction %d is nil", i)
			continue
		}
		// Validate blob transactions to detect KZG verification errors early
		// KZG verification is computationally expensive, so this acts as a
		// defensive measure against potential DoS attacks.
		if tx.Type() == types.TxTypeEthereumBlob {
			// Without blob hashes the verification below passes vacuously.
			if len(tx.BlobHashes()) == 0 {
				return errResp(ErrDecode, "Invalid blob transaction with sidecar: %v", errBloblessBlobTx)
			}
			sidecar := tx.BlobTxSidecar()
			if sidecar != nil {
				key := blobSidecarKey(tx.BlobHashes(), sidecar)
				if !pm.verifiedBlobTxs.Contains(key) {
					// If any of the transaction contains invalid KZG sidecar, terminate transaction processing immediately.
					// KZG verification is computationally expensive, so this acts as a
					// defensive measure against potential DoS attacks.
					if err := sidecar.ValidateWithBlobHashes(tx.BlobHashes()); err != nil {
						logger.Warn("Disconnect peer for protocol violation", "peer", p.GetID(), "error", err)
						return errResp(ErrDecode, "Invalid blob transaction with sidecar: %v", errKZGVerificationError)
					}
					pm.verifiedBlobTxs.Add(key)
				}
			}
		}
		p.AddToKnownTxs(tx.Hash())
		validTxs = append(validTxs, tx)
		txReceiveCounter.Inc(1)
	}
	pm.txpool.HandleTxMsg(validTxs)
	return err
