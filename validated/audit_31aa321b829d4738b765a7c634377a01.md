### Title
Missing validation of payment scripts lets unspendable/non-standard outputs be signed, burning funds or producing unbroadcastable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates payment *amounts* (dust threshold, sufficient funds, fee rate, tx weight) but performs no validation on the payment `ScriptBuf`s themselves. A payment to a provably unspendable script (e.g., `OP_RETURN`, or any invalid/non-standard script) is accepted, incorporated into the sighash, and driven through a full FROST signing round. The result is either a consensus-valid transaction whose output can never be spent (permanently burning the payment amount from the multisig's UTXO pool) or a transaction that is consensus-invalid / non-standard and can never confirm — the same "create succeeds, execution always fails" shape as the GovernorBravo `targets` report.

### Finding Description
`SignableTransaction::new` checks:
- `inputs` non-empty (`NoInputs`)
- at least one output exists (`NoOutputs`)
- payment amounts `>= DUST` (`DustPayment`)
- `data.len() <= 80`
- fee and sufficiency of funds
- `weight <= MAX_STANDARD_TX_WEIGHT` [1](#0-0) 

It never inspects `payment.0` (the `ScriptBuf`). The outputs are built verbatim at lines 188–191: [2](#0-1) 

The transaction is then signed per-input with `Prevouts::All` in `TransactionSignMachine::sign` and broadcast after `complete`: [3](#0-2) 

Payment/destination scripts originate from untrusted on-chain data — instructions embedded in deposits are decoded into payment/refund destinations (`presumed_origin`, `refund_to`, withdrawal addresses) and fed into `SignableTransaction::new` by the processor. An unprivileged depositor controls these bytes via the transaction data they cause to be acted on. There is also no duplicate-input check: two `ReceivedOutput`s (craftable via `ReceivedOutput::read`, which blindly accepts an `OutPoint` at `networks/bitcoin/src/wallet/mod.rs:122-133`) sharing the same outpoint produce a guaranteed-invalid double-spend transaction that still consumes a complete threshold signing session.

### Impact Explanation
- **Burned funds:** a payment of `>= DUST` sats to an `OP_RETURN` or otherwise unspendable script produces a valid, signed, broadcastable transaction whose output can never be spent. The multisig loses `payment_sat` sats permanently.
- **Guaranteed-failed execution / wasted signing:** a non-standard script, or duplicated inputs, yields a transaction the network will reject, yet the full FROST preprocess/sign/complete round is executed — precisely the "useless processing of queue and vote" cost from the original finding, mapped onto Serai's threshold-signing rounds.

### Likelihood Explanation
Payment scripts are attacker-influenced bytes carried in deposit instructions (refund/withdrawal destinations). No sanity check (`script_pubkey.is_op_return()`, standardness, or well-formedness) stands between that data and a signed transaction. Triggering requires only crafting a deposit whose embedded instruction decodes to an unspendable destination, or feeding a crafted `ReceivedOutput` with a duplicated/foreign outpoint.

### Recommendation
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), reject payment outputs where `script_pubkey.is_op_return()` or otherwise provably unspendable, and optionally enforce output script standardness. Also deduplicate `inputs` by `outpoint` (or reject duplicate outpoints) before constructing `tx_ins`, so a malformed `ReceivedOutput` cannot produce a guaranteed-invalid transaction after a full signing round.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs context
let payments = [(
  // Provably unspendable: OP_RETURN carrying a push
  ScriptBuf::new_op_return(PushBytesBuf::try_from(vec![0u8; 4]).unwrap()),
  100_000, // passes the >= DUST check
)];
let tx = SignableTransaction::new(vec![scanned_output], &payments, None, None, FEE).unwrap();
// Succeeds. After TransactionMachine::preprocess/sign/complete, the signed
// transaction sends 100_000 sats to an output that can never be spent —
// the funds are burned, and the multisig consumed a full FROST round.
// Variant: pass two ReceivedOutputs with the same `outpoint` (craftable via
// ReceivedOutput::read) — `new` accepts them, `multisig`/`sign`/`complete`
// succeed, and the resulting double-spend transaction is always rejected.
```
