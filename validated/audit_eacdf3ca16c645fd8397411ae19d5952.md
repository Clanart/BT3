## Finding: Tron IntentGatewayV2 authenticates unregistered source chains against its own address (fail-open default) instead of failing closed

### Title
Fail-open peer authentication in Tron `IntentGatewayV2.authenticate()` accepts settlement messages from unregistered chains - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM reference implementation of the IntentGateway (`IntentsBase.sol`) resolves a remote peer address via `_instance()`, which **reverts with `UnknownInstance`** if no gateway has been explicitly registered for a given source chain [1](#0-0) . The Tron variant of the same contract implements the equivalent `instance()` lookup with a silent fallback that returns `address(this)` instead of reverting when the chain is unregistered [2](#0-1) . This fallback value is fed directly into the authentication gate that guards `RedeemEscrow`/`RefundEscrow` settlement, the exact code path that releases escrowed user funds [3](#0-2) [4](#0-3) .

### Finding Description
`onAccept` on both implementations dispatches `RedeemEscrow`/`RefundEscrow` bodies to `withdraw()`/`_withdraw()` only after calling `authenticate(request)`/`_authenticate(request)`, which is meant to verify the incoming post request truly originates from **a registered peer instance of the gateway** on the claimed source chain [5](#0-4) .

- EVM version: `_instance()` treats an unregistered `stateMachineId` as an error (`revert UnknownInstance()`), so `_authenticate()` fails closed for any chain that has not had an explicit `Deployment` registered via governance (`NewDeployment`) [1](#0-0) .
- Tron version: `instance()` treats an unregistered `stateMachineId` as equivalent to `address(this)` — i.e., "assume the peer is myself" [2](#0-1) . `authenticate()` then compares `module` (derived from the raw `request.from` bytes of the *actual* dispatching contract on the source chain) against this fallback value, so **any post request whose `from` field equals the local Tron gateway's own address is accepted as an authenticated peer, for any source chain that was never registered** [3](#0-2) .

This is the same class of defect the external report describes: a trust boundary intended to scope authority narrowly (a manager should only touch the tokens they manage; a peer gateway should only be trusted for its own registered chain) instead grants broader-than-intended authority, here by defaulting an unauthenticated/unregistered case to a permissive fallback rather than rejecting it.

`withdraw()`/`_withdraw()` itself performs no additional check that the caller of the authenticated message actually corresponds to a real fill/cancellation event; it trusts `body.commitment`, `body.tokens`, and `body.beneficiary` verbatim once `authenticate()` passes [6](#0-5) . So once the fail-open authentication path is triggered for any commitment with outstanding escrow, the entire escrowed balance for that order can be redirected to an attacker-chosen `beneficiary`.

### Impact Explanation
If the fail-open condition is triggered, an attacker can forge a `RedeemEscrow`/`RefundEscrow` message for **any** order commitment placed on the Tron gateway and redirect its full escrowed input tokens (plus accumulated transaction fees) to a beneficiary of their choosing — a direct "stealing or loss of funds" / "false proof-state acceptance" outcome matching the bounty's accepted impact categories. This is strictly worse than the reported Balancer bug because it is not scoped to "a manager's own token" — it is scoped to the entire escrow ledger of the gateway.

### Likelihood Explanation
The precondition for triggering the fallback is that `request.source` is a state machine not yet present in `_instances` (true by default for every newly supported chain until governance issues `NewDeployment`) **and** the real dispatching module's address on that chain (which becomes `request.from`, normally set by the host itself and not spoofable by the caller) happens to equal the Tron gateway's own address bytes. Because the EVM peers are deliberately deployed at an identical deterministic CREATE2 address across EVM chains by design [7](#0-6) , this collision is far more plausible than pure hash-preimage brute force would suggest whenever a *new* chain is onboarded to the peer set before its `NewDeployment` governance call lands, or wherever any other module happens to reuse that address space. Even setting aside the collision precondition, the code-level defect itself (fail-open vs. fail-closed divergence from the audited EVM implementation) is unambiguous and locally verifiable — it is a latent access-control weakness that only needs the right combination of chain-onboarding timing/state to become live.

### Recommendation
Make `instance()` on the Tron contract match the EVM contract's fail-closed semantics: revert (e.g., with `UnknownInstance`) when no gateway is registered for the given `stateMachineId`, instead of returning `address(this)`. Never treat "unregistered peer" as implicitly equal to "self." Additionally, add a defense-in-depth check in `withdraw()` that the settlement message's origin chain matches the chain recorded at order-placement time for that specific commitment, so that even a compromised/misconfigured `authenticate()` cannot redirect funds for orders that were never associated with that peer.

### Proof of Concept
Conceptual sequence (illustrating the code-level logic; full exploitation requires an address collision as discussed above):
1. Attacker identifies (or arranges) a state machine `X` that Hyperbridge recognizes as valid but that has never had `NewDeployment` called on the Tron `IntentGatewayV2` for it (`_instances[keccak256(X)] == address(0)`).
2. Attacker deploys/controls a dispatching contract on chain `X` whose address, as raw 20 bytes, equals the Tron gateway's own address.
3. Attacker dispatches a `PostRequest` from chain `X` to the Tron gateway with body `[RedeemEscrow, WithdrawalRequest{commitment: <any known order commitment with escrow>, tokens: <full escrowed amounts>, beneficiary: <attacker address>}]`.
4. Hyperbridge relays and verifies the message is genuinely from chain `X` (state proof valid); `onAccept` is invoked with `request.source = X`, `request.from = <attacker's matching address>`.
5. `authenticate(request)` computes `instance(X)`. Since `X` is unregistered, this returns `address(this)` (the Tron gateway itself) rather than reverting [2](#0-1) ; because `module == address(this)`, the check `instance(request.source) != module` is false, so authentication **passes**.
6. `withdraw()` executes unconditionally, transferring the full escrowed inputs for the targeted commitment to the attacker's `beneficiary` [8](#0-7) .

    /**
     * @notice Withdraws the escrowed tokens for a request body.
     * @dev This function is marked as internal.
     * @param body The request body containing commitment, tokens, and beneficiary.
     * @param isRefund Whether this is a refund (true) or a successful fill (false).
     */
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
