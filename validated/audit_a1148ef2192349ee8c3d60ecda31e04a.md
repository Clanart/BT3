### Title
Ed448 `is_torsion_free` is a tautology (`-P + P == 0`), so `read_G` accepts small-order points - (crypto/ed448/src/point.rs)

### Summary
`crypto/ed448/src/point.rs` implements `Point::is_torsion_free` as `(*self * (Scalar::ZERO - Scalar::ONE)) + self`, i.e. `-P + P`, which is the identity for *every* point. The torsion check inside `GroupEncoding::from_bytes` therefore never rejects anything, and `Ed448::read_G` (via `Ciphersuite::read_G`) accepts Ed448 points with order-2/order-4 torsion components. This violates the `PrimeGroup` contract that `C::G` requires everywhere in FROST/DKG code, analogous to the report's "the filter rejects the canonical form but misses an alternate representation" class.

### Finding Description [1](#0-0) 

```rust
impl Point {
  fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
  }
}
```

`Scalar::ZERO - Scalar::ONE` is `-1`, so the expression is `-P + P`, which is unconditionally identity. Contrast with `Ed25519Point` in `crypto/dalek-ff-group`, which is Ristretto (canonically torsion-free by construction), and with the intended check here, which should be `[l]P == 0` (multiply by the prime subgroup order) or equivalent cofactor clearing. `from_bytes` gates acceptance on `point.is_torsion_free()` (line 316), so the gate is decorative.

`Ciphersuite::read_G` only checks canonical round-trip encoding (`point.to_bytes() == encoding`), not subgroup membership [2](#0-1) , and `type G: ... PrimeGroup` encodes the assumption in the type system [3](#0-2) . Any attacker-supplied bytes reaching `read_G` on Ed448 — DKG `Commitments`/`EncryptedMessage`, FROST preprocesses (nonce commitments), signature shares, `SchnorrSignature::read` — can therefore deserialize points outside the prime-order subgroup.

### Impact Explanation
All downstream math assumes every `C::G` has prime order `l`. With a torsion component admitted:

- A malicious Ed448 DKG participant can include a torsion component in a commitment/verification share or nonce commitment. Statements of the form `s·G == R + c·A` are checked over the full curve, but any expression that multiplies the adversarial point by a scalar preserves only the torsion part modulo 4 of the scalar — giving the attacker extra degrees of freedom the security proof (which assumes a prime-order group) does not account for.
- For FROST Ed448 signatures, the group key or aggregate nonce can carry a torsion component, producing signatures that verify under Serai's `SchnorrSignature::verify` (`R + cA − sG == 0` over the full curve) yet are non-canonical/mis-binding relative to RFC 8032 semantics, where cofactor clearing (`8R = 8sG − 8cA`) changes which signatures verify. A verifier-side malleability gap: signatures valid under one formula can be invalid under the other, so a signature Serai accepts may be rejected by external verifiers or vice versa — an incorrect-verifier-formula discrepancy directly reachable with attacker bytes via `SchnorrSignature::<Ed448>::read` + `verify`.
- The same vacuous check lets a torsion point be queued into `BatchVerifier` / `multiexp_vartime` paths, where random weights mod `l` do not cancel order-4 components deterministically, breaking the blame-attribution assumptions.

### Likelihood Explanation
Reachable by any unprivileged participant who can submit Ed448-encoded bytes: a DKG/commitment message, a FROST preprocess, or a serialized `SchnorrSignature`/`DLEqProof`. Crafting an order-4 point on Ed448 and encoding it is straightforward (the encoding even survives the negative-zero and sign checks already present). No collusion or privileged position is needed — only the ability to feed bytes to `read_G`, which the threat model explicitly allows.

### Recommendation
Replace the tautological check with a real subgroup-membership test, e.g. multiply by the scalar-field modulus (prime subgroup order) and require identity:

```rust
fn is_torsion_free(&self) -> Choice {
  (*self * Scalar::MODULUS-order).is_identity() // [l]P == 0
}
```

or clear the cofactor and compare encodings. Add a regression test deserializing known order-2/order-4 Ed448 points through `Ed448::read_G` and asserting rejection.

### Proof of Concept
```rust
use group::GroupEncoding;
use ed448::Point;

// Construct an order-4 point P_t (e.g. via multiply-by-cofactor inverse of a
// known torsion basis, or lift y for a torsion x), then encode it.
let torsion_bytes = /* 57-byte canonical encoding of an order-4 point */;

// This should fail (non-prime-order) but succeeds because
// is_torsion_free() computes -P + P == identity for all P.
let p = Option::<Point>::from(Point::from_bytes(&torsion_bytes));
assert!(p.is_some()); // BUG: torsion point accepted
assert!(!p.unwrap().is_identity());
```

Concretely, feeding that encoding as a FROST `Participant`'s preprocess nonce commitment or inside a `SchnorrSignature::<Ed448>` via `read` passes deserialization and reaches `verify`/`verify_share`, where the prime-order assumption of `batch_statements` (`R + cA − sG == 0`) is violated.

```rust
  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
```
