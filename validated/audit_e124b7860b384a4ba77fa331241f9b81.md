### Title
PedPoP `EncryptedMessage` is not bound to its intended recipient, enabling misdirected-blame framing of honest DKG participants - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Mirroring CVE-2020-24359 (a credential validated against a subnet instead of the specific host), PedPoP's per-message proof-of-possession authenticates an encrypted secret share to the *sender and context* but never to the *recipient*. `blame_internal` / `Decryption::decrypt_with_proof` will accept any well-formed `EncryptedMessage` attributed to an honest sender together with a caller-supplied `recipient`, compute the ECDH key against that claimed recipient's registered encryption key, and — because the plaintext is then garbage — deterministically return the *sender* as the faulty party.

### Finding Description
`encrypt()` produces the PoP via `pop_challenge(context, nonce, key, sender, msg)` — the recipient participant (or the recipient encryption key used for the ECDH) is absent from the transcript. [1](#0-0) 

The cipher likewise only mixes `context` and the ECDH output, so nothing in the ciphertext commits to who it was encrypted for. [2](#0-1) 

On the blame path, `decrypt_with_proof` verifies the PoP with `from` = the accused sender (valid, since sender/msg are bound) and then verifies the accuser's `EncryptionKeyProof` DLEq against `self.enc_keys[&decryptor]` — the *claimed* recipient's key: [3](#0-2) 

`blame_internal` then blames the sender if the decrypted bytes are a non-canonical scalar or fail share verification: [4](#0-3) 

Because the claimed `recipient` is attacker-controlled and unbound, an accuser can take a ciphertext honestly produced by sender Alice *for a different recipient* (Bob), generate a perfectly valid `EncryptionKeyProof` using their own `enc_key` (they know its discrete log, so the DLEq over `[generator, msg.key]` → `[enc_C, msg.key * enc_C]` verifies), and obtain garbage plaintext. `blame_internal` then returns `sender`, framing Alice.

### Impact Explanation
PedPoP's entire purpose is attributable fault: `PedPoPError::InvalidShare { blame }` is propagated as a fatal slash of the accused participant in the coordinator. An honest dealer/sender can be convicted of distributing an invalid share for a message that was never addressed to the accuser, using a proof the verifier accepts as correctly formed. The result is a false-positive blame verdict — effectively a forged accusation that passes all cryptographic checks. `AdditionalBlameMachine::new` explicitly allows evaluation "regardless of if the caller was a member in the DKG protocol," widening who can trigger this. [5](#0-4) 

### Likelihood Explanation
Exploitation requires the attacker to (a) obtain an `EncryptedMessage` honestly sent by the victim sender to *some* participant (in deployments where shares are published/logged for blame adjudication this is public data), and (b) be able to submit a blame statement naming themselves (or any controlled index) as recipient — which `BlameMachine::blame`/`AdditionalBlameMachine::blame` expose publicly. No discrete logs, collusion, or malformed encodings are needed; the ECDH key and DLEq proof are trivially computable by the accuser for their own encryption key. A limitation: blame resolution only burns the sender when the plaintext fails `from_repr` or share verification, which is the guaranteed outcome for a wrong-recipient ciphertext.

### Recommendation
Bind the intended recipient into the ciphertext's authentication. Concretely, extend `pop_challenge` (crypto/dkg/pedpop/src/encryption.rs) to append the recipient's `Participant` index and/or registered encryption public key (e.g., `transcript.append_message(b"recipient", to.to_bytes())` / `enc_pub_key.to_bytes()`), threading `to` through `encrypt()` and `decrypt()`/`decrypt_with_proof()`. This makes the PoP — and thus the message — non-replayable across recipients, so a wrong-recipient ciphertext fails `DecryptionError::InvalidSignature` and correctly attributes fault.

### Proof of Concept
Setup: participants Alice (1), Bob (2), Carol (3) complete commitment/encryption-key registration. Alice sends `msg_AB = encrypt(context, Alice, enc_pub_Bob, share_AB)` to Bob.

Attack (Carol, or any holder of `msg_AB`):

```rust
// Carol knows her own enc_key_C, so she computes the "decryption key" for msg_AB
// under her key and proves it honestly.
let key_C = msg_AB.key * enc_key_C;                    // ECDH w/ Carol's key
let forged_proof = EncryptionKeyProof {
    key: key_C,
    dleq: DLEqProof::prove(rng, &mut encryption_key_transcript(context),
                           &[G::generator(), msg_AB.key], &enc_key_C),
};

// Blame evaluation claims Carol was the intended recipient:
// 1) msg_AB.pop.verify(key, pop_challenge(context, R, key, Alice, msg)) -> PASSES
//    (recipient is absent from the challenge)
// 2) dleq.verify(..., [G, msg.key], [enc_keys[Carol], key_C])            -> PASSES
// 3) cipher decrypts share bytes under key_C -> garbage
// 4) from_repr fails or share verification vs commitments[Alice] at index Carol fails
// 5) blame_internal returns `Alice` — the honest sender is fatally blamed.
let faulty = additional_blame_machine.blame(Alice, Carol, msg_AB, Some(forged_proof));
assert_eq!(faulty, Alice); // wrong: Alice never sent Carol an invalid share
```

Root cause: `pop_challenge` at crypto/dkg/pedpop/src/encryption.rs:302-324 omits the recipient identity, and `decrypt_with_proof` at lines 374-393 accepts a caller-chosen `decryptor` index, so a sender-bound credential is accepted for the wrong recipient — the same over-broad validation class as vault-ssh-helper accepting a subnet OTP for a specific host.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
