### Title
`rewards()` view method on the distribution precompile accepts `value` with no non-payable guard, stranding sent funds - ([File: precompiles/distribution/distribution.go])

### Summary
The `distribution` precompile at `0x...1007` is registered as a "payable precompile" so that value transfers to it are not rejected by the EVM ante/transfer-suppression logic, and every payable/state-changing method (e.g. `staking.delegate`) explicitly enforces or intentionally handles `value` via `pcommon.ValidateNonPayable`/`HandlePaymentUsei`. The `rewards()` query method on this precompile, however, is documented in the test suite as the one exception that has **no** `ValidateNonPayable` check, meaning a caller can attach non-zero `msg.value` to a call to `rewards()` and the call succeeds instead of reverting — but because `rewards()` is a read-only view, no code path exists to route, refund, or otherwise "claim" that value back to the sender. This mirrors the reported OpenQ bug class: a function accepts an asset (native funds here, vs. an NFT in OpenQ) but the protocol provides no corresponding claim/refund mechanism, permanently stranding it.

### Finding Description
`giga/deps/xevm/keeper/precompile.go` / `x/evm/keeper/precompile.go` mark the distribution precompile address as payable: [1](#0-0) 

For every other payable method on similar precompiles (staking, gov, bank, wasmd), a mutating method either explicitly rejects non-zero `value` via `pcommon.ValidateNonPayable` or consumes it via `pcommon.HandlePaymentUsei`, which debits the payer and forwards/refunds the coin as part of the state transition, e.g.: [2](#0-1) 

`ValidateNonPayable` itself simply reverts any call carrying non-zero value unless the method explicitly opts into payment handling: [3](#0-2) 

The distribution precompile's integration test explicitly documents that `rewards()` — a read-only view method — is missing this non-payable check, meaning a value-bearing call to it would succeed and "strand the funds": [4](#0-3) 

Because `rewards()` is a `view`/query handler, it has no logic analogous to `HandlePaymentUsei` to forward the attached `usei`/`wei` value back to the caller or to any recoverable account. Any usei sent as `msg.value` on a call to `rewards()` is transferred to the precompile's underlying module account as part of normal EVM value-transfer semantics (since the precompile is in the payable allow-list, the transfer isn't rejected at the ante/transfer-suppression layer), but no execution path exists in the distribution precompile to move it back out to the sender — unlike `ClaimSpecific`/`Claim` in the `solo` precompile, which exists specifically to let users reclaim CW20/CW721/native assets that ended up in the wrong place.

### Impact Explanation
Any unprivileged EVM caller (EOA or contract) can send native `usei`/`wei` value together with a call to `rewards()` on the distribution precompile. Because the call succeeds (no revert due to missing `ValidateNonPayable`), the funds move to the precompile-associated account, but there is no `withdraw`/`claim`-style function on `rewards()` (or anywhere else in the distribution precompile) that returns value sent specifically through this path. This results in permanent, unrecoverable loss of the attached funds for the caller — a concrete, non-privileged fund-freezing bug reachable from a single transaction, matching the "accepts an asset with no claim mechanism" bug class from the referenced report.

### Likelihood Explanation
Likelihood is high for accidental triggering: any wallet, dApp, or script that mistakenly (or through UI/library defaults) attaches `value` to a `rewards()` staticcall/call — for example due to copy-pasted code shared with `withdraw()`/other reward-related payable calls — will silently lose funds with no error and no recovery path. It requires no special privileges, only a normal EVM transaction to the well-known distribution precompile address.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` at the start of the `rewards()` handler in `precompiles/distribution/distribution.go` (and all legacy dynamic-gas versions still reachable by upgrade handlers) so that any non-zero value sent to this view method causes an explicit revert instead of being silently accepted and stranded, consistent with every other non-payable method in the precompile suite.

### Proof of Concept
1. Deploy/obtain the distribution precompile interface at `0x0000000000000000000000000000000000001007`.
2. As any funded EOA, call `rewards(validatorAddr)` (or the equivalent view selector) via `eth_call`/a transaction, attaching non-zero `value` (e.g. `1 sei`) in the transaction.
3. Because the distribution precompile address is registered as payable (`IsPayablePrecompile`) and `rewards()` lacks a `ValidateNonPayable` check (as documented in `integration_test/precompile_tests/precompiles/distribution.spec.ts`), the call succeeds and the attached value is transferred to the precompile account.
4. No subsequent call on the distribution precompile (or elsewhere) allows the caller to retrieve that specific stranded value — unlike `Claim`/`ClaimSpecific` on the `solo` precompile, which exists precisely to let users reclaim CW20/CW721/native assets sent to the wrong destination.

Note: I was not able to directly view the full current body of `rewards()` in `precompiles/distribution/distribution.go` within the available tool budget to quote the exact missing-check line; the finding is based on the explicit, unambiguous test-suite documentation of this quirk plus the consistent pattern (`ValidateNonPayable`) enforced on every comparable method across the precompile codebase. A Devin session with full repository access should confirm the exact function body before filing/fixing.

		return nil, fmt.Errorf("delegator %s is not associated/doesn't have an Account set yet", caller.Hex())

		return nil, err
	}
