### Title
Unchecked ERC20 boolean return value in the ERC20→CW20 pointer contract allows silent transfer failures - (File: `example/cosmwasm/cw20/src/contract.rs`, embedded as system pointer artifact in `x/evm/artifacts/cw20/artifacts.go`)

### Summary
The CosmWasm CW20-pointer contract that wraps an arbitrary EVM ERC20 token (instantiated by the pointer factory so any CosmWasm user can create/use a CW20 view of an ERC20 token) relays `transfer`/`transfer_from`/`send` calls to the underlying ERC20 contract via an `EvmMsg::DelegateCallEvm` message, but never inspects the ABI-encoded `bool` return value of the ERC20 `transfer`/`transferFrom` call. Non-standard ERC20 tokens that return `false` instead of reverting on failure (the classic ZRX-style pattern cited in the source report) will cause the CW20 pointer to report a successful transfer even though no tokens moved.

### Finding Description
`transfer` and `transfer_from` in the pointer contract build an ABI payload via `querier.erc20_transfer_payload` / `erc20_transfer_from_payload` and dispatch it as a plain `CosmosMsg::Custom(EvmMsg::DelegateCallEvm)`: [1](#0-0) [2](#0-1) 

This message is handled on the EVM keeper side by `HandleInternalEVMDelegateCall` → `CallEVM`. The keeper only fails the Cosmos message if the EVM execution itself reverts (`res.Err != nil`); it never decodes/validates the ABI-encoded boolean returned by the ERC20 `transfer`/`transferFrom` function: [3](#0-2) 

Because the CW20 wasm message that carries `EvmMsg::DelegateCallEvm` is dispatched as a regular `CosmosMsg` (not a `SubMsg` with `reply_on`), the CW20 contract has no mechanism to read back the raw `bytes` result (`res.ReturnData`, i.e. the encoded `bool`) and therefore cannot detect a `transfer`/`transferFrom` call that returns `false` without reverting. The wasm tx is marked successful as long as the EVM call does not revert, matching exactly the "return boolean from transfer/transferFrom instead of reverting" bug class from the source report.

### Impact Explanation
Any downstream CosmWasm contract or user that treats a successful `MsgExecuteContract{transfer/transfer_from/send}` against this pointer as proof that the underlying ERC20 balance moved can be misled: escrow, marketplace, or DEX-style CosmWasm contracts relying on the pointer's "successful" response to release counter-value (e.g., release another asset, mark an order filled, credit an account) would do so without the ERC20 leg actually settling, when the wrapped ERC20 is a non-standard token that signals failure via `false` return rather than revert. This is the same fund-loss vector as the referenced Cooler.sol report — silent transfer failure being treated as success by the calling contract.

### Likelihood Explanation
Likelihood depends on a pointer being created for a non-compliant ERC20 (returns `false` on failed transfer/transferFrom instead of reverting). Pointer creation for arbitrary ERC20 tokens is a normal, unprivileged user operation, and such non-reverting ERC20 tokens exist in practice (ZRX being the canonical historical example). Any wasm/CosmWasm integrator building on top of the pointer (marketplaces, swaps, lending) that trusts the pointer's success status is exposed.

### Recommendation
- Decode the returned ABI-encoded `bool` from the `DelegateCallEvm` result in the CW20 pointer contract and treat a `false` result the same as a Cosmos-level error (abort/propagate `ContractError`), e.g. by using `SubMsg` with `reply_on: Success` and validating the payload in `reply`, or by having `HandleInternalEVMDelegateCall`/`CallEVM` decode known ERC20 selectors (`transfer`, `transferFrom`) and fail the message if the ABI-decoded bool is `false`.
- Document/flag pointer creation for ERC20 tokens with non-standard, non-reverting semantics, or add a "safe-transfer" style check at the pointer boundary similar to OpenZeppelin's `SafeERC20`.

### Proof of Concept
1. Deploy (or use) a non-standard ERC20 token contract whose `transfer`/`transferFrom` returns `false` on failure instead of reverting (functionally equivalent to ZRX).
2. Create a CW20 pointer for this ERC20 token via the standard pointer-creation flow (any unprivileged user action).
3. From a CosmWasm contract or CLI, call `transfer_from`/`transfer`/`send` on the CW20 pointer with parameters that make the underlying ERC20 return `false` (e.g., insufficient allowance/balance edge condition specific to the non-standard token's failure handling).
4. Observe: the wasm `MsgExecuteContract` succeeds (no revert propagated by `CallEVM`, since the EVM call itself did not revert, only returned `false`), while `balanceOf` on the underlying ERC20 shows no balance change — demonstrating the silent-failure/loss-of-funds condition for any caller that assumed success implied a real transfer.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
