### Untrusted `ThresholdKeys` metadata causes speculative allocation - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` trusts the serialized participant count `n` before validating it or confirming the corresponding data is present. When the interpolation byte selects `Interpolation::Constant`, it immediately allocates a vector with capacity `n` and then attempts to read `n` scalars. A truncated input can therefore trigger a multi-megabyte allocation with only a few bytes supplied. Repeated or concurrent calls expose a remote denial-of-service vector.

### Finding Description

The parser reads `t`, `n`, and `i` directly from attacker-controlled bytes. `n` is a 16-bit field, permitting values up to `65,535`. If the next byte is `0`, the code executes `Vec::with_capacity(usize::from(n))` before checking `ThresholdParams` or checking that the stream actually contains the implied scalar encodings [1](#0-0) .

This mirrors the uncontrolled allocation pattern in the reference issue: a small, malformed serialized object specifies a large internal count and causes allocation based on metadata rather than validated input length.

### Impact Explanation

Each malicious input can allocate approximately `n * size_of::<C::F>()` before failing while reading the missing scalars. At the maximum encoded `n`, this is roughly 2 MiB for a 32-byte scalar representation. An unprivileged caller able to submit `ThresholdKeys::read` input can repeatedly invoke the path to consume allocator bandwidth and transient memory, potentially aborting processes configured with restrictive memory limits.

The impact is resource exhaustion only; the bytes still fail parsing afterward, and no signature or key-recovery impact was established.

### Likelihood Explanation

The malicious prefix is only a few bytes: the curve ID header, `t`, `n = 0xffff`, participant index, and interpolation byte `0`. No valid points or scalars are required because allocation occurs before those reads.

Reachability depends on an application exposing `ThresholdKeys::read` to untrusted serialized data. The function is public and is one of the designated deserialization surfaces.

### Recommendation

Validate `t`, `n`, and `i` with `ThresholdParams::new` before allocating or deserializing dependent collections. For `Interpolation::Constant`, also reject coefficient counts inconsistent with the serialized format or protocol bound. Prefer incremental parsing without preallocating attacker-controlled capacity, or enforce a small explicit maximum before `Vec::with_capacity`.


Because the allocation precedes `read_F`, the stream can end immediately after the interpolation byte and still trigger the reservation [2](#0-1) .
