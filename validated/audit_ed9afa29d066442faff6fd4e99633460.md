### Title
Coarse `(filePath, category)` dedup key lets a genuinely new dangerous finding be silently suppressed in commit-review and push-sweep - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_commit_review_posttooluse` and `handle_push_sweep_posttooluse` both call `_dedup_against_state`, which suppresses any LLM-reported vulnerability whose key already exists in `previous_findings`. That key is `(filePath, category)` only — not the vulnerable code, line, or diff hunk — so a second, unrelated dangerous change in the same file and same vulnerability category is treated as "already known" and never surfaces a warning or `asyncRewake`. This is reachable purely through a normal edit → commit → push workflow with no elevated privilege.

### Finding Description
When a commit is reviewed, findings are recorded into `state["previous_findings"]` keyed only on `(filePath, category)`, explicitly to work around vulnerable-code-byte drift across diff context lines: [1](#0-0) . `_dedup_against_state` then drops any newly-flagged vulnerability whose `(filePath, category)` is already in that recorded set (used identically in both the commit-review and push-sweep paths): [2](#0-1)  and [3](#0-2) .

Exploit flow via `handle_push_sweep_posttooluse` (`PostToolUse` on `git push`, entered from `main()`'s Bash routing at [4](#0-3) ):
1. Attacker (any ordinary contributor with normal commit/push rights, no admin needed) commits a first dangerous change to `foo.py`, e.g. a hardcoded secret. It gets flagged, reported, and its `(filePath="foo.py", category="Hardcoded Secret")` key is recorded into `previous_findings` by the commit-review or push-sweep handler.
2. In a later, unrelated commit, the attacker introduces a *second, semantically different* hardcoded secret (or any other genuinely new instance of the same category) elsewhere in `foo.py` and pushes.
3. `handle_push_sweep_posttooluse` diffs the new range, the LLM re-flags this new instance as a distinct vulnerability, but `_dedup_against_state` sees the same `(filePath, category)` key already present in `previous_findings` and silently drops it — no warning text, no `asyncRewake`, no metrics visibility beyond a `deduped` counter: [5](#0-4) .
4. Additionally, the entire pushed range is unconditionally marked reviewed in `.git/sg-reviewed-shas` regardless of suppression, via `_append_reviewed_shas(repo_root, tail, ...)` executed before dedup is even applied: [6](#0-5) . Because push-sweep advances its diff base past any sha in the reviewed set (`_compute_push_sweep_base`), [7](#0-6) , that code region is permanently excluded from future sweep diffs even though the second vulnerability was never actually surfaced to the user.

No existing check mitigates this: the rate limiter (`atomic_check_rate_limit`) and range-size caps only limit LLM call frequency/size, not per-finding correctness, and the dedup logic itself is what causes the suppression — it is working as coded, not failing due to a bug in an unrelated guard.

### Impact Explanation
This breaks the stated invariant that dangerous edits/commands must remain reviewable and blockable across retries, amends, and pushes. A real, distinct vulnerability (e.g., a second hardcoded token, a second command-injection sink) introduced later in the same file under the same category is never reported by commit-review or push-sweep, and the commit range is marked reviewed so it won't be caught by a later sweep either. This can result in sensitive code/token/secret disclosure reaching a remote sink (e.g., pushed to a shared or public remote) without the security-guidance plugin ever emitting a warning, matching the "Sensitive code, prompt, token, diff, or local file disclosure" impact category.

### Likelihood Explanation
High feasibility and fully within normal, unprivileged repository usage: any contributor doing ordinary sequential commits/pushes to the same file can trigger it without any special setup, git trickery, or exploiting a parsing bug — it is a direct consequence of the dedup key's granularity choice. It is deterministic and repeatable given two same-category findings in the same file across two pushes.

### Recommendation
Tighten the dedup key beyond `(filePath, category)` to include a stable-but-drift-tolerant fingerprint of the finding location, e.g. `(filePath, category, normalized_line_range)` or a hash of the surrounding function/symbol name rather than raw vulnerable-code bytes. Alternatively, only suppress a re-flagged `(filePath, category)` finding when the LLM confirms it is the *same* finding location as a previous one (e.g., via overlapping line ranges) rather than merely matching file+category, and avoid marking `tail` shas as reviewed in `_append_reviewed_shas` until the corresponding findings have been either reported or deliberately recorded as suppressed-but-known.

### Proof of Concept
Integration test plan (extending existing push-sweep dedup tests, if present, or added to `security_reminder_hook` test suite):
1. Initialize a git repo; make commit A adding `SECRET_1 = "abcd1234..."` to `app.py`; run `handle_commit_review_posttooluse` (or push it) and assert a warning/`asyncRewake` is emitted and `previous_findings` now contains `{"filePath": "app.py", "category": "Hardcoded Secret"}`.
2. Make commit B adding a second, different hardcoded secret `SECRET_2 = "zzzz9999..."` in a distinct function of `app.py`; push (`git push`), triggering `handle_push_sweep_posttooluse`.
3. Assert: the LLM/vuln-analysis stage would flag `SECRET_2` as a new vulnerability (mock/stub `_agentic_review_with_race` or `analyze_code_security` to return this finding), but `_dedup_against_state` drops it because `(filePath, category)` already matches `previous_findings` — assert `new_vulns` is empty, `sys.exit(0)` is reached (no `sys.exit(2)`, no stderr guidance written), and `deduped == 1` in emitted metrics.
4. Assert `.git/sg-reviewed-shas` now includes commit B's sha (via `_load_reviewed_shas`), proving the range is permanently excluded from future sweeps despite `SECRET_2` never being reported to the user — demonstrating the disclosure-without-warning condition.

```python
def _compute_push_sweep_base(prev_upstream, push_range, reviewed):
    """Advance the diff base past the contiguous reviewed prefix.

    Spec: review `git diff B..HEAD` where `B` is the newest commit such that
    `prev_upstream..B` is entirely in `reviewed`. Returns (B, unreviewed_tail).
    `B == None` means the whole range is reviewed (caller should skip).
    `push_range` must be oldest→newest.

    Examples (✓=reviewed, ✗=not):
      [✓1, ✗2, ✓3]  → B=1, tail=[2,3]   (cannot trim suffix; Read is at HEAD)
      [✓1, ✓2, ✓3]  → B=None            (all reviewed → skip)
      [✗1, ✓2, ✗3]  → B=prev_upstream, tail=[1,2,3]
      []            → B=None
    """
    i = 0
    while i < len(push_range) and push_range[i] in reviewed:
        i += 1
    if i == len(push_range):
        return None, []
    base = push_range[i - 1] if i > 0 else prev_upstream
    return base, push_range[i:]
```
