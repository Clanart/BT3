### Title
`resolveWithin` containment check uses `startsWith` without a path-separator boundary, allowing sibling-directory escape - ([File: app/src/lib/path.ts])

### Summary
`_resolveWithin()` in `app/src/lib/path.ts` is the shared "stay inside the repo" guard used to validate paths (including symlink targets) derived from attacker-influenced sources such as merge-conflict file paths read out of a cloned/fetched repository. Its final containment test is `realResolved.startsWith(realRoot)`, which — exactly like the Yieldoor `isLowerSided` bug — is an inexact boundary comparison: it treats any path whose string prefix matches the root as "inside" the root, even when the actual next path component is a *different, sibling* directory (e.g. root `…/myrepo` vs. resolved `…/myrepo-secret/…`).

### Finding Description
`_resolveWithin` resolves symlinks via `realpath` and then performs the containment check: [1](#0-0) 

The comparison `realResolved.startsWith(realRoot)` is a pure string-prefix test with no trailing separator appended to `realRoot`. This means a resolved path like `/Users/victim/Documents/GitHub/myrepo-exfil/secret.txt` will pass the check against root `/Users/victim/Documents/GitHub/myrepo`, because the string `"…/myrepo-exfil/secret.txt"` legitimately starts with `"…/myrepo"` even though `myrepo-exfil` is a completely different, sibling directory — not a subdirectory of `myrepo`. This is the exact same bug class as the Sherlock report: a boundary/inequality check (`modulo < tickSpacing/2` vs. the correct `<=`) that doesn't treat the true boundary condition correctly, here missing the required directory-separator delimiter that distinguishes "is a subpath of root" from "merely shares a string prefix with root."

The codebase elsewhere demonstrates the *correct* pattern for this exact kind of check, confirming this is an inconsistency/regression rather than an intentional design: `isClonePathSensitive()` in `app/src/lib/git/clone.ts` explicitly appends `Path.sep` before calling `startsWith`: [2](#0-1) 

`resolveWithin` is consumed by `buildConflictContext()` specifically as an anti-symlink-escape guard for conflicted file paths coming from a real Git working tree (populated by clone/fetch/merge — fully attacker-influenced content): [3](#0-2) 

If an attacker-controlled repository contains a symlink (as one of the "conflicted" paths reported by Git, or as a path component leading to one) whose real target lands in a sibling directory that happens to share the root directory's name as a prefix (e.g. cloning `myrepo` next to a pre-existing `myrepo-old`, `myrepo (1)`, `myrepo.bak`, or any user directory naming pattern with a common prefix), `realpath()` will resolve to that sibling location and the flawed `startsWith` check will treat it as "inside" the repository. The function then returns the resolved absolute path as safe, and `buildConflictContext` proceeds to `stat()` and `readFile()` that path and includes its contents (`rawContent`) in the prompt sent to the Copilot conflict-resolution service.

### Impact Explanation
This turns a defense-in-depth "path traversal / symlink escape" guard into a bypassable check: file content located outside the repository's working directory (but in a sibling directory string-prefixed by the same name) can be read and silently transmitted off-box to the Copilot API as part of conflict-resolution context — an unauthorized read of, and exfiltration of, data outside the intended repository boundary, driven entirely by attacker-supplied repository content (a crafted symlink committed to a repo that gets cloned/fetched/merged). This matches the "file read outside the repo" / "credential exfiltration" impact class in scope.

### Likelihood Explanation
Exploitability depends on a sibling directory with a matching name-prefix existing next to the cloned repository (common in real-world workflows: re-clones like `repo (1)`, `repo-old`, `repo.bak`, forks cloned side-by-side, or nested project folders that share a prefix). This is a realistic but not universal precondition, so likelihood is moderate rather than guaranteed on every checkout — however, no user interaction beyond opening a merge/rebase/cherry-pick with a conflicted, attacker-crafted symlink path is required, and no admin/local-access/malware precondition is needed, satisfying the in-scope attacker model (attacker controls a cloned/fetched repository).

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a match followed by the platform path separator, mirroring the pattern already used in `isClonePathSensitive`:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
using the separator appropriate to the `options` (`Path.sep`/`Path.win32.sep`/`Path.posix.sep`) passed into `_resolveWithin`.

### Proof of Concept
1. Root: `/Users/victim/Documents/GitHub/myrepo` (a real cloned repository).
2. Attacker's malicious commit, when merged/rebased, produces a conflicted file whose path (after Git checks it out) is a symlink resolving (via `realpath`) to `/Users/victim/Documents/GitHub/myrepo-secrets/config.json` — a sibling directory that happens to exist on the victim's machine (e.g., an old backup clone, another project, or a directory an attacker can predict from a public dotfiles repo naming convention).
3. `buildConflictContext()` calls `resolveWithin(workingDirectory, file.path)`: [4](#0-3) 
4. Inside `_resolveWithin`, `realResolved = "/Users/victim/Documents/GitHub/myrepo-secrets/config.json"` and `realRoot = "/Users/victim/Documents/GitHub/myrepo"`. `realResolved.startsWith(realRoot)` evaluates `true` because the string literally starts with `"…/myrepo"`, even though `myrepo-secrets` is not a subdirectory of `myrepo`: [5](#0-4) 
5. The check incorrectly returns the resolved path instead of `null`; `buildConflictContext` proceeds to `stat`/`readFile` the out-of-repo file and includes its content as `rawContent` sent to the Copilot API.

Note: existing unit tests in `app/test/unit/path-test.ts` only exercise `..`-style traversal and symlink-out-and-back scenarios — none test the sibling-prefix ("`root-evil`") case, so this gap is not currently caught by test coverage. [6](#0-5)

      assert((await resolveWithin(root, join('..'))) === null)

    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {

    })
