### Title
Untrusted `n` length in `ThresholdKeys::read` triggers unbounded pre-allocation and deserialization loop — Denial of Service - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg` deserializes an attacker-controlled `n` (`u16`) and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector, then loops `n` times reading scalars and group elements, before any bound check ties `n` to the actual message length or to sane threshold parameters. This is the same bug class as CVE-2025-61910: a small, unauthenticated input declares a large count/length which is trusted for memory allocation and work, enabling an unprivileged remote party to drive repeated large allocations and allocation churn to degrade or crash the host.

### Finding Description
The relevant code path is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs` (around lines 591–623):

```rust
let (t, n, i) = { /* three u16s read directly from the reader */ };
...
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
...
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
ThresholdKeys::new(ThresholdParams::new(t, n, i)... , ...)
```

Root cause details:

- `n` is a raw `u16` taken straight from untrusted bytes. `Vec::with_capacity(usize::from(n))` is executed **unconditionally** for the `Constant` interpolation variant (interpolation tag byte = `0`), before a single byte of coefficient data is required. A ~10-byte input therefore forces an allocation of `n * size_of::<C::F>()` — up to ~2 MB for 32-byte fields (Secp256k1, Ristretto, ed25519) and ~3.7 MB for ed448's 56-byte field — an amplification of roughly 10⁵× per call.
- Validation (`ThresholdParams::new(t, n, i)` and `ThresholdKeys::new`) happens only **after** the allocation and the two `n`-bounded deserialization loops, so it cannot bound the resource consumption.
- `ThresholdKeys::read` is explicitly on the reachable-input surface (it is one of the listed `read` APIs); serialized `ThresholdKeys` blobs are consumed when loading multisig keys / signing-setup material derived from network data. Any component that feeds externally influenced bytes into this function — or into `Plan::read`-style length-prefixed readers with the same shape (`u32` counts driving loops in `processor/src/plan.rs`, tributary `SignData::read`) — is exposed. Unlike the coordinator's `RrCodec` (which caps at `MAX_LIBP2P_REQRES_MESSAGE_SIZE`) or `DkgCommitments` (which checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT`), `ThresholdKeys::read` performs no size-limit check before allocating.

Uncertain aspects I could not fully verify within the iteration budget: whether a specific in-scope caller pipes fully attacker-controlled bytes into `ThresholdKeys::read` (as opposed to locally persisted data), and whether `dealer`/`pedpop` `ReadWrite` implementations contain similar unbounded `u16`/`u32`-driven allocations (grep hits existed but contents weren't read). The `with_capacity` issue stands on its own in the listed API surface.

### Impact Explanation
An unprivileged party who can cause the node/signer to parse crafted bytes reaches memory-exhaustion and CPU-exhaustion DoS:

- Each invocation allocates up to ~2–3.7 MB for a handful of input bytes; concurrent or repeated parses exhaust memory or trigger the OOM killer / abort on allocation failure (Rust aborts on `Vec::with_capacity` failure rather than returning an error, so the process terminates rather than gracefully rejecting the input).
- Even when the subsequent `read_F`/`read_G` calls fail early (input too short), the allocation and any completed `HashMap` inserts are pure wasted work, giving a sustained amplification vector that can stall the signing/verification thread — mirroring the advisory's "receiver thread termination → DoS" outcome.

### Likelihood Explanation
Medium. The path requires only delivering malformed bytes to a `read` entry point — no key material, no validator status, no collusion. The amplification per call is bounded by `u16::MAX` (~2–3.7 MB), so a single message is recoverable; the DoS requires repetition or concurrency. Severity is Medium rather than High because the allocation is transient and capped per call, unlike the unbounded single-shot 4 GB allocation in the original CVE.

### Recommendation
- Defer `Vec::with_capacity(n)` until `ThresholdParams::new(t, n, i)` has succeeded, or cap `n` at the crate's maximum participant bound before allocating.
- Better: remove eager allocation entirely and grow the vector as elements are actually read, matching the chunked-read pattern already used in `networks/ethereum/src/machine.rs` for `data_len`.
- Audit sibling readers (`Plan::read`, `SignData::read`, `Scheduler::read`, `InInstruction::read`) that allocate `vec![0; u32]` or loop over attacker `u32` counts without checking against a byte limit, and add a uniform per-message size budget.

### Proof of Concept
```rust
use ciphersuite::Secp256k1;
use dkg::ThresholdKeys;
use std::io::Cursor;

// Minimal hostile payload:
//   [C::ID len (u32 LE)] [C::ID bytes] [t u16] [n = 0xFFFF u16] [i u16] [interpolation = 0]
// `ThresholdKeys::read` will execute Vec::with_capacity(65535) for C::F (~2 MB)
// after consuming only ~10 bytes past the curve-ID check.
fn poc() {
    let mut bytes = vec![];
    bytes.extend((Secp256k1::ID.len() as u32).to_le_bytes());
    bytes.extend(Secp256k1::ID);
    bytes.extend(1u16.to_le_bytes());      // t
    bytes.extend(u16::MAX.to_le_bytes());  // n = 65535
    bytes.extend(1u16.to_le_bytes());      // i
    bytes.push(0);                         // Interpolation::Constant -> with_capacity(65535)

    // Each call: ~2 MB alloc. Loop this concurrently from attacker-controlled input
    // to exhaust memory; allocation failure aborts the process (OOM kill / alloc error).
    loop {
        let mut c = Cursor::new(bytes.clone());
        let _ = ThresholdKeys::<Secp256k1>::read(&mut c);
    }
}
