### Title
First-locker-after-forfeit reward-hijack via zero-`totalStaked()` accrual window - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
Both `_queueNewRewardsWithoutTransfer` and `queueNewRewards` accumulate rewards into `queuedRewards` whenever `totalStaked()` (i.e. `vlMGP.totalSupply()`) is zero, and only convert `queuedRewards` into `rewardPerTokenStored` on the next call where `totalStaked() > 0`, dividing by whatever `totalStaked()` is *at that moment*. If the vlMGP contract's total supply transiently drops to zero (last locker fully exits) while a forfeiture or reward event queues funds, an attacker who becomes the very next locker with a trivially small amount becomes the sole staked balance, and a subsequent `queueNewRewards` call converts the entire accumulated `queuedRewards` pool into `rewardPerTokenStored` based on that tiny total, letting the attacker claim it all via `_earned`.

### Finding Description
`_queueNewRewardsWithoutTransfer` (called from `queueMGP`'s forfeiture path and from `_sendReward`'s forfeiture path) and `queueNewRewards` (the manager-only distribution entrypoint) share identical branching logic: [1](#0-0) 

```
if (totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    if (rewardInfo.queuedRewards > 0) {
        _amountReward += rewardInfo.queuedRewards;
        rewardInfo.queuedRewards = 0;
    }
    rewardInfo.rewardPerTokenStored += (_amountReward * 10**vlMGPDecimal) / totalStaked();
}
```

`totalStaked()` reads `vlMGP.totalSupply()` directly [2](#0-1) , a global value shared by all lockers, not a per-caller value. Because `rewardPerTokenStored` is a single global accumulator and a user's earned amount is `balanceOf(_account) * (rewardPerToken - paid) / 1e18` [3](#0-2) , whoever holds `balanceOf` at the moment `rewardPerTokenStored` jumps captures reward proportional to their *share of total supply at that instant*. If the attacker is the sole holder of vlMGP supply when `queueNewRewards` performs the merge (because they were first to re-lock after the supply hit zero), their share is 100%, regardless of how small their absolute lock amount is.

Exploit flow:
1. Last remaining vlMGP holder fully unlocks/exits, driving `vlMGP.totalSupply()` (and thus `totalStaked()`) to 0.
2. A forfeiture event fires while supply is 0 (e.g., a delayed `queueMGP` or `_sendReward` call for an already-recorded forfeiting balance) and its amount is queued into `rewardInfo.queuedRewards` via `_queueNewRewardsWithoutTransfer`.
3. Attacker locks a minimal amount of MGP (e.g., 1 wei) in `vlMGP`, becoming the sole/first token holder and thus 100% of `totalStaked()`. The attacker's `userRewardPerTokenPaid` is set to the current (stale) `rewardPerTokenStored` at stake time via the `updateReward`/`updateRewards` modifier flow triggered through `masterMagpie`.
4. `rewardManager` calls `queueNewRewards` with a large new reward amount. Since `totalStaked() > 0` now, the branch merges the queued (forfeited) rewards plus the new amount and divides by `totalStaked()`, which equals only the attacker's tiny balance.
5. Attacker calls `getReward`/`getRewards`; `_earned` computes `balanceOf(attacker) * delta / totalStaked-at-mint-time` which resolves to essentially the full merged reward pool because attacker's balance equals the entire supply used in the division.

No modifier, `nonReentrant` guard, or existing accounting logic prevents this — `onlyManager` only restricts who can *call* `queueNewRewards`, it does not protect against the zero-supply/first-staker distortion, and there is no minimum-stake or virtual-shares safeguard.

### Impact Explanation
This is a theft of unclaimed/forfeited yield belonging to prior (or future, once genuine lockers re-enter) legitimate lockers. The forfeited amount and any newly queued reward amount that arrives during the zero-supply window are fully diverted to the attacker's negligible 1-wei stake instead of being distributed pro-rata once genuine total supply is restored — matching the "theft of unclaimed yield" impact class.

### Likelihood Explanation
The attack requires a specific, narrow precondition: `vlMGP.totalSupply()` must transiently reach exactly zero (i.e., no MGP locked anywhere in the system) at the same time queued/forfeited rewards exist, and the attacker must be the very next locker before the manager's `queueNewRewards` call. In an actively used protocol with an existing base of lockers, `totalStaked()` reaching zero is unlikely except immediately after deployment/bootstrap, or in a niche scenario where all lockers simultaneously exit. This significantly limits real-world exploitability compared to a fully generic first-depositor attack, but it is not privileged — it only requires ordinary `lock()` calls and normal reward-manager operation, and capital cost is trivial (1 wei). It is a known class of "empty pool / first staker" reward-accounting flaw applicable whenever the zero-supply window can be reached, and is repeatable each time supply cycles back to zero.

### Recommendation
Do not key the queued/forfeited reward merge purely on `totalStaked() == 0`/`>0` transitions combined with an unprotected instantaneous division. Options: (a) require a minimum bootstrap lock (e.g., burn a small amount to a dead address on first lock, similar to Uniswap V2's `MINIMUM_LIQUIDITY`) so `totalStaked()` can never be trivially small when queued rewards convert; (b) track `queuedRewards` per reward token and only release them proportionally over time (e.g., streaming) rather than a single lump conversion at the next nonzero-supply call; (c) add a minimum total-staked threshold below which new reward merges are deferred rather than converted; (d) snapshot reward eligibility so that `queuedRewards` accumulated before a user's stake cannot be attributed to that user.

### Proof of Concept
Foundry test plan:
1. Deploy `vlMGPBaseRewarder`, `VLMGP`, `MasterMagpie` mocks/wiring as in existing test suite.
2. Have an initial locker A lock MGP, then fully unlock/exit so `vlMGP.totalSupply()` returns 0 (`totalStaked() == 0`).
3. Trigger a forfeiture path while `totalStaked()==0` (e.g., call `queueMGP` with a `_account` whose `getRewardablePercentWAD` yields a forfeit) so `rewards[token].queuedRewards` is populated — assert `queuedRewards > 0` and `rewardPerTokenStored` unchanged.
4. As attacker, call `lock(1)` (1 wei of MGP) via `VLMGP`/`masterMagpie` so `totalStaked() == 1`.
5. As `rewardManager`, call `queueNewRewards(largeAmount, token)`.
6. Assert `rewards[token].rewardPerTokenStored` increased by `(largeAmount + queuedRewardsFromStep3) * 1e18 / 1`.
7. Call `getReward(attacker, attacker)` and assert attacker receives (approximately) `largeAmount + queuedRewardsFromStep3`, vastly exceeding a fair pro-rata share for a 1-wei stake, confirming full capture of the forfeited/new reward pool.

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +

    }
