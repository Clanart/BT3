## Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is permanently captured by the host instead of refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it for the exact fee-token amount needed via `swapETHForExactTokens`. Uniswap V2's `swapETHForExactTokens` refunds any unspent ETH to its caller — which is `EvmHost` itself, not the end user. The host's `receive()` function is explicitly documented to "collect all dust native tokens" from this refund, meaning any ETH sent beyond the exact swap requirement is retained by the contract and never returned to the original payer.

### Finding Description
In the payable dispatch functions: [1](#0-0) [2](#0-1) [3](#0-2) 

Whenever `msg.value > 0`, the host calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. Standard `swapETHForExactTokens` semantics only consume `amounts[0] <= msg.value` and refund `msg.value - amounts[0]` back to `msg.sender` of the router call — which is `EvmHost`, not the caller of `dispatch`/`fundRequest`. That refund lands in the host via: [4](#0-3) 

There is no code path in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` that computes the unspent amount and forwards it back to `_msgSender()`. This is in sharp contrast to other payable entrypoints in the same repo — `IntentGatewayV2.placeOrder`/`fillOrder` and `ExtrinsicIntents` explicitly track `msgValue` and refund any leftover at the end of execution: [5](#0-4) [6](#0-5) 

`EvmHost` has no equivalent refund logic for its own `dispatch`/`fundRequest` payable paths — the swapped-back dust just accumulates as host balance. The only way this ETH can leave the contract is via the governance-gated `withdraw()`: [7](#0-6) 
which is restricted to `_hostParams.hostManager` and sends funds to whatever beneficiary cross-chain governance specifies — not necessarily (and with no on-chain record pointing to) the original overpaying caller.

### Impact Explanation
Any application or user calling `dispatch()`/`fundRequest()` with native ETH exceeding the exact amount needed to cover `post.fee`/`get.fee`/`amount` permanently loses the excess. This matches the "loss of funds" bounty category: the corrupted value is the caller's residual ETH balance, which silently becomes host-owned dust with no path back to the depositor. Given the SDK/docs explicitly promote native-token payment (`payable`, "automatically swapped to fee token via Uniswap") as a first-class payment method, this is a realistic operational path for ordinary app integrators, not an edge case.

### Likelihood Explanation
High. Because Uniswap swap output for a fixed `fee` in fee-token terms is price-dependent and callers typically cannot predict the exact ETH input required at call time, any caller using the native-token payment path who provides a safety margin above the expected swap cost (the same "forgot/inadvertently sent more than needed" pattern as the seed report) will lose the difference on every single call. No malicious actor, relayer, or prover is required — an honest, unprivileged caller triggers the loss by ordinary usage.

### Recommendation
Track native ETH consumption in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` the same way `IntentGatewayV2`/`ExtrinsicIntents` do: capture `address(this).balance` (or the router's return value) before/after the swap, and refund any unspent `msg.value` back to `_msgSender()` at the end of the call, reverting on failed refund transfer.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: X}(post)` where `post.fee` requires only `Y < X` in ETH-equivalent swap input.
2. `swapETHForExactTokens{value: X}(post.fee, ...)` consumes `Y` and refunds `X - Y` to `msg.sender` of the router call, i.e., `EvmHost` itself (received via its `receive()` at `evm/src/core/EvmHost.sol:386`).
3. `dispatch()` returns normally with the commitment; the caller's transaction shows they spent the full `X` ETH from their wallet, but only `Y` worth of value was used for the fee — `X - Y` is now sitting in `EvmHost`'s balance.
4. No function accessible to the caller can reclaim `X - Y`; only cross-chain governance via `withdraw()` can move it, to an arbitrary beneficiary unrelated to the original caller.
