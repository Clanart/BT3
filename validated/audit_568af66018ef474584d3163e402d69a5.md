### Title
Unauthenticated DKG encryption key allows complete threshold-secret recovery by a message tamperer - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
In PedPoP, each participant broadcasts an `EncryptionKeyMessage` containing the round-1 `Commitments` (which are bound by a Schnorr PoK) **plus a separate `enc_key` field that is covered by no signature, PoK, or transcript binding whatsoever**. A party able to tamper with a broadcast commitment message in transit can substitute the victim's `enc_key` with a public key it controls. Every other participant then encrypts that victim's secret share to the attacker's key, while the per-message PoP and share-verification checks all still pass on the sender side. The attacker recovers every participant's secret share — i.e., the full group secret — with only public inputs and message manipulation.

### Finding Description
The analog of "missing authorization check lets a non-member act" is a missing authenticity check on the encryption key registration:

- `EncryptionKeyMessage` is `{ msg: M, enc_key: C::G }`, and `enc_key` is appended verbatim with no proof attached: `crypto/dkg/pedpop/src/encryption.rs` lines 49–59.
- The round-1 PoK challenge `challenge::<C>(context, l, R, Am)` binds only `context`, `l` (sender index), the nonce `R`, and the serialized commitment points `Am` (`cached_msg`): `crypto/dkg/pedpop/src/lib.rs` lines 86–94. `cached_msg` contains only the commitment points (`Commitments::read` extends `cached_msg` solely in `read_G`): lines 110–127. `enc_key` is never hashed into the challenge.
- `verify_r1` verifies `msg.sig` against that challenge and registers `msg.enc_key` into the ECDH key table under participant `l`, without any check that `enc_key` is bound to `l` or to the signed transcript: lines 311–331 (`self.encryption.register(l, msg)` → `Decryption::register` inserts `msg.enc_key`, `encryption.rs` lines 351–362).
- `generate_secret_shares` / `encrypt` then encrypts share `f_sender(l)` with `cipher(context, ecdh(ephemeral_key, enc_key))` (`encryption.rs` lines 135–168, 460–467). The receiver-side PoP (`pop_challenge`) does bind `sender` and `msg` (lines 302–324), so senders produce perfectly valid ciphertexts — they are just encrypted to the wrong recipient key.

So the only thing protecting `enc_key` is the assumed authenticated channel. Unlike the commitment polynomial — which is signed — `enc_key` has no cryptographic binding to its claimed owner.

### Impact Explanation
An attacker who can modify commitment messages in transit (e.g., a relay/coordinator forwarding DKG messages, or any non-member able to inject bytes into the channel) substitutes `enc_key` in each victim's `EncryptionKeyMessage` with `attacker_scalar * G`. All senders then encrypt `f_sender(victim)` under a key whose ECDH shared secret the attacker knows. The attacker computes `ecdh(msg.key, attacker_scalar)` — equivalently `ecdh(attacker_priv, msg.key)` — applies `cipher`, and reads the victim's `SecretShare` plaintext (`encryption.rs` lines 95–133, 487–489).

Doing this for all `n` victims yields every participant's secret share; the Lagrange-combined sum is the group private key — total key share recovery (the strongest listed acceptance criterion). Note the victims themselves fail to decrypt and raise `InvalidShare` blame, so the honest DKG aborts — but the secret has already leaked, and nothing ties the substitution back to cryptographic proof since `enc_key` was never signed.

### Likelihood Explanation
- Reachable with public inputs: the attacker only modifies broadcast `EncryptionKeyMessage` bytes (an allowed input surface — `EncryptionKeyMessage::read` / `Commitments::read` consume untrusted bytes) and reads the resulting `EncryptedMessage`s.
- Constraint: it requires the ability to tamper with, not merely observe, the "authenticated channel." The library documents that message *origin* must be authenticated; the bug is that integrity of `enc_key` is enforced nowhere cryptographically, unlike the commitments. Where the deployment's channel authenticates only origin (or a middlebox/coordinator relays payloads), the attack is practical.
- Severity: secret-key-equivalent recovery of the entire threshold group ⇒ High severity impact; exploitability depends on channel assumptions ⇒ Medium/High overall.

### Recommendation
Bind `enc_key` to the round-1 proof. Concretely: extend the `Commitments` serialization (`cached_msg`) or the `challenge()` transcript to include `enc_key.to_bytes()`, so the Schnorr PoK over `commitments[0]` also authenticates the encryption key — e.g., `transcript.append_message(b"encryption_key", enc_key_bytes)` in `challenge::<C>` at `crypto/dkg/pedpop/src/lib.rs` lines 86–94, and append the `enc_key` bytes in `EncryptionKeyMessage::{read,write}` ordering (`encryption.rs` lines 56–64). Alternatively, add a Schnorr PoP on `enc_key` bound to `context` and `participant`, mirroring `pop_challenge`.

### Proof of Concept
1. Victim `l` broadcasts `EncryptionKeyMessage { msg: Commitments{commitments, cached_msg, sig}, enc_key: enc_l * G }` (`generate_coefficients`, `pedpop/src/lib.rs` lines 156–202).
2. Attacker replaces `enc_key` with `A = a * G`, forwarding `{ commitments…, enc_key: A }`. `verify_r1` accepts: `sig` still verifies (challenge covers only `cached_msg`), and `register(l, msg)` stores `A` as `l`'s key (`lib.rs` lines 313–331; `encryption.rs` lines 356–361).
3. Each honest sender `s` runs `encrypt(rng, l, share)` → `cipher(context, ecdh(k_s, A))` over `share = f_s(l)` (`lib.rs` lines 358–370; `encryption.rs` lines 135–168).
4. Attacker observes `EncryptedMessage{ key: k_s*G, pop, msg }`, computes `shared = msg.key * a`, derives `cipher(context, shared)`, and decrypts `f_s(l)` — a valid `SecretShare` for `l`.
5. Repeat for all participants → attacker holds every `secret_share`; `ThresholdKeys`/Lagrange interpolation over them yields the group secret key, while honest parties abort on `InvalidShare` blame.
