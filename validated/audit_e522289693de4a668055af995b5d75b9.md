### Title
Unauthenticated `ReceivedOutput` offset permits non-spendable outputs to be reported as wallet funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and outpoint without verifying that the output’s Taproot script actually corresponds to the wallet key shifted by that offset. Legitimate outputs are normally created by `Scanner::scan_transaction`, which only attaches an offset after matching `output.script_pubkey` to a script registered for `key + offset * G`. Deserialization bypasses that binding, allowing untrusted serialized bytes to represent an unspendable output as a spendable wallet input. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

The security invariant is analogous to hostname verification: a cryptographic credential or key reference must be bound to the identity it claims to represent. Here, the claimed ownership identity is the scalar `offset`, while the claimed credential is the output’s `script_pubkey`.

`Scanner` establishes that binding by registering `p2tr_script_buf(self.key + GENERATOR * offset)` and by returning a `ReceivedOutput` only when a transaction output’s `script_pubkey` is found in that map. [4](#0-3) [5](#0-4) 

`ReceivedOutput::read`, however, independently deserializes `offset`, `output`, and `outpoint` and returns the aggregate object without checking that the supplied output was generated for `key + offset * G`, or even that the output is P2TR. [2](#0-1) 

`SignableTransaction::new` then consumes these caller-supplied records directly, sums their nominal values, collects their offsets, and places their claimed outpoints in transaction inputs. [6](#0-5) 

### Impact Explanation

An attacker who can supply serialized `ReceivedOutput` bytes can cause an arbitrary valid Bitcoin output and value to be represented as a wallet-controlled input while attaching an incorrect offset. The output may be counted at `ReceivedOutput::value` and selected by `SignableTransaction::new`, but threshold signing with `base_key + offset * G` cannot authorize it unless the script actually commits to that derived key. [7](#0-6) [8](#0-7) 

The practical impact is a funds-accounting and transaction-construction failure: the wallet reports or attempts to spend value that is not spendable under the claimed key/offset relation. This can pollute locally supplied or exchanged input records and construct transactions whose Taproot inputs cannot be validly signed. [8](#0-7) 

### Likelihood Explanation

The malicious input is only bytes passed to `ReceivedOutput::read`; the attacker does not need validator access, a leaked key, malformed curve encodings, or control over blockchain data. The scalar and consensus objects merely have to be well-formed because parsing does not enforce the scanner’s ownership relation. [2](#0-1) 

The issue requires the application to deserialize wallet inputs from an untrusted or transport-level source rather than obtain them directly from `Scanner::scan_transaction`. Where that flow exists, crafting the object is straightforward because all three serialized fields are attacker-controlled. [5](#0-4) 

### Recommendation

Bind deserialized outputs to the expected base wallet key before treating them as spendable. For example, replace or supplement `ReceivedOutput::read` with a constructor such as `ReceivedOutput::read_for_key(reader, key)` which:

1. Reads the claimed scalar offset.
2. Derives `p2tr_script_buf(key + GENERATOR * offset)`.
3. Rejects the record unless it equals `output.script_pubkey`.
4. Confirms that `offset` is a registered offset for that scanner/wallet, where applicable.
5. Rejects non-P2TR scripts and malformed outpoints.

If untrusted deserialization cannot know the base key, `ReceivedOutput::read` should be documented as producing an unauthenticated record and callers should revalidate it through `Scanner` before calling `value`, accounting for it, or passing it to `SignableTransaction::new`. [2](#0-1) [3](#0-2) 

### Proof of Concept

The parser accepts a syntactically valid object whose claimed offset does not correspond to its script:

```rust
// File: networks/bitcoin/src/wallet/mod.rs
// Conceptual PoC

let wallet_key = /* even Taproot base key */;
let wrong_offset = Scalar::ONE;

// Any consensus-valid P2TR output which is *not*
// p2tr_script_buf(wallet_key + GENERATOR * wrong_offset).
let attacker_txout = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: arbitrary_p2tr_script,
};

let outpoint = OutPoint {
    txid: arbitrary_txid,
    vout: 0,
};

let mut bytes = vec![];
bytes.extend(wrong_offset.to_bytes());
bytes.extend(bitcoin::consensus::encode::serialize(&attacker_txout));
bytes.extend(bitcoin::consensus::encode::serialize(&outpoint));

// Accepted: no key/offset/script binding is checked.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The forged object reports the claimed value and is accepted as an input.
assert_eq!(forged.value(), 100_000);
let tx = SignableTransaction::new(
    vec![forged],
    &payments,
    change,
    None,
    fee_per_vbyte,
)?;
```

For a genuine scanner-derived record, `offset` is necessarily selected from `scripts[script_pubkey]`, where the script was generated from `key + offset * G`. The crafted object bypasses that construction and therefore violates the ownership relation without being rejected. [2](#0-1) [3](#0-2)

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
