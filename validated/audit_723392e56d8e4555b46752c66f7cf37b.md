### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/fee calculation, producing transactions that underpay the required fee rate — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external report's bug class is "an optional input is accepted without enforcing the safety/repair parameter, leaving funds frozen in transit." In `bitcoin-serai`, the analogous gap is that `SignableTransaction::new` accepts an optional `data` payload (an OP_RETURN output, a public, caller-supplied input of up to 80 bytes) but never includes that output in the transaction template used for weight/vbyte and fee estimation. The resulting `needed_fee` and the change/fee split are computed on a smaller transaction than the one actually signed, so the real fee rate is strictly lower than the requested `fee_per_vbyte` — potentially below the minimum relay fee — leaving the threshold-signed transaction unrelayable and the funds frozen in transit with no recovery path (the FROST preprocesses are already bound to that specific transaction and cannot be reused).

### Finding Description
`SignableTransaction::new` builds `tx_outs` and pushes the OP_RETURN output when `data` is `Some` at `send.rs:194-202`. However, both calls to `calculate_weight_vbytes` (which expands `inputs` + `payments` + optional change into a template `Transaction` to measure `tx.weight()`) are made with the raw `payments` slice only — the `data` output is never passed in:

- `send.rs:204` — `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`
- `send.rs:225-227` — `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`

Consequences:
1. `needed_fee = fee_per_vbyte * vbytes` at `send.rs:206` uses a vbyte count that excludes up to ~89 vbytes of OP_RETURN output, so the advertised `needed_fee()` underreports the fee needed to hit the requested rate.
2. The `TooLowFee` check at `send.rs:211` compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the understated `vbytes`, so a transaction can pass the check while its actual fee rate is below the relay minimum.
3. When `change` is provided, the change amount `input_sat - payment_sat - fee_with_change` at `send.rs:228-230` is computed against the understated fee, so the actual paid fee (`sum(inputs) - sum(outputs)`, see `fee()` at `send.rs:138-141`) is also below the intended rate.
4. The `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` uses the template weight that omits the OP_RETURN output.

This is reachable purely through public inputs: `data` is an untrusted caller-supplied `Option<Vec<u8>>` bounded only by the 80-byte check at `send.rs:171`, and the constructed `SignableTransaction` is then signed by the FROST machines via `TransactionSignMachine::sign`, which binds the preprocesses to this exact transaction (`send.rs:373-397`).

### Impact Explanation
A threshold-signed Bitcoin transaction whose effective fee rate falls below the node's minimum relay fee will not propagate, and — like the bridge report's stuck-transaction scenario — there is no "delegate" to repair it: `TransactionSignMachine::cache`/`from_cache` explicitly panic (`send.rs:333-349`) and the preprocesses cannot be re-targeted to a corrected transaction. The inputs are locked behind a FROST multisig, so without an out-of-band resigning ceremony the funds are frozen. Severity: Medium — funds can be frozen in transit but require a specific parameter combination (non-empty `data` plus a marginal `fee_per_vbyte`/change edge).

### Likelihood Explanation
Requires the caller to supply a `data` payload and a fee rate close enough to the minimum relay threshold that the omitted ~89 vbytes pushes the real rate below it (or below what the integrator intended). The miscalculation is systematic whenever `data` is present, not probabilistic; whether it becomes a stuck transaction depends on the chosen fee rate and mempool policy.

### Recommendation
Include the OP_RETURN output in the weight template: pass the fully-built `tx_outs` (or an equivalent `(ScriptBuf, u64)` list including the zero-value data output) into `calculate_weight_vbytes` instead of `payments`, for both the no-change and with-change estimates. Alternatively, add the OP_RETURN output's serialized size to `vbytes` before computing `needed_fee`, and re-check `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` against the final transaction.

### Proof of Concept
1. Construct `inputs` whose total value covers `payments + needed_fee` exactly.
2. Call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` is chosen so `needed_fee` just passes the `TooLowFee` check at `send.rs:211` for the data-less vbyte count.
3. The returned transaction contains an extra ~89-vbyte OP_RETURN output that was never measured; `tx.fee() / actual_vbytes < fee_per_vbyte` and can drop below `DEFAULT_MIN_RELAY_TX_FEE`, making the signed transaction unrelayable while its inputs remain locked under the threshold key.
