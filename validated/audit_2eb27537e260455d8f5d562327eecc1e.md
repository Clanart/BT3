## Title
Path traversal / symlink escape when opening or revealing committed files lets a malicious repository read files outside the working directory - (File: `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/changes/sidebar.tsx`, `app/src/lib/app-shell.ts`)

### Summary
GitHub Desktop's "Open with default program", "Reveal in Finder/Explorer" and related context-menu actions for files shown in the Commit History and Pull Request diff views build the on-disk path to act on by joining `repository.path` with the file's *relative path as reported by git* (`file.path`), and only validate cosmetic properties of that nominal path (extension allow-list, `pathExists`) before invoking the actual filesystem action. The action itself (`shell.openExternal`, `shell.showItemInFolder`) is *not* constrained to stay inside the repository the way the deep-link file-open path is (`resolveWithin` + `isAbsolute` check in `dispatcher.ts`). Since `file.path` originates from a cloned/fetched (attacker-authored) repository and git allows committing symlinks that resolve outside the repo, the checked identity ("a file that exists, has a safe extension, inside the repo") and the acted-upon identity (whatever the symlink actually resolves to on disk) can diverge — the same "check A, act on B" pattern as the referenced Illuminate PT bug.

### Finding Description
- `revealInFileManager` and `openFile` are explicitly documented as unsafe for non-validated paths: [1](#0-0) , yet `revealInFileManager` itself performs no containment check: [2](#0-1) .
- `open-file.ts`'s `openFile` simply calls `shell.openExternal(file://fullPath)` with no path validation: [3](#0-2) .
- In the commit history view, `onOpenItem` builds `fullPath` via `Path.join(repository.path, path)` from the committed file's path and passes it straight to `openFile`: [4](#0-3) . The context menu wiring for "Reveal in File Manager" / "Open in default program" / "Open in external editor" performs only an extension allow-list and `pathExists` check on the *nominal* path, not a containment check: [5](#0-4) .
- The same pattern is repeated for Pull Request file diffs: [6](#0-5)  and [7](#0-6) .
- And again in the Changes sidebar for working-directory files: [8](#0-7) .
- Elsewhere in the very same codebase, when opening a file path that originates from an untrusted external source (a deep link `x-github-client://openRepo` URL), Desktop *does* enforce that the resolved path stays inside the repository, using `isAbsolute` rejection plus `resolveWithin`: [9](#0-8) . `resolveWithin`'s own test suite confirms it is specifically designed to catch symlink-based escapes, proving the maintainers are aware of this exact attack class: [10](#0-9) .

The commit-history/PR/sidebar file-open code paths never call `resolveWithin` (or any equivalent), so a committed symlink (git mode `120000`) whose target is an absolute path or a `../../..` relative path pointing outside the repository will pass the "does file exist" / "safe extension" checks (checks operate on the symlink's own metadata/extension) but the subsequent `shell.openExternal`/`shell.showItemInFolder` call will follow the symlink to the real target outside the repo.

### Impact Explanation
A user who clones or fetches a malicious repository and simply browses its commit history or an incoming pull request's diff (both are normal, encouraged Desktop workflows, not "unnatural user steps") can trigger this by using standard context-menu items ("Reveal in File Manager", "Open with Default Program") on an attacker-crafted file. Because the symlink target is fully attacker-chosen, this can be used to:
- Read/reveal sensitive files outside the repository (e.g., surface the existence/location of `~/.ssh/id_rsa`, cloud-credential files, or other repos on disk), and
- On platforms/file types where "open with default program" causes execution (e.g., a symlink pointing to a script or an OS-associated executable path), potentially achieve code execution.

This satisfies the "file read outside the repo" / "code execution" impact classes called out as valid, and requires no local/physical access, no admin rights, no prior malware, and no leaked credentials — only that the victim opens a hostile repository, which is the core threat model for a Git client.

### Likelihood Explanation
Likelihood is high for the file-read variant: committing a symlink is trivial, no special git privileges are required, and the affected UI actions (open file, reveal in file manager, open in external editor) are common, expected user interactions when reviewing history or PR diffs — unlike the deep-link path, no extra guard exists here at all. The code-execution variant depends on OS file-association behavior and is lower likelihood but still plausible (e.g., `.desktop`, `.lnk`/shortcut-style, or extension-associated launchers).

### Recommendation
Apply the same containment logic already used in `dispatcher.ts`'s `openRepositoryFromUrl` (`isAbsolute` rejection + `resolveWithin(repository.path, file.path)`) to every place that turns a git-reported file path into a filesystem path for `openFile`, `revealInFileManager`, and the corresponding context-menu handlers in `selected-commits.tsx`, `pull-request-files-changed.tsx`, `sidebar.tsx`, and the multi-commit-operation conflict dialogs. Reject or refuse to open paths whose resolved real path (following symlinks) lies outside `repository.path`, consistent with the existing `IAppShell` documentation warning against using these APIs with non-validated paths (`app/src/lib/app-shell.ts` lines 16-23).

### Proof of Concept
1. Attacker creates a repository containing a symlink `evil.txt -> /Users/victim/.ssh/id_rsa` (or a relative `../../../../.ssh/id_rsa`) and commits it.
2. Victim clones/fetches the repository in GitHub Desktop and opens the commit (or an incoming PR) containing this file in the History/PR diff view.
3. Victim right-clicks the file and selects "Reveal in File Manager" or "Open with Default Program" — both call `Path.join(repository.path, file.path)` and pass the result unchecked to `shell.showItemInFolder`/`shell.openExternal` (`app/src/ui/history/selected-commits.tsx:384-420`, `app/src/lib/app-shell.ts:61-64`, `app/src/ui/lib/open-file.ts:1-17`).
4. Because the joined path is a symlink, the OS resolves it to the real target outside the repository, revealing/opening `/Users/victim/.ssh/id_rsa` instead of anything inside the cloned repo — with none of the safety it would have gotten had the code used `resolveWithin` as `dispatcher.ts` does for deep-link file opens.

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
