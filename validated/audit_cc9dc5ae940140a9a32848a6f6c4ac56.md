Audit Report

## Title
Reachable `assert_eq!` panic in `Bank::build_updated_stake_reward` when a stake account's delegation diverges from its epoch-boundary snapshot during multi-block reward distribution - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
`build_updated_stake_reward` hard-asserts that a stake account's calculation-time delegation plus the previously computed reward equals the delegation baked into the pending `PartitionedStakeReward` at store time [1](#0-0) . Reward distribution spans up to 10% of an epoch's slots [2](#0-1) , during which the mechanism designed to reconcile any drift, `recalculate_partitioned_rewards_if_active`, re-derives stake rewards from the live `StakesCache` and rebuilds the `PartitionedStakeReward` list before each distribution block [3](#0-2) [4](#0-3) , meaning `stake.delegation.stake` (read fresh from `stakes_cache_accounts` at store time) and `new_stake.delegation.stake` (recomputed from the same live cache moments earlier in the same block-processing pipeline) are derived from the same recalculated snapshot, not from a stale one.

## Finding Description
The claim asserts that `stake.delegation.stake` used in the `expected_delegation` computation is a "stale, epoch-boundary snapshot" while `new_stake.delegation.stake` is "fixed when rewards were calculated/recalculated," implying these two values can be read at different points in time and thus diverge from independent live account mutation. This does not hold up against the actual code path.

`recalculate_partitioned_rewards_if_active` is invoked to keep the distribution phase state consistent, and when active it calls `recalculate_stake_rewards`, which pulls `stake_delegations` from the *current* `self.stakes_cache.stakes()` [5](#0-4)  and recomputes `stake_rewards` (which becomes the new `PartitionedStakeReward::inflation.stake` used by `build_updated_stake_reward`) via `calculate_stake_rewards_and_commissions` from that same live snapshot [6](#0-5) . This recalculation happens once per block while rewards are active (evidenced by `test_recalculate_partitioned_rewards`, which recalculates and gets matching rewards against the fresh cache) [7](#0-6) . `store_stake_accounts_in_partition` then reads `stakes_cache_accounts` from `self.stakes_cache.stakes()` in the same block [8](#0-7) . Both the "current" delegation used to compute `expected_delegation` and the "new" delegation baked into `partitioned_stake_reward.inflation.stake` therefore originate from the same recalculation pass against the same `StakesCache` state within a single block's processing — there is no window in which one side reads a stale snapshot while the other reflects live mutation from an intervening block, because recalculation happens exactly once per active block, immediately reconciling both values before `build_updated_stake_reward` is called.

The claim's own writeup does not identify a concrete mechanism by which the two values could actually diverge; it explicitly states: "I was not able to locate... the specific stake-program-side guard" and describes the PoC as "not independently reproduced," "cannot be confirmed complete from static analysis," and requiring speculative reproduction against unverified stake-program guards. No sequence of unprivileged operations is demonstrated (or demonstrable from the indexed code) that causes `stake.delegation.stake + stake_reward != new_stake.delegation.stake` when both values come from the same per-block recalculation pass. The claim conflates "the reward was calculated once at the epoch boundary in a prior block" with the actual code behavior, which recalculates every active block precisely to prevent that divergence.

## Impact Explanation
No concrete divergence-inducing operation sequence was established; the claim itself acknowledges this gap. Without a demonstrated bad input or state transition reaching the `assert_eq!` with mismatched values, there is no shown false execution, consensus halt, or fund-loss condition — the claim rests on speculation about an unverified stake-program guard rather than a proven code defect.

## Likelihood Explanation
The claim self-rates likelihood as "uncertain/low-to-moderate" and explicitly could not verify the precondition needed to trigger the panic. The code review here shows the recalculation mechanism reconciles both sides of the assertion from the same live cache read within the same block, closing the gap the claim speculates about. No reachable exploit path from unprivileged input was demonstrated.

## Recommendation
N/A — claim not substantiated against the reviewed code path.

N/A — the claim provides no reproducible PoC and explicitly states it "cannot be confirmed complete from static analysis alone."
