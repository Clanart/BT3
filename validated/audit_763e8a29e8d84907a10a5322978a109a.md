### Title
Unchecked `u64` overflow in payment/fee summation bypasses the insufficient-funds check when constructing a signable Bitcoin transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `payment_sat`, `fee_per_vbyte * vbytes`, and `payment_sat + needed_fee` using plain `u64` arithmetic that silently wraps in release builds. Supplying payments whose amounts sum to a multiple of 2^64 makes `payment_sat` wrap to a small value, bypassing the `NotEnoughFunds` guard and producing a FROST-signed transaction whose outputs bear no relationship to the validated economics — the direct analog of an integer overflow corrupting size/accounting logic (CVE-2023-41056's overflow-in-buffer-sizing class).

### Finding Description
All amounts are attacker-influenced `u64` values and only checked against `DUST`:

- `payment_sat` is an unchecked sum of all payment amounts (line 187): `payments.iter().map(|payment| payment.1).sum::<u64>()`. [1](#0-0) 
- `needed_fee = fee_per_vbyte * vbytes` is an unchecked multiply (line 206). [2](#0-1) 
- The solvency check `input_sat < (payment_sat + needed_fee)` uses unchecked addition (line 215). [3](#0-2) 
- `fee()` subtracts unchecked sums of outputs from inputs (lines 139–141). [4](#0-3) 

Each payment output is created with `Amount::from_sat(payment.1)` regardless of wrapped sum (lines 188–191). [5](#0-4) 

The resulting `SignableTransaction` is then signed by the threshold multisig via `TransactionSignMachine::sign`, which signs each input's `taproot_key_spend_signature_hash` with `Prevouts::All` (lines 373–397). [6](#0-5) 

### Impact Explanation
A caller-specified payment set like `[2^63, 2^63]` yields `payment_sat == 0` after wrapping, so `input_sat < payment_sat + needed_fee` passes with arbitrarily small real inputs, and the change branch's `checked_sub(payment_sat + fee_with_change)` returns nearly the entire input as "change". The multisig then produces valid Schnorr signatures for a transaction that the insufficient-funds validation explicitly intended to reject — concrete signing of an unintended message. The produced transaction is consensus-invalid (outputs exceed `MAX_MONEY`), so the payment silently never executes while the wallet reports a valid `txid` and "sent" transaction; depending on integration, input-selection and reporting logic (`fee()` also underflows to a garbage value) is corrupted by the same overflow.

### Likelihood Explanation
Reachable by any party able to influence the `(ScriptBuf, u64)` payment list or `fee_per_vbyte` passed to `SignableTransaction::new` — public transaction data in scope for the wallet module. Exploitation requires only choosing amounts that wrap the `u64` sum; no validator collusion or key material is needed. Impact is bounded by Bitcoin consensus rejecting the final transaction, so this ranks Medium rather than High — it yields a signed transaction the economic checks were designed to forbid, plus broken fee reporting.

### Recommendation
Use `checked_add`/`checked_mul`/`checked_sub` (or `Amount`'s checked arithmetic) for `payment_sat`, `needed_fee`, `fee_with_change`, and the `fee()` subtraction, and reject any amount that would exceed Bitcoin's `MAX_MONEY` per output. Return a `TransactionError` on overflow instead of wrapping.
