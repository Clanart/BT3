### Title
NFT ownership can be attributed to any DID without approval, allowing fake NFTs to be phished as belonging to a legitimate creator/identity - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
This is the same bug class as the Gitcoin `RoundFactory.ownedBy` finding: an "ownership/attribution" field is accepted and surfaced to clients without any cryptographic verification that the claimed identity actually authorized the association. In `chia-blockchain`, the analogous field is the NFT ownership layer's `current_owner` (DID) value set when minting an "eve" NFT coin.

### Finding Description
When minting an NFT with a DID owner, `NFTWallet.generate_new_nft` explicitly creates the eve coin's ownership layer with an **empty** owner and only afterward attempts to set the DID via a `-10` "change owner" condition, with an explicit code comment acknowledging the trust problem: [1](#0-0) 

```
if did_id is not None:
    self.log.debug("Creating provenant NFT")
    # eve coin DID can be set to whatever so we keep it empty
    # WARNING: wallets should always ignore DID value for eve coins as they can be set
    #          to any DID without approval
    inner_puzzle = create_ownership_layer_puzzle(
        launcher_coin.name(), b"", p2_inner_puzzle, percentage, royalty_puzzle_hash=royalty_puzzle_hash
    )
```

Any minter can supply an arbitrary `did_id` argument (any 32-byte value corresponding to a real, well-known DID/identity) when calling `generate_new_nft`/the `nft_mint_nft` RPC, causing the resulting NFT's ownership layer to record that DID as `owner_did`, with **no on-chain enforcement that the referenced DID actually approved or spent anything**. The `-10` change-owner condition simply asserts the new DID identifier value; the ownership layer puzzle does not require any signature, announcement, or spend authorized by the DID singleton corresponding to that value at consensus level (the `get_did_approval_info` announcement flow is a courtesy the minter's own wallet software performs when it *is* the actual DID owner — it is not something the protocol requires from an arbitrary caller, and an attacker minting an NFT does not need to control the target DID to place its ID in the ownership layer).

This is uncurried and exposed to downstream consumers via `UncurriedNFT.owner_did`, `get_new_owner_did`, and `WalletStateManager.get_minter_did`: [2](#0-1) 

These values populate `NFTInfo.owner_did` / minter DID fields returned by wallet RPCs (`list_nfts`, `get_nft_info`), which marketplaces and dApps display as "Owned by DID X" or "Minted by DID X" — exactly the trust-display pattern described in the source report for `RoundCreated`'s `ownedBy`.

### Impact Explanation
An attacker can mint a fake/malicious NFT (e.g., fraudulent collectible, fake "official" item, phishing NFT with malicious metadata URIs) and set its `owner_did`/minter DID field to the DID of a well-known, trusted creator or organization. Since no on-chain nor client-verifiable proof ties the DID's actual authorization to this attribution, wallets, marketplaces, and dApps that trust the `owner_did`/minter field for display (a documented, intended interpretation of this field) will incorrectly show the fake NFT as belonging to/created by the legitimate DID. This can be used to phish users into interacting with malicious offers, trusting fraudulent collections, or transferring value to attacker-controlled addresses believing they're dealing with a verified brand/identity — mirroring the "breaking the trust relationship between program and round" impact in the original report.

### Likelihood Explanation
Likelihood is high for any user capable of minting NFTs (a standard, unprivileged wallet operation) and reachable by simply calling `nft_mint_nft` with a chosen `did_id` — no compromise of the target DID's keys is required. The comment in the source code itself acknowledges this exact risk ("can be set to any DID without approval"), indicating this is a known, unresolved trust-boundary issue rather than a hypothetical one.

### Recommendation
- Do not trust `owner_did` for the eve/mint transaction as proof of the referenced DID's endorsement anywhere in wallet RPC responses (`NFTInfo`, `list_nfts`, minter DID fields) without also verifying a corresponding authorization spend/announcement from that DID at the same block height as the mint.
- When surfacing `owner_did`/minter DID via RPC to UI/dApp consumers, include a verified/unverified flag, verified only when the code can show the actual DID singleton was spent to co-sign the mint (as `get_did_approval_info`'s announcement flow does when the wallet genuinely controls the DID).
- Document explicitly in the RPC/API surface (not just an internal code comment) that `owner_did` alone must never be treated as attestation of endorsement by downstream consumers (grants-stack-style dApps), and provide a way to cryptographically prove/check DID approval for a given NFT mint.

### Proof of Concept
1. Attacker runs `chia rpc wallet nft_mint_nft` (or calls the wallet RPC directly) specifying `wallet_id` for their own NFT wallet, arbitrary metadata (e.g., phishing content), and `did_id` set to the address of a legitimate, well-known DID (e.g., a verified brand's DID, discoverable on-chain since DIDs are public identifiers).
2. `NFTWallet.generate_new_nft` (`chia/wallet/nft_wallet/nft_wallet.py:465-573`) proceeds to create the eve coin with owner initially empty, then spends it with a `-10` condition setting `new_owner=did_id` to the attacker-chosen (victim) DID — no signature or spend from that DID is required since the attacker does not control it and only calls `get_did_approval_info` if `did_id` matches one of *their own* wallets; if it doesn't, the attacker can bypass or wrap this call path (e.g., custom bundle) to still set the ownership-layer `current_owner` value to the victim DID's id, since the ownership layer's puzzle just records whatever DID value is asserted in the condition, not a signature from that DID.
3. The resulting NFT is confirmed on-chain, with `UncurriedNFT.uncurry(...).owner_did` returning the victim's DID.
4. Any client/marketplace calling `list_nfts`/`get_nft_info` sees `owner_did` == victim DID and displays the NFT as belonging to/associated with that identity, completing the phishing/attribution-spoofing scenario, structurally identical to the original `RoundFactory.ownedBy` finding.
