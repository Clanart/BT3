### Title
`BaseRewardPool.donateRewards` fee-on-transfer/rebasing reward token inflates `rewardPerTokenStored` beyond actual balance received - (File: rewards/BaseRewardPool.sol)

### Summary
`_provisionReward()` credits `historicalRewards` and increments `rewardPerTokenStored` using the caller-supplied `_amountReward` parameter rather than the actual balance delta received after `safeTransferFrom`. Any unprivileged caller can invoke the public `donateRewards(uint256, address)` entrypoint with a registered reward token that charges a transfer fee (or rebases downward), causing the pool to promise more reward tokens via the index than it actually received and holds.

### Finding Description
`donateRewards` is external and callable by anyone as long as `_rewardToken` is already in `isRewardToken`: [1](#0-0) 

It forwards straight into `_provisionReward`, which performs `safeTransferFrom(msg.sender, address(this), _amountReward)` and then unconditionally uses the *requested* `_amountReward` (not the measured balance increase) to update `historicalRewards` and `rewardPerTokenStored`: [2](#0-1) 

If `_rewardToken` is a fee-on-transfer or negative-rebasing token, the pool's actual token balance increases by less than `_amountReward`, yet `rewardPerTokenStored` is incremented by `(_amountReward * 10**stakingDecimals()) / totalStaked()` — the full nominal amount. This inflates the reward-per-token index relative to the tokens the contract actually custodies. Later, when stakers call `getReward` (via `earned()`/`_updateFor()`), the cumulative amount owed to all stakers based on the inflated index exceeds the pool's actual token balance, so eventually some stakers cannot be paid in full — a direct violation of the invariant that the index-credited amount must equal the balance delta actually received.

There is no check anywhere in `_provisionReward` comparing balance-before/after to the requested amount, and no modifier restricts `donateRewards` to trusted, non-fee-on-transfer tokens — it only requires `isRewardToken[_rewardToken]` to be true, which is a token that some `onlyManager` account previously registered via `queueNewRewards`.

### Impact Explanation
This can lead to protocol insolvency for that reward token: the accounting (`rewardPerTokenStored`) promises more reward tokens to stakers in aggregate than the pool holds, so some legitimate `getReward` claims will fail or drain the pool such that other stakers' legitimate claims cannot be honored — permanent loss/freezing of unclaimed yield for at least some accounts. This matches "Protocol insolvency" / "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
Exploitability is fully gated on whether a fee-on-transfer or rebasing token is already registered as a reward token for the pool (`isRewardToken[_rewardToken] == true`), which happens via `queueNewRewards` under `onlyManager`. Given such a token is registered (a plausible integration risk since the codebase does not restrict reward tokens to a fee-free allowlist), any unprivileged address can trigger the miscalculation repeatedly and cheaply (down to 1 wei per call, repeatable). No special capital or flash loans are needed — just calling `donateRewards` with a fee-on-transfer token.

### Recommendation
In `_provisionReward`, measure the actual balance received rather than trusting the input parameter:
```solidity
uint256 balBefore = IERC20(_rewardToken).balanceOf(address(this));
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
uint256 received = IERC20(_rewardToken).balanceOf(address(this)) - balBefore;
// use `received` for historicalRewards / queuedRewards / rewardPerTokenStored math instead of _amountReward
```
This ensures the index is always backed 1:1 by tokens actually custodied by the contract, regardless of fee-on-transfer or rebasing behavior.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy a mock fee-on-transfer ERC20 (e.g., 10% fee) with configurable decimals matching `stakingToken`.
2. Deploy `BaseRewardPool` with a mock `MasterMagpie` (`operator`) that reports `totalStaked() > 0` and staking balances for at least two accounts (Alice, Bob).
3. As the reward manager, call `queueNewRewards(amount, feeToken)` once to register `feeToken` as a reward token (`isRewardToken[feeToken] = true`).
4. As an unprivileged attacker EOA, approve and call `donateRewards(1000e18, feeToken)`. Confirm the pool's actual `feeToken.balanceOf(pool)` increased by only 900e18 (after 10% fee) while `rewardInfo.historicalRewards` and `rewardPerTokenStored` were incremented based on the full 1000e18.
5. Have both Alice and Bob accrue `earned()` amounts based on the inflated `rewardPerTokenStored`, then call `getReward` for each sequentially.
6. Assert: sum of `feeToken` amounts paid out via `getReward` calls exceeds `feeToken.balanceOf(pool)` prior to distribution (i.e., the last claimant's `safeTransfer` reverts due to insufficient balance, or an earlier claimant drains funds owed to a later one) — demonstrating that `10**stakingDecimals()`-scaled index no longer reconciles with the actual `totalStaked()`-backed reward balance held by the pool.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
