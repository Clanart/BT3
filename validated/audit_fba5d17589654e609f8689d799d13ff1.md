## Finding: Authority confusion in `githubAssetVideoRegex` bypasses the GitHub CDN allowlist

### Title
Regex-based CDN allowlist for embedded `<video>` src can be bypassed via userinfo authority confusion - (File: `app/src/lib/markdown-filters/video-url-regex.ts`)

### Summary
`githubAssetVideoRegex` is meant to restrict embedded video `src`/`href` values in rendered markdown (PR bodies, issue comments, commit descriptions, etc.) to GitHub's asset CDN, `https://user-images.githubusercontent.com`. It is built purely from a literal string prefix match with no URL-authority boundary, so an attacker can construct a URL whose *string* begins with the exact CDN origin but whose *actual parsed host* (as resolved by the browser/URL spec and used for the real network request) is a completely different, attacker-controlled domain.

### Finding Description
The regex is constructed as: [1](#0-0) 

i.e. `^https://user-images\.githubusercontent\.com` + `.+` + `(mp4|webm|ogg|...)$`. There is no requirement that the character following the literal CDN string be a path separator (`/`), port delimiter (`:`), or end-of-string — `.+` will happily consume any character, including `@`.

Per the URL/WHATWG spec, `scheme://userinfo@host/path` treats everything before the last `@` in the authority component as userinfo, and only what follows `@` is the actual host. A crafted src such as:

```
https://user-images.githubusercontent.com@evil.example.com/malicious.mp4
```

- Matches `githubAssetVideoRegex` because the literal prefix `https://user-images.githubusercontent.com` is present, `.+` consumes `@evil.example.com/malicious`, and the trailing extension `mp4` matches.
- But when parsed as a URL (and when the browser/Electron renderer actually issues the network request for the `<video>` element), `new URL(src).host` resolves to `evil.example.com`, with `user-images.githubusercontent.com` treated merely as a (meaningless) username.

This regex is used to gate two markdown filters that process attacker-controlled repository/API content (PR/issue/commit markdown): [2](#0-1) [3](#0-2) 

`VideoTagFilter` decides whether to keep or strip a `<video>` tag based solely on this regex test against `el.src`, and `VideoLinkFilter` uses it to decide whether to *convert* an anchor into a live `<video src=...>` element. In both cases, the regex is the only gate — there is no `new URL(...).host === 'user-images.githubusercontent.com'` check. Both filters are wired into the shared markdown pipeline that processes untrusted PR/issue/commit content: [4](#0-3) 

I found no CSP `media-src` restriction in the repository that would independently constrain which hosts a rendered `<video>` element can fetch from, so the regex is the actual enforcement point for this allowlist.

### Impact Explanation
An attacker who controls a pull request description, issue body, or commit message (all unprivileged, remotely-supplied content per the review scope) can cause GitHub Desktop to render/auto-generate a live `<video>` element pointing at an attacker-controlled host, even though the intended design (per the code's own comments) is to only allow GitHub's own asset CDN and strip everything else. This defeats the security boundary the filter was written to enforce and causes the renderer to make an automatic network request to an arbitrary attacker server as soon as the victim views the PR/issue/commit — leaking the victim's IP address/user agent and enabling tracking, and generally allowing attacker-hosted media to be embedded where only GitHub's own CDN was intended to be trusted.

### Likelihood Explanation
High likelihood of triggering: the attacker only needs to post a PR/issue comment or commit message containing a crafted `<video>` tag or auto-linked URL of the form `https://user-images.githubusercontent.com@evil.example.com/x.mp4`; no unusual victim interaction beyond opening/viewing the PR/issue/commit in GitHub Desktop is required.

### Recommendation
Replace the literal-prefix regex check with an actual URL parse and strict origin/host comparison, e.g.:
```ts
function isGithubAssetVideoUrl(src: string): boolean {
  try {
    const url = new URL(src)
    return (
      url.protocol === 'https:' &&
      url.hostname === 'user-images.githubusercontent.com' &&
      url.username === '' &&
      url.password === '' &&
      videoExtensionRegex.test(url.pathname)
    )
  } catch {
    return false
  }
}
```
This removes the ambiguity between string-matching and actual authority resolution.

### Proof of Concept
```ts
import { githubAssetVideoRegex } from './video-url-regex'

const src = 'https://user-images.githubusercontent.com@evil.example.com/malicious.mp4'

console.log(githubAssetVideoRegex.test(src)) // true — passes the filter's allowlist check

const url = new URL(src)
console.log(url.host) // "evil.example.com" — actual network destination differs from the matched string
```
This demonstrates the divergence: the regex-based check in `video-url-regex.ts` says the URL is a trusted GitHub asset, while the real resolved authority (and thus the actual network request target for the rendered `<video>` element) is the attacker's domain.
