### Title
Attacker-controlled serialized bytes generate an arbitrary `ThresholdKeys` object — inconsistent secret share and attacker-chosen group key used for signing - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes every semantic field of a threshold key — the threshold parameters `(t, n, i)`, the interpolation method (including a fully attacker-supplied `Interpolation::Constant` coefficient vector), the secret share, and all `n` verification shares — directly from an untrusted byte stream, then constructs the operational key via `ThresholdKeys::new`. `ThresholdKeys::new` never checks that the supplied `secret_share` is consistent with `verification_shares[i]` (i.e., that `C::generator() * secret_share == verification_shares[&i]`), nor that any participant actually agrees the resulting `group_key` is the intended key. Analogous to the openapi-python-client advisory — where a crafted document generates arbitrary code — here crafted bytes generate an arbitrary signing key: the group key is computed solely as `sum(verification_shares[i] * interpolation_factor(i))` over participants `1..=t`, all attacker-chosen for `Constant` interpolation and attacker-influenced for `Lagrange`. The resulting `ThresholdKeys` is then used verbatim by FROST signing machines, producing signature shares under a key the holder never agreed to.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` (`crypto/dkg/src/lib.rs:591-602`), a one-byte interpolation selector where `0` reads `n` arbitrary scalars as `Interpolation::Constant` (`crypto/dkg/src/lib.rs:604-616`), an arbitrary `secret_share` (`crypto/dkg/src/lib.rs:618`), and `n` arbitrary verification-share points (`crypto/dkg/src/lib.rs:620-623`), and passes all of it to `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:625-631`). `ThresholdKeys::new` only validates structural shape — share-map length, participant indexes `<= n`, and `t == n` for `Constant` interpolation (`crypto/dkg/src/lib.rs:355-374`) — then derives `group_key` purely from the supplied verification shares and interpolation factors (`crypto/dkg/src/lib.rs:376-378`). There is no check that `G * secret_share == verification_shares[i]`. `Interpolation::Constant`'s `interpolation_factor` simply returns `c[i - 1]` for whatever signing set is used (`crypto/dkg/src/lib.rs:228`), so a crafted coefficient vector makes each participant's effective share contribution arbitrary and independent of the signer set. `ThresholdView`/`view` then interpolates `secret_share` by this attacker-chosen factor and adds the offset to `included[0]` (`crypto/dkg/src/lib.rs:494-521`), producing the value that FROST multiplies by the challenge when generating signature shares.

### Impact Explanation
A deserialized `ThresholdKeys` is a trusted operational object: FROST `sign` uses its `view()` to produce the secret-share term `lambda_i * s * c` in each signature share, and `group_key()` determines the key the final signature verifies under. Because the serialized form is a full "program" for key generation — attacker-chosen interpolation coefficients, attacker-chosen verification shares, attacker-chosen secret share — an attacker who can cause these bytes to be read (the threat model explicitly includes untrusted bytes fed to `ThresholdKeys::read`) causes the node to sign under an unintended group key with an unintended effective share. Concretely: the attacker sets `verification_shares` such that `group_key = G * k` for a known `k`, and sets `i`/`Constant` coefficients arbitrarily; the victim's shares are then computed against verification shares that do not correspond to the victim's actual polynomial, and any aggregation of shares produces signatures under the attacker's chosen key — a concrete case of signing under an unintended key (the analog of executing attacker-generated code). Additionally, because `secret_share` need not correspond to `verification_shares[i]`, the victim can be made a permanent blamed party: every share it emits fails `share_verification` / aggregate verification, enabling targeted DoS against a specific validator whenever attacker-influenced key material is loaded, and corrupting recovery (`recover_key` interpolates the same inconsistent data).

### Likelihood Explanation
Reachability depends on an integrator deserializing key material from a transport or storage an unprivileged party can influence (the scan rules explicitly designate `ThresholdKeys::read` an in-scope untrusted-bytes sink). Within the deserialization itself, exploitation requires no race, no side channel, and no cryptographic break — the attacker freely chooses every field. The only mitigations are the structural checks in `ThresholdParams::new` (`t > 0`, `t <= n`, `i <= n` — `crypto/dkg/src/lib.rs:166-178`), which do not constrain semantics. Likelihood is therefore moderate: conditional on attacker-controlled bytes reaching `read`, impact is deterministic.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify self-consistency of the deserialized key: assert `C::generator() * secret_share == verification_shares[&params.i()]` after scalar multiplication of the share by its `interpolation_factor` against the `1..=t` set used for `group_key`, and reject on mismatch. For `Interpolation::Constant`, additionally document and bound coefficient semantics, or restrict `read` to `Interpolation::Lagrange` since `Constant` is an internal MuSig construct. Treat the serialized form as untrusted input: canonicality checks already exist for scalars/points, but semantic consistency of the assembled key is entirely unverified.

### Proof of Concept
Conceptual PoC against `crypto/dkg/src/lib.rs`:

```rust
use std::collections::HashMap;
use zeroize::Zeroizing;
use dalek_ff_group::{Scalar, Ristretto};
use ciphersuite::{group::ff::Field, Ciphersuite};
use dkg::{ThresholdKeys, ThresholdParams, Participant, Interpolation};

// Attacker-known group key discrete log
let attacker_secret = Scalar::random(&mut rand_core::OsRng);
let attacker_key = <Ristretto as Ciphersuite>::generator() * attacker_secret;

// Craft serialized ThresholdKeys for ristretto: t=n=2, i=1
let mut bytes = vec![];
bytes.extend(4u32.to_le_bytes());                       // ID len
bytes.extend(<Ristretto as Ciphersuite>::ID);           // ID
bytes.extend(2u16.to_le_bytes());                       // t
bytes.extend(2u16.to_le_bytes());                       // n
bytes.extend(1u16.to_le_bytes());                       // i
bytes.push(0);                                          // Interpolation::Constant
// Constant coefficients: participant 1 -> 1, participant 2 -> 0
bytes.extend(Scalar::ONE.to_repr().as_ref());
bytes.extend(Scalar::ZERO.to_repr().as_ref());
// secret_share: arbitrary garbage (victim's "share"), NOT consistent with vs[1]
bytes.extend(Scalar::random(&mut rand_core::OsRng).to_repr().as_ref());
// verification_shares: vs[1] = attacker_key (factor 1 => group_key = attacker_key),
// vs[2] = anything (factor 0 => unused in group_key)
bytes.extend(attacker_key.to_bytes().as_ref());
bytes.extend(<Ristretto as Ciphersuite>::generator().to_bytes().as_ref());

let keys = ThresholdKeys::<Ristretto>::read(&mut bytes.as_slice()).unwrap();
// group_key is attacker_key despite the secret_share being unrelated;
// keys.view(...)/FROST sign now produce shares under the attacker's key.
assert_eq!(keys.group_key(), attacker_key);
```

Root cause: `ThresholdKeys::new` computes `group_key` from attacker-supplied `verification_shares` and `interpolation` without binding them to `secret_share` (`crypto/dkg/src/lib.rs:376-390`), and `read` accepts all fields verbatim (`crypto/dkg/src/lib.rs:591-631`).
