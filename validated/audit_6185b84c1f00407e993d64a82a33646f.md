### Title
Cached FROST preprocess seed is reused across multiple `sign` calls in `DkgConfirmer`, enabling nonce reuse and validator secret-key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The PJSIP bug class is a shared object keyed in a global table being reused/prematurely invalidated across multiple logical sessions, so distinct operations alias the same state. Serai's analog lives in `SigningProtocol`: a FROST preprocess seed is cached in the DB under a context key, never deleted, and deterministically re-expanded into identical nonces every time `share_internal` re-executes. `DkgConfirmer::share` and `DkgConfirmer::complete` each call `share_internal`, which calls `preprocess_internal` again and `machine.sign(...)` a second time with the same nonce seed but potentially a different set of counterparty preprocesses — the exact "reuse will enable third-party recovery of your private key share" condition the FROST crate forbids.

### Finding Description

`preprocess_internal` stores a `CachedPreprocess` (the ChaCha20 seed from which both FROST nonces are deterministically derived in `AlgorithmSignMachine::from_cache` / `seeded_preprocess`, `crypto/frost/src/sign.rs:121-144`) under `CachedPreprocesses` keyed only by `self.context` — `(b"DkgConfirmer", self.attempt)` — and never removes it:

- `coordinator/src/tributary/signing_protocol.rs:123-145`: `CachedPreprocesses::set` writes once; every subsequent call `get`s and decrypts the same seed, reconstructing identical `nonces`.
- `crypto/frost/src/sign.rs:209-224`: `cache`/`from_cache` explicitly state the cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" and that after `from_cache` "the preprocess must be deleted so it's never reused".

`share_internal` then consumes a rebuilt machine and calls `machine.sign(preprocesses, msg)` (`signing_protocol.rs:156-178`). Both public entry points route through it:

- `DkgConfirmer::share` → `share_internal` → `sign()` (lines 304-310).
- `DkgConfirmer::complete` → `share_internal` again → `sign()` again, then `complete_internal` (lines 312-327).

The file's own header (lines 25-35) concedes "it is explicitly unsafe to reuse nonces across signing sessions" and that safety depends on `sign` never being called on "distinct received messages". But the nonce reuse protection is purely contextual: if the `preprocesses` map handed to `share` and the one handed to `complete` differ — e.g., a different subset of validator preprocesses reached accumulation, or a malicious validator contributes different preprocess bytes to the two accumulations — the same `(d, e)` nonce pair is bound under a different `BindingFactor` rho and effectively a different challenge. Two Schnorr/FROST shares under `s_i = d + rho·e + c·λ·x_i` where `rho`/`c` differ but `d`, `e` are identical form a linear system leaking the secret share `x_i` — the classic FROST nonce-reuse/ROS attack.

Additionally, `threshold_i_map_to_keys_and_musig_i_map` (lines 208-250) remaps attacker-supplied `Participant` keys into MuSig indexes on each call, so the attacker controls which preprocesses are bound into `B` per call — the same malleable-registration shape as the PJSIP dialog-set hash collision, where one keyed entity is re-registered under different keys.

### Impact Explanation

An unprivileged counterparty validator (or anyone able to influence which preprocess set is accumulated for the share vs. complete round of a DKG confirmation) can cause the coordinator to emit two signature shares generated from the same nonce seed under different binding factors. Given `share_j = d + rho_j·e + c_j·λ_i·x_i` and `share_k = d + rho_k·e + c_k·λ_i·x_i` with attacker-chosen `rho` inputs, the private validator key share `x_i` — the root-of-trust key used for on-chain `set_keys` DKG confirmation — is recoverable algebraically. Compromise of the validator's Ristretto key lets the attacker forge `DkgConfirmer` signatures for future sets.

### Likelihood Explanation

Reachable from public inputs: the `preprocesses` map passed to `share`/`complete` is populated from network-supplied validator messages (`Commitments::read` / `read_preprocess` at `signing_protocol.rs:165`). Because the same context key deterministically re-derives nonces, any divergence between the two `sign` invocations — different included participant subset or mutated preprocess bytes — suffices. The code's own comments (lines 34-48) acknowledge the divergence risk exists if messages differ between invocations, and the TODO at lines 50-54 notes the on-chain-preprocess-consistency check is not yet implemented. Likelihood is bounded by needing two differing accumulations within one `attempt`, hence Medium-High rather than guaranteed.

### Recommendation

1. After `from_cache` consumes a seed, delete the `CachedPreprocesses` entry, or store a "consumed" marker, so a second `share_internal` call under the same context cannot rebuild the same nonces.
2. Instead of re-running `sign` in `complete`, persist the `AlgorithmSignatureMachine` state (or the computed share and binding context) from the `share` call, so `complete` cannot bind to a different preprocess set.
3. Bind the signed message/preprocess commitment into the cache key (e.g., `CachedPreprocesses: (context, msg_hash)`), and refuse to sign if the stored commitment doesn't match, enforcing the "identical messages" invariant the design relies on.

### Proof of Concept

```
Attempt A, context = (b"DkgConfirmer", 0):

1. Coordinator calls DkgConfirmer::preprocess() ->
   seed S stored under context; publishes preprocess P_us = f(S).

2. DkgConfirmer::share(preprocesses_1, kp) ->
   preprocess_internal reloads S -> nonces (d, e)
   sign(preprocesses_1, msg): rho_1 binds {P_us, attacker P_x}
   emits share_1 = d + rho_1*e + c_1*lambda*x_i

3. DkgConfirmer::complete(preprocesses_2, kp, shares) ->
   share_internal AGAIN reloads S -> same (d, e)
   preprocesses_2 differs (attacker submitted different preprocess bytes
   or the accumulated signer subset changed) ->
   sign(preprocesses_2, msg): rho_2 != rho_1
   emits share_2 = d + rho_2*e + c_2*lambda*x_i

4. Attacker solves the 2x2 linear system over {d, e, lambda*x_i}
   -> recovers the validator's secret share x_i.
```

The invariant violation is concrete in `crypto/frost/src/sign.rs:209-219` ("After this, the preprocess must be deleted so it's never reused") versus `coordinator/src/tributary/signing_protocol.rs:137-145` (same seed re-loaded for every `share`/`complete` under the same `(b"DkgConfirmer", attempt)` context with no deletion).

One caveat I could not fully verify within this scan: the exact call sites in `coordinator/src/tributary/handle.rs` that feed `preprocesses` into `share` vs `complete`, so whether differing accumulations naturally reach both calls within one attempt. The unsafe reuse pattern itself, however, is unconditional — every `complete` re-executes `sign` on re-derived identical nonces.
