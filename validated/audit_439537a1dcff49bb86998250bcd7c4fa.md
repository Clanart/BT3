### Title
Path-traversal via missing directory-boundary check in `resolveWithin()` allows deep-link `filepath` to escape the target repository - (File: `app/src/lib/path.ts`)

### Summary
The bug-class in the C4 report is a **boundary/offset miscalculation**: some fields are read using the correct byte-width while a sibling field uses a narrower width, so the computed value silently drifts outside the intended boundary and the wrong data ends up being used. GitHub Desktop has a structurally identical flaw in its path-containment primitive `resolveWithin()`: it validates that a resolved path is "inside" a root directory using a **plain string-prefix comparison instead of a directory-boundary-aware comparison**, so a resolved path in a *sibling* directory whose name happens to start with the root directory's name is incorrectly accepted as "inside" the root.

### Finding Description
`resolveWithin()` / `_resolveWithin()` in `app/src/lib/path.ts` is the shared safety primitive used to make sure an attacker-influenced relative path segment cannot escape a trusted root directory (analogous to the settlement-info structure in the C4 report where a boundary must be respected consistently across fields). The final check is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character-prefix comparison with **no trailing path-separator boundary check**. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/repo`, then any resolved path in a *sibling* directory whose name has `repo` as a prefix — e.g. `/Users/victim/Documents/GitHub/repo-secrets/data.txt` — will satisfy `startsWith(realRoot)` and be treated as "inside" the root, even though it is a completely different directory outside the intended tree. This is the exact same failure mode as the C4 finding: one boundary is computed/read correctly (`realRoot`), but the comparison against it doesn't consistently enforce the true edge of that boundary (a path separator), so data belonging to an adjacent region is silently accepted.

This primitive is reachable from an attacker-controlled surface: the `x-github-client://openrepo/...` / `github-mac://openrepo/...` deep link handler parses a `filepath` query parameter with `parseAppURL()`: [2](#0-1) 

and the dispatcher passes that attacker-controlled `filepath` straight into `resolveWithin(repository.path, filepath)` before opening the result in the OS file manager: [3](#0-2) 

The only other guard is `isAbsolute(filepath)`, which does nothing to stop a relative path with `..` segments that resolves into a sibling directory sharing a name prefix with the repository directory.

The same `resolveWithin` primitive is also relied on in `app/src/lib/copilot-conflict-context.ts:390-407` to guard which working-directory files get read and sent to the Copilot conflict-resolution feature, so the same boundary flaw affects that surface as well.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openrepo/<url>?filepath=<payload>` (or `github-mac://openrepo/...`) link can cause Desktop to resolve and reveal (via `shell.showItemInFolder`) a file located in a directory outside of, but adjacent to, the target repository — provided the victim has another repository/folder on disk whose name is a prefix-extension of the target repo's directory name (a very common real-world pattern, e.g. `app` vs `app-backup`, `desktop` vs `desktop-internal`). This is a read-outside-the-repo primitive delivered purely through a link click, matching the "Valid Impact" criteria (attacker controls a deep link the user clicks, result is file read outside the repo).

### Likelihood Explanation
Exploitation requires no local access, no admin rights, and no prior compromise — only that the victim clicks a link and that a sibling directory with an overlapping name prefix exists on disk, which is plausible in normal multi-repo development environments (Desktop's default clone root is a shared parent folder for all cloned repos). The `filepath` parameter is fully attacker-controlled and only lightly validated (`isAbsolute` check), so the likelihood of a suitably-named sibling existing is the main constraining factor, but it is not implausible in typical GitHub Desktop usage where many similarly-prefixed repos are cloned into the same parent directory.

### Recommendation
Fix the boundary check in `_resolveWithin()` to require a path-separator boundary (or exact equality) rather than a raw string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the C4 recommendation to standardize how boundaries/widths are read and compared so that no field (or in this case, no directory comparison) can silently drift past the intended edge.

### Proof of Concept
1. Victim has two directories cloned under the same parent, e.g. `/Users/victim/Documents/GitHub/repo` and `/Users/victim/Documents/GitHub/repo-secrets/data.txt` (the latter containing sensitive data, e.g. another private clone).
2. Attacker sends the victim a link such as:
   `x-github-client://openrepo/https://github.com/owner/repo?filepath=../repo-secrets/data.txt`
3. `parseAppURL()` accepts this since `filepath` has no traversal validation [2](#0-1) .
4. `openRepositoryFromUrl()` calls `resolveWithin(repository.path, '../repo-secrets/data.txt')` [3](#0-2) .
5. Inside `_resolveWithin`, `realResolved` becomes `/Users/victim/Documents/GitHub/repo-secrets/data.txt`, and `realRoot` is `/Users/victim/Documents/GitHub/repo`; `realResolved.startsWith(realRoot)` is `true` due to the shared `repo` prefix, so the function returns the resolved path instead of `null` [1](#0-0) .
6. Desktop calls `shell.showItemInFolder(resolved)`, revealing/opening the file outside the intended repository boundary, driven entirely by a link click.
