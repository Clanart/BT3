## Title
Symlink TOCTOU in `resolveWithin()` lets a validated-but-stale path be used for file reads outside the repository - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the shared guard used across GitHub Desktop to make sure a repository-relative path (coming from an attacker-controlled cloned/fetched repository) cannot escape the repository root, including via symlinks. The function performs its containment check against the fully-resolved (`realpath`) form of the path, but it **returns the un-resolved joined path instead of the value it actually validated**. Callers such as `buildConflictContext()` then perform separate, later `stat`/`readFile` calls against that returned (unvalidated-at-use-time) path. This is structurally the same class of bug as the Splits H-02 finding: a security decision is made once (ownership/containment check), and a *different, mutable* value is trusted afterward for the sensitive operation, so the check can be stale by the time it matters.

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts`: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

The containment guarantee is computed on `realResolved` (symlinks followed), but the function hands back `resolved` (symlinks *not* followed). Any caller that treats the returned value as "safe to use directly" is trusting a value that was never the one actually checked against the root.

`buildConflictContext()` in `app/src/lib/copilot-conflict-context.ts` is exactly such a caller. For every conflicted file coming from an attacker-controlled merge/rebase/cherry-pick against a cloned/fetched repository, it does: [2](#0-1) 

1. `resolveWithin(workingDirectory, file.path)` → returns `resolved` (validated only at that instant, via a fresh `realpath`).
2. A separate `await stat(absolutePath)` call.
3. A separate `await readFile(absolutePath, 'utf8')` call.

Each of these is an independent async filesystem round-trip. Because the returned path is the literal joined path and not the canonical one that was checked, if any path component becomes a symlink pointing outside the repository between step 1 and step 3, the subsequent `stat`/`readFile` will transparently follow it — the guard's result no longer reflects the actual target being read. The file content read this way is fed verbatim into the Copilot conflict-resolution prompt (`formatConflictContextForPrompt`), meaning arbitrary file content read outside the repository can be exfiltrated into an LLM request built from attacker-influenced repository state.

The same primitive (`resolveWithin`) is reused elsewhere for "open path in Finder/Explorer" from deep links, e.g. `app/src/ui/dispatcher/dispatcher.ts`: [3](#0-2) 

which has the identical check→use gap between validation and `shell.showItemInFolder(resolved)`.

### Impact Explanation
A successful race lets an attacker who controls a cloned/fetched repository (or a repository the victim merges/rebases against) cause GitHub Desktop to read a file outside the repository working directory and have its contents forwarded into the Copilot conflict-resolution prompt/context, or opened via the shell — i.e. file read/disclosure outside the intended sandboxed repo path, matching the "credential/token exfiltration" / "file read outside the repo" impact classes called out as in-scope.

### Likelihood Explanation
Exploitation requires winning a short TOCTOU window between the `realpath`-based check and the later `stat`/`readFile` calls, which lowers likelihood relative to a trivially-reachable bug, but no additional privilege, local host compromise, or victim action beyond the normal "clone/fetch and resolve a merge conflict" (or click a deep link) workflow is required. The underlying design flaw — returning a value different from the one that was actually validated — is unconditionally present in every call site, so the flaw itself is 100% reachable; only the race timing affects reliability.

### Recommendation
Have `_resolveWithin` return the already-validated `realResolved` path (or otherwise guarantee that the value returned is the exact value that was checked), and have callers perform file operations only on that canonicalized path. Where possible, use `O_NOFOLLOW`-style opens or re-validate immediately before the privileged operation instead of relying on a prior, temporally-separated check.

### Proof of Concept
1. Attacker crafts a repository such that a conflicted file path component can be swapped to a symlink pointing to a sensitive path outside the repo (e.g. via a concurrently running filter/hook or a follow-up write) in the interval between Desktop's `resolveWithin` call and its subsequent `stat`/`readFile` call in `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:390-438`).
2. Victim clones/fetches the repository and triggers a merge/rebase/cherry-pick that surfaces this file as conflicted, then opens the Copilot conflict-resolution feature.
3. During the narrow window between the containment check and the actual read, the symlink is put in place; `readFile(absolutePath, 'utf8')` follows it and returns the contents of a file outside the repository, which are then embedded into the prompt sent for conflict resolution. async function _resolveWithin(
```typescript
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
