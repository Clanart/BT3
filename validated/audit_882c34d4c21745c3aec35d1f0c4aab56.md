### Title
Silent `U256::low_u128()` truncation of accumulated relayer fees lets a portion of the `Fees` balance be zeroed without ever being paid out - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
This is a direct local analog of the `withdrawtolandlord` `u64`-amount bug: an amount field is downsized to a narrower type than the storage/accounting type that tracks it, and the withdrawal path uses that narrower value to instruct payout while zeroing the full balance locally. Here, `Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` stores relayer fees as `U256` in `Fees<T>` but, for substrate destinations, truncates the payout amount to `u128` via `.low_u128()` before dispatching the cross-chain withdrawal message, and then unconditionally zeroes the full `U256` balance regardless of whether the truncated amount matches it.

### Finding Description
`Fees<T>` is keyed by `(StateMachine, Vec<u8>)` and stores a `U256` balance: [1](#0-0) 

`Pallet::accumulate` (in `accumulate.rs`) freely adds `U256` fee values into this balance across many separate withdrawal proofs, with no bound imposed relative to `u128::MAX`: [2](#0-1) 

When a relayer calls `withdraw`, the pallet reads the full `U256` `available_amount` and, for a substrate destination, converts it with `.low_u128()`: [3](#0-2) 

`U256::low_u128()` does not check for overflow — it silently discards the upper 128 bits and returns only the low 128 bits. This is functionally the same failure mode as the reported `withdrawtolandlord` bug (a value with more precision than the target integer type can represent gets narrowed), except worse: instead of erroring like `u64::try_from` would, `low_u128()` produces a *corrupted* — not merely truncated-then-rejected — value that is silently dispatched as the real withdrawal amount.

Critically, immediately after dispatching this (possibly truncated) amount, the pallet unconditionally zeroes the *entire* `U256` balance: [4](#0-3) 

So if `available_amount > u128::MAX`, the destination chain is only instructed to pay out `available_amount mod 2^128`, while the source-chain `Fees` entry is reset to zero for the *full* `U256` amount. The difference (`available_amount − low_u128(available_amount)`) is permanently and silently lost — the relayer can never claim it again because the accounting entry that tracked it has already been wiped in the same extrinsic, and no error, event, or `try_into` check is emitted to signal the truncation occurred.

Existing guards do not stop this: `min_withdrawal_amount` only checks a *lower* bound (`available_amount < min`) and does nothing to bound the upper end; the EVM branch of the same function correctly converts the same `U256` into a full `uint256`/`U256` on the wire (`amount: available_amount.into()`), showing the substrate branch is inconsistent with its own sibling code path.

### Impact Explanation
This falls squarely in the "stealing or loss of funds" and "logic attack" categories of the impact gate. The relayer's legitimately accumulated fee balance is destroyed on-chain (the `Fees` map entry is zeroed) while only a fraction of it is actually dispatched for payout on a substrate destination — the excess (`amount - low_u128(amount)`) becomes permanently unrecoverable. Unlike the original C4 finding (which only causes failed/expensive withdrawals that can be retried), this variant causes an outright, non-recoverable loss of relayer fees because the balance-clearing step is not conditioned on how much was actually dispatched.

### Likelihood Explanation
Reaching `U256` values `> u128::MAX` (`> 2^128 - 1`, an astronomically large but not impossible fee-token amount given 18-decimal tokens and no upper bound in `accumulate`) requires an unprivileged relayer to simply accumulate enough legitimate fee-claims over time (via the normal, permissionless `accumulate_fees` extrinsic, which is proof-gated but has no cap on total accumulated `U256` value) and then call the also-permissionless `withdraw_fees` extrinsic targeting a substrate destination. No malicious peer, relayer collusion, governance action, or leaked key is needed — only ordinary use of two public extrinsics (`accumulate_fees`, `withdraw_fees`) already exposed by the pallet. The main mitigating factor is the very large numeric threshold required, which likely explains why this hasn't been observed operationally, but the code path itself contains no explicit safeguard, unlike the EVM branch which naturally uses the full-width `U256`/`uint256`.

### Recommendation
Replace `.low_u128()` with a checked conversion (`u128::try_from(available_amount)` / `TryInto`), and reject or split the withdrawal (mirroring the C4 fix suggestion of using a wider type end-to-end) rather than silently truncating. Only zero the `Fees<T>` entry by the amount actually dispatched, not unconditionally to zero — e.g., decrement by the dispatched amount so any un-dispatched remainder stays claimable, and emit an explicit error/event if `available_amount` exceeds what the destination message format can carry.

### Proof of Concept
1. An unprivileged relayer submits enough valid `accumulate_fees(withdrawal_proof)` calls (each backed by real cross-chain state proofs of legitimate deliveries) so that `Fees::<T>::get(dest_chain, relayer_address)` exceeds `u128::MAX` (2^128 − 1) — this only requires the sum of proven fees to cross that threshold, not any single oversized proof.
2. The relayer calls `withdraw_fees` with `dest_chain` set to a **substrate** `StateMachine`.
3. Inside `Pallet::withdraw`:
   - `available_amount` (a `U256` greater than `u128::MAX`) is read from storage.
   - `available_amount.low_u128()` truncates it, discarding the high bits, and this truncated `u128` is placed into the dispatched `WithdrawalRequest.amount`.
   - `Fees::<T>::insert(dest_chain, address, U256::zero())` immediately zeroes the *entire* original `U256` balance.
4. The ISMP message delivered to the destination only credits the relayer with `available_amount mod 2^128`; the remaining `available_amount − (available_amount mod 2^128)` is neither paid out nor recorded anywhere on Hyperbridge — it is lost permanently, with `Withdraw` event's `amount` field (which logs the pre-truncation `available_amount`) misleadingly implying the full value was paid.
