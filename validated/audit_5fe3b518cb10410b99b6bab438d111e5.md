### Title
Shared `BalanceHandler` instance across recursive/nested precompile calls causes EVM StateDB balance desync from actual bank balances - (File: precompiles/common/balance_handler.go)

### Summary
The `BalanceHandler` used by Cosmos EVM precompiles (staking, distribution, gov, ics20, slashing, erc20) to reconcile bank-module balance-changing events into the EVM `StateDB` records a single `prevEventsLen` cursor per handler instance. If the same `BalanceHandler` instance is reused/shared across nested or recursive precompile calls within one EVM execution (e.g., a contract that calls into a precompile, which itself triggers another precompile call, or a caller contract that re-enters a precompile), the `BeforeBalanceChange`/`AfterBalanceChange` cursor gets overwritten by the inner call, causing bank events from the outer call to be skipped or double-counted when applied to `StateDB.AddBalance`/`SubBalance`. This is functionally the same bug class as the report's "sensitive state changes not tracked/emitted correctly" — except here the consequence is not just missing an event log, but silently producing a **wrong balance value written into StateDB**, i.e., accounting corruption between the native bank ledger and the EVM-visible balance. [1](#0-0) 

### Finding Description
`BeforeBalanceChange` snapshots `len(ctx.EventManager().Events())` into `prevEventsLen`, and `AfterBalanceChange` later slices `events[bh.prevEventsLen:]` to find bank `coin_spent`/`coin_received`/precisebank fractional-balance events that occurred since the snapshot, translating them into `StateDB.AddBalance`/`SubBalance` calls. [2](#0-1) [3](#0-2) 

The repository itself contains a dedicated regression test explicitly describing this exact defect: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [4](#0-3) 

The precompile package wires `BalanceHandler` calls around precompile method execution in `precompile.go`, and every value-moving precompile (staking, distribution, gov, ics20, slashing, erc20) references this shared mechanism, meaning any code path that allows re-entrant/nested precompile invocation within a single call frame (e.g., a caller contract invoking a precompile method that itself calls another precompile, or the same precompile recursively) is subject to `prevEventsLen` being clobbered by the inner call's `BeforeBalanceChange`. When the inner call's `AfterBalanceChange` resets/advances the cursor, the outer call's subsequent `AfterBalanceChange` will only see events emitted after the inner cursor position — silently dropping the outer bank events that should have updated `StateDB`, or in other orderings, re-processing events already applied to StateDB by the inner handler, effectively duplicating or losing balance deltas in the EVM view.

Because Cosmos EVM treats `StateDB` balance as the ground truth for gas refunds, further EVM calls/transfers within the same transaction, and read-only `balanceOf`/`eth_getBalance` responses at the point of query, a divergence here means: (a) an account's EVM-visible balance can be inflated relative to its real spendable bank balance, allowing it to be used as spendable value in subsequent EVM operations within the same call trace (e.g., transferring or approving against a balance that isn't backed by real coins), and (b) or an account's EVM balance can be deflated, permanently hiding value from EVM-based transfers/liquidity even though the coins exist in the bank module (a freezing-class impact).

### Impact Explanation
This maps to the "Critical unauthorized … duplication … or irreversible accounting corruption of spendable user value across native balances, EVM balances … or precompile-mediated assets" and "permanent freezing … of user funds" impact classes. A StateDB balance that diverges from the actual bank balance is a direct violation of the core invariant stated in the precompile's own documentation ("Balance Consistency: All balance changes go through the bank module ensuring consistency"), and if exploitable by an ordinary contract performing nested precompile calls (no privileged access required), it lets an unprivileged user manipulate the EVM-visible balance used for subsequent same-transaction operations, or lose track of legitimately received funds. [5](#0-4) 

### Likelihood Explanation
The bug is directly acknowledged by an existing test in the codebase using a debug precompile purpose-built to trigger nested/recursive precompile calls and assert on emitted event counts, which strongly suggests the underlying defect was identified by the project's own engineers. [6](#0-5) 

However, I could not fully verify from the available index whether: (1) each precompile call site actually constructs a **new** `BalanceHandler` per invocation (via `BalanceHandlerFactory.NewBalanceHandler()`) rather than reusing one instance across a nested call chain, and (2) whether the existing test asserts a failing (bug-reproducing) outcome or a passing (already-fixed) outcome — the test file I could read only shows event-count assertions without balance-desync assertions in the visible excerpt, and I was unable to open `precompile.go` / `staking.go` in the final iteration to confirm handler lifecycle per call. Given the ambiguity, I cannot confirm with certainty whether this is a live, unpatched issue or a already-mitigated scenario the test now passes against a fix — flagging this explicitly as unresolved due to tool/iteration limits.

### Recommendation
- Ensure a fresh `BalanceHandler` (via `BalanceHandlerFactory.NewBalanceHandler()`) is instantiated per precompile call frame rather than being shared/reused across nested or re-entrant precompile invocations, or make the event-index tracking re-entrant-safe (e.g., use a stack of cursors instead of a single `prevEventsLen` field).
- Add an invariant check that reconciles `StateDB` balance against `bankKeeper.SpendableBalance` at the end of every top-level EVM message execution (not just individual precompile calls), failing/reverting the transaction if a divergence is detected.
- Extend the existing `evmd/tests/integration/balance_handler/balance_handler_test.go` suite to explicitly assert bank-vs-StateDB balance equality after nested precompile calls (not just event counts), across all value-moving precompiles (staking, distribution, gov, ics20, slashing, erc20, werc20).

### Proof of Concept
Not independently reproduced against live code because I could not read `precompiles/common/precompile.go` or `precompiles/staking/staking.go` in the final tool iteration to confirm exact handler construction/call-site wiring. The existing repository test `TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go` already provides a template: it deploys a caller contract that recursively invokes a debug precompile (`callback`) which internally triggers repeated bank-affecting precompile calls, then inspects emitted event counts. A complete PoC would extend this test to compare `stateDB.GetBalance(addr)` against `bankKeeper.SpendableCoin(ctx, addr, denom)` for the caller/receiver addresses after the recursive call completes and assert they diverge, using a real value-moving precompile (e.g., staking `Delegate`/distribution `WithdrawDelegatorRewards`) nested inside another precompile call from a Solidity caller contract instead of the debug precompile.

```go
// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```

```go
// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
```
