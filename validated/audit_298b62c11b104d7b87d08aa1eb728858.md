### Duplicate `ReceivedOutput` inputs are counted as separate funds without deduplication - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a vector of `ReceivedOutput`s and independently converts each entry into a transaction input and a prevout entry, without checking whether two entries reference the same `OutPoint`. Consequently, the same UTXO is counted once per duplicate in `input_sat`, is serialized once per duplicate in `tx.input`, and is signed once per duplicate in `TransactionMachine`.

An unprivileged caller can reach this path through `ReceivedOutput::read`, which accepts an offset, output, and outpoint from untrusted bytes, followed by `SignableTransaction::new` and `multisig`. This is analogous to repeatedly distributing the same balance because a consumed contribution is never recorded.

### Finding Description
The constructor computes spendable value by summing every supplied `ReceivedOutput`: [1](#0-0) 

It then stores every corresponding claimed prevout: [2](#0-1) 

There is no `HashSet<OutPoint>` or equivalent membership check. `multisig` verifies only that the prevout script corresponds to the offset-derived key; it does not establish that the claimed outpoint is unique, exists, or has the encoded amount: [3](#0-2) 

`TransactionSignMachine::sign` subsequently creates a FROST signing operation for every serialized input: [4](#0-3) 

Thus `[output, output.clone()]` is treated as `2 * output.value()` even though only one spendable UTXO exists.

### Impact Explanation
This can cause the threshold signing path to produce signatures for a transaction materially different from the intended spend: duplicated inputs inflate apparent available funds, alter payment/change feasibility, and create an invalid transaction containing repeated `previous_output`s. The signed artifact is an unintended transaction relative to the wallet API’s contract that inputs represent spendable outputs.

The issue does not appear to yield a valid double-spend or direct theft: Bitcoin consensus rejects a transaction spending the same outpoint twice, and Taproot verification uses the actual UTXO amount rather than the unattested `ReceivedOutput.output.value`. The strongest demonstrated effect is therefore construction/signing of a malformed transaction and incorrect internal accounting. Under the requested acceptance criteria, this does not establish key recovery, a forged signature, or a valid transaction that steals funds.

### Likelihood Explanation
The input bytes are attacker-controllable because `ReceivedOutput::read` parses all three fields without deriving them from chain state or checking consistency: [5](#0-4) 

However, exploitation that depends on an integrator accepting untrusted serialized `ReceivedOutput`s and submitting the result to threshold signing appears to require caller misuse rather than a self-contained protocol vulnerability.

### Recommendation
Reject duplicate `OutPoint`s and preferably reject duplicate or inconsistent `(outpoint, script_pubkey, amount)` tuples in `SignableTransaction::new`. Where possible, make `ReceivedOutput` construction private or require authenticated scanner-produced values rather than accepting independently supplied values for signing.

### Proof of Concept
Conceptually:

```rust
// networks/bitcoin/src/wallet/send.rs
let inputs = vec![output.clone(), output];
let tx = SignableTransaction::new(
    inputs,
    &payments,
    Some(change),
    None,
    fee_per_vbyte,
);
```

For a single UTXO worth `v`, `input_sat` becomes `2v`, `tx.input` contains the same `previous_output` twice, and `prevouts` contains the same claimed output twice. The constructor currently permits this; a valid implementation should return an error such as `DuplicateInput`.
