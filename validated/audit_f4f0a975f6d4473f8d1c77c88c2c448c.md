### Title
Fee bypass via undecodable signer causes free execution while message is still charged as fully processed - (File: `modules/pallets/ismp/src/fee_handler.rs`)

### Summary
`WeightFeeHandler::on_executed` accrues weight and reports `Pays::Yes` for every processed message regardless of whether the fee was actually collected. If the `signer` bytes on a `Message::Request`/`Message::Response` fail to decode into a `Signature`, or the signature fails `verify_and_get_sr25519_pubkey`, `originator` becomes `None` and the `C::transfer` call is silently skipped with no fallback rejection or alternate fee source.

### Finding Description
In the loop over `messages`, the originator is derived purely from decoding attacker-supplied `signer` bytes: [1](#0-0) 

If decoding or verification fails, `originator` is `None`, and the subsequent block is a no-op: [2](#0-1) 

Yet `total_weight` was already accrued for this message before the originator resolution attempt, and the function unconditionally returns `Pays::Yes` with the full accumulated weight at the end: [3](#0-2) [4](#0-3) 

There is no fallback fee collection (e.g., from a relayer/submitter account) and no rejection of the message when the signer can't be resolved. This decouples successful, fee-liable execution from actual fee payment: the message is still processed and reported as `Pays::Yes`, but the treasury balance never increases for that message's fee.

### Impact Explanation
This breaks the reward/fee accounting invariant that every fee-liable executed message results in fee collection to the treasury. An attacker can craft `Message::Request`/`Message::Response` payloads with garbage `signer` bytes to get cross-chain messages processed for free, undermining relayer/treasury reward accounting described in the bounty's "bridged assets... relayer rewards, and bandwidth balances must move exactly once and only to the rightful beneficiary and amount" pivot. This is a logic/accounting attack matching the "Required Impacts" (broken reward accounting / logic attack), not excluded by the scope limits (it's reachable via ordinary message submission, not requiring a malicious relayer or privileged actor — the flaw is in the fee handler's decode/verify logic itself).

### Likelihood Explanation
High. Any unprivileged submitter of an ISMP message batch can set `signer` to arbitrary/invalid bytes; no additional privilege, timing, or infrastructure compromise is needed. The `Signature::decode` / `verify_and_get_sr25519_pubkey` calls are `Result`-returning and their failure paths are trivially reachable.

### Recommendation
When the originator cannot be resolved (decode or verification failure), the handler should not silently succeed with `Pays::Yes` and zero fee collected. Options:
- Reject the batch (return an error) so the message is not treated as processed, forcing correction of the fee source, or
- Fall back to charging a well-defined, always-resolvable payer (e.g., the relayer/extrinsic submitter account) for the fee when originator signature/decoding fails, or
- Only report `Pays::Yes`/full weight for the subset of messages whose fee was actually collected, and track/report the delta so weight and fee stay coupled.

### Proof of Concept
Construct a `MessageWithWeight` wrapping `Message::Request` with a `signer` field containing bytes that do not decode to a valid `Signature` (or that decode but fail sr25519 verification). Call `WeightFeeHandler::on_executed` with `POLICY = true` and a non-zero weight/fee. Observe: return is `Ok(PostDispatchInfo { actual_weight: Some(total_weight), pays_fee: Pays::Yes })` per [4](#0-3) , while no `C::transfer` occurred and the treasury account balance is unchanged, confirming execution is accepted/charged as fully processed with zero fee actually collected.
