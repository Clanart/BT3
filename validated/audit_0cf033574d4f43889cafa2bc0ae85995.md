### Title
Missing identity check on PedPoP commitment public keys allows a forged Schnorr proof-of-knowledge for the identity "zero" key - (File: crypto/dkg/pedpop/src/lib.rs / crypto/schnorr/src/lib.rs)

### Summary
The reported bug class — accepting a zero/"null" input where a meaningful value is required — maps directly onto Serai's DKG: `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs` never rejects the identity group element for `commitments[0]`, and `SchnorrSignature::verify`/`batch_statements` in `crypto/schnorr/src/lib.rs` contain no identity checks on the public key, nonce `R`, or scalar `s`. As a result, the Schnorr proof-of-knowledge that is supposed to bind each PedPoP participant to knowledge of their polynomial's constant coefficient can be trivially forged when the submitted commitment is the identity point — the exact analog of a "zero address" passing an unchecked setter.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `Commitments::read` deserializes `params.t()` group elements plus a `SchnorrSignature` without any semantic validation: [1](#0-0) 

`verify_r1` then uses `msg.commitments[0]` as the public key for the proof-of-knowledge and batch-verifies `msg.sig` against it: [2](#0-1) 

The verification math lives in `SchnorrSignature::batch_statements`, which queues `R + c·A − s·G == 0`: [3](#0-2) 

If `A = commitments[0] = identity` and the attacker supplies `R = identity, s = 0`, the statement reduces to `identity + c·identity − 0·G == identity`, which passes for **any** challenge `c`. `SchnorrSignature::read` (lines 51–53) happily deserializes the identity `R` and zero `s`; `C::read_G` enforces canonicity, not non-identity. Neither `verify_r1` nor `share_verification_statements` checks for identity commitments, so the attacker's commitment vector is inserted into `commitments` and used normally.

This mirrors the UmamiPriceFeed finding exactly: a zero/identity input is accepted where the protocol's security depends on it being a real value (there: gov/fee address; here: the PoK public key for a participant's secret coefficient).

### Impact Explanation
The PedPoP proof-of-knowledge exists to prevent rogue-key/cancellation attacks on the DKG: it forces each participant to prove they know the discrete logarithm of `commitments[0]` (the constant coefficient of their polynomial). With the identity-key forgery, a participant can register a commitment whose constant coefficient is not proven — the PoK check becomes vacuous for them. Concretely, a participant can broadcast `commitments[0] = identity` (i.e., a polynomial with zero constant term) with a forged signature, meaning they contribute nothing to the group key while still participating fully, receiving and generating shares that pass `share_verification_statements`. More generally, the accept criterion "a forged proof" is met: a proof attesting to knowledge of a discrete logarithm is accepted despite the prover demonstrably needing no such knowledge. The strength of the impact scales with how much the identity/unproven commitment undermines the rogue-key guarantee in multi-adversary settings, which is why this is Medium rather than High.

### Likelihood Explanation
Reachability is straightforward: `Commitments::read` consumes untrusted bytes from peers during round 1 of the DKG (`SecretShareMachine::generate_secret_shares` → `verify_r1` over a `HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>` supplied by counterparties). Any participant — an unprivileged party sending protocol messages — can submit the identity point and the trivial forgery. Deterministic, no special positioning required beyond being a DKG participant, consistent with Medium likelihood.

### Recommendation
Reject the identity element when reading/validating commitments:

- In `Commitments::read` (or at the top of `verify_r1`), return `InvalidCommitments` if any `commitments[j]` — at minimum `commitments[0]` — `is_identity()`.
- Defense in depth: in `SchnorrSignature::read`/`verify`/`batch_statements`, reject `R = identity`, `s = 0` when the public key is identity, or more simply reject identity public keys at every call site that treats a Schnorr signature as a proof of knowledge (PedPoP `verify_r1`, `AdditionalBlameMachine::new`, and the encryption-key registration in `crypto/dkg/pedpop/src/encryption.rs`, which should also be audited for the same missing check on the ECDH key/PoK).

### Proof of Concept
```
// Attacker's round-1 Commitments message for participant l:
//   commitments[0] = identity encoding (all-zero repr if canonical for C)
//   commitments[1..t] = any points, e.g. j * G
//   sig = SchnorrSignature { R: identity, s: 0 }
//
// In verify_r1:
//   msg.sig.batch_verify(rng, &mut batch, l, msg.commitments[0], challenge)
// queues the statements:
//   (1, R) + (c, commitments[0]) + (-s, G)
//     = identity + c*identity + 0*G
//     = identity  →  passes batch verification
//
// The forged PoK is accepted; the participant's constant coefficient
// is never proven, yet their commitments are inserted and used for
// share verification and group-key derivation.
```

The check `multiexp_vartime(&[...]).is_identity()` at `crypto/schnorr/src/lib.rs:109` returns `true` for this input regardless of `challenge`, since every term involving the challenge or public key is multiplied by identity.

Note on scope certainty: I verified the deserialization and verification paths shown above, but did not fully enumerate every downstream consumer (e.g., `encryption.rs`'s key-registration PoK may share the same missing check and should be audited). The core forgery — identity public key accepted by `SchnorrSignature` verification and reachable via `Commitments::read` → `verify_r1` — is confirmed by the cited code.

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
