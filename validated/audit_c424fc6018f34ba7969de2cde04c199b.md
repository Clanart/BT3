## Analysis

The key finding: `getRepositoryType()` extracts a path directly from Git's stderr message via regex `/fatal: detected dubious ownership in repository at '(.+)'/` [1](#0-0) , and this attacker-influenceable path string is what gets passed to `addSafeDirectory()` when the user clicks "Trust Repository" in `add-existing-repository.tsx` and `missing-repository.tsx` [2](#0-1) [3](#0-2) . `addSafeDirectory` writes that path unconditionally into the **global**, permanent `.gitconfig` `safe.directory` list [4](#0-3) , with no verification that the value matches the path the user actually intended to trust, and no later removal/reset regardless of what happens afterward. This is structurally the same invariant break as the reported contract bug: a broad, standing grant of trust/allowance is created as a side effect of an operation and is never scoped down or revoked if the operation's context turns out to be different from what the user approved.

### Title
Unvalidated Git-reported path is persisted verbatim to global `safe.directory` allow-list when trusting a repository - (File: app/src/lib/git/config.ts, app/src/lib/git/rev-parse.ts, app/src/ui/add-repository/add-existing-repository.tsx)

### Summary
When Desktop detects a "dubious ownership" repository, it parses the path Git prints in its `fatal: detected dubious ownership in repository at '<path>'` stderr message and, if the user clicks "Trust Repository", adds that exact string to the **global** `safe.directory` Git config via `addSafeDirectory()`. Git's own path can differ from the repository the user is actually adding (e.g., due to bind mounts, symlinked `.git` files, unusual `--git-dir`/`GIT_DIR` behaviour, or a repository nested/pointed via `.git` gitfile). Desktop never re-verifies that the trusted path equals the folder the user chose before persisting it, and once written the exception is never scoped to that operation or removed later — mirroring the reported smart-contract pattern of granting an approval/allowance as a side effect that is never reset if the underlying operation's assumptions don't hold.

### Finding Description
`getRepositoryType()` runs `git rev-parse --is-bare-repository --show-cdup --git-dir` and, on the "dubious ownership" failure path, extracts the path solely via regex parsing of Git's own stderr string [1](#0-0) . This value is stored as `repositoryUnsafePath`/`unsafePath` in component state [5](#0-4) [6](#0-5) .

When the user clicks "Trust Repository" / "add an exception for this directory", `onTrustDirectory` calls `addSafeDirectory(repositoryUnsafePath)` directly — using the *Git-reported* path, not the path the user typed or navigated to [2](#0-1) . `addSafeDirectory` then writes this value to the user's **global** `.gitconfig` via `git config --global --add safe.directory <value>` [7](#0-6) .

The broken invariant: "trust" is supposed to be a scoped, user-confirmed decision about a specific directory the user opened. Instead, the trusted value is (a) sourced from a string Git itself computed/printed for the repository under test (which can diverge from the user's chosen directory when the working tree is reached indirectly, e.g. via a `.git` gitfile redirecting to another location, a submodule, or a worktree), and (b) once added, persists globally and forever — there is no path to revoke it if it later turns out to be the wrong/broader directory, and no confirmation step showing the user the literal value about to be trusted. This is the same class of bug as the contract's "allowance not reset on failed trade": a privileged, standing grant (git's blanket permission to treat a directory as safe — which per the app's own copy in the UI "may automatically execute files in the repository" [8](#0-7) ) is created and left in place without validating it matches the intended, narrower scope, and without any mechanism to reset/remove it afterward.

Existing guards do not stop this: `validatePath()` re-checks the *user's original path* after trusting, not whether the value that was actually written to `safe.directory` equals that path [2](#0-1) . There is no diffing/confirmation between `repositoryUnsafePath` and `path`, and `addGlobalConfigValueIfMissing` only dedups identical strings — it performs no sanity/allow-list check on the value being added [9](#0-8) .

### Impact Explanation
`safe.directory` in Git exists specifically to prevent automatic execution of repository-controlled files (hooks, `.gitattributes`-driven filters, etc.) for directories the current user doesn't own — the in-app copy explicitly says "Adding untrusted repositories may automatically execute files in the repository" [10](#0-9) . If the value written to this global allow-list can be broader or different than the directory the user actually inspected and intended to trust (because it's sourced from Git's own diagnostic string rather than the confirmed user-selected path, and because the value once written is never re-validated or revoked), a single trust action can silently authorize code execution for a directory that is not the one the user reviewed. Because the setting is global and persistent, this creates a durable state change with no expiry, no per-repository scoping, and no way for the user to know exactly what string was written unless they open their global `.gitconfig` manually.

### Likelihood Explanation
Requires a Desktop user to encounter an "unsafe repository" prompt (which normally happens when opening/adding a repo owned by a different account, e.g. after cloning into a shared/mounted location, or receiving a repository directory from elsewhere) and click "Trust Repository". This is a normal, expected user flow already built into the product (not a contrived attack step), so the likelihood of the flow being exercised is moderate to high for users who work with shared/mounted/cloned directories. The exploitability specifically hinges on whether Git's dubious-ownership path can be made to diverge from the directory the user opened (via `.git` gitfile redirection, submodules, or symlinks) — this divergence was not verified by tool inspection alone and is flagged as uncertain below.

### Recommendation
- Before calling `addSafeDirectory`, verify that the path reported by Git (`repositoryUnsafePath`/`unsafePath`) resolves to the same real path as the directory the user opened (`resolve`/`realpath` comparison), and refuse or warn if they differ.
- Show the user the literal path string that will be added to `safe.directory` before writing it, rather than trusting it silently.
- Avoid writing to the global config when possible; prefer a scope tied to the specific repository/session, and provide a UI affordance to review/remove previously trusted directories.
- Add regression tests that simulate a dubious-ownership path different from the working directory path to confirm Desktop does not blindly trust it.

### Proof of Concept
Full exploitation requires demonstrating a concrete way to make Git's `dubious ownership` stderr path diverge from the user-opened directory (e.g., via a `.git` file `gitdir:` redirect to a different-owner path, or a nested/linked worktree). This divergence was not confirmed with a runnable test in the available tooling — I was only able to confirm from local code that (1) the value is regex-parsed straight from Git's stderr, (2) it is written unmodified and unconfirmed into the **global** `safe.directory` list, and (3) there is no re-validation step tying the persisted value back to the user's chosen path. A Devin session with terminal/filesystem access would be needed to construct a `.git` gitfile or worktree scenario and verify whether `unsafeMatch[1]` can be made to differ from the directory the user selected in the "Add Existing Repository" dialog. /**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
