### Title
Missing subtraction of not-yet-locked tier reward allows repeated `incentiveDeposit(_mode=2)` calls in one transaction to mint excess vlMGP - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit()` computes a tiered `vlMGP` reward from `getRewardAmount()`, based on the caller's *current* `mWomSV` locked balance, and then applies a flat "50% more bonus" doubling for `_mode == 2` before minting the reward via `vlMGP.lockFor()`. There is no per-epoch/per-call guard (analogous to the missing `onlyNewEpoch` in the original report's `Voter.poke()`), so an attacker contract can call `incentiveDeposit` many times in a single atomic transaction, each time re-triggering the tier-reward + bonus computation and reward mint.

### Finding Description
`getRewardAmount()` reads the account's live state via `mWomSV.getUserTotalLocked(_account)` [1](#0-0) , and `incentiveDeposit()` calls this *before* performing `_deposit()`, then unconditionally doubles the result for lock mode and mints it as vlMGP: [2](#0-1) 

The tier-diff logic in `getRewardAmount`/`calDoubledCounted` is meant to prevent double-crediting the same locked-balance bracket across multiple calls, by subtracting a value derived from the account's `mWomSV`-locked total *before* the current call's deposit (`calDoubledCounted`) [3](#0-2) . However, this bracket-based diffing is only correct for the base (non-lock) reward; for `_mode == 2` the function applies a flat `rewardToSend = rewardToSend * 2` bonus on top *after* the tier diff has already been computed [4](#0-3) . Because this 50% bonus multiplier is applied per call rather than being amortized/tracked across the account's cumulative locked balance, splitting a single large deposit into many small `incentiveDeposit(_mode=2)` calls within one transaction (via a contract loop) changes the total reward compared to a single call with the full amount — the tier boundary crossing arithmetic in `calDoubledCounted` is evaluated repeatedly against small deltas, and the bonus doubling compounds the rounding/tier bucket effects on each call, allowing more vlMGP to be minted for the same net WOM deposited than the intended tiered-multiplier schedule allows.

This mirrors the reported bug class: a state-mutating function reachable by an ordinary wallet/contract, lacking any once-per-transaction or once-per-epoch restriction, where the reward computed from "current locked balance" is not properly reconciled against repeated calls in the same transaction, permitting reward inflation and minting of a governance/incentive token (vlMGP, minted via `lockFor`) beyond the intended amount.

### Impact Explanation
`vlMGP` is a governance/lock token used for voting weight (`WombatBribeManager.vote`) and unlocking privileges; over-minting it via `ArbWomUp3` directly inflates a user's voting power and locked-token balance beyond what their real WOM deposit entitles them to, resulting in theft of protocol incentive funds (the `mgp` balance held by `ArbWomUp3`, drained faster/further than intended) and manipulation of downstream voting power.

### Likelihood Explanation
Exploitation requires only an unprivileged wallet (via a simple attacker contract looping the call) and depends on the deployed `rewardTier`/`rewardMultiplier` configuration; the practical magnitude of the inflation depends on tier bucket boundaries chosen by the admin, so the concrete extractable profit is configuration-dependent and could not be fully quantified from static review alone.

### Recommendation
Track cumulative reward already granted per account (similar to `claimedReward` in `ArbWomUp`/`ArbWomUp2`) instead of deriving the reward purely from live `mWomSV` balance deltas within `ArbWomUp3`, and apply the lock-mode bonus consistently against the account's total cumulative reward rather than per-call, so splitting deposits into multiple calls in one transaction cannot yield more total reward than a single equivalent-sized call.

### Proof of Concept
Not independently reproduced against a live fork in this review; the vulnerability is inferred from static analysis of `getRewardAmount`, `calDoubledCounted`, and `incentiveDeposit` in `wombat/ArbWomUp3.sol`. A concrete PoC would deploy an attacker contract that calls `incentiveDeposit(smallAmount, ratio, false, 2)` N times in a loop within one transaction (approving/transferring WOM incrementally) and compare the total vlMGP minted vs. a single `incentiveDeposit(N*smallAmount, ratio, false, 2)` call, expecting the split-call total to exceed the single-call total due to the compounding bonus/tier-diff rounding described above.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

            i++;
