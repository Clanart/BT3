### Title
Unchecked fee-rate multiplication can wrap the required fee and authorize an unintended Bitcoin spend - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` calculates the required transaction fee with unchecked `u64` multiplication. A sufficiently large caller-controlled `fee_per_vbyte` causes the product to wrap to a small value, bypassing the intended funds and fee checks. The resulting transaction is then signed even though its actual fee is the entire difference between inputs and outputs. [1](#0-0) [2](#0-1) 

### Finding Description
`fee_per_vbyte` and `vbytes` are multiplied directly at `send.rs:206`. In release builds, an overflowing `u64` multiplication wraps rather than producing an error. [3](#0-2) 

The wrapped `needed_fee` is compared against the minimum relay fee and added to the requested payments when checking whether the inputs are sufficient. [4](#0-3) 

When no change output is requested, the documented behavior is to send all leftover input value to the transaction fee. [5](#0-4)  Consequently, `needed_fee` can report a small wrapped amount while `fee()` later returns the much larger `sum(inputs) - sum(outputs)`. [6](#0-5) 

The transaction is subsequently signed over Taproot sighashes committing to all prevouts and the malformed output set. [7](#0-6)  Completion places those signatures into the transaction witnesses. [8](#0-7) 

### Impact Explanation
An attacker who can supply the transaction-construction inputs can cause the threshold wallet to produce a valid signed transaction paying an excessive miner fee instead of rejecting the transaction as unaffordable. [9](#0-8)  This produces a signature for a materially different economic transaction than the wrapped `needed_fee` indicates, potentially destroying spendable wallet funds. [6](#0-5) 

### Likelihood Explanation
The fee rate, payment list, change option, and input set are ordinary inputs to `SignableTransaction::new`. [9](#0-8)  A requester does not need any private key material or validator privileges; they only need to influence a transaction that the multisig is asked to sign. [10](#0-9) 

### Recommendation
Use checked arithmetic for every monetary calculation:

- Calculate `needed_fee` with `fee_per_vbyte.checked_mul(vbytes)` and reject on overflow.
- Calculate `payment_sat + needed_fee` with `checked_add` and reject on overflow.
- Prefer checking `input_sat - payment_sat >= needed_fee` only after first proving `input_sat >= payment_sat`.
- Apply the same checked-arithmetic treatment to `fee_with_change`.
- Add regression tests with fee rates near `u64::MAX / vbytes`.

### Proof of Concept
For a transaction whose estimated size is exactly 128 vbytes, choose:

```text
fee_per_vbyte = (2^64 + 128) / 128
              = 144115188075855873
```

The calculation becomes:

```text
fee_per_vbyte * 128 mod 2^64 = 128
```

Thus `needed_fee` is 128 satoshis despite the supplied rate being approximately `1.44e17` satoshis/vbyte. [11](#0-10) 

Use one input worth `100_000_000` satoshis, one payment worth `50_000_000` satoshis, and no change address. The funds check compares `100_000_000` against `50_000_000 + 128`, so it succeeds. [12](#0-11)  The final transaction nevertheless pays `49_999_872` satoshis as its actual fee because all leftover funds become fee when no change output exists. [13](#0-12) 

`TransactionSignMachine::sign` then signs the Taproot key-spend digest for that transaction, and `complete` inserts the resulting Schnorr signatures into the witnesses. [14](#0-13) [8](#0-7)
