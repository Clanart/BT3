### Title
Fee/weight accounting in `SignableTransaction::new` ignores the OP_RETURN data output, allowing construction of under-fee or over-weight transactions that cannot be relayed — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the DepositReceipt bug — where a fixed, scale-insensitive quantity (always swapping 100 tokens) made a validation path revert for high-value assets — `SignableTransaction::new` computes transaction weight, vbytes, `needed_fee`, and the max-standard-weight check over `payments` only, permanently omitting the OP_RETURN data output that is pushed into the real transaction. An unprivileged party who can cause `data` bytes to be included in an out-transaction can produce a transaction whose true fee/weight differs from the checked values, yielding a signed transaction that is either below the minimum relay fee or above `MAX_STANDARD_TX_WEIGHT` and therefore unrelayable — funds become stuck (DoS), mirroring the "trapped deposits / impossible liquidation" impact of the original report.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at `send.rs:194-202`, **before** the weight calculation at `send.rs:204`:

```rust
// send.rs:194-202 — data output pushed into the real tx
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}

// send.rs:204 — weight/vbytes computed from `payments` only, NOT `tx_outs`
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (send.rs:62-127) builds a dummy transaction whose outputs are derived solely from `payments` (plus an optional change output). The OP_RETURN output — up to ~80 bytes of pushed data plus output overhead — is never included. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) and `fee_with_change` (send.rs:227) both understate the fee the signed transaction actually requires. The minimum-relay check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (send.rs:211) is evaluated against the understated vbytes, so a transaction can pass this check yet actually pay less than the relay minimum once the OP_RETURN output's vbytes are accounted (the *paid* fee = `inputs - outputs` stays the same while the real vsize grows, dropping the effective feerate).
2. The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (send.rs:241) uses `weight` that excludes the data output. A `payments` set sized just under the limit plus up to 80 bytes of OP_RETURN data can push the real transaction over `MAX_STANDARD_TX_WEIGHT`, making it non-standard and rejected by node mempools even though Serai signs it.
3. Symmetrically, the dust comparison for payments (`send.rs:165-169`) is fine, but the *change* decision at `send.rs:228-234` uses the wrong `fee_with_change`, so the change output may be omitted when it would have been creatable (harmless) — the harmful direction is when including change with data results in actual fee paid < min relay.

The `data` parameter is reachable from untrusted inputs: it flows from `OutInstruction` data (user-supplied payload destined for external chains) into the transaction the threshold signs, i.e., bytes an unprivileged party causes to be signed — the exact "public input" surface the rules require. The real signed transaction is assembled at send.rs:246-251 including `tx_outs` (with OP_RETURN), so the discrepancy between the checked dummy and the signed transaction is real.

### Impact Explanation
A signed out-transaction that is below the effective minimum relay feerate or over the standard weight limit is rejected by Bitcoin Core's mempool policy. Because `Prevouts::All` and the sighash commitment (send.rs:375-389) bind signatures to this exact transaction, the signatures cannot be trivially republished; the withdrawal is stuck until a new ceremony with corrected fee/weight is run — a liveness denial identical in shape to the original finding's "deposits permanently trapped / liquidation impossible". Sized correctly by the attacker, this is deterministic.

### Likelihood Explanation
Requires the attacker to supply `data` (up to the 80-byte cap at send.rs:171) to an out-instruction and to influence payment amounts/count so the dummy-weight sits near a policy boundary. That is achievable purely with public inputs to the signing pipeline; no validator compromise or leaked key needed. Severity: Medium — liveness DoS on withdrawals rather than direct theft, matching the original report's dominant impact.

### Recommendation
Compute `weight`/`vbytes`/`needed_fee` (and the change-fee variant) over the actual output set being signed, i.e., pass the already-constructed `tx_outs` (including the OP_RETURN output and, when applicable, the change output) to `calculate_weight_vbytes` — or append the data output inside the weight estimation itself. Optionally, after building `self.tx`, recompute `tx.weight()`/`get_virtual_tx_size` on the real transaction and re-assert `needed_fee` and `MAX_STANDARD_TX_WEIGHT` against it, so the checks can never diverge from the signed artifact.

### Proof of Concept
1. Call `SignableTransaction::new` with inputs sufficient for payments+fee, no change, `payments` sized so that `calculate_weight_vbytes(inputs, payments, None)` returns `weight == MAX_STANDARD_TX_WEIGHT - ε` (passes the check at send.rs:241).
2. Supply `data = vec![0u8; 80]` (passes the `TooMuchData` check at send.rs:171).
3. The returned `SignableTransaction` contains the OP_RETURN output in `tx.output` (send.rs:250), but `weight`/`needed_fee` were computed without it. The resulting signed transaction exceeds `MAX_STANDARD_TX_WEIGHT` and/or pays an effective feerate below the minimum relay fee, and is rejected by Bitcoin Core's mempool — the threshold-signed withdrawal is unbroadcastable.
