### Title
Webhook shop-domain spoofing via unauthenticated `X-Shopify-Shop-Domain` header enables cross-shop uninstall/data mutation - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request solely by verifying that the raw request body's HMAC matches a digest computed with the app's single, app-wide client secret. It never verifies that the `X-Shopify-Shop-Domain` header — which downstream job code uses as the tenant identifier to look up and mutate a specific shop's record — is bound to that signature in any way. This is the same asymmetric-verification pattern as the reported blocklist bug: one side of a two-sided operation (the payload's authenticity) is checked while the other side (the domain the payload/job is attributed to) is not.

### Finding Description
`verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` only checks `hmac_valid?(request.raw_post)`: [1](#0-0) 

`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the digest using `ShopifyApp.configuration.secret`/`old_secret` — a single app-level secret shared across every shop that has the app installed, not a per-shop key: [2](#0-1) 

The `shop_domain` accessor exposed by the same concern simply reads the unauthenticated `X-Shopify-Shop-Domain` request header, which is never part of the HMAC computation (only `request.raw_post` is signed): [3](#0-2) 

The gem's own documentation and generated job templates instruct developers to trust this header directly to resolve the shop and perform privileged, shop-scoped mutations — including destroying the shop record on `app/uninstalled` and other webhook-driven writes: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the signing secret is a single app-wide value (not shop-specific), any merchant who has installed the app can capture one of their own legitimately-signed webhook deliveries (body + valid `X-Shopify-Hmac-SHA256`), and then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim shop's domain). `verify_request` will accept it because the HMAC check only validates that *some* request was signed with the app secret — it does not tie the signature to the domain header at all. The downstream job (as scaffolded by the gem's own generators) then does `Shop.find_by(shopify_domain: shop_domain)` using the attacker-controlled header and performs privileged actions (e.g., `shop.destroy` for `app/uninstalled`, or arbitrary webhook-body writes) against a shop the attacker does not own.

### Impact Explanation
An unrelated/unprivileged merchant (who only has legitimate access to their own shop's webhook traffic) can forge the tenant-identifying header to have the app perform actions attributed to a different, victim shop — a cross-shop write/integrity issue reachable from an anonymous-ish actor relative to the victim shop (no session, cookie, or OAuth token for the victim is required). Depending on the job implementation (uninstall jobs, data-mutation jobs following the documented/generated pattern), this can range from denial of service (deleting another merchant's `Shop` record, forcing reinstall/loss of stored tokens) to corrupting another shop's application data via replayed webhook bodies attributed to it.

### Likelihood Explanation
Requires the attacker to have their own legitimate app installation to obtain at least one validly-signed webhook body/HMAC pair (readily obtainable — install the app on a $0 dev store and observe any webhook, e.g. `app/uninstalled` fired on their own uninstall, or any topic with mostly-static/attacker-influenced body content). No secret material or Shopify-side compromise is needed; only the ability to relay an HTTP POST with modified headers to the app's own public webhook route. This is fully within the "webhook HMAC verification" unprivileged-analog category.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header as an implicit authorization boundary. Either:
- Cryptographically bind the domain to the verified payload (e.g., derive/verify shop identity strictly from the webhook body's own shop-identifying fields where available, or use Shopify's per-app but replay-window-limited nonce/timestamp plus topic+id dedup to prevent cross-shop replay), and/or
- Track and enforce that a given webhook `X-Shopify-Webhook-Id` is only ever attributed to the same `shop_domain` seen previously for that installation, rejecting mismatches, and/or
- Document explicitly (and enforce in the generator templates) that `shop_domain` from the header must not be trusted for authorization of destructive/privileged actions without additional shop-relationship validation (e.g., confirming the shop record's currently active access token was actually the one used to register that specific webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own development shop (`attacker.myshopify.com`), which is a normal, legitimate installation.
2. Attacker triggers or waits for any webhook delivery to their own endpoint (e.g., `app/uninstalled`, or any subscribed topic) and captures the raw POST body and the `X-Shopify-Hmac-SHA256` header Shopify sent — this HMAC is valid because it's signed with the single app-wide client secret configured in `ShopifyApp.configuration.secret`.
3. Attacker replays this exact body and HMAC header to the app's webhook endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `ShopifyApp::WebhookVerification#verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb:15-21`) recomputes the HMAC over the raw body using the app secret and finds it valid (the header isn't part of the signed data), so the request is accepted.
5. The generated job handler (`lib/generators/shopify_app/add_app_uninstalled_job/templates/app_uninstalled_job.rb.tt:8-19`) calls `Shop.find_by(shopify_domain: shop_domain)` with the attacker-supplied `victim.myshopify.com` and executes `shop.destroy`, deleting the victim's stored shop/session record without the victim's involvement.

Note: I could not verify inside this repository whether Shopify's underlying `ShopifyAPI::Webhooks::Registry.process` (used by the default `WebhooksController`) performs any additional shop-binding check beyond HMAC, since that logic lives in the external `shopify_api` gem dependency and is out of scope per the analysis rules; the finding above is scoped to the `ShopifyApp::WebhookVerification`/`PayloadVerification` concerns and the documented/generated custom-controller pattern, which are unambiguously part of this repository and unambiguously do not bind the domain header to the signature.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
