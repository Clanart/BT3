### Title
Scanner accepts sub-dust outputs as received funds that cost more to spend than they are worth - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` reports any transaction output paying to a registered `script_pubkey` as a `ReceivedOutput`, with no minimum-value check. This mirrors the reported bug class (`MIN_GNS_WEI_IN` too small to be meaningful): the "minimum" on the intake path is effectively zero, so an unprivileged party can send an arbitrarily small output (e.g., 1 satoshi) to the threshold-controlled address and have it recorded as received funds, even though spending it via `SignableTransaction` costs more in fees than the output is worth.

### Finding Description

`scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` matches — value is never inspected (wallet/mod.rs:199-214). `scan_block` extends this to every transaction, including the coinbase (wallet/mod.rs:221-227). There is no `DUST` floor on inputs anywhere in the crate: `SignableTransaction::new` enforces `*amount < DUST` (546) only on *outgoing payments* (send.rs:165-169), while any scanned `ReceivedOutput` — including a 0- or 1-sat output — is accepted as an input (send.rs:150-256).

The cost asymmetry is the analog of the division-truncating-to-zero reward: each consumed input adds ~230 weight units / ~57 vbytes of signature and prevout data (documented at processor/src/networks/bitcoin.rs:606-637, and embodied in `calculate_weight_vbytes`, send.rs:62-127). At any nonzero `fee_per_vbyte`, a scanned input worth less than `fee_per_vbyte * 57` is net-negative: including it burns more of the multisig's funds in fees than it contributes.

That this is a real gap rather than intended behavior is shown by the consumer side: the processor's scanner wrapper explicitly re-filters with `if output.balance().amount.0 >= N::DUST` (processor/src/multisigs/scanner.rs:564, with `N::DUST = 10_000` for Bitcoin, processor/src/networks/bitcoin.rs:638). The in-scope `Scanner`/`ReceivedOutput` API itself provides no such protection, so any direct user of the crate (the documented usage in networks/bitcoin/tests/wallet.rs:213-253 constructs `Scanner` and feeds its outputs into `SignableTransaction::new`) inherits the bug.

### Impact Explanation

An attacker can grief the wallet by sending many minimal-value outputs to the multisig's P2TR address. Each is reported as received balance but is economically unspendable: sweeping it costs more in transaction fees than it returns. If such outputs are fed to `SignableTransaction::new`, the transaction either fails with `NotEnoughFunds` or silently pays extra fee. This is a "funds reported received that are not spendable" condition, reachable purely with public inputs — an ordinary on-chain Bitcoin transaction the attacker sends.

The impact is bounded because the canonical consumer (the processor scheduler) re-checks `N::DUST` before acting on scanned outputs, so for the full Serai stack this is largely a wasted-fee / accounting-accuracy issue rather than theft. Against the crate's own API contract, however, the missing lower bound is a genuine defect: the wallet reports positive balance that can never be realized.

### Likelihood Explanation

Medium-low. Exploitation requires only sending dust transactions to a known deposit address — cheap and permissionless. However, the damage is limited to distorted accounting and wasted fees, and the primary in-tree consumer mitigates it with its own higher dust threshold, so the exposure is mostly to integrators using `Scanner`/`SignableTransaction` directly.

### Recommendation

Apply a minimum-value check inside `Scanner::scan_transaction`/`scan_block` (e.g., skip outputs with `value < DUST`, or better, a configurable threshold reflecting `fee_per_vbyte * input_vbytes`), so `ReceivedOutput` only ever represents economically spendable funds. Alternatively, expose the check as an explicit parameter and document that unscanned-by-filter outputs may be unspendable.

### Proof of Concept

```rust
// Attacker broadcasts a tx paying 1 sat to the multisig's P2TR script.
let dust_tx = Transaction {
    output: vec![TxOut {
        value: Amount::from_sat(1),
        script_pubkey: p2tr_script_buf(multisig_key).unwrap(),
    }],
    ..Default::default()
};

let scanner = Scanner::new(multisig_key).unwrap();
let outputs = scanner.scan_transaction(&dust_tx);

// Accepted and reported as a received output despite being unspendable at a profit.
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 1);

// Consuming it in SignableTransaction::new adds ~57 vbytes of input weight;
// at fee_per_vbyte = 1 the input costs ~57 sats to spend while contributing 1 sat,
// net-draining the transaction's other inputs.
```

The referenced lines: `scan_transaction` lacks any amount filter at `networks/bitcoin/src/wallet/mod.rs:199-214`, while the outgoing-side dust check exists at `networks/bitcoin/src/wallet/send.rs:165-169`, demonstrating the asymmetric minimum.

Caveat: I could not fully verify whether any other in-scope caller of `Scanner` compensates for the missing check; the processor's `N::DUST` filter at `processor/src/multisigs/scanner.rs:564` is out-of-scope code that mitigates the issue for the main pipeline but does not fix the crate-level API.
