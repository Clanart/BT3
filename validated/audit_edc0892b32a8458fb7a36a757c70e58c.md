Based on my investigation, I found a concrete, exploitable divergence between the two Sei signature-verification code paths that is analogous in root cause to the reported CVE (an authentication check that fails to validate a "null"/missing credential before it is used to authenticate a request).

### Title
Missing nil-pubkey guard in CheckTx signature verification causes a nil-pointer panic reachable by any unprivileged transaction sender - (File: app/ante/cosmos_checktx.go)

### Summary
The CheckTx-specific signature-verification path in `CheckSignatures` (`app/ante/cosmos_checktx.go`) omits the null-credential check that its DeliverTx counterpart, `SigVerificationDecorator.AnteHandle` (`sei-cosmos/x/auth/ante/sigverify.go`), explicitly performs. This missing check allows an attacker to submit a transaction whose signer account has never set an on-chain public key while also omitting the public key from the transaction's `SignerInfo`. `CheckPubKeys` accepts this combination and forwards a `nil` `PubKey` into `authsigning.VerifySignature`, which unconditionally invokes `pubKey.VerifySignature(...)` on the nil interface, causing a runtime nil-pointer-dereference panic in the CheckTx path.

### Finding Description
In `sei-cosmos/x/auth/ante/sigverify.go`, `SigVerificationDecorator.AnteHandle` explicitly guards against a missing credential: [1](#0-0) 

The Sei-specific CheckTx pipeline reimplements the same logic in `app/ante/cosmos_checktx.go` but drops this guard. `CheckPubKeys` treats an omitted pubkey (`pk == nil`) as always acceptable regardless of whether the account already has a stored pubkey: [2](#0-1) 

`CheckSignatures` then retrieves `signerAcc.GetPubKey()` — which can be `nil` for a fresh account that has only received funds and never itself broadcast a signed transaction — and passes it straight into `authsigning.VerifySignature` without any nil check: [3](#0-2) [4](#0-3) 

`authsigning.VerifySignature` unconditionally calls the interface method on the (possibly nil) `pubKey`: [5](#0-4) 

Calling a method on a truly nil `cryptotypes.PubKey` interface value causes a `runtime.Error` (nil pointer dereference) panic. `CosmosCheckTxAnte` installs a `defer/recover`, but the recovery handler only knows how to deal with out-of-gas panics and re-panics for anything else: [6](#0-5) [7](#0-6) 

This is the same class of bug as the reported CVE: a credential (secp256k1 pubkey / password-equivalent) that is `nil`/absent is not rejected before being used for authentication, and the missing validation is inconsistent between two code paths that are supposed to enforce identical authentication semantics (CheckTx vs. DeliverTx).

### Impact Explanation
Any unprivileged RPC client can submit a `CheckTx` transaction naming, as fee payer/signer, an account address that exists on chain (e.g., has previously received a bank transfer, giving it sequence 0 and an empty pubkey) but has never itself broadcast a signed transaction. By constructing the tx's `SignerInfo` with an omitted `PublicKey` (a normal, valid SDK optimization for "pubkey already known on-chain"), the attacker forces `CheckSignatures` to call `VerifySignature` with a nil pubkey, triggering a nil-pointer panic on the node's `CheckTx` handling path. Whether this crashes the node process or merely propagates an unrecoverable panic depends on whether an outer `baseapp` recovery middleware (`sei-cosmos/baseapp/recovery.go`) wraps this specific CheckTx entrypoint (`app/legacyabci/check_tx.go`) — I was not able to fully confirm this wrapping within the available context. At minimum this is a reliable, remotely-triggerable authentication-check bypass/inconsistency between CheckTx and DeliverTx; at worst (if uncaught by an outer recovery layer) it is a crash of default-configuration RPC/validator nodes processing `CheckTx`.

### Likelihood Explanation
High. Constructing a fresh, funded account that has never sent a transaction (so it has no on-chain pubkey) is trivial (e.g., have someone send it a bank transfer), and omitting the pubkey field in `SignerInfo` while setting sequence 0 is a normal, well-documented SDK transaction construction technique — no privileged access or special conditions are required.

### Recommendation
Add the same `pubKey == nil` guard used in `sei-cosmos/x/auth/ante/sigverify.go` (lines 269-271) to `CheckSignatures` in `app/ante/cosmos_checktx.go` immediately after `pubKey := signerAcc.GetPubKey()`, returning `sdkerrors.ErrInvalidPubKey` instead of proceeding to `VerifySignature`. Additionally, harden `HandleOutofGas` to convert any unexpected recovered panic into a normal ABCI error rather than re-panicking, so that CheckTx-time bugs degrade to rejected transactions rather than crashes.

### Proof of Concept
1. Fund address `A` via a normal bank-send from another account so that `A` exists on chain with `sequence = 0` and no stored pubkey (`acc.GetPubKey() == nil`).
2. Craft a transaction with `A` as sole signer/fee-payer, `SignerInfo.PublicKey = nil` (omitted), `Sequence = 0`, and any signature bytes in `SignatureV2.Data`.
3. Submit the transaction via the public `CheckTx`/`broadcast_tx` RPC endpoint.
4. `CheckPubKeys` accepts it (`pk == nil` branch) and returns the account with `nil` pubkey; `CheckSignatures` calls `authsigning.VerifySignature(nil, ...)`, which panics on `pubKey.VerifySignature(...)`; the panic is caught by `CosmosCheckTxAnte`'s deferred recover, but `HandleOutofGas` re-panics because the recovered value is not `sdk.ErrorOutOfGas`.

func HandleOutofGas(recoveredErr any, gasLimit uint64, gasConsumed uint64) error {
	switch rType := recoveredErr.(type) {
	case sdk.ErrorOutOfGas:
		log := fmt.Sprintf(
			"out of gas in location: %v; gasWanted: %d, gasUsed: %d",
			rType.Descriptor, gasLimit, gasConsumed)

		return sdkerrors.Wrap(sdkerrors.ErrOutOfGas, log)
	default:
		panic(recoveredErr)
	}
}
