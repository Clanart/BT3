Confirmed: neither `ShopifyApp::AppProxyVerification` nor `ShopifyApp::WebhookVerification`/`PayloadVerification` validate the freshness (age) of the signed payload — they only check the HMAC/signature correctness, never checking whether the `timestamp` param (or a nonce) is recent. This is the direct structural analog of the reported bug class (trusting externally-supplied signed data without checking a liveness/freshness signal before accepting it).

### Title
Missing timestamp/freshness validation in `AppProxyVerification` allows indefinite replay of valid signed app-proxy requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` only recomputes and compares the HMAC signature of the query string; it never checks that the `timestamp` parameter included in every genuine Shopify App Proxy request is recent. [1](#0-0) 

### Finding Description
Shopify signs App Proxy requests with an HMAC over the full query string, which includes a `shop`, `path_prefix`, and `timestamp` parameter. `verify_proxy_request` calls `query_string_valid?`, which strips the `signature` param, recomputes `calculated_signature` over the remaining params, and does a `secure_compare` against the provided signature. [2](#0-1) 

At no point is `timestamp` checked against the current time to reject stale requests. This is exactly analogous to the Chainlink oracle bug: the contract validated the *shape/source* of the price data but never validated its *freshness/liveness* before trusting it, allowing a stale reference value to be relied upon indefinitely. Here, the app validates the *authenticity* of the signed query string (that it was truly HMAC-signed by Shopify at some point) but never validates its *age*, so a request signed once by Shopify remains "valid" and will pass `verify_proxy_request` forever.

Since App Proxy requests are plain GET requests forwarded through the storefront to the app's public endpoint, any observer who captures one such URL (via browser history, logs, a shared link, a proxy, or network capture) can replay the exact same URL indefinitely — with the same `shop`, `path_prefix`, `timestamp`, and `signature` — and it will be accepted as freshly authentic by any controller including this concern (e.g. the generated `AppProxyController` and any other controller under the App Proxy namespace). [3](#0-2) 

The same missing-freshness pattern also exists in `PayloadVerification`/`WebhookVerification`, which only checks the `X-Shopify-Hmac-SHA256` header against the raw body with no timestamp/nonce check, but Shopify webhooks are only observable by the app itself (server-to-server, secret headers not typically exposed to a third party), so that path is weaker as an unprivileged analog than the App Proxy case, where the signed URL is exposed by design in the browser. [4](#0-3) 

### Impact Explanation
Any endpoint relying solely on `ShopifyApp::AppProxyVerification` for authentication of App Proxy requests will accept an arbitrarily old, previously-captured, validly-signed request replayed by an unrelated/anonymous party at any future time. If such an endpoint performs a state-changing action keyed off proxy request params (e.g., an action gated on `shop` identity, a discount/loyalty action, or any write), this is a forged/replayed signed request being accepted — a genuine authentication/integrity bypass for that channel, matching the "accepted forged signed request" class.

### Likelihood Explanation
Exploitability requires only that an attacker obtain one previously valid App Proxy request URL (these are ordinary GET requests visible in browser network logs, referrers, shared links, or intermediary proxies/CDNs), after which replay is trivial and works indefinitely since there is no expiry enforcement in the gem itself.

### Recommendation
Add a freshness check comparing `timestamp` (Unix epoch seconds, as documented by Shopify) against `Time.now`, rejecting requests older than a small tolerance window (e.g. a few minutes), similar to how `LoginProtection`/`TokenExchange` already enforce `check_session_expiry_date` for session tokens. [5](#0-4) 

### Proof of Concept
1. Observe (or otherwise obtain) one valid App Proxy request that a real storefront browser sent to `GET /app_proxy/...?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid>`.
2. At any later time (minutes, days, or longer), issue the identical GET request with the same query string from an unrelated client/IP.
3. `AppProxyVerification#verify_proxy_request` recomputes the same signature over the same params and `query_string_valid?` returns `true`; the request is processed as if freshly authentic. [6](#0-5)

```ruby
    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
