### Title
Bitcoin In-Instruction data silently dropped for consensus-valid OP_RETURN encodings (File: processor/src/networks/bitcoin.rs)

### Summary
The Real-Wagmi bug class is: the protocol demands an *optional* facet of an external interface (`ERC20::symbol`) and therefore rejects inputs that are fully valid under the specification. The analog in Serai lives in `Bitcoin::extract_serai_data`, which recognizes the In-Instruction payload only when the `OP_RETURN` output ends in a *single, minimally-encoded* data push. Any other consensus-valid (and even standard) `OP_RETURN` encoding — multiple pushes, non-minimal `PUSHDATA1`, or a trailing non-push opcode — causes the instruction data to be silently dropped while the deposited funds are still credited.

### Finding Description
`extract_serai_data` scans transaction outputs and, for each `is_op_return()` script, reads only `instructions_minimal().last()`, requiring it to be `Instruction::PushBytes` (processor/src/networks/bitcoin.rs:493-505). Two consequences:

1. **Multiple pushes.** `OP_RETURN <part1> <part2>` is a valid, standard construction used by wallets that split data. Only `<part2>` is extracted as `data`, so the concatenated payload is lost.
2. **Non-minimal pushes.** `instructions_minimal()` yields `Err` for `PUSHDATA1`-encoded pushes that could be direct pushes (produced by many wallet implementations for data near/over the minimal-push boundary). `last()` then returns `Some(Err(_))`, which fails the `PushBytes` match and the output is skipped entirely.

The fallback path (lines 508-519) only inspects *inputs* for a `SHA256 <hash> EQUALVERIFY` witness pattern, so it does not recover a malformed-encoding `OP_RETURN`. The result is `data = vec![]` attached to the `Output` (lines 730-735). Downstream, `instruction_from_output` fails `Shorthand::decode` on the empty data and returns `None` for the instruction (processor/src/multisigs/mod.rs:66-72), so the output is routed to `PlanFromScanning::Refund` if an origin exists, or effectively donated.

Additionally, the code accepts the *first* `OP_RETURN` output that decodes, while the spec (`spec/integrations/Bitcoin.md:15`) defines the instruction as "the transaction's *last* output" — a mismatch in the other direction, but reinforcing that the parsing does not match the documented format.

### Impact Explanation
An unprivileged depositor can send a fully valid Bitcoin transaction paying the multisig's external address whose `OP_RETURN` uses any encoding other than a single minimal push. The deposit is recognized and credited (the scanner matches `script_pubkey` only), but the accompanying `InInstruction` is never executed. The user loses the aggregation fee (`2 * COST_TO_AGGREGATE` is deducted regardless) and, if the origin can't be parsed, the funds. This mirrors the Real-Wagmi finding: a core protocol feature (inbound instructions) is unavailable for a class of valid inputs because the implementation assumes a narrower interface than the spec guarantees.

### Likelihood Explanation
Anyone can craft such a transaction; some libraries habitually emit `PUSHDATA1` for all pushes or split long payloads. No privileged position is required.

### Recommendation
Parse the `OP_RETURN` script by concatenating all push-data opcodes after `OP_RETURN` (using `instructions()` rather than `instructions_minimal()`, tolerating non-minimal pushes), and enforce the spec's "last output" position. Alternatively, attempt `Shorthand::decode` against each candidate payload extraction.

### Proof of Concept
Conceptual: build a deposit transaction with output `OP_RETURN PUSHDATA1(<encoded Shorthand>)` (non-minimal for <76-byte payloads) or `OP_RETURN PUSH(<part1>) PUSH(<part2>)`. `scan_transaction` credits the deposit to the external script; `extract_serai_data` returns `vec![]` or a truncated payload; `instruction_from_output` logs "wasn't valid shorthand" and the instruction is dropped.
