### Title
Negative/malformed length in Java Lite `ArrayDecoders.skipField` can revert to an infinite skip loop on crafted `START_GROUP` payloads - (`java/core/src/main/java/com/google/protobuf/ArrayDecoders.java`)

### Summary
The Shardeum report is a classic "attacker-controlled signed value bypasses a bounds check and is fed into a loop whose increment becomes a no-op / never satisfies the exit condition" bug. The closest genuine Protobuf analog is the historical Java Lite-runtime bug in `ArrayDecoders.skipField`, where a crafted 5-byte varint length (e.g. `-6`) for a length-delimited sub-field nested inside a `START_GROUP` field caused `skipField` to loop without terminating, hanging the parsing thread on a small, valid-looking binary payload. This is documented by the still-present regression tests `testException_skipField_negativeSize_crafted` and `testException_skipField_infiniteLoop` in `java/core/src/test/java/com/google/protobuf/ArrayDecodersTest.java:364-384`.

### Finding Description
`ArrayDecoders.decodeVarint32`/`decodeLengthPrefixVarint` (`ArrayDecoders.java:67-123`) decode a raw varint into a Java `int` (`registers.int1`) without rejecting negative results at the varint-decode layer itself; negativity is only checked by individual callers (`decodeLengthPrefixVarint` at line 117 does check `length < 0` and throws `negativeSize()`). The invariant that failed in the historical bug class was that `skipField`'s handling of a length-delimited field nested within a group (tag wire-type `START_GROUP` → recursively skip inner tag `LENGTH_DELIMITED`) did not consistently route through that negative-size check before using the decoded length to advance the position/loop counter. A crafted length such as `-6` (encoded as the 5-byte varint `FA FF FF FF 0F`), when used as a skip/advance amount, can fail to move the cursor forward on every iteration of the wire-format skip loop (the analog of Shardeum's `i++` no-op on a value near the limits of the numeric type), so `skipField` never reaches `limit` and spins forever consuming CPU on the calling thread.

The exact same class of "attacker-controlled length value bypasses a range/sign check, then drives a loop counter that never converges" is present in the Shardeum bug: `fromBlock` is parsed from attacker input, escapes the `maxNumberOfOldBlocks` proximity check because it's assigned to the wrong variable, and is then used as a loop counter (`for (let i = fromBlock; ...; i++)`) that becomes a no-op due to floating point precision. The transferable invariant is: "a decoded/parsed length or index value from untrusted input must be validated for sign/range *before* being used to drive a bounded loop's termination condition; if that check is skipped or bypassed, the loop can become non-terminating and block the calling thread indefinitely (DoS)."

### Impact Explanation
If reachable, this causes a single-threaded (or worker-thread) infinite loop consuming 100% CPU while parsing a small (a few bytes), otherwise-valid-looking binary Protobuf payload submitted through any public API that calls `MessageLite.parseFrom`/`mergeFrom` in a Lite-generated message that uses `ArrayDecoders` (Android/Lite runtime). Analogous to the Shardeum impact, an attacker who can call any public message-parsing entry point that eventually reaches `ArrayDecoders.parseUnknownField`/`skipField` (e.g., an unknown/extension field wrapped in a group) could hang the parsing thread, denying service to that thread/connection. Unlike Shardeum's total network shutdown (single event-loop thread serving all requests), Java server/Android runtimes are typically multi-threaded, so the blast radius is a single request-handling thread rather than total process/network shutdown — this reduces severity from the "total network shutdown" analog to a single-thread hang, unless the calling architecture funnels all parsing onto one thread (e.g., a single-threaded event loop server built on top of protobuf-java-lite).

### Likelihood Explanation
This requires: (1) use of the Lite runtime path (`ArrayDecoders`), (2) an unknown/extension field structured as `START_GROUP` containing a nested length-delimited sub-tag with a maliciously encoded negative length, and (3) that the negative-length check present in `decodeLengthPrefixVarint` is not applied on the specific `skipField` code path exercised by that nested-group structure. The presence of dedicated regression tests (`testException_skipField_negativeSize_crafted`, `testException_skipField_infiniteLoop`) in this exact checkout indicates this exact scenario was identified and is actively tested — i.e., it corresponds to a **known, already-fixed** issue class rather than a currently-open zero-day in this codebase snapshot. I could not fully verify from the available index whether the fix (bounds/sign check) fully covers the `skipField` code path in `ArrayDecoders.java` in this checkout, because the file's `skipField` function body itself was not retrievable via the available search/read tools (index truncation) — only its call sites and the associated tests were visible.

### Recommendation
- Ensure every varint-decoded length used in `ArrayDecoders.skipField` (and any other loop that advances a position/counter based on a decoded length) is checked for `< 0` and for exceeding the remaining buffer (`limit - position`) immediately after decoding, before it is used to compute the next loop position — mirroring the check already present in `decodeLengthPrefixVarint` (`ArrayDecoders.java:113-123`).
- Add/keep loop invariants that guarantee monotonic progress (`position` strictly increases each iteration) or an explicit iteration/byte bound, independent of the sign of the decoded length, so a malformed length cannot produce a non-terminating loop.
- Keep the existing regression tests (`ArrayDecodersTest.java:364-384`) as permanent CI guards, and add fuzz coverage specifically targeting `START_GROUP`-wrapped length-delimited unknown fields with boundary/negative varint lengths.

@Test
public void testException_skipField_negativeSize_crafted() {
  // -6 encoded as 5-byte varint
  byte[] data = new byte[] {(byte) 0xFA, (byte) 0xFF, (byte) 0xFF, (byte) 0xFF, (byte) 0x0F};

      InvalidProtocolBufferException.class,
      () -> ArrayDecoders.skipField(TAG, data, 0, data.length, registers));

@Test(timeout = 1000)
public void testException_skipField_infiniteLoop() {
  // Payload that triggers the infinite loop:
  // Byte 0: 0x0B (Start Group 1)
  // Byte 1: 0x12 (Length Delimited 2)
  // Byte 2-6: FA FF FF FF 0F (Length -6)
  byte[] data =
      new byte[] {0x0B, 0x12, (byte) 0xFA, (byte) 0xFF, (byte) 0xFF, (byte) 0xFF, (byte) 0x0F};
  assertThrows(
      InvalidProtocolBufferException.class,
      () -> ArrayDecoders.skipField(0x0B, data, 1, data.length, registers));
}

  static int decodeVarint32(byte[] data, int position, Registers registers) {
    int value = data[position++];
    if (value >= 0) {
      registers.int1 = value;
      return position;
    }
    return decodeVarint32(value, data, position, registers);
  }

  /** Like decodeVarint32 except that the first byte is already read. */
  static int decodeVarint32(int firstByte, byte[] data, int position, Registers registers) {
    int value = firstByte & 0x7F;
    final byte b2 = data[position++];
    if (b2 >= 0) {
      registers.int1 = value | ((int) b2 << 7);
      return position;
    }
    value |= (b2 & 0x7F) << 7;

    final byte b3 = data[position++];
    if (b3 >= 0) {
      registers.int1 = value | ((int) b3 << 14);
      return position;

    value |= (b3 & 0x7F) << 14;

      registers.int1 = value | ((int) b4 << 21);
      return position;

  static int decodeLengthPrefixVarint(byte[] data, int position, int limit, Registers registers)
      throws InvalidProtocolBufferException {
    position = decodeVarint32(data, position, registers);
    final int length = registers.int1;
    if (length < 0) {
      throw InvalidProtocolBufferException.negativeSize();
    } else if (length > limit - position) {
      throw InvalidProtocolBufferException.truncatedMessage();
    }
    return position;
  }
