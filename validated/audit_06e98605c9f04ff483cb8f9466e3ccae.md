### Title
Silent failure to credit EVM surplus to the module account causes permanent fund loss / supply accounting mismatch - (File: x/evm/keeper/abci.go)

### Summary
`Keeper.EndBlock` computes a `surplus` amount (in wei precision) accumulated from every EVM transaction's ante/deferred fee processing during the block, and attempts to credit that surplus back to the `evm` module account via `BankKeeper().AddCoins` (usei part) and `BankKeeper().AddWei` (wei remainder). If either of these credit operations returns an error, the code only logs the error and continues — it never rolls back or re-applies the surplus, and does not fail the block. [1](#0-0) 

This mirrors the reported bug pattern: an internal accounting value (`s_clientOnlyClRewards` in the report, here the surplus that was already debited from users/coinbase accounts during transaction processing) is treated as "distributed"/settled regardless of whether the corresponding fund-moving call actually succeeded.

### Finding Description
`surplus` is accumulated from two sources: `k.GetAnteSurplusSum(ctx)` (fee-related surplus recorded during the ante handler for every EVM tx in the block) and per-transaction `deferredInfo.Surplus` values collected during `EndBlock` from `k.GetAllEVMTxDeferredInfo(ctx)`. [2](#0-1) 

This surplus amount represents usei/wei that have already been subtracted or reserved from user or coinbase balances elsewhere in the pipeline (via `AddAnteSurplus`/ante fee logic and the coinbase-balance sweep at lines 124-133), on the assumption that it will be re-credited to the EVM module account at the end of the block. However, the actual crediting step:

```go
if surplus.IsPositive() {
    surplusUsei, surplusWei := state.SplitUseiWeiAmount(surplus.BigInt())
    if surplusUsei.GT(sdk.ZeroInt()) {
        if err := k.BankKeeper().AddCoins(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), sdk.NewCoins(sdk.NewCoin(k.GetBaseDenom(ctx), surplusUsei)), true); err != nil {
            logger.Error("failed to send usei surplus to EVM module account", "surplus", surplusUsei)
        }
    }
    if surplusWei.GT(sdk.ZeroInt()) {
        if err := k.BankKeeper().AddWei(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), surplusWei); err != nil {
            logger.Error("failed to send wei surplus to EVM module account", "surplus", surplusWei)
        }
    }
}
``` [1](#0-0) 

only logs on failure and swallows the error — exactly the "if `_sendValue` fails, don't just log and move on" bug class. No state variable tracking "surplus owed" is preserved for retry, and the `EndBlock` continues normally (no panic, no revert of the block), so any coins that were already subtracted upstream in the block (e.g., during fee-cap/refund handling in the ante decorator, `x/evm/ante/fee.go`, via `AddAnteSurplus`) are permanently lost from total accounted supply if `AddCoins`/`AddWei` fails.

Unlike a Solidity contract call, a Cosmos SDK message handler returning an error normally reverts the whole message's state changes. But `EndBlock` is not a message handler — it is deferred, non-reprocessable per-block logic; an error here does not automatically unwind prior per-tx account debits from the same block, since those were already committed to the block's state before `EndBlock` runs its surplus reconciliation step. Swallowing the `AddCoins`/`AddWei` error here means the block completes with usei/wei having been removed from user/coinbase balances without a corresponding credit anywhere — a supply-destruction bug.

### Impact Explanation
If `AddCoins`/`AddWei` to the EVM module account fails (e.g., transient error, blocked-address/negative-coin edge cases, or any other internal bank error), the surplus computed from real user transactions is dropped: the corresponding usei/wei simply vanishes from total tracked balances, i.e., a coin supply destruction bug reachable purely from ordinary EVM transaction submission (since the surplus originates from live EVM tx fee reconciliation in every block). This matches the "concrete fund loss ... supply inflation or destruction" impact bar.

### Likelihood Explanation
The likelihood of `AddCoins`/`AddWei` actually failing under normal conditions is low (in the normal case, sdk.Coins are well-formed and the module account exists), so this is a defense-in-depth / edge-case bug rather than a trivially triggerable one. It requires investigation into what conditions can make these bank calls return a non-nil error (e.g., negative coin construction from an unusual surplus split, module account blocklist interactions, or an sdk.Coins validation error) to determine a concrete PoC transaction sequence. This could not be fully confirmed with the available static index — the exact circumstances under which `BankKeeper().AddCoins`/`AddWei` return errors in this call site were not verified.

### Recommendation
On failure of `AddCoins`/`AddWei` for the surplus, do not silently continue: either panic (fail the block, consistent with other supply-invariant-critical failures in `EndBlock`), or persist the un-credited surplus amount for retry in a subsequent block rather than dropping it. At minimum, treat this the same way other critical `EndBlock` accounting failures in this codebase are treated (e.g., panicking on `Finalize` errors elsewhere), so that transaction fees are never silently destroyed.

### Proof of Concept
A concrete transaction-level PoC was not obtained within the available tooling — this would require exercising `k.BankKeeper().AddCoins`/`AddWei` into a failure path (e.g. by crafting a surplus split that produces an invalid `sdk.Coin` amount, or another bank-keeper failure condition) from an EVM transaction and observing that `EndBlock` logs the error but block production and state commitment continue without the surplus being credited anywhere. Confirming an actual failure trigger for `AddCoins`/`AddWei` in this code path requires further investigation.
