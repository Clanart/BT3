### Title
Unchecked `u64` arithmetic on attacker-controlled amounts causes overflow/underflow in transaction construction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`io_pin_pages`'s bug was adding a length to a user-controlled base without an overflow check. The same shape exists in `SignableTransaction::new` / `fee` in `networks/bitcoin/src/wallet/send.rs`, where `u64` satoshi amounts taken from attacker-influenceable `ReceivedOutput` values (read via `ReceivedOutput::read`) and payment entries are summed and added with plain `+`/`sum()`/`—` instead of checked arithmetic. In release builds the arithmetic wraps; in debug/test builds it panics.

### Finding Description
Several computations in `networks/bitcoin/src/wallet/send.rs` operate on `u64` amounts without any overflow guard:

- `input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` — line 175
- `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` — line 187
- `let mut needed_fee = fee_per_vbyte * vbytes;` — line 206 (unchecked multiplication)
- `if input_sat < (payment_sat + needed_fee)` — line 215 (unchecked addition)
- `fee()` computes `sum(inputs) - sum(outputs)` by plain subtraction — lines 139–140

`ReceivedOutput` is deserialized from untrusted bytes via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122`), which consensus-decodes a `TxOut` whose `value` field is a full `u64` — nothing bounds it to the real supply. A single crafted input with `value = u64::MAX`, or two inputs whose values sum past `u64::MAX`, drives `input_sat` / `payment_sat` / `payment_sat + needed_fee` past the type bound, exactly the `uaddr + size` overflow class from the kernel report. The change-calculation path at line 228 does use `checked_sub`, but the solvency gate at line 215 and the sums feeding it do not, so a wrapped `payment_sat + needed_fee` can evaluate `< input_sat` as false/true inconsistently and let an unaffordable transaction through, after which line 228 computes `change = input_sat - payment_sat - fee_with_change` from the wrapped value.

### Impact Explanation
- In debug/overflow-checked builds this is a panic reachable by feeding crafted bytes to `ReceivedOutput::read` and then constructing a `SignableTransaction` — a denial of service of the signing pipeline.
- In release builds the wrap can produce a `SignableTransaction` whose declared change output (`Amount::from_sat(value)` at line 230) far exceeds the real inputs, yielding a threshold-signed transaction that is consensus-invalid (burning a signing attempt / preprocesses), or `fee()` underflowing (lines 139–140) and reporting a bogus fee. The FROST signers sign whatever `SignableTransaction` was constructed, so the overflow steers threshold signing toward an unintended/invalid transaction.

### Likelihood Explanation
Medium: reachable whenever `SignableTransaction::new` is invoked with `ReceivedOutput`s or payment amounts not guaranteed to be sane `u64`s (e.g., reconstructed via `ReceivedOutput::read` on untrusted bytes, as the API permits). Real scanner-produced outputs are bounded by the Bitcoin supply, which lowers likelihood in the intended pipeline, but the deserializer places no such bound and the arithmetic is unguarded.

### Recommendation
Use `checked_add`/`checked_mul`/`checked_sum` for `input_sat`, `payment_sat`, `fee_per_vbyte * vbytes`, `payment_sat + needed_fee`, and the `fee()` subtraction, returning a `TransactionError` on overflow — mirroring the kernel fix that validated `uaddr + size` before use. Optionally bound `TxOut` values read in `ReceivedOutput::read` to `MAX_MONEY`.
