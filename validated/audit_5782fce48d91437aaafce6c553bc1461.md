### Title
DID transfer preserves the old owner's recovery/backup-ID list, letting stale backup DIDs regain control after a "sale" - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
`DIDWallet.transfer_did()` always carries the current `backup_ids`/`num_of_backup_ids_needed` (recovery configuration) forward into the new owner's inner puzzle, and the corresponding RPC request type now hard-enforces that recovery info must always be preserved. This mirrors the CVE-2021-39897 bug class (inherited access/authorization persisting after an ownership boundary is crossed) applied to Chia's DID ownership-transfer flow.

### Finding Description
When a DID is transferred to a new owner via `DIDWallet.transfer_did()`, the new inner puzzle hash is computed with the *same* `backup_ids` and `num_of_backup_ids_needed` that were configured by the *previous* owner: [1](#0-0) 

The implementation comment for the sibling helper `get_innerpuz_for_new_innerhash` makes the intent explicit — the recovery list is *not* cleared by the transfer itself; it is left to the seller to manually clean it out beforehand: [2](#0-1) 

At the RPC layer, the `DIDTransferDID` request used to allow disabling recovery propagation, but that option has been removed and is now hard-enforced to always be `True`: [3](#0-2) 

`did_transfer_did()` in the RPC API simply forwards straight into `transfer_did()` with no separate step to reset the recovery list: [4](#0-3) 

`reset_recovery_list()` only returns a "cleared" hash when `num_of_backup_ids_needed == 0` **and** `backup_ids` is already empty — i.e., it is a no-op unless the owner had already cleared the list through a separate `create_update_spend`/backup-config change prior to transferring: [5](#0-4) 

Because DID identity underlies NFT ownership (`unft.owner_did`), offer counterparty verification, and "set DID" operations across the NFT/offer flow, any backup ID retained from before a sale (which could be the seller's own alternate wallet, or a third party the seller colluded with) still satisfies the on-chain DID recovery mechanism (`create_recovery_message_puzzle` / `AGG_SIG_UNSAFE` attestment) after the DID has ostensibly been handed to a new buyer: [6](#0-5) 

### Impact Explanation
A buyer who purchases/receives a DID via `transfer_did`/`did_transfer_did` RPC has no client-side signal or enforced mechanism forcing the seller to strip the old recovery/backup-ID configuration before transfer, and the RPC request type actively forbids disabling recovery-info propagation. If the seller (maliciously or carelessly) leaves stale backup IDs configured, those backup identities retain the cryptographic capability to trigger a DID recovery spend and redirect the DID's p2 puzzle hash — effectively regaining unauthorized control of a coin (and any NFT/asset identity tied to that DID) the buyer believes they now exclusively own. This is analogous to GitLab's CVE-2021-39897, where inherited permissions survived an ownership-changing operation (subgroup transfer) that should have revoked them.

### Likelihood Explanation
Exploitation requires only that the seller (an untrusted counterparty in a DID sale/offer) leave a backup ID under their control configured at time of transfer — which is the default and unremarked behavior of `transfer_did`/`did_transfer_did`, since the RPC layer no longer even exposes a way to reset recovery info during transfer. No malicious peer, timelord, or network-layer capability is needed; this is reachable purely through a standard wallet DID-transfer/offer flow by any spend-bundle submitter who controls a DID's recovery configuration prior to sale.

### Recommendation
Require `transfer_did`/`did_transfer_did` to clear `backup_ids`/`num_of_backup_ids_needed` (or otherwise force `reset_recovery_list()` to a cleared hash) as part of the transfer spend itself, rather than relying on the seller to perform an out-of-band cleanup beforehand. At minimum, restore the ability for callers to explicitly request recovery-info reset at the RPC level, and surface a clear warning/verification path for buyers to confirm a DID's recovery list is empty before accepting ownership.

### Proof of Concept
1. Owner A creates a DID with `backup_ids = [B]` (a DID/pubkey A controls or colludes with) and `num_of_backup_ids_needed = 1`.
2. Owner A calls `did_transfer_did` (or CLI `DidTransferDidCMD`) to transfer the DID to buyer C's puzzle hash. Because `with_recovery_info` must always be `True`, and `transfer_did()` forwards `self.did_info.backup_ids` unchanged (`did_wallet.py:823-832`), the new on-chain DID inner puzzle still lists `B` as a valid recovery ID.
3. After the transfer confirms and C believes they solely own the DID, A uses backup ID `B` to construct a recovery attestment spend (`create_recovery_message_puzzle`/`create_spend_for_message`) and complete a DID recovery, changing the DID's p2 puzzle hash back to one A controls — reclaiming the DID and any NFTs bound to it, without C's consent.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
