### Title
Merge preview goes stale relative to the branch actually merged, allowing silent merge of unreviewed remote commits - (File: app/src/ui/multi-commit-operation/choose-branch/merge-choose-branch-dialog.tsx)

### Summary
The C4 finding (`KnightingRound.buy`) is fundamentally a TOCTOU/missing-reconfirmation bug: the user is shown a value (`tokenOutPrice`), decides to act on it, but the value can change before the action executes, and the contract never checks "is the value I'm about to act on still the value I approved?" The closest reachable analog in this GitHub Desktop codebase is the "Merge into current branch" flow, where the merge preview (commit count / mergeability / conflict status) is computed once against a branch's `tip.sha`, but the actual merge is executed by branch reference at click-time with no re-validation that the branch still points at the reviewed SHA.

### Finding Description
`MergeChooseBranchDialog.onSelectionChanged` triggers `updateStatus(branch)` which asynchronously computes `determineMergeability` and the ahead/behind commit count for the selected branch [1](#0-0) . That async computation does guard against staleness *while it is in flight* by comparing `this.state.selectedBranch?.tip.sha !== branch.tip.sha` before committing the result to state [2](#0-1) .

However, once `mergeStatus`/`commitCount` are stored in component state, there is no mechanism that invalidates them if the underlying branch ref moves afterward (e.g., a subsequent background fetch updates a remote-tracking branch). When the user finally clicks "Merge", `start()` calls `dispatcher.mergeBranch(repository, selectedBranch, mergeStatus, ...)` using the `selectedBranch` object already held in state [3](#0-2) . Desktop's git operations throughout the codebase consistently operate on branch/ref names rather than pinned SHAs (e.g. `push`, `fetchRefspec`, `fastForwardBranches` all take branch/ref name strings that git resolves at execution time) [4](#0-3) [5](#0-4) , so the eventual `git merge` invocation resolves the branch name to whatever it currently points to at merge time — not necessarily the `tip.sha` that was used to compute the preview shown to the user.

Desktop runs an automatic `BackgroundFetcher` that periodically fetches from remotes without user interaction , and remote-tracking refs (e.g. `origin/feature`, or a PR fork remote added via `_findPullRequestBranch`) are attacker-influenced when the remote's owner (a collaborator or PR author) pushes new commits [6](#0-5) . If such a push happens between the moment the merge preview is computed and the moment the user clicks "Merge", the dialog keeps showing the old preview (clean/N commits) while the actual `git merge` executed afterward will fast-forward or merge whatever content the ref now points at.

This is structurally identical to the C4 bug: the "believed value" (previewed commit set / mergeability) is never re-checked against the "current value" (actual branch tip) immediately before the state-changing action executes.

### Impact Explanation
If exploited, a user could unknowingly merge attacker-supplied commits into their branch, believing they are merging the content they reviewed in the merge preview. Because Desktop shows no re-confirmation of the diff at the moment of the actual merge, the merge result — and anything the user subsequently commits/pushes on top of it — is silently corrupted relative to what they approved. This matches the "silent corruption of what the user commits or pushes" category, driven purely by a git remote response (a push to a branch Desktop is tracking) with no local access, admin rights, or social engineering required beyond the user opening the standard "Merge into current branch" dialog they'd use anyway.

### Likelihood Explanation
The race window is real but narrow: it depends on the automatic background fetch cadence colliding with the short interval between the user opening the merge dialog and clicking "Merge." This is plausible for automated/CI-adjacent remotes, long-lived dialogs left open, or slower human review of large merge previews, but it is not trivially triggerable on demand by an attacker (they cannot control exactly when Desktop's background fetch runs relative to the user's click). I was not able to fully confirm within the available time whether `dispatcher.mergeBranch` (and the underlying `app/src/lib/git/merge.ts` implementation) resolves the branch by name at execution time versus pinning to a captured SHA — this is inferred from the consistent branch-name-based pattern used elsewhere in the codebase, not directly verified by reading `merge.ts`'s exact git invocation.

### Recommendation
Before executing the merge in `start()` (or in `dispatcher.mergeBranch`/the underlying git store operation), re-resolve the selected branch's current tip SHA and compare it to the SHA the merge preview (`mergeStatus`/`commitCount`) was computed against. If they differ, refuse to merge and force a fresh preview computation (analogous to adding a `believedSha` check that must match the current ref before proceeding), mirroring the `believedPrice` mitigation recommended in the original report.

### Proof of Concept
1. User has a repository with a remote branch `origin/feature` that a collaborator (or PR fork owner) can push to.
2. User opens "Merge into current branch", selects `origin/feature`; `updateStatus` computes and displays "This will merge 3 commits from origin/feature into main" based on `branch.tip.sha = A`.
3. Before the user clicks "Merge", Desktop's periodic background fetch runs and pulls in new commits pushed by the branch owner, moving `origin/feature` to `tip.sha = B` (different content, e.g. containing a malicious script or altered file).
4. The dialog still displays the stale preview computed against `A` since nothing re-triggers `updateStatus`.
5. User clicks "Merge" trusting the previewed 3-commit change; `dispatcher.mergeBranch` executes `git merge origin/feature`, which git resolves to the *current* ref (`B`), silently merging different/unreviewed content into the user's branch.
6. The user commits/pushes the result, unaware the actual merged content diverged from what was reviewed.

  private updateStatus = async (branch: Branch) => {
    const { currentBranch, repository } = this.props

    const mergeStatus = await determineMergeability(
      repository,
      currentBranch,
      branch
    ).catch<MergeTreeResult>(e => {
      log.error('Failed determining mergeability', e)
      return { kind: ComputedAction.Clean }
    })

    // The user has selected a different branch since we started or the branch
    // has changed, so don't update the preview with stale data.
    //
    // We don't have to check if the state changed from underneath us if we
    // loaded the status from cache, because that means we never kicked off an
    // async operation.
    if (this.state.selectedBranch?.tip.sha !== branch.tip.sha) {
      return
    }

    // Can't go forward if the merge status is invalid, no need to check commit count
    if (mergeStatus.kind === ComputedAction.Invalid) {
      this.setState({ mergeStatus })
      return
    }

    // Commit count is used in the UI output as well as determining whether the
    // submit button is enabled

    const commitCount = aheadBehind ? aheadBehind.behind : 0

    if (this.state.selectedBranch.tip.sha !== branch.tip.sha) {
      return
    }

    this.setState({ commitCount, mergeStatus })
