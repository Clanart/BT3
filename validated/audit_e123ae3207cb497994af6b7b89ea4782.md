### Title
Cached deterministic preprocess reused across distinct signing sets/messages under the same context enables key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a FROST `CachedPreprocess` seed keyed only on `context` (e.g. `(b"DkgConfirmer", attempt)`). Every call under that context re-derives identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (ChaCha20Rng seeded from the same 32 bytes). `share()` and `complete()` both invoke `share_internal`, which calls `machine.sign(preprocesses, msg)` with caller-supplied `preprocesses` and `key_pair` — so the same nonces are signed under whatever participant set/message the caller passes. If two calls under the same context differ in the signing set or message, the validator's nonce pair `(d, e)` is reused across two distinct Schnorr challenges, enabling recovery of the MuSig private key share.

### Finding Description
`crypto/frost/src/sign.rs` documents that a cached preprocess "MUST only be used once" and that "After [from_cache], the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share." [1](#0-0) 

In `preprocess_internal`, the seed is stored in `CachedPreprocesses` keyed solely by `context` and is never deleted after use — it is fetched and re-expanded on every call. [2](#0-1) 

`DkgConfirmer::share` and `DkgConfirmer::complete` both call `share_internal`, each of which performs a full `sign()` with the same deterministic nonces but attacker-influenced `preprocesses`/`key_pair`. [3](#0-2) 

The `preprocesses` map is built from bytes supplied per-participant and its key set defines the FROST `included` signing set; the per-participant binding factor `rho` and `hash_msg` challenge depend on that set and the message. Two calls with different subsets of validators' preprocesses, or a `complete` whose preprocess set differs from the earlier `share`, produce two signature shares `s = d + b·e·ρ + λ·x·c` over the same `(d, e)` but different `ρ`/`c` pairs — a classic nonce-reuse equation system recoverable by any observer of the published shares. [4](#0-3) 

The header comment argues safety relies on BFT ordering making received messages identical, but nothing enforces that `share`/`complete` invocations within one `attempt` context bind to a single fixed participant set — the set is whatever preprocesses the caller passes in that call. [5](#0-4) 

### Impact Explanation
Reuse of deterministic FROST nonces across two different binding/challenge equations lets a third party solve for the validator's MuSig secret share, compromising the validator key that is the root of trust for confirming DKG results on-chain (i.e., forgeable `set_keys` confirmations / loss of the validator's key). This is a key-share-recovery impact reachable via public preprocess/share bytes a participant causes to be signed.

### Likelihood Explanation
A validator participant controls the preprocess bytes they publish and can influence which preprocess sets reach `share`/`complete` handling; because the cache key excludes the participant set and message, any divergence between the sets used in successive calls under the same `(context, attempt)` triggers the reuse. No collusion threshold is needed — a single participant submitting preprocesses under differing compositions across calls suffices.

### Recommendation
Include the full signing context in the cache key — the sorted participant key set and the message (or `key_pair`/`removed` set) — so a different set or message derives a different seed; and/or delete `CachedPreprocesses[context]` after the first `sign` and re-check that the on-chain committed preprocesses match the presumed ones before publishing shares (the file already notes this as a TODO).

### Proof of Concept
Under a fixed `(b"DkgConfirmer", attempt)` context:
1. Honest validator V's coordinator processes `share(preprocesses_A, key_pair)` where `preprocesses_A` is set S1 → publishes share `s1 = d + b·e·ρ1 + λ·x·c1`.
2. The same context is invoked again (`share` retry or `complete`) with `preprocesses_B` over a different participant subset S2 (a validator withholds/adds their preprocess) → `preprocess_internal` returns the same seed → same `(d, e)` → publishes `s2 = d + b·e·ρ2 + λ·x·c2` with `ρ2 ≠ ρ1`, `c2 ≠ c1`.
3. An observer collecting `s1, s2`, the public preprocess commitments, and the known `λ·x` relations solves the two linear equations for `d`, `e`, and V's secret share `x`.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.
