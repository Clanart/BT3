### Title
Stale line-selection indices are applied against a freshly re-fetched diff during partial commit staging, allowing silent inclusion/exclusion of unreviewed content - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The report's broken invariant is: *confirmation-time data is drawn from two independently-sourced values that are never cross-validated against each other before being used to mutate state.* In Desktop's partial-commit path, the same class of bug exists: the **line-selection object** (`file.selection`, built from absolute indices into a diff the user reviewed earlier) is applied against a **diff re-fetched at staging time** (`getWorkingDirectoryDiff`), with no check that the two still describe the same content. If tracked file content changes between the moment the user made their line selection and the moment the commit actually stages/applies the patch, the app will silently stage the wrong lines under the correct-looking selection UI, corrupting what gets committed.

### Finding Description
When a file has a `Partial` selection, `stageFiles` routes it to `applyPatchToIndex`: [1](#0-0) 

`applyPatchToIndex` re-fetches the diff from disk right before building the patch: [2](#0-1) [3](#0-2) 

`formatPatch` then walks this **freshly fetched** diff but decides what to include using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is a position (`hunk.unifiedDiffStart + lineIndex`) defined by whatever diff was current when the selection was created: [4](#0-3) 

Nothing in this call chain verifies that the diff used to build `file.selection` is the same diff being fetched moments later in `apply.ts`. The commit orchestration in the store reads the selection straight out of state and hands it to `createCommit`/`stageFiles` without refreshing or validating it first: [5](#0-4) [6](#0-5) 

The developers themselves acknowledge this exact race in a different code path (`updateChangesWorkingDirectoryDiff`), which reconciles selection against a newly loaded diff only when the *UI* re-renders the diff for the currently selected file — and even then only partially: [7](#0-6) 

That reconciliation is not invoked as part of the commit path itself (`_commitIncludedChanges` does not call `updateChangesWorkingDirectoryDiff` before staging), so there is no guarantee the selection held in `state.changesState.workingDirectory.files` still corresponds to the diff that will be re-fetched inside `applyPatchToIndex`.

`updateChangedFiles` — the function that merges new `git status` results into existing UI state — only clears a `Partial` selection when explicitly told to via `clearPartialState`, and otherwise blindly re-attaches the old selection object to the new file entry regardless of whether the underlying diff content changed: [8](#0-7) 

So a background repository refresh (e.g. after an autofetch-triggered fast-forward pull that merges upstream/attacker-controlled content into a tracked file) can update `workingDirectory.files` for that path while carrying forward the *old* `selection`, without ever re-diffing it against the merged content unless the user happens to re-open that file in the Changes view. If the user then commits, `applyPatchToIndex` re-diffs the now-changed (attacker-influenced) file content and applies the stale absolute-index selection to it — the resulting patch can include lines the user never selected, or omit lines the user did select, because the index positions no longer line up with the same semantic content.

### Impact Explanation
This breaks the same invariant as the report: the value ultimately used to mutate persistent state (the commit content, and by extension what gets pushed to a remote and shared) is assembled from two sources that were never validated for consistency. The outcome is **silent corruption of what the user commits** — content can be included or excluded from a commit without the user's knowledge or consent, matching the explicitly allowed impact category "silent corruption of what the user commits or pushes." Because commits are typically pushed and shared, an attacker who can influence merged/fetched content (a remote or MITM proxy serving different content than what the user last reviewed) can cause the user to commit and push content they did not intend, or to omit intended changes (e.g., silently dropping a security fix line) without any error being surfaced — `git apply --unidiff-zero` will happily apply a patch built from mismatched line offsets as long as the offsets are structurally valid, since zero-context hunks bypass the normal context-matching safety net.

### Likelihood Explanation
Medium-to-low but realistic: it requires a timing window between diff render/selection and commit staging during which the tracked file's on-disk content changes (via autofetch+fast-forward pull, a merge, or another background git operation Desktop itself performs) without the user re-opening that file's diff. Desktop performs periodic background fetches and pulls without requiring interactive confirmation, and the reconciliation logic in `updateChangedFiles` explicitly preserves stale `Partial` selections across such refreshes unless `clearPartialState` is set at the specific refresh call site. No local/admin access or pre-existing malware is required — only a remote or proxy the app fetches from serving content that changes between the user's review and their commit action.

### Recommendation
Before staging a `Partial` selection in `applyPatchToIndex`/`stageFiles`, re-validate the selection against the diff that will actually be used: either (a) recompute a diff hash/fingerprint (e.g., a hash of `diff.hunks` structure) at selection time and compare it to the freshly fetched diff's fingerprint before trusting the same absolute indices, failing the operation (or falling back to full-file inclusion with a warning) on mismatch; or (b) always call the same reconciliation logic used in `updateChangesWorkingDirectoryDiff` (clearing selection ranges that no longer correspond to includeable lines) immediately before `_commitIncludedChanges` stages any partially-selected file, rather than only doing so opportunistically on UI re-render.

### Proof of Concept
1. User opens a tracked file with several hunks and manually selects a subset of lines to commit (`DiffSelection` built against diff `D1`), leaving other lines/hunks unselected.
2. Before the user clicks "Commit", Desktop performs a background autofetch and fast-forward pull that merges new content into that same file (content that could originate from a compromised or MITM'd remote).
3. `updateChangedFiles` merges the new working-directory status into state, but reattaches the old `Partial` selection to the file entry (`existingFile.selection`) because `clearPartialState` is not set for this refresh path.
4. User, unaware the file changed underneath, clicks "Commit". `_commitIncludedChanges` passes the stale-selection file object into `createCommit` → `stageFiles` → `applyPatchToIndex`.
5. `applyPatchToIndex` calls `getWorkingDirectoryDiff` and gets a new diff `D2` (post-pull content), then `formatPatch(file, D2)` applies the `D1`-relative absolute indices against `D2`.
6. Because hunk boundaries/line counts differ between `D1` and `D2`, the indices the user thought corresponded to "my reviewed lines" now select different lines in `D2`; `git apply --cached --unidiff-zero` accepts the resulting patch without context verification, and the commit silently contains different content than what the user reviewed and intended to select.
