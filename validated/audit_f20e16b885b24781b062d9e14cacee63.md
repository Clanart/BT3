### Title
DID transfer preserves the seller's recovery (backup) list, letting a previous owner regain control of a "sold" DID without the new owner's consent - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
`DIDWallet.transfer_did` (used to send a DID to a new owner) does not clear the DID's on-chain recovery configuration (`backup_ids` / `num_of_backup_ids_needed`). The recovery list set by the *previous* owner is carried forward into the new owner's inner puzzle, unless the seller explicitly cleans it up first. This mirrors the ENS "trapdoor" pattern in the referenced advisory: an owner can transfer an asset to another party while secretly retaining a mechanism (here, a DID recovery quorum) that lets them reclaim control later, without the new owner's knowledge or consent.

### Finding Description
`transfer_did` builds the new DID puzzle for the recipient using `did_wallet_puzzles.get_inner_puzhash_by_p2`, passing `recovery_list=backup_ids` and `num_of_backup_ids_needed=backup_required`, both taken directly from `self.did_info.backup_ids` / `self.did_info.num_of_backup_ids_needed` — i.e. the seller's own current DID state: [1](#0-0) 

The recovery hash used for that computation comes from `reset_recovery_list()`, which only returns `None` (i.e., preserves the *existing* recovery hash as-is) whenever `backup_ids` is non-empty: [2](#0-1) 

This means: if the seller had configured any backup/recovery DIDs (or a recovery quorum) — which they fully control — before transferring the DID to a buyer, that recovery configuration is **not stripped** during `transfer_did`. The new inner puzzle presented to the buyer keeps the same recovery list hash and required-verifications count as the seller's. The buyer has no visibility into who controls those backup DIDs and no way to detect, from the transfer transaction alone, that a recovery "trapdoor" is baked into the puzzle they are receiving.

This exact risk is explicitly acknowledged elsewhere in the codebase for the analogous NFT/DID ownership-transfer helper, which states the recovery list is intentionally preserved and it is the *seller's responsibility* to clean it before selling: [3](#0-2) 

Because `num_of_backup_ids_needed` and `backup_ids` are curried directly into `DID_INNERPUZ_MOD` (see `create_innerpuz`), and this configuration determines whether/how a DID coin can be spent via the recovery path rather than requiring the current p2 owner's signature, a seller who quietly leaves themselves (or colluding backup IDs) able to satisfy `num_of_backup_ids_needed` retains latent authority over the "sold" DID: [4](#0-3) 

The vulnerability is a wallet-level UX/security defect: there is no enforced "clear recovery list before transfer" step, no warning surfaced to the buyer, and no on-chain indication distinguishing a "clean" DID transfer from one that retains seller-controlled recovery capability.

### Impact Explanation
A buyer of a DID (which underpins DID-linked NFTs, profiles, and any application relying on DID ownership as an identity/authorization anchor) can unknowingly receive an asset that the seller can later reclaim via the DID's built-in recovery mechanism, using backup IDs the seller never disclosed or already controlled. This is a coin/identity-takeover class issue: the buyer believes they have sole custody, but the seller retains a path to regain the singleton without the buyer's cooperation. Given DIDs are used to control NFT ownership records and other singleton-linked assets in this codebase, a takeover of the DID indirectly threatens control of assets bound to it.

### Likelihood Explanation
Exploitation requires no privileged access — any wallet user acting as a seller in a DID sale/transfer can trigger this by simply calling the standard `transfer_did` flow without first clearing the recovery list (which is not enforced or prompted anywhere in the code path). This is a normal, unprivileged wallet operation reachable by any DID owner transferring or selling a DID to a counterparty (e.g., via an offer), making the likelihood of accidental or deliberate misuse realistic, especially since the "must clean up first" responsibility is only documented in a code comment, not enforced.

### Recommendation
`transfer_did` should, by default, reset `backup_ids` to empty and `num_of_backup_ids_needed` to `0` (i.e., force `reset_recovery_list()`-style clearing) unless the caller explicitly opts to preserve recovery settings. At minimum, the wallet/CLI/RPC transfer path should surface an explicit warning or require an explicit flag when a DID with a non-empty recovery list is being transferred, and buyers should be able to verify via RPC that the recovery list is empty before accepting a DID.

### Proof of Concept
1. Seller creates a DID with `num_of_backup_ids_needed = 1` and `backup_ids = [attacker_controlled_did]` (a legitimate configurable feature at DID creation: `did_wallet_puzzles.create_innerpuz`).
2. Seller calls `DIDWallet.transfer_did(new_puzhash, ...)` to sell the DID to Buyer. As shown, `backup_ids` and `num_of_backup_ids_needed` are carried forward unchanged into the puzzle sent to Buyer. [5](#0-4) 
3. Buyer receives the DID coin, sees themselves as the new p2 owner, and is unaware the puzzle still recognizes the seller's backup DID as authorized to trigger recovery.
4. Seller (or their colluding backup DID) later invokes the DID's on-chain recovery path (satisfying `num_of_backup_ids_needed` attestations from `backup_ids`) to reassign the p2 puzzle hash back to themselves, reclaiming the DID without Buyer's signature or consent.

Note: Full verification of the exact recovery-spend CLVM logic (`did_innerpuz.clsp`) was not available in the indexed codebase context (the puzzle source file could not be located via search), so the precise recovery-path spend conditions in chialisp are not directly cited here; this should be confirmed against the actual `did_innerpuz.clsp`/compiled puzzle to fully validate the spend-level mechanics. The CHANGELOG also notes some DID recovery RPC endpoints (`did_update_recovery_ids`, `did_recovery_spend`, etc.) were removed from the wallet API, which may affect how easily recovery can be triggered via RPC — but the underlying puzzle-level recovery configuration and `transfer_did` behavior described above remain present in the code as read.

```python
    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash
```

```python
def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )
```
