### Title
Zero Slippage Protection in `WombatPoolHelperV2.depositFor` Deposit Path - (File: wombat/WombatPoolHelperV2.sol)

### Summary
The `depositFor` function in `WombatPoolHelperV2.sol` hardcodes `_minimumLiquidity` to `0` when converting a user-supplied stable token into a Wombat pool LP position, removing any slippage protection during the on-chain conversion, analogous to the `redeemExpiredPT` zero-`minTokenOut` issue in the external report where a hardcoded zero minimum during a value-conversion step exposes callers to MEV/sandwich losses.

### Finding Description
`depositFor` accepts an arbitrary `_amount` and a `_for` beneficiary from any unprivileged wallet, then calls the internal `_deposit` helper with a hardcoded `0` in place of a user-supplied minimum-liquidity value: [1](#0-0) 

This differs from the sibling `deposit` entrypoint, which forwards a caller-supplied `_minimumLiquidity`: [2](#0-1) 

The `0` value propagates into `WombatStaking.deposit`, which forwards it unmodified as the `_minimumLiquidity` parameter to the underlying Wombat pool's `deposit` call: [3](#0-2) 

Because `IWombatPool.deposit` performs an internal swap-like conversion (subject to pool haircut/slippage based on asset coverage ratio), passing `0` as the minimum liquidity removes any protection against unfavorable pool conditions or sandwich attacks timed around the deposit transaction — the same bug class as the report's `sy.redeem(..., 0, ...)` call, just on the deposit side of the LP lifecycle rather than the redemption side.

### Impact Explanation
Any unprivileged wallet calling `depositFor` receives LP-backed receipt tokens (minted via `IMintableERC20(poolInfo.receiptToken).mint`) computed from the actual LP amount returned by the pool, with zero minimum enforced. An attacker (or adverse pool conditions/MEV) can manipulate the pool's coverage ratio immediately before the deposit executes, causing the depositor to receive materially fewer LP-backed shares than the fair-value amount for their deposited tokens. This is a direct, permanent value loss to the depositing wallet with no revert-based backstop, matching the report's criteria of direct theft/loss of user funds from a conversion step with zero slippage protection.

### Likelihood Explanation
The function is externally callable by any wallet with no privilege requirements, and Wombat pools are the type of AMM (asset-based, coverage-ratio-dependent) where pre-transaction manipulation of the pool ratio is a well-known MEV pattern, making this a fully unprivileged-wallet-reachable path.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (or otherwise compute an enforced non-zero minimum, e.g., derived from an off-chain quote passed by the caller) instead of hardcoding `0`, and thread it through to `WombatStaking.deposit` and `IWombatPool.deposit`, mirroring the protection already present in the plain `deposit` function.

### Proof of Concept
1. A pool has a favorable coverage ratio such that depositing `X` stable tokens would normally mint `Y` LP tokens.
2. An attacker manipulates the pool ratio (e.g., via a large deposit/withdraw or coordinated swap) immediately before the victim's `depositFor` transaction lands.
3. Victim calls `depositFor(_amount, _for)`; because `_minimumLiquidity` is hardcoded to `0` in `_deposit(_amount, 0, _for, address(this))`, the transaction proceeds even though the LP amount returned is far below fair value.
4. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived)` mints receipt tokens based on the diminished `lpReceived`, permanently under-crediting the victim relative to the value they deposited.
