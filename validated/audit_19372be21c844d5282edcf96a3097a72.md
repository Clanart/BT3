### Title
Unprivileged caller can sweep another user's stranded reward-token dust via `compound` - (File: rewards/ManualCompound.sol)

### Summary
`compound()` computes `receivedBalance` for each registered reward as the *entire* contract balance of that token (`IERC20(_tokenAddress).balanceOf(address(this))`), then forwards that whole amount to `msg.sender` via convert/lock/deposit/transfer. Any dust that was not fully consumed by a previous caller's convertor/locker/helper (rounding, partial convert, under-consuming helper) remains on the contract and is entirely attributable to whoever calls `compound()` next, regardless of that caller's actual claim in the same transaction.

### Finding Description
In `compound(address[] calldata _lps, address[][] calldata _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp)` <cite repo="bsaldua/contracts--015" path="rewards/ManualCompound.sol" start="123,139" end="146,159" />, the contract first claims rewards on behalf of `msg.sender` via `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0) , then for every registered `Reward` in the `rewards` array it reads:
```
uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
```
and, if positive, routes the *whole* balance to `msg.sender` (via `convertor.convertFor`, `locker.lockFor`, `helper.depositFor`, or a direct `safeTransfer`) [2](#0-1) .

The balance check is not scoped to the tokens actually claimed by `msg.sender` in this same call — it is a raw `balanceOf(address(this))` snapshot. If a prior `compound()` call left residual tokens on the contract (e.g., a convertor that only partially consumes the approved amount, a helper's `depositFor` that under-consumes due to rounding, or simply no convertor/locker/helper configured for a reward so the leftover from a failed/partial transfer stays), that residual is indistinguishable from freshly-claimed tokens. The next caller — who can be a completely unprivileged EOA calling with arbitrary/empty `_lps`/`_rewards` (since `compound` has no access control and no validation that the caller actually generated the reward balance) — will have that stranded balance swept entirely to themselves.

There is no per-user accounting of reward ownership inside `ManualCompound`; the contract has no `nonReentrant`, no owner/role check on `compound`, and no reconciliation between `balanceOf` and the actual amount attributable to `msg.sender`'s claim in that transaction.

### Impact Explanation
This allows theft of reward tokens that rightfully belong to other users (whose earlier `compound()` calls left dust behind) by any unprivileged caller, satisfying "Critical - Direct theft of user funds." The magnitude depends on how much dust accumulates per compound cycle (rounding/partial-convert amounts), but it is a systemic drain: every `compound()` call is an opportunity to both leave and steal stranded balances, and repeated calls compound the loss over time.

### Likelihood Explanation
Preconditions: at least one registered reward in `rewards` for which the configured convertor/locker/helper does not consume 100% of the approved balance (a plausible/likely scenario given real-world DEX/AMM conversion rounding, or a reward with no convertor/locker/helper at all leaving a corner case where `_lockMgp` is false and locker exists but convertor doesn't, still routing to `safeTransfer` — but if any external call reverts, prior state may leave balance too). No special capital or privilege is required — any address can call `compound` with trivial or empty `_lps`/`_rewards` and no claimable position of its own, and still receive whatever balance sits on the contract for each registered `tokenAddress`. This is trivially repeatable every time dust accumulates.

### Recommendation
Track reward accounting per compound call by computing `receivedBalance` as the delta between balance before and after `multiclaimOnBehalf` for each specific token that was actually claimed for `msg.sender`, rather than sweeping the raw `balanceOf(address(this))`. Alternatively, maintain a running ledger of undistributed dust per token, and require that only the amount attributable to `msg.sender`'s current claim be forwarded, with any pre-existing dust retained under proper accounting (e.g., a `pendingRewardOf[token][user]` sweep model) rather than an implicit first-come-first-served balance grab.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ManualCompound` with a mock `masterMagpie`, one reward token `R` configured with a mock convertor that intentionally only converts 90% of the approved amount (simulating rounding/partial convert), leaving 10% as dust on the contract.
2. User A calls `compound([...], [...], ratio, minRec, false)` claiming 100 `R` tokens; assert the convertor consumes 90, and 10 `R` remain in `ManualCompound`'s balance (`IERC20(R).balanceOf(manualCompound)` == 10).
3. User B (attacker, unprivileged, no stake, calling with empty or unrelated `_lps`/`_rewards` such that `multiclaimOnBehalf` claims 0 additional `R` for B) calls `compound([], [], ratio, minRec, false)`.
4. Assert that the convertor is invoked with `receivedBalance == 10` and `msg.sender == B`, i.e., User B receives/benefits from the 10 `R` dust that belonged to User A's earlier claim, despite contributing nothing in step 3.
5. Assert the invariant violation: `IERC20(R).balanceOf(manualCompound)` after step 3 is `0`, and User B's on-chain proceeds (converted/locked/deposited amount) include the 10 dust tokens that were never theirs — confirming a fund-diversion path from User A to User B.
