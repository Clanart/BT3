### Title
Unvalidated `IRefCheck.htmlUrl` from GitHub API reaches `shell.openExternal` without scheme validation - (File: app/src/main-process/main.ts)

### Summary
A check run's `htmlUrl`, sourced directly from an untrusted GitHub Actions/Check-Run API response (`IRefCheck`), flows unmodified from `CICheckRunPopover.onViewCheckDetails`/`onViewJobStep` through `dispatcher.openInBrowser` to `AppStore._openInBrowser`, then via the `open-external` IPC channel into the main process, which calls `shell.openExternal(path)` without validating the URL scheme.

### Finding Description
`onViewCheckExternally` (wired up in `app/src/ui/check-runs/ci-check-run-step-list-header.tsx`) ultimately triggers `CICheckRunPopover.onViewCheckDetails`, where the URL is taken straight from `checkRun.htmlUrl` with no scheme validation: [1](#0-0) 

This is passed to `dispatcher.openInBrowser(url)`: [2](#0-1) 

which calls `AppStore._openInBrowser`, calling `shell.openExternal(url)` from `app-shell.ts` directly, with no validation: [3](#0-2) 

`shell.openExternal` in the renderer is `main-process-proxy.ts`'s `openExternal`, an `invokeProxy` wrapper around the `open-external` IPC channel: [4](#0-3) 

The main-process handler for `open-external` only inspects the URL to decide whether to *log* it as "opening in browser" if it starts with `http://`/`https://`; it does not reject or sanitize any other scheme before calling `shell.openExternal(path)`: [5](#0-4) 

There is no scheme allow-list, no `new URL()` parsing/validation, and no rejection path anywhere between the API-sourced `IRefCheck.htmlUrl` and the final `shell.openExternal` call.

### Impact Explanation
Electron's `shell.openExternal` delegates to the OS's default URL/protocol handling. If `htmlUrl` (or the step URL built from it) contains a non-http(s) value — e.g. a `file://` URI, a Windows UNC path (`\\attacker-server\share`), or a registered custom protocol handler URI — the OS will act on it: opening local files/folders, triggering SMB authentication leaks (potential NTLM hash/credential exfiltration on Windows via UNC paths), or invoking any installed protocol handler with attacker-controlled data. Since `IRefCheck` objects originate from the GitHub Checks/Actions API for a repository (which an attacker with a malicious/forked repo or workflow can populate), this is attacker-controlled content reaching a sensitive OS-level sink without validation.

### Likelihood Explanation
Reaching this sink requires only that a user views checks on a PR/commit from an attacker-influenced repository and clicks "View on GitHub" for a check run whose `html_url` (or job step URL) was crafted maliciously (typically via a compromised/malicious Checks API response, e.g. from a fork's workflow or a malicious GitHub App with check-run write access to the repo). No local access, malware, or leaked credentials are needed — only that the app displays and the user clicks a check-run action link, which is a normal expected user action in the check-runs UI.

### Recommendation
Validate the scheme of any URL before calling `shell.openExternal`, at the latest in the `open-external` IPC handler in `app/src/main-process/main.ts` — reject (return `false`/throw) unless the URL parses via `new URL(path)` with `protocol === 'http:'` or `'https:'` (and possibly `mailto:` if intentionally supported), rather than merely logging on the http/https case. Additionally, validate `IRefCheck.htmlUrl` and any derived check/step URLs at the point they're consumed in `ci-check-run-popover.tsx` before invoking `dispatcher.openInBrowser`.

### Proof of Concept
1. Mock a Checks API response for a repository/PR where a check run's `html_url` is set to `file:///etc/passwd` (or `\\attacker.com\share` on Windows).
2. Render `CICheckRunPopover` with that check in state and simulate a click that triggers `onViewCheckDetails`.
3. Observe that `dispatcher.openInBrowser` is called with the raw `file://.../` (or UNC) value [1](#0-0) , which flows through `_openInBrowser` [3](#0-2)  and the `open-external` IPC handler [5](#0-4)  to `shell.openExternal(path)` with no rejection.

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
