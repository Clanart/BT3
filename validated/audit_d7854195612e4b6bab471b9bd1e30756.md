### Title
Per-delegation clamping of `pending_delegator_rewards` allows aggregate block-reward over-distribution beyond a vote account's allocated pool - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The Gearbox report describes a class of bug where a per-entity accounting value is derived independently for each sub-account against a shared pool total, without the pool being decremented as each sub-account's share is computed, so the sum of individually-computed shares can diverge from (in Gearbox: exceed) the tracked global total. The Agave analog is `calculate_block_reward` in the epoch-rewards recalculation path: each stake delegation's share of a vote account's `pending_delegator_rewards` is computed independently and clamped only against the *full* pool value, not against a running remainder, so multiple delegations to the same vote account can each be capped up to the entire pool.

### Finding Description
`calculate_block_reward` computes a stake account's share of block-revenue-sharing rewards as a proportion of `total_active_stake` for the vote account, using a shared, cached `pending_delegator_rewards` value read from the vote account's state: [1](#0-0) 

The function's own comment acknowledges that during recalculation (e.g., after a partial partitioned distribution followed by snapshot restore/reload), an individual stake account's effective `stake` can already exceed `total_active_stake`, making `stake/total_active_stake > 1`. The code clamps that single computation to `pending_delegator_rewards` "just to be safe," but this clamp is per-delegation and stateless — it is not decremented as the parallel iterator (`stake_delegations.par_iter()`) computes rewards for other delegations to the *same* vote account: [2](#0-1) 

Because each delegation's `block_reward` is computed independently (in parallel, via `redeem_delegation_rewards`/`calculate_block_reward`) against the same unmodified `pending_delegator_rewards` snapshot, the *sum* of `block_reward` values paid to multiple stake accounts delegated to one vote account can exceed the vote account's actual `pending_delegator_rewards` allocation — mirroring exactly the Gearbox pattern of "total increases unequally" relative to the tracked pool.

The only cross-checking guard in this subsystem, `distribute_reward_commissions`, asserts that the network-wide inflation `point_value.rewards` covers `distributed_lamports + distributed_to_incinerator_lamports + burned_lamports + total_stake_rewards_lamports`: [3](#0-2) 
This assertion operates on the aggregate epoch-wide inflation pool, not on the per-vote-account `pending_delegator_rewards` pool that block-reward payouts are drawn from, so it does not detect or prevent an over-distribution confined to a single vote account's delegator set.

### Impact Explanation
`block_reward` lamports are drawn from a pre-funded `epoch_rewards` sysvar account balance (shown by the `distribute_epoch_rewards_in_partition` test flow subtracting `block_rewards` from that account's balance): [4](#0-3) 
If the aggregate `block_reward` computed for delegations to a single vote account exceeds what was actually reserved for it, distribution to later stake accounts in the same or later partitions could draw down the sysvar balance beyond its intended allocation. Depending on how the underflow is handled in the balance-decrement path, this manifests either as (a) some stake accounts silently receiving smaller-than-entitled rewards (economic loss for those delegators) or (b) an arithmetic underflow/panic if a `checked_sub`/`expect` is hit when the sysvar balance can't cover the computed distribution, which would panic the validator's replay path — a consensus-halt-class failure since all validators executing the same partitioned distribution logic would be affected identically.

### Likelihood Explanation
This path is explicitly reachable only inside the recalculation flow (`recalculate_stake_rewards`/`recalculate_partitioned_rewards_if_active`), which the code comments state is exercised when a stake account has already received rewards before a snapshot restore interrupts partitioned distribution — a scenario within normal validator restart/catch-up operation, not requiring any privileged or malicious actor. The developers' own comment ("this is harmless in practice, but we clamp it just to be safe") suggests this edge case was considered but only partially mitigated (individual overflow avoided, aggregate pool overrun not addressed), making it a plausible latent correctness gap rather than a fully ruled-out non-issue.

### Recommendation
Track a running remainder of `pending_delegator_rewards` per vote account across all its delegations within a single recalculation pass (or otherwise deduct/cap the sum of computed `block_reward` values at the pool level rather than clamping each computation independently against the full, undecremented pool), and add an assertion analogous to the existing epoch-wide `point_value.rewards` check but scoped to each vote account's `pending_delegator_rewards`/block-reward pool before storing/distributing.

### Proof of Concept
A concrete PoC requires reproducing the exact recalculation trigger (partial partitioned distribution + snapshot restore mid-epoch) with multiple stake accounts delegated to the same vote account, then observing whether the sum of their `PartitionedStakeReward.block_reward` fields (as constructed in `calculate_stake_rewards_and_commissions`) exceeds the vote account's single `pending_delegator_rewards` value at snapshot time. I was not able to fully trace the downstream lamport-subtraction code in `distribute_epoch_rewards_in_partition` within the available iterations to confirm whether an actual panic/underflow occurs versus silent short-payment; this would need to be verified with a live test harness (e.g., `test_recalculate_partitioned_rewards` as a starting scaffold) in a full Devin session with repository access.
