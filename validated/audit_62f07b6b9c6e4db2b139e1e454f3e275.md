### Title
`ThresholdKeys` derived `Debug` leaks secret tweak scalars (`scalar` and `offset`) - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys<C>` derives `Debug`, which formats every field — including `scalar` and `offset`, the secret ephemeral tweak scalars applied to the threshold key. The core secret share is protected by a manually redacted `Debug` on `ThresholdCore`, but the struct-level derived `Debug` bypasses that protection for the two tweak fields, printing the full `C::F` scalar bytes.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys` is declared as:

```rust
#[derive(Clone, Debug, Zeroize)]
pub struct ThresholdKeys<C: Ciphersuite> {
  #[zeroize(skip)]
  core: Arc<Zeroizing<ThresholdCore<C>>>,
  scalar: C::F,
  offset: C::F,
}
``` [1](#0-0) 

`ThresholdCore` has a hand-written `Debug` that deliberately omits `secret_share` via `finish_non_exhaustive()` — demonstrating the codebase's intent that secret material not appear in `Debug` output. [2](#0-1)  However, the derived `Debug` on `ThresholdKeys` prints `scalar` and `offset` verbatim using `C::F`'s `Debug` (which for the dalek-ff-group and kp256 scalar types renders the full canonical bytes of the scalar).

`scalar` and `offset` are secret tweak material: they are applied to the key linear combination in `group_key()` (`(group_key * scalar) + (G * offset)`) and to the secret share when constructing a `ThresholdView`. [3](#0-2)  Their doc comments state they are "ephemeral and will not be included when these keys are serialized" — i.e., the authors treat them as secret, but the derived `Debug` defeats that intent for any value that is formatted.

The same pattern is handled correctly elsewhere: `SecretShare`, `SecretShareMachine`, `KeyMachine`, `BlameMachine`, `Encryption`, and `Cosigner` all use manual `Debug` impls with `finish_non_exhaustive()` to omit key material. [4](#0-3)  `ThresholdKeys` (and the analogous manual impl on `ThresholdView`, which correctly omits `secret_share` but still prints `scalar`/`offset`) is the outlier. [5](#0-4) 

### Impact Explanation
Any code path that formats `ThresholdKeys` or `ThresholdView` with `{:?}` — diagnostic logs, `tracing` span fields, `unwrap`/`expect` on enclosing error types, or crash reports — writes the tweak scalars in the clear. `scalar`/`offset` are used to derive per-key-pair secrets (e.g., offset-derived keys such as tweaked output keys): a leaked offset/scalar combined with the corresponding tweaked public key discloses the relationship between keys the scheme treats as unlinkable/private, and — where the offset itself is a private key fragment — directly yields private key material the holder must keep secret. Because these scalars are applied on top of any existing tweak, the exposed value is the cumulative tweak, not just a single-step value. This matches the bug class of the nostr advisory: derived `Debug` emitting credential-bearing fields that the author expected to stay secret.

### Likelihood Explanation
No remote attacker can force `Debug` formatting — the leak requires the local application to format the value, and someone able to read the resulting output (shared logs, error aggregation, tracing collectors). This is a local/operational exposure consistent with the source advisory's `AV:L` rating, hence Medium rather than High.

### Recommendation
Replace `#[derive(Debug)]` on `ThresholdKeys` and the manual `Debug` on `ThresholdView` with `Debug` impls that omit `scalar` and `offset` (e.g., `finish_non_exhaustive()`), matching the precedent set by `ThresholdCore`, `SecretShare`, `KeyMachine`, and `Cosigner`. Audit any other `#[derive(Debug)]` types holding `C::F`/`Zeroizing` fields — e.g., the derived `Debug` on `KeyGen` in `processor/src/key_gen.rs` which would print the `entropy` seed field via `Zeroizing`'s transparent `Debug` — for the same defect. [6](#0-5) 

### Proof of Concept
```rust
use dkg::{ThresholdKeys, ThresholdParams, Participant};
use ciphersuite::{Ciphersuite, Ristretto};
use zeroize::Zeroizing;
use std::collections::HashMap;
use group::Group;

// After a normal DKG producing `keys: ThresholdKeys<Ristretto>`:
let tweaked = keys.offset(<Ristretto as Ciphersuite>::F::random(rng));
// Any log/trace/error path formatting the keys prints `offset` (and `scalar`)
// in full via the derived Debug:
let s = format!("{tweaked:?}");
assert!(s.contains("offset")); // scalar bytes of the secret tweak present in output
```

Verification: `cargo doc`/source inspection confirms `ThresholdKeys` has `#[derive(Clone, Debug, Zeroize)]` with non-skipped `scalar`/`offset` fields, and `ThresholdCore`'s redacted `Debug` does not apply to the outer struct's own fields.
