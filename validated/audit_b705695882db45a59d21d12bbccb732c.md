### Title
Unrestricted, repeatable `updateEndRemainingAllocation()` allows front-running the bonus snapshot to steal disproportionate airdrop bonus - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a public, unguarded function that unconditionally overwrites `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation` any time after `periodsEndTime[4]`, with no check that a snapshot has already been taken. Because `claim()` only auto-invokes it when the stored value is still zero, any unprivileged caller can call it directly at a self-chosen moment (e.g. right before their own claim, when almost everyone else has already claimed) to fix the bonus denominator to an artificially small value, inflating their own share of `totalBonus` at the expense of the forfeiting/remaining users the mechanism was meant to reward fairly.

### Finding Description
`getBonusAmount()` computes each claimant's bonus as `userAllocation * totalBonus / totalEndRemainingAllocation` [1](#0-0) . This denominator is supposed to be a one-time snapshot of `totalRemainingAllocation` taken exactly once, at the moment the first post-period-4 claim occurs, so it fairly represents everyone still unclaimed at that instant.

However, `updateEndRemainingAllocation()` has no idempotency guard - it recomputes `totalEndRemainingAllocation = totalRemainingAllocation` every single time it is called, as long as `block.timestamp >= periodsEndTime[4]`, regardless of whether it was already set: [2](#0-1) 

`claim()` only calls it conditionally (`if (totalEndRemainingAllocation == 0)`), but the function itself is `public` and callable by anyone directly, at any time after period 4 ends, as many times as desired: [3](#0-2) 

Exploit flow:
1. Time passes; multiple users claim early during periods 0-3, forfeiting the difference into `totalBonus` via `totalBonus += forfeited` in `claim()` [4](#0-3) .
2. After `periodsEndTime[4]`, an attacker waits until nearly all other allocations have been claimed (precondition: exactly one other unclaimed allocation besides the attacker's remains), so `totalRemainingAllocation` is now very small.
3. The attacker directly calls `updateEndRemainingAllocation()`, fixing `totalEndRemainingAllocation` to this artificially small remaining sum instead of the value it would have had if snapshotted earlier (at the natural first-claim moment when more allocations were still unclaimed).
4. The attacker then calls `claim()`. Since `totalEndRemainingAllocation` is now non-zero, `claim()` skips its own auto-update and uses the attacker-timed value, computing `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` with an artificially deflated denominator, granting the attacker (and the sole remaining co-claimant) a disproportionately large share of the entire `totalBonus` pool that was accumulated from many other users' forfeitures.

No modifier, role check, or reentrancy guard restricts `updateEndRemainingAllocation()`, and no logic prevents it from being called more than once or by non-claim callers, so the snapshot is trivially manipulable by transaction ordering.

### Impact Explanation
The `totalBonus` pool represents forfeited allocations rightfully belonging (by design) to all users who remain unclaimed as of the intended single snapshot point. By front-running that snapshot, an attacker redirects a disproportionate share of this shared pool to themselves, directly at the expense of the fairness invariant the contract is supposed to enforce, and potentially causes later/earlier legitimate claimants to receive less than their fair share or fail with `InsufficientBalance` if the contract's token balance is exhausted by the inflated payout. This is a direct theft of other users' rightful airdrop bonus funds.

### Likelihood Explanation
This requires no privileged role, capital, or flash loans - only a plain unprivileged EOA calling a `public` function with no access control, timed after `periodsEndTime[4]`. The precondition (few allocations remaining unclaimed) is a naturally occurring state late in the airdrop's claim window, and is trivially observable on-chain via `totalRemainingAllocation` and individual `allocations` mappings, making the attack fully repeatable and low-cost.

### Recommendation
Add an idempotency guard to `updateEndRemainingAllocation()` so the snapshot can only be taken once (e.g., `require(totalEndRemainingAllocation == 0)` before writing, or use a separate boolean flag), and/or restrict who can trigger it, so the bonus denominator cannot be manipulated by choosing the calling transaction's timing.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with a set `startTime`; `register()` 3+ users with known allocations; fund the contract with the corresponding `aidropToken` balance.
2. Advance time past `periodsEndTime[0..3]`; have some users `claim()` early to populate `totalBonus` via forfeiture.
3. Advance time past `periodsEndTime[4]`; have all but one non-attacker user and the attacker claim, so `totalRemainingAllocation` shrinks to just the attacker's and one other's allocation.
4. From the attacker's account, call `updateEndRemainingAllocation()` directly (front-running the last legitimate claimant), then call `claim()`.
5. Assert: the attacker's realized `bonusAmount` (from `getBonusAmount`) is materially larger than what it would have been had the snapshot been taken at the natural first-post-period-4-claim moment (compute and compare against a baseline run where `updateEndRemainingAllocation()` is never called directly).
6. Assert the invariant fails: sum of bonus amounts paid across all claimants no longer reconciles proportionally with `totalBonus`, and/or the last remaining legitimate claimant's `claim()` reverts with `InsufficientBalance` due to the attacker's inflated payout, demonstrating fund theft/freezing.

    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
