### Title
`host_deposit_constant` Passes Wrong Argument to `deposit_constant`, Permanently Breaking Operator Bridge-Circuit Proof Generation — (`bridge-circuit-host/src/structs.rs`)

### Summary

The host-side helper `host_deposit_constant` calls the shared `deposit_constant` function with `deposit_value_bytes` (the deposit amount from the EVM storage proof) in the position that the function signature and the in-circuit call both expect `move_txid` (the move-to-vault transaction ID). Because the `deposit_constant` value is committed inside the zkVM journal, the host-predicted journal hash never matches the actual circuit journal, causing `prove_bridge_circuit` to unconditionally return an error. An operator that is challenged can never generate a valid bridge-circuit Groth16 proof, so it can never post the required assert transactions, and its collateral is slashable by any challenger.

### Finding Description

`deposit_constant` is a shared function in `circuits-lib` with the following signature:

```rust
// circuits-lib/src/bridge_circuit/mod.rs:634-641
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],          // ← 4th param: move-to-vault txid
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
```

**Inside the zkVM circuit** (`circuits-lib/src/bridge_circuit/mod.rs:221-229`) the call is correct:

```rust
let (user_wd_outpoint, vout, move_txid) =
    verify_storage_proofs(&input.sp, light_client_circuit_output.l2_state_root);
// ...
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,          // ← correct: move-to-vault txid from storage proof
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
```

**On the host side** (`bridge-circuit-host/src/structs.rs:482-515`) the call is wrong:

```rust
fn host_deposit_constant(input: &BridgeCircuitInput) -> Result<DepositConstant, ...> {
    // ...
    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,   // ← WRONG: deposit amount, not move_txid
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}
```

`deposit_value_bytes` is the 32-byte big-endian encoding of the deposit's EVM storage value (the BTC amount), whereas the function expects the 32-byte move-to-vault transaction ID. These are entirely different values.

`host_deposit_constant` feeds into `SuccinctBridgeCircuitPublicInputs::host_journal_hash`, which is compared against the actual zkVM journal in `prove_bridge_circuit`:

```rust
// bridge-circuit-host/src/bridge_circuit_host.rs:239-241
if *journal_hash.as_bytes() != succinct_receipt_journal {
    return Err(eyre!("Journal hash mismatch"));
}
```

Because the circuit commits the correct `deposit_constant` (using `move_txid`) and the host predicts a different one (using `deposit_value_bytes`), this check always fails. `prove_bridge_circuit` never returns a proof.

### Impact Explanation

The bridge circuit proof is the operator's only mechanism to defend against a BitVM2 challenge. When a verifier challenges a kickoff, the operator must post assert transactions containing the Groth16 proof output. If `prove_bridge_circuit` always errors, the operator can never produce those assert transactions. Any challenger can then spend the disprove connector and burn the operator's collateral. This constitutes a permanent, unconditional slashable exposure of all operator collateral for every challenged withdrawal.

### Likelihood Explanation

The mismatch is unconditional — it fires on every call to `prove_bridge_circuit` regardless of network, deposit size, or any runtime parameter. Any party that challenges an operator (including a malicious one) will succeed in slashing the collateral because the operator has no viable defense path.

### Recommendation

Replace `deposit_value_bytes` with the move-to-vault transaction ID in `host_deposit_constant`. The host must derive `move_txid` from the storage proof the same way the circuit does — by calling `verify_storage_proofs` (or its host-side equivalent) and extracting the returned `move_txid`:

```rust
// bridge-circuit-host/src/structs.rs  (host_deposit_constant)
// Replace:
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();
Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,   // ← remove
    ...
))

// With:
let move_txid: [u8; 32] = /* derive from storage proof, matching circuit logic */;
Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid,             // ← correct
    ...
))
```

Add a test that runs `host_deposit_constant` and the circuit's `deposit_constant` call on the same `BridgeCircuitInput` and asserts they produce identical `DepositConstant` values.

### Proof of Concept

1. Operator fronts a withdrawal and sends a kickoff transaction.
2. A challenger spends the challenge connector, starting the BitVM2 game.
3. Operator calls `prove_bridge_circuit` to generate the assert data.
4. Inside `prove_bridge_circuit`, `SuccinctBridgeCircuitPublicInputs::new` calls `host_deposit_constant`, which computes `deposit_constant` using `deposit_value_bytes` instead of `move_txid`.
5. The zkVM circuit executes correctly and commits `journal_hash(payout_tx_blockhash, latest_blockhash, challenge_sending_watchtowers, deposit_constant_with_move_txid)`.
6. The host compares its predicted journal hash (computed with `deposit_value_bytes`) against the circuit's actual journal — they differ.
7. `prove_bridge_circuit` returns `Err("Journal hash mismatch")`.
8. The operator cannot post assert transactions.
9. The challenger spends the disprove connector, burning the operator's collateral.

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
```
