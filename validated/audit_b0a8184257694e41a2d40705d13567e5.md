### Title
Missing Retry for Previous-Block LCP in `get_citrea_l2_height_range` Permanently Halts Verifier Block Processing — (`core/src/citrea.rs`)

### Summary

`get_citrea_l2_height_range` retries indefinitely (up to a configurable timeout) for the **current** block's Light Client Proof (LCP), but performs a single, non-retried fetch for the **previous** block's LCP (`block_height - 1`). If Citrea's prover has a gap and the previous block's proof is absent, the function immediately returns an error. Because `handle_finalized_block` propagates this error, the verifier is permanently stuck on that block height and cannot advance its state machine, halting deposit/withdrawal tracking and watchtower challenge dispatch for all subsequent blocks.

### Finding Description

`get_citrea_l2_height_range` in `core/src/citrea.rs` is called by `Verifier::handle_finalized_block` for every finalized Bitcoin block. Its job is to derive the L2 height range `(l2_height_start, l2_height_end)` needed to collect deposits and withdrawals from Citrea.

The function has asymmetric retry logic:

```rust
// Retries with timeout for current block
let proof_current = loop {
    if let Some(proof) = self.get_light_client_proof(block_height, paramset).await? {
        break proof;
    }
    if start.elapsed() > timeout {
        return Err(...);
    }
    tokio::time::sleep(Duration::from_secs(1)).await;
};

// Single attempt, no retry, for previous block
let proof_previous = self
    .get_light_client_proof(block_height - 1, paramset)
    .await?
    .ok_or(eyre::eyre!(
        "Light client proof not found for block height: {}",
        block_height - 1
    ))?;
``` [1](#0-0) 

If `get_light_client_proof(block_height - 1, ...)` returns `None` — which happens when Citrea's prover has not yet produced (or has skipped) the proof for that height — the function immediately returns an error with no retry. This error propagates directly out of `handle_finalized_block`: [2](#0-1) 

The `handle_finalized_block` function is the entry point for all per-block verifier work: updating deposit/withdrawal state, updating finalized payouts, saving header chain proofs, and dispatching `LCPProcessed` events to the state manager. [3](#0-2) 

The state manager enforces strict sequential block processing:

```rust
if self.next_height_to_process != height {
    return Err(eyre::eyre!("Finalized block arrived to state manager out of order..."));
}
``` [4](#0-3) 

If `handle_finalized_block` fails, `LCPProcessed` is never dispatched, the state manager never advances `next_height_to_process`, and all subsequent blocks are rejected as out-of-order. The verifier is permanently halted at that block height.

### Impact Explanation

A permanent halt of the verifier's block processing means:

1. **Deposit and withdrawal tracking stops** — `update_citrea_deposit_and_withdrawals` is never called for the stuck block or any subsequent block.
2. **Watchtower challenge dispatch stops** — the state machine never receives `LCPProcessed`, so `WatchtowerChallenge` duties are never triggered. A malicious operator who initiates a kickoff after the halt can escape challenge within the challenge window, allowing them to claim the reimbursement output and steal bridged BTC collateral.
3. **Operator assert/disprove flow stops** — `AddRelevantTxsToTxSenderIfChallenged` and `SendOperatorAsserts` duties are never dispatched.

This is a liveness failure with material fund impact: bridged BTC and operator collateral UTXOs are at risk if a malicious operator times a kickoff to coincide with the halt.

### Likelihood Explanation

Citrea's light client prover produces one LCP per Bitcoin block. A gap can occur due to:
- Citrea prover downtime or restart
- Network partition between the verifier and the Citrea prover RPC
- A Citrea software bug that skips a block's proof

The current block's proof is waited for with a configurable timeout (default 10 minutes, `TEN_MINUTES_IN_SECS`). The previous block's proof has **zero** tolerance — a single `None` response causes the halt. This is an asymmetric design that makes the system fragile to any transient gap in proof availability. [5](#0-4) 

### Recommendation

Apply the same retry-with-timeout logic to the previous block's proof fetch:

```rust
let proof_previous = loop {
    if let Some(proof) = self.get_light_client_proof(block_height - 1, paramset).await? {
        break proof;
    }
    if start.elapsed() > timeout {
        return Err(eyre::eyre!(
            "Light client proof not found for block height {} after {} seconds",
            block_height - 1,
            timeout.as_secs()
        ).into());
    }
    tokio::time::sleep(Duration::from_secs(1)).await;
};
```

Alternatively, if the previous block's proof is structurally guaranteed to exist before the current block's proof is produced by Citrea's prover, add an assertion/comment documenting this invariant and add a bounded retry to handle transient RPC failures.

### Proof of Concept

1. Verifier is running normally, processing finalized Bitcoin blocks.
2. Citrea's light client prover has a transient gap: it produces the LCP for block `N` but not for block `N-1` (e.g., due to a restart that skipped block `N-1`).
3. When the verifier processes block `N`, `get_citrea_l2_height_range(N, ...)` successfully polls and obtains the LCP for block `N` (after waiting), then immediately calls `get_light_client_proof(N-1, ...)`.
4. `get_light_client_proof(N-1, ...)` returns `None`. The function returns `Err("Light client proof not found for block height: N-1")`.
5. `handle_finalized_block` propagates the error. `LCPProcessed` is never dispatched.
6. The state manager's `next_height_to_process` remains at `N`. All subsequent `NewFinalizedBlock` events for heights `N+1`, `N+2`, ... are rejected as out-of-order.
7. A malicious operator initiates a kickoff transaction. No watchtower challenge is ever sent. The operator claims the reimbursement output. [6](#0-5) [7](#0-6) [4](#0-3)
