### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes disproportionate preallocation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

`ThresholdKeys::read` accepts an attacker-controlled 16-bit `n` and uses it as the capacity for `Interpolation::Constant` before checking the remaining input or constructing validated `ThresholdParams`. [1](#0-0) 

### Finding Description

The deserializer reads `t`, `n`, and `i` directly from the input. [2](#0-1)  When the next byte declares constant interpolation, it immediately executes `Vec::with_capacity(usize::from(n))` and only afterwards attempts to read `n` scalar encodings. [3](#0-2)  Validation of the threshold parameters and interpolation semantics is deferred to `ThresholdKeys::new`, after all scalar and verification-share parsing. [4](#0-3) 

Consequently, a truncated message declaring `n = 65,535` causes an allocation of `65,535 * size_of::<C::F>()` bytes before returning an unexpected-EOF error. For a 32-byte scalar representation this is approximately 2 MiB, while the triggering prefix can remain only a few dozen bytes. [3](#0-2) 

### Impact Explanation

An unprivileged caller supplying untrusted bytes to the public `ThresholdKeys::read` API can force transient memory allocations vastly larger than the supplied input. [5](#0-4)  If the `Read` implementation is backed by a network stream and remains open rather than returning EOF, the allocation persists while `read_exact` waits for the first declared scalar, allowing repeated stalled requests to hold substantial memory and cause process memory exhaustion. [6](#0-5) 

### Likelihood Explanation

Only the serialized participant count and constant-interpolation marker need to be controlled; no valid signature, proof, key share, or complete message is required. [1](#0-0)  The primitive is bounded by `u16::MAX`, so a single short message does not allocate gigabytes, but concurrent or stalled deserialization requests amplify the effect.

### Recommendation

Do not preallocate from an untrusted element count. Initialize the vector with `Vec::new()` and push each scalar only after `C::read_F` succeeds, making allocated memory proportional to bytes actually received. Also validate `ThresholdParams` and enforce a protocol-specific maximum `n` before parsing variable-length data. [7](#0-6) 

### Proof of Concept

Starting from any valid serialized `ThresholdKeys<Secp256k1>`, mutate `n` to `u16::MAX`, change the interpolation marker to constant interpolation, and truncate immediately after that marker:

```rust
// crypto/dkg/src/lib.rs deserialization layout:
// u32 id_len | id[id_len] | u16 t | u16 n | u16 i | u8 interpolation | scalar...
use std::io::ErrorKind;
use frost::{curve::Secp256k1, ThresholdKeys};

let mut bytes = valid_secp256k1_keys.serialize().to_vec();

let id_len = u32::from_le_bytes(bytes[0..4].try_into().unwrap()) as usize;
let n_offset = 4 + id_len + 2;
let i_offset = n_offset + 2;
let interpolation_offset = i_offset + 2;

bytes[n_offset..i_offset].copy_from_slice(&u16::MAX.to_le_bytes());
bytes[interpolation_offset] = 0; // Interpolation::Constant
bytes.truncate(interpolation_offset + 1); // No scalar bytes follow.

let err = ThresholdKeys::<Secp256k1>::read(&mut bytes.as_slice()).unwrap_err();
assert_eq!(err.kind(), ErrorKind::UnexpectedEof);
```

Before returning `UnexpectedEof`, execution reaches `Vec::with_capacity(usize::from(n))` with `n = 65,535`. [3](#0-2)  A counting allocator or memory profiler will observe the approximately 2 MiB allocation for a 32-byte scalar representation despite the truncated input.
