### Title
Attacker-controlled `WWW-Authenticate` realm spoofs GitHub Enterprise sign-in, tricking Desktop into sending real GitHub PAT/OAuth credentials to a malicious git remote - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`PledgeManager::pledge` trusted a caller-supplied `signer` field instead of verifying it against `msg.sender`. GitHub Desktop's git credential trampoline has an analogous "identity spoofing" flaw: it classifies an unknown remote host as a GitHub/Enterprise endpoint based on an attacker-controlled `WWW-Authenticate` header value rather than any verified property of the actual host, and then launches a real sign-in flow *against that attacker-controlled host*.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential-helper trampoline, which calls `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` (lines 137-179). For hosts that are not `github.com`/`ghe.com`, the function inspects the `wwwauth[]` credential fields — values taken verbatim from the HTTP `WWW-Authenticate` response header sent by the remote server: [1](#0-0) 

If the attacker's server (a malicious git remote or a MITM/proxy answering the fetch/clone/push request) simply returns `WWW-Authenticate: Basic realm="GitHub"` on a 401, `getEndpointKind` returns `'enterprise'` — with **no verification that the host is actually GitHub Enterprise**. This value flows into `getCredential`: [2](#0-1) 

Since no account exists for this arbitrary attacker endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, where `endpoint` is the attacker's URL, and this directly drives a full "Enterprise sign-in" flow pointed at the attacker's origin: [3](#0-2) 

`beginEnterpriseSignIn` + `setSignInEndpoint(origin)` puts the sign-in store in `EndpointEntry`/`Authentication` state targeting the attacker's origin as the API endpoint, and the resulting authentication (PAT entry or OAuth browser flow) is performed against that attacker-controlled endpoint — see the sign-in store's endpoint-driven flow in `app/src/lib/stores/sign-in-store.ts` (`setEndpoint`, `authenticateWithBrowser`, `resolveOAuthRequest`). Once the user completes sign-in, the resulting `Account` (with a real GitHub token) is merged back into the credential response via `credWithAccount(cred, account)` and handed to Git for the attacker's remote: [4](#0-3) 

The broken invariant: the code treats a self-reported HTTP header string (`realm="GitHub"`) as proof of the remote's identity, exactly as `PledgeManager::pledge` treated a caller-supplied `signer` field as proof of the true caller. Neither value is authenticated against anything the attacker cannot control.

### Impact Explanation
An attacker who controls a git remote (or sits as a proxy/MITM in front of one, or hosts a malicious repository the victim clones/fetches/pushes to) can spoof the GitHub identity check purely via a response header. This can result in:
- The victim's real personal access token/password being typed into a UI flow whose underlying HTTP requests are configured against the attacker's `origin` (`setSignInEndpoint(origin)`), i.e. credential exfiltration.
- A legitimate OAuth authorization completing against a fake "enterprise" endpoint chosen by the attacker, effectively an unauthorized account-binding/token issuance flow directed at attacker infrastructure.
- No indication to the user that the "GitHub Enterprise sign-in" prompt they see is being triggered by an untrusted third-party server rather than an intentional user action.

This matches the report's core impact: an attacker-controlled remote/proxy response causing a sensitive action (credential submission/OAuth binding) to be executed under a spoofed identity that the code never independently verifies.

### Likelihood Explanation
The only prerequisite is that the victim performs a normal git operation (clone/fetch/push) against a repository or remote URL the attacker controls or intercepts, and that the attacker's server return a 401 with a crafted `WWW-Authenticate` header — no local access, malware, or unusual user action is required beyond a routine Desktop workflow. The existing `isGitHubHost` fallback check (`app/src/lib/api.ts` lines 2429-2491) is bypassed entirely by the `wwwauth[]` "happy path," so this heuristic is a real, reachable gap and not merely theoretical.

### Recommendation
Do not trust the `wwwauth[]`/`realm` value as sufficient evidence of GitHub identity. At minimum:
- Require the independent `isGitHubHost` verification (or an equivalent server-side check, e.g. presence of `x-github-request-id`) before treating an unknown host as `'enterprise'`, rather than short-circuiting on a self-reported header string.
- Clearly disclose the actual endpoint/host in the sign-in prompt so users can recognize when a "GitHub Enterprise sign-in" is being requested by an unexpected/unfamiliar host, and/or require explicit confirmation before initiating a credential-driven sign-in flow triggered by a background git credential request.

### Proof of Concept
1. Attacker hosts (or proxies) a git HTTPS remote, e.g. `https://evil.example.com/repo.git`.
2. Victim runs `git clone`/`fetch`/`push` against this remote from GitHub Desktop.
3. Attacker's server responds to the unauthenticated request with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as `wwwauth[]=Basic realm="GitHub"` to Desktop's credential helper.
5. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) matches `realm="GitHub"` and returns `'enterprise'` without contacting the real GitHub API.
6. `getCredential` finds no stored account for `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`.
7. `promptForGitHubSignIn` calls `dispatcher.beginEnterpriseSignIn(cb)` then `dispatcher.setSignInEndpoint(origin)` with `origin = https://evil.example.com`, driving the real Enterprise sign-in UI/flow against the attacker's origin.
8. The victim, believing this is a legitimate GitHub Enterprise prompt, enters a PAT or completes an OAuth flow that is validated/exchanged against the attacker-controlled origin.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
