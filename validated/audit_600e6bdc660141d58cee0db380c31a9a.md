## Analog identified: automatic, unlogged silent remote-URL rewrite driven by GitHub API data

### Title
Silent, attacker-influenced rewrite of a repository's `origin` remote URL via `updateRemoteUrl` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The bug report's core invariant — a sensitive piece of internal state (`reserve`) can be silently mutated by an outside actor through an internal setter with no event/log and no owner consent — has a structural analog in GitHub Desktop's `updateRemoteUrl` function. This function calls `gitStore.setRemoteURL(...)` (which shells out to `git remote set-url`) automatically, based solely on data returned by the GitHub API (`apiRepo.clone_url`), without any user prompt, confirmation dialog, or audit trail, silently changing where the user's `origin` remote points.

### Finding Description
`updateRemoteUrl` is invoked with a `GitHubRepository` (`gitHubRepository`) and an `IAPIRepository` (`apiRepo`) object that originates from the GitHub API response for that repository [1](#0-0) . If the current `defaultRemote.url` doesn't match `apiRepo.clone_url`, but does match the protocol and the previously cached `gitHubRepository.cloneURL`, the code calls `gitStore.setRemoteURL(...)` to rewrite the local git remote to the new `clone_url` value, with no confirmation from the user: [2](#0-1) 

`gitStore.setRemoteURL` in turn directly issues `git remote set-url` and just calls `emitUpdate()` — there is no persisted event log, no toast/dialog shown to the user, and no way for the user to see that the remote was changed unless they happen to open Repository Settings afterward: [3](#0-2) [4](#0-3) 

The matching logic (`urlMatchesRemote`) only compares `hostname`/`owner`/`name` triples parsed out of the URL — it does not verify who controls the API response, nor does it require any interactive confirmation (contrast this with `UpstreamAlreadyExists`, which does prompt the user before changing the `upstream` remote — see `app/src/ui/upstream-already-exists/upstream-already-exists.tsx` — showing that Desktop's own design pattern elsewhere is to ask first) [5](#0-4) .

`apiRepo` is the same kind of object an attacker can influence: any actor who can affect a GitHub/GHES API response for the tracked repository (e.g., a malicious/compromised GHES/API proxy in an enterprise-account setting, a repository-rename race, or a MITM'd API response for a non-.com endpoint) can cause `clone_url` to be an attacker-chosen value that satisfies the matching conditions (same hostname/owner/name mapping under `urlMatchesRemote`, or crafted to still "protocolsMatch"), driving Desktop to silently retarget the user's `origin` remote.

### Impact Explanation
If `origin` is silently repointed to an attacker-controlled endpoint that satisfies protocol/owner/name parsing, subsequent `git fetch`/`pull`/`push` operations performed by the user through Desktop's UI would be silently redirected. This can lead to:
- Fetching/merging attacker-supplied history into the user's working tree (silent corruption of what the user believes they are pulling).
- For HTTPS remotes, credential material (stored in the OS credential/keychain or supplied by the Git credential helper) being sent to the attacker's endpoint during the next push/fetch.
- No entry in the app's activity/log to warn the user the remote changed, since only `emitUpdate()` (an in-memory React state notification) fires — no persisted, user-visible audit trail exists.

### Likelihood Explanation
Exploitation requires the attacker to control (or be able to influence) the `IAPIRepository` object returned for the tracked repository — i.e., control of the GitHub API/GHES endpoint content for that repo, or the ability to intercept/tamper such a response (more plausible against self-hosted GHES/Enterprise endpoints than github.com over TLS). It also requires the specific state combination (protocols match, the previous cached `gitHubRepository.cloneURL` still matches the local remote, and the new `clone_url` doesn't match) to be true, which the code comments themselves acknowledge is an edge case ("I'm not sure when these early exit conditions would be met") [6](#0-5) . This narrows likelihood, but the underlying design gap — silently mutating a security-relevant setting from untrusted external data with no confirmation or logging — mirrors exactly the pattern flagged in the source report.

### Recommendation
Do not auto-apply remote URL changes derived from API responses. At minimum:
- Require explicit user confirmation before rewriting `origin` (as already done for the `upstream` remote via the `UpstreamAlreadyExists` dialog).
- Emit a persisted, visible notification/log entry whenever a remote URL is changed automatically by Desktop-internal logic (not just the ephemeral `emitUpdate()`).
- Consider removing the automatic-update behavior in `updateRemoteUrl` entirely and instead surface it as a prompt, consistent with the report's recommendation to "remove this functionality" for unchecked automatic state mutation.

### Proof of Concept
1. Have a Desktop user work with a repository backed by a GHES/enterprise endpoint (or any environment where the JSON returned for the tracked repo's API object can be influenced/tampered, e.g., a compromised or MITM'd internal GHES instance).
2. Ensure the local `origin` remote currently matches the cached `gitHubRepository.cloneURL` (the common case for any repo cloned through Desktop).
3. Cause the API response's `clone_url` for that repository to point to an attacker-controlled host/path that still round-trips through `urlMatchesRemote`/protocol parsing as "changed but same-shaped" (e.g. different owner or renamed repo hosted by the attacker).
4. On the next repository refresh, `updateRemoteUrl` runs `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` [7](#0-6)  silently executing `git remote set-url origin <attacker_url>` [4](#0-3) .
5. The user's next fetch/push in Desktop now targets the attacker's endpoint, with no dialog or persistent audit entry indicating the remote was altered.

Note: I could not locate, within the indexed portion of the codebase, the exact call site in `app-store.ts` that invokes `updateRemoteUrl` in production code (only test and dispatcher-adjacent references were found), so the precise UI-refresh trigger path (e.g., which refresh/poll routine calls it) could not be fully confirmed from available context — this would need direct inspection of `app/src/lib/stores/app-store.ts` for full path confirmation.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
