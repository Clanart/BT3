### Title
`ReceivedOutput::read` accepts unauthenticated bytes declaring arbitrary spendable funds without verifying the offset/script binding - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2021-45790 (unauthenticated upload of attacker-controlled content to a location where it is later trusted/interpreted), `ReceivedOutput::read` deserializes fully attacker-controlled bytes into a structure that downstream code treats as a confirmed, spendable output of the group's key. The legitimate constructor (`Scanner::scan_transaction`) cryptographically binds the output to the group key by matching `script_pubkey` against registered offset-derived scripts; the deserialization path performs no such validation, allowing a forged `ReceivedOutput` with an arbitrary value, outpoint, and offset.

### Finding Description
`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` map from derived P2TR script keys to scalar offsets, so `scan_transaction` only yields a `ReceivedOutput` when `output.script_pubkey` provably corresponds to `key + offset * G` [1](#0-0) . `ReceivedOutput` stores the `offset`, the `TxOut`, and the `outpoint`, but not the key it was derived for [2](#0-1) .

`ReceivedOutput::read` simply decodes three attacker-controlled fields — an arbitrary scalar offset via `Secp256k1::read_F`, an arbitrary `TxOut` (including its `value` and `script_pubkey`), and an arbitrary `OutPoint` — and returns the object with no consistency check [3](#0-2) . There is no verification that:

1. `output.script_pubkey` is the P2TR script of `key + offset * G` (i.e., that the group can actually spend it — `p2tr_script_buf` even returns `None` for odd keys, so not every (key, offset) pair is spendable at all [4](#0-3) );
2. the claimed `outpoint`/`output` exists on-chain or was ever seen by a `Scanner`.

The `register_offset` documentation itself acknowledges that offsets determine spendability and that arbitrary offsets can even introduce a script path spendable by a third party [5](#0-4)  — yet `read` accepts an arbitrary offset from the wire exactly like the "arbitrary directory" of the upload bug.

### Impact Explanation
Any component that persists, relays, or aggregates `ReceivedOutput`s via `serialize`/`read` (the type exposes `serialize`, `write`, and `read` as a public wire format [6](#0-5) ) can be fed a forged blob by an unprivileged party. The result is funds reported as received that are not spendable — the exact accepted impact class: the protocol can credit deposits that were never made to the group key, or worse, include a fabricated "input" in a `SignableTransaction`, causing either accounting inflation or a signer round over a non-existent UTXO. Because the offset is attacker-chosen, the forged output's script need not even be key-path spendable by the group.

### Likelihood Explanation
The attack requires only the ability to supply bytes to `ReceivedOutput::read` — no signatures, keys, or protocol participation. Any flow where scanner results transit an untrusted channel, are cached/restored, or are submitted by a peer is exploitable with a single crafted buffer. Severity is bounded by how the consumer uses the result (balance crediting vs. just indexing), hence High rather than Critical.

### Recommendation
Bind the `offset` to the spendable script at parse time: either store/derive the expected `script_pubkey` inside `ReceivedOutput::read` by accepting the scan key as a parameter and checking `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)`, or treat deserialized `ReceivedOutput`s as untrusted claims that must be re-confirmed against chain data (or re-scanned) before being credited as spendable. At minimum, document that `read` must only consume bytes produced by the local `Scanner` over authenticated storage.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs context
// Attacker crafts bytes for an output the group cannot spend:
let mut buf = vec![];
// offset: any scalar, e.g. 0
buf.extend(Scalar::ZERO.to_bytes());
// TxOut: arbitrary value + a script_pubkey NOT derived from the group key
// (e.g. pays to the attacker's own x-only key)
TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: attacker_p2tr_script,
}.consensus_encode(&mut buf).unwrap();
// OutPoint: attacker-controlled real UTXO they own
attacker_outpoint.consensus_encode(&mut buf).unwrap();

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.value() == 1_000_000_000 is now indistinguishable from a scanned
// group output; offset/script/outpoint were never validated.
```

A real deposit to the attacker's own P2TR key can be re-labeled as a group-owned output (or a wholly fabricated outpoint claimed), and any consumer that trusts `ReceivedOutput::read` output will account it as spendable group funds.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
