### Title
Division-by-zero DoS in mempool block-building when spend deduplication fully cancels a mempool item's cost - (File: chia/full_node/mempool.py)

### Summary
The kernel CVE is a division-by-zero triggered by attacker-controlled input reaching an unguarded arithmetic division. The analogous Chia code path is `Mempool.create_bundle_from_mempool_items`, which computes `fee / item_cost` for logging while assembling a block from mempool items, where `item_cost` is derived by subtracting a dedup "cost_saving" value from the item's total CLVM cost, with no check that the result is non-zero before dividing.

### Finding Description
When the full node assembles a block from the mempool, it loops over pending items and for each one computes: [1](#0-0) 

`item_cost = cost - cost_saving`, then immediately does `fee / item_cost` inside a `log.info` call with no zero-check. `cost_saving` comes from `IdenticalSpendDedup.get_deduplication_info`, which sums the previously-recorded isolated cost of any coin spend in the item that is "eligible_for_dedup" and matches an identical solution already committed by a prior mempool item spending the same coin: [2](#0-1) 

If a mempool item consists of a single coin spend that is dedup-eligible, and an earlier-processed item in the same block-building pass already spends that exact coin with the identical solution (a legitimate, supported scenario — dedup exists specifically to let multiple independent spend bundles reference/spend a shared coin with identical solutions, e.g. a common announcement/oracle coin), then `cost_saving` equals the *entire* isolated cost of that item's only coin spend. Since re-executing the same puzzle reveal and solution deterministically produces the same CLVM cost, `cost_saving == cost`, making `item_cost == 0`. The subsequent `fee / item_cost` raises an uncaught `ZeroDivisionError` inside the block-building loop.

### Impact Explanation
`create_bundle_from_mempool_items` is invoked during normal block-template assembly. An uncaught `ZeroDivisionError` here is a spend-triggered transaction-processing halt: a wallet user/spend-bundle submitter can craft two mempool items — one that spends a shared coin (with a specific, deterministic solution) as its only dedup-eligible spend, and a second item independently spending the same coin with the identical solution — to crash the node's block assembly path when both are present in the mempool at the same time.

### Likelihood Explanation
The dedup mechanism is a documented, reachable feature accessible to any unprivileged spend-bundle submitter: mark a spend "eligible_for_dedup", and have two independently-submitted spend bundles include an identical solution against the same coin. No special privileges, malicious peer, or node-internal state are required — only two ordinary spend bundle submissions via RPC before a block is assembled.

### Recommendation
Guard the division: skip logging (or treat the item's dedup savings as capped below the item's total cost, e.g. `item_cost = max(1, cost - cost_saving)`) whenever `item_cost` computes to `0`, and audit other cost-ratio computations in `mempool.py`/`eligible_coin_spends.py` for the same missing zero-check.

### Proof of Concept
1. Submit spend bundle A containing coin spend `C` (marked `eligible_for_dedup`) with solution `S`, cost `X`, plus other coins to make a distinct spend bundle A.
2. Submit spend bundle B whose *only* coin spend is the same coin `C` with the identical solution `S` (also `eligible_for_dedup`), fee `F` > 0.
3. Trigger block assembly (`create_bundle_from_mempool_items`) while both A and B are in the mempool. When B is processed after A's dedup entry for `C` is recorded, `cost_saving == B.cost`, so `item_cost = 0`, and `fee / item_cost` in the `log.info` call raises `ZeroDivisionError`, aborting block template creation.
