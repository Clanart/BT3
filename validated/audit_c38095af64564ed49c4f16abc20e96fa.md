### Title
Unbounded `Rs` count in `SchnorrAggregate::read` enables pre-validation CPU and memory exhaustion on untrusted bytes - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::read` accepts a fully attacker-controlled `u32` element count and then performs up to ~4.29 billion group-element decompressions and `Vec` pushes before any bound is enforced. This mirrors the reported bug class: expensive, unbounded pre-validation work performed on untrusted bytes before rejection. The analog exists in Serai's own code and stands independently of the external report.

### Finding Description

`crypto/schnorr/src/aggregate.rs:77-88`:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

Root cause, element by element:

- `len` is a raw `u32` from the input, so the loop bound is `0 ..= 4_294_967_295` with no cap tying it to a maximum aggregate size or to the actual remaining input length.
- Each iteration calls `C::read_G`, a full group-element decoding (canonical encoding check plus point decompression — e.g., field square roots for dalek-ff-group / ed448 / kp256 curves), which is expensive per element relative to the ~4-byte header that declared it.
- Every decoded point is pushed into `Rs`, so live memory grows linearly with the attacker's stream: `len` × `size_of::<C::G>()` with no ceiling. A sustained stream of valid encodings can drive resident memory into many gigabytes and trigger allocator/GC-style pressure before `read` ever returns.
- There is no early rejection: the count check (`self.Rs.len() != keys_and_challenges.len()`) only exists in `verify` at `aggregate.rs:128`, i.e., after all decoding and allocation already happened.
- `verify` compounds it: `Vec::with_capacity(2 * keys_and_challenges.len() + 1)` and a `multiexp_vartime` over the full attacker-sized pair list (`aggregate.rs:138-145`), so an attacker who passes a matching `keys_and_challenges` slice forces per-element scalar hashing (`weight`, `aggregate.rs:22-65`) plus multiexponentiation proportional to the supplied count.

By contrast, other length-prefixed deserializers in the codebase do bound their counts (e.g., `coordinator/src/tributary/transaction.rs:431` rejects point counts above `MAX_KEY_SHARES_PER_SET - 1`), confirming the missing bound here is inconsistent with the codebase's own hardening pattern.

Reachability: `SchnorrAggregate::read` is a public deserialization API on the in-scope `crypto/schnorr` crate operating on untrusted bytes, which is within the permitted reachability class (`read` APIs fed untrusted bytes). Note that the only in-tree caller found is `coordinator/tributary/src/tendermint/mod.rs` (out of the in-scope crates), so this assessment treats the reachable attack surface as the `read`/`verify` API itself as exposed to integrator-fed bytes.

### Impact Explanation

An unprivileged party supplying crafted serialized aggregate bytes can force:

- Unbounded CPU consumption in repeated point decompression before any validity check.
- Unbounded live-memory growth (`Rs` vector) proportional to attacker-controlled input, risking OOM termination of the host process.
- In `verify`, a multiexponentiation and transcript workload linear in the attacker's declared count — a CPU-amplification amplifier on top of the decode cost.

Because the request is rejected only after the expensive work, a `Err`/`false` outcome does not mitigate the denial of service — identical to the CoreDNS GET path failing with `400` only after decoding.

### Likelihood Explanation

Any deployment that deserializes attacker-supplied `SchnorrAggregate` encodings — e.g., aggregate signatures received in consensus messages, batches, or coordinator payloads — reaches this path without authentication or privilege. The attack requires no valid keys, signatures, or protocol state: only a large `len` prefix and a stream of syntactically valid point encodings (trivially generatable, e.g., repeated identity/generator encodings). Cost to the attacker is one byte-stream upload; cost to the victim is decompression CPU plus `len × sizeof(G)` memory.

### Recommendation

In `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs`):

1. Enforce a protocol-appropriate maximum aggregate size before the loop (e.g., a `MAX_AGGREGATE` constant or a caller-supplied limit), rejecting `len` above it prior to any `read_G`.
2. Bound `len` against the remaining input where the reader supports it (e.g., require `len ≤ remaining_bytes / encoded_point_size`) so a large prefix over a short buffer fails fast instead of looping until `read_exact` hits EOF.
3. Optionally reserve with `Vec::with_capacity` only after validation, or stream-decode into a bounded structure.
4. Apply the same early-count check philosophy to `verify` (reject `Rs.len()` mismatch is already present, but also cap `keys_and_challenges.len()` consistent with the same bound).

### Proof of Concept

Conceptual reproduction against `crypto/schnorr` (e.g., `C = Ristretto`):

```rust
use schnorr::aggregate::SchnorrAggregate;
use ciphersuite::Ristretto;
use std::io::Cursor;

// Craft input: u32::MAX declared count, followed by a stream of
// valid point encodings (e.g., the compressed generator repeated).
let mut input = u32::MAX.to_le_bytes().to_vec();
let point = <Ristretto as ciphersuite::Ciphersuite>::generator().to_bytes();
// Attacker streams as many valid encodings as desired; each is
// decompressed and pushed into `Rs` with no upper bound.
for _ in 0 .. 1_000_000 {
    input.extend(point.as_ref());
}

// Forces ~1M decompressions + ~32MB+ live Vec growth, and would
// continue to 4.29B iterations if the stream supplied more.
let _ = SchnorrAggregate::<Ristretto>::read(&mut Cursor::new(input));
```

Observed effect: `read` performs decompression and allocation for every supplied element despite the declared count being absurd; the only early exit is `read_exact` failing when the stream is exhausted — i.e., the expensive work scales with attacker input, exactly the pre-validation amplification class described in the report. A `verify` call with a matching-length `keys_and_challenges` slice additionally drives `weight()` hashing and `multiexp_vartime` over the full attacker-sized list.
