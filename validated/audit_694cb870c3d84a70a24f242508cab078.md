### Title
Non-atomic "Discard Changes" flow can permanently destroy working-directory content when the restore step fails on attacker-crafted tracked paths - (File: `app/src/lib/stores/git-store.ts`, documented in `docs/technical/discard-changes.md`)

### Summary
The bug-class in the report is: a multi-step "finalize" operation performs an irreversible destructive step (transferring/locking funds) *before* an externally-influenced step that can fail, and once that later step fails there is no way back — the destructive step cannot be undone and the whole operation is stuck. The Desktop analog is the `Discard Changes` feature, which is documented as a **three-step, non-atomic** sequence operating on paths that come from the working tree/index of a repository that can be populated by a cloned/fetched remote: (1) move files to OS trash, (2) `git reset` the paths out of the index, (3) `git checkout-index -f -u` to restore file contents from the index into the working directory.

### Finding Description
Per `docs/technical/discard-changes.md`, Discard Changes is implemented as: [1](#0-0) 
1. **Moving Files to Trash** — Desktop uses Electron's `shell.trashItem` to move *all new or modified files* out of the working directory first. [2](#0-1) 
2. **Reset Paths** — `git reset HEAD -- [path]` to unstage anything staged outside Desktop. [3](#0-2) 
3. **Checkout Paths** — `git checkout-index -f -u -- [path]` to repopulate the working directory from the index — this is the step that actually restores content for files that are being *kept* (i.e. any file not literally being discarded but whose path intersects with the operation, or where `git checkout-index` needs to reconstruct index-tracked names).

The destructive step (trash removal from disk) happens **first**, and the recovery-relevant git operations happen **after**. `git checkout-index` and `git reset` operate on the exact pathnames tracked in the repository's index — pathnames that originate from commits/trees that can be fully attacker-controlled in a cloned or fetched repository (arbitrary UTF-8 byte sequences, reserved Windows device names like `CON`/`NUL`/`AUX`, names ending in dot/space, colon sequences that collide with NTFS Alternate Data Streams, deeply nested paths that exceed `MAX_PATH`, or names that only differ by case/normalization on case-insensitive filesystems). Any of these can cause the underlying `git` CLI invocation for step 2/3 to fail on a specific filesystem while the trash step in `app/src/lib/app-shell.ts` (Electron's `shell.trashItem`) has already succeeded and removed the same content from disk. [4](#0-3) 

Because the trash step is not gated on the two git steps succeeding, and `discardChanges` in `git-store.ts` composes `moveItemToTrash`, `resetPaths`/`reset.ts`, and `checkout.ts`'s checkout-index call as sequential awaited operations rather than a single guarded transaction, a failure in the git steps (triggered by a pathological filename shipped in a cloned/fetched malicious repository) leaves the repository in a state where the file is already gone from the trash-safe location on disk and from the working directory, but Desktop's UI/state may not correctly reconcile that the discard "succeeded" only partially. I was not able to confirm within the available tool budget whether `git-store.ts` wraps this sequence in try/catch that surfaces an actionable error to the user or silently proceeds; this is the key uncertainty in this analog and needs to be verified against the actual function body before treating this as a confirmed, high-confidence vulnerability.

### Impact Explanation
If the discard flow does not correctly halt/roll back when the `git reset`/`checkout-index` step fails, a user could lose in-progress uncommitted work permanently (beyond what they intended to discard) as a direct result of file/path content that originated from an attacker-controlled cloned/fetched repository — mirroring the smart-contract bug's core defect of "irrecoverable loss caused by an externally-triggerable failure in a later stage of a supposedly-atomic operation."

### Likelihood Explanation
Likelihood is moderate and depends on details I could not fully confirm: it requires (a) the victim to have local modifications to a file whose tracked path is adversarially crafted (achievable purely by having such a file present/renamed in a cloned or fetched repository) and (b) the victim to invoke Discard Changes on it, and (c) confirmation that Desktop's error handling around this three-step sequence does not fully roll back/restore in the failure case. Because I could not verify point (c) against the actual implementation, this should be treated as a *candidate* finding requiring code-level verification rather than a fully confirmed exploit.

### Recommendation
Make the underlying `discardChanges` sequence transaction-like: perform `git checkout-index`/`reset` validation (or at least a dry-run / stash-based approach) before moving anything to the OS trash, or reorder operations so the git-index restoration step is validated to succeed before the trash step is committed, and ensure any failure in the git steps surfaces a clear, actionable error and leaves recoverable state (e.g., via `git stash` instead of direct `checkout-index`, which is naturally safer/atomic). This should be validated directly against `app/src/lib/stores/git-store.ts`'s `discardChanges`/`_discardChanges` implementation, `app/src/lib/git/reset.ts`, and `app/src/lib/git/checkout.ts` in a full read of the source (recommended: start a Devin session with full file access, since the indexed context here was insufficient to read the complete function bodies).

### Proof of Concept
1. Attacker publishes/pushes a repository containing a tracked file whose name is a Windows reserved device name (e.g. `CON`) or contains a trailing dot/space, or a very long path exceeding platform limits.
2. Victim clones/fetches this repository in GitHub Desktop and modifies that file locally.
3. Victim selects "Discard Changes" on that file. Desktop's `app-shell.ts` `moveItemToTrash` succeeds in removing the file from the working directory.
4. The subsequent `git reset`/`git checkout-index -f -u` step fails on that pathname on the affected platform/filesystem.
5. If (per the caveat above) this failure is not fully rolled back/recovered by Desktop, the user's local modifications (and possibly the file itself) are unrecoverable through the app, mirroring the "funds stuck because a later externally-influenced step reverts" pattern from the smart-contract report.

**Confidence caveat:** This finding is based on the documented multi-step, non-atomic architecture of Discard Changes in `docs/technical/discard-changes.md` and confirmed presence of `discardChanges`/`moveItemToTrash`/`resetPaths`/`checkoutPaths` in `app/src/lib/stores/git-store.ts`, `app/src/lib/git/reset.ts`, and `app/src/lib/git/checkout.ts`, but the exact error-handling/rollback logic in those functions was not retrievable within the tool budget available for this session, so this should be verified against the full source before being treated as conclusively exploitable.
