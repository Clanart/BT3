### Title
Null pointer dereference in `GetEvmTxIndex` when `MsgEVMTransaction.AsTransaction()` fails to unpack - ([File: evmrpc/tx.go])

### Summary
`GetEvmTxIndex` in `evmrpc/tx.go` dereferences the return value of `MsgEVMTransaction.AsTransaction()` without checking for `nil`, unlike the equivalent code path in `evmrpc/simulate.go`, which explicitly guards against this failure mode. This is directly analogous to the reported bug class: a lookup/derivation step can legitimately produce a `nil`/stale pointer, and a downstream function dereferences it without validation, crashing the process that serves the request.

### Finding Description
In `GetEvmTxIndex`, for each `MsgEVMTransaction` found while iterating a block's messages, the code does: [1](#0-0) 

```go
case *types.MsgEVMTransaction:
    etx, _ = m.AsTransaction()
    txHash = etx.Hash()
```

`m.AsTransaction()` returns `(*ethtypes.Transaction, error)`, and its error is explicitly discarded (`_`). If `AsTransaction()` fails to unpack the tx payload (malformed/unsupported EVM tx bytes embedded in a `MsgEVMTransaction`), it returns a `nil` transaction. The code immediately calls `etx.Hash()` on that `nil` pointer, which panics with a nil pointer dereference.

This is not a hypothetical: the exact same fallible call is guarded elsewhere in the codebase, showing the authors are aware `AsTransaction()` can return nil: [2](#0-1) 

```go
ethtx, _ := m.AsTransaction()
if ethtx == nil {
    // AsTransaction may return nil if it fails to unpack the tx data.
    continue
}
```

`GetEvmTxIndex` is missing this check. It is reachable from multiple public, unauthenticated EVM JSON-RPC endpoints that process committed block data supplied by an attacker's own submitted transaction:
- `eth_getTransactionByHash` calls it directly: [3](#0-2) 
- `eth_getTransactionReceipt` / receipt encoding path (`encodeReceipt`) calls it as well: [4](#0-3) 

Both call sites pass `filteredMsgs`/`msgs` built from `filterTransactions`, which decodes every transaction embedded in the block, including the attacker's own `MsgEVMTransaction`, and forwards it to `GetEvmTxIndex` without any additional validation of whether the embedded EVM payload can be unpacked.

### Impact Explanation
This matches the required impact bar: it crashes a default-configuration RPC node. Any node serving `eth_getTransactionByHash` or `eth_getTransactionReceipt` for a block containing a `MsgEVMTransaction` whose payload fails to unpack via `AsTransaction()` will panic inside the RPC handler goroutine. While Go RPC handlers are typically wrapped with `recover()` at a higher layer for a single request (limiting blast radius to that single request in the common case), the exact recoverability depends on where in the call graph the panic is caught; regardless, this is a validated code defect that departs from the pattern the codebase itself already fixed in `simulate.go`, and an attacker who can get a malformed `MsgEVMTransaction` included on-chain (i.e. any transaction sender) can reliably trigger it against every full/RPC node that later serves `eth_getTransactionByHash`/`eth_getTransactionReceipt` for that block.

### Likelihood Explanation
Likelihood is dependent on whether a `MsgEVMTransaction` that passes ante-handler/CheckTx validation but still fails `AsTransaction()` decoding at read time can exist (e.g. a mismatch between what ante-handler decoding accepts and what `AsTransaction()`'s stricter decode path accepts, or a payload that decodes differently at read-time than at execution-time). I was not able to fully verify this precondition within the available context — the definition of `AsTransaction()` in `x/evm/types/message_evm_transaction.go` was located but its full body was not inspected before the session ended, so I cannot state with certainty whether current ante-handler checks make this state entirely unreachable in practice. This is the main open question a reviewer must resolve before treating this as exploitable versus defense-in-depth.

### Recommendation
Add the same nil-check used in `evmrpc/simulate.go` to `GetEvmTxIndex` in `evmrpc/tx.go`:
```go
case *types.MsgEVMTransaction:
    etx, _ = m.AsTransaction()
    if etx == nil {
        continue
    }
    txHash = etx.Hash()
```
Additionally, audit all other call sites where `AsTransaction()`'s result is used without a nil check (e.g., `getEthTxForTxBz`, `filterTransactions`) to ensure the same defensive pattern is applied consistently, since these are all reachable from public JSON-RPC endpoints processing attacker-controlled transaction bytes.

### Proof of Concept
1. Submit a transaction containing a `MsgEVMTransaction` whose raw EVM-transaction bytes are constructed so that ante-handler/CheckTx-time decoding succeeds (transaction is included in a block) but `AsTransaction()`'s decode path used by `evmrpc` fails and returns `(nil, err)`.
2. Wait for the transaction to be committed in a block.
3. Call `eth_getTransactionReceipt` or `eth_getTransactionByHash` against any RPC node for that block/transaction (or any other transaction hash within the same block, since `GetEvmTxIndex` iterates all messages in the block looking for a match).
4. `GetEvmTxIndex` reaches the malformed `MsgEVMTransaction`, calls `etx, _ = m.AsTransaction()` (etx is nil), then `etx.Hash()` panics with a nil pointer dereference inside the RPC handler.
