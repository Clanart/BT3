## Analysis

The Hubble bug's core invariant break is: **a single non-transferable-token failure inside a settlement loop permanently blocks release of everything else queued alongside it, with no way to skip or isolate the bad item.**

The closest local analog is Hyperbridge's Intent Gateway escrow-release routine, `_withdraw`, which is used for both order **fills** and order **cancellations/refunds**: [1](#0-0) 

and its Tron port: [2](#0-1) 

Both iterate over `body.tokens[]` for a single order and call `safeTransfer`/`transfer` to a single `beneficiary` per token, reverting the whole function (and thus the whole order's escrow release) if any one transfer fails.

`_withdraw` is invoked from `_cancelFromDest` (cross-chain cancel, destination side) and from the `onGetResponse`/`onAccept` handlers that process the corresponding `RefundEscrow` message on the source chain: [3](#0-2) 

Crucially, this call chain is reached through `EvmHost.dispatchIncoming`, which treats module callback failure as *retryable* — it deletes the request receipt so the message can be redelivered later: [4](#0-3) 

This retry design assumes failures are transient. But if `beneficiary` (the fixed `order.user`) is blacklisted on just one of several escrowed tokens (e.g. USDC), `_withdraw`'s `safeTransfer` for that token will *always* revert — deterministically, forever. Because the loop is all-or-nothing, this also permanently blocks release of every *other* unrelated token escrowed for that same order (DAI, ETH, etc.), even though those transfers would individually succeed. Retrying the message (as `EvmHost` is designed to allow) can never help, since the underlying blacklist condition never clears. The funds are locked in escrow indefinitely.

### Title
Non-atomic multi-token escrow release in IntentsBase/`IntentGatewayV2._withdraw` lets one non-transferable token permanently lock all other escrowed assets of the same order - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_withdraw` (and its Tron equivalent `withdraw`) iterates over an order's `tokens[]` array and performs a `safeTransfer`/`.call` for each token to the same `beneficiary` in a single, non-catch-guarded loop. If any one of those per-token transfers permanently fails (e.g. `beneficiary` is on the token issuer's blacklist, the token is paused, or is a non-standard ERC-20 that reverts for the recipient), the whole function reverts, and none of the other tokens in that order — which would have transferred successfully — can ever be released. Since the callback is only reachable through `EvmHost.dispatchIncoming`'s "delete receipt / allow retry" mechanism, a permanent failure condition is indistinguishable from a transient one and the escrow is locked forever.

### Finding Description
`_withdraw` is the shared release path for order fills, cancellations, and refunds: [1](#0-0) 

`beneficiary` is fixed as `order.user` for refund/cancel flows and is derived from the immutable `Order` struct committed at order placement — it cannot be changed after the fact: [5](#0-4) 

When `_cancelFromDest` fires the `RefundEscrow` post request back to the source chain, or when a source-chain `cancelOrder`/`onGetResponse` flow triggers the refund, the source-chain module's `onAccept`/`onGetResponse` ultimately calls `_withdraw`, which is dispatched through `EvmHost.dispatchIncoming`: [4](#0-3) 

`dispatchIncoming` deletes the request receipt on failure specifically "so that it can be retried" — an assumption that failures are transient network/gas conditions, not a permanent blacklist state. Because `_withdraw` bundles every token of the order into one failure domain, a single permanently-blacklisted token poisons the whole order: every retry will hit the exact same revert, and the tokens that would have transferred fine are locked with it.

The same all-or-nothing pattern exists in the Tron port: [2](#0-1) 

### Impact Explanation
This causes permanent loss/lock of bridged escrow funds for legitimate, unrelated tokens in a multi-input order whenever one of the input tokens becomes non-transferable to the fixed beneficiary. Given Hyperbridge's Intent Gateway explicitly supports stablecoins like USDC/USDT (which have issuer-controlled blacklist functions) as order inputs, and orders frequently escrow multiple token types simultaneously, this is a realistic, unprivileged-triggerable fund-lock vector — matching the "loss of funds" impact category. No malicious relayer, prover, or admin is required; the condition can arise from ordinary regulatory/blacklist action on one escrowed asset.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a multi-token order whose beneficiary becomes blacklisted/frozen on at least one input token, and (b) that the order later needs a cancel/refund/fill release. Given USDC-style blacklists are a known and recurring real-world event (as in the referenced Hubble finding), and the Intent Gateway is designed for exactly this kind of multi-asset order, this is not a contrived edge case.

### Recommendation
Make `_withdraw` per-token fault-tolerant instead of all-or-nothing:
- Wrap each token transfer in a try/catch (or low-level call) and, on failure, credit the amount to a per-beneficiary/per-token "pending withdrawal" balance that can be claimed later via a separate pull-based `claim()` function, rather than reverting the entire batch.
- Alternatively, decrement `_orders[...]` and mark the order finalized before attempting transfers (already partially done), and only skip (not revert) the single failing token transfer, emitting an event so it can be recovered by governance or the pull-claim path.
- Ensure the same fix is applied to the Tron `withdraw` function and any other multi-asset settlement loop (e.g. `SweepDust` in the Tron `onAccept`, `_execute`'s dust sweep).

### Proof of Concept
1. User places a cross-chain order with `inputs = [USDC: 1000, DAI: 1000]`, `order.user = beneficiary`.
2. `beneficiary` gets added to USDC's blacklist (issuer action, independent of Hyperbridge) after order placement but before cancellation.
3. Order is not filled before `order.deadline`; `_cancelFromDest` (or `cancelOrder` from source, depending on flow) is triggered, dispatching `RefundEscrow{ commitment, tokens: [USDC, DAI], beneficiary }`.
4. On the source chain, `onAccept`/`onGetResponse` calls `IntentsBase._withdraw(body, isRefund: true, finalize: true)`.
5. Loop reaches `IERC20(USDC).safeTransfer(beneficiary, 1000)` → reverts because `beneficiary` is blacklisted.
6. The revert propagates out of `_withdraw`, causing the whole `onAccept`/`onGetResponse` call to fail.
7. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and allows retry — but every retry hits the same USDC blacklist revert.
8. Result: the 1000 DAI (which would have transferred successfully) is permanently stuck in `_orders[commitment][DAI]`, unrecoverable through any code path, alongside the USDC.

            to: abi.encodePacked(_instance(order.source)),

            payer: msg.sender

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
