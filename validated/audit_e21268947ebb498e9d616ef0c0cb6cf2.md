### Title
Scanner accepts dust outputs which burn more in fees than they are worth when spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` reports every transaction output whose `script_pubkey` matches a monitored script, with no minimum-value check. `SignableTransaction::new` in `send.rs` then accepts any `ReceivedOutput` as an input — dust checks are applied only to payments (`TransactionError::DustPayment` for `amount < DUST`) and to the change output, never to inputs. An unprivileged party who knows a Serai P2TR address (or any registered offset script) can send arbitrarily small outputs to it; those outputs are reported as wallet balance and, once used as inputs, each costs ~57 vbytes of fee to spend — far more than a dust input's value.

### Finding Description
`scan_transaction` matches solely on `output.script_pubkey` and pushes a `ReceivedOutput` for any value, including 1-sat outputs. [1](#0-0) 

`SignableTransaction::new` validates payment amounts against `DUST = 546` but sums inputs unconditionally: [2](#0-1) 

Each input contributes a full serialized `TxIn` plus a 64-byte witness signature to the weight used for `needed_fee` (≈230 WU ≈ 57 vbytes per the code's own accounting). [3](#0-2) 

This is the same bug class as the report's "dust left behind / over-transfer": value below the economically meaningful threshold is treated as usable balance, and the remediation (dust checks and sweeping leftovers) exists for outputs/change but is missing on the input/scanning side.

### Impact Explanation
Any Bitcoin user can send dust to a Serai deposit/change script_pubkey — the scripts are derivable from the public group key and registered offsets. The wallet reports these as received funds. If the input-selection logic consumes them (the processor aggregates available outputs), each dust input increases `needed_fee` by `fee_per_vbyte * 57+` sats while contributing near zero value, directly burning wallet funds to miners. Repeated dust outputs multiply the loss, and there is no mechanism to refuse or skip an under-dust `ReceivedOutput` — `TransactionError` has no "dust input" variant, so the only way to avoid the burn is to silently drop reported funds, breaking accounting.

### Likelihood Explanation
Sending dust to a known address is trivially cheap for the attacker relative to the ~57-vbyte-per-input cost imposed on the wallet at each spend, and requires no access to keys, validators, or internal APIs — just public transaction data, matching the reachability rules.

### Recommendation
Enforce a minimum value in `Scanner::scan_transaction` / `register_offset`-derived outputs (reject or flag outputs below `DUST`, mirroring `TransactionError::DustPayment`), or add a `DustInput`-style check in `SignableTransaction::new` so uneconomical inputs are rejected rather than silently fee-burned.

### Proof of Concept
1. Obtain a Serai-monitored script (group key → `p2tr_script_buf`, or any `register_offset` script).
2. Broadcast a transaction paying 546 sats (or less) to that script.
3. `Scanner::scan_transaction` returns a `ReceivedOutput` for it with no error.
4. `SignableTransaction::new(vec![dust_output, ...], payments, change, None, fee)` accepts it; `calculate_weight_vbytes` adds ~230 WU, raising `needed_fee` by `fee_per_vbyte * 57` — exceeding the input's contribution, so the dust donation is paid to miners.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

    // Expand this a full transaction in order to use the bitcoin library's weight function

      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()

        // The script pub key is not of a fixed size and does have to be used here

          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),

      // the value is fixed size (so any value could be used here)
