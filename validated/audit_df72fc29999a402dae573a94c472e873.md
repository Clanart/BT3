### Title
Panic on identity aggregate nonce in BIP-340 HRAm crashes the FROST signing process - (File: networks/bitcoin/src/crypto.rs)

### Summary
Analogous to the SurrealDB bug (a panic reachable by a protocol-authorized party via a crafted message), Serai's Bitcoin FROST code panics when `x()`/`x_only()`/`Hram::hram` is handed the point at infinity. A co-signer can deterministically force the aggregate FROST nonce `R = Σ(D_i + ρ_i·E_i)` to be the identity by crafting their preprocess nonce commitments, causing every honest participant's signer to panic inside `TransactionSignMachine::sign` → `Algorithm::sign_share` → `Hram::hram` → `x()`.

### Finding Description
`x()` in `networks/bitcoin/src/crypto.rs` panics on the point at infinity:

```rust
// networks/bitcoin/src/crypto.rs
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

and `Hram::hram` calls `x()` on both `R` (the aggregate nonce) and `A` (the group key) [1](#0-0) [2](#0-1) . The doc comment claims infinity has "negligible probability ... even with malicious participants present" [3](#0-2) , but that is wrong: FROST's per-participant `Curve::read_G` rejects individual identity points, not an identity *sum* [4](#0-3) . The aggregate nonce is a linear combination `Σ (D_i + ρ_i·E_i)` of attacker-influenced commitments, so a participant who transmits their `Preprocess` last can solve for commitments that cancel the sum to identity. When the honest signer runs `TransactionSignMachine::sign` [5](#0-4) , each `sig.sign(...)` computes `hram(R, A, sighash)` with `R` = identity, hitting `expect("point at infinity")` and aborting the process. The same panic is reachable in `Schnorr::verify`/`verify_share` during `complete` [6](#0-5) .

### Impact Explanation
An unprivileged counterparty in a Bitcoin threshold-signing session (e.g., one participant in a `TransactionMachine` multisig spend) causes a guaranteed panic — not a probabilistic one — in every participant that attempts `sign` or `complete` for that signing session. This is a denial of service of the signing process, matching the advisory's crash-via-crafted-protocol-message shape (CWE-248). Because the process crashes mid-session rather than returning a `FrostError`, the attacker can repeat it to permanently stall a multisig spend, and no restart-safe `io::Result`/`Option` error path exists to contain it.

### Likelihood Explanation
The attack requires the attacker to be a signing participant and to order their preprocess after observing others' commitments — achievable by simply waiting to broadcast last in the preprocess round, which is routine gossip behavior, not an assumption of collusion or broken consensus. The cancellation is computed deterministically: pick `E_a`, derive `ρ_a = hash_binding_factor(...)` over the full commitment set (computable since the attacker's own commitment is included), then set `D_a = −Σ_{j≠a}(D_j + ρ_j·E_j) − ρ_a·E_a`. The only nuance is that `ρ_a` depends on `E_a` but not on `D_a` ordering in a way that prevents solving for `D_a` last.

### Recommendation
Reject an identity aggregate nonce (and identity `R`/group key) inside `Hram::hram`'s callers — or inside `x()`/`x_only()` — by returning a `FrostError`/`Option` instead of `expect`ing non-infinity. Specifically, check `R.is_identity()` before computing the challenge in `sign_share`, `verify`, and `verify_share`, and treat an identity aggregate nonce as a proof of misbehavior attributable to the preprocess set rather than a process-fatal condition.

### Proof of Concept
1. Honest participants A, B and attacker M set up `TransactionMachine` multisigs via `SignableTransaction::multisig` for the same spend [7](#0-6) .
2. In the preprocess round, M waits for A's and B's `Preprocess` values `(D_j, E_j)`, computes `ρ_j` for all parties including itself via `Curve::hash_binding_factor` over the serialized commitment set, selects arbitrary `E_M`, then sets `D_M = −(Σ_{j≠M}(D_j + ρ_j·E_j)) − ρ_M·E_M`. Both `D_M` and `E_M` are non-identity, so `Curve::read_G` accepts them.
3. M publishes this preprocess; honest signers call `TransactionSignMachine::sign`, which slices the per-participant `Vec<Preprocess>` and invokes each `AlgorithmSignMachine::sign` → `sign_share` [8](#0-7) .
4. The aggregate `R = Σ(D_i + ρ_i·E_i)` is the identity; `Hram::hram(&R, &group_key, sighash)` invokes `x(&R)`, where `to_encoded_point(true).x()` is `None` and `expect("point at infinity")` panics, crashing the honest signer's process [9](#0-8) .

Caveat: I verified the panic site and the preprocess/`sign` plumbing in `send.rs`/`crypto.rs`, but did not fully trace `frost/src/sign.rs` to confirm no identity check on the aggregate nonce exists there; the finding assumes (per `Curve::read_G` and the doc comment's own admission of a panic path) that no such guard exists.

      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());

      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));

      <_>::conditional_select(&c, &-c, needs_negation(R))
    }

      .map(|c| {

          .iter()
