### Title
Deterministic reuse of cached FROST nonce seed across DKG confirmer contexts leaks validator secret key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives all FROST signing nonces deterministically from a 32-byte `CachedPreprocess` seed stored in the DB under a context that contains only `(b"DkgConfirmer", attempt)`. The seed is never deleted after a share is produced, and the context is not bound to the tributary spec, genesis, validator set, or the key pair being confirmed. When the same validator participates in DKG confirmations that collide on this context while signing a different message (`set_keys_message` binds `set`, `removed`, and the new `key_pair`), the same nonce is used to sign two distinct challenges, allowing recovery of the validator's private key from two public shares.

### Finding Description
In `preprocess_internal`, if `CachedPreprocesses::get(txn, context)` is `None`, a fresh preprocess is created with `OsRng` and its `cache()` seed (XOR-encrypted with `Blake2s256("Cached Preprocess Encryption Key" || context || key)`) is stored; otherwise the stored seed is decrypted and `AlgorithmSignMachine::from_cache` re-derives the *identical* nonces, since `seeded_preprocess` instantiates `ChaCha20Rng::from_seed(seed)` and feeds it to `Commitments::new` / `Curve::random_nonce` (`crypto/frost/src/sign.rs:121-144`, `crypto/frost/src/curve/mod.rs:94-121`).

The DB key is only `self.context = (b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:274-277`). Neither the spec/genesis, the participant list, nor the `key_pair` under confirmation is part of the context. `share` and `complete` both call `share_internal`, which re-loads the same seed and re-signs with the same nonces (`signing_protocol.rs:150-181, 304-327`).

The signed message is `set_keys_message(&self.spec.set(), &removed, key_pair)` (`signing_protocol.rs:296-300`), so any change to `removed` or `key_pair` produces a different challenge under the same nonce. Two Schnorr signature shares `s = r + c·x` and `s' = r + c'·x` over the same `r` yield `x = (s - s')/(c - c')`.

The module's own safety argument (lines 34-48) rests on BFT finality guaranteeing identical messages within a single attempt — it does not address reuse of the same cached seed *across* different sets/genesis contexts, since `attempt` restarts per set and the context has no genesis/set binding.

### Impact Explanation
Recovery of the validator's long-term Ristretto key. That key is the validator's Tendermint/tributary signing key (used in `Signer::sign` in `coordinator/tributary/src/tendermint/mod.rs`), so recovery enables forging tributary transactions and votes as that validator — full impersonation of a validator, not just a single signature forgery. Analogous to EOSDice: a deterministic seed reused under an attacker-influenced context breaks the nonce assumption.

### Likelihood Explanation
Requires two DKG confirmations under the same `(DkgConfirmer, attempt)` context with a differing message. This occurs naturally when the same validator set performs a re-key/rotation (identical participant list → identical MuSig aggregation coefficient → identical `original_secret_share` and identical seed → identical nonce) while `removed` or `key_pair` differs, or across consecutive sets where attempt counters repeat. Both are driven by ordinary on-chain events and processor messages rather than requiring a validator to be malicious; the re-use is automatic in the code (the seed is fetched, never cleared or rotated, at `signing_protocol.rs:137-145`).

### Recommendation
Include the full signing context in the `CachedPreprocesses` DB key (genesis/set, `removed` list, and `key_pair`), and delete the cached seed once a share has been published, regenerating it via `preprocess(&mut OsRng)` for any new signing context — matching the documented invariant that a cached preprocess must be used exactly once.

### Proof of Concept
1. Validator V participates in DKG attempt `a` for set `S`, producing share `s` over `msg = set_keys_message(S, removed_A, kp_A)`; seed `X` stored under key `(DkgConfirmer, a)`.
2. A subsequent confirmation (retry with a changed `removed` set, or a new set where V's MuSig coefficient is unchanged) again uses context `(DkgConfirmer, a)` → `CachedPreprocesses::get` returns `X` → identical nonce `r` and identical commitment.
3. The second share `s'` is produced for `msg' = set_keys_message(S', removed_B, kp_B)`, `msg' ≠ msg`, hence challenge `c' ≠ c`.
4. From the two public shares, `x_V = (s - s')·(c - c')⁻¹` recovers V's MuSig secret share; given the known aggregation coefficient, this yields V's actual private key.
