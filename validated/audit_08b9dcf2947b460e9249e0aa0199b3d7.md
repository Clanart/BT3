## Analysis Result

Confirmed analog found: the `x/erc20` IBC middleware's `OnAcknowledgementPacket`/`OnTimeoutPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20` flow swallows errors from a partially-completed, multi-step token conversion — the same "ignore the revert and treat it as done" pattern as the `StakeVault.leave()` try/catch bug, but here it can permanently lock user coins in the module account.

### Title
Silent error-swallowing in IBC ack/timeout ERC20 re-conversion permanently strands escrowed user coins in the `erc20` module account when the paired ERC20 `transfer` reverts (e.g., token paused) - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoinNativeERC20` performs a non-atomic, three-step conversion: (1) escrow the sender's Cosmos coin into the `erc20` module account, (2) call `transfer` on the paired ERC20 contract to move the tokens to the receiver, (3) burn the escrowed coins. [1](#0-0)  If step 2 reverts (for example the token contract is `Pausable` and paused, mirroring the external report's pause trigger), the function returns an error after step 1 has already mutated real chain state. [2](#0-1) 

The callers of this function on the IBC ack/timeout path do not propagate that error to fail the transaction; instead they emit a "failed" event and `return nil`: [3](#0-2)  This is functionally identical to the `StakeVault.leave()` `catch {}` block: a revert from a paused/misbehaving external contract is caught and the code proceeds as if the operation succeeded, leaving the escrow step's effects (already written to the real, non-cached `ctx`) permanently committed while the promised remediation (mint ERC20 to receiver, or refund) never happens.

### Finding Description
`ConvertCoinToERC20FromPacket` is invoked from `OnAcknowledgementPacket` (on error-ack) and `OnTimeoutPacket` (always) to convert refunded IBC coins back into their native ERC20 representation: [4](#0-3)  Both of these are invoked directly from `x/erc20`'s `IBCMiddleware.OnAcknowledgementPacket`/`OnTimeoutPacket`, which return whatever `im.keeper.OnAcknowledgementPacket`/`OnTimeoutPacket` returns to the IBC core `porttypes.IBCModule` interface: [5](#0-4)  Since `ConvertCoinToERC20FromPacket` always returns `nil` even when the inner conversion failed, the wrapping ack/timeout handler returns `nil`, so from IBC core's and baseapp's perspective the whole message succeeded — no revert of already-applied state changes made earlier in the same `ctx` (which is not a `CacheContext`, it's the same context threaded through) is triggered.

Inside `ConvertCoinNativeERC20`, the operations execute in this order using the live `ctx`:
1. `bankKeeper.SendCoinsFromAccountToModule` — moves the coin out of the sender/module escrow into `erc20` module account. [6](#0-5) 
2. `evmKeeper.CallEVM(...,"transfer", receiver, amount)` — calls `transfer` on the paired native ERC20 contract to send the equivalent ERC20 tokens to the receiver. [7](#0-6) 
3. `bankKeeper.BurnCoins` — burns the escrowed coin, only reached if step 2 succeeds. [8](#0-7) 

If step 2's EVM call fails (contract reverts) — which the default `ERC20MinterBurnerDecimalsContract` used for native ERC20 registration readily supports via its `Pausable` `pause()`/`unpause()` functions gated by `PAUSER_ROLE` — `CallEVM` returns an error and `ConvertCoinNativeERC20` returns before reaching the burn step: [9](#0-8)  `ConvertCoinToERC20FromPacket` catches this error, emits a `types.EventTypeFailedConvertERC20` event, and returns `nil` regardless: [3](#0-2)  The doc-comment even acknowledges the failure path exists ("such as an attempt to call a self-destructed ERC20 contract or an invalid function") and claims "the user receives the corresponding bank token from the TokenPair instead" — but that claim is false for this exact code path, because step 1 already moved the bank coin out of the user's account into the module account and it is neither burned, minted as ERC20, nor refunded back to the user. The coins are left permanently sitting in the `erc20` module account with no code path that returns them.

### Impact Explanation
This breaks the "Critical permanent freezing/theft of user funds" invariant. A registered native-ERC20 token pair (any token pair with `ContractOwner == OWNER_EXTERNAL` or otherwise implementing pausability/blacklisting/insufficient-liquidity reverts on `transfer`) can cause any unprivileged user's IBC-refunded (timeout or error-ack) coins to be irrecoverably escrowed in the `erc20` module account. This is not limited to the token owner deliberately harming themselves — any legitimate holder of that coin who happens to have an in-flight IBC transfer of it at the moment the underlying ERC20 is paused (by its own admin, for any reason, exactly analogous to the original report's trigger) will have their refund silently swallowed and their coins permanently stuck. This matches the allowed "Critical permanent freezing/locking of user funds" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high in normal operation: any token registered under `x/erc20` as a "native ERC20" pair whose ERC20 implementation is `Pausable` (the standard/example contract shipped in this very repo, `ERC20MinterBurnerDecimals.sol`, is `ERC20Pausable`) is exposed. No attacker privilege is required to trigger the vulnerable code path — an ordinary user's IBC transfer merely needs to time out or receive an error acknowledgement while the paired ERC20 contract is paused (or otherwise reverts `transfer`), which can be triggered by ordinary contract owner actions or even adversarially timed by a user who colludes with/controls the contract's pauser role to trap other users' funds mid-flight, or simply happens as an operational hazard. Unlike the original StakeVault report (which required a hard-to-force revert), pausing an ERC20 token contract is a common, expected, non-privileged-relative-to-the-chain operation.

### Recommendation
Do not swallow the error from `ConvertCoinNativeERC20` in `ConvertCoinToERC20FromPacket`. Either:
- Execute the entire conversion (escrow + transfer + burn) within an isolated `ctx.CacheContext()` and only `Write()` the cache if all three steps succeed, so a mid-sequence revert leaves the original bank balance of the sender untouched (true "leave the user with the bank token" behavior as the docstring promises); or
- Reorder operations so the ERC20 `transfer` (the step that can revert) happens before the irreversible bank-side escrow/burn, following a check-effects-interactions pattern; or
- Propagate the error so the whole ack/timeout message fails atomically rather than emitting a "failed" event and returning `nil`.

### Proof of Concept
1. Register a native ERC20 token pair for a `Pausable` ERC20 contract (e.g. deploy `ERC20MinterBurnerDecimals.sol` and register it via `MsgRegisterERC20`) with `ContractOwner = OWNER_EXTERNAL`, granting a pauser key.
2. A user converts some of this coin to the ERC20 form and back is unnecessary — simply have the user send an ICS-20 IBC transfer of this Cosmos-coin representation to another chain with a very short timeout.
3. Before the timeout fires (or before an error ack arrives), the pauser calls `pause()` on the ERC20 contract.
4. The packet times out (or is error-acked). IBC core calls `x/erc20`'s `IBCMiddleware.OnTimeoutPacket` → `Keeper.OnTimeoutPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
5. `SendCoinsFromAccountToModule` succeeds, escrowing the coin from the sender into the `erc20` module account.
6. `CallEVM(..., "transfer", ...)` reverts because the contract is paused; `ConvertCoinNativeERC20` returns an error.
7. `ConvertCoinToERC20FromPacket` emits `EventTypeFailedConvertERC20` and returns `nil`; `IBCMiddleware.OnTimeoutPacket` returns `nil` — the whole message is treated as successful.
8. Final state: sender's bank balance was debited during step 5 and never restored; no ERC20 tokens were minted to the sender either. The funds are permanently stranded in the `erc20` module account balance for that denom, with the sender able to observe an emitted failure event but with no operational recovery path in the code.

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}

// OnAcknowledgementPacket implements the IBCModule interface.
// It refunds the token transferred and then automatically converts the
// Cosmos Coin to their ERC20 token representation.
func (im IBCMiddleware) OnAcknowledgementPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	acknowledgement []byte,
	relayer sdk.AccAddress,
) error {
	var ack channeltypes.Acknowledgement
	if err := transfertypes.ModuleCdc.UnmarshalJSON(acknowledgement, &ack); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet acknowledgement: %v", err)
	}

	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnAcknowledgementPacket(ctx, channelVersion, packet, acknowledgement, relayer); err != nil {
		return err
	}

	return im.keeper.OnAcknowledgementPacket(ctx, packet, data, ack)
}

// OnTimeoutPacket implements the IBCModule interface.
// It refunds the token transferred and then automatically converts the
// Cosmos Coin to their ERC20 token representation.
func (im IBCMiddleware) OnTimeoutPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) error {
	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnTimeoutPacket(ctx, channelVersion, packet, relayer); err != nil {
		return err
	}

	return im.keeper.OnTimeoutPacket(ctx, packet, data)
}
