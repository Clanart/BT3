### Title
`VLMGP.unlock()` and `forceUnLock()` never decrement `totalAmountInCoolDown`, permanently corrupting `totalLocked()` accounting - (File: `VLMGP.sol`)

### Summary
`VLMGP.startUnlock()` increments the global `totalAmountInCoolDown` counter, but the two user-callable functions that complete a cooldown — `unlock()` and `forceUnLock()` — never decrement it back. Only `cancelUnlock()` correctly performs the offsetting subtraction. This mirrors the report's root-cause pattern: a decrement/"burn" operation on user state is implemented as an incomplete/inconsistent state update rather than a full, symmetric reversal, leaving protocol-wide accounting permanently wrong.

### Finding Description
In `startUnlock()`, an ordinary wallet initiating a cooldown correctly bumps the global counter: [1](#0-0) 

`cancelUnlock()` is the only path that reverses this, explicitly subtracting the slot's `amountInCoolDown` from the global tally before zeroing the slot: [2](#0-1) 

However `unlock()`, which finalizes a cooldown and pays the user, zeroes the per-user slot but never touches `totalAmountInCoolDown`: [3](#0-2) 

Likewise `forceUnLock()`, which lets a user exit early with a penalty, also zeroes the slot but omits the global decrement: [4](#0-3) 

`totalLocked()` is derived from this counter and is consumed externally by `WombatBribeManager.vewomPerLockedMgp()`: [5](#0-4) [6](#0-5) 

Every time any user completes a normal `unlock()` or a `forceUnLock()`, `totalAmountInCoolDown` remains inflated by that user's already-settled amount even though `totalSupply()` (backed by `MasterMagpie` staking balances) correctly drops. Over the lifetime of the protocol, as many users lock/cooldown/unlock through the normal flow, `totalAmountInCoolDown` accumulates monotonically and is only ever reduced by the much less common `cancelUnlock()` path.

### Impact Explanation
`totalLocked() = totalSupply() - totalAmountInCoolDown()` becomes permanently understated and, since both operands change independently over time, `totalAmountInCoolDown` can eventually exceed `totalSupply()`, causing the subtraction to underflow and revert. `WombatBribeManager.vewomPerLockedMgp()` — a value used in vote-weighting/bribe accounting — directly depends on `totalLocked()`, so this corrupts a core governance-voting-weight computation for all users and can be permanently bricked (persistent revert) once the counters diverge enough, with no way for users to reset it since `cancelUnlock()` can only fix amounts that are still mid-cooldown, not ones that have already completed via `unlock()`/`forceUnLock()`.

### Likelihood Explanation
High likelihood: `unlock()` and `forceUnLock()` are core, frequently used, fully unprivileged user functions (no admin/governance/mock dependency). Every normal exit from a cooldown slot triggers the missing decrement, so the divergence between `totalSupply()` and `totalAmountInCoolDown()` grows continuously under ordinary protocol usage, not through an edge case.

### Recommendation
Add `totalAmountInCoolDown -= slot.amountInCoolDown;` in both `unlock()` (before/after zeroing `slot.amountInCoolDown`) and `forceUnLock()`, mirroring the correct pattern already used in `cancelUnlock()`, so the global counter stays symmetric with per-user slot state.

### Proof of Concept
1. User A calls `lock()` then `startUnlock(1000)` — `totalAmountInCoolDown += 1000`.
2. After the cooldown period elapses, User A calls `unlock(slotIndex)` — the 1000 MGP is paid out and `slot.amountInCoolDown` is zeroed, but `totalAmountInCoolDown` still includes the 1000.
3. Repeat with more users completing normal `unlock()`/`forceUnLock()` cycles; `totalAmountInCoolDown` keeps growing while `totalSupply()` correctly shrinks with each real lock removal.
4. Once `totalAmountInCoolDown > totalSupply()`, any call to `totalLocked()` (and therefore `WombatBribeManager.vewomPerLockedMgp()`) reverts due to underflow, permanently breaking that voting-weight computation for all callers until upgraded. [3](#0-2) [4](#0-3)

        _checkIdexInBoundary(msg.sender, _slotIndex);

        _checkInCoolDown(msg.sender, _slotIndex);

        totalAmountInCoolDown -= slot.amountInCoolDown; // reduce amount to cool down accordingly
