Based on my investigation, I found a genuine analog of the check-after-effect pattern in the auction bid pool.

### Title
Bid pool `AddBid` mutates pool state (`insertBid`) before the gas-limit check can fail, leaving an unvalidated/failed bid persisted as the block's winner - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.AddBid` performs its state-mutating `insertBid` step *before* the final `getBidTxGasLimit` check completes, and only returns an error afterward without rolling back the insertion. This mirrors the reported pattern: a "safety"/validity check occurs after state has already changed, so a bid that ultimately fails validation still remains committed as the authoritative state.

### Finding Description
`AddBid` executes in this order: [1](#0-0) 

1. `validateBid(bid)` – stateless/signature/format checks.
2. `insertBid(bid)` – **mutates** `bp.bidMap`, `bp.bidTargetMap`, and critically `bp.bidWinnerMap[blockNumber][sender] = hash`, which marks this sender as the winning bidder for that block/target tx. [2](#0-1) 
3. Only *after* the bid is already recorded as the block's winner does the code call `getBidTxGasLimit(bid)`. If that call errors, `AddBid` returns the error to the caller — but the bid remains in `bidMap`/`bidTargetMap`/`bidWinnerMap` because there is no compensating removal on this failure path.

Because `bidWinnerMap` is used by `senderHasDifferentWinner` to reject any *other* bid from a different context for the same slot/sender, and `bidTargetMap` is what the block-builder queries to attach a bid transaction to its target transaction, a bid that failed the final gas-limit validation is nevertheless left registered as the winning bid for its target block/tx, exactly as JOJO's example let unsafe state changes persist before the "is this actually valid" check landed.

### Impact Explanation
If `getBidTxGasLimit` fails (e.g., due to an internal estimation error) after the bid has already been recorded as a `bidWinnerMap` entry, the pool is left in an inconsistent state:
- The submitting sender occupies the winner slot for that block/target, blocking legitimate future bids from being accepted (`senderHasDifferentWinner` will reject them) — a griefing/DoS vector against the auction's fairness guarantee.
- The `bidTargetMap` entry can still be picked up by the block-building path when the target transaction is detected in the pool [3](#0-2) , potentially causing a bid whose `GasLimit` was never properly set (since `bid.SetGasLimit(gasLimit)` is only reached if `getBidTxGasLimit` succeeds) to be used with a stale/zero/default gas limit, which is a form of "acceptance of an invalid bid/transaction" into block assembly.

### Likelihood Explanation
This is reachable directly from the public `auction_submitBid` RPC by any bidder/searcher who can trigger a `getBidTxGasLimit` failure (e.g., malformed `To`/call data causing gas-estimation to error, or transient EVM/backend errors), requiring no privileged access. However, I was not able to fully confirm the exact conditions under which `getBidTxGasLimit` fails or verify definitively that the stale winner-slot entry is consumed unmodified by the block-builder in `builder.go`/`getter.go`, since I ran out of tool budget before reading those files in full. This uncertainty should be resolved by reviewing `kaiax/auction/impl/builder.go` and the `getBidTxGasLimit` implementation directly.

### Recommendation
Move `getBidTxGasLimit` computation before `insertBid`, or wrap `insertBid` + `getBidTxGasLimit` in a single critical section that rolls back (`delete` from `bidMap`/`bidTargetMap`/`bidWinnerMap`) on any failure after insertion, so a bid is only considered "in the pool" once every check (including gas-limit estimation) has succeeded.

### Proof of Concept
1. Craft a bid that passes `validateBid` (valid signatures, in-range block number, positive bid, size/gas-limit under caps).
2. Ensure the bid's `To`/`Data` causes `getBidTxGasLimit` to return an error (e.g., a call that reverts during gas estimation).
3. Submit via `auction_submitBid` → `BidPool.AddBid`.
4. Observe: `AddBid` returns an error to the caller, but `bp.bidWinnerMap[blockNumber][sender]` and `bp.bidTargetMap[blockNumber][targetTxHash]` are still populated with this bid (verifiable by attempting a second, valid bid from a different sender for the same target/block and observing `ErrBidSenderExists`/replacement behavior tied to the "failed" bid).

// AddBid adds a bid to the bid pool.
// Required mutex is locked in each function.
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) insertBid(bid *auction.Bid) error {
	bp.bidMu.Lock()
	defer bp.bidMu.Unlock()

	var (
		blockNumber  = bid.BlockNumber
		targetTxHash = bid.TargetTxHash
		sender       = bid.Sender
	)

	// Re-check bidWinnerMap here — two concurrent bids can pass validateBid together.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		return auction.ErrBidAlreadyExists
	}
	if bp.senderHasDifferentWinner(bid) {
		return auction.ErrBidSenderExists
	}

	// If same block number, same target tx hash exists, replace it if it's better
	if existingBid, ok := bp.bidTargetMap[blockNumber][targetTxHash]; ok {
		// FCFS if the bid is the same.
		if existingBid.Bid.Cmp(bid.Bid) >= 0 {
			return auction.ErrLowBid
		}

		logger.Trace("Replace bid", "old", existingBid.Hash(), "new", bid.Hash())
		delete(bp.bidMap, existingBid.Hash())
		delete(bp.bidWinnerMap[blockNumber], existingBid.Sender)
	} else {
		if int64(len(bp.bidMap)) >= bp.maxBidPoolSize {
			logger.Info("Bid pool is full", "maxBidPoolSize", bp.maxBidPoolSize, "bid", bid.Hash())
			return auction.ErrBidPoolFull
		}
	}

	hash := bid.Hash()

	bp.initializeBidMap(blockNumber)

	bp.bidMap[hash] = bid
	bp.bidTargetMap[blockNumber][targetTxHash] = bid
	bp.bidWinnerMap[blockNumber][sender] = hash

	numBidsGauge.Update(int64(len(bp.bidMap)))

	logger.Trace("Add bid", "bid", hash)

	return nil
}
