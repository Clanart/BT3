### Title
Ruby `Message#==`/`#eql?`/`#hash` treat wire-distinct messages as identical because unknown fields are stripped before comparison - (File: ruby/ext/google/protobuf_c/shared_message.c, ruby/lib/google/protobuf/ffi/message.rb)

### Summary
Ruby's protobuf `Message#hash`, `#eql?`, and `#==` are implemented by re-serializing the message with `kUpb_EncodeOption_SkipUnknown | kUpb_EncodeOption_Deterministic` and then comparing/hashing the resulting bytes, rather than comparing the true parsed wire content. Any bytes in the original input that landed in unknown fields (fields not present in the trusted schema known to this binary) are discarded before the equality/hash value is computed. Two distinct, attacker-controlled binary payloads that differ only in unrecognized field numbers therefore parse into two `Message` objects that are `==`/`eql?` and hash identically, even though they are not the same message.

### Finding Description
The C extension backend computes the hash via `shared_Message_Hash`: [1](#0-0) 

The comment explicitly states the design intent ("Hash a deterministically serialized payloads with no unknown fields"), which is fine for the *serialization-not-canonical* contract (repeated serialization of the *same in-memory message* is stable), but it is misapplied as the basis for object identity/equality across two independently-parsed messages.

The FFI backend implements the same pattern for both `eql?`/`==` and `hash`, re-encoding each message with `Upb_Encode_Deterministic | Upb_Encode_SkipUnknown` and comparing the resulting byte buffers via `memcmp`, or hashing the resulting string: [2](#0-1) 

This mirrors the ZetaChain finding's failed invariant exactly: a derived value (there, a ballot `index` computed as a hash over a message's fields; here, a hash/equality computed over a re-serialization of a message) is used as the sole criterion for "these are the same event/object," but the derivation silently omits data that is present on the wire but not accounted for by the current schema/registry (there: newly-added or not-yet-hardcoded fields like `eventIndex`, `Asset`, `GasLimit`; here: unknown field numbers not registered in the `MiniTable`/descriptor used for this parse). Protobuf's own documented invariant is that deterministic serialization only guarantees "for a given binary, equal messages will serialize to the same bytes" and is explicitly *not canonical* and *not guaranteed stable when unknown fields exist or schemas change*: [3](#0-2) 

Using that non-canonical, unknown-field-stripping serialization as an equality/hash oracle breaks the stronger invariant that `Message#==`/`#eql?`/`#hash` (as used for Ruby `Hash`/`Set` deduplication, `uniq`, or any "already processed" bookkeeping keyed by message identity) must not conflate two distinct inputs into "the same object."

### Impact Explanation
Consuming applications routinely rely on `Message#hash`/`#eql?` (directly, or transitively via Ruby `Hash`/`Set`/`Array#uniq`) to deduplicate protobuf messages received from clients — e.g., idempotency/replay-protection checks ("have we already processed this event/message?"), caches keyed by message content, or set-based dedup of a batch of untrusted inputs. Because unknown fields are stripped prior to hashing/comparison, an attacker can craft two binary payloads that are byte-for-byte different (differing only in field numbers not known to the older/current schema in use) and have them collapse to the same `hash`/`eql?` result. This is the mirror image of the ZetaChain bug (there, unrelated field changes caused two semantically-identical events to get *different* indices, enabling replay; here, the flaw causes two content-distinct payloads to get the *same* identity, enabling one to silently mask/spoof the "already-seen" status of the other, or to bypass a dedup/anti-replay gate that trusts `Message` equality). Any application-level anti-duplicate or identity check built on native Ruby protobuf message equality is unsound against forward-incompatible/extra fields.

### Likelihood Explanation
This is directly reachable through the public, documented Ruby API surface (`Message#==`, `#eql?`, `#hash`), triggered purely by parsing two bounded, valid binary protobuf payloads through the standard `ParseFrom` API and then comparing/hashing the resulting objects — no privileged access, malicious schema, or resource exhaustion required. The only precondition is that the payloads contain field numbers unknown to the parsing binary's registered descriptor/MiniTable (a common, expected situation with forward-compatible protobuf evolution, exactly analogous to the ZetaChain report's "newly added field" scenario), which any ordinary client can construct at will.

### Recommendation
- Do not derive `Message#hash`/`#eql?`/`#==` from a `SkipUnknown` serialization. Equality/hash for message *identity* purposes should account for unknown fields (or explicitly document that unknown-field content is excluded from equality, requiring callers not to rely on it for security-relevant dedup).
- If unknown-field-agnostic comparison is intentional (to match semantic/schema-aware equality), provide a clearly separate, explicitly-named API (e.g., `#semantic_eql?`) rather than overriding the language-level `==`/`hash`/`eql?` contract that Ruby collection classes (and downstream security-sensitive dedup logic) implicitly depend on.
- Add regression tests asserting that two messages differing only in unknown fields are *not* `eql?`/do *not* hash equal, mirroring the analogous protobuf test pattern already used elsewhere in the codebase (e.g., `upb/message/test.cc` `ExtensionsSkipUnknownDeterministic`), but asserting the opposite outcome for identity/equality checks.
- Audit other language bindings' `Message` equality/hash implementations (C++, Java, Python, C#) for the same unknown-field-stripping pattern before relying on them for dedup semantics.

### Proof of Concept
Conceptual reproduction (Ruby FFI/C-extension backend):
1. Define a schema `Foo { optional int32 a = 1; }` in a binary that has already been built (i.e., the running process's descriptor only knows field 1).
2. Construct two raw wire payloads:
   - `payload1`: field 1 = 5, plus an extra unknown field 99 with value "AAAA".
   - `payload2`: field 1 = 5, plus an extra unknown field 99 with value "BBBB" (different unknown-field content).
3. Parse both: `msg1 = Foo.decode(payload1); msg2 = Foo.decode(payload2)`.
4. Observe `msg1 == msg2` returns `true` and `msg1.hash == msg2.hash` is `true`, per the implementation at `ruby/lib/google/protobuf/ffi/message.rb:105-138` (and the equivalent C-extension path using `shared_Message_Hash` in `ruby/ext/google/protobuf_c/shared_message.c:16-36`), even though `payload1 != payload2` on the wire and their unknown-field content differs.
5. Any application code using `{msg1 => :seen}.key?(msg2)` or `[msg1, msg2].uniq.size == 1` for a "duplicate submission" check would incorrectly treat `msg2` as an already-processed duplicate of `msg1` (or vice versa), despite them being distinct payloads.

I did not have a live Ruby build environment to execute this PoC in this session; the behavior is derived directly from reading the cited implementation (`SkipUnknown | Deterministic` encode-then-compare/hash logic) rather than from an executed test run.

uint64_t shared_Message_Hash(const upb_Message* msg, const upb_MessageDef* m,
                             uint64_t seed, upb_Status* status) {
  upb_Arena* arena = upb_Arena_New();
  if (!arena) {
    upb_Status_SetErrorMessage(status, "Out of memory");
    return 0;
  }
  char* data;
  size_t size;

  // Hash a deterministically serialized payloads with no unknown fields.
  upb_EncodeStatus encode_status = upb_Encode(
      msg, upb_MessageDef_MiniTable(m),
      kUpb_EncodeOption_SkipUnknown | kUpb_EncodeOption_Deterministic, arena,
      &data, &size);

  if (encode_status == kUpb_EncodeStatus_Ok) {
    uint64_t ret = _upb_Hash(data, size, seed);
    upb_Arena_Free(arena);
    return ret;
  }
