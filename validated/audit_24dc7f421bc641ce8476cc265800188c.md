### Title
Embedded NUL byte in a crafted commit message desynchronizes `createLogParser`'s field framing, letting attacker content land in the `sha` slot and reach `git log <sha>` as an unguarded positional argument - ([File: app/src/lib/git/git-delimiter-parser.ts], [File: app/src/lib/git/log.ts])

### Summary
The external report describes a `msggen` framing bug where a field ends up "in a different place" because the generator's output assumed a fixed field layout that a particular input could violate. The same broken-invariant class exists in Desktop's `createLogParser` (`app/src/lib/git/git-delimiter-parser.ts:18-39`), which parses `git log --format=...` output by blindly slicing the NUL-delimited stream into fixed-size chunks. If a commit's message content itself contains a literal NUL byte, the fixed chunking assumption breaks and every subsequent field — including the `sha` field used later as a raw command argument — can be desynchronized and populated with attacker-controlled bytes.

### Finding Description
`createLogParser` (`app/src/lib/git/git-delimiter-parser.ts:18-39`) builds the git format string by joining fields with the literal `%x00` byte and passes `-z` to git. Its `parse` function then does:
```
for (let i = 0; i < records.length - keys.length; i += keys.length) { ... }
```
This assumes each commit record contributes exactly `keys.length` NUL-separated tokens. That assumption is enforced by git only as long as none of the *value* fields (`%s`, `%b`, `%an`, etc.) themselves contain a NUL byte, since NUL is being reused both as the git-controlled `%x00` separator and as the -z record terminator.

Git does not sanitize embedded NUL bytes out of a commit's message when pretty-printing it — a commit message is arbitrary blob content. A normal `git commit` won't let you type a NUL, but an attacker who controls a remote/cloned repository can construct such a commit with low-level plumbing (`hash-object`, `commit-tree`, or a hand-crafted pack) and have Desktop fetch/clone it. This is the exact same bug class as the ElementsProject report: a hidden fixed-layout assumption in a delimiter-based decoder that a single crafted input value can violate, silently reassigning subsequent fields.

`getCommits` (`app/src/lib/git/log.ts:120-205`) uses this parser with 9 fields per commit (`sha, shortSha, summary, body, author, committer, parents, trailers, refs`). An embedded NUL in one commit's `%b`/`%s` shifts the chunk boundaries for that commit and all following commits in the same `git log` batch, so the `Commit.sha` field of a *later, unrelated* commit can end up populated with attacker-chosen text taken from message/trailer content rather than the real 40-hex SHA that git produced.

That corrupted `sha` string is later handed to `getChangedFiles` (`app/src/lib/git/log.ts:220-245`):
```
const args = ['log', sha, '-C', '-M', '-m', '-1', ... '--']
```
Here `sha` is inserted as a bare positional argument *before* the `--` end-of-options marker. If the corrupted value begins with `-`, `git log` will interpret it as an option rather than a revision (classic git argument-injection pattern), e.g. values shaped like `--output=<path>` (writes log output to an arbitrary file) or other git-log flags, giving the attacker a way to make Desktop's own git invocation perform file writes or unexpected behavior outside the intended command semantics — all triggered simply by the victim viewing history/diffs of a maliciously crafted cloned/fetched repository.

Existing guards in the codebase (`resolveWithin` in `app/src/lib/path.ts`, `sanitizeCloneName`/traversal checks in `app/src/lib/remote-parsing.ts` and `app/src/lib/git/clone.ts`) protect file-system path derivation from URLs, but none of them validate that `Commit.sha` is a well-formed hex SHA before it is spliced into a git argument list — there is no `isValidSHA`/hex-format check found anywhere in `app/src/lib/git/log.ts` or its callers.

### Impact Explanation
This falls under "attacker controls a cloned/fetched repository ... result is ... file write ... outside the repo" and "silent corruption of what the user commits/pushes/views." A crafted commit shipped in a repository the victim clones or fetches can (a) silently corrupt the commit history metadata Desktop displays (wrong SHA/author/summary attribution across the parsed batch — the same "field in the wrong place" defect as the seed report) and (b) turn the corrupted `sha` value into an injected `git log` option when the user opens that commit's diff, potentially causing git to write files or behave in attacker-chosen ways outside the normal revision-lookup semantics.

### Likelihood Explanation
Requires no privileges beyond the baseline "attacker controls a repository the victim clones/fetches." Crafting a commit object with an embedded NUL is straightforward with plumbing commands and does not require exploiting any cryptographic or git-transport weakness. The victim only needs to open the repository in Desktop and browse history (an entirely normal workflow), which triggers `getCommits`. Reaching `getChangedFiles` with the corrupted value additionally requires the victim to select that specific (attacker-positioned) commit row in the History view — a normal, expected interaction, not an unnatural step.

### Recommendation
- Harden `createLogParser`'s `parse` (`git-delimiter-parser.ts`) to detect or reject records where the token count is not an exact multiple of `keys.length`, rather than silently misaligning subsequent slices.
- Validate that `Commit.sha`/`shortSha` match a strict hex-SHA pattern before using them anywhere, and specifically before splicing them into git argument arrays; reject/log and abort otherwise.
- Always place caller-supplied revision-like arguments after a leading `--` (or otherwise ensure they cannot be interpreted as options) in `getChangedFiles` and any similar call sites that build `git` argument arrays from parsed data.

### Proof of Concept
1. Attacker creates a repository and, using low-level plumbing (`git hash-object -w --stdin`, `git commit-tree`), crafts a commit object whose message body contains a raw `\0` byte followed by content shaped like `-` + a git log option (e.g. `--output=/tmp/evil`), then makes a following, real commit on top of it.
2. Attacker publishes the repository; victim clones/fetches it in GitHub Desktop.
3. Victim opens the History view; Desktop calls `getCommits`, which uses `createLogParser`/`git log -z --format=...`. The embedded NUL desynchronizes the fixed 9-field chunking for the crafted commit and the following commit, causing the following commit's `Commit.sha` field to be populated with the attacker-chosen string instead of its real SHA.
4. Victim clicks that commit row to view changed files; Desktop calls `getChangedFiles(repository, sha)`, which runs `git(['log', sha, '-C', '-M', ..., '--'], ...)`. Because `sha` begins with `-` and precedes the `--` marker, git parses it as an option instead of a revision, altering the command's behavior (e.g., writing output to an attacker-chosen path) rather than looking up the intended commit. export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}
