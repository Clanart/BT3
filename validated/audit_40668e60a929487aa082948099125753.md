This confirms `findGitHubTrampolineAccount` matches purely on URL origin against stored accounts [1](#0-0) , with no binding to the specific repository, remote, or git operation that originated the request. Combined with the trampoline server's authorization check, which only verifies the token is a currently-active token and never checks which process, command, or URL is entitled to use it [2](#0-1) , any child process that inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`/`GIT_CONFIG_PARAMETERS` during a git operation can request Desktop's stored GitHub OAuth token for an arbitrary host.

### Title
Git filter/credential subprocesses spawned during clone/fetch can query the trampoline credential helper for the user's real GitHub token for any host - (File: app/src/lib/trampoline/trampoline-environment.ts)

### Summary
GitHub Desktop wires every git subprocess it spawns with `GIT_CONFIG_PARAMETERS: "'credential.helper=' 'credential.helper=desktop'"`, `DESKTOP_TRAMPOLINE_TOKEN`, and `DESKTOP_PORT` so that filters like Git LFS can also authenticate [3](#0-2) . This intentionally lets non-git children (filters, LFS, hooks) reach the trampoline server. The trampoline server, however, authorizes requests solely by checking that the token is currently "live" [2](#0-1)  — it does not verify that the request originates from the actual git process performing the operation, nor that the requested credential URL matches the repository/remote being operated on.

### Finding Description
The credential-helper handler resolves GitHub credentials purely from the `url`/`host` fields supplied in the request body, matched against the user's stored accounts by origin [4](#0-3) [1](#0-0) . There is no correlation between "which repository/remote this git invocation is working on" and "which host the credential request is for". Because `GIT_CONFIG_PARAMETERS` (and the trampoline token/port env vars) are inherited by every child process git spawns for the duration of the operation — including filter drivers, `clean`/`smudge` commands, custom diff/merge tools, and Git LFS — a process spawned as a side effect of processing an attacker-influenced repository (e.g., via `.gitattributes` invoking a filter, or a `.lfsconfig`/LFS transfer that shells out) can independently connect to `127.0.0.1:<DESKTOP_PORT>` and issue its own `get` credential-helper request with `url=https://github.com` (or `api.github.com`/`ghe.com`), unrelated to the actual clone/fetch target. Since the lookup in `getGitHubCredential` only checks origin equality against the user's signed-in accounts [5](#0-4) , the trampoline will hand back the user's real GitHub login and OAuth token, formatted as a standard git credential response [6](#0-5) . This is the "broken invariant": the credential helper assumes any process holding the (broadly propagated) trampoline token is trustworthy and scoped to the operation, but the token/env are shared with untrusted, repository-influenced subprocesses.

### Impact Explanation
An attacker who controls a cloned/fetched repository (its `.gitattributes`, `.lfsconfig`, or configured filters/diff/merge drivers processed during checkout) can obtain the victim's real GitHub OAuth token by simply having a spawned helper process connect to the loopback trampoline socket and request credentials for `github.com`/`api.github.com`, then exfiltrate that token to attacker infrastructure. This satisfies "credential/token exfiltration" from an unprivileged attacker-controlled repository content path, without requiring local access, admin rights, or prior malware.

### Likelihood Explanation
Exploitation requires the attacker's repository content to cause git (or a git-invoked helper such as LFS) to execute an attacker-supplied command during a normal Desktop operation (clone/fetch/checkout), and for that command to reach out to the loopback trampoline port using the inherited environment variables — both are properties of the current design (filters/LFS are explicitly allowed to use the trampoline's credential helper, per the comment in `withTrampolineEnv`). No additional unnatural user action beyond cloning/fetching/opening the repository is required, making this plausible for a motivated attacker distributing a malicious repository, though it still depends on the attacker achieving code execution via a filter/hook mechanism, which is a nontrivial but known git primitive.

### Recommendation
Scope trampoline credential responses to the specific operation/remote in progress rather than trusting any holder of the token: bind each trampoline token to the specific remote URL(s) the operation is authorized to authenticate against, and reject `get` credential requests whose `url`/`host` doesn't match one of those authorized remotes. Do not silently succeed cross-host credential lookups from within a single git invocation's environment; alternatively, avoid propagating `DESKTOP_TRAMPOLINE_TOKEN`/`GIT_CONFIG_PARAMETERS` to filter/LFS subprocesses beyond what's strictly required for that filter's own configured remote.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitattributes` entry that routes some tracked file through a custom filter (`filter=exfil`), plus a companion mechanism (e.g., committed LFS config or a legitimately-configured local filter that the victim already trusts, such as Git LFS itself) that, during `smudge`/`clean`, spawns an arbitrary command.
2. Victim clones/fetches/checks out this repository in GitHub Desktop; Desktop's `git()` wrapper sets `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and `GIT_CONFIG_PARAMETERS=credential.helper=desktop` in the environment for the whole operation [7](#0-6) .
3. The filter subprocess (inheriting that environment) connects to `127.0.0.1:$DESKTOP_PORT` and sends a trampoline `credential-helper get` command with `url=https://github.com`.
4. `trampolineServer` accepts it because the token is still valid [2](#0-1) , and `getCredential`/`getGitHubCredential` returns the victim's real GitHub username and OAuth token [5](#0-4) .
5. The filter process exfiltrates the returned username/token to an attacker-controlled server.

Note: I was not able to fully verify, within this index, the exact mechanics by which a freshly cloned/fetched repository's `.gitattributes`/LFS configuration reliably triggers a subprocess with code execution without additional pre-existing local filter configuration (e.g., whether Desktop auto-installs/trusts `git-lfs` filters for untrusted repos) — that portion of the chain depends on git/git-lfs's own filter-trust behavior rather than code in this repository, and would benefit from further investigation in a full Desktop checkout.
