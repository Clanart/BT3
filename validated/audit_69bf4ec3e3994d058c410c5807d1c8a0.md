### Title
`ThresholdKeys` accepts zero shares and identity verification shares, yielding a forgeable identity group key — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The InfluxDB bug (CVE-2019-20933) let authentication succeed because an empty shared secret was accepted: verification degenerated to "always valid" when the secret was zero. Serai has the same shape in `ThresholdKeys::new` / `ThresholdKeys::read`: the secret share and all verification shares are taken verbatim from the caller/byte stream, with no check that the secret share is non-zero, no check that any verification share is non-identity, and no consistency check that `G * secret_share` matches the participant's verification share. A `ThresholdKeys` deserialized from untrusted bytes with a zero secret share and all-identity verification shares produces an identity `group_key` — the "empty shared secret" — for which Schnorr/FROST signatures are forgeable by anyone.

### Finding Description
`ThresholdKeys::new` validates only counts, participant bounds, and interpolation applicability. It computes `group_key` as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` and stores everything without validating values: [1](#0-0) 

`ThresholdKeys::read` feeds raw, attacker-influenced bytes directly into `new`: `t`, `n`, `i`, the interpolation coefficients (`Interpolation::Constant` reads `n` arbitrary scalars), the `secret_share` scalar, and `n` group elements — none checked for zero/identity: [2](#0-1) 

If the encoded keys carry `secret_share = 0`, `secret_share = 0`-consistent identity verification shares, and `Interpolation::Constant` coefficients chosen so `Σ c_i * identity = identity`, the resulting `group_key` is the identity point — the group secret is effectively empty (zero). The key object's own view stays self-consistent: `view()` computes `secret_share = scalar * 0 * factor = 0` and `verification_shares[i] = identity * scalar * factor = identity`, so nothing downstream detects the degenerate state: [3](#0-2) 

Against an identity group key, the Schnorr verification equation degenerates. `SchnorrSignature::batch_statements` returns `R + c·A − s·G`; with `A = identity` the public-key term vanishes and the check reduces to `R == s·G`, satisfiable by anyone who picks `s` freely and sets `R = s·G`: [4](#0-3) 

`verify` and `batch_statements` never reject an identity public key, identity `R`, or `s = 0`, so the forge succeeds regardless of the challenge value.

### Impact Explanation
Any unprivileged party who can cause `ThresholdKeys::read` (or `ThresholdKeys::new` via `Constant` interpolation) to ingest zeroed/identity shares creates a key whose group key is the identity — a wallet or validator credential with an empty secret. Because FROST's `Schnorr::verify` reconstructs the signature as `SchnorrSignature { R, s: sum }` and calls `SchnorrSignature::verify(group_key, c)`: [5](#0-4) 
a forged `(R = s·G, s)` pair verifies for any message. For the Bitcoin network, a Serai address derived from an identity/trivially-known group secret lets anyone who recognizes it spend (or claim as received) funds controlled by that key — the exact analog of "JWT verifies because the shared secret is empty."

### Likelihood Explanation
The trigger requires feeding crafted bytes to `ThresholdKeys::read` or constructing keys with a zero secret and identity verification shares — the read path performs no value validation (only structural checks), so the degenerate state is accepted deterministically rather than probabilistically. Exploitation additionally requires an identity group key to actually be relied upon (e.g., a corrupted/attacker-written key file, or a `Constant` interpolation configuration built over identity shares). That conditioning lowers likelihood versus a remote pre-auth bypass, but once present the forgery is unconditional — hence Medium/High rather than Critical.

### Recommendation
In `ThresholdKeys::new`, reject `secret_share == 0`, reject identity verification shares, reject an identity computed `group_key`, and verify `C::generator() * secret_share == verification_shares[i]` (adjusted for `Constant` coefficients). For `Constant` interpolation, also reject coefficient vectors that are all-zero or that produce an identity group key. Defense-in-depth: have `SchnorrSignature::verify`/`read` reject identity public keys/`R` and `s == 0`, mirroring the existing identity-`R` rejection in `Signed::read`: [6](#0-5) 

### Proof of Concept
```rust
use zeroize::Zeroizing;
use ciphersuite::{group::{ff::Field, Group}, Ciphersuite};
use dkg::{ThresholdParams, ThresholdKeys, Interpolation, Participant};
use schnorr::SchnorrSignature;

// For any prime-group Ciphersuite C:
// Build ThresholdKeys with an empty (zero) secret and identity verification shares.
let n = 2u16;
let mut vs = std::collections::HashMap::new();
for l in 1 ..= n {
  vs.insert(Participant::new(l).unwrap(), C::G::identity());
}
// Constant interpolation with arbitrary (e.g. all-ONE) coefficients; t == n required.
let keys = ThresholdKeys::<C>::new(
  ThresholdParams::new(n, n, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Constant(vec![C::F::ONE; n as usize]),
  Zeroizing::new(C::F::ZERO),            // empty shared secret
  vs,
).unwrap();                            // accepted: no zero/identity/consistency checks

assert!(bool::from(keys.group_key().is_identity())); // group secret is effectively empty

// Forgery against the identity group key:
// choose any s, set R = s*G; then R + c*A - s*G = 0 for A = identity, for ALL challenges c.
let s = C::F::random(&mut rand_core::OsRng);
let forged = SchnorrSignature::<C> { R: C::generator() * s, s };
assert!(forged.verify(keys.group_key(), C::F::random(&mut rand_core::OsRng)));
```
The same bytes can be produced via `ThresholdKeys::read`: write `t = n`, any valid `i`, interpolation tag `0` followed by `n` canonical scalars, a canonical zero `secret_share`, and `n` identity point encodings (accepted by `read_G` where identity is a canonical encoding); `read` calls `ThresholdKeys::new`, which performs no value validation.

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,

  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
