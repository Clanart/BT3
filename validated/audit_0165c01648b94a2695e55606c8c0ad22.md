### Title
Cached FROST preprocesses are reused across signing attempts, enabling private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists a deterministic FROST seed under `(b"DkgConfirmer", attempt)` but never invalidates or deletes it after signing. Every call to `share_internal` reconstructs the same nonce pair through `AlgorithmSignMachine::from_cache`, while attacker-controlled preprocess bytes can change the binding factor and signature challenge. Three shares generated from the same cached nonce material are sufficient to recover the validator's Lagrange-adjusted private key share.

### Finding Description
The coordinator stores a 32-byte `CachedPreprocess` when the context is first used, decrypts that same record on every subsequent call, and reconstructs a signing machine with `AlgorithmSignMachine::from_cache`. There is no deletion after `machine.sign` completes. [1](#0-0) 

The signing path accepts serialized preprocesses, parses them with `read_preprocess`, and passes the resulting map and message to `machine.sign`. [2](#0-1) 

`from_cache` deterministically regenerates the nonce commitments and private nonce scalars from the cached seed. [3](#0-2) 

For each signing session, FROST converts the fixed nonce pair `(d, e)` into the effective nonce `d + rho * e`, where `rho` is derived from the group key, signed message, and transcript of all supplied preprocesses. [4](#0-3) 

The resulting Schnorr share has the form `s = c * x + d + rho * e`, where `x` is the participant's Lagrange-adjusted secret share. [5](#0-4) [6](#0-5) 

### Impact Explanation
If the same context is used to sign three sessions with different preprocess sets or messages, the same `d` and `e` are combined with different `rho` and `c` values. Those three public signature shares form two independent equations after subtracting the first share, allowing recovery of `x`. [7](#0-6) 

For shares `s1`, `s2`, and `s3`, define `Δρj = ρj - ρ1`, `Δcj = cj - c1`, and `Δsj = sj - s1`. The secret is:

```text
x = (Δρ2 * Δs3 - Δρ3 * Δs2)
    ------------------------------------------------
    (Δρ2 * Δc3 - Δρ3 * Δc2)
```

Recovery of a validator signing share compromises that validator's authority and can enable unauthorized participation in future threshold signing operations.

### Likelihood Explanation
The cached value remains reusable indefinitely because it is keyed only by the confirmation context and attempt, not by the participant set, message, or received preprocesses. [8](#0-7) [9](#0-8) 

A participant able to submit different preprocess bytes for the same attempt can induce different `rho` values through `read_preprocess` and the preprocess transcript. [10](#0-9) [11](#0-10) 

Exploitation requires three signatures under the same cached context with different binding-factor transcripts; repeated signing of byte-identical session data does not reveal new information.

### Recommendation
Delete or tombstone `CachedPreprocesses` before the first `machine.sign` call commits its nonce, and reject later share requests for the same context if the nonce was already consumed. If deterministic recovery is required, persist a signed-session digest covering the participant set, ordered preprocess bytes, and message, and only permit re-execution when all three values are byte-identical. Fresh nonces must be used for every distinct signing session. [12](#0-11) 

### Proof of Concept
1. Instantiate a `DkgConfirmer` for a fixed attempt, causing `preprocess_internal` to create and persist the encrypted `CachedPreprocess`. [1](#0-0) 
2. Invoke `share_internal` with preprocess set `P1` and message `m1`; it reconstructs nonce pair `(d,e)` and emits `s1 = c1*x + d + ρ1*e`.
3. Invoke `share_internal` again under the same context with preprocess set `P2` or a different message. The cached seed still produces `(d,e)`, while the changed transcript produces `ρ2` and `c2`, yielding `s2 = c2*x + d + ρ2*e`. [13](#0-12) 
4. Repeat with a third distinct session to obtain `s3`.
5. Recover `x` using the two-equation elimination formula above.

  pub(crate) fn calculate_binding_factors<T: Clone + Transcript>(&mut self, transcript: &T) {
    for (l, binding) in &mut self.0 {
      let mut transcript = transcript.clone();
      transcript.append_message(b"participant", C::F::from(u64::from(u16::from(*l))).to_repr());
      // It *should* be perfectly fine to reuse a binding factor for multiple nonces
      // This generates a binding factor per nonce just to ensure it never comes up as a question
      binding.binding_factors = Some(
        (0 .. binding.commitments.nonces.len())
          .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
          .collect(),
      );
    }
  }
