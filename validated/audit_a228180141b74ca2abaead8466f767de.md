### Title
Excess native-token payment to `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller and becomes trapped in the host contract - ([File: evm/src/core/EvmHost.sol])

### Summary
When a user pays the dispatch/fee-funding cost in native token (ETH) instead of the `feeToken`, `EvmHost` forwards the *entire* `msg.value` to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The router only spends the ETH required to buy exactly `fee` amount of `feeToken` and refunds any leftover ETH — but it refunds it to `msg.sender` as seen by the router, which is `EvmHost` itself, not the original end user. `EvmHost` never forwards this leftover ETH back to `_msgSender()`. The excess ETH is silently retained by the host contract instead of the paying user.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all follow this exact same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In every case, `msg.value` is passed wholesale into `swapETHForExactTokens{value: msg.value}(fee, ...)`. `IUniswapV2Router02.swapETHForExactTokens` only consumes `amounts[0]` ETH (converted to WETH and swapped for exactly `fee` `feeToken`), and internally refunds `msg.value - amounts[0]` back to its caller — which, from the router's perspective, is `EvmHost`, since `EvmHost` is the one invoking the router with `{value: msg.value}`. This refund lands in `EvmHost`'s own balance, not back to the actual dispatching user (`_msgSender()`/`post.payer`).

Unlike this pattern, the codebase's own `IntentGatewayV2.placeOrder` explicitly tracks and refunds leftover native token after an equivalent `swapETHForExactTokens` call: [4](#0-3) 

This shows the project is fully aware of, and normally handles, this exact bug class (over-supplied native token during a swap-for-fee operation) — but the fix was applied only in `IntentGatewayV2`, not in `EvmHost`'s `dispatch`/`fundRequest` functions, which use the identical unsafe pattern.

Once trapped in `EvmHost`, the excess ETH is not recoverable by the paying user. It can only be extracted via the privileged `IHostManager.withdraw` path, gated to the `hostManager` module: [5](#0-4) 

Ordinary users calling `dispatch`/`fundRequest` have no way to recover overpaid ETH; it becomes de facto protocol revenue extractable only through governance/host-manager action, not through any user-facing refund path.

### Impact Explanation
Any unprivileged user or contract (including `IntentGatewayV2`'s cross-chain `fillOrder`/`placeOrder` flows, which call `IDispatcher(hostAddr).dispatch{value: ...}(request)` for their native fee leg) that supplies more ETH than strictly required for the fee swap permanently loses the difference — it is siphoned into `EvmHost`'s balance rather than refunded. Given that the swap output amount required (`amounts[0]`) is unpredictable ahead of time (it depends on live DEX pricing), any reasonable caller must overestimate `msg.value` to avoid reverting from insufficient input, making unintended overpayment the common case rather than an edge case. This is a direct loss-of-funds bug against ordinary bridge users, matching the bounty's "stealing or loss of funds" impact class, reachable without any relayer, prover, or admin compromise.

### Likelihood Explanation
High. `dispatch()` and `fundRequest()` are core, frequently invoked public entrypoints used by every app module (including `IntentGatewayV2`/`ExtrinsicIntents`) whenever a caller opts to pay in native token instead of pre-approved `feeToken`. Because the exact ETH-to-fee-token exchange amount fluctuates with DEX price, callers naturally send a buffer above the minimum, guaranteeing that leftover ETH is generated on essentially every native-token-funded dispatch call.

### Recommendation
Mirror the fix already used in `IntentGatewayV2.placeOrder`: capture the `amounts[0]` actually spent from `swapETHForExactTokens`, compute `msg.value - amounts[0]`, and refund the leftover directly to `_msgSender()` (or `post.payer`) with a low-level `call`, reverting on failure, in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. Configure `EvmHost` with a live `uniswapV2` router and `feeToken`.
2. A user (or an app module like `IntentGatewayV2`) calls `dispatch(post)` with `post.fee = 10` `feeToken` units but sends `msg.value = 1 ether` (deliberately overestimating the ETH needed, since exact swap cost is unknown pre-trade).
3. `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(10, path, address(this), block.timestamp)` spends only the small amount of ETH actually needed (e.g., `0.01 ether`) and refunds `0.99 ether` back to `EvmHost` (the caller of the router).
4. `dispatch()` returns without forwarding any of the `0.99 ether` back to the user; `address(this).balance` (EvmHost) increases by `0.99 ether` while the user's balance is permanently reduced by that amount.
5. Confirm no user-callable function exists on `EvmHost` to reclaim this ETH — only `IHostManager.withdraw`, restricted to the `hostManager` module, can move it out.
