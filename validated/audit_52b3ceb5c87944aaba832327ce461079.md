### Title
Missing `request.from` (module-id) check in IntentGatewayV2/HostManager governance branches allows any Hyperbridge-chain module to trigger `SweepDust`/`UpgradeContract`/`Withdraw` — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The external report's core broken invariant is: a value that is supposed to represent "this action was authorized by the specific privileged party" is instead only checked at a coarser trust boundary that any actor sharing that boundary can also satisfy — letting an unintended party invoke privileged fund-moving logic. The Solana report checked *"is this a signer"* when it should have checked *"is this signer actually a specific, non-program account"*. The Hyperbridge analog is in the cross-chain governance dispatch of `IntentGatewayV2`/`ExtrinsicIntents.sol` (and the identical pattern in `HostManager.sol`): the governance-only branches of `onAccept` verify only that `request.source == hyperbridge()` (the request came from the Hyperbridge state machine), but never verify `request.from` (which module/account on that chain actually sent it).

### Finding Description
`ExtrinsicIntents.sol::onAccept` dispatches two classes of actions: [1](#0-0) 

- For `RedeemEscrow`/`RefundEscrow`, it calls `_authenticate(request)`, which checks **both** `request.source` and `request.from` against the specific registered gateway instance address: [2](#0-1) 

- For `NewDeployment`, `UpdateParams`, `SweepDust`, and `UpgradeContract` — explicitly documented as "Only Hyperbridge may dispatch this request" — the code checks **only** `request.source`:
```
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
```
There is no check that `request.from` equals a specific, designated governance module id (e.g. the relayer/host-executive module identifier). Any module capable of dispatching an ISMP `PostRequest` from the Hyperbridge state machine — with `to` set to the gateway's address on any destination chain — will pass this check, because `source` is a chain-level identifier, not a module-level one.

The exact same pattern exists in `HostManager.sol`, which gates `Withdraw` and `SetHostParam` (bridge revenue withdrawal, and updating `admin`/`hostManager`/`handler`/`consensusClient`/`feeToken`) behind an identical source-only check: [3](#0-2) 

Compare this to how the relayer pallet's own withdrawal dispatch sets `from` to its own fixed `MODULE_ID` when it legitimately wants to reach `HostManager`: [4](#0-3) 

Nothing on the EVM side ever checks that the incoming `from` equals that specific module id — the `source`-only guard treats *every* module on Hyperbridge as equally privileged to invoke `Withdraw`/`SetHostParam` (HostManager) or `SweepDust`/`UpgradeContract`/`UpdateParams`/`NewDeployment` (IntentGatewayV2).

### Impact Explanation
- `SweepDust` transfers `TokenInfo[] outputs` — attacker-chosen token/amount pairs — to an attacker-chosen `beneficiary`, directly moving funds held by the gateway to an unintended party.
- `UpgradeContract` performs `ERC1967Utils.upgradeToAndCall(newImpl, initData)` — a full proxy takeover, letting an attacker point the gateway at a malicious implementation and run arbitrary migration calldata in the same call, which can drain **all** escrowed order funds, not just dust.
- `HostManager`'s `Withdraw`/`SetHostParam` similarly allow draining `EvmHost`'s accrued fee-token balance and rewriting the host's core security parameters (`admin`, `hostManager`, `handler`, `consensusClient`, `feeToken`).

This satisfies the required impact classes: stealing/loss of funds, unauthorized execution, and cross-chain admin effects reachable through wrong module binding (Pivot 4 explicitly calls this out).

### Likelihood Explanation
Exploitation requires the attacker to control (or co-opt) *some* module on the Hyperbridge state machine capable of dispatching an ISMP `PostRequest` whose `to` field points at the victim gateway/host-manager address on a destination chain. I was not able to fully verify, from the indexed code alone, whether any presently-deployed, non-governance-gated pallet on the live Hyperbridge (Nexus/Gargantua) runtime lets an ordinary signed account freely choose the destination `to` address for a dispatched request (each example pallet I found hardcodes both `from` and `to`, e.g. `docs/content/developers/polkadot/dispatching.mdx`). If such a permissionless "raw dispatch" pathway exists anywhere in the runtime (present or future pallets, including any generically-configured messaging/coprocessor pallet), the missing `from` check turns it into a direct path to drain funds or take over the gateway/host contracts on every connected EVM chain. Regardless of that runtime-specific caveat, the *code-level* guard is objectively wrong: it authenticates the wrong granularity (chain vs. module), which is exactly the pattern the original report flags as the root cause of authority misuse.

### Recommendation
In the governance branches of `onAccept` in `ExtrinsicIntents.sol`/`IntentGatewayV2.sol` and `HostManager.sol`, additionally verify `request.from` against a specific, hardcoded/configured governance module id (mirroring the `_authenticate`/`authenticate` pattern already used for `RedeemEscrow`/`RefundEscrow`), rather than accepting any sender from the Hyperbridge state machine.

### Proof of Concept
1. On the Hyperbridge chain, obtain (or compromise) any module/pallet that can call `IsmpDispatcher::dispatch_request` with an attacker-controlled `to` field targeting `IntentGatewayV2`'s address on a destination EVM chain, and `body[0] = RequestKind.SweepDust` with `body[1:]` ABI-encoding `SweepDust{ outputs: [{token: <victim token>, amount: <max>}], beneficiary: <attacker> }`.
2. Relay the resulting request/proof to the destination EVM chain.
3. `EvmHost.dispatchIncoming` invokes `IntentGatewayV2.onAccept`, which only checks `keccak256(incoming.request.source) == keccak256(hyperbridge())` — true, since the dispatch genuinely originated on the Hyperbridge state machine — and never checks `incoming.request.from`.
4. `_sweepDust` executes, transferring the gateway's token balance to the attacker's `beneficiary` address: [5](#0-4)

            _authenticate(incoming.request);
