### Title
Unvalidated `Participant` indexes cause a panic (DoS) in the PedPoP blame-decryption path - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the Traefik advisory (untrusted input reaching a nil/unchecked dereference that panics the process, CWE-476), `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with caller-supplied `Participant` values. `Participant` is any non-zero `u16`, so an unauthenticated-range index (e.g. a participant `> n`) panics on `self.enc_keys[&decryptor]` / `self.commitments[&sender]` instead of returning an error, crashing the process handling a blame accusation.

### Finding Description
`Participant::new` only rejects `0` (`crypto/dkg/src/lib.rs:29-35`). In `crypto/dkg/pedpop/src/encryption.rs:388`, the DLEq verification arguments are built as `&[self.enc_keys[&decryptor], *proof.key]` — a direct `HashMap` index that panics when `decryptor` was never registered (i.e., any `Participant > n`). Similarly, `crypto/dkg/src/lib.rs:457-459` (`ThresholdView::original_verification_share`, `verification_share`) and `crypto/dkg/pedpop/src/lib.rs:599` (`self.commitments[&sender]` inside `blame_internal`) index maps with attacker-influenced `Participant` keys.

The reachable path: `AdditionalBlameMachine::new` (or a `BlameMachine` after `calculate_share`) registers encryption keys only for participants `1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`). An accuser then calls `blame(sender, recipient, msg, proof)` with `recipient = Participant(0xFFFF)`. Because `blame` takes `msg`/`proof` by value, the attacker can craft a fully valid `EncryptedMessage` themselves: pick ephemeral `k`, set `msg.key = k·G`, produce a valid Schnorr PoP with known `k`, compute the shared point `k·enc_pub_key(recipient)` publicly, and prove it with a self-generated `EncryptionKeyProof`. `msg.pop.verify` passes (`encryption.rs:374-379`), the `Some(proof)` branch evaluates `self.enc_keys[&decryptor]` (`encryption.rs:388`), and the `HashMap` index on a missing key panics. Equivalently, with a valid `recipient`, a `sender > n` reaches `self.commitments[&sender]` at `lib.rs:599` after decryption succeeds and the share bytes parse as a canonical scalar.

No bounds check exists between `Participant` validation and the map lookups; `blame`/`AdditionalBlameMachine::blame` are the public, externally-callable API for processing accusations.

### Impact Explanation
An unprivileged party submitting a blame accusation with an out-of-range `sender`/`recipient` — a single byte-level field in an otherwise cryptographically valid message — crashes the node evaluating blame. Since `blame` is invoked during fault adjudication of the DKG, a malicious DKG participant (or accuser) can reliably abort every honest validator processing their accusation, denying completion/recovery of the multisig and, in production deployments where the processor runs in a single process, killing the node. This mirrors the Traefik advisory's class: malformed protocol input reaching an unchecked dereference → process panic → availability loss.

### Likelihood Explanation
High reachability: all inputs (`Participant` indexes, `EncryptedMessage`, `EncryptionKeyProof`) are attacker-controlled/public, the attacker can satisfy the PoP and DLEq checks with self-chosen ephemeral keys, and no validation of `sender`/`recipient` against `1..=n` occurs before the indexing. Exploitation requires only participating in (or observing enough of) a PedPoP DKG to submit a blame message.

### Recommendation
In `Decryption::decrypt_with_proof` and `blame_internal`, replace map indexing with `get(...).ok_or(...)`-style lookups returning a `DecryptionError`/`PedPoPError`, or validate `sender`/`recipient` against `params.all_participant_indexes()` at the top of `blame`. Apply the same treatment to `commitments[&l]`/`commitments[&sender]` lookups and document `original_verification_share`/`verification_share` panics or convert them to `Option` returns.

### Proof of Concept
```
// After AdditionalBlameMachine::new(context, n, msgs) with participants 1..=n:
let k = random_scalar();
let enc_pub = recipient_public_enc_key;           // public
let msg = EncryptedMessage {
  key: G::generator() * k,
  pop: SchnorrSignature::sign(&k, r, pop_challenge(...)), // valid: attacker knows k
  msg: encrypted_bytes,                                    // any bytes
};
// proof.key = k * enc_pub, provable publicly since attacker knows k
let proof = EncryptionKeyProof { key: k * enc_pub, dleq: DLEqProof::prove(...) };
// Panic: HashMap index on unregistered participant
machine.blame(Participant::new(0xFFFF).unwrap(), real_recipient, msg, Some(proof));
// or: blame(sender = Participant(0xFFFF), valid recipient, ...) panics at
// self.commitments[&sender] in blame_internal (crypto/dkg/pedpop/src/lib.rs:599)
```
Panics at `crypto/dkg/pedpop/src/encryption.rs:388` (`self.enc_keys[&decryptor]`).
