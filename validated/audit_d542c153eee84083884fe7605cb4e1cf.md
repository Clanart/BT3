### Title
Assertion-based crash (uncaught `AssertionError`) when parsing a crafted offer's offered coins - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.summary()` / `Offer.get_offered_coins()` (via `_get_offered_coins()`) is the "print the interpreted/translated data" analog of the Exiv2 bug: it is a rarely-exercised, best-effort *interpretation* path (deriving human-readable offer summaries) that a wallet or GUI calls on an **untrusted, attacker-crafted offer file** before the offer is otherwise validated/executed. Inside it, `get_inner_puzzle()`/`get_inner_solution()` (outer-puzzle drivers) are allowed by their own type signatures to return `None`, but the caller immediately dereferences them with a bare `assert`, which raises an unhandled `AssertionError` instead of a handled `ValueError`.

### Finding Description
`Offer._get_offered_coins()` iterates over every `CoinSpend` in the attacker-supplied bundle, matches an outer-puzzle driver, and calls: [1](#0-0) 

`get_inner_puzzle` / `get_inner_solution` are declared to return `Program | None` per the driver protocol: [2](#0-1) 

Several concrete drivers can legitimately return `None` for a puzzle_reveal/solution shape that still matches (e.g. `TransferProgramPuzzle.get_inner_puzzle`/`get_inner_solution` always return `None`, and `RevocationOuterPuzzle.get_inner_puzzle` returns `None` or raises depending on solution shape): [3](#0-2) [4](#0-3) 

Because `match_puzzle` only checks curried-arg *shape* (mod hash + arity), not full semantic validity, a crafted `CoinSpend.puzzle_reveal` can be built so that `match_puzzle` selects a driver whose `get_inner_puzzle`/`get_inner_solution` path returns `None` for the given (attacker-controlled) solution, while `_get_offered_coins()` still reaches the `assert inner_puzzle is not None and inner_solution is not None` line and blows up with an unhandled `AssertionError`.

This is directly analogous to the Exiv2 issue: a **less-common "interpretation" code path** (there, printing translated metadata; here, deriving a human/UI-facing offer summary rather than the core spend-bundle validation path) dereferences an "optional" value without a null check, and it is reachable purely by handing the victim a crafted file (an Exiv2 image / here, a Chia offer file) — not by exploiting core consensus validation.

### Impact Explanation
`get_offered_coins()` (and hence `summary()`, `get_offered_amounts()`, `arbitrage()`, `get_pending_amounts()`, `get_primary_coins()`) is exercised by wallet RPC endpoints used to preview/summarize an offer that has been received from a counterparty (e.g. before deciding whether to accept it) and by the Data Layer wallet's offer-summary flow. A crafted offer file handed to a victim wallet/RPC caller can raise an unhandled `AssertionError` deep inside offer-summary computation, aborting that RPC call. This matches the "spend-triggered transaction-processing halt" impact class permitted by the validation rules — it is reachable by an offer counterparty handing a malicious offer to a wallet user, with no privileged access required. It is a denial-of-service against the specific offer-parsing/summary call (and any code path relying on it, such as UI offer previews or automated take-offer tooling that first calls `summary()`), not a corruption of consensus state, coin ownership, or funds.

### Likelihood Explanation
Medium: constructing a puzzle_reveal that (a) matches one of the outer-puzzle driver's shape check in `match_puzzle` and (b) drives `get_inner_puzzle`/`get_inner_solution` for that constructor to return `None` for the given solution requires understanding chia's puzzle-driver matching logic, but doing so does not require any signature, funds, or special privilege — an attacker only needs to produce a serialized offer file (`.offer`) and get a victim to load/preview it, which is the normal offer-exchange workflow. I was not able to fully enumerate every driver/solution combination that reaches `None` given real-world uncurried puzzle args (e.g. whether `TransferProgramPuzzle` can actually appear as the *outermost* puzzle_reveal of a top-level coin spend in a real offer, since it is normally nested), so this should be treated as a plausible but not fully proven concrete trigger without executing a proof-of-concept against the real driver-matching order in `driver_lookup`.

### Recommendation
- In `Offer._get_offered_coins()`, replace the bare `assert inner_puzzle is not None and inner_solution is not None` with an explicit check that raises a caught/handled exception (e.g. `ValueError`/`ValidationError`), consistent with how other unexpected-shape cases in the same function already raise `ValueError("Could not properly guess offered coins from parent spend")`.
- Audit all `assert x is not None` usages in `chia/wallet/trading/offer.py` that operate on data derived from an untrusted, attacker-supplied `WalletSpendBundle`/offer file, and convert them to explicit validation with recoverable errors, since Python `assert` statements can also be stripped entirely when running with `-O`, silently turning this into a raw `None` dereference (`AttributeError`) further down instead of a clean failure.
- Ensure callers of `Offer.summary()`/`get_offered_coins()` in wallet RPC handlers (`wallet_rpc_api.py`) and Data Layer offer flows catch and convert any resulting exception into a normal RPC error response rather than propagating an unhandled exception.

### Proof of Concept
Not independently executed in this analysis (index-only investigation; no code execution available). Conceptually: craft a `WalletSpendBundle` whose single `CoinSpend.puzzle_reveal` uncurries to match one of the outer-puzzle drivers in `chia/wallet/outer_puzzles.py:driver_lookup` (e.g. an ownership/transfer-program-like curried structure) such that, for the attacker-chosen `solution`, `get_inner_puzzle()` or `get_inner_solution()` returns `None` (as several concrete drivers are documented to do), then load this as an offer via the standard offer-parsing path (`Offer.from_bytes`/`from_bech32`) and call `.summary()` or `.get_offered_coins()` on it — this should raise an unhandled `AssertionError` inside `_get_offered_coins()` instead of a clean, caught validation error.
