### Title
Missing `_filled` finalization check in `_cancelFromDest` lets the order creator race a solver's `RedeemEscrow` message and steal both the delivered output tokens and the refunded escrow - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents._cancelFromDest` marks an order cancelled and dispatches a `RefundEscrow` message back to the source chain **without ever checking whether `_filled[commitment]` is already non-zero** (i.e., already filled by a solver). This mirrors the seed bug's core pattern — a validity check that exists for the "normal" path (`fillOrder`'s deadline/`_filled` guard) is skipped for a different code path that ultimately produces the same critical, fund-moving side effect (a cross-chain withdrawal message), letting a race condition produce a false/duplicate settlement outcome.

### Finding Description
`_cancelFromDest` is:
```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    _filled[commitment] = address(uint160(uint256(order.user)));
    ...dispatches RequestKind.RefundEscrow to order.source...
}
``` [1](#0-0) 

Unlike `_fillCrossChain`, which does check `_filled[commitment]` is unset before proceeding (via `fillOrder`'s pre-checks documented in the intent gateway overview), `_cancelFromDest` never checks that the order hasn't already been filled by a solver. Both this function and `_fillCrossChain` are independent entrypoints that each dispatch a fund-moving cross-chain `PostRequest` back to the source chain (`RefundEscrow` vs `RedeemEscrow`):

```solidity

    _filled[commitment] = msg.sender;
    ...delivers output tokens directly to beneficiary...
    ...dispatches RequestKind.RedeemEscrow to order.source...
}

Because relaying is explicitly permissionless and competitive (multiple independent relayers race to deliver messages, with no guaranteed ordering), the two independently dispatched messages (`RedeemEscrow` from the solver's fill and `RefundEscrow` from the order creator's cancellation) can arrive at the source chain's `onAccept` in either order. `_withdraw`'s only defense is "first one to see nonzero escrow wins, second one reverts with `UnknownOrder`" — it has no notion of *which* message is the legitimate/expected one, because `_cancelFromDest` never checked the destination-side `_filled` state before dispatching its own competing withdrawal.

### Impact Explanation
An order creator can, at (or after) the order deadline, wait for a solver to fill the order (delivering the output tokens directly to the beneficiary/user on the destination chain and dispatching `RedeemEscrow`), then immediately call `cancelOrder()` → `_cancelFromDest` on the same destination chain. `_cancelFromDest` does not check that `_filled[commitment]` is already set to the solver — it unconditionally overwrites it and dispatches a competing `RefundEscrow` message. If the user's `RefundEscrow` message is relayed to the source chain before the solver's `RedeemEscrow` message (achievable by paying a higher relayer fee, or simply due to normal network non-determinism), the user receives:
1. The solver's output tokens on the destination chain (already delivered by `_fillCrossChain`), and
2. The escrowed input tokens refunded back to themselves on the source chain via `_withdraw(..., isRefund=true, ...)`.

The solver's subsequent `RedeemEscrow` message then reverts with `UnknownOrder` (escrow already zeroed), so the solver never recovers the input tokens they were owed for delivering the output — a direct loss of solver funds and an unauthorized/duplicate settlement outcome for the same commitment.

### Likelihood Explanation
This requires only the order creator (an unprivileged, ordinary user) acting at/after the order's deadline — no malicious relayer, prover, or admin is needed. Relayer message ordering is inherently non-deterministic in this permissionless, competitive relayer model, so the race is realistically triggerable by simply paying a higher `relayerFee` on the cancellation dispatch to get it delivered first. Since `_cancelFromDest`'s permissionless branch (post-deadline) allows *any* caller once the deadline passes, and the pre-deadline branch is available to `order.user` directly, the attack window is fully within the order creator's control.

### Recommendation
In `_cancelFromDest`, revert if `_filled[commitment] != address(0)` before marking it cancelled and dispatching `RefundEscrow`, mirroring the finalization check already enforced on the fill path. This closes the race by ensuring a `RefundEscrow` cannot be issued for an order the destination chain already recorded as filled.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At block `D` (or slightly after), a solver calls `fillOrder` in the same block, delivering output tokens to the user and dispatching `RedeemEscrow(commitment)` to the source chain, and setting `_filled[commitment] = solver`.
3. Immediately after, since `block.number >= D`, the user (or any actor colluding with them) calls `cancelOrder()` → `_cancelFromDest`, which does **not** check `_filled[commitment]`, overwrites it to `order.user`, and dispatches `RefundEscrow(commitment)` to the source chain with a higher `relayerFee`.
4. Relayers deliver the `RefundEscrow` message first; `onAccept` → `_withdraw(isRefund=true, finalize=true)` zeroes `_orders[commitment][token]` and refunds the user.
5. The solver's `RedeemEscrow` message arrives later; `onAccept` → `_withdraw` reverts with `UnknownOrder` because escrow is already zero.
6. Net result: user received both the solver's output tokens and their own refunded input tokens; solver received nothing for the tokens they delivered.

        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }

            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        bytes memory body = bytes.concat(
