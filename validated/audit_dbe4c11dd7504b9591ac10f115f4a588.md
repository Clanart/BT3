### Title
Unhandled/inconsistent exception swallowing in `Offer` construction lets a malicious offer coin spend desync the additions/hints cache and crash trade processing - (File: `chia/wallet/trading/offer.py`)

### Summary
`CVE-2023-46839` describes a class of bug where a security-relevant setup step (IOMMU context for a PCI phantom function) is allowed to fail *non-fatally*, so the overall operation (device assignment) proceeds anyway while leaving an inconsistent, unisolated state between two domains. The same "non-fatal failure of a required setup step, followed by continued use of now-inconsistent state" pattern exists in `Offer.__post_init__`, where per-coin-spend hint/addition computation can throw and is silently swallowed with `continue`, leaving the internal `_additions`/`_hints` caches out of sync with the real spend bundle, while code elsewhere unconditionally indexes into those caches or re-derives them without the same tolerance.

### Finding Description
`Offer.__post_init__` iterates every coin spend in the offer's bundle and calls `compute_spend_hints_and_additions()` to populate `self._additions` and `self._hints`: [1](#0-0) 

Any exception other than `ValidationError` or the specific `ValueError("cost exceeded or below zero")` message is caught by a bare `except Exception: continue`, which skips setting `adds[cs.coin]` for that spend entirely — the coin's key is simply never added to the dictionary, and no error is raised.

`compute_spend_hints_and_additions()` itself contains an `assert rf is not None` and does a `bytes32(rf)` conversion: [2](#0-1) 

An attacker who controls their own coin's puzzle/solution inside the offer (a coin they are offering) can produce a `CREATE_COIN` condition whose puzzle-hash argument is not a plain atom (e.g. a cons pair), which triggers `AssertionError`/`ValueError` inside `compute_spend_hints_and_additions`, caught by the bare `except Exception` in `__post_init__`.

Later, `_get_offered_coins()` unconditionally indexes the cache built in `__post_init__` for every coin spend in the bundle, with no `.get()` fallback: [3](#0-2) 

If that coin's key was skipped during `__post_init__`, this raises an unhandled `KeyError` when a wallet/RPC caller (the offer counterparty) tries to inspect the offer via `get_offered_coins()`, `get_offered_amounts()`, or `arbitrage()`.

A second, more direct path exists in `TradeManager.calculate_tx_records_for_offer()`, which calls `compute_spend_hints_and_additions()` on every spend of the *final* (taker-completed) spend bundle with no `try/except` at all: [4](#0-3) 

Because this call site has none of the tolerance that `Offer.__post_init__` has, any offer crafted to trigger the same exception (a non-atom `CREATE_COIN` puzzle-hash argument, or other conditions that trip an `assert`/type error inside `compute_spend_hints_and_additions`) causes an unhandled exception to propagate out of `calculate_tx_records_for_offer`, aborting the take-offer transaction-record computation.

### Impact Explanation
A remote offer counterparty (someone who simply hands another user an offer file/string, e.g. via a marketplace or DM) can construct a spend bundle for their own offered coin such that:
- `Offer.__post_init__` silently drops that coin from `_additions`, leaving the `Offer` object in an inconsistent internal state, and
- any subsequent call to `get_offered_coins()`/`get_offered_amounts()`/`arbitrage()` on that `Offer` object raises an unhandled `KeyError`, or
- `TradeManager.calculate_tx_records_for_offer()` raises an unhandled exception when the taker attempts to take/settle the offer.

This is a spend-triggered halt of the wallet's offer-viewing/take-offer transaction-processing pipeline: a user who merely previews or attempts to accept a maliciously crafted offer has that operation abort with an unhandled exception, rather than a clean, actionable error. Depending on the calling context (RPC handler, background task), this can leave trade state inconsistent or repeatedly fail retried operations on the same offer.

### Likelihood Explanation
The attacker needs only to author an offer (fully within their control, since it is their own offered coin's puzzle reveal/solution) with a superficially valid-looking `CREATE_COIN` condition whose puzzle-hash argument is a non-atom program instead of a `bytes32`. No signature forgery, no consensus-level validity is required, since the code path is hit during offer *parsing/inspection*, before/independent of full spend-bundle validation against the blockchain. Any user who receives and inspects/takes such an offer is affected.

### Recommendation
- In `Offer.__post_init__`, do not silently `continue` past arbitrary exceptions from `compute_spend_hints_and_additions`; either re-raise as a `ValidationError` (as already done for the cost-exceeded case) or explicitly record a "failed" placeholder entry so downstream code can detect and reject the offer deterministically instead of hitting a `KeyError` later.
- Make `_get_offered_coins()` use `self._additions.get(parent_spend.coin, [])` (or otherwise guard against missing keys) instead of direct indexing.
- Add the same defensive `try/except` used in `Offer.__post_init__` to `TradeManager.calculate_tx_records_for_offer()`'s call to `compute_spend_hints_and_additions`, converting failures into an explicit rejected/invalid-offer error rather than letting the exception propagate.
- Consider validating that `CREATE_COIN` puzzle-hash arguments are exactly 32-byte atoms as an early, explicit check (raising a clear `ValidationError`) rather than relying on downstream `assert`/type-coercion to fail.

### Proof of Concept
1. Attacker constructs their own coin's puzzle such that, when run with an attacker-chosen solution, it emits a condition `(51 (99 . 100) 1000)` — i.e. opcode `51` (`CREATE_COIN`) whose second argument is a cons pair rather than a `bytes32` puzzle hash.
2. Attacker builds an `Offer` (or raw `WalletSpendBundle`) including this coin spend among the offered coins, and shares the resulting offer with a victim.
3. Victim's wallet calls `Offer.from_bech32(...)` (or equivalent), triggering `Offer.__post_init__`:
   - `compute_spend_hints_and_additions()` hits `assert rf is not None`/`bytes32(rf)` failure → raises.
   - Caught by `except Exception: continue` at `chia/wallet/trading/offer.py:180-181`; `adds[cs.coin]` is never set.
4. Victim's UI/RPC calls `offer.get_offered_coins()` (e.g. to display offered assets) → `_get_offered_coins()` does `self._additions[parent_spend.coin]` for that coin → unhandled `KeyError`.
5. Alternatively, victim attempts to take the offer; `TradeManager.calculate_tx_records_for_offer(offer, validate=True)` calls `compute_spend_hints_and_additions` unguarded on the finalized bundle → unhandled exception aborts the take-offer flow.
