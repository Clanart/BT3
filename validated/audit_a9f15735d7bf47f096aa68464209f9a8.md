I have sufficient evidence to write up the finding now.### Title
Missing contract-existence check in `withdraw()` low-level token transfers allows escrow to be marked settled without any tokens actually moving - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` reimplements escrow payout using raw low-level `.call()` with only a boolean `success` check, instead of `SafeERC20.safeTransfer` used by the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`). A low-level `CALL` to an address with no deployed bytecode always returns `success = true` with empty `returndata`, so `withdraw()` treats the transfer as complete, decrements internal escrow accounting, and permanently marks the order `_filled`/settled — even though zero tokens were transferred.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` pays out escrowed input tokens (refund path) or fee tokens using: [1](#0-0) 

Unlike `IntentsBase._release`/`_refund` in the canonical implementation, which uses `IERC20(token).safeTransfer(beneficiary, amount)`: [2](#0-1) 

this Tron variant performs a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the boolean `success` return value — never checking that `token` has contract code, and never decoding the `returndata` for a `false` boolean (non-reverting ERC20s that just return `false`). On the EVM, a `CALL` to an address with no code always returns `success = true` and empty return data, so this check is a no-op guard against a destroyed/non-existent token contract, exactly matching the pattern flagged in the external report for `ERC20Helper`.

This is directly reachable via the same-chain path of `cancelOrder()`, which calls `withdraw()` unauthenticated except for `order.user == msg.sender`: [3](#0-2) 

as well as via the cross-chain `onAccept` `RedeemEscrow`/`RefundEscrow` path: [4](#0-3) 

Once inside `withdraw()`, regardless of entry path, `_filled[body.commitment] = beneficiary` is set unconditionally up front, and `_orders[body.commitment][token] -= amount` executes right after the no-op `.call` succeeds: [5](#0-4) 

Tron's TVM historically supports full `SELFDESTRUCT` semantics (code + storage clearing on a subsequent transaction), unlike post-Cancun Ethereum where `EIP-6780` restricts code-clearing to the same creation transaction. That makes the "token contract later destroyed, then treated as still-functional" scenario the external report warns about concretely exploitable on this specific Tron deployment target, whereas it is largely moot on the mainline EVM chains this codebase also targets.

### Impact Explanation
Once `withdraw()` "succeeds" against a token with no code, the escrow slot is decremented and the order/commitment is permanently marked `_filled`, so the true value never reaches the beneficiary and the accounting can never be corrected or retried — the escrowed tokens are effectively lost and the settlement bookkeeping falsely reports a payout that never happened. This matches the bounty's "loss of funds" and "false settlement/state acceptance" impact categories: escrow releases must move funds exactly once to the rightful beneficiary and in the correct amount, and here it can be finalized with zero amount actually delivered while burning the one-time settlement slot.

### Likelihood Explanation
The vulnerable code path (`withdraw()`) is reachable by any unprivileged order owner through the fully permissionless, same-chain `cancelOrder()` entrypoint — no relayer, prover, or admin action is required. The precondition (a token address with no deployed code at redemption time) requires either an intentionally malicious/self-destructing token used as `order.inputs[i].token`, or any ERC20 that becomes non-existent between escrow and redemption — both plausible given Tron's SELFDESTRUCT semantics differ from post-Cancun EVM chains that the rest of the codebase assumes when relying on `SafeERC20`.

### Recommendation
- Short term: Add an `EXTCODESIZE`/`token.code.length > 0` check before every raw `.call` in `withdraw()` (input token transfer, fee token transfer) and in the `SweepDust` branch of `onAccept`, reverting with `TransferFailed`/`NotContract` if absent, mirroring `CallDispatcher.dispatch`'s existing `extcodesize` guard: [6](#0-5) 
- Also decode and validate the ERC20 boolean return value (not just `success`) to catch non-reverting `transfer` failures.
- Long term: Replace the raw `.call` pattern in the Tron `IntentGatewayV2.sol` with `SafeERC20.safeTransfer`, matching the canonical `IntentsBase.sol` implementation, so both codebases share the same vetted transfer semantics.

### Proof of Concept
1. Attacker deploys `EvilToken`, a minimal ERC20 with a `selfdestruct` backdoor function callable only by the attacker.
2. Attacker calls `placeOrder(order, ...)` with `order.inputs[0].token = EvilToken`, `amount = X`; `placeOrder` calls `IERC20(EvilToken).safeTransferFrom(attacker, address(this), X)` which succeeds since `EvilToken` is currently live and attacker controls its logic (mints/approves itself `X`). Escrow is recorded: `_orders[commitment][EvilToken] = X`. [7](#0-6) 
3. Order goes unfilled; before its deadline expires (or after, depending on desired path) attacker triggers the self-destruct backdoor on `EvilToken`, clearing its code on Tron's TVM.
4. Attacker calls `cancelOrder(order, options)` on the same chain; this invokes `withdraw(body, true)` with `body.tokens[0].token = EvilToken`. [8](#0-7) 
5. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` targets an address with zero code, returning `success = true` trivially; the `!success` check is bypassed, `_orders[commitment][EvilToken] -= amount` executes, and `_filled[commitment] = beneficiary` is set — the order is now permanently marked settled with `EscrowRefunded` emitted, despite no token transfer occurring. [9](#0-8) 

This demonstrates that escrow accounting and one-time settlement state can be finalized without any real fund movement, satisfying the false-settlement / fund-loss impact criteria.

        bytes32 commitment = keccak256(abi.encode(order));
