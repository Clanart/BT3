### Title
Symlink extension spoofing bypasses the `.exe`/`.cmd`/`.bat`/`.sh` "safe extension" guardrail when opening files from a cloned repository - (File: app/src/ui/lib/context-menu.ts, app/src/ui/lib/open-file.ts, app/src/lib/app-shell.ts)

### Summary
The 51%/`AddPartyCardsAuthority` report's broken invariant is: a security guardrail (unanimous-vote protection for precious-token transfers) is enforced on the "normal" path but is silently bypassed when the same underlying primitive is reached through a different, more generic code path (`ArbitraryCallsProposal`) that never re-checks the invariant. The GitHub Desktop analog is the `isSafeFileExtension` guardrail: Desktop explicitly refuses to let a user "Open with Default Program" files with `.exe`, `.cmd`, `.bat`, `.sh` extensions, precisely to stop a malicious repository from getting the user to launch an executable. That check inspects only the *displayed* file path/extension of a tracked git object, not what the path actually resolves to on disk. A tracked symlink object (fully valid, ordinary git content that an attacker fully controls in a cloned/fetched repository) can have an innocuous name/extension (e.g. `invoice.pdf`) while pointing at an executable. The extension gate passes, and the open action (`shell.openExternal('file://...')` / `shell.openPath`) follows the symlink to the real, unsafe target — completely bypassing the guardrail that PartyDAO-style reasoning says must apply to *every* path that performs the sensitive action, not just the "normal" one.

### Finding Description
`isSafeFileExtension` in `app/src/ui/lib/context-menu.ts` is the only gate standing between "user right-clicks a file that came from a repository they cloned/fetched" and "Desktop hands that path to the OS's default-open handler": [1](#0-0) 

It is evaluated against `Path.extname(file.path)` — the tracked git path string — in every call site that offers "Open with Default Program", e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

The action itself is `openFile`, which forwards the resolved on-disk path to `shell.openExternal('file://<path>')`: [5](#0-4) 

Nowhere in this chain is the path's *real* target inspected. If `file.path` is a tracked symlink (a completely ordinary, first-class git object type; git checks out real OS symlinks by default on macOS/Linux) named e.g. `report.pdf` but pointing at `./tools/update.sh`, `./run.exe`, or any other executable already present in the working tree (or even outside it, subject to normal filesystem permissions), then:
1. `Path.extname(file.path)` evaluates to `.pdf` → `isSafeFileExtension` returns `true`.
2. `openFile` hands the literal symlink path to `shell.openExternal('file://...')`.
3. The OS resolves the symlink and launches its real target with the default handler for *that* file (an executable), not for `.pdf`.

The same absence-of-real-path-validation pattern also exists in `revealInFileManager`, which does a plain `Path.join(repository.path, path)` with no `resolveWithin`/symlink check before calling `shell.showItemInFolder`: [6](#0-5) 

Desktop's own codebase demonstrates that the team is aware symlink escapes must be explicitly guarded against — `buildConflictContext` (used for the Copilot conflict-resolution feature) explicitly resolves through `resolveWithin`, which internally calls `realpath` to defeat exactly this class of symlink trick, and treats resolution failures as "outside repository, skip": [7](#0-6) [8](#0-7) 

But that hardened `resolveWithin` guard is applied only on the Copilot AI-context-reading code path. The much more consequential "Open with Default Program" / "Reveal in File Manager" actions — reachable from the Changes list, History/Commit view, and Pull Request Files Changed view, all of which enumerate paths taken directly from a cloned/fetched/attacker-authored repository or PR diff — never route through `resolveWithin` or any symlink-aware check. This is structurally identical to the H-01 report: a safeguard exists and is correctly enforced on one code path, but a parallel, more "generic" path that performs the same sensitive operation on attacker-supplied data has no equivalent check.

### Impact Explanation
An attacker who controls a repository the victim clones/fetches (or a pull request the victim opens in Desktop, since `pull-request-files-changed.tsx` uses the identical unguarded flow) can commit a symlink with a benign-looking name/extension pointing at an executable payload in the same repo. When the victim, believing the extension check protects them, chooses "Open with Default Program" on that file, Desktop launches the real target through the OS's default handler for that file type — resulting in local code execution outside of git's own trust model and outside of the guardrail Desktop itself put in place to prevent exactly this (`RestrictedFileExtensions = ['.cmd', '.exe', '.bat', '.sh']`). This matches the "unprivileged, attacker controls a cloned/fetched repository ... result is code execution" impact class explicitly called out as valid.

### Likelihood Explanation
- No admin rights, no pre-existing malware, and no leaked credentials are required — only that the victim clones/fetches a hostile repository or opens a hostile PR in Desktop, which is a natural Desktop workflow.
- Creating a symlink with an arbitrary "safe" extension pointing at any file in the working tree (including another file from the same malicious commit) is a single `git commit` operation on an attacker-controlled machine; nothing about it is unusual or requires special git configuration by the attacker.
- The single required user action ("right-click → Open with Default Program") is an ordinary, expected interaction Desktop's UI explicitly advertises as safe via the extension allow-list — it is not an "unnatural" or contrived step.
- The bug is Unix-symlink-dependent for automatic checkout (macOS/Linux); on Windows, `core.symlinks` must be enabled or Developer Mode/admin symlink privileges available, which somewhat reduces likelihood there but does not eliminate the vulnerability on the platforms where symlinks check out natively.

### Recommendation
- Resolve the real target of the path (e.g. via `fs.realpath`/the existing `resolveWithin` helper) before evaluating `isSafeFileExtension`, and re-evaluate the extension against the resolved target rather than the tracked git path.
- Route `openFile`, `revealInFileManager`, and the Copilot conflict "open in editor/reveal" actions through the same `resolveWithin`-style guard already used in `copilot-conflict-context.ts`, refusing to open/reveal any path whose real location resolves outside the repository or resolves to a disallowed extension.
- Consider detecting symlinked working-tree entries specifically and warning the user (similar to the existing "repository appears to be owned by another user" trust prompt) before performing "Open with Default Program" on them.

### Proof of Concept
1. On macOS/Linux, create and push/clone a repository containing:
   ```
   ln -s ./payload.sh invoice.pdf
   echo -e '#!/bin/sh\ntouch ~/PWNED' > payload.sh
   chmod +x payload.sh
   git add invoice.pdf payload.sh
   git commit -m "add invoice"
   ```
2. Victim clones this repository in GitHub Desktop and opens the History view (or Changes view if uncommitted) showing `invoice.pdf`.
3. Victim right-clicks `invoice.pdf` and selects "Open with Default Program". Because `Path.extname('invoice.pdf')` is `.pdf`, `isSafeFileExtension` in [1](#0-0)  returns `true`, so the menu item is enabled (see `enabled: isSafeExtension && fileExistsOnDisk` in [9](#0-8) ).
4. `openFile` at [10](#0-9)  calls `shell.openExternal('file://.../invoice.pdf')`. The OS follows the symlink and executes `payload.sh` with its own default handler (e.g. Terminal/shell interpreter), running attacker code (`touch ~/PWNED`) as the victim user — despite `.sh` being on the explicit `RestrictedFileExtensions` block list intended to prevent exactly this.

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
