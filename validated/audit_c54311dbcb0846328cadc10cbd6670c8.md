Missing recipient binding in `EncryptedMessage` proof-of-possession lets a relayer get an honest DKG participant blamed as faulty - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The per-message proof-of-possession (`pop`) in PedPoP's encryption layer binds the ephemeral key, the claimed sender (`from`), the context, and the ciphertext — but not the intended recipient's encryption key. Consequently, an `EncryptedMessage` created by Alice for Bob passes all authenticity checks when presented as Alice's message *to Carol*. Carol's decryption produces garbage, and the blame protocol then deterministically attributes the fault to Alice, an honest sender.

### Finding Description
`EncryptedMessage` carries an ephemeral public `key`, a `pop` Schnorr signature over it, and the ciphertext. The PoP challenge is computed as `pop_challenge::<C>(context, pub_nonce, pub_key, from, msg)` — sender and ciphertext are bound, recipient is not. [1](#0-0) 

When `KeyMachine::calculate_share` processes shares, `Encryption::decrypt` batch-verifies the PoP against `(context, R, msg.key, from, ciphertext)` and then decrypts with `ecdh(self.enc_key, msg.key)`. [2](#0-1)  Nothing distinguishes Alice's message-to-Bob from Alice's message-to-Carol. When blame is adjudicated, `blame_internal` → `Decryption::decrypt_with_proof` re-verifies the same recipient-agnostic PoP, verifies the accuser's DLEq proof that `proof.key = enc_key_recipient * msg.key`, decrypts, and — because the plaintext is garbage under the wrong ECDH key — fails `C::F::from_repr` or the share verification against the sender's commitments, returning `sender` as faulty. [3](#0-2) [4](#0-3) 

The comments acknowledge the sibling attack (Eve copying Alice's encryption *key*) and defend it with the PoP, but the inverse — copying Alice's *message* to a different recipient — is unhandled. [5](#0-4) 

### Impact Explanation
In Serai, shares are routed to each participant keyed by sender `Participant` (see `handle_machine`, which builds the per-recipient `shares` map from coordinator-delivered bytes and feeds it to `calculate_share`). [6](#0-5)  Any party able to observe and redirect the share message — e.g., the coordinator/relayer assembling the `HashMap<Participant, EncryptedMessage>` delivered to each validator — can place Alice→Bob's ciphertext in Carol's share set. Carol then emits an `InvalidShare` accusation with a valid `EncryptionKeyProof`, and every verifier of `VerifyBlame`/`AdditionalBlameMachine` independently confirms Alice as faulty. The concrete impact: an honest participant is cryptographically "proven" faulty, aborted out of key generation, and subject to slashing/removal (`RemoveParticipantDueToDkg`). This is integrity damage attributable to untrusted message bytes, not merely protocol liveness.

### Likelihood Explanation
Requires the ability to observe an encrypted share in transit and deliver it to a different recipient — no key knowledge, forgery, or collusion is needed, since the PoP is computed over recipient-agnostic fields and verifies cleanly. The relay is detectable only as "Alice sent Carol a bad share," which is exactly the (incorrect) conclusion the protocol draws. Countered only by the assumption that per-recipient channels are perfectly authenticated end-to-end, which the library explicitly delegates to callers while the blame machinery is invoked on coordinator-routed data.

### Recommendation
Bind the recipient's registered encryption public key (or recipient `Participant`) into `pop_challenge` — e.g., `pop_challenge(context, R, key, from, to_enc_key, msg)` — so a message proves it was encrypted for a specific recipient's key. `encrypt` already knows `to` (the recipient's enc key) at signing time, and `decrypt`/`decrypt_with_proof` know the recipient's registered key from `self.enc_keys[&decryptor]`/`self.enc_key`, so verification can reconstruct the same challenge. This also hardens `blame_internal`, which currently cannot distinguish "sender encrypted to wrong key" from "message was relayed to the wrong recipient." [7](#0-6) 

### Proof of Concept
1. Alice runs `generate_secret_shares`, producing `EncryptedMessage` values; `res[Bob] = encrypt(rng, context, Alice, enc_keys[Bob], share_ab)`. The `pop` signs `pop_challenge(context, R_ab, K_ab, Alice, ct_ab)`.
2. A relayer intercepts Alice's share intended for Bob and delivers it inside Carol's inbound `shares` map under `Participant::Alice`.
3. Carol's `calculate_share` calls `self.encryption.decrypt(..., from=Alice, msg)`; `msg.pop.batch_verify` passes because the challenge does not commit to Bob's key; `ecdh(carol_enc_priv, K_ab)` yields a key unrelated to `ecdh(alice_eph, bob_enc_pub)`, so `ct_ab` decrypts to garbage. `C::F::from_repr` fails or the share verification statements vs Alice's commitments fail → `PedPoPError::InvalidShare { participant: Alice, blame: Some(proof) }`. [8](#0-7) 
4. Any participant (or `AdditionalBlameMachine::new` evaluator) runs `blame_internal(Alice, Carol, msg, Some(proof))`: the PoP verifies (sender-bound only), the DLEq verifies `proof.key` against Carol's registered `enc_key`, decryption yields garbage, and the function returns `Alice` — honest Alice is adjudicated faulty and her DKG participation is slashed/aborted.

fn encrypt<R: RngCore + CryptoRng, C: Ciphersuite, E: Encryptable>(
  rng: &mut R,
  context: [u8; 32],
  from: Participant,
  to: C::G,
  mut msg: Zeroizing<E>,
) -> EncryptedMessage<C, E> {
  /*
  The following code could be used to replace the requirement on an RNG here.
  It's just currently not an issue to require taking in an RNG here.
  let last = self.last_enc_key.to_bytes();
  self.last_enc_key = C::hash_to_F(b"encryption_base", last.as_ref());
  let key = C::hash_to_F(b"encryption_key", last.as_ref());
  last.as_mut().zeroize();
  */

  // Generate a new key for this message, satisfying cipher's requirement of distinct keys per
  // message, and enabling revealing this message without revealing any others
  let key = Zeroizing::new(C::random_nonzero_F(rng));
  cipher::<C>(context, &ecdh::<C>(&key, to)).apply_keystream(msg.as_mut().as_mut());

  let pub_key = C::generator() * key.deref();
  let nonce = Zeroizing::new(C::random_nonzero_F(rng));
  let pub_nonce = C::generator() * nonce.deref();
  EncryptedMessage {
    key: pub_key,
    pop: SchnorrSignature::sign(
      &key,
      nonce,
      pop_challenge::<C>(context, pub_nonce, pub_key, from, msg.deref().as_ref()),
    ),
    msg,
  }
}
