### Title
Payout output-mutation before confirmation lets an attacker strip the OP_RETURN and misattribute a funded payout as "optimistic" - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` derives `operator_xonly_pk` solely from the OP_RETURN of whichever transaction actually confirms as the spend of the registered `withdrawal_utxo`, via `get_payout_txs_for_withdrawal_utxos` joining on `bitcoin_syncer_spent_utxos.spending_txid` matched by `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, not by a precomputed expected txid [1](#0-0) . If the input signature's sighash flag permits output mutation (`SIGHASH_SINGLE|ANYONECANPAY` or similar), an attacker can rebroadcast a variant of the operator's Payout tx with the OP_RETURN output stripped/corrupted, and if that variant confirms first, `update_finalized_payouts` records `operator_xonly_pk = None` for that withdrawal, permanently misattributing a funded payout as "optimistic".

### Finding Description
Binding claimed broken: `operator_xonly_pk` recorded for withdrawal index `i` == xonly pubkey of the operator whose payout output funded the confirmed spend of `withdrawal_utxo[i]`.

`create_payout_txhandler` builds the Payout tx with three outputs: user payout, anchor, and OP_RETURN(`operator_xonly_pk`) [2](#0-1) . The single input is spent via `SpendPath::KeySpend` with `user_sig` [3](#0-2) . I was not able to confirm, within tool-call budget, that this specific `user_sig` is bound with `SIGHASH_SINGLE|ANYONECANPAY` (I found `SinglePlusAnyoneCanPay` references across `actor.rs`, `deposit_signature_owner.rs`, `txhandler.rs`, `aggregator.rs`, `rpc/parser/operator.rs` but did not get to read them before the iteration budget ran out) — this is the key precondition the question asserts and it remains unverified from my trace.

Assuming that precondition holds (as stated in the question, the user-provided sighash flag permits it), the downstream detection logic is real and exploitable as described: `update_finalized_payouts` reads whichever tx is recorded as `bsu.spending_txid` for the registered `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the block being synced, extracts the first OP_RETURN via `get_first_op_return_output`, and parses it with `parse_op_return_data`; on any failure it silently defaults `operator_xonly_pk` to `None`, with only a log message noting ambiguity between "optimistic payout" and "operator constructed the payout tx wrong" [4](#0-3) . There is no additional check cross-referencing the payout output value/script against any specific operator's known payout, nor any check that a `None` result wasn't actually a mutated/corrupted attribution of a real operator-funded payout. This value is then persisted via `update_payout_txs_and_payer_operator_xonly_pk` [5](#0-4) , and used later by `get_first_unhandled_payout_by_operator_xonly_pk` (keyed by the recorded `payout_payer_operator_xonly_pk`) to let the honest operator claim reimbursement via `PayoutCheckerTask`/`handle_finalized_payout` [6](#0-5) [7](#0-6) . Since the recorded pk is `None`, the honest operator's `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` query never returns this withdrawal, so reimbursement is unreachable for that operator for that withdrawal permanently.

However, `is_kickoff_malicious` independently treats a `None` operator_xonly_pk as "assume malicious" [8](#0-7) , which would cause verifiers to flag the operator's kickoff as malicious rather than confirm it — this is a related but distinct consequence not fully traced here (whether this results in slashing or merely a failed reimbursement attempt was not verified in the time available).

### Impact Explanation
If realized, an honest operator that fronted a payout becomes unable to claim Reimburse for that withdrawal (funds effectively frozen from the operator's perspective, and the operator may additionally be flagged malicious by `is_kickoff_malicious`), which matches the "honest operator permanently unable to be reimbursed" Critical category. The blast radius is per-withdrawal and requires the specific sighash/malleability precondition to hold for each attempt, so it is not automatically repeatable across all withdrawals without the same signature property being present each time.

### Likelihood Explanation
The core precondition — that the Payout tx's single input signature uses a sighash flag (`SIGHASH_SINGLE|ANYONECANPAY` or equivalent) that permits third parties to alter non-witness outputs including the OP_RETURN without invalidating the signature — could not be confirmed from the code paths I was able to read before the iteration budget was exhausted. `SinglePlusAnyoneCanPay` does appear referenced in `core/src/actor.rs`, `core/src/builder/transaction/deposit_signature_owner.rs`, `core/src/builder/transaction/txhandler.rs`, and `core/src/rpc/parser/operator.rs`/`core/src/rpc/aggregator.rs`, suggesting this sighash type is used somewhere in the protocol (possibly for the deposit or operator-reimburse flows, not necessarily for the Payout tx's `user_sig`), but I did not verify whether it specifically applies to the Payout tx input that `create_payout_txhandler` signs. Given the ambiguity, likelihood cannot be conclusively assessed without further investigation.

### Recommendation
Since I could not confirm the exact sighash type bound to the Payout tx's user signature within the available tool budget, I cannot make a final determination. If the precondition holds (mutable OP_RETURN under the user's signature), the fix should ensure `user_sig`'s sighash type commits to all outputs (e.g. `SIGHASH_ALL` or `SIGHASH_SINGLE` without `ANYONECANPAY` combined with output commitment covering the OP_RETURN), or have the protocol independently attribute `operator_xonly_pk` from a source not spoofable by mutating unsigned/uncommitted outputs (e.g., from the operator's `withdraw` RPC call record correlated with `spending_txid`'s first input rather than from a mutable OP_RETURN alone).

### Proof of Concept
Not conclusively determinable from available context — reproducing this requires first confirming (via `cargo test` inspection of `core/src/actor.rs` signing code and `withdraw` in `core/src/operator.rs`) which `sighash_type` is actually applied to `user_sig` in `create_payout_txhandler`. If it is confirmed to be `SIGHASH_SINGLE|ANYONECANPAY` (or another flag that leaves the OP_RETURN output unsigned), the PoC would be: sign a Payout tx with that sighash type on regtest, construct an attacker variant with the OP_RETURN output stripped, broadcast the attacker variant so it confirms first, run `update_finalized_payouts`, and assert `get_payout_info_from_move_txid` returns `operator_xonly_pk == None` instead of the funding operator's key — demonstrating the misattribution. This assertion could not be executed or verified here.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
