### Title
Attacker-controlled `offset` is preserved verbatim through `ReceivedOutput::read` and trusted to re-key funds, causing outputs to be reported under the wrong spendable key - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs), [File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
CVE-2016-7097's class is "a privilege-carrying attribute (setgid) is preserved across an operation (setxattr) that should have stripped it." The Serai analog is the `offset` field of `ReceivedOutput`: it is deserialized verbatim via `Secp256k1::read_F` and never re-derived or validated against `output.script_pubkey`. The downstream code unconditionally trusts it both for attribution (`Output::key() = script_key - G*offset`) and for spending (the multisig applies `keys.offset(output.offset())`). A corrupted offset therefore "keeps" a capability it was never granted: it re-labels which key owns an output.

### Finding Description
`ReceivedOutput::read` reads `offset` as an arbitrary scalar and stores it alongside an arbitrary `TxOut` and `OutPoint` without checking that `script_pubkey == p2tr(key + G*offset)`: [1](#0-0) 

`Scanner` establishes the only legitimate offset↔script binding at scan time via `register_offset`/`scan_transaction`, where the offset is *derived* from the matched `script_pubkey`: [2](#0-1) 

But once an output is serialized and re-read (`Output::read` → `ReceivedOutput::read`), that binding is lost and the stored offset is taken on faith: [3](#0-2) [4](#0-3) 

The same offset is then consumed to produce the signing key for the input (`keys.offset(...)` semantics; tests confirm `output.offset()` is the spend offset, networks/bitcoin/tests/wallet.rs:217-222).

### Impact Explanation
An unprivileged party able to supply bytes to `ReceivedOutput::read`/`Output::read` can pair a genuine registered `script_pubkey` (a real, funded output) with a modified `offset` scalar. Two concrete harms:

1. **Funds reported received that are not spendable.** The wallet attributes the output to `key + G*offset'`, but at spend time the produced signature is for the wrong tweaked key, so the input can never satisfy the output's script — the funds are booked but burn.
2. **Misattribution across output kinds/keys.** `Output::key()` returns `script_key - G*offset`; by choosing `offset`, an attacker can make an output appear to belong to a different multisig key or different `OutputType` (External/Branch/Change/Forwarded), since `kinds` is keyed purely by the offset's repr (processor/src/networks/bitcoin.rs:322-331, 693-697). Forwarded outputs carry distinct handling semantics, so mislabeling can redirect downstream behavior.

### Likelihood Explanation
Reachability requires an untrusted party to influence the byte stream fed to `ReceivedOutput::read`/`Output::read` (serialized output records, e.g., processor-persisted or coordinator-relayed data). This is a listed in-scope sink in the scan rules. The missing check is real and unconditional — no code path re-verifies `script_pubkey` against the offset after deserialization — so exploitability depends only on that byte supply being attacker-influenced, which the scan model assumes. Severity Medium: integrity/fund-availability impact without key recovery.

### Recommendation
After deserialization, re-derive the binding: verify `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` (or at minimum reject offsets that would make `key()` fall outside the registered key set), rejecting mismatches instead of preserving them. Alternatively, persist only the `script_pubkey` and re-run the Scanner's script→offset map on read, never trusting a serialized offset.

### Proof of Concept
```rust
// Conceptual: attacker holds a real scanned output (offset O, script S)
// and flips the offset before the bytes are re-read.
let legit: ReceivedOutput = scanner.scan_transaction(&tx).remove(0); // offset = O
let mut buf = legit.serialize();
// Overwrite the first 32 bytes (the serialized Scalar offset) with O + 1
let bad_offset = legit.offset() + Scalar::ONE;
buf[.. 32].copy_from_slice(bad_offset.to_repr().as_ref());

let evil = ReceivedOutput::read::<&[u8]>(&mut buf.as_slice()).unwrap();
// evil.script_pubkey is still S, but offset is now O+1.
// Output::key() reports key + G*(O+1) instead of key + G*O:
assert_ne!(evil.offset(), legit.offset());
// Spending this output builds keys.offset(O+1), whose group key does not
// match S's tweaked key — the input can never be signed for.
```

Caveat: I could not fully inspect `send.rs`/`SignableTransaction::new` to confirm whether the spend path re-validates `script_pubkey` vs. offset at construction time; if it does, the primary impact narrows to a guaranteed unspendable-output (fund-freeze) outcome rather than silent misattribution.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };
