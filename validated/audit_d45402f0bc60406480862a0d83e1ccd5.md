### Title
Schnorr signature verification accepts the identity public key, enabling universal forgery - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` performs the check `R + c·A − s·G == 0` with no rejection of the identity point for either the public key `A` or the nonce commitment `R`. For `A = identity`, any `(R = s·G, s)` pair satisfies the equation for *every* challenge `c`, producing a universal forgery. The deserialization path reachable by untrusted bytes — `SchnorrSignature::read` → `Ciphersuite::read_G` — enforces canonical encoding and torsion-freedom but deliberately does **not** reject identity; only `Curve::read_G` in crypto/frost adds that check, and `SchnorrSignature`/`SchnorrAggregate` do not use it.

### Finding Description
`SchnorrSignature::batch_statements` returns `[(1, R), (challenge, public_key), (-s, G)]` and `verify` accepts iff the multiexp sums to identity [1](#0-0) . There is no `is_identity` check on `public_key` or `self.R`. Reading is equally permissive: `SchnorrSignature::read` calls `C::read_G`, and `Ciphersuite::read_G` only rejects non-canonical encodings, not the identity [2](#0-1) [3](#0-2) . Contrast with `Curve::read_G`, which explicitly rejects identity points — showing the codebase recognizes this validation requirement but only applies it on the FROST path [4](#0-3) . The same gap exists in `SchnorrAggregate::read`/`verify`, where attacker-supplied `Rs` and `keys_and_challenges` keys can be identity [5](#0-4) .

This is the direct analog of CWE-295 (improper validation of a certificate/key): a public key that carries no secret can be accepted as authenticating any message.

### Impact Explanation
Any verifier that checks `SchnorrSignature::verify(public_key, challenge)` where `public_key` originates from attacker-controlled or deserialized bytes (a routine `read_G` result) can be forged against by submitting `public_key = identity` together with `R = s·G` for arbitrary `s`. The forged "signature" passes for every challenge, including transcript-derived ones, because `c·identity = identity`. In the FROST aggregation path (`Schnorr::verify` / `verify_share` in crypto/frost/src/algorithm.rs [6](#0-5) ), `group_key`/`verification_share` are derived from threshold parameters; a share/key setup that yields an identity group key would be trivially forgeable, and the per-share batch statement inherits the same missing identity check. In `SchnorrAggregate::verify`, an identity entry among `keys_and_challenges` makes that component unconditionally satisfiable regardless of the challenge.

### Likelihood Explanation
Exploitation requires reaching a `verify` call with an attacker-influenced public key that can be the identity point. Standalone `SchnorrSignature::read`/`verify` and `SchnorrAggregate` accept such keys directly from a byte stream — no threshold ceremony needed. Whether a specific in-scope consumer permits an identity key depends on upstream key-registration validation (e.g., FROST's `Curve::read_G` blocks identity for commitments but group keys come from `ThresholdView`, not a deserializer that rejects identity). As a library-level verification flaw reachable through public deserialization + verify APIs, this is a concrete Medium/High finding rather than theoretical.

### Recommendation
- In `SchnorrSignature::verify` (and the `Schnorr::verify`/`verify_share` implementations in crypto/frost and networks/bitcoin/src/crypto.rs), reject `public_key.is_identity()` and `R.is_identity()` before evaluating `batch_statements`.
- In `SchnorrAggregate::verify`, reject identity keys/Rs.
- Prefer routing all untrusted point deserialization through a reader that rejects identity (as `Curve::read_G` does), or add an explicit `is_identity` guard where the schnorr crate reads `R`.

### Proof of Concept
```rust
// For any ciphersuite C, identity public key, arbitrary s:
let a = C::G::identity();                       // "public key", passes C::read_G
let s = C::F::ONE;                              // any scalar
let sig = SchnorrSignature::<C> { R: C::generator() * s, s };
// For ANY challenge c: R + c*identity - s*G = R - s*G = 0
assert!(sig.verify(a, C::F::random(&mut OsRng))); // forged signature accepted
```
The equation reduces to `s·G + c·0 − s·G = 0` identically in `c`, so the forger needs no knowledge of a discrete logarithm and the proof holds for every message/challenge.

Caveat: I could not exhaustively trace every production caller of `verify` to confirm an identity key is deliverable end-to-end in a deployed path (e.g., whether coordinator/tributary or processor registration blocks identity keys before they reach `verify`). The library-level forgery is unconditional; the end-to-end severity depends on that upstream filtering.

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
