## Title
Attacker-controlled `WWW-Authenticate` header from a git remote/proxy tricks the credential helper into treating a malicious host as GitHub Enterprise and initiating an OAuth sign-in (client secret + user creds) against it - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The broken invariant in the C4 report is "the guard/finalization is placed after the attacker-observable/attacker-triggerable side effect, so the attacker can steer that side effect using data it controls." The Desktop analog is `getEndpointKind()` in the git-credential trampoline: it classifies an unknown remote host as a trusted GitHub/GHE endpoint based solely on a `WWW-Authenticate` response header value, which is data returned by the remote HTTP server itself — i.e. attacker-controlled when the "git remote/proxy response" is malicious. That misclassification then drives `getCredential()` to launch a real GitHub sign-in/OAuth flow pointed at the attacker's host, sending Desktop's OAuth `client_id`/`client_secret` and potentially the user's real credentials to that host.

### Finding Description
When Git needs credentials for any remote, it invokes `git-credential-desktop`, which is handled by `createCredentialHelperTrampolineHandler` → `getCredential()`: [1](#0-0) 

`getCredential` calls `getEndpointKind(cred, store)` to decide whether the target host should be treated as `'github.com'`, `'ghe.com'`/`'enterprise'`, or `'generic'`. Inside `getEndpointKind`, before doing any authoritative check, the code trusts the `wwwauth[...]` fields harvested from the credential-fill request (these come directly from HTTP response headers sent by the remote server during Git's authentication negotiation): [2](#0-1) 

Only if none of the `wwwauth[]` values match is a real network check (`isGitHubHost(endpoint)`) performed: [3](#0-2) 

This means a remote (or a malicious proxy sitting in front of it — explicitly an in-scope attacker primitive) can respond to Git's authentication probe with `WWW-Authenticate: Basic realm="GitHub"` for any arbitrary host and be classified as `'enterprise'` purely from that header, without Desktop ever confirming the host actually runs GitHub Enterprise Server's API.

Back in `getCredential`, once `endpointKind !== 'generic'` and no existing account matches that host, Desktop automatically prompts a real GitHub sign-in flow against the attacker's endpoint: [4](#0-3) 

`ui.promptForGitHubSignIn` drives `dispatcher.beginEnterpriseSignIn` + `setSignInEndpoint(origin)` and eventually `authenticateWithBrowser()`, which builds the OAuth authorize URL and later posts the access-token exchange **to the attacker-controlled `endpoint`**, including Desktop's real OAuth `client_id`/`client_secret`: [5](#0-4) 

The existing guard — `getIsBackgroundTaskEnvironment(token)` — only suppresses the prompt for background operations (e.g. fetch on a schedule); it does not validate the target host at all, so any foreground git operation (`clone`, `pull`, `push`, `fetch` initiated by the user) against a malicious/compromised remote can trigger this flow. The correct authoritative check (`isGitHubHost`) exists in the same function but is only reached as a last resort, after the attacker-controlled header shortcut has already succeeded.

### Impact Explanation
- Desktop's shared OAuth `client_secret`/`client_id` are sent verbatim to an attacker-controlled host chosen purely by response-header spoofing (`requestOAuthToken`), which is a credential/secret exfiltration.
- The user is shown Desktop's native "Sign in to GitHub" popup pointed at the attacker's endpoint, making a convincing phishing surface fully orchestrated by Desktop itself (not a user-typed URL) — the user did not choose to add this endpoint, it was inferred from the malicious remote/proxy response.
- Because `beginEnterpriseSignIn` treats the attacker's host as a legitimate GHE instance, any account bound during this flow (`Account`) is stored by `AccountsStore` and subsequently used by Desktop to authenticate git operations against that origin, effectively an unauthorized/forced account-binding to attacker infrastructure.

### Likelihood Explanation
This requires only that a user perform a normal git network operation (clone/fetch/pull/push) against a remote that returns a crafted `WWW-Authenticate` header — either a malicious remote the user was pointed to (e.g., via a "clone this repo" link, a forked dependency, or a submodule URL) or a man-in-the-middle/proxy on an HTTP(S) remote. No local access, admin rights, or pre-existing malware is needed; the only "unnatural" step is that Desktop itself, not the user, decides to show the GitHub sign-in dialog based on the header.

### Recommendation
Do not classify a host as GitHub/Enterprise based solely on the `WWW-Authenticate` realm string returned by the remote. Always perform the authoritative `isGitHubHost(endpoint)` check (or equivalent, e.g. verifying the `/meta` or well-known GHE API endpoint with an expected response shape) before offering sign-in, and require explicit user confirmation showing the literal hostname before initiating any OAuth flow against a previously-unknown endpoint.

### Proof of Concept
1. Attacker sets up an HTTP server at `https://evil.example.com` that, when Git requests credentials (`GET`/negotiation on push/pull), responds with header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds `https://evil.example.com/foo.git` as a remote (e.g., by cloning a repo whose instructions/README tell them to add this "mirror", or via a compromised transparent proxy) and runs `git pull`/`git push` in Desktop.
3. Git's credential-fill negotiation reaches `getEndpointKind`, which sees the `wwwauth[...]` value containing `realm="GitHub"` and returns `'enterprise'`. [6](#0-5) 
4. Since no existing account matches `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')`. [7](#0-6) 
5. The sign-in flow constructs `getOAuthAuthorizationURL('https://evil.example.com', state)` and, upon completing the browser step, POSTs `client_id`/`client_secret`/`code` to `https://evil.example.com/login/oauth/access_token`. [8](#0-7) 
6. The attacker's server captures the OAuth secret and/or the callback exchange, completing credential/secret exfiltration.

Everything I could confirm is grounded in the cited source; I was not able to execute the flow end-to-end (no runtime/browser access in this mode) to observe the actual HTTP request Desktop sends, so step 5's exact request/response shape should be verified by a Devin session with the ability to run Desktop and a mock malicious server.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

export function getOAuthAuthorizationURL(
  endpoint: string,
  state: string
): string {
  const urlBase = getHTMLURL(endpoint)
  const scope = encodeURIComponent(oauthScopes.join(' '))

  return new window.URL(
    `/login/oauth/authorize?client_id=${ClientID}&scope=${scope}&state=${state}`,
    urlBase
  ).toString()
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
