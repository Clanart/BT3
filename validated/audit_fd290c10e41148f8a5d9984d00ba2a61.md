### Title
Schnorrkel challenge hash panics on short/malformed messages, enabling remote DoS of verifiers and signers - (File: crypto/schnorrkel/src/lib.rs)

### Summary
`SchnorrkelHram::hram` (the `Hram` used by FROST-style Schnorr verification under the `Schnorrkel` ciphersuite) assumes the message being hashed is a schnorrkel-style framed blob: it unconditionally slices `m[0..4]` to read a context length and then slices `m[4 .. 4 + ctx_len]`. Any message shorter than 4 bytes, or whose declared `ctx_len` exceeds the actual buffer, causes a panic (`expect("malformed message")` / slice-out-of-bounds). An unprivileged party who can cause the system to verify or sign an attacker-controlled message (e.g., feed a crafted byte string to `SchnorrSignature::verify`, `batch_verify`, `DLEqProof`-adjacent flows, or a FROST `verify`/`sign`/`complete` path built on `Schnorrkel`) crashes the process — a direct analog of the SaltStack crafted-request DoS (CWE-20 / CWE-400): insufficient input validation on attacker-controlled bytes leads to denial of service.

### Finding Description
In `crypto/schnorrkel/src/lib.rs` lines 41-53, `hram` executes:

```rust
let ctx_len =
  usize::try_from(u32::from_le_bytes(m[0 .. 4].try_into().expect("malformed message")))
    .unwrap();
let mut t = signing_context(&m[4 .. (4 + ctx_len)]).bytes(&m[(4 + ctx_len) ..]);
```

- `m[0..4]` panics via `expect` for `m.len() < 4`.
- `m[4 .. 4 + ctx_len]` panics when `ctx_len > m.len() - 4`; `4 + ctx_len` can also overflow `usize` for `ctx_len = u32::MAX` on 32-bit, and on 64-bit simply produces an out-of-range slice panic.
- `m[(4 + ctx_len) ..]` panics likewise.

`hram` is invoked inside `SchnorrSignature::verify`/`batch_verify` (crypto/schnorr) whenever the `Hram` is `SchnorrkelHram`, i.e., whenever a signature/proof over a Schnorrkel ciphersuite is checked against an attacker-supplied message `m`. It is also invoked during `sign` in `crypto/frost/src/sign.rs` when producing a signature share, so a coordinator/processor path that signs externally-supplied payloads (e.g., slash-report or instruction messages routed through a Schnorrkel-based `SignMachine`) crashes equally. No authentication, key knowledge, or collusion is required — only control of the message bytes.

### Impact Explanation
A single malformed message deterministically panics any node that runs Schnorrkel-based Schnorr verification or signing on it. In a threshold validator/processor deployment, a panic aborts the signing/verification task and can crash the process handling it, denying service to the DKG/signing pipeline. If messages are broadcast to all validators (e.g., via a mempool or coordinator fan-out), one crafted payload can crash every recipient simultaneously, halting multisig operations — availability impact matching the High-severity CWE-400 class of the reference advisory.

### Likelihood Explanation
Verification and signing functions on this code path accept raw `&[u8]` messages with no length/framing precondition enforced before `hram` slices them — the framing assumption is implicit and undocumented at the call boundary. Any reachable path where external transaction data or an external instruction becomes the signed/verified message under the Schnorrkel ciphersuite is exploitable with a 0–3 byte payload or a 4-byte payload whose first word exceeds the buffer length. Triggering requires no valid signature and no threshold collusion; the panic occurs during challenge computation before any signature check completes.

### Recommendation
Validate the message structure in `SchnorrkelHram::hram` before slicing: return a defined error (or map to a sentinel challenge) when `m.len() < 4` or `4 + ctx_len > m.len()`. Preferably, enforce message length/format at the `Schnorr::verify`/`sign` boundary for the `Schnorrkel` algorithm so malformed input yields `Err`/verification failure instead of a panic, and replace `expect`/`unwrap` with checked slicing (`get(..)`).

### Proof of Concept
For any `R`, `A`, call `SchnorrkelHram::hram(&R, &A, &m)` (equivalently `SchnorrSignature::<Ristretto,_>::verify` under the Schnorrkel algorithm) with either of:

```rust
// Case 1: fewer than 4 bytes -> `m[0..4]` panics on expect("malformed message")
let m1: &[u8] = b"ab";

// Case 2: ctx_len = 0xFFFF_FFFF while buffer is 4 bytes -> `m[4 .. 4 + ctx_len]` OOB panic
let m2: &[u8] = &[0xff, 0xff, 0xff, 0xff];
```

Both cases panic in `crypto/schnorrkel/src/lib.rs` before any signature validity is evaluated, crashing the verifying/signing task from unauthenticated input. [1](#0-0)
