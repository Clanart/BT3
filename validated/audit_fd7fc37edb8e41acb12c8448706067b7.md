### Title
`SignableTransaction` computes the fee/vbytes without the OP_RETURN data output, so the produced transaction can underpay below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output carrying up to 80 bytes of caller-supplied data into `tx_outs`, but computes `needed_fee` from a virtual size (`vbytes`) derived only from `payments` (and optionally `change`) — never including the data output. The minimum-relay-fee check is therefore performed against a smaller vbytes than the transaction that is actually signed and broadcast, which is the same bug class as the Fenix report: a component is added to the object being built but not to the aggregate used for accounting, so the committed total diverges from the real total.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- The OP_RETURN output is appended to the outputs that will be signed (lines 194-202).
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (line 204) builds a mock transaction only from `payments` — the `data` output is never part of the weight/vbytes calculation.
- `let mut needed_fee = fee_per_vbyte * vbytes;` (line 206) and the min-relay check `if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000)` (line 211) both use this under-counted vbytes.
- The change branch reuses the same omission: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (lines 225-227) still excludes the data output, so `fee_with_change` is also under-counted.
- The signed transaction (`self.tx`, lines 245-251) contains `tx_outs`, which does include the OP_RETURN output.

An OP_RETURN output with 80 bytes of data adds roughly 92 serialized bytes (~23 vbytes + output overhead). If `fee_per_vbyte` is near the minimum relay rate, `needed_fee` can satisfy the line-211 check while the *actual* transaction's fee rate falls below the default minimum relay fee, or simply below the rate the caller requested.

### Impact Explanation
The multisig produces a transaction whose effective fee rate is lower than requested and potentially below Bitcoin's default minimum relay fee. Such a transaction is rejected/non-propagated by standard nodes, so the threshold spend fails to confirm — a DoS on the multisig's ability to move funds for that plan, requiring the signing round to be re-run with corrected parameters. A participant able to influence the signed `data` payload (untrusted bytes fed into the transaction to be signed) can deliberately pad it to maximize the discrepancy.

### Likelihood Explanation
Requires `data` to be supplied and a `fee_per_vbyte` close to the minimum relay fee for the discrepancy to actually drop below relay policy. When `fee_per_vbyte` is comfortably above the minimum, the only effect is paying a slightly lower effective feerate than requested. This makes the DoS scenario conditional, hence Medium at most rather than High.

### Recommendation
Include the OP_RETURN output (and any other non-payment outputs) in the transaction used by `calculate_weight_vbytes` — e.g., pass the fully-constructed `tx_outs` (or an equivalent `(ScriptBuf, u64)` list including the data output) to the weight calculation for both the no-change and with-change paths, so `needed_fee` and the min-relay check reflect the real signed transaction.

### Proof of Concept
1. Construct `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate (1 sat/vbyte equivalent).
2. `vbytes` is computed from inputs + payments (+ change) only; `needed_fee = fee_per_vbyte * vbytes` passes the line-211 check.
3. The produced `tx` additionally contains the ~92-byte OP_RETURN output. `fee()` (lines 138-141) still reports `needed_fee`, but the true serialized transaction is larger, so its real feerate is `< fee_per_vbyte` and below `DEFAULT_MIN_RELAY_TX_FEE` per real vbyte.
4. Broadcasting the signed transaction is rejected as non-standard underpaying fee → the multisig spend does not propagate (DoS), directly analogous to `permanentTotalSupply` diverging from the actual locked sum so the last participant's operation fails.

Note: my search was limited; this is the strongest reachable analog of the "item updated but aggregate not" accounting mismatch I could identify in the in-scope code. I did not find a matching underflow/aggregate-drift pattern inside the `crypto/` crates' sign/verify paths that is reachable purely from untrusted bytes.
