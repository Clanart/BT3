## Title
Stale-snapshot race in Copilot conflict-resolution write path can silently discard in-progress edits and write content that no longer matches on-disk state - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

## Summary
GitHub Desktop's Copilot merge-conflict resolution feature computes the final file content to be written (`reassembleResolvedFile`) once, immediately after the LLM response arrives, from a **snapshot of the file taken before the (often multi-second-to-two-minute) round trip to Copilot**. When the user clicks "Continue Merge," that pre-computed content is written to disk and staged. The only safety check before the overwrite is a heuristic that skips writing *only if the file's conflict markers are already gone* — it does not verify that the on-disk content still matches the snapshot the resolution was built from. This mirrors the Karak `NativeVault` bug class: a value (the final content to write) is computed from a stale state snapshot, and the guard meant to prevent misuse of that stale value is necessary but not sufficient, letting a corrupted/inconsistent result reach the user's commit.

## Finding Description
The flow is:

1. `buildConflictContext` reads each conflicted file once and calls `extractConflictHunks` to slice out the `<<<<<<< / ======= / >>>>>>>` blocks, storing the full on-disk snapshot in `rawContent`. [1](#0-0) 

2. After the model responds (this can take a long time — the app itself tracks buckets at 15s/30s/60s/120s, confirming multi-minute latencies are an expected, common case), `reassembleResolutions` splices the model's per-hunk output back into that **stale** `rawContent`, by position/order, not by verifying the file hasn't changed since it was read. [2](#0-1) [3](#0-2) 

3. The reassembled string is cached in `copilotResolutions` in the multi-commit-operation state and is *not* recomputed later.

4. When the user clicks "Continue Merge," `_applyCopilotConflictResolutions` writes that cached, stale-derived content straight to disk and stages it: [4](#0-3) 

The only guard against overwriting newer on-disk state is:
```
const onDiskFile = state.changesState.workingDirectory.files.find(...)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue
}
``` [5](#0-4) 

This check only detects the case where the file is *fully* resolved (no markers left) by the time of writing. It does **not** detect the case where the on-disk file still shows as "Conflicted" (markers still present, so `isConflictedFileStatus` is true and `hasUnresolvedConflicts` is true) but its content has changed since the snapshot the resolution was built from — e.g., the file was auto-formatted, partially edited, regenerated by a build/watch tool, or touched by a git hook while the (multi-minute) Copilot round trip was in flight. In that case the check passes (both conditions are false → does not `continue`) and the stale, already-computed `resolvedContent` is written verbatim, clobbering whatever changed on disk without any diff-vs-current-state check or warning at write time.

The developer comment right above this exact code path explicitly acknowledges the class of bug ("Overwriting it with Copilot's stored content would silently clobber their work") but only defends against one instance of it (fully-resolved files), not the more general case of any content drift during the async window.

## Impact Explanation
- The corrupted value is the **final content written to a tracked, conflicted file and staged for commit** (`resolution.resolvedContent` written via `writeFile` + `git add`), the same class of "silent corruption of what the user commits" called out as in-scope impact.
- Because the write happens without re-diffing against the current on-disk file at write time, any legitimate change made to the file during the Copilot round trip (which can legitimately run past 60–120 seconds per the app's own instrumentation) is silently discarded and replaced by content generated from an older snapshot — with no error, warning, or additional confirmation.
- This is worse than a simple lost-edit bug because the write also stages the file (`git add`), so the corrupted/stale content can flow directly into the merge commit that the user believes reflects their (or Copilot's) latest, reviewed resolution.

## Likelihood Explanation
This requires a timing window between conflict-context capture and the user clicking "Continue Merge" during which the on-disk file content changes while still reporting as conflicted (e.g. an editor auto-save/format-on-save, a file watcher, or another tool touching the file mid-resolution). The app's own latency-bucket telemetry (15s/30s/60s/120s+) indicates this window is realistically long enough for such concurrent activity in normal developer workflows, especially on large/complex conflicts (which are also the conflicts most likely to be resolved via Copilot rather than by hand). It does not require elevated privileges, and the only "attacker" contribution needed is a repository whose merge produces conflicts large/complex enough to push resolution time into that window — no unusual or contrived user steps beyond a standard merge/rebase/cherry-pick with Copilot conflict resolution enabled.

## Recommendation
- Before writing `resolution.resolvedContent`, re-read the current on-disk file and compare it (or a hash of it) against the `rawContent` snapshot that the resolution was reassembled from; if they differ, treat the file as externally modified and skip/re-prompt instead of silently overwriting, extending the existing "already resolved" guard to also cover "changed since snapshot."
- Alternatively, re-run `reassembleResolvedFile` against a freshly-read file at apply time (immediately before `writeFile`) rather than relying on a cached reassembly computed right after the model response.
- Surface a clear conflict/merge-error to the user when a staleness mismatch is detected, rather than silently proceeding.

## Proof of Concept
1. Start a merge/rebase that produces one or more conflicted files large/complex enough that Copilot's resolution round trip is slow (the app's own telemetry buckets 15s/30s/60s/120s+ confirm this is an expected, non-contrived scenario).
2. While the Copilot resolution request is in flight (`copilotResolutionProgress` active in `MultiCommitOperationStepKind.ShowCopilotConflicts`), have any tool (editor auto-save/format-on-save, a git hook, a watch/build process) modify the still-conflicted file on disk, leaving conflict markers present but changing surrounding content.
3. Wait for the Copilot response; the app stores `copilotResolutions` computed from the pre-modification `rawContent` snapshot (`reassembleResolutions` in `copilot-conflict-resolution.ts:609-642`).
4. Click "Continue Merge," triggering `_applyCopilotConflictResolutions` (`app-store.ts:7169-7269`). Because `onDiskFile.status` is still `Conflicted` with unresolved markers, the staleness guard at lines 7241-7256 does not trigger, and the stale `resolution.resolvedContent` is written and staged over the user's/tool's in-flight changes with no warning.

**Uncertainty**: I could not fully verify within the available tooling whether any additional freshness/hash check exists elsewhere in the Copilot pipeline (e.g., inside `copilot-store.ts`) that might mitigate this before `_applyCopilotConflictResolutions` is invoked; the grep for validation/schema logic in that file returned limited results and I was not able to read its full contents. If such a check exists there, it would reduce or eliminate this finding's likelihood.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
