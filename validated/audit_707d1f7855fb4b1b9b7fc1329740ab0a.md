### Title
Global, endpoint/repo-unscoped `cachedRepoRulesets` cache lets a malicious repository poison branch-rule bypass state for other repositories - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore` maintains a single app-wide cache of GitHub repo rulesets, `cachedRepoRulesets: ReadonlyMap<number, IAPIRepoRuleset>`, keyed **only by the numeric ruleset `id`** returned by the GitHub API, with no scoping by endpoint, owner, or repository. [1](#0-0) 
When `refreshBranchProtectionState` fetches a repository's rulesets, it skips re-fetching any ruleset id that's already present in this cache, and then uses whatever object is stored under that id to compute rule enforcement (including whether the current user can silently bypass the rule): [2](#0-1) 

### Finding Description
`parseRepoRules` looks up each rule's `ruleset_id` in the shared `rulesets` map to decide whether the rule is enforced or bypassable, using `ruleset.current_user_can_bypass === 'always'`: [3](#0-2) 

Because `cachedRepoRulesets` is a single process-wide map keyed by bare numeric id, and the "don't re-query" check in `refreshBranchProtectionState` only tests `this.cachedRepoRulesets.has(id)` — not `(endpoint, owner, name, id)` — any repository whose rulesets the user causes Desktop to load can write into the same numeric id-space that other, unrelated repositories (including different GitHub.com repos or a different GitHub Enterprise endpoint entirely) will later read from. Ruleset ids are only guaranteed unique per GitHub instance, not globally, and an attacker-controlled GitHub Enterprise Server endpoint (a "GitHub API object"/remote/proxy response the attacker fully controls) can return arbitrary `id` values in `fetchAllRepoRulesets`/`fetchRepoRuleset` responses. If the attacker's repo is opened/refreshed by the victim before (or racing) a legitimate repo whose real ruleset happens to reuse the same numeric id, the legitimate repo's `parseRepoRules` call will silently consume the attacker's poisoned `IAPIRepoRuleset` object (e.g. with `current_user_can_bypass: 'always'`) instead of fetching the real one, because the id is already "cached". [4](#0-3) 

This is the same root-cause pattern as the source report: a value that should be scoped/refreshed per-context (there, `lastEthprice` per price update; here, a ruleset per endpoint+repo) is instead treated as a durable, unscoped global, letting an attacker who controls one input channel (a git remote's API responses) corrupt a downstream security decision made for an entirely different, trusted context.

### Impact Explanation
`currentRepoRulesInfo` computed from the poisoned ruleset drives `RepoRulesInfo` fields (`basicCommitWarning`, `creationRestricted`, `signedCommitsRequired`, `pullRequestRequired`, `commitMessagePatterns`, `branchNamePatterns`, etc.) which are surfaced in the commit UI (`commit-message.tsx`, `commit-message-dialog.tsx`) to warn the user before they commit/push against branch rules. Poisoning the cached bypass flag can suppress warnings the user should have seen (e.g., "signed commits required", "commit message must match pattern"), silently letting them commit/push content that violates the repository's actual push rules — matching the accepted impact class of "silent corruption of what the user commits or pushes." It does not grant code execution or credential theft, but it does invalidate a security control (repo rules/branch protection UI enforcement) using only a normal, expected attacker capability (control of one Git/GitHub API endpoint the victim connects to).

### Likelihood Explanation
Exploitation requires: (1) the victim adds/uses a repository hosted on an attacker-controlled endpoint (a malicious GHES instance or any repo whose rulesets response the attacker controls) that Desktop is made to fetch rulesets for, and (2) a numeric ruleset id collision with a ruleset id used by another repository the same Desktop instance also manages. Collisions are plausible for small/sequential ids on freshly-provisioned instances, and the cache persists for the process lifetime with no invalidation between different endpoints. This is a data/race condition rather than a trivial one-click exploit, so likelihood is moderate rather than high, but no local access, credentials, or social engineering beyond "add this GitHub Enterprise remote" is required, satisfying the "attacker controls a git remote/proxy response" precondition in the task.

### Recommendation
Key `cachedRepoRulesets` (and the has()-check before fetching) by a composite of `endpoint + owner + repo + rulesetId` instead of the bare numeric id, so rulesets from one endpoint/repository can never satisfy a cache lookup for another. Alternatively, scope the cache per `GitHubRepository.dbID` similar to how `protectionEnabledForBranchCache`/`branchProtectionSettingsFoundCache` are already keyed by `GitHubRepository` id in `repositories-store.ts`. [5](#0-4) 

### Proof of Concept
1. Victim adds a malicious repository hosted on an attacker-controlled GitHub Enterprise endpoint to Desktop; Desktop calls `refreshBranchProtectionState`, which calls `api.fetchAllRepoRulesets`/`fetchRepoRuleset` against the attacker's server. The attacker's server returns a ruleset object `{ id: 42, current_user_can_bypass: "always", ... }`. This gets stored via `_updateCachedRepoRulesets` into the shared `cachedRepoRulesets` map under key `42`.
2. Later (or concurrently), the victim works on a legitimate, trusted GitHub.com repository whose GitHub Enterprise/legitimate ruleset also happens to have `id: 42` (server-assigned, attacker cannot control it directly but ids are small/sequential on many instances, making collisions realistic across separately-provisioned orgs/instances).
3. In `refreshBranchProtectionState` for the trusted repo, `this.cachedRepoRulesets.has(42)` is `true`, so the real ruleset is never fetched from the trusted repo's real GitHub instance. [4](#0-3) 
4. `parseRepoRules` for the trusted repo's branch rules resolves `rule.ruleset_id === 42` to the attacker's poisoned object and treats the rule as bypassable (`current_user_can_bypass === 'always'`), suppressing the branch-rule warning/enforcement in the commit UI even though the real ruleset on the trusted repo does not permit bypass. [6](#0-5)
