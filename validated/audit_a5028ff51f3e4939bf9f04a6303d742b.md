### Title
Error acknowledgement returned after committed unescrow/mint duplicates value on receiving ERC20-conversion failure - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`x/erc20/keeper.OnRecvPacket` performs the ICS20-to-ERC20 auto-conversion step, but when it fails (e.g., `MintingEnabled` or `ConvertCoinNativeERC20` errors because the ERC20 contract backing a `IsNativeERC20()` pair is self-destructed, missing, or otherwise reverts), it converts the already-successful transfer acknowledgement into an error acknowledgement: [1](#0-0) 

This runs only after the underlying ICS20 transfer application has already executed and mutated bank state (unescrow/mint) on the receiving chain, since `x/erc20/ibc_middleware.go` calls the wrapped transfer app first and only short-circuits on its own failure: [2](#0-1) 

### Finding Description
The IBC middleware chain composes `im.Module.OnRecvPacket` (the standard ICS20 transfer app) with `im.keeper.OnRecvPacket` (the erc20 auto-conversion step), both operating on the *same* `ctx` object supplied by the IBC core channel keeper for that packet: [2](#0-1) 

The core IBC channel keeper (external dependency, not in this repo) commits whatever state was written to that `ctx` as long as a non-nil acknowledgement is returned — it does not distinguish between success/error acks for the purpose of deciding whether to persist state; only a `nil` (async) ack defers persistence. The design contract for IBC apps is that if a callback intends to return an error acknowledgement, it must not have already performed the token-transfer state mutation.

`x/erc20/keeper.OnRecvPacket` violates that contract for the `pair.IsNativeERC20()` branch: by the time this function runs, the transfer app has already unescrowed or minted the underlying bank coin into the recipient's account (this is a *real* value movement out of the chain's IBC escrow for a token whose canonical form is the destination-chain-native ERC20). If `MintingEnabled` or `ConvertCoinNativeERC20` subsequently fails, the function still returns `channeltypes.NewErrorAcknowledgement(err)`: [3](#0-2) 

That error acknowledgement gets relayed back to the counterparty chain, which — per standard ICS20 `OnAcknowledgementPacket` semantics — will refund/re-mint the tokens back to the original sender there, because from the counterparty chain's point of view the transfer failed. Meanwhile the receiving chain has already credited the recipient with the real (unescrowed) bank coin balance. The net effect is duplication of value across the two chains for a single transferred amount: the recipient chain has already paid out, and the source chain independently reimburses the sender.

This directly contradicts the documented intended behavior at the top of the ICS20 middleware wrapper and at `OnAcknowledgementPacket`/`OnTimeoutPacket`, which explicitly state that on conversion failure the user should simply keep the bank token (no error should propagate): [4](#0-3) [5](#0-4) 

Notably, `ConvertCoinToERC20FromPacket` (used by `OnAcknowledgementPacket`/`OnTimeoutPacket`) correctly implements this fallback pattern by swallowing the conversion error and returning `nil` instead of propagating failure: [6](#0-5) 

`OnRecvPacket`'s Case 2 (native ERC20) does not follow this same safe pattern, which is the asymmetry underpinning the bug. Test coverage in this repository already anticipates the "self-destructed contract" failure mode for the timeout path (`err - self-destructed contract` test case), confirming this is a realistic/expected state, but the equivalent scenario for `OnRecvPacket` is not verified to preserve conservation of value across chains.

### Impact Explanation
This falls under the allowed Critical impact of "unauthorized minting, burning, duplication ... of spendable user value ... across ... IBC escrows." A single IBC transfer of a returning native-ERC20-backed token can result in the recipient having spendable funds on the destination chain (from the unescrow that already occurred) while the source chain also refunds/reissues the same value to the original sender due to the erroneous error acknowledgement. This is a duplication of value, not merely a freeze, and directly undermines the 1:1 accounting invariant between escrowed value and ERC20/bank representations that the "Asset-representation path" pivot calls out.

### Likelihood Explanation
The trigger requires a token pair with `IsNativeERC20()` (the destination chain being the origin of the ERC20) and a state in which the backing ERC20 contract can no longer accept a mint call (self-destructed, or `MintingEnabled` failing for a reason such as bank `SendEnabled` toggling or blocked-address checks that can change between send and receive). Since the token's owner/deployer is generally not privileged with respect to this attack (an unprivileged holder of a native-ERC20-backed IBC voucher can trigger it simply by sending it back over IBC once the contract has died or params changed), and the repository's own tests demonstrate this failure mode is expected/reachable, likelihood is realistic rather than purely theoretical. It does require a specific pre-condition (dead/failing ERC20 contract for that pair) to exist at receive time, which is a moderate but attacker-achievable precondition if the attacker controls or can render inoperable the ERC20 contract for their own pair.

### Recommendation
Make `OnRecvPacket`'s native-ERC20 conversion failure path consistent with `ConvertCoinToERC20FromPacket`'s safe fallback design: on `MintingEnabled`/`ConvertCoinNativeERC20` failure, do not return an error acknowledgement (which would cause the counterparty to refund/duplicate value); instead, emit the failure event and return the original success `ack`, leaving the recipient with the bank-coin representation only (matching the documented "user will receive the bank token instead" contract). Alternatively, wrap the whole `OnRecvPacket` composition in `ctx.CacheContext()` in `x/erc20/ibc_middleware.go` and only commit if the erc20 conversion step also succeeds or is skipped, and return the original ack in the fallback branch.

### Proof of Concept
1. Register a token pair for a native ERC20 (`OWNER_MODULE` or externally owned) via governance; the pair is `IsNativeERC20()` and `Enabled`.
2. Convert some ERC20 to its Cosmos coin representation and send it via ICS20 to a counterparty chain (escrowing/burning appropriately on this chain).
3. Self-destruct (or otherwise disable, e.g., pause via bank `SendEnabled=false`/blocked address toggling, though self-destruct is the clean case) the ERC20 contract backing the pair (as demonstrated in `tests/integration/x/erc20/test_ibc_callback.go`'s "err - self-destructed contract" pattern via `EVMKeeper.DeleteAccount`).
4. Send the coin back over IBC from the counterparty chain to this chain.
5. `im.Module.OnRecvPacket` (transfer app) succeeds and unescrows/mints the bank coin into the recipient's balance on this chain, returning a success ack.
6. `x/erc20/keeper.OnRecvPacket` Case 2 is hit; `ConvertCoinNativeERC20` fails because the contract is dead; the function returns `channeltypes.NewErrorAcknowledgement(err)`.
7. This error ack is relayed back to the counterparty chain; its `OnAcknowledgementPacket` handling refunds/re-mints the original sender's tokens there.
8. Result: the recipient on this chain already holds the unescrowed bank coin (step 5), and the sender on the counterparty chain is separately refunded (step 7) — the same value now exists in two places.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
