### Title
Recursive clone explicitly disables Git's built-in submodule clone-protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), reintroducing CVE-2024-32002-style RCE via malicious repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
Just like the OpenDollar `AccountingEngine` bug where a debt-sufficiency guard was present in the code but neutralized by ordering/placement so the auction could proceed on non-existent debt, GitHub Desktop's `clone()` function contains a guard-defeating line: it unconditionally forces `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` on every `git clone --recursive` invocation, which disables the safety check that upstream Git added specifically to prevent malicious nested submodules from writing files (including hooks) outside their intended working directory during a recursive clone.

### Finding Description
`clone()` builds the execution environment for every clone request, including the mandatory backstop against sensitive destination paths: [1](#0-0) 

Immediately after the (unrelated) sensitive-path check, the function sets: [2](#0-1) 

and then always passes `--recursive` to `git clone`: [3](#0-2) 

`GIT_CLONE_PROTECTION_ACTIVE` is the internal flag Git's recursive-clone code path relies on to detect and reject clone operations where a submodule's on-disk layout (via symlinks, case-folding collisions on case-insensitive filesystems, or crafted `.git` files) would let a nested submodule checkout escape its own working directory and overwrite files elsewhere in the repository tree — including hook scripts that Git later executes automatically (this is the class of bug fixed upstream for CVE-2024-32002 / the git.git recursive-clone hardening). By forcing this flag to `'false'` on every Desktop-initiated clone, Desktop deliberately disables that protection instead of letting Git enforce it, so any repository containing a maliciously crafted submodule can bypass the safety net that would otherwise abort the clone.

This mirrors the reported bug class exactly: a security-relevant check exists in the underlying system (Git), but the calling code (Desktop, analogous to `AccountingEngine`'s misplaced `_settleDebt`/`_unqueuedUnauctionedDebt` check) actively neutralizes it before the dangerous operation (`git clone --recursive`) runs, so the operation proceeds using stale/incorrect protection state.

### Impact Explanation
An attacker who controls a public or shared repository (the exact threat model called out as valid: "attacker controls a cloned/fetched repository") can craft a submodule that, when recursively cloned by any Desktop user via "Clone repository," writes files outside the submodule's directory — for example into `.git/hooks` of the containing repository or another submodule — because the guard that would normally reject this layout has been turned off by Desktop itself. Since Git executes hook scripts automatically on subsequent operations (checkout, commit, merge, etc.), this can lead to arbitrary code execution on the victim's machine the moment they interact with the freshly cloned repository, i.e. file write outside the intended repo tree and code execution, both explicitly listed as valid impacts.

### Likelihood Explanation
Every single clone performed through Desktop's UI goes through this `clone()` function with `--recursive` and the disabled protection, so no unusual user action beyond "Clone repository → paste malicious URL/click Open in Desktop" is required — this satisfies the "unprivileged... repository the attacker controls... clicked link" threat model and needs no local access, admin rights, or pre-existing malware.

### Recommendation
Remove the line that forces `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`, or explicitly set it to `'true'` (or simply do not override it) so that Git's own recursive-clone submodule-safety check remains active. If this override was added to work around a compatibility issue with certain repositories, that trade-off needs to be re-evaluated, since it globally disables a security control for all clones instead of only the specific problematic case.

### Proof of Concept
1. Prepare a malicious repository containing a submodule whose on-disk layout would normally be rejected by Git's recursive-clone protection (e.g. a submodule directory structured to collide with `.git`/hook paths through case-folding or a crafted `.gitmodules`/`gitlink` layout consistent with the CVE-2024-32002 pattern).
2. Host the outer repository publicly (e.g. on GitHub) and get a victim to clone it with GitHub Desktop via "File → Clone Repository" or an `x-github-client://openRepo` deep link.
3. Desktop invokes `clone()` in `app/src/lib/git/clone.ts`, which sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and runs `git clone --recursive -- <url> <path>` [4](#0-3) .
4. Because the protection flag is forced off, Git performs the recursive submodule checkout without rejecting the malicious layout, allowing the crafted submodule content (e.g. a hook script) to be written outside its intended submodule directory.
5. The next Git operation that triggers hook execution (checkout, commit, etc.) runs the attacker-controlled script, achieving code execution on the victim's machine.

Note: I could not execute this against a live Git binary from this environment to confirm the exact upstream CVE mechanics reproduce bit-for-bit; the finding is based on static analysis showing Desktop explicitly and unconditionally disables a named Git clone-protection flag on every recursive clone, which is a security-relevant code pattern regardless of the exact underlying CVE it corresponds to.

```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
```
