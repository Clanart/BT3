## Title
Silent origin-remote hijack via unauthenticated `clone_url` from GitHub API response - (`app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
When Desktop periodically refreshes the GitHub metadata for a repository, it takes the `clone_url` field of the API response and, if certain loose conditions are met, silently rewrites the local repository's `origin` remote with `git remote set-url` — without ever verifying that the new URL still points at the same host/owner that the user originally trusted. A malicious or MITM'd API response (or a compromised/attacker-controlled GitHub Enterprise endpoint) can therefore redirect the user's push/fetch target to an attacker-controlled server with no user confirmation, dialog, or warning.

## Finding Description
`updateRemoteUrl` is invoked from `AppStore.repositoryWithRefreshedGitHubRepository`, which is called whenever Desktop refetches a repository's GitHub metadata (e.g. background repository refresh, account change, fetch/push flows via `withRefreshedGitHubRepository`): [1](#0-0) 

The update function itself only performs three checks before overwriting the remote URL: [2](#0-1) 

- `protocolsMatch` only verifies the URL *scheme* (`https:` vs `https:`) is unchanged — it does not check hostname.
- `remoteUrlUnchanged` only verifies the user hasn't manually edited the remote away from the last-known `cloneURL` — it says nothing about whether the *new* `clone_url` is safe.
- `urlsMatch` (via `urlMatchesRemote`) is used purely to decide whether an update is even necessary, not as a safety gate.

None of these checks constrain the new `clone_url` to the same host as the account's trusted API `endpoint`, nor to the same host as the previous remote. If the API response body for `GET /repos/:owner/:name` (the same request performed in `repositoryWithRefreshedGitHubRepository` via `api.fetchRepository`) reports an arbitrary `clone_url` such as `https://evil.example/owner/repo.git`, Desktop calls: [3](#0-2) 

which silently executes `git remote set-url origin https://evil.example/owner/repo.git` on the user's real, working repository — with no dialog, confirmation, or logging visible to the user.

This directly matches the "wrong address" bug class from the seed report (trusting an externally-supplied address without validating it against the expected value) — here the "oracle" is the GitHub API repository object, and the "wrong address" is the git remote URL that Desktop trusts and applies automatically.

## Impact Explanation
Once the origin remote is silently repointed:
- Every subsequent `git fetch`/`git pull` performed by Desktop (including background fetches) pulls objects and refs from the attacker's server, allowing history/commit content to be silently substituted — corrupting what the user believes they are viewing, merging, or building on.
- Every subsequent `git push` sends the user's new commits (and, depending on credential-helper configuration, HTTPS Basic Auth credentials/tokens) to the attacker-controlled host instead of GitHub — satisfying both "silent corruption of what the user commits or pushes" and potential "credential/token exfiltration" from the accepted impact list.
- The change persists in the repository's `.git/config` beyond the single session, and there is no UI surface informing the user that their remote changed.

## Likelihood Explanation
The trigger point is a GitHub API repository object under attacker influence — one of the explicitly in-scope primitives ("attacker controls ... a GitHub API object ... or a git remote/proxy response"). This can occur via:
- A compromised or malicious GitHub Enterprise Server instance the user has added an account for (explicitly supported/trusted by Desktop's multi-endpoint model), or
- A network-level proxy/MITM condition on the `fetchRepository` API call.

No local access, admin rights, or unnatural user interaction is required — the refresh happens automatically as part of normal repository/fetch/push workflows via `withRefreshedGitHubRepository` and `repositoryWithRefreshedGitHubRepository`.

## Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, additionally verify that the new `clone_url`'s hostname matches the hostname of the account's trusted `endpoint` (or the existing remote's hostname) — reject silently-changed hosts, or (at minimum) require explicit user confirmation via a dialog before rewriting an existing remote URL to a different host.

## Proof of Concept
1. Add a GitHub Enterprise account in Desktop pointing at `https://github.mycompany.com`, and clone a repository from it (`origin` = `https://github.mycompany.com/org/repo.git`).
2. Compromise/control that GHES instance's (or a MITM proxy in front of it) response to `GET /api/v3/repos/org/repo`.
3. Have the compromised endpoint return a `clone_url` of `https://attacker.example/org/repo.git` (same `https` scheme, so `protocolsMatch` passes; and the previous remote is unmodified by the user, so `remoteUrlUnchanged` passes).
4. Trigger any flow that calls `repositoryWithRefreshedGitHubRepository` (background repository refresh, account switch, or push/fetch via `withRefreshedGitHubRepository`).
5. Observe that Desktop silently runs `git remote set-url origin https://attacker.example/org/repo.git` with no user prompt; subsequent pushes/fetches now target the attacker's server.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
