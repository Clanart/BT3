## Title
Unbounded Ownership-Chain Traversal in `object::root_owner()` Can Desynchronize Object Code-Ownership Gating from `owns()`'s Bounded Check - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`root_owner()` walks the object ownership chain (`obj_owner -> owner -> owner -> ...`) with **no depth limit**, while the sibling function `owns()` in the same module explicitly bounds the same kind of walk with `MAXIMUM_OBJECT_NESTING` and aborts with `EMAXIMUM_NESTING` if exceeded. [1](#0-0) [2](#0-1) 

`root_owner()` is used as the security anchor for the new lazy module self-init / code-ownership gating mechanism: `code::publish_package` records `root_owner()` as the authorized owner for object-hosted modules, and `init::assert_may_self_initialize` re-derives `root_owner()` at self-init time and compares it to the recorded value to detect object transfers. [3](#0-2) [4](#0-3) 

### Finding Description
This is the same bug class as the external report: a chain-traversal used for a security decision that is inconsistent with a bounded sibling traversal elsewhere in the same module. In the external report, `getHigherLevelParents()` capped hops at 64 while the intended semantics required unlimited traversal, letting an attacker construct a chain that defeats the cap. Here the inverse defect exists: `owns()` bounds nested-object ownership walks at `MAXIMUM_OBJECT_NESTING` to guard against unbounded/cyclic traversal, but `root_owner()` — used for the *far more security-sensitive* purpose of gating module self-initialization signer minting — performs the identical style of walk with **no bound at all**:

```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [1](#0-0) 

This inconsistency between two traversal functions over the *same* data structure (object ownership chain) inside the same module is exactly the kind of "hop-limit mismatch" the external report calls out, except here the missing bound is on the function relied upon for a `code-safety` decision (whether a module may mint its own signer via `init::internal_maybe_initialize`), rather than the bounded one.

Because nesting depth of objects is attacker-controllable (an account can create arbitrarily deep chains of nested objects via `object::create_object` calls before transferring code-object ownership under them), an attacker can, in principle, construct a pathologically deep ownership chain terminating at (or rooted under) a code object. Every call to `root_owner()` on that chain — both at publish time (`code::publish_package`) and every time `init::internal_maybe_initialize` is invoked in the deployed module — walks the full unbounded chain, unlike `owns()` which would abort early via `EMAXIMUM_NESTING`.

### Impact Explanation
I was unable to fully verify, within the available tool budget, whether Aptos's object-ownership model prevents cycles (e.g., whether `transfer()` rejects assigning an object as owner of one of its own ancestors) or whether there is a maximum object *creation* nesting depth enforced elsewhere (e.g., in `object::create_object`) that would already bound `root_owner()`'s work indirectly. If no such upstream bound exists, the practical impact is:
- A gas-metered but potentially very long loop inside a critical security check (`assert_may_self_initialize`), which is a "verifier/native validation ... reaches protected state mutation" style issue per the Publish Impact Gate, since it directly gates whether a code-object's module may mint a signer for itself.
- If a true ownership *cycle* could ever be constructed (which I could not confirm is prevented), `root_owner()` would loop forever within a single gas-metered transaction, which would deterministically abort on out-of-gas rather than hang the node — this would reduce the practical severity to a self-inflicted DoS/gas-griefing on the caller rather than a chain-wide issue.

Given I could not confirm an actual unprivileged path to construct a chain long enough to matter (whether object nesting is capped elsewhere, and whether the theoretical DoS translates into an actual ownership-check bypass or state corruption), I cannot substantiate a "code replacement" or "unauthorized code-object ownership change" outcome — only a code-safety **inconsistency** between the two traversal functions.

### Likelihood Explanation
Low-to-Medium. Constructing a deep nested-object chain requires many prior transactions (each `object::create_object` call), all paid for and rate-limited by ordinary transaction gas costs, so there is no way to make this cheap in a single transaction. Whether it is exploitable at all further depends on facts I could not verify (object nesting caps, cycle prevention in `transfer`), so this remains a **local code inconsistency finding with unconfirmed exploitability**, not a proven bypass.

### Recommendation
- Apply the same `MAXIMUM_OBJECT_NESTING` bound (and `EMAXIMUM_NESTING` abort) used in `owns()` to `root_owner()`, since it is used in code-ownership/self-init security decisions in `init.move` and `code.move`.
- Audit whether `object::transfer` prevents an object from being made an ancestor of itself (cycle prevention); if not, add that check, since an ownership cycle would make `root_owner()` (and any future callers of a similarly unbounded pattern) loop until gas exhaustion.

### Proof of Concept
Not constructed — I was unable to confirm within available searches whether (a) object ownership cycles are prevented by `object::transfer`, and (b) whether nested-object creation depth is bounded elsewhere in `object.move`. Both are prerequisites to demonstrating a concrete exploit path (versus a purely theoretical inconsistency). A background Devin session with full repository/build access would be needed to inspect `object::transfer`'s implementation in full and to write an end-to-end Move test analogous to `init_module_api.rs`'s existing `init_maybe_initialize_object_owner_changed_aborts` test, but with a very deep nested-object chain, to empirically measure whether `root_owner()`'s unbounded loop causes disproportionate gas cost or any exploitable state relative to the bounded `owns()` check.

    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// gated: an object must still have the transitive root owner recorded for this module at
