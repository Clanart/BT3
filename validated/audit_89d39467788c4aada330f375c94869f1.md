### Title
Unbounded, unmetered ECDSA signature-recovery loop over attacker-controlled `TxSignatures` list before gas/count checks - ([File: blockchain/types/tx_signatures.go])

### Summary
Kaia transactions of "Kaia" (non-Ethereum) type carry a `TxSignatures` slice — one `{V,R,S}` tuple per signing key of a multisig account. When a transaction arrives (mempool admission or block/state-transition processing), the node recovers a public key for **every** signature tuple in the list via expensive `ecrecover` operations, before any bound on the list length or gas accounting for that work is enforced. This mirrors the reported bug class: unmetered linear iteration over an unbounded, attacker-controlled list before the metering/allow-list check that is supposed to bound it.

### Finding Description
`TxSignatures.RecoverPubkey` iterates over the full raw signature slice and calls `ecrecover` for each entry: [1](#0-0) 

This is invoked from `modernSigner.SenderPubkey` (and `RecoverTxPubkeys`) which is used to recover the sender/fee-payer of a transaction: [2](#0-1) 

Critically, in `Transaction.ValidateSender` — the function called by the tx pool during admission — `SenderPubkey` (which does all the `ecrecover` work) is executed **first**, and only afterward is the per-key gas cost (`SigValidationGas`) computed and later compared against `tx.Gas()`: [3](#0-2) 

The gas check itself happens even later in `TxPool.validateTx`, well after the expensive recovery loop has already executed for every signature present in the RLP-decoded transaction: [4](#0-3) 

The only length cap on multisig signature counts (`MaxNumKeysForMultiSig = 10`) is enforced at transaction *construction* time via `NewTxSignaturesWithValues`, and separately inside `AccountKeyWeightedMultiSig.SigValidationGas`/`CheckInstallable` against the *account's configured key count* — not against the number of raw signatures present in an arbitrary, attacker-crafted RLP-encoded transaction submitted to a public node: [5](#0-4) [6](#0-5) 

`AccountKeyWeightedMultiSig.Validate` does check `len(recoveredKeys) > len(a.Keys)` — but only *after* every signature has already been recovered (i.e., after the costly work is done, and only for post-Istanbul rules): [7](#0-6) 

### Impact Explanation
An unprivileged transaction sender can craft a single RLP-encoded transaction (or spam many such transactions) containing an arbitrarily large `TxSignatures` list (only bounded by the overall transaction size limit `MaxTxDataSize`, not by any signature-count-specific cap checked before recovery). Every node that receives this transaction — during mempool admission (`TxPool.validateTx` → `tx.ValidateSender`), transaction re-validation on reorgs, or block/state-transition processing that must recover the sender — is forced to perform many `ecrecover` (secp256k1 signature recovery) operations, each of which is computationally significant, before the transaction is ultimately rejected for insufficient gas or excess signature count. Because the account's `AccountKeyWeightedMultiSig` limit (`MaxNumKeysForMultiSig=10`) bounds the number of *valid* keys but the check against submitted signature count happens only after the whole recovery loop, an attacker does not need a real multisig account with many keys — arbitrary garbage signature tuples still get `ecrecover`'d. Broadcasting many such transactions in parallel or via public RPC (`eth_sendRawTransaction`) can impose disproportionate CPU cost on every full node validating the mempool and processing blocks, degrading node performance broadly — the same "unmetered iteration over an unbounded, attacker-supplied list" pattern described in the report, applied to signature recovery instead of restakable-denom iteration.

### Likelihood Explanation
Likelihood is elevated relative to the original report because there is no governance-configurable "restakable denom allow-list" analog protecting this path by default — this code path is always reachable by any unprivileged sender submitting a transaction to a public node, with no special configuration required to trigger it. The primary mitigating factor is the overall transaction size cap (`MaxTxDataSize`), which bounds how many signature tuples can be packed into one transaction, and the fact that most nodes will eventually reject the transaction for insufficient gas — but only after paying the CPU cost of the recovery loop.

### Recommendation
1. Enforce a maximum number of raw signatures (e.g., `MaxNumKeysForMultiSig`) on the `TxSignatures`/`AuthList`-like fields immediately upon RLP decode or as the very first check in `ValidateSender`/`ValidateFeePayer`, before any `ecrecover` calls are made.
2. Alternatively/additionally, charge (or pre-check against `tx.Gas()`) the worst-case signature-validation gas cost using `len(recoveredSignatures)` *before* performing the recovery loop, rejecting early if `tx.Gas()` cannot possibly cover it.

### Proof of Concept
1. Construct a Kaia-typed transaction (e.g., `TxTypeValueTransfer`) targeting any account.
2. Populate its `TxSignatures` field with hundreds or thousands of syntactically valid but semantically bogus `{V,R,S}` tuples (bypassing the `NewTxSignaturesWithValues` cap by constructing/RLP-encoding the transaction directly rather than through that helper).
3. Submit the transaction via `eth_sendRawTransaction` / p2p tx broadcast to a Kaia node.
4. Observe that `TxPool.validateTx` → `tx.ValidateSender` → `SenderPubkey` → `RecoverTxPubkeys` performs one `ecrecover` per signature tuple before the transaction is ultimately rejected (for insufficient gas or excessive signature count), consuming CPU proportional to the attacker-chosen list size on every node that processes the broadcast transaction.

*Note: I was unable to directly confirm within the indexed code whether the RLP-decoding path (`rlp.DecodeBytes` into `Transaction`) enforces any independent cap on the number of `TxSignatures` entries before this code runs; this should be verified in a live/full-repo session, as it affects the exact maximum achievable amplification.*

func NewTxSignaturesWithValues(signer Signer, tx *Transaction, txhash common.Hash, prv []*ecdsa.PrivateKey) (TxSignatures, error) {
	if len(prv) == 0 {
		return nil, kerrors.ErrEmptySlice
	}
	if uint64(len(prv)) > accountkey.MaxNumKeysForMultiSig {
		return nil, kerrors.ErrMaxKeysExceed
	}
	txsigs := make(TxSignatures, len(prv))

	for i, p := range prv {
		t, err := NewTxSignatureWithValues(signer, tx, txhash, p)
		if err != nil {
			return nil, err
		}
		txsigs[i] = t
	}

	return txsigs, nil
}

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil

func (s modernSigner) SenderPubkey(tx *Transaction) ([]*ecdsa.PublicKey, error) {
	// Check if this transaction type is supported
	if !s.IsSupported(tx) {
		return nil, ErrTxTypeNotSupported
	}

	// Legacy transactions are handled by the legacy signer
	if !tx.Type().IsEthTypedTransaction() {
		return s.legacy.SenderPubkey(tx)
	}

	// Validate chain ID
	if tx.ChainId().Cmp(s.chainId) != 0 {
		return nil, ErrInvalidChainId
	}

	// All modern transaction types use the same recovery mechanism
	return RecoverTxPubkeys(s.Hash(tx), tx.data.RawSignatureValues(), true, func(v *big.Int) *big.Int {
		// Modern txs use 0 and 1 as recovery id, add 27 to become equivalent to unprotected Homestead signatures.
		V := new(big.Int).Add(v, big.NewInt(27))
		return V
	})
}

func (tx *Transaction) ValidateSender(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	if tx.IsEthereumTransaction() {
		addr, err := Sender(signer, tx)
		// Legacy transaction cannot be executed unless the account has a legacy key.
		if p.GetKey(addr).Type().IsLegacyAccountKey() == false {
			return 0, kerrors.ErrLegacyTransactionMustBeWithLegacyKey
		}
		tx.mu.Lock()
		if tx.validatedSender == (common.Address{}) {
			tx.validatedSender = addr
			tx.validatedFeePayer = addr
		}
		tx.mu.Unlock()
		return 0, err
	}

	pubkey, err := SenderPubkey(signer, tx)
	if err != nil {
		return 0, err
	}
	txfrom, ok := tx.data.(TxInternalDataFrom)
	if !ok {
		return 0, errNotTxInternalDataFrom
	}
	from := txfrom.GetFrom()
	accKey := p.GetKey(from)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, GetRoleTypeForValidation(tx.Type()), len(pubkey))
	if err != nil {
		return 0, err
	}

	if err := accountkey.ValidateAccountKey(currentBlockNumber, from, accKey, pubkey, GetRoleTypeForValidation(tx.Type())); err != nil {
		return 0, ErrInvalidAccountKey
	}

	tx.mu.Lock()
	if tx.validatedSender == (common.Address{}) {
		tx.validatedSender = from
		tx.validatedFeePayer = from
	}
	tx.mu.Unlock()

	return gasKey, nil
}

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
