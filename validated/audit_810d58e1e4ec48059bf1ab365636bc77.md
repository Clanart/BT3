I found something worth examining closely: the `contracts/src/CW721ERC721Pointer.sol` `transferFrom` function only checks `from == ownerOf(tokenId)` but never verifies the caller (`msg.sender`) is the owner or an approved spender/operator — unlike the reference `ERC721.sol` which enforces `_isApprovedOrOwner`. Let me verify this precisely and check if `approve`/`setApprovalForAll` have similar gaps.## Title
CW721 ERC721 Pointer's `transferFrom` performs no caller-authorization check — any address can transfer any NFT it does not own or control - ([File: contracts/src/CW721ERC721Pointer.sol])

### Summary
`CW721ERC721Pointer.sol` is the standard EVM-facing ERC721 pointer contract that Sei deploys for every CW721 collection to let EVM users/contracts interact with a CosmWasm NFT contract through the ERC721 interface. Its `transferFrom` override only checks that the `from` argument is the current owner of the token; it never checks that `msg.sender` is the owner, an approved spender, or an approved operator, which is the exact analog of CVE‑2018‑1000141's incorrect-access-control pattern: a caller-identity/authorization check the original code relies on the framework (or, here, the base `ERC721`) to enforce is missing in the pointer's override.

### Finding Description
The base OpenZeppelin-style `ERC721` reference implementation used elsewhere in this repo (e.g. `contracts/src/ERC721.sol`) enforces authorization on transfer: [1](#0-0) 
which requires `_isApprovedOrOwner(from, msg.sender, id)`.

`CW721ERC721Pointer.sol`, however, overrides `transferFrom` and drops this check entirely: [2](#0-1) 

The only validation performed is `require(from == ownerOf(tokenId), ...)` — i.e., that the token really belongs to `from`. There is no `require(msg.sender == from || isApprovedForAll(from, msg.sender) || getApproved(tokenId) == msg.sender)` anywhere in this function or in `_execute`. The transfer request is then relayed via `delegatecall` to the `wasmd` precompile's `execute` method: [3](#0-2) 

Because the pointer contract is itself the CW721 contract's "admin/owner" from the CosmWasm contract's perspective when called via delegatecall — the wasmd precompile authorizes execution based on `caller == callingContract` (the pointer) via the delegatecall/pointer-identity check in `precompiles/wasmd/wasmd.go` (`ctx.EVMPrecompileCalledFromDelegateCall()` branch validates that the *pointer* is registered for the CW721 address, not that the original `msg.sender` is authorized to move that specific token): [4](#0-3) 

Consequently the CosmWasm `transfer_nft` message is submitted with the pointer's own delegated sender-derivation, and the CW721 contract sees the `transfer_nft` message coming from a sender the pointer resolved — but the Solidity layer that was supposed to gate "who is allowed to invoke transferFrom for this token" (equivalent to `ajaxdiscussion.php`'s missing per-discussion access check in the CVE) is missing. Any EVM caller can call `pointer.transferFrom(victimOwner, attacker, tokenId)` for a token they neither own nor were approved for, as long as `from` is correctly the token's current owner.

This mirrors CVE-2018-1000141 precisely in bug class: a state-changing action (moving/altering data — here, NFT ownership; there, discussion content) is exposed without validating that the calling identity possesses the authorization that the underlying data model requires.

### Impact Explanation
This is an unauthorized-transfer vulnerability via a CW↔EVM pointer contract, one of the explicitly in-scope reachable surfaces. Any unprivileged EVM caller (EOA or contract) could steal any NFT pointed to by a `CW721ERC721Pointer` instance by calling `transferFrom(victim, attacker, tokenId)` without any approval, resulting in direct fund/asset loss for NFT holders across every CW721 collection that has an ERC721 pointer deployed — a systemic, high-severity unauthorized-transfer bug.

### Likelihood Explanation
High likelihood if reachable as described: exploitation requires no privileges, no timing, and no race condition — a single unauthenticated `eth_call`/transaction naming any existing pointer, valid token id, and its current owner is sufficient. The precondition is simply that a CW721↔ERC721 pointer exists for the target collection, which is a normal, permissionless, publicly available and encouraged workflow (`addCW721Pointer` in the pointer precompile).

### Recommendation
Add an authorization check identical to the base `ERC721.transferFrom` (or query CW721's own approval state) before relaying `transfer_nft`: require `msg.sender == from || isApprovedForAll(from, msg.sender) || getApproved(tokenId) == msg.sender`. Since `getApproved`/`isApprovedForAll` here proxy to CW721 state via `WasmdPrecompile.query`, the check should query current CW721 approvals (not any local mapping, since this contract holds no local approval state) before executing `transfer_nft`. Apply the equivalent check to `safeTransferFrom` if it's not fully delegated to `transferFrom` internally, and audit `CW1155ERC1155Pointer.sol` for the same missing-authorization pattern.

### Proof of Concept
1. Deploy/obtain the address of a `CW721ERC721Pointer` for an existing CW721 NFT collection (e.g., via `addCW721Pointer` on the `pointer` precompile), where `tokenId=1` is owned by `victim` and `attacker` has never been approved.
2. As `attacker` (any EOA, no prior approval), call:
   `pointer.transferFrom(victim, attacker, 1)`
3. Because `transferFrom` only checks `from == ownerOf(tokenId)` and never checks that `msg.sender` (`attacker`) is `victim`, an approved spender, or an approved operator, the call succeeds and relays `transfer_nft` to the CW721 contract via the wasmd precompile delegatecall.
4. `ownerOf(1)` afterward returns `attacker`, confirming the unauthorized transfer.

**Note on verification confidence:** I was unable to directly inspect the exact sender-resolution logic used by the wasmd precompile's `execute`/delegatecall path to conclusively confirm what Sei address the CosmWasm `transfer_nft` message is submitted as when invoked via `delegatecall` from the pointer (i.e., whether it resolves to the pointer's own associated Sei address or somehow to `msg.sender`'s). The core finding — that the Solidity `transferFrom` override itself performs no `msg.sender` authorization check, unlike the project's own reference `ERC721.sol` — is directly confirmed by the source. If the underlying CW721 contract still separately enforces its own `transfer_nft` sender check against its stored approvals when called by the pointer's Sei address (which acts on behalf of no specific EVM caller once inside CosmWasm), this could reduce or negate exploitability; I recommend a Devin session with contract-execution tracing/integration tests to confirm end-to-end exploitability before treating this as a confirmed live vulnerability.
