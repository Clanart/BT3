### Title
Fee-amortization underflow in `Scheduler::created_output` silently drops all queued child payments, stranding funds — (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
The external finding concerns a missing minimum-amount check that lets economically unviable positions strand value with the protocol. The analogous Serai bug lives in the UTXO scheduler's fee-amortization path: when a branch output is created on-chain for less than the originally expected amount (the normal case, since fees are subtracted from the branch payment), `Scheduler::created_output` computes `actual - expected` in `u64`, which underflows. The wrapped-around value causes an early return that permanently drops every child payment queued behind that branch, while the branch UTXO itself is re-added to the scheduler as a generic spendable output — value stays locked in the multisig while the withdrawals it was meant to fund are never paid.

### Finding Description
`Network::prepare_send` amortizes the transaction fee across payments. For payments destined to the multisig's own branch address, it records `PostFeeBranch { expected: initial_amount, actual: reduced_amount }`, where `initial_amount` is the pre-fee payment sum and `actual` is strictly less once fees are subtracted (processor/src/networks/mod.rs:504-517).

Later, `Scheduler::created_output` is invoked with those `expected`/`actual` values:

```rust
// processor/src/multisigs/scheduler/utxo.rs:480-489
let Some(actual) = actual else { return };
// Amortize the fee amongst all payments underneath this branch
let mut to_amortize = actual - expected;   // actual < expected -> underflow
if payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>() < to_amortize {
  return;                                  // drops all child payments
}
```

Since `actual <= expected` whenever a fee was charged, `actual - expected` either:
- panics on overflow-checked (debug) builds — a liveness failure of the processor, or
- wraps to a near-`u64::MAX` value in release builds, making `sum(payments) < to_amortize` always true, so the function returns before pushing the recovered payments into `self.plans`.

The queued plan entry for `expected` was already popped at lines 471-478, so the child payments are discarded with no record. When the branch UTXO is later scanned, `add_outputs` finds no `self.plans` entry keyed by its amount and falls through to `self.utxos.push(utxo)` (utxo.rs:276-296), so the coins remain spendable by the multisig but are no longer earmarked for the withdrawals they funded.

Branch creation is triggered purely by payment count: `execute` spills payments into a branch plan whenever `payments.len() > max` (utxo.rs:234-255), with `MAX_OUTPUTS = 520` for Bitcoin (processor/src/networks/bitcoin.rs:575-576). Queueing 521+ small withdrawals forces a branch output and thus hits this path deterministically on the next fee-bearing transaction.

### Impact Explanation
All payments under the affected branch are permanently dropped on the processor side while the corresponding balances were already debited. The branch output's funds become generic multisig UTXOs — the protocol retains the coins and the victims' payouts are silently lost. In debug/overflow-checked builds it is a persistent panic (scheduler stall). This mirrors the report's class: economically-small / fee-adjusted positions cause value to be stranded with the protocol because the minimum/fee accounting path is wrong.

### Likelihood Explanation
Any unprivileged party able to submit withdrawal/payment instructions can enqueue enough payments to force branch creation; no validator collusion or privileged access is needed — only sustained small payment volume exceeding `MAX_OUTPUTS` in a single scheduling round, which the dust/batching design actively encourages.

### Recommendation
Change `created_output` to compute `to_amortize = expected.saturating_sub(actual)` (the fee actually subtracted from the branch output), since `expected` is the pre-fee amount. Additionally treat `actual > expected` or `sum(payments) < to_amortize` as hard errors rather than silent drops, and assert in `prepare_send` that branch `actual` values are `<= expected`.

### Proof of Concept
1. A scheduler exists for Bitcoin key `K` with one large UTXO.
2. An unprivileged user causes `MAX_OUTPUTS + 1` payments (e.g., 521 payments of `N::DUST` = 10,000 sats each) to be queued; `execute` drains the last payment into `queued_plans[amount]` and emits a branch `Payment` to `N::branch_address(K)` (utxo.rs:234-255).
3. `prepare_send` amortizes the tx fee across payments; the branch payment is reduced, producing `PostFeeBranch { expected: A, actual: Some(A - f) }` for fee `f > 0` (networks/mod.rs:479-517).
4. On confirmation, `created_output(txn, expected: A, actual: Some(A - f))` runs `to_amortize = (A - f) - A`, which underflows (panic in debug; wraps in release), triggering the `return` at utxo.rs:487-489 — all 521 child payments are dropped.
5. The branch UTXO is later scanned and pushed into `self.utxos` with no associated plan; the protocol keeps the funds and the withdrawals are never executed.
