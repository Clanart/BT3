### Title
Scanner Reports Dust/Unspendable Outputs As Received Funds With No Minimum-Value Check - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is: value smaller than the cost to move it accrues as permanently stranded "dust" because the protocol has no minimum-value or recovery path. In `bitcoin-serai`, `Scanner::scan_transaction` accepts any output paying to a registered `script_pubkey` regardless of its `value`, and `SignableTransaction::new` places a dust floor only on *payments*, never on *inputs* — and never checks whether an input's value exceeds the fee it costs to spend it. An unprivileged party can send dust-valued (or economically-negative) outputs to any registered deposit offset; they are reported as received `ReceivedOutput`s yet can never be profitably spent, permanently inflating the wallet's reported balance with unspendable funds. There is also no sweep/skim mechanism to recover the sub-dust change remainder that `SignableTransaction::new` silently folds into the fee.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no check on `output.value` (networks/bitcoin/src/wallet/mod.rs:199-214).

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

On the spend side, `SignableTransaction::new` enforces `DUST = 546` only against payment amounts (networks/bitcoin/src/wallet/send.rs:165-169, 32). Inputs are summed unconditionally (send.rs:175). Each Taproot input adds ~58 vbytes to the transaction weight via `calculate_weight_vbytes` (send.rs:71-84), so at any nonzero `fee_per_vbyte` an input whose value is below roughly `58 * fee_per_vbyte` sats consumes more fee than it contributes. Because `input_sat < payment_sat + needed_fee` merely errors with `NotEnoughFunds` (send.rs:215-221), including such an input makes otherwise-valid spends fail or silently burns value: the remainder below `DUST` is dropped as change and added to the fee (send.rs:224-234).

Additionally, `register_offset` lets an attacker-observable offset be registered and then dusted repeatedly; `scan_block`/`scan_transaction` will keep reporting every dust output as a `ReceivedOutput` (mod.rs:180-196, 221-227).

### Impact Explanation
- Funds are reported received that are not spendable: a deposit of 1 sat (or any value below the marginal input fee) is surfaced as a `ReceivedOutput`/`value()` (mod.rs:116-118) yet can only be spent at a net loss, and including it can push a transaction into `NotEnoughFunds` or over `MAX_STANDARD_TX_WEIGHT`.
- Analogous to the report's stranded-dust accrual, the sub-`DUST` change remainder is burned as fee on every transaction with no recovery path (send.rs:224-234).
- An unprivileged sender fully controls the deposited amount, so this is reachable purely with public transaction data — no validator, key, or RPC compromise required.

### Likelihood Explanation
Any Bitcoin user can send dust outputs to a known Serai deposit address at trivial cost. Dust outputs are non-standard to *create* as standalone payments but are trivially embeddable alongside other outputs, and economically-negative-but-standard outputs (a few hundred sats) are cheap to produce continuously. There is no code path that filters them.

### Recommendation
- Enforce a minimum value in `Scanner::scan_transaction` (or at output-registration/acceptance time) — e.g. reject outputs below `DUST` or below a fee-rate-scaled spend-cost threshold.
- In `SignableTransaction::new`, skip or refuse inputs whose value does not exceed their marginal fee contribution (`fee_per_vbyte * per-input vbytes`), rather than letting them poison the input set.
- Document or add a sweep path so sub-dust remainders and stranded dust inputs can be consolidated at low fee rates instead of being permanently unspendable.

### Proof of Concept
```rust
// Attacker sends a 1-sat (or 300-sat) P2TR output to a registered offset script.
// scan_transaction reports it:
let received: Vec<ReceivedOutput> = scanner.scan_transaction(&attacker_tx);
assert_eq!(received[0].value(), 1); // reported as received

// Spending it: input contributes ~58 vbytes at fee_per_vbyte = 10 -> ~580 sat of fee,
// far exceeding its 1-sat value. SignableTransaction::new only dust-checks payments,
// so the input is accepted into input_sat and either (a) burns value into the fee or
// (b) triggers NotEnoughFunds for a payment the wallet's other inputs could have made.
// The output is spendable in no economically rational way and no sweep path exists.
```
Root cause: missing minimum-value/economic-viability check on received outputs in `Scanner::scan_transaction` (mod.rs:205-211) combined with dust enforcement applied only to payments, not inputs or change recovery, in `SignableTransaction::new` (send.rs:165-169, 224-234).
