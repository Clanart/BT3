### Title
`is_deposit_valid` accepts `ReplacementDeposit.old_move_txid` with no provenance check, letting verifiers N-of-N presign a vault for a fabricated replacement - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` (core/src/verifier.rs:541-732) only checks that the on-chain output at `deposit_outpoint` has the correct amount and a `script_pubkey` matching `Taproot(ReplacementDepositScript(nofn_xonly_pk, old_move_txid), Multisig(security_council))`. It never checks that the transaction spending into that output actually consumed the real prior move-to-vault UTXO (`old_move_txid`'s `DepositInMove` output) via the `CheckSig(old_nofn_xonly_pk)`/`Multisig(security_council)` script path. Since `old_move_txid` is only a byte string embedded in a script the depositor writes, an unprivileged depositor can fund any taproot output with this exact script pattern themselves and name an arbitrary `old_move_txid`, and the verifier fleet will treat it as valid and sign a full N-of-N presigned transaction graph for it.

### Finding Description
The invariant that should hold is: **for every accepted `ReplacementDeposit`, `old_move_txid == txid of a move-to-vault transaction that was actually created and later spent via the `Multisig::from_security_council` script path into the new replacement-deposit output`.**

Tracing the code:
- `ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid)` (core/src/builder/script.rs:512-539) simply embeds `old_move_txid` as a constant pushed into the script; it imposes no on-chain relationship to any prior transaction.
- `DepositData::get_deposit_scripts` for `DepositType::ReplacementDeposit` (core/src/deposit.rs:206-217) builds the expected script purely from `nofn_xonly_pk` and `replacement_deposit_data.old_move_txid`, both attacker-supplied fields parsed straight from the gRPC request (`core/src/rpc/parser/mod.rs:363-374`).
- `Verifier::is_deposit_valid` (core/src/verifier.rs:659-705) computes `expected_scriptpubkey` from these attacker-supplied fields, fetches the actual on-chain tx at `deposit_outpoint`, and only checks: (a) amount == `bridge_amount`, (b) `script_pubkey == expected_scriptpubkey`, (c) confirmation height ≥ `start_height`. There is no check that the deposit tx's *input* was `old_move_txid:DepositInMove`, no check that `old_move_txid` was ever created by this bridge, and no check that it was ever spent through the security-council multisig path.
- The legitimate flow (`core/src/test/common/mod.rs:750-774`, `create_replacement_deposit_txhandler` core/src/builder/transaction/mod.rs:404-446) shows the *intended* construction: the replacement deposit tx's single input is `OutPoint{ txid: old_move_txid, vout: DepositInMove }`, spent via the security-council script path. But this construction is only exercised by test helpers (`#[cfg(test)]`) - nothing in the verifier's validation path enforces it structurally. An attacker's Bitcoin transaction can instead spend any of their own coins and simply write the same output script, with a self-chosen (possibly fabricated, or belonging to someone else's unspent deposit) `old_move_txid`.
- `is_deposit_valid` is called from `deposit_sign` (core/src/verifier.rs:876) and `deposit_finalize` (core/src/verifier.rs:994), which are the gates before verifiers issue MuSig2 partial signatures for the entire presigned transaction graph (move-to-vault, round, kickoff, disprove, etc.) for that deposit. `verify_disprove_conditions` (core/src/verifier.rs:2398 area) later operates on `deposit_data` that was already accepted at this gate - it has no independent check on `old_move_txid` either, and simply derives `move_txid`/`round_txid` from already-built `txhandlers`.
- Because `is_deposit_valid` never re-derives or verifies provenance of `old_move_txid`, the entire verifier fleet can be induced to sign a full N-of-N presigned chain for a "replacement" that replaces nothing.

### Impact Explanation
Within this repository's boundary, the demonstrable effect is that verifiers unconditionally sign (MuSig2 N-of-N) a complete presigned transaction tree (move-to-vault, round/kickoff/disprove graph) for a `ReplacementDeposit` whose `old_move_txid` is fabricated or names a UTXO never spent by the security council. This matches the listed Critical category "N-of-N partial signatures for an unauthorised spend" in the narrow sense that the signature authorization for the *replacement chain* is granted without the security-council-gated provenance the design assumes.

Whether this becomes literal BTC theft or a frozen honest deposit depends on downstream Citrea-contract logic (`replaceDeposit`) that maps `old_move_txid` to a specific `deposit_id`/existing accounting entry - that contract-side binding is out of scope for this repository per the audit rules, and its exact enforcement could not be located within this repo's indexed files, so the ultimate blast radius (double-crediting vs. no crediting vs. freezing an honest depositor's real vault) cannot be conclusively confirmed from this codebase alone. What is confirmed and reproducible purely within `core/` is that `Verifier::is_deposit_valid` performs no cross-check of `old_move_txid` against any real prior vault or its spend history, which is the exact gap the question asks about.

### Likelihood Explanation
Trivial and repeatable: any unprivileged depositor can fund one taproot output matching the required script pattern (cost: one `bridge_amount` UTXO plus fees) and submit `NewDeposit` with `DepositType::ReplacementDeposit{ old_move_txid: <anything> }` to the public aggregator. No verifier role, key, or collateral is required. This can be repeated for arbitrarily many fabricated `old_move_txid` values.

### Recommendation
In `Verifier::is_deposit_valid`, for `DepositType::ReplacementDeposit`, additionally verify that:
1. `old_move_txid` corresponds to a transaction that exists on-chain (or is known in the verifier's DB) as a genuine prior move-to-vault output, and
2. The deposit tx at `deposit_outpoint` actually spends `old_move_txid:UtxoVout::DepositInMove` as its input, through the `Multisig::from_security_council` script path (i.e., check the actual `TxIn.previous_output` of the on-chain transaction, not merely the output script committing to the claimed txid).

/// Struct for deposit script that replaces an old move tx with a replacement deposit (to update bridge design on chain)
/// It commits to the old move txid inside the script.
#[derive(Debug, Clone)]
pub struct ReplacementDepositScript(pub(crate) XOnlyPublicKey, Txid);

impl SpendableScript for ReplacementDepositScript {
    fn as_any(&self) -> &dyn Any {
        self
    }

    fn kind(&self) -> ScriptKind {
        ScriptKind::ReplacementDepositScript(self)
    }

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea_replace: [u8; 13] = "citreaReplace".as_bytes().try_into().expect("length == 13");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea_replace)
            .push_slice(self.1.as_byte_array())
            .push_opcode(OP_ENDIF)
            .into_script()
    }
}

pub fn create_replacement_deposit_txhandler(
    old_move_txid: Txid,
    input_outpoint: OutPoint,
    old_nofn_xonly_pk: XOnlyPublicKey,
    new_nofn_xonly_pk: XOnlyPublicKey,
    paramset: &'static ProtocolParamset,
    security_council: SecurityCouncil,
) -> Result<TxHandler, BridgeError> {
    Ok(TxHandlerBuilder::new(TransactionType::ReplacementDeposit)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NoSignature,
            SpendableTxIn::from_scripts(
                input_outpoint,
                paramset.bridge_amount,
                vec![
                    Arc::new(CheckSig::new(old_nofn_xonly_pk)),
                    Arc::new(Multisig::from_security_council(security_council.clone())),
                ],
                None,
                paramset.network,
            ),
            crate::builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_scripts(
            paramset.bridge_amount,
            vec![
                Arc::new(ReplacementDepositScript::new(
                    new_nofn_xonly_pk,
                    old_move_txid,
                )),
                Arc::new(Multisig::from_security_council(security_council)),
            ],
            None,
            paramset.network,
        ))
        // always use 0 sat anchor for replacement deposit tx, this will keep the amount in replacement deposit tx exactly the bridge amount
        .add_output(UnspentTxOut::from_partial(anchor_output(Amount::from_sat(
            0,
        ))))
        .finalize())
}
