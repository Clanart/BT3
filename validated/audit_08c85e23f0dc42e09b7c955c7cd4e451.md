### Title
Stale index-based diff-selection is silently re-applied to a freshly re-fetched diff at commit time, allowing corruption of partial commits/discards - (File: `app/src/lib/git/apply.ts`)

### Summary
The Sherlock report's core defect is that a stateful "should I use fresh data or the old cached value" decision is made using an indirect/positional proxy (`_rateChange` derived from stale `totalAsset`/`totalBorrow`) instead of validating against the actual current source of truth, letting time pass invisibly while state is treated as current. GitHub Desktop has a structurally identical pattern in its partial-commit/partial-discard pipeline: a user's line selection is recorded purely as a set of **positional indices** into a diff snapshot, and at commit time the app silently fetches a **brand-new** diff and blindly re-applies those same indices, without re-validating that the positions still refer to the same lines.

### Finding Description
When a user partially stages a file, Desktop shows a diff (`ITextDiff`) and records the selection as a `DiffSelection` bit-set keyed by `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [1](#0-0) . This selection is purely positional — it has no notion of *which content* was selected, only *which index*.

At commit time, `stageFiles` calls `applyPatchToIndex` for every partially-selected file [2](#0-1) . Crucially, `applyPatchToIndex` does **not** reuse the diff the user actually looked at when making the selection — it re-fetches a completely fresh diff from disk via `getWorkingDirectoryDiff` right before formatting the patch: [3](#0-2) 

`formatPatch` then walks this **new** diff's hunks and, for each line, checks `file.selection.isSelected(absoluteIndex)` [1](#0-0)  — reusing the index positions that were valid for the old diff, not the new one.

The app is aware this class of staleness exists — `updateChangesWorkingDirectoryDiff` explicitly recomputes `selectableLines` after reloading the diff for *display* purposes and says: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."* [4](#0-3) . That reconciliation only happens on the UI-refresh path, though — the commit path (`applyPatchToIndex`) fetches its own independent diff and never reconciles against it, so the guard the developers added does not cover the commit code path at all.

This mirrors the Sherlock bug precisely: a value (`file.selection`, analogous to the frax `totalAsset`/`totalBorrow` proxy) is treated as still valid/current when in fact only a *positional/derived* signal was checked, while the true underlying source of truth (`diff.hunks` freshly re-fetched, analogous to `totalAssetsAvailable`) may have shifted underneath it without anyone verifying alignment.

### Impact Explanation
If the working-tree file's line layout changes between the moment the user makes a partial line selection and the moment `applyPatchToIndex` re-fetches the diff (e.g., due to an external editor autosave, a filter/smudge re-normalization triggered by a background fetch, an autocrlf line-ending conversion warning path noted in `diff.ts`, or any other process that rewrites the file), the indices no longer correspond to the same semantic lines. `formatPatch` will then select/deselect the wrong lines against the new hunk structure, producing a patch that does **not** match what the user saw and intended. This is a silent corruption of what the user commits: lines the user explicitly deselected (e.g. secrets, debug code, unwanted changes) can be included, or lines they wanted included can be silently dropped — with no error, since `git apply --cached` will happily apply a syntactically valid but semantically wrong patch as long as hunk headers are internally consistent (which `formatPatch` always produces from whatever hunk it is handed).

### Likelihood Explanation
The precondition is a change to the working file content between diff display/selection and commit execution. Because Desktop performs many asynchronous background operations against the same working directory while dialogs are open — periodic status/indicator refresh (`refreshIndicatorForRepository`, `RepositoryIndicatorUpdater`) [5](#0-4) , background fetch + `fastForwardBranches` [6](#0-5) , and `_loadStatus` re-fetching diffs asynchronously and fire-and-forget after status updates [7](#0-6)  — there are realistic windows where a repo-controlled mechanism (a filter/attribute-driven re-write triggered on fetch/checkout, or content shifted by another concurrent Desktop-triggered git operation) can alter file content while a partial selection is still "open" in memory. It requires no local/physical access or malware — only that the attacker controls repository content/attributes and that ordinary background sync activity occurs while the victim has staged a partial selection, which is normal usage. I could not construct a full concrete PoC exercising the exact background-fetch race from the indexed code alone, so likelihood should be treated as moderate rather than confirmed exploitable in one deterministic sequence.

### Recommendation
`applyPatchToIndex`/`stageFiles` should not blindly trust index-based `DiffSelection` against a freshly fetched diff. Instead:
- Re-validate the selection against actual line content (not just index) before formatting the patch — e.g. by diffing the previously-selected diff's line text against the newly fetched diff's line text at each `absoluteIndex`, and refusing/re-prompting if they don't match.
- Alternatively, pass the exact diff object the user selected against (captured at selection time) into `applyPatchToIndex`, and detect drift (hash/mtime of the file) before staging, aborting the commit for that file with a clear "changes have changed since you selected them, please re-review" error rather than silently applying a possibly-mismatched patch.

### Proof of Concept
Not independently reproduced end-to-end; based on static code-path analysis of `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/git/update-index.ts`, and `app/src/lib/stores/app-store.ts`. Conceptual repro:
1. Open a modified file in Desktop, make a partial line selection (e.g., deselect a line containing a secret) based on the currently displayed diff.
2. Before clicking "Commit", trigger a change to the same file's line layout on disk (e.g., another process/editor inserts/removes a line above the hunk, or a smudge/attribute-driven rewrite occurs during a background fetch).
3. Click "Commit" — `applyPatchToIndex` fetches a new diff via `getWorkingDirectoryDiff` [8](#0-7)  and `formatPatch` applies the old index-based selection to it [1](#0-0) , staging/committing content that does not match what the user actually selected in step 1.
