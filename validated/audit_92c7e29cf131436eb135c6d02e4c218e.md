### Title
Zero-slippage internal swap in `SmartWomConvert._convertFor` allows sandwich attack on `WombatStaking._sendRewards` fee conversion - ([File: wombat/SmartWomConvert.sol])

### Summary
When `WombatStaking._sendRewards` converts the WOM fee portion to mWOM via `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`, the underlying `_convertFor` executes a real AMM swap on the `womMWomPool` with `amountOutMin` hardcoded to `0`. Because harvesting (`WombatStaking.harvest`) and `vote()` are externally triggerable by any unprivileged actor, an attacker who is also an LP/trader on `womMWomPool` can sandwich this swap, extracting the entire slippage/price-impact value and permanently reducing the mWOM amount queued to the fee recipient/rewarder.

### Finding Description
`WombatStaking._sendRewards` computes `feeAmount` from harvested WOM rewards and, for `isMWOM` fee entries, calls: [1](#0-0) 

This calls into `SmartWomConvert.smartConvert`, which determines a `convertRatio` from a pre-swap `currentRatio()` spot-price check, then calls `_convertFor`: [2](#0-1) 

The actual token conversion in `_convertFor` performs a live AMM swap with **no slippage protection** — `amountOutMin` is passed as `0`: [3](#0-2) 

Since `harvest()`/`vote()` on `WombatStaking` are callable by any external account (permissionless harvesting is a standard design in this codebase, confirmed by the `IWombatStaking.harvest` interface and public reward-harvest flow), an attacker can:
1. Observe a pending/mempool `harvest(_lpToken)` (or trigger it themselves since it's public) that will generate WOM fees destined for `smartConvert`.
2. Front-run with a large swap on `womMWomPool` that worsens the WOM→mWOM exchange rate.
3. Let the victim transaction execute `_convertFor`'s `swapExactTokensForTokens(..., 0, ...)`, which accepts whatever output the now-skewed pool gives (no minimum enforced).
4. Back-run to restore the pool price, capturing the price-impact value that would otherwise have gone toward the `feeTosend` amount queued via `IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken)`.

No existing modifier, `nonReentrant`, or reward-index update guards against this because the vulnerability is purely a missing slippage check on a value-bearing external swap call, not a reentrancy or access-control gap.

### Impact Explanation
This directly reduces `feeTosend` — the mWOM amount permanently queued to the fee recipient/rewarder via `queueNewRewards` — below fair value, resulting in permanent theft of unclaimed protocol/staker yield with each sandwiched harvest. This matches the "theft of unclaimed yield" impact class named in the prompt.

### Likelihood Explanation
The attack requires only: (1) capital to move the `womMWomPool` price temporarily (flash-loanable, since WOM/mWOM liquidity is finite and swap sizes here are fee-sized, i.e., attacker capital need not be enormous), and (2) the ability to front-run/back-run a public transaction (`harvest`/`vote`) — both standard MEV capabilities requiring no special privileges. It is repeatable on every harvest that includes an `isMWOM` fee and routes through `smartWomConverter`.

### Recommendation
Add real slippage protection to the internal swap in `_convertFor` (e.g., compute a `minOut` from `estimateTotalConversion`/`getAmountOut` with an acceptable tolerance, and pass a non-zero `_minRec`/`amountOutMin` down to `swapExactTokensForTokens`), and consider using a TWAP or oracle-based minimum-output bound rather than the pool's own spot price to prevent same-block manipulation.

### Proof of Concept
Foundry fork test plan:
1. Fork BSC at a block where `womMWomPool`, `WombatStaking`, and `SmartWomConvert` are deployed with the `isMWOM` fee active and `smartWomConverter` set.
2. Deploy attacker contract holding WOM/mWOM to seed `womMWomPool` swaps.
3. Simulate a pending `harvest(_lpToken)` call that will generate WOM rewards feeding into `_sendRewards`.
4. Attacker front-runs: swap a sized amount of WOM into `womMWomPool` to depress the mWOM output rate.
5. Execute `harvest(_lpToken)`; capture `feeTosend` via the `queueNewRewards` call/event on the `feeInfo.to` rewarder.
6. Attacker back-runs: reverse the swap, restoring pool price and capturing profit.
7. Assert: `feeTosend_sandwiched < feeTosend_fairValue` (computed via `estimateTotalConversion` before manipulation), and attacker's net WOM/mWOM balance increased — demonstrating value siphoned directly from the queued reward amount that would otherwise be conserved.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
