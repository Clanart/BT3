### Title
`WombatBribeManager._approveTokenIfNeeded` can permanently DoS vote casting and bribe distribution for race-condition-protected reward tokens - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager._approveTokenIfNeeded`, used by the publicly reachable `castVotes`/`voteAndCast`/`castVotesAndClaimBribes` flow, raises token allowances for `PancakeZapper` with a bare `approve()` call and never resets the allowance to zero first. For ERC-20 tokens with approval race-condition protection (e.g. USDT-style tokens, which require the current allowance to be `0` or `type(uint256).max` before it can be changed to a new non-zero value), this pattern will eventually revert once the allowance has been partially spent down to a non-zero, non-max value, permanently blocking any further `castVotes` call that routes that reward token through the zapper.

### Finding Description
`castVotes(swapForBnb)` (reachable externally via `voteAndCast` and `castVotesAndClaimBribes`, both callable by any unprivileged wallet) ends up calling `_swapFeesForBnb`, which for every non-zero bribe fee amount calls: [1](#0-0) 

which in turn calls `_approveTokenIfNeeded`: [2](#0-1) 

`_approveTokenIfNeeded` only issues a new `approve(_to, type(uint256).max)` call when the current allowance is below the needed amount, and it never resets the allowance to zero beforehand. After the zapper consumes part of the previously granted `max` allowance across multiple `zapInToken` calls, the on-chain allowance becomes some non-zero, non-max value. If a reward token enforces the classic ERC-20 approval race-condition protection (requiring the existing allowance to be `0` or `UINT_MAX` before a new non-zero value can be set — the exact bug class described in the external report for `swaptoGLP`/`poolGLP`), the subsequent `approve(_to, type(uint256).max)` call will revert once that intermediate allowance value is encountered, because it is neither `0` nor `UINT_MAX`.

This is the same root cause pattern as the reported issue: raising allowance without first zeroing it for a token that enforces the race-condition guard, causing the enclosing function to permanently revert.

### Impact Explanation
Because `_approveTokenIfNeeded` is invoked unconditionally inside the loop processing all reward tokens/fee amounts for all pools in `castVotes`, a single problematic reward token getting stuck in this state makes the entire `castVotes` (and therefore `voteAndCast` / `castVotesAndClaimBribes`) call permanently revert whenever `swapForBnb` is used and that token has accrued fees. This blocks the periodic re-casting of votes to the Wombat voter and the harvesting/forwarding of bribe rewards to pool rewarders for all pools, permanently freezing further distribution of that unclaimed bribe/reward yield to LP stakers who voted, satisfying the "permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Medium: The DoS is only triggered by a reward token that enforces allowance race-condition protection (e.g. USDT-like tokens) being configured as a bribe reward token and processed through `PancakeZapper`, and only after that allowance has been drawn down to an intermediate non-zero value across multiple `zapInToken` calls. This depends on token choice and usage pattern, matching the "medium likelihood" characterization of the analogous original report.

### Recommendation
In `_approveTokenIfNeeded`, always reset the allowance to zero before approving a new non-zero amount (e.g. `IERC20(token).approve(_to, 0)` followed by `IERC20(token).approve(_to, type(uint256).max)`), or use `safeApprove`/`forceApprove` semantics consistently, mirroring the pattern already used correctly elsewhere in the codebase (e.g. `WombatStaking.sol` lines 756-757, 767-768, which reset to zero before re-approving).

### Proof of Concept
1. Configure a bribe reward token that enforces the standard ERC-20 approval race-condition guard (allowance must be `0` or `type(uint256).max` before `approve` can set a new non-zero value) as a `rewardToken` harvested through `_swapFeesForBnb`.
2. Call `castVotes(true)` (via `voteAndCast` or directly) when fee amount > 0 for that token: `_approveTokenIfNeeded` sees allowance `0 < amount`, calls `approve(PancakeZapper, type(uint256).max)` — succeeds.
3. `PancakeZapper.zapInToken` spends part of that allowance, leaving a non-zero, non-max allowance value on the token contract.
4. On a later `castVotes(true)` call where fee amount for that token again exceeds the reduced allowance, `_approveTokenIfNeeded` calls `approve(PancakeZapper, type(uint256).max)` again; the token's race-condition guard reverts because current allowance is neither `0` nor `UINT_MAX`.
5. This reverts `castVotes`/`voteAndCast`/`castVotesAndClaimBribes` for every future call while `swapForBnb` is used, permanently blocking vote casting and bribe/reward distribution routed through this path. [3](#0-2) [4](#0-3)
