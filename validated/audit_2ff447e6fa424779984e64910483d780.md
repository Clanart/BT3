## Finding: Argument injection in `getMergedBranches` via unescaped `branchName`

### Title
Unsanitized branch name spliced into `git branch --merged` argv allows option/flag injection - (File: app/src/lib/git/branch.ts)

### Summary
`getMergedBranches` builds the `git branch` invocation by directly splicing the caller-supplied `branchName` as a bare positional argument after `--merged`, with no `--` end-of-options separator and no validation that the string does not begin with `-`.

### Finding Description
`getMergedBranches` constructs: [1](#0-0) 

```
const args = ['branch', ...formatArgs, '--merged', branchName]
```

`branchName` is passed through unmodified to `git()` as the value following `--merged`. Git's argument parser treats any token beginning with `-` as an option rather than a positional ref argument unless it is preceded by a `--` end-of-options marker. Because no `--` separator is inserted before `branchName`, a branch/ref short name that begins with `-` (e.g. `--upload-pack=...`, `-c`, `--exec=...`, or any other option-shaped string) will be parsed by git as a flag to the `branch` subcommand instead of as the ref to compare against.

Contrast this with `getBranchesPointedAt` in the same file, which embeds the untrusted `commitish` into a single `--points-at=${commitish}` token rather than passing it as a separate positional argument — a pattern that avoids this exact class of issue: [2](#0-1) 

The only in-repo caller of `getMergedBranches` is `findBranchesMergedIntoDefaultBranch` in the branch pruner, which passes `defaultBranch.name`: [3](#0-2) 

I was not able to fully trace, within the remaining tool budget, the exact code path that populates `defaultBranch.name` in `RepositoryStateCache`/`git-store.ts` (i.e., whether it is derived from a remote's `HEAD` symbolic ref/`for-each-ref` output without validation, as implied by the question). Git's own ref-name validation rules (`git check-ref-format`) do not forbid a ref/branch short name from beginning with `-`, so it is plausible for a maliciously named remote branch to reach this code path unmodified, but I could not confirm end-to-end within this session that GitHub/git actually permits creating and advertising such a ref as a repository's default branch in practice.

### Impact Explanation
If a remote-controlled ref name reaches `branchName` unmodified and begins with `-`, the resulting `git branch [...formatArgs] --merged <attacker-string>` invocation could have its flag set corrupted — e.g., turning `--merged` into a no-op and substituting an attacker-chosen option/value to the `git branch` command. The blast radius is limited to whatever `git branch` itself accepts as flags/values (it does not support option values that trigger arbitrary command execution like `--upload-pack`), so this is a lower-severity argv-corruption issue rather than direct code execution, and is scoped to local repository info-disclosure/logic corruption within `git branch`.

### Likelihood Explanation
Requires an attacker to control a repository/remote whose default (or otherwise passed-in) branch short name is option-shaped, and requires that value to survive git's/GitHub's ref-name validation unmodified — a precondition I could not fully verify against the actual default-branch-resolution code path in this session.

### Recommendation
Insert a `--` end-of-options separator before `branchName` in the `args` array (`['branch', ...formatArgs, '--merged', '--', branchName]`), matching the safer pattern already used by `getBranchesPointedAt`, or validate/reject ref names that begin with `-` before use.

### Proof of Concept

```ts
const args = ['branch', ...formatArgs, '--merged', branchName]
// if branchName === '--edit-description'
// args becomes: ['branch', '--format=...', '--merged', '--edit-description']
```
