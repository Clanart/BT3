Confirmed: `NativeSeiTokensERC20.sol` caches `name`, `symbol`, and `decimals` as immutable state variables at construction time, hardcoded from a snapshot of the token factory's bank `Metadata`, and this metadata can later be mutated on-chain by the tokenfactory denom admin via `MsgSetDenomMetadata` without ever propagating to already-deployed ERC20 pointer contracts.### Title
Native ERC20 pointer permanently hardcodes decimals/name/symbol from a mutable tokenfactory denom's bank metadata - ([File: x/evm/artifacts/native/NativeSeiTokensERC20.sol])

### Summary
The `pointer` precompile's `AddNative` method deploys a `NativeSeiTokensERC20` contract whose `name`, `symbol`, and `decimals` are copied once from the bank module's `Metadata` for a denom and stored as immutable constructor-set state variables. The tokenfactory denom admin can later change that same metadata via `MsgSetDenomMetadata`, but the already-deployed pointer never re-reads it, so the pointer's reported `decimals()`/`name()`/`symbol()` silently diverge from the bank module's source of truth — the exact "duplicate data can get out of sync" bug class described in the report.

### Finding Description
When a user calls `addNativePointer(denom)` on the pointer precompile (`0x100b`), the executor reads the denom's bank `Metadata` once, computes `name`, `symbol`, and `decimals` from `metadata.DenomUnits`, and bakes them into the constructor arguments of the deployed `NativeSeiTokensERC20` contract: [1](#0-0) [2](#0-1) 

The deployed contract stores these values in plain state variables (`nname`, `ssymbol`, `ddecimals`) set only in the constructor, and its view functions simply return the cached copies instead of consulting the bank module each time: [3](#0-2) 

Meanwhile, `balanceOf` and `totalSupply` on the same contract *do* query the live bank precompile (`IBank.balance`/`IBank.supply`), so the pointer is a mix of "live" balance/supply and "frozen" metadata: [4](#0-3) 

The bank `Metadata` (including `DenomUnits`/exponents, name, symbol) backing a tokenfactory denom is not immutable: the denom's admin can call `MsgSetDenomMetadata` at any time to rewrite it, which is processed by `x/tokenfactory/keeper/msg_server.go`'s `SetDenomMetadata` and persisted via `BankKeeper.SetDenomMetaData`: [5](#0-4) [6](#0-5) 

Once this happens, any pointer contract created earlier for that denom keeps returning the stale `decimals()`/`name()`/`symbol()` forever — there is no code path that re-syncs an already-deployed native pointer's cached metadata with a subsequent `SetDenomMetaData` call.

### Impact Explanation
`decimals()` is the standard interface used by EVM-side integrators (DEX routers, price oracles, wallets, aggregators, other smart contracts) to convert a pointer's raw `balanceOf`/`totalSupply` integer into a human/economic unit. If the tokenfactory admin later increases or decreases the denom's exponent (e.g., migrating a token's precision, or correcting metadata after launch) via `MsgSetDenomMetadata`, the pointer's cached `decimals()` no longer matches the denom's actual precision as tracked by the bank module. Any downstream EVM contract that computes swap amounts, collateral ratios, or price conversions using the pointer's stale `decimals()` against the live `balanceOf`/`totalSupply` values will miscompute by orders of magnitude (e.g., 10^n), leading to fund loss for users of that integration (e.g., a DEX pricing/quoting logic under- or over-crediting an amount, or a lending contract mis-valuing collateral). This is an unauthorized-transfer/fund-loss class impact reachable purely by an on-chain tokenfactory denom admin (an ordinary tokenfactory denom creator/admin — not privileged, not a validator) combined with ordinary EVM users interacting with the stale pointer.

### Likelihood Explanation
Both preconditions are reachable by unprivileged actors through normal transactions:
1. Any account can create a tokenfactory denom and become its admin (`MsgCreateDenom`), then register a native pointer for it via `pointer.addNativePointer(denom)`.
2. The same admin can subsequently call `MsgSetDenomMetadata` to change the denom's `DenomUnits`/exponent, name, or symbol — this is a standard, unprivileged, single-transaction operation gated only by the denom's own admin check (`authorityMetadata.GetAdmin()`), not by governance or validator authority.

No malicious peer, validator, or governance action is required — a single tokenfactory admin acting on their own denom, after third parties have integrated with the pointer, is sufficient to desynchronize the value from the source of truth.

### Recommendation
Make `NativeSeiTokensERC20.decimals()`, `name()`, and `symbol()` read live from the bank module (via the `IBank`/denom-metadata precompile) on every call, exactly as `balanceOf()` and `totalSupply()` already do, instead of caching values at construction time. If gas cost of always querying live metadata is a concern, alternatively invalidate/refresh the pointer's cached metadata whenever `SetDenomMetaData` is called for the underlying denom (e.g., re-deploy/upgrade path already used by `pointer_upgrade.go` for versioned pointers), and document/version this behavior so integrators are not silently exposed to stale decimals.

### Proof of Concept
1. Attacker/admin A creates tokenfactory denom `factory/A/TOKEN` with `MsgCreateDenom`, then sets metadata with `DenomUnits = [{denom: "utoken", exponent: 0}, {denom: "TOKEN", exponent: 6}]` (`decimals = 6`).
2. A calls `pointer.addNativePointer("factory/A/TOKEN")`; the pointer precompile deploys `NativeSeiTokensERC20` with `decimals_ = 6`, matching the current metadata (`precompiles/pointer/pointer.go` `AddNative`).
3. A third-party DEX/router integrates the pointer, reading `decimals()` once and caching/quoting swaps assuming 6-decimal precision.
4. A later calls `MsgSetDenomMetadata` on the same denom, changing the top exponent to `18` (or any different value) — this succeeds because A is still the denom admin (`x/tokenfactory/keeper/msg_server.go:SetDenomMetadata`).
5. The already-deployed pointer's `decimals()` still returns `6` (from `NativeSeiTokensERC20.ddecimals`), while `balanceOf`/`totalSupply` continue to reflect the bank module's raw integer balances unaffected by the metadata change.
6. Any EVM contract or off-chain integrator that combines the stale `decimals()` with the live raw balance to compute a token amount will be off by `10^12`, enabling A (or anyone aware of the desync) to exploit mispriced swaps/liquidity operations against that integrator for direct fund loss.

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
