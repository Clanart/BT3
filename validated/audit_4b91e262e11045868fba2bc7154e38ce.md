### Title
PedPoP blame evaluation panics on out-of-range `Participant` indexes via `HashMap` indexing - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2018-2665 (a low-privileged network attacker crashes a server with crafted input), an unprivileged participant can crash any party evaluating a PedPoP blame accusation by naming an out-of-range `Participant` index as `sender` or `recipient`. `BlameMachine::blame` / `AdditionalBlameMachine::blame` take caller-supplied `sender`/`recipient` indexes and pass them into `Decryption::decrypt_with_proof` and `blame_internal`, which index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` directly. Both maps only contain entries for participants `1..=n`; any `Participant` index outside that range causes a `HashMap` index panic, crashing the process.

### Finding Description
`AdditionalBlameMachine::blame` and `BlameMachine::blame` accept `sender: Participant` and `recipient: Participant` as attacker-influenced accusation parameters (an accusation is a public message naming who allegedly sent a bad share to whom). `Participant::new` accepts any non-zero `u16`, so nothing constrains these to `1..=n` at the type level.

Inside `blame_internal`, `decrypt_with_proof` is called first, which — once the attacker-supplied `EncryptedMessage`'s Schnorr proof-of-possession verifies — evaluates the DLEq against `self.enc_keys[&decryptor]` (encryption.rs:388), a direct `HashMap` index that panics for any `decryptor` index not registered (i.e., not in `1..=n`). An attacker can satisfy the PoP check trivially: they generate a fresh encryption key and sign `pop_challenge` themselves, since `pop_challenge` binds `sender`, the key, and the message — all attacker-chosen (encryption.rs:302-324, 374-390).

Independently, if the accusation names an out-of-range `sender` with a valid `recipient`, `blame_internal` proceeds to `&self.commitments[&sender]` (lib.rs:599), again panicking for any sender index > `n` once the message decrypts and encodes a canonical scalar — also fully attacker-constructible.

`AdditionalBlameMachine::new` is explicitly intended for third parties ("capable of evaluating blame regardless of if the caller was a member in the DKG protocol") and performs no range check on the `sender`/`recipient` passed to `blame` (lib.rs:638-682). The same panic affects `Decryption::register`'s assertion, though that is gated on callers forwarding duplicate participant messages.

### Impact Explanation
Any node, validator, or observer that feeds a blame accusation into `BlameMachine::blame` / `AdditionalBlameMachine::blame` will panic on an index-out-of-map access. In Serai this evaluation is meant to be performed redundantly (e.g., by coordinators/validators adjudicating DKG faults), so a single crafted accusation naming `Participant(u16::MAX)` crashes every node evaluating it — a complete, repeatable denial of service of the DKG/blame pipeline, mirroring CVE-2018-2665's low-privileged hang-or-crash class. No secrets or valid shares are required; the attacker only needs to emit a syntactically valid `EncryptedMessage` under a self-chosen `sender`/`recipient` pair.

### Likelihood Explanation
Triggering requires only that a party submit a blame accusation — an unauthenticated-in-band public input the protocol explicitly expects to receive — with `sender` or `recipient` outside `1..=n`. Constructing the required `EncryptedMessage` (a `C::G` key, a `SchnorrSignature` PoP, and a `SecretShare` blob) is straightforward since the PoP challenge binds only attacker-controlled values. The panic is deterministic on the first out-of-range index used.

### Recommendation
In `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal`, replace the panicking `HashMap` indexing (`self.enc_keys[&decryptor]`, `self.commitments[&sender]`) with `get()` lookups that map a missing entry to `DecryptionError`/`PedPoPError` (or blame the accuser/`recipient`). Additionally, `blame`/`blame_internal` should validate `sender` and `recipient` are within `1..=n` (or present in `commitments`/`enc_keys`) before any use, returning a typed error identifying the accuser as faulty.

  // ... each participant's EncryptionKeyMessage<Commitments<Ristretto>> ...
