### Title
Tron `IntentGatewayV2.cancelOrder`/`fillOrder` lack the `ReentrancyGuard` protection present in the mainline EVM contract, permitting reentrant escrow drainage - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is a parallel implementation of the same order-escrow/fill/cancel protocol as the mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`). The mainline contract's `cancelOrder` is explicitly guarded with `nonReentrant` [1](#0-0) , and its fill/cancel escrow-release path (`_withdraw` in `IntentsBase.sol`) was hardened with a checks-effects-interactions fix (`_filled[commitment]` set before any external token transfer) after an internal reentrancy audit, documented and regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` [2](#0-1) . The Tron variant contains none of this hardening: it inherits only `HyperApp, EIP712` — no `ReentrancyGuard` — and its `cancelOrder` function is declared `public payable` with no `nonReentrant` modifier [3](#0-2) [4](#0-3) .

### Finding Description
Both `IntentGatewayV2` implementations escrow user funds in `_orders[commitment][token]` and release them via a `withdraw`-style routine that performs external calls (native ETH `.call{value: amount}("")` or `IERC20.safeTransfer`) to a caller-controlled beneficiary address, once per token in the order's input list [5](#0-4) .

In the mainline EVM contract, Polytope Labs recognized this class of bug: the `cancelOrder` entrypoint was retrofitted with `nonReentrant` [1](#0-0) , and `_fillSameChain`/`_fillCrossChain` were rewritten to set `_filled[commitment] = msg.sender` as the very first state write (before any token transfer loop), specifically to close a reentrancy window where "`_filled` was set only inside `_withdraw(finalize=true)`... a malicious beneficiary could re-enter and steal the escrowed tx fees" or "self-fill the ERC-20 output... and steal the entire input[1] escrow" [6](#0-5) [7](#0-6) .

The Tron contract is functionally the same protocol (`placeOrder`, `cancelOrder`, `withdraw`, escrow map `_orders`, `_filled` mapping) but was not updated with either mitigation: it does not import or inherit `ReentrancyGuard`, and `cancelOrder` has no `nonReentrant` guard [8](#0-7) . Because `withdraw`'s token-release loop still performs an external call to `beneficiary` (a caller-supplied `order.user` address) before returning, a malicious contract set as `order.user`/beneficiary can re-enter the gateway during that external call. Without a reentrancy guard, the corrupted invariant is: **the same escrow accounting state (`_orders[commitment][token]`) can be read and mutated by a nested call before the outer call's own accounting write completes**, and — more importantly — the attacker can re-enter to trigger `cancelOrder`/`withdraw`/`placeOrder` on a *different* commitment that shares mutable contract state (e.g., `_nonce`, dust-fee balances, or a second escrowed order) while the outer transaction is still mid-flight, something the mainline contract's `nonReentrant` explicitly forecloses.

### Impact Explanation
This falls squarely within "stealing or loss of funds" and "transaction manipulation" for bridge custody: escrowed user funds held by the Intent Gateway are the asset at risk. A reentrant call during the beneficiary payout can be used to re-execute escrow-release logic, drain treasury/dust balances, or interleave a second order's cancellation/fill in a way the single-threaded, guard-protected mainline contract prevents. Because the Tron contract handles real user escrow (native TRX/ERC20-equivalent tokens and fee-token dust), successful exploitation directly threatens custody of bridged funds.

### Likelihood Explanation
The attack requires only an unprivileged actor able to place or receive as an order's `beneficiary`/`user` a contract with a fallback/receive function — no relayer, prover, governance actor, or leaked key is needed. This matches the "unprivileged attacker" requirement of the bounty. The existence of the exact same bug, already found and fixed with tests in the mainline EVM contract (`IntrinsicIntentsReentrancyTest.sol`), strongly indicates the underlying vulnerability class is exploitable and was previously exercised successfully against the pre-fix code — and the Tron contract is the pre-fix code shape carried forward without the corresponding `nonReentrant`/CEI fix.

### Recommendation
Apply the same fix used in the mainline EVM contract to the Tron deployment:
1. Inherit OpenZeppelin's `ReentrancyGuard` in `evm/tron/contracts/apps/IntentGatewayV2.sol` and add `nonReentrant` to `cancelOrder`, `fillOrder`, and any other externally-callable function that performs token transfers to caller-influenced addresses.
2. Audit the Tron `withdraw` function to confirm (or fix) that `_filled[commitment]` is set before any external transfer in the token-release loop, mirroring the CEI ordering now in `IntentsBase._withdraw`.

### Proof of Concept
I was not able to view the full body of the Tron contract's internal `withdraw()` function within the available context (only `cancelOrder`'s dispatch to `withdraw(body, true)` was retrieved), so I cannot confirm the exact reentrant call sequence byte-for-byte the way the mainline `IntrinsicIntentsReentrancyTest.sol` PoC does for the EVM contract. The proof-of-concept structure would mirror that existing test:
- Deploy a malicious "beneficiary" contract implementing a `receive()`/token callback that re-enters `IntentGatewayV2.cancelOrder` (or `fillOrder`) on the Tron contract during the escrow payout.
- Place an order whose `beneficiary`/`user` is this malicious contract.
- Trigger `cancelOrder`/`withdraw`; during the native-token `.call{value: amount}("")` or ERC20 callback, re-enter to manipulate a second order's escrow state before the outer call finishes, since no `nonReentrant` guard exists to block it (unlike the mainline contract, verified at `evm/src/apps/IntentGatewayV2.sol:470`).

This gap in verification is an acknowledged limitation: confirming the precise exploitable state interleaving (e.g., double-dispatch of `RefundEscrow`, double release of the same escrow) requires reading the full Tron `withdraw()` implementation and the `IntentsBase`/dispatch functions it shares, which were not fully retrievable in this session. A Devin session with full repository access should read `evm/tron/contracts/apps/IntentGatewayV2.sol` in its entirety (especially the `withdraw` function and any dust/nonce state shared across orders) to build a concrete forge-test PoC analogous to `IntrinsicIntentsReentrancyTest.sol`.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
