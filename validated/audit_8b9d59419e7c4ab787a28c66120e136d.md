### Title
Incorrect unit conversion of DIA oracle timestamp causes systematic under/over-staleness in price freshness check - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`resolve-dia()` divides the DIA oracle's `timestamp` field by `u1000`, assuming it is expressed in milliseconds, without any way to confirm this assumption against the actual on-chain DIA oracle's units, since `get-value` simply returns whatever `uint` the `oracle-updater` writes via `set-value`/`set-multiple-values`. If the real DIA integration on Stacks publishes `timestamp` already in seconds (as most DIA/Pyth-style feeds and the trait signature `{value: uint, timestamp: uint}` do not document units), this division silently divides the real timestamp by 1000, corrupting the staleness check used by every USDH price resolution.

### Finding Description
`resolve-dia` is called through `resolve-price-feed` → `price-resolve`, feeding directly into the market's per-asset oracle freshness gate: [4](#0-3) [5](#0-4) 

`oracle-timestamp-fresh` compares this timestamp against `stacks-block-time` with a per-asset `max-staleness`: [6](#0-5) 

If the real timestamp unit fed by DIA is actually seconds (not milliseconds), dividing by 1000 produces a value ~1000x smaller than the true timestamp — i.e., a timestamp appearing to be from the epoch's very early history — which would make `delta` huge and cause the price to always be rejected as stale (`ERR-ORACLE-INVARIANT`), a denial-of-service on USDH pricing rather than a manipulable "wrong direction" bug. Conversely, if the timestamp unit assumption is backwards in the other direction (e.g., DIA emits seconds, code should not divide at all, or emits some other multiplier), the staleness delta could be computed as far smaller than actual elapsed time, letting a genuinely stale/manipulated USDH price pass the freshness check as if it were fresh. This second case is the one that maps to an economically exploitable analog of the airdrop unit-confusion bug: a wrong divisor turns "old, potentially manipulated price" into "accepted as fresh," letting borrowers/liquidators use a favorable stale USDH price to inflate collateral value or under-value debt.

### Impact Explanation
If the unit assumption is wrong in the direction that relaxes staleness, an attacker (or a party in control of, or observing, the DIA feed lag) could exploit a stale USDH price to borrow against inflated USDH collateral value or to avoid liquidation when USDH's true price has dropped, resulting in theft of funds or bad debt against the protocol — a Critical/High impact on funds at rest. This lands in the in-scope impact class of "confidence or staleness gating" leading to a wrong price being accepted by the health/liquidation logic.

### Likelihood Explanation
Likelihood is uncertain because the actual timestamp unit emitted by the production DIA oracle integration used by Zest cannot be verified from the trait or the on-chain oracle contract in this repo — `get-value` merely echoes back whatever `uint` was written by `set-value`, with no unit documented in the trait. This is flagged as an unverified analog: the report's root-cause pattern (dividing/multiplying a time value by the wrong unit factor) is structurally identical to the airdrop bug, but whether this manifests as an exploitable "stale price accepted" case or a purely defensive DoS ("price always rejected") cannot be determined without knowing DIA's actual mainnet emission format.

### Recommendation
Verify against the actual DIA oracle deployment used in production what unit `timestamp` is emitted in, and remove or correct the `/ u1000` conversion in `resolve-dia` accordingly. Add an explicit sanity/bounds check on the converted timestamp (e.g., reject timestamps implausibly far in the past after conversion) so an incorrect unit assumption fails closed (denies the price) rather than potentially failing open (accepts a stale price as fresh).

### Proof of Concept
Not able to construct a concrete on-chain PoC because the actual unit of the production DIA `timestamp` field is not present in this codebase (the oracle contract shown is a local-testing mock echoing raw input); this finding is reported as an unverified analog requiring confirmation of DIA's mainnet timestamp unit before treating it as a proven vulnerability.
