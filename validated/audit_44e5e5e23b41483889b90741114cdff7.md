This confirms the key ordering issue: `EVMPreprocessDecorator` (which loops over `SetCodeAuthorizations()` doing ECDSA recovery and per-authority association) runs **before** `BasicDecorator`, which is the decorator that actually computes and enforces `core.IntrinsicGas` against `etx.Gas()` [1](#0-0) [2](#0-1) . And `validateAuthList` only rejects an *empty* list — it never bounds the maximum size of the EIP-7702 `AuthList` [3](#0-2) .

### Title
Unbounded EIP-7702 authorization-list processing in EVM ante pipeline enables DoS - (File: x/evm/ante/preprocess.go)

### Summary
The `SetCodeTx` (EIP-7702) authorization list has no maximum-size validation, and every authorization in it is processed with expensive ECDSA recovery plus a full KV-store cache-context read/write **before** the ante pipeline enforces the transaction's own intrinsic-gas/size limits.

### Finding Description
`validateAuthList` only checks that the auth list is non-empty; it imposes no upper bound on the number of entries [3](#0-2) . The EVM ante chain runs `EVMPreprocessDecorator` first, and for `SetCodeTx` it iterates every entry in `ethTx.SetCodeAuthorizations()`, calling `helpers.AuthorityToPreAssociate` (which internally calls `RecoverAddressesFromAuthorization`, an ECDSA public-key recovery) and then opens a `ctx.CacheContext()` and runs `associateHelper.AssociateAddresses` (state reads/writes) for every authority that passes the check [4](#0-3) . The same unbounded loop exists in the legacy ABCI path via `AssociateAuthorizationAuthorities`, executed on both CheckTx and DeliverTx [5](#0-4) [6](#0-5) .

Crucially, this work happens under an **infinite gas meter** (`ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))`) set earlier in preprocessing [7](#0-6) , and the intrinsic-gas check that would otherwise bound the number of authorizations relative to `etx.Gas()` (`core.IntrinsicGas(..., etx.SetCodeAuthorizations(), ...)`) only runs later, in `BasicDecorator`, which is ordered *after* `EVMPreprocessDecorator` in the ante chain [1](#0-0) [2](#0-1) . This means the expensive per-authorization ECDSA-recovery-plus-store work always executes in full before any gas-based rejection can occur — the loop itself is never gas-metered or capped by an explicit list-size limit, mirroring the unbounded-intermediate-certificate class of bug in CVE-2026-32280 (work proportional to an unbounded, attacker-supplied list executed before any limiting check).

An attacker packs a `SetCodeTx` with as many authorization tuples as fit within the max transaction/block size, each a distinct throwaway keypair authorization. Since each tuple is compact (~chainID + 20-byte address + nonce + v/r/s), thousands of tuples can fit in typical transaction size limits. Every full node performing `CheckTx` (mempool admission, run by all nodes) and `DeliverTx`/execution (validators) must perform ECDSA point recovery and a cache-context KV read/write for every tuple, unbounded by gas, before the transaction can even be rejected for insufficient intrinsic gas.

### Impact Explanation
Since `CheckTx` runs this same unbounded loop on every full node's mempool admission path (not gas-billed, and prior to the intrinsic-gas rejection), an attacker can flood the mempool/consensus pipeline with such transactions to consume disproportionate CPU on every node, delaying block production beyond the 2.5-second threshold or degrading public RPC/mempool nodes broadly — a network-wide liveness/DoS impact rather than a localized one.

### Likelihood Explanation
Likelihood is high for an attacker with only the ability to submit a standard, cheaply-fee-able EVM `SetCodeTx`: no privileged access, validator status, or special network position is required — a single crafted transaction targeting the public JSON-RPC/mempool ante path is sufficient reach. The bug class is a straightforward analog of the reported x509 issue (unbounded per-item cryptographic work driven by an attacker-controlled list length, executed before any limiting check).

### Recommendation
- Enforce an explicit maximum length on `SetCodeTx.AuthList` in `validateAuthList` (mirroring `validateAllowListSize` used elsewhere for bank/tokenfactory allow-lists) [8](#0-7) .
- Reorder the EVM ante chain so intrinsic-gas / size checks (`BasicDecorator`) execute before `EVMPreprocessDecorator`'s authorization-recovery loop, or otherwise gate the per-authorization work behind a cheap, gas-metered pre-check derived from `core.IntrinsicGas`.
- Apply the equivalent size cap to the `AssociateAuthorizationAuthorities` legacyabci path used by `EvmCheckTxAnte`/`EvmDeliverTxAnte`.

### Proof of Concept
1. Craft a `SetCodeTx` whose `AuthList` contains N (e.g., several thousand) `SetCodeAuthorization` entries, each signed by a distinct freshly generated key for the target chain ID, all pointing to an arbitrary delegate address, keeping the overall serialized tx within the node's max tx-size limit.
2. Submit the transaction to a public RPC node's mempool (`CheckTx`).
3. Observe that `EVMPreprocessDecorator.associateAuthorizationAuthorities` (or `AssociateAuthorizationAuthorities` on the legacyabci path) performs N ECDSA recoveries and N `CacheContext`/KV-store round trips per submission, before the intrinsic-gas check in `BasicDecorator` can ever reject the tx for insufficient `etx.Gas()`.
4. Repeated/parallel submission of such transactions from multiple accounts saturates CheckTx/DeliverTx CPU across full nodes, delaying block production.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
