### Title
Stale line-selection indices are silently reapplied to unrelated diff lines after a working-directory diff refresh, corrupting partial commits/discards - (File: `app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
The PoolTogether bug is a boundary/identity error: a range accounting structure (start/end draw IDs) is reused across a state transition (draw close → prize claim) without re-validating that the underlying data it refers to hasn't changed, letting stale "credit" silently leak into a new state. The Desktop analog is structurally identical but in the diff-selection subsystem: `DiffSelection` tracks which lines a user has selected/deselected for a partial commit purely by **absolute numeric index** into the unified diff (`divergingLines: Set<number>`). When the working-directory diff is reloaded (which Desktop does automatically as the working tree changes), the code only checks whether a previously-selected index is still *present* in the new diff's selectable-line set — it never checks that the index still refers to the *same line content*. If line content shifts while the numeric position stays "selectable," the old selection state is silently carried over onto different code, and that wrong selection is what gets turned into the actual `git apply` patch used for the commit or discard.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withRangeSelection`/`withLineSelection` key everything off an integer `lineIndex`, which is `hunk.unifiedDiffStart + relativeIndex` computed at diff-parse time in `app/src/lib/diff-parser.ts` (`DiffHunk.unifiedDiffStart/unifiedDiffEnd`, see `app/src/models/diff/raw-diff.ts:30-43`). [1](#0-0) 

When the app detects the diff may have changed ("The diff might have changed dramatically since last we loaded it"), it recomputes only `selectableLines` (positions that are still "includeable" lines, e.g. not turned into context) and calls `withSelectableLines`: [2](#0-1) 

`withSelectableLines` filters the previously diverging line indices by **membership in the new selectable set only** — it does not compare the actual text/oldLineNumber/newLineNumber of the line at that index between the old and new diff: [3](#0-2) 

Consequently, if the file changes (e.g. lines are inserted/removed such that the diff hunk boundaries realign) but a particular numeric index that was previously "line N, an added secret-looking string the user deliberately excluded" is still a selectable index in the new diff (now pointing at a *different* line of code), that index's diverging (or default) selection state is reused unchanged. The comment in `app-store.ts` acknowledges the diff can have "changed dramatically" but the mitigation only prunes indices that literally fell outside the new selectable-lines set — it does nothing to detect that a surviving index now denotes different content.

This selection object is later consumed verbatim, with no additional content verification, by:
- `formatPatch` in `app/src/lib/patch-formatter.ts`, which decides per-line inclusion purely via `file.selection.isSelected(absoluteIndex)` (`app/src/lib/patch-formatter.ts:157`), and
- `formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts:280`), the same pattern for discarding changes. [4](#0-3) 

Both of these produce the literal patch text that is applied to the git index (via `applyPatchToIndex`) or to the working tree (via `discardChangesFromSelection`). There is no re-derivation of "what did the user actually click on" from content — only from position.

### Impact Explanation
Because the produced patch is generated from stale, index-keyed selection state instead of content-verified state, a commit or a discard-changes operation can silently include or exclude lines the user never intended to act on. This is exactly the "silent corruption of what the user commits or pushes" category: the user sees a checkbox/diff view that appears to reflect their intent, but the underlying patch handed to `git apply --cached` (staging) or `git apply` (discard) can diverge from what is displayed, because the diff was refreshed underneath the selection between the time the user made their choice and the time `createCommit`/`discardChangesFromSelection` executed. Depending on which lines slide into the stale indices, this can cause unintended code (including attacker-planted content in a repository the user has checked out, if that content is designed to appear/disappear via build tooling, hooks, or generated files under the same tracked path) to be silently staged and committed, or intended exclusions to be silently discarded.

### Likelihood Explanation
The precondition — a diff reload occurring while a partial selection is in progress, with the diff for the same file changing shape — is a normal operational scenario Desktop explicitly programs around (`app-store.ts` comment), because Desktop watches the working directory and refreshes diffs live. Any repository-side actor able to cause file content to shift while the user is mid-selection (e.g., a build step, git hook, linter/formatter run by the user's own tooling but with attacker-controlled file layout, or a submodule update) can trigger this without needing local/physical access, admin rights, or leaked credentials — only a cloned/fetched repository whose tracked files are designed to change shape during normal developer workflows. The exact reliability of aligning "surviving selectable index" with attacker-chosen "different line" content requires precise control of insertions/deletions, so it is a real but non-trivial-to-weaponize condition; I was not able to fully verify an end-to-end exploit chain (e.g., which UI/file-watch triggers definitely fire mid-selection) within this investigation, so likelihood should be treated as plausible-but-unconfirmed pending dynamic testing.

### Recommendation
Do not key `DiffSelection` divergence purely on positional index across diff reloads. When recomputing selectable lines in `app-store.ts`/`withSelectableLines`, additionally validate that the line at a given index in the new diff matches the line that occupied that index in the old diff (e.g., by comparing `DiffLine.text`/`oldLineNumber`/`newLineNumber`/type), and drop (or explicitly re-prompt for) any diverging selection whose underlying content changed, rather than silently preserving it. Alternatively, invalidate the entire partial selection and force a fresh, explicit re-selection whenever the diff for a file changes between load and apply.

### Proof of Concept
Conceptual reproduction (not dynamically executed):
1. Open Desktop on a repository and modify a tracked file so it has, say, 20 lines, producing a diff with hunk `unifiedDiffStart=0`.
2. In the diff view, deselect line index 5 (an added line containing e.g. `+debug_flag = true`) via `withLineSelection(5, false)`, leaving everything else selected — as in `app/test/unit/patch-formatter-test.ts:251-286`, which exercises this exact `DiffSelection`/`formatPatch` pairing.
3. Before the user commits, an external process (build tool, hook, or another instance of git run by the same session) rewrites the file so that a *different* addition now lands at absolute diff index 5 (e.g., `+malicious_import`), while the total line count and hunk boundaries keep index 5 "selectable" in the new diff.
4. Desktop's `updateChangedFiles`-driven refresh calls `withSelectableLines` (`app/src/lib/stores/app-store.ts:3495-3497`), which keeps index 5 in `divergingLines` purely because it is still a member of the new `selectableLines` set (`app/src/models/diff/diff-selection.ts:320-330`) — it never compares content.
5. When the user clicks "Commit," `createCommit` → `stageFiles` → `applyPatchToIndex` runs `formatPatch`, which calls `file.selection.isSelected(5)` and, because the stale selection state is `false` at index 5, silently excludes the *new* line at index 5 (`+malicious_import`) from context handling / inclusion rules in `app/src/lib/patch-formatter.ts:157-171`, without any indication to the user that the line evaluated was not the one they originally chose.

This demonstrates the core defect: the guard that exists (`withSelectableLines`) only checks "is this index still selectable," analogous to how the original `_computeVaultTierDetails` guard only checked draw-ID bounds without checking that the underlying liquidity had actually been distributed — in both cases a stale index/ID is trusted as still representing the same state.
