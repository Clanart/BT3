## Analysis Summary

The Predy report's core failure mode is: a critical calculation relies on **transient, in-flight state** (`slot0` spot price) that can be corrupted/manipulated within the same transaction context by an interleaved operation, producing an incorrect balance/asset accounting result. The closest reachable analog in this Cosmos EVM codebase is not price-oracle related (there is no AMM/spot-price trading logic in scope here), but the same *class* of bug — a shared, mutable "before/after" checkpoint state that can be silently overwritten by nested execution — exists in the precompile balance-synchronization layer between `x/bank` and the EVM `StateDB`.

### Title
Shared `BalanceHandler.prevEventsLen` checkpoint is corrupted by nested/recursive precompile calls, causing EVM StateDB balances to desync from `x/bank` ledger balances - (File: `precompiles/common/balance_handler.go`)

### Summary
Every precompile execution records an event-log checkpoint (`prevEventsLen`) via `BeforeBalanceChange`, then replays only the events emitted *after* that checkpoint (`AfterBalanceChange`) to mirror `x/bank` `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events into the EVM `StateDB` via `AddBalance`/`SubBalance`. [1](#0-0) 

The checkpoint is a single mutable field (`prevEventsLen int`) on a `BalanceHandler` struct, not a stack. [2](#0-1) 

If a precompile call reenters itself or triggers another precompile call before the outer call's `AfterBalanceChange` runs (e.g. via a contract hook, `try/catch` wrapped nested call, or an ERC20 `_beforeTokenTransfer` hook invoking a precompile), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`. When the outer call later invokes `AfterBalanceChange`, it slices the event log starting from the *inner* call's checkpoint instead of its own, causing bank events to be double-processed, skipped, or attributed to the wrong scope, and pushed to `StateDB.AddBalance`/`SubBalance` incorrectly.

### Finding Description
This is precisely the bug the repository's own test suite documents: [3](#0-2) 

The reachable trigger is any nested/recursive precompile invocation reachable by an unprivileged user — the repo contains multiple contracts demonstrating this pattern in production precompiles (staking, distribution, ERC20 hooks, ICS20): [4](#0-3) [5](#0-4) [6](#0-5) 

`GetBalanceHandler()` is referenced from every production precompile (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`), so any of these precompiles is a potential trigger surface if the handler instance (or its `prevEventsLen` field) is shared/reused across a nested call chain within one EVM message execution. [7](#0-6) 

### Impact Explanation
If this checkpoint corruption occurs in production precompile flows (staking, distribution, ERC20, ICS20), the consequence is that `StateDB.AddBalance`/`SubBalance` calls either (a) replay bank events twice, inflating an account's EVM-visible balance relative to its true `x/bank` balance, or (b) skip events entirely, causing EVM balance to under-report versus the ledger. Because EVM balance is authoritative for subsequent EVM execution (gas debits, transfers, contract logic) within the same transaction/block, this is an accounting-corruption class bug affecting spendable user value across native/EVM/precompile-mediated balances — matching the "Critical unauthorized … irreversible accounting corruption" impact gate.

### Likelihood Explanation
Reachability requires only ordinary, unprivileged transaction flows: a smart contract that calls a precompile, catches/ignores a revert, and calls a precompile again (patterns already present and tested in this repo, e.g. `StakingReverter.sol`, `ERC20RecursiveNonRevertingPrecompileCall.sol`, ICS20 recursive-call tests). No privileged role, validator, or relayer is needed.

### Recommendation
Replace the single mutable `prevEventsLen int` field with a stack (push on `BeforeBalanceChange`, pop on `AfterBalanceChange`) or instantiate a fresh `BalanceHandler` per precompile invocation frame instead of reusing one shared instance across nested/recursive precompile calls, ensuring outer and inner event-log window scopes cannot overwrite one another.

### Proof of Concept
The repository already contains a reproducible harness for this exact pattern: [8](#0-7) 
using a recursive precompile-calling contract: [9](#0-8) 

**Important caveat / uncertainty**: I was not able to fully inspect `precompiles/common/precompile.go`'s `GetBalanceHandler()` implementation (only confirmed via `grep` that it is referenced 9 times there and once in each production precompile) to determine definitively whether a *new* `BalanceHandler` is already allocated per top-level precompile call (which could already mitigate this for single-level calls but not for same-instance reentrancy), or whether the existing test represents a **known, already-patched regression test** rather than a currently open vulnerability. Given the explicit test name/comment ("tests the balance handler bug…This leads to balance desync"), it is possible this is a regression guard for a bug that has since been fixed, rather than a live exploit. Confirming current exploitability would require reading `precompiles/common/precompile.go` in full and verifying whether `AfterBalanceChange`'s post-condition checks (if any) would reject a mismatched/inconsistent balance state before it is committed. This should be verified directly in the repository (a Devin session with full file access) before treating this as a confirmed, unpatched Critical finding.

pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
