## Analysis

The submitted claim is valid. Confirmed by tracing the actual code paths:

**1. Mint happens unconditionally before calldata validation**

In `on_accept`, the beneficiary's balance is minted/transferred at lines 93–117, *before* any calldata (including the embedded signature) is inspected: [1](#0-0) 

Only afterward, at line 120 onward, does the code decode `substrate_data` and branch on the `MultiSignature` variant. The `Eth` variant is a guaranteed, unconditional failure: [2](#0-1) 

Because `message.data` (and therefore `substrate_data.signature`) is attacker-controlled — it comes straight from the sender-supplied `data` field of the cross-chain `send()` call on the source-chain contract — an unprivileged caller can deliberately choose `MultiSignature::Eth(_)` to force a deterministic `Err(HftError::EthSignatureUnsupported)` *after* the mint/transfer has already committed to storage.

**2. ISMP core deletes the receipt on any `Err`, allowing replay**

`modules/ismp/core/src/handlers/request.rs` stores a receipt before invoking `on_accept`, and explicitly deletes it if the callback returns `Err`: [3](#0-2) 

Critically, the outer `handle()` function always returns `Ok(MessageResult::Request { events: result, .. })` regardless of whether individual per-request callbacks failed — the per-request `Err` is only captured inside the `events` vector, not propagated as the dispatchable's overall error: [4](#0-3) 

Since the top-level extrinsic succeeds, FRAME's automatic transactional rollback (which only reverts storage on a failing dispatchable) does **not** undo the mint that already occurred inside the failed `on_accept` call. This is exactly the documented hazard called out in the project's own docs: [5](#0-4) 

With the receipt deleted, the duplicate-request guard at the top of `handle()` no longer blocks reprocessing of the same request: [6](#0-5) 

As long as the source-chain state commitment/membership proof for that request remains available and the request hasn't timed out, the identical `PostRequest` (same commitment) can be resubmitted to `handle()` again, re-triggering `on_accept`, re-minting to the same beneficiary, and failing again at the same `EthSignatureUnsupported` branch — repeatable until timeout. This produces duplicate token credit from a single bridged commitment, matching the "duplicate settlement" bounty category. Resubmission of a still-valid proof does not require a malicious relayer — it is simply re-invoking a permissionless message handler with data that remains valid.

### Title
Non-atomic mint-before-validation in `on_accept` allows guaranteed-failure signature branch to enable duplicate minting via receipt deletion - (`modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` mints/transfers the bridged amount to the beneficiary before validating optional calldata's embedded signature. The `MultiSignature::Eth` variant is hard-coded to always fail (`HftError::EthSignatureUnsupported`). Because `pallet-ismp`'s core message handler deletes the request receipt whenever `on_accept` returns `Err` (by design, to allow legitimate retries), and does not roll back the pallet's own storage mutations that already executed, an attacker can force this deterministic failure to leave the mint in place while making the request eligible for reprocessing.

### Finding Description
- Lines 93–117 unconditionally credit the beneficiary.
- Lines 120–203 decode optional calldata; the `Eth` signature branch (line 172) always returns `Err`.
- `modules/ismp/core/src/handlers/request.rs` deletes the stored receipt on any callback `Err` (lines 122–125), and the enclosing `handle()` still returns `Ok` overall (line 134), so no automatic storage rollback occurs.
- With the receipt gone, the same `PostRequest` (same commitment/proof) is no longer flagged as a duplicate and can be re-submitted to `handle()`, re-invoking `on_accept` and re-minting.

### Impact Explanation
An unprivileged sender on the source chain can craft a `send()` call embedding calldata that decodes into `SubstrateCalldata{ signature: Some(MultiSignature::Eth(...)) }`. Each time the resulting request is (re)processed, tokens are minted to the beneficiary and the request remains replayable until it times out, yielding duplicate credit from a single bridged commitment — a direct fund-duplication bug.

### Likelihood Explanation
High — the trigger condition is fully attacker-controlled (choice of a hard-coded, always-failing signature variant), requires no privileged access, and depends only on standard ISMP message resubmission, which the protocol already treats as a normal retry path for failed requests.

### Recommendation
Perform all signature/calldata validation (including rejecting unsupported signature schemes) before any custody-affecting operation (mint/transfer). Alternatively, wrap `on_accept` in a transactional storage scope (`#[transactional]` / `with_storage_layer`) so that any `Err` return fully reverts prior mutations within the same call, consistent with the documented ISMP invariant that irreversible state changes must only occur after all success criteria are met.

### Proof of Concept
1. Register an asset/contract pair as in existing tests (see `should_receive_asset_with_calldata`).
2. Construct a `Message` with non-empty `data` encoding `SubstrateCalldata { signature: Some(MultiSignature::Eth(dummy_sig).encode()), runtime_call: arbitrary }`.
3. Call `module.on_accept(post.clone())` — observe the beneficiary balance increases (from lines 93–117) yet the call returns `Err(HftError::EthSignatureUnsupported)`.
4. In the full pallet-ismp flow, observe `delete_request_receipt` executes for this failed result (`modules/ismp/core/src/handlers/request.rs:122-125`).
5. Resubmit the same `RequestMessage`/proof to `handle()`; since no receipt exists, `on_accept` runs again and mints a second time to the same beneficiary from the same source commitment.

	let result = msg
		.requests
		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);

						commitment,
						relayer: signer,

				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
