### Title
Stale, position-based partial-commit line selection is silently reapplied to a re-fetched working-directory diff, allowing corrupted commit contents - (File: app/src/lib/git/apply.ts)

### Summary
The Morpho report's broken invariant is: an external state-changing event (Aave liquidation) is not reconciled with cached application state (Morpho's per-user balances) before that stale state is reused to authorize/perform another privileged action (a second liquidation), because the check relies on stored numbers instead of re-validating against ground truth at the moment of use. The Desktop analog is structurally the same pattern applied to partial commits: a user's line selection is captured against one snapshot of a file's diff, but `applyPatchToIndex` re-derives a **fresh** diff of the working directory at staging time and blindly re-applies the old, purely positional selection to it, with no check that the two diffs still describe the same content.

### Finding Description
When a user stages a subset of lines in a file, the UI computes an `ITextDiff` and a `DiffSelection` whose only state is a set of **line index numbers** (`divergingLines`) — it has no notion of the underlying text or a content hash: [1](#0-0) 

When the user commits, `createCommit` unstages everything and calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`: [2](#0-1) [3](#0-2) 

Critically, `applyPatchToIndex` does **not** reuse the diff that was shown to the user and against which the selection was made. It fetches a brand-new diff of the working directory right there, and feeds the (old) `file.selection` into `formatPatch` against this brand-new diff: [4](#0-3) 

`formatPatch` decides which lines to include purely by absolute index position in the (new) diff's hunks (`file.selection.isSelected(absoluteIndex)`), with no comparison to the diff the selection was originally derived from: [5](#0-4) 

The application is aware that diffs can change out from under a selection — `updateChangesWorkingDirectoryDiff` explicitly comments that "the diff might have changed dramatically since last we loaded it" when it recomputes `selectableLines` for the **UI-rendered** diff: [6](#0-5) 

but that reconciliation only happens for the diff used to redraw the UI. There is a **third**, independent fetch of the diff inside `applyPatchToIndex` at commit time that is never reconciled against anything — it simply trusts that the working directory hasn't changed since the selection was made, and reapplies the old index-based selection to whatever new hunk layout it gets back.

This is directly analogous to Morpho trusting `1 ETH / 2500 DAI` balances without re-checking the live Aave position before allowing a second liquidation: Desktop trusts an old, position-based selection without re-checking it against the diff it is about to actually patch with.

### Impact Explanation
If the working directory changes between when the user reviews/selects lines and the moment `applyPatchToIndex` runs (which is an `await`-separated async gap, not instantaneous), the new diff's hunks can have different line counts/offsets than the diff the selection was computed against. Because `DiffSelection.isSelected()` matches purely by numeric line index, the same index in the new hunk layout can now correspond to a *different line of content* — meaning:
- Lines the user never reviewed or intended to commit can be silently included in the commit.
- Lines the user did select for inclusion can be silently dropped.

This is a "silent corruption of what the user commits" impact: the resulting commit does not match what was shown to and approved by the user, without any error or warning. A realistic trigger for the working-directory change during this window is Git LFS smudge/clean filtering (LFS support exists in this codebase, `app/src/lib/git/lfs.ts`), where a tracked file's on-disk content can transition between a pointer file and its real content asynchronously relative to when Desktop computed the diff/selection shown to the user, or any other external process (editor auto-format/auto-save, background lint/build step, another Git client) touching the file in that window.

### Likelihood Explanation
Likelihood is bounded by the size of the async gap between the last diff render and the `applyPatchToIndex` diff fetch, and by whether something is actively touching the working tree during that window (LFS smudge completion, autosave, formatter-on-save, concurrent git operations). It requires no elevated privileges and no user-visible confirmation is bypassed — the corruption is invisible because Desktop never re-diffs against the exact content the user approved before generating the patch. It does not require local/physical access beyond normal use of Desktop with a repository whose content is expected to change slightly around checkout/staging (a common condition with LFS-tracked repos or repos with format-on-save tooling).

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-fetch (or reuse a cached, still-valid) diff and validate that it is unchanged relative to the diff the `DiffSelection` was derived from (e.g., via a content hash or unchanged hunk boundaries) before applying the stored line selection. If the diff has changed, abort staging that file and force the UI to refresh the diff/selection for user re-confirmation rather than silently reapplying stale, position-based selection to new content.

### Proof of Concept
1. Open a repository in GitHub Desktop that is tracked by Git LFS (or has a background process that touches files, e.g. an editor "format on save").
2. In the Changes view, select a modified file and select only some lines of the diff for inclusion in the commit (`DiffSelectionType.Partial`), leaving the rest deselected.
3. Before clicking "Commit," trigger an external change to the same file (e.g., allow an LFS smudge to complete, or have an editor save the file with formatting changes) that shifts line offsets without necessarily being reflected in a new diff render in Desktop's UI within the same tick.
4. Click "Commit." `createCommit` → `stageFiles` → `applyPatchToIndex` fetches a brand-new diff via `getWorkingDirectoryDiff` [7](#0-6)  and calls `formatPatch(file, diff)` using the *old* `DiffSelection` object, whose `isSelected(absoluteIndex)` checks are purely positional [1](#0-0) .
5. Inspect the resulting commit: it contains lines/content that differ from what was shown as "selected" in the UI at the time the user made their selection, without any warning from Desktop.

  public isSelected(lineIndex: number): boolean {

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {

        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
