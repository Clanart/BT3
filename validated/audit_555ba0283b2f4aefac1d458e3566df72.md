### Title
`VWAPOracle.recordSpread` normalizes output amounts with a live, attacker-controlled `IERC20Metadata.decimals()` call, letting a filler poison the cumulative spread oracle - ([File: evm/src/utils/VWAPOracle.sol])

### Summary
`VWAPOracle` maintains a cumulative, volume-weighted spread average per `(sourceChain, token)` that other Hyperbridge intent logic treats as a trust signal (comments in `sdk/packages/simplex/src/strategies/fx.ts` explicitly describe a "price guard" that exists to stop "a manipulated pool understating the value" from shrinking reorg-protection depth). Like the external report's `virtualPrice`, `spread()` is meant to be a slow-moving, trustworthy running average. But `recordSpread` normalizes the **output** token amount using `IERC20Metadata(outputToken).decimals()` fetched live on every call, while the **input** token's decimals come from a governance-cached, immutable mapping. This asymmetry mirrors the `setPrecisionMultiplier` bug: one side of the price computation is a stable, trusted constant, and the other is a value an unprivileged party fully controls and can vary call-to-call.

### Finding Description
`recordSpread` is restricted only to `_intentGateway` [1](#0-0) , but the intent gateway's fill flow lets an order's filler/creator choose the input/output token addresses and amounts for the intent. For a same-token swap, this contract computes:

- `inputDecimals` from a governance-set, cached mapping `_tokenDecimals[sourceChainHash][inputToken]` [2](#0-1) 
- `outputDecimals` from a **live external call** `IERC20Metadata(outputToken).decimals()` [3](#0-2) 

Both are then used to normalize amounts to 18 decimals and compute `spreadBps`, which feeds a running weighted average (`_updateCumulativeSpread`) that never resets and is exposed via `spread()` [4](#0-3) , [5](#0-4) , [6](#0-5) .

Because `outputToken` is not restricted to a governance-registered/whitelisted asset list inside this contract (the code accepts any address and calls `decimals()` on it directly), an attacker who controls the ERC20 contract used as `outputToken` can implement `decimals()` to return an arbitrary, even call-dependent, value (e.g., alternating 6 and 24). This is functionally identical to the report's `setPrecisionMultiplier(uint256)` — a "precision multiplier" that a malicious/self-interested actor can flip at will, corrupting the derived per-fill `spreadBps` and hence the cumulative `weightedSpreadSum` / `totalVolume` state that other callers assume is monotonic/trustworthy over time.

Existing guards do not stop this:
- The `restrict(_intentGateway)` modifier only authenticates the *caller* (the gateway contract), not the *content* (token addresses/amounts) of the intent being settled.
- `_tokenDecimals` is cached and governance-controlled for the **source** side only — there is no equivalent cache or allowlist for the **destination** token, and no sanity bound (e.g. `decimals in [6,18]`, or a fixed snapshot at intent-creation time) is applied before the live call.
- There's no economic bound tying `outputToken`'s legitimacy to `inputToken` beyond "same token" naming in the doc comment — the contract has no cross-chain address/token-identity check enforcing that `outputToken` is actually the destination-chain representation of `inputToken`.

### Impact Explanation
This corrupts a value ("cumulative weighted spread"/`spread()`) that downstream logic treats as monotonic-ish, slow-drifting ground truth for anti-manipulation checks (per the `fx.ts` comment describing exactly this class of guard). An attacker can:
1. Self-fill (or collude to fill) their own intents using a malicious ERC20 as `outputToken`.
2. Vary the returned `decimals()` per call to inject extreme, attacker-chosen `spreadBps` values into the weighted sum.
3. Repeatedly do this to swing `spread(sourceChain, inputToken)` to any value they want, cheaply (no real capital movement needed beyond whatever amount is nominally recorded), since `weightedSpreadSum`/`totalVolume` are simple additive accumulators with no decay, no per-fill caps, and no plausibility bound.

Anywhere `spread()` is consulted as a manipulation/reorg-depth safety signal, this lets an attacker manufacture a false "healthy market" (or false "manipulated market") reading to either loosen anti-fraud checks (enabling shallow-confirmation acceptance of a bad fill) or spuriously halt/degrade a competitor's legitimate order flow — a logic attack on the intent-settlement trust chain, matching the bounty's "logic attacks" / "false state acceptance" category.

### Likelihood Explanation
Medium-to-high: the only precondition is that the attacker can get `recordSpread` invoked with an `outputToken` address they control (a filler filling their own intent, or a filler using a token they deployed). No relayer, prover, or governance compromise is required — this is reachable through the ordinary, permissionless intent-fill path once `_intentGateway` calls `recordSpread` with attacker-supplied token/amount data, which is the documented, intended calling pattern of this oracle.

### Recommendation
- Cache destination-chain decimals the same way source-chain decimals are cached (governance-set, immutable mapping), instead of calling `IERC20Metadata(outputToken).decimals()` live inside `recordSpread`.
- Alternatively, snapshot decimals once at token registration/whitelisting time and validate `outputToken` against an allowlist tied to the registered `inputToken` (enforcing the "same-token" invariant the contract's own doc comment claims).
- Add sanity bounds/decay/per-fill caps to the cumulative spread accumulator so a single or repeated manipulated call cannot swing `spread()` arbitrarily.

### Proof of Concept
Conceptual PoC (mirrors the reported `setPrecisionMultiplier` pattern):
```solidity
contract EvilToken {
    uint8 public callCount;
    function decimals() external returns (uint8) {
        callCount++;
        // Return a small value first call, huge value next call —
        // recordSpread calls decimals() fresh every time, so the
        // normalized amount (and thus spreadBps) can be swung wildly.
        return callCount % 2 == 0 ? 2 : 24;
    }
    // ... rest of minimal ERC20 stubbed out ...
}

// Attacker deploys EvilToken and creates/fills same-token intents through
// IntentGatewayV2 using EvilToken as `outputToken`. Each settled intent calls
// VWAPOracle.recordSpread(...), which internally does:
//   outputDecimals = IERC20Metadata(outputToken).decimals();
// Because EvilToken.decimals() output varies per call, `outputAmountNormalized`
// and hence `spreadBps` swings unpredictably and attacker-chosen across fills,
// corrupting `_tokenSpreads[sourceChainHash][inputToken]` and the value
// returned by `spread(sourceChain, inputToken)` for every future reader.
```

        CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];

    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;
        data.totalVolume += volume;
