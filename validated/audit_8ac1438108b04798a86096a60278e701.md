### Title
Unauthenticated `ReceivedOutput` deserialization permits reporting spoofed, unspendable Bitcoin funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an attacker-controlled scalar offset, `TxOut`, and `OutPoint` without verifying that the referenced UTXO exists or that its on-chain contents match the supplied `TxOut`. [1](#0-0)  A forged serialized object can therefore report an arbitrary Bitcoin balance as received while naming a nonexistent or unrelated outpoint.

### Finding Description
A legitimate `ReceivedOutput` is produced by `Scanner::scan_transaction`, which binds the output to the transaction’s computed TXID and vout. [2](#0-1)  The deserializer bypasses that construction path and directly trusts all three fields. [3](#0-2) 

`SignableTransaction::new` then trusts the supplied `TxOut` value for wallet balance accounting and the supplied `OutPoint` as the transaction input. [4](#0-3)  When constructing the signing machine, it only verifies that `keys.offset(offset).group_key()` produces the supplied `script_pubkey`; it does not resolve the `OutPoint` or compare the encoded `TxOut` against the actual UTXO. [5](#0-4) 

### Impact Explanation
An unprivileged party can feed bytes to `ReceivedOutput::read` describing a wallet-owned Taproot script, an arbitrary amount, and a nonexistent `OutPoint`. The wallet layer can count this as received value and construct a transaction consuming it, but Bitcoin consensus will reject the transaction if the outpoint is absent, already spent, or backed by different `TxOut` data.

This satisfies the “funds reported received that are not spendable” impact class. If the outpoint exists but the supplied amount is false, the Taproot signature is generated against the attacker-supplied `Prevouts::All` data and remains unspendable against the real UTXO set. [6](#0-5) 

### Likelihood Explanation
The attacker only needs the target’s Taproot script and the ability to supply serialized `ReceivedOutput` bytes. Both the encoded scalar and Bitcoin consensus objects are public, canonical inputs. No private key, validator privilege, malformed curve point, hash collision, or protocol participant collusion is required.

Exploitation depends on a caller accepting untrusted serialized `ReceivedOutput` values rather than only consuming objects freshly returned by `Scanner::scan_transaction`. The public `read` API makes this reachable. [7](#0-6) 

### Recommendation
Do not expose `ReceivedOutput::read` as an unauthenticated constructor for spendable wallet state. Require deserialization to be followed by chain validation that resolves `outpoint` and proves the returned UTXO equals the encoded `TxOut`, including `script_pubkey` and amount. Prefer a constructor such as `ReceivedOutput::read_and_verify(reader, chain_view)` or restrict deserialization to trusted storage.

At minimum, `SignableTransaction::new` or `SignableTransaction::multisig` should receive verified previous outputs rather than trusting the embedded `TxOut`.

### Proof of Concept
Conceptually, construct serialized bytes containing:

```rust
offset = Scalar::ZERO;
output = TxOut {
  value: Amount::from_sat(1_000_000_000),
  script_pubkey: p2tr_script_buf(victim_group_key).unwrap(),
};
outpoint = OutPoint::default(); // Nonexistent null TXID input
```

Then pass the concatenated canonical encodings to `ReceivedOutput::read`. The object is accepted. `SignableTransaction::new` counts `1_000_000_000` sats and uses `OutPoint::default()` as an input, while `multisig` succeeds because the supplied script matches the zero-offset group key. The resulting signature commits to the forged prevout list via `Prevouts::All`, but the transaction cannot spend any real Bitcoin UTXO. [8](#0-7)
