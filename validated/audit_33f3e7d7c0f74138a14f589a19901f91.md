### Title
Missing zero-check on governance-controlled `GasTarget` causes division-by-zero panic in KIP-71 base fee calculation - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` explicitly guards one governance-controlled divisor (`BaseFeeDenominator`) against a zero value to avoid a panic, but fails to apply the same protection to another divisor used in the exact same formula, `GasTarget`. Since `GasTarget` is a governance parameter that can be set to any `uint64` value (including `0`) without validation, an attacker/governor can force every full node to panic while computing the next block's base fee, halting the chain. This mirrors the GMX finding: a bounded/defensive technique (the zero-guard for `BaseFeeDenominator`) was applied inconsistently to a closely related arithmetic operand (`GasTarget`) used later in the same computation.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee using both `BaseFeeDenominator` and `GasTarget` as divisors: [1](#0-0) 

Note the explicit zero-guard for `BaseFeeDenominator`:
```go
var baseFeeDenominator *big.Int
if kc.BaseFeeDenominator == 0 {
    // To avoid panic, set the fluctuation range small
    baseFeeDenominator = new(big.Int).SetUint64(64)
} else {
    baseFeeDenominator = new(big.Int).SetUint64(kc.BaseFeeDenominator)
}
``` [2](#0-1) 

However, `gasTarget` receives no such treatment and is used directly as a divisor further down in both the "gas used above target" and "gas used below target" branches: [3](#0-2) 

Specifically:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // <-- panics if gasTarget == 0
``` [4](#0-3) 
and the symmetric branch: [5](#0-4) 

`GasTarget` is a fully governable parameter (`Kip71GasTarget`) whose format checker performs no bound/zero validation, only canonicalizing it to `uint64`: [6](#0-5) 

The only branch that avoids the division is `parentGasUsed == gasTarget`, which requires `parentGasUsed` to also be `0`; any block with nonzero gas usage after `GasTarget` is set to `0` falls into the `parentGasUsed > gasTarget` branch and divides by zero. `math/big.Int.Div` panics on division by zero in Go, so this crashes the node process (not merely returning an error).

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked by every node during block header construction/validation for every block once Magma is active (used in header chain building, gas price oracle, and block validation). A single governance vote setting `Kip71GasTarget` (or `kip71.gastarget`) to `0` — reachable through the standard governance parameter update mechanism, which any governing node/participant can invoke per the protocol's governance rules — will cause a chain-wide panic/crash on the next block with nonzero gas usage, effectively halting the network (denial of service across all consensus/full nodes). This is a critical availability impact reachable through a standard, in-scope governance parameter change.

### Likelihood Explanation
Likelihood depends on whether the governance vote validation layer independently rejects `GasTarget = 0` elsewhere (e.g. at proposal application time) before it reaches `NextMagmaBlockBaseFee`. Based on the code reviewed, the `FormatChecker` for `Kip71GasTarget` is `noopFormatChecker`, i.e., it performs no validation, unlike the explicit zero-tolerant handling given to `BaseFeeDenominator` in the same function. This asymmetry (one divisor defended, the other not) is the exact bug class highlighted in the source report. Setting a governance parameter typically requires governance authority (via `GoverningNode` or on-chain vote depending on `GovernanceMode`), so likelihood is bounded by governance access rather than by an arbitrary unprivileged transaction — but it remains within the listed in-scope category "governance parameters."

### Recommendation
Apply the same defensive fallback used for `BaseFeeDenominator` to `GasTarget` in `NextMagmaBlockBaseFee` (e.g., treat `GasTarget == 0` as an invalid/degenerate case and substitute a safe default, or reject the block/computation gracefully), and/or add explicit validation in the governance parameter's `FormatChecker` for `Kip71GasTarget` to reject `0` before it can be persisted as an active parameter.

### Proof of Concept
1. Via governance, set `kip71.gastarget` (`Kip71GasTarget`) to `0`. The parameter passes validation because its `FormatChecker` is `noopFormatChecker` [6](#0-5) .
2. Once the parameter becomes active and Magma is enabled, any block with `parentGasUsed > 0` triggers the `parentGasUsed > gasTarget` branch in `NextMagmaBlockBaseFee`.
3. The code executes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, which is a division by zero in `math/big`, causing the node process to panic [7](#0-6) .
4. All nodes computing this header field (block generation, header validation, gas price oracle in `feehistory.go`/`gasprice.go`) crash simultaneously, halting the chain.
