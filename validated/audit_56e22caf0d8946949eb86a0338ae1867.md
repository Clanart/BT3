### Title
`IntentGatewayV2` fund-custody contract has no pause/circuit-breaker, unlike `HyperFungibleToken`/`WrappedHyperFungibleToken` which gate all transfer paths with `whenNotPaused` - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` is the escrow/settlement contract for the Intent Gateway protocol: it custodies user input tokens (`placeOrder`), releases them to solvers/fillers (`fillOrder`, `onAccept`→`withdraw`), and refunds them on cancellation (`cancelOrder`). Unlike `HyperFungibleToken` and `WrappedHyperFungibleToken`, which inherit OpenZeppelin `Pausable` and gate every fund-moving entrypoint (`send`, `onAccept`, `onPostRequestTimeout`, `transfer`, `transferFrom`) with `whenNotPaused`, `IntentGatewayV2` and its full inheritance chain (`IntentsBase`, `IntrinsicIntents`, `ExtrinsicIntents`) contain no `Pausable` import, no `whenNotPaused` modifier, and no pause/unpause function anywhere. The contract even documents an `_owner` field explicitly reserved "for future upgrade-gated actions (e.g. pausing)" that was never wired to any actual pause mechanism. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The report's core broken invariant is: *a fund-custody contract inherits/plans for a pause mechanism but never applies it to its money-moving functions, so an emergency-pause response is unavailable exactly where it is most needed.*

In this repository, `HyperFungibleToken` and `WrappedHyperFungibleToken` demonstrate the correct pattern: `pause()`/`unpause()` are `onlyOwner`-gated, and every function that moves value or triggers a mint/burn/transfer is annotated `whenNotPaused`: [4](#0-3) [5](#0-4) [6](#0-5) 

`IntentGatewayV2`, however, is a much larger custody surface — it escrows arbitrary ERC20/native amounts at `placeOrder`, releases them to solvers at fill time, and settles/refunds them via the ISMP `onAccept` → `withdraw` path — yet has zero pause capability anywhere in its inheritance tree (`IntentsBase`, `IntrinsicIntents`, `ExtrinsicIntents`): [7](#0-6) [8](#0-7) [9](#0-8) 

The contract's own comment acknowledges pausing was intended as a future control point tied to the `_owner` field, but no such control was ever implemented: [10](#0-9) 

This mirrors the external report's exact bug class: `KangarooVault` imported `PauseModifier` but omitted it from its fund-moving functions while its sibling `LiquidityPool` correctly applied `whenNotPaused` everywhere. Here, the protocol's own token-bridging app (`HyperFungibleToken`) demonstrates the intended pattern, but the higher-value, more complex `IntentGatewayV2` escrow/settlement contract has no equivalent safety valve at all.

### Impact Explanation
If a bug or exploit is discovered in any part of the intent fill/settlement/cancellation logic (e.g. a fee-computation error, an authentication bypass in `onAccept`/`withdraw`, or a cross-chain replay in the `RedeemEscrow`/`RefundEscrow` path), the protocol has no on/off switch to halt `placeOrder`, `fillOrder`, `cancelOrder`, or `onAccept` on `IntentGatewayV2` while a fix is prepared and deployed. Every other bridged-asset contract in this repo (`HyperFungibleToken`, `WrappedHyperFungibleToken`) can be paused instantly by the owner to stop the bleeding, but the intents escrow — which is the largest and most complex value-custody surface in the codebase — cannot be. This directly maps to the bounty's "stealing or loss of funds" category: during an active incident, funds continue to be extractable/drainable from escrow with no operational mitigation available, unlike the equivalent token-bridge contracts.

### Likelihood Explanation
This is not a hypothetical: `IntentGatewayV2` is a proxy-upgradeable, publicly deployed contract (`initialize`/`Initializable`) that holds live escrowed balances from `placeOrder` at all times, and its `fillOrder`/`cancelOrder`/`onAccept` entrypoints are called by unprivileged solvers and users continuously. The absence of a pause guard is unconditional — it applies regardless of any other bug being present — and the risk materializes as soon as any other issue in the intents settlement path needs an emergency stop. Given the contract's own comment references pausing as an intended-but-missing control, this is a design gap rather than a theoretical edge case.

### Recommendation
Add an OpenZeppelin `Pausable` (or equivalent) circuit breaker to `IntentGatewayV2`, gated by the existing `_owner` (or a proper admin/governance role), and apply `whenNotPaused` to all fund-moving entrypoints: `placeOrder`, `fillOrder`, `cancelOrder`, and `onAccept` (at minimum the branches that call `withdraw`). Mirror the pattern already used in `HyperFungibleToken`/`WrappedHyperFungibleToken` (`pause()`/`unpause()` restricted to the admin, `whenNotPaused` on every value-transferring function) so that an emergency response capability exists uniformly across all bridged-value contracts in the protocol.

### Proof of Concept
1. `IntentGatewayV2` is deployed and initialized with escrowed liquidity from many users via `placeOrder` (escrow custody, no pause guard):
`evm/src/apps/IntentGatewayV2.sol` lines 61-75, 413-491 — no `Pausable`/`whenNotPaused` anywhere in the file or its parents (`IntentsBase`, `IntrinsicIntents`, `ExtrinsicIntents`).
2. Assume a logic bug is found (independent of this report) in the fill/settlement/cancel path that allows an attacker to drain escrow (e.g. via `fillOrder` → `onAccept` → `withdraw`).
3. The protocol admin has no `pause()` function to call on `IntentGatewayV2` to halt `fillOrder`/`cancelOrder`/`onAccept` while investigating/patching, in contrast to `HyperFungibleToken.pause()` which would immediately block `send`/`onAccept`/`onPostRequestTimeout`/`transfer`/`transferFrom`:
`sdk/packages/core/contracts/apps/HyperFungibleToken.sol` lines 211-223, 264, 320-325, 336-343.
4. As a result, an active exploit against the escrow/settlement logic can continue draining funds for as long as it takes to prepare and ship a code upgrade, whereas the equivalent risk on the token-bridge contracts could be stopped instantly — exactly the loss-amplification scenario described in the seed report.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }

        if (_params.priceOracle != address(0)) {
            IIntentPriceOracle(_params.priceOracle)
                .recordSpread(commitment, order.source, order.inputs, options.outputs);
        }
    }

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
}
