# Analog Analysis: ProtoJSON `oneof`/Duplicate-Field Invariant Bypass via `null` Values

### Title
ProtoJSON parser skips oneof-exclusivity/duplicate-key verification for `null`-valued occurrences, allowing an ambiguous field to bypass the "already set" invariant - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
The SAML report's failed invariant is: *the code path that validates integrity (signature check over one XPath-located node) and the code path that determines the effective value used later (a different, independent lookup) are not cross-checked*, so an attacker can make the "verified" node and the "used" node diverge. In the ProtoJSON parser's `ParseField`, the analogous invariant is "a `oneof` may have at most one member present in the JSON payload, and this must be enforced unconditionally." The enforcement (`RecordAsSeen`) is the "verification" step; the actual field assignment is the "extraction" step. For fields whose JSON value is `null`, the code returns before ever calling the verification step, silently decoupling verification from extraction for that occurrence.

### Finding Description
`ParseField` computes the target field, and *before* recording that the field/oneof was observed, it special-cases `null`: [1](#0-0) 

```
// Any `null` values eagerly no-op, except for exactly the special cases of
// google.protobuf.Value message and google.protobuf.NullValue enum.
// Note that spec behavior is that we should do duplicate key checking in the
// case of a null value, but this implementation currently does not
// (b/519557203).
if (lex.Peek(JsonLexer::kNull)) {
  MessageType type = ClassifyMessage(Traits::FieldTypeName(*field));
  if (type != MessageType::kValue && type != MessageType::kNull) {
    return lex.Expect("null");
  }
}

SeenState seen = Traits::RecordAsSeen(*field, msg);

if (seen == SeenState::kOneofAlreadySeen ||
    (seen == SeenState::kFieldAlreadySeen &&
     !lex.options().allow_legacy_nonconformant_behavior)) {
  return lex.Invalid(...);
}
```

The `return lex.Expect("null")` for a `null`-valued, non-`Value`/`NullValue` field occurs *before* `Traits::RecordAsSeen` is ever invoked, so that occurrence is never marked "seen." This is exactly the pattern in the report: an independent, unchecked lookup (`lex.Peek(JsonLexer::kNull)` short-circuit) determines what happens to the current key, while the state that other keys later consult (`RecordAsSeen`'s internal oneof/field-seen bitmap) is left untouched — the two mechanisms are not cross-validated. The comment explicitly documents this as a known deviation from spec behavior (tracked as `b/519557203`), i.e., protobuf's own maintainers acknowledge the check does not fire in this case.

Consequence: if a `oneof` field `case_a` is presented first with the JSON value `null`, and later in the same object a *different* member of the same `oneof` (`case_b`) is presented with a real value, the exclusivity check that should reject "more than one oneof member present in this JSON text" never triggers, because `case_a`'s occurrence was invisible to `RecordAsSeen`. The parser accepts a JSON object that textually presents two different oneof case keys — a shape that ProtoJSON is specifically designed to reject unconditionally (unlike the deliberately permissive wire-format "last one wins" semantics for oneofs).

### Impact Explanation
Downstream consumers (API gateways, security filters, or logging/auditing code) may rely on ProtoJSON's documented guarantee that a conforming payload can present at most one member of a `oneof` in its JSON text, using this as a coarse sanity/anti-ambiguity check on attacker-controlled input before or after protobuf parsing. This bug allows an attacker-controlled bounded ProtoJSON payload to present two oneof-member keys simultaneously (one masked by `null`) while still being accepted by `JsonFormat`/upb JSON parsing, defeating that invariant. This is a genuine integrity-check bypass reachable purely through the public JSON parsing API, matching the report's "verification and extraction diverge, allowing acceptance of data that should have been rejected" pattern.

The blast radius is narrower than the SAML CVE: no attacker-controlled value is smuggled into a different field than what was "verified" (the `null` occurrence never writes a value), so it does not by itself cause silent data substitution comparable to identity spoofing. The primary impact is a parser-conformance/integrity violation: acceptance of syntactically ambiguous "conflicting oneof" JSON that should be rejected, which can matter for any code treating oneof-exclusivity as a security-relevant validation gate (e.g., detecting duplicate/conflicting authorization-selector fields in a JSON-based protocol layered over protobuf).

### Likelihood Explanation
High reachability: this is triggerable by any ordinary client calling the public `JsonFormat`/ProtoJSON parse APIs (C++ `json/internal/parser.cc`, and any binding sharing this logic) with a bounded, well-formed JSON payload containing a `oneof` with at least two members, no special schema requirements, no privileged access. The bug is explicitly acknowledged in the source comment (`b/519557203`), confirming it is a currently-unaddressed known gap rather than a hypothetical.

### Recommendation
Call `Traits::RecordAsSeen(*field, msg)` (or an equivalent "seen" registration) for `null`-valued field occurrences as well, before the early return, so oneof-exclusivity and duplicate-key checks are enforced uniformly regardless of whether the JSON value is `null`. At minimum, fix the identified gap tracked internally as `b/519557203`.

### Proof of Concept
Given a proto3 message with a `oneof` `test_oneof { string case_a = 1; string case_b = 2; }`, submit the following JSON to `JsonFormat.Parser.merge` / `util::JsonStringToMessage` (or any ProtoJSON parsing entry point using `src/google/protobuf/json/internal/parser.cc`):

```json
{"caseA": null, "caseB": "attacker-value"}
```

Expected (per ProtoJSON spec / other duplicate-oneof cases): parsing should be rejected because two members of the same `oneof` are present in the text — this is confirmed by the unconditional `kOneofAlreadySeen` rejection path in `ParseField` (line 1261) used for the non-null case, e.g. `{"caseA": "x", "caseB": "y"}` is rejected today. With `caseA` set to `null` instead, `RecordAsSeen` is never invoked for `caseA` (early return at line ~1252-1254), so `caseB` is treated as the first (and only) occurrence in the oneof, and parsing succeeds with `case_b` set — silently accepting a payload shape that is otherwise defined as invalid.
