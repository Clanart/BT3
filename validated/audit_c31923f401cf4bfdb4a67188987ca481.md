## Title
Unescaped filenames in `formatPatchHeader` allow diff-header injection when applying/discarding patches — (File: `app/src/lib/patch-formatter.ts`)

### Summary
`formatPatchHeader` builds a GNU unified-diff header by naively interpolating raw file paths (`a/${from}`, `b/${to}`) into a template string, with no escaping/quoting of characters that are structurally significant in the unified-diff format (most notably newline `\n`). This function is the direct producer of the patch text that Desktop feeds as **raw stdin** to `git apply --cached` (`applyPatchToIndex`) and `git apply` (`discardChangesFromSelection`) — contexts where newlines are meaningful delimiters, unlike the argv-based `git()` calls used elsewhere in the app.

### Finding Description
`formatPatchHeader` is called with `from`/`to` values taken directly from `WorkingDirectoryFileChange.path` / `file.status.oldPath` [1](#0-0) , which are themselves populated verbatim from `git status --porcelain=2 -z` output parsed by `status-parser.ts`. That parser is explicitly NUL-delimited so that filenames may legitimately contain embedded newlines and other special bytes — the repo's own test suite documents this as intended behavior: `parses a path which includes a newline` [2](#0-1) .

`formatPatchHeader` itself performs no sanitization before embedding these paths into the header: [3](#0-2) 

The resulting patch string (header + hunks) is passed as `stdin` directly to the `git apply` process, not as an argv element: [4](#0-3) [5](#0-4) 

Because `git apply` parses its stdin line-by-line to find `---`/`+++`/`@@` markers, a repository containing a file whose path embeds a newline (and crafted trailing content resembling `+++ b/<other>` or `@@ ... @@`) can cause the header Desktop constructs to be misinterpreted: extra bogus header/hunk-boundary lines are injected into the patch text that `git apply` will parse as legitimate structure. This is exactly the class of bug real `git diff`/`git status` avoid by **quoting** paths containing such characters (e.g., emitting `"a/foo\nbar"` with `\n` C-style escaped) — no equivalent quoting exists anywhere in this codebase (`quotePath`/`escapePath`/`core.quotepath` all absent).

This affects both partial-staging (`applyPatchToIndex` → `formatPatch`) and partial-discard (`discardChangesFromSelection` → `formatPatchToDiscardChanges`) flows, both of which are driven by user actions on attacker-supplied repository content (line-by-line stage/discard in the Changes view).

### Impact Explanation
If an attacker crafts a file whose name (as reported by `git status`) contains a newline plus content mimicking diff syntax, a user who performs a *partial* stage or discard on that file (or on files whose selection interacts with the injected content) could have `git apply` construct/modify the index or working tree in a way that differs from what the Desktop UI displayed as selected. This falls squarely into "silent corruption of what the user commits or pushes" — either lines the user did not intend to stage get staged, or discard operations affect the wrong hunks/files, without any error being surfaced (since a well-formed-if-corrupted patch will apply successfully).

### Likelihood Explanation
This requires: (1) a filesystem that permits newline-containing filenames (Linux/macOS — not Windows/NTFS), and (2) the user to invoke *partial* selection (line-level stage/discard) on the affected file, since full-file staging goes through `update-index`/`add` (argv-based, unaffected) rather than through `formatPatchHeader`. This narrows exploitability but does not eliminate it, since partial staging/discarding of individual hunks is a core, commonly used Desktop feature.

### Recommendation
Quote/escape paths in `formatPatchHeader` the same way `git` itself does before embedding them into unified-diff header text — at minimum, reject or C-style-escape control characters (especially `\n`, `\r`, and `"`) in `from`/`to` before formatting, mirroring git's own `core.quotepath` behavior, so that a single logical path can never expand into multiple lines within the generated patch text that is later parsed by `git apply`.

### Proof of Concept
1. On Linux/macOS, create a git repo containing a tracked text file whose name contains an embedded newline, e.g. `printf 'foo\n+++ b/other.txt\n@@ -1,1 +1,1 @@\n-old\n+injected\nbar' > "$(printf 'foo\n+++ b/other.txt\n@@ -1,1 +1,1 @@\n-old\n+injected\nbar')"` (filesystem permitting), commit it, then modify it and `other.txt`.
2. Open the repo in Desktop; in the Changes view select only some lines of the crafted file for staging (partial selection), forcing the `applyPatchToIndex` → `formatPatch` → `formatPatchHeader` code path.
3. Inspect the generated patch text (add a temporary `console.log(patch)` in `applyPatchToIndex` before the `git(...)` call, or assert on `formatPatch`'s return value in a unit test) and confirm it contains an injected `+++ b/other.txt` / `@@ ... @@` sequence inside what should be a single header line for the crafted file.
4. Verify with `git apply --check --cached -` fed this patch that it targets/affects `other.txt` content unexpectedly, demonstrating the header/hunk boundary can be forged purely via the filename, independent of the actual selection the user made in the UI.

```typescript
function formatPatchHeader(from: string | null, to: string | null): string {
  // https://en.wikipedia.org/wiki/Diff_utility
  //
  // > At the beginning of the patch is the file information, including the full
  // > path and a time stamp delimited by a tab character.
  // >
  // > [...] the original file is preceded by "---" and the new file is preceded
  // > by "+++".
  //
  // We skip the time stamp to match git
  const fromPath = from ? `a/${from}` : '/dev/null'
  const toPath = to ? `b/${to}` : '/dev/null'

  return `--- ${fromPath}\n+++ ${toPath}\n`
}
```

```typescript
function formatPatchHeaderForFile(file: WorkingDirectoryFileChange) {
  switch (file.status.kind) {
    case AppFileStatusKind.New:
    case AppFileStatusKind.Untracked:
      return formatPatchHeader(null, file.path)

    // One might initially believe that renamed files should diff
    // against their old path. This is, after all, how git diff
    // does it right after a rename. But if we're creating a patch
    // to be applied along with a rename we must target the renamed
    // file.
    case AppFileStatusKind.Renamed:
    case AppFileStatusKind.Deleted:
    case AppFileStatusKind.Modified:
    case AppFileStatusKind.Copied:
    // We should not have the ability to format a file that's marked as
    // conflicted without more information about it's current state.
    // I'd like to get to a point where `WorkingDirectoryFileChange` can be
    // differentiated between ordinary, renamed/copied and unmerged entries
    // and we can then verify the conflicted file is in a known good state but
    // that work needs to be done waaaaaaaay before we get to this point.
    case AppFileStatusKind.Conflicted:
      return formatPatchHeader(file.path, file.path)
```
