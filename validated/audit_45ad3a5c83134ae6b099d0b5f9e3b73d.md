### Title
Unrecoverable loss of user's excess native-token payment in `EvmHost` fee-swap flows — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert user-supplied `msg.value` into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, exactly mirroring the external report's pattern of an unprotected AMM swap embedded in a value-moving flow. Unlike the reported bug (missing `amountOutMinimum`), the concrete broken invariant here is a missing **refund path**: `swapETHForExactTokens` returns any unspent ETH to `msg.sender` of the swap call — which is `EvmHost` itself, not the end user who called `dispatch`/`fundRequest`. There is no code in these functions that forwards the leftover ETH back to `_msgSender()`/`post.payer`, so any native token sent above what the router actually consumes for the exact fee amount is permanently and irrecoverably absorbed by the contract.

### Finding Description
In all three payable entrypoints:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) [2](#0-1) [3](#0-2) 

`recipient` for the token leg is `address(this)` (correct — the exact `feeToken` amount is credited to `EvmHost`), but the router's own logic for `swapETHForExactTokens` refunds the *unused ETH* to the caller of the router, i.e. `EvmHost`, not to the original depositor. `EvmHost` has a `receive()` fallback (confirmed present in the file, 2 matches for `receive()`), so that ETH is silently accepted into the contract's balance with no bookkeeping that ties it back to the depositor and no function that lets the depositor reclaim it.

The docs explicitly acknowledge this exposure but frame it only as a UX/estimation problem, not a fund-safety one:

> "Use the `quote()` view function from your frontend to estimate how much native token users need to send. **Do not call `quote()` in smart contract transactions.** It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks. Only use it off-chain for frontend fee estimation" [4](#0-3) 

Because `quote()` is only an off-chain estimate and is itself subject to sandwich/slippage risk, users are structurally forced to overpad `msg.value` to guarantee the on-chain `swapETHForExactTokens` call succeeds. Every wei of that pad that the router doesn't need is refunded to `EvmHost` and then trapped — the exact "capital loss from an unprotected swap" pattern in the seed report, except here it manifests as **guaranteed loss of the user's margin** rather than sandwich-driven slippage on the received amount.

### Impact Explanation
This is a direct, unprivileged loss-of-funds path reachable by any user calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native token payment: whatever excess native token they send above the router's exact-input requirement for `post.fee`/`get.fee`/`amount` is permanently locked into `EvmHost` with no recovery mechanism for the payer. This satisfies the bounty's "stealing or loss of funds" impact category and requires no malicious relayer, prover, or admin — only an ordinary user transaction using the documented native-payment flow.

### Likelihood Explanation
High. The documentation itself instructs integrators to estimate `msg.value` off-chain and warns that the estimate is imprecise and subject to slippage/sandwiching, meaning normal usage will routinely send slightly more ETH than the swap consumes. Every such transaction results in silent fund loss for the caller, with no error, revert, or event indicating funds were retained by the protocol instead of refunded.

### Recommendation
After `swapETHForExactTokens` returns, compute the actual ETH spent and refund any leftover `address(this).balance` delta to `_msgSender()` (or `post.payer`) via a low-level call, in each of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`. Alternatively, switch to `swapExactETHForTokens` with the amount computed via `quote()` plus a bounded slippage tolerance and explicitly return unused funds, ensuring native-token payers never lose more than the swap's realized rate.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` requires only 0.8 ether worth of WETH to acquire the exact `feeToken` amount, per current pool pricing.
2. `swapETHForExactTokens` executes, consumes 0.8 ether from the router, and refunds the remaining 0.2 ether to `msg.sender` of the router call, which is `EvmHost`.
3. `EvmHost.receive()` accepts the 0.2 ether into the contract's balance.
4. No code in `dispatch()` reads or forwards this refunded ETH back to the user; the transaction completes successfully, the request is dispatched, and the user has permanently lost 0.2 ether with no `event` or recovery path attributing it to them. [5](#0-4)

    /**
     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
```

### Payment Method Comparison

| Feature | Native Token | FeeToken (Recommended) |
|---------|-------------|------------------------|
| **Gas Cost** | Higher (includes swap) | Lower (no swap) |
| **Slippage** | Yes (Uniswap swap) | No |
| **Fee Calculation** | Approximate (subject to slippage) | Exact |
| **Token Approval** | Not required | Required  |
| **User Convenience** | High (users have native tokens) | Low (users need feeToken) |
| **Best For** | One-off transactions, user-facing apps | Frequent dispatches, cost optimization |
```
