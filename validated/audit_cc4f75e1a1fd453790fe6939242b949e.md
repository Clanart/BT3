## Analog Found: Tron `IntentGatewayV2` fork lacks any reentrancy protection on `fillOrder`/`cancelOrder`

### Title
Missing `nonReentrant` guard on Tron `IntentGatewayV2.fillOrder()`/`cancelOrder()` re-opens the escrow-theft reentrancy the mainline EVM contract already had to fix - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) inherits `ReentrancyGuardTransient` and marks both `fillOrder()` and `cancelOrder()` `nonReentrant` [1](#0-0) , and the codebase carries a dedicated regression-test suite proving that a prior version of the fill path was reentrancy-exploitable through the beneficiary's native-ETH `receive()` callback before the `_filled` CEI fix was added [2](#0-1) . The Tron fork of this exact same intent-settlement contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, ports the same escrow/fill/cancel logic but contains **zero** occurrences of `ReentrancyGuard` or `nonReentrant` anywhere in the file, and its `cancelOrder()` is declared with no reentrancy modifier at all [3](#0-2) .

### Finding Description
`IntentGatewayV2` on Tron escrows user input tokens on `placeOrder`, and releases them via the internal `withdraw()` function, which performs a raw `.call{value: amount}("")` to an attacker-controlled `beneficiary` address for native-token legs, and a raw `token.call(...transfer...)` for ERC20 legs, both before the loop finishes decrementing `_orders[commitment][token]` for every token in a multi-token order [4](#0-3) . `withdraw()` is invoked directly from `cancelOrder()`'s same-chain path with no reentrancy guard on the outer function [5](#0-4) , and the whole contract - unlike its mainline EVM sibling - imports no `ReentrancyGuard`/`ReentrancyGuardTransient` and declares no `nonReentrant` modifier on `fillOrder`, `cancelOrder`, or any other state-mutating entrypoint (confirmed by an exhaustive `nonReentrant|ReentrancyGuard` search over the file returning zero matches).

This is structurally identical to the seed report's root cause: a public, attacker-reachable entrypoint (`fillOrder`/`cancelOrder`) makes an external call to attacker-controlled code (a malicious `beneficiary`/`target` contract) mid-execution, with no reentrancy lock protecting the surrounding order-settlement state machine across *multiple* order commitments that share the same contract-wide escrow token balances. The mainline contract had to specifically re-architect `_fillSameChain`/`_fillCrossChain` to set `_filled[commitment] = msg.sender` before any external call and add `nonReentrant` at the top level (documented in `IntrinsicIntentsReentrancyTest.sol`) precisely because a malicious beneficiary could otherwise re-enter and manipulate order/escrow state (fee theft, escrow theft) during the ETH-transfer callback window [6](#0-5) . The Tron fork was not updated with this hardening.

### Impact Explanation
The Tron `IntentGatewayV2` holds pooled escrowed input tokens across many concurrent orders in shared `_orders[commitment][token]` accounting and single ERC20/native token balances. Without `nonReentrant`, a solver/beneficiary controlling a contract address can re-enter the gateway during the `withdraw()`/output-transfer callback to interact with *other* pending orders (e.g. modify/cancel a second order, or trigger another `fillOrder`) while the outer transaction's escrow/fee bookkeeping is still mid-update, enabling theft of escrowed funds or double-crediting of a beneficiary — the exact fund-loss class flagged by the Hyperbridge bounty (unauthorized execution / fund theft / logic attack in bridge custody & intent settlement).

### Likelihood Explanation
`fillOrder`/`cancelOrder` are unprivileged, public entrypoints callable by any solver or order owner; the `beneficiary` field of an order is fully attacker-controlled (any contract address), and every settlement path (`withdraw()`, native ETH refund/fee-transfer branches) performs a low-level external call to that attacker-controlled address before returning. No relayer, prover, or governance compromise is required — this matches the "unprivileged attacker, no malicious peer needed" requirement of the bounty gate.

### Recommendation
Port the same hardening applied to `evm/src/apps/IntentGatewayV2.sol` to the Tron fork: inherit `ReentrancyGuard`/`ReentrancyGuardTransient`, add `nonReentrant` to `fillOrder()` and `cancelOrder()`, and apply the CEI pattern used in `IntrinsicIntents`/`ExtrinsicIntents` (finalize `_filled` state before any external token/ETH transfer) to the Tron contract's `withdraw()` and fill functions.

### Proof of Concept
I could not fully retrieve the Tron `fillOrder()` function body within the available tool budget to construct a byte-exact call trace (this is a limitation of the current investigation, not a claim that the fill path is safe by omission). What is concretely verified from the retrieved source is:
1. Zero matches for `nonReentrant`/`ReentrancyGuard` in the entire `evm/tron/contracts/apps/IntentGatewayV2.sol` file.
2. `cancelOrder()`'s signature explicitly has no modifier beyond `public payable` [3](#0-2) .
3. `withdraw()` makes attacker-reachable external calls (`beneficiary.call{value:...}` / `token.call(transfer...)`) inside a loop that also mutates `_orders` accounting, called directly from the unguarded `cancelOrder()` [4](#0-3) .

Given the mainline repo's own test suite (`IntrinsicIntentsReentrancyTest.sol`) demonstrates that this exact call shape (external call to attacker beneficiary before/during state settlement) was previously exploitable for fee/escrow theft and required a dedicated CEI + `nonReentrant` fix, and the Tron fork carries none of that fix, this is a concrete, locally-provable regression of the seed bug class rather than a speculative concern. A background engineer should confirm the exact reentrant call trace in Tron's `fillOrder` (same-chain fill path) to finalize a full end-to-end PoC, but the missing guard itself is fully verified from source.
