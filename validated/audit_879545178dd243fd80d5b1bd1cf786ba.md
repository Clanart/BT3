## Title
Stale line-index diff selection can silently splice unrelated content into a commit when the working tree changes between diff render and staging - (File: `app/src/lib/git/apply.ts`)

## Summary
GitHub Desktop's partial-commit ("select individual lines") feature stores a user's line selection as pure line-index offsets (`DiffSelection`) rather than content-addressed hunks. When the commit is actually staged, `applyPatchToIndex` re-fetches a *fresh* diff of the working directory and reapplies the old index-based selection to it, with no check that the new diff's shape matches the one the user actually looked at. This mirrors the audited bug's root cause: two logically related steps (an "update" using state at time T1, and a "process"/apply step re-reading state at time T2) are bridged by a value (an index / an amount) that is trusted without revalidation, so if the underlying data changes between T1 and T2 the result is wrong — but unlike the Superform bug it doesn't just revert, it can silently apply the wrong subset of lines.

## Finding Description
`stageFiles` in [1](#0-0)  calls `applyPatchToIndex(repository, file)` for every file with a partial selection. That function fetches a brand-new diff of the current working directory content: [2](#0-1) 

and then builds the patch to apply with `formatPatch(file, diff)` in [3](#0-2) , which decides whether to include a line purely via `file.selection.isSelected(absoluteIndex)` — a boolean keyed on the numeric offset of the line inside the diff, not on the line's content or a stable hunk identity.

The `file.selection` object, however, was constructed earlier by the UI when the user reviewed the diff in the Changes view (`updateChangesWorkingDirectoryDiff`, [4](#0-3) ) and is carried unchanged into `_commitIncludedChanges` at commit time ( [5](#0-4) ). There is no re-diff-and-compare step before staging: `createCommit` → `stageFiles` → `applyPatchToIndex` simply takes whatever `selection` came with the `WorkingDirectoryFileChange` object and applies it against whatever the working tree looks like *now* ( [6](#0-5) ).

If the tracked file's content on disk changes between the moment the user made their line selection and the moment the commit executes (e.g. an editor autosave, a linter/formatter running on save, a build/watch tool, or any other process that rewrites the tracked file — all of which are ordinary, repo-driven tooling behaviors, not "malware"), the new diff's hunks can have different line counts, different `unifiedDiffStart`/`unifiedDiffEnd` boundaries, and different content at the same absolute indices. `formatPatch` has no way to detect this: it will happily map the stale line-index selection onto the new hunk lines and hand `git apply --cached` a syntactically valid patch built from the wrong lines. Because `git apply` only requires a well-formed unified diff, not that it match "the diff the user saw," this can succeed silently, producing a commit that includes/excludes different content than what the user selected in the UI — i.e., corruption of what the user actually commits, with no error and no revert.

This is the direct structural analog of the Superform issue: there, `dstAmount` (state at withdrawal-processing time) was checked against a stale `txData` amount (state captured at payload-update time) with a strict revert-on-mismatch; here, a stale line-index selection (state captured at diff-render time) is applied against a freshly-fetched diff (state at staging time) with *no* check at all — the failure mode is worse (silent corruption instead of a safe revert).

## Impact Explanation
A user could commit content they did not intend to commit — either omitting lines they meant to include, or including lines they meant to exclude — without any error surfaced by the app. This falls squarely under "silent corruption of what the user commits," one of the explicitly valid impact categories. Because it happens without warning, a user reviewing "clean" diffs before pushing could unknowingly publish unintended file contents (e.g. partially-reverted secrets, leftover debug lines, or lines from an unrelated hunk).

## Likelihood Explanation
This requires the working tree file to change between the user's line selection and the commit action — a state that Desktop's own architecture treats as routine (it is a single-page reactive app where diffs can be re-rendered any time `_loadStatus`/refresh runs while the Changes view is open, and users commonly run auto-formatters, linters-on-save, or build watchers while making commits). No hooks, elevated privileges, or attacker code execution are needed beyond a file being touched externally during the review→commit window, which is a normal, low-effort occurrence rather than a contrived scenario, but it is a probabilistic race rather than a deterministic, remotely-triggerable exploit, so likelihood is moderate rather than high, and I could not verify from the available code whether there is any status-refresh guard that discards a selection when the underlying diff shape changes (no such guard was found in `apply.ts`, `update-index.ts`, `patch-formatter.ts`, or the relevant `app-store.ts` methods reviewed).

## Recommendation
Before applying a partial-selection patch, re-validate that the diff used to build `file.selection` still matches the diff currently being staged (e.g., by comparing hunk boundaries/line counts, or by storing a content hash of the diff used for the selection and re-fetching+comparing it in `applyPatchToIndex`/`stageFiles`). If the newly fetched diff no longer matches, abort the partial stage for that file and force the UI to refresh the diff and require the user to re-confirm their selection, rather than silently reapplying stale line indices to new content.

## Proof of Concept
1. Open a tracked file with multiple changed lines in GitHub Desktop's Changes view and select only a subset of lines for the next commit (building a `DiffSelection` keyed to absolute line indices of the diff currently rendered).
2. While the commit message box is open (before clicking "Commit"), have an external process (editor autosave, formatter-on-save, or any file-watcher tooling operating on the same tracked file) rewrite the file so that hunk boundaries/line counts shift (e.g., add/remove a blank line earlier in the file).
3. Click "Commit". `_commitIncludedChanges` passes the *stale* `file.selection` object into `createCommit` → `stageFiles` → `applyPatchToIndex` ( [2](#0-1) ), which fetches the *new* diff and applies the old index-based selection to it via `formatPatch` ( [7](#0-6) ).
4. Because `git apply --cached` only validates the patch is well-formed, it succeeds, and the resulting commit contains a different set of lines than what the user selected in the UI, with no error shown.
