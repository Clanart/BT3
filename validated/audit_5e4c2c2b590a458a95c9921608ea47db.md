## Title
Ambiguous, non-standard regex parsing of remote/clone URLs in `parseRemote` lets an attacker-crafted URL be matched to a trusted `github.com` repository while the real network/actual repository target differs - ([File: app/src/lib/remote-parsing.ts])

## Summary
`parseRemote` in `app/src/lib/remote-parsing.ts` extracts `{hostname, owner, name}` from a remote/clone URL using hand-rolled, greedy regexes instead of a standards-compliant URL parser. These regexes are the single source of truth for several security-relevant decisions elsewhere in the app (which account/credentials to associate with a URL, whether an incoming "Open in Desktop" deep-link URL matches an already-trusted local repository, etc.), all of which implicitly assume that the `hostname`/`owner`/`name` triple this function returns is the same one a real URL parser (or `git`) would derive from the same string. Because the regexes use unbounded, greedy `.+` groups with no exclusion of `/`, `\`, or `@` characters, a single URL string can be "validly decoded" by `parseRemote` into one `{hostname, owner, name}` while the WHATWG `URL` parser used elsewhere in the same codebase (`app/src/lib/trampoline/find-account.ts`, `app-window.ts`, etc.) - or Git itself - resolves the *actual* authority/host from that string differently. This is structurally the same "one blob, two valid but different decodes" issue as the LiFi report: code that is written assuming the two interpretations are mutually exclusive/agree is not actually guaranteed that, and the mismatch is used for authorization-adjacent decisions (account/credential selection, repo-identity matching).

## Finding Description
`parseRemote` uses these regexes: [1](#0-0) 

```
https: ^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$
```

The `(?:.+@)?` userinfo group and `(.+)` hostname group are both greedy and unbounded - they can match across `/`, `\`, and repeated `@` characters, since regex `.` has no notion of URL syntax. `parseRemote` is then relied upon, as ground truth, in:

- `findAccountForRemoteURL` / `matchGitHubRepository` to decide **which account's credentials/token context** get associated with a URL (compares `parsedURL.hostname` to `getHTMLURL(account.endpoint)`'s hostname). [2](#0-1) [3](#0-2) 

- `urlMatchesRemote` / `urlsMatch` (via `parseRepositoryIdentifier`, which itself calls `parseRemote` first) to decide whether a GitHub API repository/clone URL "matches" a local git remote, and whether an incoming URL from an `x-github-client://openrepo/...` deep link matches an **already-open, trusted local repository**. [4](#0-3) [5](#0-4) [6](#0-5) 

Meanwhile, other parts of the same codebase parse remote/clone-derived URLs with the standards-based WHATWG `URL()` constructor, which follows RFC 3986/WHATWG URL semantics (host = text after the *last* unescaped `@` up to the first `/`, `\` normalized to `/` for special schemes such as `https:`, etc.): [7](#0-6) 

Because `parseRemote`'s regex does not perform the same normalization (it does not treat `\` as a path separator, and its greedy `.+` groups do not necessarily settle on the same split point a WHATWG parser would choose when the string contains extra `@`/`/`/`\` characters), the same raw URL string can:
- Be classified by `parseRemote` as `hostname = "github.com"`, `owner = "<owner>"`, `name = "<name>"` (i.e., "this is a github.com repo I recognize/trust"), while
- Being resolved by a standards-based parser (and potentially by whatever ultimately issues the network request) to a completely different host/path structure.

This mirrors the LiFi bug exactly: the code assumes a single interpretation is possible (`extractMainParameters` succeeds XOR the generic-swap decode succeeds), but no such mutual exclusivity is enforced, and downstream logic (`findAccountForRemoteURL`, `urlMatchesRemote`, `doesRepositoryMatchUrl`) treats `parseRemote`'s output as authoritative for security-relevant routing decisions (credential selection, "is this a trusted existing repo" checks).

## Impact Explanation
If the two interpretations diverge such that `parseRemote` reports `hostname = "github.com"`/`owner`/`name` matching a repository the user already has open and trusts, while the string is actually resolved elsewhere to a different host, an attacker-controlled deep link (`x-github-client://openrepo/<crafted-url>?pr=...&branch=...`) or clone-URL parameter could cause Desktop to:
- Treat the crafted URL as matching the user's existing trusted local repository via `doesRepositoryMatchUrl`/`urlsMatch` (`app/src/ui/dispatcher/dispatcher.ts:1920-1938`), skipping the normal "unknown remote, needs to be cloned/verified" path.
- Route into `openPullRequestFromUrl`/`openBranchNameFromUrl`, which then fetches and checks out attacker-influenced `pr`/`branch` values against that trusted repository (`app/src/ui/dispatcher/dispatcher.ts:1940-2048`), without the safeguards that apply to genuinely-new/untrusted remotes.
- Or select the wrong account/token in `findAccountForRemoteURL`, sending authentication material intended for `github.com` toward a URL that a different parser (or eventually `git`) would treat as pointing elsewhere.

This is exploitable purely by an attacker crafting a link/URL that the user clicks (or a repository/API object containing such a URL) - matching the required "unprivileged... attacker controls... a link or deep link the user clicks" impact criteria - and can lead to unwanted checkouts/fetches or credential misdirection.

## Likelihood Explanation
The likelihood is moderate: it requires constructing a specific URL where `parseRemote`'s greedy regex and a standards-compliant parser genuinely diverge in the host/owner/name they extract for the *same* raw string, and requires that divergence to happen to collide with a real account endpoint or an already-open repository. I was not able to fully verify from static reading alone whether Node's `git`/dugite invocation path (`app/src/lib/git/clone.ts`) or Electron's network stack would actually resolve such crafted strings to a different host in a way that is remotely reachable end-to-end (this would need to be validated by actually invoking `git` with such a crafted URL, which requires runtime testing I could not perform here). What is concretely verifiable from the code alone is the structural flaw: `parseRemote`'s ad-hoc regex is used as ground truth for security-relevant matching (`findAccountForRemoteURL`, `urlMatchesRemote`, `doesRepositoryMatchUrl`) in multiple places, while other parts of the codebase use a different (WHATWG) parser on similarly-shaped strings, with no invariant enforced that both parsers must agree.

## Recommendation
- Replace the hand-rolled regexes in `parseRemote` with parsing based on a single canonical URL parser (WHATWG `URL`, or `git`'s own URL-normalization rules) for the `https`/`ssh` cases, rather than ad-hoc greedy regex groups that can disagree with the parser actually used for network/credential decisions elsewhere in the app.
- Wherever `parseRemote`'s output is used for a trust/authorization decision (`findAccountForRemoteURL`, `urlMatchesRemote`, `urlsMatch`/`doesRepositoryMatchUrl`), also parse the same string with the WHATWG `URL` parser and require the derived host to match exactly before treating the URL as "belonging to" a known account or existing repository; reject (rather than "best-effort accept") on any disagreement between the two parsers.
- Add fuzz/differential tests that feed crafted strings (embedded `@`, `\`, repeated `/`) into both `parseRemote` and `new URL()` and assert the extracted host/owner/repo agree, specifically targeting the code paths that use `parseRemote` for account or repository-identity matching.

## Proof of Concept
Conceptual PoC (I could not execute this in a runtime environment, so treat this as a reasoning-level demonstration of the parser divergence, not a confirmed end-to-end exploit):

1. Craft a remote URL such as:
   `https://attacker.com\@github.com/octocat/Hello-World.git`
2. Feed it to `parseRemote` (`app/src/lib/remote-parsing.ts:27-63`):
   - `(?:.+@)?` greedily consumes `attacker.com\@` (the only literal `@` in the string), leaving `(.+)` to match `github.com` as the `hostname` group, with `owner="octocat"`, `name="Hello-World"`.
   - Result: Desktop believes this is a `github.com` repository owned by `octocat`, e.g. via `findAccountForRemoteURL`/`matchGitHubRepository`, and it could match an already-open local `octocat/Hello-World` repository through `urlMatchesRemote`/`urlsMatch`.
3. Feed the *same* string to the WHATWG `URL` parser used elsewhere in the app (`app/src/lib/trampoline/find-account.ts:25`), which normalizes `\` to `/` for the special `https:` scheme: the authority portion becomes `attacker.com` (terminated at the first `/`), with `@github.com/octocat/Hello-World.git` folded into the path - i.e., a *different* host (`attacker.com`) than the one `parseRemote` reported.
4. Because Desktop's trust/matching logic (`findAccountForRemoteURL`, `urlMatchesRemote`, `doesRepositoryMatchUrl`) is driven entirely by `parseRemote`'s output, a URL that a standards-based parser would resolve to `attacker.com` can be accepted by Desktop's matching/authorization code as `github.com/octocat/Hello-World`.

Full confirmation that this leads to an actual mis-routed network request or credential leak would require running `git`/dugite against such a crafted string and observing the connection target, which I was unable to do in this static analysis.

/** Try to parse an owner and name from a URL or owner/name shortcut. */
export function parseRepositoryIdentifier(
  url: string
): IRepositoryIdentifier | null {
  const parsed = parseRemote(url)
  // If we can parse it as a remote URL, we'll assume they gave us a proper
  // URL. If not, we'll try treating it as a GitHub repository owner/name
  // shortcut.
  if (parsed) {
    const { owner, name, hostname } = parsed
    if (owner && name) {
      return { owner, name, hostname }
    }
  }

  const pieces = url.split('/')
  if (pieces.length === 2 && pieces[0].length > 0 && pieces[1].length > 0) {
    const owner = pieces[0]
    const name = pieces[1]
    return { owner, name, hostname: null }
  }

  return null
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}
