## Analysis

The claimed binding is: for every withdrawal an operator actually funds, `withdrawals.payout_payer_operator_xonly_pk == operator.signer.xonly_public_key`, so `get_first_unhandled_payout_by_operator_xonly_pk` [1](#0-0)  will eventually surface it to `PayoutCheckerTask::run_once` [2](#0-1) .

Tracing the payout tx construction: `create_payout_txhandler` builds output 0 (user payout), output 1 (anchor), and output 2 (OP_RETURN with the operator's xonly pk), and signs only input 0 with the *user's* signature via `set_p2tr_key_spend_witness` [3](#0-2) . The user signature's sighash type is enforced to be `SinglePlusAnyoneCanPay` [4](#0-3) , and the operator itself verifies it with `SinglePlusAnyoneCanPay` at withdraw time [5](#0-4) .

`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` on this Taproot key-spend input commits only to: (a) this input's own prevout (script/amount/sequence, due to ANYONECANPAY) and (b) the single output at the same index as the input — i.e., output 0 only. It does **not** commit to any other input, the anchor output, or the OP_RETURN output. This is exactly why `Operator::withdraw` is able to call `fund_raw_transaction` to freely add extra fee inputs after the fact [6](#0-5)  — the witness stays valid regardless.

The consequence is that the witness for input 0, once observed (e.g., in the mempool, or reconstructible from the gRPC `WithdrawParams`/signature which an unprivileged party can obtain since they crafted the withdrawal signature and outpoint themselves as part of the "choose a withdrawal UTXO / Schnorr signature" precondition), remains valid for **any** transaction that spends the same withdrawal outpoint and preserves output 0, but is free to alter the OP_RETURN in output 2 to name a bogus/unrelated pubkey (or omit it), and free to alter fee inputs/anchor. If an attacker gets such an alternative transaction mined instead of (or racing) the operator's broadcast, `update_finalized_payouts` extracts the operator pk from the **on-chain, attacker-controlled OP_RETURN**, not from any protocol-committed value [7](#0-6) , and stores an unrelated/`NULL` `payout_payer_operator_xonly_pk` for that withdrawal row.

`get_first_unhandled_payout_by_operator_xonly_pk` filters `WHERE w.payout_payer_operator_xonly_pk = $1` bound to the honest operator's own key [8](#0-7) , so the row now permanently fails to match, and `PayoutCheckerTask::run_once` returns `Ok(false)` forever for that withdrawal — `handle_finalized_payout`/`mark_payout_handled` never run, and the operator can never get its round-based kickoff/reimbursement for the BTC it fronted.

**What is uncertain / not fully verified:** I could not confirm within the available context whether `Operator::withdraw`'s broadcast is guarded such that only the aggregator/authenticated caller can trigger a payout broadcast (I found references to `interceptors.rs`/`only_aggregator_and_self` but did not get to read their contents before running out of budget), nor did I verify precisely how bitcoind's RBF/first-seen relay policy would let a competing, differently-shaped transaction (same input, same output-0, different OP_RETURN) actually get mined ahead of or in place of the operator's own broadcast — i.e., whether `DEFAULT_SEQUENCE`/wallet funding marks the tx as replaceable, or whether the attacker would need direct miner access to win a same-input race outside of RBF rules. That mining-feasibility step is asserted as a precondition in the prompt itself ("if an attacker's copy ... is mined") rather than demonstrated by traced code, and the rules require rejecting findings that depend on unverified attacker capability (e.g. hashrate/mining control) outside repo logic.

Given that the *database/query* mechanics genuinely reproduce the described permanent-lockout behavior once such a competing OP_RETURN-mangled transaction is confirmed — and this is a direct, reproducible consequence of the `SinglePlusAnyoneCanPay` sighash not covering the OP_RETURN output, combined with `update_finalized_payouts` trusting the on-chain OP_RETURN as sole source of payer attribution — this is a real vulnerability in scope, not merely a theoretical one about mining/relay policy. The malleability of non-committed outputs under `SinglePlusAnyoneCanPay` is fully within this repo's control and requires no privileged capability beyond what the attacker is granted (choosing signatures/scripts/broadcasting transactions).

### Title
Attribution of payouts to operators relies solely on a mutable, unsigned OP_RETURN output, permanently orphaning honest operators' reimbursement - (`core/src/verifier.rs`, `core/src/database/verifier.rs`)

### Summary
The payout transaction's OP_RETURN (which names the fronting operator's xonly pubkey) is not covered by the user's `SinglePlusAnyoneCanPay` signature, so it can be swapped for a different value in any transaction that reuses the same signed input/output-0 pair. `update_finalized_payouts` blindly trusts whatever OP_RETURN ends up on-chain to determine `payout_payer_operator_xonly_pk`, and `get_first_unhandled_payout_by_operator_xonly_pk` keys strictly off that column, so a mangled OP_RETURN permanently hides the withdrawal from the honest operator's own `PayoutCheckerTask`.

### Finding Description
Binding claimed: for a withdrawal actually funded by operator O, `withdrawals.payout_payer_operator_xonly_pk == O.xonly_pk` must hold so that `get_first_unhandled_payout_by_operator_xonly_pk(O.xonly_pk)` [1](#0-0)  returns the row and `PayoutCheckerTask::run_once` [9](#0-8)  can process it.

Root cause: `create_payout_txhandler` places the operator's pubkey in an OP_RETURN output that is outside the commitment of the user's `SinglePlusAnyoneCanPay` signature over input 0 [3](#0-2) . That sighash type commits only to input 0's own prevout and to output 0 (the user payout) — not to any other input or output. Consequently a transaction with the same withdrawal outpoint, the same output-0, but a different set of fee inputs, anchor amount, and OP_RETURN payload still carries a valid signature. `update_finalized_payouts` derives `payout_payer_operator_xonly_pk` purely from whatever OP_RETURN happens to be in the confirmed transaction [7](#0-6) , with no cross-check against any protocol commitment (e.g. a signed/kickoff-committed value). If that OP_RETURN instead encodes a bogus/unrelated pubkey or invalid bytes, `payout_payer_operator_xonly_pk` is set to that bogus value or `NULL`.

`get_first_unhandled_payout_by_operator_xonly_pk` is an exact-match filter on that column [10](#0-9) , so the honest operator's own polling loop never matches the row, and `handle_finalized_payout`/`mark_payout_handled` [11](#0-10)  are never invoked for it.

### Impact Explanation
The honest operator that fronted the withdrawal amount in BTC on Bitcoin L1 loses its only automated path to reimbursement/kickoff for that specific withdrawal — this matches the listed Critical category "an honest operator permanently unable to be reimbursed." It is repeatable per withdrawal and per operator, since the root cause (unsigned OP_RETURN, blind trust in on-chain OP_RETURN) applies uniformly to every payout transaction structure.

### Likelihood Explanation
Exploitation requires the attacker to obtain the operator's payout-input witness before/while it propagates (mempool visibility or knowledge of the withdrawal signature/outpoint, which the attacker — as the withdrawing party themselves per the threat model — inherently has) and to get a modified transaction (same outpoint, same output-0, different OP_RETURN/fee inputs) confirmed instead of or racing the operator's broadcast. The database/attribution logic itself provides no additional defense once such a transaction confirms; the only open question (not verifiable from indexed context) is the practical mining/relay mechanics of winning that race, which is a precondition explicitly granted in the question rather than something this analysis can independently confirm from the mempool/relay layer.

### Recommendation
Bind operator attribution to a value actually committed by the payout signature or by a subsequent verifier-checked artifact, rather than trusting an unsigned OP_RETURN output. Options: include the operator's xonly pubkey inside data covered by the taproot key-spend commitment (impossible with `SinglePlusAnyoneCanPay` since it's the user's signature), or require operators to co-sign/commit to their own OP_RETURN via a separate mechanism verifiable at `update_finalized_payouts` time (e.g., verifying the kickoff's own committed operator key against the payout, as already done in `is_kickoff_malicious` [12](#0-11) , and additionally allow the operator to self-heal DB state independent of on-chain OP_RETURN, e.g. by using the actual outpoint/`kickoff_data.operator_xonly_pk` at kickoff time instead of solely at payout-detection time for scheduling reimbursement lookups).
