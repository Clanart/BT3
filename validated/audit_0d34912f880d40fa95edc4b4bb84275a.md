### Title
Wildcard-vs-literal-name collision lets `with-ft`/`with-nft` allowances for an asset literally named `"*"` silently become blanket allowances for every asset in that contract, letting assets move past `restrict-assets?`/`as-contract?` post-conditions - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`clarity/src/vm/functions/post_conditions.rs` uses the string `"*"` both as (a) a valid, attacker-mintable Clarity asset name (`ClarityName` accepts `"*"` per `CLARITY_NAME_REGEX_STRING` [1](#0-0) , confirmed valid by `#[case::asterisk("*")]` [2](#0-1) ) and (b) an internal "match-all-assets-of-this-contract" sentinel used by `check_allowances` when merging allowance buckets. Because both meanings collapse onto the exact same `AssetIdentifier{contract_identifier, asset_name: "*"}` key, an allowance a contract author writes intending to authorize only the literal token named `"*"` is indistinguishable from — and is treated as — a wildcard allowance covering **every other fungible/non-fungible asset** minted by that contract. This is the same class of bug as the Spotipy report: a value that should be parsed strictly as opaque, literal data (`asset_name`) is instead re-interpreted as a control/meta character (wildcard) by a downstream consumer, letting a request "escape" its intended, narrower scope.

### Finding Description
`eval_allowance` builds `FtAllowance`/`NftAllowance` from user-controlled `asset_name` strings, and simply requires them to be valid `ClarityName` values — `"*"` passes validation with no special-casing: [3](#0-2) 

`check_allowances` then keys `ft_allowances`/`nft_allowances` maps by `AssetIdentifier` (contract + asset_name), and separately re-derives the *same* key, `AssetIdentifier{contract_identifier: asset.contract_identifier.clone(), asset_name: ClarityName::from_literal("*")}`, to look up a "wildcard" bucket that is merged into the check for every real asset moved in that contract: [4](#0-3) [5](#0-4) 

There is no code path that distinguishes "the caller wrote `(with-ft .c "*" u100)` meaning the literal token called `*`" from "the caller wrote `(with-ft .c "*" u100)` meaning all fungible tokens in `.c`". Both produce identical `AssetIdentifier` entries in `ft_allowances`/`nft_allowances`, so the merge logic at lines 608-613 / 637-642 always treats them as the wildcard case.

This breaks the equality that `restrict-assets?`/`as-contract?` are supposed to enforce: *only assets explicitly named in an allowance may move, and only up to the stated amount for that specific asset*. Instead, any allowance keyed on the literal name `"*"` silently authorizes movement of every other fungible/non-fungible asset defined by the same contract, up to the same amount/ID list, regardless of whether the caller ever intended that.

### Impact Explanation
This is a genuine post-condition/allowance escape ("an asset moving past its post-conditions" — explicitly listed as a Critical-tier impact in scope). A caller of `restrict-assets?`/`as-contract?` who writes an allowance scoped to a specific asset that happens to be named `"*"` unknowingly grants the invoked body permission to move *any other* asset issued by that same contract, up to the specified cap. Since the invoked body typically calls into attacker- or third-party-controlled contract code (that is the entire purpose of `restrict-assets?`), an attacker who controls (or convinces a victim to interact with) a contract that mints a token literally named `"*"` alongside other valuable tokens can leverage this ambiguity to move assets that were never covered by an explicit, asset-specific allowance — i.e., assets move past the post-conditions the caller believed they had set up. This can lead to unauthorized fungible/non-fungible token transfers within the protected `as-contract?`/`restrict-assets?` scope.

### Likelihood Explanation
The precondition is narrow but entirely realistic: any Clarity contract can legally define (or SIP-010/013-style tokens can be minted) with the asset name `"*"`, since it passes `ClarityName` validation with no reserved-word protection anywhere in `eval_allowance`, `AssetIdentifier` construction, or `check_allowances`. No privileged role is needed — a normal contract deployer can define a token named `"*"`, and any unprivileged user who later writes `(with-ft .that-contract "*" amount)` (a completely natural thing to do if they intend to authorize movement of that specific token) is silently exposed to the wildcard behavior. No signature forgery or malicious peer assumption is required; this triggers purely from ordinary Clarity execution semantics.

### Recommendation
Reserve `"*"` as an internal-only sentinel that cannot be produced from user-supplied `asset_name` strings in `eval_allowance` (reject it explicitly in the `AllowanceWithFt`/`AllowanceWithNft` branches, similar to how `RuntimeError::BadTokenName` is already raised for unparsable names), or introduce a dedicated `Allowance` variant (e.g., `Allowance::FtWildcard`/`Allowance::NftWildcard`) that is only constructed by a distinct native syntax rather than by overloading a literal asset name value.

### Proof of Concept
1. Attacker deploys contract `.evil` defining two fungible tokens: `(define-fungible-token real-token)` and `(define-fungible-token *)` (both legal per `CLARITY_NAME_REGEX_STRING`, confirmed valid by the `asterisk` test case) [2](#0-1) .
2. A victim contract (or the attacker, acting as an unprivileged sender in their own transaction, to demonstrate the break) executes:
   ```
   (as-contract?
     ((with-ft .evil "*" u100))
     (contract-call? .evil transfer-real-token u100 tx-sender))
   ```
   intending only to authorize movement of up to 100 units of the token literally named `"*"`.
3. Inside `check_allowances`, when `.evil`'s `real-token` movement is checked, the code builds the wildcard key `AssetIdentifier{contract_identifier: .evil, asset_name: "*"}` at [6](#0-5)  — which is exactly the entry the caller inserted, believing it applied only to the literal `"*"` token.
4. `real-token`'s movement (100 units) passes the check via this merged "wildcard" allowance even though no allowance was ever written for `real-token` specifically, demonstrating that an asset moved past the caller's actual post-condition scope. [7](#0-6)

            let mut merged: Vec<(usize, u128)> = Vec::new();
