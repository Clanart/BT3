### Title
ReceivedOutput deserialization accepts arbitrary offset/script pairs, letting attacker-supplied bytes report funds that cannot be spent — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2025-0510 (an invalid/ambiguous field causing a message to be attributed to a wrong sender), `ReceivedOutput::read` deserializes an `offset` scalar and a `TxOut`/`OutPoint` from untrusted bytes without checking that `offset` is actually the HDKD offset binding the scanned script_pubkey to the wallet key. The only checks are scalar canonically via `Secp256k1::read_F` and syntactic consensus decoding of the `TxOut`/`OutPoint`.

### Finding Description
`ReceivedOutput` is the structure the wallet uses to remember that an on-chain output belongs to the group key plus a scalar offset (`key + offset*G`). `Scanner::scan_transaction` only ever produces `ReceivedOutput`s whose `offset` came from `self.scripts[output.script_pubkey]`, i.e., an offset previously validated through `register_offset` and `p2tr_script_buf` (which rejects odd-Y results) [1](#0-0) .

However, `ReceivedOutput::read` performs no such consistency check:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-133
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    output = TxOut::consensus_decode(&mut buf_r)?;
    outpoint = OutPoint::consensus_decode(&mut buf_r)?;
    Ok(ReceivedOutput { offset, output, outpoint })
}
``` [2](#0-1) 

Any byte string that encodes a canonical scalar followed by any well-formed `TxOut` and `OutPoint` is accepted, even though nothing verifies that `p2tr_script_buf(key + offset*G) == output.script_pubkey`. The offset is even allowed to be an odd-Y (non-constructible) result that `Scanner::new`/`register_offset` would refuse — `p2tr_script_buf` returns `None` for odd keys precisely because such outputs are unspendable/unconstructible [3](#0-2) . Downstream signing applies `keys.offset(output.offset())` to derive the spend key; with a mismatched offset the group signs for a key unrelated to the output, producing an unusable signature.

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` bytes (e.g., a forged/relayed "received output" record consumed by the processor) can cause funds to be reported as received that are not spendable: the recorded offset does not map the real on-chain output's script_pubkey to the group key. When the wallet later attempts to spend the output, the offset tweak produces a signature for the wrong key, so the "received" balance can never be moved — a direct integrity failure matching the CVE's "incorrect sender displayed" class mapped onto Serai's "output attributed to a wrong HDKD offset" shape.

### Likelihood Explanation
Reachability depends on serialized `ReceivedOutput`s crossing a trust boundary (coordination/relayer input) rather than coming straight from `Scanner::scan_transaction`. The format is attacker-controlled bytes (`offset` scalar + arbitrary `TxOut`/`OutPoint`), so constructing a malformed object is trivial; the only requirement is a caller that feeds untrusted bytes into `ReceivedOutput::read` and then treats the result as a spendable output.

### Recommendation
After decoding in `ReceivedOutput::read`, or at the point of consumption, verify the offset is consistent with the output: recompute `p2tr_script_buf(scanner_key + GENERATOR * offset)` (requires carrying/providing the base key) and require equality with `output.script_pubkey`. Alternatively, restrict construction of `ReceivedOutput` to `Scanner` internals and make `read` verify the offset against a provided base key, rejecting odd-parity results.

### Proof of Concept
1. Let `K` be the group key and `P = p2tr_script_buf(K)` the real P2TR script for `offset = 0`.
2. Attacker serializes `offset = 1` (or any `Scalar` such that `K + G*offset` is odd or unrelated), followed by a `TxOut { value: v, script_pubkey: P }` for a real UTXO paying `K`, and a matching `OutPoint`.
3. `ReceivedOutput::read` accepts it. The consumer believes it owns output `O` under offset `1`.
4. Spending `O` applies `keys.offset(1)`, yielding signing key `K + G`; the resulting signature is valid for `K + G`, not for the output's key `K`, so the Bitcoin node rejects the spend (or, if `K + G` is odd-Y, no valid P2TR construction exists at all). The funds are reported received yet are unspendable.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
