### Title
Consumed forwarded-output instructions are written back to `ForwardedOutputDb`, letting an attacker replay a deposit instruction by sending to the publicly derivable forward address - (File: processor/src/multisigs/db.rs)

### Summary
The external report's class — value moving through a path that skips the intended enforcement — maps onto Serai's Bitcoin scanner: the internal `Forwarded` output address is deterministically derivable by anyone (`Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` over the public group key), and `Scanner::scan_transaction` accepts any output matching the script_pubkey. Worse, when a `Forwarded` output consumes a saved `InInstructionWithBalance`, `ForwardedOutputDb::take_forwarded_output` stores the *original* buffer back instead of the remainder, so the consumed instruction is never actually removed and is replayed for the next `Forwarded` output of the same balance.

### Finding Description
- `ForwardedOutputDb` is keyed solely by `ExternalBalance` (`processor/src/multisigs/db.rs:76`). `save_forwarded_output` appends SCALE-encoded `InInstructionWithBalance` entries under the balance key (`db.rs:223-227`).
- `take_forwarded_output` decodes the first entry, asserts progress, deletes the key only if nothing remains — but on the non-empty branch calls `Self::set(txn, balance, &outputs)` where `outputs` is the *full original buffer*, not `outputs_ref` (the remainder after decoding). The consumed instruction is persisted again (`db.rs:233-241`).
- The trigger path is fully reachable by an unprivileged party: the `Forwarded` script is `p2tr_script_buf(key + G * FORWARD_OFFSET)` with `FORWARD_OFFSET = hash_to_F(KEY_DST, b"forward")` (`processor/src/networks/bitcoin.rs:308-344`), and `Scanner::scan_transaction` emits a `ReceivedOutput` for any tx output paying that script_pubkey (`networks/bitcoin/src/wallet/mod.rs:199-214`). `get_outputs` classifies it via the offset map (`processor/src/networks/bitcoin.rs:686-700`).
- During `RotationStep::ForwardFromExisting`, each scanned `Forwarded` output causes `take_forwarded_output(output.balance())` to fire the stored instruction (`processor/src/multisigs/mod.rs:823-833`).

### Impact Explanation
A consumed instruction is replayed for every subsequent `Forwarded` output carrying the same balance, and (in the honest multi-entry case) the first stored instruction is repeatedly decoded while later instructions are never reached. Concretely: an attacker makes a deposit whose `InInstruction` credits their Serai account; when it is forwarded during rotation, they then broadcast their own Bitcoin transaction paying the same post-fee amount to the publicly computable forward address. The scanner emits it as `Forwarded`, `take_forwarded_output` returns the still-stored instruction, and the instruction is executed a second time — a double credit / duplicate execution obtained by transacting outside the sanctioned deposit flow, exactly the "evade the enforced path" bug class. Even without malice, two honest forwards of equal balance cause one depositor to be credited twice and the other never.

### Likelihood Explanation
Medium. Exploitation requires a multisig rotation (`ForwardFromExisting`/`ClosingExisting`) and a pending forwarded instruction whose balance the attacker can match — both publicly observable on-chain once the forward transaction or deposit exists. The DB defect is unconditional: any second `take` for a balance with remaining entries re-executes the first instruction.

### Recommendation
In `take_forwarded_output`, persist the remainder (`&outputs[consumed..]`, i.e., the bytes after `outputs_ref`'s advance) instead of `outputs`, or track and strip the consumed prefix. Consider additionally keying `ForwardedOutputDb` by something bound to the specific forward (e.g., expected outpoint/tx commitment) rather than amount alone, and documenting or restricting sends to internal offset scripts.

### Proof of Concept
1. During a rotation, deposit D sats to the old multisig's External address with an `InInstruction` crediting attacker-controlled Serai address A. The processor saves it via `save_forwarded_output(balance = D - fee)` and creates the forward transaction paying the new multisig's forward address.
2. After the legitimate `Forwarded` output is scanned and `take_forwarded_output` fires, the DB still contains the instruction because `set` wrote back the unconsumed buffer.
3. Attacker broadcasts a Bitcoin tx paying exactly `D - fee` to the forward address (computable as `p2tr_script_buf(new_key + G * FORWARD_OFFSET)`). The scanner reports it as `Forwarded`; `take_forwarded_output` decodes and returns the same instruction again, which is pushed to `instructions` and executed — crediting A a second time for a single deposit.
