### Title
`SignableTransaction::new` under-charges fees by excluding the `OP_RETURN` data output from weight calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a caller-supplied `data` field (up to 80 bytes) which is pushed onto `tx_outs` as an `OP_RETURN` output, yet both calls to `calculate_weight_vbytes` are made with `payments` only — never including the data output. The computed `needed_fee` therefore prices a smaller transaction than the one actually signed and broadcast, analogously to the TWAP bug where `charge_invocation_fee` was called with a constant `1` instead of the user-supplied `records` count: a caller-controlled quantity (here, the size contributed by `data`) is omitted from the fee accounting.

### Finding Description
The `OP_RETURN` output is appended to the real transaction's outputs before the fee is computed:

`networks/bitcoin/src/wallet/send.rs` lines 194-202 push the data output to `tx_outs`, but line 204 computes fee weight with `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` excludes the OP_RETURN. The same omission occurs on the change path at lines 225-227, and the minimum-relay-fee check at line 211 uses the understated `vbytes`. [1](#0-0) [2](#0-1) 

`calculate_weight_vbytes` builds a template `Transaction` purely from `inputs`, `payments`, and `change`; it has no parameter for data outputs at all, so the omission is structural. [3](#0-2) 

### Impact Explanation
- Every transaction carrying an `OP_RETURN` (up to 80 bytes of payload plus output overhead, roughly ~90+ vbytes) pays a fee computed for a transaction that is smaller by exactly that amount. The effective sat/vbyte rate is lower than the `fee_per_vbyte` requested — a direct revenue/fee leak of the same shape as the reference bug.
- Because the `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the understated `vbytes`, a transaction can pass the check while its real fee rate falls below the network minimum relay fee. Such a transaction will be rejected by peer mempools, leaving the output funds unspendable in practice (the signed TX cannot propagate), which maps to "funds reported received/sent that are not spendable".
- The change-amount check at line 228 (`input_sat.checked_sub(payment_sat + fee_with_change)`) also uses the understated fee, so the change output is credited more than it should be relative to the intended fee rate.

### Likelihood Explanation
Reachable by any party able to cause a `SignableTransaction` to be built with a `data` payload (e.g., a payment request carrying an OP_RETURN memo). The effect is deterministic and scales linearly with `data.len()` up to the 80-byte cap enforced at line 171 — a ~90-byte understatement per transaction, which is a material fraction of a small transaction's total size.

### Recommendation
Include the `OP_RETURN` output in the weight/vbytes accounting. Either extend `calculate_weight_vbytes` to accept the full output list (including the data output) or pass a synthesized payment entry for it:

```rust
// Build the full output list first, then:
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &all_outputs_incl_data, None);
```

and apply the same on the `change` path, so `needed_fee`, `TooLowFee`, and `MAX_STANDARD_TX_WEIGHT` are all evaluated against the true transaction size.

### Proof of Concept
```rust
// Construct a transaction with an 80-byte OP_RETURN payload
let data = Some(vec![0xAA; 80]);
let tx = SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte).unwrap();

// The produced Transaction includes the OP_RETURN output...
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// ...but needed_fee was priced as if it did not exist:
// actual_vbytes = tx.transaction().vsize() (includes ~90 extra bytes)
// paid_rate = tx.fee() / actual_vbytes < fee_per_vbyte
// With fee_per_vbyte near the minimum, paid_rate falls under the relay minimum
// and the signed transaction is non-relayable.
```

The root cause is confirmed purely by reading `send.rs`: `tx_outs` gains the data output at line 195, while `vbytes` at lines 204 and 226 is derived only from `payments`, which by construction never contains the OP_RETURN. [4](#0-3)
