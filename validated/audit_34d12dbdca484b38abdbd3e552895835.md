### Title
Unbounded `storageKeys` array in `eth_getProof`/`kaia_getProof` allows memory/CPU exhaustion from a single public RPC call - (File: api/api_eth.go)

### Summary
The `eth_getProof` (and `kaia_getProof`) RPC handler accepts a caller-supplied `storageKeys []string` argument with no cap on the number of elements. For every element the handler allocates parallel slices and performs a full trie-proof walk, so an unprivileged public-RPC caller can force large memory allocation and CPU consumption in a single JSON-RPC request, analogous to the `@solana/web3.js` OOM issue where untrusted/attacker-controlled input size directly drove unbounded memory allocation.

### Finding Description
`doGetProof` immediately sizes multiple slices from the length of the untrusted `storageKeys` parameter before doing any bound/sanity check on the count: [1](#0-0) 

```go
func doGetProof(ctx context.Context, b Backend, address common.Address, storageKeys []string, blockNrOrHash rpc.BlockNumberOrHash) (*EthAccountResult, error) {
	var (
		keys         = make([]common.Hash, len(storageKeys))
		keyLengths   = make([]int, len(storageKeys))
		storageProof = make([]EthStorageResult, len(storageKeys))
	)
	// Deserialize all keys. This prevents state access on invalid input.
	for i, hexKey := range storageKeys {
		var err error
		keys[i], keyLengths[i], err = decodeHash(hexKey)
		...
```

For every entry that survives `decodeHash`, the code performs a `storageTrie.Prove(...)` call, which walks/loads/hashes trie nodes and accumulates proof node bytes into an in-memory `proofList`: [2](#0-1) 

No limit exists on `len(storageKeys)` anywhere in this code path — the only outer constraint is the generic HTTP/WS request body size cap (`MaxRequestContentLength`). Because each storage-key string can be very short (e.g. `"0"`, 1–2 bytes plus JSON overhead), an attacker can pack an extremely large number of array elements into a single request that still fits under the byte-size cap, driving:
- Three slices sized to `len(storageKeys)` (`keys`, `keyLengths`, `storageProof`), and
- One trie `Prove` (node traversal + node hashing + proof-list allocation) per element.

This mirrors the CVE-2024-30253 bug class: "particular [attacker-controlled] inputs... result in memory exhaustion (OOM)" because the size of allocated structures is driven directly by an attacker-chosen count rather than any node-side limit. Unlike other Kaia RPC paths (e.g. `debug` tracer paths, which are gated behind `HeavyAPIRequestLimit` / `IPCOnly`), the `eth_getProof`/`kaia_getProof` endpoint is marked `Public: true` and reachable by any external caller.

### Impact Explanation
A single, unauthenticated JSON-RPC call to a public `eth_getProof`/`kaia_getProof` endpoint can:
- Force allocation of large slices proportional to the number of supplied `storageKeys`.
- Trigger a proportional number of trie `Prove` operations (disk/cache reads, node hashing, RLP encoding), consuming CPU and memory concurrently.
- Because RPC calls are dispatched onto per-request goroutines (see `handler.handleMsg`/`handleBatch`), multiple concurrent requests compound the effect, potentially exhausting node memory and causing a crash or making the node unresponsive — a denial-of-service against a public RPC node, matching the "High: loss of availability" severity class of the reference advisory.
- This does not corrupt consensus state or move value, so it is scoped to availability rather than fund safety, matching the original CVE class (DoS via memory exhaustion, not asset theft).

### Likelihood Explanation
Likelihood is high for any operator exposing `eth`/`kaia` namespace publicly with the default (or a moderately large) `MaxRequestContentLength`, since:
- No authentication or special privileges are required — any public-RPC caller can invoke `eth_getProof`.
- The attack requires only crafting one JSON array with many short string elements; no wallet funds or transaction fees are needed.
- The batch-size/response-size limits added elsewhere in the RPC handler (`batchRequestLimit`, `batchResponseMaxSize`) do not constrain the element count of a single method's parameter array.

### Recommendation
Add an explicit cap on `len(storageKeys)` in `doGetProof` (and any similarly-shaped RPC handlers that size structures directly from a caller-supplied array length, e.g. multi-key/multi-address batched RPC parameters) and reject requests exceeding a reasonable maximum (e.g., a few hundred keys) before allocating any per-key slices or performing trie operations.

### Proof of Concept
1. Start a Kaia node with the `eth`/`kaia` namespace exposed on a public HTTP/WS RPC endpoint.
2. Send a single `eth_getProof` request with `address` set to any valid address and `storageKeys` set to a JSON array containing a very large number of short hex strings (e.g. hundreds of thousands to millions of `"0x0"` entries), sized to remain under `MaxRequestContentLength`.
3. Observe node memory usage spike (three slices sized to the array length) and CPU usage spike (one `storageTrie.Prove` per key), which can be repeated/parallelized across concurrent connections to exhaust the node's resources and cause it to become unresponsive or OOM-kill.
