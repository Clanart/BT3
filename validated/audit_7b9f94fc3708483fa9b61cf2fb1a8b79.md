## Analysis Result

### Title
Daemon RPC unknown-command handler logs the full, unredacted request payload — bypassing sensitive-data redaction (Sensitive Information Logged in Application Logs) - ([File: chia/daemon/server.py])

### Summary
`WebSocketServer.incoming_connection()` redacts sensitive keys (`pass`, `key`, `secret`, `mnemonic`) before writing the "Received message" debug log, but `WebSocketServer.handle_message()` independently logs the *raw, unredacted* message a second time whenever the `command` field does not match any known/registered command.

### Finding Description
Incoming daemon websocket messages are first redacted for logging purposes: [1](#0-0) 

This redaction is applied in `incoming_connection()` right before the debug log line, but the *original*, non-redacted `decoded` dictionary is what actually gets passed on to `handle_message()`: [2](#0-1) 

Inside `handle_message()`, if the supplied `command` does not match any of the built-in daemon commands, keychain commands, or `ping`, the entire raw `message` object (which still contains the caller-supplied `data` field verbatim, including any `password`, `private_key`, `mnemonic`, `passphrase`, or `entropy` values) is logged at `ERROR` level with no redaction at all: [3](#0-2) 

The codebase clearly treats sensitive-field redaction as a security control — there is a dedicated `redact_sensitive_data()` helper and an explicit regression test (`test_message_logging_redaction`) verifying that fields like `password`, `private_key`, `mnemonic`, `passphrase`, `secret_value`, and nested equivalents are redacted before being written to logs: [4](#0-3) 

However, that redaction only covers the single "Received message" debug log line. The `self.log.error(f"UK>> {message}")` statement in `handle_message()` bypasses this protection entirely — it fires on any unrecognized `command` string, which is trivial for any local caller connected to the daemon websocket to trigger by simply misspelling/using a bogus command name while still supplying a `data` payload containing sensitive values (e.g. an attempted keychain-adjacent client mistakenly sending `add_privatekey` instead of `add_private_key`, or any malformed/legacy client command).

### Impact Explanation
Any local process capable of establishing a websocket connection to the daemon (wallet UI, CLI tools, third-party RPC integrations, or a compromised/buggy local client using daemon mTLS certs) can cause secrets such as keyring passphrases, mnemonics, or private key material passed in an RPC payload to be written in cleartext into the daemon's persistent log file at `ERROR` level — a log level that is enabled by default (unlike `DEBUG`), unlike the already-acknowledged "Known Issue" in the CHANGELOG about DEBUG-level passphrase logging. This is a direct analog of CVE-2025-30677 (CWE-532): sensitive configuration/credential values are logged in plaintext to application logs, exposing them to anyone with log file access (log aggregation systems, support bundles, other local users with log read permissions).

### Likelihood Explanation
Likelihood is straightforward: any local RPC caller (a category explicitly in scope, since the daemon is described in the codebase's own docs as a "local privilege concentrator" reachable by GUI/CLI/service clients) simply has to send a message with an unrecognized `command` value and sensitive data. No malicious peer, network access, or elevated privilege is required beyond having a working daemon connection, which many legitimate local clients already have.

### Recommendation
Route the `UK>>` unknown-command log line (and any other ad-hoc logging of the raw `message`/`decoded` object) through the existing `redact_sensitive_data()` helper before logging, consistent with how `incoming_connection()` already protects the "Received message" log line. Consider also lowering this log to `debug` level or logging only the `command` name plus safe envelope fields (`origin`, `destination`, `request_id`) rather than the full payload.

### Proof of Concept
1. Connect to the local daemon websocket using valid daemon mTLS certs (as any legitimate local client would).
2. Send a JSON RPC message with `destination: "daemon"`, a `command` value that does not match any daemon/keychain command (e.g. `"command": "add_private_keyz"`), and a `data` payload containing sensitive fields, e.g.:
```json
{"command": "add_private_keyz", "data": {"mnemonic": "word1 word2 ... word24"}, "ack": false, "origin": "test", "destination": "daemon", "request_id": "abc"}
```
3. Observe the daemon log: `handle_message()` executes `self.log.error(f"UK>> {message}")` at [5](#0-4) , writing the full mnemonic in plaintext to the log file, unlike the redacted debug log produced earlier in the same request flow.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```
