Found a concrete decimal-mistreatment bug in the `hyper-fungible-token` pallet that is a direct structural analog of the Opyn `debtToMint` issue — the fix is one-directional (uses `saturating_sub`) and silently no-ops instead of scaling in the reverse direction, letting an ordinary user mint an inflated ERC-20 amount on the destination chain.

### Title
Decimal-mismatch in `convert_to_erc20` lets `send()` mint inflated ERC20 amounts when destination decimals < local decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20`, used by `HyperFungibleToken::send()` to encode the outbound token amount for the destination EVM contract, scales using `erc_decimals.saturating_sub(local_decimals)`. `saturating_sub` clamps to `0` whenever `local_decimals > erc_decimals`, silently skipping the required down-scaling and forwarding the raw, high-precision local balance as the ERC20 amount, unchanged.

### Finding Description
`convert_to_erc20` is documented as multiplying by `10^(erc_decimals - local_decimals)` "to scale up to ERC20 precision": [1](#0-0) 

This is only correct when `erc_decimals >= local_decimals`. When the destination ERC20 token is configured with *fewer* decimals than the local Substrate asset (e.g. local asset uses 18 decimals, destination ERC20 uses 6, similar to USDC), `erc_decimals.saturating_sub(local_decimals)` evaluates to `0` instead of a negative exponent, so the multiplier becomes `10^0 = 1` and the function returns `value` completely unscaled — it should instead have divided by `10^(local_decimals - erc_decimals)`.

`send()` calls this directly on the caller-locked/burned amount and forwards the result as the wire `amount` in the cross-chain `Message` dispatched to the destination contract: [2](#0-1) 

Concretely, escrowing `1 token` of an 18-decimal local asset (`amount = 1e18` raw units) with a destination ERC20 registered at 6 decimals should produce `erc20_amount = 1e18 / 10^12 = 1e6` (i.e. `1.000000` in the ERC20's 6-decimal terms). Instead, the buggy `saturating_sub` path returns `erc20_amount = 1e18` unchanged, which the destination ERC20 contract interprets as `1e18 / 10^6 = 1,000,000,000,000` tokens — a `10^12`x inflation of the minted/released value relative to what was actually escrowed on the source chain.

The companion function `convert_to_balance`, used in `on_accept` for the reverse (incoming) direction, has the mirror-image flaw for the opposite decimal ordering: [3](#0-2) [4](#0-3) 

There, when `erc_decimals < local_decimals` the divisor also saturates to `1`, but that case only *under-mints* the beneficiary — a loss to the receiving user, not an attacker-exploitable gain. The `send()`/`convert_to_erc20` direction is the dangerous one because it lets the *sender* (an unprivileged, ordinary caller) manufacture an inflated cross-chain claim redeemable on the destination chain.

Per-chain decimals are entirely governance-configured per `(asset_id, destination)` via `register_token`/`ChainConfig`, with no validation enforcing `erc_decimals >= local_decimals`: [5](#0-4) 

Existing tests only exercise the safe direction (`erc_decimals=18, local_decimals=10`, i.e. `erc_decimals > local_decimals`): [6](#0-5) 

No test exists for `local_decimals > erc_decimals`, which is exactly the unhandled/vulnerable branch.

### Impact Explanation
Any user who calls `send()` for an asset pair configured with `local_decimals > erc_decimals` for the chosen destination can lock/burn a small, honestly-priced amount of the local asset and have the pallet dispatch a message that credits the destination EVM contract with a `10^(local_decimals - erc_decimals)`-times larger ERC20 amount than was actually escrowed. This is unauthorized minting/release of value on the destination chain — a direct fund-forging exploit, not merely a display/precision inconvenience. It requires no malicious relayer, prover, or governance actor: only a normal `send()` call by any account and a plausible, governance-set asset/chain decimal configuration (high-decimal local asset bridged to a low-decimal ERC20 wrapper, e.g. USDC-style 6-decimal tokens).

### Likelihood Explanation
The bug triggers deterministically whenever such a decimal configuration exists — there is no race condition or timing dependency, and `register_token` does not reject `erc_decimals < local_decimals`. Given how common asymmetric decimal setups are across ecosystems (Substrate assets frequently use 10, 12, or 18 decimals; many ERC20 stablecoins use 6), this configuration is realistic and not a contrived edge case.

### Recommendation
Fix both scaling helpers to handle either decimal direction symmetrically instead of relying on `saturating_sub`, e.g.:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```

and the mirrored fix for `convert_to_balance`. Add explicit tests for `local_decimals > erc_decimals` (send direction) and `erc_decimals < local_decimals` (receive direction) to lock in correct behavior both ways.

### Proof of Concept
1. Governance registers asset `X` via `register_token` with `local_decimals = 18` on the source chain and `ChainConfig { decimals: 6, .. }` for destination `Evm(dest_id)`, populating `Precisions::<T>::get(X, Evm(dest_id)) = 6`.
2. Attacker calls `HyperFungibleToken::send(origin, SendParams { asset_id: X, destination: Evm(dest_id), amount: 1_000_000_000_000_000_000 /* 1 token, 18 decimals */, .. })`.
3. Inside `send()`, `erc_decimals = 6`, `decimals = 18`; `convert_to_erc20(1e18, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so `erc20_amount = 1e18` (unscaled) instead of the correct `1e6`.
4. The dispatched `Message.amount` field carries `1e18`. On the destination EVM contract (ERC20, 6 decimals), this is interpreted as `1,000,000,000,000` whole tokens instead of `1`, a `10^12`x inflation minted/released to the attacker's chosen recipient for the cost of locking a single token's worth of the source asset.
