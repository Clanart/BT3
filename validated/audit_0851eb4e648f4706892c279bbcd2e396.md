### Title
Path-containment check in `resolveWithin` uses raw string prefix match, allowing deep-link `filepath` to escape the repository into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`x-github-client://openRepo?...&filepath=...` deep links are fully attacker-controlled (a link the user clicks), and the resulting `filepath` is validated against the target repository directory via `resolveWithin` before being passed to `shell.showItemInFolder`. The containment check in `_resolveWithin` is a bare string-prefix test (`realResolved.startsWith(realRoot)`) with no path-separator boundary, so a resolved path in a *sibling* directory that merely shares a name prefix with the repository directory (e.g. `myrepo-secrets` vs `myrepo`) is incorrectly treated as "inside" the repository.

### Finding Description
`parseAppURL` extracts an attacker-supplied `filepath` query parameter from a deep link with essentially no validation beyond rejecting absolute paths later on: [1](#0-0) 

`Dispatcher.openRepositoryFromUrl` only rejects absolute paths, then relies entirely on `resolveWithin` to keep the resolved path inside the cloned/opened repository before revealing it in the file manager: [2](#0-1) 

The containment logic itself is the broken invariant. `_resolveWithin` computes `resolved = resolve(normalizedRoot, normalizedRelative)`, `realpath`s both the root and the resolved path, and then checks containment with:
```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

This is a classic missing-separator boundary bug, analogous to the Solidity report's strict-vs-inclusive off-by-one: the check should require that `realResolved` equals `realRoot` or starts with `realRoot + path.sep`, but as written it also accepts any path whose string form merely begins with the same characters as `realRoot`. If the repository is cloned at `/Users/victim/Documents/GitHub/myrepo` and a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets` exists (a very common situation, since GitHub Desktop's default clone location groups all repos under one parent folder and repo names sharing prefixes — e.g. `foo`, `foo-internal`, `foo-private` — are common on GitHub), then a `filepath` of `../myrepo-secrets/secret.txt` resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/secret.txt`. String-wise this "starts with" `/Users/victim/Documents/GitHub/myrepo`, so the flawed check passes even though the file is in a completely different repository/directory.

The existing unit tests only cover the case of traversing out and back into the exact same root, and null-byte/symlink-escape cases; none of them exercise the sibling-prefix scenario, so this gap is not caught: [4](#0-3) 

`resolveWithin` is a shared utility also used by `Dispatcher` for file-manager reveal and by `buildConflictContext` for reading file contents into the Copilot conflict-resolution context, so the same flawed boundary check is reachable from multiple attacker-influenced code paths: [5](#0-4) 

### Impact Explanation
An attacker who can get a victim to click a crafted `x-github-client://openRepo?url=...&filepath=...` deep link (no local access, no credentials, no social-engineering beyond a normal link click) can cause GitHub Desktop to reveal/open a file located outside the intended repository, provided a sibling directory with an overlapping name prefix exists under the user's repositories root. This is a "read outside the repo" primitive per the accepted impact criteria: it can expose the existence and location of files/directories in unrelated repositories cloned by the same user (e.g. revealing a private/internal-named repo's file layout via `shell.showItemInFolder`), and if the same broken primitive is exercised through `resolveWithin`'s other callers, it undermines the sandboxing that these callers rely on to keep repository-scoped operations contained.

### Likelihood Explanation
Exploitation requires: (1) the victim clicks an attacker-supplied deep link (a normal, expected Desktop interaction — this is exactly what "Open in Desktop" links are designed for), and (2) a sibling directory sharing a name prefix with the target repository exists on disk. Condition (2) is common because Desktop's default "clone to" location places all repositories under one shared parent folder, and organizations frequently use prefix-related repo names. No admin rights, malware, or leaked credentials are needed, which keeps this within the accepted attack surface (link/deep-link driven, unprivileged).

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require a path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the appropriate `sep` for the `options` variant — `Path.sep`, `Path.posix.sep`, or `Path.win32.sep`). Add a regression test asserting that a sibling directory with an overlapping name prefix (e.g. root `.../myrepo` vs `.../myrepo-secrets/file`) is rejected by `resolveWithin`.

### Proof of Concept
1. Victim has GitHub Desktop repositories cloned under `/Users/victim/Documents/GitHub/`, including `myrepo` and, separately, `myrepo-secrets` (either another of the victim's own repos or one created by anything writing to that shared parent folder).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fsecret.txt`
3. Victim clicks the link. `parseAppURL` extracts `filepath = "../myrepo-secrets/secret.txt"` with no path-traversal rejection (only absolute paths are rejected in `Dispatcher.openRepositoryFromUrl`).
4. `resolveWithin('/Users/victim/Documents/GitHub/myrepo', '../myrepo-secrets/secret.txt')` computes `resolved = '/Users/victim/Documents/GitHub/myrepo-secrets/secret.txt'`; `realResolved.startsWith(realRoot)` evaluates to `true` because the string `'/Users/victim/Documents/GitHub/myrepo-secrets/secret.txt'` starts with `'/Users/victim/Documents/GitHub/myrepo'`, despite residing in a different directory.
5. The check passes, and `shell.showItemInFolder(resolved)` reveals `secret.txt` from the unrelated `myrepo-secrets` directory, confirming the escape outside the intended repository root.
