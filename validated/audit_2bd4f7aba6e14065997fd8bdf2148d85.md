## Analysis

The axios CVE (CVE-2026-42037) is a **structural-injection** bug: an attacker-controlled string (`value.type`) is interpolated verbatim into a syntactically-significant position of a serialized output format (the `Content-Type:` header inside a multipart part) with no escaping, while a sibling code path for plain string values *does* sanitize CRLF. This lets the attacker break out of the intended field and inject fabricated structure that a downstream parser trusts.

The transferable invariant is: **when a public parse API accepts an attacker-controlled string field and that string is later re-emitted into a structured serialization format at a position that is not quote/escape protected, the field's content can break the format's syntax.** The exposure assumption for Protobuf here is: a service parses an untrusted binary Protobuf message containing a `google.protobuf.Any` field, then re-serializes it to TextFormat (e.g., for logging, debugging, config generation, or transmission to another component that re-parses TextFormat) with `Any` expansion enabled.

I found this exact pattern in the `Any` expansion path of the TextFormat printer, present consistently in C++, Java, and Python:

- C++: `TextFormat::Printer::PrintAny` writes `generator->PrintLiteral("[")`, `generator->PrintString(type_url)`, `generator->PrintLiteral("]")` — the `type_url` is inserted raw between brackets with no character-class validation. [1](#0-0) 
- Java: `printAny` does `generator.print("[")`, `generator.print(typeUrl)`, `generator.print("]")` — again raw, unescaped. [2](#0-1) 
- Python: `self.out.write('%s[%s]%s ' % (self.indent * ' ', message.type_url, colon))` — raw string interpolation via `%s`. [3](#0-2) 

By contrast, the **parsing** side of the same Any bracket syntax explicitly validates the URL-prefix portion, rejecting control/format-breaking characters and requiring the type suffix to be a well-formed dotted identifier: [4](#0-3) 

This is the same asymmetry the axios report calls out: one path (string values / the parser) sanitizes, the sibling path (Blob `.type` / the Any printer) does not.

Note on feasibility: to reach the vulnerable print path, `internal::ParseAnyTypeUrl`/`GetAnyFieldDescriptors` only requires the last `/`-delimited segment of `type_url` to resolve to a real registered message type; everything before the last `/` (`url_prefix`) is otherwise unconstrained content controlled entirely by the attacker inside a valid, bounded binary Protobuf message. [5](#0-4) 

### Title
TextFormat `Any` expansion prints attacker-controlled `type_url` unescaped into bracket syntax, enabling TextFormat structure injection - (File: src/google/protobuf/text_format.cc)

### Summary
When `TextFormat::Printer` (and the equivalent Java/Python implementations) prints a `google.protobuf.Any` message with Any-expansion enabled, it writes the message's `type_url` field verbatim between `[` and `]` with no validation or escaping of TextFormat-significant characters (`]`, newlines, quotes, `{`/`}`). Since `type_url` is an ordinary `string` field populated from parsed, attacker-controlled binary Protobuf (or ProtoJSON) input, an attacker can embed characters that terminate the bracket expression early and inject arbitrary sibling TextFormat statements into the serialized output, mirroring the CRLF/header-injection class described in the axios advisory.

### Finding Description
`TextFormat::Printer::PrintAny` extracts `type_url` via reflection from an already-parsed message and requires only that the substring after the last `/` match a resolvable type name via the type registry/finder; it does not otherwise inspect the string's contents. [6](#0-5) 
It then emits `[` + raw `type_url` + `]` directly to the output stream using `PrintLiteral`/`PrintString`, which is the literal/pass-through write path, not the escaped string-quoting path used for normal string field values (compare with the quoted, escaped `type_url: "..."` produced when Any expansion is *not* used, as shown in the Java test expecting `"type_url: \"...\"\n"`). [1](#0-0) [7](#0-6) 

The parsing side of this exact same bracket syntax, by contrast, explicitly restricts the URL-prefix to percent-encoded/allowed characters and the type suffix to valid dotted identifiers before accepting it — confirming that sanitization was considered necessary for this construct, but (as in the axios bug) was only applied on one side (parse) and missed on the other (print). [4](#0-3) 

Because `type_url` originates from an ordinary UTF-8 `string` field in a binary Protobuf message that a public parse API happily accepts (Protobuf's wire format does not forbid `]`, `\n`, `{`, `}`, or `"` inside string fields), an attacker who controls only the `Any.type_url` bytes of an otherwise valid, bounded message can place attacker-chosen TextFormat syntax into the prefix portion (everything before the final `/`) while still satisfying the suffix-match requirement against a legitimate, registered type name (e.g., `google.protobuf.StringValue`).

### Impact Explanation
Any consuming application that (a) accepts untrusted binary Protobuf/ProtoJSON containing an `Any` field, and (b) re-serializes it via `TextFormat::Printer` with Any-expansion enabled — a common pattern for debug logging, audit trails, config dumps, or inter-process TextFormat exchange — will emit a TextFormat document whose structure is partially attacker-controlled. If that TextFormat output is subsequently consumed by anything that treats it as structured data (a downstream TextFormat parser, a log-scraping/alerting pipeline that expects one field per line, or a human reviewing logs for security events), the attacker can inject bogus fields, terminate the bracketed Any block early, or otherwise corrupt the intended document structure — the same class of "structural confusion of a downstream parser" impact called out in the axios advisory (CWE-93/template-injection style), scoped to integrity of the emitted representation rather than confidentiality or availability.

### Likelihood Explanation
Reaching the vulnerable code requires: (1) an application that parses attacker-supplied binary Protobuf containing an `Any` field — ordinary, fully public API usage; (2) that same application prints the message via `TextFormat::Printer` with `SetExpandAny(true)` (the C++ default is actually `expand_any_` enabled in many debug-string paths) or the Java/Python equivalents; and (3) the attacker being able to pick a `type_url` whose trailing segment matches some type known to the printer's type registry — a modest but not exotic constraint, since default/well-known types are commonly registered. Given these are all standard, documented usage patterns (no privileged access or hostile schema required), likelihood is credible for services that log or persist TextFormat-expanded `Any` messages from untrusted input.

### Recommendation
Before writing `type_url` between `[` and `]`, validate/escape it the same way the parser validates the Any bracket syntax: reject or escape characters that are structurally significant in TextFormat (`]`, `[`, `{`, `}`, `"`, control characters including `\r`/`\n`) in both the `url_prefix` and full `type_url` prior to printing, or fall back to the non-expanded, quoted-and-escaped `type_url: "..."` representation whenever the URL contains any character outside the already-defined allowed URL character set used by the parser (`ConsumeAnyTypeUrlOrFullTypeName`'s validation rules). Apply the equivalent fix consistently to the C#, Java, and Python `PrintAny`/`printAny`/`_TryPrintAsAnyMessage` implementations, mirroring the parser-side validation so the same invariant holds in both directions.

### Proof of Concept
Conceptual reproduction (mirrors the axios PoC pattern: construct a bounded, schema-valid input where the attacker-controlled field contains structure-breaking characters, then observe the "receiving parser" — here, TextFormat's own downstream parser — mis-structuring the result):

1. Build a valid `google.protobuf.Any` message where:
   - `value` is a serialized `google.protobuf.StringValue{ value: "x" }` (any registered type works).
   - `type_url` = `"evil]\n  injected_field: \"pwned\"\n  fake/google.protobuf.StringValue"`.
2. Feed this `Any` (embedded in a trusted, generated schema message) through the standard binary parse API (`Message::ParseFromString`) — this succeeds because Protobuf does not restrict string-field byte content beyond UTF-8 validity.
3. Print the parsed message with `TextFormat::Printer` configured with `SetExpandAny(true)` and a `TypeRegistry`/`Finder` that knows `google.protobuf.StringValue`.
4. Observe the printed output contains an early `]` closing the Any bracket, followed by an injected `injected_field: "pwned"` line and further garbage from the `type_url` before the real Any body — i.e., the printer's output stream no longer represents a single well-formed Any field, demonstrating structural corruption analogous to the injected `X-Injected-Header` in the axios PoC.

I was not able to execute this against a live Protobuf build in this environment (no test harness access here); the analog is established purely from source inspection of `TextFormat::Printer::PrintAny` (C++), `TextFormat.printAny` (Java), and `_Printer._TryPrintAsAnyMessage` (Python), all of which write `type_url` without escaping, contrasted with the validated bracket-parsing counterpart `ConsumeAnyTypeUrlOrFullTypeName`.
