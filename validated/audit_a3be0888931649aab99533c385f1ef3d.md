## Analysis

The report's broken invariant is: **a trust/authorization decision made at one point in time is never re-validated against the *current* state of the trusted entity**, allowing an actor who no longer legitimately controls that entity to still exercise privileges granted under the old state.

I found a structural analog for this in GitHub Desktop's handling of Git's "safe directory" ownership trust mechanism.

### Title
Permanent, path-based `safe.directory` trust exception is never re-validated or revoked, allowing later hijackers of a trusted path to silently gain code execution - (File: `app/src/lib/git/config.ts`, `app/src/ui/add-repository/add-existing-repository.tsx`, `app/src/ui/missing-repository.tsx`)

### Summary
When Desktop detects a repository with "dubious ownership" (i.e. owned by a different OS user than the current one), it offers the user a **"Trust Repository"** action. Clicking it calls `addSafeDirectory`, which permanently appends the path to the user's **global** `safe.directory` Git config entry [1](#0-0) . From that point on, `getRepositoryType` (via `git rev-parse`) will never again report that path as `unsafe`, because Git's `safe.directory` check is purely path-string based — it does not verify that the *current* owner is the same user who was trusted at grant time [2](#0-1) . This decision is invoked from two UI flows: `AddExistingRepository.onTrustDirectory` [3](#0-2)  and `MissingRepository.onTrustDirectory` [4](#0-3) , and there is no code path anywhere in the app that ever removes a path from `safe.directory` (e.g. on repository removal, relocation, or "forgetting" it).

### Finding Description
The exact corrupted value is the global Git config list `safe.directory`, mutated by `addSafeDirectory`/`addGlobalConfigValueIfMissing` [5](#0-4) . This value is a **path string with no owner binding and no expiry**. The invariant the UI implies to the user — "If you trust the *owner* of the directory you can add an exception" [6](#0-5)  — is not actually enforced: the exception is keyed on the path, not on the owner identity that was present at grant time. If the same path is later deleted and re-created by a different, untrusted OS user (a shared machine, CI runner with reused workspaces, a re-mounted network share, or a re-inserted removable/USB volume with the same mount point), Desktop's `getRepositoryType` will unconditionally treat it as safe again on the next visit, exactly as if it were still owned by the originally-trusted party. This mirrors the validator bug precisely: authorization was computed from stale state (the path's ownership *at grant time*) and is never re-checked against the entity's *current* state (its current owner/content) before being relied upon for subsequent operations.

### Impact Explanation
The warning text itself states the consequence: "Adding untrusted repositories may automatically execute files in the repository" [7](#0-6) . Once a path is silently re-trusted, any subsequent Desktop git operation (fetch, checkout, status, etc.) in that directory will run without Git's dubious-ownership protection, and Git's ownership-based hook/config protections exist specifically to stop an untrusted repository from having its `core.fsmonitor`, hooks, or config-driven filters executed. An attacker who gains control of a previously trusted path can therefore obtain silent code execution with the current Desktop user's privileges the next time that user (or Desktop's background refresh logic) touches the path — without ever seeing the "potentially unsafe" warning a first-time visitor would see.

### Likelihood Explanation
This requires the attacker to eventually gain write access to a filesystem path that a legitimate user previously trusted through Desktop — e.g. shared/multi-user workstations, lab machines, CI agents with recycled workspace directories, or removable media with stable mount points. This is a realistic, unprivileged scenario distinct from "physical access to the victim's live session" or "malware already on host": the attacker is a separate, otherwise-unprivileged actor who later reuses the same path once the original owner's data is gone. The bug is entirely in the missing re-validation logic, not in requiring elevated access.

### Recommendation
Do not persist `safe.directory` exceptions indefinitely and unconditionally keyed only on path. Consider recording the owner (e.g. SID/UID) validated at grant time alongside the path, and re-prompt/re-validate trust if the current owner differs from the one recorded when the exception was added; alternatively, scope trust exceptions to the specific repository the user added (validated against a stored fingerprint such as the initial commit or `.git` directory identity) rather than to a bare filesystem path that can be repopulated by anyone.

### Proof of Concept
1. On a shared machine, User A clones/creates a repo at `/shared/tmp/project`, and adds it in Desktop; Git flags it as "unsafe" (different owner) and User A clicks **Trust Repository**, causing `addSafeDirectory('/shared/tmp/project')` to write a permanent global config entry [5](#0-4) .
2. User A later deletes the repository (or it's cleaned up by CI) but the global `safe.directory` entry for that path remains, since nothing in the app removes it.
3. User B (or an attacker with an account on the same shared machine) creates a new, malicious Git repository at the exact same path `/shared/tmp/project`, containing crafted hooks/config.
4. User A (or an automated Desktop refresh under User A's session) revisits/re-adds that path. `getRepositoryType` runs `git rev-parse --is-bare-repository ...` [8](#0-7) ; because the path is already in the permanently-trusted `safe.directory` list, Git no longer reports `dubious ownership`, so Desktop treats it as a normal, safe repository and proceeds to run Git operations against the attacker-controlled content without any warning.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
```

```typescript
export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
```
