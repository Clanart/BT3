### Title
Unprivileged FIFO-eviction griefing lets an attacker burn any app's paid, unconsumed bandwidth allowance - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
This is the direct analog of the CLOB report's core primitive: a bounded, FIFO-ordered collection accepts unlimited cheap/attacker-controlled insertions, and once the cap is hit the *oldest* entry — which may belong to a legitimate, unrelated party and represent real, unconsumed value — is silently evicted. In the CLOB case that was resting limit orders; in Hyperbridge's `pallet-bandwidth` it is prepaid bandwidth `Subscription`s.

### Finding Description
`Allowance<T>` stores, per `(app_chain, app)`, a `BoundedVec<Subscription, MaxSubscriptions>` capped at `MAX_SUBSCRIPTIONS = 1024` [1](#0-0) . Every purchase message calls `push_subscription`, which, once the list is full, unconditionally removes index `0` (the oldest, i.e. FIFO head) and pushes the new entry, emitting `SubscriptionEvicted` with the lost bytes: [2](#0-1) .

Critically, the `(app_chain, app)` key that determines *whose* queue is mutated comes entirely from the purchase message body, not from `request.source` or any caller-authenticated identity:
- `on_accept` decodes `PurchaseMessage` and calls `push_subscription(&msg.chain, &key, ...)` where both `msg.chain` (the credit chain) and `key` (the app) are attacker-supplied fields of the message payload [3](#0-2) .
- The docs confirm this is intentional "sponsorship": "a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = 'EVM-8453'`" and "The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`" [4](#0-3) .

The only gate on `on_accept` is that `request.from` matches the registered `BandwidthManager` contract for that source chain [5](#0-4) . Any account holding fee tokens can call the on-chain `purchase()` entrypoint of the registered `BandwidthManager.sol`; there is no minimum price floor beyond "manager rejects purchases against a tier with a zero price" and no restriction preventing purchase of the cheapest configured tier (`TierOne`) with `months = 1` for an arbitrary victim `app`/`app_chain` pair [6](#0-5) .

This mirrors the CLOB bug's structure exactly:
- CLOB: bounded `bidTree`/`askTree` (`maxNumLimitsPerSide`) evicts the *least competitive* resting order when full, and an attacker can cheaply flood the book with throwaway orders to force eviction of legitimate resting orders.
- Bandwidth: bounded `Allowance` list (`MAX_SUBSCRIPTIONS = 1024`) evicts the *oldest* subscription when full, and an attacker can cheaply flood the (attacker-chosen) victim's queue with minimal Tier-1/1-month purchases to force eviction of the victim's expensive, unconsumed subscription — before the victim ever gets to spend those already-paid bytes.

The test suite explicitly documents this eviction-on-cap behavior (`subscription_cap_evicts_oldest`) as intended, but only validates admin `force_credit` calls, not the unprivileged, cross-app-targeting purchase path [7](#0-6) .

### Impact Explanation
This satisfies the "bandwidth balances must move exactly once and only to the rightful beneficiary and amount" invariant explicitly called out in scope. A victim application that has already paid for a large/long-duration bandwidth allotment (e.g. `TierFour`, 12 months, tens of GB) can have that allotment permanently destroyed by an attacker who spends comparatively little to push 1024 cheap `TierOne`/1-month purchases through the same `(app_chain, app)` queue. Because `expires_at` is fixed at purchase time and "never extends" and same-tier repurchases "don't stack — they queue" [8](#0-7) , there is no way for the victim to protect or reclaim the evicted, unconsumed bytes — this is a direct, permanent loss of already-paid protocol funds/value with the attacker paying a fraction of the destroyed value, an economically asymmetric griefing/fund-loss primitive.

### Likelihood Explanation
The attack requires no privileged role, relayer, prover, or governance access — only funds to submit ≥1024 cheap purchase messages via the permissionless, publicly deployed `BandwidthManager.sol::purchase()` entrypoint targeting an arbitrary `(app_chain, app)` pair known from `BandwidthCredited`/on-chain events. The eviction logic (`push_subscription`) contains no per-payer, per-purchase-size, or minimum-value checks preventing this, and the sponsorship design explicitly allows crediting (and therefore targeting) any app on any chain from any source chain.

### Recommendation
- Do not key eviction purely on FIFO age; instead evict based on remaining economic value (e.g. lowest `remaining_bytes` or soonest-expiring) similar to "worst" order eviction improvements, or better, disallow unauthenticated third parties from pushing into a queue that is already at capacity — reject the purchase (or require an explicit top-up path) instead of silently evicting.
- Consider rate-limiting or bonding purchases targeting a given `(app_chain, app)` from payers other than the app owner, or require a minimum subscription size/duration relative to existing queue entries to raise the cost of griefing.
- Alternatively, aggregate same-tier repurchases into a single row per tier (extend/stack) rather than queuing unboundedly, which removes the cheap-spam eviction vector entirely.

### Proof of Concept
1. Victim app `A` on `app_chain = EVM-8453` purchases `TierFour` for 12 months, crediting a large `remaining_bytes` allowance with a far-future `expires_at`. This creates 1 entry in `Allowance[(EVM-8453, A)]`.
2. Attacker (no special role) repeatedly calls `BandwidthManager.sol::purchase()` on any EVM chain with a registered manager, setting `tier = TierOne`, `months = 1`, and `chain = "EVM-8453"`, `app = A` in the ABI-encoded purchase body, 1024 times (across transactions/blocks, batched cheaply).
3. Each purchase dispatches a PostRequest to Hyperbridge; `on_accept` decodes the message and calls `push_subscription(&"EVM-8453", &A, TierOne, ...)`, appending to the same queue as the victim's entry [3](#0-2) .
4. On the 1025th push (i.e., attacker's last purchase), `push_subscription` evicts index `0` — the victim's `TierFour` 12-month subscription, which likely has not yet been drained since it was queued behind nothing but is now itself pushed out because *all* 1024 attacker entries preceded it in FIFO order relative to the cap, or, more directly, once the victim's paid entry ages into the head of a queue continuously refilled at capacity by attacker spam, it gets evicted before the app's own gate consumption drains it [9](#0-8) .
5. `Event::SubscriptionEvicted` fires reporting the victim's `lost_bytes`, confirming the victim's paid-for-and-unconsumed allowance is gone with no compensation, while the attacker paid only 1024× the cheapest tier price for a much larger destroyed value.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.

pub struct PurchaseMessage {
	/// Recipient app on the credit chain. Truncated to `AppKey` later.
	pub app: Vec<u8>,
	/// Tier discriminant; must map to a `TierIndex` variant.
	pub tier: u32,
	/// Multiplier on `cfg.bytes` and `cfg.duration_secs`. `0` is rejected.
	pub months: u32,
	/// Chain where the credit lands. Differs from `request.source` on
	/// sponsorship.
	pub chain: StateMachine,
}

/// `chain` is the UTF-8 form of `StateMachine::Display` (e.g.
/// `"EVM-8453"`) so EVM dapps can build it with string concat.
impl TryFrom<&[u8]> for PurchaseMessage {
	type Error = anyhow::Error;

	fn try_from(body: &[u8]) -> Result<Self, Self::Error> {
		let abi = BandwidthPurchaseMsg::abi_decode(body)
			.map_err(|err| anyhow::anyhow!(format!("invalid bandwidth purchase ABI: {err:?}")))?;

		let tier: u32 = abi.tier.try_into().map_err(|_| anyhow::anyhow!("tier exceeds u32"))?;
		let months: u32 =
			abi.months.try_into().map_err(|_| anyhow::anyhow!("months exceeds u32"))?;
		if months == 0 {
			return Err(anyhow::anyhow!("months must be >= 1"));
		}
		let chain_str = str::from_utf8(&abi.chain)
			.map_err(|err| anyhow::anyhow!(format!("chain is not utf-8: {err}")))?;
		let chain = StateMachine::from_str(chain_str)
			.map_err(|err| anyhow::anyhow!(format!("invalid chain {chain_str:?}: {err}")))?;

		Ok(PurchaseMessage { app: abi.app.into(), tier, months, chain })
	}

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
