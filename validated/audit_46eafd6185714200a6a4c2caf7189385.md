Based on my research, I was unable to locate a code path that decrements or resets the vote account's `pending_delegator_rewards` field (or debits the vote account's actual lamport balance) after `calculate_block_reward()` uses it to compute per-epoch payouts. I flag this explicitly as unconfirmed due to tool-call limits — a full verification would require tracing every consumer of `pending_delegator_rewards` across `runtime/src/bank/partitioned_epoch_rewards/*` and `programs/vote/src/vote_state/*`, which I could not complete. With that caveat, here is the strongest local analog I found to the reported bug class ("a shared reward pot is never depleted/attributed correctly, letting unprivileged parties repeatedly claim the same funds").

### Title
`pending_delegator_rewards` pot is read to mint stake-account block rewards every epoch but is never observed to be decremented on the vote account, letting delegators repeatedly claim the same deposited pot - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward()` reads `VoteStateView::pending_delegator_rewards()` off a vote account and uses it as the "pot" size to compute each delegator's share of block revenue for the epoch [1](#0-0) . That amount is then minted directly into stake accounts via `checked_add_lamports` in `build_updated_stake_reward()`/`store_stake_accounts_in_partition()`, increasing `capitalization` and `block_reward_lamports_distributed` [2](#0-1) [3](#0-2) . Meanwhile, the value is deposited into a vote account exclusively through `deposit_delegator_rewards`, which only ever *adds* to `pending_delegator_rewards` via `add_pending_delegator_rewards` [4](#0-3) [5](#0-4) , and the withdraw() guard treats it as a permanently reserved balance that can never be reduced below that amount [6](#0-5) . I could not find any function that subtracts consumed block-reward amounts from `pending_delegator_rewards`.

### Finding Description
This mirrors the Convex-SPELL bug's broken invariant: a pooled/shared value (CRV+CVX+extra rewards in SPELL / lamports deposited as `pending_delegator_rewards` in the vote account) is consumed by a payout mechanism that doesn't correctly reduce the tracked source, so the "same" funds remain available to be paid out again. In the vote program's case, `calculate_block_reward()` recomputes a delegator's proportional share of `pending_delegator_rewards` at every epoch's reward calculation, based on the delegator's `stake / total_active_stake` ratio [7](#0-6) . If the field is never decremented after distribution, the exact same pool of lamports is used as the payout basis every subsequent epoch, so delegators of that vote account receive freshly-minted lamports (via `checked_add_lamports`, which increases global `capitalization`) each and every epoch for the life of the vote account, rather than a single one-time distribution of the deposited amount.

### Impact Explanation
If confirmed, this allows any unprivileged staker delegated to a vote account with a nonzero `pending_delegator_rewards` to receive newly minted lamports every epoch indefinitely, off a "pot" that was only funded once via `deposit_delegator_rewards`. This inflates `capitalization` beyond what SIMD-0123 intends and effectively lets stakers "keep stealing" the same rewards epoch after epoch — directly analogous to attackers repeatedly invoking `_doRefund()` in the Convex report to drain a static reward balance that was never properly retired.

### Likelihood Explanation
Every epoch that has `block_revenue_sharing` enabled and stake delegated to a vote account with `pending_delegator_rewards > 0` will exercise `calculate_block_reward()` [8](#0-7) , so if the decrement is genuinely missing this would trigger automatically and repeatedly, with no attacker action needed beyond having stake delegated — this is the "unprivileged" trigger required by the task's valid-impact criteria.

### Recommendation
Trace the full lifecycle of `pending_delegator_rewards` to confirm whether/where it's decremented (e.g., inside `store_stake_accounts_in_partition`, `distribute_epoch_rewards_in_partition`, or a vote-account state update during distribution). If no decrement exists, block reward distribution must subtract the total amount distributed from the vote account's `pending_delegator_rewards` (and correspondingly debit the vote account's actual lamport balance) in the same atomic step that credits stake accounts, so the pot is monotonically consumed rather than reused every epoch.

### Proof of Concept
Not constructed — this requires runtime-level integration testing across multiple simulated epochs (deposit via `DepositDelegatorRewards`, enable `block_revenue_sharing`, advance two or more reward epochs, and check whether stake accounts receive the block reward share twice for the same deposited pool) rather than a single-file PoC, and I was unable to execute this within the available tool budget.

**Important caveat:** I was not able to fully verify the absence of a decrement path for `pending_delegator_rewards` due to running out of search iterations — it's possible such logic exists elsewhere (e.g., in vote-account state mutation code I didn't retrieve, such as `set_vote_account_state` calls during distribution, or `update_reward_commissions`). A Devin session with full read access to `runtime/src/bank/partitioned_epoch_rewards/` and `programs/vote/src/vote_state/` would be needed to conclusively confirm or refute this finding before treating it as a validated vulnerability.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
