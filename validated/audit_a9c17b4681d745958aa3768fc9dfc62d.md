## Analysis

Reducing the external report to its core primitive: a status-clearing function resets one flag but leaves a *dependent derived variable* stale, and that stale variable is later trusted by security-critical checks elsewhere. Searching Hyperbridge for this exact shape of bug in host-management/state-commitment logic surfaces a direct analog in `EvmHost.sol`'s state-commitment veto path.

`deleteStateMachineCommitmentInternal` is called by the handler when a fisherman vetoes a `StateCommitment` within its challenge period. When the vetoed height happens to be the tracked latest height for that state machine, instead of recomputing the actual latest still-valid height, it hard-codes the tracker to the sentinel value `1`: [1](#0-0) 

Compare this to `storeStateMachineCommitment`, whose own doc-comment states it "Assumes the state commitment is of the latest height" and unconditionally overwrites `_latestStateMachineHeight[height.stateMachineId] = height.height` without any ordering/monotonicity check inside the function itself: [2](#0-1) 

This mirrors the `milestoneSeason` bug precisely: `removeWhitelistStatus`/here `deleteStateMachineCommitment` mutates one piece of state (removes a commitment/whitelist flag) but corrupts a *different, dependent* bookkeeping variable (`milestoneSeason` / `_latestStateMachineHeight`) instead of properly recomputing or clearing it, and that variable is exactly the value other code paths rely on to decide whether newly-submitted state is legitimate "latest" state.

### Title
Vetoing a state commitment resets `_latestStateMachineHeight` to a hardcoded sentinel instead of the true prior height, undermining the monotonicity guarantee `storeStateMachineCommitment` assumes - (File: `evm/src/core/EvmHost.sol`)

### Summary
`deleteStateMachineCommitmentInternal` (invoked by the handler when a fisherman successfully vetoes a `StateCommitment`) resets `_latestStateMachineHeight[stateMachineId]` to the fixed value `1` whenever the vetoed height was the tracked latest, rather than restoring it to whatever the actual last-valid, non-vetoed height for that state machine is.

### Finding Description
`storeStateMachineCommitment` explicitly documents that it "Assumes the state commitment is of the latest height" and simply overwrites `_latestStateMachineHeight` with whatever height it is given [3](#0-2) . The correctness of the whole state-commitment/consensus pipeline (challenge periods, freshness checks, and any downstream comparison against "latest height") depends on `_latestStateMachineHeight` accurately reflecting the highest legitimately-accepted height.

When a fisherman vetoes the current latest commitment via `deleteStateMachineCommitment` → `deleteStateMachineCommitmentInternal`, the code does not walk back to the actual next-highest valid height that remains in `_stateCommitments`; it unconditionally collapses the tracker to `1` [4](#0-3) . This is the exact same defect class as the report: a removal/clearing operation silently corrupts a *different* bookkeeping variable that other logic relies on for validity checks, instead of properly recomputing or nulling it in a way consistent with its documented invariant.

### Impact Explanation
Because `storeStateMachineCommitment` blindly trusts `_latestStateMachineHeight` as the anchor for "latest" and performs no independent monotonicity check of its own, once the tracker is collapsed to `1`, any subsequently-verified consensus/state proof — even one for a height that is lower than a still-outstanding, previously finalized (non-vetoed) commitment for the same state machine — will be accepted and treated as the new latest height, overwriting the tracker again. This breaks the intended one-directional progression of state machine heights that consumers of `latestStateMachineHeight()` (documented as a public getter used by GET-request flows) and other height-freshness assumptions depend on, enabling stale or superseded state roots to be re-established as canonical after a legitimate veto event, i.e. false state acceptance.

### Likelihood Explanation
Vetoing is a permissionless, intended security mechanism — any fisherman with a valid fraud/veto proof can trigger `deleteStateMachineCommitment` on a legitimate commitment within its challenge period; no malicious relayer, prover, or admin collusion is required. The corruption of `_latestStateMachineHeight` happens deterministically every time the vetoed height equals the current latest, which is the common case (vetoes typically target the most recently posted commitment before its challenge period expires).

### Recommendation
On veto, recompute `_latestStateMachineHeight[stateMachineId]` from the actual remaining valid commitments (e.g., track heights in an ordered structure, or scan backward to the closest existing non-deleted commitment) instead of hardcoding it to `1`. Additionally, `storeStateMachineCommitment` should not blindly trust an externally-tracked "latest" value without an explicit height-ordering assertion at the point of storage.

### Proof of Concept
1. Handler calls `storeStateMachineCommitment` for `stateMachineId=X` at `height=100` → `_latestStateMachineHeight[X] = 100`.
2. A fisherman successfully vetoes height `100` via `deleteStateMachineCommitment` → `_latestStateMachineHeight[X]` is reset to `1` regardless of any other valid commitments that may exist for `X` [4](#0-3) .
3. A new consensus/state proof for `X` at `height=50` (lower than the previously-established `100`) is verified and `storeStateMachineCommitment` is invoked; since the function performs no comparison against a "true" previous height and just overwrites unconditionally, `_latestStateMachineHeight[X]` becomes `50`, and this stale height is now treated as the trusted latest state for `X` [5](#0-4) .

Note: I was unable to fully inspect `HandlerV2.sol`'s proof-verification flow (specifically whether it independently enforces height monotonicity before calling `storeStateMachineCommitment`) due to iteration limits; if such an independent check exists there, it would mitigate but not eliminate the underlying inconsistency of `_latestStateMachineHeight` being left in a semantically wrong state after veto. This should be verified against `evm/src/core/HandlerV2.sol` before treating severity as final.

     * @dev Store the state commitment at given state height alongside relevant metadata.
     * Assumes the state commitment is of the latest height.
     */
    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
