### Title
`DLEqProof::verify` accepts a proof bound to zero statements, allowing a forged proof that verifies nothing - (File: crypto/dleq/src/lib.rs)

### Summary
Analogous to CL-2021-44 — where the API token was required only on GET requests while POST/PATCH proceeded unauthenticated — `DLEqProof::verify` performs its challenge check unconditionally but never requires that any statement actually be verified. When `generators`/`points` are empty, the loop at crypto/dleq/src/lib.rs:171 executes zero times, so the equality check at line 175 reduces to comparing an attacker-chosen scalar `c` against a fully deterministic, publicly computable challenge. Any party can construct a `DLEqProof { c, s }` that "verifies" while binding to no generator/point statement at all.

### Finding Description
The Lighthouse bug was an auth check that existed but was skipped on a subset of inputs. Here, the verification is present but vacuously passes on a subset of inputs:

- `DLEqProof::verify` only checks `generators.len() != points.len()` (crypto/dleq/src/lib.rs:166) and then compares `self.c` to `challenge(transcript)` (line 175).
- With empty slices, the transcript contains only `domain_separate(b"dleq")` (line 170). `challenge()` (lines 28-85) then produces a deterministic scalar derived solely from the caller-supplied transcript prefix — no secret or statement is bound.
- `DLEqProof::read` (lines 191-193) accepts arbitrary `(c, s)` scalars from untrusted bytes, so a proof with `c` set to the precomputable challenge and any `s` is deserializable and passes `verify` for `generators == []`.
- `s` is never even used in the empty case: `verify_statement` (line 156), the only consumer of `s`, is never invoked. The signature half of the required check is entirely absent for this input class — the direct analog of "POST/PATCH processed without Authorization".

The same vacuity exists in `MultiDLEqProof::verify` (lines 264-294): empty `generators`/`points`/`s` vectors (all length-checked for equality, not non-emptiness) reduce it to the same attacker-controlled `c == challenge(transcript)` comparison.

### Impact Explanation
If any caller derives the number of DLEq statements from attacker-influenced data (e.g., a proof accompanying a variable-length key/commitment list where the list itself can be empty), a forged proof validates an assertion that was never made. This constitutes a forged proof acceptance under the stated criteria: `verify` returns `Ok(())` for a proof that establishes no discrete-logarithm equality, bypassing the intended authentication of the associated statement the same way Lighthouse processed unauthenticated mutations.

### Likelihood Explanation
Exploitation requires a call site where the statement list is attacker-controllable and can be empty while the proof itself is still trusted. Within the audited crates, fixed usages (e.g., generator promotion in PedPoP/musig contexts) supply non-empty generator slices, so the reachable surface depends on integrator paths feeding `DLEqProof::read`-produced proofs with attacker-influenced statement lists. That conditional reachability keeps this at Medium rather than High.

### Recommendation
Reject empty statement lists in `DLEqProof::verify` and `MultiDLEqProof::verify` (e.g., `if generators.is_empty() || points.is_empty() { Err(DLEqError::InvalidProof)? }`, and for `MultiDLEqProof` also reject empty inner vectors at crypto/dleq/src/lib.rs:279). Alternatively, transcript-bind `generators.len()`/`points.len()` so a proof cannot be replayed against a different statement count.
