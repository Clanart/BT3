## Analysis

The seed report's core broken invariant is: **an ERC20-compatibility code path silently accepts an outcome it should not, because the wrapper logic does not correctly validate the underlying token's real success/failure semantics** (in the ERC777 case, an overly strict flag caused false reverts; the general bug class is *mishandling non-standard ERC20 return-value semantics*).

Searching Hyperbridge's custody/settlement code, the Tron variant of `IntentGatewayV2` diverges from the main EVM contract's pattern (`ExtrinsicIntents.sol`, `IntrinsicIntents.sol`), which consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (these revert on both a low-level call failure *and* a returned `false`). The Tron variant instead performs raw low-level calls and only checks the call's `success` flag, never decoding/validating the returned boolean: [1](#0-0) 

and in the same file's admin `SweepDust` handling: [2](#0-1) 

### Title
IntentGatewayV2 (Tron) `withdraw()` treats ERC20 transfers returning `false` as success, permanently losing escrowed funds while marking orders settled - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse` for cancellations) releases escrowed input tokens using a raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself did not revert (`success`). It never decodes the ABI-encoded `bool` return value. Per the ERC20 standard, a compliant contract may legitimately return `false` on failure instead of reverting. In that case `success == true` (the low-level call executed without reverting) even though zero tokens moved, yet the code proceeds to decrement `_orders[...]`, mark the order settled, and emit `EscrowReleased`/`EscrowRefunded` as if funds were delivered.

### Finding Description
`withdraw()` iterates over escrowed tokens and performs:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only guards against calls that revert or hit non-contract addresses. It does not guard against ERC20 tokens that return `false` on failure (a well-known non-standard-but-valid behavior class, the same class of subtlety the seed ERC20/ERC777 report is about — token contracts not behaving exactly like the "ideal" ERC20/ERC777 model, and the bridging code failing to account for the discrepancy). If such a token is used as an order input/fee token and the transfer silently fails (`false`), the function still:
1. Decrements `_orders[body.commitment][token] -= amount;` — permanently zeroing out the escrow accounting for that leg.
2. Emits `EscrowReleased`/`EscrowRefunded`, signaling successful settlement.
3. Sets `_filled[body.commitment] = beneficiary;`

Because `_orders[...]` is now zero, `withdraw()` cannot be invoked again for that leg (the code above it reverts with `UnknownOrder()` if `_orders[...] == 0`), so the beneficiary can never claim the tokens through any other path. The tokens remain permanently locked in the `IntentGatewayV2` contract while the protocol's state says the order was fulfilled/refunded — false settlement state acceptance and loss/lock of the escrowed funds. The same unchecked-call pattern appears in the `SweepDust` handler.

### Impact Explanation
This directly violates the "moves exactly once and only to the rightful beneficiary and amount" custody invariant for order escrow/refunds. An unprivileged actor (the order creator, who freely chooses the input token when placing an order) can place an order using a token contract that returns `false` on failure under some condition they control (e.g., a token with a pausable/blacklist/fee-on-transfer edge case that returns `false` rather than reverting for certain transfers). When the escrow is later released or refunded, the beneficiary receives nothing, but the protocol marks the order permanently settled and zeroes the escrow record — resulting in stuck/lost funds and a false settlement record, with no recovery path.

### Likelihood Explanation
Requires only an unprivileged user to select or deploy a token with this non-reverting-failure behavior as an order's input asset — no relayer, prover, or governance compromise is needed. Solidity's `IERC20.transfer.selector` low-level call cannot distinguish "call succeeded, returned true" from "call succeeded, returned false" unless the return data is explicitly decoded, so this is a straightforward, reachable logic gap rather than a theoretical edge case.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and `SweepDust` handling with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in the main EVM `ExtrinsicIntents.sol`/`IntrinsicIntents.sol` contracts. `safeTransfer` correctly reverts both on a reverting call and on a call that returns `false`, ensuring escrow accounting is never decremented, and settlement events are never emitted, unless the transfer actually succeeded.

### Proof of Concept
1. Deploy/select a token `T` whose `transfer()` returns `false` (rather than reverting) when a specific condition is met (e.g., the beneficiary is blacklisted, or a fee-on-transfer edge case results in a defensive `return false`).
2. User places a cross-chain order using `T` as an input token, escrowing `amount` of `T` in `IntentGatewayV2` (Tron).
3. Order is filled/cancelled on the destination chain; a `RedeemEscrow`/`RefundEscrow` `PostRequest` arrives and `onAccept` invokes `withdraw()`.
4. Inside `withdraw()`, `token.call(...)` executes without reverting but returns encoded `false`; `success == true` so the check passes.
5. `_orders[commitment][token]` is decremented to 0 and `EscrowReleased`/`EscrowRefunded` is emitted, but the beneficiary's `T` balance is unchanged — the escrowed `T` remains stuck in the `IntentGatewayV2` contract with no further code path able to withdraw it for that commitment.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
