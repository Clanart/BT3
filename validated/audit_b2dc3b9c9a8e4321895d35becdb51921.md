### Title
Order-dependent Bash `if`-matcher routing in the security-guidance PostToolUse hook allows compound git commands to silently skip commit security review - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The `borg-core` report flags that condition-check systems whose correctness depends on evaluation order are fragile and can be bypassed by owner/operator mistakes. The strongest reachable analog in this repository is the `PostToolUse[Bash]` routing logic in `security_reminder_hook.py`, which explicitly depends on evaluating the "commit" branch before the "push" branch to guarantee the commit-security-review hook always fires for compound `git commit && git push` commands.

### Finding Description
`plugins/security-guidance/hooks/hooks.json` registers two independent `if` matchers under the same `Bash` matcher block — one firing on `Bash(git commit:*)` and one on `Bash(git push:*)`: [1](#0-0) 

Because Claude Code evaluates each `if` condition independently and spawns the hook script once per match, a compound command like `git commit -m x && git push` spawns the Python hook twice with the same `tool_use_id`. The script cannot distinguish which `if` triggered it, so it must independently re-derive which branch (commit-review vs. push-sweep) to run purely from the order in which the regex checks are evaluated: [2](#0-1) 

The code's own inline comments confirm the ordering is load-bearing and not incidental: "Routing therefore MUST check commit FIRST... The alternative — checking push first — would silently DROP commit-review on `git commit && git push`, which is a regression." A deduplication guard (`_claim_bash_hook_once`) resolves the race between the two spawned processes only by relying on that fixed check order plus the assumption that the commit-regex is checked before the push-regex in `if _GIT_COMMIT_RE.search(cmd): ... elif _GIT_PUSH_RE.search(cmd): ...`.

This mirrors exactly the reported bug class: the correctness of a security control (security review before a commit is pushed) depends entirely on an implicit, hard-coded ordering of condition checks rather than on an order-independent evaluation of all matched conditions. If a future edit reorders the `if`/`elif` chain, adds a new git-mutating subcommand pattern that matches earlier in the chain, or if a crafted compound command causes `_GIT_PUSH_RE` to match a value that should have triggered `_GIT_COMMIT_RE` first (e.g., unusual git aliasing, quoting, or ordering tricks within the compound Bash string), the `elif` structure guarantees commit-review is skipped in favor of the push-sweep path, silently dropping the security review for that commit.

### Impact Explanation
If the ordering assumption is violated (by a future code change or by an attacker-crafted command that causes the wrong branch to match first), the commit content is never reviewed by `handle_commit_review_posttooluse`, and the compensating push-sweep logic is explicitly documented as not covering the compound-call case ("the push-sweep does NOT run on the compound call"). This means a user-supplied git command could result in a commit being pushed with zero automated security review — a direct bypass of the plugin's core security guarantee (detecting secrets/dangerous changes before they leave the local repo), without any exception, error, or visible warning to the user.

### Likelihood Explanation
Exploiting this requires either (a) a maintainer/future contributor reordering the `if`/`elif` chain or introducing a new pattern that intercepts before the commit check (a plausible refactoring accident, as the code comments themselves warn against), or (b) constructing a compound Bash command whose `git commit` invocation is not matched by `_GIT_COMMIT_RE` but whose downstream `git push` is matched by `_GIT_PUSH_RE`, causing the routing to fall through to the push-sweep branch and lose the current commit's review. Since the exact regex definitions for `_GIT_COMMIT_RE`/`_GIT_PUSH_RE` could not be retrieved in this session (index size limits truncated that portion of the file), I cannot confirm a concrete input that defeats the current regexes today — the described risk is proven at the architecture level (the routing is explicitly order-dependent and self-documented as fragile), not proven end-to-end against the current regex patterns.

### Recommendation
Redesign the PostToolUse routing to be order-independent: derive the dispatch decision from which `if` matcher actually fired (e.g., via a per-invocation environment variable or argument passed by Claude Code indicating the matched pattern) rather than re-deriving it from an `if`/`elif` chain over the raw command string. Alternatively, always run both the commit-review and push-sweep logic for any compound command that matches both patterns, rather than relying on first-match-wins semantics, so that reordering the checks — or introducing a new pattern — cannot silently disable an existing security control.

    # Handle PostToolUse[Bash] — commit review or push sweep (asyncRewake).
    #
    # hooks.json has two `if` configs under the Bash matcher (`git commit:*`
    # and `git push:*`). CC evaluates each `if` independently and spawns this
    # script ONCE PER MATCH — so `git commit -m x && git push` spawns python
    # twice with the same command string and the same tool_use_id. The python
    # cannot tell which `if` fired it.
    #
    # Routing therefore MUST check commit FIRST so that compound commit+push
    # commands continue to hit commit-review (the pre-existing behaviour) on
    # the commit-matcher invocation. The push-matcher invocation of the SAME
    # compound command is deduped by `_claim_bash_hook_once` below: the second
    # spawn loses the tool_use_id sentinel race and exits early with
    # `bash_hook_dedup`, so commit-review runs exactly once. The alternative —
    # checking push first — would silently DROP commit-review
    # on `git commit && git push`, which is a regression.
    #
    # The push-sweep does NOT run on the compound call. That's acceptable: the
    # just-made commit is recorded by commit-review, so the next standalone
    # push sees it as reviewed and the sweep base advances past it. Older
    # unreviewed commits in the range are caught on that next push.
    if tool_name == "Bash" and hook_event_name == "PostToolUse":
        cmd = (input_data.get("tool_input") or {}).get("command", "") or ""
        if not (_GIT_COMMIT_RE.search(cmd) or _GIT_PUSH_RE.search(cmd)):
            return
        if not _claim_bash_hook_once(input_data):
            # Another spawn for this same tool_use_id already claimed the
            # work (compound matched multiple `if` configs). Emit a single
            # metric so telemetry can count how often the de-dupe kicks in.
            print(json.dumps({"metrics": {"bash_hook_dedup": True}}), flush=True)
            sys.exit(0)
        if _GIT_COMMIT_RE.search(cmd):
            handle_commit_review_posttooluse(input_data)
        elif _GIT_PUSH_RE.search(cmd):
            handle_push_sweep_posttooluse(input_data)
        return
