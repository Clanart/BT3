### Title
OP_RETURN data output excluded from fee/weight calculation causes underpaid fee and potentially unbroadcastable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying user-supplied `data` to the transaction's outputs, but computes the transaction weight/vbytes — and therefore `needed_fee` and the minimum-relay-fee check — using only `payments`. The bytes of the `OP_RETURN` output are never accounted for, so the actual fee rate of the produced transaction is lower than `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` while still passing the internal `TooLowFee` check.

### Finding Description
The bug class from the external report — an amount is partially consumed but the subsequent operation still uses the un-adjusted total — maps here to outputs being committed to the transaction but omitted from the size/fee accounting.

In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` before the weight calculation:

- `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` at `networks/bitcoin/src/wallet/send.rs:194-202`
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` at `send.rs:204`

`calculate_weight_vbytes` builds a template transaction whose outputs are derived solely from `payments` (plus optional `change`); it never sees `data` (`send.rs:85-99`). Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed on a smaller vbytes than the real transaction.
2. The minimum-fee sanity check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) uses the same underestimated `vbytes`, so it can pass while the real fee rate is below the relay minimum.
3. The same omission applies to the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (`send.rs:225-226`) still excludes the `OP_RETURN`, and the change value `input_sat - (payment_sat + fee_with_change)` (`send.rs:228`) overpays the change output by `fee_per_vbyte * <OP_RETURN vbytes>` — satoshis that were earmarked for fee are instead sent to change, further lowering the effective fee rate.
4. The final `weight > MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) also uses the understated weight.

The actual fee paid is `sum(inputs) - sum(outputs)` (`send.rs:138-141`), which equals the miscalculated `needed_fee` (or less when change is created), spread over a larger real transaction.

### Impact Explanation
An unprivileged user able to attach `data` (up to 80 bytes, `send.rs:171-172`) to a withdrawal/transaction request can force the multisig to produce and sign a transaction whose effective fee rate is below `fee_per_vbyte`, and below Bitcoin's default minimum relay fee when `fee_per_vbyte` is near the floor. Such a transaction is rejected by `send_raw_transaction`/mempool acceptance, stalling the signed plan and requiring re-signing — a liveness failure on funds, reachable purely from public inputs (the `data` bytes and payment amounts the caller supplies). The unsigned satoshis misdirected into the change output (`fee_per_vbyte * ~OP_RETURN size`) are also a concrete, deterministic accounting error, mirroring the original double-accounting pattern.

### Likelihood Explanation
Any caller supplying non-empty `data` triggers the miscalculation deterministically; no race or attacker collusion is needed. Whether the resulting transaction is actually unrelayable depends on `fee_per_vbyte` proximity to the 1 sat/vbyte relay floor — at low fee rates the ~23–93 omitted vbytes can push the effective rate below minimum. Even when relayable, the fee is always lower than requested, degrading confirmation priority for every data-carrying transaction.

### Recommendation
Include the `OP_RETURN` output in the weight template. Pass the full output list (or the `data` length) into `calculate_weight_vbytes`, e.g., extend its signature to accept `data: Option<&[u8]>` and push `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }` into the template transaction before calling `tx.weight()`. This fixes `needed_fee`, the `TooLowFee` check, the change-amount subtraction, and the `MAX_STANDARD_TX_WEIGHT` check simultaneously.

### Proof of Concept
```
// inputs: one ReceivedOutput of value V
// payments: [(script, P)] with P >= DUST
// change: None
// data: Some(vec![0u8; 80])
// fee_per_vbyte = 1 (1 sat/vbyte)

let tx = SignableTransaction::new(inputs, &payments, None, Some(data), 1).unwrap();

// tx.needed_fee() == vbytes(tx_without_op_return) * 1
// real vsize == vbytes(tx_without_op_return) + ~92 vbytes (OP_RETURN output)
// effective fee rate = needed_fee / real_vsize < 1 sat/vbyte
//   => below DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB)
// The TooLowFee check at send.rs:211 used the underestimated vbytes,
// so it did not fire, yet the signed TX is rejected by relay policy.
// With change: change additionally receives ~92 extra sats meant for the fee.
```
