This intent-settlement escrow logic has a real analog to the Rocket Pool bug: a multi-step "guaranteed withdrawal" whose atomicity depends on a call the beneficiary/attacker can make fail.

### Title
Malicious order creator can permanently strand solver escrow by including an unconditionally-reverting input token — `_withdraw` is all-or-nothing across multiple tokens - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`/`IntentsBase._withdraw` releases every escrowed input token for an order in a single loop with no per-token isolation. A solver who fills a cross-chain order delivers real value on the destination chain first; settlement of the solver's escrowed reward on the source chain then happens via `onAccept` → `_withdraw`, iterating over *all* of the order's input tokens in one atomic call [1](#0-0) . If the order creator includes, among the order's `inputs`, one token that reverts on transfer (a custom malicious ERC20, or a standard blacklist-capable token like USDC/USDT where the solver address gets blacklisted), the `safeTransfer` for that single token reverts the whole `_withdraw` call, which reverts the whole `onAccept`, which causes `EvmHost.dispatchIncoming` to treat the message as failed and simply delete the receipt for a retry [2](#0-1) . Because the failing token's behavior is permanent (constant revert, or a persistent blacklist), retries fail forever, and *every other, perfectly good token in the same order* is locked with it — even though the solver already delivered the promised output on the destination chain.

### Finding Description
The intent lifecycle promises that once a solver fills an order (delivering real output tokens to the beneficiary on the destination chain) and the `RedeemEscrow` settlement message lands on the source chain, the solver's escrowed input tokens will be released [3](#0-2) . This is the "withdrawal should always succeed once authorized" invariant, mirroring the Rocket Pool report.

`_withdraw` implements this release as a single loop over `body.tokens`, decrementing accounting and transferring each token in turn [4](#0-3) . There is no `try/catch` around individual transfers and no mechanism to skip or quarantine one bad token while releasing the rest. A single `IERC20(token).safeTransfer` revert (blacklist, pausable token, malicious token designed to always fail) reverts the entire transaction. The same `_withdraw` function backs both the `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) paths, and is also invoked from `onGetResponse` for source-initiated cancellations [5](#0-4) , so the same failure mode blocks cancellation refunds too.

`EvmHost.dispatchIncoming` only protects against *complete unavailability* of the destination contract (zero code size) with an early return; any other revert from the app's `onAccept` is caught by the low-level `.call` and treated as "retry later" by deleting the receipt [6](#0-5) . This retry mechanism assumes the failure is transient. It is not transient here — an attacker chooses a token whose failure condition is permanent, so the message can be resubmitted indefinitely and will always fail.

The order creator fully controls `order.inputs` at placement time (there appears to be no allowlist enforced by the escrow logic itself), so an attacker can pair one legitimate, valuable input token with one deliberately-poisoned token in the same order.

### Impact Explanation
An unprivileged attacker (the order creator) can craft an order whose `inputs` array mixes a valuable token with a token engineered to permanently revert on transfer to the solver. A solver, unaware of the poison, fills the order and delivers real output value to the beneficiary on the destination chain. When the `RedeemEscrow` settlement message arrives on the source chain, `_withdraw` reverts on the poisoned token and never completes — locking the solver's entire escrowed reward, including the legitimate token, permanently. This is a direct loss-of-funds vector against solvers with no relayer, prover, or governance collusion required, and it also blocks the `RefundEscrow`/cancellation path for the same order, so even the original depositor cannot recover the good token either — the funds are simply stuck in the gateway.

### Likelihood Explanation
High for a motivated attacker: deploying a token contract that reverts unconditionally (or is designed to look benign but blacklist the expected solver) is trivial, and nothing in `placeOrder`/`fillOrder` inspects token behavior before escrow. The only requirement is that a solver actually fills the order, which is economically likely since the order can advertise an attractive output/fee to bait solvers.

### Recommendation
Do not make the multi-token release atomic across unrelated tokens. Either:
- Wrap each token transfer in `_withdraw` in a low-level call with `try/catch` semantics (e.g. via a helper that swallows a single token's failure), crediting a per-beneficiary "stuck balance" that can be withdrawn later or skipped, so a single bad token cannot block release of the others; or
- Validate/allowlist acceptable input tokens at order-placement time so arbitrary attacker-supplied tokens cannot enter escrow; or
- Split settlement into independent per-token transfers driven by separate calls/receipts instead of one all-or-nothing loop, so a failing token only blocks itself.

### Proof of Concept
1. Attacker deploys `PoisonToken`, an ERC20 whose `transfer`/`transferFrom` always succeeds during `placeOrder` (escrow deposit) but always reverts on any subsequent `transfer` call (e.g. hardcode `revert()` in `transfer`).
2. Attacker calls `placeOrder` with `order.inputs = [GoodToken(1000), PoisonToken(1000)]`, offering an attractive output on the destination chain.
3. A solver calls `fillOrder` on the destination chain, delivering the promised output tokens to the beneficiary [7](#0-6) ; the cross-chain `RedeemEscrow` message is dispatched back to the source chain.
4. On the source chain, `onAccept` decodes the `RedeemEscrow` request and calls `_withdraw({tokens: [GoodToken, PoisonToken], beneficiary: solver}, false, true)` [3](#0-2) .
5. The loop transfers `GoodToken` successfully, then reaches `PoisonToken` and `safeTransfer` reverts, unwinding the whole `_withdraw`/`onAccept` call.
6. `EvmHost.dispatchIncoming` sees `success == false`, deletes the receipt, and the message is left retryable — but every retry hits the same `PoisonToken` revert forever [2](#0-1) .
7. Result: the solver never receives `GoodToken` (or `PoisonToken`) despite having already delivered the output on the destination chain — permanent fund loss for the solver, with the attacker paying nothing beyond gas.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);

        assembly {
            size := extcodesize(destination)
        }

            // instead of reverting the entire batch, early return here.

        if (!success) {
            // so that it can be retried

            return;
