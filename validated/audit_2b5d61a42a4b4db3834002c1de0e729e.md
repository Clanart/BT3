## Title
Recursive clone unconditionally disables Git's built-in clone-protection safeguard, enabling hook/config injection from a malicious cloned repository - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in `app/src/lib/git/clone.ts` runs every `git clone --recursive` invocation with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'`. This variable is Git's own runtime safety valve, meant to be `true` by default, that blocks a class of attacks where a maliciously crafted repository (including nested submodules) tricks the clone/checkout machinery into writing files into `.git/hooks` (via symlink or case-insensitive/short-name path collisions) and getting an executable hook run automatically. By overriding it to `'false'` unconditionally, Desktop actively defeats this Git-level protection for every clone it performs, on every platform, whether the URL/content is trusted or not.

### Finding Description
`app/src/lib/git/clone.ts` builds the environment for the `git clone --recursive` invocation like this: [1](#0-0) 

```
const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
]
```

This is invoked from `CloningRepositoriesStore.clone()` [2](#0-1)  which is reachable from fully attacker-influenced flows: the "Clone repository" dialog (arbitrary URL entry) and the `x-github-client://openRepo`/`openRepositoryFromUrl` deep-link handler that clones a URL supplied entirely by whatever page or message sent the link [3](#0-2) .

The only defensive check present in `clone.ts` is `isClonePathSensitive()`, which validates the *destination directory string* against a list of sensitive local paths (home dir, `.ssh`, `.gnupg`, etc.) [4](#0-3) . That check says nothing about the *content* of the repository being cloned, and does nothing to compensate for the disabled protection: it cannot detect a submodule tree engineered to collide with `.git/hooks`, `.git/config`, or similar sensitive git-internal paths via case-folding or symlink tricks on the destination filesystem, which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` exists to stop.

This directly mirrors the reported bug class: a guard that is supposed to gate a sensitive state transition (here, "don't let clone content write into git-internal control paths") is bypassed — except here it isn't bypassed via ordering/reentrancy, it is disabled outright by the calling code itself, for every invocation, with no compensating re-check afterward. The attacker's primitive ("attacker controls a cloned/fetched repository") is exactly one of the explicitly in-scope primitives for this task.

### Impact Explanation
If a user clones (or is induced to clone via a deep link/"Open in Desktop" flow) a repository controlled by an attacker, and that repository/its submodules are crafted to exploit the class of collision Git's own clone protection is designed to stop, the attacker can get an executable file placed into the resulting repository's real Git hooks directory (or otherwise inject configuration/executables) and have it silently executed on a subsequent Git operation (checkout, commit, etc.) performed inside Desktop or by the user's own `git` — i.e., code execution triggered purely by cloning a repository, with no additional unnatural user action required. This satisfies the reported "code execution reachable via a cloned/fetched repository" impact class.

### Likelihood Explanation
Likelihood is high in terms of reachability — cloning is a core, everyday Desktop action, triggered both interactively and via URL/deep-link with a fully attacker-supplied remote. The residual uncertainty is how easy it is, on the tester's exact filesystem/Git version, to construct a payload that Git's disabled protection would otherwise have blocked (this depends on filesystem case-sensitivity/short-name behavior and the bundled `dugite`/Git version's exact hook-write vector); I was not able to execute Git locally to confirm a working end-to-end PoC payload, only to confirm from source that the protection is explicitly and unconditionally turned off for every recursive clone in this codebase.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Let Git's clone protection run with its safe default (`'true'`) for all clones performed by Desktop. If there was a specific compatibility reason for disabling it (e.g. a legitimate submodule layout being rejected), that should be handled by surfacing the failure to the user rather than blanket-disabling the safeguard, and any bypass should be scoped/audited rather than unconditional.

### Proof of Concept
Not independently reproduced (no terminal/filesystem access in this environment to construct the exact case-collision/symlink submodule payload and confirm hook execution). The finding is based on direct source inspection: [5](#0-4)  shows `GIT_CLONE_PROTECTION_ACTIVE` is unconditionally forced to `'false'` for the `git clone --recursive` command used by every clone path in the app, including the fully attacker-controlled URL clone flow (`openOrCloneRepository` / `openRepositoryFromUrl`) [3](#0-2) . A full PoC would require crafting a repository with a submodule/path structure that Git's disabled protection specifically targets and verifying, on a real checkout, that a hook file lands in `.git/hooks` and executes — recommend a Devin session with terminal/filesystem access to build and validate this payload against the bundled Git version.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
