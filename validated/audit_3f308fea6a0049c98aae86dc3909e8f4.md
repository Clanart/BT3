### Title
Concurrent map write due to `RWMutex.RLock()` misuse guarding a map write in gasless `PreAddTx` - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
`GaslessModule.PreAddTx`, the `kaiax.TxPoolModule` hook invoked for every transaction submitted to the tx pool, takes only a **read** lock (`g.knownTxsMu.RLock()`) but then performs a **write** to the shared `knownTxs` map (`g.knownTxs.add(tx, TxStatusQueue)`) inside that same "read" critical section. `sync.RWMutex.RLock()` permits multiple goroutines to hold the lock concurrently, so any two goroutines that both enter `PreAddTx` at the same time will both proceed to mutate the `knownTxs` map (`k[tx.Hash()] = &knownTx{...}`) without mutual exclusion between themselves, producing a data race that can crash the process with Go's unrecoverable `fatal error: concurrent map writes`.

### Finding Description
`knownTxs` is a plain `map[common.Hash]*knownTx` (`kaiax/gasless/impl/tx_counter.go`), and every other accessor of it in the gasless module (`IsReady`, `PreReset`, `PostReset`) correctly acquires the **exclusive** `g.knownTxsMu.Lock()` before calling `add`/`delete`: [1](#0-0) [2](#0-1) [3](#0-2) 

However, `PreAddTx` — the hook fired for every transaction accepted into the pool (approve/swap "bundle" transactions used by the gasless flow) — takes only an `RLock`, then still calls the mutating `knownTxs.add`: [4](#0-3) 

`knownTxs.add` is an unsynchronized map write (`k[tx.Hash()] = &knownTx{...}`) with no internal locking of its own — it depends entirely on the caller holding the correct mutex mode: [5](#0-4) 

Because `RLock()` grants **shared** access, two (or more) goroutines that call `PreAddTx` concurrently can both pass the `RLock()` gate simultaneously and both execute `g.knownTxs.add(...)`, writing to the same Go map from two goroutines with no synchronization between them — the exact "concurrent map read and map write" / "concurrent map writes" bug class from the referenced Mailpit advisory (unsynchronized access racing against a lock-protected mutator of the same map). This also races against `IsReady`/`PreReset`/`PostReset`, which correctly take the exclusive `Lock()` but offer no protection against the two-reader race created by `PreAddTx`'s misuse of `RLock`.

### Impact Explanation
A Go runtime `fatal error: concurrent map writes` (or `concurrent map read and map write`) is a `runtime.throw`, which — exactly as described in the Mailpit advisory — is **not recoverable** by any `defer/recover`, including the node's own top-level panic guards. The whole `kaia` process (CN/EN/PN) terminates: consensus/mining, RPC, P2P, everything goes down simultaneously. This is a full node crash triggerable by an unprivileged, unauthenticated actor purely by submitting transactions — a Medium/High-impact remote DoS.

### Likelihood Explanation
`PreAddTx` is invoked by the standard tx-pool add path for every incoming transaction wherever the gasless `TxPoolModule` is registered, and it specifically special-cases gasless "bundle" (approve/swap) transactions, which are trivial and cheap for anyone to craft (no special privilege, no state precondition beyond a validly signed tx matching the approve/swap ABI signatures checked by `IsBundleTx`). Any RPC-reachable node that accepts concurrent transaction submissions (`eth_sendRawTransaction`/`klay_sendRawTransaction`, batched, or via multiple concurrent client connections) is a candidate trigger surface. The likelihood of two `PreAddTx` invocations racing depends on the pool's outer locking discipline; regardless of whether an outer `pool.mu` incidentally serializes some call paths today, the code as written is a genuine `RWMutex` misuse (mixing `RLock` with a map mutation) that is unsafe by construction and is flagged as racy by `go build -race`, matching exactly the class of pre-existing but latent race the Mailpit report demonstrates. Because I couldn't fully trace every txpool call path that reaches `PreAddTx` outside of the exclusive `pool.mu`-held `add()`/`addTxsLocked()` flows within the remaining tool budget, I cannot rule out a code path (e.g., a future or existing pre-lock validation stage, or a second module instance) that invokes `PreAddTx` concurrently without additional serialization — the bug is present and exploitable in principle even if the current single call path is serialized elsewhere, because the lock usage itself is incorrect regardless of caller.

### Recommendation
Change `g.knownTxsMu.RLock()`/`RUnlock()` to `g.knownTxsMu.Lock()`/`Unlock()` in `PreAddTx` (matching `IsReady`, `PreReset`, `PostReset`), since the function mutates `knownTxs` via `g.knownTxs.add(...)`. If read-only fast-path checks are desired for performance, split the function so the initial `knownTxs.get` check uses `RLock` and releases it before re-acquiring `Lock` for the `add` call, taking care to re-validate state after the lock upgrade (classic TOCTOU consideration).

### Proof of Concept
1. Run a node with the gasless `TxPoolModule` enabled.
2. Craft two distinct, validly-signed "bundle" transactions recognized by `IsBundleTx` (e.g., ERC20 `approve` calls to the gasless router matching `IsApproveTx`, or gasless `swap` calls matching `IsSwapTx`) from different senders.
3. Submit them concurrently to the node's tx pool (e.g., via concurrent `eth_sendRawTransaction` RPC calls or via `TxPool.AddRemotes` with a batch), repeating in a tight loop with many goroutines to increase the chance both invocations of `GaslessModule.PreAddTx` execute their `RLock`-protected sections at the same instant.
4. When both goroutines simultaneously execute `g.knownTxs.add(tx, TxStatusQueue)` (an unsynchronized `map[hash] = ptr` write) under only a shared `RLock`, the Go runtime detects the concurrent map mutation and raises `fatal error: concurrent map writes`, terminating the entire node process (confirmable deterministically by building with `go build -race` and observing a `WARNING: DATA RACE` at `kaiax/gasless/impl/tx_counter.go` line 53/62/64 triggered from two concurrent `kaiax/gasless/impl/tx_pool.go` `PreAddTx` calls).

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
