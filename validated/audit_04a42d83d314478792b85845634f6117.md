## Title
Untrusted Git/API error text (branch names, remote URLs, messages) is logged to disk without ANSI-escape sanitization, enabling terminal-escape-sequence injection when the log is later viewed - (File: `app/src/lib/logging/format-log-message.ts`, `app/src/lib/logging/format-error.ts`, `app/src/main-process/log.ts`)

## Summary
`formatLogMessage()` / `formatError()` copy an `Error`'s `.message`/`.stack` verbatim into the string that is handed to `log()`, and `log()` writes that string byte-for-byte to the daily log file via `DesktopFileTransport`. No stage in this pipeline strips or escapes control characters (e.g. `\x1b[`), so any attacker-controlled substring embedded in a git error (a malicious branch name, remote URL, ref name, or API error message) that contains ANSI escape sequences is persisted raw in the log file.

## Finding Description
- `formatLogMessage(message, error)` simply forwards to `formatError(error, message)` when an error is present. [1](#0-0) 
- `formatError()` builds the final string from `error.stack` (or `error.name`/`error.message` as fallback) with no character filtering. [2](#0-1) 
- `g.log.error/warn/info/debug` (installed by `main/install.ts`) call `formatLogMessage` and pass the result straight into `log()`. [3](#0-2) 
- `log()` in `app/src/main-process/log.ts` hands the message to winston, which is configured with `winston.format.simple()` and a `printf` formatter that does nothing but prepend a timestamp/level — again no sanitization. [4](#0-3) 
- `DesktopFileTransport.log()` writes `info[MESSAGE]` directly to the write stream with `fs.createWriteStream`, with no escaping of control characters. [5](#0-4) 

Git command failures (e.g., from `dugite`/`GitProcess`) frequently embed attacker-influenced text — such as a ref/branch name, remote URL, or stderr output — directly in the thrown `Error.message`, and Desktop's error-handling code logs these via `log.error(message, error)`. Since none of `formatLogMessage`, `formatError`, `log`, or `DesktopFileTransport` filters control characters, a git error whose message/stack contains raw ANSI escape sequences (`\x1b[...`) will be written to the `.desktop.<channel>.log` file unmodified.

## Impact Explanation
The impact is confined to what happens when a human (or a tool) later renders that log file in a terminal that interprets ANSI/OSC escape sequences (e.g., via `cat`, `less -r`, `tail`, or many log viewers). Depending on the sequences and the terminal emulator, this can range from cosmetic corruption (altering displayed text, hiding/obscuring parts of the log — which is itself a log-forgery/log-injection risk useful for hiding malicious footprints from a person auditing logs) up to more severe consequences on terminals that implement dangerous OSC handlers (e.g., clipboard write via OSC 52, terminal title manipulation, or in vulnerable terminal emulators, sequences that can trigger further actions). This is a classic log/terminal-injection issue rather than a direct renderer/IPC exploit inside Desktop itself — the "trigger" for real damage happens outside of Desktop's own process, when a human opens the raw log file in a permissive terminal.

## Likelihood Explanation
Likelihood of the write occurring is high: any git operation on a repository/remote with attacker-chosen refs, URLs, or error text that reaches `log.error` will be persisted verbatim, and this is a normal, frequently-hit code path (failed clones/fetches/pushes routinely log the underlying git error). Likelihood of it being *observed/exploited* is lower, since it requires a person to view the raw log file in a terminal that both doesn't sanitize and is susceptible to the specific escape codes used — this is not something that happens automatically inside GitHub Desktop's own UI (the app does not `cat` its own logs to a terminal as part of normal operation).

## Recommendation
Strip or escape ANSI/control characters (anything matching `/\x1b\[[0-9;]*[a-zA-Z]/` and other C0 control codes except `\n`/`\t`) from `message`/`error.message`/`error.stack` before they are combined in `formatError()`/`formatLogMessage()`, or apply the same sanitization centrally in `DesktopFileTransport.log()` right before writing to disk, so untrusted repository/API text can never inject raw escape sequences into the persisted log file.

## Proof of Concept
1. Create/clone a repository and create a branch whose name contains a raw ESC byte followed by an ANSI sequence, e.g. `git checkout -b $'legit\x1b[8m-hidden\x1b[0m'` (or craft a remote URL / ref with the same payload where git will echo it back in an error).
2. Trigger an operation that fails and surfaces the branch/ref/URL in the git error text (e.g., attempt to push/fetch/checkout in a way that causes git to error out referencing that branch name), causing Desktop's git wrapper to construct an `Error` whose `.message`/`.stack` contains the payload.
3. Confirm that this error reaches `log.error(message, error)` (from `main/install.ts`), which calls `formatLogMessage` → `formatError` → `log()` → `DesktopFileTransport`.
4. Open the resulting `YYYY-MM-DD.desktop.<channel>.log` file in a terminal (`cat` it) and observe that the escape sequence is interpreted (text hidden/formatted) rather than displayed as literal characters, confirming the raw, unescaped persistence. [1](#0-0) [2](#0-1) [6](#0-5) [5](#0-4)

export function formatError(error: Error, title?: string) {
  error = withSourceMappedStack(error)

  if (error.stack) {
    return title ? `${title}\n${error.stack}` : error.stack.trim()
  } else {
    return title
      ? `${title}\n${error.name}: ${error.message}`
      : `${error.name}: ${error.message}`
  }
}

function initializeWinston(path: string): winston.LogMethod {
  const timestamp = () => new Date().toISOString()

  const fileLogger = new DesktopFileTransport({
    logDirectory: path,
    level: 'info',
    format: winston.format.printf(
      ({ level, message }) => `${timestamp()} - ${level}: ${message}`
    ),
  })

  // The file transport shouldn't emit anything but just in case it does we want
  // a listener or else it'll bubble to an unhandled exception.
  fileLogger.on('error', noop)

  const consoleLogger = new DesktopConsoleTransport({
    level: process.env.NODE_ENV === 'development' ? 'debug' : 'error',
  })

  winston.configure({
    transports: [consoleLogger, fileLogger],
    format: winston.format.simple(),
  })

  return winston.log
