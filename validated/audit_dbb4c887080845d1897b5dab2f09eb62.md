### Title
`withdrawMultipleDelegationRewards` aborts the entire multi-validator reward withdrawal when a single validator's payout fails - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile's `withdrawMultipleDelegationRewards` iterates over a caller-supplied list of validator addresses and withdraws rewards for each one in a single loop. If the payout for any one validator in the list fails (e.g. because `SendCoinsFromModuleToAccount` rejects the delegator's configured withdraw address), the whole call reverts and none of the rewards — including the ones for validators whose payout would have succeeded — are paid out. This mirrors the reported OpenQ bug where a single "blocked" token in the loop causes the entire claim to fail for the user.

### Finding Description
`withdrawMultipleDelegationRewards` takes an array of validator addresses from the caller and withdraws rewards for each one by calling `p.withdraw` in a loop; any error from a single iteration causes an immediate `rerr = err; return`, aborting the whole precompile call: [1](#0-0) 

`p.withdraw` calls `p.distrKeeper.WithdrawDelegationRewards`, which for a single validator resolves the delegator's configured withdraw address and sends coins via `SendCoinsFromModuleToAccount`: [2](#0-1) 

The underlying `sei-cosmos/x/distribution/keeper/delegation.go` `withdrawDelegationRewards` performs `k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, withdrawAddr, finalRewards)` and returns the bank error unmodified if it fails: [3](#0-2) 

`SendCoinsFromModuleToAccount` fails with an error if the recipient address is on the bank module's block-list (`BlockedAddr`): [4](#0-3) [5](#0-4) 

The codebase already acknowledges this exact class of "blocked withdraw address" failure mode: a dedicated test shows that a coinbase-prefixed withdraw address passes `CanSendTo` but is rejected by `BlockedAddr`, and the comment explicitly notes that "`SendCoinsFromModuleToAccount` would later panic the force-withdraw in `AfterValidatorRemoved` during EndBlock" if this weren't caught up front at `SetWithdrawAddr` time: [6](#0-5) 

That mitigation only covers `SetWithdrawAddr`. It does not change the fact that `withdrawMultipleDelegationRewards` performs an all-or-nothing loop: if a delegator's single withdraw address becomes blocked for any reason after being validly set (or if any per-validator payout hits a bank-level restriction — e.g. `IsInDenomAllowList`/`BlockedAddr` checks reachable through `SendCoins`), the caller cannot withdraw rewards from *any* of the validators in the batch, even the ones that would have succeeded individually via `withdrawDelegationRewards` (singular).

### Impact Explanation
A delegator who batches multiple validators into one `withdrawMultipleDelegationRewards` call can be fully denied their entire batch of rewards if withdrawal fails for even one validator in the list, even though each individual `withdrawDelegationRewards` call would have succeeded on its own. This is a fund-availability/DoS issue for a legitimate unprivileged caller (a delegator calling the EVM distribution precompile), consistent with the "Medium" severity of the analog bug (temporary loss of ability to claim funds through the batched API; funds are not permanently lost since the single-validator withdraw path still works, but the batching feature loses its atomic-success guarantee and can be weaponized to force reverts).

### Likelihood Explanation
The withdraw address for a given delegator is shared across all validators, so a delegator's own withdraw address is either blocked for all validators or none — meaning within a single delegator's own batch this scenario requires the delegator's withdraw address to already be blocked (which `SetWithdrawAddr` now tries to prevent for the coinbase case, but bank block-lists / send-enable / allow-list checks can vary by denom and could differ per reward-denom composition per validator). The precise reachability of a *partial* failure within one delegator's own validator list is less certain without deeper trace of every reward denom-specific restriction path (e.g. tokenfactory `IsInDenomAllowList` per denom) that could differ per validator's specific reward coin set.

### Recommendation
Make `withdrawMultipleDelegationRewards` best-effort per validator: catch and skip (recording zero/failure) per-validator withdrawal errors instead of aborting the whole loop, or explicitly document/enforce that batched withdrawal is all-or-nothing and validate up front (as already done for `SetWithdrawAddr`) that the withdraw address is not blocked, so silent partial failures during EndBlock/withdraw flows don't unexpectedly deny an entire batch.

### Proof of Concept
1. A delegator has staked with several validators and accrued rewards from each.
2. The delegator's withdraw address (via `setWithdrawAddress`) is not caught by the `SetWithdrawAddr` guard for some non-coinbase blocking condition reachable through the bank module's `BlockedAddr`/`IsInDenomAllowList` checks (e.g., an allow-listed tokenfactory denom included among rewards from one validator).
3. The delegator calls `withdrawMultipleDelegationRewards([validatorA, validatorB, validatorC])` on the distribution precompile.
4. The loop in `withdrawMultipleDelegationRewards` reaches the validator whose reward composition trips the block, `p.withdraw` returns an error, and the function returns immediately with `rerr`, per [7](#0-6) .
5. The entire EVM transaction reverts; rewards from validatorA and validatorB (which would have succeeded individually) are also not paid out, even though calling `withdrawDelegationRewards` (singular) for those validators would have succeeded.

// SendCoinsFromModuleToAccount transfers coins from a ModuleAccount to an AccAddress.
// It will panic if the module account does not exist. An error is returned if
// the recipient address is black-listed or if sending the tokens fails.
func (k BaseKeeper) SendCoinsFromModuleToAccount(
	ctx sdk.Context, senderModule string, recipientAddr sdk.AccAddress, amt sdk.Coins,
) error {

	senderAddr := k.ak.GetModuleAddress(senderModule)
	if senderAddr == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", senderModule))
	}

	if k.BlockedAddr(recipientAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", recipientAddr)
	}
	return k.SendCoins(ctx, senderAddr, recipientAddr, amt)
}

// BlockedAddr checks if a given address is restricted from

func (k BaseSendKeeper) BlockedAddr(addr sdk.AccAddress) bool {
	if len(addr) == len(CoinbaseAddressPrefix)+8 {
		if bytes.Equal(CoinbaseAddressPrefix, addr[:len(CoinbaseAddressPrefix)]) {
			return true
		}
	}
	return k.blockedAddrs[addr.String()]
}

// TestSetWithdrawAddrRejectsCoinbaseAddress verifies that a withdraw address
// carrying the reserved "evm_coinbase" prefix is rejected at set time. Such an
// address passes CanSendTo (it is not EVM-associated) but is blocked by
// BlockedAddr, so SendCoinsFromModuleToAccount would fail on it. Rejecting it up
// front prevents a delegator from parking an unpayable withdraw address that would
// later panic the force-withdraw in AfterValidatorRemoved during EndBlock.
func TestSetWithdrawAddrRejectsCoinbaseAddress(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	params := app.DistrKeeper.GetParams(ctx)
	params.WithdrawAddrEnabled = true
	app.DistrKeeper.SetParams(ctx, params)

	addr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))
	coinbaseAddr := coinbaseWithdrawAddr()

	// CanSendTo alone would let this address through; BlockedAddr is what catches it.
	require.True(t, app.BankKeeper.CanSendTo(ctx, coinbaseAddr))
	require.True(t, app.BankKeeper.BlockedAddr(coinbaseAddr))

	require.Error(t, app.DistrKeeper.SetWithdrawAddr(ctx, addr[0], coinbaseAddr))
}
