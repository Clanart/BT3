### Title
CW721→ERC721 pointer's `transfer_nft`/`send_nft` uses `transferFrom` instead of `safeTransferFrom`, risking permanent NFT loss - (File: `x/evm/client/wasm/query.go`, `example/cosmwasm/cw721/src/contract.rs`)

### Summary
The CosmWasm CW721 pointer contract that wraps a real EVM ERC721 token builds its NFT-transfer payload using the ERC721 `transferFrom` selector instead of `safeTransferFrom`. Any unprivileged CosmWasm user who calls `transfer_nft` or `send_nft` on this pointer to move a wrapped NFT to a smart-contract recipient can cause the NFT to be permanently stuck if the recipient contract does not implement a manual recovery path, because the `onERC721Received` callback is never invoked.

### Finding Description
The CW721 pointer contract's `transfer_nft` execute handler builds the underlying EVM transfer via `transfer_nft()`: [1](#0-0) 

This helper calls `querier.erc721_transfer_payload(...)`, which is served by `HandleERC721TransferPayload` in the EVM query handler. That function explicitly packs the ERC721 `transferFrom` selector (not `safeTransferFrom`) before delegate-calling it against the real ERC721 contract: [2](#0-1) 

Both `execute_transfer_nft` and `execute_send_nft` (the CW721 analog of `safeTransferFrom`, which per the CW721/ERC721 semantics is supposed to verify the recipient can handle NFTs before transferring) route through this same `transfer_nft()` helper: [3](#0-2) 

Because the actual on-chain EVM call uses plain `transferFrom`, no `onERC721Received` check is ever performed, regardless of whether the caller used `transfer_nft` or `send_nft`. If the resolved EVM recipient address is a smart contract that relies on the `onERC721Received` hook to record incoming NFTs (e.g., an escrow/marketplace contract), the transfer will silently succeed on-chain but the receiving contract will have no record of owning the token, and if that contract lacks a manual sweep/rescue function, the NFT becomes permanently unrecoverable.

### Impact Explanation
This qualifies as concrete, permanent fund (NFT) loss for any unprivileged CW721 pointer user who transfers a wrapped NFT to a smart-contract recipient that expects the ERC721 receiver-hook to be invoked. This matches the "permanent freezing of funds" acceptance criterion, since there is no mechanism in the ERC721 `transferFrom` path to abort the transfer or notify the recipient, and CW users have no direct way to invoke `safeTransferFrom` themselves through the pointer contract's CW721 interface.

### Likelihood Explanation
Likelihood is moderate-to-high: any Sei user (not requiring special privileges) can call `transfer_nft`/`send_nft` on a CW721 pointer for a wrapped ERC721, and simply targeting a smart-contract address (a common scenario for marketplaces, vaults, or escrow use cases) as recipient triggers the issue without any attacker cooperation needed — it's a straightforward user-facing safety gap rather than an exploit requiring adversarial setup.

### Recommendation
Update `HandleERC721TransferPayload` in `x/evm/client/wasm/query.go` to pack the `safeTransferFrom(address,address,uint256)` selector instead of `transferFrom`, and correspondingly ensure `execute_send_nft` performs the receiver-acceptance check (as CW721's `send_nft` semantics require) while `execute_transfer_nft` may keep using plain `transferFrom` to preserve compatibility with EOA-style CW721 semantics, mirroring the split between `transferFrom` and `safeTransferFrom` in the ERC721 standard.

### Proof of Concept
1. Register an ERC721↔CW721 pointer for an EVM `ERC721` contract, per `registerPointerForERC721` flow (see `contracts/test/CW721toERC721PointerTest.js`).
2. Deploy or identify a smart contract at some Sei address `SC` that does not implement `onERC721Received` fallback-based recovery, only relying on the callback for accounting (analogous to any vault/marketplace escrow).
3. As any CW user owning an NFT tracked by the pointer, execute `{"transfer_nft": {"recipient": "<SC-owner-sei-addr-mapped-to-SC-evm-addr>", "token_id": "<id>"}}` on the pointer contract.
4. The pointer contract calls `HandleERC721TransferPayload`, which packs `transferFrom(owner, SC_evm_addr, id)` and delegate-calls it on the real ERC721 contract, per [4](#0-3) .
5. The transfer succeeds at the ERC721 level (owner mapping updates to `SC`), but `SC` never receives an `onERC721Received` call, so `SC`'s internal logic has no record of the deposit — the NFT is now stuck in `SC` with no code path to move it back out.

fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}

func (h *EVMQueryHandler) HandleERC721TransferPayload(ctx sdk.Context, from string, recipient string, tokenId string) ([]byte, error) {
	abi, err := cw721.Cw721MetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	fromEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(from))
	if !found {
		return nil, types.NewAssociationMissingErr(from)
	}
	toEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	t, ok := sdk.NewIntFromString(tokenId)
	if !ok {
		return nil, errors.New("invalid token ID for ERC721, must be a big Int")
	}
	bz, err := abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}
