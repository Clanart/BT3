### Title
Delayed / Reordered Transaction Can Revert Price Resolution via Monotonic Per-Feed Timestamp Check - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Zest's oracle layer enforces a monotonic per-feed timestamp guard, `oracle-timestamp-fresh`, on every price resolution used for borrow, repay, and liquidation health checks. Because market actions can bundle a Pyth price-feed update payload (`write-feed`/`write-feeds`) atomically with the action, a transaction that is delayed in the mempool and confirmed out of order relative to a competing, more recent price update will fail this monotonicity check (or fail earlier inside Pyth's own storage layer), reverting the bundled user action even though nothing is wrong with the user's position. This mirrors the reported `updateExchangeRate` bug class: comparing an update's timestamp against a moving on-chain reference without a deadline/timestamp guard on the caller's side causes legitimate-but-delayed transactions to unexpectedly fail and block normal operations.

### Finding Description
`price-resolve` in `mainnet/contracts/market/v0-4-market.clar` gates every price used in health, borrow, and liquidation logic behind: [1](#0-0) 

```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time) u0 (- stacks-block-time ts))))
    (and (<= delta max-staleness) (>= ts prev))))
```

and this check is invoked inside `price-resolve`: [2](#0-1) 

The `(>= ts prev)` clause enforces that the *previously recorded* per-feed timestamp in the `last-update` map (`{type, ident} -> uint`) can never move backward, and any resolution attempt whose timestamp is older than what's already stored fails with `ERR-ORACLE-INVARIANT`, aborting the entire calling transaction (borrow, repay, withdraw, liquidate, etc.).

Market actions can optionally bundle a raw Pyth VAA update via `write-feed`/`write-feeds`, allowing a caller to atomically push a fresh price alongside their action: [3](#0-2) 

If this transaction is delayed in the mempool (network congestion, fee competition, relayer batching) and is confirmed after a different, more recent price update transaction has already advanced `last-update`/`pyth-storage-v4`'s stored `publish-time`, the delayed transaction's bundled VAA is now stale relative to the chain state. Pyth's own storage layer enforces the same ordering invariant and will reject it: [4](#0-3) 

causing `write-feed`'s match arm to hit `update-failed`, returning `ERR-PRICE-FEED-UPDATE-FAILED` and reverting the entire user action: [5](#0-4) 

Even if the bundled feed update is skipped and the action instead relies purely on `price-resolve`'s live read, the same monotonic guard (`(>= ts prev)`) can revert a perfectly valid, freshly-published price whenever a delayed transaction happens to race behind a newer one for the same feed, because the check compares against Zest's own cached `last-update`, not a deadline chosen by the caller.

### Impact Explanation
There is no `timestamp`/deadline parameter supplied by the caller to bound how "delayed" their own transaction may be before it should simply revert cleanly instead of interacting with the monotonic state. As a result, ordinary users attempting to repay debt, withdraw collateral, or liquidate an undercollateralized position can have their transaction unexpectedly revert purely due to mempool timing/reordering relative to a competing price-feed update for the same asset — not due to any fault of their own action. During the window until a new, later price arrives, actions gated on that feed for that block/timestamp period are blocked. This lands on **temporary freezing of funds**, matching the High-impact category for unclaimed/locked positions unable to be repaid, withdrawn, or liquidated in a timely manner. Liquidators in particular can be starved from executing a legitimate liquidation on a delayed transaction, and the borrower is left unliquidated (funds effectively frozen from the liquidator's perspective) while the same delay window persists.

### Likelihood Explanation
This requires two roughly-concurrent price update paths for the same feed/ident (a bundled `write-feed` call from one caller and any other price update/read establishing a newer `last-update` value) plus normal Stacks mempool reordering/delay — a common, non-adversarial condition rather than a rare edge case, mirroring the exact failure mode described in the reference report for `updateExchangeRate`. Likelihood is assessed as medium: it does not require any privileged action or bad third-party data, only ordinary network delay across two independent, otherwise-valid transactions touching the same oracle feed.

### Recommendation
Add an explicit caller-supplied deadline/timestamp argument to any market entrypoint that bundles a price-feed update (`write-feed`/`write-feeds` callers) or that depends on `price-resolve` for time-sensitive actions (borrow, repay, withdraw, liquidate). If `block-time`/`stacks-block-time` exceeds the caller's supplied deadline, revert early with a distinct, expected error before reaching the monotonic timestamp assertion, so that delayed transactions fail predictably and cheaply for the submitter instead of being silently invalidated by a race against `last-update`. Consider also decoupling the hard `ERR-ORACLE-INVARIANT` revert-on-any-monotonicity-violation from user-facing actions by allowing a resolution to fall back to the currently cached fresh price already exceeding `prev`, rather than reverting the whole transaction when the bundled feed happens to already be superseded.

### Proof of Concept
1. Feed `ident` X currently has `last-update` timestamp `T0` in `market.clar`'s `last-update` map, set from an earlier resolution.
2. User A submits a `repay`/`liquidate` transaction bundling a Pyth VAA for asset X with `publish-time = T1 > T0`. It sits in the mempool due to fee/congestion.
3. Before A's transaction is mined, User B submits and confirms a different action (or a manual price refresh) for the same feed, whose Pyth VAA has `publish-time = T2 > T1`. This updates `pyth-storage-v4` and Zest's `last-update` map to `T2`.
4. User A's transaction is finally mined. Inside `write-feed`, `pyth-storage-v4`'s `write-batch-entry` compares the incoming `publish-time = T1` against the already-stored `T2` and rejects it via `ERR_NEWER_PRICE_AVAILABLE`/`ERR_STALE_PRICE`, so `write-feed` returns `ERR-PRICE-FEED-UPDATE-FAILED` and the entire bundled repay/liquidate action reverts, per `mainnet/contracts/market/v0-4-market.clar` lines 128-150.
5. Even absent a bundled feed update, if A's action calls `price-resolve` directly and the live-read price at execution somehow carries a timestamp less than the already-advanced `last-update` (e.g., a lagging non-Wormhole-guaranteed feed such as DIA), `oracle-timestamp-fresh`'s `(>= ts prev)` clause at `mainnet/contracts/market/v0-4-market.clar` lines 365-371 fails, producing `ERR-ORACLE-INVARIANT` and reverting the user's otherwise valid repay/liquidate/borrow call with no path to simply "wait and retry successfully with the same price data," since the reference state (`last-update`) has already moved forward.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
