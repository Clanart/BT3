### Title
Unprivileged reward sweep in `compound()` drains the contract's entire token balance instead of only the caller's own claimed share - ([File: rewards/ManualCompound.sol])

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0)  which pushes claimed reward tokens into the `ManualCompound` contract itself. It then runs a second loop over the **globally registered** `rewards` array (`rewardTokensLength = rewards.length`, set by `addReward`), not over the `_rewards` array the caller actually supplied/claimed: [2](#0-1) 

For every registered reward token it computes `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` — the contract's **total** balance of that token — and forwards/converts/locks the *entire* amount to `msg.sender`, using `msg.sender`'s own `_minRec`/`_convertRatio`. There is no bookkeeping that ties `receivedBalance` to what was actually just claimed for this caller via `multiclaimOnBehalf`. Any address can call `compound()` with an arbitrary (even empty) `_lps`/`_rewards` array — the sweep loop still executes unconditionally over the global `rewards` list and hands whatever balance the contract happens to hold at that moment to the caller, choosing the slippage floor (`_minRec`) themselves for the `convertFor` leg in `SmartWomConvert._convertFor` [3](#0-2) .

This design assumes the contract's balance is always exactly zero before any `compound()` call and exactly equal to the caller's own claim afterward, but nothing in the code enforces that invariant — there is no per-call accounting of "amount claimed by this caller" distinct from "current contract balance."

### Impact Explanation
If any token balance is present in `ManualCompound` that is not the caller's own freshly-claimed amount (e.g., dust left from rounding in the router swap inside `_convertFor`, a partially-processed prior call, or tokens sitting in the contract for any other reason), the next caller of `compound()` — even one who claims nothing themselves by passing empty/irrelevant `_lps`/`_rewards` — can sweep and redirect that entire balance to themselves via the unscoped `IERC20(_tokenAddress).balanceOf(address(this))` read and the `convertFor(..., msg.sender, ...)` call. This is a direct theft of funds that do not belong to the caller, matching Critical - Direct theft of user funds.

### Likelihood Explanation
No privileged role is required — `compound()` has no access control beyond being a regular external function. The precondition is simply that the contract's balance for some registered reward token is non-zero at the moment of the attacker's call (e.g., dust from imprecise conversions/rounding, or any residual transfer). The attacker fully controls `_minRec` (can set to 0 to guarantee the swap won't revert) and `_convertRatio`, and can call `compound()` repeatedly at zero cost with trivial/empty `_lps`/`_rewards` arrays to opportunistically claim any balance that appears.

### Recommendation
Track the amount of each reward token actually attributable to the current caller (e.g., by measuring `balanceOf(this)` immediately before and after the specific `multiclaimOnBehalf` call within this same transaction, and only ever operate on that delta) instead of using the raw, cumulative `balanceOf(address(this))` for the global `rewards` list. Additionally, restrict the second loop to only the reward tokens actually included in the caller-supplied `_rewards`/that were verified to have been claimed for `msg.sender`, and ensure no other operation can leave a non-zero contract balance of any reward token after a `compound()` call completes.

### Proof of Concept
1. Deploy `ManualCompound` with a `SmartWomConvert`-style convertor registered for `wom`.
2. Simulate a scenario where a positive residual balance of `wom` is left in `ManualCompound` (e.g., have `_convertFor`'s router swap round down leaving dust, or directly transfer tokens to the contract to model any leftover balance).
3. From an attacker EOA with zero LP stake, call `compound([], [], 10000, 0, false)` (empty `_lps`/`_rewards`).
4. Assert: `multiclaimOnBehalf` claims 0 tokens for the attacker, yet the attacker's `wom`/`mWom` balance increases by the full residual amount, and `IERC20(wom).balanceOf(address(ManualCompound))` drops to 0 — demonstrating the sweep is not scoped to what the caller actually claimed.
