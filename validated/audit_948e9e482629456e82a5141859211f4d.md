### Title
Scanner credits P2TR outputs with attacker-embedded script-path clawback, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` classifies a Bitcoin output as belonging to Serai purely by matching `output.script_pubkey` against the map of plain tweaked-key P2TR scripts it generated. A P2TR `script_pubkey` commits only to the output key; it is indistinguishable whether the sender constructed that output key with a Tapscript merkle root (script-path spend). An unprivileged depositor can therefore send BTC to a script whose output key matches Serai's tweaked key but whose internal commitment includes a script leaf letting the sender unilaterally claw the funds back. Serai reports the deposit as received while the UTXO is spendable by the attacker.

### Finding Description
`scan_transaction` at `networks/bitcoin/src/wallet/mod.rs:199-214` iterates transaction outputs and pushes a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` hits. The registered scripts come from `p2tr_script_buf` (`networks/bitcoin/src/wallet/mod.rs:80-86`), which builds `ScriptBuf::new_p2tr_tweaked` — a bare `OP_1 <32-byte x-only key>` program. That program only fixes the **output key**; the UTXO's actual spending conditions may additionally include an arbitrary script tree committed inside that key's tweak.

Serai itself acknowledges this hazard in the doc comment for `register_offset` (`networks/bitcoin/src/wallet/mod.rs:177-179`): "Arbitrary offsets may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)." That protection guards only *Serai-generated* offsets; nothing guards *attacker-constructed* outputs arriving on-chain, where the attacker is free to choose the exact same output key `Q = P_internal + H(P_internal‖m)·G` with `P_internal` equal to Serai's tweaked key and `m` a merkle root committing to e.g. `<attacker_pubkey> OP_CHECKSIG`.

When Serai later spends the `ReceivedOutput` via `SignableTransaction`, it uses the key-path (Schnorr signature) spend. The attacker's script-path spend is an equally valid alternative — whoever confirms first wins, and the attacker can wait until Serai has credited them before exercising the clawback.

### Impact Explanation
Funds are reported as received that Serai does not exclusively control. In the deposit flow, an attacker attaches an `InInstruction` (the codebase's own test demonstrates the transfer-instruction deposit pattern), gets credited on the Serai side for the BTC amount, withdraws/transfers the credited value, and then — before Serai's scheduler sweeps the UTXO — spends the output via their script path. Serai's eventual spend of that `ReceivedOutput` then fails or conflicts, having already issued value against the deposit. This is a direct monetary-loss primitive: minted/credited assets backed by a UTXO the attacker can reclaim. Severity: High.

### Likelihood Explanation
Fully reachable by any unprivileged Bitcoin user with no collusion, leaked keys, or RPC compromise: they just craft a P2TR output whose internal key is Serai's published tweaked group key (publicly derivable from the deposit address) plus their own tapscript leaf, and deposit through the normal path. The scanner cannot distinguish it — the check is impossible at `script_pubkey` level, which is precisely why the flaw exists.

### Recommendation
The `script_pubkey`-only match cannot detect hidden script paths; mitigation must occur at spend/credit policy. Options: (a) treat deposits as pending until the scheduler's own sweep transaction confirms, and only then credit — a clawed-back output never confirms the sweep, so no value is issued; (b) when scanning, reject/flag outputs whose crediting would occur faster than the sweep can be performed; (c) document and enforce that `scan_block`/`scan_transaction` results are only "provisionally owned" until spent, aligning with the existing caveat on `register_offset`. A regression test should construct a deposit output with a script-path clawback leaf and assert the credited funds cannot be reclaimed after the crediting rule is applied.

Root cause: `self.scripts.get(&output.script_pubkey)` at `networks/bitcoin/src/wallet/mod.rs:205` treats script_pubkey equality as proof of sole key-path ownership, while P2TR permits equivalent output keys with hidden script trees — the same caveat documented for `register_offset` (`networks/bitcoin/src/wallet/mod.rs:177-179`) but not enforced for inbound outputs.
