### Title
Outputs sent to a multisig address before (or during) key activation are permanently unscanned and unspendable - (File: processor/src/multisigs/scanner.rs)

### Summary
The processor's `Scanner` only credits outputs for a key in blocks strictly greater than the key's `activation_number`, and for the very first registered key it marks `activation_number` itself as already scanned without ever scanning it. Because the multisig's Bitcoin (and other network) addresses are derivable before the key is activated — the group key is fixed as soon as the DKG completes, well before the Serai block at which the key "activates" — an unprivileged depositor can send funds to the address in blocks `< activation_number` (first key: `<= activation_number`). Those outputs are never emitted by the scanner, never credited, and since the key holder's spend path is unchanged there is no recovery path — the exact analog of prefunded funds becoming unrecoverable once an account's state transitions.

### Finding Description
`ScannerHandle::register_key` takes an `activation_number` and asserts it is strictly greater than `ram_scanned`; for the first key it sets `ram_scanned = Some(activation_number)` and calls `save_scanned_block(txn, activation_number)`, which marks that block's (empty) output set as seen without scanning it (`processor/src/multisigs/scanner.rs:286-295`). The scan loop then iterates blocks from `ram_scanned + 1` upward (`scanner.rs:492`), and per key only collects outputs when `activation_number <= block_being_scanned` (`scanner.rs:550-567`).

Consequences:
1. Any output paying a registered key's address in a block `< activation_number` is never scanned — the block range is never revisited.
2. For the first key, the activation block itself is never scanned: `ram_scanned` is initialized to `activation_number`, so scanning starts at `activation_number + 1`. A deposit confirmed in the activation block is silently skipped even though the key is active.
3. Unlike the rotation case where the second key is scanned starting *at* its activation block (`activation_number == block_being_scanned` passes the filter), there is no equivalent back-scan for earlier blocks in either case.

The address for a key is publicly derivable: for Bitcoin, `p2tr_script_buf(key)` / `scanner(key, ...)` in `processor/src/networks/bitcoin.rs:80-85` and `314-347` produce deterministic P2TR scripts (`External`, `Branch`, `Change`, `Forwarded` offsets) purely from the group key — known to anyone who observes the DKG/registration event, exactly like CREATE2-prefunded addresses. An unprivileged sender only needs to broadcast a transaction; no malformed input, validator misbehavior, or trusted-party assumption is required.

### Impact Explanation
Funds confirmed on-chain to a Serai multisig address are never reported by `ScannerEvent::Block`, so the coordinator never acknowledges them as received and no `ThresholdKeys` signature is ever produced to spend them. The Bitcoin UTXOs remain cryptographically spendable by the group key, but the Serai system has no path to learn of or use them — permanent loss of the credited balance, identical to the report's "dormant funds cannot be restored after deployment."

### Likelihood Explanation
Users commonly pre-compute and prefund deposit addresses (exchanges batching deposits, forwarding contracts, users depositing before a rotation completes). The window between a key's existence (DKG complete / address publishable) and its `activation_number` — plus, for the first key, the activation block itself — is a real, attacker-and-accident-reachable gap requiring only a normal on-chain transaction.

### Recommendation
- Scan the activation block inclusive for the first key: initialize `ram_scanned` to `activation_number - 1` instead of `activation_number`.
- Either scan pre-activation blocks for newly registered keys or document loudly that funds sent to a Serai multisig address before its activation block are irrecoverable, mirroring the report's "at a minimum, document this" recommendation.
- Optionally add a manual "re-scan range" / rescue API keyed by outpoint so provably-received pre-activation outputs can be credited.

### Proof of Concept
1. Complete the DKG for a new multisig; observe group key `K` and derive `addr = p2tr_script_buf(K)` via `networks/bitcoin/src/wallet/mod.rs:80`.
2. Before the coordinator calls `register_key(txn, activation_number, K)` — or in block `activation_number` itself for the first key — broadcast a Bitcoin transaction paying `addr`.
3. `register_key` executes: for the first key, `save_scanned_block(txn, activation_number)` records the block as scanned and `ram_scanned = activation_number` (`scanner.rs:291-295`).
4. The run loop scans only blocks `>= activation_number + 1` (first key) or only applies keys where `activation_number <= block_being_scanned` (`scanner.rs:492, 550-552`). The deposit's block is never passed to `network.get_outputs(&block, K)`.
5. `ScannerEvent::Block` never carries the output; it is never saved via `save_outputs`, never acknowledged, and no batch ever spends it — funds permanently lost despite being validly paid to the active key's address. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );

  (scanner, offsets, kinds)
}
