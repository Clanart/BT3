Confirmed: `HostParams` has no slippage-related field, and there's no `receive()` in `EvmHost.sol` to reroute leftover ETH back to the original dispatcher — the swap's excess ETH refund is captured by `address(this)` (EvmHost) since it is the direct caller of the router.

### Title
Unprotected native-fee AMM swaps in `EvmHost.dispatch()`/`fundRequest()` allow sandwich-attack value extraction from message dispatchers - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` swap a caller's native token for the protocol `feeToken` via a live Uniswap V2 pool using `swapETHForExactTokens`, with no slippage/price bound other than the raw `msg.value` the caller happened to attach. This is the direct on-chain analog of the reported `buy_P()`/`sell_P()` pattern: a proposal/transaction parameter (`amountMinOut`/required input) is derived from a manipulable AMM pool price with no independent minimum-guard, so an attacker can sandwich the pool immediately around the dispatcher's transaction to force it to consume more real value than fair price, pocketing the difference.

### Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)`: [1](#0-0) 
does:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```
The same unguarded pattern is repeated for `dispatch(DispatchGet)` and `fundRequest()` [2](#0-1) [3](#0-2) .

`swapETHForExactTokens` requests an exact output (`post.fee` feeToken units) and lets the router pull as much WETH as it needs, up to `msg.value`, at whatever the pool's *current* spot price is. There is no `amountInMax` distinct from the raw `msg.value`, and `msg.value` itself is normally computed by the caller off-chain from `HyperApp.quote()`, which the docs themselves flag as manipulable: [4](#0-3) 
> "Use the `quote()` view function from your frontend to estimate how much native token users need to send. **Do not call `quote()` in smart contract transactions.** It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks."

However, the disclaimer only covers the read-only `quote()` helper; the *actual state-changing swap* executed inside `dispatch()`/`fundRequest()` has the identical unguarded-price problem and is not just advisory — it moves real native-token value. `HostParams` carries no slippage-tolerance field at all: [5](#0-4) 
so governance cannot even configure a bound; the only implicit "protection" is that the transaction reverts if the manipulated price pushes the required input above `msg.value` (`EXCESSIVE_INPUT_AMOUNT`) — this stops total drain of `msg.value` but does not stop the attacker from making the swap consume nearly all of the caller's supplied buffer at an inflated price and capturing that spread via a back-run trade, exactly the "parameter manipulated through changes in the pool" scenario the external report describes for `buy_P()`/`sell_P()`.

Any account can execute this attack unprivileged: watch the mempool for a `dispatch{value: ...}(...)` or `fundRequest{value: ...}(...)` call, front-run with a swap that moves the WETH/feeToken pool price up, let the victim's swap execute at the inflated price (consuming more WETH than fair value for the exact `post.fee` output), then back-run to restore the pool and capture the extracted value — a classic sandwich requiring no relayer, prover, admin, or leaked key.

### Impact Explanation
This directly causes loss of funds for any dispatcher/user who pays Hyperbridge's relayer/protocol fee in native token — the core mechanism nearly every EVM `HyperApp` integrator (docs recommend it as the "user-facing" payment rail) and end user relies on for cross-chain messaging (`IntentGatewayV2`, `TokenGateway`, `HyperFungibleToken`, etc., all dispatch through `EvmHost`). Because the swap is embedded in the security-critical fee-collection path of every POST/GET dispatch and `fundRequest` call, this qualifies as "stealing or loss of funds" / "transaction manipulation" under the bounty's impact gate, and is triggerable by an ordinary unprivileged actor watching public mempool transactions — not a malicious relayer, prover, or admin.

### Likelihood Explanation
High. Any dispatcher paying with native token on a chain where the configured `uniswapV2Router` pool has realistic liquidity depth is exposed on every dispatch; sandwich bots already generically monitor mempools for exactly this kind of unprotected router call (`swapETHForExactTokens`/`swapExactETHForTokens`), so no bespoke targeting of Hyperbridge is required beyond recognizing the call signature and pool address, both public.

### Recommendation
1. Add an explicit, caller-supplied `amountInMax` (distinct from the raw `msg.value` buffer) or a governance-configured `maxSlippageBps` to `HostParams`, and pass a tightly bounded `amountInMax` into `swapETHForExactTokens` (or switch to `swapExactETHForTokens`, calculating `post.fee` as a guaranteed-minimum output rather than an exact target).
2. Refund any leftover native token from the swap back to `_msgSender()` of `dispatch()`/`fundRequest()` rather than leaving it sitting on `address(this)` with no forwarding logic.
3. Consider using a TWAP or oracle-anchored reference price (similar to the `referencePrice`/`maxDeviationBps` guard already implemented for the off-chain Simplex filler) to bound the acceptable swap price before executing on-chain, rejecting the dispatch if the live pool deviates too far from the reference.

### Proof of Concept
1. Attacker monitors mempool for a `dispatch{value: v}(DispatchPost{fee: F, ...})` call on `EvmHost`.
2. Attacker front-runs with a large `swapExactETHForTokens`/`swapExactTokensForETH` on the same Uniswap V2 pool (`WETH/feeToken`) to spike the WETH price of `feeToken`.
3. Victim's `dispatch()` executes `swapETHForExactTokens(F, [WETH, feeToken], address(this), block.timestamp)`; because the pool price is now inflated, the router consumes a much larger portion of `msg.value` in WETH to obtain the same `F` feeToken, up to `EXCESSIVE_INPUT_AMOUNT`-revert threshold.
4. Attacker back-runs, reversing the price move and capturing the excess WETH value extracted from the victim as arbitrage profit.
5. Victim's transaction still succeeds (assuming they had buffered enough `msg.value`), but pays materially more real value for the same fixed `post.fee` output than a fair-price swap would have required — the exact "slippage/sandwich" bug class described in the report, reproduced against `EvmHost.dispatch`/`fundRequest` rather than `LiquidityFundsManage.buy_P/sell_P`.
