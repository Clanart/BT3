### Title
Self-funded payout with forged OP_RETURN operator pubkey triggers automatic reimbursement for an operator that never funded the withdrawal - (File: core/src/task/payout_checker.rs, core/src/verifier.rs, bridge-circuit-host/src/structs.rs)

### Summary
Because the withdrawal input's Schnorr signature uses `SinglePlusAnyoneCanPay`, an attacker (the withdrawing user, who legitimately controls that signature and UTXO) can construct and broadcast their own payout transaction that pays themselves with their own extra funding input, while writing an arbitrary victim operator's x-only pubkey into the OP_RETURN output. Verifier nodes automatically parse this OP_RETURN and credit that operator as the payer, and `PayoutCheckerTask` automatically drives that operator's kickoff/reimbursement flow with no check that the operator actually signed or funded the transaction.

### Finding Description
The broken binding: `payout OP_RETURN.operator_xonly_pk == the party that funded output 0` should hold, but nothing enforces it. `create_payout_txhandler` signs only input 0 with `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP-341 commits to input 0's outpoint/value/script and only the matching-index output (output 0); it does **not** commit to any other input, nor to the OP_RETURN output containing the operator pubkey [3](#0-2) . This is by design so operators can add funding inputs via `fund_raw_transaction` [7](#0-6) , but it also means an attacker who owns the withdrawal UTXO's signature can add funding inputs from their own wallet and set the OP_RETURN operator pubkey to any operator's key.

`bridge_circuit` (and `get_payout_input_index`) only checks that one input of the payout tx references the proven withdrawal outpoint (`user_wd_outpoint`, `vout`) [6](#0-5) ; it never validates that the remaining inputs (which actually pay for output 0) belong to the operator whose pubkey is read from the same transaction's OP_RETURN [8](#0-7) . `get_payout_input_index` itself just finds the first matching `previous_output.txid` with no further constraints [5](#0-4) .

More importantly, this reaches production impact through the verifier's chain-scanning logic: `update_finalized_payouts` blindly extracts the OP_RETURN pubkey from any confirmed payout tx spending a registered withdrawal UTXO and stores it as `payout_payer_operator_xonly_pk` [9](#0-8) . `PayoutCheckerTask::run_once` then automatically looks up "first unhandled payout" for that named operator and calls `handle_finalized_payout`, kicking off the reimbursement flow with zero verification that the operator actually broadcast or funded that transaction [2](#0-1) .

Exploit flow: the attacker (a legitimate withdrawing user) crafts and broadcasts payout tx with input[0] = their withdrawal UTXO (SIGHASH_SINGLE|ANYONECANPAY signature), input[1] = their own funding UTXO, output[0] = their own withdrawal payout (self-funded, satisfying the signed constraint), output[2] = OP_RETURN naming a victim operator's x-only pubkey. This transaction confirms on Bitcoin. Verifier's chain sync marks the victim operator as `payout_payer_operator_xonly_pk` for this withdrawal, and `PayoutCheckerTask` on the victim operator's own node (or driven by the state machine once the operator node picks it up) proceeds to build the kickoff and initiate reimbursement — even though the victim operator never signed, funded or was aware of this transaction.

### Impact Explanation
If the automated kickoff and N-of-N presigned transaction graph proceed without requiring proof that the operator itself broadcast/funded the payout, this results in "an operator reimbursed for a payout it never funded" — the victim operator's collateral round/kickoff sequence gets consumed and BTC is potentially released from the move-to-vault UTXO to reimburse a payout the operator never made, while the withdrawal was already fully self-funded by the attacker. This matches the Critical severity category. The attack is repeatable for any withdrawal and any target operator whose pubkey is public (all operator pubkeys are public), and does not require compromising any key — only crafting a self-funded transaction with the withdrawal signature the attacking user legitimately possesses.

### Likelihood Explanation
Preconditions: the attacker must be the actual withdrawing user (which they legitimately are, per the threat model) and must own the withdrawal UTXO's `SinglePlusAnyoneCanPay` signature, which they inherently do since they signed it. They pay their own withdrawal amount plus normal Bitcoin fees — no privileged access, no operator/verifier keys needed. Whether the reimbursement fully completes depends on whether `handle_finalized_payout` -> kickoff -> N-of-N presigned round/kickoff transaction graph for the named operator requires additional operator-specific secret material that the attacker cannot forge (this appears likely, since kickoff txs are part of a presigned graph tied to the operator's own round chain) — this could gate full fund loss to only affect the operator's off-chain bookkeeping/database state (falsely recording payout attribution) rather than actually spending funds, but the `update_payout_txs_and_payer_operator_xonly_pk` DB write and automated `PayoutCheckerTask` triggering are unconditionally reachable by an unprivileged attacker's crafted transaction alone.

### Recommendation
Bind the OP_RETURN operator pubkey to the actual signer/funder of the payout transaction. Options: require the operator to sign an additional witness/commitment over the OP_RETURN output (e.g., include an operator signature over the txid or use `SIGHASH_ALL` for a dedicated "attribution" input actually spent from the operator's own known collateral/wallet), or require `bridge_circuit`/`verify_storage_proofs` to check that at least one other input of the payout tx is a UTXO provably controlled by the credited operator (e.g., linked to their round/collateral chain) before crediting `payout_payer_operator_xonly_pk`.
