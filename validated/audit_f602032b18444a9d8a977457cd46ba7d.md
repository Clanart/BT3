### Title
Superlinear (O(instruction_accounts × account_infos)) account matching in `translate_accounts_common` is not priced by CPI compute charges - ([File: program-runtime/src/cpi.rs])

### Summary
`translate_accounts_common` performs, for every non-duplicate account in the callee's instruction (up to `MAX_ACCOUNTS_PER_INSTRUCTION`), a linear scan `account_info_keys.iter().position(|key| *key == account_key)` over the caller-supplied `account_info_keys` (up to `account_infos_len`, capped at `MAX_CPI_ACCOUNT_INFOS`). This makes the account-matching phase of CPI translation `O(instruction_accounts * account_infos_len)` in the worst case, while the charged compute cost (`invoke_units` + `cpi_bytes_per_unit`-derived byte charges) is only linear in the number/size of accounts, not in the product of the two counts.

### Finding Description
In `translate_accounts_common` (program-runtime/src/cpi.rs), the outer loop iterates over `next_instruction_accounts` (the callee instruction's account list, which can be as large as `MAX_ACCOUNTS_PER_INSTRUCTION`), and for each account not already flagged as a duplicate via `is_instruction_account_duplicate`, it looks up the matching caller-supplied `AccountInfo`/`SolAccountInfo` by doing: [1](#0-0) 
This `position()` call is `O(account_infos_len)`. Because it executes once per (non-duplicate) instruction account, the total cost of this phase is `O(next_instruction_accounts.len() * account_infos_len)`.

The compute charges applied around this code are only:
- A fixed `invoke_units` charge at CPI entry: [2](#0-1) 
- A charge linear in `account_infos_len * ACCOUNT_INFO_BYTE_SIZE` for the initial account-info translation pass in `translate_account_infos`: [3](#0-2) 
- A charge linear in bytes of account data (`cpi_bytes_per_unit`) for the data actually translated per matched account: [4](#0-3) 

None of these charges scale with the product `next_instruction_accounts.len() * account_infos_len`; they are each linear in one dimension only. `MAX_ACCOUNTS_PER_INSTRUCTION` bounds the callee instruction's account count, and `MAX_CPI_ACCOUNT_INFOS` (currently `255` in `program-runtime/src/cpi.rs`) bounds `account_infos_len`: [5](#0-4) . An attacker who constructs a CPI instruction that references the maximum permitted number of distinct instruction accounts, combined with the maximum permitted `account_infos_len`, and arranges for many/most of the account-info entries to *not* match early in the `account_info_keys` slice (i.e., ordering the caller's `AccountInfo` array so that `position()` must scan far before finding a match, or supplying keys that never match and force a full scan before falling into the "unknown account" error path) forces close to the worst-case quadratic number of comparisons, without any additional compute charge beyond the linear terms above.

I was not able to fully confirm within this session whether `MAX_CPI_ACCOUNT_INFOS` or `MAX_ACCOUNTS_PER_INSTRUCTION` are altered by any "increase_cpi_account_info_limit"-style feature gate (only feature-set/svm-feature-set references were located, and their exact effect on these two constants and the account-info cap in `check_account_infos`/`MAX_CPI_ACCOUNT_INFOS` could not be inspected further before the session ended). This is a known unknown; the audit question describes the max cap "post `increase_cpi_account_info_limit`" and this repo currently hardcodes `MAX_CPI_ACCOUNT_INFOS = 255`, so the analysis and PoC below use that fixed cap. If a different/larger cap is active via a feature gate, the quadratic blow-up would scale accordingly and the underpricing gap would be even larger.

### Impact Explanation
This is a compute-cost-model bug: the actual CPU work of CPI account translation grows superlinearly (`O(n*m)`) in adversarial cases, while charged CUs (`invoke_units`, `cpi_bytes_per_unit`-based costs) grow linearly. This matches the Agave bounty category of "materially underpriced compute" / DoS-via-CPU-exhaustion within a single transaction's compute budget, since an attacker-controlled unprivileged program can spend disproportionately more validator CPU time per charged CU than intended, at the bounded worst case of `MAX_ACCOUNTS_PER_INSTRUCTION * MAX_CPI_ACCOUNT_INFOS` position-scan comparisons. The impact is scoped strictly to CPI dispatch CPU cost within `cpi_common`/`translate_accounts_rust`/`translate_accounts_c`, as specified in the question.

### Likelihood Explanation
Preconditions are fully attacker-controllable: instruction account list size, `account_infos_len`, `AccountInfo`/`SolAccountInfo` key ordering, and duplication/aliasing patterns are all provided directly by an unprivileged program's CPI call arguments. No validator/leader/staked control is needed. The construct is deterministic and repeatable on every invocation, bounded only by the constants `MAX_ACCOUNTS_PER_INSTRUCTION` and `MAX_CPI_ACCOUNT_INFOS`, both of which are compile-time/feature-gated constants reachable by any transaction.

### Recommendation
Replace the linear `account_info_keys.iter().position(...)` lookup with an O(1) or O(log n) lookup structure (e.g., pre-build a `HashMap<&Pubkey, usize>` from `account_info_keys` once before the outer loop in `translate_accounts_common`), so the total account-matching cost becomes `O(next_instruction_accounts.len() + account_infos_len)` instead of `O(next_instruction_accounts.len() * account_infos_len)`. Alternatively, explicitly charge compute units proportional to `next_instruction_accounts.len() * account_infos_len` (or the actual number of comparisons performed) if a linear-lookup approach must be retained, ensuring `COST_UPPER_BOUND` covers the real CPU work.

### Proof of Concept
Rust benchmark/integration test plan (to be run within `program-runtime` or an SBF CPI test harness such as `programs/sbf/rust/invoke`):

1. Construct a CPI call where:
   - The callee instruction references `MAX_ACCOUNTS_PER_INSTRUCTION` distinct, non-duplicate accounts (via `next_instruction_accounts`).
   - `account_infos_len` is set to `MAX_CPI_ACCOUNT_INFOS` (255).
   - The `AccountInfo`/`SolAccountInfo` array is ordered so that for each instruction account, its matching entry in `account_info_keys` is placed as late as possible (e.g., reverse order relative to lookup order), maximizing `position()` scan length.
2. Benchmark wall-clock/CPU time of `cpi_common::<SyscallInvokeSigned>` (or directly `translate_accounts_rust`/`translate_accounts_c`) as a function of `account_infos_len` for fixed `next_instruction_accounts.len() = MAX_ACCOUNTS_PER_INSTRUCTION`, sweeping from small counts up to 255.
3. Compute the charged CU cost via `invoke_units + (account_infos_bytes / cpi_bytes_per_unit) + Σ(matched account data bytes / cpi_bytes_per_unit)` per the code paths cited above.
4. Fit measured CPU time against the charged-CU-implied linear model; assert failure of the invariant `measured_cpu_time <= COST_UPPER_BOUND(charged_units)` (i.e., show that CPU time grows quadratically with `MAX_ACCOUNTS_PER_INSTRUCTION * account_infos_len` while charged CUs grow linearly in `account_infos_len`).
5. Fuzz variant: randomize account key ordering/duplication patterns feeding into `is_instruction_account_duplicate` and `position()` to confirm the worst case is reachable and repeatable, and that no existing check (`check_account_infos`, `check_instruction_size`) bounds the product term.
