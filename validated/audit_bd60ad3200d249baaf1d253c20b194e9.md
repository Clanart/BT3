### Title
Improper Input Validation of DataLayer Mirror Coin URLs Causes Unhandled Decode Exception During Wallet Sync - (File: chia/data_layer/data_layer_wallet.py)

### Summary
`DataLayerWallet.coin_added()` decodes attacker-controlled mirror-coin memo bytes as UTF-8 without validating that they are valid text, mirroring the Gitea flaw of using `form.MirrorAddress` without validating it before use. Any unprivileged user can create a coin with the DataLayer mirror puzzle hash and a memo containing invalid UTF-8 bytes; when a wallet that tracks the referenced launcher id processes this coin during normal sync, an unhandled `UnicodeDecodeError` is raised.

### Finding Description
When a coin is created that spends to `create_mirror_puzzle().get_tree_hash()`, any wallet syncing chain state calls `coin_added()`, which extracts `launcher_id` and raw `urls` (bytes) from the parent coin's puzzle/solution via `get_mirror_info()` [1](#0-0) . If the referenced `launcher_id` is tracked by the wallet, the code immediately calls `Mirror.decode_urls(urls)` to build a `Mirror` record for storage [2](#0-1) .

`Mirror.decode_urls()` is defined as a straight `bytes.decode("utf8")` with no validation or exception handling: [3](#0-2) 

The bytes passed in originate entirely from an attacker-supplied CLVM memo list produced by `get_mirror_info()`, which just reads `condition.at("rrrf").as_python()` off the spending coin's own solution — there is no format or content check before it reaches `decode_urls()`: [4](#0-3) 

Unlike the RPC-level `add_mirror` path, which only validates that a non-empty local URL list is provided before calling `dl_new_mirror` [5](#0-4) , the on-chain mirror puzzle itself performs no validation of the memo contents at all. Any coin spend that produces a `CREATE_COIN` condition to the mirror puzzle hash with a memo list `[launcher_id, arbitrary_bytes...]` will be accepted by consensus and later parsed by every wallet tracking that `launcher_id`, exactly as Gitea failed to validate `form.MirrorAddress` before calling `SaveAddress`.

### Impact Explanation
A malicious actor can craft and broadcast a standard, self-funded coin spend (no cooperation from the victim needed) that creates a coin to the mirror puzzle hash with a memo whose second element is not valid UTF-8, and whose first element (`launcher_id`) matches a DataLayer store id that a target wallet is tracking (store ids are public on-chain values, easily discoverable). When that wallet's sync process reaches this coin, `coin_added()` raises an unhandled `UnicodeDecodeError` inside the wallet state manager's coin-processing path, since none of `coin_added`, `get_mirror_info`, or `decode_urls` catch decode errors. This can interrupt/halt processing of that sync batch for the affected wallet's DataLayer wallet, a spend-triggered transaction-processing disruption reachable by any unprivileged spend-bundle submitter targeting a known DataLayer store owner/subscriber.

### Likelihood Explanation
Likelihood is high for any wallet that owns or subscribes to a DataLayer store: the attacker only needs the public `launcher_id` (store id) and the ability to submit an ordinary coin spend to the mirror puzzle hash with a crafted memo, both of which are available to any unprivileged user without special permissions or timing.

### Recommendation
Validate/guard mirror URL memo bytes before decoding: wrap `Mirror.decode_urls()` calls in `coin_added()` with exception handling (e.g., catch `UnicodeDecodeError`/`ValueError` and skip/log the malformed mirror instead of propagating), and/or validate memo bytes are well-formed UTF-8 (and reasonably bounded in size) in `get_mirror_info()` before returning them, so malformed on-chain mirror coins cannot disrupt wallet sync.

### Proof of Concept
1. Attacker determines the public `launcher_id` of a DataLayer store that the victim wallet tracks (e.g., via `get_owned_stores`/`get_mirrors` RPC on their own node, or by observing the target's known store id).
2. Attacker constructs and signs a standard coin spend that creates a coin with puzzle hash `create_mirror_puzzle().get_tree_hash()` (`chia/wallet/db_wallet/db_wallet_puzzles.py:90-94`) and a solution whose conditions include a `CREATE_COIN` condition with memos `[launcher_id_bytes, b"\xff\xfe\x00invalid-utf8"]`.
3. Attacker broadcasts the spend bundle; it is accepted by mempool/consensus as an ordinary coin creation (no protocol-level validation of memo content occurs).
4. Once confirmed, the victim wallet's sync path calls `DataLayerWallet.coin_added()` for the new coin, which calls `get_mirror_info()` to extract `launcher_id`/`urls`, confirms the launcher is tracked via `dl_store.is_launcher_tracked()`, and calls `Mirror.decode_urls(urls)`.
5. `bytes.decode("utf8")` raises `UnicodeDecodeError` on the malformed memo bytes, propagating out of `coin_added()` uncaught.

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```
