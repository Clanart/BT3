### Title
Cross-transaction data/origin overwrite in `Bitcoin::get_outputs` misattributes concurrent deposits in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs:686-740` accumulates scanned outputs in a single `outputs` vector across *all* transactions in a block, but the block that populates `presumed_origin` and `data` runs once per transaction and mutates **every output accumulated so far** using the *current* transaction's `tx.input[0]` and `extract_serai_data(tx)`. Any transaction later in the block — even one with no Serai output at all — overwrites the deposit instruction data and origin of earlier deposits. [1](#0-0) 

### Finding Description
The loop structure is:

```rust
let mut outputs = vec![];                    // declared ONCE, outside the tx loop
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ...
    outputs.push(output);                    // accumulated across txs
  }
  if outputs.is_empty() { continue; }        // only skips while nothing seen yet
  let presumed_origin = { ... tx.input[0] ... };   // per-tx origin
  let data = Self::extract_serai_data(tx);          // per-tx InInstruction data
  for output in &mut outputs {               // iterates ALL accumulated outputs
    if output.kind == OutputType::External {
      output.data.clone_from(&data);
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

After the first matching output is pushed, `outputs.is_empty()` is never true again for the rest of the block. Every subsequent transaction in `block.txdata` therefore:

1. Performs an RPC fetch of `tx.input[0]`'s spent output to derive `presumed_origin`, and
2. Calls `extract_serai_data(tx)` and assigns the result to `output.data` for **all** `External` outputs collected from *earlier* transactions in the same block.

The scanner itself (`Scanner::scan_transaction`, `networks/bitcoin/src/wallet/mod.rs:199-214`) correctly distinguishes outputs by outpoint, and `output.data` for `OutputType::External` carries the user's embedded InInstruction (`data` is written into `Output` at line 697 and surfaced via `OutputTrait::data()` at `processor/src/networks/bitcoin.rs:132-134`), which the processor uses to credit/route the deposit. The ID-level dedup (`panic!("scanned an output multiple times")` in `processor/src/multisigs/scanner.rs:636-637`) only protects against duplicate outpoints — it does nothing to stop the *metadata* of distinct deposits being clobbered. [2](#0-1) [3](#0-2) 

### Impact Explanation
When two or more users deposit BTC to the Serai external address in the same block (exactly the "multiple users transfer to the same address at the same time" shape of the external report), the deposit scanned first has its `data` (the InInstruction specifying how the bridged funds should be credited) and `presumed_origin` overwritten by a later transaction's values. Consequences:

- A deposit's InInstruction is replaced by another depositor's instruction → the victim's BTC is credited under the wrong instruction (e.g., minted/attributed to a different destination).
- A deposit's data is replaced by `extract_serai_data` of an unrelated transaction (likely empty) → the deposit is reported without its instruction and cannot be correctly credited, effectively losing the user's bridged funds even though the BTC arrived and is spendable by the vault.
- An unprivileged attacker can deliberately place a transaction later in the same block (with or without a Serai output, and with attacker-chosen data in the former case) to overwrite pending deposits' data.

### Likelihood Explanation
Low-to-moderate. It requires two relevant transactions in the same block: a victim deposit followed by any later transaction (the later transaction need not even pay Serai, since the overwrite block runs whenever `outputs` is non-empty). For an attacker targeting a specific deposit, they must land their transaction in the same block after the victim's — feasible via fee/ordering incentives but not guaranteed. No privileged access, key material, or collusion is required.

### Recommendation
Populate `presumed_origin` and `data` only for the outputs scanned from the *current* transaction, and reset per-transaction state. Concretely, move `let mut outputs = vec![]` inside the `for tx` loop (or track the start index and only iterate `outputs[start..]`), so each transaction's scanned outputs are annotated exclusively with that transaction's `tx.input[0]` origin and `extract_serai_data(tx)` result, then extend a separate results vector.

### Proof of Concept
Within one block containing transactions `tx_v` (victim deposit to the Serai external key with InInstruction data `D_v`) and `tx_a` (any later transaction — attacker-controlled or benign):

1. `scan_transaction(tx_v)` pushes `Output { kind: External, data: vec![], .. }` into `outputs`.
2. The population block runs for `tx_v`, setting `output.data = extract_serai_data(tx_v) = D_v`.
3. `tx_a` is processed: `outputs.is_empty()` is false (victim output still present), so the block runs again, computing `data = extract_serai_data(tx_a)` and `presumed_origin` from `tx_a.input[0]`, then overwriting the victim output's `data` and `presumed_origin` in place.
4. `get_outputs` returns the victim's output bearing `tx_a`'s data instead of `D_v`; the scanner/scheduler at `processor/src/multisigs/scanner.rs` then emits this misattributed output, and the deposit is credited according to the wrong (or absent) instruction while the BTC remains locked in the vault.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
