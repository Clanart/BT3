### Title
Diff truncation in `build_refute_prompt` lets attacker-ordered diff content suppress self-refute review of genuinely new vulnerabilities - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` truncates the entire concatenated diff to the first 8000 characters (`diff_text[:8000]`) before handing it to the adversarial self-refute stage, while stage 1 (`build_investigate_prompt`) sees up to 400,000 bytes via `cap_diff_for_prompt`. An attacker who authors the diff content (e.g. a PR/commit reviewed by this pipeline) can pad or order the diff so the truly dangerous `+` line falls outside that 8000-character window, causing stage 2 to apply its own explicit "PRE-EXISTING" refutation rule and drop a real finding.

### Finding Description
`build_investigate_prompt` caps diff content generously per-file (80KB) and in total (400KB) via `cap_diff_for_prompt`, so stage 1 ("investigate") reliably sees the new/dangerous `+` lines and produces candidate findings. [2](#0-1) 

Those candidates are then passed to `build_refute_prompt`, which builds the adversarial second-stage prompt but truncates the diff text far more aggressively — to a flat `diff_text[:8000]` slice with no per-file capping and no anchoring to the location of the flagged candidates: [3](#0-2) 

The refute prompt then instructs the model to REFUTE any candidate as pre-existing if its cited code "does NOT appear on any + line in the DIFF block above": [4](#0-3) 

Because the DIFF block the model actually receives is only the first 8000 characters of the concatenated diff, an attacker who controls the diff content (order of files/hunks, padding with large unrelated changes, verbose comments, generated boilerplate, etc. earlier in the diff) can push the truly new, dangerous `+` line past the 8000-character cutoff. The self-refute model then correctly (per its own literal instructions) concludes the cited `vulnerableCode` is absent from the visible diff block and marks the candidate `PRE-EXISTING`/refuted — even though the change is genuinely new. This happens identically in the older single-shot path at `plugins/security-guidance/hooks/llm.py:1458` (`"\n\nDIFF:\n" + diff_text[:8000]`), confirming the same truncation defect exists in both code paths.

This differs from the schema-retry fail-open case (`ref is None` → keep all candidates), which is an already-handled failure mode. Here the model *succeeds* structurally and returns a deliberate `refuted` verdict driven by an artifact of prompt truncation, not by real evidence. The self-refute stage does have `Read`/`Grep` tool access to the repo, but the instructed refutation criterion is anchored to "the DIFF block above" (the truncated text), and reading current file content alone cannot establish whether code is newly-introduced vs. pre-existing without diff/blame context — so the tool access does not reliably compensate for the missing diff bytes.

### Impact Explanation
This breaks the stated invariant that prompt assembly must not let untrusted repo content suppress review of dangerous changes. A contributor who controls the shape of a diff (e.g., a large refactor, a padded lockfile change, or simply ordering the vulnerable file after enough other diff content) can cause the two-stage `agentic_review` pipeline (`plugins/security-guidance/hooks/llm.py:1059`, `agentic_review`) to silently drop a stage-1-identified vulnerability at the self-refute stage, so it never surfaces in guidance/blocking output. This matches the "Security-control bypass that silently disables or routes around review boundaries" impact class, since the review's own self-refute logic is tricked into discarding a true positive via a mechanical truncation artifact rather than genuine refuting evidence.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to control diff size/ordering, which is trivially achievable in any PR/commit that this reviewer processes (no special privilege needed — this is normal repository content). The 8000-character cutoff is small relative to real-world diffs (a single moderately-sized file easily exceeds it), so this can occur unintentionally as well as be deliberately engineered by an attacker padding earlier hunks.

### Recommendation
Apply the same per-file/total byte capping (`cap_diff_for_prompt`) used in `build_investigate_prompt` to the diff text passed into `build_refute_prompt`, or better, anchor the refute-stage diff text to only the diff hunks relevant to the flagged candidates (their `filePath`s) rather than a flat prefix truncation, so that a genuinely new `+` line for a flagged candidate is never dropped purely due to its position in the overall diff.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py`:
1. Construct `diff_files` with N padding files whose diffs sum to >8000 characters, followed by a final file `vulnerable.py` containing a clearly new `+` line matching an attacker-controlled sink pattern (e.g. `subprocess.run(user_input, shell=True)`).
2. Build `diff_text` by concatenating all files (mirroring how `agentic_review`/callers build `diff_text` for the refute stage).
3. Call `build_refute_prompt(candidates=[{"filePath": "vulnerable.py", "vulnerableCode": "subprocess.run(user_input, shell=True)", ...}], diff_text=diff_text)`.
4. Assert that the returned prompt's `diff_text[:8000]` slice does NOT contain the string `subprocess.run(user_input, shell=True)` (i.e., it was truncated out), demonstrating that the self-refute model would be instructed to treat the candidate as PRE-EXISTING/refute it despite the line being genuinely new — confirming the invariant "dangerous file or path remains present and correctly anchored after truncation" is violated.
