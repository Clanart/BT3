### Title
Out-of-bounds panic in `Interpolation::Constant::interpolation_factor` when a crafted preprocess carries a participant index beyond the coefficient vector - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2017-15120 is a parse-time NULL dereference reachable by unauthenticated crafted input, causing remote DoS. The Serai analog is a parse/validation gap that yields a panic (Rust's crash-equivalent): `Interpolation::Constant(c)` interpolates by indexing `c[i - 1]` with an unchecked `Participant` value. `Participant::new` only rejects zero — not indexes `> n` — so any index up to 65535 is accepted at deserialization and later used as a vector index in `interpolation_factor`, panicking the signing process.

### Finding Description
`interpolation_factor` at `crypto/dkg/src/lib.rs:226-248` computes the per-participant coefficient for a signing set:

```rust
Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
```

The constant-coefficient vector `c` is built with exactly `n` entries (see `ThresholdKeys::read` at `crypto/dkg/src/lib.rs:607-613`, which pushes `n` scalars). Meanwhile, `Participant` only enforces `i != 0` (`Participant::new` at `crypto/dkg/src/lib.rs:348`, used e.g. in `ThresholdKeys::read` at line 600). When a FROST signing session builds `included` from the set of preprocesses/participants it received — each attacker participant index arriving over the wire inside preprocess/commitment messages — a participant index `i` with `u16::from(i) > c.len()` reaches `c[i - 1]` and panics with an index-out-of-bounds.

This is the same bug class as CVE-2017-15120: a parser accepts a tag/index the downstream consumer assumes is constrained, and dereferencing it crashes the node. The bytes are fully attacker-controlled public protocol input (a preprocess/commitment message tagged with a participant index), requiring no key material, no collusion, and no special privileges.

### Impact Explanation
Any participant (or anyone who can inject a preprocess/commitment into the coordinator's signing flow, e.g. via tributary `DkgCommitments`/`SignData` messages read by `Transaction::read`) can abort a FROST signing session by panic. In a coordinator/processor built without panic isolation, this is a full node crash — an unauthenticated remote denial of service matching the CVE's A:H impact. Even caught per-task, it kills the signing attempt and can be repeated to stall signing indefinitely.

### Likelihood Explanation
High. The attacker only needs to cause a message bearing `Participant(n + k)` to be included in a signing set when the keys use `Interpolation::Constant` (the interpolation mode serialized as tag `0` by `ThresholdKeys`). No timing, no secret knowledge, and no cryptographic work is required — a single out-of-range index triggers the panic on first interpolation.

### Recommendation
Validate `i <= n` (i.e., `usize::from(u16::from(i) - 1) < c.len()`) before indexing in `interpolation_factor`, returning a `FrostError`/`io::Error` instead of panicking; and/or enforce `i <= n` when constructing the signing set/`included` list from received preprocesses in `crypto/frost/src/sign.rs`. Consider making `Participant::new` take the set bound, or adding a `Participant::new_in_range(i, n)` used by all deserialization paths (`ThresholdKeys::read`, `Commitments::read`, `EncryptedMessage::read`, tributary `Participant::new` callers).

### Proof of Concept
```rust
// Attacker registers keys with Interpolation::Constant(vec![F; n]), n = e.g. 3.
// During a FROST signing session, the attacker submits a preprocess/share
// message under Participant::new(4).unwrap() (valid: only zero is rejected).
// When sign.rs calls interpolation_factor for the included set:
match &interpolation {
  Interpolation::Constant(c) => c[usize::from(u16::from(Participant(4)) - 1)],
  //                             ^^^^^ c.len() == 3 -> index 3 -> PANIC
  ...
}
// Result: thread panic -> signing task/node abort (remote unauthenticated DoS).
```

Note: I was unable to fully confirm within available context whether `crypto/frost/src/sign.rs` rejects out-of-range participants before reaching `interpolation_factor` (e.g., via a `verification_shares.get(i)` miss that returns `FrostError` early). If such a guard exists and executes first, the panic is unreachable; the fix above (bound-checking the index directly in `interpolation_factor`) is correct and defense-in-depth regardless.   fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
```rust
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
```
