### Title
Unwrap of `None` x-coordinate on attacker-forced infinity nonce point panics the signer - (File: networks/bitcoin/src/crypto.rs)

### Summary
The BIP-340 `Hram` implementation in `crypto.rs` extracts the x-coordinate of the aggregate nonce point `R` via `key.to_encoded_point(true).x().expect("point at infinity")`. `EncodedPoint::x()` returns `None` for the point at infinity, so this is a direct analog of dereferencing a null return value: a fallible result is unwrapped without a check. A malicious FROST participant can force the aggregate nonce `R` to be the point at infinity through their `Commitments` in a preprocess message, deterministically panicking every signer in the session when `sign_share`/`verify` evaluates `Hram::hram`.

### Finding Description
In `networks/bitcoin/src/crypto.rs`, `x()` computes `key.to_encoded_point(true)` and calls `.x().expect("point at infinity")` (line 15). `x_only()` similarly `expect`s (line 22). `Hram::hram` calls `x(R)` and `x(A)` (lines 65-66), and the wrapping `Schnorr::verify` calls `needs_negation(&sig.R)` (line 146).

`R` in `Hram::hram` is the aggregated FROST nonce. In `crypto/frost/src/sign.rs`, `AlgorithmSignMachine::sign` builds `Rs = B.nonces(&nonces)` (line 383), where each `R` entry is the binding-factor-weighted sum `base + rho_l * commitments_l` aggregated across all included participants (lines 386-396, `nonce.rs`). Each participant's `Commitments` are parsed from untrusted bytes via `read_preprocess` → `Commitments::read` → `C::read_G` (lines 276-281). While each individual commitment point must decode to a valid non-infinity SEC1 point, the *weighted sum* can be the identity. A rushing malicious participant observes all other preprocesses, computes the public binding factors `rho` (deterministic function of `group_key`, `hash_msg`, and the `preprocesses` transcript challenge, lines 362-371), and chooses their commitment point as the negation of the other participants' weighted contribution, forcing `R = ProjectivePoint::identity()`. `sign_share` then calls `hram(R, group_key, msg)`, which panics inside `x()`.

The code comments acknowledge the panic ("If either `R` or `A` is the point at infinity, this will panic", line 54) but claim it has "a negligible probability... even with malicious participants present" (lines 79-80). That claim is incorrect: this is not a probabilistic event, it is deterministically reachable by any participant through public preprocess bytes.

### Impact Explanation
Any single unprivileged participant in a FROST signing session over Secp256k1 (i.e., Bitcoin multisig signing) can cause a guaranteed panic in every honest signer that processes their preprocess. Since a panic in the signing path crashes or aborts the signing task, one malicious participant can indefinitely block all Bitcoin signing operations — a denial of service on the threshold wallet, matching the Medium/availability-impact severity class of the reference CVE.

### Likelihood Explanation
Reachable entirely from public inputs: the attacker only needs to be a legitimate (or compromisable single-share) participant broadcasting a crafted preprocess message — no collusion, no key material, no broken assumptions. The attack is deterministic rather than probabilistic, and the panic path (`encoded.x()` returning `None` on infinity) is a certain unwrap of an absent value.

### Recommendation
In `crypto.rs`, handle the infinity case explicitly instead of `expect`ing: check `key.is_identity()` (or `encoded.x()` returning `None`) in `x()`/`x_only()`/`needs_negation` and propagate an error through `Hram::hram`/`Schnorr::verify` rather than panicking. Additionally, `IetfSchnorr::sign_share`/`verify` should reject an aggregate `R` that is the identity before evaluating `hram`, since an identity `R` is never a valid BIP-340 nonce commitment.

### Proof of Concept
```rust
// Attacker is participant j in a session with included = {1..=t}.
// 1. Collect all other participants' Preprocess messages (commitments C_i).
// 2. Locally reproduce the binding factors: build the rho_transcript from
//    group_key, hash_msg(msg), and hash_commitments(transcript challenge) as in
//    crypto/frost/src/sign.rs lines 362-371; rho_i = binding factor per participant.
// 3. Compute the aggregate nonce contribution of everyone else:
//      S = sum_{i != j} (base_i + rho_i * C_i)   // base_i is the non-bound commitment
// 4. Choose own commitment:  C_j = -S / rho_j    (valid non-infinity SEC1 point, passes read_G)
//    so that R = S + rho_j * C_j = ProjectivePoint::identity().
// 5. Broadcast the crafted Preprocess. When any honest signer calls
//    AlgorithmSignMachine::sign -> sign_share -> Hram::hram(R=identity, A, msg)
//    -> x(&identity) -> to_encoded_point(true).x() == None
//    -> .expect("point at infinity") panics   (networks/bitcoin/src/crypto.rs:15)
// The same panic occurs in Schnorr::verify via needs_negation(&sig.R) (crypto.rs:146).
```
