### Title
Unsigned OP_RETURN in payout transaction lets any withdrawer attribute a self-funded payout to an arbitrary operator, causing false reimbursement crediting - (File: core/src/verifier.rs)

### Summary
The payout transaction's OP_RETURN output (which names the operator to be reimbursed) is not covered by the withdrawer's `SinglePlusAnyoneCanPay` signature, so anyone who owns a registered withdrawal UTXO and its signature can self-fund the payout output while naming any operator's `xonly_pk` in the OP_RETURN. `Verifier::update_finalized_payouts` blindly trusts this unsigned field and persists it as the "paying operator," which the named operator's own `PayoutCheckerTask` later uses to drive a real on-chain reimbursement claim for a payout it never funded.

### Finding Description
The broken binding: `operator_xonly_pk` recorded in `withdrawals.payout_payer_operator_xonly_pk` (set from `parse_op_return_data` in `update_finalized_payouts`, [1](#0-0) ) is assumed to equal "the operator whose own funds paid `output[0]` of the confirmed payout tx." No signature enforces this equality.

`create_payout_txhandler` builds the payout tx with input 0 = the withdrawal UTXO (key-spend), output 0 = user payout, output 2 = OP_RETURN with the fronting operator's xonly pubkey [2](#0-1) . The withdrawer's signature is required to be `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` [3](#0-2)  and verified against sighash of input 0 in `Operator::withdraw` [4](#0-3) . `calculate_pubkey_spend_sighash` shows that for `*PlusAnyoneCanPay` types only a single prevout (`Prevouts::One`) is committed [5](#0-4) ; per BIP-341/342 semantics for `SIGHASH_SINGLE`, only `output[input_index]` (index 0 here) is committed, and `ANYONECANPAY` frees all other inputs. The anchor output (index 1) and OP_RETURN (index 2) are outside the commitment.

Exploit: an unprivileged attacker who owns a registered withdrawal UTXO and its `SinglePlusAnyoneCanPay` signature (i.e. any withdrawer using the public `withdraw`/Citrea flow) constructs their own transaction: input 0 = the withdrawal UTXO (with the existing valid signature), plus their own extra funding input(s) (allowed by `ANYONECANPAY`), output 0 = exactly the previously-signed payout output (script_pubkey/amount unchanged, so the signature verifies), and an arbitrary OP_RETURN naming victim operator `O`'s `xonly_pk`. They broadcast this directly to Bitcoin, bypassing any operator entirely.

When this transaction confirms, `update_finalized_payouts` finds the OP_RETURN, parses `O`'s pubkey, and writes it as `payout_payer_operator_xonly_pk` for that withdrawal [6](#0-5) . `O`'s `PayoutCheckerTask::run_once` subsequently reads this via `get_first_unhandled_payout_by_operator_xonly_pk(O.signer.xonly_public_key)` [7](#0-6)  and drives `handle_finalized_payout`/kickoff/reimbursement for a payout `O` never funded.

Existing guards don't close the gap: `is_kickoff_malicious` only checks that the OP_RETURN pubkey equals the kickoff's claimed operator pubkey [8](#0-7)  — it never verifies that the named operator's own funds paid `output[0]`. The bridge circuit itself (used for BitVM disprove) derives `operator_xonlypk` the same insecure way from the unsigned OP_RETURN [9](#0-8) , so the false attribution propagates into the on-chain-provable reimbursement path as well.

### Impact Explanation
If the named operator's automation processes the forged attribution, that operator can claim reimbursement (draw bridge value from the deposit's move-to-vault UTXO) for a payout it never actually fronted — this is explicitly listed as Critical ("an operator reimbursed for a payout it never funded"). Alternately, an attacker can front-run/replace an honest operator's real payout broadcast for the same withdrawal UTXO with their own self-funded, falsely-attributed transaction, permanently preventing the honest operator from ever fronting (and being reimbursed for) that withdrawal, matching the Critical category "an honest operator permanently unable to be reimbursed." The attack is repeatable per withdrawal and independent of deposit/operator identity, since it only depends on the withdrawer controlling their own registered withdrawal UTXO/signature — something every withdrawer legitimately possesses.

### Likelihood Explanation
Preconditions are met by any ordinary user who withdraws through Citrea: they inherently own a valid `SinglePlusAnyoneCanPay` signature over their own withdrawal UTXO by design of the protocol (it is meant to be handed to operators off-chain, but nothing prevents the signer from using it themselves). Attacker cost is only Bitcoin fees for the extra funding input and normal chain confirmation; no aggregator/verifier/operator privilege, TLS cert, or collateral is required. This is fully attacker-executable with standard tooling (build the tx, keep output 0 fixed, add an OP_RETURN of choice) and is repeatable across every withdrawal.

### Recommendation
Bind operator attribution to a value the payer actually commits to under signature — e.g., require the operator to co-sign the payout transaction (so the OP_RETURN/operator identity is inside a signature the operator controls), or have `update_finalized_payouts`/`is_kickoff_malicious` verify that the extra funding input(s) of the payout tx are provably controlled by (or committed by) the operator named in the OP_RETURN, rather than trusting an unauthenticated OP_RETURN byte string. At minimum, extend the sighash type used (or require `SIGHASH_ALL`/covering the OP_RETURN output) so the operator-naming output cannot be altered independently of the signed input.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub fn calculate_pubkey_spend_sighash(
        &self,
        txin_index: usize,
        sighash_type: TapSighashType,
    ) -> Result<TapSighash, BridgeError> {
        let prevouts_vec: Vec<&TxOut> = self
            .txins
            .iter()
            .map(|s| s.get_spendable().get_prevout())
            .collect();
        let mut sighash_cache: SighashCache<&bitcoin::Transaction> =
            SighashCache::new(&self.cached_tx);
        let prevouts = match sighash_type {
            TapSighashType::SinglePlusAnyoneCanPay
            | TapSighashType::AllPlusAnyoneCanPay
            | TapSighashType::NonePlusAnyoneCanPay => {
                bitcoin::sighash::Prevouts::One(txin_index, prevouts_vec[txin_index])
            }
            _ => bitcoin::sighash::Prevouts::All(&prevouts_vec),
        };

        let sig_hash = sighash_cache
            .taproot_key_spend_signature_hash(txin_index, &prevouts, sighash_type)
            .wrap_err("Failed to calculate taproot sighash for key spend")?;
