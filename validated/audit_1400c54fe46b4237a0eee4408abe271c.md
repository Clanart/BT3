### Title
Stop-hook/UserPromptSubmit race permanently desyncs git review baseline from touched_paths, causing security review hook bypass - (File: plugins/security-guidance/hooks/security_reminder_hook.py, plugins/security-guidance/hooks/diffstate.py)

### Summary
The `security-guidance` plugin tracks two pieces of shared, session-scoped state that must stay in sync for its LLM-based vulnerability review to work: `touched_paths` (files edited this turn) and `baseline_sha` (the git ref the next review will diff against). `consume_stop_state` reads and clears these under one lock, and `restore_unreviewed_stop_state` puts them back if the Stop hook aborts for a transient reason. Because the Stop hook is `asyncRewake` (runs in the background after the turn ends), the next turn's `UserPromptSubmit` handler can interleave between these two locked operations, exactly as the Perennial `BalancedVault`'s global/user settlement flywheels get out of sync across epoch boundaries when an intermediate deposit shifts the pending epoch. The result is the same class of bug: two logically-linked state variables (`baseline_sha` and `touched_paths`) end up representing different points in time, causing edits to be silently excluded from all future security reviews.

### Finding Description
`consume_stop_state` (`plugins/security-guidance/hooks/diffstate.py:74-113`) atomically snapshots `touched_paths` and clears it to `[]` under a single `with_locked_state` call, deliberately *before* any slow work (git ops, network, LLM calls) happens in `handle_stop_hook` (`security_reminder_hook.py:1700-1735`).

If the Stop hook then exits early for a transient reason (API unreachable, HTTP error), it calls `restore_unreviewed_stop_state(session_id, touched_paths, snap_baseline)` (`diffstate.py:116-137`) to put the consumed `touched_paths` back so the *next* Stop fire reviews them:

```python
def _restore(state):
    existing = state.get("touched_paths", [])
    merged = list(dict.fromkeys(list(paths) + list(existing)))
    ...
    state["touched_paths"] = merged
    if baseline_sha and not state.get("baseline_sha"):
        state["baseline_sha"] = baseline_sha
```
`plugins/security-guidance/hooks/diffstate.py:129-136`

Between the `consume_stop_state` clear and this `restore_unreviewed_stop_state` call, the user (or the agent, via the harness) can submit a new prompt, firing `handle_user_prompt_submit` concurrently (this is explicitly the documented race — see the comment "UPS racing the asyncRewake Stop hook caused a meaningful share of reviews to be lost when the wipe landed before Stop's state read" in `security_reminder_hook.py:429-456`). At that intermediate moment, `state["touched_paths"]` is empty (already consumed by Stop but not yet restored), so the UPS preservation guard:

```python
if state.get("touched_paths") and state.get("baseline_sha"):
    preserved["value"] = True
    return
if sha:
    state["baseline_sha"] = sha
```
`plugins/security-guidance/hooks/security_reminder_hook.py:493-498`

sees `touched_paths` falsy and **overwrites `baseline_sha` with a fresh baseline that already includes the unreviewed edits from the aborted turn**. When `restore_unreviewed_stop_state` subsequently runs, its baseline-restore guard (`if baseline_sha and not state.get("baseline_sha")`) is now false because `state["baseline_sha"]` was just set by the racing UPS — so it only restores `touched_paths`, not the old `baseline_sha`. The state is now split: `touched_paths` correctly still lists the unreviewed files, but `baseline_sha` has been advanced past the very changes those paths represent.

`compute_v2_review_set` (`diffstate.py:353-438`) computes the review set as `dirty_now ∩ changed_since_baseline`, where `changed_since = git diff <baseline_sha>`. Because the new baseline already contains the unreviewed edits, `git diff baseline_sha` shows no difference for those files, so `changed_since` excludes them and the intersection becomes empty for those paths — **permanently** removing them from all future reviews, since the baseline can never be rolled back once advanced.

This is structurally identical to the Perennial bug class: two dependent counters (`_pendingEpochs` for the user flywheel vs. `_pendingRedemption`/`_pendingDeposit` for the global flywheel; here `touched_paths` vs. `baseline_sha`) are each updated under their own atomic operation, but a third-party action (a new deposit / a new UserPromptSubmit) interleaved between the two operations desynchronizes them, and the desync is unrecoverable rather than self-correcting.

### Impact Explanation
The `security-guidance` plugin exists specifically to catch vulnerabilities (hardcoded secrets, injection flaws, auth bypasses, etc.) introduced by Claude's edits before they land, per `plugins/security-guidance/hooks/hooks.json:1-56` and `llm.py`'s `analyze_code_security`. A successful trigger of this race causes those edits to be silently and permanently excluded from every subsequent Stop-hook, commit-review, and push-sweep review pass for the remainder of the session (the exclusion is baked into `baseline_sha`, which only ever moves forward). This is a direct security-guardrail bypass: vulnerable or malicious code introduced in the affected turn will never be flagged by this security-review mechanism, with no user-visible indication that coverage was lost (the metrics path in `handle_stop_hook` reports `"skipped"`/transient reasons, not "coverage permanently dropped").

### Likelihood Explanation
The race requires the Stop hook to hit a transient failure path (documented as a real, expected occurrence — "CCR API unreachable, Haiku HTTP error") at the same time the user or harness submits the next prompt quickly enough to land between `consume_stop_state`'s clear and `handle_stop_hook`'s later `restore_unreviewed_stop_state` call. Given the Stop hook is asyncRewake (backgrounded) specifically because it can run for a while, and users/automations frequently submit follow-up turns immediately, this window is realistically reachable, though it depends on transient network/API failures to trigger the restore path at all — making it a plausible but not trivially reproducible race in normal usage, and much more reliable if an attacker can induce transient failures (e.g., by controlling/interfering with the API endpoint or network timing) to force the restore path deliberately.

### Recommendation
Treat `touched_paths` and `baseline_sha` as one atomic unit that is only ever mutated together under a single lock acquisition, rather than as two independently-guarded fields updated across three separate `with_locked_state` calls (`consume_stop_state`, the racing UPS `_save`, and `restore_unreviewed_stop_state`). Concretely:
- Have `restore_unreviewed_stop_state` unconditionally restore `baseline_sha` to the pre-consume value whenever `touched_paths` being restored is non-empty, regardless of whether a racing UPS has already written a newer `baseline_sha` — i.e., make baseline restoration take priority over a UPS write that happened during the "consumed but not yet restored" window.
- Alternatively, add an explicit "in-flight Stop hook" marker (already partially present via `stop_hook_active`) that UPS checks before deciding whether to advance `baseline_sha`, so UPS defers its baseline write until the in-flight Stop hook either commits its new baseline or restores the old one.
- Add a regression test that simulates: Stop hook consumes state → simulated transient failure → concurrent UPS fires and advances baseline → Stop hook calls restore — assert `baseline_sha` ends up as the *pre-consume* value, not the UPS's newer one, whenever `touched_paths` is non-empty.
