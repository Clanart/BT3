## Title
Attacker-controlled remote/proxy can force an unsolicited GitHub Enterprise sign-in prompt bound to an attacker-chosen origin - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
When Desktop's embedded credential helper decides how to classify an HTTPS remote (as `github.com`, `enterprise`, or `generic`), it partially trusts the `WWW-Authenticate` header returned by the remote/proxy itself. A malicious git server (the repo/remote the user cloned or fetched) can return `WWW-Authenticate: Basic realm="GitHub"` on a 401 to any arbitrary hostname it controls, causing Desktop to classify that host as `enterprise` and automatically pop a GitHub Enterprise sign-in flow pre-bound to the attacker's origin — without the user ever choosing "Add Enterprise Account".

## Finding Description
`getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts:137-179` inspects the credential parameters Git passes to the helper, which include any `wwwauth[...]` header values captured from the remote's HTTP response: [1](#0-0) 

If the realm string matches `"GitHub"`, the endpoint is classified `'enterprise'` purely on the server's say-so, with no verification that the host is an actual GitHub Enterprise instance (no TLS pinning, no `/meta` check, no manifest, nothing beyond a header the attacker's own server emits).

That classification then flows into `getCredential()`: [2](#0-1) 

Because `endpointKind !== 'generic'` and there is no stored account whose endpoint matches this attacker host, Desktop calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` equal to the attacker-controlled URL. In `trampoline-ui-helper.ts`, this directly invokes `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using that attacker origin, and shows the `PopupType.SignIn` dialog with `credentialHelperUrl` set to the attacker's URL: [3](#0-2) 

This is triggered purely by a `git fetch`/`clone`/`push` HTTPS handshake against a remote the attacker controls (e.g. embedded as a submodule URL, a changed `origin`, or a fetch from a malicious proxy/MITM on an open network) — it does not require the user to type anything or intentionally add an enterprise account. The broken invariant is: *"enterprise" account-binding classification should only be trusted for hosts Desktop can verify are actually GitHub-compatible, not for arbitrary attacker-supplied `WWW-Authenticate` headers echoed back through Git's credential protocol.*

## Impact Explanation
This is an unauthorized-account-binding / phishing primitive that lets an attacker-controlled remote initiate GitHub Enterprise OAuth/sign-in against an attacker-chosen origin from inside Desktop's trusted UI chrome, purely by responding to a Git HTTPS auth challenge. A user who is not paying close attention to the pre-filled sign-in host (which now matches the "legitimate-looking" git remote they just cloned) may complete sign-in and hand credentials/tokens to the attacker's endpoint, or have a spurious enterprise account silently added/bound in Desktop's `AccountsStore`, which then gets offered up as a stored credential (`findGitHubTrampolineAccount`) for subsequent requests to that same origin, i.e., silent credential exposure on future interactions with that remote.

## Likelihood Explanation
Likelihood is moderate: it requires only that a victim clone/fetch/push against an attacker-controlled HTTPS git remote (or a network path where a proxy/MITM can inject the 401 response) — no local access, no prior malware, and no unnatural user steps beyond the routine "add repository from URL" or fetching a submodule. The realm-sniffing heuristic in `getEndpointKind()` is reachable on the very first credential-helper "get" call for any HTTPS remote.

## Recommendation
Do not trust the `wwwauth[...]` realm header alone to bind a URL to `'enterprise'`/GitHub classification. Require a positive verification step (e.g., calling `isGitHubHost()`'s network probe, or checking against a known-endpoints allowlist) before invoking `promptForGitHubSignIn()`, and always display the actual remote host prominently and non-editable-by-attacker in the sign-in dialog so users cannot be steered into authenticating against a spoofed enterprise endpoint from an untrusted response.

## Proof of Concept
1. Stand up an HTTPS server at `https://evil.example.com` that, on any request lacking `Authorization`, responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone/add `https://evil.example.com/foo/bar.git` (or set it as a submodule URL / remote in an otherwise legitimate-looking repo the user is asked to clone).
3. Desktop's trampoline credential helper invokes `getCredential()` → `getEndpointKind()`, which parses the `wwwauth[...]` parameter, matches `realm="GitHub"`, and returns `'enterprise'` (`trampoline-credential-helper.ts:157-166`).
4. Since no stored account matches `evil.example.com`, Desktop calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which calls `dispatcher.beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with the attacker's origin, and shows the sign-in popup (`trampoline-ui-helper.ts:80-99`) — entirely from a background git operation, without the user having chosen "Add Enterprise Account."

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
