### Title
`ThresholdKeys::read` accepts attacker-supplied inconsistent key material, letting an unprivileged party define the group key the node signs under - ([File: crypto/dkg/src/lib.rs])

### Summary
The analog to CVE-2022-0517 (trusting configuration/key material loaded from an unsecured location, letting a low-privilege party steer privileged execution) is `ThresholdKeys::<C>::read`: it deserializes `t`, `n`, `i`, the interpolation variant, `secret_share`, and all `n` verification shares entirely from the input byte stream, then calls `ThresholdKeys::new`, which derives `group_key` solely from `verification_shares[1..=t]` without ever checking that `secret_share` is consistent with `verification_shares[i]` or that the verification shares form a coherent polynomial. An attacker who feeds crafted bytes to `ThresholdKeys::read` therefore fully controls the resulting `group_key` the node will treat as its threshold public key.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), every field is read from the reader: `t`, `n`, `i` (`:591-602`), the interpolation selector including `n` arbitrary `Constant` coefficients (`:604-616`), `secret_share` (`:618`), and `n` verification shares keyed `1..=n` (`:620-623`). These are passed to `ThresholdKeys::new` (`:625-631`).

`ThresholdKeys::new` (`:349-391`) only checks that the map has exactly `n` entries with indexes `<= n`, and computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

There is no check that `C::generator() * secret_share == verification_shares[&i]`, nor that the shares lie on a degree-`t-1` polynomial. Because the reader controls all `n` points, the attacker can set `verification_shares[l] = G * a_l` for scalars `a_l` they know, making `group_key = G * a` for a fully attacker-known discrete log `a` (e.g., with `Interpolation::Constant`, coefficients `[a, 0, ..., 0]` make every interpolation factor effectively collapse so `group_key = G*a` regardless).

Downstream, `view()` (`:463-533`) and `group_key()` (`:445-447`) build on this attacker-defined key, and FROST signing with these keys produces signatures valid under the attacker's chosen `group_key`. `ThresholdKeys::read` is explicitly in the accepted untrusted-bytes surface.

### Impact Explanation
Any component that accepts serialized `ThresholdKeys` and then reports or uses `group_key()` as the key-set identity will report an attacker-owned key as the validator set's key. Funds addressed to that `group_key` (e.g., a Bitcoin output under the reported network key) are spendable only by the attacker — the analog of "unsecured config -> arbitrary code under elevated privilege": untrusted bytes become trusted key material, and the node "signs" for a key it never generated. If the secret share is additionally made inconsistent, the node can also be driven to emit invalid signature shares (availability impact on the threshold protocol).

### Likelihood Explanation
Requires delivering crafted bytes to `ThresholdKeys::read`. Where this reads locally persisted keys it needs a write to the store, but the API performs no authentication or self-consistency check, so any path feeding externally supplied serialized keys (migration, recovery, replication, or coordinator-provided key blobs) is exploitable. The cryptographic cost to the attacker is zero — they pick the scalars freely.

### Recommendation
In `ThresholdKeys::new` (and hence `ThresholdKeys::read`), verify self-consistency: check `C::generator() * secret_share == verification_shares[&params.i()]` and, for `Interpolation::Constant`, verify the verification shares are consistent with the committed coefficients; more generally, require proof the shares lie on a degree `t-1` polynomial (e.g., reject inputs where shares were not produced by a verified DKG transcript, or carry/verify a binding commitment to the DKG context). At minimum, bind the serialized form to a domain/context so bytes cannot be reinterpreted across sessions.

### Proof of Concept
```rust
// Attacker-crafted ThresholdKeys bytes for C with n >= t, i = 1:
//   id_len = C::ID.len(), id = C::ID
//   t = t, n = n, i = 1

//   secret_share = a  (or any value; consistency is never checked)

//
// group_key = sum_l G*a * interp_factor(l) = G * a  -> attacker knows dlog a.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
