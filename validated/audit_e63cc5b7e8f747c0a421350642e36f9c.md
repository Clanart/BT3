### Title
Custom YAML-like parser in `extract_frontmatter` silently truncates inline dict conditions containing commas, weakening hookify security rules - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` implements a hand-rolled YAML-lite parser that detects "inline dict" list items by checking for both `:` and `,` in the line, then blindly splits the whole item on `,` to build the condition dict. If a `pattern` value (e.g. a regex like `\.env$|credentials,secrets`) itself contains a literal comma, the split silently truncates the pattern at the first comma and drops/corrupts subsequent key/value pairs, producing a `Condition` whose `pattern` no longer matches the intended sensitive files. This happens with no error or warning, so a block/warn rule guarding sensitive files can silently stop firing.

### Finding Description
In `extract_frontmatter` (`plugins/hookify/core/config_loader.py`), for inline list items the parser does: [1](#0-0) 

This treats every comma in the line as a field separator, with no quote-awareness or escaping. A rule author writing an inline condition such as:
```
conditions:
  - field: file_path, operator: regex_match, pattern: \.env$|credentials,secrets
```
will have the `pattern` value split at the comma inside the regex, so `item_dict['pattern']` becomes `\.env$|credentials` and the trailing `secrets` becomes an unintended, malformed key (`secrets` with no `:`, silently ignored by the `if ':' in part` check) rather than part of the pattern. The resulting `Condition.pattern` (built in `Rule.from_dict` via `Condition.from_dict(c)` for each item in `frontmatter['conditions']`, see `plugins/hookify/core/config_loader.py:51-54`) is shorter/weaker than intended.

This corrupted `Condition` then flows into `RuleEngine._check_condition` / `_regex_match` in `plugins/hookify/core/rule_engine.py:256-273`, which compiles the truncated pattern and evaluates it against `file_path`/`new_text` etc. If the truncated regex fails to match sensitive files that the full pattern was meant to catch, `_rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) returns `False` for that rule and `evaluate_rules` never blocks or warns on the operation, even though the rule "looks" correct in the source file and no parsing error is ever surfaced (`load_rule_file` only catches `ValueError/KeyError/AttributeError/TypeError`, not silent semantic corruption — see `plugins/hookify/core/config_loader.py:244-274`).

The multi-line dict-item path (`elif ':' in item_text:` at line 173, and the continuation branch at line 184) does not have this problem since it only splits on the first `:`, but the inline comma-list shortcut at lines 164-171 is the vulnerable code path whenever a rule author or PR author writes the condition inline instead of multi-line.

### Impact Explanation
This weakens the intended security control of the hookify hook pipeline: a rule meant to block or warn on edits to sensitive files (`.env`, `credentials`, `secrets`, etc.) via `PreToolUse`/`PostToolUse` hooks (`plugins/hookify/hooks/pretooluse.py`, `posttooluse.py`) can be silently defanged. Since `pretooluse.py` always exits 0 and only prints a `systemMessage` (never hard-fails), there is no visible signal that the rule failed to load correctly — the sensitive-file edit simply proceeds without warning or block. If such rule files are shared/committed within a project (used for team-wide enforcement despite documentation recommending `.gitignore`), a PR that "innocuously" edits or adds a comma-containing regex pattern can silently disable enforcement for future edits to protected files, with no error surfaced to the reviewer or user. This matches an "unauthorized file action" / "trust-boundary bypass" impact category: a security-relevant guardrail is bypassed due to a parser flaw rather than a policy decision.

### Likelihood Explanation
The bug is deterministic and trivial to trigger: any inline-style condition list item whose `pattern` (or other field) value contains a comma will be truncated. This is highly likely to occur in practice because regex patterns for sensitive-file matching commonly use `|` alternation lists that are naturally rewritten with commas by rule authors, and the inline single-line list syntax is the more compact/common style shown in the plugin's own documentation examples. No special privileges are needed to introduce such a rule file — only the ability to add or edit a `.claude/hookify.*.local.md` file (e.g., via a PR to a repo that keeps hookify configs in version control despite the plugin's `SKILL.md` guidance against it).

### Recommendation
Replace the hand-rolled comma-split inline-dict parser with a proper mini-parser that only splits on commas that are top-level key separators (e.g., split on `, <identifier>:` boundaries via regex, or require quoting values that contain commas and unescape them), or simply require multi-line dict syntax for conditions and remove the inline comma-splitting shortcut. Alternatively, replace the entire custom parser with Python's built-in `yaml.safe_load` (PyYAML is already implied as the “real” parser referenced in the audit's differential-test idea) to eliminate this class of parser-differential bugs entirely. At minimum, add a validation step after parsing that logs/raises a clear error when a `pattern` field looks truncated (e.g., contains an unmatched `|` or fails to compile as the author intended), and add regression tests using PyYAML as an oracle.

### Proof of Concept
Add a unit test in `plugins/hookify/core/` (or wherever tests live) comparing `extract_frontmatter` output against `yaml.safe_load`:

```python
import yaml
from hookify.core.config_loader import extract_frontmatter

def test_inline_condition_pattern_with_comma_is_preserved():
    content = '''---
name: block-secrets
event: file
action: block
conditions:
  - field: file_path, operator: regex_match, pattern: \\.env$|credentials,secrets
---
Blocked: sensitive file edit.
'''
    fm, _ = extract_frontmatter(content)
    cond = fm['conditions'][0]

    # Oracle: what real YAML parsing intends via the raw frontmatter block
    # (author intent: pattern should be the full alternation, unmodified)
    expected_pattern = r'\.env$|credentials,secrets'

    assert cond['pattern'] == expected_pattern, (
        f"Pattern truncated by inline comma-split parser: got {cond['pattern']!r}, "
        f"expected {expected_pattern!r}"
    )
```

Expected current (buggy) behavior: `cond['pattern']` equals `\.env$|credentials` (truncated), and the assertion fails, demonstrating the silent corruption. A second integration test should feed a `tool_input` with `file_path=".env"` through `RuleEngine.evaluate_rules` using the loaded rule and assert that the block still fires — showing it currently does not for patterns crafted to exploit the truncation boundary (i.e., where the truncated prefix alone no longer matches the target file but the full pattern would).
