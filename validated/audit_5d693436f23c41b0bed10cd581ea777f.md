## Analysis

`build_refute_prompt` in `plugins/security-guidance/hooks/review_api.py` hard-truncates the diff text to the first 8000 characters when constructing the Stage 2 (self-refute) prompt, independent of the much larger per-file/total byte caps (`DIFF_PER_FILE_BYTES`=80000, `DIFF_TOTAL_BYTES`=400000) used for Stage 1 (investigate): [1](#0-0) 

The full prompt instructs the adversarial-verifier model to REFUTE a finding as "PRE-EXISTING" if the cited `vulnerableCode` does not appear on a `+` line "in the DIFF block above": [2](#0-1) 

This "DIFF block above" is the same string sliced to 8000 characters (`diff_text[:8000]`). Meanwhile, the diff-anchor tagging (`in_diff`/`off_diff`) that is embedded into the same prompt is computed from the *untruncated* `diff_text` in the caller (`llm.py`): [3](#0-2) 

and the identical truncation is duplicated inline in the legacy `llm.py` path: [4](#0-3) 

The mismatch: a candidate can be correctly tagged `in_diff` (verified against the full, untruncated diff) yet the model refuting it only sees the first 8000 characters of that same diff, so if the diff is long — e.g. several large touched files ordered (alphabetically, as `git diff`/`parse_diff_into_files` emits them) before the file containing the actual vulnerable hunk — the vulnerable `+` line falls outside the visible window. The model then has textual grounds to invoke the PRE-EXISTING refutation rule ("does NOT appear on any + line in the DIFF block above") even though the finding is genuinely new and diff-anchored. Because the Agent SDK loop for this stage only has Read/Grep/Glob (no Bash/git), it cannot independently recover provenance (new vs. pre-existing) once the diff excerpt is truncated — reading the current file on disk shows merged final state, not which lines are new. Stage 1 (investigate) is not affected because it uses the much larger 80KB/400KB caps, so the finding can be correctly raised in Stage 1 and then incorrectly dropped in Stage 2 purely due to this narrower, inconsistent 8000-char slice.

An attacker who controls the diff content submitted for agentic review (e.g. a malicious contribution/PR that Claude Code reviews, or an agent instructed to make many edits) can pad the diff with large, benign-looking, alphabetically-earlier file changes so the genuinely dangerous hunk lands past byte 8000 of the concatenated `diff_text`, causing self-refute to silently discard the correct finding as "pre-existing," effectively bypassing the security review without needing any prompt-injection wording — plain diff bulk/ordering suffices.

### Title
Stage 2 self-refute prompt truncates diff to 8000 chars independent of diff-anchor evidence, letting padded diffs cause false PRE-EXISTING refutation of real findings - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` slices the diff to `diff_text[:8000]` when building the Stage 2 adversarial-refute prompt, while the `in_diff`/`off_diff` anchor tag given to the same model is computed against the full untruncated diff. An attacker who controls diff content (ordering/size of touched files) can push the actual vulnerable hunk past the 8000-character window, causing the refute model to invoke its "PRE-EXISTING: not on any + line in the DIFF block above" rule and drop a genuinely new, correctly diff-anchored finding.

### Finding Description
`build_refute_prompt` (review_api.py:210-216) embeds only `diff_text[:8000]` in the refute prompt, whereas `tag_diff_anchor`/the equivalent inline logic in `llm.py` (`_intersects_diff`, lines 1390-1439) computes the `in_diff`/`off_diff` tag from the full diff text. Both are stitched into the same prompt sent to the Stage 2 model, which is told to refute candidates whose cited code is absent from the visible "DIFF block" (lines 232-236) — but that visible block can be a small, arbitrarily-placed prefix of the real diff. Since Stage 1 (`build_investigate_prompt`/`cap_diff_for_prompt`) uses 80KB-per-file/400KB-total caps, a legitimate high-severity finding can be correctly surfaced in Stage 1 from a hunk that is entirely absent from the Stage 2 8000-char excerpt. The Stage 2 agent has no Bash/git access to independently reconstruct which lines are new, so it must rely on the truncated text, creating a mechanical path to silently refute (drop) an otherwise-surviving finding.

### Impact Explanation
This breaks the review pipeline's core guarantee that self-refute only drops findings on genuine refuting evidence ("Default = SURVIVES unless you find concrete refuting evidence"). An attacker who can shape the size/order of files in a reviewed diff (e.g., a malicious contribution reviewed by the agentic commit reviewer, or an agent producing many edits in one turn) can reliably suppress detection of a specific vulnerability they introduce elsewhere in the same diff, resulting in the security-control (Stop-hook/commit-review blocking) being silently bypassed for that change.

### Likelihood Explanation
The precondition is only that the total diff exceeds ~8000 characters before the target hunk, which is easy to reach given per-file caps of 80,000 bytes and touched-file ordering is deterministic (alphabetical, driven by `git diff`/`parse_diff_into_files`), so an attacker can engineer file names/content to control positioning. No special privileges beyond normal repo-editing/PR-submission capability are needed, and the effect is deterministic/repeatable, not probabilistic.

### Recommendation
Make the Stage 2 refute prompt diff excerpt consistent with the anchor computation: either (a) raise/remove the 8000-char cap to match the Stage 1 caps (or at minimum ensure it covers all `_diff_anchor=="in_diff"` candidates' cited hunks), or (b) for each candidate, include only the relevant file's diff hunk near its cited `vulnerableCode`/`filePath` rather than a raw prefix slice of the concatenated diff, so truncation cannot silently exclude the evidence needed to evaluate a specific candidate.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py`:
1. Construct `diff_files` with several dummy files (alphabetically early names) each ~2000 chars of benign `+` lines totaling >8000 chars, followed by a file `zzz_target.py` whose diff contains a clearly dangerous `+` line (e.g. `+ eval(user_input)`).
2. Call `tag_diff_anchor(candidates, diff_text)` with a candidate citing that dangerous line — assert it is tagged `in_diff` (true, using full diff).
3. Call `build_refute_prompt(candidates, diff_text)` and assert that the dangerous `+ eval(user_input)` line is NOT present in the returned prompt string (i.e., `diff_text[:8000]` cut it off) — demonstrating the model-visible evidence is missing despite the correct `in_diff` anchor.
4. Assert this mismatch: `candidates[0]["_diff_anchor"] == "in_diff"` while the dangerous line's substring is absent from `build_refute_prompt(...)`, proving the invariant "truncation must not consistently drop the high-risk lines the user expects to be reviewed" is violated.
