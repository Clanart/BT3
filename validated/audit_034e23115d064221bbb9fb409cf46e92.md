## Analysis

The report's underlying invariant is: *an internal record (the "lock") that grants trust/authority over a resource is not re-validated against the actual, mutable ownership of that resource, so stale or attacker-influenced data can silently redirect the benefit of that trust to someone else.*

The closest Desktop analog is in the automatic remote-URL rewriting logic that runs whenever a repository's associated `GitHubRepository` is refreshed from the GitHub/GHES API. [1](#0-0) 

### Title
Unvalidated GitHub API `clone_url` silently rewrites a repository's Git remote, redirecting future push/fetch - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically overwrites the local `origin` remote URL with the `clone_url` field taken from a GitHub API repository object, whenever the remote appears "unchanged" from the previously cached value. It never verifies that the new URL points at the same host/endpoint the account is authenticated against, so an attacker who can influence that API response (a malicious/compromised GitHub Enterprise Server, or a MITM/proxy sitting in front of it) can make Desktop silently repoint the repository's remote to an attacker-controlled server.

### Finding Description
When Desktop refreshes the GitHub association for a repository (`repositoryWithRefreshedGitHubRepository`), it fetches the repository object from the account's API endpoint and passes it straight to `updateRemoteUrl`: [2](#0-1) 

Inside `updateRemoteUrl`, the only checks performed before calling `gitStore.setRemoteURL` are:
- `protocolsMatch` – compares only the URL *protocol* (e.g. `https:` vs `https:`), not the host.
- `remoteUrlUnchanged` – confirms the user hasn't manually edited the remote away from the previously cached `gitHubRepository.cloneURL` (i.e., it's the app's own prior "lock" value, not proof the new value is legitimate).
- `urlsMatch` – merely detects that the value differs, used to decide *whether* to trigger the rewrite, not whether the new value is safe. [3](#0-2) 

None of these guards pin the new `clone_url`'s hostname to the account's expected endpoint (`getHTMLURL(account.endpoint)`/API host). The write itself is a direct `git remote set-url`: [4](#0-3) 

For GitHub Enterprise Server accounts, `API.fromAccount(account)` talks to that self-hosted instance's API. If that instance (or any proxy terminating/forwarding its traffic) is attacker-controlled or compromised, the attacker can return a `fetchRepository` response for the matched `owner/name` whose `clone_url` field points to an entirely different, attacker-owned Git server while keeping the same `https:` protocol so `protocolsMatch` passes. Because `remoteUrlUnchanged` only checks against Desktop's own previously cached value (not a signed/trusted value), and there is no hostname allow-list, Desktop will rewrite `.git/config`'s `origin` URL to the attacker's server with no user confirmation, dialog, or diff shown — exactly mirroring the report's pattern of an internal "lock" (`gitHubRepository.cloneURL`) being trusted without re-verifying the underlying, externally-mutable resource.

### Impact Explanation
This is a "silent corruption of what the user commits or pushes" scenario, one of the explicitly valid impact classes:
- Future `git push` operations initiated from Desktop's UI will silently send the user's commits (potentially private source code) to the attacker's server instead of the real one.
- Future `git fetch`/pull operations will pull refs/objects from the attacker's server, which can then be merged into the user's branches, letting the attacker inject malicious commits that the user unknowingly builds on top of and may push back to the real remote.
- The rewrite happens as a background side effect of a routine repository refresh, with no visible diff or prompt, so the user has no natural opportunity to notice the remote changed.

### Likelihood Explanation
The precondition is that the attacker controls (or can influence via a MITM/compromised proxy) the API responses of a GitHub Enterprise Server endpoint the user has already added an account for in Desktop — this squarely matches the allowed attacker model ("a GitHub API object ... or a git remote/proxy response"). It does not require local/physical access, admin rights, prior malware, leaked credentials, or unnatural user steps: it fires automatically during normal background repository refresh (`repositoryWithRefreshedGitHubRepository`), which Desktop performs periodically and after various user actions.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new `clone_url`'s hostname matches the hostname of the account's configured endpoint (or the current remote's existing hostname), and require explicit user confirmation (a dialog showing old vs. new URL) before silently rewriting `origin`. At minimum, reject rewrites where the hostname changes.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop pointing at `https://ghe.example.com`, and has a repository cloned from `https://ghe.example.com/org/repo.git` tracked by Desktop.
2. Attacker compromises (or proxies/MITMs) `ghe.example.com`'s API so that `GET /api/v3/repos/org/repo` returns a JSON body identical to the real repo except `"clone_url": "https://attacker.example/org/repo.git"`.
3. Desktop performs a routine refresh (e.g. `_refreshRepository`), calling `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository('org','repo')` → `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
4. `protocolsMatch` is true (`https:` == `https:`), `remoteUrlUnchanged` is true (remote still matches the cached `cloneURL`), `urlsMatch` is false (URLs differ) → the condition at [5](#0-4)  is satisfied and `origin` is silently rewritten to `https://attacker.example/org/repo.git`.
5. The next push/fetch from Desktop's UI now talks to `attacker.example` instead of `ghe.example.com`.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
