### Title
JSON duplicate-field-key check compares raw JSON key strings instead of resolved field identity, allowing snake_case/camelCase alias pairs to bypass duplicate detection - ([File: python/google/protobuf/internal/json_format_test.py])

### Summary
The ZNS report's underlying invariant is: an identity (a domain name) is derived from an attacker-supplied string without canonicalizing it first, so two different string spellings that a consuming system treats as "the same identity" are allowed to independently reference/mutate that identity, and the system's own uniqueness/anti-duplicate protection never sees the collision because it compares the *raw, unnormalized* strings rather than the *resolved* identity. The corresponding surface in Protobuf's public ProtoJSON parsing API is field-name resolution: every field can be addressed in JSON by either its default `json_name` (lowerCamelCase) or, per implementation, its original proto field name. The duplicate-key check in the pure-Python `json_format` implementation is documented as comparing literal JSON key strings, not the field they resolve to, so `{"int32Value": 1, "int32_value": 2}` — two spellings that resolve to the identical `FieldDescriptor` — silently succeeds with "last write wins" instead of being rejected as a duplicate, exactly mirroring the missing-normalization class of bug in the report.

### Finding Description
`FieldDescriptor` name resolution in ProtoJSON accepts multiple textual aliases for the same field (its `json_name`/camelCase form and its original snake_case name), analogous to how `wilder` and `wIlder` both resolve to the same conceptual domain off-chain. The report's failed invariant was: "distinct on-chain string values that are supposed to be the same identity are not normalized before being used as the uniqueness key." The Protobuf analog is the pure-Python JSON parser's duplicate-field check, which is explicitly acknowledged as a bug: [1](#0-0) 

```

  # implementation, but would be a breaking change to fix. The duplicate field
  # checker intends reject inputs with duplicate key names, but it only
  # catches keys that are exact matches and not alternate spellings that
  # correspond to the same field.
  parsed_message = json_format_proto3_pb2.TestMessage()
  json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
  self.assertEqual(parsed_message.int32_value, 2)
```

and for maps as well: [2](#0-1) 

The check is intended to catch duplicate keys (`testDuplicateField` correctly rejects `{"int32Value": 1,"int32Value":2}` because the raw strings are identical), but it fails to normalize/resolve `int32_value` and `int32Value` to the same `FieldDescriptor` before comparing, so the "same identity, different spelling" case slips through — this is precisely the missing on-chain-normalization pattern from the report, translated to field-identity resolution instead of domain-hash derivation.

The C++/upb reference implementation guards against the *schema-authoring* side of this ambiguity (rejecting a `.proto` file that defines two fields whose `json_name`s collide): [3](#0-2) 

and upb's `_upb_MessageDef_InsertField` similarly rejects duplicate `json_name`s at schema build time: [4](#0-3) 

But neither of those checks addresses the input-time (attacker-controlled JSON payload) scenario handled by the pure-Python parser, which is the one shown to be broken: it is *not* a schema ambiguity (there's only one field, `int32_value`) but an unnormalized comparison of the two accepted *spellings* of the same field name at parse time.

### Impact Explanation
This is a data-integrity issue, not memory-safety: an attacker who controls a JSON payload consumed via the public `google.protobuf.json_format.Parse` API can smuggle two different values for what should be a single field, bypassing an intended duplicate/conflict-rejection safeguard. Consuming applications that rely on "duplicate key detection == the payload is well-formed and each field set exactly once" (e.g., idempotency checks, replay-protection, or "last-writer-wins across trusted merges only" assumptions) can be misled: two different senders' logical inputs (one uses `int32_value`, one uses `int32Value`) collapse silently to a single field with only the second value surviving, with no error surfaced, unlike the fully-duplicate case which does raise `ParseError`. This directly parallels the reported "duplicate identity, no on-chain rejection" risk, scoped down to field-level data integrity in JSON parsing rather than blockchain identity spoofing. It does not provide memory corruption or code execution and is bounded to a single message/field scope, so it sits at Medium/Low severity, not Critical/High — it does not meet the bar of the domain-spoofing report's "impersonation" impact, but it is the closest genuine analog to the missing-normalization invariant.

### Likelihood Explanation
High likelihood of triggering: any client of the pure-Python `json_format.Parse()` API can supply a JSON object containing both the snake_case and camelCase spelling of any field to reproduce this, no privileged access or malformed schema required, and the behavior is already confirmed and reproduced in-tree by the cited test. It is limited to the Python pure implementation's duplicate-key detector (the test comment explicitly calls this "a bug" that would be "a breaking change to fix," implying it has not been changed since being discovered).

### Recommendation
When tracking "already seen" JSON keys for duplicate-key rejection, resolve each incoming JSON key to its canonical `FieldDescriptor` (via `FieldByName`/`json_name` lookup) before deduplication, rather than comparing raw string keys — mirroring the report's recommendation to normalize before using a string as an identity key. This is a low-risk backward-compatibility change if gated behind proto3 conformance rules (already partially formalized in `docs/design/editions/edition-zero-json-handling.md`'s `ALLOW`/`DISALLOW`/`LEGACY_BEST_EFFORT` json_format feature), so it could be introduced as strict behavior under `ALLOW` mode while leaving `LEGACY_BEST_EFFORT` unchanged for compatibility. ### Proof of Concept
Using the pure-Python implementation of `google.protobuf.json_format`:
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb2

msg = pb2.TestMessage()
# "int32Value" (default json_name) and "int32_value" (original field name)
# both resolve to the SAME FieldDescriptor, but the duplicate-key checker
# treats them as different keys, so no ParseError is raised.
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # silently "last spelling wins"; contrast with:
# json_format.Parse('{"int32Value": 1,"int32Value":2}', msg2)  -> raises ParseError
```
