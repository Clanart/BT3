## Analysis

**Core broken invariant (from the seed report):** a governance-documented, config-exposed safety limit is silently different from what the code actually enforces, letting a value exceed its intended cap and enabling fund loss.

**Local analog found:** in the Simplex filler's `calculateProfitability` pricing loop, the "overfill protection" limit — documented and configured as `maxOverfillBps` (default 500 bps / 5%) — is **not actually enforced**. The code computes the ceiling, detects a breach, but explicitly skips clamping and only logs a warning. [1](#0-0) 

The documentation and shipped config template both describe this as a hard bound: "the filler clamps its computed output to at most (1 + maxOverfillBps) × user-requested amount," specifically to bound "per-leg loss when internal pricing is wrong (bug, stale cache, manipulated venue)." [2](#0-1) [3](#0-2) 

The only remaining safety net for venue-priced (Uniswap V4 pool) legs is `checkPriceGuard`/`referenceRate`, but that guard is **optional** (unconfigured chains are explicitly "unguarded") and only compares the venue price against a static `referencePrice` band — it does nothing to bound the *output amount* itself once a leg is priced. [4](#0-3) [5](#0-4) 

The halt mechanism (`recordOrderOutcome`/`maxConsecutiveClamps`) only fires when a clamp *would* have activated on a venue-priced leg, but since the clamp is disabled, an attacker can keep the ratio just under whatever "consecutive-clamp" counting threshold applies while still draining well beyond the 5% designed ceiling on each individual order, since `finalOutputAmount` is capped only by wallet balance/vault liquidity, not by the overfill ceiling: [6](#0-5) [7](#0-6) 

### Title
Overfill protection clamp is documented as an enforced fund-loss bound but is disabled, letting `policyMaxOutput` exceed the ceiling with no compensating control — (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
The `[simplex.overfillProtection]` config and its `maxOverfillBps` parameter are documented and shipped as a hard cap that bounds the filler's per-leg loss to `(1 + maxOverfillBps) × user-requested output` whenever internal pricing goes wrong (stale cache, bug, or a manipulated venue price). In the actual pricing loop, this cap is never applied to `policyMaxOutput` — the code computes `overfillCeiling`, detects a breach, and only logs a `warn`, explicitly noting "the clamp is DISABLED." The unclamped `policyMaxOutput` then flows directly into the amount sourced from wallet balance and funding-venue withdrawals and is used as the filler's actual on-chain fill amount.

### Finding Description
`computeLegPolicyOutput` returns a `policyMaxOutput` derived from `rates.rate`, which for venue-priced legs comes straight from a live Uniswap V4 pool quote (`resolveLegRates`, `getVenueUsdPrice`). This price source is untrusted by design — the surrounding code comments repeatedly acknowledge it can be "manipulated," "stale," or wrong due to a bug. The only mitigation historically was the overfill clamp: cap the output to at most 5% above what the user actually requested, so a bad price at worst causes a bounded loss. That clamp's implementation was removed/disabled while its detection, logging, config surface, and documentation were left intact, creating a mismatch between the advertised safety bound and the enforced behavior — the same class of defect as the seed report's spec-vs-code limit mismatch. The `checkPriceGuard`/`referenceRate` mechanism that could otherwise compensate is optional per-chain and only screens the *rate* against a static reference band, not the resulting *output amount*, so it does not substitute for the disabled clamp.

### Impact Explanation
An order requester who can influence or time against the venue price (e.g., by manipulating the Uniswap V4 pool the filler reads for pricing, or by exploiting a stale price cache) can cause the filler to compute an inflated `policyMaxOutput` for one or more legs. Because the clamp is disabled, that inflated amount is paid out in full (limited only by the filler's own wallet/vault liquidity, not by any percentage-based ceiling), resulting in direct loss of solver/filler funds — the "logic attack causing loss of funds" category the bounty targets, reachable by an ordinary unprivileged order placer without needing a compromised relayer, prover, or operator.

### Likelihood Explanation
Likelihood is elevated because: (1) the vulnerable path is the primary pricing path for any pair configured with Uniswap V4 pool pricing (explicitly recommended in the docs as "the recommended approach"), (2) the price guard that could catch manipulation is optional and unguarded by default on chains without a configured `referencePrice`, and (3) the halt-on-consecutive-clamp safety net is keyed off the clamp actually firing — since it never fires, the halt never triggers either, so a single or repeated exploit is not self-limiting.

### Recommendation
Re-enable the clamp: cap `policyMaxOutput` (or the final `finalOutputAmount`) to `overfillCeiling = output.amount * (10000 + maxOverfillBps) / 10000` before it is used to size wallet/vault withdrawals, restoring the clamp behavior that the configuration and documentation already describe, and ensure `recordOrderOutcome`/halt logic is driven by the actual clamp event so systemic pricing errors still trigger an operator-required halt.

### Proof of Concept
1. Configure a pair with Uniswap V4 pool-based pricing and no `referencePrice`/`maxDeviationBps` guard (an explicitly supported, unguarded configuration per the docs).
2. An order requester manipulates the referenced Uniswap V4 pool's tick (or exploits price-cache staleness) so `getVenueUsdPrice`/`resolveLegRates` returns a rate favorable to the requester, well beyond the 5% `maxOverfillBps` band relative to the order's `output.amount`.
3. Place an order sized so the filler's wallet/vault liquidity can cover the inflated `policyMaxOutput`.
4. `calculateProfitability` computes `rawPolicyMaxOutput > overfillCeiling`, logs the warning at [8](#0-7)  but does not reduce `policyMaxOutput`.
5. `finalOutputAmount` is set to the unclamped `policyMaxOutput` (bounded only by available balance) at [9](#0-8) , and the filler fills the order at this inflated amount, realizing a loss beyond the documented and configured 5% ceiling.

```text
#### Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the filler exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the filler refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
