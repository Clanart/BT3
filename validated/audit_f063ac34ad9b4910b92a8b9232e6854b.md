### Title
Consumed FROST cached preprocess is never deleted, enabling nonce reuse and secret-share recovery - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The external report describes a "claimed but not deducted" bug: a resource (rewards) is consumed yet the accounting state is never decremented, letting the same resource be paid out again. The Serai analog lives in `SigningProtocol::preprocess_internal`: the FROST nonce seed (`CachedPreprocess`) is stored in `CachedPreprocesses` keyed by context and is reloaded — but never deleted — after use. Every call to `preprocess_internal` / `share_internal` for the same context therefore regenerates the identical nonces and commitments, exactly the condition the FROST spec and the `from_cache` doc-comment say must never happen: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share." [1](#0-0) 

### Finding Description
`create_db!` declares `CachedPreprocesses: (context) -> [u8; 32]`. In `preprocess_internal`, a new seed is generated and stored only when `CachedPreprocesses::get(...)` returns `None`; afterwards the same stored seed is decrypted and fed to `AlgorithmSignMachine::from_cache`. [2](#0-1) 

`from_cache` routes through `seeded_preprocess`, which deterministically derives the FROST nonces `(d, e)` from `ChaCha20Rng::from_seed(*seed.0)`. Identical seed ⇒ identical nonces ⇒ identical published commitments. [3](#0-2) 

No code path deletes the entry. `share_internal` calls `self.preprocess_internal(participants).0` and then `machine.sign(preprocesses, msg)`. [4](#0-3)  `DkgConfirmer::share` and `DkgConfirmer::complete` both funnel through `share_internal` for the same `context = (b"DkgConfirmer", attempt)`, so a single attempt can produce multiple shares under the same nonces if the set of received preprocesses or the signed message (`set_keys_message` over an attacker-influenced `key_pair`) differs between calls. [5](#0-4) 

In FROST the share is `z = d + e·ρ_i + λ·x·c`. Two shares produced with the same `(d, e)` but different binding factors `ρ_i` (different preprocess sets — a single participant changing its commitment changes everyone's `ρ` via the `preprocesses` transcript challenge) or different challenges `c` (different `msg`) give two linear equations that solve for `d`, `e`, and then `λ·x`, recovering the signer's secret share. [6](#0-5) 

This is the exact "claimed but not removed" shape: the seed is consumed by `sign` yet remains in `CachedPreprocesses`, so it is "paid out" (used to sign) again on every subsequent call.

### Impact Explanation
**High** — reuse of a FROST nonce across two distinct signing sessions is catastrophic: an observer of the two published shares (all shares are broadcast on the tributary) recovers the validator's MuSig secret share, enabling forgery of `DkgConfirmer` signatures and related validator-signed messages. This is key-share recovery, which the in-scope crates explicitly treat as the consequence of preprocess reuse. [7](#0-6) 

### Likelihood Explanation
**Medium-High** — triggering requires `share_internal` to be invoked twice for one context with differing inputs. `DkgConfirmer::share` is called when the coordinator processes the preprocess transaction set, and `complete` re-runs `share_internal` (re-signing) before completing; any difference between the two invocations' preprocess maps or `key_pair` (both sourced from externally supplied, BFT-finalized transaction data, which an unprivileged validator can influence via its own preprocess bytes) produces the second signature under the reused nonce. The file's own header acknowledges the danger: "it is explicitly unsafe to reuse nonces across signing sessions... a logical flaw exists, letting new messages overwrite prior messages" — the missing delete is exactly such a flaw. [8](#0-7)  A partial caveat: I could not fully trace the `handle.rs` call sites within the iteration budget to confirm both `share` and `complete` can be driven with divergent inputs in one attempt; if the inputs are guaranteed identical, impact degrades to a still-unsafe reliance on an undocumented invariant.

### Recommendation
Delete the cached seed when it is consumed: after `CachedPreprocesses::get` succeeds and the machine is rebuilt, call a `CachedPreprocesses::del(txn, &context)` (or set a tombstone) so a second `preprocess_internal`/`share_internal` for the same context either generates a fresh nonce or fails loudly, mirroring the upstream mandate that the preprocess "must be deleted so it's never reused." [1](#0-0) 

### Proof of Concept
1. Instantiate `DkgConfirmer` for attempt `n`; call `share(preprocesses_A, key_pair)` — internally `preprocess_internal` loads seed `s` from `CachedPreprocesses` (stored on first call, `signing_protocol.rs:134`) and `sign` produces share `z₁` over nonces derived from `s`.
2. Call `complete(preprocesses_B, key_pair, shares)` (or a second `share`) where `preprocesses_B` differs from `preprocesses_A` in one commitment — `share_internal` reloads the same seed `s` (entry never removed), producing share `z₂` with identical `(d, e)` but different `ρ_i`/`c`.
3. Solve `z₁ − z₂ = e·(ρ_A − ρ_B) + λx·(c₁ − c₂)` together with the commitment equations to recover the validator's Ristretto secret share, demonstrating secret-key recovery from publicly broadcast shares — the direct analog of "rewards after withdraws lpFt: 900469856" (the consumed value still present).

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  Additionally, to ensure a rebuilt service isn't flagged as malicious, we have to check the
  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).
