### Title
Silent Git Remote URL Rewrite from Untrusted GitHub API `clone_url` Field Enables Attacker-Controlled Remote Injection - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically rewrites a repository's origin remote using the `clone_url` field taken verbatim from a GitHub API repository object, with no validation of the URL's transport/scheme, and no user confirmation, mirroring the Penrose bug class of "an add/update function that mutates trust-relevant state from external input while skipping the validation the rest of the system relies on."

### Finding Description
When Desktop refreshes a repository's associated GitHub metadata, `repositoryWithRefreshedGitHubRepository` fetches the repo from the API and, if a GitHub repository association already exists, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

Inside `updateRemoteUrl`, the new remote URL is taken directly from `apiRepo.clone_url` — a field of the API response — and, once a few loose heuristics pass (protocol string match, and the existing remote matching the previously cached `cloneURL`), it is written straight into the local git config via `gitStore.setRemoteURL`, with no allow-listing of the URL scheme itself: [2](#0-1) 

`setRemoteURL` on the `GitStore` and the underlying git wrapper pass this value straight to `git remote set-url` without any scheme/host restriction: [3](#0-2) [4](#0-3) 

The same pattern — writing an API-supplied `clone_url` straight into `git remote set-url`/`addRemote` without scheme validation — recurs in the fork-conversion and upstream-remote flows: [5](#0-4) [6](#0-5) 

The only guard I found anywhere in the clone/remote code paths is a destination-path sensitivity check in `clone.ts` (`isClonePathSensitive`), which protects the *local* clone target directory, not the *remote URL* value used for remote operations: [7](#0-6) 

This is directly analogous to the Penrose finding's broken invariant: a function whose job is to "register"/"update" trusted state (there: `masterContractOf`; here: the git `remote.origin.url` used for all future `fetch`/`push`/`pull` operations) accepts attacker-influenced input and commits it to authoritative state without validating it against the invariants the rest of the system depends on (here: that a remote URL is a benign `https/ssh` endpoint, not an arbitrary git transport string).

### Impact Explanation
Git remote URLs are not merely locators — they can select arbitrary git transport helpers (e.g. `ext::`, `fd::`, or helper-invoking `ssh` argument strings), some of which can execute local commands as part of `fetch`/`push`/`clone`. If a compromised or malicious GitHub Enterprise Server, or an attacker able to influence the API response the client sees (e.g. via a MITM'd GHES endpoint, since GHES admins/endpoints are outside GitHub.com's TLS-pinned trust root), returns a `clone_url` containing such a transport string, Desktop will silently rewrite the user's `origin` remote on the next background metadata refresh (`updateRemoteUrl` runs as part of normal repository refresh, not a user-initiated "update remote" action). The next time the user performs an ordinary `fetch`, `pull`, or `push` from within Desktop, the crafted URL would be used by `git`, potentially executing attacker-controlled commands, exfiltrating credentials, or silently redirecting where the user's future pushes/pulls go — matching the report's "malfunctioning/exploitable object due to missing validation, with no straightforward mechanism to detect or undo it" theme.

### Likelihood Explanation
The `updateRemoteUrl` path runs automatically during background repository refresh (`repositoryWithRefreshedGitHubRepository`) — no unusual user action is required beyond having previously used Desktop with a GitHub Enterprise endpoint whose API response can be influenced or compromised (satisfying the "attacker controls a GitHub API object" criterion, and not "leaked credentials" or "local access"). The `_convertRepositoryToFork` and `updateExistingUpstreamRemote` paths do require a user click ("Update" in `UpstreamAlreadyExists`), which somewhat reduces likelihood there but is still a normal, expected user flow presented by Desktop itself, not an "unnatural" step. I could not confirm, from the code I reviewed, that an environment-level protocol allow-list (e.g. `GIT_ALLOW_PROTOCOL`) is set for these remote-mutating git invocations — `envForRemoteOperation` was referenced in `clone.ts` but I did not get to inspect its contents, so this is an area of uncertainty that should be verified in a follow-up review.

### Recommendation
Before ever writing an API-derived `clone_url`/`ssh_url` into a repository's git remotes (in `updateRemoteUrl`, `_convertRepositoryToFork`, and `updateExistingUpstreamRemote`), validate the URL against a strict allow-list of expected schemes (`https:`, `ssh:`, `git:`) and expected host patterns (matching the endpoint the account is authenticated against), rejecting anything else (e.g. `ext::`, `fd::`, or other git remote helper syntax). Additionally, set `GIT_ALLOW_PROTOCOL` (or the modern `protocol.allow` config) for all git invocations spawned by Desktop to defense-in-depth block unexpected transports regardless of where a URL string originates.

### Proof of Concept
1. User has a repository in Desktop associated with a GitHub Enterprise Server account.
2. Attacker compromises/MITMs the GHES API endpoint (or controls a malicious GHES instance the user is signed into) and returns a repository JSON payload with `clone_url` set to a crafted value using the `ext::` git transport (e.g. an argument string that invokes a shell command upon use).
3. Desktop performs its normal periodic repository refresh, calling `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`, which passes the protocol/remote-unchanged heuristics and calls `gitStore.setRemoteURL('origin', attackerControlledUrl)` — silently, with no dialog show to the user. [8](#0-7) 
4. The user later performs a normal `fetch`/`push`/`pull` from Desktop's UI; git invokes the attacker-controlled transport helper string as part of the operation, achieving code execution / credential exfiltration under the user's account.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
