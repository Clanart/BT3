### Title
Timeout non-membership proofs are verified against a swappable `EvmHosts` address, enabling double-settlement of already-delivered requests after a host migration - (File: `modules/pallets/host-executive/src/lib.rs`, `modules/ismp/core/src/handlers/timeout.rs`, `modules/ismp/state-machines/evm/src/lib.rs`)

### Summary
This is the same bug class as the Chakra report: a handler trusts a swappable settlement/host address to answer "was this message already processed?" instead of tracking delivery status independently. In Hyperbridge, `pallet-ismp-host-executive::update_evm_hosts` lets governance repoint `EvmHosts[state_machine]` to a new `EvmHost` contract address for a chain [4](#0-3)  — analogous to `upgrade_settlement` in the report. Every `StateMachineClient::verify_non_membership`/`verify_membership`/`verify_state_proof` implementation (`EvmStateMachine`, `SubstrateEvmStateMachine`, `TendermintEvmStateMachine`, `PharosStateMachine`) resolves *which contract's storage* to check purely from the current value of this mapping at verification time [2](#0-1) , not from anything bound to the request/proof itself.

### Finding Description
`PostRequest`/`GetRequest` delivery receipts (`_requestReceipts`, `_responseReceipts`) live in the destination `EvmHost` contract's own storage [5](#0-4) . The timeout handler proves a request was *never delivered* by producing a Merkle non-membership proof of the receipts slot against the state root recorded for the chain at some height, and resolving the destination address via `EvmHosts::<T>::get(&proof.height.id.state_id)` [6](#0-5) .

If governance calls `update_evm_hosts` to repoint a state machine's entry to a freshly deployed `EvmHost` contract (e.g. as part of a migration or bug fix), the mapping value changes for *all* subsequent proof heights, including ones referencing requests that were already delivered and receipted on the **old** host contract. Because the new contract's `_requestReceipts`/`_responseReceipts` storage starts empty, and nothing in `update_evm_hosts` clears, migrates, or otherwise invalidates already-dispatched-but-unconfirmed request commitments on Hyperbridge, a non-membership proof against the new contract's (empty) receipts storage will succeed even though the request was in fact delivered through the old contract.

### Impact Explanation
An unprivileged relayer can submit a `TimeoutMessage::Post`/`Get` for a request that was already delivered (via the old host) and successfully processed by the destination module, using a non-membership proof against the new host address. `handlers/timeout.rs` will accept it, call `on_timeout` on the source module, delete the request commitment, and (per the relayer-fee flow) refund the payer [7](#0-6) . This produces double-settlement: the application state changed once via `on_accept` on the destination (delivered before migration) and again reverses/refunds on the source via `on_timeout`, causing fund loss or inconsistent bridge state — matching the required impact class of "replay/double-claim/double-settlement" and "false proof/state acceptance."

### Likelihood Explanation
Governance-driven host-address migrations are an anticipated operational event (the pallet explicitly supports `HostAddressUpdated`), and the relayer-facing timeout path is fully permissionless — any relayer holding a valid non-membership proof against the *new* contract can trigger it. The only actor with elevated privilege is the one performing the migration itself (a normal maintenance action, not an attack); the actual fund-affecting replay is executed by an ordinary, unprivileged relayer, mirroring exactly how the judges characterized the original Chakra finding ("this scenario is likely... transaction replays would be possible in the edge case described").

### Recommendation
- When calling `update_evm_hosts`, require migrating (or provably invalidating) the pending outbound request/response commitments and delivery state associated with the old host address before accepting proofs against the new one, or reject non-membership proofs at heights predating the switchover.
- Alternatively, bind non-membership timeout proofs to the specific host contract address that was authoritative at request-dispatch time (store it alongside the request commitment) rather than resolving it dynamically from the current `EvmHosts` value.
- Require the new host contract to be seeded/migrated with the outstanding receipts of the old host before it can be registered as an active `EvmHosts` entry.

### Proof of Concept
1. Request `R` is dispatched to state machine `M` and delivered to `EvmHost_old` at `M`; `EvmHost_old._requestReceipts[hash(R)] = relayer` is set, and `on_accept` executes on `M` (e.g. mints/settles funds).
2. Before Hyperbridge observes/records this delivery via a receipt-membership proof, governance calls `update_evm_hosts({M: EvmHost_new})` [4](#0-3)  (e.g. a routine host upgrade/migration).
3. An attacker/relayer waits for `R`'s `timeout_timestamp` to elapse and submits `TimeoutMessage::Post{requests: [R], timeout_proof}` where `timeout_proof` is a valid non-membership proof of `hash(R)` in `EvmHost_new`'s (empty) `_requestReceipts` storage at a recent height.
4. `modules/ismp/core/src/handlers/timeout.rs` resolves the state-machine client, which fetches `EvmHosts::<T>::get(M) == EvmHost_new` [8](#0-7) , verifies the non-membership proof successfully (since `EvmHost_new` never received `R`), and dispatches `on_timeout` to the source module and refunds the payer — even though `R` was already executed once on `M` via `EvmHost_old`.
