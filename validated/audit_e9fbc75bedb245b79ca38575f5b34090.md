I have enough evidence now to identify the concrete analog: `applyPatchToIndex` in `app/src/lib/git/apply.ts` re-fetches a **fresh** diff via `getWorkingDirectoryDiff` and then applies the file's `selection` (a set of absolute line indices computed against a previously-loaded diff) onto that fresh diff's hunks, via `formatPatch`'s `hunk.unifiedDiffStart + lineIndex` indexing. This is the closest local analog to the "stale accounting basis reused against a changed structure" bug class.

### Title
Partial-commit selection line-indices are replayed against a freshly re-fetched diff, silently staging different content than what the user selected - (File: `app/src/lib/git/apply.ts`)

### Summary
`PaymentSettler`'s bug was that positional accounting (fee balances) computed under one denomination (stablecoin decimals) was blindly reused after the denomination changed, corrupting the ledger. The Desktop analog is `applyPatchToIndex`, which takes a `WorkingDirectoryFileChange` whose `selection` is a set of **absolute line indices** computed against the diff the user was shown, but then calls `getWorkingDirectoryDiff` again to fetch a brand-new diff and reuses those same indices against it in `formatPatch`/`formatPatchToDiscardChanges`. If the working tree changes between the moment the UI diff was rendered/selected and the moment the user commits, the hunk layout (`unifiedDiffStart`/`unifiedDiffEnd`, line count, line types) can shift, so the same absolute index now points at a structurally different line.

### Finding Description
The partial-commit pipeline works as follows:
1. The Changes view loads a diff and displays it; the user selects a subset of lines to stage. Selection is stored as absolute indices (`hunk.unifiedDiffStart + lineIndex`) inside `DiffSelection`, on the `WorkingDirectoryFileChange` object [1](#0-0) .
2. When the commit happens, `stageFiles` calls `applyPatchToIndex` for every file with a partial selection [2](#0-1) .
3. `applyPatchToIndex` does **not** reuse the diff that was displayed/selected against — it independently re-invokes `getWorkingDirectoryDiff(repository, file)` to obtain a new diff object [3](#0-2) .
4. `formatPatch` is then called with that brand-new diff and the file's (now potentially stale) `selection`, indexing lines by `hunk.unifiedDiffStart + lineIndex` and checking `file.selection.isSelected(absoluteIndex)` [4](#0-3) .
5. The resulting patch is fed straight into `git apply --cached` [5](#0-4) , directly mutating the index/what gets committed.

The app-store itself acknowledges this exact class of staleness for the *rendering* path (rebuilding `selectableLines` when a newly-loaded diff differs from what was previously shown) but explicitly does **not** revalidate that previously-selected absolute indices still correspond to the same content — the comment says "we'll settle on just updating the selectable lines... isn't still selected", not that it re-maps selected indices to equivalent content [6](#0-5) . This mitigation only runs on the **UI's** diff-refresh path (`updateChangesWorkingDirectoryDiff`), not on `applyPatchToIndex`'s independent diff refetch at commit time — so the guard that exists doesn't cover the actual commit path.

### Impact Explanation
If the working tree content changes between the diff the user reviewed/selected and the moment `applyPatchToIndex` re-fetches the diff (e.g., a build tool, background formatter, git hook, LFS smudge/clean filter, or any external/automated process attacker-influenced content triggers regenerates the file, or another process appends/reorders lines), the hunk boundaries and absolute line indices can no longer line up with what the user saw. Because `formatPatch` blindly reapplies the old indices to the new hunk structure, lines the user did **not** intend to include can be silently staged and committed (or vice versa — intended lines silently dropped), all without any warning dialog. This is a silent corruption of what the user commits — the same fundamental invariant break as the reported `PaymentSettler` bug (stale positional/denominated state reused unconditionally against changed underlying structure).

### Likelihood Explanation
This does not require local/physical access beyond normal usage of Desktop: any workflow where content in the working directory can change between selecting lines and clicking "Commit" (auto-formatters, watch-mode build tools, LFS filters invoked as part of `git diff`/`git apply`, or a slow user leaving the selection open while another tool modifies the file) can trigger the mismatch. The existing safeguard in `app-store.ts` only recomputes selectable lines when the **UI** diff changes, but `applyPatchToIndex` doesn't share or validate against that same diff/state, so the protection has a gap precisely at the point where content is actually written to the index.

### Recommendation
`applyPatchToIndex` (and `stageFiles`) should not re-fetch a fresh diff independently of the diff for which the selection indices were computed. Either: (1) pass the exact diff object the selection was made against through to `applyPatchToIndex` end-to-end instead of re-querying `getWorkingDirectoryDiff`, or (2) after refetching, structurally validate that the new diff is equal to the diff used to build the selection (e.g. using `textDiffEquals`, already used elsewhere [7](#0-6) ) and abort/refresh selection state before staging if they differ, rather than silently indexing into the new structure.

### Proof of Concept
1. Modify a tracked file with distinguishable hunks (e.g. `repo-with-changes/modified-file.md` as used in existing tests) and open it in Desktop's Changes view; select specific lines for partial commit (this computes absolute indices against hunk `unifiedDiffStart` as in `app/test/unit/patch-formatter-test.ts` lines 192-201).
2. Before clicking "Commit", have an external process rewrite the file so that the hunk boundaries/line counts shift (e.g. insert a line above the first hunk, changing every subsequent `unifiedDiffStart`).
3. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (now reflecting the externally modified content) and calls `formatPatch` with the stale `selection` object.
4. Inspect the resulting commit: lines are staged based on absolute index positions from the old diff structure, not the content the user actually selected in the UI, demonstrating the corruption without any warning shown to the user.
