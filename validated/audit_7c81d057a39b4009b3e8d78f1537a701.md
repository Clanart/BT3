## Finding: Path-Keyed `safe.directory` Trust Persists Independent of the Content Later Found at That Path

This maps directly onto the reported bug class: a whitelist entry is bound to a *mutable identifier* (a proxy contract address / here, a filesystem path) rather than to the *content* that was actually reviewed, so once trust is granted it silently carries over to whatever different content later occupies that same identifier.

### Finding Description

Git's "dubious ownership" protection blocks git from operating on a repository owned by a different user, specifically to stop an attacker from planting a hostile repo (with malicious hooks/config) at a path a victim will later open. Desktop lets the user permanently bypass this protection for a given directory via `addSafeDirectory`, which appends the raw path string to the *global* `safe.directory` git config: [1](#0-0) 

This is invoked from two UI entry points, both offering a one-time "Trust Repository" action for a path flagged as unsafe: [2](#0-1) [3](#0-2) 

The trust decision is keyed **only on the path string**, not on repository identity (remote URL, commit, fingerprint, or ownership). `getRepositoryType` subsequently classifies any repository found at a trusted path as safe purely by consulting the global `safe.directory` list: [4](#0-3) 

This is the exact "whitelist is incompatible with proxies" pattern: the whitelist entry is `%path%`, but the "implementation" behind that identifier (the actual repository content/owner at that path) can be swapped out at any later time — e.g., on a shared machine, a mapped network drive, a container mount, or simply because the user removed and later reused the same working-directory path for an unrelated/malicious clone. Once whitelisted, Desktop/Git never re-checks *who* owns the content now — only that the path string matches an entry that was trusted at some point in the past.

### Impact Explanation

If an attacker (a different local/network user with write access to the same mount point, e.g. a shared drive, multi-user machine, or CI runner reusing workspace paths) can place a git repository with malicious `.git/hooks`, `core.hooksPath`, or other repo-scoped config at a path previously whitelisted via "Trust Repository," Desktop will treat it as fully trusted and allow git to execute repository-controlled hooks/config on subsequent operations (fetch, checkout, commit, etc.) — the very outcome the "dubious ownership" check exists to prevent. The change is silent: nothing in the UI re-surfaces the unsafe-ownership warning once a path has been whitelisted, matching the report's core complaint that stale trust in a mutable identifier is worse than no whitelist at all.

### Likelihood Explanation

The scenario Desktop's own warning text targets — "The Git repository appears to be owned by another user on your machine" — is precisely the shared-filesystem / multi-user-workstation / mapped-network-drive threat model, not a case requiring prior malware or admin rights on the victim's own account. Path reuse is common in practice: users delete and re-clone into the same directory, share `Documents/GitHub` style base folders across accounts, or work off network shares where multiple parties can write to the same UNC path over time.

### Recommendation

Do not persist trust keyed solely by filesystem path. Either:
- Re-validate ownership/ACL of the path at each operation rather than relying on a static global allowlist entry, or
- Bind the trust decision to a content fingerprint (e.g., the specific `.git` directory's inode/creation identity or an explicit hash of `HEAD`) so a later swap of the directory's contents invalidates the prior trust, or
- At minimum, surface a fresh warning ("this path's ownership changed since you last trusted it") whenever `getRepositoryType` detects the owner differs from the owner recorded at the time `addSafeDirectory` was invoked, instead of unconditionally trusting the path forever.

### Proof of Concept

1. User A clones (or is walked through "Trust Repository") a legitimate repo at shared path `/mnt/shared/project`; Desktop calls `addSafeDirectory('/mnt/shared/project')`, which is written permanently to the user's global `~/.gitconfig`.
2. Later, User A deletes that folder (or a different user on the shared mount removes it) and Attacker B — who has write access to the same shared mount — creates a new git repository at the exact same path `/mnt/shared/project`, containing a malicious `.git/hooks/post-checkout` (or `core.hooksPath` pointing to attacker code).
3. User A reopens Desktop, which points at `/mnt/shared/project` again. `getRepositoryType` runs `git rev-parse ...` in that path; because `safe.directory` still contains that path string, git no longer reports "dubious ownership," and the earlier "unsafe" UI flow in `missing-repository.tsx` / `add-existing-repository.tsx` never re-triggers.
4. Any git operation Desktop performs (checkout, submodule update, etc.) now executes with the attacker's hooks/config running under User A's privileges, with no additional warning ever shown, because the whitelist entry — the path — never expired even though the content behind it completely changed. /**
```typescript
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

```typescript
export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
```
