The Sherlock report is a Go/on-chain math bug (`Gt` vs `Gte` boundary condition in a convergence loop) — not directly portable to GitHub Desktop's TypeScript/Electron code. However, the same *bug class* — an incorrect/insufficiently strict boundary comparison that lets a value pass a guard it should not — has a real analog in Desktop's path-containment check.

### Title
Insufficient boundary check in `resolveWithin`'s `startsWith` root comparison allows sibling-directory escape - (File: app/src/lib/path.ts)

### Summary
`_resolveWithin` is Desktop's core "is this path safely inside the repo root" guard. It resolves both the root and the candidate path with `realpath` and then decides containment using a bare string-prefix comparison, `realResolved.startsWith(realRoot)`, with no check that the next character after the prefix is a path separator (or that the strings are exactly equal).

### Finding Description
`_resolveWithin` computes `realRoot` and `realResolved` via `fs.realpath` and returns `resolved` only if `realResolved.startsWith(realRoot)`: [1](#0-0) 

This is structurally the same class of bug as the reported `Gt`/`Gte` mistake: the code approximates the correct invariant ("resolved path is *at or under* root") with a comparison that is technically satisfiable at the wrong boundary. `String.prototype.startsWith` matches on raw characters, so any real path that shares `realRoot` as a textual prefix — even if it is actually a *sibling* directory rather than a descendant (e.g. `realRoot = /Users/victim/repo` and `realResolved = /Users/victim/repo-evil` or `/Users/victim/repository`) — passes the check even though it does not reside "underneath" the root as the function's own doc comment promises: [2](#0-1) 

This guard is the exact mechanism Desktop relies on to defend against path traversal and symlink escapes when resolving attacker-influenced file paths that originate from repository content — for example when building merge-conflict context, where `file.path` comes from the working tree/index of a cloned repository and is explicitly documented as a defense against "path traversal and symlink escapes (cross-platform)": [3](#0-2) 

The existing unit tests only cover the "obviously outside" (`..`) and null-byte cases, and symlink tests that redirect fully outside the root — none test the sibling-prefix boundary case that `startsWith` mishandles: [4](#0-3) 

### Impact Explanation
If an attacker can get a repository (via clone/fetch, or a crafted working-tree entry / symlink) to contain a directory or symlink target whose realpath textually begins with the intended root path but is actually a sibling location outside it, `resolveWithin`'s guard is bypassed. In the conflict-resolution flow this function gates raw file reads that are subsequently sent to Copilot and used to auto-resolve merge conflicts; a bypass could let the resolved "in-repo" path actually point to files outside the repository, enabling reads (and, depending on downstream write-back logic, corruption of what gets written/committed) outside the intended directory tree — matching the report's "silent corruption of what the user commits" and "read outside the repo" impact categories.

### Likelihood Explanation
Exploitability depends on being able to arrange a root/sibling pair sharing a string prefix and controlling a symlink or path entry whose `realpath` resolves into that sibling — this is a narrower precondition than a plain `..` traversal, and I could not fully verify from the index which of `resolveWithin`'s call sites (in `app-store.ts`, `dispatcher.ts`) allow attacker-chosen root paths versus only Desktop-chosen root paths, which affects real-world reachability.

### Recommendation
Replace the string-prefix check with a boundary-aware comparison, e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)`, mirroring the fix pattern in the reported issue (tightening a loose relational/string comparison to enforce the exact intended boundary).

### Proof of Concept
Conceptual (not executed): call `resolveWithin('/Users/victim/repo', someSegment)` where `someSegment` resolves (after `realpath`) to `/Users/victim/repo-evil/secret.txt`. Because `'/Users/victim/repo-evil/secret.txt'.startsWith('/Users/victim/repo')` is `true`, the function returns the resolved path as "safe" even though it is outside `/Users/victim/repo`, at line 71 of `app/src/lib/path.ts`: [5](#0-4) 

Note: I was unable to fully trace whether an attacker-controlled repository can realistically place content whose real path collides at this exact string boundary given current call sites; this should be validated in a live Devin session with full repo/file access before treating it as confirmed-exploitable rather than a latent guard weakness.
