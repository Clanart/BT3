### Title
Missing non-payable check in distribution precompile's `rewards` query permanently strands sent funds - (File: `precompiles/distribution/distribution.go`)

### Summary
The `rewards(address)` view method of the distribution precompile (address `0x0000000000000000000000000000000000001007`) is the only query-type method in that precompile that omits `pcommon.ValidateNonPayable(value)`. Because the EVM's standard call semantics move `msg.value` into the precompile's associated Sei bank account before precompile logic runs, and `rewards` never returns or forwards that credited balance, any wei sent alongside a `rewards` call becomes permanently stuck in the distribution module's mapped Sei address, exactly matching the reported bug class ("payable-capable entry point with no withdraw mechanism → permanent fund lockup").

### Finding Description
For EVM calls with value, `DBImpl.AddBalance`/`SubBalance` (`x/evm/state/balance.go` and `giga/deps/xevm/state/balance.go`) automatically transfer the `usei`/`wei`-split amount into the recipient EVM address's associated Sei bank account as part of standard message-call processing — this happens irrespective of whether the target is a normal contract or a precompile, and independent of what the precompile's `Execute` implementation itself does. [1](#0-0) 

To avoid stranding these auto-credited funds, every payable state-mutating distribution method (`setWithdrawAddress`, `withdrawDelegationRewards`, etc.) either rejects value with `ValidateNonPayable` or explicitly consumes it via `pcommon.HandlePaymentUsei`, which refunds the amount from the precompile's Sei address back to the payer before constructing the real `Msg`. [2](#0-1) 

Every other read-only distribution method funnels through `p.validateInput`, which calls `pcommon.ValidateNonPayable(value)` and rejects any nonzero `value` before even reaching the querier: [3](#0-2) [4](#0-3) 

`rewards`, however, only validates argument length and never checks or handles `value` at all, despite being dispatched the same way as the other view methods and receiving the same `value` parameter: [5](#0-4) [6](#0-5) 

This gap is explicitly flagged in the integration test suite comment, which documents that `rewards()` is "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)" and deliberately has no "view rejects value" test for it: [7](#0-6) 

### Impact Explanation
Any unprivileged EVM caller (contract or EOA transaction sender) that calls `rewards(address)` on `0x...1007` with a nonzero `value` will have that value auto-credited into the distribution precompile's mapped Sei bank account by the StateDB bridge, but the precompile logic performs no refund, no `HandlePaymentUsei`, and no other mechanism exists to recover or forward this balance. The sent usei/wei is permanently locked/inaccessible — a concrete, irreversible loss of user funds triggered by a single transaction, meeting the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
High from a mechanical standpoint (any transaction sender can trigger it with a single call), though realistic exploitation requires a caller to mistakenly or naively attach `value` to a `rewards` query — likely via wallet/dApp misuse, an integrator bug, or a griefing/social-engineering vector, similar to the original accidental-ETH-transfer scenario in the source report.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` (or route through `p.validateInput(value, args, 1)`) inside `rewards` in `precompiles/distribution/distribution.go`, consistent with all sibling view methods (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`), so a value-bearing call reverts before the StateDB credits the precompile's Sei address.

### Proof of Concept
1. Caller (any associated EVM account) constructs a transaction calling `rewards(address delegatorAddr)` on `0x0000000000000000000000000000000000001007` with `value = 1000000000000000000` wei (1 SEI) attached.
2. The EVM's standard call path (`x/evm/state/balance.go` `AddBalance`) credits the corresponding usei amount into the Sei account mapped to the precompile's EVM address before `PrecompileExecutor.Execute`/`rewards` runs. [1](#0-0) 
3. `rewards` executes normally (`pcommon.ValidateArgsLength(args, 1)` only), returns the queried reward data, and the call succeeds — no error, no refund, no `HandlewPaymentUsei`. [6](#0-5) 
4. The 1 SEI sent by the caller is now held by the distribution-precompile's associated Sei address with no code path in the precompile or module to reclaim or withdraw it — permanent fund loss confirmed by comparing pre/post bank balances of caller vs. the precompile address.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
