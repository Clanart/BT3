The strongest analog to the report's root cause — a component (the withdrawal precompile) trusting an unchecked `source`/`target` field of an incoming object — is `shopify_app`'s webhook HMAC verification, where the payload signature is validated but the claimed shop identity is not bound to that signature at all.

### Title
Webhook HMAC verification does not bind `X-Shopify-Shop-Domain` to the signed payload, enabling cross-shop webhook forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only authenticates the raw request body via HMAC; it never verifies that the `X-Shopify-Shop-Domain` header actually belongs to the shop that produced that body. The `shop_domain` accessor simply returns the raw, unauthenticated header value, which downstream code (including the gem's own generator templates) uses directly to resolve tenant/shop records.

### Finding Description
`PayloadVerification#hmac_valid?` computes an HMAC over `request.raw_post` using the app's single shared `ShopifyApp.configuration.secret` (the app's OAuth client secret, identical for every shop that has installed the app) and compares it to the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`WebhookVerification#verify_request` gates the action purely on this body HMAC, and `shop_domain` is derived independently from an unsigned header: [2](#0-1) 

Because the secret is shared across *all* shops on the app (not per-shop), and the HMAC covers only the body (never the shop-domain header), any account that legitimately installs the app on their own shop can generate a validly-signed webhook body of their choosing (by triggering any webhook event with attacker-controlled fields), then resend that exact body/HMAC pair while substituting an arbitrary victim shop's domain in `X-Shopify-Shop-Domain`. The signature check still passes because it never inspected the domain.

The generator-provided job template — the gem's own recommended pattern for consuming this concern — takes that unauthenticated domain and uses it directly to resolve the tenant record: [3](#0-2) 

The documentation explicitly instructs custom controllers to dispatch background jobs keyed on this same unauthenticated `shop_domain` value: [4](#0-3) 

This is the same class of defect as the reported issue: an object (`Transfer` there, the webhook "shop identity" claim here) is accepted and acted upon by a privileged routine without validating that its asserted source actually corresponds to the party the cryptographic check authenticated.

### Impact Explanation
Any unrelated/unprivileged merchant who installs the target app can forge webhook events that are processed by the app *as if they originated from a completely different, victim shop* — a cross-tenant confused-deputy condition. Depending on which webhook topic is abused, this can inject fabricated order/customer data into a victim shop's records, or trigger mandatory privacy webhooks (`shop/redact`, `customers/data_request`, `customers/redact`) against a victim shop, causing unauthorized data deletion/processing for a shop the attacker has no relationship with.

### Likelihood Explanation
The only prerequisite is that the attacker be an app user on any shop (installing a public/embedded app is unprivileged and self-service), and be able to trigger or capture one legitimately-signed webhook body for content they control. No secret disclosure or elevated access is required — this is directly reachable from an unrelated-merchant HTTP flow (webhook delivery endpoint is public), making it a Critical/High-likelihood forgery path once identified.

### Recommendation
Bind the authenticated shop identity to the HMAC-verified payload rather than trusting the `X-Shopify-Shop-Domain` header independently — e.g., derive/validate the shop from the signed body content itself, or require the shop domain to be cross-checked against a per-shop-derived secret/session before use, mirroring the CALLCODE fix's approach of properly validating the `source`/`target` fields instead of blindly trusting caller-supplied identity.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with attacker-controlled body content `B`; Shopify sends `POST /webhooks` with `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures this request and resends it unmodified except for the header value: `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `verify_request` recomputes `hmac_valid?(B)` using the same shared app secret — passes, since `B` is unchanged. [5](#0-4) 
4. The job handler resolves `Shop.find_by(shopify_domain: "victim.myshopify.com")` and processes attacker-controlled payload `B` under the victim shop's context. [6](#0-5)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
