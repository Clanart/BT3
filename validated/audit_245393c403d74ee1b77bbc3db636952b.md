### Title
Arbitrary non-standard `script_pubkey` payments make the entire multisig transaction unbroadcastable, bricking all co-batched payments - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`SignableTransaction::new` validates only the payment *amounts* (≥ `DUST`) and the total transaction weight (`MAX_STANDARD_TX_WEIGHT`), but never validates that each payment's `script_pubkey` is itself standard/relayable. A single non-standard output script makes the fully-signed transaction fail Bitcoin `IsStandard` relay policy, so the transaction can never be broadcast — mirroring the Notional bug where a transfer reverting on an uncooperative receiver blocked liquidations.

### Finding Description

In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), payments are accepted as raw `(ScriptBuf, u64)` pairs. The only checks applied are:

- `*amount < DUST` → `DustPayment` (line 165-169)
- `data.len() > 80` → `TooMuchData` (line 171)
- aggregate weight > `MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction` (line 241)

Nothing verifies that `payment.0` (the `script_pubkey`) is standard or even well-formed. Bitcoin Core rejects transactions containing non-standard output scripts at mempool admission — e.g., scripts with pushes exceeding `MAX_SCRIPT_ELEMENT_SIZE` (520 bytes), non-standard bare multisig (>3-of-3), scripts with excessive opcodes, or certain unspendable forms. `calculate_weight_vbytes` (line 62) only measures size, not validity.

Downstream, `TransactionSignMachine::sign` (line 355) produces valid Schnorr signature shares and `TransactionSignatureMachine::complete` (line 413) produces a fully-signed `Transaction` — which then cannot be relayed. The transaction object itself reports a plausible `txid()` (line 259), so signing/orchestration layers believe a valid send was produced, but the TX will never confirm. Because Serai batches multiple payments into one transaction, one malicious payment script poisons the entire batch: every other legitimate payment and the change output in that transaction is blocked, exactly as one reverting receiver blocked the whole liquidation in the reference report.

Reachability: the processor builds refund `Payment`s whose destination `script_pubkey` is derived from the *origin's* on-chain `script_pubkey` (see `get_outputs` in processor/src/networks/bitcoin.rs:714-728, which reads `spent_output.script_pubkey` as the presumed refund origin). An attacker who funds a Serai InInstruction from an input with a deliberately non-standard script (e.g., a P2WSH whose script pattern resolves to a nonstandard bare form, or a bare nonstandard script directly) causes any subsequent refund to that script to render the whole transaction non-standard and unrelayable.

### Impact Explanation

Permanent blocking of a batched transaction: signature shares are consumed, the transaction is "complete," yet it cannot enter the mempool. All other payments sharing the transaction are frozen; the consumed `ReceivedOutput` inputs remain tied to a plan whose eventuality can never resolve — an unprivileged-party-reachable denial of service on protocol fund movement, analogous to unliquidatable accounts.

### Likelihood Explanation

Requires the scheduler to emit a payment to a non-standard script — most naturally via the refund-to-origin path, where the attacker fully controls the origin `script_pubkey` by spending from a non-standard script. No collusion, key access, or validator misbehavior needed.

### Recommendation

Validate each payment `ScriptBuf` for standardness in `SignableTransaction::new` (e.g., accept only known standard templates — P2TR/P2WPKH/P2WSH/P2PKH/P2SH — or run an `IsStandard`-equivalent check), and on the refund path fall back to a safe destination (or skip/donate the dust) when the origin script is non-standard.
