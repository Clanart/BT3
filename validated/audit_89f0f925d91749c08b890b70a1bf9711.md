### Title
Out-of-bounds indexing panic in PedPoP `KeyMachine::calculate_share` via a `ThresholdCommitments` message with fewer than `t` coefficients - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The analog of CVE-2024-21176 (a difficult-to-exploit, low-privileged-party remote denial of service causing a repeatable crash) is present in Serai's PedPoP DKG. `KeyMachine::calculate_share` assumes every participant's PedPoP commitment vector contains exactly `params.t()` coefficients and indexes it directly (`commitments[t]`). The commitment vectors are deserialized from peer-supplied bytes with attacker-chosen lengths and are never checked against `t`, so a DKG participant who publishes a short commitment vector triggers an index-out-of-bounds panic — a repeatable crash of the victim's key-generation task, aborting the DKG.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` precomputes "stripes" by indexing each participant's commitment vector at every degree `0 .. t`:

```rust
// crypto/dkg/pedpop/src/lib.rs:505-508
let mut stripes = Vec::with_capacity(usize::from(self.params.t()));
for t in 0 .. usize::from(self.params.t()) {
  stripes.push(self.commitments.values().map(|commitments| commitments[t]).sum());
}
```

`self.commitments` is a `HashMap<Participant, Vec<C::G>>` populated from `ThresholdCommitments` messages each participant broadcasts. On the wire these carry an explicit, sender-controlled length: the tributary `Transaction::read` for `DkgCommitments` reads `commitments_len` (u8) and `each_commitments_len` (u16) and allocates vectors of exactly those lengths, bounded only by `TRANSACTION_SIZE_LIMIT` — with no comparison against the negotiated threshold `t` (`coordinator/src/tributary/transaction.rs:275-296`). The same absence of a length check applies inside PedPoP: `calculate_share` calls `share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share)` (line 490) and later `commitments[t]` (line 507), both of which assume `commitments.len() == t` but never enforce it.

`validate_map` (line 468) only checks the *key set* of the shares map (that the sender set equals all participant indexes), not the per-participant vector length. A participant `l` can therefore send a validly-formed `ThresholdCommitments`/encrypted-share bundle whose commitment vector has length `k < t`. The batch verification of the share itself may even succeed or fail gracefully, but the stripe loop at line 507 indexes `commitments[k]` on a `Vec` of length `k`, producing a `index out of bounds` panic.

Separately, `self.commitments[&l]` at line 490 panics outright if a participant index accepted by `validate_map` (any `1 ..= n`) is absent from the local commitments map — e.g., when commitment and share rounds race and a participant's `ThresholdCommitments` was never recorded, while `DkgShares`/`EncryptedMessage` bytes naming that participant were accepted.

### Impact Explanation
An unprivileged DKG participant (any party able to submit PedPoP messages, i.e., a validator-set member during key generation, reachable purely through public `EncryptedMessage::read` / `ThresholdCommitments` bytes) can cause a deterministic, repeatable panic in every honest participant that calls `calculate_share` on its message. This halts the key-generation attempt; combined with `DkgCommitments`/`DkgShares` retries it produces a "frequently repeatable crash" of the DKG path, matching the CVE's complete-DOS-of-service impact class. Because the panic aborts the task rather than returning a `PedPoPError`, no blame proof is generated — the attacker is not even attributable, enabling repeated disruption across attempts.

### Likelihood Explanation
Likelihood is moderate ("difficult to exploit" analog): the attacker must be a participant in a DKG session and must craft a structurally valid `EncryptedMessage`/`ThresholdCommitments` bundle whose share component parses (`SecretShare` deserialization inside `decrypt`) while the accompanying commitment vector is short, or arrange for the `commitments[&l]` missing-key panic by timing share delivery. It does not require breaking cryptography — only control over the length field of self-authored commitment vectors, which the wire format explicitly provides (`commitments_len`, `each_commitments_len`). No collusion or threshold compromise is needed; a single malicious participant suffices.

### Recommendation
- In `KeyMachine` construction (and in `ThresholdCommitments::read`/`EncryptionKeyMessage::read` paths), reject any participant commitment vector whose length is not exactly `params.t()`, returning `PedPoPError::InvalidCommitments { participant }` (with blame) instead of panicking.
- Replace `self.commitments[&l]` and `commitments[t]` with fallible lookups (`get(l).ok_or(...)`, `get(t)`) that map to `PedPoPError`, so malformed or absent commitments produce blame-attributable errors rather than process aborts.
- Enforce `each_commitments_len == C::G::Repr::len() * t` (or the expected serialized shape) at the tributary `Transaction::read` layer so over- or under-length `DkgCommitments` transactions are rejected at parse time.

### Proof of Concept
1. Initialize a PedPoP `KeyMachine` for `t = 3, n = 3` as an honest participant `i`.
2. As participant `l`, serialize a `ThresholdCommitments`-equivalent payload containing a commitment vector of length 1 (e.g., `[C::generator() * r]` only) and a well-formed `EncryptedMessage<C, SecretShare<C::F>>` whose plaintext share is any canonical scalar.
3. Feed both through the normal paths: `Transaction::read`/`ThresholdCommitments` registration stores the length-1 vector in `self.commitments[l]` (only `TRANSACTION_SIZE_LIMIT` is checked at `transaction.rs:286`), then `calculate_share(rng, shares)` is invoked.
4. `validate_map` passes (all expected participant keys present); share decryption and `share_verification_statements` queueing proceed using `self.commitments[&l]`; after `batch.verify_with_vartime_blame()`, the stripe loop evaluates `commitments[1]` on the length-1 vector at `pedpop/src/lib.rs:507`, panicking with `index out of bounds: the len is 1 but the index is 1`.
5. Every honest participant executing `calculate_share` crashes identically, and no `PedPoPError`/blame proof is emitted, so the abort is repeatable on each DKG attempt.

Caveat: if a commit-time length equality check (`commitments.len() == t`) exists in a code path not surfaced here (e.g., inside `ThresholdCommitments` construction or an upstream `PedPoPMachine` validation layer), the `commitments[t]` panic is partially mitigated, but the `self.commitments[&l]` missing-key panic at line 490 for a validated-but-absent participant index remains as the reachable crash.   pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;
