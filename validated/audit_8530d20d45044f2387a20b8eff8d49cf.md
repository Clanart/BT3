### Title
OP_RETURN output omitted from fee/weight calculation causes underpaid fee and non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external finding describes a pricing formula whose denominator omits a scale factor, producing a systematically wrong result used downstream. The analog in Serai is `SignableTransaction::new`, where the transaction's weight/vbytes — the denominator-equivalent in the fee formula `fee = fee_per_vbyte * vbytes` — is computed from a transaction skeleton that omits the OP_RETURN output, even though that output is appended to the final signed transaction. Every transaction carrying `data` pays a fee computed for a smaller transaction than the one actually produced.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before the weight calculation, but `calculate_weight_vbytes` is invoked with `payments` — not `tx_outs` — so it builds its model transaction solely from the payment outputs. The same omission occurs on the change path, which again passes `payments` rather than the outputs actually present. [1](#0-0) [2](#0-1) 

Consequences of the undercounted `vbytes`/`weight`:

1. `needed_fee = fee_per_vbyte * vbytes` undercharges by `fee_per_vbyte * vbytes(OP_RETURN)` — roughly 90+ vbytes for a near-maximal 80-byte payload. [3](#0-2) 
2. The minimum-relay-fee guard compares the undercharged fee against the undercounted vbytes, so a transaction can pass the check while its *real* feerate (`needed_fee / real_vbytes`) falls below `DEFAULT_MIN_RELAY_TX_FEE`, producing an unrelayable signed transaction. [4](#0-3) 
3. The `MAX_STANDARD_TX_WEIGHT` check uses the undercounted `weight`, so a transaction whose real weight exceeds standardness can be constructed and signed. [5](#0-4) 
4. `fee()` reports `inputs - outputs`, which equals the miscomputed `needed_fee` regardless of the transaction's true size, so accounting sees a consistent but wrong number. [6](#0-5) 

### Impact Explanation
Any call to `SignableTransaction::new` with `data: Some(_)` yields a signed transaction whose effective feerate is lower than the caller-specified `fee_per_vbyte`, potentially below the relay minimum or above the standard weight cap. Such a transaction will not propagate/confirm — funds are committed to a spend that cannot be mined at the intended rate, and `Eventuality`-style txid matching can never resolve. Since `data` content and length are caller/input-controlled (untrusted transaction data per scope rules), an unprivileged party influencing the data payload controls the magnitude of the fee shortfall.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is non-empty — no race or adversarial sequencing is required. The shortfall scales linearly with `data` length (up to the 80-byte cap), and with high `fee_per_vbyte` the divergence grows. It requires the caller to attach data, so it affects only that code path rather than all transactions.

### Recommendation
Compute the weight/vbytes over the *complete* output set. Move the OP_RETURN push before the weight calculation and pass `tx_outs` (or an equivalent enumeration including data and change) to `calculate_weight_vbytes` in both the no-change and with-change calls, and use that corrected weight for `MAX_STANDARD_TX_WEIGHT`. Alternatively, add the encoded OP_RETURN size to the skeleton transaction inside `calculate_weight_vbytes`.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0; 80]), fee_per_vbyte)`. The returned `needed_fee` equals `fee_per_vbyte * vbytes(tx without the OP_RETURN)`, while `tx.vsize()` includes the ~91-vbyte OP_RETURN, so `needed_fee / tx.vsize() < fee_per_vbyte`. Choosing `fee_per_vbyte` such that `needed_fee` equals the minimum-relay threshold for the undercounted size makes the real feerate strictly below `DEFAULT_MIN_RELAY_TX_FEE` while the `TooLowFee` check still passes, yielding a signed transaction Bitcoin nodes will not relay.
