### Title
Security-review finding dedup keys on `(filePath, category)` only, letting a second distinct vulnerability silently collide with and bypass an already-reported finding - ([File: plugins/security-guidance/hooks/llm.py])

### Summary
The `security-guidance` plugin's commit/push/Stop review hooks track which vulnerabilities have already been surfaced to the developer using a dedup key composed of only `filePath` and `category`, deliberately excluding the actual vulnerable code snippet. This mirrors the `DestinationBridge` bug where a hash derived from too few distinguishing fields let two logically different transactions collide, silently overwriting the earlier one's approval state. Here, two genuinely different vulnerabilities of the same category in the same file collide on the same key, so the second one can be treated as "already known" and its blocking review (`sys.exit(2)`) is suppressed.

### Finding Description
`_finding_keys` builds the identity set purely from `filePath` and `category`: [1](#0-0) 

This key is used both to record findings into the persisted `previous_findings` state and to decide whether a newly-found vulnerability should be dropped as a duplicate: [2](#0-1) 

The comment at the recording sites explicitly acknowledges the tradeoff of not including the code content in the key: [3](#0-2) 

The same `(filePath, category)`-only key is used to build the "already surfaced — do not re-flag" instruction fed back to the LLM reviewer: [4](#0-3) 

Because the key does not include any content-derived component (e.g., a hash of `vulnerableCode`, line number, or code location), a **second, unrelated** vulnerability of the same category in the same file (e.g., two separate hardcoded secrets, two separate SQL-injection sinks, or two separate SSRF spots in one file) collides with the first one's key. The system then instructs the reviewer not to re-flag it unless it decides the "same spot" had an incomplete fix, and `_dedup_against_state` will drop it outright if a concurrent hook already recorded that key — exactly analogous to the bridge's `txnHash` collision silently overwriting `txnToThresholdSet[txnHash]` for an unrelated transaction.

### Impact Explanation
The security-guidance plugin's entire enforcement mechanism (blocking `Stop`/commit/push hooks with exit code 2 to force Claude to fix flagged issues) relies on findings actually being surfaced. A collision on `(filePath, category)` means a second, distinct, newly-introduced vulnerability in the same file and category as a prior finding can be silently treated as already-known and never surfaced to the developer or the agent, i.e., a real security defect ships without ever triggering the blocking review — a direct bypass of the security-review approval gate, analogous to how the bridge's threshold-approval record was overwritten and broken by the colliding `txnHash`.

### Likelihood Explanation
This requires only ordinary, unprivileged code-editing activity within a single session: introducing two different vulnerabilities of the same category in the same file across turns/commits is a common and easily-triggered pattern (e.g., copy-pasted insecure code, or a prompt-injected/malicious diff intentionally engineered to reuse a category+file pair already flagged earlier in the session to "ride along" undetected). No special privileges or race conditions are needed beyond normal session flow, making this readily reachable.

### Recommendation
Include a content-derived discriminator in the dedup key — e.g., a hash of `vulnerableCode` (or a normalized form of it) combined with `filePath` and `category` — so that only truly identical findings are deduplicated, while distinct vulnerabilities sharing a file/category are still surfaced independently. This mirrors the bridge fix of including `srcChain`/`srcAddr` in the hashed payload to prevent unrelated data from colliding into the same key.

### Proof of Concept
1. Introduce vulnerability A (e.g., hardcoded secret) at `app.py:10`, category `"Hardcoded Secret"`. Commit review flags it; `previous_findings` records key `("app.py", "Hardcoded Secret")` per [5](#0-4) .
2. In a later commit within the same session, remove vulnerability A but introduce an unrelated vulnerability B — a different hardcoded secret at `app.py:80`, same category `"Hardcoded Secret"`.
3. The reviewer prompt tells the LLM "already surfaced ... DO NOT re-flag" for `("app.py", "Hardcoded Secret")` unless the exact same spot has an incomplete fix, per [6](#0-5) ; even if the LLM still emits it, `_dedup_against_state` can drop it if the key was recorded concurrently, per [7](#0-6) .
4. Vulnerability B is never surfaced to the developer, and the blocking `sys.exit(2)` review gate never fires for it — the new, distinct vulnerability ships undetected.

```python
def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```

```python
    def _record_findings(state):
```
