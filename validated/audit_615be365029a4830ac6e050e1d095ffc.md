### Title
`ReceivedOutput::read` deserializes an attacker-controlled `offset`/`TxOut` pair without verifying the output's `script_pubkey` is actually controlled by `key + offset·G`, allowing forged "received" outputs to enter the spending pipeline - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner` establishes a critical invariant when producing `ReceivedOutput`s: the stored `offset` is guaranteed to satisfy `output.script_pubkey == P2TR(x_only(key + offset·G))` (with even-Y), i.e. the output is spendable by the threshold key after applying that offset. The serialization path `ReceivedOutput::read` reconstructs `offset`, `output`, and `outpoint` from raw bytes with no such consistency check, letting an unprivileged party fabricate outputs that will be treated as received/spendable.

### Finding Description
`ReceivedOutput` couples three fields: a `Scalar` `offset` (the private scalar adjustment needed to spend), the `TxOut` (which commits to `script_pubkey` and `value`), and the `OutPoint`. [1](#0-0)  The only code path that legitimately produces these values is `Scanner::scan_transaction`, which only emits a `ReceivedOutput` when `self.scripts` — populated exclusively by `register_offset` — contains the output's `script_pubkey`, thereby binding `offset` to that exact script. [2](#0-1)  `register_offset` itself only registers scripts derived as `key + offset·G` with an even Y coordinate, so every scanner-produced output is provably spendable via `tweak_keys`-style offset application. [3](#0-2) 

`ReceivedOutput::read` accepts a raw `Scalar` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, with no check that `output.script_pubkey` equals the P2TR script for the claimed key/offset pair. [4](#0-3)  The invariant that makes the value spendable exists only at scan time and is silently dropped at the trust boundary of deserialization.

This is the structural analog of CVE-2025-53098: untrusted bytes crossing a boundary into a context that assumes they were produced by a privileged/validated path. Just as Roo Code's `.roo/mcp.json` write path assumed file contents were agent-sanctioned and then executed them, `ReceivedOutput::read` assumes its fields satisfy the scanner's spendability invariant and hands the result to consumers that act on `value()` and `outpoint()`.

### Impact Explanation
Any component that persists or transmits `ReceivedOutput`s (e.g., scanner output relayed to a signing/spending pipeline that consumes `ReceivedOutput::read`) can be fed fabricated entries: an output whose `value` is inflated, whose `outpoint` references a UTXO the attacker controls or that doesn't exist, or whose `offset` corresponds to a different key than the one controlling `script_pubkey`. Downstream, this yields funds reported received that are not spendable — a signing session is scheduled around an input the threshold key cannot actually authorize, or an attacker is credited for a deposit that was never made to a group-controlled script. If the consumer signs a transaction spending the forged `outpoint`, the resulting transaction is invalid at best and, where the fabricated `TxOut`'s value feeds fee/change computation (`SignableTransaction` construction consumes `output.value`), corrupts the change/dust math for the real inputs. [5](#0-4) 

### Likelihood Explanation
Reachability requires only that an attacker supply bytes to `ReceivedOutput::read` — i.e., any channel where scanned outputs are serialized and re-read (DB, network relay, processor handoff) that an untrusted party can write to. The prerequisite is a deserialization consumer rather than the scanner itself; where `ReceivedOutput` is passed between mutually-distrusting components rather than kept in-process after `scan_transaction`, the forged-object attack is directly reachable. Severity is Medium–High depending on whether the consumer credits reported `value` (fund-crediting impact) or merely attempts spends (liveness/invalid-tx impact); the forging cost is zero and detection requires re-deriving the script, which no consumer is forced to do.

### Recommendation
Make the `offset ↔ script_pubkey` binding unforgeable at the deserialization boundary. Either (a) have `ReceivedOutput::read` take the `Scanner`/group key and re-derive `p2tr_script_buf(key + offset·G)`, rejecting inputs whose `output.script_pubkey` doesn't match, or (b) store a proof/domain-separated commitment that `scan_transaction` produced this output (e.g., an HMAC over `offset || output || outpoint` keyed by scanner state) so `read` cannot be satisfied by arbitrary bytes. At minimum, document `read` as trusted-inputs-only and ensure no inter-service channel feeds it unauthenticated data. [6](#0-5) 

### Proof of Concept
```rust
// networks/bitcoin context: forge a ReceivedOutput for bytes fed to ReceivedOutput::read
use bitcoin::{OutPoint, TxOut, ScriptBuf, Amount, Txid, hashes::Hash};
use k256::Scalar;
use serai_bitcoin::wallet::ReceivedOutput;

// Attacker picks: an offset that yields a key the attacker knows (e.g., offset = a),
// a TxOut paying a huge nominal value to ANY script (e.g., their own address or a
// burn script that does NOT correspond to key + a*G), and a nonexistent outpoint.
let forged_offset = Scalar::ONE; // attacker-chosen
let forged_output = TxOut {
  value: Amount::from_sat(21_000_000_0000_0000), // fabricated "received" amount
  script_pubkey: ScriptBuf::new(),              // not bound to offset at all
};
let forged_outpoint = OutPoint { txid: Txid::all_zeros(), vout: 0 };

let mut bytes = forged_offset.to_bytes().to_vec();
bytes.extend(bitcoin::consensus::encode::serialize(&forged_output));
bytes.extend(bitcoin::consensus::encode::serialize(&forged_outpoint));

// ReceivedOutput::read accepts this unconditionally — no script/offset binding check.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 21_000_000_0000_0000);
// `forged` is now indistinguishable from a scanner-produced ReceivedOutput:
// value() reports a deposit that was never made to a group-controlled script,
// and any consumer spending forged.outpoint() either builds an invalid tx or
// signs against a UTXO the threshold key cannot authorize (offset doesn't match
// the real script_pubkey's discrete log relationship).
```

Caveat: the end-to-end exploitability depends on which component consumes deserialized `ReceivedOutput`s from an attacker-reachable channel — that consumer lives outside the in-scope `networks/bitcoin/src` files, so the confirmed defect is the missing invariant enforcement at `ReceivedOutput::read` itself.

  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  /// Write a ReceivedOutput to a generic satisfying Write.
  pub fn write<W: Write>(&self, w: &mut W) -> io::Result<()> {
    w.write_all(&self.offset.to_bytes())?;
    w.write_all(&serialize(&self.output))?;
    w.write_all(&serialize(&self.outpoint))
  }

  /// Serialize a ReceivedOutput to a `Vec<u8>`.
  pub fn serialize(&self) -> Vec<u8> {
    let mut res = Vec::new();
    self.write(&mut res).unwrap();
    res
  }

    // This loop will terminate as soon as an even point is found, with any point having a ~50%

    loop {

            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
