### Title
Reward Accrual Permanently Frozen When `_totalSupply` Is Zero in `WomUp` Staking Contract - (File: `wombat/WomUp.sol`)

### Summary
`WomUp.sol` implements a Synthetix-style staking rewards mechanism identical in structure to the pattern described in the external report. Its `rewardPerToken()` function returns the stored value without accruing rewards whenever `_totalSupply` is zero, while `rewardRate` and the elapsed-time window (`lastTimeRewardApplicable()`/`periodFinish`) keep advancing independently of participation. Any ordinary staker can trigger the zero-supply condition simply by withdrawing, permanently freezing the MGP rewards that would have accrued during that gap.

### Finding Description
`rewardPerToken()` in `WomUp.sol` is implemented as: [1](#0-0) 

When `totalSupply() == 0`, the function simply returns `rewardPerTokenStored` and does not account for elapsed time. However, `rewardRate` is fixed once at campaign start via `initializeRewards()`, and `periodFinish` continues to progress with `block.timestamp` regardless of whether anyone is staked: [2](#0-1) 

Because `stake`/`withdraw`/`migrate` are unprivileged, ordinary-user functions that directly mutate `_totalSupply`, any staker (or the last remaining staker) can reduce `_totalSupply` to zero at any point during the active 7-day reward window: [3](#0-2) 

During any interval where `_totalSupply == 0`, `lastUpdateTime` is advanced to `lastTimeRewardApplicable()` by the `updateReward` modifier without incrementing `rewardPerTokenStored`, so the MGP reward corresponding to that time slice is never credited to `rewardPerTokenStored` and can never be claimed by any staker, past or future: [4](#0-3) 

Unlike other reward-pool implementations in this codebase (e.g., `BaseRewardPool`/`BaseRewardPoolV2`), which queue undistributed rewards via `queuedRewards` when `totalStaked() == 0` and later fold them back into `rewardPerTokenStored` once someone stakes again, `WomUp.sol` has no queuing/reclaim mechanism at all: [5](#0-4) 

There is also no way to recover the lost rewards after the campaign starts — `rescueReward()` only works before `startTime` or before `rewardRate` is set: [6](#0-5) 

### Impact Explanation
MGP tokens allocated as rewards for the 7-day `WomUp` campaign become permanently unclaimable for any period during which `_totalSupply` is zero. This is a direct, permanent loss/freeze of protocol reward funds with no recovery path once the campaign has started, since `rescueReward()` is only usable pre-launch. This matches "permanent freezing/loss of unclaimed yield" impact criteria.

### Likelihood Explanation
The trigger requires no privileged access — any staker can call `withdraw()` (or `migrate()`) to zero out `_totalSupply`, and this is entirely plausible in practice: a single staker who withdraws before another stakes (or the sole/last staker withdrawing) creates the zero-supply gap during the live 7-day period. No admin action or governance step is needed to reach the vulnerable state.

### Recommendation
Track and carry forward unclaimed rewards from zero-supply intervals, analogous to the `queuedRewards` pattern already used in `BaseRewardPool`/`BaseRewardPoolV2`: when `_totalSupply == 0`, accumulate the reward otherwise lost and fold it into `rewardPerTokenStored` (or extend `periodFinish`) once staking resumes, or provide an owner-controlled sweep specifically for reward amounts that accrued during verified zero-participation windows.

### Proof of Concept
1. Owner calls `initializeRewards()`, setting `rewardRate = balance / 7 days` and `periodFinish = now + 7 days`.
2. User A calls `stake(amount)`; `_totalSupply > 0`.
3. Time passes (T1); User A calls `withdraw(amount, false)` — now `_totalSupply == 0`. `lastUpdateTime` is set to `lastTimeRewardApplicable()` (current time), `rewardPerTokenStored` unchanged for the elapsed window since deposit, but no further accrual can occur while supply is 0.
4. Time passes further (T2) with zero stakers — `rewardRate * (T2 - T1)` worth of MGP is never reflected in `rewardPerTokenStored`.
5. User B calls `stake()` after T2; `updateReward` sets `lastUpdateTime = block.timestamp` without ever crediting the `T1→T2` reward interval to `rewardPerTokenStored`.
6. When `periodFinish` is reached, the MGP corresponding to the `T1→T2` zero-supply window remains locked in the `WomUp` contract, unclaimable by any user, and unrecoverable by the owner since `rescueReward()` reverts once `rewardRate > 0`.

        _balances[msg.sender] = _balances[msg.sender] - (amount);

        IERC20(mWom).safeTransfer(msg.sender, amount);

        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();
