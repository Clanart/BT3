## Title
Inflation calculation uses `slots_per_year` from the calculation-time slot-time regime while capitalization accrues at the (possibly different) faster slot-time regime active during the actual epoch — mismatched rate constant analogous to stale `blocksPerYear` - (File: `runtime/src/bank.rs`)

### Summary
The external report's core issue is a hardcoded, epoch-derived time constant (`blocksPerYear`) becoming stale relative to the actual block-production rate, silently inflating a rate calculation by 25%. In this Agave fork, the analogous per-time constant is `slots_per_year`, which is no longer a single genesis constant but a table-driven value (`SlotParams::slots_per_year`) that changes when slot-time-reduction features (`reduce_slot_time_to_350ms/300ms/250ms/200ms`) activate [1](#0-0) . The inflation-reward formula divides capitalization growth by `slots_per_year` the same way Compound's rate model divides `baseRatePerYear` by `blocksPerYear` [2](#0-1) .

### Finding Description
`calculate_epoch_inflation_rewards` computes the reward for `epoch` as `validator_rate * capitalization * epoch_duration_in_years`, where `epoch_duration_in_years` is `slots_in_epoch / slots_per_year_for_epoch(epoch)` [3](#0-2) [2](#0-1) . `slots_per_year_for_epoch` looks up the `SlotParams` active at the *first slot of that epoch* via `slot_params_at_slot` [4](#0-3) .

The `SlotParamsArchive` used for this lookup is rebuilt fresh from the *currently active* `FeatureSet` every time `apply_slot_time_persistent_changes`/`new_from_feature_set`-style construction runs, using `SlotParamsArchive::new` [5](#0-4) . Crucially, a slot-time-reduction feature's effect is delayed by exactly one epoch via `feature_effective_slot` (activation epoch E → effective at first slot of E+1) [6](#0-5) . This one-epoch lag is intentional for shred-filter enforcement, but it is reused unconditionally for the inflation-rate divisor as well, because `slot_params_at_slot`/`params_at_slot` is the single source of truth for both concerns [7](#0-6) .

This mirrors the report's bug exactly: a constant meant to represent "how many time-units occur per year" (`blocksPerYear` / `slots_per_year`) is derived from an assumption (block/slot cadence) that can change out from under the formula that consumes it. Here, the change is legitimate (feature-gated slot-time reduction), but the *rate at which the divisor updates* (one full epoch after activation) does not necessarily match the *rate at which the numerator (actual slot production) changes* — slot production speeds up immediately once the new slot-time takes effect at consensus level (tracked separately via PoH/bank `ns_per_slot`), while `slots_per_year` used for the inflation-reward divisor is deliberately staged behind an epoch boundary. If actual slot cadence increases before the epoch boundary that the `slots_per_year_for_epoch` lookup honors (e.g., due to any path that advances `ns_per_slot` faster than the staged `param_transitions` table, or due to `slots_per_year_for_epoch` being computed for the *first slot* of an epoch rather than accounting for a mid-epoch transition when `slot_time_feature_gates()` ever changes order/gating logic), the divisor used in `calculate_epoch_inflation_rewards` under- or over-states the number of slots per year relative to the actual number of slots the epoch will contain, producing an inflation-reward miscalculation analogous to the 25% error in the report.

### Impact Explanation
If `slots_per_year` used in the inflation-reward formula is inconsistent with the epoch's actual slot count/duration, the validator/staker inflation reward computed by `calculate_epoch_inflation_rewards` is proportionally wrong (over- or under-minting capitalization) [2](#0-1) . Because this calculation is consensus-critical (it feeds `capitalization` and epoch reward distribution used identically by all validators), a systematic mismatch would still be deterministic and not directly cause a fork by itself — but it constitutes real "false execution"/incorrect fund issuance (over/under minting) if the staged `slots_per_year` table and the actual slot-time-in-effect for that epoch diverge, which is the direct analog of the financial-loss class named in the External Report (miscalculated rate causing incorrect payout).

### Likelihood Explanation
This requires the slot-time-reduction feature-gate machinery (`reduce_slot_time_to_*` features) to be activated, and for the one-epoch-delayed `SlotParamsArchive` transition table to disagree with the slot cadence actually observed within an epoch. I was not able to fully trace, within the remaining budget, every call site that advances `ns_per_slot`/PoH timing at consensus level to confirm whether such a mismatch window is actually reachable in the current codebase, or whether the one-epoch delay is uniformly respected everywhere `ns_per_slot` is read (e.g., `apply_slot_time_persistent_changes` in `runtime/src/bank.rs:4888-4898`) [8](#0-7) . This is a design area unique to this fork (not present in mainline Agave) and warrants deeper review of `SlotParamsArchive::new`, `feature_effective_slot`, and every consumer of `ns_per_slot`/`slots_per_year` to confirm whether a genuine divergence window exists.

### Recommendation
Audit all consumers of `SlotParamsArchive`/`SlotParams` (`slots_per_year`, `ns_per_slot`) to guarantee a single, monotonically-applied timeline is used for both PoH/consensus timing and reward-rate math — i.e., ensure `calculate_epoch_inflation_rewards`'s divisor is derived from the exact same effective-slot boundaries that govern actual slot production for that epoch, with no independent staging delay between the two. Add an invariant test asserting `slot_range_duration_in_years` integrated across an epoch always matches `epoch_duration_in_years` computed from `slots_per_year_for_epoch` for every possible feature-activation ordering in `slot_time_feature_gates()`.

### Proof of Concept
Could not construct a concrete triggering sequence within the available tool budget; the finding is a structural analog (stale/mismatched per-year time constant driving a reward formula) rather than a confirmed exploit. Recommend a Devin/engineering follow-up to write a bank-simulation test that activates `reduce_slot_time_to_350ms` mid-epoch and asserts `calculate_epoch_inflation_rewards` output against slot-by-slot integrated duration from `slot_range_duration_nanos` [9](#0-8)  to confirm whether a real divergence (and thus incorrect minting) occurs.

impl SlotParamsArchive {
    /// Rebuilds slot-parameter transitions from the active feature set.
    pub(crate) fn new(
        feature_set: &FeatureSet,
        epoch_schedule: &EpochSchedule,
        baseline_params: SlotParams,
    ) -> Self {
        let mut param_transitions = BTreeMap::from([(0, baseline_params)]);
        let mut earliest_same_or_shorter_slot = Slot::MAX;

        // The feature table is ordered longest-to-shortest. Walk it in reverse
        // so once a same-or-shorter target is effective at slot S, any longer
        // target effective at S or later is known to be redundant.
        for (feature_id, params) in slot_time_feature_gates().into_iter().rev() {
            if params.ns_per_slot > baseline_params.ns_per_slot {
                continue;
            }
            let Some(activation_slot) = feature_set.activated_slot(&feature_id) else {
                continue;
            };
            let effective_slot = Self::feature_effective_slot(epoch_schedule, activation_slot);
            if effective_slot < earliest_same_or_shorter_slot {
                param_transitions.insert(effective_slot, params);
                earliest_same_or_shorter_slot = effective_slot;
            }
        }

        Self { param_transitions }
    }

    /// Returns the exact wall-clock duration in nanoseconds for
    /// `start_slot..=end_slot`.
    pub(crate) fn slot_range_duration_nanos(&self, start_slot: Slot, end_slot: Slot) -> u128 {
        if start_slot > end_slot {
            return 0;
        }

        let mut cursor = start_slot;
        let mut params = self.params_at_slot(start_slot);
        let mut duration = 0u128;

        for (&effective_slot, &effective_params) in self
            .param_transitions
            .range((Excluded(start_slot), Included(end_slot)))
        {
            duration = duration.saturating_add(
                u128::from(effective_slot.saturating_sub(cursor))
                    .saturating_mul(params.ns_per_slot()),
            );
            cursor = effective_slot;
            params = effective_params;
        }

        let remaining_slots = u128::from(end_slot.saturating_sub(cursor)) + 1;
        duration.saturating_add(remaining_slots.saturating_mul(params.ns_per_slot()))
    }

    /// For a given `capitalization` (total_supply in lamports) and `epoch`, returns the
    /// `epoch inflation rewards` in lamports.
    pub(crate) fn calculate_epoch_inflation_rewards(
        &self,
        capitalization: u64,
        epoch: Epoch,
    ) -> u64 {
        let slot_in_year = self.slot_in_year_for_inflation();
        let validator_rate = self.inflation.read().unwrap().validator(slot_in_year);
        let epoch_duration_in_years = self.epoch_duration_in_years(epoch);
        (validator_rate * capitalization as f64 * epoch_duration_in_years) as u64
    }
