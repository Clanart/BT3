### Title
FROST cached preprocess reused across signing attempts enables secret share recovery via nonce reuse - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in the external report is "untrusted input steers execution onto a dangerous path" (injection into a signing/config context). In Serai's in-scope code, the analogous shape is FROST nonce handling: an unprivileged co-signer controls which preprocesses are fed to `read_preprocess`/`sign`, and the signer derives its nonce deterministically from a cached seed. `SigningProtocol::preprocess_internal` generates a `CachedPreprocess` once per `context` and, on every subsequent invocation, regenerates the *identical* preprocess (identical nonces `d`, `e`) via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)`. It never rotates or deletes the cached seed.

### Finding Description
In `crypto/frost/src/sign.rs:121-144` and `crypto/frost/src/sign.rs:386-396`, the effective nonce is `d + e * rho_l` where `rho_l` is the per-participant binding factor computed in `crypto/frost/src/nonce.rs:161-173` from the `rho_transcript` (`crypto/frost/src/sign.rs:362-379`). `rho` binds the group key, `hash_msg(msg)`, and the challenge over the transcripted preprocesses — all of which are attacker-influenceable because an untrusted participant chooses which preprocess bytes it submits via `read_preprocess` (`crypto/frost/src/sign.rs:276-281`, `Commitments::read` at `crypto/frost/src/nonce.rs:133-139`).

`coordinator/src/tributary/signing_protocol.rs:123-147` caches the 32-byte seed under `CachedPreprocesses` keyed only by `self.context` and reuses it whenever `sign` is reached. If `share_internal` (`signing_protocol.rs:150-181`) is invoked more than once under the same context with a *different* set of preprocesses or a different message (e.g., a retry after a failed share, or a malicious peer submitting different preprocess bytes across attempts of the same plan), the victim signs twice with the same `(d, e)` but different `rho`:

```
share_1 = ... + (d + e*rho_1) * ...
share_2 = ... + (d + e*rho_2) * ...
```

From two shares, the adversary solves for `e = (share_1 - share_2)/(rho_1 - rho_2)`-adjusted linear system and recovers the victim's secret share (`sign_share` is affine in the nonce and the secret share; with the nonce known, the secret share term is directly extractable). The comments at `crypto/frost/src/sign.rs:83-92` and `spec/cryptography/FROST.md:51-60` explicitly acknowledge that preprocess reuse enables private key share recovery — yet the production caller reuses the cached preprocess unconditionally whenever the context key repeats.

### Impact Explanation
Two signature shares produced with the same nonce under different binding factors yield a linear equation system that recovers `d`, `e`, and hence the signer's FROST secret share (`ThresholdKeys.secret_share`). Combined with `t-1` colluding-free knowledge of the verification shares, a single recovered share meaningfully reduces the threshold security; recovered shares can also be used to blame-frame the victim or, with enough shares, forge signatures for the group key controlling Bitcoin/Monero multisig funds. This is the canonical FROST nonce-reuse share-recovery attack reachable entirely through attacker-controlled preprocess bytes.

### Likelihood Explanation
The trigger requires `share_internal` (or another caller reaching `sign`) to execute twice under the same `context` with differing preprocess sets — for example, when a signing attempt fails validation (`FrostError::InvalidShare`/`InvalidPreprocess` at `signing_protocol.rs:170-178`) and the coordinator retries, or when an adversary deliberately submits a preprocess that parses but causes an abort so the protocol re-runs with a new participant set. An unprivileged validator participating in the tributary signing protocol controls their submitted preprocess bytes and the message's binding transcript, so they can force divergent `rho` values while the victim's nonce stays fixed. Whether the coordinator ever retries under an identical `context` encoding is the one residual uncertainty — if `context` is incremented per attempt, the cache key changes and the vulnerability does not trigger; the code does not itself guarantee this.

### Recommendation
Invalidate the cached seed the moment a share is produced for a given context: after `from_cache` is used in `sign`, call `CachedPreprocesses::del`/overwrite so any second `sign` under the same context either generates a fresh seed or errors. Alternatively, key the cache by a monotonically increasing attempt index (context + attempt nonce) and refuse to sign twice for the same `(context, seed)` pair. At the library level, `AlgorithmSignMachine` should be consumable-once (it is), and the caller must guarantee `from_cache` is never invoked twice with the same `CachedPreprocess` for semantically different signing sessions.

### Proof of Concept
1. Adversary participates in a tributary signing session for `context` C with preprocess set P1 and message m. Victim produces `share_1` using nonce `d + e*rho_1`.
2. The attempt aborts (adversary sends a bad share or a malformed-but-parseable preprocess to trigger `InvalidShare`/`InvalidPreprocess`).
3. A second attempt under the same `context` C runs with a different participant set or different adversarial preprocess P2 → `rho_2 ≠ rho_1`. `CachedPreprocesses::get` returns the same seed; `seeded_preprocess` regenerates the same `d, e`. Victim produces `share_2`.
4. Adversary solves `share_1 - share_2` for `e` (Lagrange coefficients and `rho` values are all public/derivable), recovers `d`, then solves either share equation for the victim's `secret_share` since `sign_share = f(nonce, lambda_i * secret_share)` is affine.
5. Verify: recovered share satisfies `verification_shares[i] == G * secret_share` (offset/interpolation handled via `ThresholdView`).

Key code: `coordinator/src/tributary/signing_protocol.rs:123-147` (unconditional cache reuse), `crypto/frost/src/sign.rs:127-144` (deterministic `ChaCha20Rng::from_seed` preprocess), `crypto/frost/src/sign.rs:386-396` (nonce `base + rho * actual`), `crypto/frost/src/nonce.rs:161-191` (attacker-influenced `rho`).
