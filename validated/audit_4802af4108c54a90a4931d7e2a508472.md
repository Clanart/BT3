### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable, locking funds in unbuildable/unrelayable transactions - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the reported "deducted-but-locked fee," `Scanner::scan_block` reports outputs received that cannot actually be spent. It iterates over *every* transaction in a block, including `block.txdata[0]` — the coinbase transaction. Coinbase outputs are encumbered by the Bitcoin consensus maturity rule (COINBASE_MATURITY = 100 blocks), so a `ReceivedOutput` produced this way is fed into `SignableTransaction::new`/`TransactionMachine::sign` as if it were a normal UTXO, but any transaction spending it is consensus-invalid and can never confirm. The value is effectively locked inside the wallet's accounting with no mechanism to distinguish it.

### Finding Description
`scan_block` calls `scan_transaction` on all transactions without excluding the coinbase:

```rust
// networks/bitcoin/src/wallet/mod.rs
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {   // includes block.txdata[0], the coinbase
    res.extend(self.scan_transaction(tx));
  }
  res
}
``` [1](#0-0) 

`scan_transaction` matches solely on `script_pubkey` and returns a `ReceivedOutput` carrying the txid/vout, with no maturity or input-type check: [2](#0-1) 

That `ReceivedOutput` then flows into `SignableTransaction::new`, which sums `input.output.value` into `input_sat` and constructs a `TxIn` spending the immature outpoint, and into `TransactionSignMachine::sign`, which produces a valid FROST/BIP-340 signature over the sighash for it: [3](#0-2) [4](#0-3) 

The result is a fully signed transaction the network will reject with `bad-txns-premature-spend-of-coinbase`. The only mitigation is a code comment telling integrators to post-filter — there is no enforcement in the API itself.

### Impact Explanation
Funds reported as received are not spendable. Any coin-selection or accounting layer built on `scan_block` treats immature coinbase value as available balance; transactions constructed to spend it produce valid signatures yet are permanently unbroadcastable until maturity, and the immature amount is silently burned into the "available" inputs (affecting `NotEnoughFunds` checks and change computation). In a threshold-wallet setting this wastes a full FROST signing ceremony and misreports treasury balances — the same "value accounted but not deliverable" shape as the fee stuck in `earlyEndGame`.

### Likelihood Explanation
Any miner (or mining pool paying the Serai wallet address in a coinbase output) can trigger it using only a public transaction; no validator collusion or leaked material is required. `scan_block` is the natural API for block-based scanning, and the failure is silent — the `ReceivedOutput` is indistinguishable from a mature one.

### Recommendation
Skip the coinbase transaction in `scan_block` (i.e., iterate `block.txdata[1 ..]` by default), or tag `ReceivedOutput` with maturity information and have `SignableTransaction::new` reject immature outpoints. If scanning the coinbase must remain available, return a distinct type or an `Option`/error rather than silently emitting unspendable outputs.

### Proof of Concept
1. Register a P2TR script for the threshold key via `Scanner::new`/`register_offset`.
2. A miner constructs a block whose coinbase (`txdata[0]`) pays `value` to that `script_pubkey`.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for `(coinbase_txid, vout)` — indistinguishable from a spendable UTXO.
4. `SignableTransaction::new(vec![received], payments, change, None, fee_per_vbyte)` succeeds; `multisig`/`preprocess`/`sign`/`complete` produce a fully signed transaction.
5. Broadcasting it fails consensus validation (`coinbase` spent before 100 confirmations); the reported balance was never spendable.
