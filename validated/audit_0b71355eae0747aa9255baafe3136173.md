### Title
Nil-pointer dereference panic in `SetCodeTx.AsEthereumData()` from a `to`-less EIP-7702 transaction - (File: `x/evm/types/ethtx/set_code_tx.go`)

### Summary
`SetCodeTx.Validate()` only checks the `To` address format if `tx.To != ""`, allowing an empty `To` field to pass validation. `AsEthereumData()`, however, unconditionally dereferences the pointer returned by `GetTo()` via `To: *tx.GetTo()`. `GetTo()` returns `nil` when `tx.To == ""`, so this produces a Go nil-pointer dereference panic — the same bug class as ALPINE-CVE-2024-0727, where OpenSSL dereferenced a NULL field it should have rejected, causing an application crash on attacker-supplied data.

### Finding Description
`SetCodeTx` is the protobuf-backed representation of an EIP-7702 (type 0x04) EVM transaction used inside `MsgEVMTransaction.Data`. Its accessor and validation logic are defined in [1](#0-0) , which explicitly returns `nil` for `GetTo()` when `To == ""`. Its `Validate()` function only enforces address format when `To` is non-empty and never requires `To` to be set at all: [2](#0-1) .

`AsEthereumData()` builds the real go-ethereum `ethtypes.SetCodeTx` and dereferences the pointer directly: [3](#0-2) . If `To == ""`, `tx.GetTo()` returns `nil` and `*tx.GetTo()` panics with a nil-pointer dereference.

`MsgEVMTransaction` is a normal Cosmos SDK `Any`-wrapped message, and its `ValidateBasic()` calls `txData.Validate()` (skipping only `AssociateTx`) without ever calling `AsEthereumData()`: [4](#0-3) . This means a hand-crafted Cosmos transaction that packs a `SetCodeTx` payload with an empty `To` field passes `ValidateBasic()` cleanly, because the emptiness of `To` is never rejected there.

Downstream, multiple ante-handler and RPC code paths call `AsTransaction()`/`AsEthereumData()` on unpacked tx data, e.g. `msg.AsTransaction()` in `BasicDecorator.AnteHandle` (`x/evm/ante/basic.go:27`), `ethtypes.NewTx(txData.AsEthereumData())` in `EvmCheckTxAnte` (`app/ante/evm_checktx.go:52`) and in `PreprocessUnpacked` (`x/evm/ante/preprocess.go:208`), and `msg.AsTransaction()` in `evmrpc` handlers (`evmrpc/tx.go`, `evmrpc/simulate.go`, `evmrpc/block.go`). Any of these paths reaching a `SetCodeTx` with an empty `To` triggers the panic.

Unlike a normally RLP-decoded EIP-7702 transaction from `eth_sendRawTransaction` (where go-ethereum's decoder inherently requires a `to` field for `SetCodeTx`, since `NewSetCodeTx` only calls `SetTo` when `tx.To()` is non-nil, per `giga/deps/xevm/types/ethtx/set_code_tx.go:24`), an attacker is not limited to that path. A `MsgEVMTransaction` can also be submitted as a **plain Cosmos SDK transaction** — packing an arbitrary `ethtx.SetCodeTx` protobuf value directly into `Data` — bypassing the go-ethereum RLP invariant that guarantees `To` is present. This gives a single unprivileged transaction sender direct control over the `To` field's emptiness.

### Impact Explanation
A submitted transaction that reaches `AsEthereumData()`/`AsTransaction()` with `To == ""` panics. Depending on which code path is hit:
- If reached inside `CheckTx`/`DeliverTx` ante processing that is wrapped by a top-level `recover()` (as seen in `app/legacyabci/check_tx.go` and `deliver_tx.go`), the panic is caught and converted into a tx-level error — not a crash, but a denial-of-service against transaction validity semantics.
- If reached from a JSON-RPC handler code path or another goroutine without an enclosing recover (e.g., during `eth_call`/`eth_estimateGas`/tracing/simulation flows in `evmrpc/simulate.go`, `evmrpc/tx.go`, `evmrpc/block.go` that call `AsTransaction()`), an unrecovered panic can crash the serving goroutine, and if unhandled at the top of that goroutine, the entire node process, taking down the public EVM JSON-RPC surface — a Medium-severity availability impact analogous to the OpenSSL PKCS12 NULL-dereference DoS.

### Likelihood Explanation
The trigger requires only a syntactically valid Cosmos transaction wrapping `MsgEVMTransaction` with a `SetCodeTx` payload whose `To` field is left empty — no valid EOA signature recovery, balance, or special privilege is required to reach `ValidateBasic()`/early ante stages before the panic point. This is a straightforward, cheaply constructible input from any RPC/transaction submitter.

### Recommendation
Make `SetCodeTx.Validate()` explicitly require a non-empty, well-formed `To` address (per EIP-7702, `to` is mandatory for `SetCodeTx`), rejecting empty `To` before it can propagate to `AsEthereumData()`. Additionally, harden `AsEthereumData()` itself to avoid the raw pointer dereference (e.g., check `GetTo() == nil` and return an error/sentinel rather than panicking) as defense-in-depth for any other caller that might construct a `SetCodeTx` without going through `Validate()`.

### Proof of Concept
1. Construct an `ethtx.SetCodeTx` protobuf message directly with `To: ""` (skipping the go-ethereum-derived `NewSetCodeTx` constructor), valid `GasTipCap`/`GasFeeCap`/`ChainID`/`V`/`R`/`S` fields, and a well-formed `AuthList`/`Accesses` so it passes `Validate()`.
2. Pack it into `MsgEVMTransaction.Data` as an `Any`.
3. Wrap the message into a standard Cosmos `TxBody`/`TxRaw` and sign/broadcast it via the node's RPC (`broadcast_tx_sync`/`CheckTx`).
4. When ante processing (or an RPC path such as simulate/trace) calls `msg.AsTransaction()` → `SetCodeTx.AsEthereumData()`, the line `To: *tx.GetTo()` panics because `GetTo()` returns `nil` for an empty `To`.

Note: I could not fully verify from static inspection alone whether any specific `evmrpc` code path invoking `AsTransaction()` lacks an enclosing `recover()` (this would need runtime/dynamic tracing or a live repro to confirm an actual node crash versus a caught tx-error); the ante-pipeline paths I found are protected by top-level recovers, so the strongest confirmed impact is validation-bypass-driven panic recovery/DoS-at-tx-level, with process-level crash being a plausible but unconfirmed escalation via un-recovered RPC/tracing goroutines.
