### Title
Stale Decimal-Precondition Check Lets Mutable Asset Decimals Inflate Cross-Chain Mint Amounts - (File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/impls.rs, modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The external report's core broken invariant is: a fixed-point/decimal-scaling calculation trusts a decimals value without re-validating it at the time of use, so a value that changes between "checked" and "used" corrupts the money math. `hyper-fungible-token` reproduces this exact pattern: `register_token`/`update_token` validate `config.decimals >= local_decimals` only once, at registration time, using a snapshot of `local_decimals` read from `fungibles::metadata::Inspect::decimals()`. The actual cross-chain amount conversion in `send()`, `on_accept`, and `on_timeout` re-reads `decimals()` live and feeds it into `convert_to_erc20`/`convert_to_balance`, which use `saturating_sub` instead of a checked/validated exponent. If the underlying asset's decimals value is ever raised after registration, the registration-time invariant (`erc_decimals >= local_decimals`) silently breaks, `saturating_sub` clamps to 0, and `convert_to_erc20` stops scaling up the amount — producing an amount encoded in the outgoing ISMP message that is orders of magnitude larger than what was actually escrowed/burned locally.

### Finding Description
- `register_token` and `update_token` enforce the precondition `config.decimals >= local_decimals` only once, using a live read of `local_decimals`: [1](#0-0) 
- The precondition is never re-checked afterward. The pallet's `Precisions` storage caches only the destination `erc_decimals`, not the local asset's decimals at registration time: [2](#0-1) 
- At actual transfer time, `send()` re-fetches the *current* decimals of the asset live via `fungibles::metadata::Inspect` and feeds it straight into the conversion helper: [3](#0-2) 
- `convert_to_erc20` computes the scaling exponent with `saturating_sub`, which silently becomes `0` (no scale-up) instead of erroring or scaling correctly when `erc_decimals < local_decimals`: [4](#0-3) 
- The same live re-read and `saturating_sub` pattern is used on the receive/timeout side (`convert_to_balance`) in `on_accept`/`on_timeout`: [5](#0-4) [6](#0-5) 

The `Assets` type is a generic `fungibles::Mutate + fungibles::metadata::Inspect` (e.g. `pallet-assets`), whose `decimals()` value is standard on-chain asset *metadata*, mutable after asset creation (via `pallet_assets::set_metadata`, callable by the asset's `Owner`). Nothing in this pallet pins or re-validates that value once `register_token` has run. This is the identical bug class to the LP Oracle report: an untrusted, mutable decimals source is trusted for fixed-point math with only a one-time precondition check, and a value swap after the check invalidates the invariant the downstream arithmetic depends on.

### Impact Explanation
If `local_decimals` for a registered, non-native asset increases after registration/last `update_token` call to a value `>= erc_decimals` (the registered EVM precision), then on the next `send()`:
- `convert_to_erc20(amount, erc_decimals, new_local_decimals)` computes `erc_decimals.saturating_sub(new_local_decimals) == 0`, so the multiplier collapses to `10^0 = 1` instead of the (now negative, unrepresentable) correct scale-down.
- The full, un-scaled local-precision `amount` (e.g. 18-decimal units) is placed directly into the `Message.amount` field dispatched to the destination EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which expects amounts scaled to the registered `erc_decimals` (e.g. 6).
- The destination contract mints/unlocks an amount up to `10^(new_local_decimals - erc_decimals)` times larger than what was actually locked/burned on the source chain — direct fund creation/inflation from a single ordinary `send()` call, satisfying the bounty's "stealing or loss of funds" / "transaction manipulation" criteria.

This is a public-entrypoint (`send()`), single-transaction path requiring no malicious relayer, prover, or governance actor — only that the pre-checked invariant (`erc_decimals >= local_decimals`) no longer holds at execution time.

### Likelihood Explanation
Likelihood depends on whether the runtime's `pallet-assets` configuration allows the asset `Owner`/`Issuer` (a role that may be held by a non-privileged, non-bridge-governance account for permissionlessly-created assets) to call `set_metadata` and change `decimals` after the asset has been registered by `hyper-fungible-token`'s `T::CreateOrigin`. Because `register_token`/`update_token` never re-derive or cache the local decimals validated at check time (they trust a live, externally-mutable value both at check time and at use time, but never re-verify the invariant between those two reads), any runtime wiring where asset decimals metadata is not immutable/frozen makes this directly triggerable. I could not fully confirm from the indexed code whether this specific parachain's `pallet-assets` instance locks metadata after `register_token`, so exploitability hinges on that external configuration — flagging this as the main uncertainty.

### Recommendation
- Cache the local asset's decimals in `Precisions` (or a companion storage item) at `register_token`/`update_token` time, and use that cached value in `send()`, `on_accept`, and `on_timeout` instead of re-reading `fungibles::metadata::Inspect::decimals()` live.
- Alternatively, re-validate `erc_decimals >= current_local_decimals` inside `send()`/`on_accept`/`on_timeout` before every conversion and reject the dispatch/message if the invariant no longer holds.
- Replace `saturating_sub` in `convert_to_erc20`/`convert_to_balance` with a checked subtraction that errors (rather than silently clamping to `0`) when `erc_decimals < local_decimals`, so a broken precondition fails closed instead of open.
- If feasible, freeze asset metadata (decimals) for any asset once registered with `hyper-fungible-token`, so the bridge's precision invariant cannot be invalidated by the underlying asset pallet's owner-level calls.

### Proof of Concept
1. Governance registers asset `X` (a `pallet-assets` asset, currently `decimals() == 6`) via `register_token` for destination chain `C` with `config.decimals = 6`. Check passes (`6 >= 6`).
2. The asset's `Owner` (not bridge governance) later calls `pallet_assets::set_metadata` to change `X`'s decimals to `18` (a self-service metadata call standard in `pallet-assets`, generally permitted to the asset owner without governance).
3. An ordinary user calls `hyper-fungible-token::send()` with `asset_id = X`, `amount = 1_000_000` (i.e., "1 X" at the new 18-decimal metadata, extremely small raw value under the new denomination) or any chosen amount:
   - `decimals = Assets::decimals(X) = 18` (live read).
   - `erc_decimals = Precisions::get(X, C) = 6` (stale, from step 1).
   - `convert_to_erc20(amount, 6, 18)` → multiplier `= 10^(6saturating_sub(18)) = 10^0 = 1` → `erc20_amount = amount` (unscaled).
4. The dispatched `Message.amount` is `amount` interpreted by the destination `HyperFungibleToken` EVM contract as a 6-decimal quantity — `10^12` times larger than the correctly-scaled equivalent would have been, causing the EVM contract to mint/unlock a vastly inflated token amount relative to what was escrowed/burned on the source chain in step 3.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
