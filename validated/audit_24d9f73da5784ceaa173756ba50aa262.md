### Title
`CostModel::calculate_allocated_accounts_data_size` undercounts BPF CPI-driven account growth, allowing `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` block cap to be bypassed - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects top-level `SystemInstruction` variants (`CreateAccount`, `Allocate`, `AllocateWithSeed`, `CreateAccountWithSeed`, `CreateAccountAllowPrefund`) to estimate how much new account data a transaction allocates. Account growth performed by a BPF program via CPI-into-System-with-zero-space followed by direct realloc (`AccountInfo::realloc` / `sol_realloc`, handled by `extend_from_slice`/`update_accounts_resize_delta` in `transaction-context`) is never inspected by this static scan, so `TransactionCost.allocated_accounts_data_size` reports less growth than what actually happens.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` (`cost-model/src/cost_model.rs:265-301`) iterates only the transaction's top-level instructions and, for each instruction whose `program_id` equals `system_program::id()`, deserializes it as a `SystemInstruction` to look for space allocation (`calculate_account_data_size_on_instruction` / `calculate_account_data_size_on_deserialized_system_instruction`, lines 203-261). Any instruction that targets a user BPF program is unconditionally treated as `SystemProgramAccountAllocation::None` (line 258-260) — CPI calls made *inside* that program's execution are invisible to this function because it never inspects the invoke stack, only the transaction's compiled top-level instructions.

This value feeds `TransactionCost::allocated_accounts_data_size`, which is the sole quantity used by `CostTracker::would_fit`/`add_transaction_cost` (`cost-model/src/cost_tracker.rs:288-293,313-314`) to enforce `CostTrackerLimits::allocated_data_size` (defaulted to `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, `cost-model/src/cost_tracker.rs:87-95`). Critically, this same field is recomputed identically post-execution via `CostModel::calculate_cost_for_executed_transaction` (`cost-model/src/cost_model.rs:56-77`), which is invoked from `get_transaction_costs`/`check_block_cost_limits` in `runtime/src/transaction_execution.rs:157-195` to re-validate the *actual* committed block against the same limit. Both the pre-execution and post-execution paths call the exact same static `calculate_allocated_accounts_data_size(instructions, feature_set)` — neither ever consults the real resize delta that the transaction produced (`TransactionContext`'s `accounts_resize_delta()`/`accounts_deltas.accounts_resize_delta`, which *is* correctly tracked for the separate, ledger-wide `bank.accounts_data_size_delta_on_chain` accounting in `runtime/src/bank.rs:4419-4430`).

Exploit flow: an attacker deploys an arbitrary BPF program that, when invoked, issues a CPI `SystemInstruction::CreateAccount`/`Allocate` with `space = 0` (or omits system involvement for existing owned accounts) and then grows the account directly via `AccountInfo::realloc` (`sol_realloc` syscall), which is implemented through the loader's direct memory-mapping resize handler (`transaction-context/src/transaction.rs:525-624`) and `InstructionAccount::extend_from_slice`/`update_accounts_resize_delta` (`transaction-context/src/instruction_accounts.rs:209-226`, `transaction-context/src/transaction_accounts.rs:297-326`). This growth is bounded per-transaction by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (via `can_data_be_resized`), so a single transaction can realistically grow account data by that per-tx maximum while `calculate_allocated_accounts_data_size` reports `0` for it (no top-level `SystemInstruction::Allocate`/`CreateAccount` with nonzero `space` is present).

### Impact Explanation
The bank's global, ledger-wide accounts-data-size accounting (`accounts_data_size_delta_on_chain`, enforced against `MAX_ACCOUNTS_DATA_LEN`) is computed independently from real execution deltas and is **not** affected by this bug — that hard cap still holds. The concrete, scoped impact is limited to the `CostTracker`'s block-level pacing control, `WouldExceedAccountDataBlockLimit` (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`), which is meant to rate-limit how much real account-data growth a single block can absorb. Because `allocated_accounts_data_size` is derived purely from static System Program instruction inspection, an attacker who grows accounts exclusively through BPF-driven realloc/CPI can pack many such transactions into one block while the tracker believes zero (or near-zero) allocation budget is being consumed, so `would_fit`'s `WouldExceedAccountDataBlockLimit` check never fires for this traffic. This is a real gap in the "cost-charging completeness" invariant for the block-level data-growth cap — it corresponds to Agave's "materially underpriced compute/resource accounting" bounty category, scoped strictly to the block-level pacing limit, not to the ledger-wide hard cap or to consensus safety (since every validator computes the same, uniformly wrong, value, this does not cause non-determinism between validators).

### Likelihood Explanation
Fully feasible by an unprivileged attacker: deploying arbitrary BPF bytecode and invoking it with a CPI to System Program (0 space) followed by `AccountInfo::realloc`/`sol_realloc` growth is standard, well-supported program behavior (see existing tests exercising CPI-then-local-realloc patterns, e.g. `programs/sbf/tests/programs.rs:3474-3523`). No validator/operator control, no memory corruption, and no bypass of ELF/verifier/compute-meter checks is required — it purely exploits an accounting gap in `cost_model.rs`. Repeatable per-transaction, bounded only by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` per transaction and by however many such transactions the attacker can fit/pay for in a block.

### Recommendation
Make the block-level allocation accounting use the actual resize delta observed during/after execution (the same value already computed for `accounts_data_size_delta_on_chain`) rather than (or in addition to) the static System Program instruction scan, for both the pre-execution estimate used in scheduling and, more importantly, the post-execution `check_block_cost_limits` re-validation in `runtime/src/transaction_execution.rs`. Concretely, thread the transaction's real `accounts_resize_delta`/`accounts_uninitialized_size` (already computed in `runtime/src/bank.rs:4419-4430`) into `CostModel::calculate_cost_for_executed_transaction`'s `allocated_accounts_data_size`, so `CostTracker::would_fit`'s `WouldExceedAccountDataBlockLimit` check is evaluated against real growth, closing the gap for CPI-driven reallocation.

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

    // Returns the highest account cost for all write-lock accounts `TransactionCost` updated
    fn add_transaction_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>) -> u64 {
        self.allocated_accounts_data_size += tx_cost.allocated_accounts_data_size();
        self.transaction_count += 1;
        self.transaction_signature_count += tx_cost.num_transaction_signatures();
        self.secp256k1_instruction_signature_count +=
            tx_cost.num_secp256k1_instruction_signatures();
        self.ed25519_instruction_signature_count += tx_cost.num_ed25519_instruction_signatures();
        self.secp256r1_instruction_signature_count +=
            tx_cost.num_secp256r1_instruction_signatures();
        self.add_transaction_execution_cost(tx_cost, tx_cost.sum())
    }

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(

) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)

                ))
            } else {
                None
            }
        })
        .collect()

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
