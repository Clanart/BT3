### Title
Gas-refund double-counting via duplicate EIP-7702 authority tuples in `applyAuthorization` - (File: blockchain/state_transition.go)

### Summary
`StateTransition.TransitionDb` iterates over every entry of a `TxTypeEthereumSetCode` transaction's `AuthList()` and calls `applyAuthorization` for each tuple without deduplicating by authority address [1](#0-0) . `applyAuthorization` grants a gas refund whenever the target authority account already exists in state, intended to offset the "new account" gas that was pre-charged for that tuple at intrinsic-gas time [2](#0-1) . Because the "already exists" check (`st.state.Exist(authority)`) is evaluated independently per tuple and the loop never tracks which authorities have already been refunded, repeating the same authority address multiple times in a single authorization list causes the refund to be granted once per repetition instead of once per unique address.

### Finding Description
Intrinsic gas for a `SetCodeTx` charges `params.CallNewAccountGas` per authorization-list *entry* (not per unique address), via `IntrinsicGas` [3](#0-2) . During execution, `TransitionDb` walks `msg.AuthList()` and calls `st.applyAuthorization(&auth, rules)` for every entry, ignoring errors [1](#0-0) .

Inside `applyAuthorization`, if the target authority already exists as a legacy-key account, the code adds a refund of `params.CallNewAccountGas - params.TxAuthTupleGas` via `st.state.AddRefund(...)`: [2](#0-1) 

There is no bookkeeping (e.g. a "seen authorities" set) to ensure this refund is only granted once per unique authority. If an attacker crafts a `SetCodeTx` whose `AuthorizationList` repeats the *same* already-existing, legacy-keyed authority address N times (each a validly-signed authorization tuple for that address, e.g. re-using the same nonce/signature or, since nonce increments after the first application, providing N correctly incrementing nonces), each of the N applications independently re-evaluates `st.state.Exist(authority)` (still true after the first iteration) and calls `AddRefund` again, so the refund is credited N times instead of once.

This is a direct refund/state-accounting double-counting bug: the same "already exists" condition is processed and credited multiple times for what should be a single logical event, analogous to the double-processing (double-free) root cause pattern in the reference CVE, except here it manifests as a double gas-refund credit rather than a memory-safety crash.

### Impact Explanation
The inflated refund is added to `s.refund` in the `StateDB` [4](#0-3)  and later consumed in `calcRefund`, which caps the refund at `gasUsed / RefundQuotientEIP3529` (post-Kore, i.e. `gasUsed / 5`) [5](#0-4) . Because the cap is a function of `gasUsed`, and a `SetCodeTx` with many authorization tuples burns more intrinsic gas (raising `gasUsed`), an attacker can size the number of duplicate tuples to both inflate the raw refund pool and raise the cap ceiling, extracting a larger-than-intended refund of `st.gas` that is subsequently returned to the fee payer in `returnGas` (crediting `validatedFeePayer`/`validatedSender`) [6](#0-5) . This is a fee-accounting/value-movement bug reachable purely from a submitted transaction: the sender or fee-delegation payer receives more gas refund than the protocol design intends, effectively underpaying the true cost of the transaction and altering fee/burn distribution between coinbase/rewardbase and the payer.

### Likelihood Explanation
Any unprivileged transaction sender can submit an `EthereumSetCode` (`TxTypeEthereumSetCode`) transaction with a crafted `AuthorizationList` containing multiple valid tuples for the same already-existing legacy-key authority address — this requires only ordinary EIP-7702 authorization signing capability, no privileged role, no node compromise, and no second party. The `TxPool` only validates that the authorization list is non-empty and does full per-tuple signature/replay checks elsewhere, but does not reject duplicate authority addresses in a single list [7](#0-6) .

### Recommendation
Track authorities already processed within a single `AuthList()` iteration (e.g., a `map[common.Address]bool`) and only apply the "existing account" refund the first time a given authority is seen in the list, mirroring the deduplication already implemented for `SetCodeAuthorities()` [8](#0-7) . Alternatively, reject `SetCodeTx`s whose `AuthorizationList` contains duplicate authority addresses at validation time in `tx_pool.go`.

### Proof of Concept
1. Create account `A` with a legacy account key and existing balance (so `state.Exist(A)` is true).
2. Craft a `TxTypeEthereumSetCode` transaction from any sender whose `AuthorizationList` contains N `SetCodeAuthorization` tuples all authorizing address `A` to delegate to some contract, each signed with `A`'s correctly incrementing nonce (nonce increments by 1 after each successful `applyAuthorization` call since it calls `st.state.IncNonce(authority)`).
3. Submit the transaction; during `TransitionDb`, the loop over `msg.AuthList()` calls `applyAuthorization` N times; each call sees `st.state.Exist(A) == true` and each credits `AddRefund(CallNewAccountGas - TxAuthTupleGas)`, resulting in `N * (CallNewAccountGas - TxAuthTupleGas)` total refund instead of the intended single credit.
4. Observe the resulting `ExecutionResult.UsedGas` / receipt gas-used is lower than the honestly-expected value, and the sender/fee-payer balance reflects the extra refunded gas.

```go
func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}
```

```go
// calcRefund computes refund counter, capped to a refund quotient.
func (st *StateTransition) calcRefund() uint64 {
	var gasRefund uint64
	if !st.evm.ChainConfig().Rules(st.evm.Context.BlockNumber).IsKore {
		// Before EIP-3529: refunds were capped to gasUsed / 2
		gasRefund = st.gasUsed() / params.RefundQuotient
	} else {
		// After EIP-3529: refunds are capped to gasUsed / 5
		gasRefund = st.gasUsed() / params.RefundQuotientEIP3529
	}
	if gasRefund > st.state.GetRefund() {
		gasRefund = st.state.GetRefund()
	}
	return gasRefund
}
```

```go
// returnGas returns KAIA for remaining gas, exchanged at the original rate.
func (st *StateTransition) returnGas() {
	remaining := new(big.Int).Mul(new(big.Int).SetUint64(st.gas), st.gasPrice)

	validatedFeePayer := st.msg.ValidatedFeePayer()
	validatedSender := st.msg.ValidatedSender()
	feeRatio, isRatioTx := st.msg.FeeRatio()
	if isRatioTx {
		feePayer, feeSender := types.CalcFeeWithRatio(feeRatio, remaining)

		st.state.AddBalance(validatedFeePayer, feePayer)
		st.state.AddBalance(validatedSender, feeSender)
	} else {
		// To make a short circuit, the below routine processes when feeRatio == 100.
		st.state.AddBalance(validatedFeePayer, remaining)
	}
}
```

```go
// SetCodeAuthorities returns a list of unique authorities from the
// authorization list.
func (tx *Transaction) SetCodeAuthorities() []common.Address {
	if tx.Type() != TxTypeEthereumSetCode {
		return nil
	}
	var (
		marks = make(map[common.Address]bool)
		auths = make([]common.Address, 0, len(tx.AuthList()))
	)
	for _, auth := range tx.AuthList() {
		if addr, err := auth.Authority(); err == nil {
			if marks[addr] {
				continue
			}
			marks[addr] = true
			auths = append(auths, addr)
		}
	}
	return auths
}
```
