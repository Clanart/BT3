### Title
`internal_withdraw` bypasses the aggregator EIP-712 authorization check enforced on `withdraw` - (File: `core/src/rpc/operator.rs`)

### Summary
The analog report is about a Permit2/EIP-712 witness type that fails to bind all the fields/parties it is supposed to authorize, letting a caller obtain a valid `permitWitnessTransferFrom` for something other than what was actually signed. In Clementine, the equivalent authorization primitive is the EIP-712 `OperatorWithdrawalMessage`/`OptimisticPayoutMessage` signature checked by `recover_address_from_ecdsa_signature`, which is meant to prove that "citrea/aggregator" authorized a specific payout before an operator fronts funds. The `ClementineOperator::withdraw` RPC enforces this check, but the parallel `ClementineOperator::internal_withdraw` RPC calls the exact same fund-fronting logic (`self.operator.withdraw(...)`) with no such check at all.

### Finding Description
`withdraw()` in [1](#0-0)  requires a `verification_signature` recovered via `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` to match `self.operator.config.aggregator_verification_address` before it will call `self.operator.withdraw(...)`, which produces the signed payout transaction that fronts the withdrawal (the operator's reimbursable action). This mirrors the intent of `PERMIT2_ORDER_TYPE`/witness binding in the external report: the signature is supposed to bind the caller's request to the party (aggregator) authorized to trigger a payout.

However, `internal_withdraw()` at [2](#0-1)  takes an unauthenticated `WithdrawParams` request and calls `self.operator.withdraw(...)` directly — the same state-changing/fund-committing call — without ever invoking `recover_address_from_ecdsa_signature` or checking `aggregator_verification_address`. Both RPC handlers are part of the same `ClementineOperator` gRPC service defined in `clementine.proto` [3](#0-2) , so both are reachable through the same network-facing interface.

The verification signature scheme exists specifically to prevent unauthorized parties from getting an operator to sign a payout transaction; `internal_withdraw` opens exactly the code path the check was designed to gate, with the caller supplying only Bitcoin-side data (an `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) and none of the aggregator authorization.

### Impact Explanation
If `internal_withdraw` is reachable by an unauthenticated network caller (I could not verify whether some other layer, e.g. mTLS/config-level ACL, gates access to it, since no such gating appears in the reviewed handler code), an attacker could invoke the operator's payout/fronting logic for a withdrawal UTXO of their choosing without ever obtaining the aggregator's EIP-712 verification signature, directly reaching a signing/state-changing method meant only for the aggregator-authorized path. This corresponds to the "unauthenticated state-changing or broadcasting call" High-impact category, and — depending on what `self.operator.withdraw` does internally with the resulting signed transaction — could result in the operator fronting a payout that was never actually authorized/validated by the aggregator, i.e., "an operator reimbursed for a payout it never funded" pattern from the Critical category if such a transaction is later broadcast and reimbursement is later claimed by the operator against a citrea deposit.

### Likelihood Explanation
The likelihood depends entirely on whether `internal_withdraw` is exposed on the same unauthenticated network surface as the other operator RPCs, or is restricted to local/administrative use (its name and appearance only in `core/src/bin/cli.rs` suggest it may be intended as an internal/CLI-only utility). I was unable to confirm within the available tool budget whether the gRPC server applies any additional access control (mTLS, allow-list) uniformly across `ClementineOperator` methods that would exclude `internal_withdraw` from being callable by an arbitrary unprivileged caller. If no such differentiated gating exists and the method is exposed like `withdraw`, likelihood is high, since it requires no cryptographic material beyond data already visible on-chain/off-chain for a target withdrawal.

### Recommendation
Apply the same `aggregator_verification_address` / `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` check to `internal_withdraw` as is applied in `withdraw`, or remove/restrict `internal_withdraw` from the network-exposed `ClementineOperator` service (e.g., gate it behind a local-only interface) so it cannot be invoked without the aggregator's authorization signature.

### Proof of Concept
1. An attacker (or any caller with network access to an operator's gRPC endpoint) crafts a `WithdrawParams` message referencing a real withdrawal UTXO, `input_signature`, `output_script_pubkey`, and `output_amount`.
2. The attacker calls `ClementineOperator.internal_withdraw` directly (as defined in [2](#0-1) ), skipping the `WithdrawParamsWithSig.verification_signature` field required by `withdraw`.
3. `self.operator.withdraw(...)` executes and returns a signed payout transaction exactly as it would for a properly-authorized `withdraw` call, with no aggregator EIP-712 signature ever checked — the state-changing/signing path meant only for aggregator-authorized requests is reached by an unauthorized caller.

    async fn withdraw(
        &self,
        request: Request<WithdrawParamsWithSig>,
    ) -> Result<Response<RawSignedTx>, Status> {
        tracing::info!("Withdraw rpc called");
        let params = request.into_inner();
        let withdraw_params = params.withdrawal.ok_or(Status::invalid_argument(
            "Withdrawal params not found for withdrawal",
        ))?;
        let (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) =
            parser::operator::parse_withdrawal_sig_params(withdraw_params)?;

        tracing::warn!(
            "Parsed withdraw rpc params, withdrawal id: {:?}, input signature: {:?}, input outpoint: {:?}, output script pubkey: {:?}, output amount: {:?}, verification signature: {:?}", withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount, params.verification_signature
        );

        // if verification address is set in config, check if verification signature is valid
        if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
            let verification_signature = params
                .verification_signature
                .map(|sig| {
                    PrimitiveSignature::from_str(&sig).map_err(|e| {
                        Status::invalid_argument(format!("Invalid verification signature: {e}"))
                    })
                })
                .transpose()?;
            // check if verification signature is provided by aggregator
            if let Some(verification_signature) = verification_signature {
                let address_from_sig =
                    recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(
                        withdrawal_id,
                        input_signature,
                        input_outpoint,
                        output_script_pubkey.clone(),
                        output_amount,
                        verification_signature,
                    )?;

                // check if verification signature is signed by the address in config
                if address_from_sig != address_in_config {
                    return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
                }
            } else {
                // if verification signature is not provided, but verification address is set in config, return error
                return Err(BridgeError::ECDSAVerificationSignatureMissing).map_to_status();
            }
        }
