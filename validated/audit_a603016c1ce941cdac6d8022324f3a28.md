The external report describes an accounting error: `LendingPool` assumes it holds deposited `crvUSD`, but the funds were transferred to `RToken`, so its internal accounting (`currentBuffer`/vault deposit) does not match reality → permanent DoS.

Mapping onto Serai: the analogous shape is `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, which builds `tx_outs` including an OP_RETURN data output, but performs its weight/vbytes/fee accounting on `payments` only — i.e., it accounts for outputs that do not match the actual transaction. The result is a signed transaction whose declared fee/weight diverges from its real fee/weight: the actual fee rate can fall below the minimum relay rate, and the weight can silently exceed `MAX_STANDARD_TX_WEIGHT`, yielding a threshold-signed transaction that cannot be broadcast — funds locked until a full re-sign.

Code support:
- `tx_outs` is extended with the OP_RETURN output at send.rs:194-202, but `calculate_weight_vbytes` is invoked with `payments` at send.rs:204 and 226, so the OP_RETURN output is never weighed.
- The minimum-fee check at send.rs:211 and the weight cap check at send.rs:241 therefore validate against an under-counted transaction.
- `fee()` at send.rs:138-141 computes the real fee from `prevouts - tx.output`, which will include the unaccounted OP_RETURN bytes' missing fee as a shortfall in fee rate (not in absolute sats).

This is reachable by any party able to supply the `data` argument to `SignableTransaction::new` (the transaction-building path is the public API feeding `TransactionMachine`/FROST signing). The concrete impact: the multi-input, multi-party FROST ceremony completes and produces a transaction that is non-standard (`weight > 400_000 WU` not detected) or below min relay fee — i.e., unbroadcastable, and every input's preprocess/share round is wasted since preprocesses cannot be cached (`cache`/`from_cache` panic by design, send.rs:333-349).

### Title
OP_RETURN data output omitted from weight/fee accounting produces unbroadcastable signed transactions — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output to `tx_outs` but computes weight, vbytes, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check using only `payments`. The accounting therefore does not reflect the transaction actually signed and broadcast, analogously to the LendingPool assuming a balance it does not hold.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202` the OP_RETURN output is pushed onto `tx_outs`, which becomes `tx.output`. However, `calculate_weight_vbytes` is called at line 204 (and again at 226 for the change variant) with `payments`, not `tx_outs`, so the data output's bytes are never included in `weight`/`vbytes`. Consequently:
1. `needed_fee = fee_per_vbyte * vbytes` undercharges; the real fee (`prevouts - outputs`, send.rs:138-141) is fixed, so the *effective* fee rate is below the requested one and can fall below `DEFAULT_MIN_RELAY_TX_FEE` — the check at send.rs:211 compares `needed_fee` against a minimum computed from the same underestimated `vbytes`, so it passes.
2. The `weight > MAX_STANDARD_TX_WEIGHT` check at send.rs:241 can pass even when the real transaction exceeds the standardness limit.

### Impact Explanation
The completed FROST ceremony yields a transaction that either pays below minimum relay fee or exceeds standard weight — in both cases peers will not relay it and it cannot be mined. Because `TransactionSignMachine::cache`/`from_cache` are `unimplemented!`, the signing round cannot be cheaply resumed; all inputs' signing must be redone. The funds in the spent outputs are frozen until a corrected transaction is negotiated and re-signed by the threshold group.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(_)` triggers the miscalculation. With large `data` (up to 80 bytes) plus many inputs/payments, both the weight-cap bypass and the relay-fee shortfall are realistic. No secret material or privileged position is needed — only influence over the transaction template.

### Recommendation
Pass the full output list (including the OP_RETURN and, when present, change) into `calculate_weight_vbytes`, or build the template `Transaction` first — including all outputs — and derive weight/vbytes from it directly, so accounting always matches the signed transaction.

### Proof of Concept

    None,

    fee_per_vbyte,
