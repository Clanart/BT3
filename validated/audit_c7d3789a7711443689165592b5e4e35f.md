## Title
Clone operation explicitly disables Git's clone-time protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling code execution from attacker-controlled repositories/submodules - (File: app/src/lib/git/clone.ts)

## Summary
`clone()` in [1](#0-0)  builds the environment for every `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the child process environment. This variable is used internally by upstream Git as part of the fix for the clone/submodule hook-execution vulnerabilities (the class of issues addressed by CVE-2024-32004 and related fixes), where Git refuses or guards against executing repository-supplied content (e.g., symlinked `hooks` directories, or files that escape the worktree via crafted paths in nested/recursively cloned submodules) during a clone. Forcing this flag to `false` tells Git the protection has already been satisfied, bypassing the safeguard Git added specifically to stop malicious repository content from running during `clone --recursive`.

## Finding Description
Analogous to the Sherlock finding — where a value that gates a security-sensitive outcome (royalty %) can be manipulated by an untrusted party right before it is used — here the value that gates whether Git enforces its clone-time hook/symlink protection (`GIT_CLONE_PROTECTION_ACTIVE`) is deliberately forced to `false` by Desktop's own code before every clone, regardless of what the actual repository being cloned contains: [2](#0-1) 

The `clone` command is always invoked with `--recursive`, meaning submodules are fetched and checked out automatically as part of the same operation: [3](#0-2) 

An attacker who controls the content of a public/shared repository (or any submodule referenced by it) — the exact "attacker controls a cloned/fetched repository" primitive named in scope — can craft a repository whose recursive submodule structure the underlying Git protection is designed to catch (e.g., symlinks that redirect Git into executing hook/config content outside the intended worktree during the recursive submodule checkout). Because Desktop forces `GIT_CLONE_PROTECTION_ACTIVE=false` on every clone call, that upstream guard never fires for Desktop users, even when running a patched Git version that would otherwise refuse the operation.

Existing guards in this file do not stop this path: `isClonePathSensitive()` only checks the destination directory against a fixed deny-list of sensitive local paths (home dir, `.ssh`, `.gnupg`, etc.) — it says nothing about the content of the repository being cloned — [4](#0-3) . There is no other sanitization of the remote content between the attacker-controlled repository and the `git clone --recursive` invocation.

## Impact Explanation
If exploitable against a Git version whose clone protection depends on this flag being left at its default, this results in code execution during a normal "Clone repository" action in Desktop — the highest-impact category listed in scope (code execution from an attacker-controlled cloned repository), triggered by an entirely unprivileged action (a user cloning a URL/repo they were given, e.g. via `Ctrl+Shift+O` / "Clone repository" / "Open in Desktop" deep link / CLI `github clone`). No local access, admin rights, or pre-existing malware is required — only that the user clones a repository the attacker controls.

## Likelihood Explanation
Likelihood is high in the sense that every single clone operation in Desktop passes through this code path unconditionally — there is no opt-in/opt-out, no repository trust check, and no user-facing warning. The exploitability depends on the specific Git version bundled with Desktop and exactly which scenario `GIT_CLONE_PROTECTION_ACTIVE` guards in that version (I could not fully verify Desktop's bundled Git version's exact reliance on this flag from the indexed code alone), but the presence of an explicit, hardcoded override of a security-purposed environment variable on every clone is itself a clear regression that removes a defense-in-depth control Git added for exactly this attacker model.

## Recommendation
- Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override, or clearly document (with an upstream Git changelog/issue reference) why disabling this specific protection is safe for Desktop's use.
- If the flag is being set to work around a benign side effect of the protection (e.g., a spurious warning) for Desktop's own trusted operations (like re-cloning from `desktop`-known GitHub URLs), scope the override narrowly and never apply it to arbitrary user-supplied/attacker-supplied clone URLs, especially ones arriving via `x-github-client://` deep links, `github://openRepo`, or the `github clone` CLI.
- Add a regression test that clones a fixture repository containing the exact submodule/symlink structure the upstream CVE fix targets, and assert Desktop refuses/warns instead of silently permitting it.

## Proof of Concept
Conceptual PoC (exact upstream trigger structure not verifiable from the indexed code alone, but the vulnerable Desktop code path is directly evidenced):
1. Attacker publishes a repository containing a submodule (or `.gitmodules` entry) constructed per the technique Git's clone protection (tied to `GIT_CLONE_PROTECTION_ACTIVE`) was built to reject — e.g., a submodule whose worktree/hooks path is redirected via a symlink outside the intended checkout directory.
2. Victim clones the repository through GitHub Desktop (Clone dialog, "Open in Desktop" deep link, or `github clone owner/repo` CLI).
3. Desktop calls `clone()` in [1](#0-0) , which spawns `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the environment.
4. Because the protection flag is forced off, Git proceeds with the recursive submodule clone/checkout without applying the guard it would otherwise apply, and the attacker-controlled repository content executes/writes as if the protection did not exist. [5](#0-4)

import { git, IGitStringExecutionOptions } from './core'
import { ICloneProgress } from '../../models/progress'
import { CloneOptions } from '../../models/clone-options'
import { CloneProgressParser, executionOptionsWithProgress } from '../progress'
import { getDefaultBranch } from '../helpers/default-branch'
import { envForRemoteOperation } from './environment'
import { homedir } from 'os'
import * as Path from 'path'

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

/**
 * Clones a repository from a given url into to the specified path.
 *
 * @param url     - The remote repository URL to clone from
 *
 * @param path    - The destination path for the cloned repository. If the
 *                  path does not exist it will be created. Cloning into an
 *                  existing directory is only allowed if the directory is
 *                  empty.
 *
 * @param options  - Options specific to the clone operation, see the
 *                   documentation for CloneOptions for more details.
 *
 * @param progressCallback - An optional function which will be invoked
 *                           with information about the current progress
 *                           of the clone operation. When provided this enables
 *                           the '--progress' command line flag for
 *                           'git clone'.
 */
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
