### Title
Attacker-controlled `Participant` index causes panic (DoS) in PedPoP blame adjudication via unchecked HashMap indexing - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to CVE-2018-17096 (assertion/abort on attacker-influenced input in SoundTouch's `BPMDetect`), Serai's PedPoP DKG blame path crashes the process when evaluating a blame accusation that names a participant index which was never registered. `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with `self.enc_keys[&decryptor]` and `self.commitments[&sender]` directly, panicking on missing keys instead of returning an error. An unprivileged party submitting a blame/accusation (the `InvalidDkgShare` flow) can crash any node that adjudicates it.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender`, `recipient`, an `EncryptedMessage`, and an optional `EncryptionKeyProof`, all of which originate from an accusing participant's message. They call `blame_internal`, which calls `Decryption::decrypt_with_proof` at crypto/dkg/pedpop/src/encryption.rs:366-397. Inside, once the attacker-supplied `pop` signature verifies (trivially satisfiable — the accuser generates `msg.key` and signs the PoP themselves via `SchnorrSignature::sign`), the code evaluates `self.enc_keys[&decryptor]` at line 388. `enc_keys` only contains entries for participants registered in round 1 (`Decryption::register`, lines 351-362, is only invoked for `all_participant_indexes()` / `1 ..= n`). A `recipient` (a.k.a. `decryptor`) index outside that set — e.g. `Participant::new(500)` when `n = 4` — hits HashMap's `Index` impl and panics with "no entry found for key".

A second panic exists in `blame_internal` at crypto/dkg/pedpop/src/lib.rs:599: `&self.commitments[&sender]` panics if `sender` was not a DKG participant, reachable when the accuser supplies a message that decrypts correctly for a valid `recipient` but names an out-of-set `sender`.

There is no bounds check that `sender`/`recipient` ∈ `1 ..= params.n()` anywhere in `blame` or `decrypt_with_proof`. `Participant::new` only rejects zero, so any nonzero u16 is accepted.

### Impact Explanation
Denial of service: a single crafted blame accusation aborts the process/thread performing blame adjudication. For a validator/coordinator processing `InvalidDkgShare`-style accusations, this is a remotely triggerable crash — the same bug class as the reference CVE (assertion failure / application exit on adversarial input). In Rust this is an unwinding/abort panic rather than a graceful error, so any caller not wrapping the call in `catch_unwind` crashes. This also lets a faulty participant evade blame adjudication entirely by crashing the adjudicator.

### Likelihood Explanation
Reachable by any DKG participant able to submit an accusation to the blame API — no threshold cooperation or key knowledge required. The accuser needs only: (a) `msg.pop` to verify, which they fully control since `msg.key` is their own ephemeral key signed under `pop_challenge`, and (b) `proof: Some(_)` whose contents are never reached because the panic occurs during argument evaluation at `self.enc_keys[&decryptor]`. `Participant` has no upper-bound validation (`Participant::new` in crypto/dkg/src/lib.rs only rejects 0), so `recipient = Participant(0xFFFF)` works. Likelihood is therefore high wherever the blame path is exposed to unauthenticated participant indices.

### Recommendation
Replace HashMap indexing with checked lookups in `Decryption::decrypt_with_proof` (`self.enc_keys.get(&decryptor)`) and `BlameMachine::blame_internal` (`self.commitments.get(&sender)`), mapping a missing entry to a fault outcome (blame the accuser/recipient) or a `DecryptionError`. Additionally, validate `sender` and `recipient` against `1 ..= n` at the top of `blame`/`blame_internal` before touching either map. The debug-style `assert!` in `Decryption::register` (encryption.rs:356-359) should likewise become a fallible check if registration can ever be driven by remote messages.

### Proof of Concept
```rust
// Context: n = 4, t = 2 PedPoP DKG completed; node holds a BlameMachine
// constructed via AdditionalBlameMachine::new(context, n=4, commitment_msgs),
// which registered enc_keys only for participants 1..=4.

// Attacker (participant 2) crafts an accusation:
let bogus_recipient = Participant::new(500).unwrap(); // not in 1..=n

// Attacker generates a key they control so pop verifies:
let k = Zeroizing::new(C::random_nonzero_F(&mut rng));
let key = C::generator() * k.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut rng));
let pub_nonce = C::generator() * nonce.deref();
let pop = SchnorrSignature::sign(
    &k, nonce,
    pop_challenge::<C>(context, pub_nonce, key, attacker_i, &share_bytes),
);
let msg = EncryptedMessage { key, pop, msg: share_bytes };

// Any (even garbage) proof — never verified because indexing panics first:
let proof = Some(attacker_supplied_proof);

// Crashes the adjudicating node:
machine.blame(sender=Participant(1), recipient=bogus_recipient, msg, proof);
// -> panic at crypto/dkg/pedpop/src/encryption.rs:388:
//    self.enc_keys[&decryptor]  — "no entry found for key"
```

Uncertainty: whether the coordinator's `InvalidDkgShare` handler passes attacker-chosen `sender`/`recipient` directly into `blame` was not fully traced; however, the panic exists unconditionally in the public `blame` API surface, which is the documented accusation-adjudication entry point, and the rules accept untrusted bytes fed to library verify/complete-style APIs.
