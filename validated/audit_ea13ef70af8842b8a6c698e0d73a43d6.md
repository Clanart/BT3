### Title
Re-registration resets `claimed` to 0, enabling double-claim of already-paid vesting tokens - ([File: rewards/MGPRelease.sol])

### Summary
`register()` unconditionally overwrites the entire `Vesting` struct for an address, including resetting `claimed` to `0`, even when that address is already an active beneficiary who has previously claimed tokens. Any subsequent `claim()` call by that beneficiary then computes `claimable` against the new `totalAlloced` with `claimed` starting from zero, allowing the previously paid-out amount to be paid out again.

### Finding Description
In `register()`, each entry is written as a brand-new struct: [1](#0-0) 
This does not check whether `beneficiaries[_addresses[i]]` already exists with a non-zero `claimed` value — it simply replaces it, losing the record of tokens already transferred to that beneficiary.

`getClaimable()` and `claim()` both rely on `vesting.claimed` to determine how much more is owed: [2](#0-1) [3](#0-2) 

Exploit flow:
1. Beneficiary is registered with `totalAlloced = A`, calls `claim()` once vesting has started and receives a partial amount `P`, so `beneficiaries[addr].claimed = P`.
2. Owner re-registers the same address later (e.g., to top up the allocation or correct a typo) with `totalAlloced = B` (B ≥ A). This overwrites `claimed` back to `0`, even though `P` tokens were already paid out for the prior allocation.
3. Beneficiary immediately calls `claim()` again. `getClaimable()` now computes vesting against `B` with `claimed = 0`, so the beneficiary can withdraw up to the full vested portion of `B` — including the `P` tokens already paid in step 1.

There is no modifier or check anywhere in `register()`, `claim()`, or `getClaimable()` that reconciles or preserves prior `claimed` amounts across re-registration, so the conservation invariant ("claimed tokens are never reissued") is broken purely by the contract's own bookkeeping logic once a re-registration occurs — no attacker privilege is required to trigger the loss, only a routine admin action that the contract itself does not guard against.

### Impact Explanation
This causes direct theft of `tokenToRelease` (MGP) from the contract: a beneficiary can receive `P` (already paid) plus a fresh vested amount computed from the full new allocation, meaning `totalReceived > totalAlloced` for that beneficiary at the same vesting timestamp. Across many beneficiaries and re-registrations (e.g., allocation corrections, top-ups, or team schedule updates), this can drain the contract's token balance beyond what governance intended to distribute, causing protocol insolvency for other beneficiaries whose claims may then fail due to insufficient balance (`safeTransfer` revert) — a form of both direct theft and freezing of legitimately owed funds for others.

### Likelihood Explanation
Preconditions are simple and require no attacker capital: an address must already be a beneficiary with a nonzero `claimed`, and the owner must call `register()` again for that same address at any later point in the vesting schedule (a plausible, even routine, admin operation such as increasing an allocation, which the code does not distinguish from a fresh registration). The beneficiary then only needs to call `claim()` normally; no special timing, flash loans, or reentrancy is needed. This is fully repeatable for every re-registered address.

### Recommendation
When re-registering an address that already has a `Vesting` entry, preserve the existing `claimed` value rather than resetting it to `0`. For example, either revert if `beneficiaries[_addresses[i]].totalAlloced != 0` (forcing a separate "update" function that adjusts `totalAlloced` without touching `claimed`), or explicitly carry over `claimed` when constructing the new struct:
```solidity
uint256 alreadyClaimed = beneficiaries[_addresses[i]].claimed;
beneficiaries[_addresses[i]] = Vesting({
    totalAlloced: _amounts[i],
    claimed: alreadyClaimed,
    revoked: false
});
```

### Proof of Concept
Foundry test plan:
1. Deploy `MGPRelease` with `startTimestamp = now`, appropriate `endTimestamp`, and `initialUnlockPercentage` such that some tokens are immediately claimable.
2. Fund the contract with sufficient `tokenToRelease`.
3. Owner calls `register([alice], [1000e18])`.
4. Warp time forward partway through vesting; `alice` calls `claim()`, receives `P` tokens; assert `beneficiaries[alice].claimed == P`.
5. Owner calls `register([alice], [2000e18])` again (simulating a top-up/correction).
6. Assert `beneficiaries[alice].claimed == 0` (bug confirmed) instead of `P`.
7. `alice` calls `claim()` again immediately; assert she receives another chunk `Q` computed against `2000e18` with `claimed` starting at 0.
8. Assert `P + Q` exceeds the amount that should be vested at that timestamp under the corrected total `2000e18` minus `P` — i.e., `alice`'s cumulative tokens received exceed the properly vested amount, proving double-claim of the already-paid `P`.

    function getClaimable(address _account) public view returns (uint256 claimable) {
        Vesting storage vesting = beneficiaries[_account];
        uint256 initialUnlockedAmount = vesting.totalAlloced * initialUnlockPercentage / denominator;

        if (block.timestamp <= startTimestamp)
            return  initialUnlockedAmount - vesting.claimed;

        if (block.timestamp >= endTimestamp)
            return vesting.totalAlloced - vesting.claimed;

        uint256 needVesting = vesting.totalAlloced - initialUnlockedAmount;
        uint256 vested = (((block.timestamp - startTimestamp) * needVesting) / (endTimestamp - startTimestamp));

        claimable = (initialUnlockedAmount + vested - vesting.claimed);
    }
