Based on the investigation, I found a concrete Desktop analog: `updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` carries forward the `manualResolutions` map across a merge/rebase-abort transition without clearing it, mirroring the report's core defect — state that should be reinitialized at the start of a new "cycle" (there: a new day; here: a new merge/rebase operation) is instead silently inherited, corrupting the outcome.

### Title
Manual conflict resolutions are not cleared across an aborted-and-restarted merge/rebase, allowing stale resolutions to silently apply to a new (attacker-influenced) conflict - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
`updateConflictState` computes the next `ConflictState` by always reusing the previous `manualResolutions` map whenever the new status is of the same kind (`merge`→`merge` or `rebase`→`rebase`), even when the underlying operation has actually changed (different branch/tip, i.e., the previous merge/rebase was aborted and a new one started). The only reset of `manualResolutions` occurs when `prevConflictState` is `null` or when the conflict `kind` itself changes (merge↔rebase).

### Finding Description
In `getConflictState`, every new `ConflictState` object is built directly from whatever `manualResolutions` map is passed in [1](#0-0) . That map is only reset to empty when there is no previous conflict state at all: [2](#0-1) .

Crucially, `performEffectsForMergeStateChange` and `performEffectsForRebaseStateChange` detect that the branch identity changed (which they interpret as "the previous operation was aborted") purely to bump a stats counter (`mergeAbortedAfterConflictsCount` / `rebaseAbortedAfterConflictsCount`) — they never signal back to `updateConflictState` to drop the stale `manualResolutions`: [3](#0-2) [4](#0-3) . `updateConflictState` then unconditionally returns `newConflictState` — which still embeds the old `manualResolutions` — after these effect functions run: [5](#0-4) .

This carried-forward map is exactly what drives auto-resolution of files in the conflicts UI (`getResolvedFiles`, `hasUnresolvedConflicts`) and what `_updateManualConflictResolution` / `updateMultiCommitOperationStateAfterManualResolution` in `app-store.ts` project into the active multi-commit-operation step [6](#0-5) . If the same relative file path appears conflicted in two different operations in quick succession — e.g., the user aborts a merge in which they had already chosen "theirs" for `path/to/file`, then immediately starts a different merge/rebase (potentially against an attacker-influenced remote branch) that also conflicts on `path/to/file` — the stale "theirs" resolution from the first, unrelated operation is silently reapplied to the second operation's conflict, without the user re-reviewing that specific file.

Existing guards do not stop this path: the branch/tip-change detection exists (`branchNameChanged`) but is used only for telemetry, not for invalidating `manualResolutions`; and `getConflictState` has no notion of "this is a different underlying operation" beyond the `kind` field.

### Impact Explanation
If exploited, a file resolution chosen in one conflict context is silently carried into a subsequent, unrelated conflict on a same-path file, causing the working tree/commit content for that file to reflect a resolution the user never made for the second conflict. This can corrupt what the user ultimately commits/pushes without any visible warning, since the conflicts dialog will show the file as already resolved (via `manualResolution` lookup in `conflicts-dialog.tsx`) rather than prompting the user to resolve it again [7](#0-6) .

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (1) the user to have left an unresolved/only-partially-resolved conflict with at least one manual per-file resolution recorded, (2) abort or otherwise leave that operation, and (3) immediately encounter a new conflict of the same kind (`merge`/`merge` or `rebase`/`rebase`) that happens to conflict on the same file path. An attacker who controls a remote/fork the user is merging from could increase the odds by deliberately crafting conflicting content on commonly-modified paths (e.g. `package.json`, `README.md`), but they cannot force the sequence of user actions that leads to the carryover.

### Recommendation
Clear `manualResolutions` whenever the effect functions determine the underlying operation changed (i.e., when `branchNameChanged` is true in `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange`, or more generally whenever `currentTip`/`targetBranch`/`originalBranchTip` identity differs from the previous conflict state), rather than only resetting on `prevConflictState === null` or a `kind` change.

### Proof of Concept
1. Start a merge of branch B into A that conflicts on `shared.txt`; in the Conflicts dialog, manually mark `shared.txt` as "Use their version," but do not commit.
2. Abort the merge (`git merge --abort` via the dialog).
3. Immediately start a merge/rebase of a different branch C (attacker-controlled) into A, which also conflicts on `shared.txt` with different, attacker-authored content.
4. Observe that `updateConflictState` reuses the previous `manualResolutions` map (still containing `shared.txt` → "theirs") for the new conflict, per `app/src/lib/stores/updates/changes-state.ts` lines 268-275 and 281-305, so the conflicts dialog shows `shared.txt` as already resolved with the attacker's "theirs" content, which can be committed without further review.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

function performEffectsForMergeStateChange(
  prevConflictState: MergeConflictState | null,
  newConflictState: MergeConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
): void {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.currentBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.currentBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the merge must have been aborted
  if (branchNameChanged) {
    statsStore.increment('mergeAbortedAfterConflictsCount')
    return
  }

  const { currentTip } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null
  ) {
    const previousTip = prevConflictState.currentTip

    if (previousTip !== currentTip) {
      statsStore.increment('mergeSuccessAfterConflictsCount')
    } else {
      statsStore.increment('mergeAbortedAfterConflictsCount')
    }
  }
}

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

    this.updateMultiCommitOperationStateAfterManualResolution(repository)

    this.emitUpdate()
  }
