### Title
`ThresholdKeys::read` / `ThresholdKeys::new` never bind the secret share to the reconstructed group key, letting attacker-crafted bytes "claim" an arbitrary group key — ([File: crypto/dkg/src/lib.rs])

### Summary
The MOKE incident is an unprotected public `claim()`: a function releases value to anyone without checking the caller is entitled to it. The Serai analog lives in the threshold-key deserialization path. `ThresholdKeys::read` accepts fully attacker-controlled `t`, `n`, `i`, interpolation coefficients, `secret_share`, and `verification_shares`, and `ThresholdKeys::new` reconstructs the public `group_key` solely from `verification_shares[1..=t]` — without ever verifying that `secret_share` actually corresponds to `verification_shares[i]` or that the shares interpolate to any honest prior state. An attacker who feeds crafted bytes to `ThresholdKeys::read` therefore gets a struct whose `group_key()` is a key they fully control — the equivalent of claiming ownership of a key (and any funds/authorizations bound to it) with no eligibility check.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new` (lines 349–391) validates only that `verification_shares.len() == n` and that participant indexes are `<= n`. It then computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

The `group_key` is derived purely from the first `t` attacker-supplied verification shares. There is no check that `C::generator() * secret_share == verification_shares[i]` (the holder's own share is never bound to the declared verification shares), and with `t = 1` the Lagrange interpolation factor for participant 1 in set `{1}` is 1, so `group_key = verification_shares[1]` — a point the attacker chooses directly.

`ThresholdKeys::read` (lines 574–632) feeds untrusted bytes straight into this constructor: `t`, `n`, `i`, the interpolation variant (including `Interpolation::Constant` with arbitrary coefficients, whose `t != n` guard is easily satisfied with `t == n` or with `t = 1`... note `Constant` requires `t == n`, so `t = n = 1` works), the `secret_share`, and all `verification_shares` are read verbatim.

Since `view()` (lines 463–533) interpolates `secret_share` against whatever `included` set is passed and `group_key()` returns `(core.group_key * scalar) + G * offset`, the resulting `ThresholdKeys` is self-consistent and fully usable for signing — yet its "threshold group key" is a single key whose discrete log the attacker set as `secret_share`.

### Impact Explanation
Any unprivileged party who can get `ThresholdKeys::read` to consume their bytes (the prompt's reachability model explicitly includes untrusted bytes fed to `ThresholdKeys::read`) obtains a signing-capable key object for a `group_key` whose private key they chose. Concretely:

- The attacker picks `x`, serializes keys with `t = n = 1`, `i = 1`, `secret_share = x`, `verification_shares = {1: G*x}`. `group_key()` returns `G*x` — a public key that may already hold funds or authority in the integrating system.
- The victim application then signs messages under `group_key` using `x`; equally, the attacker can sign anything for `G*x` independently, since they know `x`. Funds bound to that group key are spendable by the attacker — the same "drain the reserve" outcome as MOKE, reached by claiming a group key rather than claiming tokens.
- Alternatively, the attacker sets `secret_share` inconsistent with `verification_shares[i]` to corrupt a real key set silently (the inconsistency is only detectable by re-running DKG verification, which `new` never performs).

This is a forgery/key-control vulnerability, not a panic or DoS.

### Likelihood Explanation
Exploitation requires an integration path where serialized `ThresholdKeys` come from untrusted input rather than local trusted storage. In Serai's own processor, keys are regenerated via PedPoP and loaded from a local DB, which lowers real-world likelihood. However, the API is public, the format is self-describing, and nothing in the type system distinguishes "keys produced by an honest DKG" from "keys deserialized from the wire" — any caller, cache, or recovery flow that round-trips `serialize`/`read` over a boundary the attacker can touch is exposed. Consistent with the MOKE severity: **Medium**.

### Recommendation
In `ThresholdKeys::new`, bind the holder's share to the verification shares: require `C::generator() * *secret_share == verification_shares[&params.i()]` before constructing the keys. This single check forces any accepted `ThresholdKeys` to be a genuine share of its declared `group_key`, closing the claim-without-eligibility hole at the deserialization boundary. Optionally, also reject `t == 1` parameter sets or degenerate `Interpolation::Constant` vectors on `read` when the keys are expected to originate from a DKG with known parameters.

### Proof of Concept
```rust
// crypto/dkg — conceptual PoC
use ciphersuite::{group::ff::Field, Ciphersuite};
use dalek_ff_group::Ristretto;
use dkg::{Participant, ThresholdKeys, ThresholdParams, Interpolation};
use zeroize::Zeroizing;
use std_shims::collections::HashMap;
use frost::curve::Curve; // for read_G/write helpers as needed

// Attacker chooses a scalar they know
let x = <Ristretto as Ciphersuite>::F::random(&mut rand_core::OsRng);

// Craft serialized ThresholdKeys: C::ID, t = 1, n = 1, i = 1,
// interpolation = Lagrange (byte 1), secret_share = x,
// verification_shares = { Participant(1): G * x }
let mut buf = vec![];
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID.as_bytes());
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1);                    // Interpolation::Lagrange
buf.extend(x.to_repr().as_ref());
buf.extend((Ristretto::generator() * x).to_bytes().as_ref());

// ThresholdKeys::read accepts this: group_key() == G*x, and secret_share == x,
// so every signature it produces verifies under a key the attacker controls —
// yet no check ever confirmed the secret share was legitimately issued.
let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
assert_eq!(keys.group_key(), Ristretto::generator() * x);
assert_eq!(*keys.original_secret_share(), x);
```
