## Finding

### Title
Tx-Origin-Based Sender Authorization in ICS20 Precompile Allows Any Contract to Drain a User's Funds via IBC Transfer - (File: `precompiles/ics20/types.go`)

### Summary
The `OnlyEOAPolicy` bug class is: an authorization check whose scope is broader than the specific call-context it's meant to protect, so an approval intended for one context is silently reused to authorize unrelated actions. The `CheckOriginAndSender` helper in the ICS20 (IBC transfer) precompile exhibits the same class of flaw: it authorizes a `MsgTransfer` sender based on `tx.origin` equality rather than requiring the direct caller (`contract.Caller()`) to be the account whose funds are moved, letting **any intermediate contract in a call chain** move funds out of the origin EOA's account.

### Finding Description
`CheckOriginAndSender` is defined at [1](#0-0) :

```go
func CheckOriginAndSender(contract *vm.Contract, origin common.Address, sender common.Address) (common.Address, error) {
	if contract.Caller() == sender {
		return sender, nil
	} else if origin != sender {
		return common.Address{}, fmt.Errorf(ErrDifferentOriginFromSender, origin.String(), sender.String())
	}
	return sender, nil
}
```

The intent is clearly to permit two legitimate patterns: (1) a contract calling the precompile on its own behalf (`contract.Caller() == sender`), or (2) a plain EOA calling the precompile directly (where `origin == sender` because there is no intermediary). However, the second branch only checks `origin == sender` — it does **not** verify that `contract.Caller() == origin`, i.e. it does not verify that the call is actually a *direct* call from the EOA. Any contract sitting between the EOA and the precompile can pass `sender = origin` as an argument and this check will pass, even though `contract.Caller()` (the immediate caller of the precompile) is the intermediate contract, not the EOA itself.

`sender` here is used to build the ICS20 `MsgTransfer.Sender` field via `NewMsgTransfer`, at [2](#0-1) . The resulting `MsgTransfer` causes the transfer keeper to debit coins from `sender`'s bank balance and escrow them for the IBC channel — i.e., whichever `sender` address is supplied controls whose funds get moved.

Because `sender` is attacker-controlled input to the precompile call (`args[4]` in `NewMsgTransfer`, [3](#0-2) ), and the only gate preventing an arbitrary address from being used is `CheckOriginAndSender`, the flawed origin-based check means: **any contract that a user's EOA transacts with (for any reason) can silently smuggle in an IBC transfer of that EOA's funds**, by calling the ICS20 precompile with `sender = tx.origin`. The EOA never explicitly authorizes that specific transfer, and never even needs to interact with the ICS20 precompile directly — the malicious/compromised contract does so on the EOA's behalf using the ambient `tx.origin`.

This is structurally identical to the reported `OnlyEOAPolicy` issue: an authorization decision (`allowedContracts` / `origin==sender`) is scoped too broadly — shared across contexts it should not apply to — so a permission that should only cover one specific interaction ends up authorizing unrelated, unintended actions performed by a different, untrusted actor (an arbitrary intermediate contract) with real fund-moving consequences.

### Impact Explanation
This falls squarely under the "Critical … theft, or unauthorized extraction of user funds … IBC escrows" allowed-impact bucket. Any EOA that calls into an arbitrary or malicious contract (a common, unprivileged, everyday action — e.g. interacting with a DeFi contract, an NFT mint, or any dApp) can have that contract silently forward the EOA's `tx.origin` as the `sender` of an ICS20 `MsgTransfer`, draining bank-held coins out of the EOA's account into an IBC channel to an address the attacker controls on the destination chain. This is a direct, irreversible extraction of user funds requiring no explicit approval, allowance, or signature from the user beyond the single tx that invoked the malicious contract.

### Likelihood Explanation
Likelihood is high: no privileged role is required. An attacker only needs to get a victim to send one transaction to any attacker-controlled (or compromised) contract; that contract can internally call the ICS20 precompile address with `sender = tx.origin`. This mirrors the classic `tx.origin`-based-authorization anti-pattern, which is a well-known, easily exploitable EVM bug class, and here the precompile's own helper explicitly implements it.

### Recommendation
Remove the `origin == sender` branch entirely, or additionally require `contract.Caller() == origin` before allowing that branch to succeed (i.e., only allow the origin-based bypass when there is no intermediate contract in the call chain). The safer and standard approach is to always require `sender == contract.Caller()`, and if a delegated-transfer flow is desired, implement it via an explicit ICS20 allowance/authorization mechanism scoped per spender/denom (analogous to `AllowlistPolicy`/`CombinedPoliciesPolicy` recommended in the source report), rather than relying on `tx.origin`.

### Proof of Concept
1. Victim EOA holds a bank balance of denom `X` on the Cosmos EVM chain.
2. Attacker deploys `MaliciousContract` with a function `lure()` that internally calls the ICS20 precompile's `transfer` method, passing `sender = tx.origin` (equal to whatever EOA happens to call `lure()`), `receiver` = attacker's address on a connected IBC chain, and `amount` = victim's full balance.
3. Victim is enticed to call `MaliciousContract.lure()` (e.g. disguised as an airdrop claim or swap function) directly (no `msg.value` or approval needed).
4. Inside the precompile's transfer handler, `CheckOriginAndSender(contract, origin=victim, sender=victim)` is invoked: `contract.Caller()` is `MaliciousContract`'s address (not equal to `sender`), but `origin == sender` (both are the victim), so the check **passes**.
5. `MsgTransfer` executes with `Sender = victim`, debiting the victim's bank balance and escrowing it over IBC to the attacker's receiver address — funds extracted with only one, unrelated-looking transaction signed by the victim.
