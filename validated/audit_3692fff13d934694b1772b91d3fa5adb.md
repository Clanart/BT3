### Title
Unrestored mempool conflict eviction on failed replacement admission - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.add_spend_bundle()` removes conflicting mempool items *before* confirming that the replacement item can actually be inserted, and does not restore them if insertion subsequently fails. This mirrors the CVE-2018-17205 bug class: a "commit" step removes prior valid state to make room for a new item, and if the new item's insertion fails afterward, the removed state is not rolled back.

### Finding Description
When a submitted spend bundle passes `validate_spend_bundle()` with a successful RBF (replace-by-fee) resolution, `check_removals()`/`can_replace()` determine the set of conflicting mempool items to evict, returned as `conflicts` and passed back to the caller as `remove_items` (the `err is None` return path) [1](#0-0) .

`add_spend_bundle()` then unconditionally removes those conflicting items from the pool via `self.mempool.remove_from_pool(remove_items, MempoolRemoveReason.CONFLICT)` and only afterward attempts `self.mempool.add_to_pool(item)`: [2](#0-1) 

`Mempool.add_to_pool()` can still fail after this point. Specifically, when the new item's `assert_before_height`/`assert_before_seconds` is close to expiring, it tries to evict other soon-to-expire, lower-priority items to make room; if the new item's own fee-per-virtual-cost is not high enough to justify evicting those items, it aborts and returns `Err.INVALID_FEE_LOW_FEE` without adding the new item to the pool: [3](#0-2) 

At this point the caller sees `info.error is not None` and returns `MempoolInclusionStatus.FAILED`, but the previously evicted conflicting item(s) removed at line 651 are never re-inserted: [4](#0-3) 

The net effect: a legitimate, valid, already-accepted higher-fee transaction from another user can be permanently evicted from the mempool as a side effect of an unrelated spend bundle submission that ultimately fails to be admitted itself — the victim transaction is not replaced by anything and simply disappears from the node's mempool.

### Impact Explanation
Any unprivileged party who can submit a spend bundle (via RPC `push_tx` or gossip) can construct a bundle that:
1. Spends the same coin(s) as an existing, higher-fee-per-cost mempool item, qualifying as a valid RBF replacement per `can_replace()` (satisfying superset/fee-increase rules), causing `check_removals()`/RBF logic to mark the old item for removal.
2. Is itself soon-to-expire (via `assert_before_height`/`assert_before_seconds` set close to the current tip) with an overall fee-per-virtual-cost lower than other unrelated soon-expiring items already in the mempool, so the internal eviction check in `add_to_pool()` aborts and returns `INVALID_FEE_LOW_FEE`.

The result is a transaction-processing disruption: the honest victim's valid, fee-paying transaction is silently dropped from the mempool with nothing replacing it, delaying/denying its confirmation and forcing re-submission — achievable purely through a single crafted spend bundle from any network participant, without needing to actually get any transaction included on chain.

### Likelihood Explanation
The precondition (crafting a bundle that satisfies RBF fee/superset rules while intentionally under-shooting the internal capacity-eviction fee bar) is deterministic and fully attacker-controlled, since both `can_replace()` thresholds and the mempool's internal fee-priority ordering are public/derivable from mempool state observable via RPC. No race condition or privileged access is required, only crafting the two related fee levels correctly, so likelihood is high for anyone actively probing mempool internals; skill required is moderate (need to understand RBF vs. capacity-pruning fee thresholds).

### Recommendation
Make the remove-then-add sequence atomic with respect to failure: either validate that `add_to_pool()` will succeed before removing conflicting items (e.g., pre-check capacity/expiry eviction feasibility ahead of removal), or catch `info.error is not None` in `add_spend_bundle()` and re-insert the removed conflicting items back into the pool before returning `FAILED`.

### Proof of Concept
Conceptual reproduction (cannot be dynamically executed here, but derivable from the cited code paths):
1. Submit spend bundle `A` (spends coin `X`) with a fee sufficient to sit in the mempool normally.
2. Submit spend bundle `B` that spends `X` with a strictly higher fee-per-cost than `A` (satisfying `can_replace()`), and also sets `assert_before_height` a few blocks out (soon-to-expire), while keeping absolute fee-per-virtual-cost lower than several other unrelated, already-present soon-expiring low-priority mempool items.
3. `validate_spend_bundle()` succeeds RBF checks for `B`, returning `err=None` with `remove_items=[A.name]`.
4. `add_spend_bundle()` calls `remove_from_pool([A.name])`, evicting `A`.
5. `add_to_pool(B)` hits the expiring-item eviction check in `mempool.py` lines 418-447, finds `B`'s priority insufficient to evict the other soon-expiring items, and returns `Err.INVALID_FEE_LOW_FEE` without inserting `B`.
6. Final state: neither `A` nor `B` is in the mempool — `A`'s valid transaction has been permanently and silently dropped as a side effect of `B`'s failed submission.

Note: I was not able to execute this scenario in a running node to empirically confirm the exact fee/priority values needed to trigger the `INVALID_FEE_LOW_FEE` branch after a successful conflict removal; this analysis is based on static code review of `chia/full_node/mempool_manager.py` and `chia/full_node/mempool.py` only.
