### Title
Decoy conflict-marker text in a file causes silent misalignment and data loss during Copilot conflict resolution reassembly - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` splices Copilot's per-hunk resolutions into a conflicted file by scanning for lines that merely *look like* Git conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`), with no verification that these markers were actually produced by Git for a real conflict. This is structurally the same class of bug as the reported `_vote()` issue: a positional counter (`hunkIndex`, analogous to `_totalVoteWeight`) is advanced using a superset of entries that includes bogus/attacker-controlled ones, while the actual payload array (`hunkResolutions`, analogous to the "valid gauges") was sized against a different, independently-computed count of *real* conflicts. The mismatch is never detected, and the result is silently spliced into the wrong location or dropped entirely.

### Finding Description
`validateResolutionPaths` enforces that the number of hunks the model returns for a file equals `f.hunks.length` — the count of conflicts as determined by whatever upstream conflict-context gatherer parsed the file (`app/src/lib/copilot-conflict-resolution.ts:473-521`).

`reassembleResolvedFile` independently re-scans the raw file content line-by-line and treats *any* line matching `^<{7}(?:\s|$)` as the start of a conflict block, provided it can later find a line matching `^={7}$` and a line matching `^>{7}(?:\s|$)` before EOF (`app/src/lib/copilot-conflict-resolution.ts:524-526, 560-579`): [1](#0-0) 

This scan has no way to distinguish a genuine Git-generated conflict block from three lines of ordinary file content that happen to match the same regex (e.g., a code comment, a string literal, a markdown example, or documentation that itself illustrates Git conflict-marker syntax — such as the very `ConflictResolutionSystemPrompt` block reproduced in this file, or a `diff-parser-test.ts`-style fixture). If such a decoy block exists anywhere in the working tree copy of a conflicted file (attacker-controlled via a cloned/fetched malicious repository or branch that is being merged), `reassembleResolvedFile` will:

1. Consume one entry from `hunkResolutions` for the decoy block (`hunkIndex++` at line 591), even though this entry was actually generated by the model for a *later, real* conflict (since `IFileConflictContext.hunks.length`, used to size and order `hunkResolutions`, never counted the decoy).
2. Splice the wrong resolution content into the decoy location.
3. For every real conflict encountered after the decoy, the resolutions are now off-by-one, and once `hunkIndex >= hunkResolutions.length` the block simply falls through the `if (hunkIndex < hunkResolutions.length)` guard, meaning the real conflict's markers are removed but **no content is substituted at all** (line 585-590), silently deleting code.

None of the existing guards catch this: `validateResolutionPaths` only compares two client-side *counts*, both of which are wrong for the same reason (upstream context-gathering also parses conflicts, and if it undercounts the decoy the same way, the counts will match and validation passes even though the wrong hunk is consumed at reassembly time). The check at lines 444-448 in `parseCopilotConflictResolution` (rejecting hunks whose `resolvedContent` still contains conflict markers) only protects against the model echoing markers back — it does nothing for this mis-indexing.

### Impact Explanation
This causes silent corruption of what the user commits after a guided merge/rebase conflict resolution: legitimate hunks can be replaced with unrelated resolved content, or have their content deleted outright with no error, warning, or diff review forcing function beyond the user's own diligence. Since the whole point of the Copilot conflict-resolution feature is to let the user trust the automated reassembly and commit it, a user who accepts the suggested resolution can commit/push code that silently drops or corrupts real conflict resolutions, which matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Medium: it requires (1) a merge/rebase conflict occurring on a file that also happens to contain text resembling Git conflict markers elsewhere in the file (documentation, generated diffs, examples, escaped/quoted marker strings), which an attacker with any commit access to a branch being merged can deliberately plant, and (2) the user using the Copilot-assisted conflict resolution feature and committing without diffing the reassembled result. This is a plausible, low-effort attacker action (a single crafted line in a comment or literal) against a genuinely reachable code path (`reassembleResolvedFile`) that runs automatically whenever this feature is used.

### Recommendation
`reassembleResolvedFile` (and whatever function originally counts/extracts conflict hunks for `IFileConflictContext.hunks`) must use one authoritative, shared conflict-block parser rather than two independently-written regex scans. The reassembly step should validate, for each file, that the number of well-formed marker blocks it detects while walking `rawContent` exactly equals `hunkResolutions.length`, and throw a `CopilotValidationError` (surfacing the file for manual resolution) rather than silently proceeding, splicing wrong content, or dropping trailing hunks when the counts diverge.

### Proof of Concept
1. Set up two branches that conflict on `foo.md`.
2. In the branch content (either side), add, above the real conflict, a block of ordinary file text that matches the marker regexes but is not an actual Git conflict, e.g.:
   ```
   Example of a merge conflict:
   <<<<<<< example
   old text
   =======
   new text
   >>>>>>> example
   ```
   followed further down by the real `<<<<<<< HEAD ... ======= ... >>>>>>> branch` conflict introduced by the merge.
3. Trigger the merge in Desktop so the file ends up with one real conflict as far as Git/the context gatherer is concerned, but two "marker-shaped" blocks as far as line-based regex scanning is concerned.
4. Invoke "Resolve with Copilot." The model returns exactly one hunk resolution for `foo.md` (matching the validated hunk count of 1).
5. `reassembleResolvedFile` walks the file, matches the decoy block first (since it also satisfies `hasSeparator`/`closingIndex`), consumes the single available `hunkResolutions[0]` entry there, and then reaches the real conflict block with `hunkIndex (1) >= hunkResolutions.length (1)`, so the real conflict's markers are stripped with nothing spliced in — its content silently disappears from the reassembled file that the user is then prompted to commit. export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
