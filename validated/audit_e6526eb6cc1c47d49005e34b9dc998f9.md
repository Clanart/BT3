### Title
`hyper-fungible-token` decimals mismatch lets a re-validated-at-registration-only precision invariant be broken by later asset metadata changes, causing cross-chain amount inflation - (File: modules/pallets/hyper-fungible-token/src/module.rs, modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance`/`convert_to_erc20` scale amounts between a local asset's decimals and the remote ERC20's decimals by computing `10^(erc_decimals.saturating_sub(local_decimals))` (or the reverse), exactly analogous to the reported `Oracle.getUnderlyingPrice` bug of dividing/multiplying by a decimal-derived magic exponent without re-validating the assumption at the time of use. [1](#0-0) 

### Finding Description
The pallet only enforces the invariant `erc_decimals >= local_decimals` once, inside `register_token`/`update_token`, using the asset's decimals *at that moment*: [2](#0-1) [3](#0-2) 

However, `send`, `on_accept`, and `on_timeout` all re-fetch the local asset's decimals dynamically via `fungibles::metadata::Inspect::decimals(local_asset_id)` on every call, instead of using the value captured/validated at registration: [4](#0-3) [5](#0-4) 

If the underlying `pallet-assets` asset's decimals metadata is mutable after registration (e.g. via the asset's own `set_metadata` permission, which in `pallet-assets` is typically controlled by the asset's `Issuer`/`Owner`, not necessarily the bridge's `CreateOrigin`/governance), the once-checked invariant `erc_decimals >= local_decimals` can be silently violated later. Because the scaling exponent is computed with `saturating_sub`, a violation does not panic or revert — it silently clamps to `10^0 = 1`: [1](#0-0) 

Concretely, in `convert_to_erc20` (used by `send`), if `local_decimals` grows above the registered `erc_decimals`, the raw local balance (now denominated at higher precision) is forwarded unscaled as the ERC20 `amount` field of the outgoing message, where the destination EVM contract interprets it at the (lower) registered `erc_decimals`. This inflates the ERC20-denominated amount by a factor of `10^(local_decimals_new - erc_decimals)` relative to what was actually escrowed/burned on the Substrate side. [6](#0-5) 

The mismatch is not re-checked anywhere along the `on_accept` (mint/release) or `on_timeout` (refund) paths either — they use whatever decimals the asset currently reports, without ever comparing it against the counterpart chain's `Precisions` entry: [7](#0-6) 

This is the direct structural analog of the C4 report: a decimal-derived scaling factor is trusted from a stale/one-time assumption (`8 → 6` in the oracle; `erc_decimals >= local_decimals` here) instead of being asserted at the point of use, and drift silently corrupts the computed value rather than reverting.

### Impact Explanation
If exploitable, this breaks the "bridged assets must move exactly once and only to the rightful beneficiary and amount" invariant: an attacker who can influence or benefits from a decimals change on a registered asset could escrow a small local amount and cause the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to mint or release an amount many orders of magnitude larger, draining EVM-side custody/backing for that asset. Conversely, on the refund/`on_timeout` path a similar drift could under- or over-refund the original sender.

### Likelihood Explanation
This is rated with caveats: exploitation strictly depends on (a) whether the specific `pallet-assets`/`fungibles::Mutate` implementation wired into `Config::Assets` in the `gargantua`/`nexus` runtimes permits decimals metadata to be changed after asset creation, and (b) whether that permission is held by an actor less privileged than the pallet's own `CreateOrigin`. I was not able to confirm the exact `pallet_assets::Config` wiring (`MetadataDepositBase`, `ForceOrigin`, asset ownership model) for these runtimes within the available search results, so I cannot fully confirm reachability by an unprivileged actor versus only a governance/admin actor. This is a genuine gap in verification, not a dismissal of the finding — the code-level guard (`saturating_sub` silently clamping instead of reverting, combined with a registration-time-only check) is a real design weakness that should be fixed regardless of current asset-permission configuration, since it removes defense-in-depth against future config or asset changes.

### Recommendation
- Re-validate `erc_decimals >= local_decimals` (or the appropriate directional check) at the time of `send`, `on_accept`, and `on_timeout`, not only at `register_token`/`update_token`, and hard-fail (return an error) rather than silently clamping via `saturating_sub`.
- Alternatively, snapshot and store `local_decimals` in the `Precisions` map at registration time so the pallet never depends on a live, externally-mutable `decimals()` call for the scaling computation.
- Add an explicit error variant (already present as `ErcDecimalsBelowLocal`) to the `on_accept`/`on_timeout`/`send` runtime paths instead of relying solely on registration-time enforcement.

### Proof of Concept
Conceptual (I could not execute a live test given index constraints):
1. Governance registers asset `X` with `local_decimals = 6` and `erc_decimals = 6` via `register_token`, passing the `ensure!(config.decimals >= local_decimals)` check.
2. The `pallet-assets` asset owner for `X` (assumed to have `set_metadata` rights independent of the bridge's `CreateOrigin`) later changes `X`'s decimals to `18`.
3. A user calls `Pallet::send` with `params.asset_id = X`. `decimals` is now re-read as `18`, `erc_decimals` is still `6` from `Precisions`. `convert_to_erc20(amount, 6, 18)` computes `6u8.saturating_sub(18u8) = 0`, so `erc20_amount = amount * 10^0 = amount` — the raw 18-decimal-denominated balance is sent as the ERC20 message amount, which the destination `HyperFungibleToken` contract mints/releases at its configured (6-decimal) precision, over-crediting the recipient by `10^12`. [8](#0-7) [9](#0-8) 

Because I could not verify the exact `pallet_assets` permission model for the target runtimes, this finding should be treated as a **confirmed code-level weakness with unconfirmed full exploit reachability** — recommend a Devin session with repo access to inspect `parachain/runtimes/gargantua/src/lib.rs` and `nexus/src/lib.rs`'s `pallet_assets::Config` (specifically `ForceOrigin`/asset ownership for `set_metadata`) to close the reachability gap.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
