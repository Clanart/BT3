## Analysis

The Clearpool `bid()` bug is fundamentally a **missing-binding** flaw: the contract only checks *that* a bid arrived, not *whether it is entitled to win at this exact moment* — any late-arriving transaction can substitute itself for the "real" final bid because the check (is this a valid bid?) is decoupled from the actual state it's supposed to protect (who should win). Looking for this same shape of bug — "the authorization/validity check does not bind the request to the specific context it's supposed to be scoped to" — in Desktop, the closest analog is in the **trampoline credential IPC channel** used to relay Git credentials from Desktop to `git` subprocesses.

`isValidTrampolineToken()` only checks whether a token exists in a global set, not which repository/remote/host it was issued for: [1](#0-0) 

Any process holding *any* currently valid token can call the credential-helper `get` handler and specify an arbitrary `host`/`url`/`protocol` to request a credential for, and Desktop resolves the account purely from that attacker-suppliable data — not from the actual remote of the git operation the token was minted for: [2](#0-1) [3](#0-2) 

The token is minted per git invocation and passed to the child process (and anything the child spawns, e.g. Git LFS smudge/clean filters or hooks) via environment variables, but its scope is never checked against the actual remote host being contacted: [4](#0-3) 

The server only validates the token's mere existence before dispatching the handler, with no per-request binding to the invoking git command's remote: [5](#0-4) 

### Title
Trampoline credential-helper does not bind token to the requesting remote, allowing cross-host credential exfiltration - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Desktop's Git credential helper trampoline authenticates *requests* using a short-lived token (`DESKTOP_TRAMPOLINE_TOKEN`) but never verifies *what* the token-holder is asking a credential for. Any process that is a child of a Desktop-invoked `git` operation — including a Git LFS smudge/clean filter, custom transfer agent, or a hook triggered by content from an attacker-controlled repository — inherits the token and port, and can request credentials for an arbitrary `host=`/`url=`/`protocol=` combination, not just the one associated with the running operation. Desktop will happily hand back the signed-in user's stored GitHub token for that arbitrary host.

### Finding Description
`withTrampolineEnv()` mints a random token via `withTrampolineToken()` and injects it, along with the local trampoline server's port, into the environment used to spawn `git`: [6](#0-5) 

This environment is inherited by every child process `git` spawns during that operation — filters (e.g. `git-lfs smudge`/`clean`, LFS custom transfer agents), and potentially hooks — because Git passes its own process environment down to filters/hooks.

When a credential is requested over the trampoline socket, `createCredentialHelperTrampolineHandler` and `getCredential()` derive the target endpoint entirely from the credential payload supplied by the caller (`getCredentialUrl(cred)`), never comparing it to the actual remote URL of the git operation the token was issued for: [7](#0-6) [2](#0-1) 

`isValidTrampolineToken` — the only gate on the socket — merely checks set membership: [8](#0-7) 

There is no invariant tying "this token may only be used to fetch credentials for the remote that this specific `git` invocation targets." Exactly like the auction `bid()` accepting any transaction as "the" winning bid without confirming it belongs to the correct, current auction round, the trampoline server accepts any credential request carrying a valid-but-unscoped token as legitimate for whatever host is named in the request — regardless of whether that host has anything to do with the operation the token was created for.

### Impact Explanation
A malicious/compromised repository that is cloned or fetched can ship a `.gitattributes`/`.lfsconfig` that triggers execution of a filter/custom transfer process (a very common, unprivileged, already-supported Git/LFS feature) as part of the same `git` invocation Desktop is running. That filter process inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` and can open a raw socket to the trampoline server and issue a forged `get` credential request for `host=github.com`. Because `getGitHubCredential`/`getGenericCredential` do not verify the request's host against the actual remote being operated on, Desktop returns the signed-in user's real GitHub OAuth token/PAT, which the malicious process can exfiltrate to an attacker-controlled endpoint. This is unprompted credential/token exfiltration purely from cloning/fetching an attacker-controlled repository — matching the "attacker controls a cloned/fetched repository ... credential/token exfiltration" impact bar.

### Likelihood Explanation
Git LFS filter/custom-transfer execution during `clone`/`fetch`/`checkout` is a standard, unprivileged code path that many users already have enabled (LFS is common). No special user interaction beyond opening/cloning the attacker's repository in Desktop is required, and the trampoline port/token are handed to the filter process automatically as part of normal environment inheritance — the attacker does not need local access, admin rights, or any pre-existing malware.

### Recommendation
Bind each trampoline token to the specific remote URL(s) legitimately associated with the git operation it was minted for (e.g., store the expected host alongside the token in `trampolineEnvironmentPath`-style maps), and have `getCredential`/`getGenericCredential`/`getGitHubCredential` reject requests whose `host`/`url` does not match the operation's actual remote before consulting the account store.

### Proof of Concept
1. Sign in to GitHub.com in Desktop.
2. Clone/open an attacker-controlled repository that has Git LFS enabled (`.gitattributes` marking files as `filter=lfs`) and a `.lfsconfig`/hook configured to run a small program during checkout.
3. During the checkout, the LFS smudge process (a child of the `git` process Desktop spawned) reads `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its inherited environment.
4. The process connects to `127.0.0.1:<DESKTOP_PORT>` and sends a `CREDENTIALHELPER get` command with `protocol=https`, `host=github.com` in the payload.
5. `trampoline-credential-helper.ts`'s `getCredential()` finds the account bound to `github.com` (unrelated to the attacker's own repo) via `getGitHubCredential` and returns the token in the response, which the malicious process exfiltrates over the network.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

export const createCredentialHelperTrampolineHandler: (
  store: AccountsStore
) => TrampolineCommandHandler = (store: Store) => async command => {
  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command
  const input = parseCredential(command.stdin)

  if (__DEV__) {
    debug(
      `${firstParameter}\n${command.stdin
        .replaceAll(/^password=.*$/gm, 'password=***')
        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )
  }

  try {
    if (firstParameter === 'get') {
      const cred = await getCredential(input, store, token)
      if (!cred) {
        const endpoint = `${getCredentialUrl(input)}`
        info(`could not find credential for ${endpoint}`)
        setHasRejectedCredentialsForEndpoint(token, endpoint)
      }
      return cred ? formatCredential(cred) : undefined
    } else if (firstParameter === 'store') {
      await storeCredential(input, store, token)
    } else if (firstParameter === 'erase') {
      await eraseCredential(input, store, token)
    }
    return undefined
  } catch (e) {
    error(`${firstParameter} failed`, e)
    return undefined
  }
}

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

  private async processCommand(socket: Socket, command: ITrampolineCommand) {
    if (!isValidTrampolineToken(command.trampolineToken)) {

      return
    }

      socket.end(result)
    } else {

    }
