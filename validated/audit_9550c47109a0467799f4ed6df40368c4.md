## Finding: Unchecked ERC-20 return value in escrow withdrawal path allows funds to be marked settled without being transferred - `evm/tron/contracts/apps/IntentGatewayV2.sol`

### Summary
The report's core defect is: code assumes every ERC-20 `transfer`/`approve` call either reverts on failure or returns `true`, and never actually inspects the returned boolean. The Hyperbridge analog exists in the Tron variant of the intent gateway, where the escrow-withdrawal and dust-sweep paths perform a raw low-level `.call()` to `IERC20.transfer` and only check the outer `success` flag from the call, never decoding/validating the returned `bool` payload.

### Finding Description
In `withdraw()` and the `SweepDust` handler of `evm/tron/contracts/apps/IntentGatewayV2.sol`, token payouts use: [1](#0-0) 

and the fee payout: [2](#0-1) 

and the dust-sweep path: [3](#0-2) 

All three sites do `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treat the transfer as successful purely based on the low-level `success` boolean (i.e., the callee did not revert). They never decode the returned data to check whether the ERC-20 actually reports `true`. Many ERC-20 implementations (including several already recognized by this codebase's own fee-on-transfer test fixtures, e.g. `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2501-2547) return `false` on failure instead of reverting. Against such a token, `token.call(...)` succeeds (returns `success == true`) even though the transfer moved zero tokens, because the call itself does not revert — only the encoded return data (which is ignored) would indicate failure.

Immediately after this unchecked call, the contract unconditionally decrements the escrow accounting and marks the order settled: [4](#0-3) 

The escrow state `_orders[body.commitment][token]` is reduced and `_filled[body.commitment] = beneficiary` (or `EscrowReleased`/`EscrowRefunded` emitted) regardless of whether tokens were actually delivered. Compare this to the main (non-Tron) `IntentGatewayV2`/`ExtrinsicIntents` path and other apps in this repo, which consistently use `SafeERC20.safeTransfer`/`safeTransferFrom` (e.g. `evm/src/apps/IntentGatewayV2.sol` line 219, 290, `EvmHost.sol` lines 844/874/903, `WrappedHyperFungibleToken.sol` lines 349/352/358/361) — confirming that the raw `.call()`-without-decode pattern in the Tron contract is the deviating, unsafe implementation, directly matching the bug class in the external report (unchecked/ambiguous ERC-20 return value handling).

### Impact Explanation
This is a direct fund-loss / false-settlement bug matching the bounty's "stealing or loss of funds" and "false ... acceptance" categories: escrowed input tokens or transaction fees can be permanently marked as withdrawn/refunded/released in on-chain accounting while the beneficiary receives nothing, because the accounting update is gated only on `success` of the outer call, not on the actual boolean transfer result. This can happen with any ERC-20 that returns `false` instead of reverting on failure (e.g. due to insufficient balance in some non-standard token implementations, paused/blacklist tokens, etc.), permanently locking the escrowed value with no path to re-claim it since `_orders[commitment][token]` is already zeroed and `_filled` is already set (guarding against retries).

### Likelihood Explanation
No privileged actor, malicious relayer, or governance action is required — the flow is triggered by the normal `onGetResponse`/withdrawal callback path once escrow conditions are met, and the vulnerable branch fires deterministically whenever the escrowed token is one that returns `false` on a failed transfer (a legitimate, unprivileged token behavior, not an attacker-controlled peer/relayer assumption). This is a standing execution-path bug in the Tron deployment target, not a hypothetical malicious-actor scenario.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` and the `SweepDust` handler) with `SafeERC20.safeTransfer`, matching the pattern already used consistently elsewhere in the codebase (`evm/src/apps/IntentGatewayV2.sol`, `EvmHost.sol`, `WrappedHyperFungibleToken.sol`). This ensures both non-standard no-return tokens and false-returning tokens revert the whole withdrawal instead of silently marking escrow as settled.

### Proof of Concept
1. Create/escrow an order whose input or fee token is an ERC-20 that returns `false` (rather than reverting) on a failed `transfer` — for example, a token that returns `false` once balance drops below some internal threshold, or a mock token used purely to demonstrate the gap (as already scaffolded by `FeeOnTransferToken` test patterns in this repo, extended to return `false` on failure instead of reverting).
2. Trigger `withdraw()` via the normal `onGetResponse` callback path in `evm/tron/contracts/apps/IntentGatewayV2.sol` line 729-734 for a commitment whose escrowed token transfer call returns `false`.
3. Observe: `token.call(...)` at line 697 returns `success == true` (call didn't revert), so execution proceeds to decrement `_orders[body.commitment][token] -= amount` (line 701) and set `_filled[body.commitment] = beneficiary` (line 684), emitting `EscrowReleased`/`EscrowRefunded` — even though the beneficiary's token balance never increased.
4. The beneficiary has lost the escrowed amount with no code path to retry, since escrow state has already been zeroed and the order marked filled. [5](#0-4)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
