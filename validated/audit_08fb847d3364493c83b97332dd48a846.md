## #Valid Vulnerability Found

### Title
Trampoline credential helper token is not bound to a specific host/repository, allowing any Git-spawned subprocess (e.g. an LFS smudge filter) to exfiltrate the user's real GitHub token — (File: `app/src/lib/trampoline/trampoline-server.ts`, `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` are set as plain environment variables on every Git subprocess Desktop spawns, and are intentionally propagated to filter processes (e.g. Git LFS smudge/clean filters) because Desktop configures the credential helper via `GIT_CONFIG_PARAMETERS` rather than CLI args specifically "so commands invoked by filters ... can pick up our configuration". Any process that inherits these two values — including an attacker-supplied LFS custom filter declared in a repository's `.lfsconfig` — can open its own raw TCP connection to `127.0.0.1:$DESKTOP_PORT` and replay the trampoline wire protocol directly (bypassing the compiled trampoline client entirely, as the vendor test suite demonstrates is possible with a bare `execFile`+socket). The server only validates that the supplied token is a currently active, server-issued token; it performs no binding between the token/connection and the host or repository the credential request is actually for.

### Finding Description
`TrampolineServer.processCommand` in [1](#0-0)  only checks `isValidTrampolineToken(command.trampolineToken)` — i.e., whether the token exists in the in-memory `trampolineTokens` set ( [2](#0-1) ). It never checks that the `host`/`url` supplied in the credential request corresponds to the git remote actually being operated on for that token/session.

The `CredentialHelper get` handler resolves credentials purely from the caller-supplied host: `getGitHubCredential` builds an `endpoint` from the credential map sent over the socket and calls `findGitHubTrampolineAccount`, which merely matches any signed-in account whose endpoint origin equals the origin of the attacker-chosen host, then returns that account's real login/token via `credWithAccount`: [3](#0-2) . The matching logic itself has no session/repo binding: [4](#0-3) .

The token/port are deliberately exposed to filter subprocesses, as documented in the code: [5](#0-4) . The wire protocol used by the trampoline client is trivial to replicate directly over TCP (parameter count, parameters, env-var count, `DESKTOP_TRAMPOLINE_TOKEN=...`, then stdin credential lines) as shown by the vendor's own tests interacting with the server socket: [6](#0-5)  and [7](#0-6) .

Because the token supplied to a given Git invocation is valid for the entire lifetime of that invocation (`withTrampolineToken`, [8](#0-7) ) and is not scoped to any particular remote host, a malicious LFS smudge/clean filter — configured entirely via repository content (`.lfsconfig`) and spawned as a child of the `git`/`git-lfs` process during clone/fetch/checkout — can use the inherited `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` to request credentials for an arbitrary host, such as `github.com`, rather than the (unrelated) LFS endpoint it was actually invoked to authenticate against. If the user is signed into GitHub.com/GHE in Desktop, `getGitHubCredential` returns their real username and OAuth token to the malicious filter.

### Impact Explanation
Full exfiltration of the user's GitHub account token(s) stored in Desktop, simply by cloning/fetching an attacker-controlled repository containing a malicious `.lfsconfig`/custom filter. This satisfies "credential/token exfiltration" from an attacker-controlled cloned/fetched repository.

### Likelihood Explanation
High: no special local access or user interaction beyond a normal clone/fetch of a malicious repo is required. Git LFS custom smudge/clean filters and `.lfsconfig` are standard, well-documented, repository-controlled mechanisms; the attacker only needs the victim to clone/fetch the repo with Git LFS support enabled (Desktop bundles/manages LFS). No compiled trampoline binary is even required — the attacker's filter script can implement the simple text protocol itself over a raw socket.

### Recommendation
Bind each trampoline token to the specific remote/host (and possibly repository) the Git operation was started for, and validate that any `CredentialHelper get`/`store`/`erase` request's host matches the expected remote's host for that token before returning stored credentials. Additionally, consider not exposing `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` to filter/hook subprocesses beyond what is strictly required, or issuing filter subprocesses a separate, more restricted capability (e.g. a token scoped only to the LFS remote host associated with the operation) rather than the full session token capable of retrieving any account's credentials.

### Proof of Concept
1. Attacker creates a repository containing a `.lfsconfig` (or `.gitattributes` filter) defining a custom smudge command, e.g. a script `evil-smudge`.
2. Victim clones the repository in GitHub Desktop; Desktop spawns `git clone`/`git lfs smudge` with `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` in its environment (per `withTrampolineEnv`, [9](#0-8) ), which Git passes through to the LFS filter subprocess.
3. `evil-smudge` reads `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its environment, opens a TCP socket to `127.0.0.1:$DESKTOP_PORT`, and sends a hand-crafted trampoline request:
   - `1` (parameter count), `get` (parameter)
   - `1` (env var count), `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`
   - stdin: `protocol=https\nhost=github.com\n\n`
   - Also sends `DESKTOP_TRAMPOLINE_TOKEN=<stolen token>` as required env var.
4. Server validates the token (valid, since it's the real session token) and calls `getCredential`, which finds the signed-in GitHub.com account and returns `username=<login>` and `password=<real OAuth token>`.
5. The filter script exfiltrates this token to an attacker-controlled server.
