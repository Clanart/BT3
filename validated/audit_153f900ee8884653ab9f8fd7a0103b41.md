### Title
Insufficient lock in Gasless module `PreAddTx` allows concurrent map writes to `knownTxs`, causing corruption/crash reachable by any RPC transaction sender - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
This is the closest reachable analog to the HNS3 "vlan list lock" bug: a shared mutable collection (`knownTxs`) is protected by a mutex, but one write path (`PreAddTx`) takes only a **read** lock (`RLock`) while mutating the map, whereas the other write paths (`IsReady`, `PreReset`, `PostReset`) correctly take the **write** lock (`Lock`). Just as the HNS3 vlan list lacked adequate protection between a periodic cleanup task and a concurrent VLAN modification (leading to use-after-free), the `knownTxs` map here lacks adequate mutual exclusion between `PreAddTx` (invoked when transactions are submitted) and the promotion/reset paths (invoked by the transaction-pool's internal reorg/promotion routines).

### Finding Description
`GaslessModule.PreAddTx` is a `kaiax.TxPoolModule` hook invoked whenever a transaction is submitted to the pool (i.e., reachable by any unprivileged sender via public RPC `eth_sendRawTransaction`/`SendTransaction`). It acquires only a read lock before mutating the `knownTxs` map: [1](#0-0) 

`g.knownTxs.add(tx, TxStatusQueue)` at line 50 performs an in-place Go map write (`k[tx.Hash()] = &knownTx{...}`): [2](#0-1) 

Meanwhile, the sibling hooks `IsReady`, `PreReset`, and `PostReset` — invoked from the transaction pool's promotion/reset machinery — correctly take the exclusive write lock (`g.knownTxsMu.Lock()`) before mutating the same map: [3](#0-2) [4](#0-3) [5](#0-4) 

Because Go's `sync.RWMutex` allows multiple concurrent `RLock` holders, if `PreAddTx` can be entered concurrently by more than one transaction-submission path (e.g., overlapping `AddLocal`/`AddRemotes` batch calls, or any future/alternate ingestion path in the pool that doesn't fully serialize module hooks under a single writer lock), two goroutines can simultaneously execute `g.knownTxs.add(...)`, causing concurrent unsynchronized writes to the same Go map. Go map writes are not safe for concurrent use even between two "readers" holding only `RLock` — this is a genuine data race that can corrupt the map's internal structure or trigger Go's runtime `fatal error: concurrent map writes`, crashing the node process. This mirrors the "use after free" root cause of the HNS3 CVE: a periodic/other-context writer (`IsReady`/`PreReset`/`PostReset`, holding a full write lock) racing with an insufficiently-guarded writer (`PreAddTx`, holding only a read lock) on the same shared collection.

### Impact Explanation
If triggered, `fatal error: concurrent map writes` is unrecoverable and immediately terminates the Go process — a full node crash / denial-of-service, and if the race instead silently corrupts the map without crashing, it can desynchronize gasless bundle bookkeeping (`numQueue`, `numExecutable`, `numPending`), causing the gasless module's queue/pending admission limits (`MaxBundleTxsInQueue`, `MaxBundleTxsInPending`) to be miscounted and potentially bypassed, or causing legitimate gasless bundles to be dropped/mispromoted. Because `PreAddTx` fires on every incoming transaction from any public RPC caller, the vulnerable code path is trivially reachable by an unprivileged sender.

### Likelihood Explanation
Exploitability depends on whether the surrounding `blockchain.TxPool` fully serializes calls into `TxPoolModule.PreAddTx` against calls into `IsReady`/`PreReset`/`PostReset` via its own outer lock (e.g., `pool.mu`). I was not able to fully confirm, within the available context, that no code path invokes these hooks without holding a common outer write lock for the entire pool. If such serialization does exist for every call path (present and future), the race is masked at the pool level, though the module-internal lock usage is still incorrect. If any code path invokes `PreAddTx` without that external serialization (e.g., a future addition, an alternate submission API, or already-existing paths I could not fully trace given index limits), the race is directly and repeatedly triggerable by concurrent public transaction submissions.

### Recommendation
Change `PreAddTx` to acquire `g.knownTxsMu.Lock()` (write lock) instead of `RLock()`, since it performs a map write (`g.knownTxs.add`), consistent with `IsReady`, `PreReset`, and `PostReset`. More generally, audit all `knownTxs` accessors to ensure every mutating call path holds the exclusive lock and every pure-read path holds only the shared lock, removing any reliance on external/incidental serialization by the caller.

### Proof of Concept
Not independently reproducible from static analysis alone given index limits on confirming the outer `TxPool` locking guarantees; the described defect is a static, provable code-level race (mismatched `RLock`/`Lock` usage guarding writes to the same `knownTxs` map) directly visible in the cited lines. Confirming actual concurrent triggerability would require exercising `TxPool.AddLocal`/`AddRemotes`/`reset()` concurrently against the live pool and observing either a `fatal error: concurrent map writes` crash or `go test -race` flagging the data race in `kaiax/gasless/impl/tx_pool.go` and `tx_counter.go`.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
