### Title
Blind SSRF via unvalidated DataLayer mirror URLs fetched by subscribed peers - (File: chia/data_layer/download_data.py)

### Summary
Chia's DataLayer mirror feature lets any wallet holder publish an on-chain "mirror" coin containing a list of free-form URL strings for a given DataLayer store. Any other node that subscribes to that store as a normal DataLayer client will automatically pick up these attacker-controlled URLs and issue outbound HTTP requests to them during periodic sync, with no restriction on scheme, host, or destination IP range. This mirrors the Nextcloud Mail CVE-2023-23943 bug class: unvalidated, user-supplied server URLs are used to make server-side outbound requests, enabling blind SSRF / internal network scanning.

### Finding Description
Any wallet owner can call the `add_mirror` RPC to publish an arbitrary list of URLs on-chain for a DataLayer store they reference: [1](#0-0) 

The urls are wrapped into `Mirror` and stored on a coin using `create_mirror_puzzle`/`get_mirror_info`, with no validation of scheme or host — only an empty-list check: [2](#0-1) 

Any peer that already tracks/subscribes to that store id will process the new mirror coin in `coin_added`, decode the URLs, and persist them as trusted server locations without any URL sanitization: [3](#0-2) 

During the background sync loop, `fetch_and_validate` iterates these mirror URLs and calls `insert_from_delta_file` → `download_file` → `http_download`, which performs an unguarded `aiohttp` GET request built directly from the attacker-supplied URL: [4](#0-3) [5](#0-4) 

There is no allow-list/deny-list for private, link-local, or loopback addresses, and no scheme restriction — `http_download` will happily connect to `http://169.254.169.254/...`, `http://127.0.0.1:<internal-port>/...`, or any RFC1918 address reachable from the victim node. Distinguishable success/`ClientConnectorError`/timeout outcomes (logged and used to compute per-server ban/backoff state) let an attacker infer whether internal hosts/ports are reachable — a classic blind-SSRF internal-network scan primitive, directly analogous to CVE-2023-23943.

### Impact Explanation
A malicious DataLayer store owner/mirror publisher can weaponize any node that subscribes to (or auto-subscribes as an owner-tracked pseudo-subscription for) their store to make it issue outbound HTTP requests to internal-only endpoints (cloud metadata services, internal admin APIs, other localhost services on the victim's own machine/network) on a recurring basis via the `periodically_manage_data()` loop. Response contents are streamed to disk (bounded by `max_delta_file_size`) and success/failure is exposed indirectly through logs and the `ServerInfo` ban/retry state exposed via `get_mirrors`/`get_subscriptions`, enabling port/service enumeration of the victim's internal network. This is a Medium-severity confidentiality/availability-adjacent issue (internal reconnaissance, not direct fund loss), matching the CVSS 5.0 rating of the original Nextcloud advisory.

### Likelihood Explanation
Likelihood is moderate: any wallet holder can create a mirror coin cheaply (`add_mirror`/`dl_new_mirror` only require a fee-bearing coin), and any node that subscribes to a store — a normal, expected DataLayer client action — will automatically process attacker-controlled URLs with no opt-in or confirmation. Subscription is required, so the victim must be an active client of that specific store, but this is a routine and encouraged DataLayer usage pattern (subscribing to third-party datasets).

### Recommendation
Validate mirror/server URLs before storing and before making outbound requests in `http_download`/`download_file`: restrict schemes to `http`/`https`, resolve and reject requests targeting private, loopback, link-local, and other non-routable/internal address ranges (unless explicitly allowed via config), and consider requiring an explicit user opt-in or allow-list before a node automatically fetches from newly announced mirror URLs.

### Proof of Concept
1. Attacker creates a DataLayer store and publishes a mirror coin with `chia data add_mirror --id <store_id> --url http://169.254.169.254/latest/meta-data/ --amount 1` (see `chia/cmds/data.py:474-511`), which is picked up by `add_mirror` in `data_layer_rpc_api.py:468-475`.
2. Victim node, already tracking/subscribed to `<store_id>` for legitimate data replication, observes the mirror coin via `DataLayerWallet.coin_added` (`data_layer_wallet.py:775-800`) and stores the URL as a `Mirror`/`ServerInfo` entry with no validation.
3. On the next `periodically_manage_data()` cycle, `fetch_and_validate` (`data_layer.py:642-705`) selects the malicious server URL and calls `insert_from_delta_file` → `download_file` → `http_download` (`download_data.py:298-324`), causing the victim node to issue an outbound GET to the attacker-chosen internal URL.
4. Repeating with different internal hosts/ports and observing success vs. `ClientConnectorError`/timeout (reflected in ban timers retrievable via `get_mirrors`/subscription state) allows the attacker to enumerate reachable internal services from the victim's network.

class Mirror(Streamable):
    coin_id: bytes32
    launcher_id: bytes32
    amount: uint64
    urls: list[str]
    ours: bool
    confirmed_at_height: uint32 | None

    @staticmethod
    def encode_urls(urls: list[str]) -> list[bytes]:
        return [url.encode("utf8") for url in urls]

    @staticmethod
    def decode_urls(urls: list[bytes]) -> list[str]:
        return [url.decode("utf8") for url in urls]

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
