### Title
Unbounded revert in `_sendRewards`'s `smartConvert` leg blocks principal deposit/withdraw in `WombatStaking` — (File: wombat/WombatStaking.sol)

### Summary
`WombatPoolHelperV2.deposit`/`depositLP`/`withdraw` all route through `WombatStaking._toMasterWomAndSendReward`, which unconditionally calls `_sendRewards` on every harvested WOM amount. When `smartWomConverter` is configured, `_sendRewards` calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`, whose internal slippage check (`MinRecNotMatch`) can be made to fail by anyone who moves the WOM/mWOM Wombat pool price, causing the entire deposit/withdraw transaction to revert and freezing principal movement for the whole pool, not just the fee leg.

### Finding Description
`WombatPoolHelperV2.deposit()` calls `WombatStaking.deposit()` [1](#0-0) , which after minting LP from the real Wombat pool (protected by its own `_minimumLiquidity` slippage check) unconditionally calls `_toMasterWomAndSendReward(_lpAddress, lpReceived, true)` [2](#0-1) . The same call happens in `depositLP` and `withdraw` [3](#0-2) .

`_toMasterWomAndSendReward` harvests pending WOM from `MasterWombat` and forwards it to `_sendRewards` [4](#0-3) . Inside `_sendRewards`, when a fee entry is marked `isMWOM` and a `smartWomConverter` is set, WOM fee proceeds are routed through `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` with no try/catch [5](#0-4) .

`SmartWomConvert.smartConvert` self-derives `_minRec = _amountIn` and hands it to `_convertFor`, which reverts with `MinRecNotMatch` if `convertAmount + amountRec < _minRec` [6](#0-5) [7](#0-6) . `amountRec` is the output of a live swap on `womMWomPool` via the Wombat router, and the split between `convertAmount`/`amountToSwap` depends on `currentRatio()`/`maxSwapAmount()`, both read live from the WOM/mWOM pool's cash/liability and swap-quote state [8](#0-7) [9](#0-8) .

Any unprivileged actor can move the WOM/mWOM pool price/liquidity (an external, publicly tradable pool) immediately before a victim's (or their own) `deposit`/`depositLP`/`withdraw` call so that the buyback swap's `amountRec` falls short of the self-imposed `_minRec`, forcing `MinRecNotMatch` to revert. Because this call sits in the middle of the mandatory harvest path shared by every principal-moving entrypoint, the revert bubbles all the way up and blocks the deposit or withdrawal — even though the user's principal LP/receipt-token movement (guarded separately by the AMM's own `_minimumLiquidity`/`_minAmount` checks) has nothing to do with the reward conversion outcome. No modifier, `nonReentrant`, or `whenNotPaused` guard prevents this; they only gate re-entrancy/pausing, not a legitimate but unrelated external-call revert deep in the shared harvest path.

### Impact Explanation
This DoS affects the WOM-denominated fee/reward leg but blocks all *principal* operations for the pool: `deposit`, `depositLP`, and `withdraw` all revert as long as the WOM/mWOM pool remains in an unfavorable state and pending WOM rewards are non-zero. Users cannot withdraw principal, and new deposits cannot be made, which is a temporary freezing of funds for the affected pool. This matches "High – Temporary freezing of funds for at least 24 hours," since an attacker (or ambient market conditions) can keep the WOM/mWOM pool skewed for an extended period, and governance intervention (disabling `smartWomConverter` or the fee, or manually restoring pool balance) is required to unblock the pool.

### Likelihood Explanation
Preconditions: `smartWomConverter` must be configured and an active `isMWOM` fee entry on WOM rewards must exist (an operational/admin configuration, not attacker-controlled, but a realistic production setup for this protocol) and the pool must have accrued non-zero pending WOM at the time of the call. Given those preconditions, no privileged role is needed by the attacker — moving a public AMM pool's price via swaps is a capital-bound but otherwise permissionless action, and the check is deterministic (`convertAmount + amountRec < _amountIn`), so triggering the revert is reproducible and can be repeated/maintained as long as the attacker is willing to keep swapping against the pool or the imbalance persists naturally.

### Recommendation
Do not let the reward-conversion path's success gate principal deposit/withdraw:
- Wrap the `smartConvert` (and other optional reward/fee) calls in `_sendRewards` with a low-level `call` and swallow/ log failures instead of reverting, or
- Move `_toMasterWomAndSendReward`'s harvest-and-fee-distribution logic to a separate, best-effort step (e.g., a `try/catch`, or a queued/claimable fee model) so that a failure in the WOM→mWOM conversion never blocks LP deposit/withdrawal, or
- Have `smartConvert`/`_convertFor` accept a caller-supplied minimum (or 0) instead of self-imposing `_minRec = _amountIn`, so temporary price impact cannot force a revert.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatStaking`, register a pool via `registerPool`, set `smartWomConverter` to a `SmartWomConvert` instance wired to a live WOM/mWOM Wombat pool, and add an active `isMWOM` fee (`addFee`).
2. Have `MasterWombat` accrue pending WOM for the pool (mock reward-per-sec or advance blocks).
3. As an unprivileged actor, execute swaps against the WOM/mWOM pool (or its mock) to push `SmartWomConvert.currentRatio()` below `buybackThreshold` and make the router's `swapExactTokensForTokens(wom→mWom)` return less than the swapped-in `amountToSwap`.
4. Call `WombatPoolHelperV2.deposit(_amount, _minimumLiquidity)` (or `withdraw`) from a second, honest user account.
5. Assert the transaction reverts with `SmartWomConvert.MinRecNotMatch`, that the honest user's principal deposit token was not consumed / withdrawal LP was not burned (balance delta ~0), and that repeating the call while the pool imbalance persists continues to revert, demonstrating a sustained freeze of principal movement for the pool.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
