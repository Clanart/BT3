### Title
Delegated PoX-4 stacking locks STX without recording the movement in the AssetMap, letting a lock evade `Staking` post-condition enforcement - ([File: pox-locking/src/pox_4.rs])

### Summary
`handle_stack_lockup_pox_v4` (and its `-extend`/`-increase` siblings) only calls `global_context.log_stacking(...)` when the invoked PoX-4 function is exactly `"stack-stx"` (respectively `"stack-extend"`, `"stack-increase"`), explicitly skipping the log for `"delegate-stack-stx"`, `"delegate-stack-extend"`, and `"delegate-stack-increase"`, even though those calls apply the *exact same* `STXBalance` lock via `pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4`. [1](#0-0) [2](#0-1) 

### Finding Description
This is the same bug class as the Cork Protocol H-5 finding: an asset movement (there, incoming RA on `repurchase()`; here, an STX lock via `delegate-stack-stx`) mutates real balances but is not fed into the ledger/accounting structure (`PsmRedemptionAssetManager.locked` / here, the transaction's `AssetMap`) that a downstream check relies on to be exhaustive.

The `AssetMap` is the single source of truth `check_transaction_postconditions` uses to decide whether a transaction's asset movements are covered by the sender's post-conditions. For STX locking specifically, coverage is enforced through `asset_map.get_all_stacking()`, which is populated only by `GlobalContext::log_stacking`: [3](#0-2) [4](#0-3) 

In `Deny` mode (and in `Originator` mode for the origin), *every* principal whose stacking amount is non-zero in the `AssetMap` must be covered by an explicit `TransactionPostCondition::Staking` condition, or the transaction aborts: [5](#0-4) 

However, `pox_4.rs` deliberately gates the `log_stacking` call on the *function name* rather than on "did a lock actually happen":
```
Ok(_) => {
    // For direct stacking, we log the locked amount in the asset map.
    if function_name == "stack-stx" {
        global_context.log_stacking(&stacker, locked_amount)?;
    }
    ...
``` [6](#0-5) 

`handle_contract_call` dispatches both `"stack-stx"` and `"delegate-stack-stx"` (and the extend/increase pairs) into the same lock-applying handler, so the underlying state change (`pox_lock_v4` locking the stacker's STX) is identical regardless of which entry point was used: [7](#0-6) 

Nothing in the PoX-4 contract or in `handle_contract_call` prevents a principal from delegating stacking rights to themselves via `delegate-stx` and then, in a transaction they sign as `tx-sender`, calling `delegate-stack-stx` directly on their own principal. In that case the origin of the transaction is the very account whose STX ends up locked, so a `Staking` post-condition (or a `Deny`-mode transaction with no post-conditions at all, expecting "no stacking will happen") is the exact protection SIP-040/Epoch 4.0 introduced this feature for. But because the code path taken is `"delegate-stack-stx"`, `log_stacking` is never called, so the `AssetMap` never records that principal's locked amount, and the coverage-enforcement loop in `check_transaction_postconditions` (`asset_map.get_all_stacking()`) sees nothing to check. The lock is applied to the account balance regardless, silently bypassing the post-condition system.

This breaks the intended equality: "in Deny/Originator mode, every STX-locking action taken by/affecting the covered principal within the transaction must be checked against a `Staking` post-condition." The `delegate-stack-stx` path moves (locks) an asset past the post-condition system entirely, exactly analogous to Cork's `repurchase()` moving RA past `PsmRedemptionAssetManager` tracking.

### Impact Explanation
This falls under the "Critical - an asset moving past its post-conditions" category defined in scope. A wallet or contract relying on a `Staking` post-condition (or on `Deny` mode with no such condition, expecting no stacking to occur) to bound how much of the signer's own STX may become locked for PoX can have that STX locked without the post-condition ever being evaluated against the real amount, because the `AssetMap` entry that drives the check is never populated for this specific, reachable call path. Locked STX is unusable until the PoX unlock height, which is a meaningful, unauthorized-by-post-condition state change on the signer's own funds.

### Likelihood Explanation
Reaching this path requires only: (1) the target principal delegate to itself (or to any address it also controls) via `delegate-stx`, a normal supported PoX-4 operation with no special privilege, and (2) sign a `delegate-stack-stx` (or `-extend`/`-increase`) contract-call transaction as `tx-sender`, with a `Staking` post-condition (or `Deny` mode) that the signer believes protects them. No miner, signer set, or other account's key is required — it is fully reachable by an ordinary unprivileged transaction signer, per the constraints given.

### Recommendation
Log the stacking amount in the `AssetMap` for the delegated lock/extend/increase paths whenever the *effective stacker* principal (the one whose balance is actually locked, from `parse_pox_stacking_result`/`parse_pox_extend_result`/`parse_pox_increase`) is present, independent of whether the invoked function name was the "direct" or "delegate" variant — i.e., remove the `function_name == "stack-stx"` (and analogous) gating and always call `global_context.log_stacking(&stacker, locked_amount)?` after a successful `pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4`, mirroring how `delegate-stx` already unconditionally logs via `log_stacking` at line 440 of the same file. This makes the `AssetMap`, and therefore `check_transaction_postconditions`'s staking-coverage enforcement, consistent for every code path that can actually lock STX.

### Proof of Concept
1. Principal `A` (an unprivileged account) calls `delegate-stx` naming itself (`A`) as the delegate — this is a normal, permitted PoX-4 operation and is recorded in the `AssetMap` via the unconditional `log_stacking` call at [8](#0-7) .
2. In a later transaction signed by `A` (as `tx-sender`/origin), `A` calls `pox-4.delegate-stack-stx` targeting itself as the stacker, with `post_condition_mode = Deny` and no `TransactionPostCondition::Staking` condition present (or with one bounding the amount to less than what actually gets locked).
3. `handle_contract_call` routes this into `handle_stack_lockup_pox_v4` with `function_name == "delegate-stack-stx"`. `pox_lock_v4` succeeds and locks `A`'s STX, but the `if function_name == "stack-stx"` guard at line 211 prevents `log_stacking` from being called.
4. `check_transaction_postconditions` runs its staking-coverage loop over `asset_map.get_all_stacking()` (`crates/stacks-transactions/src/lib.rs:394-407`) and finds no entry for `A`, so it reports no violation — the transaction is accepted even though `A`'s STX was locked and even though `Deny` mode/the missing or too-small `Staking` post-condition should have aborted it.

I was not able to independently re-confirm from the PoX-4 Clarity contract source (`pox-4.clar`) within the remaining tool budget whether the contract imposes any additional restriction preventing `tx-sender == stacker == delegate` for `delegate-stack-stx`; this should be verified against `stackslib/src/chainstate/stacks/boot/pox-4.clar`'s `delegate-stack-stx` definition before treating the PoC as fully confirmed end-to-end, though nothing found in the Rust dispatch/lock-application code (`pox_4.rs`) itself blocks this scenario.
