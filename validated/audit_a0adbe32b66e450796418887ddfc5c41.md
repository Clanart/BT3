## Title
Path-containment check in `resolveWithin` accepts sibling directories via unanchored `startsWith` prefix match, enabling attacker-controlled deep links to read/reveal files outside the intended repository - (File: `app/src/lib/path.ts`)

## Summary
The report's underlying bug class is a **boundary/containment check that is off by the wrong operator/anchor**, so a value that is exactly on the boundary of "inside" vs "outside" is misclassified. In `has_ended`, `<` instead of `<=` misclassifies "exactly at the boundary" as "not yet ended." In GitHub Desktop's `resolveWithin` helper, the analogous flaw is a **string-prefix check without a path-separator anchor**, which misclassifies a *sibling* directory whose name happens to share a prefix with the root as being "inside" the root.

## Finding Description
`resolveWithin` is Desktop's generic guard against path traversal: it is supposed to guarantee that a resolved path is "at, or underneath" a given root path [1](#0-0) . The actual containment test is:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`startsWith` performs a raw character-prefix comparison, not a path-segment comparison. If `realRoot` is `/Users/victim/Documents/GitHub/repo-good` and `realResolved` is `/Users/victim/Documents/GitHub/repo-good-evil/secret.txt`, the latter *does* start with the former as a string, even though `repo-good-evil` is a completely different, sibling directory. The correct check would additionally require that the character immediately after `realRoot` in `realResolved` be a path separator (or that the lengths match exactly).

This function is used to sanitize a user-controlled, repository-relative `filepath` coming from a **GitHub Desktop deep link** (`x-github-client://openrepo?...&filepath=...`), which is parsed by `parseAppURL` [3](#0-2)  and consumed in `Dispatcher.openRepositoryFromUrl`:

```ts
if (isAbsolute(filepath)) {
  log.error(`Refusing to open absolute path: ${filepath}`)
  return
}

const resolved = await resolveWithin(repository.path, filepath)

if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(
    `Prevented attempt to open path outside of the repository root: ${filepath}`
  )
}
``` [4](#0-3) 

The `isAbsolute(filepath)` guard only blocks a literally absolute path string; it does **not** stop a relative traversal such as `../repo-good-evil/secret.txt`. That value is joined/normalized and resolved against `repository.path` (`repo-good`) inside `_resolveWithin` [5](#0-4) , producing `/Users/victim/Documents/GitHub/repo-good-evil/secret.txt`. Because that resolved path shares `realRoot` as a literal string prefix, the unanchored `startsWith` check wrongly reports it as "within" `repo-good`, and `resolved` is handed to `shell.showItemInFolder`, revealing/selecting a file that lives in a sibling directory outside the repository the link was supposed to be scoped to.

Existing tests only exercise `..`-then-back-into-root and symlink-escape cases [6](#0-5) ; none exercise the sibling-directory-with-shared-prefix scenario, so the gap is unguarded by current tests as well as by code.

## Impact Explanation
This falls squarely in the requested impact category: **an attacker controls a link/deep link the user clicks, and the result is a file read/reveal outside the repo.** `shell.showItemInFolder` opens the OS file manager focused on the resolved path — an attacker who can predict or influence the naming of a sibling directory relative to the target clone destination (e.g. a user who commonly keeps multiple related clones side-by-side, such as `project` and `project-internal`, or `repo` and `repo.bak`) can craft an `openrepo` deep link whose `filepath` traverses one level up and back into the sibling, causing Desktop to expose a file that is explicitly outside the intended repository root, defeating the "Prevented attempt to open path outside of the repository root" safeguard that is supposed to be authoritative here.

## Likelihood Explanation
Exploitation requires:
1. The victim to click an attacker-supplied `x-github-client://openrepo?...&filepath=...` link (standard Desktop deep-link flow, no other user interaction required beyond the click).
2. A sibling directory that shares a path-string prefix with the resolved repository directory to exist on disk (either coincidentally, from the user's own habits, or because the `url`/clone-destination-derived directory name itself was influenced by the attacker's chosen repo name).

Condition (2) is a real-world-plausible but not universal precondition, so likelihood is best characterized as **medium**: the vulnerable code path itself is unconditionally reachable from an attacker-controlled deep link, but successful exploitation depends on directory-naming happenstance around the victim's clone layout.

## Recommendation
In `_resolveWithin` (`app/src/lib/path.ts`), replace the bare `startsWith` prefix check with a boundary-anchored comparison, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the correctly-anchored pattern already used elsewhere in the codebase, such as `isClonePathSensitive`'s `clonePath.startsWith(sensitive + Path.sep)` check in `app/src/lib/git/clone.ts` [7](#0-6) , which correctly requires a path separator after the prefix.

## Proof of Concept
1. Victim has two sibling clones under the same parent directory, e.g. `/Users/victim/Documents/GitHub/repo-good` and `/Users/victim/Documents/GitHub/repo-good-internal/secret.txt`.
2. Attacker sends the victim a link: `x-github-client://openrepo?url=<url that resolves to repo-good>&filepath=..%2Frepo-good-internal%2Fsecret.txt`.
3. Desktop parses the URL via `parseAppURL`, producing `filepath = "../repo-good-internal/secret.txt"` (not absolute, so the `isAbsolute` guard does not trigger) [8](#0-7) .
4. `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)` [9](#0-8) .
5. `_resolveWithin` resolves to `/Users/victim/Documents/GitHub/repo-good-internal/secret.txt`; `realResolved.startsWith(realRoot)` evaluates `true` because `"...repo-good-internal/secret.txt".startsWith("...repo-good")` is true as a raw string comparison [10](#0-9) .
6. `shell.showItemInFolder(resolved)` reveals `secret.txt` from the sibling directory, outside `repo-good`.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
