### Title
Division-by-zero panic in KIP-71 dynamic base fee calculation when `GasTarget` governance parameter is 0 - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without checking it is non-zero, unlike its sibling parameter `BaseFeeDenominator`, which is explicitly guarded. Because the `Kip71GasTarget` governance parameter uses a no-op format checker that accepts any `uint64` including `0`, a governance vote ratifying `governance.kip71.gastarget = 0` causes every subsequent block with non-zero gas usage to trigger a `big.Int` division-by-zero panic in header verification, RPC gas-price/fee-history endpoints, and block assembly — crashing all nodes that process the chain. This mirrors the CVE-2017-13735 bug class: an unchecked divisor derived from untrusted/attacker-influenced input reaching an arithmetic division, causing an unconditional crash (DoS).

### Finding Description
`NextMagmaBlockBaseFee` computes the KIP-71 dynamic base fee: [1](#0-0) 

When `parentGasUsed != gasTarget`, the code divides by `gasTarget` (as a `*big.Int`) with no zero-check:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // <-- divide by gasTarget, unguarded
```
This pattern occurs in both the "gas used above target" branch and the "gas used below target" branch. [2](#0-1) 

By contrast, the code explicitly protects against a zero `BaseFeeDenominator`:
```go
if kc.BaseFeeDenominator == 0 {
    // To avoid panic, set the fluctuation range small
    baseFeeDenominator = new(big.Int).SetUint64(64)
}
``` [3](#0-2) 

No equivalent guard exists for `GasTarget`. The governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation and therefore accepts `0`, whereas the adjacent `Kip71BaseFeeDenominator` parameter explicitly rejects `0`: [4](#0-3) 

`GasTarget` flows unchanged from the governance `ParamSet` into `KIP71Config` via `ToKip71Config()`: [5](#0-4) 

`NextMagmaBlockBaseFee` (and its header-validating counterpart `VerifyMagmaHeader`) is invoked by:
- Block header verification for every incoming block: `blockchain/block_validator.go` (imports `kaiax/gov` and calls into KIP-71 verification for Magma headers).
- The public gas-price/fee-history RPC oracle, which is directly reachable by any public RPC caller: [6](#0-5) 
- Block assembly in the miner/worker path (`work/worker.go`), and transaction pool base-fee checks (`blockchain/tx_pool.go`).

Once `GasTarget=0` is ratified via a governance vote and becomes effective (per the standard header-governance ratification flow), any block with non-zero gas usage — i.e., essentially every real block — causes `parentGasUsed > gasTarget(0)` and triggers `x.Div(x, big.NewInt(0))`, which panics in Go's `math/big` package (`Div: division by zero`).

### Impact Explanation
This is not a value-theft bug but an unconditional consensus/liveness-halting crash: since `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` is invoked by all full nodes during block header verification, once the malicious/misconfigured `GasTarget=0` parameter takes effect, every node in the network panics on the very next non-empty block, effectively taking down the entire chain (denial of service to all users, deployers, gasless/auction participants, and RPC callers). It is also independently reachable via the public `eth_feeHistory`/gas price oracle RPC path even before block-level consensus processing occurs, so any public RPC caller querying fee history for a governance-affected block range triggers the node crash directly.

### Likelihood Explanation
The bug requires a single governance vote (`governance_vote` API call from the governing node, in accordance with the `single`/`none` governance modes already supported by the protocol) setting `governance.kip71.gastarget` to `0`. The `FormatChecker` for this parameter is a no-op (`noopFormatChecker`) and does not reject `0`, so nothing in the code path prevents this value from being ratified — in contrast to the neighboring `BaseFeeDenominator` parameter which is explicitly protected. Because parameter ratification through header governance is a documented, first-class mechanism (not an out-of-band bug), and no additional runtime guard exists to protect the division, the likelihood of triggering the panic once the value is set is effectively 100% on the next non-empty block.

### Recommendation
Add a zero-check for `GasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing `BaseFeeDenominator` fallback (e.g., treat `gasTarget == 0` as an error or substitute a safe default), and add an explicit `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, consistent with `Kip71BaseFeeDenominator`.

### Proof of Concept
1. As the governing node, cast `governance_vote("kip71.gastarget", 0)`; since `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, the vote is accepted and, following normal epoch ratification, `GasTarget=0` becomes the effective parameter.
2. On the first subsequent block where `parentGasUsed != 0` (virtually guaranteed), `NextMagmaBlockBaseFee` executes the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(0))`.
3. `math/big.Int.Div` panics with "division by zero"; because this function is invoked from `VerifyMagmaHeader` in header validation (`blockchain/block_validator.go`), every full node processing that block panics, and the gas-price oracle (`node/cn/gasprice/feehistory.go`) panics identically when serving `eth_feeHistory` for the same range — producing a network-wide denial of service.
