### Title
Post-mint acknowledgement override on failed native-ERC20 conversion enables IBC double-credit - (File: `x/erc20/ibc_middleware.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`x/erc20`'s ICS20 middleware executes the core transfer module's `OnRecvPacket` first (which mints/unescrows Cosmos coins to the recipient and returns a **success** acknowledgement), and only afterwards attempts an auxiliary Coin→ERC20 auto-conversion. If that auxiliary conversion fails, the middleware discards the already-successful ack and substitutes an **error acknowledgement**, without reverting the coin credit that the core transfer module already committed to the same (uncached) context.

### Finding Description
The transfer stack is composed as `transfer.NewIBCModule -> erc20.NewIBCMiddleware -> ibccallbacks.NewIBCMiddleware`, and `RecvPacket` flows `channel.RecvPacket -> callbacks.OnRecvPacket -> erc20.OnRecvPacket -> transfer.OnRecvPacket`, as documented in the wiring comment: [1](#0-0) .

In `IBCMiddleware.OnRecvPacket`, the underlying (core ICS20) `OnRecvPacket` is invoked first, on the **same, non-cached** `ctx`, which performs the standard unescrow/mint that credits the recipient's bank balance and returns a success acknowledgement: [2](#0-1) 

Only if that first call succeeds does the code call `k.OnRecvPacket`, which attempts to auto-convert the newly-credited Cosmos coin into its native ERC20 representation via `ConvertCoinNativeERC20`. If this conversion call fails for any reason — the `MintingEnabled` check errors, or the EVM `transfer` call to the registered native-ERC20 contract fails/reverts/underdelivers — the function returns `channeltypes.NewErrorAcknowledgement(err)`: [3](#0-2) 

Nothing in this path reverts the state changes made by the earlier, already-committed transfer `OnRecvPacket` call (no `ctx.CacheContext()`/`writeFn()` pattern is used here, unlike other flows in the codebase such as the IBC callbacks keeper which explicitly uses `ctx.CacheContext()` + `writeFn()` to gate commits: [4](#0-3) ). The function-level doc comment even acknowledges the mismatch is by design for a different case ("if conversion fails ... the user will receive the bank token instead") [5](#0-4) , but that reasoning does not hold once the returned acknowledgement is downgraded to an *error* ack rather than a success ack.

Per IBC semantics, an error acknowledgement written on the receiving chain instructs the sending chain, upon relaying that acknowledgement, to refund/unescrow the originally-sent tokens back to the sender. Consequently:
- The receiving chain (this chain) has already durably credited the recipient's bank balance with the transferred coin (from the core `transfer.OnRecvPacket` mint/unescrow, which was never rolled back).
- The sending chain, upon seeing the error ack, will refund the same amount to the original sender.

This directly matches the bug class in the external report: forwarding an operation across a trust boundary (here, the ICS20 core commit vs. the auxiliary ERC20-conversion step) without keeping accounting consistent when the second step fails — except here the failure mode duplicates value rather than losing it.

The trigger requires only an unprivileged action: registering (or already having registered, e.g. via governance or if `PermissionlessRegistration` is enabled — see `RegisterERC20`, `x/erc20/keeper/msg_server.go:324-362`) a "native ERC20" token pair whose contract can be made to fail a `transfer` call on demand (e.g. pausable/blacklistable/self-destructing/fee-reverting token, or the `MintingEnabled` send-enabled check being toggled off for the denom via `x/bank`'s `SetSendEnabled`, which the test suite in `evmd/tests/ibc/ibc_middleware_test.go` demonstrates is used to force this exact failure path), then relaying an inbound IBC transfer of that coin.

### Impact Explanation
This falls under the "Critical unauthorized minting/duplication of spendable user value across IBC escrows" impact category. An attacker can cause the receiving chain to durably credit a recipient with bank coins while simultaneously causing the sending chain (upon relay of the resulting error ack) to refund the sender the equivalent amount, producing a net duplication of value across the two chains that participate in the channel — a supply/escrow-accounting corruption analogous to the "financial contract receives less than expected without adjusting total_ton_supply" pattern in the seed report, but inverted into a double-credit rather than a shortfall.

### Likelihood Explanation
Reachable by any unprivileged user who can (a) get a native-ERC20 token pair registered whose ERC20 contract can conditionally fail transfers (achievable permissionlessly if `PermissionlessRegistration` is enabled, or by using an already-registered pair and toggling a condition such as `SendEnabled=false` for the coin, which the middleware test suite already exercises as a way to force the `ConvertCoinNativeERC20` failure branch), and (b) send/relay an ordinary IBC transfer. No validator, relayer, or governance collusion is required beyond normal permissionless message submission and packet relaying.

### Recommendation
Perform the auxiliary Coin→ERC20 auto-conversion inside a `ctx.CacheContext()` (as already done elsewhere in this codebase, e.g. `x/ibc/callbacks/keeper/keeper.go`), and only call `writeFn()` (committing the conversion's own state changes) when it succeeds. Regardless of conversion success/failure, once the core transfer `OnRecvPacket` has already committed a mint/unescrow, the final acknowledgement returned up the middleware stack must remain a **success** acknowledgement — conversion failures should only cause the recipient to keep the plain bank coin (as the doc comments intend), never downgrade a completed, committed transfer into an error ack that triggers a source-chain refund.

### Proof of Concept
1. Governance (or a permissionless caller, if `PermissionlessRegistration=true`) registers a native ERC20 token pair for a contract that the attacker controls (or an existing pair for a coin whose bank `SendEnabled` flag can be toggled/exploited to force `MintingEnabled`/`ConvertCoinNativeERC20` to fail).
2. Attacker (or any user) initiates an ICS20 transfer of that coin from chain B to chain A (the Cosmos EVM chain).
3. On chain A, `channel.RecvPacket` invokes the transfer stack: `ibccallbacks.OnRecvPacket -> erc20.IBCMiddleware.OnRecvPacket -> transfer.OnRecvPacket`. The core `transfer.OnRecvPacket` succeeds, unescrowing/minting the coin to the recipient's bank balance in `ctx` and returning `ack.Success() == true` (`x/erc20/ibc_middleware.go:59-64`).
4. `erc20.IBCMiddleware.OnRecvPacket` then calls `k.OnRecvPacket` (`x/erc20/keeper/ibc_callbacks.go:35-154`), which reaches Case 2 (`found && pair.IsNativeERC20()`), and the attacker arranges for either `MintingEnabled` or `ConvertCoinNativeERC20` to fail (e.g., the underlying token contract reverts on `transfer`, or `SendEnabled` for the denom is `false`).
5. The keeper returns `channeltypes.NewErrorAcknowledgement(err)` (`x/erc20/keeper/ibc_callbacks.go:134,138`), overriding the previously successful ack, while the bank credit from step 3 remains committed in state (there is no cache-context rollback of that earlier mint).
6. `WriteAcknowledgement` records this error ack on chain A. When chain B processes the acknowledgement (`OnAcknowledgementPacket` with an `Acknowledgement_Error`), it refunds the original sender the full transferred amount.
7. Net effect: the recipient on chain A holds the credited bank coin, and the sender on chain B also has the funds refunded — the same value now exists (spendable) on both sides of the channel, an unauthorized duplication of user value.

Note: I was unable to fully trace the exact IBC-go v10 core `channel.RecvPacket` handler logic (whether it independently ever branches/reverts state for a returned error ack) within the indexed portion of this repository, since ibc-go is largely a vendored dependency and its `RecvPacket` implementation was not found in the indexed files; if a Devin session confirms ibc-go's `RecvPacket` handler always writes whatever module state changes occurred regardless of the ack's success value (which matches documented ibc-go behavior — the app module, not core IBC, is responsible for reverting on failure), this finding stands as described.

```go
func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
```
