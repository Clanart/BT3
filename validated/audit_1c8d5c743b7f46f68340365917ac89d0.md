### Title
`ExtrinsicIntents.onAccept` authorizes governance-only actions (upgrade / param-update / dust-sweep / deployment) by checking only the request's `source` chain id, not the sender module (`request.from`) — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The Nayms report's root cause was that the two-phase diamond-cut approval bound the "allowed" state to only part of the execution parameters (the `_diamondCut` hash), leaving `_init`/`_calldata` completely unconstrained, so anyone able to trigger an approved cut could redirect execution to an arbitrary contract. `ExtrinsicIntents.onAccept` in the IntentGatewayV2 has the same structural gap: for the set of "Hyperbridge-only" governance actions (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`) the authorization check validates only the coarse `request.source` field (the origin chain id string) and never validates `request.from` (the specific sending module/pallet address on that chain) — unlike the `RedeemEscrow`/`RefundEscrow` path, which explicitly calls `_authenticate()` to bind `request.from` to the registered gateway instance.

### Finding Description
In `onAccept`: [1](#0-0) 

```
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        _authenticate(incoming.request);
        ...
    }
    // only hyperbridge is permitted to perform these actions
    if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
    if (kind == RequestKind.NewDeployment) {
        _addDeployment(...);
    } else if (kind == RequestKind.UpdateParams) {
        _updateParams(...);
    } else if (kind == RequestKind.SweepDust) {
        _sweepDust(...);
    } else if (kind == RequestKind.UpgradeContract) {
        (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
        ERC1967Utils.upgradeToAndCall(newImpl, initData);
    }
}
```

Compare this to the withdrawal path's authentication, which binds to the actual sending module address: [2](#0-1) 

`_authenticate` checks `request.from` (the 20-byte module address) against the registered gateway `_instance` for that source chain — i.e., it binds authorization to *who* sent the message, not just *which chain* it came from.

The governance branch skips this: it only checks `request.source` equals the configured Hyperbridge state-machine identifier (a chain id such as `"POLKADOT-1000"`), a coarse per-chain string, and never checks `request.from`. Because `StateMachine`/`source` identifies an entire chain rather than a specific pallet/contract, this check does not prove the request actually originated from the trusted governance/coprocessor pallet on that chain — any code capable of dispatching an ISMP POST request from the Hyperbridge relay chain with `source` set to the hyperbridge id can produce a message that satisfies this check. This is the same broken invariant pattern as the Nayms bug: the "authorized" predicate (here, "source chain == hyperbridge") does not cover all the fields relevant to trust (`from`), leaving a gap through which arbitrary privileged execution (`UpgradeContract` → `ERC1967Utils.upgradeToAndCall(newImpl, initData)`, `SweepDust` → arbitrary beneficiary sweep, `UpdateParams` → arbitrary fee/admin/oracle rewrite) can be reached without validating the specific authorized sender.

`ERC1967Utils.upgradeToAndCall` is the closest direct analog to the diamond cut's `_init`/`_calldata` delegatecall: it sets the proxy implementation to an attacker-chosen `newImpl` and (if `initData` is non-empty) executes it via delegatecall against the proxy's own storage — this can rewrite `_filled`, `_orders`, `_admin`, or any other storage slot in the gateway.

### Impact Explanation
If this check can be satisfied without the actual governance/coprocessor pallet ("wrong module bindings" per the bounty pivot), an attacker can:
- Force `UpgradeContract` to point the gateway proxy at malicious bytecode and run arbitrary `initData` via delegatecall against the proxy's storage, corrupting `_filled`/`_orders` and draining/duplicating escrowed funds.
- Force `SweepDust` to drain accumulated dust balances to an attacker beneficiary.
- Force `UpdateParams`/`NewDeployment` to redirect protocol fee, oracle, or peer-gateway bindings to attacker-controlled addresses, enabling subsequent order-fill/escrow manipulation.

This falls squarely under "unauthorized execution / transaction manipulation / false state acceptance via wrong module binding," matching the bounty's explicit pivot on cross-chain admin effects reachable through wrong module bindings.

### Likelihood Explanation
This is a structural code gap, not a hypothetical: the check that is present for asset-moving requests (`_authenticate` on `request.from`) is conspicuously absent for admin-moving requests, which is exactly the class of bug the Nayms report describes (authorization bound to an incomplete/coarser identifier than the executed action requires). Full exploitability depends on whether any component able to dispatch an ISMP POST tagged with `source == hyperbridge` other than the trusted coprocessor pallet exists on the relay chain; that dispatch-origin surface could not be fully enumerated from the indexed code, so this should be verified against the complete set of pallets/precompiles that can invoke `IsmpDispatcher::dispatch_request` on the Hyperbridge relay chain.

### Recommendation
Bind the governance-action check to the specific expected sender module, not just the source chain id — e.g., compare `request.from` against a stored coprocessor/pallet address (analogous to `_instance` binding used in `_authenticate`), mirroring the Nayms fix of hashing/validating *all* parameters relevant to trust rather than a subset.

### Proof of Concept

2. Craft `body = bytes.concat(bytes1(uint8(RequestKind.UpgradeContract)), abi.encode(maliciousImpl, initCalldata))` targeting a deployed `IntentGatewayV2` instance as `to`.

Once relayed and proven through the host (`onlyHost` only requires a valid Hyperbridge state proof for the message, not sender-specific validation beyond `source`), `onAccept` passes the `source == hyperbridge` check and calls `ERC1967Utils.upgradeToAndCall(maliciousImpl, initCalldata)`, executing attacker logic against the gateway's storage.
