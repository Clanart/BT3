### Title
Unbounded recursive RLP decoding of AccountKeyRoleBased causes stack-exhaustion DoS on any account-creation/account-update transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
An unprivileged transaction sender (or anyone submitting a raw transaction via `eth_sendRawTransaction`/`klay_sendRawTransaction` or the P2P tx-pool ingress) can craft a `TxTypeAccountCreation` or `TxTypeAccountUpdate` transaction whose `Key` field is a deeply, self-nested `AccountKeyRoleBased` structure. Decoding this transaction recursively invokes `AccountKeyRoleBased.DecodeRLP` with no depth limit, which can exhaust the goroutine stack, crashing or hanging the node — the same bug class as ALPINE-CVE-2018-6544 (`pdf_load_obj_stm` recursively referencing itself and exhausting the error stack before any semantic validation occurs).

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an arbitrary list of sub-key blobs and, for each element, calls `rlp.DecodeBytes` on a fresh `AccountKeySerializer`, which in turn calls `NewAccountKey` + `s.Decode(serializer.key)` — and if that sub-key is itself `AccountKeyTypeRoleBased`, this recurses back into `AccountKeyRoleBased.DecodeRLP`: [1](#0-0) [2](#0-1) 

Nothing in the decode path enforces a nesting-depth limit. The only place that rejects nested role-based keys is `CheckInstallable`, which returns `kerrors.ErrNestedCompositeType` for a composite sub-key type: [3](#0-2) 

Critically, this check runs *after* the transaction (and its `Key` field) has already been fully RLP-decoded — decoding is a prerequisite step performed unconditionally whenever a raw transaction bytes are parsed by `types.Transaction`/`TxInternalDataAccountCreation`/`TxInternalDataAccountUpdate`, well before `CheckInstallable`/`Validate`/tx-pool admission logic runs: [4](#0-3) 

The existing test suite only demonstrates that a **single level** of nesting is rejected at the validation stage (`TestAccountUpdateRoleBasedKeyNested`, expecting `kerrors.ErrNestedCompositeType` from `txpool.AddRemote`/block application): [5](#0-4) 

but that rejection happens *after* decode, so it does nothing to bound the decode-time recursion itself. An attacker can nest `AccountKeyRoleBased{ AccountKeyRoleBased{ AccountKeyRoleBased{ ... } } }` to an arbitrary depth (each level only costs a few RLP list bytes), and the recursive `DecodeRLP`/`rlp.DecodeBytes` calls will consume stack frames proportional to nesting depth with no cap. The generic `rlp` package itself also has no recursion-depth guard for `Decoder`-implementing types (confirmed: no `maxDepth`/recursion-limit constants exist in `rlp/decode.go`), so the only potential bound would have to come from the `accountkey` package, and it does not provide one at decode time.

### Impact Explanation
A stack-exhaustion crash reachable from a single, cheaply-constructed transaction submitted through public RPC (`eth_sendRawTransaction`) or gossiped through the tx pool is a concrete denial-of-service: it can crash or hang any full node/validator that attempts to decode the transaction (during tx-pool admission, block building, or block execution), potentially affecting multiple honest nodes simultaneously if the malicious transaction propagates before validation short-circuits it. This satisfies the "state divergence between honest nodes" / DoS class explicitly in scope.

### Likelihood Explanation
The attack requires no special privileges, no valid signature verification bypass, and no prior account state — an attacker only needs to submit raw bytes representing a syntactically valid, deeply nested `AccountKeyRoleBased` RLP blob as the `Key` field of an `AccountCreation` (or `AccountUpdate`/fee-delegated variants) transaction. The transaction does not even need to be executable or pass signature checks first, because RLP decoding of the `Key` occurs as part of basic transaction deserialization before any semantic checks; a large batch of moderate-nesting-depth transactions (or even one very deep one) is straightforward to construct offline.

### Recommendation
Enforce a maximum recursion/nesting depth for `AccountKeyRoleBased` decoding directly inside `AccountKeyRoleBased.DecodeRLP` (and/or in `AccountKeySerializer.DecodeRLP`), rejecting any sub-key whose type is itself `AccountKeyTypeRoleBased` (or otherwise limiting total decode depth) at decode time rather than only at `CheckInstallable`/pool-admission time. Consider adding a general recursion-depth counter to the `rlp` package's `Decoder`-dispatch path (`decodeDecoder`) to bound arbitrary custom recursive decoders.

### Proof of Concept
Conceptually (mirrors the structure already validated as reachable in `TestAccountUpdateRoleBasedKeyNested`, but nested many levels instead of one):
```go
// Build N-deep nested AccountKeyRoleBased
var key accountkey.AccountKey = accountkey.NewAccountKeyLegacy()
for i := 0; i < N; i++ { // N chosen large enough to exhaust the goroutine stack
    key = accountkey.NewAccountKeyRoleBasedWithValues([]accountkey.AccountKey{key})
}
ser := accountkey.NewAccountKeySerializerWithAccountKey(key)
encodedKey, _ := rlp.EncodeToBytes(ser) // small, cheap payload despite deep nesting

// Embed encodedKey as the Key field of TxTypeAccountCreation/TxTypeAccountUpdate,
// RLP-encode the full transaction, and submit it via eth_sendRawTransaction or
// gossip it to txpool.AddRemote. Decoding recurses N times in
// AccountKeyRoleBased.DecodeRLP before ErrNestedCompositeType can ever be raised.
```
This reaches `accountkey.NewAccountKeySerializer()` / `rlp.DecodeBytes(b, &serializer)` recursively at [6](#0-5) , with no depth cap prior to that recursive call chain.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
