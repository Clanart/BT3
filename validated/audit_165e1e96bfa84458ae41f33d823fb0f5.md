### Title
Attacker-controlled `t`/`n` values cause quadratic-time Lagrange interpolation during `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts serialized `t`, `n`, and participant-index values bounded only by `u16`, then calls `ThresholdKeys::new`, which derives the group key by evaluating every Lagrange factor for participants `1..=t`. [1](#0-0)  For Lagrange keys, each factor evaluation iterates over the entire `t`-sized participant list, making key deserialization require `O(t²)` scalar multiplication and inversion work. [2](#0-1) [3](#0-2) 

### Finding Description
`ThresholdParams::new` permits `t == n == u16::MAX`, provided `i <= n`, so a serialized key may declare 65,535 participants without violating parameter validation. [4](#0-3)  `ThresholdKeys::read` then reads `n` public verification shares and immediately invokes `ThresholdKeys::new`. [5](#0-4) 

Inside `ThresholdKeys::new`, the group key calculation evaluates `interpolation_factor` once for each of the `t` participants. [2](#0-1)  Under `Interpolation::Lagrange`, every evaluation loops over all `t` participant IDs, updates a numerator and denominator for each, and performs a field inversion. [3](#0-2)  A roughly 2 MiB serialized key can therefore force approximately `65,535²` field operations and 65,535 field inversions during a single parse.

### Impact Explanation
An unprivileged party that can cause a node or service to deserialize an attacker-supplied `ThresholdKeys` blob can make the host perform billions of scalar operations before returning. This is a sustained CPU denial of service analogous to the referenced optimizer DoS: validly shaped input reaches an unexpectedly expensive internal computation and can repeatedly stall the executing task or process. [6](#0-5) [2](#0-1) 

The primitive fields do not need to be malformed or non-canonical; all point and scalar encodings may be valid. The resource exhaustion is caused by accepting a serialized committee size and evaluating Lagrange coefficients naively before any caller-enforced committee limit can apply. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
`ThresholdKeys::read` is an untrusted-byte parser explicitly exposed by the in-scope DKG crate, and the trigger requires only a complete, well-formed serialized Lagrange key. [9](#0-8)  No invalid participant index is needed: `Participant::new` rejects zero, but every value from `1` through `65535` is representable and accepted when `n` is `65535`. [10](#0-9) [8](#0-7) 

The payload size is only about `32 + 65,535` point encodings plus headers and the secret share, so it is small enough to submit repeatedly in systems that accept serialized threshold state or recovery material.

### Recommendation
Reject protocol-implausible `t`/`n` values during deserialization before allocating vectors or evaluating interpolation, preferably enforcing a configurable or consensus-defined maximum committee size. [1](#0-0)  For legitimate large committees, avoid the nested Lagrange calculation when deriving the same product for every participant by incrementally maintaining numerator/denominator products or calculating the group key through a cheaper committed representation. [11](#0-10) 

### Proof of Concept
The following payload is syntactically valid for `Secp256k1` and reaches the quadratic group-key derivation without corrupting any scalar or point encoding. [12](#0-11) [6](#0-5) 

```rust
use ciphersuite::{group::GroupEncoding, Ciphersuite};
use dkg::ThresholdKeys;
use frost::curve::Secp256k1;

fn quadratic_threshold_keys_parse() {
    let n = u16::MAX;
    let mut serialized = Vec::new();

    // Curve ID checked by ThresholdKeys::read.
    serialized.extend_from_slice(
        &(u32::try_from(Secp256k1::ID.len()).unwrap()).to_le_bytes(),
    );
    serialized.extend_from_slice(Secp256k1::ID);

    // t, n, i: all valid under ThresholdParams::new.
    serialized.extend_from_slice(&n.to_le_bytes());
    serialized.extend_from_slice(&n.to_le_bytes());
    serialized.extend_from_slice(&1u16.to_le_bytes());

    // Interpolation::Lagrange.
    serialized.push(1);

    // secret_share.
    serialized.extend_from_slice(Secp256k1::F::ONE.to_repr().as_ref());

    // n canonical verification shares.
    let point = Secp256k1::generator().to_bytes();
    for _ in 0..n {
        serialized.extend_from_slice(point.as_ref());
    }

    // Before returning, ThresholdKeys::new computes 65,535 Lagrange factors,
    // each iterating over 65,535 participant IDs.
    let _ = ThresholdKeys::<Secp256k1>::read(&mut serialized.as_slice());
}
```

impl<F: Zeroize + PrimeField> Interpolation<F> {
  /// The interpolation factor for this participant, within this signing set.
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
