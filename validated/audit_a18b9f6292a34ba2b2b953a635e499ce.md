### Title
`HftError::ErcDecimalsBelowLocal` invariant is checked only at registration time, not enforced at mint time — a later local-asset decimals change silently disables downscaling and inflates cross-chain mints - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s inbound message handler (`on_accept`) converts an incoming EVM `Message.amount` (expressed at the remote ERC20's decimal precision) into the local Substrate balance via `convert_to_balance`, which computes `value / 10^(erc_decimals.saturating_sub(local_decimals))` [1](#0-0) . The only place the protocol guarantees `erc_decimals >= local_decimals` (so the subtraction never floors to zero and the amount is correctly scaled down) is in `register_token`/`update_token`, which check the *current* value returned by `fungibles::metadata::Inspect::decimals` at configuration time [2](#0-1) . `on_accept` re-reads `decimals` live from the same `Inspect` trait on every inbound message rather than using a value pinned at registration [3](#0-2) . This is the exact analog of the M-3 IchiLpOracle bug: a decimal-scaling calculation whose invariant is checked once, informally, but not re-validated at the point where the value directly drives a fund-moving operation.

### Finding Description
`convert_to_balance` uses `erc_decimals.saturating_sub(local_decimals)` as the divisor exponent [1](#0-0) . `saturating_sub` floors to `0` instead of underflowing when `local_decimals > erc_decimals`, meaning `10^0 = 1` and **no downscaling is applied at all** — the raw ERC20-precision `U256` amount (potentially many orders of magnitude larger than intended) is parsed directly into the local `Balance` type and then minted or transferred to the beneficiary [4](#0-3) .

The pallet only prevents `local_decimals > erc_decimals` at the moment `register_token`/`update_token` is called, via `ensure!(config.decimals >= local_decimals, ErcDecimalsBelowLocal)` [5](#0-4) . That check reads `local_decimals` from `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(...)` at that instant — it does **not** snapshot/store this value; `Precisions` storage only records `erc_decimals` (the remote precision), not `local_decimals` [6](#0-5) . Since local asset metadata (decimals) lives in `pallet-assets` and can be altered independently of `pallet-hyper-fungible-token` (e.g. via `pallet-assets::set_metadata`, which is typically controlled by the asset's own admin/owner — a role distinct from and not necessarily coordinated with this pallet's `CreateOrigin`), a later increase to the local asset's decimals value invalidates the invariant that was only checked once at registration time. From that point forward, every `on_accept` for that asset computes `erc_decimals.saturating_sub(local_decimals) == 0`, and the division that should scale the ERC20 amount down to the local (now higher) precision silently becomes a no-op, inflating every subsequent minted/transferred amount by `10^(local_decimals - erc_decimals)`.

### Impact Explanation
This directly causes the exact class of harm required by the impact gate: unauthorized minting / loss-of-funds through false amount acceptance. Since the pallet either mints new supply (`Assets::mint_into`) or releases custodied native/escrowed funds (`NativeCurrency::transfer` / `Assets::transfer` from `pallet_account()`) using the corrupted `amount` value, an inbound message for even a tiny genuine EVM-side transfer would mint/release an amount inflated by orders of magnitude, draining the pallet's custody account (for native/custodied assets) or creating unbacked new supply (for mint/burn assets). The same broken invariant also affects `on_timeout` refunds, which reuse `convert_to_balance` with the same decimals lookup [7](#0-6) .

### Likelihood Explanation
The trigger does not require a malicious relayer, prover, or governance actor of *this* pallet — it only requires the local asset's decimals metadata (owned by `pallet-assets`, a separate, commonly-more-permissive admin surface) to change after the token was registered here, which is a routine maintenance action unrelated to bridge security assumptions. No code path re-validates the `erc_decimals >= local_decimals` invariant against the live decimals value before scaling; the only gate is a one-time check at `register_token`/`update_token`, and it silently goes stale.

### Recommendation
Store `local_decimals` in the `Precisions` map (or a parallel map) at `register_token`/`update_token` time instead of re-reading `Inspect::decimals()` on every `on_accept`/`on_timeout`/`send` call, so the enforced invariant (`erc_decimals >= local_decimals`) always matches the decimals actually used for conversion. Alternatively, re-validate `erc_decimals >= local_decimals` inside `convert_to_balance`/`convert_to_erc20` and hard-fail (reject the message / hold the mint) rather than silently saturating to a zero exponent.

### Proof of Concept
1. Governance registers asset `X` via `register_token` with `erc_decimals = 6` on `EVM-1`; at that time `Assets::decimals(X) == 6`, so the `ErcDecimalsBelowLocal` check passes and `Precisions[X][EVM-1] = 6` is stored.
2. Later, the asset's admin (via `pallet-assets::set_metadata`, independent of this pallet) updates asset `X`'s decimals to `18` for display/precision reasons.
3. A user sends `1` unit of `X` (6-decimals precision) worth of value from the EVM `HyperFungibleToken` contract; the ISMP message carries `amount` encoded in the ERC20 contract's own decimal precision.
4. `on_accept` on Substrate calls `convert_to_balance(amount, erc_decimals=6, local_decimals=18)`. Since `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0`, the divisor is `10^0 = 1`, so the full raw ERC20-precision `amount` (already scaled to what would be 1e6-equivalent) is parsed directly as the local balance — effectively a `10^12`-times over-mint relative to the intended, correctly-scaled amount [1](#0-0) .
5. `on_accept` mints/transfers this inflated `amount` to the beneficiary [8](#0-7) , draining custody or creating unbacked supply.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
