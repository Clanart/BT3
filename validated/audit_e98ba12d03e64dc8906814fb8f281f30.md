## Finding

### Title
Unverified `Signature.signer()` extraction lets an attacker forge the delivery-receipt identity used for relayer fee/reward payout - ([File: modules/pallets/ismp/src/host.rs], [File: modules/pallets/relayer/src/accumulate.rs])

### Summary
The external report's core broken invariant is: a public key is accepted as authoritative *without* being cryptographically bound to the signature/private key that is supposed to prove it — a decoupled "keypair" used as an oracle. The same primitive exists in Hyperbridge's relayer-identity extraction path: `Signature::signer()` returns the embedded `public_key`/`address` field of a `Signature` value with **no call to `Signature::verify`**, so the "identity" recorded for a delivery is an unauthenticated claim, not a proven one.

### Finding Description
`crypto_utils::verification::Signature` has two distinct methods:
- `verify(msg, public_key_op)` — cryptographically checks the signature and only then returns the signer.
- `signer()` — simply extracts the embedded `public_key`/`address` field, doing **no cryptographic check at all**: [1](#0-0) 

Two production call sites use `.signer()` instead of `.verify()` to derive the identity that is later trusted for fund flow:

1. `extract_signer` in the ISMP host pallet, which decodes a message's raw `signer` bytes as a `Signature` and calls `.signer()` when the bytes are longer than 32 (i.e. a SCALE-encoded `Signature`, not a raw 32-byte key): [2](#0-1) 

2. `decode_receipt_relayer` in `pallet-relayer`, used by both the fee-accumulation path (`accumulate.rs`) and the outbound-request delivery-reward path (`outbound_request.rs`), which decodes the value proven at `RequestReceipts[commitment]` on a substrate destination the same unverified way: [3](#0-2) 

Because `store_request_receipt`/`extract_signer` never validates the signature bytes embedded in the `Signature` enum, whoever controls the `signer` field of the ISMP delivery message (or any byte blob later stored as a receipt value) can embed **any public key they choose, paired with arbitrary/garbage signature bytes**, and it will be accepted and persisted on-chain as the proven "delivering relayer" identity — with zero cryptographic cost.

This value is later trusted downstream as `delivered_by`/the fee-accumulation `address`, which both `accumulate` (fee crediting) and `process_outbound_request_delivery_claim` (treasury-funded reward) use as ground truth: [4](#0-3) 

The final gate in the claim path (`recovered == delivered_by`) *is* a real `Signature::verify`, but since `delivered_by` is itself an unauthenticated value the attacker chose at receipt-write time, the attacker trivially satisfies it by signing with the same keypair they embedded — the "double public key" pattern from the report: the value that should have been bound by a real signature never was, so it can be freely substituted by whoever controls the message envelope.

### Impact Explanation
`RequestReceipts` is the single source of truth for "who delivered this request" across:
- `pallet-relayer`'s fee accumulation (`accumulate.rs`, pays out `Fees[state_machine][address]`),
- the outbound-request delivery-reward claim (`outbound_request.rs`, pays BRIDGE from the treasury PalletId account),
- replay/duplicate-delivery protection for `on_accept` execution (`modules/ismp/core/src/handlers/request.rs:108`).

Since the identity written into this receipt is an unauthenticated `.signer()` extraction rather than a verified signature, the binding between "the account that actually delivered/authorized the delivery" and "the account credited/paid" is broken. This corrupts the beneficiary of relayer fees and treasury-funded delivery rewards — falling squarely under "unauthorized transaction... wrong beneficiary or amount" in the impact gate.

### Likelihood Explanation
The `signer` field of an ISMP message is attacker/relayer-controlled input on a permissionless, unsigned (`ensure_none`) extrinsic path, so no privileged actor, admin, or malicious-relayer assumption is required — any party able to submit an ISMP request-delivery message can shape the stored `signer` bytes. The decode-then-`.signer()` pattern is repeated in two independent modules (`host.rs`, `accumulate.rs`), indicating it is the standard (but flawed) idiom used throughout the relayer-identity code, not a one-off typo.

### Recommendation
Replace every `Signature::decode(..).signer()` call used for identity attribution with `Signature::verify(&msg, None)` (or an explicit variant that both decodes and cryptographically validates before returning the identity), binding the recorded receipt identity to an actual proof of signature validity, exactly as `ed25519-dalek` v2's revised API forbids decoupled public-key/signature assembly outside explicitly labeled "hazmat" paths. At minimum, `extract_signer` and `decode_receipt_relayer` must require `signature.verify(msg, None)` to succeed against the actual signed payload used when the message was submitted, not just decode the struct and trust its embedded key field.

### Proof of Concept
Not independently executable from the indexed context (no unit/integration test harness for `pallet-ismp`'s message-submission path was retrieved), but the code trace is:
1. Attacker submits an unsigned ISMP request-delivery message where `msg.signer` is `Signature::Sr25519 { public_key: ATTACKER_KEY, signature: [0u8; 64] }` (garbage signature).
2. `store_request_receipt` → `extract_signer(&msg.signer)` decodes the `Signature` and calls `.signer()`, returning `ATTACKER_KEY` with the garbage signature never checked: [2](#0-1) 
3. `RequestReceipts[commitment] = ATTACKER_KEY` is persisted and later state-proven.
4. Attacker builds `OutboundRequestDeliveryClaim`/`WithdrawalProof`; `decode_receipt_relayer` re-extracts `ATTACKER_KEY` via `.signer()` (again unverified): [3](#0-2) 
5. Attacker signs `outbound_request_delivery_message(commitment, destination, payee)` with the real private key for `ATTACKER_KEY` (which they generated themselves), satisfying `recovered == delivered_by`: [5](#0-4) 
6. Treasury funds/relayer fees are paid to the attacker-chosen `payee`, with the on-chain "proof of delivery" identity never having been cryptographically authenticated.

Given index size limits, the exact call site of `extract_signer` inside `store_request_receipt` (to confirm the full invocation chain) was not directly retrievable; a Devin session with full repository access should confirm this wiring before remediation.

fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
