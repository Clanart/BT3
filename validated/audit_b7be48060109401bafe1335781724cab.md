### Title
Manual conflict resolutions persist across distinct rebase/cherry-pick steps for the same file path, silently corrupting what gets committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
The reported Venus bug is fundamentally about a stale, previously-computed decision (`pendingScoreUpdates` / a user's frozen score) being carried forward and applied to a *new* state it was never actually evaluated against, because the invariant "this cached decision is still valid" is not re-checked before reuse. The GitHub Desktop analog is `updateConflictState()` in `app/src/lib/stores/updates/changes-state.ts`, which reuses the `manualResolutions` map (keyed only by file `path`) across successive `git status` polls whenever the conflict `kind` (`merge`/`rebase`/`cherryPick`) stays the same, without verifying that the underlying conflict content at that path is the same conflict the user actually resolved.

### Finding Description
`updateConflictState` computes the new conflict state like this: [1](#0-0) 

The `manualResolutions` map is carried over from `prevConflictState` unconditionally as long as the conflict kind is preserved (merge→merge or rebase→rebase), and is only reset when the kind actually changes (e.g., merge↔rebase) or the conflict clears entirely: [2](#0-1) 

The map is keyed purely by relative file `path` (`Map<string, ManualConflictResolution>`), not by blob SHA, commit, or conflict identity. During a multi-commit rebase or cherry-pick of a series of commits from an attacker-controlled remote, each commit that touches the same path produces a *new, independent* conflict at that path with different `ours`/`theirs` content. Because `RebaseConflictState`/`CherryPickConflictState` only change `currentTip`/target info between commits while remaining the same `kind`, the user's earlier choice (e.g. "theirs" for commit N's conflict on `config.json`) is silently reapplied to commit N+1's unrelated conflict on the same path, via `stageManualConflictResolution` which picks the file based purely on the resolution enum, not on re-inspecting the new conflict markers: [3](#0-2) 

This mirrors the Venus flaw exactly: a decision computed under one state (`pendingScoreUpdates` value / one conflict's content) is blindly reused for a materially different subsequent state (score after alpha change / a different commit's conflict) because the code only checks a coarse-grained "kind" match, not the specific identity of what was resolved.

### Impact Explanation
An attacker who controls the upstream repository/branch being rebased or cherry-picked onto (a git remote fully under attacker control, satisfying the "unprivileged... attacker controls a cloned/fetched repository" criterion) can craft a multi-commit series where two commits touch the same file path with conflicting-but-different content. If the user (or the app's UI, which shows resolved files as "resolved" without requiring re-review — see `renderResolvedFile`/`renderBanner` in `app/src/ui/lib/conflicts/unmerged-file.tsx` and `app/src/ui/multi-commit-operation/dialog/conflicts-dialog.tsx`) picks "theirs" once, subsequent unrelated conflicts at the same path in later commits of the same rebase/cherry-pick will be auto-staged with the stale resolution, without the user reviewing the actual new content. This can result in the wrong content (attacker-chosen "theirs" from an earlier commit, or stale "ours" content) being silently committed and later pushed — i.e., silent corruption of what the user commits, at the expense of the user's intent, matching the "silent corruption of what the user commits or pushes" impact category. [4](#0-3) 

### Likelihood Explanation
This requires the user to be rebasing/cherry-picking a series of commits from an attacker-influenced branch/remote (a normal, unprompted-by-attacker workflow: rebasing onto a malicious fork/PR branch, or cherry-picking commits proposed by an untrusted contributor) and touching the same path across multiple conflicting commits — a realistic scenario for any multi-commit rebase workflow. No local/admin access, no leaked credentials, and no unnatural steps are required beyond the normal act of resolving conflicts during a rebase, which GitHub Desktop explicitly supports and encourages via its guided-conflict UI. However, this could not be fully verified end-to-end (e.g., whether the rebase/cherry-pick continuation flow ever explicitly clears `manualResolutions` between individual commit steps) because the relevant rebase continuation call sites in `app-store.ts` could not be inspected in the time available — this is a gap that should be verified before treating this as fully confirmed.

### Recommendation
Key `manualResolutions` by a value that uniquely identifies the specific conflict instance (e.g., a hash of the conflicting blob OIDs for `ours`/`theirs`/`base`, or the current rebase/cherry-pick step's commit SHA combined with path) rather than by path alone, and clear/re-derive resolutions whenever the underlying conflicted blobs for a path change between polls — analogous to the Venus fix of not letting a stale decision silently persist across a state transition it was never evaluated against.

### Proof of Concept
1. Attacker crafts branch `evil` with two commits: commit A changes `config.json` to conflict with `ours` on rebase (offering "theirs" = malicious payload), commit B (further down the rebase) also touches `config.json` producing a new, unrelated conflict.
2. Victim runs "Rebase onto `evil`" in GitHub Desktop, hits conflict on commit A, chooses "Use theirs" for `config.json`, continues.
3. Desktop resolves commit A's conflict, moves to commit B. `updateConflictState` sees `rebaseInternalState !== null` (kind still `rebase`) and reuses `prevConflictState.manualResolutions`, so `config.json` is shown/treated as already resolved with "theirs" even though commit B's conflict content is entirely different: [5](#0-4) 
4. When the user finishes the rebase, `stageManualConflictResolution` stages `config.json` using the stale resolution enum without inspecting commit B's actual conflicting content: [6](#0-5) 
5. The victim commits/pushes a file whose content was never reviewed for commit B's conflict, achieving silent corruption of what is committed.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }

  /**
   * Renders the banner based on count of resolved files.
   *
   * Always shows the resolved count when there are resolved files. If the
   * count drops to 0 after having been non-zero, shows the "undone" banner.
   */
  public renderBanner(conflictedFilesCount: number) {
    const { workingDirectory, manualResolutions } = this.props
    const countResolved = getResolvedFiles(
      workingDirectory,
      manualResolutions
    ).length

    if (countResolved > 0) {
      this.hasSeenResolvedFiles = true
    }

    if (countResolved === 0 && !this.hasSeenResolvedFiles) {
      return
    }

    if (countResolved === 0) {
      return <DialogSuccess>All resolutions have been undone.</DialogSuccess>
    }

    if (conflictedFilesCount === 0) {
      return (
        <DialogSuccess>All conflicted files have been resolved. </DialogSuccess>
      )
    }

    const conflictPluralized = countResolved === 1 ? 'file has' : 'files have'
    return (
      <DialogSuccess>
        {countResolved} conflicted {conflictPluralized} been resolved.
      </DialogSuccess>
    )
  }
