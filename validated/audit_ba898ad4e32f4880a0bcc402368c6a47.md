### Title
Minimum-fee check is satisfied by a vbyte count that excludes the OP_RETURN data output, so the "minimum fee" invariant doesn't bind the actual transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

The DYAD finding is about an invariant (`MIN_MINT_DYAD_DEPOSIT`) that is checked at entry but never actually enforced against the user's real state — the requirement is satisfied on paper while the mechanism it was meant to constrain is trivially bypassed. In `SignableTransaction::new`, the analogous gap exists: the transaction's fee is computed and validated against the minimum relay fee using a vbyte count that omits the OP_RETURN data output, so the declared/validated fee rate is not the fee rate the final transaction actually carries.

### Finding Description

In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`), the caller can attach up to 80 bytes of arbitrary `data`, which is pushed onto `tx_outs` as an OP_RETURN output at lines 194-202. However, the weight/vbyte calculation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing `payments`, not `tx_outs` — so the data output is never included in the size estimate. The same omission occurs in the change path at lines 224-235, where `calculate_weight_vbytes` is again called with `payments` only.

`calculate_weight_vbytes` (lines 62-127) builds a mock `Transaction` purely from `payments` and `change`; the OP_RETURN output (~83-byte script + 8-byte value + overhead, i.e. ~90+ non-witness bytes) is invisible to it. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` under-charges by roughly `fee_per_vbyte * ~90` satoshis worth of size.
2. The minimum-fee gate at lines 211-213 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000 → TooLowFee`) validates a fee that satisfies the relay minimum only for the *smaller, data-less* transaction. The actual serialized transaction includes the OP_RETURN output, so its effective sat/vbyte rate is strictly lower than what was checked — and can fall below Bitcoin's `DEFAULT_MIN_RELAY_TX_FEE` even though `TooLowFee` was not triggered.

The actual paid fee is `sum(inputs) − sum(outputs)` (lines 137-141), which equals `needed_fee`; the check passes while the real transaction does not meet the rate it was validated against — the exact "enforced minimum that doesn't enforce behavior" shape of M-01.

### Impact Explanation

A transaction constructed via the public `SignableTransaction::new` API with `data` attached can be produced whose real fee rate is lower than both the caller-specified `fee_per_vbyte` and the minimum relay fee the code explicitly intended to enforce. In the worst case the signed transaction is rejected by relay policy, leaving the multisig's inputs committed to a transaction that cannot propagate — funds effectively stuck until an alternate path is used, and the transaction's `Eventuality` (its expected txid) never confirms. This qualifies as "funds reported/committed that are not spendable as intended" and an "incorrect verifier formula" (the min-fee validation uses the wrong denominator). Severity: Medium — it requires using the `data` parameter, and the fee shortfall is bounded (~90 vbytes × fee rate), but it silently defeats the protocol's only fee floor.

### Likelihood Explanation

`data` is a public, caller-controlled input to `SignableTransaction::new` (validated only for `<= 80` bytes at line 171). Any integration that attaches metadata triggers the miscount on every transaction. Whether the resulting transaction falls below the relay minimum depends on how close `fee_per_vbyte` is to the minimum, but the fee under-accounting itself is deterministic on every call with `data.is_some()`. The processor currently passes `None` for data (`processor/src/networks/bitcoin.rs:446-452`), so the trigger depends on other callers of this public API; the miscounting bug itself is unconditional.

### Recommendation

Include the OP_RETURN output in the size estimate. Either pass `tx_outs` (post-data) into `calculate_weight_vbytes` instead of `payments`, or add the data output's serialized size to the weight before computing `vbytes` — e.g., build the mock transaction from the final output list, mirroring how `change` is handled at lines 224-235. Recompute `vbytes` *after* all outputs (payments, data, change) are known, and apply the `DEFAULT_MIN_RELAY_TX_FEE` check against that final size so the minimum-fee invariant actually binds the produced transaction.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/send.rs
// Conceptual: SignableTransaction::new with a large `data` payload
let data = vec![0u8; 80]; // max allowed
let tx = SignableTransaction::new(
    inputs,                       // ReceivedOutputs
    &payments,                    // e.g. one payment
    None,                         // no change -> leftover becomes fee
    Some(data),                   // OP_RETURN output added to tx_outs (lines 194-202)
    fee_per_vbyte,                // chosen exactly at min relay rate
).unwrap();

// Line 204: vbytes computed from `payments` only — the ~90-byte OP_RETURN
// output pushed at lines 194-202 is excluded.
// Line 211: needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000 passes.
// But tx.tx.output contains the extra OP_RETURN output, so the real
// transaction's vsize > vbytes, and:
//   real_rate = tx.fee() / tx.vsize()  <  needed_fee / vbytes = fee_per_vbyte
// If fee_per_vbyte was the minimum relay rate, the signed TX is below the
// relay minimum despite the TooLowFee check passing — the "minimum" was
// satisfied for a transaction that is not the one being broadcast.
```

Concrete delta: the OP_RETURN output adds ~92 bytes of non-witness data (`8` value + script len + `OP_RETURN` + push opcode + 80 bytes), all unaccounted for in `weight`, so `needed_fee` is short by `fee_per_vbyte * ~92` satoshis of required coverage.
