Based on the investigation, the strongest analog to the ENS "validation checked once at a superficial level, then permanently bypassable due to broken invariant" bug class is a stateful-regex validation bypass in GitHub Desktop's deep-link branch-name check.

### Title
Deep-link branch name validation (`testForInvalidChars`) can be bypassed due to shared stateful global regex `lastIndex` - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
`app/src/lib/parse-app-url.ts` validates the `branch` query parameter of an incoming `x-github-client://openrepo/...` deep link using `testForInvalidChars()` before treating it as trusted enough to attach to an `IOpenRepositoryFromURLAction` and hand off to git ref/checkout code paths via the dispatcher.

### Finding Description
The validator and the sanitizer share one module-level regex object declared with the global flag: [1](#0-0) 

`testForInvalidChars` calls `.test()` on this shared `const invalidCharacterRegex` object. Because the regex literal carries the `g` flag, `RegExp.prototype.test` mutates the object's `lastIndex` property as a side effect whenever it finds a match. That mutated `lastIndex` persists on the module-level singleton across *all* subsequent, unrelated calls to `testForInvalidChars` for the remainder of the process lifetime (the app never reinstantiates the regex). Consequently, if one deep-link's `branch` value contains an invalid character that gets matched near the end of the string, `lastIndex` is left pointing past that position. The *next* call to `testForInvalidChars`, on a completely different, attacker-controlled `branch` string, resumes scanning from that stale `lastIndex` instead of position 0 — silently skipping any invalid/dangerous characters located before that offset and returning `false` (i.e., "looks safe") for a string that actually contains disallowed control characters, `..` traversal sequences, or other `git-check-ref-format`-violating content.

This is invoked here: [2](#0-1) 

The guard's only job is to gate what `branch` value is allowed to flow into `IOpenRepositoryFromURLAction`, which `dispatcher.dispatchURLAction` forwards to `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branch)`: [3](#0-2) 

Unlike the sanitizer (`sanitizedRefName`, which uses `.replace()` — a call that internally resets `lastIndex` to 0 after a global replace and is therefore not affected), the validator path has no such reset, making it uniquely vulnerable to this stateful bypass.

### Impact Explanation
This mirrors the ENS bug's broken invariant: a guard that is supposed to universally reject an unsafe class of names can be desynchronized by prior activity so that a *specific*, attacker-crafted value slips past validation while the surrounding code believes it was checked. Here, the attacker fully controls the trigger (a link/deep link the user clicks) and the corrupted value is the `branch` string threaded into git ref/checkout logic downstream of `openBranchNameFromUrl`. Depending on what that function does with an unsanitized ref (e.g., passing it as a literal argument to `git`), this could allow injection of characters `sanitizedRefName`/`testForInvalidChars` were meant to strip (leading `-`/`+`, `..` traversal, control characters), potentially corrupting what gets checked out or, in the worst case, enabling git argument/ref injection.

### Likelihood Explanation
Exploitation requires two things the attacker controls entirely: (1) getting the victim to open one crafted deep link whose `branch` parameter contains an invalid character positioned so that `lastIndex` is left at a specific offset, and (2) shortly after (same app session, since the regex singleton lives for the process lifetime), getting the victim to open a second crafted deep link whose malicious character sits before that stale offset. Both can be delivered via a single webpage that fires two `x-github-client://` navigations in sequence, so this is plausible without any local access, admin rights, or leaked credentials — it only requires the normal "user clicks a link" flow that Desktop's protocol handler already treats as an entry point (`app/src/main-process/main.ts`, `possibleProtocols`/`handleAppURL`).

### Recommendation
Do not reuse a single global-flag regex instance across `.test()` calls that must be idempotent per-input. Either construct a fresh `RegExp` per call (`new RegExp(invalidCharacterRegex.source, 'g')`), strip the `g` flag from the object used by `testForInvalidChars` (only `.replace()` needs `g`), or explicitly reset `invalidCharacterRegex.lastIndex = 0` before each `.test()` invocation.

### Proof of Concept
Conceptually (Node/JS semantics), given the shared regex:
```
const re = /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g
re.test("foo..bar")          // true, sets re.lastIndex to point past "foo.."
re.test("..evil")            // may return false here because lastIndex
                              // is now nonzero and scanning starts mid-string,
                              // skipping the leading ".." at the start
```
Applied to the real code path: an attacker sends the victim link A: `x-github-client://openrepo/https://github.com/x/y?branch=aaa..bbb`, which is (correctly) rejected but advances `lastIndex`. Immediately after, link B: `x-github-client://openrepo/https://github.com/x/y?branch=..%2F..%2Fetc` is sent; because `lastIndex` from the previous call is nonzero, `testForInvalidChars` scans from that offset and can miss the leading `../../` sequence, causing `parseAppURL` to accept it as a valid `branch` and forward it to `dispatchURLAction` → `openBranchNameFromUrl`.

Note: I could not view the full body of `openBranchNameFromUrl` in the available tool budget to confirm the exact git command it executes with the unsanitized `branch` string, so the ultimate severity (whether it results in argument injection, path traversal, or is caught by a further downstream check) is not fully verified and should be confirmed by a Devin session with full file access.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
