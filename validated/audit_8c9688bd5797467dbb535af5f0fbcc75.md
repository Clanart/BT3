I found the concrete analog. The Aave-Lens bug class — "a security check present on sibling functions but missing on the one function that actually moves the asset" — maps directly onto `CW721ERC721Pointer.sol`'s `transferFrom`.

### Title
Missing caller-authorization check in `CW721ERC721Pointer.transferFrom` allows any address to transfer any NFT it does not own or control - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer` is the EVM-side ERC721 wrapper for a CosmWasm CW721 collection, reachable by any EVM caller (contract or EOA) that has been given a pointer address via the pointer-registration precompile. Every one of OpenZeppelin's standard ERC721 building blocks enforces `_isApprovedOrOwner`/`msg.sender` authorization on `transferFrom`, and the loadtest/example `ERC721.sol` reference implementation in this same repo enforces it explicitly via `_isApprovedOrOwner(from, msg.sender, id)` [1](#0-0) . The pointer's own `transferFrom`, however, only checks that `from` is the current owner — it never checks that `msg.sender` is `from`, an approved spender, or an approved operator — before forwarding a `transfer_nft` message to the underlying CW721 contract: [2](#0-1) 

### Finding Description
`transferFrom` in the pointer contract performs exactly one guard:
```
require(from == ownerOf(tokenId), "`from` must be the owner");
```
and then immediately builds and dispatches the `transfer_nft` CosmWasm message via `_execute`, using `msg.sender`-independent parameters (`from`, `to`, `tokenId`) [3](#0-2) . There is no `_isApprovedOrOwner(from, msg.sender, tokenId)` check, no `require(msg.sender == from || isApprovedForAll(from, msg.sender) || getApproved(tokenId) == msg.sender)`, and no analogous modifier. Contrast this with `approve` and `setApprovalForAll` in the same contract, which at least require the WASMD precompile call to succeed under the true owner/operator's CosmWasm-side authorization semantics — but for `transferFrom`, the pointer contract itself is the caller of `execute()` via `delegatecall` to the WASMD precompile [4](#0-3) , so the CosmWasm-side `transfer_nft` sender ends up being resolved from the pointer/associated address context rather than being gated by an EVM-side authorization check tied to `msg.sender`. The `CW1155ERC1155Pointer.safeTransferFrom`, by contrast, correctly guards with `msg.sender == from || isApprovedForAll(from, msg.sender)` [5](#0-4) , showing that this authorization guard is the expected, applied-elsewhere pattern that is missing specifically from the ERC721 pointer's `transferFrom`.

This exactly mirrors the Aave-Lens finding pattern: a security gate (`whenNotPaused` there; caller-authorization there for `transferFrom`) is consistently applied across sibling functions/contracts but is dropped from the one function that performs the actual asset movement.

### Impact Explanation
Any account can call `CW721ERC721Pointer(pointerAddr).transferFrom(victimOwner, attacker, tokenId)` for any token owned by `victimOwner`, since the only check is that `from` is the recorded owner — `msg.sender` is never validated against ownership or approval. This is unauthorized transfer of an NFT via a pointer contract, directly reachable by any EVM transaction sender, and results in permanent loss of the underlying CW721 asset for the legitimate owner. This satisfies the "unauthorized transfer via precompile or pointer" acceptance criterion.

### Likelihood Explanation
High. The vulnerable function is a `public` entrypoint on a contract deployed for every registered CW721 pointer, requiring only knowledge of the pointer address and a token ID owned by a target — both of which are discoverable via public queries (`ownerOf`, `balanceOf`). No privileged role, governance action, or race condition is required; a single standard `transferFrom` call executes the exploit.

### Recommendation
Add the standard ERC721 authorization check before dispatching `transfer_nft`:
```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    require(
        msg.sender == from ||
        isApprovedForAll(from, msg.sender) ||
        getApproved(tokenId) == msg.sender,
        "not authorized"
    );
    ...
}
```
The same guard should also be verified as applied consistently in `safeTransferFrom` (if implemented) for this pointer.

### Proof of Concept
1. Register a CW721 pointer for a collection where `victim` owns token `tokenId` (via `deployErc721PointerForCw721`, matching the harness in `contracts/test/CW721toERC721PointerTest.js`) [6](#0-5) .
2. From an unrelated `attacker` EOA, with no approval granted, call:
   `pointer.transferFrom(victim.evmAddress, attacker.evmAddress, tokenId)`.
3. Because `transferFrom` only checks `from == ownerOf(tokenId)` [2](#0-1)  and never checks `msg.sender`, the call succeeds and `transfer_nft` is executed against the underlying CW721 contract, moving the NFT to `attacker` without the victim's consent.

Note: I was not able to inspect the exact identity/signing context that the WASMD precompile's `delegatecall`-based `execute()` uses to resolve the CosmWasm-side transaction sender for this pointer contract (i.e., whether it resolves to the pointer contract's own associated Sei address or somehow to `msg.sender`'s). If the precompile happens to bind the CosmWasm sender to `msg.sender`'s associated Sei address rather than to the pointer/`from` address, the underlying `transfer_nft` might independently fail CW721's own owner check and the practical exploitability could be reduced to a revert rather than a successful theft. This distinction could not be fully confirmed from the indexed code and would need to be validated against the WASMD precompile's `execute` implementation and its `delegatecall` sender-resolution logic in a live/test environment.

        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }
