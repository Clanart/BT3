### Title
Hookify PreToolUse hook fails open on any exception, silently bypassing user-defined block rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The Sherlock report describes a root cause where a failure signal (`transferFrom` returning `false`) is not checked/enforced, so execution proceeds as if the operation had succeeded, letting an attacker mint pool shares without paying. The structurally equivalent pattern in this codebase is the `hookify` plugin's `PreToolUse` executor: any failure during rule loading or rule evaluation is swallowed and the hook unconditionally reports success/allow (`sys.exit(0)`), even though the intended semantics of the rule engine are to **deny** ("block") a matching dangerous operation. The failure signal (an exception) is captured but never translated into a deny decision — the caller (Claude Code's tool-permission pipeline) proceeds as if the hook had legitimately evaluated to "no rule matched."

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is registered as a `PreToolUse` command hook that is supposed to enforce user-authored `.claude/hookify.*.local.md` block/warn rules before Bash/Edit/Write/MultiEdit tool calls execute. [1](#0-0) 

The `main()` function:
1. Loads rules via `load_rules(event=...)`.
2. Evaluates them via `RuleEngine().evaluate_rules(rules, input_data)`.
3. Prints the resulting JSON and **always** calls `sys.exit(0)` in a `finally` block — regardless of whether evaluation succeeded, threw, or produced a "block" decision object.
4. On **any** exception (`except Exception as e`), it discards the actual decision, prints only a `systemMessage`, and still exits 0.

Exit code 0 with no `permissionDecision: "deny"` in `hookSpecificOutput` is interpreted by Claude Code as "no opinion / allow." This means: if `RuleEngine.evaluate_rules()` or its helpers throw for any reason before returning the `{"hookSpecificOutput": {"permissionDecision": "deny"}}` payload, the hook fails open, and the tool call that a user-authored rule was meant to block proceeds anyway.

Concrete exception surfaces that can be reached with attacker/model-influenced tool input, analogous to how a no-revert token silently returns `false` instead of aborting:

- `RuleEngine._extract_field` calls `.startswith()`/`.endswith()`/`in`/`==` on `field_value`, and `MultiEdit` field extraction does `e.get('new_string', '')` — if `tool_input['edits']` contains non-dict entries (a shape Claude/the model can produce, or that a malicious MCP tool result / prompt-injected instruction can induce), `e.get` raises `AttributeError`. [2](#0-1) 
- `_check_condition`'s `contains`/`starts_with`/`not_contains` operators assume `field_value` is a string; if a rule's `pattern` (attacker- or user-authored `.local.md` file, or config drifted by a compromised dependency/marketplace plugin) is not a string (e.g., a list from a malformed YAML frontmatter parse), `pattern in field_value` or `field_value.startswith(pattern)` raises `TypeError`. [3](#0-2) 
- The custom hand-rolled YAML-like parser in `config_loader.extract_frontmatter` is fragile (manual indentation/list/dict-item state machine); a crafted `.claude/hookify.*.local.md` (which is themselves untrusted content when synced from a plugin marketplace or committed by a lower-trust contributor to a shared repo) can produce a `Condition`/`Rule` whose fields have unexpected types, feeding directly into the exception surfaces above. [4](#0-3) 

Whenever any of these throw inside `RuleEngine.evaluate_rules`, control returns to `pretooluse.py`'s outer `try/except Exception`, which prints only a diagnostic `systemMessage` and exits 0 — **the block decision is lost**, and the dangerous Bash/Edit/Write operation that the user's own rule was written to stop is allowed to execute without ever presenting a deny or even an "ask" to the user. [5](#0-4) 

### Impact Explanation
This is a genuine unprivileged-user-relevant permission-bypass / fail-open defect within an in-repo hook-authorization mechanism: a user configures a `block` rule (e.g., to prevent `rm -rf`, writes to `.env`, or destructive commands) expecting it to be enforced pre-execution; a crafted or edge-case tool call (which the agent itself, following a prompt-injected instruction, could shape to trigger the exception path — e.g., an `edits` array with a non-dict element, or content that trips the fragile hand-written frontmatter parser used to load the rule) causes the enforcement layer to silently no-op instead of denying. The result is unauthorized execution of an operation the user explicitly intended to block — a direct local compromise/bypass of a security control, matching the "fails open instead of reverting/denying" root cause of the reference report (unchecked failure signal → operation proceeds as if it had succeeded/been authorized).

### Likelihood Explanation
Medium-to-High. `hookify` is a first-party plugin shipped in this repo specifically to let users declare block rules; the `pretooluse.py` `finally: sys.exit(0)` combined with `except Exception` swallowing means *any* bug in the rule engine or the ad hoc YAML parser converts an intended "deny" into a silent "allow." No special privileges are needed to trigger it — a normal tool call whose `tool_input` shape doesn't match the engine's untested assumptions (e.g., malformed `MultiEdit.edits`, or a rule pattern that isn't a plain string due to a frontmatter parsing quirk) is sufficient, and such shapes are plausible via ordinary agent behavior or a prompt-injection nudging Claude to use an unusual tool-input shape.

### Recommendation
- Change `pretooluse.py` to fail **closed** (or at least "ask") when rule evaluation raises, instead of unconditionally `sys.exit(0)`: on exception, emit `{"hookSpecificOutput": {"permissionDecision": "ask"}}` (or `deny` for high-risk event types) plus the diagnostic `systemMessage`, so a broken rule can never silently downgrade an intended block into an allow.
- Harden `RuleEngine._check_condition`/`_extract_field` to defensively coerce/validate types (ensure `field_value` and `pattern` are strings, ensure `edits` entries are dicts) rather than relying on well-formed input, and treat validation failures as "rule cannot be evaluated" → conservative deny/ask rather than an uncaught exception.
- Replace the hand-rolled frontmatter parser in `config_loader.extract_frontmatter` with a real YAML parser (`yaml.safe_load`) to eliminate the whole class of malformed-structure bugs feeding untyped data into the engine.

### Proof of Concept
1. Author `.claude/hookify.block-secrets.local.md` with a `block` rule targeting `MultiEdit`, e.g. matching `new_text` against a secret-looking pattern, intended to stop writes containing credentials.
2. Have Claude (or a prompt-injected instruction) issue a `MultiEdit` tool call whose `tool_input.edits` array contains one entry that is not a dict (e.g. a bare string), which can occur due to model output formatting drift or a compromised MCP tool relaying malformed input.
3. `RuleEngine._extract_field` (`plugins/hookify/core/rule_engine.py:249-252`) executes `e.get('new_string', '')` on the non-dict entry and raises `AttributeError`.
4. `pretooluse.py`'s outer `except Exception` catches it, prints only `{"systemMessage": "Hookify error: ..."}`, and `finally: sys.exit(0)` runs — no `permissionDecision: deny` is ever emitted.
5. Claude Code treats the hook's exit-0/no-deny output as "no objection," and the `MultiEdit` operation — which the user's `block` rule was meant to stop — proceeds unhindered, silently bypassing the configured guard exactly as the reference bug allowed an unchecked failure to be treated as success.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()

    # Simple YAML parser that handles indented list items
    frontmatter = {}
    lines = frontmatter_text.split('\n')

    current_key = None
    current_list = []
    current_dict = {}
    in_list = False
    in_dict_item = False

    for line in lines:
        # Skip empty lines and comments
        stripped = line.strip()
        if not stripped or stripped.startswith('#'):
            continue

        # Check indentation level
        indent = len(line) - len(line.lstrip())

        # Top-level key (no indentation or minimal)
        if indent == 0 and ':' in line and not line.strip().startswith('-'):
            # Save previous list/dict if any
            if in_list and current_key:
                if in_dict_item and current_dict:
                    current_list.append(current_dict)
                    current_dict = {}
                frontmatter[current_key] = current_list
                in_list = False
                in_dict_item = False
                current_list = []

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':
                    value = False
                frontmatter[key] = value

        # List item (starts with -)
        elif stripped.startswith('-') and in_list:
            # Save previous dict item if any
            if in_dict_item and current_dict:
                current_list.append(current_dict)
                current_dict = {}

            item_text = stripped[1:].strip()

            # Check if this is an inline dict (key: value on same line)
            if ':' in item_text and ',' in item_text:
                # Inline comma-separated dict: "- field: command, operator: regex_match"
                item_dict = {}
                for part in item_text.split(','):
                    if ':' in part:
                        k, v = part.split(':', 1)
                        item_dict[k.strip()] = v.strip().strip('"').strip("'")
                current_list.append(item_dict)
                in_dict_item = False
            elif ':' in item_text:
                # Start of multi-line dict item: "- field: command"
                in_dict_item = True
                k, v = item_text.split(':', 1)
                current_dict = {k.strip(): v.strip().strip('"').strip("'")}
            else:
                # Simple list item
                current_list.append(item_text.strip('"').strip("'"))
                in_dict_item = False

        # Continuation of dict item (indented under list item)
        elif indent > 2 and in_dict_item and ':' in line:
            # This is a field of the current dict item
            k, v = stripped.split(':', 1)
            current_dict[k.strip()] = v.strip().strip('"').strip("'")

    # Save final list/dict if any
    if in_list and current_key:
        if in_dict_item and current_dict:
            current_list.append(current_dict)
        frontmatter[current_key] = current_list

    return frontmatter, message
```
