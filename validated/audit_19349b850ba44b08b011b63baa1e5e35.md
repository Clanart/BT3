### Title
Unauthenticated `InternalSendTx` broadcasting call on the Aggregator gRPC service - (File: `core/src/rpc/aggregator.rs`)

### Summary
The `ClementineAggregator` gRPC service exposes `internal_send_tx`, a state-changing/broadcasting RPC that accepts an arbitrary caller-supplied raw Bitcoin transaction and queues it for network broadcast (with automatic fee-bumping), yet the Aggregator server applies no client-certificate authentication at all, so any network peer that can reach the Aggregator's port can invoke it.

### Finding Description
`create_aggregator_grpc_server` builds the Aggregator's gRPC service and passes it through the generic `create_grpc_server` helper [1](#0-0) . That helper wires an `Interceptors::OnlyAggregatorAndSelf` interceptor only "if `config.client_verification`" is set, and otherwise falls back to `Interceptors::Noop`, which passes every request through unchecked [2](#0-1) [3](#0-2) . The project's own documentation confirms this is the intended, documented deployment posture for the Aggregator specifically: "The aggregator does not enforce client certificates but does use TLS for encryption" [4](#0-3) . This is unlike the Verifier/Operator servers, which reject any call whose gRPC method name starts with `Internal` unless the caller's leaf TLS certificate equals the entity's own client certificate [5](#0-4) [6](#0-5) .

Despite this, the Aggregator proto defines multiple RPCs explicitly named/commented as being for internal/automation use only, e.g. `rpc InternalSendTx(SendTxRequest) returns (Empty) {}` ("Send a pre-signed tx to the network") [7](#0-6) . Its handler `internal_send_tx` deserializes the caller-supplied `raw_tx`, logs it, and unconditionally forwards it to the transaction sender for broadcast/fee-management, with no check binding the caller's identity or the transaction's purpose to any deposit/round/kickoff state: [8](#0-7) 

Because the Aggregator's `Interceptors::Noop` accepts every peer regardless of TLS identity, this "Internal" method — meant to be triggered only by the Aggregator's own automation tasks (as done in tests: `aggregator.internal_send_tx(SendTxRequest{...})` [9](#0-8) ) — is reachable by any unauthenticated network caller who can connect to the Aggregator's gRPC/TLS endpoint. This directly matches the "caller reaching a … state-changing method versus the party it is meant for" analog class: the intended caller is the Aggregator itself/its automation, but the actual reachable caller is anyone on the network.

The sibling RPCs `SendMoveToVaultTx`, `NewDeposit`, `Withdraw`, and `OptimisticPayout` are similarly unauthenticated broadcast/state-changing entry points on the Aggregator, explicitly documented as "Used by the clementine-backend service" [10](#0-9) , yet reachable by anyone since the Aggregator enforces no client certificate.

### Impact Explanation
This falls squarely under the report's accepted High-severity bucket: "an unauthenticated state-changing or broadcasting call." `internal_send_tx` lets any unauthenticated party trigger the Aggregator to submit arbitrary pre-signed Bitcoin transactions into its `tx_sender` queue for broadcast and automatic RBF fee management [11](#0-10) , decoupling the decision of *when* and *whether* to broadcast protocol transactions (rounds, kickoffs, challenges, disproves, etc.) from the entity that is supposed to control that timing. Since round/kickoff/challenge/disprove flows in this bridge are deadline-sensitive, an attacker able to force premature or out-of-order broadcasts of transactions they can obtain (e.g., from public mempool/chain data, logs, or other side channels) can disrupt the intended sequencing of the protocol — matching the "premature disclosure of a protocol commitment" / broadcast-timing impact category called out as High.

Note: the raw transaction must still carry valid Bitcoin-level signatures, so this does not by itself allow the attacker to forge N-of-N or operator signatures or steal BTC outright; the concrete downstream consequences (e.g., whether the tx_sender's RBF/fee-bumping logic could be abused to make a legitimate pending disprove/challenge transaction unconfirmable via conflicting-input replacement) could not be fully verified from the accessible slice of `insert_try_to_send`/`tx_sender` internals, so that stronger escalation path is not asserted here.

### Likelihood Explanation
High. No credentials, keys, or privileged role are required — only network reachability to the Aggregator's gRPC/TLS port, which per the documented design intentionally omits client-certificate verification. Any party who can connect can call `internal_send_tx` (and the other unauthenticated Aggregator RPCs) directly.

### Recommendation
Require the Aggregator to authenticate callers of state-changing/broadcasting RPCs (at minimum `Internal*`-prefixed methods such as `InternalSendTx`, and ideally `NewDeposit`/`Withdraw`/`OptimisticPayout`/`SendMoveToVaultTx`) using the same certificate-pinning approach already used by the Verifier/Operator servers (`Interceptors::OnlyAggregatorAndSelf`), rather than relying on `Interceptors::Noop` by default.

### Proof of Concept
1. Start an Aggregator instance configured per the documented/default posture (`client_verification` not enforced for the Aggregator, as documented).
2. From an arbitrary, non-whitelisted TLS client (no aggregator/self certificate), connect to the Aggregator's gRPC endpoint and call `ClementineAggregator/InternalSendTx` with any previously-obtained valid raw Bitcoin transaction and a `fee_type`.
3. Observe that `internal_send_tx` deserializes and forwards the transaction to `tx_sender.insert_try_to_send` for broadcast without any caller-identity check [12](#0-11) , confirming the method is reachable and acted upon despite being labeled "Internal" and intended only for the Aggregator's own automation.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    #[tracing::instrument(skip(self), err(level = tracing::Level::ERROR))]
    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
