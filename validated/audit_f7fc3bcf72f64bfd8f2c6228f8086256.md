### Title
Unvalidated repository-relative file paths in "Reveal in File Manager" / "Open with Default Program" allow symlink escape outside the repository root - (File: `app/src/lib/app-shell.ts`)

### Summary
GitHub Desktop already recognizes that file paths sourced from repository content cannot be trusted to stay inside the repository root: it ships a dedicated `resolveWithin` helper [1](#0-0)  that resolves symlinks via `realpath` and rejects any result that escapes the given root, and it is deliberately used when handling the `x-github-client://openRepo` deep-link's `filepath` parameter [2](#0-1) . However, the much more commonly used "Reveal in File Manager" / "Open with Default Program" / "Open in External Editor" context-menu actions — which build their target path from `file.path` values that come directly from `git status`/diff output of a cloned or fetched repository — do **not** go through `resolveWithin`. They simply do `Path.join(repository.path, path)` and then call `shell.showItemInFolder`/`openFile`.

### Finding Description
`revealInFileManager` in `app/src/lib/app-shell.ts` builds the path to reveal with a plain `Path.join` and explicitly documents that its inputs must be pre-validated, yet none of its callers validate them: [3](#0-2) 

This function (and the analogous `Path.join(repository.path, path)` pattern) is invoked from multiple context menus that operate on paths reported for files in the working directory, in historical commits, and in pull request diffs — all of which are values under attacker control once the user clones/fetches a hostile repository or checks out a hostile PR branch: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

By contrast, the deep-link handler for `openRepositoryFromUrl` treats the exact same shape of input (a repository-relative path controlled by a remote/URL) as untrusted and explicitly guards it with `resolveWithin` plus an `isAbsolute` rejection before calling `shell.showItemInFolder`: [2](#0-1) 

The broken invariant is: "a path reported for a file inside the repository always stays inside the repository working directory." That invariant does not hold when the repository itself contains a tracked symlink (a normal, legal Git object type) whose target points outside the repository (e.g., `../../../../etc` or an absolute path). Git will happily check out such a symlink (unless `core.symlinks` is disabled), and `git status`/diff will report ordinary-looking relative paths for files "inside" that symlinked directory. When the user right-clicks such a file and chooses "Reveal in File Manager" or "Open with Default Program," the unguarded `Path.join` + OS-level path resolution follows the symlink and interacts with the location the attacker chose, not a location Desktop verified to be inside the repository.

### Impact Explanation
This lets a malicious cloned/fetched repository or forked PR branch (a GitHub API object under attacker control) cause the victim's Desktop app to open or reveal files outside the intended repository boundary via routine, expected user actions (browsing changes/history/PR diffs and using standard context-menu items). Depending on the target and the OS default-application association, "Open with Default Program" can result in disclosure of sensitive file contents or, for certain file types/handlers, execution of attacker-influenced content — a stronger consequence than the mere "wrong event semantics" of the original report, since here it is Desktop's own file-path trust boundary that is inconsistently enforced.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker's repository to contain a symlink pointing outside the repo (a config a git host will store without complaint) and the victim to interact with a context-menu item on a file reached through that symlink. No local access, admin rights, or prior compromise is needed — only cloning/fetching an attacker-controlled repository or checking out a PR, both normal Desktop workflows. The presence of the hardened `resolveWithin` pattern elsewhere in the same codebase, applied to a narrower/rarer code path (deep links) but not the everyday Changes/History/PR context menus, indicates the gap is a real inconsistency rather than a deliberate accepted risk.

### Recommendation
Route all repository-relative path constructions that end up in `shell.showItemInFolder`, `shell.openPath`/`openFile`, or `dispatcher.openInExternalEditor` (in `sidebar.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`, and `app-shell.ts`'s `revealInFileManager`) through `resolveWithin(repository.path, path)` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate), rejecting and logging any path that resolves outside the repository root, exactly as is already done in `dispatcher.ts`'s `openRepositoryFromUrl`.

### Proof of Concept
1. Attacker creates and pushes a repository containing a tracked symlink, e.g. `payload -> /etc` (POSIX) or a directory junction on Windows pointing to a sensitive path outside the eventual clone directory.
2. Victim clones or fetches the repository in GitHub Desktop, or checks out a PR branch containing this symlink; `git checkout` materializes the symlink on disk since Desktop does not disable `core.symlinks`.
3. Desktop's Changes/History/PR-files view reports an ordinary relative path such as `payload/passwd` for a file "inside" the symlinked directory.
4. Victim right-clicks the entry and selects "Reveal in File Manager" or "Open with Default Program".
5. `revealInFileManager`/`openFile` computes `Path.join(repository.path, 'payload/passwd')` with no `resolveWithin` check [8](#0-7) , the OS resolves the symlink transparently, and the file manager/default application opens the target outside the cloned repository — demonstrating the missing guard that exists for the equivalent deep-link `filepath` case [9](#0-8) .

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
