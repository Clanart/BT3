Let me check the remaining in-scope wallet files for stronger analogs.### Title
`SignableTransaction::new` computes fee, minimum-relay check, and weight limit without accounting for the OP_RETURN data output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output carrying user-supplied `data` into `tx_outs`, but then calculates the transaction's weight/vbytes — and therefore `needed_fee`, the `TooLowFee` minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` check — using `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which rebuilds the transaction from `payments` only and omits the data output entirely. Every size-dependent check is performed on a transaction smaller than the one actually signed, mirroring the reported bug class where a bound is checked against a value that fails to account for something deducted/added later.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` before the weight calculation:

- `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` at lines 194-202.
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` at line 204 — this reconstructs a model `Transaction` whose `output` is built only from `payments` (lines 85-94), so the serialized size of the data output is never counted.

All downstream checks use this underestimated `vbytes`/`weight`:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) under-prices the real transaction.
- The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (line 211) validates a fee rate against a smaller size.
- The insufficient-funds check `input_sat < payment_sat + needed_fee` (line 215) and the change calculation `input_sat - (payment_sat + fee_with_change)` (line 228) both use the understated fee.
- `weight > MAX_STANDARD_TX_WEIGHT` (line 241) can pass while the real signed transaction (which includes the OP_RETURN output) exceeds the standardness weight limit.

The actual fee paid, `sum(inputs) - sum(outputs)` (line 139), is fixed at construction, so the produced transaction simply relays at a lower effective fee rate than `fee_per_vbyte` requested — or fails the min-relay / max-weight policy entirely once broadcast, after the threshold signature has already been produced.

### Impact Explanation
An unprivileged caller supplies `data` (up to 80 bytes, checked at line 171) and `fee_per_vbyte` to `SignableTransaction::new`. The resulting transaction is what the FROST `TransactionMachine` signs (lines 373-397). The signed transaction is systematically under-priced relative to the requested fee rate — by `fee_per_vbyte` times the OP_RETURN output's serialized size — so it may linger unconfirmed or be rejected by `sendrawtransaction`'s mempool checks. In the edge case where the underestimated `weight` straddles `MAX_STANDARD_TX_WEIGHT`, a fully-signed, definitively non-standard transaction is produced and can never be broadcast, burning the inputs' availability in the signing session. This is a funds-stuck / invalid-transaction-producing flaw reachable purely through public inputs.

### Likelihood Explanation
Any use of the `data` field (e.g., the processor embedding metadata for the Serai protocol) triggers the under-calculation deterministically — no race or adversarial timing needed. The severity of the outcome depends on fee-market conditions: with a tight `fee_per_vbyte` near the relay minimum, or large `data`, the produced transaction will not propagate.

### Recommendation
Include the OP_RETURN output in the weight calculation. Either pass the already-built `tx_outs` (or `payments` plus the data output) into `calculate_weight_vbytes`, or move the data-output push after line 204 into a shared code path so `vbytes`, `needed_fee`, and `weight` reflect the final transaction. The same correction must apply to the `fee_with_change` path so the change-vs-dust decision uses the real size.
