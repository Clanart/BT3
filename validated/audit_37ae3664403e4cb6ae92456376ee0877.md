### Title
Dust-sized output spam to a public multisig address permanently commits the multisig to spending uneconomical UTXOs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` treats any on-chain output paying to the multisig's `p2tr` script as a legitimately received, spendable input. Because the deposit address is public, an unprivileged attacker can create arbitrarily many outputs just above the fixed `DUST` constant (546 sats). Every such output is irrevocably registered as a UTXO the multisig must later spend, and the signing pipeline has no notion of output "economicality" — `SignableTransaction::new` includes every input it's given and each Taproot input adds ~57.5 vbytes of fee. When the median fee rate exceeds roughly 9–10 sat/vB, a 546-sat input costs more fee than the value it contributes, so each spammed output becomes net-negative and drains the multisig's real funds.

### Finding Description
- `Scanner` keys `scripts` purely by `ScriptBuf` and pushes any matching output into `ReceivedOutput` (`networks/bitcoin/src/wallet/mod.rs:199-214`). Anyone who knows the P2TR address (publicly derivable from the group key) can mint recognized outputs.
- `DUST` is a hardcoded 546 sats (`networks/bitcoin/src/wallet/send.rs:32`), decoupled from the actual fee rate. Filtering at `N::DUST` only removes outputs below it; a 546-sat output always passes.
- In `SignableTransaction::new`, `input_sat` sums all provided inputs and the fee is `fee_per_vbyte * vbytes`, where vbytes grow linearly with `inputs` (`send.rs:62-186`). There is no per-input profitability check: an input whose value is less than `fee_per_vbyte * 57.5` still gets spent, reducing change or pushing the transaction toward `NotEnoughFunds`/`NoOutputs`.
- Downstream (processor scheduler), every received output lands in `self.utxos` and is unconditionally aggregated/spent in chunks of `MAX_INPUTS` (`processor/src/multisigs/scheduler/utxo.rs:350-385`), and the whole scheduler — including the unbounded `utxos` vec — is re-serialized to disk on every mutation (`utxo.rs:442`, TODO at `utxo.rs:109-111`). So spam also causes unbounded DB growth and O(n) reserialization per schedule.

### Impact Explanation
The attacker forces the multisig to permanently carry and eventually spend attacker-created UTXOs. Each forced spend burns real multisig value: at a median fee of e.g. 50 sat/vB, spending a 546-sat input costs ~2,875 sats, i.e. the multisig loses ~2,300 sats of its own funds per attack output while the attacker only pays 546 sats plus a cheap self-transfer fee. With enough outputs, spam also degrades availability: `utxos` grows unboundedly, every `schedule` call performs a full serialize+write of the entire state, and the input-selection "highest value first" ordering is polluted. At worst, plans can become unfulfillable (`NoOutputs`/`NotEnoughFunds` → `PreparedSend { tx: None }` with branches dropped and funds booked as operating costs), i.e. funds reported received become unusable in practice. This mirrors the source bug class: a cheap, permissionless action consumes a bounded/costly resource belonging to a victim who cannot refuse it.

### Likelihood Explanation
Fully reachable by any Bitcoin user: the multisig's external address is public, and sending P2TR outputs to it requires no Serai interaction. The attack is repeatable at ~546 sats + fees per iteration and the damage scales linearly, while there is no code path that ever discards a received ≥546-sat output. The net-negative-spend condition depends on the prevailing fee rate, so at very low fees the loss is bounded (input is roughly fee-neutral), which keeps severity at Medium rather than High.

### Recommendation
Compute effective dust dynamically: treat an output as economically unspendable when `value < fee_per_vbyte * input_vbytes` (or a small multiple thereof), and exclude such outputs from `SignableTransaction` inputs / scheduler `utxos`. Alternatively, allow outputs to be explicitly abandoned/blacklisted (analogous to the source report's "let the receiver remove delegations") rather than committing every scanned output to mandatory spending. Persist `utxos` incrementally instead of reserializing the entire scheduler on each mutation.

### Proof of Concept
1. Observe the Serai Bitcoin multisig's external P2TR address (derived from the group key via `p2tr_script_buf`).
2. In a single transaction, create N outputs of 546 sats each to that address.
3. `Scanner::scan_transaction` returns N `ReceivedOutput`s (`mod.rs:199-214`); each passes the `>= N::DUST` check and is pushed into the scheduler's `utxos`.
4. When the fee rate is >~9.5 sat/vB, the scheduler chunks these into aggregation `Plan`s; `SignableTransaction::new` spends them, each consuming ~57.5 vB and returning less than 546 sats of net value — change is reduced or the plan is dropped as unfulfillable.
5. Repeat indefinitely; `utxos` and the serialized scheduler state grow without bound, and cumulative fees burned on worthless inputs exceed the attacker's outlay.
