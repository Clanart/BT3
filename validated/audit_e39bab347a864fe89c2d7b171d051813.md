### Title
`with-ft` wildcard sentinel lets a single fungible-asset allowance authorize movement of *any* fungible token in a contract — ([File: clarity/src/vm/functions/post_conditions.rs])

### Summary
`check_allowances` treats any `Ft` allowance whose `asset_name` is the literal string `"*"` as a match-all wildcard for every fungible token defined in that contract, not just a token that happens to be named `"*"`. Because `AllowanceWithFt` evaluation (`eval_allowance`, `NativeFunctions::AllowanceWithFt`) builds the `AssetIdentifier` directly from whatever ASCII string the caller supplies as the asset name, with no reservation or rejection of the sentinel value, a `(with-ft ...)` allowance that a post-condition author believes applies to one specific fungible asset can silently be expanded by the checker to authorize the transfer of any/all fungible tokens issued by that contract, up to the stated amount. This mirrors the external report's core defect class: the vault/allowance mechanism "treats all valid tokens exactly the same," breaking the equality that a specific-asset authorization should cover only that asset.

### Finding Description
`eval_allowance` for `NativeFunctions::AllowanceWithFt` takes the asset name argument as an arbitrary ASCII string and converts it into a `ClarityName` with no special-casing: [1](#0-0) 

The resulting `AssetIdentifier { contract_identifier, asset_name }` is stored in `ft_allowances`, keyed by the exact `AssetIdentifier` (including whatever `asset_name` value the caller passed): [2](#0-1) 

During enforcement, `check_allowances` iterates every fungible token actually moved by the owner and, for each one, looks up both an exact match **and** a "wildcard" entry keyed by the same `contract_identifier` but with `asset_name` hard-coded to the literal `"*"`: [3](#0-2) 

There is nothing in the allowance-construction path (`eval_allowance` / `AllowanceWithFt`) that reserves `"*"` as a special token, rejects it as a real asset name, or otherwise distinguishes "the real fungible asset literally named `*`" from "match anything in this contract." The two concepts collapse to the same `AssetIdentifier` value, so the checker in `check_allowances` cannot tell them apart. Any post-condition author (or contract calling `restrict-assets?`/`as-contract?` on the user's behalf) who supplies `"*"` as the asset-name argument to `with-ft` — whether intentionally to invoke the internal wildcard mechanism, or because a contract genuinely defines a fungible token literally named `*` — creates an allowance entry that `check_allowances` treats as authorizing *every* fungible token asset under that `contract_identifier`, not just the one the post-condition's author intended to scope the transaction to.

This breaks the equality that a `with-ft` allowance restricts spending to a specific `(contract, asset-name)` pair: an attacker-influenced or attacker-crafted call path (e.g., a contract that lets a caller pick which asset name to request an allowance for, or that defines multiple fungible tokens in one contract, one of them named `*`) can cause tokens that were never meant to be authorized to move past the post-condition/allowance check, as long as the total amount moved for the "other" asset does not exceed the stated allowance amount. This is directly analogous to the yAxis vault issue, where distinct fungible assets sharing a container (the vault / the contract) were treated interchangeably by the accounting logic, letting one asset's accounting stand in for another's.

### Impact Explanation
This falls under the "asset moving past its post-conditions" Critical impact category: a `restrict-assets?`/`as-contract?` guarded call is supposed to bound movement of a *specific* fungible asset, but due to the `"*"` sentinel collision, a completely different fungible token defined in the same contract can move without ever being named in an allowance meant for it — the checker is satisfied by the wildcard collision instead of a genuine per-asset check. Any code (wallet, dApp contract, or multi-sig authorization scheme) relying on `with-ft` to scope exactly which token can move inside a protected block can be bypassed for other tokens issued by the same contract, up to the stated numeric allowance.

### Likelihood Explanation
Exploitability hinges on whether `"*"` is accepted as a valid `ClarityName` for either (a) a real `define-fungible-token` name, or (b) simply as the string argument passed into `with-ft` (which does not require the name to correspond to an actually-defined token at allowance-construction time — the check only compares `AssetIdentifier`s, and the `AssetIdentifier` is entirely attacker/author-controlled data, not validated against a token registry at the time the allowance is built). Since `ClarityName` validation was not directly inspected in this pass, whether `"*"` round-trips through `ClarityName::try_from` is an open question that should be verified before treating this as consensus-critical; however, the code path itself — a hard-coded sentinel value used to encode wildcard semantics inside the same type that also carries genuine user-supplied names, with no reservation of the sentinel — is a structural equality-breaking flaw independent of that detail, since nothing prevents `eval_allowance` from accepting `"*"` as an argument to `with-ft`.

### Recommendation
Do not overload `AssetIdentifier.asset_name` to encode wildcard intent. Represent "all fungible assets in this contract" as a distinct `Allowance` variant (e.g., `Allowance::FtAll { contract_identifier, amount }`) that is impossible to construct via a normal `asset_name` string argument, so a legitimately-named asset (however unusual) can never collide with the wildcard sentinel. Alternatively, explicitly reject `"*"` (and any other sentinel value) at `AllowanceWithFt` parse time so it can never be supplied as a real asset name, and require whatever new native the wildcard capability is exposed through (if any) to construct the wildcard variant directly rather than through the shared identifier type.

### Proof of Concept
Conceptual PoC (pending confirmation that `"*"` is accepted by `ClarityName::try_from`):
1. A contract `token-factory` defines two fungible tokens: `alpha` and `beta` via `define-fungible-token`.
2. A wallet/dApp builds a `restrict-assets?`/`as-contract?` guarded call intending to authorize only `alpha` transfers: `(with-ft 'SP...token-factory "*" u1000)` — either because the caller mistakenly (or maliciously, if the asset name is attacker-influenced input) supplies `"*"` instead of `"alpha"`.
3. Inside the protected scope, the callee contract transfers `1000` units of `beta` (a completely different fungible asset from the same contract) instead of `alpha`.
4. In `check_allowances`, the `beta` movement is looked up in `ft_allowances` by its exact `AssetIdentifier`, fails to find a match, but then successfully matches the wildcard entry `AssetIdentifier { contract_identifier: token-factory, asset_name: "*" }` created in step 2, so no violation is recorded. [4](#0-3) 
5. Result: `beta` moves past a check that was only supposed to authorize `alpha`, breaking the authorization scoping the caller believed they had configured.
