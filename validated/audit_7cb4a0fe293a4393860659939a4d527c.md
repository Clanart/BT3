### Title
Bridge circuit accepts a payout transaction that spends the registered withdrawal outpoint but pays nothing to the withdrawer, letting an operator be reimbursed for value it never delivered - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` verifies that the payout transaction's input at `payout_input_index` correctly references the withdrawal outpoint proven by `verify_storage_proofs`, but it never inspects any *output* of that same transaction to confirm that the withdrawer's script/amount was actually paid. `deposit_constant` and `journal_hash` are built purely from txid/pubkey/round linkage data, with no output-value or output-script commitment, so a payout transaction that consumes the correct input and routes 100% of the value to fees/anchor still produces a valid journal hash.

### Finding Description
The binding that must hold is: `value paid to withdrawer's script in payout_tx == amount Citrea credits operator for this withdrawal`. Tracing `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs):

- `verify_storage_proofs` recovers `(user_wd_outpoint, vout, move_txid)` from Citrea storage (index 7/8), with no "amount" or "destination script" field ever extracted [1](#0-0) .
- The circuit only asserts that `input[payout_input_index].previous_output` matches this outpoint's txid and vout [2](#0-1) .
- `get_first_op_return_output` is then used purely to extract `operator_xonlypk`, a public, attacker-controllable/known value with no cryptographic tie to any transaction output value [3](#0-2) [4](#0-3) .
- `deposit_constant` is a SHA-256 over `move_txid`, watchtower pubkeys digest, `operator_xonlypk`, `watchtower_challenge_connector_start_idx`, `round_txid`, `kickoff_round_vout`, and `genesis_state_hash` - none of which encode any output value or output script pubkey of the payout transaction [5](#0-4) .
- `journal_hash` further folds in only `payout_tx_blockhash`, `latest_blockhash`, and `challenge_sending_watchtowers`, again with no amount/output binding [6](#0-5) .

Nowhere between reading `BridgeCircuitInput` and `guest.commit(journal_hash.as_bytes())` does the circuit iterate `input.payout_spv.transaction.output` to check that some output pays the withdrawer's registered script pubkey the correct value. As long as the attacker constructs a transaction that spends `previous_output.txid/vout == user_wd_outpoint/vout` at `payout_input_index` and includes any OP_RETURN naming a real operator's public xonly pubkey, the assert block, SPV proof, storage proofs, and Groth16/watchtower checks all pass and the circuit emits a valid `journal_hash` — regardless of whether any real value reached the withdrawer.

### Impact Explanation
An operator (or any party colluding with/impersonating one via the public xonly pubkey) can be credited as having fronted a withdrawal payout while the withdrawer receives 0 sats, since the reimbursement is keyed off `deposit_constant`/`journal_hash`, which never encodes the payout amount or destination. This is a direct instance of "an operator reimbursed for a payout it never funded" (Critical), and is repeatable for every withdrawal/operator pair since the missing check is structural, not data-dependent.

### Likelihood Explanation
The attacker only needs to broadcast a Bitcoin transaction spending the specific withdrawal outpoint (whose bytes the attacker/withdrawer chooses per the threat model) with a fee-only payout and a crafted OP_RETURN — no signature over the operator's identity or the payout amount is required, and no privileged role is needed. The only cost is standard Bitcoin transaction fees. Preconditions (public operator xonlypk, existing withdrawal registration) are already satisfied by normal protocol operation.

### Recommendation
Bind the actual value transfer into the circuit's committed output: locate the payout output(s) of `input.payout_spv.transaction` that pay the withdrawer's registered script pubkey/amount (sourced from the Citrea withdrawal record, not just the input outpoint), assert the paid value meets or exceeds the required withdrawal amount, and fold that output's script/value into `deposit_constant` or `journal_hash` so a divergent payout cannot produce the same journal hash as a genuine one.

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
```

```rust
pub fn journal_hash(
    payout_tx_blockhash: PayoutTxBlockhash,
    latest_blockhash: LatestBlockhash,
    challenge_sending_watchtowers: ChallengeSendingWatchtowers,
    deposit_constant: DepositConstant,
) -> blake3::Hash {
    let concatenated_data = [
        payout_tx_blockhash.0,
        latest_blockhash.0,
        challenge_sending_watchtowers.0,
    ]
    .concat();

    let binding = blake3::hash(&concatenated_data);
    let hash_bytes = binding.as_bytes();

    let concat_journal = [deposit_constant.0, *hash_bytes].concat();

    blake3::hash(&concat_journal)
}
```
