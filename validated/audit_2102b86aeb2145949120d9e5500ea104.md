### Title
`prepare-commit-msg`/`commit-msg` Git Hooks Silently Rewrite Commit Content on Routine `git commit` - (File: `app/src/lib/git/commit.ts`, `app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/hooks-proxy.ts`)

### Summary
The external report's core pattern is: a routine, automated operation (`executePriceChange()` upkeep) transfers control to an object the operator does not fully trust (the secondary fee address), which can hijack execution via a callback and corrupt or block the outcome of the "upkeep". The closest analog in this codebase is Desktop's Git-hooks execution feature: every `git commit`, `merge`, `pull`, and `push` performed through Desktop silently hands off execution to scripts discovered inside the repository being operated on, via `interceptHooks` (`app/src/lib/git/commit.ts:58-65`, `app/src/lib/git/merge.ts:55`), resolved and run out-of-process by `withHooksEnv()`/`createHooksProxy()` (`app/src/lib/hooks/with-hooks-env.ts:29-96`, `app/src/lib/hooks/hooks-proxy.ts:144-309`).

### Finding Description
`getRepoHooks()` enumerates hook scripts to run for a given git invocation by resolving `core.hooksPath` from the repository's own git config (falling back to `.git/hooks`) and yielding any executable file matching a known hook name [1](#0-0) . `withHooksEnv()` then stands up a local proxy server and rewrites `GIT_CONFIG_PARAMETERS` so that `core.hooksPath` points at a temp directory of hook-proxy stubs, causing `git commit`/`merge`/`pull`/`push` to invoke whatever hook scripts were discovered [2](#0-1) . The actual hook process is then spawned with the user's real shell environment and a `GITHUB_DESKTOP=1` marker via `createHooksProxy()` [3](#0-2) .

`createCommit()` explicitly intercepts `pre-commit`, `prepare-commit-msg`, `commit-msg`, and `post-commit` for every commit made through the UI [4](#0-3) , and `merge()` intercepts `pre-merge-commit`/`post-merge`/`commit-msg` for every merge [5](#0-4) . These hooks run with full ability to rewrite the commit message (`prepare-commit-msg`, `commit-msg`), modify staged content before it is written to the object database (`pre-commit`), or execute arbitrary shell commands with the user's full shell environment — mirroring the report's "secondary fee address" that can intercept and corrupt the outcome of a supposedly deterministic, automated flow. Unlike the smart-contract analog where the fix is to avoid the untrusted callback entirely, Desktop's design intentionally performs this callback as a first-class feature, and the only mitigating control is the `getHooksEnvEnabled()`/`enableHooksEnvironment` flag pair, which gates whether hooks execute at all [6](#0-5) ; once enabled there is no further per-repository trust prompt, diff review of the hook script, or confirmation before Desktop silently executes it during what looks to the user like a normal commit/merge/push action.

### Impact Explanation
If a repository (or a directory whose path becomes `core.hooksPath`, e.g. via a checked-in setup step the user runs once) contains hook scripts, opening that repository in Desktop and performing an ordinary commit, merge, pull, or push causes those scripts to run automatically and silently rewrite the commit message/content or execute arbitrary commands, exactly the "silent corruption of what the user commits or pushes" and "code execution" impacts called out as valid in this exercise.

### Likelihood Explanation
Likelihood is bounded by the fact that `core.hooksPath` and `.git/hooks` are local, non-versioned locations that a plain `git clone` does not populate by itself — I could not find code in `clone.ts` that copies hook scripts from the remote or sets `core.hooksPath` from remote-controlled data [7](#0-6) . The realistic trigger requires the hooks-path to already be pointed at repository content (a common but user-initiated pattern, e.g. tooling that runs `git config core.hooksPath <dir>` as part of project setup). I was not able to fully trace, within the available index, whether any Desktop-driven flow (submodule init, template directory, or config import) can cause `core.hooksPath` or `.git/hooks` to be populated purely from untrusted repository content without an explicit, separate user action outside Desktop.

### Recommendation
Given the uncertainty above, this should be treated as a design-risk finding rather than a proven, fully attacker-triggerable exploit chain. Confirm whether any Desktop code path (clone with `--recursive`, submodule updates in `app/src/lib/git/submodule.ts`, or template/`init.templateDir` handling) can cause `core.hooksPath` or `.git/hooks` contents to originate from remote/repository-controlled data without a separate, explicit local action; if so, treat hook discovery as untrusted input and require an explicit per-repository trust prompt (similar to VS Code's workspace-trust model) before `getHooksEnvEnabled()` is honored, rather than relying solely on the global `git-hooks-env-enabled` setting.

### Proof of Concept
Not independently verified against a live build; based on static code review, the theoretical chain is: (1) a repository or its `core.hooksPath` target contains a `prepare-commit-msg`/`commit-msg` script, (2) the user has "Load Git hook environment" enabled in Preferences (`app/src/ui/preferences/git.tsx:79-93`), (3) the user performs a normal commit/merge/push in Desktop, (4) `getRepoHooks()` finds and `createHooksProxy()` executes the script, silently altering the commit message or running arbitrary commands with the user's shell environment [3](#0-2) .

```typescript
export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
```

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

  const ext = __WIN32__ ? '.exe' : ''
  const processProxyPath = join(__dirname, `process-proxy${ext}`)

  const token = crypto.randomUUID()
  const tmpHooksDir = await mkdtemp(join(tmpdir(), 'desktop-git-hooks-'))
  const hooksProxy = createHooksProxy(
    cwd =>
      memoizedGetShellEnv(
        getGitHookEnvShell(),
        cwd,
        // We always cache environment per token (i.e. per operation, e.g commit, apply, etc)
        // but we can optionally cache it over multiple operations in the same repository if the user
        // has enabled that setting.
        getCacheHooksEnv() ? 'global' : token
      ),
    tmpHooksDir,
    opts?.onHookProgress,
    opts?.onHookFailure
  )

  const server = createProxyProcessServer(
    conn =>
      hooksProxy(conn).catch(err => {
        log.error(`hooks proxy failed:`, err)
        conn.exit(1).catch(() => {})
      }),
    { validateConnection: async receivedToken => receivedToken === token }
  )
  const port = await new Promise<number>(resolve => {
    server.listen(0, '127.0.0.1', () =>
      resolve((server.address() as AddressInfo).port)
    )
  })
  try {
    for (const hook of hooks) {
      await cp(processProxyPath, join(tmpHooksDir, `${hook}${ext}`))
    }

    const existingGitEnvConfig =
      opts?.env?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    return await fn({
      // TODO: Do we need to escape tmpHooksDir? Could it possibly include a single quote?
      // probably not?
      GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'core.hooksPath=${tmpHooksDir}'`,
      PROCESS_PROXY_PORT: `${port}`,
      PROCESS_PROXY_TOKEN: token,
    })
```

```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
```
