### Title
`SignableTransaction::new` floors the minimum-relay-fee threshold, accepting transactions that underpay the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report concerns rounding that favors the transacting user instead of the "vault"/system, leaking value. The analog in Serai's in-scope code is in `SignableTransaction::new`, which checks the transaction's fee against Bitcoin's minimum relay fee using floor division, computing a threshold strictly lower than the real requirement and thereby admitting transactions that will not be relayed.

### Finding Description
`SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes` and rejects the transaction only if it is below `(DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` [1](#0-0) . `DEFAULT_MIN_RELAY_TX_FEE` is denominated in sats per kilo-vbyte, so the true minimum fee is `ceil(min_fee_rate_per_kvbyte * vbytes / 1000)`. The integer division truncates, so for `vbytes` values not divisible by the denominator the accepted threshold is up to ~0.999 of the real minimum. Analogous to `previewMint`/`previewWithdraw` rounding toward the user, this rounds the system-enforced minimum toward the transaction creator, who pays less than the fee floor the code intends to enforce.

### Impact Explanation
A `SignableTransaction` can be constructed (and signed by the FROST multisig flow via `attempt_sign`) whose `needed_fee` satisfies the floored check yet is below the actual `DEFAULT_MIN_RELAY_TX_FEE`-derived minimum for its vsize. Such a transaction fails Bitcoin Core's relay policy, producing a signed transaction that will not propagate — funds committed to outputs the network will never confirm. The miss is at most a fraction of a satoshi per transaction (`fee_per_vbyte` is integral, so divergence requires sub-1-sat/vB rates), but the rounding direction is systematically in favor of the transaction creator rather than the enforced floor.

### Likelihood Explanation
Reachable by anyone constructing a `SignableTransaction` via the public `new` API with untrusted `fee_per_vbyte` and payments. Exploitation as value extraction is limited — the leak is sub-satoshi — but the incorrect inequality is deterministic whenever `DEFAULT_MIN_RELAY_TX_FEE * vbytes` is not a multiple of 1000, i.e., almost always for `fee_per_vbyte < 1`-scale regimes or when the policy constant is divided down. Severity: Medium-Low; the primary risk is producing non-relayable transactions, not fund theft.

### Recommendation
Round the minimum-fee bound up: `((DEFAULT_MIN_RELAY_TX_FEE as u64 * vbytes) + 999) / 1000`, matching the same "round in favor of the system" direction prescribed by EIP-4626's rounding guidance in the source report.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`, `DEFAULT_MIN_RELAY_TX_FEE = 1000` (sats/kvB), so the real minimum is `ceil(1000 * vbytes / 1000) = vbytes` sats; for other effective rates or intermediate constants the floored expression `X * vbytes / 1000` undercounts by `(X * vbytes) % 1000 / 1000` sats. A caller passing `fee_per_vbyte` such that `fee_per_vbyte * vbytes` lands in `[floor(min), ceil(min))` produces a `SignableTransaction` accepted by `new` whose fee is below relay policy, which `sign`/broadcast then fails to propagate.
