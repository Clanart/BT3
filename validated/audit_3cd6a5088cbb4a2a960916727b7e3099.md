### Title
Panic on HashMap index of unregistered participant during PedPoP blame/decryption - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2018-10373 is a crafted-input crash (NULL deref → application abort) in binutils. The Serai analog is a reachable Rust panic (`HashMap` index on a missing key / `assert!` on duplicate key) inside the PedPoP encryption layer, triggered by messages an unprivileged DKG participant controls. Several `read`/`decrypt`/blame paths index `self.enc_keys[...]` or assert invariants without returning an error, so malformed or out-of-protocol participant messages crash the host instead of producing `DecryptionError`.

### Finding Description
The bug class is "untrusted input reaches a code path that assumes a value exists, crashing the process". In `Decryption::decrypt_with_proof`, the decryptor's registered encryption key is fetched via a direct index: `&[self.enc_keys[&decryptor], *proof.key]` at crypto/dkg/pedpop/src/encryption.rs:388. If `decryptor` is a `Participant` that never successfully registered an `EncryptionKeyMessage` (absent from `enc_keys`), this panics rather than returning `DecryptionError`. The function is invoked during blame resolution, where the accused/accuser identities come from protocol messages. Similarly, `Decryption::register` uses `assert!(!self.enc_keys.contains_key(&participant), ...)` at crypto/dkg/pedpop/src/encryption.rs:356-359, so a participant whose message is processed twice panics instead of erroring, and `Encryption::encrypt` indexes `self.decryption.enc_keys[&participant]` at crypto/dkg/pedpop/src/encryption.rs:466.

The read path (`EncryptedMessage::read`, `EncryptionKeyMessage::read`, `EncryptionKeyProof::read` at encryption.rs:57-59, 171-177, 267-269) correctly returns `io::Result`, but validation of "was this participant registered" is deferred to these panicking lookups. An analogous out-of-bounds-style index also exists in `ThresholdKeys::new`/`view` (`self.core.verification_shares[i]` at crypto/dkg/src/lib.rs:378 and 502), though `read` populates keys 1..=n so that specific site is not reachable via `ThresholdKeys::read`; the pedpop `enc_keys` map has no such completeness guarantee.

### Impact Explanation
An unprivileged participant in a PedPoP key-generation session can cause a panic (abort/unwind) in any honest participant processing blame or a duplicate registration. In an async/node context this can crash the key-gen task or, if panics are fatal/`panic=abort`, the whole process — a denial of service matching the CVE's class (remote-crafted input → crash, CVSS 6.5-equivalent availability impact). No secret leakage or forgery, so severity is Medium.

### Likelihood Explanation
Triggering requires sending DKG messages: either an `EncryptionKeyMessage` processed twice for the same participant, or inducing a blame flow whose `decrypt_with_proof` is called for a participant that never registered a key. Both are within the message surface PedPoP exposes to mutually distrusting participants; no collusion or special privileges needed. Whether the outer protocol layer deduplicates `EncryptionKeyMessage`s before calling `register` determines how easy the `assert!` path is; the `enc_keys[&decryptor]` index depends only on an absent registration, which a non-cooperating participant can always arrange by not sending their key message while still being named in a blame flow.

### Recommendation
Replace panicking lookups with fallible access: return `DecryptionError` (or a dedicated error) when `enc_keys.get(&decryptor)`/`enc_keys.get(&participant)` returns `None` in `decrypt_with_proof` and `encrypt`, and change `Decryption::register`'s `assert!` into a returned error for duplicate registration. Apply the same pattern to any `HashMap` indexing keyed by remote-supplied `Participant` values.

//    decryption.decrypt_with_proof(from, P_bad, msg, Some(proof))

//    self.enc_keys[&decryptor]            // encryption.rs:388
