### Title
Oracle staleness check is bypassed by future-timestamped price feeds, allowing stale/manipulated prices to be treated as fresh - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`oracle-timestamp-fresh` in `v0-4-market.clar` computes the staleness delta as `u0` whenever the feed timestamp `ts` is greater than `stacks-block-time`, instead of enforcing an upper bound. Combined with the monotonic check `ts >= prev`, this means any price update whose reported timestamp is set ahead of the current block time is unconditionally treated as "fresh" and, once accepted, permanently raises the floor (`last-update`) for that feed — as with the external report's root cause, a storage/gating value is advanced based on an assumption that doesn't hold, and downstream consumers (health checks, liquidations, borrow/withdraw sizing) silently use the wrong (stale-but-accepted) price without reverting.

### Finding Description
`price-resolve` gates every price used in collateral/debt valuation through `oracle-timestamp-fresh`: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

If `ts > stacks-block-time` (the feed's reported timestamp is ahead of the chain's current time), `delta` is forced to `u0`, so `(<= delta max-staleness)` is trivially true regardless of how stale or manipulated the actual price data is. The second clause `(>= ts prev)` is also trivially satisfied for a larger-than-current `ts`, so the monotonicity guard provides no additional protection in this branch.

This gate feeds directly into `price-resolve`, which is the single choke point used for every collateral/debt valuation, health check, and liquidation calculation: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        ...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Because `map-set last-update key timestamp` persists any accepted (even bogus/future) timestamp as the new floor `prev`, a single future-dated update permanently raises `last-update` for that feed. Any subsequent legitimate-but-real-time update from Pyth/DIA with a normal, current timestamp will now fail the `(>= ts prev)` monotonicity check and revert with `ERR-ORACLE-INVARIANT` — denying fresh price updates — while any other future-dated (still stale/incorrect) submission continues to pass because it again hits the `delta = 0` branch. This is a logic defect in the market contract's own gating function (not simply "bad third-party oracle data" — the code fails to bound the future-side of the delta at all), so it is in scope per the rules.

### Impact Explanation
Because `price-resolve` underlies `get-assets`/`get-notional-evaluation` used in `borrow`, `collateral-remove`, and `liquidate`, an accepted stale/incorrect price:
- Can inflate a user's apparent collateral value or deflate apparent debt value, allowing borrowing or collateral withdrawal beyond what the true market price would allow (health check passes on a wrong value) — [3](#0-2) .
- Can block legitimate liquidations of genuinely unsafe positions if the stale price makes the position appear healthy, or conversely can allow liquidators to seize collateral against an incorrect valuation — [4](#0-3) .
- Once a future timestamp is accepted, it can permanently freeze further updates to that feed (denial of price refresh) until the real chain time catches up to the recorded `last-update` value, effectively freezing all positions that depend on that asset's fresh pricing.

This lands in the **temporary freezing of funds** / **protocol insolvency** impact classes: positions can be over-borrowed against a wrong price (protocol insolvency risk) or health/liquidation availability can be frozen for an asset once a bad timestamp is recorded.

### Likelihood Explanation
The `ts` value is taken from oracle response data (`publish-time` for Pyth, converted timestamp for DIA) and is not independently bounded against `stacks-block-time` before this delta calculation — the code only special-cases the "future" branch to zero out delta rather than rejecting it. Any minor clock skew between the oracle publisher and the chain, a relayed/replayed price message, or a malformed feed payload could trigger the `ts > stacks-block-time` branch. Given price feeds are submitted permissionlessly via `write-feeds`/`write-feed` (as referenced in `price-resolve`'s callers), the condition is plausibly reachable without requiring a compromised oracle key — it can be triggered by ordinary clock drift or a stale relay.

### Recommendation
Bound the future side of the delta explicitly and reject timestamps that are unreasonably ahead of `stacks-block-time`, e.g.:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   (- ts stacks-block-time)   ;; measure forward skew, don't zero it
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
This ensures a future-dated timestamp is only accepted within the same staleness tolerance window (e.g., small clock skew), rather than being unconditionally treated as fresh, and prevents an attacker/relay from permanently poisoning the `last-update` floor for a feed.

### Proof of Concept
Uncertainty note: I could not execute a live Clarinet/Foundry-equivalent test against this repo in this session; the following is a code-level trace, not an executed test.

1. Attacker (or a relay with clock skew) submits a Pyth/DIA price update for asset `X` whose `publish-time` is, e.g., `stacks-block-time + 10_000`.
2. `resolve-price-feed` → `resolve-pyth`/`resolve-dia` returns `{ value: final-price, timestamp: ts }` with `ts > stacks-block-time` — [5](#0-4) .
3. `price-resolve` calls `oracle-timestamp-fresh(ts, last-update-time, max-staleness)`; since `ts > stacks-block-time`, `delta = u0`, so `(<= delta max-staleness)` passes and `(>= ts prev)` passes because `ts` is arbitrarily large — [1](#0-0) .
4. `final-price` is accepted, and `map-set last-update key ts` persists the inflated timestamp as the new floor — [6](#0-5) .
5. All subsequent calls to `borrow`, `collateral-remove` (with debt), and `liquidate` for that asset now use this accepted (possibly wrong) price for health calculations, and any later legitimate real-time price update with `ts < prev` will revert with `ERR-ORACLE-INVARIANT`, freezing further price refresh for that asset until on-chain `stacks-block-time` exceeds the injected future value.
