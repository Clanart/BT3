Based on my research, I found a plausible analog in the `kaiax/gasless` module, but I want to flag upfront that I could not fully verify one key assumption (bundle atomicity between `LendTxGenerator` and `GaslessSwapTx`) within the available tool budget — this is called out explicitly below.

### Title
Stale-Price Admission Check in Gasless Swap Allows Sponsor-Funded Transactions to be Validated Against a Rate That No Longer Holds at Execution Time - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The KIP-247 gasless module validates a `GaslessSwapTx`'s slippage-related fields (`minAmountOut`, required `amountIn`) at transaction-pool admission time using a single, synchronous view call against the *current* AMM state, with no mechanism to ensure this check remains valid at actual block-execution time.

### Finding Description
`checkBalanceForSwap` in [1](#0-0)  enforces:
- `minAmountOut >= amountRepay`
- `amountIn >= routerContract.GetAmountIn(nil, token, minAmountOut)` — a live call to `GaslessSwapRouter.GetAmountIn`, i.e. a snapshot of the **current** exchange rate at admission time.

This is precisely analogous to the reported bug class: a swap-amount check is performed without binding it to the price/state that will actually be in effect when the swap executes. The tx-pool only re-validates these fields when the transaction is (re-)promoted to pending, not at the moment of block execution, and gasless transactions skip the ordinary sender-balance check entirely per the module's own documentation ( [2](#0-1) ). Meanwhile the block proposer unconditionally funds the user's gas cost up front via `GetLendTxGenerator`, which is prepended before the approve/swap transactions in the bundle ( [3](#0-2)  and [4](#0-3) ).

Because the AMM reserves used by `GetAmountIn` can shift between admission-time validation and inclusion-time execution (through ordinary trading activity, or through an adversarial searcher/user deliberately trading against the same pool before their own gasless swap is included), the swap that passed the tx-pool's stale-rate check can still fail its on-chain `minAmountOut` requirement inside `GaslessSwapRouter.swapForGas` at execution time.

### Impact Explanation
If the `GaslessSwapTx` reverts at execution because the real-time swap output falls below `minAmountOut` (a condition the admission-time check could not have detected since it used a stale rate), the gas cost has already been consumed on-chain, and per the module's documented repayment model ("user repays the lent amount **during** gasless swap" — [5](#0-4) ), repayment to the block proposer is contingent on a successful swap. This creates the potential for the block proposer's lent KAIA to be spent on gas for a transaction that cannot repay it, since the user's swap-side revert prevents `amountRepay` from ever reaching the proposer.

### Likelihood Explanation
Reachable by any unprivileged gasless-swap submitter with a single `swapForGas` transaction; no special privileges are required, and price movement between tx-pool admission and block-inclusion is a routine occurrence for actively-traded AMM pools, not an exotic edge case. However, whether this materializes into actual unauthorized value loss to the proposer depends on whether the `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` bundle is executed atomically (i.e., whether the whole bundle — including the lend transfer — is rolled back/excluded if `GaslessSwapTx` reverts). I was not able to confirm the exact atomicity semantics of `work/builder.Bundle` in the time available, so I cannot state with certainty that fund loss occurs versus merely a benign, bundle-excluded no-op. This uncertainty should be resolved before treating this as a confirmed value-loss bug.

### Recommendation
- Re-validate `minAmountOut`/`GetAmountIn` immediately before or during block-building/execution (not only at initial tx-pool admission) so that stale-price approvals cannot slip into a block.
- Confirm and, if necessary, enforce that the `LendTxGenerator` transaction is only ever included/finalized atomically with a successful `GaslessSwapTx`, so a reverted swap cannot result in an uncompensated lend.
- Consider adding a maximum allowable staleness window or a price-deviation bound between the pool-admission check and inclusion to reduce the odds of doomed-to-revert gasless swaps being bundled at proposer expense.

### Proof of Concept
1. Attacker (or any user) submits a `GaslessSwapTx` with `minAmountOut` computed against the pool's current reserves; `checkBalanceForSwap` passes because `GetAmountIn(token, minAmountOut)` reflects the state at that instant ( [6](#0-5) ).
2. Before this bundle is mined, the same pool's reserves shift unfavorably (ordinary trading, or an adversarial trade the attacker times deliberately).
3. The block proposer includes the bundle `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` ( [4](#0-3) ); `LendTxGenerator` transfers KAIA to the user to cover gas.
4. `GaslessSwapRouter.swapForGas` executes against the now-current (worse) reserves and reverts because on-chain output < `minAmountOut`, consuming gas without producing `amountRepay`.
5. Whether the proposer's lent KAIA is unrecoverable in this scenario depends on bundle atomicity, which requires further verification in `work/builder` (not confirmed in this analysis).

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}
