### Title
Infinite loop via cyclic coin dependency in `Offer.get_root_removal` when processing an attacker-crafted offer - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_root_removal()` walks a coin's ancestry chain within the coin spends bundled inside an `Offer` object to find the "primary" (non-ephemeral) coin backing a settlement payment. The traversal relies on `parent_coin_info` fields, which are attacker-controlled values chosen by whoever constructs the offer's `SpendBundle` — they are not validated against real on-chain lineage before this function is called. If a malicious offer author crafts two (or more) coin spends inside the bundle whose `parent_coin_info` values form a cycle, the `while` loop's exit condition (`coin not in non_ephemeral_removals`) can never become true, causing the loop to run indefinitely, analogous to the "Loop with Unreachable Exit Condition" pattern described in CVE-2026-44186 for `mod_proxy_ftp`.

### Finding Description
`get_root_removal` is: [1](#0-0) 

```python
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
``` [2](#0-1) 

`non_ephemeral_removals` is defined as the set of removal coins whose `parent_coin_info` does not match the `name()` of *any other removal coin in the bundle*. This determination is purely a function of attacker-supplied `Coin` fields (`parent_coin_info`, `puzzle_hash`, `amount`) inside `self._bundle.coin_spends`, which are never checked against the actual blockchain state before this method runs.

If two coins `A` and `B` in the same offer bundle are crafted such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`, then neither `A` nor `B` belongs to `non_ephemeral_removals` (each one's parent id is present in the set of other removal names). The `while` loop will alternate `coin = A → B → A → B → ...` forever, since `next()` will always find a match and the exit condition never becomes true.

`get_root_removal` is invoked by `get_primary_coins()`, which iterates every coin returned by `get_offered_coins()` and calls `get_root_removal` on each — meaning any offer containing a settlement-payment coin whose ancestry passes through such a cycle will hang: [2](#0-1) 

`get_primary_coins`/`get_pending_amounts` are used by wallet-side reasoning about offers (pending-amount computation), and `Offer` objects are directly deserialized from untrusted bech32/hex offer files supplied by a counterparty — the offer's `SpendBundle` is not required to correspond to real on-chain coins at the point these summary/traversal helpers run (`Offer.from_bech32`/`Offer.from_bytes` perform no lineage validation of `parent_coin_info` chains). Any wallet user, DID/NFT/CAT trade counterparty, or CLI/RPC caller who loads/examines an untrusted offer through paths that end up calling `get_primary_coins`/`get_pending_amounts` is exposed to this hang.

This is unrelated to CLVM cost accounting or mempool cost limits — the loop lives entirely in Python wallet code and has no cost meter, so a crafted offer can freeze the wallet process indefinitely (or block async event loop for a very long time), matching the report's "Loop with Unreachable Exit Condition" bug class where attacker-controlled data prevents the loop from terminating.

### Impact Explanation
A malicious offer counterparty can construct an offer file with a cyclic coin ancestry among its bundled coin spends. When a victim wallet processes that offer through any code path that calls `get_primary_coins()`/`get_pending_amounts()` (offer amount/pending-balance computation), the wallet enters an infinite loop, hanging the wallet's processing thread/event loop. This is a spend-triggered transaction-processing halt reachable by any offer counterparty without needing any privileged access — a legitimate high-severity denial-of-service against the wallet.

### Likelihood Explanation
Constructing such a cyclic-parent offer requires only crafting a `SpendBundle` with attacker-chosen `parent_coin_info`/`puzzle_hash`/`amount` fields for the offer's coin spends (these fields are freely settable when building a `CoinSpend`/`Coin`, no on-chain validity is required for this function to be exercised) and getting a victim to load/inspect the offer (a routine operation for anyone evaluating an incoming trade). This is easily reachable and requires no signature validation or chain state, making exploitation straightforward once a victim opens the crafted offer.

### Recommendation
In `Offer.get_root_removal` (and the underlying ancestor-walk logic), detect cycles during traversal — e.g., track visited coin IDs and raise a `ValueError`/`ConsensusError` if a coin is revisited, or bound the loop by the number of removals in the bundle (`len(all_removals)`) before declaring the offer malformed. Apply the same protection to any other coin-ancestor traversal in `offer.py` that relies on attacker-controlled `parent_coin_info` chains (e.g., re-audit `get_cancellation_coins`'s dependency loops for similar cyclic-input assumptions).

### Proof of Concept
Conceptually: construct an `Offer` whose bundle contains coin spends `A` and `B` where:
- `A = Coin(parent_coin_info=B.name(), puzzle_hash=..., amount=...)`
- `B = Coin(parent_coin_info=A.name(), puzzle_hash=..., amount=...)`

and where one of the settlement-payment coins offered resolves (via `get_offered_coins()`) to an ancestor chain passing through `A`/`B`. Call `offer.get_primary_coins()` (or any caller that reaches `get_root_removal` on such a coin) — the call never returns, because `next(c for c in all_removals if c.name() == coin.parent_coin_info)` will alternate between `A` and `B` forever since both fail the `non_ephemeral_removals` membership test on every iteration.

Note: I could not fully trace every GUI/RPC call path that invokes `get_primary_coins`/`get_pending_amounts` on unvalidated attacker offers within the indexed portion of the codebase (some files were only partially covered by search results), so the exact set of reachable entry points (beyond the wallet's pending-amount/summary computation) should be confirmed against the full source before remediation.
