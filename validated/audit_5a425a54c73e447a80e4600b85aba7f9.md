### Title
Unsafe raw `IERC20.transfer` call for reward payout in `ArbWomUp.incentiveDeposit` is incompatible with non-standard ERC20 tokens - (File: `wombat/ArbWomUp.sol`)

### Summary
`ArbWomUp.incentiveDeposit()` pays out the configurable `usdt` reward token to the caller using a raw, unchecked `IERC20(usdt).transfer(...)` call instead of OpenZeppelin's `safeTransfer`, even though the same contract already imports and uses `SafeERC20` for the WOM deposit leg of the same function.

### Finding Description
In `ArbWomUp.sol`, `SafeERC20` is imported and used via `using SafeERC20 for IERC20;` [1](#0-0) , and the deposit path correctly uses `safeTransferFrom` for the `wom` token: [2](#0-1) 

However, the user-reachable `incentiveDeposit` function pays out the reward token (`usdt`) with a raw, unchecked `transfer` call whose return value is ignored: [3](#0-2) 

`usdt` is a settable admin parameter, not hardcoded to a specific well-behaved token address [4](#0-3) . If it is ever set to a token that returns `false` on failure instead of reverting (e.g. `ZRX`-style tokens), the unchecked `.transfer` call will silently "succeed" from the contract's perspective even though no tokens were actually delivered to the caller. Because `claimedReward[msg.sender] += rewardToSend;` is unconditionally updated right before the transfer regardless of whether the transfer truly succeeded [5](#0-4) , and `claimedReward` is subtracted from the user's future reward entitlement in `getRewardAmount` [6](#0-5) , a failed-but-unreverted transfer permanently reduces/loses the user's future claimable reward without them ever receiving the corresponding tokens.

This is the exact bug class from the referenced report: code directly calling ERC20 `transfer`/`transferFrom` without using `SafeERC20`, which breaks with tokens that return `false` on failure rather than reverting.

### Impact Explanation
Because the accounting update (`claimedReward[msg.sender] += rewardToSend`) is not conditioned on the transfer's actual success, a non-reverting-on-failure `usdt` token causes permanent loss of the user's unclaimed reward allocation — the user's tier/tranche of reward is marked as claimed forever even though the tokens never left the contract. This matches the accepted impact category of "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
Likelihood depends on whether the configured `usdt` address is a token with this specific non-standard behavior (returns `false` instead of reverting). This is a known real-world token behavior class (e.g. `ZRX`), and since `usdt`/reward token is admin-configurable rather than fixed to a single audited address, the risk exists any time such a token is used as the reward asset for this airdrop incentive contract.

### Recommendation
Replace the raw `IERC20(usdt).transfer(msg.sender, rewardToSend);` call with `IERC20(usdt).safeTransfer(msg.sender, rewardToSend);` using the already-imported `SafeERC20` library (consistent with the `safeTransferFrom` already used in `_deposit`), so that failures are always reverted and reward accounting can never advance without an actual successful transfer.

### Proof of Concept
1. Owner initializes `ArbWomUp` with `usdt` set to a token that returns `false` on failed `transfer` (rather than reverting), e.g. a `ZRX`-style token, or a token whose balance for the contract becomes insufficient at call time (this can happen for other reward tiers/tokens later swapped in via the same pattern).
2. A user calls `incentiveDeposit(_amount)`, depositing WOM correctly via `safeTransferFrom`.
3. `getRewardAmount` computes `rewardToSend`; `claimedReward[msg.sender] += rewardToSend` executes unconditionally.
4. `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` (transfer fails) but the call does not revert.
5. The user's on-chain reward balance is unchanged (they received nothing), yet `claimedReward[msg.sender]` is permanently incremented, permanently reducing all future reward computations in `getRewardAmount` for that user — the difference is unclaimed yield that is now unrecoverable.

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 usdtReward = (rewardAmount / DENOMINATOR) - claimedReward[_account];
        uint256 usdtleft = IERC20(usdt).balanceOf(address(this));

        return usdtReward > usdtleft ? usdtleft : usdtReward;
    }
