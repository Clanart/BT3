I have sufficient evidence to confirm the analog. The `IntentsBase._withdraw()` function used by the `IntentGatewayV2`/`ExtrinsicIntents` cross-chain intent settlement flow is a direct local analog of the OLAS M-12 bug: an immutable beneficiary address baked into a cross-chain message, combined with an unconditional ERC-20 `safeTransfer`/`transfer` call, causes any settlement (escrow release or refund) to permanently revert and lock funds if the token blocklists/pauses the beneficiary.

### Title
Blocklisted/paused-token beneficiary permanently locks escrowed intent funds in `IntentsBase._withdraw` / `IntentGatewayV2.withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._withdraw()` (and its Tron counterpart `IntentGatewayV2.withdraw()`) is the single settlement path that releases escrowed order tokens to a `beneficiary` address embedded, at order-placement time, into a cross-chain `WithdrawalRequest` (`RedeemEscrow`/`RefundEscrow`). This beneficiary is fixed inside the ISMP message body dispatched from the destination/source chain and cannot be altered after the fact. If the escrowed token (or the protocol fee token) blocklists that beneficiary or pauses transfers before the message is delivered and processed, the mandatory `IERC20.safeTransfer(beneficiary, amount)` call inside `_withdraw`/`withdraw` reverts, which reverts the whole `onAccept` handling of that unique, one-time incoming ISMP `PostRequest`. [1](#0-0) [2](#0-1) 

### Finding Description
When a solver fills a cross-chain order or a user/anyone cancels an unfilled order, the gateway dispatches a `RedeemEscrow`/`RefundEscrow` request whose body encodes a `WithdrawalRequest{commitment, tokens, beneficiary}` — the beneficiary being either the solver (`msg.sender` at fill time) or the original order user, both fixed at dispatch time: [3](#0-2) [4](#0-3) 

When the message is delivered to the destination host and routed to `onAccept`, it authenticates the source gateway and unconditionally calls `_withdraw`, which for every escrowed token performs `IERC20(token).safeTransfer(beneficiary, amount)` (or the raw low-level `token.call(transfer(...))` in the Tron variant) with no fallback path if the transfer fails: [5](#0-4) [6](#0-5) 

Because `SafeERC20.safeTransfer` reverts on failure (and the Tron `token.call(...)` path explicitly reverts on `!success`), any blocklist-capable or pausable ERC-20 used as an order input token (e.g. USDC) that blocks the beneficiary address makes this transfer permanently fail. Since `beneficiary` is immutable inside the already-dispatched, already-committed cross-chain message, and there is no code path to update it, retarget it, or split "mark filled/refunded" from "transfer funds," the escrowed tokens for that `commitment` are stuck forever in the gateway contract — precisely the OLAS `StakingBase.unstake()`/`_withdraw` bug pattern, but here trapping user/solver escrow funds instead of a staked service NFT.

The same unconditional-transfer-to-fixed-beneficiary pattern also exists in the accumulated transaction-fee payout inside the same function, so even partial remediation attempts (e.g., only unblocking dust) would not help — the whole `_withdraw` call must succeed atomically to finalize: [7](#0-6) 

### Impact Explanation
This is a real fund-lock in the production intent-settlement bridging path (RedeemEscrow/RefundEscrow), not a peripheral utility. Because `_filled[commitment]` is only set when `finalize` succeeds, a reverting transfer means the order is never marked filled/refunded, and the escrow can never be redeemed by anyone — the solver's fill proceeds (or the timeout/cancel proof) is wasted, and the underlying escrowed principal (potentially the full order input amount) is permanently locked in the `IntentsBase`/`IntentGatewayV2` contract, unrecoverable by the rightful beneficiary or any privileged actor, since there is no admin bypass, no beneficiary-update mechanism, and no split "finalize vs pay" step. This matches the required impact class of fund loss/lock in bridge custody and intent settlement.

### Likelihood Explanation
No malicious peer, relayer, prover, or governance actor is required — an ordinary, unprivileged ERC-20 issuer action (adding the beneficiary to a blocklist, e.g., Circle's USDC compliance blacklist, or pausing the token) after an order is placed but before the cross-chain settlement message is processed is sufficient to trigger the failure. Given that stablecoins with blocklist/pause functionality (USDC, USDT) are the primary expected input assets for this intents system, and beneficiaries are end-user or solver addresses outside the protocol's control, this scenario is realistically reachable in production without any attacker action beyond normal usage plus an external compliance event.

### Recommendation
Split settlement into two steps as recommended in the referenced report: (1) unconditionally mark the order as finalized/filled once the cross-chain message is authenticated, decrementing escrow accounting, and (2) attempt the token transfer with a `try/catch` (or low-level call) that, on failure, credits the amount to an internal pull-based balance mapping keyed by `(beneficiary, token)` that the beneficiary (or anyone on their behalf, to a beneficiary-specified alternate address) can withdraw later once unblocked, or allow the beneficiary to supply a fresh receiving address for that residual claim. This decouples order finalization from the token-transfer liveness assumption and prevents permanent fund lock from a single blocklist/pause event.

### Proof of Concept
1. User places a cross-chain order on the source chain, escrowing USDC as input via `placeOrder`.
2. Solver fills the order on the destination chain via `ExtrinsicIntents.fill`, and the gateway dispatches a `RedeemEscrow` `WithdrawalRequest{beneficiary: solver}` to the source chain (`evm/src/apps/intentsv2/ExtrinsicIntents.sol` lines 139-151).
3. Before the message is delivered/relayed, Circle blocklists the solver's address on USDC (or pauses USDC transfers globally).
4. The relayer delivers the `RedeemEscrow` post request; `onAccept` authenticates it and calls `_withdraw(body, false, true)` (`ExtrinsicIntents.sol` lines 289-295).
5. Inside `_withdraw`, `IERC20(usdc).safeTransfer(solver, amount)` reverts because the solver is blocklisted (`IntentsBase.sol` lines 404-409).
6. The entire `onAccept` transaction reverts; `_filled[commitment]` is never set, and the escrowed USDC remains locked in the contract under `_orders[commitment][usdc]` with no way to ever release it to the solver or anyone else.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens

        for (uint256 i; i < len;) {
