### Title
Persistent cached FROST preprocess seed enables nonce reuse and secret share recovery when a context signs a second, differing message - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` generates a FROST preprocess seed once per `context`, encrypts it, and stores it in the `CachedPreprocesses` DB table. The seed is never deleted after use. Every subsequent `share_internal`/`complete_internal` call for the same context deterministically rebuilds the same nonces and the same preprocess. If the same context is ever used to produce signature shares over two different messages, the validator's secret share is recoverable by anyone who observes the two published shares — exactly the "use-after-free/reuse of a one-time value" class of CVE-2023-51782 mapped onto Serai's deterministic preprocess caching.

### Finding Description
In `preprocess_internal`, the seed is only written when `CachedPreprocesses::get(...).is_none()`; thereafter the same encrypted seed is read back and passed to `AlgorithmSignMachine::from_cache` (lines 123–145). `from_cache` calls `seeded_preprocess`, which derives the FROST nonces deterministically via `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:127–132). Nothing removes or rotates the entry after `share_internal` consumes it, and `share_internal` re-invokes `preprocess_internal` itself (line 156), so a context is permanently bound to one nonce pair.

The FROST docs in this repo state the invariant explicitly: a cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:85–87, 209–213; spec/cryptography/FROST.md:51–55). The enforcement burden is on the caller to delete the cache after use — `SigningProtocol` never does.

The only instantiated context is `DkgConfirmer`, keyed `(b"DkgConfirmer", attempt)` (line 275). Its `share`/`complete` path signs `set_keys_message(&self.spec.set(), &removed, key_pair)` — the message varies with `key_pair` and `removed` (lines 288–301). `complete` re-runs `share_internal` (line 322), and `share` can be invoked again after a crash/reboot or retry within the same `attempt`. If between two such invocations the confirmed key pair or the removed-validator set differs (e.g., the processor regenerated `key_pair`, or `removed_as_of_dkg_attempt` advanced), the second call emits a signature share computed with identical nonces `(d, e)` but a different challenge `c`. Since `share = d + e·b·ρ + λ·c·x`, two shares with the same nonce commitments and different `c` yield `x` (the MuSig secret share of the validator) by linear elimination — and the shares are broadcast in public tributary transactions, so no privileged position is needed to collect them.

### Impact Explanation
High. Recovery of a validator's secret share under the substrate validator-set key. Combined with threshold−1 other leaked/compromised shares — or more directly, break of the MuSig signing key's per-validator component — this undermines the integrity of `set_keys` confirmations that install network keys. At minimum it is permanent compromise of a signer secret that was designed to be protected by one-time-nonce semantics; the cached-seed design makes a single repeated context sufficient for full share disclosure to a passive observer.

### Likelihood Explanation
The unsafe state is unconditional: the DB entry persists across reboots and is reused for the lifetime of the context. Exploitation additionally requires the same `(b"DkgConfirmer", attempt)` context to produce shares over two distinct messages. That requires either a different `key_pair` or a different `removed` set within one attempt — plausible during retries where the key-generation output or removal set changes, but not guaranteed to occur in normal operation. Because the seed is encrypted under the signing key and stored in a non-secret-store DB, an attacker who obtains DB read access (the code itself notes the DB "isn't a proper secret store") could also extract a *used* seed to derive nonces directly. Likelihood: medium — a deterministic design flaw needing an environmental trigger.

### Recommendation
Delete the `CachedPreprocesses` entry (or rotate it with fresh `OsRng` entropy) the first time it is consumed by `share_internal`, so each signing action uses a unique seed; alternatively, incorporate a monotonic per-message nonce-mixing value into the seed derivation. Additionally, fold the message (or a hash of it) into the context used for caching so distinct messages cannot collide on one seed.

### Proof of Concept
1. Coordinator enters `DkgConfirmer` for `attempt = A`; `preprocess`/`share` is invoked with `key_pair = K1`, producing share `s1` over `m1 = set_keys_message(set, removed, K1)` with seed-derived nonces `(d, e)`. `s1` is published on the tributary.
2. The coordinator reboots (or `complete` is retried) and now signs `key_pair = K2` (regenerated by the processor), producing `s2` over `m2` with the *same* cached seed → same `(d, e)` and same preprocess commitments, hence identical `R` and identical binding factor `ρ`.
3. An observer collects `s1, s2` from the public tributary data. With `s_i = d + e·b·ρ + λ·c_i·x`, subtracting gives `s1 − s2 = λ·(c1 − c2)·x`, so `x = (s1 − s2) / (λ·(c1 − c2))` — the validator's secret share — since `c1 ≠ c2` (different `m`) while `d, e, b, ρ, λ` are identical.

Root cause: `CachedPreprocesses::set` writes a permanent seed and neither `share_internal` nor `complete_internal` deletes it (coordinator/src/tributary/signing_protocol.rs:123–147, 156, 322), violating the one-time-use precondition documented at crypto/frost/src/sign.rs:85–87 and spec/cryptography/FROST.md:51–55. Note: the precise on-chain trigger (a differing `key_pair`/`removed` within one `attempt`) depends on coordinator/processor retry behavior I could not fully trace in `handle.rs` within the available iterations; the persistent-reuse root cause itself is confirmed in the cited code.
