### Title
Duplicate Citrea `withdrawal_utxo` across indices causes one Bitcoin payout to be attributed to two withdrawal rows, doubling operator reimbursement - (File: `core/src/database/verifier.rs`)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` only on `(txid, vout)`, never on `idx`. Since each Citrea withdrawal index `i`/`j` is written into its own row via `update_withdrawal_utxo_from_citrea_withdrawal` with no uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, if two distinct withdrawal rows are populated with the identical outpoint `U`, a single Bitcoin transaction spending `U` gets matched to both rows and both get marked paid by the same operator.

### Finding Description
Binding claimed broken: `count(vault UTXOs spent for {i, j}) == count(reimbursements issued for {i, j})`. Before the bug this should be `1 == 1`; the finding claims it becomes `1 == 2`.

Trace:
- `core/src/database/schema.sql:269-281` — `withdrawals` table has `idx int primary key`, `withdrawal_utxo_txid`, `withdrawal_utxo_vout`, with **no unique constraint** on the `(txid, vout)` pair. [1](#0-0) 
- `Verifier::update_citrea_deposit_and_withdrawals` iterates every new withdrawal returned by `CitreaClient::collect_withdrawal_utxos` and blindly calls `Database::update_withdrawal_utxo_from_citrea_withdrawal(idx, outpoint, …)` per index, with no cross-index duplicate check. [2](#0-1) 
- `Database::update_withdrawal_utxo_from_citrea_withdrawal` just does an `UPDATE … WHERE idx = $1`, again with no uniqueness enforcement across rows. [3](#0-2) 
- `Database::get_payout_txs_for_withdrawal_utxos` joins purely on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, returning one row per matching `withdrawals.idx`, so if two rows share the same `(txid, vout)`, both are returned for the single spending transaction. [4](#0-3) 
- `Verifier::update_finalized_payouts` consumes that result directly and calls `update_payout_txs_and_payer_operator_xonly_pk` for every `(idx, payout_txid, …)` pair returned, so both rows get `payout_txid = T` and `payout_payer_operator_xonly_pk = operator`. [5](#0-4) 
- `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk`, processes the first unhandled row via `Operator::handle_finalized_payout` (which allocates a fresh unused kickoff connector and produces a distinct reimbursement transaction per call), then marks it handled and loops back for the *next* unhandled row (`is_payout_handled` is per-row, not per-UTXO). [6](#0-5) [7](#0-6) 

Root cause: withdrawal rows are keyed and reasoned about by `idx` everywhere except in the one place that correlates on-chain spend data back to a withdrawal (`get_payout_txs_for_withdrawal_utxos`), which drops `idx` from the join predicate. The system assumes `withdrawal_utxo` values are unique across Citrea withdrawal indices, but nothing in this repository enforces that assumption, and the withdrawal UTXO's bytes are attacker-supplied at `withdraw()`-call time on the Citrea Bridge contract for each of the attacker's own deposits.

Exploit flow: an attacker makes two separate deposits into the bridge, obtaining two distinct vaults with Citrea deposit/withdrawal indices `i` and `j` (this repo's `withdrawals` table keys both deposit and withdrawal metadata by the same `idx`, i.e., one row per deposit/withdrawal slot). The attacker calls Citrea Bridge `withdraw()` for index `i` and index `j`, supplying byte-for-byte the same `(txid, vout)` for the withdrawal UTXO in both calls (this is fully attacker-controlled input, along with the corresponding Schnorr signature since the attacker owns that UTXO). An operator, seeing either request, fronts a single payout transaction `T` spending `U`. The chain-syncer records `U` spent by `T` once. The verifier's finalized-block processing then double-attributes `T` to both `idx=i` and `idx=j`, and the operator's `PayoutCheckerTask` autonomously drives two independent kickoff/reimburse cycles, spending two separate vault UTXOs (`i`'s and `j`'s deposit) to reimburse itself, despite having only funded one payout.

Existing guards do not stop this: `Verifier::is_deposit_valid` and `Operator::is_profitable` validate the payout tx construction and profitability but never check whether the same withdrawal UTXO was already claimed at another index; there is no DB uniqueness constraint on `withdrawal_utxo_txid/vout`; `get_first_unhandled_payout_by_operator_xonly_pk`/`mark_payout_handled` operate per-row (`idx`), not per-UTXO.

### Impact Explanation
An operator ends up reimbursed twice for a single fronted payout, draining a second vault's `bridge_amount` in BTC that was never actually paid out to any user for that second vault — this is a Critical-severity outcome ("an operator reimbursed for a payout it never funded" / bridge value leaving a vault without a matching fronted withdrawal). The attack is repeatable for every pair of deposits the attacker (or any user who deposits twice) controls, and does not require collusion with the operator — any operator that services either of the duplicate-UTXO withdrawal requests is unwittingly granted a second, illegitimate reimbursement by the verifier network's automatic bookkeeping.

### Likelihood Explanation
Preconditions are attacker-affordable: two on-chain deposits into the bridge (cost = 2×`bridge_amount` locked, standard deposit flow) and two `withdraw()` calls on the Citrea Bridge contract with identical UTXO bytes (only Bitcoin fee costs and Citrea gas). No verifier/operator/aggregator privilege, key share, or TLS access is required. The remaining precondition — that Citrea's Bridge contract permits registering the same Bitcoin UTXO bytes at two different withdrawal indices — is an assumption about external contract behavior needed to reach this repository's flawed join; nothing in the reachable Clementine code queried here rejects or deduplicates such a registration, so if the contract does not enforce global UTXO uniqueness across withdrawal indices (which is plausible, since UTXO uniqueness on the Bitcoin side is not something an EVM contract can verify without an SPV check it isn't shown to perform here), the exploit is fully mechanical and deterministic once triggered.

### Recommendation
Change `get_payout_txs_for_withdrawal_utxos` (and the surrounding attribution logic) to enforce a strict UTXO-to-withdrawal binding: add a unique constraint/index on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (rejecting/ignoring later duplicate registrations, or flagging them for manual dispute resolution instead of auto-crediting), and/or change the join and downstream `update_finalized_payouts`/`PayoutCheckerTask` logic to attribute a spent UTXO to at most one withdrawal row (e.g., pick the lowest `idx` deterministically and mark any other row referencing the same outpoint as invalid/unpayable rather than paid).

#[tokio::test]
async fn duplicate_withdrawal_utxo_double_attribution() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let spending_txid = Txid::from_byte_array([0xAA; 32]);
    let shared_utxo = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0xBB; 32]),
        vout: 0,
    };
    let idx_i = 0u32;
    let idx_j = 1u32;

    let block_id = db.insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 0).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &spending_txid).await.unwrap();
    // T spends U exactly once
    db.insert_spent_utxo(&mut dbtx, block_id, &spending_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    // Two distinct deposit/withdrawal rows (i, j) both register the SAME withdrawal_utxo = U
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_i, &Txid::from_byte_array([1;32])).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_j, &Txid::from_byte_array([2;32])).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_i, shared_utxo, block_id).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_j, shared_utxo, block_id).await.unwrap();

    // BINDING CHECK: one Bitcoin spend of U should map to exactly one withdrawal row
    let payout_txs = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();
    assert_eq!(payout_txs.len(), 2, "one payout tx wrongly attributed to two withdrawal rows");

    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx),
        payout_txs.into_iter().map(|(idx, txid)| (idx, txid, Some(generate_random_xonly_pk()), BlockHash::all_zeros())).collect(),
    ).await.unwrap();

    // Both rows are now independently payable/handleable, i.e. mark_payout_handled would
    // fire for both idx_i and idx_j from a single fronted payout tx T, violating ATTRIBUTION.
}

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }

    pub async fn handle_finalized_payout<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",
                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;
        }

        // get signed txs,
        let kickoff_data = KickoffData {
            operator_xonly_pk: self.signer.xonly_public_key,
            round_idx,
            kickoff_idx,
        };

        let payout_tx_blockhash = payout_tx_blockhash.as_byte_array().last_20_bytes();

        #[cfg(test)]
        let payout_tx_blockhash = self
            .config
            .test_params
            .maybe_disrupt_payout_tx_block_hash_commit(payout_tx_blockhash);

        let context = ContractContext::new_context_for_kickoff(
            kickoff_data,
            deposit_data,
            self.config.protocol_paramset(),
        );

        let signed_txs = create_and_sign_txs(
            self.db.clone(),
            &self.signer,
            self.config.clone(),
            context,
            Some(payout_tx_blockhash),
            Some(dbtx),
        )
        .await?;
