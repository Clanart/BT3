### Title
Stale in-memory file snapshot silently overwrites user's on-disk edits when applying Copilot conflict resolutions - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes a `resolvedContent` string that was reassembled from a **snapshot** of the conflicted file taken at the start of the (up to 10‑minute) Copilot turn, guarded only by a coarse "is this file still fully unresolved" check. That guard does not detect edits made to the file *within* the still-present conflict markers during the async window, so those edits are silently discarded and replaced with the stale reconstruction — the same "cached value diverges from live state, and only a coarse boolean guard exists to catch it" pattern as the rebasing-token `amountToRedeem` bug.

### Finding Description
1. `buildConflictContext` reads each conflicted file from disk and stores the *entire raw file content* (`rawContent`) at the moment the Copilot resolution is kicked off: [1](#0-0) 

2. The Copilot SDK turn can run for a long time — the configured per-attempt timeout is 10 minutes (`timeoutMs ?? 600_000`), during which the underlying file remains on disk in the same conflicted state and is fully editable by the user: [2](#0-1) 

3. Once results return, `reassembleResolutions`/`reassembleResolvedFile` splice the model's per-hunk output back into that **captured `rawContent` snapshot**, not the current on-disk content: [3](#0-2) 

4. When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes this stale, snapshot-derived `resolvedContent` to disk. The only re-validation performed is a check that the file is no longer "unresolved": [4](#0-3) 

5. "Unresolved" is determined purely by counting remaining `<<<<<<<` conflict markers (`conflictMarkerCount > 0`), not by comparing the current file content to the snapshot used for reassembly: [5](#0-4) 

Broken invariant: the code assumes "no markers removed ⇒ file unchanged since the snapshot," but a user can edit code *inside* the conflict block (fix a typo, add a line, adjust logic) without removing the `<<<<<<<`/`=======`/`>>>>>>>` markers. `conflictMarkerCount` stays > 0, so the skip-guard does not fire, and the whole file is overwritten with the T1 snapshot's reconstruction — discarding the user's T2 edits with no warning. This is directly analogous to `WithdrawQueue` storing `amountToRedeem` at request time and blindly transferring it at claim time: a value computed from state-at-T1 is used at T2 with only a shallow guard that fails to detect the state has diverged.

### Impact Explanation
This causes silent corruption of what the user is about to commit: real, intentional edits the user made to a conflicted file while Copilot was thinking are dropped without any diff/confirmation, and replaced by content the user never reviewed against their latest changes. Because the overwrite happens automatically on "Continue Merge" and the write path can also affect files outside the strictly conflicted hunks (only non-conflicted regions are preserved from the *stale* snapshot, not the live file), this can produce a commit whose content silently diverges from what the developer believes they authored — a direct "silent corruption of what the user commits" outcome.

### Likelihood Explanation
No local/physical access, admin rights, prior malware, or leaked credentials are needed — this occurs during completely ordinary use of the shipped "Resolve merge conflicts with Copilot" feature: the user opens the conflicted file in another editor (a common practice while waiting on a long-running AI resolution) and makes a small in-place fix without deleting markers, then returns to Desktop and clicks "Continue Merge". The 600-second timeout window is easily long enough in real merges/rebases with many or large conflicts, and an adversarial "theirs" branch/PR (an attacker-controlled fetched ref being merged) can be crafted with more/larger conflicts specifically to prolong this window and increase the chance of the race.

### Recommendation
Before writing `resolvedContent`, re-read the file's current on-disk content and compare it against the `rawContent` snapshot captured in `buildConflictContext` (e.g. hash comparison). If they differ, treat the resolution for that file as stale: skip the write, mark the file for manual resolution, and surface this to the user instead of silently overwriting. Alternatively, re-run `extractConflictHunks`/reassembly against the live file content at apply time rather than the T1 snapshot.

### Proof of Concept
1. Start a merge/rebase that produces at least one text conflict; enable Copilot conflict resolution and let it start resolving.
2. While the Copilot request is streaming (can be extended by triggering conflicts on a large/complex adversarial branch), open the conflicted file in an external editor and make a small edit *inside* the `<<<<<<<`/`=======`/`>>>>>>>` block (e.g., fix a value) — do not remove the markers.
3. Wait for the Copilot result dialog and click "Continue Merge".
4. Observe: `_applyCopilotConflictResolutions` finds `isConflictedFileStatus` true and `hasUnresolvedConflicts` true (markers still present) via `app/src/lib/stores/app-store.ts:7247-7256`, so it does **not** skip the write, and instead writes the stale reassembled content from `app/src/lib/copilot-conflict-resolution.ts:635`, discarding the edit made in step 2 without any error or diff prompt.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
