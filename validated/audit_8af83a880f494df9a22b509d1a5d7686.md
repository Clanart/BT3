### Title
Silent File Corruption via Conflict-Marker Desync Between Copilot Extraction and Reassembly - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
GitHub Desktop's AI-assisted merge-conflict resolution feature extracts conflict hunks from a file with `extractConflictHunks()` [1](#0-0) , sends them to Copilot, validates only the *count* of returned hunks against the extracted count [2](#0-1) , and then splices the model's per-hunk resolutions back into the original on-disk file using an independently-implemented scanner, `reassembleResolvedFile()` [3](#0-2) . The two scanners use different lookahead logic for locating the end of a conflict block, so a file whose "theirs" side (fully attacker-controlled content coming from a merged branch/PR) contains marker-like text can make them disagree about where a conflict block ends. Instead of raising an error when this desync occurs, the reassembly path always succeeds and silently writes the wrong content — including possible leftover raw conflict-marker text or dropped attacker/legit content — straight into the file the user is about to commit.

### Finding Description
`extractConflictHunks()` locates a hunk boundary with a narrow, single-pass scan: once it sees the `<<<<<<<` marker it collects "ours" lines until it hits **either** the base marker `|||||||` **or** the separator `=======`, then (for the non-diff3 case) collects "theirs" lines until the **first** `>>>>>>>`-looking line it encounters [4](#0-3) .

`reassembleResolvedFile()` instead does a wider lookahead: starting from `<<<<<<<` it scans forward for the first `=======` (`hasSeparator = true`, but the loop keeps going) and the first `>>>>>>>` after that, then treats the entire span as one conflict block to be replaced with the *next* item in `hunkResolutions`, matched purely by order [5](#0-4) .

Both functions use the same regexes for the markers, but their termination conditions differ (first separator/first closer vs. "keep scanning until a closer is found, regardless of how many separators are seen along the way"). If the incoming ("theirs") branch content — which is entirely attacker-controlled in a merge from an untrusted PR/remote — contains additional marker-like lines (e.g. `<<<<<<<`, `=======`, or `>>>>>>>` at column 0, which is trivial to include in example code, documentation about Git, or crafted fixtures) inside what should be the "theirs" text of a real conflict, the two functions can compute **different hunk boundaries for the same file**:

- `extractConflictHunks()` may report N hunks (used as `expectedHunkCounts` in `validateResolutionPaths()` [6](#0-5) ), while the actual byte range consumed by `reassembleResolvedFile()` for that same "hunk" extends further into the file (because it kept scanning past an embedded separator/closer look-alike before finding the real closing marker).
- The count-only check in `validateResolutionPaths()` cannot catch this because it never re-derives boundaries — it just compares `resolution.hunks.length` to the previously-computed extraction count.
- `reassembleResolvedFile()`'s own recovery logic ("malformed marker — copy through as regular content") only triggers when a `<<<<<<<` has **no** separator or **no** closer at all before EOF [7](#0-6) ; it does not detect the case where separator/closer markers exist but at a different offset than the extractor assumed. Consequently there is no error path here at all — the function always returns a plausible-looking file.

The net effect: the model's resolution is spliced over an incorrect span of the real file. Depending on the crafted input this can (a) leave a stray raw conflict-marker line (e.g. a leftover `>>>>>>> feature`) inside the committed file, and/or (b) silently drop legitimate lines that fell inside the over-consumed span, and/or (c) misapply resolution N's content to a different logical hunk than the one it was generated for. None of this raises `CopilotValidationError` or any other error — the UI presents it as a normal, successful AI-assisted resolution, and the corrupted content is what gets written to disk and is available to be staged/committed/pushed by the user.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." An attacker who controls a branch/PR that the victim merges (or the "theirs" side of any conflict, which is exactly the untrusted-remote-content scenario called out as valid) can craft file content that desyncs the two marker-scanning passes. The victim, trusting the "AI resolved this conflict" UI, commits and pushes a file that:
- silently reintroduces attacker-supplied lines in place of code the developer or the model intended to keep,
- can leave literal `>>>>>>>`/`<<<<<<<` conflict-marker text embedded in shipped source (which can itself be a build/security signal or, worse, hide extra attacker payload lines that never went through the model's actual review because they were incorrectly folded into an unrelated resolution),
- is a real corruption of the working tree/commit content, unlike a benign parse failure — there is no user-facing warning as there would be for the `DiffContentsWarning` line-ending/bidi cases [8](#0-7) .

### Likelihood Explanation
This requires no local access, no elevated privileges, and no prior compromise — only that the victim uses the Copilot conflict-resolution feature on a merge involving a branch/PR whose content the attacker controls, which is a normal collaborative workflow (reviewing/merging a fork's PR). Getting marker-like sequences into ordinary source or documentation files (Markdown docs about Git, test fixtures with embedded diff examples, generated files) is easy and unremarkable, so the crafted input does not need to look obviously malicious to a human reviewer glancing at the PR diff before the merge is attempted.

### Recommendation
- Make `reassembleResolvedFile()` use the exact same boundary-detection algorithm as `extractConflictHunks()` (ideally have both derive hunk boundaries from a single shared parsing pass, or have `extractConflictHunks()` return concrete `[start, end)` line ranges that `reassembleResolvedFile()` consumes directly instead of re-scanning).
- After reassembly, re-run conflict-marker detection over the final content and fail (or require manual resolution) if any conflict-marker-looking line remains, instead of trusting that the removal was complete.
- Add a sanity check that the total number of lines consumed across all conflict blocks during reassembly matches what was originally extracted for that file before writing the result to disk.

### Proof of Concept
Consider a conflicted file where the "theirs" (incoming, attacker-controlled) side embeds a spurious marker sequence as ordinary text:
```
line before
<<<<<<< HEAD
ours
=======
<<<<<<< HEAD
embedded-lookalike
=======
inner
>>>>>>> feature
outer-theirs-tail
>>>>>>> feature
line after
```
- `extractConflictHunks()` sees the first `<<<<<<<`, collects `ours`, breaks on the first `=======`, then collects "theirs" lines until the **first** `>>>>>>>` it meets — which is the inner one — yielding one hunk whose `theirsContent` is `"<<<<<<< HEAD\nembedded-lookalike\n=======\ninner"` [9](#0-8) . Everything after that inner `>>>>>>>` (`outer-theirs-tail` and the real closing `>>>>>>> feature`) is left outside any hunk.
- `reassembleResolvedFile()`, scanning the same file, keeps looking past the first `=======` it meets for the first `>>>>>>>`, and lands on the **outer** closing marker, consuming the entire block through `line after`'s predecessor [10](#0-9) .
- The single model resolution (generated for the narrower hunk extracted above) gets spliced in place of the much larger span consumed by `reassembleResolvedFile()`, silently dropping `outer-theirs-tail` and the true closing marker context from the final file — with no exception thrown anywhere in the pipeline.

I was not able to trace the exact downstream call site that writes `reassembleResolvedFile()`'s output to the working tree within the indexing budget, so I cannot cite the final "write to disk"/stage step directly; this should be verified in a full session, but the extraction/validation/reassembly logic itself is confirmed from the source shown above.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
