### Title
Unbounded pool-reward claim loop in `PlotNFT2Wallet.claim_rewards` can build an oversized spend bundle that cannot be included in a block, permanently stalling reward claims - (File: chia/wallet/plotnft_wallet/plotnft_wallet.py)

### Summary
`PlotNFT2Wallet.claim_rewards` fetches **all** unclaimed pool-reward coins for a PlotNFT and constructs a single `WalletSpendBundle` that spends every one of them plus the singleton coin in one transaction, with no batching or cap on the number of rewards processed at once. [1](#0-0) 

### Finding Description
`claim_rewards` calls `plotnft2_store.get_pool_rewards(plotnft_id=...)` to retrieve the full list of unclaimed reward coins, then unconditionally builds delegated puzzles/solutions and coin spends for every entry via `plotnft.claim_pool_rewards(rewards_to_claim=..., ...)`, iterating `for i, reward in enumerate(rewards_to_claim)`: [2](#0-1) 

This is unlike the legacy `PoolWallet.claim_pool_rewards`, which explicitly caps the number of spends aggregated into a single bundle with a `max_spends_in_tx` parameter (defaulting to `DEFAULT_MAX_CLAIM_SPENDS`) and truncates the claim, logging "pool wallet truncating absorb to X spends to fit into block": [3](#0-2) [4](#0-3) 

The new `PlotNFT2Wallet.claim_rewards` has no analogous limiting parameter and no early-exit/batch logic. Every accumulated pool-reward coin (one per farmed block while pooling) is included in a single spend bundle, whose CLVM execution cost grows linearly with the number of rewards. Chia enforces a hard `MAX_BLOCK_COST_CLVM` per spend bundle at both the mempool/consensus level and inside wallet-side validation (e.g., `Offer` explicitly raises `ValidationError` when a spend bundle's cost exceeds the block cost budget): [5](#0-4) 

Once a user (or an automated farming setup) accumulates enough unclaimed reward coins - which happens naturally over time while self-pooling without regularly claiming - `claim_rewards` will always try to spend the entire backlog in one transaction. If that backlog's aggregate CLVM cost exceeds the block cost limit, `generate_signed_transaction`/wallet push will produce a spend bundle that the mempool/consensus will reject (`BLOCK_COST_EXCEEDS_MAX` or similar), and because the function has no way to request a partial batch, the user has no built-in way to shrink the claim - the wallet keeps trying (and failing) to claim everything at once.

### Impact Explanation
This does not create unauthorized fund movement, but it is a spend-triggered transaction-processing halt for the affected PlotNFT: the reward coins can become effectively stuck, since the sole claim path (`claim_rewards`) always attempts to spend the full unclaimed set and there is no batching mechanism to work around a bundle that is too large to fit in a block. This matches the reported bug class (unbounded loop building a transaction that can exceed the block cost/gas limit), reachable purely by a normal wallet user's own claim action without any privileged or malicious-peer involvement.

### Likelihood Explanation
Likely to occur naturally for any self-pooling PlotNFT that farms many reward coins between claims (e.g., a farmer who claims infrequently, or a large/pooled farming operation with a self-pooling payout target), since each block farmed while self-pooling adds one more unclaimed reward coin to the set and `get_pool_rewards` returns the entire unbounded history until claimed. No adversarial input is needed - it is a straightforward self-inflicted denial-of-service via ordinary use.

### Recommendation
Add a batching/limit parameter (analogous to `PoolWallet.claim_pool_rewards`'s `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`) to `PlotNFT2Wallet.claim_rewards`, allowing callers (and the RPC layer) to cap the number of reward coins processed per spend bundle and to claim in multiple transactions when the backlog is large. Additionally, consider proactively estimating/checking the resulting bundle's CLVM cost before submission and truncating to fit within `MAX_BLOCK_COST_CLVM`, mirroring the safeguard already present in the legacy pool wallet code path.

### Proof of Concept
1. Create a `PlotNFT2Wallet` in self-pooling mode with `payout_instructions` pointed at the wallet's own puzzle hash.
2. Farm many blocks while self-pooling without calling `claim_rewards`, so that `plotnft2_store.get_pool_rewards` accumulates a large number of unclaimed `PoolReward` coins (each contributing its own `DelegatedPuzzleAndSolution` and `CoinSpend` in `plotnft.claim_pool_rewards`).
3. Call `PlotNFT2Wallet.claim_rewards`; observe that it builds one `WalletSpendBundle` spending every accumulated reward coin plus the singleton, with cost scaling linearly in the number of rewards - unlike `chia/pools/pool_wallet.py`'s `claim_pool_rewards`, which truncates via `max_spends_in_tx`.
4. Once the aggregate cost of that single bundle exceeds `MAX_BLOCK_COST_CLVM`, pushing the resulting transaction fails validation, and since `claim_rewards` offers no way to request fewer rewards, the user cannot claim any of the backlog until the code is fixed to support batching.
