### Title
`SignableTransaction::new` computes `needed_fee` from a weight estimate that omits the OP_RETURN data output, so the constructed transaction pays a lower fee rate than the caller requested - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class is a fee computed from stale/incomplete state at request time, so the fulfillment transaction's accounting does not match the fee actually required. In `SignableTransaction::new`, the transaction's weight/vbytes — and therefore `needed_fee` and the minimum-relay-fee check — are derived from `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only models the payment outputs. The OP_RETURN output created from the `data` parameter is pushed onto `tx_outs` before this calculation but is never included in the weight estimate. The built transaction is larger than estimated and pays `fee_per_vbyte` over a smaller vsize, so its effective fee rate is below the caller-specified rate.

### Finding Description
`SignableTransaction::new` pushes the data output into `tx_outs` at networks/bitcoin/src/wallet/send.rs:194-202, then computes the weight estimate at line 204 via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`. `calculate_weight_vbytes` (lines 62-127) reconstructs a mock transaction whose outputs are only `payments` (plus optional change) — the `data` output is not modeled. The same omission exists on the change path at lines 225-227. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is under-charged by `fee_per_vbyte * vsize(OP_RETURN_output)` (up to ~90 vbytes for the maximum 80-byte payload).
- The `TooLowFee` check at line 211 divides by the understated `vbytes`, so a transaction whose actual fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` can pass validation.
- The `NotEnoughFunds` check at line 215 uses the understated `needed_fee`, and the change calculation at line 228 uses `fee_with_change` also computed without the data output — so change is over-credited by the same amount, inflating the change output and further shrinking the real fee paid.

### Impact Explanation
A caller passing `data` receives a `SignableTransaction` whose real fee rate is lower than the `fee_per_vbyte` they specified and whose `needed_fee()` return value is wrong. If the requested rate was near the minimum relay fee, the signed transaction will be rejected by Bitcoin mempool policy (`min relay fee not met`), so the fulfillment transaction fails exactly as in the reference bug — the fee accounted at request time does not cover the transaction actually produced. The over-credited change output also means up to ~90 vbytes × `fee_per_vbyte` satoshis intended as fee are instead sent back as change, silently degrading confirmation priority of every data-carrying transaction.

### Likelihood Explanation
Any invocation of `SignableTransaction::new` with a non-`None` `data` argument and a `fee_per_vbyte` near the minimum triggers the divergence deterministically; no attacker privileges are needed since `data` and `fee_per_vbyte` are caller-supplied public inputs. The magnitude is bounded (~90 vbytes of weight), which caps severity, but the failure is deterministic and silent — the constructed `SignableTransaction` reports a `needed_fee` it does not satisfy.

### Recommendation
Include the data output in the weight estimate: pass the serialized OP_RETURN output (or a worst-case 80-byte `TxOut`) into `calculate_weight_vbytes` alongside `payments`, on both the no-change and change paths, so `needed_fee`, the `TooLowFee` check, `NotEnoughFunds` accounting, and the change-amount deduction all reflect the true transaction weight. Alternatively, perform the `TooLowFee` check against `self.fee()`/`tx.weight()` after the final transaction is assembled.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`:

```rust
// At line 194-202 the OP_RETURN output is added to tx_outs
tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) });

// At line 204, the estimate only covers `payments` — data output excluded
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

Construct a `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte * actual_vbytes` is just above `DEFAULT_MIN_RELAY_TX_FEE * actual_vbytes / 1000` but `fee_per_vbyte * estimated_vbytes` is below the actual requirement. The `TooLowFee` check at line 211 passes using the understated `vbytes`, `new` returns `Ok`, yet the resulting transaction's true fee rate is below the minimum relay fee and will be rejected by the network. Additionally, `signable.fee()` (lines 137-141, inputs minus outputs) minus `signable.needed_fee()` shows the change output absorbed the sats that should have covered the missing ~90 vbytes.
