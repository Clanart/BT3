### Title
MasterMagpie `_deposit` credits `user.amount`/`user.available` with the raw input amount instead of the actual tokens received, allowing MGP reward-share theft via `type(uint256).max`-quirk tokens - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie._deposit` increments a user's staked balance by the caller-supplied `_amount` parameter *before* transferring tokens, and never verifies that the amount actually received via `safeTransferFrom` matches `_amount`. For any staking token registered in a pool that implements the well-known "max-uint256 transfers actual balance instead of reverting" quirk (e.g. Compound v3 Comet-style tokens such as cUSDCv3, referenced in the source report), an ordinary user can inflate their recorded stake to an arbitrary value while transferring only their real, tiny balance.

### Finding Description
In `_deposit`, the staking accounting is updated with the raw `_amount` argument, and only afterward is `safeTransferFrom` invoked for the same `_amount`: [1](#0-0) 

Specifically:
- `user.amount = user.amount + _amount;` and `user.available = user.available + _amount;` are unconditionally applied using the caller-provided `_amount`.
- `IERC20(pool.stakingToken).safeTransferFrom(address(msg.sender), address(this), _amount);` is executed afterward, but `SafeERC20.safeTransferFrom` only checks that the call succeeded (returned `true`/non-reverting) — it does not verify that `_amount` tokens were actually moved.
- `user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;` is then derived from the corrupted `user.amount`.

If `pool.stakingToken` is a token that special-cases `amount == type(uint256).max` by silently transferring only the caller's actual balance (returning success) instead of reverting for insufficient balance — the exact bug class described in the external report — a user can call the deposit entry point with `_amount = type(uint256).max` while holding only a negligible real balance. The token transfer succeeds by moving only the user's small real balance, but `user.amount`/`user.available` are permanently set to `type(uint256).max` (or any other unbacked value the token happens to allow through), completely decoupled from the capital actually contributed.

This differs from `WombatStaking.deposit()`, which correctly measures the actually-received LP amount via a `balanceOf` diff before crediting anything: [2](#0-1) 
`MasterMagpie._deposit` has no equivalent balance-diff check, making it the vulnerable analog of the reported bug class.

### Impact Explanation
Because `user.amount` directly determines the user's share of the pool's `accMGPPerShare`-based MGP emission (`pendingReward = user.amount * accMGPPerShare - rewardDebt`), and pool-wide staked totals used to compute future `accMGPPerShare` increments are similarly influenced by nominal staked amounts, an attacker who inflates their own `user.amount` to an outsized value can capture a hugely disproportionate share of subsequently-accrued MGP rewards for that pool while contributing negligible real capital. This constitutes theft of unclaimed yield from all other legitimate stakers in the same pool and permanently corrupts that pool's emission accounting, since `user.amount`/`rewardDebt` cannot be reconciled back to real economic contribution.

### Likelihood Explanation
Exploitability is contingent on the pool's `stakingToken` being (or wrapping) a token that implements the specific "transfer actual balance instead of specified amount on `type(uint256).max` input" behavior. This requires that such a token is registered as a `stakingToken` for some `MasterMagpie` pool. Given the protocol's pattern of onboarding new receipt/underlying tokens over time (as flagged by the source report for Compound v3-style assets), this is a plausible, non-privileged-admin-dependent condition rather than a purely theoretical one — it only requires an already-whitelisted pool token to have this quirk, not any malicious admin action.

### Recommendation
In `MasterMagpie._deposit`, measure the actual tokens received via a `balanceOf(address(this))` diff around the `safeTransferFrom` call, and use that measured amount (not the raw `_amount` parameter) to update `user.amount`, `user.available`, and `user.rewardDebt`. This mirrors the balance-diff pattern already used correctly in `WombatStaking.deposit()`.

### Proof of Concept
1. Assume/administratively register a `stakingToken` for some `MasterMagpie` pool that implements the Comet-style quirk: calling `transferFrom(user, this, type(uint256).max)` transfers only `user`'s real balance and returns `true` instead of reverting.
2. Attacker holds a negligible real balance (e.g., 1 wei) of that token and grants `MasterMagpie` a `type(uint256).max` approval.
3. Attacker calls the public deposit path that routes into `_deposit(stakingToken, attacker, type(uint256).max, false)`.
4. Inside `_deposit` [3](#0-2) , `user.amount` and `user.available` become `type(uint256).max`, while `safeTransferFrom` only pulls the attacker's 1 wei real balance.
5. `user.rewardDebt` is computed from the corrupted `user.amount`, and the attacker now holds an unbacked, effectively unlimited claim on the pool's future MGP emissions relative to all legitimately staked users.

        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

            _harvestMGP(_stakingToken, _account);

        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount + _amount;
        if (!_isVlmgp) {
            user.available = user.available + _amount;
            IERC20(pool.stakingToken).safeTransferFrom(address(msg.sender), address(this), _amount);
        }
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)
            if (!_isVlmgp)
                emit Deposit(_account, _stakingToken, _amount);
            else
                emit DepositNotAvailable(_account, _stakingToken, _amount);
    }
