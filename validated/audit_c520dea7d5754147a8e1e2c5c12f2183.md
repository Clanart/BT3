### Title
Malformed/extra `---` frontmatter delimiters cause `extract_frontmatter` to silently downgrade a `block` rule to `warn` (or drop it entirely) - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` splits rule-file content on the literal substring `---` with `maxsplit=2`, so any additional/misplaced `---` line inside the YAML block is treated as the frontmatter-closing delimiter. Any frontmatter key (most importantly `action: block`) that appears after that spurious delimiter is silently spilled into the message body and never parsed into the `frontmatter` dict, causing `Rule.from_dict` to fall back to its permissive default `action = "warn"`. This lets a rule file that visually reads as a hard `block` rule actually be enforced only as a non-blocking `warn` (or be entirely inert), defeating the enforcement Claude Code relies on before dangerous tool invocations.

### Finding Description
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` does: [1](#0-0) 

`content.split('---', 2)` splits the raw string at the first two occurrences of the substring `---` regardless of whether they represent proper standalone YAML delimiter lines. If a rule file happens to contain a third `---` line before the field that sets `action:` (e.g. a stray horizontal rule inserted by a template, an AI-generated markdown separator, or an attacker-crafted commit), the parser treats the *second* `---` occurrence as the end of frontmatter. Everything after it — including a literal `action: block` line — becomes part of `message` (`parts[2]`), and is never parsed into the `frontmatter` dict.

`Rule.from_dict` then computes: [2](#0-1) 

Since `'action'` is absent from `frontmatter`, `frontmatter.get('action', 'warn')` returns the default `"warn"`.

`load_rule_file` only rejects the file if the entire `frontmatter` dict is empty — it does not validate that expected keys like `action` were actually captured: [3](#0-2) 

Finally, `RuleEngine.evaluate_rules` performs an exact-match check `rule.action == 'block'`; anything else (including the silently-defaulted `"warn"`) is routed to `warning_rules`, which never denies the tool call: [4](#0-3) 

The enforcement hooks (`pretooluse.py`, `posttooluse.py`) call `load_rules()` → `load_rule_file()` → `extract_frontmatter()` directly on every `Bash`/`Edit`/`Write`/`MultiEdit` invocation, so any malformed rule file silently loses its blocking power on every subsequent tool call: [5](#0-4) 

No other layer re-validates the parsed `Rule` against the raw file text, so nothing catches the divergence between what a human/AI would read from the file (an apparent `block` rule) and what is actually enforced (`warn`, or no rule at all if `action` is the only remaining field lost).

### Impact Explanation
A rule author (or a project relying on a shipped/reviewed `.claude/hookify.*.local.md` policy) believes a dangerous operation (e.g. writing outside the approved workspace, `rm -rf`, editing `.env`, etc.) is hard-blocked. Due to this parser bug, the enforcement hook only emits a `systemMessage` warning (or nothing) instead of `permissionDecision: "deny"`, allowing Claude Code to execute the dangerous tool call. This directly maps to "Unauthorized file read or write outside the user-approved workspace or target scope" since the intended blocking guardrail is bypassed while appearing intact to anyone inspecting the file.

### Likelihood Explanation
No special privileges are required beyond the ability to introduce or modify a `.claude/hookify.*.local.md` file in the working repository (e.g., via a crafted PR/commit merged into a cloned project, or content that causes Claude/`/hookify` to write a rule containing an extra markdown `---` separator). The bug is fully deterministic in `extract_frontmatter` and triggers on every hook invocation once such a file exists — no race condition or timing dependency, making it trivially repeatable.

### Recommendation
- Only treat a line as a frontmatter delimiter if it is exactly `---` on its own line (after stripping), not a mid-string substring match, and stop scanning for a second delimiter once genuinely found — reject/warn on any additional bare `---` before the real closing delimiter instead of silently reclassifying content as the message body.
- Validate that expected fields are present after parsing (e.g., require `action` to be present when the file textually contains an `action:` marker) and fail closed (treat unparsable/ambiguous rule files as `block`-safe-invalid, i.e., refuse to load rather than defaulting to `warn`) when parsing produces a `frontmatter` dict inconsistent with the raw text's key count.
- Replace the hand-rolled YAML subset parser with a proper YAML parser (`yaml.safe_load`) restricted to the frontmatter block delimited by a regex that anchors `---` to start-of-line, eliminating substring-based ambiguity entirely.

### Proof of Concept
Add to `plugins/hookify/core/config_loader.py` test suite (or a standalone script):

```python
from hookify.core.config_loader import extract_frontmatter, Rule

malformed = """---
name: block-secrets-write
enabled: true
event: file
---
action: block
pattern: \\.env$
---

This should BLOCK writes to .env files.
"""

fm, msg = extract_frontmatter(malformed)
rule = Rule.from_dict(fm, msg)

# Visible file clearly intends action: block, but parser drops it:
assert 'action' not in fm            # action line spilled into message
assert rule.action == 'warn'         # silently downgraded from intended 'block'
```

Integration-level PoC: place this file as `.claude/hookify.block-env.local.md` in a cloned repo, then feed a `PreToolUse` payload for an `Edit`/`Write` tool targeting a `.env` file into `plugins/hookify/hooks/pretooluse.py` via stdin. Expected (buggy) result: `hookSpecificOutput.permissionDecision` is never `"deny"`; only a non-blocking `systemMessage` warning is returned, allowing the write to proceed — demonstrating the block-to-warn downgrade purely from the extra `---` delimiter.
