## Analysis

The external report describes a **CWE-362 data race** caused by an unsound blanket `Sync` implementation: `ImmediateIO`/`TransactionalIO` implement `Sync` unconditionally, but this lets callers retrieve the wrapped `Expander<EI>` — which may not itself be thread-safe — and use it from multiple threads, racing on non-synchronized state. The failed invariant is: *"a wrapper type must not claim `Sync` when it exposes a handle to interior-mutable state that isn't itself synchronized."*

### Protobuf analog found

The upb Rust kernel has the exact same unsound pattern. `Arena` is explicitly documented and typed as **not** `Sync` (it uses raw `upb_Arena_Malloc`, and upb's own docs say `upb_Arena` "is *not* thread-safe" — [1](#0-0)  and [2](#0-1) ). `Arena::alloc`/`checked_alloc` perform unsynchronized interior mutation through a `&self` receiver [3](#0-2) .

However, the mutator wrapper types that hold `&Arena` are unconditionally marked `Sync`:
- `RepeatedMut<'msg, T>` — `unsafe impl<'msg, T> Sync for RepeatedMut<'msg, T> {}` [4](#0-3)  — and exposes the arena via a `&self` method: `pub fn arena(&self, _private: Private) -> &'msg Arena` [5](#0-4) .
- `MapMut` — `unsafe impl<'msg, K: ?Sized, V: ?Sized> Sync for MapMut<'msg, K, V> {}` [6](#0-5) .
- The generated per-message `$Msg$Mut` type — `unsafe impl $std$::marker::Sync for $Msg$Mut<'_> {}` [7](#0-6)  — whose upb-backend inner type exposes `pub fn arena(&self) -> &Arena` from a shared reference [8](#0-7) .

Because these `*Mut` types are `Sync`, a `&RepeatedMut`/`&MapMut`/`&$Msg$Mut` can legally be shared across threads (per Rust's `Sync` contract: `&T: Send`). Each thread can then call the shared-`&self` `.arena()` accessor to obtain `&Arena` and drive arena allocation (`Arena::alloc`) concurrently — but `Arena` itself is deliberately `!Sync` (`_not_sync: PhantomData<UnsafeCell<()>>`) precisely because upb arenas cannot tolerate concurrent unsynchronized allocation. This reproduces the max7301 bug class one-to-one: the outer wrapper's blanket `Sync` claim is not actually justified by the safety of everything it lets you reach, and the accessor that leaks the non-`Sync` resource takes `&self` rather than requiring exclusive access.

The soundness argument documented in code (`"No concurrent mutation for any two fields... mutators cannot be Send but are Sync"`) [9](#0-8)  only reasons about *field* mutation methods (which correctly take `&mut self`), but doesn't account for the `arena()` escape hatch, which is `&self` and hands out a reference to genuinely `!Sync` interior-mutable state.

### Title
Unsound `Sync` on upb-backed `RepeatedMut`/`MapMut`/`$Msg$Mut` leaks non-thread-safe `Arena` reference, enabling concurrent unsynchronized allocation — (File: `rust/upb_kernel/repeated.rs`, `rust/upb_kernel/message.rs`, `rust/map.rs`, `rust/repeated.rs`, `src/google/protobuf/compiler/rust/message.cc`)

### Summary
The upb Rust kernel's mutator proxy types (`RepeatedMut`, `MapMut`, generated `$Msg$Mut`) are marked `unsafe impl Sync`, but each provides a `&self` accessor (`arena()`) that returns a reference to the underlying `upb::Arena`, which is explicitly documented as not thread-safe and is intentionally `!Sync` in its own type definition. Sharing a `&RepeatedMut`/`&MapMut`/`&$Msg$Mut` across two threads (legal because of the `Sync` impl) lets both threads independently call `.arena()` and then allocate concurrently from the same `upb_Arena`, racing on unsynchronized internal arena state.

### Finding Description
`Arena` in `rust/upb/arena.rs` carries `_not_sync: PhantomData<UnsafeCell<()>>` specifically to prevent `Sync`, and only implements `Send`, because `Arena::alloc`/`checked_alloc` mutate shared state through a `&self` receiver without any locking, matching upb's own documentation that `upb_Arena` "is *not* thread-safe" (`upb/mem/arena.h`). Despite this, the higher-level mutator wrapper types that internally hold `&Arena` are blanket-marked `Sync`:
- `RepeatedMut<'msg, T>` (`rust/repeated.rs:260`), with `arena(&self, _private: Private) -> &'msg Arena` in `rust/upb_kernel/repeated.rs:181-183`.
- `MapMut<'msg, K, V>` (`rust/map.rs:310`).
- Every generated `$Msg$Mut<'msg>` (from `message.cc:684-694`), whose upb-backend inner type `MessageMutInner` exposes `arena(&self) -> &Arena` (`rust/upb_kernel/message.rs:116-118`).

`Sync` means `&T` can be sent to and used from another thread. Once two threads each hold `&RepeatedMut<T>` (or `&MapMut`, `&$Msg$Mut`) for the same underlying arena, both can call the shared-`&self` `arena()` method and obtain aliased `&Arena` references, then call `Arena::alloc` from each thread concurrently. Because `Arena::alloc` performs raw `upb_Arena_Malloc` calls without any synchronization (matching the non-thread-safe C `upb_Arena`), this is a genuine data race on the arena's internal block/allocation-pointer state.

### Impact Explanation
This is stronger than the original CVE's abstract "data race" framing: because `upb_Arena_Malloc` mutates internal pointers/bump-allocator state without synchronization, a true concurrent-allocation race here can corrupt the arena's internal bookkeeping, leading to memory corruption (overlapping allocations, use of stale metadata) rather than merely returning inconsistent results. This is a genuine invariant violation reachable purely through the safe public Rust API surface (shared references plus normal accessor methods), not requiring `unsafe` code from the caller.

### Likelihood Explanation
Requires an application to share a `RepeatedMut`/`MapMut`/message-`Mut` (or something built on top of it) across threads and drive mutation/allocation concurrently — plausible in any multi-threaded Rust service using generated protobuf types with the upb backend, since `Sync` is the language-level "this is safe to share across threads" contract that the type system advertises as true.

### Recommendation
Either make `RepeatedMut`, `MapMut`, and the upb-backend `$Msg$Mut` types genuinely `!Sync` (remove the blanket `unsafe impl Sync`), or change `arena()`/equivalent accessors to require `&mut self` so that Rust's aliasing rules prevent two threads from concurrently obtaining `&Arena` through these wrappers. Audit all `unsafe impl Sync`/`Send` in `rust/` for accessors that leak references to types intentionally marked `!Sync` (i.e., `Arena`).

### Proof of Concept
Conceptual reproduction (not run in this environment): construct a `Repeated<T>` on the upb backend, obtain `RepeatedMut` via `as_mut()`, wrap it in `Arc`/`std::thread::scope` and share `&RepeatedMut<T>` to two threads; each thread calls `.arena(Private)` to get `&Arena` and then calls `.alloc(...)` concurrently. Under a race detector (e.g. ThreadSanitizer against the underlying upb C allocator, since `upb_Arena_Malloc` is explicitly documented non-thread-safe), this should report a data race on the arena's internal allocation state, consistent with the documented `upb::Arena` thread-compatibility (not thread-safety) model in `docs/upb/vs-cpp-protos.md:79-85`.

/// mutability. The upb_Arena C object could be understood as being Sync (at
/// least vacuously under current API since there are not any const upb_Arena*
/// API functions), but the Rust Arena is necessarily expressed as interior
/// mutability (&self rather than &mut self receivers) See https://doc.rust-lang.org/nomicon/lifetime-mismatch.html and
/// https://blog.reverberate.org/2021/12/19/arenas-and-rust.html, and the
/// 'known problems' section of https://rust-lang.github.io/rust-clippy/master/index.html#/mut_from_ref.

pub struct Arena {
    // Safety invariant: this must always be a valid arena
    raw: RawArena,
    _not_sync: PhantomData<UnsafeCell<()>>,
}

// SAFETY: `Arena` uniquely holds the underlying RawArena and has no
// thread-local data.
unsafe impl Send for Arena {}

    /// # Safety

    /// - `align` must be less than `UPB_MALLOC_ALIGN`.
    #[allow(clippy::mut_from_ref)]
    #[inline]
    pub unsafe fn alloc(&self, size: usize, align: usize) -> Option<&mut [MaybeUninit<u8>]> {
        debug_assert!(align <= sys_arena::UPB_MALLOC_ALIGN);
        // SAFETY: `self.raw` is a valid UPB arena
        let ptr = unsafe { sys_arena::upb_Arena_Malloc(self.raw, size) };

        if ptr.is_null() {
            None
        } else {
            // SAFETY:
            // - `upb_Arena_Malloc` promises that if the return pointer is non-null, it is
            //   dereferencable for `size` bytes and has an alignment of `UPB_MALLOC_ALIGN`

            //   `UPB_MALLOC_ALIGN` boundary.

        }
    }
