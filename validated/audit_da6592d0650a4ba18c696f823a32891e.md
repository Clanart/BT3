### Title
Path-boundary check in `resolveWithin` uses unanchored `startsWith`, allowing a symlink in a fetched/merged repo to exfiltrate files outside the repo via Copilot conflict resolution - (File: `app/src/lib/path.ts`)

### Summary
Every "is this path still inside the repo" guard in Desktop — used for deep-link file opening, and for reading/writing files during AI-assisted merge-conflict resolution — funnels through `resolveWithin()`/`_resolveWithin()`. Its final safety check is a bare string `startsWith` comparison between the `realpath`-resolved candidate and the `realpath`-resolved root, with no separator boundary. A resolved path in a sibling directory whose name merely starts with the repository directory's name (e.g. `myrepo-old`, `myrepo.bak`, `myrepo2`) passes the check even though it is *not* inside the repository, exactly the same class of bug as the seed report: a boundary/invariant comparison that is subtly wrong and always/incorrectly evaluates true for a class of otherwise-invalid inputs. [1](#0-0) 

### Finding Description
`_resolveWithin` computes:
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` has no notion of path segments. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` and `realResolved` is `/Users/victim/Documents/GitHub/myrepo-secret/id_rsa`, the check passes because `"myrepo-secret".startsWith("myrepo")` is true, even though `myrepo-secret` is a completely different, sibling directory. The existing unit tests only cover `..`-traversal, null bytes, and symlinks pointing to ancestor directories — they never test the "sibling directory with matching prefix" case, so this gap is unguarded. [3](#0-2) 

This primitive becomes attacker-reachable through the Copilot merge-conflict-resolution feature, which is exactly the "attacker controls a cloned/fetched repository" scenario:

1. `buildConflictContext` resolves each conflicted file's repo-relative path with `resolveWithin(workingDirectory, file.path)` and then reads its content with `readFile`, later sending that content to the Copilot model as prompt context. [4](#0-3) 

2. `_stageCopilotResolutions` in `app-store.ts` resolves each Copilot resolution's path the same way and then writes the model-influenced content back to disk with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`. [5](#0-4) 

An attacker who controls a branch/commit that the victim merges, rebases, or cherry-picks from (a normal, unprivileged git operation on a fetched remote) can commit a symlink at a path that will end up conflicted, pointing outside the repository at a sibling directory whose name happens to share the repo directory name as a prefix (a common naming pattern for backups/forks: `project`, `project-old`, `project.bak`, `project2`, etc.). When the victim opens the "resolve conflicts with Copilot" flow:
- The read path resolves and reads the symlink target content (e.g. secrets/config living in the sibling directory) and uploads it to Copilot as conflict context — **credential/token exfiltration**.
- The write path can be induced to write model output back through the same symlink, corrupting a file **outside** the intended repository — **file write outside the repo** and silent corruption of unrelated data.

### Impact Explanation
This breaks the repo-containment invariant that `resolveWithin` is supposed to provide app-wide. Concretely it enables:
- Reading arbitrary files in sibling directories and exfiltrating their contents to a third-party network service (Copilot), satisfying "credential/token exfiltration."
- Writing to files outside the intended repository root, satisfying "file write ... outside the repo" and "silent corruption of what the user commits."

Because `resolveWithin` is the single shared guard used by multiple features (deep-link filepath opening in `dispatcher.ts`, Copilot conflict read/write in `copilot-conflict-context.ts` and `app-store.ts`), a fix or bypass here has app-wide consequences. [6](#0-5) 

### Likelihood Explanation
No local access, admin rights, or leaked credentials are required. The only requirement is that the victim merges/rebases/cherry-picks a branch containing attacker-controlled content (a completely ordinary, expected git workflow with a fetched/cloned remote) and then uses the built-in "resolve with Copilot" feature on the resulting conflict. Whether a matching-prefix sibling directory exists is somewhat environment-dependent (though prefix-matching backup/fork directory names are common), which is the main factor limiting reliability, but the underlying boundary check is unconditionally broken for any input that satisfies the naming condition.

### Recommendation
Fix the boundary check to compare path segments instead of raw strings, e.g.:
```ts
import { sep } from 'path'
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
Apply the fix once in `_resolveWithin` in `app/src/lib/path.ts` (and its `win32`/`posix` variants share the same helper, so a single fix covers all callers). Add regression tests for the "sibling directory with matching name prefix" case (both as a plain path and via a symlink) alongside the existing `resolveWithin` tests.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdtemp, symlink, mkdir, rmdir, unlink, writeFile } from 'fs/promises'
import { join, dirname } from 'path'
import { tmpdir } from 'os'

// Simulate: root = ".../myrepo", sibling = ".../myrepo-secret"
const base = await mkdtemp(join(tmpdir(), 'poc-'))
const root = join(base, 'myrepo')
const secretDir = join(base, 'myrepo-secret')
await mkdir(root)
await mkdir(secretDir)
await writeFile(join(secretDir, 'id_rsa'), 'PRIVATE KEY DATA')

// attacker-committed symlink inside the repo, pointing to the sibling dir
await symlink(join(secretDir, 'id_rsa'), join(root, 'conflicted-file.txt'))

const resolved = await resolveWithin(root, 'conflicted-file.txt')
// BUG: resolved !== null even though the real target lives in "myrepo-secret",
// a completely different directory outside "myrepo".
console.log(resolved) // -> join(root, 'conflicted-file.txt'), used to readFile/writeFile
```
When exercised through `buildConflictContext`, `readFile(absolutePath, 'utf8')` at line 431 of `copilot-conflict-context.ts` returns `PRIVATE KEY DATA` and includes it in the Copilot prompt payload, despite the file living entirely outside the repository.
