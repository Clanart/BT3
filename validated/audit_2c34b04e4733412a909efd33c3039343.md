## Analysis

Confirmed: the `msg.chain`/`msg.app` in `PurchaseMessage` are attacker-controlled fields inside the ISMP request body sent from any EVM `BandwidthManager.purchase()` call, and `push_subscription` keys the FIFO list by `(app_chain, app)` — not by `request.source`. Any account on any registered source chain can call `purchase()` for the cheapest configured tier and target an arbitrary victim `app` on an arbitrary `app_chain`. Once the target's `Allowance` list reaches `MAX_SUBSCRIPTIONS` (1024), each further cheap purchase evicts index 0 — the oldest live subscription — regardless of its size or value, per [1](#0-0) .

### Title
Unprivileged bandwidth-subscription eviction griefing causes loss of paid bandwidth allowance - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth` keys the FIFO `Allowance` list by `(app_chain, app)` taken from the purchase message body, not by the caller/source chain [2](#0-1) . This "sponsorship" design intentionally lets any payer on any chain credit bandwidth for any app. Combined with the FIFO cap-and-evict logic in `push_subscription`, which unconditionally evicts the single oldest entry once the list holds 1024 subscriptions [3](#0-2) , an unprivileged attacker can spam cheap tier purchases targeting a victim app's `(app_chain, app)` key until the queue fills, then continue purchasing to evict the victim's legitimately paid, larger/more valuable, still-unconsumed subscription — permanently destroying the bytes the victim already paid for (`SubscriptionEvicted.lost_bytes`).

### Finding Description
This is the local analog of the RocketPool deposit-delay DoS: in the external report, an attacker's cheap, permissionless action (`stake()`) resets shared state (the deposit delay) that blocks another user's legitimate withdrawal (`unstake()`). Here, an attacker's cheap, permissionless action (`purchase()` for the lowest tier, targeting an arbitrary `(app_chain, app)`) mutates shared per-app state (the FIFO `Allowance` list) in a way that destroys another user's already-paid entitlement (`SubscriptionEvicted`), rather than blocking a call outright — the same "cheap attacker action corrupts shared queued state to the victim's detriment" primitive.

The eviction rule evicts strictly by position (`list.remove(0)`), not by value, size, or remaining-bytes — so a 1-byte cheapest-tier purchase can evict a subscription that cost the victim a large sum and still has most of its allowance unconsumed, as long as it happens to be at the front of the FIFO (i.e., the oldest not-yet-fully-drained entry). Because `msg.chain` and `msg.app` come straight from the ISMP request body of the purchase message and are validated only against the registered `BandwidthManager` contract address for that chain (`request.from == manager`), not against any relationship between the caller and the app being credited, nothing stops a purchaser from targeting any third party's app [4](#0-3) . This is explicitly the intended "sponsorship" model documented in the docs, which states the payer chain can be entirely independent of the app's own chain [5](#0-4) .

### Impact Explanation
Victim apps lose bandwidth they already paid for — a direct loss-of-funds impact under the bounty's "stealing or loss of funds" and "logic attacks" categories. Because the gate drains FIFO from the head and enforces "no mutation on insufficient" only for the *consume* path, not the *credit/evict* path, the eviction directly destroys value with no compensating mechanism: `SubscriptionEvicted` is emitted but the pallet performs no refund. If the queue is spammed faster than the victim's app drains it, an attacker can target and destroy a specific expensive subscription entry deterministically once the queue is at cap and the victim's target entry is next in FIFO order.

### Likelihood Explanation
The attack is fully public-entrypoint and requires no privileged role, relayer collusion, or malicious node — only calling `BandwidthManager.purchase()` on any registered source chain enough times for the cheapest configured tier, and a delivering relayer (which is a normal, permissionless part of message flow, not an adversarial assumption). Cost scales with `MAX_SUBSCRIPTIONS` (1024) times the cheapest tier price, which per the plan table can be as low as $50 for 100 KB — so filling/evicting through a 1024-entry queue is bounded and could be economically feasible for an attacker targeting a high-value victim subscription, especially since eviction only requires reaching the cap once and doesn't require draining any bytes.

### Recommendation
- Key `Allowance` eviction/credit paths so an app's own subscriptions cannot be evicted by third-party purchasers, e.g., require the purchasing chain to match `app_chain`, or maintain a per-payer sub-list, or increase `MAX_SUBSCRIPTIONS` bound per unique payer.
- Alternatively, evict by remaining value/lowest-value entry rather than strict insertion order, or refuse to evict entries with remaining_bytes above a de minimis threshold, forcing new purchases beyond the cap to fail instead of destroying value.
- Emit and gate on a cost-to-evict metric so an attacker cannot destroy a large paid allowance with a disproportionately cheap purchase.

### Proof of Concept
1. Victim buys a large/expensive tier for `(app_chain = EVM(8453), app = "MyApp")`, creating a `Subscription` with large `remaining_bytes` inserted into `Allowance::<T>::get(EVM(8453), "MyApp")`.
2. Attacker, from any registered source chain (can even be a different chain than `app_chain`, per the sponsorship model), repeatedly calls `BandwidthManager.purchase()` with `chain = EVM(8453)`, `app = "MyApp"`, and the cheapest configured tier, `months = 1`.
3. Each delivered purchase message hits `on_accept` → `push_subscription(&msg.chain, &key, ...)` [6](#0-5) , appending a new subscription to the same `Allowance` list keyed by the victim's `(app_chain, app)`.
4. Once the list reaches 1024 entries, each subsequent attacker purchase evicts `list.remove(0)` — the oldest entry — via `push_subscription` [1](#0-0) .
5. If the victim's expensive subscription is (or becomes, after enough spam purchases age it to the front) the oldest live entry, it gets evicted and its `remaining_bytes` are permanently lost (`SubscriptionEvicted.lost_bytes`), with no refund path in the pallet.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
