## Finding Analysis [1](#0-0) 

`HyperbridgeWithdrawalModule::on_accept` only authenticates the **chain** that a `PostRequest` came from — it never authenticates **which module/pallet on that chain** dispatched it: [2](#0-1) 

```rust
fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
    // Only the configured coprocessor may instruct withdrawals.
    let source = request.source;
    if Some(source) != T::Coprocessor::get() {
        Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
    }

    let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
        .map_err(...)?;
    ...
```

`request.source` binds to a `StateMachine` identifier (i.e., which chain originated the message, validated via consensus/state proofs — this part is genuine and not spoofable). However, `request.from`, the module identifier of the *sender pallet/contract on that source chain*, is never checked. The routing that dispatches into this module is purely keyed on the *destination* id (`HYPERBRIDGE_MODULE_ID`) via `IsmpHostRouter::module_for_id`: [3](#0-2) 

Because `dispatch_request` (the generic outbound `IsmpDispatcher` on any chain, including the Coprocessor chain) lets the calling pallet/contract freely set both `to` (destination module id) and `from` (source module id) on the `PostRequest` it constructs: [4](#0-3) 

any account/pallet that has access to dispatch an ISMP `PostRequest` **from the configured Coprocessor state machine** to `to = HYPERBRIDGE_MODULE_ID` on this chain can craft a body that decodes as `Message::WithdrawRelayerFees(WithdrawalRequest { account, amount })`. There is no verification that the message actually originated from the specific intents-coprocessor pallet/logic that is supposed to be the sole authority for relayer-fee accounting — only that it came from *some* application on the correct chain. The transfer itself is fully attacker-controlled at the destination step: [5](#0-4) 

This exactly matches the "source-app binding" gap called out in the file's own scope description — the check authenticates the state machine but not the sending module, so `account`/`amount` are attacker-controlled if any code path on the Coprocessor chain can originate an ISMP post addressed to `HYPERBRIDGE_MODULE_ID`.

**What I could not fully verify:** whether the Coprocessor state machine's own runtime restricts *who/what* on that chain may dispatch arbitrary ISMP `PostRequest`s (i.e., whether sending a cross-chain message with an arbitrary `to`/`from` is itself gated to a privileged, single-purpose pallet such as `intents-coprocessor`, or is reachable by any ordinary account/contract on that chain). I found the `intents-coprocessor` pallet exists on that chain [6](#0-5)  but did not confirm in this session whether generic outbound ISMP dispatch on that specific parachain is open to arbitrary unprivileged callers or narrowly scoped to trusted pallets only. If dispatch is open (e.g. via a generic pallet-ismp "dispatch" extrinsic/precompile available to any account on the Coprocessor chain), this is directly exploitable by an unprivileged user. If it is hard-restricted so that only the intents-coprocessor pallet logic can ever produce a `PostRequest` targeting `HYPERBRIDGE_MODULE_ID`, then the missing `from` check is a defense-in-depth gap rather than an immediately exploitable path.

### Title
Missing source-module binding in `HyperbridgeWithdrawalModule::on_accept` allows any Coprocessor-chain sender to forge relayer-fee withdrawals - (File: modules/pallets/ismp/src/dispatcher.rs)

### Summary
`on_accept` verifies only that the request's source **state machine** equals `T::Coprocessor`, but never verifies the request's source **module** (`request.from`). Any code path capable of dispatching an ISMP `PostRequest` from the Coprocessor chain targeting `HYPERBRIDGE_MODULE_ID` can forge a `Message::WithdrawRelayerFees` payload with an arbitrary `account`/`amount`.

### Finding Description
`IsmpHostRouter::module_for_id` routes all inbound requests addressed to `HYPERBRIDGE_MODULE_ID` to `HyperbridgeWithdrawalModule`, regardless of which pallet/contract on the source chain produced the request [3](#0-2) . `on_accept` then checks `request.source == T::Coprocessor::get()` but performs no check on `request.from` [2](#0-1) . The decoded `account`/`amount` fully determine the destination and size of a direct transfer out of `RELAYER_FEE_ACCOUNT` [5](#0-4) , with no additional binding to the original fee-payer, claimant identity, or a specific trusted sending pallet.

### Impact Explanation
If the Coprocessor chain permits any account/module to dispatch a generic outbound ISMP `PostRequest` (setting arbitrary `to`/`from`/`body`), an attacker can redirect the entire relayer-fee pool to an arbitrary account, causing direct loss of protocol/relayer funds.

### Likelihood Explanation
Depends entirely on whether outbound ISMP dispatch on the Coprocessor chain is permissionless or restricted to the trusted `intents-coprocessor` pallet — this could not be conclusively confirmed in this review.

### Recommendation
Bind `on_accept` to both `request.source` and a well-known `request.from` module id corresponding to the trusted fee-accounting pallet/contract on the Coprocessor chain, rejecting any request whose `from` does not match.

### Proof of Concept
Not constructed — would require confirming that the Coprocessor chain's runtime exposes an unprivileged/dispatchable path to send an ISMP `PostRequest` with `to = HYPERBRIDGE_MODULE_ID` and attacker-chosen `body`.

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
