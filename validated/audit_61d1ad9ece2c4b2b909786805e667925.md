### Title
`PedPoPError::InvalidShare` embeds the ECDH decryption key, leaking DKG secret shares when the error is logged or printed - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG's error type `PedPoPError::InvalidShare` carries `blame: Option<EncryptionKeyProof<C>>`, where `EncryptionKeyProof.key` is the ECDH shared point used to ChaCha20-decrypt that participant's secret share. Because `PedPoPError` derives `Debug` and is a `thiserror` `Error` rendered with `blame {blame}` (Debug of `Option<EncryptionKeyProof>`), any standard error logging (`log::warn!("{err}")`, `println!("{err:?}")`, error-reporting middleware, etc.) writes the ECDH key — sufficient to decrypt the corresponding `EncryptedMessage<SecretShare>` — to OS-visible logs. This is the Serai analog of "passwords in shell history": a secret that must never touch logs is placed inside a type whose whole purpose is to be displayed.

### Finding Description
- `PedPoPError::InvalidShare` is defined with `blame: Option<EncryptionKeyProof<C>>` and derives `Debug`; its `#[error]` string interpolates `blame`, so formatting the error emits the proof's fields. [1](#0-0) 
- `EncryptionKeyProof` contains `key: Zeroizing<C::G>` — the ECDH shared point `enc_key * msg.key` — and derives `Debug`, so `Zeroizing<C::G>`'s point bytes are printed by `{:?}`/Display of the error. [2](#0-1) 
- That key is exactly what `decrypt_with_proof` feeds to `cipher(context, &proof.key).apply_keystream(...)` to recover the plaintext `SecretShare`; possession of `key` plus the public ciphertext is equivalent to possessing the share. [3](#0-2) 
- The error is produced in `KeyMachine::calculate_share` whenever `C::F::from_repr` rejects a decrypted share, or when the batch share-verification fails (`BatchId::Share`), attaching `blames[l]` unconditionally — even when the failure was caused by an attacker-controlled malformed message, i.e., an unprivileged remote participant can force this error to be produced and logged. [4](#0-3) 
- The code comments acknowledge the danger: revealing `bX` (the ECDH key) "reveals Alice's message to Bob. This is a massive side effect which could break some protocols" — yet the error path emits exactly this secret into a `Debug`-derived, `Display`-able error value intended to propagate to callers. [5](#0-4) 

### Impact Explanation
A malicious DKG participant (a reachable, unprivileged party: they only need to send an `EncryptedMessage` / `EncryptionKeyMessage` to `calculate_share` / `verify_r1`) sends a deliberately corrupted share. The victim's `calculate_share` returns `Err(PedPoPError::InvalidShare { blame: Some(proof) })`. If the embedding application logs the error — the idiomatic handling for a `std::error::Error` — the ECDH key lands in journald/syslog/stdout. Anyone with read access to those logs plus the (broadcast/transmitted) ciphertext can run `cipher(context, &proof.key)` over the ciphertext bytes and recover the victim's intended secret share for that sender. Combined with the documented threat model ("third-party knowledge of your preprocess... enables recovery of your private key share"), leaked shares across enough senders collapse the DKG's privacy and can enable reconstruction of signing key material the share contributes to.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that logs errors (the default behavior for `thiserror` types in Rust services). The trigger is fully attacker-controlled: any participant in the DKG can cause `InvalidShare` by sending garbage in the encrypted-share round. The secret material leaked (`EncryptionKeyProof.key`) is directly sufficient for offline decryption — no further interaction is required. The only mitigating factor is that the error must actually be formatted/persisted by the caller, which is extremely common but integrator-dependent.

### Recommendation
Do not place secrets inside error values. `PedPoPError::InvalidShare` should carry only a non-secret indicator (e.g., `participant` plus a hash/commitment of the blame proof, or a `bool` that blame evidence exists). Return the `EncryptionKeyProof` through a separate, explicitly-secret channel: either a distinct `Ok`-like return type the caller must opt into persisting, or a dedicated `blame_proof()` accessor on `BlameMachine`/`AdditionalBlameMachine`. At minimum, remove `Debug`/`Display` coverage of `EncryptionKeyProof`'s `key` field (a manual `fmt::Debug` printing `finish_non_exhaustive()`, as `SecretShare` already does at `crypto/dkg/pedpop/src/lib.rs:242-246`), and document that blame proofs must be zeroized and never logged.

### Proof of Concept
```rust
// Requires: a PedPoP DKG session on any in-scope ciphersuite (e.g., Ristretto).
// Attacker (participant l) sends victim i a malformed EncryptedMessage<SecretShare>
// in KeyMachine::calculate_share. Victim's call returns:
let err = key_machine
  .calculate_share(&mut OsRng, attacker_controlled_shares)
  .unwrap_err();

// Idiomatic logging of a thiserror error, as deployed services do:
log::warn!("DKG failed: {err}");
// Output contains: "invalid share (participant N, blame Some(EncryptionKeyProof {
//   key: <POINT BYTES>, dleq: ... }))" — i.e., the ECDH shared point.

// An attacker (or anyone) reading the logs extracts `key` and decrypts the
// ciphertext they themselves sent... or any ciphertext encrypted under the
// same ECDH relation — for the blame key, this is the victim's share bytes:
let mut ct = intercepted_ciphertext_bytes(); // EncryptedMessage.msg for sender N -> victim
let key: <C as Ciphersuite>::G = parse_logged_point();
let mut cipher = cipher::<C>(context, &Zeroizing::new(key)); // same derivation as decrypt_with_proof
cipher.apply_keystream(&mut ct);
// ct now equals SecretShare bytes for sender N's polynomial evaluated at victim i.
// Repeating this against enough senders leaks enough share data to attack the
// resulting ThresholdKeys secret share.
```
