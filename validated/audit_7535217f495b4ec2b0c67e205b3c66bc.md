### Title
Deserialized `ThresholdKeys` are never authenticated: `ThresholdKeys::read`/`new` accept attacker-controlled shares and participant index with no consistency or provenance check - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The AVideo report is a missing-authorization bug: an endpoint consumes fully attacker-controlled inputs (token, IDs) and acts on them, while sibling endpoints enforce `User::isAdmin()`. The structural analog in Serai is `ThresholdKeys::read`, an explicitly in-scope sink for untrusted bytes. It deserializes `t`, `n`, the caller's `Participant` index `i`, the interpolation, the `secret_share`, and all `verification_shares` purely from the byte stream, then calls `ThresholdKeys::new`, which performs only syntactic validation — never checking that `secret_share` actually corresponds to `verification_shares[i]`, nor binding the keys to any authorized/expected `group_key`. Any party who can feed bytes to `ThresholdKeys::read` (e.g., key-recovery, key-promotion, or transport paths that ship serialized `ThresholdKeys` between components) can therefore materialize a signing-capable `ThresholdKeys` claiming an arbitrary participant index and an arbitrary group key, with no proof that the secret share is authorized for that key.

### Finding Description
`ThresholdKeys::read` reads `(t, n, i)`, the interpolation variant, `secret_share`, and `n` verification shares directly from the reader, then constructs keys via `ThresholdKeys::new` [1](#0-0) .

`ThresholdKeys::new` validates only:

- `verification_shares.len() == n` and each participant index `<= n` [2](#0-1) 
- interpolation applicability and `t <= n` (inside `ThresholdParams::new`) [3](#0-2) 

It then derives `group_key` by interpolating verification shares `1..=t` — all attacker-chosen [4](#0-3) . There is no check equivalent to `C::generator() * secret_share == verification_shares[&i]`, the exact analog of AVideo's missing `User::isAdmin()` gate: the secret that authorizes signing is accepted without any proof it belongs to the claimed public key. The code itself acknowledges this gap downstream: `AlgorithmSignatureMachine::complete` documents `InternalError("everyone had a valid share yet the signature was still invalid")` as reachable "to deserialize a semantically invalid FrostKeys" [5](#0-4) .

Two consequences follow from feeding crafted bytes:

1. **Self-authorized key material**: an attacker sets all `verification_shares` to `k_l * G` for scalars they know and a consistent `secret_share` under `i`. `read` succeeds, `group_key()` returns an attacker-chosen key, and `view()` + `AlgorithmSignatureMachine::complete` produce valid FROST signatures under it — under whatever `Participant` index the bytes claim, impersonating that participant index to any downstream logic that keys off `params().i()`. The reader performs "arbitrary Graph API calls through the server" in analog form: arbitrary participant identity and group key are honored without authorization.
2. **Inconsistent shares**: attacker sets `verification_shares` to the *honest* DKG output (public data) but `secret_share` to a value they choose. `read` succeeds; signing then fails share verification or hits the `InternalError` path above — silently swapping which participant is blamed (the honest participant whose index `i` was claimed gets `InvalidShare(i)`).

By contrast, the sibling trust boundary in the same crate is enforced: `ThresholdKeys::view` rejects duplicated/out-of-range/non-participating sets [6](#0-5) , and PedPoP's `calculate_share` batch-verifies every received share against commitments [7](#0-6)  — the equivalent of the authenticated `uploadVideo.json.php`/`refresh.json.php` siblings. The deserialization path is the one endpoint missing the check.

### Impact Explanation
Any component that accepts serialized `ThresholdKeys` from a party other than the local DKG output — key recovery (`crypto/dkg` recovery/`promote` paths), backup restore, or cross-process key transport — grants the byte supplier an unauthenticated assertion of (participant index, group key, secret share). At minimum this yields a signing oracle under attacker-chosen group keys wearing an arbitrary participant identity, misattributed blame (`FrostError::InvalidShare`/`InvalidPreprocess` pointing at an innocent index), and denial of service of signing sessions via the `InternalError` path. Where the receiving component cross-checks `group_key()` against an expected network key (e.g., a Bitcoin-derived address), impact reduces to DoS; where it does not (which this API permits — nothing forces such a check), it is unauthorized signing key registration. Consistent with the report's Medium rating.

### Likelihood Explanation
Reachable whenever serialized `ThresholdKeys` bytes cross a trust boundary; the sink is explicitly in-scope for untrusted bytes. Exploitation requires no secret knowledge — option 1 needs only scalars the attacker generates, option 2 only public verification shares. The primary mitigations are external: honest participants normally generate keys via PedPoP rather than `read`, and callers may independently compare `group_key()`. The missing primitive-level check means the API provides no defense in depth.

### Recommendation
In `ThresholdKeys::new`, enforce the authorization invariant that the secret share is valid for the claimed index:

```rust
// crypto/dkg/src/lib.rs, inside ThresholdKeys::new, after existing checks
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::InvalidShare)? // new variant: secret share inconsistent with verification share
}
```

Additionally document that `ThresholdKeys::read`/`new` do not authenticate provenance — callers deserializing keys from external input must verify `group_key()` equals an expected/authorized key before signing, mirroring the report's fix of gating the endpoint on `User::isAdmin()`.

### Proof of Concept
```rust
// Attacker supplies bytes to any path calling ThresholdKeys::read.
// t=1, n=1, i=Participant(1), Interpolation::Lagrange (tag 1)
let k = <Ed25519 as Ciphersuite>::F::random(&mut OsRng);   // attacker-known secret
let mut bytes = vec![];
bytes.extend((Ed25519::ID.len() as u32).to_le_bytes());
bytes.extend(Ed25519::ID);
bytes.extend(1u16.to_le_bytes());                          // t
bytes.extend(1u16.to_le_bytes());                          // n
bytes.extend(Participant::new(1).unwrap().to_bytes());     // i — attacker claims index 1
bytes.push(1);                                             // Lagrange
bytes.extend(k.to_repr().as_ref());                        // secret_share = k
bytes.extend((Ed25519::generator() * k).to_bytes().as_ref()); // vs[1] = k*G

// Succeeds: no authorization check binds these keys to any expected group key.
let keys = ThresholdKeys::<Ed25519>::read(&mut bytes.as_slice()).unwrap();
assert_eq!(keys.params().i(), Participant::new(1).unwrap());
// keys.view(vec![Participant(1)]) + AlgorithmSignatureMachine::complete
// now sign under the attacker-chosen group_key() while claiming participant 1.
```

Variant: replace `k*G` in the last field with the victim DKG's real `verification_shares[1]` and `k` with `random` — `read` still succeeds, but every `complete` fails with `InvalidShare(Participant(1))` or `InternalError`, attributing fault to the impersonated index.

      (usize::from(self.params().n()) < included.len())

      let mut found = included[0] == self.params().i();
