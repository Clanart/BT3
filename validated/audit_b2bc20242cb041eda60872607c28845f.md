## Title
Missing path-separator boundary in `resolveWithin()` allows sibling-directory escape via attacker-controlled deep-link `filepath` - (File: `app/src/lib/path.ts`)

## Summary
`resolveWithin()` is the app's sole containment guard for turning an untrusted relative path into a path that is guaranteed to stay "at or underneath" a root directory. Its final check is a plain string `startsWith()` comparison between the resolved real path and the real root path, with no verification that the next character after the root is a path separator (or that the paths are exactly equal). This mirrors the root cause pattern in the Auction bug: a boundary/validity check computed without accounting for the exact edge condition, letting an attacker craft an input that numerically/lexically satisfies the check while violating its intended semantics.

## Finding Description
`_resolveWithin()` in `app/src/lib/path.ts` resolves `pathSegments` against `rootPath` and then validates containment purely with: [1](#0-0) 

```
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path boundaries: `"/Users/victim/Documents/GitHub/myrepo-secrets/passwords.txt".startsWith("/Users/victim/Documents/GitHub/myrepo")` evaluates to `true`, even though `myrepo-secrets` is a sibling directory, not a descendant of `myrepo`. So any resolved path whose sibling directory name simply has the repository's directory name as a string prefix passes the "containment" check.

This function is reachable from an attacker-controlled input via the "Open in Desktop" custom URL scheme handler. `parseAppURL()` extracts a `filepath` query parameter directly from the URL with no sanitization beyond checking it isn't absolute: [2](#0-1) 

That `filepath` flows into `openRepositoryFromUrl()`: [3](#0-2) 

```
    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
```

`isAbsolute()` only blocks paths starting with `/` or a drive letter; it does not block `..` traversal segments, so a value like `filepath=../myrepo-secrets/passwords.txt` (relative, non-absolute) passes the absolute-path check, is joined/resolved against `repository.path`, and produces a path in a *sibling* directory whose name starts with the repository's own folder name. The buggy `startsWith` boundary check then incorrectly treats that sibling path as "within" the repository and passes it to `shell.showItemInFolder`.

Existing tests confirm the exact boundary case is intentionally treated as valid for the "root ends exactly at a path separator" scenario but never test the sibling-prefix collision case: [4](#0-3) 

## Impact Explanation
This breaks the "attacker controls a link/deep link the user clicks" → "file read outside the repo" category. A crafted `x-github-client://openRepo/...?filepath=...` (or platform-equivalent `github-windows://`/`github-mac://`) link, once clicked by the victim, can cause Desktop to reveal/select an arbitrary file located in a sibling directory of the cloned repository (as long as that sibling directory's name has the repo folder's name as a prefix — which is a realistic layout, e.g. `myrepo` next to `myrepo-backup`, `myrepo.old`, `myrepo-secrets`, etc., or an attacker can also lure the victim into naming/cloning into a directory whose name is a prefix of another sensitive folder). Because `resolveWithin` is the app's general-purpose containment primitive (also used to gate `writeFile` calls, e.g. in Copilot conflict resolution), the same boundary flaw threatens any other call site that uses it to guard a filesystem write or read against attacker-influenced relative segments — not only the deep-link `filepath` handler.

## Likelihood Explanation
Exploitation requires only that the user click a single deep link (a normal, expected Desktop feature — "Open in Desktop" links are meant to be clicked by users from web pages/emails) — no local access, no malware, no elevated privileges. The `filepath` parameter is fully attacker-controlled through the URL and only lightly validated (absolute-path rejection, no `..` rejection). The main constraint is that a plausibly-named sibling directory must exist next to the target repository, which is a common real-world occurrence (backup folders, `-old`/`-secrets`/`-v2` suffixed sibling repos, etc.), making this a realistic, low-effort attack chain rather than a purely theoretical one.

## Recommendation
Fix `_resolveWithin()` to check the path boundary explicitly, not just a string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Additionally, reject `..` traversal segments (or any resolution that requires escaping `rootPath` before returning) in the deep-link `filepath` handler as defense in depth, matching the stricter validation already applied to `branch` via `testForInvalidChars` in `app/src/lib/parse-app-url.ts`.

## Proof of Concept
1. Victim has a cloned repository at `/Users/victim/Documents/GitHub/myrepo` and a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets/passwords.txt`.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fpasswords.txt`.
3. Victim clicks the link; GitHub Desktop opens/handles it via `parseAppURL` → `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1940-1972`).
4. `resolveWithin(repository.path, "../myrepo-secrets/passwords.txt")` resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/passwords.txt`; the `startsWith(realRoot)` check in `app/src/lib/path.ts:71` incorrectly returns this as "within" `myrepo` because the string `"...myrepo-secrets/passwords.txt"` starts with `"...myrepo"`.
5. `shell.showItemInFolder(resolved)` reveals/selects the out-of-repo file to the attacker's chosen location, confirming the containment bypass.

Note: I was unable to fully verify every other call site of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` in the codebase (the `grep_search` for the exact call pattern failed due to a regex escaping error and could not be re-run since tool access has ended); the Copilot conflict-resolution `writeFile` usage shown earlier in this session is one such additional call site worth auditing for the same boundary flaw.
