### Title
Missing "approve-to-zero-first" in `IBCReceivePacketCallback` permanently freezes user funds for USDT-style native ERC20 tokens - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCReceivePacketCallback` sets an ERC20 allowance for a destination contract by calling `approve(contractAddr, amountInt)` unconditionally on every incoming IBC-callback-enabled transfer, without first resetting the allowance to zero. This is the exact bug class described in the Connext report: certain ERC20 tokens (e.g. USDT) revert on `approve()` when the current allowance is non-zero and the new amount is also non-zero. Because the token contract targeted here can be an arbitrary, externally registered "native ERC20" contract (not the Cosmos-controlled minter/burner contract), a USDT-style token can end up in a permanently-reverting state for a given isolated receiver address, freezing user funds that were sent via IBC.

### Finding Description
In `IBCReceivePacketCallback`: [1](#0-0) 

the keeper resolves the destination ERC20 contract via `tokenPair.GetERC20Contract()` and directly calls `approve(contractAddr, amountInt.BigInt())` through `CallEVM`, using only the standard ERC20 ABI for encoding — the actual bytecode executed is whatever contract is registered for that token pair. For token pairs of type "native ERC20" (arbitrary externally-deployed tokens registered through the module, as opposed to the Cosmos-native `ERC20MinterBurnerDecimalsContract`), this can be any ERC20 implementation, including tokens that implement the classic front-running-protection restriction (revert `approve()` if current allowance ≠ 0 and new amount ≠ 0, e.g. USDT).

The isolated receiver address for a given packet is deterministic — derived only from `packet.GetDestChannel()` and `data.Sender`: [2](#0-1) 

so the same `(channel, sender)` pair always reuses the same isolated EVM address, and thus the same `(owner, spender)` allowance slot for a given destination contract.

After the approve+call sequence, the code only checks that the receiver's *balance* is fully drained, not that the *allowance* was fully consumed: [3](#0-2) 

A destination contract can legitimately satisfy this balance check by pulling part of the funds via `transferFrom` and the rest via a plain `transfer()`/other mechanism, leaving a non-zero residual allowance for `contractAddr` on the token contract. On any subsequent IBC receive callback from the same sender/channel targeting the same token and same destination contract, the unconditional `approve(contractAddr, amountInt)` call will attempt to set a non-zero allowance over an existing non-zero allowance. For a USDT-style token this reverts every time, and there is no code path anywhere in this keeper that first sets the allowance to zero (unlike the fix pattern recommended in the referenced report and applied by Connext).

### Impact Explanation
Once the stale non-zero allowance exists, every future `IBCReceivePacketCallback` for that `(sender, channel, token, contractAddr)` combination permanently fails at the `approve` step, since the allowance can never be reset to zero through this code path. Since the isolated address is deterministic and cannot be changed by the user, tokens delivered to that address in the failing packet become unrecoverable: the callback path is the only way to move funds out of the isolated address (per the comment "funds may get stuck ... becomes irretrievable" at lines 230–233), and normal transfers from the isolated address are not otherwise exposed to the user. This results in permanent freezing/loss of user funds for the affected sender, matching the Critical impact category of "permanent freezing, locking, theft, or unauthorized extraction of user funds ... token-pair-backed balances."

### Likelihood Explanation
This does not require a malicious relayer or validator — any unprivileged actor can:
1. Register (or already have registered) a native ERC20 token pair backed by a USDT-style token (or deploy/point to any ERC20 with front-running-protected `approve`).
2. Send an IBC transfer with a destination callback whose target contract intentionally (or incidentally) leaves a non-zero residual allowance after moving the full balance out (e.g., contract calls `transferFrom` for part of the amount and `transfer`/other mechanism for the rest, or simply retains partial allowance by design).
3. Send a second IBC transfer from the same sender/channel to the same contract — the mandatory `approve()` call reverts, and the packet's callback fails, freezing the newly delivered funds in the (now permanently allowance-poisoned) isolated address.

This requires only ordinary user-controlled transaction/IBC flows and a single properly-behaving-but-imperfectly-draining destination contract or a real-world token with USDT semantics — no privileged access is needed.

### Recommendation
Before calling `approve(contractAddr, amountInt)`, first read the current allowance via a `allowance(owner, spender)` call (or simply always call `approve(contractAddr, 0)` first) and only then set the new allowance, mirroring the fix applied upstream (`safeApprove(..., 0)` before `safeApprove/safeIncreaseAllowance(..., amount)`). Additionally, consider enforcing/validating that the allowance is fully consumed (not just the balance) after the destination call, to prevent the residual-allowance condition from arising in the first place.

### Proof of Concept
1. Register a native ERC20 token pair for a token implementing USDT-style `approve()` (reverts if `allowance(owner,spender) != 0 && amount != 0`).
2. Configure an IBC transfer with a destination callback contract that: (a) calls `transferFrom(isolatedAddr, address(this), amount - 1)`, and (b) additionally has the isolated address itself invoke a plain `transfer(contract, 1)` for the remainder (satisfying the zero-balance check at lines 234-239 while leaving `allowance(isolatedAddr, contract) == 1`).
3. Complete the first IBC receive callback successfully; verify the isolated address balance is 0 but `allowance(isolatedAddr, contract) == 1`.
4. Send a second IBC transfer with a callback to the same contract from the same `(sender, channel)`; observe that `k.evmKeeper.CallEVM(..., "approve", contractAddr, amountInt)` at [4](#0-3)  reverts because the underlying token enforces non-zero-to-non-zero approval restriction, causing `IBCReceivePacketCallback` to return `ErrAllowanceFailed` and the newly transferred funds to become stuck in the isolated address indefinitely, since no code path resets the allowance to zero.

**Uncertainty:** I could not fully verify within index limits (a) the exact bytecode/behavior of `ERC20MinterBurnerDecimalsContract.approve()` to confirm it never itself imposes the USDT-style restriction, and (b) whether "native ERC20" token pairs (arbitrary externally-deployed contracts) can indeed be registered such that `tokenPair.GetERC20Contract()` points to an unrestricted third-party token contract — this is based on the module's documented purpose (`x/erc20` supports both "native Cosmos coin" and "native ERC20" token pair types) but the registration/whitelisting constraints on native ERC20 registration were not fully retrievable from the index. A Devin session with full repository access should confirm the `RegisterERC20` proposal flow and `ERC20MinterBurnerDecimalsContract.sol` implementation to close this gap.
