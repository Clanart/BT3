## Title
Single depleted-bandwidth app in a batched `GetRequestsWithProof` submission blocks delivery of all other (valid, proof-verified) GET responses in the same batch — (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
Hyperbridge's `handle_get_requests` processes a batch of unrelated apps' `GetRequest`s together, verifying membership/state proofs for the whole batch and then metering each request against `pallet-bandwidth`'s per-app allowance in a loop. Because the bandwidth check for request *i* uses `?` to propagate any `GateError` out of the enclosing dispatchable, one app's exhausted bandwidth allowance aborts the entire extrinsic — discarding the proof-verification work and blocking delivery of every other (fully valid, unrelated) response bundled in that same batch. This mirrors the Notional rebalance bug: one failing "leg" of a multi-leg batch DOSes the whole batch, even though the other legs are individually valid and ready to settle.

### Finding Description
`handle_get_requests` in `modules/pallets/state-coprocessor/src/impls.rs` accepts a `GetRequestsWithProof { requests: Vec<GetRequest>, source, response, address }` payload carrying multiple GET requests from potentially different apps/destinations, verified together against one source-membership proof and one destination state proof.

After both proofs verify, the function loops over every request and meters bandwidth per request: [1](#0-0) 

The `try_consume` call for request *i* can fail with `GateError::Insufficient`/`GateError::NoAllowance` if that request's specific `(source, app)` bandwidth subscription is drained or absent, per the gate logic: [2](#0-1) 

Because the error is propagated with `?` (`.map_err(|err| Error::Custom(...))?`), the failure aborts the entire `handle_get_requests` call. In FRAME, a dispatchable that returns `Err` has all of its storage mutations (including the proof-verification bookkeeping and any bandwidth already deducted for earlier, unrelated requests in the same loop) rolled back atomically. None of the batch's responses — including those belonging to apps with ample bandwidth and whose proofs already verified — get inserted into the MMR or dispatched via `dispatch_get_response`: [3](#0-2) 

Relayers are documented/designed to batch multiple apps' GET responses together for gas efficiency (destined for the same source/height), e.g. the messaging relayer batches all GetResponse candidates for a given state-machine height: [4](#0-3) 

This means bundling unrelated apps into one submission is *normal, expected relayer behavior*, not an attacker-controlled anomaly the protocol defends against. An unprivileged actor can dispatch a cheap `GetRequest` from an app/chain pair that has no (or a nearly-exhausted) bandwidth subscription — a subscription state fully under the actor's own control, since anyone can dispatch requests, and bandwidth subscriptions are keyed per `(source chain, app)` per the bandwidth gate design: [5](#0-4) 

If a relayer bundles this poisoned request together with an unrelated, financially meaningful response — for example, an IntentGateway `cancelOrder` GET query whose response would trigger `withdraw()` and refund escrowed user funds — the entire batch fails and the escrow refund is not processed in that attempt, even though its own proof was valid.

This directly contrasts with the EVM-side `EvmHost.dispatchIncoming`/`dispatchTimeOut`, which deliberately isolate each per-item external callback with a low-level `.call()` and swallow individual failures without reverting the whole handler call — exactly the resilience pattern the Notional report recommends, and exactly what is missing from the Substrate-side batched GET-response bandwidth metering: [6](#0-5) 

### Impact Explanation
A single unrelated app's bandwidth exhaustion, purely a function of that app's own (attacker-controllable) subscription state, can cause an entire batch of otherwise valid, proof-verified GET responses to fail atomically. Legitimate GET-response-driven state transitions — most notably IntentGateway escrow refunds gated on `onGetResponse` — can be repeatedly delayed/locked as long as the poisoning request keeps landing in the same batch as the victim's request, without any compromised relayer, prover, or admin being required.

### Likelihood Explanation
Likelihood is moderate: it depends on the relayer's batching heuristics naturally grouping the victim's request with an attacker's low/no-bandwidth request bound for the same state-machine height. Relayers are designed to batch for gas efficiency rather than to defensively isolate per-app failures, so this is a realistic (not purely theoretical) occurrence, especially as bandwidth becomes a widely adopted metering mechanism across many apps sharing destination chains/heights.

### Recommendation
Do not let one request's bandwidth-gate failure abort the whole batch. Either:
1. Skip/defer only the offending request (emit an event / leave it for retry) while still processing and dispatching the other requests' responses in the same batch, or
2. Perform bandwidth pre-checks for all requests before doing any proof verification/state mutation, and partition the batch into "processable" vs "deferred" sets rather than failing the entire call with `?`.

This mirrors the isolation pattern already used correctly in `EvmHost.dispatchIncoming`/`dispatchTimeOut`, which should be applied symmetrically to the Substrate-side batched GET-response/bandwidth-metering path.

### Proof of Concept
1. Attacker deploys/uses an app with no bandwidth subscription on `pallet-bandwidth` (or lets an existing one fully drain).
2. Attacker dispatches a cheap `GetRequest` from that app to any destination chain at the same height a victim (e.g., an `IntentGateway.cancelOrder` GET query) is also querying.
3. A relayer, batching by efficiency, bundles both requests into one `GetRequestsWithProof` and submits `handle_get_requests`.
4. Proofs for both requests verify successfully (lines 105–124 of `impls.rs`), but at line 146–151 the attacker's request fails `BandwidthGate::try_consume`, propagating `Err` via `?`.
5. The whole extrinsic reverts: no responses are inserted into the MMR, none are dispatched via `dispatch_get_response`, and the victim's valid, ready-to-settle `GetResponse` — which would have refunded escrowed tokens via IntentGateway's `onGetResponse` → `withdraw()` — is not delivered in that attempt, delaying the refund indefinitely as long as batching repeats this pattern.

```rust
impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
```

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.
```
