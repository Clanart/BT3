### Title
GitHub repository association can be silently overwritten via reused login+name, enabling remote hijack - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
The `[M-05]` report's broken invariant is: a privileged setter overwrites an already-set, security-relevant value (`assetAggregator`) keyed by a caller-supplied identifier, with no check that the identifier already resolves to a different, previously-trusted value. The Desktop analog is `RepositoriesStore._upsertGitHubRepository`, which looks up and overwrites a locally cached `GitHubRepository` record (including its `cloneURL`) using the composite key `[ownerID+name]`, where `ownerID` is itself derived from the GitHub **login string** rather than GitHub's immutable numeric repository/owner IDs. Because GitHub logins and repository names can be freed and re-registered by unrelated third parties, an attacker who acquires a previously-used `login/name` pair can have their own repository silently merged into the record Desktop already trusts for the user's real repository, and Desktop will automatically rewrite the user's local `origin` remote to point at the attacker's clone URL.

### Finding Description
Local GitHub repository metadata is cached keyed by `[ownerID+name]`: [1](#0-0) 

`ownerID` comes from `putOwner`, which is keyed by `endpoint+login` (a mutable, reusable string), not GitHub's numeric owner id: [2](#0-1) 

When Desktop refreshes GitHub repository info, `_upsertGitHubRepository` looks up an existing DB record purely by this `[ownerID+name]` key and, if found, **overwrites** `cloneURL`, `htmlURL`, `permissions`, and `parentID` with whatever the API currently returns for that login/name — there is no comparison against GitHub's stable numeric repository id to confirm it's still the same underlying repository: [3](#0-2) 

This cached record is refreshed opportunistically via `repositoryWithRefreshedGitHubRepository`, which re-resolves the local git remote to an owner/name pair, fetches that repo from the API (`api.fetchRepository(owner, name)` — a GitHub REST call by login/name, not by ID), and then both rewrites the user's local git remote and upserts the (possibly different) API repository into the existing cache entry: [4](#0-3) [5](#0-4) 

The remote-URL auto-update logic (`updateRemoteUrl`) only checks that the protocol hasn't changed and that the *previous* clone URL still matches the current remote — it never verifies that the "new" API repository is actually the same underlying GitHub object (e.g., via a stable numeric id): [6](#0-5) 

### Impact Explanation
If the original owner of `login/name` renames or deletes their GitHub account (freeing the login) and an attacker re-registers that exact `login` and creates a repository with the same `name`, the next background/periodic refresh of the local repository (`repositoryWithRefreshedGitHubRepository`) will:
1. Resolve `owner`/`name` from the (still old) local git remote URL,
2. Fetch the **attacker's** repository object from the GitHub API for that owner/name,
3. Call `updateRemoteUrl`, which will pass its guard checks (protocol unchanged, previous cloneURL still matches the stored/trusted value, new URL differs) and silently rewrite the user's `origin` remote to the attacker's clone URL via `gitStore.setRemoteURL`,
4. Call `upsertGitHubRepository`, which matches the existing DB row by `[ownerID+name]` and overwrites its `cloneURL`/`htmlURL`/`permissions` in place, permanently rebinding the trusted local repository entry to the attacker's remote.

The result is silent corruption of what the user pushes/fetches: subsequent `git push`/`git fetch` operations, PR checkout flows, and "Open in Desktop" branch resolution all use the now-hijacked remote/GitHubRepository association without any user-visible warning, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires only unprivileged, off-host actions available to any GitHub user: renaming/abandoning an account frees a login for reuse, and repository names are not globally reserved once an account is renamed away. No local access, malware, or leaked credentials are needed — the attacker only needs to observe (e.g., via a public fork/clone or a rename notice) that a `login/name` pair used by a Desktop-tracked repository has become available, and race to claim it before the victim's next background refresh. GitHub Desktop's periodic repository refresh (triggered on repository selection, app foreground, etc.) makes exploitation practical without any unusual user action.

### Recommendation
Do not treat `owner.login + repo.name` as a stable identity key for cached `GitHubRepository` records or as sufficient justification to auto-update the user's git remote. Instead:
- Persist and key repositories/owners by GitHub's immutable numeric `id` fields (repository id, owner id) in `IDatabaseGitHubRepository`/`IDatabaseOwner`, and use `[ownerID+name]` purely as a secondary lookup/migration aid, not as the sole match criterion for overwriting `cloneURL`/`htmlURL`/`permissions`.
- In `updateRemoteUrl`, refuse to auto-rewrite the remote if the fetched API repository's numeric id differs from the previously cached repository's numeric id, even if login/name still match.
- In `_upsertGitHubRepository`, when an `existingRepo` is found by `[ownerID+name]` but its numeric repository id (once persisted) differs from the fetched API object's id, treat it as a new repository (or prompt the user) instead of silently overwriting the record.

### Proof of Concept
1. User A owns `github.com/A/widget`; Desktop tracks it locally, with the `gitHubRepositories` table row keyed by `[ownerID(A)+"widget"]` and `cloneURL = https://github.com/A/widget`.
2. User A renames their GitHub account away from `A` (login `A` becomes available).
3. Attacker registers GitHub account with login `A`, creates repository `A/widget`.
4. On the next call to `repositoryWithRefreshedGitHubRepository` for the user's local repo (app-store.ts:4874), `matchGitHubRepository` resolves owner=`A`, name=`widget` from the still-unchanged local remote URL, and `api.fetchRepository('A','widget')` returns the **attacker's** repository object.
5. `updateRemoteUrl` (update-remote-url.ts:7-45) sees `remoteUrlUnchanged = true` (stored `gitHubRepository.cloneURL` still equals the local remote) and `urlsMatch = false` (attacker's clone_url differs only if attacker changed default branch/clone_url format — in the common case where the attacker keeps the same owner/name the URLs are actually string-identical, so no even change is needed to redirect metadata) → the DB record and/or remote get updated to the attacker's repository data via `repoStore.upsertGitHubRepository(endpoint, apiRepo)` (app-store.ts:4909), silently rebinding the user's local repository to the attacker-controlled remote for future pushes/PR flows.

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }

    if (existingRepo !== undefined) {
      // If nothing has changed since the last time we persisted the API info
      // we can skip writing to the database and (more importantly) avoid
      // telling store consumers that the repo store has changed.
      if (shallowEquals(existingRepo, updatedGitHubRepo)) {
        return this.toGitHubRepository(existingRepo, owner, parent)
      }
    }

    const id = await this.db.gitHubRepositories.put(updatedGitHubRepo)
    this.emitUpdatedRepositories()
    return this.toGitHubRepository({ ...updatedGitHubRepo, id }, owner, parent)
  }

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
