### Title
Direct token transfer to `MasterMagpie` inflates `_calLpSupply()` and permanently dilutes/freezes staker reward emissions - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.updatePool()` computes the per-second MGP emission for a staking-token pool by dividing `mgpReward` by a "supply" value obtained from `_calLpSupply(_stakingToken)`. For any ordinary staking token (i.e. not `vlmgp`/`mWomSV`), this helper returns the raw ERC20 balance of the pool contract itself, `IERC20(_stakingToken).balanceOf(address(this))`, rather than the sum of `userInfo[...].amount` actually deposited through `deposit()`/`depositFor()`. This is the exact same bug class as the referenced LPFarming.sol finding: using `balanceOf(address(this))` as the pool's tracked supply.

### Finding Description
`_calLpSupply` falls back to `balanceOf` for any generic staking token: [1](#0-0) 

This value is used directly as the denominator when accruing rewards per share in `updatePool`: [2](#0-1) 

Any unprivileged wallet can call `IERC20(stakingToken).transfer(address(masterMagpie), amount)` directly (a plain ERC20 transfer, not `deposit`/`depositFor`), which increases the balance MasterMagpie holds without incrementing any `user.amount` in `userInfo`. Because `lpSupply` in `updatePool` is inflated by this phantom balance while `mgpReward` (numerator, based on `mgpPerSec * pool.allocPoint / totalAllocPoint`) is unaffected, `accMGPPerShare` accrues more slowly than it should for the true depositors of that pool. Since `mgpPerSec` is a fixed emission schedule that continues to run over time, the portion of the corresponding MGP allocation that is "lost" to the inflated denominator is never credited to any user's `rewardDebt`/`accMGPPerShare` accounting and cannot subsequently be claimed by anyone — it is permanently under-distributed for as long as the phantom balance remains in the contract (which is indefinitely, since nothing ever removes tokens that were sent via a bare `transfer`).

### Impact Explanation
This causes a permanent, non-recoverable loss of pool reward accrual for legitimate stakers of the affected `_stakingToken` pool in `MasterMagpie`. The intended MGP emission for that pool's `allocPoint` share is diluted forever whenever anyone (attacker, or an honest user by mistake) sends the staking token directly to the `MasterMagpie` contract address instead of calling `deposit`. This matches "theft or permanent freezing of unclaimed yield" for the affected stakers, since the diluted rewardPerShare growth can never be corrected retroactively.

### Likelihood Explanation
The trigger is trivial and requires no special privileges: any wallet holding the pool's staking token (e.g., an LP/receipt token accepted by `MasterMagpie`) can call `transfer` to the `MasterMagpie` contract. No admin or governance action is needed, and the effect is immediate and permanent once the next `updatePool` call occurs (which happens automatically on every deposit/withdraw/harvest for that pool).

### Recommendation
Track total staked amount internally per pool (e.g., a `totalStaked` field on `PoolInfo`, incremented/decremented in `_deposit`/`_withdraw`) and use that value in `_calLpSupply`/`updatePool` instead of relying on `IERC20(_stakingToken).balanceOf(address(this))`.

### Proof of Concept
1. Pool for `stakingToken` is registered in `MasterMagpie` with some `allocPoint`.
2. Attacker (unprivileged EOA) calls `stakingToken.transfer(masterMagpie, X)` directly, bypassing `deposit()`.
3. Alice calls `MasterMagpie.deposit(stakingToken, Y)`, staking legitimately.
4. Time passes; `updatePool(stakingToken)` runs, computing `lpSupply = _calLpSupply(stakingToken) = X + Y` (attacker's phantom balance included), so `accMGPPerShare` grows slower than the `mgpPerSec` emission schedule intends for `Y` actual staked.
5. Alice's `earned`/harvestable MGP reward under `accMGPPerShare * user.amount / 1e12 - user.rewardDebt` is permanently lower than the amount the emission schedule allocated to the pool; the "missing" MGP corresponding to the `X` phantom balance is never credited to any `userInfo` entry and can never be claimed by anyone, matching the root cause described in the referenced LPFarming.sol finding.
```text
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }    
```

**File:** rewards/MasterMagpie.sol (L659-667)
```text
    function _calLpSupply(address _stakingToken) internal view returns (uint256) {
        if (_stakingToken == address(vlmgp)) {
            return IERC20(address(vlmgp)).totalSupply();
        }
        if (_stakingToken == address(mWomSV)) {
            return IERC20(address(mWomSV)).totalSupply();
        }
        return IERC20(_stakingToken).balanceOf(address(this));
    }
```
