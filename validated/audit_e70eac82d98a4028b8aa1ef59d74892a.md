## Finding

The upb JSON decoder's quoted-number path for `double`/`float` fields calls the locale/NUL-dependent C library function `strtod()` directly on a **non-NUL-terminated string view** taken from the middle of the caller-supplied JSON buffer, instead of copying it into a bounded, NUL-terminated scratch buffer the way the sibling numeric-literal path does.

### Title
Unterminated-buffer over-read in ProtoJSON quoted double/float parsing via `strtod()` - (File: `upb/json/decode.c`)

### Summary
`jsondec_double()` parses a JSON string like `"1.5"` for a `double`/`float` field by taking the `upb_StringView` returned from `jsondec_string()` and passing `str.data` directly to `strtod()`, relying on `strtod` to stop at `str.data + str.size`. `strtod()` has no concept of the view's `size`; it scans from `str.data` until it hits a byte it cannot classify as part of a number or a C-string NUL terminator. Because `str.data` is a raw pointer into the caller's original JSON buffer (not a copy, not NUL-terminated at `str.size`), if the numeric-looking bytes continue past the closing quote (e.g., adjacent JSON content that happens to look numeric, or if the quoted number sits at the very tail of the buffer with no guaranteed terminator), `strtod` reads beyond the intended token boundary — and potentially beyond the allocated buffer if it is the last field in an unterminated, explicitly-sized `buf/size` input. [1](#0-0) 

### Finding Description
`upb_JsonDecode` is invoked with an explicit `(buf, size)` pair, so the input is an arbitrary-length byte buffer with no NUL-termination guarantee at `buf+size` — this is the attacker-controlled value/boundary. In the numeric-literal path, `jsondec_number()` explicitly copies the token into a bounded local buffer `char nullz[64]` and NUL-terminates it before calling `strtod`, precisely to avoid feeding `strtod` an unterminated pointer: [2](#0-1) 

However, the quoted-number path in `jsondec_double()` (used for JSON string-encoded doubles/floats, e.g. `{"f": "1.5"}`) skips that safety copy and calls `strtod(str.data, &end)` directly on the raw `upb_StringView` produced by `jsondec_string()`, only validating *after the fact* that `end == str.data + str.size`: [3](#0-2) 

This is the same class of failed invariant as CVE-2019-11046: a numeric-string consumer assumes it can safely scan characters using a C-string-oriented function (there `isdigit`-driven locale character classification with no bound; here `strtod` with no bound) over memory that is not guaranteed to be delimited the way the function expects, so the scan can run past the intended/allocated extent before the post-hoc check catches it. The identical vulnerable pattern is duplicated in three build artifacts of the same upb source: the canonical `upb/json/decode.c`, and the vendored single-file amalgamations `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`. [4](#0-3) [5](#0-4) 

### Impact Explanation
`strtod` reading past `str.data + str.size` before the mismatch is detected constitutes an out-of-bounds read relative to the intended token; in the worst case (the quoted number is the last bytes of the caller's buffer, or immediately abuts non-NUL-terminated memory) this can read adjacent heap/stack memory, matching the CVE's "read beyond allocated space" / potential disclosure characterization. The over-read is bounded by wherever `strtod` first finds a non-numeric-or-non-terminator byte, so severity is disclosure-class, not corruption, consistent with the reference CVE's Medium rating (`C:L`, no `I`/`A` impact).

### Likelihood Explanation
The trigger is fully attacker-reachable through the public ProtoJSON parse API: any client sending `{"someDoubleOrFloatField": "<attacker string>"}` to `upb_JsonDecode` (and transitively through the PHP/Ruby JSON parse bindings that embed the same code) exercises this path with no privileged access, hostile schema, or native-API misuse required — only a trusted schema with a `double`/`float` field and a bounded, ordinary JSON payload with the number encoded as a JSON string rather than a JSON literal.

### Recommendation
Mirror the fix already applied in `jsondec_number()`: copy the `upb_StringView` content for the quoted-number path into a bounded, explicitly NUL-terminated scratch buffer (rejecting overly long values, as `jsondec_number` does with its 64-byte `nullz` buffer and "excessively long number" check) before calling `strtod`, rather than passing `str.data` directly. Apply the same fix to all three occurrences (`upb/json/decode.c`, `php-upb.c`, `ruby-upb.c`) since they are independently generated copies of the same logic.

### Proof of Concept
Conceptually: allocate a heap buffer of exactly `size` bytes containing `{"optionalDouble":"1"` with **no trailing byte reserved for NUL** (i.e., a heap allocation sized exactly to the JSON content, as would occur if a caller passes a `std::string`'s data/size or a network-received buffer of exact length without extra padding), and call `upb_JsonDecode(buf, size, msg, ...)`. Inside `jsondec_double()`'s `JD_STRING` branch, `str.data` points at `'1'` with `str.size == 1`, and `strtod(str.data, &end)` will continue scanning into memory immediately following the allocation (since there is no `"` closing-quote byte or NUL guaranteed to be adjacent in the exact-sized buffer) until it encounters a byte that does not extend a valid `strtod` grammar token — reading past the buffer's intended/allocated extent. A full runtime reproduction with ASan to observe the heap-buffer-overflow read was not executed in this session; the reachability and missing-bound-copy defect are established from direct source inspection of `jsondec_double` versus the bounded-copy pattern in `jsondec_number`. static double jsondec_number(jsondec* d) {
```c
  const char* start = d->ptr;

  UPB_ASSERT(jsondec_rawpeek(d) == JD_NUMBER);

  /* Skip over the syntax of a number, as specified by JSON. */
  if (*d->ptr == '-') d->ptr++;

  if (jsondec_tryparsech(d, '0')) {
    if (jsondec_tryskipdigits(d)) {
      jsondec_err(d, "number cannot have leading zero");
    }
  } else {
    jsondec_skipdigits(d);
  }

  if (d->ptr == d->end) goto parse;
  if (jsondec_tryparsech(d, '.')) {
    jsondec_skipdigits(d);
  }
  if (d->ptr == d->end) goto parse;

  if (*d->ptr == 'e' || *d->ptr == 'E') {
    d->ptr++;
    if (d->ptr == d->end) {
      jsondec_err(d, "Unexpected EOF in number");
    }
    if (*d->ptr == '+' || *d->ptr == '-') {
      d->ptr++;
    }
    jsondec_skipdigits(d);
  }

parse:
  /* Having verified the syntax of a JSON number, use strtod() to parse
   * (strtod() accepts a superset of JSON syntax). */
  errno = 0;
  {
    // Copy the number into a null-terminated scratch buffer since strtod
    // expects a null-terminated string.
    char nullz[64];
    ptrdiff_t len = d->ptr - start;
    if (len > (ptrdiff_t)(sizeof(nullz) - 1)) {
      jsondec_err(d, "excessively long number");
    }
    memcpy(nullz, start, len);
    nullz[len] = '\0';

    char* end;
    double val = strtod(nullz, &end);
    UPB_ASSERT(end - nullz == len);
```

```c
static upb_MessageValue jsondec_double(jsondec* d, const upb_FieldDef* f) {
  upb_StringView str;
  upb_MessageValue val;

  switch (jsondec_peek(d)) {
    case JD_NUMBER:
      val.double_val = jsondec_number(d);
      break;
    case JD_STRING:
      str = jsondec_string(d);
      if (str.size == 0) {
        jsondec_checkempty(d, str, f);
        val.double_val = 0.0;
      } else if (jsondec_streql(str, "NaN")) {
        val.double_val = NAN;
      } else if (jsondec_streql(str, "Infinity")) {
        val.double_val = INFINITY;
      } else if (jsondec_streql(str, "-Infinity")) {
        val.double_val = -INFINITY;
      } else {
        char* end;
        val.double_val = strtod(str.data, &end);
        if (end != str.data + str.size) {
          d->result = kUpb_JsonDecodeResult_Error;
          upb_Status_SetErrorFormat(
              d->status,
              "Non-number characters in quoted number (field: %s). "
              "This will be an error in a future version.",
              upb_FieldDef_FullName(f));
        }
      }
      break;
```
