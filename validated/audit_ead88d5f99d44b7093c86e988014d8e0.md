### Title
Duplicate participant registration causes `assert!` panic and aborts the DKG node - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`Decryption::register` (and its wrapper `Encryption::register`) contains `assert!(!self.enc_keys.contains_key(&participant))`, which panics the entire process if a participant's encryption-key registration is submitted twice. A remote, unprivileged party participating in the DKG (or relaying on behalf of a claimed participant index) can trigger a second registration for an already-registered `Participant`, causing an abort — a direct analog of CVE-2020-29562's "untrusted input reaches an assertion and aborts the program" DoS class.

### Finding Description
`EncryptedMessage`/`EncryptionKeyMessage` are deserialized from peer-supplied bytes via `EncryptedMessage::read` / `EncryptionKeyMessage::read` (encryption.rs:171-177, 57-59), and then processed per `Participant`. `Decryption::register` inserts into `enc_keys` under an asserted-unique key:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

(encryption.rs:356-360). There is no graceful `Err` path — duplicate registration is enforced by `assert!`, not by returning an error. Two related unguarded indexing panics also exist on attacker-influenced lookups:

- `self.decryption.enc_keys[&participant]` in `Encryption::encrypt` (encryption.rs:466) — panics with `HashMap` index-miss if a message references an unregistered participant.
- `self.enc_keys[&decryptor]` in `decrypt_with_proof` (encryption.rs:388) — same index-miss panic during blame/decryption handling of a proof referencing an absent decryptor.

Unlike the surrounding `read`/`verify` functions which uniformly return `io::Result`/`DecryptionError`, these paths abort the process on adversary-controlled conditions.

### Impact Explanation
Any node running the PedPoP DKG that receives two registration messages carrying the same `Participant` index — trivially producible by a single malicious DKG participant, or by message replay — hits the `assert!` and aborts. Since this runs inside the key-generation/signing processor, aborting mid-DKG denies service to the whole multisig session and can repeatedly crash the node on restart if the offending messages are re-delivered. This matches the CVE's profile: a library routine reaches a hard assertion on adversary-controlled input and kills the host program (CVSS-class Medium availability impact, no integrity loss).

### Likelihood Explanation
Triggering requires only that an attacker submit a DKG encryption-key registration twice (or reference an unregistered participant index in an encrypt/decrypt flow). No threshold collusion, leaked keys, or validator privileges are needed — the input is a plain DKG message field (`Participant` index plus `enc_key` point) read from the wire. The panic is deterministic, not probabilistic.

### Recommendation
Replace the `assert!` in `Decryption::register` with a returned error (e.g., extend `DecryptionError` or a new `RegistrationError`) so callers can reject/blame the duplicate instead of aborting. Similarly, replace `enc_keys[&participant]` / `enc_keys[&decryptor]` indexing with `.get().ok_or(...)` lookups so references to unknown participants return errors rather than panicking.

### Proof of Concept
```rust
// crypto/dkg/pedpop/src/encryption.rs — conceptual PoC
// C = Ristretto (or any Ciphersuite)
let context = [0u8; 32];
let mut decryption = Decryption::<Ristretto>::new(context);

// Attacker-controlled bytes deserialize to an EncryptionKeyMessage
// for participant index 1.
let msg1 = EncryptionKeyMessage::<Ristretto, M>::read(&mut bytes_for_p1, params)?;
decryption.register(Participant::new(1).unwrap(), msg1); // ok

// A second message (replayed or re-sent by the attacker) with the
// same participant index reaches the assert! and aborts the process.
let msg2 = EncryptionKeyMessage::<Ristretto, M>::read(&mut bytes_for_p1_again, params)?;
decryption.register(Participant::new(1).unwrap(), msg2); // panic!
```

The panic is at `encryption.rs:356-359`. Related reachable panics: `enc_keys[&participant]` at `encryption.rs:466` and `enc_keys[&decryptor]` at `encryption.rs:388`, both index-miss aborts on attacker-supplied participant indexes.
