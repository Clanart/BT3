### Title
Unchecked ERC20 return value in ERC20→CW20 pointer contract can report failed transfers as successful - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The CosmWasm CW20-over-ERC20 pointer contract's `transfer`/`transfer_from` handlers dispatch `EvmMsg::DelegateCallEvm` to the wrapped ERC20 contract but never inspect the ABI-encoded boolean return value of the ERC20 `transfer`/`transferFrom` call. If the underlying ERC20 token does not revert on failure but instead returns `false` (non-standard-but-common ERC20 behavior, e.g. tokens modeled like USDT), the delegatecall itself completes without an EVM revert, so the pointer contract treats the operation as fully successful even though no balance actually moved.

### Finding Description
`transfer()` and `transfer_from()` in [1](#0-0)  build an ABI payload for the wrapped ERC20's `transfer`/`transferFrom` and wrap it in `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }`, then immediately construct a `Response` with success attributes — without ever decoding or checking the boolean returned by the ERC20 call.

That `DelegateCallEvm` message is routed to `HandleInternalEVMDelegateCall` in [2](#0-1) , which calls `k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)`. This only reports an `error` back to the CosmWasm layer if the EVM execution reverts; it does not decode/validate the ABI return payload of the callee. Consequently, if the wrapped ERC20's `transfer`/`transferFrom` function returns `false` on failure (rather than reverting, as with non-standard ERC20 tokens such as USDT), `CallEVM` returns no error, `HandleInternalEVMDelegateCall` succeeds, and the CosmWasm submessage in `transfer`/`transfer_from` is considered successful. The contract then emits success attributes (`from`, `to`, `amount`) and, in `execute_send`/`execute_send_from` in [3](#0-2)  and [4](#0-3) , proceeds to fire a `Cw20ReceiveMsg` to the recipient contract as if tokens were actually delivered.

This is directly analogous to the reported bug class: an ERC20 call's return value (`bool success`) is not checked, allowing token transfers that silently fail to be treated as successful.

### Impact Explanation
A CosmWasm caller (any unprivileged user invoking `execute_transfer`, `execute_transfer_from`, `execute_send`, or `execute_send_from` on a deployed ERC20→CW20 pointer instance) can experience or induce fund loss: if the wrapped ERC20 returns `false` instead of reverting (e.g., insufficient balance/allowance edge cases in non-standard tokens), the pointer contract reports the transfer as completed and downstream logic (e.g. `Cw20ReceiveMsg` dispatch, application-level accounting relying on the pointer's success/attributes) proceeds under the false assumption that the balance move occurred, resulting in accounting desync and potential loss of funds for a party relying on the reported outcome.

### Likelihood Explanation
Likelihood depends on the specific wrapped ERC20 token's compliance with the ERC20 standard. Since pointer contracts (via `MsgRegisterPointer`) can be created for arbitrary ERC20 contracts, including deliberately or accidentally non-reverting tokens, an attacker or a naturally non-compliant token deployment can trigger this condition without any special privilege.

### Recommendation
Decode the ABI return value of the delegatecalled ERC20 `transfer`/`transferFrom` function in the Go handler (`HandleInternalEVMDelegateCall`/`CallEVM`) or in the CosmWasm contract querier layer, and propagate an error/`ContractError` when the returned boolean is `false`, mirroring OpenZeppelin's `SafeERC20` pattern used elsewhere in the codebase (e.g. [5](#0-4) ).

### Proof of Concept
1. Deploy a non-standard ERC20 contract whose `transfer`/`transferFrom` returns `false` on failure instead of reverting (analogous to USDT-style tokens).
2. Register an ERC20→CW20 pointer for that token via `MsgRegisterPointer`.
3. Call `transfer_from` on the pointer with an amount exceeding the owner's balance/allowance so the underlying ERC20 call returns `false`.
4. Observe that `execute_transfer_from` in [6](#0-5)  returns a successful `Response` with `action=transfer_from` attributes, while the ERC20 balances remain unchanged — the pointer falsely reports a successful transfer.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
}
