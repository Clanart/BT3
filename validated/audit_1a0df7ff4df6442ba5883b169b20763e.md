### Title
Reachable panic (process crash) via unregistered/missing encryption key during PedPoP decryption/blame handling - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The DKG decryption/blame path in `pedpop` indexes into `self.enc_keys` with an attacker-influenced `Participant` index instead of returning an error. If a message is processed for a participant whose encryption key was never registered (or a blame/decryption flow references a non-registered participant), `self.enc_keys[&decryptor]` panics, crashing the process — analogous to CVE-2022-21297's "repeatable crash / complete DOS" availability impact.

### Finding Description
`Decryption::decrypt_with_proof` performs a DLEq verification against `self.enc_keys[&decryptor]`:

```rust
// crypto/dkg/pedpop/src/encryption.rs
pub(crate) fn decrypt_with_proof<E: Encryptable>(
  &self,
  from: Participant,
  decryptor: Participant,
  mut msg: EncryptedMessage<C, E>,
  proof: Option<EncryptionKeyProof<C>>,
) -> Result<Zeroizing<E>, DecryptionError> {
  ...
  proof.dleq.verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // panics if `decryptor` never registered
  )
``` [1](#0-0) 

`HashMap`'s indexing operator (`map[&key]`) panics on a missing key. There is no earlier check that `decryptor` is present in `enc_keys` — `enc_keys` is only populated by `Decryption::register`, which itself panics on re-registration rather than handling the case gracefully:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
``` [2](#0-1) 

The same unchecked-index pattern exists in `Encryption::encrypt`, which does `self.decryption.enc_keys[&participant]` — a panic if `participant` is not in the map. [3](#0-2) 

The attacker-controlled surface is `EncryptedMessage::read` / `EncryptionKeyMessage::read` — both deserialize the point key and PoP from raw bytes supplied over the channel — and `EncryptionKeyProof::read`, all of which feed the decryption/blame path:

```rust
pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
  Ok(Self {
    key: C::read_G(reader)?,
    pop: SchnorrSignature::<C>::read(reader)?,
    msg: Zeroizing::new(E::read(reader, params)?),
  })
}
``` [4](#0-3) 

A party who submits a valid `EncryptedMessage`/`EncryptionKeyProof` but whose encryption key was never registered (or who is named as `decryptor`/`from` in a blame flow without registration) causes the indexing panic rather than a `DecryptionError`. Because DKG orchestration is handled by the caller, nothing in this crate guarantees `enc_keys` contains the referenced participant before the index occurs.

### Impact Explanation
Availability: a single crafted or mis-sequenced message deterministically crashes the process running the DKG (panic on `HashMap` index). Since `decrypt_with_proof` is invoked during the blame/accusation flow — precisely when a counterparty has already misbehaved — this is repeatedly triggerable, matching the "hang or frequently repeatable crash (complete DOS)" impact class of CVE-2022-21297. A crashed participant aborts key generation (or, in threshold protocols built on it, stalls signing for the set containing that participant).

### Likelihood Explanation
The crash requires the caller to route a decryption/blame request for a participant absent from `enc_keys`. In an adversarial DKG round, a peer can arrange this by refusing to broadcast (or having their registration rejected/dropped as faulty) while still being referenced in subsequent blame processing — an accusation against a non-registered participant is exactly the scenario `decrypt_with_proof` exists for. No valid proofs are needed to reach the panic for the indexing line itself (the `pop.verify` for `from` runs first, but the `enc_keys[&decryptor]` index targets `decryptor`, which is a distinct participant and need not correspond to a valid signature). Likelihood is moderate: it depends on integrator flow control, but the vulnerable pattern is unconditional once reached.

### Recommendation
Replace the indexing with a fallible lookup that returns a `DecryptionError` (or a dedicated `UnregisteredParticipant` error):

```rust
let decryptor_key = self
  .enc_keys
  .get(&decryptor)
  .copied()
  .ok_or(DecryptionError::InvalidProof)?;
```

Apply the same fix to `Encryption::encrypt` (`enc_keys.get(&participant)`) and make `Decryption::register` return an error on duplicate registration instead of asserting. Additionally, surface validation that `from`/`decryptor` are within `1..=n` and present in the registered set before any cryptographic work.

### Proof of Concept
Conceptual (state machine level):

1. Instantiate `Decryption::<C>::new(context)`; register keys for participants 1..=t but **not** for participant `d`.
2. Construct an `EncryptedMessage` via `EncryptedMessage::read` from attacker bytes (any valid `key`, `pop` for `from`, ciphertext).
3. Call `decrypt_with_proof(from, d, msg, Some(proof))` where `proof` is any `EncryptionKeyProof` (e.g. produced by `EncryptionKeyProof::read`).
4. After `pop.verify` succeeds for `from`, evaluation reaches `self.enc_keys[&d]` → `thread panicked at 'no entry found for key'` → process aborts.

The panic is at `crypto/dkg/pedpop/src/encryption.rs` (`decrypt_with_proof`, `enc_keys[&decryptor]`) and is deterministic for any missing `decryptor`.

Caveat: exact reachability depends on the caller invoking `decrypt_with_proof`/`encrypt` for participants whose keys were never registered; within the in-scope crate itself, the unchecked-index panic is unconditional once such a call is made, and the crate documents that networking-level deduplication/ordering is the caller's responsibility — meaning nothing prevents an untrusted message stream from producing this state.
