### Title
Post-commit hook stdout can inject a decoy `[branch sha]` token that diverts `handle_commit_review_posttooluse` to review an unrelated real commit instead of the actual new commit — (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`_COMMIT_SHA_RE` extracts the "last" line-anchored `[branch sha]`-style bracket token from combined Bash stdout+stderr on the theory that "the real commit line is always last in git's own output." This assumption holds for pre-commit hooks (which run *before* git prints the summary line) but not for post-commit hooks, which run *after* git prints `[branch sha]` / the diffstat and whose output is captured in the same Bash tool response. A malicious post-commit hook committed into the repo can print a crafted decoy bracket token referencing an unrelated, but real, commit SHA, causing the review to be pinned to that commit instead of the actual new one.

### Finding Description
`handle_commit_review_posttooluse` computes `commit_succeeded` by requiring both a `_COMMIT_SHA_RE` match and a `_COMMIT_DIFFSTAT_PATTERNS` match anywhere in `bash_output` [1](#0-0) . It then extracts the SHA(s) to review via `all_shas = _COMMIT_SHA_RE.findall(bash_output); shas = [all_shas[-1]]`, explicitly picking the *last* match because "the real commit line is always last in git's own output — the earlier matches are either decoys or superseded commits" [2](#0-1) .

This "last-match-is-real" invariant assumes hook output (e.g. pre-commit/husky) only ever precedes git's own `[branch sha]` summary line, as stated in `_COMMIT_DIFFSTAT_PATTERNS`'s comment [3](#0-2) . That is true for pre-commit/lint-staged/husky pre-commit hooks, but `git commit` also invokes a `post-commit` hook *after* the commit object is created and *after* it has already printed the `[branch sha]` summary and diffstat lines. A `post-commit` (or husky `post-commit`) script — already present in repository content the attacker contributed, or shipped by a compromised dependency's install script that wires up hooks — can print an attacker-chosen line such as `[decoy 1234567]` to stdout. Because that line is emitted after the genuine summary in the same captured stream, `findall(...)[-1]` returns the decoy hex string instead of the real new commit's SHA.

The resolved SHA is only sanity-checked by running `git show -p <sha> --` and checking `returncode == 0` [4](#0-3) ; there is no check that the SHA is reachable from the pre-commit HEAD, is an ancestor/descendant relationship consistent with "just created," or matches `HEAD` after the commit. Any valid, resolvable 7–40 hex-char object in the repo (e.g. an old, already-reviewed, entirely benign commit whose SHA the attacker can predict or embed literally) passes this check and gets diffed/shown instead of the actual new commit.

The `_COMMIT_DIFFSTAT_PATTERNS` gate does not prevent this because the diffstat lines legitimately exist in `bash_output` from the *real* successful commit that just happened — `commit_succeeded` correctly evaluates to `True`; the flaw is purely in which SHA within that same, genuinely-successful output gets selected for review.

### Impact Explanation
This diverts the immediate post-commit LLM security review away from the actual newly-created (potentially malicious) commit and onto attacker-chosen, unrelated repository content, matching the "review pinned to wrong/attacker-influenced commit" impact described. The genuinely vulnerable diff added by the real commit is not reviewed via this code path (`skip_reason` metrics would show a "successful" review, masking the miss). This is a review-integrity / trust-boundary bypass of the plugin's commit-review guarantee, not a sandbox escape — the Stop-hook (`git diff baseline_sha…HEAD`) and push-sweep reviewers are separate mechanisms that use unrelated SHA-derivation logic and may still catch the change later in the session, which reduces but does not eliminate the practical severity of the miss for that specific commit-review invocation.

### Likelihood Explanation
Requires the attacker to have gotten a `post-commit` (or husky `post-commit`) hook script into the repository beforehand (e.g., via a merged PR, a `package.json`/`.husky` config change, or a compromised dependency's postinstall that wires hooks) — this is "ordinary repository content" reachable without any elevated privilege, consistent with the rules' scope. Once present, every subsequent `git commit` run through the Bash tool in that repo deterministically triggers the misattribution, making it fully repeatable, not a one-off race.

### Recommendation
Do not rely solely on "last bracket match = real commit." Strengthen `_COMMIT_SHA_RE` selection by:
1. Anchoring/molecule-matching only the segment of `bash_output` between the `git commit` invocation and the first diffstat line (mirroring `_push_section`'s approach for push output), so hook output emitted after the diffstat is excluded from SHA candidates.
2. Cross-checking the selected SHA against `git rev-parse HEAD` (and/or `git log -g -1 --format=%H`) captured immediately after the commit, requiring the extracted SHA to be a prefix of the actual current HEAD (or a reflog `HEAD@{0..N}` entry) rather than merely `git show`-able.
3. Applying the same reflog-based corroboration already used in `_resolve_amend_pre_sha` (prefix-matching `expected_post_sha` against `HEAD@{0}`) to the primary (non-amend) SHA-extraction path.

### Proof of Concept
Unit test in the hook's test suite (fuzz/invariant style):
1. Create a temp git repo; install a `post-commit` hook script that prints `\n[decoy 1234567]\n` to stdout, where `1234567` is the abbreviated SHA of an earlier, unrelated commit already in the repo.
2. Make a real commit with a small vulnerable diff (e.g., introduces a hardcoded secret) via `subprocess.run(["git","commit","-m","legit"])`, capturing combined stdout/stderr exactly as the Bash tool would.
3. Call `handle_commit_review_posttooluse` (or directly exercise the `_COMMIT_SHA_RE.findall` + selection logic) with that captured output.
4. Assert (expected to fail today): the SHA selected for review equals `git rev-parse HEAD` (the just-created commit), not the decoy commit's SHA.
5. Additional invariant fuzz: generate random `bash_output` strings combining a genuine `[branch <real_head_sha>] subject\n N files changed` block followed by random attacker-controlled `[decoy <hex>]` lines (using SHAs of pre-existing, unrelated commits) and assert the extracted SHA always resolves to a commit that is `git cat-file -e`-valid **and** equals the HEAD created by this invocation — the current implementation violates this on any post-commit-hook-appended decoy line.
