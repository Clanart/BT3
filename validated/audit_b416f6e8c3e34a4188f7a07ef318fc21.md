### Title
Unvalidated PR fork `clone_url` from GitHub API passed to `git remote add` enables argument/protocol injection - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user checks out a pull request from a fork, `_findPullRequestBranch` takes `headCloneUrl` — a string sourced directly from the GitHub API's `pull_request.head.repo.clone_url` (or, in the deep-link flow, `pullRequest.head.repo.clone_url` from `openPullRequestFromUrl`) — and passes it unvalidated to `addRemote`, which shells out to `git remote add <name> <url>`. Unlike `clone.ts`, which validates destination paths (`isClonePathSensitive`) and sanitizes derived names (`sanitizeCloneName`), and unlike `remote-parsing.ts`, which restricts recognized remote URL shapes to `https`/`ssh` via strict regexes for UI purposes, there is no equivalent allow-listing of the URL scheme before it reaches `addRemote`/`git remote add`.

### Finding Description
`_findPullRequestBranch` (`app-store.ts:8633-8660`) does:
```
remote = await addRemote(repository, forkRemoteName, headCloneUrl)
```
`addRemote` (`app/src/lib/git/remote.ts:28-37`) runs:
```
await git(['remote', 'add', name, url], repository.path, 'addRemote')
```
Git supports non-`https`/`ssh` transport schemes for `remote add`/`fetch`, notably `ext::` (arbitrary shell command) and `file://` (local filesystem, subject to `protocol.file.allow`). `headCloneUrl` originates from `pullRequest.head.repo.clone_url`, an attacker-influenced field of a GitHub API object (an attacker who creates a PR from a fork, or a repository proxying/mirroring that data, controls this string in the general threat model described in the task). This value flows to `git remote add` without any scheme validation, and is later fetched via `_fetchRemote`.

While GitHub.com's actual API is expected to return well-formed `https://` clone URLs, the code path itself performs **no defensive validation** of the URL before using it as a git remote — it only checks whether an existing remote already matches it (`urlMatchesRemote`). This differs from the pattern seen elsewhere in the codebase, e.g. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:1-47`), which explicitly checks that the protocol of an API-supplied `clone_url` matches the existing remote's protocol before applying it, precisely because API-supplied URLs are not implicitly trusted values to feed into git remote operations.

### Impact Explanation
If an attacker can get their crafted `clone_url` value used in the checkout-PR path (e.g., via a compromised/malicious GitHub Enterprise API endpoint, a man-in-the-middle on the API request, or any code path that constructs `PullRequest`/`head.repo` objects from external/less-trusted data), a value like `ext::sh -c "...")` or `file:///etc` could be added as a git remote and subsequently fetched, potentially resulting in arbitrary command execution on the user's machine or disclosure/write of files outside the intended repository — squarely matching the "attacker controls a GitHub API object... resulting in code execution or file read/write outside the repo" impact class in this task's scope.

### Likelihood Explanation
Likelihood is constrained because `git`'s `ext::` handler is disabled by default in modern Git versions unless the caller passes `-c protocol.ext.allow=always` (Desktop does not set this explicitly for the PR-remote-add/fetch path I could confirm), and Desktop's own `envForRemoteOperation`/fetch code does not appear to explicitly allow-list dangerous protocols for this flow the way `updateSubmodulesAfterOperation` does for `protocol.file.allow`. This significantly reduces exploitability against a stock Git installation. I was unable to fully verify from the indexed code whether any global git config (e.g., a user's own `~/.gitconfig` enabling `protocol.ext.allow`) or another code path relaxes this protection for the PR-checkout flow specifically, which affects the practical likelihood.

### Recommendation
Validate `headCloneUrl` (and any other API-sourced clone URL used with `git remote add`/`fetch`, e.g., in `_checkoutPullRequest`, `openPullRequestFromUrl`, `_convertRepositoryToFork`) against the same allow-listed protocol/host shape enforced elsewhere (mirroring `parseRemote`'s `https`/`ssh` regexes in `app/src/lib/remote-parsing.ts:1-53`), rejecting anything that doesn't match before calling `addRemote`. Additionally, explicitly pass `-c protocol.ext.allow=never` (or omit any allow flag) and avoid ever enabling `protocol.file.allow=always` for externally-sourced clone URLs outside the deliberate, already-scoped submodule-update usage.

### Proof of Concept
1. Obtain or simulate a `PullRequest` object (e.g., via a malicious/compromised GitHub Enterprise endpoint, or by crafting the object in a code path that doesn't go through GitHub.com's PR API directly) where `head.repo.clone_url` is set to `ext::sh -c "touch /tmp/pwned"` instead of a normal `https://...` URL.
2. Trigger the "Checkout this PR" / "Open PR from Desktop" flow, which calls `dispatcher.checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch` (`app/src/lib/stores/app-store.ts:8613-8660`).
3. `addRemote(repository, forkRemoteName, headCloneUrl)` executes `git remote add <forkName> "ext::sh -c \"touch /tmp/pwned\""` (`app/src/lib/git/remote.ts:28-37`).
4. `_fetchRemote` is subsequently invoked on that same remote, causing git to invoke the `ext::` handler and execute the attacker-supplied command, assuming `protocol.ext.allow` is not restricted in the effective git configuration.

**Caveat:** I could not fully confirm from the indexed source whether Desktop's git invocation wrapper (`core.ts`/`environment.ts`) globally disables `protocol.ext.allow`/`protocol.file.allow` for all git invocations (which would mitigate this), so the actual exploitability depends on git/version defaults and any user-level git configuration. A Devin session with full repository access could verify this by inspecting `app/src/lib/git/environment.ts` and all `GIT_CONFIG_PARAMETERS`/`-c` flags applied globally to `git()` calls.
