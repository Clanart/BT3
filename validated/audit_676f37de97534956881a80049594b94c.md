### Title
Webhook shop-identity spoofing via HMAC verification that excludes the shop domain header - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` verifies inbound webhooks by computing an HMAC over the raw request body only, and exposes a separate, unauthenticated `shop_domain` helper that simply reads the `X-Shopify-Shop-Domain` header. Because the shop identity is never included in the signed payload, a valid `(body, HMAC)` pair generated for one shop can be replayed with a different `X-Shopify-Shop-Domain` header value and will still pass verification — letting an attacker attribute a legitimately-signed webhook body to an arbitrary victim shop. This is the same bug class as the `launchGroupCoin` report: the signature check omits a value (there, a nonce; here, the shop identity) that should scope/bind what the signature is allowed to authorize, so a single valid signature can be "replayed" under different, attacker-chosen context.

### Finding Description
`PayloadVerification#hmac_valid?` computes and compares an HMAC solely over `request.raw_post`: [1](#0-0) 

`WebhookVerification` uses this exact check as its `before_action`, and separately defines `shop_domain` by reading the `X-Shopify-Shop-Domain` header directly, with no cryptographic binding to the verified body: [2](#0-1) 

The gem's own documentation instructs app authors to build custom webhook controllers that trust this `shop_domain` value to dispatch shop-scoped jobs: [3](#0-2) 

Because the app's webhook secret (`ShopifyApp.configuration.secret`) is a single shared secret used for every shop that installs the app (not a per-shop secret), any merchant/attacker who installs the app on their own store will receive genuinely Shopify-signed webhooks (valid `body` + valid `X-Shopify-Hmac-Sha256`) for their own store. Since the HMAC never covers the shop domain, that attacker can resend the exact same `raw_post`/signature pair to the endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `hmac_valid?` still returns true (it only ever re-derives the HMAC from `data = request.raw_post`), and `shop_domain` now resolves to the victim's domain, so any custom controller built per the documented pattern will process/enqueue shop-scoped work (e.g. cart/order/privacy jobs) under the wrong (victim) shop.

### Impact Explanation
This allows an authenticated app-installer (any merchant who installs the app, i.e. an "unrelated-merchant" caller relative to the victim shop) to forge webhook events that appear to belong to a different shop, without needing to know or brute-force the shared secret. Depending on the app's webhook job logic (e.g. mandatory privacy webhooks, `shop_redact`, `carts/update`, etc.), this can corrupt or exfiltrate data attributed to a shop the attacker does not control — a cross-shop data/action confusion analogous to the "multiple Groupcoins under the same signature" issue, where a signature intended to authorize one identity/action is reused to authorize a different one.

### Likelihood Explanation
Likelihood is medium: it requires the attacker to be able to install the app themselves (common for many public apps) or otherwise capture one valid signed webhook body, and requires the target app to use `shop_domain` from this concern to route/scope job processing — which is exactly the pattern promoted in the gem's own documentation.

### Recommendation
Include the shop domain (and ideally webhook id / timestamp, i.e. a nonce-like binding) as part of what is cryptographically verified before trusting it, e.g. verify that the `X-Shopify-Shop-Domain` header corresponds to a shop that actually has an active, previously-established session/subscription for the specific webhook topic (cross-check against `SessionRepository`/webhook registration), rather than trusting the header purely because the body's HMAC validates. At minimum, document and enforce that `shop_domain` must never be used to authorize shop-scoped state changes without an independent authorization check against stored shop records.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared app secret), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the identical `B` and `H` to the same webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `PayloadVerification#hmac_valid?` re-derives the HMAC from `B` alone and matches `H` → passes.
5. A custom controller built with `ShopifyApp::WebhookVerification` (per `docs/shopify_app/webhooks.md`) calls `SomeJob.perform_later(shop_domain: shop_domain, ...)`, where `shop_domain` now returns `"victim.myshopify.com"`, causing the job to run against the victim shop using attacker-controlled webhook body content.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
