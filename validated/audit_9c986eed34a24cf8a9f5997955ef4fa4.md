## Title
Stale working-directory snapshot lets Copilot auto-resolve silently overwrite a user's manual conflict fix - (File: `app/src/lib/stores/app-store.ts`)

## Summary
`AppStore._applyCopilotConflictResolutions` writes AI-generated conflict resolutions to disk and stages them. Before overwriting a file it is supposed to check whether the user already resolved that conflict manually (e.g. in their editor) and, if so, skip it to avoid clobbering the user's fix. That guard is evaluated against a `repositoryStateCache` snapshot captured once at function entry, before the function's per-file loop performs multiple `await`s (`resolveWithin`, `writeFile`, `git add`). Because the snapshot is never refreshed, the "already resolved" check can be stale for the entire multi-file loop, allowing Copilot's stored resolution to silently overwrite content the user fixed by hand after the snapshot was taken.

## Finding Description
`_applyCopilotConflictResolutions` reads state once: [1](#0-0) 

For each conflict resolution it resolves the path and then relies on the *same, pre-loop* `state.changesState.workingDirectory.files` to decide whether the file was "already resolved externally": [2](#0-1) 

The comment at lines 7241-7246 documents the intent explicitly - avoid clobbering a resolution the user made in their editor while the result dialog was open - but the check is only as fresh as the `state` variable captured on line 7172, before any of the loop's async I/O runs. This is structurally the same defect as the GMX report: a security-relevant decision (whether it's safe to overwrite state) is made from data that predates the operations that can invalidate it, instead of being re-validated immediately before the mutating action (`writeFile` at line 7258). Unlike `updateChangesStashDiff` elsewhere in the same file, which explicitly re-fetches state after an `await` and bails out if it has changed (`stateAfterLoad`/`changesStateAfterLoad` pattern), `_applyCopilotConflictResolutions` has no equivalent re-check.

Because merge/rebase/cherry-pick conflicts by definition involve "theirs" content that can originate from an untrusted branch or fork (the exact scenario a GitHub Desktop user hits when resolving a PR from a fork), the resolved content being written (`resolution.resolvedContent`) is derived from repository content that is not fully trusted, and the write path that is supposed to defer to the user's own fix can go stale and overwrite it.

## Impact Explanation
If the guard's stale snapshot causes it to write Copilot's resolution over a file the user had already fixed by hand during the (multi-file, I/O-bound) apply loop, the user's real fix is silently discarded and replaced with the AI-generated content without any error or warning, and that content is immediately staged (`git add`) and will be part of what the user commits/pushes next. This matches the "silent corruption of what the user commits" impact category — the user believes they resolved the conflict correctly, but a stale-state race caused an unreviewed overwrite.

## Likelihood Explanation
The window requires the Copilot resolution flow to be mid-flight across the internal loop (which does per-file `resolveWithin`/`writeFile` awaits plus a trailing `git add`) while the user edits/saves a conflicting file externally during that window - the same kind of TOCTOU window the code's own comment acknowledges but only partially mitigates (the mitigation checks a snapshot that is never refreshed). This is a real, non-hypothetical race condition rather than a purely theoretical one, but it depends on timing and is not remotely triggerable by an attacker without the victim also invoking the Copilot conflict-resolution feature on a repository containing attacker-influenced "theirs" content.

## Recommendation
Re-fetch (or re-read) the on-disk/working-directory status for each file immediately before the `writeFile` call inside the loop (mirroring the "state changed underneath us, bail" pattern already used in `updateChangesStashDiff`), rather than relying on the single `state` snapshot captured at function entry.

## Proof of Concept
1. Start a merge/rebase/cherry-pick against a branch or fork whose conflicting side is attacker-influenced, and enable Copilot conflict resolution.
2. Let Copilot compute resolutions for multiple conflicted files (`resolveOAuthRequest`-style multi-file loop in `_applyCopilotConflictResolutions`).
3. While the "Continue Merge" apply loop is executing (lines 7196-7260), manually resolve one of the still-pending files directly on disk in an external editor and save it, removing conflict markers.
4. Because `onDiskFile` at line 7247 is looked up against the `state` object captured at line 7172 (before the loop began), it does not reflect the just-made edit; the loop proceeds to `writeFile` at line 7258 for that file, silently overwriting the user's manual fix with Copilot's resolution, which is then staged via `git add`.
