## Finding: Session-ID Fallback Collision in security-guidance Hook State (Cross-Session Bypass)

### Title
Hardcoded `session_id` fallback to `"default"` causes cross-session state collisions that silently suppress security-review findings and rate limits - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
The Sherlock finding describes `createCommonProjectIDAndDeploymentRequest()` hardcoding an index to `0` instead of an incrementing per-user value, so two legitimate, distinct requests collide on the same storage slot and one is silently lost. The same bug class — a hardcoded/constant identity value used as a state-partitioning key, causing distinct events to collide and overwrite each other — is reachable in the `security-guidance` plugin's hook dispatcher.

### Finding Description
`main()` in `security_reminder_hook.py` derives the partitioning key for all per-session security state from the hook's JSON input, falling back to the literal string `"default"` whenever `session_id` is absent or falsy: [1](#0-0) 

This value flows straight into `_state_key()`, which additionally allows `CLAUDE_CODE_REMOTE_SESSION_ID` to override it, and is used verbatim to compute the state and lock file paths: [2](#0-1) [3](#0-2) 

If `session_id` is ever missing (e.g. a hook invocation malformed/omitted by a caller, a race during session bootstrap, or any code path that emits an event without the field), every such invocation — potentially from unrelated concurrent Claude Code sessions/projects on the same machine — collapses onto the single shared file `security_warnings_state_default.json`. This is directly analogous to `BlueprintCore`'s `index = 0`: a value meant to disambiguate distinct logical "requests" (here, distinct sessions) is instead constant, so unrelated state gets merged/overwritten.

The consequences are concrete because this shared state backs multiple security-relevant dedup and rate-limit mechanisms:
- Per-file/rule warning suppression: `warning_key = f"{file_path}-{rule_name}"` gated by `atomic_check_and_mark_warning(session_id, warning_key)` — collapsed sessions sharing the same `session_id="default"` will suppress each other's pattern warnings once either has "seen" the same key. [4](#0-3) 
- Commit-review hourly rate limiting: `atomic_check_rate_limit(session_id, "CommitReview", MAX_COMMIT_REVIEWS_PER_HOUR, ...)` — with a shared key, one session's commits consume the shared quota, silently disabling the LLM commit-security review for a different, unrelated session/project once the limit is hit. [5](#0-4) 
- Cross-session finding dedup: `previous_findings`/`_dedup_against_state` keyed only by `(filePath, category)` under the shared state file, so a genuine vulnerability found in project A can be treated as "already known" and dropped when the identical relative path/category recurs in unrelated project B. [6](#0-5) 

### Impact Explanation
This is a "hook bypass" analog in the trust-boundary sense called out by the task: the security-guidance plugin's whole purpose is to catch dangerous patterns and vulnerable commits before/around tool use. A cross-session collision on the state-partition key means legitimate security findings or reviews for one workspace can be silently dropped or throttled because of unrelated activity in a different session that happens to share the fallback key — the equivalent of the Sherlock bug's "user paid for two agents but only one gets finalized." Here, a user (or an unrelated concurrent session on a shared host) can cause security review coverage to be silently lost for another session, without any error surfaced (the code paths involved just `sys.exit(0)`/skip on rate-limit or dedup match).

### Likelihood Explanation
Likelihood depends on how reliably Claude Code always supplies a non-empty `session_id` in hook JSON payloads for every event type; this repo mirror does not contain the core CLI's hook-dispatch source, only the plugin side, so I cannot verify from this codebase alone whether `session_id` can actually be empty/missing in practice for `PreToolUse`/`PostToolUse`/`Stop` events. The code defensively handles that case (`input_data.get("session_id", "default")`), which itself indicates the plugin authors anticipated it could happen, but the actual frequency/triggerability on the real CLI could not be confirmed from the indexed files.

### Recommendation
Do not fall back to a constant literal for `session_id`. If the field can legitimately be absent, generate a random per-invocation identifier (and accept that recovery/reconciliation across restarts is not possible) rather than defaulting to a value that is identical across all callers/sessions, mirroring the Sherlock fix of using an incrementing per-user index instead of a hardcoded `0`.

### Proof of Concept
Not independently verified against the live CLI (no terminal access in this environment) — the analysis is based on static code paths in `security_reminder_hook.py` and `session_state.py`. Conceptually: two concurrent Claude Code sessions in different projects both send a hook event with `session_id` omitted/empty; both resolve to `security_warnings_state_default.json`; session A commits code and exhausts `MAX_COMMIT_REVIEWS_PER_HOUR` under that shared file; session B's subsequent `git commit` in an unrelated project is silently skipped from LLM security review because `atomic_check_rate_limit` reads the same shared counter [5](#0-4) .

```python
def _state_key(session_id):
    # In CCR each user turn is a new CC process with a fresh session_id; the
    # remote session ID is stable across those restarts. Prefer it so the
    # pending-warnings sweep and any unprocessed touched_paths survive.
    key = os.environ.get("CLAUDE_CODE_REMOTE_SESSION_ID") or session_id
    # The key becomes a filename component under the state dir. CC session ids
    # are UUIDs (sanitization is a no-op for them), but nothing in the hook
    # protocol guarantees that, so strip path separators and anything else
    # that could escape the state dir, and bound the length.
    return re.sub(r"[^A-Za-z0-9._-]", "_", str(key))[:128]
```

```python
def _finding_keys(findings: List[Dict[str, Any]]) -> set:
    return {(f.get("filePath", ""), f.get("category", ""))
            for f in findings if isinstance(f, dict)}


def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```
