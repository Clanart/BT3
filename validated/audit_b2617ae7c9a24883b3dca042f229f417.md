The current `json.go` `ExtractAsUint256` already caps `strValue` at 100 characters (`len(strValue) > 100`), which is bounded and cheap to parse — `big.Int.SetString` on a 100-digit string is negligible, so the main precompile is not exploitable this way. However, this length cap is only present in some versions. Checking the legacy versions I found (`precompiles/json/legacy/v603/json.go`, `v605`, `v614`, `v640`), their `ExtractAsUint256` implementations do **not** have this 100-character cap — they call `new(big.Int).SetString(strValue, 10)` directly on a string extracted from attacker-controlled JSON with no length bound, while `RequiredGas` charges only `GasCostPerByte * len(input)` (linear in the whole calldata).

### Title
Unbounded numeric-string parsing in legacy `json` precompile `extractAsUint256` allows underpriced quadratic-cost Denial of Service - (File: `precompiles/json/legacy/v603/json.go`, `precompiles/json/legacy/v605/json.go`, `precompiles/json/legacy/v606/json.go`, `precompiles/json/legacy/v610/json.go`, `precompiles/json/legacy/v614/json.go`, `precompiles/json/legacy/v620/json.go`, `precompiles/json/legacy/v630/json.go`, `precompiles/json/legacy/v640/json.go`)

### Summary
Legacy versions of the `json` Cosmos precompile (address `0x0000000000000000000000000000000000001003`) expose `extractAsUint256(bytes input, string key)`, which extracts a JSON value as a string and passes it directly to `new(big.Int).SetString(strValue, 10)` with no length bound. [1](#0-0)  Gas for the call is charged purely as a linear function of calldata length (`GasCostPerByte * len(input)`), never accounting for the cost of parsing the extracted decimal string. [2](#0-1)  This mirrors the cowlib CVE-2026-7790 bug class: an unbounded digit string is fed into a bignum accumulator (multiply by base, add digit) whose cost is quadratic in the digit count, while the caller is billed only linearly.

### Finding Description
`ExtractAsUint256` in the affected legacy versions decodes the JSON payload, looks up `key`, trims quotes from the resulting value, and converts it straight to a `big.Int`: [3](#0-2) 

There is no check on `len(strValue)` before `SetString` is invoked (contrast this with the current head-of-tree `precompiles/json/json.go`, which added `if len(strValue) > 100 { return nil, ... }` before calling `SetString`) [4](#0-3) . Go's `big.Int.SetString` for base-10 input parses the string digit-by-digit, multiplying the accumulator by 10 and adding the next digit each time; because the accumulator grows with the number of digits already consumed, the total cost is quadratic (O(n²)) in the number of digits — exactly the "digit accumulates via multiply/add" pattern the cowlib advisory describes for `cow_http_te:chunked_len/4`.

The gas actually charged for the call is only `GasCostPerByte * len(input)` (a flat 100 gas/byte over the entire ABI-encoded calldata) [2](#0-1) , which is linear in the size of the JSON payload — not the quadratic cost of the `SetString` call the payload can trigger. An attacker can therefore submit a JSON blob such as `{"k":"999999999...9"}` with an arbitrarily long digit string (bounded only by the tx's calldata/gas limit, not by any check inside `extractAsUint256`), causing the node executing the transaction to spend CPU time proportional to the square of that digit count while paying gas that only scales linearly.

### Impact Explanation
Any account can deploy or call a contract that invokes the `json` precompile at `0x...1003` with `extractAsUint256`, since it is a public, stateless, always-available Cosmos precompile reachable from ordinary EVM transactions/`eth_call`. Because the actual parsing cost is quadratic while the gas metering is linear, an attacker can construct calldata that is cheap in gas but expensive in wall-clock CPU time for every validator that must execute the transaction during block processing. If a sufficiently long digit string is used, this can push single-transaction/block EVM execution time past normal bounds, risking validator block-processing delay (potentially beyond the 2.5-second threshold) and, in the worst case, degraded liveness across the network since every full node must re-execute the same transaction deterministically.

### Likelihood Explanation
Likelihood is High if any of the affected legacy `json` precompile versions (`v603`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`) are still reachable/live on any deployed chain height (Sei's precompiles are versioned per-upgrade and legacy versions are typically retained for historical block replay/tracing). The call requires no special privilege — only calldata crafted by any transaction sender or contract — and the underpriced gas model makes the attack economically cheap relative to the CPU cost it imposes.

### Recommendation
Backport the length cap already present in the current `precompiles/json/json.go` (`if len(strValue) > 100 { return nil, fmt.Errorf(...) }` before calling `SetString`) to all legacy versions that lack it, or otherwise ensure gas charged for `extractAsUint256` scales with the square of the extracted numeric string length (or is capped to a small fixed maximum) rather than only with total calldata length. Since legacy precompile code is used for historical block replay, verify whether these versions are actually reachable for new transactions today; if they are frozen to historical heights only, the practical risk is limited to replay/tracing nodes, but if any legacy version can still be dispatched for current transactions (e.g., via version-selection logic), it must be patched or hard-disabled for new calls.

### Proof of Concept
1. Deploy or use any contract, or call directly via `eth_call`/a raw transaction, targeting precompile address `0x0000000000000000000000000000000000001003`.
2. ABI-encode a call to `extractAsUint256(bytes input, string key)` where `input` is `{"k":"<N digits>"}` with `N` chosen as large as the tx gas limit allows under the linear `GasCostPerByte * len(input)` charge (e.g., tens of thousands of digits).
3. Submit the transaction/call against a node running one of the affected legacy precompile code paths (`v603`/`v605`/`v606`/`v610`/`v614`/`v620`/`v630`/`v640`).
4. Observe that `ExtractAsUint256` calls `new(big.Int).SetString(strValue, 10)` on the full N-digit string with no pre-check [5](#0-4) , consuming CPU time proportional to N², while gas charged remains proportional to N — demonstrating the underpriced quadratic-cost resource consumption.

**Uncertainty note:** I could not fully confirm from the index whether these legacy `json` precompile versions are still dispatchable for *new* (non-historical) transactions today, or are strictly gated to replay of old blocks below their respective upgrade heights (which would limit real-world exploitability to trace/replay nodes rather than live consensus). Confirming the precompile version-selection/dispatch logic (likely in `x/evm` upgrade-height routing) would require further investigation beyond what the index surfaced.

		return p.extractAsBytes(ctx, method, args, value)
	case ExtractAsBytesListMethod:
		return p.extractAsBytesList(ctx, method, args, value)
	case ExtractAsUint256Method:
		byteArr := make([]byte, 32)
		uint_, err := p.ExtractAsUint256(ctx, method, args, value)
		if err != nil {
			return nil, err
		}

		if uint_.BitLen() > 256 {
			return nil, errors.New("value does not fit in 32 bytes")
		}

		uint_.FillBytes(byteArr)
		return byteArr, nil
	case ExtractAsBytesFromArrayMethod:
		return p.extractAsBytesFromArray(ctx, method, args, value)
	}
	return
