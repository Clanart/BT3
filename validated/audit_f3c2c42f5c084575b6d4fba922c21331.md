### Title
Out-of-bounds panic in `Interpolation::Constant` factor lookup via deserialized `ThresholdKeys` enables remote crash/DoS - ([File: crypto/dkg/src/lib.rs])

### Summary
CVE-2022-21527 is a low-complexity, network-reachable crash/hang (complete DoS). The Serai analog is a reachable panic — an index-out-of-bounds inside `Interpolation::interpolation_factor` — triggered when a `ThresholdKeys` object whose `Interpolation::Constant` coefficient vector is shorter than the participant set is used in `view()` / `sign()`. `ThresholdKeys::new` validates `t == n` for `Constant` interpolation but never checks that the coefficient vector's length equals `n`, so a malformed serialized `ThresholdKeys` (or one constructed by an integrator feeding untrusted bytes into `ThresholdKeys::read`) carries an inconsistent state that later panics when a participant index ≥ vector length is looked up.

`ThresholdKeys::new` only rejects `Constant` interpolation when `t != n`; it performs no length check on `c` against `n`:

```rust

  Interpolation::Constant(_) => {
    if params.t() != params.n() {
      Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;

  Interpolation::Lagrange => {}

``` [2](#0-1) 

The panic site is reached from `ThresholdKeys::view`, which is called on every signing operation from `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:312`, `self.params.keys.view(included.clone()).unwrap()`), and is also invoked inside `ThresholdKeys::new` itself at line 378 for `i` in `1..=t`. Any participant index `i` with `u16::from(i) - 1 >= c.len()` panics with an index-out-of-bounds — a hard crash, not a recoverable `Err`.

### Impact Explanation
An unprivileged counterparty who can cause a node/deserializer to load a crafted `ThresholdKeys` (via `ThresholdKeys::read`, or an integrator reconstructing keys from untrusted/storage-tampered bytes) can crash the process as soon as the keys are used for `view()` or a FROST `sign()`. In a validator/processor context this is a complete, repeatable DoS of that node's signing pipeline — matching the CVE's "unauthorized ability to cause a hang or frequently repeatable crash". Because the panic happens inside the crypto crate (not via a catchable error), it cannot be handled by the caller's `Result` flow.

### Likelihood Explanation
Internally produced `Constant` interpolations are always well-formed (`musig` builds `binding_factors` with exactly `keys_len` entries, `crypto/dkg/musig/src/lib.rs:140-157`), so honest paths never panic. However, `ThresholdKeys` exposes a `read` path and `ThresholdKeys::new` is public; neither enforces `c.len() == n`. Any consumption of a `Constant`-interpolated `ThresholdKeys` whose byte-level or caller-supplied coefficient vector is truncated reaches `c[i - 1]` with `i` up to `n` (forced to `1..=t` at line 376-378 even before any attacker-chosen signing set), making the crash deterministic. Reachability depends on an integrator deserializing keys from a less-trusted source (DB, RPC payload), which the crate's own serialization API invites.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:367-374), add a length check for `Interpolation::Constant(c)` requiring `c.len() == usize::from(params.n())`, returning a new `DkgError` variant (e.g. `IncorrectAmountOfInterpolationCoefficients`) on mismatch. Apply the same validation in `ThresholdKeys::read` / deserialization so malformed encodings are rejected as `io::Error`/`DkgError` rather than stored. Additionally, consider making `interpolation_factor` return `Option<F>`/use `c.get(...)` so a defensive `Err` propagates instead of a panic.

### Proof of Concept
```rust
// Requires: crypto/dkg (in-scope), any Ciphersuite, e.g. via dalek-ff-group
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation, DkgError};
use std::collections::HashMap;
use zeroize::Zeroizing;

fn poc<C: ciphersuite::Ciphersuite>() {
  let n: u16 = 3;
  let params = ThresholdParams::new(n, n, Participant::new(1).unwrap()).unwrap();

  // Attacker-crafted: Constant vector shorter than n. ThresholdKeys::new
  // only checks t == n, never c.len() == n.
  let interpolation = Interpolation::Constant(vec![C::F::ONE, C::F::ONE]); // len 2 < n 3

  let mut verification_shares = HashMap::new();
  for i in 1 ..= n {
    verification_shares.insert(Participant::new(i).unwrap(), C::generator());
  }

  // PANIC inside ThresholdKeys::new -> interpolation_factor(Participant(3), ..)
  // indexes c[2] on a length-2 Vec: index out of bounds.
  let _ = ThresholdKeys::<C>::new(
    params,
    interpolation,
    Zeroizing::new(C::F::ONE),
    verification_shares,
  );
}
```

Even if `ThresholdKeys::new` hypothetically skipped the `1..=t` group-key computation, the same panic is reached later through `keys.view(included)` → `interpolation_factor` (crypto/dkg/src/lib.rs:496,505) for any signing set containing a participant index beyond the truncated vector — i.e., the first `AlgorithmSignMachine::sign` call (crypto/frost/src/sign.rs:312). Caveat: the exact wire-`read` constructor for `ThresholdKeys` was not fully inspected in this session; the panic itself and the missing length validation are confirmed in `crypto/dkg/src/lib.rs`.
