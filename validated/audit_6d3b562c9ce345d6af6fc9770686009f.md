### Title
Auto-repointing of `origin` to an attacker-controlled URL via unvalidated GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` silently rewrites the local `origin` remote to whatever `clone_url` a GitHub/GHE API response contains, with no check that the new URL's hostname belongs to the account's configured endpoint. A hostile or compromised GitHub Enterprise (GHE) host — which Desktop already trusts once an account for it exists — can therefore redirect a tracked repository's remote to an arbitrary, attacker-controlled git server during a routine background refresh, with no user interaction.

### Finding Description
When Desktop periodically refreshes repository metadata, `repositoryWithRefreshedGitHubRepository` calls `API.fromAccount(account).fetchRepository(owner, name)` and feeds the resulting `IAPIFullRepository` object into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then decides whether to rewrite the git remote purely from string comparisons of owner/name/hostname parsed out of URLs — it never checks that the new `clone_url`'s hostname equals the account's own endpoint hostname: [2](#0-1) 

The only real guards are:
- `protocolsMatch` — same scheme (http/https vs ssh), not same host.
- `remoteUrlUnchanged` — the *previously stored* remote must still equal the previously stored `gitHubRepository.cloneURL` (i.e., the user hasn't manually customized the remote).
- `!urlsMatch` — the new URL differs from the current one.

None of these validate that the new `clone_url` hostname matches the account's own endpoint (`account.endpoint` / `getHTMLURL(account.endpoint)`). `urlMatchesRemote` (used for `urlsMatch`) only compares the *new* value against the *current* remote, and `parseRemote`/`parseRepositoryIdentifier` extract hostname/owner/name generically from any URL without pinning it to a trusted host list: [3](#0-2) [4](#0-3) 

Because the account used to call `fetchRepository` was itself selected by matching the *existing* remote's hostname (`matchGitHubRepository`), the attacker does not need to compromise the app's account list — they only need control over the API response for a GHE host the user already has configured (a malicious/compromised enterprise server, or a MITM'd insecure HTTP GHE endpoint, both of which the app's own changelog acknowledges as previously mishandled: "Resolved auth failures... on non-GitHub hosts", "Clear stored credentials when authentication fails on insecure http hosts"): [5](#0-4) [6](#0-5) 

Once `setRemoteURL` executes, git's `origin` is silently repointed: [7](#0-6) [8](#0-7) 

The subsequent credential lookup for push/fetch is host-based, so a same-`.ghe.com`/different-path attacker URL (satisfying `ghe.com` subdomain SSH regex) or an HTTPS URL under a hostname the user is willing to authenticate to will trigger the generic-credential prompt path, harvesting credentials the user believes belong to their known repository: [9](#0-8) 

### Impact Explanation
This breaks the invariant "the local `origin` remote for a tracked repository always points to the same GitHub-hosted repository the user cloned/added it for." A hostile GHE server response can silently repoint `origin` to a different host/path. Consequences:
- **Silent corruption of what the user pushes** — future pushes go to an attacker-controlled repository instead of the intended one, without any dialog or confirmation, directly matching the report's core theme (stale ownership references causing assets/data to flow to the wrong destination).
- **Credential exfiltration** — if the redirected URL requires generic auth, Desktop will prompt the user for credentials for what appears to be their normal workflow, handing plaintext credentials to the attacker's endpoint via `promptForCredential`/`getGenericCredential`.
- Downstream, a maliciously substituted remote also affects fetch/pull paths in the same repository, allowing serving of attacker-chosen objects to the victim's working tree.

### Likelihood Explanation
Requires the victim to already have added a GitHub Enterprise account that later becomes malicious/compromised, or to be using an insecure (HTTP) GHE endpoint subject to MITM — both explicitly in-scope per the task ("attacker controls ... a GitHub API object", "a git remote/proxy response"). No local access, no admin rights, no pre-existing malware, and no unusual user action are required: the background repository refresh (`repositoryWithRefreshedGitHubRepository`) runs automatically and silently on Desktop's normal refresh cadence.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, verify that the parsed hostname of `updatedRemoteUrl` matches the hostname of the account's own configured endpoint (`getHTMLURL(account.endpoint)`/GHE endpoint used to fetch the repo), not merely that it differs from the previous remote. Reject (and, if desired, surface a warning to the user) any `clone_url` whose hostname doesn't match the expected host for that account/endpoint before silently rewriting `origin`.

### Proof of Concept
1. User adds a GitHub Enterprise account for `ghe.company.com` and has a repository whose `origin` is `https://ghe.company.com/team/project.git`, tracked with `gitHubRepository.cloneURL = https://ghe.company.com/team/project.git`.
2. The GHE server (compromised, or an attacker performing MITM on an insecure/self-signed HTTP endpoint the user has trusted) responds to `GET repos/team/project` with `clone_url: "https://ghe.company.com/attacker/project.git"` (same host, satisfying `protocolsMatch`, hostname parse succeeds, owner differs so `urlsMatch` is false).
3. On the next background refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` finds `remoteUrlUnchanged === true` (user hadn't customized remote) and `urlsMatch === false`, so it calls `gitStore.setRemoteURL('origin', 'https://ghe.company.com/attacker/project.git')` without any prompt.
4. The next `git push`/`git fetch` from Desktop silently operates against `attacker/project`, and if credential prompting occurs, the user's credentials are sent to the attacker-influenced endpoint.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
