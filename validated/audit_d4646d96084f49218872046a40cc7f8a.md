### Title
Anyone can steal accumulated reward-token balances from `ManualCompound` via unrestricted balance-sweeping in `compound()` - (File: `rewards/ManualCompound.sol`)

### Summary
`ManualCompound.compound()` is `external` with no access control and, like the reported `Option.take()` bug, blindly sweeps the *entire current token balance* of the contract (`IERC20(token).balanceOf(address(this))`) and sends it to `msg.sender`, rather than tracking and paying out only the amount attributable to the caller's own claim in that transaction. Any wallet can therefore drain reward tokens that belong to, or were left in the contract on behalf of, other users.

### Finding Description
`compound()` first triggers `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, which is a privileged, compounder-only entrypoint on `MasterMagpie` [1](#0-0) . Internally `_multiClaim` sends the claimed reward tokens for the specified `_account` to `_receiver = msg.sender` of `multiclaimOnBehalf`, i.e., to the `ManualCompound` contract itself [2](#0-1) .

Back in `ManualCompound.compound()`, two loops then move tokens out of the contract:

1. For "non-compoundable" rewards explicitly listed by the caller in `_rewards[i][j]`, it reads `IERC20(_rewards[i][j]).balanceOf(address(this))` and transfers the **entire balance** to `msg.sender`: [3](#0-2) 

2. For every registered "compoundable" reward token, it again reads `IERC20(_tokenAddress).balanceOf(address(this))` and routes/transfers the **entire balance** to `msg.sender` (or to a locker/converter/helper "for" `msg.sender`): [4](#0-3) 

Neither loop computes a "before/after" delta for this specific call, nor validates that the swept balance actually corresponds to rewards earned by the caller's `_lps`/stake. Any token balance sitting in the `ManualCompound` contract — whether from another user's reward claim that wasn't fully swept (e.g., a caller who omits a token from `_rewards[i]` or from the registered `rewards` list, leaving that token's balance stranded in the contract after their own `compound()` call), or from any other transfer into the contract — is claimable by the next arbitrary caller who references that token address in their own `_rewards` array or has it in the registered `rewards` list. This mirrors the root cause of the reported `Option.take()` issue: an unauthenticated, `external` function that syncs/sweeps actual token balance to the caller instead of crediting only what is owed to them.

### Impact Explanation
Direct theft of user funds: reward tokens claimed on behalf of one user (or otherwise resting in the `ManualCompound` contract) can be swept by any other, unrelated wallet simply by calling `compound()` with matching token addresses. Because `masterMagpie` is `immutable` and `compoundableRewards`/`rewards` are contract-wide (not per-user), there is no isolation between users' claims that pass through this contract in the same or different transactions, so unclaimed/leftover reward balances are permanently exposed to theft.

### Likelihood Explanation
High. No access control, no reentrancy protection is needed for the attack (it doesn't require reentrancy — a normal call suffices whenever token balance exists in the contract), and the caller fully controls the `_rewards` argument determining which token balances get swept to them. The only precondition is that some balance of a given reward token exists in the `ManualCompound` contract at call time, which routinely occurs whenever a prior `compound()` call does not perfectly enumerate every reward token that `MasterMagpie` sent to the contract.

### Recommendation
Track and transfer only the balance delta generated by the current call (before/after balance diff) for each token, scoped to `msg.sender`'s own claim, instead of sweeping `balanceOf(address(this))`. Alternatively, remove the reliance on ambient contract balance and have `MasterMagpie`/`BaseRewardPool` pay reward tokens directly to the end user rather than to the `ManualCompound` intermediary, consistent with how the original report's fix removed the vulnerable `take()`/balance-sync pattern from `Option.sol`.

### Proof of Concept
1. User A calls `MasterMagpie`-integrated pool actions such that pending rewards in tokens `X` and `Y` accrue to A.
2. User A calls `ManualCompound.compound(_lps, _rewards, ...)` but only includes token `X` in `_rewards[i]` (omitting `Y`, or `Y` happens not to be in the registered `rewards` array as compoundable). `_multiClaim` transfers both `X` and `Y` to the `ManualCompound` contract, but only `X` gets swept to A in `compound()`'s loops; `Y`'s balance remains stuck in `ManualCompound`.
3. Attacker B (unrelated wallet, no stake, no claim) calls `ManualCompound.compound(_lps=[], _rewards=[[Y]], _convertRatio=0, _minRec=0, _lockMgp=false)`. Since `_lps` is empty, `multiclaimOnBehalf` claims nothing for B, but the first loop iterates `_rewards[0][0] = Y`, reads `IERC20(Y).balanceOf(address(this))` (which is User A's stranded balance), and transfers it entirely to B via `IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance)` [5](#0-4) .
4. B has stolen User A's reward token `Y` without ever staking or being entitled to it.
