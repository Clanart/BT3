### Title
Payout attribution to an operator is derived from an unsigned OP_RETURN output, letting anyone credit a payout to an operator that never funded it - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The user's withdrawal signature over the `payout_tx` only commits to the withdrawal input and the user's output (`SinglePlusAnyoneCanPay`), leaving the OP_RETURN output that records "which operator fronted this payout" completely unauthenticated. Anyone who can fund the difference between the dust withdrawal UTXO and the withdrawal amount can construct and broadcast a valid `payout_tx` that embeds an arbitrary operator's x-only pubkey in that OP_RETURN, causing the bridge to later credit and reimburse an operator that never paid.

### Finding Description
`create_payout_txhandler` builds the OP_RETURN output from a caller-supplied `operator_xonly_pk` argument, and only the withdrawal input (index 0) and the user output (index 0) are signed by the user via `SinglePlusAnyoneCanPay`: [1](#0-0) 

Because the signature type is `SinglePlusAnyoneCanPay`, the transaction is malleable: any party can add funding inputs and freely choose the OP_RETURN payload (the "operator fronted this" claim) without invalidating the user's signature. This is exactly the equality that should be preserved and is broken: `operator credited via OP_RETURN == party that actually funded the payout`.

Downstream, the bitcoin-sync logic in the verifier reads this exact OP_RETURN to decide which operator is attributed as having paid the withdrawal, with no further verification that the attributed operator actually supplied the funding: [2](#0-1) 

This attribution is then persisted (`update_payout_txs_and_payer_operator_xonly_pk`) and later consumed by the operator's automated task, which treats any payout attributed to its own xonly pubkey as something it must reimburse itself for via the kickoff/reimburse flow: [3](#0-2) [4](#0-3) 

Nothing in this chain checks that the operator whose key appears in the OP_RETURN actually supplied the additional funding input(s) that made up the difference between the small withdrawal-registration UTXO and the real payout amount. The only value checks performed elsewhere in the withdrawal path (`Operator::is_profitable` in `core/src/operator.rs:502-537`, and the `output_amount` cap in `Verifier::sign_optimistic_payout` in `core/src/verifier.rs:1634-1644`) are run by an operator *before it itself* builds and signs a payout — they do not protect the *reverse* case where a third party builds and broadcasts the transaction first with a different operator's pubkey baked in.

### Impact Explanation
This directly instantiates the explicitly listed Critical impact: "an operator reimbursed for a payout it never funded." An unprivileged party (no verifier/operator/aggregator role needed) can:
1. Obtain a valid, signed withdrawal input/output pair (available once a withdrawal is registered/broadcast, since the signature only binds input 0 / output 0 and is meant to be completed by whichever party fronts it).
2. Construct a competing `payout_tx` that adds its own funding input(s) to make up the payout amount, and set the OP_RETURN to an arbitrary honest operator's x-only pubkey.
3. Broadcast this before the intended operator's own payout tx.
4. Once finalized, the verifier's `update_finalized_payouts` attributes the payout to the embedded operator, and that operator's `PayoutCheckerTask` automatically drives `handle_finalized_payout` → kickoff → reimburse, pulling `bridge_amount` out of that deposit's move-to-vault UTXO to reimburse an operator who spent nothing.

This breaks the core custody equality the bridge is meant to preserve (operator reimbursed == operator fronted the payout), and can be used to force honest operators to consume their own kickoff/round slots and be reimbursed for a payment they did not make (griefing their round schedule) or, in principle, to redirect vault funds to an operator not intended to be involved in that specific withdrawal.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: constructing the alternate transaction requires no privileged role or key compromise, only capital to cover the funding gap and knowledge of a currently-open withdrawal (which is visible on Citrea/mempool once registered). The main friction is a race against the legitimate operator to get the alternate transaction confirmed first, and access to the same public withdrawal signature/outpoint that any operator is designed to be able to consume. Whether this is easy to win the race against the true operator's automation in practice is not something the static code review here can fully confirm.

### Recommendation
Bind the "who fronted this payout" attribution to something the user's (or protocol's) signature actually authenticates, e.g.:
- Have the operator sign or otherwise cryptographically commit to the OP_RETURN payload as part of constructing/broadcasting the payout, and have `update_finalized_payouts` reject/ignore attribution unless that commitment is present and valid.
- Alternatively, require that the additional funding input(s) used to complete the payout provably originate from the operator's known collateral/reimbursement address, and validate that at attribution time.
- At minimum, treat OP_RETURN-derived attribution as untrusted hint data and cross-check it against an authenticated source (e.g., a per-withdrawal reservation/lock by the operator, established before broadcast) before allowing `handle_finalized_payout`/kickoff/reimburse to proceed for that operator.

### Proof of Concept
1. A user's withdrawal is registered on Citrea with a signed `SinglePlusAnyoneCanPay` input/output pair for the withdrawal amount (dust UTXO input, user output), as produced by `sign_withdrawal_output` / `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`).
2. Attacker observes this outpoint/signature (available as soon as any operator attempts to fulfill the withdrawal, or via the withdrawal registration data itself).
3. Attacker builds a new transaction reusing input 0 (dust UTXO, signature valid because ANYONECANPAY) and output 0 (user payout, signature valid because SINGLE), then adds their own additional input(s) to cover the payout amount and appends an OP_RETURN output containing `victim_operator_xonly_pk` instead of their own.
4. Attacker broadcasts and gets this confirmed before the real operator's payout tx.
5. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2310-2343`) parses the OP_RETURN and attributes the payout to `victim_operator_xonly_pk`.
6. `victim_operator`'s `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-79`) later picks this up as an unhandled payout for its own xonly pubkey and drives `handle_finalized_payout`, entering the kickoff/reimburse flow and claiming `bridge_amount` from the deposit's move-to-vault UTXO — despite `victim_operator` never having funded the payout.

**Note:** I was unable to fully trace `Operator::handle_finalized_payout`'s internal body (only its signature/call sites were retrieved) or definitively confirm whether any additional out-of-band operator-consent check exists before kickoff is broadcast; the full contents of `core/src/operator.rs` around `handle_finalized_payout`'s implementation were not returned by search within the available iterations. If such a check exists, it should be examined to see whether it fully closes this gap.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
