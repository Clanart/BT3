### Title
Daemon keychain RPC exposes full secret-key material with no per-caller authorization scoping - ([File: chia/daemon/keychain_server.py])

### Summary
Any local client that can complete the daemon TLS handshake (any Chia service on the node, since they all use the shared daemon private cert/CA per `.cursor/context/ssl.md`) can issue `get_keys`/`get_all_private_keys`/`get_key` daemon commands and receive every wallet's mnemonic/private-key material in plaintext, and can additionally target arbitrary other keychains via attacker-controlled `kc_user`/`kc_service` fields, with no authorization check tying the request to the caller's own identity or privilege level.

### Finding Description
`WebSocketServer.handle_message()` routes any incoming command that is a member of `keychain_commands` straight to `KeychainServer.handle_command()` before any command-specific authorization is applied [1](#0-0) . The daemon's only gate is mutual TLS with the daemon private cert, which is the same shared local trust material used by every "less-trusted" local component (harvester, timelord, etc.) per the documented cert matrix [2](#0-1) ; there is no per-command or per-service authorization inside the daemon protocol itself [3](#0-2) .

Once inside `KeychainServer`, `get_keychain_for_request()` selects which `Keychain` instance to operate on purely from attacker-supplied `kc_user`/`kc_service` fields in the request body, with no check that the caller is authorized to access that particular keychain: [4](#0-3) . Every keychain method (`add_key`, `delete_all_keys`, `get_all_private_keys`, `run_request` for `get_key`/`get_keys`) resolves the target keychain through this same unauthenticated selector, e.g. `get_all_private_keys()` [5](#0-4)  and `run_request()` [6](#0-5) .

The `get_keys`/`get_key` typed requests accept an `include_secrets: bool` flag directly from the request and, when `True`, return full mnemonics/private-key data via `keychain.get_keys(self.include_secrets)` [7](#0-6) , confirmed by the test showing `include_secrets=True` returns full `KeyData` including secrets [8](#0-7) . `get_all_private_keys` unconditionally returns every private key/entropy pair with no `include_secrets` gate at all [5](#0-4) .

This mirrors the Kruise bug class (CWE-269/CWE-250): an over-broadly-privileged local component (the daemon-connected peer) can enumerate secret material belonging to the whole node/"cluster" of keychains rather than only its own scope, because the RPC/authorization boundary grants the same blanket trust to every connected client regardless of the service it represents.

### Impact Explanation
An attacker who can reach the daemon socket as any local Chia service (harvester, farmer, timelord, or any process holding the shared daemon private cert) can exfiltrate every wallet mnemonic and private key on the node via `get_all_private_keys` or `get_keys`/`get_key` with `include_secrets=True`, and can pivot across `kc_user`/`kc_service` boundaries to reach keychains outside its own intended scope. Stolen private keys allow the attacker to sign and broadcast arbitrary spends from any wallet on the node, i.e. unauthorized coin movement/theft of funds, matching the "Impact: High Confidentiality/Integrity" rating of the original advisory.

### Likelihood Explanation
Likelihood is High for any actor that already runs as, or has compromised, one of the node's local Chia services (which is the same threat model as the original Kruise finding — an attacker with access to a lower-trust local component). No additional network exposure, user interaction, or race condition is required; a single daemon command achieves full key exfiltration.

### Recommendation
Scope keychain daemon commands to the identity of the registered/connecting service (e.g., derive `kc_user`/`kc_service` from the authenticated connection/service registration rather than from attacker-supplied request fields), and require an explicit, non-default authorization step (separate from generic daemon TLS) before returning `include_secrets=True` data or invoking `get_all_private_keys`/`get_first_private_key`. Consider issuing distinct per-service daemon certificates so the daemon can enforce least-privilege per connecting service type.

### Proof of Concept
1. Start `chia start daemon` and any second local service (e.g. `harvester`) that only needs plotting/harvester access to the daemon; both connect using the shared daemon private cert per `ssl_context_for_server()`/`ssl_context_for_client()`.
2. From the harvester's (or any daemon-connected) process, open a websocket to the daemon and send:
```json
{"command": "get_all_private_keys", "data": {}, "destination": "daemon", "request_id": "x", "ack": false, "origin": "harvester"}
```
3. The daemon returns `{"success": true, "private_keys": [{"pk": ..., "entropy": ...}, ...]}` for every key in the default keychain, as shown by `KeychainServer.get_all_private_keys()` [5](#0-4) .
4. Alternatively send `{"command": "get_keys", "data": {"include_secrets": true}}` to get full `KeyData` (mnemonic entropy included) as validated by `test_get_keys` [8](#0-7) .
5. Use the returned entropy/mnemonic to reconstruct the private key and sign/broadcast a spend bundle draining the associated wallet.

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

        keychain = self.get_keychain_for_request(request_dict)
        if keychain.is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        try:
            request = request_type.from_json_dict(request_dict)
        except Exception as e:
            return {
                "success": False,
                "error": KEYCHAIN_ERR_MALFORMED_REQUEST,
                "error_details": {"message": str(e)},
            }

        try:
            return {"success": True, **request.run(keychain).to_json_dict()}

    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}
```
