### Title
Line-index-based diff selection is silently re-applied against a freshly re-fetched diff at commit time, allowing corruption of what gets committed - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The bug class in the external report is: a numeric/positional value computed against one piece of data (the calldata `msg.data`) is blindly trusted and reused for an unrelated action (transferring a *different* token than the one the computation was performed on), with no check that the two values are consistent. The GitHub Desktop analog is the partial-commit/"stage selected lines" pipeline: the user's line selection is stored purely as **numeric line indices** (`DiffSelection`), computed against a diff snapshot shown in the UI. At commit time, `applyPatchToIndex` re-fetches a **brand-new** diff via `getWorkingDirectoryDiff` and blindly re-applies those same numeric indices to it via `file.selection.isSelected(absoluteIndex)` in `formatPatch`, with no verification that the new diff's hunks/lines are the same ones the user actually reviewed and selected.

### Finding Description
`DiffSelection` (`app/src/models/diff/diff-selection.ts`) is a purely index-based data structure — it has no notion of the actual line content, only a set of "diverging" line-number offsets: [1](#0-0) [2](#0-1) 

That selection is built by the UI against one specific `diff` object (fetched once when the Changes view loaded the file), for example in `side-by-side-diff.tsx`: [3](#0-2) 

When the user commits, `_commitIncludedChanges` in `app-store.ts` passes the working-directory `WorkingDirectoryFileChange` objects — each carrying only this index-based `selection` — straight to `createCommit`: [4](#0-3) 

`createCommit` → `stageFiles` → `applyPatchToIndex` (for any file with a partial selection): [5](#0-4) 

Critically, `applyPatchToIndex` does **not** reuse the diff the user looked at. It calls `getWorkingDirectoryDiff(repository, file)` again, fresh, at commit time: [6](#0-5) 

The freshly-fetched diff is then handed to `formatPatch`, which walks `diff.hunks[].lines[]`, computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex`, and decides whether to include each line **purely based on whether that numeric index was marked selected** — never checking that the line at that index is the same line the user actually saw and selected: [7](#0-6) 

The doc comment for `formatPatch` even acknowledges the model is "a number of selected or unselected lines (from `file.selection`)" with no claim that the underlying diff content is verified to be unchanged: [8](#0-7) 

**The broken invariant:** the numeric selection is computed against diff snapshot A (shown to the user), but is applied — unchecked — against diff snapshot B (fetched independently at commit time). Nothing ties the selection to a content hash, hunk header, or line text of the diff it was derived from. This is structurally identical to `bps()` grabbing an address off the end of `calldata` without checking that it corresponds to the token address the earlier computation actually used.

**Attacker-controlled trigger:** if the working tree file is mutated between the time the user opens the diff/makes a selection and the time they click "Commit" — e.g., by a script or process running as part of the cloned/fetched repository (a build tool, watch script, editor plugin, or any tooling the attacker convinces/causes to run on files in the repo, or simply a slow race where the file is rewritten between refresh and commit) — hunk boundaries shift while `DiffSelection`'s raw integer offsets stay the same. `formatPatch` will then happily include/exclude *different* lines than what the user visually selected, because `isSelected(absoluteIndex)` has no way to detect that hunk `unifiedDiffStart`/line content at that index no longer matches what was displayed.

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes": the user believes they are selectively staging line X, but the actual applied patch (built from a re-fetched, potentially different, diff) can select unintended lines — including lines the user explicitly chose *not* to commit, or omit lines they wanted included. Because the patch is applied with `git apply --cached`, this happens silently in the index with no diff-mismatch warning to the user before the commit is created.

### Likelihood Explanation
The window between diff-fetch-for-display and diff-fetch-for-commit is real and unguarded (`getWorkingDirectoryDiff` is called again inside `applyPatchToIndex`, per commit, per partially-selected file). The likelihood is moderate: it requires the working file to change between viewing/selecting and clicking commit in a way that shifts hunk boundaries while keeping the file "logically" stageable (not enough to trigger a full status refresh that would force the user to re-select). No content-based confirmation (e.g., hash of hunk text) currently exists in `formatPatch`/`applyPatchToIndex`/`DiffSelection` to catch this, so an existing guard does not stop the path once triggered.

### Recommendation
Bind the `DiffSelection` (or the patch-generation step) to the actual diff content it was computed against — e.g., include the hunk headers or a hash of the diff text alongside the selection, and have `applyPatchToIndex`/`formatPatch` verify the freshly-fetched diff's hunk boundaries/line content match before blindly reusing the stored numeric selection. If they don't match, force a refresh and require the user to re-confirm their selection rather than silently applying stale indices to new content.

### Proof of Concept
Conceptual sequence (exact reproduction requires a live Desktop session/background script and was not executed as part of this static review):
1. Open a repository with a modified file containing multiple hunks; in the Changes view, select only specific added lines (e.g., lines 10–12) via the diff gutter, producing a `DiffSelection` with divergent indices `{10,11,12}`.
2. Before clicking "Commit", have a process (build tool/watch script/editor autosave triggered by content in the cloned repo) insert or remove lines earlier in the file, shifting the hunk's `unifiedDiffStart` so that indices `{10,11,12}` now correspond to different lines than the ones originally selected.
3. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff, and `formatPatch` (`app/src/lib/patch-formatter.ts:129`) applies `file.selection.isSelected(absoluteIndex)` against the new hunk layout, staging/committing lines the user never reviewed or approved as part of that commit.

Note: due to indexing limits I could not fully trace `getWorkingDirectoryDiff`'s complete implementation in `app/src/lib/git/diff.ts` (only partial content was retrievable), so I cannot confirm whether any hash/staleness check exists deeper in that function. If such a check exists, it would need to be examined to determine whether it fully closes this gap; based on all reachable code (`apply.ts`, `patch-formatter.ts`, `diff-selection.ts`), no such check is applied before `formatPatch` uses the stored indices. A full Devin session with repository access would be needed to verify this definitively and to attempt a live reproduction.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
