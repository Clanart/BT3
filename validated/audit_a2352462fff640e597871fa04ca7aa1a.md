### `ThresholdKeys::read` accepts malformed constant-interpolation keys, causing inconsistent key policy enforcement - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts a serialized `Interpolation::Constant` whose coefficient vector length is attacker-controlled only through the serialized `n` field. `ThresholdKeys::new` enforces that constant interpolation is used only when `t == n`, but it never validates the mathematical policy of the supplied coefficients: it does not require the coefficient vector to implement a nonzero coefficient for every participant, nor does it reject all-zero coefficients.

An untrusted key blob can therefore deserialize into an n-of-n threshold key whose public group key and per-signing shares are derived from a policy degenerate to zero authorization for some or all participants. This is an analog of insufficient policy enforcement: the byte format and constructor enforce field shape and bounds, but do not enforce that the requested threshold policy is actually cryptographically enforced.

### Finding Description
`ThresholdKeys::read` reads `n` canonical scalars whenever the interpolation tag is `0` and passes them as `Interpolation::Constant`. `ThresholdKeys::new` checks only that `t == n`, then derives `group_key` by multiplying each of the first `t` verification shares by its corresponding coefficient. There is no check that coefficients are nonzero or that the coefficient policy cannot collapse a participant's effective share to zero.

### Impact Explanation
A participant or integrator that accepts serialized `ThresholdKeys` from untrusted bytes can receive keys which appear to describe an n-of-n policy but have an effective authorization policy weaker than requested. If a coefficient is zero, the corresponding participant's signing share contributes nothing to the claimed group key. If all coefficients are zero, the group key is driven only by the offset path rather than any participant secret shares.

This can produce “funds received that are not spendable” or unexpectedly spendable under an unintended policy depending on how the surrounding system uses the resulting `group_key` and views. The concrete accepted impact classes include an incorrect verifier/key policy and funds credited to a key whose intended threshold authorization is not actually represented by the shares.

### Likelihood Explanation
Exploitation requires an application to deserialize and trust attacker-controlled `ThresholdKeys` bytes. `ThresholdKeys::read` is explicitly exposed for untrusted bytes and uses strict canonical scalar/point parsing, but does not semantically validate the interpolation policy. A malicious sender can freely choose `t == n`, supply arbitrary canonical coefficients and public verification shares, and pass all current structural checks.

The issue is not a probabilistic cryptographic bypass: malformed policy bytes are accepted deterministically. Its practical severity is bounded by the number of integrations accepting serialized threshold keys as trusted state.

### Recommendation
For `Interpolation::Constant`, `ThresholdKeys::new` should enforce the full expected invariant:

- Require `coefficients.len() == usize::from(params.n())`.
- Reject zero coefficients unless a zero coefficient is an explicitly supported and documented policy.
- Prefer making constant interpolation construction private or internally generated where possible.
- Add a regression test that deserializes `Interpolation::Constant(vec![0, ...])` and rejects it.
- Consider authenticating serialized `ThresholdKeys`, since they contain both secret material and authorization policy parameters.

### Proof of Concept
Construct a serialized `ThresholdKeys` for a supported curve with:

1. `t = n = 2`.
2. `i = 1`.
3. Interpolation tag `0`.
4. Constant coefficients `[0, 1]`.
5. Any canonical secret share and two canonical verification shares.

`ThresholdKeys::read` will pass the coefficient vector to `ThresholdKeys::new`; because `t == n`, the constant-interpolation check succeeds, and the first participant's coefficient is used to scale its share. Because coefficient `0` is accepted, participant 1 contributes a zero effective share while the object still reports a 2-of-2 policy.
