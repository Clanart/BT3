### Title
Missing caller-authorization check in `CW721ERC721Pointer.transferFrom` allows any account to transfer another user's NFT - (File: `contracts/src/CW721ERC721Pointer.sol`)

### Summary
`CW721ERC721Pointer.sol` is the EVM-side ERC-721 pointer contract that lets EVM callers interact with a native CW721 NFT collection through the wasmd precompile. Its `transferFrom` implementation only checks that the `from` argument matches the on-chain token owner; it never checks that `msg.sender` is the owner, an approved spender, or an approved operator for that token. Any address can call `transferFrom(ownerAddr, attackerAddr, tokenId)` for a token it does not own and does not have approval for, and the pointer will execute a `transfer_nft` message on the underlying CW721 contract on the caller's behalf, moving the NFT away from its rightful owner.

### Finding Description
The vulnerable code: [1](#0-0) 

```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
    string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
    string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
    _execute(bytes(req));
}
```

The only check performed is that the supplied `from` parameter equals the real CW721 token owner returned by `ownerOf(tokenId)`. There is no check of `msg.sender` at all — neither `msg.sender == from`, nor `isApprovedForAll(from, msg.sender)`, nor `getApproved(tokenId) == msg.sender`. Standard ERC-721 semantics (and OpenZeppelin's `ERC721._isApprovedOrOwner`) require the caller to be the owner or an approved party; this pointer skips that check entirely. Since `_execute` performs a `delegatecall` into the wasmd precompile using `msg.sender`'s Sei address as the tx signer context (as in the analogous CW1155 pointer's `_execute`), the resulting `transfer_nft` execution on the CW721 contract is attributed to the caller, but the pointer itself imposed no restriction on who may invoke the transfer.

This directly parallels the reported PraisonAI bug class: an endpoint that correctly checks a coarse-grained condition (workspace membership / "the correct owner exists") but omits the fine-grained authorization check that only the resource's owner/approved party may act on it (delete/transfer). Here the coarse check is "does `from` equal the real owner" while the missing fine check is "is `msg.sender` allowed to move `from`'s token."

For contrast, the sibling `CW1155ERC1155Pointer.sol` contract does implement the correct authorization pattern for its state-changing burn functions: [2](#0-1) 

showing the codebase's intended design includes `msg.sender == account || isApprovedForAll(...)` guards — which is exactly what is missing from `CW721ERC721Pointer.transferFrom` (and also from its `approve`, which similarly lacks any `msg.sender` check).

### Impact Explanation
Any unprivileged EVM transaction sender that knows a CW721-pointer contract address and a `tokenId` owned by another account can call `transferFrom(victim, attacker, tokenId)` directly, with no prior approval, and steal the NFT. This is an unauthorized transfer via a CW↔EVM pointer contract, meeting the "unauthorized transfer via precompile or pointer" impact criterion — a direct, permanent loss of an owned NFT asset for any user who registers/uses a CW721 pointer.

### Likelihood Explanation
Any account controlling an EVM private key can send this transaction; it requires no special permissions, no prior interaction with the target NFT, and no governance or admin access. The only prerequisite is that a CW721 pointer exists for the target collection, which is a normal, expected way to interact with CW721 NFTs from the EVM side of Sei.

### Recommendation
Add an explicit authorization check in `transferFrom` (and `approve`) mirroring the pattern already used in `CW1155ERC1155Pointer.sol`:
```solidity
require(
    msg.sender == from || isApprovedForAll(from, msg.sender) || getApproved(tokenId) == msg.sender,
    "ERC721: caller is not token owner or approved"
);
```
before constructing and executing the `transfer_nft` message, and add a similar check for `approve` to require `msg.sender == owner || isApprovedForAll(owner, msg.sender)`.

### Proof of Concept
1. Owner mints/owns CW721 token `tokenId=1` on a collection registered with a `CW721ERC721Pointer` contract at address `P`.
2. Attacker (no approval whatsoever) calls, from their own EVM account:
   ```solidity
   P.transferFrom(ownerEvmAddr, attackerEvmAddr, 1);
   ```
3. `transferFrom` checks only `require(from == ownerOf(tokenId))`, which passes since `from == ownerEvmAddr` is correct — it does not check that `msg.sender == ownerEvmAddr` or that the attacker has any approval.
4. The pointer executes `{"transfer_nft":{"recipient":"<attacker sei addr>","token_id":"1"}}` on the underlying CW721 contract via `_execute`, and token `1` is transferred to the attacker with zero authorization from the owner.
