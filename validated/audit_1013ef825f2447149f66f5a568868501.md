### Title
Non-standard-return-value ERC20 tokens cause silent transfer failure and permanent fund lock in Tron `IntentGatewayV2.withdraw`/`onAccept` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the intent gateway re-implements its own "safe" ERC20 transfer logic using raw low-level `.call(...)` with `IERC20.transfer.selector`, instead of reusing OpenZeppelin's audited `SafeERC20.safeTransfer` — exactly as the EVM/mainline gateway does in `evm/src/apps/intentsv2/IntentsBase.sol`. This is the same anti-pattern flagged in the external report: redundant, inconsistent reimplementation of an already-solved, audited primitive instead of relying on it, and the reimplementation is unsafe.

### Finding Description
`IntentsBase._withdraw` (the canonical, audited path used by the standard EVM `IntentGatewayV2`) correctly uses `SafeERC20`: [1](#0-0) 

In contrast, the Tron `IntentGatewayV2.withdraw` and its `onAccept`/`SweepDust` branch re-implement token transfer manually, checking only that the low-level `.call` itself did not revert (`success`), and never inspecting the ABI-decoded boolean return value that the ERC20 standard mandates for `transfer`: [2](#0-1) [3](#0-2) 

For any ERC20 token that returns `false` on a failed transfer instead of reverting (a well-known non-standard-but-common pattern, e.g. tokens following the original ERC20 spec loosely, or ones with paused/blacklist checks that return `false`), the low-level `.call` completes successfully (`success == true`) even though no value was moved, because the check only validates call execution, not the encoded return data. `SafeERC20.safeTransfer` specifically guards against this by checking `returndata.length == 0 || abi.decode(returndata, (bool))`.

Critically, in `withdraw`, escrow accounting is mutated unconditionally right after the (falsely-successful) transfer call: [4](#0-3) 
`_filled[body.commitment] = beneficiary;` is set at the top of the function before any transfer occurs, and `_orders[body.commitment][token] -= amount;` executes right after the low-level call regardless of the token's real transfer outcome.

### Impact Explanation
Once `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, the order is permanently considered settled from the contract's perspective. If the underlying token silently fails the transfer (returns `false`), the escrowed tokens remain physically locked in the `IntentGatewayV2` contract with no accounting path left to reclaim them — `UnknownOrder()` will now revert any further attempt to withdraw that (commitment, token) pair since escrow appears to be zero, while the tokens are still sitting in the contract balance. This is a direct loss/permanent-lock of bridged/escrowed funds belonging to the rightful beneficiary (solver on fill, user on refund), which falls squarely under the "stealing or loss of funds" and "funds must move exactly once to the rightful beneficiary" impact categories for intent settlement.

### Likelihood Explanation
This does not require a malicious relayer, prover, or governance actor — it only requires that one of the arbitrary ERC20 tokens used as an order's `input`/`output`/fee token exhibits the well-documented non-reverting-`false`-return behavior. Given `IntentGatewayV2` accepts arbitrary attacker/solver-supplied token addresses for order inputs and outputs (as shown by the fee-on-transfer token test harness already present in the repo), an order can be placed or filled using such a token, and once it reaches `withdraw`/`onAccept`, the accounting silently finalizes while the transfer never lands — a state-vs-reality mismatch reachable through the normal public order lifecycle.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw` and the `SweepDust`/dust-sweep branch of `onAccept`) with `SafeERC20.safeTransfer`/`safeTransferFrom`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This eliminates the redundant, unaudited reimplementation and ensures both the syntactic call success and the ERC20-mandated boolean return are checked before escrow state is mutated.

### Proof of Concept
1. Deploy a minimal ERC20-like token whose `transfer` function returns `false` (without reverting) whenever the recipient is blacklisted/paused, and register it as an input token for an order on the Tron `IntentGatewayV2`.
2. Place and fill (or cancel) the order so that `onAccept`/`withdraw` is invoked with that token in `body.tokens`.
3. Have the token's internal condition cause `transfer` to return `false` for the beneficiary at settlement time (e.g., temporarily blacklist the beneficiary or trigger the token's failure condition).
4. Observe: `success` from the low-level `.call` is `true` (the call executed without reverting), so `TransferFailed()` is never triggered; `_orders[commitment][token] -= amount` executes and `_filled[commitment]` is set, finalizing the order.
5. Confirm the beneficiary's token balance did not increase, while the contract's token balance still holds the escrowed amount and `_orders[commitment][token]` is now zero/reduced — the funds are stuck with no valid withdrawal path (`UnknownOrder()` reverts any retry).

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                if (!success) revert TransferFailed();

                ++i;
            }
