### Title
Attacker can flash-stake and force-harvest to steal a disproportionate share of newly distributed rewards from existing WombatStaking pool depositors - ([File: rewards/BaseRewardPoolV2.sol], [File: wombat/WombatStaking.sol])

### Summary
`BaseRewardPoolV2` bakes newly received rewards into `rewardPerTokenStored` instantly, using the *current* `totalStaked()` as denominator, instead of streaming rewards over time. Combined with the fact that `WombatStaking.harvest()` is a permissionless function that anyone can call at will, an attacker can stake into a pool and immediately force a harvest, capturing a share of newly-realized Wombat rewards proportional to their fresh deposit, then withdraw — diluting/stealing yield that should accrue to long-term, genuine depositors. This is the same underlying bug class as the MuteBond finding: a state variable that determines payout (there, bond price; here, `rewardPerTokenStored`) can be manipulated in the attacker's favor by timing a transaction around another state-changing action (there, front-running a purchase; here, front-running/forcing a reward booking) at the expense of another legitimate user's expected payout.

### Finding Description
`_provisionReward` in `BaseRewardPoolV2` updates the global reward index immediately and irreversibly at the moment new rewards are queued: [1](#0-0) 

The denominator used is the live `totalStaked()`, which simply reads the caller's current balance recorded in `MasterMagpie`: [2](#0-1) 

A user's earned amount is computed from the delta between the current `rewardPerToken` and the value recorded for that user at their last interaction (`userRewardPerTokenPaid`), which is set the moment they stake: [3](#0-2) 

Crucially, `WombatStaking.harvest()` is a completely permissionless, non-privileged function that any wallet can call at any time to pull pending WOM rewards from the underlying Wombat pool into the `BaseRewardPoolV2` via `queueNewRewards`: [4](#0-3) 

Because there is no time-weighting/streaming of rewards and no minimum holding period, an attacker can:
1. Deposit into a `WombatPoolHelper`/`WombatStaking` pool, which stakes them in `MasterMagpie` (registering their balance for `totalStaked()`/`balanceOf()`).
2. Immediately call the permissionless `harvest()` function to force any pending Wombat yield to be booked into `rewardPerTokenStored` while their large fresh stake is counted in the denominator.
3. Call `getReward`/`getRewards` to claim their share of the just-booked reward, then withdraw their principal.

This is functionally the same root cause pattern as the referenced report: a payout-determining value (`bondPrice` there, `rewardPerTokenStored` here) is settled atomically based on state that an attacker can manipulate with a well-timed transaction, at the expense of users who were honestly staked/waiting beforehand.

### Impact Explanation
Legitimate long-term stakers see their share of freshly harvested yield diluted because the harvested reward is divided by a `totalStaked()` inflated by the attacker's momentary stake, while the attacker — who contributed zero staking duration — extracts a proportional cut of that same yield. This constitutes theft of unclaimed yield from genuine stakers, reachable purely by an ordinary wallet calling public, unprivileged functions (`deposit`, `harvest`, `getReward`, `withdraw`).

### Likelihood Explanation
High. `harvest()` requires no special permission beyond the pool being active, and deposit/withdraw in `WombatPoolHelper`/`WombatStaking` are open to any wallet. No cooldown, vesting, or minimum staking duration gates entry into the reward-sharing denominator, making the attack executable atomically within a single block (deposit → harvest → claim → withdraw), similar in spirit to a flash-loan/sandwich attack, though it does not strictly require flash capital if the attacker is willing to hold capital briefly.

### Recommendation
Stream rewards over time (e.g., Synthetix-style `rewardRate`/`periodFinish` accrual) instead of instantly booking the full reward into `rewardPerTokenStored` based on the instantaneous `totalStaked()`. Alternatively, enforce a minimum staking duration before a user's balance counts toward `totalStaked()` for reward-booking purposes, or restrict/rate-limit who/how often `harvest()` can be invoked in immediate succession after a deposit.

### Proof of Concept
Conceptual PoC (matches the reachable path validated above):
1. Attacker calls `WombatPoolHelper.deposit(amount, minLiquidity)` → internally calls `WombatStaking.deposit` (triggers harvest #1 with old, smaller `totalStaked()`) then registers the attacker's stake via `MasterMagpie.depositFor` [5](#0-4) .
2. Attacker immediately calls `WombatStaking.harvest(lpToken)` [4](#0-3) , which pulls any pending Wombat rewards and calls `queueNewRewards`, booking `rewardPerTokenStored` using `totalStaked()` that now includes the attacker's large fresh stake [6](#0-5) .
3. Attacker calls `getReward`/`getRewards` on the rewarder to realize their share of the newly booked reward [7](#0-6) , then withdraws their principal via `WombatPoolHelper.withdraw`.

I was not able to fully trace `_toMasterWomAndSendReward`'s internal implementation (only its call sites), so I cannot 100% confirm whether an ordinary deposit alone (without the follow-up explicit `harvest()` call) already exposes the attacker to the newly-harvested reward in the same transaction; the explicit permissionless `harvest()` function, however, independently and unambiguously enables this attack regardless of that detail.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
