### Title
Unauthenticated denial of service via panic on identity point in BIP-340 `Hram` / `x_only` helpers - (File: networks/bitcoin/src/crypto.rs)

### Summary
The octokit advisory is a bug class where an error path was left unhandled, letting an attacker crash the process with a crafted request. Serai's analog is a panic — not a returned error — when elliptic-curve points that can be attacker-influenced deserialize to (or sum to) the point at infinity and are then fed to the BIP-340 helpers `x` / `x_only` / `Hram::hram` in `networks/bitcoin/src/crypto.rs`, which call `.expect("point at infinity")` instead of returning `Err`. [1](#0-0) 

### Finding Description
`x(key)` calls `key.to_encoded_point(true)` and then `encoded.x().expect("point at infinity")`; `x_only` does `XOnlyPublicKey::from_slice(&x(key)).expect(...)` [1](#0-0) . `Hram::hram` invokes `x(R)` and `x(A)` unconditionally [2](#0-1) , and its own documentation admits: "If either `R` or `A` is the point at infinity, this will panic" [3](#0-2) . `hram` is invoked inside `frost::algorithm::Schnorr`'s `sign_share`/`verify`, reached from `AlgorithmSignMachine::sign` (`self.params.algorithm.sign_share(&view, &Rs, nonces, msg)`) and `AlgorithmSignatureMachine::complete` (`self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum)`) [4](#0-3) [5](#0-4) .

The attacker-controlled angle is the group key `A`. `ThresholdKeys::read` deserializes `verification_shares` using `<C as Ciphersuite>::read_G` — the permissive ciphersuite reader, not `frost::Curve::read_G`, which is the only reader that rejects identity points ("Err(io::Error::other(\"identity point\"))") [6](#0-5) [7](#0-6) . The group key is then computed by interpolating verification shares for participants `1..=t` in `ThresholdKeys::new`. `ThresholdKeys::read` is explicitly listed as an untrusted-bytes entry point, so a peer that supplies crafted `ThresholdKeys` bytes whose interpolated `group_key` is the identity (e.g., all verification shares set to identity, which the ciphersuite `read_G` accepts as a valid encoding) produces a `ThresholdKeys` object that passes deserialization but poisons every subsequent signing operation: `sign` and `complete` call `hram(R, A = identity, msg)` and panic inside `x()`.

A second, narrower trigger is `R`: `Rs` are sums of preprocess nonce commitments weighted by binding factors. Identity commitments are rejected by `Curve::read_G`, but nothing in `B.nonces`/aggregate assembly checks the *sum* for identity, so a crafted preprocess set could in principle yield an identity aggregate nonce — the code comments concede this is only "negligible probability" for honest inputs, not structurally prevented [8](#0-7) .

### Impact Explanation
An unauthenticated party who can feed bytes to `ThresholdKeys::read` (key-sync, key-rotation, or recovery data) or preprocesses to `read_preprocess` and then cause a `sign`/`complete` call will abort the node process with a panic rather than receive an `io::Error`/`FrostError`. This is a per-message remote crash of the threshold-signing processor — the same availability impact as the octokit bug (CVSS A:H). Note one caveat I could not fully verify in this pass: whether `ThresholdKeys::new` independently rejects an identity `group_key` — if it does, the reachable surface narrows to the identity-`R` path via crafted preprocess nonce sums, which requires grinding the binding factor and is much weaker.

### Likelihood Explanation
Deserializing a `ThresholdKeys` blob with all-identity verification shares is trivial for an attacker supplying the bytes; serialization is deterministic (`secret_share` plus `n` group elements). The only uncertainty is whether `ThresholdParams::new`/`ThresholdKeys::new` validates the resulting group key — the read path itself performs no identity check on the shares [9](#0-8) . The identity-R variant is low likelihood because `rho` binds over all commitments.

### Recommendation
- In `ThresholdKeys::new`/`ThresholdKeys::read`, reject any identity verification share and a resulting identity `group_key` (use the identity-checking `Curve::read_G` semantics or explicit `is_identity` checks) in `crypto/dkg/src/lib.rs` [6](#0-5) .
- In `networks/bitcoin/src/crypto.rs`, make `x`/`x_only`/`Hram::hram` total: return a neutral/attacker-detectable result or propagate an error through `Algorithm::verify`/`sign_share` instead of `expect` [1](#0-0) .
- In `crypto/frost/src/sign.rs`, after computing `Rs`, reject identity aggregate nonces before calling `algorithm.verify`/`sign_share` [10](#0-9) .

### Proof of Concept
1. Construct `ThresholdKeys::<Secp256k1>` bytes: valid `ID`, `t`,`n`,`i` such that `ThresholdParams::new` accepts them, `Interpolation::Lagrange` (tag `1`), any `secret_share`, then `n` copies of the 33-byte compressed identity point (`0x00…00` / encoded infinity as accepted by `Ciphersuite::read_G`).
2. Feed to `ThresholdKeys::read` → succeeds if `new` doesn't check the group key.
3. Build `AlgorithmMachine::new(bitcoin::crypto::Schnorr::new(), keys)`, call `preprocess`, feed any peers' preprocesses, and call `sign(commitments, msg)`.
4. `sign` → `Schnorr::sign_share` → `Hram::hram(R, A = group_key = identity, msg)` → `x(A)` → `expect("point at infinity")` panics, aborting the process — mirroring the octokit uncaught-exception kill.
