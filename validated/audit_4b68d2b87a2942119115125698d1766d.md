## Title
Reentrant escrow drain via checks-effects-interactions violation in the Tron IntentGatewayV2 `withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The external report's core defect is that a value used to authorize/inform a fund-moving action (`amount`) was handled incorrectly relative to the actual transfer, letting a transaction move value the user/verifier did not properly account for. The local Hyperbridge analog is in the **Tron** build of `IntentGatewayV2`'s escrow-release routine: unlike the canonical EVM implementation, it performs the outbound token/native transfer to `beneficiary` **before** decrementing the escrow ledger `_orders[commitment][token]`, violating checks-effects-interactions and leaving the escrow accounting value stale during an external call.

## Finding Description
The canonical escrow-release logic in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` decrements the escrow mapping **before** making the external transfer call: [1](#0-0) 

The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, reverses this order — it calls out to `beneficiary` (native `.call{value: amount}("")` or ERC20 `token.call(transfer(...))`) **first**, and only afterward subtracts `amount` from `_orders[body.commitment][token]`: [2](#0-1) 

`beneficiary` in this function is directly attacker-influenced: it comes from the `WithdrawalRequest.beneficiary` field decoded from either a `RedeemEscrow` message (the solver/filler address that filled the order) or a `RefundEscrow` message (the order's original user) — both are addresses an ordinary, unprivileged user can set (`placeOrder`, `fillOrder`, `cancelOrder`), and both flow into `onAccept`/`onGetResponse` which call `withdraw`: [3](#0-2) [4](#0-3) 

The only guard before the transfer is `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — it checks for a nonzero balance, not `>= amount`, and critically the ledger update that should make the invariant hold (escrow can only be spent once) happens **after** control has already left the contract via the external call: [5](#0-4) 

If `beneficiary` is a contract with a fallback/`receive` (for the native-token branch) or a malicious/non-standard token contract that calls back into the gateway before returning, that reentrant call can reach the same `withdraw()` path again for the same commitment/token while `_orders[commitment][token]` still reflects the pre-transfer balance, allowing more than the escrowed amount to be paid out. This is exactly the disclosed-amount/actual-amount mismatch class from the seed report, translated to a fund-custody context: the value that should gate the transfer (`_orders[...]`) is stale at the moment the transfer executes.

## Impact Explanation
This falls squarely within the accepted impact categories: **stealing or loss of funds** and **double-claim/double-settlement** of bridge escrow. A successful reentrant call drains escrowed input tokens or accumulated `TRANSACTION_FEES` beyond the amount legitimately owed to the beneficiary, at the expense of the protocol/other order participants — matching "Bridged assets... must move exactly once and only to the rightful beneficiary and amount."

## Likelihood Explanation
The attack requires only a permissionless, unprivileged path: any user can place an order and later act as (or route through) the filler/beneficiary address that receives the `RedeemEscrow`/`RefundEscrow` payout — no malicious relayer, prover, or governance actor is needed. The remaining question is whether the ISMP host's message-delivery model allows a second `onAccept`/`onGetResponse` invocation to be triggered mid-reentrancy for the same or a related commitment before the first call returns; I was not able to fully verify this cross-call reentrancy reachability within the available context (the host dispatch/delivery guarantees for the Tron deployment specifically were not inspected). What is concretely and locally provable is the checks-effects-interactions violation itself — a direct code-level regression compared to the hardened `IntentsBase._withdraw` used elsewhere in the same protocol — which is the necessary precondition for the drain.

## Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match `IntentsBase._withdraw`: read `escrowed = _orders[commitment][token]`, revert if `escrowed < amount`, write `_orders[commitment][token] = escrowed - amount` **before** performing the native call or token transfer, for every token in the loop. Additionally, add a reentrancy guard to `withdraw`/`onAccept`/`onGetResponse` consistent with `IntentGatewayV2.sol`'s `nonReentrant` usage on `fillOrder`.

## Proof of Concept
Conceptual sequence (exact reentrancy trigger point not independently confirmed against the Tron host's delivery semantics, but the vulnerable ordering is directly verifiable in the cited code):
1. User places an order on the Tron gateway escrowing token `T`, amount `A`.
2. Order is filled/cancelled such that a `WithdrawalRequest{ commitment, tokens: [{T, A}], beneficiary: attackerContract }` is delivered to `onAccept`/`onGetResponse`.
3. `withdraw()` checks `_orders[commitment][T] != 0` (true), then calls `attackerContract` via `token.call(transfer(...))` or native `.call{value: A}("")`.
4. `attackerContract`'s callback re-enters a path that invokes `withdraw()` again for the same `commitment`/`T` before step 3's caller returns and decrements `_orders[commitment][T]`.
5. The second invocation still sees `_orders[commitment][T] == A` (unchanged), passes the same `!= 0` check, and transfers `A` again — the escrow is paid out twice for a single deposit. [6](#0-5)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
