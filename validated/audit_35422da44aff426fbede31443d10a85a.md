### Title
Full relayer/transaction fee released to solver on a same-chain partial fill that transitions the order to `finalize=true` on the last fill, while a small earlier fill can trigger fee release logic tied to `finalize`, not fill proportion - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The Astaria bug paid the strategist a reward computed against the full outstanding lien amount (`stack.point.amount`) instead of the amount actually paid, letting a tiny payment trigger a reward sized to the whole position. The Hyperbridge analog is in `_withdraw()`: the escrowed `TRANSACTION_FEES` bucket (`order.fees`, collected in full at order placement) is released to whichever address happens to be `beneficiary` on the fill that sets `finalize = true` — regardless of how large or small that particular fill actually was relative to the whole order.

### Finding Description
`_withdraw` in [1](#0-0)  releases the entire accumulated `_orders[commitment][TRANSACTION_FEES]` balance whenever `finalize == true`, in a single lump sum, to the current call's `beneficiary`:
```
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
}
```
`finalize` is computed in `_fillSameChain` as `isFullyFilled` [2](#0-1) , i.e. whichever solver happens to be the one whose fill makes `totalRequired == amountFilled` for every output pair. For orders that support partial fills (same-chain orders), the escrowed input tokens are split proportionally to `fillAmount` across solvers, but the entire `order.fees` payment — sized to cover the *whole* order's relayer/dispatch cost — is captured wholesale by whichever solver happens to land the last (possibly tiny) fill, not distributed proportionally to each solver's contribution. A solver can watch the mempool/partial-fill state, wait until an order is nearly filled by other solvers, then submit a minimal remaining fill just to trigger `isFullyFilled = true` and collect the full `order.fees` amount that was meant to compensate proportional work/dispatch costs.

This mirrors the root cause in the Astaria report exactly: a reward/fee quantity that should track the proportion of work/payment actually contributed by the specific actor is instead paid in full based on a coarse binary trigger (`finalize`/lien full), letting the last small contributor collect a reward sized for the entire transaction.

### Impact Explanation
This causes an unfair/unintended reallocation of `order.fees` funds among solvers within the Hyperbridge IntentGateway (a bridge/custody contract holding escrowed funds). It doesn't (from what I could verify) let an attacker mint funds from nowhere — it redirects the fixed fee pool set aside for relayer/dispatch costs to the final contributor. Because this a fee/reward accounting issue is directly analogous to the accepted M-08 Astaria finding, but I could not confirm from local code/docs whether `order.fees` is meant to be split proportionally per partial fill (the docs table only shows fees paid "At order placement" by the "User", without specifying a proportional split rule for partial fills) — so the severity depends on the intended fee semantics that I was unable to fully confirm from available files.

### Likelihood Explanation
Any unprivileged solver participating in partial fills of a same-chain order can trigger this by choosing when to submit the final (possibly minimal) fill; no relayer, admin, or privileged role is required.

### Recommendation
Prorate `TRANSACTION_FEES` release across all solvers who contributed to a partially-filled order (e.g., proportional to `fillAmount`/`totalRequired` per solver, tracked incrementally), rather than paying the whole bucket to whichever fill happens to set `finalize = true`.

### Proof of Concept
1. User places a same-chain order with `order.fees = F` (escrowed into `_orders[commitment][TRANSACTION_FEES]`).
2. Solver A fills 99% of the order via `fillOrder` → proportional input released to A, `isFullyFilled = false`, no fee release (see `_fillSameChain`, [3](#0-2) ).
3. Solver B fills the remaining 1% → `isFullyFilled = true` → `_withdraw(..., finalize=true)` is called with `beneficiary = B` → the **entire** fee `F` is transferred to B [4](#0-3) , even though B contributed only 1% of the fill.

**Uncertainty note:** I could not locate documentation or tests in the indexed portion of the repo that explicitly define the intended per-solver fee-split policy for partial fills (only the placement-time fee table in `docs/content/developers/evm/intent-gateway/overview.mdx` was found, which does not address proration). This limits my confidence that this is a *bug* versus intended behavior — a Devin session with full repository access (including any fee-distribution design docs or off-chain solver agreements) would be needed to confirm the intended split policy before treating this as confirmed.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
