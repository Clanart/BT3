### Title
Symlink-following write in `.gitignore` persistence allows arbitrary file overwrite from a cloned repository - (File: `app/src/lib/git/gitignore.ts`)

### Summary
`saveGitIgnore` (and its caller `appendIgnoreRule`/`appendIgnoreFile`) writes to `Path.join(repository.path, '.gitignore')` using Node's `fs/promises` `writeFile`, which follows symlinks by default (no `O_NOFOLLOW`/`lstat` check). [1](#0-0) 
Git can track a symlink named `.gitignore` inside a repository. If a victim clones/checks out an attacker-controlled repository containing a tracked symlink `.gitignore -> <sensitive path>`, and later performs the ordinary Desktop action of ignoring a file (via `appendIgnoreFile`) or editing/saving the ignore list in Repository Settings (`saveGitIgnore`), Desktop will write attacker-influenced content through that symlink to the target path, rather than to the repository's `.gitignore`. [2](#0-1) [3](#0-2) 

### Finding Description
`saveGitIgnore` builds the ignore file path by simple string join and calls `writeFile(ignorePath, fileContents)` without ever checking whether `.gitignore` is a symlink pointing outside the repository: [4](#0-3) 

`appendIgnoreRule`/`appendIgnoreFile` build on top of `saveGitIgnore`, and are invoked from the "Ignore file" context-menu action in the Changes sidebar as well as from the Repository Settings "Git Ignore" tab (`onSubmit` in `repository-settings.tsx`, gated only on `ignoreTextHasChanged`): [5](#0-4) [2](#0-1) 

This mirrors the class of bug in CVE-2022-32207: a program writes to a well-known filename in a way that follows an existing filesystem object (symlink/special file) instead of verifying it is a regular file it owns before overwriting it. In curl's case the broken invariant was "preserve/verify the target before rewriting a cookie/HSTS/altsvc database"; here the broken invariant is "verify `.gitignore` is a plain file inside the repository before writing to it." Git itself will happily clone and check out a tracked symlink entry named `.gitignore` (this is standard, allowed Git functionality — no corrupt/invalid ref or index entry is required), so an attacker only needs to publish or get a victim to clone/fetch a repository containing:
```
lrwxrwxrwx  .gitignore -> /home/victim/.ssh/authorized_keys
```
Desktop performs no `lstat`/`readlink` check anywhere in the read/write path (`readGitIgnoreAtRoot`, `saveGitIgnore`, `appendIgnoreRule`) to detect or reject this before calling `FS.writeFile`.

### Impact Explanation
This allows an attacker who controls a cloned/fetched repository to redirect a Desktop-initiated file write to an arbitrary path writable by the victim's user account (subject to normal OS file permissions, no privilege escalation required, and no admin/local access needed beyond cloning the repo). Realistic escalation targets include:
- `~/.ssh/authorized_keys` (extend keys attacker controls, if it exists and is user-writable) — enabling remote access,
- shell startup files (`~/.bashrc`, `~/.zshrc`, `~/.profile`) — enabling arbitrary code execution on next shell start,
- other application config files.

The write is not a full "arbitrary content of the attacker's choosing" (it is `.gitignore`-shaped content built by `formatGitIgnoreContents`, generally line-based patterns), which does constrain what can be usefully injected — the attacker can only append line-oriented, `\n`/`\r\n`-terminated text (the ignore pattern plus optional escaping), which is a meaningful practical limitation for exploitation into e.g. `authorized_keys` (a single-line pattern could still be a valid SSH public key entry) or a shell rc file (comment lines are easy; arbitrary shell commands are also just text lines, so RCE via `.bashrc`/`.zshrc` injection is plausible).

### Likelihood Explanation
Requires the victim to (a) clone/fetch a malicious repository containing a tracked `.gitignore` symlink, and (b) perform an ordinary, common Desktop action afterward — either right-click "Ignore file" on any untracked file in the Changes list, or open Repository Settings → Git Ignore tab and click Save after any edit. Both are everyday user actions that don't require unusual steps, elevated privileges, or prior compromise. The main uncertainty is whether the target path (e.g. `authorized_keys`) already exists and is writable by the user — this is common on developer machines using SSH for git remotes.

### Recommendation
Before writing to `.gitignore` (in `saveGitIgnore`, `appendIgnoreRule`, and `readGitIgnoreAtRoot`), `lstat` the path and refuse to read/write through it if it is a symlink (or any non-regular file) that resolves outside `repository.path`. Alternatively, always write to a temp file inside the repository and atomically `rename` it over `.gitignore` only after confirming (via `lstat`) that any existing `.gitignore` is a regular file, mirroring the fix approach suggested in the original curl report (only reuse/overwrite an existing path if it is a plain regular file owned appropriately).

### Proof of Concept
1. Attacker creates and publishes a repository containing a tracked symlink: `git symlink-add.sh` equivalent — `ln -s /home/victim/.bashrc .gitignore && git add .gitignore && git commit -m x` (from a Linux/macOS attacker checkout; symlinks are stored as blobs with mode `120000`).
2. Victim clones this repository with GitHub Desktop (`Clone repository` from URL) — Desktop checks out the tree, materializing the on-disk symlink `.gitignore -> ~/.bashrc`. [6](#0-5) 
3. Victim makes some unrelated change to a file in the working directory, right-clicks the new untracked file in the Changes sidebar, and selects "Ignore file" — this calls `dispatcher.appendIgnoreFile` → `appStore._appendIgnoreFile` → `appendIgnoreFile`/`appendIgnoreRule` → `saveGitIgnore`. [7](#0-6) [5](#0-4) 
4. `saveGitIgnore` calls `writeFile(ignorePath, fileContents)` where `ignorePath` is the on-disk symlink; Node follows it and writes the new ignore-pattern content into `~/.bashrc`, silently appending attacker-influenced content to a file the attacker never had direct access to. [8](#0-7) 
5. On the victim's next shell session, the appended `.bashrc` content executes.

```typescript
export async function readGitIgnoreAtRoot(
  repository: Repository
): Promise<string | null> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  return new Promise<string | null>((resolve, reject) => {
    FS.readFile(ignorePath, 'utf8', (err, data) => {
      if (err) {
        if (err.code === 'ENOENT') {
          resolve(null)
        } else {
          reject(err)
        }
      } else {
        resolve(data)
      }
    })
  })
}
```

```typescript
export async function saveGitIgnore(
  repository: Repository,
  text: string
): Promise<void> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  if (text === '') {
    return new Promise<void>((resolve, reject) => {
      FS.unlink(ignorePath, err => {
        if (err) {
          reject(err)
        } else {
          resolve()
        }
      })
    })
  }

  const fileContents = await formatGitIgnoreContents(text, repository)
  await writeFile(ignorePath, fileContents)
```

```typescript
/** Add the given pattern or patterns to the root gitignore file */
export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}
```
