## Title
Path traversal via symlinked working-directory entries in "Reveal in Finder / Explorer" and "Open in External Editor" - ([File: app/src/lib/app-shell.ts])

### Summary
GitHub Desktop already hardened one file-path join against directory-traversal/symlink escape — `resolveWithin()` in [1](#0-0)  resolves a repo-relative path and validates via `realpath()` that the result still lives under the repository root, and it's used for the `x-github-client://openRepo` deep-link `filepath` argument in [2](#0-1) . However, several other call sites that join a git-status/diff-derived, attacker-influenced relative path onto `repository.path` were never updated to use this guard — they do a raw `Path.join(repository.path, path)` and hand the result straight to the OS shell.

### Finding Description
The unguarded pattern appears in:
- `revealInFileManager()`, whose own doc comment warns "Do not use this method with non-validated paths" yet does exactly `Path.join(repository.path, path)` with no validation: [3](#0-2) 
- `onOpenInExternalEditor` in the main app component: [4](#0-3) 
- The commit/PR file context menus, which build `fullPath = Path.join(repository.path, file.path)` and pass it to `revealInFileManager`, `openInExternalEditor`, and `openFile` (which does `shell.openExternal('file://'+fullPath)`): [5](#0-4) [6](#0-5) 

The `path`/`file.path` values in every one of these call sites originate from `WorkingDirectoryFileChange`/`CommittedFileChange` objects built from `git status`/`git diff` output — i.e., from the contents of a cloned or fetched repository, which is attacker-controlled. Git itself refuses to store literal `..` path *components* in a tree, so pure `../` segments can't come through, but a tracked/untracked **symlink** committed inside the repository (e.g. a directory entry `evil -> /` or `evil -> C:\`) is fully permitted content. When status/diff reports a nested path underneath that symlinked directory (e.g. `evil/Users/victim/.ssh/id_rsa`), `Path.join(repository.path, path)` resolves lexically to a path that still starts with `repository.path`, but the OS will actually traverse through the symlink at open time and land the operation outside the repository — exactly the same class of bug as `resolveWithin`'s own symlink-escape regression test: [7](#0-6) . None of the vulnerable call sites perform the `realpath`-based containment check that `resolveWithin` performs, so this guard is bypassed.

### Impact Explanation
An attacker who gets a victim to clone/fetch a crafted repository containing a symlinked directory can cause GitHub Desktop's "Reveal in Finder/Explorer", "Open in External Editor", or "Open with default program" actions (all one context-menu click away on a listed changed file) to operate on a file outside the repository working tree — reading/exposing or launching an arbitrary file chosen by the attacker (e.g. exfiltrating an SSH key path via Finder reveal, or invoking the OS default handler / user's external editor against `~/.ssh/id_rsa`, `.aws/credentials`, etc.). This satisfies the "attacker controls a cloned/fetched repository … result is file read outside the repo" criterion.

### Likelihood Explanation
Requires only a normal clone/fetch of a malicious repo followed by one ordinary user action (right-click → Reveal/Open, or double-click a changed file) — no admin rights, no pre-existing malware, no unnatural steps. Symlinks inside a git repo are a standard, fully supported git object type, so crafting the payload requires no exotic tooling.

### Recommendation
Route every one of these paths through `resolveWithin(repository.path, path)` (or `win32`/`posix` variants as appropriate) before calling `shell.showItemInFolder`, `dispatcher.openInExternalEditor`, or `shell.openExternal('file://...')`, mirroring the fix already applied in `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1963`). If resolution returns `null`, refuse the action and log/report an error instead of silently operating outside the repo.

### Proof of Concept
1. Create a repository containing a symlink `link -> /` (POSIX) or `link -> C:\` (Windows), commit it, and add an untracked/modified file such that `git status` reports an entry like `link/Users/victim/.ssh/id_rsa`.
2. Victim clones this repository in GitHub Desktop.
3. In the Changes list, right-click the entry and choose "Reveal in Finder" (or "Open in External Editor" / double-click in the commit/PR file list).
4. `revealInFileManager`/`onOpenInExternalEditor` computes `Path.join(repository.path, 'link/Users/victim/.ssh/id_rsa')`; the OS resolves the `link` symlink at access time, and Finder/Explorer/the editor opens `/Users/victim/.ssh/id_rsa`, outside the cloned repository — with no `resolveWithin` check ever having rejected it.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
