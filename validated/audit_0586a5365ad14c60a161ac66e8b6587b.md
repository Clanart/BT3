### Title
Cross-chain `RedeemEscrow` beneficiary is set to `msg.sender` verbatim, permanently locking escrowed funds when the filler is a contract wallet - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_fillCrossChain` encodes the filler's raw address (`msg.sender`) as the `beneficiary` of the `RedeemEscrow` message that is dispatched to the **source** chain via Hyperbridge. `_withdraw` on the source chain then blindly transfers the escrowed input tokens (and accumulated fees) to that same address interpreted as a source-chain account/contract, with no way to know whether that address is controllable there.

### Finding Description
When a solver fills a cross-chain order on the destination chain, `_fillCrossChain` builds a `WithdrawalRequest` whose beneficiary is the filler's `msg.sender` address, cast straight into `bytes32`, and dispatches it as a `RedeemEscrow` POST request to the order's source chain: [1](#0-0) 

The receiving `onAccept` on the source-chain gateway authenticates only that the message came from the registered gateway instance, then calls `_withdraw`, which transfers the escrowed tokens directly to `address(uint160(uint256(body.beneficiary)))`: [2](#0-1) 

This is the exact analog of the reported bug class: an address that is meaningful and controllable on one chain (the filler's contract wallet/multisig/vault on the destination chain) is reused as-is as the recipient on a *different* chain, where the same address may correspond to no deployed code, unrelated code, or a contract with no function to move funds back out (EVM addresses are congruent across chains but contract bytecode/state is chain-specific and typically not deployed identically unless using the exact same CREATE2 salt/factory/nonce on both chains). There is no `isContract`/opt-in flag and no alternate refund-address parameter — the filler has no way to designate a different, chain-appropriate beneficiary for the redeemed escrow.

The same pattern also appears in the same-chain/partial-fill path, where the redeem beneficiary is likewise `msg.sender`: [3](#0-2) 

and in the Tron variant's `withdraw`: [4](#0-3) 

### Impact Explanation
If a solver fills an order using a smart-contract account (multisig, vault, smart-account wallet, proxy) that does not exist — or exists with different/no code — at that same address on the order's source chain, the escrowed input tokens (`order.inputs`) and any accrued protocol/transaction fees released by `_withdraw` are sent to an address nobody can operate on the source chain. This is a permanent loss of the user's escrowed principal that was meant to pay the solver, matching the bounty's "loss of funds" impact category. Given that solvers/market-makers commonly operate through smart contract wallets for security and multisig custody, this is a realistic, non-adversarial failure mode baked into the core redeem path.

### Likelihood Explanation
Any solver that uses a contract-based wallet (a common, recommended security practice for capital-holding entities) to call `fillOrder`/`_fillCrossChain` is exposed every time it fills a cross-chain order, with no override available in `FillOptions` to specify an alternate redeem beneficiary. No malicious relayer, prover, or governance actor is required — this triggers through the normal, permissionless `fillOrder` entrypoint.

### Recommendation
Add an explicit, separate `redeemBeneficiary` (or `refundAddress`) field to `FillOptions` that the filler supplies independently of `msg.sender`, allowing solvers to designate an address they control on the *source* chain. Optionally, require an `isContract` acknowledgement/flag akin to the original report's suggested mitigation, or validate/allow the filler to update the redeem beneficiary before the message is dispatched.

### Proof of Concept
1. A solver operates via a Safe/multisig deployed at address `S` on the destination chain (e.g., using a factory/salt combination unique to that deployment).
2. The solver's relayer/bot calls `fillOrder` (→ `_fillCrossChain`) from `S`, supplying output tokens to the order beneficiary.
3. `_fillCrossChain` dispatches a `RedeemEscrow` `WithdrawalRequest{ beneficiary: bytes32(uint256(uint160(S))) }` to the order's source chain: [5](#0-4) 
4. On the source chain, `onAccept` → `_withdraw` transfers the escrowed input tokens to `address(uint160(uint256(S)))`: [6](#0-5) 
5. Because the Safe at address `S` was never deployed on the source chain (different chain, no corresponding CREATE2 deployment there), the tokens land on an address with no code and no known private key — the escrowed funds are irrecoverable.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {

                if (!sent) revert InsufficientNativeToken();

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

                (bool sent,) = beneficiary.call{value: amount}("");
