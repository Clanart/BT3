### Title
Deterministic cached FROST nonces reused across distinct signing inputs within the same `attempt` allow secret-share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
Like the NextGen bug — where a cumulative global counter (`viewCirSupply`) was applied to a new sale phase instead of a per-phase baseline — `SigningProtocol::preprocess_internal` derives the FROST preprocess from a cached seed keyed only by `context = (b"DkgConfirmer", self.attempt)`. Any call to `share_internal`/`complete_internal` under the same `attempt` regenerates the *identical* nonces, regardless of which preprocesses or message are supplied. The "session state" is bound to a coarse counter (`attempt`) instead of the actual signing instance (preprocess set + message), so a second signing attempt under the same attempt number reuses the nonce — the direct FROST key-share-recovery condition the code comments themselves warn about.

### Finding Description
`preprocess_internal` encrypts and caches a 32-byte seed under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` and reloads it on every subsequent call where `context` is unchanged (`coordinator/src/tributary/signing_protocol.rs:123-145`). For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`), so the seed — and therefore every nonce generated by `seeded_preprocess` via `ChaCha20Rng::from_seed(*seed.0)` in `crypto/frost/src/sign.rs:127-133` — is a pure function of `attempt` and the validator key.

`sign()` in `crypto/frost/src/sign.rs:283-380` then computes per-participant binding factors `rho` from a transcript covering the *supplied* preprocesses (`hash_commitments` of the participant/addendum transcript) and the message (`hash_msg(msg)`). Both inputs are externally influenced: `share_internal` receives `preprocesses: HashMap<Participant, Vec<u8>>` fed through `read_preprocess` (`signing_protocol.rs:155-178`), and `msg` is `set_keys_message(...)` built from `key_pair` and the `removed` set (`signing_protocol.rs:296-300`).

Critically, `DkgConfirmer::complete` calls `share_internal` *again* (`signing_protocol.rs:321-324`) after `share` was already called. If the preprocesses or `key_pair` passed to `complete` differ from those passed to `share` — both are attacker-influenced byte inputs read via `read_preprocess`/`read_share` — the validator produces a second `SignatureShare` with the **same nonce** `d + rho·e` structure but a different binding factor/challenge linearization. Two shares over one nonce yield `s_i` directly, exactly the "preprocess MUST only be used once" violation documented in `crypto/frost/src/sign.rs:85-87` and `spec/cryptography/FROST.md:51-55`. The header comment in `signing_protocol.rs:25-55` explicitly relies on BFT ordering to make received messages unique per nonce decision — but the cache key does not include the received messages, the participant set, or the message digest, only `attempt`.

The file's own `TODO` flags the missing guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (`signing_protocol.rs:50-54`). Because the produced preprocess bytes are deterministic given the seed, a validator's published preprocess for attempt `k` binds it to nonces that will be reused for *any* signing under `attempt == k`, including a logically distinct confirmation phase — the analog of a "second minting event" reusing state computed from the prior phase.

### Impact Explanation
Reuse of a FROST nonce across two different `(commitments, message)` tuples produces two signature shares `z1 = d + rho1·e + λ·c1·s_i` and `z2 = d + rho2·e + λ·c2·s_i` (same `d`, `e`). Since `rho`, `c`, `λ` are publicly computable, `s_i` — the validator's MuSig/threshold secret share over `Ristretto` — is recoverable by anyone observing both shares. That key is the validator root-of-trust key used to confirm DKG results on Substrate (`signing_protocol.rs:1-14`), so recovery enables forging set-keys confirmations and compounding toward threshold compromise.

### Likelihood Explanation
The trigger is that a validator signs twice under one `attempt` with different effective inputs. `complete` re-invokes `share_internal` unconditionally (`signing_protocol.rs:321-324`), so any divergence between the preprocess map/key_pair seen at `share` time versus `complete` time produces the second share. An unprivileged participant reaching these functions controls the `HashMap<Participant, Vec<u8>>` bytes and, through `key_pair`, the message. One caveat I could not fully verify within scope: whether the tributary/BFT layer upstream guarantees the same preprocesses and `key_pair` at `share` and `complete` time; the code itself performs no such equality check — `share_internal` re-derives the machine and re-signs whatever it is given, so the defense rests entirely on the out-of-scope caller and the unimplemented TODO.

### Recommendation
Include the full signing inputs in the cache key / nonce binding: key `CachedPreprocesses` by `(context, hash(sorted preprocesses), hash(msg))`, or assert before producing a share that a nonce has never been consumed for a different `(preprocesses, msg)` pair under the same context (store and compare the first tuple, analogous to `FirstPreprocessDb::save_first_preprocess`'s `assert_eq!` in `coordinator/src/db.rs:90-94`). Implement the pending TODO of verifying on-chain preprocesses match the presumed preprocess before publishing shares (`signing_protocol.rs:50-54`).

### Proof of Concept
Conceptual reproduction against the in-scope crates:

1. Instantiate `DkgConfirmer` with fixed `attempt = k`. Call `share(preprocesses_A, key_pair)` → nonce seed `seed_k` cached; share `z_A` emitted with nonce `d + rho_A·e`.
2. Call `complete(preprocesses_B, key_pair', shares)` where `preprocesses_B` differs in one participant's commitment bytes (attacker feeds distinct bytes through `read_preprocess`) or `key_pair` differs → `share_internal` reloads `seed_k`, regenerates identical `d, e` (`sign.rs:127-133`), but `rho_B`/challenge differ (`sign.rs:361-379`) → share `z_B` emitted.
3. Solve `z_A - z_B = (rho_A - rho_B)·e + λ·(c_A - c_B)·s_i` for `e`, then `s_i` from either equation → validator secret share recovered.
