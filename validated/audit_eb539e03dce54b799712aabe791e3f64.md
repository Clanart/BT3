### Title
Path traversal via unsanitized worktree/repository name in `RepositoryPath` (`safeDirectoryName`) — inconsistent with `sanitizeCloneName` — ([File: app/src/ui/lib/repository-path.tsx])

### Summary
The external report's underlying theme — duplicated logic that should be centralized, because divergent copies drift and reintroduce bugs — has a direct, verifiable analog in GitHub Desktop. The codebase contains at least three independent "sanitize a name for use in a filesystem path" implementations: `sanitizeCloneName` (`app/src/lib/remote-parsing.ts`), `sanitizedRepositoryName` (`app/src/ui/add-repository/sanitized-repository-name.ts`), and `safeDirectoryName` (`app/src/ui/lib/repository-path.tsx`). Only `sanitizeCloneName` explicitly strips directory-traversal segments (`..`, `.`) and collapses to a single path component. `safeDirectoryName`, used by the shared `RepositoryPath` component for both "Create Repository" and "Add Worktree" flows, deliberately does **not** strip `/`, `\`, or `..` sequences.

### Finding Description
`safeDirectoryName` in [1](#0-0)  only replaces Windows-reserved characters (`<>:"|?*`) and trailing whitespace; by explicit design (per the inline comment) it passes `/` and `\` through untouched "letting users type something like OrgA\RepoB." It performs no rejection of `..` traversal components at all, on either platform.

That sanitized value is then joined directly onto the base path with no post-hoc containment check: [2](#0-1) 

This is the same class of defect the external report is warning about: elsewhere in this same codebase (`app/src/lib/remote-parsing.ts:88-116`, `sanitizeCloneName`) the team correctly implemented traversal-segment stripping and rejection of `..`/`.`-only names, and even added a dedicated regression test suite for it (`app/test/unit/clone-path-safety-test.ts`). The `RepositoryPath`/`safeDirectoryName` copy was never brought in line with that hardening, so the same "resolved path escapes intended base directory" bug class that was fixed for clone destinations remains open for the worktree/create-repository name field. Unlike `_resolveWithin` (`app/src/lib/path.ts:36-71`), which does enforce containment via `realpath` comparison, `RepositoryPath.getFullPath()` never routes through any equivalent containment check.

### Impact Explanation
If a `..`/backslash-or-slash-laden value ever reaches the `name` state of `RepositoryPath` (e.g., pre-filled from `initialWorktreeName`/`initialName` props, which can originate from names derived from remote data such as branch names), `Path.join(path, safeDirectoryName(name))` can resolve outside the user-chosen base directory. Combined with `AddWorktreeDialog`'s `addWorktree(repository, fullPath, …)` call (`app/src/ui/worktrees/add-worktree-dialog.tsx:96-109`), this could cause `git worktree add` to write a working tree outside the intended folder — a silent file-write-outside-target-directory condition, matching the class of bug this report's "avoid duplicate code" complaint predicts (divergent copies of the same security-relevant logic, one hardened and one not).

### Likelihood Explanation
Moderate/uncertain. I could not, within the available tool budget, conclusively trace an end-to-end path where a value from an attacker-controlled source (a fetched repo's branch name, a GitHub API object, or a deep link) is placed into `RepositoryPath`'s `name` field without going through `sanitizedRefName` or other sanitizers first. The `name` field is normally free-typed by the local user, which would not satisfy the "unprivileged attacker controls the input" bar. This gap should be treated as an unconfirmed but structurally real inconsistency rather than a fully verified end-to-end exploit chain.

### Recommendation
Consolidate all directory/component-name sanitization into the single hardened implementation (`sanitizeCloneName`, or a shared utility built on the same traversal-rejection logic), and route `RepositoryPath.getFullPath()` through the same containment check used elsewhere (`resolveWithin` in `app/src/lib/path.ts`) before the path is handed to `addWorktree`/repository-creation code. Add a regression test analogous to `app/test/unit/clone-path-safety-test.ts` for the worktree/create-repository path.

### Proof of Concept
Not confirmed end-to-end due to inability to verify an attacker-controlled data source feeding `RepositoryPath`'s `name` prop within the available investigation time. Conceptually: if `initialWorktreeName` (or the name field) is ever populated with a value like `../../../.ssh`, `RepositoryPath.getFullPath()` returns `Path.join(basePath, '../../../.ssh')`, which resolves outside `basePath` because `safeDirectoryName` performs no `..`-rejection (contrast with `sanitizeCloneName`, which explicitly returns `null` for such input, and with `_resolveWithin`, which explicitly rejects it via `realpath` comparison).

**Caveat:** Given the residual uncertainty about whether attacker-controlled data (as opposed to local user typing) can reach this field, this should be treated as a code-hygiene/defense-in-depth finding discovered via the "duplicate code" lens rather than a fully proven exploitable vulnerability. A Devin session with full repo/browser access would be needed to trace every call site of `RepositoryPath` and confirm or rule out a genuine attacker-controlled path.

```typescript
// We use this instead of sanitizedRepositoryName because it deals with
// valid repository names on GitHub.com but here we only care about whether
// we'll be able to create a directory with the given name. If a user
// creates a repository with a name that GitHub.com doesn't like here it'll
// get sanitized in the Publish dialog later on.
//
// Note that we don't sanitize `\` or `/` here since we use `Path.join` to
// create the full path and that will handle those characters appropriately
// letting users type something like OrgA\RepoB and have the new repo be
// created in the OrgA folder.
//
// macOS and Linux are way more allowing so there's no need to sanitize
const safeDirectoryName = (name: string) => {
  return __WIN32__ ? name.replace(/[<>:"|?*]/g, '-').replace(/\s+$/, '') : name
}
```

```typescript
  private getFullPath(): string | null {
    const { name, path } = this.state
    if (path === null || path.length === 0 || name.trim().length === 0) {
      return null
    }
    return Path.join(path, safeDirectoryName(name))
  }
```
