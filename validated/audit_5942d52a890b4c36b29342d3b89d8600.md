### Title
Directory/Symlink Traversal via Unvalidated Repository-Relative Paths in "Reveal in File Manager" / "Open in External Editor" / "Open with Default Program" — (File: `app/src/lib/app-shell.ts`)

### Summary
Desktop already recognizes and mitigates path-traversal in one specific location: `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` explicitly rejects absolute `filepath` values and calls `resolveWithin(repository.path, filepath)` — a helper in `app/src/lib/path.ts` that normalizes, resolves, and `realpath`s the target to make sure it does not escape the repository root (defeating both `..` traversal and symlink escapes). [1](#0-0) [2](#0-1) 

However, the equivalent guard is missing for several other code paths that build a "full path" the exact same way — via a naive `Path.join(repository.path, path)` — using file paths that ultimately originate from the working tree contents of a cloned/fetched attacker-controlled repository (tracked symlinks). The clearest instance is `revealInFileManager` in `app/src/lib/app-shell.ts`:

```
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
``` [3](#0-2) 

Its own doc-comment on the underlying `IAppShell.showItemInFolder`/`openPath` explicitly warns "Do not use this method with non-validated paths" — yet `revealInFileManager` (and the several call sites that build similar full paths) never validates the path. [4](#0-3) 

### Finding Description
Git does not restrict the *target* of a tracked symlink (mode `120000`) — only tree entry *names* are restricted (e.g. `.` / `..` are rejected by `git fsck`/checkout to prevent tree-based traversal). An attacker can therefore commit a symlink such as `notes.txt -> ../../../../../../.ssh/id_rsa` (or any absolute path) into a public repository or a pull-request branch. When a victim clones/fetches that repository or opens that PR in Desktop, git checkout will happily materialize this symlink on disk inside the working directory, exactly as designed by git.

Desktop then surfaces this file in the Changes list and in the "Files Changed" view for a PR, both of which build a full path by directly joining `repository.path` with the (attacker-supplied) relative file path, with no `resolveWithin`/`realpath` check:

- `revealInFileManager(repository, path)` → `Path.join(repository.path, path)` then `shell.showItemInFolder(...)`. [5](#0-4) 
- `pull-request-files-changed.tsx` builds `fullPath = Path.join(repository.path, file.path)` from a `CommittedFileChange` and offers "Open in External Editor" / "Open with Default Program" / "Reveal in File Manager" against it. [6](#0-5) 
- `app.tsx`'s `onOpenInExternalEditor` also does `const fullPath = Path.join(repository.path, path)` before invoking the editor. [7](#0-6) 
- Conflict-resolution UI (`unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`) similarly does `join(repository.path, props.path)`/`join(repository.path, path)` before opening files. [8](#0-7) [9](#0-8) 

None of these code paths call `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, and none check whether the resolved entry is a symlink before opening it. The only file-type gate present, `isSafeFileExtension`, filters by file *extension*, not by whether the underlying path is a symlink pointing outside the repository. [10](#0-9) 

By contrast, `resolveWithin` was purpose-built (per its own doc comment and the dedicated `clone.ts`/`dispatcher.ts` backstops and `path-test.ts` symlink test cases) specifically to stop "a crafted URL/repository from tricking the UI into deriving a path outside the intended base directory," including via a symlink used to hop out of the root and never getting back in. [11](#0-10) 

The broken invariant: any UI action that turns a repository-relative path into a full filesystem path for opening/revealing/editing should guarantee the resolved path stays under the repository root even through symlinks — exactly what `resolveWithin` guarantees for the URL-deep-link case, but not for these UI actions.

### Impact Explanation
If the victim invokes "Open with Default Program," "Open in External Editor," or double-clicks a file entry (in Changes list or PR "Files Changed" view) for a maliciously-crafted tracked symlink, the OS/editor will follow the symlink and open the *target* file, which can reside anywhere on the victim's filesystem (SSH keys, cloud-credential files, browser cookie stores, etc.), disclosing its contents to the victim's screen/editor. "Reveal in File Manager" additionally confirms the existence and reveals metadata about arbitrary host paths. This satisfies the "attacker controls a cloned/fetched repository ... and the result is ... file ... read outside the repo" criterion.

### Likelihood Explanation
Medium. The attack requires the victim to open a malicious/forked repository or PR in Desktop and interact with a specific file entry (open/reveal/edit) — a normal workflow when reviewing PRs from external contributors, which is exactly the trust boundary GitHub Desktop is meant to broker safely. No admin rights, local access, or prior compromise are needed; the only "unnatural" step is a single click a reviewer would routinely perform when inspecting PR file changes.

### Recommendation
Route every repository-relative "open"/"reveal" full-path construction through `resolveWithin` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) before invoking `shell.showItemInFolder`, `shell.openPath`, `launchExternalEditor`, or `openFile`, mirroring the guard already implemented in `dispatcher.ts`'s `openRepositoryFromUrl`. If the resolved path is `null` (i.e., it escapes the repository root, including via a symlink), refuse the action and log/warn instead of performing it. Apply this uniformly to `revealInFileManager`, `pull-request-files-changed.tsx`, `app.tsx#onOpenInExternalEditor`, `unmerged-file.tsx`, and `copilot-conflicts-dialog.tsx`.

### Proof of Concept
1. Attacker creates a public repository (or opens a PR against a target repository) containing a tracked symlink, e.g.:
   ```
   git symlink harmless-notes.txt -> ../../../../../../Users/victim/.ssh/id_rsa
   git add harmless-notes.txt
   git commit -m "add notes"
   ```
2. Victim opens the PR / clones the repo in GitHub Desktop and views the "Files Changed" list, or checks out the branch so the symlink appears in the Changes list.
3. Victim right-clicks `harmless-notes.txt` and selects "Open with Default Program" (or "Open in External Editor").
4. `Path.join(repository.path, 'harmless-notes.txt')` resolves to the symlink path; the OS/editor follows the symlink and opens the *actual target file* (`~/.ssh/id_rsa`), disclosing its contents to the victim's default text editor/viewer — with no `resolveWithin` check ever having been performed to prevent this, unlike the equivalent deep-link `filepath` handling in `dispatcher.ts`.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
