### Title
DkgConfirmer reuses a cached FROST preprocess across distinct `set_keys_message` payloads in the same attempt, enabling nonce reuse and validator secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a FROST preprocess seed in `CachedPreprocesses` keyed only by `context = (b"DkgConfirmer", attempt)` and regenerates identical nonces from that seed on every subsequent call within the attempt. Both `DkgConfirmer::share` and `DkgConfirmer::complete` route through `share_internal` → `preprocess_internal`, and the message being signed (`set_keys_message(...)`) is built from a caller-supplied `key_pair`. The cached object is fetched by attempt-ID alone and never bound to the message or the participant/preprocess set, so the same nonce commitments can be applied to a different challenge — the same missing-binding/deputy pattern as the TypeBot credential updated by global `id`.

### Finding Description
- `coordinator/src/tributary/signing_protocol.rs:88-90` — `CachedPreprocesses: (context) -> [u8; 32]` is keyed solely on `context`.
- Lines 123-145: if a cached entry exists, it is loaded and passed to `AlgorithmSignMachine::from_cache`; the seed is never deleted after use.
- `crypto/frost/src/sign.rs:121-144` — `seeded_preprocess` derives `(nonces, commitments)` deterministically from `ChaCha20Rng::from_seed(*seed.0)`, so reloading the same seed yields identical FROST nonces `d, e`.
- `DkgConfirmer::signing_protocol` (lines 274-277) sets `context = (b"DkgConfirmer", self.attempt)`, identical for every call in the attempt.
- `DkgConfirmer::share` (304-310) and `complete` (312-327) both call `share_internal`, which signs `msg = set_keys_message(set, removed, key_pair)` where `key_pair` is an argument supplied per call (lines 296-301), and `preprocesses` is an attacker-influenced map of serialized preprocess bytes read via `read_preprocess` (lines 164-168).

Because the cached preprocess is selected by attempt context only — not by the `key_pair`/`msg` nor by the preprocess set — an invocation of `share` followed by `complete` (or two `share`-path invocations) with a different `key_pair` produces two signature shares `s1 = d + e·ρ1·λ·x`, `s2 = d + e·ρ2·λ·x` over challenges `c1 ≠ c2` using the same nonces. Solving the two equations recovers `λ·x`, the validator's MuSig secret share, and thereby the tributary signing key material. This is the classic cross-context nonce-reuse that the `CachedPreprocess` documentation itself warns against (`crypto/frost/src/sign.rs:84-93`, `211-224`).

### Impact Explanation
Reuse of a FROST preprocess across two distinct messages leaks the signer's secret share algebraically. Here the victim is a validator's MuSig/Ristretto key used for DKG confirmations (`set_keys_message` signatures), so recovery of `x` lets an attacker forge `Transaction::Sign`/set-keys signatures for that validator — equivalent to full compromise of that validator's signing identity for the set. Severity: High/Critical.

### Likelihood Explanation
The trigger requires two `share_internal` executions within one `attempt` whose `key_pair` (or effective `msg`/binding set) differ. `complete` unconditionally re-executes `share_internal` after `share` has already run (the cache persists), so any path where the committed DKG data yields a different `KeyPair` between the share phase and completion — or where a DKG participant supplies conflicting `key_pair` values that both reach `share`/`complete` — produces the reuse. An unprivileged DKG participant controls their own `key_pair`/DKG message bytes flowing into `set_keys_message`, making the divergence attacker-influencable rather than purely accidental. The one-use guarantee documented for `CachedPreprocess` is violated structurally: the entry is set-if-absent and never consumed.

### Recommendation
Bind the cached preprocess to everything that determines the signature: key `CachedPreprocesses` by a digest of `(context, participants, key_pair/msg)` and refuse (or regenerate) on mismatch; alternatively delete the cache entry after the first `share_internal` for an attempt and require `complete` to reuse the share already produced rather than re-signing. More robustly, have `share` return and persist the `(machine, share)` so `complete` never rebuilds a signing machine from a consumed seed.

### Proof of Concept
```text
1. Within DkgConfirmer attempt N, share() is invoked with key_pair = KP_A.
   preprocess_internal writes CachedPreprocesses[("DkgConfirmer", N)] = S
   and signs msg_A = set_keys_message(set, removed, KP_A), emitting
   share s1 derived from nonces (d, e) = f(S).
2. complete() (or a second share() call for a conflicting committed KeyPair
   KP_B) is invoked for the same attempt N.
   preprocess_internal finds the cache entry, rebuilds the machine from S
   via from_cache → seeded_preprocess, regenerating the SAME (d, e).
   It signs msg_B = set_keys_message(set, removed, KP_B) ≠ msg_A, emitting
   s2 = d + e·ρ2·λ·x  with challenge/binding ρ2 ≠ ρ1.
3. Given public preprocess commitments, the verifier challenge relation is
   public, so solving
       s1 - s2 = e·λ·x·(ρ1 - ρ2)   (with d cancelling only if the ρ
       derivation splits d and e; otherwise the standard two-nonce FROST
       linear system in (d, e·λ·x) applies)
   yields the secret share x·λ (and hence the validator's MuSig key
   contribution), since ρ1, ρ2, s1, s2 are all known/observable on-chain.
```

Note: reachability of step 2 (two distinct `key_pair` values in one attempt) depends on how `handle.rs` feeds `KeyPair` into `share`/`complete`; I could not fully verify that call path within available iterations, but the structural reuse — a cached nonce seed selected by attempt-ID alone, never invalidated, and applied to caller-determined messages — is directly visible at `signing_protocol.rs:123-145` and `sign.rs:121-144`.
