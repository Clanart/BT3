### Title
Webhook HMAC signature covers only the request body, not the `X-Shopify-Shop-Domain`/topic headers, enabling cross-shop webhook replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates an inbound webhook solely by recomputing an HMAC over `request.raw_post` and comparing it to the `X-Shopify-Hmac-Sha256` header. The shop identity used to route the job (`shop_domain`) is read from a separate, unsigned header. Because the signature never binds the request to a specific shop (or topic), a validly-signed webhook body captured for one shop can be replayed with a different `X-Shopify-Shop-Domain` header value, and it will still pass verification while being processed under a different, victim shop's context — mirroring the Futureswap `instantWithdraw` issue where the signed payload lacked platform/recipient-binding data.

### Finding Description

`WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` — the HMAC covers the body only: [2](#0-1) 

The shop identity that downstream code trusts, however, comes from a header that is *not* part of the signed material: [3](#0-2) 

The documented custom-controller pattern explicitly takes this unauthenticated `shop_domain` and forwards it, together with the (signed) body, to a job: [4](#0-3) 

Generated job templates (including the mandatory privacy jobs) then use that `shop_domain` value, verbatim, to look up and act on a `Shop` record: [5](#0-4) [6](#0-5) 

Because the app's webhook secret is shared across every shop that installs the app, and the HMAC never incorporates the shop-domain/topic headers, any party who can obtain one legitimately-signed `(body, hmac)` pair (e.g., by installing the app on their own store and triggering a webhook such as `shop/redact` or `app/uninstalled`) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `hmac_valid?` will still succeed because it only validates the body, and the job will run using the attacker-supplied `shop_domain` — not the shop the body was actually generated for.

### Impact Explanation
This allows an authenticated-but-unrelated merchant (anyone who can install the app on their own store) to trigger webhook-driven side effects against a different, victim shop that they do not control — e.g., invoking `ShopRedactJob`/`CustomersDataRequestJob`/`CustomerRedactJob` logic against the victim's `Shop` record, or any custom job built on this documented pattern. This is a cross-shop trust boundary violation caused by an accepted forged/replayed signed request, matching the "cross-shop access" and "accepted forged signed request" categories.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate (even if unrelated) merchant who has installed the target app on a shop they control, which is trivial for any public Shopify app, plus knowledge of the victim's `.myshopify.com` domain (public/discoverable). No secrets need to be leaked and no developer misconfiguration is required — this is the exact usage pattern the gem's own documentation instructs developers to build.

### Recommendation
Bind the webhook signature verification to shop/topic context rather than trusting unauthenticated headers for routing: include `X-Shopify-Shop-Domain` and `X-Shopify-Topic` in the data verified (e.g., verify the shop domain returned against a shop that is know to have an active, matching webhook subscription/registration, or require the HMAC computation to additionally cover these headers), and/or reject requests where the header-supplied shop domain doesn't correspond to an install that actually has this webhook topic registered.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) a `shop/redact` (or any subscribed) webhook; captures the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify computed for it.
3. Attacker resends this exact body + HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `PayloadVerification#hmac_valid?` succeeds (body/HMAC unchanged), `WebhookVerification#shop_domain` returns `victim-shop.myshopify.com`, and the corresponding job (e.g. `ShopRedactJob`) executes `Shop.find_by(shopify_domain: "victim-shop.myshopify.com")` and proceeds with `shop.with_shopify_session`, acting on the victim's shop instead of the attacker's.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
