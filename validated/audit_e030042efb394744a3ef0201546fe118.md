Gasless swap repayment amount is validated against a manipulable spot AMM price, allowing under-collateralized gas repayment - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The KIP-247 gasless transaction mechanism lets a block proposer front gas fees for a user (via `LendTxGenerator`) which the user then repays from a token-to-KAIA swap executed through the `GaslessSwapRouter` contract [1](#0-0) . The amount of token the user must supply (`amountIn`) is validated in `checkBalanceForSwap` by calling `GaslessSwapRouter.GetAmountIn(token, minAmountOut)`, which returns the exchange rate computed from the live, spot reserves of the underlying DEX pool (a UniswapV2-style pair, per the bindings in `contracts/bindings/uniswap/router` and `contracts/bindings/kip247/GaslessSwapRouter.go`) rather than a time-weighted average price [2](#0-1) .

### Finding Description
`checkBalanceForSwap` performs the following check when a `GaslessSwapTx` is admitted to the pool:
```go
requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
...
if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
    return fmt.Errorf("insufficient amountIn: ...")
}
``` [3](#0-2) 

`GetAmountIn` on `GaslessSwapRouter` (bound in `contracts/bindings/kip247/GaslessSwapRouter.go`) resolves the whitelisted token's DEX pool via `GetDEXInfo`/`DexAddress` [4](#0-3)  and derives the price from the pool's Uniswap-V2-style reserves, the same pattern exercised in the integration test where a single `UniswapV2Router02` pair is deployed with a fixed, small `initialLiquidity` and used directly as the price source for gasless swaps [5](#0-4) .

This is the same bug class as the external WBGL report: a protocol-critical price calculation (there, USSD mint valuation; here, the KAIA-equivalent value the block proposer must be repaid) is derived from a single AMM pool's instantaneous reserves with no TWAP or external oracle safeguard. An attacker holding the token/KAIA pair can trade against the pool immediately before submitting (or bundling with) a `GaslessSwapTx` to shift the spot price so that `GetAmountIn` returns an artificially low `requiredAmountIn`. The gasless tx pool's `IsExecutable`/`isReady` promotion logic and the `worker`'s bundling of `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` [6](#0-5)  execute the lending and swap in the same block, so the manipulation and the gasless swap can be realized within a single block/bundle context, satisfying the "single submitted transaction/bundle" reachability requirement.

### Impact Explanation
If the manipulated spot price causes the router to under-price the required `amountIn`/`amountRepay`, the block proposer's `LendTxGenerator` advance (real KAIA gas) can be repaid with less real economic value than it lent, resulting in a direct value loss to the proposer (fee-delegation/gasless settlement abuse) — this matches the "fee delegation abuse" / "gasless settlement theft" categories in scope.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control (or heavily trade against) a thinly-liquidated token/KAIA pool used by an `allowedToken` in the `GaslessSwapRouter` whitelist. Only whitelisted, low-liquidity tokens (added via `AddToken`, referenced in `tests/gasless_test.go:465` [7](#0-6) ) are exposed to this risk, and the actual on-chain `swapForGas` execution may still enforce its own `minAmountOut` slippage bound — I could not verify the Solidity source of `GaslessSwapRouter.swapForGas` (only the compiled bytecode/ABI bindings are indexed), so I cannot confirm whether the contract has additional protections (e.g., a secondary oracle, a maximum price-impact cap, or same-block manipulation detection) that would block this exact exploit path.

### Recommendation
- Use a TWAP or an external oracle (in addition to, or instead of, spot AMM reserves) when computing `GetAmountIn`/settlement rates in `GaslessSwapRouter` for whitelisted tokens with shallow liquidity.
- Add a maximum allowed single-block price deviation check before honoring a gasless swap's declared `minAmountOut`/`amountRepay`.
- Restrict `AddToken` (token whitelisting) to pools meeting a minimum liquidity/TVL threshold, and re-validate liquidity periodically.

### Proof of Concept
Conceptual PoC (blocked by missing Solidity source for `GaslessSwapRouter`, only Go bindings/ABI were available in the index):
1. Attacker identifies a whitelisted low-liquidity token pool used by `GaslessSwapRouter` (e.g., `testTokenAddr`/`wkaiaAddr` pair pattern shown in `tests/gasless_test.go:378-390`).
2. Attacker (or colluding party) submits a large swap on the underlying UniswapV2 pool to skew reserves, shifting the spot price such that `GaslessSwapRouter.GetAmountIn(token, minAmountOut)` returns an artificially low value.
3. In the same block, attacker submits `GaslessApproveTx` + `GaslessSwapTx` with `amountIn` computed against the manipulated rate; `checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go:128-141` accepts it because it only checks against the manipulated `GetAmountIn` result.
4. The gasless bundle executes, and the block proposer's `LendTxGenerator` advance is repaid at the manipulated (unfavorable) rate.

I was unable to fully confirm step 4's real-world outcome without the `GaslessSwapRouter.sol` source (not indexed) to see if `swapForGas` independently re-validates against `amountRepay` in KAIA terms or performs its own slippage protection at settlement — this should be verified directly in the repository before treating this as a confirmed, exploitable finding.
