### Title
Hookify `action: block` rules silently fail to enforce on `prompt` (and `PostToolUse`) events, giving users false confidence in a security control - (File: plugins/hookify/core/rule_engine.py)

### Summary
The Turnstile bug is a class of vulnerability where a user-facing "registration"/configuration action succeeds without error at the application layer, but the enforcement layer silently fails to apply the intended protection, with no signal to the user that anything is wrong. The `hookify` plugin in this repo reproduces this exact bug class: a user can create a rule with `action: block` for the `prompt` event type (and effectively for `PostToolUse`), the rule is accepted, saved, and listed as active by `/hookify:list`, but the enforcement code path for those event types never actually blocks anything — it silently downgrades to a cosmetic message.

### Finding Description
`RuleEngine.evaluate_rules` only implements real blocking behavior for two `hook_event_name` values: `'Stop'` (returns `decision: block`) and `'PreToolUse'`/`'PostToolUse'` (returns `hookSpecificOutput.permissionDecision: deny`) [1](#0-0) . For every other hook event — including `UserPromptSubmit`, which is the event the plugin's own documentation calls the `prompt` event type — a matched `block` rule falls into the generic `else` branch and returns only a `systemMessage`, with no denial/blocking field at all [2](#0-1) .

The `UserPromptSubmit` hook script (`userpromptsubmit.py`) calls `load_rules(event='prompt')` and feeds the result straight into `evaluate_rules`, printing whatever JSON comes back and always exiting 0 [3](#0-2) . Since `hook_event_name` for this event is `UserPromptSubmit`, not `Stop`/`PreToolUse`/`PostToolUse`, `evaluate_rules` can never produce a real block for it — only a `systemMessage`.

Yet the plugin's own configuration surface actively encourages users to create exactly this kind of rule: `event: prompt` is a documented, supported event type [4](#0-3) , and `action: block` is documented generically as "Prevents operation or stop session" in the `/hookify` slash-command file with no caveat that it doesn't apply to `prompt` events [5](#0-4) . Nothing in `config_loader.py`'s `Rule.from_dict` or `load_rules` validates that `action: block` is only meaningful for supported events — an invalid/no-op combination is accepted silently [6](#0-5) , `/hookify:list` and `/hookify:configure` would still show the rule as `enabled: true, action: block`.

This exactly mirrors the root cause pattern in the report: a "registration" (rule creation) succeeds and is durably recorded with no error, while a separate enforcement layer (the per-event hook executor + `RuleEngine`) has a stricter/incomplete implementation that silently never activates the protection for that configuration, and there is no feedback loop that would reveal the mismatch to the user.

### Impact Explanation
A user (or an automated `/hookify` invocation acting on the user's behalf, e.g. "block prompts containing X") who configures a `block` rule against `event: prompt` reasonably believes they have installed a hard guardrail against certain user-prompt content (e.g. a rule intended to stop dangerous instructions, jailbreak phrases, or prompt-injection markers from being submitted to the model). In reality the prompt is always allowed to proceed to the model; only a `systemMessage` is shown, which is informational only and does not prevent processing. Because the file is created, enabled, and listed as an active `block` rule with no error anywhere in the pipeline, the user has no way to discover the gap except by manually testing every rule and noticing the "blocked" content actually got processed. This is a local guardrail-bypass in the unprivileged user's own hook-authorization/enforcement trust boundary — the very mechanism (`hookify`) that exists specifically to let a user add hard blocks around dangerous agent behavior fails open for one of its four documented event types without any indication of failure.

### Likelihood Explanation
High likelihood of silent occurrence: any user who creates a `prompt`-scoped `block` rule (a natural, documented, and encouraged usage pattern — the `/hookify` command's own workflow guidance shows `event`/`action` as freely combinable, and prompt-based blocking is one of the five documented event types) will hit this gap every time, with 100% reproducibility and zero error signal. It requires no adversarial timing or race condition — it is a straightforward logic gap in `evaluate_rules`'s event-name branching.

### Recommendation
In `plugins/hookify/core/rule_engine.py`, extend the blocking branch to also handle `UserPromptSubmit` (and any other event that supports a real deny/block hook output), returning the appropriate blocking `hookSpecificOutput` (e.g. `{"decision": "block"}` or the correct `UserPromptSubmit`-specific stop field) instead of falling into the generic `systemMessage`-only branch. Alternatively/additionally, validate at rule-load time in `config_loader.py` that `action: block` is only accepted for event types that the corresponding hook script can actually enforce, and either reject or warn (loudly, not just to stderr) when a rule requests an enforcement mode that isn't implemented for its event type, so the discrepancy is surfaced to the user at rule-creation time rather than silently at runtime.

### Proof of Concept
1. Run `/hookify Block any prompt that mentions "delete all files"` (or manually create `.claude/hookify.block-delete-all.local.md`):
```markdown
---
name: block-delete-all
enabled: true
event: prompt
pattern: delete all files
action: block
---

🛑 Blocked: this prompt requests a destructive operation.
```
2. `/hookify:list` shows the rule as enabled with `action: block`, giving the appearance of a real guardrail.
3. Submit a prompt containing "delete all files".
4. `userpromptsubmit.py` loads the rule (`event='prompt'`), `RuleEngine.evaluate_rules` matches it as a `blocking_rules` entry, but since `hook_event_name == 'UserPromptSubmit'` doesn't match `'Stop'` or `['PreToolUse','PostToolUse']`, it falls to the generic branch and returns only `{"systemMessage": "..."}` [2](#0-1) .
5. The hook exits 0 with that JSON; the prompt is processed normally by Claude Code — the "block" never happens, despite the rule being configured, enabled, and displayed as an active blocking control.

```python
def main():
    """Main entry point for UserPromptSubmit hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Load user prompt rules
        rules = load_rules(event='prompt')

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
```
