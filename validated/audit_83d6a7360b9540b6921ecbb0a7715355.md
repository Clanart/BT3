### Title
Malformed `CREATE_COIN` condition in an untrusted offer/spend triggers an unhandled `AssertionError` crash in `compute_spend_hints_and_additions` - ([File: chia/wallet/util/compute_hints.py])

### Summary
`compute_spend_hints_and_additions()` parses `CREATE_COIN` conditions produced by running a `CoinSpend`'s puzzle. It extracts the puzzle-hash argument with `condition.at("rf").atom` and then does `assert rf is not None` instead of raising a handled/typed error [1](#0-0) . If the CLVM output for the puzzle hash argument is a cons pair (or any non-atom) rather than an atom, `.atom` returns `None` and the bare `assert` fires an `AssertionError`. This mirrors the CVE-2018-14367 bug class: a parser that fails to properly/gracefully check for a "NULL"/missing value on attacker-influenced structured input, causing a crash rather than a controlled rejection.

### Finding Description
This function is invoked from `chia/wallet/trading/offer.py` in `Offer.__post_init__()` [2](#0-1) , where exceptions (including `AssertionError`, a subclass of `Exception`) are caught by a broad `except Exception: continue`, so that call site is not exploitable on its own.

However, the same function is also called directly, without any exception handling, from `TradeManager.calculate_tx_records_for_offer()`: [3](#0-2) 
```python
async def calculate_tx_records_for_offer(self, offer: Offer, validate: bool) -> list[TransactionRecord]:
    if validate:
        final_spend_bundle: WalletSpendBundle = offer.to_valid_spend()
        ...
        for hinted_coins, _ in (
            compute_spend_hints_and_additions(spend) for spend in final_spend_bundle.coin_spends
        ):
```
`final_spend_bundle` comes from `offer.to_valid_spend()`, i.e. it includes the coin spends embedded in the `Offer` object that was received from a counterparty (a `.offer` file / bech32m-encoded offer supplied over RPC, e.g. via `take_offer`/`respond_to_offer` flows referenced in `chia/wallet/wallet_rpc_api.py` and `chia/cmds/wallet.py`). A malicious counterparty can craft a puzzle/solution whose output condition list contains something shaped like `(51 (a . b) 100)` — a `CREATE_COIN` opcode followed by a cons pair instead of a bytes atom for the puzzle hash. Because `Offer.__post_init__` uses `match_puzzle`/heuristics and only executes the *puzzle reveal itself*, an attacker fully controls both puzzle and solution for coins in the offer bundle (the counterparty coin spends are attacker-authored CLVM), so they can make the run output any condition shape they like without needing a valid signature (this code path runs before/independent of signature validation, since it's purely a CLVM interpretation step for computing hints/additions).

When this crafted spend flows through `calculate_tx_records_for_offer`, the `assert rf is not None` raises unhandled, propagating up through the wallet RPC call that processes the offer (accepting it, computing valid times, computing transaction records for display/confirmation), crashing that request/handler.

### Impact Explanation
This is a spend/offer-triggered processing halt: an unprivileged offer counterparty can cause an unhandled exception in the wallet's offer-acceptance code path by supplying a specially crafted offer file. This matches the "spend-triggered transaction-processing halt" impact category — denial of service against a wallet client processing an incoming offer, without requiring the victim to have signed anything or exposed private keys. It does not directly cause fund loss, but it is a reachable, attacker-controlled crash in a security-relevant validation/parsing path (mirroring the referenced CVE's dissector-crash bug class).

### Likelihood Explanation
High likelihood of reachability: crafting an offer with a puzzle that outputs a non-atom in the `CREATE_COIN` puzzle-hash slot requires no special privileges, no valid signature, and no chain state — only the ability to construct an offer file/spend bundle and have the victim wallet call `calculate_tx_records_for_offer(offer, validate=True)`, which is on the "accept incoming offer" path.

### Recommendation
Replace the bare `assert rf is not None` (and the related `.atom` extraction pattern) in `compute_spend_hints_and_additions` with an explicit check that raises a caught/typed exception (e.g. `ValidationError`) when the puzzle-hash argument is not a well-formed atom, and ensure all call sites (including `TradeManager.calculate_tx_records_for_offer`) handle that exception the same way `Offer.__post_init__` does, rather than letting it propagate unhandled.

### Proof of Concept
1. Construct a `CoinSpend` whose puzzle, when run, returns a condition list containing `(51 (0x01 . 0x02) 100)` — i.e., a `CREATE_COIN` (opcode 51) condition where the puzzle-hash argument is a cons pair rather than a 32-byte atom (achievable trivially with a `(mod (X) (list (list 51 (c X X) 100)))`-style puzzle).
2. Wrap this spend into an `Offer`/`WalletSpendBundle` following `Offer.to_spend_bundle`/`from_bytes` conventions and deliver it as an offer file to a victim wallet.
3. Victim wallet calls `trade_manager.respond_to_offer(...)` → `calculate_tx_records_for_offer(offer, validate=True)` → `compute_spend_hints_and_additions(spend)` for the crafted spend.
4. `condition.at("rf").atom` evaluates to `None`; `assert rf is not None` raises `AssertionError`, unhandled at this call site, aborting the RPC request/handler that was processing the offer.

*Note: exact confirmation of this crash reaching the caller unhandled relies on `calculate_tx_records_for_offer`'s call to `compute_spend_hints_and_additions` lacking a try/except, which is visible in the cited code; I was not able to fully trace every RPC entry point (`take_offer`/`respond_to_offer` handler) within the available context to confirm there is no outer catch-all at the RPC framework layer that converts this into a normal error response rather than a hard crash — this should be verified directly in `wallet_rpc_api.py`'s offer-related handlers.*
