### Title
Auction bid signature validated against stale `auctioneer`/`auctionEntryPoint` config due to TOCTOU between `validateBid` and `insertBid` - (File: `kaiax/auction/impl/bid_pool.go`)

### Summary
`BidPool.AddBid` checks a submitted auction bid's EIP-712 signatures against the currently configured `auctioneer` and `auctionEntryPoint` in `validateBid`/`validateBidSigs`, then separately commits the bid to the pool in `insertBid`. These are two independent critical sections guarded by different locks (`auctionInfoMu` for the config snapshot used in signature verification, `bidMu` for the bid maps), with no atomicity between "verify signature against config" and "admit bid into pool." If `updateAuctionInfo` rotates `auctioneer`/`auctionEntryPoint` (and wipes the pool via `clearBidPool`) in the window between these two steps, a bid that was signature-checked against the *old* auctioneer/entry point is inserted into the pool as if it belonged to the *new* configuration, with no re-check of the signature at insertion time.

### Finding Description
`AddBid` performs the check-then-act sequence: [1](#0-0) 

`validateBid` reads `bp.Chain.CurrentBlock()` and then calls `validateBidSigs`, which snapshots `bp.auctioneer` / `bp.auctionEntryPoint` / `bp.auctionEntryPointVersion` under `auctionInfoMu.RLock()` and verifies the searcher and auctioneer signatures against that snapshot: [2](#0-1) 

Once `validateBid` returns success, `insertBid` acquires only `bidMu.Lock()` and writes the bid into `bidMap`/`bidTargetMap`/`bidWinnerMap`. Its own comment acknowledges a re-check is needed for concurrent bid races, but the re-check is limited to duplicate/`senderHasDifferentWinner` detection — it does not re-verify the signature or re-read the current auction config: [3](#0-2) 

Meanwhile, `updateAuctionInfo` — invoked from block-processing (`execution.go`, triggered on `PostInsertBlock` for every new block) — can concurrently rotate `auctioneer`/`auctionEntryPoint`/version and call `clearBidPool()`, which empties all three bid maps: [4](#0-3) [5](#0-4) 

Because `AddBid`'s signature verification (reads config under `auctionInfoMu`) and its pool insertion (writes under `bidMu`) are not covered by a single lock or re-validated atomically, a race window exists analogous to the diffusers TOCTOU: the "trust check" (signature validity against the currently-configured auctioneer/entry point) is evaluated against one configuration state, while the actual admission into the authoritative bid pool can land after that configuration has since changed. The bid pool has no gate that re-verifies the signature against the post-rotation configuration before it is later picked up by `GetTargetTxMap`/`GetBidTxGenerator` and turned into an executable `BidTx` bundle by the block-building worker.

### Impact Explanation
An auctioneer key rotation (e.g., due to key compromise or normal operational rotation of the KIP-249 auctioneer/`AuctionEntryPoint`) is exactly the security-relevant event this check exists to enforce. If a bid signed by the *outgoing* auctioneer key lands in `insertBid` immediately after `clearBidPool`/`updateAuctionInfo` runs, it is stored in the pool as a live winning bid for its target block, indistinguishable from a bid validated against the new configuration. The block proposer will subsequently select it via `GetTargetTxMap`, generate a `BidTx` targeting the (now current) `AuctionEntryPoint` with `GetBidTxGenerator`, and include it as `[BidTx]` ahead of the target transaction. This allows a bid effectively signed off by a revoked/rotated auctioneer to still secure the priority/front-running slot for its sender, undermining the very key-rotation security boundary the signature check exists to enforce.

### Likelihood Explanation
The race requires an `updateAuctionInfo`/`clearBidPool` call (a new block causing an auction-config change) to land precisely between the unlocked `validateBid` return and the `bidMu.Lock()` acquisition inside `insertBid` for a specific in-flight `AddBid` call. This is a narrow window under normal conditions, but `AddBid` is reachable by any external caller submitting bids via the `auction_submitBid` RPC method or peer bid gossip (`HandleBid`), and config rotations are driven by ordinary block processing which runs continuously and independently of bid submission timing. As with the referenced CVE, exploitability is probabilistic rather than deterministic per attempt, but becomes practically achievable given a busy bid pool and routine `AuctionEntryPoint`/auctioneer updates (statistical success over many attempts), and the mitigation comment in `insertBid` shows the maintainers already recognize (and partially fixed) a closely related race, having only closed the duplicate/winner-list race but not the signature/config race.

### Recommendation
Re-verify the bid's signatures against the *current* `auctioneer`/`auctionEntryPoint`/version inside `insertBid` while holding the lock that guards insertion (or hold `auctionInfoMu` across the entire validate-then-insert sequence so the config snapshot used for signature verification cannot change before the bid is committed). Alternatively, tag each accepted bid with the config version/generation it was validated against, and reject insertion if the pool's current generation differs at insert time.

### Proof of Concept
1. Configure the auction module with `auctioneer = A`, `auctionEntryPoint = E1`.
2. A searcher submits a bid via `auction_submitBid` → `AddBid(bid)`; `validateBid`/`validateBidSigs` pass, verifying `bid.SearcherSig`/`bid.AuctioneerSig` against `(A, E1)` (`kaiax/auction/impl/bid_pool.go:397-419`).
3. Before `insertBid` acquires `bidMu.Lock()`, a new block is inserted that rotates the on-chain auctioneer/entry point to `(B, E2)`, causing `PostInsertBlock` → `updateAuctionInfo(B, E2, ...)` → `clearBidPool()` (`kaiax/auction/impl/bid_pool.go:196-213`).
4. `insertBid` now runs against the freshly cleared maps and inserts the bid signed under `(A, E1)` as a winning bid for its target block, with no re-check against `(B, E2)` (`kaiax/auction/impl/bid_pool.go:276-293`).
5. The block proposer later retrieves this bid via `GetTargetTxMap`/`GetBidTxGenerator`, builds a `BidTx` addressed to the current `AuctionEntryPoint` (`GetAuctionEntryPoint()` now returns `E2`), and includes it in the block ahead of the target transaction — despite the bid never having been validated under the post-rotation auctioneer/entry-point configuration.

func (bp *BidPool) clearBidPool() {
	bp.bidMu.Lock()
	defer bp.bidMu.Unlock()

	bp.bidMap = make(map[common.Hash]*auction.Bid)
	bp.bidTargetMap = make(map[uint64]map[common.Hash]*auction.Bid)
	bp.bidWinnerMap = make(map[uint64]map[common.Address]common.Hash)
}

func (bp *BidPool) updateAuctionInfo(auctioneer common.Address, auctionEntryPoint common.Address, auctionEntryPointVersion string, bidTxGasBuffer uint64) {
	bp.auctionInfoMu.Lock()
	defer bp.auctionInfoMu.Unlock()

	if bp.auctioneer == auctioneer && bp.auctionEntryPoint == auctionEntryPoint && bp.auctionEntryPointVersion == auctionEntryPointVersion && bp.bidTxGasBuffer == bidTxGasBuffer {
		return
	}

	// Clear the existing auction pool since the auctioneer or auction entry point address is changed.
	bp.clearBidPool()

	bp.auctioneer = auctioneer
	bp.auctionEntryPoint = auctionEntryPoint
	bp.auctionEntryPointVersion = auctionEntryPointVersion
	bp.bidTxGasBuffer = bidTxGasBuffer

	logger.Info("Update auction info", "auctioneer", auctioneer, "auctionEntryPoint", auctionEntryPoint, "auctionEntryPointVersion", auctionEntryPointVersion, "bidTxGasBuffer", bidTxGasBuffer)
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
