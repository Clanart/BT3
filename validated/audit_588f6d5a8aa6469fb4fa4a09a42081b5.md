### Title
Post-condition type confusion allows a `Fungible` post-condition to forge coverage of the STX sentinel `AssetIdentifier`, bypassing the real STX post-condition check - (File: crates/stacks-transactions/src/lib.rs)

### Summary
`check_transaction_postconditions` tracks which assets have been "checked" per principal in a `HashMap<PrincipalData, HashSet<AssetIdentifier>>` keyed purely by `AssetIdentifier { contract_identifier, asset_name }` equality/hash, with no discriminant recording *which kind* of post-condition (`STX` vs `Fungible`) produced the entry. The reserved sentinel identifiers `AssetIdentifier::STX()` and `AssetIdentifier::STX_burned()` are ordinary values of this same struct, built from a null principal and the strings `"STX"`/`"BURNED"`. An attacker fully controls the `AssetInfo{contract_address, contract_name, asset_name}` fields of a `Fungible` post-condition, so they can construct an `AssetIdentifier` that collides byte-for-byte with `AssetIdentifier::STX()`, causing their forged `Fungible` post-condition to be recorded as "STX checked" for their own principal even though no real STX-amount check was performed.

### Finding Description
`AssetIdentifier::STX()` is defined as: [1](#0-0) 
and `AssetIdentifier::STX_burned()`: [2](#0-1) 

Both are plain `AssetIdentifier { contract_identifier, asset_name }` values with no special tag distinguishing them from a user-defined fungible token identifier — `AssetIdentifier` derives `PartialEq`/`Eq`/`Hash` from these two fields alone: [3](#0-2) 

In `check_transaction_postconditions`, the `STX` post-condition branch inserts `AssetIdentifier::STX()`/`AssetIdentifier::STX_burned()` into `checked_fungible_assets` only after actually validating `amount_sent` against the condition code: [4](#0-3) 

But the `Fungible` post-condition branch builds an `AssetIdentifier` entirely from attacker-supplied `asset_info` fields, checks it against `asset_map.get_fungible_tokens(...)` (the *token* map, not the STX map), and then inserts that identifier into the very same `checked_fungible_assets` set: [5](#0-4) 

Since `AssetInfo.contract_address` is an arbitrary `StacksAddress` and `contract_name`/`asset_name` are arbitrary valid `ContractName`/`ClarityName` values, an attacker can choose `contract_address` = the null address (version 0, `Hash160([0;20])`, matching `StandardPrincipalData::null_principal()`), `contract_name = "STX"`, `asset_name = "STX"`. The resulting `AssetIdentifier` is then identical to `AssetIdentifier::STX()`. Because `get_fungible_tokens` looks this identifier up in `token_map` (which never contains STX transfers — those live in `stx_map`/`burn_map`), it returns `None → 0`, so a condition such as `FungibleConditionCode::SentLe 0` on this forged identifier is trivially satisfied. Crucially, this insert happens into the *same* `checked_fungible_assets[principal]` set that the final enforcement pass consults: [6](#0-5) 

That enforcement pass iterates `asset_map.to_table()`, where real STX transfers are recorded under the key `AssetIdentifier::STX()` (built the same way, via `to_table`): [7](#0-6) 

When the enforcement pass reaches this entry, it merely checks `checked_ft_asset_ids.contains(&asset_identifier)` — true, because of the forged `Fungible` insertion — so no failure is raised, even though the actual STX amount transferred was never checked at all: [8](#0-7) 

This is structurally the same bug class as GHSA-hmfr-rx46-4jx2: a security check keys off a "name"-like value (`AssetIdentifier`'s address+name fields) without checking the "kind" of node that produced it (whether the identifier came from a genuine `STX`/`STX_burned` branch or an attacker-controlled `Fungible` branch), letting an attacker's crafted input satisfy a privileged identity check meant for a different, non-attacker-controlled code path.

### Impact Explanation
This lets a transaction's origin bypass its own declared post-conditions on STX movement: an attacker can attach a single, trivially-satisfiable `Fungible` post-condition crafted to collide with the STX sentinel identifier, and the transaction will be treated (both by mempool admission and by block execution) as if the *STX* movement was properly checked — even though it was not checked at all. In `Deny`/`Originator` post-condition mode (the mode meant to *guarantee* the sender explicitly authorizes each moved asset), this allows a malicious contract call to move the origin's STX in ways the origin never actually authorized/checked, i.e., an asset moving past its post-conditions. This matches the "asset moving past its post-conditions" Critical-impact category defined in the rules.

### Likelihood Explanation
The attacker only needs control over their own outgoing transaction's post-condition list — no signer, miner, or other account's key is required. Both `PostConditionPrincipal` and `AssetInfo` fields are fully attacker-controlled and serialized directly into the transaction, and `StacksAddress`/`ContractName`/`ClarityName` place no restriction preventing the null address or the strings `"STX"`. The collision requires no hash break — it's a direct struct-field match. This makes the exploit deterministic and reproducible.

### Recommendation
Do not treat `AssetIdentifier::STX()`/`STX_burned()` as ordinary values indistinguishable from user-defined fungible-token identifiers inside the shared `checked_fungible_assets` set. Either: (1) track STX coverage in a separate boolean/flag per principal rather than inserting sentinel `AssetIdentifier`s into the same set used for `Fungible` post-conditions, or (2) reject `Fungible`/`Nonfungible` `AssetInfo` values whose derived `AssetIdentifier` equals `AssetIdentifier::STX()` or `AssetIdentifier::STX_burned()` at parse/validation time, or (3) add an explicit `AssetKind` discriminant to `AssetIdentifier`/the checked-set key so a forged `Fungible` entry can never satisfy the STX coverage check.

### Proof of Concept
1. Attacker constructs a transaction that will actually transfer STX from their own account (e.g., via `stx-transfer?` in a contract call), so the real `AssetMap` will contain `origin → {AssetIdentifier::STX() → amount}`.
2. Set `post_condition_mode = Deny` (or `Originator`).
3. Attach a single `TransactionPostCondition::Fungible(PostConditionPrincipal::Origin, AssetInfo { contract_address: StacksAddress::new(0, Hash160([0;20])), contract_name: "STX", asset_name: "STX" }, FungibleConditionCode::SentLe, 0)`.
4. Because `contract_address`/`contract_name` collide with `StandardPrincipalData::null_principal()` + `"STX"`, the derived `AssetIdentifier` in `check_transaction_postconditions` equals `AssetIdentifier::STX()`.
5. `get_fungible_tokens` returns `None` (STX lives in `stx_map`, not `token_map`) → `amount_sent = 0`, so `SentLe 0` trivially passes, and `AssetIdentifier::STX()` is inserted into `checked_fungible_assets[origin]`.
6. In the enforcement pass over `asset_map.to_table()`, the real STX transfer entry under key `AssetIdentifier::STX()` is found in `checked_fungible_assets[origin]` (due to step 5) and the check passes — despite no real STX amount check having ever occurred, allowing the STX to move in violation of the transaction's real post-condition intent.
