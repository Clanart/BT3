### Title
Unbounded length-prefix walk in `is_atom_canonical` can raise an uncaught `IndexError` on every mempool spend-bundle submission - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()`/`is_clvm_canonical()` in `chia/full_node/mempool_manager.py` re-parse the raw serialized `puzzle_reveal` and `solution` bytes of every submitted coin spend to decide canonical-form eligibility (DEDUP), but unlike the sibling parsers in `chia/full_node/full_block_utils.py`, they perform **no bounds checking** of the CLVM atom length prefix against the remaining buffer length before indexing into it. This mirrors the CVE-2016-10722 bug class: an attacker-controlled length/size field is trusted and used to walk/index a buffer without validating it stays within the buffer.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` decodes a multi-byte CLVM atom length prefix (1–6 bytes) and then, in the `for i in range(prefix_len)` loop, repeatedly does `offset += 1; atom_len |= clvm_buffer[offset]` with no check that `offset < len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()`, its caller, also advances `offset` by the returned `atom_len` (again attacker-controlled and unchecked against the buffer size) and continues the `while True` loop reading `clvm_buffer[offset]` on the next iteration: [2](#0-1) 

Contrast this with `full_block_utils.py`'s equivalent low-level parsers (`skip_bytes`, `generator_from_block`, `block_info_from_block`), which explicitly validate every length field against the remaining buffer and raise a controlled `ValueError` instead of indexing out of bounds: [3](#0-2) [4](#0-3) 

`is_clvm_canonical()` is invoked unconditionally, for **every** coin spend in every submitted spend bundle, in `MempoolManager.validate_spend_bundle()`: [5](#0-4) 

This is reached from `MempoolManager.add_spend_bundle()`, the mempool admission path invoked for every wallet/RPC-submitted transaction: [6](#0-5) 

Because Python `bytes` objects are memory-safe, out-of-bounds indexing raises `IndexError` rather than corrupting heap memory (unlike the C-based `partclone.fat` bug). However, none of `is_clvm_canonical`, `validate_spend_bundle`, or `add_spend_bundle` catch `IndexError`, so a crafted `puzzle_reveal`/`solution` byte sequence that produces an out-of-range atom-length walk turns into an unhandled exception at spend-bundle admission time instead of a clean `Err.INVALID_COIN_SOLUTION` rejection.

### Impact Explanation
The severity is materially lower than the original CVE because Python bounds-checks prevent memory corruption/RCE. The practical impact here is a spend-triggered exception in the mempool admission path: a single unprivileged submitter can craft a `puzzle_reveal` or `solution` whose non-canonical multi-byte length prefix, when walked by `is_atom_canonical`, runs past the end of the buffer before hitting the length that satisfies `tokens_left == 0`. Since this check runs unconditionally on the raw coin-spend bytes for every incoming spend bundle (not only DEDUP-eligible ones), an uncaught `IndexError` there could disrupt transaction processing for that request instead of returning the intended `INVALID_COIN_SOLUTION` error, which is a validation/availability defect at consensus-adjacent mempool admission code rather than a memory-safety or asset-theft bug.

### Likelihood Explanation
This code path is reached by construction for every spend bundle that reaches `validate_spend_bundle` (i.e., every transaction that passes the earlier Rust `validate_clvm_and_signature` cost/condition pass), and the buffers passed in (`bytes(coin_spend.puzzle_reveal)`, `bytes(coin_spend.solution)`) are attacker-supplied raw bytes under the submitter's full control. The existing test suite (`chia/_tests/core/mempool/test_mempool_manager.py::test_mempool_requires_canonical_clvm`) exercises exactly this function with non-canonical prefixes and expects a clean `INVALID_COIN_SOLUTION`, but only for prefixes that stay within-buffer; it does not appear to cover a length prefix crafted to walk past the end of the buffer, so this edge case does not appear to be defended against by tests I was able to inspect.

### Recommendation
Add explicit bounds checks in `is_atom_canonical`/`is_clvm_canonical` before every `clvm_buffer[offset]` access and before advancing `offset` by `atom_len`, mirroring the defensive style already used in `chia/full_node/full_block_utils.py` (`skip_bytes`, `generator_from_block`), returning `False`/raising a handled error instead of allowing an `IndexError` to propagate. Additionally, wrap the call site in `validate_spend_bundle` (or the function itself) to catch any parsing exception and translate it to `Err.INVALID_COIN_SOLUTION`, ensuring malformed input can never surface as an unhandled exception during mempool admission.

### Proof of Concept
Conceptual PoC (not verified against a live Rust CLVM parser, since I could not execute code in this environment):
1. Construct a `solution`/`puzzle_reveal` byte buffer whose overall structure is accepted by the Rust CLVM deserializer (so it passes `pre_validate_spendbundle`'s `validate_clvm_and_signature` and yields valid `SpendBundleConditions`).
2. Within that buffer, craft an atom whose length-prefix leading byte selects the 6-byte-prefix encoding (`0b11111100` pattern, `prefix_len = 5`) but where the buffer ends fewer than 5 bytes after the prefix byte, positioned so it is reached as the "current" token during `is_clvm_canonical`'s walk (e.g., embedded as a not-outermost atom that CLVM's real deserializer still accepts due to differing tolerance/back-reference handling versus this simplified canonical-form walker).
3. Submit the resulting `SpendBundle` via the wallet/RPC `push_tx` path.
4. `MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` / `...solution)`, which walks into `is_atom_canonical`, and `clvm_buffer[offset]` raises `IndexError` once `offset` exceeds `len(clvm_buffer) - 1`, propagating as an unhandled exception instead of returning `Err.INVALID_COIN_SOLUTION`.

I was not able to run the Rust CLVM deserializer in this environment to confirm it would accept a buffer shaped this way while still causing `is_atom_canonical` to run out of bounds; this would need to be validated with a live Devin session that can execute the full mempool test harness (`chia/_tests/core/mempool/test_mempool_manager.py`) with a crafted buffer.

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)

def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
