### Title
`BandwidthManager.onAccept` fails to verify the sender module ID, allowing any Hyperbridge-chain module to drain the manager's treasury - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.onAccept` authenticates inbound governance messages (`SetTiers`, `Withdraw`) by checking only that `request.source` equals the Hyperbridge state machine, without ever validating `request.from` against the expected `pallet-bandwidth` module ID (`PALLET_BANDWIDTH_MODULE_ID = "BWMARKET"`). Every other authenticated app in this codebase (e.g. `HyperFungibleToken.onAccept`) binds both the source chain *and* the sender's module/contract identity before trusting a message body. This contract only checks the chain.

### Finding Description
`onAccept` is protected by `onlyHost` and a chain-level check: [1](#0-0) 


No check compares `request.from` to `PALLET_BANDWIDTH_MODULE_ID`, even though that constant is declared for exactly this purpose. By contrast, `HyperFungibleToken.onAccept` explicitly binds both chain and module identity: [2](#0-1) 

The project's own documentation confirms this is a real asymmetry, not a stylistic choice: the inbound purchase path (pallet-side) strictly checks `request.from` against the registered manager address, while the manager-side `onAccept` explicitly does **not** perform a module-id lookup: [3](#0-2) 

Because the ISMP `from` field on a Substrate-originated message is set by whichever pallet performs the dispatch (see `pallet_bandwidth::dispatch_governance` setting `from: PALLET_BANDWIDTH.0.to_vec()`), any other module or pallet on the Hyperbridge chain that has (or gains, via upgrade, misconfiguration, or a bug in a different pallet) the ability to dispatch an ISMP POST request with an attacker-chosen `to`/`body` can address that message to a deployed `BandwidthManager` contract. Since `BandwidthManager.onAccept` only verifies the source *chain* and not the module identity, such a message — even though it did not originate from `pallet-bandwidth` — will be accepted and its `Withdraw` action executed, transferring the manager's entire fee-token/native-ETH treasury to an attacker-controlled `beneficiary`.

### Impact Explanation
A successful forged `Withdraw` message drains all funds held by `BandwidthManager` (accumulated `purchase()` fee-token payments and any native ETH), sending them to an arbitrary `beneficiary` chosen by the forger. This is a direct "stealing/loss of funds" and "false state acceptance" impact under the bounty scope: an admin-only treasury operation becomes reachable without going through the legitimate `pallet-bandwidth::dispatch_withdraw` (which is gated by `AdminOrigin`), purely because the EVM-side module binding is missing.

### Likelihood Explanation
Exploitation requires the ability to dispatch an ISMP POST request from the Hyperbridge chain with an arbitrary `from`/`to`/`body` triple that ultimately routes to the target `BandwidthManager` address. This is not achievable by a normal external EVM caller alone — it depends on the existence of some other message-origination path on Hyperbridge that a non-privileged party can trigger with a controlled `to`/`body`. I was not able to confirm within the indexed code whether such a permissionless dispatch primitive currently exists elsewhere in the runtime; if it does (now or after a future pallet addition/upgrade), this contract offers no defense at all, whereas comparable apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`) do. This is precisely the class of "wrong module binding" issue the bounty scope calls out, and the codebase's own documentation flags the missing check as deliberate (rather than accidental), which increases confidence this is a genuine, provable gap rather than a false positive — but the exact triggering path from an unprivileged external account is not fully confirmed from the available files.

### Recommendation
Add a module-id check to `BandwidthManager.onAccept` mirroring the check already used by `pallet-bandwidth` and by `HyperFungibleToken`:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
if (keccak256(request.from) != keccak256(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
This binds both chain and sender module identity symmetrically with the pallet-side check (`request.from` must equal the registered manager), closing the asymmetry described in the project's own governance documentation.

### Proof of Concept
1. Assume a Hyperbridge-chain actor (any pallet/module capable of dispatching an ISMP POST, not necessarily `pallet-bandwidth`) crafts a `DispatchPost` with `dest = <EVM chain hosting BandwidthManager>`, `to = <BandwidthManager address>`, and `body = [ACTION_WITHDRAW] || abi.encode(Withdrawal{token: feeToken, beneficiary: attacker, amount: fullBalance})`.
2. The message is relayed and finalized through the normal ISMP flow; `request.source` correctly equals the Hyperbridge state machine id (since it truly originated there), satisfying the only check present in `onAccept`.
3. `EVMHost` calls `BandwidthManager.onAccept(incoming)`. The `onlyHost` and `request.source == hyperbridge` checks both pass.
4. `onAccept` decodes the `Withdraw` action and executes `IERC20(feeToken).safeTransfer(attacker, fullBalance)` (or a native ETH transfer), draining the contract — without ever verifying that the message actually came from `pallet-bandwidth` (`request.from == "BWMARKET"`).

```text
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
```
