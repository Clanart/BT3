### Title
Unauthenticated output-kind classification lets any sender forge "internal" outputs (Branch/Change/Forwarded) by paying to publicly derivable offset addresses - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Evmos flaw (a privileged action gated only by a claimed/implicit channel, with no authorization check that the counterparty was allowed to exercise it), `Scanner::scan_transaction` classifies any transaction output paying to a registered `script_pubkey` as an output of the corresponding internal kind — `External`, `Branch`, `Change`, or `Forwarded` — without authenticating that the output was actually produced by the protocol. The offsets for `Branch`, `Change`, and `Forwarded` are deterministic (`Secp256k1::hash_to_F(KEY_DST, b"branch"/"change"/"forward")`), so any unprivileged third party can derive the internal addresses from the public group key and send an arbitrary transaction to them. The scanner then reports these as `Branch`/`Change`/`Forwarded` outputs with empty `data`, instead of as `External` deposits.

### Finding Description
`Scanner::register_offset` maps offset scalars to P2TR scripts and `scan_transaction` returns a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts`, keyed only by script match (`networks/bitcoin/src/wallet/mod.rs:199-214`). In `get_outputs` (`processor/src/networks/bitcoin.rs:686-740`), the kind is recovered via `kinds[offset_repr_ref]` and the Serai instruction `data` is populated **only** when `output.kind == OutputType::External` (lines 730-735). Since `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` are `hash_to_F` of public constants (lines 308-344) and the group `key` is public, anyone can compute `key + G*offset` and the corresponding `p2tr_script_buf` and pay to it. Like the Evmos attacker's unauthorized IBC channel triggering privileged claims migration, an unauthorized external transaction here triggers the privileged "internal output" classification path.

### Impact Explanation
- A user (or attacker) sending a deposit with an `InInstruction` data payload to the `Change`/`Branch`/`Forwarded` address has the output registered as an internal output: `data` is never populated, so the attached instruction is silently dropped. The funds are credited to the multisig but the depositor's intent (mint/route) is never executed — funds received but not credited to the sender's purpose, analogous to claims being migrated by an unauthorized caller.
- Conversely, forged `Branch`/`Forwarded` outputs enter the scheduler's internal-output queue, where branch inputs carry assumptions about origin/structure; an attacker-shaped branch output can be scheduled into a `SignableTransaction` and cause the validators to sign spends including an input whose real semantics differ from what the kind tag asserts.

### Likelihood Explanation
Reachable by any unprivileged party able to send a Bitcoin transaction: the group key is public, offsets are deterministic hashes of constants, and `p2tr_script_buf` is a public function. No validator status, collusion, or RPC access required. Exploitation cost is a single transaction; the misclassification is deterministic.

### Recommendation
Authorize internal-kind classification the way the Evmos patch authorized channels: treat script match as necessary but not sufficient. For `Branch`/`Change`/`Forwarded` outputs, additionally require the funding transaction to satisfy a protocol-authenticatable property (e.g., spend a known prior output, or carry a recognizable marker/commitment), or restrict the classification: only classify `Branch`/`Change` when the spending relationship chains from outputs Serai itself created, and treat unmatched payments to internal addresses as `External` deposits so their `data`/origin is still processed.

### Proof of Concept
1. Observe the current multisig group key `K` (public on-chain / from `GeneratedKeyPair`).
2. Compute `offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` (incrementing by 1 until `K + G*offset` has even Y, mirroring `register_offset`).
3. Construct `addr = p2tr_script_buf(K + G*offset)`.
4. Broadcast any transaction paying ≥ dust to `addr` — optionally with an OP_RETURN `InInstruction` to show intent is dropped.
5. `get_outputs` calls `scanner.scan_transaction(tx)`, which matches the script in `self.scripts`, returns `ReceivedOutput { offset }`, and `kinds[offset_repr_ref]` yields `OutputType::Change`; the loop at `processor/src/networks/bitcoin.rs:731-735` skips `data` population, so the output is emitted as an internal `Change` output with empty `data` and the attacker's tx as `presumed_origin`.
