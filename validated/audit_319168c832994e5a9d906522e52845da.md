### Title
Payout crediting relies solely on unauthenticated OP_RETURN data, letting a third party redirect operator credit via SIGHASH_SINGLE|ANYONECANPAY malleability - (File: core/src/operator.rs, core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
`Operator::withdraw` (core/src/operator.rs:630-637) only verifies the user's Schnorr signature over `calculate_sighash_txin(0, SinglePlusAnyoneCanPay)`, which commits solely to input 0 and output 0 of `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436). The OP_RETURN output (index 2, embedding `operator_xonly_pk`) and any other inputs/outputs are unconstrained by that signature. `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2353) later attributes the withdrawal to whichever `operator_xonly_pk` it parses out of the OP_RETURN of the transaction that actually ends up spending the withdrawal UTXO on-chain — with no check that this operator's own funds paid for the output.

### Finding Description
The binding the system is supposed to enforce is: `payout_payer_operator_xonly_pk` (stored via `update_payout_txs_and_payer_operator_xonly_pk`, read via `get_first_unhandled_payout_by_operator_xonly_pk`, core/src/database/verifier.rs:198-313) == the operator whose own BTC funded `output_txout` (index 0) of the confirmed payout tx.

Because the taproot key-spend witness for input 0 is just the Schnorr signature itself and the sighash type is `SinglePlusAnyoneCanPay`, that witness is valid for *any* transaction that reuses the same input-0 outpoint/prevout and the same output-0 (script+amount) — regardless of any other inputs or outputs. This is exactly the well-known ANYONECANPAY/SINGLE malleability property, and `create_payout_txhandler` intentionally leaves the OP_RETURN (operator identity) and the funding inputs uncommitted.

Attack path:
1. Attacker observes any operator A's broadcast (unconfirmed) payout tx: input 0 (Citrea withdrawal UTXO + valid keypath witness), output 0 (fixed user payout), output 1 (anchor), output 2 (OP_RETURN with A's `xonly_pk`).
2. Attacker crafts a competing transaction reusing the identical input 0 outpoint and witness, output 0 unchanged, but with attacker-supplied funding input(s) to cover the payout value, and a new OP_RETURN containing operator B's real, currently-registered `xonly_pk` instead of A's.
3. Attacker broadcasts this with a higher fee so it confirms first (or in place of A's version), double-spending the withdrawal UTXO.
4. `Verifier::update_finalized_payouts` (core/src/verifier.rs:2299-2343) finds whichever tx actually spent the withdrawal UTXO (matched by `bitcoin_syncer_spent_utxos` on outpoint, core/src/database/verifier.rs:170-196), parses its OP_RETURN via `parse_op_return_data`, and writes B's `xonly_pk` into `payout_payer_operator_xonly_pk` with no cross-check against B's actual funding of the output.
5. Operator B's own automation, `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111), polls `get_first_unhandled_payout_by_operator_xonly_pk(B)`, finds this withdrawal, and legitimately calls `Operator::handle_finalized_payout`, proceeding to sign and broadcast its own Kickoff/Reimburse chain (core/src/builder/transaction/operator_reimburse.rs:341-385) — claiming reimbursement funded by the attacker, not B. Meanwhile A's version of the payout tx conflicts with the confirmed one and can never confirm, so A can never be credited for that withdrawal (`get_first_unhandled_payout_by_operator_xonly_pk` never returns a row for A because `payout_payer_operator_xonly_pk` was written for B).

No existing guard intercepts this: `Operator::is_profitable` and `SECP.verify_schnorr` (core/src/operator.rs:605-637) run only inside the honest operator's own `withdraw()` RPC call and are bypassed entirely since the attacker broadcasts directly to Bitcoin; `update_finalized_payouts` trusts the OP_RETURN unconditionally; nothing in the Kickoff/Reimburse presigned-transaction graph verifies that the crediting operator's own capital funded output 0.

### Impact Explanation
- Operator B can be credited (and can proceed to `handle_finalized_payout` → sign Kickoff/Reimburse) for a payout it never funded, matching the Critical category "an operator reimbursed for a payout it never funded."
- Operator A, who genuinely constructed and (initially) broadcast the payout, permanently loses the ability to be credited for that withdrawal once the withdrawal UTXO is spent by the substituted transaction, matching "an honest operator permanently unable to be reimbursed."
- This is repeatable for any withdrawal index where an attacker can observe/intercept an operator's payout transaction before its own confirmation, and for any currently-active operator's `xonly_pk` an attacker chooses to embed, so the blast radius spans all deposits/withdrawals and all operators in the system.

### Likelihood Explanation
Preconditions: attacker must (a) observe the unconfirmed input-0/output-0 pair (visible in mempool or reconstructible from Citrea's public withdrawal-UTXO data and the user's off-chain signature, which is also given to operators and thus not inherently secret), and (b) front the BTC needed to complete output 0 plus fees, then win the fee race to get it mined first (RBF/fee-bump). No verifier, operator, or aggregator privilege, TLS cert, or key share is required — only broadcast capability and BTC/fee budget, consistent with the "unprivileged attacker" threat model. The economic cost is nontrivial (attacker must front the full payout amount, which goes to the legitimate withdrawing user, not to the attacker), making this primarily a griefing/sabotage vector rather than a self-enriching one for a lone attacker, but it is fully feasible and requires no collusion from operator B (B's automation reacts automatically to the DB state written by the verifier).

### Recommendation
Bind the operator identity into the signed portion of the payout transaction so the SIGHASH_SINGLE|ANYONECANPAY signature commits to it — e.g., require `SIGHASH_ALL` (or `SIGHASH_NONE`/`SIGHASH_SINGLE` without `ANYONECANPAY`, and additionally commit to the OP_RETURN output) for the payout tx's input 0, or restructure `create_payout_txhandler` so the OP_RETURN output is at a fixed pre-signed index that is covered by the sighash (not `SinglePlusAnyoneCanPay`'s single-output commitment). Alternatively, require operators to pre-register/commit off-chain (in the aggregator/verifier DB) which payout transaction (full txid, not just outpoint) they intend to broadcast for a given withdrawal index before crediting, and reject any payout observed on-chain whose txid doesn't match a pre-committed candidate from a known operator.

### Proof of Concept
```
cargo test -p core --test <payout_malleability_credit_hijack>
```
Test plan:
1. Set up two mocked operators A and B with distinct `xonly_public_key`s in the test harness (`core/src/test/common/*`), both registered as valid operators for the same deposit.
2. Have operator A call `Operator::withdraw` to build/sign/broadcast a payout tx `tx_A` (input 0 = withdrawal UTXO, output 0 = user payout, OP_RETURN = A's xonly_pk), but do NOT let it confirm.
3. Craft `tx_B`: same input 0 outpoint and witness taken byte-for-byte from `tx_A`, same output 0, but funded from a separate test wallet, with OP_RETURN replaced by B's `xonly_pk`, and a higher fee.
4. Broadcast `tx_B` and mine it (excluding `tx_A`), asserting `tx_A` is rejected/evicted as a conflicting spend.
5. Run `Verifier::update_finalized_payouts` (via block sync) and assert `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` / `get_payout_info_from_move_txid` returns B's xonly_pk, not A's.
6. Run `PayoutCheckerTask::run_once` for operator B and assert it succeeds, proceeding to `handle_finalized_payout` and eventually building `create_reimburse_txhandler` for B.
7. Assert that running the same `PayoutCheckerTask` for operator A returns `Ok(false)` (no unhandled payout ever found for A), proving A is permanently unable to be credited for this withdrawal.
