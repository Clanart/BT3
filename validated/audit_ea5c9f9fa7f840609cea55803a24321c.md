## Analysis: Division-by-zero analog found in `kaiax/staking` reward-splitting logic

I found a concrete analog to the reported `estimateWithdrawalAmounts` division-by-zero bug: the `consolidatedNode.Split()` function in the Kaia reward/staking modules divides by an unchecked, potentially-zero denominator when splitting block-proposer rewards between a validator's CN staking and Consensus-Liquidity (CL) staking pool.

### Title
Division-by-zero panic in `consolidatedNode.Split()` when a proposer's consolidated CN and CL staking amounts both truncate to zero - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split()` computes `totalAmount = cnAmountBig + clAmountBig` and then divides by it without checking for zero, exactly analogous to the reported `_totalSupply` division-by-zero pattern. This function is invoked every block during deferred reward finalization (`FinalizeState`) whenever the block proposer has a registered `CLStakingInfo`.

### Finding Description
`Split()` is defined as: [1](#0-0) 

It is called from the reward module's proposer/fund assignment routines, which run on every block during deferred reward distribution: [2](#0-1) [3](#0-2) 

`cn.StakingAmount` and `CLStakingInfo.CLStakingAmount` are both derived by truncating wei amounts to whole KAIA units via integer division, which can yield `0` for small amounts: [4](#0-3) 

Separately, validator qualification has an explicit fallback: if every council member's CN staking amount is below `minStake` (e.g. after a governance-driven `reward.minstake` increase, or before validators have staked enough), the code intentionally makes everyone qualified regardless of actual stake: [5](#0-4) 

Combining these: if the current block proposer (a) has a CN staking amount that truncates to `0` KAIA (a valid, tested state — see `expectedConsolidated` entries with `a0` and a non-nil `CLStakingInfo` in the staking tests) and (b) has a `CLStakingInfo` whose `CLStakingAmount` also truncates to `0` (e.g., delegated less than 1 KAIA, or newly registered CL pool with no delegation yet), then `totalAmount` in `Split()` becomes `0`, and `clAmount.Div(clAmount, totalAmount)` panics (`big.Int` division by zero is a runtime panic in Go, not a recoverable error). [6](#0-5) 

### Impact Explanation
`FinalizeState()`/`getDeferredRewardFull*` run deterministically on every full node processing the block (they are part of core state-transition/reward accounting), so a panic here halts every honest node identically when they reach that block — a full chain liveness failure triggered by ordinary staking/delegation activity rather than by any privileged or malicious peer/consensus message. This falls squarely within the allowed "staking and reward distribution" / "state transition and gas/burn accounting" analog classes.

### Likelihood Explanation
The conditions are reachable through normal, unprivileged transactions:
- Any staker can create a CN staking contract with an arbitrarily small stake and register it in the AddressBook.
- Any delegator can create/leave a CL pool registered to a node with a sub-1-KAIA delegation (or none at all), which truncates to `0`.
- The "all validators demoted → nobody demoted" fallback is an explicit design branch (not a rare edge case) that allows under-staked validators to remain qualified and be selected as proposer.

### Recommendation
In `consolidatedNode.Split()`, guard against `totalAmount.Sign() == 0` before dividing (e.g., return `(amount, big.NewInt(0))` or `(big.NewInt(0), amount)` when `totalAmount == 0`), mirroring the recommended fix in the original report (checking the denominator before dividing).

### Proof of Concept
1. Governance temporarily raises `reward.minstake` (or genesis/early-network state) such that no CN meets `minStake`; per `getDemotedValidatorsIstanbul`, all council members become "qualified" despite sub-`minStake` CN amounts.
2. A validator's CN staking amount is left at a value that truncates to `0` KAIA (`stakingAmounts[i] = Div(amount, KAIA)`).
3. The same validator's node registers a `CLStakingInfo` (via CL pool registration) with a delegation amount that also truncates to `0` KAIA.
4. When this validator is selected as block proposer (possible under the "all demoted → none demoted" fallback, or after Prague/CL rollout with a genuinely small delegation), `FinalizeState` calls `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` → `cn.Split(proposer)`.
5. `totalAmount = cnAmountBig(0) + clAmountBig(0) = 0`; `clAmount.Div(clAmount, totalAmount)` panics, crashing every node executing that block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

func getDemotedValidatorsIstanbul(council *valset.AddressSet, si *staking.StakingInfo, pset gov.ParamSet) *valset.AddressSet {
	var (
		demoted        = valset.NewAddressSet(nil)
		singleMode     = pset.GovernanceMode == "single"
		governingNode  = pset.GoverningNode
		minStake       = pset.MinimumStake.Uint64() // in KAIA
		stakingAmounts = collectStakingAmounts(council.List(), si)
	)

	// First filter by staking amounts.
	for _, node := range council.List() {
		if uint64(stakingAmounts[node]) < minStake {
			demoted.Add(node)
		}
	}

	// If all validators are demoted, then no one is demoted.
	if demoted.Len() == len(council.List()) {
		demoted = valset.NewAddressSet(nil)
	}

	// Under single governance mode, governing node cannot be demoted.
	if singleMode && demoted.Contains(governingNode) {
		demoted.Remove(governingNode)
	}
	return demoted
}
