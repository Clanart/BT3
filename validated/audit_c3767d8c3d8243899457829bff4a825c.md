### Title
Panic (null-equivalent index) in PedPoP blame evaluation lets an out-of-range `Participant` crash the verifier - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The analog of CVE-2021-32276 (NULL dereference → DoS) in Serai is an unchecked map index on an attacker-controlled participant index inside the PedPoP blame path. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]`. Since `Participant::new` only rejects the value `0`, an accusation naming any `Participant` in `(n, u16::MAX]` causes a panic instead of an error, aborting the caller (e.g., the processor's `VerifyBlame` handler).

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys and commitments only for participants `1..=n` [1](#0-0) . However, `blame()` / `blame_internal()` accept `sender` and `recipient` as free-form `Participant` values [2](#0-1) . `Participant::new` validates only that the index is non-zero — there is no upper bound vs. `n` [3](#0-2) .

Inside `decrypt_with_proof`, the proof branch performs `self.enc_keys[&decryptor]` [4](#0-3) , which panics on a missing key when `recipient > n`. Even if `proof` is `None`, the share-validity check later dereferences `self.commitments[&sender]` for an out-of-range `sender` [5](#0-4) .

On the deployment path, `CoordinatorMessage::VerifyBlame` carries an `accuser`/`accused` parsed from a tributary transaction whose only validation is `Participant::new` (non-zero check), then passes them straight into `AdditionalBlameMachine::blame` [6](#0-5) ; the wire parser likewise accepts any non-zero u16 [7](#0-6) .

### Impact Explanation
A panic here is a direct denial of service: the party evaluating blame (a validator's processor) crashes rather than returning a `Participant` verdict. Any `Participant` value `> n` (up to `u16::MAX`) suffices; no valid key share, proof, or threshold cooperation is needed. This mirrors the CVE's profile — a single crafted input reaching an unguarded dereference/index causes availability loss. Severity Medium.

### Likelihood Explanation
The participant indexes reach `blame` from externally supplied accusation data, and `Participant` carries no `<= n` invariant — bounds are only enforced inside `ThresholdParams`/`view`, not on the blame path. The only mitigations are (a) an integrator validating indexes before calling `blame`, and (b) the panic being caught by the runtime. In the observed processor call site neither occurs: `accuser`/`accused` are forwarded unchecked, and `blame` is invoked on a `.unwrap()`ed machine. Whether a non-validator can inject `VerifyBlame` traffic depends on the consensus layer (out of scope), but within the DKG crate the panic is fully reachable via the public `AdditionalBlameMachine::blame` API with attacker-influenced `sender`/`recipient`.

### Recommendation
Validate `sender` and `recipient` against the registered set in `blame_internal` (and `AdditionalBlameMachine::blame`) before indexing: return `PedPoPError::InvalidParticipant`/`MissingParticipant` instead of using `HashMap` index syntax. Alternatively, use `.get(&participant)` and map `None` to an error, and/or tighten `Transaction::read`'s `InvalidDkgShare`/`VerifyBlame` fields to require `Participant <= n`.

### Proof of Concept
```rust
// Setup: n = 2 participant PedPoP DKG completes; we construct the blame machine
// as the processor does in CoordinatorMessage::VerifyBlame.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 2, commitment_msgs).unwrap();

// Attacker-controlled accusation: recipient (accuser) index 0xFFFF is non-zero,
// so Participant::new accepts it, but it is > n.
let bogus_recipient = Participant::new(u16::MAX).unwrap();

// EncryptedMessage::read bytes for `msg` can be any syntactically valid
// (or even invalid) encoding — the panic occurs before content matters.
// With proof = Some(...), decrypt_with_proof evaluates:
//   &self.enc_keys[&decryptor]   // HashMap index on missing key -> panic
machine.blame(sender, bogus_recipient, msg, Some(proof)); // panics (DoS)
```

Exact panic sites:
- `self.enc_keys[&decryptor]` — `crypto/dkg/pedpop/src/encryption.rs` (line ~388), reached when `proof.is_some()`.
- `self.commitments[&sender]` — `crypto/dkg/pedpop/src/lib.rs` (line ~599), reached for an out-of-range `sender` once the message verifies or earlier branches pass.

Uncertain/caveat: the panic requires a panic-uncaught runtime (standard for Serai's processor binaries) and an integrator that forwards unvalidated participant indexes — the in-repo processor does exactly this in `VerifyBlame`. If the deployment wraps calls in `catch_unwind`, impact degrades to per-request failure rather than crash.
