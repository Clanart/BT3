### Title
Unchecked `u64` arithmetic on attacker-influenced amounts bypasses the funds check and wraps the fee computation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` and `SignableTransaction::fee` perform plain `u64` addition, multiplication and subtraction over payment amounts, fees, and input/output values. In release builds these wrap silently. An attacker who can cause large payment amounts to be included (payments originate from user-supplied instructions carrying a `u64` amount) can wrap `payment_sat`, bypass the `NotEnoughFunds` check, and cause the threshold multisig to sign a transaction whose declared outputs exceed its inputs, while `fee()` underflows to ~`u64::MAX`.

### Finding Description
In `SignableTransaction::new`, the arithmetic on public/caller-supplied values is unchecked: [1](#0-0)  `payment_sat` is a raw `sum::<u64>()` over attacker-influenced payment amounts. [2](#0-1)  `needed_fee = fee_per_vbyte * vbytes` is an unchecked multiply. [3](#0-2)  the solvency check `input_sat < (payment_sat + needed_fee)` uses unchecked addition, which can wrap below `input_sat` and pass when the plan is actually unfundable.

Only the change computation is protected (`input_sat.checked_sub(...)` at line 228), leaving the primary accounting unchecked. [4](#0-3)  `fee()` then computes `sum(inputs) - sum(outputs)` with a plain subtraction. When the wrapped check above lets an oversized output set through, this underflows to a wrapped value near `u64::MAX` (or panics under debug/overflow-checks builds).

The contrast with the rest of the codebase shows this is not idiomatic here: the substrate amount types explicitly use `checked_add`/`checked_sub`/`checked_mul` (`substrate/primitives/src/amount.rs:42-62`) and the coins pallet uses `checked_sub`/`checked_add` for every balance mutation.

### Impact Explanation
Two concrete consequences when `payment_sat` or `payment_sat + needed_fee` wraps:

1. `SignableTransaction::new` returns `Ok` for a plan that is not actually fundable. The resulting `Transaction` is what gets threshold-signed via FROST, so the multisig produces a signature over a transaction the coordinator never had the balance for — a signature over an unintended (unspendable, invalid) message, and downstream the processor treats the plan as executed.
2. `SignableTransaction::fee()` returns a wrapped ~`u64::MAX` "fee" or panics. This value is consumed by accounting code (e.g., `instruction.balance.amount.0 -= tx.0.fee()` in `processor/src/multisigs/mod.rs:884`), turning the arithmetic error into corrupted balance accounting or a processor panic — a liveness failure of the signing pipeline.

### Likelihood Explanation
Payment amounts originate from on-chain instructions any user can submit (a `u64` in the `Amount` type). Two payments of ~`u64::MAX/2` each — or one payment near `u64::MAX` — wrap `payment_sat` to a small value. The scheduler will happily amortize and construct a plan around it; the wrapped `NotEnoughFunds` check then passes regardless of real input value, deterministically producing the overflowed state on the first such plan. No collusion or privileged position is needed, only the ability to request payments, which is a public input.

### Recommendation
Use checked arithmetic for all value math in `send.rs`:

- `payments.iter().try_fold(0u64, |a, p| a.checked_add(p.1))` for `payment_sat` (and `input_sat` for symmetry).
- `fee_per_vbyte.checked_mul(vbytes)` for `needed_fee` and `fee_with_change`.
- `input_sat.checked_sub(payment_sat)` / `checked_sub` against `payment_sat + needed_fee` for the funds check, mirroring the existing `checked_sub` used for change at line 228.
- Compute `fee()` with `checked_sub` and surface an error rather than wrapping.

### Proof of Concept
```rust
// networks/bitcoin — attacker causes a Plan whose payments wrap payment_sat
let huge = u64::MAX - 1000;
let payments = vec![(addr(), huge), (addr(), huge)]; // sum wraps to ~u64::MAX - 2001 -> small
// payment_sat + needed_fee wraps below input_sat, so NotEnoughFunds is skipped
let stx = SignableTransaction::new(inputs, &payments, Some(change), None, FEE).unwrap();
// stx is threshold-signed even though outputs >> inputs; tx is invalid on-chain
let fee = stx.fee(); // underflows -> ~u64::MAX (or panic with overflow checks)
```
The signed artifact is unusable and `fee()` poisons downstream balance accounting with a wrapped value.
