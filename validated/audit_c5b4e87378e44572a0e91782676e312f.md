### Title
`Schnorr::verify` emits BIP-340-invalid signatures for odd-Y group keys instead of rejecting them - (File: networks/bitcoin/src/crypto.rs)

### Summary
The external report describes signature verification that only handles one signer class (EOA via `ECDSA.recover`), leaving contract signers (EIP-1271) unable to produce accepted signatures. The Serai analog lives in the BIP-340 Schnorr algorithm wrapper in `bitcoin_serai::crypto`: `Schnorr::verify` produces a serialized signature whenever the inner FROST Schnorr equation holds, but only normalizes the nonce parity — never the group-key parity. For an odd-Y group key `A`, the emitted signature will not verify under BIP-340 (which lifts `x(A)` to the even-Y representative `-A`), yet `verify` returns `Some(sig)`, signaling a successful signing completion that is unspendable on Bitcoin.

### Finding Description
BIP-340 defines verification over x-only keys: the verifier lifts `x(A)` to the even-Y point. Equivalently, a valid signature must satisfy `s·G = R + c·A_even` where `c = H(R_x || A_x || m)` and `R` must itself be even-Y after `s` normalization.

In `networks/bitcoin/src/crypto.rs`, `Hram::hram` hashes `x(R)`, `x(A)` and conditionally negates the challenge when `R` is odd, and `Schnorr::verify` negates `s` when `sig.R` is odd:

```rust
fn verify(
  &self,
  group_key: ProjectivePoint,
  nonces: &[Vec<ProjectivePoint>],
  sum: Scalar,
) -> Option<Self::Signature> {
  self.0.verify(group_key, nonces, sum).map(|mut sig| {
    sig.s = <_>::conditional_select(&sum, &-sum, needs_negation(&sig.R));
    sig.serialize()[1 ..].try_into().unwrap()
  })
}
```

The inner check (`SchnorrSignature::verify` in `crypto/schnorr/src/lib.rs`) computes `R + c·A − s·G == 0` with the *actual* `group_key` `A`, not the even-lifted `-A`. So when `A` is odd-Y:

- the share-verification/completion equation uses `A`,
- the emitted `(R_x, s)` satisfies `s·G = R + c·A`,
- a BIP-340 verifier checks `s·G = R_even + c·(−A)` — which fails.

`verify` returns `Some` instead of rejecting or handling the odd-key case, exactly mirroring the report: the verification path only supports one key class (even-Y) while silently "accepting" another (odd-Y) into an output the downstream verifier rejects.

The fix-up helpers exist but are external and opt-in: `tweak_keys` in `networks/bitcoin/src/wallet/mod.rs` scales keys by `−1` when `needs_negation(group_key)` holds, and `Scanner::register_offset` skips odd offsets. Nothing in `Schnorr::verify` itself enforces the precondition, and its doc comment only documents the point-at-infinity panic — it does not state the group key must be even-Y. Any `ThresholdKeys` set used with `bitcoin_serai::crypto::Schnorr` without first passing through `tweak_keys` (or an output whose effective spend key is odd) produces signatures that complete the FROST protocol yet are consensus-invalid on Bitcoin — i.e., the signature bytes were "verified" by the library but cannot spend the funds.

### Impact Explanation
Funds controlled by an odd-Y group key (or an odd effective spend key) cannot be spent: every FROST signing session completes successfully, `verify` returns `Some`, yet the resulting 64-byte signature is rejected by every Bitcoin node. This is a completeness failure of the signature-verification path, matching the report's impact class (a legitimate signer type cannot produce an accepted signature). At minimum it causes signing failure/liveness loss for affected keys; at worst, outputs locked to such keys are permanently unspendable since no signature scheme on that key can satisfy the P2TR key-path spend.

### Likelihood Explanation
The main pipeline mitigates this by routing keys through `tweak_keys` and only registering offsets whose tweaked point is even. However, `Schnorr` is a public `Algorithm` exposed for `Secp256k1` signing, and `verify`'s only documented contract concerns the point at infinity — there is no documented or enforced even-key requirement. With an odd-Y aggregate key (50% probability for an untweaked DKG output), every signing attempt deterministically produces invalid signatures. Reachability by an unprivileged party depends on integrator usage rather than attacker-controlled bytes, so the practical exposure is lower than the raw FROST signing path; severity is Medium consistent with the source report.

### Recommendation
In `Schnorr::verify` (or in `Hram::hram`), enforce BIP-340 key parity: either return `None`/`panic` when `needs_negation(group_key)` is set, or negate `group_key` (and correspondingly the signed share `sum`/secret semantics) so the emitted signature satisfies the even-lifted key. Additionally, document on `Schnorr` and `tweak_keys` that all keys passed to `sign_share`/`verify` MUST be even-Y. A regression test should assert `verify` rejects (or correctly normalizes) an odd group key rather than emitting a signature that fails `bitcoin::key::XOnlyPublicKey` / `secp256k1::schnorr` verification.

### Proof of Concept
Conceptual: construct `ThresholdKeys<Secp256k1>` whose `group_key()` has odd Y (do not call `tweak_keys`), run the FROST signing flow with `bitcoin_serai::crypto::Schnorr` to completion, and call `verify(group_key, nonce_sums, sum)`. It returns `Some(sig)`. Feeding `sig` to `bitcoin::secp256k1` `verify_schnorr` (or `schnorr::Signature::verify` against `XOnlyPublicKey::from(x(A))`) fails, because the verifier computes `s·G − c·(−A) ≠ R`. The same code path with an even-Y `A` verifies both internally and on-chain — demonstrating the verification accepts one key class and silently produces invalid output for the other.

Confidence note: the residual exposure after `tweak_keys`/`register_offset` normalization is integrator-dependent; if the mandate is that all Bitcoin signing flows already pass through `tweak_keys`, this reduces to an undocumented-contract hardening issue rather than a live exploit path. I could not confirm every call site of `bitcoin_serai::crypto::Schnorr` within the allowed iterations.
