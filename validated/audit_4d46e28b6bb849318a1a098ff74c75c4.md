### Title
Unbounded allocation in `SchnorrAggregate::read` allows remote memory exhaustion via attacker-controlled length prefix - (File: crypto/schnorr/src/aggregate.rs)

### Summary

Analogous to CVE-2020-27174 (an unbounded buffer grown by untrusted input in Firecracker's serial console), `SchnorrAggregate::read` trusts a `u32` count in attacker-supplied bytes and grows a `Vec<C::G>` without any bound other than the attacker's willingness to keep the input stream producing data. An unprivileged party that can feed bytes to this public `read` entry point (or to any caller deserializing a `SchnorrAggregate` over a network/`io::Read` stream) can drive memory usage to roughly `(point encoding size) × count`, up to `u32::MAX` elements (~128+ GB nominally), limited only by how much data they stream — memory that is never released until the read completes or the connection is dropped, and which can be repeated across concurrent connections.

### Finding Description

In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads a little-endian `u32` length and then loops `0 .. len` calling `C::read_G`, pushing each element into an unbounded `Vec`:

```rust
// crypto/schnorr/src/aggregate.rs
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

The loop is driven entirely by the declared count and by whatever bytes the reader keeps yielding. There is no sanity bound on `len` (e.g., relative to the number of signatures actually being aggregated, or a protocol-level maximum), no chunked-read mitigation like the one the codebase itself uses in `networks/ethereum/src/machine.rs` ("A valid DoS would be to claim a 4 GB data is present for only 4 bytes / We read this in 1 KB chunks"), and no cap on how much backing storage the `Vec` grows to. Because `read` accepts any `io::Read`, a length prefix of `0xFFFFFFFF` followed by an endless or large stream of syntactically valid point encodings causes the deserializer to keep allocating — the direct analog of Firecracker's serial-console buffer that grows "without limit when data is sent to the standard input."

Each `C::read_G` requires `GroupEncoding::Repr` bytes (e.g., 32–33 bytes for secp256k1/ed25519), so memory consumed is proportional to bytes delivered but with zero protocol-meaningful limit: the attacker controls growth purely by how much they send, and the allocation persists for the duration of the read. No invalid input is needed — a peer merely sends a huge count and keeps feeding points.

### Impact Explanation

The class is memory-exhaustion DoS against any process that deserializes a `SchnorrAggregate` (or a containing structure) from bytes controlled by an untrusted counterparty. Because allocation scales with attacker-supplied stream length up to ~4 billion points, a single malicious message stream can grow heap usage far beyond intended bounds and, combined with multiple concurrent deserializations, OOM-kill the host process — the same availability impact rated High (CVSS 7.5) in CVE-2020-27174. The read is on an in-scope public API (`crypto/schnorr`), reachable from untrusted bytes per the scope rules, and requires no key material, valid signature, or privileged position.

### Likelihood Explanation

Likelihood depends on deployment: `read` only grows for bytes actually present, so exploitation requires the attacker to stream data continuously rather than triggering amplification from a tiny input. Wherever `SchnorrAggregate` (or a transaction/proof embedding it) is read off a socket without an outer byte limit, an unauthenticated peer can trigger it at will. This is a concrete, remotely reachable, no-cost-per-attempt DoS — Medium.

### Recommendation

Bound the count before allocating. Either take an expected signature count from the caller (as `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs` does with `params.t()`, and `NonceCommitments::read` in `crypto/frost/src/nonce.rs` does with the generator list) or impose a hard `MAX_AGGREGATE_SIGNATURES` and reject larger prefixes. Additionally, where the caller knows the total message size, verify `len` does not exceed `remaining_bytes / point_encoding_len` before entering the loop, or read in bounded chunks as `Call::read` in `networks/ethereum/src/machine.rs` does.

### Proof of Concept

```rust
use std::io;
use serai_schnorr::aggregate::SchnorrAggregate; // illustrative path
use ciphersuite::Secp256k1;

// Attacker stream: u32::MAX count followed by an endless supply of points.
struct Endless;
impl io::Read for Endless {
  fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
    // Emit a valid compressed point on repeat (e.g., generator encoding pattern)
    for b in buf.iter_mut() { *b = 0x02; }
    Ok(buf.len())
  }
}

// This loop pushes up to 4,294,967,295 group elements into `Rs` — heap grows
// without bound for as long as the attacker keeps the stream alive.
let _ = SchnorrAggregate::<Secp256k1>::read(&mut Endless);
```

Prefix bytes: `[0xff, 0xff, 0xff, 0xff]` (count = u32::MAX), then arbitrary valid `GroupEncoding` bytes. Each iteration allocates a new `C::G` entry; no code path caps the vector's growth.
