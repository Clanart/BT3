## Title
Missing zero-value validation on the `governance.kip71.gastarget` parameter causes a network-wide divide-by-zero panic in KIP-71 base fee calculation - (File: `params/kip71_config.go`)

### Summary
The KIP-71 (Magma) base-fee update function `NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without ever checking whether it is zero, while the sibling parameter `BaseFeeDenominator` explicitly guards against the same class of misconfiguration. Because the governance parameter registration for `Kip71GasTarget` uses `noopFormatChecker` (no format validation at all), a value of `0` is accepted and propagated into every node's base fee computation, which is executed by all nodes on every block during header validation.

### Finding Description
`NextMagmaBlockBaseFee` reads `gasTarget := kc.GasTarget` directly from the `KIP71Config` and uses it as a divisor in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

Note that `BaseFeeDenominator` has an explicit zero-guard right above it in the same function ("To avoid panic, set the fluctuation range small"): [3](#0-2) 

No equivalent guard exists for `gasTarget`. `big.Int.Div`/`.Div` on a zero divisor panics at runtime ("division by zero"), which is functionally identical to the CVE-2014-0142 bug class (a zero-value field causing a divide-by-zero crash), just applied to Kaia's KIP-71 dynamic gas pricing instead of QEMU's disk image parsers.

The root cause of reachability is that the governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker` instead of a `v != 0` check like its sibling `Kip71BaseFeeDenominator`: [4](#0-3) 

Governance parameter changes are applied via `PartialParamSet.Add`, which only rejects a value if `param.FormatChecker(cv)` returns false: [5](#0-4) 

Since `Kip71GasTarget`'s checker always returns true, a `GasTarget=0` vote passes validation and is written into the effective `ParamSet`, which is later converted straight into `KIP71Config` and used for consensus-critical header validation: [6](#0-5) 

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked by `BlockValidator.ValidateHeader` for every incoming block on every node (as exercised in the test harness that wires `KIP71Config` from `gov.ParamSet`): [7](#0-6) [8](#0-7) 

### Impact Explanation
Once the effective `GasTarget` parameter becomes `0` at a given block height, every full node and validator computing/validating the next block's base fee via `NextMagmaBlockBaseFee` hits the unguarded `x.Div(x, new(big.Int).SetUint64(gasTarget))` call and panics. Because this code path runs in header validation/consensus block processing on all nodes uniformly, this results in a synchronized chain-wide crash/halt (denial of service) rather than an isolated node crash — the strongest possible impact for this bug class in a blockchain: acceptance/production of blocks becomes impossible for the entire network, a form of state-processing failure/state divergence.

### Likelihood Explanation
`GasTarget` is a live governance parameter (`governance.kip71.gastarget`), changeable at runtime through the standard on-chain governance voting mechanism (header-vote or `GovParamContract`), same as any other KIP-71 parameter. The only thing stopping a governance-approved value of `0` from being applied is `FormatChecker`, and for this specific parameter that checker is a no-op, unlike `BaseFeeDenominator` which explicitly disallows zero. This makes the misconfiguration realistically reachable through the normal governance parameter-update pathway, not just a theoretical edge case.

### Recommendation
Add a `v != 0` format checker to `Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-guard directly in `NextMagmaBlockBaseFee` (similar to the existing `BaseFeeDenominator` fallback) before using `gasTarget` as a divisor.

### Proof of Concept
1. Submit/approve a governance vote setting `governance.kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`). [9](#0-8) 
2. Once the parameter becomes effective at the target block, any node computing the next block's base fee calls `NextMagmaBlockBaseFee` with `parentGasUsed != gasTarget(0)`, entering either the ">" or "<" branch and dividing by `gasTarget`: [10](#0-9) 
3. `big.Int.Div(x, 0)` panics with "division by zero", crashing block processing on every node that reaches this code path, halting the chain.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}
