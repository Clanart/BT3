### Title
SchnorrAggregate::verify accepts a forged aggregate signature when the signer/challenge list is empty - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The OpenSSL CVE-2026-75803 bug class — "verification silently skipped on empty input, success returned without any integrity check being performed" — has a direct analog in Serai's half-aggregated Schnorr signature verification. `SchnorrAggregate::verify` reduces verification to a single multiexp equaling identity; when `keys_and_challenges` is empty, the only remaining pair is `(-s, G)`, so a forged aggregate with zero `Rs` and `s = 0` verifies as valid without any actual signature check occurring.

### Finding Description
`SchnorrAggregate::read` (crypto/schnorr/src/aggregate.rs:77-88) accepts a length-prefixed list of `Rs` where `len = 0` is legal, followed by an arbitrary scalar `s`. `SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146) checks `self.Rs.len() != keys_and_challenges.len()` and returns false on mismatch, but performs no lower bound: with `keys_and_challenges == []` and `Rs == []`, the loop appends nothing, `pairs` becomes just `[(-s, G)]`, and `multiexp_vartime(&pairs).is_identity()` is true whenever `s == 0`. The attacker-supplied "signature" bytes `00 00 00 00 || 0x00*32` therefore verify against an empty signer set.

This is reachable from untrusted bytes through `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs:200-229`, which reads the aggregate via `SchnorrAggregate::read` and passes `signers.iter().zip(challenges)` — an empty `signers` slice yields empty `keys_and_challenges`, and the forged aggregate passes. Any other caller that builds the key/challenge list from a (possibly attacker-influenced or empty) signer set inherits the same vacuous-acceptance.

Note `SchnorrAggregator::complete` (aggregate.rs:175-178) refuses to *produce* an empty aggregate, but nothing prevents an attacker from deserializing one — the read and write sides are asymmetric.

### Impact Explanation
An unprivileged party can fabricate a `SchnorrAggregate` encoding that `verify` reports as valid for a zero-signer statement, i.e., a "signature" over a message no one signed, forging consensus-relevant proof bytes wherever an empty signer/committee list can reach verification. This is the same failure mode as the CVE: a caller sees a successful return while no verification of any signer actually occurred.

### Likelihood Explanation
The cryptographic defect is unconditional — `(empty Rs, s = 0)` always passes `verify` with an empty key list. Exploitability into consensus depends on a caller invoking `verify_aggregate` with zero signers; Tendermint quorum logic normally requires weighted signers, so the practical blast radius is bounded to any code path that treats "verified aggregate" as meaningful without separately enforcing non-empty signers. Medium.

### Recommendation
Reject empty aggregates: in `SchnorrAggregate::read` (or `verify`), require `Rs.len() >= 1` and/or `keys_and_challenges.len() >= 1`, returning an error/`false` for the empty case, mirroring `SchnorrAggregator::complete` which already returns `None` for zero signatures. `Validators::verify_aggregate` should additionally require `!signers.is_empty()`.

### Proof of Concept
```rust
// crypto/schnorr aggregate — for any PrimeGroup Ciphersuite C:
// Forged bytes: u32 len = 0, s = 0
let mut forged = vec![0u8; 4 + C::F::ZERO.to_repr().as_ref().len()];
// len field already zero
let agg = SchnorrAggregate::<C>::read::<&[u8]>(&mut forged.as_slice()).unwrap();
assert_eq!(agg.Rs().len(), 0);
// No signer verified anything, yet verify returns true:
assert!(agg.verify(b"any_dst", &[]));
```
`multiexp_vartime(&[(-C::F::ZERO, C::generator())])` is identity, so `verify` returns `true` for a signature produced by no key — an empty-input verification bypass analogous to EVP_Cipher skipping tag verification on empty ciphertext.
