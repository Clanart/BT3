### Title
Transaction fee computed on pre-finalization output set, omitting the OP_RETURN data output from weight calculation - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` calculates the transaction's weight, vbytes, and resulting `needed_fee` using a snapshot of the outputs taken *before* the OP_RETURN data output is added. The function builds `tx_outs` (payments + OP_RETURN), but the weight/fee helpers are invoked with only the `payments` slice, so the data output — up to 80 bytes of attacker-influenced data — is never priced into the fee. This mirrors the M-1 bug class: a value (the fee) is computed from a stale, pre-operation state and then applied to the final transaction after the state has changed, without re-valuation.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs), the ordering is:

1. `tx_outs` is built from `payments` (line 188-191).
2. The OP_RETURN output is pushed onto `tx_outs` when `data` is specified (lines 193-202).
3. `calculate_weight_vbytes(tx_ins.len(), payments, None)` is called at line 204 — passing `payments`, which does **not** contain the OP_RETURN output.
4. `needed_fee = fee_per_vbyte * vbytes` is computed from that stale snapshot (line 206), and the `TooLowFee` minimum-relay-fee check uses the same understated `vbytes` (line 211).
5. When a change output is considered, `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at line 225 again uses `payments`, still omitting the OP_RETURN output — so the "with change" fee is also underestimated.

`calculate_weight_vbytes` (lines 62-127) builds a mock `Transaction` solely from the slices it is given, so any output not passed in simply does not exist in the fee's valuation. The finalized `SignableTransaction` then carries `tx_outs` (which includes the OP_RETURN) together with the under-priced `needed_fee`, and the change amount (line 228-230) is derived as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is again the stale value.

The actual broadcast transaction is ~90 vbytes larger than the size the fee was priced for (8-byte value + script length + OP_RETURN pushdata up to 80 bytes), so the achieved fee rate is strictly below the caller-specified `fee_per_vbyte`.

### Impact Explanation
- Every `SignableTransaction` carrying embedded data pays a lower effective sat/vbyte than requested; the fee is under-collected relative to the intended rate, exactly analogous to M-1's under-collection from a stale valuation point.
- The `TooLowFee` guard at line 211 is evaluated against the understated vbytes, so a transaction whose real size puts it below `DEFAULT_MIN_RELAY_TX_FEE` can pass the check. Such a transaction is non-standard for relay: it will be signed but rejected/unpropagated, leaving the inputs' funds committed to a transaction that cannot confirm — outputs the coordinator reports as spendable are effectively unspendable until re-signed at a correct fee.
- Change outputs absorb the mispricing error (change is computed against the wrong fee), causing accounting drift between the expected and actual change value.

### Likelihood Explanation
Any transaction built with `data != None` triggers the bug deterministically — no attacker effort is needed beyond supplying the data field (which callers of `SignableTransaction::new` may provide, up to 80 bytes). The miscalculation occurs on the public construction path with no privileged access required. Because the error scales with data length and is zero when `data` is `None`, it silently produces a systematically lower fee rate whenever data is embedded.

### Recommendation
Compute the weight/vbytes over the final output set. Either pass `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or defer the fee computation until after all outputs — payments, data, and change — are fixed, then re-evaluate `needed_fee` and the `TooLowFee` check against the finalized transaction. Concretely: build the complete output list first (payments + OP_RETURN + change decision), then call `calculate_weight_vbytes` once on that final list, mirroring M-1's fix of valuing the fee at the deduction point rather than a pre-mutation snapshot.

### Proof of Concept
```rust
// Conceptual; wallet test context
let (keys, key) = keys();
let scanner = Scanner::new(key).unwrap();
let output = send_and_get_output(&rpc, &scanner, key).await;
let input_sat = output.value();

// A transaction with an 80-byte OP_RETURN data output
let data = vec![0u8; 80];
let payments = [(p2tr_script_buf(key).unwrap(), 1000)];
let tx = SignableTransaction::new(
    vec![output], &payments, None, Some(data), FEE,
).unwrap();

// tx.output includes the OP_RETURN output (3 total incl. payment),
// yet needed_fee was priced on `payments` only.
assert_eq!(tx.tx.output.len(), 2); // payment + OP_RETURN

// The actual fee equals needed_fee computed WITHOUT the ~90-vbyte
// OP_RETURN output:
let actual_vbytes = tx.tx.vsize() as u64;
assert!(tx.fee() < FEE * actual_vbytes);
// i.e. achieved sat/vbyte < FEE: fee under-collected, exactly the
// stale-snapshot mispricing class.
```

The root cause is that `calculate_weight_vbytes` is invoked at send.rs:204 and send.rs:225 with `payments` rather than the already-augmented `tx_outs` containing the OP_RETURN output added at send.rs:193-202, so the fee snapshot is taken before the full transaction state exists.
