### Title
Isolated receiver address for IBC/EVM callbacks is derived only from `(channelID, sender)`, allowing an attacker to sweep any token balance accumulated at that address via an arbitrary-calldata callback - ([File: x/ibc/callbacks/types/keys.go], [File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`GenerateIsolatedAddress` derives the ICS-20 EVM-callback "isolated receiver" solely from `(destChannelID, sender)`, with no packet sequence, denom, or callback-contract binding. Because `IBCReceivePacketCallback` executes attacker-supplied `calldata` with `msg.sender = isolatedReceiver` (a keeper-privileged, unrestricted EVM call), and the isolated address is reused across every packet a given sender sends over the same channel, an attacker can accumulate or otherwise cause tokens to sit at their isolated address (which the code itself acknowledges can happen, see the "trapped balance" test) and then drain them by supplying calldata that calls `transfer()`/other state-changing functions on any contract the isolated address holds a balance in — completely bypassing the intended "approve then transferFrom of the current packet's amount" flow.

### Finding Description
`GenerateIsolatedAddress` in `x/ibc/callbacks/types/keys.go` computes:
```go
func GenerateIsolatedAddress(channelID string, sender string) sdk.AccAddress {
	return sdk.AccAddress(address.Module(ModuleName, []byte(channelID), []byte(sender))[:20])
}
``` [1](#0-0) 

This is deterministic per `(channelID, sender)` pair only — independent of packet sequence, denom/token, or the `dest_callback` contract chosen in the memo. `IBCReceivePacketCallback` in `x/ibc/callbacks/keeper/keeper.go` uses this address as the ICS-20 receiver and, after validating it matches, performs two EVM calls: an `approve` for the current packet's token/amount, followed by an arbitrary, attacker-controlled calldata call with `msg.sender = receiverHex` (the isolated address) and `commit = true`:
```go
res, err = k.evmKeeper.CallEVMWithData(cachedCtx, receiverHex, &contractAddr, cbData.Calldata, true, remainingGas)
``` [2](#0-1) 

Because `commit=true` and `from=receiverHex`, this call gives the attacker's `contractAddr` the ability to act with full authority of `receiverHex` — it is not limited to the `approve`d token/amount from the current packet. It can call `transfer()` (or any other function) directly on **any** ERC-20/token-pair contract where the isolated address currently holds tokens.

The isolated address is not single-use: the repository's own tests demonstrate it can legitimately accumulate/trap balances from unrelated packets. For example, `TestOnRecvPacketNativeErc20` shows a packet whose conversion failed leaves its funds sitting in the isolated address:
```go
isolatedAddr := callbacktypes.GenerateIsolatedAddress(path.EndpointA.ChannelID,
    suite.chainB.SenderAccount.GetAddress().String())
trappedBal := evmApp.BankKeeper.GetBalance(evmCtx, isolatedAddr, nativeErc20.Denom)
suite.Require().Equal(recvAmt.String(), trappedBal.Amount.String())
``` [3](#0-2) 

Since the same `(channelID, sender)` pair is reused for every subsequent packet, once any balance ends up at the isolated address (via a trapped/failed conversion, a plain non-callback transfer to the same bech32/hex-equivalent address, dust from a prior callback that didn't fully sweep, or simply a second concurrent in-flight packet from the same sender/channel), the attacker only needs to send one more packet with a `dest_callback` pointing to their own contract and calldata that calls `transfer(attacker, balance)` on whatever token contract holds the balance. The `approve`+`transferFrom` scoping and the final `receiverTokenBalance == 0` check in `IBCReceivePacketCallback` only validate the **current packet's** token pair, not any other asset the isolated address may hold — so this sweep of unrelated tokens goes undetected by that final safety check.

### Impact Explanation
This allows unauthorized, irreversible extraction/theft of user funds held at an isolated ICS-20-callback address that does not belong to the current packet's transferred amount, triggerable entirely by an ordinary unprivileged IBC packet sender/relayer using standard `MsgRecvPacket` flow with a crafted memo. This matches the in-scope critical impact: "theft or unauthorized extraction of user funds ... or token-pair-backed balances."

### Likelihood Explanation
Reachable by any user who can (a) get some balance parked at a victim's isolated address (their own prior failed/partial transfer, a native-ERC20 conversion restriction, or another in-flight packet using the same sender/channel), and (b) submit a subsequent ICS-20 packet from the same `(sender, channel)` with a `dest_callback` pointing at their own contract. No privileged role, validator, or relayer collusion is required — only a standard IBC packet relay through the ordinary transfer + callback middleware path.

### Recommendation
Bind the isolated receiver address to unique, single-use packet context (e.g., include the packet sequence and/or the specific denom/token pair in the `address.Module` derivation) so that it cannot be reused across multiple packets/senders, and/or restrict the arbitrary calldata call so that `msg.sender=isolatedReceiver` can only invoke `transferFrom`/`transfer` on the specific token pair contract associated with the current packet, rejecting calls to arbitrary contracts.

### Proof of Concept
1. Attacker sends packet #1 (destined for chain A) with `sender = S`, `dest_channel = C`, containing a native ERC20 whose destination conversion restriction is intentionally triggered to fail conversion (as shown in `TestOnRecvPacketNativeErc20`), leaving `recvAmt` of the bank-denom token sitting at `isolatedAddr = GenerateIsolatedAddress(C, S)`.
2. Attacker sends packet #2 from the same `sender = S` over the same `channel = C`, with a `dest_callback.address` pointing to an attacker-deployed contract and `calldata` that calls `transfer(attacker, recvAmt)` on the trapped token's ERC20/precompile contract.
3. `IBCReceivePacketCallback` re-derives the same `isolatedAddr` for packet #2, executes the attacker's calldata with `msg.sender = isolatedAddr`, `commit = true`; the attacker's contract calls `transfer()` directly (no `approve`/`transferFrom` needed since `isolatedAddr` is the token owner) moving the trapped balance from packet #1 to the attacker.
4. The post-check `receiverTokenBalance` in `IBCReceivePacketCallback` only checks the current packet's token pair balance is zero, so it does not detect or block the drain of the unrelated, previously trapped token. [4](#0-3)
