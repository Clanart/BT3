### Title
EVM Transaction Sender Authentication Bypass via Unverified Pre-Populated `Derived` Field - (File: x/evm/ante/preprocess.go)

### Summary
The EVM ante pipeline determines the sender of a submitted `MsgEVMTransaction` either by cryptographically recovering it from the ECDSA signature (the normal path) or, if the message already carries a non-nil `Derived` field, by trusting that field outright without re-validating that the signature in `Data` actually corresponds to the `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` it carries.

### Finding Description
`PreprocessUnpacked` is the function responsible for establishing which account is the legitimate signer/sender of an incoming EVM transaction: [1](#0-0) 

If `msgEVMTransaction.Derived` is already non-nil, the function only checks that `PubKey` is non-nil and immediately returns success — treating the message as "already preprocessed" — instead of recomputing `evmAddr`/`seiAddr`/`pubkey` from the raw ECDSA signature bytes (`V, R, S`) in `Data` and comparing them against the claimed `Derived` values. The inline comment ("this means the message has `Derived` set from the outside, in which case we should reject") shows the authors were aware this field can originate from outside the normal ante flow, yet the only guard implemented is a nil check on `PubKey`, not a cryptographic equivalence check between the claimed identity and the actual transaction signature.

This is structurally the same bug class as the reported Android issue: a subsystem relies on a "success"/"already-verified" signal (`Derived != nil`, analogous to `onAuthenticationSucceeded`) rather than requiring the underlying cryptographic proof (a `CryptoObject`/ECDSA signature check) to be independently re-derived and checked at the point of use.

Downstream consumers propagate this same trust without further verification:
- `EVMPreprocessDecorator.AnteHandle` pulls `SenderSeiAddr`/`SenderEVMAddr` directly out of `msg.Derived` and uses them to perform address association and balance checks. [2](#0-1) 
- `EVMSigVerifyDecorator.AnteHandle` uses `Derived.SenderEVMAddr` for nonce validation and sets it as the EVM/Sei sender address in context, again with no signature re-check. [3](#0-2) 
- `EvmDeliverHandleSignatures` (used on the DeliverTx fast path) explicitly special-cases a pre-populated `Derived`, calling `AssociateAddress` with the embedded `evmAddr`/`seiAddr`/`PubKey` and skipping `CheckAndDecodeSignature` (the actual ECDSA-recovery path) entirely. [4](#0-3) 

By contrast, the genuine derivation path performs real ECDSA recovery via `helpers.GetAddresses`/`RecoverPubkey`, which is bypassed whenever `Derived` is already set: [5](#0-4) 

### Impact Explanation
If the `Derived` field of `MsgEVMTransaction` is attacker-controllable at the point the message is decoded from submitted transaction bytes (i.e., if it is serialized on the wire or otherwise settable before reaching `PreprocessUnpacked`), an attacker could craft a transaction claiming an arbitrary victim's `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` (public keys are generally recoverable/public once an account has transacted) without possessing that account's private key. The EVM ante pipeline would then treat the attacker's transaction as validly signed by the victim, use the victim's nonce, and execute EVM logic (including value transfers) attributed to and paid for by the victim's account — i.e., unauthorized transaction execution/fund loss for accounts whose public key is already known on-chain.

### Likelihood Explanation
Exploitability hinges entirely on whether the `Derived` field can actually be populated by an external, unprivileged submitter before `PreprocessUnpacked` runs (e.g., via the raw protobuf-encoded transaction bytes, or via any RPC/tx-building code path that lets a caller set this field prior to ante processing). I was not able to fully confirm from the generated protobuf code (`x/evm/types/tx.pb.go`) whether `Derived` is included in the wire `Marshal`/`Unmarshal` implementation of `MsgEVMTransaction` or whether it is a purely in-memory/transient field that is always reset to `nil` on decode from network bytes. The explicit "set from the outside" rejection comment in the code strongly suggests the developers anticipated this as a reachable scenario, but the mitigation implemented (checking only `PubKey != nil`) does not perform the cryptographic re-validation needed to close the gap.

### Recommendation
Regardless of how `Derived` becomes non-nil, `PreprocessUnpacked` (and `EvmDeliverHandleSignatures`) should not trust an already-populated `Derived` for signature/identity purposes unless it was set by trusted, prior in-process ante execution (e.g., gate reuse behind a private/unexported flag or an internal-only invocation path incapable of being reached with attacker-controlled input). At minimum, whenever a message enters the ante pipeline from the mempool/consensus layer, the code should unconditionally recompute the sender identity from the raw ECDSA signature bytes (as `CheckAndDecodeSignature`/`GetAddresses` already do) and reject the transaction if the recomputed identity does not match any pre-populated `Derived` fields, closing the analog of the "must require the CryptoObject/cryptographic proof for authentication" recommendation from the reference report.

### Proof of Concept
Not independently reproduced — reachability depends on confirming whether `Derived` survives protobuf decode of an externally submitted `MsgEVMTransaction`. This should be validated (e.g., by crafting a raw `MsgEVMTransaction` with `Derived` set to an arbitrary victim address/pubkey and a `Data` payload not actually signed by that victim, submitting it via `CheckTx`, and observing whether `PreprocessUnpacked`/`EvmDeliverHandleSignatures` accept and process it as the victim's transaction) before treating this as confirmed-exploitable.

func EvmDeliverHandleSignatures(ctx sdk.Context, ek *evmkeeper.Keeper, txData ethtx.TxData, chainID *big.Int, msg *evmtypes.MsgEVMTransaction) (common.Address, sdk.AccAddress, derived.SignerVersion, error) {
	if msg.Derived != nil {
		if msg.Derived.PubKey == nil {
			return common.Address{}, nil, 0, sdkerrors.ErrInvalidPubKey
		}
		evmAddr := msg.Derived.SenderEVMAddr
		seiAddr := msg.Derived.SenderSeiAddr
		version := msg.Derived.Version
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, msg.Derived.PubKey); err != nil {
			return evmAddr, seiAddr, version, err
		}
		if ek.EthReplayConfig.Enabled {
			ek.PrepareReplayedAddr(ctx, evmAddr)
		}
		return evmAddr, seiAddr, version, nil
	}
