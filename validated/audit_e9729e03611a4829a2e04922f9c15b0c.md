### Title
Out-of-bounds read (unhandled `IndexError`) in CLVM canonical-encoding check on submitted spend bundle solutions - (File: `chia/full_node/mempool_manager.py`)

### Summary
CVE-2024-50597 describes an integer-underflow in NetX Duo's HTTP server caused by insufficient validation of an attacker-controlled length field before it is used to index/advance through a buffer, leading to a crash. The chia-blockchain codebase contains an analogous bug-class instance in the mempool's canonical-CLVM-serialization check, `is_clvm_canonical()` / `is_atom_canonical()`, which advances a byte offset using a length prefix taken directly from an untrusted, attacker-supplied buffer (a spend bundle's puzzle/solution bytes) without validating that the buffer actually contains enough remaining bytes.

### Finding Description
`is_atom_canonical()` decodes a variable-length atom-length prefix (1–6 bytes) from `clvm_buffer` starting at `offset`, then reads `prefix_len` additional bytes by incrementing `offset` and indexing `clvm_buffer[offset]` in a loop, with no bounds check that `offset < len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` drives this loop over an entire serialized CLVM buffer, only asserting the buffer is non-empty up front, and likewise indexes `clvm_buffer[offset]` for each token without checking `offset` stays within bounds before dereferencing it: [2](#0-1) 

Contrast this with the deliberately hardened parsers elsewhere in the same codebase (e.g. `skip_bytes`/`skip_list` in `chia/full_node/full_block_utils.py`), which explicitly check `n > len(buf)` and raise a clean `ValueError` before consuming untrusted length fields: [3](#0-2) 

`is_clvm_canonical`/`is_atom_canonical` lack this equivalent bounds check. A crafted atom whose length-prefix byte (e.g. `0xFC`, requiring 5 additional prefix bytes plus the declared atom length) appears near the very end of the buffer will cause `offset` to be advanced past `len(clvm_buffer) - 1` while indexing, raising an unhandled Python `IndexError` instead of a controlled rejection (`ValueError`/`False`). This mirrors the CVE's root cause: a length field derived from untrusted external input is used to walk a buffer without first confirming enough bytes remain, producing an out-of-bounds access instead of a defensive error return.

This function is used to determine DEDUP eligibility for spends: per project documentation, canonical-serialization checking is "Required for DEDUP-eligible spends. Without canonical form, identical solutions could have different serializations, breaking dedup," directly connecting it to spend-bundle processing in the mempool manager. Because the input buffer originates from a submitted spend bundle's puzzle reveal/solution bytes (fully attacker-controlled), a single unprivileged submitter can trigger this code path.

### Impact Explanation
If the resulting `IndexError` is not caught by the caller (this could not be fully confirmed with the available tool budget — the call site(s) that invoke `is_clvm_canonical` were not fully inspected before the session ended), the exception would propagate out of the mempool item's canonical/dedup-eligibility check during spend bundle validation. This can crash or abort the processing task handling that specific transaction/RPC call, constituting a spend-triggered transaction-processing halt — a remotely triggerable denial-of-service condition reachable by any party who can submit a spend bundle (wallet RPC caller, peer, or mempool submitter), analogous in bug class and impact (DoS via unchecked length-derived buffer walk) to CVE-2024-50597.

### Likelihood Explanation
Likelihood is contingent on exception handling at the call site, which I was unable to verify within the available tool calls (grep located only the definition site and 2 additional references, plus test file references, but I did not get to read the exact call site code before the session ended). If the call is unguarded by a broad `try/except`, exploitation only requires crafting one non-canonical CLVM atom whose length-prefix bytes exceed the remaining buffer — trivial to construct and reachable via a standard spend-bundle submission.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` and `is_clvm_canonical()` before indexing `clvm_buffer[offset]`, mirroring the pattern already used in `chia/full_node/full_block_utils.py` (`skip_bytes`/`skip_list`), raising a controlled error (or returning `False`) when the declared prefix/atom length would exceed the remaining buffer, instead of allowing Python's implicit `IndexError` to propagate. Additionally, verify (and add if missing) that all callers of `is_clvm_canonical` wrap it in exception handling so malformed input cannot escalate into an unhandled crash of the mempool/transaction-processing task.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

```python
def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
```
