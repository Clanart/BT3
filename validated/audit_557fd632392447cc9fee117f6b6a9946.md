### Title
Value sent with a call to the distribution precompile's `rewards()` view method is permanently stranded because it lacks a non-payable check - (File: `precompiles/distribution/distribution.go`)

### Summary
The distribution precompile's `Execute` dispatcher enforces `pcommon.ValidateNonPayable(value)` for state-changing/query methods such as `WithdrawValidatorCommissionMethod`, but the `RewardsMethod` case dispatches directly to `p.rewards(ctx, method, args)` without ever validating that `value` is zero. [1](#0-0)  The `rewards()` implementation itself also never checks `value`. [2](#0-1)  This is a known but unfixed quirk explicitly called out in the test suite. [3](#0-2) 

### Finding Description
When an EVM `CALL` is made to a precompile address with non-zero `value`, the standard EVM state-transition machinery moves that value from the caller to the precompile's associated Sei address via `AddBalance`, which credits `usei`/`wei` through the bank keeper. [4](#0-3)  This transfer happens as part of normal EVM call semantics, independent of whatever the precompile's Go logic subsequently does with `value`.

Distribution precompile methods that are meant to be non-payable are protected by `pcommon.ValidateNonPayable(value)`, which reverts if a payable call is attempted, e.g. for `WithdrawValidatorCommissionMethod`. [5](#0-4)  Every other read-only/query method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, etc.) routes through `p.validateInput(value, args, N)`, which similarly validates non-payability. However, `RewardsMethod` is dispatched straight to `p.rewards(ctx, method, args)` with no `value` argument passed and no `ValidateNonPayable` check anywhere in the call chain. [6](#0-5) [7](#0-6) 

Because `rewards()` succeeds and returns a normal response even when `value != 0`, the EVM value transfer that already occurred (crediting the distribution precompile's associated Sei account) is never reversed or repurposed into any accounted flow. Unlike `bank`, `staking`, and `gov`, the distribution precompile is not one of the "payable precompiles" whose transfer events get intentionally suppressed/tracked. [8](#0-7)  There is no corresponding code path in the distribution module that lets any user retrieve funds credited to the precompile's backing account this way — no "refund" or "withdraw stranded value" mechanism exists for this case, unlike `HandlePaymentUseiWei`/`HandlePaymentUsei`, which explicitly refund the payer immediately after crediting the precompile address for the methods that do call it. [9](#0-8) 

### Impact Explanation
Any EOA or contract can call `rewards(address)` on the distribution precompile at `0x...1007` while attaching non-zero `value` (usei/wei). The call succeeds, the caller loses the attached value, and that value becomes permanently stuck in the precompile's associated account with no method exposed by the distribution precompile (or any other reachable contract) to move it back out. This is a permanent, unrecoverable loss of user funds triggerable by any public RPC client via a single transaction — a direct analog to the reported "Ether sent to SwapRouter is lost" bug class, but reachable on-chain through a Cosmos precompile rather than an external DeFi contract.

### Likelihood Explanation
Likelihood is high: `rewards()` is a normal, documented, frequently-called precompile method (used by any application wanting to query staking rewards). A user or wallet integration mistakenly (or a malicious dApp intentionally) attaching a `value` to this call — e.g., due to a UI bug that defaults to sending gas/value with every contract call — will silently lose funds with no revert and no error to signal the mistake.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` case in `Execute` (or at the top of `rewards()`) so that a payable call to `rewards()` reverts exactly like the other query/view methods, consistent with `WithdrawValidatorCommissionMethod` and the `validateInput` helper used elsewhere in the same file.

### Proof of Concept
1. From any EOA associated with a Sei address, construct an EVM transaction to the distribution precompile address (`0x0000000000000000000000000000000000001007`) calling `rewards(address delegator)` with `value = 1 sei` (or any non-zero amount) attached.
2. The EVM state transition credits that value to the precompile's associated Sei account via `AddBalance` before/while `Execute` runs. [4](#0-3) 
3. `Execute` dispatches to `case RewardsMethod: return p.rewards(ctx, method, args)` without any `ValidateNonPayable(value)` check. [6](#0-5) 
4. `rewards()` runs the query and returns a success response; the transaction succeeds (status 1). [10](#0-9) 
5. The caller's balance is now permanently reduced by the attached `value`, with no corresponding refund and no exposed withdrawal path — confirmed by the test suite's own comment noting this exact quirk and that a "value-bearing call would succeed and strand the funds." [3](#0-2)

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return

func (s *DBImpl) AddBalance(evmAddr common.Address, amtUint256 *uint256.Int, reason tracing.BalanceChangeReason) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	amt := amtUint256.ToBig()
	if amt.Sign() == 0 {
		return *ZeroInt
	}
	if amt.Sign() < 0 {
		return s.SubBalance(evmAddr, new(uint256.Int).Neg(amtUint256), reason)
	}

	ctx := s.ctx
	var oldBalance *uint256.Int
	if s.logger != nil && s.logger.OnBalanceChange != nil {
		oldBalance = s.GetBalance(evmAddr)
	}
	// this avoids emitting cosmos events for ephemeral bookkeeping transfers like send_native
	if s.eventsSuppressed {
		ctx = ctx.WithEventManager(sdk.NewEventManager())
	}

	usei, wei := SplitUseiWeiAmount(amt)
	addr := s.getSeiAddress(evmAddr)
	err := s.k.BankKeeper().AddCoins(ctx, addr, sdk.NewCoins(sdk.NewCoin(s.k.GetBaseDenom(s.ctx), usei)), true)
	if err != nil {
		s.err = err
		return *ZeroInt
	}
	err = s.k.BankKeeper().AddWei(ctx, addr, wei)
	if err != nil {
		s.err = err
		return *ZeroInt
	}

func HandlePaymentUseiWei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Int, sdk.Int, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoinsAndWei(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, usei, wei); err != nil {
		return sdk.Int{}, sdk.Int{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return usei, wei, nil
}
