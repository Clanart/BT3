This confirmed the analog. `_addDeployment` (invoked only via `NewDeployment` in `onAccept`, gated to messages sourced from Hyperbridge itself) simply overwrites `_instances[keccak256(body.chain)]` with a new gateway address, with no check for orders still in flight against the old deployment. `_cancelFromSource` and `_authenticate` both resolve the *current* `_instance(...)` value at call time rather than the instance that was authoritative when the order was placed — this is the direct structural analog to the `AaveV3Connector`/`CompoundV2Connector` bug: a migration that repoints custody/authority to a new contract while state tied to the old contract (an in-flight fill, its pending `RedeemEscrow` message) is left stranded, permitting a duplicate settlement. ### Title
Redeployment of a gateway instance mid-flight causes a stale-instance GET proof to falsely prove "not filled," enabling double settlement of a cross-chain order - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` binds every cross-chain order to a *dynamic* per-chain "instance" address (`_instances[keccak256(chain)]`), which Hyperbridge governance can repoint at any time via `NewDeployment` → `_addDeployment`. `_cancelFromSource` builds its storage-proof query against whatever address `_instance(order.destination)` currently resolves to — not the address that was authoritative when the order was placed and filled. If the destination instance is redeployed while an order's `RedeemEscrow` settlement message is still in flight, the storage-proof query silently targets a brand-new, empty contract, so the proof will always show `_filled[commitment] == 0` regardless of the real fill state on the old instance. This lets the user cancel-and-refund the source-chain escrow even though the order was already correctly filled by a solver on the (now orphaned) old destination gateway.

### Finding Description
An order commitment binds `order.source`/`order.destination` (immutable chain identifiers), but does **not** bind the concrete gateway *address* that will be checked at cancellation time. `_instance()` always dereferences the live mapping:

```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

`_cancelFromSource` uses this live value to construct the GET-request storage key that will later be checked against a state proof:

```solidity
keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
```

Sequence:
1. User places a cross-chain order; escrow locked on source. Solver fills it on the destination gateway at address `A` (the value of `_instance(destinationChain)` at fill time). `_filled[commitment]` is set to `true` in contract `A`'s storage, and `A` dispatches a `RedeemEscrow` message toward the source chain.
2. Before that `RedeemEscrow` message is delivered/finalized on the source chain (a normal, non-trivial cross-chain latency window, further extendable by any relayer delay or fee-related retry), Hyperbridge governance performs a legitimate `NewDeployment` for the destination chain, updating `_instances[keccak256(destinationChain)]` from `A` to `B` (e.g., an upgrade, redeploy, or fixing a bug in `A`).
3. After `options.height > order.deadline`, the user calls `cancelOrder` → `_cancelFromSource` on the source chain. This dispatches a `DispatchGet` whose storage key now points at instance `B`, which has never seen this order — its `_filled[commitment]` slot is empty.
4. The relayer proof is verified honestly by Hyperbridge's real state-proof machinery (no malicious relayer or prover needed — the proof is truthful for address `B`, just semantically wrong for this order).
5. `onGetResponse` sees an empty value and calls `_withdraw(body, true, true)`, refunding the escrowed input tokens to `order.user` and setting `_filled[commitment] = user` on source.
6. The solver, who already delivered the output tokens to the beneficiary against instance `A`, either never receives the input escrow (its `RedeemEscrow` from `A` will later be authenticated fine via `_authenticate`, since that check is against `_instance(request.source)` which is the *source* chain, unaffected by the destination migration — but `_withdraw` will revert with `UnknownOrder`/already-finalized state once `_filled[commitment]` is non-zero) or the ordering is reversed and the legitimate redeem is blocked after the fraudulent-looking refund lands first.

Either ordering produces the same broken invariant: the user ends up holding both the destination output tokens delivered by the solver **and** the refunded source-chain escrow, while the solver — who performed the fill in good faith — is left unpaid. This is exactly the same failure mode as the external report: a migration (of the authoritative "instance"/strategy address) is performed without accounting for value/state still bound to the old address, and a legitimate concurrent action (rescue / cancel) exploits the resulting inconsistency to cause loss.

### Impact Explanation
This is a direct loss-of-funds / double-claim vulnerability reachable by an unprivileged actor (the order's own user, who is incentivized to trigger it): the user can obtain both the solver-delivered output *and* a refund of their own input escrow, at the solver's expense. It maps to "stealing or loss of funds" and "double-claim/double-settlement" in the bounty scope. No malicious relayer, prover, or governance actor is required — the `NewDeployment` action is an ordinary, expected governance/administrative operation (upgrading or redeploying a gateway instance), and the race is a natural byproduct of unavoidable cross-chain message latency, not privileged misbehavior.

### Likelihood Explanation
The trigger conditions are realistic: gateway redeployments/upgrades will happen over the life of the protocol, and cross-chain `RedeemEscrow` delivery is never instantaneous (it requires consensus finality, challenge periods, and relayer submission). Any order filled shortly before a destination-instance migration is settlement-message-in-flight during a window that is trivially exploitable by simply waiting for `order.deadline` to be observably passed and calling `cancelOrder`. The attack requires no special access — it is executed entirely through the public `cancelOrder`/`_cancelFromSource` path that already exists for legitimate use.

### Recommendation
Bind the storage-proof lookup (and the authentication in `_authenticate`) to the destination gateway address that was authoritative **at order-placement/fill time**, not the live value of `_instances[...]`. Concretely:
- Snapshot the destination gateway address into the order/commitment (e.g., store it alongside `_orders[commitment]` at placement, or include it as part of the signed `Order` struct) and use that snapshot in `_cancelFromSource`'s GET-request key construction.
- Alternatively, disallow `_addDeployment` from overwriting an existing non-zero mapping entry for a chain that still has pending/unsettled orders, and instead require a new state-machine identifier (or explicit draining/quiescence period) for redeployments, mirroring Balmy's fix of disabling migrations while a rescue is outstanding.

### Proof of Concept
1. Deploy `ExtrinsicIntents`/`IntentGatewayV2` on chain S (source) and chain D (destination), with `_instances[keccak256(D)] = A`.
2. User places a cross-chain order on S with `destination = D`, escrowing input tokens.
3. Solver calls `fillOrder` on D against instance `A`; `A` sets `_filled[commitment] = solver` and dispatches `RedeemEscrow` toward S (not yet delivered/finalized).
4. Before the `RedeemEscrow` message lands on S, Hyperbridge dispatches `NewDeployment` for chain D pointing at a fresh instance `B` (`_instances[keccak256(D)] = B`); `B` has no knowledge of `commitment`.
5. After `order.deadline`, user calls `cancelOrder(order, {height: h, relayerFee})` on S. `_cancelFromSource` builds the GET key using `_instance(D) == B`.
6. Hyperbridge relayers produce a legitimate storage proof for `B`'s empty `_filled[commitment]` slot at height `h`; `onGetResponse` sees `values[0].value.length == 0` and calls `_withdraw(..., isRefund=true, finalize=true)`, refunding escrow to `order.user` and finalizing `_filled[commitment]`.
7. The solver's earlier `RedeemEscrow` (from `A`) either arrives and reverts on `_withdraw`'s `UnknownOrder`/already-finalized checks, or is processed first and the refund attempt should instead have reverted with `Filled()` — in practice, whichever message reaches S first determines that the *other* party is left without recourse. In the scenario above (refund lands first), the user has both the solver's output tokens and the refunded escrow; the solver has paid out and receives nothing.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({

            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
