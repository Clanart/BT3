## Title
Stale by-index line selections silently apply to the wrong diff lines after a working-directory diff reload, corrupting partial commits/discards - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/patch-formatter.ts`, `app/src/models/diff/diff-selection.ts`)

## Summary
GitHub Desktop's partial-commit ("stage some lines") feature stores the user's line selection as a set of *absolute integer indices* (`hunk.unifiedDiffStart + lineIndex`) rather than by any content-derived identity. When the working directory diff is asynchronously reloaded (e.g. because the file on disk changed between the initial diff load and the moment the user actually stages/commits/discards), the code only prunes indices that are no longer "includeable" lines — it does **not** verify that a surviving index still corresponds to the same logical change the user selected. If the reloaded diff has hunks of the same shape/length but different content at those indices (fully plausible for a file that is being modified by another process, or one whose disk contents an attacker can influence in the moment the user reviews and stages a diff), the previously "selected" indices now silently point at different Add/Delete lines. `formatPatch` / `formatPatchToDiscardChanges` then build the git patch purely from `file.selection.isSelected(absoluteIndex)`, so the wrong lines get staged/committed or discarded without any warning to the user.

## Finding Description
The invariant that should hold is: *"the lines the user visually selected are the exact lines that end up in the patch."* This is broken because:

1. The diff is parsed independently each time via `DiffParser`/`getWorkingDirectoryDiff`, and every parse recomputes `unifiedDiffStart`/`unifiedDiffEnd` per hunk based on `linesConsumed`, a purely positional counter: [2](#0-1) 
2. The user's selection state, `DiffSelection`, is keyed only by these positional indices — there is no line-content fingerprint tying a selected index to what a user actually saw.
3. When the diff is reloaded (`updateChangesWorkingDirectoryDiff`), the reconciliation logic explicitly performs only a coarse fixup: it drops indices that are no longer includeable, but keeps every surviving index as still-selected, with the comment openly stating this is a known simplification ("Ideally we would be more clever about validating that any partial selection state is still valid ... but for now..."): [1](#0-0) 
4. When the commit/discard action actually runs, `formatPatch` and `formatPatchToDiscardChanges` build the patch strictly from `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and `selection.isSelected(absoluteIndex)`, trusting that index to mean the same thing it meant when the user clicked it: [3](#0-2) 
5. `applyPatchToIndex` then feeds this patch straight into `git apply --cached`, and `stageFiles` invokes it for every partially-selected file when the user commits: [4](#0-3) [5](#0-4) 

No guard anywhere checks that the line *text* at a retained index is the same text the user originally selected — only that the line is still of an "includeable" type (`Add`/`Delete`). Two diffs of the same file can trivially have identical hunk shapes with different content (e.g. same number of added/removed lines, different bytes), so the existing guard does not stop this path.

## Impact Explanation
This is a silent corruption of what the user commits or pushes to a real remote: a user can review a diff, deliberately deselect a sensitive/unwanted change (e.g. a secret, a debug statement, or a malicious line), yet if the on-disk file changes shape-compatibly before the actual `git apply --cached` runs, Desktop can stage a different line than the one the user reviewed and approved — without any diff re-confirmation or warning. Because staging happens through `git apply --cached` on an attacker-influenceable patch body, this can also produce patches that don't match user intent for discard operations (`formatPatchToDiscardChanges`), permanently discarding the wrong working-directory changes. This matches the report's core class ("wrong scoping variable silently changes what a bounded operation actually processes"), mapped here onto a real Desktop data-integrity primitive (partial commit staging) rather than a smart-contract mint counter.

## Likelihood Explanation
The trigger requires the working directory file to change between the time Desktop parses/display a diff and the time the user commits/discards, in a way that preserves the shape of at least one hunk. This is plausible without any privileged local access: build tools, editors with format-on-save, linters/pre-processors, or any background process that rewrites a file with the same line count can cause it. It does not require exploiting git hooks, admin rights, or malware — only ordinary background file activity concurrent with normal partial-commit workflow, which is a supported, common Desktop feature (`DiffSelectionType.All`/`None`/partial range selection, `withRangeSelection`, `withLineSelection`). The comment in `app-store.ts` shows the developers were aware only a partial mitigation exists, increasing confidence this is a genuine, currently-unaddressed gap rather than a misread of intentional behavior.

## Recommendation
Do not treat survival of a positional index as sufficient proof of selection validity. When reconciling `selectableLines` after a diff reload, also compare line `type` and `text` (or a stronder identity such as `oldLineNumber`/`newLineNumber` plus content hash) between the previous and new diff at each index; if content differs, drop the stale selection entirely instead of preserving it. Consider additionally re-diffing right before `applyPatchToIndex`/`formatPatch` executes and refusing to stage/discard if the diff has changed since the selection was captured, prompting the user to re-review.

## Proof of Concept
1. Open a repository in Desktop and modify a tracked file so that it has, e.g., 3 added lines (`+a`, `+b`, `+c`) in one hunk.
2. In the Changes view, select only line `+b` for inclusion (deselect `+a` and `+c`) using the line-level partial-selection UI (`withLineSelection`/`withRangeSelection`).
3. Before hitting "Commit", have another process (editor autosave, formatter, build step) rewrite the file so the same hunk now contains 3 different added lines (`+x`, `+y`, `+z`) — same line count/type, different content.
4. Desktop's file watcher triggers `updateChangesWorkingDirectoryDiff`; per [1](#0-0) , index for `+b`'s position remains in `selectableLines` since it's still an "includeable" `Add` line — the selection carries over unchanged even though the content is now `+y`.
5. User clicks "Commit". `formatPatch` builds the patch using `absoluteIndex` against the *new* diff, selecting `+y` (not `+b`), and `applyPatchToIndex`/`git apply --cached` stages it: [3](#0-2) [4](#0-3) 
6. Result: the user believes they committed `+b` and excluded `+a`/`+c`, but the actual commit contains `+y` (and possibly `+x`/`+z` depending on selection state) — a silent mismatch between reviewed intent and committed content.

**Note on verification limits:** I was not able to execute the application to reproduce this end-to-end (no filesystem/terminal access in this mode); the analysis is based on static code review of the cited files. If deeper confirmation is needed (e.g., exact timing window of the file-watcher race, or whether any additional guard exists elsewhere in the commit flow that I didn't locate), a Devin session with full repo/terminal access should be used to build and exercise this scenario directly.
