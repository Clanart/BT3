### Title
Un-guarded `?` after module callback execution leaves commitment/timeout bookkeeping inconsistent - (File: `modules/ismp/core/src/handlers/timeout.rs`)

### Summary
The external Etherlink report identifies a class of bug where a paired "begin/end" (or "record/settle") operation is split across a fallible boundary using Rust's `?` operator: if the second half of the pair errors out, the cleanup/finalization step is skipped and the system is left in an inconsistent state. `modules/ismp/core/src/handlers/timeout.rs` contains the same structural pattern in the ISMP timeout-processing closures for both `TimeoutMessage::Post` and `TimeoutMessage::Get`.

### Finding Description
In both branches of `handle()` in `modules/ismp/core/src/handlers/timeout.rs`, each request in a timeout batch is processed by a per-item closure that:

1. Deletes the outgoing commitment: `let meta = host.delete_request_commitment(&request)?;` [1](#0-0) 
2. Invokes the destination module's `on_timeout` callback, which can itself trigger real side effects (fund refunds, state mutation) in the router-selected `IsmpModule` (e.g. `pallet_hyper_fungible_token`).
3. **Only if** the callback succeeded, finalizes bookkeeping with `host.on_request_timeout(&request, meta)?;` [2](#0-1) 
4. If it failed, it restores the commitment for a retry with `host.store_request_commitment(&request, meta)?;` [3](#0-2) 

The problem: step 3's `host.on_request_timeout(&request, meta)?` runs strictly *after* the module callback has already executed and mutated state, but if this finalization call itself errors (e.g. an internal accounting failure), there is no corresponding "undo" path — the code only restores the commitment in the `else` branch (module callback failure), not when the callback succeeded but finalization failed. The `?` immediately propagates an `anyhow::Error` out of the closure, which is then caught by `.collect::<Result<Vec<_>, _>>()?` [4](#0-3)  and bubbles all the way out of `handle()`, discarding the `Event`s/results for every other request already successfully processed earlier in the *same* batch.

This is the same "enter-call-stack, fallible-exit-without-cleanup" shape flagged in the report: the commitment is already deleted (§1) and the module-side effect has already run (§2), but the paired finalization/rollback (§3/§4) is not guaranteed to execute for every item, and a failure at that exact point is unrecoverable within the closure — the request's commitment is gone, its module callback already fired, yet `host.on_request_timeout` bookkeeping (which is responsible for e.g. releasing fee/relayer accounting tied to that commitment, per the crate's `on_request_timeout` role in `IsmpHost`) never completes for that request, and the error return also throws away the successfully-computed results for sibling requests processed earlier in the batch.

### Impact Explanation
The corrupted invariant is the atomicity of "commitment removal + module timeout callback + host bookkeeping finalization" as a single logical unit. Once `delete_request_commitment` and the module's `on_timeout` side effects have executed, the request cannot be timed out or delivered again (its commitment is gone), but if `on_request_timeout` then errors, the fee/relayer/settlement bookkeeping tied to that commitment is left unresolved, and the whole batch's other successfully-processed events are silently dropped by the early `?` return. This maps to the bounty's "logic attacks / inconsistent state / false settlement acceptance" category rather than a benign retry: state that should be atomically paired (delete + finalize) is not, and no compensating action exists for the failure of the finalize half when the callback succeeded.

### Likelihood Explanation
This is reachable by any relayer submitting a normal `TimeoutMessage` batch (public entrypoint, no privileged actor needed) as long as one of the timed-out requests' module callback succeeds but the subsequent host finalization call can fail for that request (e.g. transient/adversarially-crafted state that makes `on_request_timeout` bookkeeping fail while the module callback itself does not). No malicious relayer, prover, or governance action is required — an ordinary user-triggered timeout batch containing multiple pending requests is enough to expose the gap.

### Recommendation
Restructure the per-item closure so that `on_request_timeout`'s own failure is treated symmetrically with the module-callback failure: either wrap the delete/callback/finalize sequence in an explicit storage transaction that is rolled back on any error, or explicitly restore the commitment (mirroring the `else` branch) if `host.on_request_timeout` fails after a successful callback, instead of relying on the bare `?` to abort the whole batch. As in the referenced fix, prefer isolating the fallible sequence into its own function so that `?` is only used once all invariants that must not be split are already handled, and make sure a mid-batch failure does not discard results already computed for other requests in the same `.collect::<Result<Vec<_>, _>>()?`.

### Proof of Concept
Structural PoC (Rust, illustrating the exact code path in `modules/ismp/core/src/handlers/timeout.rs:113-135`):
```rust
// TimeoutMessage::Post branch, per-item closure
let meta = host.delete_request_commitment(&request)?;     // (1) commitment gone
let res = cb.on_timeout(request.clone()).map(|w| { .. }); // (2) module side effects already applied
if res.is_ok() {
    host.on_request_timeout(&request, meta)?;              // (3) FAILS HERE -> no restore path exists
} else {
    host.store_request_commitment(&request, meta)?;        // only covers callback failure, not (3)
}
Ok::<_, anyhow::Error>(res)
```
If `host.on_request_timeout` returns `Err` for this item, the surrounding `.collect::<Result<Vec<_>, _>>()?` [4](#0-3)  propagates the error out of `handle()`, so the caller never receives the `MessageResult::Timeout` containing events for requests processed earlier in the batch, while this request's commitment remains permanently deleted with its module-side effects already committed and no compensating restoration.

I was not able to fully inspect `IsmpHost::on_request_timeout`'s concrete implementation (fee/relayer settlement logic) within the available tool budget to quantify the exact bookkeeping/funds impact of its failure; this should be verified directly against `modules/pallets/ismp/src/impls.rs` (or equivalent host implementation) to confirm whether its failure mode can actually be triggered by an unprivileged relayer and what specific balances/receipts it leaves unresolved.
