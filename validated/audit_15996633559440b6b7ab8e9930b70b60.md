### Title
Unverified-PoP share-deserialization fault releases blame proof, leaking the ECDH key protecting another participant's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
PedPoP's defense against the "co-opted per-message key" attack is the Schnorr proof-of-possession (`msg.pop`) bound to the sender and ciphertext. However, `Encryption::decrypt` only *queues* that PoP for batch verification, while `KeyMachine::calculate_share` returns an `InvalidShare` error — containing the blame `EncryptionKeyProof` that reveals the ECDH shared key — on a non-canonical share scalar *before* `batch.verify_with_vartime_blame()` is ever reached. A malicious participant can therefore force an honest recipient to publish the ECDH key for a message using a per-message key the attacker copied from an honest sender's message, revealing that honest party's encrypted secret share to everyone.

### Finding Description
The bug class of the CVE (a malicious message causing a privileged party to disclose protected memory/secrets) maps onto the documented PedPoP side-effect: a blame proof reveals `proof.key = ecdh(enc_key_recipient, msg.key)`, i.e., the ChaCha20 shared key for that message. The code explicitly guards this with a PoP: "If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X… they'd reveal bX, revealing Alice's message to Bob" (crypto/dkg/pedpop/src/encryption.rs:84-91). The spec repeats this rationale in `spec/cryptography/Distributed Key Generation.md:28-35`.

The guard is bypassed because verification is deferred:

1. In `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:479-488), the PoP is added to the `BatchVerifier` under `BatchId::Decryption(from)`, but decryption and `EncryptionKeyProof` construction proceed immediately — the proof is returned regardless of whether the PoP is valid.

2. In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499), the loop decrypts each share and attempts `C::F::from_repr(share_bytes.0)`. On failure it returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` via `?` at line 482 — an early return that skips `batch.verify_with_vartime_blame()` at line 493 entirely. The PoP of the offending message is never checked before its decryption key is released.

Concretely: Eve copies `msg.key = X` from honest Alice's `EncryptedMessage` to Bob, attaches a garbage `pop`, and a random ciphertext. Bob computes `key = ecdh(enc_key_bob, X)` — the same shared key protecting Alice's real share — decrypts to pseudorandom bytes, and `from_repr` rejects them as non-canonical with overwhelming probability (for a ~2^252 group order, a uniform 32-byte string fails canonicality ~15/16 of the time). Bob's `calculate_share` returns `blame` = `(key, DLEq(X·b, b·X))`, which the integrator broadcasts (see `processor/src/key_gen.rs:504-556`, `VerifyBlame` handling). Since `key` is a valid DLEq-bound decryption key for Alice's message, `BlameMachine::blame` / `AdditionalBlameMachine::blame` will verify it, attribute the fault to Eve for the malformed message — and simultaneously anyone holding Alice's ciphertext can now decrypt her secret share to Bob.

### Impact Explanation
The ECDH key revealed is exactly the key encrypting Alice's `SecretShare` to Bob. Eve (and all observers of the blame) recover `s_{Alice→Bob}`, an evaluation of Alice's secret-sharing polynomial at Bob's index, which she was never authorized to learn. Combined with Eve's own legitimate share `s_{Alice→Eve}`, for `t = 2` this fully recovers Alice's secret contribution; for larger `t`, each leaked share erodes the DKG's secrecy margin and can be combined with additional malicious participants to reach threshold. This is the precise "massive side effect which could break some protocols" the PoP was added to prevent, and it constitutes disclosure of secret key material caused purely by an unprivileged participant's crafted message — matching the reported bug class (key share recovery / unauthorized secret disclosure).

### Likelihood Explanation
Fully deterministic in structure and high-probability in triggering: any participant in a PedPoP DKG session may submit an `EncryptedMessage` with a copied `msg.key`, invalid PoP, and random ciphertext. The recipient's unmodified `calculate_share` then emits the revealing blame proof with probability ≈ 1 − ℓ/2^256 (over 93% for 25519-family curves; guaranteed if the attacker can instead encrypt a deliberately non-canonical plaintext under a key they control while copying `msg.key`). No race, no collusion, and no privileged position is required — only an authenticated channel every DKG participant already has.

### Recommendation
Verify the PoP of each message *before* releasing the `EncryptionKeyProof`, not in the deferred batch. Options:

- In `Encryption::decrypt`, verify `msg.pop` immediately (or at minimum, verify it inline before returning the blame proof on the `from_repr` failure path in `calculate_share`).
- Alternatively, do not attach `blame` to `PedPoPError::InvalidShare` until `batch.verify_with_vartime_blame()` has confirmed the message's `BatchId::Decryption` statement — i.e., run the batch verification before interpreting deserialization failures, so a forged-PoP message maps to `BatchId::Decryption(l)` → `blame: None`.
- Also reject `msg.key` values that fail canonical/identity checks on `read_G` to reduce attacker-controlled ECDH inputs.

### Proof of Concept
```
Setup: PedPoP DKG, participants {Alice=1, Bob=2, Eve=3}, any params.

1. Alice's honest EncryptedMessage to Bob: { key: X, pop: σ_A, msg: enc(s_{A→B}) },
   broadcast as part of shares[Alice][Bob].
2. Eve constructs shares[Eve][Bob] = { key: X,                 // copied from Alice's message
                                     pop: <invalid Schnorr>,  // cannot know dlog(X)
                                     msg: <random 32 bytes> }.
3. Bob: calculate_share(rng, shares):
   - decrypt(Eve's msg): queues Eve's pop under BatchId::Decryption(Eve) (unverified),
     computes key = ecdh(b_enc, X) == shared key for Alice's message,
     decrypts ciphertext → pseudorandom bytes.
   - C::F::from_repr(random_bytes) → None with probability ~1 − ℓ/2^256.
   - Returns Err(PedPoPError::InvalidShare { participant: Eve,
        blame: Some(EncryptionKeyProof { key: b·X, dleq: DLEq(G,X ; b_enc, b·X) }) })
     at lib.rs:482 — before batch.verify_with_vartime_blame() at lib.rs:493.
4. Bob's integrator broadcasts the blame (processor/src/key_gen.rs VerifyBlame flow).
   Eve decrypts Alice's ciphertext msg field with cipher(context, b·X)
   → recovers s_{A→B} (Alice's secret share to Bob).
   With t = 2, Eve additionally holds s_{A→E} and recovers Alice's DKG secret a_{0,A}.
```

Root cause: `PedPoPError::InvalidShare` with `blame: Some(..)` is produced on the `from_repr` failure path (crypto/dkg/pedpop/src/lib.rs:480-482) prior to the deferred batch verification (lib.rs:493) that is the only place the PoP — the sole defense against per-message-key co-option (encryption.rs:84-91) — is checked.
