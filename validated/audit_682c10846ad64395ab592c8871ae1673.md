### Title
DID Recovery/Backup List Persists After DID Ownership Transfer, Allowing Old Backup DIDs to Recover the Singleton From the New Owner - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
`DIDWallet.transfer_did` unconditionally reuses the current `backup_ids` (the DID's recovery/backup-DID list) and `num_of_backup_ids_needed` when generating the new inner puzzle for a transferred DID, with no way to actually clear them. This means that after a DID (and any NFTs pinned to it) is transferred to a new owner, any previously-authorized "backup DIDs" retain the power to trigger DID recovery and regain control of the singleton — mirroring the reported bug class where a delegated sub-asset permission is not revoked when the underlying position changes owner.

### Finding Description
`DIDWallet.transfer_did` builds the new DID inner puzzle hash directly from the wallet's existing recovery state: [1](#0-0) 

Notably, `backup_ids` and `backup_required` are pulled straight from `self.did_info.backup_ids` / `self.did_info.num_of_backup_ids_needed` with no parameter or override path to clear them during a transfer, and the innersol also explicitly carries over `self.did_info.backup_ids`: [2](#0-1) 

The only "clearing" helper, `reset_recovery_list`, is a no-op whenever there is an existing non-empty backup list — it only returns a cleared hash if `len(self.did_info.backup_ids) == 0`: [3](#0-2) 

The CLI exposes a `reset_recovery` flag on `did transfer` (default `False`, i.e. recovery preserved unless the user opts out), and the RPC exposes a `with_recovery_info` flag on `did_transfer_did`: [4](#0-3) [5](#0-4) 

However, `DIDWallet.transfer_did` itself takes no such flag at all — it always keeps the existing backup DID list intact in the new singleton state regardless of caller intent, so there is no code path in `transfer_did` that actually drops a previously-set non-empty recovery/backup list when ownership changes hands.

### Impact Explanation
Any DID (and by extension NFTs held under that DID, since DID backup/recovery power lets a party regain full control of the DID singleton) transferred to a new owner retains its old backup-DID list. If the previous owner (or anyone the previous owner had granted backup/recovery rights to) still holds the backup keys, they can later initiate a DID recovery spend and seize control of the DID singleton from the new owner without the new owner's consent — directly analogous to the reported issue where a delegatee's authority over sub-assets is not revoked on ownership transfer. This is an unauthorized-control/asset-theft class impact reachable purely from a normal wallet user's own transfer action (no privileged access needed), so it fits Medium/High severity guidance for "unauthorized coin movement" / "offer settlement theft"-equivalent control hijack.

### Likelihood Explanation
Likelihood is moderate: it requires that the DID being transferred actually has a non-empty recovery/backup list (a supported, common DID feature) and that the new owner does not independently know to spend down/replace the recovery configuration after receiving the DID. Since the CLI/RPC flags (`reset_recovery` / `with_recovery_info`) exist and imply the option to clear recovery info during transfer, but `DIDWallet.transfer_did` provides no mechanism to actually honor a "clear recovery" intent, this is likely to be silently ignored by users who believe they've reset recovery info during a sale/transfer.

### Recommendation
Add an explicit parameter to `DIDWallet.transfer_did` (wired through the CLI's `reset_recovery` and RPC's `with_recovery_info` flags) that, when set, clears `backup_ids`/`num_of_backup_ids_needed` (and produces the corresponding empty-recovery inner puzzle, similar to the empty-recovery puzzle construction already used elsewhere in the codebase) instead of always propagating the old recovery configuration. Ensure the resulting `innersol` also reflects the cleared backup list rather than unconditionally reusing `self.did_info.backup_ids`.

### Proof of Concept
1. Owner A creates a DID wallet and sets a backup/recovery DID list `[B]` with `num_of_backup_ids_needed = 1`.
2. Owner A sells/transfers the DID to Owner C via `did_transfer_did` (or `did transfer` CLI), intending (or explicitly requesting via `reset_recovery`/`with_recovery_info=False`) to remove B's recovery power.
3. Because `DIDWallet.transfer_did` unconditionally forwards `self.did_info.backup_ids` (`[B]`) into the new inner puzzle curry and solution: [6](#0-5) 
the resulting on-chain DID singleton still lists `B` as an authorized backup.
4. B, using the still-valid backup authority, later submits a DID recovery spend bundle and regains control of the DID singleton, bypassing Owner C's exclusive ownership — with no action from Owner C required to enable this.

        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
