### Title
Malicious git remote can spoof `WWW-Authenticate: realm="GitHub"` to trigger a GitHub Enterprise sign-in flow against an attacker-controlled endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The `AdminUpgradeabilityProxy` report's core defect is a missing validation check on attacker-influenceable input before it is trusted to configure a sensitive permission (the admin address). The GitHub Desktop analog is `getEndpointKind()` in the git credential-helper trampoline, which decides whether an arbitrary git remote host should be treated as a trusted "GitHub" endpoint based solely on a `WWW-Authenticate` HTTP header value returned by that remote — with no verification that the host is actually GitHub or GHE.

### Finding Description
When Git needs credentials for an HTTP(S) remote, it captures the server's `WWW-Authenticate` response header and passes it into Desktop's credential helper via the trampoline protocol. `getEndpointKind()` scans these headers: [1](#0-0) 

If the attacker-controlled server responds with a header containing `realm="GitHub"`, the function unconditionally classifies the endpoint as `'enterprise'` — i.e., a trusted GitHub Enterprise host — with no cross-check against the actual hostname, TLS certificate, or any GitHub-specific API probe at this stage (that probe, `isGitHubHost()`, is only reached later, and is skipped entirely once the `wwwauth` header match succeeds). This is directly analogous to `_setAdmin()` being called without the zero-address check that exists in the sibling `changeAdmin` path: one code path (`isGitHubHost` heuristic based on live API probing) is checked, but another path (header-based short-circuit) is not.

That classification then flows into `getCredential()`: [2](#0-1) 

Because `endpointKind !== 'generic'` and no existing account matches this brand-new attacker `apiEndpoint`, Desktop calls `ui.promptForGitHubSignIn(endpoint)` with the attacker's own URL.

`promptForGitHubSignIn` then drives the real Enterprise sign-in UI, pointed at the attacker's origin: [3](#0-2) 

This calls `dispatcher.beginEnterpriseSignIn` and `dispatcher.setSignInEndpoint(origin)` using the attacker-supplied `origin`, launching Desktop's legitimate-looking GitHub Enterprise sign-in dialog/browser flow against a host the attacker fully controls.

### Impact Explanation
An attacker who controls a git remote (or a man-in-the-middle/proxy in the request path for an HTTPS remote the user has added, e.g. from a malicious `.gitmodules`, a compromised mirror, or a poisoned proxy) can cause Desktop, entirely by returning a crafted `WWW-Authenticate: Basic realm="GitHub"` header on a 401 response, to:
- Present the user with Desktop's native "sign in to GitHub Enterprise" UI pointed at the attacker's server.
- Drive `setSignInEndpoint`/`beginEnterpriseSignIn`, which triggers OAuth/browser-based authentication flows and credential submission dialogs targeting the attacker's endpoint instead of a real GitHub Enterprise instance.
- This can be used to phish enterprise git credentials or an OAuth authorization the user believes they are granting to GitHub Enterprise, achieving "unauthorized OAuth or account binding" against an attacker-chosen endpoint, without any local access, prior malware, or leaked credentials — the only requirement is that the user's git operation talks to the attacker's remote/proxy, which is the standard "attacker controls a git remote/proxy response" threat model.

### Likelihood Explanation
Likelihood is moderate: the attacker needs the victim's Desktop instance to perform an authenticated git HTTP(S) operation (clone/fetch/push) against a server they control or intercept (e.g., a spoofed corporate git host, a malicious fork URL a user is tricked into adding as a remote, or a network-level proxy). No social engineering beyond "the user has a remote pointing at the attacker's server" is required, and the header-based shortcut in `getEndpointKind` bypasses the more careful `isGitHubHost()` verification that exists later in the same function, so the existing safeguard does not protect this path.

### Recommendation
- Short term: Do not trust the `WWW-Authenticate` realm string alone to classify a host as GitHub/Enterprise. Require it to be corroborated by the same host-verification logic used for `isGitHubHost()` (e.g., an authenticated API probe or hostname allow-list) before elevating trust and invoking the Enterprise sign-in flow.
- Long term: Audit all trampoline/credential-helper decision points that consume server-controlled data (headers, redirect targets, realm strings) and ensure every branch that grants elevated trust (GitHub/Enterprise classification) passes through a single, consistently-applied verification function, mirroring the invariant-review recommendation in the original report.

### Proof of Concept
1. Stand up an HTTPS server at `https://attacker.example/repo.git`.
2. Configure it to respond to Git's credential probe (unauthenticated request) with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone/add this URL as a remote and trigger a fetch.
4. Git invokes the trampoline credential helper; `getEndpointKind` sees the `wwwauth[...]` entry matching `realm="GitHub"` and returns `'enterprise'` [4](#0-3) .
5. `getCredential` finds no existing account for `attacker.example` and calls `ui.promptForGitHubSignIn('https://attacker.example')` [5](#0-4) .
6. Desktop shows the native GitHub Enterprise sign-in dialog and calls `setSignInEndpoint('https://attacker.example')`, beginning an OAuth/credential flow against the attacker's server [6](#0-5) .

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
