I found an interesting analog worth examining closely: `blockchain/vm/evm.go`, the EIP-3541 code-rejection check.### Title
EIP-3541 (0xEF-prefixed code) rejection check runs after `SetCode` and after the revert branch, letting invalid contract code persist in state - ([File: blockchain/vm/evm.go])

### Summary
`EVM.create()` in `blockchain/vm/evm.go` stores the deployed contract's returned code via `evm.StateDB.SetCode(address, ret)` and only afterward checks `err != nil` to decide whether to call `evm.StateDB.RevertToSnapshot(snapshot)`. The EIP-3541 check that rejects code beginning with `0xEF` for the Kore-but-not-Prague fork window is placed *after* that revert branch, so setting `err = ErrInvalidCode` at that point can no longer trigger the snapshot revert that would undo the `SetCode` call. This mirrors the CVE-2018-15601 root cause: a rejection check ("cannot store this content") is evaluated too late in the pipeline, after the corresponding write ("upload"/`SetCode`) has already taken effect.

### Finding Description
In `blockchain/vm/evm.go`, `create()`: [1](#0-0) 
- Lines 601–616: if `err == nil`, the code computes `createDataGas`, and if gas is available, calls `evm.StateDB.SetCode(address, ret)`, committing `ret` as the account's code in the state DB.
- Lines 618–625: `if err != nil { evm.StateDB.RevertToSnapshot(snapshot) ... }` — this is the only revert path, and it only fires if `err` is already non-nil at this point.
- Lines 627–633: only *after* that revert check does the code test `ret[0] == 0xEF` (EIP-3541) for `IsKore && !IsPrague` and set `err = ErrInvalidCode`.

Because the EIP-3541 rejection is evaluated strictly after the revert branch, setting `err` here has no effect on state: the account's code was already persisted via `SetCode` in the earlier block, and the snapshot is never rolled back for this specific failure. The comment in the code itself, [2](#0-1) , explicitly acknowledges: "This validation was incorrectly placed after the code was already stored in state DB, which should have been prevented." This is the same bug class as the Elefant CMS advisory: the "forbidden content" check (banned file extension / banned code prefix) is applied on already-committed/already-decoded data, after the point where blocking it would have been effective — the check exists but is functionally too late to prevent the write.

### Impact Explanation
If the returned `err` from `create()` does not itself cause the *entire* transaction/message state to be discarded at a higher layer (e.g., in `StateTransition.TransitionDb` / `ApplyMessage`), then a contract deployer can submit init code that returns bytecode beginning with `0xEF` during the Kore (post-Istanbul, pre-Prague) fork window. The resulting account will have `0xEF...`-prefixed code permanently stored in state despite the EVM/consensus rule (EIP-3541) intending to reject such code. Any later `CALL` to that address will execute the stored "invalid" bytecode, since the interpreter does not re-check the `0xEF` prefix on ordinary calls — only new-contract-creation flows attempt this check. This can produce state that violates the EIP-3541 invariant that all consensus-following clients are supposed to enforce, is a potential state-divergence / cross-implementation consensus risk, and allows persistence of code that the protocol explicitly intends to forbid.

Whether this manifests as an *externally exploitable* state-corruption bug versus a harmless quirk depends on whether the outer transaction-processing path (`StateTransition.TransitionDb`) unconditionally reverts to a pre-call snapshot whenever `vmerr != nil` is returned from the top-level `Create` call. I was not able to fully confirm this from the code I could inspect (the `blockchain/state_transition.go` grep only located line matches, not full logic), so this remains an open question that a Devin agent with fuller access should verify by tracing `ApplyMessage`/`TransitionDb`'s handling of the `vmerr` returned from `evm.Create`.

### Likelihood Explanation
The relevant path (`TxInternalDataSmartContractDeploy.Execute` → `vm.Create`/`CreateWithAddress` → `evm.create`) is reachable by any unprivileged transaction sender submitting a smart-contract-deployment transaction whose init code returns bytecode starting with byte `0xEF`, targeting a chain state in the Kore-but-pre-Prague fork window. No special privileges, keys, or validator/peer control are required — only crafting init code with the desired return value, which is trivial. The comment in the source confirms the authors were aware of the ordering issue and consciously chose to preserve it "for backwards compatibility," which suggests it may already be a known, intentionally-retained historical quirk of the chain rather than a newly introduced flaw — this reduces the likelihood that it represents an unpatched, exploitable vulnerability versus a documented consensus-compatibility artifact.

### Recommendation
- Trace whether `StateTransition.TransitionDb`/`ApplyMessage` reverts all state changes (including the `SetCode` call) whenever `vmerr != nil` is returned from the top-level contract-creation call. If it does, this finding has no security impact beyond a cosmetic/ordering code smell. If it does not fully revert `SetCode`, this is a genuine state-invariant violation that must be fixed by moving the EIP-3541 check before the `SetCode` and revert logic (mirroring how the Prague-era check at lines 592–595 is placed correctly, before code is written).
- Since consensus-compatibility for already-produced historical blocks likely constrains any fix (the comment explicitly says so), any change must be scoped so it only takes effect from a specific block/fork boundary forward, to avoid a hard-fork-incompatible chain split.

### Proof of Concept
1. On a Kaia chain configured with `IsKore = true` and `IsPrague = false` (i.e., between the Kore and Prague hardforks).
2. Submit a `TxTypeSmartContractDeploy` (or fee-delegated variant) transaction whose init code, when executed, `RETURN`s bytecode whose first byte is `0xEF` (e.g., simple init code: `PUSH1 0xEF PUSH1 0 MSTORE8; PUSH1 1 PUSH1 0 RETURN`).
3. Observe `evm.create()`'s flow: `SetCode(address, ret)` executes and commits the `0xEF...` bytecode to `evm.StateDB` (line 604) before the EIP-3541 check at line 631 runs and sets `err = ErrInvalidCode`.
4. Because the revert branch (lines 618–625) only fires when `err != nil` *at that point* (before the 3541 check runs), it does not revert this `SetCode`.
5. Inspect state (via `eth_getCode` at the created address) after the transaction is included in a block — confirm whether the `0xEF`-prefixed bytecode is present at the contract address despite the "receipt status: failed" outcome, or whether an outer revert (in `StateTransition`) actually erased it (this final check requires tracing/verifying `blockchain/state_transition.go`, which I could not fully confirm within available tool calls).

**Note on confidence:** I was unable to fully verify, within the available search budget, whether the outer `StateTransition.TransitionDb`/`ApplyMessage` logic unconditionally discards all state changes (including `SetCode`) when a non-nil `vmerr` is returned from the top-level `Create` call. This is the single missing piece needed to convert this from "documented quirk" into a confirmed, concrete state-persistence vulnerability. I recommend a Devin session with full repository access review `blockchain/state_transition.go`'s `TransitionDb` function in detail, specifically how it uses `vmerr` and whether/when it calls `StateDB.RevertToSnapshot` for the whole message, before treating this as a confirmed critical/high-severity finding.
