### Title
Out-of-bounds atom-length read in CLVM canonical-serialization check crashes spend-bundle validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse raw, attacker-controlled CLVM bytes (`puzzle_reveal` and `solution` of a submitted `CoinSpend`) by repeatedly indexing into the buffer based on a length-prefix decoded from the buffer itself, without ever checking that the computed `offset` stays within the buffer bounds before dereferencing it. This mirrors the CVE-2016-9811 bug class: a parser trusts an internal length field taken from crafted/untrusted input and reads past the end of the buffer instead of validating remaining length first.

### Finding Description
`is_atom_canonical()` decodes a length prefix and then loops `prefix_len` times reading `clvm_buffer[offset]` to build `atom_len`, incrementing `offset` each iteration with no bounds check: [1](#0-0) 

`is_clvm_canonical()` walks the whole buffer the same way, indexing `clvm_buffer[offset]` and calling `is_atom_canonical` without ever confirming `offset < len(clvm_buffer)` before the read, and only checks buffer-length consistency *after* the entire walk completes: [2](#0-1) 

This function is invoked directly on attacker-supplied bytes from every coin spend inside a submitted `SpendBundle`, in the mempool validation path reachable by any unprivileged spend-bundle submitter: [3](#0-2) 

Because Python `bytes`/`bytearray` indexing is itself bounds-checked, an out-of-range `offset` raises an uncaught `IndexError` (Python's analog to a native OOB read: the parser blows past the buffer end following an attacker-controlled length field, exactly the `windows_icon_typefind`-style bug class). Unlike a native OOB read, this doesn't leak memory, but it produces an unhandled exception inside `validate_spend_bundle()`, which is called from `add_spend_bundle()` and ultimately from the full node's transaction-intake path.

A crafted `puzzle_reveal` or `solution` can be built by picking an atom-marker byte (e.g. `0xFC`, requesting a 6-byte length prefix) placed so close to the end of the buffer that the `for i in range(prefix_len)` loop tries to read bytes past the buffer's actual end, e.g. a 1-byte buffer consisting solely of `\xFC` (claims a 5-byte continuation that doesn't exist).

### Impact Explanation
This is a spend-triggered transaction-processing fault: an unprivileged party can submit a spend bundle containing a crafted, otherwise well-formed-looking `puzzle_reveal`/`solution` whose final bytes are truncated relative to what the length-prefix encoding implies. When the full node calls `is_clvm_canonical` during `validate_spend_bundle`, it raises an unhandled `IndexError` instead of returning a controlled validation error (e.g. `Err.INVALID_COIN_SOLUTION`). Depending on how far up the call stack this propagates uncaught, this can disrupt mempool-item processing for that spend bundle (task/RPC failure), which matches the "spend-triggered transaction-processing halt" impact class called out in scope. I could not fully verify, within available tool budget, whether an outer `try/except Exception` wraps this call somewhere between `validate_spend_bundle` and the network/RPC entry points in `chia/full_node/full_node.py` / `chia/full_node/full_node_api.py`, so I cannot confirm whether this only fails a single spend bundle gracefully or causes a broader disruption (e.g., an unhandled task exception). This uncertainty should be resolved by tracing the exact exception handling around `MempoolManager.add_spend_bundle()` callers.

### Likelihood Explanation
Likelihood is high in terms of reachability — any unprivileged party who can submit a spend bundle (via wallet RPC `push_tx`/`send_transaction` or direct P2P `new_transaction`/`request_transaction` flow) controls `puzzle_reveal` and `solution` bytes directly, and no prior validation trims/bounds-checks them before `is_clvm_canonical` runs. Constructing the crafted byte sequence is straightforward (a single out-of-range atom-length marker at the tail of the buffer, as shown above).

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (verify `offset < len(clvm_buffer)`, raising/returning a controlled invalid-canonical result rather than falling through to unchecked indexing), and add a similar guard in `is_clvm_canonical()`'s main loop before dereferencing `clvm_buffer[offset]`. Ensure `validate_spend_bundle()` (and any other caller) treats malformed/truncated CLVM buffers as `Err.INVALID_COIN_SOLUTION` rather than allowing an `IndexError` to propagate, and add regression tests using truncated/crafted length-prefix buffers similar to the existing `test_clvm_not_canonical` cases in `chia/_tests/core/mempool/test_mempool_manager.py`.

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
