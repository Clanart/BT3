### Title
Bridge Circuit never validates that `payout_spv.transaction` actually pays the withdrawer, only that it spends the registered outpoint - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs:137-236) verifies that `input.payout_spv.transaction.input[payout_input_index].previous_output` equals the withdrawer's registered `user_wd_outpoint`/`vout` obtained from `verify_storage_proofs`, but never inspects `input.payout_spv.transaction.output` to confirm a payment to the withdrawer's destination script/amount. The only output the circuit reads is the *first OP_RETURN* output, used solely to extract the `operator_xonlypk` for `deposit_constant` — not to validate the payout. This confirms the binding `payment_to_withdrawer == bridge_amount_recorded_by_citrea_withdraw` is never checked between the SPV/storage-proof verification and `guest.commit(journal_hash)`.

### Finding Description
The broken binding: **payout_fronted_to_withdrawer_by_operator == bridge_amount_recorded_by_citrea_withdraw** is asserted nowhere. What is actually checked (`circuits-lib/src/bridge_circuit/mod.rs:186-204`) is only:
```
assert_eq!(user_wd_txid, input.payout_spv.transaction.input[payout_input_index].previous_output.txid, ...);
assert_eq!(vout, input.payout_spv.transaction.input[payout_input_index].previous_output.vout, ...);
```
i.e., that *some* input of the claimed payout transaction spends the exact outpoint recorded as `withdrawal_utxo` for that Citrea withdrawal (`core/src/database/verifier.rs:139` / `verify_storage_proofs` in `circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`). After this, the code only reads `get_first_op_return_output(&input.payout_spv.transaction)` to extract the operator's xonly pubkey for `deposit_constant` — it never reads any `TxOut` that would need to match the withdrawer's `output_script_pubkey`/`output_amount` recorded when they called `withdraw` (`core/src/operator.rs:560-627`, `core/src/rpc/clementine.proto:239-253`).

Root cause: the intended design relies on the withdrawer's outpoint being spendable *only* via the specific pre-agreed signature (`in_signature`, `SIGHASH_SINGLE|ANYONECANPAY`) that ties the withdrawer's key to a specific output (see `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`, and comment in `core/src/rpc/clementine.proto:242-252`: "User's signature is only valid for this pubkey/amount"). The bridge circuit was written assuming that "outpoint got spent" implies "the operator paid correctly", because normally only a transaction carrying the withdrawer's specific `SIGHASH_SINGLE|ANYONECANPAY` signature (bound to the intended output) can validly spend that Taproot key-path UTXO. However, the circuit never actually checks that binding on-chain — it does not verify the payout transaction's witness/signature or its outputs at all. It merely trusts that whichever transaction spends that outpoint is *the* payout. Since the withdrawer still holds their own private key for that UTXO (it is their own wallet output), they can spend it themselves at any later time for an unrelated purpose (e.g., moving dust), producing a completely different, validly-confirmed transaction that has nothing to do with the withdrawal payout. Neither `bridge_circuit` nor the disprove machinery (`BridgeDisproveScript`/`ClementineDisproveScript`, documented in `docs/bridge-circuit.md`) re-derives or checks the actual payout output, because the disprove circuits only re-verify the same (flawed) `bridge_circuit` logic and watchtower/challenge bookkeeping — not payment correctness.

Exploit flow: withdrawal is registered (Citrea `withdraw`), operator never fronts BTC, the designated outpoint is later spent by any confirmed transaction (honest or not), operator supplies that transaction's SPV proof + correct `payout_input_index` as `payout_spv`, and constructs an OP_RETURN output committing an operator xonlypk (trivial — operator can construct this arbitrarily via a helper transaction, or even use a transaction they fully control if they can get the withdrawer's key-spend signature reused via anyone-can-pay flexibility — though the strict precondition given is that some third-party/withdrawer tx spends it). The rest of the pipeline (`total_work_and_watchtower_flags`, SPV `verify`, `lc_proof_verifier`, `verify_storage_proofs`) all succeed because none of them touch payment correctness. `guest.commit(journal_hash)` is reached, producing a valid Groth16 proof that watchtowers/verifiers cannot fault (they only check total work and challenge-signature bookkeeping, not payment correctness, per `docs/bridge-circuit.md`). This journal then flows through Assert → uncontested ChallengeTimeout → Reimburse, releasing vault BTC without a matching fronted payout.

### Impact Explanation
This allows a malicious operator to be reimbursed (BTC leaving the move-to-vault UTXO) for a payout it never funded — an explicit Critical category ("operator reimbursed for a payout it never funded", "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal"). It is repeatable per withdrawal/operator whenever the precondition (designated outpoint spent by any tx) holds, and there is no disprove path to catch it since the disprove circuits check the same unconstrained journal/logic rather than payment correctness. Blast radius: any withdrawal whose registered outpoint is later spent for any reason is a target.

### Likelihood Explanation
The gating precondition is narrow but not implausible: the withdrawal outpoint (a UTXO the withdrawer owns and signs over with `SIGHASH_SINGLE|ANYONECANPAY`) must get spent by some transaction other than a correct payout. Because the withdrawer retains their own private key for that UTXO, they can trivially spend it themselves at any time (e.g. consolidating/moving dust, or even by an operator convincing them to sign something unrelated). No mainnet or live Citrea access is required to demonstrate the circuit-level gap: a unit test on `bridge_circuit` with a `payout_spv.transaction` whose outputs contain no payment to the withdrawer's registered destination (but whose `input[payout_input_index].previous_output` matches `user_wd_outpoint`/`vout`) will not panic and will produce a `journal_hash`, proving the missing binding is real regardless of how likely the spend-precondition is to occur in a given deployment.

### Recommendation
In `circuits-lib/src/bridge_circuit/mod.rs::bridge_circuit`, after validating `payout_input_index` matches the withdrawal outpoint, add an explicit check that some `TxOut` in `input.payout_spv.transaction.output` pays exactly the withdrawer's registered destination script and amount (these must be committed into `StorageProof`/`BridgeCircuitInput` and included, e.g., as additional withdrawal-output storage-proof fields verified via `verify_storage_proofs`, analogous to how `user_wd_outpoint`/`vout` are already proven). The circuit must assert `payout_output.script_pubkey == withdrawer_script_pubkey && payout_output.value == withdrawal_amount` before computing `deposit_constant`/`journal_hash`, closing the gap between "outpoint spent" and "withdrawer actually paid."
