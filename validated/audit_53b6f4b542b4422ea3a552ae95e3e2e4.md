### Title
Aggregator gRPC server accepts unauthenticated `Setup`/state-changing calls when `client_verification` is `false` - ([File: core/src/servers.rs])

### Summary
When `config.client_verification` is `false`, `create_grpc_server` builds a `ServerTlsConfig` without `.client_ca_root(...)` (no client certificate is requested during the TLS handshake) and wraps the service in `Interceptors::Noop`, whose `call()` unconditionally returns `Ok(req)`. `create_aggregator_grpc_server` does not force `client_verification` on for the aggregator; it only emits a `tracing::warn!` when it happens to be enabled. The result is that any network peer able to open a plain TLS connection to the aggregator's advertised host:port can invoke `ClementineAggregator/Setup` (and any other aggregator RPC) with no authentication at all.

### Finding Description
The broken binding is: `CALLER_AUTHORITY(Setup caller) == aggregator_operator_holding(aggregator_cert_path)`. Tracing the code:

- `create_grpc_server` only adds `.client_ca_root(client_ca)` to `ServerTlsConfig` when `config.client_verification` is `true`; otherwise `ServerTlsConfig::new().identity(server_identity)` is used with no client CA, meaning the TLS handshake never requests, let alone validates, a client certificate. [1](#0-0) 
- The interceptor is selected the same way: `OnlyAggregatorAndSelf` only when `client_verification` is true, else `Noop`. [2](#0-1) 
- `Interceptors::Noop::call` returns `Ok(req)` unconditionally, performing no identity check whatsoever. [3](#0-2) 
- `create_aggregator_grpc_server` does not enforce `client_verification`; it merely warns if it is enabled and always delegates to `create_grpc_server` with whatever the config says. [4](#0-3) 

With this configuration (the default posture the question describes for the aggregator), an attacker who is only able to reach the aggregator's TCP port over TLS — with no client certificate, no key share, no prior relationship with the bridge — can dial in and call `Setup` (or any other unary/streaming RPC exposed by `ClementineAggregatorServer`) as if they were the legitimate aggregator operator. `only_aggregator_and_self`, the only guard that would otherwise enforce the `CALLER_AUTHORITY` binding by comparing `leaf_cert` against `aggregator_cert`/`our_cert`, is never invoked in this configuration because `Noop` is used instead. [5](#0-4) 

### Impact Explanation
This is, at minimum, an unauthenticated state-changing call reachable by an unprivileged network attacker, matching the "High" bucket ("an unauthenticated state-changing or broadcasting call"). `Setup` drives collection and redistribution of verifier/operator public keys used to derive `nofn_xonly_pk`, so an attacker triggering it arbitrarily (including interleaved with legitimate `NewDeposit` flows) can influence which key set backs subsequently-presigned transactions. Whether this concretely escalates to "Critical – a move-to-vault UTXO permanently frozen" depends on the internal locking/versioning behavior of `AggregatorServer::setup` and its interaction with an in-flight `NewDeposit`, which I was not able to fully trace within the available context (the `setup` RPC handler implementation in `core/src/rpc/aggregator.rs` was not reached before the context/tool budget was exhausted). The demonstrated, code-confirmed impact is the authentication bypass itself; the specific "frozen movetx via concurrent Setup/NewDeposit interleaving" scenario remains a plausible but unverified consequence that would need a targeted `cargo test` reproduction against `AggregatorServer::setup` and `AggregatorServer::new_deposit` to confirm.

### Likelihood Explanation
This is trivially reachable by any unprivileged attacker with network access to the aggregator's TCP port whenever the deployment runs with `client_verification = false` — no cost in BTC or fees, no special access, and fully repeatable (every RPC call is independent and the interceptor state never changes). The only precondition is the deployment configuration flag, which per the question is the documented default for the aggregator role.

### Recommendation
Do not allow `client_verification = false` for the aggregator role, or, independent of that flag, always require and validate a client certificate (mTLS) for privileged aggregator RPCs such as `Setup`, `NewDeposit`, and any key-management endpoint — i.e., make `create_aggregator_grpc_server` unconditionally use `ServerTlsConfig::client_ca_root(...)` and `Interceptors::OnlyAggregatorAndSelf` rather than making this contingent on a config flag that can be silently left at its insecure default.

### Proof of Concept
A `cargo test` under `core/src/test` (or a new integration test) should:
1. Start `create_aggregator_grpc_server` with `config.client_verification = false`.
2. Dial the resulting `host:port` over TLS without presenting a client certificate.
3. Assert the raw `tonic` channel connects successfully and a `ClementineAggregator/Setup(Empty)` call returns `Ok(...)` rather than `Status::unauthenticated`.
4. To probe the escalation claim, additionally: run `setup()` twice concurrently interleaved with `new_deposit()`, then assert whether the resulting `movetx`'s presigned scripts still match the `nofn_xonly_pk` recorded in the deposit's DB row — this second assertion is the part that still needs verification against `AggregatorServer::setup`'s actual locking behavior before it can be confirmed as a Critical-severity fund-freezing bug rather than just the confirmed High-severity authentication bypass.

```rust
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
```
