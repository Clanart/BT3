### Title
Silent, unverified rewrite of local git remote URL from GitHub API `clone_url` allows push-target hijacking - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The external report's broken invariant is: a security-relevant decision (accepting a swap price) is driven by an attacker-influenced data source (a low-liquidity oracle) without adequate corroboration or bounds checking. In GitHub Desktop, `updateRemoteUrl` in [1](#0-0)  performs an analogous unchecked trust decision: it silently rewrites the user's local `origin` remote URL to whatever `clone_url` value is returned by the GitHub API for a repository, based only on a protocol match and a "did the user manually change it" heuristic — never re-validating that the new URL still points to the same owner/repo identity the user originally added.

### Finding Description
`updateRemoteUrl` computes `urlsMatch` by comparing the git remote's current URL against `apiRepo.clone_url` via `urlMatchesRemote` [2](#0-1) . It then checks only two conditions before calling `gitStore.setRemoteURL(...)`:
1. `protocolsMatch` — that the URL scheme (http/ssh) hasn't changed [3](#0-2) .
2. `remoteUrlUnchanged` — that the previously cached `gitHubRepository.cloneURL` still matches the current git remote, i.e., the user hasn't manually customized the remote [4](#0-3) .

If both hold and the URLs differ, the function calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` [5](#0-4) , which directly rewrites the `origin` remote in the on-disk git config via `git remote set-url` (`setRemoteURL` in `git-store.ts`/`git/remote.ts`).

Crucially, there is no check that `updatedRemoteUrl` still refers to the *same owner/repo* as before — `urlMatchesRemote` in [6](#0-5)  is only used to detect whether a change occurred, not to constrain what the new value is allowed to be. The value `apiRepo.clone_url` comes straight from a GitHub API response object (`IAPIRepository`), which is exactly the "GitHub API object" attacker-control surface called out as in-scope: a hostile or compromised GitHub Enterprise Server, a malicious API proxy/MITM on a self-hosted GHES instance, or a subverted API response (e.g., via a compromised or malicious integration) can return an attacker-chosen `clone_url` for a repository the user already has cloned. As long as the scheme matches (trivial to satisfy) and the user hasn't hand-edited their remote, Desktop will silently retarget `origin` to the attacker's URL.

This mirrors the oracle bug's structure precisely: a value from an external, attacker-influenceable source is accepted as ground truth with only superficial sanity checks (fee/TWAP staleness ↔ protocol/previous-state match), rather than a strong invariant (owner+name identity, or explicit user confirmation).

### Impact Explanation
Once `origin` is silently repointed, all subsequent `git push` operations from the user (and from Desktop's own push/pull-request flows) go to the attacker-controlled repository instead of the real one. This is a silent corruption of what the user pushes, and — because Desktop authenticates pushes with the stored GitHub credentials/token for that account/host — it can also result in credential/token exfiltration if the attacker-controlled endpoint captures the git-credential HTTPS auth flow, or at minimum leaks proprietary commit content to a third party the user never intended. The user receives no interactive warning; the remote change happens as a background side effect of a repository-info refresh.

### Likelihood Explanation
The path requires the attacker to control (or be believed as) the GitHub API endpoint or its response for a repository the user has already added to Desktop — realistic for GitHub Enterprise Server deployments where Desktop trusts the configured host's API, or for a network-position/MITM actor against a GHES instance without pinned TLS validation. The two guard conditions (`protocolsMatch`, `remoteUrlUnchanged`) are satisfiable by any attacker who simply keeps the scheme the same and targets users who have not customized their remote (the common case), so the guard does not meaningfully constrain the attacker's chosen destination host/owner/repo.

### Recommendation
Before calling `setRemoteURL`, validate that the new `clone_url` still resolves (via `parseRemote`) to the same `hostname` as the account's configured API host, and ideally require that the repository's persistent identity (API `id`, not just owner/name string) is unchanged — not merely that the client-computed protocol matches. If the host or owner/name differs from what is on record, treat it as an explicit repository-transfer/rename event requiring user confirmation (similar to how GitHub.com already surfaces "repository renamed" flows) rather than silently rewriting the remote.

### Proof of Concept
1. Add a repository cloned from a GitHub Enterprise Server instance (`https://ghe.example.com/acme/webapp.git`) to Desktop.
2. Compromise or MITM the GHES API endpoint (or operate a malicious GHES instance the user is pointed at) so that `GET /repos/acme/webapp` returns `clone_url: "https://ghe.example.com/attacker/webapp.git"`.
3. Desktop's periodic background refresh calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` [7](#0-6) . Since the user hasn't manually edited `origin` and the scheme is unchanged, `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is true, and `gitStore.setRemoteURL('origin', 'https://ghe.example.com/attacker/webapp.git')` executes [5](#0-4) .
4. The user's next `git push` (via Desktop's UI or CLI, since Desktop rewrote the actual `.git/config`) silently sends commits/credentials to the attacker's repository.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
