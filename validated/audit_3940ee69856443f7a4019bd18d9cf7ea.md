### Title
`internal_withdraw` Bypasses Aggregator ECDSA Signature Check with No Mandatory Compensating Control — (`core/src/rpc/operator.rs`)

### Summary

`OperatorServer::internal_withdraw` calls `operator.withdraw()` directly without performing any ECDSA aggregator verification signature check. The only protection is an optional mTLS interceptor (`OnlyAggregatorAndSelf`) that is gated on the `client_verification` config flag. When that flag is false — a fully supported code path — any network-reachable caller can trigger a payout transaction with no aggregator authorization.

### Finding Description

`withdraw` (the public endpoint) enforces the ECDSA check: [1](#0-0) 

If `aggregator_verification_address` is set and no valid signature is provided, it returns `ECDSAVerificationSignatureMissing` or `InvalidECDSAVerificationSignature`.

`internal_withdraw` skips this entirely: [2](#0-1) 

It parses the `WithdrawParams` and calls `self.operator.withdraw(...)` with no signature check at all. The only server-level protection is the interceptor applied in `create_grpc_server`: [3](#0-2) 

When `config.client_verification` is `false`, the `Noop` interceptor is used — no client certificate is required. This is an explicitly supported code path, not an edge case. [4](#0-3) 

The Unix socket path (used in tests and potentially in some deployments) also has **no TLS or interceptor at all**: [5](#0-4) 

### Impact Explanation

An attacker who can reach the operator's gRPC port when `client_verification=false` (or via a Unix socket) can submit arbitrary `WithdrawParams` — any `withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount` — and receive a signed payout transaction without any aggregator authorization. This directly violates the invariant that all withdrawal requests must carry a valid aggregator ECDSA signature, and can result in bridged BTC being paid out without aggregator consent.

### Likelihood Explanation

`client_verification` is an optional config flag. Operators who deploy without it (e.g., relying on network-level firewalls, or in staging/internal environments) expose `internal_withdraw` to any reachable caller. The endpoint is on the same port as all other operator gRPC methods with no per-method mandatory auth.

### Recommendation

1. Remove `internal_withdraw` from the production gRPC surface entirely, or gate it behind `#[cfg(test)]` like `internal_finalized_payout` does: [6](#0-5) 
2. If it must remain in production, apply the same ECDSA aggregator signature check as `withdraw`, or enforce `client_verification=true` as a hard requirement when `aggregator_verification_address` is set.

### Proof of Concept

A Rust integration test would:
1. Start an operator server with `client_verification=false` and `aggregator_verification_address` set.
2. Call `internal_withdraw` with valid `WithdrawParams` but no `verification_signature` field (the message type `WithdrawParams` has no such field — it is structurally impossible to include one).
3. Assert that a `RawSignedTx` is returned with no error, confirming the payout was produced without aggregator authorization.

The structural impossibility of including a `verification_signature` in `WithdrawParams` (unlike `WithdrawParamsWithSig`) means this bypass is unconditional at the message level: [7](#0-6)
