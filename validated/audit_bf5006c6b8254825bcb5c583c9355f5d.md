### Title
Infinite loop DoS via cyclic coin dependency graph in `Offer.get_root_removal` / `Offer.get_cancellation_coins` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_root_removal()` walks a coin's `parent_coin_info` chain through the set of removal coins declared in an (attacker-supplied) offer bundle until it finds a "non-ephemeral" root. `Coin.parent_coin_info` is an arbitrary field controlled by whoever crafts the `CoinSpend`/`Offer` — it is not required to correspond to any real chain relationship until the bundle is actually submitted and validated against blockchain state. This is analogous to the ImageMagick DJVU parser bug (CVE-2017-11478): a malformed/adversarial input containing a self-referential structure drives a loop that never reaches its termination condition, causing CPU exhaustion / hang. Here, a crafted offer with two or more removal coins whose `parent_coin_info` fields form a cycle (each parent points to another coin inside the same removal set, with no root outside the set) makes `non_ephemeral_removals` empty for that cycle, so the `while coin not in non_ephemeral_removals:` loop in `get_root_removal` never terminates.

### Finding Description
`get_root_removal` computes, for a given coin, the earliest non-ephemeral ancestor within the bundle: [1](#0-0) 

```
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
```

`non_ephemeral_removals` is the set of removal coins whose `parent_coin_info` is *not* the name of any other removal coin — i.e. the "roots" of the dependency graph induced purely by the (unverified) `parent_coin_info`/`name()` fields of the coins in the offer. Because `Coin.parent_coin_info` is just an arbitrary `bytes32` field supplied by whoever authored the offer file (no chain lookup or signature ties it to an actual parent until the spend bundle is later pushed and validated by consensus), an attacker who crafts an `Offer`/`WalletSpendBundle` can make two coins, A and B, whose `parent_coin_info` fields point at each other's `name()` (a 2-cycle, or an N-cycle). For every coin in such a cycle, `parent_coin_info` *is* the name of another removal coin, so none of them qualify as `non_ephemeral_removals`. The `while` loop in `get_root_removal` then oscillates around the cycle forever, since it can never find a coin that is a member of `non_ephemeral_removals`.

`get_root_removal` is invoked from `get_primary_coins`, which is invoked while examining an offer (e.g. to enumerate the coins backing offered assets): [2](#0-1) 

and `get_cancellation_coins`, which walks all non-addition coin spends' announcement/dependency graph in a similar unbounded fashion: [3](#0-2) 

Both of these entry points process a fully attacker-controlled `Offer` object (deserialized from an offer file/string a counterparty shares), which is exactly the "offer counterparty" reachable path called out in scope. `Offer.__bytes__`/parsing and `WalletSpendBundle` structures do not validate that `parent_coin_info` fields form a DAG rooted outside the removal set before these methods run.

### Impact Explanation
This is a spend-triggered transaction-processing halt: any wallet code path that calls `get_primary_coins()`/`get_cancellation_coins()`/`get_root_removal()` on an attacker-crafted offer (for example when a user opens/inspects/imports an offer file received from a counterparty before deciding whether to accept it) will hang the calling thread/task in an infinite Python loop, consuming CPU indefinitely with no timeout, effectively denying wallet service for that operation (and, depending on how it's invoked — e.g. from an RPC handler — potentially blocking the RPC/event loop). This matches the CVSS 6.5 / DoS impact class of the reported CVE (infinite loop causing CPU exhaustion from malformed untrusted input).

### Likelihood Explanation
Likelihood is high given reachability: constructing an `Offer`/`WalletSpendBundle` with attacker-chosen `Coin` objects (arbitrary `parent_coin_info`, `puzzle_hash`, `amount`) is straightforward — no cryptographic proof of parentage is required to build the data structure, only to have it accepted by consensus later, which is irrelevant to this client-side analysis path. No special privileges are needed: this is the "offer counterparty" trust boundary — simply sharing a malicious offer file/string with a victim wallet user is enough to trigger the loop when the victim's wallet inspects it.

### Recommendation
Add cycle detection / progress bound to `get_root_removal` (e.g. track visited coin names and raise a `ValueError` if a coin is revisited or the number of iterations exceeds `len(all_removals)`), and apply the same bounded-iteration/cycle-guard to the dependency-resolution loops in `get_cancellation_coins`. Treat these as untrusted-input parsers and validate that the coin graph is acyclic before traversal.

### Proof of Concept
Conceptually:
1. Build two `Coin` objects, `coin_a` and `coin_b`, with `coin_a.parent_coin_info == coin_b.name()` and `coin_b.parent_coin_info == coin_a.name()` (choose puzzle_hash/amount so the two names differ, but each references the other as parent).
2. Create `CoinSpend`s for `coin_a` and `coin_b` (any puzzle reveal/solution producing conditions, e.g. simple `CREATE_COIN`s not creating `coin_a`/`coin_b` themselves so `additions()` excludes them and they remain in `removals()`), aggregate into a `WalletSpendBundle`.
3. Wrap in an `Offer` (`Offer(requested_payments={}, _bundle=bundle, driver_dict={})`) and call `offer.get_primary_coins()` (or `offer.get_cancellation_coins()`).
4. Observe the call never returns — `get_root_removal` loops indefinitely because `non_ephemeral_removals` for `{coin_a, coin_b}` is empty.

Note: I was unable to fully verify every helper (`additions()`, `removals()` definitions were not retrieved in full detail before the tool budget ran out), so the exact preconditions for keeping both cyclic coins out of `additions()` should be double-checked by a follow-up code read of `Offer.additions()`/`Offer.removals()` before finalizing a concrete reproducible test.
