### Title
Missing `AGG_SIG_UNSAFE` domain-separation denylist in `pkm_pairs()` allows signature replay across AGG_SIG_* domains - (File: `chia/consensus/condition_tools.py`)

### Summary
`chia/consensus/condition_tools.py` contains two parallel functions that build BLS `(pubkey, message)` pairs for aggregate-signature verification: `pkm_pairs()` (operating on the Rust-produced `SpendBundleConditions`, the path documented as the one used by mempool and block validation) and `pkm_pairs_for_conditions_dict()` (a legacy path operating on `ConditionWithArgs` dicts). Only the legacy function enforces the check that an `AGG_SIG_UNSAFE` message may not end with any of the domain-separated suffixes reserved for `AGG_SIG_ME`/`AGG_SIG_PARENT`/`AGG_SIG_PUZZLE`/etc. `pkm_pairs()` omits this check entirely, exactly mirroring the CVE-2024-39887 pattern where a denylist (`DISALLOWED_SQL_FUNCTIONS`) was enforced in some code paths but not all, letting attackers bypass the intended authorization control via the unchecked path.

### Finding Description
`agg_sig_additional_data()` computes, for each network, the domain-separation suffixes appended to coin-bound AGG_SIG messages before signing: [2](#0-1) 

`pkm_pairs_for_conditions_dict()` uses these suffixes as a denylist to reject any `AGG_SIG_UNSAFE` message ending in one of them, precisely to stop an `AGG_SIG_UNSAFE` signature (which is not bound to any coin identity) from being crafted/replayed so that it is indistinguishable, in the aggregate BLS pairing check, from a legitimately domain-separated `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc. signature: [3](#0-2) 

`pkm_pairs()`, which is documented as the function used to "extract AGG_SIG conditions" for the actual mempool/block validation paths, builds the `AGG_SIG_UNSAFE` pairs directly from `conditions.agg_sig_unsafe` with no such filtering: [4](#0-3) [5](#0-4) 

The project's own test suite documents the two functions as expected to behave equivalently (`test_pkm_pairs_vs_for_conditions_dict`), but the equivalence is only exercised for the non-`AGG_SIG_UNSAFE` opcodes in the snippet I could inspect: [6](#0-5) 

### Impact Explanation
If `pkm_pairs()` is the function actually consulted on the consensus-critical path (as the CLVM-execution context documentation states), an attacker can craft a spend bundle that presents an `AGG_SIG_UNSAFE` condition whose message is engineered to end with the `AGG_SIG_ME_ADDITIONAL_DATA` (or other opcode-specific) suffix. Because `AGG_SIG_UNSAFE` messages are never bound to a specific coin, this removes the domain separation that is supposed to prevent a signature produced/observed in one context (e.g., a different coin, a different chain fork, or a different `AGG_SIG_*` condition) from being repurposed to satisfy an unrelated authorization requirement in the aggregated BLS check. This is the same class of bug as the Superset advisory: a security-relevant denylist exists but is not applied on the path that is actually reachable and enforced, permitting an unprivileged submitter of a spend bundle to bypass the intended sig/authorization boundary and potentially move or unlock coins without a properly domain-bound signature.

### Likelihood Explanation
Any spend-bundle submitter can add arbitrary `AGG_SIG_UNSAFE` conditions with attacker-chosen messages; no privileged access is required, so the reachable surface is a single submitted spend bundle. The severity depends on whether `pkm_pairs()` (missing the check) or `pkm_pairs_for_conditions_dict()` (has the check) is the function actually invoked by `MempoolManager`/`FullNode` validation, and whether an equivalent denylist is enforced natively inside the Rust `chia_rs` signature/condition validation that ultimately backs `SpendBundleConditions`. I was not able to fully confirm within the available tool budget whether the Rust layer independently re-implements this check (which would make the Python gap latent/non-exploitable) or whether `full_node.py`'s two call sites to `pkm_pairs` feed directly into the aggregate-signature check without any other domain-separation enforcement.

### Recommendation
Apply the same denylist check used in `pkm_pairs_for_conditions_dict()` to `pkm_pairs()` before adding `agg_sig_unsafe` pairs, and add explicit tests asserting that `AGG_SIG_UNSAFE` messages ending in any of `agg_sig_additional_data()`'s values are rejected via the `pkm_pairs()` path (not just the legacy dict path). Confirm in the `chia_rs` Rust source whether an equivalent check exists server-side; if it does not, this is a real consensus-signature-authorization gap that must be fixed in lockstep with any Rust-side validation.

### Proof of Concept
Conceptually: construct a spend bundle whose coin spend includes an `AGG_SIG_UNSAFE` condition `(43 pubkey message)` where `message` is chosen so that `message` ends with `agg_sig_additional_data(AGG_SIG_ME_ADDITIONAL_DATA)[ConditionOpcode.AGG_SIG_ME]` (i.e., the raw `AGG_SIG_ME_ADDITIONAL_DATA` bytes). If `pkm_pairs()` is the function consulted by mempool/full-node validation for signature-pair construction, this condition is accepted unchecked, whereas the same construct fed through `pkm_pairs_for_conditions_dict()` is rejected with `Err.INVALID_CONDITION`, demonstrating the enforcement gap between the two code paths described above.

def pkm_pairs_for_conditions_dict(
    conditions_dict: dict[ConditionOpcode, list[ConditionWithArgs]],
    coin: Coin,
    additional_data: bytes,
) -> list[tuple[G1Element, bytes]]:
    ret: list[tuple[G1Element, bytes]] = []

    data = agg_sig_additional_data(additional_data)

    for cwa in conditions_dict.get(ConditionOpcode.AGG_SIG_UNSAFE, []):
        validate_cwa(cwa)
        for disallowed in data.values():
            if cwa.vars[1].endswith(disallowed):
                raise ConsensusError(Err.INVALID_CONDITION)
        ret.append((G1Element.from_bytes(cwa.vars[0]), cwa.vars[1]))
