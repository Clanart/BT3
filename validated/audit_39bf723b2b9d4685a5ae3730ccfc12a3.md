### Title
Uncaught array-index crash from raw/numstat desync in `parseRawLogWithNumstat` when diffing an attacker-crafted commit range - (File: app/src/lib/git/log.ts)

### Summary
The Dogecoin/Bitcoin bug fixed duplicate transaction inputs breaking an implicit "one distinct entry per input" invariant, letting a crafted transaction desynchronize per-input accounting and crash the node. Desktop's `parseRawLogWithNumstat` in `app/src/lib/git/log.ts` has the analogous invariant: it assumes a strict 1:1, order-preserving correspondence between the raw diff entries (`:`-prefixed lines) it pushes into the `files` array and the numstat lines it later walks through using a separate counter (`numStatCount`) to index back into that same array.

### Finding Description
`parseRawLogWithNumstat` parses combined `git diff/log --raw --numstat -z` output in two passes over one interleaved token stream: [1](#0-0) 

For every line starting with `:` it pushes a new `CommittedFileChange` onto `files`. For every other line (a numstat line) it does not look up the corresponding raw entry by path — it uses a simple incrementing counter `numStatCount` to index directly into `files[numStatCount]`: [2](#0-1) 

This hard-codes the assumption that Git will always emit exactly the same number of raw entries and numstat entries, in the same order, for a given diff. That assumption is the "no duplicates / no extra entries" invariant — analogous to the "no duplicate inputs" invariant in the Dogecoin transaction-validation code. The changelog shows Desktop has already hit a related failure mode once ("Fix 'Invalid numstat line' error when trying to preview a pull request - #17267"), indicating the raw/numstat pairing in this function is fragile and reachable with attacker-influenced repository content (e.g. PR preview diffing).

If a maliciously crafted repository/branch (e.g. via case-only duplicate paths on a case-insensitive filesystem, unusual rename/copy/typechange combinations, or other edge cases that cause Git to emit a different count/order of raw vs. numstat lines) causes `numStatCount` to exceed `files.length - 1`, the line
```
isCopyOrRename(files[numStatCount].status)
```
dereferences `undefined.status`, throwing an uncaught `TypeError` instead of the more benign, already-handled `forceUnwrap('Invalid numstat line', ...)` failure path used elsewhere in the same function for malformed lines.

### Impact Explanation
This function backs several changed-file computations that are invoked on data coming from a remote/fetched repository the user does not control the content of:
- `getChangedFiles` (viewing a commit)
- `getCommitRangeChangedFiles` / `getBranchMergeBaseChangedFiles` (comparing branches / previewing a pull request diff, per the `#17267` changelog entry)
- `getStashedFiles` [3](#0-2) [4](#0-3) 

An attacker who controls a repository, fork, or pull request that a victim opens/previews in Desktop can craft commit content designed to desynchronize the raw/numstat line counts, causing an unhandled exception when Desktop tries to render the changed-file list or diff stats for that commit/PR. Because this is a rendering/parsing failure rather than a memory-safety bug, the ceiling of impact is denial-of-service/crash of the diff-viewing flow (and potentially of the async operation's promise chain if uncaught), not code execution.

### Likelihood Explanation
Likelihood is moderate-to-uncertain: reaching a genuine raw/numstat count mismatch requires an actual Git-emitted discrepancy, and I could not find or construct in the available code/tests a concrete Git command sequence that reliably produces mismatched raw/numstat line counts (Git's own invariant is normally that these sections are in lockstep). The historical `#17267` "Invalid numstat line" bug demonstrates this parser has broken on real-world diffs before, but I don't have proof the *array-index* variant (rather than the *regex-mismatch* variant already guarded by `forceUnwrap`) is currently reachable. This should be treated as a fragility/defense-in-depth finding rather than a confirmed, reproducible crash.

### Recommendation
Add a bounds check before indexing `files[numStatCount]` in `parseRawLogWithNumstat` (e.g. verify `numStatCount < files.length`, or match numstat lines to raw entries by path instead of position), and throw the existing descriptive `forceUnwrap`-style error instead of allowing an uncaught `TypeError`. Ensure callers of `getChangedFiles`/`getCommitRangeChangedFiles`/`getBranchMergeBaseChangedFiles` handle parser failures gracefully (e.g. surface a "diff not available" UI state) rather than letting the exception propagate unhandled.

### Proof of Concept
I could not construct a concrete Git repository/commit that reproduces the raw/numstat count mismatch using only the available indexed code and tests — this would require experimentation with the real `git` binary (e.g. combined-diff edge cases, case-collision renames, or unusual typechange sequences) that is outside the scope of static code search. A background Devin session with terminal/git access would be needed to attempt to construct such a fixture and confirm whether `files[numStatCount]` can actually go out of bounds in practice.

): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)

  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}

export async function getCommitRangeChangedFiles(
  repository: Repository,
  shas: ReadonlyArray<string>,
  useNullTreeSHA: boolean = false
): Promise<IChangesetData> {
  if (shas.length === 0) {
    throw new Error('No commits to diff...')
  }

  const oldestCommitRef = useNullTreeSHA ? NullTreeSHA : `${shas[0]}^`
  const latestCommitRef = shas.at(-1) ?? '' // can't be undefined since shas.length > 0
  const baseArgs = [
    'diff',
    oldestCommitRef,
    latestCommitRef,
    '-C',
    '-M',
    '-z',
    '--raw',
    '--numstat',
    '--',
  ]

  const { stdout, gitError } = await git(
    baseArgs,
    repository.path,
    'getCommitRangeChangedFiles',
    {
      expectedErrors: new Set([GitError.BadRevision]),
    }
  )

  // This should only happen if the oldest commit does not have a parent (ex:
  // initial commit of a branch) and therefore `SHA^` is not a valid reference.
  // In which case, we will retry with the null tree sha.
  if (gitError === GitError.BadRevision && useNullTreeSHA === false) {
    const useNullTreeSHA = true
    return getCommitRangeChangedFiles(repository, shas, useNullTreeSHA)
  }

  return parseRawLogWithNumstat(stdout, latestCommitRef, oldestCommitRef)
}
