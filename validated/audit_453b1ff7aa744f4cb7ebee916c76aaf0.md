### Title
External payments to publicly derivable internal addresses are misclassified as protocol-internal outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Like Kirby treating `.dev` domains and reverse-proxied deployments as "local" based on an environmental assumption that stopped being true, bitcoin-serai's `Scanner` and the processor's `get_outputs` classify any transaction paying to the Branch, Change, or Forwarded offset addresses as an internally-generated protocol output — an assumption that only holds if those addresses are private to the protocol. They are not: the offsets are deterministic outputs of `Secp256k1::hash_to_F` over a fixed DST (`b"Serai Bitcoin Output Offset"`) and public labels (`b"branch"`, `b"change"`, `b"forward"`), so any unprivileged party can compute the internal addresses and send a transaction that is "trusted" as protocol-internal.

### Finding Description
`Scanner::scan_transaction` attributes an output solely by `self.scripts.get(&output.script_pubkey)` in `networks/bitcoin/src/wallet/mod.rs`. The scanner is populated with offsets derived purely from public data in `processor/src/networks/bitcoin.rs`'s `scanner()`: `BRANCH_OFFSET`/`CHANGE_OFFSET`/`FORWARD_OFFSET` are `hash_to_F(KEY_DST, b"branch"|b"change"|b"forward")`. `get_outputs` then maps each scanned output to `OutputType::Branch`, `OutputType::Change`, or `OutputType::Forwarded` via `kinds[offset_repr]` — classifications that downstream code treats as "we made this output ourselves". Nothing authenticates that the transaction was actually created by the threshold; the classification is entirely an ambient property of the destination address, exactly as Kirby's `.dev` check was an ambient property of the hostname. There is also no binding to whether the tx was signed by the group key — any on-chain tx paying to the matched `script_pubkey` qualifies.

### Impact Explanation
Outputs classified as `Forwarded`/`Branch`/`Change` enter the processor's internal output pipeline rather than the external-deposit path (which requires the attached Serai `InInstruction` data and only attaches `data` to `OutputType::External` outputs). An attacker can therefore inject outputs the protocol believes it owns and must act on: forwarded outputs are eligible for the protocol's forwarding/spend plans, causing the multisig to construct and sign transactions spending attacker-supplied (possibly dust-sized) inputs. At minimum this enables fee-drain griefing — dust payments to the Forwarded address cause the threshold to sign spends whose fee cost exceeds the injected value, drawing on real protocol inputs. It also corrupts accounting: externally sent funds are counted as internal protocol liquidity without any corresponding deposit instruction.

### Likelihood Explanation
Reachability requires only sending a standard Bitcoin transaction — the exact class of unprivileged public input in scope. The internal addresses are computable by anyone from the group key plus the public `hash_to_F` constants; no collusion, malformed encodings, or validator misbehavior is needed. Exploitation cost is one on-chain transaction.

### Recommendation
Bind internal-output classification to proof of protocol authorship rather than destination pattern: e.g., only treat a scanned output as `Change`/`Forwarded`/`Branch` if the containing transaction was produced by a recognized protocol spend (matching eventuality/signature provenance), or require an authenticated marker (a committed plan/eventuality ID in the tx) for non-`External` classifications. Externally originated payments to offset addresses should be rejected or treated as `External` deposits.

### Proof of Concept
1. Obtain the current group key `K` (public) and compute `fwd = K + G*hash_to_F("Serai Bitcoin Output Offset", "forward")` (incrementing until even, per `register_offset`), then `addr = p2tr_script_buf(fwd)`.
2. Broadcast a transaction paying a small (dust or near-dust) amount to `addr` from an arbitrary input.
3. On the next scanned block, `get_outputs` records the output with `kind == OutputType::Forwarded`, no `InInstruction` data, and `presumed_origin` set from the attacker's own input — indistinguishable from a protocol-created forward output.
4. The processor schedules/signs a spend of this output per its forwarding logic, consuming protocol inputs for fees in excess of the injected value; repeating the transaction repeats the drain.
