## Analog Found: Stale line-index diff selection is silently re-applied to a freshly re-read working-tree diff during partial commits

### Title
Partial-commit line selection is re-applied against a freshly-read diff with no staleness check, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The Sherlock report's broken invariant is: a value computed from one state snapshot (fixed borrow shares from a floating-debt-dependent conversion) is later re-evaluated against a *different*, drifted state, without ever re-validating that the snapshot is still consistent - silently changing the outcome the user was promised. The GitHub Desktop analog is `applyPatchToIndex` in [1](#0-0)  combined with `formatPatch` in [2](#0-1) : a user's *line-level* selection (`DiffSelection`, addressed by absolute line index into a diff object) is captured once when the Changes view renders a diff, but is later re-applied — unchecked — against a **brand-new diff fetched fresh from disk** at commit time, with no verification that the two diffs still line up.

### Finding Description
When a user partially stages/commits a file (selects specific lines/hunks in the Changes view), the UI stores that selection as a `WorkingDirectoryFileChange.selection` object whose `isSelected(absoluteIndex)` addresses lines by their *position* in a previously rendered diff. That selection can persist for an arbitrary amount of time before the user actually presses "Commit."

At commit time, `stageFiles` ( [3](#0-2) ) calls `applyPatchToIndex` for every file with a partial selection. That function does **not** reuse the diff the UI had rendered — it independently re-fetches the diff from the working directory right there: [4](#0-3) 

`formatPatch` then walks this freshly-fetched diff's hunks and, for every line, calls `file.selection.isSelected(absoluteIndex)` — i.e., it trusts that `absoluteIndex` in the *new* diff still refers to the same logical line the user selected in the *old* diff: [5](#0-4) 

There is no hash/etag/mtime check anywhere in this path comparing the diff used to build the selection against the diff used to build the patch. This is in stark contrast to other places in the same codebase that explicitly guard against exactly this kind of async staleness — e.g. `updateChangesStashDiff` snapshots state before an `await` and bails if anything changed underneath it: [6](#0-5) 

and `initDiffSyntaxMode` in the diff renderer does the same for syntax highlighting: [7](#0-6) 

No equivalent guard exists for the commit-time patch-application path, even though `createCommit` ( [8](#0-7) ) explicitly intercepts and runs repository-controlled git hooks (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`) as part of the same flow, and Desktop also runs `post-checkout`/filter hooks automatically outside user confirmation.

### Impact Explanation
If the tracked file's on-disk content changes between (a) the moment the user reviews a diff and picks specific lines/hunks to include, and (b) the moment Desktop actually re-reads the diff to build the patch for staging, the line indices no longer correspond to the same content. `formatPatch` will apply the user's old selection indices to unrelated hunk content in the new diff, silently including lines the user never reviewed/selected (or dropping ones they did select) into the final commit — and that corrupted commit can subsequently be pushed. This is a "silent corruption of what the user commits or pushes" outcome: the user believes they staged exactly the lines they clicked, but the actual commit content can differ, including attacker-supplied content that was not present when the selection was made.

### Likelihood Explanation
An attacker who controls a cloned/fetched repository can arrange for tracked file content to change asynchronously without any unusual user action: `.gitattributes`-declared `clean`/`smudge` filters, or hook scripts (`post-checkout`, etc.) that execute automatically as part of normal repository operations already exercised by Desktop's git flow (`createCommit`'s `interceptHooks` list shows Desktop already executes several repository-defined hooks around commit time). Any window between diff render and commit click — which is normal, human-timescale UI interaction, not an unnatural step — is sufficient; no elevated privileges, local access, or leaked credentials are required.

### Recommendation
Before applying a stored `DiffSelection` to a newly fetched diff in `applyPatchToIndex`/`formatPatch`, verify that the diff used to build the patch is byte-identical (or structurally equivalent, e.g. same hunk boundaries/content hash) to the diff the selection was computed against. If it differs, invalidate the stale selection and force the user to re-review/re-select before committing, mirroring the staleness-guard pattern already used in `updateChangesStashDiff` and `initDiffSyntaxMode`.

### Proof of Concept
1. Attacker publishes a repository containing a file `app.js` and a `.gitattributes` entry wiring a `clean`/`smudge` filter (or a `post-checkout` hook) that rewrites `app.js` shortly after checkout/on a timer.
2. Victim clones the repo in GitHub Desktop, edits `app.js`, and in the Changes view selects only specific lines to include in the commit (leaving other lines unstaged) — this fixes a `DiffSelection` keyed by absolute line index against the diff currently shown.
3. Before the victim clicks "Commit," the attacker-controlled filter/hook rewrites `app.js` on disk, shifting or altering lines without changing the file's high-level status.
4. Victim clicks "Commit." `stageFiles` → `applyPatchToIndex` ( [9](#0-8) ) fetches a new diff of the now-modified file and `formatPatch` applies the old absolute-index selection to it ( [5](#0-4) ), producing a patch whose included/excluded lines no longer match the user's intended review.
5. The resulting commit — and any subsequent push — silently contains different content than what the victim reviewed and approved in the UI.

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,

        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
