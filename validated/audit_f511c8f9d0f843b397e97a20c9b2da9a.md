## Title
Webhook `shop_domain` is not bound to the HMAC-verified payload, allowing cross-shop webhook forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates only that the raw request body matches an HMAC computed with the app's shared client secret, but it never verifies that the `X-Shopify-Shop-Domain` header used to attribute the webhook to a specific shop is actually bound to that signed payload. This mirrors the reported `CredibleAccountModule` flaw: a signature/hash is checked, but the "identity" field it's supposed to authorize (`op.sender` there, `shop_domain` here) is taken from unrelated, unverified input and never cross-checked against what was signed.

### Finding Description
`PayloadVerification#hmac_valid?` computes an HMAC over `request.raw_post` using `ShopifyApp.configuration.secret` (the app's single client secret, shared across every shop that installs the app) and compares it to the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`WebhookVerification#verify_request` only calls this body-HMAC check as a `before_action`, and separately exposes `shop_domain`, which is read directly from an unauthenticated header with no relation to the HMAC computation: [2](#0-1) 

The officially documented pattern for custom webhook controllers (which developers are told to copy) uses exactly this unverified `shop_domain` to route/attribute the job: [3](#0-2) 

Because the secret used for `hmac_valid?` is the app-wide client secret (not a per-shop secret), *any* body/HMAC pair that was legitimately generated by Shopify for one shop's webhook remains a valid HMAC for that same body regardless of which shop the request claims to be from. Nothing ties the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header — the value that downstream code uses as the trusted tenant identifier — to the signed content. This is the same class of bug as the reported issue: a valid, correctly-verified "hash" (HMAC/`userOpHash`) is accepted, but the accompanying "identity"/"target" data (`shop_domain`/`op.sender`) is never checked to actually correspond to that verified hash, so an attacker can supply mismatched identity data alongside a legitimately-signed payload.

### Impact Explanation
A merchant who has legitimately installed the app (an "unrelated merchant" from the perspective of any other tenant) receives real, correctly-HMAC-signed webhooks from Shopify for events in their own store. They can capture a `(body, X-Shopify-Hmac-Sha256)` pair and replay it to the app's webhook endpoint while spoofing `X-Shopify-Shop-Domain` to name a different, victim shop. `hmac_valid?` still passes (it never inspects the shop header), so the request is accepted and processed as if it were authentic data for the victim shop — leading to cross-shop data injection/corruption in any app built on the documented `shop_domain:`-keyed job pattern (e.g., orders, products, customers being attributed to the wrong tenant). This is a cross-shop trust boundary bypass, matching "cross-shop or cross-user access" / "accepted forged signed request."

### Likelihood Explanation
Any user of the app who can install it on a shop can obtain valid signed webhook bodies for that shop and only needs to change one HTTP header to target another shop; no secret, cryptography breakage, or privileged access is required, making this straightforward to exploit for any app that follows the gem's own documented webhook controller pattern.

### Recommendation
Do not treat `shop_domain` (or any other header/param outside the signed payload) as trusted just because `hmac_valid?` passed. Either:
- Include the shop domain in the HMAC-covered material (e.g., verify it against a shop-scoped secret, or require the shop domain be embedded in and derived from the signed payload itself), or
- Cross-check that the shop named in the request actually has an active, verified session/installation matching the claimed identity before attributing any processed data to it, analogous to enforcing `op.sender == msg.sender` in the referenced report.

### Proof of Concept
1. Legitimately install the app on shop `attacker.myshopify.com`; trigger a real webhook (e.g. `orders/create`) and capture the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify using the app's shared client secret).
2. Send a POST to the app's custom webhook endpoint (built per `docs/shopify_app/webhooks.md`'s example using `ShopifyApp::WebhookVerification`) with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` → `hmac_valid?(B)` succeeds because the same shared secret and body are used; the action executes `SomeJob.perform_later(shop_domain: "victim-shop.myshopify.com", webhook: B)`, injecting attacker-controlled data under the victim shop's identity.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
