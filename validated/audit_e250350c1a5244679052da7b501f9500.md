## Analysis

The Hats Protocol bug is a **reentrancy-driven state-desync**: a snapshot value (`_existingModulesHash`) captured before an operation gets silently overwritten by a nested/reentrant call, so the post-check compares against the wrong baseline and a dangerous invariant (no new modules) is bypassed.

Cosmos EVM has a structurally identical construct in the precompile `BalanceHandler`, and the codebase itself already contains a dedicated regression test acknowledging it as a bug.

### Title
Nested/Reentrant Precompile Calls Cause Double-Application of Bank Balance Events in `BalanceHandler`, Desyncing EVM StateDB from Bank Module Balances - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler.BeforeBalanceChange` snapshots the current length of `ctx.EventManager().Events()` into `prevEventsLen`, and `AfterBalanceChange` replays every event *after* that index to mirror bank-module balance changes into the EVM `StateDB` [1](#0-0) . When a precompile's native action triggers a **nested precompile call** (reentrancy into another/the same precompile via `CallEVM`/self-call), the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` pair consumes and applies the events generated during the inner call. However, because the outer call's `prevEventsLen` was captured *before* the nested call started, the outer `AfterBalanceChange` — invoked after the nested call returns — re-slices the event log from the same starting point and **reprocesses the events that the inner handler already applied**, double-crediting/debiting `StateDB` balances for the same underlying bank operation.

### Finding Description
`runNativeAction` calls `balanceHandler.BeforeBalanceChange(ctx)` before invoking `action(ctx)`, then `balanceHandler.AfterBalanceChange(ctx, stateDB)` afterward [2](#0-1) . `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` and applies `stateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived`/fractional-balance event found in that window [3](#0-2) .

If a precompile's native action itself triggers another EVM-visible precompile invocation (e.g., a contract calling a precompile whose native logic internally performs an EVM call back into a precompile, or a contract making back-to-back/nested calls to precompiles within the same outer call frame while sharing the same underlying `ctx.EventManager()`), the inner invocation's own `BeforeBalanceChange`/`AfterBalanceChange` cycle runs to completion first and applies its slice of events to `StateDB`. The **outer** handler's `prevEventsLen` was fixed *before* the inner call ran, so when the outer handler later executes, its slice `events[prevEventsLenOuter:]` still contains the inner call's events — which were already applied to `StateDB` by the inner handler — causing them to be applied a second time.

This exact mechanism is already reproduced and documented in-repo by a dedicated integration test: `TestRecursivePrecompileCallsWithDebugPrecompile`, whose docstring states the test "demonstrates the balance handler bug by triggering recursive calls that share the same BalanceHandler instance ... leads to balance desync between native bank keeper and EVM stateDB" [4](#0-3) .

### Impact Explanation
If reachable via a production precompile whose native action can trigger nested balance-changing calls (distribution reward withdrawal invoking nested staking calls, ERC20 precompile `transferFrom` composed with further internal calls, ICS20 transfer combined with bank calls, etc.), this causes `StateDB` balances to diverge from actual bank-keeper balances — an unauthorized duplication of spendable value in the EVM-visible balance state (the target account's on-chain, contract-visible balance becomes larger than what the bank module actually holds for it). Since `StateDB` balances directly back subsequent transfers/calls within the same EVM execution, this is a form of unauthorized balance duplication/inflation, matching the "Critical unauthorized minting/duplication ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets" impact category.

### Likelihood Explanation
The precompile framework's `RunNativeAction` currently instantiates a fresh `BalanceHandler` per top-level `Run()` invocation via `BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) , so the double-application only manifests when a *single* `Run()`'s native action itself synchronously drives further balance-changing native actions sharing the same `ctx` event stream before its own `AfterBalanceChange` executes. I was unable to fully confirm, within the available indexed code, a production (non-test) precompile whose native action path performs such a nested/recursive call into another balance-changing precompile execution using the shared context — the only concretely demonstrated trigger in the codebase is the test-only `debugprecompile` used in `TestRecursivePrecompileCallsWithDebugPrecompile`. That debug precompile is registered only in test setup (`RegisterStaticPrecompile`/`EnableStaticPrecompiles` calls inside the test) [6](#0-5)  and is not part of the default production precompile set, so it does not itself constitute an unprivileged production-reachable Critical bug. Confirming reachability from an unprivileged EVM transaction through a real, always-enabled precompile (staking/distribution/gov/erc20/ics20/slashing) would require deeper tracing of each precompile's native action for internal nested `CallEVM`/precompile invocation, which was not completed within the available index.

### Recommendation
Given the uncertainty about production reachability, this should be treated as a confirmed logic defect worth hardening regardless: make `prevEventsLen` re-synchronize or use a monotonically-consistent mechanism (e.g., track a global "last processed event index" on the `StateDB`/journal rather than a per-call local snapshot, or have nested calls consume/truncate the event slice so outer handlers never see already-applied events) so that nested balance-changing precompile executions cannot cause double-application of bank events into `StateDB`.

### Proof of Concept
The existing test `TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go` [7](#0-6)  already reproduces the mechanics: a contract (`DebugPrecompileCaller`) recursively calls a precompile that emits balance-changing events, and the test asserts on event counts consistent with the "balance handler bug" description. Because this reproduction currently only exists against the test-only debug precompile, I could not independently verify from the indexed code that an unprivileged user can trigger the same double-application through a production, always-registered precompile — this reachability gap should be validated by tracing native-action call graphs of the production precompiles (staking, distribution, gov, erc20, ics20, slashing) for any internal nested precompile/EVM call under `RunNativeAction`.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
