### Title
Cross-transaction stale liquidity/borrow index cache leads to mispriced zTokens and incorrect debt/health valuation - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s `index-cache` map is keyed only by `{ timestamp: stacks-block-time, aid: aid }`, not by transaction. Since `stacks-block-time` is identical for every transaction mined in the same block, `accrue-and-cache` will return a *cache hit* — and thus a stale `index`/`lindex` — to any later transaction in that block, even though an earlier transaction in the same block may have already mutated the real vault indexes (via deposit/borrow/repay/redeem). This is the same root-cause pattern as the reported `tallyPledgesToday` bug: a value meant to be scoped/reset per unit-of-work (there: per day, here: per transaction) is instead allowed to persist across units of work, silently corrupting downstream computations — here, the price of zTokens (`resolve-ztoken`) and the debt notional used for collateral/LTV health checks.

### Finding Description
`accrue-and-cache` is the single choke point through which the market fetches vault `index`/`lindex` for both:
- zToken price resolution (`resolve-ztoken`, used inside `resolve-callcode` for `CALLCODE-ZSTX/ZSBTC/ZSTSTX/ZUSDC/ZUSDH/ZSTSTXBTC`), and
- debt notional valuation (`calculate-asset-notional-value`, used by `get-notional-evaluation` for health/LTV checks). [1](#0-0) 

The cache key intentionally omits any transaction/nonce identifier and relies solely on `stacks-block-time`: [2](#0-1) 

Documentation confirms the cache is meant only to avoid redundant vault calls *within* a single call, but the implementation actually spans the whole block: [3](#0-2) 

The developers were themselves aware that vault indexes can change mid-flow and require a cache refresh — they explicitly re-populate `index-cache` after `socialize-debt-asset` because "lindex decreased": [4](#0-3) 

However, this manual refresh is applied only to the liquidation/socialization path. Ordinary `deposit`, `redeem`, `borrow`, and `repay` calls on the vault contracts (`vault-stx.clar`, `vault-ststx.clar`, etc.) mutate `index`/`lindex` directly inside the vault without any corresponding `map-set index-cache` call from the market. If transaction A in block N calls `market.borrow`/`collateral-add`/etc. and this causes `accrue-and-cache` to populate the cache for asset `aid` with the pre-mutation `{index, lindex}`, and then a *different* vault operation later in the same block changes the vault's real state (e.g. another user deposits or a liquidation/borrow accrues additional interest through direct vault interaction), a subsequent transaction B in that same block reading the market's collateral/debt/health path will hit `map-get? index-cache {timestamp: stacks-block-time, aid}` and receive transaction A's stale indexes rather than the vault's current state: [5](#0-4) 

That stale `lindex` flows straight into `resolve-ztoken`, corrupting the price used for that zToken as collateral: [6](#0-5) 

and the stale `index` flows into debt notional computation used for the LTV/health check: [7](#0-6) 

### Impact Explanation
Because the cache-hit path silently substitutes an out-of-date liquidity/borrow index for the correct one, the protocol can compute:
- an **undervalued** zToken collateral price (if the real `lindex` grew between the caching transaction and the reading transaction), which can wrongly report a position as unhealthy/undercollateralized and trigger unwarranted liquidation, or
- an **overvalued** zToken collateral price/an **undervalued** debt notional (if the cached value is stale in the other direction), letting a borrower's position pass the health check and borrow/withdraw more than their real collateral supports.

Either direction lands on a wrong health verdict, which can permit borrowing beyond actual collateral backing (temporary/permanent freezing of other users' funds in the vault) or trigger incorrect liquidations (theft of collateral from a healthy position). This satisfies the required in-scope impact class (temporary/permanent freezing of funds via a wrong health verdict / mispriced collateral) and is directly analogous to the reported bug class: a value that must be re-derived per unit-of-work is instead persisted and reused across units-of-work it should not span.

### Likelihood Explanation
Multiple transactions touching the same vault asset within a single block is a routine occurrence in a live lending protocol (deposits, borrows, repayments, liquidations from different users all interacting with the same handful of vaults). No malicious coordination beyond ordinary usage/mempool ordering is required to trigger the stale read — this is a systemic correctness bug in the caching layer rather than a rare edge case, though its exploitability for profit depends on the direction and magnitude of the index drift within a single block, which is generally small under normal interest-rate parameters but can be significant after a socialization/large liquidation event that is not immediately followed by another cache-consuming call in the same transaction.

### Recommendation
Do not key the index cache purely on `stacks-block-time`; either invalidate/refresh the cache at the start of every vault-mutating public entrypoint (deposit/redeem/borrow/repay), or remove the block-scoped cache entirely and always call `vault-accrue` fresh for indexes consumed by price/health computations. At minimum, every operation in `market.clar` (and the corresponding vault contracts) that changes vault `index`/`lindex` must perform the same `map-set index-cache` refresh that `socialize-debt-asset` already performs, ensuring later transactions in the same block cannot observe stale indexes.

### Proof of Concept
1. In block N, transaction A calls a vault-mutating market entrypoint for asset `aid` (e.g., `borrow` or `collateral-add`) that internally calls `accrue-and-cache(aid)`; this populates `index-cache {timestamp: T, aid}` with the vault's current `{index, lindex}`.
2. Still within block N, a separate operation changes the same vault's real `index`/`lindex` (e.g., a liquidation via `socialize-debt-asset` refreshes the cache for a *different* code path, or, absent such refresh, an ordinary interest accrual/deposit elsewhere changes vault state without updating `index-cache`).
3. Transaction B, also in block N, calls a market entrypoint that needs the price or debt notional of `aid` (e.g., `collateral-add` for a zToken, or a health check via `get-notional-evaluation`). `accrue-and-cache(aid)` hits the cache from step 1 and returns the pre-mutation `{index, lindex}` instead of the vault's actual current values.
4. `resolve-ztoken`/`calculate-asset-notional-value` compute a zToken price or debt notional using the stale index, producing an incorrect collateral valuation or debt valuation for transaction B's health check — either wrongly passing an unhealthy position or wrongly failing a healthy one.

Note: I was not able to fully trace whether every vault-mutating public function in every vault contract (`vault-stx.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststxbtc.clar`) omits an `index-cache` refresh in market.clar besides the one explicit refresh found in `socialize-debt-asset`; confirming the full set of code paths that mutate vault indexes without refreshing the market's cache would require a deeper cross-contract trace than the available index coverage allowed.

## Index Caching

The market maintains a timestamp-based cache for vault liquidity indexes to optimize ztoken price resolution:

```clarity
;; In market.clar
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

**Purpose:** 
- Multiple price resolutions for the same vault within a single block use cached indexes
- Avoids redundant cross-contract calls to vaults
- Significantly reduces gas costs for transactions involving multiple ztoken prices

**Cache Invalidation:** Cache is timestamp-based using `stacks-block-time`, automatically invalidating when a new block is processed.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
