### Title
`ThresholdKeys::read`/`new` never verifies the secret share corresponds to its verification share, and accepts identity verification shares — attacker-controlled key material defines a group key with known discrete log - (File: crypto/dkg/src/lib.rs)

### Summary
The XWiki bug class — a security analysis that enumerates some properties while silently skipping an unhandled/default kind — maps onto `ThresholdKeys` deserialization in `crypto/dkg`. `ThresholdKeys::read` reconstructs `(t, n, i)`, the interpolation method, `secret_share`, and all `verification_shares` from raw bytes, then `ThresholdKeys::new` derives `group_key` solely by interpolating the attacker-supplied verification shares. No check binds `secret_share` to `verification_shares[i]`, no check rejects the identity point for verification shares (the read uses `Ciphersuite::read_G`, not the identity-rejecting `Curve::read_G`), and nothing proves the loaded key was produced by a real DKG. Any consumer that loads `ThresholdKeys` from untrusted bytes gets a well-formed-looking key whose group key's discrete logarithm the attacker fully controls.

### Finding Description
`ThresholdKeys::<C>::read` (crypto/dkg/src/lib.rs, lines 574-632) parses `t`, `n`, `i`, an interpolation selector, one scalar `secret_share`, and `n` group elements via `<C as Ciphersuite>::read_G` — the base `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs, lines 91-101) enforces canonicality only; it does not reject the identity point (that check exists only in `frost::Curve::read_G`, crypto/frost/src/curve/mod.rs lines 125-131).

`ThresholdKeys::new` (crypto/dkg/src/lib.rs, lines 349-391) then:
- checks `verification_shares.len() == n` and that no participant index exceeds `n`,
- checks `t == n` only for `Interpolation::Constant`,
- computes `group_key = Σ_{i ∈ 1..=t} verification_shares[i] · interpolation_factor(i, [1..=t])`,

and returns `Ok` without ever verifying that `C::generator() * secret_share == verification_shares[params.i()]`, i.e., that the holder actually possesses a share consistent with the shares committed to. The verification-share values are entirely attacker-chosen: the serializer (`write`) emits raw `to_bytes()` of each share, and `read` accepts any canonical point — including identity or points whose discrete logs are known.

This is exactly the XWiki shape: the "analysis" (`new`'s consistency validation) enumerates structural properties (count, index range, interpolation applicability) while never considering the one property that matters — correspondence between the supplied secret share and the group key.

### Impact Explanation
An attacker who can supply serialized `ThresholdKeys` bytes to a participant (the prompt's allowed untrusted-bytes surface for `ThresholdKeys::read`) produces a key set where:

- Every verification share is `k_j · G` for attacker-known `k_j`, so `group_key`'s discrete log is `Σ λ_j k_j` — fully known to the attacker. Any funds, deposits, or protocol authority routed to that group key (e.g., a Bitcoin `Scanner` built on `keys.group_key()`, or a MuSig/FROST session keyed on it) are spendable solely by the attacker, while the victim believes they hold a threshold share of a jointly-generated key.
- The victim's `secret_share` is attacker-chosen, so the victim's signature shares verify correctly under `view()`/`verify_share` (the per-participant verification share was set to `secret_share·G` by the attacker if they want cooperation, or anything else if they don't). The victim can even produce valid shares for signatures the attacker could have produced alone — the "threshold" is pure theater.

This is "concrete signing of an unintended message / funds reported received that are not spendable (by the group)": any output credited to the attacker's known-dlog group key is reported as received by scanners/`ReceivedOutput` consumers but is not controlled by the honest threshold set.

### Likelihood Explanation
Medium. Exploitation requires an attacker to get crafted `ThresholdKeys` bytes loaded by a participant — a realistic channel wherever key material is imported, restored, or provided by an external party/coordinator rather than locally generated by `dkg_dealer`/`pedpop`. The deserialization API is explicitly public (`pub fn read`) and used for exactly such import flows (cf. `vectors_to_multisig_keys` in crypto/frost/src/tests/vectors.rs). Once loaded, no downstream check (`view`, `group_key`, FROST `sign`) re-derives consistency — the poisoned key is used verbatim.

### Recommendation
In `ThresholdKeys::new` (and transitively `read`), additionally verify:
- `verification_shares[l]` is non-identity for all `l` (or use the stricter reader).
- `C::generator() * secret_share == verification_shares[&params.i()]` — the share holder actually holds the committed share.
- For `Interpolation::Constant`, verify `vec.len() == n` explicitly rather than relying on indexing.

Ideally, derived `group_key` consistency should be proven cryptographically at import time rather than recomputed from attacker-supplied shares.

### Proof of Concept
```rust
// Attacker crafts a ThresholdKeys<Secp256k1> blob: t = n = 2, i = 1, Lagrange.
let mut blob = vec![];
blob.extend(4u32.to_le_bytes());                  // len("secp256k1") per C::ID
blob.extend(Secp256k1::ID);
blob.extend(2u16.to_le_bytes());                  // t
blob.extend(2u16.to_le_bytes());                  // n
blob.extend(1u16.to_le_bytes());                  // i = Participant(1)
blob.push(1);                                     // Interpolation::Lagrange

// secret_share the victim will hold (attacker-chosen, e.g. 1)
blob.extend(Scalar::ONE.to_repr());

// verification shares with attacker-known discrete logs
let k1 = Scalar::from(0x1111u64);
let k2 = Scalar::from(0x2222u64);
blob.extend((ProjectivePoint::GENERATOR * k1).to_bytes()); // share for participant 1
blob.extend((ProjectivePoint::GENERATOR * k2).to_bytes()); // share for participant 2

let keys = ThresholdKeys::<Secp256k1>::read(&mut blob.as_slice()).unwrap();
// SUCCEEDS despite secret_share(=1)·G != verification_shares[1]

// group_key = λ1·k1·G + λ2·k2·G for Lagrange λ over {1,2}:
// λ1 = 2·(2-1)^-1 = 2, λ2 = 1·(1-2)^-1 = -1
// => group key discrete log = 2·k1 - k2, known to the attacker.
// The victim loads keys, and any funds sent to keys.group_key()
// are spendable only by the attacker.
```

Note: I verified `read` and `new` directly; the `interpolation_factor` implementations and `ThresholdParams::new` internals were not fully re-inspected in this pass, but neither performs a `secret_share ↔ verification_share` binding check (that mapping lives only where shares are generated, not where they are imported).
