### Title
Panic via crafted `Participant` identifiers in PedPoP blame evaluation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG's public blame-evaluation APIs (`BlameMachine::blame` / `AdditionalBlameMachine::blame`) accept caller-supplied `sender` and `recipient`/`decryptor` `Participant` values and use them to directly index `HashMap`s (`self.enc_keys[...]` and `self.commitments[...]`) with no membership check. `Participant` only enforces non-zero (any `u16` up to 65535 is valid), while `enc_keys`/`commitments` only contain indexes `1..=n`. This is the analog of the CKAN "crafted resource id" class: an attacker-controlled identifier is used as an unchecked lookup key, causing a panic (abort of the process evaluating blame) rather than a graceful error.

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys only for `i in 1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`), and `BlameMachine` similarly only has `enc_keys`/`commitments` for real participants. However:

- `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` unconditionally when `proof` is `Some`, before any DLEq verification (`crypto/dkg/pedpop/src/encryption.rs:388`).
- `blame_internal` evaluates `self.commitments[&sender]` when checking share validity (`crypto/dkg/pedpop/src/lib.rs:599`).

The PoP signature check that precedes the index is satisfiable by an attacker: `pop_challenge` binds the claimed `sender` id into the transcript, but `SchnorrSignature::sign` only requires knowledge of the ephemeral key `K` — the `sender` field is not authenticated against anything. An attacker can therefore produce an `EncryptedMessage` whose `pop` verifies for `from = Participant(1)` (or any value), then invoke `blame`/`decrypt_with_proof` with `recipient = Participant(9999)` — an id that was never registered — triggering a `HashMap` index panic in `no_std`-free code (`HashMap::index` panics on missing key).

### Impact Explanation
Any party that can submit a blame accusation (including the explicitly supported non-member caller of `AdditionalBlameMachine`) can crash the evaluating process/node by supplying a `recipient`/`decryptor` index outside `1..=n`, or a `sender` not present in `commitments`. This aborts DKG fault attribution and can take down the validator/coordinator evaluating the blame — a denial of service reachable purely through crafted identifiers fed to a public API.

### Likelihood Explanation
`blame` is the designated entry point for fault accusations and is documented as usable by non-participants, so untrusted `Participant` values are expected input. No check that `sender <= n` or `recipient <= n` exists anywhere on this path; `Participant::new` accepts any non-zero `u16`. Exploitation requires only forging a self-generated `pop` signature, which is trivial.

### Recommendation
Validate that `sender` and `recipient`/`decryptor` are present in the `commitments`/`enc_keys` maps (or `<= n`) before indexing in `decrypt_with_proof` and `blame_internal`, returning a `DecryptionError`/`PedPoPError` or a defined blame result instead of panicking. Use `.get()` rather than `[]` indexing for attacker-controlled keys.

### Proof of Concept
```rust
// After a DKG with n participants, build the blame evaluator:
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage bound to sender=Participant(1):
let key = Zeroizing::new(C::random_nonzero_F(rng));
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(rng));
let msg = EncryptedMessage { /* key: pub_key, pop: SchnorrSignature::sign(
       &key, nonce, pop_challenge(context, pub_nonce, pub_key, Participant(1), &share_bytes)) ... */ };

// Call blame with an out-of-range recipient (any u16 > n):
machine.blame(
  Participant::new(1).unwrap(),      // sender: real participant
  Participant::new(9999).unwrap(),   // recipient/decryptor: never registered
  msg,
  Some(attacker_proof),              // any EncryptionKeyProof; index panics before verify
);
// `self.enc_keys[&decryptor]` at encryption.rs:388 -> index panic -> abort
```
