### Title
Malicious preprocess forces aggregate nonce `R` to the point at infinity, panicking every honest signer inside `Hram::hram`/`x_only` — (File: networks/bitcoin/src/crypto.rs)

### Summary
The Xen bug class is denial of service caused by mishandled error paths that stall CPU progress. The Serai analog is a signer-reachable panic: the Bitcoin BIP-340 `Hram` unconditionally calls `x(R)`, which `expect`s `R` to be non-infinity. A participant in a FROST signing session controls its own preprocess nonce commitment and can choose it so the aggregate `nonce_sums[0][0]` equals `G::identity()`, causing `hram` — called from `Schnorr::sign_share` — to panic on every honest participant. [1](#0-0) [2](#0-1) 

### Finding Description
`x()` extracts the x-coordinate of a `ProjectivePoint` and panics when the point is at infinity: `(*encoded.x().expect("point at infinity"))`. `x_only` and `needs_negation` have the same assumption. `Hram::hram` calls `x(R)` and `needs_negation(R)` with no identity check. [3](#0-2) 

In `crypto/frost/src/algorithm.rs`, `Schnorr::sign_share` computes `let c = H::hram(&nonce_sums[0][0], &params.group_key(), msg)`, where `nonce_sums[0][0]` is the sum of all participants' nonce commitments (the aggregate `R`). Each participant's commitment comes from their preprocess message, deserialized via `C::read_G` / `read_preprocess` — i.e., attacker-controlled bytes. There is no rejection of a commitment that makes the aggregate nonce sum to identity; per-participant identity may be filtered by `read_G`, but the *sum* is never checked. [4](#0-3) 

The comment on `crypto.rs`'s `Schnorr` algorithm acknowledges the panic but claims it has "a negligible probability for a well-reasoned caller, even with malicious participants present". That is wrong: a malicious signer who transmits its preprocess last (or observes others' preprocesses, as ROS-style/parallel-session scheduling permits) computes its commitment as `D_i = -(Σ_{j≠i} D_j)`, forcing `R = identity` deterministically, not probabilistically. [5](#0-4) 

### Impact Explanation
Every honest participant that processes the crafted preprocess set calls `sign_share` → `hram` → `x(R)` and panics. The panic kills the signing task / processor thread handling the sign session, aborting the signature and — depending on the executor — repeatedly crashing the processor, permanently denying signing service for that multisig session. This is a remotely triggerable, deterministic denial of service by an unprivileged signing participant using only public preprocess bytes, matching the Medium-severity DoS class of the reference advisory.

### Likelihood Explanation
Requires only that the attacker be a FROST participant able to supply a preprocess (`Commitments`/`read_G` input) and order its message after seeing the other commitments — a standard assumption for threshold-signing adversaries and explicitly within scope (untrusted bytes to `read_preprocess`/`read_G` and `sign`/`complete` APIs). No collusion, leaked keys, or broken BFT needed.

### Recommendation
Check for the point at infinity on the aggregate `R` before invoking `Hram::hram` in `sign_share` and before `SchnorrSignature::verify`/serialization, returning a `FrostError`/`Option::None` rather than panicking. Alternatively, reject preprocess commitments that make `nonce_sums` contain the identity when assembling `nonce_sums` in `crypto/frost/src/sign.rs`, and make `x`/`x_only`/`hram` total (return `Option`) instead of `expect`ing non-infinity. [6](#0-5) 

### Proof of Concept
```
// Attacker is participant i in a Bitcoin Schnorr (Hram) FROST sign session.
// 1. Collect all other participants' nonce commitments D_j (public preprocess messages).
// 2. Publish own commitment D_i = -(sum of D_j)  // a valid non-identity point, passes read_G
// 3. Every honest signer computes nonce_sums[0][0] = sum(D_j) + D_i = identity
// 4. Schnorr::sign_share -> Hram::hram(&nonce_sums[0][0], ...) -> x(R)
//    -> encoded.x().expect("point at infinity") -> panic!
// Signing session aborts on all honest nodes; signature is never produced.
```

  fn sign_share(
    &mut self,
    params: &ThresholdView<C>,
    nonce_sums: &[Vec<C::G>],
    mut nonces: Vec<Zeroizing<C::F>>,
    msg: &[u8],
  ) -> C::F {
    let c = H::hram(&nonce_sums[0][0], &params.group_key(), msg);
    self.c = Some(c);
    SchnorrSignature::<C>::sign(params.secret_share(), nonces.swap_remove(0), c).s
  }

  #[must_use]
  fn verify(&self, group_key: C::G, nonces: &[Vec<C::G>], sum: C::F) -> Option<Self::Signature> {
    let sig = SchnorrSignature { R: nonces[0][0], s: sum };
    Some(sig).filter(|sig| sig.verify(group_key, self.c.unwrap()))
  }

  fn verify_share(

      SchnorrSignature::<C> { R: nonces[0][0], s: share }
