### Title
Out-of-range participant index in a blame accusation panics every evaluating node via unguarded `HashMap` indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the quic-go HANDSHAKE_DONE assertion (CVE-2025-59530), where an unauthenticated message triggers an `assert!`/panic, Serai's PedPoP DKG blame path performs unguarded `HashMap` indexing on attacker-chosen `Participant` indexes. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` evaluates `self.commitments[&sender]` without checking that the supplied `sender`/`recipient` indexes are within `1..=n`. Any party able to submit a blame accusation (which `AdditionalBlameMachine` explicitly supports for non-participants) can crash every node evaluating the accusation.

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys and commitments only for `Participant::new(1 ..= n)` in `crypto/dkg/pedpop/src/lib.rs:656-660`. `Participant` is a non-zero `u16`, so indexes `n+1 ..= 65535` are representable but never inserted into either map.

When a blame accusation is evaluated:

1. `BlameMachine::blame` / `AdditionalBlameMachine::blame` pass the caller-supplied `sender` and `recipient` straight into `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:574-588, 674-682`) with no range check.
2. `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` (`crypto/dkg/pedpop/src/lib.rs:582`).
3. Inside `decrypt_with_proof`, after the PoP signature check passes, `self.enc_keys[&decryptor]` is indexed (`crypto/dkg/pedpop/src/encryption.rs:388`). For any `recipient` not in `1..=n`, `HashMap` indexing panics.
4. Even if `proof` is `None` (or the panic above is avoided), `blame_internal` later indexes `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`), which panics for any `sender` not in `1..=n` once the share decodes to a canonical scalar — trivially achievable since `msg` is attacker-controlled ciphertext and `EncryptedMessage::read`/`SecretShare::read` accept arbitrary bytes (`crypto/dkg/pedpop/src/lib.rs:264-268`).

Note that for the `recipient`-side panic, the accuser only needs a message whose Schnorr PoP verifies under `from = sender` — i.e., any legitimately authenticated secret-share message copied from the transcript, exactly what `blame` is documented to accept (`crypto/dkg/pedpop/src/lib.rs:615-617`).

### Impact Explanation
A single blame accusation referencing a `Participant` index outside `1..=n` causes an unconditional panic (`HashMap` index on missing key) in `decrypt_with_proof` or `blame_internal`. Since blame accusations are broadcast for all parties — including non-member observers via `AdditionalBlameMachine`, whose constructor exists specifically to let non-participants evaluate blame — every honest node evaluating the accusation crashes. This is an unauthenticated-reachability denial of service on the DKG/blame-evaluation path, matching the quic-go bug class of an assertion/panic reachable by a misbehaving peer with no authentication or valid handshake state required beyond supplying well-formed protocol bytes.

### Likelihood Explanation
Firing the panic requires only that a node call `blame` with a `sender` or `recipient` value of `n+1` or greater. `Participant::new` accepts any non-zero `u16`, and neither `blame`, `blame_internal`, nor `decrypt_with_proof` validates the indexes against the protocol's participant set. The accompanying `msg` can be a verbatim copy of any real `EncryptedMessage` (authenticated channel already guarantees availability), and `proof` can be `None` for the `commitments[&sender]` path. No threshold cooperation, key knowledge, or malformed cryptography is needed — just an out-of-range index in the accusation metadata.

### Recommendation
Validate `sender` and `recipient` in `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal` against the registered participant set (`1..=n`, i.e., membership in `self.commitments`/`enc_keys`) before any map access, returning the accusing party (or an explicit error) when out of range. Replace `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`) and `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) with `.get()` lookups that map missing keys to a blame/error result rather than panicking.

### Proof of Concept
```rust
// Setup: 2-of-3 PedPoP DKG completes; each honest node holds a
// BlameMachine, and an observer holds an AdditionalBlameMachine built
// via AdditionalBlameMachine::new(context, 3, commitment_msgs).

// Attacker (any party who can submit a blame accusation) takes ANY real
// EncryptedMessage<C, SecretShare<C::F>> previously sent by participant 1
// to participant 2 (msg), plus that recipient's EncryptionKeyProof (proof),
// and submits an accusation with an out-of-range recipient:

let bogus = Participant::new(4).unwrap(); // n == 3, but Participant allows any non-zero u16

// On every evaluating node:
// AdditionalBlameMachine::blame(sender=1, recipient=bogus, msg, Some(proof))
//   -> blame_internal -> decrypt_with_proof
//   -> self.enc_keys[&bogus]  // PANIC: key not present (only 1..=3 registered)
observer_blame_machine.blame(p1, bogus, msg.clone(), Some(proof.clone()));

// Variant reaching the second panic site:
// blame(sender=bogus, recipient=2, msg, None)
//   -> decrypt_with_proof returns Err(InvalidProof) -> recipient ... 
//   or with a forged-decryptable msg: self.commitments[&bogus] // PANIC
participant_blame_machine.blame(bogus, p2, msg, None);
```

Both calls panic on unguarded `HashMap` indexing inside in-scope production code (`crypto/dkg/pedpop/src/encryption.rs`, `crypto/dkg/pedpop/src/lib.rs`), crashing the evaluating process — a DoS directly analogous to the quic-go assertion crash, reachable with only publicly observable protocol messages and an out-of-range index the accuser controls.
