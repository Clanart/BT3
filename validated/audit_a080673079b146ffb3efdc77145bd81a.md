Confirmed vulnerability: `get_payout_txs_for_withdrawal_utxos` at `core/src/database/verifier.rs:170-196` joins `withdrawals` to `bitcoin_syncer_spent_utxos` **purely on `withdrawal_utxo_txid`/`withdrawal_utxo_vout`**, with no `deposit_id`/`move_to_vault_txid` disambiguation, and no on-chain check that the spending transaction actually consumed *this* deposit's `MoveToVaultTx` output.

### Title
Payout matching keyed only on withdrawal outpoint lets an aliased deposit_id be marked paid and reimbursed without its vault ever being spent - (File: core/src/database/verifier.rs)

### Summary
`update_payout_txs_and_payer_operator_xonly_pk` populates `withdrawals.payout_txid`/`payout_tx_blockhash` for every `idx` whose `withdrawal_utxo_txid`/`withdrawal_utxo_vout` matches a spent UTXO detected by the syncer, joining solely on the outpoint bytes rather than the deposit-specific move-to-vault txid. Because an attacker fully controls the withdrawal UTXO bytes it registers on the Citrea bridge contract for each `deposit_id`, it can register the identical outpoint for two different deposits (e.g. 5 and 9). Once deposit 5's optimistic-payout (or operator payout) tx spends that shared outpoint, the join in `get_payout_txs_for_withdrawal_utxos` matches it against deposit 9's row too, and `update_payout_txs_and_payer_operator_xonly_pk` stamps deposit 9 with the same `payout_txid`/`payout_tx_blockhash`/payer key — even though deposit 9's own `MoveToVaultTx` `DepositInMove` output was never touched.

### Finding Description
The claimed binding is: `payout_txid(deposit_id) == txid of the transaction that spends deposit_id's own move-to-vault-linked withdrawal, and that transaction's second input consumes move_to_vault_txid(deposit_id)`.

Trace:
- `Verifier::update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2204+`) calls `update_withdrawal_utxo_from_citrea_withdrawal` per `idx` with whatever outpoint Citrea reports for that withdrawal id — these bytes are attacker-controlled via the `withdraw()` call on the Citrea bridge contract (per the threat model, the attacker can "choose the bytes of a withdrawal UTXO").
- Nothing in `update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:108-135`) enforces uniqueness of `(withdrawal_utxo_txid, withdrawal_utxo_vout)` across different `idx` rows.
- `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) finds "spent" withdrawal rows by joining `withdrawals.withdrawal_utxo_txid/vout` to `bitcoin_syncer_spent_utxos` **only** — no check against `move_to_vault_txid`, no check that the spending tx's *second* input is `move_to_vault_txid(idx)`'s `DepositInMove` output.
- Whatever caller consumes this result (presumably in `update_citrea_deposit_and_withdrawals` or a follow-up sync step) then calls `update_payout_txs_and_payer_operator_xonly_pk`, which will set `payout_txid`/`payout_tx_blockhash`/`payout_payer_operator_xonly_pk` for **every** `idx` that shares the outpoint, including deposit 9, from the single transaction that only actually paid out deposit 5.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs`) then picks up deposit 9 via `get_first_unhandled_payout_by_operator_xonly_pk` (matches on `payout_txid IS NOT NULL AND is_payout_handled = FALSE AND payout_payer_operator_xonly_pk = self`), fetches `deposit_data` for deposit 9's own `move_to_vault_txid`, and calls `operator.handle_finalized_payout(deposit_9_outpoint, payout_tx_blockhash)`, ultimately calling `mark_payout_handled` for deposit 9 with the kickoff txid — putting deposit 9 on the Reimburse path even though deposit 9's vault UTXO (`MoveToVaultTx:DepositInMove` for deposit 9) is untouched and still sitting on-chain.

Why existing guards fail: `Aggregator::optimistic_payout`'s `is_utxo_spent(&input_outpoint)` check and `Verifier::sign_optimistic_payout`'s amount bound (`output_amount > bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`) both operate on the *withdrawal_utxo* outpoint and the *requested* deposit's data at request time — they correctly prevent issuing a *second signature* for the same outpoint once it is spent. But they do nothing to prevent the retrospective, syncer-driven bookkeeping (`get_payout_txs_for_withdrawal_utxos`) from crediting a *different* deposit_id's row as "paid" purely because it shares the outpoint value with an already-spent one. The vulnerability is not in the signing path at all — it's in the payout-detection/accounting path that feeds `PayoutCheckerTask` and, downstream, operator reimbursement eligibility.

### Impact Explanation
Deposit 9's vault (`MoveToVaultTx` `DepositInMove` output) is never spent, yet the DB marks deposit 9 as having a valid `payout_txid`, driving `PayoutCheckerTask` to call `handle_finalized_payout`/`mark_payout_handled` for deposit 9. This unlocks the Kickoff/Reimburse machinery for a deposit whose bridge_amount was never fronted for that specific vault — this is the "operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" class of impact (Critical), because deposit 9's vault remains intact on Bitcoin but the operator's accounting (and potentially the eventual kickoff/reimburse claim, since `handle_finalized_payout` records `deposit_9`'s outpoint as paid) treats it as settled — either freezing deposit 9's real withdrawal forever (its own registered withdrawal can never independently be matched/settled again, since `payout_txid` is already set) or enabling an operator to claim reimbursement for deposit 9 without having spent BTC for it. This is repeatable across any number of aliased deposit_id pairs sharing attacker-chosen outpoint bytes and across operators, since the DB join has no operator- or deposit-scoping beyond the outpoint value.

### Likelihood Explanation
The attacker only needs unprivileged access to the Citrea bridge contract's `withdraw()` entry point, twice, submitting the same outpoint bytes for two different withdrawal indices tied to two different deposits it controls (or even deposits belonging to other users, since the outpoint field is just registered data, not a real spend requirement at registration time). No verifier, operator, or aggregator collusion is required. Cost is limited to the deposit amounts and gas/fees for two `withdraw()` calls and one optimistic-payout (or operator withdraw) request — well within reach of an ordinary user. This is highly likely to be reachable given the code confirms the join has no deposit-scoping.

### Recommendation
Change `get_payout_txs_for_withdrawal_utxos` (and any related payout-matching query) to join/verify per-deposit uniquely: require that the spending transaction's designated input (the one spending `move_to_vault_txid`'s `DepositInMove` output, or equivalently the transaction's OP_RETURN/committed operator key and the `payout_input_index` used by the bridge circuit) actually references *this* deposit's move-to-vault UTXO, not merely a matching withdrawal-outpoint value. Additionally, enforce uniqueness of `(withdrawal_utxo_txid, withdrawal_utxo_vout)` across `idx` at the point `update_withdrawal_utxo_from_citrea_withdrawal` is called (reject/flag duplicate registrations), or reject a Citrea withdrawal registration whose outpoint value already exists for another `idx`.

Test plan:
1. Insert two `deposits`/`withdrawals` rows, idx=5 and idx=9, with distinct `move_to_vault_txid`s but the SAME `withdrawal_utxo_txid`/`withdrawal_utxo_vout` (call `upsert_move_to_vault_txid_from_citrea_deposit` and `update_withdrawal_utxo_from_citrea_withdrawal` twice with identical outpoint).
2. Simulate the syncer detecting a spend of that shared outpoint via `insert_spent_utxo` for a single `payout_txid` (representing deposit 5's real optimistic-payout tx).
3. Call `get_payout_txs_for_withdrawal_utxos` and assert it returns **both** idx=5 and idx=9 mapped to the same `payout_txid` — asserting the broken binding: `payout_txid(9) == payout_txid(5)` even though deposit 9's `move_to_vault_txid` output was never referenced as an input anywhere.
4. Call `update_payout_txs_and_payer_operator_xonly_pk` with both rows, then `get_first_unhandled_payout_by_operator_xonly_pk` and confirm deposit 9 is surfaced as an unhandled payout candidate, and that `PayoutCheckerTask::run_once` would call `handle_finalized_payout`/`mark_payout_handled` for deposit 9 while `is_utxo_spent(MoveToVaultTx_9:DepositInMove)` remains `false` on-chain — proving the equality `output_amount charged against vault(9) == bridge_amount fronted` is violated (deposit 9 is credited as paid with zero BTC moved from vault 9).
