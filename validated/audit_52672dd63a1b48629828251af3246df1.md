This confirms the vulnerability. On the EVM sending side, `HyperFungibleToken.sol`'s `_buildDispatchPost` sets `from: abi.encodePacked(msg.sender)` [1](#0-0) , so `message.from` is always the actual caller's address on the EVM side — but this only holds for the reference `HyperFungibleToken.sol` implementation. Nothing in the substrate-side `on_accept` handler enforces that `message.from` must equal an authenticated signer; the pallet trusts whatever bytes are present in the decoded `Message.from` field of the POST request body, and any ISMP-compliant/malicious peer contract (or any EVM contract registered as a token via `register_token`, including ones an attacker could get approved, or any other module sending to this pallet's well-known `PALLET_ID`) can freely set `from` to arbitrary bytes. Since the only authentication of the request source is `ContractToAsset::<T>::get(source, &from)` matching a configured `(StateMachine, contract address)` pair [2](#0-1) , this only authenticates *which contract* sent the message, not the `from` field's identity/ownership — `from` is separate, attacker-controlled payload data.

### Title
Unsigned `SubstrateCalldata` dispatch allows arbitrary account impersonation for governance-permitted calls - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
In `on_accept`, when the optional `SubstrateCalldata.signature` field is `None`, the pallet dispatches `runtime_call` with `RawOrigin::Signed(origin)` where `origin` is derived directly from the unauthenticated `message.from` bytes, with zero cryptographic proof that the caller controls that account.

### Finding Description
`on_accept` decodes the incoming cross-chain `Message` and, if `message.data` is non-empty, decodes it into a `SubstrateCalldata{ signature, runtime_call }` [3](#0-2) . When `signature` is `Some`, the code verifies an Ed25519/Sr25519/Ecdsa signature over `(nonce, runtime_call)` against the `beneficiary` account before using `beneficiary` as origin [4](#0-3) . However, when `signature` is `None`, the code takes the **else** branch and sets `origin` directly from `message.from` — either converting the last 20 bytes via `T::EvmToSubstrate::convert` (EVM source) or copying 32 raw bytes into an `AccountId` (substrate source) — with no signature check whatsoever [5](#0-4) .

The `runtime_call` is then checked only against `BaseCallFilter::contains` [6](#0-5)  — a generic maintenance-mode/SafeMode filter, not an authorization mechanism — and dispatched with `RawOrigin::Signed(origin.clone()).into()` [7](#0-6) .

Because `message.from` is arbitrary payload data chosen by whoever triggers the send on the source chain, and the pallet's only source authentication is `ContractToAsset::<T>::get(source, &from)` matching the registered token contract address [2](#0-1)  (which authenticates *which contract sent the request*, not the identity embedded in `from`), any account bytes can be placed in `from`. An attacker who can get any message accepted through a registered token bridge (e.g., by using the standard `send`/`_buildDispatchPost` path but supplying a spoofed `from` via a custom or malicious yet registered peer contract, or any future/alternate app contract that doesn't enforce `from == msg.sender`) can cause `runtime_call` to be dispatched as `RawOrigin::Signed(victim_account)` for any `victim_account`, provided `BaseCallFilter` permits that call for signed origins.

This breaks the invariant that dispatchable calls requiring a `Signed` origin (e.g., `pallet_democracy::vote`, `pallet_proxy::add_proxy`, `pallet_staking::bond`/`nominate`) are authorized by the actual key holder — `BaseCallFilter` filters call *types*, not caller *identity*, so it provides no protection against origin spoofing.

Note: the reference `HyperFungibleToken.sol` contract does correctly bind `from = abi.encodePacked(msg.sender)` [1](#0-0) , so for *that specific, honestly-behaving* contract, an attacker cannot spoof `from` without controlling the EVM `msg.sender` private key. The exposure exists for: (1) any other registered token contract/app that does not enforce this binding, (2) any future non-EVM (substrate) peer registered via `register_token`/`update_token` (the pallet explicitly restricts registration to EVM peers only via `NonEvmPeerChain` [8](#0-7) , which mitigates the substrate-peer variant), and (3) the fundamental design flaw that the unsigned code path trusts a payload-embedded identity field as an origin for privileged dispatch instead of requiring proof-of-possession in all cases.

### Impact Explanation
If exploitable (i.e., if any registered/approved source-chain contract fails to bind `from` to the true sender, or a future non-conforming app is registered), an attacker could execute arbitrary `BaseCallFilter`-permitted governance/staking/proxy actions as an arbitrary victim account without their consent — e.g., voting on referenda, delegating proxy authority, bonding/unbonding funds, or transferring assets via other pallets reachable through `Signed` origin — corrupting governance outcomes and potentially moving funds. This matches the "unauthorized transaction or execution" and "logic attack" bounty categories.

### Likelihood Explanation
Exploitability is contingent on the source-chain contract's behavior. Against the canonical `HyperFungibleToken.sol`, exploitation requires controlling `msg.sender`'s private key (not exploitable as-is). The residual risk is architectural: the substrate-side pallet has no independent verification that `from` reflects the actual message originator — it fully delegates that trust to the source-chain contract's implementation, which is an app-level (not protocol-level) invariant, making this fragile against future/alternate/misconfigured peer contracts. Given the mitigations found (EVM `from`-binding in the reference contract, and `NonEvmPeerChain` restricting registrable peers to EVM only), likelihood in the current production configuration is limited, but the design pattern remains a latent risk if any other app contract is registered as a peer.

### Recommendation
Require the signature-verified path unconditionally for any `SubstrateCalldata` execution (remove the unsigned fallback), or at minimum, restrict the unsigned fallback's origin to being derived strictly from a value the destination pallet can independently authenticate (e.g., always require a signature over `(nonce, runtime_call)` regardless of source, rather than trusting `message.from`). If the unsigned path must remain for UX reasons, document and enforce (at the protocol level, not just in one reference contract) that all registrable peer contracts MUST bind `from` to their chain's authenticated caller, and add defense-in-depth by additionally restricting which `RuntimeCall` variants are reachable via the unsigned path (e.g., an explicit allow-list rather than relying solely on `BaseCallFilter`).

### Proof of Concept
1. Deploy/register a peer contract for `StateMachine::Evm(X)` that (unlike `HyperFungibleToken.sol`) allows the caller to freely set the `from` field of the ISMP `Message` (or use `HyperFungibleToken.sol`'s `_buildDispatchPost` after compromising a relayed message body via any code path that doesn't bind `from` to `msg.sender`).
2. Construct `Message.data` as SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded pallet_democracy::vote or pallet_staking::bond call> }`.
3. Set `Message.from` = victim's 20/32-byte account identity.
4. Configure a mock runtime whose `BaseCallFilter` allows the target call for `Signed` origins; submit the resulting POST request through `on_accept`.
5. Observe `runtime_call.dispatch(RawOrigin::Signed(origin).into())` at [7](#0-6)  executes with `origin` equal to the victim's account, with no signature ever checked.
