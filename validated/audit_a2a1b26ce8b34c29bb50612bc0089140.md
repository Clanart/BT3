### Title
Unauthenticated JSON-RPC `send_tx` endpoint allows arbitrary transaction injection and cancellation into the operator's fee-paying queue - (File: `crates/clementine-tx-sender/src/jsonrpc/server.rs`)

### Summary
Every entity-to-entity RPC surface in this codebase (`ClementineOperator`, `ClementineVerifier`, `ClementineAggregator`) is protected by mutual TLS with a certificate-pinning interceptor that restricts calls to the aggregator or the entity's own certificate [1](#0-0) [2](#0-1) , and this is documented as the mandatory authentication model [3](#0-2) . The `clementine-tx-sender` crate exposes a second, independent JSON-RPC server with a `send_tx` method that has **no authentication whatsoever** — no TLS, no certificate check, no signature verification of the caller [4](#0-3) . This method directly forwards attacker-controlled parameters to `TxSenderClient::insert_try_to_send`, including an arbitrary raw transaction to be queued for CPFP/RBF fee-bumping, and arbitrary `cancel_outpoints`/`cancel_txids`/`activate_txids`/`activate_outpoints` lists [5](#0-4) [6](#0-5) .

### Finding Description
The binding that should hold is: **only the operator/aggregator that owns the fee-paying wallet may authorize spending from that wallet to fee-bump a transaction, and only transactions/outpoints legitimately belonging to the operator's own pending queue may be cancelled.** The unauthenticated `send_tx` JSON-RPC method breaks this binding.

`start_jsonrpc_server` builds a plain `jsonrpsee` HTTP server with only a body-size limit — no TLS, no client identity check of any kind [7](#0-6) . The `send_tx` handler decodes the caller-supplied hex transaction and forwards it, together with caller-supplied `fee_paying_type`, `cancel_outpoints`, `cancel_txids`, `activate_txids`, and `activate_outpoints`, straight into `insert_try_to_send` and commits the DB transaction [8](#0-7) .

`insert_try_to_send` persists the transaction into the tx-sender queue with the given `fee_paying_type` and also records the supplied `cancel_outpoints`/`cancel_txids` as cancellation triggers in the database [6](#0-5) [9](#0-8) . When `fee_paying_type = FeePayingType::CPFP`, the tx-sender's background loop later attaches the operator's own funds (via CPFP anchor spending) to get the attacker-supplied transaction confirmed — the same mechanism used for legitimate protocol transactions like `Round`, `ReadyToReimburse`, `Kickoff`, etc. [10](#0-9) [11](#0-10) . There is no check anywhere in this path that the caller is authorized to spend the operator's fee-paying wallet or that the `cancel_outpoints`/`cancel_txids` correspond to entries the caller is entitled to invalidate.

This is a direct analog of the reported bug class ("a caller reaching a state-changing method versus the party it is meant for") — but unlike the reported memory-exhaustion issue (explicitly out of scope), this is a genuine missing-authorization defect: the method is state-changing and fully reachable by any network client, with no rate-limiting angle involved.

### Impact Explanation
An unauthenticated attacker who can reach the tx-sender's JSON-RPC port can:
1. Submit arbitrary transactions with `FeePayingType::CPFP`, causing the operator's tx-sender loop to repeatedly spend real BTC from the operator's fee-paying wallet to fee-bump attacker-chosen transactions — burning the operator's collateral on transactions it never intended to send.
2. Submit `cancel_outpoints`/`cancel_txids` entries that collide with the operator's own legitimate queued transactions (e.g. `ReadyToReimburse`, `Round`, `Reimburse`), causing those entries to be marked cancelled in the database and potentially preventing the operator from being reimbursed.

Both outcomes map to the accepted Critical impact categories: "an honest operator's collateral burned" and "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
The likelihood is high for any deployment where this JSON-RPC port is reachable by anything other than a fully trusted, air-gapped caller, since the code contains zero authentication or authorization logic on this endpoint — in stark contrast to every other RPC surface in the repository, which enforces mTLS with certificate pinning by design. No credentials, keys, or roles are required to invoke it; only network reachability to the bound `SocketAddr` is needed.

### Recommendation
Add authentication to the tx-sender JSON-RPC server consistent with the rest of the codebase's mTLS model (or, at minimum, require a shared secret / signed request), and validate that `cancel_outpoints`/`cancel_txids`/`activate_*` parameters supplied by the caller only reference transactions that the calling identity is authorized to affect, before accepting them into `insert_try_to_send`.

### Proof of Concept
1. Start the tx-sender with `jsonrpc` enabled per `crates/clementine-tx-sender/src/task.rs` (`spawn_txsender_loop`), binding to the configured address.
2. From any host that can reach that address, issue:
```
curl -X POST http://<bind>:<port> -H 'content-type: application/json' -d '{
  "jsonrpc":"2.0","id":1,"method":"send_tx",
  "params": [{
     "tx_metadata": null,
     "signed_tx_hex": "<attacker-crafted tx hex>",
     "fee_paying_type": "Cpfp",
     "rbf_signing_info": null,
     "cancel_outpoints": [{"txid":"<operator's pending outpoint txid>","vout":0}],
     "cancel_txids": [],
     "activate_txids": [],
     "activate_outpoints": []
  }]
}'
```
No credential, certificate, or key is required — the request is accepted by `send_tx` in `crates/clementine-tx-sender/src/jsonrpc/server.rs:58-88`, and `insert_try_to_send` persists both the attacker's transaction (to be CPFP fee-bumped from the operator's wallet) and the attacker-chosen cancellation entry into the database.

pub async fn start_jsonrpc_server(
    tx_sender_client: TxSenderClient,
    bind_addr: SocketAddr,
) -> Result<TxSenderJsonRpcServer, BridgeError> {
    let server: Server = ServerBuilder::default()
        .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
        .build(bind_addr)
        .await
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let local_addr = server
        .local_addr()
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let mut module = RpcModule::new(tx_sender_client.clone());
    module
        .register_async_method("send_tx", |params, client, _| async move {
            let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;

            let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
            let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;

            let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;

            let try_to_send_id = client
                .insert_try_to_send(
                    &mut dbtx,
                    req.tx_metadata,
                    &signed_tx,
                    req.fee_paying_type,
                    req.rbf_signing_info,
                    &req.cancel_outpoints,
                    &req.cancel_txids,
                    &req.activate_txids,
                    &req.activate_outpoints,
                )
                .await
                .map_err(jsonrpc_err)?;

            client
                .db
                .commit_transaction(dbtx)
                .await
                .map_err(jsonrpc_err)?;

            Ok::<u32, ErrorObjectOwned>(try_to_send_id)
        })
        .map_err(|e| BridgeError::Eyre(e.into()))?;
