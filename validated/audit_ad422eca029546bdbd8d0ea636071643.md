### Title
`depositFor()` in `WombatPoolHelperV2` hardcodes `_minimumLiquidity` to 0, removing user's slippage/sandwich protection - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2` exposes both a `deposit(uint256 _amount, uint256 _minimumLiquidity)` function that forwards the caller-supplied `_minimumLiquidity` to the underlying Wombat pool deposit, and a `depositFor(uint256 _amount, address _for)` function that silently hardcodes this same protection parameter to `0`, completely disabling it for that code path.

### Finding Description
`deposit()` correctly threads the user-chosen `_minimumLiquidity` all the way into `IWombatPool.deposit(...)` via `WombatStaking.deposit`, giving the caller control over the minimum LP output they will accept: [1](#0-0) 

`depositFor()`, however, pulls tokens from `msg.sender` and stakes on behalf of an arbitrary `_for` address, but calls `_deposit(_amount, 0, _for, address(this))`, passing a hardcoded `0` instead of any user-supplied limit: [2](#0-1) 

That `0` flows straight through to the underlying pool call: [3](#0-2) 

Because the minimum-liquidity check in the underlying Wombat pool degenerates to `receivedLiquidity >= 0` (always true), the deposit path used by `depositFor()` has no functional bound on the resulting LP amount, unlike the sibling `deposit()` function which enforces the same check with a real, user-chosen limit. This mirrors the reported bug class: a user-control/limit parameter (`limitIndex_`/`_minimumLiquidity`) that exists and is properly enforced on one code path but is silently skipped/neutralized on another reachable path performing an economically equivalent operation, removing the caller's ability to bound an unfavorable price/ratio move.

### Impact Explanation
Any address can call `depositFor()` for itself or on behalf of another user. Because `_minimumLiquidity` is forced to `0`, the deposit is executed without any protection against Wombat pool price/ratio manipulation (e.g., an attacker temporarily skewing the pool's cash/liability ratio around the victim's transaction). The depositor/recipient can receive materially fewer LP (and therefore fewer downstream staking-token/receipt-token) shares than the fair-value exchange rate would produce, resulting in a direct, uncapped economic loss of value on deposit with no way for the caller to prevent it.

### Likelihood Explanation
Likelihood is high: `depositFor()` is a normal, permissionless, frequently-used entry point (no privileged role required), takes only `_amount` and `_for` as parameters, and always uses `_minimumLiquidity = 0` — every single call through this function is exposed, not just an edge case.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor(uint256 _amount, address _for, uint256 _minimumLiquidity)` and forward it (instead of the hardcoded `0`) into `_deposit(...)`, matching the protection already provided by `deposit()`.

### Proof of Concept
1. Attacker observes a pending `depositFor()` transaction (or triggers one on behalf of a victim) in the mempool.
2. Attacker sandwiches it: performs a large swap/withdraw against the Wombat pool right before the victim's transaction to skew the pool's cash/liability ratio unfavorably, then reverses it right after.
3. The victim's `depositFor()` call executes with `_minimumLiquidity = 0` — `IWombatPool.deposit(...)` cannot revert regardless of how few LP tokens are minted, so the victim (or the address specified in `_for`) receives less LP/receipt tokens than a fair-rate deposit would have produced, realizing the attacker's extracted value as the victim's loss.
