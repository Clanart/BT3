### Title
Cross-chain replay of `associate()` signatures in the `addr` precompile due to missing chain ID in the signed message hash - (File: `precompiles/addr/addr.go`)

### Summary
The `associate` method of the `addr` precompile (and all of its legacy versions) recovers a signer's address by hashing an arbitrary `customMessage` string with plain `crypto.Keccak256Hash([]byte(customMessage))` and using that hash together with the caller-supplied `v/r/s` to run `helpers.GetAddresses`. No chain identifier (or any other domain separator) is mixed into the hashed data, so a signature that is valid on one Sei chain/environment is equally valid on any other Sei-based chain that shares the same precompile address and ABI. [1](#0-0) 

### Finding Description
`associate()` decodes attacker/caller-supplied `v`, `r`, `s` and `customMessage`, computes `customMessageHash := crypto.Keccak256Hash([]byte(customMessage))`, and calls `helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)` to recover the EVM address, Sei address, and public key that will be associated together. [2](#0-1) 

Unlike the EVM transaction signing path, where chain ID is validated separately at the ante-handler level (`EVMSigVerifyDecorator.AnteHandle` explicitly checks `ethTx.ChainId()` against the keeper's configured chain ID before allowing further processing), the `associate()` precompile has no equivalent check. [3](#0-2) 

The same unbounded-message/no-chain-id pattern is duplicated across all legacy precompile versions (`v575`, `v600`, `v601`, `v603`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`), so every historical binary is affected identically. [4](#0-3) [5](#0-4) 

This mirrors the referenced Sherlock finding pattern: a signature-validation routine (`_validateSigner()` in the report, `associate()`/`GetAddresses()` here) that hashes signed data without folding in `block.chainId`, enabling a signature produced for one network to be replayed verbatim on another network that shares the same contract/precompile address and verification logic.

### Impact Explanation
Sei operates multiple networks that share the same EVM precompile addresses and ABI (e.g., mainnet `pacific-1`, testnet `atlantic-2`, devnet `arctic-1`) as evidenced by the chain-ID test constants used elsewhere in the codebase. [6](#0-5) 

Because the `associate()` hash has no chain separator, a `(v, r, s, customMessage)` tuple that a user signed to associate their addresses on one network can be resubmitted on another network to force the same EVM address ↔ Sei address ↔ pubkey mapping. Address association is security-sensitive: it determines which account controls direct-cast balances, staking, and distribution state for a given address pair (as explicitly called out in the codebase's own security commentary on a related SetCode-authorization replay fix). [7](#0-6) 

Forcing an association a victim did not intend on a chain they did not sign for could migrate/lock their balances into an association they don't control there, or interfere with an account's ability to be associated the way they intend on that specific chain — a permanent, cross-chain state-corruption/fund-control issue rather than a purely cosmetic one.

### Likelihood Explanation
Exploitation only requires observing a publicly broadcast `associate()` call (transaction data is public on-chain) and resubmitting the same calldata to the `addr` precompile at address `0x0000000000000000000000000000000000001004` on a different Sei network. No privileged access, validator collusion, or additional secrets are needed — any user or dApp integrator who reuses the same signing flow across multiple Sei environments (mainnet/testnet/devnet, or future forks) is exposed. [8](#0-7) 

### Recommendation
Include the chain ID (`ctx` chain ID via `evmKeeper.ChainID(ctx)` or the precompile address itself) as part of the data that is hashed and signed for `associate`/`associatePubKey`, e.g. `keccak256(abi.encodePacked(chainID, precompileAddress, customMessage))`, and reject associate calls whose recovered hash does not match the current chain's domain-separated hash. This should be applied consistently to the current `precompiles/addr/addr.go` implementation and, if still reachable, to the legacy versioned copies.

### Proof of Concept
1. On Chain A (e.g. `atlantic-2` testnet), a user signs a message and calls `associate(v, r, s, customMessage)` on the `addr` precompile to link `EVMAddr` with `SeiAddr`; the call succeeds because `customMessageHash = keccak256(customMessage)` recovers the correct signer. [9](#0-8) 
2. An attacker observes this transaction's calldata (public) and resubmits the identical `(v, r, s, customMessage)` tuple to the `addr` precompile at the same address `0x...1004` on Chain B (e.g. `pacific-1` mainnet). [8](#0-7) 
3. Because `GetAddresses` performs no chain-ID or domain check, Chain B recovers the same `evmAddr`/`seiAddr`/`pubkey` and calls `associateAddresses`, creating/overwriting the association on Chain B without the victim's consent for that specific chain. [10](#0-9) 

**Uncertainty note:** I could not fully inspect `associateAddresses()`'s exact state-mutation guards (e.g., whether it silently no-ops if an association already exists) since the tool budget ran out before I could open that function body; this affects how easily an existing association can be overwritten versus only being exploitable for first-time associations. A Devin session with full file access would be needed to confirm the exact blast radius of `associateAddresses`.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}
