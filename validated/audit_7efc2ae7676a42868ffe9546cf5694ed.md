## Title
Tokenfactory `MsgSetDenomMetadata` allows unbounded `Description`/`Name`/`Symbol` strings, enabling storage bloat and downstream DoS via bank/EVM metadata readers - (File: `x/tokenfactory/types/msgs.go`, `sei-cosmos/x/bank/types/metadata.go`)

### Summary
The Discourse advisory describes free-text user profile fields (Location, Website) that were never length-checked, letting a normal user store arbitrarily large payloads that later broke rendering for any client that loaded the profile. The analogous sei-chain path is `x/tokenfactory`'s permissionless `MsgCreateDenom` → `MsgSetDenomMetadata` flow: any unprivileged account can become the "admin" of a token-factory denom simply by creating it, and then call `MsgSetDenomMetadata` with a `cosmos.bank.v1beta1.Metadata` whose `Description`, `Name`, and `Symbol` fields have no length bound.

### Finding Description
`MsgSetDenomMetadata.ValidateBasic()` and the keeper's `SetDenomMetadata` handler both delegate all field checking to `banktypes.Metadata.Validate()`: [1](#0-0) [2](#0-1) 

`Metadata.Validate()` only checks that `Name`/`Symbol` are non-blank and that `Base`/`Display` are syntactically valid denoms; it never bounds the length of `Description`, `Name`, or `Symbol`, and does not validate `DenomUnit.Aliases` length either: [3](#0-2) 

Any token-factory creator (permissionless — anyone can call `MsgCreateDenom`, becoming the admin of `factory/{creator}/{subdenom}`) can therefore submit a `MsgSetDenomMetadata` transaction with, e.g., a multi-megabyte `Description` string (bounded only by the generic Cosmos SDK tx-size limit, not by any metadata-specific limit). This is persisted permanently via `bankKeeper.SetDenomMetaData`, keyed by the denom, with no size cap: [4](#0-3) 

That metadata is subsequently read by every consumer that enumerates denom metadata, including the EVM bank precompile's `denomsMetadata`/`DenomsMetadata` query, which loads and ABI-packs **all** metadata records (not scoped to a single denom) into a single EVM call response: [5](#0-4) 
and the per-denom `name`/`symbol` precompile methods that any EVM contract or `eth_call` can invoke: [6](#0-5) 

Unlike the denom itself, whose length is capped by `sdk.ValidateDenom` and the tokenfactory `MaxSubdenomLength`/`MaxCreatorLength` constants, the free-text `Description`/`Name`/`Symbol` fields have no such cap enforced anywhere in this repo (`x/tokenfactory/types/denoms.go` only bounds `subdenom`/`creator`, not metadata text fields): [7](#0-6) 

### Impact Explanation
An unprivileged transaction sender can permanently inflate on-chain state with oversized, unbounded metadata strings for each denom they create, and this bloated metadata is served back through the public EVM JSON-RPC/precompile surface (`bank` precompile `name`, `symbol`, `denomsMetadata`) to any RPC client or contract that queries it. Aggregating this across many denoms makes the `DenomsMetadata` precompile query (which returns all denom metadata in one call) increasingly expensive to marshal/ABI-encode, degrading or potentially failing public-RPC responses for all callers of that query — a resource/availability issue reachable purely from unprivileged, permissionless token creation.

### Likelihood Explanation
High reachability: `MsgCreateDenom` is fully permissionless, and the resulting creator is automatically the denom's admin, authorized to call `MsgSetDenomMetadata` with no additional privilege check beyond `sender == admin`. No governance or validator cooperation is required — a single account can trigger this with two transactions.

### Recommendation
Add explicit maximum length bounds (analogous to `MaxSubdenomLength`/`MaxCreatorLength`) for `Metadata.Description`, `Metadata.Name`, `Metadata.Symbol`, and `DenomUnit.Aliases` inside `banktypes.Metadata.Validate()` (or in `x/tokenfactory` message `ValidateBasic`/keeper handler as defense-in-depth), rejecting oversized metadata before it is persisted or exposed via the bank precompile.

### Proof of Concept
1. Submit `MsgCreateDenom{Sender: attacker, Subdenom: "x"}` — attacker becomes admin of `factory/{attacker}/x`.
2. Submit `MsgSetDenomMetadata{Sender: attacker, Metadata: {Base: "factory/{attacker}/x", Display: "factory/{attacker}/x", Name: <multi-MB string>, Symbol: <multi-MB string>, Description: <multi-MB string>, DenomUnits: [...]}}` via `x/tokenfactory/keeper/msg_server.go`'s `SetDenomMetadata`, which only calls `msg.Metadata.Validate()` (no length checks) before calling `bankKeeper.SetDenomMetaData`.
3. Repeat for many denoms created by many/the same attacker; each call to the EVM bank precompile's `denomsMetadata` method (`precompiles/bank/bank.go`) must now enumerate and ABI-pack all of this oversized metadata, and any RPC/precompile `name`/`symbol` lookup on the poisoned denom returns the oversized string, imposing cost on all consumers.

func (p PrecompileExecutor) name(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) ([]byte, uint64, error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	denom := args[0].(string)
	metadata, found := p.bankKeeper.GetDenomMetaData(ctx, denom)
	if !found {
		return nil, 0, fmt.Errorf("denom %s not found", denom)
	}
	bz, err := method.Outputs.Pack(metadata.Name)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
