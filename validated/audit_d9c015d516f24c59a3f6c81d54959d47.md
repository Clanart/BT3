### Title
Unbounded recursive AccountKey RLP decoding enables stack-overflow DoS via nested `AccountKeyRoleBased` in account-update transactions - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each element of the role-based key list through `AccountKeySerializer`, which in turn can itself decode as another `AccountKeyRoleBased`, with no depth limit. A crafted `TxTypeAccountUpdate` (or its fee-delegated variants) can nest role-based account keys arbitrarily deep, driving the decoder into unbounded recursion and exhausting the goroutine stack — the same bug class as the KCL parser DoS (deep nesting through a recursive decode path with no depth guard).

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte strings and, for each one, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a `keyType`, allocates a concrete `AccountKey` via `NewAccountKey(keyType)`, and decodes into it: [2](#0-1) 

If `keyType` is `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, and the whole cycle (`RoleBased -> Serializer -> RoleBased -> ...`) repeats for every level of nesting the attacker encodes. There is no depth counter, no recursion limit, and no size ceiling on the number of nested key layers — only `CheckInstallable`/`CheckUpdatable` reject composite-within-composite keys, and those checks run *after* decoding has already completed: [3](#0-2) 

The decode path is reached directly from transaction deserialization. `TxInternalDataAccountUpdate.fromSerializable` calls `rlp.DecodeBytes(serialized.Key, serializer)` on the attacker-supplied `Key` bytes before any validation occurs: [4](#0-3) 

This same pattern is used by `TxInternalDataFeeDelegatedAccountUpdate`, `TxInternalDataFeeDelegatedAccountUpdateWithRatio`, and account-creation transaction types, all of which embed an `accountkey.AccountKey` field decoded the same way, making the reachable surface every transaction type that carries an `AccountKey`.

### Impact Explanation
An attacker who can submit a single `TxTypeAccountUpdate`-family transaction (via `eth_sendRawTransaction` or p2p tx propagation into the pool) with a deeply nested `AccountKeyRoleBased` key structure forces every node that decodes/validates that transaction (tx-pool admission and later block processing) to recurse until the goroutine stack limit is hit. In Go, stack overflow is a fatal, unrecoverable runtime error (not a `panic` that `recover()` can catch), so it crashes the node process. If the malicious transaction also gets included in a block, all honest full nodes processing that block would crash identically — a single-transaction denial-of-service against the network's transaction-processing/consensus path.

### Likelihood Explanation
Any unprivileged externally-owned account can craft and RLP-encode such a transaction offline (no special access to the network or a real target account key). It reaches txpool admission at RLP-decode time before any AccountKey composite-type or size validation runs, so no capital, fees beyond gas price, or on-chain preconditions are required beyond the ability to submit a raw transaction.

### Recommendation
Add and enforce a maximum recursion/nesting depth (and/or maximum total decoded size) for `AccountKey` RLP decoding — check depth before recursing in `AccountKeyRoleBased.DecodeRLP` / `AccountKeySerializer.DecodeRLP`, and reject/at least short-circuit when `keyType == AccountKeyTypeRoleBased` is nested inside another `AccountKeyRoleBased`, mirroring the existing `ErrNestedCompositeType` check but performed *during* decode rather than only after decode completes.

### Proof of Concept
1. Build an innermost valid key, e.g. `AccountKeyNil`, and RLP-encode it via `AccountKeySerializer` to get bytes `B0`.
2. Wrap `B0` as the single element of an `AccountKeyRoleBased` list, RLP-encode that `AccountKeyRoleBased` via `AccountKeySerializer` (keyType = `AccountKeyTypeRoleBased`) to get `B1`.
3. Repeat step 2 using `B(i-1)` as the sole element for N iterations (e.g., N = 50,000) to produce `BN`.
4. Set `BN` as the `Key` field of a `TxInternalDataAccountUpdate` (or a fee-delegated variant), RLP-encode the full transaction, and submit it via `eth_sendRawTransaction` or directly into the tx pool.
5. When the node decodes the transaction (`fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)`), the recursive `AccountKeyRoleBased.DecodeRLP` ↔ `AccountKeySerializer.DecodeRLP` cycle recurses N times before any `CheckInstallable` validation runs, exhausting the stack and crashing the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
