### Title
Payout output-index-0 pinning is real, but the operator-attribution OP_RETURN output is unsigned and attacker-forgeable via a conflicting ANYONECANPAY spend - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`SinglePlusAnyoneCanPay` correctly pins output 0 (the user's `output_script_pubkey`/`output_amount`), so an attacker cannot redirect the payout value itself — `SECP.verify_schnorr` in `Operator::withdraw` (`core/src/operator.rs:630-637`) will reject any mutation of output 0. However, `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) places the operator-attribution `OP_RETURN` at output index 2, which is not committed by `SIGHASH_SINGLE` (SIGHASH_SINGLE only commits to the output at the same index as the signed input, i.e. index 0). Because the sighash is `AnyoneCanPay`, an attacker can also freely add/remove/replace other inputs. This lets an unprivileged attacker construct a conflicting transaction spending the same withdrawal UTXO, with an identical output 0 (satisfying the SINGLE-pinned signature) but an arbitrary OP_RETURN and their own fee-paying inputs, causing the confirmed payout's operator-attribution to diverge from the actual funder.

### Finding Description
Binding claimed broken (as tested): `payout_tx.output[0].value == Citrea.output_amount ∧ payout_tx.output[0].script_pubkey == Citrea.output_script_pubkey`. This binding **holds** because `calculate_sighash_txin`/`calculate_pubkey_spend_sighash` compute `Prevouts::One` for `SinglePlusAnyoneCanPay` (`core/src/builder/transaction/txhandler.rs:222-233`) and `taproot_key_spend_signature_hash` for `SIGHASH_SINGLE` commits to `tx.output[input_index]` verbatim; `Operator::withdraw` at `core/src/operator.rs:630-637` re-derives the sighash from the actual constructed `payout_txhandler` and verifies it against the user's Schnorr signature, so any output-0 mutation invalidates the signature.

The real broken binding is different: `payout_tx.OP_RETURN(output[2]).operator_xonly_pk == the operator who actually funded/broadcast the payout`. This is **not** enforced by any signature, because `SIGHASH_SINGLE|ANYONECANPAY` only commits the input being signed to the *single* output at the same index (index 0). Outputs 1 (anchor) and 2 (`OP_RETURN` with `operator_xonly_pk`, `core/src/builder/transaction/operator_reimburse.rs:418,432`) are entirely unconstrained by the user's signature. Since the sighash flag is also `AnyoneCanPay`, the transaction's other inputs (fee-funding UTXOs) are unconstrained too.

Exploit flow: an unprivileged attacker observes an honest operator's unconfirmed payout tx for withdrawal `i` in the mempool (correct output 0, output 1 anchor, output 2 OP_RETURN naming the honest operator). The attacker rebuilds a new transaction that: (1) spends the same withdrawal UTXO input with the identical `taproot::Signature` (still valid since output 0/committed input is unchanged — same sighash, same signature); (2) keeps output 0 byte-for-byte identical (so the sighash-committed content is untouched); (3) replaces the fee-paying inputs, anchor output, and/or the OP_RETURN output (e.g., pointing to a different operator's xonly pubkey, an unrelated key, or garbage), then broadcasts this with higher fee/RBF to win the race and confirm before the honest operator's tx.

Downstream, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) and the bridge circuit's `host_deposit_constant`/`bridge_circuit` (`bridge-circuit-host/src/structs.rs:482-516`, `circuits-lib/src/bridge_circuit/mod.rs:206-229`) both derive `operator_xonly_pk` purely by parsing the first `OP_RETURN` output of whatever payout tx actually confirmed — with no cryptographic tie to the signer/funder of that tx. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) compares the kickoff sender's `operator_xonly_pk` against this DB-recorded value from `payout_info`, and if they match, the kickoff is *not* flagged malicious.

### Impact Explanation
If the attacker sets the forged `OP_RETURN` to a different (real, non-paying) operator's xonly pubkey, that operator (who did not fund the payout) can later send a `kickoff` for withdrawal `i`; `is_kickoff_malicious` will find the DB-recorded `operator_xonly_pk` matches the kickoff sender, so verifiers will not flag it as malicious, and the presigned reimbursement transaction graph will let that operator reimburse itself from bridge funds for a payout it never fronted. This matches the Critical category "an operator reimbursed for a payout it never funded." It also corrupts `bridge_circuit`'s `deposit_constant` (which embeds `operator_xonlypk` from the OP_RETURN), potentially letting a false claim be proved for an operator who did not pay, or making the true payer's later legitimate kickoff for the same withdrawal fail/conflict (since the withdrawal UTXO is already spent), permanently blocking the honest funder's own reimbursement path. This is repeatable across any withdrawal whose payout tx is visible unconfirmed in mempool, and across all operators.

### Likelihood Explanation
Precondition: an honest operator's payout tx must be visible in the mempool before it confirms (routine, since `Operator::withdraw` broadcasts via `fund_raw_transaction`/RBF, `core/src/operator.rs:651-674`). Attacker cost is only the fee needed to outbid the honest operator's fee-bump/RBF race, plus their own dust-fee-funding inputs — no bridge collateral, key share, or privileged access required, fully within the stated unprivileged attacker capability of broadcasting Bitcoin transactions. Feasibility is high given only standard mempool RBF/fee-bidding is needed; it is fully repeatable per-withdrawal.

### Recommendation
Bind the operator-attribution output cryptographically to the same signature that authorizes the spend, e.g. by using `SIGHASH_ALL|AnyoneCanPay` semantics for the OP_RETURN (or including its content in a covenant/second signed output), or by having verifiers require the OP_RETURN operator pubkey to match the operator identity independently authenticated at kickoff time via a stronger binding (e.g., requiring the kickoff-committed operator key to also match a Merkle/txid-level attestation of who funded/broadcast the specific payout inputs), rather than trusting an unauthenticated OP_RETURN output.
