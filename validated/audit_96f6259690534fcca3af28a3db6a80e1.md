### Title
Unbounded recursive parsing of attacker-controlled on-chain memo data in `PuzzleWithRestrictions.from_memo()` allows a spend-triggered stack-overflow / crash - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
The reported CVE (CVE-2016-4008) is a classic "unbounded/unguarded recursive decode of untrusted structured data causes infinite recursion / stack overflow" bug class. The chia-blockchain codebase's own CLVM tree-hashing code explicitly documents this exact concern and was hardened against it (`sha256_treehash()` is "deliberately iterative to avoid Python recursion limits on deeply nested CLVM" — see `.cursor/context/types.md`). However, `PuzzleWithRestrictions.from_memo()` in `chia/wallet/puzzles/custody/custody_architecture.py` reconstructs a `MofN`/`PuzzleWithRestrictions` tree from a `Program` memo taken directly from on-chain coin data, and does so **recursively with no depth bound**, matching the same bug class.

### Finding Description
`PuzzleWithRestrictions.from_memo()` [1](#0-0)  parses a `Program` memo and, whenever `further_branching` is true, recurses into itself once per `MofN` member:

```
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```

There is no maximum-depth check, no bound on the number of nested `MofN` layers, and the only exception guard in the function catches `ValueError`, not `RecursionError`. The memo consumed here is `singleton_create_coin.memo_blob`, i.e., arbitrary hint/memo bytes attached to a `CREATE_COIN` condition that any spend-bundle submitter fully controls. This memo is fed into `from_memo()` from `PlotNFT.get_next_from_coin_spend()` in `chia/pools/plotnft_drivers.py`:

```
unknown_inner_puzzle = PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())
```

`get_next_from_coin_spend()` is called from wallet-side puzzle-driver code paths (`plotnft_wallet.py`, `wallet_state_manager.py`, `cat_wallet.py`, `vc_wallet.py`, etc.) that process coin spends/coin states observed on chain during normal wallet sync — i.e., it is driven by data that originates from a spend a remote party pushed to the mempool/chain, not by a value the wallet itself chose. By nesting `MofN` structures inside the memo thousands of levels deep, an attacker can force `from_memo()` into recursion depths that exceed Python's default recursion limit, raising an uncaught `RecursionError` in wallet code that only defends against `ValueError`.

`MofNMerkleTree._m_of_n_proof()` in the same file [2](#0-1)  is a second, structurally similar recursive helper over merkle-proof generation, though it operates over the merkle tree of an already-constructed `MofN`, so the primary externally-reachable path is `from_memo()`.

### Impact Explanation
An unhandled `RecursionError` during wallet coin-state processing halts (crashes or repeatedly fails) the processing of that spend/coin update in the affected wallet client, which is a spend-triggered transaction-processing halt — one of the accepted impact categories. Because the trigger is an ordinary `CREATE_COIN` memo inside a spend that any unprivileged submitter can construct and push through the mempool, this is broadly and cheaply reachable, without needing special privileges, a malicious peer, or a malicious node.

### Likelihood Explanation
Medium-to-high likelihood of reachability: constructing a deeply nested `MofN` memo requires only assembling a CLVM list structure, no signatures or special puzzle execution — it is pure data shaped to match the memo grammar consumed by `from_memo()`. The harder part is getting a wallet to actually invoke `PuzzleWithRestrictions.from_memo()` on the attacker's memo; this currently appears gated behind PlotNFT/pool-related singleton recognition logic (`get_next_from_coin_spend()`), so the attacker would need the created coin to be recognized/attempted as a PlotNFT-style singleton coin by a victim wallet during sync. I was not able to fully trace every call path (cat_wallet.py, vc_wallet.py, vc_drivers.py, cr_cat_drivers.py also reference `get_next_from_coin_spend`/`from_memo`-style flows) within the available iterations, so the exact set of wallets that unconditionally hit this recursive parser on arbitrary attacker memos is not fully confirmed.

### Recommendation
- Add an explicit recursion/nesting depth limit (and/or an iterative work-stack implementation) to `PuzzleWithRestrictions.from_memo()`, mirroring the iterative design already used in `sha256_treehash()`.
- Catch `RecursionError` (in addition to `ValueError`) at the boundary where untrusted memo bytes are parsed (e.g., in `PlotNFT.get_next_from_coin_spend()`), and treat it as "invalid memoization" rather than letting it propagate and crash wallet sync.
- Bound the size/branching factor of `MofNHint.member_memos` before recursing.

### Proof of Concept
Conceptually:
1. Attacker crafts a `CREATE_COIN` condition whose memo is a `PuzzleWithRestrictions` memo (`spec_namespace = "CHIP-0043"`) where the `puzzle_hint` is an `MofNHint` with `further_branching=True` and a single member whose memo is itself another such `MofN` memo, nested N times (N large enough to exceed Python's recursion limit, e.g. a few thousand).
2. Attacker pushes a spend bundle creating a coin with this memo attached, in a shape that a victim wallet's pool/PlotNFT (or similar) sync logic will attempt to interpret via `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()`.
3. When the victim wallet processes this coin during sync, `from_memo()` recurses N times and raises `RecursionError`, which is not caught by the existing `except ValueError` handling, propagating up and interrupting wallet coin-state processing.

I could not fully verify within this session whether every consuming wallet path (`cat_wallet.py`, `vc_wallet.py`, `vc_drivers.py`, `cr_cat_drivers.py`) reaches `from_memo()` unconditionally for arbitrary attacker-supplied coins versus only for coins that already match a specific recognized puzzle shape; confirming the exact minimal trigger conditions per wallet type would require further code tracing.

class MofNMerkleTree(MerkleTree):  # Special subclass that can generate proofs for m of n puzzles in the tree
    def _m_of_n_proof(self, puzzle_hashes: list[bytes32], spends_to_prove: dict[bytes32, ProvenSpend]) -> Program:
        if len(puzzle_hashes) == 1:  # we've reached a leaf node
            if puzzle_hashes[0] in spends_to_prove:
                spend_to_prove = spends_to_prove[puzzle_hashes[0]]
                # If it's one that we've been requested to prove, the format is (() puzzle_reveal . solution)
                return Program.to((None, (spend_to_prove.puzzle_reveal, spend_to_prove.solution)))
            else:
                return Program.to(hash_an_atom(puzzle_hashes[0]))
        else:
            first, rest = self.split_list(puzzle_hashes)
            first_proof = self._m_of_n_proof(first, spends_to_prove)
            rest_proof = self._m_of_n_proof(rest, spends_to_prove)
            if first_proof.atom is None or rest_proof.atom is None:
                # If either side has returned as a cons, part of the subtree needs to be revealed
                # so we just return the branch as is
                return Program.to((first_proof, rest_proof))
            else:
                return Program.to(hash_a_pair(bytes32(first_proof.as_atom()), bytes32(rest_proof.as_atom())))

    def generate_m_of_n_proof(self, spends_to_prove: dict[bytes32, ProvenSpend]) -> Program:
        return self._m_of_n_proof(self.nodes, spends_to_prove)
