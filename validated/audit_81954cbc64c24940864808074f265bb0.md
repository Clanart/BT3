### Title
Panic via identity group nonce in BIP-340 HRAm lets a participant crash FROST signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
The `rbpf` bug class — a panic reachable by feeding untrusted structured input into code that assumes well-formedness — maps onto Serai as a panic reachable from attacker-controlled preprocess messages during FROST signing for Bitcoin. `networks/bitcoin/src/crypto.rs` `x()` and `x_only()` call `.expect("point at infinity")` on the x-coordinate of an encoded `ProjectivePoint`. The BIP-340 `Hram::hram` invokes `x(R)` on the *aggregate* group nonce `R` (`nonce_sums[0][0]`), which is the sum of per-participant nonce commitments. Individual commitments pass `Curve::read_G` (which rejects identity at `crypto/frost/src/curve/mod.rs:125-131`), but nothing prevents the *sum* of accepted commitments from being the identity. A signing-set participant who submits their preprocess last can choose nonce commitments that cancel the other participants' contributions, forcing `R = identity` and panicking every honest signer inside `Schnorr::sign_share` (`crypto/frost/src/algorithm.rs:208`).

### Finding Description
- `x()` does `key.to_encoded_point(true).x().expect("point at infinity")` — panics on the identity point [1](#0-0) .
- `x_only()` likewise panics on identity [2](#0-1) .
- `Hram::hram` feeds the aggregate nonce `R` and group key `A` into `x()` [3](#0-2) .
- `hram` is invoked from `Schnorr::sign_share` with `&nonce_sums[0][0]`, the summed group nonce commitment [4](#0-3) .
- The nonce sums are built from participant-supplied `Preprocess` commitments read via `read_preprocess`/`Commitments::read` [5](#0-4) . Deserialization only rejects *individual* identity points [6](#0-5)  — the sum is unchecked.
- The doc comment on `Hram` admits the panic: "If either `R` or `A` is the point at infinity, this will panic" [7](#0-6) , and claims the probability is negligible "even with malicious participants" — which is wrong, since an adaptive participant can *deterministically* force `R = identity`.

Because FROST's hiding commitment `D` is summed unweighted (the binding factor `rho` only multiplies `E`), an attacker who observes the other signers' preprocesses chooses `D_i = -Σ D_j` and `E_i = -Σ (rho·E_j)/rho_i` to make the aggregate `R` the identity. The panic then fires inside `sign_share` on every honest validator that reaches the signing step, before any share is produced.

### Impact Explanation
An unprivileged participant in a Bitcoin threshold-signing session can deterministically crash the signing machines of honest validators by submitting a maliciously crafted (but individually valid, non-identity) preprocess. This is an availability failure of the entire FROST signing round — the same "panic on malformed adversarial input" class as the `solana_rbpf` ELF-header overflow. Under the common operational pattern of a panic aborting the node or signing task, this is a reachable denial of service gated behind no proof of work and no secret knowledge.

### Likelihood Explanation
Triggering requires only participating in a signing session (sending a preprocess message) — the precise capability the in-scope rules grant to an unprivileged party. Individual commitments remain canonical non-identity points, so all deserialization and duplicate/missing-participant checks pass [8](#0-7) . The only residual question is whether the attacker can pick their preprocess after seeing others' (parallel/ROS-style preprocess collection), which `sign()`'s `HashMap<Participant, Preprocess>` interface permits since all preprocesses arrive before `sign` is called.

### Recommendation
Reject the identity point at the aggregate level, not just per-commitment: after computing each `nonce_sums[i][j]` in `sign()`/`sign_share`, check `is_identity()` and return `FrostError::InvalidPreprocess`/`InvalidSigningSet` instead of proceeding into `Hram::hram`. Alternatively (defense in depth), make `x()`/`x_only()` return `Option`/`Result` and propagate an error from `Hram::hram` rather than panicking, since `hram`'s signature would need to change or a documented non-identity invariant enforced upstream.

### Proof of Concept
Conceptual reproduction inside `sign()`:

1. Victim and attacker run `AlgorithmSignMachine` for `bitcoin::crypto::Schnorr` (BIP-340). Attacker receives all other participants' preprocesses first.
2. Attacker computes the partial aggregate nonce commitment `R_rest = Σ (D_j + rho_j·E_j)` over the other signers, then sets their own preprocess commitments to `D_i = generator * d`, `E_i = generator * e` choosing `d, e` such that `D_i + rho_i·E_i = -R_rest`. Commitments serialize fine (non-identity) and pass `Commitments::read`.
3. Each honest validator calls `sign()` → `nonce_sums[0][0] = R_rest + (D_i + rho_i·E_i) = identity` → `IetfSchnorr::sign_share` → `Hram::hram(&identity, &group_key, msg)` → `x(&identity)` → `to_encoded_point(true).x()` returns `None` → `expect("point at infinity")` panics.
4. Result: every honest signer's machine panics; no signature share is produced; the signing round — and any enclosing node process without panic isolation — is aborted.
