### Title
Block gas-limit admission relies on a self-declared, unverified `gas_estimate` field, allowing actual per-block EVM computation to exceed `ConsensusParams.Block.MaxGas` - ([File: app/app.go])

### Summary
`ProcessProposal`'s block-level gas guard, `checkTotalBlockGas`, decides whether to admit a proposed block by summing either `GasWanted` (Cosmos txs) or a transaction-supplied `gas_estimate` (EVM txs) and comparing the sum to `ConsensusParams.Block.MaxGas` [1](#0-0) . The `gas_estimate` value is not derived from consensus-verified real execution: it is either a fully client-declared quantity (equal to the tx's own `Gas()`/gas-limit field when RPC-side simulation is disabled), or a locally-simulated pre-check value baked into the signed transaction bytes. Because nothing at proposal-admission time re-verifies that the declared estimate reflects real execution cost, an adversarial submitter can under-declare `gas_estimate` while their transactions still legally consume up to their full `GasWanted`/`Gas()` limit during actual execution, letting a proposer pack a block whose real aggregate computation greatly exceeds `MaxGas` while passing the block-gas admission check. This mirrors CVE-2017-0887's root cause: a resource quota gate trusting a client-supplied "declared size/cost" header instead of the value actually consumed.

### Finding Description
`checkTotalBlockGas` explicitly documents itself as using "our best estimate" of total gas, and for EVM transactions prefers `decodedTx.GetGasEstimate()` over the real gas limit whenever that estimate is `>= MinGasEVMTx` and `<= gasWanted` [2](#0-1) . The only guard against abuse is an upper bound (`est <= gasWanted`) that stops the estimate from being inflated above the tx's own gas limit — there is no lower bound tying the estimate to the tx's real computational cost. `GasEstimate` is a field carried inside the signed transaction (`Fee.gas_estimate`) [3](#0-2) , and is populated by the RPC layer at submission time: when simulation is disabled it is set to the transaction's own declared `Gas()` (in this specific case not exploitable since it equals `gasWanted`), but when simulation is enabled the value comes from a local `eth_estimateGas`-style simulation run once at submit time [4](#0-3) . A single simulation snapshot can diverge arbitrarily from real gas usage at inclusion time (e.g., state-dependent branches, other transactions' interleaved state changes, or a contract deliberately crafted to behave cheaply under a probe call but expensively under actual execution), and this divergence is never re-checked once the tx is gossiped and reaches `ProcessProposal`. `x/evm/ante/gas.go`'s `GasDecorator` further just copies whatever `tx.GetGasEstimate()` says into `ctx.WithGasEstimate(...)` without any independent recomputation [5](#0-4) . The real, per-transaction gas ceiling enforced during execution is `GasWanted`/`Gas()`, which can be up to `MaxGasWanted`, decoupled from the block-level cap intended by `MaxGas`.

### Impact Explanation
An attacker (or colluding proposer/relay) can submit many EVM transactions whose `gas_estimate` is deliberately understated but whose `Gas()`/`GasWanted` (and hence potential real execution cost) remains high. `checkTotalBlockGas` sums the deflated estimates and admits the block because `totalGas <= MaxGas` looks satisfied, even though real per-tx execution can consume up to each tx's full gas limit. This can push actual block computation well past the intended `MaxGas` ceiling, degrading node processing time for that block and risking block-time delay beyond the network's target interval, and in the worst case validator resource exhaustion/slow processing consistent with the report's accepted "block delay beyond 2.5 seconds" / "validator halt" impact classes. The scope is exactly the kind of self-reported "declared size vs. real consumption" gap that made CVE-2017-0887 exploitable.

### Likelihood Explanation
Reachability is straightforward: any unprivileged EVM transaction sender who controls the RPC node forwarding their transaction (or who submits pre-signed raw transactions with a manipulated `gas_estimate` field via `eth_sendRawTransaction`) can influence this value, since it travels as part of `Fee.gas_estimate` in the signed tx bytes and is trusted verbatim by validators executing `ProcessProposal`. The only constraint enforced is `est <= gasWanted`, which does not prevent understatement. The known-and-tested boundary behavior (`TestExecutorOCCAllowsDeclaredGasSumAboveBlockLimitWhenUsedGasFits` [6](#0-5) ) shows the system already tolerates declared sums diverging from real usage in the *overestimate* direction; the *underestimate* direction analyzed here is not covered by an equivalent safety test in the excerpts reviewed, and no additional re-verification of `gas_estimate` against real execution was found in the code paths inspected.

### Recommendation
Do not admit blocks based on a client-supplied `gas_estimate`; bound `checkTotalBlockGas` accounting strictly by each transaction's real, consensus-enforced ceiling (`GasWanted`/`Gas()`), or require the estimate to be recomputed/verified locally by the proposer/validator (e.g., via local simulation against the proposal's pre-state) rather than trusting the value embedded by the original submitter. If the estimate optimization is kept for mempool prioritization only, it should be explicitly excluded from any consensus-level gas-limit admission decision.

### Proof of Concept
1. Craft an EVM transaction whose `Gas()` (gas limit) is set high, e.g. 20,000,000 (allowing it to actually spend a large amount of gas during execution).
2. Submit it via `eth_sendRawTransaction` on a node running with `enableSimulation=true`, but engineer the contract call so the initial simulation snapshot under-reports usage (e.g., branch on a storage slot that a companion transaction in the same block later flips before this tx executes, driving up its real gas consumption), or, if simulation is disabled, directly construct/sign the tx bytes so the embedded `Fee.gas_estimate` field is a small value (just above `MinGasEVMTx`) while `Gas()` remains large — bypassing RPC-side estimate assignment entirely since the ante `GasDecorator` and `checkTotalBlockGas` both trust the embedded field as-is [5](#0-4) .
3. Repeat for enough transactions such that `sum(gas_estimate) <= MaxGas` but `sum(actual GasUsed during execution)` substantially exceeds `MaxGas`.
4. Observe that `checkTotalBlockGas` admits the proposal [7](#0-6)  while real block execution time/computation exceeds the value the `MaxGas` parameter was meant to cap.
