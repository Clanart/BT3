## Title
Missing enforcement of `allowFileProtocol` in submodule update lets a malicious repo trigger `file://` submodule fetches, enabling arbitrary local file/path read outside the repo - (File: `app/src/lib/git/submodule.ts`)

### Summary
The Quantstamp finding is a classic "missing caller/access-control check" bug: `SapTestToken.releaseTokens()` trusted that it would only ever be invoked through `SapienRewards`, but nothing in the function itself enforced that assumption, so any caller could invoke it directly. The Desktop analog to search for is the same *broken invariant* pattern: a privileged/dangerous operation (spawning `git` against a URL taken from repository-controlled data, i.e. `.gitmodules`) that is supposed to only be reachable under a trusted, restricted condition (`allowFileProtocol` explicitly enabled by the app), but where the code path that actually shells out to `git submodule update`/`git clone` does not itself re-validate that the submodule URL is safe before use.

### Finding Description
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` parameter documented as controlling "whether to allow file:// protocol for submodules" [1](#0-0) . This is the same shape of problem as the token-release bug: the *intent* is that only a trusted caller path is allowed to permit `file://` submodules, but the enforcement of that intent lives in the caller rather than being checked/derived from the actual submodule URLs that Git resolves from the attacker-controlled `.gitmodules` file. `.gitmodules` (and `submodule.<name>.url` config entries, which are read directly from repository content, e.g. `getConfigValue(repository, 'submodule.${path}.url', true)`) is fully attacker-controlled content of a cloned/fetched repository [2](#0-1) . If any call site fails to correctly gate `allowFileProtocol` to `false` for untrusted/attacker-supplied repositories (the exact analog of forgetting the "only `SapienRewards` may call `releaseTokens()`" check), Git will happily fetch a submodule via `file://<absolute-path>`, letting a malicious repository pull in — and thus stage a local read of — arbitrary files/directories on the victim's machine that are reachable from the account running Desktop, entirely outside the cloned repository's directory tree.

This mirrors the report's underlying flaw exactly: a sensitive operation (`releaseTokens` / spawning git against a submodule URL) is documented/expected to be constrained to a specific trusted context, but the function that actually performs the sensitive action does not itself verify that constraint — it relies on every caller getting it right.

### Impact Explanation
If `allowFileProtocol` is not (or cannot be) reliably enforced to `false` for all code paths that clone/fetch/update submodules from untrusted third-party repositories, an attacker who controls a repository (or a PR/fork a victim opens with Desktop) can define a submodule with a `file://` URL pointing at sensitive local paths (e.g. `~/.ssh`, `~/.aws`, corporate config directories). When Desktop runs `git submodule update --init --recursive` (or equivalent) against that repository, Git would copy the contents of that local path into the submodule's working tree inside the (otherwise sandboxed) cloned repository, which the user might then inadvertently commit/push or otherwise expose — satisfying the "read outside the repo" / "silent corruption of what the user commits" impact classes named in the report's Valid Impact section.

### Likelihood Explanation
Confidence here is limited: I was only able to confirm the presence and documented intent of the `allowFileProtocol` parameter and the fact that submodule URLs are sourced from repository-controlled `.gitmodules`/git-config data; the file read was truncated before I could inspect the full body of `updateSubmodulesAfterOperation` and every call site that decides the value passed for `allowFileProtocol` (e.g. whether it's hardcoded `false` for "clone repository from URL" flows vs. user-added local repos). Without seeing every call site, I cannot definitively confirm whether the gate is actually missing/bypassable in current code, only that the pattern (a security-relevant boolean flag threaded through, rather than enforced at the point of use) is structurally the same class of bug as the reported missing access control, and is a well-known real-world Git attack vector (CVE-class "malicious submodule file:// URL" issues) that Desktop must correctly gate on every entry point.

### Recommendation
- Enumerate every call site of `updateSubmodulesAfterOperation` and confirm `allowFileProtocol` is hardcoded to `false` whenever operating on a repository/URL that did not originate from a fully trusted, user-initiated local action.
- Rather than trusting each caller to pass the correct flag, enforce the restriction inside `submodule.ts` itself (defense in depth) by validating parsed submodule URLs and rejecting `file://` (and any protocol not in an explicit allow-list) unless a single, centrally audited trust check confirms the operation is safe — analogous to adding the caller check directly inside `SapTestToken.releaseTokens()` rather than relying on `SapienRewards` alone.
- Add regression tests (mirroring `app/test/unit/git/clone-test.ts`'s sensitive-path tests) that assert `file://` submodule URLs are rejected by default for fetch/clone/pull operations against untrusted remotes.

### Proof of Concept
Not fully verifiable from the indexed code alone (the complete body of `updateSubmodulesAfterOperation` and all its callers were not available before the tool budget was exhausted). A conceptual PoC would be:
1. Attacker creates a public repository with a `.gitmodules` entry: `[submodule "x"] path = x url = file:///Users/victim/.ssh`.
2. Victim clones or opens this repository in GitHub Desktop and Desktop runs its submodule-update flow.
3. If any reachable call path passes `allowFileProtocol: true` (or omits the check) for this untrusted clone, `git submodule update --init` copies the victim's `~/.ssh` directory contents into the submodule path inside the repo working tree, which the user could then diff, view, or accidentally commit/push.

Given the incomplete visibility into `submodule.ts`'s full implementation and call graph, I recommend a Devin session with full repository access to confirm whether `allowFileProtocol` is actually gated safely at every call site before treating this as a confirmed (rather than suspected) vulnerability.
