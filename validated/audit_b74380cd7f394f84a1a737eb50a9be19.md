### Title
Unauthorized third parties can force premature MGP forfeiture for any vlMGP holder via `multiclaimFor` - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie.multiclaimFor()` has no access control restricting who may trigger a reward claim on behalf of another account. Any external address can call it for an arbitrary victim's `_stakingToken` positions, including the `vlmgp` pool. When the claimed pool is `vlmgp`, the claim path routes accrued MGP through `vlMGPBaseRewarder.queueMGP`, which computes a time-dependent forfeiture (`_calExpireForfeit`) based on the victim's *current* cooldown/unlock state. Because any unprivileged wallet can force this calculation to execute at a moment of the attacker's choosing, an attacker can force-realize a victim's MGP harvest at the earliest, least favorable possible time, permanently destroying (forfeiting) yield the victim would otherwise have kept had they controlled the timing of their own claim.

### Finding Description
`multiclaimFor` is callable by anyone with no ownership or manager check: [1](#0-0) 

It forwards to the internal `_multiClaim`, which for the `vlmgp` staking token accumulates `vlMGPPoolAmount` and sends it via `_sendMGPForVlMGPPool`: [2](#0-1) [3](#0-2) 

`_sendMGPForVlMGPPool` calls `vlMGPBaseRewarder.queueMGP(_amount, _account, _receiver)`, which is only restricted to `onlyManager` (MasterMagpie is a manager), not to the account owner: [4](#0-3) 

`queueMGP` computes `_calExpireForfeit(_account, _amount)` using the account's live vlMGP lock/cooldown state, queuing the forfeited portion back into the reward pool (redistributed to other stakers) and permanently zeroing that share for the victim: [5](#0-4) 

The forfeiture percentage is directly a function of elapsed cooldown time (`unlockFactor`), decreasing (i.e., less forfeited) the longer the account waits before claiming: [6](#0-5) 

Normally, only the account owner decides when to trigger a claim, so they can choose to wait until their unlock factor is favorable before realizing MGP rewards through the `vlmgp` pool. Because `multiclaimFor` has no `onlyAccountOrManager`/`onlySelf` restriction, any wallet can call it against any victim at any time (e.g., immediately after the victim starts an unlock via `VLMGP.startUnlock`, which itself already triggers a forced `multiclaimFor` at line `VLMGP.sol:287`, so this griefing can also be repeated afterward), locking in the maximum possible forfeiture and permanently transferring that forfeited MGP amount into the shared reward pool for other stakers. This is directly analogous to the Pendle `claimRewards()` finding: a claim/harvest entry point lacking access control lets an unprivileged caller force reward realization for someone else's holdings at an attacker-chosen time, but here concretely causing permanent loss of the victim's yield.

### Impact Explanation
The victim permanently loses a portion of their earned MGP (forfeited to the shared reward pool) because an unauthorized third party could force the claim/forfeiture calculation to run at a time unfavorable to the victim, rather than when the victim would have chosen to claim. This is a permanent, protocol-native loss of unclaimed yield for the affected user, matching the "theft or permanent freezing of unclaimed yield" impact class, and is repeatable against any vlMGP holder at zero cost to the attacker.

### Likelihood Explanation
Likelihood is high: `multiclaimFor` is a fully public, unauthenticated external function requiring only the victim's staking token addresses (publicly known, e.g. `address(vlmgp)`) and the victim's address — both trivially obtainable on-chain. No special timing, race condition, or privileged role is required; any wallet can call it directly against any vlMGP holder who currently has an active unlock/cooldown slot.

### Recommendation
Restrict `multiclaimFor` (and any other claim-on-behalf path that can force realization of forfeitable rewards, e.g., ensure `multiclaimOnBehalf`'s `_onlyCompounder` restriction pattern is consistently applied) so that only the account owner (`msg.sender == _account`) or an explicitly authorized compounder/manager contract can trigger claims that affect that account's forfeiture calculations.

### Proof of Concept
1. Victim locks MGP in `VLMGP` and later calls `startUnlock` to begin a cooldown slot; at this point their `getRewardablePercentWAD` is at its lowest (freshly started cooldown), so `_calExpireForfeit` would forfeit the maximum share of any pending `vlmgp`-pool MGP reward.
2. Immediately after, an attacker (any wallet, no permissions needed) calls `MasterMagpie.multiclaimFor([address(vlmgp)], [[]], victim)`.
3. This routes through `_multiClaim` → `_sendMGPForVlMGPPool` → `vlMGPBaseRewarder.queueMGP(amount, victim, victim)`, which computes `_calExpireForfeit` at the current (unfavorable) timestamp and permanently forfeits the maximum penalty amount into the shared reward pool instead of letting the victim wait for their unlock factor to improve.
4. The victim receives less MGP than they would have if they had controlled the timing of their own claim, and the forfeited amount is irreversibly redistributed to other stakers via `_queueNewRewardsWithoutTransfer`.

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
