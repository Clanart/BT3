<title>Unbounded buffer read in CLVM canonical-encoding check crashes mempool validation - (File: chia/full_node/mempool_manager.py)</title>

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` walk an attacker-supplied CLVM byte buffer and increment an `offset` index while decoding multi-byte atom length prefixes, but never verify that `offset` stays within `len(clvm_buffer)` before indexing into it. This is the same bug class as CVE-2019-13619 (Wireshark ASN.1 BER dissector "improperly restricting buffer increments" causing an out-of-bounds read/crash): a variable-length-prefix decoder increments a cursor based on attacker-controlled length fields without bounding it to the buffer size.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the leading byte at `offset` to determine how many additional prefix bytes (`prefix_len`, 0–5) encode the atom length, then loops: [1](#0-0) 
```
atom_len = b & mask
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]
return 1 + prefix_len + atom_len, atom_len >= min_value
```
There is no check that `offset` (after incrementing) is `< len(clvm_buffer)` before `clvm_buffer[offset]` is evaluated. If the trailing bytes of the buffer look like the start of a multi-byte length prefix (e.g. end in `0xFC`, which claims 5 additional length bytes) but the buffer doesn't actually contain that many trailing bytes, this line raises an uncaught `IndexError`.

`is_clvm_canonical()` also fails to bound-check before its own top-level byte read: [2](#0-1) 
It also never validates that the *body* of a claimed atom (the `atom_len` bytes after the prefix) actually exists in the buffer — it just advances `offset += atom_len` and loops back to `clvm_buffer[offset]`, which will similarly raise `IndexError` if `atom_len` overruns the buffer.

This function is invoked directly on attacker-controlled spend-bundle bytes inside `MempoolManager.validate_spend_bundle()`: [3](#0-2) 
```
if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(
    bytes(coin_spend.solution)
):
    return Err.INVALID_COIN_SOLUTION, None, []
```
`validate_spend_bundle()` is called from `add_spend_bundle()` [4](#0-3) , which is the standard admission path for any spend bundle submitted by an unprivileged peer, wallet, or RPC caller.

Because CLVM's serialization format allows trailing bytes after the top-level object has been fully parsed (Rust's `run_chia_program`/`validate_clvm_and_signature` only needs to successfully decode the top-level expression and does not require the buffer to be exhausted — this is exactly why `is_clvm_canonical` has a final "no trailing garbage" check at the end of the function), an attacker can craft a `puzzle_reveal` or `solution` blob consisting of: (1) a normal, fully valid CLVM program/solution that executes and passes signature/condition validation, followed by (2) a short trailing "garbage" tail engineered to look like a truncated multi-byte atom length prefix (e.g. a single `0xFC` byte at the very end of the buffer, or fewer bytes than the claimed prefix length). CLVM execution/signature validation ignores the trailing bytes and succeeds; only afterward, in the canonical-encoding check, `is_clvm_canonical`/`is_atom_canonical` attempt to walk through those trailing bytes and index past the end of the buffer.

### Impact Explanation
An `IndexError` raised from `is_atom_canonical`/`is_clvm_canonical` is not a `ValueError`/`ValidationError`, which is the exception type explicitly expected and converted by the surrounding mempool admission code paths (see `pre_validate_spendbundle`'s `except ValueError` handling [5](#0-4) ). An unexpected exception type propagating out of `validate_spend_bundle`/`add_spend_bundle` during transaction admission is consistent with the "spend-triggered transaction-processing halt" impact class: a single submitted spend bundle can throw an uncaught exception in the coroutine/task handling that mempool addition, disrupting processing of that transaction-add request (and, depending on how far up the call stack the exception is unhandled, potentially the full-node's transaction-handling task). This matches the CVE's crash impact (`AC:L`, `PR:N`, `UI:N`, unprivileged, network/spend-bundle-reachable, availability-impacting).

### Likelihood Explanation
Medium-High. Constructing the trailing "malformed atom prefix" bytes only requires appending a few extra bytes after a normal, valid, well-formed puzzle reveal/solution — no special privileges, network position, or prior state are required. The check is reached on the ordinary mempool-admission path (`add_spend_bundle` → `validate_spend_bundle`) for every incoming spend bundle, whether via full-node p2p tx gossip, wallet push, or RPC `push_tx`. I was not able to fully confirm (due to iteration limits) whether the top-level caller (`FullNode.add_transaction` / RPC handler) wraps this call in a broad `except Exception` that would degrade the crash to just a failed transaction rather than a broader processing halt — this needs to be verified against `chia/full_node/full_node.py`'s `add_transaction()` exception handling to establish the exact blast radius.

### Recommendation
In `is_atom_canonical()`, bound-check `offset` against `len(clvm_buffer)` before every index access when reading multi-byte length-prefix bytes, and return a definitive "not canonical"/error result instead of indexing out of range. In `is_clvm_canonical()`, similarly bound-check `offset` before reading `clvm_buffer[offset]` at the top of the loop, and validate that the atom body (`atom_len` bytes) actually fits within the remaining buffer before advancing `offset` past it. Consider making these functions return `False` on any structurally invalid/truncated input rather than raising, and audit all callers to ensure only well-defined exception types (`ValueError`/`ValidationError`) can escape mempool admission code.

### Proof of Concept
1. Construct a normal, valid CLVM puzzle reveal and solution that will pass `validate_clvm_and_signature` (e.g. the identity puzzle with a simple solution).
2. Append a single trailing byte `0xFC` (or `0xFE`-adjacent multi-byte-prefix marker) to the end of the solution buffer, without providing the 5 additional bytes it claims to need — i.e. make the buffer end immediately after this marker byte.
3. Submit this as a `SpendBundle`'s `coin_spend.solution` via `push_tx`/mempool submission. CLVM execution parses and stops at the original valid top-level object, ignoring the trailing byte, so `validate_clvm_and_signature` succeeds.
4. When `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` at `chia/full_node/mempool_manager.py:723`, the parser walks to the trailing `0xFC` byte and calls `is_atom_canonical()`, which attempts to read 5 more bytes past the end of the buffer via `clvm_buffer[offset]`, raising an uncaught `IndexError` instead of the expected `Err.INVALID_COIN_SOLUTION`/`ValidationError`.
