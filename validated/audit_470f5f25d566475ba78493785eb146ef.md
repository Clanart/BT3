### Title
`compound()` sweeps the entire contract token balance regardless of the caller's own claim, allowing theft of other users'/residual reward funds - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` calls `multiclaimOnBehalf` for the caller's own stake, but the subsequent distribution loop over the registered `rewards` array is not gated on what that particular call actually produced. It unconditionally reads `IERC20(rewards[i].tokenAddress).balanceOf(address(this))` and forwards/locks/converts *the entire contract balance* to `msg.sender`, even when the caller supplied `_lps`/`_rewards` for staking tokens they hold zero stake in.

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0)  — this is properly user-scoped inside `_multiClaim`, since MasterMagpie indexes `userInfo[_stakingToken][_user]` by the caller's own address, so a caller with zero stake in `_lps` legitimately claims zero MGP/base rewards for those tokens [2](#0-1) .

However, the second loop in `compound()`, which distributes the "compoundable" registered rewards (convert/lock/deposit/transfer), is completely decoupled from `_lps`/`_rewards`. It iterates the contract-level `rewards` array (configured by the owner, not scoped per call) and unconditionally sweeps whatever `IERC20(_tokenAddress).balanceOf(address(this))` currently is: [3](#0-2) 

There is no "before/after" delta computation tied to the current call's `multiclaimOnBehalf` result, and no check that `receivedBalance` corresponds to value the *caller* actually generated. Any residual balance sitting in the contract — from rounding leftovers of a prior user's `convertFor`/`lockFor`/`depositFor` call (which only approves/consumes part of `receivedBalance`), from a fee-on-transfer or rebasing reward token, or from any third party accidentally/intentionally sending the reward token directly to the `ManualCompound` contract address — will be handed to whoever next calls `compound()`, even with `_lps = []`/`_rewards = []` (zero own stake, zero own claim).

The same unconditional-balance pattern also affects the first "send non-compoundable reward back to caller" loop, but that one is at least scoped to tokens the caller explicitly listed in `_rewards[i][j]` [4](#0-3) ; the second loop (lines 139-160) has no such scoping at all and is the primary issue.

Existing guards do not stop this: `_multiClaim` in MasterMagpie has `nonReentrant`, preventing reentrant claims, but that only protects the claim step, not the unconditional sweep in `ManualCompound`. There is no modifier restricting who can call `compound()` — it is fully public/external with no role check.

### Impact Explanation
Any unprivileged EOA can call `compound()` with staking tokens they have no stake in (or empty arrays) and drain any reward-token balance currently sitting in the `ManualCompound` contract to themselves via transfer, or route it to a convertor/locker/helper "for" themselves. This is a direct theft of funds that do not belong to the caller — matching Critical: Direct theft of user funds, since legitimate users' unclaimed/residual reward balances held transiently in this contract can be permanently redirected to an attacker.

### Likelihood Explanation
Feasibility depends on there being a nonzero balance of a `rewards[i].tokenAddress` sitting in `ManualCompound` at the time of the attacker's call. This can occur from: (a) rounding/partial consumption in `IConverter.convertFor`/`ILocker.lockFor`/`ISimpleHelper.depositFor` leaving unspent approved tokens behind, (b) fee-on-transfer or rebasing reward tokens, or (c) any direct transfer to the contract. The attack itself requires no capital, no special role, and is trivially repeatable — the attacker only needs to front-run/observe a moment when residual balance exists and call `compound()` with dummy `_lps`/`_rewards`.

### Recommendation
Scope the reward distribution to the value produced by the current call only: snapshot `IERC20(_tokenAddress).balanceOf(address(this))` immediately before calling `multiclaimOnBehalf`, then compute `receivedBalance = balanceOf(after) - balanceOf(before)` for each reward token, instead of using the raw absolute balance. Alternatively, have `multiclaimOnBehalf`/`_harvestBaseRewarder` return the exact amounts claimed for the caller and use those values directly instead of re-reading `balanceOf(address(this))`. Additionally, sweep any truly unattributed residual dust only via an owner-only rescue function, not through the public `compound()` path.

### Proof of Concept
Hardhat/Foundry plan:
1. Deploy `MasterMagpie`, `ManualCompound`, and register a reward token/convertor pair in `rewards`.
2. Have a legitimate user (victim) stake and call `compound()` such that a `convertFor` leaves 1 wei (or a deliberately crafted fee-on-transfer amount) unspent in `ManualCompound` (simulate via a mock convertor that only pulls `receivedBalance - 1`).
3. As an unprivileged attacker with zero stake in any pool, call `compound(_lps=[unrelatedOrEmptyLp], _rewards=[[]], _convertRatio=0, _minRec=0, _lockMgp=false)`.
4. Assert: `multiclaimOnBehalf` yields zero new tokens for the attacker's own stake, yet `IERC20(rewardToken).balanceOf(attacker)` increases by the residual amount left over from the victim's earlier call, proving the sweep loop distributed value the attacker did not generate.
