### Title
Path-boundary check in `resolveWithin` uses unanchored `startsWith`, allowing sibling-directory escape via crafted "Open in Desktop" deep link - (File: app/src/lib/path.ts)

### Summary
`resolveWithin` (and its `posix`/`win32` variants) is the app's core safety guard for keeping file operations confined to a repository root. It resolves a path and then checks containment with `realResolved.startsWith(realRoot)`. This check is not anchored on a path-separator boundary, so any resolved path whose string happens to begin with the same characters as the root path — including an unrelated **sibling** directory (e.g. root `/Users/victim/repo` vs. target `/Users/victim/repo-private`) — is incorrectly treated as "inside" the root.

### Finding Description
`_resolveWithin` in [1](#0-0)  computes:
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```
There is no check that `realResolved === realRoot` or that the next character after the shared prefix is a path separator. Consequently a target path like `/Users/victim/repo-evil/secret.txt` passes the check against a root of `/Users/victim/repo`, because the string `"repo-evil"` starts with `"repo"`.

This guard is consumed by `openRepositoryFromUrl` in the URL-handler path of the dispatcher, which processes the `filepath` parameter from an `x-github-client://openRepo` deep link: [2](#0-1) 
Absolute `filepath` values are explicitly rejected (`isAbsolute(filepath)` check), but *relative* traversal segments are not rejected — they are only expected to be constrained by `resolveWithin`. A relative filepath such as `../repo-private/id_rsa` resolves to an absolute path outside the intended repository, and because GitHub Desktop commonly clones multiple repositories as siblings under the same base folder with related/prefixed names (e.g. `myproject`, `myproject-private`, `myproject2`), the broken prefix check will accept the escape whenever a sibling directory name happens to share the root directory's name as a prefix.

The same flawed primitive (`resolveWithin`) is reused as the sole boundary guard for other attacker-influenced writes, e.g. Copilot AI conflict-resolution file writes in [3](#0-2)  and conflict content reads in [4](#0-3) , so any future or additional caller that forwards attacker-influenced paths through this helper inherits the same weak boundary check.

### Impact Explanation
An attacker who gets a victim to click a crafted GitHub Desktop deep link can direct `shell.showItemInFolder` (or, for other resolveWithin call sites, a file read/write) to a directory that is *not* the intended repository but merely shares a name prefix with it. This breaks the invariant "resolved path is contained in the repository root" the same way the reported contract bug broke the invariant "claimedInterest equals only newly issued interest" — a security-relevant accounting/containment check silently produces a value that looks valid but is not, and the code downstream (file reveal / potential write path in other callers) trusts it. This can result in disclosure of file existence/location outside the intended repo, and in any call site that performs writes (not just reveals) through this same helper, unauthorized file writes outside the repo boundary.

### Likelihood Explanation
Exploitation requires: (1) the victim has a directory structure where a sibling folder name is a superstring of the current repository's folder name (common, since Desktop clones many repos into one base folder with related/incremental names), and (2) the victim clicks a malicious `x-github-client://openRepo/...&filepath=...` deep link. No local access, admin rights, or prior compromise is needed — only a crafted link click, which matches the accepted "link/deep link the user clicks" primitive. The likelihood of a suitably-named sibling directory existing is environment-dependent, which is the main mitigating factor.

### Recommendation
Anchor the containment check on a path-separator boundary instead of a raw string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the fix once in `_resolveWithin` in `app/src/lib/path.ts` so all call sites (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) are corrected simultaneously.

### Proof of Concept
1. Victim has two repositories cloned as siblings: `/Users/victim/Documents/GitHub/myproject` and `/Users/victim/Documents/GitHub/myproject-private`.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/attacker/myproject?filepath=..%2Fmyproject-private%2Fsecrets.txt`.
3. Desktop's `openRepositoryFromUrl` (app/src/ui/dispatcher/dispatcher.ts) opens/clones `myproject`, sees `filepath` is not absolute, and calls `resolveWithin(repository.path, '../myproject-private/secrets.txt')`.
4. Inside `_resolveWithin` (app/src/lib/path.ts), `realResolved` = `.../myproject-private/secrets.txt`, `realRoot` = `.../myproject`; `realResolved.startsWith(realRoot)` evaluates `true` because `"myproject-private"` starts with `"myproject"`.
5. The function returns the resolved path instead of `null`, and `shell.showItemInFolder(resolved)` reveals a file belonging to a different repository, confirming the boundary check is bypassed.

Note: I was not able to fully trace every other consumer of `resolveWithin` across the codebase in the time available (e.g., worktree or LFS write paths) — a full audit of all call sites of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` is recommended to confirm whether any of them perform writes (not just reveals) with attacker-reachable relative segments, which would raise this from an information-disclosure primitive to a file-write primitive.
