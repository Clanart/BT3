### Title
OP_RETURN data output excluded from weight/vsize calculation, producing transactions with an under-charged fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight (and therefore the required fee) using only the payment outputs, never accounting for the `OP_RETURN` output that is appended when `data` is supplied. The resulting transaction is larger than the size used to derive `needed_fee`, so it pays a lower effective fee rate than the caller requested — in edge cases below the configured minimum and below Bitcoin's minimum relay fee.

### Finding Description
`SignableTransaction::new` builds `tx_outs` first from `payments`, then pushes an `OP_RETURN` output carrying the attacker-influenceable `data` field:

```rust
// networks/bitcoin/src/wallet/send.rs
193|    if let Some(data) = data {
194|      tx_outs.push(TxOut {
195|        value: Amount::ZERO,
196|        script_pubkey: ScriptBuf::new_op_return(...)
199|    }
```

The fee derivation, however, calls `calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing `payments`, not `tx_outs` — so the OP_RETURN output's weight is never included:

```rust
204|    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
205|
206|    let mut needed_fee = fee_per_vbyte * vbytes;
```

The same omission occurs on the change path (`calculate_weight_vbytes(..., payments, Some(&change))` at line 226), and the minimum-relay-fee check at line 211 uses the under-counted `vbytes`. The change-amount computation at line 228 (`input_sat - (payment_sat + fee_with_change)`) then locks in the too-low fee: the actual fee paid is `input_sat - sum(tx_outs)`, which equals `needed_fee` computed for a smaller transaction.

This is the analog of the CVE's memory-corruption class mapped onto Serai's real shape: an unhandled case where a field (`data`) contributes to the produced object but is omitted from the size bound used to charge for it, reachable purely from untrusted input (the `data` argument originates from user-supplied `InInstruction` data, and `ReceivedOutput`s come from scanned Bitcoin transactions).

### Impact Explanation
A `SignableTransaction` carrying an `OP_RETURN` payload pays a fee rate strictly lower than `fee_per_vbyte` — by `fee_per_vbyte * (OP_RETURN output weight in vbytes)` (roughly `(11 + data.len())` vbytes, up to ~91 vbytes for the allowed 80 bytes of data). When `fee_per_vbyte` is near the minimum, the produced transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` on its true size and be rejected by relay/mining, while `needed_fee()` and the `TooLowFee` guard at line 211 both report success. The threshold-signed transaction is then broadcast with funds committed to inputs that cannot confirm — payments are locked in an unconfirmable transaction and the consumed `ReceivedOutput`s cannot be re-spent by a replacement until the invalid one is abandoned. This is a real discrepancy between the fee the scheduler asked for and what the signed transaction actually delivers, corrupting the economic invariant the fee math is meant to guarantee.

### Likelihood Explanation
Triggering requires a `SignableTransaction` with `data` set (InInstruction-driven withdrawals/that attach data), plus a fee rate low enough that the ~few-hundred-sat shortfall matters. The defect is deterministic — every transaction carrying a `data` payload under-charges by exactly the omitted weight — but whether it causes a non-relayable transaction depends on the configured fee rate and mempool conditions. An unprivileged user who can influence the `data` field chooses the worst case (80 bytes) to maximize the fee shortfall.

### Recommendation
Pass the complete output list — including the OP_RETURN output — into `calculate_weight_vbytes` instead of `payments`. Concretely, construct `tx_outs` (payments + OP_RETURN + provisional change) first, then compute weight over `tx_outs`, and recompute when the change output is added. Alternatively, add the known size of `ScriptBuf::new_op_return(data)` output (~`8 + 1 + script_len` bytes serialized) to the weight estimate.

// Using networks/bitcoin/src/wallet/send.rs logic:
// inputs: one ReceivedOutput worth 100_000 sats
// payments: [(p2tr_script, 90_000)]
// data: Some(vec![0u8; 80])
// change: Some(change_script)
// fee_per_vbyte: 1

// calculate_weight_vbytes is invoked with `payments` only:
//   vbytes = size(inputs=1, outputs=[payment])           // missing OP_RETURN
// The returned SignableTransaction's tx has outputs [payment, OP_RETURN, change],
// which is ~91 vbytes heavier than `vbytes`.

// Actual fee paid = input_sat - payment_sat - change = needed_fee (= vbytes * 1),
// so the real feerate is needed_fee / (vbytes + ~91) < 1 sat/vbyte.
// The TooLowFee check at line 211 used the under-counted vbytes, so it passes
// even though the true transaction is below the minimum relay feerate.
