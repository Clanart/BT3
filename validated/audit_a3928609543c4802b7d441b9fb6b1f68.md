## Title
Divergent conflict-marker parsers between context extraction and resolution reassembly let a crafted file corrupt or silently drop merge content in Copilot conflict resolution — (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Sherlock report's root cause is a return value (`amountMinted`) that can silently be a degenerate/zero result and is consumed without validation, letting reserve state and minted-token state drift apart. The GitHub Desktop analog is a *pair of independent parsers* that are both derived from the same source of truth (a conflicted file's `<<<<<<<`/`=======`/`>>>>>>>` markers) but are not guaranteed to agree, and whose disagreement is not detected by the one guard (`validateResolutionPaths`) that exists to catch it — resulting in resolved content being spliced into the wrong hunk, or dropped entirely, when the user accepts an AI-suggested merge-conflict resolution.

### Finding Description
`extractConflictHunks` in [1](#0-0)  walks a conflicted file to build the hunk list sent to Copilot. If it encounters an opening `<<<<<<<` marker for which no closing `>>>>>>>` is ever found, it treats that hunk as malformed, drops it via `continue`, and — critically — because the inner scanning loop already advanced `i` to end-of-file while searching for the missing closer, extraction of the file effectively stops there: [2](#0-1) 

Later, `reassembleResolvedFile` in [3](#0-2)  re-parses the *same* raw file content from scratch, using its own independent lookahead logic: [4](#0-3) 

This lookahead does not require the `=======` it finds to "belong" to the `<<<<<<<` it started from — it simply records `hasSeparator = true` on the first separator-looking line and keeps scanning until it finds *any* subsequent `>>>>>>>`. So a `<<<<<<<`-looking line with no true closing marker before EOF is parsed by `extractConflictHunks` as "malformed → drop, stop scanning further hunks in this file," while `reassembleResolvedFile`, given the exact same bytes, can happily walk past an intervening real `=======`/`>>>>>>>` pair (or misidentify block boundaries after the divergence point) and treat it as one or more *different* well-formed blocks than the extraction phase saw.

The one guard designed to prevent a hunk-count mismatch, `validateResolutionPaths`, only compares the model's returned hunk count against `expectedHunkCounts` — which is itself derived from `extractConflictHunks`, not from `reassembleResolvedFile`'s independent walk: [5](#0-4) 

Because both the "expected count" and the model's hunk list trace back to `extractConflictHunks`, this check can never detect that `reassembleResolvedFile` will enumerate a different number/ordering of marker blocks over the identical raw content at splice time. When `reassembleResolvedFile` finds more marker blocks than there are entries in `hunkResolutions`, the excess block's `<<<<<<<...>>>>>>>` region is silently deleted from the output (the `if (hunkIndex < hunkResolutions.length)` guard means nothing is pushed for it), rather than either failing loudly or leaving the markers intact: [6](#0-5) 

That reassembled content is written to disk and staged without further diffing against the original once the user clicks "Continue Merge": [7](#0-6) 

The existing guards — path traversal checks (`resolveWithin`), the "still contains conflict markers" regex check in `parseCopilotConflictResolution`, and `validateResolutionPaths`'s hunk-count check — all operate on values derived from a single parse of the file and therefore cannot catch a cross-parser disagreement about how many/which marker blocks exist in that same file.

### Impact Explanation
This falls squarely in the requested impact category of "silent corruption of what the user commits or pushes." A victim who merges/rebases/cherry-picks a branch supplied by an attacker (e.g., a malicious PR or fetched remote branch) and then uses the "Resolve with Copilot" feature can end up committing a file with entire code regions silently deleted or misattributed, with no error surfaced — the operation reports success and the mismatched/truncated content is staged and can be pushed. Since the attacker only needs to control the *content of a file that will conflict* (not the model or the app), this requires no elevated privileges beyond normal contribution to a repository the user merges from.

### Likelihood Explanation
This requires a specific but reachable precondition: the attacker's branch must contain, in a file that will also have a real merge conflict, a `<<<<<<<`-shaped line with no genuine matching `=======`/`>>>>>>>` closing pair before end-of-file (e.g. literal conflict-marker-like text inside a lockfile, generated file, code sample, or diff/patch content committed to the repo). This is a realistic scenario for auto-generated files, vendored diffs, or files that document/contain git conflict markers as literal text. It also depends on the user opting into the AI-assisted conflict resolution flow, which is an explicit, but ordinary, user action (clicking "Resolve with Copilot" then "Continue Merge") — not an unnatural step.

### Recommendation
Do not maintain two independently-implemented marker parsers over the same file. `reassembleResolvedFile` should reuse `extractConflictHunks`'s exact same walk (or the hunk boundaries it produced) to locate splice points, rather than re-deriving block boundaries with separate regex/lookahead logic. At minimum, `reassembleResolvedFile` should assert that the number of marker blocks it recognizes on the raw content equals `hunkResolutions.length` and throw a `CopilotValidationError` (rather than silently dropping content) on any mismatch, and `extractConflictHunks` should never silently truncate hunk discovery when it hits a malformed marker — it should either flag the whole file as skipped/unresolvable or recover by resuming the scan.

### Proof of Concept
1. Attacker adds a file, e.g. `notes.md`, to a branch, containing a line beginning with `<<<<<<< ` (7 `<` characters) as literal prose (e.g., documenting git conflict-marker syntax) with no matching `=======`/`>>>>>>>` following it anywhere else in that section, followed later in the file by a region that will become a genuine two-way conflict when merged (its own real `<<<<<<<`/`=======`/`>>>>>>>` block).
2. Victim merges the attacker's branch; git reports `notes.md` as conflicted with markers written to disk exactly as committed plus the real conflict block inserted by git.
3. `buildConflictContext` → `extractConflictHunks` ( [8](#0-7) ) scans from the attacker's fake `<<<<<<<` line, never finds its true closing `>>>>>>>` before EOF (or misattributes the real conflict's `=======`/`>>>>>>>` to it), and either drops the hunk or produces exactly one merged/garbled hunk for the file — undercounting relative to the real, independent conflict block(s) actually present.
4. Copilot resolves the (miscounted) hunk(s); `validateResolutionPaths` passes because it only compares against the same undercount from step 3.
5. `reassembleResolvedFile` ( [4](#0-3) ) re-walks the raw file independently, finds a different number of well-formed marker blocks than `hunkResolutions` has entries, and for any block beyond `hunkResolutions.length` silently omits its content from the reassembled output.
6. `_applyCopilotConflictResolutions` writes this corrupted content to disk and stages it ( [9](#0-8) ); the user commits/pushes the truncated/misassembled file believing the merge was resolved correctly.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

    // The ours marker line is at oursStart - 1
    const markerStart = oursStart - 1
    const contextStart = Math.max(0, markerStart - contextLines)
    const contextEnd = Math.min(lines.length - 1, hunkEnd + contextLines)

    // Clamp context to not include conflict markers from adjacent hunks
    const contextBeforeLines: Array<string> = []
    for (let j = markerStart - 1; j >= contextStart; j--) {
      if (isConflictMarker(lines[j])) {
        break
      }
      contextBeforeLines.unshift(lines[j])
    }

    const contextAfterLines: Array<string> = []
    for (let j = hunkEnd + 1; j <= contextEnd; j++) {
      if (isConflictMarker(lines[j])) {
        break
      }
      contextAfterLines.push(lines[j])
    }

    const contextBefore = contextBeforeLines.join('\n')
    const contextAfter = contextAfterLines.join('\n')

    hunks.push({
      oursContent: oursLines.join('\n'),
      theirsContent: theirsLines.join('\n'),
      baseContent: hasBase ? baseLines.join('\n') : null,
      contextBefore,
      contextAfter,
    })
  }

  return hunks
}

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
