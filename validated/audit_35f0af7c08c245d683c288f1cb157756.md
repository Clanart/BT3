## Analysis Summary

The external report's core pattern is: **a parsing routine handles the common case (single occurrence) but silently fails to validate/handle an edge case, and no guard catches the gap** — leading to security-relevant items (withdrawals) being processed incorrectly.

Searching the Desktop codebase for an analogous "trusted parser is inconsistent in what it validates" pattern in an attacker-reachable surface (deep links), I found `parseAppURL` in `app/src/lib/parse-app-url.ts`.

### Title
Unsanitized `filepath` query parameter in `openRepo` deep link allows path traversal outside the cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates the `branch` and `pr` query-string parameters of an `openRepo` deep link with strict regexes/character checks before returning them, but the `filepath` parameter is extracted with `getQueryStringValue` and passed through completely unvalidated.

### Finding Description
`parseAppURL` is the entry point for handling `x-github-client://openRepo/...` and similar protocol URLs, invoked from `handleAppURL` in `app/src/main-process/main.ts` for both macOS `open-url` events and Windows `--protocol-launcher` command-line args [1](#0-0) . Inside `parseAppURL`, for the `openrepo` action, `pr` is checked against `/^\d+$/`, `branch` is checked against `/^pr\/\d+$/` (for forked PRs) and against `testForInvalidChars` (which rejects control characters, `..`, path separators like leading/trailing dots, etc.) — but `filepath` receives no such treatment: [2](#0-1) 

`testForInvalidChars`, defined in `app/src/lib/sanitize-ref-name.ts`, is explicitly the guard used elsewhere to reject `..`, leading `.`, path separators, and other unsafe characters [3](#0-2) , but this guard is applied only to `branch`, not to `filepath`, even though `filepath` is documented as "the file to open after cloning the repository" [4](#0-3) . The `IOpenRepositoryFromURLAction.filepath` value then flows into `app/src/ui/dispatcher/dispatcher.ts`, which contains multiple references to it (confirmed by matches), presumably to open the file relative to the repository once cloned.

### Impact Explanation
This mirrors the report's broken invariant: one field (`branch`) is properly hardened against traversal-style payloads, while a structurally identical field (`filepath`) that is later used for file-system access is not. If the dispatcher joins `filepath` onto the working directory path without independent sanitization, a crafted deep link (e.g. `github-mac://openRepo/https://github.com/owner/repo?filepath=..%2F..%2F..%2F.ssh%2Fid_rsa`) sent via a webpage, chat link, or email could cause Desktop to attempt to open a file outside the cloned repository after the user clicks the link and completes the (normal, expected) clone/open flow — matching the "attacker controls a link/deep link the user clicks" impact class (file read outside the repo).

### Likelihood Explanation
Medium. Exploitation requires the user to click a malicious `x-github-client://` / `github-mac://` link, which Desktop registers as a default protocol handler, so no other attacker capability is required. Whether this results in actual out-of-repo file disclosure depends on exactly how `dispatcher.ts` consumes `filepath` (e.g., whether it uses `path.join` without a containment check) — this downstream logic could not be fully confirmed from the indexed code available, so a Devin session with full file access would be needed to verify the exact sink and confirm exploitability end-to-end.

### Recommendation
Apply the same `testForInvalidChars` (or a stricter path-traversal-aware) validation to `filepath` as is already applied to `branch` in `parseAppURL`, and/or ensure the consumer in `dispatcher.ts` resolves `filepath` against the repository root and verifies the resolved path stays within that root before opening it.

### Proof of Concept
1. Register/observe that Desktop is the default handler for `x-github-client://` and `github-mac://` schemes (`setAsDefaultProtocolClient` in `app/src/main-process/main.ts`).
2. Craft a link: `github-mac://openRepo/https://github.com/octokit/octokit.net?branch=master&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`.
3. Have the target click it (via webpage/email/chat).
4. `parseAppURL` returns `{ name: 'open-repository-from-url', url, branch: 'master', pr: null, filepath: '../../../../.ssh/id_rsa' }` with no rejection, since only `branch`/`pr` are validated [5](#0-4) .
5. This action is dispatched to `dispatcher.ts`'s open-repository-from-url handling; full confirmation of the file-open sink logic requires further inspection beyond what the index exposes.

**Note on confidence:** Steps 1–4 are directly evidenced in the codebase. Step 5 (the exact sink behavior in `dispatcher.ts`) could not be fully verified due to index limits — a Devin session with full repository access is recommended to confirm the downstream file-open logic and validate real-world exploitability before treating this as fully confirmed.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
