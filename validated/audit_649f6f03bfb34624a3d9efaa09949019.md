### Title
Certificate-trust exception is not host-scoped, allowing a MITM-accepted certificate to silently bypass future TLS validation for other endpoints - ([File: app/src/main-process/app-window.ts])

### Summary
The external report's underlying invariant is: "the client must actively verify it is using an up-to-date, correctly-behaving TLS trust mechanism before trusting network data, and must fail closed if it cannot." In GitHub Desktop, the closest analog is the certificate-error/"trust this certificate" flow: when Electron detects an invalid/self-signed certificate on a request (API call or, indirectly, an Electron-mediated network request), Desktop shows a dialog offering the user an escape hatch to trust it. That trust decision is granted through Electron's OS-level `showCertificateTrustDialog`, which is not bound to the specific hostname that triggered the prompt — it is bound to the certificate object itself.

### Finding Description
The main process registers a handler for Electron's `certificate-error` event that always rejects the default validation (`callback(false)`) and forwards the certificate, error, and URL to the renderer: [1](#0-0) .

The renderer listens for this and, unless the exact URL has previously been suppressed, shows the `PopupType.UntrustedCertificate` popup: [2](#0-1) .

The dialog itself explicitly frames "continuing" as reasonable in ambiguous cases — GitHub Enterprise trials or unusual top-level domains — which primes users toward accepting exceptions rather than treating any TLS failure as an active attack signal: [3](#0-2) .

If the user clicks "Add certificate"/"View Certificate", `onContinue` fires `onContinueWithUntrustedCertificate`, which calls `showCertificateTrustDialog` with a generic warning message — it passes only the `certificate`, not the originating `url`/host: [4](#0-3) .

In the main process, `showCertificateTrustDialog` simply forwards to Electron/OS's native trust dialog, again without associating the decision to the triggering hostname: [5](#0-4) .

Electron's `dialog.showCertificateTrustDialog` (backed by the OS keychain/certificate store on macOS, or the Windows certificate store) marks the certificate itself as trusted going forward — it is a certificate-level trust grant, not a host+certificate pinning decision. Because the invariant "this exact certificate is only valid for this exact host" is never enforced anywhere in this flow (no hostname/pin check before or after the trust dialog), once a user accepts an exception for one MITM'd connection (e.g., to what they believe is a GitHub Enterprise trial instance on an odd domain), the same certificate becomes implicitly trusted by the OS for any other TLS connection Desktop or other apps make using that certificate — including subsequent requests to `api.github.com` or other API endpoints if an attacker reuses/replays the same certificate material in a broader on-path position.

### Impact Explanation
If successfully exploited, this breaks TLS's core guarantee for all subsequent connections that happen to encounter the now-trusted certificate, enabling MITM decryption/modification of GitHub API traffic (including OAuth/device-flow tokens, GitHub Enterprise credentials) and of Git network traffic proxied similarly. This maps to credential/token exfiltration and unauthorized OAuth/account exposure, which are in-scope impact categories.

### Likelihood Explanation
Exploitation requires the attacker to already be in a network man-in-the-middle position (e.g., malicious/compromised proxy or Wi-Fi) to trigger the initial `certificate-error`, and it further requires a user to click through the "Add certificate" exception — the same precondition the dialog itself explicitly anticipates and rationalizes ("GitHub Enterprise trial", "unusual top-level domain"). This is a realistic but not-trivial likelihood: it depends on user interaction and an active network attacker, not local/physical access or prior malware.

### Recommendation
- Scope the trust decision to the specific host and certificate pair (store `(hostname, certificate fingerprint)` rather than relying solely on Electron/OS-wide certificate trust).
- Avoid re-using the OS "Always Trust" mechanism for a one-off exception; instead maintain an in-app allow-list keyed by host+fingerprint that is consulted only for that host on future `certificate-error` events, and require the trust to be re-confirmed if the host or certificate changes.
- Reconsider the dialog copy that normalizes clicking through certificate warnings, and consider disabling the "continue" path entirely for non-Enterprise (github.com) hosts.
- Audit `suppressCertificateErrorFor`/`isCertificateErrorSuppressedFor` in `app/src/lib/suppress-certificate-error.ts` and its callers in `app/src/lib/api.ts` to confirm suppression is also correctly scoped per exact host and not overly broad; this file was not fully reviewed and should be checked directly.

### Proof of Concept
1. Attacker positions as a network MITM (rogue Wi-Fi/proxy) and intercepts a GitHub Enterprise sign-in request to `https://ghe.example.com`.
2. Desktop's `certificate-error` handler in `main.ts` rejects Electron's default validation and shows the `UntrustedCertificate` dialog, which suggests this could be a legitimate GHE trial/odd-TLD scenario.
3. User clicks "Add certificate" — `onContinueWithUntrustedCertificate` invokes `showCertificateTrustDialog(certificate, message)` with no host binding.
4. The OS trusts that certificate going forward, independent of hostname.
5. Attacker later performs MITM against `api.github.com` traffic reusing the same certificate (or a certificate sharing the same trusted anchor/keychain entry) — the app no longer flags the connection as untrusted, and the attacker can intercept API tokens/credentials.
