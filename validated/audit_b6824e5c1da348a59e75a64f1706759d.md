### Title
FX filler's size-tiered spread can be bypassed by splitting a large order into several small ones, forcing under-priced fills against the filler's own liquidity - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
The reference Simplex FX filler prices each intent order against a size-tiered curve (`bidPriceCurve`/`askPriceCurve`) that is meant to charge a wider spread for larger trades. The notional used to evaluate that curve is computed strictly from the current order's own legs in `sizeOrder()` [1](#0-0) , with no memory of previous fills against the same pair. Consequently a user can split one large intent into many small intents and have every one of them priced at the curve's most favorable (smallest-amount) point, bypassing the size-based spread the operator configured to protect against large-trade risk — directly mirroring the OracleMaker `_getBasePriceWithSpread()` bug where the spread was computed only from pre-trade state and ignored the trade's own size.

### Finding Description
`calculateProfitability()` calls `sizeOrder()` to compute `cappedByPair`, the per-pair token0 notional (capped at `maxOrderSize`) that the curve is evaluated at: [2](#0-1) 

That `cappedByPair` value is passed straight into `resolveLegRates()` as `cappedPairNotional`, which is the exact input fed to `FillerPricePolicy.getPrice()` (the curve interpolation): [3](#0-2) 

`FillerPricePolicy.getPrice()` returns a strictly better rate (less spread) for smaller `amount` values, by design (documented in the config docs, e.g. ask curve `100 → 0.99`, `100000 → 0.999`) — small orders are explicitly quoted a worse rate for the *filler* (i.e., the intended protection is inverted here for stablecoin pairs where the smaller order is quoted the worst price, but for cross-asset pairs like USDC/CNGN, small orders get the operator's best/tightest rate and large orders are pushed to the wider/safer rate): [4](#0-3) 

Because `sizeOrder()` is invoked fresh for every incoming `Order` with zero cross-order state, nothing prevents an attacker from submitting `N` intents of size `total/N` instead of one intent of size `total`. Each of the `N` intents is independently capped/priced at its own small notional, so the filler is forced to quote the tightest curve point on every leg — exactly the price it configured for small, low-risk trades — while the attacker's aggregate exposure against the filler equals what a single large order would have produced. This is the same broken invariant as the Sherlock OracleMaker finding: a size-tiered price protection that only looks at the current instruction's own declared size, not the cumulative exposure being created, is trivially defeated by decomposing a large trade into a sequence of smaller ones.

### Impact Explanation
The impact lands on the Simplex filler's own escrowed/vault liquidity used to settle `IntentGatewayV2` fills — analogous to the OracleMaker LPs in the source report. An attacker can force the filler to sell more of an asset (or accept less-favorable relative pricing) at the "small order" rate rather than the "large order" rate the operator explicitly configured to price in inventory/FX risk for large notional, degrading the filler's realized spread/margin on every large trade it would otherwise have adequately priced. Because `remainingByPair`/`cappedByPair` are recomputed with no persisted per-pair running total across orders, there is no protection against this decomposition regardless of how quickly or slowly the split orders are submitted — no relayer collusion, prover assumption, or privileged action is required.

### Likelihood Explanation
Likelihood is high: any user of the `IntentGateway` who wants a better fill price than the large-order tier need only split their trade into a handful of intents sized to land on the curve's cheapest breakpoint. This is a normal, permissionless usage pattern of the public `IntentGateway` entrypoint requiring no special conditions, unlike the original report's network-race caveat for the Sherlock Maker (which was itself judged Medium even under that additional friction).

### Recommendation
Track cumulative notional per `(pair, time window)` or per `(pair, counterparty)` across orders — not just within a single order — and evaluate the curve against the running total (or an average that includes the new trade's contribution), similar to the recommended fix in the source report of pricing off the average of pre-trade and post-trade exposure rather than the pre-trade state alone. At minimum, add a configurable cooldown/decay-weighted volume tracker per pair so that a burst of small orders from the same solver/user session is priced as if it were the equivalent large order.

### Proof of Concept
1. Operator configures a `USDC/CNGN` pair with `askPriceCurve = [{amount:100, price:1560}, {amount:5000, price:1550}]` (small orders get the filler's tightest/most favorable-to-user rate, large orders get the wider spread the operator wants for risk control) as shown in the sample config: [5](#0-4) 
2. Attacker wants to move 5000 USDC → CNGN. A single order of 5000 USDC is capped/priced at `cappedByPair = min(5000, maxOrderSize) = 5000`, so `resolveLegRates` returns the ask=1550 tier.
3. Instead, attacker submits 50 separate intents of 100 USDC each through the public `IntentGateway`. Each call to `calculateProfitability` → `sizeOrder` independently computes `cappedByPair = 100` for that order, so `resolveLegRates`/`FillerPricePolicy.getPrice(100)` returns ask=1560 every time.
4. Aggregate result: attacker receives `50 × 100 × 1560 = 7,800,000` CNGN instead of `5000 × 1550 = 7,750,000` CNGN — extracting the small-order rate on the filler's entire large-order exposure, with no code path in `fx.ts` that aggregates or rate-limits notional across the 50 separate orders.

	getPrice(orderValueUsd: Decimal): Decimal {
		const amount = orderValueUsd

		// Below minimum configured amount, use the first point
		if (amount.lte(this.points[0].amount)) {
			return this.points[0].price
		}

		// Above maximum configured amount, use the last point
		const lastPoint = this.points[this.points.length - 1]
		if (amount.gte(lastPoint.amount)) {
			return lastPoint.price
		}

		// Piecewise linear interpolation between surrounding points; duplicate
		// amounts would divide by zero, so skip zero-width segments (the later
		// point wins via the following segment or the clamped-tail checks above)
		for (let i = 0; i < this.points.length - 1; i++) {
			const p1 = this.points[i]
			const p2 = this.points[i + 1]
			if (p2.amount.eq(p1.amount)) continue

			if (amount.gte(p1.amount) && amount.lte(p2.amount)) {
				const t = amount.minus(p1.amount).div(p2.amount.minus(p1.amount))
				return p1.price.plus(t.mul(p2.price.minus(p1.price)))
			}
		}

		// Fallback (should not be reached due to earlier checks)
		return lastPoint.price
	}
