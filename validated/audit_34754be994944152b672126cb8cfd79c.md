### Title
Missing recipient binding in PedPoP blame resolution lets any party frame an innocent participant as faulty - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class in the Apache Answer advisory is a missing ownership check: an authenticated party supplies an identifier (a file URL) and the system performs a privileged/destructive action on another user's resource without verifying the caller owns it. The Serai analog lives in the PedPoP blame path. `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` accept a caller-supplied `recipient: Participant` and, on any failure of the accuser-supplied decryption proof, unconditionally return that `recipient` as the faulty party — without verifying the supplied `EncryptedMessage` was ever addressed to that participant, and without binding the intended recipient into the message's proof-of-possession challenge. Any party (including a non-participant, via `AdditionalBlameMachine`) can take a valid encrypted share sent to *themselves* and adjudicate blame naming an arbitrary victim as `recipient`, causing the victim to be declared faulty.

### Finding Description
`pop_challenge` binds only `context`, `R`, the per-message key, the claimed sender (`from`), and the ciphertext — the intended recipient is never transcripted (`crypto/dkg/pedpop/src/encryption.rs`, `pop_challenge` usage at lines 374–377 and 479–485). `blame_internal` (`crypto/dkg/pedpop/src/lib.rs` lines 575–609) takes `sender`, `recipient`, `msg`, and `proof` as independent inputs. When `proof` is `None`, or the DLEq fails, it hits `Err(DecryptionError::InvalidProof)` and `return recipient` (lines 586–587). `decrypt_with_proof` verifies the DLEq against `self.enc_keys[&decryptor]` — i.e., whatever participant the caller *claims* was the decryptor (lines 381–390). `AdditionalBlameMachine::blame` exposes this to anyone holding the public commitment messages, explicitly "regardless of if the caller was a member in the DKG protocol" (lib.rs lines 639–681). Nothing ties `msg` to `recipient`; the only documented safeguard is that `msg` be authenticated as coming from `sender`, which does not prevent re-attribution of the recipient.

### Impact Explanation
An attacker who legitimately received an encrypted secret share from participant S can call `blame(sender: S, recipient: V, msg, proof: None)` (or a proof against their own ECDH key). The PoP verifies because it only binds `from = S` and the ciphertext; the proof then cannot validate against `enc_keys[V]` (or is absent), so `blame_internal` returns `V` as the faulty party. In Serai's deployment, blame output feeds fatal slashing (`ProcessorMessage::Blame`/`VerifyBlame` semantics — an incorrect blame result marks an honest validator as malicious). This mirrors the advisory exactly: supplying someone else's identifier causes destructive action against them with no ownership check, reachable purely with public inputs (commitments, a real share message, and chosen `Participant` values).

### Likelihood Explanation
Requires only that the attacker participate in (or observe authenticated transcripts of) a DKG session and that blame arbitration be invoked — a routine, intended protocol path triggered whenever any share verification fails. The attacker needs no stolen keys and produces no invalid cryptography; the exploit is purely a mis-attribution. Cost is trivial.

### Recommendation
Bind the intended recipient into the per-message authentication: include `to: Participant` in `pop_challenge` alongside `from`, and/or have `blame` verify the accuser is the `recipient` (for `BlameMachine`, check `recipient == self.params.i()`). In `AdditionalBlameMachine`, require the `EncryptionKeyProof` to be present and verify against `enc_keys[&recipient]` *before* assigning blame to `recipient`, treating a missing/mismatched proof as accuser fault rather than silently blaming the named recipient.

### Proof of Concept
```rust
// Attacker A received a valid share msg from S: shares[S][A] (EncryptedMessage with
// PoP binding from=S). A wants to frame honest participant V.
let machine = AdditionalBlameMachine::new(context, n, commitment_msgs).unwrap();
// Re-attribute the message's recipient to V and provide no decryption proof:
let blamed = machine.blame(S, V, shares_msg_from_S_to_A.clone(), None);
// msg.pop.verify(...) uses pop_challenge(context, R, key, S, ciphertext) -> passes,
// since the PoP binds only the sender and ciphertext, never the recipient.
// proof is None -> DecryptionError::InvalidProof -> blame_internal returns `recipient` = V.
assert_eq!(blamed, V); // innocent V is declared faulty
```
The same result holds with `Some(proof)` where `proof` is A's real ECDH proof: the DLEq is checked against `enc_keys[&V]` (encryption.rs line 388), fails, and again returns `V`.
