### Title
SimplexPaymaster's Chainlink price fetch never validates the price against the aggregator's min/max bounds, letting gas fees be charged at a stale clamped price during a depeg or crash - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`_getOraclePrice()` in `SimplexPaymaster.sol` only checks that `answer > 0` and that the round isn't stale by `updatedAt`, exactly mirroring the flawed pattern in the reported `D3Oracle.getPrice()`/`getOriginalPrice()` bug. It never checks the returned answer against the Chainlink aggregator's configured `minAnswer`/`maxAnswer`, so during a market crash or stablecoin depeg the aggregator will silently clamp and keep returning the boundary price as if it were current and valid. [1](#0-0) 

### Finding Description
`_getOraclePrice()` is the sole price source used by `_tokenPrice()`, which is used both in the public, unprivileged `_fetchDetails()` gas-charging path and in the treasury-gated `swapAndDeposit()`: [2](#0-1) 

`_fetchDetails()` is invoked on every ERC-4337 UserOp that uses this paymaster, computing `tokenPrice` purely from `_getOraclePrice(nativeOracle, ...)` and `_getOraclePrice(cfg.tokenOracle, ...)`: [3](#0-2) 

The only guards applied to the raw Chainlink `answer` are `answer <= 0` and a staleness check on `updatedAt`: [4](#0-3) 

This is precisely the same broken invariant as the reported bug: Chainlink feeds have a `minAnswer`/`maxAnswer` clamp built into the aggregator. When the real price moves past that range (e.g., a stablecoin depegs below `minAnswer`, or the native asset crashes below its feed's floor), `latestRoundData()` keeps returning the clamped boundary value with a **fresh** `updatedAt` timestamp — so it passes both existing checks (`answer > 0` and "not stale") while being numerically wrong. Neither `_getOraclePrice` nor any caller cross-checks the returned `answer` against the aggregator's `minAnswer()`/`maxAnswer()` (which are exposed on the real Chainlink `AggregatorV3Interface`/`AggregatorV2V3Interface` but not even declared in this contract's minimal `AggregatorV3Interface`).

Because `_tokenPrice()` divides by `tokenUsd` and multiplies by `nativeUsd`, a clamp on either side directly and proportionally distorts `tokenPrice`, which is the exact conversion rate `PaymasterERC20` uses to pull `erc20Cost = weiCost * tokenPrice / 1e18` from the user's wallet.

### Impact Explanation
Because `_fetchDetails()` is reached by any unprivileged UserOp author with no relayer, prover, or admin involvement, a clamped feed value converts directly into wrong-amount fund movement at the paymaster's public gas-charging entrypoint:
- If the token's USD feed depegs downward (e.g., a stablecoin de-pegs during a crash) but the aggregator clamps to `minAnswer` (which is above the real crashed price), `tokenUsd` is reported artificially high, so `tokenPrice` (token units per wei) is computed artificially low. Users are then charged fewer token units than the true market-adjusted cost of the gas they consume, draining the paymaster's/treasury's subsidized native balance — a direct loss of funds to the protocol.
- Conversely, if the native asset's feed crashes below its `minAnswer`, `nativeUsd` is reported artificially high, inflating `tokenPrice` and causing ordinary users to be overcharged in ERC-20 tokens for the same gas — a direct loss of funds to users.

Both directions satisfy the bounty's "stealing or loss of funds" / "transaction manipulation" impact class, since price is a first-class input to an actual token transfer (`transferFrom` inside `PaymasterERC20`), not merely a display value.

### Likelihood Explanation
This requires no malicious peer, relayer, prover, or governance actor — it is triggered purely by normal market conditions (a de-peg or crash event) combined with any ordinary user submitting a UserOp through the paymaster while the underlying Chainlink feed is clamped. This is realistic and has happened historically to real Chainlink feeds (e.g., stablecoin de-peg events), and the contract's own doc comment acknowledges "even against a malicious oracle" as a residual risk but only bounds it via small permit/allowance amounts — it does not eliminate the wrong-price condition itself, and `swapAndDeposit()`'s slippage-based `amountOutMin` is derived from the same unclamped prices, so the same flaw also degrades the treasury's fee-recycling swaps.

### Recommendation
Extend the minimal `AggregatorV3Interface` to expose `minAnswer()`/`maxAnswer()` (or use the standard `AggregatorV2V3Interface`), and in `_getOraclePrice()` add:
```solidity
require(answer > minAnswer && answer < maxAnswer, "Chainlink: price out of range");
```
before normalizing decimals, reverting the whole UserOp/swap when the feed is clamped, matching the recommendation in the referenced report.

### Proof of Concept
1. Deploy `SimplexPaymaster` with a token/USD `MockOracle` (as used in `SimplexPaymasterTest.t.sol`) and set its `answer` to a clamp-boundary value (e.g., simulate a de-peg by setting the mock to return the aggregator's documented `minAnswer` while `updatedAt = block.timestamp`). [5](#0-4) 
2. Call `getTokenPrice(token)` / trigger `_fetchDetails` via a UserOp: observe that `_getOraclePrice` returns the clamped value without reverting, since only `answer <= 0` and staleness are checked. [4](#0-3) 
3. Compare the paymaster-computed `tokenPrice`/`erc20Cost` against the true off-chain market price at the time of the simulated crash — the amounts diverge because the contract never rejects out-of-range answers, confirming funds move at the wrong rate through the public gas-charging path.

```text
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
