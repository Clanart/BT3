### Title
`sendNative()` bank precompile bypasses tokenfactory `DenomAllowList`/`BlockedAddr` compliance freeze, unlike `send()` and native `MsgSend` - (File: `precompiles/bank/bank.go`)

### Summary
The `send()` bank-precompile method and the native `x/bank` `MsgSend` handler both route funds transfers through the same enforcement path (`bankMsgServer.Send` / `msgServer.Send`), which checks `IsInDenomAllowList` and `BlockedAddr` before moving funds. `sendNative()`, however, calls `p.bankKeeper.SendCoinsAndWei` directly, skipping those checks entirely — the same class of bug as the OpenQ report, where a fund-restriction mechanism (`closeCompetition`/freeze) is implemented in one code path but not enforced in a sibling path that also moves the same funds.

### Finding Description
`x/bank`'s `msgServer.Send` enforces token-factory compliance controls before any transfer: it calls `IsInDenomAllowList` for both sender and receiver and checks `BlockedAddr` on the receiver. [1](#0-0) 

The EVM `bank` precompile's `send()` method (ERC20-pointer-gated) correctly reuses this same enforcement by constructing a `banktypes.MsgSend` and calling `p.bankMsgServer.Send(...)`, inheriting the allow-list/blocked-address checks. [2](#0-1) 

However, `sendNative()` — reachable directly by any EVM caller sending native `usei`/wei value to the precompile address — bypasses `bankMsgServer.Send` entirely and calls `p.bankKeeper.SendCoinsAndWei` directly: [3](#0-2) 

`SendCoinsAndWei`/`SendCoins` at the keeper level do not themselves enforce `IsInDenomAllowList` or `BlockedAddr` — those checks live only in the message-server layer (`msgServer.Send`/`MultiSend`), as also shown by the analogous `IsInDenomAllowList` helper used exclusively from `msg_server.go`. [4](#0-3) 

This mirrors the OpenQ pattern exactly: a restriction/enforcement mechanism (`closeCompetition` sets `status = CLOSED` to freeze funds; here, `SetDenomAllowList`/`BlockedAddr` restrict who may send/receive a token-factory denom) is checked in one fund-moving entry point (`closeCompetition`'s sibling check would be in `claimBounty`; here it's `send()`/`MsgSend`) but omitted in a second fund-moving entry point (`ClaimManagerV1::claimBounty` there; `sendNative()` here).

Note: `sendNative` only handles the base denom (`usei`/wei), so token-factory denom allow-lists (which key off the `factory/...` prefix) would not apply to it directly — but `BlockedAddr` (module account protection) is denom-agnostic and is bypassed for `usei`/wei transfers through `sendNative`, since `SendCoinsAndWei` performs no such check.

### Impact Explanation
`BlockedAddr` exists to prevent unprivileged senders from crediting protected module accounts (e.g., to prevent supply/accounting manipulation or unauthorized funding of module funds pools). Because `sendNative` skips this check, any EVM caller can send native `usei` (via `msg.value`) to a blocked/module address that `MsgSend` would otherwise reject, undermining a fund-safety guarantee that is supposed to hold uniformly across all bank transfer surfaces. This is a Medium-severity access-control/consistency gap: a compliance/protection control implemented in one transfer path is not enforced in a parallel path handling the same underlying funds movement, directly matching the reported bug class ("freeze"/restriction control set in one path, not honored in a sibling path that moves the same funds).

### Likelihood Explanation
High reachability: `sendNative` is a public, non-privileged EVM precompile method invoked by simply sending a transaction with `value` to the bank precompile address (`0x...1001`); no special permissions or preconditions are required beyond having `usei` to send.

### Recommendation
Route `sendNative`'s fund transfer through the same enforcement layer as `send()`/`MsgSend` — e.g., check `BlockedAddr` (and, if wei-denominated tokenfactory transfers are ever supported, `IsInDenomAllowList`) on the receiver before calling `SendCoinsAndWei`, or refactor `SendCoinsAndWei` to perform the blocked-address check internally so all transfer paths are protected uniformly.

### Proof of Concept
1. Governance/tokenfactory admin sets up `BlockedAddr`-protected module accounts (already default in `x/bank` genesis for standard modules).
2. An unprivileged EVM user calls the bank precompile `sendNative(receiver)` with `msg.value > 0`, where `receiver` is a Sei address mapped to a blocked module account.
3. `sendNative()` calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly [5](#0-4) , with no `BlockedAddr` check, unlike the equivalent native `MsgSend`/`send()` precompile path which would reject the same transfer with `"%s is not allowed to receive funds"` [6](#0-5) .
4. The transfer to the blocked/module address succeeds via `sendNative` where it would have been rejected via `send()`/`MsgSend`, demonstrating the inconsistent enforcement of the fund-protection control.

	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
