### Title
Convexity of the expired-slot decay formula in `getRewardablePercentWAD` lets a multi-slot user retain a higher rewardable share (lower forfeiture) than a single-slot user with identical total stake - ([File: VLMGP.sol])

### Summary
`VLMGP.getRewardablePercentWAD` (mirrored in `mWomSV.getRewardablePercentWAD`) computes, for each expired-but-unclaimed unlock slot, a decay term `amountInCoolDown * (endTime-startTime) / (timeNow-startTime)` [1](#0-0) . Because `coolDownInSecs` (the slot duration `D`) is fixed for every slot [2](#0-1) , this per-slot term is a convex function of the slot's `startTime`. By Jensen's inequality, an attacker who splits an equal total unlock amount across multiple slots with different `startTime`s gets a strictly larger summed rewardable percentage than a single-slot user unlocking the same total amount at the average start time, causing `vlMGPBaseRewarder._calExpireForfeit` to under-forfeit for the multi-slot attacker relative to an equal-stake peer.

### Finding Description
`getRewardablePercentWAD` starts from the fully-locked share and then, for each unlock slot, adds a term:
- If still cooling down (not yet past `endTime`): full 100% credit for that slot's amount, no decay [3](#0-2) .
- If expired but unclaimed (`block.timestamp > endTime`): `amountInCoolDown * (endTime - startTime) / (timeNow - startTime)` [4](#0-3) .

Since every slot uses the same fixed `coolDownInSecs = D` (`endTime = startTime + D`, set in `startUnlock`) [2](#0-1) , the expired-slot term for amount `a` and start time `t` reduces to `a * D / (timeNow - t)`, i.e. `a * f(t)` where `f(t) = D/(timeNow - t)` is strictly convex in `t` for `t < timeNow`.

Consequence: for a fixed total amount `L` and a fixed weighted-average start time `t̄`, splitting `L` into `n` slots with different individual start times `t_1...t_n` (weighted average = `t̄`) and letting all of them expire produces `Σ a_i * f(t_i) ≥ L * f(t̄)` by Jensen's inequality (strict inequality whenever the `t_i` differ). This is exactly the sum used in `getRewardablePercentWAD`, so a multi-slot attacker's rewardable percent for equal total locked/unlocking amount and equal average unlock start time is strictly higher than a single-slot user's.

This rewardable percent directly drives `vlMGPBaseRewarder._calExpireForfeit`, which computes `rewardableAmount = _amount * rewardablePercentWAD / 1e18` and `forfeitAmount = _amount - rewardableAmount`, and is invoked on every `getReward`/`_sendReward` call [5](#0-4) , [6](#0-5) . Forfeited amounts are recycled into `rewardPerTokenStored` for the remaining stakers via `_queueNewRewardsWithoutTransfer` [7](#0-6) . Thus a multi-slot attacker keeps a larger share of "unclaimed yield" that should have been forfeited to the pool, at the expense of honest single-slot stakers who receive a smaller redistributed forfeit pool - a real, quantifiable transfer of unclaimed yield between users with identical stake, not merely a rounding/no-fund-impact issue.

No existing modifier, `nonReentrant`, or receipt-token accounting prevents this: `startUnlock` merely enforces slot-count limits (`maxSlot`) via `getNextAvailableUnlockSlot` [8](#0-7) , and multiclaim/relock logic does not equalize or normalize timing across slots, so the convexity bias in `getRewardablePercentWAD` is fully attacker-controllable by picking `startTime`s (via when `startUnlock` is called for each slot) and picking the block timestamp at which `getReward` is triggered.

### Impact Explanation
This is a "theft or permanent freezing of unclaimed yield" style impact under Immunefi's classification: an attacker deliberately staggers unlock slots to reduce their own forfeiture and, symmetrically, siphon a disproportionate share of the redistributed forfeit-reward pool that would otherwise accrue to honest single-slot stakers with the same total vlMGP balance. It violates the intended conservation invariant (equal total stake -> equal expected forfeiture/reward share), producing an economic loss for peers, though the magnitude per exploit is bounded by `maxSlot` and by how skewed the attacker can make their slot start times.

### Likelihood Explanation
Fully attacker-controlled and capital-light: any vlMGP holder can call `startUnlock` multiple times (up to `maxSlot`) with different amounts/timings and then call `getReward` at a chosen block timestamp to maximize the convex-sum effect. No special privileges are required, and the attack is repeatable every unlock/reward cycle. The benefit scales with `maxSlot` and with how long the attacker can spread `startTime`s while keeping slots technically "expired but unclaimed."

### Recommendation
Change the decay formula so the discount applied to an expired slot depends only on `(timeNow - endTime)` (time since expiry) rather than `(timeNow - startTime)`, and/or make the per-slot decay function homogeneous/linear (not convex) in a way that summing over split slots at the same weighted-average timing cannot exceed the single-slot equivalent (e.g., normalize by `Σ a_i` first, or compute a single blended "effective start time" for cooldown purposes rather than a per-slot convex sum). Alternatively, cap the total expired-slot contribution to be provably additive/linear in `a_i` for a fixed elapsed-since-expiry ratio, and add invariant tests asserting that `calExpireForfeit`/`getRewardablePercentWAD` is invariant to how a fixed total unlocking amount with a fixed weighted-average timestamp is split across slots.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP` with `coolDownInSecs = D` and `maxSlot >= 2`; lock and later unlock for two users, both ending with identical total vlMGP-equivalent stake `L` at the time of the check.
2. User A (single-slot): call `startUnlock(L)` once at `t̄`.
3. User B (multi-slot): call `startUnlock(L/2)` at `t̄ - Δ` and `startUnlock(L/2)` at `t̄ + Δ` (weighted average start time = `t̄`, same as A).
4. Warp time to `timeNow > t̄ + Δ + D` so both of B's slots and A's slot are expired but unclaimed.
5. Call `getRewardablePercentWAD(A)` and `getRewardablePercentWAD(B)` and assert `percent(B) > percent(A)` despite identical total stake and identical average unlock timing.
6. Additionally call `vlMGPBaseRewarder._calExpireForfeit` (or `getReward`) for both users with equal pending `userRewards` and assert B's `forfeitAmount < A's forfeitAmount`, demonstrating B retains a larger share of what should be forfeited, and that the difference is redistributed away from A via `_queueNewRewardsWithoutTransfer`.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
