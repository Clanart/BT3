I found a concrete unbound-ID access-control gap that maps to the Chartbrew pattern: an RPC caller supplies both a scoping `wallet_id` and a separate resource ID (`target_coin_id`), and the code fetches the resource **globally** rather than validating it belongs to the wallet the caller claims to be operating on — exactly like Chartbrew's unbound `policy_id` under a `project_id` path.

### Title
Wallet `split_coins` RPC accepts a `target_coin_id` unbound to the specified `wallet_id`, letting a caller drive one wallet's spend construction with another wallet's coin - (File: `chia/wallet/fungibility_manager.py`)

### Summary
`WalletRpcApi.split_coins` takes a `wallet_id` (used only to select which `Wallet`/`CATWallet` object will build and sign the transaction) and a `target_coin_id` (the coin to be split). `FungibilityManager.split_coins` resolves `target_coin_id` via `self.coin_store.get_coin_record(target_coin_id)` — a global, wallet-unscoped lookup — and then unconditionally treats the returned coin as belonging to the `wallet` object selected purely from `request.wallet_id`. There is no check that the coin record's `wallet_id`/`wallet_type` actually matches the wallet chosen to perform the split, unlike the sibling `combine_coins` path, which explicitly scopes its coin lookup with `wallet_id=wallet.id()` in the `coin_store.get_coin_records(...)` call.

### Finding Description [1](#0-0) 
`split_coins` resolves the acting wallet strictly from `request.wallet_id` via `fungibility_manager.get_fungible_wallet(request.wallet_id)`, and passes `request.target_coin_id` straight through. [2](#0-1) 
Inside `FungibilityManager.split_coins`, the target coin is looked up with an unscoped, global query:
```
optional_coin = await self.coin_store.get_coin_record(target_coin_id)
```
No comparison is made between `optional_coin.wallet_id` and `wallet.id()` (the wallet resolved from `request.wallet_id`), nor between `optional_coin.wallet_type` and `wallet.type()`. The coin is then unconditionally selected and passed to `wallet.generate_signed_transaction(...)` as if it is owned by the caller-specified wallet.

This is the same class of bug as the Chartbrew report: the caller supplies two identifiers — a scoping id (`wallet_id`/`project_id`) and a target resource id (`target_coin_id`/`policy_id`) — and the authorization/binding check is only performed on the scoping id while the target resource id is trusted without verifying it actually belongs to that scope. The sibling `combine_coins` implementation in the same file demonstrates the intended, safe pattern by filtering `coin_store.get_coin_records(wallet_id=wallet.id(), coin_id_filter=...)`, confirming that `split_coins` is missing the equivalent scoping check.

### Impact Explanation
Because `split_coins` binds an arbitrary, caller-known coin ID to whatever wallet object the caller separately names, a coin belonging to one wallet (e.g., a CAT wallet's CAT coin, or another standard wallet's coin) can be fed into a different wallet's `generate_signed_transaction` path. Depending on wallet-type combinations this can produce puzzle/coin type confusion during spend construction (the calling wallet's `puzzle_for_pk`/inner-puzzle assumptions do not match the actual coin's puzzle hash), which can result in constructing invalid/rejected spends (a spend-triggered transaction-processing failure) or, in wallet-type combinations where the mismatch is not immediately caught, incorrect fee/amount accounting during signed-transaction construction. It also breaks the implicit safety invariant (documented and enforced in `combine_coins`) that a wallet only ever selects and signs coins it actually owns.

### Likelihood Explanation
Any RPC caller who can invoke `split_coins` (a standard wallet-RPC endpoint, reachable by any local wallet-RPC client) and who knows the coin ID of a coin tracked by the wallet service (obtainable via the also-unauthenticated `get_coin_records`) can trigger this mismatch by simply supplying a `wallet_id` different from the coin's true owning wallet. No special privilege beyond ordinary wallet-RPC access is required, and the request shape (`wallet_id` + `target_coin_id`) is exactly the shape validated correctly elsewhere (`combine_coins`), making the omission in `split_coins` a straightforward, easily triggered inconsistency.

### Recommendation
In `FungibilityManager.split_coins`, after resolving `optional_coin`, verify that `optional_coin.wallet_id == wallet.id()` (and/or `optional_coin.wallet_type` matches `wallet.type()`) before proceeding, raising a `ValueError` otherwise — mirroring the wallet-scoped `coin_store.get_coin_records(wallet_id=wallet.id(), ...)` filtering already used in `combine_coins`.

### Proof of Concept
1. Create two wallets in the same wallet service: wallet 1 (standard XCH) and wallet 2 (a CAT wallet).
2. Note a coin ID owned by wallet 2 (e.g. via `get_coin_records` filtered by `wallet_id=2`).
3. Call the `split_coins` RPC with `wallet_id=1` and `target_coin_id=<wallet 2's coin id>`.
4. Observe that `FungibilityManager.split_coins` fetches the coin via the global `coin_store.get_coin_record(target_coin_id)` (no wallet-scoping check) and proceeds to call `wallet_1.generate_signed_transaction(...)` treating the CAT coin as if it belonged to the standard wallet — contrasted with the equivalent `combine_coins` call, which would reject this because its coin lookup is scoped with `wallet_id=wallet.id()`.     async def split_coins(
        self,
        *,
        action_scope: WalletActionScope,
        wallet: Wallet | CATWallet,
        target_coin_id: bytes32,
        amount_per_coin: uint64,
        number_of_coins: uint16,
        fee: uint64,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> None:
        optional_coin = await self.coin_store.get_coin_record(target_coin_id)
        if optional_coin is None:
            raise ValueError(f"Could not find coin with ID {target_coin_id}")
        else:
            coin = optional_coin.coin

        total_amount = amount_per_coin * number_of_coins

        if coin.amount < total_amount:
            raise ValueError(f"Coin amount: {coin.amount} is less than the total amount of the split: {total_amount}.")

        outputs = [
            CreateCoin(
                await action_scope.get_puzzle_hash(self.wallet_state_manager, override_reuse_puzhash_with=False),
                amount_per_coin,
            )
            for _ in range(number_of_coins)
        ]

        if wallet.type() == WalletType.STANDARD_WALLET and coin.amount < total_amount + fee:
            async with action_scope.use() as interface:
                interface.side_effects.selected_coins.append(coin)
            coins = await wallet.select_coins(
                uint64(total_amount + fee - coin.amount),
                action_scope,
            )
            coins.add(coin)
        else:
            coins = {coin}

        await wallet.generate_signed_transaction(
            [output.amount for output in outputs],
            [output.puzzle_hash for output in outputs],
            action_scope,
            fee,
            coins=coins,
            extra_conditions=extra_conditions,
        )
