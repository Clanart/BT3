### Title
Deep-link controlled branch name may allow Git argument injection into `git checkout` - (File: `app/src/lib/parse-app-url.ts`, `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The external report's core issue is that attacker-supplied input flows into a sensitive operation (creating a pool/pair) without validation beyond syntax parsing. The closest Desktop analog is the `x-github-client://openRepo/...?branch=<name>` deep link handler: the `branch` query parameter is attacker-controlled (anyone can host a link the user clicks), is validated only for ref-name character legality via `testForInvalidChars` [1](#0-0) , and is then passed straight through to `openBranchNameFromUrl` → `checkoutLocalBranch(repository, branchName)` [2](#0-1) .

### Finding Description
`parseAppURL` extracts `branch` from the deep link query string and only rejects it if `testForInvalidChars` flags it [3](#0-2) . This check (analogous to Git's `check-ref-format` rules) validates ref-name syntax but, in most such implementations, does not necessarily reject names beginning with a dash (`-`), which is a distinct and separate safety property from "is a syntactically valid ref name." If the branch string is subsequently interpolated into a `git checkout <branch>` argument list without a preceding `--` separator (as is the pattern used elsewhere in `checkout.ts`, e.g., `args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]` for `checkoutBranch` [4](#0-3) ), a value like `--conflict=merge` or other Git flags could be injected as a command-line option rather than treated as a literal ref name — the classic "argument injection via user-controlled ref name" bug class.

**I was unable to confirm** whether `checkoutLocalBranch`/`getBranchCheckoutArgs` actually places a `--` separator before the branch argument, or whether `testForInvalidChars` already blocks a leading dash — repeated attempts to read `app/src/lib/sanitize-ref-name.ts` and the `checkoutLocalBranch` implementation failed due to tool errors. This is the critical missing piece to confirm exploitability.

### Impact Explanation
If confirmed, a crafted `x-github-client://openRepo/<url>?branch=<injected-flag>` link clicked by a victim could cause Desktop to invoke `git checkout` with an attacker-chosen flag against a repository the victim already has cloned or is about to clone, potentially altering working tree state, triggering unexpected Git behavior, or (depending on which flags are reachable) writing files outside the intended path. This matches the "attacker controls a...link or deep link the user clicks" and "silent corruption of what the user commits" impact categories.

### Likelihood Explanation
Deep links are a normal, low-friction attack vector (a webpage or email link), and the branch value already flows through only syntax validation before being handed to a Git command — the same shape of bug as the reported `addLiquidity` issue (validation of format but not of "safe to use as a positional argument"). However, without confirming the exact argument construction and the exact behavior of `testForInvalidChars`, I cannot assign confidence beyond "plausible, unverified."

### Recommendation
Verify that `testForInvalidChars` (or an additional check) rejects branch/ref names beginning with `-`, and audit all call sites where deep-link/API-derived strings (branch names, PR refs) are passed to `git` argument arrays to ensure a `--` separator always precedes user-controlled positional arguments, consistent with Git's own recommended defenses against argument injection.

### Proof of Concept
Not fully constructible without confirming the two unverified points above. Conceptually: `x-github-client://openRepo/https://github.com/owner/repo?branch=--upload-pack%3Dtouch%20/tmp/pwned` (or an equivalent Git flag reachable by `checkout`) clicked by a victim with Desktop installed, if the deep link handler reaches `git checkout` without a `--` separator and the branch string passes `testForInvalidChars`.

**Given the significant uncertainty on the two unverified code paths, this should be treated as a lead for a background agent to confirm/deny rather than a fully validated finding.**

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
