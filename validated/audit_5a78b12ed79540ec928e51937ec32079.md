### Title
Consumed FROST preprocess reloaded from DB cache reuses the same nonces across distinct sign calls, enabling secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's `SigningProtocol::preprocess_internal` persists a deterministic preprocess seed (`CachedPreprocesses`, keyed by `context`) in the database and re-derives the identical FROST nonces `(d, e)` every time it runs. Every call to `share` and `complete` re-executes `sign` with those same nonces. Because the included participant set and the signed message are supplied by transaction submitters and can differ between calls within one `context`, the same nonce pair is reused under different binding factors/challenges — the direct analog of a use-after-free: one-time secret state that was "consumed" by a prior `sign` is dereferenced again.

### Finding Description
`preprocess_internal` generates a random `CachedPreprocess` seed only once per `context`, encrypts it under `key || context`, stores it in `CachedPreprocesses`, and on every subsequent call reloads the same seed and calls `AlgorithmSignMachine::from_cache`, which feeds it to `seeded_preprocess` → `ChaCha20Rng::from_seed` → `Commitments::new`, reproducing the exact same nonces `d, e`. [1](#0-0) [2](#0-1) 

Both `DkgConfirmer::share` and `DkgConfirmer::complete` independently invoke `share_internal` → `preprocess_internal` → `machine.sign(preprocesses, msg)`, i.e., `sign` consumes the same seed repeatedly rather than the consumed state being retired after first use. [3](#0-2) [4](#0-3) 

The inputs that determine the FROST share equation are attacker-influenced:
- `preprocesses` is built from a `HashMap<Participant, Vec<u8>>` supplied per transaction; the *subset* of published preprocesses included is chosen by the submitter. Different subsets change the `included` set, the per-participant binding factor `rho`, and the Lagrange coefficients `lambda_i`. [5](#0-4) 
- `msg` is `set_keys_message(set, removed, key_pair)`, so a different `key_pair` or `removed` list changes the challenge `c` while nonces stay fixed. [6](#0-5) 

The file's own header acknowledges the hazard — "it is explicitly unsafe to reuse nonces across signing sessions ... For nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — and relies on BFT finality plus rebuild-redeciding to prevent it. But the DB cache makes the nonce survive rebuilds, and `complete` unconditionally re-signs, so distinct finalized transactions carrying different preprocess subsets/`key_pair`s within one attempt cause exactly the forbidden second `sign`. [7](#0-6) 

### Impact Explanation
Each `sign` emits a public share `s = d + e·rho + lambda·x·c` with fixed `(d, e)` and secret share `x`. Every distinct `(preprocess set, msg)` tuple yields one more linear equation in the same unknowns `(d, e, x)` (rho, lambda, c are publicly derivable). Three distinct sign invocations under one `context` fully determine the system and reveal the validator's secret share `x`, and repeated signing lets anyone reconstruct it; combined with the documented property that knowledge of the preprocess enables private-key recovery, this escalates to full compromise of the coordinator's threshold share. [8](#0-7) 

### Likelihood Explanation
Triggering requires two or more finalized `set_keys`-style transactions in the same DKG attempt carrying different preprocess subsets or `key_pair` values — the preprocess bytes themselves are already public, so selecting a different subset costs the submitter nothing. `complete` alone already guarantees a second `sign` per confirmation flow; any divergence between the preprocess map used at `share` time and at `complete` time (different participant subsets finalize legitimately, since only `t` of `n` are required) produces the second equation. No collusion, no DB access, and no malformed encodings are required — only crafted ordering/subsets of valid public data.

### Recommendation
Never call `sign` twice on nonces derived from one cached seed. Either (a) delete/invalidate `CachedPreprocesses[context]` after the first `share`/`complete` and treat any subsequent `share` for the same context as an error, or (b) record the exact `(preprocesses, msg)` tuple used in the first `sign` and refuse — rather than re-sign — any subsequent call whose inputs differ, returning the originally published share deterministically. The persisted commitment bytes should additionally be checked against what was actually published before emitting a share, closing the TODO noted in the file header. [9](#0-8) 

### Proof of Concept
Sketch (validator-side, within one DKG `attempt` → fixed `context`):

1. Publish preprocess `P_me`; collect peers' published preprocesses `P_1..P_n` (public on the tributary).
2. Submit transaction A carrying the full preprocess set `{P_1..P_n}` and `key_pair` `K`. The coordinator runs `sign` → emits share `s_A = d + e·rho_A + lambda_A·x·c_A`.
3. Submit transaction B (or observe `complete`) carrying subset `{P_1..P_t}` — still a valid ≥t set — or a different `key_pair` `K'`. `share_internal` reloads the same seed, reuses `(d, e)`, and emits `s_B = d + e·rho_B + lambda_B·x·c_B`.
4. Repeat for a third distinct tuple → `s_C`. Solve the 3×3 linear system over the scalar field for `(d, e, x)`; `x` is the coordinator's secret share. Verify via `G·x == verification_share_of(coordinator)` from `ThresholdKeys`.

Caveat: I could not fully trace `handle.rs` to confirm the transaction-level path that feeds `preprocesses`/`key_pair` into `DkgConfirmer::share`/`complete`; if that path hard-pins both to a single canonical value per attempt, reachability narrows to the `share`→`complete` double-sign with divergent subsets, which still yields the same reuse whenever the two sets differ.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
