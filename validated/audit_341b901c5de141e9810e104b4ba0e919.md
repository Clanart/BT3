### Title
Unhandled `URI::InvalidURIError` from malformed `Referer` header crashes public login-redirect path - ([File: lib/shopify_app/controller_concerns/sanitized_params.rb])

### Summary
`ShopifyApp::SanitizedParams#referer_sanitized_shop_name` calls Ruby's stdlib `URI(request.referer)` with no `rescue` guard. Any unauthenticated request whose `Referer` header is not a syntactically valid URI (e.g. contains a raw space or other RFC3986-invalid character) causes Ruby's `URI()` to raise `URI::InvalidURIError`, which propagates uncaught through the call chain that any anonymous, session-less visitor triggers.

### Finding Description
`referer_sanitized_shop_name` is defined as: [1](#0-0) 

`URI(request.referer)` is invoked directly with no `begin/rescue`. This is reachable from `ShopifyApp::LoginProtection#activate_shopify_session`, which is the standard before_action used to protect app routes: when `current_shopify_session.blank?` (i.e., any request without a valid session — the default state for an anonymous visitor), it calls `redirect_to_login`: [2](#0-1) 

`redirect_to_login` calls `login_url_with_optional_shop` → `login_url_params`, which unconditionally calls `referer_sanitized_shop_name`: [3](#0-2) 

None of the surrounding methods rescue `URI::InvalidURIError`. The controller-level `rescue_from` only handles `ShopifyAPI::Errors::HttpResponseError`: [4](#0-3) 

so a `URI::InvalidURIError` raised here is not intercepted anywhere in this concern and will surface as an unhandled exception (500 error in production, full backtrace in development) for a request that requires no authentication at all — the attacker only needs to set an arbitrary `Referer` header, which HTTP allows to contain characters such as spaces that are invalid in a URI (e.g. `Referer: http://example.com/foo bar`). This is distinct from `ShopifyApp::Utils.sanitize_shop_domain`, which already wraps its own URI parsing (`Addressable::URI.parse`) in a `rescue Addressable::URI::InvalidURIError` per the existing fix noted in the changelog for PR #1852, but that fix does not cover this stdlib `URI()` call in `referer_sanitized_shop_name`.

### Impact Explanation
An anonymous client can force any request that hits `redirect_to_login` (i.e., practically all protected app routes when no valid session cookie is present, which is the default unauthenticated state) to raise an unhandled `URI::InvalidURIError`, resulting in a 500 error / crashed request handling on a public, unauthenticated code path. This matches an "application crash / unhandled exception on public route" impact class — it does not by itself leak data or bypass auth, but it is a real, repeatable server-side robustness/availability defect triggerable without any credentials.

### Likelihood Explanation
High feasibility and full repeatability: the attacker needs no authentication, no valid shop, and no special network position — only the ability to set an arbitrary `Referer` header value (trivial with `curl` or any HTTP client), and to hit any route protected by `ShopifyApp::LoginProtection#activate_shopify_session` while unauthenticated (the default case for any anonymous first request).

### Recommendation
Wrap the `URI(request.referer)` call in `referer_sanitized_shop_name` with a `rescue URI::InvalidURIError` (and consider `rescue URI::InvalidComponentError`), returning `nil` on failure, mirroring the existing pattern used in `ShopifyApp::Utils.uri_from_shop_domain`. The equivalent unguarded `URI(request.referer || "/")` call in `LoginProtection#redirect_to_login` (line 114) should receive the same treatment.

### Proof of Concept
```ruby
# test/shopify_app/controller_concerns/login_protection_test.rb (illustrative)
test "redirect_to_login does not raise on malformed Referer header" do
  @controller.request.env["HTTP_REFERER"] = "http://example.com/foo bar" # unescaped space -> invalid URI
  assert_nothing_raised do
    get :some_protected_action # no session cookie set -> activate_shopify_session triggers redirect_to_login
  end
  assert_response :redirect # expect graceful redirect, not 500
end
```
Expected current (buggy) behavior: `URI::InvalidURIError: bad URI(is not URI?): "http://example.com/foo bar"` propagates and the test/request fails with an unhandled exception instead of completing the redirect.
