## Title
Truncating cast in `allocate_response_region` can silently under-allocate the shared response region, leading to out-of-bounds writes across the Agave/scheduler shared-memory boundary - (File: `scheduling-utils/src/responses_region.rs`)

### Summary
The reported bug class is an unchecked integer multiplication feeding an allocator's size parameter, where the product can overflow the destination integer type and cause a mis-sized allocation. The closest structural analog in this codebase is `allocate_response_region` in [1](#0-0) , which computes the allocation size with `num_transaction_responses.wrapping_mul(core::mem::size_of::<T>())` and then truncates the `usize` result with `as u32` before calling `allocator.allocate(size as u32)`.

### Finding Description
`allocate_response_region` takes `num_transaction_responses: usize`, multiplies it by `size_of::<T>()` using `wrapping_mul` (an explicit, silent-overflow operation), and then narrows the `usize` product to `u32` via an as-cast before passing it to `Allocator::allocate` [2](#0-1) . Both operations discard information on overflow instead of erroring: `wrapping_mul` wraps the `usize` product, and the subsequent `as u32` truncates any remaining high bits. If a large `num_transaction_responses` were ever passed to this function, the size actually requested from the allocator could be far smaller than `num_transaction_responses * size_of::<T>()`, while the returned `TransactionResponseRegion` still records a `num_transaction_responses` count that downstream consumers use to interpret the region [3](#0-2) . Callers later reconstruct slices/iterate over `count` elements based on `num_transaction_responses`, e.g. in `CheckResponsesPtr::iter` and `ExecutionResponsesPtr::iter`, which call `core::slice::from_raw_parts(self.ptr.as_ptr(), self.count)` [4](#0-3) [5](#0-4) , so an under-sized allocation combined with a large recorded count would cause out-of-bounds reads/writes on the shared-memory allocator region.

However, this path is only reachable through `TransactionResponseRegion::num_transaction_responses`, which is a `u8` field [6](#0-5) , and the values that flow into `allocate_response_region` originate from iterator lengths bounded by `MAX_TRANSACTIONS_PER_MESSAGE` (referenced throughout `core/src/banking_stage/consume_worker.rs` and `scheduling-utils/src/bridge/bindings.rs`/`transaction_ptr.rs`). Given that batch sizes are capped at a small constant well under `u8::MAX`, `num_transaction_responses * size_of::<T>()` cannot realistically approach `u32::MAX` (or even `u8::MAX * size_of::<ExecutionResponse or CheckResponse>()`), so the `wrapping_mul`/`as u32` truncation is not attacker-triggerable under the existing call sites and asserts (`assert!(batch.len() <= MAX_TRANSACTIONS_PER_MESSAGE)` in `scheduling-utils/src/bridge/bindings.rs`).

### Impact Explanation
If this size computation were ever fed by an unbounded or larger-than-`u8`-capacity value (e.g., a future refactor removing the `MAX_TRANSACTIONS_PER_MESSAGE`/`u8` cap, or a new caller that doesn't respect it), the silent wraparound in `wrapping_mul`/`as u32` would produce an under-sized shared-memory allocation while the recorded transaction count remains large, leading to out-of-bounds writes into the scheduler's shared allocator arena — a memory-corruption primitive in the banking-stage/TPU packet-processing path. As implemented today with the existing `u8` cap and `MAX_TRANSACTIONS_PER_MESSAGE` bound, the overflow cannot actually be reached.

### Likelihood Explanation
Low. The `num_transaction_responses` value is architecturally constrained to fit in a `u8` (per the `TransactionResponseRegion` struct) and is further bounded by `MAX_TRANSACTIONS_PER_MESSAGE` in all current call paths (`core/src/banking_stage/consume_worker.rs`, `scheduling-utils/src/bridge/bindings.rs`), so the multiplication `num_transaction_responses * size_of::<T>()` stays far below `u32::MAX` in practice. There is no remote/unprivileged input in the current codebase that can drive `num_transaction_responses` to a value large enough to overflow `u32`.

### Recommendation
Replace the `wrapping_mul`/`as u32` truncation in `allocate_response_region` (`scheduling-utils/src/responses_region.rs:57-58`) with a checked computation, e.g. `u32::try_from(num_transaction_responses).ok().and_then(|n| n.checked_mul(size_of::<T>() as u32))`, returning `None`/an error on overflow instead of silently truncating, so the function is safe independent of future changes to how `num_transaction_responses` is bounded upstream.

### Proof of Concept
Not exploitable today given the `u8` cap on `TransactionResponseRegion::num_transaction_responses` and the `MAX_TRANSACTIONS_PER_MESSAGE` bound enforced at all call sites (e.g., `assert!(batch.len() <= MAX_TRANSACTIONS_PER_MESSAGE)` in `scheduling-utils/src/bridge/bindings.rs`). A concrete PoC would require a code path that calls `allocate_response_region::<T>(allocator, tag, num_transaction_responses)` with `num_transaction_responses` large enough that `num_transaction_responses * size_of::<T>() > u32::MAX`; no such caller currently exists in this codebase.
