### Title
Unvalidated `Participant` index into `enc_keys`/`commitments` maps panics during DKG blame evaluation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The Packetbeat bug class is improper validation of an array index (CWE-129): an index derived from external input is used to index a container, causing a panic and process termination (DoS). The analogous pattern exists in PedPoP's blame-adjudication path: `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with `Participant` values supplied by the accusing party, without checking that those participants were ever registered. Indexing a `HashMap` with `map[&key]` panics when the key is absent, so a crafted blame accusation crashes the process evaluating it.

### Finding Description

`AdditionalBlameMachine::blame` and `BlameMachine::blame` take `sender` and `recipient` `Participant` values describing the accusation and forward them to `blame_internal` (crypto/dkg/pedpop/src/lib.rs:674-682, 575-631). `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`. Inside `decrypt_with_proof`, when a proof is present, the DLEq verification indexes the encryption-key map with the accuser-declared `decryptor`:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```
(crypto/dkg/pedpop/src/encryption.rs:383-390)

`enc_keys` is only populated via `Decryption::register` for participants `1..=n` (encryption.rs:351-362, lib.rs:654-661). If `decryptor` is a `Participant` value outside that set — or any participant whose key was not registered — `self.enc_keys[&decryptor]` panics on the missing-key index before the proof is even checked, so the panic needs no valid proof. Similarly, if decryption succeeds, `blame_internal` evaluates `self.commitments[&sender]` (lib.rs:599), which panics for any `sender` not in the commitments map; the accuser can forge the required per-message PoP for an arbitrary `from` index because `pop_challenge` merely binds `sender.to_bytes()` and the accuser controls `msg.key` and its secret (encryption.rs:302-324).

The index (`Participant` u16) reaches the map unchecked: `Participant::new` only rejects zero (crypto/dkg/src/lib.rs:29-35), and neither `blame` nor `blame_internal` nor `decrypt_with_proof` bounds `sender`/`recipient` against `n` or the registered sets.

### Impact Explanation

An unprivileged party submitting a blame accusation (or, for `AdditionalBlameMachine`, any party feeding the adjudicator an accusation naming arbitrary `sender`/`recipient` indexes) can deterministically panic the process performing blame evaluation. This is a denial of service against DKG fault resolution: a malicious DKG participant can send garbage shares, then crash any node that tries to adjudicate blame for them by embedding out-of-range participant indexes, stalling or aborting key generation and preventing the faulty party from being identified/slashed. This mirrors the CVE's impact — a crafted input causes a panic that terminates the host process.

### Likelihood Explanation

Reachability requires only that the attacker can get a blame statement evaluated, which is the designed response to a faulty share — i.e., the attacker first behaves faultily (cheap) and the honest nodes themselves invoke `blame`/`AdditionalBlameMachine::blame` with attacker-influenced indexes. The `sender` field is attacker-controlled (the PoP binds the index the signer claims, and the signer is the attacker constructing the message). The `decryptor`/`recipient` in the proof path is taken verbatim from the accusation. No cryptographic break is needed; severity is Medium (DoS only, no secret leakage or forgery).

### Recommendation

Validate `sender` and `recipient` before indexing:

- In `AdditionalBlameMachine::new`, store `n` and have `blame`/`blame_internal` return an error (or blame the accuser) when `u16::from(sender) > n` or `u16::from(recipient) > n`.
- Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get(&...)` plus a graceful error/early-return identifying the accusing party as faulty for naming unknown participants.

### Proof of Concept

```rust
// n = 3 participants; AdditionalBlameMachine built with the 3 real commitment msgs.
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker (or an accusation naming a bogus recipient) supplies:
//   sender    = Participant::new(1)            // any value
//   recipient = Participant::new(77)           // not registered in enc_keys (only 1..=3 are)
//   msg       = any EncryptedMessage<SecretShare> with a valid PoP for `from`
//               (attacker knows msg.key's discrete log, so SchnorrSignature::sign succeeds;
//                or msg with invalid PoP still reaches the index if proof is supplied)
//   proof     = Some(arbitrary EncryptionKeyProof)  // never verified — panic happens first
machine.blame(sender, Participant::new(77).unwrap(), msg, Some(proof));
// Decryption::decrypt_with_proof evaluates `self.enc_keys[&Participant(77)]`
// -> HashMap index panic -> process aborts before DLEq verification runs.
```

Alternatively, with a valid `recipient` (the accuser's own index, so a valid `proof` can be produced) and `sender = Participant::new(77)`, `blame_internal` reaches `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) and panics on the missing commitments entry — the accuser signs the PoP with `from = 77` since `pop_challenge` binds only the serialized index (encryption.rs:317).
