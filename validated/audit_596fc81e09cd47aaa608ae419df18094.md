## Confirmed: `check_dependencies` (upgrade-policy dependency check) is only wired into `freeze_code_object`, never into `publish_package`

The grep confirms `check_dependencies` only appears three times in `code.move`: its definition, and a single call site inside `freeze_code_object`. It is not called anywhere in `publish_package` [1](#0-0) .

### Title
Immutable/compatible package upgrade-policy vs. dependency-policy invariant is enforced only at object freeze time, not at publish/upgrade time - (File: aptos-move/framework/aptos-framework/sources/code.move)

### Summary
`code::publish_package` never calls `check_dependencies`, so a package can be published (or upgraded) with an `immutable` or `compatible` upgrade policy while depending on a package whose own upgrade policy is strictly weaker (e.g. `arbitrary`/mutable), violating the documented and audited invariant that "the upgrade policy of a package must not exceed the strictness level imposed by its dependencies."

### Finding Description
`PackageMetadata.deps` is a declared list of `PackageDep { account, package_name }` entries. The function `check_dependencies` walks this list and asserts `dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy` (`EDEP_WEAKER_POLICY`), and additionally enforces `EDEP_ARBITRARY_NOT_SAME_ADDRESS` for `arbitrary` deps [2](#0-1) .

This is exactly the invariant documented and marked "Enforcement: This has been manually audited" in the module's own formal-spec header ("No. 5: The upgrade policy of a package must not exceed the strictness level imposed by its dependencies... In addition, the native code properly restricts the use of dependencies outside the passed-in metadata") [3](#0-2) , and matches the CLI/user-facing documentation stating an `immutable` package cannot refer, directly or indirectly, to a `compatible` package [4](#0-3) .

However, walking through `publish_package` end-to-end: it records deploy owners, checks `check_upgradability` (policy monotonicity within the *same* package name) and `check_coexistence` (module-name clash with *other* packages at the same address), updates the registry, emits the `PublishPackage` event, and finally calls the native `request_publish[_with_allowed_deps]` [5](#0-4) . `check_dependencies` is not part of this sequence. The native side (`aptos_vm.rs::validate_publish_request`) only checks that immediate dependencies of published modules are within the caller-declared `allowed_deps` address/module set — it never inspects any dependency's `upgrade_policy` [6](#0-5) .

The only place `check_dependencies` is actually invoked is `freeze_code_object`, which is exclusive to the object-code-deployment flow (`object_code_deployment::freeze_code_object`) [7](#0-6) . Regular account-address packages published directly with `upgrade_policy_immutable()` (e.g. via `code::publish_package_txn`, `resource_account::create_resource_account_and_publish_package`, or `large_packages` chunked publish to an account) never call `freeze_code_object` and therefore never have their declared dependencies' policies validated at all.

### Impact Explanation
An attacker (or an unwitting integrator) can publish a package `P` at their own account address (or an object address without ever calling `freeze_code_object`) declaring `upgrade_policy = immutable` while listing a dependency `D` whose actual on-chain policy is `compatible` or even `arbitrary`. Downstream users/auditors who rely on the on-chain `PackageMetadata.upgrade_policy == immutable` as the guarantee "no unexpected updates can happen under the hood" (as documented) are misled: the dependency `D` can later be freely (or compatibly) upgraded by its own owner, silently changing behavior/data layout reachable from `P`'s "immutable" code, without `P` itself ever being touched. This breaks the code-safety invariant that immutable/compatible packages have a verified, policy-consistent dependency closure — a "compatibility, upgrade-policy, or allowed-dependency bypass that places forbidden bytecode on chain" per the impact criteria, and it is a mismatch between the metadata that is verified/stored and the guarantee callers are told it provides.

### Likelihood Explanation
High likelihood of occurrence in practice: this requires no special privilege beyond normal permissionless publishing (the "attacker" is simply the publisher of package `P`, who fully controls `P`'s own metadata, including its declared `deps` and `upgrade_policy`). No feature flag, admin action, or race condition is needed — any account can publish a package today claiming `immutable` while depending on mutable code, since the enforcement path (`check_dependencies`) is dead code for the standard publish flow. The only place it's exercised is the far less common object-freeze operation.

### Recommendation
Call `check_dependencies` (or an equivalent policy-consistency check) from within `publish_package` itself for every publish/upgrade, not just from `freeze_code_object`, so that the dependency-policy invariant documented in `code.spec.move` (#5) actually holds at the time metadata is committed on-chain, independent of whether the package was deployed under an account or later frozen as an object.

### Proof of Concept
1. Deploy package `D` at address `0xD1` with `upgrade_policy = compatible` (default via `PackageBuilder::with_policy(UpgradePolicy::compat())` used throughout the test-harness helpers [8](#0-7) ).
2. Publish package `P` at a different address `0xP1` with `upgrade_policy = immutable` and a `PackageDep { account: 0xD1, package_name: "D" }` entry in its metadata, using `code::publish_package_txn` directly (not via `object_code_deployment`, so `freeze_code_object`/`check_dependencies` is never invoked).
3. Observe the transaction succeeds — `check_upgradability`/`check_coexistence` don't inspect cross-package dependency policy, and the native `request_publish` only checks module-name/address membership in `allowed_deps`, not policy strength.
4. Later, upgrade `D` (still `compatible`) with new logic/state; `P`'s on-chain metadata still claims `immutable`, but code reachable transitively through `D` has changed underneath it, contradicting the on-chain "immutable" guarantee.

(Note: I was not able to trace every historical code path — e.g., whether `code_dependency_check_enabled()`/`allowed_deps` gating in the native layer was intended to substitute for this policy check in some newer feature-gated mode — so this should be verified against the intended design of `request_publish_with_allowed_deps` before treating it purely as a regression versus an existing, always-present gap.)

    /// Check that the upgrade policies of all packages are equal or higher quality than this package. Also
    /// compute the list of module dependencies which are allowed by the package metadata. The later
    /// is passed on to the native layer to verify that bytecode dependencies are actually what is pretended here.
    fun check_dependencies(publish_address: address, pack: &PackageMetadata): vector<AllowedDep>
    acquires PackageRegistry {
        let allowed_module_deps = vector::empty();
        let deps = &pack.deps;
        deps.for_each_ref(|dep| {
            let dep: &PackageDep = dep;
            assert!(exists<PackageRegistry>(dep.account), error::not_found(EPACKAGE_DEP_MISSING));
            if (is_policy_exempted_address(dep.account)) {
                // Allow all modules from this address, by using "" as a wildcard in the AllowedDep
                let account: address = dep.account;
                let module_name = string::utf8(b"");
                vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
            } else {
                let registry = borrow_global<PackageRegistry>(dep.account);
                let found = vector::any(&registry.packages, |dep_pack| {
                    let dep_pack: &PackageMetadata = dep_pack;
                    if (dep_pack.name == dep.package_name) {
                        // Check policy
                        assert!(
                            dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy,
                            error::invalid_argument(EDEP_WEAKER_POLICY)
                        );
                        if (dep_pack.upgrade_policy == upgrade_policy_arbitrary()) {
                            assert!(
                                dep.account == publish_address,
                                error::invalid_argument(EDEP_ARBITRARY_NOT_SAME_ADDRESS)
                            )
                        };
                        // Add allowed deps
                        let account = dep.account;
                        let k = 0;
                        let r = vector::length(&dep_pack.modules);
                        while (k < r) {
                            let module_name = vector::borrow(&dep_pack.modules, k).name;
                            vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
                            k += 1;
                        };
                        true
                    } else {
                        false
                    }
                });
                assert!(found, error::not_found(EPACKAGE_DEP_MISSING));
            };
        });
        allowed_module_deps
    }

Those policies are ordered by strength such that `compatible < immutable`,
i.e., compatible is weaker than immutable. The policy of a package on-chain can
only get stronger, not weaker. Moreover, the policy of all dependencies of a
package must be stronger or equal to the policy of the given package. For example,
an `immutable` package cannot refer directly or indirectly to a `compatible` package.
