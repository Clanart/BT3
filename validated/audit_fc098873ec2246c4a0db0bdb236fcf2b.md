## Title
App Proxy signature verification uses ambiguous, non-canonical concatenation, allowing HMAC signature collisions (`abi.encodePacked`-style bug) - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#calculated_signature` builds the string it HMACs by concatenating `"key=value"` fragments (sorted, joined with commas for arrays, then joined with no separator between fragments) instead of using an unambiguous, length-prefixed or otherwise canonical encoding. This is the exact bug class described in the reference report: packing variable-length data with no delimiters/length markers means two semantically different parameter sets can serialize to the identical byte string and therefore produce the identical HMAC signature.

### Finding Description
`query_string_valid?` extracts `signature` from the query string and compares it to a value computed by `calculated_signature`: [1](#0-0) 

`calculated_signature` builds the signed message like this: [2](#0-1) 

`query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join` concatenates all `key=value` fragments with **no separator between fragments**, and joins array values with a bare comma with **no escaping**. Because query parameter values may legally contain the literal characters `=` and `,` (percent-decoded by `Rack::Utils.parse_query`, which splits the raw query string on `&`/`=` *before* decoding, so decoded `=`/`,` inside a value never affect key/value boundaries at parse time), the resulting concatenated string is not a canonical/injective encoding of the parameter hash. Two different parameter hashes can serialize to the exact same string and thus produce the exact same HMAC digest — precisely the collision class described in the report (packing differently-sized/variable fields without delimiters).

Concrete collision:
- Hash A: `{"a" => "1", "bc" => "2"}` → sorted fragments `"a=1"`, `"bc=2"` → concatenated `"a=1bc=2"`
- Hash B: `{"a" => "1bc=2"}` → sorted fragments `"a=1bc=2"` → concatenated `"a=1bc=2"`

Both hashes serialize to the identical string `"a=1bc=2"`, so `OpenSSL::HMAC.hexdigest` produces the identical signature for two structurally different parameter sets. A similar collision exists via the array-join step (e.g., `["a,b"]` vs `["a","b"]` both join to `"a,b"`).

### Impact Explanation
This breaks the injectivity guarantee that a MAC-based verification scheme depends on: a signature that is valid for one parameter set is also valid for a different, differently-structured parameter set. Since App Proxy requests are triggered by anonymous storefront visitors (the attacker fully controls arbitrary extra query parameters forwarded through the proxy, per `docs/shopify_app/engine.md:56`), an attacker can engineer a request whose Shopify-proxy-signed parameter set collides with an alternate parameter interpretation, causing the app to accept the alternate/forged semantics under a signature that was never actually computed over it. This falls squarely in the "accepted forged signed request" category for the App Proxy HMAC verification path used by `ShopifyApp::AppProxyVerification`, which every `app_proxy_controller.rb` generated by this gem relies on: [3](#0-2) .

### Likelihood Explanation
Exploitation requires the attacker to be able to influence which query parameters get signed by the proxy (true, since App Proxy forwards arbitrary attacker-supplied query parameters along with Shopify-added ones such as `shop`, `path_prefix`, `timestamp`, `logged_in_customer_id`) and to construct a colliding alternate parameter set. This is a deterministic, reproducible string-construction exercise (not a cryptographic break of HMAC-SHA256 itself), so likelihood is driven entirely by the attacker's ability to control input values, which is realistic for a public storefront-facing endpoint.

### Recommendation
Replace the ad-hoc `"key=value"` concatenation with an unambiguous canonical encoding before hashing, e.g.:
- Percent-encode/escape `=`, `,`, and any separator characters within keys and values before concatenation, or
- Use a length-prefixed or otherwise injective encoding (analogous to using `abi.encode` instead of `abi.encodePacked`), or
- Join fragments with an unambiguous delimiter that is itself escaped within keys/values (e.g., `URI.encode_www_form` semantics), and join array values with an escaped separator rather than a bare comma.

This aligns with Shopify's own documented app-proxy signature algorithm, which should be reproduced exactly and defensively hardened against this ambiguity.

### Proof of Concept
```ruby
require "openssl"

secret = "shared_secret"

def calculated_signature(secret, query_hash_without_signature)
  sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join
  OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), secret, sorted_params)
end

hash_a = { "a" => "1", "bc" => "2" }
hash_b = { "a" => "1bc=2" }

sig_a = calculated_signature(secret, hash_a)
sig_b = calculated_signature(secret, hash_b)

puts sig_a == sig_b # => true, distinct parameter sets share a valid signature
```
`AppProxyVerification#query_string_valid?` (`lib/shopify_app/controller_concerns/app_proxy_verification.rb:17-27`) will accept either of these two structurally different query strings under the same `signature` value, demonstrating that the verification is not injective over the parameter space it claims to authenticate.
