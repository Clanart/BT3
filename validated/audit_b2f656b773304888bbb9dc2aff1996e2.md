### Title
Incomplete/permissive extension allow-list in `isSafeFileExtension()` lets a malicious repository trigger script execution via "Open with Default Program" - (File: app/src/ui/lib/context-menu.ts)

### Summary
The external report describes a Solidity access-control modifier that decides trust by linearly scanning an unbounded array, which is fragile and easy to get wrong. The structural analog in GitHub Desktop is `isSafeFileExtension()`, a small hard-coded array used as the sole gate deciding whether the "Open with Default Program" context-menu action is allowed to run a file straight from a cloned/fetched repository. Like the Solidity pattern, the security decision hinges entirely on membership in a short, manually maintained list — and here that list is both incomplete and platform-scoped, so the "access control" fails open for the vast majority of dangerous file types and for two of three supported OSes.

### Finding Description
`isSafeFileExtension()` is the only check gating whether a file selected in the Changes list, History view, or Pull Request diff view can be opened via `shell.openExternal('file://...')` (i.e., "Open with Default Program"): [1](#0-0) 

```
const RestrictedFileExtensions = ['.cmd', '.exe', '.bat', '.sh']
...
export function isSafeFileExtension(extension: string): boolean {
  if (__WIN32__) {
    return RestrictedFileExtensions.indexOf(extension.toLowerCase()) === -1
  }
  return true
}
```

Two broken invariants mirror the reported bug class:
1. On Windows, the "trust" decision is `indexOf() === -1` against a 4-item blocklist. This omits numerous natively-executable Windows extensions such as `.com`, `.scr`, `.pif`, `.msi`, `.msc`, `.ps1`, `.vbs`, `.js`, `.jar`, `.hta`, `.lnk`, `.wsf`, etc. Any of these, if present in a cloned/fetched repository (or arriving via a pull request diff), is classified "safe" and the "Open with Default Program" menu entry is enabled.
2. On macOS and Linux (`__DARWIN__`/other), the function unconditionally returns `true` — there is no blocklist applied at all, so every extension (including `.command`, `.sh`-with-executable-bit, `.desktop`, AppleScript, etc.) is treated as safe.

The callers all just gate menu-item `enabled` state on this boolean and then call `openFile()`, which does `shell.openExternal('file://' + fullPath)`: [2](#0-1) 

`shell.openExternal` on a `file://` URL delegates to the OS's "open with associated default application" behavior — for the omitted extensions above that means direct execution by the OS shell, not passive viewing.

This check is invoked from several UI surfaces that operate on attacker-influenced content: the Changes list context menu, the History/commit file list context menu, and the Pull Request "Files changed" context menu: [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who controls a cloned/fetched repository (or a pull request the victim views in Desktop) can plant a file with an extension that `isSafeFileExtension()` misclassifies as safe (e.g. `evil.scr`, `evil.com`, `evil.js`, `evil.jar` on Windows; effectively anything on macOS/Linux). When the victim right-clicks that file in the Changes list, History view, or PR "Files changed" view and selects "Open with Default Program" — a normal, expected Desktop workflow for inspecting an unfamiliar file — the OS executes it directly via `shell.openExternal`. This yields arbitrary code execution in the context of the logged-in user, satisfying the "attacker controls a cloned/fetched repository ... result is code execution" criterion.

### Likelihood Explanation
The bar for exploitation is low: no admin rights, no pre-existing malware, and no unnatural steps are required — "Open with Default Program" is a documented, discoverable context-menu action exposed specifically to let users open non-diffable/binary files. A victim reviewing an untrusted fork's PR or a newly cloned third-party repository is a completely ordinary Desktop scenario. The blocklist's coverage gap (4 Windows extensions vs. the dozens of natively executable Windows extensions) and the total absence of filtering on macOS/Linux make the "guard" easy to bypass without any unusual technique.

### Recommendation
Replace the narrow hard-coded blocklist with a maintained, cross-platform allow/deny list of executable-capable extensions (covering `.com`, `.scr`, `.pif`, `.msi`, `.msc`, `.ps1`, `.vbs`, `.vbe`, `.js`, `.jse`, `.jar`, `.hta`, `.lnk`, `.wsf`, `.wsh`, `.cpl`, `.reg`, `.command`, `.app`/bundle heuristics, executable-bit-set files, etc.), and apply the same restriction on `__DARWIN__`/Linux instead of unconditionally returning `true`. Consider also warning the user before invoking `openExternal` on any file located inside a repository that has not been explicitly trusted, similar to Office's "Protected View"/Mark-of-the-Web pattern.

### Proof of Concept
1. Attacker creates/forks a public repository and adds a file `payload.scr` (a renamed PE executable) or, on macOS, `payload.command` with a malicious shebang script, and commits it.
2. Victim clones the repository (or opens the attacker's PR) in GitHub Desktop.
3. Victim right-clicks `payload.scr`/`payload.command` in the Changes list (or PR Files Changed view) and selects "Open with Default Program", which is enabled because `isSafeFileExtension('.scr')` (Windows) or `isSafeFileExtension('.command')` (macOS) returns `true`.
4. `openFile()` → `shell.openExternal('file://.../payload.scr')` causes the OS to execute the file, achieving code execution as the victim user.
