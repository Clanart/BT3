Audit Report

## Title
`is_simple_vote_transaction_view` in sigverify skips instruction-data validation performed by the canonical vote checker, causing SIMPLE_VOTE_TX misclassification - (File: perf/src/sigverify.rs)

## Summary
`perf/src/sigverify.rs::is_simple_vote_transaction_view` classifies a packet as a simple vote transaction based only on signature count, legacy-message version, single-instruction count, and the instruction's `program_id` matching the vote program — it never deserializes the instruction data to confirm it decodes to a `VoteInstruction` variant satisfying `is_single_vote_state_update()`. [1](#0-0) . This diverges from `vote/src/vote_parser.rs::is_valid_vote_only_transaction`, which performs the same program-id/instruction-count checks but additionally requires `limited_deserialize::<VoteInstruction>(...).map(|ix| ix.is_single_vote_state_update())` to succeed. [2](#0-1) 

## Finding Description
In `verify_packet`, the flag `PacketFlags::SIMPLE_VOTE_TX` is set purely based on `is_simple_vote_transaction_view`'s result, and this same boolean also determines whether the packet is exempted from `reject_non_vote` filtering (i.e., a mislabeled "vote" packet skips the non-vote-rejection short-circuit and proceeds directly to signature verification). [3](#0-2)  A transaction with a single instruction whose `program_id_index` resolves to the vote program ID, ≤2 signatures, and a legacy message will be classified `is_simple_vote_tx = true` regardless of what garbage or non-single-vote-state-update instruction data it carries, because the function only checks `*program_id == solana_sdk_ids::vote::id()` and never inspects `instruction.data`. [4](#0-3) 

By contrast, the canonical vote classifier used elsewhere for `RuntimeTransaction` construction (`is_simple_vote_transaction` calling into `solana_transaction::simple_vote_transaction_checker::is_simple_vote_transaction_impl`), and `vote_parser::is_valid_vote_only_transaction`, and `LatestValidatorVote::new_from_view` all require deserializing the instruction and matching against valid `VoteInstruction` variants. [5](#0-4) [6](#0-5)  This confirms the divergence: sigverify's classifier is strictly looser than the downstream/canonical classifiers.

However, I was unable to verify, within the tool budget available, the actual implementation body of `is_simple_vote_transaction_impl` (defined in the external `solana_transaction` crate, not present in this repo's indexed source), so I cannot confirm with certainty whether it also performs instruction-data deserialization or merely checks program_id like the sigverify version. This leaves open the possibility that the "canonical" `RuntimeTransaction`-path classifier is actually just as loose as `is_simple_vote_transaction_view`, and that only `vote_parser::is_valid_vote_only_transaction`/`LatestValidatorVote::new_from_view` are the strict deserializing checkers. Even so, the core claim — that `is_simple_vote_transaction_view` in sigverify disagrees with `vote_parser::is_valid_vote_only_transaction` and `LatestValidatorVote::new_from_view` — is directly supported by the code read.

## Impact Explanation
This is a genuine classification inconsistency between pipeline stages: sigverify can tag a packet with `PacketFlags::SIMPLE_VOTE_TX` when its instruction data does not actually decode to a valid vote instruction, while downstream consumers (`vote_parser::is_valid_vote_only_transaction`, `LatestValidatorVote::new_from_view`) will reject the same transaction as not-a-vote. The concrete effect at the sigverify layer is that such packets bypass the `reject_non_vote` short-circuit (intended to drop non-vote traffic without full signature verification under load) and instead go through full signature verification as if they were legitimate vote traffic — a modest QoS/DoS-adjacent effect on the TPU/sigverify path (extra signature-verification CPU work for garbage packets that should have been cheaply dropped), rather than a fund-theft, false-execution, false-rooting, or consensus-halt outcome. Downstream stages (banking stage, vote_parser, `LatestValidatorVote`) still correctly reject the malformed "vote," so it cannot be used to smuggle a fake vote into stake-weighted vote-processing paths or affect rooting/consensus.

## Likelihood Explanation
Trivially reachable: any unprivileged sender can construct such a legacy, single-instruction, ≤2-signature transaction targeting the vote program with arbitrary instruction data. No privileged relationship or valid signature semantics beyond passing `signature.verify` (which is independent of instruction content) is required to hit the diverging classification.

## Recommendation
Align `is_simple_vote_transaction_view` with the canonical vote-instruction check by deserializing the instruction data (`limited_deserialize::<VoteInstruction>`) and requiring `is_single_vote_state_update()`, consistent with `vote_parser::is_valid_vote_only_transaction`, to avoid extra signature-verification work being performed on non-vote traffic that should be dropped by `reject_non_vote`, and to keep vote-classification consistent across sigverify, banking stage, and vote parsing.

## Proof of Concept
1. Construct a legacy `Transaction` with exactly one instruction whose `program_id` is `solana_sdk_ids::vote::id()`, 1–2 signatures, and instruction `data` set to bytes that fail `limited_deserialize::<VoteInstruction>` or decode to a non-single-vote-state-update variant (e.g., `VoteInstruction::Authorize`).
2. Feed the packet through `perf/src/sigverify.rs::verify_packet` with `reject_non_vote = true`: `is_simple_vote_transaction_view` returns `true` (program-id/count/version checks pass), so the packet skips the non-vote rejection path and is fully signature-verified and tagged `PacketFlags::SIMPLE_VOTE_TX`.
3. Pass the same transaction to `vote_parser::is_valid_vote_only_transaction`: it returns `false` because the instruction fails the `is_single_vote_state_update()` check, demonstrating the cross-stage classification mismatch.

fn is_simple_vote_transaction_view<D: TransactionData>(view: &SanitizedTransactionView<D>) -> bool {
    // vote could have 1 or 2 sigs; zero sig has already been excluded by sanitization.
    if view.num_signatures() > 2 {
        return false;
    }

    // simple vote should only be legacy message
    if !matches!(view.version(), TransactionVersion::Legacy) {
        return false;
    }

    // skip if has more than 1 instruction
    if view.num_instructions() != 1 {
        return false;
    }

    let mut instructions = view.instructions_iter();
    let Some(instruction) = instructions.next() else {
        return false;
    };
    if instructions.next().is_some() {
        return false;
    }

    let program_id_index = usize::from(instruction.program_id_index);
    let Some(program_id) = view.static_account_keys().get(program_id_index) else {
        return false;
    };

    *program_id == solana_sdk_ids::vote::id()
}

pub fn is_valid_vote_only_transaction(tx: &impl SVMTransaction) -> bool {
    let mut instructions = tx.program_instructions_iter();

    let Some((program_id, instruction)) = instructions.next() else {
        return false;
    };

    if instructions.next().is_some() {
        return false;
    }

    if !solana_sdk_ids::vote::check_id(program_id) {
        return false;
    }

    limited_deserialize::<VoteInstruction>(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)
        .map(|ix| ix.is_single_vote_state_update())
        .unwrap_or(false)
}
