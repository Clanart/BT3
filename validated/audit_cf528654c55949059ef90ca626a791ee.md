### Title
Withdrawal-to-operator attribution is unauthenticated and forgeable via SIGHASH_SINGLE|ANYONECANPAY payout witness reuse - ([File: core/src/verifier.rs])

### Summary
`Operator::withdraw` builds the `payout_tx` where the user's Schnorr signature covers only input 0 (withdrawal UTXO) and output 0 (payout) under `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, leaving the OP_RETURN output that encodes the fronting `operator_xonly_pk` completely unsigned. Anyone observing the honest operator's broadcast in the mempool can rebroadcast a competing transaction that reuses the exact input0+witness/output0 but substitutes arbitrary additional funding inputs and an arbitrary OP_RETURN payload, and if it confirms instead, `Verifier::update_finalized_payouts` blindly trusts that OP_RETURN to bind the withdrawal to whatever `operator_xonly_pk` the attacker chose.

### Finding Description
The broken binding, stated as an equality that the protocol needs but does not enforce:

`withdrawals.payout_payer_operator_xonly_pk` (for withdrawal idx `i`) SHOULD equal the xonly pubkey of the party whose own wallet funds actually covered `output0`'s value (the party that ran `fund_raw_transaction`/paid the fee-covering inputs), but it actually equals: whatever bytes appear in the first OP_RETURN output of whichever transaction happens to be the one that spends `withdrawal_utxo` on-chain — regardless of who funded it.

Code path:
1. `Operator::withdraw` (core/src/operator.rs:560-692) builds `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436). The tx has input0 = withdrawal UTXO (`SpendPath::KeySpend`), output0 = user payout, plus an anchor output and an OP_RETURN output carrying `operator_xonly_pk.serialize()`.
2. Only input0's witness is set: `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)` (operator_reimburse.rs:434), and the sighash is computed and verified only for txin 0 with the user-supplied `sighash_type` [1](#0-0) .
3. `SIGHASH_SINGLE|ANYONECANPAY` commits only to input0 (its own prevout) and to the single output at the same index (output0). It commits to nothing else — not the anchor output, not the OP_RETURN, and not any other inputs added later by `fund_raw_transaction` (`add_inputs: Some(true)`, `change_position: Some(1)`) [2](#0-1) .
4. Any party that observes this raw signed witness in the mempool (a normal, unprivileged capability) can construct an alternate transaction that reuses input0+its witness and output0 verbatim, but adds its own funding inputs and an arbitrary OP_RETURN (a different operator's pubkey, garbage, or nothing parseable), and race it into a block instead of the honest operator's broadcast — this is a plain double-spend/fee race on `in_outpoint`, requiring no signature forgery.
5. Whichever transaction actually confirms is picked up by `get_payout_txs_for_withdrawal_utxos` (keyed only on which txid spent `withdrawal_utxo_txid/vout`) and fed into `update_finalized_payouts` (core/src/verifier.rs:2283-2353), which parses the first OP_RETURN output and sets `payout_payer_operator_xonly_pk` to whatever xonly pubkey (or `NULL`, if unparsable) it finds — with no check that this key corresponds to whoever actually paid for the tx [3](#0-2) .
6. This corrupted value is the sole key used by `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313) and is polled unconditionally by every operator's own `PayoutCheckerTask::run_once`, which automatically calls `handle_finalized_payout` → kickoff → `Reimburse` for any match against its own pubkey, with no verification that it itself broadcast or funded that specific payout tx [4](#0-3) . The downstream `validate_payer_is_operator` check (core/src/operator.rs:1686-1740) only re-reads the same corrupted DB column, so it cannot catch the forgery — it is by construction reading the attacker-controlled value.

Why existing guards fail: `SECP.verify_schnorr` only proves input0/output0 integrity, not the OP_RETURN; `Verifier::is_deposit_valid`, `is_kickoff_malicious`, and the presigned N-of-N transaction graph never reference who funded the payout economically — they are set up per-deposit for all operators in advance and are agnostic to which operator's wallet actually paid the withdrawal difference.

### Impact Explanation
Two attacker-selectable outcomes from the same primitive, both meeting Critical severity:
- Attacker sets the OP_RETURN to a real, legitimate operator's public xonly pubkey (public information) while funding the tx with its own inputs. That operator's automated `PayoutCheckerTask` will subsequently kick off and claim `Reimburse` from bridge collateral for a payout it never funded — "an operator reimbursed for a payout it never funded."
- Attacker sets the OP_RETURN to unparsable/garbage/no-real-operator bytes. `payout_payer_operator_xonly_pk` becomes `NULL` and no operator's `PayoutCheckerTask` will ever match it, so no kickoff is ever initiated for that deposit — the deposit's move-to-vault-derived reimbursement flow for that withdrawal permanently stalls, and the honest operator that intended to front it is permanently unable to be reimbursed for it.

The attack is repeatable per-withdrawal (every `withdraw` call produces a fresh SIGHASH_SINGLE|ANYONECANPAY signature exposed once broadcast) and is not tied to any specific operator or deposit — it generalizes across the whole withdrawal flow.

### Likelihood Explanation
The attacker needs zero privileged role: only the ability to observe the Bitcoin mempool (public), extract the raw witness of a broadcast, unconfirmed `payout_tx`, and rebroadcast a modified transaction with a competitive fee rate. Cost is limited to Bitcoin transaction fees plus whatever is needed to relay/mine ahead of the honest broadcast (a standard fee-based mempool race, exploitable whenever an operator processes a withdrawal). No key compromise, no majority hashrate, and no interaction with verifiers/aggregator is required.

### Recommendation
Bind the OP_RETURN (operator attribution) output into the user's signature coverage — e.g., have the user sign with `SIGHASH_ALL` (or otherwise include the OP_RETURN output's commitment in a covenant/second signature), or have operators commit to `operator_xonly_pk` via a mechanism that isn't malleable by third parties (such as a separate presigned/committed value keyed by the deposit rather than parsed from an arbitrary, unauthenticated on-chain OP_RETURN).

### Proof of Concept
`cargo test` plan (regtest, no mainnet/Citrea):
1. Register a deposit and withdrawal in the test DB/regtest as usual; call `Operator::withdraw` for operator A to produce and broadcast `payout_tx_A` (containing `OP_RETURN = A.xonly_pk`), but do not mine it.
2. Read `payout_tx_A` from `getrawmempool`/`getrawtransaction`; extract input0 (outpoint+witness) and output0 verbatim.
3. Construct `payout_tx_B`: same input0+witness+output0, but with attacker's own added funding input(s) and an OP_RETURN containing operator B's xonly pubkey (a different, uninvolved registered operator). Assert `SECP.verify_schnorr` still validates for input0 exactly as in `Operator::withdraw`.
4. Broadcast `payout_tx_B` with higher fee, mine it; ensure `payout_tx_A` is evicted/never confirms.
5. Run `Verifier::update_finalized_payouts` on the block containing `payout_tx_B`; assert `withdrawals.payout_payer_operator_xonly_pk == B.xonly_pk` (not `A.xonly_pk`, and B never called `withdraw` or funded anything).
6. Run operator B's `PayoutCheckerTask::run_once`; assert it returns `Ok(true)` and proceeds to `handle_finalized_payout`, proving B is credited with a payout it never funded.
