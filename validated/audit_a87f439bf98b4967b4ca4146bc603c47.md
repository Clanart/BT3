### Title
`SignableTransaction::new` omits `OP_RETURN` data from fee and weight calculations - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` adds the caller-controlled `OP_RETURN` output to `tx_outs`, but subsequently calculates transaction weight, virtual size, required fee, and maximum-standard-weight eligibility using only `payments`, excluding the already-added data output. [1](#0-0) 

### Finding Description
When `data` is supplied, the function appends an `OP_RETURN` `TxOut` before calling `calculate_weight_vbytes(tx_ins.len(), payments, None)`. [2](#0-1)  The size helper only constructs outputs from its `payments` argument and an optional change output; it has no access to `tx_outs` or the data output. [3](#0-2) 

`needed_fee` is therefore derived from a transaction missing the data output, and the minimum-relay check also uses that understated virtual size. [4](#0-3)  The same omission occurs when change is considered because the second size calculation is again passed `payments` rather than the complete output list. [5](#0-4) 

The returned transaction nevertheless includes the `OP_RETURN`, while `prevouts`, `offsets`, and `needed_fee` describe the understated accounting. [6](#0-5) 

### Impact Explanation
An unprivileged caller able to cause a Bitcoin transaction carrying up to 80 bytes of data to be signed can make the threshold signer produce a transaction whose actual fee rate is lower than the requested `fee_per_vbyte`. [7](#0-6) 

For a boundary fee such as `1` sat/vbyte, the constructor can accept the transaction using the smaller calculated virtual size while the signed transaction is materially larger and below the default relay rate. The result is a validly signed Bitcoin transaction that may be rejected by standard mempool admission or remain unconfirmed, delaying the scheduled payment and requiring the reserved inputs to be re-signed into a corrected transaction.

### Likelihood Explanation
The condition is deterministic whenever `data` is supplied: the omitted output is always included in the final transaction but never included in either fee estimate. The resulting severity depends on the selected fee rate and transaction size; transactions near the minimum relay rate or standard-weight boundary are affected most directly.

### Recommendation
Calculate weight and virtual size from the complete output vector after adding the `OP_RETURN` output. Equivalently, move data-output construction before fee estimation and pass a representation that includes every output to `calculate_weight_vbytes`. Recompute both `weight` and `needed_fee` whenever change is added, and base the maximum-standard-weight and minimum-relay checks on the final transaction.

### Proof of Concept
1. Construct `SignableTransaction::new` with:
   - at least one input,
   - at least one payment,
   - `data = Some(vec![0; 80])`,
   - `change = None`,
   - `fee_per_vbyte = 1`.
2. The function appends the `OP_RETURN`, then estimates size from `payments` only. [8](#0-7) 
3. Let the estimated virtual size be `V_est` and the actual virtual size be `V_actual`; because the `OP_RETURN` is excluded, `V_actual > V_est`.
4. The constructor returns `needed_fee == V_est`, while the actual transaction contains the data output and has `V_actual` virtual bytes. Its actual fee rate is therefore `V_est / V_actual`, below the requested `1` sat/vbyte and potentially below default relay policy.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
