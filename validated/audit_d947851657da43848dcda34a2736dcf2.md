### Title
Silent, unconfirmed rewrite of the `origin` push remote based on optimistic trust of GitHub API `clone_url` - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
The reported OmniXMultisender bug is a case of an "optimistic peer assumption": the contract sends value to a destination it never explicitly verified as trusted, relying on an assumption (same CREATE2 address) instead of a hard, explicit allow-list check. The closest analog in GitHub Desktop is `updateRemoteUrl`, which automatically rewrites a repository's `origin` remote URL to whatever `clone_url` value the GitHub API currently reports, based only on a string-URL-match heuristic rather than an explicit, user-confirmed trust anchor.

### Finding Description
`updateRemoteUrl` compares the repository's cached `gitHubRepository.cloneURL` against the current `defaultRemote.url` to decide whether the user "manually changed" the remote, and if not, it silently calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` with the new `apiRepo.clone_url` supplied by the GitHub API: [1](#0-0) 

The only checks performed are (1) that the URL protocol didn't change, and (2) that the previously known remote URL still equals the previously cached `cloneURL` (i.e., "the user hasn't touched it"): [2](#0-1) 

Nowhere does this logic verify that the *new* `clone_url` still refers to the same underlying repository identity (e.g., a stable numeric repo ID) that the user originally added — it optimistically trusts that "the API says this is my repo's new location" and rewires the destination of all future `git push` operations accordingly, exactly like the multisender optimistically trusted "the CREATE2-deployed contract at this address is the same OmniX peer" without an explicit `peers` mapping check.

`findDefaultRemote` reinforces the same class of "assume a reasonable default in absence of explicit config" behavior for the remote actually used by push/pull, falling back to the first alphabetical remote when `origin` is absent: [3](#0-2) 

and `loadRemotes` further falls back silently to `_defaultRemote` if the tracked upstream remote name can't be found: [4](#0-3) 

### Impact Explanation
If a repository is renamed, transferred, or "repo-jacked" (a well-known GitHub attack class where an abandoned or renamed repo slug is claimed by a different, potentially malicious account), the GitHub API's `clone_url` for that repository will legitimately point to a new location. Desktop's background repository refresh will pick this up via `updateRemoteUrl` and silently repoint the user's `origin` remote to the new URL — with no confirmation dialog, no diff shown to the user, and no verification that the "new" repository is actually still under the same trusted owner/organization. The next time the user pushes, their code/commits (which may contain proprietary source, secrets, or credentials committed accidentally) would be sent to the new — potentially attacker-controlled — destination, corrupting the invariant "what I push goes to the remote I explicitly configured." This is directly analogous to the OmniXMultisender flaw where funds were silently redirected to whatever address was "optimistically" assumed to be the correct peer.

### Likelihood Explanation
LOW-MEDIUM. This requires an attacker to control (or reclaim) the exact repository name/owner slug the victim's `origin` currently maps to after a rename/transfer, and depends on the GitHub API actually returning that URL as `clone_url` for the repository object Desktop already associates with the local repo (matched by ID, not by name), somewhat limiting straightforward repo-jacking. Note: I was unable to fully trace the exact call site(s) in `app/src/lib/stores/app-store.ts` invoking `updateRemoteUrl` (3 references found but not inspected in full) within the tool-call budget, so I cannot confirm the exact trigger conditions (e.g., whether it's gated behind additional repository-ID equality checks upstream) with full certainty — this should be verified against `app-store.ts` before treating this as conclusively exploitable.

### Recommendation
Before rewriting the local `origin` remote URL, require an explicit, user-visible confirmation (similar to the "repository has moved" banner GitHub.com shows), and/or verify that the new `clone_url`'s owner/repo still resolves to the same immutable GitHub repository ID that was recorded when the remote was first configured, rather than trusting a bare URL match/mismatch heuristic.

### Proof of Concept
1. User adds/clones a repository; Desktop caches `gitHubRepository.cloneURL` matching `origin`.
2. Repository is renamed or ownership transfers such that the GitHub API's `clone_url` for the same repository ID now points to a new owner/path (or, in the repo-jacking scenario, the old slug becomes claimable by a different account and Desktop's cached mapping becomes stale/ambiguous).
3. On the next background metadata refresh, `updateRemoteUrl` sees `remoteUrlUnchanged === true` (user hasn't manually edited origin) and `urlsMatch === false`, and silently calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)`. [5](#0-4) 
4. The user, unaware of the silent remote change, runs `git push` (via Desktop's push flow using `remote.url` from the just-rewritten remote), and their commits are sent to the new/unverified destination. [6](#0-5)

  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
