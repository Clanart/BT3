## Title
Memory leak in `upb_JsonEncoder_Encode` when JSON-encoding an `Any` field with attacker-controlled content triggers an encoder error - (File: `upb/json/encode.c`)

## Summary
`upb_JsonEncode()` lazily allocates a scratch `upb_Arena` (`e->arena`) the first time a `google.protobuf.Any` field is encountered while serializing a message to ProtoJSON. That arena is only freed on the success path of `upb_JsonEncoder_Encode`. Every error path inside the encoder (bad type URL, unresolvable `Any` type, malformed embedded bytes, invalid timestamp/duration/FieldMask, etc.) triggers `UPB_LONGJMP` back to the `UPB_SETJMP` at function entry, which returns immediately without ever calling `upb_Arena_Free(e->arena)`. This is directly analogous to CVE-2017-13058's `WritePCXImage`, which allocates a buffer and leaks it on an error/early-return path instead of freeing it during cleanup.

## Finding Description
`jsonenc_arena()` creates the scratch arena on first use: [1](#0-0) 

This arena backs a newly-decoded `Any` submessage: [2](#0-1) 

The only place the arena is freed is the success branch of the top-level encode driver: [3](#0-2) 

Because every `jsonenc_err`/`jsonenc_errf` call performs `UPB_LONGJMP(e->err, 1)` (see `upb/json/encode.c` lines 58-70), control returns to `if (UPB_SETJMP(e->err) != 0) return -1;` at line 791, bypassing line 794 (`if (e->arena) upb_Arena_Free(e->arena);`) entirely. Once `upb_JsonEncode()` returns, the local `jsonenc e` struct (and its `arena` pointer) goes out of scope; no other reference to that arena exists anywhere in the caller stack, so the memory backing it (and anything allocated from it, e.g. the decoded `Any` payload message) is leaked for the remainder of the process.

The failed invariant that transfers from the CVE is: **"resource allocated in a helper structure must be released along every exit path of the function, not only the success path."** In `WritePCXImage`, a buffer allocated for pixel data was not released when the write failed partway through; here, `e->arena` is allocated as soon as an `Any` field is first hit, but is only released along the success return, not any of the numerous `jsonenc_err`/`jsonenc_errf` early exits.

## Impact Explanation
This is a per-call memory leak (bounded by the size of the temporary `Any` decode target), not an unbounded/attacker-driven memory-growth or resource-exhaustion primitive by itself — each vulnerable encode call leaks one arena's worth of memory (typically small, proportional to the size of the embedded `Any` payload). Repeated invocation (e.g., a service that JSON-serializes attacker-supplied protobuf messages containing malformed `Any` fields in a loop, such as a logging/telemetry/gateway service) will accumulate leaked memory over time, consistent with the CWE-401/"Denial of Service (memory leak)" classification of the original CVE (rated Medium, C:N/I:N/A:H).

## Likelihood Explanation
An ordinary client that controls the content of a protobuf message which is later serialized to ProtoJSON by an application using `upb_JsonEncode` (via `protobuf.util.MessageToJson`-style calls, Ruby/PHP/Python `to_json`/`MessageToJson` wrappers backed by upb, etc.) can trivially set:
- an `Any.type_url` with no `/` (bad URL) or an unresolvable type name, or
- a syntactically valid `Any` wrapping malformed bytes that fail to decode as the target type, or
- an invalid `Timestamp`/`Duration`/`FieldMask` value nested inside an `Any`.

Any of these deterministically reaches `jsonenc_err`/`jsonenc_errf` after `jsonenc_arena(e)` has already allocated the arena in `jsonenc_any`, guaranteeing the leak on every such call. This requires no privileged access, no huge payloads, and no depth/size-limit bypass — it is a straightforward, always-reachable missing-cleanup bug on an error path, closely mirroring the deterministic nature of the `WritePCXImage` leak.

## Recommendation
Ensure `e->arena` is freed on every exit path of `upb_JsonEncoder_Encode`, not just the success path, e.g.:
```c
static size_t upb_JsonEncoder_Encode(jsonenc* const e,
                                     const upb_Message* const msg,
                                     const upb_MessageDef* const m,
                                     const size_t size) {
  size_t ret;
  if (UPB_SETJMP(e->err) != 0) {
    ret = -1;
  } else {
    jsonenc_msgfield(e, msg, m);
    ret = jsonenc_nullz(e, size);
  }
  if (e->arena) upb_Arena_Free(e->arena);
  return ret;
}
```
This guarantees `e->arena` is released regardless of whether encoding succeeds or `UPB_LONGJMP`s out via an error.

## Proof of Concept
Conceptual reproduction (would need to be run in a Devin session against the actual build/tests to confirm with a leak-detection tool such as ASan/LSan or Valgrind, which I was not able to execute here):
1. Build a message containing a `google.protobuf.Any` field whose `type_url` has no `/`, e.g. `type_url = "badurl"`, `value = ""`.
2. Call `upb_JsonEncode(msg, ..., ext_pool, options, buf, size, &status)`.
3. Execution reaches `jsonenc_any()` → `jsonenc_arena(e)` (allocates `e->arena`) → `jsonenc_getanymsg()` → `goto badurl` → `jsonenc_errf(e, "Bad type URL: ...")` → `UPB_LONGJMP(e->err, 1)`.
4. Control returns to `upb_JsonEncoder_Encode`'s `if (UPB_SETJMP(e->err) != 0) return -1;`, skipping the `upb_Arena_Free(e->arena)` call at line 794.
5. Repeating this call in a loop and observing process RSS growth (or running under Valgrind/LeakSanitizer) would confirm the arena is never reclaimed.

I was unable to actually execute this PoC or a sanitizer run in this session; the above is a source-level trace of the exact missing-cleanup control flow, not a confirmed dynamic-analysis result.
