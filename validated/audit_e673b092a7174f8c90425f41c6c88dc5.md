### Title
Governance-settable `Kip71GasTarget` value of 0 causes a division-by-zero panic in `NextMagmaBlockBaseFee`, crashing block processing on all nodes - ([File: params/kip71_config.go])

### Summary
`NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without any zero-check, unlike the sibling parameter `BaseFeeDenominator`, which explicitly falls back to a safe default when zero. A governance vote that sets `kip71.gastarget` to `0` (which passes validation, since it uses `noopFormatChecker`) will cause a `big.Int` division-by-zero panic the moment `parentGasUsed != 0`, i.e. on essentially every subsequent block. This matches the CVE-2025-71002 bug class (unchecked division causing a floating-point/arithmetic exception DoS), but here manifests as a Go runtime panic that halts block processing/consensus on every node that evaluates this function.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next block's Magma base fee: [1](#0-0) 
For `BaseFeeDenominator`, a `0` value is explicitly detected and replaced with a safe fallback (`64`) "to avoid panic". No equivalent guard exists for `GasTarget`: [2](#0-1) [3](#0-2) 
Both the "gas used above target" and "gas used below target" branches perform `x.Div(x, new(big.Int).SetUint64(gasTarget))`, where `gasTarget := kc.GasTarget`. If `gasTarget == 0`, Go's `math/big.Int.Div` panics with "division by zero", and this path is taken whenever `parentGasUsed != gasTarget` (i.e., whenever `parentGasUsed != 0`, since `gasTarget == 0`), which is essentially every real block.

The root cause is that the `Kip71GasTarget` governance parameter's `FormatChecker` is a no-op, unlike `Kip71BaseFeeDenominator`, which explicitly rejects `0`: [4](#0-3) 

The header-governance vote-verification logic (`checkConsistency`) also does not add any extra semantic check for `Kip71GasTarget`; it is grouped with parameters that are "valid as long as it passes the format checks in `NewVoteData()`" — and since the format checker is a no-op, `0` passes: [5](#0-4) 

Once a `kip71.gastarget = 0` vote is ratified at an epoch boundary, `NextMagmaBlockBaseFee` is called by every node during header preparation/validation and mining: [6](#0-5) [7](#0-6) [8](#0-7) 
This means the panic is triggered network-wide on block-proposal and block-validation code paths of every full node/validator, not just an isolated process.

### Impact Explanation
This causes a total denial of service of the chain: after the malicious/faulty `GasTarget=0` value is ratified, every node attempting to build or validate the next block (as soon as gas is used) panics inside `NextMagmaBlockBaseFee`. This affects block proposers computing `header.BaseFee`, and validators verifying it via `VerifyMagmaHeader`, meaning the network halts (no valid blocks can be produced) — a severe availability/consensus-halting impact, consistent with a "High" denial-of-service class bug, matching the reachable-path categories "governance parameters" and "state transition/gas accounting" explicitly listed as in-scope.

### Likelihood Explanation
Reaching this requires a `kip71.gastarget` vote of `0` to be cast by an eligible voter (a council member / proposer, or the governing node in "single" mode) and ratified at an epoch boundary. This is a normal, sanctioned governance action (not a "malicious validator"/consensus-message exploit) that passes all existing validation because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, in stark contrast to the analogous `Kip71BaseFeeDenominator`, which explicitly disallows `0`. The vote itself requires no exploit of consensus/networking internals — it is submitted through the standard `governance_vote` API and RLP-encoded header vote mechanism, and is accepted by `VerifyVote`/`checkConsistency` without complaint.

### Recommendation
Add a zero-value rejection to `Kip71GasTarget`'s `FormatChecker` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and/or add a defensive zero-check/fallback for `GasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, consistent with the existing `BaseFeeDenominator == 0` fallback, so that a zero `GasTarget` can never reach the division.

### Proof of Concept
1. As a council member/proposer (or the governing node in single mode), submit a governance vote `kip71.gastarget = 0` via the `governance_vote` API; `NewVoteData`/`VerifyVote`/`checkConsistency` all accept it because `Kip71GasTarget`'s format checker is a no-op [9](#0-8) .
2. At the next epoch boundary, the vote is ratified into `header.Governance`, updating the effective `GasTarget` to `0`.
3. On the next block where `parentGasUsed != 0`, any node (proposer building the header, or validator verifying `header.BaseFee`) calls `NextMagmaBlockBaseFee`, which executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` [10](#0-9) , causing a division-by-zero panic and crashing/halting the node's block processing.
