Based on my research, the strongest verified local analog to the Kerosene spot-price manipulation bug is in the **Simplex FX filler strategy** (`sdk/packages/simplex/src/strategies/fx.ts`), where a safety clamp against manipulated venue (AMM) prices has been explicitly disabled, removing the only bound on payout size when the price source is manipulated within a single block — structurally identical to the DYAD report's core invariant break: *a manipulable spot value feeds directly, unbounded, into a critical fund-movement decision*.

I was unable to fully verify (given tool-call limits) whether the confirmation-depth sizing path (`getOrderUsdValue` → `usdFactors`) shares the same price-guard as the fill-pricing path (`resolveLegRates`/`checkPriceGuard`) — the test file `fx.price-guard.test.ts` suggests the authors were aware of this exact risk and built a guard for it, so I could not confirm a live gap there and have excluded it from the finding to avoid speculation.

### Title
Disabled overfill clamp lets a manipulated Uniswap V4 venue price force unbounded solver payout in intent settlement - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
The `FXFiller` strategy that fills cross-chain/same-chain Intent Gateway orders used to cap output amounts at `(1 + maxOverfillBps) × user-requested amount` specifically to bound loss from "a bug / stale cache / manipulated venue price." That clamp has been disabled: the code now only logs a warning and pays out the full unclamped, venue-priced amount.

### Finding Description
In `calculateProfitability`, for venue-priced (Uniswap V4 pool) legs, the filler computes `policyMaxOutput` from the live pool price and then explicitly does **not** cap it: [1](#0-0) 

```
// Overfill detection is warn-only: the clamp is DISABLED, so the filler
// fills the full computed amount even when it exceeds
// (1 + maxOverfillBps) × user-requested — including venue-priced legs
// (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that
// previously protected against a bug / stale cache / manipulated venue
// price. Output is no longer capped; we only emit a warning.
const overfillCeiling = (output.amount * (10000n + this.maxOverfillBps)) / 10000n
const policyMaxOutput = rawPolicyMaxOutput
```

The halt-on-repeated-clamp circuit breaker is also permanently dormant because it is always fed `clamped = false`: [2](#0-1) 

The venue price itself comes straight from the pool's current tick/`sqrt PriceX96` via `UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd`, i.e. an instantaneous, single-block spot price of a concentrated-liquidity pool: [3](#0-2) 

An optional `referencePrice`/`maxDeviationBps` guard exists (`checkPriceGuard`), but it is opt-in, per-position config — omitting it (or the pool moving only just inside the band) still leaves the actual output size uncapped by anything other than the filler's wallet/vault balance: [4](#0-3) 

This mirrors the DYAD/Kerosene invariant break exactly: a shared, permissionlessly-movable spot value (there: TVL/kerosene supply; here: a Uniswap V4 pool's instantaneous price) is consumed directly by a critical fund-disbursement calculation, and the safety margin that would have bounded the blast radius of that manipulation has been intentionally removed, leaving only a log line.

### Impact Explanation
An attacker who moves a Uniswap V4 pool's price in the same block (flash swap / large directional swap immediately before or atomically with placing an intent order) can inflate `rawPolicyMaxOutput` for a venue-priced leg far beyond what the order economically justifies. Because `policyMaxOutput` is used unclamped as `finalOutputAmount` (bounded only by wallet/vault balance, not by price sanity), the filler pays out an inflated amount of the exotic token to the order's beneficiary while only receiving the user's (unmanipulated, real) input — a direct, unbounded loss of the solver's escrowed/vault capital that backs Intent Gateway settlement. This is fund loss inside the intent-settlement path described in scope ("intent settlement, reward claims... bandwidth accounting, paymaster logic"), not a front-run-only or generic DoS issue — it is a wrong-amount fund transfer triggered by an unprivileged actor's own transaction.

### Likelihood Explanation
Likelihood is bounded by which pools/positions an operator lists under `[vault.uniswapV4]` and whether a `referencePrice` guard is configured for that chain — thin or low-liquidity concentrated positions (explicitly the scenario the removed clamp was designed for) are the most exposed, and the code's own comments acknowledge this as a known, previously-mitigated risk that was deliberately relaxed for competitiveness ("Note: we may intentionally overfill relative to the user's requested outputs ... This is how we stay competitive").

### Recommendation
Re-enable the overfill ceiling for venue-priced legs (`policyMaxOutput = min(rawPolicyMaxOutput, overfillCeiling)`), restore `recordOrderOutcome` to feed real clamp events, and require an operator-configured `referencePrice`/`maxDeviationBps` band whenever a pair sources pricing from `[vault.uniswapV4]` with no static curve, rather than leaving it optional.

### Proof of Concept
1. Operator configures a `[vault.uniswapV4]` position for pair `USDC/CNGN` with no `referencePrice` guard (an explicitly supported, documented configuration).
2. Attacker places a normal Intent Gateway order requesting a modest amount of CNGN for USDC.
3. In the same block (or immediately prior, if the destination chain's block time allows), the attacker executes a large swap against the same V4 pool to move `sqrtPriceX96` so that CNGN appears far cheaper in USD terms than its real market price.
4. `getExoticTokenPrice` / `computeDirectPoolPriceUsd` returns the manipulated price; `calculateProfitability` computes an inflated `rawPolicyMaxOutput` for the CNGN leg.
5. Because the clamp is disabled (`policyMaxOutput = rawPolicyMaxOutput`, no ceiling check reverts or caps), the filler executes `fillOrder` and transfers the inflated CNGN amount to the beneficiary while only ever having received the user's real (unmanipulated) USDC input — realizing a loss equal to the manipulated price delta, times order size, capped only by the filler's on-chain balance/vault liquidity at fill time.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

#### Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the filler exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the filler refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
positions = [
    # referencePrice is the expected cNGN per USD; reject if the quote is more than 2% off
    { chain = "EVM-8453", tokenId = "2087350", referencePrice = "1575", maxDeviationBps = 200 },
]
