### Title
Empty `conditions: []` in a hookify rule file silently neutralizes an apparently active block/warn rule - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
`RuleEngine._rule_matches` unconditionally returns `False` whenever `rule.conditions` is empty: [1](#0-0) . `Rule.from_dict` only populates `conditions` from the frontmatter's `conditions` list, and if that list is present but empty (`conditions: []`), no fallback to the legacy `pattern` field occurs because the fallback is gated on `not conditions` — an empty list is falsy so it *would* actually fall through to the legacy path only if `pattern` is also set: [2](#0-1) . If a rule author supplies `conditions: []` and omits `pattern`, the resulting `Rule` has `enabled=True` and `conditions=[]`, so `_rule_matches` always returns `False` for any input, and `evaluate_rules` never adds it to `blocking_rules` or `warning_rules`, producing `{}` (no block, no warning) for every call: [3](#0-2) .

Critically, nothing in the loading or listing tooling flags this as invalid. `load_rules` only checks `rule.enabled` before including the rule: [4](#0-3) , and the `/hookify:list` command instructs displaying rules as `✅ Active`/`✅ Yes` based solely on the `enabled` field, not on whether `conditions` (or `pattern`) is non-empty: [5](#0-4) . So a rule file with a convincing name (`block-dangerous-rm`), `enabled: true`, `conditions: []`, and an alarming message body will appear fully active in `/hookify:list` while never actually blocking or warning about anything.

These rule files live at `.claude/hookify.*.local.md` in the project's working directory and are loaded purely by filesystem glob with no ownership, signature, or git-tracking check: [6](#0-5) . Nothing in the repository enforces that these `.local.md` files be excluded from version control (no `.gitignore` entry was found), so if such a file is committed to a shared repository, any collaborator who clones it and uses hookify will silently inherit the neutered rule and believe a security guard (e.g., against `rm -rf`) is protecting them when it is not.

### Impact Explanation
This is a false-sense-of-security / silent guard-disablement bug rather than a code-execution or data-exfiltration primitive. The scoped impact is: a user relying on hookify's PreToolUse blocking to prevent destructive Bash commands, sensitive-file edits, or other project-defined guardrails will have that protection silently bypassed, because the "advertised" rule (with a name and message implying active enforcement) never fires. Because `_rule_matches` is a pure logic function with no external side effects and the file must be present in `.claude/` to have any effect, this does not constitute an actual `Claude Code` process compromise, arbitrary command execution, or sandbox/workspace escape by itself — it is a logic/trust flaw in the plugin's own advisory mechanism, contingent on the victim actually trusting and relying on a committed rule file they didn't author or fully audit.

### Likelihood Explanation
Requires: (1) an unprivileged contributor able to add/merge a `.claude/hookify.*.local.md` file into a shared repository (e.g., via PR), and (2) a victim who runs Claude Code with hookify installed in that repository and trusts the rule's presence/name/message as an active safeguard without inspecting the `conditions` field or without noticing `/hookify:list` doesn't actually validate the semantic activeness of a rule. This is plausible in open-source or team repos where `.claude/` config files are reviewed less carefully than application code, but it depends on social trust in a config file's authenticity, and it is inert by design ("Rules must have at least one condition to be valid") rather than a parsing exploit.

### Recommendation
Treat a `Rule` with `enabled: true` but empty `conditions` and no legacy `pattern` as invalid at load time (reject or warn loudly, similar to the missing-frontmatter case), and have `/hookify:list` explicitly surface rules that are `enabled` but structurally inert (no conditions/pattern) as `⚠️ Enabled but non-functional` instead of `✅ Active`, so users cannot be misled by convincing names/messages alone.

### Proof of Concept
Integration test:
1. Write `.claude/hookify.dangerous-rm.local.md` with frontmatter `name: block-dangerous-rm`, `enabled: true`, `event: bash`, `action: block`, `conditions: []`, and message `"Dangerous rm command blocked!"`.
2. Call `load_rules('bash')` and assert the returned `Rule` has `conditions == []` and `enabled == True`.
3. Call `RuleEngine().evaluate_rules([rule], {"hook_event_name": "PreToolUse", "tool_name": "Bash", "tool_input": {"command": "rm -rf /"}})`.
4. Assert the result is `{}` (no `hookSpecificOutput`/`permissionDecision: deny`, no `systemMessage`), proving the rule never blocks or warns despite `enabled: true` and a "block-dangerous-rm" name/message, confirming the guard is silently neutralized.
