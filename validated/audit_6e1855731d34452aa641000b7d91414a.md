### Title
Tokenfactory denom admin can instantly weaponize `allow_list` via `MsgUpdateDenom` to permanently freeze existing holders' funds - (File: `x/tokenfactory/keeper/msg_server.go`, `x/tokenfactory/keeper/createdenom.go`, `sei-cosmos/x/bank/keeper/send.go`)

### Summary
The tokenfactory module lets any account permissionlessly create a denom and become its "admin." `x/tokenfactory/keeper/msg_server.go`'s `UpdateDenom` handler, guarded only by an admin check, lets that admin call `MsgUpdateDenom` to set/replace the denom's `AllowList` in bank state via `SetDenomAllowList` at any time and with no timelock, cooldown, or opt-out window for existing holders [5](#0-4) . The new list is enforced immediately by `IsInDenomAllowList`, which is checked on every `Send`/`MultiSend` for both sender and receiver [3](#0-2) [6](#0-5) .

### Finding Description
This mirrors the reported bug class exactly: a privileged creator/admin can unilaterally and instantly change a parameter that governs existing users' ability to move their already-held funds, with no grace period for affected holders to exit first. Here, instead of a fee percentage, the parameter is the token's `allow_list`.

Validation of the update is limited to bech32-address well-formedness and a size cap; there is no check that current, already-funded holders remain included in the new list: [7](#0-6) .

Because any account can call `MsgCreateDenom` to become admin of `factory/{creator}/{subdenom}`, mint/distribute/sell that token to others (e.g., via a DEX, airdrop, or vesting scheme), and only afterward call `MsgUpdateDenom` with an `allow_list` that excludes those recipients, holders who legitimately acquired the token become permanently unable to send it (`"is not allowed to send funds"`) and, if the admin also excludes them as a receiver, unable to ever receive it back either — with no mechanism in the module to remove or dispute the list.

### Impact Explanation
This is a direct, permanent freezing-of-funds vector reachable by a single `MsgUpdateDenom` transaction from an unprivileged (self-appointed) tokenfactory admin. Once the allow list flips, held balances of that denom become non-transferable for excluded addresses — the CosmWasm/Solidity analog to the reported "cred" issue, except there is no fee escape hatch at all (100% freeze) rather than a partial 50% haircut, making the worst case strictly worse than the original finding.

### Likelihood Explanation
High. `MsgCreateDenom` is fully permissionless, and `MsgUpdateDenom`'s allow-list mutation is a one-line admin-gated call with no timelock, no minimum notice period, and no on-chain warning mechanism. Any denom admin can trivially bait users into acquiring the token (e.g., promoted as freely tradeable) then rug them by excluding them from the allow list in a later block/transaction.

### Recommendation
Add a timelock (e.g., enforce that a new, more restrictive `allow_list` only takes effect after N blocks/hours), or require that addresses holding a nonzero balance of the denom at the time of the update remain in the allow list (or be given a withdrawal/exit window before restriction is enforced), consistent with the judge's recommendation in the original report to place such admin-controlled fund-affecting parameters behind a timelock.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` with subdenom `x`, becoming admin of `factory/attacker/x`.
2. Attacker mints tokens and distributes/sells them to victims (e.g., via bank `Send` while no allow list is set, which is permitted by default per `IsInDenomAllowList`'s pass-through path [8](#0-7) ).
3. Attacker calls `MsgUpdateDenom` on `factory/attacker/x` with an `allow_list` containing only the attacker's address; `UpdateDenom` accepts it since the sender is admin and the list passes `validateAllowList` [9](#0-8) .
4. Any victim holding `factory/attacker/x` who now tries `MsgSend` gets rejected with `"... is not allowed to send funds"` [10](#0-9) , and their balance is permanently stuck with no on-chain remedy.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (k Keeper) validateUpdateDenom(ctx sdk.Context, msg *types.MsgUpdateDenom) (tokenDenom string, err error) {
	_, _, err = types.DeconstructDenom(msg.GetDenom())
	if err != nil {
		return "", err
	}
	_, found := k.bankKeeper.GetDenomMetaData(ctx, msg.GetDenom())
	if !found {
		return "", types.ErrDenomDoesNotExist.Wrapf("denom: %s", msg.GetDenom())
	}

	err = k.validateAllowList(ctx, msg.AllowList)
	if err != nil {
		return "", err
	}

	return msg.GetDenom(), nil
}

func (k Keeper) validateAllowListSize(ctx sdk.Context, allowList *banktypes.AllowList) error {
	if allowList == nil {
		return types.ErrAllowListUndefined
	}

	if len(allowList.Addresses) > int(k.GetDenomAllowListMaxSize(ctx)) {
		return types.ErrAllowListTooLarge
	}
	return nil
}

func (k Keeper) validateAllowList(ctx sdk.Context, allowList *banktypes.AllowList) error {
	err := k.validateAllowListSize(ctx, allowList)
	if err != nil {
		return err
	}

	// validate all addresses in the allow list are bech32
	for _, addr := range allowList.Addresses {
		if _, err = sdk.AccAddressFromBech32(addr); err != nil {
			return fmt.Errorf("invalid address %s: %w", addr, err)
		}
	}
	return nil
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
