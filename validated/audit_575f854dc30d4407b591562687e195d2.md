### Title
Division by zero in `_updateVote` permanently DoSes staking/withdrawal in `DelegateVoteRewardPool` - (File: `rewards/DelegateVoteRewardPool.sol`)

### Summary
`DelegateVoteRewardPool._updateVote()` divides by the state variable `totalWeight` without checking whether it is zero, mirroring the reported `sharesToTokenAmount` division-by-zero bug class. Because `_updateVote()` is invoked from `stakeFor` and `withdrawFor` — the core entry points reachable from any ordinary vlMGP holder's staking/withdrawal transaction — a zero `totalWeight` while `votePools` is non-empty permanently reverts all deposits and withdrawals for every user of this pool.

### Finding Description
`_updateVote()` computes, for every registered vote pool, the user's target vote share: [1](#0-0) 

```
uint256 targetVote = (votingWeights[pool] * totalSupply) / totalWeight;
```

`totalWeight` is only updated in the admin function `updateWeight`, which both registers new pools into `votePools` and adjusts `totalWeight`: [2](#0-1) 

Critically, a pool is pushed into `votePools` (making `votePools.length > 0`) regardless of the `weight` value passed in. Setting the first pool's weight to `0` (or reducing the only pool's weight to `0`, which is a legitimate, non-malicious admin action — e.g. temporarily deactivating a pool's vote allocation) results in `totalWeight == 0` while `votePools.length >= 1`.

Once in this state, every call to `_updateVote()` performs `.../ totalWeight` with `totalWeight == 0`, which reverts. `_updateVote()` is unconditionally called inside both: [3](#0-2) [4](#0-3) 

These are the functions ordinary users' staking/withdrawal flows route through (via the operator, e.g. `WombatBribeManager`), so this is reachable through unprivileged wallet transactions, not just admin calls — the admin only sets up the zero-weight condition, after which any user's stake or withdraw call triggers the revert.

### Impact Explanation
Once `totalWeight` becomes `0` with at least one entry in `votePools`, `stakeFor` and `withdrawFor` become permanently unusable for all users of this reward pool — no user can stake, and critically, no user can withdraw their already-staked balance, since `withdrawFor` also calls `_updateVote()` before executing the withdrawal logic. This constitutes a permanent freeze of user funds, satisfying the "permanent freezing of funds" impact bar. Unlike the original report (a pure view function reverting), here the affected functions are state-changing entry points that gate withdrawal of user principal.

### Likelihood Explanation
The precondition (an active vote pool with `weight == 0`, driving `totalWeight` to `0`) can arise from a single, unremarkable `updateWeight` call — e.g., registering a new pool before assigning it a nonzero weight, or reducing the only pool's weight to zero to temporarily pause voting for it. No malicious intent or governance compromise is required, only an ordinary configuration operation, after which the bug is deterministically triggered by the very next user stake/withdraw.

### Recommendation
Guard the division in `_updateVote()`:
```solidity
uint256 targetVote = totalWeight == 0 ? 0 : (votingWeights[pool] * totalSupply) / totalWeight;
```
Alternatively, disallow `totalWeight` from reaching `0` while `votePools` is non-empty, or skip pools whose weight is `0` in the loop.

### Proof of Concept
1. Owner calls `updateWeight(lp1, 0)` for a new pool `lp1`. This pushes `lp1` into `votePools` and leaves `totalWeight == 0` (`totalWeight = totalWeight - votingWeights[lp1] + weight` with `votingWeights[lp1]` initially `0` and `weight = 0`). [2](#0-1) 
2. Any user attempts to stake via the operator (`stakeFor`) or withdraw (`withdrawFor`).
3. `_updateVote()` executes the loop over `votePools` (length 1), computing `(votingWeights[lp1] * totalSupply) / totalWeight` = `.../0`, reverting the entire transaction. [1](#0-0) 
4. All subsequent `stakeFor`/`withdrawFor` calls revert identically — user funds already staked in this pool cannot be withdrawn until an admin corrects `totalWeight` (and even then, prior depositors already may be stuck if no such correction is intentionally made), constituting a permanent freeze.

    function _updateVote() internal {
        uint256 length = votePools.length;
        int256[] memory deltas = new int256[](length);
        for (uint256 index = 0; index < length; ++index) {
            address pool = votePools[index];
            uint256 targetVote = (votingWeights[pool] * totalSupply) /

        IWombatBribeManager(operator).vote(votePools, deltas);
    }
