### Title
Malformed Schnorrkel message causes out-of-bounds panic during signing - (File: crypto/schnorrkel/src/lib.rs)

### Summary
`SchnorrkelHram::hram` treats the caller-controlled `msg` as a serialized context-prefixed message without validating its length before indexing it. A message shorter than four bytes, or one whose encoded context length exceeds the remaining input, causes an out-of-bounds slice panic while FROST is producing the signature share. [1](#0-0) [2](#0-1) 

### Finding Description
`AlgorithmSignMachine::sign` accepts `msg: &[u8]` and ultimately invokes the algorithm's `sign_share` implementation. [2](#0-1)  The generic Schnorr implementation passes that byte slice directly to `H::hram` as `m`. [3](#0-2) 

Inside `SchnorrkelHram::hram`, `m[0 .. 4]` is interpreted as a little-endian context length without first checking `m.len() >= 4`. [4](#0-3)  It then uses that untrusted length as `ctx_len` in `m[4 .. (4 + ctx_len)]` and `m[(4 + ctx_len) ..]`, also without checking that `4 + ctx_len <= m.len()`. [5](#0-4) 

There is no validation layer in the shown FROST path that rejects malformed messages before this HRAm callback. [6](#0-5) 

### Impact Explanation
An unprivileged party who can cause a participant to sign an attacker-selected message can crash that participant's signing process by supplying malformed Schnorrkel message bytes. [2](#0-1)  If the malformed message is broadcast to the signing set, every participant using this algorithm can panic while calculating the challenge, preventing completion of the signing session. [3](#0-2) 

This is an availability impact rather than key disclosure: the panic occurs during challenge construction before a signature share is returned. [7](#0-6) 

### Likelihood Explanation
The trigger requires only control over the public message input to `sign`; it does not require access to private nonce material, a threshold key share, invalid curve encodings, or malformed preprocess data. [2](#0-1)  Inputs such as a three-byte message or a four-byte message declaring a nonzero context length deterministically violate the unchecked slice bounds. [1](#0-0) 

The likelihood therefore depends on whether integrators allow externally supplied messages to reach the Schnorrkel signing machine without independently enforcing Schnorrkel's expected message encoding. [8](#0-7) 

### Recommendation
Validate `msg` before indexing it: require at least four bytes, decode `ctx_len`, and reject values where `ctx_len > msg.len() - 4` or where checked addition of `4 + ctx_len` overflows. [1](#0-0)  The validation should return a protocol error rather than panic; because `Algorithm::sign_share` currently returns a scalar directly, the malformed-message check may need to occur in a caller-facing validation step or the algorithm API may need an error-returning path. [9](#0-8) 

### Proof of Concept
Given a validly initialized Schnorrkel sign machine and sufficient participant preprocesses, either malformed message triggers the panic:

```rust
// Panics at `m[0 .. 4]`.
let (_machine, _share) = machine.sign(preprocesses, &[0x01, 0x02, 0x03])?;
```

```rust
// ctx_len = 1, but no context byte follows the 4-byte length.
// Panics at `m[4 .. (4 + ctx_len)]`.
let (_machine, _share) = machine.sign(preprocesses, &[0x01, 0x00, 0x00, 0x00])?;
```

The first input reaches `m[0 .. 4]` with length three, while the second reaches `m[4 .. 5]` with length four. [1](#0-0)  Both execute through the normal `sign -> sign_share -> Hram::hram` call path before a signature share can be returned. [7](#0-6) [3](#0-2)
