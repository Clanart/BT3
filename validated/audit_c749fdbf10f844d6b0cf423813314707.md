### Title
Empty signer set produces a trivially-valid Schnorr aggregate signature - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` returns `true` when called with an empty `keys_and_challenges` slice and an aggregate signature containing zero `Rs` and `s = 0`. This is the direct analog of the Validium "empty committee" bug: the verification equation degenerates to `0 == 0` when the signer set is empty, so a forged "aggregate signature" with no signers is accepted. An attacker controlling the serialized aggregate bytes (via `SchnorrAggregate::read`) and able to influence/empty the signer list handed to `verify` can produce a valid-looking attestation that no key ever signed.

### Finding Description
`SchnorrAggregate::read` parses a `u32` count, then that many `R` points and a scalar `s`, with no minimum-count check (`crypto/schnorr/src/aggregate.rs:77-88`). `verify` only checks `self.Rs.len() == keys_and_challenges.len()`, builds a multiexp of `(z, R_i)`, `(z*c_i, key_i)` pairs plus `(-s, G)`, and returns whether the result is identity (`crypto/schnorr/src/aggregate.rs:127-146`).

With `keys_and_challenges = []` and a crafted aggregate `{ Rs: [], s: 0 }`, the pairs vector reduces to `[(-0, generator)]` — a single identity term — so `multiexp_vartime(&pairs).is_identity()` evaluates to `true`. The loop `for _ in 0 .. u32::from_le_bytes(len)` in `read` happily accepts `len = 0`, and `C::read_F` accepts the zero scalar. No code path rejects the empty case.

The same degenerate-acceptance pattern exists in `BatchVerifier` (`crypto/multiexp`): `BatchVerifier::new(0)` / an empty queue verifies trivially, and in `dkg` the structures guard against it only because `ThresholdParams::new` rejects `t == 0 || n == 0` (`crypto/dkg/src/lib.rs:166-173`). `SchnorrAggregate` has no equivalent non-emptiness invariant.

### Impact Explanation
Any protocol that calls `SchnorrAggregate::verify` with a signer/key set derived from untrusted or separately-supplied input is vulnerable: if the effective signer list can be empty (e.g., all candidates filtered out, an empty committee, a zero-weight validator set, or a caller-side mapping that yields no keys), the attacker supplies 4 bytes of `0x00000000` plus a zero-scalar encoding and `verify` returns `true`. This is a signature forgery for the empty set — exactly the reported bug class where `requiredAmountOfSignatures = 0` lets empty input pass verification. It converts a "no one signed" state into "validly signed," which for attestation/commit-style usage means accepting messages with zero backing.

### Likelihood Explanation
Exploitation requires the caller to reach `verify` with an empty `keys_and_challenges` while still treating the result as meaningful authorization. This is plausible wherever the key set is computed dynamically (filtered, weighted, or committee-derived) rather than hard-coded; it is not exploitable where the caller independently enforces a quorum over the signers before/after verification. The primitive itself provides no defense — the check must exist at every call site, and `verify`'s doc comment warns about challenge construction but never mentions the empty-set case. Rated Medium: a real forgery primitive, but gated on an integrator reaching it with an empty set.

### Recommendation
In `SchnorrAggregate::verify`, return `false` early when `keys_and_challenges.is_empty()` (equivalently, when `self.Rs.is_empty()`). Optionally also reject `s == 0` during `read`/`verify` and reject empty `Rs` in `SchnorrAggregate::read`. Apply the same non-empty guard to `BatchVerifier::verify`/`verify_vartime_with_vartime_blame` in `crypto/multiexp` so a zero-statement batch cannot silently pass.

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
