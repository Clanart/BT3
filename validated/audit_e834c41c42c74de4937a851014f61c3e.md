### Title
`calculate_share` leaks the ECDH blame key for unauthenticated messages before verifying the sender's proof-of-possession — ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
In `KeyMachine::calculate_share`, each incoming `EncryptedMessage` is decrypted and its ciphertext is canonicalized with `C::F::from_repr` **before** the batch verifier containing the sender's proof-of-possession (PoP) Schnorr signature is evaluated. If the decrypted bytes are not a canonical scalar, the function early-returns `PedPoPError::InvalidShare { blame: Some(EncryptionKeyProof) }`, which contains `key` — the ECDH shared point `enc_key * msg.key` — plus a DLEq proof. Because the early return fires before `batch.verify_with_vartime_blame()` runs, an attacker can attach a victim-observed message key without possessing its discrete log, and still receive a blame proof that reveals the ECDH output for that key. This mirrors the Bookkeeper flaw class: authentication (here, the PoP) is not enforced before the connection/message is acted upon, enabling a man-in-the-middle-style key-confusion attack.

### Finding Description
`Encryption::decrypt` queues the PoP into a `BatchVerifier` and immediately applies the ChaCha20 keystream derived from `ecdh(self.enc_key, msg.key)`, returning the plaintext together with an `EncryptionKeyProof` whose `key` field is exactly that ECDH point [1](#0-0) . The code comments themselves describe the danger: if Eve reuses Alice's message key `X` without a PoP, Bob may "reveal bX, revealing Alice's message to Bob" — the PoP exists specifically to prevent this [2](#0-1) .

However, in `calculate_share`, the ordering defeats the protection:

```rust
// crypto/dkg/pedpop/src/lib.rs:477-484
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);   // <-- early return before PoP batch verification at line 493
```

The PoP is only validated inside `batch.verify_with_vartime_blame()` [3](#0-2) , which is unreachable on this path. The returned `EncryptionKeyProof` is `Some` and wraps the raw ECDH point [4](#0-3) .

### Impact Explanation
An unprivileged party who observes any honest `EncryptedMessage` from Alice to Bob (public channel data) can send Bob a forged message `{ key: Alice_key_X, pop: <self-signed under a key they control — actually they must set key = X and cannot produce a valid PoP>, msg: <32 bytes of 0xFF> }`. Bob's `calculate_share` decrypts garbage, `from_repr` fails on the non-canonical bytes, and the function returns `InvalidShare { blame: Some(proof) }` where `proof.key = b·X` (Bob's ECDH with Alice's key) with a valid DLEq binding it to `msg.key` and Bob's encryption key. Publishing/using this blame proof — the protocol's intended action — reveals the ECDH shared key that decrypts Alice's genuine secret share to Bob, leaking a DKG secret share. The PoP, the sole defense against this documented attack, is never checked on this path.

### Likelihood Explanation
Requires: (1) observing one encrypted share message to the victim (public transcript data), and (2) the victim's caller surfacing the `blame` field of the returned error, which is its designed purpose for accusing faulty senders. No collusion or key compromise needed. Constrained by needing the blame proof to become visible to the attacker, but the error type explicitly exists to be published. Severity: Medium, matching the source advisory class.

### Recommendation
Verify the PoP synchronously (or evaluate the PoP-only batch) before attempting `from_repr` and before constructing/returning any `EncryptionKeyProof`. Concretely, in `calculate_share`, either call `batch.verify_with_vartime_blame()` partitioned so `BatchId::Decryption(l)` failures are resolved before share parsing, or return `blame: None` whenever the share fails canonicalization unless the PoP has already been confirmed valid. Alternatively, have `Encryption::decrypt` itself check the PoP inline before applying the keystream, so no code path can yield an ECDH-derived proof for an unauthenticated `msg.key`.

### Proof of Concept
1. Alice and Bob run PedPoP; observe Alice's `EncryptedMessage` to Bob, extracting `msg.key = X` (`EncryptedMessage::read` / public bytes).
2. Eve crafts `EncryptedMessage { key: X, pop: SchnorrSignature::sign(&e, nonce, pop_challenge(...)) }` — invalid under `X` — and `msg` = `SecretShare` bytes of all `0xFF` (non-canonical `C::F`).
3. Bob calls `calculate_share` with Eve's message under `l = Eve`'s participant index. `decrypt` queues the (failing) PoP and produces `EncryptionKeyProof { key: b·X, dleq }`.
4. `from_repr` fails → early `?` returns `InvalidShare { participant: Eve, blame: Some(proof) }` before `batch.verify_with_vartime_blame()` would have mapped the failure to `BatchId::Decryption` → `blame: None`.
5. Eve obtains `b·X` from the surfaced blame proof and applies `cipher(context, b·X)` keystream to Alice's original ciphertext, recovering Alice's secret share to Bob.
