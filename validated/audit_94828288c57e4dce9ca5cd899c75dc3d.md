### Title
Payout-tx OP_RETURN operator attribution is unauthenticated, allowing anyone to front-run/frame a victim operator for reimbursement of a payout it never funded - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The withdrawal "payout" transaction that determines which operator gets reimbursed on Citrea binds the payer identity via an `OP_RETURN` output containing an arbitrary `operator_xonly_pk`, but the user's authorizing signature uses `SinglePlusAnyoneCanPay`, which never covers that output. Any unprivileged party who observes the user's public withdrawal signature can therefore construct their own payout transaction naming any operator's `xonly_pk` in the `OP_RETURN`, and that operator will be recorded on-chain/off-chain as the "payer" entitled to reimbursement — exactly the "caller ≠ pubkey owner" binding break described in the report, applied to the payer-attribution mechanism instead of operator/validator registration.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user's payout output (index 0), an anchor output (index 1), and an `OP_RETURN` output carrying `operator_xonly_pk` "that fronts the peg-out" (index 2). [1](#0-0) 

The single input is spent with the user's Taproot key-spend signature, and the protocol explicitly requires (and enforces) `TapSighashType::SinglePlusAnyoneCanPay` for this signature: [2](#0-1) [3](#0-2) 

`SinglePlusAnyoneCanPay` commits only to the single signed input and to the output at the *same index* as that input (index 0 — the user payout output); it does not cover any other input or output of the transaction, matching `bitcoin`'s Taproot sighash semantics used by `calculate_script_spend_sighash`/`calculate_sighash_txin` (the `Prevouts::One` / outputs-hash-skip branches): [4](#0-3) 

Consequently, the `operator_xonly_pk` embedded in the `OP_RETURN` output (index 2) is **not authenticated by the user at all** — it can be set to any value by whoever assembles and broadcasts the final transaction, as long as output 0 exactly matches what the user signed.

This attribution is later read back verbatim from the confirmed transaction and used to determine which operator is credited as the payer: [5](#0-4)  and stored into `withdrawals.payout_payer_operator_xonly_pk`: [6](#0-5) [7](#0-6) 

The victim operator's own automation then picks this up purely by matching its own key against that unauthenticated column and proceeds toward reimbursement: [8](#0-7) [9](#0-8) 

and the kickoff/assert flow only checks that the OP_RETURN-derived pubkey matches the kickoff's operator — it never verifies that the named operator actually broadcast or funded the payout transaction: [10](#0-9) [11](#0-10) 

**The binding that should hold:** `operator credited for reimbursement == operator that actually fronted (paid) the withdrawal in BTC`. Because the `OP_RETURN` naming is unsigned by the user and the payout transaction's remaining inputs/outputs are unconstrained by `SinglePlusAnyoneCanPay`, an attacker can break this binding: `operator named in OP_RETURN of the confirmed payout tx != party who funded/broadcast the transaction`. This is the direct analog of the reported bug class — a public-key argument determining ownership/credit that isn't tied by signature to the actual actor, letting anyone "front-run" and register credit under someone else's key.

### Impact Explanation
Whoever confirms the payout transaction controls the `OP_RETURN`, so an unprivileged attacker who observes the user's `SinglePlusAnyoneCanPay` withdrawal signature (available off-chain to operators, and/or extractable from any operator's broadcast/mempool transaction, since the signature itself is public once used) can:
- Reconstruct and broadcast a competing/faster-fee version of the payout transaction that pays the exact same output-0 to the withdrawing user (satisfying the signature) but sets `OP_RETURN` to name an arbitrary or targeted operator's `xonly_pk`, funding any extra inputs/fees itself via `AnyoneCanPay`.
- This causes a targeted, uninvolved operator to be recorded in the `withdrawals` table as `payout_payer_operator_xonly_pk`, triggering that operator's own `PayoutCheckerTask`/kickoff automation to pursue reimbursement (Round → Kickoff → Reimburse flow) for a payment it never made.

This matches the Critical impact category "an operator reimbursed for a payout it never funded" (if the attacker cooperates with/controls that operator) or, in the adversarial framing, forces an honest operator into an unwanted on-chain kickoff/reimbursement claim it did not initiate, which can expose it to challenge/slashing risk if the rest of the protocol treats an unexpected kickoff as suspicious, or otherwise misattributes bridge collateral/reimbursement flow away from the true payer.

### Likelihood Explanation
Likelihood is significant but bounded by the fact that the input UTXO can only be spent once, so this is a race against the real operator's own broadcast of the payout — the attack must win that race (e.g., by fee-bumping or by acting before the intended operator broadcasts). No signing key, operator role, or verifier/watchtower privilege is required; the only prerequisite is visibility of the user's public `SinglePlusAnyoneCanPay` signature (routed to operators off-chain, but also observable once any payout attempt appears on the network) and the ability to broadcast a Bitcoin transaction — an unprivileged capability.

### Recommendation
Bind the `OP_RETURN` operator-attribution output to the user's authorization by using a sighash type that commits to all outputs (e.g., `SIGHASH_ALL` or `SIGHASH_ALL|ANYONECANPAY`) for the payout transaction, or otherwise have the user's off-chain message explicitly name the authorized operator and verify that name against the actual `OP_RETURN` content before treating a confirmed payout as attributing reimbursement rights.

### Proof of Concept
1. User submits a withdrawal with `input_signature` using `TapSighashType::SinglePlusAnyoneCanPay` as required by `parse_withdrawal_sig_params` (core/src/rpc/parser/operator.rs:170-187), authorizing spend of `input_outpoint` to `output_script_pubkey`/`output_amount` only.
2. Attacker obtains this signature (it is distributed off-chain to operators and/or becomes visible in any broadcast attempt).
3. Attacker builds a payout transaction via the same construction as `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436): input = the signed UTXO, output 0 = the exact user payout (matches the signed `SinglePlusAnyoneCanPay` commitment), output 1 = anchor, output 2 = `OP_RETURN` containing an arbitrary `operator_xonly_pk` chosen by the attacker (e.g., a real operator's key, not the attacker's own).
4. Attacker funds any extra fee inputs (allowed by `AnyoneCanPay`) and broadcasts with higher fee/priority than the legitimate operator.
5. Once confirmed, `update_finalized_payouts` (core/src/verifier.rs:2312-2342) parses the `OP_RETURN` and stores the attacker-chosen `operator_xonly_pk` as `payout_payer_operator_xonly_pk` in the `withdrawals` table, with no check that this operator actually broadcast or funded the transaction.
6. The named operator's `PayoutCheckerTask` (core/src/task/payout_checker.rs:41-79) picks up this withdrawal as its own unhandled payout and proceeds to kickoff/reimbursement, despite never having funded the payment.

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
