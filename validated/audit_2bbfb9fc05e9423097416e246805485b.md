### Title
Fee/weight estimate omits the OP_RETURN output, so transactions with data are built paying less than the requested (and possibly below-relay) fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the JOJO issue where the same logical quantity (`t0Amount`) was computed one way in `_borrow` and a different, inconsistent way in `_repay`, `SignableTransaction::new` estimates transaction weight/vbytes for fee purposes via `calculate_weight_vbytes`, but that estimate is computed from only `inputs` and `payments` — it never accounts for the OP_RETURN output created when `data` is specified. The transaction actually built and signed includes the extra output, so the "needed fee" priced into the transaction is derived from a smaller size than the transaction really has.

### Finding Description
In `SignableTransaction::new`, the data output is pushed onto `tx_outs` before the weight is estimated:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs a synthetic transaction from `inputs`, `payments`, and an optional `change` script only — there is no parameter for the data output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` undercounts by the serialized size of the OP_RETURN output (up to ~91+ vbytes for 80 bytes of data, i.e. `value` + `script_pubkey` + length prefixes).
- The minimum-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` is performed against the underestimated size, so a transaction can pass the check while its true fee rate is below the relay minimum.
- The final `weight > MAX_STANDARD_TX_WEIGHT` check uses the same underestimated `weight`, so an oversized transaction can be accepted.
- When a change output exists, the change amount is `input_sat - payment_sat - fee_with_change`, again based on the underestimated `vbytes_with_change`, so the change is slightly larger than it should be and the effective fee rate is lower than `fee_per_vbyte`.

### Impact Explanation
An unprivileged caller supplying `data` causes the signing flow to produce and sign a transaction whose real fee rate is materially below the requested `fee_per_vbyte` — and potentially below the network's minimum relay fee. The result is a signed transaction that relays poorly or not at all (stuck funds until replaced/abandoned), silently violating the caller-specified fee rate. With large `data` and low `fee_per_vbyte`, the discrepancy is amplified. Additionally, the MAX_STANDARD_TX_WEIGHT gate can be bypassed by up to the size of the omitted output.

### Likelihood Explanation
Any use of `SignableTransaction::new` with `data: Some(..)` hits this deterministically; the data output is always excluded from both `vbytes` and `vbytes_with_change`. No special timing or adversarial peer is required — only a caller specifying an OP_RETURN payload, which is an intended feature of the API (`TooMuchData` bound at 80 bytes exists precisely to support it).

### Recommendation
Include the data output in the weight estimate. The simplest fix is to perform the weight calculation over the actual `tx_outs` (payments + OP_RETURN), e.g. move the `calculate_weight_vbytes` calls after `tx_outs` is finalized and pass the real output list (with a placeholder/actual change output as appropriate), or add a `data_len`/`Option<&ScriptBuf>` parameter to `calculate_weight_vbytes` so the OP_RETURN output is included in the synthetic transaction. Both the initial `vbytes` and the `vbytes_with_change` paths must account for it.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// With inputs = [1 BTC output], payments = [(script, 10_000)], change = None,
// data = Some(vec![0; 80]), fee_per_vbyte = 10:
//
// tx_outs ends with an OP_RETURN output of ~91 bytes (8 value + ~83 script+len).
// calculate_weight_vbytes(tx_ins.len(), payments, None) builds a TX *without*
// that output, so vbytes excludes ~91 vbytes.
//
// needed_fee = 10 * vbytes  // underpriced by ~910 sats
// actual tx weight includes the OP_RETURN output, so real fee rate
//   = needed_fee / (vbytes + ~91) < 10 sat/vbyte
//
// With fee_per_vbyte chosen at the minimum boundary, the
// DEFAULT_MIN_RELAY_TX_FEE check passes against the underestimated vbytes
// while the signed TX's true rate falls below the relay minimum.
```
Concrete check: build two `SignableTransaction`s identical except `data: None` vs `Some(vec![0; 80])` and compare `tx.weight()` (the real, signed weight) against the `vbytes` used for `needed_fee`; the `Some(..)` transaction's actual size exceeds the estimate by the serialized OP_RETURN output size.
