### Title
`SignableTransaction::new` never validates payment `script_pubkey`s, allowing the threshold group to sign transactions paying to provably unspendable scripts - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the Gravity faucet accepting an unvalidated `destinationAddress`, `SignableTransaction::new` accepts a list of `(ScriptBuf, u64)` payments and builds/signs a transaction paying to them without any check that each `script_pubkey` is a well-formed, spendable script. The only validation performed on a payment is `amount >= DUST` (`send.rs:165-169`). An `OP_RETURN`-prefixed script, an empty/oversized script, or otherwise unspendable scriptPubKey passes all checks, is included in the signed transaction, and the FROST multisig will sign the spend — permanently burning/locking the funds. The spec for the consuming system explicitly documents "No validation of external addresses/data is performed on-chain" (`spec/integrations/Instructions.md:57`), so a malformed destination supplied via an Out Instruction can reach this constructor as a raw script.

### Finding Description
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` validates:
- `inputs` non-empty, `payments`/`change`/`data` non-empty (lines 157-163),
- each payment `amount >= DUST` (lines 165-169),
- `data.len() <= 80` (lines 171-173),
- fee sufficiency and `MAX_STANDARD_TX_WEIGHT` (lines 204-243).

It never validates `payment.0` (the `ScriptBuf`). Each payment is copied verbatim into a `TxOut` (lines 188-191). `multisig` only verifies that each *input's* prevout script matches the offset key (`p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey`, lines 273-285) — the *output* scripts are never checked. `TransactionSignMachine::sign` then produces a valid BIP-341 signature committing to those outputs (lines 373-397), and `complete` finalizes the transaction (lines 413-428).

Note the code itself creates an `OP_RETURN` output with `Amount::ZERO` for `data` (lines 194-202) — the author knows OP_RETURN is unspendable — yet a payment script beginning with `OP_RETURN` carrying a nonzero value sails through the dust check and gets signed.

### Impact Explanation
Any output whose `script_pubkey` is unspendable (e.g., starts with `OP_RETURN`, or is a malformed/invalid script) results in the paid satoshis being permanently unspendable — the exact "tokens locked, users lose funds without warning" impact of the reference bug. Because the transaction is produced by the threshold signing machine and committed via `Prevouts::All` sighash, the burn is fully signed and valid on-chain. Funds are debited from Serai's multisig-controlled inputs and can never be recovered.

### Likelihood Explanation
Per `spec/integrations/Instructions.md`, "Addresses have no validation performed unless otherwise noted" and "No validation of external addresses/data is performed on-chain." An unprivileged user supplying a malformed or wrong-network address in an Out Instruction (or an In Instruction paying out to a destination) can cause a payment `ScriptBuf` that is unspendable to reach `SignableTransaction::new`. Bitcoin consensus accepts arbitrary scriptPubKeys on outputs; standardness checks in `MAX_STANDARD_TX_WEIGHT` only bound weight, not script validity. Likelihood is moderate — it requires an integrator/scheduler to pass through an unchecked address — which is precisely the documented behavior.

### Recommendation
Validate every payment `script_pubkey` in `SignableTransaction::new` before constructing the transaction. At minimum:
- Reject scripts whose first opcode is `OP_RETURN` (`script.is_op_return()` from rust-bitcoin).
- Restrict payments to known standard spendable forms (P2PKH/P2SH/P2WPKH/P2WSH/P2TR) or use `Address::from_script`/`script.is_*` checks, mirroring the decoding in `substrate/client/src/networks/bitcoin.rs:85-114` (`try_to_vec`), so only scripts that decode to a valid address type are payable.
- Return a new `TransactionError::InvalidPaymentScript` variant rather than signing the burn.

### Proof of Concept
```rust
// networks/bitcoin context; shows a payment to an unspendable script is accepted and signed
use bitcoin::script::ScriptBuf;
use bitcoin::opcodes::all::OP_RETURN;

let mut payments: Vec<(ScriptBuf, u64)> = vec![];
// An OP_RETURN output carrying value is provably unspendable, yet passes the dust check
let burn_script = ScriptBuf::new_op_return(&[]); // first opcode = OP_RETURN
assert!(burn_script.is_op_return());
payments.push((burn_script, DUST)); // DUST = 546 sats, passes `amount < DUST` check

let tx = SignableTransaction::new(
    inputs,          // valid ReceivedOutputs owned by the multisig
    &payments,
    None,            // no change
    None,
    fee_per_vbyte,
).unwrap(); // succeeds: no script validation anywhere in `new`

// The multisig will then sign this burn:
let machine = tx.multisig(&keys).unwrap();
// ... preprocess/sign/complete yields a valid on-chain transaction whose only
// payment output is unspendable. Funds are permanently destroyed.
```
`SignableTransaction::new` returns `Ok` for the `OP_RETURN`-valued payment because the only per-payment check is the dust bound at `send.rs:165-169`; no `is_op_return`, standardness, or spendability check exists anywhere in `new` or downstream in `multisig`/`sign`.
