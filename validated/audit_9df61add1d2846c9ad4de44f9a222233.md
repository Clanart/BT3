### Title
Path-containment check in `resolveWithin` uses unanchored `startsWith`, allowing sibling-directory escape from attacker-controlled deep-link `filepath` - ([File: app/src/lib/path.ts])

### Summary
The external report's broken invariant is: a value that is supposed to be bounded/contained (`fee_to_encrypt ≤ transfer_amount`) is instead validated with an incomplete comparison (`fee_to_encrypt == maximum_fee`), letting an attacker-influenced value escape its intended bound. The Desktop analog is the containment check in `_resolveWithin` in `app/src/lib/path.ts`, which is supposed to guarantee a resolved path stays *underneath* a root directory, but the check used is a bare string `startsWith`, which does not enforce a path-separator boundary.

### Finding Description
`_resolveWithin` computes a candidate path and validates it against a root directory like this: [1](#0-0) 

The final containment test is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a purely lexical string comparison. If `realRoot` is `/Users/alice/repo`, a resolved path of `/Users/alice/repo-secrets/passwords.txt` also satisfies `startsWith('/Users/alice/repo')`, even though `repo-secrets` is a **sibling** directory, not a subdirectory of `repo`. The intended invariant ("resolved path is at or underneath rootPath") is silently violated, exactly analogous to the original report's "no inherent verification that `maximum_fee` is less than or equal to `transfer_amount`" — the check exists, but it doesn't actually enforce the stated bound.

This function is consumed with attacker-influenced input in the deep-link handler. `parseAppURL` extracts a `filepath` query parameter from an `x-github-client://openrepo/...` URL that is entirely attacker-controlled (arrives via a link the user clicks): [2](#0-1) 

`openRepositoryFromUrl` in the dispatcher only rejects absolute paths, then relies on `resolveWithin` as the sole containment guard before acting on the resolved path: [3](#0-2) 

Because `resolveWithin`'s guard is bypassable via the sibling-prefix trick (e.g. `filepath=../repo-evil/secret.txt` when the repo directory is named `repo`), the "Prevented attempt to open path outside of the repository root" log branch never triggers for such inputs, and the escaped path is passed to `shell.showItemInFolder`.

### Impact Explanation
This breaks the guarantee that GitHub Desktop only ever touches paths inside the opened repository when handling an externally supplied deep link. `resolveWithin` (and its `posix`/`win32` variants) is a shared primitive; grep shows it is also used in `app/src/lib/copilot-conflict-context.ts` and `app/src/lib/stores/app-store.ts`, meaning any consumer that trusts its boundary guarantee inherits the same escape when the untrusted segment (e.g., filenames from a fetched/cloned repository, or from a crafted deep link) happens to produce a sibling directory whose name has the root directory's name as a prefix. The most directly reachable path is the deep-link `filepath` flow, which allows an attacker (via a link the user clicks) to make Desktop resolve and act on a path outside the intended repository — a file read/access outside the repo root, satisfying the report's core impact class even though the specific downstream action (`shell.showItemInFolder`) is comparatively low severity on its own; other/future consumers of `resolveWithin` that use it to gate writes would be more severely impacted.

### Likelihood Explanation
Exploitation only requires the victim to click a link (e.g. `x-github-client://openrepo/<url>?filepath=../<reponame-suffix>/secret`), and for the local clone directory name to be a prefix of a sibling directory name — a condition attackers can also engineer by controlling the repository name that gets cloned (`sanitizeCloneName` in `app/src/lib/remote-parsing.ts`) before sending the victim a link referencing it. This requires no local access, no admin rights, and no prior compromise — it fits squarely in the "link the user clicks" / "GitHub API object" attacker model.

### Recommendation
Change the containment check in `_resolveWithin` to enforce a path-separator boundary rather than a raw prefix match, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the appropriate `sep` for the `join/normalize/resolve` variant in use), and add a regression test asserting that a sibling directory sharing the root's name as a prefix (e.g. root `/x/repo`, candidate `/x/repo-evil/file`) is rejected.

### Proof of Concept
1. Victim has a repository cloned at `/Users/alice/Documents/repo` and, in a sibling directory `/Users/alice/Documents/repo-secrets/`, has an unrelated sensitive file `passwords.txt` (e.g., created by another tool, or itself a `repo-secrets` clone made after receiving a crafted repo name).
2. Attacker sends the victim a link:
   `x-github-client://openrepo/https://github.com/owner/repo?filepath=..%2Frepo-secrets%2Fpasswords.txt`
3. `parseAppURL` accepts this because `filepath` only fails on `testForInvalidChars` for the `branch` field, not `filepath`, and passes it through to `open-repository-from-url` action [2](#0-1) .
4. `openRepositoryFromUrl` checks `isAbsolute(filepath)` (false, since it's relative), then calls `resolveWithin(repository.path, filepath)` [4](#0-3) .
5. Inside `_resolveWithin`, `resolved` normalizes to `/Users/alice/Documents/repo-secrets/passwords.txt`, and `realResolved.startsWith(realRoot)` evaluates true because `realRoot = "/Users/alice/Documents/repo"` is a literal prefix of `realResolved`, despite `repo-secrets` not being a subdirectory of `repo`.
6. The guard passes and `shell.showItemInFolder(resolved)` is invoked on a path outside the intended repository, confirming the escape. [5](#0-4)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
```
