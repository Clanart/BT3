### Title
Missing upper bound on `fee_per_vbyte` / total fee enables burning of all input funds as miner fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates the fee only from below (`TooLowFee`) but never from above. `needed_fee = fee_per_vbyte * vbytes` is accepted for any caller-supplied `fee_per_vbyte`, and whenever no usable change output is produced, the entire `input_sat - payment_sat` remainder is silently paid as fee. This is the direct analog of the Vaultka report: an execution path applies only a one-sided bound (slippage checked at execution, unbounded at the parameter level), so an outdated or manipulated fee input produces a transaction whose real cost is far from the expected `needed_fee`.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
``` [1](#0-0) 

- `fee_per_vbyte` is an unconstrained `u64` parameter; there is no maximum-fee-rate check and no cap relating `needed_fee` to `input_sat` or `payment_sat` (only `NotEnoughFunds` at equality).
- Change is only created when `input_sat - payment_sat - fee_with_change >= DUST`; otherwise the whole remainder goes to miners. With `change: None`, *all* leftover funds become fee by construction (documented at lines 145–147), so any overestimate of `fee_per_vbyte` is irreversible once signed.
- `fee()` returns `sum(prevouts) - sum(outputs)` (lines 137–141), so the transaction actually signs whatever fee results — there is no `fee > needed_fee` or `fee > max_reasonable` assertion before the FROST signing flow consumes `self.tx`.

The producer of `fee_per_vbyte` (a median fee sampled from a recent block in the processor) is a volatile, externally influenced value — exactly the "volatile market / outdated oracle" condition of the report — yet unlike `ExecuteDeposit`'s slippage check, nothing bounds how far the realized fee may drift from expectation.

### Impact Explanation
A `SignableTransaction` built with an inflated `fee_per_vbyte` commits the multisig to sign a transaction donating up to `sum(inputs) - sum(payments)` satoshis to miners. The signature is over that exact transaction, so once broadcast the loss is unrecoverable — funds are destroyed rather than merely delayed, matching the report's "user receives less than expected / funds lost to the protocol" outcome.

### Likelihood Explanation
Fee estimation depends on recent-block medians, which spike under congestion or fee manipulation, and the parameter is consumed raw with no sanity bound. Any caller passing a stale, mis-scaled (e.g., sat/kvB vs sat/vB), or manipulated value gets a valid, signable, consensus-legal transaction. Medium likelihood: it requires a bad fee input rather than purely internal state, but no privileged access to Serai internals is needed to influence observed fee rates.

### Recommendation
Add an upper bound analogous to slippage control: reject construction when `needed_fee` exceeds a configurable `max_fee` or a sane fraction of `input_sat`/`payment_sat`, and cap `fee_per_vbyte` at a protocol-defined maximum rate. Also error (rather than donating to fee) when the change remainder is large but below `DUST` would not apply — i.e., require a change output whenever the expected remainder materially exceeds `needed_fee`.

### Proof of Concept
1. Obtain any `ReceivedOutput` worth, e.g., 1 BTC.
2. Call `SignableTransaction::new(vec![output], &[(payment_script, 10_000)], None, None, fee_per_vbyte)` with `fee_per_vbyte = 1_000_000` (or any value such that `needed_fee` stays below `input_sat - payment_sat`).
3. Construction succeeds (`needed_fee` passes the lower-bound check, `input_sat >= payment_sat + needed_fee` holds, no change output is added).
4. Sign and broadcast: `fee()` returns `input_sat - payment_sat - 0` = ~1 BTC paid to miners, versus the intended few-thousand-sat fee. No error path in `SignableTransaction::new` prevents this; only the caller's trust in `fee_per_vbyte` does.
