## Title
Stale index-based diff-selection reused across a hook-triggered working-tree mutation causes Desktop to silently commit/push unreviewed content - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/stores/updates/changes-state.ts`, `app/src/lib/patch-formatter.ts`)

## Summary
The reported bug is a "value desync" class issue: `wrappedVault` kept using a stale balance representation instead of re-deriving it from the authoritative source (`lendShares`) after a state-changing action (`claimInterest`), breaking fungibility. The Desktop analog is a stale **derived state reused across a state-changing action**: GitHub Desktop persists a partial-line `DiffSelection` (an index-based bitmap) across working-directory refreshes without validating that the underlying diff content is still the same, and Desktop now (since hooks were enabled by default) automatically executes repository-defined Git hooks — including `post-merge` on every `pull`/`merge` — which can rewrite tracked files as a side effect of an operation the user believed was a passive network sync. The stale selection is then blindly applied to the new diff when the user commits, so the wrong lines can be included in the commit/push.

## Finding Description
`pull()` and `merge()` explicitly intercept and run `post-merge` (and other) hooks as part of routine `git pull`/fetch-driven merge operations: [1](#0-0) [2](#0-1) 

Which hooks run is resolved from `core.hooksPath`, honoring whatever the repository has configured (a very common convention for tracked hook frameworks such as Husky/lefthook, where the hooks directory is versioned inside the repo and can be changed by any commit that lands via a pull/merge): [3](#0-2) 

Separately, when the Changes view refreshes (e.g., after `_refreshRepository` following a pull), the previous per-line `DiffSelection` is carried forward onto the new working-directory diff purely by file ID, and is only discarded wholesale via `clearPartialState`, which is `false` on the normal post-pull refresh path: [4](#0-3) [5](#0-4) 

The diff-reload logic that runs afterward explicitly acknowledges that the diff content can have changed "dramatically" but only prunes lines that are no longer selectable — it does not verify that a still-selectable line at the same absolute index still represents the same content the user reviewed: [6](#0-5) 

Finally, when the user commits, `formatPatch`/`applyPatchToIndex` build the patch by re-fetching the **current** on-disk diff and applying the **stale** `DiffSelection` bitmap purely by absolute line index, with no content-identity check: [7](#0-6) [8](#0-7) 

The broken invariant: "the set of selected line indices represents the lines the user reviewed and intended to include" is assumed to remain valid across a working-tree mutation that Desktop itself triggers (hook execution during pull/merge), but nothing revalidates that assumption before the patch is generated — directly analogous to `wrappedVault.balanceOf` silently drifting from the authoritative `lendShares` after `claimInterest`.

## Impact Explanation
An attacker who controls the upstream remote/repository content (already an accepted primitive per the valid-impact list) can ship a modified `post-merge` hook script in a repository that uses a tracked `core.hooksPath` (a mainstream pattern). When the victim performs an ordinary `Fetch`→`Pull` in Desktop while they have a partially-selected file pending in the Changes tab, the hook runs automatically and can alter a tracked file's content while preserving the diff's hunk shape/selectable-line count. Desktop's stale, index-based selection is then silently reapplied to the mutated diff, and the resulting commit — created and pushed by the unsuspecting user — contains attacker-influenced content the user never reviewed or consented to. This is a silent corruption of what the user commits/pushes, without any unusual local steps: fetch/pull and commit are core, expected workflows.

## Likelihood Explanation
Moderate. It requires: (1) hooks enabled (default as of Desktop 3.5.5), (2) a repository configured with a tracked hooks path (common with Husky/lefthook-style setups), (3) the victim having an in-progress partial selection at the time of a pull/merge that changes the same file. These are all realistic, non-malware, non-admin, ordinary-user conditions, but they do require a specific timing/workflow overlap, which is why this is not "high" likelihood.

## Recommendation
- Invalidate (not merely prune) `DiffSelection` state whenever the underlying diff content differs from what it was computed against, e.g., by comparing content hashes/line text rather than only absolute indices, in `app/src/lib/stores/app-store.ts` (`updateChangesWorkingDirectoryDiff`) and `app/src/lib/stores/updates/changes-state.ts` (`updateChangedFiles`).
- Treat any post-hook working-tree mutation (post-merge/post-checkout/post-rewrite) as a trigger to force `clearPartialState: true` on the subsequent Changes refresh.
- Consider surfacing a confirmation/diff-recompute step before committing if the file changed on disk since the selection was last validated.

## Proof of Concept
1. Clone/attacker-controlled repo sets `core.hooksPath` to a tracked directory (e.g., `.husky`) containing a `post-merge` hook.
2. Victim, using Desktop, opens a tracked file in the Changes tab and selects only some lines for a future commit (partial `DiffSelection`), leaving the rest unselected.
3. Victim clicks `Fetch`/`Pull` in Desktop; the merge silently triggers the attacker's `post-merge` hook (`app/src/lib/git/pull.ts:47-56`), which appends/edits lines in the same file at positions that keep the previous absolute line indices "selectable."
4. Desktop's post-pull refresh reuses the old `DiffSelection` (`changes-state.ts:56`, `clearPartialState:false` in `app-store.ts:4110-4114`) instead of invalidating it.
5. Victim commits; `formatPatch`/`applyPatchToIndex` build the patch from the fresh (hook-mutated) diff using the stale selection bitmap, silently including attacker-authored lines the victim never reviewed, which are then committed and pushed.
