Based on the code, I found a real analog in GitHub Desktop's **"Git hook environment" feature**, which mirrors the *FreezerAddress* bug class exactly: a control introduced for one narrow, documented purpose ends up silently granting a much broader capability that isn't disclosed to the user.

### Title
Git hook environment loading exposes full shell environment (secrets) to repository-controlled hooks, exceeding its documented scope - ([File: app/src/lib/hooks/hooks-proxy.ts])

### Summary
GitHub Desktop's hook-interception feature is documented and presented to users as a narrow convenience: "load environment variables from your shell when executing Git hooks... useful if your Git hooks depend on environment variables set in your shell configuration files, a common practice for version managers such as nvm, rbenv, asdf" [1](#0-0)  Its actual implementation, however, hands every intercepted hook the *entire* shell environment obtained from the user's login shell, filtered only by a small blocklist of Git-internal variables, not by an allowlist tied to the stated purpose (PATH/tool-manager variables).

### Finding Description
`withHooksEnv` intercepts Git hook execution by rewriting `core.hooksPath` to a temporary directory of proxy executables whenever `interceptHooks` is requested and the hooks-environment setting is enabled [2](#0-1) . `createHooksProxy` then spawns the real hook using `getShellEnv`, which sources the user's interactive login shell (bash/zsh/PowerShell/etc.) to resolve PATH extensions for tools like nvm/rbenv. The resulting environment, `shellEnv.env`, is merged wholesale into the hook's process environment:

```
env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' },
``` [3](#0-2) 

The only filtering applied anywhere in this path is a small denylist of Git-internal variables (`GIT_SYSTEM_CONFIG`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, `GIT_CONFIG_PARAMETERS`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`) [4](#0-3) . There is no allowlist restricting `shellEnv.env` to PATH/tool-manager variables, so anything else sourced by the user's shell rc files (API tokens, cloud credentials, `NPM_TOKEN`, `AWS_SECRET_ACCESS_KEY`, SSH agent sockets, etc.) is passed straight into the hook's process. This is a materially larger capability than the stated purpose ("load PATH from shell for version managers"), and there is no user-facing notice enumerating which environment variables will be exposed to hook scripts, nor any event/warning fired when this occurs — exactly the "more power than documented, no notification" pattern described in the report.

Hook scripts in `.git/hooks` are attacker-reachable content in realistic workflows even though they aren't part of a normal `git clone`: many JavaScript/Node projects install hooks automatically via tooling (e.g., Husky) run as part of routine `npm install`/`npm ci` after cloning. A malicious or compromised package can drop an executable hook (e.g., `pre-commit`, `post-checkout`, `pre-push` — all of which are intercepted, see `commit.ts`, `merge.ts`, `pull.ts`, `push.ts`) that simply dumps `process.env` (or exfiltrates specific variable names) the next time the user commits, merges, pulls, or pushes from Desktop.

### Impact Explanation
If the hooks-environment setting is active, any hook already present or later planted in the working repository gets silent access to the user's full shell environment rather than only PATH-related state, which can leak credentials/tokens configured in the user's shell profile (`.bashrc`, `.zshrc`, `.profile`, PowerShell profile) to a script that came from the repository/its dependencies. This satisfies the "credential/token exfiltration" impact category: the corrupted value is the hook's process environment, which is supposed to carry only PATH-management state for version managers but instead carries the user's complete shell environment.

### Likelihood Explanation
`enableHooksEnvironment()` always returns `true` [5](#0-4) , and the underlying preference defaults to on for beta/dev channels via `enableHooksByDefault = enableBetaFeatures` [6](#0-5) , and is user-toggleable in stable via Preferences → Git → "Load Git hook environment variables from shell" [7](#0-6) . Changelog entries show hook support (and this shell-loading behavior) being progressively enabled by default across 3.5.5 betas [8](#0-7) . Given hooks fire on everyday operations (commit, merge, pull, rebase, push), any user who has this preference on and clones/uses a repository whose tooling installs a hook will trigger the leak without any further action or warning.

### Recommendation
Replace the denylist-based filtering in `hooks-proxy.ts` with an allowlist scoped to the documented purpose (e.g., `PATH`, and known version-manager variables like `NVM_*`, `RBENV_*`, `ASDF_*`), and surface to the user, at minimum in the Preferences description, exactly what data is exposed to hook scripts. Consider firing a one-time warning/log entry the first time a hook actually receives the shell environment, analogous to the audit's recommendation for the FreezerAddress case (event/notification when a control's side effects exceed its stated purpose).

### Proof of Concept
1. Enable "Load Git hook environment variables from shell" in Preferences → Git (default in beta/dev builds).
2. Export a secret in the shell profile that GitHub Desktop's `getShellEnv` will source, e.g. `export SUPER_SECRET_TOKEN=abcd1234` in `~/.zshrc`.
3. In any repository, add an executable `.git/hooks/pre-commit` (or have it installed transparently by a dependency's postinstall/Husky script) containing:
   ```sh
   #!/bin/sh
   echo "$SUPER_SECRET_TOKEN" > /tmp/exfiltrated
   ```
4. Commit from GitHub Desktop. The hook runs via `createHooksProxy` with `shellEnv.env` merged into its process environment [3](#0-2) , and `SUPER_SECRET_TOKEN` — unrelated to Git/PATH resolution — is written to `/tmp/exfiltrated`, confirming the hook received far more than the "PATH for version managers" scope advertised in the UI.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```
