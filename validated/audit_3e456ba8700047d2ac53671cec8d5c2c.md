### Title
Gasless swap tx admission can be permanently denied via on-chain DEX price manipulation of `GetAmountIn` - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.checkBalanceForSwap()` gates admission of a `GaslessSwapTx` into the tx pool by comparing the tx's declared `amountIn` against a `requiredAmountIn` fetched live from the `GaslessSwapRouter` contract's `getAmountIn(token, minAmountOut)`, which is priced off the underlying DEX pool's current reserves. Because this reference price is computed on-chain from spot reserves at admission time, it can be manipulated by any actor with sufficient capital or a flashloan, causing legitimate gasless swap transactions to be permanently rejected from the pool — the same bug class described in the external report (`calcImpact`-based expected price gating a swap causing denial of service).

### Finding Description
`checkBalanceForSwap` enforces:
```
tx.amountIn >= gsr.getAmountIn(minAmountOut)
``` [1](#0-0) 

`GetAmountIn` is a live `view` call into the `GaslessSwapRouter` contract, which internally resolves the token's DEX pair/router and computes the required input using the pair's current reserves (Uniswap V2 style `getAmountIn(amountOut, reserveIn, reserveOut)` formula) [2](#0-1) [3](#0-2) .

This check is invoked from `GetCheckBalance()`, which is called during transaction pool admission for every incoming gasless swap transaction (`IsModuleTx` → `GetCheckBalance`) [4](#0-3) . Since the DEX pool's reserves are on-chain state that any address can move with a swap in the same or a preceding block (including via flashloan for a low-liquidity pair), an attacker can inflate `requiredAmountIn` beyond the honest user's fixed `AmountIn`, causing `swapArgs.AmountIn.Cmp(requiredAmountIn) < 0` to trigger and the tx to be rejected with `"insufficient amountIn"` [5](#0-4) , exactly as validated in the existing test case for this rejection path [6](#0-5) .

This mirrors the reported pattern: an on-chain "simulated" expected value (`calcImpact`/`GetAmountIn`) that gatekeeps a swap operation, is trivially manipulable via flashloan/capital, and can be front-run to deny the operation entirely.

### Impact Explanation
Because `ShouldCheckSwapAmount()` gating this on-chain price check can be enabled (`BalanceCheckLevelSwapAmount`) [7](#0-6) , an attacker who repeatedly (or via a bot) manipulates the DEX reserves for a targeted token/pair immediately before a victim's `GaslessSwapTx` is considered for pool admission can cause a persistent denial-of-service against the KIP-247 gasless swap feature for that token: legitimate users' swap transactions are rejected from admission, they cannot get gas lent, and their transaction never enters the pool. This is a functional denial-of-service on the gasless module, reachable by any unprivileged actor with capital or flashloan access — no special privilege needed.

### Likelihood Explanation
Likelihood is significant when a token's underlying DEX pool has low liquidity or the pool can be moved cheaply/with a flashloan, since manipulating reserves before the target's admission check is straightforward and requires no privileged access — only an ordinary swap transaction against the pool.

### Recommendation
Do not rely purely on a live/spot on-chain reserve-based `GetAmountIn` result as an absolute floor for tx-pool admission. Consider: (1) using a TWAP or otherwise manipulation-resistant reference price, (2) allowing tolerance/slippage margin around the spot quote instead of a hard `>=` cutoff, or (3) treating this check as an advisory/soft filter rather than an outright rejection reason, deferring the final settlement enforcement to the swap's own on-chain slippage checks (`minAmountOut`) at execution time rather than at pool admission time.

### Proof of Concept
1. Identify a `GaslessSwapTx` target token whose `GaslessSwapRouter`-registered DEX pair has thin liquidity.
2. Submit (or flashloan-fund) a large swap against that pair's reserves immediately before/around the victim's `GaslessSwapTx` submission, shifting `reserveIn`/`reserveOut` so that `getAmountIn(token, minAmountOut)` returns a value greater than the victim's `swapArgs.AmountIn`.
3. When the victim's `GaslessSwapTx` reaches `checkBalanceForSwap` during pool admission, `swapArgs.AmountIn.Cmp(requiredAmountIn) < 0` is true, and the transaction is rejected with `"insufficient amountIn"` [1](#0-0) , never entering the pool despite being a well-formed, otherwise valid gasless swap.
4. Repeating this before every submission attempt produces a sustained denial-of-service against the gasless swap feature for that token.

	if tx == nil {
		return false
	}

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}
