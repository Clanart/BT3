### Title
`SignableTransaction::new` omits the OP_RETURN `data` output from fee/weight accounting, underpaying the fee for every transaction carrying data - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes a caller-supplied OP_RETURN `data` output into `tx_outs` but computes `needed_fee` using `calculate_weight_vbytes`, which is only ever invoked with `payments` (and optionally `change`). The data output's weight is never accounted for, so every transaction created with `data` pays less than the requested `fee_per_vbyte`, and the actual fee can fall below the network minimum relay fee even though the `TooLowFee` check passed. This mirrors the factory bug class: an inadequately provisioned fee produces a transaction that silently fails to propagate/confirm while the caller treats the plan as executed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

1. `SignableTransaction::new` validates `data` length (`<= 80` bytes) and appends an OP_RETURN `TxOut` to `tx_outs` at lines 194–202.
2. Fee sizing happens at line 204: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and again at lines 225–226 with `change`. `calculate_weight_vbytes` (lines 62–127) builds a mock `Transaction` whose `output` vector contains only `payments` plus optional `change` — the `data` output is never included.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) is therefore computed for a transaction ~`8 + script_len` weight units smaller than the real one. With the maximum 80-byte payload plus OP_RETURN overhead, the discrepancy is ~90 bytes / ~90–360 weight units, i.e. ~25%+ of the vsize of a minimal 1-input/1-output transaction.
4. The `TooLowFee` check at line 211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the same underestimated `vbytes`, so a transaction can pass validation while `self.fee()` (the actual `sum(inputs) - sum(outputs)`) is below the relay minimum for the true size.
5. `SignableTransaction::sign`/broadcast then produces a transaction the network will not relay or that confirms far below the intended rate. Nothing signals this back to the caller: `new` returned `Ok`, `needed_fee()` reports the (wrong) target, and the signed transaction simply never confirms — the same silent partial-failure shape as the `jetton_minter` balance depletion, where the upstream `factory` proceeded as if all mints succeeded.

### Impact Explanation
Any caller of the public `SignableTransaction::new` API that attaches `data` (e.g., embedding a protocol commitment/In/Out instruction in an OP_RETURN, as Serai's own stack does in `tests/full-stack/src/tests/mint_and_burn.rs`) gets a transaction whose effective fee rate is strictly lower than the `fee_per_vbyte` they specified. At low fee rates the transaction fails the minimum-relay-fee policy and is never propagated; at higher rates it confirms materially later than priced. For a system like the processor, which treats `SignableTransaction`/`Eventuality` creation as a committed plan, this yields the reported inconsistency: the plan/DAO is "active" but the payment leg silently never lands. Medium severity: funds are not stolen, but payments are stuck/delayed and state diverges from what was agreed, with no error surfaced.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some` — no attacker ingenuity is needed, only use of a documented public parameter. Reachability by an unprivileged party depends on integrators exposing the `data` field (Serai's own protocol encodes instructions via OP_RETURN); where the processor itself passes `None`, it is unreachable. Severity is capped at Medium because it degrades availability/consistency rather than enabling theft.

### Recommendation
Include the data output in weight accounting. Either pass the final `tx_outs` (or a `data_len` parameter) into `calculate_weight_vbytes`, or compute the mock transaction's `output` from `payments + OP_RETURN(data) + change`, so `vbytes` reflects the actual transaction before `needed_fee` and the `TooLowFee`/`MAX_STANDARD_TX_WEIGHT` checks are evaluated.

### Proof of Concept
```rust
// networks/bitcoin SignableTransaction::new with a data payload
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, None, Some(data.clone()), fee_per_vbyte)
  .unwrap();

// needed_fee was computed for vbytes WITHOUT the OP_RETURN output
assert_eq!(
  tx.needed_fee(),
  fee_per_vbyte * (u64::try_from(/* tx without data */ vsize).unwrap())
);

// The real transaction is ~90 vbytes larger than accounted, so its true
// fee rate is < fee_per_vbyte. At fee_per_vbyte == min relay rate, the
// signed TX is below the minimum for its actual size and never relays,
// while `new` returned Ok and no error is propagated to the caller.
```
The concrete defect is that `tx_outs` gains an output at `send.rs:194–202` after the only weight calculation paths at `send.rs:204` and `send.rs:225–226`, neither of which is aware of `data`.
