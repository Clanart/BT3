### Title
Quadratic Lagrange interpolation in `SignMachine::sign`/`complete` enables CPU-exhaustion DoS from attacker-supplied preprocess/share sets - (File: crypto/dkg/src/lib.rs)

### Summary
The external report (CVE-2023-2198) describes a denial of service where a small crafted input forces the server to perform superlinear work (catastrophic regex backtracking). The analog in Serai's in-scope code is the Lagrange interpolation path in `Interpolation::interpolation_factor`: computing the factor for one signer is O(k) in the size of the signing set, and FROST's `sign`/`complete` flow computes it for every included signer, yielding O(k²) field operations plus k modular inversions for a signing set of size k. Because `n` is a `u16`, an unprivileged counterparty can supply a preprocess/share map containing up to 65,535 distinct `Participant` keys, forcing ~4.3×10⁹ field multiplications and tens of thousands of inversions inside `ThresholdKeys::view` / `ThresholdView::interpolation_factor` for a few megabytes of input.

### Finding Description
`Interpolation::interpolation_factor` iterates the entire `included` set, multiplying a numerator and denominator per other signer and finishing with a field inversion: [1](#0-0) 

`SignMachine::sign` builds `included` from the attacker-influenced `HashMap<Participant, Preprocess>` keys, only bounds it by `n` (`u16`), then calls `self.params.keys.view(included)` and `validate_map`, which interpolates per participant: [2](#0-1) 

`ThresholdView::interpolation_factor` is likewise O(k) per query and is invoked per signer during share verification in `complete`: [3](#0-2) 

The per-signer byte cost to trigger this is tiny: `Commitments::read` reads a fixed number of points (bounded by the algorithm's nonce generators), and `read_share` reads a single scalar, so ~64–96 bytes per participant suffice: [4](#0-3) [5](#0-4) 

### Impact Explanation
A single message of a few megabytes (65,535 preprocesses × ~64 bytes) forces the victim node to perform billions of scalar multiplications and 65,535 sequential field inversions during `view()` and again during share verification. This stalls the signing/coordinator task for a far longer period than the input size would suggest — the same asymmetric-work DoS pattern as the GitLab ReDoS, mapped onto Serai's threshold-signing path. Repeated submissions keep the node's signing pipeline saturated, preventing timely production of signatures (liveness failure for bridge operations).

### Likelihood Explanation
Reachability requires the attacker to participate as (or spoof) many distinct `Participant` indexes in a signing set. In deployments where preprocesses are relayed per-participant and `n` is large, or where an adversary can register many validator indexes, the input is reachable via `read_preprocess`/`read_share` bytes fed into `sign`/`complete` — exactly the untrusted-input surfaces enumerated as in-scope. For small validator sets (n ≤ a few hundred) the quadratic term is negligible, so the severity is bounded by the maximum `n` actually supported; with the `u16` cap the theoretical worst case is ~65k signers. This is why it is Medium rather than High: it is a pure CPU/liveness DoS with no key or forgery impact, and real deployments likely cap `n` well below 65,535.

### Recommendation
- Cap the accepted signing-set size to a sane protocol maximum (e.g., a few hundred participants) before building `included`, rather than allowing `n` up to `u16::MAX`.
- Compute Lagrange denominators once per session: the denominator of `λ_i` can be derived in O(k) total using a product tree or prefix/suffix products (`denom_i = prod_{l≠i}(l - i)` via prefix products), reducing the per-signer work to O(1) amortized, and batch the inversions with Montgomery's trick (one inversion + O(k) multiplications for all k signers).
- Alternatively, prefer `Interpolation::Constant` (O(1) per factor, `crypto/dkg/src/lib.rs:228`) where the protocol permits, avoiding the per-session quadratic entirely.

### Proof of Concept
Sketch against the library API (no network needed to demonstrate the asymmetry):

```rust
// crypto/frost — attacker side
// Build keys with Lagrange interpolation and n = u16::MAX via
// ThresholdParams::new(t, u16::MAX, i) and a Lagrange-interpolated key gen.
// Then submit preprocesses for participants 1..=65535:
let mut preprocesses = HashMap::new();
for l in 1u16..=u16::MAX {
    // ~64 bytes of point encodings parsed by read_preprocess
    preprocesses.insert(Participant::new(l).unwrap(), crafted_preprocess_bytes);
}
// Victim executes:
//   machine.sign(parsed_preprocesses, msg)
//   -> included.len() == 65535
//   -> view(): for each of 65535 signers, interpolation_factor iterates 65535 others
//      => ~4.3e9 field multiplications + 65535 sequential inversions
//   -> complete() repeats the same quadratic work during share verification
```

Cost asymmetry: input ≈ 65535 × ~64 B ≈ 4 MB; server work ≈ O(65535²) ≈ 4.3 billion field operations plus 65,535 inversions, run twice (once in `view`/sign, once in share verification during `complete`).

Caveat: I could not fully verify within the available context whether production callers (coordinator/processor) already bound the preprocess map to a small validator-set size before calling `sign`; the `coordinator/src/tributary` transaction reader bounds transaction size, which indirectly limits per-transaction attacker keys, but the quadratic complexity in the in-scope `crypto/dkg` + `crypto/frost` crates stands on its own.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
