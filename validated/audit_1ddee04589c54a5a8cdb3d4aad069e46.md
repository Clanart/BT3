### Title
Cached preprocess seed is not bound to `ThresholdKeys`/params: resuming via `from_cache` after a key-set mutation reuses FROST nonces under a new signing context, enabling private key share recovery - (File: crypto/frost/src/sign.rs)

### Summary
The reported bug class is *cached session state reused after the trust/configuration inputs mutated, without re-deriving or re-validating the security-critical material*. In `crypto/frost`, `AlgorithmSignMachine::from_cache` rebuilds a sign machine from a 32-byte seed (`CachedPreprocess`) that was cached under potentially different `ThresholdKeys`/`Params`. `seeded_preprocess` deterministically regenerates the FROST nonces solely from the seed (plus the unchanged `original_secret_share`), so if the participant set / `Params` mutated between `cache()` and `from_cache()`, the resumed session emits the identical nonce commitments and will produce a second signature share under the same nonces — classic FROST nonce reuse across distinct binding contexts, which leaks the secret share.

### Finding Description
`SignMachine::cache()` returns only the RNG `seed` (sign.rs:264-266), discarding `params`/`keys`. `from_cache` (sign.rs:268-274) accepts fresh `algorithm` and `keys` and calls `AlgorithmMachine::new(algorithm, keys).seeded_preprocess(cache)`. Inside `seeded_preprocess` (sign.rs:121-144), `ChaCha20Rng::from_seed(*seed.0)` regenerates `(nonces, commitments)` via `Commitments::new(&mut rng, params.keys.original_secret_share(), ...)` and `blame_entropy` from the same stream. Nothing in the seed derivation, the nonce derivation, or `from_cache` binds the cached seed to `params.multisig_params()` (t, n, i), `params.keys` (verification shares, group key, interpolation), or the algorithm's transcript state. There is no check that the resumed `keys` equal the keys in effect when the seed was cached.

### Impact Explanation
If `ThresholdKeys` are mutated between `cache()` and `from_cache()` — e.g., a participant set change, threshold change, offset change, or key rotation that leaves `original_secret_share` intact — the resumed machine outputs the same `Preprocess.commitments` (same nonce scalars d, e) while `sign()` now computes binding factors `rho` over a different included set / `ThresholdView` / `group_key`. Two shares produced under the same nonce with different `(rho, lagrange coefficient, challenge)` form a linear system that recovers the signer's secret share (standard FROST/ROS-style nonce-reuse key recovery). This is precisely the resumed-session-with-mutated-trust-config pattern: the "resumed handshake" (from_cache) proceeds with stale cached material rather than re-deriving nonces bound to the current configuration. Result: private key share recovery by a party observing the two shares — an accepted impact (key share recovery) reachable through the public `sign`/`read_preprocess`/`from_cache` API surface.

### Likelihood Explanation
The `SignMachine` trait explicitly supports the cache/rebuild flow, and `from_cache` performs zero validation that the supplied `keys`/`params` match those used at cache time — the seed is an opaque `[u8; 32]` with no bound context. Any integrator or caller that persists a `CachedPreprocess` and later resumes it under reconstructed `ThresholdKeys` (exactly the documented "rebuild from a cache" pattern) hits this whenever the key material was regenerated, re-viewed (`keys.view(included)`), offset, or re-parameterized between cache and resume. Because the nonce stream depends only on the seed and `original_secret_share`, identical nonces are emitted deterministically whenever the share is unchanged — no probabilistic or attacker-exotic conditions required.

### Recommendation
Bind the cached material to the signing configuration: derive the nonce RNG seed as `seed' = H(seed || params.keys.group_key() || multisig_params() || algorithm context)` inside `seeded_preprocess`, so any mutation of keys/params changes the derived nonces. Alternatively, store and re-verify a commitment to the effective `ThresholdKeys`/`Params` inside `CachedPreprocess` (extend it beyond `[u8; 32]`) and have `from_cache` reject on mismatch. Either approach makes resumption under mutated configuration fail safe instead of silently reusing nonces.

### Proof of Concept
1. Create `AlgorithmMachine::new(alg, keys_v1)`, call `preprocess(rng)` → `(machine_v1, preprocess)`, then `machine_v1.cache()` → `seed`. Sign once with a set `S1` of peer preprocesses and `msg1` → share `s1` (nonces `d, e`).
2. Mutate configuration: construct `keys_v2` with a different participant set/threshold/offset but the same `original_secret_share` (e.g., `ThresholdKeys::new` with different `params` or a different `Interpolation`), then call `AlgorithmSignMachine::from_cache(alg, keys_v2, seed)`.
3. The resumed machine deterministically regenerates the same `(nonces, commitments)` (same `ChaCha20Rng` stream — sign.rs:127-132) and emits the same preprocess commitments. Sign a second time with a different included set `S2`/`msg2` → share `s2` computed with the same `d, e` but a different `rho`/Lagrange coefficient/challenge.
4. Solve the two share equations to recover `original_secret_share` — private key share recovery from an unprivileged party's perspective, needing only the two publicly broadcast shares and preprocesses.

Root cause: `from_cache`/`seeded_preprocess` (crypto/frost/src/sign.rs:121-145, 268-274) treats the cached seed as configuration-agnostic and re-validates nothing about the resumed keys, mirroring the TLS session-resumption flaw where the resumed path skips re-checking against the mutated trust configuration.
