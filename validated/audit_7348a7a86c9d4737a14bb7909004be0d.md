### Title
Unvalidated `bypassURL` extracted from attacker-controlled git server push-rejection message is rendered as a trusted GitHub link - ([File: app/src/ui/dispatcher/error-handlers.ts])

### Summary
`extractSecretScanningResults` parses the raw stderr text returned by the git remote when a push is rejected by secret scanning, and pulls a `bypassURL` string straight out of that server-controlled text via regex with no validation that it is actually a `github.com` URL. [1](#0-0)  That value is then handed unchanged to the UI as `secret.bypassURL` and rendered as a clickable `LinkButton`. [2](#0-1) 

### Finding Description
This is the same broken invariant as the `ecrecover` report: a value produced by a "recovery"/parsing step (`ecrecover`'s recovered address, or here, the regex-captured `bypassURL`) is trusted and used directly for a security-relevant purpose (indexing a trust map / rendering a "GitHub" action link) instead of first being validated against the expected value (a real signer address, or here, a real `github.com` URL).

`remoteMessage` is the literal text a git remote sends back on a rejected push — fully attacker-controlled if the user's remote or push proxy is malicious or compromised. The extraction regex only requires the captured text to start with `https` (`(?<bypassURL>https[\s\S]*?) `), with no check that it points at `github.com` or any expected host: [3](#0-2) 
The `id` used to key the "bypassed" state map is also derived from this unvalidated string (`bypassURL.split('/').pop()`), inheriting the same lack of validation. [4](#0-3) 

The dialog then presents this attacker-supplied URL as the target of a "Bypass" button styled and positioned identically to the legitimate GitHub bypass flow, with no indication that the destination has not been verified to be `github.com`: [2](#0-1) 

Existing guards do not stop this path: there is no host/domain allowlist check anywhere between the regex extraction and the `LinkButton` render, and the surrounding UI text ("removing the secret…", "Bypass") reinforces user trust that the link is an official GitHub URL.

### Impact Explanation
A malicious or compromised git server (or a machine-in-the-middle git proxy) can reject a push with a crafted secret-scanning-style message containing a `bypassURL` pointing to an attacker-controlled phishing page that mimics GitHub's bypass-approval UI. Because Desktop presents this as a first-party "Bypass" action inside a dialog it generated itself, users are primed to trust and click it, potentially leading to credential/token exfiltration once redirected to the attacker page in the system browser — this fits the in-scope impact category of "a link ... the user clicks" resulting in "credential/token exfiltration."

### Likelihood Explanation
Any git host or MITM proxy that Desktop pushes to can return arbitrary stderr text on a rejected push; no special privileges beyond controlling the remote/proxy are needed, matching the report's baseline "attacker controls ... a git remote/proxy response." The only user action required is clicking a button inside a dialog that Desktop itself displayed as trustworthy, which is a normal, expected interaction (not an unnatural social-engineering step).

### Recommendation
Validate `bypassURL` (and any similarly extracted URL from git remote error output) against an explicit allowlist (e.g., must have host `github.com`/the configured Enterprise host and a path matching the expected bypass-approval route) before storing or rendering it, exactly as the original report recommends for `ecrecover`: use the parsed/recovered value only for comparison against a known-good expected value, never as an untrusted, freely-usable value.

### Proof of Concept
1. Set up a git remote (or a transparent push proxy) that rejects any push with a rejection message crafted to match the `secretsRegex` pattern used in `extractSecretScanningResults`, e.g.:
   ```
   —— GitHub Access Token ——————————————
   locations:
     - commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
       path: secrets.txt:1
   https://attacker.example/fake-bypass-approval 
   ```
2. Have a victim add this remote in GitHub Desktop and attempt to push a commit.
3. Desktop parses the rejection message via `extractSecretScanningResults` [1](#0-0) 
and shows the `PushProtectionErrorDialog` with a "Bypass" link whose `uri` is `https://attacker.example/fake-bypass-approval`. [2](#0-1) 
4. The victim, trusting the in-app dialog, clicks "Bypass" and is taken to the attacker's phishing page instead of a legitimate `github.com` bypass-approval page.

function extractSecretScanningResults(
  remoteMessage: string
): ReadonlyArray<ISecretScanResult> {
  const secretsRegex =
    /—— (?<description>.*?) —+[\s\S]*?locations:(?<locationsGroup>(?:\s+- commit: [a-f0-9]{40}\s+path: [\s\S]*?)+).*?(?<bypassURL>https[\s\S]*?) /g

  const matches = [...remoteMessage.matchAll(secretsRegex)]

  const secrets: Array<ISecretScanResult> = []
  if (matches.length === 0) {
    return secrets
  }

  for (const match of matches) {
    if (match.groups === undefined || match.index === undefined) {
      continue
    }

    const { bypassURL, description, locationsGroup } = match.groups
