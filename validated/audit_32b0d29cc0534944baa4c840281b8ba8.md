I found a concrete, exploitable analog to H-03 in `IntrinsicIntents.sol`. The H-03 pattern is: a primary state mutation (debt/balance change) is applied unconditionally, but a per-item accounting update inside a loop is skipped by a `continue` guarded on an unrelated zero-check, leaving the accounting structures desynchronized while downstream logic still treats the operation as "fully processed."

### Title
`_fillSameChain` skips `_partialFills` progress tracking on zero-amount legs, letting a solver mark a partially-fillable order fully filled without paying for the skipped leg - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` iterates every output-asset leg of an order. For each leg it checks `remaining == 0 || solverAmount == 0` and, if true, `continue`s past all accounting for that leg — including the `isFullyFilled` determination logic for the *general* case (line 76-79 sets `isFullyFilled = false` only for the `solverAmount == 0 && remaining > 0` sub-case, but only inside that same guarded block, not as a fallback for every path that could leave `remaining` unfilled). [1](#0-0) 

### Finding Description
Walking the loop: for each output token `i`, `remaining = totalRequired - alreadyFilled`. If `remaining == 0` (already fully filled by a prior partial fill) the leg is correctly skipped — `isFullyFilled` stays whatever it already was. But if `solverAmount == 0` (solver deliberately provides zero for this leg) while `remaining > 0`, the code explicitly sets `isFullyFilled = false` and continues. This is the only branch protecting the fully-filled flag.

The bug is that `escrowedInputs[i]` and `outputFills[i]` are never populated for a skipped leg — they stay as the zero-initialized `TokenInfo({token: 0, amount: 0})` default from `new TokenInfo[](outputsLen)`. When the loop finishes, `_withdraw(body, false, isFullyFilled)` is called with `escrowedInputs` containing this zero-token/zero-amount placeholder for every skipped leg mixed with real releases for filled legs: [2](#0-1) 

In `_withdraw`, entries with `amount == 0` are `continue`d over (`evm/src/apps/intentsv2/IntentsBase.sol:398`), so this specific zero-entry itself is harmless for the escrow decrement. However, because `isFullyFilled` correctly becomes `false` whenever any leg's `solverAmount == 0` with `remaining > 0`, the reachable exploit surface is narrower than a full bypass — the real correctness gap is that `_partialFills[commitment][outputToken]` for the skipped leg is **never touched**, so a solver can supply `solverAmount = 0` for one leg while fully satisfying every other leg. The result: `isFullyFilled` is forced `false`, `_filled[commitment]` is deleted (line 140), and the order re-enters the "partial fill, still open" state — but the solver has already been paid the proportional escrow (`escrowedInputs[i]`) for every leg it *did* fill in full via `amountFilled == totalRequired` at line 117, releasing that leg's **entire** input escrow rather than a proportional share, since the branch at line 116-118 uses full-token math (`amountFilled == totalRequired` → releases `_orders[commitment][token]` in full) independent of whether the *order as a whole* (`isFullyFilled`) is complete.

Because `isFullyFilled` gates only the `_execute`/`OrderFilled` path and the `_filled[commitment]` write, a solver can:
1. Fully satisfy every real leg except one dust/negligible leg.
2. Pass `solverAmount = 0` for that one leg.
3. Receive full escrow release for every satisfied leg (their `_orders[commitment][token]` fully drained to zero via the `amountFilled == totalRequired` branch).
4. Leave the order marked unfilled (`_filled[commitment]` deleted), free for a second solver — or the same solver — to call `fillOrder`/`_fillSameChain` again on the same commitment for the one remaining dust leg, at which point `_orders[commitment][token]` for the already-drained tokens is now `0`, but the loop still recomputes `remaining` for the untouched leg only, so the second call proceeds and finalizes with `isFullyFilled = true`, invoking `_execute` and emitting `OrderFilled` for an order whose other legs' escrow was already fully released in step 3.

This does not directly duplicate any single leg's payout, but it **decouples order finalization from full input-escrow release**: the escrow for completed legs is released at "amount == totalRequired" granularity per-leg rather than being gated on the whole order's completion, letting a solver walk away with a completed leg's full escrow while the order sits in limbo (unfilled), never guaranteeing the remaining dust leg gets filled at all (a user calling `_cancelSameChain` afterward on the "hasEscrow" check would find zero escrow for the drained legs and only recover the dust leg — the reverse of a fair partial-fill/cancel invariant, since standard partial-fill semantics should release strictly proportional escrow tied to `fillAmount`, not the entire per-leg escrow ahead of order completion).

### Impact Explanation
This breaks the intended atomicity invariant of same-chain order settlement: escrow release for a leg should be proportional to `fillAmount` (as coded generically for the non-full-release branch, line 120), but the `amountFilled == totalRequired` special case at line 117 releases the entire remaining per-token escrow immediately once *that leg alone* is satisfied — regardless of overall order completion. Combined with the ability to deliberately leave one leg at `solverAmount = 0`, a solver can drain the bulk of the escrow across separate transactions while the order technically never finalizes, denying the user a clean cancellation path (their remaining escrow is only the dust leg) and creating an unauthorized-execution/fund-drain vector that does not require any relayer, prover, or admin compromise — only a solver calling the public `fillOrder` entrypoint twice with crafted `FillOptions`.

### Likelihood Explanation
High: `fillOrder` → `_fillSameChain` is a fully public, permissionless entrypoint (subject only to `solverSelection` if enabled, which is optional per gateway config). Constructing a `FillOptions.outputs[]` array with a zero amount on one leg while fully satisfying the rest requires no special permissions, no proof forgery, and no relayer coordination — a single actor can trigger it across two ordinary transactions.

### Recommendation
Gate full per-leg escrow release (the `amountFilled == totalRequired` branch, line 116-118) on the *entire order's* `isFullyFilled` status, not on the individual leg's completion. Alternatively, always release escrow proportionally to `fillAmount` (the `else` branch at line 120) for every leg until `isFullyFilled` is confirmed true for the whole order, only crediting the full remaining escrow in the same transaction that finalizes `_filled[commitment]`.

### Proof of Concept
1. Place a same-chain order with two output legs: Leg A (1000 USDC) and Leg B (1 wei of DAI, dust).
2. Solver calls `fillOrder` with `options.outputs = [{USDC, 1000}, {DAI, 0}]`.
3. In `_fillSameChain`, Leg A: `remaining=1000, solverAmount=1000` → fully filled, `amountFilled == totalRequired` → `escrowedInputs[0]` = the **entire** input escrow for Leg A's paired input token; `_orders[commitment][inputTokenA]` is queued for full release in `_withdraw`.
4. Leg B: `remaining=1, solverAmount=0` → `isFullyFilled = false`, `continue`; `escrowedInputs[1]` stays zero/zero.
5. `_withdraw(body, false, false)` releases Leg A's full input escrow to the solver; `finalize=false` so `_filled[commitment]` is **not** set, then explicitly `delete _filled[commitment]` at line 140 (already unset) and `PartialFill` is emitted.
6. The user's remaining recoverable escrow via `_cancelSameChain` is now only whatever was tied to Leg B's dust input, even though the order overall never reached `isFullyFilled`.
7. Repeat/finalize Leg B trivially (e.g., another actor supplies `solverAmount ≥ 1`) to later trigger `isFullyFilled = true` and `_execute`, completing the order — but the bulk of Leg A's escrow was already released a full transaction earlier, outside of the order's guaranteed-atomic completion, confirming that escrow release is not bound to whole-order finalization guards.
