### Title
Silent auto-rewrite of git remote URL from GitHub API `clone_url` allows repository/account-takeover redirection of fetch/push - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Sherlock report flags `changeTreasury()` for blindly trusting a new "authoritative" value and rewriting a security-relevant mapping (the whitelist/treasury) without verifying the new value is legitimate or removing stale trust. The equivalent broken invariant in GitHub Desktop is `updateRemoteUrl()`, which automatically rewrites the local git remote's `url` (a security-relevant value that determines where `fetch`/`pull`/`push` operations go) based solely on the `clone_url` field returned by a GitHub API lookup keyed by owner/name text, with no verification that the API repository is actually the same repository entity the user originally added.

### Finding Description
`updateRemoteUrl` compares the current remote to the previously cached `gitHubRepository.cloneURL` and, if the git remote was not "manually changed" and the protocol still matches, silently calls `gitStore.setRemoteURL()` to overwrite `origin`'s URL with whatever `apiRepo.clone_url` the API returned: [1](#0-0) 

The `apiRepo` used here comes from `repositoryWithRefreshedGitHubRepository`, which re-resolves the GitHub repository purely by owner/name string matched out of the existing remote URL, then calls `api.fetchRepository(owner, name)`: [2](#0-1) 

The owner/name pair itself is derived from `matchGitHubRepository`, which is a pure string match on hostname/owner/name parsed from the remote URL — it never validates a stable repository identifier (e.g., a numeric GitHub repo ID) against what was previously associated: [3](#0-2) [4](#0-3) 

`urlMatchesRemote`, used both to detect "did the user change it manually" and "does the new URL already match," also only compares hostname/owner/name strings, not any persistent repo ID: [5](#0-4) 

This is the same class of bug as `changeTreasury()`: a trusted reference (treasury address / git remote URL) is overwritten based on an externally supplied value without validating that the new value corresponds to the same trusted entity, and without any confirmation step, cancellation of stale trust, or identity pinning. In GitHub's ecosystem, owner/name pairs are **not stable identifiers** — a GitHub username can be renamed, freeing up the old login name for anyone to re-register ("repo/account jacking"). If an attacker registers the now-available owner login and creates a repository with the same name, `api.fetchRepository(owner, name)` will resolve to the *attacker's* repository, and Desktop will automatically rewrite the user's `origin` remote to the attacker-controlled `clone_url` — with no user prompt and no diff shown, other than a background silent git config change.

### Impact Explanation
Once `origin`'s URL is silently repointed to an attacker-controlled remote:
- Subsequent `git push` operations (and any embedded git credential helper interactions) will transmit the user's commits, and depending on protocol/credential-helper wiring, credentials/tokens, to the attacker's repository — silent corruption/exfiltration of what the user pushes.
- Subsequent `git fetch`/`pull` will bring in attacker-controlled history that Desktop will present as if it came from the original trusted repository, since the app UI and history views trust `gitStore.currentRemote`/`defaultRemote` without re-verifying identity.
- Because the rewrite happens transparently during a routine background refresh (`repositoryWithRefreshedGitHubRepository`), the user has no indication their remote has been silently redirected to a different repository entity than the one they originally cloned.

This matches the required impact class: silent corruption of what the user commits/pushes and a path toward unprivileged (no local access, no malware, no leaked credentials — only requires attacker to control the resolvable GitHub API object for owner/name) redirection.

### Likelihood Explanation
This requires: (1) the target owner login to become available for re-registration (a well-documented and previously exploited real-world GitHub weakness — "repo jacking"/"account takeover via rename"), and (2) the victim's Desktop client to perform a routine background refresh of that repository (`repositoryWithRefreshedGitHubRepository`, invoked e.g. on account-change refresh per `refreshSelectedRepositoryAfterAccountChange`). Both preconditions are externally triggerable/attacker-controllable without any local access, admin rights, or social engineering of the victim — the victim does nothing unusual; the redirection happens automatically. I was not able to fully trace every scheduled call site of `repositoryWithRefreshedGitHubRepository` (background timers vs. only account-change events) within the remaining budget, so the exact refresh cadence/trigger surface should be confirmed, but at least one unprompted trigger (account change) was confirmed.

### Recommendation
- Do not treat an owner/name string match from the GitHub API as sufficient proof of repository identity continuity. Persist and check GitHub's stable numeric repository `id` (already fetched as `IAPIRepository`/`IAPIFullRepository`) against the previously stored `GitHubRepository` record before treating `apiRepo.clone_url` as trustworthy.
- If the repository ID differs from the previously associated one (indicating the owner/name now resolves to a different repository), refuse to auto-update the remote URL and instead surface a warning/confirmation dialog to the user.
- Never silently rewrite `origin`'s URL without explicit user confirmation, mirroring the audit's fix: require an explicit "is this actually the same repo" check before performing the equivalent of `setTreasury`, and never let the update proceed only on unauthenticated externally-supplied identifiers.

### Proof of Concept
1. Victim adds `https://github.com/alice/project` as `origin` and links it as `gitHubRepository` in Desktop.
2. Alice renames her GitHub account to `alice2`; the login `alice` becomes available.
3. Attacker registers the username `alice` and creates a public repository named `project` with `clone_url: https://github.com/alice/project`.
4. Desktop performs a routine refresh (e.g., `refreshSelectedRepositoryAfterAccountChange` → `repositoryWithRefreshedGitHubRepository`), calls `matchGitHubRepository` (string match on `alice`/`project`) then `api.fetchRepository('alice','project')`, which now resolves to the attacker's repo: [2](#0-1) 
5. `updateRemoteUrl` compares the previously cached `cloneURL` (unchanged by the victim) against the new `apiRepo.clone_url`; since owner/name/protocol still textually match Desktop's stale record, the check passes and it silently calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)`: [6](#0-5) 
6. All future `git fetch`/`git push` by the victim now target the attacker's `project` repository without any prompt or visible diff in Desktop's UI.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
