### Title
Out-of-range `Participant` index in a PedPoP blame accusation panics via unchecked `HashMap` indexing - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
Analogous to CVE-2016-2572 (a remote peer crashing the daemon by feeding malformed input to a path that asserts on it), `BlameMachine::blame` / `AdditionalBlameMachine::blame` index `HashMap`s with attacker-influenced `Participant` values without checking membership, causing a panic (process abort) instead of a handled error.

### Finding Description
`blame()` accepts `sender` and `recipient: Participant` from an accusation message and calls `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575`). Inside `blame_internal`:

1. `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` is called, which indexes `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`). `enc_keys` is populated in `Decryption::register` only for participants whose `EncryptionKeyMessage` was processed — in the normal `BlameMachine` flow, `verify_r1` registers every participant *except* the local node itself (`crypto/dkg/pedpop/src/lib.rs:313-315`). An accusation naming `recipient = i` (the local participant) indexes a key that was never inserted, and `HashMap`'s `Index` impl panics.
2. If decryption succeeds, `self.commitments[&sender]` is indexed (`crypto/dkg/pedpop/src/lib.rs:599`). `commitments` only contains `all_participant_indexes()` (1..=n); an accusation naming `sender = Participant(n+1)` or any index outside that set panics. The same applies to `AdditionalBlameMachine::new`, which only registers 1..=n (`crypto/dkg/pedpop/src/lib.rs:656-659`).

The crate itself documents this hazard: `AdditionalBlameMachine::new` warns that invalid input "may cause everything from inaccurate blame to panics" (`crypto/dkg/pedpop/src/lib.rs:646-648`), confirming the panic is real and unguarded.

### Impact Explanation
An unprivileged DKG participant can broadcast a blame accusation whose `sender`/`recipient` fields reference a participant index that is nonzero yet outside the registered set (e.g., `recipient = victim's own i`, since the victim never registers its own encryption key). Every honest node evaluating that accusation hits `self.enc_keys[&decryptor]` or `self.commitments[&sender]` and panics, aborting the key-generation/signing session — a denial of service mirroring the Squid assertion-failure/exit class, reachable purely through a crafted protocol message.

### Likelihood Explanation
Blame handling is a documented part of the protocol flow — accusations are meant to be processed by any party (note `AdditionalBlameMachine` explicitly supports non-participants evaluating blame). The `Participant` fields come from peer-supplied accusation data and are never validated against `params.n` or map membership before indexing. Triggering requires only sending one malformed accusation.

### Recommendation
Validate `sender` and `recipient` against the registered key/commitment sets at the top of `blame_internal` / `blame`, returning a defined error (or treating the accuser as faulty) instead of relying on `HashMap` `Index`. Replace `self.enc_keys[&decryptor]` in `decrypt_with_proof` with `.get(&decryptor)` returning `DecryptionError`, and similarly guard `self.commitments[&sender]`.

### Proof of Concept
```rust
// n-of-t DKG completed; honest node holds BlameMachine for params n, t, i.
// Malicious participant broadcasts an accusation with:
//   sender    = Participant::new(1)   // any valid participant
//   recipient = our own params.i()    // never registered in enc_keys
//   msg       = any EncryptedMessage with a valid PoP for sender's key
//             // or even an invalid-PoP msg won't help: PoP verify happens
//             // before indexing? No — enc_keys lookup happens at line 388
//             // only inside `if let Some(proof)`; an invalid signature
//             // returns early. So supply a valid-PoP message plus a proof
//             // to reach the indexing.
let (machine, faulty) = blame_machine.blame(sender, recipient, msg, Some(proof));
// -> thread panics at crypto/dkg/pedpop/src/encryption.rs:388
//    "no entry found for key" instead of returning blame for `sender`.
// Equivalently, sender = Participant::new(n + 1) with a structurally valid
// msg/proof panics at crypto/dkg/pedpop/src/lib.rs:599.
```

Note: the `msg` must carry a valid `pop` signature (trivially produced by the malicious sender for their own key) so that `decrypt_with_proof` proceeds past the `InvalidSignature` early return to the `enc_keys[&decryptor]` index, or past it to `commitments[&sender]` in `blame_internal`.
