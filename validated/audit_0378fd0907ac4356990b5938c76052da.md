## Analog identified: shared, unscoped trampoline token lets a repo-controlled subprocess "re-enter" the credential trampoline mid-operation and pull the real GitHub OAuth token

### Title
Unscoped, long-lived `DESKTOP_TRAMPOLINE_TOKEN` allows repo-controlled git subprocesses (filters/hooks/tools) to re-enter the trampoline server and exfiltrate GitHub credentials mid-operation - (File: `app/src/lib/trampoline/trampoline-tokens.ts`, `app/src/lib/trampoline/trampoline-server.ts`, `app/src/lib/trampoline/trampoline-environment.ts`)

### Summary
The ERC777 bug's core primitive is: an external call happens *before* the invariant (funds received == funds accounted) is closed, and the untrusted callee re-enters the same privileged entry point to draw more value than it should be entitled to from a shared pool. The Desktop analog is the trampoline credential system: for the whole duration of a git operation, Desktop opens a shared secret (`DESKTOP_TRAMPOLINE_TOKEN`) valid on a local TCP server, and hands it to the git process via environment variables. That token is accepted by the server for *any* registered trampoline command (askpass, SSH, and critically the git `credential` helper's `get`) with no binding to which subprocess or which remote host is allowed to use it. Any process that inherits the git process's environment during that operation - a hook, a `.gitattributes` filter/diff/merge/textconv command, a submodule update command, etc., all of which can be supplied by an attacker via a cloned/fetched repository - can independently open a socket to the trampoline server, present the still-valid token, and directly request the user's real GitHub OAuth credential (`git credential get` semantics) for `https://github.com`, before the top-level operation (and its token revocation) completes.

### Finding Description
- `withTrampolineToken` mints one token via `crypto.randomUUID()`, adds it to a global `Set`, and only revokes it in a `finally` after the *entire* enclosing git operation (`fn`) finishes: [1](#0-0) 
- `TrampolineServer.processCommand` authorizes any command solely by checking `isValidTrampolineToken(command.trampolineToken)` — there is no check of which process, which command identifier is expected next, or which remote/host the caller is allowed to query: [2](#0-1) 
- `withTrampolineEnv` injects `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` (plus `GIT_ASKPASS=''` and the credential-helper config) directly into the environment object used to spawn the git process for the operation: [3](#0-2) 
- The registered `get` handler for the credential-helper command returns the user's actual signed-in GitHub account credential when the target looks like a GitHub host: [4](#0-3)  and `findGitHubTrampolineAccount` matches purely by URL origin, with no verification that the request originated from the actual git transport talking to that origin: [5](#0-4) 
- The project's own hooks subsystem shows the team is aware that child processes must not see this sensitive environment: `hooks-proxy.ts` deliberately whitelists only `GIT_`/`GITHEAD_`-prefixed variables and explicitly excludes dangerous ones before spawning the actual hook script: [6](#0-5) , and explicitly excludes `GIT_ASKPASS`, `GIT_SSH_COMMAND`, etc.: [7](#0-6) . This filtering exists *only* for the intercepted-hooks path (`withHooksEnv`, gated by `opts?.interceptHooks` and a settings flag): [8](#0-7) . There is no equivalent allow-list/env-sanitization shown anywhere for other subprocesses that git itself spawns during the same operation (e.g. `.gitattributes` filter/clean/smudge/diff/merge/textconv drivers, or `.gitmodules` `update = !command`) — these inherit the full process environment, including `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`, by default the way Node's `child_process` and native `exec`/`spawn` propagate environment unless explicitly stripped.

The broken invariant: the trampoline token is meant to authorize exactly "the askpass/credential exchange that Git performs for *this* remote operation," but in practice it authorizes *any* trampoline command from *any* process that can read that one environment variable, for the entire lifetime of the operation. Just like the ERC777 re-entrant `createAuction` call let the attacker draw more from `SizeSealed`'s shared balance than it received, an attacker-supplied subprocess spawned mid-operation can re-enter the shared trampoline "pool" and draw a credential it was never meant to receive.

### Impact Explanation
If a repo-controlled hook or filter/tool command that git itself spawns during a clone/fetch/push/pull can read `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its environment, it can connect to the trampoline server itself and issue a `credential get` command for `https://github.com`, receiving back the signed-in user's real GitHub OAuth token/credential via `getGitHubCredential` — a full account credential exfiltration triggered purely by cloning/fetching a malicious repository, with no local access, no admin rights, and no pre-existing malware required. This matches the explicitly in-scope impact category: "credential/token exfiltration" from an attacker-controlled cloned/fetched repository.

### Likelihood Explanation
Confirmed from code: the token is a single shared secret with no per-command/per-origin scoping and a lifetime spanning the whole operation (`trampoline-tokens.ts`, `trampoline-server.ts`). Confirmed: the credential `get` handler will hand back the real GitHub credential for github.com-like origins regardless of caller identity (`trampoline-credential-helper.ts`, `find-account.ts`). What is **not directly confirmed** from the indexed code is the exact env-inheritance behavior of every non-hook subprocess git spawns (filter/diff/merge/textconv drivers, `.gitmodules` `update = !cmd`) — I could not locate the spawn/env-construction code for those specific mechanisms in this pass, only the fact that the hooks path required a dedicated, explicit filter (`hooks-proxy.ts` `safeEnv`) to strip these variables, which strongly suggests no other path in the codebase performs equivalent filtering. This should be verified directly against the git process spawn code path (`core.ts`) and Node's `child_process` defaults to fully confirm the propagation before treating this as certain, but the design gap (one global secret good for the whole operation, checked only by membership in a `Set`) is a real, code-confirmed weakness independent of that remaining question.

### Recommendation
- Scope trampoline tokens per remote-operation *and* bind each issued credential response to the specific command/channel that Git's own askpass/credential-helper invocation used (e.g., a single-use, per-request nonce rather than one reusable token good for the whole operation).
- Apply the same environment allow-list used in `hooks-proxy.ts` (`safeEnv`, `excludedEnvVars`) to every other place git spawns repository-influenced subprocesses (filter/clean/smudge/diff/merge/textconv drivers, submodule commands), stripping `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and `GIT_ASKPASS` before those subprocesses are executed.
- Revoke/rotate the trampoline token immediately after the specific askpass/credential exchange it was issued for completes, rather than holding it valid until the entire git operation finishes.

### Proof of Concept
Conceptual PoC (cannot be executed without the full Desktop app + git binary environment, so this documents the reachable path rather than a runnable exploit):
1. Attacker publishes a repository containing a `.gitattributes` filter (or a `pre-commit`/`post-checkout` hook, if hook interception is disabled, or a `.gitmodules` `update = !cmd`) whose command is: read `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` from its own process environment, open a TCP socket to `127.0.0.1:$DESKTOP_PORT`, and send a trampoline command frame requesting the `credential-helper get` operation for `url=https://github.com`.
2. Victim clones/fetches this repository in GitHub Desktop, triggering `withTrampolineEnv` (`app/src/lib/trampoline/trampoline-environment.ts`) to set `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` on the spawned git process for the duration of the clone/fetch.
3. Git spawns the attacker's filter/hook/submodule command as a child of that process; the attacker's command inherits the token before the operation (and thus `withTrampolineToken`'s revocation) completes.
4. The attacker's command sends the crafted command to `trampolineServer`, which validates only `isValidTrampolineToken` (`app/src/lib/trampoline/trampoline-server.ts:162-165`) and dispatches to `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential`, returning the victim's real GitHub account credential (`app/src/lib/trampoline/trampoline-credential-helper.ts:93-99`).
5. The attacker's command exfiltrates the returned credential over the network from within the same process.

  private async processCommand(socket: Socket, command: ITrampolineCommand) {
    if (!isValidTrampolineToken(command.trampolineToken)) {
      throw new Error('Tried to use invalid trampoline token')
    }

    const handler = this.commandHandlers.get(command.identifier)

    if (handler === undefined) {
      socket.end()
      return
    }

    const result = await handler(command).catch(e =>
      log.error('Error processing trampoline command', e)
    )

    if (result !== undefined) {
      socket.end(result)
    } else {
      socket.end()
    }
  }

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
