### Title
`update_finalized_payouts` binds one broadcast payout tx to two withdrawal indices sharing a UTXO, letting an operator be credited twice for a single payout - ([File: core/src/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` derives `(idx, payout_txid)` pairs from `Database::get_payout_txs_for_withdrawal_utxos`, which joins the `withdrawals` table to `bitcoin_syncer_spent_utxos` purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`. If two withdrawal rows (`idx1`, `idx2`) carry the same withdrawal UTXO, a single Bitcoin transaction spending that UTXO matches both rows, and `update_payout_txs_and_payer_operator_xonly_pk` writes the same `payout_txid`/`operator_xonly_pk`/`block_hash` into both rows. This makes `get_payout_info_from_move_txid` return a valid, fully-populated payout record for both deposits even though only one payout transaction was ever broadcast.

### Finding Description
The binding that must hold is: for a given withdrawal `idx`, `withdrawals.payout_txid` must equal the txid of a Bitcoin transaction that was actually broadcast to fund **that specific** withdrawal `idx`'s payout, and this must be true exactly once per broadcast payout transaction.

Trace:
- `withdrawals` has `PRIMARY KEY (idx)` only; there is no uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` [1](#0-0) . Two different `idx` rows can therefore be set to the identical Bitcoin UTXO via `update_withdrawal_utxo_from_citrea_withdrawal`, which is called per `idx` from Citrea-sourced withdrawal events with no dedup check against other idxs [2](#0-1) [3](#0-2) .
- `get_payout_txs_for_withdrawal_utxos` joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` solely on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, with no additional per-idx disambiguation [4](#0-3) . If `idx1` and `idx2` both point to the same UTXO, and that UTXO is spent once on-chain, this query returns two rows: `(idx1, payout_txid)` and `(idx2, payout_txid)` with the identical `payout_txid`.
- `Verifier::update_finalized_payouts` iterates `for (idx, payout_txid) in payout_txids`, decodes the OP_RETURN operator xonly pk from the (single) payout transaction for each matched row, and pushes `(idx, payout_txid, operator_xonly_pk, block_hash)` for both `idx1` and `idx2` into `payout_txs_and_payer_operator_idx` [5](#0-4) .
- `update_payout_txs_and_payer_operator_xonly_pk` performs a bulk `UPDATE ... FROM (VALUES ...) WHERE w.idx = c.idx`, so both `idx1` and `idx2` rows are updated with the same `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash` [6](#0-5) .
- Consequently `get_payout_info_from_move_txid` returns `Some((operator_xonly_pk, block_hash, payout_txid, idx))` for both deposits' `move_to_vault_txid` values, since it only checks `payout_txid IS NOT NULL AND payout_tx_blockhash IS NOT NULL` per row [7](#0-6) .
- This record is what drives operator reimbursement: `Operator::send_asserts` and `PayoutCheckerTask::run_once` call `get_payout_info_from_move_txid`/`get_first_unhandled_payout_by_operator_xonly_pk` per deposit and unconditionally proceed to `handle_finalized_payout` and kickoff creation as if a genuine payout had occurred for that specific deposit [8](#0-7) [9](#0-8) .

None of the standard guards intercept this: `is_deposit_valid`, `SPV::verify`, `verify_storage_proofs`, and the musig2/signature checks all validate deposit/withdrawal integrity or storage-proof correctness for a single `idx` in isolation; none of them cross-check that a payout UTXO/txid is not already attributed to a different withdrawal `idx`. There is also no database uniqueness constraint blocking two `idx` rows from sharing a `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair.

Exploit flow: an attacker withdraws twice from the Citrea bridge contract (as two separate withdrawal requests/indices for two different deposits), choosing the identical Bitcoin UTXO bytes as the `withdrawal_utxo` for both `withdrawal_id`s (attacker fully controls the withdrawal UTXO bytes per the threat model). Any operator later pays out that UTXO once (fulfilling withdrawal idx1 legitimately, fronting BTC once). The Bitcoin syncer records this single spend once in `bitcoin_syncer_spent_utxos`, but `get_payout_txs_for_withdrawal_utxos` reports it for both idx1 and idx2, and the verifier persists `payout_txid` for both rows.

### Impact Explanation
This breaks ATTRIBUTION: the withdrawal idx2, for which zero BTC was actually fronted, is marked as paid out by the operator with a valid `payout_txid`/`payout_tx_blockhash`/`operator_xonly_pk`. Downstream, `send_asserts`/`handle_finalized_payout`/kickoff creation treats idx2's deposit as reimbursable to the operator, so the operator can claim (via the presigned kickoff/reimbursement path) the reimbursement connector for a payout it never made, effectively spending idx2's move-to-vault vault UTXO's backing value without a matching fronted withdrawal. This is repeatable per pair of withdrawal indices sharing a UTXO and is not bound to a single operator or deposit — it scales with however many withdrawal indices an attacker points at the same UTXO. This matches the Critical category: "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
Preconditions: an attacker needs to (1) make two withdrawal calls on the Citrea Bridge contract with different `withdrawal_id`s but the same chosen withdrawal UTXO bytes, and (2) wait for any operator to pay out one of them on Bitcoin. Both are within the stated attacker capabilities (calling `withdraw`, choosing UTXO bytes). No verifier, operator, or aggregator privilege is required from the attacker; only an honest operator's routine payout is needed to trigger the double-attribution. This makes the bug low-cost and reliably reproducible, contingent on the described duplicate-withdrawal-UTXO registration being achievable at the Citrea-contract layer (assumed as given precondition per the question).

### Recommendation
Enforce a strict one-to-one mapping between a Bitcoin UTXO and a withdrawal index: add a uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (or reject/ignore subsequent registrations of an already-registered UTXO), and modify `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` to detect and error out (rather than silently duplicate) when more than one withdrawal `idx` maps to the same spent UTXO in a block.

async fn duplicate_withdrawal_utxo_causes_double_payout_attribution() {
    // 1. Set up DB, insert two deposits (idx1, idx2) with distinct move_to_vault_txid1/2.
    // 2. Call update_withdrawal_utxo_from_citrea_withdrawal for idx1 and idx2 with the SAME OutPoint (utxo).
    // 3. Spin up regtest bitcoind, broadcast+mine a single transaction spending `utxo` (the payout tx).
    // 4. Run the bitcoin syncer to ingest the block, populating bitcoin_syncer_spent_utxos once for `payout_txid`.
    // 5. Call Verifier::update_finalized_payouts (or directly db.get_payout_txs_for_withdrawal_utxos + 
    //    db.update_payout_txs_and_payer_operator_xonly_pk) for that block.
    // 6. Assert:
    let info1 = db.get_payout_info_from_move_txid(None, move_to_vault_txid1).await.unwrap();
    let info2 = db.get_payout_info_from_move_txid(None, move_to_vault_txid2).await.unwrap();
    assert!(info1.is_some());
    assert!(info2.is_some()); // BUG: both deposits show a valid payout, but only one payout tx was broadcast
    assert_eq!(info1.unwrap().2, info2.unwrap().2); // same payout_txid attributed to both idx1 and idx2
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
