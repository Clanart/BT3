### Title
Inaccurate hardcoded slippage protection in `SmartWomConvert.smartConvert` enables sandwich attack on WOM→mWOM fee conversion - ([File: wombat/SmartWomConvert.sol])

### Summary
`SmartWomConvert.smartConvert()` sets the minimum-amount-out for a WOM→mWOM AMM swap to a naive floor equal to the raw input amount, instead of a value derived from the actual expected market rate. This is the same bug class as the reported Alchemix `RevenueHandler._melt` finding: the code assumes a favorable, roughly-1:1-or-better exchange rate will always hold and enforces only that floor, leaving the entire "healthy spread" between the naive floor and the true fair-market output exposed to a sandwich attacker.

### Finding Description
`smartConvert` is documented as being used by `WombatStaking` when routing WOM fee rewards into mWOM: [1](#0-0) 

It forwards `_amountIn` itself as `_minRec` into `_convertFor`, instead of computing an expected output with a real slippage tolerance (e.g. via `estimateTotalConversion`, which already exists in the same contract for this exact purpose): [2](#0-1) 

Inside `_convertFor`, the portion of WOM routed to the AMM (`womMWomPool`) is swapped with **zero** slippage protection at the router level (`swapExactTokensForTokens(..., 0, ...)`), and the only backstop is the coarse aggregate check `convertAmount + amountRec < _minRec`: [3](#0-2) 

Because `womMWomPool`-routed conversion exists specifically to capture the mWOM discount relative to WOM (the direct `deposit` path already gives a strict 1:1 mint, so the AMM path is only used when it can do better), under normal market conditions `convertAmount + amountRec` is expected to be *meaningfully greater* than `_amountIn`. That spread is exactly what a sandwich attacker can extract: front-run the harvest transaction to push the pool price against the contract's swap, let the transaction pass (it still clears the naive `_minRec == _amountIn` floor), then back-run to restore the price and pocket the difference between the true fair-value output and the naive floor. This mirrors precisely the root cause identified in the Alchemix report — a "minimumAmountOut == inputAmount" heuristic substituting for real slippage protection based on price feeds/expected value.

### Impact Explanation
This code path is reached whenever WOM protocol fees are distributed, e.g. via `WombatStaking._sendRewards`, called from `WombatStaking.harvest()` — a function callable by any unprivileged wallet — whenever an mWOM fee is configured and `smartWomConverter` is set: [4](#0-3) [5](#0-4) 

The mWOM output of this conversion is queued as reward yield to `BaseRewardPool` via `queueNewRewards`, so value siphoned off by the sandwich directly reduces yield ultimately claimable by stakers — i.e., theft of unclaimed yield, reachable purely by an ordinary wallet triggering `harvest()` at a time favorable to the attacker (no privileged role needed).

### Likelihood Explanation
Any unprivileged address can call `WombatStaking.harvest()` at will, and sandwiching an on-chain AMM swap with a known, weak floor is a standard MEV technique requiring no special access — likelihood is high whenever the mWOM/WOM pool has meaningful liquidity depth manipulable within a block.

### Recommendation
Replace the hardcoded `_minRec = _amountIn` in `smartConvert` with a minimum output computed from the pool's actual expected rate (e.g., using `estimateTotalConversion` or an on-chain oracle-based expected value) minus an explicit, configurable slippage tolerance, and pass a non-zero `amountOutMin` into the underlying `swapExactTokensForTokens` call rather than `0`.

### Proof of Concept
1. Admin configures a WOM fee with `isMWOM = true` and sets `smartWomConverter` on `WombatStaking`, with `womMWomPool` having typical liquidity such that mWOM trades at a discount to WOM (`currentRatio()` reasonably below 10000/DENOMINATOR, i.e., mWOM cheaper).
2. An unprivileged user calls `WombatStaking.harvest(lpToken)` (or any deposit/withdraw path that triggers `_toMasterWomAndSendReward`/`_sendRewards`) which internally calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`.
3. Before this transaction is mined, an attacker front-runs by swapping WOM into `womMWomPool` to depress the mWOM output rate, letting the victim's swap (internally protected only by `amountOutMin = 0`) execute at the manipulated rate.
4. The aggregate check `convertAmount + amountRec < _minRec` in `_convertFor` still passes because `_minRec` is only `feeAmount` (input amount) rather than the true expected discounted-rate output — the naive floor does not reflect the real fair value that should have been received.
5. Attacker back-runs to restore the pool price and captures the spread between the true fair-value mWOM output and the naive `_minRec` floor, at the expense of the mWOM ultimately queued to `BaseRewardPool` for stakers. [6](#0-5) [7](#0-6)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
