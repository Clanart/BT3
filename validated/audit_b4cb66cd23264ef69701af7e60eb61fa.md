### Title
Crafted FROST nonce commitments force aggregate nonce `R` to the point at infinity, panicking BIP-340 `Hram`/`x` during signing - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The analog of CVE-2019-1787 is not a memory-unsafe OOB read (Serai's deserializers are safe Rust over `io::Read`), but the same bug class mapped onto Serai's real shape: **untrusted, attacker-controlled bytes (a FROST `Preprocess` nonce commitment) deterministically drive the signing code into a crash**. In `networks/bitcoin/src/crypto.rs`, the BIP-340 `Hram::hram` calls `x(R)`, which executes `.expect("point at infinity")` and `XOnlyPublicKey::from_slice(...).expect(...)` on the aggregate nonce point `R`. `R` is the sum of every participant's nonce commitment, all of which arrive as raw `read_G`-parsed points via `SignMachine::read_preprocess` / `Commitments::read` in `crypto/frost/src/sign.rs`. A malicious (or even a single rushing) participant can choose their commitment so the aggregate `R` is the point at infinity — e.g. submitting commitment `C = -(Σ other commitments)` after observing the other preprocesses, or supplying an identity commitment if `read_G` accepts it. No per-participant check can prevent *aggregate* cancellation, since each individual commitment remains a valid, non-identity curve point. When `sign`/`verify` later computes the challenge, `x(R)` panics, crashing the signing process.

### Finding Description
- `fn x(key: &ProjectivePoint) -> [u8; 32]` in `networks/bitcoin/src/crypto.rs` (lines 13–16) does `key.to_encoded_point(true).x().expect("point at infinity")`, and `x_only` (lines 21–23) re-panics via `expect`. These are reachable from `Hram::hram` (lines 59–73) which hashes `x(R)` and `x(A)`.
- `R` is derived from `nonce_sums`, i.e. the sum of `Preprocess.commitments` points supplied by all co-signers. Those points are deserialized from untrusted bytes via `AlgorithmSignMachine::read_preprocess` → `Commitments::read` (`crypto/frost/src/sign.rs` lines 276–281), with no check that the *aggregate* nonce is non-identity. Per-commitment identity checks (if present in `sign`) cannot help: the attacker's own commitment is a valid non-identity point chosen to cancel the honest sum.
- The file itself documents the gap: the `Schnorr` doc comment (lines 78–83) claims panic has "a negligible probability... even with malicious participants present" — true only for random failure, not for an adversary who algebraically forces `R` to infinity.
- The same `R` (post-negation via `needs_negation(&sig.R)` in `verify`, lines 145–149) is again fed to `to_encoded_point`, so both share-generation and completion paths panic.

### Impact Explanation
Any unprivileged party whose preprocess/commitment bytes are fed into a Bitcoin-network FROST signing session (a co-signer in the validator set, or anyone who can inject/gossip a preprocess message) can deterministically panic every honest signer that consumes it. This is a remote, input-triggered denial of service against the threshold-signing process — halting Bitcoin multisig signing/cosigning — the direct analog of ClamAV crashing on a crafted PDF. In a deployment where the process aborts on panic (e.g. the relayer installs a panic hook that `exit(1)`s, `networks/ethereum/relayer/src/main.rs` lines 12–19), a single malicious preprocess takes the node offline.

### Likelihood Explanation
Medium-to-high: the attacker only needs their serialized preprocess bytes routed into `read_preprocess`/`sign`, which is exactly the untrusted-input path Serai exposes for FROST. The attack requires being a protocol participant able to submit a preprocess and (for the cancellation variant) observing other preprocesses first — a standard rushing-adversary assumption in multisig protocols. No secret knowledge, collusion, or leaked keys are needed. Impact is DoS-only (crash), not key recovery, which caps severity at Medium.

### Recommendation
- Reject the point at infinity both per-commitment in `Commitments::read`/`sign` **and** for the aggregate `R` before calling `hram`. Return a `FrostError`/`io::Error` instead of panicking.
- Replace `x`'s/`x_only`'s `expect` calls with `Option`/`Result`-returning variants and propagate failure through `HramTrait`, `sign_share`, and `verify` so malicious input is a blamed `InvalidPreprocess(l)`/`InvalidShare(l)` rather than a panic.
- Reorder/commit the preprocess exchange (commit-then-reveal on nonce commitments) so a rushing signer cannot compute a cancelling commitment after seeing honest preprocesses.

### Proof of Concept
1. Honest signers broadcast preprocesses with nonce commitments `D_i, E_i`. Attacker `j` waits, computes `C = -(Σ_{i≠j} D_i + Σ_{i≠j} E_i)` over the two-generator set (per-generator: `C_k = -(Σ_{i≠j} commitment_{i,k})`), and submits `C` as their serialized preprocess — a valid non-identity `ProjectivePoint` encoding that passes `read_G` and any per-commitment identity check.
2. In `sign`, the nonce sum `R_generator = Σ commitments` equals the identity. `sign_share`/`verify` invoke `Hram::hram(&R_agg, &group_key, msg)` → `x(&R_agg)` → `to_encoded_point(true).x().expect("point at infinity")` → panic.
3. Every honest signer processing that preprocess set crashes identically; the signing session cannot complete, and with a panic-aborting runtime the node exits. A PoC is two signers plus the attacker in an `AlgorithmSignMachine<Schnorr>` session where the attacker's preprocess encodes `-(D_1 + D_2)`/`-(E_1 + E_2)`; `machine.sign(preprocesses, msg)` panics in `x` rather than returning `Err(FrostError::InvalidPreprocess(_))`.

Note: I verified the panic sites in `networks/bitcoin/src/crypto.rs` and the untrusted deserialization path in `crypto/frost/src/sign.rs`; I could not fully confirm whether `Secp256k1::read_G` or `sign` rejects per-commitment identity points, but that does not affect the finding — the aggregate-cancellation variant works regardless of per-point validation.
