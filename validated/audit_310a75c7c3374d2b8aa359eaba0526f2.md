## #Vulnerability found

### Title
Future-dated oracle timestamps are treated as unconditionally fresh, bypassing staleness protection - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`oracle-timestamp-fresh` computes the staleness delta as `u0` whenever the reported publish timestamp is greater than `stacks-block-time`, instead of computing (or bounding) how far ahead the timestamp is. Because `delta = u0` always satisfies `<= delta max-staleness`, any price whose timestamp is ahead of the chain's current block time is accepted as "fresh" no matter how far in the future it is, and it stays "fresh" for as long as `stacks-block-time` has not caught up to it. [1](#0-0) 

### Finding Description
`price-resolve` gates every price used by the market on `oracle-price-legal` and `oracle-timestamp-fresh`: [2](#0-1) 

`oracle-timestamp-fresh` is defined as:
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 

The branch handling `ts > stacks-block-time` (a publish timestamp ahead of the current chain time) collapses `delta` to `u0` unconditionally, instead of computing the actual forward distance (`ts - stacks-block-time`) and validating it against a bound. This is the same class of defect as the referenced Zebra fix: an "ahead" case that should be explicitly scored/handled is instead left effectively unchecked (a free pass), while only the "behind" (stale) case is scored against `max-staleness`. The monotonicity check `(>= ts prev)` still holds, so once a price with a future `ts` is written via `price-resolve`'s `map-set last-update`, every subsequent read for that feed keeps `delta = u0` (still fresh) until real block time finally catches up to that future timestamp — which, depending on how far ahead `ts` is, can be an arbitrarily long window during which the price can no longer be refreshed to reflect real market movement, yet is always reported as "fresh" and used for collateral/debt valuation in `get-asset-value` and `get-notional-evaluation`.

This is a logic defect in Zest's own oracle-freshness gating code (`market.clar`/`v0-4-market.clar`), independent of whether the oracle relayer's data is itself correct at submission time — the flaw is in how the market interprets and bounds a future-dated timestamp, exactly mirroring the "which arm gets scored vs. left unscored" defect pattern in the report.

### Impact Explanation
If a price feed update is ever recorded with a publish time ahead of `stacks-block-time` (e.g., due to relayer/publisher clock skew, or a burst of price submissions where publish-time briefly outruns Stacks block time), that price becomes pinned as permanently "fresh" for the affected asset until block time advances past it. Positions using that asset for collateral or debt valuation will be priced off a value that can no longer be legitimately superseded within the intended `max-staleness` window, letting borrowers over-borrow against stale/favorable prices or evade liquidation, or letting liquidators under/over-value collateral — a direct pricing/health-verdict error that can lead to theft of funds or protocol insolvency.

### Likelihood Explanation
This requires only a future-leaning `publish-time` relative to `stacks-block-time` to reach the market, not a compromised oracle; ordinary clock/latency skew between chain block time and oracle publish time can plausibly trigger the `ts > stacks-block-time` branch. Once triggered, exploitation of the frozen "fresh" state (borrowing, avoiding liquidation) does not require further special conditions.

### Recommendation
Compute `delta` symmetrically for the "ahead" case (e.g., `ts - stacks-block-time`) and bound it against a defined tolerance (or reject/clamp), rather than forcing `delta = u0` unconditionally whenever `ts > stacks-block-time`.

### Proof of Concept
1. Submit a Pyth (or DIA) price update whose `publish-time`/`timestamp` is set slightly ahead of the current `stacks-block-time` (within what upstream `pyth-storage-v4`/DIA permits).
2. `price-resolve` calls `oracle-timestamp-fresh` with `ts > stacks-block-time`, so `delta = u0`, `<= max-staleness` trivially holds, and `map-set last-update key timestamp` records the future `ts`.
3. Until real `stacks-block-time` advances past that recorded `ts`, every later call to `oracle-timestamp-fresh` for that feed again finds `ts > stacks-block-time` (or, once caught up, satisfies `>= ts prev` trivially) and returns fresh, even though the true price may have since diverged materially.
4. A borrower can use the frozen/stale-but-"fresh" price to maximize borrow capacity or to keep a position appearing healthy through `is-healthy`/`get-notional-evaluation`, avoiding liquidation despite real-market price moves.
