### Title
Unvalidated Reward Token Sweep in `ManualCompound.compound()` Allows Draining Contract's Full Token Balance - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` lets any wallet supply arbitrary `_lps` and `_rewards` arrays that are not validated against the tokens actually earned/claimed by the caller. The function then transfers the **entire current balance** of any `_rewards[i][j]` token held by the `ManualCompound` contract to `msg.sender` whenever that token is not in the `compoundableRewards` allow-list, rather than only the amount freshly received from the claim in that call.

### Finding Description
`ManualCompound.compound()` forwards the caller-supplied `_lps`/`_rewards` arrays straight to `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`: [1](#0-0) 

Critically, the `_rewardTokens` argument that reaches `BaseRewardPool.getReward()` is never actually used to decide what gets paid out — `getReward()` ignores its `_rewardTokens`-style filtering and simply iterates over the pool's own internally-registered `rewardTokens` array: [2](#0-1) 
(and the sibling `getRewards()` override is an empty stub) [3](#0-2) 

This means the `_rewards` array a caller passes into `compound()` has no verified relationship to what was actually claimed for the `_lps` pools specified. Back in `ManualCompound.compound()`, any `_rewards[i][j]` token that isn't registered as `compoundableRewards[token]` (only tokens explicitly whitelisted via the owner's `addReward()`) is swept using `IERC20(_rewards[i][j]).balanceOf(address(this))` — i.e. the contract's total current balance of that token — and sent wholesale to `msg.sender`: [4](#0-3) 

The same balance-based (not delta-based) sweep pattern is repeated for the registered "compoundable" reward tokens at the end of the function: [5](#0-4) 

`ManualCompound` is a shared, non-`nonReentrant`-protected contract (no `ReentrancyGuard` is used anywhere in the file) that accumulates reward tokens from claims made on behalf of many different users. Because the payout in the first loop is (a) keyed on an attacker-chosen token address rather than a verified claimed amount, and (b) computed from the live `balanceOf(address(this))` rather than a per-call delta, any ERC20 balance that happens to be sitting in the contract (residual/dust from prior claims, tokens belonging to other users mid-flow, or tokens routed there for reasons unrelated to the caller's own stake) can be swept to an unprivileged caller who supplies a matching, arbitrary `_lps`/`_rewards` pairing — even for pools/tokens they have zero stake in.

This is analogous in root cause to the CowSwap `SwapGuard.envelope()` exploit: an unprivileged caller supplies attacker-controlled parameters (there: arbitrary `target`/`calldata`; here: arbitrary `_rewards` token addresses paired with unrelated `_lps`) that are executed/trusted by a privileged contract without validating they correspond to the caller's actual authorized action, resulting in transfer of funds the caller does not own.

### Impact Explanation
Any ERC20 token balance temporarily held by `ManualCompound` — including reward tokens belonging to other users that have not yet completed their compound flow, or leftover balances from rounding/partial-consumption in `convertFor`/`depositFor`/`lockFor` — can be swept to an arbitrary caller by pairing an unrelated staking pool with the target token address, since the code performs no check tying claimed amount to swept amount or tying `_rewards[i][j]` to tokens actually earned by `msg.sender` for `_lps[i]`. This constitutes direct theft of unclaimed yield belonging to other users.

### Likelihood Explanation
No special privilege is required — any wallet can call `compound()` with self-chosen `_lps`/`_rewards` arrays. The only precondition is that the target token has a nonzero balance sitting in `ManualCompound` at the time of the call, which can occur from normal contract operation (rounding remainders from `_provisionReward`/`convertFor`, or timing of multiple users' claims routed through the shared contract).

### Recommendation
Track exact amounts received per token within each `compound()` call (delta = balance-before vs. balance-after the `multiclaimOnBehalf` call) instead of sweeping the full live `balanceOf(address(this))`. Additionally, validate that `_rewards[i][j]` entries actually correspond to registered reward tokens of the corresponding `_lps[i]` pool (e.g., by cross-checking against `IBaseRewardPool(rewarder).rewardTokenInfos()`), and add reentrancy protection (`nonReentrant`) to `compound()` given its multiple external calls to converters/lockers/helpers.

### Proof of Concept
1. Attacker identifies any ERC20 token `X` currently held (even a small dust amount) by the `ManualCompound` contract, where `X` is not in `compoundableRewards`.
2. Attacker calls `compound(_lps, _rewards, 0, 0, false)` where `_lps = [anyRegisteredStakingToken]` (attacker need not have any stake in it — `claimableMgp` will simply be 0) and `_rewards = [[X]]`.
3. `multiclaimOnBehalf` executes with attacker's zero-stake claim (no legitimate reward yielded for `X`), per `_multiClaim`/`_claimBaseRewarder` logic reachable via `BaseRewardPool.getReward()` which ignores the reward-token argument.
4. Back in `compound()`, since `compoundableRewards[X] == false`, the code executes `IERC20(X).balanceOf(address(this))` and transfers the *entire* balance to `msg.sender` — [6](#0-5)  — regardless of the fact the attacker earned none of it.

        uint256 rewardTokensLength = rewards.length;        
        IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
        // send none compoundable reward back to caller
        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
