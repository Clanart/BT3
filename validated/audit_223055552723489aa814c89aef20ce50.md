I'll examine the bitcoin signing path and FROST preprocess handling for the "same input processed multiple times" pattern.### Title
`Scanner::scan_block` credits immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates `block.txdata` in full — including `block.txdata[0]`, the coinbase transaction — and emits a `ReceivedOutput` for any coinbase output paying to a registered script. Coinbase outputs are bound by Bitcoin's 100-block maturity rule and cannot be spent. Any miner can therefore cause the scanner to report "received" balance that is not spendable, the wallet-level analog of Derby's `xChainController` processing a vault that should not have been paid.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for every tx output whose `script_pubkey` matches a registered script [1](#0-0) . `Scanner::scan_block` calls it for **all** transactions, including the coinbase, and only documents — not enforces — the maturity hazard:

> "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed to remove those outputs." [2](#0-1) 

There is no flag on `ReceivedOutput` marking it as immature, and the API happily produces inputs for `SignableTransaction::new` [3](#0-2) . Serai's own processor had to special-case this by slicing `block.txdata[1 ..]` to skip the coinbase [4](#0-3) , proving the default behavior is unsafe. A transaction spending an immature coinbase prevout is consensus-invalid, so `SighashCache::taproot_key_spend_signature_hash` still produces a signature, the witness is assembled normally, and only `publish_completion` fails at broadcast [5](#0-4) .

Like the Derby bug, the root cause is a missing gate: a code path processes (credits) something it should skip, and the protocol layer is left with funds it cannot move.

### Impact Explanation
An unprivileged miner (or merged-mining pool) can craft a coinbase paying P2TR to the multisig's external/offset script. `scan_block` reports it as a normal `ReceivedOutput`, so the credited balance is unsatisfiable for 100 blocks — "funds reported received that are not spendable." If integrators select it as an input, the resulting signed transaction is invalid at broadcast, stalling signing plans and potentially triggering repeated rebroadcast/fee-escalation attempts for an output that can never be spent in that window. Repeated coinbase deposits inflate apparent balance while forcing invalid transactions.

### Likelihood Explanation
Any miner can include an arbitrary P2TR output to the scanner's key in their coinbase at negligible cost (they forgo nothing by paying the protocol instead of themselves). No collusion, leaked key, or malicious peer is needed — just a standard block template. Deterministic triggering whenever the attacker's block lands in the scanned range.

### Recommendation
- Skip `block.txdata[0]` inside `Scanner::scan_block`, matching the processor's `txdata[1 ..]` behavior, or
- tag `ReceivedOutput` with an `immature` flag derived from coinbase membership (e.g., pass `is_coinbase` into `scan_transaction`) so callers can exclude it, and
- add a regression test that `scan_block` on a coinbase paying a registered script returns no spendable output (or a flagged one).

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
