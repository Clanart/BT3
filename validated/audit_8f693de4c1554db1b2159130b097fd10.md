The user's withdrawal signature is enforced by `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-187`) to use `TapSighashType::SinglePlusAnyoneCanPay`. Per BIP341, `SIGHASH_SINGLE|ANYONECANPAY` on a key-spend input commits only to input 0 (the signer's own input and its corresponding output index 0), and explicitly does **not** commit to any other outputs, including output 2 (the OP_RETURN). This is confirmed in `calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`), which uses `Prevouts::One` for this sighash type — meaning only input 0's prevout is committed, and (per Taproot sighash rules for `SINGLE|ANYONECANPAY`) only output 0 is committed to the signature.

### Title
Attacker can rewrite the Payout tx's OP_RETURN (unbound by SinglePlusAnyoneCanPay sighash) to erase operator attribution and get the honest fronting operator falsely flagged malicious - (File: core/src/verifier.rs)

### Summary
The Payout transaction's user signature uses `SIGHASH_SINGLE|ANYONECANPAY`, which per BIP341 commits only to input 0 and output 0, leaving output 2 (the operator-identifying OP_RETURN) completely unauthenticated. An attacker (the withdrawing user themselves, or anyone with the broadcast signature since it's public once observed in mempool) can rebroadcast a competing/replacement transaction with the same input 0, same signature, same output 0, but a corrupted OP_RETURN (wrong push length) in output 2, causing `parse_op_return_data` to fail in `update_finalized_payouts` and the DB column to become `NULL`.

### Finding Description
Binding claimed broken: `operator_xonly_pk` stored in DB for withdrawal `i` (via `update_payout_txs_and_payer_operator_xonly_pk`, read back by `get_payout_info_from_move_txid`) == `signer.xonly_public_key` of the operator who actually funded output 0 of the Payout tx for withdrawal `i`.

Code path:
1. `Operator::withdraw` (`core/src/operator.rs:560-637`) builds the Payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), with output 2 = `op_return_txout(operator_xonly_pk.serialize())`, and verifies the user's `SinglePlusAnyoneCanPay` signature against `calculate_sighash_txin(0, ...)` — which per `calculate_pubkey_spend_sighash` only binds input 0 and output 0.
2. Because output 2 is unauthenticated by the signature, anyone in possession of the signed input 0 witness (visible once the operator's tx is broadcast/in mempool, or supplied by the withdrawing user who created the signature) can construct an alternate transaction with identical input 0 (same witness/signature) and output 0, but a mutated output 2 OP_RETURN with an invalid push length (e.g., 31 or 33 bytes instead of 32), and get it mined instead of (or racing with) the operator's original broadcast.
3. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the mined tx's OP_RETURN via `parse_op_return_data` + `XOnlyPublicKey::from_slice`; a malformed push length makes this `None`, and `operator_xonly_pk` is stored as `NULL` in `withdrawals.payout_payer_operator_xonly_pk`.
4. Later, when the honest operator sends its Kickoff to claim reimbursement, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) reads `operator_xonly_pk_opt = None` and hits the `else` branch at line 1882-1885, unconditionally returning `Ok(true)` — flagging the true, honest operator as malicious, triggering a Challenge against them (`handle_kickoff`, `core/src/verifier.rs:1966-2026`).

No existing guard prevents this: `parse_withdrawal_sig_params` only enforces the sighash *type*, not that the signature also commits to all outputs; the protocol intentionally uses `SinglePlusAnyoneCanPay` so operators can freely set fees/add inputs, but this also frees the OP_RETURN output from any commitment. `update_finalized_payouts`'s own comment (`core/src/verifier.rs:2316-2318`) explicitly acknowledges `None` can arise from "operator constructed the payout tx wrong" but does not anticipate a third-party mutating a previously-broadcast, still-unconfirmed transaction's non-committed output before it confirms.

### Impact Explanation
The honest operator that fronted the withdrawal is disprovable/challenged (Critical: "an honest operator permanently unable to be reimbursed" and/or the operator's collateral being burned upon a successful challenge/disprove flow, since `is_kickoff_malicious` returning `true` triggers Challenge tx and puts the honest operator into the adversarial BitVM disprove path they did not prepare for, or leads to permanent inability to complete Reimburse if disprove succeeds unjustly). This is repeatable per withdrawal for any operator, since it only requires racing the still-unconfirmed Payout tx broadcast with a malleated variant before the honest one confirms.

### Likelihood Explanation
Preconditions: the operator must have broadcast (not yet confirmed) the Payout tx, and the attacker must observe this in the mempool (trivial, public) or be the withdrawing user themselves (who already knows the signature since they produced it) and race a malleated copy into confirmation first. Cost is one transaction fee (must outbid/replace or win the confirmation race — feasible via higher fee or RBF since operator's fee rate is public/estimable). No privileged access, no key compromise required — purely leveraging that `SIGHASH_SINGLE|ANYONECANPAY` leaves output 2 unauthenticated. This is a standard "sighash malleability" issue in Bitcoin transaction design and is directly reachable by an unprivileged actor.

### Recommendation
Do not rely on an unauthenticated output for operator attribution. Options: (a) require the user's payout signature to use `SIGHASH_ALL` (or `AllPlusAnyoneCanPay`) so all outputs, including the OP_RETURN, are committed and cannot be altered without invalidating the signature; or (b) derive operator attribution from a source not spendable/malleable by third parties, e.g., verify the payout via matching the exact previously-fully-signed and previously-broadcast transaction (raw tx bytes matching what the operator's `tx_sender` submitted) rather than re-deriving from mined tx contents; or (c) if the sighash type must remain `SinglePlusAnyoneCanPay` for fee flexibility, restrict the OP_RETURN attribution check to require it be embedded within the covered output (e.g., pack the operator pubkey commitment into output 0 or into a script covered by SIGHASH_SINGLE) so it cannot be altered independent of the signed output.
