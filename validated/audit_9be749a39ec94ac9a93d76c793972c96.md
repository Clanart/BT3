## Title
Explicit disabling of Git's CVE-2024-32002 clone protection during recursive clones enables RCE via malicious submodules - (File: app/src/lib/git/clone.ts)

## Summary
GitHub Desktop's `clone()` function force-sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` on every `git clone --recursive` invocation. This is the exact guard Git itself introduced to fix CVE-2024-32002 (a critical RCE where a malicious repository containing crafted submodules could write into `.git/hooks` on case-insensitive or Unicode-normalizing filesystems during a recursive clone, resulting in hook execution). By explicitly forcing this variable off, Desktop reintroduces the vulnerability class that upstream Git deliberately closed, for every clone (including "Clone repository" via URL or GitHub API) that uses `--recursive`.

## Finding Description
Git added an internal env-based guard, `GIT_CLONE_PROTECTION_ACTIVE`, as part of the fix for CVE-2024-32002. When a `git clone` operation recursively initializes submodules, Git needs to know it's still within the "initial untrusted clone" context so it can apply stricter checks against submodule paths that could collide with `.git` on case-insensitive/normalizing filesystems (the vector that let a malicious repo plant files like hooks outside the intended worktree).

which unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and is passed to `git ... clone --recursive -- url path`: [2](#0-1) [3](#0-2) 

This mirrors the Tortuga bug pattern exactly: a security invariant (minimum-delegation / here, clone-time submodule path protection) is properly enforced by the underlying system by default, but a specific caller (direct-delegation withdraw / here, Desktop's recursive-clone code path) explicitly disables the very check that should apply, because that code path assumes it doesn't need the guard. Just as `certify_delegation`'s minimum check wasn't mirrored on withdrawal, Git's clone-time hardening isn't allowed to remain active here — it's forcibly turned off before the untrusted repository content (including its `.gitmodules` and submodule trees) is ever processed.

Separately, the codebase does implement a similar guard correctly elsewhere: `updateSubmodulesAfterOperation` conditionally allows `protocol.file.allow=always` only when explicitly requested via `allowFileProtocol`, showing the team is aware that submodule-related protections must not be blanket-disabled: [4](#0-3) 
This makes the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in `clone.ts` an outlier/regression relative to the pattern used elsewhere in the same module.

## Impact Explanation
An attacker who controls a repository that a user clones with GitHub Desktop's clone flow (Clone dialog by URL, or picking any repository from the GitHub API listing) can craft submodule entries that abuse case-insensitive or Unicode-normalizing filesystem behavior (default on macOS and common on Windows) to write into `.git/hooks` or otherwise escape the intended checkout location during the automatic `--recursive` submodule initialization. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, the check Git added specifically to block this is disabled for the whole operation, which can lead to arbitrary code execution the moment the clone/submodule-update completes (e.g., via an auto-run hook), satisfying the "attacker controls a cloned/fetched repository ... result is code execution" impact category.

## Likelihood Explanation
This triggers on the default/most common Desktop workflow — cloning any repository — since `clone()` always passes `--recursive` and always sets the disabling env var, with no opt-in/opt-out and no user interaction beyond initiating a normal clone of a repository they were led to (e.g., via a malicious org/repo link, a phishing invite, or a public poisoned repo). No local access, admin rights, or prior compromise is required; the only requirement is that the user clones an attacker-controlled repository, which is squarely within Desktop's threat model for untrusted content.

## Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or set it to `'true'`/leave it unset) so Git's own CVE-2024-32002 clone-time submodule path protections remain active during `git clone --recursive`. If the override was added to work around an unrelated failure, gate it narrowly and only for trusted/local sources, following the same opt-in pattern already used for `protocol.file.allow` in `updateSubmodulesAfterOperation`.

## Proof of Concept
1. Attacker publishes a repository with a `.gitmodules` file and a submodule whose path is engineered to collide with `.git`/`.git/hooks` under case-insensitive or Unicode-normalization rules (the same technique used in the original CVE-2024-32002 exploit).
2. Victim uses GitHub Desktop's "Clone repository" (URL or from the GitHub API list) to clone the attacker's repository.
3. `clone()` in [5](#0-4)  runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` set, disabling Git's protective path checks for the recursive submodule checkout.
4. During submodule checkout, the crafted paths escape into `.git/hooks` (or another sensitive location within `.git`), planting an executable hook.
5. That hook (e.g., `post-checkout`) is invoked automatically by Git as part of the same clone/checkout sequence, executing attacker-controlled code on the victim's machine.

```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
```
