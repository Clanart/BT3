## Analog Found

### Title
Nil-pointer dereference in legacy EVM precompile error handling due to missing `GetDBImpl` sanity check - (File: `precompiles/common/legacy/v600/precompiles.go`)

### Summary
Multiple versioned/legacy precompile implementations (`v562`, `v575`, `v580`, `v600`, `v605`, `v606`, `v610`) call `state.GetDBImpl(evm.StateDB)` a second time inside `HandlePrecompileError` without re-checking for `nil`, even though the same file's `Prepare` function explicitly anticipates and guards against `GetDBImpl` returning `nil`. This is the same bug class as CVE-2025-21901: a callback path is invoked without validating that a previously-nullable object handle is still valid, producing a guaranteed nil-pointer dereference when that precondition is hit.

### Finding Description
`Prepare` on the legacy `Precompile` type explicitly handles the case where `state.GetDBImpl(evm.StateDB)` returns `nil`: [1](#0-0) 

But `Run`/`RunAndCalculateGas` unconditionally defer `HandlePrecompileError(err, evm, operation)` regardless of which step produced the error, including the "cannot get context from EVM" error from `Prepare`: [2](#0-1) 

`HandlePrecompileError` in these legacy versions then calls `state.GetDBImpl(evm.StateDB)` again — on the exact same `evm.StateDB` that just yielded `nil` in `Prepare` — and immediately dereferences the result without a nil check: [3](#0-2) 

This is a deterministic reproduction of the nil-dereference bug class: whenever `Prepare` legitimately returns the "cannot get context from EVM" error (i.e. `evm.StateDB` does not satisfy the `*state.DBImpl` type assertion performed by `GetDBImpl`), the deferred error handler re-derives the same nil value and calls `.SetPrecompileError(err)` on it, causing a panic. The later (fixed) precompile versions closed this gap: [4](#0-3) 

confirming the maintainers recognized `GetDBImpl` could legitimately return `nil` in this call site and needed the same guard as `Prepare`, exactly mirroring the "add sanity checks on validity" fix pattern in the CVE.

### Impact Explanation
An unrecovered panic in precompile execution crashes the goroutine processing the EVM call. Precompiles versioned to historic heights (`v562`–`v610`) are reachable whenever the node re-executes or traces a historical block/transaction at those heights, as documented: "Precompiles are versioned by block height, allowing tracer functionality at historical heights" [5](#0-4) . Public JSON-RPC clients can request historical trace/replay execution, and if the `evm.StateDB` supplied for such execution does not satisfy the `x/evm/state.DBImpl` type assertion, this crash path is guaranteed to trigger (not merely conditionally), directly threatening default-configuration RPC node availability.

### Likelihood Explanation
The vulnerable code is confirmed present and unguarded in seven legacy precompile package copies (`v562`, `v575`, `v580`, `v600`, `v605`, `v606`, `v610`), and the fix pattern applied starting at `v614` confirms the maintainers themselves identified `GetDBImpl` nil-return as a real, previously-unguarded hazard at this exact call site. What I could not fully confirm within the available tooling is the precise external condition under which `evm.StateDB` fails the `*state.DBImpl` type assertion for a non-`giga` (in-scope) legacy-precompile invocation — e.g., a specific historical-trace or state-override RPC code path that constructs a different `vm.StateDB` implementation. This should be validated against the `evmrpc` tracing/simulation code paths to pin down the exact trigger before treating likelihood as fully proven.

### Recommendation
Apply the same guard used in `v614`+ to all legacy precompile packages still reachable for historical execution (`v562`, `v575`, `v580`, `v600`, `v605`, `v606`, `v610`): change `HandlePrecompileError` to check `if sdb := state.GetDBImpl(evm.StateDB); sdb != nil { sdb.SetPrecompileError(err) }` before dereferencing, matching the nil-check already present in `Prepare`.

### Proof of Concept
1. Construct a `vm.EVM` whose `StateDB` is not a `*state.DBImpl` (any legacy code path that reaches one of the affected precompile versions, e.g. historical trace/replay execution at a block height mapped to `v562`–`v610`).
2. Invoke any method on that legacy precompile. `Prepare` calls `state.GetDBImpl(evm.StateDB)`, gets `nil`, and returns the "cannot get context from EVM" error.
3. The deferred `HandlePrecompileError(err, evm, operation)` runs with `err != nil`, calls `state.GetDBImpl(evm.StateDB)` again (still `nil`), and calls `.SetPrecompileError(err)` on the nil pointer, panicking the call stack.
