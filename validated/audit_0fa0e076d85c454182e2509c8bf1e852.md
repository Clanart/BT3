### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes disproportionate allocation before any validation (OOM amplification) — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes a `t, n, i` triple from untrusted bytes and, when the interpolation tag selects `Interpolation::Constant`, immediately executes `Vec::with_capacity(usize::from(n))` where `n` is a raw `u16` from the stream. This allocation of up to ~2–4 MB is performed before `ThresholdParams::new`/`ThresholdKeys::new` validate `n`, and before a single field element is actually read. It is the same bug class as CVE-2026-73232 (ffuf decompression bomb): a small attacker-supplied size field drives a large resource commitment, with the byte-level "guard" (the stream simply ending) providing no bound on the allocation.

### Finding Description

`Vec::with_capacity(usize::from(n))` reserves `n * size_of::<C::F>()` bytes — for a 32-byte scalar, ~2 MB — purely from a 2-byte length prefix. The subsequent `read_F` loop fails fast on EOF, but the allocation has already been committed. Only after the reads does `ThresholdKeys::new`/`ThresholdParams::new` get a chance to reject an unreasonable `n` (line ~625), which is too late. Contrast with the explicitly length-guarded network read in `coordinator/src/p2p.rs` (`MAX_LIBP2P_REQRES_MESSAGE_SIZE` checked before `vec![0; len]`) and the chunked read in `networks/ethereum/src/machine.rs`, which show the codebase's intended pattern of bounding allocation by a declared length.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (listed in-scope as an untrusted-bytes sink; Serai deserializes validator-set / key material received over its channels) can force a ~2 MB heap allocation per invocation with a ~10-byte input, an amplification factor of ~10^5. Repeated calls — e.g., garbage `ThresholdKeys` blobs supplied in every message round — exhaust memory and crash the process, denying signing/key-rotation service. The effect scales linearly with call rate; no authentication or valid proof is needed because the allocation precedes all semantic validation.

### Likelihood Explanation
Reachability requires only that serialized `ThresholdKeys` bytes cross a trust boundary, which is the documented purpose of `ThresholdKeys::read`/`serialize` (restoring keys, exchanging verification-share material). The trigger is trivial: interpolation tag `0` plus `n = 0xFFFF`. No malformed cryptography, race, or privileged position is needed. Impact is capped per call by `u16` (≈2 MB per `Vec`, plus a second `n`-sized `HashMap` insertion loop of `read_G` that fails fast on short input), making this a sustained-call OOM rather than a single-shot one — hence Medium rather than High.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` before allocating or reading any collection; reject the `Interpolation::Constant` variant (or bound its vector to `n`) only after `n` is confirmed sane. Prefer pushing into a `Vec` (or reading in bounded chunks, as in `networks/ethereum/src/machine.rs::Call::read`) over `with_capacity` on an unvalidated length so that memory consumed is proportional to bytes actually received.

### Proof of Concept
Serialize a header for `ThresholdKeys::read` consisting of: `u32` `C::ID.len()` + `C::ID` bytes (correct curve tag), then `t = 1u16`, `n = 0xFFFFu16`, `i = 1u16`, interpolation tag `0x00`, and truncate the stream. `ThresholdKeys::read` will execute `Vec::with_capacity(65535)` for `C::F` (≈2 MB) and then error on the first `read_F` EOF — confirming the allocation occurs from ~40 bytes of input with zero validation. Repeating in a loop grows committed memory unboundedly (`while let Err(_) = ThresholdKeys::<Secp256k1>::read(&mut &hdr[..]) {}` with the allocation observable via a counting allocator or RSS growth).
