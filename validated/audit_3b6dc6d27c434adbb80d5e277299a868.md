### Title
Recursive clone explicitly disables Git's submodule-clone protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), allowing a malicious repo's `.gitmodules` to read files outside the intended clone target - (File: `app/src/lib/git/clone.ts`)

### Summary
The seed report is about a setter (`_updateFeeWallet`) that accepts an address with no validation, letting an attacker-influenced value corrupt state that later drives a critical operation. The direct analog in GitHub Desktop is `clone()`, which unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone while also passing `--recursive`, without validating or restricting what a fetched repository's submodule configuration is allowed to point at. This mirrors the same broken invariant: a value that should be validated/constrained (submodule transport/target) is instead trusted implicitly, because Desktop actively turns off Git's own guard.

### Finding Description
`clone()` builds the environment for the underlying `git clone --recursive ...` invocation like this: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced (alongside `protected.clone`) specifically to prevent unsafe local-transport submodule clones during `--recursive` operations — the fix class for CVE-2022-39253, where a malicious repository could ship a `.gitmodules` file with a submodule URL using the local (`file://` or bare path) transport pointing outside the intended destination, causing arbitrary files on the clone host to be copied into the checkout (an information-disclosure/read primitive). By force-setting this flag to `'false'`, Desktop deliberately turns that guard off for every clone it performs, while still requesting `--recursive` submodule checkout: [2](#0-1) 

Desktop does add its own defense for the *destination* path (`isClonePathSensitive`, blocking clones into `~/.ssh`, `~/.gnupg`, etc.): [3](#0-2) 

but this check only validates the clone destination directory chosen by the user — it does nothing to constrain what a malicious repository's own `.gitmodules` submodule URLs can reference once the recursive submodule checkout runs with Git's file-transport protection disabled. There is no `GIT_ALLOW_PROTOCOL`/`protocol.file.allow` restriction anywhere else in the codebase either (no occurrences found in the repo), so nothing else backstops the disabled protection.

### Impact Explanation
This exactly matches the accepted impact class "attacker controls a cloned/fetched repository ... and the result is ... file write or read outside the repo": a repository the user chooses to clone in Desktop (e.g., from a link, a fork, or a public/malicious GitHub repo) can embed a `.gitmodules` file whose submodule uses a local transport pointing at an arbitrary filesystem path. With `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` and `--recursive` requested unconditionally, Desktop performs the exact operation Git's upstream protection exists to block, allowing submodule content from outside the intended repo location to be pulled into the user's checkout.

### Likelihood Explanation
Every clone performed through Desktop's `clone()` function passes through this code path unconditionally — there is no per-repository opt-in/opt-out and no user prompt, so any attacker who can get a victim to clone a crafted repository (the most basic Desktop use case: "Clone a repository" or "Open with GitHub Desktop" deep link) triggers the recursive submodule checkout with the protection disabled.

### Recommendation
Do not unconditionally force `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Instead, either leave Git's default protection active (letting Git safely fail/prompt on unsafe submodule transports) or, if `--recursive` submodule cloning must be supported, apply an explicit allow-list (e.g., `GIT_ALLOW_PROTOCOL=https:http:ssh:git` and `protocol.file.allow=never`) so that a malicious repository cannot use local/file transports for its submodules regardless of this override.

### Proof of Concept
1. Attacker publishes a public GitHub repository containing a `.gitmodules` entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = /home/victim/.ssh
   ```
2. Victim uses Desktop's "Clone a repository" (or a `x-github-client://openRepo` deep link) to clone the attacker's repository.
3. `clone()` in `app/src/lib/git/clone.ts` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the child process environment.
4. Because the protection normally added to block exactly this local-transport submodule technique is disabled, the submodule checkout copies the contents of `/home/victim/.ssh` into the cloned repository's `leak/` directory, exposing files from outside the intended repository to whatever surfaces (working tree, later commit/push) the user interacts with next.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
