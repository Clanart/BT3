## Analysis

The external report's core broken invariant is: **an irreversible fund-moving side effect executes, then a later step in the same logical operation fails, and the failure handler resets the "not yet settled" state instead of treating the fund movement as authoritative — enabling the operation to be retried and the fund movement repeated.**

Hyperbridge's ISMP module-callback dispatch has the exact same shape, and it is explicitly acknowledged (but not fixed) in the protocol's own documentation.

### The verified mechanism

`modules/ismp/core/src/handlers/timeout.rs` calls into an `IsmpModule::on_timeout` callback and, regardless of whether the callback succeeds, keeps the *overall* extrinsic `Ok` so a bad message in a batch doesn't poison the whole batch: [1](#0-0) 

```rust
// Delete commitment to prevent rentrancy attack
let meta = host.delete_request_commitment(&request)?;
...
let res = cb.on_timeout(request.clone()).map(|weight| {...});
if res.is_ok() {
    host.on_request_timeout(&request, meta)?;
} else {
    // Module callback failed; restore commitment so the request
    // can be retried.
    host.store_request_commitment(&request, meta)?;
    ...
}
Ok::<_, anyhow::Error>(res)
```

Because the outer closure always returns `Ok(res)`, the top-level `pallet_ismp::execute` dispatchable itself succeeds. Substrate's automatic storage-transaction rollback only triggers when a **dispatchable returns `Err`** — since it returns `Ok` here, **any storage writes `cb.on_timeout` already committed before it internally failed are never rolled back**, while the commitment is explicitly restored to "pending" so the same timeout can be resubmitted and replayed. The docs confirm this is a known, deliberate design tradeoff pushed onto module authors: [2](#0-1) 

The Hyperbridge `IsmpModule` implementations that actually run inside this dispatch path perform multi-step, fund-moving logic where a token mint/transfer happens **before** a later, independently-fallible step — exactly the structural precondition the external report describes. `pallet_hyper_fungible_token`'s `on_accept` mints/transfers tokens to the beneficiary first, and only afterward executes attacker-supplied optional calldata via a runtime-call dispatch that can fail for reasons unrelated to the transfer (decode error, base-call-filter rejection, dispatch error): [3](#0-2) [4](#0-3) 

If that later `runtime_call.dispatch(...)` step fails, `on_accept` returns `Err`, and — following the same non-transactional "swallow and allow retry" pattern verified in `timeout.rs` (and referenced by the identical `store_request_receipt`/`delete_request_receipt`/`on_accept` machinery present in `modules/ismp/core/src/handlers/request.rs`) — the request receipt is not persisted as delivered, so the identical incoming `PostRequest` (with its still-valid membership proof) can be resubmitted by a relayer. On replay, `on_accept` runs again and mints/transfers the beneficiary's tokens a second time, while the first mint was never reverted.

**Corrupted value:** the beneficiary's fungible-asset balance (or native currency balance) inside `pallet_hyper_fungible_token`, credited via `NativeCurrency::transfer` / `Assets::mint_into` in `on_accept`.

**Why existing guards don't stop it:** the guard is the request-receipt / request-commitment presence check, but that guard is only written on the `Ok` path of the callback. It has no visibility into partial storage mutations already performed by the callback body before it errored, and the framework performs no automatic rollback because the enclosing dispatchable never returns `Err`.

### Title
Non-transactional module callback dispatch lets a partially-executed `IsmpModule::on_accept`/`on_timeout` mutation be replayed for double-credit - (File: `modules/ismp/core/src/handlers/timeout.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
Hyperbridge's ISMP dispatch layer calls into `IsmpModule` callbacks and, on failure, restores the request commitment/receipt to allow a retry — but never rolls back storage mutations the callback already made before it failed, because the enclosing dispatchable is deliberately kept `Ok`. Modules like `pallet_hyper_fungible_token` perform an irreversible token mint/transfer *before* a later fallible step (arbitrary calldata dispatch), so a crafted request whose calldata step fails leaves the mint/transfer committed while the message is marked retryable, allowing the same PostRequest to be replayed and the beneficiary credited again.

### Finding Description
`modules/ismp/core/src/handlers/timeout.rs` (and, by the same design pattern, `request.rs`/`response.rs`) deletes the commitment/receipt before invoking the module callback, then re-stores it if the callback returns `Err`, explicitly to permit a retry. Because the top-level dispatchable always returns `Ok`, Substrate's automatic transactional storage rollback (which only fires on dispatchable `Err`) never engages, so any storage writes the callback made prior to its internal failure persist. `pallet_hyper_fungible_token::on_accept` mints/transfers funds to the beneficiary first and only afterward dispatches attacker-supplied calldata, which can fail independently of the transfer.

### Impact Explanation
An attacker who controls the calldata payload of a cross-chain token-transfer message can craft calldata that reliably fails the post-mint dispatch step (e.g., a call rejected by `BaseCallFilter`, or invalid signature-verification for the substrate-calldata branch after the transfer executed for the native/native-asset path... though in the current code order the signature check for calldata happens before the mint only for the substrate-calldata branch — the message-level mint itself precedes calldata handling entirely). This causes the message to be treated as failed/retryable while the beneficiary already received funds, and a relayer resubmitting the same valid membership proof re-triggers `on_accept`, minting/transferring the same funds again — direct loss of protocol/bridge funds via duplicate settlement.

### Likelihood Explanation
Medium: it requires crafting a cross-chain message with calldata that predictably fails after the token credit executes, and requires no privileged relayer/prover/admin cooperation — a normal relayer resubmitting a legitimately-provable, already-seen message is sufficient to trigger the double credit, matching the "no attacker needed, natural resubmission suffices" characteristic of the seed report.

### Recommendation
Treat the funds-moving mutation as the authoritative commit point: either (1) wrap each `IsmpModule` callback invocation in an explicit transactional boundary (`frame_support::storage::with_transaction`) so any callback-internal `Err` reverts everything the callback did, restoring true atomicity before the commitment/receipt is re-stored for retry; or (2) reorder module logic so all fallible, non-fund-related steps (calldata decode, signature verification, filter checks) run strictly before any balance-mutating operation, ensuring a callback failure never occurs after value has moved.

### Proof of Concept
1. Attacker dispatches (or has delivered) a `PostRequest` into `pallet_hyper_fungible_token` whose `Message.data` encodes a `SubstrateCalldata` with a `runtime_call` that is valid to decode but filtered by `BaseCallFilter` (or whose signature check is deliberately malformed for the beneficiary's account) — see `on_accept`'s calldata branch in `modules/pallets/hyper-fungible-token/src/module.rs:119-203`.
2. `on_accept` mints/transfers the message amount to `beneficiary` (`module.rs:93-117`), then reaches the calldata execution branch and fails at `Err(HftError::CallFiltered)?` or `Err(HftError::SignatureVerificationFailed)?`.
3. The enclosing ISMP request handler (mirroring the verified `timeout.rs:106-134` pattern) catches this `Err`, does not persist the request as delivered, and the overall extrinsic still returns `Ok`, so the beneficiary's mint from step 2 is never rolled back.
4. A relayer resubmits the identical `PostRequest` with the same (still valid) membership proof; `on_accept` runs again, minting/transferring the same amount to the same beneficiary a second time.
