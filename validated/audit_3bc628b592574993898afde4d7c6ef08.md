Based on the investigation, I found a concrete local analog: the Tron variant of `IntentGatewayV2.sol` applies governance `UpdateParams` requests without any bounds validation, unlike its canonical EVM counterpart (`evm/src/apps/intentsv2/IntentsBase.sol`) and unlike `SimplexPaymaster.sol`, both of which enforce hard caps before writing new parameters.

### Title
Missing bounds validation on `UpdateParams` in Tron `IntentGatewayV2.onAccept` allows `protocolFeeBps`/`surplusShareBps` to be set outside safe range - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2`/`IntentsBase.sol` validates every governance-supplied `Params` value (`protocolFeeBps < 10_000`, `surplusShareBps <= 10_000`, non-zero `host`/`dispatcher`) via `_validateParams` before committing them in `_updateParams`. The Tron port of the same contract implements the identical `UpdateParams` request kind but writes `_params = update.params` and `_destinationProtocolFees[stateMachineId] = feeBps` directly, with no equivalent validation call anywhere in the file.

### Finding Description
`IntentsBase.sol::_updateParams` calls `_validateParams(update.params)` which reverts with `InvalidInput` if `protocolFeeBps >= 10_000` or `surplusShareBps > 10_000`, and also validates the per-destination `feeBps < 10_000` in the loop: [1](#0-0) 

The Tron `IntentGatewayV2.onAccept` implements the same `RequestKind.UpdateParams` branch but skips validation entirely, directly assigning `_params = update.params` and looping over `update.destinationFees` to write `_destinationProtocolFees[stateMachineId] = feeBps` with no upper-bound check: [2](#0-1) 

`protocolFeeBps` (or an override in `_destinationProtocolFees`) is consumed unchecked in `placeOrder`'s fee computation:
```
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [3](#0-2) 

If `protocolFeeBps` (or a destination override) is ever set to a value `>= 10_000` — a single off-by-one/fat-finger difference from the equivalent, validated EVM deployment — `reducedAmount = originalAmount - protocolFee` underflows in an unchecked-arithmetic Solidity context that is not wrapped in a `try/catch` and is not protected by a prior sanity check, reverting every `placeOrder` call for that destination (denial of order placement / bricked gateway), or, for a `protocolFeeBps` in the ambiguous range close to `10_000`, silently confiscates almost the entire user input as "protocol fee/dust" with no ceiling stopping governance-side misconfiguration from being applied verbatim on-chain. This is the exact bug class from the seed report: a governance setter for a numeric economic parameter (`setApys`-equivalent) lacking a `require`/bounds check that other, better-guarded code paths in the very same codebase already enforce.

### Impact Explanation
`protocolFeeBps` and per-destination fee overrides directly determine how much of every user's escrowed input is retained by the protocol versus made available to solvers (`reducedAmount`, later used to compute the order `commitment` and escrow amount). An unvalidated write here can cause disproportionate loss of user funds retained as "dust" or complete denial of service for order placement on that gateway instance, matching the "stealing or loss of funds" / "transaction manipulation" category in the bounty scope. Because `IntentGatewayV2` on Tron shares the same request-kind schema and cross-chain governance channel as the validated EVM contract, this divergence is a genuine deployment-specific hole rather than a documentation/style nit.

### Likelihood Explanation
Likelihood is Medium: the `UpdateParams` message must originate from Hyperbridge's own governance channel (`onlyHost` + `source == hyperbridge()` check), so it is not directly attacker-triggerable without a governance/relayer message. However, this is precisely the scenario the original "no validation of apy" report targeted — an operational safeguard missing on a *specific* contract variant while present on its sibling, so a single misconfigured multi-chain governance dispatch (intended for the validated EVM gateways) applied to the Tron deployment would silently corrupt tokenomics with no on-chain check to stop it, unlike every other config-setter for the same field in this codebase.

### Recommendation
Add the same `_validateParams`/bounds-check logic used in `evm/src/apps/intentsv2/IntentsBase.sol` (`protocolFeeBps < 10_000`, `surplusShareBps <= 10_000`, non-zero `host`/`dispatcher`, and `feeBps < 10_000` per destination) to `evm/tron/contracts/apps/IntentGatewayV2.sol::onAccept`'s `UpdateParams` branch before committing `_params` and `_destinationProtocolFees`, matching the pattern already enforced in `SimplexPaymaster::_setParams` (`MAX_MARKUP_BPS`, `MAX_SWAP_SLIPPAGE_BPS` caps).

### Proof of Concept
1. Hyperbridge governance dispatches an `UpdateParams` PostRequest to the Tron `IntentGatewayV2` instance with `params.protocolFeeBps = 10_000` (100%) or a `destinationFees` entry with `destinationFeeBps = 10_000`, intending it for a validated EVM chain but reusing/misrouting the payload for the Tron deployment.
2. `onAccept` decodes the body and executes `_params = update.params; _destinationProtocolFees[stateMachineId] = feeBps;` with no revert, at [2](#0-1) .
3. Any subsequent `placeOrder` call computes `protocolFee = originalAmount * 10_000 / 10_000 = originalAmount`, then `reducedAmount = originalAmount - protocolFee = 0`. Depending on the exact bps chosen, this either underflows and reverts (bricking new orders on the gateway) or reduces every user's escrowed input toward zero while the "dust" fee event reports the difference — confirming the missing cap enabled a config that the EVM `_validateParams` function would have rejected.     /**
     * @dev Validates gateway configuration parameters. Reverts with InvalidInput if any
     * value would brick the gateway or cause arithmetic errors in fee calculations.
     *
     * @param p The parameters to validate.
     */
    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
