## Analog Vulnerability Found

### Title
Division-by-zero panic in `consolidatedNode.Split()` during block-reward finalization when a proposer's CN and CL staking amounts are both zero - (File: kaiax/staking/staking_info.go)

### Summary
The Sherlock report shows `_withdraw()` in Multipool dividing by `_totalSupply`/`liquidity` without guarding against the case where the numerator components are zero, causing an unconditional revert of a public-facing function. Kaia's reward-distribution code has the same structural flaw: `consolidatedNode.Split()` performs `clAmount.Div(clAmount, totalAmount)` where `totalAmount = StakingAmount + CLStakingAmount`, and is invoked for the block proposer with **no check that this sum is non-zero**.

### Finding Description
`consolidatedNode.Split()` computes:
```go
totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
clAmount = clAmount.Div(clAmount, totalAmount)
``` [1](#0-0) 

This is called from `specWithProposerAndFunds` and `specWithProposerAndFundsFlex`, which select the `consolidatedNode` whose `RewardAddr` equals `config.Rewardbase` (the block proposer) and call `cn.Split(proposer)` as long as `cn.CLStakingInfo != nil` - **without any check that `cn.StakingAmount` or `cn.CLStakingInfo.CLStakingAmount` is greater than zero**: [2](#0-1) [3](#0-2) 

Contrast this with the staking-reward allocation functions (`assignStakingRewards`, `assignStakingRewardsFlex`), which only call `Split()` after confirming `cnTotalStakingAmount > minStake` (i.e., a provably non-zero excess), making the divisor safe there: [4](#0-3) 

However, the proposer-reward path has no equivalent guard, meaning `Split()` is reached even when `cn.StakingAmount == 0`.

`CLStakingInfo.CLStakingAmount` is populated directly from `CLRegistry`'s `MultiCallDPStakingInfo` result, rounded down to whole KAIA, with no filtering out of zero-amount entries: [5](#0-4) [6](#0-5) 

So a validator that is registered in the CL Registry (has a non-nil `CLStakingInfo`) but currently has `CLStakingAmount = 0` (e.g., withdrew consensus-liquidity stake below 1 KAIA, which floors to 0 due to integer division) combined with `StakingAmount = 0` in its CNStaking contract, would cause `totalAmount = 0` in `Split()`. Go's `big.Int.Div` panics on division by zero (unlike Solidity's revert, this is a hard panic), which occurs inside `GetDeferredReward`/`GetBlockReward`, part of the consensus-critical `FinalizeState` reward computation executed by every full node.

### Impact Explanation
If reached, this panics the node process during block finalization/reward computation — a consensus-critical, deterministic code path executed by every node validating or querying the block. This is not a simple revert (as in the original report) but a **process-level panic**, which can crash nodes computing that block's reward, or at minimum cause `kaia_getReward`/`kaia_getBlockReward` RPC calls to panic/error. If it occurs during actual block processing (`FinalizeState`), it can halt block production/validation across honest nodes, a critical safety property failure, matching "state divergence/halt" per the validation criteria.

### Likelihood Explanation
Confidence is limited because I could not fully verify (given time constraints) whether `valset.NodeState.IsRewardEligible()` (used to filter which CN profiles participate, and by extension whether one becomes proposer) can be true while `StakingAmount == 0`, nor did I verify the exact conditions under which the permissioned `parseCallResult` path admits a zero-stake node into `RewardAddrs`. The reachability of "a CN with 0 CNStaking and CLStakingInfo present with 0 CLStakingAmount becomes `Rewardbase`" is plausible via ordinary staking/unstaking transactions (a staker fully unstaking a CN or CL pool while remaining registered) but is not proven with full certainty from the code reviewed.

### Recommendation
Add a non-zero guard in `consolidatedNode.Split()` (return `(amount, big.NewInt(0))` or `(big.NewInt(0), amount)` when `totalAmount.Sign() == 0`), mirroring the missing-zero-amount check pattern from the original report's `_withdraw()` recommendation, and add the same `> 0` staking-amount guard used in `assignStakingRewards`/`assignStakingRewardsFlex` to the proposer-split logic in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`.

### Proof of Concept
Not independently executed; conceptual trace based on static code review:
1. Validator registers CN in AddressBook and also registers a CL pool via CLRegistry.
2. Validator fully unstakes/withdraws from the CN staking contract (`StakingAmount` → 0) and reduces CL pool stake below 1 KAIA (`CLStakingAmount` rounds to 0), while remaining registered in both AddressBook and CLRegistry.
3. If this validator's `RewardAddr` is selected as `config.Rewardbase` for a block (contingent on unverified reward-eligibility rules), `getDeferredRewardFullKore`/`Flex` calls `specWithProposerAndFunds(Flex)` → `cn.Split(proposer)` with `totalAmount = 0`.
4. `big.Int.Div` panics, crashing reward computation for that block on every node executing it. [1](#0-0) [7](#0-6)

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
