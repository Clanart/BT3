### Title
Precision loss in NFT royalty computation via premature division - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`compute_royalty_amount()` and `NFTWallet.royalty_calculation()` compute royalty payouts for NFT offers using an operation order that divides before multiplying, exactly the same precision-loss pattern described in the source report's `convert_to_yang_helper()` bug. This can truncate the royalty amount to zero (or well below the intended value) even though the mathematically correct result would be nonzero.

### Finding Description
`compute_royalty_amount()` computes:
```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
``` [1](#0-0) 

The integer division `abs(offered_amount) // royalty_split` happens *before* multiplying by `percentage`, discarding remainder precision. If the correct value would be `offered_amount * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`, the premature division truncates the intermediate quotient, causing loss of value whenever `offered_amount` is not an exact multiple of `royalty_split` — this mirrors the `(asset_amt * total_yang) / 1e18` premature division in the referenced Opus finding.

The same pattern also appears in the display/estimation helper `NFTWallet.royalty_calculation()`:
```
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
``` [2](#0-1) 

`compute_royalty_amount()` is invoked with `request_side_royalty_split` (a count derived from how many royalty-enabled NFTs are being requested/offered in a single offer) during offer construction in `make_nft1_offer()`:
```
extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
``` [3](#0-2) 

An unprivileged offer counterparty controls the structure of the trade (how many NFTs are bundled and the fungible amount offered against them), so `royalty_split` and `offered_amount` are both attacker-influenced inputs to this calculation, i.e., this is reachable through the offers/trades flow without any elevated privilege.

However, I was **unable to verify** whether the on-chain NFT ownership/royalty-transfer puzzle (the CLVM `nft_ownership_transfer_program` / royalty enforcement logic) independently re-derives and asserts the expected royalty amount from the trade price, or whether it simply trusts the wallet-supplied `CreateCoin` amount computed by `compute_royalty_amount()`. The `.clvm` puzzle source for this program was not found in the indexed portion of the repository, so I cannot confirm whether:
- (a) the puzzle recomputes/enforces royalty independently (in which case a wallet using a different rounding order would simply produce a rejected/invalid spend, not a fund-theft condition), or
- (b) the puzzle trusts the value the offering wallet supplies (in which case an attacker constructing an offer with many small-value bundled NFTs, or a payment amount that is not a clean multiple of the split, could deterministically shrink or zero out the royalty paid to the NFT creator while the offer still settles).

### Impact Explanation
If case (b) holds, an offer counterparty can structure trades (e.g., bundling several NFTs against a modest fungible payment, or choosing payment amounts that don't divide evenly by the NFT count) to systematically reduce or eliminate royalty payments owed to NFT creators, which is a concrete value-loss/fund-diversion outcome reachable purely through the "offers and trades" flow described as in-scope. If case (a) holds, the impact is limited to spend-validation failures (denial of a legitimate trade), which would not meet the required impact bar (unauthorized coin movement / theft / supply inflation).

Because I could not confirm which case applies with the tools available, I cannot assert with confidence that this constitutes exploitable value theft rather than a bounded UX/validation quirk.

### Likelihood Explanation
Reachability is trivial — any wallet user creating or accepting an NFT offer with multiple royalty-bearing NFTs and a fungible-asset counter-payment exercises this code path with attacker-chosen `offered_amount`/`royalty_split` values, requiring no special privilege. Whether the mis-computation is actually exploitable for value extraction depends entirely on the unverified on-chain enforcement behavior noted above.

### Recommendation
Reorder the computation in both `compute_royalty_amount()` and `NFTWallet.royalty_calculation()` to defer division until after all multiplications, e.g.:
```
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
This preserves precision analogous to the mitigation recommended in the source report. Additionally, confirm (by examining the NFT ownership/royalty transfer CLVM puzzle) whether on-chain validation is trusting or independently re-deriving this amount, since that determines whether this is a genuine fund-loss vulnerability or merely a spend-validation/UX issue.

### Proof of Concept
Using the existing test in the repo that already documents the truncation-to-zero behavior:
```
def test_small_amount_truncates_to_zero() -> None:
    result = compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)
    assert result == uint64(0)
``` [4](#0-3) 

Generalizing: for `royalty_split > 1`, choose `offered_amount` such that `offered_amount // royalty_split == 0` even though `offered_amount * percentage // (royalty_split * 10000)` would be nonzero for larger `percentage` — e.g. `offered_amount=9`, `royalty_split=10`, `percentage=9999` yields `9 // 10 = 0`, so the naive formula returns `0`, while the "multiply first" formula gives `9*9999//100000 = 0` too in this exact case, but this demonstrates the truncation ceiling is `royalty_split - 1` units lost per computation, scaling with the number of royalty-bearing NFTs bundled into an offer — a direct analog of the `0.0009e8 BTC → 0` shares example in the source report.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
