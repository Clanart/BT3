## Title
Copilot conflict resolution silently overwrites non-conflict file content that merely resembles conflict markers - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted merge-conflict resolution feature locates conflict blocks in a file purely by scanning for lines that *look like* `<<<<<<<` / `=======` / `>>>>>>>` markers, with no cross-check against git's actual conflict metadata (index stages 1/2/3). The per-hunk resolutions returned by the model are then spliced back into the file **by ordinal position, not by identity**, and staged with `git add` without further validation. A file that is legitimately conflicted by git but also happens to contain marker-look-alike literal text elsewhere (documentation, test fixtures, embedded patches, etc.) will have that unrelated text misidentified as an extra "conflict," sent to the LLM, and silently overwritten with fabricated content when the resolution is written back to disk and staged.

### Finding Description
Two independent naive line-scanners are used across the feature, and neither is aware of git's real conflict boundaries:

`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks the raw file text line-by-line and treats *any* line matching `oursMarker = /^<{7}(?:\s|$)/` (followed eventually by a `=======` and `>>>>>>>` line) as a conflict hunk: [1](#0-0) [2](#0-1) 

This is purely regex-based against on-disk text — it never consults `git ls-files -u` / index stages to confirm the block is a real unmerged conflict.

The extracted hunks (ordinal, `Conflict 1 of N`, `Conflict 2 of N`, …) are sent to the model as the entire source of truth: [3](#0-2) 

`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` re-scans the same raw content with the same marker regexes and splices `hunkResolutions[hunkIndex]` into every detected marker block strictly **in file order**, explicitly documented as "matched by order, not by line number": [4](#0-3) [5](#0-4) 

The reassembled content is then written straight to disk and staged, with the only safety check being whether the file *still has any* conflict markers left (to avoid clobbering a user's own manual edit) — there is no check that the number/identity of detected marker blocks matches what git considers a real conflict: [6](#0-5) 

Because both the extraction and the reassembly steps key purely on **counting marker-shaped text blocks in order**, any extra marker-look-alike block anywhere in the file (before, between, or after the real conflict) shifts every subsequent index. The model is asked to resolve N "conflicts" (including the fake one), and its ordinal resolution for the fake block gets spliced into that exact location in the file — silently rewriting content that was never part of a real merge conflict, and is not what the user reviewed as the actual diff of committed changes.

### Impact Explanation
This is a silent-corruption-of-committed-content bug driven entirely by attacker-controlled repository content: a contributor can add a file (docs, changelog, shell script, YAML/config example, or even a `.patch`/test-fixture file — this very repository's own test suite, `app/test/unit/copilot-conflict-resolution-test.ts`, contains files with literal `<<<<<<<`/`=======`/`>>>>>>>` text as fixture data, demonstrating how common this pattern is) that legitimately contains marker-look-alike text. Once the victim later has a genuine, unrelated git conflict in that same file and uses "Resolve with Copilot," the naive scanner counts the fake block as an additional conflict, the model fabricates content for it, and `reassembleResolvedFile` overwrites the unrelated literal text with hallucinated content — all before the file is staged via `git add`. The user's dialog (`copilot-conflicts-changes.tsx`) presents the resolution using the same "Conflict N of M" framing built from the same flawed count, giving no indication that a non-conflict region of the file is being rewritten. The end result is a corrupted commit whose content silently diverges from both the user's intent and the actual git-resolved state, without any warning.

### Likelihood Explanation
Requires no privileged access, malware, or social engineering beyond a normal contribution to a repository (a PR, a vendored file, or an existing file in the repo) that contains marker-look-alike text, combined with an unrelated future genuine conflict in that file — a scenario likely in any repository containing documentation about git, conflict-resolution test fixtures, or embedded diff/patch examples. It fires automatically whenever the user opts into the "Resolve with Copilot" flow on such a file; no unusual user action is needed beyond using the advertised feature as intended.

### Recommendation
- Only treat lines as conflict markers when they correspond to a real unmerged path/region reported by git (e.g., cross-check against `git diff --check` output, or use git's own conflict-aware diff rather than naive regex scanning of raw file text).
- After model resolution, verify `hunkIndex === hunkResolutions.length` (and that the count of detected blocks in `reassembleResolvedFile` equals the count sent in `extractConflictHunks`) before writing/staging; abort and fall back to manual resolution on any mismatch.
- Consider anchoring resolutions to unique markers/hashes of each real conflict's `oursContent`/`theirsContent` rather than pure ordinal position, so a rogue marker-shaped block cannot desynchronize the mapping.

### Proof of Concept
1. Attacker contributes `notes.md` to the repository containing, among other unrelated content:
   ```
   Example of a git conflict:
   <<<<<<< example
   foo
   =======
   bar
   >>>>>>> example
   ```
2. Later, the victim's branch and the attacker's branch both modify `notes.md` in an unrelated location, producing one genuine git conflict in that file.
3. Victim runs the merge in Desktop, sees `notes.md` conflicted, and clicks "Resolve with Copilot."
4. `buildConflictContext` → `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts`) scans the raw file and reports **two** hunks: the fake `example` block and the real conflict, in file order.
5. The model resolves both "conflicts" (it has no way to know the first is not a real merge conflict) and returns two `resolvedContent` entries.
6. `reassembleResolutions` → `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts`) splices resolution[0] into the fake `example` block and resolution[1] into the real conflict, purely by order.
7. `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts`) writes the reassembled content to disk and runs `git add`, silently replacing the "Example of a git conflict" text with fabricated model output, staged as part of the merge commit with no user visibility into the corruption.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
