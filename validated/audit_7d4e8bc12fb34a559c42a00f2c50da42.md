### Title
Empty session scope treated as "covers all required scopes", bypassing forced re-authentication after scope changes - ([File: lib/shopify_app/access_scopes/user_strategy.rb])

### Summary
`ShopifyApp::AccessScopes::UserStrategy.covers_scopes?` treats an *empty* stored scope list as automatically satisfying the app's currently required scopes, the same class of bug as the reported `MarginTrading` issue where a "zero"/absent state (`debtWithAccruedInterest == 0`) was implicitly treated as "healthy" and allowed to pass a security-relevant threshold check. Here, a session with no recorded `scope` (the "empty" sentinel state) is treated as "fully covers required scopes," which short-circuits the `reauth_on_access_scope_changes` protection in `LoginProtection#activate_shopify_session`.

### Finding Description
`covers_scopes?` is defined as: [1](#0-0) 

```ruby
def covers_scopes?(current_shopify_session)
  current_shopify_session.scope.to_a.empty? || current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```

`LoginProtection#activate_shopify_session` calls this to decide whether to force re-login when scopes changed: [2](#0-1) 

The intent of `reauth_on_access_scope_changes` is: if the app's configured required scopes have expanded/changed since the session's access token was granted, the stale session should be discarded and the merchant forced through OAuth again to obtain a token with the correct scopes. The `.to_a.empty?` clause conflates "no scope information recorded" with "scope requirement satisfied," exactly mirroring the report's root cause: `_calculatePortfolioRatio` returns `0` for "no debt," and the liquidation check `ratio <= redCoeff` treats that `0` sentinel as "unhealthy" without distinguishing "no debt" from "actually below threshold." Here, an *absent*/empty scope value is treated as "covers everything," without distinguishing "we don't know the scope" from "the scope is sufficient."

### Impact Explanation
Any session whose stored `scope` attribute is empty (e.g., an older/migrated session row created before scope tracking was consistently populated, or one that legitimately has zero granted scopes) is treated by this method as if it already has every scope the app currently requires. This defeats the security purpose of `reauth_on_access_scope_changes`: a session lacking the up-to-date/expanded access scopes is allowed to continue being used without being forced to re-authenticate, so API calls proceed with a token that may have been issued under different scope requirements than the app currently declares. This is a logic/authorization-boundary weakness rather than a token-theft primitive.

### Likelihood Explanation
This path is only exercised when the app operator has explicitly enabled `reauth_on_access_scope_changes` (an opt-in configuration flag) and is using the `UserStrategy` (online/user-token) access-scope strategy, and only affects sessions whose `scope` value is empty. It is not directly reachable purely from an anonymous/unrelated HTTP request without first having a session that ends up with an empty stored scope; I was not able to fully verify, from the indexed code, all real-world conditions under which a legitimately-authenticated session would end up with an empty `scope` while still being loaded and reused (e.g., data migration gaps, incomplete `UserSessionStorage` population, or scope revocation flows). This uncertainty means the practical attacker-reachable severity is lower than the H-03 analog, and it should be treated as a defense-in-depth gap rather than a confirmed cross-tenant/cross-user compromise.

### Recommendation
Do not treat an empty/absent scope as automatically satisfying the required scopes. Only return `true` from `covers_scopes?` when the session's scope is present and actually a superset of `ShopifyAPI::Context.scope`; if scope information is missing, treat it the same as "does not cover," forcing re-authentication:
```ruby
def covers_scopes?(current_shopify_session)
  return false if current_shopify_session.scope.to_a.empty?
  current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```

### Proof of Concept
1. Configure the app with `config.reauth_on_access_scope_changes = true` and `config.user_access_scopes_strategy = ShopifyApp::AccessScopes::UserStrategy`.
2. Persist (or otherwise obtain) a valid online/user `ShopifyAPI::Auth::Session` whose `scope` is empty (`ShopifyAPI::Auth::AuthScopes.new([])`), while the app's currently configured `ShopifyAPI::Context.scope` requires one or more scopes.
3. Send an authenticated request using cookies/JWT that resolve to this session through a controller including `ShopifyApp::LoginProtection`.
4. Observe that `activate_shopify_session` calls `covers_scopes?`, which returns `true` due to the `scope.to_a.empty?` short-circuit, so `clear_shopify_session`/`redirect_to_login` is never triggered and the stale/under-scoped session is activated and used to make API calls, even though the configured scopes changed.
