### Title
`updateEndRemainingAllocation()` is unguarded against re-invocation, letting an unprivileged caller shrink the bonus denominator and over-allocate `totalBonus`, breaking the claimable-vs-balance invariant - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, callable by anyone at any time after `periodsEndTime[4]`, and unconditionally overwrites `totalEndRemainingAllocation` with the current `totalRemainingAllocation`. Because `claim()` only auto-calls it once (guarded by `totalEndRemainingAllocation == 0`), an attacker can repeatedly re-invoke it directly, front-running other users' `claim()` transactions to shrink the bonus denominator while `totalBonus` (the numerator) stays fixed, inflating bonus payouts to whichever claim lands next and starving later claimants until `claim()` reverts with `InsufficientBalance`.

### Finding Description
`getBonusAmount()` computes each user's bonus as:
```
bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation
``` [1](#0-0) 

This formula is only mathematically balanced (sum of all bonuses == `totalBonus`) if `totalEndRemainingAllocation` is fixed exactly once, as a snapshot of `totalRemainingAllocation` taken the moment `periodsEndTime[4]` is reached, and never changed afterward. `claim()` enforces the "only once" semantics only for its own internal call:
```
if (totalEndRemainingAllocation == 0) {
    updateEndRemainingAllocation();
}
``` [2](#0-1) 

However, `updateEndRemainingAllocation()` itself has no such guard - it can be called directly by anyone, any number of times, and will overwrite the snapshot every time as long as `block.timestamp >= periodsEndTime[4]`:
```
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
``` [3](#0-2) 

Exploit flow (no privileged role required):
1. `periodsEndTime[4]` is reached. Some users have already forfeited allocation from early claims, so `totalBonus = B > 0`. The first post-period-4 `claim()` sets `totalEndRemainingAllocation = R0` (sum of all unclaimed allocations at that instant).
2. User `U1` claims, receiving `bonus = alloc_U1 * B / R0`, reducing `totalRemainingAllocation` to `R1 < R0`.
3. Attacker (unprivileged, no special role) directly calls `updateEndRemainingAllocation()`, resetting `totalEndRemainingAllocation` to the now-smaller `R1`.
4. Because `totalEndRemainingAllocation` is now non-zero, `claim()`'s internal guard never re-fires, but the denominator has already been shrunk. The next claimant, `U2`, now receives `bonus = alloc_U2 * B / R1`, which is larger than the fair `alloc_U2 * B / R0`.
5. Repeating steps 3-4 before every subsequent claim causes the sum of bonuses paid out to exceed `totalBonus`, and the sum of `getClaimableAmount()` across all remaining holders to exceed the token balance actually held by the contract.

The `if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();` check does not prevent the underlying accounting corruption; it merely converts the overspend into a hard revert for whichever late claimant tries to withdraw once the pool is drained, permanently freezing their legitimate allocation. [4](#0-3) 

### Impact Explanation
Because any unprivileged address can repeatedly re-snapshot `totalEndRemainingAllocation` downward between claims, the bonus-sharing invariant (`sum(bonus_i) == totalBonus`) is broken: earlier/attacker-favored claimants extract a disproportionate share of `totalBonus`, and the token balance held by the contract can fall below the sum of remaining legitimate `getClaimableAmount()` values. The last claimants in the sequence will have their `claim()` permanently revert with `InsufficientBalance`, freezing their allocation indefinitely (no recovery path besides `withdrawDust()`, which is owner-only and locked until 9 months after airdrop end). This matches "protocol insolvency / permanent freezing of user funds."

### Likelihood Explanation
No special privileges, capital, or flash loans are required - only calling the `public` `updateEndRemainingAllocation()` function directly (instead of relying on it being invoked implicitly inside `claim()`) and timing/front-running it relative to other users' `claim()` transactions after `periodsEndTime[4]`. This is trivially repeatable by any observer of the mempool for as long as unclaimed allocations remain, making it a low-cost, high-repeatability griefing/self-enrichment vector.

### Recommendation
Guard `updateEndRemainingAllocation()` so the snapshot can only be taken once, e.g.:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4] && totalEndRemainingAllocation == 0) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
Additionally consider restricting the function to be called only internally by `claim()` (e.g., making it `internal`/`private`) since there is no legitimate reason for external actors to invoke it directly.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, register allocations for `U1`, `U2`, `U3` (equal amounts, e.g., 100e18 each), fund contract with total (300e18).
2. Warp time to just before `periodsEndTime[4]`; have `U1` call `claim()` early (before period 4) so a nonzero `forfeited` amount accrues into `totalBonus`.
3. Warp time to `periodsEndTime[4]`.
4. Have `U2` call `claim()` - assert `totalEndRemainingAllocation` is set to `totalRemainingAllocation` at that point (`R0`), and record `U2`'s payout as baseline `bonus_R0`.
5. Reset state (or run a parallel scenario) and instead: after `U2` claims, have the attacker directly call `updateEndRemainingAllocation()` to force `totalEndRemainingAllocation` down to the post-`U2`-claim `totalRemainingAllocation` (`R1 < R0`).
6. Have `U3` call `claim()`; assert `U3`'s bonus (`alloc_U3 * totalBonus / R1`) is strictly greater than what it would have been under the un-manipulated snapshot (`alloc_U3 * totalBonus / R0`).
7. Assert that `sum(claimableAmount for U1, U2, U3-after-manipulation) > aidropToken.balanceOf(airdrop)` before `U3`'s transfer, or, with more claimants, assert a final legitimate claimant's `claim()` reverts with `InsufficientBalance` despite having a valid nonzero `allocations[user]`.
