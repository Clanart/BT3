## Title
Reflection-based Map field size/serialize inconsistency on duplicate wire-format entries — historically fixed, now enforced only by a `ABSL_CHECK`/crash guard - (File: `src/google/protobuf/message_lite.cc`, `src/google/protobuf/map_test.inc`)

## Summary
The Zebra advisory's failed invariant is that **two different counting routines over the same untrusted input diverge**: a legacy sigop counter and an "accurate" P2SH counter disagree on the same redeem script, and that divergence is trusted for a consensus-critical accept/reject decision, with no cross-check between the two counts. The strongest structural analog in this Protobuf checkout is the documented `map_int32_int32`/`MapFieldBase` class of bug where `ByteSizeLong()` computed the size from the **repeated-field view** of a map (which can contain duplicate keys) while `Serialize`/wire output used the **deduplicated map view**, producing a size computed by one code path that did not match the bytes produced by another path for the same attacker-influenced structure. Today this specific case is guarded by an `ABSL_CHECK` (`ByteSizeConsistencyError`) rather than fully architecturally eliminated, i.e. Protobuf turned an integrity-mismatch bug into a fail-fast/crash — the same shape of "two independent counters disagreeing over attacker data" that caused Zebra's consensus split, but Protobuf's mitigation converts it into an availability guard rather than a memory-safety or protocol-divergence issue.

## Finding Description
`MessageLite::SerializePartialToCodedStream` computes `size = ByteSizeLong()` on one pass and then serializes with `SerializeWithCachedSizes(output)` on a second, logically independent pass, finally asserting the two agree: [1](#0-0) 

If they disagree, `ByteSizeConsistencyError` is invoked, which `ABSL_CHECK`s and then `ABSL_LOG(FATAL)`s: [2](#0-1) 

The exact scenario that used to defeat this invariant is documented in the regression test for map fields: when a map field is marked `STATE_MODIFIED_REPEATED` (e.g., because reflection touched the underlying `RepeatedPtrField` representation and introduced duplicate keys), `ByteSizeLong()` used the **repeated-field representation** (which counts every entry, including duplicates) while `SerializeToString()`/parse-back used the **deduplicated map representation** — the same "two counting mechanisms produce different totals for the same attacker-shaped input" pattern as the Zcash sigop bug: [3](#0-2) [4](#0-3) 

The comment in the test explicitly states the historical failure mode: *"Protobuf used to have a bug for serialize when map is marked CLEAN. It used repeated field to calculate ByteSizeLong but use map to serialize the real data, thus the ByteSizeLong may bigger than real serialized size. A crash might be happen at SerializeToString(). Or an 'unexpected end group' warning was raised at parse back."*

This maps directly onto the external report's invariant: a consumer of untrusted, duplicate-key map entries (an ordinary client can construct a wire-format message with duplicate map keys, per `DuplicatedKeyWireFormat`/`DuplicateEntriesInWireFormatLastOneWins` tests) can put the internal map representation into a state where two size-computation code paths (repeated-field-based vs. map-based) disagree, exactly as zcashd/Zebra's two sigop-counting code paths disagreed on the same redeem script. [5](#0-4) [6](#0-5) 

The `Map`/`UntypedMapBase` "last-one-wins" merge semantics (`InsertOrReplaceNodes`, `InsertOrReplaceNode`) are the canonical, currently-used mechanism to collapse duplicate keys: [7](#0-6) [8](#0-7) 

## Impact Explanation
Unlike the Zcash report — where the miscounted total is the primary security-relevant output, causing a chain split — in Protobuf the divergent size computation is caught by an `ABSL_CHECK`/`FATAL` log at serialization time rather than silently causing a buffer overrun or acceptance/rejection divergence in a wire-format parser. That means the current, in-tree behavior is a **crash-on-mismatch (fail-closed) safety net**, not a silent corruption or a consensus-style accept/reject split. Under this repo's exclusion rules (no unbounded-allocation/resource-exhaustion/DoS-only claims, and crash-only findings are excluded unless they demonstrate corruption/disclosure/integrity failure beyond a controlled abort), this does not rise to a Critical/High vulnerability comparable to the reported one — it is the same *bug class* (dual, disagreeing counters over attacker-shaped data) but Protobuf's current mitigation removes the exploitable consequence, leaving only a guarded/fatal-log outcome for the specific repeated-vs-map size divergence.

## Likelihood Explanation
Constructing wire-format input with duplicate map keys is trivial for an ordinary client sending bounded binary Protobuf through `ParseFrom*`, as demonstrated by the existing test fixtures (`DuplicatedKeyWireFormat`, `DuplicateEntriesInWireFormatLastOneWins`). However, triggering the specific "map field marked STATE_MODIFIED_REPEATED then re-queried via `ByteSizeLong`" divergence additionally requires reflection-level manipulation (`RemoveLast` + `MergeFrom`) shown in the regression test, which is not something an ordinary remote-parsing client can induce purely via wire bytes without cooperating application code exercising the reflection API in a specific sequence. That significantly lowers the likelihood that an external attacker sending only bounded Protobuf bytes through a public parse API can reach the divergence today.

## Recommendation
No code change is proposed as an urgent fix based on current investigation, because:
1. The specific documented case (`map_test.inc:3811-3870`) is already covered by a regression test and an `ABSL_CHECK`-based fail-fast guard in `message_lite.cc`.
2. I was not able to fully verify, within the remaining investigation budget, whether an equivalent divergent-size path is reachable purely from `ParseFrom*` on bounded, attacker-controlled bytes without additional reflection-API usage by trusted application code (the `map_field.h`/`map_field.cc` `SyncRepeatedFieldWithMap`/`STATE_MODIFIED_REPEATED` state machine would need deeper tracing to confirm reachability from parse-only code paths).

If a background engineer wants to close the residual risk, the actionable next step is to audit `MapFieldBase`'s `SyncRepeatedFieldWithMap`/`SyncMapWithRepeatedField` state transitions (`src/google/protobuf/map_field.h`, `src/google/protobuf/map_field.cc`) to confirm no parse-only (no-reflection) sequence can leave the field in `STATE_MODIFIED_REPEATED` with duplicate keys at `ByteSizeLong()` time, and consider replacing the `ABSL_CHECK`/`FATAL` guard with a graceful `false`-returning failure path in `SerializePartialToCodedStream` so a crash isn't the only backstop.

// When serializing, we first compute the byte size, then serialize the message.
// If serialization produces a different number of bytes than expected, we
// call this function, which crashes.  The problem could be due to a bug in the
// protobuf implementation but is more likely caused by concurrent modification
// of the message.  This function attempts to distinguish between the two and
// provide a useful error message.
void ByteSizeConsistencyError(size_t byte_size_before_serialization,
                              size_t byte_size_after_serialization,
                              size_t bytes_produced_by_serialization,
                              const MessageLite& message) {
  ABSL_CHECK_EQ(byte_size_before_serialization, byte_size_after_serialization)
      << message.GetTypeName()
      << " was modified concurrently during serialization.";
  ABSL_CHECK_EQ(bytes_produced_by_serialization, byte_size_before_serialization)
      << "Byte size calculation and serialization were inconsistent.  This "
         "may indicate a bug in protocol buffers or it may be caused by "
         "concurrent modification of "
      << message.GetTypeName() << ".";
  ABSL_LOG(FATAL) << "This shouldn't be called if all the sizes are equal.";
}

bool MessageLite::SerializePartialToCodedStream(
    io::CodedOutputStream* output) const {
  const size_t size = ByteSizeLong();  // Force size to be cached.
  if (size > INT_MAX) {
    ABSL_LOG(ERROR) << GetTypeName()
                    << " exceeded maximum protobuf size of 2GB: " << size;
    return false;
  }

  int original_byte_count = output->ByteCount();
  SerializeWithCachedSizes(output);
  if (output->HadError()) {
    return false;
  }
  int final_byte_count = output->ByteCount();

  if (final_byte_count - original_byte_count != static_cast<int64_t>(size)) {
    ByteSizeConsistencyError(size, ByteSizeLong(),
                             final_byte_count - original_byte_count, *this);
  }

  return true;
}

  // If the key is a duplicate, it inserts the new node and deletes the old one.
  bool InsertOrReplaceNode(Arena* arena, KeyNode* node) {
    ABSL_DCHECK_EQ(arena, this->arena());

    bool is_new = true;
    auto p = this->FindHelper(node->key());
    map_index_t b = p.bucket;
    if (ABSL_PREDICT_FALSE(p.node != nullptr)) {
      EraseImpl(arena, p.bucket, static_cast<KeyNode*>(p.node),
                /*do_destroy=*/true);
      is_new = false;
    } else if (ResizeIfLoadIsOutOfRange(arena, num_elements_ + 1)) {
      b = BucketNumber(node->key());  // bucket_number
    }
    InsertUnique(b, node);
    ++num_elements_;
    return is_new;
  }
