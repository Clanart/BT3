### Title
`WombatPoolHelperV2.depositFor` hardcodes zero minimum liquidity, exposing depositors to sandwich/front-running loss - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor` calls `_deposit(_amount, 0, _for, address(this))`, hardcoding the `_minimumLiquidity` slippage parameter to `0` instead of accepting a caller-supplied minimum, unlike the sibling `deposit()` and `depositNative()` functions on the same contract which both take a user-supplied `_minimumLiquidity`.

### Finding Description
`WombatPoolHelperV2.deposit(uint256 _amount, uint256 _minimumLiquidity)` and `depositNative(uint256 _minimumLiquidity)` both forward a caller-chosen `_minimumLiquidity` down to `_deposit`, which passes it through `IWombatStaking.deposit(...)` and ultimately to the underlying `IWombatPool.deposit(token, amount, minimumLiquidity, to, deadline, shouldStake)` call. [1](#0-0) [2](#0-1) 

However, `depositFor` — which any ordinary wallet can call directly, and which is also invoked by `ManualCompound.compound` via the generic `ISimpleHelper.depositFor(uint256 _amount, address _for)` interface — hardcodes the minimum liquidity to `0`: [3](#0-2) [4](#0-3) 

Because `ISimpleHelper.depositFor` only exposes `(uint256 _amount, address _for)`, there is no way for a caller (or for `ManualCompound`) to supply any slippage protection for this Wombat pool deposit. This is the direct analog of the reported bug class: minting/depositing liquidity into an AMM pool "not considering the slippage" (`add_liquidity(amounts, 1)` in the original report), which allows an attacker to imbalance the Wombat pool (e.g., via a large swap immediately before the victim's deposit transaction) and cause the depositor to receive fewer LP/receipt tokens than expected, extracting value from the depositor.

### Impact Explanation
Any wallet calling `depositFor` directly, or depositing stablecoins through `ManualCompound.compound` (which routes converted reward tokens through `ISimpleHelper(_helperAddress).depositFor`), receives zero slippage protection on the Wombat pool deposit. An attacker monitoring the mempool can front-run the deposit by imbalancing the Wombat pool's cash/liability ratio (via a swap or another deposit/withdraw), causing the `deposit` call to mint fewer LP shares than the fair-value amount, then reverse the imbalance afterward (sandwich), profiting at the depositor's expense. This is a concrete extraction of value from the depositing user's funds during deposit.

### Likelihood Explanation
`depositFor` is a public, unprivileged, permissionless entry point reachable directly by any wallet and also reachable via the common `ManualCompound` auto-compounding flow, so the vulnerable path is exercised regularly in normal operation whenever users or the compounder route deposits through it. Any MEV searcher or attacker with mempool visibility can execute the sandwich with standard tooling, making this readily exploitable.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (and to the `ISimpleHelper.depositFor` interface / `ManualCompound` call site) so callers can specify their expected minimum LP output, mirroring the pattern already used in `deposit()` and `depositNative()`, and forward this to `IWombatStaking.deposit`/`IWombatPool.deposit` instead of hardcoding `0`.

### Proof of Concept
1. Attacker observes a pending `depositFor(_amount, _for)` transaction targeting `WombatPoolHelperV2`, e.g. sent as part of a `ManualCompound.compound(...)` call or directly by a user.
2. Attacker front-runs with a large swap/deposit against the same Wombat pool asset to imbalance `cash`/`liability`, worsening the deposit exchange rate.
3. Victim's `depositFor` executes with `_minimumLiquidity = 0` hardcoded at [3](#0-2) , so it cannot revert regardless of how unfavorable the resulting LP mint is.
4. Attacker reverses their position, capturing the value lost by the victim's under-minted LP/receipt tokens.
