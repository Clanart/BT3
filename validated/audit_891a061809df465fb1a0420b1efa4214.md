Given the constraints, the strongest defensible analog to the Electra "fixed-height assumption breaks after upgrade" bug is a similarly hardcoded, incomplete set-membership check in GitHub Desktop's Unicode bidi (Trojan Source) detection, which was specifically added as a security control and can be bypassed by using bidi control characters that fall outside the hardcoded ranges.

### Title
Incomplete `HiddenBidiCharsRegex` allows Trojan-Source Unicode bypass of the bidirectional-text warning - (File: app/src/lib/diff-parser.ts)

### Summary
GitHub Desktop added a dedicated security control (`hasHiddenBidiChars`) to warn users when a diff contains bidirectional Unicode control characters that can make code render differently than it actually is ("Trojan Source" attacks). The detection relies on a single hardcoded regex covering only two narrow Unicode ranges. Like the beacon-chain bug, where a fixed structural constant (`BEACON_STATE_TREE_HEIGHT`) silently stopped being a valid invariant, this fixed character-range assumption silently fails to cover other bidi control characters that produce the same visual-spoofing effect, defeating the warning it was built to provide.

### Finding Description
The detection regex is defined once and is the sole gate for the warning across the whole diff pipeline: [1](#0-0) 

It is used both for the initial parse of a diff and for any lines revealed later via hunk expansion: [2](#0-1) [3](#0-2) 

The resulting `hasHiddenBidiChars` boolean is the only signal driving the UI warning shown to the user before they review/stage/commit a change: [4](#0-3) [5](#0-4) 

`\u202A-\u202E` covers LRE/RLE/PDF/LRO/RLO and `\u2066-\u2069` covers LRI/RLI/FSI/PDI, but it omits other bidi/formatting control points that are also usable to reorder or hide displayed text relative to actual byte/character order (e.g. `U+200E` LRM, `U+200F` RLM, `U+061C` ALM), and any future Unicode-introduced bidi control code point. This is structurally the same class of bug as the report: a fixed, hardcoded set of "heights"/ranges is trusted as complete, and when the underlying alphabet of valid values is larger than what was hardcoded, the invariant silently breaks without an explicit error — the function just returns `false`/"no hidden chars" instead of throwing or failing safely.

### Impact Explanation
An attacker who controls a cloned/fetched repository (a fork, a PR branch, or any remote the user pulls from) can craft a file whose diff contains bidi control characters outside the two hardcoded ranges. Desktop will render the diff without the "This diff contains bidirectional Unicode text..." warning, so the reviewer/user has no indication that the visually-reviewed code differs from what will actually be compiled/executed after checkout — the classic Trojan Source deception. This can lead a maintainer to unknowingly merge/commit/push code whose real semantics differ from what was reviewed in Desktop, i.e. the user is misled about the actual content they are approving and committing.

### Likelihood Explanation
The attacker primitive required — crafting file content with alternate Unicode bidi control characters in a branch/fork the victim later views in Desktop — is fully within the "attacker controls a cloned/fetched repository" threat model and requires no local access, no elevated privileges, and no unusual user action beyond opening the Changes/diff view, which is the normal workflow for reviewing incoming changes.

### Recommendation
Do not enumerate a fixed hardcoded set of ranges as the sole detector. Use the canonical/complete list of Unicode Bidi_Control characters (or a maintained Unicode-property-based regex, e.g. `\p{Bidi_Control}` with the `u` flag) so that the check does not silently miss characters, and treat detection failures/unknowns conservatively (warn on ambiguity) rather than defaulting to "no hidden characters."

### Proof of Concept
1. Create a file in a repository whose diff line includes `U+200F` (RIGHT-TO-LEFT MARK) positioned to visually reorder a security-relevant token (e.g. making a `//` comment appear to comment out one line while it actually comments out another).
2. Push this to a branch/fork and have the victim fetch/check it out in GitHub Desktop.
3. Observe that `HiddenBidiCharsRegex.test(text)` in `app/src/lib/diff-parser.ts` returns `false` because `U+200F` is outside `[\u202A-\u202E]|[\u2066-\u2069]`, so `diff-contents-warning.tsx` never renders the bidi warning, even though the diff is visually deceptive.
