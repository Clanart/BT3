### Title
Fee and weight calculation omits the OP_RETURN data output, producing under-priced transactions - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/bsaldua/serai--019/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Astaria `createLien` bug — where the `maxPotentialDebt` check was evaluated against the debt *before* the new loan was added — `SignableTransaction::new` computes the transaction's weight, virtual size, minimum-relay-fee check, and `needed_fee` from `payments` only, *after* it has already appended the OP_RETURN data output to `tx_outs` but *without* including that output in the size calculation. The fee and standardness checks therefore validate a smaller transaction than the one that is actually built and signed.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the OP_RETURN output is pushed into `tx_outs` first (lines 193–202), and only afterwards are `(weight, vbytes)` and `needed_fee` computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204). `calculate_weight_vbytes` builds its template transaction solely from `payments` plus an optional change output — the `data` output is never passed in (lines 62–99). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` under-counts the true vsize by the size of the OP_RETURN output (up to ~86 bytes of data + ~9 bytes of output overhead for the maximum-allowed 80-byte payload, i.e. ~95 vbytes missing).
- The `TooLowFee` minimum-relay check (line 211) compares against this underestimated `vbytes`, so a `fee_per_vbyte` at the relay boundary can pass the check while the *real* transaction's effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE`.
- The change amount (line 228, `input_sat - payment_sat - fee_with_change`) is computed with `fee_with_change` that likewise excludes the data output, so change is over-credited and the actual fee `sum(inputs) - sum(outputs)` equals the under-estimated `needed_fee`, not the intended `fee_per_vbyte * actual_vsize`.
- The `TooLargeTransaction` standardness check (line 241) uses `weight` that excludes the data output, so a transaction at the boundary of `MAX_STANDARD_TX_WEIGHT` can pass while the final transaction is non-standard.

The processor's `make_signable_transaction` calls this constructor with `data: None`, so the issue only manifests for direct users of `SignableTransaction::new` who supply `data`; however `data` is fully attacker/user-controlled up to 80 bytes (`TooMuchData` check bounds it, but that bound itself is validated against the un-counted size model).

### Impact Explanation
An unprivileged caller can cause a SignableTransaction to be produced whose actual fee rate is lower than the `fee_per_vbyte` requested, and which can fall under Bitcoin's minimum relay fee or above `MAX_STANDARD_TX_WEIGHT` even though all internal checks passed. Such a transaction will be signed (the multisig signs what `SignableTransaction` builds) yet be non-relayable/non-standard, leaving the associated funds in an unspendable state until reconstructed. This is "funds reported/handled as spendable that are not", matching the accepted impact class; severity Medium.

### Likelihood Explanation
Requires a caller to pass `data` with a `fee_per_vbyte` near the relay minimum or a payment set near the weight limit. `data` is rarely used (the processor passes `None`), which lowers likelihood, but when used the miscalculation is deterministic — the data output is always omitted from the size model.

### Recommendation
Include the OP_RETURN output in the size model: build the data `TxOut` before calling `calculate_weight_vbytes` and pass the full output list (payments + optional data + optional change) into it, or add a `data_len` parameter to `calculate_weight_vbytes` so both `weight`/`vbytes` and `needed_fee` reflect the final transaction. Also re-check `TooLowFee` and `TooLargeTransaction` against the corrected values.

### Proof of Concept
```rust
// Construct inputs with value = payments + minimal fee
let payments = vec![(addr(), X)];
let data = vec![0u8; 80]; // max allowed, passes TooMuchData check

// fee_per_vbyte chosen exactly at the relay minimum boundary
let tx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte).unwrap();

// The real transaction contains the OP_RETURN output (~95 extra vbytes),
// but needed_fee was computed without it:
assert!(tx.tx.output.iter().any(|o| o.script_pubkey.is_op_return()));
// effective feerate = needed_fee / real_vsize < fee_per_vbyte,
// and can be < DEFAULT_MIN_RELAY_TX_FEE -> non-relayable once signed.
```
