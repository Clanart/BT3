## Title
Unbounded, unlimited `scan_accounts` full-index scan on `getProgramAccounts` allows single low-rate RPC call to degrade the JSON-RPC service - (File: `accounts-db/src/accounts_db.rs`, `accounts-db/src/accounts.rs`, `rpc/src/rpc.rs`)

## Summary
The C4 finding is about `VTVLVesting.sol`'s `vestingRecipients` array, which only ever grows (no removal mechanism), so the getter `allVestingRecipients()` eventually DoSes anyone who calls it. The Agave analog is the set of "live accounts owned by program X," which any unprivileged wallet can grow without bound by creating cheap accounts, combined with a `getProgramAccounts` code path that has *no* size/byte limit when the (optional, off-by-default) secondary `ProgramId` index is not configured — the exact same "growing collection + unbounded full retrieval" pattern.

## Finding Description
`JsonRpcRequestProcessor::get_filtered_program_accounts` branches on whether the validator has the `AccountIndex::ProgramId` secondary index enabled: [1](#0-0) 

- If the secondary index **is** configured, it goes through `get_filtered_indexed_accounts`, which is explicitly bounded by a `byte_limit_for_scan` (enforced via `accumulate_and_check_scan_result_size` in `accounts-db/src/accounts.rs`, and tested in `test_get_filtered_indexed_accounts_limit_exceeded`).
- If the secondary index is **not** configured — which is the default validator configuration; the `AccountIndex::ProgramId`/`SplTokenOwner`/`SplTokenMint` indexes are opt-in flags added via `--account-index`, per `validator/src/commands/run/args/account_secondary_indexes.rs` — the code takes the `else` branch with the comment: *"this path does not need to provide a mb limit because we only want to support secondary indexes."* It calls `bank.get_filtered_program_accounts`, which calls `Accounts::load_by_program_with_filter`: [2](#0-1) 

This in turn calls `AccountsDb::scan_accounts` with `ScanConfig::default()`: [3](#0-2) 

`scan_accounts` walks the *entire* accounts index (all live pubkeys visible from the bank's ancestors), loading each account from storage/cache, and only *after* loading applies the owner/filter predicate (`account.owner() == program_id && filter(account)`) inside `load_while_filtering`. There is no cap on the number of pubkeys scanned, no cap on bytes loaded, and no cap on the resulting `Vec` size — the only abort hook is `config.is_aborted()`, which is never set true in this default path.

The corrupted/uncontrolled value is the total live-account population of the bank (the `accounts_index`), which is directly analogous to `vestingRecipients`: any unprivileged user can grow it arbitrarily by submitting ordinary `CreateAccount`/`Allocate` transactions (rent-exempt account creation is cheap and permissionless), and there is no compaction/removal mechanism tied to `getProgramAccounts` — accounts persist until their owner explicitly closes them. Once the account population under some owner (or under `System::id()`, which nearly everyone touches) is large, a single `getProgramAccounts` RPC call forces the validator to synchronously scan and load the whole matching set inside a `spawn_blocking` task: [4](#0-3) 

## Impact Explanation
`getProgramAccounts` is a standard, unauthenticated, unprivileged JSON-RPC method exposed by any RPC-capable Agave validator. A single low-rate call from one client (no elevated privileges, no malicious peer/validator assumption) can force a full unbounded scan/load of the live-account set for a chosen owner. Because this executes as a blocking task on the RPC thread pool, a small number of such calls can exhaust the pool's blocking-thread capacity or hold it for an extended period, degrading or effectively denying service to legitimate RPC clients on that node — this matches the accepted impact category "single-client low-rate RPC crash/degradation." This is a local/per-node resource-exhaustion issue and does not affect consensus, but it directly parallels the C4 report's DoS-via-unbounded-collection pattern.

## Likelihood Explanation
Likelihood is high for nodes running with default secondary-index configuration (the common case, since account indexes are opt-in and impose their own memory overhead many operators avoid). Growing the underlying account population is cheap and fully permissionless — an attacker only needs to fund rent-exempt account creation, which is inexpensive at scale and does not require cooperation from any validator, peer, or admin. The vulnerable code path (the `else` branch with no `byte_limit_for_scan`) is reached automatically whenever the `ProgramId` index isn't set, so no special conditions or races are needed to trigger it — just growing the account set and issuing one `getProgramAccounts` call.

## Recommendation
Apply the same `byte_limit_for_scan` (or a pubkey/account-count cap) to the non-indexed `get_filtered_program_accounts` path that is already used for `get_filtered_indexed_accounts`, or require pagination/mandatory filters (e.g., `dataSize`, `memcmp`) before allowing a full scan when no secondary index exists, and reject/short-circuit scans whose accumulated result size exceeds the configured RPC response/memory bounds.

## Proof of Concept
1. Start a validator with default JSON-RPC config (no `--account-index program-id`).
2. From an unprivileged wallet, submit many cheap `CreateAccount` transactions assigning a large number of small, rent-exempt accounts to a chosen `program_id` (or simply rely on the natural growth of `System::id()`-owned accounts across the cluster).
3. Call `getProgramAccounts(program_id)` with no filters against the RPC node.
4. Observe that the call triggers `Accounts::load_by_program_with_filter` → `AccountsDb::scan_accounts`, which loads every live account in the index before filtering by owner, consuming a `spawn_blocking` thread and CPU/memory proportional to the *entire* live account set rather than just the matching accounts — degrading response time for concurrent RPC requests on that node, as demonstrated functionally by `test_rpc_get_program_accounts` in `rpc/src/rpc.rs` (correctness only, no bound is exercised) contrasted with the bound enforced in `test_get_filtered_indexed_accounts_limit_exceeded` in `runtime/src/bank/tests.rs`, which only applies to the indexed path. [5](#0-4)

    pub(crate) fn scan_accounts<F>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        mut scan_func: F,
        config: &ScanConfig,
    ) -> ScanResult<()>
    where
        F: FnMut(Option<(&Pubkey, AccountSharedData, Slot)>),
    {
        // Register this scan so that slots needed by the scan are not cleaned out from under us.
        let scan_guard = ScanGuard::try_new(&self.scan_tracker, bank_id, || self.max_root())
            .ok_or(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            })?;

        // If the scan's ancestors are all rooted, drop them and scan roots only
        // Scan Guard max root must be used as the scan guard guarantees that
        // the account state as of max root is persisted in the database
        let max_root_ancestors = Ancestors::from(vec![scan_guard.max_root()]);
        let ancestors = if scan_guard.should_use_ancestors(ancestors) {
            ancestors
        } else {
            &max_root_ancestors
        };

        // Step 1: Pre-scan the cache index to find the newest visible cached version of each
        // pubkey. Hold the Arc<CachedAccount> to keep the data alive even if the cache flushes
        // between now and step 3 (Arc clone is just a refcount bump).
        let cached_pubkeys = self.accounts_cache.cached_pubkeys();
        let mut cached_versions =
            HashMap::with_capacity_and_hasher(cached_pubkeys.len(), PubkeyHasherBuilder::default());
        for pubkey in cached_pubkeys {
            if config.is_aborted() {
                break;
            }

            if let Some((cached_account, slot)) =
                self.accounts_cache.load_latest(&pubkey, ancestors)
            {
                cached_versions.insert(pubkey, (cached_account, slot));
            }
        }

        // Step 2: Scan the accounts_index. For each pubkey, return the newest version found in
        // either the storage or the cache. If both versions are the same, use the cached version
        // to avoid a redundant load from storage.
        // Bound max_root by ancestors.min_slot() so that roots from slots
        // beyond the querying bank's ancestor chain are not visible.
        let mut max_root = scan_guard.max_root();
        if let Some(min) = ancestors.min_slot() {
            max_root = max_root.min(min);
        }
        self.accounts_index.scan_accounts(
            ancestors,
            max_root,
            |pubkey, (account_info, slot)| {
                if let Some((cached_account, cache_slot)) = cached_versions.remove(pubkey)
                    && cache_slot >= slot
                {
                    scan_func(Some((pubkey, cached_account.account.clone(), cache_slot)));
                    return;
                }

                let mut account_accessor =
                    self.get_account_accessor(slot, &account_info.storage_location());

                let account_slot = account_accessor.get_loaded_account(|loaded_account| {
                    (pubkey, loaded_account.take_account(), slot)
                });
                scan_func(account_slot)
            },
            config,
        );

fn test_get_filtered_indexed_accounts_limit_exceeded() {

            ..ACCOUNTS_DB_CONFIG_FOR_TESTING

        &genesis_config,

        vec![],
