### Title
Client-side repo-rule enforcement silently drops unrecognized/unhandled rule types, allowing commits that violate server-side push rules to appear unwarned - (File: `app/src/lib/helpers/repo-rules.ts`)

### Summary
`parseRepoRules` in [1](#0-0)  converts the GitHub API's list of repo rules into an internal `RepoRulesInfo` object that Desktop uses to warn users before they commit/push in violation of server-side branch/repo rules. The conversion is done via a `switch (rule.type)` statement that only recognizes a fixed set of `APIRepoRuleType` cases [2](#0-1) . Any rule type returned by the API that isn't one of those explicit `case` branches falls through the switch with no `default` handling and is silently discarded — the same class of bug as the audited Solidity code, where `DAOType.PRIVATE` is defined but never has enforcement logic wired in, so it silently behaves like `PUBLIC`.

### Finding Description
The invariant that should hold is: "every repo rule reported by GitHub's API results in Desktop warning the user before they violate it." The `switch` statement in `parseRepoRules` [2](#0-1)  only has cases for `Update`, `RequiredDeployments`, `RequiredStatusChecks`, `Creation`, `RequiredSignatures`, `PullRequest`, `CommitMessagePattern`, `CommitAuthorEmailPattern`, `CommitterEmailPattern`, and `BranchNamePattern`. There is no `default` branch, so any rule type not explicitly enumerated (whether a rule type added to the GitHub API after this code was written, or one that Cyfrin-style auditors would call "the unhandled case") is silently ignored — same failure mode as the `DAOType.PRIVATE` case in the original report, which is defined but has no code path enforcing it.

`useRepoRulesLogic` [3](#0-2)  is also worth noting: it purposely returns `true` (rules might exist) for repos owned by someone else even when it can't check their plan, which is a deliberately conservative default. But the corresponding data-population function (`parseRepoRules`) does not carry the same "unknown → be conservative" philosophy; unknown/unhandled rule types are dropped rather than surfaced as a generic warning.

I additionally found `isBranchPushable` in [4](#0-3) , which has a similar "fail open" pattern: `return allow_actor !== false && noMergeRequirements` — if `allow_actor` is `undefined` (not explicitly `false`), the user is treated as allowed to push. The comment at lines 46-48 explicitly acknowledges this is an intentional fail-open decision in case the API removes/renames the field. I was not able to fully trace all three call sites in `app-store.ts` to confirm whether this fail-open path is reachable with attacker-influenced data (e.g., a malicious/compromised GitHub Enterprise Server or a man-in-the-middle proxy returning a push-control response missing `allow_actor`), so I cannot confirm this is exploitable versus purely defensive.

### Impact Explanation
For `parseRepoRules`, if the GitHub API (or a malicious GitHub Enterprise Server that a user's Desktop is pointed at) returns a rule type not present in the switch, Desktop will not add any entry to `RepoRulesInfo`, meaning the corresponding UI warning ("this commit will violate a repo rule") never appears. The user could commit/push content believing there is no rule in effect, when in fact server-side enforcement would reject it (or, worse, if enforcement is client-side-only for some check, the corruption is silent). This maps to the original report's impact: a restriction category exists in name but has no enforcement path in the client, misleading the user into believing they aren't restricted.

### Likelihood Explanation
Likelihood is dependent on the attacker's ability to control the API response — e.g., a compromised or malicious GitHub Enterprise Server instance, or a MITM against the connection if certificate validation were bypassed. I was unable to fully confirm reachability/attacker control conditions within the remaining tool budget, so likelihood should be treated as uncertain pending further verification (e.g., checking whether `rule.type` values are validated against the enum before reaching `parseRepoRules`, and whether GHES rule sets can introduce new/custom types).

### Recommendation
Add a `default` case to the `switch` in `parseRepoRules` that surfaces a generic "unknown rule may apply" warning rather than silently dropping unrecognized rule types, so the fail-safe direction matches `useRepoRulesLogic`'s conservative "assume rules might exist" behavior. Similarly, reconsider whether `isBranchPushable`'s fail-open default (`allow_actor !== false`) should instead fail closed when the field is absent, given the stated uncertainty about why it could be missing.

export function useRepoRulesLogic(
  account: Account | null,
  repository: Repository
): boolean {
  if (
    !account ||
    !repository ||
    !isRepositoryWithGitHubRepository(repository)
  ) {
    return false
  }

  const { endpoint, owner, isPrivate } = repository.gitHubRepository

  if (!supportsRepoRules(endpoint)) {
    return false
  }

  // repo owner's plan can't be checked, only the current user's. purposely return true
  // if the repo owner is someone else, because if the current user is a collaborator on
  // the free plan but the owner is a pro member, then repo rules could still be enabled.
  // errors will be thrown by the API in this case, but there's no way to preemptively
  // check for that.
  if (
    account.login === owner.login &&
    (!account.plan || account.plan === 'free') &&
    isPrivate
  ) {
    return false
  }

  return true
}

export async function parseRepoRules(
  rules: ReadonlyArray<IAPIRepoRule>,
  rulesets: ReadonlyMap<number, IAPIRepoRuleset>,
  repository: Repository
): Promise<RepoRulesInfo> {
  const info = new RepoRulesInfo()
  let gpgSignEnabled: boolean | undefined = undefined

  for (const rule of rules) {
    // if a ruleset is null/undefined, then act as if the rule doesn't exist because
    // we don't know what will happen when they push
    const ruleset = rulesets.get(rule.ruleset_id)
    if (ruleset == null) {
      continue
    }

    // a rule may be configured multiple times, and the strictest value always applies.
    // since the rule will not exist in the API response if it's not enforced, we know
    // we're always assigning either 'bypass' or true below. therefore, we only need
    // to check if the existing value is true, otherwise it can always be overridden.
    const enforced =
      ruleset.current_user_can_bypass === 'always' ? 'bypass' : true

    switch (rule.type) {
      case APIRepoRuleType.Update:
      case APIRepoRuleType.RequiredDeployments:
      case APIRepoRuleType.RequiredStatusChecks:
        info.basicCommitWarning =
          info.basicCommitWarning !== true ? enforced : true
        break

      case APIRepoRuleType.Creation:
        info.creationRestricted =
          info.creationRestricted !== true ? enforced : true
        break

      case APIRepoRuleType.RequiredSignatures:
        // check if the user has commit signing configured. if they do, the rule
        // passes and doesn't need to be warned about.
        gpgSignEnabled ??=
          (await getBooleanConfigValue(repository, 'commit.gpgsign')) ?? false

        if (gpgSignEnabled !== true) {
          info.signedCommitsRequired =
            info.signedCommitsRequired !== true ? enforced : true
        }
        break

      case APIRepoRuleType.PullRequest:
        info.pullRequestRequired =
          info.pullRequestRequired !== true ? enforced : true
        break

      case APIRepoRuleType.CommitMessagePattern:
        info.commitMessagePatterns.push(toMetadataRule(rule, enforced))
        break

      case APIRepoRuleType.CommitAuthorEmailPattern:
        info.commitAuthorEmailPatterns.push(toMetadataRule(rule, enforced))
        break

      case APIRepoRuleType.CommitterEmailPattern:
        info.committerEmailPatterns.push(toMetadataRule(rule, enforced))
        break

      case APIRepoRuleType.BranchNamePattern:
        info.branchNamePatterns.push(toMetadataRule(rule, enforced))
        break
    }
  }

  return info
}

export function isBranchPushable(pushControl: IAPIPushControl) {
  const {
    allow_actor,
    required_status_checks,
    required_approving_review_count,
  } = pushControl

  // See https://github.com/desktop/desktop/issues/9054#issuecomment-582768322
  // We'll guard against this being undefined until we can determine the
  // root cause and fix that.
  const requiredStatusCheckCount = Array.isArray(required_status_checks)
    ? required_status_checks.length
    : 0

  // If user is admin and branch is not admin-enforced,
  // required status checks and reviews get zeroed out in API response (no merge requirements).
  // If user is admin and branch is admin-enforced,
  // required status checks and reviews do NOT get zeroed out in API response.
  // If user is allowed to push based on `Restrict who can push` setting, they must still
  // respect the merge requirements, and can't push if checks or reviews are required for merging
  const noMergeRequirements =
    requiredStatusCheckCount === 0 && required_approving_review_count === 0

  // We check for !== false so that if a future version of the API decides to
  // remove or rename that property we'll revert to assuming that the user
  // _does_ have access rather than assuming that they _don't_.
  return allow_actor !== false && noMergeRequirements
}
