### Title
Unauthenticated deposits to internal offset addresses are scanned as spendable `ReceivedOutput`s, inflating the tracked balance — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The original Napier issue: `requestWithdrawalAll` calls `STETH.balanceOf(address(this))`, so an attacker's direct donation inflates the amount the contract accounts as its own. The analog in Serai is `Scanner::scan_transaction`, which credits *any* on-chain output paying to a registered script_pubkey — including the internally-reserved `Branch`, `Change`, and `Forwarded` offset addresses — as a spendable `ReceivedOutput`, with no distinction between legitimate deposits and unsolicited "donations" to addresses that were never meant to receive external funds.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping every registered offset's P2TR script to its scalar offset [1](#0-0) . `scan_transaction` emits a `ReceivedOutput` for any tx output whose `script_pubkey` is in that map [2](#0-1) . All offset scripts are deterministic and publicly derivable: `p2tr_script_buf(key + GENERATOR * offset)` is a pure function of the group key and offset [3](#0-2) . In the processor, the `Branch`, `Change`, and `Forwarded` offsets are fixed `hash_to_F` values (`b"branch"`, `b"change"`, `b"forward"` under `KEY_DST`), so anyone can compute those addresses [4](#0-3) . `get_outputs` scans every non-coinbase tx, tags each match by offset kind, and pushes it as a balance-bearing `Output` — a payment a third party sends to the change or forward address is reported identically to internally-created change [5](#0-4) .

### Impact Explanation
Like the stETH donation, an unprivileged attacker can inflate the multisig's reported balance by sending arbitrary outputs to the `Change`/`Forwarded`/`Branch` addresses. These outputs are real and spendable, but they pollute the internal accounting: outputs marked `OutputType::Change` or `Forwarded` bypass the deposit path (no `InInstruction` data attached — data is only copied to `External` outputs [6](#0-5) ), yet are fed to the scheduler as available funds. This can desynchronize expected liquidity, trigger eventuality-completion logic, or cause the scheduler to plan spends around funds the protocol never accounted as deposits.

### Likelihood Explanation
Any external party can compute the branch/change/forward P2TR addresses from the public group key and the fixed hashed offsets, and send a transaction paying to them. No special access is needed — this is exactly the "direct transfer" reachability of the original report.

### Recommendation
Track which offset addresses are expected to receive funds independently of raw script matching — e.g., only treat `Change`/`Branch`/`Forwarded` outputs as valid when produced by transactions the multisig itself signed (verify `tx.input` spends a known output, or maintain an expected-txid set), and quarantine or reclassify unsolicited payments to internal offsets rather than crediting them as `Change`/`Forwarded`.

### Proof of Concept
1. Observe the multisig group key `K` (public on-chain).
2. Compute `change_addr = p2tr_script_buf(K + G * hash_to_F(KEY_DST, b"change"))` — a fixed, public derivation.
3. Broadcast a transaction paying `change_addr`.
4. `get_outputs` returns it as `Output { kind: OutputType::Change, .. }`; the scanner emits it in `ScannerEvent::Block` and it is saved via `save_outputs` as a spendable balance, inflating tracked funds without any deposit instruction.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
