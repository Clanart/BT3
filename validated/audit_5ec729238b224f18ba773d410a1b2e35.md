## Analysis

The core of the original Sherlock finding is that a state-changing account "recovery"/"exit" action trusts an externally-supplied destination and silently moves the user's assets there once the normal guard (`whenNotPaused`) is bypassed by design. The applicable Desktop-analog invariant is: **Desktop must not silently rewrite the user's trusted git remote to a location controlled by an untrusted party** without a positive user action.

That invariant is broken in `updateRemoteUrl`.### Title
Silent, unconfirmed rewrite of a repository's git remote based on an untrusted API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` is invoked automatically every time Desktop refreshes a repository's associated GitHub metadata (`repositoryWithRefreshedGitHubRepository` in `app-store.ts`, called during normal repository refresh flows). If the GitHub API response for `GET /repos/{owner}/{name}` returns a `clone_url` that differs from what Desktop has on record, and the URL scheme (`http`/`ssh`) hasn't changed, Desktop silently rewrites the repository's `origin` remote with `git remote set-url` — with no confirmation dialog, no hostname/owner verification, and no user awareness. This mirrors the underlying bug class in the seed report: a codepath that moves a user's "funds" (here, the destination of every future `push`/`fetch`) to an address supplied by another party, while the ordinary UI never signals that anything happened.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` (lines 4874–4914) fetches repository data from the API and unconditionally calls: [1](#0-0) 

That call flows into `updateRemoteUrl`: [2](#0-1) 

The only checks performed before overwriting the remote are:
1. That the *scheme* (https vs ssh) of the new URL matches the old one (`protocolsMatch`).
2. That the *previous* remote URL still matched the *last known* `cloneURL` Desktop stored for that `GitHubRepository` record (`remoteUrlUnchanged`) — i.e., a check that only prevents overwriting a URL the user manually customized, not a check that the new URL is safe. [3](#0-2) 

Crucially, there is **no verification that the new `clone_url`'s hostname/owner/repo matches the account's expected endpoint**, and `gitStore.setRemoteURL` is invoked directly via `git remote set-url`: [4](#0-3) [5](#0-4) 

The attacker-controlled surface is the GitHub API object (`IAPIRepository`/`IAPIFullRepository.clone_url`) returned by the configured endpoint — this is squarely within the accepted "GitHub API object" / "git remote or proxy response" attacker model. A user connected to a GitHub Enterprise Server instance whose network path or server is compromised/malicious (or any scenario where the `repos/{owner}/{name}` response can be tampered with, e.g., a rogue/MITM proxy terminating TLS for that specific enterprise host) can return an arbitrary `clone_url` pointing at an attacker-controlled git host with the same scheme. On the next periodic refresh (which happens routinely, e.g. on repository selection, background refresh, PR checks, etc.), Desktop will silently `git remote set-url origin <attacker-url>` with zero user interaction or notification.

### Impact Explanation
Once the `origin` remote is silently repointed:
- Every subsequent `git push` by the user is sent to the attacker's git server instead of the real repository — the commit history and any secrets/code in it are exfiltrated to the attacker, and the user has no visual indication the destination changed (the UI still shows the same repository name/association).
- Every subsequent `git fetch`/`pull` retrieves content from the attacker's server, allowing the attacker to inject malicious commits/branches that the user then believes originate from their trusted GitHub repository — a silent corruption of what the user is working with.
- Because Desktop's credential trampoline (`app/src/lib/trampoline/trampoline-credential-helper.ts`) resolves credentials by matching the *current remote URL's* endpoint against known accounts, redirecting the remote to an unrecognized host causes Desktop to fall back to generic credential handling and can prompt the user for a username/password against the attacker's host, risking credential exfiltration: [6](#0-5) 

This satisfies the "silent corruption of what the user commits or pushes" / "credential exfiltration" criteria in the accepted impact list, without requiring local access, admin rights, or social engineering — only control over the API response for an already-connected endpoint.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control or tamper with the API response of an endpoint the victim already trusts (most plausible on self-hosted GitHub Enterprise Server deployments with a compromised server, misconfigured/legacy TLS, or a MITM position on that specific host — dotcom's TLS pinning/CA validation makes this harder there). The `repositoryWithRefreshedGitHubRepository` path is exercised routinely during normal app usage (not a rare or user-initiated corner case), so once the attacker can spoof a single API response, no further user interaction is needed for the remote to be silently rewritten.

### Recommendation
- Never silently rewrite an existing remote URL based on API data. At minimum, require explicit user confirmation (a dialog naming the old and new URL) before calling `setRemoteURL`.
- Validate that the new `clone_url`'s hostname matches the expected account endpoint's hostname before considering it a legitimate rename, rather than only checking that the URL scheme didn't change.
- Consider treating a mismatched hostname as a signal to warn the user rather than an authoritative update.

### Proof of Concept
1. User adds/clones a repository hosted on a GitHub Enterprise Server instance and it becomes a `RepositoryWithGitHubRepository` with the current, correct remote URL matching `gitHubRepository.cloneURL`.
2. Attacker gains the ability to tamper with the `GET /repos/{owner}/{name}` API response for that GHE endpoint (e.g., malicious/compromised GHE admin, or a MITM position for that hostname), returning a JSON body identical to the real repository except `clone_url` set to `https://attacker-server.example/owner/name.git` (same `https` scheme as before, so `protocolsMatch` passes).
3. On the next background/periodic refresh, `repositoryWithRefreshedGitHubRepository` runs, calls `updateRemoteUrl`, finds `protocolsMatch === true`, `remoteUrlUnchanged === true` (user never manually edited the remote), and `urlsMatch === false` — triggering `gitStore.setRemoteURL('origin', 'https://attacker-server.example/owner/name.git')`.
4. Desktop's UI shows no dialog, warning, or diff; the repository still appears associated with the same GitHub repository. All future pushes/fetches now go through the attacker's server, and Desktop's credential trampoline may prompt for generic credentials against the new host.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)
```

```typescript
  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
```
