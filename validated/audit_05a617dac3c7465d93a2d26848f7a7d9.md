Based on the code, I found a direct local analog to the reported bug class: an unrestricted "core execution" contract that a wrapper is *supposed* to gate, but which is fully callable by anyone.

### Title
`CallDispatcher.dispatch()` has no access control — any address can directly invoke the shared dispatcher used by IntentGatewayV2 to move escrowed order funds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`IntentGatewayV2` (and `IntentsBase`) routes all predispatch/postdispatch order calldata through a single shared `CallDispatcher` contract, transiently parking user/solver tokens (and ETH) on it while executing swap/composability calldata before sweeping the tracked tokens back. `CallDispatcher.dispatch(bytes)` is `external` with **no modifier whatsoever** — no `onlyGateway`, no `restrict`, nothing — so it is exactly as unauthenticated as `AlignedLayerServiceManager.createNewTask()` was in the source report relative to `BatcherPaymentService`. The gateway's escrow-accounting invariants (only tracked input/output tokens get swept back; only entitled users/solvers get funds) hold only as long as callers reach the dispatcher exclusively through the gateway's own bookkeeping. Because `dispatch()` is public, anyone can call it directly.

### Finding Description
`CallDispatcher.dispatch()`: [1](#0-0) 

blindly ABI-decodes an attacker-supplied `Call[]` and executes each entry with `dispatcher` as `msg.sender`, sending along `call.value` and arbitrary `call.data` to any contract-holding address, using whatever native/ERC20 balance the dispatcher currently holds.

`IntentGatewayV2`/`IntentsBase` treats this contract as a trusted, single shared instance (`_params.dispatcher`) and temporarily transfers real user/solver funds onto it during order placement and fill:
- Predispatch: assets are pushed to `dispatcher`, then `dispatch(order.predispatch.call)` runs, and only the amounts corresponding to `order.inputs[...]` are pulled back via a second `dispatch(transferCalls)` call: [2](#0-1) 
- Postdispatch/fill: solver output tokens are sent to the dispatcher as `beneficiary`, `_execute()` runs the order's `output.call`, and only known `outputsLen` tokens are swept back as dust: [3](#0-2) 

Both sweep steps only recover balances for the *specific tokens the gateway already knows about* (`order.inputs[i].token` / `order.output.assets[i].token`). Any other asset that ends up on the dispatcher — an intermediate hop token from a multi-step swap encoded in `predispatch.call`/`output.call`, leftover approvals, or native ETH accepted via `receive()` — is never automatically swept, and remains sitting on this single, protocol-wide, permissionless contract indefinitely. Because `dispatch()` has no caller restriction, any unprivileged address can construct its own `Call[]` (e.g., `{to: strandedToken, value: 0, data: transfer(attacker, strandedToken.balanceOf(dispatcher))}` or simply `{to: attacker, value: address(dispatcher).balance, data: ""}`) and call `CallDispatcher.dispatch()` directly to move that balance to itself — completely bypassing the `IntentGatewayV2` accounting/dust/treasury-sweep model that assumes it is the only caller. This mirrors the bug-report's exact broken invariant: a supposedly "gated" execution surface (`createNewTask` / here `dispatch`) is in fact a public, unauthenticated entry point with no binding to the intended caller (`BatcherPaymentService` / here `IntentGatewayV2`).

### Impact Explanation
Any tokens or ETH stranded on the shared `CallDispatcher` — whether from swap slippage/dust, an intermediate-hop token not enumerated in `order.inputs`/`order.output.assets`, or native ETH sent to its `receive()` — can be stolen outright by any unprivileged caller invoking `dispatch()` directly, redirecting funds to an arbitrary address instead of their rightful destination (the order's user/beneficiary, the solver, or the protocol treasury via governance sweep). This is a direct "stealing or loss of funds" / "unauthorized execution" impact against escrowed order funds handled by `IntentGatewayV2`.

### Likelihood Explanation
No privileged actor, relayer, or malicious peer is required — any EOA can call `CallDispatcher.dispatch()` at any time it holds a nonzero balance. The likelihood of the dispatcher holding a stealable balance depends on order flows that leave non-tracked tokens/ETH on it (multi-hop predispatch/postdispatch swaps, fee-on-transfer tokens, slippage), which the codebase's own tests demonstrate are realistic and already exercised (e.g. Uniswap swap calldata routed through `dispatcher` in `IntentGatewayV2Test.sol`).

### Recommendation
Restrict `CallDispatcher.dispatch()` to the intended caller(s) — e.g., add an `onlyGateway`/`restrict(gateway)` modifier bound at construction/config time, or make each `IntentGatewayV2` deploy its own dedicated dispatcher instance instead of sharing one public, unauthenticated contract. Additionally, ensure every use of the dispatcher fully sweeps *all* balances it could plausibly hold (not just the tokens explicitly enumerated in the order) back to the gateway within the same transaction, so no exploitable residual balance can persist between calls.

### Proof of Concept
1. A user places an order with `predispatch.call` containing a multi-hop swap (e.g., TokenA → TokenB → TokenC) where only TokenC is declared as `order.inputs[0].token`; TokenB, an intermediate hop token, is left on the `CallDispatcher` due to slippage/rounding.
2. `IntentGatewayV2.placeOrder` only sweeps TokenC back via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` (see [4](#0-3) ); the residual TokenB balance remains on `dispatcher`.
3. Any external address (no relation to the order) calls `CallDispatcher.dispatch(abi.encode([Call({to: TokenB, value: 0, data: transfer(attacker, dispatcher.balanceOf(TokenB))})]))` directly — this succeeds because `dispatch()` in [1](#0-0)  has no caller restriction — draining the stranded TokenB to the attacker instead of it being collected as protocol dust.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
