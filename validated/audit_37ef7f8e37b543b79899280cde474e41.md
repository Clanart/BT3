### Title
Invalid `EncryptedMessage` with non-canonical share forces ECDH blame-key reveal before the proof-of-possession is ever verified, re-enabling the key-copy attack the PoP exists to prevent - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
A malicious DKG participant can replay another sender's per-message encryption key inside an `EncryptedMessage` whose ciphertext decrypts to a non-canonical scalar. `KeyMachine::calculate_share` decrypts the message and generates the blame `EncryptionKeyProof` (which contains the recipient's ECDH shared key) *before* the queued PoP batch verification runs. When `C::F::from_repr` fails, the function returns early with `blame: Some(...)`, permanently skipping `batch.verify_with_vartime_blame()`. The victim therefore publishes the ECDH key that decrypts an honest participant's secret-share message — the exact attack the PoP in `EncryptedMessage` was added to stop.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` loops over received shares: it calls `self.encryption.decrypt(...)`, which only *queues* the PoP (`msg.pop.batch_verify`) and immediately returns the plaintext plus an `EncryptionKeyProof` containing `key = ecdh(self.enc_key, msg.key)` (`encryption.rs:469-501`). Immediately after, the share is canonicalized: [1](#0-0) 

If `from_repr` fails, `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` is returned via `?` — before `batch.verify_with_vartime_blame()` at line 493 is reached. The queued PoP verification is dropped entirely. Yet the returned blame proof is precisely the material the protocol publishes to let third parties decrypt the message (`spec/cryptography/Distributed Key Generation.md`, `decrypt_with_proof` at `encryption.rs:366-397` accepts the revealed `key` after only checking a DLEq against `enc_keys[decryptor]`).

The code comments themselves document this attack class: an Eve who "observes Alice encrypt to Bob with key X, then send[s] Bob a message also claiming to use X" causes Bob's blame to "reveal bX, revealing Alice's message to Bob" (`encryption.rs:83-91`). The PoP binds `key`, `sender`, and `msg` (`pop_challenge`, `encryption.rs:302-324`) — but only if it is actually verified. The early error path returns the ECDH-key-revealing blame while the PoP sits unverified in the abandoned `BatchVerifier`.

### Impact Explanation
Eve copies `msg.key = X` from Alice's `EncryptedMessage` to Bob (visible on the authenticated channel), attaches any garbage `pop`, and supplies ciphertext bytes that decrypt to a non-canonical scalar (with overwhelming probability for random garbage; ~7/8 of random 32-byte strings exceed the Ristretto/ed25519 group order). Bob's `calculate_share` returns a blame proof exposing `bX`, the ECDH key for Alice's message. Once Bob or the coordinator publishes that blame, Eve decrypts Alice's secret share to Bob, recovering a FROST secret-share contribution — concrete key-share material leakage reachable by an unprivileged protocol participant sending crafted `EncryptedMessage` bytes to `calculate_share`. This mirrors the advisory's shape exactly: secret material (the ECDH decryption key) is released before the trust/authenticity check (PoP verification) completes.

### Likelihood Explanation
Any DKG participant can observe `EncryptedMessage`s on the channel and craft the malicious message locally; no collusion, no honest-behavior dependence, and the non-canonical-ciphertext condition is trivially satisfiable by brute-force over random ciphertext bytes (each attempt is a fresh message in a new/retried DKG attempt or targets distinct victims). The only requirement is that blame proofs are published, which is their designed purpose.

### Recommendation
Verify the PoP before returning or deriving any blame material: either perform `msg.pop.verify` inline in `Encryption::decrypt` (or a pre-pass in `calculate_share`) and only produce an `EncryptionKeyProof` for messages whose PoP is valid, or withhold `blame` (return `blame: None`, as already done for `BatchId::Decryption` failures) whenever the PoP batch was not fully verified. Additionally, treat non-canonical share bytes as a decryption-layer fault attributable to the sender without revealing the ECDH key until the PoP is confirmed.

### Proof of Concept
1. Alice runs the PedPoP DKG with participants including Bob and Eve. Alice's `generate_secret_shares` emits `EncryptedMessage { key: X, pop, msg }` destined for Bob on the authenticated channel; Eve observes `X`.
2. Eve constructs `EncryptedMessage { key: X, pop: garbage_signature, msg: c }` where `c` is random 32 bytes such that Bob's decryption `c XOR keystream` is not a canonical scalar (retry until so — succeeds with probability ~7/8 per guess).
3. Eve submits this as her share message to Bob. In `calculate_share` (`lib.rs:476-482`), `decrypt` queues the invalid PoP, computes `key = bob_enc_key * X`, decrypts to a non-canonical value, and `from_repr` fails → returns `InvalidShare { participant: eve, blame: Some(EncryptionKeyProof{ key: bX, dleq }) }`.
4. The blame proof is published. `AdditionalBlameMachine::blame` / `decrypt_with_proof` verifies the DLEq (valid — Bob honestly generated it) and reveals `bX`; Eve uses `bX` in `cipher(context, bX)` to decrypt Alice's real `msg`, recovering Alice's secret share to Bob — despite Eve never knowing the discrete log of `X` and the PoP never having been verified.
