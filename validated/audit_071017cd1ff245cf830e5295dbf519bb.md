### Title
Unconditional minimum-fee enforcement rejects transactions whose leftover value would already satisfy the relay fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the reference bug — where `_migrateTo` unconditionally applies deposit/borrow pause checks and calls `_postDeposit` even when no deposit/borrow occurs, DoSing legitimate debt-only or collateral-only migrations — `SignableTransaction::new` in bitcoin-serai unconditionally enforces the declared `fee_per_vbyte`-derived `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE` *before* computing the actual fee the transaction will pay (`sum(inputs) - sum(outputs)`). When no change output is created, all leftover input value becomes the fee; a transaction built with a low declared fee rate but a large leftover would still pay above the minimum relay fee, yet is rejected with `TransactionError::TooLowFee`.

### Finding Description
In `SignableTransaction::new`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
// Technically, if there isn't change, this TX may still pay enough of a fee to pass the
// minimum fee. Such edge cases aren't worth programming when they go against intent, as the
// specified fee rate is too low to be valid
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

The code itself acknowledges the flaw in the comment: the check uses the *declared* fee rate, not the *actual* fee. When `change.is_none()` (or the change value falls below dust and is dropped at lines 224-235), the entire `input_sat - payment_sat` remainder becomes the fee. That remainder can be arbitrarily large and comfortably above `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, yet the transaction is rejected solely because `fee_per_vbyte` was low — exactly the pattern of enforcing a condition that doesn't apply to the operation actually being performed.

The same over-enforcement pattern appears in the fund check `input_sat < payment_sat + needed_fee`: `needed_fee` is a floor, but the code treats it as the exact required surplus, ignoring that a larger leftover is fine.

### Impact Explanation
Any caller constructing a `SignableTransaction` (e.g., `processor/src/networks/bitcoin.rs::make_signable_transaction`, which feeds user-requested `payments` and UTXO `inputs`) can hit `TooLowFee` on a transaction that would be relay-valid, or `NotEnoughFunds` even though the inputs cover payments plus an adequate actual fee. In the processor, `TransactionError::TooLowFee` and `TooLargeTransaction` are treated as unreachable (`panic!`), turning this over-strict check into a crash/DoS of the signing pipeline for a transaction that was actually valid. Like the reference, this is a denial of service blocking legitimate fund movement, produced by enforcing a constraint unconditionally where the real condition (actual fee vs. minimum) would have passed.

### Likelihood Explanation
Moderate. It requires `fee_per_vbyte` derived from the median block fee to fall below the relay floor while inputs carry a sufficient surplus — plausible during fee-market troughs, or when inputs substantially exceed payments without a change output. It does not require a malicious validator; it is reachable purely through public inputs (payment requests and scanned outputs).

### Recommendation
Compute the actual fee (`input_sat - payment_sat` when no change output will be emitted, or `input_sat - payment_sat - change_value` otherwise) and compare *that* against the minimum relay fee for the real weight. Only reject when the effective fee — not the declared rate — is insufficient. Gate `TooLowFee`/`NotEnoughFunds` on the operation actually occurring, mirroring the fix pattern `if (collatToAdd > 0) _verifyIsDepositNotPaused()`.

### Proof of Concept
```rust
// One input worth far more than the payment; no change; declared fee rate of 0.
let inputs = vec![output_worth_100_000_sats];
let payments = vec![(addr(), 1_000)]; // leftover ~99,000 sats becomes the fee

// Actual fee (~99k sats) vastly exceeds DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000,
// yet this is rejected:
assert_eq!(
  SignableTransaction::new(inputs, &payments, None, None, /* fee_per_vbyte */ 0),
  Err(TransactionError::TooLowFee),
);
```
The existing test at `networks/bitcoin/tests/wallet.rs:193-196` even encodes this over-rejection as expected behavior (`fee = 0` → `TooLowFee`), confirming the check fires on the declared rate regardless of the actual fee the transaction would pay.
