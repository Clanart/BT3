### Title
WombatBribeManager reward-fee swap reverts for non-standard ERC20 bribe tokens (e.g. USDT) due to raw `approve()` usage - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager._approveTokenIfNeeded` uses the raw `IERC20.approve()` call instead of `safeApprove`/`forceApprove`. This is the same bug class as the referenced report: any ERC20 token whose `approve()` does not return a `bool` (e.g. USDT and USDT-like tokens) will cause the call to revert when Solidity attempts to decode a non-existent return value.

### Finding Description
`_approveTokenIfNeeded` is called from `_swapFeesForBnb`, which iterates over bribe reward tokens collected during a vote and approves `PancakeZapper` to spend them before zapping into BNB: [1](#0-0) [2](#0-1) 

The developers themselves flagged this as suspect with the comment `// Should replace with safeApprove?` directly above the vulnerable function [3](#0-2) . Reward/bribe tokens are registered by admins for various pools/bribes and are not restricted to "safe" ERC20 implementations — if any bribe reward token behaves like USDT (no boolean return on `approve`), the `IERC20(token).approve(_to, type(uint256).max)` call at line 476 will revert because `SafeERC20`/`IERC20` interface decoding expects a `bool` return value.

This mirrors exactly the root cause described in the external report for `SolidlyV2AMO`/`SolidlyV3AMO`: raw `approve()` calls that assume a boolean return, which breaks compatibility with non-standard ERC20 tokens like USDT.

### Impact Explanation
Any unprivileged wallet (a vlMGP holder) that calls the voting flow with the caller-fee/auto-bribe-swap path and encounters a USDT-like reward token among the bribe rewards will have their entire transaction revert. Because the fee-swap logic is embedded inside the shared vote/harvest flow (not separable), this can block callers from claiming their caller fee entirely whenever such a token is present among the collected bribe rewards, effectively freezing that portion of unclaimed yield for the caller. This qualifies as a permanent freezing of unclaimed yield in the affected code path, matching the accepted impact categories.

### Likelihood Explanation
Likelihood depends on whether a USDT-like (non-bool-return) token is ever whitelisted/used as a bribe reward token for any pool — this is plausible since bribe reward tokens are diverse ERC20 tokens supplied by third parties/protocols across chains (as in the original report's context of "any full-EVM chain" support), and the code's own inline comment indicates the developers were uncertain about the correctness of using raw `approve()` here.

### Recommendation
Replace the raw `approve()` call in `_approveTokenIfNeeded` with `safeApprove` (or `forceApprove`/reset-then-approve pattern) from OpenZeppelin's `SafeERC20`, consistent with the rest of the codebase (e.g. `WombatStaking.sol` and `ManualCompound.sol` already use `safeApprove` throughout) [4](#0-3) [5](#0-4) .

### Proof of Concept
1. Admin (or protocol integration) registers a bribe with a reward token whose `approve()` does not return a `bool` (USDT-style ABI).
2. A vlMGP holder calls the vote/cast function that triggers `_swapFeesForBnb`, which processes that reward token.
3. `_approveTokenIfNeeded` calls `IERC20(token).approve(PancakeZapper, type(uint256).max)` at [6](#0-5) .
4. Since the ABI decoding expects a `bool` return value that the token does not provide, the low-level call reverts, reverting the entire voting/fee-claim transaction and blocking the caller from receiving their bribe fee for that call.

        for (uint256 i; i < bribeLength; i++) {
            uint256 rewardLength = rewardTokens[i].length;
