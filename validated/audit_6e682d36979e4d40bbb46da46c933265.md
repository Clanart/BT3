## Analog Vulnerability Found

### Title
Unbounded `rewardTokens` Array Iteration in `_harvestBaseRewarder` Can Permanently Block User Withdrawals - (File: rewards/BaseRewardPool.sol, rewards/MasterMagpie.sol)

### Summary
`BaseRewardPool.getReward()` (and its analogous implementations in `BaseRewardPoolV2.sol`, `vlMGPBaseRewarder.sol`, and `mWOMSVBaseRewarder.sol`) iterate over the *entire* `rewardTokens` array on every call, with no ability to target a specific token or index. This function is invoked unconditionally inside `MasterMagpie`'s core, unprivileged user-facing `_deposit` and `_harvestAndUnstake` paths, meaning every single deposit or withdrawal transaction pays the full iteration cost of the reward-token list. As the list grows over the pool's lifetime, this creates the exact "unbounded loop / block gas limit" bug class described in the external report, but here the impact is on ordinary stakers trying to withdraw their own principal.

### Finding Description
`getReward` loops over `rewardTokens.length` without any index-based fast path: [1](#0-0) 

The same unbounded-loop pattern exists in the sibling reward pool implementations: [2](#0-1) [3](#0-2) 

Reward tokens are appended to this array via `queueNewRewards`, and there is no corresponding removal mechanism, so the array is monotonically growing over the life of a pool: [4](#0-3) 

Critically, this loop is not opt-in — it is executed on *every* ordinary user deposit and withdrawal through `MasterMagpie`'s internal functions `_deposit` and `_harvestAndUnstake` (called from `_withdraw`), via `_harvestBaseRewarder`: [5](#0-4) 

Because `deposit`, `withdraw`, `depositFor`, and `withdrawFor` are all plain unprivileged wallet-callable entry points that funnel into `_deposit`/`_harvestAndUnstake`, any user attempting to move their own staked funds must pay for iterating the full, ever-growing `rewardTokens` array for that pool.

### Impact Explanation
As reward tokens accumulate for an actively used pool (a normal, expected operational occurrence — analogous to the original report's terms array growing to 100 entries), the gas cost of `_harvestBaseRewarder`'s loop inside `getReward` grows linearly and unboundedly. Once combined with the rest of the deposit/withdraw transaction cost (ERC20 transfers, `updatePool`, `_harvestMGP`, etc.), a sufficiently long `rewardTokens` array can push a single `withdraw`/`withdrawFor` call over the block gas limit. Since `_harvestBaseRewarder` is unconditionally invoked and not skippable, this permanently locks the affected user's principal in the pool — a genuine, non-privileged, permanent freezing-of-funds condition, not merely a "gas-only" inefficiency, because there is no alternate withdrawal path that bypasses the reward harvest.

### Likelihood Explanation
Likelihood is directly tied to protocol usage growth: any pool that accumulates enough distinct reward tokens (via legitimate `queueNewRewards` calls from managers over time, with no removal path) will eventually hit this ceiling for all of its depositors, not just a single attacker-crafted case. This mirrors the original report's premise that the system is expected to scale to on the order of 100 tokens, at which point ordinary withdrawal transactions risk exceeding the block gas limit.

### Recommendation
Add a `getRewards(address _account, address _receiver, address[] memory _rewardTokens)`-style targeted path to the mandatory harvest performed during deposit/withdraw (partially present in `BaseRewardPoolV2` but not used by `_harvestBaseRewarder`), or decouple full reward settlement from the deposit/withdraw critical path so that a user can always withdraw principal regardless of `rewardTokens` array length, deferring reward accounting/claims to a separate, chunkable call.

### Proof of Concept
1. Deploy a `BaseRewardPool` for a staking token and progressively call `queueNewRewards` (manager-permissioned but not attacker-required — this is normal protocol operation) to add reward tokens until `rewardTokens.length` is large (e.g., on the order of what would exceed remaining block gas when combined with `_deposit`/`_harvestAndUnstake`'s other operations).
2. A user who staked earlier in the pool's life calls `MasterMagpie.withdraw(stakingToken, amount)`.
3. `_withdraw` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward` iterates the full `rewardTokens` array, and the transaction reverts due to exceeding the block gas limit.
4. The user has no alternative code path to retrieve their staked principal (no reward-skipping emergency withdraw variant exists for this scenario since `emergencyWithdraw` still requires the pool functioning), resulting in a stuck, permanently frozen position.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();

        _harvestBaseRewarder(_stakingToken, _account);
