### Title
Attacker-supplied `ReceivedOutput` fields (offset, value, outpoint) are mass-assigned into `SignableTransaction` inputs without re-derivation — (`networks/bitcoin/src/wallet/send.rs`, `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The Cerebrate bug class is "an attacker-supplied identifier survives normalization and is used during object creation where the value should have been server-derived." In bitcoin-serai, `ReceivedOutput` is exactly this shape: it bundles a spend-`offset` (which the `Scanner` derives and must match a registered script path) with a claimed `TxOut` and `OutPoint`. `ReceivedOutput::read` deserializes all three fields verbatim from untrusted bytes, and `SignableTransaction::new` mass-assigns them — the claimed `value` feeds the balance/fee accounting, the claimed `outpoint` becomes the signed input's `previous_output`, and the claimed `offset` is copied into `offsets` for signing — without re-deriving the offset from a `Scanner` or confirming the output against chain data.

### Finding Description
`ReceivedOutput::read` reads `offset`, `output`, and `outpoint` straight from the byte stream with no consistency check (`networks/bitcoin/src/wallet/mod.rs:122-134`). `SignableTransaction::new` then trusts every field: `input_sat` sums attacker-declared `output.value` (`send.rs:175`), `offsets` is copied from `input.offset` (`send.rs:176`), and `tx_ins` uses `input.outpoint` (`send.rs:180`). The only downstream check, in `multisig`, is that `p2tr_script_buf(offset.group_key())` equals the *claimed* `prevouts[i].script_pubkey` (`send.rs:276-279`) — i.e., the object is checked for internal self-consistency, not against any server-controlled ground truth. This is the same failure mode as Cerebrate's `add()`: the "normalized" object still carries the attacker-chosen identifier (the outpoint) and attacker-chosen metadata (the value).

### Impact Explanation
Any integration that accepts `ReceivedOutput`s from untrusted bytes (e.g., outputs relayed by a peer or user rather than produced by the node's own `Scanner`) will treat fabricated outputs as real balance. Concretely: an attacker supplies `{offset: 0, output: TxOut{value: V, script_pubkey: p2tr(key)}, outpoint: <attacker-chosen or nonexistent>}`. `SignableTransaction::new` counts `V` as spendable input value, and `multisig`'s script check passes because the attacker set the script to match the true key. The resulting transaction is fully signed by the threshold group yet spends a nonexistent/attacker-chosen outpoint — funds are reported received and even "spent" that were never spendable by the group, burning real fees or corrupting accounting. Alternatively the attacker can make a *real* outpoint appear with an inflated `value`, skewing `needed_fee`/change math (`send.rs:228-233`).

### Likelihood Explanation
Reachable whenever `ReceivedOutput::read` is applied to peer/user-controlled serialization — an explicitly in-scope input class per the scope rules. It requires a caller that forwards deserialized outputs to `SignableTransaction::new`/`multisig` rather than only using `Scanner::scan_transaction` results. The honest path (`scan_transaction` sets `offset` from `self.scripts`, `mod.rs:205-210`) is safe; the vulnerability is the permissive deserializer combined with a consumer that never re-derives identity fields. Impact is bounded to invalid transactions / false balance reporting (Medium), since a forged `script_pubkey` that doesn't match `key + G·offset` is rejected in `multisig`.

### Recommendation
Treat `offset` and `outpoint` as server-derived identifiers: either make `SignableTransaction::new` take a `Scanner`/key and re-derive the offset from the output's `script_pubkey` (rejecting unrecognized scripts), or document and enforce at the type level that `ReceivedOutput` may only be constructed by `Scanner`. At minimum, `multisig` should verify each input's `outpoint` against confirmed chain state before signing.

### Proof of Concept
```rust
// Attacker crafts bytes for ReceivedOutput::read
let mut buf = Vec::new();
buf.extend(Scalar::ZERO.to_bytes());                 // offset = 0 -> key + 0*G = group key
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(1_000_000),              // claimed value
    script_pubkey: p2tr_script_buf(group_key).unwrap(), // matches group key
}));
buf.extend(serialize(&OutPoint { txid: Txid::all_zeros(), vout: 0 })); // nonexistent outpoint

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.value() == 1_000_000 is now treated as spendable input
let tx = SignableTransaction::new(vec![forged], &payments, change, None, fee).unwrap();
let machine = tx.clone().multisig(&keys).unwrap();    // script check passes
// FROST signs a TX spending a UTXO that does not exist / isn't owned by the group
```
Root cause: `ReceivedOutput::read` (`mod.rs:122`) admits an attacker-chosen `offset`/`outpoint`/`value`, and `SignableTransaction::new` (`send.rs:175-185`) consumes them without re-derivation, mirroring the Cerebrate mass-assignment of `id`.
