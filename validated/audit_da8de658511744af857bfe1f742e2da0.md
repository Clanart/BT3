### Title
Crafted blame accusation with out-of-set Participant index panics `blame_internal`, enabling DoS - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept attacker-chosen `sender`/`recipient` `Participant` indexes and index `self.commitments` (a `HashMap`) with them via `[]`. `Participant::new` only rejects `0`, so any value `1..=65535` — including participants that do not exist in the `n`-party DKG set — is accepted and causes a panic inside `blame_internal`, aborting the calling process. Analogous to the referenced bug class (a specially crafted input triggers denial of service), an unauthenticated party can crash a node evaluating blame proofs by naming a participant index that was never part of the protocol.

### Finding Description
In `blame_internal`, after decryption/proof handling, the code evaluates whether the decrypted share is valid for the accused sender:

- `crypto/dkg/pedpop/src/lib.rs` (~line 599): `&self.commitments[&sender]` — `commitments` is a `HashMap<Participant, Vec<C::G>>` populated only for participants `1..=n` (either by `verify_r1` via `all_participant_indexes`, or by `AdditionalBlameMachine::new` iterating `1..=n`). Indexing a `HashMap` with `[]` panics on a missing key.

`Participant` is defined in `crypto/dkg/src/lib.rs` (lines 23–42): `Participant::new` returns `Some` for any non-zero `u16`. Neither `BlameMachine::blame` (~line 623) nor `AdditionalBlameMachine::blame` (~line 674) checks that `sender` (or `recipient`) is in `1..=n` before `blame_internal` is invoked.

The same unchecked indexing pattern also exists in `KeyMachine::calculate_share` (~line 490: `&self.commitments[&l]`), though there `l` is constrained by `validate_map`, so the blame path is the reachable one.

`AdditionalBlameMachine::new` explicitly advertises itself as usable "regardless of if the caller was a member in the DKG protocol" — i.e., a third-party/non-participant caller evaluating blame statements is an intended use, making attacker-controlled `sender`/`recipient` values reachable without any privileged position.

### Impact Explanation
Denial of service: a single crafted blame accusation carrying a `sender` (or `recipient`) participant index `> n` (any non-zero `u16` not in the DKG set) causes a hard panic in `blame_internal`. In any deployment that exposes blame adjudication — e.g., a coordinator or indexer evaluating `Transaction::InvalidDkgShare`-style accusations, which carry `accuser`/`faulty` participant fields read from wire bytes — one malformed accusation crashes the process rather than returning a `PedPoPError`. This is a crafted-input → crash DoS, matching the referenced vulnerability class.

### Likelihood Explanation
Triggering requires only submitting a blame evaluation request with an out-of-set participant index. `Participant::new` validates only non-zero, and no boundary check against `n` exists on this path. The cost to the attacker is one message; no valid cryptographic material is needed since the panic occurs on the map lookup before/around proof evaluation (for an unknown `sender`, `self.commitments[&sender]` is reached whenever decryption/proof handling doesn't early-return; even when it does, `AdditionalBlameMachine` callers supplying `sender` values within range but `recipient` out of range similarly pass `recipient` only into `share_verification_statements`, so `sender` is the reliable panic vector when its early returns are avoided — e.g., by a `sender` in-set vs. out-of-set combination where the panic always fires for out-of-set `sender` on the `commitments` lookup). Medium likelihood where blame adjudication is externally reachable.

### Recommendation
Validate `sender` and `recipient` against the known participant set before indexing `self.commitments`, e.g.:

- In `blame_internal`, replace `self.commitments[&sender]` with `self.commitments.get(&sender)` and treat a `None` as `sender` being faulty/invalid rather than panicking.
- Reject `u16::from(sender) > n` (and same for `recipient`) up front in `BlameMachine::blame` / `AdditionalBlameMachine::blame`, returning a defined result or storing `n` on the machine for bounds checks.
- Apply the same defensive `get()` pattern anywhere `commitments`/`verification_shares`/`original_verification_shares` maps are indexed with party-supplied `Participant` values (also see `ThresholdView::verification_share`/`original_verification_share` in `crypto/dkg/src/lib.rs` lines ~672–681, which panic on out-of-set indexes).

```rust
// blame() -> blame_internal() -> self.commitments[&sender] panics.

let recipient = Participant::new(1).unwrap();

// BlameMachine::blame (or AdditionalBlameMachine::blame):
let (_, faulty) = blame_machine.blame(sender, recipient, msg, proof);
// ^ panics inside blame_internal at crypto/dkg/pedpop/src/lib.rs:
//   multiexp_vartime(&share_verification_statements::<C>(
//       recipient, &self.commitments[&sender], ...))
// HashMap index on a missing key -> panic -> process abort / DoS.
```

Note: I did not fully trace `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs`, not read) to confirm every early-return ordering for an out-of-set `sender`, so the exact panic line may shift, but the `self.commitments[&sender]` indexing with an unvalidated `Participant` is confirmed in `blame_internal`, and no bounds check exists on the blame entry points.
