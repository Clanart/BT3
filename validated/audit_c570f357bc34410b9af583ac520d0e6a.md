Based on the investigation, the closest structural analog to the `cooldown()` bug — a function that lacks a "kill switch" check that its sibling functions enforce — is in the ERC-20 IBC callback flow in `x/erc20/keeper/ibc_callbacks.go`.

### Title
Inconsistent enforcement of token-pair `Enabled` flag across IBC callback paths allows conversion of a governance-disabled token pair via failed-ack/timeout path - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
`OnRecvPacket` checks `pair.Enabled` before minting/converting a native ERC-20 token pair, but the sibling function `ConvertCoinToERC20FromPacket` (invoked by both `OnAcknowledgementPacket` on error and `OnTimeoutPacket`) does not check this same flag before performing the reverse conversion back into ERC-20.

### Finding Description
In the success path, `OnRecvPacket` explicitly checks the per-pair `Enabled` flag before minting: [1](#0-0) 

In the failure/timeout path, `ConvertCoinToERC20FromPacket` only checks the module-wide `EnableErc20` param and denom registration, but never checks `pair.Enabled` before calling `ConvertCoinNativeERC20`: [2](#0-1) 

This mirrors the `cooldown()` inconsistency pattern: a state-mutating entrypoint (`ConvertCoinToERC20FromPacket`, reached from `OnAcknowledgementPacket`/`OnTimeoutPacket`) omits the same governance-controlled disable check (`pair.Enabled`) that its sibling entrypoint (`OnRecvPacket`) enforces. [3](#0-2) 

### Impact Explanation
`pair.Enabled` is the governance-controlled circuit breaker for a specific token pair (e.g., used to freeze conversion for a token pair known to have a vulnerable or misbehaving ERC-20 contract, per `x/erc20/keeper/proposals.go` and `x/ibc/transfer/keeper/msg_server.go` which both gate on `pair.Enabled`). Because the timeout/failed-ack path skips this check, an attacker could still trigger `ConvertCoinNativeERC20` for a token pair that governance has explicitly disabled, by causing (or waiting for) an IBC transfer of that denom to fail or time out. This reintroduces interaction with a contract/pair that was frozen specifically to prevent it, potentially bypassing an emergency pause intended to stop fund loss.

### Likelihood Explanation
Reachability depends on being able to cause or observe a failed acknowledgement or a timed-out IBC transfer for a coin whose corresponding native ERC-20 pair has been disabled — a condition attacker-controllable via standard IBC packet flow (timeouts, and refusal/error acks are influenceable in many IBC configurations). No privileged access is required to trigger the callback; only the pre-condition that the module and denom remain otherwise valid.

### Recommendation
Add an explicit `if !pair.Enabled { return nil }` (or equivalent early no-op) check in `ConvertCoinToERC20FromPacket` before invoking `ConvertCoinNativeERC20`, mirroring the check already present in `OnRecvPacket`, so that a governance-disabled token pair cannot be reactivated via the failed-ack/timeout code path.

### Proof of Concept
Not independently executed; the finding is derived directly from static comparison of the two callback code paths shown above. **Caveat/uncertainty:** I was unable to fully confirm within the available tool budget whether `ConvertCoinNativeERC20` (defined in `x/erc20/keeper/msg_server.go`) performs its own internal `pair.Enabled` check that would make this omission harmless — the `grep_search` for `pair.Enabled` only returned one hit inside `ibc_callbacks.go` (the `OnRecvPacket` check), suggesting `ConvertCoinNativeERC20` itself does not re-check the flag, but this was not read directly to verify. A Devin session with full file access should confirm the body of `ConvertCoinNativeERC20` before treating this as conclusively exploitable at Critical severity.

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
