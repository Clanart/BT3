### Title
`SignableTransaction` under-charges the fee when an OP_RETURN `data` output is added, so the transaction pays less than the requested `fee_per_vbyte` — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`SignableTransaction::new` accepts an optional `data` field, appends an OP_RETURN output to `tx_outs`, but computes the transaction's vbytes — and therefore `needed_fee` — from `payments` only, which excludes the OP_RETURN output. The declared fee is enforced against `input_sat`, yet the actual bytes carried by the transaction are larger than what was priced. The caller can pass a `fee_per_vbyte` that satisfies the minimum-relay sanity check while the broadcast transaction pays an effective fee rate lower than requested — a direct analog of "only the fixed fee is charged while the additional required value is silently dropped."

### Finding Description

In `networks/bitcoin/src/wallet/send.rs`:

```rust
193|    if let Some(data) = data {
194|      tx_outs.push(TxOut {
195|        value: Amount::ZERO,
196|        script_pubkey: ScriptBuf::new_op_return(...)
197|      })
198|    }
199|
204|    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
205|
206|    let mut needed_fee = fee_per_vbyte * vbytes;
```

`tx_outs` (which includes the OP_RETURN output) is what actually goes into the signed `Transaction` at line 250, but `calculate_weight_vbytes` at line 204 is called with `payments` — not `tx_outs` — so the OP_RETURN output's weight is never priced into `vbytes` or `needed_fee`. The OP_RETURN output adds roughly `8 + script_len` bytes (~12–92 bytes of real weight, up to 80 bytes of pushed data), none of which is charged at `fee_per_vbyte`.

The subsequent checks then validate this *understated* fee:

- Line 211: `needed_fee` is only required to exceed `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, again using the understated `vbytes`.
- Line 215: `input_sat < payment_sat + needed_fee` validates the input covers payments plus the understated fee.
- The change branch (lines 224–235) recomputes with `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — still omitting the OP_RETURN output — so the change amount is likewise computed against a fee that never accounts for the data output.

The result: `needed_fee()` and `fee()` report a fee consistent with `inputs − outputs`, but the *effective* sat/vbyte rate of the final transaction is strictly below the caller-specified `fee_per_vbyte`, with no error returned. Analogously to the nouns-builder bug, the protocol enforces only a fixed minimum (`builderFee` / min-relay fee) while the remaining obligated value (treasury payment / the requested fee rate on the extra bytes) is silently zeroed out.

### Impact Explanation

- Any caller of `SignableTransaction::new` that supplies `data` (a public, untrusted-input parameter) gets a transaction whose true fee rate is below the rate it asked for and below what `needed_fee` implies was paid for the actual serialized size.
- The signed transaction commits to the OP_RETURN output via `Prevouts::All` sighashes (`TransactionSignMachine::sign`, lines 373–391), so the threshold multisig signs a transaction carrying unpaid-for bytes — the signature is valid, but the economic terms (`fee_per_vbyte`) the signer/scheduler specified are not met.
- For large `data` (up to the 80-byte cap) and modest payment sets, the fee-rate shortfall can be a double-digit percentage, degrading confirmation priority and, under mempool congestion, risking eviction or never-confirming transactions — funds remain locked in the inputs until the tx is replaced or dropped.

### Likelihood Explanation

Triggering requires a caller to pass `Some(data)` — a public input to `SignableTransaction::new`. Within the in-repo production path, `processor/src/networks/bitcoin.rs::make_signable_transaction` always passes `None` for data, so the bug is not exercised by the shipped processor. However, `SignableTransaction` is a public wallet API explicitly documented to support `data` ("If data is specified, an OP_RETURN output will be added with it"), and any integrator or future code path that uses it silently produces an under-priced transaction. Because the failure is silent (no error, `fee()` still reports a self-consistent number) and depends only on a documented public input, likelihood is moderate; severity Medium.

### Recommendation

Price the OP_RETURN output (and any future output additions) into the fee:

- Change `calculate_weight_vbytes` to take the final `tx_outs` (or take `payments` plus `data`/`change` explicitly) rather than `payments`, at both call sites (lines 204 and 225–226), so `vbytes` and `vbytes_with_change` include the OP_RETURN output.
- Alternatively, build the candidate `Transaction` with `tx_outs` inside `calculate_weight_vbytes` directly, eliminating the possibility of the priced outputs diverging from the signed outputs.
- Add a test asserting `tx.fee() >= fee_per_vbyte * tx.vsize()` when `data` is `Some`.

### Proof of Concept

```rust
// networks/bitcoin context: Secp256k1, ReceivedOutput, SignableTransaction
let inputs = vec![received_output];                    // any funded ReceivedOutput
let payments = vec![(p2tr_script_buf(key).unwrap(), 10_000)];
let data = vec![0xAA; 80];                             // max-allowed OP_RETURN payload
let fee_rate = 10u64;                                  // sat/vbyte requested

let stx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_rate).unwrap();
let tx = stx.transaction().clone();

// needed_fee was computed WITHOUT the OP_RETURN output's weight
let actual_vsize = tx.vsize() as u64;
let paid_fee = stx.fee();

// The effective rate is strictly below the requested fee_per_vbyte
assert!(paid_fee < fee_rate * actual_vsize);
// Yet no error was returned, and needed_fee passed the min-relay check
// because it was also computed against the smaller, data-less vbytes.
```

Note: I verified `send.rs` end-to-end but could not fully audit every downstream consumer of `SignableTransaction` for data-bearing usage; in-repo callers (the processor) pass `data: None`, so the exposure is via the public API rather than the shipped scheduler path.
