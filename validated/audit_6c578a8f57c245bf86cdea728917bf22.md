### Title
Spoofed `WWW-Authenticate` realm from a malicious/compromised git remote causes GitHub Desktop to treat an arbitrary host as an "enterprise" GitHub endpoint and trigger the internal sign-in flow with the user's identity - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The credential helper invoked by Desktop's git trampoline (`createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`) classifies an HTTP(S) remote as `'enterprise'`, `'github.com'`, or `'generic'` partly by trusting server-supplied `wwwauth[...]` header content forwarded by git itself, rather than only relying on Desktop's own knowledge of which hosts are GitHub/GHE. [1](#0-0) 

### Finding Description
`getEndpointKind` walks the parsed `Credential` map for keys starting with `wwwauth[` and, if a value contains `realm="GitHub"`, immediately classifies the endpoint as `'enterprise'`: [2](#0-1) 

This `wwwauth[...]` data originates from the HTTP `WWW-Authenticate` response header returned by whatever server git is actually talking to for that remote — fully attacker-controlled if the remote is malicious or a MITM proxy sits between the client and the real host. This satisfies the "attacker controls...a git remote/proxy response" primitive from the seed report (which itself exploited unvalidated inbound data driving privileged token handling).

Once `endpointKind !== 'generic'` and no existing account is bound to that exact `apiEndpoint`, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

instead of falling back to the generic credential path (`getGenericCredential`/`promptForGenericGitAuthentication`) that would otherwise be used for an arbitrary third-party host. This means an attacker who controls the answering server for a git operation (clone/fetch/push over HTTPS, or a corporate/coffee-shop proxy performing TLS interception or acting as a transparent HTTP proxy for a `git://`/`http://` remote) can spoof the realm to force Desktop's "sign in to GitHub Enterprise" UI/flow to be presented for their own arbitrary domain, rather than the generic-git-auth prompt. This blurs the trust boundary between "known GitHub host" and "arbitrary host," which is the same class of bug as the seed report: a security-relevant classification/allocation decision is made from data an attacker fully controls, without an independent trust check, and can be triggered by simply causing the target function to run (frontrunning `vest()`/`lock()` there, spoofing the WWW-Authenticate response here).

### Impact Explanation
The most severe consequence — automatic release of an already-stored account token to the attacker's endpoint — is not exploitable through this exact path, because `getGitHubCredential`/`findGitHubTrampolineAccount` only auto-supplies stored credentials when the account's own endpoint origin matches the credential URL's origin, which an unrelated attacker domain cannot satisfy: [4](#0-3) 

However, forcing the `'enterprise'` classification for an attacker-chosen host still routes the user into Desktop's dedicated "GitHub Enterprise sign-in" UX for that attacker-controlled endpoint instead of the neutral generic-credential prompt, increasing the credibility of a phishing-style credential prompt and diverging from the intended trust model (only hosts Desktop itself has verified via `isGitHubHost`/known endpoints should get GitHub-branded sign-in treatment).

### Likelihood Explanation
Requires the attacker to control the server (or a network proxy) answering a git HTTPS request that Desktop performs, and to add a crafted `WWW-Authenticate: ... realm="GitHub"` header - achievable for any malicious/compromised git host or on-path proxy without further exploitation on the client. No local access, malware, or leaked credentials are needed, matching the "unprivileged...attacker controls a git remote/proxy response" scope of the task.

### Recommendation
Do not use the git-forwarded `wwwauth[...]` realm string as sufficient evidence to classify an endpoint as `'enterprise'`. Require corroboration from Desktop's own host validation (e.g. `isGitHubHost(endpoint)` or an existing verified account) before elevating an unknown host into the GitHub/enterprise-branded sign-in flow, or fall through to the generic-git-auth prompt whenever the host isn't independently known/verified by Desktop.

### Proof of Concept
1. Configure a malicious HTTPS server (or a MITM/corporate proxy performing TLS termination) to answer any git-over-HTTP request with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, attempt to clone/fetch/push a repository whose remote points at this server.
3. Git forwards the `WWW-Authenticate` header content as `wwwauth[0]=...` to the `desktop` credential helper via the trampoline.
4. `getEndpointKind` matches `realm="GitHub"` and returns `'enterprise'`; because no account is yet bound to that host, `getCredential` invokes `ui.promptForGitHubSignIn(endpoint)` for the attacker's domain, presenting the GitHub-Enterprise-branded sign-in path for a server that is not actually GitHub Enterprise. [5](#0-4) 

Note: I could not confirm in the available index whether `ui.promptForGitHubSignIn` performs any additional host verification (e.g., checking `/meta` or the GHES API) before presenting sign-in, since `trampoline-ui-helper.ts` contents were not retrieved in this session; further review of that file (and of `isGitHubHost` in `app/src/lib/api.ts`) is recommended to fully bound the impact.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
