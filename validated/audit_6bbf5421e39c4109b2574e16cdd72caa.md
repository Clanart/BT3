### Title
Unbounded allocation in `SchnorrAggregate::read` allows remote memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes an unbounded-request-size DoS: a service accepts attacker-controlled input whose size is never capped, so repeated large requests exhaust memory until the OS kills the process. The same bug class exists in Serai's `SchnorrAggregate::read`: a `u32` element count is read from untrusted bytes, then that many group elements are deserialized into a `Vec` with no cap on the declared count or the total input size. [1](#0-0) 

### Finding Description
`SchnorrAggregate<C>::read` deserializes an aggregate Schnorr signature from an arbitrary `io::Read`:

```rust
// crypto/schnorr/src/aggregate.rs
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

The `len` field is fully attacker-controlled and permits up to `u32::MAX` (~4.29 billion) `C::G` points. There is no bound on `len` and no relationship enforced between `len` and the number of signatures actually being aggregated — the count is never checked against `keys_and_challenges.len()` until `verify` runs, which happens *after* the entire `Vec` has been allocated and populated. [2](#0-1) [3](#0-2) 

An unprivileged party that feeds crafted bytes into this `read` (the same reachability class as the other `read_*`/`verify` APIs listed for untrusted input) can stream a multi-gigabyte buffer of validly-encoded points. Each 32-byte point becomes a decompressed `C::G` group element in a heap `Vec`, so memory consumption is at least proportional to — and for expanded group representations greater than — the bytes sent. Repeating the request in parallel (as in the report's `grequests` PoC) multiplies resident memory, since each in-flight deserialization holds its own `Vec`. On a modern OS the process is OOM-killed once consumption exceeds available memory.

This is exactly the report's root cause mapped onto Serai: a deserialization entry point reachable with public inputs that imposes no size limit, causing unbounded memory consumption and a remotely-triggered crash. Related in-scope readers are bounded by comparison — e.g. `Commitments::read` in PedPoP reads exactly `params.t()` elements [4](#0-3) , and `ThresholdKeys::read` is bounded by a `u16` `n` [5](#0-4)  — whereas `SchnorrAggregate::read` trusts a 32-bit count with no upper bound.

### Impact Explanation
**High.** Memory exhaustion of any Serai process that deserializes `SchnorrAggregate` values from unprivileged input results in the OS killing the process. In a deployment where aggregate signatures (or any `read`-parsed structure carrying an attacker-chosen `u32` vector length) are accepted from the network, an attacker can repeatedly crash the node, denying service to honest stakers/participants — the same "service killed by the operating system" outcome demonstrated in the external report.

### Likelihood Explanation
**High.** The attacker needs only to reach a code path calling `SchnorrAggregate::read` (or an equivalent unbounded length-prefixed `read`) on bytes they control, and to send a few hundred MB–GB of trivially-constructed data (a large `len` prefix followed by repeated valid point encodings, or simply a large byte stream across parallel connections). No keys, threshold position, or protocol role is required; a declared length of up to `u32::MAX` means a single 4-byte prefix dictates allocation behavior.

### Recommendation
Cap the aggregate length during deserialization, mirroring the report's `RequestSize`-style fix:

- In `crypto/schnorr/src/aggregate.rs`, reject `len` values above a protocol-reasonable maximum (e.g. the maximum aggregation batch size), before the read loop:
  ```rust
  let len = u32::from_le_bytes(len);
  if len > MAX_AGGREGATE_SIGNATURES { Err(io::Error::other("aggregate too large"))?; }
  ```
- Ideally bound by the reader itself: wrap `reader` in `reader.take(max_bytes)` or require a `&[u8]` slice so allocation can never exceed input actually held in memory.
- Apply the same audit to all `read`/`read_*` functions that size allocations from attacker-controlled length prefixes, and enforce transport-level request/message size limits at every network boundary feeding these deserializers.

### Proof of Concept
```rust
// Anywhere SchnorrAggregate::<C>::read is reachable on untrusted bytes:
use std::io::Cursor;
use schnorr::SchnorrAggregate;
use ciphersuite::Ristretto; // example ciphersuite

fn dos() {
    // Declare 4 billion Rs
    let mut bytes = u32::MAX.to_le_bytes().to_vec();
    // Append a large stream of canonical Ristretto points (32 bytes each)
    let point = <Ristretto as ciphersuite::Ciphersuite>::generator().to_bytes();
    for _ in 0 .. 100_000_000 { // ~3.2 GB of compressed points
        bytes.extend(point.as_ref());
    }
    // Allocates/decompresses a Vec<C::G> proportional to input; repeated
    // invocations in parallel exhaust RAM and the OOM killer terminates
    // the process, exactly as in the Staking-API report.
    let _ = SchnorrAggregate::<Ristretto>::read(&mut Cursor::new(bytes));
}
```

Concretely, the attacker writes `0xFFFFFFFF` as the length prefix and streams point encodings over however many parallel connections/channels feed this `read`. Each connection holds its own growing `Vec`, so N streams multiply memory pressure; once total RSS exceeds system memory the kernel kills the process — no valid signatures, keys, or protocol standing required.
