### Title
Identity group key via unfiltered `Ciphersuite::read_G` in PedPoP `Commitments::read` causes a fatal panic during Bitcoin signing - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The Routinator bug class is "malformed externally-supplied data is treated as a fatal error (process abort) instead of a recoverable error." The Serai analog: `Commitments::read` in PedPoP decodes group elements with `C::read_G` (the `Ciphersuite` trait method), while `frost::curve::Curve::read_G` exists specifically to add an identity check on top of it. Because the PedPoP path skips that wrapper, an attacker-controlled participant can submit the identity point as a commitment coefficient, drive the resulting multisig group key to the point at infinity, and every downstream Bitcoin signing attempt panics inside `x()`/`x_only()` via `Hram::hram` — a reachable assertion / fatal exit rather than a handled error.

### Finding Description
`Commitments::read` reads `t` group elements directly through `C::read_G`, which performs no identity rejection:

```rust
// crypto/dkg/pedpop/src/lib.rs:115-125
let mut read_G = || -> io::Result<C::G> {
  let mut buf = <C::G as GroupEncoding>::Repr::default();
  reader.read_exact(buf.as_mut())?;
  let point = C::read_G(&mut buf.as_ref())?;
  ...
};
for _ in 0 .. params.t() {
  commitments.push(read_G()?);
}
``` [1](#0-0) 

By contrast, `Curve::read_G` (used for FROST preprocesses) explicitly rejects identity, proving the base `Ciphersuite::read_G` accepts it:

```rust
// crypto/frost/src/curve/mod.rs:125-131
fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
  let res = <Self as Ciphersuite>::read_G(reader)?;
  if res.is_identity().into() {
    Err(io::Error::other("identity point"))?;
  }
  Ok(res)
}
``` [2](#0-1) 

The Schnorr proof of knowledge attached to `Commitments` proves knowledge of the discrete log of the coefficients; the identity point has a known discrete log (`0`), and the negation of a known scalar is also known, so the attacker produces a perfectly valid `sig` for the malicious commitment set. The PoK challenge (`challenge()` at `crypto/dkg/pedpop/src/lib.rs:86-94`) binds the bytes but does not constrain their semantics.

The attacker waits for the other participants' broadcast `Commitments`, then publishes `A_0 = -(Σ_l A_{l,0})` (and arbitrary remaining coefficients). The multisig group key, formed by summing the constant-term commitments / verification shares in `ThresholdKeys::new`, becomes the point at infinity.

All Bitcoin signing then goes through `crypto::Hram::hram`, which calls `x(R)` and `x(A)`:

```rust
// networks/bitcoin/src/crypto.rs:13-22
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
``` [3](#0-2) [4](#0-3) 

With `A = group_key = ∞`, `x(A)` hits `.expect("point at infinity")` and the process aborts. `tweak_keys` (`networks/bitcoin/src/wallet/mod.rs:46-75`) likewise operates on the group key's byte encoding and negation, producing the same fatal behavior at key-tweak time.

### Impact Explanation
A single malicious DKG participant permanently poisons the multisig. Any attempt to produce a Bitcoin threshold signature (or even to tweak/scan the key) panics rather than returning a `FrostError`, mirroring the Routinator advisory exactly: untrusted data that should produce a recoverable decoding/validation error instead causes a fatal exit. Worst case is denial of service of the signing/validation capability for all keys derived in that session — same shape as "denial of service for RPKI data to routers." The code itself documents this panic exposure: "If either `R` or `A` is the point at infinity, this will panic" and "This may panic if called with nonces/a group key which are the point at infinity."

### Likelihood Explanation
Requires only that the attacker is a DKG participant (or controls bytes fed to `Commitments::read`), and that the deployment does not enforce simultaneous commitment publication — the attacker publishes last, after seeing the honest `A_{l,0}` values. No collision, collusion, or leaked material is needed; the PoK signature is honestly generated for a known-scalar commitment. The window exists because PedPoP's decode path bypasses the identity check that `Curve::read_G` was written to enforce.

### Recommendation
- In `Commitments::read`, reject identity points (check `point.is_identity()` after `C::read_G`, as `Curve::read_G` does).
- Additionally, in `ThresholdKeys::new` / PedPoP verification, reject a group key (sum of constant-term commitments) equal to the identity and return an error rather than constructing keys that panic downstream.
- Defense in depth: have `x()`/`x_only()`/`Hram::hram` return `Option`/`Result` instead of panicking, so a residual infinity input is a `FrostError`, not a process abort.

### Proof of Concept
1. Run a PedPoP DKG for `Secp256k1` with `n ≥ 2`, `t ≥ 1`; attacker controls participant `j` and broadcasts last.
2. After receiving all honest `Commitments`, attacker computes `A_0 = -(Σ_{l≠j} A_{l,0})`, picks arbitrary `A_1..A_{t-1}`, generates the Schnorr PoK for the known coefficient scalars, and calls `Commitments::write`. Honest parties call `Commitments::read` — every point decodes via `C::read_G` without error.
3. Attacker deals shares consistent with the polynomial defined by `A_0..A_{t-1}`; share verification passes since the commitments are valid points.
4. Resulting `ThresholdKeys` have `group_key() == identity`. Constructing `Scanner::new`/`tweak_keys`, or running `AlgorithmMachine::new(Schnorr::new(), keys).preprocess(...).sign(...)` — which calls `Hram::hram(R, A, m)` — panics on `.expect("point at infinity")` in `x()`, aborting the process instead of returning an error.

Caveat: whether `ThresholdKeys::new` or the share-verification path already rejects an identity group key could not be fully confirmed within the available context; if it does reject it via `Err`, that path is safe and the panic instead occurs wherever the identity-bearing commitments are first aggregated into verification shares (still an unhandled panic if done via arithmetic on a point assumed non-identity, but it would need confirmation to pin the exact panic site).
