### Title
Naive BEEFY verifier path omits MMR leaf freshness check, allowing authority-set rotation suppression - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The naive (`PROOF_TYPE_NAIVE`) BEEFY consensus verification path — `verify_consensus` → `verify_mmr_update_proof` → `verify_mmr_leaf` — never checks that the supplied `latest_mmr_leaf.parent_number_and_hash.0` equals `block_number - 1`. The SP1 path (`verify_sp1_consensus`) explicitly enforces this via `Error::StaleMmrLeaf`, and the Solidity `SP1Beefy.sol`/docs explicitly document why this check is required, but the equivalent naive Rust/EcdsaBeefy-style path lacks it.

### Finding Description
`verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs` advances `trusted_state.latest_beefy_height` to the new commitment's `block_number` and conditionally rotates `current_authorities`/`next_authorities` based on `mmr.latest_mmr_leaf.beefy_next_authority_set.id`, but only after calling `verify_mmr_leaf`: [1](#0-0) 

`verify_mmr_leaf` itself only checks that the supplied leaf hashes into a valid MMR inclusion proof against `mmr_root` — it never checks `parent_number_and_hash.0 + 1 == commitment.block_number`: [2](#0-1) 

Because an MMR is append-only, every historical leaf still produces a valid inclusion proof against the *current* `mmr_root`. An attacker (an unprivileged relayer submitting a proof through the naive path) can therefore submit a commitment for a fresh/high `block_number` (satisfying `StaleHeight` check) while pairing it with an old `latest_mmr_leaf` whose `beefy_next_authority_set` is stale — i.e., a superseded authority set. The verifier will accept it, since `verify_mmr_leaf` only validates the old leaf's inclusion in the current MMR, not its recency.

Contrast this with the SP1 path, which explicitly enforces the freshness check and documents the reasoning: [3](#0-2) 

And the corresponding `Error::StaleMmrLeaf` variant's doc comment describes exactly this attack, but it is only ever constructed in `sp1.rs`: [4](#0-3) 

The naive path is reachable by any relayer via `PROOF_TYPE_NAIVE` in `BeefyConsensusClient::verify_consensus`: [5](#0-4) 

This confirms the described concern is accurate: the naive path is missing the `parent_number + 1 == block_number` check that the SP1 path has, and a dedicated regression test (`rejects_sp1_proof_carrying_a_stale_mmr_leaf`) exists only for the SP1 path, with no analogous test/enforcement for `verify_mmr_update_proof`: [6](#0-5) 

### Impact Explanation
If the naive path's rotation logic is fooled into skipping a real authority-set rotation (by supplying a stale leaf while still advancing `latest_beefy_height`), the trusted consensus state retains a `next_authorities` set that the relay chain has actually retired. A `verify_fraud_proof`/subsequent proof submission signed by that stale-but-still-trusted set could later be used to push a forged state commitment (parachain header / state root) into the ISMP state machine, which downstream modules (asset bridging, order settlement, etc.) treat as authoritative. This can enable false proof acceptance and downstream unauthorized fund movement, matching the "false proof/state acceptance" and "stealing/loss of funds" impact categories.

### Likelihood Explanation
Exploitation requires the attacker to have (or obtain) a validly-signed BEEFY commitment for a target `block_number` from the legitimately active authority set (this is a normal, obtainable artifact from the relay chain, not a forged signature), then pair it with an *old* `latest_mmr_leaf` (also a legitimately obtainable artifact, since it is just a historical leaf with a valid current-root inclusion proof) instead of the leaf actually appended at that block. No signature forgery or privileged access is needed — only assembling a proof from two otherwise-honest artifacts. Whether this is currently reachable in production depends on whether `PROOF_TYPE_NAIVE` is enabled/allowed by the deployed `BeefyClientConfig::allowed_proof_types()`; if the naive path is enabled for any live consensus client, the attack is directly exploitable by any relayer submitting proofs.

### Recommendation
Add the same freshness check to the naive path that exists in `verify_sp1_consensus`: in `verify_mmr_update_proof` (or `verify_mmr_leaf`), require `mmr.latest_mmr_leaf.parent_number_and_hash.0.saturating_add(1) == commitment.block_number`, returning `Error::StaleMmrLeaf` otherwise, mirroring `modules/consensus/beefy/verifier/src/sp1.rs` lines 71-74.

### Proof of Concept
A regression test analogous to `rejects_sp1_proof_carrying_a_stale_mmr_leaf` (in `modules/consensus/beefy/verifier/src/test.rs`) but calling `verify_mmr_update_proof` (or `verify_consensus`) from `modules/consensus/beefy/verifier/src/lib.rs` would demonstrate the gap: construct a valid signed commitment for `block_number = N` from the current authority set, but supply an `mmr.latest_mmr_leaf` whose `parent_number_and_hash.0 = N - 500` (an older leaf still provable against the current `mmr_root` because MMRs are append-only, with a stale `beefy_next_authority_set`). Currently, `verify_mmr_update_proof` will accept this and set `trusted_state.latest_beefy_height = N` without rotating to the real (different, more recent) next authority set — whereas `verify_sp1_consensus` correctly rejects the equivalent construction with `Error::StaleMmrLeaf`.

fn verify_mmr_leaf<H: Keccak256 + Send + Sync>(
	mmr: &MmrProof,
	mmr_root: H256,
) -> Result<(), Error> {
	// `leaf_indices` is supplied by the relayer in the unsigned consensus message;
	// an empty vector previously panicked the runtime via the unchecked `[0]` index
	// after the BEEFY signature and authority membership checks had already succeeded.
	// This verifier checks a single MMR leaf, so reject any proof that does not carry
	// exactly one leaf index.
	if mmr.mmr_proof.leaf_indices.len() != 1 {
		Err(Error::InvalidMmrProof)?
	}
	let leaf_index = mmr.mmr_proof.leaf_indices[0];
	let leaf_hash = H::keccak256(&mmr.latest_mmr_leaf.encode());
	let mmr_size = leaf_index_to_mmr_size(leaf_index);

	let mmr_proof = MmrMerkleProof::<[u8; 32], KeccakMerge<H>>::new(
		mmr_size,
		mmr.mmr_proof.items.iter().map(|h| (*h).into()).collect(),
	);
	let leaf_pos = leaf_index_to_pos(leaf_index);
	let leaf = (leaf_pos, leaf_hash.into());
	let valid = mmr_proof
		.verify(mmr_root.into(), vec![leaf])
		.map_err(|e| Error::MmrVerificationFailed(e.to_string()))?;

	if !valid {
		Err(Error::InvalidMmrProof)?
	}

	Ok(())
}

// SP1 proves that the leaf is *in* the mmr, not that it is the latest leaf, and an mmr is
// append-only — so every historical leaf also proves against the commitment's root. Accepting
// one would advance `latest_beefy_height` while replaying an old `beefy_next_authority_set`,
// suppressing the rotation and stranding the client on a set the relay chain has retired.
#[test]
fn rejects_sp1_proof_carrying_a_stale_mmr_leaf() {
	use beefy_verifier_primitives::Sp1BeefyProof;

	const SET_ID: ValidatorSetId = 42;
	const BLOCK_NUMBER: u32 = 1_000;
	// Mainnet SP1Beefy verification key, as in the fixture test above.
	const VKEY: &str = "0x007d1720c695842ed647a1a72e981751f9b5e26fc5ca038523b23430a1292f08";

	let trusted_state = ConsensusState {
		latest_beefy_height: BLOCK_NUMBER - 1,
		beefy_activation_block: 0,
		mmr_root_hash: H256::zero(),
		current_authorities: authority_set(SET_ID, 100),
		next_authorities: authority_set(SET_ID + 1, 100),
	};

	let mut proof = Sp1BeefyProof {
		block_number: BLOCK_NUMBER,
		validator_set_id: SET_ID,
		mmr_leaf: MmrLeaf {
			version: MmrLeafVersion::new(0, 0),
			parent_number_and_hash: (BLOCK_NUMBER - 1, H256::zero()),
			beefy_next_authority_set: BeefyNextAuthoritySet {
				id: SET_ID + 1,
				len: 100,
				keyset_commitment: H256::zero(),
			},
			leaf_extra: H256::zero(),
		},
		headers: vec![],
		proof: vec![],
		nonce: H256::zero(),
	};

	// The leaf appended at `BLOCK_NUMBER` clears the freshness check and is only rejected
	// later, by the Groth16 verifier — so the check discriminates on leaf freshness alone.
	let fresh = sp_io::TestExternalities::default().execute_with(|| {
		crate::sp1::verify_sp1_consensus::<TestHost>(trusted_state.clone(), proof.clone(), VKEY)
	});
	assert!(matches!(fresh, Err(Error::Sp1VerificationFailed)), "got {fresh:?}");

	// Swap in a leaf from an earlier block, as an attacker replaying a historical leaf would.
	proof.mmr_leaf.parent_number_and_hash.0 = BLOCK_NUMBER - 500;
	let stale = sp_io::TestExternalities::default().execute_with(|| {
		crate::sp1::verify_sp1_consensus::<TestHost>(trusted_state, proof, VKEY)
	});
	assert!(matches!(stale, Err(Error::StaleMmrLeaf { .. })), "got {stale:?}");
