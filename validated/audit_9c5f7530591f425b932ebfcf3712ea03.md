### Title
`githubAssetVideoRegex` performs a naive `startsWith`-style match instead of proper origin validation, allowing attacker-controlled video `src` to bypass the GitHub asset allowlist - (File: `app/src/lib/markdown-filters/video-url-regex.ts`)

### Summary
`VideoTagFilter` is meant to strip any `<video>` tag whose `src` is not hosted on GitHub's trusted `user-images.githubusercontent.com` CDN, and `VideoLinkFilter` is meant to only auto-convert a link into a `<video>` tag when the link target is on that same trusted CDN. Both rely exclusively on `githubAssetVideoRegex` to decide "is this a GitHub user-asset URL". That regex is built with plain string concatenation rather than real URL parsing, so it does not actually anchor the check to the URL's origin/host.

### Finding Description
`githubAssetVideoRegex` is constructed as: [1](#0-0) 

This compiles to `^https://user-images\.githubusercontent\.com.+(mp4|webm|ogg|mov|qt|avi|wmv|3gp|mpg|mpeg|)$` (case-insensitive). Two problems combine to defeat the allowlist:

1. There is no boundary requirement (`/`, `\.`, or an actual `URL().hostname` comparison) right after the literal `https://user-images.githubusercontent.com` string, so `.+` is free to append *any* character sequence, including another host component. A string like `https://user-images.githubusercontent.com.attacker.com/evil.mp4` or `https://user-images.githubusercontent.com@attacker.com/evil.mp4` legitimately starts with the trusted literal and therefore passes `test()`, even though the actual origin the browser/webview will fetch from is `attacker.com`.
2. The trailing extension group `(mp4|webm|ogg|mov|qt|avi|wmv|3gp|mpg|mpeg|)` contains an empty alternative (`...|mpeg|)`), so the "extension" check is effectively optional — any string ending in `.+` will satisfy it regardless of actual file extension, further weakening the check.

Both consumers trust this single regex as their only origin check: [2](#0-1) [3](#0-2) 

The comment in `video-tag-filter.ts` even acknowledges the trust boundary explicitly: unlike dotcom, Desktop does *not* verify against a DB that the asset actually exists, it relies solely on the URL pattern: [4](#0-3) 

Because the regex does not correctly restrict the host, an attacker who controls markdown content that Desktop renders (a PR description, issue body, commit message, or any other API object routed through this markdown-filter pipeline) can craft a `<video src="https://user-images.githubusercontent.com.attacker.tld/x.mp4">` (or an auto-linked equivalent for `VideoLinkFilter`) that survives the filter and is rendered pointing at an attacker-controlled origin.

### Impact Explanation
The practical effect is a bypass of an intended allowlist, not a sandbox escape: the renderer will fetch/play video content from an arbitrary attacker-controlled URL inside the Desktop UI. This can be used to fingerprint/track the victim (their IP, User-Agent, timing) via the video request, or to display attacker content/media inside otherwise trusted-looking rendered markdown. It does not by itself grant code execution, file system access, or credential exfiltration, so severity is bounded — this is an allowlist-bypass / trust-boundary weakening issue rather than an RCE or IPC-escape primitive. I was not able to fully verify from the index alone what network/CSP restrictions apply to `<video>` `src` fetches in the Desktop renderer (e.g., whether a `webRequest`/CSP layer further restricts arbitrary hosts), which would affect the ultimate exploitability; this could not be confirmed from the available files.

### Likelihood Explanation
Likelihood is high for a bypass occurring given attacker-controlled markdown (PR/issue/commit content), since the crafted URL is a simple, no-interaction string that a normal markdown renderer will happily accept — no unusual user action is required beyond viewing the rendered content (which is the app's normal function).

### Recommendation
Replace the string-prefix regex with real URL parsing: parse the candidate `src`/`href` with `new URL(value)` and explicitly check `url.protocol === 'https:'` and `url.hostname === 'user-images.githubusercontent.com'` (exact match, not `startsWith`), then separately validate the pathname/extension. This removes both the host-boundary ambiguity and the meaningless empty-alternative extension match.

### Proof of Concept
1. Craft a GitHub Flavored Markdown body (e.g., a commit message or PR description an attacker controls) containing:
   `<video src="https://user-images.githubusercontent.com.attacker.example/poc.mp4"></video>`
2. Have GitHub Desktop render that content through the markdown-filter pipeline that applies `VideoTagFilter`.
3. Observe that `githubAssetVideoRegex.test(...)` returns `true` (because the string literally starts with the trusted prefix), so the tag is **not** stripped, and the video element is left with an `src` pointing at `attacker.example`, an origin the filter was supposed to reject.
4. Equivalent PoC for `VideoLinkFilter` using an auto-linked `<a href="https://user-images.githubusercontent.com.attacker.example/poc.mp4">…</a>` inside a `<p>`, which will be converted into a `<video>` tag pointing at the attacker origin.
