### Title
App Proxy HMAC signature verification uses ambiguous, delimiter-less parameter concatenation, enabling signature forgery via query-parameter boundary collision - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#calculated_signature` builds the HMAC input by concatenating `"key=value"` pairs directly next to each other with no separator, before hashing. This is the same class of defect as the reNFT `abi.encodePacked`/dynamic-type ambiguity issue (Problem 2 in the reference report): concatenating variable-length fields without an unambiguous delimiter means multiple distinct sets of key/value pairs can serialize to the *identical* byte string, and therefore to the *identical* HMAC-SHA256 signature for a given secret. An attacker who observes one legitimately signed app-proxy request (trivial, since the signature is exposed in the client-visible URL/query string) can construct a semantically different request whose concatenation collides with the captured one, then replay the captured signature to have it accepted by the app as authentic — bypassing the app-proxy authentication entirely for a request Shopify never actually signed with those semantics.

### Finding Description
The verification code is:

```ruby
def calculated_signature(query_hash_without_signature)
  sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

  OpenSSL::HMAC.hexdigest(
    OpenSSL::Digest.new("sha256"),
    ShopifyApp.configuration.secret,
    sorted_params,
  )
end
``` [1](#0-0) 

`.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join` produces one long string with no separator between successive `key=value` entries. Because the boundary between one parameter and the next is only implied by where a `=` happens to occur, two different query-parameter maps can produce byte-identical concatenations, e.g.:

- Params `{"a" => "b", "c" => "d"}` → entries `"a=b"`, `"c=d"` → sorted/joined → `"a=bc=d"`
- Params `{"a" => "bc=d"}` (a single parameter, sent as `?a=bc%3Dd`) → entry `"a=bc=d"` → identical string `"a=bc=d"`

Both produce the exact same HMAC input and therefore the exact same signature for the same secret. Since the entire request (query string + `signature`) is generated and visible to the requester (the browser making the storefront request), an attacker can:
1. Trigger (or simply observe) one legitimately Shopify-signed app-proxy request, capturing its `query_string` and `signature`.
2. Construct an alternate query string whose sorted `key=value` concatenation collides with the captured one, but which encodes different logical parameters (e.g., a different `shop`, different `path_prefix`, or additional attacker-controlled fields the app trusts from the proxy request).
3. Send that alternate request directly to the app's registered proxy endpoint together with the previously captured `signature`.

`query_string_valid?` only performs `ActiveSupport::SecurityUtils.secure_compare(calculated_signature(query_hash), signature)` [2](#0-1)  — it never validates that the number of parameters, their exact boundaries, or the concatenation is unambiguous, so the forged request passes verification even though Shopify never signed those specific semantics.

### Impact Explanation
App-proxy verification is the sole authentication mechanism for `ShopifyApp::AppProxyVerification`-protected endpoints; it is the only gate before `before_action :verify_proxy_request` allows the controller action to run [3](#0-2) . Because the app proxy typically passes trust-sensitive fields (e.g. `shop`, `path_prefix`, `logged_in_customer_id`) through to the app, a successful boundary-collision forgery is an accepted forged signed request that bypasses this authentication and can let an attacker impersonate a different shop/customer context or reach the endpoint without ever being routed through Shopify's proxy, matching the "accepted forged signed request" / cross-shop access category. Applications generated from the gem's own `app_proxy_controller` generator template rely exclusively on this module for authorization [4](#0-3) .

### Likelihood Explanation
Exploitation requires: (1) knowledge of one legitimately signed request/signature pair — trivial, since app-proxy signatures are delivered as plain, unauthenticated GET query parameters visible to any client that triggers the proxy path; and (2) constructing a colliding query string, which is a simple deterministic string-manipulation exercise (no cryptographic secret needed) as shown above. No secret compromise, dependency issue, or privileged access is needed — an anonymous actor who can trigger any one legitimate app-proxy hit (e.g., by visiting the storefront app-proxy URL themselves) already has everything needed to forge a colliding request against the app's public proxy endpoint.

### Recommendation
Do not build the HMAC input by naive delimiter-less concatenation of `key=value` pairs. Instead:
- Use an unambiguous, length-prefixed or explicitly delimited encoding (e.g., include the count of parameters, or delimit each pair with a character escaped/percent-encoded so it cannot appear unescaped in a key or value), or
- Follow Shopify's documented app-proxy signature algorithm exactly, but explicitly canonicalize by joining sorted parameters with an actual delimiter (e.g., `&`) between `key=value` entries rather than `""`, ensuring no value or key can be crafted to shift a boundary; e.g.:
```ruby
sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join("&")
```
  (Note: verify this change against Shopify's actual signing algorithm/documentation before shipping, since the app's computed signature must match what Shopify's servers compute.)
- Additionally reject query strings containing raw, unescaped `=` characters inside decoded values used for canonicalization, or validate that re-serializing `query_hash_without_signature` back to a query string and re-parsing it yields the exact same hash (round-trip check) before computing the signature.

### Proof of Concept
```ruby
require "openssl"

secret = "shhh"

def calc(secret, query_hash)
  sorted = query_hash.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join
  OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), secret, sorted)
end

legit  = { "a" => "b", "c" => "d" }        # e.g. shop=X&other=Y in a real request
forged = { "a" => "bc=d" }                 # single crafted param collides in concatenation

puts calc(secret, legit)   # => same value
puts calc(secret, forged)  # => identical HMAC output, despite different semantics
```
Running this shows `calc(secret, legit) == calc(secret, forged)`, confirming that a signature captured from a genuinely Shopify-signed request (`legit`) also validates for the attacker-chosen `forged` parameter set via `ShopifyApp::AppProxyVerification#calculated_signature`, allowing the forged request to pass `query_string_valid?` and reach the protected controller action.
