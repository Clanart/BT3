**Analysis:**

`BatchVerifyMultiPoints` (internal/kzg/kzg_verify.go) has a `batchSize == 1` short-circuit that calls `Verify` directly [1](#0-0) , while `batchSize > 1` uses the randomized-linear-combination technique: sampling one fresh random field element via `randomNumber.SetRandom()`, computing `randomNumbers := utils.ComputePowers(...)`, and folding commitments/evaluations/quotients before a single `PairingCheck` [2](#0-1) .

The invariant claimed to be tested (`batch accepts <=> every member individually accepts`) holds up to the standard, negligible soundness error of randomized batch-opening schemes (probability ~1/|F_r|, i.e. ~2^-255 for BLS12-381 scalar field). This is not a code defect — it is the intended and universally-used cryptographic technique for KZG batch verification, matching the consensus-specs `verify_kzg_proof_batch` reference implementation and c-kzg's approach. Key points that defeat the proposed attack:

1. **Completeness is perfect**: if the (commitment, proof, point, value) tuple is a genuine opening, folding it (even duplicated) with any random scalar linear combination still satisfies the pairing equation, so both the size-1 `Verify` path and the size-2 folded path will always accept a valid duplicate — they cannot diverge on valid inputs.
2. **Soundness is probabilistic by design**: for an invalid (forged) tuple, the size-1 `Verify` deterministically rejects (it's a direct pairing check with no randomness), and the size-2 folded path rejects except with cryptographically negligible probability tied to the freshly sampled `randomNumber`, which the attacker cannot predict, choose, or influence because it is generated via `SetRandom()` per call and is not derived from any attacker-controlled transcript (no Fiat-Shamir on attacker bytes to grind).
3. **Replay across two calls does not help the attacker**: each call to `BatchVerifyMultiPoints` samples an independent fresh `randomNumber`; there is no shared/pooled state between calls (no cache, no memoization of `randomNumbers`), so an attacker cannot use one call's outcome to predict or bias another's.

Since acceptance/rejection can only diverge between the size-1 and size-2 paths with negligible probability inherent to any randomized batch-KZG verifier (a property shared with the reference spec and c-kzg, not a deviation from them), this does not meet the required impact bar (accepted-but-not-a-true-opening, or a deterministic disagreement with the spec for the same input).
