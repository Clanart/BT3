## Title
Persistent ERC20 allowance granted to IBC receive-packet callback contracts is never revoked and is committed to state even when the callback safety-check fails, enabling theft of user funds - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`ContractKeeper.IBCReceivePacketCallback` approves an arbitrary, packet‑memo‑supplied `contractAddress` to spend the full transferred amount of ERC20 tokens owned by a deterministic "isolated address," then invokes that contract. This mirrors the audited Oku pattern: an allowance is granted to an externally‑controlled/untrusted contract before an external call, and it is never reset to zero afterward. Worse, the state produced by the approve + external call is committed via `writeFn()` **before** the function's own safety check (`receiverTokenBalance == 0`) runs, so even when that check fails and the function returns an error, the dangling allowance is already durably persisted on-chain.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, `IBCReceivePacketCallback`: [1](#0-0) 

grants `contractAddr` (attacker/memo-controlled, taken directly from the ICS-20 `dest_callback.address` field) an ERC20 `approve` for `amountInt` (the full packet amount) over the isolated address `receiverHex`'s balance, then calls the contract with attacker-controlled `calldata`: [2](#0-1) 

The isolated address is deterministic and reused across every packet from the same `(destChannel, sender)` pair, with no private key ever able to sign for it: [3](#0-2) . The module's own documentation confirms that any tokens left in the isolated address are considered permanently unreachable by design: [4](#0-3) .

The critical ordering flaw is that `writeFn()` — which commits **all** of the cached-context state changes (the `approve` call and whatever the callback contract executed) back into the real context — is invoked at line 227, **before** the balance-based safety check at lines 234-239 that is supposed to catch incomplete fund transfers. If the callback contract's code completes successfully (no EVM-level revert) but only partially spends the granted allowance (e.g., transfers 1 wei via `transferFrom` and leaves the rest), then:
1. The `approve(contractAddr, amountInt)` and partial `transferFrom` are permanently committed via `writeFn()`.
2. The subsequent balance check fails (`receiverTokenBalance != 0`) and the function returns an error, which per the module's design becomes an `ErrAck` — but this only affects the acknowledgement, not the already-committed state.
3. The residual allowance (`amountInt - partialSpend`) granted to `contractAddr` over the isolated address's tokens is never reset to zero, exactly as in the Oku bug (`order.tokenIn.safeApprove(target, order.amountIn)` followed by no `approve(target, 0)`).

Because `contractAddr` is an ordinary contract that anyone can re-invoke at will (it is not consumed or destroyed), the same allowance can be exercised again at any later time to call `transferFrom(isolatedAddr, attacker, remainingAllowance)`, extracting tokens that the protocol's own documentation describes as permanently "unreachable."

### Impact Explanation
This allows unauthorized extraction of user funds that are otherwise supposed to be inaccessible (stuck in the isolated address). Any dest-callback contract that does not perfectly consume its granted allowance in one shot — whether due to attacker design or ordinary contract bugs/edge cases — leaves a standing, unrevoked ERC20 allowance that can be drained later, at the attacker's leisure, regardless of whether the original callback "succeeded" per the on-chain acknowledgement. This is a direct theft/unauthorized-extraction-of-user-funds primitive against token-pair-backed ERC20 balances, matching the Critical impact bucket for theft/unauthorized extraction of user funds and token-pair-backed balances.

### Likelihood Explanation
The `dest_callback.address` and `dest_callback.calldata` fields are fully attacker/sender-controlled memo fields on an ICS-20 transfer — no privileged or validator access is required. An attacker triggering a transfer to themselves (self-targeting their own isolated address) with a purpose-built callback contract that deliberately transfers less than the full approved amount can reliably reproduce this every time. No race condition or timing dependency is needed; the vulnerable ordering (`writeFn()` before the balance check) is deterministic and always executed on this code path.

### Recommendation
- Perform the `receiverTokenBalance == 0` safety check **before** calling `writeFn()`, so that a failing check discards the cached state (including the approval) rather than committing it.
- Additionally/defensively, always reset the allowance to zero after the callback call regardless of success or failure (`approve(contractAddr, 0)`), mirroring the standard "approve, call, revoke" pattern, so no residual allowance to `contractAddr` ever survives a single callback invocation.

### Proof of Concept
1. Attacker (as the source-chain `sender`) computes their own isolated address: `isolatedAddr = GenerateIsolatedAddress(destChannel, attackerSenderAddr)`.
2. Attacker deploys a malicious EVM contract `Evil` on the destination chain whose callback entrypoint calls `token.transferFrom(isolatedAddr, attackerAddr, 1)` (spending only 1 unit of the granted allowance) and then returns normally (no revert).
3. Attacker sends an ICS-20 transfer with `receiver = isolatedAddr`, `amount = amountInt`, and memo:
   ```json
   {"dest_callback": {"address": "<Evil address>", "gas_limit": "1000000", "calldata": "<encoded call>"}}
   ```
4. On receipt, `IBCReceivePacketCallback` approves `Evil` for `amountInt`, calls `Evil`, which transfers `1` unit out and leaves `amountInt - 1` in `isolatedAddr` with `amountInt - 1` allowance still granted to `Evil`.
5. `writeFn()` commits this state. The subsequent balance check fails (`amountInt - 1 != 0`), the function returns an error/ErrAck — but the approval is already persisted.
6. At any later time, the attacker calls `Evil.drainRemaining()` (a second function on their own contract) which executes `token.transferFrom(isolatedAddr, attackerAddr, amountInt - 1)`, fully draining the "stuck"/"unreachable" tokens using the still-valid, never-revoked allowance. [5](#0-4)

## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
