## Title
Stale partial-commit line selections are silently re-applied to a freshly generated diff, letting attacker-controlled remote content corrupt what the user actually commits - (File: `app/src/lib/git/apply.ts`, `app/src/lib/stores/updates/changes-state.ts`)

### Summary
This is the closest Desktop analog to the TraitForge `nuke()` bug: a value (there, the `fund`; here, a per-line commit *selection*) is computed against one state snapshot but consumed against a *different, later* state snapshot, with no check that the two still agree. In `nuke()`, `claimAmount` was computed from a stale `fund`. In Desktop, a user's line-by-line "include in this commit" selection is computed against one diff, but at staging time Desktop silently regenerates a *fresh* diff and blindly re-applies the old line indices to it, with no validation that the file hasn't changed underneath the selection.

### Finding Description
When a user does a partial/line-level commit, the UI keeps a `DiffSelection` bit-set of "selected" absolute line indices for a `WorkingDirectoryFileChange`, computed against the diff that was rendered at selection time.

That selection is carried forward across every working-directory status refresh (which fires automatically on filesystem events) with **no revalidation** unless the file happens to be the one currently displayed in the diff viewer: [1](#0-0) 

Only the *currently selected/displayed* file's selection is revalidated (`withSelectableLines`) when its diff is reloaded: [2](#0-1) 

Any other file in the Changes list that has a pending partial selection (e.g. the user partially staged file A, then switched focus to file B, then pulled/merged/checked out something that modified file A) keeps its old line-index selection unchanged.

When the commit is finally triggered, `_commitIncludedChanges` takes the current in-memory `WorkingDirectoryFileChange` objects (with their possibly-stale selections) and stages them: [3](#0-2) 

Staging for a partially-selected file calls `applyPatchToIndex`, which **re-fetches the diff from disk at that exact moment** — not the diff the user actually reviewed: [4](#0-3) 

`formatPatch` then walks the *new* diff's hunks and decides what to include purely by absolute line index membership in the stale selection, with no check that the new hunk content matches what the user saw when selecting: [5](#0-4) 

The broken invariant: "the lines the user visually selected for inclusion are the lines that get committed." Nothing enforces that the diff used to build the patch is the same diff the selection indices were derived from — exactly analogous to `nuke()` using a `fund` value that had changed since `finalNukeFactor` was computed.

### Impact Explanation
If the working-tree content of a file with a pending partial selection changes between selection time and commit time — for example because the user pulled/merged a branch (attacker-controlled remote content), checked out another branch and back, or a background tool/filter touched the file — Desktop will stage whatever lines happen to fall at the old selected line offsets in the *new* diff, not the content the user actually reviewed. This can silently commit and push attacker-influenced or unintended content while the UI gave no indication that the file changed, corrupting what the user believes they are committing/pushing (data integrity impact on commit history, potential to smuggle in unreviewed changes).

### Likelihood Explanation
This requires no local/physical access, no malware, and no credentials: it only requires an unprivileged action the user naturally performs while Desktop is open — pulling/merging/checking out a branch (which can bring in content from an attacker-controlled remote/fork) while a partial selection is pending on an unrelated open file in the Changes list. Because status/diff refreshes happen automatically and asynchronously and only the *focused* file's selection is revalidated, the race window is realistic in normal day-to-day multi-file workflows, not a contrived edge case.

### Recommendation
- Store (or hash) the diff/hunk fingerprint alongside the `DiffSelection` for every file with a partial selection, not just the currently displayed one.
- Before staging, re-fetch the diff and compare it to the fingerprint used to build the selection; if it differs, clear/re-map the selection (as already done via `withSelectableLines` for the focused file) or block the commit and prompt the user to re-review.
- Alternatively, have `applyPatchToIndex`/`stageFiles` reuse the diff object already held in application state (when available and fresh) instead of unconditionally re-fetching from disk at staging time.

### Proof of Concept
1. Modify `file.md` and open it in Desktop; a diff with hunks H1/H2 is generated and displayed.
2. Select only specific lines in H1 for partial commit (leave H2 unselected). This selection is stored as absolute line indices in `DiffSelection`.
3. Without touching `file.md`, switch focus in the Changes list to a different file `other.md`.
4. Pull/merge a branch (e.g. from a remote/fork you don't fully trust) that also modifies `file.md`, changing its hunk boundaries/line offsets but keeping the same file `id`. Desktop's background status refresh merges the new `file.md` status but reuses the old `existingFile.selection` unchanged per `updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:56`), and no revalidation runs because `file.md` isn't the focused file.
5. Click Commit. `_commitIncludedChanges` stages `file.md`, `applyPatchToIndex` re-fetches the diff fresh (`app/src/lib/git/apply.ts:60`), and `formatPatch` applies the old absolute-index selection to the new hunks (`app/src/lib/patch-formatter.ts:157`), staging/committing different lines than what the user originally selected — silently.
