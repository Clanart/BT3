Based on the investigation, I found a legitimate, code-proven analog for permanently-locked/unrecoverable funds, arising from Sei's Cosmos↔EVM address-association model, which is functionally the closest reachable analog to the Hegic pattern (funds becoming permanently stuck because the protocol logic silently prevents them from ever being spent/claimed).

### Title
Funds sent to the direct-cast Sei address of a not-yet-associated EVM account become permanently unspendable once that EVM address is later associated to a different pubkey - ([File: x/evm/keeper/address.go])

### Summary
Sei allows an EVM address to be referenced by its direct byte-cast Cosmos `AccAddress` before the account is formally "associated" with a real pubkey-derived Sei address. `CanAddressReceive`/`CanSendTo` gate whether that cast address may *receive* new funds once association happens, but any balance that was already sent to the cast address **before** association is not protected against the case where the true owner's EVM key later gets associated with a *different* Sei address (via `associatePubKey`), permanently orphaning the previously-received balance under an address nobody can spend from through normal transaction signing.

### Finding Description
`CanAddressReceive` in `x/evm/keeper/address.go` intentionally blocks the bank module from crediting a cast address (`sdk.AccAddress(evmAddress[:])`) once that EVM address has been associated with a *different* true Sei address: [1](#0-0) 

This same logic is duplicated in the `giga` engine's keeper: [2](#0-1) 

The intent is that once an EVM address's real Sei identity is known, direct-cast addresses should stop accepting deposits (deposits get migrated during association instead, see `AssociateAddresses`/`MigrateBalance`): [3](#0-2) 

However, this protection is a point-in-time migration only. `sei-cosmos/x/distribution/keeper/keeper_test.go`'s own regression tests demonstrate the resulting permanent-loss/no-payout condition explicitly: a validator operator address that is a direct EVM cast address can later be re-associated (via `associatePubKey`) to a *different* Sei address. After that re-association, `CanSendTo`/`BlockedAddr`-style checks report the original cast address as unable to receive funds, and any commission/rewards addressed to it can never be paid — the distribution module falls back to the community pool instead of crashing: [4](#0-3) 

The same "already has funds parked at an address that later becomes permanently unpayable" pattern is also explicitly handled (not crashed on, but funds retained/never delivered) in `x/gov`'s deposit refund logic, which documents that recovering such deposits "requires a migration": [5](#0-4) 

Root cause: any unassociated cast address that accumulates a balance (native usei/wei, staking rewards, deposits, etc.) via ordinary transfers is fully spendable up until the moment its EVM counterpart re-associates to a *different* Sei address. From that point forward, that address is unable to receive top-ups and — more importantly — outbound movement of the funds it already holds depends entirely on whoever controls the signing key for that literal 20-byte address continuing to be able to sign for it. Since Sei's association model explicitly severs the "true owner" relationship between the EVM key and that cast address once re-associated to someone else, the original depositor generally has no path to reclaim funds already resting there except an ad-hoc chain migration (as literally called out in the `gov` module comment). This mirrors the Hegic incident's core failure mode: funds get stranded in a contract/account state that the protocol's normal user-facing operations cannot unwind, requiring an off-chain/administrative remediation.

### Impact Explanation
Funds (native usei/wei balances, staking rewards, or CW/native token balances sent to the cast address of an EVM account) can become permanently unrecoverable through normal user transactions once the corresponding EVM address is associated to a different Sei identity. This is a fund-freezing bug matching the "Medium" severity class of the Hegic report (funds stuck, not stolen), reachable purely by an ordinary EVM/Cosmos user sending a transaction to an unassociated address and a later `associatePubKey`/`AssociateAddresses`-style call by anyone controlling that EVM key.

### Likelihood Explanation
This requires no special privilege: any user can send funds to any valid Sei-format address (including a cast/direct-mapped EVM address) before it is associated, and any holder of the corresponding EVM private key can later associate that EVM address with an unrelated true Sei address via the standard `associatePubKey`/association flow. This is a normal, commonly exercised code path (association happens automatically on the first EVM transaction from an address per `x/evm/ante/preprocess.go`), so the scenario is readily reachable, though it requires a specific ordering of events (deposit before final association) to actually strand funds.

### Recommendation
Extend the balance-migration logic so that re-association events sweep any residual balance sitting at the previous cast address to the newly associated true Sei address (similar to what `MigrateBalance` already does at initial association time), rather than only protecting against *future* deposits via `CanAddressReceive`. Alternatively, provide a permissionless on-chain "sweep" precompile/message that lets the EVM key holder recover any balance still parked at their cast address regardless of current association state, removing the need for governance-level migrations as referenced in the `x/gov` deposit-refund comment.

### Proof of Concept
1. Do not associate EVM address `E` (do not send any tx from it yet).
2. Have any user send `usei` to `sdk.AccAddress(E[:])` (the cast address) via `MsgSend` or an EVM-side precompile transfer — this succeeds because `CanAddressReceive`/`CanSendTo` return true for unassociated cast addresses.
3. From EVM address `E`, submit an `associatePubKey`-style association that maps `E` to a different true Sei address `S'` (not equal to `sdk.AccAddress(E[:])`) — e.g. by using the "associate addresses" precompile flow illustrated in the distribution keeper test's `SetAddressMapping` call: [6](#0-5) 
4. Query `CanSendTo`/`CanAddressReceive` for the cast address — it now returns false, and any subsequent deposit or refund destined for that cast address is retained rather than delivered, exactly as demonstrated by `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`: [7](#0-6) 
5. The `usei` balance deposited in step 2 remains at the cast address, which per the code comment in `x/evm/keeper/address.go` cannot receive new funds and (per the observed distribution-module fallback behavior) cannot be reliably paid out through standard flows either, leaving it stranded absent a manual migration.

	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator covers the
// case where the validator operator address itself cannot receive funds — its EVM
// address was re-associated (e.g. via associatePubKey) away from the direct-cast Sei
// address it was created under. The withdraw-address fallback in GetDelegatorWithdrawAddr
// resolves back to that same unreceivable operator address, so the commission
// force-withdraw fails. AfterValidatorRemoved runs during EndBlock, so it must not panic:
// the commission is routed to the community pool instead, which conserves value because
// the coins already back the distribution module account.
func TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	// The validator operator is the direct-cast Sei address of an EVM address.
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	castAddr := sdk.AccAddress(evmAddr[:])
	valAddr := sdk.ValAddress(castAddr)
	valAccAddr := sdk.AccAddress(valAddr) // == castAddr

	require.True(t, app.BankKeeper.CanSendTo(ctx, castAddr))

	// Re-associate the EVM address to a different true Sei address, mirroring
	// associatePubKey after a validator was created under the direct-cast address.
	associatedAddr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))[0]
	app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)

	// The operator/delegator address can no longer receive funds, and the
	// withdraw-address fallback resolves back to that same unreceivable address.
	require.False(t, app.BankKeeper.CanSendTo(ctx, castAddr))
	require.Equal(t, valAccAddr.String(), app.DistrKeeper.GetDelegatorWithdrawAddr(ctx, valAccAddr).String())

	commission := sdk.DecCoins{sdk.NewDecCoin("usei", sdk.NewInt(10))}
	coins := sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(10)))
	distrAcc := app.DistrKeeper.GetDistributionAccount(ctx)
	require.NoError(t, apptesting.FundModuleAccount(app.BankKeeper, ctx, distrAcc.GetName(), coins))
	app.AccountKeeper.SetModuleAccount(ctx, distrAcc)

	app.DistrKeeper.SetValidatorOutstandingRewards(ctx, valAddr, types.ValidatorOutstandingRewards{Rewards: commission})
	app.DistrKeeper.SetValidatorAccumulatedCommission(ctx, valAddr, types.ValidatorAccumulatedCommission{Commission: commission})

	communityBefore := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	moduleBalanceBefore := app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei")

	require.NotPanics(t, func() {
		app.DistrKeeper.Hooks().AfterValidatorRemoved(ctx, sdk.ConsAddress{}, valAddr)
	})

	// The commission could not be paid out, so it stays in the distribution module
	// account and is accounted to the community pool. No value leaves the module and
	// the unreceivable operator address receives nothing.
	communityAfter := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	require.Equal(t, communityBefore.Add(sdk.NewDec(10)), communityAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, castAddr, "usei").IsZero())
	require.Equal(t, moduleBalanceBefore, app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei"))

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
