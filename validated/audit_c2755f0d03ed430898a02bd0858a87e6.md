### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s — funds reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Allo bug class is a mismatch between the value actually moved and the value the protocol accounts for, leaving funds stranded inside the contract. In `bitcoin-serai`, the same accounting-vs-spendability mismatch exists in `Scanner::scan_block`: it iterates over `block.txdata` including `txdata[0]` (the coinbase transaction) and returns any output paying to a registered script as a normal `ReceivedOutput`. Coinbase outputs are consensus-immature for 100 blocks, yet the scanner reports them identically to ordinary outputs, so downstream accounting credits funds that cannot be spent.

### Finding Description
`Scanner::scan_transaction` has no notion of transaction position within a block; it matches solely on `output.script_pubkey` and pushes a `ReceivedOutput { offset, output, outpoint }` for every match [1](#0-0) . `scan_block` then applies this to every transaction, including the coinbase at index 0 [2](#0-1) .

A `ReceivedOutput` produced by the scanner is treated as spendable input material: `SignableTransaction::new` consumes `ReceivedOutput`s directly to build `tx_ins`/`prevouts` [3](#0-2) , and `multisig` produces real FROST signature machines for them [4](#0-3) . Nothing in the scan→sign path checks coinbase maturity. The only safeguard is a doc comment on `scan_block` saying "a post-processing pass is needed" — the code itself performs no filtering, and the valid use `scan_transaction(&block.txdata[1..])` is left to the caller.

Any unprivileged miner can place an output paying to Serai's P2TR script in their coinbase (the script is public). The scanner reports it received; if consumed before maturity the resulting transaction is consensus-invalid, and if the block is reorganized out, the output ceases to exist while it was already credited.

### Impact Explanation
Funds are reported as received that are not spendable: deposit/balance accounting credited from `scan_block` overstates spendable funds for up to 100 blocks, and permanently if the block is orphaned. Additionally, the signing pipeline will happily produce a fully-signed transaction spending an immature coinbase output, which is rejected by the network — a plausible liveness/operating-cost sink mirroring the "stuck funds" impact of the original report.

### Likelihood Explanation
Requires a miner (or a coinbase payout recipient influencing the coinbase template, e.g., a pool payout address) to pay to the scanned script. No protocol privilege is needed; the attack surface is any party capable of creating a coinbase output. Accidental triggering is also possible whenever a mining pool payout coincides with a registered deposit script. Severity Medium: temporary accounting inflation and wasted signing/broadcast effort, with permanent mis-credit under a reorg.

### Recommendation
In `Scanner::scan_block`, skip `block.txdata[0]` (the coinbase) entirely — i.e., iterate `block.txdata[1..]` — so the safe behavior is the default. If coinbase scanning is ever desired, tag `ReceivedOutput`s originating from coinbase transactions and require an explicit maturity check before they can be passed to `SignableTransaction::new`.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
