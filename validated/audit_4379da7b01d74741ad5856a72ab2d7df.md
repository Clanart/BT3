## Analysis

The Sherlock report's core issue is a **boundary/off‑by‑one flaw in a containment check** (`>` used where `>=` was required), which caused a value that should have been considered "inside" the valid range to be treated as invalid. The closest structural analog in GitHub Desktop is the opposite failure mode of the same class of bug: a path-containment check that uses a **string-prefix comparison without a separator boundary**, which causes a value that should be **outside** the trusted directory to be incorrectly treated as **inside** it.

This is implemented in `resolveWithin()`: [1](#0-0) 

### Title
Path-containment check in `resolveWithin()` uses prefix comparison without directory-separator boundary, allowing traversal to sibling directories - (File: app/src/lib/path.ts)

### Summary
`resolveWithin()` is Desktop's designated guard against path traversal/symlink escape when resolving attacker/remote-influenced relative paths against a trusted root (e.g. the repository directory). Its final check is:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` performs a raw substring comparison, not a path-segment comparison. If `realRoot` is `/Users/victim/Documents/GitHub/app` and the resolved path is `/Users/victim/Documents/GitHub/app-secrets/config.json` (a sibling directory whose name happens to have `app` as a prefix), `startsWith` returns `true` even though `app-secrets` is a completely different directory outside of `app`. The missing check is that the character immediately following `realRoot` in `realResolved` must be a path separator (or `realResolved === realRoot`).

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` normalizes the caller-supplied segments, resolves them relative to `rootPath`, and is supposed to guarantee the result stays "at or underneath" `rootPath`: [3](#0-2) 

The unit tests only cover exact round-trip traversal (`..` then back into the exact same root, verified via `basename(root)`), and symlink-based escapes — but never test the case of a sibling directory whose name is a superstring of the root's basename: [4](#0-3) 

This function is used to resolve attacker/remote-influenced relative paths against the repository root in at least two security-relevant call sites:

1. **Deep link `filepath` parameter** — fully attacker-controlled via a URL a user clicks (`x-github-client://openRepo/...&filepath=...`), parsed in `parse-app-url.ts` and consumed in `openRepositoryFromUrl`: [5](#0-4) 

2. **Copilot conflict-resolution file writer**, which writes AI/model-derived content to disk after resolving the path via the same guard: [6](#0-5) 

3. **Copilot conflict context file reader**: [7](#0-6) 

In all three cases, the code's threat model explicitly assumes `resolveWithin` returning non-null means "the path is safely confined to the repository," and treats a `null` result as the only rejection signal. The prefix-only comparison silently violates that invariant when a sibling path shares a directory-name prefix.

### Impact Explanation
For the deep-link path (case 1), a malicious webpage/email only needs to know (or guess) that a user has two adjacent local folders where one name is a prefix of another (e.g. `project` and `project-backup`, or `repo` and `repo2` — a common pattern for forks/backups) under the same parent. Clicking a crafted `x-github-client://openRepo/...` link causes Desktop to call `shell.showItemInFolder(resolved)` on a path outside the intended repository, revealing/opening arbitrary files elsewhere on disk outside the repo. For the Copilot write path (case 2), the same class of confusion could cause `writeFile` to target a file outside the repository if a resolution path and directory naming coincide in this way, silently corrupting content the user did not intend to touch — matching the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
Exploitation requires the coincidental existence of a sibling directory name that is a prefix/superset of the trusted root's name, which is a common naming pattern (`repo`/`repo-old`, `app`/`app2`, `project`/`project-private`). The deep-link vector requires only a single click and no other conditions from the attacker's side, matching the "link the user clicks" trust boundary. This is a well-known class of bug (CWE-22 variant: improper path-prefix validation without separator boundary) and the existing unit tests for `resolveWithin` do not cover this exact scenario, suggesting it was not considered.

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a match followed by the platform path separator, e.g.:
```js
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the separator appropriate to the `options` passed in, i.e. `Path.sep`, `Path.posix.sep`, or `Path.win32.sep`), and add regression tests for sibling-directory-name-prefix cases.

### Proof of Concept
1. Locally have two folders side by side: `/Users/victim/Documents/GitHub/app` (the Desktop-tracked repository) and `/Users/victim/Documents/GitHub/app-secrets/config.json` (an unrelated folder/file).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/app?filepath=..%2Fapp-secrets%2Fconfig.json`.
3. Desktop parses the URL via `parseAppURL`, producing `filepath = "../app-secrets/config.json"` (relative, passes the `isAbsolute` check), and calls `resolveWithin(repository.path, filepath)`.
4. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/app-secrets/config.json`; `realRoot` is `/Users/victim/Documents/GitHub/app`. Because `realResolved.startsWith(realRoot)` is `true` (string prefix match), the function returns the out-of-repo path instead of `null`.
5. `dispatcher.ts` then calls `shell.showItemInFolder(resolved)`, revealing/opening a file completely outside the repository that the attacker predicted the name of — despite the code's explicit intent to "prevent attempt to open path outside of the repository root." [8](#0-7) [9](#0-8)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
