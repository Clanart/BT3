Based on the investigation, the strongest analog in GitHub Desktop is a trust-boundary gap in the Copilot merge-conflict auto-resolution flow, structurally similar to the original bug: code assumes an invariant ("the model will only return resolutions for genuinely conflicted files") that is never actually enforced at the point where the side effect (file write / staging) happens — just like GroupBuy assumed "equal price never displaces" but never enforced it with `<=`.

### Title
Copilot conflict-resolution acceptance writes/staged files without verifying the path was an actual unresolved conflict, letting a malicious repo (via prompt-injected commit/PR content) cause silent corruption of committed files - (File: app/src/lib/stores/app-store.ts)

### Summary
When the user accepts Copilot's AI-generated merge-conflict resolutions, `app-store.ts` iterates `copilotResolutions` and, for each entry, resolves the path within the repo and writes `resolution.resolvedContent` to disk, then stages it for commit. The only guard that skips a write is a check for whether the path already refers to a *resolved* conflicted file in the working directory; there is no check that the path was one of the files actually presented to the model as conflicted in the first place.

### Finding Description
In the acceptance handler, resolutions are only skipped if an on-disk entry exists, is a conflicted-file status, and no longer has unresolved conflict markers: [1](#0-0) 

For any other case — including a path that does not correspond to a conflicted file at all (e.g. an unrelated clean tracked file elsewhere in the working tree) — the code falls straight through to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and adds it to `pathsToStage`, which is later `git add`-ed: [2](#0-1) 

The only sanitization applied to `resolution.path` is `resolveWithin(repository.path, resolution.path)`, which correctly prevents traversal outside the repository root via `realpath` checks, but says nothing about whether the path is one of the files that were actually part of the merge/rebase/cherry-pick conflict set: [3](#0-2) 

The model's JSON response format explicitly instructs it to return a `path` per resolved file, driven by an LLM prompt that ingests attacker-influenced repository content — commit messages, PR title/description, and conflict-marker context from both merge sides: [4](#0-3) 

Because the model's output is free-form JSON generated from content the repository owner (attacker) fully controls (commit messages, PR description, diff content), a crafted commit/PR — reachable simply by the victim cloning/fetching the repo and hitting a conflict that invokes Copilot resolution — can attempt to make the model emit a `resolutions[].path` entry pointing at a file that was never conflicted (any tracked, non-conflicted file in the repository). Nothing in the acceptance path cross-checks `resolution.path` against the original conflicted-file set before calling `writeFile`; the check only inspects the *current* on-disk status of that path, which for a non-conflicted file will be `undefined` from `hasUnresolvedConflicts` reasoning and will not trigger the `continue`.

### Impact Explanation
This matches the "silent corruption of what the user commits or pushes" impact category: a file outside the actual conflict — potentially security-relevant code, CI config, or other tracked content — gets its content silently replaced and staged into the merge/rebase commit without any diff review specific to that file being shown to the user in the normal unresolved-conflict list, since it was never flagged as conflicted in the first place.

### Likelihood Explanation
Exploitation requires: (1) the attacker controls a repository or branch the victim merges/rebases/cherry-picks with Copilot conflict resolution enabled, and (2) the LLM can be steered via prompt injection embedded in commit messages/PR text to emit an out-of-scope `path`. Condition (2) depends on model compliance and is not guaranteed by design — I was not able to verify from the index whether there is server-side or client-side validation elsewhere (e.g. when the JSON response is parsed) that filters `resolutions` to the known conflicted-file list before it's placed into `state.multiCommitOperationState.copilotResolutions`. I searched for such validation (schema/zod checks, `conflictedFilePaths` cross-referencing) but could not confirm its presence or absence within the indexed portion of `copilotResolutions`. This is the key remaining uncertainty, and it should be verified directly in a full checkout before treating this as confirmed rather than probable.

### Recommendation
Before writing/staging any Copilot resolution, explicitly validate `resolution.path` against the authoritative set of conflicted file paths captured at the time the resolution request was built (not just against current on-disk status), and reject/skip any resolution whose path falls outside that set — mirroring the `<=` fix pattern from the original report: make the boundary condition ("is this file actually one we're allowed to touch?") an explicit, enforced check rather than an implicit assumption about model behavior.

### Proof of Concept
Conceptual PoC (not fully verified against unseen parsing code):
1. Attacker prepares a repository/branch such that merging it with the victim's branch produces a real conflict in file `a.txt`, and includes a commit message or PR description crafted to prompt-inject the model, e.g. instructing it to also "resolve" `b.txt` (a normal, unconflicted, tracked file) with attacker-chosen content.
2. Victim clones/fetches and triggers a merge that hits the Copilot conflict-resolution flow; the prompt in `ConflictResolutionSystemPrompt` is sent along with attacker-controlled commit/PR content [4](#0-3) .
3. If the model returns a `resolutions` entry for `b.txt`, the acceptance handler resolves the path, finds no matching *conflicted* `onDiskFile`, and proceeds to `writeFile` + stage it [5](#0-4) .
4. The victim commits, silently including attacker-chosen content in `b.txt` that was never part of the reviewed conflict set.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
