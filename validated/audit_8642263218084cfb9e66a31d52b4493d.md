## Finding [1](#0-0) 

`getResolutionDiff` in `app/src/lib/git/diff.ts` reads the working-tree file content by simple path concatenation and `fs/promises.readFile`, with **no symlink/traversal guard**:

```ts
const baseContent = await readFile(
  Path.join(repository.path, filePath),
  'utf8'
)
``` [2](#0-1) 

Compare this to the sibling function `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts`, which handles the *exact same* class of input (a conflicted file's relative path from the working directory) and explicitly defends against exactly this attack:

```ts
// Guard against path traversal and symlink escapes (cross-platform)
let absolutePath: string | null
try {
  absolutePath = await resolveWithin(workingDirectory, file.path)
} catch { ... }
if (absolutePath === null) {
  return { path: file.path, hunks: [], skippedReason: 'File path is outside the repository' }
}
``` [3](#0-2) 

`resolveWithin` (`app/src/lib/path.ts`) is the project's designated safe-join primitive; it resolves symlinks via `realpath` and rejects anything that escapes the root, and there's a dedicated regression test proving it blocks symlink escapes: [4](#0-3) [5](#0-4) 

`getResolutionDiff` never calls `resolveWithin`, `Path.join` alone does not resolve symlinks, and `fs.readFile` follows symlinks by default — so if `filePath` resolves (via an on-disk symlink) to a location outside `repository.path`, the function will silently read that external file.

### Title
Symlink-escape file read outside the repository in Copilot conflict-resolution diff preview - (File: app/src/lib/git/diff.ts)

### Summary
`getResolutionDiff`, used to render the "ours/theirs/Copilot" diff preview in the Copilot merge-conflict resolution UI, reads the on-disk conflicted file via unguarded `Path.join(repository.path, filePath)` + `readFile`. Unlike the adjacent `buildConflictContext` function, it does not call `resolveWithin` to confirm the resolved path stays inside the repository, so a conflicted path that is actually a symlink pointing outside the working directory will have its target's contents read and surfaced in the app.

### Finding Description
Merge/rebase conflicts can occur on paths whose working-tree entry is a symlink (e.g. one side of history changed a regular file into a symlink). Because git tracks symlinks as blobs, an attacker who controls a branch/commit history that the victim merges, rebases, or checks out during a merge conflict flow can make a conflicted path resolve on disk to a symlink pointing at an arbitrary absolute path (e.g. `~/.ssh/id_rsa`, browser credential stores, etc.).

The Copilot conflicts dialog (`copilot-conflicts-changes.tsx`) calls `getResolutionDiff(repository, file.path, ...)` for every conflicted file the user selects, for both the `stage: 'ours'|'theirs'` and the Copilot `content` resolution paths: [6](#0-5) 

`getResolutionDiff` then does:
```ts
const baseContent = await readFile(Path.join(repository.path, filePath), 'utf8')
```
with no call to `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`. If `filePath` is a symlink escaping the repo root, `readFile` transparently follows it and returns the *external* file's contents as `baseContent`, which becomes `oldContents` in the returned `IResolutionDiff` and is rendered directly in the diff view and fed to syntax highlighting via `buildFileContents`. [7](#0-6) 

This is the same broken invariant as the seed report: a value that should be scoped to a single trusted record/boundary (here, "content confined to the repository working directory") is instead read from an unchecked, attacker-influenced location (here, whatever the filesystem symlink actually points to), overriding the intended scoping.

### Impact Explanation
An attacker who can get a victim to merge/rebase/pull a crafted branch containing a symlink-vs-file conflict can cause GitHub Desktop to read and display the contents of arbitrary files on the victim's machine (limited by the OS user's read permissions) the moment the victim opens that file in the Copilot conflict resolution dialog — a normal part of resolving a real merge conflict, not an unusual user action. This is a file-read-outside-the-repo primitive with local file content disclosed into the renderer/UI (and potentially forwarded to the Copilot resolution pipeline as apparent "old" file content).

### Likelihood Explanation
Reaching this path only requires the victim to merge/rebase a repository/branch that contains the crafted symlink conflict and to use the (default, standard) conflict-resolution UI on that file — no local access, admin rights, or pre-existing malware needed, matching the scope's "attacker controls a cloned/fetched repository" primitive. The likelihood is bounded by needing git/platform behavior where a conflicted path materializes as a real filesystem symlink; this platform-specific detail (POSIX vs Windows symlink handling, and how git materializes symlink-vs-content conflicts) was not independently re-verified in this pass and would need confirmation with a live repro, but the missing guard itself is unambiguous by direct comparison with `buildConflictContext`, which was hardened for precisely this scenario in the same feature area.

### Recommendation
In `getResolutionDiff` (`app/src/lib/git/diff.ts`), resolve `filePath` with `resolveWithin(repository.path, filePath)` (as `buildConflictContext` already does) before reading `baseContent`, and reject/skip the file (returning `DiffType.Unrenderable` or a skip reason) if the resolved path is `null` or outside the repository root.

### Proof of Concept
1. Attacker prepares a repo with two branches that conflict on path `evil`: branch A has `evil` as a symlink to `/Users/victim/.ssh/id_rsa` (or a Windows-equivalent sensitive path); branch B has `evil` as a modified regular file.
2. Victim clones/fetches the repo in GitHub Desktop and performs a merge/rebase that conflicts on `evil`, ending up with `evil` materialized on disk as the symlink.
3. Victim opens the Copilot Conflicts dialog and selects `evil`, or picks "ours"/"theirs" resolution for it, triggering `CopilotConflictsChanges.loadDiffForFile` → `getResolutionDiff(repository, 'evil', ...)`. [8](#0-7) 
4. `getResolutionDiff` executes `readFile(Path.join(repository.path, 'evil'), 'utf8')`, which follows the symlink and returns the contents of `id_rsa` as `baseContent`/`oldContents`, rendered in the diff pane. [2](#0-1)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

  private buildFileContents(
    file: CommittedFileChange,
    result: IResolutionDiff
  ): IFileContents {
    // Mirror the standard getFileContents path, which caps the amount of
    // content it hands to the syntax-highlighting worker. We only allow

      .split(/\r?\n/)
