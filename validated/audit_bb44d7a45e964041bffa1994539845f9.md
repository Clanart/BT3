### Title
Same-chain order cancellation lacks a "filled" check, letting order creators reclaim un-swept escrow after a solver has already paid out — solver fund loss via input/output array-length mismatch - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The external report's core invariant break is: a contract computes settlement (LP shares) from only *part* of the deposited value (`min` of two proportional shares), leaving an "excess" that is never returned to its rightful depositor and is instead absorbed by others. Hyperbridge's same-chain intent settlement has a structurally identical flaw: `_fillSameChain` in `evm/src/apps/intentsv2/IntrinsicIntents.sol` releases escrow by indexing `order.inputs[i]` against `order.output.assets[i]` using the *output* array's length, silently ignoring any input assets beyond that length. Combined with `_cancelSameChain` never checking whether the order was already filled, a user can construct an order with more input assets than output assets, let a solver fully fill it (paying the beneficiary in full), and then reclaim the untouched extra input escrow via cancellation — extracting value the solver never received compensation for.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` never validates that `order.inputs.length == order.output.assets.length`. A user may freely place an order with e.g. 2 inputs and 1 output [1](#0-0) .

In `_fillSameChain`, the loop bound is `outputsLen = order.output.assets.length`, yet inside the loop the escrowed-input amount to release is derived from `order.inputs[i]` using the *same* loop index `i`: [2](#0-1) [3](#0-2) 

If `order.inputs.length > order.output.assets.length`, the loop only ever touches indices `0..outputsLen-1` of `order.inputs`; any input token at index `>= outputsLen` is never read, never included in `escrowedInputs`, and consequently `_orders[commitment][thatToken]` is never decremented by `_withdraw` [4](#0-3) . Yet the fill is still marked `isFullyFilled = true` and `_filled[commitment]` is set to the solver [5](#0-4) , so the solver has already paid the beneficiary the *complete* required output.

`_cancelSameChain` — the only other path that ever touches `_orders[commitment][token]` for that leftover input — does **not** check `_filled[commitment]` at all. It only checks `msg.sender == order.user`, that the order was placed on the current chain, and that *any* input still has non-zero escrow: [6](#0-5) 

Since the extra input token's escrow was never decremented during the (already-completed) fill, `hasEscrow` is true, so the order creator can call `cancelOrder` after the order was fully filled and reclaim that leftover input in full via `_withdraw(body, true, true)`, which also overwrites `_filled[commitment]` from the solver's address to the user's own address.

### Impact Explanation
This is a direct fund-loss / double-settlement bug matching the bounty's accepted impact categories ("stealing or loss of funds", "replay/double-claim/double-settlement"). The solver pays the full output amount required by the order (as computed strictly from `order.output.assets`), but only receives escrow release for the subset of `order.inputs` indices that happen to fall within `outputsLen`. Any additional input assets the user escrowed beyond that length are effectively "excess" locked value — precisely analogous to the Caviar LP-share disproportion bug — except here the excess is not shared among LPs but is instead reclaimable by the order's own creator through `_cancelSameChain`, which lacks the invariant "an order that is already `_filled` cannot be cancelled." The result: the order creator gets their swap executed by the solver *and* gets part of their escrowed principal refunded, at the solver's direct expense.

### Likelihood Explanation
High. No privileged actor, malicious relayer, prover, or governance action is required — only an ordinary, unprivileged order creator constructing an order whose `inputs.length` exceeds `output.assets.length` (fully permitted by `placeOrder`, which never validates array-length parity), and then calling the public `fillOrder`/cancel entry points in sequence. This is a straightforward, repeatable, single-account exploit against any solver willing to fill same-chain orders.

### Recommendation
1. Enforce `order.inputs.length == order.output.assets.length` (or otherwise explicitly define and validate the correspondence between the two arrays) in `placeOrder`.
2. In `_cancelSameChain`, reject cancellation once `_filled[commitment] != address(0)` (i.e., the order has already been finalized by a fill), mirroring the "no double-settlement" guarantee that `_withdraw`'s `finalize` flag is meant to provide.
3. Alternatively/additionally, make escrow release logic in `_fillSameChain` release *all* remaining `order.inputs` entries proportionally to overall fill progress rather than indexing by the output array's length, so no input asset can be silently skipped.

### Proof of Concept
1. User calls `placeOrder` with:
   - `order.inputs = [ {tokenA, 100}, {tokenB, 100} ]`
   - `order.output.assets = [ {tokenC, 100} ]` (single output)
   
   No check rejects the length mismatch [1](#0-0) . Escrow becomes `_orders[commitment][tokenA] = 100`, `_orders[commitment][tokenB] = 100`.

2. Solver calls `fillOrder` with `options.outputs = [{tokenC, 100}]`, fully paying the beneficiary 100 `tokenC`. `_fillSameChain` runs with `outputsLen = 1`; it only reads `order.inputs[0]` (tokenA), releasing 100 `tokenA` to the solver via `_withdraw`. `isFullyFilled = true`, `_filled[commitment] = solver` [7](#0-6) . `_orders[commitment][tokenB]` remains `100`, untouched.

3. User (order.user) calls `cancelOrder` → `_cancelSameChain(order, commitment)`. The function does not check `_filled[commitment]`; it only sees `_orders[commitment][tokenB] == 100 > 0`, sets `hasEscrow = true`, and refunds `tokenB` (100) back to the user via `_withdraw(body, true, true)` [6](#0-5) .

4. Net result: the solver paid 100 `tokenC` and received only 100 `tokenA` back (instead of both `tokenA` + `tokenB`), while the user keeps 100 `tokenB` that was supposed to compensate the solver — a direct fund loss for the solver caused entirely by an unprivileged order-creation choice and a missing "already filled" guard on cancellation.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
