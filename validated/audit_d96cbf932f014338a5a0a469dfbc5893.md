Confirmed: `pallet_assets::Config for Runtime` uses `type CreateOrigin = AsEnsureOriginWithArg<frame_system::EnsureSigned<AccountId32>>` [1](#0-0)  — asset creation in the underlying `pallet-assets` is **permissionless**: any signed account can create an asset and becomes its `Admin`/`Owner`, which grants it the ability to call `set_metadata` and change `decimals` at will (governed by `pallet-assets`, not by `pallet_hyper_fungible_token`). The pallet's own `CreateOrigin` (`EnsureRoot`) only gates `register_token`/`update_token`, i.e., which assets get bridged, not who controls that asset's metadata afterward.

### Title
Live re-read of mutable asset `decimals` in `send` desynchronizes escrowed amount from dispatched `Message.amount` - (File: modules/pallets/hyper-fungible-token/src/lib.rs)

### Summary
`register_token`/`update_token` validate `config.decimals >= local_decimals` and store only the destination `erc_decimals` in `Precisions`; they never snapshot the local asset's decimals used for validation. [2](#0-1)  `send` then re-reads the local asset's decimals live via `fungibles::metadata::Inspect::decimals` at call time and feeds it into `convert_to_erc20` together with the stored `erc_decimals`. [3](#0-2)  `convert_to_erc20` scales the raw escrowed balance by `10^(erc_decimals - local_decimals)`. [4](#0-3) 

### Finding Description
Since `pallet-assets`' `Admin`/`Owner` of a given asset can call `set_metadata` to change `decimals` at any time (permissionless creation, `AsEnsureOriginWithArg<EnsureSigned<...>>`) [5](#0-4) , an asset admin can lower the asset's `decimals` immediately before calling `send`. The raw balance amount actually escrowed/burned (`params.amount`, unaffected by metadata) stays the same, but `decimals` fed into `convert_to_erc20` decreases, which increases the exponent `erc_decimals.saturating_sub(decimals)` and inflates the resulting `erc20_amount` encoded into `Message.amount` beyond what the escrowed raw balance represents relative to the `erc_decimals` fixed at registration. [6](#0-5) 

### Impact Explanation
If the destination EVM contract mints/releases tokens according to `Message.amount`, an attacker-controlled decimals reduction causes the destination side to release more value than was actually locked/burned on the source chain, corrupting outbound settlement accounting and potentially draining destination-side custody relative to source-side backing.

### Likelihood Explanation
Exploitability is gated by needing to be the `Admin`/`Owner` of the specific asset registered in `TokenContracts`/`Precisions` — not an arbitrary unprivileged caller of `send`, since getting a token registered still requires `T::CreateOrigin` (`EnsureRoot`). [7](#0-6)  However, once an asset is registered (e.g. because it looked innocuous at registration time), its permissionless admin retains full, ungated control over `decimals` via `pallet-assets` outside this pallet's authorization model, so the actual attacker set is "asset admins of registered tokens," which is a realistic unprivileged-relative-to-the-bridge actor.

### Recommendation
Snapshot and store `local_decimals` in `Precisions` (or a dedicated storage item) at `register_token`/`update_token` time instead of re-reading live metadata in `send`, and re-validate/reject sends if live decimals ever diverge from the stored snapshot.

### Proof of Concept
1. Asset admin creates asset `X` with `decimals = 18`; governance calls `register_token` for `X` with `erc_decimals = 18` (passes `config.decimals >= local_decimals`). [2](#0-1) 
2. Admin calls `pallet_assets::set_metadata` to change `X`'s decimals to `6`.
3. Admin calls `send` with `params.amount = 1_000_000` (raw units). `convert_to_erc20(1_000_000, 18, 6)` now multiplies by `10^12` instead of `10^0`, producing an `erc20_amount` a trillion times larger than the amount consistent with the registered precision, while only `1_000_000` raw units were actually escrowed. [4](#0-3) [8](#0-7)

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
