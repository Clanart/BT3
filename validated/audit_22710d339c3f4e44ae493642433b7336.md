### Title
Duplicate PedPoP encryption-key registration message panics the DKG host (CHECK-failure DoS) - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The external report concerns a TensorFlow `CHECK` failure (assertion abort) reachable from attacker-controlled input sizes — a remote denial of service via panic. The analog in Serai is the `assert!` inside `Decryption::register` in `crypto/dkg/pedpop/src/encryption.rs`, which aborts the whole process when a participant submits a second `EncryptionKeyMessage`, instead of returning an error.

### Finding Description
`Decryption::register` unconditionally panics on re-registration:

```rust
// crypto/dkg/pedpop/src/encryption.rs
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

`EncryptionKeyMessage` is a public, wire-deserializable structure: `EncryptionKeyMessage::read` parses `M::read(reader, params)` plus a group element via `C::read_G` (`encryption.rs:57-59`). The PedPoP DKG feeds these per-participant messages through `Encryption::register` → `Decryption::register` (`encryption.rs:452-458`). A participant that delivers its key-registration message twice (or a coordinator that forwards a duplicate) causes the receiving node to hit the `assert!` and panic, mirroring the `tf.reshape` CHECK-failure class: an assertion on reachable input aborts the process rather than producing a handled error.

There is no `Err` return path — the function signature returns `M` directly, so callers cannot even catch the condition short of `catch_unwind`.

### Impact Explanation
Denial of service. A single duplicated message from any participant aborts the victim's DKG ceremony mid-protocol. Since `register` is invoked while processing each participant's broadcast message, the crash occurs on the happy path of message handling, destroying in-progress key-generation state (and potentially leaking partially-zeroized `enc_keys`, since `Zeroize` for `Encryption` only runs on clean drops). This matches the TensorFlow advisory: medium-severity, availability-only, attacker-triggerable assertion failure.

### Likelihood Explanation
Any party able to emit a PedPoP key-registration message (a DKG participant, or whatever transport relays `EncryptionKeyMessage`s to `register`) can trigger it deterministically — no race, no special timing. The only mitigating factor is that triggering it requires being a participant in the DKG round, so it is a peer-level rather than fully anonymous attack; consistent with the Medium rating of the reference advisory.

### Recommendation
Replace the `assert!` with a fallible check: have `Decryption::register` (and `Encryption::register`) return `Result<M, PedPoPError>` (or reuse `DkgError::DuplicatedParticipant`, which already exists in `crypto/dkg/src/lib.rs:112` for exactly this condition) so a duplicate registration rejects the message and optionally attributes blame instead of aborting the process.

### Proof of Concept
Conceptually, against an `Encryption`/`Decryption` instance for participant set with `i` local:

```rust
let mut dec = Decryption::<Secp256k1>::new(context);
let msg = EncryptionKeyMessage::<Secp256k1, _>::read(&mut bytes, params).unwrap();
dec.register(Participant::new(1).unwrap(), msg.clone());
// Attacker replays/duplicates the same wire message:
dec.register(Participant::new(1).unwrap(), msg); // thread panics at encryption.rs assert!
```

In the real protocol flow, the attacker simply broadcasts their `EncryptionKeyMessage` twice (or re-sends it in a later round where the transport permits), and every other honest participant's node panics instead of marking the sender malicious.

**Uncertainty note:** I verified the `assert!` and the public read/registration path in `encryption.rs`, but did not fully trace the call site inside `crypto/dkg/pedpop/src/lib.rs` that invokes `register` per received message. If the caller already deduplicates per-participant messages before reaching `register`, reachability would depend on that transport behavior; the assertion remains a latent panic on the public-facing message path regardless.
