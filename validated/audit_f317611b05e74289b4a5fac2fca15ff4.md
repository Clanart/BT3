### Title
Missing Validation of Wombat Pool Deposit Return Amount Can Lock User Funds With Zero Receipt Tokens Minted - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.deposit` forwards a user's deposit token to the underlying Wombat pool via `IWombatPool(poolInfo.depositTarget).deposit(...)` and computes the amount of LP received purely by measuring the balance delta of `poolInfo.lpAddress` before and after the call. It then mints `poolInfo.receiptToken` to the caller (the pool helper, acting on behalf of the depositing user) using this `lpReceived` value, without ever validating that `lpReceived > 0`.

### Finding Description
In `deposit()`, the depositor's tokens are pulled in with `safeTransferFrom`, approved to the Wombat pool, and then deposited: [1](#0-0) 

The code assumes the external Wombat pool (`IWombatPool(poolInfo.depositTarget)`) will always mint a non-trivial amount of LP tokens back to `WombatStaking` for the deposited amount. This is the same class of issue described in the reference report: an external "vault" (here, the Wombat pool) is trusted to return shares/LP for a deposit, and the caller proceeds to credit the depositor based on that return without any sanity check. If the underlying Wombat pool's internal accounting is skewed (e.g., because of extreme cash/liability ratios, an unusual amplification factor state, or a pool that has very low liquidity/large fee-slippage relative to the deposit size), `lpReceived` can end up being `0` or negligible even though the user's `depositToken` was fully transferred out of their wallet and consumed by the pool.

Because `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived)` mints exactly `lpReceived` (potentially `0`) receipt tokens, the depositing user's principal is transferred into the Wombat pool, but they receive no (or negligible) receipt/staking-token credit representing their claim, with no revert or recovery path in this call path.

### Impact Explanation
A user's deposited principal can be irreversibly consumed by the underlying Wombat pool while the caller/user receives zero (or dust) receipt tokens in return, permanently freezing/losing the deposited funds with no way to redeem them, since redemption in this system is entirely driven by receipt token balances (`WombatPoolHelper.withdraw` burns/uses receipt tokens to withdraw). This matches the "permanent freezing of funds" / "direct theft of user funds" impact class.

### Likelihood Explanation
This does not require any privileged or malicious actor — it is triggered purely by an ordinary user calling `WombatPoolHelper.deposit` → `WombatStaking.deposit` under specific but externally-reachable Wombat pool states (e.g., very small deposit relative to pool liability/cash skew, or pools with extreme parameters), which is analogous to the referenced report's "pre-funded vault" edge case for ERC4626-style deposits.

### Recommendation
Add an explicit check after computing `lpReceived` (and similarly for `depositLP`'s effective received amount where applicable) to revert if the amount is zero or below a caller-supplied minimum, e.g.:
```solidity
uint256 lpReceived = IERC20(poolInfo.lpAddress).balanceOf(address(this)) - beforeBalance;
require(lpReceived > 0, "WombatStaking: zero LP received");
```
This mirrors the existing `_minimumLiquidity` parameter already passed into the Wombat pool's own `deposit` call, but that value is currently only enforced by the external pool, not independently validated by `WombatStaking` before minting receipt tokens.

### Proof of Concept
1. A user calls `WombatPoolHelper.deposit(_amount, _minimumLiquidity)` with `_minimumLiquidity = 0` (or a helper/integration that does not tightly bound slippage).
2. This routes to `WombatStaking.deposit(...)`, which calls `IWombatPool(poolInfo.depositTarget).deposit(depositToken, _amount, _minimumLiquidity, address(this), block.timestamp, false)`.
3. Under pool conditions where the resulting LP mint rounds to (near) zero for the given deposit size relative to the pool's cash/liability state, `lpReceived` computed by the balance-diff is `0`.
4. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived)` mints `0` receipt tokens to the pool helper for the user.
5. The user's `depositToken` has already been transferred into the Wombat pool via `safeTransferFrom` and consumed, but the user holds no receipt token balance and thus has no mechanism to withdraw their principal via `WombatPoolHelper.withdraw`, resulting in permanent loss of the deposited funds.
