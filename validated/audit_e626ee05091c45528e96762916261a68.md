## Finding [1](#0-0) 

### Title
Escrow double-drain via reentrancy in `IntentGatewayV2.withdraw()` — state decrement occurs after external token transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` implements its own `withdraw()` function that violates checks-effects-interactions: for each escrowed token it performs an external low-level `.call` (native transfer or `IERC20.transfer`) to the beneficiary and only *afterwards* decrements the corresponding `_orders[commitment][token]` escrow balance. The canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`) fixes exactly this class of bug by decrementing the escrow balance *before* transferring, but the Tron contract was not updated to match.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, function `withdraw()`: [2](#0-1) 
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    // redeem escrowed tokens
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // decrement AFTER the external call
        ...
    }
```
The escrow balance check (`_orders[...][token] == 0`) uses a strict zero-check, not a comparison against `amount`, and the decrement happens after the external interaction. A malicious/hookable `token` (or a beneficiary receiving native TRX via `.call`) can re-enter during the transfer, before `_orders[commitment][token]` has been reduced. Because the check is only `== 0` (not `>= amount`), and the balance hasn't been reduced yet, a second re-entrant iteration of the same withdrawal path (or another function reading the same escrow slot) still sees the pre-decrement balance and can trigger another transfer of the same escrowed funds.

Contrast this with the current CEI-compliant implementation in `IntentsBase.sol._withdraw`, which decrements first: [3](#0-2) 
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
The repository's own reentrancy regression test suite explicitly documents that the fill-side functions (`_fillSameChain`/`_fillCrossChain`) were hardened with this exact CEI pattern after a prior vulnerability window: [4](#0-3) 
This confirms the team is aware of and actively defends against this exact bug class (external-call-before-state-update during escrow release) — but the fix was not carried over to the Tron contract copy, and no `nonReentrant` guard exists anywhere in that file (confirmed absent via search).

### Impact Explanation
This directly matches the "Bridged assets... must move exactly once and only to the rightful beneficiary and amount" invariant. If `token` is any contract with a transfer-hook or callback (common on Tron via TRC-10/TRC-20 style tokens with proxy/callback patterns, or if the beneficiary is a contract receiving a native TRX `.call`), the attacker can re-enter mid-transfer and cause the same escrowed funds to be paid out more than once, or interleave with `_filled[commitment]` state to bypass finalization checks — directly stealing escrowed order funds from the IntentGateway, a real fund-loss/double-settlement scenario matching the bounty's accepted impact list.

### Likelihood Explanation
The withdrawal path is reached unconditionally whenever `onAccept` processes a `RedeemEscrow`/`RefundEscrow` message and calls `withdraw()`, and the beneficiary/token addresses are attacker-influenced (an order's beneficiary is chosen at order-placement time and can be any attacker-controlled contract). No relayer collusion, admin action, or private key compromise is required — only that the attacker controls the receiving contract/token used as an order input/beneficiary, which is a standard, permissionless capability for any user placing/filling an intent order. This is a straightforward, unprivileged-attacker-reachable path.

### Recommendation
Port the CEI fix from `evm/src/apps/intentsv2/IntentsBase.sol._withdraw` into `evm/tron/contracts/apps/IntentGatewayV2.sol.withdraw`: decrement `_orders[commitment][token]` (and delete `TRANSACTION_FEES`) *before* performing the external transfer, and change the guard to check `escrowed >= amount` rather than `!= 0`. Add a reentrancy guard (`nonReentrant`) to `onAccept`/`withdraw` as defense in depth, consistent with the hardening already applied elsewhere in the EVM codebase.

### Proof of Concept
1. Attacker places/fills an order whose escrow input or fill output token is a malicious contract implementing a transfer hook (or beneficiary is a contract that reverts/re-enters on native TRX receipt).
2. Hyperbridge relays a `RedeemEscrow`/`RefundEscrow` message; `onAccept` calls `withdraw(body, isRefund)`.
3. In the loop, `_orders[commitment][token]` is still non-zero when `token.call(transfer(...))` (or `beneficiary.call{value}("")`) executes.
4. The malicious token/beneficiary re-enters (e.g., via `onAccept` for a duplicate/crafted message referencing the same commitment/token, or any other function reading `_orders[commitment][token]`) before the decrement at line 701 executes, allowing a second transfer against the same still-nonzero escrow balance.
5. Execution returns to the original call, which then also decrements/transfers, resulting in more total tokens paid out than were ever escrowed for that commitment — a fund-loss/double-settlement condition.
