### Title
Independent per-vote consistency checks allow ratifying `Kip71LowerBoundBaseFee` > `Kip71UpperBoundBaseFee` in the same epoch - (File: kaiax/gov/headergov/impl/header.go)

### Summary
`checkConsistency` validates a `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` vote only against the *currently ratified* `ParamSet`, not against any other vote for the paired parameter cast within the same (still un-ratified) epoch. Two individually "valid" votes cast in the same epoch can combine into an inconsistent ratified pair where `LowerBoundBaseFee > UpperBoundBaseFee`, exactly analogous to the reported `HatsSignerGateBase` issue where `setTargetThreshold()` only checked the new value against `maxSigners` and not against `minThreshold`.

### Finding Description
`checkConsistency` handles the two KIP-71 base-fee bound votes like this: [2](#0-1) 

Both branches call `h.GetParamSet(blockNum)`, which returns the parameter set ratified from the *previous* epoch (per the module's own documentation of `GetParamSet`) [3](#0-2)  — i.e., it does not reflect other votes cast earlier in the same epoch that have not yet been ratified.

Because votes are collected for an entire epoch and only the last vote per parameter is ratified at the epoch boundary [4](#0-3) , the governing node (the only account permitted to vote once in `single` governance mode, which is used by both Mainnet and Kairos) can cast, within the same epoch:
1. `Kip71UpperBoundBaseFee = X` where `X` is still `>=` the *old* `LowerBoundBaseFee` (passes the check).
2. `Kip71LowerBoundBaseFee = Y` (`Y > X`) where `Y` is still `<=` the *old* `UpperBoundBaseFee` (passes the check).

Both votes pass `VerifyVote`/`checkConsistency` independently since each is only compared to the stale, not-yet-updated bound. At the epoch boundary both votes are ratified together into `header.Governance`, producing a final `ParamSet` with `LowerBoundBaseFee (Y) > UpperBoundBaseFee (X)`.

This ratified, inconsistent pair is then consumed directly by `NextMagmaBlockBaseFee`, which has no defensive check that `LowerBoundBaseFee <= UpperBoundBaseFee`: [5](#0-4) 

Similar to `_getCorrectThreshold()` in the reported issue silently producing an incorrect value when `targetThreshold < minThreshold`, `NextMagmaBlockBaseFee` will compute base fee bounds using an inverted lower/upper pair, since the clamp logic (`parentBaseFee.Cmp(upperBoundBaseFee) >= 0` then `else if parentBaseFee.Cmp(lowerBoundBaseFee) <= 0`) assumes `lower <= upper`.

### Impact Explanation
The block base fee (`baseFee`), used for KIP-71/Magma fee calculation and burn accounting for every transaction on-chain, becomes governed by an invalid, self-contradictory bound pair. Depending on `parentBaseFee`'s position, the base fee computation can behave unpredictably (e.g., permanently clamp to a value determined by the "wrong" bound, or oscillate), causing state divergence risk between implementations/clients that may interpret the inverted bounds differently, and it can make the fee market convergence broken (mispriced fees / incorrect burn amounts) network-wide until governance corrects it. This satisfies "state divergence between honest nodes" / "acceptance of an invalid ... parameter state" impact criteria.

### Likelihood Explanation
Requires the governing node (single, privileged voter in `single` mode) to cast two votes within one epoch — no external attacker or unprivileged sender can trigger it, but it is a straightforward governance-parameter mistake or intentional manipulation reachable purely through the standard `governance_vote` API twice in one epoch, with no cross-parameter validation at ratification time. There is no need for any implementation bug in block production/consensus beyond the existing vote-validation logic; the check is simply comparing against stale state, matching the root-cause pattern of the reported issue (`_setTargetThreshold` compares only against `maxSigners`, never against `minThreshold`).

### Recommendation
When ratifying `header.Governance` at the epoch boundary (`getExpectedGovernance`) or when applying a `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` vote, re-check the *final combined* value of both parameters (using the pending vote value for one and either the pending or current ratified value for the other) rather than only comparing each vote against the stale `ParamSet`. Alternatively, add a final invariant check `LowerBoundBaseFee <= UpperBoundBaseFee` in `VerifyGov`/`getExpectedGovernance` before committing `header.Governance`, and defensively guard `NextMagmaBlockBaseFee` against an inverted bound pair.

### Proof of Concept
1. Chain runs in `single` governance mode with `governance.governingnode = N`, epoch length `E`, current ratified `LowerBoundBaseFee = 25e9`, `UpperBoundBaseFee = 750e9`.
2. At block `k*E + 1`, `N` calls `governance_vote("kip71.upperboundbasefee", 650e9)`. Since `650e9 >= LowerBoundBaseFee(25e9)`, `checkConsistency` passes and the vote is embedded in `header.Vote`. [6](#0-5) 
3. At block `k*E + 2` (same epoch), `N` calls `governance_vote("kip71.lowerboundbasefee", 700e9)`. Since `params.UpperBoundBaseFee` returned by `GetParamSet` is still the old ratified value `750e9`, and `700e9 <= 750e9`, `checkConsistency` passes this vote too. [7](#0-6) 
4. At the next epoch boundary `(k+1)*E`, `getExpectedGovernance` collects the last vote per parameter within epoch `k` and ratifies both into `header.Governance`: `LowerBoundBaseFee = 700e9`, `UpperBoundBaseFee = 650e9`. [8](#0-7) 
5. From block `(k+1)*E + 1` onward, `NextMagmaBlockBaseFee` uses this inverted pair; e.g., with `parentBaseFee = 700e9`, the clamp `parentBaseFee.Cmp(upperBoundBaseFee) >= 0` triggers, clamping `parentBaseFee` down to `650e9`, even though the "lower" bound is nominally `700e9` — producing self-contradictory, unintended fee behavior network-wide. func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:
