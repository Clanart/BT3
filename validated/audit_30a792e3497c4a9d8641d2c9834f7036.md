Based on my investigation, the strongest local analog to the nimiq `assert!`-based reachable-assertion bug is the `assert.equal` invariant in `getAuthors` in `app/src/lib/git/log.ts`.

### Title
Reachable assertion crash via duplicate commit SHAs passed to `getAuthors` - (File: app/src/lib/git/log.ts)

### Summary
`getAuthors` in [1](#0-0)  feeds a caller-supplied `shas: string[]` array to `git log --no-walk=unsorted --stdin`, then asserts that the number of author records returned by git equals `shas.length`:
```
const authors = stdout.split('\0').map(CommitIdentity.parseIdentity)
assert.equal(authors.length, shas.length, 'Commit to author mismatch')
``` [2](#0-1) 

The code comment itself documents the broken invariant: `git log` only emits one author record per **unique** SHA, so if the `shas` input contains duplicates, `authors.length` will be smaller than `shas.length` and the `assert.equal` throws an uncaught `AssertionError`, structurally identical to the reachable `assert!` in `HistoryStore::put_historic_txns` from the report — an invariant enforced with a hard assertion instead of a graceful validation/rejection path.

### Finding Description
This is directly analogous to the nimiq bug class: a hard `assert`/`assert!` is used to enforce a data-shape invariant on input that is influenced by data that ultimately originates from a remote, rather than being validated and handled as a normal error path. In Desktop, the caller of `getAuthors` (`app/src/ui/branches/branch-list.tsx`) builds the `shas` array from branch tip commits. Because git refs (local, remote-tracking, and tags fetched from a malicious/compromised remote) are fully attacker-controlled and many distinct branches can point at the exact same commit object, the array of tip SHAs collected for the branch list can easily contain duplicate entries after a `fetch`/`clone` from an untrusted remote with many branches funneled to one commit.

When this happens, `git log --stdin` de-duplicates and returns fewer author lines than SHAs supplied, so `authors.length !== shas.length`, and the `assert.equal` throws. Unlike a `try { … } catch` guarded git-command failure (which Desktop generally handles gracefully via `performFailableOperation`/`catchAndTrack`), an `AssertionError` thrown mid-function is an unexpected exception type that is not a `GitError`, so higher-level git-command error handling (which typically expects `GitError`/exit-code based failures) may not intercept it, resulting in an unhandled promise rejection that can crash the branch list render path.

### Impact Explanation
This falls squarely under Improper Check for Unusual or Exceptional Conditions / Reachable Assertion (matching the CWEs in the original report). The direct effect is a renderer-level crash/unhandled exception when computing branch-author avatars, which is a denial-of-service against a specific UI feature triggered purely by the shape of an untrusted remote's ref graph (attacker chooses which commits multiple branches point to) — no local access, no malware, no credentials required.

### Likelihood Explanation
Likelihood is moderate: creating a repository/remote where multiple branches share the same tip commit is trivial for any attacker who controls a repo that the victim clones or adds as a remote and then views in the Branches list. However, I was not able to fully confirm within this session whether `branch-list.tsx`'s call site already de-duplicates SHAs before calling `getAuthors` (I could only confirm two call-site references via grep but did not get to inspect the exact surrounding code before the tool budget was exhausted), so the actual reachability of the duplicate-SHA condition through the current UI flow is not fully verified and should be validated directly in `app/src/ui/branches/branch-list.tsx`.

### Recommendation
Replace the `assert.equal` invariant in `getAuthors` with normal input validation/error handling (e.g., de-duplicate `shas` before calling git, or tolerate a mismatched count by mapping authors back via a Map keyed on SHA), consistent with how other git-output parsing in this codebase (e.g., `parsePorcelainStatus`, `createLogParser`) throws recoverable `Error`s instead of assertion failures, and ensure any remaining hard invariants over remote/ref-derived data are validated before use rather than enforced via `assert`.

### Proof of Concept
1. Attacker publishes a repository with two or more branches (e.g., `refs/heads/a`, `refs/heads/b`) pointing at the identical commit SHA.
2. Victim adds/fetches this remote in GitHub Desktop and opens the branch list, which collects the tip SHAs of all branches into an array (containing the duplicate SHA) and calls `getAuthors(repository, shas)`.
3. `git log --no-walk=unsorted --stdin` returns one author line for the deduplicated SHA set, so `authors.length < shas.length`.
4. `assert.equal(authors.length, shas.length, 'Commit to author mismatch')` throws an `AssertionError` [3](#0-2) , which is not the `GitError` type most Desktop call sites are prepared to catch, producing an unhandled crash path in the branch-list feature.

**Note on limitations:** I could not fully verify the exact branch-list call site that constructs the `shas` array (only located via `grep_search`, not read in full before the session ended), so confirmation that current UI logic passes unde-duplicated SHAs requires direct inspection of `app/src/ui/branches/branch-list.tsx`.

```typescript
/** Get the author identity for the given shas */
export async function getAuthors(repository: Repository, shas: string[]) {
  if (shas.length === 0) {
    return []
  }

  const { stdout } = await git(
    [
      'log',
      '--format=format:%an <%ae> %ad',
      '--no-walk=unsorted',
      '--date=raw',
      '-z',
      '--stdin',
    ],
    repository.path,
    'getAuthors',
    { stdin: shas.join('\n') }
  )

  const authors = stdout.split('\0').map(CommitIdentity.parseIdentity)

  // This can happen if there are duplicate shas in the input, git log will only
  // return the author once for each sha.
  assert.equal(authors.length, shas.length, 'Commit to author mismatch')

  return authors
}
```
