### Title
Unauthenticated panic in PedPoP blame adjudication via out-of-range participant index - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary

Analogous to CVE-2021-22174 (a crash in a packet dissector reachable by crafted input), PedPoP's blame/adjudication path — the code that "dissects" an accusation consisting of a sender index, recipient index, an `EncryptedMessage`, and an `EncryptionKeyProof` — indexes `self.enc_keys` and `self.commitments` with `HashMap`'s `Index` operator, which panics on a missing key. An unprivileged party that submits a crafted blame accusation (or a crafted `EncryptedMessage`/`proof` pair) naming a `Participant` index that was never registered crashes the process evaluating blame, aborting the DKG adjudication for everyone.

### Finding Description

`Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` while building the arguments to `DLEqProof::verify`, i.e., *before* any check that `decryptor` is a real participant: [1](#0-0) 

`decryptor` is the `recipient` argument of `BlameMachine::blame` / `AdditionalBlameMachine::blame` and flows straight from the accusation: [2](#0-1) 

`enc_keys` is only populated for `1 ..= n` via `register` (`encryption.rs:351-362`), so any `Participant` index outside the registered set — e.g. `Participant::new(n + 1)` — hits `HashMap::index` and panics instead of returning `DecryptionError`. `Participant::new` only rejects zero, so indexes `> n` are expressible.

The only gate in front of the panic is `msg.pop.verify(...)` (`encryption.rs:374-379`). That signature's challenge binds `context`, `sender`, `key`, `nonce`, and `msg` — all attacker-chosen — and the attacker knows the discrete log of `msg.key` because they generate it, so producing a validly verifying PoP is trivial. No authentication of `sender`/`recipient` occurs inside the library (the API explicitly takes them as raw arguments).

The same crash exists on the `sender` axis: if `recipient` is a registered participant but `sender` is not, `decrypt_with_proof` succeeds (the attacker can forge a correct DLEq proof for `proof.key` since they control both the proof scalar and `msg.key`), after which `blame_internal` evaluates `self.commitments[&sender]` (`lib.rs:599`) and panics on the missing key.

`AdditionalBlameMachine::new` compounds this by design: it is explicitly constructed so that *non-participants* can evaluate blame over arbitrary accusations (`lib.rs:638-661`), meaning the adjudicator role — and therefore the panic surface — is exposed to anyone who receives accusation bytes, not just DKG members.

### Impact Explanation

A single crafted accusation deterministically panics any honest node evaluating blame. In a coordinator/processor deployment this is a remote denial of service on the DKG-fault-adjudication path, reachable with a few hundred attacker-controlled bytes, matching the "crash on crafted input" class of CVE-2021-22174. Because `blame` consumes the machine, the panic occurs while the operator is handling a suspected fault — the exact moment liveness matters.

### Likelihood Explanation

Triggering requires only: (1) a valid `EncryptedMessage` serialization (attacker-made key + self-signed PoP), (2) an `EncryptionKeyProof` the attacker constructs normally, and (3) a `recipient` (or `sender`) `Participant` value that is nonzero but not in `1 ..= n`. All are unprivileged public inputs to a public API; `Participant` carries no upper bound. Likelihood is high wherever blame accusations are relayed, but the impact is limited to availability (crash), not secret leakage or forgery.

### Recommendation

Replace infallible `HashMap` indexing with checked lookups in `decrypt_with_proof` and `blame_internal`:

- In `decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` before calling `dleq.verify`.
- In `blame_internal`, check `self.commitments.get(&sender)` and return `sender` (or `recipient`, per adjudication semantics) when absent.
- Optionally, have `blame`/`AdditionalBlameMachine::blame` early-reject `sender`/`recipient` values not in `1 ..= n`, since `n` is known to the machine.

### Proof of Concept

```rust
// Honest setup: n = 3 DKG completed; an observer builds an
// AdditionalBlameMachine with the 3 real commitment messages.
let machine = AdditionalBlameMachine::<Ed25519>::new(context, 3, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage they can satisfy the PoP for:
let key = Zeroizing::new(Ed25519::random_nonzero_F(&mut rng));
let pub_key = Ed25519::generator() * key.deref();
let nonce = Zeroizing::new(Ed25519::random_nonzero_F(&mut rng));
let pub_nonce = Ed25519::generator() * nonce.deref();
let mut msg_bytes = SecretShare::<Scalar>(Scalar::ONE.to_repr());
let pop = SchnorrSignature::sign(
    &key,
    nonce,
    pop_challenge::<Ed25519>(context, pub_nonce, pub_key, sender, msg_bytes.as_ref()),
);
let forged_msg = EncryptedMessage { key: pub_key, pop, msg: Zeroizing::new(msg_bytes) };

// Attacker-accuser names a recipient index that was never in the DKG.
let bogus_recipient = Participant::new(500).unwrap(); // valid: nonzero, > n
machine.blame(sender, bogus_recipient, forged_msg, Some(attacker_proof));
// pop.verify passes (attacker signed it), then
// `self.enc_keys[&bogus_recipient]` -> panic: "key not found"
```

The panic occurs at `crypto/dkg/pedpop/src/encryption.rs:388` (`self.enc_keys[&decryptor]`) — and, for a bogus `sender` with a valid `recipient`, at `crypto/dkg/pedpop/src/lib.rs:599` (`self.commitments[&sender]`) — on fully attacker-controlled input with no authentication requirement inside the library.
