## Confirmed Analog: Trampoline credential token is not bound to the git operation/host it was issued for

### Title
Cross-context replay of the trampoline credential token lets a hook/filter from a malicious repository exfiltrate the user's stored GitHub credentials for any endpoint - ([File: app/src/lib/trampoline/trampoline-tokens.ts])

### Summary
The Sherlock report's broken invariant is: a signed authorization (deploy/call payload) omits a domain-separator (`chainId`), so a value that is valid in one context (chain A) is blindly accepted in a different context (chain B) it was never meant for. The same class of bug exists in GitHub Desktop's trampoline credential mechanism: the `DESKTOP_TRAMPOLINE_TOKEN` that authorizes a caller to talk to the local credential-helper socket is validated only by set membership, with no binding to the specific repository, remote host, or git subprocess it was minted for.

### Finding Description
When Desktop performs a remote git operation it mints a random token and exposes it (plus the local trampoline server's TCP port) to the spawned `git` process via environment variables: [1](#0-0) [2](#0-1) 

The server that receives commands over that TCP socket validates the token with nothing more than "is this token currently outstanding," irrespective of which operation, repository, or destination host it was created for: [3](#0-2) 

Once the token passes this check, the credential-helper `get` handler will look up and return the user's real GitHub credentials for **whatever URL is supplied in the request**, taken from attacker-controlled `stdin` parameters of the trampoline protocol, not from anything tying the request back to the git operation the token was issued for: [4](#0-3) [5](#0-4) [6](#0-5) 

Crucially, environment variables (including `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT`) set for the `git` process are inherited by any child process `git` spawns during that operation — including smudge/clean filters and hooks defined by the *content of the repository being cloned/fetched* (e.g. `.gitattributes` filters, `post-checkout`, LFS filters). Such a hook is fully attacker-controlled content shipped in a malicious repository. That hook can simply open a TCP connection to `127.0.0.1:$DESKTOP_PORT`, replay the inherited `DESKTOP_TRAMPOLINE_TOKEN` with `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`, and send a `get` request with `stdin` containing `host=github.com\nprotocol=https\n`. Because `isValidTrampolineToken` performs no scoping to the operation, endpoint, or repository the token was minted for, the credential-helper handler proceeds exactly as if the legitimate `git` process for github.com had asked, and returns the user's stored GitHub PAT/OAuth token via `getGitHubCredential` → `findGitHubTrampolineAccount`.

This mirrors the audited bug precisely: the "signature" (trampoline token) lacks a domain-separation field (bound host/endpoint/operation, i.e. the "chainId" analog), so a credential valid in the narrow context it was minted for (e.g., a generic git server clone) can be replayed in an unrelated context (a request for `github.com` credentials) that the token holder was never authorized to access.

### Impact Explanation
A malicious/compromised repository's git hook or filter — which the user only had to clone or fetch, no git-credential prompts or user interaction needed beyond the normal clone/fetch — can exfiltrate the currently-signed-in user's GitHub.com/GHE credentials (access token) by directly connecting to the local trampoline socket and impersonating the credential-helper protocol for an arbitrary host. This is credential/token exfiltration from an unprivileged attacker-controlled repository, matching the "Valid Impact" criteria (attacker controls a cloned/fetched repository; result is credential/token exfiltration).

### Likelihood Explanation
Likelihood is high for any user who clones or fetches an untrusted repository while signed in to Desktop: the token and port are unconditionally placed in the git subprocess environment for every remote operation, hooks/filters routinely run as part of clone/fetch/checkout, and no additional validation (host/operation binding, one-time-use per request, mutual auth) exists on the trampoline server side to prevent an out-of-band client from using the leaked token for an unrelated request.

### Recommendation
Bind each trampoline token to the specific operation/repository/host it was minted for (the "chainId" equivalent), and have `processCommand`/`getCredential` reject requests whose target host does not match the host recorded for that token when it was issued. Consider also scoping tokens to a single command identifier/invocation (already partially one-shot via `withTrampolineToken`, but not host-scoped) and not exposing github.com-scoped credential responses to a token that was issued for a different (e.g., generic/self-hosted) remote's askpass/credential flow.

### Proof of Concept
1. Sign in to GitHub Desktop with a GitHub.com account.
2. Clone/fetch a malicious repository containing a `.gitattributes` clean/smudge filter (or a `post-checkout`/other hook) that runs during the operation.
3. The hook script reads `process.env.DESKTOP_TRAMPOLINE_TOKEN` and `process.env.DESKTOP_PORT` (inherited from the parent `git` process spawned by Desktop, see `withTrampolineEnv` in `app/src/lib/trampoline/trampoline-environment.ts:93-147`).
4. The hook opens a raw TCP socket to `127.0.0.1:$DESKTOP_PORT` and speaks the trampoline wire protocol (parameter count `1`, parameter `get`, env count `2`, `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`, `DESKTOP_TRAMPOLINE_TOKEN=<stolen token>`, then stdin `protocol=https\nhost=github.com\n\n`).
5. `TrampolineServer.processCommand` (`app/src/lib/trampoline/trampoline-server.ts:162-166`) validates the token via `isValidTrampolineToken`, which only checks Set membership (`app/src/lib/trampoline/trampoline-tokens.ts:13-16`) — it succeeds because the token is still outstanding for the ongoing clone/fetch, regardless of the requested host.
6. `createCredentialHelperTrampolineHandler`'s `get` path calls `getCredential` → `getGitHubCredential` → `findGitHubTrampolineAccount`, which returns the signed-in account's token for `github.com` (`app/src/lib/trampoline/trampoline-credential-helper.ts:50-57`, `app/src/lib/trampoline/find-account.ts:20-29`), and the response is written back over the socket to the malicious hook process.

const trampolineTokens = new Set<string>()

function requestTrampolineToken() {
  const token = crypto.randomUUID()
  trampolineTokens.add(token)
  return token
}

function revokeTrampolineToken(token: string) {
  trampolineTokens.delete(token)
}

/** Checks if a given trampoline token is valid. */
export function isValidTrampolineToken(token: string) {
  return trampolineTokens.has(token)
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
