### Title
Unhandled ZeroDivisionError in mempool block-building when a fully-deduplicated item's cost is fully saved - (File: `chia/full_node/mempool.py`)

### Summary
`create_bundle_from_mempool_items` in `chia/full_node/mempool.py` computes `item_cost = cost - cost_saving` and unconditionally evaluates `fee / item_cost` inside a `log.info(...)` call before any check that `item_cost` is non-zero. If `item_cost` reaches `0`, this raises an unhandled `ZeroDivisionError`, analogous to the division-by-zero UB in iccDEV's TIFF handling (CVE-2026-34546), aborting block-template construction.

### Finding Description
In `create_bundle_from_mempool_items`: [1](#0-0) 

```
                else:
                    bundle_coin_spends, ff_state_update = singleton_ff.process_fast_forward_spends(...)
                    (
                        unique_coin_spends,
                        cost_saving,
                        atoms_saving,
```

`cost` is `item.conds.cost` (the mempool item's aggregate CLVM+condition cost), guaranteed non-zero at admission (`if cost == 0: return Err.UNKNOWN, None, []`, see `chia/full_node/mempool_manager.py:816-817`). `cost_saving` comes from `IdenticalSpendDedup.get_deduplication_info` in `chia/full_node/eligible_coin_spends.py:180-222`, which sums `dedup_coin_spend.cost` for every coin spend in the item that is `eligible_for_dedup` and was already registered by a previously processed (higher fee-rate) mempool item spending the same coin with the identical solution: [2](#0-1) 

Python evaluates all call arguments (including `fee / item_cost`) before invoking `log.info`, regardless of the configured log level, so this division executes unconditionally on every mempool item processed while building a block.

For a mempool item consisting of a single, fully DEDUP-eligible coin spend whose recorded per-spend cost equals the item's total `conds.cost` (i.e., no other spends or overhead contribute to the item's cost), `cost_saving` can equal `cost` exactly once an earlier item in the same block-building pass has already registered that identical (coin, solution) pair in `deduplication_spends`. In that scenario `item_cost == 0`, and `fee / item_cost` raises `ZeroDivisionError`.

### Impact Explanation
`create_bundle_from_mempool_items` is the code path a full node uses to assemble a spend bundle from mempool items when farming a block (the `create_bundle_from_mempool` public entry point calls it under `_db_conn` iteration order by `priority DESC, seq ASC`). An unhandled `ZeroDivisionError` raised mid-loop aborts block-template construction for that call, which is a spend-triggered transaction-processing halt: an unprivileged party can submit two ordinary spend bundles (one already in the mempool, one that duplicates an eligible coin spend with an identical solution) to reach this code path without any special privileges, matching the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
The trigger only requires the attacker to control the CLVM cost/solution shape of a single-spend, DEDUP-eligible transaction that is admitted into the mempool after an identical-coin-and-solution transaction from another party (or itself) is already present with a matching fee-rate ordering that puts it earlier in the cursor. Constructing a case where the item's *entire* cost equals the dedup-saved cost (no other spends, no cost outside the deduplicated spend) is plausible for a minimal one-spend transaction, but requires the exact cost bookkeeping to line up (no other cost components e.g. from a second non-dedup spend in the bundle). This makes exploitation feasible but requiring careful bundle construction, hence Medium likelihood.

### Recommendation
Guard the division: skip or special-case items where `item_cost <= 0` before computing `fee / item_cost` (e.g., log fee-per-cost only when `item_cost > 0`, or use `item.fee_per_cost` derived safely, or move the logging statement behind an explicit `if item_cost:` check). Additionally add an assertion/defensive check that `cost_saving` can never make `item_cost` non-positive, since a zero-cost mempool item is otherwise disallowed by `validate_spend_bundle`.

### Proof of Concept
1. Submit spend bundle `SB1` that spends coin `C` with puzzle/solution `S`, eligible for DEDUP, admitted into the mempool (fee `f1`).
2. Submit a second spend bundle `SB2` that is a single-spend transaction spending a *different* coin `C2` with the exact same puzzle reveal and solution `S` (also DEDUP-eligible against the same dedup key used for identical-spend aggregation), constructed so that `SB2`'s entire `conds.cost` equals the per-spend cost recorded for the duplicate solution, and admitted with a higher fee rate/priority ordering than `SB1` so it is processed by the cursor before `SB1` re-registers, or vice versa so that when `SB1`/`SB2` are processed in the same `create_bundle_from_mempool_items` pass, the second-processed item's `cost_saving` (looked up via `self.deduplication_spends`) equals its full `cost`.
3. Call `mempool.create_bundle_from_mempool(...)` / trigger block-template creation on the full node.
4. Observe an unhandled `ZeroDivisionError` raised from `chia/full_node/mempool.py:668` inside the block-building loop, aborting bundle creation for that call.

(Exact minimal cost values that make `cost_saving == cost` need to be validated empirically against `chia_rs` cost accounting for a single-spend bundle, since I could not execute code to confirm the precise numeric cost breakdown within this investigation — this is the main remaining uncertainty.)
