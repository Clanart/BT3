### Title
Governance vote can set `reward.proposerupdateinterval` / `reward.stakingupdateinterval` to zero despite genesis enforcing non-zero, risking division-by-zero panics - ([File: kaiax/gov/param.go])

### Summary
`params/config.go`'s `SetDefaultsForGenesis` explicitly treats `StakingUpdateInterval` and `ProposerUpdateInterval` as values that "must be nonzero because it is used as denominator," and overrides them to defaults if zero is found in genesis. However, the same parameters can be changed after genesis via a governance vote (`RewardProposerUpdateInterval` / `RewardStakingUpdateInterval`), and that governance path performs no such zero check, so the invariant enforced at genesis-time can be bypassed by an on-chain vote.

### Finding Description
In `params/config.go`, `SetDefaultsForGenesis` guards these two values specifically because they are used as denominators: [1](#0-0) 

But the corresponding governance parameter definitions in `kaiax/gov/param.go` use `noopFormatChecker` — i.e., no validation at all — for both `RewardProposerUpdateInterval` and (per the surrounding definitions in the same file) `RewardStakingUpdateInterval`: [2](#0-1) 

Contrast this with sibling parameters in the same table that *do* enforce non-zero, e.g. `IstanbulCommitteeSize` (`v > 0`) and `Kip71BaseFeeDenominator` (`v != 0`): [3](#0-2) [4](#0-3) 

Furthermore, `headergov`'s consistency checker (`checkConsistency`), which runs additional semantic validation for certain votes (e.g. bounding checks for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`), explicitly falls through `RewardProposerUpdateInterval` and `RewardStakingUpdateInterval` into the "no more checks here" bucket, accepting any value that merely passes the (non-existent) format check: [5](#0-4) 

This mirrors the reported bug class exactly: a constructor/genesis-time invariant ("must not be zero because it's used as a denominator") is enforced in one code path (`SetDefaultsForGenesis`) but not enforced in the corresponding runtime setter path (governance vote → `ParamSet.Set` → `checkConsistency`), allowing any council/governing-node voter to push the value to zero post-genesis.

### Impact Explanation
`StakingUpdateInterval` and `ProposerUpdateInterval` are consumed as denominators elsewhere in the codebase (staking and validator-proposer selection logic, per `kaiax/staking/impl/init.go` and `kaiax/valset/impl/getter_proposers.go`, both of which reference these parameters). If a governance vote sets either to `0`, any downstream modulo/division operation using that value would panic, causing a chain-wide crash/halt across all nodes processing the block that applies the new parameter — a state-processing DoS reachable via a normal governance transaction, not a privileged/node-operator action.

### Likelihood Explanation
Likelihood is bounded by needing an authorized governance vote (from the governing node/council, depending on `GovernanceMode`) to change these specific parameters, since `checkConsistency` only performs extra checks for a handful of parameters and passes these two through unconditionally. Given no additional gating exists at the format-check or consistency-check layer, any voter permitted to cast governance votes for reward parameters can trigger this with a single well-formed vote of value `0`.

### Recommendation
Add an explicit non-zero `FormatChecker` for `RewardProposerUpdateInterval` and `RewardStakingUpdateInterval` in `kaiax/gov/param.go` (analogous to `IstanbulCommitteeSize`'s `v > 0` check), so that governance votes attempting to set these denominators to zero are rejected at the same layer that other parameters (like `Kip71BaseFeeDenominator`) are protected, rather than relying solely on the genesis-time default-filling logic in `params/config.go`.

### Proof of Concept
1. A governing node (in `single` governance mode) or sufficient council votes (in `none`/other modes) submit a governance vote setting `reward.proposerupdateinterval` (or `reward.stakingupdateinterval`) to `0`.
2. `NewVoteData` accepts the vote because the associated `FormatChecker` is `noopFormatChecker` [2](#0-1) .
3. `checkConsistency` in `headergov` performs no additional validation for this parameter name and returns `nil` [5](#0-4) .
4. The vote is applied at the next epoch, and `GetParamSet` now returns `ProposerUpdateInterval == 0` (or `StakingUpdateInterval == 0`).
5. Any subsequent code path in the proposer-selection (`kaiax/valset/impl/getter_proposers.go`) or staking-update (`kaiax/staking/impl/init.go`) logic that divides/mods by this interval panics, halting block processing on every node that reaches that code path — consistent with the exact invariant `params/config.go` was trying to protect via `SetDefaultsForGenesis` [1](#0-0) .
