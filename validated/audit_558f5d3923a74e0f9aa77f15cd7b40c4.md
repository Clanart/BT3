## Analog Found

### Title
Missing duplicate-binding check in `register_token`/`update_token` lets two assets collide on the same `ContractToAsset` key, causing wrong-asset minting on `on_accept` - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
This is a direct structural analog of the yAxis `addToken` bug: a privileged registration call writes into a shared routing map (`vaults[_token]` in yAxis, `ContractToAsset` here) with no check that the key is not already bound to a *different* entry, so the second registration silently overwrites custody/routing state for the first asset.

### Finding Description
`register_token` and `update_token` in [1](#0-0)  insert into `TokenContracts` (asset → contract) and `ContractToAsset` (contract → asset) with no check that the target `(chain, token_contract)` pair in `ContractToAsset` is unbound or already owned by the same asset. `update_token`'s add-chain path has the same gap — it only clears the *old* reverse mapping belonging to the asset being updated [2](#0-1) , never checking whether the incoming `token_contract` is already claimed by a *different* asset ID.

`ContractToAsset` is the sole authentication and routing mechanism in `on_accept`: it both authenticates the source contract and determines which local asset gets minted/released for the beneficiary: [3](#0-2) [4](#0-3) 

If `register_token` (or `update_token`) is invoked a second time mapping a *different* `local_id` to a `token_contract`/`chain` pair already bound to an earlier asset, `ContractToAsset::<T>::insert` silently repoints that key to the new asset — exactly the "token first being added to two vaults" scenario from the yAxis report, where `vaults[_token]` gets reassigned and breaks the original vault's accounting.

### Impact Explanation
Once the collision occurs, any subsequent legitimate `on_accept` message from the *original*, unmodified EVM contract `X` on chain `C` resolves `local_asset_id` to the *new* asset B instead of the original asset A. Depending on custody model:
- If B is non-native, the pallet calls `Assets::mint_into` and mints fresh B tokens to the beneficiary out of thin air, with no corresponding backing (unauthorized minting / loss for the asset issuer). [5](#0-4) 
- Asset A's escrowed/locked funds in `Pallet::pallet_account()` become permanently stranded since no incoming message will ever resolve back to asset A's ID again (fund lock/loss for original depositors).

This matches the required impact classes: loss of funds, unauthorized minting/execution, and logic-driven mis-settlement of cross-chain transfers, without requiring a malicious relayer, prover, or compromised key — only a second `register_token`/`update_token` call that reuses a contract/chain pair.

### Likelihood Explanation
`register_token`/`update_token` are gated by `CreateOrigin` (governance/technical collective), so triggering the collision requires a privileged call — same trust level as `Manager.addToken` in the original yAxis report, which was also DAO-gated yet still rated High because "the DAO may mistakenly add the same token twice" or repoint a contract address during a token config update (e.g., re-pointing a chain's contract after a redeploy, a routine maintenance operation). No validation exists anywhere in the codebase to prevent this operational mistake, and once it happens the fund-loss/unauthorized-mint consequence is triggered entirely by ordinary, honest message flow from the legitimate remote contract — no attacker action needed beyond the original registration mistake.

### Recommendation
Before inserting into `ContractToAsset` in both `register_token` and `update_token`, verify the `(chain, token_contract)` key is either unbound or already bound to the same `local_id`:
```rust
if let Some(existing_asset) = ContractToAsset::<T>::get(chain, &token_contract) {
    ensure!(existing_asset == registration.local_id, Error::<T>::ContractAlreadyBound);
}
```
Apply the same guard in `update_token`'s add-chain loop.

### Proof of Concept
1. Governance calls `register_token` for `local_id = A`, `chains = { Evm(1) => ChainConfig { token_contract: X, decimals } }`. This sets `TokenContracts[(Evm(1), A)] = X` and `ContractToAsset[(Evm(1), X)] = A`.
2. Users bridge asset A through contract `X`; funds are escrowed in `Pallet::pallet_account()` awaiting return messages.
3. Governance later calls `register_token` again for a new `local_id = B` using the same `token_contract = X` on `Evm(1)` (e.g., mistakenly reusing an address, or intentionally repointing during a migration). `ContractToAsset[(Evm(1), X)]` is silently overwritten to `B`.
4. Contract `X` (unchanged, still legitimately holding/escrowing asset-A-equivalent value) sends a normal `on_accept` PostRequest back to the pallet.
5. `module.rs::on_accept` resolves `local_asset_id = ContractToAsset::get(Evm(1), X) = B` and mints/releases asset B to the beneficiary instead of releasing the escrowed asset A — unauthorized asset B is created/paid out, while asset A remains permanently locked in `pallet_account()`.
