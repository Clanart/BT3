### Title
Missing timestamp freshness check in App Proxy HMAC verification allows unlimited replay of signed proxy requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the HMAC signature over the app-proxy query string matches, but never checks the `timestamp` parameter that Shopify includes in every signed proxy request against a freshness window. This mirrors the reported bug class of using time-stamped signed data (`NodeOutput.Data` in the oracle report) without verifying the timestamp against a threshold.

### Finding Description
`query_string_valid?` extracts the `signature` param and recomputes the HMAC over the remaining sorted query params, then does a constant-time compare: [1](#0-0) 

The `timestamp` field is treated as just another signed parameter — it is included in the HMAC computation (as shown in the test fixtures using `timestamp=1466106083` from 2016), but the code never checks how old that timestamp is: [2](#0-1) 

Because the signature never expires, any request that was legitimately signed once by Shopify (and is captured via browser history, server logs, proxies, Referer headers, or a compromised CDN/cache) remains valid forever and can be replayed by an anonymous requester an unlimited number of times, as long as the shared `secret` is unchanged. `PayloadVerification#hmac_valid?` (used for webhooks and the extension verification controller) has the same structural gap — it never checks freshness of the request either, though Shopify webhook payloads don't carry an explicit timestamp field in the signed body the way app-proxy requests do: [3](#0-2) 

### Impact Explanation
Impact is Medium: an attacker who obtains one valid, previously-issued signed app-proxy URL (e.g., from logs, a shared link, browser history, or a misconfigured CDN cache) can replay it against the app's proxy endpoint indefinitely. Depending on what the app-proxy action does (e.g., issuing discount codes, triggering side effects, reading/writing data scoped to the shop identified in the query string), this can lead to duplicate or unauthorized actions being performed under the guise of a legitimately-signed Shopify request, with no way for the app to detect the request is stale.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to first obtain a previously valid signed query string (via log/URL leakage, browser history, shared links, etc.) rather than forging one from scratch. Given that app-proxy signed URLs are visible to any user browsing the storefront (they appear in the address bar/network requests of the merchant's storefront pages) and often get logged by CDNs, analytics tools, or referrer headers, capture-and-replay is a realistic attack path for third parties.

### Recommendation
In `query_string_valid?` (`lib/shopify_app/controller_concerns/app_proxy_verification.rb`), after confirming the signature is valid, parse the `timestamp` query parameter and reject the request if `Time.now.to_i - timestamp.to_i` exceeds a defined freshness threshold (e.g., a few minutes), similar to replay-protection patterns used elsewhere in the OAuth callback flow. Apply the same freshness check pattern to `PayloadVerification#hmac_valid?` wherever a timestamp is available in the request (e.g., some webhook headers), so that a valid HMAC alone is not sufficient — the request must also be recent.

### Proof of Concept
1. Observe a legitimately signed app-proxy request URL to a `ShopifyApp::AppProxyVerification`-protected endpoint, e.g. via a proxy log or browser history:
   `GET /apps/my-app?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd`
2. Replay the exact same URL at any later time (days, months, years later, as shown by the test fixture still using a valid signature from 2016).
3. `query_string_valid?` recomputes the same HMAC (unchanged since the query string and shared secret are identical) and returns `true`, so `verify_proxy_request` allows the request through with `head(:forbidden)` never triggered — confirming there is no timestamp-based freshness enforcement.     def verify_proxy_request
```ruby
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
