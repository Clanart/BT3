### Title
Stale cached FROST preprocess seed reused across `share()` and `complete()` enables secret key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2017-15227 is a lifecycle bug: an object removed from the live set was never removed from a tracking list, so later state updates operated on stale (freed) state. The analog in Serai is `SigningProtocol::preprocess_internal`, which caches a deterministic FROST preprocess seed in `CachedPreprocesses` keyed only by `context`, and never deletes it. `DkgConfirmer::complete` internally invokes `share_internal` a second time for the same `(b"DkgConfirmer", attempt)` context, re-deriving identical nonces from the stale seed. The two produced shares sign the same context but can be computed over different signing sets / challenges, which is textbook Schnorr nonce reuse and leaks the validator's MuSig secret share — i.e., the FROST-equivalent of "updating state later on" against an entry that should have been destroyed. [1](#0-0) 

### Finding Description
`preprocess_internal` only generates a fresh seed when `CachedPreprocesses::get(self.txn, &self.context)` is empty; after the first call the encrypted seed is stored and every subsequent call with the same context reconstructs the machine via `AlgorithmSignMachine::from_cache` with the same seed. [1](#0-0) 

`from_cache` routes to `seeded_preprocess`, which feeds the seed into `ChaCha20Rng::from_seed`, so the nonces (`Commitments::new` output) are a pure function of the cached seed — identical every time the cache is hit. [2](#0-1) 

The lifecycle violation (the analog of the dangling "destroyed channel" entry) is in `DkgConfirmer`:

- `share()` calls `share_internal`, which calls `preprocess_internal` → machine `A` built from the cached seed, emitting signature share `s_A` over `preprocesses` supplied by the caller. [3](#0-2) 
- `complete()` later calls `share_internal` *again* for the same `context = (b"DkgConfirmer", self.attempt)`, rebuilding a machine from the *same stale seed* (same nonces), then completes over `shares`. [4](#0-3) 
- The cache entry is never cleared — there is no `CachedPreprocesses::del`/remove anywhere; the "destroyed" preprocess remains live for the attempt's whole lifetime. [5](#0-4) 

The share emitted inside `complete()` is consumed by `complete_internal`, but `share()`'s output is broadcast externally during `DkgConfirmed` handling, while `complete()` is invoked when the accumulated confirmation shares become `Ready` — a distinct call site that can carry a different `preprocesses`/`shares` participant set. [6](#0-5) 

A FROST signature share is `s = d + b·ρ + λ·x·c` where `d + b·ρ` is the nonce and `c` is the challenge computed over the binding factors/commitment list. Two shares produced with identical nonces but different `included` sets (different ρ values / different challenge) yield `s₁ − s₂ = λ·x·(c₁ − c₂) + (bρ₁ − bρ₂)`; since ρ is publicly recomputed from the preprocesses, the difference reveals `λ·x`, and dividing by the known Lagrange coefficient recovers the validator's MuSig secret key share `x` — the raw `self.key` scalar used across the whole validator set. [7](#0-6) 

The code itself documents that this reuse is fatal: "Reusing preprocesses would enable a third-party to recover your private key share." [8](#0-7) 

### Impact Explanation
High. Any observer who collects two signature shares derived from the same cached seed with different challenges (publicly broadcast protocol messages) can algebraically recover the validator's MuSig secret key (`self.key`), the long-lived key identifying the validator in the set — not merely an ephemeral share. That key authorizes `Transaction`s signed on the tributary and participates in every future MuSig/FROST signing context, so recovery is equivalent to full impersonation of the validator for the session.

### Likelihood Explanation
The reuse is deterministic, not probabilistic: `complete()` unconditionally re-enters `share_internal` after `share()` already ran under the same `attempt` context, and the seed persists because no deletion path exists. The exploit condition reduces to the two calls seeing different effective signing inputs — which occurs whenever the set of preprocesses/shares accumulated at `Ready` differs from the set present when `share()` first ran (participants removed via `RemovedAsOfDkgAttempt` / `removed_as_of_dkg_attempt` change the `removed` list, the `threshold_i_map_to_keys_and_musig_i_map` mapping, and hence `msg` via `set_keys_message(..., removed, key_pair)`). [9](#0-8) [10](#0-9)  DKG re-attempts with evolving `removed` sets are a normal, attacker-inducible condition (a validator simply going offline changes the removed list between attempts), so a passive observer or a participating peer who triggers a re-attempt reaches this path with public inputs only.

### Recommendation
Delete the cache entry after first consumption — e.g., `CachedPreprocesses::del(self.txn, &self.context)` inside `share_internal` after `preprocess_internal` loads it — so the stale seed cannot be "updated later" (the exact fix pattern of the CVE: remove destroyed objects from the list). Additionally, have `complete()` accept the `AlgorithmSignatureMachine` produced by the earlier `share()` call (store/return it from `share()`) instead of re-deriving a machine from the cached seed. If caching across reboots must be retained, key the cache by a per-invocation nonce or burn the seed after producing a share, and assert at signing time that a seed-derived machine cannot produce two shares for distinct challenges.

### Proof of Concept
1. Validator set runs a DKG; attempt `a` proceeds to `DkgConfirmed` accumulation.
2. `DkgConfirmer::share(preprocesses_S1, key_pair)` executes: `CachedPreprocesses` has no entry for `(b"DkgConfirmer", a)`, so a seed is generated, cached, and share `s₁` (nonce `N`) is broadcast. [11](#0-10) 
3. Before/while confirmations accumulate, the removed set changes (a participant is fatally slashed or marked offline → `RemovedAsOfDkgAttempt` differs), so the `Ready` accumulation is handled with `removed'`/`preprocesses_S2` differing from S1 — a different `msg` and different binding factors/challenge. [12](#0-11) 
4. `DkgConfirmer::complete(preprocesses_S2, key_pair, shares)` calls `share_internal` again; the stale cached seed regenerates nonce `N` and produces share `s₂` under the new challenge. [13](#0-12) 
5. An observer with `s₁`, `s₂`, both preprocess sets, and the public messages computes `x = (s₁ − s₂ − (bρ₁ − bρ₂)) / (λ(c₁ − c₂))`, recovering the validator's MuSig secret key.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

**File:** spec/cryptography/FROST.md (L51-62)
```markdown
Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
```
