### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-shop webhook forgery - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook purely by checking that `HTTP_X_SHOPIFY_HMAC_SHA256` matches an HMAC-SHA256 of the raw request body against the app's shared secret. The shop-identifying header, `HTTP_X_SHOPIFY_SHOP_DOMAIN`, is never included in that HMAC computation, so it is not covered by the "authenticated" guarantee. Any actor who possesses one genuine, validly-signed webhook body (e.g. from their own installed shop) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `verify_request` will accept the request as valid, and downstream consumers key all shop-scoped processing off that unauthenticated header value.

### Finding Description
`verify_request` only validates the body: [1](#0-0) 

`shop_domain` is read straight from the header with no relation to the HMAC check: [2](#0-1) 

`hmac_valid?` computes the digest solely over `data` (the raw body), never mixing in the shop domain header: [3](#0-2) 

Generated webhook controllers/jobs then trust the (unauthenticated) shop identifier taken from the request/header to select which shop record to act on, mirroring the report's pattern of an unguaranteed-correct target identifier being trusted for a sensitive operation: [4](#0-3) [5](#0-4) 

This is directly analogous to the referenced Stakehouse finding: an operation (`_smartWallet` in the analog report; shop selection here) succeeds based on an address/identifier that is never cross-checked against the value that was actually authenticated (the ETH transfer success vs. the HMAC-validated body). Here, the HMAC only proves the request body came from someone possessing the app secret; it proves nothing about which shop the header claims to represent.

### Impact Explanation
Because every shop that installs the app shares the same app-level secret used for the HMAC, an attacker who legitimately controls one installed shop can generate a valid webhook body/HMAC pair for their own shop's events, then replay that request to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `verify_request` passes because the body HMAC is untouched, and the app processes attacker-controlled webhook data under the victim shop's identity (`Shop.find_by(shopify_domain: shop_domain)` in the generated job templates), leading to cross-shop data injection / processing performed with the victim's `with_shopify_session` context.

### Likelihood Explanation
Any merchant/developer who has installed the app (an "unrelated" tenant relative to the victim shop) can capture one of their own genuine webhook deliveries (trivial, since webhooks are delivered routinely) and replay it with a modified header via a normal HTTP POST to the publicly reachable webhooks endpoint. No secret leakage, host misconfiguration, or privileged access is required beyond having installed the app once.

### Recommendation
Do not treat `HTTP_X_SHOPIFY_SHOP_DOMAIN` (or any header) as trusted shop context unless it is itself covered by the HMAC or independently corroborated. Instead, derive the shop identity solely from an authenticated source — e.g., parse the shop domain out of the verified body payload (which Shopify includes for most webhook topics) rather than the header, or use the shop domain returned by `ShopifyAPI::Webhooks::Registry`/`Request` only after confirming it is derived from signed data, and reject requests where the header-derived and body-derived shop values disagree.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a real webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and HMAC header to the app's `/webhooks/:type` endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because the body and HMAC are unchanged; the header is never checked. [1](#0-0) 
4. Generated job/controller code passes the spoofed `shop_domain` to `Shop.find_by(shopify_domain: shop_domain)` and processes the attacker's webhook body under the victim shop's session context. [6](#0-5)

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
