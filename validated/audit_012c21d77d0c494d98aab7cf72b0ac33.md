Audit Report

## Title
Vote Account Commission-Collector State Corruption on Implicit V3→V4 Conversion - ([File: programs/vote/src/vote_state/mod.rs])

## Summary
`update_commission_collector` (SIMD-0232) allows the authorized withdrawer to set either the `InflationRewards` or `BlockRevenue` commission collector of a vote account [1](#0-0)  . When the target vote account is still stored in the legacy `V3` layout, the underlying handler implicitly converts it to `V4` as part of servicing the update, and the field the caller did not intend to touch is populated with a hardcoded V4-conversion default (`node_pubkey` for `BlockRevenue`) rather than being left untouched, which is confirmed by the repository's own test assertions [2](#0-1) [3](#0-2)  .

## Finding Description
`update_commission_collector` fetches the vote state through `get_vote_state_handler_checked`, verifies the withdrawer signature, resolves the new collector key, and then calls only `set_inflation_rewards_collector` or `set_block_revenue_collector` for the requested `CommissionKind` before persisting the state via `set_vote_account_state` [1](#0-0)  . The existing test `test_update_commission_collector` explicitly documents and reproduces the side effect: constructing a V3-encoded vote account, calling `update_commission_collector` only for `CommissionKind::InflationRewards`, and then asserting that the untouched `BlockRevenue` collector field is silently overwritten to `v3_node_pubkey` — a value the caller never specified for that field [2](#0-1) [4](#0-3)  . Because the write path is `get_vote_state_handler_checked` → mutate one field → `set_vote_account_state`, there is no isolation preventing the V3→V4 conversion step from stamping the second, unrelated collector field with a default derived from stale V3 data instead of preserving prior operator intent or leaving it unset. I was unable to directly inspect `try_convert_to_vote_state_v4` in `programs/vote/src/vote_state/handler.rs` to confirm the precise default-derivation logic due to a tool access failure, but the test's assertions (which must pass for the test suite to succeed) corroborate that this behavior is present and exercised in the current codebase.

## Impact Explanation
This causes silent corruption of vote-account commission-collector state: an operator who intends to set only the `InflationRewards` collector on a legacy V3-encoded vote account can inadvertently reset the `BlockRevenue` collector to `node_pubkey`, redirecting future block-revenue commission payouts away from the intended recipient (e.g., a treasury or multisig) to the validator identity account. This matches the fund-misdirection/loss impact category, since real commission lamports would flow to an address the operator did not choose for that purpose.

## Likelihood Explanation
This triggers deterministically and without any adversarial input whenever the authorized withdrawer invokes `update_commission_collector` against a vote account still encoded in the legacy `V3` format — which is the default state for any vote account not yet upgraded to `V4`. Any operator adopting the SIMD-0232 collector feature on an existing V3 vote account without setting both collectors simultaneously will hit this path, making it highly likely to occur in normal operation rather than requiring exploitation by a malicious third party.

## Recommendation
When implicitly converting a V3 vote account to V4 inside `update_commission_collector`'s call path, the untouched collector field must be explicitly preserved from any prior intended value or clearly documented as an operator-visible default, rather than silently derived from stale V3 fields such as `node_pubkey`. Consider requiring both collectors to be set together during the V3→V4 transition, or staging the "other" collector value and only committing an explicit default when no prior value exists.

## Proof of Concept
The existing test `test_update_commission_collector` in `programs/vote/src/vote_state/mod.rs` reproduces this: construct a `VoteStateV3` account, call `update_commission_collector` only for `CommissionKind::InflationRewards`, and observe that the `BlockRevenue` collector is overwritten to `v3_node_pubkey` even though it was never referenced in the instruction [4](#0-3) .

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
