Based on the codebase, the reported bug class ("contract sweeps its *entire* token balance to a caller without accounting for whether that balance rightfully belongs to the caller") has a direct, unprivileged-wallet analog in `ManualCompound.sol`.

### Title
Unprivileged caller can drain any leftover/dust reward-token balance held by `ManualCompound` by calling `compound()` with empty arrays - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` is a fully public, unpermissioned function. After (optionally) claiming rewards via `multiclaimOnBehalf`, it sweeps the entire current balance of every registered reward token held by the contract and sends it to `msg.sender`, rather than only sending the amount that was actually claimed for that caller in the current transaction.

### Finding Description
`compound()` first claims rewards on behalf of the caller via `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0)  and then, for every non-compoundable reward token and every registered compoundable reward token, computes the amount to forward using the contract's raw balance:
```
uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
``` [2](#0-1) 
and the "non-compoundable" branch does the same thing:
```
uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
if (rewardBalance > 0)
    IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
``` [3](#0-2) 

`compound()` has no access control and accepts caller-supplied `_lps` / `_rewards` arrays of any length, including empty arrays, which makes `multiclaimOnBehalf` a no-op (the internal `_multiClaim` loop is simply skipped when `_stakingTokens.length == 0`) [4](#0-3) . Despite this, the subsequent loop over `rewards[i]` still executes unconditionally and forwards *whatever* balance of each registered reward token currently sits in the `ManualCompound` contract to `msg.sender` [5](#0-4) .

Because reward-token balances can legitimately end up sitting in `ManualCompound` between calls — e.g. rounding remainders left over from a `convertor`/`locker`/`helper` call not consuming 100% of the approved `receivedBalance`, or any other caller's claimed-but-not-yet-fully-forwarded tokens — an unrelated, unprivileged wallet can call `compound()` with empty `_lps`/`_rewards` arrays and redirect that residual balance to itself. This mirrors exactly the reported `WithdrawPeriphery._convertToToken` bug class: using `balanceOf(address(this))` as the "amount to send to caller" instead of tracking only the delta attributable to the current caller's action.

### Impact Explanation
Any reward-token balance parked in `ManualCompound` that does not belong to the calling wallet (dust from imperfect conversions/locks, or tokens still in transit for other users' claims within the flow) can be permanently redirected to an arbitrary caller. This is a direct theft of other users'/protocol's unclaimed reward funds, satisfying the "concrete direct theft of user funds" bar, since the transferred tokens are `wom`/`mWom`/`mgp`-class reward tokens with real economic value and the taking wallet needs no special privilege.

### Likelihood Explanation
`compound()` is a public, unauthenticated entry point; calling it with empty arrays costs only gas and requires no prior state setup by the attacker. Any wallet can call it repeatedly/opportunistically to sweep whatever reward-token dust has accumulated in the contract at that moment, making exploitation trivial and repeatable, though the size of any single sweep depends on how much residual balance happens to be present.

### Recommendation
Compute the amount to convert/forward per reward token as the balance *delta* attributable to the current call (i.e., snapshot `balanceOf(address(this))` before calling `multiclaimOnBehalf`, and only forward `after - before` for each token), the same before/after-balance pattern already correctly used elsewhere in the codebase, e.g. `WombatStaking.withdraw` and `WombatPoolHelper._deposit` [6](#0-5) [7](#0-6) . Alternatively, add an owner-only sweep/rescue function for genuine dust and disallow using raw `balanceOf` as the caller-payable amount in `compound()`.

### Proof of Concept
1. Assume the `ManualCompound` contract ends up holding 100 units of `wom` as leftover dust from a previous `compound()` call (e.g., because `IConverter.convertFor` only consumed 99.999... of the approved `receivedBalance` due to rounding), leaving 100 units unaccounted for and belonging to no specific user.
2. An arbitrary wallet `Eve` (with no stake, no pending rewards) calls:
```
ManualCompound.compound([], [], 0, 0, false)
```
3. `multiclaimOnBehalf([], [], Eve)` is a no-op since `_stakingTokens.length == 0` [8](#0-7) .
4. The loop over registered `rewards` still runs, reads `receivedBalance = IERC20(wom).balanceOf(address(this)) == 100`, and forwards it to `Eve` via the configured convertor/locker/helper or direct `safeTransfer` [2](#0-1) .
5. `Eve` has extracted 100 units of `wom` that did not belong to her, with zero cost besides gas.
