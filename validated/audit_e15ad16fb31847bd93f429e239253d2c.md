### Title
Attacker-controlled block transactions inflate `median_fee`, causing Serai Bitcoin transactions to burn treasury funds as fees - (File: processor/src/networks/bitcoin.rs)

### Summary
The external report's bug class is: a protocol function reads externally manipulable on-chain state (Uniswap reserves) and writes it into a persistent baseline (`basis`), so that a later routine distributes/pays out far more than intended — theft of funds enabled by a single manipulation of a value the protocol blindly trusts. In Serai, `Bitcoin::median_fee` plays the role of `fetchBasis`: it derives the fee rate Serai will pay from fee data of arbitrary third-party transactions in a Bitcoin block, which an unprivileged party fully controls. That inflated rate is then applied as the baseline for the real fee paid by every `SignableTransaction` constructed from that block.

### Finding Description
`make_signable_transaction` fetches the fee rate for a planned transaction by calling `median_fee` on a recent block (processor/src/networks/bitcoin.rs:430-431):

```rust
let block_for_fee = self.get_block(block_number).await?;
let fee = self.median_fee(&block_for_fee).await?;
```

`median_fee` (lines 388-414) iterates `block.txdata[1 ..]`, computes `(in_value - out) / vsize` for each transaction, sorts the per-vbyte fee rates, and takes `fees.get(fees.len() / 2)`:

```rust
fees.sort();
let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);
Ok(Fee(fee.max(1)))
```

Every element of `fees` comes from transactions that any unprivileged Bitcoin user can create and get mined. There is no upper bound, no sanity cap, and no cross-check against mempool/estimatefee — the only floor is `.max(1)` sat/vbyte.

The resulting `fee.0` is passed straight into `BSignableTransaction::new` as `fee_per_vbyte` (line 451), which computes `needed_fee = fee_per_vbyte * vbytes` (networks/bitcoin/src/wallet/send.rs:206). If there is no change output, or the leftover change is below `DUST` (send.rs:224-235), the entire `input_sat - payment_sat` remainder becomes the paid fee regardless — and even with change, `needed_fee` is locked in at the manipulated rate. The transaction is then threshold-signed (send.rs:373-397) and broadcast; the overpaid fee is irrevocably donated to miners.

Like the flashloan in the original report, the manipulation is temporary (one block) but its effect is written into a committed value (the signed transaction's fee) that cannot be corrected afterward. And unlike `fetchBasis`, which required a keeper outage, `median_fee` is fed adversarial input on every single call — no privileged actor needs to fail.

### Impact Explanation
Loss of funds for the protocol: Serai's Bitcoin multisig pays inflated fees to miners on transactions it signs during the manipulated window. If several transactions (payments, aggregation, change creation) are planned off the same block's fee — a block can feed multiple `make_signable_transaction` calls — a single attacker transaction amplifies the damage across all of them. An attacker who mines (or collaborates with a miner via a fee-rate deal / out-of-band payment) recovers the fee they paid, making the manipulation nearly free, exactly as the flashloan made reserve manipulation nearly free in the original.

### Likelihood Explanation
- Reachability: fully unprivileged. Anyone can broadcast a Bitcoin transaction with a large fee; `median_fee` performs no authentication or bounds checking.
- Cost: for a block with few transactions, one high-fee transaction alone becomes the median (`fees[len/2]` with small `len`). The attacker pays the inflated fee once; Serai pays `rate * vbytes` on each transaction planned from that block. If the attacker has hashpower or a mining arrangement, the cost is recovered, so manipulation is cheap — the same asymmetry the original report relied on (flashloan → free skew → later profit).
- Mitigations in code are absent: no cap against a reference feerate, no averaging across blocks (`// TODO2: Use an fee representative of several blocks` at line 429 acknowledges this), no rejection of outlier fees.
- Trigger condition: Serai only needs to plan a Bitcoin transaction using a block that contains the attacker's transaction — a routine, continuously occurring event.

This maps to Medium/High under the same reasoning the judges applied: possible by an unprivileged party, leads to loss of protocol funds, though magnitude depends on attacker cost vs. number of affected transactions.

### Recommendation
- Bound `median_fee` against an independent, less manipulable reference (e.g., the node's `estimatesmartfee`, or a hard cap such as a multiple of the relay minimum).
- Use a robust statistic across multiple blocks (e.g., a trimmed mean or a lower percentile over several blocks) rather than the median of a single block's arbitrary transactions.
- Cap `needed_fee` in `SignableTransaction::new` at an absolute maximum so a manipulated `fee_per_vbyte` cannot cause unbounded fee burn, and/or reject `fee_per_vbyte` values that exceed a configured ceiling.

### Proof of Concept
1. Serai's scheduler plans a Bitcoin spend; `make_signable_transaction(block_number, ...)` is invoked.
2. Attacker broadcasts a transaction `T` paying an abnormally large fee (e.g., 1000 sat/vbyte), arranged to be mined in `block_number` — trivially satisfiable since miners prefer high-fee transactions, and free if the attacker mines the block themselves.
3. `median_fee` reads `block.txdata`; `T`'s fee rate becomes `fees[len/2]` and `Fee(1000)` is returned.
4. `BSignableTransaction::new` sets `needed_fee = 1000 * vbytes` — e.g., ~100x overpayment versus a ~10 sat/vbyte market rate — and the multisig signs and broadcasts it.
5. The excess satoshis are paid to the miner irreversibly; Serai's Bitcoin holdings are reduced by `needed_fee - honest_fee` per affected transaction, repeated for every transaction planned from that block.
