## Finding: Relayer-fee top-ups via `fundRequest`/`fund_message` are refunded to the *original payer* rather than the funder on timeout

### Title
Third-party fee top-ups on pending requests are refunded to the wrong beneficiary on timeout, causing permanent loss of the funder's tokens - (File: `evm/src/core/EvmHost.sol`, `modules/pallets/ismp/src/lib.rs`)

### Summary
`EvmHost.fundRequest()` and its Substrate counterpart `pallet_ismp::fund_message()` let *anyone* top up the relayer fee of a pending, in-flight request/response by transferring tokens from their own account. Both functions add the contributed amount to the stored `fee`, but never change the stored `sender`/`payer` field that determines who receives a refund on timeout. When the request eventually times out, the entire accumulated fee — original fee plus every third-party top-up — is refunded solely to the original `payer`, not to whoever actually supplied the top-up funds. This is the direct mirror of the Vader `[H-17]` bug class: value is attributed to the wrong account, except here it happens on the *credit* side (refund) rather than the *debit* side (burn).

### Finding Description
On EVM: [1](#0-0) 
`fundRequest` pulls `amount` from `_msgSender()` via `safeTransferFrom`/native swap, then does `metadata.fee += amount; _requestCommitments[commitment] = metadata;` — it never touches `metadata.sender`, which was fixed at dispatch time to `post.payer`: [2](#0-1) 

On timeout, the full fee is refunded to that original `meta.sender`: [3](#0-2) 

The identical pattern exists in the Substrate pallet. `fund_message` is a plain signed extrinsic (any account) that transfers `message.amount` from the caller to `RELAYER_FEE_ACCOUNT` and increments `metadata.fee.fee`, without updating the original `payer` stored in the commitment metadata: [4](#0-3) 

The runtime test explicitly demonstrates the accounting: the *same* `account` that dispatched the original request is the one that calls `fund_message`, and the whole `20 * UNIT` balance is attributed to that one account's `metadata.fee.fee`: [5](#0-4) 

If instead a *different* account funds someone else's pending request (e.g., to incentivize faster delivery of a stuck message, a legitimate and encouraged use case per the docs), and the request later times out, the timeout-refund path — which only knows about a single `sender`/`payer` field — sends the whole pot back to the original requester: [6](#0-5) 

The documentation confirms this is the actual, unguarded behavior rather than a corner case: "Additional fee refunded to `payer` if request times out." [7](#0-6) 

### Impact Explanation
Any unprivileged account that tops up a pending cross-chain request or response belonging to someone else (a normal, documented, permissionless action intended to speed up delivery) permanently loses those funds if the request times out — the tokens flow entirely to the original `payer`/`sender`, not to the funder. This is an unauthorized, wrong-beneficiary fund transfer that requires no malicious relayer, prover, or admin: it is triggered purely by the combination of two public entrypoints (`fundRequest`/`fund_message` and the existing timeout-refund logic) that already ship in the protocol. It directly violates the invariant that bridged fees/refunds "must move exactly once and only to the rightful beneficiary."

### Likelihood Explanation
High for anyone who actually uses the advertised "fund a stuck request to speed up delivery" feature on a request they didn't originate — a scenario the docs/README explicitly encourage ("Increase the relayer fee for in-flight requests... Should not be called on a message that has been completed"). No special conditions besides a normal request timeout are required; timeouts are a routine occurrence in ISMP messaging (network delays, high destination gas, relayer downtime).

### Recommendation
Track top-up contributions per-funder (e.g., a `Vec<(address/AccountId, amount)>` or separate mapping keyed by `(commitment, funder)`), and on timeout refund each contributor their own portion instead of sending the aggregate `fee` to a single stored `sender`. At minimum, `fundRequest`/`fund_message` should restrict top-ups to the original `payer` (matching `_msgSender()`/`account` against `metadata.sender`) if per-funder accounting is not desired, so third parties cannot lose funds to an address they don't control.

### Proof of Concept
1. Alice dispatches a `DispatchPost`/`DispatchGet` with `fee = X`, `payer = Alice`. `_requestCommitments[commitment] = {sender: Alice, fee: X}` (EVM) or the pallet's equivalent `RequestCommitments`.
2. Bob notices the message is stuck (fee too low for current gas prices) and calls `fundRequest(commitment, Y)` (EVM) or `fund_message(...)` (Substrate) from his own account, intending to help deliver Alice's message faster. `fee` becomes `X + Y`; `sender` stays `Alice`.
3. The request times out before any relayer delivers it (destination gas spike, relayer outage, etc.).
4. `dispatchTimeOut`/`on_request_timeout` refunds the full `X + Y` to `Alice` — Bob's `Y` is gone with no recovery path, confirmed by the existing test pattern in `test_dispatch_fees_and_refunds`/`test_fund_message`, which only exercises the single-payer case and never exercises (or guards against) a distinct funder.

		/// Add more funds to a message (request or response) to be used for delivery and execution.
		///
		/// Should not be called on a message that has been completed (delivered or timed-out) as
		/// those funds will be lost forever.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(5))]
		#[pallet::call_index(4)]
		pub fn fund_message(
			origin: OriginFor<T>,
			message: FundMessageParams<T::Balance>,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;

			let metadata = match message.commitment {
				MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),
				MessageCommitment::Response(commitment) =>
					ResponseCommitments::<T>::get(commitment),
			};

			let Some(mut metadata) = metadata else {
				return Err(Error::<T>::MessageNotFound.into());
			};

			T::Currency::transfer(
				&account,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				message.amount,
				Preservation::Expendable,
			)?;

			match message.commitment {
				MessageCommitment::Request(commiment) => {
					metadata.fee.fee += message.amount;
					RequestCommitments::<T>::insert(commiment, metadata);
				},
				MessageCommitment::Response(commiment) => {
					metadata.fee.fee += message.amount;
					ResponseCommitments::<T>::insert(commiment, metadata);
				},
			};

			Ok(())
		}

#[test]
fn test_fund_message() {
	let mut ext = new_test_ext();
	let account: AccountId32 = H256::random().0.into();
	let host = Ismp::default();

	ext.execute_with(|| {
		let msg = DispatchGet {
			dest: StateMachine::Evm(1),
			from: vec![0u8; 32],
			keys: vec![vec![1u8; 32], vec![1u8; 32]],
			context: Default::default(),
			height: 3,
			timeout: 2_000_000_000,
		};

		assert_eq!(Balances::balance(&account), Default::default());
		Balances::mint_into(&account, 20 * UNIT).unwrap();
		assert_eq!(Balances::balance(&account), 20 * UNIT);

		let commitment = host
			.dispatch_request(
				DispatchRequest::Get(msg.clone()),
				// lets pay 10 units
				FeeMetadata { payer: account.clone().into(), fee: 10 * UNIT },
			)
			.unwrap();

		// pallet-ismp now has it
		assert_eq!(Balances::balance(&RELAYER_FEE_ACCOUNT.into_account_truncating()), 10 * UNIT);

		// fund the request
		Ismp::fund_message(
			Origin::<Test>::Signed(account).into(),
			FundMessageParams {
				commitment: MessageCommitment::Request(commitment),
				amount: 10 * UNIT,
			},
		)
		.unwrap();

		assert_eq!(Balances::balance(&RELAYER_FEE_ACCOUNT.into_account_truncating()), 20 * UNIT);

		let metadata = RequestCommitments::<Test>::get(commitment).unwrap();
		assert_eq!(metadata.fee.fee, 20 * UNIT);
	});
}

### fundRequest()

Increases the relayer fee for a pending request to incentivize faster delivery.

```solidity lineNumbers
function fundRequest(bytes32 commitment, uint256 amount) external payable
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `commitment` | `bytes32` | The request commitment hash |
| `amount` | `uint256` | Additional relayer fee in fee token |

**Payment:**
- **Native token** (`msg.value`): Automatically swapped to fee token via Uniswap
- **Fee token**: Transferred from caller (requires prior approval)

**Behavior:**
- Additional fee refunded to `payer` if request times out
- Can be called multiple times for incremental increases
- If request already delivered, funds donated to protocol
