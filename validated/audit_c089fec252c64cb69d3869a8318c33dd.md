### Title
Out-of-bounds read / panic on attacker-influenced message length in `SchnorrkelHram::hram` - (File: crypto/schnorrkel/src/lib.rs)

### Summary
The GDAL report describes an out-of-bounds read in `memmove` reached when a length field inside a parsed file is trusted to locate buffer contents (`frmts/hdf4/hdf-eos/SWapi.c`). The Serai analog is `SchnorrkelHram::hram`, which parses an attacker-influenced `msg` buffer as `u32 ctx_len || ctx[ctx_len] || message` by reading a length prefix from the buffer and then slicing past it with no bounds check. A malformed length produces an out-of-bounds slice (`m[0..4]`, `m[4..(4 + ctx_len)]`, `m[(4 + ctx_len)..]`), panicking inside FROST share production — the same bug class: a buffer-internal length field driving an out-of-bounds memory access.

### Finding Description
`SchnorrkelHram::hram` at `crypto/schnorrkel/src/lib.rs:41-53` performs:

```rust
let ctx_len =
  usize::try_from(u32::from_le_bytes(m[0 .. 4].try_into().expect("malformed message")))
    .unwrap();
let mut t = signing_context(&m[4 .. (4 + ctx_len)]).bytes(&m[(4 + ctx_len) ..]);
```

The first four bytes of `m` are treated as a little-endian `u32` context length, and `m` is then sliced at attacker-controlled offsets `4 .. 4 + ctx_len` and `(4 + ctx_len) ..`. There is no check that `m.len() >= 4 + ctx_len` (nor even `m.len() >= 4`). Any `msg` shorter than 4 bytes, or whose leading `u32` exceeds `m.len() - 4`, causes `m[0..4].try_into()` to fail or the subsequent slice to panic with an index-out-of-bounds — the Rust manifestation of the report's OOB read.

`hram` is invoked from `Schnorr::sign_share` at `crypto/frost/src/algorithm.rs:208`, which is called by `AlgorithmSignMachine::sign` at `crypto/frost/src/sign.rs:398` with `msg` being the exact byte string supplied to `sign()`. `msg` is untrusted protocol input: it is the message the threshold group is asked to sign, and in the coordinator's Schnorrkel-based tributary path it is whatever `share_internal` is handed (`coordinator/src/tributary/signing_protocol.rs:170`), reaching it through the public `sign` API used with externally-proposed signing plans.

Supporting code: `crypto/schnorrkel/src/lib.rs:41-53`, `crypto/frost/src/algorithm.rs:201-211`, `crypto/frost/src/sign.rs:398`.

### Impact Explanation
A panic inside `sign_share` aborts the signing round mid-`sign()`, after the local preprocess/nonces have been consumed (`self.nonces.drain(..)` at `crypto/frost/src/sign.rs:386-396`) and after the machine's cached preprocess has been rotated. The panic unwinds out of `AlgorithmSignMachine::sign`, killing the signing attempt for that participant. Repeated across attempts, an attacker who can get a malformed `msg` admitted into a Schnorrkel signing session can deny signature production — matching the report's CVSS 5.5 `A:H` impact (local denial of service via OOB read). Because the panic occurs after nonce consumption, it also risks desynchronizing preprocess cache state relative to the emitted preprocesses, a secondary integrity concern for the `CachedPreprocess` path in `coordinator/src/tributary/signing_protocol.rs:144-147`.

### Likelihood Explanation
`msg` reaching `sign()` is external, untrusted data: it is the byte string a counterparty/plan asks the threshold group to sign (e.g., the serialized payload in `SignData`/batch flows). The panic triggers deterministically whenever `msg.len() < 4` or `u32::from_le_bytes(msg[0..4]) > msg.len() - 4` — no race, no secret required. The only requirement is that the `Schnorrkel` algorithm is the one in use, which is true for all Ristretto/substrate signing (`crypto/schnorrkel/src/lib.rs:77-80`, `coordinator/src/tributary/signing_protocol.rs:117`). Likelihood is constrained to Medium because Serai-internal callers are expected to pre-format `msg` as `ctx_len || ctx || payload` via `signing_context(...).bytes(...)`, so the attacker must influence a code path that feeds raw or truncatable bytes into `sign` rather than a properly framed message; the empty-`msg` invocation pattern (`machine.sign(preprocesses, &[])`, `processor/src/signer.rs:531`) shows frames where raw/non-context-formatted messages do reach `sign` for machine-level algorithms.

### Recommendation
Bound the parse before slicing:

```rust
if m.len() < 4 { panic-free error or defined behavior }
let ctx_len = u32::from_le_bytes(m[0..4].try_into().unwrap()) as usize;
if m.len() < 4 + ctx_len { return error / use saturating slice }
```

Since `hram` returns `C::F` and cannot fail, the clean fix is to treat malformed input as a defined, non-panicking path (e.g., clamp/encode the actual available bytes, or have `sign_share` validate `msg` framing before invoking `hram` and return `FrostError`). At minimum, validate message framing at the `Algorithm::sign_share` boundary so untrusted `msg` bytes cannot drive an out-of-bounds slice inside the hash function.

### Proof of Concept
With a `Schnorrkel` `AlgorithmMachine` and any valid `ThresholdKeys<Ristretto>` plus preprocesses:

```rust
// msg whose first u32 claims a 16-byte context but only 2 bytes follow
let msg = [16u32.to_le_bytes().as_slice(), b"ab"].concat();
// reaches SchnorrkelHram::hram -> m[4 .. 20] on a 6-byte buffer -> panic
machine.sign(preprocesses, &msg);
```

or simply `machine.sign(preprocesses, &[])` → `m[0..4]` panics on the empty slice. Both deterministically panic in `hram` (`crypto/schnorrkel/src/lib.rs:43-46`), aborting the signing round, directly mirroring the advisory's "length inside the buffer drives a read past the buffer" bug class.

Caveat: I could not fully verify, within the indexed context, every call chain that forwards a raw attacker-controlled buffer (rather than a Serai-framed `ctx_len || ctx || msg`) into `Schnorrkel` `sign`; the vulnerability stands on the missing bounds check in `hram` and the fact that `msg` is a public, untrusted input to the `sign` API.
