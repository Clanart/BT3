### Title
MessageSet extension-lookup guard (`Descriptor::IsExtensionNumber`) is applied on one payload-ordering path but omitted on the other in `WireFormat::MessageSetParser::ParseElement` - ([File: src/google/protobuf/wire_format.cc])

### Summary
`WireFormat::MessageSetParser::ParseElement` (the reflection-based binary parser for legacy `MessageSet` wire format, `src/google/protobuf/wire_format.cc:614-709`) resolves the extension `FieldDescriptor` for a `type_id` through two structurally symmetric branches depending on whether the `type_id` field or the `message` field arrives first on the wire. In the "type_id arrives first" branch (`state == State::kHasType`, lines 674-687) the code guards the lookup with `descriptor->IsExtensionNumber(type_id)` before calling `reflection->FindKnownExtensionByNumber`/`pool->FindExtensionByNumber`. In the "message arrives first" branch (`state == State::kHasPayload`, lines 636-664) the identical lookup is performed **without** the `IsExtensionNumber` guard.

### Finding Description
This mirrors the node-tar bug class: two code paths that are supposed to enforce the same security-relevant precondition (validating that a number is a legitimate extension number for the extendee) diverge, because one path re-implements the check with an extra guard while the sibling path — which an attacker can reach simply by re-ordering sub-fields inside the length-delimited `MessageSetItem` group — omits it.

Concretely, an attacker fully controls the wire bytes of a `MessageSetItem` group (tag 1, `START_GROUP`) and can choose the order in which the `type_id` (tag 2) and `message` (tag 3) sub-fields appear:
- Order A (type_id, then message): guarded by `descriptor->IsExtensionNumber(type_id)` (line 677).
- Order B (message, then type_id): **not** guarded (lines 636-644) — the code goes straight to `FindKnownExtensionByNumber`/`pool->FindExtensionByNumber` for any attacker-supplied `type_id`.

`Descriptor::IsExtensionNumber()` is the check that establishes that the field number falls inside a declared extension range for the extendee descriptor — the same "is this reference to a sanctioned target" role that node-tar's hardlink safety check plays before allowing a filesystem write. Skipping it in Order B means the subsequent lookup call is reached with an unvalidated number in exactly the situation the sibling branch was written to avoid.

### Impact Explanation
Whether this differential is exploitable beyond a harmless redundancy depends entirely on whether `Reflection::FindKnownExtensionByNumber` and `DescriptorPool::FindExtensionByNumber(descriptor, type_id)` themselves already restrict results to genuine, registered extensions of `descriptor`. Both functions are documented/expected to look up extensions scoped to the given extendee, so in the common case a missing `IsExtensionNumber` pre-check is redundant defense-in-depth rather than an independently exploitable gap. I was not able to fully verify, within available context, whether there exists any registration or pool state (e.g., dynamically-built extensions, lazily-built dependency pools, or extensions registered outside their declared numeric range) for which `FindExtensionByNumber`/`FindKnownExtensionByNumber` can return a non-null field for a `type_id` that `IsExtensionNumber` would have rejected. If such a case exists, the "message-first" ordering would let an attacker route MessageSet payload bytes into a message-typed extension field that should have been treated as unknown/out-of-range, causing that field to be populated with attacker payload data that the type_id-first path would have correctly rejected into unknown fields — a parsing-result/integrity divergence based purely on wire ordering, not on any legitimate schema property.

Given the uncertainty about whether the two lookup functions already close this gap internally, I cannot confirm actual memory-safety or type-confusion impact; the finding is a structural code-path inconsistency whose worst-case effect (if the lookup functions do not already gate on range) is at most a MessageSet field being processed instead of treated as unknown, i.e., no confirmed memory corruption. This keeps the confirmed severity at most Medium (integrity/consistency issue), not the High/Critical class typically associated with the node-tar CVE's arbitrary file overwrite.

### Likelihood Explanation
The precondition — attacker fully controls a bounded, well-formed MessageSet-encoded binary protobuf reaching a public `ParseFrom*`/`MergeFrom*` API, with a trusted schema that uses `option message_set_wire_format = true` (e.g. via the legacy `google.protobuf.bridge.MessageSet` or user-defined MessageSet types) — is realistic and requires no privileged access, hostile schema, or resource exhaustion. Reordering `type_id`/`message` sub-tags inside the `MessageSetItem` group is trivial to construct (the codebase's own `wire_format_unittest.h` conformance tests, e.g. `ParseMessageSetWithAnyTagOrder`, confirm both orderings are accepted as valid input). However, likelihood of actual harmful impact is gated on the unresolved question above about whether `FindExtensionByNumber`/`FindKnownExtensionByNumber` already enforce the extension-number-range invariant internally, which I could not conclusively verify.

### Recommendation
Apply the same `descriptor->IsExtensionNumber(type_id)` guard in the `state == State::kHasPayload` branch of `WireFormat::MessageSetParser::ParseElement` (lines 636-644) before calling `reflection->FindKnownExtensionByNumber` / `ctx->data().pool->FindExtensionByNumber`, matching the `state == State::kHasType` branch (lines 674-687) and the top-level `ParseMessageSet` loop (lines 725-735). Ideally, factor the guarded lookup into a single shared helper so the two orderings cannot diverge again, and add a conformance test that serializes the same MessageSet extension in both tag orders with a `type_id` deliberately outside `IsExtensionNumber` range, asserting identical (unknown-field) results regardless of order.

Inspect whether `reflection->FindKnownExtensionByNumber(N)` / `pool->FindExtensionByNumber(descriptor, N)` return non-null for this out-of-range `N` in either ordering; if they return non-null only in the message-first path (because the type_id-first path additionally required `IsExtensionNumber(N)` to be true before calling them), this would confirm a wire-order-dependent parsing divergence.
