### Title
Order-based splicing in Copilot merge-conflict reassembly can silently misattribute resolved content to the wrong conflict, corrupting the committed merge - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`reassembleResolvedFile` reconstructs a merged file by scanning the raw on-disk file for `<<<<<<<` / `=======` / `>>>>>>>` marker lines and replacing each detected block with the *next* entry from `hunkResolutions`, matched strictly by traversal order rather than by any stable identifier (e.g. line range or hunk id) tied back to the conflict the model actually analyzed.

### Finding Description
`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) walks `rawContent` line by line and, whenever it sees a line matching `reassemblyOursMarker` (`/^<{7}(?:\s|$)/`), looks ahead for a `=======` line and a `>>>>>>>` closing line. If found, it treats everything between as one "hunk" and splices in `hunkResolutions[hunkIndex]`, then increments `hunkIndex`: [1](#0-0) 

The doc comment for this function explicitly states the resolutions are "matched by order, not by line number": [2](#0-1) 

Separately, `validateResolutionPaths` only checks that the *count* of hunks the model returned equals the *count* of hunks the context-extraction step (`extractConflictHunks`, in `app/src/lib/copilot-conflict-context.ts`) found for that file: [3](#0-2) 

This is the same broken-invariant pattern as the vault report: one code path (extraction/context building, analogous to "shares burned") produces an authoritative count/accounting of N conflicts and asks the model for N resolutions; a second, independently-implemented code path (`reassembleResolvedFile`, analogous to the "transfer" logic) re-derives its own notion of where conflict blocks are by re-scanning raw content with a different algorithm, and mechanically consumes resolutions in the order it happens to encounter marker lines. Nothing ties a given `IHunkResolution` back to the specific conflict region it was generated for.

Attacker-controlled input: the `rawContent` being scanned is the working-tree file after a merge/rebase/cherry-pick against a repository the user is merging with — i.e., content that can originate from an attacker-controlled remote branch, fork, or PR the victim merges locally in Desktop. If a conflicting file's "ours" or "theirs" side (real source content, not a git-inserted marker) itself contains lines that happen to match the marker regexes — e.g. a code comment, string literal, embedded diff/patch text, or ASCII banner starting a line with 7+ `<`, `=`, or `>` characters — `reassembleResolvedFile`'s naive line scan can interpret that content as an additional (fake) conflict block distinct from the real one. If the extraction step (`extractConflictHunks`) parses hunk boundaries differently and does not count that same embedded text as a separate hunk, the two counts still match numerically in the simple case that matters for `validateResolutionPaths`, but the *positions* `reassembleResolvedFile` walks through no longer line up 1:1 with the conflicts the model reasoned about — a resolution meant for conflict 2 can be spliced into the location of a fake/real conflict encountered earlier, or an off-by-one shift can push every subsequent resolution into the wrong location for the remainder of the file.

### Impact Explanation
If a resolution is spliced at the wrong position, the file that Desktop presents as "Copilot-resolved" and that the user commits via `_applyCopilotConflictResolutions` will not actually match the reasoning/summary shown to the user, nor correctly merge the intended changes: [4](#0-3) 
This is a silent corruption of what the user commits — the resolved content the user reviews (or trusts) in the dialog and the content actually written to disk/committed can diverge from what either side intended, potentially dropping security-relevant changes, reintroducing vulnerable code that was supposed to be replaced, or silently merging in unintended content, all without any error or warning to the user.

### Likelihood Explanation
This requires the file being merged/rebased to contain source content that coincidentally or deliberately matches the loose marker regexes (7+ `<`, `=`, or `>` at start of line) inside a real conflict region. This is a narrow but realistic condition for source files that themselves discuss/contain git conflict markers, diff/patch fixtures, or long separator/banner comments — and can be deliberately engineered by an attacker who controls a branch the victim merges (e.g. via a malicious PR). Because the feature is a core "Continue Merge"/"resolve with Copilot" flow, likelihood is moderate rather than high, and is gated on triggering the mismatch rather than on every conflict.

### Recommendation
Do not rely on re-scanning raw content and matching resolutions purely by traversal order. Instead, have `extractConflictHunks` return stable positional identifiers (e.g., byte/line offsets or the exact original marker-block text) for each conflict it sends to the model, and have `reassembleResolvedFile` locate and replace each block by matching against that same identifier/verbatim original text rather than a re-derived, independently computed line scan. At minimum, harden the marker-detection regexes so extraction and reassembly use identical, shared parsing logic (single source of truth) so any embedded look-alike marker text is treated consistently by both stages, and add a runtime check that the number of blocks found during reassembly exactly matches the number of hunks extracted for that same file before splicing anything, failing loudly instead of proceeding with a mismatched count.

### Proof of Concept
1. Create a merge conflict in a file where one side's real content contains a line that matches the marker regex, e.g. inside `theirs`:
```
<<<<<<< HEAD
function real() { return 1 }
=======
// the following is sample text used in a tutorial, not a real conflict
<<<<<<< example
placeholder
=======
placeholder2
>>>>>>> example
function real() { return 2 }
>>>>>>> feature
```
2. Run this file through `extractConflictHunks` (context builder) and separately through `reassembleResolvedFile` with a `hunkResolutions` array sized to what `extractConflictHunks` reports.
3. Observe that `reassembleResolvedFile`'s line-walking loop, per its own logic at `app/src/lib/copilot-conflict-resolution.ts:559-591`, will detect the inner `<<<<<<< example ... >>>>>>> example` block as its own conflict block (since it independently matches the same marker regexes), consuming and incrementing `hunkIndex` an extra time relative to what `extractConflictHunks` counted as a single logical conflict — demonstrating the resolutions are no longer aligned with the correct region of the file.

Because I could not fully inspect `extractConflictHunks`'s exact boundary-detection algorithm in this session, I recommend a background engineer confirm whether its parsing of nested/embedded marker-like lines is identical to `reassembleResolvedFile`'s, which will determine whether the mismatch is exploitable exactly as described or only under a narrower set of malformed-marker conditions.
