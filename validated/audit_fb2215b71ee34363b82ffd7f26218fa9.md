### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s without flagging them - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes an action being executed (a refund/blacklist) while a state flag preventing continued/preconditioned action is never set. The analog in Serai is `Scanner::scan_block`, which scans every transaction in a block — including the coinbase (`block.txdata[0]`) — and emits `ReceivedOutput` values that are indistinguishable from ordinary spendable outputs. The output carries no flag marking it as a coinbase output bound by the 100-block maturity rule, so funds are reported received that are not yet spendable.

### Finding Description
`Scanner::scan_transaction` matches `output.script_pubkey` against the registered scripts and produces a `ReceivedOutput` containing only `offset`, `output`, and `outpoint` (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` iterates `block.txdata` wholesale, including the coinbase transaction at index 0 (`networks/bitcoin/src/wallet/mod.rs:221-227`).

The `ReceivedOutput` type (`networks/bitcoin/src/wallet/mod.rs:90-97`) has no maturity/coinbase marker. Downstream, `SignableTransaction::new` accepts any `Vec<ReceivedOutput>` as `inputs` and builds a transaction spending them (`networks/bitcoin/src/wallet/send.rs:150-185`), computing prevouts, fees, and witness structure with no maturity check. A transaction spending a coinbase output younger than 100 blocks is consensus-invalid and will be rejected by the Bitcoin network — yet nothing in the returned type distinguishes it.

A comment acknowledges the behavior ("If received outputs must be immediately spendable, a post-processing pass is needed"), but the API provides no way to perform that pass: `ReceivedOutput` does not expose whether its outpoint belongs to a coinbase, and the caller cannot recover that information from the returned data without re-scanning the block themselves.

### Impact Explanation
An unprivileged miner can craft a coinbase transaction paying a P2TR script the `Scanner` watches (the script is publicly derivable from the group key / registered offsets). `scan_block` then reports the output as a normal `ReceivedOutput`. Any consumer that feeds scanner results into `SignableTransaction::new` constructs and signs a consensus-invalid transaction burning a real input set; the "received" funds are unspendable until maturity and are silently mixed with mature funds. This is exactly the "funds reported received that are not spendable" impact class, and it is reachable purely via a Bitcoin transaction an unprivileged party causes to be mined/scanned.

### Likelihood Explanation
Any miner can place an arbitrary `script_pubkey` in their coinbase output at negligible cost. Triggering the bug requires the scanning key/script to be public or inferable, which is typical for deposit/bridge scanners watching a fixed threshold address. The defect triggers deterministically whenever a matching coinbase output is scanned — no race or misconfiguration is needed beyond the normal `scan_block` path. Impact is bounded to incorrect accounting / invalid transaction construction rather than key compromise, fitting Medium.

### Recommendation
Set the missing flag, mirroring the report's fix: mark coinbase-derived outputs so they cannot be silently treated as spendable. Concretely, either skip `block.txdata[0]` inside `scan_block` (forcing callers who want it to call `scan_transaction(&block.txdata[0])` explicitly), or add a `coinbase: bool` / maturity field to `ReceivedOutput` set when `tx.is_coinbase()` is true, and have `SignableTransaction::new` reject immature coinbase inputs.

```diff

-  for tx in &block.txdata {
+  for tx in &block.txdata[1 ..] {

  }
```
