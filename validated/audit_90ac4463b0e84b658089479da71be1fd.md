### Title
`EvmHost.fundRequest` refunds accumulated fee top-ups to an attacker-chosen `payer`, not the actual funder - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` records the refund beneficiary for a request's relayer fee as an attacker-controlled `post.payer` field that is fully decoupled from the address that actually supplies the tokens (`_msgSender()`), exactly like the Hyperdrive bug where the token-owner/beneficiary identity used for downstream fund movement was an untrusted parameter rather than the true depositor. Any later caller who tops up that same request via the public `fundRequest` function has their contribution permanently bound to the original attacker-chosen `sender`, so on timeout the entire accumulated fee — including funds that never came from the attacker — is refunded to the attacker. [1](#0-0) 

### Finding Description
In `dispatch(DispatchPost memory post)`, the fee token is always pulled `from _msgSender()`: [2](#0-1) 

but the `FeeMetadata` stored for the request commitment binds the refund identity to the caller-supplied `post.payer` field instead of to `_msgSender()`: [3](#0-2) 

This is already a decoupling of "who paid" from "who gets refunded," analogous to Hyperdrive's `_lp` parameter being distinct from the actual token source. The exploitable consequence appears in `fundRequest`, which lets *any* address top up the fee for *any existing* commitment by transferring tokens from themselves: [4](#0-3) 

Note that `fundRequest` only checks `metadata.sender != address(0)` (i.e., that the commitment exists) — it never verifies that `_msgSender()` matches `metadata.sender`, and it never records or tracks which address contributed which portion of `metadata.fee`. It simply increases `metadata.fee` while leaving `metadata.sender` (the original `post.payer`) unchanged.

When the request times out, the whole accumulated `meta.fee` is refunded in one shot to `meta.sender`: [5](#0-4) 

(The GET-request path binds `sender` correctly to `_msgSender()` at creation time, confirming the POST path's use of an independent `payer` field is the anomalous, exploitable divergence.) [6](#0-5) 

### Impact Explanation
An attacker can create a cheap/low-fee POST request whose `FeeMetadata.sender` they control (by setting `post.payer` to their own address), then wait for any legitimate user or integrator to call the public, unauthenticated `fundRequest` function to boost that same request's relayer incentive (a normal, expected action meant to help a stuck cross-chain message get relayed faster, or to top up a fee they mistakenly under-funded). All of that user's contributed feeToken becomes irrecoverably owned by the attacker once the request times out, since the refund is unconditionally paid to `meta.sender`. This is direct, unauthorized loss of funds to an attacker-chosen beneficiary via a public entrypoint — matching the "stealing or loss of funds" / "wrong beneficiary" impact class, with no relayer, prover, or governance compromise required.

### Likelihood Explanation
Both `dispatch(DispatchPost)` and `fundRequest` are unauthenticated, permissionless, public functions reachable by any EOA or contract. The `payer` field is fully attacker-controlled at request creation, and `fundRequest` performs no ownership check tying the top-up sender to the commitment's registered beneficiary. Any legitimate use of `fundRequest` to rescue/accelerate someone else's (or even their own, if `payer` was set by an intermediary module to a different identity) pending request is immediately at risk. The only prerequisite is that a request commitment exists and eventually times out — both are routine, expected protocol states, not adversarial assumptions.

### Recommendation
- Require `fundRequest` callers to either match `metadata.sender` or explicitly track per-funder contributions (e.g., a `mapping(bytes32 => mapping(address => uint256))` of top-up amounts) and refund each contributor their own share on timeout.
- Alternatively, bind `FeeMetadata.sender` to `_msgSender()` at dispatch time (as already done for GET requests) rather than trusting a caller-supplied `post.payer`, removing the decoupling entirely, consistent with the Hyperdrive fix of "always transfer/attribute from `msg.sender`."

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchPost({..., fee: 1, payer: attacker, timeout: T}))`. This pulls `1` feeToken unit from the attacker and stores `FeeMetadata({sender: attacker, fee: 1})` for `commitment`.
2. A legitimate user Bob, wanting to ensure the request (which may be his own outbound message routed through the same commitment scheme via an integrating module, or simply an act of goodwill/incentive-bumping) gets relayed, calls `EvmHost.fundRequest(commitment, 10_000e6)`, transferring `10_000e6` feeToken from himself into the Host. `metadata.fee` becomes `10_000e6 + 1`, but `metadata.sender` remains `attacker`.
3. The request times out without being delivered (or the destination handler naturally reverts/needs retry). The relayer submits the timeout proof, invoking `dispatchTimeOut(PostRequestTimeout, meta, commitment)`.
4. `EvmHost` refunds `meta.fee = 10_000e6 + 1` entirely to `meta.sender = attacker`, per line 903, even though Bob supplied `10_000e6` of it. Bob's funds are permanently lost to the attacker. [7](#0-6)

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});

    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }
