### Title
Positional (not identity-based) hunk-to-marker matching lets an attacker-influenced Copilot response silently swap conflict resolutions between hunks - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile()` reassembles a Copilot-resolved file by walking the on-disk conflicted file and splicing `hunkResolutions[hunkIndex]` into each successive `<<<<<<<`/`=======`/`>>>>>>>` block it encounters, **matched purely by array order, not by any content or position identity** [1](#0-0) . The only server-side guard, `validateResolutionPaths()`, checks that the *count* of hunks returned for a file equals the expected count — it never verifies that hunk *N* in the model's response actually corresponds to conflict block *N* in the file [2](#0-1) . This is structurally the same invariant violation as the `StrategyManager.addPairAllocation()` bug: two parallel data structures (conflict-block order vs. resolution order) are assumed to stay aligned, but nothing enforces or re-normalizes that alignment before the values are committed.

### Finding Description
The system prompt tells the model that `hunks` must be "An ordered array with one entry per conflict in the file, matching the 'Conflict 1 of N', 'Conflict 2 of N' order from the input" [3](#0-2) , but this is only a prompt instruction — there is no structural tag (e.g. a hunk id/anchor) tying a returned `resolvedContent` to the specific conflict block it must replace. `parseCopilotConflictResolution()` validates shape (string type, no leftover markers) but not order/identity [4](#0-3) . `validateResolutionPaths()` only compares `resolution.hunks.length` to the expected hunk count per path [2](#0-1) , so a response with the same count but transposed order for two-or-more-hunk files passes validation cleanly. `reassembleResolvedFile()` then walks the raw file, and for every well-formed conflict block increments `hunkIndex` and blindly pulls `hunkResolutions[hunkIndex]` [5](#0-4) . If the model returns hunk resolutions out of order — whether from confusion on files with multiple/nested conflicts, or steered by content in the conflicting branch itself (the model reads and reasons over full file/conflict content that is fully attacker-controlled when merging a malicious remote branch, PR, or fetched ref) — the wrong resolved content is spliced into the wrong conflict location. The result is written verbatim via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged with `git add` once the user clicks "Continue Merge" [6](#0-5) , with no diff-level structural check that resolved content matches the corresponding original hunk's context.

Note that the existing path-traversal guard (`resolveWithin`) and the "user already resolved externally" guard at that call site are unrelated protections that do **not** address this specific hunk-ordering/identity gap [7](#0-6) . Notably, the project's own changelog documents a prior, closely related bug class in this exact subsystem — "Resolve Copilot conflict resolution data loss where file content outside conflicted regions was overwritten when using AI-assisted conflict resolution" (3.5.13-beta3) [8](#0-7)  — confirming that index/positional mismatches in this reassembly logic are a demonstrated, recurring fragility.

### Impact Explanation
An attacker who controls a branch/PR/remote that a victim merges, rebases onto, or cherry-picks from (a classic "attacker controls a fetched/cloned repository" scenario) can craft a file with multiple conflict hunks such that the model is likely (or, with embedded prompt-injection text inside code comments/strings that the model reads as part of its context, more reliably) to return hunk resolutions out of order. Because `validateResolutionPaths()` cannot detect this, the wrong resolved content silently replaces the wrong conflict region, and once the user clicks "Continue Merge" the corrupted file is written to disk and staged/committed without any visible warning. This is a silent corruption of what the user commits/pushes — potentially reintroducing vulnerable code, dropping security fixes, or injecting attacker logic into a section of the file the user believed was reviewed and correctly resolved by the "ours" or "theirs" side they intended.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a file with 2+ conflict hunks, and (b) the model returning hunk resolutions in the wrong order. Ordinary model imperfection alone can trigger this on complex multi-hunk files; an attacker can materially increase the odds by engineering the conflicting content (e.g., deceptive comments, misleading hunk boundaries, or explicit prompt-injection text embedded in the "theirs" side of the conflict) to bias the model toward reordering hunks, since the model has no tool access and reasons only over the textual content supplied — content the attacker fully controls in the malicious branch. No local access, credentials, or social engineering beyond a normal merge/rebase workflow is required.

### Recommendation
Do not rely on positional array order to bind a hunk resolution to its physical conflict block. Instead:
1. Tag each conflict block sent to the model with a stable identifier (e.g. `Conflict 1 of N` markers already described in the prompt) and require the model to echo that identifier back per hunk resolution.
2. In `reassembleResolvedFile()`, match resolutions to conflict blocks by that identifier rather than by array index, and reject/flag any resolution whose identifier is missing, duplicated, or doesn't match the expected set.
3. Strengthen `validateResolutionPaths()` to fail (not just count-check) when hunk identifiers are absent or inconsistent with the expected ordered set.
4. Consider a post-write structural sanity check (e.g. diffing resolved content against ours/theirs to flag resolutions that look implausible relative to the conflict they claim to resolve) before staging.

### Proof of Concept
1. Create a file with two independent conflict blocks (Conflict 1: security-check logic; Conflict 2: unrelated formatting change), on a branch fetched from an attacker-controlled remote.
2. Attacker crafts the conflicting content/comments so that, when Copilot resolves the merge, it returns:
   ```json
   "resolutions": [{
     "path": "src/auth.ts",
     "hunks": [
       { "resolvedContent": "<content meant for Conflict 2>" },
       { "resolvedContent": "<content meant for Conflict 1>" }
     ],
     "reasoning": "..."
   }]
   ```
3. `validateResolutionPaths()` sees `hunks.length === 2 === expectedHunkCounts.get(path)` and passes [9](#0-8) .
4. `reassembleResolvedFile()` splices `hunkResolutions[0]` into the first `<<<<<<<...>>>>>>>` block found (the security-check conflict) and `hunkResolutions[1]` into the second, swapping the intended content [5](#0-4) .
5. User clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the swapped content to disk and stages it with `git add`, silently corrupting the security-relevant hunk with the unrelated formatting change (or vice versa) [6](#0-5) .
