### Title
Missing enforcement of `sighash_type == SinglePlusAnyoneCanPay` in `Aggregator::optimistic_payout` allows a malleated user signature to bind to no output - ([File: core/src/rpc/aggregator.rs])

### Summary
In `Aggregator::optimistic_payout`, the aggregator computes the sighash for the user-supplied `input_signature` using whatever `sighash_type` the attacker embedded in that signature (`input_signature.sighash_type`), and never asserts that this value equals `TapSighashType::SinglePlusAnyoneCanPay` before calling `SECP.verify_schnorr`. This lets an attacker submit a `TapSighashType::None` (or other non-output-binding) signature that passes verification for arbitrary `output_amount`/`output_script_pubkey` combinations, because `calculate_pubkey_spend_sighash(0, TapSighashType::None)` does not commit to the payout output at all.

### Finding Description
The intended binding is: `input_signature.sighash_type == TapSighashType::SinglePlusAnyoneCanPay` guarantees that the message signed by the user (`user_xonly_pk`) commits to the specific `output_txout` (amount + script) chosen for that call. This is exactly what the error message on verification failure implies ("Ensure the signature uses SinglePlusAnyoneCanPay sighash type") — but that string is only shown *after* a failed `verify_schnorr`, it is not an actual precondition enforced in code.

Tracing `core/src/rpc/aggregator.rs`:
- `parse_withdrawal_sig_params` extracts `input_signature` (a `taproot::Signature`, attacker-controlled bytes including `sighash_type`) directly from the request.
- `create_optimistic_payout_txhandler` builds the payout tx using the attacker-chosen `output_amount`/`output_script_pubkey` [1](#0-0) .
- The sighash used for verification is computed with the attacker-supplied type: `opt_payout_txhandler.calculate_pubkey_spend_sighash(0, input_signature.sighash_type)` [2](#0-1) .
- `SECP.verify_schnorr` is then called against `user_xonly_pk` with no prior assertion on `input_signature.sighash_type` [3](#0-2) .

If `sighash_type == TapSighashType::None`, the resulting sighash does not commit to any output, so the same 64-byte Schnorr signature can validate against two different `WithdrawParams` (different `output_amount`) for the same `input_outpoint`/`deposit_id`, since `is_utxo_spent` is only checked once at the top of `optimistic_payout` and is not re-checked atomically with the signature verification or with any in-flight signing session for the same deposit.

However, the value-moving authorization for the actual vault funds is *not* this user signature. The transaction's second input (index 1, the deposited move-to-vault UTXO) is signed by the verifiers' musig2 N-of-N process, and that sighash is computed separately with a fixed, non-attacker-controlled sighash flag: `calculate_script_spend_sighash_indexed(1, 0, bitcoin::TapSighashType::Default)` [4](#0-3) . `TapSighashType::Default` commits to all outputs, so each concrete `output_amount`/`output_script_pubkey` combination requires its own dedicated nonce-generation/co-signing round with the verifiers before a usable N-of-N signature for that specific output exists. The user-signature check at line 1125 gates whether the aggregator even proceeds to request verifier co-signing, but it does not itself produce the fund-moving signature.

I was unable to fully inspect `Verifier::sign_optimistic_payout` (in `core/src/verifier.rs`) within the available tool budget to confirm whether it re-validates `output_amount`/`sighash_type` or enforces any per-deposit uniqueness/locking before contributing its partial signature, so I cannot confirm or rule out whether the verifier side independently blocks the described race of two concurrent co-signing sessions for the same `deposit_id`/`withdrawal_utxo`.

### Impact Explanation
If the missing sighash-type check on the aggregator side is combined with an absence of a locking/uniqueness guard in `Verifier::sign_optimistic_payout` for concurrent optimistic-payout sessions on the same `deposit_id`, the impact would be Critical: N-of-N partial signatures produced for two different spends of the same vault UTXO, only one of which corresponds to funds actually authorized by the Citrea withdrawal record. This is unverified for the verifier side due to incomplete code review.

### Likelihood Explanation
The precondition on the aggregator side (no explicit sighash-type check) is confirmed directly from `core/src/rpc/aggregator.rs`. The full exploit additionally requires a race window and an absence of session-level locking in the verifier's signing path, which I could not confirm within this investigation due to tool-call exhaustion.

### Recommendation
Explicitly assert `input_signature.sighash_type == TapSighashType::SinglePlusAnyoneCanPay` in `Aggregator::optimistic_payout` before computing the sighash / calling `verify_schnorr`, rather than relying on `verify_schnorr` to fail organically for non-binding sighash types. Additionally, verify (in a follow-up review of `Verifier::sign_optimistic_payout`) that concurrent optimistic-payout signing sessions for the same `deposit_id`/`withdrawal_utxo` are serialized/locked so that only one in-flight co-signing round per deposit can produce verifier partial signatures.

### Proof of Concept
Not produced — the aggregator-side gap is demonstrable in isolation (craft a `taproot::Signature` with `sighash_type = TapSighashType::None` over `calculate_pubkey_spend_sighash(0, TapSighashType::None)` for one `output_amount`, then show `SECP.verify_schnorr` at line 1125 also passes for a second, different `output_amount`), but a complete `cargo test` demonstrating the Critical impact (two verifier co-signed transactions for the same vault UTXO) requires confirming `Verifier::sign_optimistic_payout`'s locking behavior, which was not fully verified in this pass.
