## Confirmed: SIGHASH_SINGLE|ANYONECANPAY leaves the OP_RETURN output unauthenticated

The binding this question challenges: **`payout_payer_operator_xonly_pk` credited in the DB == the operator whose `Operator::withdraw`/`create_payout_txhandler` actually built/broadcast the tx**. Tracing the code confirms this binding is **not enforced cryptographically** — it depends entirely on the shape of the confirmed on-chain transaction, and the user's authorizing signature does not cover the output that carries operator attribution.

### Evidence

- `create_payout_txhandler` builds a 3-output tx: `[0] user payout, [1] anchor, [2] OP_RETURN(operator_xonly_pk)`, with a single **key-spend** input authorized only by `user_sig`: [1](#0-0) 
- The proto explicitly documents (and the code enforces) that this user signature must use `SinglePlusAnyoneCanPay`: [2](#0-1)  and the operator verifies it against that sighash type: [3](#0-2) 
- `SIGHASH_SINGLE` commits **only to the output at the same index as the input (index 0)**; `ANYONECANPAY` restricts input commitment. Neither covers output `[2]` (the OP_RETURN carrying the operator pubkey) or output `[1]` (anchor). This means **the OP_RETURN content is entirely unauthenticated by the user's signature** — any party holding a valid `(user_sig, input_outpoint, output_txout)` triple can attach *any* OP_RETURN payload and the resulting transaction remains a valid, broadcastable spend of the withdrawal UTXO.
- The verifier's attribution logic trusts confirmed chain data blindly: it finds any tx spending the registered `withdrawal_utxo_txid/vout` via `get_payout_txs_for_withdrawal_utxos` (a DB join keyed only on outpoint, with **no check of who built or signed the tx beyond the input spend**) [4](#0-3) , then parses whatever xonly pubkey sits in the first OP_RETURN and writes it to `payout_payer_operator_xonly_pk` with **zero cross-check against any operator action** — this happens in `update_finalized_payouts`: [5](#0-4) 
- That DB column is later trusted, without additional Bitcoin-level proof, to bind operator identity to the withdrawal for kickoff-eligibility (`get_first_unhandled_payout_by_operator_xonly_pk`, consumed automatically by `PayoutCheckerTask::run_once`, which calls `handle_finalized_payout` and proceeds to `end_round`/kickoff on the operator's behalf): [6](#0-5) 
- Downstream, `is_kickoff_malicious` only checks that the kickoff's `operator_xonly_pk` matches the DB-recorded `payout_payer_operator_xonly_pk` — it never re-derives that it was actually O who authored the payout tx: [7](#0-6) 
- Crucially, all of the profitability/consistency checks that exist in the legitimate path (`withdrawal_utxo != input_utxo.outpoint`, `is_profitable`) live only inside `Operator::withdraw`: [8](#0-7) . Since the attacker constructs and broadcasts the transaction **directly**, bypassing this RPC entirely, none of these guards run.

### Conclusion

The `TransactionType::Payout | TransactionType::Challenge` identical match-arm observation in `tx_sender_queue.rs` is a symptom, not the root cause — the real gap is that the protocol's payout→operator binding relies solely on OP_RETURN content in a confirmed transaction, and the mandated `SinglePlusAnyoneCanPay` sighash flag structurally excludes that OP_RETURN output from the user's authorization. An attacker acting as the withdrawing party (registers withdrawal on Citrea, owns the input UTXO and its key, chooses the sighash flag as permitted by the ruleset) can produce a validly-signed payout transaction, insert an arbitrary operator's x-only pubkey into the OP_RETURN, and broadcast it directly to Bitcoin without ever invoking that operator's `withdraw`/`create_payout_txhandler`. This transaction confirms, is picked up by `update_finalized_payouts`, and results in operator O being bound to (and later reimbursed for) a payout O never funded or authorized — matching the Critical impact category "an operator reimbursed for a payout it never funded."

I was not able to fully trace whether any additional Citrea-side (contract) validation re-derives/enforces the operator identity from the payout tx independent of the Clementine-side OP_RETURN parsing (that logic lives in the Citrea Bridge contract / bridge circuit, outside this repo's direct control, though `circuits-lib/src/bridge_circuit/mod.rs` shows the bridge circuit itself also just parses `parse_op_return_data` from the payout tx with the same trust assumption [9](#0-8) , suggesting the same unauthenticated-OP_RETURN weakness propagates into the ZK circuit layer as well). This would need confirmation via a live regtest/Citrea test, which requires a background Devin session to construct and broadcast a hand-crafted transaction and assert the DB-level attribution, as suggested by the proof idea in the question.
