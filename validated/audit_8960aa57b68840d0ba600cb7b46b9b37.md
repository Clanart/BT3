Based on my investigation, the strongest local analog to the Surge fee-share miscalculation is a proportional-escrow-release bug in `IntrinsicIntents._fillSameChain`, where the code assumes a strict 1:1 positional pairing between `order.inputs[i]` and `order.output.assets[i]` that is never enforced when the order is created.

### Title
Same-chain fill loop indexes `order.inputs[i]` by output-array position with no enforced length parity, letting escrow release/lock diverge from actual fill state - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`placeOrder` in [1](#0-0)  never validates that `order.inputs.length == order.output.assets.length`. `_fillSameChain` then iterates `for (uint256 i; i < outputsLen; i++)` and unconditionally reads `order.inputs[i]` to compute the escrow amount to release for output slot `i`: [2](#0-1) . This silently assumes each output asset has a dedicated, positionally-matched input asset — an invariant that is never checked or documented as required at order-placement time.

### Finding Description
The proportional-release formula itself, `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`, mirrors the Surge bug's shape (a ratio computed against the wrong/mismatched base value) at [3](#0-2) . Because `inputsLen` and `outputsLen` are independent lengths that no code path forces to be equal, an order with more `inputs` than `output.assets` (e.g. two escrowed input tokens funding a single output pair) causes the fill loop to only ever touch `order.inputs[0..outputsLen-1]`. Any input tokens at indices `>= outputsLen` are never included in `escrowedInputs`, never passed to `_withdraw`, and never decremented from `_orders[commitment][token]` — yet `isFullyFilled` still evaluates to `true` because it is only set `false` when a *tracked* output's `remaining` is nonzero, at [4](#0-3) . The order is then marked filled and `OrderFilled` is emitted at [5](#0-4)  while an entire escrowed token position sits untouched in `_orders`.

The corrupted value is `isFullyFilled` (and, by extension, `_filled[commitment]`): it reflects only the subset of inputs whose index falls under `outputsLen`, not the true completion state of all escrowed inputs for the order.

### Impact Explanation
This produces a state where the protocol's `_filled` bookkeeping says the order is fully settled (guards built on `_filled != 0` elsewhere, e.g. duplicate-fill prevention, treat the order as closed) while real value remains locked in `_orders[commitment][token]` for the untracked input token. Because `_cancelSameChain`, at [6](#0-5) , does not check `_filled[commitment]` before refunding whatever remains in `_orders`, the same commitment can end up in a state where one input was already handed to the solver as part of a "completed" fill and a second input is later drained via cancellation — a split disposition of one order's escrow across two different finalization paths, which is exactly the kind of "logic attack / wrong beneficiary or amount / duplicate settlement" invariant break the bounty targets.

### Likelihood Explanation
The trigger requires nothing beyond an ordinary unprivileged user constructing an order with `inputs.length != output.assets.length` — no malicious relayer, prover, or governance actor is needed, and no length-equality check anywhere in `placeOrder` or `_fillSameChain` prevents it. This is a self-contained flaw reachable through the standard `placeOrder` → `fillOrder` public entrypoints.

### Recommendation
Enforce `order.inputs.length == order.output.assets.length` in `placeOrder` (revert `InvalidInput()` otherwise), or, if 1:many/many:1 mappings between inputs and outputs are an intended feature, decouple the escrow-release accounting from positional indexing entirely — iterate over all `order.inputs` explicitly and release/track each one independently rather than deriving `escrowedInputs` solely from `outputsLen`. Additionally, gate `_cancelSameChain` on `_filled[commitment] == 0` so a commitment already marked filled can never also be refunded.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenA: 100, TokenB: 50]` and `order.output.assets = [TokenC: 90]` (2 inputs, 1 output — no revert occurs since lengths are never compared).
2. Solver calls `fillOrder`, providing `TokenC: 90`. In `_fillSameChain`, `outputsLen = 1`, so the loop only processes `i = 0`: `order.inputs[0]` (TokenA) is released to the solver in full, `isFullyFilled` stays `true` (nothing ever set it `false`).
3. `_withdraw` is called with only `escrowedInputs[0]` (TokenA); `_orders[commitment][TokenB]` is untouched and TokenB's 50 units remain escrowed.
4. `OrderFilled` fires and `_filled[commitment] = solver` — the order is now recorded as fully settled.
5. The user (or anyone observing that `_cancelSameChain` never checks `_filled`) calls `cancelOrder` for the same commitment; `hasEscrow` is `true` because `_orders[commitment][TokenB] == 50`, so the refund path executes and returns TokenB to the user — an order simultaneously "filled" (solver got TokenA) and "cancelled" (user got TokenB back), an inconsistent double-disposition of one commitment's escrow that downstream indexers/integrations relying on `_filled` as a single source of truth would not expect.

Note: I was not able to fully trace every downstream consumer of `_filled` (e.g., cross-chain `RedeemEscrow`/`RefundEscrow` message handlers in `ExtrinsicIntents.sol`) within the available iterations to confirm whether any of them add an implicit `_filled`-gate on cancellation that would block step 5; this should be verified against `ExtrinsicIntents.sol` and the full `IntentGatewayV2.sol` fill/cancel entrypoints before treating the PoC as fully confirmed end-to-end.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
