### Title
Deterministic cached-preprocess reuse in the coordinator's DKG-confirmation MuSig signing lacks any single-use/cooldown guard, allowing nonce reuse and validator key-share recovery if `share` is invoked twice under one attempt context - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The external report's bug class is a missing cooldown/rate-limit: a privileged action (share increase + operator registration) can be repeated instantly within a block, giving defenders no window to react. The Serai analog is a missing *single-use* guard on a privileged cryptographic action: `SigningProtocol::preprocess_internal` deterministically regenerates the same FROST nonces from a DB-cached seed for a fixed `context`, and `share_internal` signs with them, with no mechanism preventing a second `sign` under the same context using a different message or preprocess set — which leaks the validator's private key share.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs:99-148`, `preprocess_internal` derives the signing nonces from `CachedPreprocesses::get(self.txn, &self.context)`, where `context` for the DKG confirmer is `(b"DkgConfirmer", self.attempt)` (line 275). The seed is created once per context and **never deleted or marked consumed**; every call to `preprocess_internal` or `share_internal` rebuilds `AlgorithmSignMachine::from_cache` with the same seed, producing identical nonces/commitments via `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`).

The module's own header (lines 25-54) states this is explicitly unsafe: nonce reuse occurs if `sign` is called again with distinct received preprocesses or a distinct message. Safety is asserted purely from BFT ordering plus two unimplemented TODOs (line 51: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)"; lines 53-54: a matching check for Processor preprocesses).

`share_internal` is invoked from two paths under the same attempt context:

- `generated_key_pair` (`coordinator/src/tributary/handle.rs:47-60`): calls `DkgConfirmer::share(preprocesses, key_pair)` where `msg = set_keys_message(set, removed, key_pair)` (line 296-301). `DkgKeyPair::set` and `KeyToDkgAttempt::set` overwrite unconditionally on every call, so a second invocation with a different `key_pair` or a different `removed` set (which changes via `removed_as_of_dkg_attempt` as removal votes land) produces a **different message** signed under the **same nonces**.
- `DkgConfirmer::complete` (lines 312-327) calls `share_internal` again, re-signing with the same cached nonces.

The signature share is `s = d + rho·e + λ·challenge·share` over the FROST binding; two shares over the same nonce with different challenges/preprocess sets yield the secret share by linear algebra — exactly the "parallel-session / ROS-style share reuse" and "CachedPreprocess determinism" failure mode the spec warns about (`spec/cryptography/FROST.md:51-62`: "Reusing preprocesses would enable a third-party to recover your private key share").

### Impact Explanation
Recovery of a validator's MuSig key share lets an attacker forge DKG-confirmation signatures (`set_keys` on Substrate), i.e., full compromise of the validator root-of-trust for that set — analogous to the EigenLayer report's "attacker instantly gains operator control." This is key-share recovery reachable purely through on-chain tributary data (participant-controlled DKG shares, blame transactions, and key-pair inputs an unprivileged validator influences), not a malicious-node assumption.

### Likelihood Explanation
The leak requires a second `share`/`complete` under the same `(b"DkgConfirmer", attempt)` context with a differing message or preprocess set. Two honest paths produce identical input (same share → no leak), but the code relies on unimplemented checks: nothing prevents `generated_key_pair` from being re-invoked after `DkgKeyPair`/`KeyToDkgAttempt` are overwritten with a distinct pair, or after `removed` changes mid-attempt (both alter `set_keys_message`'s `msg`). A validator submitting DKG shares/blame that alter the confirmed `key_pair` or the `removed` list between the two sign calls induces the differing message. This is reachable without breaking BFT — it only needs the documented TODO guards to be absent, which they are. Medium-to-high likelihood given the acknowledged incomplete hardening.

### Recommendation
- Enforce single-use at the source: after `share_internal` succeeds, delete or tombstone `CachedPreprocesses` for the context so `preprocess_internal` errors or derives fresh nonces on re-entry.
- Implement the noted TODOs: before publishing a share, verify the on-chain accumulated preprocesses/message match the values presumed when the nonce commitments were published (lines 51-54), and pin `key_pair`/`removed` into the nonce-derivation context so a changed message can never reuse the seed.
- Alternatively include the `msg` hash and preprocess-set hash in the `CachedPreprocesses` key so each distinct signing input deterministically maps to a distinct nonce.

### Proof of Concept
1. A validator participates in DKG attempt `k`; the coordinator publishes confirmation preprocess via `dkg_confirmation_nonces`, seeding `CachedPreprocesses[(b"DkgConfirmer", k)]`.
2. `generated_key_pair` is invoked with `key_pair_A` → `share_internal` signs `set_keys_message(set, removed_A, key_pair_A)` using nonces `N`.
3. Via a valid blame/removal transition or a second processor-emitted key pair, `generated_key_pair`/`complete` is invoked again with `key_pair_B` (or `removed_B`) → `share_internal` re-derives the identical nonces `N` from the unchanged cached seed and signs a different message.
4. The two published `DkgConfirmed` shares satisfy `s₁ - s₂ = λ·share·(c₁ - c₂)`; solving yields the validator's private key share, forging future `set_keys` confirmations.
