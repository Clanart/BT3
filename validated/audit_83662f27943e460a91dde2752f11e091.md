## Title
Missing HTML/JS-context escaping (`<`, `>`, `&`) of attacker-controlled string field values in non-Java ProtoJSON encoders — (File: `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, `upb/json/encode.c`, `php/src/Google/Protobuf/Internal/GPBJsonWire.php`, `python/google/protobuf/json_format.py`)

## Summary
The Apache Hop advisory (CVE-2024-24683) is a classic CWE-20 case: a server takes an attacker-influenced value (`id`) and emits it into an HTML response without context-appropriate output encoding, so it can break out of its intended context. The invariant that fails is "every value written into a context with special metacharacters must be escaped for that context before being trusted downstream." Protobuf has no HTTP server of its own, but its official ProtoJSON encoders serve exactly this trust boundary: an attacker-controlled `string` field (accepted verbatim by the wire/JSON parser, since proto3 `string` only requires valid UTF-8, not any charset restriction) is echoed into the serialized JSON output that calling applications commonly embed into HTML `<script>` blocks or otherwise process as text. Google's own Java implementation treats this as a real risk and hardens against it; several other official language bindings do not.

## Finding Description
`JsonFormat.java`'s printer explicitly escapes `<`, `>`, `&`, `=`, and `'` as `\u003c`/`\u003e`/etc. in addition to the RFC-mandated JSON escapes, with an explicit code comment stating this is done "to prevent XSS risks": [1](#0-0) 
This is validated by a dedicated regression test (`testHtmlEscape`, regression for b/73832901) proving `</script>` is escaped to `\u003c/script\u003e`: [2](#0-1) 

The C++ core `json/internal/writer.cc` implements a *partial* version of this same defense — it escapes `<` and `>` but not `&`, `=`, or `'`: [3](#0-2) 

However, the upb-based JSON encoder shared by the PHP extension, Ruby extension, and generic C/upb users (used transitively by many bindings) contains **no such logic at all** — `jsonenc_put_escaped_char` only implements the strict JSON-spec escapes (`\n \r \t \" \f \b \\` and control chars `<0x20`) and passes `<`, `>`, `&`, `=`, `'` straight through as raw bytes: [4](#0-3) [5](#0-4) [6](#0-5) 

The pure-PHP encoder (`GPBJsonWire.php`) delegates STRING encoding to `json_encode($value, JSON_UNESCAPED_UNICODE)` without the `JSON_HEX_TAG`/`JSON_HEX_AMP`/`JSON_HEX_APOS` flags, so `<`, `>`, `&`, `'` are likewise emitted unescaped: [7](#0-6) 

Python's `json_format.py` builds a plain dict and hands it to the stdlib `json.dumps`, which also only implements RFC-mandated escaping — no `<`/`>`/`&` hardening: [8](#0-7) [9](#0-8) 
(This test explicitly documents that `<` and `>` in `message.string_value` are emitted raw, only standard JSON control-character escapes are applied.)

**Failed invariant / attacker-controlled value / missing check:** A client-supplied `string` field value (fully attacker-controlled, valid UTF-8, no charset restriction enforced by the wire format) flows unmodified through `ParseFrom*`/`Parse` into the message, and then through `MessageToJson`/`JsonEncode`/`print()` into the serialized JSON text. Java's printer inserts a context-hardening check (`getReplacementOrNull` covering `<>&='`) before emitting the string; the upb-based (PHP/Ruby/C), pure-PHP, and Python encoders omit this check entirely.

## Impact Explanation
This is the same bug class as the CVE: a value under attacker control is written into output without escaping needed for the context in which that output is commonly consumed. Applications frequently embed `MessageToJson`/`upb_JsonEncode` output directly into HTML pages (e.g., inline `<script>var data = {{json}};</script>` bootstrapping, a widely-documented pattern that is precisely why Java's implementation and the C++ core both carry this defense). If a downstream PHP, Ruby, or Python application relies on ProtoJSON's built-in escaping instead of applying its own HTML-context encoding — reasonably assuming that the "same protobuf library" behaves consistently across languages — a proto `string` field containing `</script><script>alert(1)</script>` will be reflected unescaped, enabling stored/reflected XSS (CWE-20 → CWE-79-class outcome) in exactly the same "consuming-application exposure" pattern the CVE describes. Impact is confidentiality/integrity of the embedding page, matching CVSS `C:N/I:H` in the original advisory.

## Likelihood Explanation
Medium. Exploitation requires (1) an attacker able to control a proto `string` field's contents (a very common scenario — is the entire point of ProtoJSON as a client-facing serialization format), and (2) a consuming application embedding ProtoJSON output into HTML/JS without its own escaping — a pattern common enough that Google chose to bake mitigation directly into `JsonFormat.java`'s printer as defense-in-depth. The inconsistency across officially maintained bindings (protecting Java/C++ users but not PHP/Ruby/Python/C users) is the concrete, provable gap; it doesn't require any privileged access, malformed wire data, or resource exhaustion — only an ordinary supported JSON-serialization call with a crafted string value.

## Recommendation
Port the `<>&='`/HTML-context escaping logic from `JsonFormat.java`'s `printStringEscapedAndQuoted`/`getReplacementOrNull` (and complete the C++ `writer.cc` set to include `&`, `=`, `'`) into the shared upb JSON encoder (`upb/json/encode.c`, used by PHP/Ruby/C extensions), the pure-PHP `GPBJsonWire.php::jsonNiceEscape`, and Python's `json_format.py` (either post-processing the JSON string or supplying a custom `json.JSONEncoder`). This should be applied uniformly across all officially maintained language runtimes so consuming applications get a consistent security guarantee regardless of language binding, and should be explicitly documented as a defense-in-depth measure (not a substitute for context-aware output encoding by the embedding application).

## Proof of Concept
1. Define `message TestMessage { string value = 1; }` and set `value = "</script><script>alert(document.domain)</script>"`.
2. Java: `JsonFormat.printer().print(msg)` → outputs `"value": "\u003c/script\u003e\u003cscript\u003ealert(document.domain)\u003c/script\u003e"` (safe), confirmed by the analogous `testHtmlEscape` unit test.
3. Python: `json_format.MessageToJson(msg)` → outputs `"value": "</script><script>alert(document.domain)</script>"` verbatim (per `testJsonEscapeString`, only `\n \" \r \b \t \f \\` and non-ASCII are escaped — `<`/`>`/`&` pass through raw), confirming the missing check.
4. PHP (`protobuf_c` extension, upb-based) / Ruby: same message serialized via `upb_JsonEncode`/`jsonenc_stringbody` emits the raw `<`, `>` bytes untouched, since `jsonenc_put_escaped_char` has no case for them.
5. If either JSON payload is interpolated into an HTML page inside a `<script>` block (a documented use case that motivated Java's mitigation), the `</script>` sequence terminates the intended script element and the following `<script>alert(...)</script>` executes — reflected XSS, whereas the Java-serialized payload remains inert text.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
