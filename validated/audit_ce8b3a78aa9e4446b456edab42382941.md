### Title
`ThresholdKeys::read` accepts zero secret shares and identity verification shares, yielding an identity `group_key` for which signatures are trivially forgeable - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `secret_share` via `C::read_F` and each verification share via `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:618-623`). `read_F` only enforces canonicality, not non-zero, and `Ciphersuite::read_G` only enforces canonicality, not non-identity (`crypto/ciphersuite/src/lib.rs:74-101`). `ThresholdKeys::new` then computes `group_key` as a linear combination of the supplied verification shares with no identity or consistency check (`crypto/dkg/src/lib.rs:376-390`). A blob of all-identity verification shares is therefore accepted as "valid," exactly like the oracle report where a `0` price was treated as valid and poisoned the aggregate result — here the zero/identity values silently produce `group_key == identity`, and a Schnorr signature `(R = s·G, s)` verifies for *any* challenge against an identity public key (`crypto/schnorr/src/lib.rs:88-110`).

### Finding Description
- `ThresholdKeys::read` reads `t`, `n`, `i`, an `Interpolation` variant, one scalar `secret_share`, and `n` points for `verification_shares`, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:574-632`).
- `Ciphersuite::read_F` rejects only non-canonical scalars; `0` is accepted. `Ciphersuite::read_G` rejects only invalid/non-canonical encodings; the identity point is a valid canonical encoding and is accepted. The stricter `Curve::read_G`, which rejects identity (`crypto/frost/src/curve/mod.rs:125-131`), is not used here.
- `ThresholdKeys::new` checks only the *count* of verification shares and that participant indexes are `<= n` (`crypto/dkg/src/lib.rs:355-365`). It never checks that `verification_shares[i]` is non-identity, that `secret_share != 0`, or that `verification_shares[i] == G * share_i`.
- `group_key` is computed as `sum(verification_shares[i] * interpolation_factor(i))` over participants `1..=t` (`crypto/dkg/src/lib.rs:376-378`). With all verification shares set to the identity encoding (32 zero bytes on Ristretto/ed25519), `group_key` is identity.
- `SchnorrSignature::verify` checks `R + c·A − s·G == 0` (`crypto/schnorr/src/lib.rs:92-99`). For `A = identity`, this reduces to `R == s·G`, which any party satisfies by choosing arbitrary `s` and setting `R = s·G`. The same holds for FROST signature verification, which reduces to the same group equation under `view.group_key()`.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (listed in-scope as reachable untrusted input) causes the deserialization of a semantically invalid key set whose `group_key` is the identity element. Any signature verified against that group key — FROST aggregate signatures, Schnorr signatures — is forgeable by anyone with no knowledge of any secret: pick `s`, set `R = s·G`. Funds or protocol actions gated by this threshold key become spendable/authorizable by an arbitrary party, and blame/share verification inside `complete` cannot detect it because the failure is upstream at deserialization. The honest holder of the blob is also given `secret_share = 0` and identity shares, so the keys "work" (produce internally consistent shares) while being universally forgeable — worse than a detectable failure.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ThresholdKeys::read`. This is plausible wherever threshold keys are transported or restored from untrusted storage rather than produced locally by the DKG. The exploit needs no computation — just `n` identity encodings and a zero scalar — and produces a deterministic, permanent forgery capability rather than a probabilistic one. Severity is bounded by the fact that the attacker's blob replaces the victim's keys rather than compromising existing honestly-generated keys, hence High rather than Critical; the code itself acknowledges this class with the comment at `crypto/frost/src/sign.rs:492-494` ("deserialized a semantically invalid FrostKeys") without actually preventing it.

### Recommendation
In `ThresholdKeys::new` (or in `ThresholdKeys::read`), reject identity verification shares and a zero `secret_share`, and reject a computed `group_key` that `is_identity()`. Concretely, inside the loop at `crypto/dkg/src/lib.rs:361-365`, add `if bool::from(verification_shares[&participant].is_identity()) { Err(...) }`, and after computing `group_key` at `crypto/dkg/src/lib.rs:377-378`, add `if bool::from(group_key.is_identity()) { Err(...) }`. Optionally verify `verification_shares[params.i()] == C::generator() * secret_share` to catch inconsistent blobs.

### Proof of Concept
```rust
// For any C: Ciphersuite (e.g. Ristretto), construct a blob:
//   id_len || C::ID || t=1 || n=1 || i=1 || interpolation=1 (Lagrange)
//   || secret_share = 0 (canonical zero repr)
//   || verification_shares[1] = identity encoding (canonical)
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// keys.group_key() == C::G::identity()

// Forgery for any message/challenge c:
let s = C::F::random(rng);
let forged = SchnorrSignature::<C> { R: C::generator() * s, s };
// verify(group_key, c) computes R + c*identity - s*G == identity  -> true
assert!(forged.verify(keys.group_key(), arbitrary_challenge));
```
The read succeeds because neither `read_F` nor `read_G` nor `ThresholdKeys::new` rejects zero/identity values, mirroring the oracle's acceptance of `answer == 0` as a valid price.
