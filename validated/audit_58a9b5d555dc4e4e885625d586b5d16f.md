### Title
Scalar and offset state is silently dropped during generator promotion - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` rebuilds promoted `ThresholdKeys` from only the original secret share, discarding any scalar or offset accumulated on the source keys. For a key with effective secret `s * x + o`, promotion produces keys for `x` under the new generator rather than preserving `s * x + o`.

### Finding Description
`ThresholdKeys` supports composable multiplicative and additive key transformations through `scale` and `offset`, and defines the effective group key as `(group_key * scalar) + (generator * offset)`. [1](#0-0) [2](#0-1) 

`GeneratorPromotion::promote` generates the DLEq proof only over `original_secret_share` and binds the transcript to `original_group_key`, ignoring both current transformations. [3](#0-2)  `complete` then constructs the promoted key using `original_secret_share` again. [4](#0-3)  `ThresholdKeys::new` initializes the result with `scalar = ONE` and `offset = ZERO`, so the transition discards the effective balance-equivalent component of the key state. [5](#0-4) 

Externally supplied `GeneratorProof` messages can be decoded from public bytes and passed to `complete`, making this state transition reachable during the public promotion protocol. [6](#0-5) [7](#0-6) 

### Impact Explanation
If keys have been scaled or offset for account, privacy, parity, or Taproot-style tweaks, promotion changes the represented key from `G2 * (s * x + o)` to `G2 * x`. The promoted signing set therefore cannot authorize outputs addressed to the expected promoted-and-tweaked key, resulting in funds which appear controlled by the migrated key but are not spendable by the promoted shares. This is a Medium-severity loss-of-funds condition when scalar or offset use is expected to survive promotion.

### Likelihood Explanation
The condition requires promoting keys after applying `scale` or `offset`. Both transformations are public, documented `ThresholdKeys` features intended for account and privacy schemes, and `GeneratorPromotion` neither rejects non-default transformations nor warns that they will be discarded. [1](#0-0) 

### Recommendation
`GeneratorPromotion` should either reject `ThresholdKeys` whose `current_scalar` is not `ONE` or whose `current_offset` is not `ZERO`, or preserve the complete effective key state. To preserve it, construct the promoted `ThresholdKeys` and reapply `base.current_scalar()` and `base.current_offset()`, while binding the promotion transcript to the effective source group key and the carried parameters so all participants agree on the promoted key.

### Proof of Concept
```rust
// For a threshold secret x and transformed keys:
let base = raw_keys
  .scale(s)
  .unwrap()
  .offset(o);

// The source effective group key is:
//   G1 * (s * x + o)
assert_eq!(
  base.group_key(),
  (base.original_group_key() * s) + (C1::generator() * o),
);

let (promotion, _proof) =
  GeneratorPromotion::<C1, C2>::promote(&mut rng, base);
let promoted = promotion.complete(&other_participant_proofs).unwrap();

// Actual result after promotion:
//   G2 * x
assert_eq!(promoted.current_scalar(), F::ONE);
assert_eq!(promoted.current_offset(), F::ZERO);

// Expected result preserving the effective key:
//   G2 * (s * x + o)
assert_ne!(
  promoted.group_key(),
  C2::generator() * ((s * recovered_x) + o),
);
```

This follows because signing views apply `scalar` to every original share and add `offset` to the lowest participant, while promotion serializes none of that effective state into the new `ThresholdKeys`. [8](#0-7) [9](#0-8)
