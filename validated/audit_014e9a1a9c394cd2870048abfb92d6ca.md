### Title
Missing ownership/consistency check in `ReceivedOutput::read` lets untrusted bytes register foreign UTXOs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` couples a scalar `offset` (the key offset needed to spend) with a Bitcoin `TxOut`/`OutPoint`. Its constructor is private and is only correctly populated by `Scanner::scan_transaction`, which derives `offset` by matching `output.script_pubkey` against the registered `key + offset·G` scripts (`networks/bitcoin/src/wallet/mod.rs:199-214`). However, `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes all three fields from an untrusted byte stream and performs **no check that the claimed offset actually maps the scanner's key to the output's `script_pubkey`** — the exact analog of the AzuraCast bug: a fetch/read path (`/file/{id}/play`) that returns a resource while skipping the ownership check (`requireForStation`-equivalent) enforced by every sibling path.

### Finding Description
- `scan_transaction` is the "authorized" path: an output is only reported as received if `self.scripts.get(&output.script_pubkey)` returns an offset previously bound to `key + offset·G` via `register_offset` (`mod.rs:180-196`, `205-211`). Ownership (spendability) is proven by construction.
- `ReceivedOutput::read` (`mod.rs:122-134`) accepts `offset`, `TxOut`, and `OutPoint` verbatim from `read_F`/`consensus_decode`. Any caller that later uses `output.offset()` to build `ThresholdKeys::offset(offset)` and sign will produce a signature for `key + offset·G`, which is unrelated to the output's actual `script_pubkey` unless the attacker happened to match it.
- There is no `verify`/`belongs_to` helper on `ReceivedOutput`, so a deserialized object is indistinguishable from a scanner-produced one. An attacker who can feed `ReceivedOutput::read` bytes (e.g., through any channel carrying serialized scanner results to a co-signer/processor) can report arbitrary on-chain outputs — including outputs paying to *other people's* addresses, dust, or already-spent/nonexistent UTXOs — as funds received by the Serai key.

### Impact Explanation
Funds are reported received that are not spendable: downstream accounting (deposits credited, liquidity released, or signing orchestration attempted against `key + offset·G` for a script that doesn't correspond) can mint credit for outputs the threshold key cannot ever spend, or burn/do-work on unspendable inputs. Severity: Medium — bounded by whatever value the integrating system credits per reported output, with no key leakage.

### Likelihood Explanation
Requires an attacker-controlled serialization path into `ReceivedOutput::read` (i.e., the deserialized output isn't produced by the local `Scanner`). Where Serai components exchange scan results as bytes rather than re-scanning locally, the check is entirely absent, so any peer in that path can inject forged outputs at will.

### Recommendation
Make `ReceivedOutput` self-validating: either give `read` the scanning key (or expected `ScriptBuf` set) and reject objects where `p2tr_script_buf(key + G·offset) != output.script_pubkey`, or expose a `ReceivedOutput::verify(&self, key: &ProjectivePoint) -> bool` performing that check and require consumers of deserialized outputs to call it. Alternatively, transport only `(OutPoint, offset)` and re-derive the `TxOut`/`script_pubkey` binding locally.

### Proof of Concept
```rust
// Attacker crafts bytes where `offset` is arbitrary and `output` pays
// to an unrelated P2TR script_pubkey (someone else's address).
let mut buf = vec![];
buf.extend(Scalar::from(42u64).to_bytes());                    // bogus offset
buf.extend(bitcoin::consensus::encode::serialize(&TxOut {      // foreign output
    value: Amount::from_sat(100_000),
    script_pubkey: victim_script,                              // not key + 42·G
}));
buf.extend(bitcoin::consensus::encode::serialize(&real_outpoint));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted
// forged.offset() -> 42; signing with keys.offset(42) cannot spend victim_script,
// yet the object is indistinguishable from a legitimate scan result.
```

Uncertainty note: I could not fully trace every consumer of `ReceivedOutput::read` in this snapshot; the vulnerability is conditional on at least one in-scope path deserializing attacker-influenced bytes and crediting the enclosed output without re-scanning against the local `Scanner`.
