### Title
Blame proof reveals ECDH key before PoP verification, leaking honest participants' secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` emits an `EncryptionKeyProof` (the ECDH shared point plus a DLEq proof) as soon as a decrypted share fails scalar deserialization, returning early *before* the queued batch verification of the message's Schnorr proof-of-possession ever runs. A malicious participant can copy the per-message `key` field from another participant's encrypted share message into their own message to the same victim, and the victim's resulting blame proof will reveal the ECDH shared key that also decrypts the copied-from (honest) message — leaking an honest participant's secret share.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` decrypts each incoming `EncryptedMessage` via `Encryption::decrypt`, which (a) queues the message's PoP signature into a `BatchVerifier` under `BatchId::Decryption(l)` and (b) immediately computes `ecdh(enc_key_self, msg.key)` and returns an `EncryptionKeyProof { key, dleq }` proving correctness of that shared point (`crypto/dkg/pedpop/src/encryption.rs` lines 479–500). Back in `calculate_share` (lines 479–482), if `C::F::from_repr(share_bytes.0)` fails, the function early-returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` — the `?` bypasses `batch.verify_with_vartime_blame()` at line 493, so the PoP is never checked on this path.

The comments in `encryption.rs` (lines 84–90) explicitly describe this attack class: an adversary reusing another party's per-message key would cause the victim's blame proof to reveal `bX`, thereby revealing the co-opted party's encrypted message. The per-message Schnorr PoP (`pop_challenge`, binding `key`, `sender`, and `msg`) exists solely to stop this — but it is only enforced inside the batch, which the deserialization-failure path skips.

Since `ecdh::<C>(&self.enc_key, msg.key)` depends only on the victim's encryption key and the attacker-controlled `msg.key` point — not on `from` — copying an honest sender's `key` field makes the victim compute the *same* shared point used for the honest ciphertext. The blame proof's DLEq (`verify` in `decrypt_with_proof`, encryption.rs lines 381–393) confirms `key = enc_key_victim * msg.key`, so anyone can derive the ChaCha20 cipher (`cipher()`, encryption.rs lines 101–133) and decrypt the honest message.

### Impact Explanation
Recovery of an honest participant's FROST/PedPoP secret share for a victim. `SecretShare` is the per-recipient evaluation of the sender's polynomial (`generate_secret_shares`, lib.rs lines 366–369); combined with the public `Commitments`, leaked shares directly contribute to threshold key-share recovery. In the Serai processor, `InvalidShare` blame is serialized and published via `ProcessorMessage::InvalidShare` / `VerifyBlame` (`processor/src/key_gen.rs` lines 419–425, 504–563), so the revealing `EncryptionKeyProof` is distributed to all observers — making the honest share publicly decryptable via `AdditionalBlameMachine`/the public transcript construction. This is a confidentiality break of DKG secret material, matching the report's sensitive-information-exposure class (CWE-200/CWE-522).

### Likelihood Explanation
Requires a malicious DKG participant who observes the honest sender's `EncryptedMessage.key` (transmitted over the authenticated channel, visible to all participants) and sends their own `EncryptedMessage` to the same victim with that copied `key`, a garbage `pop`, and a `msg` payload that decrypts to a non-canonical scalar. Under an unknown keystream a random 32-byte payload is canonical for Ristretto with probability ≈ 2^252/2^256 = 1/16, so the attacker retries across DKG attempts (or precomputes against a keystream they legitimately know by reusing their own key for a dry run in a prior session — ECDH depends only on the two points). No collusion, no broken BFT, and no leaked keys are needed — just an unprivileged participant feeding crafted bytes to `calculate_share`.

### Recommendation
Verify the PoP for a message *before* releasing its `EncryptionKeyProof`. Concretely, in `calculate_share`, defer attaching `blame` until after `batch.verify_with_vartime_blame()` succeeds, or synchronously call `msg.pop.verify(...)` inside `Encryption::decrypt` and withhold/return `None` for the proof when the PoP is invalid — mirroring the existing `BatchId::Decryption(l) => (l, None)` handling so that a failed PoP never yields a revealing proof.

### Proof of Concept
1. Victim Bob (`enc_key_b`) and honest Alice run PedPoP. Alice's message to Bob is `EncA = { key: aG, pop: σ_a, msg: Enc(K_a, share_A→B) }` where `K_a = ChaCha20(H(b·aG))`.
2. Malicious Eve, a participant, observes `EncA` on the authenticated channel. Eve sends Bob `EncE = { key: aG (copied), pop: arbitrary bytes, msg: random 32 bytes }`.
3. Bob's `calculate_share` calls `decrypt`: it queues Eve's (invalid) PoP into the batch, computes `ecdh(b, aG) = abG`, decrypts `msg` to garbage, and returns `EncryptionKeyProof{ key: abG, dleq }`.
4. With probability ~15/16 the garbage fails `C::F::from_repr`; `calculate_share` returns `InvalidShare { participant: Eve, blame: Some(proof) }` at lib.rs:481 — **without ever running** `batch.verify_with_vartime_blame()`, so Eve's forged PoP is never detected.
5. The blame proof propagates (processor serializes it into `ProcessorMessage::InvalidShare`/`VerifyBlame`). Anyone — including Eve — takes `proof.key = abG`, feeds it through the public `cipher()` transcript (`"DKG Encryption v0.2"`, static IV `"DKG IV v0.2\0"`), and xors the keystream against `EncA.msg` to recover Alice's plaintext secret share to Bob.
