## Finding: Excess native-token payment permanently stuck in `EvmHost` on POST/GET dispatch and `fundRequest`

### Title
Unrefunded excess `msg.value` from Uniswap swap is retained by `EvmHost` instead of returned to caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment and forward the entire `msg.value` to Uniswap's `swapETHForExactTokens`, requesting only the exact fee amount (`post.fee` / `get.fee` / `amount`) in output tokens. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swapETHForExactTokens` only consumes the ETH needed to obtain the exact requested output amount and refunds the unused ETH — but that refund is sent to `msg.sender` from the router's perspective, which is `EvmHost` itself, since `EvmHost` is the direct caller of the Uniswap router (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`). The original transaction sender (the EOA or app contract that called `dispatch`/`fundRequest`) never receives this refund. There is no code in `EvmHost.sol` that captures the ETH balance before/after the swap and forwards the difference back to `_msgSender()`.

This is the direct analog of the `AssetController._relayTransfer` bug in the external report: a function accepts `msg.value` intended to cover a specific fee amount, forwards only the necessary portion downstream, and never verifies or refunds the remainder — leaving excess ETH permanently trapped in the contract.

Notably, the codebase is clearly aware of this exact bug class and fixes it at the application layer: `IntentGatewayV2`/`IntentsBase.sol` explicitly refund excess native-token overpayment to the original payer after fee swaps (see `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`), but `EvmHost` — the core dispatcher used by every app including those exact intent gateways when they forward `msg.value` directly to `IDispatcher(host()).dispatch{value: msg.value}(request)` — has no equivalent protection. [4](#0-3) [5](#0-4) 

### Impact Explanation
Any caller (EOA or app contract) who dispatches a POST/GET request or funds an existing request with slightly more native token than exactly needed for the Uniswap swap (which is the normal/expected pattern, since callers cannot predict the exact swap price at submission time and must overpay for slippage protection) will have the unused ETH permanently retained by `EvmHost` with no recovery mechanism for the payer. This is a direct, unconditional loss of user funds triggered purely by normal usage of a public entrypoint — matching the bounty's "loss of funds" impact class.

### Likelihood Explanation
High. `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` are the primary, unprivileged, public entrypoints used by every app built on Hyperbridge (`HyperFungibleToken`, `IntentGatewayV2`, `ExtrinsicIntents`, etc.) whenever native-token fee payment is chosen. Since Uniswap swap output requires an exact fee amount but callers must send `msg.value` conservatively higher to account for price movement, excess ETH loss occurs in essentially every native-payment dispatch, not just an edge case.

### Recommendation
Capture `address(this).balance` before and after the `swapETHForExactTokens` call (or use the router's returned `amounts[0]`) inside `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and forward any leftover ETH back to `_msgSender()` via a low-level call, mirroring the refund pattern already implemented in `IntentGatewayV2`/`IntentsBase.sol`.

### Proof of Concept
1. Caller estimates `post.fee` (fee token amount) needed for a `DispatchPost` and, to account for price slippage, sends `msg.value = 2x` the expected ETH cost.
2. `EvmHost.dispatch` executes:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [6](#0-5) 
3. Uniswap consumes only the ETH needed for `post.fee` tokens and refunds the remainder to `msg.sender` of the swap call — which is `EvmHost`, not the original caller.
4. The excess ETH becomes part of `EvmHost`'s balance permanently; the original caller has no function to reclaim it, and repeating this across many dispatches accumulates unrecoverable value inside the Host contract.

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
