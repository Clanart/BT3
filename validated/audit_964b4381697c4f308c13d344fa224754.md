## Finding

<title>NFT Royalty Dilution via Equal Per-Count Split Instead of Value-Proportional Split in Offer Construction - (File: chia/wallet/nft_wallet/nft_wallet.py)</title>

### Summary
The wallet's NFT-offer royalty logic (`NFTWallet.make_nft1_offer` and `compute_royalty_amount`) computes the "trade price" attributed to each royalty-enabled NFT in a bundled offer by dividing the total fungible amount **evenly by the count** of royalty NFTs involved, rather than by each NFT's actual value share. This mirrors the Kairos bug class: a shared pool of value is split equally per "position" (here, per bundled NFT) instead of proportionally, letting a party who controls extra cheap/self-created positions dilute the fair share owed to another party (here, a legitimate NFT creator's royalty).

### Finding Description
`compute_royalty_amount()` computes royalty as:
```python
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
``` [1](#0-0) 

In `make_nft1_offer`, `offer_side_royalty_split`/`request_side_royalty_split` are simple **counts** of royalty-enabled NFTs bundled into one offer (not weighted by value), and the "trade price" used as the royalty basis for each NFT offered together is:
```python
trade_prices.append((uint64(amount // offer_side_royalty_split), settlement_ph))
``` [2](#0-1) 

This `trade_price` is fed as `trade_prices_list` into the NFT's spend, which becomes the on-chain royalty basis enforced by `NFT_TRANSFER_PROGRAM_DEFAULT` (percentage × trade_price paid to the immutable `royalty_address` baked in at mint time): [3](#0-2) [4](#0-3) 

Because the split is purely a headcount of bundled NFTs and the on-chain puzzle only checks that the declared `trade_price` matches an announcement from the fungible-asset offer coin (it cannot verify that the split reflects true relative value), an offer creator can pad a bundle containing a legitimate, valuable, royalty-bearing NFT (owned by a third party or acquired elsewhere) together with additional self-minted, low/negligible-royalty "filler" NFTs for the same aggregate price. This inflates the divisor and reduces the `trade_price` (and thus the royalty) attributed to the legitimate NFT, even though the full requested/offered amount is still collected in the trade. The reduction directly shortchanges the immutable royalty address baked into the legitimate NFT's mint-time transfer program — an economic actor with no ability to consent to or prevent this dilution, since royalty enforcement is purely a percentage of a self-declared, unverified per-NFT "trade price."

This is analogous to the Kairos `sendInterests` bug: a shared value pool (`interests` / here, the aggregate offered/requested amount) is divided **equally by count of positions** (`loan.nbOfPositions` / here, `offer_side_royalty_split`/`request_side_royalty_split`) rather than proportionally to actual contribution/value, and the party constructing the transaction (the borrower / here, the offer maker) controls how many extra "positions" (dummy offers / here, dummy self-minted NFTs) are injected, thereby diverting the honest party's fair share to themselves.

### Impact Explanation
A malicious offer creator can systematically underpay NFT creator royalties by bundling filler NFTs into any multi-NFT offer, redirecting value that should flow to a legitimate royalty address back to themselves (as the un-royaltied portion of the settlement remains with the trading parties instead of the creator). This is a form of offer-settlement value diversion reachable by any wallet user constructing an offer, with no cooperation needed from the victim (the original NFT creator, who is not even a party to the trade).

### Likelihood Explanation
Any wallet user can construct an offer bundling multiple NFTs (mixing a targeted valuable NFT with self-minted low-royalty NFTs) using the standard `create_offer_for_ids` / `make_nft1_offer` flow — no special privileges, mempool timing, or multi-party collusion are required beyond normal NFT minting and offer creation, both of which are ordinary unprivileged wallet actions.

### Recommendation
Compute each bundled NFT's royalty basis proportionally to its actual value contribution to the trade (e.g., require/derive a per-NFT price that is independently verifiable rather than an even split by count), or restrict `make_nft1_offer` to a single royalty-enabled NFT per fungible-asset trade unless a verifiable per-NFT price breakdown is supplied and enforced on-chain.

### Proof of Concept
1. Attacker (as an offer maker/seller) owns/acquires one legitimate royalty-enabled NFT `N_legit` (royalty 10%, creator address `C`) alongside a self-minted throwaway royalty-enabled NFT `N_dummy` (royalty 0% or negligible, address controlled by attacker).
2. Attacker calls `create_offer_for_ids` offering `{N_legit: -1, N_dummy: -1, CAT_asset: 1000}` (requesting 1000 CAT for both NFTs as one bundle).
3. Inside `make_nft1_offer`, `offer_side_royalty_split = 2` (count of offered royalty NFTs), so `trade_prices = [(1000 // 2, settlement_ph)] = [(500, ...)]` is used for both NFTs' transfer-program solutions.
4. `N_legit`'s royalty is computed and enforced on-chain as `500 * 10% = 50` CAT to creator `C`, instead of the `1000 * 10% = 100` CAT that would be owed if `N_legit` were sold alone for the same aggregate price.
5. Creator `C` receives half the royalty they are otherwise entitled to, while attacker still collects the full 1000 CAT (minus the reduced royalty), demonstrating value diversion enabled purely by the count-based split in `compute_royalty_amount`/`make_nft1_offer`.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
