### Title
Missing-participant panic in `GeneratorPromotion::complete` allows a faulty participant to crash the node instead of being cleanly rejected - (File: crypto/dkg/promote/src/lib.rs)

### Summary
CVE-2016-0667 is an availability-only flaw: a local party abuses a code path (locking) to crash/stall MySQL. The analog in Serai is a reachable `unwrap()` panic on untrusted protocol input inside `crypto/dkg/promote`: `GeneratorPromotion::complete` validates only the *count* and *range* of submitted `GeneratorProof`s, then indexes the map with `.unwrap()` for every expected participant. A participant set that passes both checks but omits a required index (e.g. includes the receiver's own `params.i()` as a filler key) causes an out-of-bounds `HashMap` lookup panic, turning a well-formed-length, well-formed-range message into a node crash — the same "ordinary input → availability loss" shape as the MySQL locking bug.

### Finding Description
`GeneratorPromotion::complete` enforces two checks on the `proofs: &HashMap<Participant, GeneratorProof<C1>>` argument:

1. `proofs.len() == params.n() - 1` (crypto/dkg/promote/src/lib.rs:125-131)
2. every key `i` satisfies `u16::from(i) <= params.n()` (lib.rs:132-136)

It then iterates `i in 1 ..= params.n()`, skipping `params.i()`, and calls `proofs.get(&i).unwrap()` (lib.rs:140-156).

Nothing checks that `proofs` does *not* contain `params.i()` itself, nor that the map's key set equals `1..=n \ {params.i()}`. A map like `{params.i(), 1, 2, ..., n-2}` (with participant `n-1`'s proof omitted, assuming `i == n-1` for illustration — generally `{i} ∪ (1..=n \ {i, j})` for any `j != i`) has exactly `n - 1` entries and all keys `<= n`, so it passes both checks. When the loop reaches the omitted `j`, `proofs.get(&j).unwrap()` panics.

The poisoned proof can be built with `GeneratorProof::read`/`serialize` (each entry is a well-formed `share` point plus a `DLEqProof`), so the crash is triggered by semantically malformed-but-syntactically-valid protocol data submitted over the ordinary promotion flow, not by corrupt bytes.

Note that `promote`/`complete` are intended for the n-of-n MuSig-style sets (e.g. `musig()` produces `t == n` keys in crypto/dkg/musig/src/lib.rs:128-137), which is exactly where promotion is invoked, so the `proofs.get(&i)` loop is exercised on the real path.

### Impact Explanation
Availability: a single faulty or malicious participant in a generator-promotion round causes an unconditional panic in every honest participant that runs `complete` with the adversary's map interleaved in place of the omitted entry (or, in a relayed-message model, whoever assembles the map). In the Serai validator context this aborts the key-rotation/promotion step and, depending on runtime panic handling, kills the processor task — matching the "local party degrades availability via an internal code path" profile of CVE-2016-0667. No secret material is exposed; severity is therefore Medium rather than High.

### Likelihood Explanation
Triggering requires the attacker to be a participant in the promotion session (or to control the messages routed into `complete`), and the omitted index `j` must not equal the victim's `params.i()`. The check bypass is trivial — include the victim's own index as a key with any syntactically valid `GeneratorProof` — and no cryptographic validity of the proof for `params.i()` is needed because that entry is never verified. Exploitation is deterministic once the message reaches `complete`.

### Recommendation
In `GeneratorPromotion::complete` (crypto/dkg/promote/src/lib.rs), replace the implicit set-membership assumption with explicit validation:

- Reject any `proofs` key equal to `params.i()`: `if i == params.i() { Err(PromotionError::InvalidParticipant { .. })? }` (a new variant or `IncorrectAmountOfParticipants`).
- In the `1 ..= params.n()` loop, replace `proofs.get(&i).unwrap()` with `.get(&i).ok_or(PromotionError::MissingParticipant(i))?` (adding a `MissingParticipant` variant), or use `dkg`-style `validate_map` logic.

The same pattern (`insert(params.i())` then iterate all others) means any future caller populating `proofs` from authenticated-but-untrusted messages must never index without checking presence.

### Proof of Concept
Setup: `n = 3` participants, victim `params.i() = 2`, `C1 = Ristretto`, `C2 = AltGenerator<Ristretto>`.

1. Victim runs `GeneratorPromotion::promote(rng, victim_keys)`, obtains `promotion` + its own proof.
2. Attacker (participant 1) delivers `proofs` map = `{Participant(1): valid_proof_1, Participant(2): any_parseable_GeneratorProof}` — omitting participant 3 and including the victim's own index.
   - `proofs.len() == 2 == n - 1` passes the count check.
   - `Participant(2) <= n` passes the range check.
3. Loop: `i = 1` verifies proof 1; `i = 2` skipped; `i = 3` executes `proofs.get(&Participant(3)).unwrap()` → `None.unwrap()` panic.

The forged filler proof needs no valid DLEq — `GeneratorProof::read` (`share: C::read_G` + `DLEqProof::read`) succeeds on any canonical encodings, since participant 2's own entry is never fed to `proof.verify()`. Honest execution instead requires a `PromotionError`, never a panic.

Relevant code: crypto/dkg/promote/src/lib.rs:120-166 (`complete`), with the unchecked lookup at line 146 (`let proof = proofs.get(&i).unwrap();`) and the insufficient checks at lines 125-136.
