## Analysis

Audiobookshelf's CVE-2023-51697 is a blind SSRF where a user-supplied URL (a podcast feed URL) is fetched server-side without validating the target host, letting an attacker make the server issue arbitrary outbound requests. Chia's DataLayer module has a directly analogous pattern: mirror URLs are attacker-controlled data published on-chain, and the local DataLayer service fetches them via `aiohttp` with no host/scheme restriction.

### Title
Blind SSRF via unvalidated DataLayer mirror URLs in `download_data.py`/`data_layer.py`

### Summary
Any wallet user can publish an arbitrary URL as a DataLayer "mirror" for any store id by spending a coin through `DataLayerWallet.create_new_mirror()`, which places the attacker-chosen URL bytes into on-chain memos with no validation of scheme or destination. [1](#0-0)  Any other node that subscribes to that store id will read these mirror URLs via `dl_get_mirrors`/`update_subscriptions_from_wallet` and store them unvalidated, [2](#0-1)  then periodically issue outbound HTTP requests to them via `http_download()`, which builds the request straight from `server_info.url` with no restriction against loopback, link-local, or private-network addresses. [3](#0-2) 

### Finding Description
1. `DLNewMirror`/`create_new_mirror` lets a wallet owner attach an arbitrary list of URL strings to a mirror coin, which is then broadcast on-chain via a standard spend. [1](#0-0)  `chia/wallet/wallet_request_types.py`'s `DLNewMirror` request type does not constrain the `urls` field. [4](#0-3) 
2. Any node's `DataLayer.update_subscriptions_from_wallet()` reads these mirror URLs from the wallet (`dl_get_mirrors`) and inserts them into its subscription table without validating scheme or host, only trimming a trailing slash. [2](#0-1) 
3. During the periodic `fetch_and_validate()` sync loop, one of these stored mirror URLs is chosen and passed to `insert_from_delta_file()`/`download_file()`, which (absent a configured downloader plugin) calls `http_download()`. [5](#0-4) 
4. `http_download()` performs `session.get(server_info.url + "/" + filename, ...)` directly, with no allow-list/deny-list for IP ranges (loopback, RFC1918, link-local/cloud-metadata addresses) or URL schemes. [3](#0-2) 
5. The project's own internal documentation explicitly flags mirror URLs as untrusted, but frames the concern purely around data integrity ("Downloaded data must continue to be verified against wallet-advertised roots"), not network-destination validation — confirming the SSRF surface was not addressed. [6](#0-5) 

Because mirror data is public on-chain data (readable/writable by any wallet with funds for the mirror coin), an attacker does not need any special privilege on the victim's node — they only need any full node with DataLayer enabled to be a subscriber of the malicious store id (subscriptions can even be attacker-suggested since DataLayer store ids/URLs are commonly shared to attract subscribers).

### Impact Explanation
This is a blind SSRF: it lets a remote unprivileged attacker force any DataLayer-enabled node that subscribes to their store to send outbound HTTP GET requests to attacker-chosen destinations, including internal-network addresses, cloud instance-metadata endpoints, or other local services on the victim host (e.g. other RPC ports bound to `127.0.0.1`). While the response body is fed through content-length/size checks and eventually into `insert_into_data_store_from_file()` validation (so it can't fully forge chain state), the request itself — headers, timing, and repeated firing on every sync cycle — is a classic SSRF primitive that can be used for internal network reconnaissance/pivoting or to abuse any GET-triggered side effects on internal endpoints.

### Likelihood Explanation
Likelihood is Medium: DataLayer is a specialized module (not the default sync path for standard wallet/mempool operations), so it is not reachable by every wallet user by default, but it is reachable by any user who runs DataLayer and subscribes to an attacker-created store id, which requires no permission beyond normal on-chain coin creation. The sync loop retries periodically (`manage_data_interval`), giving attackers a steady SSRF trigger without further interaction.

### Recommendation
Validate mirror/server URLs before storing/using them in `update_subscriptions_from_wallet()`/`subscribe()` and again in `http_download()`/`get_downloader()`: enforce an allow-listed scheme (e.g. `https`), resolve and reject loopback/private/link-local/multicast/metadata IP ranges (with re-validation after DNS resolution to prevent DNS rebinding), and consider requiring an explicit operator opt-in/allow-list for mirror hosts rather than trusting arbitrary on-chain-advertised URLs.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror`/`create_new_mirror` with `urls=["http://169.254.169.254/latest/meta-data/"]` (or `http://127.0.0.1:<victim-internal-port>/...`). [7](#0-6) 
2. Victim node operator (or automatic peer discovery) subscribes to attacker's store id via `subscribe()`. [8](#0-7) 
3. Victim's periodic `periodically_manage_data()` loop calls `update_subscription()` → `update_subscriptions_from_wallet()`, pulling the attacker's URL into the subscription table unmodified. [2](#0-1) 
4. `fetch_and_validate()` selects the malicious server info and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, causing the victim node to issue an outbound `GET` request to the attacker-chosen internal/metadata address. [3](#0-2)

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
