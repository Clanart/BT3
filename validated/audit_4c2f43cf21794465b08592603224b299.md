### Title
Remote-code-execution via unvalidated "Open in Desktop" deep-link URL passed to `git clone` (missing transport-protocol allowlist) - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/git/clone.ts`)

### Summary
The external report's broken invariant is: *an externally-supplied parameter that controls a sensitive operation is never range/format-checked before being used, allowing a malicious value to break the intended invariant.* In GitHub Desktop, the analogous unvalidated external parameter is the repository **URL** embedded in a custom-protocol ("Open in Desktop") deep link. `parseAppURL` extracts this URL from the link path without validating its scheme, and the resulting string is later passed straight to `git clone`. Because Desktop never restricts the set of git transport helpers (no `GIT_ALLOW_PROTOCOL`/`protocol.allow` hardening anywhere in `app/src/lib/git/environment.ts`), a URL using git's `ext::` (or `fd::`) remote-helper syntax will cause `git` to execute an arbitrary shell command supplied by the attacker the moment Desktop attempts to clone it — i.e., simply clicking a crafted link executes attacker code on the victim's machine.

### Finding Description
`parseAppURL` in `app/src/lib/parse-app-url.ts` handles the `openrepo` deep-link action. It validates the `pr` and `branch` query parameters with regexes, but the repository `url` itself (the deep-link path) is passed through completely unvalidated: [1](#0-0) 

This `url` flows to the dispatcher's clone-or-open logic (`openOrCloneRepository`) and — when the repository is not already present locally — down into `CloningRepositoriesStore.clone` → `clone()` in `app/src/lib/git/clone.ts`, which builds the git command line directly from the caller-supplied `url` and executes it: [2](#0-1) 

The only environment hardening applied before invoking git is `envForRemoteOperation`, which merely sets authentication headers and an HTTP(S) proxy — it does **not** set `GIT_ALLOW_PROTOCOL` or `protocol.ext.allow`/`protocol.allow` to restrict which transport helpers git may use: [3](#0-2) 

Git natively supports the `ext::<command>` remote helper, which runs `<command>` via the shell to establish the "transport" — this is a well-known technique for achieving command execution through a crafted git URL when the invoking application does not explicitly disable it (upstream git added `protocol.ext.allow=user` as the default specifically to mitigate this, but that default can be, and here is not verified to be, honored/enforced by the embedded git binary configuration Desktop ships). Because Desktop performs no scheme allowlisting of its own anywhere between `parseAppURL` and the `git clone` invocation, an `ext::` (or `fd::`) URL supplied via the deep link reaches the `git` process verbatim.

### Impact Explanation
If the transport-helper is not blocked at the git-config layer Desktop bundles/ships, a single click on an attacker-crafted `x-github-client://openrepo/...` link (or a "Clone repository" URL typed/pasted from an attacker-controlled webpage) results in arbitrary command execution in the context of the desktop user — satisfying the "attacker controls a link/deep link the user clicks... result is code execution" criterion. This is strictly more severe than the DoS scenario described in the seed report, but the causal pattern is identical: a value that reaches a sensitive sink (`git clone`) is never validated against an allowed set of protocols/formats.

### Likelihood Explanation
Likelihood depends entirely on whether the embedded git binary/config that Desktop ships defaults to blocking `ext::`/`fd::` (`protocol.ext.allow != user`) or whether Desktop explicitly sets this. No such configuration was found anywhere in `app/src/lib/git/environment.ts` or in the `clone`, `fetch`, `push`, `pull`, `checkout`, `revert`, `submodule`, `tag`, or `branch` git wrappers (`grep` for `GIT_ALLOW_PROTOCOL`/`protocol.allow` across the repo returned no matches). Because I could not fully trace `openOrCloneRepository` in `app/src/ui/dispatcher/dispatcher.ts` (ran out of tool iterations) to confirm there is no separate scheme allowlist check inserted specifically for the deep-link clone path, this should be treated as a **strong candidate requiring confirmation** rather than a fully proven exploit chain — the missing piece to verify is (a) the exact git version/config Desktop bundles for `protocol.ext.allow`, and (b) whether `openOrCloneRepository` performs any scheme filtering before calling `clone()`.

### Recommendation
- Explicitly set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or equivalent `-c protocol.ext.allow=never -c protocol.fd.allow=never`) in the environment/args built for every git invocation that takes an externally-influenced URL (`clone.ts`, `remote.ts`'s `setRemoteURL`/`addRemote`, `fetch.ts`, `push.ts`, `pull.ts`).
- In `parse-app-url.ts`, validate that the `openrepo` `url` parses as `http:`/`https:`/`ssh:` before returning an `IOpenRepositoryFromURLAction`, mirroring the checks already applied to `pr`/`branch`.
- Add regression tests analogous to `enterprise-validate-url-test.ts` that assert deep-link and clone-dialog URLs using `ext::`, `fd::`, or other non-network schemes are rejected.

### Proof of Concept
1. Host a page containing: `<a href="x-github-client://openrepo/ext::sh%20-c%20touch%20/tmp/pwned">Open in Desktop</a>`.
2. Victim with GitHub Desktop installed clicks the link.
3. `parseAppURL` extracts `parsedPath = "ext::sh -c touch /tmp/pwned"` as the `url` field of the `open-repository-from-url` action with no scheme check [4](#0-3) .
4. Desktop determines the repository isn't local and calls `clone(url, path, options)`, which shells out to `git ... clone --recursive -- ext::sh -c touch /tmp/pwned <path>` with no `GIT_ALLOW_PROTOCOL` restriction [5](#0-4) .
5. If the embedded git does not block the `ext` helper, `/tmp/pwned` is created — demonstrating arbitrary command execution triggered purely by clicking a link.

(This PoC's success is contingent on the bundled git's default `protocol.ext.allow` value, which could not be verified within the available tool budget — this is flagged above as the key remaining uncertainty.)

```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
```
