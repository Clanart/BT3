## Analysis

The Sherlock report's core issue is that a **non-standard ERC20 transfer path silently breaks the transfer/settlement invariant** because the code doesn't correctly validate the token's return semantics. Hyperbridge's `evm/tron/contracts/apps/IntentGatewayV2.sol` has a local analog with the **opposite but equally damaging** manifestation: instead of a strict revert-on-noncompliant-return (DoS), the escrow settlement path silently *accepts* a `transfer()` call that returns `false` as a successful payout.

### Title
Escrow settlement (`withdraw`) treats ERC20 `transfer()` returning `false` as success, permanently finalizing orders without paying the beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron variant) correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom` when pulling tokens into escrow, but the payout path (`withdraw`) and the `SweepDust` handler in `onAccept` bypass `SafeERC20` entirely. They instead perform a raw low-level `.call` and only check that the call itself did not revert, discarding the ABI-decoded boolean return value: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
```

The contract declares `using SafeERC20 for IERC20;` [2](#0-1)  and uses it consistently for pulling funds into escrow (`safeTransferFrom` in `placeOrder`), [3](#0-2)  but for *paying out* escrow via `withdraw()` and via the `SweepDust` branch of `onAccept`, it reverts to a raw `.call` that only inspects the outer call success, not the returned boolean payload: [4](#0-3) [5](#0-4) 

### Finding Description
ERC20 tokens are permitted by the standard to signal failure either by reverting **or by returning `false`**. Many real, non-malicious tokens use the latter pattern (e.g., failed transfers due to blacklists, pausing, or insufficient allowance handling implemented via a boolean return instead of a revert). `token.call(...)` only returns `success = false` when the callee reverts; if the callee token returns `false` while still completing execution normally, the low-level call itself succeeds (`success == true`), and the ABI-encoded `false` return payload is silently discarded because the code writes `(bool success,) = token.call(...)`.

As a direct result:
- `withdraw()` unconditionally treats the call as a successful payout, decrementing `_orders[commitment][token]` and setting `_filled[commitment] = beneficiary`, [6](#0-5)  even though the beneficiary received zero tokens.
- The corresponding `EscrowReleased`/`EscrowRefunded` event fires, publicly attesting that settlement succeeded. [7](#0-6) 
- The escrowed tokens remain physically locked in the `IntentGatewayV2` contract with the accounting (`_orders[commitment][token]`) already zeroed out, so there is no code path left to reclaim them for the intended beneficiary — the order is marked filled/refunded (`_filled[commitment]` is non-zero) which blocks any retry via `cancelOrder`/`fillOrder`, since those check `if (_filled[commitment] != address(0)) revert Filled();`.

The same discarded-return-value pattern also appears in the `SweepDust` admin-initiated payout in `onAccept`. [8](#0-7) 

The `withdraw()` path is reached both from `onGetResponse` (cross-chain cancellation confirmation) and from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages, which are the core settlement primitives paying solvers for filled orders and refunding users for cancelled orders. [9](#0-8)  The escrowed token itself (`order.inputs[i].token`) is fully attacker-controlled at order-placement time (decoded directly from the user-supplied `bytes32`), with no allowlist visible in `placeOrder`. [10](#0-9)  This means an order creator can deliberately select an escrow token whose `transfer()` returns `false` under conditions they control (e.g., a token they can pause/blacklist the solver-beneficiary against, or one with a supply/allowance edge case that returns `false` instead of reverting), guaranteeing that when the solver fills the order and `RedeemEscrow` attempts to pay the solver, the payout silently no-ops while the order is finalized as filled.

### Impact Explanation
This is a direct fund-loss / false-settlement-state bug in the core intent escrow settlement logic: the solver who fulfilled an order (delivered output assets to the user) never receives their escrowed compensation, yet the protocol's on-chain state (`_orders`, `_filled`, emitted events) asserts the payout occurred. The escrowed tokens become permanently stranded in the contract with no remaining accounting path to recover them, since the balance is already marked spent. This is exactly the class of "loss of funds" / "false state acceptance" / "wrong beneficiary or amount" impact the bounty gate targets, applied to Hyperbridge's own intent-settlement bookkeeping rather than any imported dependency's bug.

### Likelihood Explanation
Any order using an ERC20 token that follows the return-false-on-failure convention (a real and standard-compliant category of tokens, distinct from but analogous to USDT's missing-return-value issue) will trigger this on the very first failed transfer condition for that token, with no attacker collusion, relayer/prover misbehavior, or governance action required — only an order creator choosing (or being forced by external token state, e.g. a later blacklist) a non-reverting-failure token as one of the escrowed assets.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with how the contract already handles inbound transfers via `safeTransferFrom`. `SafeERC20.safeTransfer` correctly decodes and enforces the boolean return value (and tolerates tokens with no return value), preventing a `false`-returning transfer from ever being accepted as successful settlement.

### Proof of Concept
1. Order creator places a cross-chain order whose `order.inputs[0].token` is a token contract that returns `false` (rather than reverting) when `transfer()` is called to a specific address/amount the creator controls (e.g., blacklists the solver's address post-placement, or engineers a state where `transfer` returns `false` for the settlement amount).
2. A solver fills the order on the destination chain, delivering the output assets to the user.
3. The source-chain `RedeemEscrow` message triggers `onAccept` → `withdraw(body, false)` on `evm/tron/contracts/apps/IntentGatewayV2.sol`. [9](#0-8) 
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, solver, amount))` returns `success = true` (call did not revert) but the token internally returned `false`. [1](#0-0) 
5. `_orders[commitment][token] -= amount` executes, `_filled[commitment] = solver` is set, and `EscrowReleased` is emitted — the solver receives nothing, and the tokens are now unrecoverable stuck balance in the gateway contract. [11](#0-10)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
