### Title
EIP-712 Domain Missing `chainId` and `verifyingContract` Enables Cross-Deployment/Cross-Chain Signature Replay in Aggregator Authorization — (`core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

`CLEMENTINE_EIP712_DOMAIN` is constructed with only `name` and `version`, omitting both `chain_id` and `verifying_contract`. Any ECDSA verification signature the aggregator produces for an optimistic payout or operator withdrawal on one Clementine deployment (or one Citrea chain) is cryptographically valid on every other deployment or chain that shares the same aggregator key, because the domain separator does not bind the signature to a specific chain or contract instance.

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 standard uses the domain separator precisely to prevent cross-chain and cross-contract replay. Both `chainId` and `verifyingContract` are absent here, even though the config already carries `citrea_chain_id` (a `u32`) and `bridge_contract_address` (a string). [2](#0-1) 

This domain is the sole cryptographic binding used by `recover_address_from_ecdsa_signature` to authenticate the aggregator for both flows:

**Optimistic payout** — `sign_optimistic_payout` in `verifier.rs`: [3](#0-2) 

**Operator withdrawal** — `withdraw` RPC in `rpc/operator.rs`: [4](#0-3) 

Both call `recover_address_from_ecdsa_signature` and compare the recovered address to `aggregator_verification_address` in config: [5](#0-4) 

Because the domain separator does not include `chain_id` or `verifying_contract`, the EIP-712 hash — and therefore the recovered address — is identical across all deployments and chains that share the same aggregator key.

### Impact Explanation

An attacker who obtains a legitimately-produced aggregator signature for a withdrawal on deployment A (e.g., testnet, or an older mainnet instance) can submit it verbatim to deployment B (e.g., mainnet, or a re-deployed instance). If deployment B has a deposit registered with the same `withdrawal_id` and the same `input_outpoint` Bitcoin UTXO (possible when the same Bitcoin UTXO is re-registered after a contract re-deployment, or when testnet and mainnet share an aggregator key), the operator and verifiers will accept the replayed signature as valid aggregator authorization and execute the withdrawal — potentially to an output address the aggregator never intended to authorize on that deployment. The result is an unauthorized payout of bridged BTC from the bridge vault.

### Likelihood Explanation

The `aggregator_verification_address` guard is optional (the `if let Some(...)` branch is skipped when the field is absent), so the vulnerability is only reachable when operators/verifiers have opted into the ECDSA verification feature. When it is enabled, the preconditions for replay — same aggregator key across deployments, and a matching `(withdrawal_id, input_outpoint)` pair — are realistic in re-deployment scenarios or when testnet and mainnet share infrastructure keys, which is a common operational mistake.

### Recommendation

Include `chain_id` and `verifying_contract` in `CLEMENTINE_EIP712_DOMAIN`. Both values are already present in `BridgeConfig` (`citrea_chain_id` and `bridge_contract_address`). The domain should be constructed at runtime from config rather than as a `static`:

```rust
Eip712Domain::new(
    Some("ClementineVerification".into()),
    Some("1".into()),
    Some(alloy::primitives::U256::from(config.citrea_chain_id)),
    Some(bridge_contract_address.parse()?),
    None,
)
```

Pass this domain into `recover_address_from_ecdsa_signature` instead of the global `CLEMENTINE_EIP712_DOMAIN` constant.

### Proof of Concept

1. Operator/verifier config has `aggregator_verification_address` set to address `A` on both a testnet deployment and a mainnet deployment, using the same aggregator private key.
2. Aggregator signs an `OptimisticPayoutMessage` on testnet for `(withdrawal_id=7, input_outpoint=<UTXO_X>, output_script_pubkey=<attacker_p2tr>, output_amount=<bridge_amount>)`. The EIP-712 hash is computed over `CLEMENTINE_EIP712_DOMAIN = {name, version}` only.
3. The same Bitcoin UTXO `<UTXO_X>` is registered as the withdrawal UTXO for `deposit_id=7` on mainnet (e.g., after a contract re-deployment that re-ingested the same deposits).
4. Attacker submits the testnet signature to the mainnet verifier's `optimistic_payout_sign` RPC. `recover_address_from_ecdsa_signature` recomputes the identical EIP-712 hash (domain is the same), recovers address `A`, and the check `address_from_sig != address_in_config` passes.
5. Verifiers produce partial MuSig2 signatures; the aggregated optimistic payout transaction sends bridge BTC to the attacker's address. [1](#0-0) [6](#0-5) [7](#0-6)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
