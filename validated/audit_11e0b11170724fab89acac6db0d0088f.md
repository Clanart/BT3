### Title
Panics on point-at-infinity aggregate nonce in BIP-340 HRAm cause remotely triggerable DoS - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Bitcoin `Hram` implementation calls `x()`/`x_only()`, which `expect()` that the point is not the point at infinity. `Hram::hram` is invoked on the aggregate nonce `R = Σ nonce commitments` during `sign_share`/`verify`. Although `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) rejects the identity for each individual commitment, the *sum* of attacker-controlled commitments can still be the identity. A malicious participant can therefore craft a preprocess whose commitments cancel the aggregate nonce, turning `hram` into a panic and aborting the process — the same class as CVE-2024-6119 (unreachable-code-path crash triggered only when the application checks an attacker-influenced identifier/value against an expected one).

### Finding Description
- `x()` panics on the point at infinity via `encoded.x().expect("point at infinity")` (networks/bitcoin/src/crypto.rs:13-16); `x_only` documents the same (lines 21-23).
- `Hram::hram` unconditionally calls `x(R)` where `R` is the aggregate nonce commitment (lines 59-67).
- The FROST verifier/signer path computes `R` as the sum of per-participant nonce commitments (`nonce_sums`), which are parsed from untrusted preprocess bytes. `Curve::read_G` rejects each identity commitment, but a non-identity commitment equal to the negation of the honest aggregate produces `R = 0`. A rushing/adaptive adversary that submits its preprocess after seeing the others can arrange this, since binding factors are computed over *all* commitments, not constraining the sum to non-identity.
- The doc comments even acknowledge this: "If either `R` or `A` is the point at infinity, this will panic" (lines 54, 78-83), but reachability analysis treats the probability as negligible only for honest inputs — it ignores that an adversary can *deterministically* force `R` to infinity by choosing its own commitment after observing the honest ones.

### Impact Explanation
A single malicious signing participant (an unprivileged party feeding public preprocess bytes) can deterministically crash any validator executing `Schnorr::sign_share`/`verify` for Bitcoin signing, halting the signing session and, depending on panic handling in the processor, the entire process. This is a denial of service reachable purely through public inputs (the preprocess/commitment bytes), matching the CVE class.

### Likelihood Explanation
High within a signing session containing one malicious participant. The attack requires seeing honest nonce commitments (normal FROST ordering: preprocesses are broadcast) and submitting a negating commitment — trivially computable, no secret knowledge needed.

### Recommendation
Replace the `expect("point at infinity")` path in `x()`/`x_only`/`Hram::hram` with a fallible result propagated as a `FrostError`, and/or explicitly check the aggregate `R` for identity before computing the challenge (blame the participant whose commitment caused it). At minimum, treat `R` identity like the existing `signature.R.is_identity()` courtesy rejection in `Signed::read`.

### Proof of Concept
Conceptual (no executable exploit provided): during a FROST Bitcoin signing session, the attacker waits for all other participants' nonce commitments `{D_j, E_j}`, computes the would-be aggregate `R_others = Σ_j ρ_j·D_j + E_j` (the code already computes binding factors and nonce sums), then publishes its own preprocess with commitment `C = -R_others` (a valid, non-identity point that passes `read_G`). When `sign_share` computes the final aggregate `R = R_others + C = ∞` and calls `Hram::hram(&R, &A, m)`, `x(R)` executes `encoded.x().expect("point at infinity")` at networks/bitcoin/src/crypto.rs:15, panicking and terminating the signing attempt.

Note: I verified the panic site (`x`/`x_only`/`hram` in `crypto.rs`) and the identity-rejection boundary (`Curve::read_G`). I did not read the exact `IetfSchnorr::sign_share` nonce-sum aggregation lines in `crypto/frost/src/sign.rs` before the iteration limit, so the precise line where the attacker cancels the sum is inferred from the standard `nonce_sums` mechanism documented in `crypto.rs:131-143` — the panic site itself is confirmed.
