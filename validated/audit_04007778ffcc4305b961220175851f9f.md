Kaia does support EIP-7702-style set-code transactions (`TxTypeEthereumSetCode`, `blockchain/types/tx_internal_data_ethereum_set_code.go`, `validate7702` in `blockchain/types/tx_internal_data.go`), which lets an EOA authorize code to be attached to its own address within a single transaction. Combined with the gasless module's stale, per-block "sender has no code" check, this reproduces the same class of bug as the report (an EOA/contract-code check that can be defeated because it doesn't reflect the account's code state at the actual moment of use), but I was not able to fully trace and confirm the exact reachable path (i.e., whether a set-code authorization applied in block N can be exploited against `getCurrentHasCode` before `PostInsertBlock` refreshes `g.currentState` for block N+1, and whether `GetCheckBalance` is invoked from a context using genuinely stale state) within the available tool calls.

### Title
Gasless sender-code check bypass via stale per-block code check combined with EIP-7702 set-code authorization - (File: kaiax/gasless/impl/tx_pool.go, kaiax/gasless/impl/init.go)

### Summary
The gasless module's `checkBalanceForApprove`/`checkBalanceForSwap` functions reject a gasless approve/swap transaction if the sender "has code," using `getCurrentHasCode`, which compares `GetCodeHash` against `types.EmptyCodeHash` on a cached `g.currentState`. [1](#0-0) [2](#0-1) 

### Finding Description
`g.currentState` is only refreshed in `PostInsertBlock`, i.e., once per committed block, not per pending transaction. [3](#0-2) 
This is structurally the same weakness pattern as the reported `onlyEOAEx()` bug: a code-presence check (`EXTCODESIZE`/code-hash based) is used as a substitute for "is this address a plain EOA," but the check is evaluated against a state snapshot that does not reflect the account's true code status at the moment the check matters, allowing an account that is in the process of acquiring code (e.g., via an EIP-7702 `TxTypeEthereumSetCode` authorization observed elsewhere in the codebase, `blockchain/types/tx_internal_data_ethereum_set_code.go`) to appear code-less to the gasless module even though the sender is effectively a delegated/contract-code account by the time the swap/approve executes.

### Impact Explanation
If exploitable, this would let an account with attached code (which the `BalanceCheckLevelAll` sender-code check is explicitly designed to exclude) participate in the gasless module's approve/swap flow, undermining the intended restriction and potentially enabling gasless-lending abuse (fee/repayment theft) by disallowed account types.

### Likelihood Explanation
Low-to-uncertain. The check is a mempool/tx-pool admission-time filter (`GetCheckBalance`), not an execution-time `require`, and final settlement still goes through `VerifyExecutable`/`checkBalanceForSwap`'s other checks (allowance, balance, deadline, nonce sequencing) which are unaffected by the code check. I could not confirm within the available searches whether `g.currentState` staleness is actually reachable within the same block as a set-code authorization transaction, nor whether any additional validation elsewhere re-checks code status before final inclusion.

### Recommendation
Recompute the sender's code status against the most current pending/prospective state (or re-validate at block-building/insertion time) rather than relying solely on the last committed block's cached state, and audit whether `TxTypeEthereumSetCode` authorizations can be combined with a subsequent gasless approve/swap in the same block before `g.currentState` is refreshed.

### Proof of Concept
Not fully constructed — requires confirming (1) whether `GetCheckBalance` is invoked using `g.currentState` at a point where a same-block/preceding set-code authorization tx's effect is not yet reflected, and (2) whether such an ordering is achievable by an unprivileged submitter. This could not be completed with the remaining tool budget; a background Devin session with repo access would be needed to trace `tx_pool.go`'s call sites for `GetCheckBalance` and `PostInsertBlock` ordering against `TxTypeEthereumSetCode` processing to confirm exploitability.

func (g *GaslessModule) getCurrentHasCode(addr common.Address) bool {
	g.currentStateMu.Lock()
	defer g.currentStateMu.Unlock()

	return g.currentState.GetCodeHash(addr) != types.EmptyCodeHash
}

func (g *GaslessModule) PostInsertBlock(block *types.Block) error {
	currentState, err := g.Chain.StateAt(block.Header().Root)
	if err != nil {
		return err
	}
	g.setCurrentState(currentState)
	return g.updateAddresses(block.Header())
}
