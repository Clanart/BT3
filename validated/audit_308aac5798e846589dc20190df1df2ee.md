### Title
Windows shell metacharacter injection when opening a repository-derived path in Git Bash/Cygwin/Alacritty/Hyper/Warp - (File: `app/src/lib/shells/win32.ts`)

### Summary
`app/src/lib/shells/win32.ts`'s `launch()` function builds several shell command-line strings by naively interpolating the repository's working-directory `path` into a double-quoted argument and then executes it with Node's `child_process.spawn(..., { shell: true })`. On Windows, `shell: true` invokes `cmd.exe`, whose parsing of metacharacters (`&`, `%`, `^`, `!`, `(`, `)`) is not reliably neutralized by surrounding double quotes — this is the same class of "insecure command concatenation" flaw as the reported `vboxmanage.js` issue, where user-controlled data is spliced into a command string executed via a shell. GitHub Desktop already has a proper escaping utility for exactly this purpose (`app/src/lib/hooks/shell-escape.ts`'s `cmdEscape`), but it is only used for the hooks-env feature and not applied to the shell-launch code path in `win32.ts`.

### Finding Description
The `launch()` function in `app/src/lib/shells/win32.ts` handles several shells by string-interpolating `path` (the repository's local path) directly into command-line arguments and passing `shell: true`: [1](#0-0) [2](#0-1) [3](#0-2) 

`path` originates from `_openShell(path)` in `app-store.ts`, which is invoked with the repository's on-disk path whenever the user chooses "Open in <shell>": [4](#0-3) 

That directory name can, in turn, be derived from an attacker-controlled remote/repository name during clone. `sanitizeCloneName()` — used by the Clone dialog to turn a parsed repo name into a filesystem directory component — only strips path separators and rejects traversal segments (`..`, `.`, empty); it does **not** strip cmd.exe metacharacters such as `&`, `%`, `^`, `!`, `(`, `)`: [5](#0-4) [6](#0-5) 

Because the "Clone repository" URL/alias flow accepts arbitrary remote URLs (not restricted to GitHub.com's stricter repo-name charset), an attacker who controls a git server/proxy can serve a repository whose name (or URL path segment) contains `&`, `%`, `^`, etc. — all legal in NTFS filenames. These characters survive `sanitizeCloneName()` untouched and become part of the local clone directory name that is later interpolated into a `shell:true` command string in `win32.ts`.

Critically, the project already recognizes this exact hazard and ships a dedicated escaping module, `cmdEscape`, that properly neutralizes `%&<>^|` for `cmd.exe` — but only for the shell-hooks-environment feature (`app/src/lib/hooks/get-shell-env.ts`): [7](#0-6) [8](#0-7) 

The `win32.ts` shell-launcher code performs no equivalent escaping; it simply wraps the path in literal double quotes (`` `"${path}"` ``), which is exactly the "insecure command concatenation" pattern flagged in the external report.

### Impact Explanation
If exploited, this allows execution of arbitrary commands via `cmd.exe` on the victim's machine under the identity/privileges of the currently logged-in Desktop user, triggered purely by the user performing a normal, expected action ("Open in Git Bash/Cygwin/Alacritty/Hyper/Warp") on a repository that was cloned from an attacker-influenced remote. This matches the "attacker controls a cloned/fetched repository ... and the result is code execution" impact category.

### Likelihood Explanation
Exploitation requires: (1) the victim clones from a URL/host that isn't validated against GitHub.com's stricter naming rules (any generic git remote, enterprise/self-hosted git server, or malicious proxy responding to a `git@github.com:owner/name` style URL with a crafted API/redirect), (2) the resulting local directory name contains an un-sanitized cmd.exe metacharacter, and (3) the user later clicks "Open in [Shell]" for that repository on Windows using one of the affected shell integrations (Git Bash, Cygwin, Alacritty, Hyper, Warp — all of which build a `shell:true` command string with the path interpolated). Steps 1–3 are all part of Desktop's ordinary, expected workflow and require no unnatural user action, elevated privileges, or pre-existing host compromise, but the attacker does need to control the naming/content served by the git remote — reducing likelihood somewhat compared to a fully passive drive-by, but keeping it within the "attacker controls a git remote/proxy response" valid-impact category.

### Recommendation
- Apply the existing `cmdEscape` (or an equivalent PowerShell/shell-appropriate escaper from `app/src/lib/hooks/shell-escape.ts`) to any path segment interpolated into a `spawn(..., { shell: true })` command string in `app/src/lib/shells/win32.ts`, for all affected cases (`PowerShell`, `PowerShellCore`, `Hyper`, `Alacritty`, `GitBash`, `Cygwin`, `Warp`, `Cmd`, `WindowsTerminal`, `FluentTerminal`).
- Prefer passing `path` exclusively via the `cwd` spawn option (as already done correctly for some cases) rather than interpolating it into the command-line string, eliminating the need for shell quoting entirely where possible.
- Additionally harden `sanitizeCloneName()` in `app/src/lib/remote-parsing.ts` to reject or replace cmd.exe/PowerShell metacharacters (`& % ^ ! ( )` etc.), not just path separators and traversal sequences, mirroring the character class already excluded by `safeDirectoryName()` in `app/src/ui/lib/repository-path.tsx`.

### Proof of Concept
1. Stand up a git server (or HTTP proxy in front of one) that serves a repository reachable via a Desktop-parsable URL such as `https://evil.example.com/owner/name%26calc%26.git` (URL-decodes / parses to a repo name containing `&`).
2. Victim opens GitHub Desktop → "Clone Repository" → pastes the URL. `parseRepositoryIdentifier`/`sanitizeCloneName` derive the clone directory name `name&calc&`, which is legal on NTFS, so `git clone` succeeds and creates `<BaseDir>\name&calc&`.
3. Victim right-clicks the repository in Desktop and selects "Open in Git Bash" (or Cygwin/Alacritty/Hyper/Warp).
4. `_openShell` → `Win32.launch()` executes:
   ```
   spawn(`"C:\...\git-bash.exe"`, [`--cd="<BaseDir>\name&calc&"`], { shell: true, cwd: path })
   ```
   which `cmd.exe /d /s /c` expands; because `&` is not escaped, `cmd.exe` interprets it as a command separator, executing the injected trailing command (e.g., launching `calc.exe` or any attacker-supplied payload) in addition to (or instead of) opening Git Bash.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

// https://github.com/ericcornelissen/shescape/blob/89072ba7de233f81f5553b52098671c94eb9bd0c/src/internal/win/cmd.js#L35
const cmdEscape = (arg: string) =>
  arg
    .replace(/[\0\u0008\r\u001B\u009B]/gu, '')
    .replace(/\n/gu, ' ')
    .replace(/"/gu, '""')
    .replace(/([%&<>^|])/gu, '"^$1"')
    .replace(/(?<!\\)(\\*)(?="|$)/gu, '$1$1')

export const cmd: Shell = {
  args: ['/d', '/s', '/c'],
  quoteCommand: (cmd, ...args) =>
    `"${[cmd, ...args].map(a => `"${cmdEscape(a)}"`).join(' ')}"`,
}
