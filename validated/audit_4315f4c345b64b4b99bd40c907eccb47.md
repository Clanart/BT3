### Title
OP_RETURN data output excluded from weight and fee accounting, producing under-fee / over-weight transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` (payments + optional OP_RETURN data output + optional change output) but calls `calculate_weight_vbytes` with `payments` — the raw payment list — not the actual output list. Any weight contributed by the OP_RETURN output (9 bytes overhead + up to 80 bytes of data) is omitted from both the fee computation and the standardness weight check. This is the same bug class as the Ignite report: an accounting value (`needed_fee`, `weight`) is derived from the wrong quantity, so a later "redemption" (broadcast) fails because the tracked value was smaller than it should have been.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is pushed onto `tx_outs` at lines 194-202, before weight is computed:

```rust
// line 204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62-127) reconstructs a `Transaction` using only `payments` and the optional `change` script; it never receives `tx_outs`, so the already-pushed OP_RETURN output is invisible to it. The same omission occurs in the change path at line 226, which also passes `payments`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is calculated on a vsize that excludes the OP_RETURN output (~11 + data_len real vbytes).
- `fee()` (lines 138-141) shows the *actual* fee equals `sum(inputs) - sum(outputs)`, which is unchanged in absolute satoshis — meaning the *effective feerate* of the built transaction is below the requested `fee_per_vbyte`.
- The minimum-relay-fee check at line 211 and the `MAX_STANDARD_TX_WEIGHT` check at line 241 are both evaluated against the understated `vbytes`/`weight`.

The data payload is attacker-influenced: `SignableTransaction::new` accepts `data: Option<Vec<u8>>` of up to 80 bytes, supplied from instruction metadata an unprivileged user causes to be signed. The code path does not depend on validator misbehavior — any externally triggered payment carrying data hits it.

### Impact Explanation
Two failure modes, both reachable purely by requesting a payment with attached data:

1. **Under-fee / non-standard relay failure.** With a boundary `fee_per_vbyte` (e.g., the relay minimum), the omitted OP_RETURN weight (~90 WU for 80-byte data) means the real feerate falls below the minimum relay fee even though the check at line 211 passed. The signed transaction is then rejected by node mempools — the multisig produced a transaction it cannot broadcast, a DoS on the payment identical in shape to the Ignite redemption DoS.
2. **Over-weight non-standardness.** If payments+inputs+change sit just below `MAX_STANDARD_TX_WEIGHT`, the uncounted OP_RETURN output can push the real transaction over the standardness limit; the check at line 241 uses the too-small `weight`, so construction succeeds but the result is non-standard and unrelayable.

The signed artifact commits via `Prevouts::All` and `TapSighashType::Default` (lines 373-390), so once shares are combined the bad transaction is final for that attempt.

### Likelihood Explanation
Requires only that a payment carry `data` and that `fee_per_vbyte`/size land near a boundary. Data-carrying payments are an intended, externally reachable feature (the 80-byte OP_RETURN limit exists precisely for arbitrary instruction data), so the trigger is a normal public input, not an edge case requiring privileged state. However, both impacts require boundary alignment (fee rate near relay minimum or weight near the standardness cap), and absolute overpayment of fees is impossible — the bug only ever *under*-accounts. That caps this at Medium: a reachable DoS on specific transactions, not a loss of funds.

### Recommendation
Pass the actual output list into the weight calculation, or compute weight after `tx_outs` is finalized. Concretely, change `calculate_weight_vbytes` to take `&[TxOut]` and call it with `&tx_outs` (plus the hypothetical change output where applicable) at `send.rs:204` and `send.rs:226`, so `needed_fee`, `vbytes`, `weight`, the min-relay check, and the max-weight check all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
```rust
// In a test for SignableTransaction::new:
let inputs = vec![received_output_with(10_000)];         // one 10k-sat input
let payments = vec![(dest_script, 5_000)];
let data = Some(vec![0xaa; 80]);                          // max OP_RETURN payload

let stx = SignableTransaction::new(inputs, &payments, None, data, 1).unwrap();

// The real tx has an extra ~91-byte OP_RETURN output that needed_fee never saw:
//   real_vbytes = stx.transaction().vsize()  >  vbytes used internally
// assert!(stx.needed_fee() >= 1 * stx.transaction().vsize() as u64);  // FAILS:
// needed_fee was computed as fee_per_vbyte * vbytes(payments only),
// short by ~1 * (OP_RETURN output size) sat.
//
// With fee_per_vbyte chosen so needed_fee just clears DEFAULT_MIN_RELAY_TX_FEE,
// tx.fee() / tx.vsize() < min relay feerate → relay rejection (DoS).
```

The discrepancy is directly observable: `stx.fee()` counts the OP_RETURN output's effect on `sum(outputs)` while `needed_fee` was computed without it, proving the two accounting values diverge by exactly the OP_RETURN output's weight.
