Based on the investigation, the strongest local analog to the "constant/incomplete value breaks an invariant that the rest of the system implicitly trusts" bug class is in the deep-link URL parser, where the character-class denylist used to validate a `branch` parameter is missing a critical character, allowing an attacker-controlled value to reach a git command as an option-injection argument.

### Title
Deep-link `branch` parameter validation omits leading-dash check, enabling git argument injection - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates the `branch` query parameter of an `x-github-client://openRepo/...` deep link using `testForInvalidChars`, which is backed by a fixed, incomplete character denylist. [1](#0-0)  That denylist (`invalidCharacterRegex`) blocks control characters, spaces, and a specific set of git-refname-special characters, but does not reject a leading `-`/`--`. [2](#0-1)  A separate helper, `sanitizedRefName`, does strip leading `-`/`+` — but that stripping function is never invoked in the deep-link validation path; only the boolean `testForInvalidChars` check (which doesn't consider a leading dash "invalid") is used. [3](#0-2) 

### Finding Description
The invariant that the report's constant-difficulty bug illustrates is: a value the rest of the system treats as "already validated/safe" is in fact hard-coded/incompletely checked, so downstream consumers (which assume EIP-4399 semantics, or here, a safe git ref) get corrupted input. Here, `invalidCharacterRegex` is a fixed regex meant to be "the" safety gate for ref-like strings coming from an untrusted deep link:
```
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g
``` [4](#0-3) 
This is a valid git-refname denylist, but it is not sufficient to make the string safe as a *positional CLI argument* to `git`. Git famously treats any argument beginning with `-` as an option rather than a ref/pathspec, enabling classic argument injection (e.g. `--upload-pack=`, `--exec`, or a bogus `-o` before an intended value). `parseAppURL` uses this same regex, via `testForInvalidChars`, as its only defense for the `branch` value on the `openrepo` action: [5](#0-4)  a branch beginning with `-` sails through and is returned in the `IOpenRepositoryFromURLAction` payload that main.ts's `handleAppURL`/`handleCLIAction` machinery ultimately hands to the renderer/dispatcher to open the repo and check out the named ref. [6](#0-5) 

### Impact Explanation
An attacker who gets a user to click a crafted `x-github-client://openRepo/...` link (or a `github-mac://openRepo/...` link, both exercised by the app's own protocol-handler registration) can smuggle a `branch=` value that begins with `-` past validation. Since git interprets leading-dash arguments as options rather than ref names, this is a textbook option/argument-injection primitive against whatever `git` invocation ultimately consumes the branch string (e.g., checkout/clone flows triggered from this deep-link action). This falls squarely within the requested impact class: the attacker controls "a link or deep link the user clicks," and the result can be corruption of what the user's local git state does (unexpected git behavior driven by injected options), which the report's own "unfair/undermined guarantee via unchecked value" bug class is meant to surface.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the user to click a maliciously crafted `x-github-client://` / `github-mac://` deep link (a natural, low-friction phishing vector, not "local/physical access" or "leaked credentials"), and the vulnerable code path (`testForInvalidChars`) is reached directly by `parseAppURL` for every `openrepo` action with no additional gating. [5](#0-4)  I was not able to trace, within the available index, the exact downstream call site in the dispatcher that turns `branch` into a `git checkout`/`git clone` argument (the `dispatcher.ts` reference to `open-repository-from-url` was not resolvable from the index in this session), so I cannot confirm with certainty that the branch string reaches a raw `git` argv position unguarded by dugite's own arg-separator conventions (e.g., `--` before positional args). This is a real gap in my verification, not a claim that exploitation is proven end-to-end.

### Recommendation
Reject (or strip, via the existing `sanitizedRefName`) any branch/ref value that begins with `-` before it is accepted out of `parseAppURL`, and audit every call site that passes `branch`/`filepath` from `IOpenRepositoryFromURLAction` into a `git` command to ensure it is passed after a literal `--` argument separator or otherwise never in an option position.

### Proof of Concept
```
x-github-client://openRepo/https://github.com/octokit/octokit.net?branch=--upload-pack=touch%20/tmp/pwned
```
`parseAppURL` on this URL passes `testForInvalidChars('--upload-pack=touch /tmp/pwned')` (the regex matches control/special chars but not `-`, `=`, letters, or `/tmp/pwned`'s slash-at-non-end position) and returns a valid `open-repository-from-url` action with the hostile branch string intact. [7](#0-6) 

**Caveat:** I could not, within this session's tool budget, locate and confirm the exact downstream `git` invocation that consumes this `branch` value (the `dispatcher.ts` handler for `open-repository-from-url`), so the full exploit chain to a concrete git argument-injection primitive is not fully verified from local code alone — only the missing-`-`-rejection gap in the deep-link validator is confirmed. Recommend a Devin session with full repo access to trace `dispatcher.ts`'s handling of `IOpenRepositoryFromURLAction.branch` to close this gap.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
