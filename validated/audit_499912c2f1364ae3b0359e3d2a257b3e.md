### Title
Payout tx OP_RETURN attribution is spoofable via SIGHASH_SINGLE|ANYONECANPAY output insertion - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`get_first_op_return_output` blindly trusts the first OP_RETURN output of a payout transaction to identify the funding operator's xonly pubkey, both in-circuit (`deposit_constant`) and in `update_finalized_payouts`. Because the withdrawer's own input signature uses `TapSighashType::SinglePlusAnyoneCanPay`, it commits only to input 0 and its matching output, leaving every other input and output — including the position and content of any OP_RETURN — completely unconstrained for anyone who possesses that signature.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` stored in `withdrawals` (via `update_payout_txs_and_payer_operator_xonly_pk`, `core/src/database/verifier.rs:199`) should equal `kickoff_data.operator_xonly_pk` of the operator that actually funded the payout output.

`get_first_op_return_output` [1](#0-0)  simply returns the first output whose script is OP_RETURN, with no check that it belongs to, or was added by, the operator. It is used both to derive `operator_xonlypk` for the in-circuit `deposit_constant` [2](#0-1)  and, separately, by `update_finalized_payouts` to populate the DB column that later feeds `is_kickoff_malicious` [3](#0-2) .

The withdrawer's signature over the withdrawal-UTXO input is enforced to be exactly `SinglePlusAnyoneCanPay` [4](#0-3) . Under BIP341/BIP143, `SIGHASH_SINGLE | ANYONECANPAY` commits only to the single input being signed and the single output at the same index — it places no constraint whatsoever on any other input or output that ends up in the final broadcast transaction, including their count, order, or content. This means the party who possesses that signature can freely assemble a transaction containing extra outputs (e.g., an attacker-chosen OP_RETURN) at any position, including before wherever a legitimate operator-funded OP_RETURN would otherwise land, without invalidating the withdrawer's own signature.

### Impact Explanation
If an attacker-controlled OP_RETURN is picked up instead of the true funding operator's, `update_finalized_payouts` will persist a `payout_payer_operator_xonly_pk` that does not correspond to the operator who actually funded the output. Downstream, `is_kickoff_malicious` [5](#0-4)  compares this stored value against `kickoff_data.operator_xonly_pk` of the operator submitting a reimbursement kickoff. A mismatch causes the real funding operator's legitimate kickoff to be rejected as malicious, permanently blocking reimbursement — matching the Critical category "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
I was not able to fully confirm two architectural details within the available tool budget: (1) whether the transaction that actually gets accepted by `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` as "the" payout for a given withdrawal is the one an operator itself constructs and broadcasts (in which case the operator's own funding input(s) would need to also use a permissive sighash type for an attacker to inject an extra OP_RETURN into that same transaction), or (2) whether a withdrawer/attacker can instead self-fund and broadcast an entirely separate, competing transaction that only reuses the withdrawer's own `SinglePlusAnyoneCanPay` signature and independently satisfies the SPV/storage-proof checks for that withdrawal. The mod.rs and verifier.rs code confirms the parsing logic is unconditionally "first OP_RETURN wins," and the sighash-type enforcement confirms the withdrawer-controlled input/output pair is the only part of the payout tx that is cryptographically pinned — everything else, by construction, is malleable by whoever assembles the final transaction.

### Recommendation
Do not infer the funding operator's identity from an unauthenticated "first OP_RETURN" heuristic. Bind the OP_RETURN (or whichever output encodes `operator_xonlypk`) to a specific, protocol-committed output index (e.g., always the last output, or an index fixed by the presigned transaction template / kickoff commitment) rather than "the first one found," and additionally require that output to be covered by a signature with a sighash type that commits to the full output set (e.g., `SIGHASH_ALL` from the operator's own funding input), so attacker-inserted outputs cannot be inserted ahead of it without invalidating the operator's own signature.

### Proof of Concept
```
cargo test -p core --lib -- verifier::tests::payout_op_return_spoofing
```
Test plan:
1. Construct a `payout_tx` with: input 0 spending the known withdrawal UTXO, output 0 = the withdrawer's own script/amount, signed with `TapSighashType::SinglePlusAnyoneCanPay` per `parse_withdrawal_sig_params`.
2. Add an attacker-controlled OP_RETURN output before any operator-funded input/output, then append a second OP_RETURN encoding the real operator's `operator_xonly_pk`.
3. Feed this tx through `update_finalized_payouts` and assert the `withdrawals` table's `payout_payer_operator_xonly_pk` equals the attacker's chosen bytes rather than the real operator's `operator_xonly_pk`.
4. Call `is_kickoff_malicious` with a `kickoff_data.operator_xonly_pk` equal to the real (honest) operator's key and assert it returns `true` (rejecting the honest operator).
