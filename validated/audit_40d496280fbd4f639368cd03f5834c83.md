### Title
Missing lower-bound check in `set-max-confidence-ratio` allows setting confidence ratio to 0, permanently blocking Pyth price resolution and freezing all price-dependent market operations - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`set-max-confidence-ratio` in `v0-4-market.clar` only enforces an upper bound (`ratio <= BPS`) but has no lower bound, mirroring the reported `PaymentProcessor.setTokenPricingBounds` flaw where only one side of a two-sided threshold is validated. Setting the ratio to `u0` makes the confidence-gating check in `check-confidence` reject virtually every legitimate Pyth price, causing `ERR-PRICE-CONFIDENCE-LOW` on every subsequent `price-resolve` call for Pyth-backed assets, which freezes borrow, repay, withdraw, collateral-add, and liquidation flows that depend on price resolution.

### Finding Description
`set-max-confidence-ratio` is DAO-gated and validates only the upper bound: [1](#0-0) 

This value feeds directly into `check-confidence`, which is invoked on every Pyth price resolution: [2](#0-1) 

`check-confidence` requires `confidence <= (price * ratio) / BPS`. If `ratio = u0`, the right-hand side is always `0`, so the assertion requires `confidence <= 0`. Pyth confidence intervals are always positive `uint` values in practice, so this check will always fail once `ratio` is `0`, unconditionally reverting with `ERR-PRICE-CONFIDENCE-LOW` for every Pyth-sourced asset.

This price resolution is the single choke point used by `price-resolve` / `price-multi-resolve`, which every collateral/debt-valuing operation depends on: [3](#0-2) 

Since `resolve-price-feed` routes Pyth-type assets through `resolve-pyth` → `check-confidence`, setting `max-confidence-ratio` to `0` makes every function that needs a Pyth price for a collateral/debt asset (borrow, repay, withdraw collateral, health checks, liquidation) revert, exactly analogous to how the reported bug allowed an admin-settable bound (`ceilingPrice`) to be pinned to a value (`0`) that deterministically blocks transactions relying on it.

Just as the external report notes the setter is missing a sanity check that the two bounds cannot collapse to a degenerate value, `set-max-confidence-ratio` is missing a sanity check that `ratio > 0` (or some sane minimum), letting a single call collapse the confidence gate to an unusable state.

### Impact Explanation
Once `max-confidence-ratio` is `0`, all Pyth-priced collateral/debt assets become unusable for any price-dependent action (borrow, repay, collateral withdrawal, liquidation) because `price-resolve` always errors out. Users' collateral and outstanding positions cannot be modified or liquidated while priced through Pyth, which is a temporary freezing of funds until the DAO corrects the parameter — matching the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
The call is DAO-authorized (`check-dao-auth`), so it requires a governance/multisig transaction, not a privileged-key compromise. The likelihood stems purely from the missing input validation: any legitimate DAO call intending to tighten oracle confidence tolerance to its strictest possible setting (`0`, "no tolerance") — which is a plausible, non-malicious governance action, not a mistake requiring insider compromise — will unexpectedly brick all Pyth-priced market operations, since nothing in the code signals that `0` is an invalid/degenerate value.

### Recommendation
Add a lower-bound check in `set-max-confidence-ratio`, e.g. `(asserts! (and (> ratio u0) (<= ratio BPS)) ERR-ORACLE-INVARIANT)`, or otherwise enforce a sane minimum confidence-ratio floor so the confidence gate can never be collapsed to a value that makes `check-confidence` unconditionally fail.

### Proof of Concept
1. DAO calls `set-max-confidence-ratio(u0)` via `check-dao-auth`-authorized path. [1](#0-0) 
2. Any subsequent call resolving a Pyth-backed asset price (e.g. `collateral-add`, `borrow`, `liquidate`) invokes `resolve-pyth` → `check-confidence`. [4](#0-3) 
3. `check-confidence` requires `confidence <= (price * 0) / BPS = 0`; since Pyth's `conf` field is always `> 0`, the assertion fails and the call reverts with `ERR-PRICE-CONFIDENCE-LOW` for every Pyth-priced asset, blocking all price-dependent operations until the DAO issues a corrective transaction.

  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
