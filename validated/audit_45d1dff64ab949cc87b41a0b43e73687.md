### Title
Local GitHub-repository identity keyed by mutable `login` (not GitHub's immutable owner ID) allows login-squatting to silently overwrite an unrelated repository's cloneURL/permissions/parent - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
`IDatabaseOwner` records are looked up and created solely from the case-insensitive pair `(endpoint, login)` [4](#0-3) , ignoring the GitHub API's immutable numeric `owner.id`. Because GitHub allows a username to be freed (renamed away or account deleted) and later claimed by a different, unrelated account, the same local `Owner` row (and thus the same `ownerID`) can end up representing two different real GitHub accounts over the app's lifetime. Since `IDatabaseGitHubRepository` uniqueness and lookup is `[ownerID+name]` [5](#0-4) , an attacker who registers a previously-used login and creates a repo with a name matching one the app already has stored for that login will cause `_upsertGitHubRepository` to treat their repo as the "same" DB record, overwriting `cloneURL`, `permissions`, `parentID`, `htmlURL`, `private`, etc. on the next fetch/upsert (e.g. pull-request refresh, `repositoryWithRefreshedGitHubRepository`, fork conversion) [6](#0-5) .

### Finding Description
The described "rename to collide on `[ownerID+name]`" scenario as literally stated (same owner, same account, renaming one of its own repos to a name already used by another of its own repos) cannot occur through the real GitHub API, because GitHub itself enforces name-uniqueness per account — you cannot create/rename a repo to a name your account already owns. So the exact PoC as phrased is not directly reproducible via legitimate API responses from a single, unchanged account.

However, the underlying weakness the question is circling is real: the `ownerID` used as half of that unique key is derived only from the attacker/user-controlled `login` string per endpoint [1](#0-0) , not from GitHub's stable numeric `owner.id`. GitHub logins are mutable and reusable (rename or delete an account, then a different person registers that login). If:
1. Desktop has previously stored a `GitHubRepository` for `login="victim"`, `name="cool-repo"` (real record, real cloneURL/permissions), and
2. The `victim` account is later renamed or deleted, freeing the login, and an attacker registers `login="victim"` and creates a public repo named `cool-repo`,

then the next time any code path calls `_upsertGitHubRepository`/`upsertGitHubRepositoryLight`/`upsertGitHubRepositoryFromMatch` with API data referencing `owner.login === "victim"` and `name === "cool-repo"` (e.g. refreshing associated repo info, PR base/head repo upsert in `pull-request-store.ts` [7](#0-6) , or `_convertRepositoryToFork` [8](#0-7) ), `putOwner` resolves to the *same* local `ownerID` as before, `[ownerID+name]` matches the old record, and the attacker's `clone_url`, `permissions`, `parentID`, `html_url` silently replace the legitimate ones in that single existing DB row [3](#0-2) .

### Impact Explanation
If a user's locally tracked repository's `GitHubRepository.cloneURL` is corrupted this way, subsequent flows that trust that stored `cloneURL` (e.g. updating remotes, `updateRemoteUrl` when refreshing associated GitHub repo info) could point the user's local git remote at an attacker-controlled clone URL, and permission/fork metadata could also be misrepresented. This matches the "silent corruption of what the user commits or pushes" class of impact since a remote could be redirected without explicit user action.

### Likelihood Explanation
This requires the specific, somewhat rare precondition that Desktop has previously recorded a repo for a login, that login later becomes available (rename/deletion by the original owner — an action the attacker does not control), and the attacker registers exactly that freed login and a matching repo name before the app's next relevant sync. This is a real design weakness (identity keyed by mutable `login` rather than immutable `owner.id`), but the exploit scenario is a login-squatting race rather than the simpler same-account rename collision described in the question, which isn't directly possible given GitHub's own uniqueness constraints.

### Recommendation
Key `IDatabaseOwner` (and thus `[ownerID+name]` for `IDatabaseGitHubRepository`) by GitHub's immutable numeric `owner.id` (already present in `IAPIRepository.owner.id`) in addition to/instead of `login`, so a reused login cannot silently inherit a stale repository record's identity. At minimum, when upserting, verify the numeric owner id matches before treating `existingRepo` as the same repository, or invalidate/re-key cached owner records when the numeric id changes for a given login.

### Proof of Concept
Not directly reproducible as literally stated in the question (same account cannot rename to collide with its own existing repo name via the real GitHub API). A genuine variant would require: (1) upsert repo for `login="victim"`, `name="cool-repo"` establishing a DB record with real `cloneURL`; (2) simulate `victim` login being freed and reused by a different account holder; (3) upsert a new API repository object with the same `login="victim"`, `name="cool-repo"`, but attacker-controlled `clone_url`; observe that `_upsertGitHubRepository`'s `[ownerID+name]` lookup returns the original DB row id and overwrites its `cloneURL` in place, as shown by `updatedGitHubRepo` reusing `existingRepo.id` [9](#0-8) .

  private async putOwner(
    endpoint: string,
    login: string,
    ownerType?: GitHubAccountType
  ): Promise<Owner> {
    const key = getOwnerKey(endpoint, login)
    const existingOwner = await this.db.owners.get({ key })
    let id

    // Since we look up the owner based on a key which is the product of the
    // lowercased endpoint and login we know that we've found our match but it's
    // possible that the case differs (i.e we found `usera` but the actual login
    // is `userA`). In that case we want to update our database to persist the
    // login with the proper case.
    if (
      existingOwner === undefined ||
      existingOwner.login !== login ||
      // This is added so that we update existing owners with an undefined type.
      (ownerType !== undefined && existingOwner.type !== ownerType)
    ) {
      id = existingOwner?.id
      const existingId = id !== undefined ? { id } : {}
      id = await this.db.owners.put({
        ...existingId,
        key,
        endpoint,
        login,
        type: ownerType,
      })
    } else {
      id = forceUnwrap('Missing owner id', existingOwner.id)
    }

    return new Owner(login, endpoint, id, ownerType ?? existingOwner?.type)

  public async _convertRepositoryToFork(
    repository: RepositoryWithGitHubRepository,
    fork: IAPIFullRepository
  ): Promise<Repository> {
    const gitStore = this.gitStoreCache.get(repository)
    const defaultRemoteName = gitStore.defaultRemote?.name
    const remoteUrl = gitStore.defaultRemote?.url
    const { endpoint } = repository.gitHubRepository

    // make sure there is a default remote (there should be)
    if (defaultRemoteName !== undefined && remoteUrl !== undefined) {
      // update default remote
      if (await gitStore.setRemoteURL(defaultRemoteName, fork.clone_url)) {
        await gitStore.ensureUpstreamRemoteURL(remoteUrl)
        // update associated github repo
        return this.repositoriesStore.setGitHubRepository(
          repository,
          await this.repositoriesStore.upsertGitHubRepository(endpoint, fork)
        )
      }
    }
    return repository
  }
