I found a promising analog candidate in the fee amortization path. Let me verify the `created_output` call site and semantics.### Title
Fee amortization in `Scheduler::created_output` subtracts `expected - actual` in the wrong order, silently dropping all payments under any fee-bearing branch output - (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
The Sentiment M-16 bug class is "a pre-action check that fails to account for a fee deducted during execution, leaving the post-action state invalid." The Serai analog lives in the UTXO scheduler's post-fee accounting. When a Plan pays the transaction fee by reducing a `Branch` output, `created_output` is called with `expected` (pre-fee amount) and `actual` (post-fee on-chain amount). The code computes the fee to amortize as `actual - expected`, which underflows on every fee-bearing branch (in release builds wrapping to ~`u64::MAX`), causing the "payments can't cover the fee" early-return path and silently dropping all child payments queued under that branch. This is reachable by unprivileged users via ordinary `burn`/OutInstruction flows that get scheduled through branch outputs.

### Finding Description
`SignableTransaction`/`prepare_send` amortize transaction fees by decrementing payment amounts before signing (`processor/src/networks/mod.rs`, `prepare_send` amortization loop). For payments destined to a `Branch` address, a `PostFeeBranch { expected, actual }` is emitted where `expected` is the original amount and `actual` is `Some(post_fee_amount)` (or `None` if dropped below dust). In `processor/src/multisigs/mod.rs`, `substrate_block` forwards each `PostFeeBranch` to `scheduler.created_output(txn, branch.expected, branch.actual)`.

Inside `Scheduler::created_output` (`processor/src/multisigs/scheduler/utxo.rs:463-524`):

```rust
// Amortize the fee amongst all payments underneath this branch
{
  let mut to_amortize = actual - expected;
  // If the payments are worth less than this fee we need to amortize, return, dropping them
  if payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>() < to_amortize {
    return;
  }
  ...
}
```

The fee that must be re-amortized across the branch's queued child payments is `expected - actual` (fees only ever reduce the output; `actual <= expected` by construction, since `actual` is produced after subtracting `tx_fee` in the amortization loop). The subtraction is inverted:

- If `actual < expected` (the normal case, any nonzero fee): `actual - expected` underflows. In a release build (`overflow-checks` off) this wraps to a near-`u64::MAX` value, so `payments_sum < to_amortize` is always true and the function returns early — dropping every child payment that was queued under that branch output. In a debug/overflow-checked build it panics, halting the processor's block-handling loop mid-transaction (liveness failure).
- The correct intent (`to_amortize = expected - actual`) would subtract only the small fee delta.

Additionally, the bookkeeping has an inverted framing even absent the underflow: the child payments are stored at their pre-fee values and the code intends to decrement them by the fee the parent transaction paid, which is `expected - actual`, never `actual - expected`.

### Impact Explanation
- **Silent loss of user funds (release):** Every branch output whose fee is nonzero causes all queued child `Payment`s beneath it to be dropped without refund path — users who burned `sriXYZ` never receive their external-network payment. This directly mirrors the M-16 class: the pre-state (`expected`) check does not correctly account for the fee deducted during execution (`actual`), so the post-state accounting is corrupted.
- **Processor halt (debug/panic-on-overflow):** A single fee-bearing branch output panics `plans_from_block`/`substrate_block` processing, stalling all payouts for that multisig.
- Reachability: burn instructions from any unprivileged Serai user create payments; whenever the scheduler aggregates payments under a branch output (standard operation per the UTXO management spec) and the created TX pays a nonzero fee, `created_output` is invoked with `actual < expected`.

### Likelihood Explanation
High. This is not dependent on attacker crafting — any branch output created with a nonzero amortized fee triggers it. `PostFeeBranch.actual` is `Some(amount)` only when the post-fee amount is nonzero and ≥ dust, and `actual < expected` holds whenever `total_fee > 0`, i.e., essentially always in production. The path is exercised only when the scheduler routes payments through `Branch` outputs, which is the designed mechanism for aggregating scheduled payments.

### Recommendation
Fix the subtraction direction and clarify the invariant:

```rust
// Amortize the fee amongst all payments underneath this branch
let fee = expected - actual; // actual <= expected since fees only reduce the output
let mut to_amortize = fee;
```

Additionally:
- Add `debug_assert!(actual <= expected)` at the top of `created_output` to catch contract violations.
- Re-check the branch's solvency post-amortization: after subtracting, assert `actual >= sum(remaining payments)` (already present at line 513) and consider logging dropped payments with amounts and payment IDs so funds aren't silently unaccounted.
- Consider marking dropped child payments explicitly in the DB (e.g., an operating-cost/dead-payment record) instead of silent `return`, so accounting remains auditable.

### Proof of Concept
Concrete flow with `Bitcoin` (`N::DUST = 10_000`):

1. Users submit burns; scheduler queues payments under a `Branch` output of `expected = 100_000` sats (children sum to `100_000` per the `assert_eq!` at line 474).
2. `prepare_send` computes `tx_fee = 5_000`, amortizes it across payments; the branch payment is reduced to `95_000`. `PostFeeBranch { expected: 100_000, actual: Some(95_000) }` is emitted (`processor/src/networks/mod.rs` branch-outputs loop, lines 505-517).
3. `substrate_block` calls `scheduler.created_output(txn, 100_000, Some(95_000))` (`processor/src/multisigs/mod.rs:775`).
4. In `created_output`: `to_amortize = 95_000u64 - 100_000u64` → underflow → `18_446_744_073_709_546_611` (release) or panic (debug).
5. Line 487: `payments_sum (100_000) < to_amortize` → `return`. All child payments queued under the branch are discarded; the branch output of 95_000 sats on-chain is never scheduled for onward payment. Users' burns are permanently unfulfilled.

The intended `to_amortize = expected - actual = 5_000` would have subtracted only the fee from the children and rescheduled `95_000` sats of payments via `self.plans.entry(actual)`.
