### Title
Panic on unregistered `decryptor` in `Decryption::decrypt_with_proof` lets any participant crash a validator with a crafted blame/accusation — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2021-28090's bug class is "remote input reaches an assertion/abort path, killing the node" (TROVE-2021-002). The Serai analog is an unchecked `HashMap` index in the PedPoP blame machinery: `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]`, which panics when `decryptor` has no registered encryption key, aborting the host process during blame verification.

### Finding Description
`Decryption::register` only inserts an entry for participants that submitted an `EncryptionKeyMessage` (commitments round of PedPoP). In `decrypt_with_proof`, after the PoP check, the code verifies the accuser-supplied `EncryptionKeyProof` DLEq against the decryptor's registered key:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```

`self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388` uses `Index` on `HashMap`, which panics on a missing key. The `decryptor` participant index is derived from the accusation/blame message being verified — i.e., the accuser names who the ciphertext was destined for. There is no check that `decryptor` was ever registered.

The same pattern exists at `crypto/dkg/pedpop/src/encryption.rs:356-358`, where `Decryption::register` contains `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")` — a second remote-triggerable abort if a participant's registration is processed twice.

### Impact Explanation
A panic inside PedPoP share verification / blame resolution unwinds through `KeyMachine::calculate_share` / `AdditionalBlameMachine::blame` callers. In the processor, blame verification runs on consensus-provided `VerifyBlame` messages (`processor/src/key_gen.rs:504-549` calls `AdditionalBlameMachine::blame(accuser, accused, ...)` with attacker-named `accuser`/`accused`). A panic there kills the validator's signing/key-gen task — a remote, unprivileged denial of service against a threshold node, directly paralleling directory authorities exiting on an assertion.

### Likelihood Explanation
A malicious participant can trigger it by sending an accusation naming a `decryptor`/`accused` participant that never submitted a DKG commitments message (so no entry exists in `enc_keys`), or any participant index for which registration never ran. The PoP check on `msg` happens before the index, but the accuser can supply a validly-formed `EncryptedMessage` for an arbitrary `from`, so the only requirement is reaching `decrypt_with_proof` with a proof and an unregistered `decryptor`. Cost is one blame transaction; no threshold cooperation required.

### Recommendation
Replace `self.enc_keys[&decryptor]` with a checked lookup, e.g. `let Some(dec_key) = self.enc_keys.get(&decryptor) else { Err(DecryptionError::InvalidProof)? };`, and return `DecryptionError::InvalidProof` for unregistered decryptors. Similarly, replace the `assert!` in `Decryption::register` with a fallible duplicate check or an overwrite policy, since duplicate registration is externally triggerable rather than an internal invariant.

### Proof of Concept
Conceptual, at the library level:

```rust
// Participant `victim` runs a Decryption context where only participants
// {1, 2} registered EncryptionKeyMessages.
let mut dec = Decryption::<Ristretto>::new(context);
dec.register(p1, key_msg_1);
dec.register(p2, key_msg_2);

// Attacker supplies a blame for an EncryptedMessage "from" p1 "to" p3,
// where p3 (the `decryptor`) never registered an encryption key,
// plus a syntactically valid EncryptionKeyProof.
// The msg.pop Schnorr PoP verifies for the attacker's own key, then:
dec.decrypt_with_proof(p1, Participant::new(3).unwrap(), msg, Some(proof));
// => thread panics: "key not found" at self.enc_keys[&decryptor]
```

`Decryption::new`/`register`/`decrypt_with_proof` are `pub(crate)`, so the concrete trigger is via `PedPoP`'s blame path (`AdditionalBlameMachine::blame`, invoked from `processor/src/key_gen.rs` `CoordinatorMessage::VerifyBlame` handling), where `accused`/`accuser` are taken directly from the consensus message without checking registration.

Uncertainty note: I could not fully trace `pedpop/src/lib.rs`'s `blame`/`AdditionalBlameMachine` to confirm whether it filters `decryptor`/`accused` against `enc_keys` before calling `decrypt_with_proof`; if it does validate membership, the panic is unreachable from that path and this analog should be downgraded. The `assert!` in `register` is independently suspicious for the same bug class if registration can be invoked per-message rather than per-unique-participant.
