# [High] `CallDispatcher.dispatch()` is a fully unauthenticated entrypoint that pays out attacker-chosen calls from a shared, value-holding contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary

The Marginswap report's core broken invariant is: *a function that moves protocol-custodied value/executes arbitrary target calls has no caller restriction and no validation of the call targets/contents, letting anyone drive the protocol's funds/contract calls*. The direct Hyperbridge analog is `CallDispatcher.dispatch()`, which is `external` with **no access-control modifier whatsoever** and blindly executes an attacker-supplied `Call[]` (arbitrary `to`, `value`, `data`) using the `CallDispatcher` contract's own balance as source funds.

### Finding Description

`CallDispatcher` is a shared execution-proxy contract used by multiple HyperApp modules (`IntentGatewayV2`/`IntentsBase._execute`, `HyperFungibleToken.onAccept`) to run "untrusted" calldata attached to cross-chain orders/messages: [1](#0-0) 

Its `dispatch(bytes memory encoded)` function:
- has **no `msg.sender` / caller check** at all (unlike `EvmHost.dispatchIncoming`, which is gated with `restrict(_hostParams.handler)`, see [2](#0-1) ),
- decodes an arbitrary `Call[]` from raw calldata supplied by the caller,
- only checks that `to` has code (`extcodesize`), never that `to`/`value`/`data` are consistent with any expected order or with the calling application,
- executes `to.call{value: call.value}(call.data)` using **the CallDispatcher contract's own ETH balance**, and
- accepts ETH from anyone via `receive() external payable {}` (line 39).

Compare this to `IntentsBase._execute`, which is the *intended* caller of `dispatch()`: [3](#0-2) 

`_execute` calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` and then sweeps back any residual token/ETH balance left in the dispatcher as "dust." This design assumes `CallDispatcher` is only ever driven by the trusted gateway contract, and that any balance transiently sitting in `CallDispatcher` belongs to whichever order is currently being executed. But because `dispatch()` itself is public and unauthenticated, and `CallDispatcher` is a **shared singleton** used by multiple gateway/app instances, **any external account can call `CallDispatcher.dispatch()` directly**, supplying `Call({to: attacker, value: dispatcher.balance, data: ""})` to drain whatever ETH balance the contract currently holds — before the legitimate gateway's own sweep step ever executes.

This is structurally identical to the Marginswap finding: a value-moving/arbitrary-call function with (1) no caller check, (2) no validation of the target/contents of the calls, and (3) fully attacker-constructable "pairs" (here, `Call.to`), enabling execution of self-constructed code that can move funds out of the protocol's shared contract.

### Impact Explanation

Any ETH that is transiently or accidentally present in `CallDispatcher` — e.g., ETH sent directly via its permissionless `receive()`, or a residual balance between the moment an app funds it (to cover `order.output.call`'s `value` fields) and the moment `_execute`'s sweep step runs — is stealable by an unprivileged attacker who front-runs the legitimate flow with a direct call to `dispatch()`. Since `CallDispatcher` is shared across every gateway instance configured to use it, this is not confined to a single app's internal accounting: it is a shared custody surface with zero entry checks. This matches the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" impact categories and requires no malicious relayer, prover, or admin — only a public transaction from any address.

### Likelihood Explanation

High for any window in which `CallDispatcher` holds a non-zero ETH balance: the `receive()` function is unconditionally payable by anyone, and the contract has no way to distinguish "funds temporarily staged for an in-flight order's calldata" from "funds an attacker is free to take." An attacker only needs to monitor the contract's balance (e.g., via mempool-level observation of transactions that fund the dispatcher before calling `dispatch()`) and front-run with their own `dispatch()` call.

### Recommendation

- Restrict `CallDispatcher.dispatch()` to a whitelist of authorized callers (e.g., an `onlyAuthorizedApp` modifier configured per deployment, mirroring `EvmHost`'s `restrict(_hostParams.handler)` pattern), or
- Avoid pre-funding the shared `CallDispatcher` with value at all — instead deploy per-order/per-call ephemeral executors, or require the caller to pass `value` directly in the same call rather than relying on a resident balance, and
- Ensure the contract cannot accumulate value between transactions (remove the permissionless `receive()`, or sweep-and-revert if any balance persists after `dispatch()` returns).

### Proof of Concept

1. Any user/attacker sends ETH directly to the `CallDispatcher` contract address (accepted unconditionally by `receive()` at [4](#0-3) ), or observes a pending transaction that is about to fund the dispatcher ahead of an `order.output.call` execution.
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: attackerAddress, value: currentBalance, data: ""})]))` directly — no permission is required per [5](#0-4) .
3. The call succeeds (`attackerAddress` has no code requirement to receive plain ETH), draining the ETH currently held by `CallDispatcher` to the attacker before the legitimate `_execute`/sweep flow in `IntentsBase` ( [6](#0-5) ) ever runs.

Note: I was not able to fully trace, within the available index, the exact upstream step that pre-funds `CallDispatcher` with ETH before `_execute` calls `dispatch()` (e.g., the `predispatch` flow in `placeOrder`), since that portion of `IntentGatewayV2.sol` was not fully retrievable in this session. The core vulnerability — `dispatch()` having zero caller/content authentication and paying out of the contract's own balance — is directly confirmed in `evm/src/utils/CallDispatcher.sol`. A Devin session with full file access should verify the exact funding path to size the maximum stealable balance in the worst case.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
