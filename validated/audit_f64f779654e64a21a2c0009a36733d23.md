### Title
Silent origin-remote hijack via loosely-validated GitHub API `clone_url` in `updateRemoteUrl` - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The reviewed report describes a class of bug where a value that is supposed to be validated against a strict invariant before being trusted (`incentiveRate`) is instead accepted under an under-constrained check, letting an attacker redirect value flow to themselves. The closest reachable analog in GitHub Desktop is `updateRemoteUrl`, which silently rewrites a user's `origin` remote URL based on a GitHub API-supplied `clone_url`, but only checks that the URL *protocol* (https/ssh) is unchanged — not that the *host/owner/repo* actually still refers to the same trusted destination. This creates a path where a repository-name-squatting or repo-transfer scenario ("attacker controls a GitHub API object") can cause Desktop to silently repoint a victim's `origin` remote to an attacker-controlled repository, corrupting where the user's future pushes go, with no user confirmation.

### Finding Description
`updateRemoteUrl` is invoked automatically during `repositoryWithRefreshedGitHubRepository`, which runs on routine repository refresh: [1](#0-0) 

It calls `api.fetchRepository(owner, name)` using the **locally stored** `owner`/`name` strings (not a stable numeric repository ID), and then feeds the resulting `apiRepo.clone_url` straight into `updateRemoteUrl`: [2](#0-1) 

The only safeguards before Desktop silently calls `gitStore.setRemoteURL(...)` are:
1. `remoteUrlUnchanged` — the *current* remote URL still matches the *previously cached* `gitHubRepository.cloneURL`.
2. `protocolsMatch` — the URL **protocol** (e.g. `https`) of the old and new URL are the same.
3. `!urlsMatch` — the new URL differs from the current one.

Crucially, `protocolsMatch` only compares the URL scheme via `URL.parse(...).protocol`, not the hostname, owner, or repository name. There is no check that the new `clone_url`'s hostname/owner/repo actually correspond to the same trusted GitHub entity as before — `urlMatchesRemote` is only used to detect whether the URL is *unchanged*, not to gate whether the swap is *safe*.

This differs from the explicit "Upstream Already Exists" flow, where changing a remote is surfaced to the user via a confirmation dialog: [3](#0-2) 

`updateRemoteUrl`, by contrast, performs the rewrite with **no user interaction at all**.

Because the lookup key is `owner/name` (strings), if the originally-tracked repository is renamed, deleted, or transferred away and a different (attacker-controlled) repository is subsequently created/renamed to occupy that exact `owner/name` slot (a well-known "repo/org name-squatting" pattern on GitHub), the next background refresh's `api.fetchRepository(owner, name)` call will legitimately return the squatter's `clone_url` from the real GitHub API — this is "attacker controls a GitHub API object" in the sense that the attacker can arrange for the API to return an object of their choosing for that owner/name, without compromising GitHub itself. `updateRemoteUrl`'s weak `protocolsMatch`-only gate then treats this as an acceptable update and silently retargets the user's `origin` remote to the attacker's repository.

### Impact Explanation
If exploited, a user's local `origin` remote is silently corrupted to point at an attacker-controlled repository while retaining the same protocol, so the app's own UI (which trusts `gitStore.defaultRemote`) shows nothing alarming. Subsequent `git push` operations initiated from Desktop will silently push the user's commits/history to the attacker's repository instead of the intended one. This matches the "silent corruption of what the user commits or pushes" impact category. It could also be leveraged for information disclosure (private code, commit history) since the user is pushing directly to attacker infrastructure believing it is their own repository's remote.

### Likelihood Explanation
This requires a specific precondition (the originally tracked GitHub `owner/name` becomming re-associated with a different repository the attacker controls — e.g., via repo/org deletion+re-registration or a rename race), which is a known, previously documented risk pattern for GitHub-integrated tools ("repo-jacking"), not something requiring local/physical access, admin rights, prior malware, or leaked credentials. It does require that the victim's repository slug become available for takeover, which is a real but non-trivial precondition — likelihood is moderate rather than trivially exploitable on demand.

### Recommendation
In `updateRemoteUrl` (and similarly in `_convertRepositoryToFork`/`ensureUpstreamRemoteURL`), do not gate the automatic remote rewrite on protocol equality alone. Instead, either:
- Require an explicit user confirmation (similar to the `UpstreamAlreadyExists` dialog) any time the resolved GitHub repository's owner/name/host changes, not just when the raw URL string differs, or
- Anchor the trust decision to a stable identifier (the GitHub repository's numeric `id`) rather than `owner`/`name` strings, and refuse to silently update remotes if the numeric repository ID associated with the endpoint has changed since the remote was last confirmed by the user.

### Proof of Concept
1. User adds/clones a GitHub repository `victim/repo` in Desktop; Desktop stores `gitHubRepository.cloneURL = https://github.com/victim/repo.git` and `origin` remote equal to that URL.
2. `victim/repo` is later deleted or renamed away (e.g., account transfer), freeing the `victim/repo` slug.
3. Attacker creates a new repository at the now-available `victim/repo` slug with `clone_url = https://github.com/victim/repo.git` (same protocol/host string form, but now backed by attacker's content).
4. On the next periodic refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('victim', 'repo')`, which legitimately returns the attacker's new repository object as `apiRepo`.
5. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (still matches previously cached cloneURL) and `protocolsMatch === true` (both `https`), and silently calls `gitStore.setRemoteURL('origin', apiRepo.clone_url)`.
6. The user's next `git push` from Desktop pushes to the attacker's repository, with no warning shown, as verified by the existing unit test asserting the URL update succeeds silently: [4](#0-3)

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
