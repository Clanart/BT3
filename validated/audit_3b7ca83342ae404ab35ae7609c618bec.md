### Title
Fee and weight estimation omits the OP_RETURN data output, producing an undersized `needed_fee` and an unchecked oversized transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output to `tx_outs` when `data` is supplied, but then computes the transaction's weight/vbytes via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only reconstructs outputs from `payments` — never the data output. All downstream accounting (`needed_fee`, the `TooLowFee` minimum-relay check, the `NotEnoughFunds` check, the change-output value, and the `MAX_STANDARD_TX_WEIGHT` check) therefore operates on a transaction smaller than the one actually built and signed. This is the same class as the reference bug: the accounting routine is fed the wrong set of outputs, so cost estimation diverges from the real transaction.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, the OP_RETURN output is pushed onto `tx_outs`. Immediately after, at line 204, weight/vbytes are computed from `payments` only:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62-94) builds its dummy `Transaction` with `output` mapped exclusively from `payments` (plus optionally `change` at lines 95-99). The `data` output — up to 80 bytes of payload inside a script push, i.e. roughly 90+ serialized bytes / ~360+ weight units / ~90 vbytes — is absent from every estimate:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are understated.
- The minimum-relay check at line 211 uses the understated `vbytes`, so it can certify a fee that is below `DEFAULT_MIN_RELAY_TX_FEE` for the real transaction size.
- The change amount `input_sat - (payment_sat + fee_with_change)` (line 228) is inflated by the unpaid fee for the data output; the signed transaction's effective feerate is lower than `fee_per_vbyte`, potentially below relay minimum, making the broadcast transaction non-standard/unrelayable.
- `needed_fee()` (line 133) reports the understated fee, so callers comparing `fee()` vs `needed_fee()` see a mismatch only in the over-paid direction absorbed by change.
- The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 is evaluated on the weight without the data output, so a transaction near the 400,000 WU boundary can pass construction while the signed transaction exceeds the standardness limit and is rejected by the network.

### Impact Explanation
When `data` is specified alongside `change`, the resulting transaction pays an effective feerate strictly below the requested `fee_per_vbyte`; for marginal fee rates this drops below `DEFAULT_MIN_RELAY_TX_FEE`, and for boundary-size transactions the real weight can exceed `MAX_STANDARD_TX_WEIGHT`. In both cases the threshold-signed transaction is invalid for relay — the funds move only if the transaction is rebuilt, and the change output embeds an incorrect amount relative to the accounted fee. Additionally `needed_fee()` misreports the fee to any caller (e.g. fee amortization logic) that relies on it being accurate for the produced transaction.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with `data: Some(..)`; the `data` argument is attacker/controllable bytes (up to 80 bytes after the `TooMuchData` check) in any integration that exposes OP_RETURN embedding. The mis-estimation is proportional to the data length, so a maximal 80-byte payload produces the largest discrepancy (~90 vbytes of unaccounted size). In Serai's own processor usage `data` is always `None`, so the defect only manifests for direct consumers of the `bitcoin-serai` wallet API who attach data or who request feerates/size near policy boundaries.

### Recommendation
Pass the actual output set (including the OP_RETURN output) into `calculate_weight_vbytes`, or add a `data_len`/`Option<&ScriptBuf>` parameter so the dummy transaction includes the data output. Concretely: build `tx_outs` first, then compute `(weight, vbytes)` from `&tx_outs`, and repeat that for the with-change variant so `needed_fee`, the relay-fee check, the change value, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed.

### Proof of Concept
```rust
// networks/bitcoin SignableTransaction with an OP_RETURN output.
let data = vec![0u8; 80]; // maximal allowed payload
let tx = SignableTransaction::new(
    vec![output],            // one ReceivedOutput
    &[(payment_script, 546)],
    Some(change_script),     // change absorbs the leftover
    Some(data.clone()),
    fee_per_vbyte,
).unwrap();

// The constructed transaction has an extra OP_RETURN output (~91 serialized bytes,
// ~364 weight units) that was never included in `vbytes`.
let real_vsize = tx.transaction().vsize() as u64;
let accounted = tx.needed_fee() / fee_per_vbyte;
assert!(real_vsize > accounted); // ~90 vbytes unaccounted

// Effective feerate of the signed TX is below the requested rate:
let effective_rate = tx.fee() as f64 / real_vsize as f64;
assert!(effective_rate < fee_per_vbyte as f64);
// For fee_per_vbyte == 1 sat/vb this drops the real feerate below
// DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvb), producing an unrelayable TX,
// and a boundary-sized TX bypasses the MAX_STANDARD_TX_WEIGHT check at
// send.rs:241 since `weight` excludes the OP_RETURN output.
```
