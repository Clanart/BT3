### Title
Transaction-fee escrow credited with nominal `order.fees` instead of actual tokens received - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`placeOrder()` in `IntentGatewayV2.sol` carefully measures the *actual* balance delta received for every escrowed input token — protecting against fee-on-transfer/deflationary tokens — but the transaction-fee leg (`order.fees`, paid in the Hyperbridge `feeToken`) skips this check and credits the full nominal amount to internal accounting, exactly the "approve/transfer nominal amount but real balance is smaller" pattern from the seed report.

### Finding Description
For every escrowed input, the contract snapshots the gateway's balance before `safeTransferFrom` and derives the escrow credit from the balance delta: [1](#0-0) 

This is the exact mitigation for fee-on-transfer tokens — confirmed by the dedicated test suite covering FOT tokens in `placeOrder`: [2](#0-1) 

But the fee-token leg, paid a few lines later in the same function, does no such measurement — it transfers `order.fees` via `safeTransferFrom` and then unconditionally records the nominal `order.fees` value as the liability owed on withdrawal: [3](#0-2) 

That liability is later paid out at settlement/withdrawal time by transferring exactly the recorded (nominal) amount out of the gateway's real feeToken balance: [4](#0-3) [5](#0-4) 

If the governance-configured `feeToken` (`IDispatcher(hostAddr).feeToken()`) is, or is ever migrated to, a token with non-1:1 transfer semantics (fee-on-transfer, deflationary burn, rebasing), the gateway will hold strictly less of the fee token than `_orders[commitment][TRANSACTION_FEES]` records across all outstanding orders. This is precisely the broken invariant from the seed report: a downstream consumer (`initiateAuction`/here, `withdraw`/`_withdraw`) is given a nominal accounting value that assumes 1:1 transfer, while the actual token movement can be less.

### Impact Explanation
Because every order's fee credit is inflated relative to real balance, the aggregate liability recorded in `_orders[*][TRANSACTION_FEES]` across all pending orders can exceed the gateway's true feeToken balance. Whichever order's beneficiary calls `withdraw`/`onAccept` first drains real balance to satisfy their nominal credit; later beneficiaries' `safeTransfer(beneficiary, fees)` calls then revert (funds locked, `withdraw` cannot finalize the order, escrow release is blocked) — a direct case of fund loss/lock on settlement for a subset of legitimate order beneficiaries, matching the bounty's "loss of funds"/"false state acceptance of a solvency invariant" class.

### Likelihood Explanation
This does not require a malicious peer, relayer, or governance actor — it is purely a property of whichever ERC-20 is configured as the network-wide Hyperbridge `feeToken`. The likelihood is conditional (like the seed report's "if the EasyAuction owner changes the fee") on the feeToken having non-standard transfer semantics, which is plausible over the life of a multi-chain deployment (fee tokens can be swapped via governance, or a chain's canonical stablecoin could carry blacklist/fee logic). Given the code already anticipates and defends against exactly this class of token for the input-asset leg, the omission on the fee leg is a real, provable inconsistency in the same function.

### Recommendation
Apply the same balance-delta measurement used for `order.inputs` to the `order.fees` transfer: snapshot the feeToken balance before `safeTransferFrom`, and set `_orders[commitment][TRANSACTION_FEES]` to the actual received delta rather than the nominal `order.fees`, mirroring the pattern at lines 289–291.

### Proof of Concept
1. Governance sets `feeToken` to a token with a 1% transfer fee (or any token whose `transferFrom` delivers less than the requested amount).
2. User A calls `placeOrder` with `order.fees = 1000`; the gateway executes `safeTransferFrom(user, this, 1000)` but only actually receives 990 tokens; `_orders[commitmentA][TRANSACTION_FEES]` is nonetheless set to `1000`.
3. User B similarly places an order with `order.fees = 1000`, actually contributing 990; total real feeToken balance held by the gateway is 1980, but total recorded liability is 2000.
4. Order A settles first: `withdraw`/`_withdraw` calls `feeToken.safeTransfer(beneficiaryA, 1000)`, succeeding and leaving the gateway with `1980 - 1000 = 980`.
5. Order B settles: `feeToken.safeTransfer(beneficiaryB, 1000)` reverts (insufficient real balance), permanently blocking finalization/escrow release for order B's beneficiary.
