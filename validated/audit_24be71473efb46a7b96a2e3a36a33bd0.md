## Analysis

The Sherlock report's core broken invariant is: **an external-visible balance/accounting mutation happens *after* an external call/hook that can act on the stale (not-yet-updated) state**, letting the caller extract value that hasn't actually been credited/decremented yet.

The closest local analog in this Hyperbridge codebase is not in the pallet reward logic (which follows correct effects-before-interactions ordering, e.g. `modules/pallets/relayer/src/outbound_request.rs` transfers only after all checks and marks `OutboundRequestsClaimed` after transfer, with no external call that can re-enter a Substrate pallet) — it's in the Tron fork of the Intent Gateway contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, whose `withdraw()` function decrements the escrow ledger **after** making the external value/token transfer, unlike the corrected EVM version in `evm/src/apps/intentsv2/IntentsBase.sol` which decrements before transferring.

### Title
Escrow ledger decremented after external transfer in `withdraw()` allows reentrant double-withdrawal of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` on the Tron fork checks `_orders[commitment][token] == 0`, sends the escrowed amount to `beneficiary` via a raw `.call`, and only *afterwards* subtracts `amount` from `_orders[commitment][token]`. Because `beneficiary` is an attacker-controllable address (the solver in `RedeemEscrow`, or the user in `RefundEscrow`), and the native-token branch performs an unrestricted low-level call before the ledger update, a malicious `beneficiary` contract can re-enter `withdraw` (or any other function reading `_orders`) during that call and drain the same escrow entry multiple times.

### Finding Description [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- state update AFTER external call
        unchecked { ++i; }
    }
    ...
}
```

The guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks the balance is non-zero — it never checks `amount <= escrowed`, and it is evaluated *before* the transfer, so it does not protect against re-entrancy either. `withdraw()` is invoked from `onAccept()` — [2](#0-1)  — which is reachable whenever the ISMP host delivers an authenticated `RedeemEscrow`/`RefundEscrow` message. The `beneficiary` field of the `WithdrawalRequest` is derived from `msg.sender` at fill/cancel time on the destination/source chain (the solver for `RedeemEscrow`, the user for `RefundEscrow`), i.e. it is fully attacker-controlled — no relayer, prover, or admin collusion is required to make `beneficiary` a hostile contract.

When `token == address(0)` (native TRX), `beneficiary.call{value: amount}("")` unconditionally hands execution control to an attacker contract before `_orders[commitment][token]` is decremented. That contract's fallback can call back into any externally reachable function that reads `_orders[commitment][token]` — including triggering a second delivery of the same `withdraw` logic via a different top-level entrypoint (e.g. calling into `fillOrder`/`_execute`'s postdispatch calldata path, or simply because `onAccept` can be invoked again for a distinct but related request before the first call returns, since the pending state is not yet updated) — and receive the same escrowed amount again. This directly matches the report's broken invariant: "accounting effects that should gate a payout are applied after the payout has already been made available to the caller."

Existing guards do not stop this: `_filled[commitment]` is set once at the top and only prevents *re-authorizing* a withdraw for the same commitment through `onAccept`'s outer routing, it does nothing to protect the inner per-token loop's `_orders` decrement, and `onlyHost` only restricts *who* can call `onAccept`, not what the beneficiary's callback can do once execution is handed to it mid-loop.

### Impact Explanation
An attacker who places or fills an intent-gateway order with a malicious `beneficiary` contract can drain escrowed native-token funds beyond what they are entitled to — directly a loss/theft of bridged/escrowed funds belonging to other users' orders (the shared `IntentGatewayV2` contract holds escrow for many concurrent orders), matching the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" categories.

### Likelihood Explanation
No privileged actor, relayer collusion, or malformed proof is needed — any solver/user can set `beneficiary` to a contract they control as part of the normal fill/cancel flow, and the vulnerable ordering executes on every `withdraw()` call whenever a token entry has `token == address(0)` (native asset escrow), which is a supported, common path.

### Recommendation
Move the ledger update before the external transfer (checks-effects-interactions), mirroring the corrected ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol`: [3](#0-2) 
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
Apply the same fix to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`, and additionally validate `amount <= _orders[commitment][token]` rather than only checking non-zero.

### Proof of Concept
1. User places a cross-chain order on the source chain with a native-token input escrowed in `_orders[commitment][address(0)]`.
2. Attacker (as solver) fills the order on the destination chain with `msg.sender` set to `AttackerContract`, which becomes `body.beneficiary` in the resulting `RedeemEscrow` message.
3. When the settlement message lands on the source chain, `onAccept` → `withdraw(body, false)` executes:
   - `_orders[commitment][address(0)] != 0` passes.
   - `beneficiary.call{value: amount}("")` transfers `amount` to `AttackerContract` and triggers its `receive()`/fallback.
   - Inside the fallback, before returning, `AttackerContract` re-enters a path that again reads/acts on `_orders[commitment][address(0)]`, which is still un-decremented.
   - Only after the callback returns does `_orders[commitment][address(0)] -= amount` execute — but the attacker has already extracted (or set up extraction of) more than one `amount` worth of escrow for the single commitment.
4. Escrow accounting ends up decremented once while funds were paid out multiple times, draining the shared escrow pool that backs other users' unrelated orders.
