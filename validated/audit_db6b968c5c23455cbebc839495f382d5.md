## Finding: Valid — Stale-Precision / Decimals TOCTOU in `convert_to_balance`

### Title
Divisor Underflow to `10^0` in `convert_to_balance` via Post-Registration Asset Decimals Change - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The invariant `erc_decimals >= local_decimals` is enforced only once, at `register_token`/`update_token` time, but `on_accept` and `on_timeout` re-derive `local_decimals` live from the asset's current metadata on every message. If the underlying asset's `decimals` metadata increases after registration, the stale `erc_decimals` stored in `Precisions` can become smaller than the live `local_decimals`, causing the scaling divisor in `convert_to_balance` to collapse to `1` and the raw ERC20 `U256` value to be parsed directly as the local balance.

### Finding Description
`register_token` and `update_token` validate the precision invariant only at write time: [1](#0-0) 
This check compares `config.decimals` (which becomes `Precisions`) against `local_decimals`, computed at that moment from `fungibles::metadata::Inspect::decimals`: [2](#0-1) 

However, in the message-processing paths (`on_accept` and `on_timeout`), `decimals` is **not** the value validated at registration — it is fetched live from the asset's current metadata each time a message is processed: [3](#0-2) [4](#0-3) 

`Precisions::<T>` (the `erc_decimals` used for scaling) is fixed at registration and only updated by a subsequent privileged `update_token` call: [5](#0-4) 

`convert_to_balance` computes the divisor as `10^(erc_decimals.saturating_sub(local_decimals))`: [6](#0-5) 
If `local_decimals > erc_decimals` (stale), `saturating_sub` returns `0`, so the divisor is `10^0 = 1`, and the raw ERC20 `U256` amount is parsed directly as the local balance without any down-scaling — inflating the resulting balance by `10^(local_decimals - erc_decimals)`.

The gap is a classic time-of-check/time-of-use issue: the registration-time check assumes `local_decimals` is immutable, but for non-native assets, `local_decimals` is sourced from the generic `Config::Assets` metadata provider (e.g., `pallet_assets`), whose `decimals` metadata field can be mutated independently of this pallet's `CreateOrigin` governance (e.g., by the asset's own `Owner`/`Issuer` account via `set_metadata`), if such asset was permissionlessly created and is owned by an account distinct from the bridge's governance origin.

### Impact Explanation
If exploitable, this would allow massive over-minting or over-transfer of funds from `pallet_account` custody on `on_accept`/`on_timeout` processing — an unrelated party could receive `10^(local_decimals - erc_decimals)` times the intended amount, draining escrowed custody funds or minting an inflated non-native asset supply, matching the bounty's "stealing or loss of funds" / "wrongful asset movement" impact category.

### Likelihood Explanation
This requires: (1) an asset registered in this pallet whose decimals metadata is *not* under the same governance control as the pallet's `CreateOrigin` (e.g., a permissionlessly created `pallet_assets` asset owned by its creator), and (2) that owner subsequently calling `set_metadata` (or equivalent) to raise `decimals` above the registered `erc_decimals`. I was not able to fully verify, within the available tool budget, whether the actual runtime configuration (`gargantua`/`nexus`) permits permissionless asset creation/ownership separate from the HFT pallet's `CreateOrigin`, or whether `Config::Assets` is restricted such that only the same governance origin that calls `register_token` can also alter decimals (which would make this unexploitable by an unprivileged party). This is the key open question that determines whether this crosses into "requires a privileged operator" territory excluded by the bounty's decision standard.

### Recommendation
- Cache `local_decimals` at registration time inside `Precisions` (or a parallel storage item) rather than re-reading live asset metadata in `on_accept`/`on_timeout`, so the validated invariant cannot silently drift.
- Alternatively, re-validate `erc_decimals >= local_decimals` inside `convert_to_balance`'s call sites and return a hard error (e.g., reuse `ErcDecimalsBelowLocal`) instead of using `saturating_sub`, which masks the underflow instead of failing safely.

### Proof of Concept
1. Register a non-native asset `A` with `local_decimals = 6` and `erc_decimals = 18` via `register_token` (passes the `config.decimals >= local_decimals` check).
2. Separately (assuming `Config::Assets` permits it), change asset `A`'s metadata `decimals` field to `20` via a call not gated by this pallet's `CreateOrigin`.
3. Relay an `on_accept` message carrying a raw ERC20 `U256` amount scaled for 18 decimals.
4. `convert_to_balance` computes `erc_decimals.saturating_sub(local_decimals) = 18u8.saturating_sub(20u8) = 0`, so divisor becomes `1`; the full raw `U256` value is minted/transferred instead of the intended `value / 10^12`, inflating the payout by `10^12`. [6](#0-5)

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```
