Confirmed: in `withdraw()` and the `SweepDust` handler of `evm/tron/contracts/apps/IntentGatewayV2.sol`, the code makes a raw low-level `.call()` with the ERC20 `transfer` selector and only checks that the *call itself* did not revert (`success`), but never decodes/validates the boolean payload the token contract returns.### Title
Escrow release/refund/dust-sweep accepts non-reverting `transfer()` failures on Tron `IntentGatewayV2` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) as the EVM sibling contract does, but the intent-settlement paths — `withdraw()` (escrow release/refund) and the `SweepDust` handler inside `onAccept()` — do not use `safeTransfer`. Instead they perform a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the external call did not revert (`success`), without decoding and validating the boolean return payload the ERC20 standard requires. This is the same broken invariant as the H01 report: the code checks that an external accounting operation "did not error at the call level" but ignores the actual success/failure signal returned by that operation, and treats the operation as fully settled regardless.

### Finding Description
In `withdraw()`: [1](#0-0) 
the escrowed balance `_orders[body.commitment][token]` is decremented unconditionally once `success` is true, even if the token's `transfer()` function internally returned `false` (a non-compliant but not-uncommon ERC20 behavior, e.g. tokens that return `false` on insufficient balance/paused state rather than reverting).

The same pattern repeats for transaction-fee redemption: [2](#0-1) 
and for the host-authorized dust-sweep path: [3](#0-2) 

By contrast, the maintained EVM contract for the same protocol logic (`evm/src/apps/intentsv2/IntentsBase.sol`) uses `IERC20(token).safeTransfer(beneficiary, amount)`, which decodes and requires the boolean return value: [4](#0-3) 

Because the Tron variant substitutes `SafeERC20.safeTransfer` with a manual low-level call that inspects only the outer call-success flag, the internal escrow accounting (`_orders[commitment][token]`, `_filled[commitment]`) is marked as settled (funds released, refunded, or swept) even when the underlying token transfer silently failed and returned `false`. This is functionally identical to the Compound `NO_ERROR` bug: an operation's own success code is ignored, and the caller proceeds as if it succeeded.

`withdraw()` is reached from `onAccept()` for `RequestKind.RedeemEscrow`/`RefundEscrow` (an ISMP `onlyHost`-gated but attacker-influenced, message-driven path since the request body/commitment/token list originates from the escrow-fill flow on the counter chain) and from `onGetResponse()` for cancellation refunds. In all three call sites the escrow debit/mark-as-filled state transition is irreversibly committed before/without any confirmation that the beneficiary actually received the tokens.

### Impact Explanation
This breaks the "moves exactly once and only to the rightful beneficiary and amount" guarantee for escrowed assets required by the intent-settlement flow. If a token that returns `false` on failed transfer (rather than reverting) is escrowed, `withdraw()` will mark the commitment as filled/refunded and zero out `_orders[commitment][token]` while the tokens remain stuck in the `IntentGatewayV2` contract — the beneficiary receives nothing and the accounting states the transfer succeeded, i.e. permanent loss of escrowed user funds for the affected token with no revert protection, and no path to retry (since `_filled` is already set and the escrowed amount already decremented to zero).

### Likelihood Explanation
The trigger condition depends on which tokens are configured for the intents system supporting `false`-returning-on-failure ERC20 semantics (a known real-world token category, e.g. some old/USDT-like or custom tokens). No malicious relayer, prover, or admin is required — the flow executes through the standard, already-authenticated `onAccept`/`onGetResponse` intent-settlement message handling; the only requirement is that the escrowed token can return `false` instead of reverting under some condition (e.g., paused, blacklist, insufficient allowance/balance edge cases), which is plausible for any non-audited or non-OZ ERC20 listed as an escrow asset.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, fee redemption, and `SweepDust` handling) with `IERC20(token).safeTransfer(...)`, consistent with `SafeERC20` already being imported and used elsewhere in the same file, mirroring the checked pattern already present in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Configure/escrow an ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., paused state, internal blacklist, or an edge-case balance check) as an input/output asset for an intent order on the Tron deployment.
2. Have the order proceed through normal fill/settlement so that an ISMP `RedeemEscrow` (or `RefundEscrow`) request reaches `onAccept()` → `withdraw()` on `evm/tron/contracts/apps/IntentGatewayV2.sol`.
3. Arrange for the token's `transfer()` call to return `false` at settlement time (e.g., the token contract is paused by its own admin, or a balance/allowance edge case triggers a `false` return rather than revert) — the low-level `.call` still succeeds (`success == true`) because the call itself executes without reverting.
4. `withdraw()` at lines 693-699 does not detect the `false` return value, decrements `_orders[body.commitment][token]` to zero, and sets `_filled[body.commitment] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded` — the escrowed tokens remain locked in the contract while accounting states settlement occurred, and the beneficiary cannot re-claim since the commitment is now considered filled.
