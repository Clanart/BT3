## Finding

### Title
Order creator can use a malicious/blacklist-capable input token to permanently brick `withdraw()`, stealing solver-delivered output while locking escrow forever - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` iterates over every token in an order's escrow and reverts the **entire** call if any single token transfer fails [1](#0-0) . Because `order.inputs` (the escrowed token list) is chosen freely by the order creator at `placeOrder` time, a malicious user can include a token they control the "blacklist"/callback logic of. After a solver honestly delivers real output tokens on the destination chain (triggering a cross-chain `RedeemEscrow`), the creator blacklists the solver's address on the poisoned token; every future call to `withdraw()` for that commitment then reverts on that one token's `.call()`, permanently blocking release of the *entire* escrow bundle - including the other, non-malicious tokens and the accrued fee - to the solver, and equally blocking refund via `cancelOrder`'s same-chain path, since it also routes through `withdraw()`.

### Finding Description
`withdraw()` performs a raw low-level call per escrowed token and hard-reverts on failure, with the escrow decrement (`_orders[...] -= amount`) applied only *after* the external call succeeds: [2](#0-1) 

This function is the sole settlement path for:
- `onAccept` handling `RedeemEscrow`/`RefundEscrow` messages from the counterparty chain (`onlyHost`) [3](#0-2) 
- `onGetResponse` for cancellation refunds [4](#0-3) 
- `cancelOrder`'s same-chain branch [5](#0-4) 

`order.inputs` — the exact set of tokens iterated in `withdraw()` — is fully attacker-controlled by whoever calls `placeOrder`; there is no allowlist check on escrowed token addresses. If one of those tokens implements a callback/blacklist mechanism the order creator controls (e.g., a pausable/blacklistable ERC20 clone, or a token that reverts for a chosen recipient), the creator can:
1. Place a cross-chain order whose inputs include one "poison" token alongside legitimate tokens.
2. Let a solver fill the order on the destination chain, delivering real value to the beneficiary and triggering the `RedeemEscrow` dispatch back to source.
3. Before/when the `RedeemEscrow` message lands on source and `onAccept` calls `withdraw()`, blacklist the solver's address on the poison token.
4. Every subsequent `withdraw()` call for that commitment reverts on the poison token's `.call()` (`TransferFailed`), so **none** of the escrowed tokens (including the healthy ones) nor the transaction fee are ever released to the solver, and `cancelOrder`/refund is equally bricked since it shares the same `withdraw()` code path.

This exactly mirrors the seed report's core invariant break: a single callback/blacklist-capable award token lets one party block payout for everyone sharing that settlement transaction, with no mechanism for "other winners" (here, the other escrowed tokens/fees in the same order) to be withdrawn independently.

### Impact Explanation
The solver, an honest counterparty who already delivered real assets on the destination chain, permanently loses the compensation they were promised, and the escrow becomes permanently locked (unrefundable to the user, unclaimable by the solver) — a direct, attacker-profitable fund loss/lock reachable via a normal unprivileged `placeOrder` call, satisfying the "stealing or loss of funds" / "logic attack" bar in the impact gate.

### Likelihood Explanation
No privileged role, relayer/prover misbehavior, or governance action is required. The only precondition is that the order creator controls a token contract with revert-on-demand semantics (trivial to deploy) and includes it as one of several `order.inputs`. Solvers fill orders based on visible output/fee economics and have no way to inspect at fill-time whether the escrowed input list contains a poison token that will later be blacklisted for their address specifically.

### Recommendation
Make per-token settlement independent: wrap each token transfer in `withdraw()` so a failure on one token doesn't revert the release of the others (e.g., catch failures and move the failed amount to a per-token, per-beneficiary pull-payment ledger rather than reverting the whole loop). Additionally consider validating escrowed input tokens against an allowlist or disallowing tokens with admin-controlled transfer restrictions, consistent with the seed report's recommendation to disallow callback/permission-gated tokens from being used as settlement assets.

### Proof of Concept
1. Attacker deploys `PoisonToken` (ERC20-like) with an admin-settable `blacklist(address)` that makes `transfer` to a blacklisted address revert.
2. Attacker calls `placeOrder` with `order.inputs = [PoisonToken, DAI]`, escrowing both.
3. A solver calls `fillOrder` on the destination chain, delivering the required output tokens to the beneficiary and triggering the `RedeemEscrow` dispatch.
4. Before the `RedeemEscrow` message is processed by `onAccept` on source, attacker calls `PoisonToken.blacklist(solver)`.
5. `onAccept` → `withdraw()` loop hits `PoisonToken.transfer(solver, amount)`, which reverts; `withdraw()` reverts entirely via `if (!success) revert TransferFailed();` [6](#0-5) .
6. Every retry of message delivery (and any `cancelOrder` refund attempt) hits the same revert forever — DAI escrow and fee are permanently locked, and the solver never recovers value for the output tokens already delivered.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
