### Title
ReDoS via attacker-controlled hookify rule 'pattern' hangs PreToolUse/UserPromptSubmit guard on unbounded `regex.search()` - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
`compile_regex()` compiles any `pattern` string taken from a `.claude/hookify.*.local.md` rule file's `pattern`/`conditions[].pattern` field, and `_regex_match()` calls `regex.search(text)` with no timeout, size bound, or complexity check. [1](#0-0) [2](#0-1) 
Rule files are loaded from disk via `load_rules()`/`load_rule_file()` in `config_loader.py`, and the `pattern` value is taken verbatim from YAML frontmatter with no sanitization or length/complexity checks. [3](#0-2) 
If such a rule file is checked out (e.g. from a malicious PR/branch adding `.claude/hookify.evil.local.md`) and the field it targets (`command`, `new_text`, `user_prompt`, etc.) receives attacker- or victim-supplied text of sufficient length, a catastrophic-backtracking pattern such as `(a+)+$` matched against a string like `"a"*40 + "!"` will cause `re.search` to hang the Python process executing the hook (`pretooluse.py`, `userpromptsubmit.py`, etc.), since these scripts call `evaluate_rules()` synchronously with no timeout before printing the JSON decision. [4](#0-3) 

However, the `lru_cache` eviction portion of the question does not hold: each hook invocation (`pretooluse.py`, `userpromptsubmit.py`, `posttooluse.py`, `stop.py`) is a fresh, short-lived Python process that calls `sys.exit(0)` at the end of `main()`, so `compile_regex`'s 128-entry `lru_cache` is process-local and reset on every hook call — there is no persistent long-lived process for an attacker to exhaust cache state across invocations. [5](#0-4) 

### Impact Explanation
A hang in `_regex_match()` blocks the specific hook invocation from ever returning its JSON decision. Because `PreToolUse` output determines the `permissionDecision` for the tool call currently being evaluated, a hang prevents that hook from ever emitting a `deny`, effectively stalling (not globally disabling) the guard for that one command until the process is killed/times out at a higher layer. This is a denial-of-service on the guard mechanism scoped to the specific invocation, not a full compromise, approval bypass, or persistent disablement of the block path for "subsequent" commands, since each invocation is independent.

### Likelihood Explanation
Exploitation requires that a hookify rule file with a malicious `pattern` actually be present under `.claude/hookify.*.local.md` in the checked-out working directory, and that the corresponding field content contain attacker- or victim-controlled text long enough to trigger backtracking. Whether an unprivileged attacker (e.g., via a PR) can get such a file merged/checked out and exercised depends on the victim's workflow (auto-loading rule files from untrusted branches), which could not be fully confirmed from the indexed content — there is no `.gitignore` entry excluding `hookify.*.local.md`, but the file naming convention (`.local.md`) suggests these are intended as local, user-authored configuration rather than files an unprivileged remote attacker would routinely inject and have executed. This precondition is uncertain from the available code and reduces confidence in real-world reachability by an unprivileged attacker.

### Recommendation
- Bound regex evaluation with a timeout (e.g., run `regex.search` in a subprocess/thread with a hard deadline, or use the `regex` module's timeout support, or `signal.alarm` on POSIX) and treat a timeout as "no match" rather than blocking indefinitely.
- Validate/limit pattern complexity at rule-load time (e.g., reject nested quantifiers, cap pattern length, use a linear-time regex engine such as RE2 via `google-re2`).
- Cap the length of `field_value` passed into `_regex_match()` before matching to reduce worst-case backtracking cost.

### Proof of Concept
Unit/fuzz test targeting `rule_engine.RuleEngine.evaluate_rules`:
```python
import time
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_redos_pattern_times_out():
    rule = Rule(
        name="evil",
        enabled=True,
        event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+$")],
        message="boom",
        action="block",
    )
    engine = RuleEngine()
    payload = {"tool_name": "Bash", "tool_input": {"command": "a" * 40 + "!"}}

    start = time.monotonic()
    result = engine.evaluate_rules([rule], payload)
    elapsed = time.monotonic() - start

    # Expected (currently failing): evaluation should be bounded, e.g. < 1s,
    # and should not hang; current implementation has no timeout and will
    # take exponential time / hang for growing input length.
    assert elapsed < 1.0, f"regex evaluation took {elapsed}s - no timeout enforced"
```
Running this with increasing repeats of `"a"` (e.g. 30, 40, 50) demonstrates exponential growth in `evaluate_rules()` runtime, confirming the absence of any timeout/size bound in `_regex_match()`.

@lru_cache(maxsize=128)
def compile_regex(pattern: str) -> re.Pattern:
    """Compile regex pattern with caching.

    Args:
        pattern: Regex pattern string

    Returns:
        Compiled regex pattern
    """
    return re.compile(pattern, re.IGNORECASE)

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
