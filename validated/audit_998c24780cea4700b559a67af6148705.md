### Title
Fee-on-transfer / deflationary staking tokens break MasterMagpie accounting and cause protocol insolvency - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie._deposit()` credits `user.amount` / `user.available` with the full `_amount` parameter and only afterwards calls `safeTransferFrom` for that same amount, assuming the full amount is always received. This is the exact bug class from the external report (assuming `amount` transferred equals `amount` credited), applied to MasterMagpie's staking-token accounting instead of `DepositVault`.

### Finding Description
In `_deposit`, the internal accounting is updated before/independently of what is actually received: [1](#0-0) 

`user.amount` and `user.available` are incremented by the full `_amount` requested, and `IERC20(pool.stakingToken).safeTransferFrom(msg.sender, address(this), _amount)` is called without checking the contract's real token balance delta. If `pool.stakingToken` ever behaves as a fee-on-transfer / rebasing / deflationary token, the contract would receive less than `_amount`, yet the user's `amount`/`available` (and thus their claim on `_calLpSupply` — which for ordinary pools is `IERC20(_stakingToken).balanceOf(address(this))`) would be overstated relative to what's actually held: [2](#0-1) 

On withdrawal, `_withdraw` transfers out the full recorded `_amount` with no reconciliation against actual contract balance: [3](#0-2) 

If aggregate user `available` balances exceed the real token balance held by the contract (due to fee-on-transfer losses accumulating over many deposits), later users' withdrawals for that pool will revert (insufficient balance), permanently freezing their staked funds — an insolvency condition analogous to the reported `DepositVault` bug, but here it also corrupts the shared reward-per-share accounting (`_calLpSupply` overstates total staked, diluting `accMGPPerShare` for all depositors of that pool), not just an individual depositor's balance.

### Impact Explanation
Registered staking tokens in `MasterMagpie` are typically protocol-controlled receipt tokens (`WombatStaking` receipt tokens, `mWOM`, `vlMGP`, `mWomSV`) that are minted 1:1 and are not fee-on-transfer today. However, this determination is entirely a function of which token address is registered via `add()`/`set()` — the accounting logic itself contains no defense (no before/after balance check) against a non-standard token. Any pool whose `stakingToken` deviates from strict 1:1 transfer semantics causes permanent fund lock/insolvency for that pool's depositors, matching the "permanent freezing of funds" / "protocol insolvency" impact bar. Reachability from an ordinary wallet's `deposit()`/`withdraw()` calls is direct and requires no privileged action — the flaw is in the depositing logic itself, not in choosing which token to add.

### Likelihood Explanation
Medium. Exploitability today depends on whether any currently-registered `stakingToken` exhibits fee-on-transfer/rebase behavior; the analysis of the currently deployed pool helpers (`WombatPoolHelper`, `WombatPoolHelperV2`, `AnkrBNBPoolHelper`) shows they already defensively measure `beforeDeposit`/`afterDeposit` balance deltas before calling `MasterMagpie.depositFor`, e.g.: [4](#0-3)  — meaning the actual amount forwarded into `MasterMagpie.depositFor` is already fee-adjusted for LP receipt tokens. The residual risk is confined to `mWOM`/`SmartWomConvert`/`vlMGP` paths and any future pool addition, and to the direct user-facing `MasterMagpie.deposit()` entrypoint which has no such balance-delta protection at all.

### Recommendation
In `MasterMagpie._deposit`, measure the actual balance received via before/after `balanceOf(address(this))` deltas (as already done in the pool helpers) and credit `user.amount`/`user.available` with the actually-received amount rather than the requested `_amount`. Apply the same before/after balance check symmetrically to `_withdraw` if a non-1:1 token is ever used.

### Proof of Concept
1. A `PoolManager` (or via future upgrade) registers a `stakingToken` that has fee-on-transfer behavior (e.g., taking 1% fee) via `MasterMagpie.add()`.
2. User A calls `MasterMagpie.deposit(stakingToken, 1000)`. Only 990 tokens actually arrive in the contract (10 taken as fee), but `user.amount = 1000` and `user.available = 1000` are recorded, and `_calLpSupply` reports `balanceOf(address(this)) == 990`.
3. Multiple users repeat this, and the contract's real balance is deterministically less than the sum of all `user.available`.
4. When later users call `withdraw(stakingToken, amount)` for their full recorded `available` amount, `safeTransfer` reverts because the contract does not hold enough tokens to cover all outstanding balances — the last users to withdraw find their funds permanently frozen/lost.

        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        if (user.amount > 0) {
            _harvestMGP(_stakingToken, _account);

        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount + _amount;
        if (!_isVlmgp) {
            user.available = user.available + _amount;
            IERC20(pool.stakingToken).safeTransferFrom(address(msg.sender), address(this), _amount);
        }
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)
            if (!_isVlmgp)
                emit Deposit(_account, _stakingToken, _amount);
            else
                emit DepositNotAvailable(_account, _stakingToken, _amount);
    }
