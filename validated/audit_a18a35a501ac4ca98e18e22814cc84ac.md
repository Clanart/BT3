## Finding: `SimplexPaymaster::_getOraclePrice` accepts Chainlink's clamped min/max answer, letting depegged/crashed stablecoins pay for gas at a stale floor price

### Title
`SimplexPaymaster::_getOraclePrice` trusts Chainlink `latestRoundData()` without checking `minAnswer`/`maxAnswer` bounds, allowing gas payment at a stale clamped price during a depeg/crash - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using two Chainlink `AggregatorV3Interface` feeds (native/USD and token/USD) via `_getOraclePrice`. This function checks only for a non-positive answer and staleness by timestamp, but never checks whether the returned `answer` sits within the underlying aggregator's configured `minAnswer`/`maxAnswer` circuit-breaker bounds — exactly the flaw described in the external report. [1](#0-0) 

### Finding Description
Chainlink aggregators have a hard-coded `minAnswer`/`maxAnswer` range. If the real market price of an asset moves outside that range (e.g. a stablecoin depeg crash), the aggregator continues to report the clamped `minAnswer` (or `maxAnswer`) as a fresh, non-stale, positive value, because the underlying transmitters are still submitting rounds — they are just clamped by the aggregator's own bounds check before being stored. `_getOraclePrice` only guards against `answer <= 0` and staleness: [2](#0-1) 

Both call sites rely on this unguarded price:
- `_tokenPrice`, which computes the token-per-wei conversion rate used by `PaymasterERC20` to charge the user's ERC-20 balance for gas: [3](#0-2) 
- `swapAndDeposit`, which uses the same clamped price to compute `expectedWei`/`amountOutMin` slippage bounds for swapping accumulated token surplus to native currency: [4](#0-3) 

Since `_fetchDetails` (called during every `UserOperation` validation) derives `tokenPrice` directly from `_tokenPrice`, and this value determines exactly how much ERC-20 the paymaster charges relative to the real gas cost in wei: [5](#0-4) 

If a registered stablecoin's real market value collapses below the Chainlink feed's `minAnswer` floor (a de-peg/crash event — not a compromised oracle, prover, or relayer; the feed is functioning as designed by its own circuit breaker), `tokenUsd` will remain frozen at the artificially high floor price instead of reflecting the crashed real value. Because `tokenUsd` sits in the denominator of `_tokenPrice`, an artificially inflated `tokenUsd` produces an artificially deflated `tokenPrice` (fewer token units required per wei of gas). Any unprivileged user can then submit `UserOperation`s using the depegged/crashed token as `paymasterData`'s token, paying near-worthless tokens valued at the stale floor price while the paymaster's `EntryPoint` deposit — real native currency — is drained to cover the actual gas cost.

### Impact Explanation
This directly causes loss of funds from the paymaster's `EntryPoint` deposit (real, valuable native currency) in exchange for tokens that are actually worth far less than what the frozen oracle price implies. Every subsequent `UserOperation` routed through `SimplexPaymaster` for the affected token would be mispriced until governance intervenes via `DeactivateToken`/`UpdateParams` — governance action that itself relies on detecting the depeg, which is not guaranteed to happen before meaningful drainage. The contract's own security note acknowledges bounded exposure only through allowance/permit caps against a "malicious oracle," but this scenario requires no malicious or compromised oracle at all — it is the expected, documented clamping behavior of a legitimate, correctly functioning Chainlink aggregator during a real market crash.

### Likelihood Explanation
Reachable by any unprivileged actor holding (or cheaply acquiring) the depegged token once a real de-peg/crash event occurs on a registered token's feed and the price crosses the aggregator's `minAnswer`/`maxAnswer` boundary — a scenario that has occurred historically for multiple Chainlink-fed assets (as cited in the external report). No relayer, prover, admin, or governance compromise is required; the exploit path is a normal `UserOperation` submission through the paymaster's standard `_fetchDetails`/`_validatePaymasterUserOp` flow.

### Recommendation
In `_getOraclePrice`, fetch and compare `answer` against the target aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV2V3Interface`/proxy `aggregator()` and its exposed bounds, or a governance-configured bound per feed) and revert (e.g. a new `AnswerOutOfBounds` error) when `answer` is at or beyond those limits, mirroring the staleness/non-positive checks already present at `evm/src/utils/SimplexPaymaster.sol:431-434`.

### Proof of Concept
1. Governance registers a stablecoin `T` with a Chainlink token/USD feed via `RegisterToken`, per `_registerToken`/`RequestKind.RegisterToken`.
2. `T` depegs; its real market value falls below the feed's `minAnswer` (e.g. floor of $0.90 while actual value is $0.05). The feed keeps returning `answer = minAnswer` with a fresh `updatedAt`, so `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:428-442`) neither reverts on `answer <= 0` nor on staleness.
3. An attacker acquires cheap depegged `T` (market price ~$0.05) and submits a `PackedUserOperation` with `paymasterData` referencing `T`. `_fetchDetails` (`evm/src/utils/SimplexPaymaster.sol:374-393`) calls `_tokenPrice`, which computes `tokenPrice` using the stale $0.90 floor instead of the real $0.05 value.
4. `PaymasterERC20` charges the attacker `T` at the inflated $0.90 valuation while the paymaster's `EntryPoint` deposit pays out real native currency for the actual gas cost — the attacker profits the ~18x differential, and repeated `UserOperation`s drain the deposit funded by real value while paying with near-worthless `T`.

```text
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
