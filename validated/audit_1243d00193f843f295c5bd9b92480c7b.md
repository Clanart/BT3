## Title
Bandwidth allowance is permanently drained on failed `on_accept` even though the failed message's receipt is deleted and the message can be replayed indefinitely - (`File: parachain/runtimes/gargantua/src/ismp.rs`, `parachain/runtimes/nexus/src/ismp.rs`, `modules/pallets/bandwidth/src/lib.rs`)

## Summary
This is the same broken invariant as the Wormhole report: a side effect that is supposed to be atomic with the "main" action is committed to storage in a step that is not rolled back when the main action later fails, while the "used" marker for the main action *is* rolled back — allowing the same message to be resubmitted an unbounded number of times, each time re-charging the irreversible side effect. In Hyperbridge, the irreversible side effect is bandwidth consumption (`pallet_bandwidth::try_consume`), and the recoverable "used" marker is the ISMP request receipt.

## Finding Description
`ProxyModule::on_accept` in the Gargantua/Nexus runtimes consumes an app's prepaid bandwidth allowance **before** dispatching the request to the destination pallet: [1](#0-0) 

The gate call `BandwidthGate::try_consume` mutates `pallet_bandwidth::Allowance` storage immediately and unconditionally (outside of any `Insufficient` short-circuit) as part of this single function call: [2](#0-1) 

If the subsequent dispatch to `pallet_hyper_fungible_token::Pallet::<Runtime>::on_accept(request)` fails for any reason (e.g. unregistered asset, decode error in the payload, or any other module-side validation failure), `ProxyModule::on_accept` returns `Err`, and the ISMP core request handler treats this as a recoverable failure: it deletes the just-stored request receipt so that the request "can be timed out" / retried, but it never attempts to reverse the bandwidth debit that already happened inside the same call: [3](#0-2) 

The framework's own documentation states the expected invariant explicitly — the module is responsible for not leaving partial state changes when `on_accept` fails, precisely so a request can be safely retried without a residual cost: [4](#0-3) 

`ProxyModule` violates this invariant: the bandwidth debit performed by `pallet_bandwidth::try_consume` (a *different* pallet/module than the one that ultimately fails) is not undone when the receipt is deleted. Because relaying is fully permissionless (`handle<H>(host, msg: RequestMessage)` can be invoked by any relayer, as documented), and because the deleted receipt means the exact same `PostRequest` can be resubmitted with the same membership proof repeatedly (it is not marked as processed and has not timed out), an attacker can replay the identically-failing request over and over. Each replay:
1. Passes the bandwidth gate and drains `bytes` from the destination app's live `Allowance` subscriptions (a value the attacker fully controls the count of, since request size determines `bytes` consumed).
2. Fails deep in `pallet_hyper_fungible_token::on_accept`, so the intended action never completes.
3. Has its receipt deleted, resetting "used" state so it can be replayed again.

This mirrors the Wormhole bug's exact mechanics: one subsystem's "already accounted for" state is committed irreversibly (bandwidth ledger vs. VAA-used flag) while the paired subsystem's state that gates re-processing is rolled back on failure (request receipt vs. NEAR receipt gas), letting the attacker desynchronize the two and repeatedly extract/burn the irreversible resource without ever completing the paired action.

## Impact Explanation
An app that has purchased bandwidth (a paid resource, purchased via `BandwidthManager.sol` for real fee-token payment) can have its entire prepaid allowance drained to zero by anyone relaying a request that is guaranteed to fail at the destination pallet — without a single successful cross-chain delivery ever occurring. This is direct loss of purchased/paid-for bandwidth (a fund-equivalent resource under "bandwidth accounting" per the bounty scope), triggerable by any unprivileged relayer with no special access, no malicious peer/prover/admin assumption, and no reliance on front-running. Because the request receipt is deleted on every failure, there is no bound on how many times the same request can be replayed, so the attack is not a one-shot griefing but an unbounded resource-drain against the target app.

## Likelihood Explanation
High. Relaying of `RequestMessage`s is a core permissionless protocol feature — any party may submit a valid `RequestMessage` with its membership proof. All the attacker needs is one legitimately-dispatched request whose payload will deterministically fail deep inside the destination `IsmpModule` (e.g., referencing an unregistered/paused asset, a body the token module rejects, or any other post-bandwidth-gate validation failure) and the ability to resubmit that same message multiple times, which the protocol explicitly permits after a failed `on_accept` (by design, to allow retries/timeouts). No race condition or gas-inflation trick (unlike the original NEAR bug) is even required — the flaw is structural: the debit and the retry-eligibility are decided by two different code paths that are not kept consistent.

## Recommendation
Make the bandwidth debit conditional on the destination module's dispatch actually succeeding, or refund/credit back the consumed bytes whenever the receipt is deleted due to a failed `on_accept`. Concretely:
- Move the `try_consume` call to occur only after the destination pallet dispatch succeeds (i.e., wrap the whole `on_accept` body — bandwidth gate + destination dispatch — in a transactional boundary using `frame_support::storage::with_transaction`, and only commit if the final result is `Ok`), or
- Track the exact bytes consumed for a given request commitment and refund them in the same failure branch in `modules/ismp/core/src/handlers/request.rs` that currently calls `host.delete_request_receipt`, symmetric to how `timeout.rs` restores `request_commitment`/`request_receipt` on module failure.

## Proof of Concept
1. App `A` on a source chain purchases a bandwidth tier via `BandwidthManager.sol`, crediting `(app_chain, A)` with `N` bytes on the `pallet-bandwidth` ledger (`Self::push_subscription` in `modules/pallets/bandwidth/src/lib.rs:477`).
2. App `A` (or an attacker impersonating a legitimate cross-chain call originating from `A`, e.g. by pointing `to` at an unregistered asset id or otherwise-malformed-but-decodable body for `pallet_hyper_fungible_token`) dispatches a `PostRequest` destined for `pallet_hyper_fungible_token::PALLET_ID` that is guaranteed to fail `on_accept` on the destination pallet (e.g. references an asset id that is not registered).
3. Any relayer submits `RequestMessage{ requests: [that PostRequest], proof }` to `handle<H>` (`modules/ismp/core/src/handlers/request.rs`).
4. `ProxyModule::on_accept` runs: `try_consume` drains `len(encoded request)` bytes from `A`'s allowance (`modules/pallets/bandwidth/src/lib.rs:509-564`), then `pallet_hyper_fungible_token::on_accept` fails and returns `Err`.
5. `request.rs` sees `res.is_err()` and calls `host.delete_request_receipt(&wrapped_req)` — the request is now un-marked as processed.
6. The relayer resubmits the identical `RequestMessage` (same proof, same request — `dedup_requests` only guards against duplicates *within* one batch, not across separate submissions) as many times as desired, each time draining another `len(encoded request)` bytes from `A`'s allowance, until the allowance reaches zero — with zero successful transfers ever completing.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
</Callout>
