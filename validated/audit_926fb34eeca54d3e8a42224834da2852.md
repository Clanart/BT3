### Title
Challenge Transaction Silently Suppressed on Mainnet and Testnet4, Disabling the Entire BitVM Disprove Security Flow — (`core/src/verifier.rs`)

---

### Summary

`Verifier::handle_kickoff` contains an explicit network guard that prevents the challenge transaction from ever being queued on `Bitcoin::Network::Bitcoin` (mainnet) or `Bitcoin::Network::Testnet4`. Because the challenge transaction is the on-chain trigger that starts the BitVM disprove game, its suppression on production networks means a malicious operator can submit a fraudulent kickoff, wait out the challenge timeout, and collect reimbursement from the bridge vault without any verifier ever contesting it.

---

### Finding Description

In `core/src/verifier.rs`, `handle_kickoff` (the function called whenever a verifier determines a kickoff is malicious) contains the following guard:

```rust
// do not automatically send challenge txs on mainnet or testnet4
if !challenged_before
    && !matches!(
        self.config.protocol_paramset().network,
        bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
    )
{
    #[cfg(feature = "automation")]
    self.tx_sender
        .add_tx_to_queue(
            dbtx,
            TransactionType::Challenge,
            &challenge_tx,
            ...
        )
        .await?;
}
``` [1](#0-0) 

On mainnet and testnet4 the inner block is never reached. The function logs a warning and returns `Ok(is_malicious)` without queuing the challenge transaction.

The `InternalHandleKickoff` gRPC endpoint, which is the only explicit "manual trigger" for this path, calls the same `handle_kickoff` function and is documented in the proto as: *"on networks other than mainnet and testnet4, it will send the challenge tx"* — confirming the suppression is present in both the automated and the manual code paths. [2](#0-1) 

The `KickoffStateMachine` transitions to the `challenged` state only when the on-chain challenge UTXO is spent by a transaction that is not the `ChallengeTimeout` tx. Because no challenge transaction is ever queued on mainnet/testnet4, the state machine stays in `kickoff_started` indefinitely. [3](#0-2) 

As a result, none of the downstream duties are ever dispatched on production networks:

- `Duty::WatchtowerChallenge` — never triggered (requires `challenged` state)
- `Duty::SendOperatorAsserts` — never triggered
- `Duty::VerifierDisprove` — never triggered [4](#0-3) [5](#0-4) 

---

### Impact Explanation

A malicious operator on mainnet or testnet4 can:

1. Send a fraudulent kickoff (claiming a payout that never happened, or claiming an incorrect block hash).
2. Wait for the `ChallengeTimeout` period to expire — no verifier will ever queue a challenge tx.
3. Spend the challenge UTXO via the pre-signed `ChallengeTimeout` transaction, which transitions the kickoff state machine to `closed` and clears all matchers.
4. Proceed to collect reimbursement from the bridge vault.

The entire BitVM2 challenge/disprove security model — watchtower challenges, operator asserts, and the disprove transaction — is unreachable on production networks. Bridged BTC held in the vault can be drained by a colluding or malicious operator with no on-chain recourse.

---

### Likelihood Explanation

The suppression is unconditional on mainnet/testnet4 — it is not gated on any configuration flag, operator behavior, or external condition. Any operator who initiates a kickoff on mainnet or testnet4 is guaranteed that no automated challenge will be sent. The `InternalHandleKickoff` RPC, the only alternative trigger, exhibits the same behavior. There is no other code path in the production surface that queues `TransactionType::Challenge` on these networks.

---

### Recommendation

Remove the network guard from `handle_kickoff` so that the challenge transaction is queued on all networks when a malicious kickoff is detected. If manual review is desired before broadcasting on mainnet, the appropriate place to add that gate is in the tx-sender queue policy (e.g., a `paused` or `requires_approval` state), not in the detection-and-queue logic itself. The detection and queuing must be unconditional; broadcasting policy can be separated.

```rust
// Remove the network check; queue the challenge on all networks
if !challenged_before {
    #[cfg(feature = "automation")]
    self.tx_sender
        .add_tx_to_queue(
            dbtx,
            TransactionType::Challenge,
            &challenge_tx,
            &[],
            Some(tx_metadata),
            self.config.protocol_paramset(),
            None,
        )
        .await?;
}
```

---

### Proof of Concept

**Trigger path (automated):**

1. Operator broadcasts a fraudulent kickoff on mainnet.
2. `BitcoinSyncer` ingests the block; the verifier's state manager dispatches `Duty::CheckIfKickoff`.
3. Verifier creates a `KickoffStateMachine` and later dispatches `Duty::CheckIfKickoffMalicious`.
4. Verifier calls `handle_kickoff` → `is_kickoff_malicious` returns `true`.
5. Network guard fires: `matches!(network, Bitcoin | Testnet4)` → challenge tx is **not** queued.
6. `KickoffStateMachine` remains in `kickoff_started`; no `Challenged` event is ever dispatched.
7. `ChallengeTimeout` tx is broadcast by the operator after the timeout; state machine closes.
8. Operator proceeds to reimbursement; bridge vault funds are lost.

**Trigger path (manual RPC):**

Calling `InternalHandleKickoff` with the kickoff txid on mainnet/testnet4 produces the same outcome — the proto comment itself confirms: *"on networks other than mainnet and testnet4, it will send the challenge tx"*. [6](#0-5) [7](#0-6)

    /// Checks if the kickoff is malicious and sends the appropriate txs if it is.
    /// Returns true if the kickoff is malicious.
    /// Sends a challenge tx if the kickoff is first malicious one in the current round, and the network is not mainnet or testnet4.
    pub async fn handle_kickoff<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        kickoff_witness: Witness,
        mut deposit_data: DepositData,
        kickoff_data: KickoffData,
        challenged_before: bool,
    ) -> Result<bool, BridgeError> {
        let is_malicious = self
            .is_kickoff_malicious(kickoff_witness, &mut deposit_data, kickoff_data, dbtx)
            .await?;

        let deposit_outpoint = deposit_data.get_deposit_outpoint();

        let (_signed_txs, tx_metadata, challenge_tx) = self
            .get_signed_txs_for_kickoff(dbtx, kickoff_data, deposit_data)
            .await?;

        if is_malicious {
            tracing::warn!(
                "Malicious {} detected. {} Challenge tx: {} for deposit {}",
                kickoff_data,
                match challenged_before {
                    false => "This is the first malicious kickoff in the current round.",
                    true => "This is not the first malicious kickoff in the current round.",
                },
                bitcoin::consensus::encode::serialize_hex(&challenge_tx),
                deposit_outpoint
            );
            // do not automatically send challenge txs on mainnet or testnet4
            if !challenged_before
                && !matches!(
                    self.config.protocol_paramset().network,
                    bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
                )
            {
                #[cfg(feature = "automation")]
                self.tx_sender
                    .add_tx_to_queue(
                        dbtx,
                        TransactionType::Challenge,
                        &challenge_tx,
                        &[],
                        Some(tx_metadata),
                        self.config.protocol_paramset(),
                        None,
                    )
                    .await?;
            }
        } else {
            tracing::debug!(
                "Non-malicious {} detected, challenge tx: {}",
                kickoff_data,
                bitcoin::consensus::encode::serialize_hex(&challenge_tx)
            );
        }

        Ok(is_malicious)
    }

    #[tracing::instrument(skip(self), err(level = tracing::Level::ERROR))]
    async fn internal_handle_kickoff(
        &self,
        request: Request<clementine::Txid>,
    ) -> Result<Response<Empty>, Status> {
        let txid = request.into_inner();
        let txid = bitcoin::Txid::try_from(txid).map_err(|e| {
            Status::invalid_argument(format!("Failed to convert txid to bitcoin::Txid: {e}"))
        })?;
        tracing::warn!(
            "Called internal_handle_kickoff for kickoff txid: {:?}",
            txid
        );
        let mut dbtx = self.verifier.db.begin_transaction().await?;
        let kickoff_data = self
            .verifier
            .db
            .get_deposit_data_with_kickoff_txid(None, txid)
            .await?;
        if let Some((deposit_data, kickoff_id)) = kickoff_data {
            self.verifier
                .handle_kickoff(&mut dbtx, Witness::new(), deposit_data, kickoff_id, false)
                .await?;
        } else {
            return Err(Status::not_found("Kickoff txid not found"));
        }
        dbtx.commit()
            .await
            .wrap_err("Failed to commit transaction")
            .map_to_status()?;
        Ok(Response::new(Empty {}))
    }
