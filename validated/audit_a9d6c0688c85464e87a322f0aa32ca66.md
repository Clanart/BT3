### Title
Unsandboxed `post-checkout` hook execution on branch/commit checkout bypasses the hooks-interception allowlist - ([File: app/src/lib/git/checkout.ts])

### Summary
`git()` calls for `checkout` in `checkout.ts` never set `interceptHooks`, so `withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts:34`) takes the early-return path (`if (!opts?.interceptHooks || !getHooksEnvEnabled()) return fn(opts?.env)`) and runs Git with whatever `core.hooksPath`/`.git/hooks/post-checkout` already exists on disk for that repository, instead of routing through the hooks-proxy allowlist mechanism used for commit/merge/pull/push.

### Finding Description
GitHub Desktop added a hooks-proxy sandbox (`app/src/lib/hooks/hooks-proxy.ts`, `app/src/lib/hooks/with-hooks-env.ts`) specifically to intercept git hooks: it discovers hooks via `getRepoHooks()` (`app/src/lib/hooks/get-repo-hooks.ts`), copies only known/allow-listed hook names into a fresh temp directory, and forces Git to use that directory by injecting `GIT_CONFIG_PARAMETERS: core.hooksPath=<tmpHooksDir>` (`with-hooks-env.ts:90-96`), which overrides any attacker-controlled repo-local `core.hooksPath`. This mechanism is only invoked when the calling `git()` invocation passes `interceptHooks` (`app/src/lib/git/core.ts:89`), and it is currently only wired up in `commit.ts`, `merge.ts`, `pull.ts`, and `push.ts` per the codebase-wide grep.
`app/src/lib/git/checkout.ts` (`checkoutBranch`, `checkoutCommit`) builds its `IGitStringExecutionOptions` (`getCheckoutOpts`) without an `interceptHooks` field, and then calls `git(args, repository.path, 'checkoutBranch'/'checkoutCommit', opts)`. Since `opts?.interceptHooks` is `undefined`, `withHooksEnv` short-circuits and Git runs with real environment, meaning any `post-checkout` hook that is physically present under the repository's actual `.git/hooks` (or an attacker-set repo-local `core.hooksPath`) executes unsandboxed. `checkoutBranch`/`checkoutCommit` additionally call `updateSubmodulesAfterOperation()` (`app/src/lib/git/submodule.ts`), which runs `git submodule update --init --recursive` — also without `interceptHooks` — so submodule checkouts can trigger `post-checkout` in nested submodule `.git/modules/.../hooks` as well.

### Impact Explanation
An attacker who controls a repository the user opens in Desktop (e.g. via a crafted "Open in Desktop" deep link handled by `parseAppURL`/`openRepositoryFromUrl`, or a repository shared/extracted with an already-populated `.git` directory containing a hook, or one whose local config sets `core.hooksPath` to an attacker-writable path inside the working tree) can get arbitrary shell command execution on the victim's machine the moment Desktop performs a branch/commit checkout — an action that happens routinely and silently as part of normal workflows (switching branches, checking out PR branches from `openRepositoryFromUrl`, etc.). This satisfies the requested impact category of code execution triggered by an attacker-controlled repository/link, and directly undermines the very security boundary that the hooks-proxy sandbox was built to provide for the other Git operations.

### Likelihood Explanation
Likelihood is moderate-to-high in scenarios where Desktop opens or checks out branches in repositories not obtained purely through `git clone` over the network (where hooks aren't transferred), because Desktop supports adding/opening arbitrary local folders as repositories, and switching branches/PRs via `checkoutBranch`/`checkoutCommit` is an extremely common, low-friction action that requires no unusual user steps beyond normal repository/branch selection.

### Recommendation
Pass `interceptHooks: ['post-checkout']` (and equivalent allow-listed hook names for submodule updates) through the `IGitStringExecutionOptions` used in `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation`, mirroring the pattern already used in `commit.ts`/`merge.ts`/`pull.ts`/`push.ts`, so that all checkout-triggering hook executions go through the same sandboxed, allow-listed hooks-proxy path.

### Proof of Concept
I was not able to fully verify end-to-end exploitability (e.g., confirm exactly how a "local folder with pre-existing `.git/hooks/post-checkout`" gets added as a repository in the UI, or trace every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to rule out an additional guard elsewhere) within the available tool budget. This assessment is based on static code inspection of `app/src/lib/git/checkout.ts`, `app/src/lib/git/submodule.ts`, `app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/hooks-proxy.ts`, and `app/src/lib/git/core.ts`, and the fact that a targeted `grep` for `interceptHooks` across the repo only returned `merge.ts`, `pull.ts`, `commit.ts`, and `push.ts` as callers — `checkout.ts` and `submodule.ts` are absent from that list. export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

  const ext = __WIN32__ ? '.exe' : ''
  const processProxyPath = join(__dirname, `process-proxy${ext}`)

  const token = crypto.randomUUID()
  const tmpHooksDir = await mkdtemp(join(tmpdir(), 'desktop-git-hooks-'))
  const hooksProxy = createHooksProxy(
    cwd =>
      memoizedGetShellEnv(
        getGitHookEnvShell(),
        cwd,
        // We always cache environment per token (i.e. per operation, e.g commit, apply, etc)
        // but we can optionally cache it over multiple operations in the same repository if the user
        // has enabled that setting.
        getCacheHooksEnv() ? 'global' : token
      ),
    tmpHooksDir,
    opts?.onHookProgress,
    opts?.onHookFailure
  )

  const server = createProxyProcessServer(
    conn =>
      hooksProxy(conn).catch(err => {
        log.error(`hooks proxy failed:`, err)
        conn.exit(1).catch(() => {})
      }),
    { validateConnection: async receivedToken => receivedToken === token }
  )
  const port = await new Promise<number>(resolve => {
    server.listen(0, '127.0.0.1', () =>
      resolve((server.address() as AddressInfo).port)
    )
  })
  try {
    for (const hook of hooks) {
      await cp(processProxyPath, join(tmpHooksDir, `${hook}${ext}`))
    }

    const existingGitEnvConfig =
      opts?.env?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    return await fn({
      // TODO: Do we need to escape tmpHooksDir? Could it possibly include a single quote?
      // probably not?
      GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'core.hooksPath=${tmpHooksDir}'`,
      PROCESS_PROXY_PORT: `${port}`,
      PROCESS_PROXY_TOKEN: token,
    })

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
}
