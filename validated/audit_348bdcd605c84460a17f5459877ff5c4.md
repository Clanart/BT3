### Title
Floating-point precision loss in stake-ratio threshold comparisons can flip consensus-critical PASS/FAIL decisions near exact boundaries - (File: `core/src/consensus.rs`, `ledger/src/blockstore_processor.rs`, `runtime/src/commitment.rs`)

### Summary
The Allora M-6 report is a boundary-condition bug class: a loop/threshold comparison uses the wrong operator/representation (`Gt` vs `Gte`) so the code stops (or accepts/rejects) one increment away from the mathematically specified point, silently corrupting a downstream weight/coefficient. Agave has a structurally identical bug class in its stake-percentage threshold checks: several consensus-critical comparisons compute `stake as f64 / total_stake as f64` and then compare with `>` against a constant threshold (`SWITCH_FORK_THRESHOLD`, `VOTE_THRESHOLD_SIZE`, `DUPLICATE_THRESHOLD`). Because integer stake ratios are cast to `f64`, values that are exactly at or extremely close to the threshold can round to the wrong side of the comparison, exactly like the Allora off-by-one — except here the root cause is float rounding rather than a wrong comparison operator, but the effect (loop/threshold accepts or rejects at the wrong boundary) is the same.

### Finding Description
Multiple core consensus code paths compute a stake fraction as `f64` and compare it directly to a hard-coded threshold constant:

- `Tower::make_check_switch_threshold_decision` computes `(locked_out_stake as f64 / total_stake as f64) > SWITCH_FORK_THRESHOLD` twice, deciding whether a `SwitchProof` is generated. [1](#0-0) [2](#0-1) 

- `Tower::check_vote_stake_threshold` computes `lockout = *fork_stake as f64 / total_stake as f64` and compares `lockout > threshold_size` to decide `PassedThreshold` vs `FailedThreshold`, which gates whether a validator is allowed to vote/lock out a slot. [3](#0-2) 

- `supermajority_root` in the blockstore processor sums stake and compares `total as f64 / total_epoch_stake as f64 > VOTE_THRESHOLD_SIZE` to decide the highest supermajority root used at startup/replay. [4](#0-3) 

- `BlockCommitmentCache::get_lockout_count` performs the same pattern: `(sum as f64 / self.total_stake as f64) > minimum_stake_percentage`, feeding `get_confirmation_count`/`calculate_highest_confirmed_slot`, which RPC commitment levels (`processed`/`confirmed`/`finalized`) rely on. [5](#0-4) 

The codebase itself demonstrates that this exact `stake as f64 / total as f64 > threshold` pattern is unsound: a test in the newer `Fraction` type (introduced specifically "for precise stake threshold comparisons") shows that at `total_stake = 100_000_000_000_000_000` and `stake = 60_000_000_000_000_001` (60% + 1 lamport), the `f64` ratio rounds down and the comparison `f64_ratio <= 0.6` incorrectly evaluates true — the comment literally says `// wrong!` — while the exact rational `Fraction` comparison correctly reports the stake is greater than 60%. [6](#0-5) 

`core/src/consensus.rs` already imports `agave_votor_messages::fraction::Fraction` (used elsewhere for `GENESIS_VOTE_THRESHOLD`), showing the project is aware exact-fraction comparisons are needed for consensus-safety, yet `SWITCH_FORK_THRESHOLD`/`VOTE_THRESHOLD_SIZE`/`DUPLICATE_THRESHOLD` stake-ratio checks in `check_vote_stake_threshold`, `make_check_switch_threshold_decision`, and `supermajority_root` still use plain `f64` division and comparison instead of the exact `Fraction` type. [7](#0-6) 

None of these call sites clamp, round, or otherwise guard against float precision loss the way `Fraction::cmp` does (cross-multiplication in `u128`). [8](#0-7) 

### Impact Explanation
These comparisons directly gate:
1. Whether a validator generates a `SwitchProof` to switch forks (`make_check_switch_threshold_decision`), which affects fork choice / voting behavior across the whole network.
2. Whether a vote passes the lockout "threshold check" (`check_vote_stake_threshold`), gating whether a slot can be voted on / rooted.
3. Whether a slot is deemed to have a supermajority root during ledger replay/startup (`supermajority_root`), affecting the initial commitment/root state a validator boots into.
4. RPC-visible confirmation counts and commitment levels (`get_lockout_count`).

With large mainnet-scale total stake values (order of 10^17–10^18 lamports as in the demonstrated test), a stake sum that is mathematically exactly at or 1 lamport above/below a threshold boundary can be misclassified by `f64` rounding, causing a validator to reach a different `PassedThreshold`/`SwitchProof` decision than intended by the exact stake accounting. Because this logic runs identically on every validator using the same (correct) stake inputs, in most cases all honest nodes would compute the same wrong-but-consistent answer, so the practical impact is bounded — but it is exactly the class of bug (false threshold pass/fail from imprecise boundary arithmetic) that can produce inconsistent voting/switching behavior at the margins and undermines the exactness guarantee that stake-weighted consensus depends on.

### Likelihood Explanation
This requires the aggregated stake to land extremely close to the exact threshold fraction (within f64's ~15-17 significant digits of relative precision) which is a narrow, hard-to-hit condition under organic stake distributions, but is not implausible at Solana's actual total-stake scale as directly demonstrated by the project's own regression test. It does not require a malicious actor — it is a latent arithmetic correctness issue triggerable by ordinary stake totals.

### Recommendation
Replace the raw `f64` division/comparison pattern in `Tower::check_vote_stake_threshold`, `Tower::make_check_switch_threshold_decision`, `supermajority_root`, and `BlockCommitmentCache::get_lockout_count` with the exact `agave_votor_messages::fraction::Fraction` (or equivalent integer cross-multiplication) comparison already used elsewhere in the codebase, so that `stake / total_stake` vs `threshold` comparisons are exact rather than float-rounded.

### Proof of Concept
The project's own test demonstrates the failure mode of the pattern used in `consensus.rs`/`blockstore_processor.rs`/`commitment.rs`: [6](#0-5) 
Reproducing the equivalent computation as done in `check_vote_stake_threshold`/`make_check_switch_threshold_decision` (`stake as f64 / total_stake as f64 > threshold`) with `total_stake = 100_000_000_000_000_000` lamports and `stake = 60_000_000_000_000_001` lamports (0.6 + 1 lamport of total stake) against a `threshold_size = 0.6` yields `false` (fails threshold) under the current f64-based code paths, whereas the exact ratio is strictly greater than 0.6 and should pass — confirming the same class of boundary-comparison defect described in the Allora M-6 report can manifest in Agave's stake-threshold consensus logic.

I could not find any place in `core/src/consensus.rs`, `ledger/src/blockstore_processor.rs`, or `runtime/src/commitment.rs` where this f64 ratio is cross-checked or replaced with `Fraction` before the threshold comparison, so the existing guard in `votor-messages/src/fraction.rs` does not protect these call sites.

fn supermajority_root(roots: &[(Slot, u64)], total_epoch_stake: u64) -> Option<Slot> {
    if roots.is_empty() {
        return None;
    }

    // Find latest root
    let mut total = 0;
    let mut prev_root = roots[0].0;
    for (root, stake) in roots.iter() {
        assert!(*root <= prev_root);
        total += stake;
        if total as f64 / total_epoch_stake as f64 > VOTE_THRESHOLD_SIZE {
            return Some(*root);
        }
        prev_root = *root;
    }

    None
}

impl Ord for Fraction {
    fn cmp(&self, other: &Self) -> std::cmp::Ordering {
        // Cross-multiply to compare
        let lhs = (self.numerator as u128)
            .checked_mul(other.denominator.get() as u128)
            .unwrap();
        let rhs = (other.numerator as u128)
            .checked_mul(self.denominator.get() as u128)
            .unwrap();
        lhs.cmp(&rhs)
    }
}
