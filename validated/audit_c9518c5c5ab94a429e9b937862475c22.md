### Title
Attacker-chosen group key via `ThresholdKeys::read` — no binding between the deserialized `secret_share`, our `verification_shares[i]`, and the derived `group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts untrusted bytes and reconstructs a `ThresholdKeys` whose `group_key` is derived *solely* from the attacker-supplied `verification_shares` map (participants `1..=t` under the declared interpolation). Neither `ThresholdKeys::read` nor `ThresholdKeys::new` verifies that the deserialized `secret_share` actually corresponds to `verification_shares[params.i()]`, nor that the shares are consistent with the claimed group key. An untrusted key file therefore grants an attacker the equivalent of a permission/access-control bypass: they can assert an arbitrary group identity for the victim node while the victim's share is unrelated, exactly analogizing the Curio incident class where a permission-logic gap let the attacker confer authority the protocol never granted.

### Finding Description
`ThresholdKeys::new` computes the group key as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` for `i in 1..=t`, purely from the provided map — the local `secret_share` is never involved. [1](#0-0)  The only checks are share-map length and that all participant indexes are `<= n`. [2](#0-1)  `ThresholdKeys::read` then deserializes `t`, `n`, `i`, the interpolation variant, the `secret_share` scalar, and `n` points via `read_G`, passing them straight to `ThresholdKeys::new` with no consistency check between `secret_share` and `verification_shares[&i]`. [3](#0-2)  Because Lagrange interpolation over the fixed set `{1..=t}` maps any choice of those `t` points to any target point at evaluation 0, the attacker fully controls `group_key()`. Meanwhile `view()` interpolates the attacker's `secret_share` under whatever participant set is later used, and `verification_shares` / `params.i()` are equally attacker-defined. [4](#0-3) 

### Impact Explanation
Two concrete impacts, both reachable purely from bytes fed to `ThresholdKeys::read`:

1. **Funds received but unspendable / attacker-spendable.** The attacker sets `verification_shares[1..=t]` to points interpolating to a key *they* control (e.g., `verification_shares[1] = attacker_pub`, `verification_shares[2..=t] = identity` for `Lagrange`, or `Constant` coefficients of `1` with shares summing to `attacker_pub`). `ThresholdKeys::new` succeeds and `group_key()` returns the attacker's key. Any integrator that loads this file and derives receive addresses (Bitcoin scanner, etc.) from `group_key()` credits deposits to an address the attacker — not the threshold group — can spend. This is a direct unauthorized-ownership grant, mirroring the Curio permission flaw.

2. **Silent signing corruption / misattributed blame.** If the attacker instead crafts shares matching the victim's real group key but with `secret_share` mismatched to `verification_shares[i]`, every signature share the victim emits via `sign()` fails `verify_share`, causing `complete` to abort and the batch-blame path to finger the victim (`InvalidShare(i)`) rather than the malformed key file. [5](#0-4) 

### Likelihood Explanation
`ThresholdKeys::read` is the documented deserialization path for persisting/restoring threshold keys; it is explicitly an untrusted-bytes sink in scope. Exploitation requires the attacker to supply or corrupt a serialized `ThresholdKeys` blob — plausible via compromised storage, backups, config distribution, or any node provisioning pipeline — no validator privileges, collusion, or leaked secrets needed. The missing check costs one scalar multiplication, so its absence is a genuine validation gap, not an accepted trade-off.

### Recommendation
In `ThresholdKeys::new` (covering both `read` and direct construction), verify `C::generator() * secret_share == verification_shares[&params.i()]` and return a `DkgError` on mismatch. Optionally also enforce that `interpolation`'s `Constant` vector length equals `n` (currently only `t == n` is checked, and `interpolation_factor` blindly indexes `c[i - 1]`). [6](#0-5) 

### Proof of Concept
For `Interpolation::Constant` with `t = n = 2`, attacker serializes: `t=2, n=2, i=1`, tag `0`, coefficients `[1, 1]`, `secret_share = 0`, `verification_shares = {1: attacker_pub, 2: identity}`. `ThresholdKeys::read` succeeds; `group_key() = attacker_pub` (Constant interpolation: `1*attacker_pub + 1*identity`). [1](#0-0)  For `Interpolation::Lagrange` with `t = 2`, set `verification_shares = {1: attacker_pub * 2^{-1}·... }` — concretely `λ1 = 2, λ2 = -1` over indexes `{1,2}`, so `{1: attacker_pub/2 ... }` equivalently `{1: attacker_pub * λ1^{-1}, 2: identity}` yields `group_key() = attacker_pub`. The victim's `secret_share` is never consulted in deriving or validating this key.

  pub fn view(&self, mut included: Vec<Participant>) -> Result<ThresholdView<C>, DkgError> {
    if (included.len() < self.params().t.into()) ||
      (usize::from(self.params().n()) < included.len())
    {
      Err(DkgError::IncorrectAmountOfParticipants {
        t: self.params().t,
        n: self.params().n,
        amount: included.len(),
      })?;
    }
    included.sort();
    {
      let mut found = included[0] == self.params().i();
      for i in 1 .. included.len() {
        if included[i - 1] == included[i] {
          Err(DkgError::DuplicatedParticipant(included[i]))?;
        }
        found |= included[i] == self.params().i();
      }
      if !found {
        Err(DkgError::NotParticipating)?;
      }
    }
    {
      let last = *included.last().unwrap();
      if u16::from(last) > self.params().n() {
        Err(DkgError::InvalidParticipant { n: self.params().n(), participant: last })?;
      }
    }

    // The interpolation occurs multiplicatively, letting us scale by the scalar now
    let secret_share_scaled = Zeroizing::new(self.scalar * self.original_secret_share().deref());
    let mut secret_share = Zeroizing::new(
      self.core.interpolation.interpolation_factor(self.params().i(), &included) *
        secret_share_scaled.deref(),
    );

    let mut verification_shares = HashMap::with_capacity(included.len());
    for i in &included {
      let verification_share = self.core.verification_shares[i];
      let verification_share = verification_share *
        self.scalar *
        self.core.interpolation.interpolation_factor(*i, &included);
      verification_shares.insert(*i, verification_share);
    }

    /*
      The offset is included by adding it to the participant with the lowest ID.

      This is done after interpolating to ensure, regardless of the method of interpolation, that
      the method of interpolation does not scale the offset. For Lagrange interpolation, we could
      add the offset to every key share before interpolating, yet for Constant interpolation, we
      _have_ to add it as we do here (which also works even when we intend to perform Lagrange
      interpolation).
    */
    if included[0] == self.params().i() {
      *secret_share += self.offset;
    }
    *verification_shares.get_mut(&included[0]).unwrap() += C::generator() * self.offset;
