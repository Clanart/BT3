### Title
Spoofed `WWW-Authenticate` realm header triggers unwarranted GitHub Enterprise sign-in prompt for an untrusted host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The report's core defect is a false-equivalence assumption: the code treats two distinct things (rETH and ETH) as interchangeable without verifying the underlying reality, and an attacker exploits the gap between the assumed and actual value. The closest verified analog in GitHub Desktop is in the git-credential trampoline: `getEndpointKind` treats a `WWW-Authenticate` header containing `realm="GitHub"` — a value fully controlled by the remote Git server Desktop is talking to — as proof that the remote is a genuine GitHub Enterprise host, without any independent verification (no TLS/hostname check, no `/meta` probe). This false equivalence ("realm says GitHub" ≈ "is GitHub") drives Desktop to open its GitHub Enterprise sign-in flow against an attacker-controlled endpoint.

### Finding Description
When Git needs credentials for a remote it invokes Desktop's credential helper (`trampoline-credential-helper.ts`). `getEndpointKind` classifies the target endpoint in order to decide whether to treat it as a first-party GitHub endpoint (and thus prompt an OAuth/token sign-in) or a generic Git host (and thus fall back to prompting for a plain username/password): [1](#0-0) 

```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```

This header is emitted by the remote HTTP server during the Git handshake (an ordinary 401 challenge), so any server the user's git operation talks to — a malicious remote, a compromised/rogue proxy, or a spoofed self-hosted "GitHub-like" host reached via a crafted clone URL — can supply `WWW-Authenticate: realm="GitHub"` and be classified `'enterprise'` with **no verification whatsoever** (unlike the fallback path a few lines below, which performs an actual network probe via `isGitHubHost`): [2](#0-1) 

Once classified `'enterprise'`, `getCredential` checks whether an account already exists for that endpoint; since it doesn't (it's an unrecognized host), Desktop calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then unconditionally begins the "Enterprise sign-in" flow against that attacker-supplied `endpoint`/origin, presenting it to the user as a GitHub Enterprise host to authenticate to: [4](#0-3) 

This mirrors the report's broken invariant: "value X claims to equal trusted value Y, so treat it as Y" without validating X against Y through an authoritative channel. In the Omnipool case the untrusted value was a price feed; here it's an HTTP response header from the very same untrusted party the user is being asked to authenticate to — a self-attested claim used as its own proof.

### Impact Explanation
A user fetching/pushing/cloning from an attacker-controlled or MITM'd HTTP git remote can force Desktop to display its official "Sign in to GitHub Enterprise" dialog pointed at the attacker's host. Because the dialog is presented by the trusted Desktop UI, and Enterprise sign-in ultimately involves the user supplying either OAuth device-flow credentials or a personal access token bound to that endpoint, this creates a credential/token phishing and unauthorized-account-binding primitive: a legitimate-looking sign-in prompt is spawned for a host the user never explicitly configured as an Enterprise endpoint, based solely on an unauthenticated header the remote server sent about itself. This falls squarely within the requested impact class of "unauthorized OAuth or account binding" driven by an attacker-controlled git remote/proxy response.

### Likelihood Explanation
Triggering the condition only requires the user to run any ordinary git network operation (fetch/pull/push/clone) against a server the attacker controls (or a MITM situation before TLS is otherwise validated at the git transport layer) that returns a 401 with `WWW-Authenticate: realm="GitHub"`. No local access, malware, or unnatural user steps are needed beyond the user already performing a git operation against that remote — which is the exact "attacker controls a git remote/proxy response" scenario called out as in-scope.

### Recommendation
Do not treat the `WWW-Authenticate: realm="GitHub"` header as sufficient proof of an endpoint's identity. Require the same authoritative verification used in the fallback path (`isGitHubHost`, e.g. checking for the `x-github-request-id` header via a same-origin probe, or matching against a known/allow-listed set of Enterprise endpoints already configured by the user) before classifying an unrecognized endpoint as `'enterprise'` and before invoking `promptForGitHubSignIn`. At minimum, gate the header-based fast path behind confirmation that the endpoint was already previously verified/known, rather than trusting a self-reported realm string from an unauthenticated host.

### Proof of Concept
1. Stand up an HTTP server that responds to Git's credential probe (a request without valid credentials) with `WWW-Authenticate: realm="GitHub"` in the 401 response, mimicking any endpoint (e.g. `https://evil.example.com/foo/bar.git`).
2. In GitHub Desktop, clone/fetch from `https://evil.example.com/foo/bar.git` (or add it as a remote to an existing repo and fetch).
3. Git captures the `WWW-Authenticate` header and forwards it as `wwwauth[...]` to the credential helper, which is handled in `getEndpointKind` at [5](#0-4) .
4. Because `realm="GitHub"` matches, `getEndpointKind` returns `'enterprise'` without any network verification.
5. `getCredential` finds no existing account for `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com')`, at [6](#0-5) , which opens Desktop's "Sign in to GitHub Enterprise" dialog bound to that attacker-controlled origin, per [7](#0-6) .

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
