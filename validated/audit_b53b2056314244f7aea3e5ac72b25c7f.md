## Analysis

The Sherlock finding's broken invariant is: a stateful value (`amount`) is computed and cached by the caller, then used later to perform an irreversible action (`withdraw`), without any function to re-derive/validate that value against the current, possibly-changed state (`balanceOf`) immediately before the action executes.

The closest verified analog in this codebase is in the partial-commit ("stage this hunk/line") pipeline, where GitHub Desktop caches a user's line-selection as **positional indices** into a diff, and later replays those same indices against a **freshly recomputed diff** at commit time — without ever re-validating that the line at a given index is still the same line the user selected.

### Title
Stale positional diff-selection indices are replayed against a freshly recomputed working-directory diff, silently changing what gets staged/committed - (File: `app/src/lib/patch-formatter.ts`)

### Summary
`DiffSelection` tracks user line selections purely as a set of **positional indices** (`divergingLines`) into a diff's flattened line list, not by line content or a stable content hash. [1](#0-0) 
When the working directory status is refreshed, `updateChangedFiles` reattaches a file's *previous* `DiffSelection` object to the new `WorkingDirectoryFileChange` purely by matching the file's ID — it does not consult the new diff content at all. [2](#0-1) 
Later, `updateChangesWorkingDirectoryDiff` only narrows `selectableLines` to indices that still exist in the newly-loaded diff (`withSelectableLines`); it never checks whether the *content* at a given index is unchanged from when the user selected it. [3](#0-2) 
Finally, at commit time `applyPatchToIndex` calls `getWorkingDirectoryDiff` again to get the current diff and hands it, together with the file's (possibly stale) `selection`, to `formatPatch`, which maps `selection.isSelected(absoluteIndex)` straight onto the new diff's line list by index. [4](#0-3) [5](#0-4) 

### Finding Description
`formatPatch` never re-derives "what will actually be committed" from scratch before acting — analogous to `IStream` lacking a `balanceOf()`-equivalent to compute the correct withdrawal amount before `withdraw()` executes. Here the "amount" is the set of diff-line indices considered included in the commit, and the missing "balance check" is: *is the line at index N in the freshly-loaded diff still the same line the user selected N against?*

If the file's on-disk content changes shape (lines inserted/removed above the hunk the user was editing) between the time the user makes a partial selection and the time `applyPatchToIndex`/`formatPatch` run, hunk boundaries and `unifiedDiffStart` offsets shift, but the cached `divergingLines` set of absolute indices does not shift with it. `formatPatch` will then evaluate `selection.isSelected(absoluteIndex)` against lines that are no longer the ones the user actually selected/deselected — including or excluding lines that were never reviewed by the user in that state.

Repository-controlled/attacker-influenced ways this shape-change occurs after a user has already made a partial selection but before commit fires include:
- A cloned/fetched repository using `.gitattributes` clean/smudge filters or a `post-checkout`/`post-merge` hook that rewrites tracked file content during a `pull`/`fetch`+merge that runs concurrently with an in-progress partial commit selection.
- Any background re-diff triggered by Desktop's file watcher picking up a change to the file mid-selection (e.g., a build tool, linter, or format-on-save integration mutating the file).

None of the existing code paths (`updateChangedFiles`, `updateChangesWorkingDirectoryDiff`) validate line *content* — only line *existence/type* — before the stale selection is reused, and `formatPatch`/`applyPatchToIndex` perform no independent verification either.

### Impact Explanation
The commit or discard patch generated can silently include lines the user intended to exclude, or exclude lines the user intended to include, because the "amount" (selected-line set) was never recomputed/validated against the current diff before the irreversible git action (`git apply --cached` / commit) executed. This is a silent corruption of what the user commits, matching the accepted impact category directly.

### Likelihood Explanation
Requires a race between (a) a user making a partial line selection on a file and (b) that file's diff shape changing (via a filter/hook/background process tied to repository content or a concurrent git operation) before the commit action is taken. This does not require local/physical access, admin rights, or prior malware — only attacker-influenced repository configuration (gitattributes filters/hooks) or a naturally-occurring background refresh, both of which are part of normal Desktop usage flows.

### Recommendation
Before generating the commit/discard patch, re-validate the cached `DiffSelection` against the freshly-loaded diff by content (e.g., diffing hunk headers/line text at each previously-selected index, not just checking the index still exists) and drop/warn on any selection whose underlying content has changed, rather than blindly replaying positional indices via `formatPatch`/`formatPatchToDiscardChanges`.

### Proof of Concept
1. Modify `file.txt` locally so it has two separate hunks; partially select lines only in the second hunk (leave first hunk fully deselected) via the Desktop UI — this stores absolute indices in `DiffSelection.divergingLines`.
2. Before committing, trigger a change to the file's diff shape without changing the semantic content the user cares about — e.g., a `.gitattributes`-driven `clean` filter (which can be shipped inside a cloned repository) rewrites line endings/whitespace at the top of the file, shifting hunk boundaries and `unifiedDiffStart` offsets for the second hunk.
3. Desktop's background status/diff refresh (`updateChangesWorkingDirectoryDiff`) reloads the diff and only narrows `selectableLines`; it keeps the old `divergingLines` index set as-is. [6](#0-5) 
4. User clicks "Commit". `applyPatchToIndex` re-fetches the diff and calls `formatPatch`, which evaluates `file.selection.isSelected(absoluteIndex)` against the new hunk layout. [7](#0-6) 
5. Because the index-to-content mapping shifted, lines from the (originally deselected) first hunk area can now land at indices the user had marked "selected," and vice versa — the resulting commit contains different content than what the user reviewed and intended, with no error or warning shown.
