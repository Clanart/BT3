## Analysis

The Alpine advisory describes an **interpretation conflict**: multiple boundary parameters in one MIME message let different consumers (mail scanner vs. mail client) disagree on how to segment the message, so a security check (banned-file/malware scan) inspects one interpretation while the actual delivered content is another. The transferable invariant is: *a single logical entity has more than one textual representation, and a security-relevant "duplicate" check fails to normalize across representations, letting attacker-chosen input silently override a value that was already validated/set*.

In `google.protobuf.json_format`, a Protobuf field has two valid JSON textual spellings — the canonical `json_name` (lowerCamelCase) and the raw proto `field.name` (snake_case) — exactly analogous to "multiple boundary parameters" naming the same logical thing. The duplicate-field guard in `_ConvertFieldValuePair` only tracks the raw JSON key string, not the resolved `FieldDescriptor`: [1](#0-0) [2](#0-1) [3](#0-2) 

Because `names` stores the literal key (`"int32Value"` vs `"int32_value"`), two keys that resolve to the *same field* both pass the `if name in names` test, so the "no multiple X fields" rejection is bypassed and the second occurrence silently overwrites the first — this is confirmed as an acknowledged implementation oversight in the test suite itself: [4](#0-3) 

By contrast, the C++/upb JSON parser and the Java `JsonFormat` implementation track "seen" state by resolved `FieldDescriptor`/oneof identity, not by raw string, so alternate spellings are correctly caught as duplicates: [5](#0-4) [6](#0-5) 

This means an ordinary client submitting bounded ProtoJSON via the public `json_format.Parse` API in the pure-Python implementation can supply the same field twice under different valid spellings; any application logic that inspects/validates the first-seen value (e.g., reading `message.int32Value` conceptually "before" a second aliased key is applied, or code paths that assume the duplicate-key rejection guarantees single-assignment) will disagree with the final parsed value, which is silently taken from whichever alias appears last in the object — the same "last consumer wins, differently from what the checker saw" pattern as the MIME analog. This is already flagged in-repo as unintended ("non-spec... oversight bug"), so it's a genuine, reproducible interpretation-conflict differential in a production public parsing path, not a theoretical concern.

### Title
JSON duplicate-field detection bypass via alternate field-name spelling in `json_format.Parse` (pure-Python) - (File: python/google/protobuf/json_format.py)

### Summary
`_Parser._ConvertFieldValuePair` rejects duplicate JSON keys by comparing the literal JSON key string, not the resolved protobuf `FieldDescriptor`. Since every non-extension field has two legal spellings (`json_name` camelCase and `field.name` snake_case), an attacker can submit both spellings for the same field in one JSON object; the "must not have multiple X fields" safety check does not fire, and the field silently takes the value of whichever spelling occurs later in the object — an interpretation conflict directly analogous to CVE-2024-28054's multiple-boundary ambiguity.

### Finding Description
`_ConvertFieldValuePair` resolves each incoming JSON key to a `field` via `fields_by_json_name` or `fields_by_name` [2](#0-1) , then checks for duplicates using the raw key text (`if name in names`) rather than the resolved field object [3](#0-2) . Two different JSON keys that map to the same `FieldDescriptor` therefore both pass the check and both get applied, with the second silently overwriting the first (`_SetFieldOrExtension`/`_ClearFieldOrExtension` are keyed on the field, not the JSON text). The comparable C++/upb (`RecordAsSeen` keyed by field/oneof identity, `src/google/protobuf/json/internal/parser.cc:1256-1267`) and Java (`builder.hasField(field)` in `JsonFormat.java`) implementations correctly detect this case because they track state per resolved field, not per literal string — showing the check is feasible and was simply omitted in the pure-Python path.

### Impact Explanation
Any consuming application that treats "duplicate JSON keys must be rejected" as a guarantee that a field can only be set once per request (e.g., using presence/duplication as an integrity or replay-safety signal, or performing a security decision on an initially-parsed value before a later aliased key overrides it) can be bypassed by a client sending the same logical field under both spellings. The effect mirrors the MIME advisory: whichever component/observer looks at the "first" or a differently-scanned representation reaches a different conclusion than the value that is ultimately stored in the message, enabling an integrity/interpretation-conflict bypass of application-level validation built on top of `json_format.Parse`.

### Likelihood Explanation
High reachability: this is default behavior of the standard public `google.protobuf.json_format.Parse` API on any message with at least one field, requires no special schema, and needs only a small, fully bounded JSON payload from an ordinary client. It is already reproduced by an existing (accepted-as-buggy) test in the repository, confirming both correctness and ease of triggering.

### Recommendation
Track "already seen" state by resolved `FieldDescriptor` (and by containing `oneof`, as already done for oneofs) rather than by the raw JSON key string in `_ConvertFieldValuePair`, matching the approach already used by the C++/upb and Java JSON parsers, so that any alternate spelling of the same field is correctly rejected as a duplicate.

### Proof of Concept
Using the existing repository test as the reproduction (pure-Python backend, default `ignore_unknown_fields=False`):
```python
parsed_message = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
assert parsed_message.int32_value == 2  # second spelling silently wins; no ParseError raised
```
This matches [7](#0-6) , which the test file itself annotates as unintended, non-spec behavior — the duplicate-field checker's intended rejection is bypassed whenever the two occurrences are spelled differently but resolve to the same field.
