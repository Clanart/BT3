### Title
Panic on out-of-range participant index in PedPoP blame path crashes the node - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
Analogous to CVE-2015-8915 (crafted input → invalid read → crash), PedPoP's blame-verification path performs unchecked `HashMap` indexing on attacker-supplied `Participant` indexes. `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` directly, panicking if the accuser names a participant that was never registered (any `Participant` in `(n, u16::MAX]`).

### Finding Description
`Participant::new` accepts any nonzero `u16`; the `(n, u16::MAX]` range is only rejected where callers explicitly compare against `params.n()`. In the blame flow, neither the public `AdditionalBlameMachine::blame` nor `BlameMachine::blame` bounds-check `sender`/`recipient` before they are used as `HashMap` keys:

- `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` (line 388). `enc_keys` only contains indexes `1..=n` inserted via `register`/`AdditionalBlameMachine::new` (lib.rs lines 656–660). `decryptor` is the `recipient` argument, which is the accused/accuser index supplied with the blame message — an arbitrary `Participant`.
- `BlameMachine::blame_internal` evaluates `self.commitments[&sender]` (lib.rs line 599) with the same problem for the `sender` index.

An attacker who submits a blame accusation naming `Participant(n + 1)` (or any nonzero index with no registered commitments) reaches one of these indexing operations after supplying a `msg` whose Schnorr PoP verifies (they control `msg.key` and can sign `pop_challenge` for it), causing a panic instead of an orderly blame/fault return.

### Impact Explanation
A single crafted blame message deterministically panics the processor/library caller during DKG fault adjudication. This aborts the key-generation session and can crash the node handling the blame, a remote denial of service reachable by any participant able to submit blame — mirroring the "crafted input causes invalid read and crash" class of the reference CVE.

### Likelihood Explanation
The trigger requires only that the accuser supply an out-of-range participant index plus an `EncryptedMessage` with a valid PoP (trivially producible since the accuser chooses the ephemeral key). No collusion, no honest-party misbehavior, and no secret knowledge is needed. The only mitigating factor is whether the outer coordinator bounds `accused`/`accuser` to `1..=n` before constructing `Participant`; the crypto crate itself does not enforce it.

### Recommendation
Replace `HashMap` indexing with fallible lookups in `blame_internal`/`decrypt_with_proof` (e.g., `self.enc_keys.get(&decryptor)` / `self.commitments.get(&sender)`), returning `InvalidProof` or identifying the accusing party as faulty when either participant index is unknown. Additionally, validate `sender <= n` and `recipient <= n` in `BlameMachine::blame` and `AdditionalBlameMachine::blame` before proceeding.

### Proof of Concept
1. Run PedPoP with `n` participants; construct `AdditionalBlameMachine::new(context, n, commitment_msgs)` with all `1..=n` registered.
2. As accuser, call `blame(sender = Participant(1), recipient = Participant(n + 1), msg, Some(proof))` where `msg` is an `EncryptedMessage` with `key = G * k` and a valid `pop` Schnorr signature over `pop_challenge(context, R, key, sender, msg_bytes)` for attacker-chosen `k`, and `proof` is a valid `EncryptionKeyProof` (`key = msg.key * b`, `dleq` proving equality of dlog across `[G, msg.key]` → `[enc_key_b, proof.key]` for the accuser's own registered `enc_key_b`).
3. `decrypt_with_proof` verifies `msg.pop`, verifies the DLEq against `self.enc_keys[&decryptor]` — index `n + 1` absent → `HashMap` index panic.
4. Alternatively, omit step 2's proof and use `sender = Participant(n + 1)`: once `decrypt_with_proof` reaches `self.commitments[&sender]` in `blame_internal` (line 599), it panics on the missing key. [1](#0-0) [2](#0-1) [3](#0-2)

    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
