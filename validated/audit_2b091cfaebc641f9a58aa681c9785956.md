### Title
Deposit memo (`data`) and `presumed_origin` mis-attributed to every Serai-bound output in a Bitcoin transaction - ([File: processor/src/networks/bitcoin.rs])

### Summary
The Bitcoin `get_outputs` implementation scans a transaction for any outputs paying to the current Serai multisig key, then unconditionally copies the transaction's single extracted `InInstruction` (`Self::extract_serai_data(tx)`) and a single `presumed_origin` (derived only from `tx.input[0]`) onto *every* `External`-kind output found in that transaction. A transaction's per-output property — which deposit memo / origin belongs to which output — is discarded, and one transfer's descriptor is applied to all Serai-bound outputs in the same transaction.

### Finding Description
In `get_outputs`, all outputs matching the scanner across the whole transaction are collected into `outputs`, then a single `data` value is extracted from the transaction and a single `presumed_origin` is computed from `tx.input[0]`'s spent output. Every output whose `kind == OutputType::External` receives `output.data.clone_from(&data)` and every output receives `output.presumed_origin.clone_from(&presumed_origin)` [1](#0-0) .

The `kind` classification itself is recovered only from the script-matched offset (`kinds[offset_repr_ref]` at line 695), so any output paying to the plain (offset-zero) external address is `External` regardless of which input funded it or which instruction it relates to. Bitcoin transactions routinely contain multiple inputs from different parties (CoinJoin, PayJoin, batched deposits by exchanges/services). In such a transaction, the `InInstruction` embedded via the `OP_SHA256 <hash> OP_EQUALVERIFY` witness/script path belongs to the depositing input, yet it is stamped onto every Serai-bound output in that transaction, and `presumed_origin` (used for refunds) is taken solely from `input[0]` regardless of which input actually funded a given output.

This mirrors the XSA-214 bug class: a property claimed/associated with a transferred object is not correctly bound to that object, so privileged handling is applied based on mismatched metadata.

### Impact Explanation
- An attacker who can get an output paying to the Serai external address included in the same transaction as a victim's deposit (PayJoin/CoinJoin-style construction, or a service batching withdrawals) causes their `InInstruction` (e.g., `Shorthand::transfer` to the attacker's Serai address) to be attached to the victim's `ReceivedOutput`. If downstream crediting honors `output.data()` per output, the victim's deposit is credited/minted to the attacker's destination — theft of bridged funds.
- Refund flows relying on `presumed_origin` can be redirected to `tx.input[0]`'s funder rather than the actual funder of a specific output.

### Likelihood Explanation
Reachable by an unprivileged party sending ordinary on-chain Bitcoin transactions; no validator or threshold corruption needed. Exploitation requires co-constructing a multi-input transaction with a victim (as PayJoin/CoinJoin routinely do) or batching scenario; probability is moderate but the primitive is fully attacker-controlled. Severity hinges on consumers of `data`/`presumed_origin`, which I could not fully trace within the available iterations — the mis-binding itself is concretely present.

### Recommendation
Bind `data` to the specific output(s) the `InInstruction` actually commits to (e.g., require the instruction to name an output index/amount, or only attach `data` to the output in the same position the protocol defines), and derive `presumed_origin` per output from the input that provably funded it — or mark origin ambiguous when a transaction has multiple distinct funders and refuse to set `presumed_origin`.

### Proof of Concept
1. Victim and attacker co-sign a PayJoin-style transaction with inputs from both.
2. Attacker places an `InInstruction` (witness-embedded `OP_SHA256 <hash> OP_EQUALVERIFY` script with the message) crediting their own Serai address.
3. The transaction has two outputs to the Serai external address: attacker's small output and the victim's larger deposit.
4. `get_outputs` scans both outputs as `External` and assigns the attacker's `data` plus `tx.input[0]`-derived `presumed_origin` to both [2](#0-1) .
5. The victim's outpoint is processed with the attacker's transfer instruction — funds reported received are credited to the wrong destination.

  async fn get_outputs(&self, block: &Self::Block, key: ProjectivePoint) -> Vec<Output> {
    let (scanner, _, kinds) = scanner(key);

    let mut outputs = vec![];
    // Skip the coinbase transaction which is burdened by maturity
    for tx in &block.txdata[1 ..] {
      for output in scanner.scan_transaction(tx) {
        let offset_repr = output.offset().to_repr();
        let offset_repr_ref: &[u8] = offset_repr.as_ref();
        let kind = kinds[offset_repr_ref];

        let output = Output { kind, presumed_origin: None, output, data: vec![] };
        assert_eq!(output.tx_id(), tx.id());
        outputs.push(output);
      }

      if outputs.is_empty() {
        continue;
      }

      // populate the outputs with the origin and data
      let presumed_origin = {
        // This may identify the P2WSH output *embedding the InInstruction* as the origin, which
        // would be a bit trickier to spend that a traditional output...
        // There's no risk of the InInstruction going missing as it'd already be on-chain though
        // We *could* parse out the script *without the InInstruction prefix* and declare that the
        // origin
        // TODO
        let spent_output = {
          let input = &tx.input[0];
          let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
          spent_tx.reverse();
          let mut tx;
          while {
            tx = self.rpc.get_transaction(&spent_tx).await;
            tx.is_err()
          } {
            log::error!("couldn't get transaction from bitcoin node: {tx:?}");
            sleep(Duration::from_secs(5)).await;
          }
          tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
        };
        Address::new(spent_output.script_pubkey)
      };
      let data = Self::extract_serai_data(tx);
      for output in &mut outputs {
        if output.kind == OutputType::External {
          output.data.clone_from(&data);
        }
        output.presumed_origin.clone_from(&presumed_origin);
      }
    }
