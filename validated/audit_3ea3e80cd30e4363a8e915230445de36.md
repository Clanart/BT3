### Title
Shared `_params.dispatcher` balance-sweep lets an attacker misattribute donated/residual tokens into their own order escrow - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()`'s predispatch path measures how much of each input token to escrow by reading `IERC20(token).balanceOf(dispatcher)` on the shared `_params.dispatcher` contract and sweeping its *entire* balance into the gateway, instead of using only the amount that the specific predispatch call actually produced for this order. This is the same broken invariant as the `FortaStakingVault` report: a contract's raw token balance — which anyone can inflate by sending tokens directly to it — is used as the authoritative "amount transferred/withdrawn" instead of a value derived from the specific operation.

### Finding Description
In `placeOrder`, when an order carries `predispatch.call`/`predispatch.assets`, the gateway:

1. Transfers the predispatch input assets to the shared `dispatcher` (`_params.dispatcher`), which is a single persistent contract address, not an ephemeral per-order deployment: [1](#0-0) 

2. Executes the predispatch calldata via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`. [2](#0-1) 

3. For each required input token, reads `dispatcher`'s **current balance** (not the amount the predispatch call actually produced) and builds a sweep call that transfers that *entire* balance to the gateway: [3](#0-2) 

4. The measured `received` delta on the gateway's own balance becomes `order.inputs[i].amount`, which is then written into the order's escrow ledger and used to compute the commitment hash and protocol fee: [4](#0-3) [5](#0-4) 

Because `dispatcher` is a single, fixed, publicly-known contract address reused across every `placeOrder` call that uses predispatch calldata (as opposed to a fresh per-order distributor as in the `InactiveSharesDistributor` pattern), any residual token balance left in it — from a previous predispatch execution that produced excess output, from a partially-consumed swap, or from tokens an attacker sends to it directly — is indistinguishable from the tokens this specific order's predispatch call produced. The code has no way to attribute the swept balance to the specific caller/order; it simply trusts `balanceOf(dispatcher)` at read-time.

This mirrors exactly the flaw described in the seed report: `InactiveSharesDistributor` used `IERC20(FORT).balanceOf(address(this))` instead of the value returned by `FortaStaking.withdraw(...)`, letting anyone corrupt the accounting by sending tokens to the distributor. Here, `IntentGatewayV2` uses `IERC20(token).balanceOf(dispatcher)` instead of tracking the actual output produced by `ICallDispatcher(dispatcher).dispatch(...)` for this specific call.

### Impact Explanation
An attacker can:
- Send tokens directly to the known `dispatcher` address (or exploit normal dust left behind by a prior order's predispatch execution that over-produced output relative to what that order required), then
- Call `placeOrder` with a minimal predispatch that legitimately produces just enough of the required token to pass the `balance < requiredAmount` check, and
- Have the *entire* balance (including the previously-donated/residual tokens that do not belong to them) swept into their own order's escrow, recorded under `_orders[commitment][token]`.

The attacker can subsequently cancel the order (or have it filled) to redeem the inflated escrow, effectively stealing tokens that were deposited by a different party or were unattributed protocol dust sitting in the shared dispatcher. This is a genuine "wrong beneficiary/amount" fund-diversion path through a public, unprivileged entry point (`placeOrder`), matching the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" criteria — no relayer, prover, or admin compromise is required.

### Likelihood Explanation
Exploitability depends on the shared `dispatcher` actually holding an attacker-attributable residual balance at the moment of the sweep. This can happen either passively (protocol dust from a previous order's predispatch producing more output than that order needed, since only the *required* amount is checked, not an exact match) or actively (an attacker directly transferring tokens to the known `dispatcher` address before calling `placeOrder`). Because `dispatcher` is a fixed, discoverable address and the sweep uses "current full balance" rather than a per-call delta scoped to the actual dispatch outcome, no privileged position or timing race with a relayer/prover is needed — only ordinary transaction sequencing that any unprivileged user controls.

### Recommendation
Do not sweep `balanceOf(dispatcher)`. Instead:
- Snapshot `dispatcher`'s balance for each input token **before** transferring the predispatch assets and executing the dispatch call, then only sweep/attribute the **delta** produced by this specific `dispatch()` invocation (mirroring the pattern already correctly used in the non-predispatch branch, lines 289-291, which snapshots `balanceOf(address(this))` immediately before the transfer).
- Alternatively, deploy a fresh, single-use `dispatcher`/executor per order (analogous to fixing the `InactiveSharesDistributor` bug by using the `withdraw()` return value instead of a shared balance), so no cross-order or attacker-donated balance can be swept.
- Any true leftover dust in the shared dispatcher should be swept exclusively via the governance-only `SweepDust` path already present in the type definitions, not implicitly folded into a user's order escrow.

### Proof of Concept
1. Governance configures `_params.dispatcher = D` (a persistent, shared `ICallDispatcher`).
2. Attacker directly sends `1000` units of token `T` to `D` (a simple `IERC20.transfer`), or waits for a legitimate prior order's predispatch call to leave `T` dust behind in `D` (this can occur any time `balance` measured after the predispatch call exceeds that order's `requiredAmount`, since the excess is only logged as `DustCollected`, not swept out of `D`).
3. Attacker calls `placeOrder` with `order.predispatch.call` crafted so that its `ICallDispatcher(D).dispatch(...)` produces at least a token amount `T` equal to `requiredAmount` (a small legitimate amount, e.g. `1`), satisfying `balance >= requiredAmount` at line 244.
4. The gateway builds `transferCalls[i]` to sweep `D`'s **entire** `T` balance (`1000 + 1`), not just what the attacker's predispatch call produced.
5. `received = 1001` is credited into `_orders[commitment][T]` (minus protocol fee), i.e., the attacker's order escrow now includes `1000` units of `T` that were never actually contributed by the attacker for this order.
6. Attacker cancels the order (or lets a solver fill it and captures cross-chain settlement), reclaiming the inflated escrow — extracting tokens that belonged to a different party or to unattributed protocol dust.

Note: I was not able to fully trace the `cancel`/refund code path (`ExtrinsicIntents.sol` / `IntrinsicIntents.sol`) within the available iterations to confirm the exact refund mechanics line-by-line; the escrow-crediting root cause in `placeOrder` (steps 1-5 above) is fully verified from source, but confirming the precise cancel-and-redeem call sequence would benefit from a deeper Devin session with full repository access.
