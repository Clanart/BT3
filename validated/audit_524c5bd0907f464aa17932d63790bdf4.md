### Title
Unauthenticated blame submissions panic `BlameMachine`/`AdditionalBlameMachine` via unindexed `Participant` lookups, crashing the validator (availability) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2023-21875 is an encryption-component flaw whose impact is unauthorized modification of protected data and a repeatable crash/DoS. The closest analog in Serai's in-scope code is the PedPoP DKG blame/decryption path (`crypto/dkg/pedpop`), which performs encryption (ECDH + ChaCha20 under `cipher()`) of secret shares and evaluates publicly-submitted blame statements. `blame_internal` / `Decryption::decrypt_with_proof` index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `Participant` values taken directly from the accusation. `Participant` carries no `<= n` bound (callers must validate it, as `sign.rs` does with its explicit `InvalidParticipant` check), and `Decryption::register`/`AdditionalBlameMachine::new` only populate indexes `1..=n`. An accusation naming a `recipient` or `sender` outside the registered set (or one that never registered an encryption key) panics on the `HashMap` index, producing a repeatable crash of the node evaluating blame — the same complete-DoS impact class as the CVE, reachable by an unprivileged party via untrusted bytes fed to `EncryptedMessage::read` plus the public `blame` API.

### Finding Description
- `EncryptedMessage::read` accepts attacker-controlled bytes for `key`, `pop`, and `msg` (`crypto/dkg/pedpop/src/encryption.rs:171-177`).
- `BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender`/`recipient` `Participant` arguments and an optional `EncryptionKeyProof` entirely from the caller (`crypto/dkg/pedpop/src/lib.rs:623-632`, `674-682`). `AdditionalBlameMachine` is explicitly designed for evaluators who were not DKG members, i.e., anyone arbitrating blame (`lib.rs:639-648`).
- `blame_internal` calls `Decryption::decrypt_with_proof(sender, recipient, msg, proof)` (`lib.rs:582`).
- Inside `decrypt_with_proof`, when `proof` is `Some`, the expression `self.enc_keys[&decryptor]` is evaluated as an argument to `DLEqProof::verify` before any bounds check (`encryption.rs:383-390`). `enc_keys` only contains entries for participants registered via `Decryption::register`/`Encryption::register` (`encryption.rs:351-362`, `452-458`), which `AdditionalBlameMachine::new` populates strictly for `1..=n` (`lib.rs:656-660`). A `recipient` participant index `> n` (valid `Participant`, never registered) indexes a missing key → panic.
- Similarly, `self.commitments[&sender]` (`lib.rs:598`) panics for any `sender` not in the commitments map, and `Decryption::register` asserts on re-registration (`encryption.rs:356-359`).
- The attacker can satisfy the preceding `msg.pop.verify` gate (`encryption.rs:374-379`) because `pop_challenge` binds `sender` as a claimable label (`encryption.rs:302-324`): the accuser forges an `EncryptedMessage` with a fresh per-message key and signs the PoP over the arbitrary `sender` index they chose, then supplies `proof: Some(..)` (contents irrelevant — the panic occurs while evaluating verify's arguments).

### Impact Explanation
A repeatable panic (complete crash/hang) of any node or arbitrator evaluating blame — matching the CVE's availability impact. In Serai's deployment, blame evaluation is invoked when handling `VerifyBlame`-style messages; a crash there aborts the DKG adjudication and can take down the validator process. Integrity is also affected indirectly: a fabricated accusation crashes the blame arbiter, preventing legitimate fault attribution.

### Likelihood Explanation
Reachable by any unprivileged party who can submit an accusation (`sender`, `recipient`, `EncryptedMessage`, `EncryptionKeyProof`) to the blame API; no threshold collusion, leaked keys, or curve tricks needed. Required conditions are minimal: pick an out-of-range `Participant`, craft a self-signed PoP over it (free, since the attacker knows their own key), and pass a `Some` proof. Likelihood is gated only by how the surrounding protocol exposes blame submission, hence Medium rather than High.

### Recommendation
Validate `sender`/`recipient` in `blame_internal`/`decrypt_with_proof` against the registered participant set (`1..=n` and presence in `enc_keys`/`commitments`) and return a `PedPoPError`/`DecryptionError` instead of indexing. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` + error propagation, and make `Decryption::register` return `Result` rather than asserting on duplicates.

### Proof of Concept
1. Build `AdditionalBlameMachine::new(context, n, commitment_msgs)` for a completed `n`-party PedPoP run (registers `enc_keys` only for `Participant(1..=n)`).
2. Attacker constructs `EncryptedMessage` with a random scalar `k`, `key = G*k`, and `pop = SchnorrSignature::sign(k, nonce, pop_challenge(context, R, key, sender = Participant(n+5), ciphertext))` — valid since the signer controls `k` and chooses the `sender` label arbitrarily.
3. Call `blame(sender = Participant(1), recipient = Participant(n+5), msg, proof = Some(any EncryptionKeyProof))`.
4. `decrypt_with_proof` verifies the PoP (passes), reaches `if let Some(proof)`, and evaluates `self.enc_keys[&Participant(n+5)]` — the index panics ("key not found"), crashing the evaluator. Using `sender = Participant(n+5)` and reaching `self.commitments[&sender]` panics identically.

(Note: I did not confirm `Participant::new`'s exact bounds in `crypto/dkg/src/lib.rs` — the explicit `> n` OOB check in `crypto/frost/src/sign.rs:302-304` strongly indicates `Participant` permits indexes beyond `n`, but if it internally capped at `u16::MAX` participants the out-of-range index is still constructible.)
