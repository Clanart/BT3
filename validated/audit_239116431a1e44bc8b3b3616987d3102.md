### Title
Cross-purpose signature replay via undomain-separated message hash lets an attacker force-consume a relayer's fee-withdrawal nonce - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`pallet-relayer` uses one shared per-`(address, state_machine)` nonce counter (`Nonce<T>`) to protect two structurally different signed actions: the beneficiary-redirect authorization inside `accumulate_fees` and the `withdraw_fees` extrinsic. Both actions hash their signed payload with the exact same SCALE-encoded tuple shape `(nonce, state_machine, beneficiary)`, so a signature a relayer produces for one action is byte-identical to, and therefore valid for, the other action. This mirrors the UMA bug class: a commitment/signature that is not bound to enough context (here, the *purpose*/call-site of the signature) can be copied and reused somewhere it was never intended for.

`withdrawal.rs` builds its signed payload with: [2](#0-1) 

```rust
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
    if let Some(beneficiary) = beneficiary {
        return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
    }
    sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
```

When `beneficiary` is `Some`, both functions SCALE-encode the identical tuple shape `(u64, StateMachine, bytes)` — `&[u8]` and `Vec<u8>` encode identically under SCALE — so `beneficiary_message(n, sm, b) == message(n, sm, Some(b))` for the same `n`, `sm`, `b`. Both call sites read the *same* nonce counter and increment the *same* storage item: [3](#0-2) [4](#0-3) 

`accumulate_fees` and `withdraw_fees` are both unsigned extrinsics (`ensure_none(origin)`), so anyone can submit either call as long as they supply a signature that verifies: [5](#0-4) 

Because `WithdrawalProof.commitments`/`source_proof`/`dest_proof` require only *publicly reconstructible* state proofs (no relayer signature needed for that part), an unprivileged attacker who observes a relayer's `withdraw_fees` transaction sitting in the mempool (containing `signature = sign_R(message(nonce=N, chain=C, Some(B)))`) can extract that signature and resubmit it as the `beneficiary_details` field of a freshly built `accumulate_fees(withdrawal_proof)` call for any already-verifiable, unclaimed delivery commitment attributed to the same relayer `R` on chain `C`. The pallet recomputes `beneficiary_message(N, C, B)`, which is bit-identical to what `R` signed, so `signature.verify(...)` succeeds and `delivered_by == recovered`. This front-run:
- Consumes nonce `N` for `(R, C)` via `accumulate_fees`'s own `Nonce::try_mutate` increment.
- Causes `R`'s pending `withdraw_fees(nonce=N, ...)` to subsequently fail verification (the stored nonce is now `N+1`, so the recovered signer no longer matches `R`), forcing the relayer to re-sign and resubmit.

### Impact Explanation
This breaks the intended one-signature-one-action invariant of the relayer fee pallet: a signature scoped to authorizing a *withdrawal* is also valid as an authorization for an unrelated *fee-accumulation redirect*, and vice versa, because neither payload embeds a domain/purpose tag or the call being authorized. An unprivileged attacker can weaponize a captured, still-valid signature to front-run and desynchronize a relayer's nonce, causing their legitimate `withdraw_fees` call to be rejected (transaction manipulation / logic attack against the nonce replay-protection scheme) and forcing repeated re-signing, and more broadly demonstrates that the signed-message construction in this pallet fails to bind the action type, which is exactly the missing-context defect the source report calls out.

### Likelihood Explanation
Any relayer's `withdraw_fees`/`accumulate_fees` unsigned extrinsics pass through the public transaction pool before inclusion, so the signature bytes are observable by anyone monitoring the mempool. Constructing the competing `accumulate_fees` call requires only public state-proof data for a commitment already attributable to the target relayer — no privileged key, relayer, prover, or governance role is needed, satisfying the "unprivileged attacker" bar. The main constraint is timing (front-running before the original `withdraw_fees` lands), which is a normal capability for any chain observer/searcher.

### Recommendation
Domain-separate the two signed payloads so a signature produced for one action can never satisfy verification for the other, e.g. prefix each hash with a distinct constant/tag (`b"ACCUMULATE_BENEFICIARY"` vs `b"WITHDRAW_FEES"`), or include a call-type discriminant/enum in the encoded tuple before hashing. Consider also using disjoint nonce counters (or a single nonce space where the message unconditionally encodes the specific call variant) so consuming a nonce in one flow cannot be mistaken for authorization of the other.

### Proof of Concept
1. Relayer `R` broadcasts `withdraw_fees(WithdrawalInputData { signature: sign_R(message(N, C, Some(B))), dest_chain: C, beneficiary: Some(B) })` to the mempool.
2. Attacker observes the pending extrinsic and extracts `signature`.
3. Attacker builds any valid `WithdrawalProof` for chain `C` whose recovered `delivery_address == R` (using public state proofs of an unclaimed request `R` already delivered), sets `beneficiary_details = Some((B, signature))`, and submits `accumulate_fees(withdrawal_proof)` before `R`'s `withdraw_fees` lands.
4. `accumulate.rs::accumulate` recomputes `beneficiary_message(N, C, B)`, which equals `message(N, C, Some(B))`; signature verification succeeds; `Nonce::<T>` for `(R, C)` is incremented to `N+1`.
5. `R`'s original `withdraw_fees(nonce=N, ...)` extrinsic subsequently executes against the now-stale nonce `N`, `message(N, C, Some(B))` no longer matches the current on-chain nonce state check path (nonce read fresh is `N+1`), signature verification fails, and the withdrawal reverts — demonstrating the cross-call replay and resulting denial-of-withdrawal.
