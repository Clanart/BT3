### Title
Point-in-time (non-time-weighted) `getRewardablePercentWAD` in `_calExpireForfeit` lets a user relock right before claiming to escape forfeiture on bonus-token rewards - (File: `rewards/vlMGPBaseRewarder.sol`)

### Summary
`_sendReward`/`_calExpireForfeit` in `vlMGPBaseRewarder.sol` compute the forfeitable share of *any* accrued reward token (MGP and bonus tokens alike) using `vlMGP.getRewardablePercentWAD(_account)` evaluated at the exact block of the claim, not a time-weighted measure over the full accrual period covered by `userRewards`. Because a user can cheaply mutate their lock/cooldown composition (e.g. relock a cooldown slot, trigger `getReward`, then immediately restart the unlock) right before the claim transaction executes, they can retroactively apply a favorable "mostly locked" percentage to rewards that in fact accrued mostly while they were unlocked/in cooldown.

### Finding Description
`_calExpireForfeit` is shared logic used by `_sendReward` for every reward token in `rewardTokens[]`, not just MGP: [1](#0-0) 

It reads the account's current `rewardablePercentWAD` and applies it directly to the entire pending `userRewards[_rewardToken][_account]` balance, which may have accrued via `rewardPerTokenStored` over an arbitrarily long prior period (since `earned`/`_earned` accumulate reward based on `balanceOf(_account)` = locked + in-cooldown balance across that whole period): [2](#0-1) 

`getRewardablePercentWAD` in `VLMGP.sol` computes the percent from the account's *current* `fullyInLock` vs `inCoolDown` split, with only a partial time-weighting applied to already-expired cooldown slots (and none for the "currently fully locked" component or for slots still in cooldown): [3](#0-2) 

Because `fullyInLock` is derived from `getUserTotalLocked`, which is just `stakingInfo` amount in `MasterMagpie` minus the amount currently sitting in cooldown slots, moving MGP from a cooldown slot back into "locked" state (relock) instantaneously increases `fullyInLock` and decreases `inCoolDown`, directly inflating `percent` toward `1e18` (0% forfeit) regardless of how long the tokens actually spent unlocked during the accrual window that generated `userRewards`. The `ReLock` event declared in `VLMGP.sol` (`event ReLock(address indexed user, uint256 slotIdx, uint256 amount);`) confirms such a state-toggling mechanism exists.

An attacker can therefore:
1. Hold vlMGP with an active/expired cooldown slot for an extended period, during which bonus reward tokens are queued and accrue in `rewardPerTokenStored` proportional to `balanceOf` (which counts cooldown/unlocked balance too).
2. Immediately before calling (or having `MasterMagpie.multiclaim` call) `getReward`/`getRewards`, relock the cooldown amount back into "locked" state.
3. Let `_calExpireForfeit` read the now-inflated `getRewardablePercentWAD`, yielding little-to-no `forfeitAmount` on the entire pending bonus-token balance.
4. Restart the unlock/cooldown again afterward, since nothing in `_sendReward`, `getReward`, or `getRewardablePercentWAD` locks in a time-weighted history of the account's lock state across the reward-accrual interval.

Existing protections (`nonReentrant`, `onlyMasterMagpie`, `updateRewards`) only guard against reentrancy/authorization on the claim call itself; none of them prevent the account's *lock composition* from being manipulated between reward accrual and the point-in-time forfeit calculation. The forfeited amount that should have gone to `_queueNewRewardsWithoutTransfer` (redistributed to properly-locked users) is instead paid directly to the manipulating account — this is a real transfer of value away from the pool of other lockers/faithfully-locked stakers, matching "theft of unclaimed yield."

### Impact Explanation
This causes direct economic loss to other lockers: forfeited bonus-token yield that should be redistributed via `_queueNewRewardsWithoutTransfer` to properly-locked participants is instead captured by the manipulating account, effectively stealing unclaimed yield. Since `_calExpireForfeit`/`_sendReward` apply generically to every token in `rewardTokens[]` (any externally queued bonus token via `queueNewRewards`), the exploit is not limited to MGP — any bonus reward token routed through `vlMGPBaseRewarder.getReward`/`getRewards` is exposed.

### Likelihood Explanation
Preconditions are attacker-affordable and require no privileged role: the attacker only needs to hold vlMGP with an unlock slot in progress (from ordinary `startUnlock`) and have accrued bonus-token rewards. Relocking/toggling lock state is a normal user action (no special permission), and the whole sequence (relock → claim → restart unlock) can be done within one or a few transactions, making it cheaply repeatable for every reward distribution cycle.

### Recommendation
Compute the forfeit percentage as a genuine time-weighted average of the account's locked/unlocked composition over the exact interval during which the pending `userRewards` accrued (e.g., snapshot/checkpoint the rewardable percentage at each `_updateFor` call and accumulate a weighted `userRewards`/`forfeitable` amount incrementally, rather than applying a single point-in-time percentage to the entire accumulated balance at claim time). At minimum, `_updateFor` should apply `_calExpireForfeit` incrementally each time `rewardPerTokenStored` advances, rather than allowing forfeiture to be deferred and computed once, at an attacker-chosen block, over the whole accrued balance.

### Proof of Concept
Foundry fork test plan:
1. Deploy/queue a bonus reward token via the reward manager into `vlMGPBaseRewarder` (`queueNewRewards`).
2. User A locks MGP and immediately calls `startUnlock` for most of the balance, leaving it in cooldown for a long duration while bonus rewards accrue (advance time, queue more bonus rewards).
3. Confirm via `calExpireForfeit`/`earned` that a large forfeit would apply given the account's mostly-unlocked/cooldown state.
4. Immediately before calling `MasterMagpie.multiclaim` (which triggers `getReward`), have User A perform the relock action that moves the cooldown slot's amount back to "locked" (per the `ReLock` mechanism), then claim, then re-start the unlock again in the same or immediately following transaction.
5. Assert: `toSend` bonus tokens received by User A are far greater than the time-weighted rewardable share computed by correctly integrating `getRewardablePercentWAD` over the true accrual period, and that `forfeitAmount` requeued via `_queueNewRewardsWithoutTransfer` is near zero despite the account being unlocked for most of the accrual window.

    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userVlmgpShare) internal view returns (uint256) {
        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**vlMGPDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
