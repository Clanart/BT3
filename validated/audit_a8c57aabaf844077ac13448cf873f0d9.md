### Title
Uncounted LP transfer fees in `WombatStaking.depositLP` cause receipt-token over-minting - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.depositLP` pulls LP tokens from the caller with `safeTransferFrom` using the caller-supplied `_lpAmount`, but then uses that same nominal `_lpAmount` — instead of the actual balance increase received by the contract — both to forward tokens into the Wombat master pool and to mint receipt tokens to the pool helper. If the LP token being staked has any transfer fee or rebasing/deflationary behavior (i.e. `transferFrom` delivers less than the amount requested, mirroring the reported USDT `transferFrom` fee issue), the contract will mint receipt tokens backed by fewer actual LP tokens than promised.

### Finding Description
In `depositLP`:
```solidity
function depositLP(
    address _lpAddress,
    uint256 _lpAmount,
    address _for
) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
    Pool storage poolInfo = pools[_lpAddress];

    // Transfer lp to this contract and stake it to wombat
    IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);

    _toMasterWomAndSendReward(_lpAddress, _lpAmount, true);
    IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);

    emit NewLPDeposit(_for, poolInfo.lpAddress, _lpAmount, poolInfo.receiptToken, _lpAmount);
}
``` [1](#0-0) 

This is inconsistent with the sibling `deposit` function in the same contract, which correctly measures the actual LP received via a before/after balance diff before minting or forwarding funds:
```solidity
uint256 beforeBalance = IERC20(poolInfo.lpAddress).balanceOf(address(this));
IWombatPool(poolInfo.depositTarget).deposit(...);
uint256 lpReceived = IERC20(poolInfo.lpAddress).balanceOf(address(this)) - beforeBalance;
_toMasterWomAndSendReward(_lpAddress, lpReceived, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived);
``` [2](#0-1) 

`depositLP` skips this measurement entirely and trusts `_lpAmount` as ground truth. Any transfer-fee, deflationary, or rebasing LP token onboarded for staking would cause the contract to actually hold less LP than `_lpAmount` while still minting receipt tokens (and crediting master-Wombat reward accounting) for the full nominal amount.

### Impact Explanation
Because receipt tokens are minted 1:1 with the nominal `_lpAmount` rather than the amount actually custodied, the receipt token supply becomes permanently over-collateralized relative to real LP holdings. This is a protocol-insolvency condition: later withdrawals (via `WombatStaking.withdraw`, which burns receipt tokens 1:1 against actual LP unstaked) will eventually be unable to satisfy all receipt-token holders, since the pool as a whole holds fewer underlying LP tokens than receipt tokens issued. Earlier depositors/withdrawers can drain the shortfall, leaving later ordinary users unable to redeem — a permanent freeze/loss of funds for those users.

### Likelihood Explanation
Exploitability depends entirely on whether a given pool's `lpAddress` charges a transfer fee. Wombat pool LP tokens are typically NOT fee-on-transfer, so this analog cannot be proven exploitable under the current in-scope configuration without evidence of such a token being (or becoming) an actively supported pool. This lowers confidence that this is concretely reachable today, but the code path itself contains the same root-cause pattern (trusting requested amount over verified received balance for an externally supplied token contract).

### Recommendation
In `depositLP`, measure the actual LP token balance delta received by the contract (as already done in `deposit`) and use that measured amount for `_toMasterWomAndSendReward` and for the receipt-token mint, instead of trusting the caller-supplied `_lpAmount`.

### Proof of Concept
1. Assume a pool is configured with an LP token that charges a transfer fee (e.g., 1%) on `transferFrom`.
2. A pool helper calls `WombatStaking.depositLP(lpToken, 100e18, user)`.
3. `safeTransferFrom(_for, address(this), 100e18)` executes, but the contract's actual LP balance only increases by 99e18 due to the fee.
4. `_toMasterWomAndSendReward(_lpAddress, 100e18, true)` and `IMintableERC20(receiptToken).mint(msg.sender, 100e18)` both use the nominal 100e18, not the 99e18 actually held.
5. Receipt token supply is now backed by less real LP than issued, creating a shortfall that surfaces as insolvency when receipt holders attempt to withdraw via `WombatStaking.withdraw`. [1](#0-0) [3](#0-2)
