PedPoP `calculate_share` attaches an ECDH-revealing blame proof before the message's proof-of-possession is ever verified - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` and immediately receives an `EncryptionKeyProof` (which reveals the ECDH shared key between the recipient's encryption key and the message's ephemeral key). If the decrypted bytes fail scalar deserialization (`C::F::from_repr`), the function returns `InvalidShare` with `blame: Some(blame)` early, without ever running `batch.verify_with_vartime_blame()` — so the per-message Schnorr PoP that was queued (but not yet checked) is skipped entirely. A malicious participant can exploit this to make honest participants publish blame proofs revealing the shared keys of other participants' messages, decrypting their secret shares and ultimately recovering the full group private key. This is the exact attack the PoP was added to prevent per the in-code commentary.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs:469-501`, `Encryption::decrypt` performs two things:

1. It queues the `msg.pop` Schnorr signature verification into the provided `BatchVerifier` under the caller-supplied `batch_id` (lines 479-485).
2. It unconditionally decrypts the message and constructs an `EncryptionKeyProof { key, dleq }` where `key = ecdh(enc_priv, msg.key)` — the shared key that decrypts the ciphertext (lines 487-499).

The code comments at `encryption.rs:84-91` explain why `pop` exists: without it, an observer Eve can replay Alice's per-message key `X` to Bob, cause Bob to issue blame, and Bob's blame reveals `bX` — the shared key decrypting Alice's real message to Bob. The PoP is the sole mitigation: a message "claiming to use X" can only be sent by someone knowing `X`'s discrete logarithm.

However, in `crypto/dkg/pedpop/src/lib.rs:476-482`:

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

If `from_repr` fails, the function returns early with `blame: Some(...)` — an `EncryptionKeyProof` attesting to the shared key for `msg.key` — even though the queued `BatchId::Decryption(l)` PoP statement was never verified. The later `batch.verify_with_vartime_blame()` call (lines 493-499) is never reached on this path. The PoP check — the "second factor" authenticating possession of the ephemeral key — is skipped whenever deserialization fails, mirroring the CVE class where an expired-session state skipped the second-factor confirmation.

An unprivileged DKG participant exploits this per recipient `v`:
- Observe an honest sender `j`'s `EncryptedMessage` to `v` and copy its ephemeral public key `K_{j→v}` (the wire format is readable via `EncryptedMessage::read`, `encryption.rs:171-177`).
- Send `v` a crafted `EncryptedMessage { key: K_{j→v}, pop: <invalid>, msg: <arbitrary bytes> }`.
- `v` computes the share keystream `cipher(context, ecdh(v.enc_priv, K_{j→v}))` over the garbage `msg`; with high probability (e.g. ~15/16 for a Ristretto-class scalar field where `l ≈ 2^252`) the result is a non-canonical scalar, `from_repr` fails, and `v` returns `InvalidShare` carrying `Some(blame)` that reveals `key = ecdh(v.enc_priv, K_{j→v})` plus a DLEq proof binding it to `v`'s registered `enc_key` and `K_{j→v}`.
- Once `v` publishes the blame (as the blame protocol requires), anyone can run `cipher(context, key)` to decrypt `j`'s genuine ciphertext to `v`, recovering the secret share `s_{j→v}`.

Repeating this for every honest sender `j` and every victim `v` yields all evaluations of every honest participant's polynomial, allowing reconstruction of every contributed secret — i.e., recovery of the entire group private key, even though every honest participant followed the protocol and blamed the "faulty" attacker.

The PoP does not save this: the early `from_repr` return path never checks whether the PoP statement (queued with `BatchId::Decryption(l)`) would have passed. The blame-selection logic at lines 493-497, which correctly maps a `Decryption(l)` failure to `blame: None`, is unreachable for this failure mode.

### Impact Explanation
Complete compromise of DKG confidentiality and of the resulting threshold key. A single malicious participant causes every honest participant to emit blame proofs that reveal the ECDH shared keys protecting honest-to-honest secret shares. Decrypting those shares lets the attacker reconstruct every participant's polynomial and hence the group's private scalar (the sum of all constant terms), unilaterally, while the protocol appears to have simply faulted with blame assigned to the attacker. Any funds or signing authority controlled by the resulting `ThresholdKeys` are fully compromised. This is a Critical key-share/key-recovery impact reachable purely through crafted bytes fed to `EncryptedMessage::read` / `calculate_share`.

### Likelihood Explanation
High. The attacker only needs to observe one `EncryptedMessage` per honest sender-victim pair (the protocol's own commentary assumes Eve can observe ciphertexts) and send one crafted message per victim. The `from_repr` failure that triggers the early return is near-certain for scalar fields whose order is well below `2^(8·len)` (e.g., Ristretto/ed25519 scalars, `2^252` order in a 32-byte encoding — ~94% success per attempt, per the same reasoning used by the `invalidate_share_serialization` test at `encryption.rs:228-238`), and the attacker may retry across sessions/messages regardless. No honest misbehavior, collusion, or timing assumption is required; a single faulty-appearing message is enough per leak.

### Recommendation
In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs), do not attach a blame proof when scalar deserialization fails before the PoP has been verified. Concretely: either
- verify the PoP for the offending message before constructing/attaching `blame` (e.g., drain and verify the queued `BatchId::Decryption(l)` statement on the `from_repr` failure path, returning `blame: Some(...)` only if the PoP is valid and `blame: None` otherwise), or
- restructure so `Encryption::decrypt` does not produce an `EncryptionKeyProof` until PoP validity is established, treating an unparseable plaintext under an unproven key identically to a PoP failure (`BatchId::Decryption(l)` → `blame: None`).

The invariant should be: a blame proof revealing an ECDH shared key is only ever emitted for a message whose `pop` verifiably proves knowledge of `msg.key`'s discrete logarithm under the claimed sender.
