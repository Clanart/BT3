### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/fee and max-weight checks, producing under-priced or oversized transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `getOracleData()` computing a capacity bound while omitting an additive term (`accruedToTreasury`), `SignableTransaction::new` computes the transaction weight, required fee, and the `MAX_STANDARD_TX_WEIGHT` check using only `payments` and `change`, while the actual transaction also carries the caller-supplied OP_RETURN `data` output. The omitted output inflates the real vsize/weight beyond the calculated bound, so the transaction is built with a fee below the intended `fee_per_vbyte` (and potentially below minimum relay fee) and can pass the standardness weight check while actually exceeding it.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` when `data` is supplied (lines 194-202), but both calls to `calculate_weight_vbytes` pass only `payments` and the optional `change` script:

- Line 204: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — used to derive `needed_fee = fee_per_vbyte * vbytes` (line 206) and the `TooLowFee` / `NotEnoughFunds` / `TooLargeTransaction` checks.
- Line 226: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — used when change is added.

`calculate_weight_vbytes` (lines 62-127) builds a template `Transaction` whose `output` list is derived exclusively from `payments` plus the optional `change` output; the `data` OP_RETURN output is never included. Consequently:

1. `needed_fee` and `fee_with_change` are lower than what `fee_per_vbyte` demands for the real transaction (the missing output is ~9 + up-to-80-byte pushdata ≈ up to ~90 vbytes).
2. The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 is evaluated against a weight that excludes the data output, so a transaction can be constructed that is actually non-standard (unbroadcastable) or pays a fee rate below the caller's specification and possibly below `DEFAULT_MIN_RELAY_TX_FEE`.

This mirrors the referenced Aave bug exactly: a bound calculation (`maxExternalDeposit` there; `weight`/`vbytes`/`needed_fee` here) omits an additive term that the real constraint includes, so the downstream operation (Aave `rebalance()` reverting on `SUPPLY_CAP_EXCEEDED`; Serai transaction failing relay/standardness or paying less than the requested fee) fails despite the check "passing".

### Impact Explanation
Any caller of `SignableTransaction::new` that supplies `data` (a public, caller-controlled byte string of up to 80 bytes) produces a `SignableTransaction` whose embedded `Transaction` is larger than what was priced and checked. The resulting signed transaction:

- pays a fee rate lower than the `fee_per_vbyte` the caller requested, and
- can fall under the network minimum relay fee or exceed `MAX_STANDARD_TX_WEIGHT` while the constructor returned `Ok`, meaning the fully-signed transaction (produced via `TransactionMachine`/`complete`) is unbroadcastable — the same failure shape as `rebalance()` reverting because the true Aave cap was exceeded.

The impact is bounded by the 80-byte data cap, but it deterministically corrupts the fee/weight accounting whenever `data` is used, and can turn an apparently-valid spend into a stuck/unrelayable transaction for a threshold wallet, requiring re-signing with new nonces.

### Likelihood Explanation
The bug triggers whenever `data` is non-empty — a routine, externally reachable input. No attacker collusion or privileged position is needed; an integrator or user supplying OP_RETURN metadata deterministically gets an underpriced transaction. Whether it crosses from "lower fee than requested" to "unbroadcastable" depends on how close the chosen `fee_per_vbyte` is to minimum relay fee and how close the weight is to the standardness cap, but the accounting error itself is unconditional.

### Recommendation
Include the OP_RETURN output in the weight/vsize template. Either pass the full `tx_outs` (including the data output) into `calculate_weight_vbytes`, or add a `data_len`/`script_pubkey` parameter so the template transaction contains the same output set the final `Transaction` will. Apply this in both call sites (lines 204 and 226), so `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check at line 241 all reflect the actual transaction.

### Proof of Concept
In `SignableTransaction::new`:

```rust
// data output IS added to the real tx outputs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: op_return_script });
}

// but weight/vbytes are computed WITHOUT that output
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;   // understated by ~up to ~90 vbytes
```

`calculate_weight_vbytes` builds `tx.output` only from `payments` (plus `change` at line 98), never from `tx_outs`/`data`. Therefore `vbytes < real_vsize` whenever `data.is_some()`, so `needed_fee` is too small and the `MAX_STANDARD_TX_WEIGHT` check at line 241 can return `Ok` for a transaction whose true weight exceeds the limit — the omitted-additive-term accounting error paralleling the missing `accruedToTreasury` term in `getOracleData()`.
