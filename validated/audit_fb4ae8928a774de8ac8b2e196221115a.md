## Title
Silent, unconfirmed rewrite of a repository's git remote URL from an API-supplied `clone_url` allows a malicious/compromised GitHub host to redirect future pushes/fetches - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically calls `gitStore.setRemoteURL(...)` and silently repoints the local `origin` remote whenever the GitHub API's `clone_url` for a tracked repository differs from what's configured locally, as long as the URL protocol (http vs ssh) hasn't changed and the local remote still matches the previously cached `cloneURL`. There is no user confirmation before the remote is changed. [1](#0-0) 

### Finding Description
`updateRemoteUrl` is invoked from `app-store.ts` whenever Desktop refreshes repository metadata from the API. It reads `apiRepo.clone_url` — a value returned by the GitHub API/GHES endpoint — and compares it to the current `origin` remote:

```
const remoteUrl = gitStore.defaultRemote.url
const updatedRemoteUrl = apiRepo.clone_url
const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)
...
if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
``` [2](#0-1) 

The only guards are:
1. `protocolsMatch` — a coarse check that only compares the URL *scheme* string (`https:` vs `https:`), not the hostname, owner, or repo name. [3](#0-2) 
2. `remoteUrlUnchanged` — confirms the *local* remote still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited the remote). [4](#0-3) 

Neither guard verifies that the *new* `clone_url` still points to the same host/owner/repo identity that the user originally added — it only checks the scheme matches. This is analogous to the audited Curve bug: a narrow, hardcoded condition (`protocolsMatch`) is treated as a sufficient proxy for "safe to trust this externally supplied value," while the actual identity/ownership of the resource is never re-validated, so a mismatched/attacker-influenced value flows straight into a state-changing action (rewriting `origin`).

For a GitHub Enterprise Server instance (or any endpoint reachable via a malicious/compromised proxy — explicitly an in-scope primitive per this task's rules, "a git remote/proxy response"), the API response backing `apiRepo` is not authenticated end-to-end against the specific repository identity Desktop expects; if that response is spoofed or the server is compromised, `clone_url` can point to a different host while keeping the same protocol. Since `protocolsMatch` only checks the scheme, this passes, and `!urlsMatch` becomes true (because the new host differs), triggering an automatic `git remote set-url origin <attacker_url>` with no user-visible prompt or confirmation.

### Impact Explanation
Once `origin` is silently repointed:
- Subsequent `git push` operations (and any push credentials sent via the trampoline/credential helper for that remote's host) go to the attacker-controlled destination instead of the legitimate repository.
- Subsequent `git fetch`/`pull` operations pull code from the attacker's server, which could be used to plant malicious commits that the user unknowingly builds on and re-pushes.
- This is a direct instance of "silent corruption of what the user commits or pushes," explicitly called out as in-scope impact, since the destination of push/fetch is changed without user awareness or consent.

### Likelihood Explanation
- No local/physical access, admin rights, or pre-existing malware is required — the trigger is entirely the content of an API response tied to a repository Desktop already tracks (GHES/compromised proxy scenario), a class explicitly allowed by this task ("attacker controls a git remote/proxy response").
- The existing guard (`protocolsMatch`) is coarse and does not perform any hostname/owner/name validation, so it does nothing to prevent a cross-host redirect.
- The action is fully automatic (no confirmation dialog), unlike other remote-changing flows in the app.

### Recommendation
Do not auto-update the remote when the *hostname* (or owner/name) of the new `clone_url` differs from the existing remote — restrict automatic updates to same-host rename/path changes (e.g., case changes, repo renames within the same GitHub host) and require explicit user confirmation for any change that alters the hostname. Concretely, extend `updateRemoteUrl` to also parse both URLs with `parseRemote`/`urlMatchesRemote`-style structural comparison and require `hostname` equality between old and new URLs before calling `gitStore.setRemoteURL`.

### Proof of Concept
1. User adds/clones a repository hosted on a GitHub Enterprise Server instance and it becomes tracked with `gitHubRepository.cloneURL = https://ghe.example.com/org/repo.git`.
2. The GHES instance (or a network intermediary/proxy in front of it) is compromised or spoofed, and the API response for repository metadata returns `clone_url: "https://attacker.example.com/org/repo.git"` (same `https:` scheme).
3. On the next metadata refresh, `app-store.ts` calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`.
4. `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true` (user never touched the remote), `urlsMatch` is `false` (different host) → `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')` executes silently.
5. The user's next `git push`/`fetch` in Desktop now targets `attacker.example.com` without any warning.

Note: I could not fully trace how `apiRepo` is authenticated/verified upstream in `app-store.ts` beyond the call sites found via `grep_search`; confirming the exact trust boundary of the API response (e.g., whether TLS/cert pinning or additional integrity checks exist elsewhere) would require deeper review of `app-store.ts`, which was not fully inspected due to iteration limits.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
