### Title
Encrypted secret-share message is not bound to its intended recipient, letting a malicious DKG participant frame an honest sender in blame proceedings - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the Mattermost flaw (a credential accepted without verification that it originates from the same flow it was issued for), PedPoP's `EncryptedMessage` proof-of-possession binds the *sender* (`from`) but never binds the *recipient*. An `EncryptedMessage<C, SecretShare>` Alice produced for Bob is accepted, byte-for-byte, as a message Alice sent to any participant `l`. Because secret-share messages and blame evidence are published to all participants, any participant can replay Alice's message-to-Bob as "Alice's message to me," and the blame machine will decrypt it under the wrong recipient key, get garbage, and blame honest Alice.

### Finding Description
`pop_challenge` transcripts `context`, the nonce `R`, the per-message `key`, `sender`, and `msg` — but not the recipient or the recipient's registered encryption key `to`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:302-324
transcript.append_message(b"nonce", nonce.to_bytes());
transcript.append_message(b"key", key.to_bytes());
transcript.append_message(b"sender", sender.to_bytes());
transcript.append_message(b"message", msg);
```

`encrypt` computes the ECDH against `to` (`self.decryption.enc_keys[&participant]`), yet `to` appears nowhere in the PoP or anywhere else inside `EncryptedMessage`. In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`), `decrypt_with_proof(sender, recipient, msg, proof)`:

1. Verifies `msg.pop` with `from = sender` — passes, since the replayed message genuinely carries Alice's sender-bound PoP.
2. Verifies the accuser's `EncryptionKeyProof` via DLEq against `self.enc_keys[&decryptor]` — passes, because the accuser knows their own private encryption key and produces a valid proof for the shared key with `msg.key`.
3. Decrypts with `cipher(context, proof.key)` — yields garbage, since the ciphertext was keyed to Bob's `enc_key`, not the accuser's.
4. `C::F::from_repr` fails → `blame_internal` returns `sender` (Alice) as faulty.

So an honest participant is adjudicated faulty by `BlameMachine::blame` / `AdditionalBlameMachine::blame` for a message she never sent to the accuser.

### Impact Explanation
A single malicious DKG participant can cause arbitrary honest participants to be publicly blamed and marked faulty, forcing the DKG to abort and (in deployments where blame carries economic penalties, e.g., validator slashing) punishing innocent parties. The accuser needs nothing secret — only a copy of a legitimately-sent `EncryptedMessage`, which blame proceedings already assume are publishable/authenticatable. The protocol's verifiability guarantee ("the blame proof correctly identifies the faulty party") is broken by a missing recipient binding — the same root cause as CVE-2025-12421, where a token was accepted without checking it belonged to the flow that produced it.

### Likelihood Explanation
Reachable by any DKG participant with only public/attributable data. The exploit requires the attacker to (a) obtain an `EncryptedMessage` addressed to someone else — plausible whenever shares or blame evidence are relayed through a common channel or published — and (b) submit a blame accusation, a normal protocol action. No cryptographic assumptions are violated; the PoP, DLEq, and parsing all behave exactly as coded. Constraints: requires a DKG context where the attacker can trigger `blame`/`AdditionalBlameMachine::blame` and obtain a victim's ciphertext; the effect is mis-attribution/abort rather than direct key recovery.

### Recommendation
Bind the intended recipient into the per-message proof: extend `pop_challenge` (and the mirrored call in `encrypt`, `decrypt`, `decrypt_with_proof`, and `invalidate_msg`) to append `to` — the recipient's `Participant` index and/or their registered `enc_key` (`transcript.append_message(b"recipient", ...)`/`append_message(b"to", key.to_bytes())`). Then a message for Bob can never satisfy `from`/`to` verification under any other `(sender, recipient)` pair, and `blame_internal` can only be reached for messages actually addressed to the accuser. This is a transcript-format change, so it requires a version bump of the `"DKG Encryption Key Proof of Possession v0.2"` transcript.

### Proof of Concept
1. Participants run `KeyGenMachine`/`SecretShareMachine` for some `context`. Honest Alice (`from = A`) produces `EncryptedMessage` `m` for Bob (`to = enc_keys[B]`) via `Encryption::encrypt` — `m.pop` is bound to `(context, m.pop.R, m.key, A, m.msg)` only.
2. Malicious Dave obtains `m` (from the wire or a prior blame publication).
3. Dave calls `BlameMachine::blame(sender = A, recipient = D, msg = m, proof = Some(proof_D))` where `proof_D` is an `EncryptionKeyProof` he constructs honestly: `key = ecdh(d_private, m.key)`, `dleq = DLEqProof::prove(.., &[G, m.key], &d_private)` — this verifies under `encryption_key_transcript(context)` with `[G, m.key]` and `[enc_keys[D], proof_D.key]`.
4. `decrypt_with_proof` returns garbage bytes (the ChaCha key is `H(context || enc_keys[B]*k)`, not `enc_keys[D]*k`); `C::F::from_repr` fails; `blame_internal` returns `A`.
5. Result: honest Alice is reported as the faulty party; the `BlameMachine`/`AdditionalBlameMachine` verdict is wrong solely because `m` was never bound to recipient `B`.

Uncertainty note: I verified the missing recipient binding directly in `pop_challenge`, `decrypt_with_proof`, and `blame_internal`. I did not fully verify whether deployment layers authenticate each ciphertext to a specific recipient index before reaching `blame` (the API takes `sender`/`recipient` as free parameters, suggesting not), which is the one precondition for the replay.
