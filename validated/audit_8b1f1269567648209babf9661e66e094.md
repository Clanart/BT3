### Title
`ReceivedOutput::read` accepts an attacker-supplied scalar offset without binding it to the output's `script_pubkey`, letting crafted bytes claim funds belong to Serai's key when they are not spendable - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The reported bug class is a public entry point that performs an action "on behalf of" a party without validating that the caller is authorized: `claim()` credits the recipient regardless of who calls it. The Serai analog is the deserialization/re-keying path for Bitcoin outputs. `Scanner::scan_transaction` correctly attributes outputs by looking `script_pubkey` up in the registered-offset map, but `ReceivedOutput::read` — an explicitly in-scope untrusted-bytes entry point — trusts whatever `offset` scalar is in the byte stream. The spendable key for the output is then computed as `script_key - offset*G` in `Output::key` (`processor/src/networks/bitcoin.rs:112-122`), so a forged `ReceivedOutput` can "claim" an arbitrary P2TR output belongs to the multisig under an arbitrary offset — the same "act on behalf of another without validation" shape, with a concrete consequence.

### Finding Description
`ReceivedOutput` couples a `Scalar` `offset` to a `TxOut`/`OutPoint`, where the offset is the HDKD re-keying scalar: the wallet can only spend the output if `offset` is genuinely the scalar registered with `Scanner::register_offset` for that output's script. During scanning, this binding is enforced — `scan_transaction` only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` hits, so `offset` is always the registered one (`networks/bitcoin/src/wallet/mod.rs:199-214`).

`ReceivedOutput::read` performs no such check. It reads a `Scalar` via `Secp256k1::read_F`, then a `TxOut` and `OutPoint`, and returns the tuple as-is (`networks/bitcoin/src/wallet/mod.rs:122-134`). Downstream, `Output::read` composes this directly (`processor/src/networks/bitcoin.rs:156`), and `Output::key` reconstructs the purported owning key by subtracting `GENERATOR * offset` from whatever x-only key the script commits to (`processor/src/networks/bitcoin.rs:120-121`). Nothing proves the deserialized `offset` is the one the Scanner registered for that script — the same gap as `claim()` never validating the caller against the `recipientId`.

An unprivileged party who can feed bytes to this read path (an untrusted output record, or any input other than the scanner's own pipeline) can therefore attach any offset to any P2TR `TxOut`. The consumer treats it as a valid spendable output of `key()`.

### Impact Explanation
The impact is funds reported received/spendable that are not actually spendable. A `ReceivedOutput` pairing a foreign (or dust/spam) P2TR output with a bogus offset will be attributed to the multisig's key with a wrong re-keying scalar. If integrated into transaction building, the resulting `SignableTransaction` would produce signatures that don't correspond to the output's real tweaked key — at best burning inputs/fees and halting a signing plan; at worst crediting the set with outputs it can never spend. Unlike the upstream report (pure timing, funds still reach the right address), here the misattribution corrupts what the wallet believes it owns.

### Likelihood Explanation
Reachability depends on an integrator feeding untrusted bytes into `ReceivedOutput::read`/`Output::read` rather than only using scanner-produced values — the serialization exists precisely so outputs can be persisted and transmitted (`write`/`serialize` at `wallet/mod.rs:136-148`), so round-tripping through any attacker-influenced channel hits this path. Within Serai's own processor the values are DB-loaded from the honest scanner, which lowers practical likelihood; accordingly this rates Medium, mirroring the source report's severity.

### Recommendation
Bind the offset to the output on deserialization: either (a) make `ReceivedOutput::read` verify `output.script_pubkey == p2tr_script_buf(key + offset*G)` for the expected key (requires passing the key/expected scripts into read), or (b) re-derive the offset by looking `script_pubkey` up in the registered-scripts map instead of trusting the serialized scalar, returning an error on mismatch — i.e., perform at read time the same check `scan_transaction` performs at scan time.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs path
// Given Serai's even group key `key` and any foreign P2TR output `victim_txout`
// (e.g., paying an attacker's own key), craft bytes:
let mut forged = vec![];
forged.extend(Scalar::ONE.to_bytes().iter().copied());        // arbitrary offset
forged.extend(serialize(&victim_txout));                       // attacker TxOut
forged.extend(serialize(&OutPoint::new(attacker_txid, 0)));    // attacker outpoint
let ro = ReceivedOutput::read(&mut forged.as_slice()).unwrap(); // accepted, no binding check

// Output::key() then reports the output as owned by:
//   x_only(victim_script_key) - GENERATOR * Scalar::ONE
// which does not equal `key`, yet the output is carried as a valid ReceivedOutput.
// A wallet crediting it reports unspendable funds as spendable; signing re-keys
// with offset=1 and produces a signature useless for the real output.
```

Relevant code: `ReceivedOutput::read` lacks validation (`networks/bitcoin/src/wallet/mod.rs:122-134`); the correct binding exists only in `Scanner::scan_transaction` (`wallet/mod.rs:205-211`); the offset is consumed for key recovery in `Output::key` (`processor/src/networks/bitcoin.rs:112-122`).
