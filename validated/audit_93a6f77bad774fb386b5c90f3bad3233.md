### Title
EIP-712 domain separator for aggregator withdrawal-verification signatures is not chain/deployment-bound, enabling cross-deployment signature replay - (File: core/src/rpc/ecdsa_verification_sig.rs)

### Summary
The `CLEMENTINE_EIP712_DOMAIN` used to authenticate that an `optimistic_payout` / operator-withdrawal request genuinely originates from the aggregator is a hard-coded, global constant (`name` + `version` only), with no `chainId` or `verifyingContract` component, so it is identical for every Clementine bridge deployment that runs this exact code.

### Finding Description
`CLEMENTINE_EIP712_DOMAIN` is defined as a `static` with only `name`/`version`: [1](#0-0) 

This domain is used by `recover_address_from_ecdsa_signature` to compute the EIP-712 signing hash for both `OptimisticPayoutMessage` and `OperatorWithdrawalMessage`: [2](#0-1) 

This is the exact analog of the reported bug class: a security-relevant "domain separator" is derived from a value fixed at build/compile time (equivalent to being fixed "in the constructor") rather than being bound per-deployment (equivalent to per-proxy `initialize`). Any two independently configured Clementine networks (e.g., different chains/environments, or two verifier/operator sets that happen to reuse the same `aggregator_verification_secret_key`/`aggregator_verification_address`, which is a single value in `BridgeConfig` — `core/src/config/mod.rs`, checked in `core/src/verifier.rs` `sign_optimistic_payout`) will accept an EIP-712 signature computed under an identical domain: [3](#0-2) 

This verification result is the sole authentication gate the verifier applies before contributing its MuSig2 partial signature toward broadcasting the optimistic-payout transaction, which pays out BTC from the bridge's custody: [4](#0-3) 

Because the domain carries no `chainId`/`verifyingContract`, the equality that should hold — "a verification signature authorizes a payout only for the specific deployment/network it was produced for" — instead degenerates to "a verification signature authorizes a payout for any deployment sharing the same aggregator key," breaking the intended per-deployment binding, exactly mirroring the MechMarketplace domain-separator issue.

### Impact Explanation
In principle this maps to "an unauthenticated state-changing or broadcasting call": if the same aggregator key/address is reused across two bridge instances (test/staging vs. production, or two independently operated networks sharing operational tooling/config), a verification signature that is valid on one instance is also valid on the other, since the EIP-712 hash it authenticates is identical in both. However, in practice the full message (`withdrawal_id`, `input_signature`, `input_outpoint_txid/vout`, `output_script_pubkey`, `output_amount`) is deposit/UTXO-specific and would need to coincide across the two deployments for a captured signature to be usable, and the withdrawal UTXO's spent-status check (`core/src/verifier.rs:1582`) prevents any double-execution on the same deployment. This substantially limits real-world exploitability compared to the original report, where the entire signed payload (not just the domain) was deployment-agnostic by design.

### Likelihood Explanation
Low. Exploitation requires two Clementine deployments configured with the same aggregator verification key/address (an operational choice, not a per-code-path guarantee) plus a coincidental or engineered collision of the full withdrawal message fields (deposit id, real BTC outpoint, script, amount) between those deployments — Bitcoin outpoints are effectively unique, making natural collisions implausible, and the reporter would need to specifically target a shared-key, matching-message scenario.

### Recommendation
Bind `CLEMENTINE_EIP712_DOMAIN` to deployment-specific data, e.g. include `chain_id` (Bitcoin network / Citrea chain id) and/or a `verifying_contract`/protocol-paramset identifier, so that the same signature cannot be valid across different Clementine deployments even if they happen to share the aggregator key.

### Proof of Concept
1. Configure two independent Clementine deployments (Deployment A, Deployment B) with the same `aggregator_verification_secret_key`/`aggregator_verification_address`.
2. Have the aggregator in Deployment A sign an `OptimisticPayoutMessage` verification signature for a given `withdrawal_id`/outpoint/output using `sign_withdrawal_verification_signature` (`core/src/test/sign.rs`), which uses the shared `CLEMENTINE_EIP712_DOMAIN`.
3. Submit the identical withdrawal params + captured verification signature to Deployment B's `optimistic_payout_sign` RPC (`core/src/rpc/verifier.rs:77-141`).
4. Because `recover_address_from_ecdsa_signature` derives the same EIP-712 hash under the shared domain, Deployment B's verifier will accept the signature as coming from "its" aggregator (`core/src/verifier.rs:1601-1623`), even though it was produced for Deployment A.

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)

    async fn optimistic_payout_sign(
        &self,
        request: Request<OptimisticPayoutParams>,
    ) -> Result<Response<PartialSig>, Status> {
        tracing::info!("Optimistic payout sign rpc called");
        let params = request.into_inner();
        let agg_nonce = AggregatedNonce::from_byte_array(
            params
                .agg_nonce
                .as_slice()
                .try_into()
                .map_err(|_| Status::invalid_argument("agg_nonce must be exactly 66 bytes"))?,
        )
        .map_err(|e| Status::invalid_argument(format!("Invalid musigagg nonce: {e}")))?;
        let nonce_session_id = params
            .nonce_gen
            .ok_or(Status::invalid_argument(
                "Nonce params not found for optimistic payout",
            ))?
            .id
            .parse::<u128>()
            .map_err(|e| Status::invalid_argument(format!("Invalid nonce session id: {e}")))?;

        let opt_withdraw_params = params.opt_withdrawal.ok_or(Status::invalid_argument(
            "Withdrawal params not found for optimistic payout",
        ))?;

        tracing::info!(
            "Parsed optimistic payout rpc params: {:?}",
            opt_withdraw_params
        );

        let verification_signature_str = opt_withdraw_params.verification_signature.clone();
        let withdrawal_params = opt_withdraw_params
            .withdrawal
            .ok_or(Status::invalid_argument(
                "Withdrawal params not found for optimistic payout",
            ))?;
        let (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) =
            parser::operator::parse_withdrawal_sig_params(withdrawal_params)?;

        let verification_signature = verification_signature_str
            .map(|sig| {
                PrimitiveSignature::from_str(&sig).map_err(|e| {
                    Status::invalid_argument(format!("Invalid verification signature: {e}"))

            })
            .transpose()?;

        let partial_sig = self

                withdrawal_id,
                input_signature,
                input_outpoint,
                output_script_pubkey,
                output_amount,
                verification_signature,
            )
            .await?;
        tracing::info!("Optimistic payout sign rpc completed successfully");
        Ok(Response::new(partial_sig.into()))
    }
