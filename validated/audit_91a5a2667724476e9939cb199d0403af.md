### Title
Division-by-zero panic in `calculate_stake_rewards()` migration-epoch branch when `point_value.points == 0` but an individual stake's `ag_points != 0` - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
The Cork `_swapRaForDsViaRollover()` bug is a case where a per-call denominator (`lvReserve + psmReserve`) can be zero while the surrounding guard clause only checks unrelated conditions, causing `checked_div`-style logic to panic instead of gracefully returning. The closest local analog in this Agave fork is in the `AlpenglowEpochType::MigrationEpoch` arm of `calculate_stake_rewards()`, where a guard checks `ag_points == 0 && point_value.points == 0` but then unconditionally divides `tower_points * rewards` by `point_value.points`, which can still be `0` when `ag_points != 0` while `tower_points == 0`.

### Finding Description
In the migration-epoch reward calculation: [1](#0-0) 

the guard only protects the case where **both** `ag_points == 0` **and** `point_value.points == 0`. It does not protect the case where `ag_points != 0` (this individual stake earned alpenglow points) but `point_value.points == 0` (the epoch's tower point total is zero). In that case, `tower_points` for this stake is `0` (since `tower_points == 0 && ag_points == 0` guard already excluded the all-zero case, this branch is reached specifically when `tower_points == 0` and `ag_points != 0`), and the code computes:

```
tower_points.checked_mul(u128::from(point_value.rewards))   // = 0 * rewards = 0
    .expect(...)
    .checked_div(point_value.points)                         // 0u128.checked_div(0) => None
    .unwrap()                                                 // panics
```

`checked_div` in Rust returns `None` whenever the divisor is `0`, regardless of the numerator value, so even though the numerator here is `0`, `.unwrap()` on `None` triggers a panic ("called `Option::unwrap()` on a `None` value"). The comment directly above this code, "The final unwrap is safe, as points_value.points is guaranteed to be non zero above," is inherited from the plain `Tower` arm (where the guard properly checks `point_value.points == 0` unconditionally) but does not hold for the `MigrationEpoch` arm, where the zero-point-value guard is conditioned on `ag_points == 0`.

`point_value.points` for a migration epoch is populated by `calculate_reward_points_partitioned()`, which sums only the *tower* portion of points across all stake delegations and returns a `PointValue` unconditionally with whatever total it computed (it only returns `None` — skipping the whole epoch — if the aggregate sum is exactly `0`): [2](#0-1) 

So `point_value.points` genuinely reflects the *global* tower-point total, while `ag_points` for a single stake is computed independently in `calculate_alpenglow_points()`/`calculate_migration_points()` based on that stake's own credits and the vote account's delegated-stake total: [3](#0-2) 

There is no invariant forcing "if any stake has nonzero `ag_points`, the epoch aggregate `point_value.points` (tower points only) must be nonzero" — these are two independently-computed point systems (tower vs. alpenglow) that happen to coexist only during the migration epoch. A stake can easily have earned alpenglow credits/points in the migration epoch while contributing zero tower points (e.g. its tower-epoch-credits iterator saw no non-migration entries before the marker), and if this holds true epoch-wide for every delegation (or the fixed-point tower math truncates the aggregate to exactly zero while individual `ag_points` remain nonzero due to differing units/precision), `point_value.points == 0` while a given stake's `ag_points != 0`.

### Impact Explanation
This code runs in `Bank::calculate_stake_rewards_and_commissions`, which is called from the validator's own epoch-boundary reward-distribution pipeline (`begin_partitioned_rewards` / partitioned epoch rewards machinery), executed by every validator identically during the Tower→Alpenglow migration epoch. A panic here is not a remotely-triggerable crash from a malicious peer message; it is a deterministic panic derived from validator-internal state (stake/vote account credits) during bank replay at an epoch boundary. If triggered, it would abort the bank-processing thread with a Rust panic during consensus-critical replay of every validator that reaches that epoch boundary with the described point distribution, which is a fleet-wide crash/consensus-halt scenario rather than fund theft, matching the "non-RPC remote exhaustion/crash" / "consensus halt" category for unprivileged, non-malicious-actor conditions (arising purely from legitimate stake/vote data combinations at a one-time protocol migration event).

### Likelihood Explanation
This is narrowly scoped to the one-time Tower→Alpenglow migration epoch (`AlpenglowEpochType::MigrationEpoch`), so it is not continuously exploitable, but the condition (`point_value.points == 0` while some individual `ag_points != 0`) is derived from ordinary stake/vote-credit bookkeeping and does not require a malicious validator, leaked keys, or trusted-plugin assumptions — it can arise from natural cluster state (e.g., very small/edge-case tower point totals due to fixed-point stake math truncation, or a delegation whose vote account had zero pre-migration tower credits but nonzero migration-epoch alpenglow credits). Confirming the exact numeric conditions that make the epoch-wide summed tower points equal to zero while an individual delegation's alpenglow points are nonzero would require deeper analysis of `calculate_points_for_tower`/fixed-point stake math, which was not fully traced in this investigation.

### Recommendation
Change the guard in the `MigrationEpoch` arm of `calculate_stake_rewards()` to check `point_value.points == 0` unconditionally (matching the plain `Tower` arm's guard), rather than gating it on `ag_points == 0`:

```rust
if tower_points == 0 && ag_points == 0 {
    return skip_reward(SkippedReason::ZeroPoints);
}
if point_value.points == 0 {
    // tower_points must be 0 here too since points can't exist without a nonzero denominator having been summed;
    // skip the tower portion, keep ag_points contribution only, or skip entirely per protocol semantics.
    return skip_reward(SkippedReason::ZeroPointValue);
}
```
or, more precisely, compute the tower-derived reward conditionally on `point_value.points != 0`, falling back to `0` for that term when it is zero, before adding `ag_points`.

### Proof of Concept
No runnable PoC was constructed in this investigation (this fork's test suite would require constructing a `MigrationEpoch` `AlpenglowEpochType` with a stake delegation whose `tower_points == 0`/`ag_points != 0` and a `point_value.points == 0` — see existing test scaffolding for this exact code path): [4](#0-3) 

A concrete Rust unit test analogous to `calculate_migration_points` tests above, but explicitly setting `reward_epoch_delegated_stakes`/`point_value.points` to `0` while forcing `ag_points != 0` (e.g., via a stake whose vote account has migration-epoch alpenglow credits but zero tower credits before the marker), would reproduce the panic at `runtime/src/inflation_rewards/mod.rs:306` (`.checked_div(point_value.points).unwrap()`).

fn calculate_migration_points(
    stake: &Stake,
    mut epoch_credits_iter: impl Iterator<Item = (Epoch, u64, u64)>,
    stake_history: &StakeHistory,
    inflation_point_calc_tracer: Option<impl Fn(&InflationPointCalculationEvent)>,
    new_rate_activation_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
    reward_epoch_delegated_stakes: &RewardEpochDelegatedStakes,
) -> Result<(u128, u128, u64), CalculatedStakePoints> {
    let (tower_points, tower_new_credits_observed, saw_marker) = tower_epoch_credits_iter(
        stake,
        epoch_credits_iter.by_ref(),
        stake_history,
        inflation_point_calc_tracer.as_ref(),
        new_rate_activation_epoch,
        use_fixed_point_stake_math,
    );
    let (ag_points, ag_new_credits_observed) = if saw_marker {
        calculate_alpenglow_points(
            stake,
            epoch_credits_iter.next(),
            stake_history,
            inflation_point_calc_tracer,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
            reward_epoch_delegated_stakes,
        )?
    } else {
        (0, stake.credits_observed)
    };

    let new_credits_observed = tower_new_credits_observed.max(ag_new_credits_observed);
    Ok((tower_points, ag_points, new_credits_observed))
}
