### Title
Forfeiture logic for cooling-down mWomSV lockers is a no-op, letting withdrawing accounts keep 100% of rewards instead of forfeiting a share to remaining lockers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never actually computes a forfeiture: it sets `rewardableAmount = _amount` and then computes `forfeitAmount = _amount - rewardableAmount`, which is always `0` by construction. This differs from the parallel `vlMGPBaseRewarder._calExpireForfeit`, which queries `vlMGP.getRewardablePercentWAD(_account)` to determine what fraction of rewards an account in a cooldown/unlock state should forfeit. Because `mWomSV.sol` itself exposes a `getRewardablePercentWAD` function (implying the same early-unlock forfeiture mechanism was intended for mWomSV lockers), but `mWOMSVBaseRewarder` never calls it, any account with `userRewards[_rewardToken][_account] > 0` that claims via `MasterMagpie`'s multiclaim (`getReward` → `_sendReward` → `_calExpireForfeit`) receives its full reward with zero forfeiture, regardless of its cooldown/unlock status.

### Finding Description
In `rewards/mWOMSVBaseRewarder.sol`: [1](#0-0) 

```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
```
`rewardableAmount` is assigned directly from `_amount`, so `forfeitAmount = _amount - _amount = 0` unconditionally, before the "if smaller than 0.1%" branch even triggers. This is called from `_sendReward`: [2](#0-1) 

Compare against the sibling contract `rewards/vlMGPBaseRewarder.sol`, which correctly derives the rewardable share from the locker's actual cooldown/unlock state: [3](#0-2) 

```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
```

The `mWOMSV` locker contract (`wombat/mWomSV.sol`) itself implements a `getRewardablePercentWAD` function, matching the design used by `vlMGPBaseRewarder`/`VLMGP.sol`, confirming that the same early-unlock/cooldown forfeiture mechanism was intended for mWomSV holders [4](#0-3) . However, `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)`; it is dead/stubbed-out logic that always yields zero forfeiture.

Any unprivileged holder of mWOMSV who is currently in a cooling-down/partially-unlocked state can simply call `MasterMagpie.multiclaim` (or the underlying `getReward(account, receiver)`), reaching `_sendReward` → `_calExpireForfeit`, and will always receive `toSend = userRewards[...]` in full, with `forfeitAmount == 0`, so `_queueNewRewardsWithoutTransfer` is never invoked (the `if(forfeitAmount > 0)` branch is unreachable).

### Impact Explanation
Because forfeiture is structurally always zero, the yield that should be redistributed to remaining/non-cooling-down mWomSV lockers via `_queueNewRewardsWithoutTransfer` (which increases `rewardInfo.queuedRewards`/`rewardPerTokenStored` for all other stakers) is never generated. Every cooling-down account keeps 100% of accrued rewards that the protocol design intended to partially confiscate and redistribute. This is a permanent loss of unclaimed yield for the remaining honest lockers, matching the Immunefi "theft or permanent freezing of unclaimed yield" impact class — the forfeited share is never minted into `queuedRewards` for other users, so it is permanently unavailable to them.

### Likelihood Explanation
This requires no special privilege: any EOA that has locked into mWomSV and is in a cooling-down/unlocking state, holding `userRewards[_rewardToken][_account] > 0`, can trigger this simply by calling the normal, public claim path (`getReward`/multiclaim) offered by `MasterMagpie`. No flash loans, reentrancy, or governance/admin rights are needed — this is 100% reachable by ordinary user interaction and occurs on every single claim by every cooling-down account, making it fully repeatable and not an edge case.

### Recommendation
Fix `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` to actually query the account's rewardable percentage from the mWOMSV locker, mirroring `vlMGPBaseRewarder`:
```
uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```
This requires adding `getRewardablePercentWAD` to `ILocker` (or a more specific interface implemented by `mWomSV.sol`) since the current `ILocker` interface only exposes `lockFor` [5](#0-4) .

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `mWOMSVBaseRewarder`, `mWomSV`, and `MasterMagpie` per existing test fixtures.
2. Have account A lock mWomSV, accrue rewards via `_provisionReward`, then begin an early unlock/cooldown on a portion of A's position (so `mWOMSV.getRewardablePercentWAD(A) < 1e18`).
3. Record `rewards[rewardToken].queuedRewards` before A calls `getReward(A, A)` (directly or via `MasterMagpie.multiclaim`).
4. Assert that `userRewards[rewardToken][A]` earned amount is fully transferred to A (`toSend == earned amount`) and that `rewards[rewardToken].queuedRewards` is unchanged (still equals pre-claim value), proving `forfeitAmount == 0` despite A being in a cooling-down state — demonstrating the forfeited share is never redistributed to other lockers such as account B, whose `rewardPerTokenStored` never increases from A's expected forfeiture.

        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
