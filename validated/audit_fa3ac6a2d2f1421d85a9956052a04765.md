### Title
Oversized diffs bypass the hidden-bidirectional-Unicode ("Trojan Source") warning and let a file be committed/pushed without ever showing its real contents - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop implements a security control comparable to what the report says MetaMask *should* enforce: before a file's changes are committed, the app is supposed to render the diff and, if the diff contains bidirectional Unicode override characters (a classic "Trojan Source" trick that makes code look different from what will actually run/commit), show a `DiffContentsWarning` banner. This control is computed in `DiffParser.parse` and surfaced by `DiffContentsWarning`. However, exactly like the `displayMessage` toggle in the report, this control can be silently defeated: if the diff/file is classified as "too large," Desktop skips parsing (and therefore the bidi check) entirely and shows a placeholder instead of the real content, while the commit/push action itself is never blocked or gated on the user having actually viewed the diff.

### Finding Description
Diff rendering has an early size guard in `buildDiff`: [1](#0-0) 

If the raw git diff buffer is too large (`isBufferTooLarge`, buffer size ≥ `MaxReasonableDiffSize`), `buildDiff` returns `{ kind: DiffType.Unrenderable }` **without ever calling `diffFromRawDiffOutput`/`DiffParser.parse`**, which is the only place `hasHiddenBidiChars` is computed: [2](#0-1) 

Even when the buffer is small enough to parse but a hunk contains a very long line (`isDiffTooLarge`, based on `MaxCharactersPerLine`), the diff becomes `DiffType.LargeText`, and the UI hides it behind an opt-in "Show Diff" button, never surfacing the `DiffContentsWarning` until the user manually clicks through: [3](#0-2) [4](#0-3) 

The bidi-character warning itself is only rendered as part of the normal text-diff view: [5](#0-4) 

Critically, none of this gates the actual commit action. The commit button's enabled state depends only on file selection and a non-empty summary — not on whether the diff was ever displayed or the warning acknowledged: [6](#0-5) 

So an attacker who controls content the victim has cloned/fetched (e.g., a source file already containing Trojan-Source bidirectional override characters, sized or line-length-padded to cross `MaxReasonableDiffSize`/`MaxCharactersPerLine`) can ensure that any future diff touching that file renders as `Unrenderable` or hidden `LargeText` in Desktop. The victim can still stage and commit/push the file — exactly as the dapp's `displayMessage: false` lets a signature proceed without showing what's being signed — because Desktop's "show what you're about to commit" invariant is bypassed by the same size-based short-circuit that skips the bidi-character parser.

### Impact Explanation
This allows silent corruption of what the user actually commits/pushes: bidirectional-Unicode "Trojan Source" content (which can make reviewed/committed code execute or compile differently than what visually appears) can enter a user's history and be pushed upstream without the security banner that exists specifically to catch this class of attack ever being shown. This matches the report's impact category — a value the user did not knowingly approve gets silently propagated through an action (commit/push) that Desktop's own controls are meant to make transparent.

### Likelihood Explanation
Requires only that the attacker control repository content the victim clones/fetches (a valid, unprivileged attacker primitive per the task's valid-impact criteria) and that the victim later diffs/commits/pushes a file touching that content — no local access, no malware, no social engineering beyond normal collaboration on a shared/forked repository. The size/line-length thresholds (`MaxReasonableDiffSize`, `MaxCharactersPerLine`) are fixed and can be reliably triggered by padding a file, making exploitation straightforward.

### Recommendation
Decouple the "diff too large to render" short-circuit from the security-relevant bidi-character/line-ending checks: always run `HiddenBidiCharsRegex` detection (or an equivalent check) over the raw diff/file contents regardless of size, and surface the `DiffContentsWarning` (or a dedicated non-dismissible warning) even when the visual diff itself is not rendered, so the user is never allowed to commit/push content flagged as containing hidden bidi characters without acknowledgement.

### Proof of Concept
1. Attacker crafts/commits a source file containing Unicode bidirectional override characters (e.g., `\u202E`) hidden inside a single very long line (> `MaxCharactersPerLine`) or pads the file so its diff buffer exceeds `MaxReasonableDiffSize`.
2. Victim clones/fetches this repository in GitHub Desktop and makes an innocuous edit to the file.
3. In the Changes view, Desktop shows either "The diff is too large to be displayed" (`Unrenderable`, no bidi check ever run) or the collapsed `LargeText` panel (bidi check computed but warning not shown until "Show Diff" is clicked) — see `app/src/ui/diff/index.tsx:178-203` and `app/src/lib/git/diff.ts:861-864`.
4. Victim selects the file and clicks "Commit," which is permitted regardless of whether the diff/warning was ever viewed (`app/src/ui/changes/commit-message.tsx:1600-1633`).
5. The commit (and subsequent push) proceeds, propagating the hidden bidi characters without the user ever seeing the `DiffContentsWarning` that exists specifically to prevent this.

  private getTextDiffWarningItems(): ReadonlyArray<DiffContentsWarningItem> {
    const items = new Array<DiffContentsWarningItem>()
    const { diff } = this.props

    if (diff.hasHiddenBidiChars) {
      items.push({
        type: DiffContentsWarningType.UnicodeBidiCharacters,
      })
    }

    if (diff.lineEndingsChange) {
      items.push({
        type: DiffContentsWarningType.LineEndingsChange,
        lineEndingsChange: diff.lineEndingsChange,
      })
    }

    return items
  }
