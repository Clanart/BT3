### Title
Deterministic nonce reuse across `share`/`complete` replays within one DKG-confirmer attempt enables secret key share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary

Analogous to the Trigger.dev issue — where a scoped object (a run's stored payload) was replayed in a second, attacker-influenced execution context without an integrity/scope check — `SigningProtocol::share_internal` replays a cached preprocess seed keyed only by `context`, not by the message or the participant/preprocess set it is actually used with. `DkgConfirmer::complete` then invokes `share_internal` a second time for the same `attempt`, causing the same FROST nonces to sign under a potentially different binding-factor/member set.

### Finding Description

`preprocess_internal` derives the signing nonces from a cached 32-byte seed stored under `CachedPreprocesses` keyed by `self.context`, and regenerates the identical machine every call via `AlgorithmSignMachine::from_cache` → `seeded_preprocess`, which feeds the seed to `ChaCha20Rng::from_seed`. The nonces are therefore a pure function of `(context, key)` — nothing else. [1](#0-0) [2](#0-1) 

For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)`. It does not commit to the preprocess set, the participant set, or the message. [3](#0-2) 

`share()` performs one `sign` with the supplied `preprocesses`. `complete()` later calls `share_internal` again — a second `sign` with the same deterministic nonces — using a freshly supplied `preprocesses` map. [4](#0-3) 

In `AlgorithmSignMachine::sign`, the binding factors `rho` are computed over the participant list and each participant's commitments (`transcript.append_message(b"participant", ...)` / `commitments.transcript(...)` / `rho_transcript` over `group_key`, `hash_msg(msg)`, and `hash_commitments(preprocesses)`). If the set or any commitment bytes differ between the two invocations, `rho` and the resulting challenge differ while the signer's nonces `d, e` are identical. [5](#0-4) 

The preprocess bytes fed to `read_preprocess` are untrusted, replayable wire bytes; there is no check that the preprocess used in `complete` is the same one used in `share` (the file's own header notes the missing on-chain-preprocess-matches-presumed-preprocess check as a TODO). [6](#0-5) 

### Impact Explanation

A FROST share is `z_i = d_i + (e_i * rho_i) + (lambda_i * s_i * c)`. Two shares produced with the same `(d_i, e_i)` but different `(rho_i, c, included set)` — i.e., `share()` executed when preprocess set S₁ was present and `complete()` executed after the set became S₂ within the same `attempt` — yield two linear equations over the signer's static secret share `s_i` and the nonce pair. Since `rho` is publicly computable and both shares are published, the victim's MuSig/FROST secret share (the validator's Ristretto private key share used for DKG confirmation) is recoverable. This is key share recovery, the highest-impact outcome in scope. The module itself acknowledges that nonce reuse here enables "third-party recovery of your private key share." [7](#0-6) 

### Likelihood Explanation

The same-attempt double-sign is structural: `share` and `complete` both call `share_internal`, and the cached seed is deliberately re-loaded for re-execution safety. Whether the exploit fires depends only on the `preprocesses` map differing between the two calls — e.g., `share` ran at threshold `t` preprocesses and `complete` ran after additional validators' preprocesses arrived, or a reordered/replayed preprocess byte string for a participant is included. Preprocesses arrive asynchronously per-validator, so a differing map across the two calls is reachable through ordinary message timing (an unprivileged participant publishing their preprocess between the two events, or submitting distinct commitment bytes — the bytes are only checked for parseability, not session/attempt consistency). No malicious intent by the victim is required; the victim deterministically reuses nonces by design whenever the inputs to `sign` differ.

### Recommendation

Bind the cached preprocess to the full signing context: key `CachedPreprocesses` by `(context, H(participants || serialized_preprocesses || msg))`, or before publishing a share verify on first use that the preprocesses/message hash matches a stored digest for that `context` and abort (or fail closed) on mismatch. Alternatively, regenerate the nonce seed per `share_internal` invocation and only reuse it for byte-identical replays detected via a stored commitment. The acknowledged TODO of checking that our commitments on-chain match the presumed preprocess before publishing shares would also mitigate this.

### Proof of Concept

1. In `attempt` A, the coordinator calls `DkgConfirmer::share(preprocesses_S1, key_pair)`, producing share `z_1` over nonces `(d, e)` derived from `CachedPreprocesses[("DkgConfirmer", A)]`.
2. After an additional validator's preprocess arrives (or with a preprocess map S₂ ≠ S₁ containing different commitment bytes for any signer), `DkgConfirmer::complete(preprocesses_S2, key_pair, shares)` internally calls `share_internal` again, producing `z_2` with the *same* `(d, e)`.
3. `rho_i` for the victim differs between S₁ and S₂ (different participant list and/or commitments fed into the `rho_transcript`), and the aggregate `R`/challenge `c` differs. The observer computes `rho_1, rho_2, c_1, c_2` from public data and solves the two-equation system `{z_1, z_2}` for the victim's secret share `s_i`, recovering the validator's private key share.

Caveat: I confirmed the caching/replay mechanics and the per-call re-sign in `complete`; I did not trace the exact call sites in `handle.rs`/`main.rs` that populate the `preprocesses` maps for `share` vs `complete`, so whether S₁ ≠ S₂ occurs in the same attempt in practice depends on how on-chain preprocess accumulation is passed in — but nothing in `SigningProtocol` prevents or detects it, and the module's own comments flag the missing preprocess-consistency check.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
