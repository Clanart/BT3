### Title

`ReceivedOutput::read` accepts unauthenticated offsets and prevout metadata, permitting unspendable deposits - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary

`ReceivedOutput::read` deserializes the spending offset, claimed `TxOut`, and `OutPoint` as independent fields without validating that the offset produces the output's Taproot script or that the claimed output corresponds to the outpoint. [1](#0-0)  An attacker-controlled serialization can therefore create a structurally valid `ReceivedOutput` that is credited by value/accounting logic but cannot be spent. [2](#0-1) 

### Finding Description

`Scanner` normally guarantees consistency by deriving an output only when its `script_pubkey` matches a registered offset. [3](#0-2)  The serialized format does not preserve that invariant: it writes the scalar offset followed by the claimed output and outpoint, while `read` accepts all three fields without recomputing `p2tr_script_buf(key + offset * G)` or checking the outpoint's actual on-chain output. [4](#0-3) [1](#0-0) 

The inconsistency is only detected later: `SignableTransaction::multisig` compares the script for the offset-adjusted group key with the claimed prevout script and returns `None` on mismatch. [2](#0-1)  A forged serialized output can also alter the claimed prevout value while retaining the victim's real outpoint and script, because `SignableTransaction::new` trusts `input.output.value` for balance and fee accounting. [5](#0-4)  The signing path then commits that supplied prevout list through `Prevouts::All`. [6](#0-5) 

### Impact Explanation

An unprivileged party that can feed serialized `ReceivedOutput` bytes to the wallet can cause funds to be reported as received even though the represented output is not spendable. [1](#0-0)  They can also create an input whose claimed value differs from the actual UTXO, causing incorrect balance/fee calculations and an invalid transaction once signed. [5](#0-4) [6](#0-5) 

### Likelihood Explanation

Exploitation requires the application to deserialize attacker-supplied `ReceivedOutput` bytes rather than only consuming objects produced locally by `Scanner::scan_transaction`. [3](#0-2)  Where such serialized objects cross a trust boundary—RPC, storage recoverable by another component, or peer-provided payment metadata—the attack needs only byte-level modification because no authentication or consistency validation exists. [1](#0-0) 

### Recommendation

Do not treat `ReceivedOutput::read` as validating untrusted input. [1](#0-0)  Either authenticate serialized outputs as internal state, or extend deserialization to take the scanner/group key and reject records unless `p2tr_script_buf(key + offset * G) == output.script_pubkey`. [7](#0-6)  Before signing or crediting the output, retrieve the outpoint from chain state and verify both its script and amount match the serialized `TxOut`. [2](#0-1)

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
