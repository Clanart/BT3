### Title
Partial-commit patch built from stale line-selection indices applied to freshly re-fetched diff, allowing silent inclusion/exclusion of unreviewed lines - ([File: app/src/lib/git/apply.ts])

### Summary
`applyPatchToIndex()` re-fetches the working-directory diff for a file at commit time (a *fresh* value) but then reuses the `WorkingDirectoryFileChange.selection` object that was computed against a *previously loaded* diff (a *stale* value) to decide which absolute line indices to include. This mirrors the report's bug class: a value used to build an authoritative result (the outstanding-debt total / here, the committed patch) is composed by mixing a fresh component with a stale component instead of atomically recomputing both, so the final result can silently diverge from what the user actually reviewed and intended.

### Finding Description
The Changes view loads a diff once (`updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts:3404-3513`) and stores it in `IChangesState.selection.diff`. The user then interacts with that specific diff object to build a `DiffSelection`, choosing individual absolute line indices via `withLineSelection`/`withRangeSelection` (`app/src/lib/patch-formatter.ts:157`, `formatPatch` uses `file.selection.isSelected(absoluteIndex)`).

`updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:90-95`) explicitly caches/reuses this diff across repeated status refreshes as long as the same file ID stays selected: [1](#0-0) 
so the diff shown/selected against can persist across multiple background refresh cycles without necessarily being re-validated against the file's current content.

At commit time, `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`) is invoked with the `WorkingDirectoryFileChange` carrying that possibly stale `selection`. Critically, `applyPatchToIndex` does **not** reuse the diff the selection was made against — it re-fetches a brand-new diff straight from disk: [2](#0-1) 
and then feeds that freshly-fetched diff, together with the stale `file.selection` (line indices computed against the old diff's hunk layout), into `formatPatch`: [3](#0-2) 

`formatPatch` (`app/src/lib/patch-formatter.ts:129-232`) walks the **new** diff's hunks and lines using `hunk.unifiedDiffStart + lineIndex` as `absoluteIndex`, then asks the **old** `selection.isSelected(absoluteIndex)` whether that index was chosen: [4](#0-3) 

If the file content on disk changes between the time the diff was displayed/selected and the time the user clicks "Commit" (hunks shift, get added/removed, lines renumbered), the absolute indices no longer refer to the same logical lines. The selection bitmap is applied against a structurally different diff, so `formatPatch` can silently select the wrong lines — including lines the user never reviewed/approved, or excluding lines they did select — while still producing a syntactically valid patch that `git apply --cached` accepts. No error is raised because a valid (but semantically wrong) patch is produced whenever the shifted line still exists as an addition/deletion at the reused index.

Existing guards do not close this window:
- `updateChangesWorkingDirectoryDiff` refreshes the diff/selectable-lines set only on the next full status refresh, and does so asynchronously and independently from the commit action; there is no synchronous "re-diff and re-validate selection immediately before staging" step in the commit path.
- `stageFiles`/`applyPatchToIndex` trust the caller-supplied `selection` object without any check that it was derived from the diff currently being re-fetched (no hash/etag/oid comparison of the diff used to build the selection vs. the diff just fetched).

### Impact Explanation
An attacker who controls a cloned/fetched repository (or anything that mutates the working tree between the diff being shown and the commit button being clicked — e.g. a `post-checkout`/other automated hook, a build tool, file watcher, or any background process triggered by repository content) can cause GitHub Desktop to build a commit whose actual staged content differs from what the user reviewed and explicitly selected in the diff viewer. This is "silent corruption of what the user commits," one of the explicitly in-scope impact categories: a user could unknowingly commit and push unreviewed/attacker-influenced lines, or fail to commit lines they believed they had selected.

### Likelihood Explanation
The race window exists on every partial commit (a common workflow) and does not require unusual user action beyond the ordinary "select some lines, then commit" flow while the working tree is being modified concurrently (e.g., by a git hook shipped with a cloned malicious repository, an IDE autosave/format-on-save triggered by the repo's own tooling config, or a background refresh-triggered operation). It does not require local/physical access, admin rights, or leaked credentials — only that the repository content itself can trigger a working-tree mutation during the small window between diff load and commit action.

### Recommendation
Before staging a partially-selected file, re-fetch the diff synchronously within `applyPatchToIndex` (or immediately prior to calling `stageFiles`) and validate that the file's diff hash/structure (e.g. hunk boundaries or a content hash) matches what the `selection` was computed against. If it does not match, abort the commit for that file and force the UI to reload the diff and require the user to re-confirm their line selection, rather than silently applying stale indices to new hunk data.

### Proof of Concept
1. Create a repo and modify `file.txt`, producing a diff with hunk H at lines [10-20].
2. In Desktop, open Changes, select `file.txt`; the diff is loaded and cached in `IChangesState.selection.diff`.
3. In the diff viewer, select only line 15 (an added line) to be included in the commit; leave the rest unselected (`DiffSelectionType.Partial`).
4. Before clicking "Commit", have an external process (simulating a hook/background tool triggered by the repository) insert 5 new lines above line 10 in `file.txt`, shifting all subsequent line numbers down by 5, and altering hunk boundaries.
5. Click "Commit". `applyPatchToIndex` re-fetches the diff (now with shifted hunks) but reuses `file.selection` computed against the old line numbering; `formatPatch` evaluates `isSelected(absoluteIndex)` against the new hunk's line at that same absolute index — which is now a different, unreviewed line.
6. Inspect the resulting commit: it includes a line the user never selected (formerly at index 15 in the old diff, now a different line in the new diff), or omits the line the user intended to include — demonstrating silent divergence between reviewed/selected content and actually committed content.
