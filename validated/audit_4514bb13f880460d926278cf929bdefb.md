### Title
Cached DKG-confirmation nonces are reused across `share` and `complete` calls with caller-supplied messages/preprocess sets, enabling key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

Analogous to the web3-react `chainId` bug — where a value captured once becomes stale after the underlying state changes mid-flow — `SigningProtocol::preprocess_internal` derives the FROST nonces once per `(context)` and caches only the 32-byte seed (`CachedPreprocesses`). Every subsequent `share_internal` call rebuilds the sign machine via `AlgorithmSignMachine::from_cache` with the **same seed**, regenerating identical secret nonces `d, e`, and then calls `machine.sign(preprocesses, msg)` again — even though `preprocesses` (the participant set, hence the per-participant binding factors ρ and Lagrange coefficients) and `msg` (`set_keys_message`, which embeds the caller-supplied `key_pair`) are supplied fresh on each call. A nonce fixed at "preprocess time" is therefore bound to a message/signing-set that may differ at "share time" — the stale-derivation bug class of CVE-2023-30543.

### Finding Description

`preprocess_internal` stores `machine.cache()` (the RNG seed) keyed only by `self.context` — for `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` [1](#0-0) [2](#0-1) .

Both `share()` and `complete()` funnel into `share_internal`, which calls `preprocess_internal` (deterministic nonces from the same cached seed) and then `machine.sign(preprocesses, msg)` [3](#0-2) . `complete` takes its **own** `preprocesses` and `key_pair` arguments and re-runs `share_internal` unconditionally [4](#0-3) . Meanwhile `DkgConfirmer::new` snapshots `removed` per construction, and `threshold_i_map_to_keys_and_musig_i_map` maps the *threshold* participant indexes into fresh *MuSig* indexes — so different reported preprocess sets produce different `included` sets [5](#0-4) .

Inside `sign`, the share is `nonce_i + c_i · (λ_i · x + offset)` where `nonce_i = d + e·ρ_i`, and `ρ_i`, `c_i`, `λ_i` all depend on the per-call `preprocesses`/`msg` while `d`, `e` come from the fixed cached seed [6](#0-5) . The module's own header concedes reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign … called again," resting safety entirely on BFT finality — but `share` and `complete` consume separately-supplied data and re-execute `sign` [7](#0-6) .

### Impact Explanation

Each published `[u8; 32]` signature share is a linear equation `s_j = d + e·ρ_j + c_j·λ_j·x_j` in the secret share. When `share` is published for one `(preprocesses, key_pair)` and `complete` re-signs with different ones (different preprocess set → different ρ/λ; different `key_pair`/`removed` → different `c`), the same `d, e` are reused. Across repeated calls at the same `attempt` context (distinct reported preprocess maps, a `key_pair` differing from the one used at share time, or a `DkgConfirmer` re-built with a different `removed` set), an observer collecting ≥3 such shares solves for the validator's MuSig secret share — full recovery of the key that signs `set_keys_message` (the root-of-trust DKG confirmation). This matches the acceptance bar of "key share recovery" and is exactly the "stale derived value after state change" pattern: the nonce was bound at cache time to inputs that changed before signing.

### Likelihood Explanation

Reachable by an unprivileged party only to the extent that any validator/participant can feed distinct `preprocesses`, `shares`, or a differing `key_pair` into the share/complete path within one attempt — these are attacker-influenced maps passed by value to `share`/`complete` from tributary data. No colluding-threshold, leaked key, or broken-BFT assumption is needed: the reuse is triggered whenever the inputs at `complete` differ from those at `share` (e.g., a preprocess that fails `read_preprocess` at share time being absent, or slashing/`removed` changing the participant mapping). The required condition — two `sign` executions on divergent inputs under one `attempt` — is a race-of-inputs, not a race of threads, mirroring the advisory's connection-flow mutation. I was unable to fully trace `coordinator/src/tributary/handle.rs` call sites, so whether distinct inputs reach `share` vs `complete` in practice is not 100% confirmed; however the code unconditionally re-executes `sign` in `complete` on independently supplied arguments, and the header's own threat analysis lists exactly this failure mode.

### Recommendation

Bind the cached preprocess to the signing inputs, not just the attempt: store a commitment (hash of the sorted preprocess map and `msg`) alongside `CachedPreprocesses`, and in `share_internal`/`complete_internal` abort — rather than re-sign — if the inputs differ from those used when the share was first produced. Alternatively, have `complete` reuse the `SignatureShare`/`SignatureMachine` result persisted from `share` instead of calling `share_internal` again, so `sign` executes exactly once per `(context, msg, included)` triple. Include `key_pair` and the `removed` set in the cache key so any change forces a fresh nonce.

### Proof of Concept

1. In attempt `N`, a `DkgConfirmer` is built with `removed = R1`. `share(preprocesses_A, key_pair_K)` runs `preprocess_internal` → caches seed under `(b"DkgConfirmer", N)` → `sign` emits share `s1 = d + e·ρ_A + c_K·λ_A·x`.
2. Later, `complete(preprocesses_B, key_pair_K', shares)` is invoked where `preprocesses_B ≠ preprocesses_A` (a participant's preprocess was dropped/replaced) or `K' ≠ K`. `share_internal` reloads the same seed → same `d, e` → `sign` emits `s2 = d + e·ρ_B + c_K'·λ_B·x` with publicly computable `ρ, c, λ` for both executions.
3. Two equations leave `d, e, x` underdetermined; a third execution at the same `attempt` (any further share/complete call with a third distinct input tuple) yields a solvable linear system over `Ristretto::F`, recovering `x` — the validator's private MuSig share used for `set_keys_message`. All inputs (`preprocesses`, `shares`, `key_pair`) are attacker-influenced byte maps; no trusted-state assumptions are violated.

Uncertain: whether `handle.rs` actually invokes `share`/`complete` with divergent inputs in a reachable flow; the vulnerability is in the unconditional re-`sign` on independently supplied arguments and the context-only cache key, which is directly visible in the cited code.
