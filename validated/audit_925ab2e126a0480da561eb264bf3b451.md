## Title
Unauthenticated GitHub-realm spoofing forces the GitHub sign-in/OAuth flow for an attacker-controlled Git host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts](getEndpointKind))

## Summary
The Solidity report's broken invariant is that a security-relevant piece of state (`poolIdArrayIndexForExcessDeposit`) is advanced based on an attacker-influenceable input without verifying the precondition (`findValidator`) that should gate the update, letting an attacker bias which entity benefits from a later privileged action. The closest structural analog in GitHub Desktop is `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, which decides — based on data supplied by the remote Git server itself — whether an unknown host should be treated as `'enterprise'` (GitHub) before the app's own network-based verification (`isGitHubHost`) ever runs.

## Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's `credential.helper=desktop`, forwarding any `WWW-Authenticate` response headers it received from the remote server as `wwwauth[]` fields on the credential request.

`getEndpointKind` uses this attacker-controlled data as a shortcut to classify the host: [1](#0-0) 

```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
```

Because the `WWW-Authenticate` header is emitted by the remote server itself, an attacker who controls the Git remote (e.g. `https://evil.example/foo.git`, added to a cloned repository's config or offered as a "fork"/"upstream" suggestion) fully controls this string. They can simply respond to the HTTPS auth challenge with `WWW-Authenticate: Basic realm="GitHub"` and get classified as `'enterprise'` — the same classification normally reserved for a verified GitHub/GHE instance — without any of the legitimate verification performed by `isGitHubHost()` (a HEAD request checking for the `x-github-request-id` header, third-party host denylist, etc.): [2](#0-1) 

That real check is only reached as a fallback later in the function; the `wwwauth[]` shortcut bypasses it entirely for any attacker-chosen host.

Once classified as `'enterprise'`, `getCredential()` treats the arbitrary host as GitHub-like and, if no existing account matches, launches the actual GitHub sign-in UI/OAuth flow scoped to that host: [3](#0-2) 

```
if (
  endpointKind !== 'generic' &&
  !accounts.some(a => a.endpoint === apiEndpoint)
) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
  ...
}
```

`promptForGitHubSignIn` then begins a genuine "GitHub Enterprise" sign-in flow bound to the attacker's origin: [4](#0-3) 

## Impact Explanation
This lets an attacker-controlled remote force Desktop to present its trusted "Git requesting credentials… / Sign in with GitHub Enterprise" dialog for a server that has none of the properties Desktop normally requires (real `/meta` endpoint, `x-github-request-id`, etc.). Because the same code path is the one used for legitimate GitHub Enterprise sign-in, this is an "unauthorized OAuth/account binding" style issue: a user who is only expecting a routine credential prompt because they cloned/fetched an attacker's repository can instead be walked through a full GitHub sign-in flow (or shown UI implying the remote is GitHub-verified) initiated by an untrusted party. It weakens the trust boundary the `isGitHubHost` network check is meant to enforce and can be used to make a phishing/social-engineering sign-in prompt look authoritative ("Git requesting credentials to access…" + a GitHub-branded sign-in flow) for a host the user has no reason to trust.

## Likelihood Explanation
Likelihood is limited but real: it requires the user to fetch/push/clone against an attacker-supplied HTTPS remote (a plausible scenario — cloning a malicious repo, adding a malicious remote/fork URL, or an on-path/proxy response), and the attacker's server must simply answer HTTP 401 with a crafted `WWW-Authenticate: ... realm="GitHub"` header — trivial to implement. No local access, admin rights, or prior compromise is needed; the trigger is entirely a network-observable action the app already performs during normal Git operations.

## Recommendation
Do not trust the `wwwauth[]` realm string as a basis for classifying a host as GitHub/GHE (`'enterprise'`) for UI/flow-selection purposes. At minimum:
- Require the `isGitHubHost()` network verification (or an equivalent stronger check, e.g. TLS cert / known endpoint allowlist) before ever surfacing the GitHub-branded sign-in flow for a host that is not already a known account endpoint.
- If the `wwwauth[]` heuristic is kept purely as a performance shortcut, treat it as advisory only for logging/telemetry, not for making the security-relevant branch decision that changes which prompt (`generic` vs `GitHub sign-in`) is shown to the user.

## Proof of Concept
1. Attacker hosts a Git server at `https://evil.example/repo.git` and configures it to respond to unauthenticated HTTPS requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim clones or adds `https://evil.example/repo.git` as a remote in GitHub Desktop and performs a `fetch`/`push`.
3. Git invokes the `desktop` credential helper with `wwwauth[0]=Basic realm="GitHub"` among the credential fields.
4. `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts:157-165` matches `realm="GitHub"` and returns `'enterprise'` — skipping the real `isGitHubHost()` verification in `app/src/lib/api.ts:2429-2491`.
5. Since no account exists for `evil.example`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example')`, which opens Desktop's GitHub Enterprise sign-in dialog scoped to the attacker's host.

Note: I was unable to trace fully whether the OAuth token exchange (`requestOAuthToken`/`fetchUser` in `app/src/lib/api.ts`) sends any Desktop-held secret to the attacker's endpoint versus simply performing a normal OAuth handshake against it; that would require deeper tracing of the enterprise OAuth request construction, which wasn't feasible to confirm within the available search results. The confirmed and exploitable part of the bug is the bypass of `isGitHubHost` verification via attacker-controlled `WWW-Authenticate` data, which incorrectly upgrades an arbitrary host to the trusted "GitHub" classification and triggers the GitHub sign-in UI/flow.

/**
 * Attempts to determine whether or not the url belongs to a GitHub host.
 *
 * This is a best-effort attempt and may return `undefined` if encountering
 * an error making the discovery request
 */
export async function isGitHubHost(url: string) {
  const { hostname } = new window.URL(url)

  const endpoint =
    hostname === 'github.com' || hostname === 'api.github.com'
      ? getDotComAPIEndpoint()
      : getEnterpriseAPIURL(url)

  if (isDotCom(endpoint) || isGHE(endpoint)) {
    return true
  }

  if (isKnownThirdPartyHost(hostname)) {
    return false
  }

  // github.example.com,
  if (/(^|\.)(github)\./.test(hostname)) {
    return true
  }

  // bitbucket.example.com, etc
  if (/(^|\.)(bitbucket|gitlab)\./.test(hostname)) {
    return false
  }

  if (getEndpointVersion(endpoint) !== null) {
    return true
  }

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}

      })
