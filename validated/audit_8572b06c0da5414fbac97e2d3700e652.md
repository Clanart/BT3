### Title
Symlink-boundary bypass in `resolveWithin` lets attacker-crafted repo content escape the sandbox and be exfiltrated via Copilot conflict-resolution - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its `posix`/`win32` variants) is the guard `buildConflictContext` relies on to ensure that a conflicted-file path read from an attacker-controlled repository stays inside the repository's working directory before its raw content is sent to the Copilot merge-conflict-resolution model. The final containment check uses a naive string `startsWith` comparison on `realpath`-resolved paths, without verifying that a path separator (or exact equality) follows the root prefix. A symlink checked into a malicious repository can therefore resolve, after `realpath`, to a sibling directory whose name merely shares the same string prefix as the repository root (e.g. root `.../alice/repo` vs. sibling `.../alice/repo-secrets` or `.../alice/repository`), and the guard will incorrectly treat it as "inside the repository."

### Finding Description
`_resolveWithin` computes `realRoot = realpath(normalizedRoot)` and `realResolved = realpath(resolved)`, then returns `resolved` only if `realResolved.startsWith(realRoot)`: [1](#0-0) 

This is the classic prefix-containment bug: `startsWith` matches on raw characters, not path components, so `/Users/alice/repo-secrets/id_rsa` is considered "within" root `/Users/alice/repo` even though it is a completely different, sibling directory. The existing unit tests only cover directory-traversal (`../..`) and same-basename edge cases, not the sibling-prefix scenario: [2](#0-1) [3](#0-2) 

This guard is exactly the one used in `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts`) to sandbox reading conflicted files before they are packaged into the prompt sent to Copilot: [4](#0-3) 

`file.path` originates from the list of files with merge conflicts in the working directory of a cloned/fetched repository — content fully controlled by whoever authored the repository/branch being merged. An attacker can commit a symlink at some path inside the repo (e.g. `linkdir`) pointing to a sibling directory that shares the repository's own path as a string prefix (a very common layout, since users routinely clone multiple repositories — forks, `-old`, `-backup`, numbered clones like `repo`/`repo2` — into the same parent folder) and place a conflicting file entry underneath that symlinked path. When the user resolves conflicts with Copilot, `resolveWithin` resolves the symlink via `realpath`, the buggy `startsWith` check passes, and the guard reports the path as safely "inside the repository" even though it is not.

### Impact Explanation
If bypassed, `buildConflictContext` proceeds to `readFile` the target and includes its raw content (subject only to size limits, not location) as `rawContent` in the payload built for the AI model: [5](#0-4) 

That content is then transmitted off-box as part of the Copilot conflict-resolution request. This allows exfiltration of files outside the intended repository boundary — e.g. `.git/config` (which can embed credentials/tokens), SSH keys, or source in a sibling private repository — satisfying the "file read outside the repo" / "credential exfiltration" impact classes for an unprivileged attacker who only controls a cloned/fetched repository's contents.

### Likelihood Explanation
The path-name-prefix collision needed (root repo name being a literal string prefix of another directory on disk) is a common real-world layout pattern (`repo` + `repo2`, `repo` + `repo-old`, `project` + `project-secrets`), so this is plausible without any local/admin access or pre-existing malware — the only requirement is the victim cloning/merging a malicious repository and invoking the Copilot conflict-resolution feature on a conflicted file located behind a symlinked path. No unusual manual steps are required beyond the normal git workflow of resolving a merge conflict.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require that `realResolved` equals `realRoot` exactly or is followed immediately by the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
(using the appropriate separator for the `options` variant — `path.sep`, `/`, or `\\`), and add regression tests covering sibling-directory-prefix collisions (`root` vs `root-something`) both with and without symlinks.

### Proof of Concept
1. Attacker creates a malicious git repository/branch such that merging it into the victim's checkout produces a merge conflict on a file path that traverses a symlink, e.g. `linkdir -> ../repo-secrets` (a relative symlink checked into the repo), with the conflicting file `linkdir/leak.txt`.
2. Victim clones/fetches the attacker's branch into `.../alice/repo` where a sibling directory `.../alice/repo-secrets` happens to exist (or attacker chooses a target name matching a common convention such as `.../repo2`, `.../repo-old`).
3. Victim performs the merge, hits the conflict, and invokes GitHub Desktop's Copilot "Resolve with AI" feature, which calls `buildConflictContext(workingDirectory, files, ...)`.
4. `resolveWithin(workingDirectory, 'linkdir/leak.txt')` resolves the symlink via `realpath` to `.../alice/repo-secrets/leak.txt`, and the buggy `startsWith` check in `app/src/lib/path.ts` lines 64-71 incorrectly returns this path as valid.
5. `buildConflictContext` reads the file's content (`app/src/lib/copilot-conflict-context.ts` lines 429-461) and includes it in the request sent to the Copilot API, exfiltrating data from outside the intended repository. [6](#0-5) [7](#0-6)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
