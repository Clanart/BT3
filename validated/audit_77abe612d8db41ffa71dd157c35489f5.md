### Malformed Bitcoin transaction input data can panic threshold transaction signing - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`TransactionSignMachine::sign` assumes every participant-supplied preprocess vector contains exactly one FROST preprocess per transaction input. While `read_preprocess` enforces that shape for byte-decoded messages, the public `sign` API accepts `HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>>` directly and indexes `commitments[c]` without validating the nested vector length. An unprivileged signing participant that can supply a malformed preprocess object through an integration path can therefore cause an out-of-bounds panic, mirroring the reported malformed-input crash/DoS class.

### Finding Description
`TransactionSignMachine::read_preprocess` reads `self.sigs.len()` preprocesses for every participant, so serialized untrusted bytes must have the expected shape. However, `TransactionSignMachine::sign` accepts the already-deserialized `HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>>` and transposes it by indexing `commitments[c]` for each input index `c`. There is no check that each participant vector has length `self.sigs.len()` before indexing. A short vector causes Rust bounds checking to panic when `sign` reaches `commitments[c]`. The affected path is `TransactionSignMachine::sign` in `networks/bitcoin/src/wallet/send.rs:355-397`.

### Impact Explanation
The panic aborts the signing operation and can crash the calling process if it does not isolate signing in a separate thread or catch panics. In a threshold Bitcoin-wallet service that accepts participant preprocess objects through an IPC, message-passing, or deserialized-object interface, one malformed signing-set member can repeatedly prevent transaction completion. This is a reachable denial of service against signing availability, analogous to the reported over-read crash caused by malformed input. It does not itself forge a signature or reveal key material.

### Likelihood Explanation
Likelihood is bounded by the interface used to carry preprocesses. If every caller exclusively uses `TransactionSignMachine::read_preprocess`, malformed bytes cannot produce a short vector because that reader either returns `Err` or creates exactly `self.sigs.len()` entries. The issue remains exposed for integrations that construct or forward the public `HashMap<Participant, Vec<Preprocess<..>>>` value directly, which the API permits. Since Rust converts the invalid index into a panic rather than memory disclosure, the practical result is application-level DoS rather than exploitable memory corruption.

### Recommendation
Validate the nested preprocess vectors before indexing them in `TransactionSignMachine::sign`. Specifically, reject any participant whose `Vec<Preprocess<Secp256k1, ()>>` length differs from `self.sigs.len()` with `FrostError`, or make `read_preprocess` the only supported construction path by hiding the vector representation behind an opaque type whose invariant is enforced at construction.

### Proof of Concept
Conceptually, for a transaction with two inputs (`self.sigs.len() == 2`), provide a remote participant entry whose preprocess vector contains only one `Preprocess`:

```rust
// networks/bitcoin/src/wallet/send.rs
let mut commitments = HashMap::new();
commitments.insert(remote_participant, vec![only_one_preprocess]);

// Reaches c == 1, then evaluates commitments[1] on a Vec of length 1.
machine.sign(commitments, b"");
```

The exact vulnerable operation is:

```rust
commitments
  .iter()
  .map(|(l, commitments)| (*l, commitments[c].clone()))
```

from `networks/bitcoin/src/wallet/send.rs:364-371`, where `c` ranges over `0 .. self.sigs.len()` but `commitments` is an unvalidated per-participant vector.
