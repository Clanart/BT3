## Analysis

The report's core issue is that raw, attacker-influenced error text from a network peer (`zcashd`'s JSON-RPC replies) is fed directly into a UI surface without being restricted to safe, pre-sanitized content — allowing spoofed messages/phishing payloads to reach the user. GitHub Desktop has a structurally identical pattern: raw stderr/stdout from Git operations against a remote server is passed unmodified into an `@xterm/xterm` terminal widget for rendering.

### Title
Raw, remote-controlled Git stderr/stdout is rendered unsanitized in an xterm.js terminal widget, enabling escape-sequence/hyperlink spoofing - (File: `app/src/ui/terminal.tsx`)

### Summary
When a Git command against a remote (clone/fetch/push/etc.) fails without matching a known `DugiteError`, GitHub Desktop falls back to displaying the raw combined stdout/stderr text captured from the Git subprocess as the error message. This "raw git error" is rendered via the `Terminal` component, which wraps `@xterm/xterm` and writes the untouched bytes directly to a real terminal emulator that interprets ANSI/OSC control sequences (including OSC 8 hyperlinks).

### Finding Description
`git()` in [1](#0-0)  captures combined stdout/stderr into `terminalChunks` for any Git invocation, and when a command fails without a recognized `DugiteError`, `GitError` falls back to using that raw terminal output (or raw stderr/stdout) as `message` and sets `isRawMessage = true`: [2](#0-1) .

`app-error.tsx` checks `isRawGitError` and, if true, renders the message through the `Terminal` component instead of plain text: [3](#0-2) . The same pattern is used for worktree-deletion failures: [4](#0-3) , and for Git hook failures: [5](#0-4) .

The `Terminal` component itself instantiates a real `@xterm/xterm` terminal and writes the content verbatim: [6](#0-5)  and [7](#0-6) . There is no stripping/escaping of ANSI/OSC control sequences before the raw bytes are written to `this.terminal.write(data)`.

This is the exact broken invariant described in the report: text that ultimately originates from an untrusted network peer (a Git server responding to `clone`/`fetch`/`push`, or the output of a hostile server-side hook triggered during those operations) is displayed to the user through a rich rendering surface (a terminal emulator) rather than being restricted to a safe, pre-defined, plain-text presentation. Unlike a `<p>{e.message}</p>` (used for known/mapped errors, e.g. [8](#0-7) ), the xterm-based path interprets control sequences: it can move the cursor, clear lines, and — since xterm.js natively supports OSC 8 hyperlinks — render clickable links whose displayed text and destination differ. Git's own client is known to reflect arbitrary bytes from server responses (e.g. remote messages, `remote:` progress lines) into stderr/stdout, so a malicious or MITM'd Git server can supply attacker-chosen escape sequences here.

### Impact Explanation
An attacker controlling (or intercepting/MITM'ing on an insecure network) the Git remote a user is cloning/fetching/pushing to can craft Git server output containing terminal escape sequences. Rendered inside xterm.js, this could be used to construct a convincing, misleading dialog (obscuring the real error via cursor/line manipulation) or to embed an OSC 8 hyperlink presenting benign-looking link text that actually points to a malicious/phishing URL displayed as part of the "error" content — the same phishing pattern (fake update prompts / credential-stealing links) referenced in the source report against wallet software.

### Likelihood Explanation
This requires the user to be interacting with an attacker-controlled or MITM'd Git remote — no local access, malware, or leaked credentials are needed, only network-position control over the Git server responses (the same threat model as the original report's "Eve" scenario, applicable to any unauthenticated/self-hosted remote or a compromised proxy). The affected code paths (`app-error.tsx`, `delete-worktree-failed-dialog.tsx`, `hook-failed.tsx`) are reached whenever a Git command produces an unrecognized/unmapped failure, which is a fairly common occurrence for non-GitHub remotes and custom Git server configurations.

### Recommendation
- Short term: Before writing raw Git output to the `Terminal`/xterm component, strip or neutralize OSC/DCS/hyperlink escape sequences (or disable link/OSC 8 handling), keeping only safe formatting (e.g., `\r`/`\n` handling already done via `createTerminalStream`) so remote-supplied bytes cannot alter chrome or inject clickable content.
- Long term: Establish a single, centralized sanitization layer for all "raw" Git terminal output (used by `app-error.tsx`, `delete-worktree-failed-dialog.tsx`, `hook-failed.tsx`, `commit-progress.tsx`) that allowlists a minimal safe subset of terminal control codes and rejects/encodes everything else, rather than relying on each call site to pass untouched subprocess output into the terminal emulator.

### Proof of Concept
1. Set up a Git "remote" (e.g., a custom `git-upload-pack`/`git-receive-pack` shim, or a MITM proxy on an insecure network) that responds to a `fetch`/`push` request with a non-zero exit and stderr containing a crafted OSC 8 sequence, e.g.:
   `\x1b]8;;https://evil.example/update\x1b\\Update available: click here\x1b]8;;\x1b\\` followed by an unrecognized fatal message.
2. In GitHub Desktop, perform a fetch/push against that remote so the Git process exits with an error code that `parseError` cannot map to a known `DugiteError` (making `gitError === null`, so `gitErrorDescription` is `null` and `GitError` falls back to raw `terminalOutput`).
3. Observe the resulting error dialog (`app-error.tsx` → `isRawGitError` branch) renders the message via `Terminal`, and the injected OSC 8 sequence becomes a clickable hyperlink inside the terminal widget pointing to the attacker's URL while displaying attacker-chosen "trusted-looking" text.

import {
  ITerminalOptions,
  ITerminalInitOnlyOptions,
  Terminal as XTermTerminal,
} from '@xterm/xterm'
import React from 'react'
import { getMonospaceFontFamily } from './get-monospace-font-family'
import { TerminalOutput } from '../lib/git'

export const defaultTerminalOptions: Readonly<ITerminalOptions> = {
  convertEol: true,
  fontFamily: getMonospaceFontFamily(),
  fontSize: 12,
  screenReaderMode: true,
}

export type TerminalProps = ITerminalOptions &
  ITerminalInitOnlyOptions & {
    readonly terminalOutput?: TerminalOutput
    readonly hideCursor?: boolean
  }

export class Terminal extends React.Component<TerminalProps> {
  private terminalRef = React.createRef<HTMLDivElement>()
  private terminal: XTermTerminal | null = null

  public get Terminal() {
    return this.terminal
  }

  public write(data: TerminalOutput) {
    if (Array.isArray(data)) {
      data.forEach(chunk => this.terminal?.write(chunk))
    } else {
      this.terminal?.write(data)
    }
  }

  public componentWillUnmount(): void {
    this.terminal?.dispose()
  }
