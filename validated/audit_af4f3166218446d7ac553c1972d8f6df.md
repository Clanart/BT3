## Analysis: Division by Zero in `consolidatedNode.Split` (Reward Distribution)

### Title
Division by Zero in `consolidatedNode.Split` via unguarded proposer CL-staking split during deferred reward finalization - (File: `kaiax/staking/staking_info.go`)

### Summary
The `consolidatedNode.Split` function divides by the sum of a validator's CN stake and its Consensus-Liquidity (CL) stake without checking for a zero denominator. Most call sites guard this by only invoking `Split` when the combined stake exceeds `minStake` (which is always > 0), but the proposer-reward finalization path (`specWithProposerAndFundsFlex` / `specWithProposerAndFunds`) invokes `Split` on the block proposer's node unconditionally whenever a `CLStakingInfo` exists, with no minimum-stake guard.

### Finding Description
`consolidatedNode.Split` computes: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- panics if totalAmount == 0
	...
}
```

`StakingAmount` and `CLStakingAmount` are derived by integer-dividing the raw wei balance by `params.KAIA` (10^18), so any staked amount below 1 KAIA truncates to `0`: [2](#0-1) 

In `assignStakingRewards`/`assignStakingRewardsFlex`, `Split` is only called after confirming `cnTotalStakingAmount > minStake` (which guarantees `StakingAmount + CLStakingAmount > 0`), so those paths are safe: [3](#0-2) 

However, in `specWithProposerAndFundsFlex`, `Split` is invoked on the proposer's `consolidatedNode` with **no such check** — only that `CLStakingInfo` is non-nil: [4](#0-3) 

If a validator's own CN stake truncates to `0` (raw stake < 1 KAIA) **and** the CL pool registered for that validator also has a staked amount truncating to `0` (< 1 KAIA), then `totalAmount = 0 + 0 = 0`, and `Div` panics (Go's `big.Int.Div` panics on division by zero, it does not return an error).

### Impact Explanation
This panic occurs inside `FinalizeState` while computing the deferred block reward for the current block's proposer — a step every full/validator node executes for every block. A panic there crashes node processes uniformly across the network when they attempt to finalize the affected block, which is a chain-wide liveness/DoS impact rather than an isolated revert. This matches the "state divergence / node crash" impact category called out in the validation rules.

### Likelihood Explanation
The trigger requires:
1. A validator's CN staking amount to be less than 1 KAIA (achievable if the validator itself stakes a tiny amount, which is plausible pre-`minStake` enforcement or via a validator/operator with a nominal stake), and
2. A CL pool registered for that validator's node to also hold less than 1 KAIA — which any unprivileged staker can arrange by staking a sub-1-KAIA "dust" amount into that CL pool (CL staking is designed to be permissionless per `kaiax/staking/README.md`).

Because condition (2) alone is entirely controllable by an ordinary, unprivileged staker (no validator cooperation is strictly required if the target validator's own stake is already below 1 KAIA, e.g., early in onboarding or under governance configurations with low/no `minStake` requirement), this is reachable without a malicious-validator or malicious-node precondition. I was not able to fully verify from the indexed code whether GC/validator admission strictly enforces `minStake` at all times (independent of reward eligibility) — this could not be fully confirmed within available context and would need further verification (e.g., in `kaiax/valset` admission logic) to establish the precise likelihood.

### Recommendation
Add an explicit zero-check before dividing in `consolidatedNode.Split`:
```go
if totalAmount.Sign() == 0 {
    return amount, big.NewInt(0) // or another well-defined fallback
}
```
Alternatively, guard the call sites in `specWithProposerAndFundsFlex` / `specWithProposerAndFunds` to skip the CN/CL split when `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount == 0`, mirroring the guard already used in `assignStakingRewards`/`assignStakingRewardsFlex`.

### Proof of Concept
1. Register/operate a CN validator node whose CN staking-contract balance is under 1 KAIA (so `StakingAmount` truncates to `0` per `kaiax/staking/impl/getter.go:286-301`).
2. As any unprivileged staker, stake a sub-1-KAIA amount (e.g., 1 wei up to 0.999999 KAIA) into that validator's CL pool via the CL registry/staking flow, so `CLStakingAmount` also truncates to `0`.
3. Wait for/arrange for that validator to be selected as block proposer (Prague hardfork active, `UseFlexReward` or Kore rules active).
4. During `FinalizeState` for that block, `getDeferredRewardFullFlex`/`getDeferredRewardFullKore` → `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` → `consolidatedNode.Split(proposer)` computes `totalAmount = 0`, and `big.Int.Div` panics, crashing the node's block-finalization routine.

Note: I could not execute this against a live node from this environment; the PoC is derived purely from static code tracing of the cited functions. Confirming the exact validator-admission preconditions (whether `minStake` is enforced independent of this reward code) would require running a local devnet, which is outside the scope of this read-only analysis.
