### Title
Repository-identity re-derivation from mutable remote URL text allows GitHub "repo-jacking" to silently rebind a tracked repository (and its remote URL) to an attacker's repository - (File: `app/src/lib/stores/app-store.ts`)

### Summary
On every background/periodic refresh, Desktop re-resolves the GitHub repository associated with a local clone not from a stable identifier, but by re-parsing the current text of the local git remote URL and asking the GitHub API for whatever repository currently sits at that `owner/name` slug. If that slug becomes squatted after a rename/transfer/account-rename on GitHub (a well known "repojacking" technique), the API object returned is attacker-controlled, and Desktop will (a) overwrite its local database record of the tracked `GitHubRepository` with the attacker's data, and (b) under certain conditions rewrite the actual git `origin` remote URL to the attacker's `clone_url` — all without prompting the user.

### Finding Description
`matchGitHubRepository` in `app-store.ts` derives the `owner`/`name` pair to query the API purely from the current text of `gitStore.defaultRemote.url`, not from any GitHub numeric repository id stored earlier: [1](#0-0) 

`repository-matching.ts`'s `matchGitHubRepository` helper performs this parsing purely on URL text via `parseRemote`, with no cross-check against a previously stored repository identity: [2](#0-1) 

That `owner`/`name` pair is then used directly to hit the GitHub API for "the" repository, and the result is trusted to update both the persisted `GitHubRepository` record and (via `updateRemoteUrl`) the actual git remote: [3](#0-2) 

`updateRemoteUrl` will rewrite the local `origin` remote's URL to the API-reported `clone_url` as long as the protocol scheme text matches and the remote hasn't been "manually" changed away from what was last recorded — it does not verify that the API response actually corresponds to the *same* GitHub repository ID the user originally added: [4](#0-3) 

Even in the (common) case where the URL text hasn't changed and `updateRemoteUrl` is a no-op, the surrounding code unconditionally persists the API repository into the local database as the association for this repository via `upsertGitHubRepository`, replacing `cloneURL`, `permissions`, `private`, `isArchived`, etc. with whatever the API returned for that slug: [5](#0-4) [6](#0-5) 

**Broken invariant:** the app assumes an `owner/name` GitHub slug is a stable, non-reusable identity for the lifetime of a cloned repository. On GitHub, slugs are *not* permanently reserved — renaming a repository, transferring it, or renaming/deleting the owning account frees the old `owner/name` combination for anyone to claim (classic repo-jacking / dependency-confusion vector documented across the industry for CI configs, GitHub Actions, npm/go module paths, etc.). Desktop re-resolves this identity from scratch on every refresh instead of pinning to the GitHub repository's immutable numeric `id`, so once an attacker claims the freed slug, the next background refresh silently swaps in the attacker's repository as ground truth.

### Impact Explanation
This meets the "attacker controls a GitHub API object" primitive: the attacker's primitive is simply registering/claiming a repository at a slug that a victim's Desktop instance still references. Concrete consequences:
- The local `GitHubRepository` record (permissions, private flag, parent/fork info, `cloneURL`) is silently replaced with the attacker's repository's data, corrupting the trust basis for subsequent operations (branch protection checks via `refreshBranchProtectionState`, "View on GitHub", PR association, etc.) — all performed without any user confirmation.
- In scenarios where the freed slug is reclaimed by an attacker in a way that changes the reported `clone_url` (e.g., different casing/host normalization, or the user's remote still pointing to the pre-rename URL while the API now reports a slug the attacker owns), `updateRemoteUrl` will rewrite the user's `origin` remote to the attacker-controlled URL with no prompt, so the next `git push`/`fetch` silently targets the attacker's repository — a "silent corruption of what the user commits or pushes."

This is a background/unattended action (repository refresh runs on startup, account switch, and periodically), so it requires no unusual user steps beyond simply having Desktop open with the repository tracked.

### Likelihood Explanation
Likelihood is Medium: it requires a real-world precondition (a tracked repository's `owner/name` slug becoming available for squatting via rename/transfer/account-rename on GitHub — a documented, previously-exploited class of issue in the broader GitHub ecosystem) rather than any local/privileged access. No credentials, malware, or social engineering are required from the Desktop app's perspective; the trigger is entirely on GitHub's namespace-reuse side and Desktop's blind trust in the "current" API response for a mutable slug.

### Recommendation
Track and validate GitHub repository identity by the immutable numeric API repository `id`, not solely by `owner`/`name` text parsed from the local remote URL. Before persisting `upsertGitHubRepository`/rewriting the remote via `updateRemoteUrl`, verify that the `id` field of the newly fetched `apiRepo` matches the `id` previously stored for this local repository's `GitHubRepository` record; if it has changed unexpectedly, surface this to the user (e.g., "This repository's association on GitHub has changed — is this expected?") instead of silently applying the update.

### Proof of Concept
1. Victim clones `https://github.com/victim-org/project.git` in GitHub Desktop; Desktop stores a `GitHubRepository` DB record (`repositories-store.ts`) with `cloneURL`, `permissions`, etc. for this slug.
2. `victim-org` renames the repository to `project-v2` (or the `victim-org` account itself is renamed/deleted), freeing the `victim-org/project` slug.
3. Attacker creates a new repository at the now-available `victim-org/project` slug (or an equivalent freed owner/name combination).
4. On the victim's next Desktop refresh (app start, account switch, or periodic timer), `matchGitHubRepository` (`app-store.ts:4964-4977`) re-parses the still-unchanged local remote text `https://github.com/victim-org/project.git`, extracts `owner=victim-org`, `name=project`, and `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('victim-org', 'project')` (`app-store.ts:4890`) — which now resolves to the attacker's repository object.
5. `upsertGitHubRepository` (`repositories-store.ts:596-666`) persists the attacker's `cloneURL`/`permissions`/`private` flags as the local `GitHubRepository` record for this path, and `updateRemoteUrl` (`update-remote-url.ts`) may rewrite the git `origin` URL to the attacker's `clone_url`, all without any dialog or confirmation shown to the user.

**Note on completeness:** I was not able to fully trace every caller/scheduling path of `repositoryWithRefreshedGitHubRepository` (e.g. exact periodic refresh interval, and every downstream consumer of the corrupted `GitHubRepository` record such as branch protection or PR flows) within the available search iterations; a full audit of `app-store.ts` refresh scheduling and all consumers of `gitHubRepository.cloneURL`/`permissions` would strengthen confidence in the exact blast radius.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }
