### Title
`forceUnLock`/`cancelUnlock` in VLMGP fail to sync `ReferralStorage` factor, unlike `lock`/`startUnlock` - ([File: VLMGP.sol])

### Summary
This is the same bug class as the reported `RCTreasury.payout` issue: a function that changes a user's underlying locked-balance state fails to propagate the corresponding status update to a dependent accounting structure, while sibling functions performing the equivalent state change do perform that update.

### Finding Description
`VLMGP.sol` maintains `userUnlockings` slots that track a user's locked vs. cooling-down MGP, and a separate `ReferralStorage` contract caches a `totalFactor` per user that is derived from the user's vlMGP lock/cool-down position (used via `getRewardablePercentWAD`/lock amounts for referral reward accounting).

Both `_lock` and `startUnlock` explicitly call `IReferralStorage(referralStorage).updateTotalFactor(...)` immediately after changing the user's locked/cool-down amounts: [1](#0-0) [2](#0-1) 

However, `cancelUnlock` and `forceUnLock` also mutate the user's locked/cool-down amounts (`totalAmountInCoolDown`, `slot.amountInCoolDown`, and via `_unlock` the underlying `totalAmount`/master-magpie balance), but neither calls `updateTotalFactor`: [3](#0-2) 

`_unlock` itself only touches `totalAmountInCoolDown`/`totalAmount` and the master-magpie balance — it never touches `referralStorage`: [4](#0-3) 

This means after a user cancels an unlock or force-unlocks (forfeiting a penalty) their vlMGP balance/position changes, but `ReferralStorage`'s cached `totalFactor` for that user is left stale, exactly mirroring the `RCTreasury.payout` pattern where a balance-changing function omits the state-flag update that a sibling balance-changing function (`refundUser`) performs.

### Impact Explanation
Because `ReferralStorage.totalFactor` is used to compute referral reward shares, a stale factor after `forceUnLock`/`cancelUnlock` causes referral reward accounting to be computed against a locked-balance snapshot that no longer reflects the user's real vlMGP position. Depending on how `totalFactor` is consumed downstream, this can result in referral yield being permanently miscredited (either frozen away from rightful recipients or captured by a user whose real position no longer supports it) — i.e., theft or permanent freezing of unclaimed referral yield.

### Likelihood Explanation
`forceUnLock` and `cancelUnlock` are ordinary user-callable functions requiring no privileged role, and the missing call is deterministic — any user who has a referral factor tracked and calls either function will trigger this inconsistency. Likelihood is high; the only uncertainty is the precise downstream financial magnitude, which depends on `ReferralStorage`'s consumption of `totalFactor` (not fully inspectable within this review's context).

### Recommendation
Add `if (referralStorage != address(0)) IReferralStorage(referralStorage).updateTotalFactor(msg.sender);` to both `cancelUnlock` and `forceUnLock` in `VLMGP.sol`, mirroring `_lock`/`startUnlock`. The analogous `mWomSV.sol` `cancelUnlock`/`unlock` paths should be checked for the same omission if `mWomSV` also feeds a referral/factor accounting system.

### Proof of Concept
1. User locks MGP via `VLMGP.lock`, which sets an initial `ReferralStorage.totalFactor` via `updateTotalFactor`.
2. User calls `startUnlock` — `totalFactor` is refreshed correctly.
3. User calls `forceUnLock` (or `cancelUnlock`) on that slot — the user's locked balance changes (`totalAmount`/`totalAmountInCoolDown` reduced, tokens returned), but `updateTotalFactor` is never invoked, per `VLMGP.sol` lines 339-367.
4. `ReferralStorage.totalFactor[user]` remains at the pre-unlock value indefinitely (until the user happens to call `lock`/`startUnlock` again), causing referral reward computations to use a stale, incorrect factor for that user for an unbounded period. [3](#0-2) [5](#0-4)
