## Title
Stale VAT-eligibility filter allows a validator to panic the Bank's epoch-boundary state transition via `checked_sub().expect(...)` underflow — ([File: runtime/src/bank.rs])

### Summary
The reported bug's broken invariant is: a "should never happen" state (debt-free account) is treated by a downstream guard as if the earlier check still holds, so the guarded action executes on state that no longer satisfies the assumption. The same pattern exists in Agave's Validator Admission Ticket (VAT) mechanism: `VoteAccounts::clone_and_filter_for_vat` [1](#0-0)  filters vote accounts to only those with `lamports() >= minimum_vote_account_balance`, and the resulting `VersionedEpochStakes` is later relied upon at burn time by `Bank::maybe_burn_vat_from_staked_accounts`, which asserts the invariant with an `.expect()` rather than re-validating it against the live account state [2](#0-1) .

### Finding Description
`clone_and_filter_for_vat` computes eligibility (`has_bls`, `has_stake`, `has_balance`) from a snapshot of vote-account lamports taken when epoch stakes are computed: [3](#0-2) 

The result is stored as part of `VersionedEpochStakes`/`Stakes`, which persists until it is consumed at the *next* epoch boundary by `maybe_burn_vat_from_staked_accounts`:
```
// Vote accounts have already been filtered by clone_and_filter_for_vat to only include
// accounts with non-zero stake and sufficient balance.
for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
    let mut account = self.get_account(vote_pubkey).unwrap();
    total_vat += vat_to_burn_per_epoch;
    account.set_lamports(
        account.lamports().checked_sub(vat_to_burn_per_epoch).expect(
            "Vote accounts should have already been filtered to contain enough balance for the VAT",
        ),
    );
    ...
}
``` [2](#0-1) 

The comment states the invariant is guaranteed by the filtering step, but the filtering step only inspected the vote account's lamports **at the time epoch stakes were computed**, not at burn time. Between that computation and the burn (which happens at least one full epoch later, since `epoch_stakes` for epoch N is computed during epoch N-1 and the VAT burn using those `epoch_stakes` executes as part of epoch N's boundary processing), the vote account's authorized withdrawer can call the vote program's `withdraw` instruction — an ordinary, permissionless, non-privileged transaction — to reduce the vote account's balance below `vat_to_burn_per_epoch`.

`withdraw` only checks that the account keeps a rent-exempt minimum (or is fully closed with epoch-credits/pending-reward checks); it has no knowledge of, and does not enforce, the separate VAT-burn reservation that `minimum_vote_account_balance_for_vat` is supposed to guarantee at the time of the *next* burn: [4](#0-3) 

`minimum_vote_account_balance_for_vat` is only consulted during the filtering step that produced the stale snapshot, not re-checked at burn time: [5](#0-4) 

Consequently, an attacker who controls a vote account's withdraw authority can:
1. Get included in the top VAT-eligible set for epoch N (balance ≥ threshold at filter time).
2. Withdraw lamports down to just above rent-exemption before the burn actually executes in epoch N's boundary processing.
3. Cause `checked_sub(vat_to_burn_per_epoch)` to return `None`, hitting the `.expect(...)` and panicking the validator process during bank-freeze/epoch-boundary processing.

Because this state transition is deterministic and part of consensus-critical bank processing (executed identically by every validator replaying the same epoch boundary), this is not merely a single-node crash: every validator that reaches this slot will panic identically, which is a consensus-halting condition, not a benign single-node event.

### Impact Explanation
This breaks the same class of invariant as the report: a guard (`has_balance` check) that is valid at check-time is treated as still valid at act-time, letting an unprivileged actor (any vote-account withdraw authority, no special stake or leader privilege required) drive the guarded code into an unhandled/unexpected state. Here the consequence is more severe than griefing a single account — it is a `panic!`/`.expect()` failure in `Bank`'s deterministic epoch-boundary code path (`maybe_burn_vat_from_staked_accounts`), which every validator will hit at the same slot, causing a cluster-wide halt.

### Likelihood Explanation
High. Triggering this requires only:
- A vote account that manages to be included in the VAT-eligible top set for one epoch (attacker fully controls this, since they control the vote account's balance and can top it up transiently to qualify).
- A withdraw instruction, executable by anyone with `authorized_withdrawer` for their own vote account, with no special stake or protocol privilege, sent at any point before the VAT burn is applied.

No malicious peer, leaked validator key, or trusted-component assumption is needed — this is exploitable by any ordinary vote-account owner using standard `Withdraw` instructions.

### Recommendation
Do not rely on a stale filter snapshot for a value used unconditionally at a later deterministic state transition. Either:
- Re-validate `account.lamports() >= vat_to_burn_per_epoch` inside `maybe_burn_vat_from_staked_accounts` and use `saturating_sub` (clamping at the rent-exempt minimum, or skipping burn / deactivating VAT eligibility for that account) instead of `checked_sub().expect(...)`; or
- Enforce, at the vote program's `withdraw` instruction level, that the withdrawable balance can never drop below the currently reserved `vat_to_burn_per_epoch` amount for accounts that are part of the current epoch's VAT-eligible set.

### Proof of Concept
1. Fund a vote account so its balance is exactly at `minimum_vote_account_balance_for_vat` (rent-exempt minimum + `vat_to_burn_per_epoch`), and ensure it has a BLS pubkey and non-zero delegated stake, so it passes `clone_and_filter_for_vat` and is captured into `epoch_stakes` for the upcoming epoch [3](#0-2) .
2. Before the epoch boundary where `maybe_burn_vat_from_staked_accounts` is invoked for that epoch's stakes, submit a `Withdraw` vote instruction reducing the vote account's lamports to just the rent-exempt minimum (or slightly above) [4](#0-3) .
3. When the bank reaches the epoch boundary and calls `maybe_burn_vat_from_staked_accounts`, `account.lamports().checked_sub(vat_to_burn_per_epoch)` returns `None` and the `.expect(...)` panics [6](#0-5) .

Note: I was unable to fully trace, within the available index, the exact number of slots/epochs between when `epoch_stakes`/`VersionedEpochStakes` for a given epoch are computed and when `maybe_burn_vat_from_staked_accounts` consumes them (the calls span `runtime/src/stakes.rs` and `runtime/tests/vote_account.rs`, which the index only partially surfaced). This timing gap is what creates the exploit window, and confirming its exact bounds would require examining the full epoch-boundary/reward-distribution call graph directly in the repository rather than through the indexed search results available here.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }
