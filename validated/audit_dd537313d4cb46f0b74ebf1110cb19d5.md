### Title
`rewards()` view in the distribution precompile omits the non-payable value check, permanently stranding sent SEI/usei - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` rejects `msg.value` on every other query method via `pcommon.ValidateNonPayable`, but the `rewards` method's handler skips this check entirely, allowing a value-bearing call to succeed while the attached SEI is never credited, refunded, or otherwise accounted for.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` at [1](#0-0) , passing no `value` parameter at all, whereas the read-only sibling methods like `params`, `validatorOutstandingRewards`, `communityPool`, etc. are called with `value` and enforce `p.validateInput(value, args, N)` → `pcommon.ValidateNonPayable(value)` before proceeding (e.g. [2](#0-1)  and [3](#0-2) ). The `rewards` function itself, defined at [4](#0-3) , only validates argument length via `pcommon.ValidateArgsLength(args, 1)` and never touches `value`. `ValidateNonPayable` is the mechanism intended to reject value-bearing calls to non-payable functions, as defined generically in `precompiles/common/precompiles.go`: [5](#0-4) . Because the EVM ante/execution pipeline still debits the caller's usei/wei balance for the attached `value` when the call target succeeds, and the `rewards` handler does nothing with that `value` (no `HandlePaymentUsei`/`HandlePaymentUseiWei` refund path is invoked, unlike precompiles that intentionally accept payment), any ETH-denominated value sent alongside a `rewards()` call is debited from the caller and left unaccounted for at the precompile address, with no withdrawal or refund path—an on-chain analog of the reported "empty receive()/no-payable-guard" bug pattern that traps funds. This is confirmed directly by the codebase's own test-suite documentation: [6](#0-5) , which explicitly notes rewards() is the one precompile view lacking this guard and that the test suite deliberately skips a "view rejects value" assertion for it because it would fail.

### Impact Explanation
Any unprivileged EVM caller (contract or EOA) who calls `rewards(address)` on the distribution precompile with non-zero `msg.value` will have that value deducted from their usei/wei balance via the standard EVM value-transfer semantics, but the precompile performs no bank transfer crediting the value anywhere reachable by the user or protocol — it is neither refunded to the caller nor delivered to any recoverable pool. This constitutes direct, permanent loss of user funds reachable from a single public transaction, matching the "Medium" concrete-fund-loss/freezing bar in the validation criteria.

### Likelihood Explanation
Trivial to trigger: any caller can invoke `rewards(delegatorAddress)` through the ABI-exposed precompile at `0x1007` and simply attach a nonzero `value`. No special privileges, prior state, or multi-step setup are required beyond having an associated address and a positive balance, making this reachable by any public RPC client.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by every other view method to `rewards`, either by passing `value` into `p.rewards(...)` at the dispatch site and checking it first, or by refactoring `rewards` to call `p.validateInput` like `params`/`communityPool` do, so a value-bearing call reverts instead of silently stranding funds.

### Proof of Concept
1. Associate an EVM address with a Sei account and ensure it holds usei/wei balance.
2. Call the distribution precompile (`0x0000000000000000000000000000000000001007`) function `rewards(address delegatorAddress)` via `eth_call`/a transaction, attaching `value: 1` wei (or any nonzero amount) instead of `0`.
3. Observe the call succeeds (no revert), in contrast to identical value-bearing calls to `params()`, `communityPool()`, or `validatorOutstandingRewards()` on the same precompile, which revert with "sending funds to a non-payable function" (as unit-tested in `precompiles/staking/staking_test.go` for the analogous staking precompile pattern).
4. Confirm the caller's on-chain balance decreased by the attached value while the precompile/distribution module shows no corresponding credit, delegation reward increase, or refund — the value is unrecoverable.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
