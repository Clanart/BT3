### Title
`allowed-tools` scoping on `/pr-review-toolkit:review-pr` is not inherited by `Task`-spawned subagents, allowing untrusted repo content to trigger unrestricted `Write`/`Edit` - ([File: plugins/pr-review-toolkit/commands/review-pr.md])

### Summary
`review-pr.md` restricts its own tool set to `["Bash", "Glob", "Grep", "Read", "Task"]`, but the agents it dispatches via `Task` — `code-reviewer.md` and `code-simplifier.md` — omit the `tools:` frontmatter field entirely, so they default to unrestricted tool access, including `Write`/`Edit`. Because subagent tool scoping is governed solely by the subagent's own frontmatter and not bounded by the invoking command's `allowed-tools`, a crafted repository can steer the command into launching `code-simplifier` and obtain file-mutation capability that `review-pr.md`'s declared tool set explicitly excludes.

### Finding Description
`review-pr.md` declares `allowed-tools: ["Bash", "Glob", "Grep", "Read", "Task"]` [1](#0-0) , and its documented workflow is: run `git diff --name-only` to identify changed files, then dispatch specialized review agents via `Task`, including `code-simplifier` "After passing review" and unconditionally suggests `code-reviewer` for "general quality" [2](#0-1) .

The dispatched agents `code-reviewer.md` and `code-simplifier.md` have no `tools:`/`allowed-tools:` field in their frontmatter at all [3](#0-2) [4](#0-3) . Per the plugin-dev agent-development documentation, this is explicit: "**Default:** If omitted, agent has access to all tools" [5](#0-4) , and the MCP tool-usage reference reiterates "Agents have broader tool access than commands: Can use any tool Claude determines is necessary" [6](#0-5) .

`code-simplifier`'s own system prompt explicitly instructs it to operate autonomously and mutate code: "You operate autonomously and proactively, refining code immediately after it's written or modified without requiring explicit requests" [7](#0-6) . Combined with unrestricted tool defaults, this agent is designed to call `Write`/`Edit`.

Because the `Task` tool call is the boundary at which subagent selection and tool scoping occur, and the CHANGELOG confirms subagent tool restriction is agent-frontmatter-driven and permission-mode is what's inherited from the parent session — not the tool allowlist — ("Deprecated the Task tool's `mode` parameter (now ignored); subagents inherit the parent session's permission mode by default") [8](#0-7) , there is no mechanism in this repo's plugin files that clamps a spawned agent's effective tool set to the parent command's `allowed-tools`. An attacker who controls the reviewed repository content (diff, comments, file structure) can shape what `review-pr.md` decides to review and can make the natural review flow invoke `code-simplifier`/`code-reviewer`, both of which can then call `Write`/`Edit` — tools not present in `review-pr.md`'s declared `allowed-tools` — without any additional gating specific to this command.

### Impact Explanation
This is a tool-scope escalation: a command explicitly declared as read/analysis-only (no `Write`/`Edit`) can transitively cause unapproved file mutation via a subagent it spawns, because the child agent's frontmatter (or its absence) — not the parent's `allowed-tools` — determines the effective capability. This maps to Claude Code's "unauthorized file/command action despite deny-by-default tool scoping" bounty category: a user who trusts `allowed-tools` as an enforced ceiling on a slash command's blast radius can have files modified by a subagent triggered while reviewing attacker-controlled repository content.

### Likelihood Explanation
Preconditions are modest: the attacker only needs to control files/diff content in a repository that a legitimate user reviews with `/pr-review-toolkit:review-pr` (e.g., a cloned PR branch). The command's own documented workflow already lists `code-simplifier` as a standard, expected step ("After passing review": code-simplifier) [9](#0-8) , so no unusual prompt injection is even required — normal command usage on `simplify`/`all` review aspects reaches the subagent. This is reproducible on any clone of the plugin without special privileges.

### Recommendation
Enforce tool-set intersection at the `Task` boundary: when a command frontmatter declares `allowed-tools`, any subagent it spawns via `Task` should have its effective tool set clamped to the intersection of its own declared tools and the invoking command's `allowed-tools`, rather than defaulting to "all tools" independent of the parent scope. Additionally, `pr-review-toolkit`'s `code-reviewer.md` and `code-simplifier.md` should explicitly declare a minimal `tools:` list (e.g., `["Read", "Grep", "Glob"]` for review-only agents) instead of omitting the field, and any agent that legitimately needs `Write`/`Edit` (like `code-simplifier`) should require explicit user approval before those tool calls when invoked transitively from a read-only-scoped command.

### Proof of Concept
Integration test plan:
1. Create a temporary git repo with a tracked file and an unstaged diff crafted to be "simplifiable" (e.g., nested ternaries, dense code matching `code-simplifier`'s trigger heuristics from its system prompt) [10](#0-9) .
2. Invoke `/pr-review-toolkit:review-pr simplify` (or `all`) against this repo in a harness that records every tool invocation and its declared source (command vs. subagent).
3. Assert that `git diff --name-only`, `Read`, `Grep` calls occur from the `review-pr` command context, consistent with its `allowed-tools` [1](#0-0) .
4. Assert that when `Task(subagent_type=code-simplifier)` is invoked, no `Write`/`Edit` tool call is executed without an explicit separate user-approval prompt distinguishable from the parent command's pre-authorized `allowed-tools`.
5. Expected failure mode today: `code-simplifier` (and `code-reviewer`) issue `Write`/`Edit` calls that are treated as within scope because the agents' own frontmatter has no `tools:` restriction, violating the invariant that the parent's `allowed-tools` bounds transitive subagent capability.
