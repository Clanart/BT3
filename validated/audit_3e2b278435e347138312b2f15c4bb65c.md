### Title
Fee-on-Transfer / Deflationary Reward Tokens in `donateRewards`/`queueNewRewards` Cause Inflated Reward Accounting and Permanent Freezing of Unclaimed Yield - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool._provisionReward` (reached via the unprivileged, unauthenticated `donateRewards` function) trusts the `_amountReward` parameter as the exact amount of reward tokens received by the contract, without measuring the actual balance delta from the `safeTransferFrom` call. For any reward token that takes a fee/deducts a portion on transfer, the contract will credit `rewardPerTokenStored`/`historicalRewards` for more tokens than it actually holds, permanently breaking reward accounting for that token and eventually causing `getReward` to revert due to insufficient balance.

### Finding Description
`donateRewards` is a fully public, unprivileged function — any wallet may call it for any token that has previously been registered as a reward token (`isRewardToken[_rewardToken] == true`): [1](#0-0) 

It calls `_provisionReward`, which pulls the token via `safeTransferFrom(msg.sender, address(this), _amountReward)` and then unconditionally uses the nominal `_amountReward` value — not the actual balance received — to update `historicalRewards` and `rewardPerTokenStored`: [2](#0-1) 

If `_rewardToken` charges any transfer fee (a common, non-malicious ERC20 behavior — see [weird-erc20 fee-on-transfer](https://github.com/d-xo/weird-erc20?tab=readme-ov-file#fee-on-transfer)), the contract actually receives `_amountReward - fee`, but `rewardPerTokenStored` is inflated as if the full `_amountReward` was received. This is the exact same root cause identified in the referenced Metrom report: the code assumes `transferFrom` amount == amount received, instead of measuring the balance before/after the transfer.

Because `rewardPerTokenStored` only ever increases and is shared across all stakers via `earned()`: [3](#0-2) 

the aggregate `userRewards` owed across all accounts for that token will eventually exceed the real token balance held by the pool. When users call `getReward` (via MasterMagpie), the `safeTransfer` call will revert once the contract's real balance is insufficient to cover the inflated accounting: [4](#0-3) 

Since `rewardPerTokenStored` cannot be reduced and the missing tokens can never be recovered (they were taken as a transfer fee, not held by the contract), this results in permanent freezing of unclaimed yield for that reward token — later claimants (whoever calls `getReward` after the pool balance is depleted) are permanently unable to withdraw their accrued rewards.

The identical unguarded pattern also exists in `_provisionReward` of `BaseRewardPoolV2.sol`: [5](#0-4) 

### Impact Explanation
This causes permanent freezing/loss of unclaimed yield for legitimate stakers of a pool: once the reward-token accounting outpaces the actual token balance (triggered by any wallet supplying a fee-on-transfer/deflationary reward token via the unprivileged `donateRewards` entrypoint), some users' `getReward` calls will permanently revert for that reward token, and the shortfall can never be corrected on-chain. This matches the "permanent freezing of unclaimed yield" impact criterion.

### Likelihood Explanation
Likelihood is moderate: it requires a reward token registered in the pool (`isRewardToken[token] == true`) to be a fee-on-transfer/deflationary token. Reward-token registration itself happens via the manager-only `queueNewRewards`, but exploitation of the resulting mismatch requires no privilege at all — `donateRewards` is callable by any wallet, and even routine, honest reward funding via `queueNewRewards` with such a token triggers the same bug without any malicious admin action, mirroring the exact non-malicious scenario in the source report (an ordinary campaign/reward creator using a fee-on-transfer token).

### Recommendation
In `_provisionReward`, measure the actual amount received instead of trusting the parameter:
```solidity
uint256 balanceBefore = IERC20(_rewardToken).balanceOf(address(this));
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
uint256 received = IERC20(_rewardToken).balanceOf(address(this)) - balanceBefore;
// use `received` for historicalRewards / rewardPerTokenStored / queuedRewards calculations
```
Apply the same fix to `BaseRewardPoolV2._provisionReward` and any other reward-provisioning function (e.g., `vlMGPBaseRewarder.queueNewRewards`) that assumes transferred amount equals received amount.

### Proof of Concept
1. A manager registers a fee-on-transfer token `T` (e.g., 5% fee) as a reward token via `queueNewRewards(1000, T)`, which is a normal, non-malicious operational action — the pool only actually receives 950 `T`, but `rewardPerTokenStored`/`historicalRewards` are updated for 1000.
2. Alternatively/subsequently, any unprivileged wallet calls `donateRewards(1000, T)` — again the pool only receives 950 `T`, but accounting reflects 1000 distributed.
3. Over time, as `rewardPerTokenStored` accumulates deposits from `T`, aggregate `userRewards[T][*]` computed via `earned()` exceeds the pool's actual `T` balance.
4. When enough users call `getReward` and drain the real (short) balance, the remaining users' `getReward` calls revert at `IERC20(rewardToken).safeTransfer(_receiver, reward)` inside `BaseRewardPool.getReward` because the contract's `T` balance is less than the sum of outstanding `userRewards[T]`. Those users' accrued `T` rewards are permanently unclaimable.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
