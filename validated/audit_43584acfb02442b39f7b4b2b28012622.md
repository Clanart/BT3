### Title
Scanner accepts and reports outputs of any value, including uneconomical dust that cannot be spent without a net loss — (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_transaction`/`scan_block` match received outputs solely on `script_pubkey` and return them as spendable `ReceivedOutput`s with no minimum-value bound. While `SignableTransaction::new` carefully enforces a lower bound (`DUST`) on payments it *creates* and a minimum fee, the receiving path enforces no bound at all. Any external party can send arbitrarily small outputs (e.g., 1 sat) to a Serai P2TR address and have them reported to the protocol as received, spendable funds.

### Finding Description
The scanning logic in `Scanner::scan_transaction` performs a pure `script_pubkey` lookup against registered scripts and immediately constructs a `ReceivedOutput` for any match, with no check on `output.value`: [1](#0-0) 

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

The only public key needed to derive a matching `script_pubkey` is the (public) group key: `Scanner::new` registers `p2tr_script_buf(key)` for the base key with offset `Scalar::ZERO` (`mod.rs:162-166`). Anyone who knows the group's tweaked key — which is public — can craft a standard P2TR output paying to it.

This is the mirror image of the reported bug: value bounds are enforced on outbound payments (`*amount < DUST` → `DustPayment`, `send.rs:165-169`) and on fees (`TooLowFee`, `send.rs:211-213`), but the symmetric inbound bound — a minimum output value for a `ReceivedOutput` to be considered economically spendable — is missing. `SignableTransaction::new` will then happily consume these outputs as inputs (`send.rs:150-156`, `input_sat` summation at `send.rs:175`), since it only verifies `input_sat >= payment_sat + needed_fee` and never checks that any individual input is worth more than the fee required to spend it.

### Impact Explanation
Each Taproot input costs ~57 vbytes to spend (documented in the processor's `DUST` rationale: 230 weight units ≈ 57 vbytes). An output below the marginal fee cost of its own input is a net liability: including it in a transaction destroys value rather than adding it. Because `scan_transaction` reports these outputs as ordinary `ReceivedOutput`s with no distinguishing flag, downstream accounting treats dust as real received funds — funds "received" that are not spendable at a profit, and are outright unspendable at any fee rate where `value < input_cost`. A sender can thus inflate reported balances, force fee amortization onto legitimate payments, or saddle the wallet with inputs whose inclusion strictly reduces the value of every transaction spending them.

### Likelihood Explanation
The attack requires only a standard, consensus-valid Bitcoin transaction paying a tiny amount to a publicly derivable Serai address — fully reachable by any unprivileged on-chain party. No collusion, malicious validator, or leaked key is needed. Likelihood is limited mainly by the fact that exploiting it costs the attacker the dust amount and the effect is bounded per-output, hence Medium rather than High.

### Recommendation
Apply a minimum-value bound in `Scanner::scan_transaction`/`scan_block` symmetric to the outbound `DUST` check — e.g., only emit a `ReceivedOutput` when `output.value.to_sat() >= DUST` (or a documented network spendability threshold such as the 10,000-sat value used downstream). Alternatively, return the output but mark/report sub-threshold outputs distinctly so callers do not treat uneconomical inputs as spendable funds.

### Proof of Concept
```rust
// Attacker learns the group's tweaked key (public), derives the P2TR script:
let victim_script = p2tr_script_buf(group_key).unwrap();

// Attacker broadcasts a TX with a 1-sat output to that script.
// Inside Serai's scanner:
let received = scanner.scan_transaction(&attacker_tx);
assert_eq!(received.len(), 1);
assert_eq!(received[0].value(), 1); // reported as a spendable ReceivedOutput

// The wallet then accepts it as an input despite it being unspendable at a profit:
let stx = SignableTransaction::new(
  vec![received[0].clone()],
  &[(payment_script, DUST)],
  None, None, fee_per_vbyte,
);
// input_sat = 1 << payment + fee -> NotEnoughFunds, or with mixed inputs the
// dust input silently consumes ~57 vbytes * fee_rate in fees for 1 sat of value.
```

The one-sided bound (enforced minimum on outgoing payments/fees, none on incoming outputs) is the direct analog of enforcing a `feeRate` ceiling but no floor.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
