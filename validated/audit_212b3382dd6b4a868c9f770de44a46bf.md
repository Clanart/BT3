### Title
Unprotected AMM swap with input-amount floor in `SmartWomConvert._convertFor`/`smartConvert` allows sandwich-attack theft of protocol revenue - (File: `wombat/SmartWomConvert.sol`)

### Summary
`WombatStaking.harvest()` is a permissionless, unprivileged-wallet-callable function that ultimately routes harvested WOM fees through `SmartWomConvert.smartConvert()`, which performs a Wombat AMM swap (`swapExactTokensForTokens`) with `minAmountOut = 0` at the router level and only checks the aggregate output against a floor equal to the input amount (`_minRec = _amountIn`). This mirrors the RevenueHandler bug class: the code assumes the swap price can never fall below 1:1, and enforces only that weak floor rather than a price derived from a trusted, un-manipulatable reference — allowing an attacker to sandwich the harvest transaction with a flash loan, capture the difference between the fair swap output and the lax floor, and cause the protocol/stakers to receive less mWOM than they should.

### Finding Description
`WombatStaking.harvest(address _lpToken)` has no caller restriction beyond `whenNotPaused` and `_onlyActivePool` (pool-state check, not an access-control check), so any wallet can trigger it: [1](#0-0) 

`harvest` calls `_toMasterWomAndSendReward`, which computes the WOM rewards harvested and forwards them to `_sendRewards`: [2](#0-1) 

`_sendRewards`, when the fee is configured as `isMWOM` and a `smartWomConverter` is set, calls `smartConvert(feeAmount, 0)` on `SmartWomConvert`: [3](#0-2) 

Inside `SmartWomConvert.smartConvert`, the fair conversion ratio is derived from `currentRatio()` (a live on-chain AMM quote from the same `womMWomPool`/router that will be used for the actual swap) and, when the price is favorable to buy back mWOM from the market (`mWomToWom < buybackThreshold`), a portion of the WOM is routed through the market instead of being minted 1:1: [4](#0-3) 

The actual swap call passes `0` as the router-level minimum output, and the only protection is a post-swap floor check requiring the total output (swap output + 1:1-minted portion) to be at least the raw input amount: [5](#0-4) 

This is structurally identical to the reported RevenueHandler bug: the code path assumes a price relationship (`buybackAmount` should always yield materially more than 1:1 because `mWomToWom < buybackThreshold` i.e. mWOM is priced at a discount) but the actual on-chain slippage guard only enforces the breakeven amount (`_minRec == _amountIn`), not a value derived from the pre-manipulation fair price. Because `currentRatio()` is read from the very same pool that is swapped against in the same transaction, an attacker can:
1. Flash-loan WOM/mWOM and swap into the `womMWomPool` to push the pool's mWOM price up (worsening the exchange rate) right before calling `harvest()`.
2. Call (or front-run someone else's call to) `harvest()`, which invokes `smartConvert` — the degraded ratio still satisfies the loose `_minRec = _amountIn` floor and the transaction succeeds, but the WombatStaking/veWOM stakers now receive close to the 1:1 floor instead of the fair discounted-buyback amount.
3. Reverse the swap to restore the pool and realize a profit equal to the amount of mWOM value that should have gone to stakers but was instead captured by the attacker.

### Impact Explanation
This results in direct theft of protocol revenue that would otherwise accrue to mWOM/WombatStaking depositors — WOM fees are converted at a manipulated, worse-than-fair rate, and the difference is extracted by the attacker via the sandwich. This is a direct loss of user/protocol funds each time `harvest()` is triggered while `mWomToWom < buybackThreshold`, matching the accepted "direct theft of user funds" impact category.

### Likelihood Explanation
`harvest()` is callable by anyone with no special permissions or capital requirement (funded via flash loan), exactly as in the original report ("Anyone can call `RevenueHandler.checkpoint()`"). The trigger condition (`mWomToWom < buybackThreshold`, i.e., mWOM trading at a discount relative to WOM) is a normal, expected market condition this code path is explicitly designed to handle, so the attack surface is regularly available, not a rare edge case.

### Recommendation
Do not use the raw input amount as the slippage floor for a swap whose purpose is to capture better-than-1:1 pricing. Instead:
- Pass a real `minAmountOut` to `IWombatRouter.swapExactTokensForTokens` derived from a manipulation-resistant reference (e.g., a TWAP, or a caller-supplied slippage-bounded parameter validated against an oracle/external quote), not a same-block spot quote from the pool being swapped against.
- Consider having `harvest`/`_sendRewards` accept a caller-supplied minimum output for the WOM→mWOM buyback leg (with reasonable bounds) instead of hardcoding `0` and relying only on the aggregate `_amountIn` floor.

### Proof of Concept
Conceptual PoC (adapting the pattern from the referenced report to this codebase):
1. Attacker flash-loans WOM (or mWOM) and swaps a large amount into `womMWomPool` via the Wombat router, moving `currentRatio()` unfavorably (pushing mWOM's price up relative to WOM) so that the true buyback rate a legitimate call to `smartConvert` would have achieved is much better than 1:1.
2. Attacker calls `WombatStaking.harvest(lpToken)` for a pool whose fee config routes WOM fees through `smartConvert` (`isMWOM = true`, `smartWomConverter` set). This triggers `_sendRewards` → `SmartWomConvert.smartConvert(feeAmount, 0)` → `_convertFor`, which swaps `buybackAmount` WOM for mWOM at the now-manipulated rate; the router call uses `minAmountOut = 0` [6](#0-5) , and the post-swap check only requires `convertAmount + amountRec >= _amountIn` [7](#0-6) , which still passes despite the degraded rate.
3. Attacker reverses the initial swap in `womMWomPool`, restoring the price and realizing a profit equal to the mWOM value that would otherwise have gone to the `WombatStaking` rewarder/stakers.

Note: I could not execute this PoC (no test/fork execution available in this environment); the analysis is based on static code tracing of the call path `harvest → _toMasterWomAndSendReward → _sendRewards → smartConvert → _convertFor`, mirroring the exact bug-class mechanics described in the report.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
