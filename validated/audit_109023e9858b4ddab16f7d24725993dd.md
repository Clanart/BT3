### Title
Silent block-rule neutralization via `pattern`/`conditions` precedence mismatch in `Rule.from_dict` - (File: plugins/hookify/core/config_loader.py)

### Summary
`Rule.from_dict` gives absolute precedence to an explicit `conditions` list over the legacy `pattern` field whenever a `conditions` key is present in frontmatter, even if that list is empty, malformed, or never matches, silently discarding the `pattern`-derived condition. This lets a rule file that visually appears to enforce a strict `pattern`-based block (e.g. `pattern: rm\s+-rf`) actually become inert, because any co-present `conditions` key — however trivial or unreachable — takes over and the `pattern` is never converted into a matching condition. A hookify-generated rule (influenced by conversation/prompt content) or a repo-shipped `.claude/hookify.*.local.md` file can exploit this to make a nominally protective block rule never fire.

### Finding Description
In `plugins/hookify/core/config_loader.py`, `Rule.from_dict` (lines 45-84) builds `rule.conditions` with this logic: [1](#0-0) 
- If `'conditions' in frontmatter` (key presence check, not truthiness/validity check) and it is a list, `conditions` is built solely from `Condition.from_dict` on that list — the sibling `pattern` field is never consulted.
- The legacy fallback (`if simple_pattern and not conditions`) only fires when `conditions` ends up empty/absent.
- `rule.pattern` is still stored on the `Rule` object for display/reference, but `RuleEngine` (`plugins/hookify/core/rule_engine.py`, `_rule_matches`) only ever consults `rule.conditions`, never `rule.pattern`.

Consequences:
1. A rule author (human or the `/hookify` generation flow) can accidentally or maliciously combine both fields, e.g.:
   ```
   pattern: rm\s+-rf
   action: block
   conditions:
     - field: file_path
       operator: regex_match
       pattern: this-never-exists
   ```
   For a `bash` event, `file_path` is never populated in `tool_input`, so `_extract_field` returns `None` and `_check_condition` always fails — the rule silently never matches, even though the visible `pattern: rm\s+-rf` line makes it look like an active, correctly enforcing block rule.
2. Because `Condition.from_dict` defaults missing keys to `field=''`, `operator='regex_match'`, `pattern=''` (lines 22-29), a malformed/incomplete conditions entry produces a condition that can never resolve a field value (`field=''` is never present in `tool_input`), reinforcing the silent no-op behavior without any parse error or warning.
3. `load_rule_file`/`load_rules` never validate that `conditions`, if present, actually reference reachable fields for the declared `event`, and any exception anywhere in the hook is swallowed with `sys.exit(0)` in `pretooluse.py`, so there is no operator-visible signal that the rule stopped protecting anything. [2](#0-1) 

The net effect is that the legacy pattern form and the explicit conditions form do not compose safely: whichever form's semantics an author/reviewer believes is in effect (`pattern`) can be silently overridden by the other (`conditions`) with no indication in the loaded rule, other than diffing the raw frontmatter file by hand.

### Impact Explanation
A block rule intended to prevent dangerous operations (e.g., `rm -rf`, writing secrets to `.env`, exfiltrating tokens) can be shipped or auto-generated in a form that looks correct on inspection but never actually triggers, because of the undocumented `conditions`-over-`pattern` precedence and the lack of any reachability validation for `conditions` fields. This can be used to smuggle a de-fanged rule into a repository's `.claude/` directory (via PR review, or via `/hookify` auto-generation influenced by conversation content) that a reviewer believes is protecting against a known-dangerous pattern, while it is actually inert — enabling the dangerous command/file operation it was supposed to block, potentially leading to disclosure of sensitive code/secrets/tokens through the now-unblocked operation.

### Likelihood Explanation
Reaching this requires only the ability to influence the contents of a `.claude/hookify.*.local.md` file — either directly (repo-shipped rule file merged via normal contribution flow) or indirectly through `/hookify` rule generation, both of which are explicitly in-scope attacker channels per this question. No parser errors, admin privileges, or additional bypass is required; the dual-field precedence and silent-failure behavior are deterministic and always reproducible given the described frontmatter.

### Recommendation
- In `Rule.from_dict`, reject (or loudly warn/error on) rule files that specify both `pattern` and `conditions` simultaneously, since combining them is ambiguous.
- Validate that each `Condition`'s `field` is reachable for the rule's declared `event` at load time (in `load_rule_file`), and refuse to load (rather than silently loading a rule with zero matching conditions) if the resulting rule can never match anything for `action: block`.
- Make `Condition.from_dict` reject conditions missing required `field`/`pattern` values instead of defaulting to empty strings.
- Surface a non-suppressed warning/error to stderr (already partially done for other failures) specifically when a `block` rule is loaded with conditions that reference no reachable field for its event.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py`/`rule_engine.py` test suite:
```python
frontmatter = {
    "name": "block-dangerous-rm",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "pattern": r"rm\s+-rf",
    "conditions": [
        {"field": "file_path", "operator": "regex_match", "pattern": "unreachable"}
    ],
}
rule = Rule.from_dict(frontmatter, "Dangerous rm detected!")

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /important/data"},
})

# Expected (if invariant held): result should deny/block the dangerous command
# Actual: result == {} because rule.conditions only contains the unreachable
# file_path condition, and rule.pattern ("rm\s+-rf") is never consulted.
assert result == {}
```
This demonstrates that a visually "block `rm -rf`" rule silently allows the exact command it claims to block, confirming the legacy/explicit differential breaks the intended security invariant.
