### Title
Infinite loop via crafted cyclic coin-parent chain in `Offer.get_root_removal()` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_root_removal()` walks a chain of `Coin.parent_coin_info` pointers within the untrusted set of coins declared by an offer, looking for a "non-ephemeral" ancestor. The loop's termination condition can be defeated by a crafted offer whose declared coins form a cycle of `parent_coin_info` references, causing the loop to spin forever — the same bug class as CVE-2021-3508 (`get_xref_linear_skipped()`'s unbounded pointer-chasing loop over attacker-controlled offsets in a crafted PDF).

### Finding Description
`get_root_removal()` computes the set of "non-ephemeral" removals — coins whose `parent_coin_info` is *not* the name of another coin in the same offer — and then walks backward from a given coin until it lands on one of them: [1](#0-0) 

Both `all_removals` and the parent-hash graph come directly from `self._bundle.coin_spends`, i.e., from the raw `Offer` bytes/bech32 supplied by a counterparty (`Offer.from_bytes` → `Offer.from_spend_bundle`), with no cycle or acyclicity check performed anywhere before this point: [2](#0-1) 

Because `Coin` objects are just `(parent_coin_info, puzzle_hash, amount)` tuples supplied by the offer's `CoinSpend.coin`, an attacker can construct two (or more) coins A and B in the bundle such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`. Neither A nor B qualifies as "non-ephemeral" per the set-comprehension filter, so the `while coin not in non_ephemeral_removals` loop in `get_root_removal()` alternates forever between A and B via `next(c for c in all_removals if c.name() == coin.parent_coin_info)`, never terminating.

This function is reachable from `TradeManager.coins_of_interest_farmed()`, which is invoked during normal wallet coin-state sync processing for any stored trade (created by `create_offer_for_ids` or accepted via `respond_to_offer`/`take_offer`): [3](#0-2) 

Since offers are exchanged out-of-band between counterparties and a wallet routinely calls `Offer.from_bytes()` on a counterparty-supplied offer (summarizing it, taking it, or later reconciling it during farm/sync events), a malicious counterparty can plant this cyclic parent-hash structure directly in the `CoinSpend` list without needing any valid signature or executable puzzle logic, since the loop never runs or validates any CLVM.

### Impact Explanation
Once a wallet stores a trade containing such a crafted offer and later observes any relevant coin state change, `coins_of_interest_farmed()` calls `offer.get_root_removal()` per addition, hanging the async task that handles coin-state updates. Because this runs under `WalletStateManager`'s sync/coin-state processing path, it can stall wallet transaction/sync processing (a spend/offer-triggered processing halt) for the victim wallet, a denial-of-service reachable purely from an untrusted offer file exchanged by an offer counterparty — no privileged or node-level access required.

### Likelihood Explanation
Likelihood is moderate-to-high for any wallet user who takes or otherwise loads offers from untrusted or semi-trusted counterparties (a routine, expected wallet workflow, e.g., via `take_offer`/`respond_to_offer` CLI/RPC). Constructing the cyclic `Coin` parent/name relationship requires only computing coin names (a simple hash of known/attacker-chosen puzzle hash/amount/parent fields) — no signature or successful puzzle execution is needed to reach the vulnerable loop.

### Recommendation
Add cycle detection (e.g., bound the walk by the number of removals, or maintain a `visited` set and raise a `ValueError`/`ValidationError` if a coin is revisited) in `get_root_removal()` before it is used by `get_primary_coins()`/`coins_of_interest_farmed()`. More generally, validate that an `Offer`'s coin-spend parent/child graph is acyclic as part of `Offer.from_bytes()`/`Offer.__init__` before any traversal method is exposed to wallet logic driven by external offer files.

### Proof of Concept
Conceptually:
1. Craft two `CoinSpend`s for coins A and B (arbitrary puzzle reveal/solution not required to execute correctly) where:
   - `A.coin.parent_coin_info == B.coin.name()`
   - `B.coin.parent_coin_info == A.coin.name()`
2. Include these coin spends, plus a `settlement_payment` (`OFFER_MOD`) addition that traces back to A, in an `Offer`'s underlying `WalletSpendBundle` so `Offer.from_bytes()` parses successfully.
3. Serialize/encode this as a normal offer file (`to_bech32()`).
4. Have a victim wallet take or otherwise process the offer such that `TradeManager.coins_of_interest_farmed()` (or any other caller of `Offer.get_primary_coins()`/`get_root_removal()`) is later invoked for that trade — the wallet's coin-state handling task hangs indefinitely in the `while coin not in non_ephemeral_removals` loop in `chia/wallet/trading/offer.py`.

```python
    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
