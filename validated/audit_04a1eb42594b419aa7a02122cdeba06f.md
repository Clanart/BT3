### Title
Repository refresh silently repoints the local git remote/GitHub association using an owner+name lookup instead of a stable repository ID, enabling repo-squatting to hijack push/pull destinations - (File: app/src/lib/stores/app-store.ts, app/src/lib/stores/updates/update-remote-url.ts, app/src/lib/stores/repositories-store.ts)

### Summary
The reported swETH bug is about a trusted-but-unvalidated input (`_preRewardETHReserves`) being used to silently overwrite critical bookkeeping (`ethReserves`) with no check that the new value is actually consistent with the previous truth, corrupting all future computations. The closest Desktop analog is `repositoryWithRefreshedGitHubRepository()` in [1](#0-0) , which re-resolves a tracked repository's GitHub identity purely by `owner/name` string lookup via `api.fetchRepository(owner, name)` [2](#0-1)  and then feeds whatever comes back into `updateRemoteUrl()`, which will silently rewrite the local git remote URL [3](#0-2) .

### Finding Description
`repositoryWithRefreshedGitHubRepository` derives `owner`/`name` from the current local remote via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` — a name-based GitHub API lookup, not a lookup by the GitHub-side immutable repository ID: [4](#0-3) 

The returned `apiRepo` is trusted and passed straight into `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`, which will overwrite the local remote's URL: [5](#0-4) 

The guard conditions in `updateRemoteUrl` (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) only compare structural URL components (hostname/owner/name) via `urlMatchesRemote`/`parseRemote` [6](#0-5) . None of them verify that the API object returned for `owner/name` is *the same repository* the user originally added — there is no comparison against a stable numeric repository ID.

The local persistence layer has the same weakness: `_upsertGitHubRepository` keys existing records by `[ownerID+name]` in the local database, not by the GitHub API `id` field: [7](#0-6) 

So if the `owner/name` combination that Desktop is tracking ceases to point at the original repository (e.g., the repository is deleted/renamed or the owning account is renamed/deleted and the name becomes available again) and a different, attacker-controlled repository is created at that same `owner/name`, subsequent background refreshes (`_fetch`, `_pull`, account-change refresh, etc., all of which route through `repositoryWithRefreshedGitHubRepository` / `withRefreshedGitHubRepository`) will:
1. Fetch the attacker's repository object from the API.
2. Treat it as a continuation of the previously tracked repository (same `ownerID+name` key).
3. Silently call `gitStore.setRemoteURL()` to repoint the user's local `origin` remote to the attacker's `clone_url`.

This mirrors the reported bug's broken invariant exactly: a value from an untrusted/attacker-influenceable source (here, "whatever the GitHub API returns for this owner/name string") is trusted to overwrite critical local state (the git remote target) with only superficial consistency checks, and no verification against the previously-known ground truth (a stable identifier).

### Impact Explanation
If exploited, this would cause the user's future `git push`/`git fetch`/`git pull` operations performed through Desktop to silently target a different, attacker-controlled repository at the same GitHub hostname/owner/name — this is "silent corruption of what the user commits or pushes" as defined in the in-scope impact list. In the push case this can result in exfiltration of a private repository's contents (the attacker's repo would receive the user's pushed commits/branches) and in the fetch/pull case it can result in the user unknowingly pulling attacker-crafted history/code into their working tree. No UI warning is shown to the user before the remote is repointed.

### Likelihood Explanation
Exploitation depends on the attacker being able to claim the exact `owner` and `name` combination that a victim's Desktop instance is already tracking (e.g., after the legitimate account/org or repo name becomes available — a known "repo-jacking"/"account-jacking" pattern that has been demonstrated against other tools that resolve dependencies or remotes by name rather than ID). This requires no local access, no admin rights, and no social engineering of the victim beyond them continuing to use Desktop normally (background fetches happen automatically). The likelihood is therefore plausible but conditioned on real-world timing/availability of the squatted owner/name, which is outside Desktop's control — this is a genuine reachable code path, not a hypothetical one, since `withRefreshedGitHubRepository` is invoked on ordinary fetch/pull/push flows.

### Recommendation
- Persist and check the GitHub API's immutable numeric repository `id` (and owner `id`) alongside `owner/name`, and require an ID match before treating an `owner/name`-fetched API repository as a continuation of a previously-tracked repository.
- In `updateRemoteUrl`, refuse to silently update the remote URL if the underlying repository ID differs from what was last recorded for this `GitHubRepository`; instead surface a prompt to the user before repointing the remote.
- In `_upsertGitHubRepository`/`upsertGitHubRepositoryFromMatch`, key repository identity lookups by API `id` in addition to `[ownerID+name]`, so a name being reclaimed by a different repository does not get conflated with the original tracked entity.

### Proof of Concept
1. User adds/clones `https://github.com/acme/widgets` in Desktop; Desktop stores a `GitHubRepository` row keyed by `[ownerID(acme), name(widgets)]` and sets `origin` to `https://github.com/acme/widgets.git`.
2. The `acme` organization is later renamed or deleted, and the `widgets` name at that path becomes available; an attacker registers `acme/widgets` (or an org of the same name) with their own repository content and clone URL.
3. On the victim's next Desktop-initiated fetch/pull/push, `_fetch`/`_pull`/`_push` calls `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository('acme', 'widgets')`, which now returns the attacker's repository object (same owner/name, different backing repo).
4. `updateRemoteUrl` compares `apiRepo.clone_url` against the stored `gitHubRepository.cloneURL` (`https://github.com/acme/widgets`) via `urlMatchesRemote`; since owner/name/hostname strings are unchanged, `remoteUrlUnchanged` is `true`, and if the attacker sets an identical-looking clone URL protocol, the local remote is left as-is or, if the attacker's `clone_url` differs textually (e.g., different casing or a redirect that GitHub returns for the new object), `setRemoteURL` fires and the local `origin` is rewritten to the value returned by the API for the squatted repo — all without any explicit repository-identity check or user confirmation.

Note: I was not able to fully trace every internal call site guarding `withRefreshedGitHubRepository` within the truncated view of `app-store.ts`, so there may be additional guards elsewhere in that very large file that partially mitigate this; this could not be fully verified due to the size of the file and index truncation limits. I recommend a full review of `app-store.ts`'s `withRefreshedGitHubRepository` usage in a Devin session with full file access to confirm there is no additional ID-based check elsewhere in the codebase.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
