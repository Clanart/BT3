Let me look at the FROST signing internals for the strongest analog — nonce/preprocess reuse which leaks key shares (the real "exposure of sensitive information" shape in this codebase).### Title
Blame proof returned before PoP verification lets a malicious participant reveal a victim's ECDH key and decrypt their DKG share - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` and immediately returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` if the decrypted bytes are not a canonical scalar. The `blame` is an `EncryptionKeyProof` containing `proof.key = enc_key_recipient * msg.key` — the full ECDH shared key — yet the per-message proof-of-possession (`msg.pop`) has only been *queued* into the `BatchVerifier` at that point and is not verified until `batch.verify_with_vartime_blame()` runs after the loop. The PoP exists precisely to stop an attacker who reuses another participant's per-message key `X` from causing the victim to emit a blame argument that reveals `b·X` (documented in `EncryptedMessage`'s own comments). The early return bypasses that protection.

`Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:469-500) only *queues* the PoP for batch verification; it unconditionally computes `key = ecdh(&self.enc_key, msg.key)` and returns `EncryptionKeyProof { key, dleq }`. When `C::F::from_repr` fails, the function returns early — the queued PoP verification never runs — and the caller (processor/src/key_gen.rs:416-425) serializes and publishes `blame` via `ProcessorMessage::InvalidShare`.

An attacker Eve participating in the DKG copies the `key` field `X` from victim Alice's `EncryptedMessage` addressed to Bob (shares are relayed through the coordinator, and the blame design explicitly assumes third parties can later inspect the message — see spec/cryptography/Distributed Key Generation.md:19-35). Eve constructs her own `EncryptedMessage` to Bob with `key = X`, an arbitrary/invalid `pop`, and random `msg` bytes. ChaCha20 decryption of random bytes yields a pseudorandom 32-byte scalar encoding which is non-canonical with high probability (~15/16 for 252-bit Ristretto scalars). Bob's `calculate_share` returns early with `blame = EncryptionKeyProof { key: b·X, dleq }`, where `b` is Bob's private encryption key. The blame is published; Eve reads `b·X` from it, derives the ChaCha20 key via `cipher(context, b·X)`, and decrypts Alice's `SecretShare` to Bob — recovering `f_Alice(Bob)` without ever producing a valid PoP.

The `pop_challenge` binding (encryption.rs:374-379) that was designed to prevent this key-reuse attack is only enforced in `decrypt_with_proof` (blame resolution) and in the batch path — both of which run too late or never for this path. `blame_internal` will still correctly identify Eve as faulty (`DecryptionError::InvalidSignature` → `sender`), but the sensitive ECDH key has already been disclosed to all observers.

### Impact Explanation
Exposure of sensitive information to an unauthorized actor: Eve obtains Alice's secret share to Bob, `f_Alice(Bob)`. For `t = 2` parameters, Eve additionally knows `f_Alice(Eve)` (the share Alice legitimately sent her), so two points of Alice's degree-1 polynomial fully recover Alice's polynomial — her secret contribution and her share for every participant. This undermines the confidentiality guarantees the PedPoP ECDH + PoP construction was built to provide and weakens the DKG to partial key-share disclosure attributable to a single unprivileged malicious participant sending public input bytes.

### Likelihood Explanation
Any DKG participant can execute this with bytes they fully control: they choose `msg` arbitrarily, so they retry the construction offline until a non-canonical decryption is expected, then submit once. No collusion, no special position, and the trigger probability per attempt is ~15/16 with a single submission (and effectively 1 by grinding the ciphertext offline, since the plaintext is unknown but its canonicity distribution is not). The only requirement is observing the victim's `key` field, which the protocol's own blame model assumes is visible.

### Recommendation
Do not return a blame proof before the PoP for that message has been verified. In `calculate_share`, either:
- verify `msg.pop` inline (non-batched) before attempting `from_repr` and before releasing the `EncryptionKeyProof`, or
- defer emission of any `EncryptionKeyProof` until after `batch.verify_with_vartime_blame()` confirms the `BatchId::Decryption(l)` statement, attaching `blame: None` for non-canonical plaintext when the PoP is invalid/unverified.

### Proof of Concept
1. Instantiate PedPoP with `ThresholdParams::new(2, 3, i)`; Eve is participant 3, Bob participant 2, Alice participant 1. Complete round 1 normally (`generate_secret_shares` by all parties).
2. Eve obtains Alice's `EncryptedMessage<Ristretto, SecretShare<F>>` for Bob and reads its `key` field `X`.
3. Eve builds `EncryptedMessage { key: X, pop: <arbitrary SchnorrSignature>, msg: SecretShare([random 32 bytes]) }` for her share to Bob.
4. Bob runs `machine.calculate_share(rng, shares)` with `shares[Eve] = evil_msg`. `Encryption::decrypt` computes `key = b·X` and returns the `EncryptionKeyProof`; `F::from_repr` on the decrypted bytes returns `None`; `calculate_share` returns `PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }` before the batch (and thus the PoP) is ever verified.
5. Eve takes `proof.key = b·X`, recomputes `cipher::<Ristretto>(context, &proof.key)`, and applies the keystream to Alice's `msg` ciphertext, recovering Alice's `SecretShare` `f_Alice(Bob)`. Together with the legitimate `f_Alice(Eve)`, Eve interpolates Alice's full degree-1 polynomial.
