### Title
Unescaped `Any.type_url` printed raw into `TextFormat` debug output enables terminal-escape-sequence injection - (File: `src/google/protobuf/text_format.cc`)

### Summary
The BusyBox CVE-2017-16544 invariant is: an attacker-controlled string (a filename) is written to a terminal by a "helpful" feature (autocomplete) without escaping ANSI/control-character sequences, letting the attacker's bytes be interpreted by the terminal emulator instead of being displayed as literal text. `TextFormat::Printer::PrintAny` in `src/google/protobuf/text_format.cc` has the same missing-escape pattern: it writes the `type_url` field of a `google.protobuf.Any` message directly into the generated debug/text output with `generator->PrintString(type_url)`, bypassing the control-character escaping (`HardenedPrintString`/`CEscape`) that every other string/bytes field goes through.

### Finding Description
When `expand_any_` is enabled (the default for `Message::DebugString()`/`Utf8DebugString()` on messages containing an `Any` field), `TextFormat::Printer::PrintMessage` calls `PrintAny`: [1](#0-0) 

Inside `PrintAny`, the `type_url` value — extracted directly from the attacker-supplied `Any.type_url` string field via `reflection->GetString(message, type_url_field)` — is written unescaped: [2](#0-1) 

Contrast this with the normal string-field path, where every printable/control-character check runs through `HardenedPrintString`, which explicitly escapes any byte that is `!absl::ascii_isprint(ch)` (this includes ESC `0x1B` and other C0 control bytes used to build ANSI escape sequences): [3](#0-2) [4](#0-3) 

Similarly, unknown length-delimited fields and normal strings/bytes are passed through `absl::CEscape` before being emitted: [5](#0-4) 

The `type_url` field is fully attacker-controlled: it is a plain `string` field inside a message that a client can populate with any UTF-8/byte content when submitting a binary-encoded `Any` through a normal, public `ParseFrom*` API. Protobuf's wire format and `Any`'s field validation do not restrict `type_url` to a "safe" character set — only `ParseAnyTypeUrl` splits on the last `/` to extract url-prefix/full-type-name, but does not reject control characters. There is no invariant enforced that `type_url` is printable-only, and unlike every other field-printing path, this one specifically skips the escaping step that exists exactly to prevent unescaped control bytes from reaching the generated debug text.

The consuming-application exposure assumption: this defect is only exploitable when application code calls `Message::DebugString()` (or `Utf8DebugString()`/`ShortDebugString()`) on a message containing an `Any` field with attacker-controlled contents and then writes/logs that string to an interactive terminal, a terminal-emulating log viewer, or any consumer that interprets ANSI/VT100 escape sequences (this is a very common debug/logging pattern for protobuf messages, e.g. `LOG(INFO) << msg.DebugString()`, `google::protobuf::Message::PrintDebugString()` — the latter does `printf("%s", DebugString().c_str())` directly to stdout). [6](#0-5) 

### Impact Explanation
If a downstream application prints `DebugString()`/`Utf8DebugString()` output of a message containing an attacker-supplied `Any` to a terminal (a routine debugging/logging practice), the unescaped `type_url` bytes are emitted verbatim. An attacker who controls the serialized `Any.type_url` string can embed ANSI/VT100 escape sequences (e.g., cursor movement, screen clearing, OSC sequences that some terminal emulators interpret as commands, title-bar/clipboard injection, or sequences that in vulnerable terminal emulators can lead to further compromise) directly into that output. This mirrors the BusyBox impact category (terminal escape sequence injection potentially leading to arbitrary file writes/code execution depending on the terminal emulator), scoped here to Protobuf's debug-printing surface rather than a shell autocomplete feature. Severity is bounded by the fact that impact depends on a vulnerable/permissive terminal emulator and on the operator viewing the output live; it is not itself remote code execution in Protobuf.

### Likelihood Explanation
Likelihood is credible but not certain: it requires (1) an application accepting an untrusted binary `Any` message, (2) that message being rendered via `TextFormat`'s expand-any debug path (default behavior of `DebugString()`), and (3) the resulting string being echoed to a terminal or terminal-emulating consumer. All three conditions are common in real-world logging/debugging setups, especially services that log request/response protos for troubleshooting. The bug is a straightforward oversight (missing call to `HardenedPrintString`/`CEscape` for `type_url`), consistent with how easily the BusyBox filename-escaping gap went unnoticed for years.

### Recommendation
In `TextFormat::Printer::PrintAny` (`src/google/protobuf/text_format.cc`), route the `type_url` value through the same escaping used for all other strings before printing, e.g. call `TextFormat::Printer::HardenedPrintString(type_url, generator)` (or at minimum `absl::CEscape`) instead of `generator->PrintString(type_url)`. Apply the same treatment anywhere else `type_url` is interpolated into human-readable output without escaping (e.g., the `ABSL_LOG(WARNING)` calls in the same function, and equivalent `printAny` implementations in Java/Python/upb if they exhibit the same gap).

bool DefinitelyNeedsEscape(unsigned char ch) {
  if (ch >= 0x80) {
    return false;  // High byte; no escapes necessary if UTF-8 is valid.
  }

  if (!absl::ascii_isprint(ch)) {
    return true;  // Unprintable characters need escape.
  }

  switch (ch) {
    case '\"':
    case '\'':
    case '\\':
      // These characters need escapes despite being printable.
      return true;
  }

  return false;
}

void TextFormat::Printer::HardenedPrintString(
    absl::string_view src, TextFormat::BaseTextGenerator* generator) {
  // Print as UTF-8, while guarding against any invalid UTF-8 in the string
  // field.
  //
  // If in the future we have a guaranteed invariant that invalid UTF-8 will
  // never be present, we could avoid the UTF-8 check here.

  generator->PrintLiteral("\"");
  while (!src.empty()) {
    size_t n = SkipPassthroughBytes(src);
    if (n != 0) {
      generator->PrintString(src.substr(0, n));
      src.remove_prefix(n);
      if (src.empty()) break;
    }

    // If repeated calls to CEscape() and PrintString() are expensive, we could
    // consider batching them, at the cost of some complexity.
    generator->PrintString(absl::CEscape(src.substr(0, 1)));
    src.remove_prefix(1);
  }
  generator->PrintLiteral("\"");
}
