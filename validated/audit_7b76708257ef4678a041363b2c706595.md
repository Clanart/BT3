### Title
Missing Minimum Output Validation in ArbWomUp3 WOM-to-mWom Swap (`_deposit`) - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.incentiveDeposit()` is a fully public, unprivileged entry point that lets any user convert WOM into mWom/vlMGP rewards. When `_mode == 2`, the internal `_deposit()` function routes half of the deposited WOM through `SmartWomConvert.convert()` with a hardcoded `_minRec` of `0`, completely disabling the slippage/minimum-output protection that `SmartWomConvert` otherwise provides.

### Finding Description
`incentiveDeposit()` accepts a user-supplied `_convertRatio` and forwards it to `_deposit()`: [1](#0-0) 

For `_mode == 2`, `_deposit()` swaps half of the WOM amount through the wom/mWom pool via `SmartWomConvert.convert()`, passing `0` as the minimum-received parameter: [2](#0-1) 

Inside `SmartWomConvert._convertFor()`, the received `_minRec` (here `0`) is used both for the guard check and to bound the AMM swap call: [3](#0-2) 

Because `_minRec` is `0`, the check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` can never fail, and the underlying `router.swapExactTokensForTokens(... , 0, ...)` call at line 195 also has zero minimum-out protection. The only external, price-dependent output validation `SmartWomConvert` offers is thus completely bypassed by its caller, `ArbWomUp3`, even though `incentiveDeposit()`/`_deposit()` are reachable by any ordinary wallet and irreversibly commit the caller's WOM to this swap. This mirrors the HODL `_buyHodl()` pattern: a price-sensitive conversion executes without allowing the user to bound their acceptable output, so the amount of mWom actually received depends entirely on the pool state at the moment of execution, which any other actor (including a searcher) can manipulate immediately before the transaction.

### Impact Explanation
An attacker (or generalized MEV searcher) observing a pending `incentiveDeposit(..., _mode = 2)` transaction in the mempool can sandwich it: push the wom/mWom pool price unfavorably immediately before the victim's transaction, let the zero-slippage swap execute at the manipulated price, and revert the price back afterward, capturing the difference. This is a direct extraction of value from an unprivileged user's deposited WOM with no way for the user to prevent or bound the loss, i.e., a direct theft of user funds via price manipulation enabled by the missing minimum-output check.

### Likelihood Explanation
`incentiveDeposit()` is a standard public function with no special role requirements; `_mode == 2` is a normal, documented code path (used to split WOM between direct mWom deposit and “smart convert” swap-and-lock). Any wallet interacting with the contract in this mode is exposed, and sandwiching public mempool transactions against AMM pools is a well-established, low-cost attack that requires no privileged access.

### Recommendation
Thread a user-supplied `_minRec` (or equivalent minimum-output) parameter from `incentiveDeposit()` through `_deposit()` into the `SmartWomConvert.convert()` call instead of hardcoding `0`, so users can set slippage bounds for the WOM-to-mWom conversion, consistent with how `SmartWomConvert.convert`/`convertFor` already support a genuine `_minRec` argument.

### Proof of Concept
1. User calls `incentiveDeposit(amount, convertRatio, false, 2)`.
2. `_deposit()` computes `toSwap = amount - amount/2` and calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` [4](#0-3) .
3. In `SmartWomConvert._convertFor`, `buybackAmount` (derived from `_convertRatio`) is swapped via `router.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` [5](#0-4) .
4. A searcher front-runs with a large wom→mWom swap to move the price, lets the victim's zero-minOut swap execute at the worse rate, then back-runs to restore the pool, pocketing the victim's slippage as profit — with the on-chain `MinRecNotMatch` check never able to trigger because `_minRec == 0`.
