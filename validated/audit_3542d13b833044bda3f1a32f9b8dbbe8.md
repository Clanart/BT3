### Title
Working-directory symlink lets an untrusted repository make Desktop reveal/open files outside the repo when using "Reveal in Finder/Explorer" or "Open with Default Program" - (File: app/src/lib/app-shell.ts)

### Summary
Desktop's file-list actions (Reveal in Finder/Explorer, Open with Default Program, Open in External Editor) build the on-disk path by simply joining the repository root with the path reported by `git status`/`git diff`, without ever confirming the resolved path stays inside the repository (`resolveWithin` is not used here). If a cloned/fetched repository contains a symlink whose target points outside the repository (e.g. to a sensitive file or directory on the victim's machine), git will happily track and report it as a normal working-directory entry, and Desktop's UI actions will follow that symlink and hand the *real, outside-the-repo* path to the OS shell (`shell.showItemInFolder`, `shell.openExternal`, or an external editor). This mirrors the yAxis `removeToken` bug class: a state-changing/attacker-influenced operation (adding a tracked path) has no boundary check before being trusted downstream, breaking an implicit invariant ("a repo-relative file action always stays inside the repo").

### Finding Description
`revealInFileManager` computes the path to reveal purely with `Path.join`: [1](#0-0) 

This function is called from multiple UI surfaces (Changes list, commit history, PR file list, conflict resolution) with `file.path` taken directly from `git status --porcelain` / `git diff` parsing: [2](#0-1) [3](#0-2) [4](#0-3) 

The "Open with Default Program" path does the same, forwarding the joined path to `shell.openExternal('file://' + fullPath)`: [5](#0-4) [6](#0-5) 

Git itself does not restrict what a symlink *inside* the repo may point to — only the tracked path name is constrained (no `..` components), not the link target. A malicious/compromised remote can therefore commit a symlink such as `notes.txt -> /home/victim/.ssh/id_rsa` (or `..\..\..\AppData\Roaming\secret.cfg` on Windows). After the victim clones/fetches and checks out that branch, the symlink shows up as a normal tracked/changed file in the Changes list or in a PR's "Files changed" view (`pull-request-files-changed.tsx`, populated when reviewing an untrusted fork's PR — see `openPullRequestFromUrl`/`_checkoutPullRequest` in `dispatcher.ts`). When the victim right-clicks and chooses "Reveal in Finder"/"Show in Explorer" or "Open with Default Program", the OS follows the symlink and reveals/opens the real target file, which lives outside the repository.

This is the same missing-invariant pattern as `removeToken`: Desktop already recognizes this exact class of risk and has hardened it elsewhere — e.g. `resolveWithin` is used specifically to stop the deep-link `filepath` action from escaping the repo root: [7](#0-6) 

and `resolveWithin`'s own tests explicitly document and defend against the "symlink used to traverse outside of the root" scenario: [8](#0-7) 

But that same `resolveWithin` guard is **not** applied to the `revealInFileManager` / `openFile` / external-editor code paths that consume `file.path` values sourced from working-directory status or PR diffs, leaving this analogous route unguarded.

### Impact Explanation
An attacker who controls a remote/cloned repository or a pull request from a fork can cause Desktop to reveal or open a file located anywhere on the victim's filesystem that the OS user account can read (SSH keys, cloud credential files, browser profile data, etc.), by tricking the victim into using ordinary, expected context-menu actions (Reveal in Finder, Open with Default Program) on a file in the Changes list or in a reviewed PR. This is a read-outside-the-repo primitive driven purely by repository content the attacker controls, matching the report's "no safety check on a critical path-deriving operation" class (the `removeToken` analog). It does not require local/physical access, admin rights, or prior malware — only that the victim clone/fetch the repo or open a PR from a fork and interact with a listed file, which is normal Desktop usage.

### Likelihood Explanation
Moderate-to-high. Creating a tracked symlink pointing outside the repository is trivial (`ln -s /outside/target link-name && git add -A && git commit`), and git and GitHub Desktop both track/display it without warning. Reviewing PR diffs from forks and clicking file actions is a normal Desktop workflow, so the victim does not need to be tricked into any unnatural steps — just to use the feature as intended on a file supplied by an untrusted repository/PR.

### Recommendation
Route every file path derived from repository status/diff/PR data through `resolveWithin(repository.path, path)` (the same helper already used for the deep-link `filepath` action) before calling `shell.showItemInFolder`, `shell.showFolderContents`, `shell.openExternal`/`openFile`, or launching an external editor. Reject (and surface a clear error for) any path whose resolved, symlink-followed location falls outside the repository root, consistent with the existing `resolveWithin` symlink test coverage.

### Proof of Concept
1. On a machine controlled by the attacker (or as a malicious PR author), create a repository:
   ```
   git init evil-repo && cd evil-repo
   ln -s "$HOME/.ssh/id_rsa" leak.txt   # or a Windows UNC/relative escape on Windows
   git add -A && git commit -m "add notes"
   ```
2. Victim clones this repo (or opens a PR built from a fork containing this commit) in GitHub Desktop.
3. In the Changes list (or PR "Files changed" view), the victim right-clicks `leak.txt` and selects "Reveal in Finder" (calls `revealInFileManager` → `Path.join(repository.path, 'leak.txt')` → `shell.showItemInFolder`) or "Open with Default Program" (calls `openFile` → `shell.openExternal('file://' + fullPath)`).
4. Because `leak.txt` is a symlink to `~/.ssh/id_rsa`, the OS resolves and opens/reveals the victim's real SSH private key file instead of anything inside `evil-repo`, since no `resolveWithin`-style containment check was performed on the path before invoking the shell.

```typescript
/**

 * @param repository The currently active repository instance
 * @param path The path of the file relative to the root of the repository

export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
```

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
