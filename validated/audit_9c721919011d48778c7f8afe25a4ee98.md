### Title
Unbound `customMessage` digest in the `addr` precompile's `associate()` allows cross-context signature replay to force account association and involuntary balance/stake migration - (File: `precompiles/addr/addr.go`)

### Summary
The Keycloak advisory (CVE-2023-0264) describes an authentication flow that correctly verifies a cryptographic artifact but fails to bind it to the specific session/action it was intended for, letting an attacker replay a piece of data captured from a victim to complete an authentication action on the victim's behalf. Sei-chain's `addr` precompile (`0x1004`) has the same bug class: its `associate` transaction method recovers a public key from an attacker-supplied `(v, r, s, customMessage)` tuple but never binds the signed digest to Sei, to the "associate" action, or to any nonce/chain — so any valid ECDSA signature the victim produced over a known 32-byte digest for a completely unrelated purpose can be replayed on Sei to force-associate the victim's addresses and trigger balance migration, without the victim ever intending to associate on Sei at all.

### Finding Description
`PrecompileExecutor.associate` in `precompiles/addr/addr.go` takes attacker-supplied `v`, `r`, `s`, and a free-form `customMessage` string, computes `customMessageHash := crypto.Keccak256Hash([]byte(customMessage))`, and passes that digest straight into `helpers.GetAddresses`, which calls `crypto.Ecrecover` to recover the pubkey: [1](#0-0) 

Because `customMessage` is passed through as raw bytes (Go's `[]byte(string)` conversion preserves the exact byte sequence, with no UTF‑8 validation), an attacker who controls the transaction can supply as `customMessage` the exact preimage bytes of *any* 32‑byte digest a victim has ever signed with `ecrecover`-compatible ECDSA for a totally different purpose (a `personal_sign`/EIP‑191 login message for another dApp, an EIP‑712 typed message, or even an EIP‑7702 `SetCodeAuthorization` for a different chain whose RLP preimage is public). `keccak256(customMessage)` will reproduce that exact digest, so `Ecrecover` succeeds and yields the victim's real public key — with no chain ID, nonce, or action-type binding at all. [2](#0-1) 

Sei-chain's own codebase explicitly documents this exact bug class as a real, previously-recognized risk for the closely related EIP‑7702 authorization path, and added mitigating checks (chain ID match, nonce match, code check, already-associated check) specifically to prevent it there: [3](#0-2) 

No equivalent mitigations exist for the `associate()` precompile path. The recovered `evmAddr`/`seiAddr`/`pubkey` are passed straight to `associateAddresses`, which only checks that the Sei address isn't already associated, then calls `AssociateAddresses`, which unconditionally performs `MigrateBalance` — moving all spendable coins and wei balance from the EVM-cast Sei address to the native Sei address, and removing the cast account if it has no locked coins: [4](#0-3) 

### Impact Explanation
This lets any transaction sender replay a signature captured from a victim in an unrelated context (another dApp's login flow, another chain's signed message/authorization, etc.) to force an association action on Sei that the victim never intended to authorize for this chain. Consequences reachable by an unprivileged caller:
- Forced, involuntary migration of the victim's funds between their own cast (`sdk.AccAddress(evmAddr[:])`) and native Sei addresses, at a time and in a manner the attacker chooses, not the victim.
- Potential orphaning of staking/distribution state tied to the cast address, exactly as sei-chain's own code comments warn for the analogous EIP‑7702 case ("migrating their direct-cast balance and orphaning staking/distribution state").
- Removal of the cast account (`RemoveAccount`) once its locked coins are zero, discarding account state (sequence/pubkey) the victim may still have been relying on for that address.
- Because the association is permanent (checked via `GetEVMAddress` "already associated"), this action cannot be undone by the victim once triggered by the attacker.

This matches the CWE-287/CWE-345 class from the advisory: authentication data that is cryptographically valid but not bound to the specific action/session it is being used for, enabling unauthorized cross-context replay against another party's identity/state.

### Likelihood Explanation
Exploitability requires only that an attacker observe (a) a signature `(v, r, s)` and (b) the exact byte preimage of the digest it signed, both of which are routinely public: EIP‑7702 authorizations broadcast in mempools/blocks on other chains, `personal_sign`/EIP‑712 signatures shared with third-party services, or any other ECDSA signature over a disclosed 32-byte hash. No special privilege is needed — the caller just submits a normal EVM transaction to the `addr` precompile. This is realistically reachable by any public-RPC client or contract deployer.

### Recommendation
Bind the digest signed for Sei's `associate()` to a chain- and action-specific domain before hashing, e.g. require `customMessage` to embed (and the precompile to enforce) the Sei chain ID, a purpose tag (e.g., `"sei-associate"`), and ideally a nonce/expiry, mirroring the checks already implemented in `AuthorityToPreAssociate` for the EIP‑7702 path (chain ID match, nonce/account-state checks, already-associated check). Reject `associate()` calls whose `customMessage` does not match the enforced domain-separated format instead of hashing arbitrary attacker-supplied bytes directly.

### Proof of Concept
1. Victim signs an unrelated message elsewhere (e.g., a `personal_sign` login challenge for a third-party dApp, or an EIP‑7702 `SetCodeAuthorization` for Ethereum mainnet) with their EOA key, producing signature `(v, r, s)` over digest `D = keccak256(preimageBytes)`; the signature and `preimageBytes` become observable to the attacker (mempool, dApp log, support ticket, etc.).
2. Attacker (any Sei account, no special privilege) submits an EVM transaction calling the `addr` precompile at `0x1004`, method `associate(v, r, s, customMessage)`, setting `customMessage = preimageBytes` (as a string preserving the exact bytes) and the harvested `v, r, s`.
3. `precompiles/addr/addr.go:associate` computes `customMessageHash = keccak256(customMessage) == D`, calls `helpers.GetAddresses`, which calls `Ecrecover(D, sig)` and recovers the victim's real pubkey/evmAddr/seiAddr.
4. `associateAddresses` finds the Sei address not yet associated and calls `AssociateAddresses`, which sets the address mapping and runs `MigrateBalance`, moving the victim's balance from the cast address to the native Sei address and removing the cast account — all without the victim submitting or approving any Sei-chain transaction.

func GetAddresses(V *big.Int, R *big.Int, S *big.Int, data common.Hash) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	pubkey, err := RecoverPubkey(data, R, S, V, true)
	if err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}

	return GetAddressesFromPubkeyBytes(pubkey)
}

func GetAddressesFromPubkeyBytes(pubkey []byte) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	evmAddr, err := PubkeyToEVMAddress(pubkey)
	if err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}
	seiPubkey := PubkeyBytesToSeiPubKey(pubkey)
	seiAddr := sdk.AccAddress(seiPubkey.Address())
	return evmAddr, seiAddr, &seiPubkey, nil
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
