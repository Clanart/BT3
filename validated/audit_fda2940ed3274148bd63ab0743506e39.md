### Title
Unfinalized `deposit_blockhash` Used as Kickoff-UTXO Seed Without Finality Check — Permanent Signature Invalidation on Bitcoin Reorg (`core/src/builder/transaction/sign.rs`, `core/src/verifier.rs`, `core/src/operator.rs`)

---

### Summary

`get_kickoff_utxos_to_sign()` deterministically selects which kickoff UTXOs each operator must sign for a given deposit, using `deposit_blockhash` as part of its seed. Every actor (aggregator, verifier, operator) independently fetches this blockhash via `get_blockhash_of_tx()` with no finality-depth guard. If a Bitcoin reorg occurs after the deposit signing ceremony completes but before the deposit block reaches `finality_depth` confirmations, the deposit transaction is re-mined in a different block with a different hash. The signatures already stored in the database were computed over the pre-reorg kickoff-UTXO set; the post-reorg blockhash selects a completely different set. Because `insert_deposit_data_if_not_exists` prevents re-processing the same deposit outpoint, the mismatch is permanent: the operator can never produce a valid kickoff for that deposit and cannot be reimbursed for any withdrawal it services.

---

The in-code comment on the consistency test confirms the invariant: *"This test should never fail, do not make changes to code that changes the result of `get_kickoff_utxos_to_sign`, as doing so will invalidate all past deposits."*

All four call `self.rpc.get_blockhash_of_tx(txid)`, which only requires the transaction to be confirmed in any block:

```rust
// crates/clementine-extended-rpc/src/client.rs:211-219
pub async fn get_blockhash_of_tx(&self, txid: &bitcoin::Txid) -> Result<bitcoin::BlockHash> {
    let raw_transaction_results = self.get_raw_transaction_info(txid, None).await?;
    let Some(blockhash) = raw_transaction_results.blockhash else {
        return Err(eyre::eyre!("Transaction not confirmed: {0}", txid).into());
    };
    Ok(blockhash)   // ← no confirmation-count check
}
```

`is_deposit_valid()` (`core/src/verifier.rs:541–731`) checks that the deposit is confirmed and at height ≥ `start_height`, but **never checks** `chain_tip_height - block_height + 1 >= finality_depth`.

**Signature storage is keyed by the pre-reorg kickoff indices.** After `deposit_finalize`, signatures are stored in the DB indexed by `(deposit_outpoint, operator_xonly_pk, round_idx, kickoff_idx)` where `kickoff_idx` was derived from the pre-reorg blockhash. A subsequent reorg changes the canonical blockhash, so `get_kickoff_utxos_to_sign(new_blockhash)` returns a disjoint set of indices. The stored signatures are now orphaned.

**Re-processing is blocked.** `insert_deposit_data_if_not_exists` (`core/src/verifier.rs:880–886`) prevents the deposit from being re-signed with the new blockhash, making the mismatch permanent.

---

### Impact Explanation

1. **Operator kickoff permanently broken.** The operator cannot construct a valid kickoff transaction for the affected deposit because the stored signatures cover the wrong kickoff-UTXO indices. Any withdrawal the operator has already paid out for this deposit cannot be reimbursed — a direct, unrecoverable loss of operator collateral/liquidity equal to the bridge amount.

2. **Normal withdrawal liveness broken.** The kickoff is the entry point for the entire payout/challenge/reimbursement chain. Without a valid kickoff, the operator cannot enter the challenge window, cannot assert, and cannot claim reimbursement. The deposit is effectively dead for the normal withdrawal path.

3. **User funds are not directly stolen** (the move-to-vault transaction is already on-chain and the N-of-N vault plus security-council path remain intact), but the bridge's liveness guarantee for that deposit is permanently violated and the operator suffers a material fund loss.

---

### Likelihood Explanation

Bitcoin reorgs of 1–2 blocks occur regularly on mainnet and are far more common on testnet/regtest. The default `finality_depth` is a configurable parameter (e.g., `DEFAULT_FINALITY_DEPTH`). Any deposit processed while fewer than `finality_depth` blocks have been built on top of it is vulnerable. Because `new_deposit` can be called immediately after a single confirmation (the only guard is `is_deposit_valid` which only checks `>= start_height`), the window is wide. An operator or user who calls `new_deposit` promptly after the deposit is mined — the expected production behavior — is exposed for the entire finality window.

---

### Recommendation

Before any actor uses `deposit_blockhash` as a seed, enforce that the deposit transaction has at least `finality_depth` confirmations. Add a helper analogous to `is_block_finalized` and call it inside `is_deposit_valid`:

```rust
// In is_deposit_valid(), after fetching block_height:
let current_tip = self.rpc.get_current_chain_height().await?;
if !self.config.protocol_paramset().is_block_finalized(block_height as u32, current_tip) {
    return Err(BridgeError::InvalidDeposit(format!(
        "Deposit block {} has not reached finality depth {} (tip {})",
        block_height, self.config.protocol_paramset().finality_depth, current_tip
    )));
}
```

This single guard, applied in `is_deposit_valid` (called by both `deposit_sign` and `deposit_finalize` on verifiers, and should also be added to the operator's `deposit_sign`), ensures that by the time any actor fetches and commits to `deposit_blockhash`, the block is deep enough that a reorg cannot change it.

---

### Proof of Concept

1. User sends deposit tx; it is mined in block B₁ (hash H₁) at height N.
2. Aggregator immediately calls `new_deposit` (only 1 confirmation). All actors call `get_blockhash_of_tx` → all receive H₁.
3. `get_kickoff_utxos_to_sign(H₁)` → indices `[i₁, i₂, …]`. Signatures are collected and stored in DB under those indices. Move-to-vault tx is signed and broadcast.
4. A natural 1-block reorg occurs. The deposit tx is re-mined in block B₂ (hash H₂ ≠ H₁) at the same height N.
5. Move-to-vault tx is still valid (it spends the deposit UTXO directly, not the blockhash) and lands on-chain. User's BTC is in the vault.
6. Operator later attempts a kickoff. It calls `get_blockhash_of_tx(deposit_txid)` → receives H₂. `get_kickoff_utxos_to_sign(H₂)` → indices `[j₁, j₂, …]` (different from `[i₁, i₂, …]`).
7. DB lookup for signatures at `(deposit_outpoint, op_pk, round_idx, j₁)` returns nothing (signatures are stored at `i₁`). Kickoff construction fails.
8. `insert_deposit_data_if_not_exists` blocks re-running `new_deposit` for the same outpoint. The deposit is permanently broken; the operator cannot be reimbursed. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

pub fn get_kickoff_utxos_to_sign(
    paramset: &'static ProtocolParamset,
    op_xonly_pk: XOnlyPublicKey,
    deposit_blockhash: BlockHash,
    deposit_outpoint: bitcoin::OutPoint,

        deposit_blockhash.to_byte_array().to_vec(),
        deposit_outpoint.txid.to_byte_array().to_vec(),

    ]

    let seed = bitcoin::hashes::sha256d::Hash::hash(&deposit_data).to_byte_array();
    let mut rng = ChaCha12Rng::from_seed(seed);

    let mut numbers: Vec<usize> = (0..paramset.num_kickoffs_per_round).collect();
    numbers.shuffle(&mut rng);

    numbers
