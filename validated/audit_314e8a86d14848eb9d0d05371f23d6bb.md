### Title
OP_RETURN data output excluded from fee/vsize calculation causes systematic fee underpayment - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes transaction weight/vbytes — and therefore the fee — using only `payments` and `change`, but the OP_RETURN output carrying `data` is pushed into `tx_outs` **before** the weight is measured and is never included in `calculate_weight_vbytes`. The signed transaction pays a fee computed for a smaller transaction than the one broadcast, so the effective feerate is always below the requested `fee_per_vbyte`, and can fall below the minimum relay feerate even though the `TooLowFee` check passed.

### Finding Description
The Balancer incident is a precision-loss/business-logic bug: the code computed a rate against one accounting view while the actual swap settled against a different (smaller) supply, letting the attacker profit from the discrepancy. The direct analog in Serai is a fee computed against a smaller transaction than the one actually signed and broadcast.

In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

1. The OP_RETURN output is appended to `tx_outs` at lines 194–202.
2. The weight/vbytes used for `needed_fee` is computed at line 204 via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds the dummy transaction **only from `payments`** (lines 85–93) — the OP_RETURN output is omitted.
3. The `TooLowFee` floor check at line 211 uses this same underestimated `vbytes`, so it validates the fee against a smaller size too.
4. The change path repeats the mistake: `fee_with_change = fee_per_vbyte * vbytes_with_change` at lines 225–234 again ignores the data output. The change amount is `input_sat - payment_sat - fee_with_change`, so the OP_RETURN's cost is silently deducted from the change output rather than priced into the fee. [1](#0-0) 

The actual broadcast transaction (lines 245–255) contains the OP_RETURN output, so its real vsize exceeds the one the fee was priced on. `fee()` (lines 138–141) confirms the paid fee equals `sum(inputs) - sum(outputs)` = exactly `needed_fee`/`fee_with_change`, i.e., the underestimated value. A caller-controlled `data` payload of up to 80 bytes (checked at line 171) inflates the real transaction by ~9–92 bytes (~92 non-witness bytes → up to ~92 extra vbytes of weight), which is a large relative feerate error for small transactions.

The upstream caller `Bitcoin::make_signable_transaction` passes `None` for data today, but `SignableTransaction::new` is the public wallet API for constructing the multisig's spends and explicitly supports caller-provided `data` (e.g., Serai `Shorthand` OP_RETURN transfers as in `tests/full-stack/src/tests/mint_and_burn.rs`).

### Impact Explanation
- The effective feerate is strictly lower than the requested `fee_per_vbyte`, by up to ~90 vbytes worth of fee on a small transaction — e.g., a 1-input/2-output P2TR tx (~140 vbytes) carrying an 80-byte OP_RETURN pays roughly 60% of the intended rate.
- If `fee_per_vbyte` is set to the minimum relay rate, the transaction passes the `TooLowFee` check yet broadcasts below `DEFAULT_MIN_RELAY_TX_FEE` sat/vbyte, so standard nodes won't relay it. For a threshold-wallet spend this means signed transactions that are silently non-relayable/stuck, requiring reconstruction — a liveness/fee-accounting failure on attacker-influenced data size.
- When change exists, the shortfall is absorbed by reducing the change output, so accounting (`needed_fee` vs `fee()`) still agrees while the delivered feerate is wrong — the discrepancy is invisible to `needed_fee()` callers.

### Likelihood Explanation
Any caller supplying `data` triggers it deterministically; the miscalculation is unconditional whenever `data.is_some()`. No adversarial math is required — it is a straight business-logic omission of an output from the size estimate. Severity is bounded by transaction-stuck/underpaid-fee impact rather than direct theft, so Medium.

### Recommendation
Include the data output in the weight estimate: build the vbyte calculation from the final `tx_outs` (or pass `payments` plus an optional OP_RETURN script built from `data`) in `calculate_weight_vbytes`, for both the no-change and `fee_with_change` computations. Alternatively compute the OP_RETURN output's serialized size and add it to the estimated vbytes before multiplying by `fee_per_vbyte`.

### Proof of Concept
Construct `SignableTransaction::new(inputs, &payments, change, Some(vec![0u8; 80]), fee_per_vbyte)`. The returned `needed_fee()` equals `fee_per_vbyte * vsize_of(tx_without_opreturn)`, while `tx.output` contains the extra ~92-byte OP_RETURN output; broadcasting the signed tx yields an effective feerate of `fee_per_vbyte * vsize_est / vsize_actual`. With `fee_per_vbyte` at the minimum relay rate and no change, `fee()` equals `needed_fee` yet `fee() / tx.vsize()` < min relay feerate, so the transaction is rejected by standard mempool policy despite passing `TooLowFee`.
