## Analysis: FSD-style precision/direction assumption violation in `pallet-hyper-fungible-token`

### Title
Stale precision assumption allows inflated cross-chain mint amount when asset decimals are mutated after token registration — (`modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The FSD bug is a formula that silently produces wrong output once an implicit precondition (`a` is non-negative) is violated by a value the formula's author did not defend against at the point of use. The local analog is `convert_to_balance`/`convert_to_erc20` in `pallet-hyper-fungible-token`, which assume `erc_decimals >= local_decimals` — a precondition that is checked once, at `register_token`/`update_token` time, but never re-verified at message-processing time, where `local_decimals` is re-fetched dynamically and can drift.

### Finding Description
`convert_to_balance` and `convert_to_erc20` compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`: [1](#0-0) 

This is only correct when `erc_decimals >= local_decimals`. That invariant is enforced solely inside `register_token` and `update_token`, using a *freshly fetched* `local_decimals` at admin-call time: [2](#0-1) 

But `Precisions::<T>` (the stored `erc_decimals`) is fixed at registration, while the local asset's `decimals()` is **not** stored — it's re-read live from `fungibles::metadata::Inspect` in both `on_accept` and `on_timeout`: [3](#0-2) [4](#0-3) 

If the local asset's decimals metadata increases after registration (via `pallet-assets`' standard `set_metadata`, which is callable by the asset's own `Owner`, not this pallet's `CreateOrigin`/governance), `local_decimals` can exceed `erc_decimals`. Since `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, the divisor in `convert_to_balance` becomes `10^0 = 1` instead of the correct downscaling factor. The incoming ERC20 `U256` amount is then interpreted almost verbatim as the local balance unit, minting/crediting `10^(local_decimals - erc_decimals)` times more tokens than the sender actually escrowed/burned on the source chain.

### Impact Explanation
This is a direct "wrong amount" / fund-inflation bug in the mint/transfer path of a bridge asset (`on_accept` mints or releases custody funds to `beneficiary`, `on_timeout` refunds the sender). An attacker who can influence or is themselves the owner of the local asset registered in `NativeAssets`/`Precisions` (a normal, non-privileged, non-admin actor relative to the bridge's `CreateOrigin`) can bump the asset's decimals metadata after registration, then trigger a cross-chain transfer that gets converted with the stale/broken scaling factor, minting an inflated amount to any beneficiary they choose. This falls squarely under "unauthorized transaction... wrong beneficiary or amount / fund loss."

### Likelihood Explanation
Requires only: (1) the bridged asset to be a `pallet-assets`-style asset whose metadata decimals are owner-mutable independently of this pallet's admin, and (2) that asset's owner (not the bridge's `CreateOrigin`) to change its decimals after `register_token`. No relayer, prover, or bridge-admin compromise is needed — the trust boundary crossed is purely "asset owner vs. bridge admin," which the pallet incorrectly conflates by checking the invariant only once and never re-validating it at conversion time.

### Recommendation
- Snapshot `local_decimals` at registration time into `Precisions`/a new storage item instead of re-deriving it live from mutable asset metadata, OR
- Re-validate `erc_decimals >= local_decimals` inside `convert_to_balance`/`convert_to_erc20` (or immediately before calling them in `on_accept`/`on_timeout`) and return a hard error (`ErcDecimalsBelowLocal`) rather than silently saturating the exponent to zero.

### Proof of Concept
1. Admin registers asset `X` with `local_decimals = 6` and `erc_decimals = 18` via `register_token` — passes the `ensure!(config.decimals >= local_decimals, ...)` check at that time.
2. Asset `X`'s owner (a regular, non-bridge-admin account) later calls `pallet-assets::set_metadata` to change `X`'s decimals to `18`.
3. A user on the EVM side sends `1` token (i.e., `1 * 10^18` in `message.amount`) via the registered `HyperFungibleToken` contract.
4. On `on_accept`, `decimals` is now re-fetched as `18` (not the original `6`), so `erc_decimals.saturating_sub(local_decimals) = 18 - 18 = 0`.
5. `convert_to_balance` divides by `10^0 = 1`, yielding a local balance of `10^18` instead of the intended `10^6` (i.e., `1` unit in 6-decimal terms) — a `10^12`x mint inflation credited to the beneficiary.

**Note:** I was unable to fully confirm in this session whether the concrete runtime wiring for `T::Assets` in `gargantua`/`nexus` grants asset-owner-level `set_metadata` access independent of `CreateOrigin` (iteration budget was exhausted before checking `parachain/runtimes/*/src/lib.rs` `pallet_assets::Config` binding). This is the one open verification step; if `set_metadata` in the deployed runtime is gated behind the same governance/admin origin as `CreateOrigin`, the severity of this analog is reduced to a governance-only footgun rather than an unprivileged-actor exploit.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
