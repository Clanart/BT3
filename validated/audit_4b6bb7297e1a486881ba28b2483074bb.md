### Title
SignableTransaction trusts `ReceivedOutput`'s declared value, so a misreported input amount produces an unbroadcastable transaction or misallocated change - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The original bug class is "assumed received amount ≠ actual received amount": the depositor credits itself `_amount` then tries to deposit `_amount`, reverting when a fee-on-transfer token delivered less. The Serai analog lives in `SignableTransaction::new`, which computes `input_sat`, the change output, and the Taproot `Prevouts::All` sighash commitment entirely from the `TxOut` values carried inside each `ReceivedOutput` — values that are attacker-influenceable bytes when a `ReceivedOutput` is deserialized via `ReceivedOutput::read` rather than produced by `Scanner::scan_transaction`.

### Finding Description
`Scanner::scan_transaction` builds `ReceivedOutput`s by cloning the real `TxOut` from an on-chain transaction, so its `output.value` is guaranteed to match consensus reality [1](#0-0) . However, `ReceivedOutput::read` deserializes `offset`, `TxOut`, and `OutPoint` from raw bytes with no consistency check against any chain state [2](#0-1) . `SignableTransaction::new` then sums `input.output.value` into `input_sat` and uses it for the sufficiency check and the change calculation [3](#0-2) . Finally, `TransactionSignMachine::sign` commits every signature to `Prevouts::All(&self.tx.prevouts)`, and BIP-341 commits to each prevout's amount — so any divergence between the declared `TxOut.value` and the real UTXO value invalidates every produced signature [4](#0-3) .

This mirrors the fee-on-transfer bug exactly: the code assumes the amount "received" equals the amount claimed. Where the Depositor reverts inside `gauge.deposit(_amount, 0)`, here the FROST ceremony completes and emits a fully-signed transaction that no node will accept, because the sighash-committed amounts don't match the actual prevouts.

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` bytes (e.g., an inflated or deflated `TxOut.value` paired with a real outpoint) causes the coordinator to construct and threshold-sign a transaction that is permanently unbroadcastable — the Schnorr signatures commit to fabricated prevout amounts. If the value is inflated, the change output can also claim funds that don't exist; if deflated, intended funds are left on the table and burned as excess fee. Each attempt wastes a full signing ceremony and can repeatedly stall treasury operations. This is a reachable-with-public-inputs impact on a signing path, not a test-only or documented-misuse issue: `ReceivedOutput::read` is part of the untrusted-input surface and performs no binding to on-chain truth.

### Likelihood Explanation
Reachability requires untrusted `ReceivedOutput` bytes reaching `SignableTransaction::new`. In the honest scanner pipeline outputs come from `scan_transaction`, but the type exposes a public `read`/`serialize` round-trip precisely so outputs can be transported between components — any hop that accepts externally supplied bytes (or a corrupted/attacker-written DB entry) is a trigger. The misreport needs no collusion, no valid key material, and no miner cooperation; any `u64` value can be encoded into the `TxOut`. Likelihood is moderate: it depends on an integrator path feeding deserialized outputs into the transaction builder without re-deriving them from the chain.

### Recommendation
Measure reality rather than trusting declared amounts, per the original report's own mitigation ("measure the asset change before and after"). Concretely: when constructing a `SignableTransaction`, verify each `ReceivedOutput`'s `TxOut` against the actual prevout fetched by outpoint (or carry the resolved value from the scanning consensus path only). At minimum, `SignableTransaction::new`/`multisig` should reject inputs whose `outpoint`-resolved value differs from the declared `output.value`, failing before any signing rather than producing an invalid transaction. Alternatively, note in `ReceivedOutput::read`'s contract that deserialized outputs are unauthenticated and must be re-validated against chain state before use.

### Proof of Concept
Conceptual, using the public API in `networks/bitcoin/src/wallet`:

```rust
// Take a legitimately scanned output for a real on-chain UTXO.
let real = scanner.scan_transaction(&funding_tx).remove(0);

// Serialize it, then corrupt the declared value upward
// (e.g., claim 10 BTC where the UTXO holds 1 BTC).
let mut bytes = real.serialize();
// offset is 32 bytes; TxOut value is the next 8 bytes (consensus-encoded)
bytes[32 .. 40].copy_from_slice(&1_000_000_000u64.to_le_bytes());
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The builder trusts the forged value.
let tx = SignableTransaction::new(
    vec![forged],
    &[(dest_script, 900_000_000)],
    Some(change_script),
    None,
    fee_rate,
).unwrap(); // passes NotEnoughFunds check with fictitious input_sat

// The FROST ceremony completes; each signature commits to
// Prevouts::All containing the fabricated amount.
let signed = sign(&keys, &tx);

// Broadcast fails: BIP-341 sighash commits to prevout amounts,
// so every taproot key-spend signature is invalid on-chain.
assert!(rpc.send_raw_transaction(&signed).await.is_err());
```

Same shape as `AMMToken.transferFrom` crediting less than `_amount`: the discrepancy between claimed and actual value is only discovered at the final spend step, after all prior logic succeeded.
