### Title
Stale diff-line-selection indices are replayed against a freshly regenerated diff, silently corrupting partial commits - (File: app/src/lib/stores/app-store.ts)

### Summary
GitHub Desktop tracks which lines of a modified file a user wants to commit using an index-based `DiffSelection` bitmap keyed on `hunk.unifiedDiffStart + lineIndex` [1](#0-0) . When the diff for the currently selected file is refreshed in the background (e.g. after a periodic status/diff poll), the code explicitly acknowledges that it does not fully revalidate whether previously "selected" indices still refer to the same logical lines — it only prunes indices that turned into context/disappeared, but keeps the rest of the stale selection bitmap intact [2](#0-1) . At commit time, `applyPatchToIndex` re-fetches a brand-new diff from disk and applies that same stale selection bitmap against the new hunk layout to build the patch that is staged and committed [3](#0-2) [4](#0-3) . This is structurally the same "incorrect calculation via cached/stale data" bug class as the Cover Protocol report, where a stale balance value was used for a later on-chain calculation instead of being revalidated.

### Finding Description
`DiffSelection` is a positional bitmap: it records inclusion/exclusion by absolute diff-line index, not by line content or a content hash. The comment in `updateChangesWorkingDirectoryDiff` states plainly:

> "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [5](#0-4) 

This means: if a hunk's shape shifts (lines added/removed above or around a previously selected line — e.g. via a `.gitattributes` clean/smudge filter, a `post-checkout`/`post-merge` hook shipped by the cloned repository, or the file being touched by another git operation) between the moment the user visually reviews/selects lines in the diff viewer and the moment they click "Commit", the index that used to mean "the deletion at line 42 that I excluded" can now point at a completely different line in the freshly re-generated diff.

The commit path (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`) does not re-render the diff to the user or re-confirm the selection before staging: it takes the cached `WorkingDirectoryFileChange.selection` from `repositoryStateCache` [6](#0-5)  and replays it against a brand-new diff fetched right before `git apply --cached` is invoked [7](#0-6) . `formatPatch` then walks the new hunks and decides inclusion purely by `file.selection.isSelected(absoluteIndex)` [8](#0-7)  — with no check that the line at that index is the same line the user actually looked at.

### Impact Explanation
This breaks the invariant "what the user visually selected to commit is what actually gets committed." A file whose diff shape changes between selection and commit-click (driven by content injected via a checkout/merge-triggered filter or hook in an attacker-authored repository) can cause Desktop to silently stage/commit lines the user never reviewed or intended to include, or to omit lines the user explicitly meant to commit. Because this happens transparently inside a normal "Commit" action, the user has no visual indication that the staged patch diverges from what was last rendered on screen — this is a silent corruption of what the user commits, which can lead to unintended disclosure of local-only content, reintroduction of previously excluded secrets/lines, or omission of intended fixes without any error being surfaced.

### Likelihood Explanation
The likelihood is limited by timing: the attacker-controlled repository content (filter/hook) needs to alter the working copy of the exact file the user has open for partial selection within the narrow window between diff render and clicking Commit — a race rather than a deterministic trigger. Desktop's periodic background status/diff refresh (`updateChangesWorkingDirectoryDiff`) widens this window somewhat since it re-fetches diffs even while the Changes tab sits idle, but reliable exploitation still depends on the user leaving a partial selection open while background/filter-driven writes occur. This is a real, code-acknowledged gap (the comment explicitly flags the missing revalidation) rather than a purely theoretical one, but it is not trivially reliable to trigger remotely.

### Recommendation
Replace the positional `unifiedDiffStart + index` selection scheme with a selection keyed on stable line identity (e.g. hash of line content plus surrounding context, or diffing the old and new hunk sets to remap indices) so that a refreshed diff cannot silently reinterpret previously selected indices as different lines. At minimum, `_commitIncludedChanges`/`applyPatchToIndex` should detect when the diff fetched at staging time differs from the diff the selection was computed against and abort/re-prompt the user to re-review their selection rather than silently applying a stale bitmap to new hunk data.

### Proof of Concept
Conceptual PoC (cannot be executed without live UI/timing control, so this documents the code path rather than a runnable exploit):
1. User opens a modified tracked file in the Changes view and manually deselects a specific deletion (e.g. index 42) using partial-line commit, leaving other lines selected. This state is cached in `WorkingDirectoryFileChange.selection` in `repositoryStateCache`.
2. Before the user clicks Commit, a `post-checkout`/`merge`/smudge-filter script defined in the (attacker-authored, cloned) repository rewrites the same file, inserting/removing lines above index 42, shifting hunk boundaries. Desktop's background diff refresh (`updateChangesWorkingDirectoryDiff`, `app/src/lib/stores/app-store.ts:3404-3497`) recomputes selectable lines but leaves the stale selection bitmap otherwise intact per the code comment at lines 3480-3485.
3. User clicks Commit. `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3696`) passes the stale-selection file object to `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`), which fetches a brand-new diff and calls `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`), applying `isSelected(absoluteIndex)` against the new hunk layout.
4. Because index 42 in the new diff now corresponds to a different physical line than what the user reviewed, the resulting patch/commit includes or excludes content the user never actually saw or approved. [2](#0-1) [3](#0-2) [9](#0-8)

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
