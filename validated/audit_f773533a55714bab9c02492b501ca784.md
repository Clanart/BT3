The strongest local analog to the "check transfer success / use safeTransferFrom" report is the Tron-specific `IntentGatewayV2` contract, which reverts to unchecked low-level `.call()` payouts on the escrow-release path instead of `SafeERC20.safeTransfer`, even though `SafeERC20` is imported and used for the *inbound* `safeTransferFrom` calls elsewhere in the same file.

### Title
Escrow marked settled on a false ERC20 `transfer()` return, permanently losing beneficiary funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron `IntentGatewayV2` pay out escrowed tokens with a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level `call` did not revert (`success`). They never decode/validate the ERC20 boolean return value. Any ERC20 that returns `false` instead of reverting on a failed transfer (fully spec-compliant behavior, e.g. blacklist/pause conditions or a purpose-built malicious token) will pass the `success` check while moving zero tokens, yet escrow accounting is decremented and the order is marked filled/refunded regardless.

### Finding Description
`withdraw()` decrements escrow and finalizes state unconditionally after the raw call "succeeds": [1](#0-0) 

The same unchecked pattern appears for the fee-token payout in the same function: [2](#0-1) 

And again in the governance dust-sweep handler: [3](#0-2) 

Contrast this with the inbound escrow path in the same contract, which correctly uses `SafeERC20.safeTransferFrom` (reverts on a `false` return): [4](#0-3) 

and with the non-Tron `IntentsBase._withdraw`, which uses `safeTransfer` for the equivalent payout: [5](#0-4) 

Because `token.call(...)` only reports whether the call reverted, not the ABI-decoded `bool` the ERC20 standard requires `transfer()` to return, a token that legitimately returns `false` (rather than reverting) on a failed transfer will satisfy `if (!success) revert TransferFailed();` while delivering no tokens. `withdraw()` then does `_orders[body.commitment][token] -= amount`, marks `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` as if settlement completed. There is no mechanism afterward to retry or reclaim the escrow — from the protocol's point of view the order is finalized and the tokens are gone.

### Impact Explanation
This directly matches "stealing or loss of funds" / "false state acceptance": escrowed input tokens are treated as delivered to the beneficiary (solver on `RedeemEscrow`, user on `RefundEscrow`/cancellation) when in fact no value moved. The escrow entry is destroyed (`_orders[...] -= amount`) and the order is finalized, so the funds cannot be recovered through any other code path — permanent loss for the intended beneficiary while the contract's internal state falsely records successful settlement.

### Likelihood Explanation
The order's input token (`order.inputs[i].token`) is fully attacker-controlled at `placeOrder()` time — any user can place an order denominated in an arbitrary ERC20, including one they author. A token that returns `false` on transfer to a specific address instead of reverting is a normal implementation choice (many real tokens do this for blacklisted/paused/frozen recipients), and is trivial to write intentionally. No relayer, prover, or admin collusion is required — the withdrawal/settlement path (`onAccept` → `withdraw`) is triggered by ordinary ISMP message delivery for a `RedeemEscrow`/`RefundEscrow` request that any user or solver can cause by normal use of the protocol.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`'s token loop, its fee-token payout, and the `SweepDust` branch of `onAccept()`) with `SafeERC20.safeTransfer`, consistent with the rest of the contract's inbound transfers and with the non-Tron `IntentsBase` implementation. `SafeERC20` correctly decodes and reverts on a `false` return value as well as on missing return data, closing the false-success gap.

### Proof of Concept
1. Deploy a minimal ERC20 whose `transfer(to, amount)` returns `false` (without reverting) whenever `to == <target beneficiary address>`, and `true` otherwise.
2. As an ordinary user, call `placeOrder()` on the Tron `IntentGatewayV2` with this token as `order.inputs[0].token`, escrowing `amount` tokens (uses `safeTransferFrom`, succeeds normally).
3. A solver fills the order cross-chain / same-chain such that the settlement flow dispatches a `RedeemEscrow` (or the order is cancelled, dispatching `RefundEscrow`) with `beneficiary` set to the crafted target address.
4. When `onAccept()` → `withdraw()` executes on the source chain holding escrow, `token.call(...transfer(beneficiary, amount)...)` returns `success = true` (call didn't revert) even though the token's internal logic returned `false` and moved no balance.
5. `_orders[commitment][token] -= amount` executes, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the contract now believes settlement is complete, but the beneficiary's token balance is unchanged and the escrowed tokens remain stuck/unaccounted for in the gateway with no remaining code path to claim them.
