## Title
Governance-Set Zero `Kip71GasTarget` Causes Division-by-Zero Panic in KIP-71 Base Fee Calculation - (File: params/kip71_config.go)

### Summary
The `Kip71GasTarget` governance parameter is missing a non-zero format check that its sibling parameter `Kip71BaseFeeDenominator` has. If ratified with a value of `0`, the parameter is later used as a divisor in `KIP71Config.NextMagmaBlockBaseFee`, causing a division-by-zero panic in Go's `math/big` package. This function is invoked during header verification and block assembly (base fee calculation) on every node processing blocks, causing a consensus-wide chain halt — the same bug class as the reported `AutoPoolFees` division-by-zero DoS, but here the unchecked-zero denominator is a governance parameter (`GasTarget`) instead of a computed local variable.

### Finding Description
`Kip71BaseFeeDenominator` explicitly rejects zero in its `FormatChecker`: [1](#0-0) 

But the analogous `Kip71GasTarget` parameter uses `noopFormatChecker`, which accepts any `uint64` value, including `0`: [2](#0-1) 

The header-governance vote/ratification path (`checkConsistency`) does not add any extra validation for `Kip71GasTarget` either — it falls into the bucket of parameters that only rely on the (no-op) format check: [3](#0-2) 

Once ratified through governance (via `governance_vote` RPC and header `Vote`/`Governance` fields), the value becomes effective and is fed directly into `NextMagmaBlockBaseFee` as the divisor: [4](#0-3) 

Note the asymmetry with `BaseFeeDenominator`, which does have an explicit zero-guard directly in this function: [5](#0-4) 

but `gasTarget` has no equivalent guard. When `parentGasUsed != gasTarget` (true for nearly every block once `gasTarget == 0`, since any nonzero gas usage triggers the "used more than target" branch), the code executes:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
Dividing by a `big.Int` set to `0` panics in Go's `math/big` implementation (`Div` calls into `z.abs.div` which panics with "division by zero"), unlike Solidity's `revert`.

### Impact Explanation
`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is called in block header verification (consensus-critical path) as well as in block assembly (`work/worker.go`) and gas price oracle logic (`node/cn/gasprice/gasprice.go`, `node/cn/gasprice/feehistory.go`). A panic in this function during header verification would crash every full node attempting to validate the very next Magma-enabled block after the malicious parameter takes effect, resulting in a full chain halt (all honest nodes crash uniformly) rather than a mere isolated transaction revert. This is more severe than the original `AutoPoolFees` bug (single transaction revert) because it affects block-level state transition and header verification network-wide.

### Likelihood Explanation
Reaching this requires a legitimate governance vote for `Kip71GasTarget = 0` to be cast and ratified. In `single` governance mode (Kaia Mainnet/Kairos default), only the `GoverningNode` can cast votes that get ratified; in `none` mode, any GC member's last vote in an epoch is ratified. Since `Kip71GasTarget` is explicitly listed as an in-scope, votable governance parameter and has no zero-rejection safeguard (unlike its sibling `Kip71BaseFeeDenominator`), a single errant or malicious vote from an authorized governance voter — with no additional safety net in `NewVoteData`, `VerifyVote`, or `checkConsistency` — is sufficient to brick the chain 1 epoch later when the parameter becomes effective.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) that rejects `0`, mirroring the existing check for `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should guard against `gasTarget == 0` the same way it already guards against `BaseFeeDenominator == 0`, to prevent any other code path (e.g. genesis misconfiguration, CLI-provided KIP71Config) from triggering the same panic.

### Proof of Concept
1. As the governing node (single mode), call `governance_vote("kip71.gastarget", 0)`.
2. Once the node becomes proposer, the vote is written to `header.Vote`; other validators' `VerifyVote` accepts it because `checkConsistency` performs no extra validation for `Kip71GasTarget` (`kaiax/gov/headergov/impl/header.go:214-220`) and `NewVoteData`'s format check is a no-op (`kaiax/gov/param.go:324-334`).
3. At the next epoch boundary, the vote is ratified into `header.Governance`, making `GasTarget = 0` effective starting the following epoch.
4. On the first block of that epoch with `parentHeaderGasUsed != 0` (virtually guaranteed), `NextMagmaBlockBaseFee` executes `x.Div(x, new(big.Int).SetUint64(0))`, panicking every node that verifies or builds that block, halting the chain.
