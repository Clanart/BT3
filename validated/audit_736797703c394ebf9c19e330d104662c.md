## Finding: In-place ERC pointer code upgrade with no interface-compatibility check between pointer artifact versions

### Summary
The reported bug class is: an upgrade implementation is deployed that is not a strict superset of the previous implementation's interface, so calls that used to work against a fixed address start reverting after the upgrade is applied, breaking downstream flows and potentially freezing/locking assets. The closest reachable analog in sei-chain is the CW↔ERC "pointer" contract upgrade path: `UpsertERCPointer` in `x/evm/keeper/pointer_upgrade.go` overwrites the bytecode at an existing pointer's fixed EVM address with a newer artifact's bytecode, with no verification that the new artifact preserves the function selectors (interface) or storage semantics of the version it replaces.

### Finding Description
`UpsertERCPointer` handles both first-time deployment and version-bump ("exists") cases for native/CW20/CW721/CW1155 pointer contracts: [1](#0-0) 

When a pointer already exists (`exists == true`), instead of using `evm.Create` to deploy a fresh contract at a new address, the keeper calls `evm.GetDeploymentCode(...)` with the **existing** contract address and then directly overwrites the on-chain bytecode at that same address via `k.SetCode(writeCtx, contractAddr, ret)`: [2](#0-1) 

This "upgrade in place" is triggered by any unprivileged caller through the permissionless pointer precompile methods (`AddCW20`/`AddNative`/`AddCW721`/`AddCW1155`) once the embedded chain artifact's `CurrentVersion` is bumped above the existing pointer's stored version — the only guard is a version-number comparison, not an interface/ABI compatibility check: [3](#0-2) 

The same pattern exists in `x/evm/keeper/msg_server.go`'s `RegisterPointer` handler for the CW-side pointers, which similarly only checks `existingVersion >= currentVersion` before migrating the pointer to new bytecode: [4](#0-3) 

Nowhere in this pipeline is there a check that the new `artifacts.GetBin(typ)` bytecode for a bumped version is a strict superset of the previous version's external function selectors (e.g., ERC20 `transfer`/`approve`/`transferFrom`/`balanceOf`) or storage layout. The pointer contract's compiled artifact is simply swapped in at the same address that other contracts, wallets, and integrations have already been calling and holding references/approvals against.

### Impact Explanation
Any external contract or user that has integrated with a pointer address (e.g., a DEX, lending market, or wallet holding an `IERC20(pointerAddr)` reference or an existing `approve` for `transferFrom`) can be broken the moment any unprivileged account triggers the version-bump upgrade path. If a newer pointer artifact ever drops, renames, or changes the selector/ABI encoding of a previously available entrypoint (the exact bug class described in the report — "V1.1 missing distribute"), every subsequent call to the old selector on that address reverts. Because the bytecode swap happens in place at a fixed, already-integrated address (not a new address that callers must discover), this can strand funds that are routed through the pointer (e.g., pending `transferFrom` flows, DEX settlement calls, automated claim/distribution bots depending on the old ABI) until a further migration restores the missing functions — matching the "blocked flow / rollback or additional deployment required" impact in the original report.

### Likelihood Explanation
This path is reachable by any transaction sender: the pointer precompile `Add*` methods and `MsgRegisterPointer` are permissionless and only gate on the pointer's stored version being behind `CurrentVersion`; they perform no interface-compatibility validation between the old and new embedded artifacts. Whether a concrete regression has ever shipped in a pointer artifact bump is not verifiable from the indexed code (the artifacts are embedded compiled `.bin`/`.abi` files, and only their packaged interface is visible here), so likelihood depends on rigor of manual review at each `bump_version` release rather than any code-level safeguard.

### Recommendation
Before allowing the in-place bytecode overwrite in `UpsertERCPointer` (and the analogous CW pointer `Migrate` path in `RegisterPointer`), verify that the new artifact's ABI is a strict superset of the previous version's external selectors, and/or run an automated fork test that exercises every previously-supported entrypoint against the freshly upgraded pointer address before the version bump is shipped, exactly as recommended in the referenced report for the `RewardsEngine` upgrade.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without modifying an artifact, which is out of scope here):
1. Register a CW20→ERC20 pointer for a CW20 token; an external contract records the pointer address and calls `approve`/`transferFrom` against it (standard ERC20 usage).
2. Chain artifact for `cw20` pointer type is bumped to a new `CurrentVersion` whose compiled bytecode (hypothetically) omits or renames a previously present selector (e.g., `transferFrom`).
3. Any unprivileged account calls the pointer precompile (`AddCW20`) or sends `MsgRegisterPointer` for that same CW20 address; since `existingVersion < currentVersion`, `UpsertERCPointer`/`Migrate` overwrites the bytecode at the same address: [5](#0-4) 
4. The external contract's subsequent `transferFrom` call to the now-upgraded pointer address reverts because the selector no longer exists, blocking settlement/claim flows that depend on that fixed address — with no code-level guard having prevented the incompatible swap.

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
