### Title
Gasless swap `deadline` is only advisory in the mempool and is never enforced on-chain, allowing a stale swap to execute at an exchange rate/gas price the user never agreed to - (File: `kaiax/gasless/impl/tx_pool.go`)

### Summary
The gasless module lets a user submit a `swapForGas` transaction carrying a `deadline` parameter that is supposed to bound how long the transaction remains valid for execution, exactly analogous to the OpenQ `_expiration` parameter on deposits. In OpenQ, the `_expiration` field is only checked by the funder-side refund path and is never consulted by the claim path, so it "serves no external purpose" for the party it is meant to protect. In `kaiax`'s gasless module, `deadline` is checked only once, off-chain, when the transaction is admitted into the tx pool (`checkBalanceForSwap`), but is never re-validated at promotion time or enforced by the `GaslessSwapRouter` contract itself at execution time.

### Finding Description
`checkBalanceForSwap` performs a one-time "insufficient deadline" check comparing `swapArgs.Deadline` against `g.Chain.CurrentBlock().Time()` when the transaction is first validated for entry into the pool: [1](#0-0) 

This check is invoked from `pool.validateTx` at initial admission time (`pool.add` → `pool.validateTx`), which calls `module.GetCheckBalance()`: [2](#0-1) 

The same `checkBalance` function is also used by `txList.Filter`, which is invoked during `promoteExecutables`/`demoteUnexecutables` to decide whether a *queued* transaction should be dropped for being "unpayable": [3](#0-2) 

However, this re-check only happens for transactions sitting in the `queue` (non-executable, out-of-order) bucket; once a swap transaction is nonce-ready and becomes part of the `pending`/executable set (see `promoteExecutables` gathering `readyTxs` via `list.Ready`/`list.ReadyWithGasPrice` and directly calling `pool.promoteTx`) the deadline is not re-evaluated: [4](#0-3) 

Critically, promotion into `pending` can be delayed indefinitely by the sender-nonce ordering the gasless module enforces between an `ApproveTx` and its paired `SwapTx` (`isApproveTxReady`/`isSwapTxReady`), by re-orgs (`lockedReset`/`promoteExecutables(nil)` on every new head), or simply by a busy network. Because `checkBalanceForSwap` is a *view-based* check against the current chain state at the moment it runs, a transaction that passed the deadline check when queued can still be pending and eventually mined well after its declared `deadline` has elapsed if it is never re-filtered (there is no dedicated periodic re-check keyed specifically on the deadline field the way `Filter` re-checks balance/allowance each reset). Additionally, the on-chain `GaslessSwapRouter.swapForGas` contract call itself is only reachable through this off-chain gate — there is no evidence in the repository that the router contract independently reverts on an expired deadline; the enforcement lives entirely in the Go tx-pool module, which is bypassable in principle (e.g., different `BalanceCheckLevel` configurations skip parts of `checkBalanceForSwap`, per `ShouldCheckToken`/`ShouldCheckSwapAmount` gating seen in the same function) and is not part of consensus-level state-transition validation.

This mirrors the OpenQ bug precisely: a party-facing time bound (`deadline` for the gasless user, `_expiration` for the OpenQ funder) is declared in the transaction/deposit but the code path that actually moves value (`swapForGas` execution / bounty `claimBounty`) does not itself enforce it — the check exists only in a place that does not guarantee it is honored at execution time.

### Impact Explanation
If a stale gasless swap executes after its declared deadline, the user's `minAmountOut`/`amountRepay` parameters no longer reflect the exchange rate or gas price conditions the user intended, and the lending party (the gasless relayer) can be repaid `amountRepay` in KAIA computed against out-of-date assumptions, while the user's token is swapped at whatever exchange rate exists at actual execution time. This can result in the user receiving less value than expected or the relayer/lender extracting value from a swap that should have been rejected — a concrete instance of "fee-delegation/gasless settlement abuse" via acceptance of a transaction whose declared temporal validity constraint was not actually enforced at settlement time.

### Likelihood Explanation
The condition requires that a submitted `SwapTx` remain in the pool without being promoted/re-filtered past its deadline — realistic when it is nonce-blocked behind a not-yet-mined `ApproveTx`, during periods of congestion, or across chain reorgs that re-run `promoteExecutables` but do not necessarily re-run `checkBalanceForSwap` for already-pending transactions. This is reachable by any ordinary gasless user/relayer interaction with the public tx pool and does not require privileged access.

### Recommendation
Enforce the `deadline` at the point where value is actually transferred, not only at pool admission:
- Add an explicit `require(block.timestamp <= deadline)` (or the KAIA equivalent) inside `GaslessSwapRouter.swapForGas` itself, so the on-chain state transition rejects stale swaps regardless of tx-pool behavior.
- If keeping the off-chain check, re-validate `checkBalanceForSwap` (specifically the deadline condition) immediately before a swap transaction is moved into the pending/executable set and again immediately before block assembly, not just at initial admission or only for queued (non-ready) transactions.

### Proof of Concept
1. Attacker/relayer environment: submit an `ApproveTx` (nonce N) and a paired `SwapTx` (nonce N+1) with `deadline = now + 5s`, per `checkBalanceForSwap`'s deadline check: [1](#0-0) 
2. Because the gasless module requires nonce N to clear before N+1 is "ready" (`isSwapTxReady`), and admission-time validation already passed for the `SwapTx`, delay block production for the account (e.g., due to fee/priority under network load) so that `ApproveTx` is only mined after `deadline` elapses.
3. Once `ApproveTx` mines and `SwapTx` becomes nonce-ready, `promoteExecutables` moves it directly to `pending` via `list.Ready`/`promoteTx` without re-invoking `checkBalanceForSwap`'s deadline branch: [4](#0-3) 
4. The `SwapTx` is included in a block and `swapForGas` executes on-chain with no deadline check at the contract level, settling at post-deadline market conditions the user did not consent to.
