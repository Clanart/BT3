### Title
`Airdrop.claim()` lets attackers re-snapshot `totalEndRemainingAllocation` via the unguarded public `updateEndRemainingAllocation()` to inflate their own bonus share and over-drain the bonus pool - (File: rewards/Airdrop.sol)

### Summary
`claim()` only auto-calls `updateEndRemainingAllocation()` while `totalEndRemainingAllocation == 0`, i.e. exactly once, but `updateEndRemainingAllocation()` itself is `public` with no one-shot guard and can be called by anyone at any time after `periodsEndTime[4]`. Because `totalRemainingAllocation` shrinks every time someone claims, calling `updateEndRemainingAllocation()` again after other users have claimed re-snapshots `totalEndRemainingAllocation` to a smaller value, which inflates the bonus share (`getBonusAmount`) paid to whoever claims after the re-snapshot at the expense of the fixed `totalBonus` pool that funds it.

### Finding Description
The relevant code: [1](#0-0) 

`updateEndRemainingAllocation()` sets `totalEndRemainingAllocation = totalRemainingAllocation` unconditionally whenever `block.timestamp >= periodsEndTime[4]`, and it has no restriction preventing it from being called repeatedly. `claim()` only guards the *automatic* invocation with `if (totalEndRemainingAllocation == 0)`, meaning the automatic path effectively only fires once (the first time any user claims after period 4), but nothing stops an unprivileged caller from invoking the public function `updateEndRemainingAllocation()` directly, multiple times, at any later point.

`getBonusAmount()` divides `userAllocation * totalBonus` by `totalEndRemainingAllocation`: [2](#0-1) 

The invariant the design relies on is that `totalEndRemainingAllocation` is snapshotted **once**, at the moment period 4 ends, so that summing `userAllocation_i / totalEndRemainingAllocation * totalBonus` over every remaining allocation exactly reconstitutes `totalBonus` (since `sum(userAllocation_i) == totalEndRemainingAllocation` at snapshot time).

If an attacker (or anyone) calls `updateEndRemainingAllocation()` again after some users have already claimed (their allocations subtracted from `totalRemainingAllocation` via `totalRemainingAllocation -= userAllocation` in `claim()`), the new snapshot `totalEndRemainingAllocation_new` becomes smaller than the original `totalEndRemainingAllocation_old`. Denote:
- `S = totalEndRemainingAllocation_old`
- `C` = sum of allocations claimed before the re-snapshot (each computed with denominator `S`)
- After re-snapshot, `totalEndRemainingAllocation_new = S - C`

Bonus paid to early claimers: `(C/S) * totalBonus`.
Bonus paid to all remaining claimers after re-snapshot: `((S-C)/(S-C)) * totalBonus = totalBonus` (full pool again).

Total bonus actually disbursed = `totalBonus * (1 + C/S)`, which strictly exceeds `totalBonus`, the amount actually reserved from forfeitures. This directly breaks the invariant that `sum of all allocations` (plus bonus obligations) must reconcile with `aidropToken.balanceOf(address(this))`.

The per-call check `if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();` only prevents a single transaction from transferring more than the currently held balance — it does not prevent the aggregate over-allocation across multiple claimers, nor does it protect later, legitimate claimants from having insufficient balance left for their (rightfully smaller) bonus share, effectively enabling early/attacker claimants to extract value that should have gone to others.

### Impact Explanation
By strategically calling the permissionless `updateEndRemainingAllocation()` right before their own `claim()` (after observing/waiting for other users to claim and shrink `totalRemainingAllocation`), an attacker locks in an artificially small denominator for their own bonus computation, extracting a disproportionately large share of `totalBonus`. This directly reduces the funds available for other claimants' bonuses and base allocations, resulting in some legitimate users being unable to claim their full entitled `getClaimableAmount()` (reverting with `InsufficientBalance`) once the contract balance is depleted by earlier, manipulated over-payments. This is a direct theft of value from other users' unclaimed bonus/allocation pool to the attacker.

### Likelihood Explanation
No privileged role is required: `updateEndRemainingAllocation()` is `public` and unguarded, and any address — including a non-claimant — can call it. The only precondition is `block.timestamp >= periodsEndTime[4]` and that at least one claim has occurred to shrink `totalRemainingAllocation` between the initial auto-snapshot and the attacker's manual re-snapshot. This requires no capital, no flash loans, and is trivially repeatable by any claimant timing their own `claim()` after calling `updateEndRemainingAllocation()`.

### Recommendation
Add a one-shot guard directly inside `updateEndRemainingAllocation()` (not just at the `claim()` call site), e.g. `require(totalEndRemainingAllocation == 0, "already snapshotted")` before writing to `totalEndRemainingAllocation`, so the manual and automatic paths enforce the identical single-snapshot constraint.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, register allocations for users A, B, C, D with known amounts; fund the contract with exactly `sum(allocations)` tokens (no extra buffer).
2. Warp time to `periodsEndTime[4]`.
3. Have user A call `claim()` — this triggers the automatic `updateEndRemainingAllocation()` (since it's 0), snapshotting `totalEndRemainingAllocation = totalRemainingAllocation` (sum of B, C, D's allocations, since A just zeroed out its own before the subtraction order — adjust based on exact state); record `totalBonus` and `totalEndRemainingAllocation` after A's claim.
4. Have user B call `claim()` normally (uses existing snapshot), record bonus paid to B.
5. Before user C claims, have attacker (could be C itself) call `updateEndRemainingAllocation()` directly — assert `totalEndRemainingAllocation` decreases from the value in step 3 to `totalRemainingAllocation` at this later point (only C+D allocations remain).
6. Have C call `claim()`, record bonus paid to C using the smaller denominator; assert `bonus_C / allocation_C > bonus_B / allocation_B` for equal-sized allocations, demonstrating unfair inflation.
7. Have D attempt to `claim()` last; assert either `InsufficientBalance()` reverts or D receives a truncated amount relative to `getClaimableAmount(D)` before the manipulation.
8. Assert cumulative `sum(bonus paid to A,B,C)` exceeds the original `totalBonus` recorded in step 3, and/or `aidropToken.balanceOf(address(this))` reaches 0 before D can claim its full entitlement — confirming the invariant `sum of allocations == balanceOf(this)` is broken and D's funds are frozen/stolen.

```text
    function updateEndRemainingAllocation() public {
        if (block.timestamp >= periodsEndTime[4]) {
            totalEndRemainingAllocation = totalRemainingAllocation;
        }
    }

    /// @notice Claim MGP and forfeit remaining allocation
    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
```
