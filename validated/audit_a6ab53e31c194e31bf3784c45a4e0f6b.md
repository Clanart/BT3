### Title
Self-destructed native-ERC20 token pairs are silently deleted, permanently freezing all outstanding bank-coin balances of that denom - (File: x/erc20/keeper/msg_server.go)

### Summary
`ConvertERC20` and `ConvertCoin` both contain a "cleanup" branch that silently deletes a native-ERC20 `TokenPair` the moment the underlying ERC20 contract is found to be self-destructed (`acc == nil || !acc.HasCodeHash()`), without reconciling or migrating any bank Coins that are still in circulation under that pair's denom. This is the same root-cause pattern as the Cork `VaultPoolLib` bug: a piece of user-owned value (here, the still-circulating `coin.erc20/<addr>` bank balances) is silently detached from the only mechanism that lets it move (the ERC20 conversion path) and is never dealt with again.

### Finding Description
When either conversion entrypoint is called against a native-ERC20 pair, the keeper checks the liveness of the backing contract before performing the conversion: [1](#0-0) 

and symmetrically in `ConvertCoin`: [2](#0-1) 

If the contract has been self-destructed (code hash cleared, e.g. via EIP-6780 in-transaction destruction or any post-Cancun destruct path exposed through the EVM), the keeper calls `DeleteTokenPair` and returns `nil, nil` — a *successful* no-op response — instead of returning an error: [3](#0-2) 

`DeleteTokenPair` removes the `TokenPair`, the ERC20↔ID map, the denom↔ID map, and allowances, but does nothing about:
- Any bank `Coin` balances of `pair.Denom` still held by users (minted earlier via `convertERC20IntoCoinsForNativeToken`, e.g. [4](#0-3) ).
- Any escrowed ERC20 balance the module account previously held for the pair.

Once the denom/ID mapping is deleted, `GetTokenPairID` returns nothing for that denom, so `MintingEnabled` will always fail to resolve a pair for it going forward — the denom becomes permanently un-convertible. Any bank Coins of that denom that are still held by any account (not just the caller who triggered the deletion) are now dead: they can never be converted back to an ERC20 token, and no equivalent value-recovery path exists (unlike `ConvertCoinNativeERC20`'s burn/unescrow flow, which never runs in this branch).

This mirrors the Cork report precisely: a comment/mechanism exists to "temporarily" or "as-needed" retire an asset representation, but the leftover value attributed to other holders is left permanently untracked and unreachable.

### Impact Explanation
This is an unprivileged, permanent freezing of user funds:
- Any address can register a native ERC20 contract (permissionless registration is supported, see `RegisterERC20`), obtain the corresponding bank Coin balances for other users via ordinary transfers, and then self-destruct the underlying contract.
- Any single account — not necessarily a fund holder — can then trigger `MsgConvertERC20` or `MsgConvertCoin` referencing that contract, which deletes the `TokenPair` as a side effect of a message that otherwise appears to be a harmless "no-op" success.
- Every other holder of `pair.Denom` bank Coins (who may have received them via ordinary transfers, IBC, or DEX activity) permanently loses the ability to convert their balance back into an ERC20 representation. There is no admin recovery path, no timeout, and no distribution mechanism — the value is orphaned exactly like the un-ration `Pa` in the Cork report.

This falls under "Critical permanent freezing, locking … of user funds … or token-pair-backed balances," triggerable by an ordinary unprivileged user through the standard `MsgConvertERC20`/`MsgConvertCoin` message flow.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires (1) permissionless or governance registration of an attacker-controlled ERC20 (permissionless registration is a supported, non-privileged parameter, see `RegisterERC20`), (2) some coin balance to already be in circulation under that denom (a natural outcome of normal usage — transfers, IBC, DEX swaps), and (3) any account calling `ConvertERC20`/`ConvertCoin` after the contract self-destructs. None of these steps require special privileges, and the deletion happens as an incidental side effect of a message that returns success, making it easy to trigger accidentally or maliciously.

### Recommendation
- Do not silently delete the `TokenPair` when the contract is found to be destroyed. Instead, return an explicit error, or transition the pair to a "disabled/frozen" state that still allows redemption of outstanding bank Coins for any residual value (e.g., burn-and-refund, or a permanent Coin-only fallback) rather than removing the mapping outright.
- Before deleting a `TokenPair`, verify there is no outstanding supply of `pair.Denom` (query bank total supply for the denom) and reject/queue the deletion if a non-zero supply exists, or provide an explicit migration/redemption path for existing holders.
- Emit a clear, non-silent event/error when this condition is hit so wallets, indexers, and holders are alerted rather than the call quietly succeeding with `nil, nil`.

### Proof of Concept
1. Deploy a minimal ERC20 contract with a public `kill()` function that calls `selfdestruct`.
2. Governance/permissionless-register the contract as a native-ERC20 `TokenPair` (`MsgRegisterERC20`).
3. Mint ERC20 tokens to account A, call `MsgConvertERC20` to mint bank Coins of `pair.Denom` to A.
4. Transfer some of those Coins to account B via ordinary bank send (B now legitimately holds value in `pair.Denom`).
5. From account A, call `kill()` on the contract, causing `acc.HasCodeHash()` to become false.
6. Any account calls `MsgConvertERC20` (or `MsgConvertCoin`) referencing the now-destroyed contract address; the keeper hits the `acc == nil || !acc.HasCodeHash()` branch, calls `DeleteTokenPair`, and returns success.
7. Account B still holds Coins of `pair.Denom`, but `GetTokenPairID`/`GetTokenPair` no longer resolve it — B's balance is now permanently unconvertible and its underlying ERC20 backing (via the deleted pair) is unreachable.

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}
