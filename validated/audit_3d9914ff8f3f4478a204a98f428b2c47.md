Audit Report

## Title
Repair response acceptance relies solely on a spoofable 32-bit nonce, not sender authentication - (core/src/shred_fetch_stage.rs)

## Summary
Incoming repair-response packets are accepted as satisfying an outstanding repair request purely by matching a `Nonce` (`u32`) extracted from the packet via `verify_repair_nonce`, which calls `OutstandingRequests::register_response`. Neither function checks that the packet's source `SocketAddr` matches the peer the original request was actually sent to, so an off-path attacker who obtains a valid nonce can inject a spoofed response that consumes the outstanding-request slot and causes the legitimate response to be discarded.

## Finding Description
`OutstandingRequests::add_request`/`add_request_with_metadata` register an outstanding repair request under a randomly generated `nonce`, with no binding to the destination peer's address. [1](#0-0) 

When a UDP packet with the `PacketFlags::REPAIR` flag arrives, `shred_fetch_stage::verify_repair_nonce` extracts `(shred, nonce)` from the raw packet bytes and calls `register_response`; if it returns `Some`, the packet is treated as a valid response and kept, otherwise discarded. [2](#0-1) 

`register_response` itself keys purely off `nonce`, checking only expiration and `request.verify_response(response)` (content shape validation of the shred against the expected repair type/slot/index) — it never inspects or requires a matching sender `SocketAddr` for the incoming packet. [3](#0-2) 

The call site in `modify_packets` passes only the packet and the shared `outstanding_repair_requests` map — no `packet.meta().socket_addr()` or equivalent is compared against the address the corresponding request was sent to. [4](#0-3) 

This contrasts with the *request*-side path (`verify_signed_packet` in `serve_repair.rs`), which explicitly checks `header.recipient == my_id`, timestamp freshness, and an Ed25519 signature — a much stronger authentication bar that is absent on the response side. I was unable to fully re-verify the exact contents of `ShredRepairType::verify_response` in this session (ran out of tool iterations), so I cannot confirm the full extent of shred-content validation beyond what's implied by the report; the core structural gap — no sender-address binding — is confirmed directly from `outstanding_requests.rs` and `shred_fetch_stage.rs`.

## Impact Explanation
If an attacker can produce a UDP packet with a matching nonce (via observation, prediction, or flooding within the 60s `DEFAULT_REQUEST_EXPIRATION_MS` window), `register_response` will decrement/remove the outstanding-request slot regardless of the packet's true source address. This causes the genuine response (when it later arrives) to find no matching entry and be discarded as invalid, suppressing that repair. This falls under the listed valid-impact category of repair/blockstore-completion degradation, without requiring a malicious validator or privileged capability — only the ability to send UDP packets that happen to hit a live nonce.

## Likelihood Explanation
Exploitability depends on the attacker's ability to learn or guess a live 32-bit nonce within a 60-second window. Blind brute force across the full 32-bit space is impractical over a UDP round-trip budget, but an attacker positioned to observe repair traffic to/from the victim (on-path, or a peer who was itself sent the corresponding repair request and thus already knows the nonce) can exploit this reliably and repeatably. This is a lower-but-nonzero likelihood gap, and it is a real structural difference between this response path and the signature/identity-bound request path in the same subsystem.

## Recommendation
Bind the destination `SocketAddr` (and, where available, expected responder identity) into the `RequestStatus` recorded at `add_request` time, and require the incoming response packet's source address to match before accepting it in `register_response`/`verify_repair_nonce`, mirroring the sender/identity checks already applied to signed repair requests in `verify_signed_packet`.

## Proof of Concept
1. Validator V sends a `ShredRepairType` request to peer P, registering `nonce = N` via `OutstandingRequests::add_request` (`core/src/repair/outstanding_requests.rs:20`).
2. Attacker A, who has learned `N` (e.g., by observing traffic to/from V's repair port, or because A itself received the corresponding repair request), sends V a UDP packet flagged as a repair response containing a shred payload plus trailing `nonce = N` from a spoofed or arbitrary source address.
3. `shred_fetch_stage::verify_repair_nonce` → `outstanding_repair_requests.register_response(N, shred, now, ...)` succeeds purely on the nonce/content match (`core/src/repair/outstanding_requests.rs:60-94`), consuming the outstanding-request slot without ever checking the packet's source address.
4. When P's legitimate response later arrives with nonce `N`, `register_response` finds no matching entry (already popped) and the packet is discarded by `verify_repair_nonce` returning `false`, leaving V's genuine repair unfulfilled — reproducible as a unit test asserting `register_response` succeeds for an out-of-band caller supplying only `(nonce, response, now)` with no address parameter at all.

```rust
    pub fn register_response<R>(
        &mut self,
        nonce: u32,
        response: &S,
        now: u64,
        success_fn: impl Fn(&T) -> R,
    ) -> Option<R> {
        let mut should_delete = false;
        let response = self.requests.get_mut(&nonce).and_then(|status| {
            if status.num_expected_responses == 0 {
                // No more expected responses
                return None;
            }

            if now >= status.expire_timestamp || !status.request.verify_response(response) {
                // Invalid/expired response should invalidate this nonce.
                should_delete = true;
                return None;
            }

            status.num_expected_responses -= 1;
            if status.num_expected_responses == 0 && status.metadata.is_none() {
                // No metadata, and no more expected responses safe to delete eagerly.
                should_delete = true;
            }
            Some(success_fn(&status.request))
        });

        if should_delete {
            self.requests
                .pop(&nonce)
                .expect("request must exist when marked for deletion");
        }
        response
    }
```

```rust
// Returns false if repair nonce is invalid and packet should be discarded.
#[must_use]
fn verify_repair_nonce(
    packet: PacketRef,
    now: u64, // solana_time_utils::timestamp()
    outstanding_repair_requests: &mut OutstandingShredRepairs,
) -> bool {
    debug_assert!(packet.meta().flags.contains(PacketFlags::REPAIR));
    let Some((shred, Some(nonce))) = shred::layout::get_shred_and_repair_nonce(packet) else {
        return false;
    };
    outstanding_repair_requests
        .register_response(nonce, shred, now, |_| ())
        .is_some()
}
```
