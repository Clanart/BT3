### Title
Attacker-Controlled Participant Count Causes Eager ~2–4 MB Heap Allocation per `ThresholdKeys::read` Call (Memory-Exhaustion DoS) - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::<C>::read` trusts a serialized `u16` participant count `n` and calls `Vec::with_capacity(usize::from(n))` before validating that any corresponding data actually exists in the stream. This is the same bug class as the Pandora DAA decompression bomb: a tiny attacker-controlled input prefix forces a disproportionately large memory allocation. An unprivileged party able to feed bytes to `ThresholdKeys::read` can spend ~15 bytes of input to force a ~2 MB allocation (65,535 × 32-byte field elements; ~3.7 MB for Ed448's 56-byte field), and repeat this to exhaust memory.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` deserializes `t`, `n`, `i` as raw `u16`s, then reads a single interpolation-method byte. When the byte is `0` (`Interpolation::Constant`), it immediately executes:

```rust
// crypto/dkg/src/lib.rs:607-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

`n` is fully attacker-controlled (any nonzero `u16`, up to 65,535). `Vec::with_capacity` eagerly reserves `n * size_of::<C::F>()` on the heap — for Ristretto/Ed25519-class fields ~2 MB, for Ed448 ~3.7 MB — regardless of whether the reader actually contains that many field elements. If the stream is truncated, `C::read_F` fails on the first missing element, but the oversized allocation was already performed. This is precisely the "small input → large memory consumption" amplification pattern of the reported decompression bomb, minus the compression layer; Serai's equivalent is an unbounded length-prefixed allocation. Additionally, the verification-share loop `for l in 1 ..= n` (`crypto/dkg/src/lib.rs:621-623`) reads `n` group elements driven by the same unchecked count, and `ThresholdParams::new` validation (which bounds `i <= n` but not `n` itself against any sane cap) runs only after all allocations/reads complete.

By contrast, related readers in scope are amplification-safe or out of scope: `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`) grows a `Vec` only as actual bytes are consumed (allocation ∝ input), and `Block::read`'s `Vec::with_capacity(txs)` lives in the coordinator, outside the listed scope.

### Impact Explanation
Memory-exhaustion denial of service. Each maliciously crafted input costs the attacker ~15 bytes (ID length + ID + `t`/`n`/`i` + interpolation tag) and forces the victim to allocate up to ~2–3.7 MB of heap. Repeated submissions, or many such values embedded in a single deserialized structure, scale this linearly to OOM/termination of the process performing deserialization — analogous to the Pandora worker being killed by a decompression bomb. Per the engagement's reachability rules, `ThresholdKeys::read` is an explicitly listed untrusted-bytes entry point, so no privileged position is required. There is no secret leakage or forgery, placing this in the Medium (availability) band consistent with the source CVE's VA:H rating.

### Likelihood Explanation
Exploitation requires only that some deployment path deserializes `ThresholdKeys` (or a structure containing it) from attacker-influenced bytes — e.g., keys/state synced or submitted by peers during set rotation or recovery flows. The trigger is deterministic (no race, no valid signature needed, since the allocation precedes all semantic validation), works on any `Ciphersuite` with a multi-byte field, and is repeatable. Likelihood is bounded only by whether the integrating service exposes this reader to unauthenticated input, which the rules stipulate.

### Recommendation
- Do not pre-allocate from untrusted counts. Replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` and let growth track bytes actually read, or cap `n` against a protocol maximum (e.g., `MAX_KEY_SHARES_PER_SET`, as `Transaction::SlashReport` does at `coordinator/src/tributary/transaction.rs:431`) before any allocation.
- Validate `t <= n <= MAX` and `i <= n` via `ThresholdParams::new` **before** entering the interpolation/verification-share loops, rather than at the end of `read`.
- Consider reading field elements incrementally into a bounded buffer and aborting when the cumulative deserialized size exceeds a documented limit, mirroring the `max_extracted_filesize` approach of the upstream patch.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ristretto;
use dkg::ThresholdKeys;

fn main() {
  // A truncated ThresholdKeys blob: valid Ristretto ID header, then t=1, n=0xFFFF,
  // i=1, interpolation=Constant(0), and NO field/scalar data at all.
  let mut bytes = vec![];
  bytes.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
  bytes.extend(Ristretto::ID);
  bytes.extend(&1u16.to_le_bytes());      // t
  bytes.extend(&u16::MAX.to_le_bytes());  // n = 65535  <-- attacker-controlled
  bytes.extend(&1u16.to_le_bytes());      // i
  bytes.push(0);                          // Interpolation::Constant -> with_capacity(65535)

  // read() will fail at the first read_F, but only AFTER Vec::with_capacity
  // has already reserved ~65535 * 32 bytes (~2 MB) on the heap.
  let res: io::Result<ThresholdKeys<Ristretto>> =
    ThresholdKeys::read(&mut bytes.as_slice());
  assert!(res.is_err());

  // In a server loop handling untrusted ThresholdKeys payloads, repeating the
  // ~15-byte effective payload forces ~2 MB allocations per call (Ed448: ~3.7 MB),
  // exhausting memory without ever needing to supply the promised elements.
}
```

Root cause: `crypto/dkg/src/lib.rs:608` — `Vec::with_capacity(usize::from(n))` trusts the attacker-supplied `n` before any bound check or data-availability verification, enabling small-input/large-allocation amplification.
