### Title
Ed448 point decoding accepts non-prime-order points due to a vacuous torsion check - ([File: crypto/ed448/src/point.rs])

### Summary
`Point::is_torsion_free` computes `(-1 * self) + self`, which is the identity for every point, so it never rejects Ed448 components of order 2 or 4. [1](#0-0) 

### Finding Description
`GroupEncoding::from_bytes` gates decoded points on `point.is_torsion_free()`, but that predicate is mathematically vacuous because `Scalar::ZERO - Scalar::ONE` is `-1`, making the expression `P - P`. [1](#0-0)   
`Ciphersuite::read_G` checks that the decoded point re-encodes to the same bytes, but it relies on `from_bytes` for subgroup validity and therefore accepts canonical encodings of non-identity torsion points. [2](#0-1)   
The FROST `Curve::read_G` wrapper rejects only the identity, so non-identity Ed448 torsion points can enter signing inputs through `read_preprocess`, `read_share`, or other callers that pass untrusted point encodings. [3](#0-2)   
This violates the `PrimeGroup` assumption used by `SchnorrSignature`, PedPoP commitments and encrypted-share keys, and generator-promotion DLEq shares. [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
The verifier formula `R + cA - sG = identity` is only sound when `R` and `A` are confined to the prime-order subgroup. [8](#0-7)   
If `A` is a non-identity order-4 Ed448 point and `R` is another torsion point, the equation reduces to a relation modulo 4, while `sG` contributes no torsion component. [9](#0-8) [10](#0-9)   
An attacker can therefore forge a Schnorr signature or proof under an attacker-selected torsion public key by choosing `s = 0` and searching `R`/message bindings until the challenge satisfies the required congruence modulo 4. [11](#0-10) [12](#0-11)   
In PedPoP, this weakens the proof-of-knowledge guarantee for `commitments[0]`, because `Commitments::read` accepts torsion points and the resulting Schnorr PoK is verified with the same subgroup-confused equation. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
An unprivileged participant can supply the affected Ed448 encodings through normal deserialization paths such as `Commitments::read`, `EncryptionKeyMessage::read`, `EncryptedMessage::read`, `SchnorrSignature::read`, and `GeneratorProof::read`. [5](#0-4) [15](#0-14) [6](#0-5) [16](#0-15)   
There are only three non-identity torsion points to try, and the relevant torsion relation depends only on the challenge modulo 4, so chosen-message or chosen-commitment contexts permit practical grinding rather than solving a discrete logarithm. [8](#0-7) [12](#0-11) 

### Recommendation
Implement a real cofactor check for Ed448, such as rejecting any decoded point for which multiplication by the cofactor does not yield identity or otherwise proving membership in the prime-order subgroup before returning success. [1](#0-0)   
Reject identity where the caller requires non-identity points, and keep the canonical re-encoding check as a secondary encoding check rather than a substitute for subgroup membership. [2](#0-1) [3](#0-2) 

### Proof of Concept
1. Let `T` be a canonical Ed448 encoding of a non-identity order-4 point. `Ed448::read_G` accepts it because `is_torsion_free(T)` evaluates `T - T` and returns true. [1](#0-0) [2](#0-1) 
2. Set the claimed public key to `A = T`. For `j in 0..=3`, choose `R = jT` and `s = 0`, then serialize `SchnorrSignature { R, s }`. [17](#0-16) 
3. For each candidate, compute the protocol’s normal challenge `c = H(R, A, msg_or_commitments)`. The verifier evaluates `R + cA - sG = (j + c)T`, so the proof verifies whenever `j + c = 0 mod 4`. [18](#0-17) 
4. Vary attacker-controlled transcript-bound data, such as the message or later PedPoP commitment encodings represented in `cached_msg`, until one of the four `R` values satisfies that congruence. [12](#0-11) [5](#0-4) 
5. The resulting `(R, s)` is accepted as a valid Schnorr proof/signature for the torsion public key even though no prime-order discrete-log knowledge exists. [19](#0-18)

  /// This is intended to be used with a multiexp.
  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }
