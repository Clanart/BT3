## Title
Partial-commit line selections are applied against a re-fetched, unvalidated diff at commit time, silently corrupting which lines are actually committed — (File: `app/src/lib/git/apply.ts`)

### Summary
This is the closest Desktop analog to the reported bug class: a cached/derived aggregate (`ERC721Power::totalPower`) is used by a critical operation without being recalculated against current state first. In Desktop, the equivalent stale value is the **line-selection index set** (`DiffSelection`) a user builds while reviewing a *rendered* diff. When the commit is actually created, Desktop re-fetches a **fresh** working-directory diff and blindly re-applies the old selection's absolute line indices to it, without revalidating that those indices still correspond to the same textual change.

### Finding Description
When a user partially selects lines in the Changes view, the app stores selection state as a set of **absolute line indices** (`divergingLines`) computed against the diff that was rendered at that time [1](#0-0) . Committing happens in `_commitIncludedChanges`, which pulls `state.changesState.workingDirectory.files` and their `.selection` straight from the current cache and passes them to `createCommit` — with no diff refresh or selection revalidation immediately beforehand [2](#0-1) .

For files with a partial selection, `stageFiles` calls `applyPatchToIndex` per file [3](#0-2) . Critically, `applyPatchToIndex` does **not** use the diff that was displayed to the user (`changesState.selection.diff`); it fetches a brand-new diff straight from disk at that moment: `const diff = await getWorkingDirectoryDiff(repository, file)` [4](#0-3) . This fresh diff is then handed to `formatPatch`, which walks the **new** hunks and, for every non-context line, tests `file.selection.isSelected(absoluteIndex)` using the index scheme `hunk.unifiedDiffStart + lineIndex` from the *new* diff [5](#0-4) . The selection object, however, was built against indices from the diff the user actually looked at, which may be older.

Desktop is aware this gap exists: the working-directory diff refresh routine explicitly documents that it does not verify selected lines still correspond to the same content, only that stale indices are dropped if they fall outside the newly computed `selectableLines` set: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."* [6](#0-5) . `DiffSelection.withSelectableLines` performs only an index-membership filter — not a content-identity check — when reconciling old selections against a new line-index universe [7](#0-6) . Even this partial safeguard is only invoked opportunistically during `updateChangesWorkingDirectoryDiff`, not guaranteed to run immediately prior to `applyPatchToIndex`'s independent, later re-fetch of the diff.

### Impact Explanation
If the on-disk content of a file under partial-commit review changes between the time the user reviews/selects diff lines and the moment they click "Commit" (e.g., a build tool, linter with auto-fix, file watcher, or any tooling shipped by/triggered from a cloned or fetched repository rewrites tracked files, such as a postinstall/dev-server/format-on-save script), the old numeric line indices can silently land on different, unreviewed lines in the freshly fetched diff. This can cause Desktop to stage and commit content the user never selected (or exclude content they intended to include) with no warning — a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact category. Because staging occurs at the git-index level via `git apply --cached`, there's no secondary review step before the commit is finalized.

### Likelihood Explanation
This requires no privileged access: it only needs (a) a repository (cloned or opened) whose tooling can rewrite tracked files asynchronously while the user is composing a partial commit, and (b) the user taking any non-trivial time between making a line selection and clicking commit (typing a commit message is normal, expected behavior, not an "unnatural" step). The relevant code paths (`_commitIncludedChanges`, `applyPatchToIndex`, `formatPatch`) contain no timestamp/hash check tying the selection to the diff version it was computed from, and the existing `withSelectableLines` guard is acknowledged in-code as incomplete.

### Recommendation
Before staging partially-selected files, re-fetch the working-directory diff for each such file and validate that the currently selected line indices still correspond to the same textual content (e.g., by diffing on content/hash rather than positional index, or by aborting/re-prompting the user if the file changed since the diff was last rendered) rather than relying solely on index-bounds filtering in `DiffSelection.withSelectableLines`.

### Proof of Concept
1. Open a repository in Desktop containing a script (e.g., `npm run watch`, a pre-configured formatter, or any auto-run tooling from the repo) that rewrites a tracked file's lines on a timer/trigger.
2. Modify the file locally so it has multiple hunks; open the Changes view and partially select specific lines (e.g., select only lines belonging to hunk 2), leaving the commit message box open.
3. While composing the commit message, let the repo's background tooling rewrite the file so hunk boundaries/line counts shift.
4. Click "Commit". Observe via `git show` on the resulting commit that the staged/committed lines do not match the lines the user visually selected, because `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetched the diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-170`) applied the stale `DiffSelection` indices against the new hunk layout.

    } else if (this.defaultSelectionType === DiffSelectionType.None) {
