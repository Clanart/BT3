### Title
`updateRemoteUrl` silently rewrites a repository's `origin` remote based on an untrusted GitHub API field, redirecting future pushes/fetches — ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically overwrites the local git remote URL with `apiRepo.clone_url` — a value returned by the GitHub/GHES API — whenever the API-reported clone URL no longer matches what Desktop currently has cached, as long as the URL scheme ("protocol") is unchanged. This runs automatically as part of the normal repository-refresh flow, without any explicit user confirmation, and the new URL's hostname is never checked against anything the user actually trusts.

### Finding Description
`updateRemoteUrl` compares the repository's current default remote to the `clone_url` field of an `IAPIRepository` object fetched from the GitHub API: [1](#0-0) 

The only checks performed are:
1. `protocolsMatch` — the scheme (`https`/`ssh`) of the old and new URL must match.
2. `remoteUrlUnchanged` — the *current* remote must still match the previously-cached `gitHubRepository.cloneURL`.
3. `!urlsMatch(updatedRemoteUrl, gitStore.defaultRemote)` — the new URL differs from what's configured.

If all three hold, `gitStore.setRemoteURL(...)` is invoked with the API-supplied URL, with no verification that the new host is the same host the repository was originally associated with, or any host the user has ever explicitly trusted: [2](#0-1) 

This is invoked from the app store's repository-refresh pipeline (`withRefreshedGitHubRepository`), which is a routine, largely automatic operation triggered on repository selection, branch checkout, push, and pull — not a deliberate, explicit user action such as "change remote URL" in Repository Settings.

The broken invariant is analogous to the StRSR bug: two pieces of state that are supposed to stay in lockstep (the GitHub API's belief about where the repo lives, and the git remote actually used for network operations) are allowed to diverge and then silently "resynced" using attacker-influenced data, without re-validating trust boundaries — just as StRSR reset `stakeRSR`'s era without keeping `draftRSR`'s era consistent.

### Impact Explanation
`IAPIRepository.clone_url` originates from a GitHub Enterprise server endpoint or the GitHub API. If that endpoint is attacker-controlled/compromised, or if the response can otherwise be manipulated (a network attacker able to tamper with the specific API response, a malicious/compromised GHES instance a user has added, or an org/repo hand-off scenario where a new owner controls the repository metadata for a name the user still has configured locally), the API can supply an arbitrary `clone_url` on a different host. Desktop will accept it as long as the URL scheme matches, and will call `git remote set-url` to point `origin` at the attacker's host — with no user prompt. Subsequent pushes/fetches then talk to the attacker-controlled remote:
- Code the user commits can be silently exfiltrated to the attacker's server.
- Any credentials or tokens resolved for that (now attacker-chosen) host during push/fetch (`envForRemoteOperation`, credential helper, SSH agent) could be sent to the attacker's server depending on how broadly the local credential helper/SSH config matches hosts.
- What the user believes they are pushing to is silently corrupted (the destination remote), matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires the attacker to control (or spoof) the GitHub/GHES API response for a repository the victim already has cloned and where the previously known `cloneURL` currently matches the local remote — a state that's common for any normal repo. No local access, no admin rights, and no unusual user action are required; the update happens as part of Desktop's routine background repository refresh. The likelihood is bounded by needing control over an API response (e.g. via a malicious/compromised GHES server, or a repository-transfer scenario where new owners control the metadata for a still-cached repo), which is a plausible "attacker controls a GitHub API object" scenario per the task's valid-impact criteria.

### Recommendation
Before silently rewriting the remote URL, require that the new URL's **hostname** matches the existing remote's hostname (only allow owner/name changes from renames/transfers on the same host), or otherwise prompt the user for explicit confirmation before changing the remote to a different host. At minimum, log/telemetry-flag any hostname change and require user consent, since a scheme-only check (`protocolsMatch`) provides no real trust boundary.

### Proof of Concept
1. Victim has a repository cloned with `origin` = `https://ghe.example.com/acme/widgets.git`, matching the cached `gitHubRepository.cloneURL`.
2. Attacker who controls (or can spoof responses from) `ghe.example.com`'s API for that repo path returns `clone_url: "https://ghe.example.com/attacker/widgets.git"` (or any other host reachable using the same https scheme) the next time Desktop refreshes repository metadata (a routine background operation).
3. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (local remote still equals old cached clone URL), and `urlsMatch(updatedRemoteUrl, defaultRemote) === false`, so it calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com/attacker/widgets.git')` with no user prompt: [3](#0-2) 
4. The next push/fetch the victim performs silently goes to the attacker-controlled repository/path instead of the intended one.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
