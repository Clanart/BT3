## Finding

The exploit is real and confirmed by the code and by the app's middleware wiring.

### Title
Attacker-controlled dest-callback revert strands already-minted ERC20/voucher funds at an unrecoverable isolated address while the source chain refunds the sender, duplicating value - (File: `x/ibc/callbacks/keeper/keeper.go`, `x/erc20/keeper/ibc_callbacks.go`, `evmd/app.go`)

### Summary
The transfer stack is wired with the IBC callbacks middleware as the **outermost** layer: `callbacks -> erc20 -> transfer` [1](#0-0) . On `OnRecvPacket`, the callbacks middleware first invokes the wrapped app (erc20 middleware → transfer app), which mints the IBC voucher coin and converts/mints its ERC20 representation directly to the isolated receiver address on the **real, uncached** `ctx` [2](#0-1) [3](#0-2) . Only *after* this mint is committed does the callbacks middleware run `ContractKeeper.IBCReceivePacketCallback`, which uses its own internal `CacheContext()` solely to scope the EVM `approve`/calldata execution [4](#0-3) .

If the callback contract fails the `approve` call, returns `false`, or does not fully drain the isolated address's balance via `transferFrom`, `IBCReceivePacketCallback` returns an error (`ErrAllowanceFailed` or "unrecoverable tokens after callback") [5](#0-4) . This error only converts the outer acknowledgement into an error ack — it does **not** unwind the mint that was already committed to the real `ctx` before the callback ran.

### Finding Description
Since the mint happens in the non-cached outer context prior to callback invocation, an error returned from `IBCReceivePacketCallback` cannot reverse it. The packet's designated receiver is the isolated address `types.GenerateIsolatedAddress(destChannel, sender)` [6](#0-5)  — a deterministically derived address with no associated private key, and the only sanctioned path to move funds out of it is the `approve`+`transferFrom` sequence performed inside the callback itself. Once that callback fails, there is no other authorized mechanism to recover the balance from the isolated address.

Meanwhile, because the acknowledgement returned to the counterparty (source) chain is an error ack, the standard ICS20 `OnAcknowledgementPacket` logic on the source chain will refund/un-escrow the equivalent value back to the original sender. The net effect is that the same economic value now exists twice: once refunded to the sender on the source chain, and once permanently stuck at the isolated address on the destination chain.

### Impact Explanation
This satisfies two Critical impact categories:
- Permanent freezing/locking of user funds: the minted balance at the isolated address is unrecoverable since no key controls it and the recovery mechanism (the callback's `approve`/`transferFrom`) is exactly what failed.
- Accounting/value duplication: the source-chain refund plus the stuck destination-chain mint means backing invariants between escrowed/burned value and minted representations are violated, producing spendable value beyond what should exist for a single transfer.

### Likelihood Explanation
Fully triggerable by an unprivileged attacker using ordinary IBC transfer flows: they need only send an ICS20 transfer to themselves with a `dest_callback` memo pointing at a contract they control that intentionally reverts, returns `false` from `approve`, or performs a partial `transferFrom` [7](#0-6) . No validator, relayer, or governance action is required — this is a standard sender-controlled packet-crafting exploit, matching the test harness pattern already used in `TestOnRecvPacketWithCallback`/`TestOnRecvPacketNativeErc20` [8](#0-7) [9](#0-8) , which already demonstrates trapped balances remaining at the isolated address after a failed callback.

### Recommendation
Perform the destination-callback contract invocation and its balance-sufficiency validation within the same cached/branched context as the underlying transfer+erc20 mint, and only commit (`writeFn`) the entire packet-processing state (mint + callback) atomically when the callback succeeds. Alternatively, on `IBCReceivePacketCallback` failure, explicitly move/burn-and-refund the isolated address's balance back through an authorized module path before returning the error acknowledgement, so no value is stranded while the source chain independently refunds the sender.

### Proof of Concept
1. Attacker on chain B sends an ICS20 transfer to chain A (EVM chain) with `receiver` set to `GenerateIsolatedAddress(destChannel, senderB)` and `memo.dest_callback` pointing at an attacker-deployed contract whose function never calls `transferFrom` (or reverts).
2. `channel.RecvPacket` → `callbacks.OnRecvPacket` → `erc20.OnRecvPacket` → `transfer.OnRecvPacket` executes on the real `ctx`, minting the voucher/ERC20 balance to the isolated address [3](#0-2) .
3. `IBCReceivePacketCallback` runs the callback; balance check finds `receiverTokenBalance != 0` and returns `ErrEVMCall "unrecoverable tokens after callback"` [10](#0-9) .
4. The acknowledgement written back to chain B is an error ack; chain B's `OnAcknowledgementPacket` refunds the sender.
5. Assert: ERC20/voucher balance at the isolated address on chain A remains equal to the transferred amount (as already shown by `trappedBal` assertions in existing tests) [9](#0-8) , while the sender's balance on chain B has also been restored — demonstrating duplicated, permanently stuck value.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
