### Title
Deserialized threshold keys accept identity verification shares, enabling signatures for the identity group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts identity points as verification shares and does not validate that the supplied secret share matches the claimed verification share. A malicious caller can therefore construct a syntactically valid `ThresholdKeys` object whose group key is the identity and whose secret share is zero, then use the normal FROST signing flow to produce a signature for that public key.

### Finding Description
`ThresholdKeys::read` reads every participant verification share with `<C as Ciphersuite>::read_G`, which performs canonical point decoding but permits the identity point. It then calls `ThresholdKeys::new`, which validates the share count, participant indexes, and interpolation mode, but does not reject identity verification shares or check `C::generator() * secret_share == verification_shares[i]`.

For parameters `t = 1`, `n = 1`, `i = 1`, a serialized key containing:

- interpolation `Lagrange`
- `secret_share = 0`
- `verification_shares[1] = identity`

is accepted. `ThresholdKeys::new` calculates `group_key` as the identity verification share multiplied by the sole interpolation factor, yielding the identity group key. During signing, the singleton interpolation factor is `1`, so the signature share is simply the participant nonce because the secret contribution is `0 * challenge`. The resulting FROST Schnorr equation verifies under the identity public key.

### Impact Explanation
An unprivileged party supplying crafted bytes to `ThresholdKeys::read` can obtain a usable threshold-signing machine for the identity public key and complete a signature without knowing any meaningful private key. Since the identity has no usable discrete logarithm, signatures validating under it should not be producible through the threshold API. This can turn an allegedly threshold-controlled signing path into a universally forgeable key when callers accept attacker-provided or recovered serialized key material.

### Likelihood Explanation
The malicious serialization is deterministic and requires no cryptanalytic work. All fields are public-input-controlled bytes accepted by `ThresholdKeys::read`. The crafted parameters pass the explicit validation because `1 <= t <= n` and the participant index is in range. The only remaining acceptance condition is successful canonical decoding of scalar zero and the identity point.

### Recommendation
Reject identity verification shares during `ThresholdKeys` construction and deserialization. Also validate that the participant’s supplied secret share matches its claimed verification share before constructing `ThresholdKeys`, or return an error when `C::generator() * secret_share != verification_shares[i]`. Reject identity group keys after the group-key calculation.

### Proof of Concept
Construct a serialized `ThresholdKeys<C>` containing:

```text
C::ID length and C::ID
t = 1
n = 1
i = 1
interpolation tag = 1
secret_share = 0
verification_shares[1] = identity
```

Then:

```rust
let keys = ThresholdKeys::<C>::read(&mut malicious_bytes.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::G::identity());

let (machine, preprocess) =
  AlgorithmMachine::new(schnorr_algorithm, keys).preprocess(&mut OsRng);
let (machine, share) = machine.sign(HashMap::new(), message).unwrap();
let signature = machine.complete(HashMap::new()).unwrap();
```

The share is `nonce + challenge * 0`, so the aggregate `R` equals `sum_nonce * G` and the Schnorr equation `sG == R + cA` holds with `A = identity`.
