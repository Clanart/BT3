## Analog Found: First-Depositor Share Inflation on `StreamingYieldVault`

This is a real local analog of the rsETH bug: an ERC-4626 vault whose exchange rate is driven directly by `asset.balanceOf(vault)` rather than pure internal accounting, and whose only anti-inflation defense (a fixed decimals offset) has a bounded protection radius that a sufficiently-funded attacker can exceed.

### Title
First-depositor donation attack defeats the fixed decimals-offset defense in `StreamingYieldVault`, causing victim deposits to round to zero shares - (File: `sdk/packages/core/contracts/vaults/StreamingYieldVault.sol`)

### Summary
`StreamingYieldVault.totalAssets()` is computed as `asset.balanceOf(address(this)) - lockedYield()` [1](#0-0)  — a raw balance read, not an internally tracked deposit ledger. Any direct ERC-20 transfer into the vault (outside of `deposit`/`mint`/`addYield`) immediately inflates `totalAssets`, exactly the "unexpected amount of supported assets" failure mode described in the rsETH report. The vault mitigates the classic empty-vault inflation attack only with a fixed `DECIMALS_OFFSET = 6` virtual-share offset [2](#0-1) , and documentation explicitly states a "seed-and-burn" is still recommended, i.e. the offset alone is known to be incomplete [3](#0-2) . Seeding is not enforced by the contract itself — an unseeded deployment (or, more generally, any deployment where the attacker's available capital exceeds the offset's protection ratio) remains exploitable.

### Finding Description
`_decimalsOffset()` returns a constant `6` [4](#0-3) , which OpenZeppelin's ERC4626 uses as virtual shares/assets in its conversion formula:
```
shares = assets * (totalSupply + 10^offset) / (totalAssets + 1)
```
This only makes the attack unprofitable when the victim's deposit is large relative to the attacker's donation, scaled by `10^offset`. Concretely, on an empty vault:

1. Attacker deposits `1` wei → mints `≈10^6` shares (the virtual-share credit), since `totalSupply` was `0`.
2. Attacker transfers (donates) `D` of the underlying `asset` directly to the vault via a plain `IERC20.transfer`, bypassing `deposit`/`addYield` entirely. `totalAssets()` immediately reflects `1 + D` because `lockedYield()` is `0` outside a vesting window [5](#0-4) .
3. Victim deposits `V`. Their minted shares are `V * (10^6 + 10^6) / (D + 2)`, which floors to `0` whenever `D` is large enough relative to `V` (specifically once `D ≳ 2·10^6·V`).
4. Victim's `V` assets are now inside the vault backing outstanding shares, but the victim holds `0` shares. Attacker redeems and captures the victim's contribution.

The existing test suite only exercises a 1:1 donation-to-deposit ratio (`100 ether` donation vs. `100 ether` victim deposit) [6](#0-5) , which is exactly the regime the `10^6` offset is designed to defend. It does not test the case where the attacker's capital is materially larger than the offset's protection ratio relative to the victim's deposit — the case the docs' "seed-and-burn ... still recommended" caveat is warning about [7](#0-6) . Because seeding is an operational recommendation, not an enforced constructor step, any vault deployed and used before the owner performs the seed-and-burn sequence [8](#0-7)  is exposed to this window.

### Impact Explanation
This is a direct loss-of-funds / wrong-beneficiary path: an unprivileged attacker manipulates the share price on an unseeded (or under-capitalized-relative-to-attacker) vault so that a victim's deposit mints zero (or near-zero) shares, and the attacker captures that value on redemption. No relayer, prover, admin, or malicious peer is required — it is a pure two-transaction (deposit + transfer) attack executable by anyone with sufficient capital and a live deposit window (`maxDeposit`/`maxMint` non-zero, i.e. no tranche currently vesting) [9](#0-8) .

### Likelihood Explanation
Likelihood is bounded by whether operators reliably perform the documented seed-and-burn before real deposits land, and by whether attacker capital can exceed the `10^6` protection ratio relative to real depositor sizes — both are deployment/economic conditions, not code guarantees. Since the contract itself does not enforce seeding and the docs concede the offset alone is insufficient, this is a locally provable, code-level gap rather than a purely theoretical concern.

### Recommendation
- Enforce a mandatory seed-and-burn in the constructor (mint a minimum initial share amount to `address(0xdead)` atomically at deployment) rather than relying on a post-deploy manual step.
- Track deposited/added assets via internal accounting (a running `_totalManagedAssets` incremented only by `deposit`/`mint`/`addYield`) instead of reading raw `asset.balanceOf(address(this))`, so unsolicited transfers cannot move the share price at all.
- If raw-balance accounting must be kept for simplicity, increase the decimals offset and/or add a minimum-shares-out check on `deposit`/`mint` so a call reverts rather than silently minting zero shares.

### Proof of Concept
Using the existing test harness (`sdk/packages/core/test/StreamingYieldVault.t.sol`), replace the `test_InflationAttack_isUnprofitable_andVictimKeptWhole` amounts with an asymmetric ratio:
```solidity
uint256 donation = 2_000_000 ether;   // attacker capital, not "some amount", but sized to exceed 10^6 * victimDeposit
uint256 victimDeposit = 1 ether;      // ordinary victim size

vm.prank(attacker);
vault.deposit(1, attacker);           // 1-wei seed, mints ~10^6 shares

vm.prank(attacker);
asset.transfer(address(vault), donation); // raw donation, no deposit()/addYield()

uint256 victimShares = _deposit(alice, victimDeposit);
assertEq(victimShares, 0, "victim minted zero shares — deposit captured by attacker");
```
With `donation ≳ 2·10^6 · victimDeposit`, `victimShares` rounds to `0`, and the attacker's subsequent `redeem` recovers more than they spent, confirming the analog to the rsETH first-depositor inflation attack is reproducible against `StreamingYieldVault` outside the ratio the current test suite checks.

```text
    function test_InflationAttack_isUnprofitable_andVictimKeptWhole() public {
        uint256 donation = 100 ether;
        uint256 victimDeposit = 100 ether;

        uint256 attackerSpent;

        // 1 wei first deposit.
        vm.prank(attacker);
        vault.deposit(1, attacker);
        attackerSpent += 1;

        // Direct donation to inflate balanceOf (and thus the naive price).
        vm.prank(attacker);
        asset.transfer(address(vault), donation);
        attackerSpent += donation;

        // Victim deposits.
        uint256 victimShares = _deposit(alice, victimDeposit);

        // The offset prevents the victim from being rounded down to nothing.
        assertGt(victimShares, 0, "victim minted zero shares");

        // Attacker unwinds; must not profit from the manipulation.
        uint256 attackerOut = _redeemAll(attacker);
        assertLt(attackerOut, attackerSpent, "attack was profitable");

        // Victim can recover essentially their whole deposit (>= 99%).
        uint256 victimOut = _redeemAll(alice);
        assertGe(victimOut, (victimDeposit * 99) / 100, "victim lost value to the attacker");
    }
```
