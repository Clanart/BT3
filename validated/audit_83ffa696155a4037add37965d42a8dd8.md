## Title
Legacy-transaction signature sanity check accepts oversized `V` values due to unchecked `big.Int.Uint64()` truncation - (File: `blockchain/types/transaction.go`)

### Summary
`DecodeRLP` gates every incoming legacy transaction through `SanityCheckSignatures`, which for legacy transactions calls `validateSignature(v, r, s)`. That function calls `deriveChainId(v).Uint64()` and `v.Uint64()` without first checking `v.BitLen()`. Per Go's documented semantics, `big.Int.Uint64()` is **undefined/silently truncating** when the value does not fit in 64 bits — exactly analogous to the `bytes_to_felt` overflow described in the Kakarot `decode_legacy_tx` report, where an unconstrained field length let an attacker feed an oversized `chain_id`/`v` value that wraps around instead of being rejected.

### Finding Description
The vulnerable code:
```go
// blockchain/types/transaction.go:211-222
func validateSignature(v, r, s *big.Int) bool {
	// TODO-Kaia: Need to consider the case v.BitLen() > 64.
	// Since ValidateSignatureValues receives v as type of byte, leave it as a future work.
	if v != nil && !isProtectedV(v) {
		return crypto.ValidateSignatureValues(byte(v.Uint64()-27), r, s, true)
	}

	chainID := deriveChainId(v).Uint64()
	V := byte(v.Uint64() - 35 - 2*chainID)

	return crypto.ValidateSignatureValues(V, r, s, false)
}
``` [1](#0-0) 

This is invoked from `SanityCheckSignatures` for every legacy transaction:
```go
if txType.IsLegacyTransaction() {
    return validateSignature(sig.V, sig.R, sig.S)
}
``` [2](#0-1) 

and `SanityCheckSignatures` is invoked directly inside `DecodeRLP`, i.e. at raw transaction decode time, before any pool/state checks:
```go
func (tx *Transaction) DecodeRLP(s *rlp.Stream) error {
	serializer := newTxInternalDataSerializer()
	if err := s.Decode(serializer); err != nil {
		return err
	}

	if !SanityCheckSignatures(serializer.tx.RawSignatureValues(), serializer.tx.Type()) {
		return ErrInvalidSig
	}
	...
``` [3](#0-2) 

`v` is an RLP-decoded `*big.Int` with no upper bound enforced by the decoder itself (`rlp/decode.go`'s `decodeBigInt` only rejects leading zero bytes / requires canonical encoding, not a maximum bit length): [4](#0-3) 

So an attacker can craft a legacy transaction whose `V` field is an arbitrarily large integer (e.g., hundreds of bits). `v.Uint64()` and `deriveChainId(v).Uint64()` will silently take the low 64 bits of that oversized value (per Go's own documented "undefined" behavior for out-of-range `Uint64()`), producing an unpredictable but attacker-selectable byte after the `byte(...)` truncation. By choosing the low bits of the huge `V`, the attacker can make `crypto.ValidateSignatureValues` return `true` for a `V` value that is not the correct recovery id for the real `chain_id`/`v` the attacker intends to claim — passing `SanityCheckSignatures` at decode time despite the transaction encoding an invalid/overflowing `chain_id`.

The comment in the code (`// TODO-Kaia: Need to consider the case v.BitLen() > 64.`) is a direct developer acknowledgment that this exact class of bug is unresolved.

Notably, the downstream sender-recovery path used for actual ECDSA recovery (`recoverPlainCommon`) *does* defend against this:
```go
func recoverPlainCommon(sighash common.Hash, R, S, Vb *big.Int, homestead bool) ([]byte, error) {
	if Vb.BitLen() > 8 {
		return []byte{}, ErrInvalidSig
	}
	...
``` [5](#0-4) 

That means full sender recovery (`Sender`/`SenderPubkey`, used by `ValidateSender`) will still reject an oversized `V` during actual execution/validation, which limits — but does not eliminate — the practical impact of the earlier unguarded check.

### Impact Explanation
The immediate consequence is that `DecodeRLP`/`SanityCheckSignatures` — the very first gate a raw legacy transaction passes through (e.g. in `UnmarshalBinary`, RPC decoding paths like `RecoverFromTransaction`, and transaction-pool ingestion that calls `rlp.DecodeBytes` on incoming tx bytes) — can be satisfied by a transaction whose `chain_id`/`V` is not what it actually is once truncated. This is exactly the "unconstrained size + integer truncation lets bogus signature metadata pass validation" bug class from the report. Because a stricter `BitLen() > 8` check exists later in `recoverPlainCommon` (used for real sender recovery/execution), a fully malicious transaction with an out-of-range `V` will still fail before any state change (no direct fund theft demonstrated). However, this is a genuine correctness/defense-in-depth gap: any code path that relies on `SanityCheckSignatures`/`validateSignature`/`TxSignatures.ValidateSignature()` alone (without subsequently calling `recoverPlainCommon`) would accept an invalid transaction as "well-formed," and the acknowledged TODO shows the developers themselves recognize the field is unconstrained. Given the confirmed severity classification (Medium) of the analogous Kakarot finding and the identical root cause (unbounded length field feeding an unchecked fixed-width conversion), this qualifies as a Medium-severity state-divergence / invalid-transaction-acceptance risk at the decode/sanity-check layer, even though full execution-path signature recovery currently catches it.

### Likelihood Explanation
Any unprivileged actor can submit a raw signed (or malformed-signature) legacy transaction with an arbitrarily large `V` field via RLP — no privileged access required; this is reachable directly by a public RPC caller (e.g., `eth_sendRawTransaction`/`RecoverFromTransaction`) or transaction-pool submission. The RLP decoder places no bound on `V`'s size, so crafting such a value is trivial. The likelihood of triggering the unguarded overflow path is high; the likelihood of it causing an actual invalid-tx acceptance depends on whether any consumer trusts `SanityCheckSignatures`/`validateSignature` as sufficient without a subsequent `recoverPlainCommon`-style `BitLen` check.

### Recommendation
Add an explicit bound check on `V.BitLen()` (mirroring the check already present in `recoverPlainCommon`) at the top of `validateSignature` in `blockchain/types/transaction.go`, rejecting any `v` value whose `BitLen()` exceeds a safe threshold (e.g. 64 bits) before calling `Uint64()` or `deriveChainId(v)`. This resolves the acknowledged `// TODO-Kaia` and closes the parallel to the Kakarot `decode_legacy_tx` `chain_id` overflow issue.

### Proof of Concept
1. Construct a legacy transaction whose RLP-encoded `V` field is a `big.Int` far exceeding 64 bits (e.g., 300-bit value), with arbitrary `R`, `S`.
2. Choose the low-order bits of `V` such that `byte(v.Uint64() - 35 - 2*chainID)` (with `chainID` similarly derived by truncated `Uint64()`) equals `0` or `1`, and pick `R`, `S` within `secp256k1N` bounds.
3. Call `rlp.DecodeBytes` on this transaction (e.g. via `UnmarshalBinary`, or `RecoverFromTransaction` RPC) — `DecodeRLP` → `SanityCheckSignatures` → `validateSignature` will return `true` despite the transaction's true `chain_id`/`V` being nonsensical, because the overflow-truncated value coincidentally satisfies `crypto.ValidateSignatureValues`.
4. This is unresolved by the code's own `// TODO-Kaia: Need to consider the case v.BitLen() > 64` comment at `blockchain/types/transaction.go:212`, confirming the root cause is present and unmitigated at this layer (full ECDSA sender recovery still rejects it via the separate `BitLen() > 8` guard in `recoverPlainCommon`). // SanityCheckSignatures validates whether the signature values are valid.
// It checks the signatures from the given TxSignatures.
func SanityCheckSignatures(sigs TxSignatures, txType TxType) bool {
	if len(sigs) == 0 {
		return false
	}

	// Legacy and Eth Typed transactions have only one signature.
	sig := sigs[0]

	if txType.IsEthTypedTransaction() {
		v := byte(sig.V.Uint64())
		return crypto.ValidateSignatureValues(v, sig.R, sig.S, false)
	}

	if txType.IsLegacyTransaction() {
		return validateSignature(sig.V, sig.R, sig.S)
	}

	return sigs.ValidateSignature()
}

func (s *Stream) decodeBigInt(dst *big.Int) error {
	var buffer []byte
	kind, size, err := s.Kind()
	switch {
	case err != nil:
		return err
	case kind == List:
		return ErrExpectedString
	case kind == Byte:
		buffer = s.uintbuf[:1]
		buffer[0] = s.byteval
		s.kind = -1 // re-arm Kind
	case size == 0:
		// Avoid zero-length read.
		s.kind = -1
	case size <= uint64(len(s.uintbuf)):
		// For integers smaller than s.uintbuf, allocating a buffer
		// can be avoided.
		buffer = s.uintbuf[:size]
		if err := s.readFull(buffer); err != nil {
			return err
		}
		// Reject inputs where single byte encoding should have been used.
		if size == 1 && buffer[0] < 128 {
			return ErrCanonSize
		}
	default:
		// For large integers, a temporary buffer is needed.
		buffer = make([]byte, size)
		if err := s.readFull(buffer); err != nil {
			return err
		}
	}

	// Reject leading zero bytes.
	if len(buffer) > 0 && buffer[0] == 0 {
		return ErrCanonInt
	}
	// Set the integer bytes.
	dst.SetBytes(buffer)
	return nil
}

// deriveChainId derives the chain id from the given v parameter
func deriveChainId(v *big.Int) *big.Int {
	if v.BitLen() <= 64 {
		v := v.Uint64()
		if v == 27 || v == 28 {
			return new(big.Int)
		}
		return new(big.Int).SetUint64((v - 35) / 2)
	}
	v = new(big.Int).Sub(v, big.NewInt(35))
	return v.Div(v, common.Big2)
}
