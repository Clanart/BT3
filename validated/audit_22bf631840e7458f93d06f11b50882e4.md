### Title
Index-out-of-bounds panic on malicious FROST peer's short preprocess/share vector crashes the Bitcoin transaction signer - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` assume every peer's `Vec<Preprocess>` / `Vec<SignatureShare>` has the same length as the local `self.sigs` vector. Those vectors are deserialized from raw peer bytes via `read_preprocess` / `read_share`, whose lengths are determined by the *sender's* number of inputs, not the receiver's. A malicious participant who builds their `TransactionMachine` over fewer inputs (or a truncated share list) triggers a panic — the Rust analog of the CVE-2017-11189 NULL-deref crash — in a long-running signing process.

### Finding Description
In `sign`, each peer's preprocess vector is indexed by the local input count `c`:

```rust
// networks/bitcoin/src/wallet/send.rs:364-370
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
```

`commitments[c]` panics if the peer-supplied `Vec<Preprocess>` has fewer than `self.sigs.len()` entries. There is no length check anywhere.

Similarly, `complete` does `shares.remove(0)` per input:

```rust
// networks/bitcoin/src/wallet/send.rs:417-419
let sig = schnorr.complete(
  shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
)?;
```

`Vec::remove(0)` on an empty share vector panics.

Both vectors originate from `read_preprocess` (send.rs:351-353) and `read_share` (send.rs:409-411), which read `self.sigs.len()` items — the *local* machine's count. A peer whose `SignableTransaction` was built with fewer inputs produces a legitimately-shorter vector; nothing enforces that all parties agreed on the same transaction before `sign`/`complete` index into it.

### Impact Explanation
An unprivileged counterparty in a FROST Bitcoin multisig signing session can crash the victim's signer process (panic → abort/thread unwind) simply by sending a preprocess or signature-share vector shorter than the victim's input count. Since these vectors are pure untrusted bytes fed to `read_preprocess`/`read_share`/`sign`/`complete`, the crash is fully attacker-controlled and reachable whenever multisig parties disagree (honestly or maliciously) on the transaction being signed.

### Likelihood Explanation
Any signing peer can trigger it; no cryptographic work is required. The only mitigation is out-of-band agreement on the transaction, which the protocol does not enforce cryptographically at this layer. The panic reliably fires because indexing is unconditional and unchecked.

### Recommendation
Validate lengths before indexing: in `sign`, check `commitments.values().all(|v| v.len() == self.sigs.len())` and return `FrostError` instead of indexing; in `complete`, check `shares.values().all(|v| v.len() == self.tx.input.len())`. Alternatively make `read_preprocess`/`read_share` length-prefix the vector and reject mismatches at deserialization time.

### Proof of Concept
1. Victim builds `SignableTransaction` with N=2 inputs; attacker builds one with 1 input (or crafts a single-element preprocess vec).
2. Victim calls `read_preprocess` on the attacker's bytes — succeeds, producing a `Vec<Preprocess>` of length 1 (attacker's machine only wrote 1).
3. Victim calls `sign(commitments, b"")` → `commitments[1]` on the attacker's length-1 vector → `index out of bounds` panic. Same via `shares.remove(0)` in `complete` with an empty share vec.
