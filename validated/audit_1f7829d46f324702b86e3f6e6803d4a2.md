## Title
Chained-Merkle-Root Consistency Check Is Unconditionally Skipped for Block-ID-Repaired (`Alternate`) Shreds - (File: `ledger/src/blockstore.rs`)

## Summary
The original report describes a bug class where a Merkle-verification routine is gated by a condition that assumes verification has already happened (or will happen) through another code path, and that assumption silently fails for a subset of inputs, letting unverified leaf data be accepted as valid. `Blockstore::check_chained_merkle_root_consistency` in Agave has the same structural pattern: it unconditionally `continue`s (skips the forward/backward chained-Merkle-root checks) whenever shreds are inserted into the `BlockLocation::Alternate` column, based solely on the comment/assumption that such shreds are "already pre verified via merkle proofs before ingest."

## Finding Description
`check_chained_merkle_root_consistency` iterates newly-created `MerkleRootMeta` entries and, for each, is supposed to verify SIMD-0340 forward/backward chaining between adjacent FEC sets: [1](#0-0) 

```
/// Note: This check is not performed on Alternate columns as the shreds are already pre verified.
fn check_chained_merkle_root_consistency(...) {
    ...
    // Note: this check is not performed on Alternate columns as they are already validated
    // via a separate merkle proof on repair ingest
    if !matches!(location, BlockLocation::Original) {
        continue;
    }
    ...
}
```

This mirrors the reported bug precisely: verification of the actual leaf-to-leaf chaining invariant is bypassed via a conditional (`location != Original`), and the correctness of skipping depends entirely on an *assumption*, stated only in a comment, that block-id repair (`BlockIdRepairType::ParentAndFecSetCount` / `FecSetRoot`) already enforced the same invariant before the shred reached `check_chained_merkle_root_consistency`.

Examining `BlockIdRepairType::verify_response` (the "separate merkle proof on repair ingest" referenced by the comment), it only proves two things: [2](#0-1) 
1. That a claimed `parent_info` leaf (bound to `fec_set_count`) is included under the double-Merkle root `block_id`.
2. That a claimed `fec_set_root` at `leaf_index` is included under `block_id`.

Neither of these proofs verifies the SIMD-0340 chained-Merkle-root relationship between *individual* data/coding shreds of adjacent FEC sets — that check is a *separate, intra-slot* invariant computed by `check_forward_chained_merkle_root_consistency`/`check_backwards_chained_merkle_root_consistency`, which compares `shred.merkle_root()` of one FEC set against `shred.chained_merkle_root()` embedded in the next FEC set's shreds: [3](#0-2) 

The double-Merkle proof only proves "this FEC-set root is a leaf of the tree rooted at `block_id`" — it says nothing about whether the *chained_merkle_root* field embedded inside a shred's payload correctly points at the *previous* FEC set's root. That chaining metadata is shred-payload data, not covered by the double-Merkle inclusion proof at all. So for the `Alternate` column, the code skips the one check that actually validates intra-slot chaining consistency, while the "separate merkle proof" it relies on doesn't cover that invariant.

## Impact Explanation
If a block-id repair peer serves internally-inconsistent FEC sets (e.g., shreds whose `chained_merkle_root` do not correctly chain to the previous/next FEC set's actual root) while still supplying valid double-Merkle inclusion proofs for the `parent_info` and `fec_set_root` leaves, the receiving validator's blockstore will accept and store the block in the `Alternate` column without ever running the SIMD-0340 consistency check that would normally have flagged it as a duplicate/dead slot. Since blocks are later promoted from `Alternate` to `Original` via `switch_block_from_alternate` without re-running `check_chained_merkle_root_consistency` (that function is only invoked at insertion time and is unconditionally skipped for `Alternate`), the block can be replayed and confirmed with inconsistent chaining metadata — undermining the duplicate/consistency protections SIMD-0340 was designed to enforce, potentially leading to a validator accepting a block that should have been marked dead/duplicate. This falls in the "false execution/acceptance" impact category.

## Likelihood Explanation
This requires an adversarial or misbehaving block-id-repair server (the peer answering `BlockIdRepairType` requests) to serve a self-consistent-but-chain-inconsistent block, which is a role any gossip peer offering repair can occupy. Because the double-Merkle proof scheme deliberately does not cover the chained-Merkle-root shred-payload field, this is not merely a hypothetical trust gap — the two verification mechanisms are covering genuinely different data. Likelihood is moderate: it is not the default/easy path (an attacker must control an FEC-boundary shred's embedded chaining field while keeping the FEC-set root itself valid under the double-Merkle proof), but no additional privilege beyond being a responsive repair peer is required.

## Recommendation
Do not unconditionally skip `check_chained_merkle_root_consistency` for the `Alternate` column. Either (a) perform the same forward/backward chained-Merkle-root check on `Alternate`-column shreds during insertion (the underlying data is available the same way it is for `Original`), or (b) if skipping is intentional for performance, explicitly verify SIMD-0340 chaining as an additional field folded into the double-Merkle leaf/proof (e.g., include `chained_merkle_root` in the parent-info/fec-set leaf hash) so that the "separate merkle proof on repair ingest" actually covers the invariant being skipped, closing the gap between the assumption and the guarantee.

## Proof of Concept
Conceptual (no test harness available in this pass to fully execute against `check_chained_merkle_root_consistency`, so this is a structural PoC based on code paths cited above):
1. Attacker acts as a block-id repair server. A validator requests `ParentAndFecSetCount`/`FecSetRoot` for a target `block_id`.
2. Attacker crafts FEC set N and FEC set N+1 such that: `fec_set_root(N)` and `fec_set_root(N+1)` are each valid leaves under the double-Merkle root `block_id` (satisfying `verify_response`), but the shreds of FEC set N+1 embed a `chained_merkle_root` that does **not** equal `fec_set_root(N)` (breaking SIMD-0340 chaining).
3. Validator repairs and inserts these shreds via `do_insert_shreds(..., BlockLocation::Alternate { block_id })`.
4. `check_chained_merkle_root_consistency` sees `location != Original` and `continue`s for every entry, so `check_forward_chained_merkle_root_consistency`/`check_backwards_chained_merkle_root_consistency` are never invoked — the chaining defect goes undetected, and the block is accepted/completed in the `Alternate` column, eligible for later `switch_block_from_alternate` promotion.     fn verify_response(&self, response: &Self::Response) -> bool {
        match (self, response) {
            (_, Self::Response::Ping { ping }) => ping.verify(),
            (
                Self::ParentAndFecSetCount {
                    slot: _slot,
                    block_id,
                },
                Self::Response::ParentFecSetCount {
                    fec_set_count,
                    parent_info: (parent_slot, parent_block_id),
                    parent_proof,
                },
            ) => {
                if *fec_set_count > MAX_FEC_SETS_PER_SLOT {
                    return false;
                }

                // + 1 here to account for the parent info which is the final leaf of the tree
                let proof_size = merkle_tree::get_proof_size(*fec_set_count as usize + 1);
                if parent_proof.len()
                    != proof_size as usize * merkle_tree::SIZE_OF_MERKLE_PROOF_ENTRY
                {
                    return false;
                }

                let parent_info_leaf = hashv(&[
                    &parent_slot.to_le_bytes(),
                    parent_block_id.as_ref(),
                    &fec_set_count.to_le_bytes(),
                ]);
                merkle_tree::verify_merkle_proof(
                    parent_info_leaf,
                    *fec_set_count as usize,
                    parent_proof,
                    *block_id,
                )
                .is_ok()
            }

            (
                Self::FecSetRoot {
                    slot: _slot,
                    block_id,
                    fec_set_index,
                },
                Self::Response::FecSetRoot {
                    fec_set_root,
                    fec_set_proof,
                },
            ) => {
                // The double-Merkle tree contains at least one FEC-set root and
                // the parent-info leaf, so a valid proof cannot be empty.
                if fec_set_proof.is_empty() {
                    return false;
                }
                debug_assert_eq!(*fec_set_index as usize % DATA_SHREDS_PER_FEC_BLOCK, 0);
                // Convert from shred-space to leaf-index
                let leaf_index = *fec_set_index as usize / DATA_SHREDS_PER_FEC_BLOCK;
                merkle_tree::verify_merkle_proof(
                    *fec_set_root,
                    leaf_index,
                    fec_set_proof,
                    *block_id,
                )
                .is_ok()
            }

            (Self::ParentAndFecSetCount { .. }, _) | (Self::FecSetRoot { .. }, _) => false,
        }
    }
