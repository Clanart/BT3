### Title
Attacker-controlled participant index in PedPoP blame evaluation panics on unregistered encryption key (DoS) - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The bug class of CVE-2016-5029 — a crafted input causing a crash (NULL dereference in C; an indexing panic in Rust) — maps onto PedPoP's blame machinery. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a `HashMap` `Index` lookup that panics when the `decryptor` `Participant` index was never registered. `blame_internal` (called by `BlameMachine::blame` and `AdditionalBlameMachine::blame`) passes attacker-supplied `sender`/`recipient` values straight through, and the `enc_keys` map provably never contains the evaluating node's own index nor any index `> n`.

### Finding Description
`Decryption::register` inserts into `enc_keys` only when an `EncryptionKeyMessage` for that participant is registered [1](#0-0) . During the DKG, `verify_r1` registers only other participants — the node's own index `i` is skipped via `commitment_msgs.remove(&l)` returning `None` (own commitments are forbidden by `validate_map`) [2](#0-1) . `AdditionalBlameMachine::new` registers exactly `1 ..= n` [3](#0-2) .

`blame` accepts arbitrary `sender`, `recipient`, `msg`, and `proof` [4](#0-3)  and forwards them to `blame_internal` → `decrypt_with_proof` [5](#0-4) . Inside `decrypt_with_proof`, once the message's proof-of-possession signature verifies — which the attacker can satisfy since they craft `msg` (the PoP binds `from`, i.e. the attacker's own claimed sender index) — the code evaluates `self.enc_keys[&decryptor]` while building arguments for `dleq.verify`, panicking before any proof-validity check if `decryptor` is absent [6](#0-5) . An unregistered index is trivially reachable: `recipient` set to the evaluator's own participant index (never in its own `enc_keys`) or, for `AdditionalBlameMachine`, any index `> n`.

A secondary panic exists at `self.commitments[&sender]` in `blame_internal` for an out-of-range `sender`, though reaching it additionally requires a valid DLEq `proof` [7](#0-6) .

### Impact Explanation
An unprivileged DKG participant (or any party able to submit a blame claim to a node/coordinator evaluating PedPoP blame) crashes the evaluating process with a single crafted message. No valid proof is needed: the panic occurs while indexing `enc_keys` before `dleq.verify` runs. This is a remote, input-triggered denial of service directly analogous to the crafted-file NULL dereference of the CVE.

### Likelihood Explanation
The vulnerable index lookup sits on the blame-evaluation path, which exists precisely to process unauthenticated-by-construction accusations. Any `Participant` value fits `sender`/`recipient` with no bounds check against the registered set. The only prerequisite the attacker must satisfy is a valid `SchnorrSignature` PoP over their own `msg.key`, which they produce by generating an `EncryptedMessage` themselves (the wire format is just `key || sig || msg` via `EncryptedMessage::read`/`write`) [8](#0-7) .

### Recommendation
Replace the panicking `HashMap` index with a checked lookup: `let Some(dec_key) = self.enc_keys.get(&decryptor) else { return Err(DecryptionError::InvalidProof) };` in `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:388`). Similarly, use `.get()` for `self.commitments[&sender]` in `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:599`) and treat a missing sender as a faulty/unresolvable accusation rather than panicking.
