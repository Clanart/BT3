### Title
Broken forfeiture accounting permanently starves the redistribution pool, letting unlocking mWomSV holders keep rewards owed to fully-locked holders - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)` and instead sets `rewardableAmount = _amount` directly, so `forfeitAmount` is unconditionally `0`. This is confirmed by comparing it to the sibling contract `vlMGPBaseRewarder._calExpireForfeit`, which correctly multiplies by `vlMGP.getRewardablePercentWAD(_account)`. As a result, `_queueNewRewardsWithoutTransfer` (and thus `rewardInfo.rewardPerTokenStored` bumps from forfeitures) is dead code, and every account that starts/cancels unlocks keeps 100% of rewards proportional to its raw `balanceOf`, instead of a reduced share with the difference redistributed to accounts that stay fully locked.

### Finding Description
`_earned`/`_sendReward` compute a user's reward share purely from `balanceOf(_account)` (total staked mWomSV via `IMasterMagpie.stakingInfo`), with no adjustment for lock vs. cooldown state: [1](#0-0) 

The intended penalty/redistribution mechanism is `_calExpireForfeit`, which in this contract is: [2](#0-1) 

Here `rewardableAmount` is set equal to `_amount` with no call to `mWOMSV.getRewardablePercentWAD(_account)`, so `forfeitAmount = _amount - rewardableAmount` is always `0`. Compare this to the working analogue in `vlMGPBaseRewarder._calExpireForfeit`, which correctly scales `rewardableAmount` by the locker's time-weighted rewardable percentage: [3](#0-2) 

`mWomSV.getRewardablePercentWAD` exists and is designed precisely to reduce the rewardable share of an account currently in cooldown (`startUnlock`) relative to fully-locked accounts, with the shortfall meant to flow back to fully-locked holders via `_queueNewRewardsWithoutTransfer` → `rewardInfo.rewardPerTokenStored` bump: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `_calExpireForfeit` never invokes this percentage, `getRewardablePercentWAD` has zero effect on reward accounting in `mWOMSVBaseRewarder`: any account that calls `startUnlock`/`cancelUnlock` (public, unprivileged functions) continues to accrue the full reward rate on its entire `balanceOf`, exactly as if it were fully locked, and the redistribution channel to fully-locked holders (`rewardInfo.rewardPerTokenStored` increases from forfeitures) never fires. No existing modifier (`nonReentrant`, `whenNotPaused`, `onlyMasterMagpie`) addresses this — it is a pure accounting-logic gap, reachable through the normal `lock`/`startUnlock`/`unlock`/`cancelUnlock` flow that every unprivileged EOA can call.

### Impact Explanation
This is a permanent loss of the yield-boost feature that fully-locked stakers were designed to receive from cooldown/forfeiting stakers. Under correct accounting, cycling accounts should forfeit a portion of rewards proportional to `1 - getRewardablePercentWAD`, and that portion should permanently raise `rewardPerTokenStored` for the benefit of loyal, fully-locked holders. Since forfeiture never triggers, that value is retained by unlocking/cycling accounts instead of being redistributed, causing a real, quantifiable and permanent diversion of unclaimed yield away from fully-locked holders (Immunefi: theft/permanent loss of unclaimed yield).

### Likelihood Explanation
No capital or special privilege is required — any holder of mWomSV can call `startUnlock`/`cancelUnlock`/`unlock` repeatedly (all public/external, unprivileged) to remain in a permanent partial-cooldown state while still earning full reward rate. The bug is deterministic and triggers on every reward claim (`getReward`/`getRewards` → `_sendReward` → `_calExpireForfeit`), so it is 100% repeatable across all reward tokens and all epochs, not a probabilistic or race-condition-dependent exploit.

### Recommendation
Fix `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` to mirror `vlMGPBaseRewarder._calExpireForfeit`: compute `rewardableAmount = _amount * mWOMSV.getRewardablePercentWAD(_account) / 1e18` instead of `rewardableAmount = _amount`, so that accounts with active cooldowns actually forfeit the intended fraction of rewards, which then flows into `_queueNewRewardsWithoutTransfer` and boosts `rewardPerTokenStored` for fully-locked holders.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` (or mocks matching `stakingInfo`) and a reward token.
2. Have User A `lock` a fixed amount and remain fully locked; have User B `lock` an equal amount, then call `startUnlock` for the full amount (never `unlock`/`cancelUnlock`, staying in cooldown for the whole test).
3. Have the reward manager call `queueNewRewards`/`_provisionReward` to add rewards, then have both users call `getReward` repeatedly across multiple cooldown cycles (`startUnlock` → `cancelUnlock` → `startUnlock` for User B).
4. Assert: `rewards[token].rewardPerTokenStored` never increases as a result of any `ForfeitRewardAdded` event (i.e., `_queueNewRewardsWithoutTransfer` is never invoked with a nonzero amount) even though `mWOMSV.getRewardablePercentWAD(userB)` is provably less than `1e18` while B is in cooldown.
5. Assert User B's claimed reward equals the full pro-rata share based on raw `balanceOf`, identical to what User A (fully locked) receives per unit balance — demonstrating User A receives no boosted share despite the forfeiture mechanism's intent, confirming permanent starvation of the redistribution pool.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
