### Title
Unauthenticated `InternalSendTx` broadcasts arbitrary attacker-supplied transactions when the aggregator runs without client-certificate verification - ([File: core/src/servers.rs], [File: core/src/rpc/interceptors.rs], [File: core/src/rpc/aggregator.rs])

### Summary
`ClementineAggregator::internal_send_tx` accepts a caller-supplied raw Bitcoin transaction and unconditionally queues it in `TxSenderClient::insert_try_to_send` for broadcast, with no validation that the transaction originates from any known presigned txhandler. The only gate protecting "Internal*" RPCs is the `only_aggregator_and_self` mTLS interceptor, which is compiled out (`Interceptors::Noop`) whenever `config.client_verification == false` — a configuration that is explicitly supported and even exempted from the mainnet configuration check for the Aggregator actor.

### Finding Description
The intended binding is: *a caller reaching `InternalSendTx` == the aggregator's own client certificate (`our_cert`)*, enforced by `is_internal()`/`only_aggregator_and_self` in [1](#0-0) , [2](#0-1) .

That check only runs inside the `OnlyAggregatorAndSelf` interceptor arm; `create_grpc_server` selects it only `if config.client_verification` is `true`, otherwise it installs `Interceptors::Noop`, which forwards every request unchanged and, critically, also skips setting `client_ca_root` in the TLS config — i.e., no client certificate is required to even complete the TLS handshake: [3](#0-2) .

`BridgeConfig::check_mainnet_requirements` enforces `client_verification == true` only for `cli::Actor::Verifier | cli::Actor::Operator`, explicitly excluding the Aggregator actor from this mainnet safety check: [4](#0-3) . This matches the documented design: "The aggregator does not enforce client certificates but does use TLS for encryption" [5](#0-4) , and `create_aggregator_grpc_server` even logs a warning if `client_verification` is turned *on* for the aggregator, implying `false` is the anticipated/default operational mode: [6](#0-5) .

`internal_send_tx` itself performs zero authorization or content validation beyond deserializing the bytes: [7](#0-6) . It hands the transaction straight to `TxSenderClient::insert_try_to_send`, which only deduplicates by txid and persists the tx for the background sender loop to broadcast — it never checks that the tx spends from a known bridge UTXO, matches a presigned txhandler, or carries a valid N-of-N/committee signature: [8](#0-7) .

Consequently, when the aggregator is deployed with `client_verification = false` (a supported, documented, mainnet-legal configuration for this actor), any network peer that can reach the aggregator's gRPC/TLS port — with no client certificate at all — can call `InternalSendTx(SendTxRequest{raw_tx, fee_type})` with an arbitrary valid Bitcoin transaction and have the aggregator's tx-sender relay/broadcast it. The `is_internal()`/`only_aggregator_and_self` guard the question describes never executes in this mode, so "caller reached InternalSendTx" no longer implies "caller is self."

### Impact Explanation
This is an unauthenticated, network-reachable, state-changing/broadcasting RPC: any unprivileged attacker can force the aggregator to spend its own fee-bumping funds submitting an arbitrary transaction to Bitcoin (fee-paying wallet abuse), and more importantly can inject transactions into the aggregator's persistent tx-sender queue/database with attacker-chosen `fee_type`/`raw_tx` bytes without any signature-of-origin check. While `internal_send_tx` does not by itself let the attacker forge a valid N-of-N signature over a bridge UTXO (Bitcoin consensus still requires a valid script witness to actually spend a UTXO), it is a fully unauthenticated broadcast primitive callable repeatedly across the whole aggregator lifetime — matching the "High: an unauthenticated state-changing or broadcasting call" category in the rules directly, since normal deployments intentionally run the aggregator without client-certificate enforcement.

### Likelihood Explanation
Preconditions: the aggregator must be run with `client_verification = false` (Noop interceptor). This is not merely a test artifact — it is the documented default posture for the aggregator entity (`docs/usage.md`) and is not flagged by `check_mainnet_requirements`, meaning operators can legitimately run this configuration even on mainnet without violating the built-in misconfiguration checks. Attacker cost is negligible: no BTC, no key material, no TLS cert — just network reachability to the aggregator's public port and a syntactically valid signed transaction (which the attacker can construct themselves, e.g. spending their own UTXOs). This is fully repeatable per call.

### Recommendation
Require the `OnlyAggregatorAndSelf`/self-only mTLS check (or an equivalent explicit authentication mechanism) for all `Internal*` aggregator RPCs regardless of the `client_verification` toggle, or make `client_verification=true` mandatory for the Aggregator actor and include it in `check_mainnet_requirements`. Additionally, `internal_send_tx`/`insert_try_to_send` should validate that submitted transactions correspond to a known, previously-generated presigned txhandler (or otherwise strictly whitelist expected transaction shapes) before queuing them for broadcast.

    config: BridgeConfig,

        tracing::warn!("Client verification is enabled on aggregator gRPC server",);

            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }

    pub async fn insert_try_to_send(
        &self,
        dbtx: &mut crate::TxSenderTransaction,
        tx_metadata: Option<TxMetadata>,
        signed_tx: &Transaction,
        fee_paying_type: FeePayingType,
        rbf_signing_info: Option<RbfSigningInfo>,
        cancel_outpoints: &[OutPoint],
        cancel_txids: &[Txid],
        activate_txids: &[ActivatedWithTxid],
        activate_outpoints: &[ActivatedWithOutpoint],
    ) -> Result<u32, BridgeError> {
        let txid = signed_tx.compute_txid();

        // do not add duplicate transactions to the txsender
        let tx_exists = self
            .db
            .check_if_tx_exists_on_txsender(Some(dbtx), txid)
            .await?;
        if let Some(try_to_send_id) = tx_exists {
            return Ok(try_to_send_id);
        }

        tracing::info!(
            "Added tx {} with txid {} to the queue",
            tx_metadata
                .as_ref()
                .map(|data| format!("{:?}", data.tx_type))
                .unwrap_or("N/A".to_string()),
            txid
        );

        let try_to_send_id = self
            .db
            .save_tx(
                dbtx,
                tx_metadata,
                signed_tx,
                fee_paying_type,
                txid,
                rbf_signing_info,
            )
            .await?;
