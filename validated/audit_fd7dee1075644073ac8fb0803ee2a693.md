### Title
Balance desync between EVM StateDB and native bank balances due to shared `BalanceHandler` state across recursive/nested precompile calls - (File: `precompiles/common/balance_handler.go`, `testutil/testdata/debug/debug.go`)

### Summary
The external `batchLiquidateTroves` bug is a "stale-window accounting" class of bug: state computed/consumed based on a marker set at the start of an operation gets silently invalidated or skipped when nested/iterative sub-operations mutate that same marker before the outer operation finishes, causing some deltas to never be reconciled. The Cosmos EVM analog is `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` in `precompiles/common/balance_handler.go`, which records `prevEventsLen` (an event-log cursor) before a precompile call and replays bank events from that cursor afterward to sync `x/bank` coin-spent/received events into the EVM `StateDB` (`stateDB.AddBalance`/`SubBalance`). This is exactly analogous to the liquidation contract recording pre-operation debt/coll snapshots and reconciling them only once, after a loop of sub-operations.

### Finding Description
`BalanceHandler` is a small struct holding a single mutable `prevEventsLen int` field (`precompiles/common/balance_handler.go:38-41`). `BeforeBalanceChange` overwrites `prevEventsLen` with the current event count, and `AfterBalanceChange` later slices `events[bh.prevEventsLen:]` to find bank Coin Spent/Received events to translate into `StateDB.AddBalance`/`SubBalance` calls (`precompiles/common/balance_handler.go:46-105`).

The repository's own test, `evmd/tests/integration/balance_handler/balance_handler_test.go` (`TestRecursivePrecompileCallsWithDebugPrecompile`), is explicitly documented as demonstrating "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" (lines 23-25).

The root cause: if a precompile's `Run` implementation invokes `BeforeBalanceChange`/`AfterBalanceChange` (or the debug precompile / an intermediate contract call) using a shared `BalanceHandler` instance, and that precompile is re-entered recursively (contract → precompile → contract → precompile again) before the outer call's `AfterBalanceChange` executes, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` to a *later* event-log index. When the outer call later executes `AfterBalanceChange`, it uses the now-advanced `prevEventsLen`, silently skipping all bank Coin Spent/Received events that were emitted between the outer call's original starting point and the inner call's start. Those native coin movements are never applied to the EVM `StateDB` via `AddBalance`/`SubBalance` — exactly mirroring how `batchLiquidateTroves` computes debt/coll from a pre-loop snapshot and skips reconciling changes made by earlier iterations before redistributing.

The stateful precompile wrapper in `precompiles/common/precompile.go` (`runNativeAction`) does create a **new** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` (lines 99-102), which appears to be a mitigation for most standard precompiles (staking, distribution, gov, slashing, erc20, ics20 each reference `BalanceHandlerFactory`/`GetBalanceHandler` per the grep results). However, the debug/test precompile (`testutil/testdata/debug/debug.go`) calls `p.GetBalanceHandler()` directly rather than instantiating a fresh handler per call, and the dedicated regression test confirms this exact failure mode occurs when the same `BalanceHandler` instance is reused/shared across a nested call chain.

### Impact Explanation
If any reachable path allows a shared `BalanceHandler` instance to be reused across nested/recursive precompile invocations within a single EVM call (e.g., an unprivileged user calls a contract that re-enters a precompile via callback/try-catch, similar to the `StakingReverter` recursive patterns already present in the test suite), native bank coin movements that legitimately occurred can be dropped from `StateDB` reconciliation. This produces a state divergence between the true `x/bank` balance and the EVM-visible balance for an account — the EVM `StateDB.balance` could under- or over-represent actual spendable native funds. Because `StateDB` balance is authoritative for subsequent EVM balance checks/transfers within that same transaction (and gets committed to the multi-store), this can lead to unauthorized minting/duplication of spendable EVM balance (StateDB balance higher than actual bank balance, permitting further spends not backed by real funds) or permanent loss/freezing of value (StateDB balance lower than actual, effectively freezing part of a user's funds from EVM-visible use) — matching the Critical "unauthorized minting/duplication" and "permanent freezing" impact gates for balance/accounting corruption across native and EVM balances.

### Likelihood Explanation
This requires a specific trigger: nested/recursive re-entry into a stateful precompile from within the execution of another stateful precompile call, using a code path where the `BalanceHandler` instance is not freshly allocated per invocation (as seen in the debug precompile, and potentially in other custom or future precompile plumbing that doesn't go through `runNativeAction`'s per-call `NewBalanceHandler()`). The core `precompiles/common/precompile.go` `runNativeAction` path for the standard shipped precompiles (staking/distribution/gov/slashing/erc20/ics20) does create a new handler per call, which appears to mitigate the issue for those specific precompiles. I could not fully verify (due to running out of tool iterations) whether any of those standard precompiles' `Run` methods bypass `runNativeAction` in a nested-call scenario, or whether a shared/cached `BalanceHandler` could otherwise be reintroduced by call structure (e.g. via `RunNativeAction` being invoked with a handler captured by closure across reentrant frames). The presence of a dedicated, named regression test for this exact bug in the codebase strongly suggests it is a known, real, previously (or currently) triggerable issue, but I cannot confirm from the available index whether it is fully patched in the current production precompile set.

### Recommendation
- Ensure every precompile entry point (not just those going through `runNativeAction`) allocates a fresh `BalanceHandler` per top-level EVM call and correctly threads it through all nested precompile invocations so `prevEventsLen` snapshots and their corresponding event replays are strictly nested (stack-based), never overwritten by an inner call before the outer call's events are reconciled.
- Replace the single `prevEventsLen int` field with a stack (or track a nesting depth/snapshot-scoped cursor) so `AfterBalanceChange` can be called safely at any nesting level without clobbering an outer frame's starting cursor.
- Add an invariant check/assertion that after each precompile call completes, the sum of `StateDB`-tracked balance deltas equals the sum of bank Coin Spent/Received events observed during that call's execution window, failing loudly (reverting) on mismatch rather than silently dropping events.
- Extend the existing `TestRecursivePrecompileCallsWithDebugPrecompile`-style test to cover all production precompiles (staking, distribution, gov, slashing, erc20, ics20) with genuine recursive/reentrant call chains to confirm none of them can share a `BalanceHandler` instance across nested invocations.

### Proof of Concept
The repository already contains a working PoC demonstrating the underlying mechanism: `evmd/tests/integration/balance_handler/balance_handler_test.go`, `TestRecursivePrecompileCallsWithDebugPrecompile` (lines 43-106). It deploys a `DebugPrecompileCaller` contract that triggers recursive calls into the debug precompile sharing one `BalanceHandler` instance, and asserts on the resulting event counts to show the desync (`debug_count` expected to equal 10 out of 15 total events, i.e., not all balance-change events are processed 1:1 with expectations). The same recursive-call construction pattern used against a production stateful precompile (e.g., via `try/catch` re-entrancy as already exercised in `contracts/solidity/precompiles/testutil/contracts/StakingReverter.sol`'s `nestedTryCatchDelegations`/`callPrecompileBeforeAndAfterRevert`, combined with a bank-balance-moving precompile call) would need to be adapted to confirm whether the shared-handler condition is reachable in a currently shipped precompile; this was not verified before running out of investigation budget. type BalanceHandler struct {
	bankKeeper    BankKeeper

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
