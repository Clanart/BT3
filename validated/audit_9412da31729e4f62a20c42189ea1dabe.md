### Title
Deserialized verification shares permit the identity point, enabling share-verification griefing and zero-share forgery - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` reads each participant's verification share with `<C as Ciphersuite>::read_G`, which accepts the identity point, and `ThresholdKeys::new` performs no identity check on `verification_shares` values. An attacker who supplies crafted `ThresholdKeys` bytes can embed an identity verification share. Under `SchnorrSignature::batch_statements`, a signature share verified against an identity key reduces to `R - sG == 0`, so an identity share causes honest shares to be rejected (griefing) or lets a party with no secret produce a validly-verifying share — the direct analog of an unchecked zero recovered-signer being accepted.

### Finding Description
The external report describes `ECDSA.recover` returning the zero address being accepted as a valid `order.signer`. In Serai the analogous trust boundary is `ThresholdKeys::read`, which reconstructs a full set of threshold keys from untrusted bytes, including the `verification_shares` map that later gates whether a participant's signature share is accepted.

`ThresholdKeys::read` deserializes verification shares via `<C as Ciphersuite>::read_G` at `crypto/dkg/src/lib.rs:620-623`. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces canonical, on-curve encodings; it does not reject the identity. The identity-rejecting wrapper `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) is not used here, nor in `GeneratorProof::read` (`crypto/dkg/promote/src/lib.rs:72-77`) or `SchnorrSignature::read` (`crypto/schnorr/src/lib.rs:51-53`).

`ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) validates only the count of shares, that participant indexes are `<= n`, and the interpolation method — never that verification shares are non-identity. `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:500-521`) then interpolates these shares directly into `ThresholdView::verification_shares`, which FROST's `verify_share` consumes (`crypto/frost/src/algorithm.rs:219-230`) via `SchnorrSignature::batch_statements` (`crypto/schnorr/src/lib.rs:88-99`): the check is `R + c·Y_i - sG == 0`. When `Y_i` is identity, `c·Y_i == 0`, so the equation degenerates to `R == sG`, which the submitter controls entirely through their nonce.

### Impact Explanation
Two concrete impacts for the party deserializing attacker-crafted `ThresholdKeys` (explicitly in-scope as an untrusted-bytes entry point):

- **Forged share acceptance**: a participant whose verification share is set to identity can submit `share = d + e·rho` (pure nonce, no secret share knowledge) and pass `verify_share`, contributing to a signature without possessing any secret material for the group key.
- **Griefing**: if the victim's own verification share is replaced with identity while their `secret_share` is a real nonzero share, their honestly-computed share fails `R + c·Y_i - sG == 0` (the `c·share` term is silently dropped), so every signing session involving them produces `InvalidShare`/blame — a persistent, unrecoverable signing DoS indistinguishable from the victim cheating.

### Likelihood Explanation
Reachable whenever `ThresholdKeys::read` processes externally-supplied bytes (key backup/restore, peer-provided key material, coordinator distribution). The attack requires no hash collisions, no collusion, and no timing: `Ciphersuite::read_G` accepts the canonical identity encoding, `ThresholdKeys::new` never inspects share values, and the verification equation algebraically degenerates for identity keys. The constraint that limits severity is that the attacker must control the deserialized key material rather than injecting a single field into an otherwise-trusted structure.

### Recommendation
In `ThresholdKeys::read` (and any other deserialization of untrusted points used as keys/shares — `GeneratorProof::read`, `Commitments::read` in PedPoP), use the identity-rejecting `Curve::read_G` or add an explicit `is_identity` check in `ThresholdKeys::new` for every `verification_shares` value, rejecting identity shares before they reach `view()`/`verify_share`.
