### Title
Hookify `contains`/`not_contains`/`regex_match` rule matching operates on raw, unparsed shell text and is trivially bypassed by shell-quoting/escaping tricks, letting a blocked destructive command (e.g. `rm -rf`) execute unmodified while the block rule silently fails to fire - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._check_condition` and `_regex_match` in `plugins/hookify/core/rule_engine.py` compare the literal `command` string against a user-authored pattern using plain Python substring/regex operations, with no shell-aware tokenization or canonicalization step. Because the shell (`bash -c "<command>"`) removes quotes/escapes at execution time but the rule engine sees the pre-parsed, quoted text, a command can be re-written (e.g. `r'm' -rf /`, `r\m -rf /`, `${IFS}`-based splitting) so that it no longer contains the literal pattern text the rule was written to catch, yet still executes identically to the blocked command once bash parses it.

### Finding Description
`load_rules`/`Condition` supports simple patterns and multi-condition rules keyed on fields like `command` [1](#0-0) , and `RuleEngine._check_condition` dispatches these to plain Python operators: `pattern in field_value` for `contains`, `pattern not in field_value` for `not_contains`, and `_regex_match` (an `re.search` over the cached compiled pattern) for `regex_match` [2](#0-1) . `_regex_match` performs no normalization of the input text before matching [3](#0-2) .

The `command` field fed into this engine is the exact `tool_input.command` string from the `PreToolUse`/`PostToolUse` hook JSON, taken verbatim from stdin and passed straight to `RuleEngine.evaluate_rules` [4](#0-3) . This is the same string that Claude Code's Bash tool subsequently executes via the shell. Because the shell interprets quoting/escaping/variable-splitting at execution time (after the hook has already approved it), an attacker-controlled or prompt-injected command such as `r'm' -rf /important/dir` or `r\m -rf /important/dir` does **not** contain the substring `rm -rf` and will not match a rule like `pattern: rm\s+-rf` / `operator: contains, pattern: rm -rf` / `operator: not_contains` used to guard it, yet once handed to `bash -c`, the quotes/backslash are stripped and the command executes as literal `rm -rf /important/dir`.

The "Unicode homoglyph" and "null byte" framing in the question is not itself a viable bypass: `execve`/PATH lookup requires an actual byte-identical program name, so a homoglyph "гm -rf" or a command containing an embedded NUL would not actually invoke `/bin/rm` — it would fail with "command not found" rather than delete anything. The genuinely exploitable variant of this same root cause is shell-quoting/escaping obfuscation, which achieves exactly the "matches at OS execution time but not at the literal-pattern check" property the question is probing for.

### Impact Explanation
Any user-authored hookify `block` rule intended to stop destructive commands (the README's own canonical example, `pattern: rm\s+-rf`, `action: block`) can be silently bypassed with a trivially rewritten but semantically identical command, allowing unauthorized destructive filesystem operations to execute even though the user explicitly configured a control to deny them. This is an "unauthorized command execution" / security-control bypass matching the bounty category of bypassing an enforced deny/block decision, scoped to installations relying on hookify's block rules as a safety net (e.g., paired with auto-approved/YOLO Bash execution settings, where hookify's `permissionDecision: deny` is the only remaining gate).

### Likelihood Explanation
No special privilege is required — a prompt-injected instruction from ordinary repository content (malicious file, PR/issue text) that causes Claude to run a lightly-obfuscated shell command is sufficient. Shell quote-splitting/backslash-escaping is a well-known, mechanical technique with no need for exotic encodings, making this trivially repeatable against any `contains`/`not_contains`/`regex_match` rule that does naive literal/regex matching over unparsed command text.

### Recommendation
Do not rely on raw substring/regex matching over unparsed shell text for security-relevant `block` rules. At minimum:
- Document prominently in `README.md`/`SKILL.md` that hookify pattern rules are a best-effort heuristic and are not a hard security boundary against shell obfuscation.
- Consider shell-aware normalization before matching (e.g., tokenize with `shlex`/a shell parser, or execute `bash -n`/`printf %q`-style canonicalization) so that quote/escape variants of a matched command are normalized to the same form before applying `contains`/`regex_match`.
- For `not_contains`/`contains`, consider case-insensitive, whitespace/quote-stripped comparison as a minimum improvement, and warn users that regex-only rules like `rm\s+-rf` are inherently bypassable.

### Proof of Concept
Unit test to add to `plugins/hookify/core/rule_engine.py`'s test harness or a new `tests/test_rule_engine_bypass.py`:
```python
from hookify.core.config_loader import Condition, Rule
from hookify.core.rule_engine import RuleEngine

def test_quote_split_bypasses_contains_block_rule():
    rule = Rule(
        name="block-rm-rf",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="contains", pattern="rm -rf")],
    )
    engine = RuleEngine()

    # Obfuscated command: bash strips the quote, executes identical to "rm -rf /tmp/x"
    obfuscated_input = {
        "tool_name": "Bash",
        "tool_input": {"command": "r'm' -rf /tmp/x"},
    }
    result = engine.evaluate_rules([rule], obfuscated_input)
    # Expected (desired) behavior: rule should still block
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", (
        "Block rule silently bypassed: obfuscated command not detected, "
        "but bash would execute it identically to 'rm -rf /tmp/x'"
    )
```
Running this against current `_check_condition` shows `evaluate_rules` returns `{}` (no match, operation allowed) for the obfuscated command, while a real shell invocation of `bash -c "r'm' -rf /tmp/x"` executes `rm -rf /tmp/x`, confirming the block rule silently fails to trigger for a semantically identical destructive command. Extend with additional variants (`r\m -rf`, `"rm" -rf`, `${x:-rm} -rf`) to fuzz the same gap in `regex_match`/`not_contains`.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)

            return bool(regex.search(text))
