## Analysis

The reported Monero bug is a classic **uncontrolled resource consumption from an attacker‑controlled size value**: a value taken from untrusted, attacker‑supplied data (`tx_hashes.size()`) is used to size an allocation with no upper bound, and that lack of a cap crashes the process when the attacker inflates the value.

GitHub Desktop already hit and fixed an almost identical class of bug: git output being unbounded. This was patched in `app/src/lib/git/core.ts` by capping the git process's `maxBuffer` at `kStringMaxLength` for the default (string) path (changelog: "Cap output from git at string max length" / "Prevent crash due to excessively long Git output", #19724). However, that fix has a gap: the cap is only applied when the caller uses the default `string` encoding. For callers that request `encoding: 'buffer'`, the cap is explicitly disabled. [1](#0-0) 

`getCommits`, the function that builds the commit history shown to the user from `git log`, is one such caller — it explicitly requests `encoding: 'buffer'`: [2](#0-1) 

Because `maxBuffer` is `Infinity` on this path, Node/dugite will happily buffer the *entire* raw `git log` output — regardless of how large a malicious or corrupted remote/cloned repository's history metadata (huge number of commits, oversized commit bodies/trailers/refs, etc.) is — before any of GitHub Desktop's own truncation logic (e.g. the `subarray(0, 100 * 1024)` calls applied to `commit.summary`/`commit.body`) ever runs: [3](#0-2) 

The truncation only clips per-field values *after* the whole (unbounded) buffer has already been read into memory and split by the parser — it does not prevent the initial unbounded allocation, so it doesn't mitigate the resource-exhaustion primitive itself.

### Title
Uncontrolled memory growth reading `git log` output due to disabled `maxBuffer` cap on buffer-encoded Git calls - (File: app/src/lib/git/core.ts)

### Summary
`git()` in `app/src/lib/git/core.ts` caps `maxBuffer` to `kStringMaxLength` only for string-encoded output; for `encoding: 'buffer'` calls it sets `maxBuffer: Infinity`, removing the size cap entirely. `getCommits()` (`app/src/lib/git/log.ts`) uses `encoding: 'buffer'` to read `git log` output, so the full history text is buffered into memory with no upper bound before any of the app's own field-level truncation is applied.

### Finding Description
Desktop's own fix for issue #19724 recognized that "excessively long Git output" can crash the app, and added a `maxBuffer` cap using `kStringMaxLength` for the common (string) execution path in `git()`. The same function, however, computes the cap conditionally:
```
maxBuffer: options?.encoding === 'buffer' ? Infinity : kStringMaxLength,
```
`getCommits()` opts into `encoding: 'buffer'` when running `git log`, so this specific call is exempt from the fixed cap. The size of `git log`'s stdout is driven entirely by repository content that is not controlled by the local user when the repository was cloned or fetched from an attacker-controlled remote: number of commits, commit body length, trailers, and refs are all attacker-influenceable. Downstream, `getCommits()` does apply `subarray(0, 100*1024)` to `summary`/`body`, but that only bounds individual field sizes after the entire buffer has been received and parsed — it does not bound the total buffer size consumed while git is producing output.

### Impact Explanation
A crafted remote/cloned repository (e.g. one with an enormous number of commits, or commits with abnormally large commit-message bodies/trailers across the whole history) can force GitHub Desktop to buffer an effectively unbounded amount of data in memory when the user simply opens the repository or views history (`getCommits`). This can exhaust process memory and crash the app (renderer/main process), which is the same "Uncontrolled Resource Consumption" outcome as the Monero report, and it is exactly the failure mode the earlier #19724 fix set out to prevent — just left unmitigated on this particular buffer-encoded call path.

### Likelihood Explanation
`getCommits` is invoked automatically as part of normal repository loading/history browsing, requiring no unusual user action beyond adding/cloning/fetching an attacker-supplied repository — which is within the accepted threat model (attacker controls a cloned/fetched repository). No admin rights, local access, or social engineering beyond pointing Desktop at the malicious repo is required.

### Recommendation
Apply the same `maxBuffer` bound (or an explicit, sane cap) to buffer-encoded git invocations as is applied to string-encoded ones, rather than setting it to `Infinity`. At minimum, `getCommits`/`git log` buffer reads should be capped, with graceful handling (e.g. truncation with a warning, or fetching history in bounded batches) instead of unbounded accumulation.

### Proof of Concept
1. Create/host a Git repository with an extremely large number of commits and/or commits containing very large bodies/trailers (attacker controls remote content).
2. Have the victim clone/fetch this repository into GitHub Desktop and open its history view, which triggers `getCommits()` → `git(['log', ...], repo.path, 'getCommits', { encoding: 'buffer' })`.
3. Because `maxBuffer` is `Infinity` for this call, dugite/Node will buffer the entire oversized `git log` output in memory before `parse()`/truncation ever runs, leading to excessive memory consumption and a crash — mirroring the unbounded-allocation crash described in the Monero report. export async function getCommits(
  repository: Repository,
  revisionRange?: string,
  limit?: number,
  skip?: number,
  additionalArgs: ReadonlyArray<string> = []
): Promise<ReadonlyArray<Commit>> {
  const { formatArgs, parse } = createLogParser({
    sha: '%H', // SHA
    shortSha: '%h', // short SHA
    summary: '%s', // summary
    body: '%b', // body
    // author identity string, matching format of GIT_AUTHOR_IDENT.
    //   author name <author email> <author date>
    // author date format dependent on --date arg, should be raw
    author: '%an <%ae> %ad',
    committer: '%cn <%ce> %cd',
    parents: '%P', // parent SHAs,
    trailers: '%(trailers:unfold,only)',
    refs: '%D',
  })

  const args = ['log']

  if (revisionRange !== undefined) {
    args.push(revisionRange)
  }

  args.push('--date=raw')

  if (limit !== undefined) {
    args.push(`--max-count=${limit}`)
  }

  if (skip !== undefined) {
    args.push(`--skip=${skip}`)
  }

  args.push(
    ...formatArgs,
    '--no-show-signature',
    '--no-color',
    ...additionalArgs,
    '--'
  )
  const result = await git(args, repository.path, 'getCommits', {
    successExitCodes: new Set([0, 128]),
    encoding: 'buffer',
  })

  // if the repository has an unborn HEAD, return an empty history of commits
  if (result.exitCode === 128) {
    return new Array<Commit>()
  }

  const parsed = parse(result.stdout)

  return parsed.map(commit => {
    // Ref is of the format: (HEAD -> master, tag: some-tag-name, tag: some-other-tag,with-a-comma, origin/master, origin/HEAD)
    // Refs are comma separated, but some like tags can also contain commas in the name, so we split on the pattern ", " and then
    // check each ref for the tag prefix. We used to use the regex /tag: ([^\s,]+)/g)`, but will clip a tag with a comma short.
    const tags = commit.refs
      .toString()
      .split(', ')
      .flatMap(ref => (ref.startsWith('tag: ') ? ref.substring(5) : []))

    return new Commit(
      commit.sha.toString(),
      commit.shortSha.toString(),
      commit.summary.subarray(0, 100 * 1024).toString(),
      commit.body.subarray(0, 100 * 1024).toString(),
      CommitIdentity.parseIdentity(commit.author.toString()),
      CommitIdentity.parseIdentity(commit.committer.toString()),
      commit.parents.length > 0 ? commit.parents.toString().split(' ') : [],
      // We know for sure that the trailer separator will be ':' since we got
      // them from %(trailers:unfold) above, see `git help log`:
      //
      //   "key_value_separator=<SEP>: specify a separator inserted between
      //    trailer lines. When this option is not given each trailer key-value
      //    pair is separated by ": ". Otherwise it shares the same semantics as
      //    separator=<SEP> above."
      parseRawUnfoldedTrailers(commit.trailers.toString(), ':'),
      tags
    )
  })
}
