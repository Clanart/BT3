### Title
Authentication bypass via unregistered-chain fallback lets any Hyperbridge-connected chain drain IntentGateway escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`instance()` in the Tron `IntentGatewayV2` returns `address(this)` whenever no peer gateway is registered for a state machine, instead of reverting. `authenticate()` uses this value to validate the `from` field of incoming ISMP `PostRequest`s. Any contract on any chain that Hyperbridge has connected consensus for — but for which this specific IntentGateway deployment has never called `_addDeployment`/`NewDeployment` — can dispatch a `PostRequest` whose `from` field equals the gateway's own address. `authenticate()` will treat that spoofed message as coming from "itself," passing the check, and `onAccept` will execute an attacker-crafted `RedeemEscrow`/`RefundEscrow` `WithdrawalRequest` naming an arbitrary existing `commitment`, token, amount, and beneficiary.

### Finding Description
The `_instances` mapping records known peer `IntentGatewayV2` deployments per state machine, populated only via governance-authenticated `NewDeployment` messages. `instance()` is supposed to answer "who is the trusted counterpart on chain X"; when the mapping is empty, the correct answer is "nobody" (as correctly implemented with `revert UnknownInstance()` in the sibling `IntentsBase.sol` used by the primary EVM deployment). The Tron variant instead defaults to `address(this)`, meaning it implicitly trusts a peer that was never configured.

Since ISMP `from`/`source` fields are populated by the sender's own dispatch call on the source chain (any external contract can set `from` to any 20-byte value it likes when it calls its local host's `dispatch`), an attacker deploys a trivial contract on any chain connected to Hyperbridge's consensus (but not registered in `_instances` for this specific gateway) and dispatches a `PostRequest` with `from = address(intentGatewayOnTargetChain)` and body `RedeemEscrow`/`RefundEscrow` encoding a `WithdrawalRequest{commitment: <any real order's commitment>, tokens: [...], beneficiary: attacker}`. The message passes normal Hyperbridge consensus/state proof verification (it is a genuine message from a genuinely connected chain), reaches `onAccept`, and `authenticate()` incorrectly accepts it because `instance(request.source) == address(this) == module`.

`withdraw()` only checks `_orders[commitment][token] != 0` (nonzero), not that the caller is entitled to that specific order or that the amount is properly bounded to what remains for the legitimate flow — the entire trust boundary was supposed to be enforced by `authenticate()`, which has been bypassed.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance" categories: escrowed user funds sitting in `_orders[commitment][token]` for any pending cross-chain order can be redirected to an attacker-chosen beneficiary, or an order can be force-refunded/finalized prematurely, without any relayer, prover, or admin compromise — only an unregistered, ordinary chain connected to the same Hyperbridge instance, which the attacker fully controls as a normal user of that chain.

### Likelihood Explanation
Requires only deploying an unprivileged contract on any Hyperbridge-connected chain and dispatching a message through the standard, permissionless ISMP `dispatch` path — no relayer collusion, no governance key, no malicious prover. The only precondition is that this specific `IntentGatewayV2` instance has not registered a peer for that chain, which is the default/likely state for any newly connected or lesser-used chain in a multi-chain deployment.

### Recommendation
Change `instance()` to revert (e.g., `revert UnknownInstance()`) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the `_instance()` implementation already used in `evm/src/apps/intentsv2/IntentsBase.sol`. Never fall back to `address(this)` as an implicit trust anchor for unconfigured chains.

### Proof of Concept
1. Governance never calls the Tron gateway's registration path for state machine `X` (so `_instances[keccak256(X)] == address(0)`).
2. Attacker deploys `EvilSender` on chain `X` and calls `X`'s ISMP host `dispatch(PostRequest{ from: abi.encodePacked(intentGatewayTron), to: abi.encodePacked(intentGatewayTron), source: X, body: abi.encodePacked(uint8(RequestKind.RedeemEscrow), abi.encode(WithdrawalRequest{ commitment: knownRealCommitment, tokens: [existingEscrowedToken], beneficiary: attackerAddress })) })`.
3. Hyperbridge relayer (a normal, honest relayer) delivers this legitimately-proven message; `onAccept` is invoked on the Tron `IntentGatewayV2`.
4. `authenticate()` computes `instance(X) == address(this)` (fallback) and compares to `module == intentGatewayTron == address(this)` → passes.
5. `withdraw()` transfers the escrowed tokens for `knownRealCommitment` to `attackerAddress`, even though the attacker had no relationship to that order. [2](#0-1) [3](#0-2) [4](#0-3) [1](#0-0)
