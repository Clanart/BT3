### Title
Peer-supplied identity nonce commitment triggers panic in BIP-340 HRAm during FROST signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
The original bug class is a peer-reachable panic on an unhandled invalid/empty state (`history_index().unwrap()`). The Serai analog is the `x()`/`x_only()` helpers in `networks/bitcoin/src/crypto.rs`, which `expect()` that a point is not the point at infinity. This assumption is violated by public input: `Commitments::read` (reached via `AlgorithmSignMachine::read_preprocess`) deserializes nonce commitments with `C::read_G` without an identity check, and `sign()`/`complete()` feed the resulting combined nonce point `R` into `Hram::hram`, which calls `x(R)` and `x(A)`. A co-signing participant who submits a preprocess whose binding-adjusted nonce commitment sums to the point at infinity crashes every other signer's `sign_share`/`verify_share` path. [1](#0-0) 

### Finding Description
- `x()` does `key.to_encoded_point(true)` then `.x().expect("point at infinity")` — for `ProjectivePoint::IDENTITY`, `to_encoded_point` yields the SEC1 infinity encoding whose `x()` is `None`, so it panics. `x_only` and `needs_negation` document "Panics on invalid input." [2](#0-1) 
- `Hram::hram` calls `x(R)` and `x(A)` unconditionally. It is invoked from `Schnorr::sign_share` (via `FrostSchnorr::sign_share`, `H::hram(&nonce_sums[0][0], ...)` at `crypto/frost/src/algorithm.rs:208`) and transitively from `verify`/`verify_share` in `complete()`. [3](#0-2) [4](#0-3) 
- `nonce_sums[0][0]` (`Rs`) is computed in `AlgorithmSignMachine::sign` from `B.nonces(&nonces)`, i.e., the sum over all included participants of `D_l + rho_l * E_l`. These commitments arrive as raw bytes over `read_preprocess` → `Commitments::read` → `C::read_G`, with no rejection of the identity or small-order/constructed points in `sign.rs` before the points are summed and consumed. [5](#0-4) [6](#0-5) 
- An attacker controlling one participant index can craft preprocess commitment points such that the binding-weighted sum `R` is the identity (e.g., send commitments `D = identity`, `E` chosen so `rho * E` cancels the honest contributions; the binding factor `rho` is deterministic given the transcript, which the attacker can predict for a known message and participant set, or simply brute-force/adaptively choose commitments so the aggregate is infinity). The same identity result can be achieved trivially if `read_G` accepts the SEC1 infinity encoding (`0x00`) directly, letting the attacker submit identity commitments outright. I was unable to fully verify whether `read_G` for `Secp256k1` (kp256) accepts the infinity encoding, but the combined-sum-to-identity path does not depend on it — only on the attacker's commitment being an arbitrary valid point, which `read_G` permits.
- On crash path 1, `sign()` calls `sign_share` → `hram` → `x(R)` → panic, aborting the honest signer's process. On crash path 2, the honest node survives `sign` only if `R` is non-identity but `group_key` (controllable via key-aggregation offsets/participant keys) is identity — `x(A)` then panics.

### Impact Explanation
Any participant in a FROST signing session can remotely panic every other honest signer (and the aggregator in `complete()`, which calls `self.params.algorithm.verify` and `verify_share` → `batch_statements` → the same `hram`-based challenge), permanently halting threshold signing for the bitcoin-serai Schnorr algorithm. This is a network-reachable denial of service on the critical signing path, matching the CVE's `A:L`/medium shape: a peer triggers a panic on a path that assumed an input-validity invariant that was never enforced.

### Likelihood Explanation
Preprocess messages are explicitly untrusted bytes (`read_preprocess` is listed as an attack surface), and FROST's security model already assumes malicious co-signers. Triggering the panic only requires producing commitments whose bound sum is infinity — feasible since the attacker sees/controls the message and can compute `rho` for a chosen signing set. No secret leakage is needed; the attack needs no privileged position beyond being one of the `n` participants. The `bitcoin::Schnorr` docs even concede "This may panic if called with nonces/a group key which are the point at infinity," acknowledging the missing check but treating it as negligible — which is false when participants are adversarial and `rho` is deterministic. [7](#0-6) 

### Recommendation
- In `Hram::hram` / `x()`, return a `Result`/use `Option` and propagate an error instead of `expect()`; or earlier, in `Commitments::read`/`B.nonces`, reject the identity point and reject an `Rs` aggregate that is identity, returning `FrostError::InvalidCommitment`-style errors.
- In `complete()`, treat an identity `R` as an invalid-share condition attributable to the contributing participant rather than panicking.
- Reject identity encodings in `C::read_G` for secp256k1 (defense in depth; does not by itself fix the aggregate-sum case).

### Proof of Concept
```rust
// Attacker is participant j in the signing set. For a known msg and set of
// included participants, compute the rho transcript as in sign() and choose
// commitment points such that sum_l (D_l + rho_l * E_l) == ProjectivePoint::IDENTITY.
// Simplest instantiation: submit a preprocess whose commitment encodes the
// identity point directly (SEC1 0x00), or pick E_j = -(1/rho_j) * sum_of_others.
// Honest signer then executes:
let preprocess = sign_machine.read_preprocess(&mut attacker_bytes)?; // Commitments::read -> C::read_G
let mut map = HashMap::new();
map.insert(attacker, preprocess);
sign_machine.sign(map, b"tx digest")?; // -> B.nonces -> Rs[0][0] == IDENTITY
                                      // -> Schnorr::sign_share -> Hram::hram -> x(R)
                                      // -> encoded.x().expect("point at infinity") PANIC
```
The panic occurs deterministically inside `x()` at `networks/bitcoin/src/crypto.rs:15` once `Rs[0][0]` (or `A`) is the point at infinity, crashing the signer before any share is produced.

      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
