## Title
Fee-in-native-token swaps in `placeOrder`/`IntentGatewayV2` and the cross-chain fee quoting path rely on a single hardcoded Uniswap V3 fee tier with no minimum-liquidity or slippage-invariant check, allowing an attacker-created low-liquidity pool to manipulate the amount of native token the protocol swaps or the fee it charges — (File: `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core broken invariant is: *trusting a single, statically configured Uniswap fee-tier/pool as the source of truth for pricing, with no dynamic liquidity check, letting an attacker create/manipulate a low-liquidity pool at that exact fee tier to distort the quoted price.* The direct local analog is `UniV3UniswapV2Wrapper`, which is deployed with an immutable `_params.maxFee` (a single fee tier) and is used by `IntentGatewayV2.placeOrder` (see the `evm/tron` variant) to convert a user's native-token payment into the exact protocol fee token amount via `swapETHForExactTokens`, and by `HyperFungibleToken.quote()`/`EvmHost` as the price oracle for the relayer fee. Both call sites hard-code the fee tier (`_params.maxFee`) at deployment time and never check pool liquidity or use a TWAP/liquidity-weighted price, exactly the anti-pattern flagged in the external report.

### Finding Description
`UniV3UniswapV2Wrapper` is a V2-router-compatible shim around Uniswap V3 that always swaps through one specific fee tier: [1](#0-0) 

`swapETHForExactTokens` (used to buy an exact amount of the protocol fee token with the user's native-token input) executes `exactOutputSingle` against that single fee-tier pool with `sqrtPriceLimitX96: 0` (no price-limit protection) and bounds slippage only by `msg.value` as `amountInMaximum`: [2](#0-1) 

This wrapper is the contract wired in as the host's `uniswapV2Router()`/fee oracle, and `IntentGatewayV2.placeOrder` calls it directly whenever a user pays `order.fees` in native token instead of the fee token: [3](#0-2) 

The same wrapper is also used as a price oracle for cross-chain dispatch fee quoting (`HyperFungibleToken.quote()` reaches it via a `CALL`, since the V3 quoter must write state to read a quote): [4](#0-3) 

Because the fee tier is a single, statically configured pool address derived from `(token0, token1, fee)`, and there is no liquidity check, no TWAP, and no fallback comparison against other fee tiers, an attacker can create a new pool at that exact fee tier (or thinly seed the existing one) and move its instantaneous price arbitrarily within one transaction (flash-loan supported, single-block), exactly as the external report describes for `UniswapV3SwapManager`. This is not a "malicious relayer/prover" scenario — any unprivileged party can create/manipulate a Uniswap V3 pool that Hyperbridge's own fee-token/WETH pair resolves to, because pool addresses are deterministic from `(WETH, feeToken, maxFee)` and pool creation is permissionless on Uniswap.

### Impact Explanation
- In `placeOrder`, a manipulated pool price causes `swapETHForExactTokens` to consume the user's native-token payment (`msgValue`) for far less or far more of the actual fee token than intended, directly moving value based on the manipulated price at the moment of the swap — user funds (loss of funds) or protocol fee under-collection.
- In the relayer-fee-quoting path (`HyperFungibleToken.quote()`/`EvmHost`), a manipulated price under-quotes the native fee required to cover the relayer's fee-token-denominated cost. If the dispatcher only validates `msg.value >= quote()`, an attacker can submit a dispatch paying an artificially low native fee (because the oracle under-priced the fee-token cost), causing the relayer fee to be under-funded — either the message is never economically viable to relay (a value/availability failure) or, if the shortfall is silently absorbed by the protocol elsewhere, it is an unauthorized reduction of protocol/relayer revenue extracted by an unprivileged attacker.
- This satisfies the "loss of funds" / "transaction manipulation" bar in the impact gate because the corrupted value (`spent`/`amountOut` returned from the V3 pool via the hardcoded `maxFee` tier) directly determines exact fee-token/native amounts moved on behalf of a real user, with no minimum-liquidity guard.

### Likelihood Explanation
High under the same reasoning as the external report: Uniswap V3 pool creation is permissionless, and pool address resolution is deterministic by `(tokenA, tokenB, fee)`. The wrapper is configured once at deployment with an immutable `maxFee`; there is no governance-driven repricing or liquidity check performed per-call, so once liquidity for that exact fee tier is thin (either because it was never seeded, or because Uniswap governance adds/deprecates tiers as the original report describes), any address can profitably manipulate the price within a single transaction. No privileged role, relayer, or off-chain actor is required — this is directly triggerable by any account calling `placeOrder` with a native-fee payment, or by anyone dispatching a message priced through the same oracle.

### Recommendation
- Do not hard-code a single fee tier for on-chain pricing/swapping used to derive exact protocol amounts. Either (a) require a TWAP-based price with a minimum observation window instead of the instantaneous spot quote from `exactOutputSingle`/`quoteExactInputSingle`, or (b) dynamically select the fee tier with the deepest on-chain liquidity at call time (mirroring the SDK's own `getBestV3Pool` liquidity-search logic already implemented off-chain in `sdk/packages/sdk/src/utils/swap.ts`), or (c) require an off-chain-supplied quote bounded by a governance-configured min/max sanity band.
- Enforce a real `sqrtPriceLimitX96` and an explicit `amountInMaximum`/`amountOutMinimum` slippage bound decoupled from `msg.value`, rather than letting `msg.value` alone bound slippage.
- Add a minimum-liquidity check on the resolved pool before trusting its quote for fee computation.

### Proof of Concept
1. Attacker observes that Hyperbridge's `UniV3UniswapV2Wrapper` is configured with `maxFee = 500` (0.05%) for the WETH/feeToken pair, but most real liquidity for that pair sits in the 0.3% tier, leaving the 0.05% pool thin or attacker-creatable.
2. Attacker creates (if non-existent) or flash-swaps against the 0.05% WETH/feeToken pool to push its instantaneous price far from the deep-liquidity market price.
3. In the same block, attacker (or an unwitting user, to their own detriment, or the attacker acting against the protocol's fee revenue) calls `IntentGatewayV2.placeOrder` with `order.fees > 0` and `msgValue > 0`; `placeOrder` calls `swapETHForExactTokens(order.fees, [WETH, feeToken], ...)` on the wrapper, which executes `exactOutputSingle` at the manipulated 0.05% pool.
4. Because `amountInMaximum` is bound only by `msg.value` and there is no independent sanity check against the deep-liquidity price, the swap executes at the manipulated price, either draining excess native token from the caller or letting the attacker acquire fee tokens for anomalously little native token (depending on manipulation direction), before the pool price reverts back after the attacker's own subsequent trade closes the position.
5. Repeating (2)-(4) whenever the wrapper's hardcoded tier is the manipulated one — code in `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol:114-149` and `evm/tron/contracts/apps/IntentGatewayV2.sol:465-479` — repeatably extracts value with no governance or relayer involvement required.

Note: I was unable to fully trace the exact `EvmHost.sol` code path where `quote()`/`uniswapV2Router()` gates dispatch-fee validation (the file's relevant lines were not returned by the final search), so the precise on-chain enforcement of the relayer-fee shortfall scenario in item 2 of the Impact section is inferred from `HyperFungibleTokenTest.sol` and interface wiring rather than directly confirmed line-by-line; a Devin session with full repo access should verify `EvmHost.sol`'s `quote`/`dispatch` fee-validation logic before treating that half of the impact as fully proven.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }
