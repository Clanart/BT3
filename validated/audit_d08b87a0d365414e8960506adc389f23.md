### Title
Cached preprocess seed is reused on every `share`/`complete` call, enabling nonce reuse and secret-share recovery via distinct preprocess sets or messages - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary

The Osmosis fix removed non-determinism where a value assumed stable could vary across executions. The analog in Serai is the inverse assumption in `SigningProtocol::preprocess_internal`: the FROST preprocess *seed* is cached in the DB per `context` and deterministically re-expanded into the same nonces on every call. The code assumes each context's cached preprocess is only ever used to sign a single `(preprocesses, msg)` pair, but nothing enforces that — `share_internal`/`complete_internal` re-derive identical nonces from the cached seed for whatever preprocesses and message are passed in. An unprivileged participant who can get the coordinator to run `share` (or `share` then `complete`) over two distinct preprocess sets — or two distinct `key_pair` messages — obtains two signature shares computed with identical nonces under different binding factors/challenges, recovering the validator's secret share.

### Finding Description

`preprocess_internal` loads or creates a `CachedPreprocess` seed under `CachedPreprocesses` keyed only by `context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`), decrypts it, and calls `AlgorithmSignMachine::from_cache`, which runs `seeded_preprocess` — a fully deterministic `ChaCha20Rng::from_seed` expansion producing the same `nonces` and the same published commitments every time the context repeats. [1](#0-0) [2](#0-1) 

`share_internal` then calls `machine.sign(preprocesses, msg)` with attacker-influenced `serialized_preprocesses` and a `msg` derived from `key_pair`. The FROST share is `d + e·ρ + λ·x·c`, where `ρ` and `c` are bound to the full preprocess transcript and message via `rho_transcript` and `hash_msg`. [3](#0-2) [4](#0-3) 

Critically:

1. `from_cache` is called fresh on every `share_internal`/`complete_internal` invocation; the seed is never deleted after use. `SignMachine::from_cache`'s own contract states "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" — the coordinator never deletes it. [5](#0-4) 

2. `share_internal` returns `Err(InvalidPreprocess(p))`/`Err(InvalidShare(p))` for malformed peer preprocesses, letting a participant force retries within the same context/attempt against a modified preprocess set — a ROS-style parallel-session: same nonces, different `ρ`/binding factors and/or different `msg`.

3. The file's own comments acknowledge the unresolved gap: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" and the nonce-reuse safety argument depends entirely on every `sign` call in a context seeing identical received messages — an assumption the code does not enforce. [6](#0-5) 

### Impact Explanation

Two shares `s₁ = k + λ·x·c₁` and `s₂ = k + λ·x·c₂` over the same deterministic nonce `k` but distinct challenges `c₁ ≠ c₂` (arising from any difference in the peer preprocesses' commitments/addenda or in `msg`, e.g. a different `key_pair` in `set_keys_message`) yield `λ·x = (s₁ − s₂)/(c₁ − c₂)` — the validator's effective MuSig/FROST secret share under this signing set. Since this MuSig key is the validator root-of-trust key used to confirm DKG results on-chain, recovering it enables forging validator signatures / DKG confirmations. This is key-share recovery via nonce reuse, reachable purely from public inputs (preprocess bytes fed to `read_preprocess` and signed messages). Critical severity for key confidentiality.

### Likelihood Explanation

Reachability requires two `sign` executions under the same `(domain, attempt)` context with differing inputs. That occurs naturally when (a) a participant submits an invalid preprocess, the call errors, and a retry is issued with a corrected/different set — each retry reuses the identical nonce because the seed is context-pinned; (b) `share` is called and later `complete` re-runs `share_internal` with a `key_pair` that differs from the earlier call; (c) a partial rebuild/re-execution occurs, which the file's own comments flag as an unhandled edge (only "complete rebuilds" re-decide nonces, and the on-chain-commitment-consistency check is an explicit TODO). The trigger is bytes an ordinary DKG participant controls, not validator compromise.

### Recommendation

- Consume (delete) the cached seed the first time `sign` is executed for a context, or cache the full `AlgorithmSignMachine`-equivalent state plus the exact `preprocesses`/`msg` digest and refuse to sign if they differ on re-execution.
- Implement the noted TODO: before publishing a share, verify on-chain that the preprocess commitments signed over match the ones this machine committed to.
- Key the cache by a digest of `(context, sorted preprocess bytes, msg)` rather than `context` alone, so any input divergence produces a fresh seed — or fails closed.

### Proof of Concept

Conceptual, using the code paths above:

1. Validator's `DkgConfirmer::share` is invoked for `(b"DkgConfirmer", attempt)`. `preprocess_internal` creates+caches seed `S`, and `from_cache` deterministically expands `S` into nonce scalars `(d, e)` and commitments `D, E`.
2. A malicious participant `p` supplies a preprocess whose commitments differ between two invocations (first call returns `Err(InvalidPreprocess)` after reading others' bytes, or two competing preprocess sets reach the coordinator within the same attempt).
3. Second invocation rebuilds the machine from the same `S` → identical `(d, e)`. In `sign`, `B.calculate_binding_factors` and `hash_msg` now produce different `ρ`/`c` because the transcript committed different peer commitments.
4. Two published shares satisfy `s₁ − s₂ = λ·x·(c₁ − c₂)`, recovering `λ·x` — the secret share — by observation of public share bytes alone.

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
