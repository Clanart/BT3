## Title
Sandwich/frontrunning of the WOM→mWOM buyback swap in `SmartWomConvert` triggered from unprivileged `WombatStaking` calls - (File: `wombat/SmartWomConvert.sol`)

### Summary
`WombatStaking._sendRewards` automatically routes a configurable percentage of every harvested WOM fee through `SmartWomConvert.smartConvert()` to "buy back" mWOM when it trades below peg. The actual on-chain swap inside `SmartWomConvert._convertFor` is executed against `IWombatRouter.swapExactTokensForTokens` with a hardcoded `0` minimum-out, exactly the bug class described in the referenced report (UniswapHandler passing `0` as `amountOutMin`), allowing a sandwich attacker to skim value from protocol-owned WOM/mWOM fee funds that are destined for reward-pool stakers.

### Finding Description
`WombatStaking.harvest`, `deposit`, `withdraw`, and `depositLP` are permissionless/unprivileged-callable entry points (gated only by `_onlyActivePool`/`_onlyPoolHelper`, not by caller identity), and each one funnels harvested WOM rewards through `_sendRewards`: [1](#0-0) 

This calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`, whose amount is fully deterministic and visible in the mempool ahead of execution: [2](#0-1) 

Internally, `_convertFor` swaps the "buyback" portion of WOM for mWOM via `IWombatRouter.swapExactTokensForTokens` with a **hardcoded `0`** as the per-swap minimum received, relying solely on a coarse aggregate post-swap check: [3](#0-2) 

The aggregate check compares `convertAmount + amountRec` against `_minRec`, but when called from `smartConvert()`, `_minRec` is simply set to the original `_amountIn` — not a tight, market-derived slippage bound tied to the actual swap leg. Since the buyback logic is only triggered when mWOM trades below peg (i.e., the swap is expected to yield a favorable rate), there is normally enough slack in this aggregate bound for an attacker to sandwich the individual swap (front-run to worsen the WOM/mWOM pool price, let the zero-slippage swap execute at the manipulated rate, then back-run to restore price and capture the difference) without tripping the `MinRecNotMatch()` revert.

### Impact Explanation
Because these harvest/deposit/withdraw calls are permissionless and predictable, this is repeatable MEV extraction on essentially every fee-conversion event. The value extracted comes out of protocol-owned WOM fee funds that are otherwise destined for `BaseRewardPool` and distributed as yield to reward-pool stakers (an unprivileged, shared pool of user funds), matching the "theft ... of unclaimed yield" impact category.

### Likelihood Explanation
Any address can trigger `harvest()`/`deposit()`/`withdraw()`/`depositLP()` on `WombatStaking` at will, and the resulting `feeAmount` and swap path are fully computable off-chain before submission, making this trivially observable and exploitable by mempool-watching bots, similar to the trivially exploitable nature described in the referenced report.

### Recommendation
Do not hardcode `0` as the minimum-out for the internal `swapExactTokensForTokens` call in `SmartWomConvert._convertFor` (`wombat/SmartWomConvert.sol:194-196`). Instead, compute an on-chain, oracle/TWAP-independent slippage bound tied to the actual swap leg (e.g., derive from `getAmountOut` at call time with a tight tolerance), and pass that as the swap's `minimumReceived`, rather than relying only on the coarse aggregate `_minRec` check that spans both the minted and swapped legs.

### Proof of Concept
1. Attacker monitors mempool for any call to `WombatStaking.harvest(_lpToken)` (or `deposit`/`withdraw`/`depositLP`) that will accumulate WOM rewards.
2. Attacker computes the resulting `feeAmount` that will be routed to `smartConvert` (deterministic from `feeInfos` and harvested WOM amount).
3. Attacker front-runs with a trade that shifts the WOM/mWOM pool price unfavorably for the pending buyback swap.
4. The victim's transaction executes `swapExactTokensForTokens(..., 0, ...)` in `SmartWomConvert._convertFor`, accepting whatever output the manipulated pool state gives (since the outer `_minRec = _amountIn` check has enough slack to still pass, given normal buyback conditions).
5. Attacker back-runs to reverse their initial trade, capturing the price differential as profit extracted from the protocol's fee funds.
