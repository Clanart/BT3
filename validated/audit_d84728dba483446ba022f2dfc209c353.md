Confirmed: `WireFormat::MessageSetParser::ParseElement` in `src/google/protobuf/wire_format.cc` (lines 618-648, mirrored in `extension_set_inl.h` `ParseMessageSetItemTmpl`) uses an explicit `State` machine (`kNoTag`/`kHasType`/`kHasPayload`/`kDone`) that **only accepts a `type_id` when state is `kNoTag` (first sighting) or `kHasPayload` (payload arrived first)** — a duplicate `type_id` arriving while state is already `kHasType` is silently parsed and discarded, leaving the *first* `type_id` authoritative [1](#0-0) . `upb/wire/decode.c`'s `upb_Decoder_DecodeMessageSetItem` similarly enforces strict first-wins semantics for both `type_id` and payload via `state_mask` and "Ignore dup" comments [2](#0-1) .

In contrast, Java's `MessageSetSchema.mergeFrom` (Lite runtime array decoder) unconditionally **overwrites `typeId` on every occurrence of the type-id tag**, with no state tracking to preserve the first value once a message payload may already have been consumed under the previous type [3](#0-2) . The stream-based `GeneratedMessageLite.mergeMessageSetExtensionFromCodedStream` exhibits the same last-wins overwrite of `typeId` [4](#0-3) .

This is a genuine three-way differential in how the *same* raw MessageSet::Item bytes are semantically resolved by different official Protobuf runtimes — directly analogous to the CVE-2022-31081 class of bug, where different consumers of identical framing bytes (there, `Content-Length`; here, the `type_id` tag) disagree on the message's true boundary/identity.

### Title
Inconsistent Interpretation of Duplicate MessageSet `type_id` Fields Across C++/upb vs. Java Runtimes - ([File: src/google/protobuf/wire_format.cc], [File: java/core/src/main/java/com/google/protobuf/MessageSetSchema.java])

### Summary
When parsing a legacy `MessageSet`-wire-format `Item` group containing two different `type_id` tags before (or interleaved with) the `message` payload tag, the C++ (`WireFormat::MessageSetParser::ParseElement`, `ExtensionSet::ParseMessageSetItemTmpl`) and upb (`upb_Decoder_DecodeMessageSetItem`) decoders bind the payload to the **first** `type_id` seen, while the Java Lite runtime (`MessageSetSchema.mergeFrom`, `GeneratedMessageLite.mergeMessageSetExtensionFromCodedStream`) binds it to the **last** `type_id` seen. Given identical wire bytes and identical trusted schemas registering extensions for both type ids, a C++/upb-based component and a Java-based component reach different conclusions about which extension/message type the payload represents.

### Finding Description
The invariant "a length/identity-defining field, once resolved, must be interpreted identically by every conformant parser of the same bytes" fails here. The attacker-controlled value is the ordering and count of `type_id` (field 2, varint) tags inside an attacker-supplied `MessageSet::Item` group (`kMessageSetTypeIdTag`), sent via any public `ParseFrom*`/`MergeFrom` API on a message using `message_set_wire_format = true`. C++'s state machine explicitly special-cases only `kNoTag`→`kHasType` and `kHasPayload`→(resolve with new id) transitions, dropping a `type_id` seen while already `kHasType` [5](#0-4) ; upb enforces "ignore dup" on both id and payload maps with a `state_mask` [6](#0-5) . Java's `MessageSetSchema.mergeFrom`, however, re-executes `extension = extensionSchema.findExtensionByNumber(..., typeId)` and overwrites `typeId` on every VARINT-typed `type_id` tag it encounters, with no guard against having already consumed a payload under a prior id [3](#0-2) . There is no upstream check that rejects duplicate `type_id` fields within one `Item` (the spec/legacy comment explicitly says both fields may appear, in theory, "exactly once," but doesn't enforce it) [7](#0-6) .

### Impact Explanation
In heterogeneous deployments where the same encoded MessageSet bytes are validated/authorized by one language runtime and then acted on (persisted, forwarded, or further merged) by a different one, this produces a classic smuggling/confused-deputy condition (CWE-444 analog): a C++ or upb-based front-end/gateway could bind the payload to extension `A` (and permit or reject it under `A`'s policy/schema), while the Java backend that later reparses the identical bytes binds the same payload to extension `B`, executing attacker data under a message type the front-end never validated against. This is an integrity/logic bypass, not memory corruption — bounded to CWE-444-style parsing disagreement.

### Likelihood Explanation
Requires: (1) a proto2 message with `message_set_wire_format=true`, (2) two extensions registered on the same MessageSet whose payload byte layout can be crafted to be valid for both extension types (or where only one side's parse succeeding is the exploited difference), and (3) a mixed-language pipeline that shares raw MessageSet bytes across C++/upb and Java components. This is a legacy, narrower attack surface (MessageSet is largely used internally/legacy at Google) but is fully reachable through the public parse API with a trusted schema and a fully attacker-controlled, bounded payload — no privileged access needed.

### Recommendation
Standardize MessageSet `Item` parsing across all runtimes to reject (or deterministically ignore, first-wins) duplicate `type_id`/`message` tags the same way C++ and upb already do; specifically add state tracking to `MessageSetSchema.mergeFrom` and `GeneratedMessageLite.mergeMessageSetExtensionFromCodedStream` so a second `type_id` tag is ignored once a `type_id` has already been resolved (matching `ExtensionSet::ParseMessageSetItemTmpl`'s state machine), or alternatively make all runtimes reject the message outright when duplicate `type_id` tags are detected within one `Item`.

### Proof of Concept
Construct one `MessageSet::Item` group (tag `0x0B`=field1/START_GROUP, end tag `0x0C`=field1/END_GROUP) with two `type_id` occurrences (tag `0x10`=field2/VARINT) for registered extension numbers `A` and `B`, followed by one `message` tag (tag `0x1A`=field3/LENGTH_DELIMITED) carrying a payload valid for both `A`'s and `B`'s message types:
```
0x0B                      # START_GROUP (field 1)
0x10 <varint A>           # type_id = A   (first occurrence)
0x10 <varint B>           # type_id = B   (second occurrence)
0x1A <len> <payload>      # message bytes
0x0C                      # END_GROUP (field 1)
```
- Parsed via `Message::ParseFromString` (C++) or upb: `type_id` resolves to `A` (first-seen wins per the state machine / `state_mask`), so `payload` is decoded as extension `A`'s message type.
- Parsed via the equivalent Java Lite `mergeFrom` path (`MessageSetSchema`/`GeneratedMessageLite`): `typeId` is overwritten to `B` on the second tag before `message` is processed, so `payload` is decoded as extension `B`'s message type.

Both are conformant parses of the identical byte string, but they disagree on the extension/message type the payload represents — the core "inconsistent interpretation" condition.
