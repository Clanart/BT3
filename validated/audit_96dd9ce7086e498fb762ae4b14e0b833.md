## Finding [1](#0-0) 

### Title
Auto-rewrite of `origin` remote URL from GitHub API `clone_url` validates protocol but not hostname, allowing silent remote hijack - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically calls `gitStore.setRemoteURL()` to repoint a repository's `origin` remote whenever the GitHub API reports a different `clone_url` for a repository the user hasn't manually re-pointed. The function only verifies that the *protocol* of the new URL matches the old one; it never verifies that the *hostname* (or owner/name identity beyond the built-in mismatch trigger) is consistent with the previously trusted repository. This mirrors the reported bug class: a security-relevant derived value (here, "is this still the same trusted remote?") is computed using a check that omits the very field (host) whose change should invalidate the decision — just as `_domainSeparatorV4` kept using the stale `name` after `setName()` changed it.

### Finding Description
`updateRemoteUrl` is invoked during repository refresh with the previously stored `GitHubRepository` object and a freshly fetched `apiRepo: IAPIRepository` from the GitHub API: [2](#0-1) 

The decision to call `gitStore.setRemoteURL(...)` (which actually executes `git remote set-url`) is gated by three checks:
- `protocolsMatch` — compares `URL.parse(remoteUrl).protocol` to `URL.parse(updatedRemoteUrl).protocol` (e.g. `https:` vs `https:`).
- `remoteUrlUnchanged` — confirms the user hasn't manually edited the local remote away from the previously known `cloneURL`.
- `!urlsMatch` — confirms the new API `clone_url` differs from the current remote (this is what triggers the "the repo was renamed, let's follow it" behavior).

None of these three checks verifies that the **hostname** of `updatedRemoteUrl` matches the hostname of the existing remote or of `gitHubRepository`. `urlMatchesRemote` in `app/src/lib/repository-matching.ts` is only used to detect *equality*, not to constrain what a *different* value is allowed to be: [3](#0-2) 

So if the GitHub API response for a repository ever returns a `clone_url` pointing at a different host (e.g. `https://attacker.example/foo/bar`), while keeping the same `https:` protocol, `updateRemoteUrl` will treat that as a legitimate "repository rename" and silently rewrite the user's `origin` remote to the attacker-controlled host — with no prompt, no diff view, and no user confirmation.

### Impact Explanation
This is a "git remote/proxy response" trust boundary: the `apiRepo` object originates from the network response of `GET /repos/:owner/:repo` (or the GHES-hosted equivalent). Anyone who can influence that response — a compromised/malicious GHES instance the user has authenticated against, a network-position attacker performing TLS termination on a misconfigured GHES deployment, or a service-side bug returning attacker-supplied `clone_url` — can cause Desktop to silently repoint `origin` to an arbitrary host of the attacker's choosing. Consequences:
- Silent corruption of what the user pushes: subsequent `git push` from Desktop goes to the attacker's server instead of the real repository, without any visible change in the UI besides the (easy-to-miss) remote URL field.
- Because Desktop's credential helper resolves credentials per-host (`findGitHubTrampolineAccount`/`findGenericTrampolineAccount`, see `app/src/lib/trampoline/find-account.ts`), if the attacker's host doesn't match a known GitHub endpoint the flow falls back to generic credential prompts/storage, but if the attacker mimics a known GHE endpoint hostname pattern this could also risk credential exposure during push/fetch.

### Likelihood Explanation
The check exists specifically to auto-follow legitimate GitHub repository renames (confirmed by `app/test/unit/stores/updates/update-remote-url-test.ts`), so the code path is exercised on every repository refresh where `apiRepo.clone_url` differs from the stored value — this is routine, automatic, unprompted behavior, not a rare edge case. The only thing preventing exploitation is trust in the correctness/authenticity of the GitHub API (or GHES) response; the code performs no independent host-identity check (e.g., comparing against a stable server-assigned repository id, or requiring hostname continuity) the way it does for protocol continuity.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, additionally verify that the hostname of `updatedRemoteUrl` matches the hostname of the existing remote (and of the `gitHubRepository`'s associated endpoint). If the hostname differs, do not silently rewrite the remote — instead surface the change to the user for explicit confirmation, similar to how protocol changes are already deliberately left alone.

### Proof of Concept
1. User has cloned a repository from a GitHub Enterprise Server instance and has `origin` set to `https://ghe.example.com/acme/widget.git`, matching `gitHubRepository.cloneURL`.
2. Attacker (with control over the GHES instance's API responses — e.g., a compromised/malicious admin, or a MITM position on a GHES deployment using a self-managed cert some users may implicitly trust) changes the API's reported `clone_url` for that repository object to `https://ghe.example.com.attacker-controlled/acme/widget.git` while keeping the `https:` scheme.
3. On the next repository refresh, `updateRemoteUrl` computes: `protocolsMatch = true` (both `https:`), `remoteUrlUnchanged = true` (user never touched `origin`), `urlsMatch = false` (hostnames differ) → condition `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is `true`.
4. Desktop calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com.attacker-controlled/acme/widget.git')`, silently rewriting the remote.
5. The next `git push`/`git fetch` performed through Desktop's UI targets the attacker's host instead of the legitimate repository, with no confirmation dialog shown to the user.

Note: I was not able to fully trace every caller of `updateRemoteUrl` inside `app/src/lib/stores/app-store.ts` within the available tool budget (only match locations were confirmed, not full surrounding logic), so I cannot rule out an additional upstream guard I didn't inspect; if such a guard exists it should be reviewed against this exact hostname-validation gap.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
