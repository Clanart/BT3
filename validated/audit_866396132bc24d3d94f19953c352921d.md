### Title
Attacker-controlled `n` in serialized `ThresholdKeys` drives unbounded `Vec::with_capacity` / per-element allocation before any data is validated - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg` (in scope) reads the `t, n, i` header fields directly from the untrusted byte stream and immediately allocates `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector and loops `n` times to fill `verification_shares`, with no bound on `n` beyond `u16::MAX` and no check that the input actually contains `n` elements. This is the same bug class as the external report (CWE-1325, improperly controlled sequential memory allocation driven by an attacker-chosen length): a small crafted input triggers allocation of up to ~65 535 scalars (~2–4 MB) plus per-iteration `HashMap` growth before the first `read_exact` ever fails.

### Finding Description
In `crypto/dkg/src/lib.rs:591-616`, `ThresholdKeys::read` deserializes `n` as a raw `u16` from the reader. For `Interpolation` variant `0` it executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
```

and then fills `verification_shares` for `l in 1 ..= n` via `C::read_G`. `n` is attacker-controlled, there is no sanity check (`t <= n`, `n` vs. remaining bytes, `n` vs. `MAX_PARTICIPANTS`), and `with_capacity` commits the full allocation up front — so a roughly 11-byte header with `n = 0xFFFF` forces a multi-megabyte allocation and 65 535 group-element reads before an `UnexpectedEof` error unwinds it. Per call this is bounded to a few MB, but an unprivileged party feeding repeated crafted blobs to any of the sanctioned sinks (`ThresholdKeys::read`, or callers that deserialize key material/preprocess payloads) forces repeated allocation/free churn and memory exhaustion (the same "allocation before validation" flaw fixed upstream in weixin4j's `CharArrayBuffer`).

A related instance exists in `crypto/schnorr/src/aggregate.rs:77-87`, where `SchnorrAggregate::read` loops `0 .. u32::from_le_bytes(len)` pushing a `C::G` per iteration — the vector itself only grows as bytes arrive, but the loop count is entirely attacker-controlled with no maximum.

### Impact Explanation
A remote unauthenticated party who can supply bytes to `ThresholdKeys::read` (or to an embedder that deserializes serialized `ThresholdKeys`/aggregate signatures from messages or transaction data) can cause large, repeated heap allocations and up to 65 535 expensive `read_G`/`read_F` deserialization attempts per tiny input. This yields CPU + memory exhaustion of the signing/key-handling process — availability loss consistent with the Medium severity and VC:L rating of the reference advisory.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API on untrusted bytes per the accepted sink list. The trigger requires only a ~11-byte crafted payload (`id_len`, `C::ID`, `t`, `n = 0xFFFF`, `i`, interpolation byte `0`), so exploitation is trivial once any reachable path exposes the reader. Reachability depends on the integrator exposing deserialization of externally supplied key blobs, hence Medium rather than High.

### Recommendation
- Before `Vec::with_capacity(usize::from(n))` in `crypto/dkg/src/lib.rs`, validate `n` against `ThresholdParams` limits (`t <= n <= MAX_KEY_SHARES_PER_SET` / `u16::MAX` participant bound) and, where the reader supports it, against the remaining input length.
- Prefer incremental `Vec::push` without `with_capacity` (or cap capacity at a small constant) so allocation is proportional to bytes actually consumed.
- Add an explicit upper bound on the `Rs` count in `SchnorrAggregate::read` (e.g., reject counts above a protocol maximum before looping).

### Proof of Concept
```rust
// crypto/dkg — conceptual PoC against ThresholdKeys::<C>::read
let mut blob = Vec::new();
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);                       // valid curve ID
blob.extend(1u16.to_le_bytes());          // t = 1
blob.extend(u16::MAX.to_le_bytes());      // n = 65535  <- attacker-controlled
blob.extend(1u16.to_le_bytes());          // i = 1
blob.push(0);                             // Interpolation::Constant
// no scalar/point data follows
let res = ThresholdKeys::<C>::read(&mut blob.as_slice());
// Errors with UnexpectedEof, but only after Vec::with_capacity(65535)
// commits ~2-4 MB and 65535 read_F attempts are issued.
assert!(res.is_err());
```
Repeating this call in a loop demonstrates the sequential-allocation amplification characteristic of CWE-1325.
