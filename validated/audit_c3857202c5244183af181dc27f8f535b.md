## Finding: Stale/Compromised Hardcoded GitHub SSH Host-Key Fingerprint Enables Silent MITM Trust

### Title
Hardcoded, outdated GitHub SSH RSA host-key fingerprint causes auto-trust of a compromised key during git SSH operations - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

### Summary
`handleSSHHostAuthenticity` auto-accepts `github.com` as a known SSH host whenever the presented RSA host-key fingerprint matches a single hardcoded constant, without prompting the user [1](#0-0) . This is the same bug class as the reported `_INIT_CODE_HASH` issue: a security-relevant identity/verification constant is hardcoded and never kept in sync with the authoritative value, so a stale value is silently trusted for a critical trust decision.

### Finding Description
The comment above the check references GitHub's documentation page for SSH key fingerprints [2](#0-1) , and the code compares the presented fingerprint against the single literal `SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8` [3](#0-2) . This is the RSA host-key fingerprint GitHub used **before** the March 24, 2023 rotation, which was necessitated because that RSA private key was briefly exposed publicly. GitHub has since published a new fingerprint (`SHA256:uNiVztksCsDhcc0u9e8BujQXVUpKZIDTMczCvj3tD2s`) and retired the old key. The codebase, however, still hardcodes and trusts the old (compromised) fingerprint as the sole basis for the `'yes'` auto-accept decision, exactly mirroring the `_INIT_CODE_HASH` flaw: the constant used to validate an external identity was never updated to the correct/current authoritative value.

`parseAddSSHHostPrompt` (`app/src/lib/ssh/ssh.ts`) extracts `host`, `keyType`, and `fingerprint` straight from the OpenSSH "authenticity of host" prompt text emitted by the trampoline's askpass handler, and no other validation (e.g., no check that the connection actually terminated at GitHub's real IPs, no certificate/HSTS-style pinning of an up-to-date key set) gates the decision besides string equality against this one stale constant.

### Impact Explanation
Because the check only validates `info.host === 'github.com'` and a fingerprint match against a retired key, an attacker capable of intercepting or redirecting the user's SSH traffic to `github.com` (e.g., via DNS spoofing, a malicious/compromised network proxy, ARP/MITM on an untrusted network, or a poisoned `/etc/hosts`/corporate SSH proxy) and presenting the previously-exposed old RSA private key will have their host key **silently accepted as trusted** by Desktop, with no prompt shown to the user. This lets the attacker's SSH endpoint impersonate `github.com` for git fetch/push/clone operations run through Desktop's trampoline, enabling interception or tampering with git objects being pushed/pulled and exposure of anything sent over that SSH session (potentially including SSH-agent-forwarded operations), i.e., silent corruption of what the user pushes/fetches and interception of git traffic — squarely in the reportable impact category (git remote/proxy response leading to silent corruption or credential exposure).

### Likelihood Explanation
Exploitation requires the attacker to be positioned on the network path presenting the specific old key (a non-trivial but realistic MITM/DNS-spoofing scenario, not local/physical access, not admin rights, and not reliant on the user doing anything unusual — the user just performs a normal git operation through Desktop). Likelihood is moderate: it depends on network positioning, but the underlying flaw (a stale constant with no update mechanism) means the vulnerable code path is always live and requires no application misconfiguration to trigger.

### Recommendation
Update the hardcoded fingerprint(s) in `handleSSHHostAuthenticity` to GitHub's current, documented RSA/ED25519/ECDSA fingerprints, and consider fetching/validating them from GitHub's `/meta` API `ssh_key_fingerprints` field at runtime (with appropriate caching/pinning) instead of a build-time literal, so future key rotations do not silently reopen this class of trust bug. At minimum, add an automated test/CI check that fails the build if GitHub's published fingerprints diverge from the hardcoded value, analogous to updating `_INIT_CODE_HASH` when the underlying protocol's authoritative value changes.

### Proof of Concept
1. Attacker gains a MITM position for the victim's network traffic to `github.com:22` (e.g., DNS spoofing on public Wi-Fi, malicious captive portal, or compromised corporate SSH proxy) and stands up an SSH server presenting the pre-2023 GitHub RSA host key (whose private key was exposed publicly and is not secret).
2. Victim performs any git SSH operation (clone/fetch/push) via GitHub Desktop.
3. Desktop's trampoline askpass handler receives the "authenticity of host" prompt; `parseAddSSHHostPrompt` extracts `host: 'github.com'`, `keyType: 'RSA'`, and the attacker's presented fingerprint, which equals the hardcoded `SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8` [4](#0-3) .
4. `handleSSHHostAuthenticity` returns `'yes'` automatically — no prompt is shown to the user, and the attacker's key is silently added as trusted for `github.com`, allowing continued interception/tampering with the git SSH session.
