### Title
Partial-commit line selection is indexed by position, not content — stale selection can silently commit different lines than the user reviewed - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit ("stage some lines/hunks") feature tracks which lines a user has selected to include in a commit by **line index within the diff**, not by the actual line content. When the working-directory diff changes between the time the user makes their selection and the time the commit is actually created, Desktop recomputes the diff and reuses the old line-index-based selection against the new diff without verifying the underlying content is the same. This mirrors the report's core defect class: state computed at time T1 (the reward/balance snapshot; here, the user's line selection) is silently reapplied at time T2 against a different underlying value (new active balance/rewards; here, a changed file), producing an incorrect result that the guard code does not detect.

### Finding Description
The diff refresh logic in `_updateChangesWorkingDirectoryDiff`/`updateChangesWorkingDirectoryDiff` explicitly acknowledges this limitation: [1](#0-0) 

It says: "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines" — and then only prunes indices that no longer exist as includable lines, keeping all other indices selected [2](#0-1) .

At commit time, `_commitIncludedChanges` takes the files currently marked as having a selection and calls `createCommit`/`stageFiles`, which for partially-selected files calls `applyPatchToIndex` [3](#0-2) . `applyPatchToIndex` re-fetches a **fresh** diff of the working directory (`getWorkingDirectoryDiff`) and formats a patch using the file's `selection` object, which is still populated with line indices from the earlier (now possibly stale) diff [4](#0-3) . Nothing recomputes or validates that the indices the user selected still correspond to the same textual content — the mapping is purely positional.

Because the selection state (`DiffSelectionType.Partial` + line index set) is preserved across status refreshes via `updateChangedFiles` (`existingFile.selection` is carried forward onto the newly-fetched file object) [5](#0-4) , any external modification to the tracked file between the user's selection and the click of "Commit" will cause Desktop to build a patch from indices that now point at different lines than what the user actually reviewed and checked.

### Impact Explanation
If a working-directory file the user has partially staged is modified by another process (a build tool, a file watcher, a `post-checkout`/`post-merge` hook triggered by an unrelated Desktop-initiated git operation, or any tool running concurrently while GitHub Desktop is open) after the user selects specific lines/hunks but before they press commit, the final commit can silently include different content than what the user reviewed in the diff viewer. This is a "silent corruption of what the user commits" scenario: the user visually confirms hunk A/B was selected, but the actual committed patch is generated against updated file content at those same line offsets, which may now contain unrelated or attacker-influenced text. This could be leveraged by a malicious build/dev-dependency (already present via the cloned repo) to smuggle unreviewed content into a commit that the developer believes only contains the lines they explicitly checked, defeating the entire purpose of the partial-commit review flow.

### Likelihood Explanation
The comment in the code itself concedes this is a known, un-remediated gap ("for now we'll settle on..."), meaning there's no defense-in-depth check preventing it. The precondition — a file changing on disk between selection and commit — is realistic in normal developer workflows (auto-formatters, linters-on-save, generated files, watch-mode builds, git hooks) without requiring any unusual user action; it does not require local/physical access, admin rights, or pre-existing malware — only a repository whose accompanying tooling (already run by the developer as part of normal workflow) can modify a file mid-review.

### Recommendation
When re-deriving the diff for a file that has a `Partial` selection, validate the persisted selection against the *content* of the new diff (e.g., hash or compare line text at each previously-selected index) rather than only pruning indices that no longer exist. If content at a previously-selected line has changed, the safest behavior is to clear the partial selection (forcing the user to re-review and re-select) rather than silently carrying the stale indices forward. Additionally, `applyPatchToIndex`/`stageFiles` should perform a final content-consistency check immediately before generating the patch that's applied to the index, aborting or warning the user if the underlying diff differs from what was last rendered.

### Proof of Concept
1. In a cloned repository, open a file with multiple hunks/lines of changes in the Desktop Changes view.
2. Partially select specific lines (e.g., lines 5–10) for inclusion in the commit; leave other lines unselected.
3. Before clicking "Commit", have an external process modify the same file at those line offsets (simulating a formatter/build step or a hook run by a concurrent Desktop git operation), changing the text at lines 5–10 to different content while keeping the file's line count the same (so the "selectable lines" pruning in `updateChangesWorkingDirectoryDiff` doesn't invalidate the selection).
4. Desktop's status refresh re-fetches the diff, keeps the selection because line indices 5–10 are still "includeable" [6](#0-5) , and the UI may not re-render the diff pane if the file remains selected and no explicit re-fetch is triggered by the user.
5. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` generates a patch from the *new* file content at the old selected indices [4](#0-3) , committing content the user never explicitly reviewed at commit time.

Note: I was unable to fully inspect `app/src/lib/patch-formatter.ts`'s exact line-matching implementation due to a tool call failure in the final iteration, so the precise mechanics of how `DiffSelection` indices map onto patch hunks (e.g., whether any hash/context-line comparison exists there) could not be independently confirmed from `patch-formatter.ts` itself — this should be verified by a follow-up review of that file before treating this as fully confirmed.
