I found a concrete analog: an unbounded backward pointer scan in the ProtoJSON "Any" decoder (`upb/json/decode.c`, and duplicated verbatim in the Ruby/PHP `upb` amalgamations), which mirrors the ocfs2 pattern of scanning an in-memory region for a delimiter without verifying the scan stays within valid bounds.

### Title
Out-of-bounds backward scan in `jsondec_any()` while locating the preceding comma before a late `"@type"` key - (File: `upb/json/decode.c`)

### Summary
`jsondec_any()` parses a JSON `google.protobuf.Any` object. When fields appear *before* the `"@type"` key, it records `pre_type_data` (start of the first such field) and, once `"@type"` is found later, walks backward from `start` (the position where the `"@type"` key began) to locate the preceding comma via `while (*pre_type_end != ',') pre_type_end--;`. This loop has no lower-bound check against `pre_type_data` or the start of the buffer, relying entirely on the assumption that a comma will be found before running off the front of the buffer.

### Finding Description
The ocfs2 bug scans a sequence of on-disk xattr entries for a name match using an attacker-influenced entry count/pointer, with no check that the scan pointer stays inside the valid entries region — allowing it to read past the intended buffer. [1](#0-0) 

The `jsondec_any()` code has the analogous structural flaw for a public, attacker-reachable parse API (ProtoJSON `Any` unmarshaling): the backward-walking pointer `pre_type_end` is decremented in a `while` loop keyed only on finding a `,` byte, with no `pre_type_end > pre_type_data` (or `> d->buffer_start`) guard: [2](#0-1) 

Whether this is actually reachable with out-of-bounds memory depends on whitespace/formatting handling upstream (`d->ptr`/`start` bookkeeping in `jsondec_objnext`/`jsondec_string`), which determines whether a comma is always guaranteed to exist between `pre_type_data` and `start` in every well-formed-enough input the tokenizer would accept before erroring. I was not able to fully trace `jsondec_objnext()`/`jsondec_skipws()` bookkeeping in this pass to conclusively prove a comma is always present before `pre_type_data` in all accepted branches (e.g., interaction with nested skipped values via `jsondec_skipval()`, or malformed-but-partially-tokenized input); this needs deeper verification.

The same code (byte-for-byte) is duplicated in the Ruby and PHP extensions: [3](#0-2) [4](#0-3) 

### Impact Explanation
If the backward scan can be driven past `pre_type_data` (e.g., due to a tokenizer edge case where `jsondec_skipval()` consumes a value containing an internal `,` inside a string/nested structure that is itself skipped, moving `d->ptr` past a real separator without leaving a comma directly before `start`), the loop would read backward past the start of the caller-supplied JSON buffer, an OOB read of arbitrary length until a `,` byte happens to occur in adjacent memory, then a subsequent `memcpy` using `len = pre_type_end - pre_type_data + 1` would copy attacker-uncontrolled adjacent heap/stack memory into an arena buffer that is then re-parsed as JSON and merged into a message. This is a memory-disclosure / crash-primitive class similar in spirit to the ocfs2 xattr entry OOB read, contingent on the tokenizer invariant not always holding.

### Likelihood Explanation
Medium-to-low confidence without full step-through: This code path is only reached for `google.protobuf.Any` JSON parsing where the `"@type"` key is *not* the first key in the object (an intentionally supported but unusual ordering), which requires the caller to enable ProtoJSON parsing (a supported public entry point in upb/Ruby/PHP). Whether it's actually exploitable depends on tokenizer guarantees I could not fully confirm in this pass.

### Recommendation
Add an explicit lower-bound check in the backward scan, e.g. `while (pre_type_end > pre_type_data && *pre_type_end != ',') pre_type_end--;`, and treat failure to find a comma as a parse error rather than silently using a wild pointer, mirroring the ocfs2 fix pattern of bounding the scan against the known valid region before dereferencing.

### Proof of Concept
Not run. A concrete PoC would require constructing a `google.protobuf.Any` JSON payload where a pre-`"@type"` field's value is skipped via `jsondec_skipval()` in a way that does not leave a literal `,` immediately preceding the `"@type"` key's start offset, then feeding it to `upb_JsonDecode()` (or the Ruby/PHP `JSON.parse`/`decode` wrappers) under ASan to check for a heap-buffer-underflow. I was unable to execute this in the current session — this should be validated by a Devin session with test-execution capability before treating it as a confirmed, exploitable vulnerability rather than a plausible analog.

static void jsondec_any(jsondec* d, upb_Message* msg, const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  /* string type_url = 1;

  upb_Message* any_msg;
  const upb_MessageDef* any_m = NULL;
  const char* pre_type_data = NULL;
  const char* pre_type_end = NULL;
  upb_MessageValue encoded;

  jsondec_objstart(d);

  /* Scan looking for "@type", which is not necessarily first. */
  while (!any_m && jsondec_objnext(d)) {
    const char* start = d->ptr;
    upb_StringView name = jsondec_string(d);
    jsondec_entrysep(d);
    if (jsondec_streql(name, "@type")) {
      any_m = jsondec_typeurl(d, msg, m);
      if (pre_type_data) {
        pre_type_end = start;
        while (*pre_type_end != ',') pre_type_end--;
      }
    } else {
      if (!pre_type_data) pre_type_data = start;
      jsondec_skipval(d);
    }
  }
