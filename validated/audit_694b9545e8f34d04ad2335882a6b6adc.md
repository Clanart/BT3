### Title
Panic on missing/duplicate-indexed `GeneratorProof` in `GeneratorPromotion::complete` enables remote DoS - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The Pion STUN advisory is a remotely-triggerable panic during parsing of attacker-controlled input. The closest analog in the in-scope Serai code is `GeneratorPromotion::complete`, which consumes a `HashMap<Participant, GeneratorProof>` built from proofs received from other participants. Its validation only checks the map's *length* and that every key is `<= n`, then indexes the map with `.unwrap()` for each participant `1..=n`. A proof map that passes both checks but lacks an entry for some participant (because an attacker supplied a proof keyed to a duplicate or to the local participant's own index) causes an unconditional panic, crashing the promotion/DKG flow — a remotely reachable denial of service, mirroring the "panic on malformed/attacker-supplied input" bug class.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `GeneratorPromotion::complete` performs two checks before consuming proofs:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... }        // line 125
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }                          // line 133
}
```

Then for each `i in 1..= params.n()` (skipping the local `params.i()`), it does:

```rust
let proof = proofs.get(&i).unwrap();                            // line 146
```

The checks verify cardinality and an upper bound, but not that the map covers exactly `1..=n` minus the local index. A map containing the local participant's index `params.i()` as a key — or any duplicated participant index — still has length `n - 1` with all keys `<= n`, yet is missing some legitimate `j != params.i()`. When the loop reaches `j`, `proofs.get(&j)` returns `None` and `.unwrap()` panics.

This is reachable from public inputs: `GeneratorProof::read` (`crypto/dkg/promote/src/lib.rs:72`) deserializes proofs supplied by remote participants, and the caller assembles them into the `HashMap` keyed by claimed sender index. A malicious participant can send a `GeneratorProof` while asserting a participant index that collides with an existing entry or equals the victim's own index, producing exactly this map shape.

A related panic-on-untrusted-input site exists in `crypto/dkg/pedpop/src/encryption.rs:388`, where `self.enc_keys[&decryptor]` panics if `decrypt_with_proof` is invoked for a participant whose encryption key was never registered — also attacker-influenced, though dependent on integrator usage.

### Impact Explanation
An unprivileged participant in the generator-promotion protocol can crash the victim's process (or at minimum abort the promotion with an unhandled panic) by sending a validly-parsed `GeneratorProof` under an index that duplicates another entry or matches the victim's own `params.i()`. Since the panic occurs before any share verification, no valid proofs are required — the attacker's proof bytes don't even need to verify. This is a medium-severity availability impact identical in class to the Pion STUN panic: malformed/attacker-arranged input reaching an unchecked `.unwrap()`.

### Likelihood Explanation
- Reachability: `GeneratorProof::read` accepts any canonical `(point, DLEqProof)` bytes; no authentication or index checks occur during deserialization. The `HashMap` keys are attacker-controllable participant indexes.
- The length/bounds checks do not enforce set coverage, so constructing the panic-inducing map requires only that one expected index be absent — trivially achieved by a single malicious participant claiming a wrong/duplicate index (or by a participant simply being absent while the attacker supplies an extra proof under a colliding key).
- Panics in Rust abort or unwind through the calling protocol code; unless the integrator wraps every call in `catch_unwind`, this is a reliable crash.

### Recommendation
Replace the `.unwrap()` at `crypto/dkg/promote/src/lib.rs:146` with an explicit check that every expected participant `1..=n` (except `params.i()`) is present, returning `PromotionError::IncorrectAmountOfParticipants` or a new `MissingProof`/`DuplicatedParticipant` error otherwise. Additionally reject `proofs` maps containing `params.i()` or validate that `proofs.keys()` equals the expected set before iterating. Similarly, `Decryption::decrypt_with_proof` in `crypto/dkg/pedpop/src/encryption.rs` should return a `DecryptionError` instead of panicking on `self.enc_keys[&decryptor]`.

### Proof of Concept
```rust
// Requires: crypto/dkg/promote with a concrete ciphersuite (e.g. dalek-ff-group Ed25519).
// Victim: params = ThresholdParams { t: n, n: 3, i: Participant(1) }.
//
// Attacker (participant 2 or 3) sends a GeneratorProof but the integrator keys
// it under participant 1 (the victim's own index) instead of its real index.
// The victim builds:
let mut proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof); // collides with self
proofs.insert(Participant::new(2).unwrap(), honest_proof);
// proofs.len() == 2 == n - 1  -> passes line 125 check
// all keys <= 3               -> passes line 133 check
// participant 3's entry is missing
//
// GeneratorPromotion::complete(proofs)
//   -> loop reaches i = Participant(3)
//   -> proofs.get(&3).unwrap()  // PANIC: None.unwrap()
```

**Uncertainty note:** Whether the integrator-level code keys `proofs` by a sender-claimed index versus a session-verified index could not be fully verified within the in-scope crates (`promote` only exposes the `HashMap` API). The panic is certain given a map missing an expected key; reaching that map shape depends on how callers populate it, but the API contract does not prevent it and provides no error path for it.
