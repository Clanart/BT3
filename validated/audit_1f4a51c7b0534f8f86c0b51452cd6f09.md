### Title
Unvalidated EIP-7702 authorization `V` byte length causes a deterministic panic when decoding `SetCodeTx` - ([File: x/evm/types/ethtx/auth_list.go])

### Summary
The Linux CVE-2026-43176 patches a case where hardware-reported data (a TX release report) is used before its content is validated, allowing malformed report data to crash the driver. The analogous pattern in `sei-chain` is `AuthList.ToEthAuthList()` in `x/evm/types/ethtx/auth_list.go`, which converts the protobuf-decoded `SetCodeAuthorization` list of an EIP-7702 (`SetCodeTx`, type 4) transaction into go-ethereum's `ethtypes.SetCodeAuthorization`. The conversion trusts the wire-decoded `V` byte slice and only checks its numeric range *after* already having parsed it into a `uint256.Int`, and reacts to an out-of-range value with `panic(...)` instead of returning an error.

### Finding Description
`SetCodeAuthorization.V` is a protobuf `bytes` field with no length constraint enforced by the schema, so any submitter can encode it as multiple bytes representing a value greater than `math.MaxUint8`. [1](#0-0) 

When converting to the go-ethereum representation, the code sets the byte slice into a `uint256.Int` and only then validates the numeric range, panicking on failure rather than surfacing a decode/validation error: [2](#0-1) 

This mirrors the CVE's root cause: content originating from an untrusted/unvalidated source (there, a hardware release report; here, a transaction submitted over the public RPC) is used to build an internal structure, and validation of that content happens too late — after the malformed value has already caused unsafe behavior (there, an out-of-bounds/garbage index; here, an unconditional `panic`).

`ToEthAuthList()` is invoked by `SetCodeTx.GetAuthList()`, which is part of the standard `ethtypes.Transaction`-compatible interface exposed by `SetCodeTx`: [3](#0-2) 

This path is reached whenever a `MsgEVMTransaction` wrapping a `SetCodeTx` is converted back to an `ethtypes.Transaction` via `AsTransaction()`, which is exercised on every submitted EVM transaction during ante-handler preprocessing, CheckTx, DeliverTx/message execution (`x/evm/keeper/msg_server.go`), and RPC-facing tx/receipt formatting (`evmrpc/tx.go`, `evmrpc/block.go`). Because `msg.AsTransaction()` in `x/evm/keeper/msg_server.go` is called before the function's own panic-recovery `defer` is registered, a panic here can escape the local recovery and propagate up to whatever recovery exists at the ABCI/RPC boundary — in `app.ProcessBlock`, a bare `recover()` turns the entire block into an error (`err = fmt.Errorf("ProcessBlock panic: %v", r)`), and on an unprotected RPC path (e.g., simulate/eth_call/eth_sendRawTransaction handling) it can crash the serving goroutine/node outright. [4](#0-3) [5](#0-4) 

### Impact Explanation
Because the malformed `V` value is fully attacker-controlled and deterministic (embedded in the raw transaction bytes), every node that decodes and preprocesses the same transaction — validators during block proposal/verification and public RPC nodes handling `eth_sendRawTransaction`/simulation/tracing — hits the identical panic. This can crash default-configuration RPC nodes and, if it occurs during block processing without adequate recovery at every layer, risks a chain-wide processing failure/halt across validators that receive the same transaction in a block, satisfying the "crash of default-configuration RPC nodes" / "validator halt" impact bar.

### Likelihood Explanation
Any unprivileged account can submit a type-4 (`SetCodeTx`) `MsgEVMTransaction` with an authorization entry whose `V` field is encoded as more than one byte representing a value above 255. No special privileges, signatures matching real accounts, or state setup are required — only that the message reach decode/preprocessing (mempool ingestion, ante handling, or RPC transaction formatting), all of which are on the direct path for any submitted transaction.

### Recommendation
Validate `SetCodeAuthorization.V` (and similarly `R`/`S`) length/range immediately after unmarshalling the `MsgEVMTransaction`/`SetCodeTx`, rejecting with a normal decode error instead of panicking. Replace the `panic("v value too large to fit in uint8")` in `ToEthAuthList()` with a returned error that is properly surfaced by all callers (`GetAuthList`, `AsTransaction`), and audit `x/evm/keeper/msg_server.go` to ensure `msg.AsTransaction()` is only called after panic-recovery is registered, or wrap it in its own recovery so a single malformed transaction cannot escape into block processing as an unhandled panic.

### Proof of Concept
1. Craft a `MsgEVMTransaction` wrapping a `SetCodeTx` (`type_url` ending in `.SetCodeTx`) with one `SetCodeAuthorization` entry whose `v` field is encoded as protobuf `bytes` containing e.g. `0x01 0x00` (a 2-byte value > 255) instead of a single byte.
2. Submit this transaction via the public JSON-RPC `eth_sendRawTransaction` endpoint or broadcast it as a Cosmos tx to a node's CheckTx.
3. When the node decodes the message and calls `AsTransaction()` → `SetCodeTx.GetAuthList()` → `AuthList.ToEthAuthList()`, the `v.Uint64() > math.MaxUint8` branch triggers `panic("v value too large to fit in uint8")`, crashing or erroring the node/RPC handler processing the transaction.

Note: I was not able to fully trace every call site of `AsTransaction()`/`GetAuthList()` (e.g., all RPC and ante-handler entry points) to confirm which specific ones lack panic recovery versus which are protected by an enclosing `recover()`; this would need direct verification in a live/checked-out repo to determine the exact blast radius (isolated tx rejection vs. block-wide failure vs. RPC-node crash).

func (al AuthList) ToEthAuthList() *[]ethtypes.SetCodeAuthorization {
	ethAuthList := make([]ethtypes.SetCodeAuthorization, len(al))

	for i, auth := range al {
		chainId := new(uint256.Int)
		chainId.SetFromBig(auth.ChainID.BigInt())
		v := new(uint256.Int)
		v.SetBytes(auth.V)

		var v8 uint8
		if v.Uint64() > math.MaxUint8 {
			panic("v value too large to fit in uint8")
		}
		v8 = uint8(v.Uint64()) //nolint:gosec

		r := new(uint256.Int)
		r.SetBytes(auth.R)
		s := new(uint256.Int)
		s.SetBytes(auth.S)
		ethAuthList[i] = ethtypes.SetCodeAuthorization{
			ChainID: *chainId,
			Address: common.HexToAddress(auth.Address),
			Nonce:   auth.Nonce,
			V:       v8,
			R:       *r,
			S:       *s,
		}
	}

	return &ethAuthList
}
