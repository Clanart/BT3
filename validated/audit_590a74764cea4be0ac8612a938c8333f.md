### Title
Future-dated oracle timestamps bypass staleness gating and can permanently freeze a price feed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` computes staleness `delta` as `stacks-block-time - ts`, but when the reported feed timestamp `ts` is **greater** than the current Stacks block time, it silently substitutes `delta = 0` instead of treating this as an invalid/unexpected timestamp. That branch always satisfies `(<= delta max-staleness)` and, because the same "future" `ts` is by construction `>= prev`, it also always satisfies the monotonicity check `(>= ts prev)`. The feed's `last-update` map is then advanced to this future timestamp. From that point on, every subsequent price update for that feed must present a timestamp `>= ` this inflated value or the transaction reverts with `ERR-ORACLE-INVARIANT`, permanently blocking legitimate price refreshes for that asset.

### Finding Description
The staleness/monotonicity gate lives in `oracle-timestamp-fresh`: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

This is invoked from `price-resolve`, which also writes the new `last-update` reference used as `prev` for the next call: [2](#0-1) 

The `ts` fed into this function comes from two structurally different clocks depending on `type`:
- `resolve-pyth` uses Pyth's own `publish-time` (the external oracle network's UTC clock).
- `resolve-dia` uses DIA's timestamp, converted from milliseconds to seconds via integer division. [3](#0-2) 

`stacks-block-time`, on the other hand, is the Stacks L2 block's own timestamp. This is exactly the two-clock pattern described in the external report: a value derived from one clock source (the external oracle's own report time) is compared against a different clock source (the local chain's block time) for both freshness and monotonicity, and the comparison logic mishandles the case where the two clocks disagree. Instead of rejecting or clamping `ts` when it is ahead of the chain's own block time, the code treats it as automatically "fresh" (`delta = 0`), defeating the purpose of the `max-staleness` gate for that call, and — more importantly — it lets that value become the new floor (`prev`) that all future updates for the feed must meet or exceed.

Any time `stacks-block-time` lags behind the true clock feeding the oracle's `ts` (e.g., due to block-production delays, or any transient/legitimate skew between the Stacks chain clock and the external time source), `last-update` for that feed gets bumped to a timestamp higher than the chain will "catch up to" quickly. Every subsequent honest `price-resolve` call for that same `{type, ident}` key must then supply `ts >= prev`; if the chain's block time transiently lagged again (or the skew persists), fresh legitimate updates keep failing `(>= ts prev)` is actually satisfied by real time progressing, but the freshness half `(<= delta max-staleness)` is where the "future" bypass matters — a single anomalously-far-future `ts` (from a relay bug, reorg, misconfigured feed migration, or any non-malicious data glitch) is accepted with zero scrutiny and permanently raises the bar for all later updates.

### Impact Explanation
Once `last-update` for a feed is advanced past what the chain's real timestamp progression can satisfy, every subsequent call to `price-resolve` for that asset's oracle feed reverts with `ERR-ORACLE-INVARIANT`. Since `price-resolve`/`price-multi-resolve` are the only path market operations use to obtain a price for an asset, this freezes all operations that require pricing that asset — borrowing against it, repaying against it, and liquidating positions collateralized by it — because the health-check and notional-value calculations cannot proceed without a valid price. This matches the in-scope **permanent freezing of funds** impact class: user collateral/debt denominated in the affected asset becomes unusable until the feed is somehow reconfigured.

### Likelihood Explanation
The bypass triggers on the `ts > stacks-block-time` branch, which is the normal branch whenever the external oracle's own reported time is even slightly ahead of the Stacks chain's block timestamp — not a rare or contrived condition given oracle networks and L2 chain clocks are independently maintained. The bug is purely in the local comparison logic (`oracle-timestamp-fresh`), not in oracle data being deliberately malicious, so it is not excluded as "incorrect data supplied by third-party oracles" — the flaw is that the contract's own gating logic silently disables itself instead of properly validating/rejecting a timestamp from a source ahead of the local clock.

### Recommendation
Do not special-case `ts > stacks-block-time` as automatically fresh. Instead, reject timestamps that are ahead of `stacks-block-time` by more than a small allowed clock-skew tolerance, and compute `delta` consistently (e.g., using absolute difference or explicitly erroring on `ts > stacks-block-time + skew-tolerance`) so a single anomalous or skewed timestamp cannot become a "poison" floor that blocks all future legitimate updates for the feed.

### Proof of Concept
1. A feed's oracle response for `{type, ident}` reports `ts0` such that `ts0 > stacks-block-time` at call time (e.g., due to normal clock skew between the external oracle time source and the Stacks chain block clock).
2. `oracle-timestamp-fresh(ts0, prev, max-staleness)` computes `delta = 0`, so `(<= delta max-staleness)` passes trivially, and `(>= ts0 prev)` also passes since `ts0` is the newest value seen. `price-resolve` then sets `last-update[{type, ident}] = ts0`. [4](#0-3) 
3. On the next legitimate call, the oracle returns `ts1` reflecting real progression of the external clock, but if `stacks-block-time` has not caught up (or `ts1 < ts0` due to any transient inconsistency), `(>= ts1 prev)` fails and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every subsequent call, freezing all borrow/repay/liquidate operations that need this asset's price.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
