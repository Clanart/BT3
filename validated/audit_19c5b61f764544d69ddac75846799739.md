### Title
`smartConvert`'s underlying AMM swap uses `amountOutMinimum: 0`, letting MEV sandwich attacks steal WOM→mWOM buyback value from the permissionless harvest flow - ([File: wombat/SmartWomConvert.sol])

### Summary
`WombatStaking::harvest` is a permissionless, externally callable function that routes protocol WOM fees through `SmartWomConvert::smartConvert`, which performs an on-chain swap of WOM for mWOM with `amountOutMinimum` hardcoded to `0`. The only downstream check is a loose break-even floor (`_minRec = _amountIn`), not a real slippage bound. Any wallet can trigger `harvest()`, and an MEV searcher can sandwich the resulting swap to capture the WOM/mWOM arbitrage value that should accrue to the protocol's reward pools.

### Finding Description
`WombatStaking::harvest` has no access restriction beyond `_onlyActivePool` (a pool-existence check, not a privileged role), so any ordinary wallet can call it. [1](#0-0) 

`harvest` calls `_toMasterWomAndSendReward`, which calls `_sendRewards` for the harvested WOM. When a fee bucket is marked `isMWOM` and a `smartWomConverter` is configured, `_sendRewards` calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` on the harvested WOM fee before queueing it to the reward pool. [2](#0-1) 

`SmartWomConvert::smartConvert` computes a `convertRatio` based on the current mWOM/WOM peg (via `currentRatio()` and `maxSwapAmount()`), then calls `_convertFor` with `_minRec` set to the *full input amount* (`_amountIn`), not a true price-derived minimum: [3](#0-2) 

Inside `_convertFor`, the "buyback" portion of the WOM is swapped for mWOM through the Wombat router with `amountOutMinimum` hardcoded to `0`: [4](#0-3) 

The final check only reverts if `convertAmount + amountRec < _minRec` (i.e., if the total obtained mWOM would fall below the original WOM amount put in) — this is a break-even floor, not a slippage protection tied to the market price at the time of the call: [5](#0-4) 

Because the swap leg itself has zero minimum-output protection, and the aggregate floor only guarantees "no worse than 1:1", an MEV searcher observing a pending `harvest()`/`smartConvert()` call can:
1. Front-run: buy mWOM to push its price back toward peg (making mWOM more expensive to buy).
2. Let the victim's WOM→mWOM swap execute at the worsened rate, capturing far less mWOM than fair value would provide (but still enough to satisfy the loose `_amountIn` floor).
3. Back-run: sell mWOM back to profit from the round-trip.

This is the same bug class as the external report: a swap with `amountOutMinimum: 0` combined with no meaningfully tight slippage bound, reachable via a fully permissionless entry point (`harvest`), which any wallet can call to trigger the vulnerable conversion at will (e.g., calling it repeatedly to force conversions during a self-created sandwich window).

### Impact Explanation
The value extracted by the sandwich attacker is WOM fee revenue that is meant to be converted into mWOM and queued into the `BaseRewardPool` (`IBaseRewardPool(feeInfo.to).queueNewRewards(...)` / rewarder in `_sendRewards`) as yield for stakers/lockers. Since the arbitrage upside from the below-peg buyback mechanism is systematically skimmed by MEV instead of flowing to the reward pool, this constitutes theft of protocol yield that would otherwise be distributed to users, falling within the permitted "theft of unclaimed yield" impact category. Because `harvest()` is unauthenticated and can be triggered by anyone, the attack does not require any privileged access.

### Likelihood Explanation
Likelihood is elevated because `harvest()` requires no permission and can be called by any wallet (including the attacker themselves) at a time of the attacker's choosing, and the swap always uses `amountOutMinimum: 0` with no true price-derived slippage bound — the aggregate `_minRec = _amountIn` check does not meaningfully constrain the attacker's extractable value whenever the pre-attack mWOM discount is more than negligible. On L2s/low-gas chains this is straightforwardly profitable, consistent with the original report's assessment.

### Recommendation
Compute an off-chain or on-chain oracle-independent expected output for the buyback swap leg (e.g., via a TWAP or a caller-supplied slippage-tolerant minimum) and pass a non-zero `amountOutMinimum` to `IWombatRouter::swapExactTokensForTokens` inside `SmartWomConvert::_convertFor`, rather than relying solely on the loose `convertAmount + amountRec >= _amountIn` floor. Additionally, consider allowing `harvest`/`smartConvert` callers (or a keeper role) to supply a real slippage parameter for the buyback swap, and enforce a genuine deadline rather than `block.timestamp` at execution.

### Proof of Concept
1. Attacker monitors the mempool/public state for conditions where `currentRatio() < buybackThreshold` (mWOM trading below peg) on `SmartWomConvert`. [6](#0-5) 
2. Attacker calls `WombatStaking::harvest(_lpToken)` for a pool with accrued WOM fees, or waits for/front-runs another user's call, knowing it will trigger `_sendRewards` → `smartConvert`.
3. Attacker sandwiches the resulting `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` call in `SmartWomConvert::_convertFor` (line 194-196): front-run by buying mWOM to move the pool price, let the harvest's buyback swap execute at the worse rate, then back-run by selling mWOM back.
4. Because `_minRec` is merely `_amountIn` (break-even), the transaction does not revert despite the attacker capturing the price-improvement (arbitrage) value that should have flowed into the mWOM amount credited to the reward pool via `_sendRewards`/`queueNewRewards`. [7](#0-6)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
