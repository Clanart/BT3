## Title
Duplicate, non-identical conflict-marker parsers can desynchronize AI hunk-count validation from actual splice points, silently corrupting merged/rebased file content - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Like the ChainlinkFactory bug where a "count" check (`numRequested`) was computed but never actually enforced against the thing it was supposed to gate (per-item fee application), GitHub Desktop's Copilot conflict-resolution feature computes an expected hunk *count* with one parser and then uses that count as the sole safety check before splicing AI-generated content into the file with a **second, independently-defined** parser. The two parsers are not the same code and can disagree on which lines constitute a well-formed `<<<<<<< / ======= / >>>>>>>` block, so an equal aggregate count does not guarantee the resolutions are spliced into the correct boundaries.

### Finding Description
Two separate functions independently decide where conflict-marker blocks start and end in the same raw file content:

- `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` builds the list sent to the model. Its "collect ours" loop only checks for `baseMarker`/`separatorMarker` while consuming lines — it never checks for the closing `theirsMarker` while doing so: [1](#0-0) 
A block missing its `=======` separator is not simply skipped — the loop keeps consuming subsequent lines (including a legitimate `>>>>>>>` line, since it isn't checked for) looking for a base/separator marker, so a malformed block can absorb or misidentify boundaries from later content, and is ultimately dropped from the hunk list only when no closing marker is ever found: [2](#0-1) 

- `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` defines its own, separate marker regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) and its own well-formedness test — an unbounded forward scan for *any* separator followed by *any* closing marker: [3](#0-2) 
This is a structurally different algorithm from `extractConflictHunks`'s sequential state machine, and is not shared/imported from a single source of truth.

- The only safety net between the model's per-hunk output and reassembly is an aggregate **count** comparison: [4](#0-3) 
This mirrors exactly the ChainlinkFactory flaw: a count (`numRequested` / `expectedCount`) exists, but the consuming function (`_applicableValue` / `reassembleResolvedFile`) doesn't verify that the count actually corresponds 1:1, in order, to the real entries being acted on — it just trusts the aggregate number. If the two parsers disagree on *where* boundaries fall while still landing on the *same total count* for a given file, `validateResolutionPaths` passes, and `reassembleResolvedFile` then splices `hunks[i].resolvedContent` into whatever the *second* parser thinks block `i` is — which may not be the block the model actually reasoned about.

The reassembly path is reached directly from the Copilot conflict-resolution store, right after validation, with no further boundary check: [5](#0-4) 

### Impact Explanation
The raw file content being parsed (`ctx.rawContent`) originates from files that came from a merge/rebase/cherry-pick against attacker-influenced input (a branch or commit an attacker crafted, e.g. via a pull request the user later merges/rebases, or a `theirs` side pulled from a remote). Because conflict markers are literal text the attacker fully controls the shape of, an attacker can craft content specifically designed so `extractConflictHunks` and `reassembleResolvedFile` disagree on hunk boundaries while agreeing on the total hunk count for the file. The result is that Copilot's resolved content for one logical conflict gets spliced into the wrong marker block (or a block is silently dropped, since `reassembleResolvedFile` pushes nothing when `hunkIndex >= hunkResolutions.length`, and non-well-formed blocks are copied through verbatim with markers still in place). Either way, the reassembled file — which the user then commits and pushes without necessarily re-diffing every hunk against the model's four-line "reasoning" — silently contains different code than the user or the model intended. This is exactly the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
This requires no local access, no admin rights, and no prior compromise: any repository or branch merged/rebased by the user (including one an attacker contributes to, e.g. via a PR) can contain the crafted conflicting content. It does require the user to invoke the Copilot AI conflict-resolution feature and to trust its output without manually verifying every hunk against the diff, which is a realistic workflow given the feature is explicitly marketed for automated resolution. Crafting content that produces divergent parses in two structurally different, hand-rolled marker scanners is a tractable, deterministic engineering exercise, not a probabilistic race.

### Recommendation
- Unify the two marker parsers into one shared implementation (single source of truth for what constitutes a well-formed conflict block), used both to build `IFileConflictContext.hunks` and to drive `reassembleResolvedFile`.
- Have `reassembleResolvedFile` accept the same hunk boundary metadata (line ranges) computed by `extractConflictHunks` instead of re-deriving boundaries from scratch, eliminating any chance of drift.
- In `validateResolutionPaths`, validate more than aggregate hunk count where feasible (e.g., structural fingerprint of each hunk's `oursContent`/`theirsContent` against what was sent in the prompt) so a boundary mismatch fails loudly rather than silently reassembling wrong content.

### Proof of Concept
1. Produce (or have an attacker's branch produce, via merge/rebase/cherry-pick) a conflicted file whose raw content contains a `<<<<<<<` block that is missing its `=======` separator but is later followed — beyond intervening unrelated text — by a legitimate `=======`/`>>>>>>>` pair belonging to a *different*, real conflict further down in the file.
2. `extractConflictHunks` (context.ts, lines 200-242): the "collect ours" loop for the first, separator-less block does not stop at a closing marker, keeps consuming lines looking for `baseMarker`/`separatorMarker`, latches onto the unrelated `=======` belonging to the second conflict, and ultimately may miscount/drop hunks differently than a strict per-block scan would.
3. `reassembleResolvedFile` (copilot-conflict-resolution.ts, lines 560-579): independently scans forward from each `<<<<<<<` line for *any* subsequent `=======` then *any* subsequent `>>>>>>>`, with no bound tying the separator to "belongs to this block" — it can happily treat the same malformed stretch as one big well-formed block spanning into the next real conflict, or vice versa.
4. Because both parsers were exercised on the same bytes but with different algorithms, run both mentally (or in a unit test) on a small three-marker-set file with one malformed block lacking a separator followed by one real block, and compare `extractConflictHunks(content).length` vs. the number of splices `reassembleResolvedFile` performs and where — they can diverge in boundary attribution while `validateResolutionPaths`'s count-only check still passes if totals coincide.
5. Confirm by writing a unit test analogous to the existing ones in `app/test/unit/copilot-conflict-context-test.ts` ("skips a malformed hunk with no closing marker") and `app/test/unit/copilot-conflict-resolution-test.ts`, but with a malformed-then-real two-block file, asserting that `extractConflictHunks(content).length` and the count of well-formed blocks `reassembleResolvedFile` actually splices into differ, or that the same total count corresponds to different content boundaries between the two functions.   fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
