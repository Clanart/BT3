## Title
CEI violation in Tron `IntentGatewayV2.withdraw()` transfers escrow before decrementing it, unlike the patched EVM twin - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core broken invariant is: a claim/settlement function performs the external token transfer *before* zeroing the internal accounting for that claim, letting a reentrant callback observe and re-consume the not-yet-cleared balance. The Hyperbridge codebase already fixed exactly this bug class in the mainline EVM Intent Gateway (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, and the `IntrinsicIntents`/`ExtrinsicIntents` fill paths, confirmed fixed by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`). However, the Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still contains the pre-fix, vulnerable ordering in its `withdraw()` function.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 682-721, the internal `withdraw()` function (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse` for source-side cancellation) does:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");     // <-- external call FIRST
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;                  // <-- state cleared AFTER
        ...
    }

    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        address feeToken = IDispatcher(host()).feeToken();
        (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
        if (!success) revert TransferFailed();
        delete _orders[body.commitment][TRANSACTION_FEES];          // <-- also cleared AFTER
    }
    ...
}
``` [1](#0-0) 

This is the exact checks-effects-interactions violation described in the H-04 report (transfer, then zero the balance). Compare this with the already-hardened mainline version in `IntentsBase.sol::_withdraw`, which decrements `_orders[body.commitment][token]` **before** issuing the native/ERC20 transfer:

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;   // effect first
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [2](#0-1) 

The `IntrinsicIntentsReentrancyTest.sol` regression suite explicitly documents that the mainline `_fillSameChain`/`_fillCrossChain` paths were patched to set `_filled[commitment]` and decrement state before any external call, specifically to close a reentrant fee/escrow theft found in these fill paths. [3](#0-2) 

The Tron `withdraw()` function was not brought in line with this fix: it still uses raw `.call` for both native ETH and ERC-20 transfers (instead of `safeTransfer`) and still updates `_orders[...]` and deletes `TRANSACTION_FEES` only after the transfer completes. [4](#0-3) 

### Impact Explanation
`beneficiary` is attacker-controlled — it is `order.user` (refund path) or the solver address recorded on fill (redeem path), both of which can be arbitrary contracts. A malicious beneficiary contract that reenters during the native-ETH `.call{value: amount}("")` (or via any ERC-20 with a transfer hook) executes while `_orders[body.commitment][token]` for the currently processed token still reflects the pre-transfer (unspent) balance, and the loop for the remaining tokens/fees in the same `withdraw()` call has not yet run its decrements either. Any state transition reachable from that reentrant callback that reads `_orders[commitment][*]` before it is cleared — including a second entry into `withdraw()` for the same commitment via a duplicate/successive incoming message, or any other function that consults escrow accounting for that commitment/token pair before the loop finishes — can result in the beneficiary being paid out more than once, or the fee balance being drained twice, directly matching the "fund loss/duplicate settlement" impact class the report demonstrates against `MultiRewardStaking.claimRewards`.

### Likelihood Explanation
The vulnerable code path (`onAccept` → `withdraw`) is reached by any legitimately delivered `RedeemEscrow`/`RefundEscrow` ISMP message — a normal, unprivileged part of the Intent Gateway's cross-chain settlement flow, not requiring a malicious relayer, prover, or admin. The only attacker-controlled inputs needed are: (1) being the beneficiary of an order (any user can be the beneficiary of their own refund, and any solver can be the beneficiary of a fill they execute), and (2) deploying that beneficiary as a contract with a reentrant `receive()`/token hook, which is a standard, unprivileged, permissionless action. This mirrors the unprivileged-attacker requirement of the accepted H-04 report exactly.

### Recommendation
Apply the same CEI fix already shipped in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron fork's `withdraw()`:
- Move `_orders[body.commitment][token] -= amount;` (and the `delete _orders[body.commitment][TRANSACTION_FEES];`) to occur *before* the corresponding `.call`/`transfer`.
- Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the mainline contract.
- Add a `nonReentrant` guard to the public entry points that ultimately invoke `withdraw()` (`onAccept`, `onGetResponse`), matching the `nonReentrant` modifier already present on `IntentGatewayV2.cancelOrder` in the mainline contract.

### Proof of Concept
Not independently re-executed in this session; the concrete evidence is the direct code diff between the patched mainline `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-425`) and the unpatched Tron `withdraw` (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-721`), plus the existing `IntrinsicIntentsReentrancyTest.sol` suite that documents and tests exactly this bug class (fee/escrow theft via reentrant `receive()`) against the mainline contract before its fix. A concrete exploit for the Tron variant would follow the same harness pattern as `IntrinsicIntentsReentrancyTest.sol`: deploy a malicious beneficiary contract that arms a reentrant call in its `receive()`/ERC20-hook, trigger `onAccept`/`onGetResponse` with a multi-token `WithdrawalRequest` for that beneficiary, and observe that `_orders[commitment][token]` is still non-zero (and the `TRANSACTION_FEES` entry undeleted) during the reentrant callback because `withdraw()` in this file performs the transfer before the corresponding storage decrement/delete. I was not able to run this PoC in this session (no execution environment), so likelihood/impact above should be validated with an actual Foundry test targeting `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw` before remediation.
