## Title
Path Traversal via unresolved file paths from remote diff/status data used to reveal/open files outside the repository - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/lib/app-shell.ts`)

## Summary
GitHub Desktop already contains a dedicated, well-tested defense against path traversal: `resolveWithin()` in `app/src/lib/path.ts`, which normalizes, resolves, and `realpath`-verifies that a joined path stays under a given root before it is used. This exact guard is applied in the deep-link handler `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` (`resolveWithin(repository.path, filepath)` at lines 1963-1971) specifically because the `filepath` there is attacker-influenced (parsed from an `x-github-client://openrepo/...?filepath=` URL).

However, several other code paths that build a filesystem path from a repository-relative `path` string taken from PR file lists / commit data still use plain `Path.join(repository.path, path)` with **no** `resolveWithin` check, before passing the result to filesystem/shell primitives (`shell.showItemInFolder`, `openFile`, `dispatcher.openInExternalEditor`).

`Path.join` does **not** prevent traversal: `Path.join('/repo', '../../../../etc/passwd')` resolves to `/etc/passwd`. This is structurally identical to the reported `bruteser` bug, where `filepath = req.url` was used to build a path with no containment check — except here the "request" is a file path string embedded in PR/diff/status metadata rather than an HTTP URL.

## Impact Explanation
If a `path` string containing `..` segments (or an absolute path) reaches any of these call sites, `shell.showItemInFolder`/`openFile`/`openInExternalEditor` would operate on a file outside the repository working directory. Depending on which primitive is reached, this ranges from information disclosure (revealing/opening arbitrary files, e.g. SSH keys, `.netrc`, credential files) to execution if the resolved file is an executable/script opened via `openFile` (native "open" verb) or via a configured external editor that executes files. This matches "attacker controls a … GitHub API object … and the result is code execution/file read outside the repo," a category explicitly called in scope by the assignment.

## Likelihood Explanation
The likelihood hinges on whether a value containing `..`/absolute-path components can actually reach `file.path` on a `CommittedFileChange` for a pull request. I was **not able to fully confirm** end-to-end in the available index whether:
- git's tree/diff machinery (as invoked here, via `getChangedFiles`/`parseRawLogWithNumstat` in `app/src/lib/git/diff.ts` and `log.ts`) enforces path-safety validation identically for diff/log output as it does at checkout time, particularly for commits fetched but **not checked out** (the `nonLocalCommitSHA` scenario surfaced in `pull-request-files-changed.tsx`/`app-store.ts`), or
- Desktop performs any additional sanitization of `IStatusEntry`/diff-parsed paths before constructing `CommittedFileChange`/`WorkingDirectoryFileChange` objects.

Given git's own hardening against `..`-named tree entries in most modern versions, exploitability may be low today, but the code itself provides **no independent, Desktop-side containment guarantee** at these call sites — unlike the deep-link path, which the maintainers explicitly hardened with `resolveWithin`. This inconsistency (one path validated, several structurally identical paths not) is the actual defect being reported; it is a defense-in-depth gap rather than a confirmed, git-independent bypass.

## Recommendation
Route every `Path.join(repository.path, <attacker/remote-influenced path>)` construction that is followed by a filesystem/shell action through `resolveWithin` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate), mirroring `dispatcher.ts`'s `openRepositoryFromUrl`. Concretely: `revealInFileManager` in `app/src/lib/app-shell.ts`, `onOpenFile`/`onFileContextMenu` in `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `onOpenItem` in `app/src/ui/changes/sidebar.tsx`, `onOpenInExternalEditor` in `app/src/ui/app.tsx`, `onContextMenu` in `app/src/ui/history/selected-commits.tsx`, and `onOverflowMenuClick` in `copilot-conflicts-dialog.tsx` should all reject/null-out paths that resolve outside `repository.path` before invoking `shell.showItemInFolder`, `openFile`, or `dispatcher.openInExternalEditor`.

## Proof of Concept
Conceptual (not independently verified against live git behavior due to index limitations):
1. A malicious PR is opened against a repository added in Desktop, whose head commit's tree contains a blob/tree entry crafted so that the resulting `git diff`/`git log` raw path string is `../../../../../../.ssh/id_rsa` (or similar) when the commit is fetched but not checked out (`nonLocalCommitSHA` path).
2. The victim opens "Pull Requests" → the PR's "Files changed" tab in Desktop, which renders `CommittedFileChange.path` directly from the diff output: [10](#0-9) 
3. Victim right-clicks the crafted entry and selects "Reveal in Finder/Explorer" or "Open with Default Program".
4. `Path.join(repository.path, file.path)` at line 162/87 resolves outside the repo, and `shell.showItemInFolder`/`openFile` is invoked on the attacker-chosen path, with no `resolveWithin` containment check as exists for the analogous deep-link flow.

Given the uncertainty about whether git itself would ever surface such a crafted path via diff/log without checkout-time validation, this should be treated as a **defense-in-depth gap confirmed by code inspection**, not a fully demonstrated exploit chain — a Devin session with terminal/git access would be needed to attempt crafting such a tree object and confirm whether `git diff`/`git log --raw` actually emits a `..`-containing path string for an unchecked-out commit.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
