### Title
Early `InvalidShare` error in `KeyMachine::calculate_share` publishes a blame proof (ECDH key) before the message's proof-of-possession is verified, letting any participant force disclosure of another party's encrypted message - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` via `Encryption::decrypt`, which queues the message's Schnorr proof-of-possession (PoP) into a `BatchVerifier` but immediately computes and returns an `EncryptionKeyProof` containing the ECDH shared key `enc_key_recipient * msg.key` plus a DLEq proof. If the decrypted bytes fail `C::F::from_repr`, `calculate_share` returns `PedPoPError::InvalidShare { blame: Some(blame) }` *eagerly*, without ever running `batch.verify_with_vartime_blame()`. The blame proof is therefore produced and propagated even when the message's PoP is invalid — exactly the key-co-option attack the PoP was added to prevent. A malicious participant can copy the per-message `key` point `X` from an honest sender's encrypted share to the victim, attach garbage ciphertext and a bogus PoP, and the victim will emit a blame proof that reveals the ECDH shared key `X * enc_key_victim`, which also decrypts the honest sender's genuine message to the victim.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` (lines 469-501) performs three steps: it queues `msg.pop` for batch verification under `batch_id`, computes `key = ecdh(&self.enc_key, msg.key)`, and unconditionally returns an `EncryptionKeyProof { key, dleq }` proving `key` is the correct shared secret. Crucially, the PoP is *not* verified before the proof material is created — it is only verified later, inside the batch.

The comments at lines 78-91 of `encryption.rs` document the threat model explicitly: if Eve reuses Alice's per-message key `X` in a message to Bob, Bob's blame would reveal `bX`, decrypting Alice's real message to Bob — "a massive side effect." The PoP bound to `sender` (via `pop_challenge`, lines 302-324) exists solely to stop this.

However, in `crypto/dkg/pedpop/src/lib.rs` `calculate_share` (lines 476-499), the loop does:

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

`batch.verify_with_vartime_blame()` is only called after the loop (line 493). A `from_repr` failure exits through `?` *before* the batch — containing the invalid PoP — is ever verified. The returned `blame` (the `EncryptionKeyProof`) is then treated as a legitimate blame proof: it is propagated in `PedPoPError::InvalidShare` and, per the blame workflow (`BlameMachine::blame` / `AdditionalBlameMachine` and `processor/src/key_gen.rs` `VerifyBlame`), published so third parties can decrypt the accused message via `Decryption::decrypt_with_proof`.

Because the PoP was never checked, the attacker does not need to know the discrete log of `msg.key`. They can copy `X` from any observed encrypted share addressed to the victim (the protocol's own comments assume Eve observes Alice's message), and the victim's published blame proof reveals `enc_key_victim * X` — the identical shared key the honest sender used — making the honest sender's ciphertext to the victim publicly decryptable (`cipher(context, proof.key)`).

The same bypass also occurs when the batch *is* reached: if the attacker supplies ciphertext that decodes to a valid scalar but fails share verification, both `BatchId::Decryption(M)` and `BatchId::Share(M)` statements fail, and `verify_with_vartime_blame` may return the `Share` ID, again emitting `blame: Some(proof)` despite the PoP being invalid.

### Impact Explanation
This is a direct analog of CVE-2020-2307 (an unprivileged party gaining access to sensitive data meant to be protected). Any DKG participant — an unauthenticated-privilege party who merely sends public protocol messages — can cause the victim to emit a blame proof that reveals an ECDH shared key belonging to a *different* sender's message. Publishing `enc_key_victim * X` decrypts the honest sender's encrypted secret share to the victim, disclosing that share's plaintext (a Pedersen polynomial evaluation at the victim's index) to all observers of the blame transcript. While a single additive share does not by itself recover the victim's final key share, it breaks the confidentiality guarantee the DKG encryption layer is designed to provide, it defeats the documented key-co-option mitigation, and it grants a static-ECDH oracle against the victim's long-term encryption key (the victim computes and publishes `enc_key * P` for attacker-chosen `P` of unknown discrete log). It also enables targeted disclosure of multiple messages if the attacker repeats the trick per observed `X`.

### Likelihood Explanation
Exploitation requires the attacker to observe an honest sender's per-message `key` point `X` addressed to the victim (the in-code threat model already assumes Eve observes ciphertexts), then send the victim one crafted `EncryptedMessage` with `key = X`, an invalid PoP, and garbage ciphertext during round 2 of PedPoP. No special privileges, collusion, or timing are needed — the leak is deterministic because the `from_repr` error path returns before batch verification. The only requirement is participation in the same DKG session, i.e., a low-privilege user.

### Recommendation
In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs`, lines 476-499), do not attach the blame `EncryptionKeyProof` to errors raised before the batch is verified. Decode-check the share after `batch.verify_with_vartime_blame()` confirms the PoP, or run the batch first and only then attempt `from_repr`, so that a `Decryption` (PoP) failure always yields `blame: None`. More robustly, restructure so `EncryptionKeyProof` is only ever exposed for messages whose PoP has been verified — e.g., have `decrypt` return a token redeemable for the proof only after batch success. Additionally, when batch verification reports both a `Decryption` and `Share` failure for the same participant, prefer the `Decryption` (PoP) failure and emit `blame: None`.

### Proof of Concept
Context: 3 participants run `KeyGenMachine`/`SecretShareMachine`/`KeyMachine` (PedPoP, e.g. `Ristretto`). Alice (participant 1) sends Bob (participant 2) an honest `EncryptedMessage` with fresh per-message key `X = xG`. Mallory (participant 3) observes Alice's message to Bob (at minimum its `key` field).

1. Mallory constructs `EncryptedMessage::<C, SecretShare<C::F>> { key: X (copied from Alice), pop: <any bytes parsed as SchnorrSignature — will not verify>, msg: SecretShare(<32 non-canonical/garbage bytes, e.g. 0xFF…>) }` and sends it to Bob over the authenticated channel as her secret share.
2. Bob calls `KeyMachine::calculate_share(rng, shares)` where `shares[M] = crafted_msg`.
3. In `decrypt`, Bob's machine queues `pop.batch_verify` for `BatchId::Decryption(M)` — never executed — then computes `key = ecdh(bob_enc_key, X)`, which equals Alice's shared key for her message to Bob, and wraps it in `EncryptionKeyProof { key, dleq }` (the DLEq proves knowledge/correctness relative to Bob's registered `enc_pub_key`, so it verifies).
4. Back in `calculate_share`, `C::F::from_repr(garbage)` returns `None`, so the function immediately returns `PedPoPError::InvalidShare { participant: M, blame: Some(proof) }` via `?` — `batch.verify_with_vartime_blame()` at line 493 is unreachable, so the invalid PoP is never detected.
5. Bob's integration treats the error as a valid accusation and publishes `proof` as blame (per `VerifyBlame` in `processor/src/key_gen.rs` lines 504-563, which accepts the proof and runs `AdditionalBlameMachine::blame`).
6. Any observer computes `cipher::<C>(context, &proof.key)` and applies it to Alice's original ciphertext to Bob, recovering Alice's secret-share plaintext — disclosure the PoP was specifically introduced (encryption.rs lines 84-88) to prevent, bypassed because the scalar-decode error exits before PoP verification.
