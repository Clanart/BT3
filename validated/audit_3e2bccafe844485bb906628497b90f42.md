## Analysis

The external report's core broken invariant: **a value used to authorize/size a fund-moving effect across a loop of external calls is read into local memory (or checked loosely) before the calls execute, and the corresponding storage debit happens *after* the external call instead of before it — so a reentrant callback can exploit the stale/incomplete state to re-drain the same balance.**

The real local analog is in the legacy Tron build of the intents settlement path: `evm/tron/contracts/apps/IntentGatewayV2.sol`, function `withdraw`.

### Title
Escrow double-withdrawal via reentrancy — state debit happens after the external token/ETH transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` transfers escrowed tokens/ETH to a beneficiary *before* debiting `_orders[commitment][token]`, and its only balance guard is a non-zero check rather than a sufficiency check. A malicious `beneficiary` (attacker-controlled recipient) or a token with transfer hooks can re-enter `withdraw` for the same commitment during the transfer and drain the escrow multiple times before the decrement is ever applied — the same class of bug as the reported `_removeAllPods`: a stale/insufficiently-updated balance value is trusted across a loop that performs external calls with side effects.

### Finding Description
`withdraw(WithdrawalRequest memory body, bool isRefund)` [1](#0-0)  :

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        unchecked { ++i; }
    }
    ...
}
```

Two issues combine to reproduce the reported bug class:

1. **Checks-Effects-Interactions is violated per-token.** The guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder()` only rejects a fully-zeroed balance — it does not check `>= amount`. The actual debit, `_orders[body.commitment][token] -= amount`, executes *after* the low-level `.call` to the beneficiary/token. This is exactly the pattern flagged in the external report: an in-flight external call happens while the authorizing balance is still "old" (not yet decremented), letting a reentrant callback observe/exploit the pre-decrement state.
2. **`withdraw` is reachable from `onAccept`/`onGetResponse` with no reentrancy guard of its own** [2](#0-1) [3](#0-2) . `_filled[body.commitment]` is set once at entry, but nothing inside the loop re-checks it, and there is no explicit re-entrancy lock (`nonReentrant`) on `withdraw`, `onAccept`, or `onGetResponse`.

Because native ETH transfer uses a raw `.call{value: amount}("")` and ERC20 transfer uses a raw low-level `.call` (not `SafeERC20.safeTransfer`, so no transfer-hook protection assumption holds even for compliant tokens with callback surfaces), a beneficiary contract's `receive()`/fallback, or an ERC777-style/callback token's transfer hook, executes fully-attacker-controlled code with `_orders[body.commitment][token]` **still non-zero and undecremented** for the current token/index, and with entries for *later* tokens in `body.tokens` (from index `i+1` onward, and the `TRANSACTION_FEES` slot) still fully intact and untouched.

### Impact Explanation
This matches the bounty's "stealing or loss of funds" and "logic attacks / double-claim" classes: a reentrant call during the transfer of token `i` can, before the loop's decrement executes, trigger the same or another entry point that reads `_orders[body.commitment][*]` and pays out escrow a second time (e.g., by re-invoking `withdraw` through a crafted `onAccept`/`onGetResponse` path, or by having a hostile beneficiary/token siphon out the remaining un-decremented balances for other tokens in the same commitment during the callback window). The result is the beneficiary receiving more than the escrowed amount for the order — fund loss to the protocol/other legitimate parties, i.e. the same "balance not updated before it's trusted again" primitive as `_removeAllPods`.

### Likelihood Explanation
This requires only an unprivileged party who controls the `beneficiary` address of a withdrawal (the order's own beneficiary/user, which is user-supplied data carried in `WithdrawalRequest`) or who can get a hostile token registered as an order input — no relayer, prover, or admin compromise is needed, satisfying the "public-entrypoint, unprivileged attacker" requirement. The trigger is a normal cross-chain settlement flow (`RedeemEscrow`/`RefundEscrow` delivered via `onAccept`, or the GET-response cancellation path via `onGetResponse`), which are routine, expected calls, not malformed-proof or malicious-relayer paths.

### Recommendation
Debit `_orders[body.commitment][token]` (and validate `amount <= escrowed`) **before** making the external transfer call, exactly as already done in the fixed/current `IntentsBase._withdraw` implementation [4](#0-3) , which reads `escrowed`, checks it, decrements storage, and only then performs the transfer. Backport that Checks-Effects-Interactions ordering (and switch to `SafeERC20.safeTransfer`) into `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, and add an explicit reentrancy guard around `withdraw`/`onAccept`/`onGetResponse` for defense in depth.

### Proof of Concept
1. Attacker places/receives a cross-chain order whose `output.beneficiary` (or `order.user` for a refund) is a contract they control, with escrow for two tokens: `TokenA` (attacker-controlled/malicious, with a transfer hook) and `TokenB` (any valuable asset), both escrowed under the same `commitment`.
2. Relayer delivers the `RedeemEscrow`/`RefundEscrow` request, invoking `onAccept` → `withdraw(body, ...)` [2](#0-1) .
3. Inside the loop, the `TokenA.call(transfer(...))` triggers the attacker's hook before `_orders[commitment][TokenA] -= amount` executes.
4. During the hook, the attacker re-enters a path that reads `_orders[commitment][TokenB]` (still un-decremented) and forces a second payout for `TokenB` — e.g., by causing another `withdraw` invocation for the same commitment via a crafted follow-up request, since `_filled` is only set once at the top and never re-validated inside the loop against per-token debits.
5. The loop then completes its original decrement for `TokenA`, but `TokenB` has already been paid out twice, resulting in the protocol/legitimate parties losing the duplicated amount.
