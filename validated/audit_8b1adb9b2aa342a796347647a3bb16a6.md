This confirms the vulnerability class: `DiffSelection` tracks selected lines purely by **positional index** (`lineIndex`/`absoluteIndex`), with no binding to the actual line content or diff identity, exactly mirroring the Balancer bug's core flaw of trusting positional/array alignment instead of validating that two related structures still correspond to the same data.

### Title
Partial-commit staging trusts stale positional line-selection against a freshly re-fetched diff, allowing wrong/attacker-influenced lines to be silently staged and committed - (File: app/src/lib/git/apply.ts, app/src/lib/patch-formatter.ts, app/src/models/diff/diff-selection.ts)

### Summary
When a user makes a partial commit (selecting individual lines/hunks to stage), Desktop stores the selection as a set of purely positional line indices (`DiffSelection.divergingLines`) computed against a diff object that was fetched at selection time. At commit time, `applyPatchToIndex` [1](#0-0)  independently re-fetches the working directory diff via `getWorkingDirectoryDiff` rather than reusing the diff the user actually looked at, and then `formatPatch` walks the **new** diff's hunks, computing `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and calling `file.selection.isSelected(absoluteIndex)` [2](#0-1)  purely by index, with zero verification that the line at that index still corresponds to the same content the user selected.

### Finding Description
`DiffSelection.isSelected(lineIndex)` only tracks integer line indices that diverge from a default state; it has no concept of line content or diff identity [3](#0-2) . The only place this positional index is re-validated against a changed diff is `updateChangesWorkingDirectoryDiff`, which recomputes `selectableLines` when the UI reloads the diff for display [4](#0-3)  — but this reconciliation only clears indices that are no longer selectable (context lines/hunk headers); it does **not** guarantee that a still-selectable index at the same position still represents the same source line, and it is not on the code path that actually builds the commit.

The commit path is separate: `createCommit` → `stageFiles` → `applyPatchToIndex` [5](#0-4) [6](#0-5) , and `applyPatchToIndex` fetches its own fresh diff at that moment [1](#0-0) , using whatever `file.selection` object was attached to the `WorkingDirectoryFileChange` passed in — which may have been computed against an older diff snapshot (e.g., from an earlier render or from before the working directory changed).

If the on-disk file content changes between the moment the user made their line selection and the moment `applyPatchToIndex` re-diffs the file (e.g., a background `git checkout`/merge/rebase continuation, an editor auto-save, a build tool, or content rewritten by a smudge/clean filter or a hook triggered by another Desktop operation running concurrently), the new diff's hunks can have a different number of hunks/lines while still allowing the same absolute indices to resolve to *different* lines. Since `formatPatch` never compares the new line's `text` against what was originally shown to the user, it will build a patch and `git apply --cached` it based on stale index positions — potentially staging attacker/tool-modified lines the user never reviewed or approved, or dropping lines the user intended to include. This is structurally the same bug as the Balancer report: two data structures (`maxAmountsIn`/`amountsIn`, or here "diff structure at selection time" vs "diff structure at commit time") are assumed to stay in lockstep by position, but nothing enforces that invariant, and no existing guard (only `isSelectable`/`selectableLines` filtering, which only prunes indices, not verifies content) catches divergence.

### Impact Explanation
This can result in **silent corruption of what the user commits**: content the user never selected or reviewed can be staged and committed under the commit message they wrote, or content they explicitly intended to include can be silently dropped. Since Desktop commits are later pushed, this can propagate unreviewed/attacker-influenced changes into the remote history without the user's knowledge — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is constrained by the need for the working tree to change between line-selection and the actual `stageFiles`/`applyPatchToIndex` call, which in the normal single-threaded UI flow is small but non-zero (Desktop performs many async operations — background fetches, checkouts, stash pops, LFS smudge filters, or externally-triggered file writes from build tools/editors — that can race with a pending commit action). I was not able to fully verify, given tool-call limits, whether there is an additional guard elsewhere (e.g., in `Dispatcher.commitIncludedChanges` or similar) that re-validates the diff/selection consistency immediately before calling `createCommit`; this should be confirmed by an engineer with full repository access before treating this as an unconditionally exploitable path.

### Recommendation
Before applying `formatPatch`'s output, verify that the diff fetched in `applyPatchToIndex` structurally matches (same hunk boundaries and line text) the diff against which `file.selection` was computed, or better, pass the diff object itself (not just re-fetch it) from the moment of selection through to `stageFiles`/`applyPatchToIndex`, failing/re-prompting the user if the working directory has changed in the interim (similar to the "diff might have changed dramatically" comment already present in `app-store.ts` [7](#0-6) , but enforced on the actual staging path, not just the render path).

### Proof of Concept
Conceptual PoC (requires confirming exact timing window in the live app):
1. User opens a modified file with several hunks and selects specific lines (e.g., lines 5–7) to stage for a partial commit; `DiffSelection` records indices 5–7 as diverging.
2. Before the user clicks "Commit", an external process (build tool, editor autosave, git hook triggered by a concurrent Desktop action, or a smudge filter tied to repository content) rewrites the file so that the diff produced by a fresh `git diff` has a different hunk layout, shifting which source line falls at absolute indices 5–7.
3. User clicks "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff [1](#0-0) , and `formatPatch` selects lines at indices 5–7 from the *new* diff [2](#0-1)  without checking they match what the user actually reviewed, staging and committing different content than intended.
