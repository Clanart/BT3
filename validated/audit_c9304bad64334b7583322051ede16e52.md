### Title
Out-of-range `Participant` index in `blame` causes panic (DoS) via unchecked HashMap indexing - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` index `self.commitments[&sender]` (and the ECDH `enc_keys` map inside `decrypt_with_proof`) with a caller-supplied `Participant`. `Participant` is any non-zero `u16`, while `commitments`/`enc_keys` only contain entries `1..=n`. Passing a `Participant` greater than `n` panics the thread — a direct analog of the Nicotine+ null-character crash: a single attacker-supplied value (here an out-of-range participant index accompanying an `EncryptedMessage`) crashes the process.

### Finding Description
- `AdditionalBlameMachine::new` populates `commitments` only for `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-660`).
- `blame` delegates to `blame_internal(sender, recipient, msg, proof)` without validating `sender`/`recipient` against `n` (`lib.rs:674-682`).
- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` (`lib.rs:582`), which internally resolves the sender's registered encryption key — the same unchecked `enc_keys[&participant]` indexing pattern used at `crypto/dkg/pedpop/src/encryption.rs:466` (`self.decryption.enc_keys[&participant]`).
- If decryption succeeds, `blame_internal` unconditionally executes `self.commitments[&sender]` (`lib.rs:599`).
- Both `HashMap` index operations panic when the key is absent, i.e. whenever `u16::from(sender) > n`.

The `msg` argument is produced by `EncryptedMessage::<C, SecretShare<C::F>>::read` over untrusted bytes (`encryption.rs:171-177`), and `sender`/`recipient` are attacker-influenced metadata (e.g. the accuser/accused fields of a blame/verification message). Nothing in the read path or the blame API bounds the participant index to `n` — `Participant::new` only rejects `0` (`crypto/dkg/src/lib.rs:29-35`).

### Impact Explanation
An unprivileged counterparty who can submit a blame/accusation (or any message reaching `blame`) supplies an out-of-range `Participant` (e.g. `Participant::new(n + 1)`) plus any `EncryptedMessage`. The receiving validator panics on the `enc_keys[&sender]` / `commitments[&sender]` lookup, crashing the processor — mirroring the remote-crash severity of the reference advisory (availability-only, no key material required, no valid cryptography needed).

### Likelihood Explanation
Requires only the ability to route a blame message to a participant running `BlameMachine::blame`/`AdditionalBlameMachine::blame`. The trigger needs no valid proof, signature, or key — just a syntactically valid `Participant` value above `n`. This is cheap to attempt, though it only fires when a deployment exposes this accusation flow to untrusted input.

### Recommendation
Validate `sender` and `recipient` against the known participant set (`1 ..= n`) at the top of `blame`/`blame_internal`, and replace `self.commitments[&sender]` / `enc_keys[&participant]` indexing with `.get()` returning a fault/error result instead of panicking.

### Proof of Concept
```rust
// crypto/dkg/pedpop, C = Ristretto, params with t/n known
let n: u16 = 4;
// commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>
// collected for participants 1..=n (or fabricated after a round-1)
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker-controlled accusation: accuser index n + 1 is a valid non-zero u16
let malicious = Participant::new(n + 1).unwrap();

// msg: any bytes parseable by EncryptedMessage::<Ristretto, SecretShare<_>>::read
let msg = EncryptedMessage::<Ristretto, SecretShare<_>>::read(&mut bytes.as_ref(), params).unwrap();

// Panics: `enc_keys[&malicious]` inside decrypt_with_proof, or `commitments[&malicious]` at
// pedpop/src/lib.rs:599 — process aborts (DoS)
machine.blame(malicious, victim, msg, None);
```

Note: I was unable to read `Decryption::decrypt_with_proof` in full to confirm whether the `enc_keys` lookup or the `commitments[&sender]` lookup fires first; both are unchecked for out-of-range participants, so the panic holds either way.
