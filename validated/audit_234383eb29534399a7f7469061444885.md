### Title
Missing validation of untrusted `ReceivedOutput` prevouts lets an attacker make Serai sign consensus-invalid or fee-burning transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The Reality Cards bug was a missing `balancedBooks` invariant on functions that move funds: checks existed on some paths (`deposit`, `withdrawDeposit`, `payRent`, `payout`, `sponsor`) but not on `refundUser`/`topupMarketBalance`, so a miscalculation could silently make the system insolvent. The Serai analog lives in `SignableTransaction`: the transaction builder and signing machine trust the *declared* value and outpoint of every `ReceivedOutput` input, while the only sanity check performed (`multisig`) verifies the prevout's `script_pubkey` against the offset-derived group key — never the amount, and never that the outpoint actually exists on chain. `ReceivedOutput` is explicitly deserializable from untrusted bytes via `ReceivedOutput::read`.

### Finding Description
`SignableTransaction::new` computes `input_sat` by summing `input.output.value` straight from caller-supplied `ReceivedOutput`s [1](#0-0) . All downstream accounting — the `NotEnoughFunds` check [2](#0-1) , the change computation `input_sat - payment_sat - fee_with_change` [3](#0-2) , and `fee()` = `sum(prevouts) - sum(outputs)` [4](#0-3)  — is derived from these unverified numbers.

The only validation anywhere in the pipeline is in `multisig`, which checks `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` [5](#0-4) . This binds the *key* to the prevout script but not the *value* nor the *outpoint*. `sign` then commits `Prevouts::All(&self.tx.prevouts)` into each `taproot_key_spend_signature_hash` [6](#0-5) , so whatever the attacker put into `TxOut { value, script_pubkey }` via `ReceivedOutput::read` [7](#0-6)  is signed verbatim.

### Impact Explanation
An unprivileged party who can feed serialized `ReceivedOutput` bytes (the type is designed for wire transport via `read`/`write`/`serialize`) can:

- **Inflate `value`**: `input_sat` is overstated, so `NotEnoughFunds` passes and the change output `input_sat - payment_sat - fee` is oversized. The threshold group then produces a fully valid set of BIP-340 signatures over a transaction whose outputs exceed its real inputs — consensus-invalid, unconfirmable, and indistinguishable from a normal plan until it fails to confirm, locking the plan and stalling the pipeline.
- **Inflate `value` with no change address**: the declared surplus silently becomes fee; when the real input is smaller than declared, the signed transaction burns a larger-than-intended miner fee (direct fund loss, the "insolvency" analog).

This is exactly the M-03 shape: a value-conservation check (`NotEnoughFunds`, `fee()`) exists but operates on unvalidated inputs, and the one integrity check that does run (`multisig`'s script_pubkey comparison) omits the amount field — funds are "balanced" against numbers nobody verified.

### Likelihood Explanation
`ReceivedOutput::read` is a public deserialization API reachable with attacker-controlled bytes (per the threat model, untrusted bytes fed to `ReceivedOutput::read` are in scope). The attacker needs no key material and no validator collusion; they only need the processor/wallet to construct a `SignableTransaction` from outputs they supplied or tampered with in transit. The failure is deterministic once a malformed `ReceivedOutput` is accepted: signing succeeds and yields an invalid transaction or an oversized fee.

### Recommendation
Mirror the `balancedBooks` fix: extend the validation performed per input before signing. In `SignableTransaction::new` or `multisig`, re-derive and assert conservation where possible, and reject `ReceivedOutput`s whose authenticity cannot be established — concretely, only accept inputs produced by `Scanner::scan_transaction`/`scan_block` over confirmed blocks (which guarantees the outpoint, script, and value all come from chain data) rather than from deserialized attacker bytes. At minimum, document and enforce at the call site that `inputs` must originate from a trusted scan, and cross-check each prevout's value against the confirming transaction on chain before creating the signing machines.

### Proof of Concept
1. Deserialize a `ReceivedOutput` where `outpoint` references a real UTXO paying to the threshold key, but `output.value` is `real_value + delta` (or where `outpoint` is fabricated entirely with a script_pubkey matching a registered offset).
2. Call `SignableTransaction::new(vec![forged], &payments, Some(change), None, fee_rate)` with `payments` sized so `payment_sat + needed_fee <= real_value + delta` but `> real_value`.
3. `new` succeeds; `multisig` succeeds (script_pubkey matches). Run `preprocess`/`sign`/`complete` — the FROST machines emit valid shares because nothing checks the prevout against chain state.
4. The completed `Transaction` has `sum(outputs) > sum(real inputs)` (oversized change) → rejected by the network; or, without change, pays `real_value - payment_sat` as fee → funds burned. In both cases Serai signed an unintended, economically harmful transaction.
