## Title
ProtoJSON alternate-field-name aliasing bypasses duplicate-key uniqueness check, allowing silent "last one wins" value substitution - (File: python/google/protobuf/json_format.py)

## Summary
The authentik bug is fundamentally an **interpretation differential**: a security-relevant identity value is validated (signature-checked) under one textual representation, while the consuming component resolves the *same* underlying wire content differently (via XML comment truncation), causing a different logical value to be adopted. The strongest Protobuf analog is the Python `json_format.Parse()` implementation's incomplete duplicate-key enforcement: JSON accepts two *different string spellings* (`lowerCamelCase` and the original `snake_case` proto field name) that both resolve to the **same** `FieldDescriptor`, but the uniqueness/duplicate checker only compares literal JSON key strings, not resolved field identity. An attacker-controlled JSON payload can therefore present two "different" keys that silently collide on one field, with the second occurrence silently overriding the first ("last one wins") — exactly the "two representations, one identity, unguarded merge" pattern in the authentik report.

## Finding Description
`google.protobuf.json_format.Parse()` is a public parse API that an ordinary client can invoke with attacker-controlled bounded JSON. Duplicate-key protection is implemented purely at the raw-JSON-text level in `_DuplicateChecker`: [1](#0-0) 

This function raises `ParseError: Failed to load JSON: duplicate key {0}` only when the **exact same string** appears twice as a JSON object key. It has no knowledge that ProtoJSON accepts multiple valid spellings for the same field (the canonical `lowerCamelCase` JSON name and the original proto `snake_case` field name), a fact acknowledged and specified in the field-presence semantics: "each member must have a unique name" is required by the JSON discipline that names should be resolved to at most one active field per message, but the checker enforces this only syntactically: [2](#0-1) 

Because `_DuplicateChecker` only sees literal strings before any field-name resolution occurs, a payload such as `{"int32Value": 1, "int32_value": 2}` passes the uniqueness gate untouched — no error is raised — even though both keys deterministically resolve to the identical `FieldDescriptor` during subsequent `ParseDict` processing. The last key processed (dictionary iteration order, attacker-controlled via key placement) wins, silently overwriting the first value. This exact defect is documented as a known, unfixed oversight in the test suite itself: [3](#0-2) 

This mirrors the authentik invariant failure precisely: (1) a component performs a uniqueness/duplicate check meant to guarantee unambiguous input, (2) the check operates on the *surface* representation rather than the *resolved semantic identity*, (3) an attacker exploits the representation gap to inject a second, attacker-chosen value that silently overrides the first without tripping the uniqueness guard, and (4) the "winning" value is determined by parse order rather than by the value the validating logic inspected.

Critically, this differs from the C++/`upb` JSON parser (`src/google/protobuf/json/internal/parser.cc`), which tracks "seen" state **per resolved `FieldDescriptor`**, not per literal string, via `Traits::RecordAsSeen`: [4](#0-3) 

That correctly rejects `{"int32Value":1,"int32_value":2}` as "already been set." The pure-Python `json_format.py` path — which remains the documented public API surface (`google.protobuf.json_format.Parse`) — does not perform this resolution before the uniqueness check, producing a genuine cross-implementation interpretation differential within Protobuf's own supported backends: the same bytes are treated as unambiguous by one backend and rejected as ambiguous by another.

## Impact Explanation
If a consuming application relies on `json_format.Parse`'s duplicate-key rejection as an implicit guarantee that a JSON payload maps unambiguously to field values (e.g., using ProtoJSON as a trust boundary for structured input, or diffing/logging the first-seen key for auditing while the parser actually commits the last-seen value), an attacker can present a payload with two spellings of a security-relevant field (e.g., a role, tenant ID, or account-linking identifier field) so that: the value an external validator/logger observes for the first occurrence of the "canonical" key differs from the value Protobuf ultimately binds to that field. This is the same class of confusion that enabled account/identity binding to diverge between the signature-validated NameID and the consumed NameID in authentik — a "different components, different final value from the same nominal identifier" bug. The severity is bounded by application usage (Protobuf itself has no authentication boundary), but the invariant violation is real, deterministic, and reachable via the public, documented `Parse`/`ParseDict` API with a fully bounded, ordinary JSON payload.

## Likelihood Explanation
High reachability: no privileges, no schema control, no native/plugin access — just an ordinary bounded JSON string through the standard public `json_format.Parse` API. The only precondition is that the target message contains at least one field whose `lowerCamelCase` JSON name differs from its proto `snake_case` name (nearly universal for multi-word field names), which is the common case. The behavior is deterministic and already reproduced in-repo by `testDuplicateFieldAlternateNames` / `testDuplicateFieldAlternateNamesMap`.

## Recommendation
Move duplicate-detection in the Python `json_format.py` path from the raw-string level (`_DuplicateChecker` in `json.loads`) to the resolved-field level, matching the `upb`/C++ JSON parser's `RecordAsSeen`-per-`FieldDescriptor` approach: track "already consumed" state keyed by the resolved `FieldDescriptor` (or oneof group) rather than by the literal JSON key text, and raise `ParseError` when a second key — regardless of spelling — resolves to a field/oneof case already populated in the same object.

## Proof of Concept
Using the repository's own pure-Python `json_format` module and any message with a multi-word field (e.g. `TestMessage.int32_value`), the following call succeeds without raising a duplicate-key error and silently applies "last spelling wins":
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2

msg = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1, "int32_value": 2}', msg)
assert msg.int32_value == 2  # no ParseError raised; silent override
```
This behavior and its non-spec nature is confirmed directly in the repository's own test comments at [5](#0-4) , showing the exact reproduction with both a scalar field and a map field.

```python
def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result
```
