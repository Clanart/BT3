### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise identity, redirecting sign-in credentials to a malicious host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
GitHub Desktop's Git credential-helper trampoline decides whether a Git remote is a trusted "GitHub Enterprise" host by inspecting the `WWW-Authenticate` response header that the *remote server itself* returns during authentication. Any HTTP(S) Git server — including one fully controlled by an attacker — can set `WWW-Authenticate: Basic realm="GitHub"` on a 401 response and Desktop will classify that arbitrary host as `'enterprise'`, then launch the GitHub Enterprise sign-in flow pointed at the attacker's origin.

### Finding Description
In `getEndpointKind`, Desktop trusts unauthenticated, remote-supplied metadata to determine trust level: [1](#0-0) 

This function is a "happy path" heuristic explicitly documented as relying on data forwarded by Git from the remote's HTTP response — data that is entirely attacker-controlled when the remote is malicious (a cloned/fetched repository's origin, a link that triggers a clone, or a MITM/malicious proxy sitting in front of an HTTP git transport).

When `getEndpointKind` returns `'enterprise'` and no existing Desktop account matches that host, `getCredential` calls into the UI layer to start a real sign-in flow using the **attacker's endpoint string**, not a vetted GitHub Enterprise URL: [2](#0-1) 

The endpoint that reaches the sign-in prompt is derived directly from the credential map's `getCredentialUrl(cred)`, i.e., the host/path Git observed for the failing remote — fully attacker-supplied. `promptForGitHubSignIn` then dispatches this value straight into the Enterprise sign-in machinery: [3](#0-2) 

Because `hostname !== 'github.com'`, Desktop calls `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with `origin` equal to the attacker's server, then shows the standard "Sign in to your GitHub Enterprise instance" dialog, pre-filled/pointed at that origin. Nothing in this path verifies that `origin` actually hosts a genuine GitHub Enterprise Server (e.g., via a `/meta` capability probe) before soliciting credentials against it.

The broken invariant: **"An endpoint classified as `enterprise` is a real, verified GitHub Enterprise host."** This is exactly analogous to the GMX report's broken invariant ("calling `compoundForAccount` will succeed because the caller is entitled") — in both cases the code assumes a privileged/trusted state without verifying it, and the assumption is falsifiable by an external, adversarial party (the GMX governor check vs. Desktop's blind trust of a self-reported `WWW-Authenticate` realm).

### Impact Explanation
If a user clones or adds a remote for an attacker-controlled repository (e.g., via a phishing link that points to `https://evil.example/legit-looking-repo.git`, or is on a network path where an attacker can respond to the Git HTTP handshake), a Git operation that requires auth will surface Desktop's credential-helper trampoline. The attacker's server needs only to respond with `WWW-Authenticate: Basic realm="GitHub"` to force Desktop into the Enterprise sign-in flow against the attacker's own origin. A user who completes that sign-in (basic auth or OAuth-style flow, believing it is a legitimate corporate/GHE prompt triggered by Desktop) will have their GitHub Enterprise credentials or resulting token sent to the attacker-controlled server. This is credential/token exfiltration and an unauthorized sign-in redirection, matching the "Valid Impact" criteria (attacker controls the git remote/proxy response, resulting in credential exfiltration / unauthorized OAuth flow) — no local access, malware, or leaked credentials are required beforehand.

### Likelihood Explanation
The trigger requires only that the user add/clone a malicious HTTP(S) remote and attempt an authenticated Git operation (fetch/push/clone) that fails with 401 — a common, unremarkable Desktop workflow, not an "unnatural user step." The comment in the code (`app/src/lib/trampoline/trampoline-credential-helper.ts:153-156`) confirms this is a deliberate but weak heuristic ("happy-path... without having to resort to making a request ourselves"), i.e., it is a known, real code path, not a hypothetical. The remaining condition — a user completing the resulting sign-in prompt — is the normal expected interaction with that exact dialog, and social engineering is limited to it looking like the standard Desktop-native GHE sign-in UI.

### Recommendation
Do not classify a host as `'enterprise'`/trusted solely from a self-reported `WWW-Authenticate` realm string. Before initiating a full Enterprise sign-in flow against a previously-unknown origin, perform a server-side verification step (e.g., query the candidate origin's `/api/v3/meta` or equivalent GitHub Enterprise identification endpoint over an independent, validated request) and/or require explicit user confirmation that clearly displays the raw hostname/origin being contacted (not just a generic "GitHub Enterprise" branding) before collecting credentials. At minimum, treat the `wwwauth[]`-derived classification as `'generic'`-trust and never auto-launch the GitHub-branded sign-in UI purely from that signal.

### Proof of Concept
1. Attacker hosts a Git repository over HTTPS at `https://evil.example/repo.git` and configures the server to respond to unauthenticated Git smart-HTTP requests with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote in GitHub Desktop (e.g., via a "clone this repo" deep link or a URL shared in an issue/PR) and performs a fetch/push.
3. Git forwards the `WWW-Authenticate` header as a `wwwauth[]=...realm="GitHub"...` field to Desktop's credential helper via the trampoline.
4. `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts:157-165` matches `realm="GitHub"` and returns `'enterprise'`.
5. `getCredential` finds no matching account for `evil.example` and calls `ui.promptForGitHubSignIn('https://evil.example')`.
6. `trampolineUIHelper.promptForGitHubSignIn` (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-99`) sees `hostname !== 'github.com'`, calls `beginEnterpriseSignIn` and `setSignInEndpoint('https://evil.example')`, and shows the GitHub Enterprise sign-in dialog.
7. Victim, believing this is a legitimate Desktop-triggered GHE login, enters credentials, which are submitted to `evil.example` — resulting in credential exfiltration.

**Note:** I was unable to fully trace `beginEnterpriseSignIn`/`setSignInEndpoint` inside `app/src/lib/stores/sign-in-store.ts` and `app/src/ui/dispatcher/dispatcher.ts` before running out of investigation budget, so I cannot confirm from local code whether any additional server-verification (e.g., a `/meta` probe) exists further down that flow that might mitigate this before actual credential submission. This should be verified directly in those files before treating the impact as fully confirmed end-to-end.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
