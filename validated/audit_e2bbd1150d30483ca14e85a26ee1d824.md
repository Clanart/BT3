### Title
PedPoP encryption key is not bound by the proof-of-knowledge signature, allowing substitution of a victim's `enc_key` so shares for the victim's index are encrypted to the attacker - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`EncryptionKeyMessage` consists of `Commitments` (which carry a Schnorr PoK) plus an `enc_key` read separately in `EncryptionKeyMessage::read` (crypto/dkg/pedpop/src/encryption.rs:57-59). The PoK challenge in `challenge` (crypto/dkg/pedpop/src/lib.rs:86-94) commits only to `context`, `participant`, the nonce `R`, and the serialized commitments `cached_msg` — never to `enc_key`. Analogous to CVE-2021-36980 (a decoder validates one object while a replaced/stale object is later used), `verify_r1` verifies the signature over the commitments but then uses the *unauthenticated* `enc_key` for ECDH encryption of that participant's secret shares (crypto/dkg/pedpop/src/lib.rs:315-329, `Encryption::encrypt` at encryption.rs:460-467).

### Finding Description
In `verify_r1`, each participant's `EncryptionKeyMessage` is split: `self.encryption.register(l, msg)` stores `msg.enc_key` for participant `l` (encryption.rs:351-362), and the returned inner `Commitments` are checked via `msg.sig.batch_verify(...)` against `challenge(context, l, sig.R, cached_msg)`. Nothing in that challenge transcript covers `enc_key`, and `register` does not authenticate it either.

An unprivileged participant (or anyone who can supply the commitments message to an honest party within the DKG session context) can take a victim's broadcast `Commitments` + valid `sig` and pair it with the attacker's own `enc_key`. All verification passes. When honest parties call `generate_secret_shares`, `self.encryption.encrypt(rng, victim_index, share)` performs `ecdh(&ephemeral_key, attacker_enc_key)` (encryption.rs:154, 466), so every participant's share evaluated at the victim's participant index is encrypted to a key the attacker controls.

### Impact Explanation
The attacker decrypts all `f_j(victim_index)` values, recovering the secret share for the victim's participant index — while the victim cannot decrypt anything and is blamed/DoSed. An attacker running one DKG instance thus obtains key shares at two participant indexes (their own and the victim's), directly reducing the effective threshold by one per substituted victim. This is concrete key share recovery reachable purely from public protocol inputs (`EncryptedMessage::read` / `EncryptionKeyMessage::read` bytes and `calculate_share`), matching the accepted impact classes.

### Likelihood Explanation
Requires an attacker who can deliver a modified `EncryptionKeyMessage` for a victim's participant index to honest participants in a DKG round. Since the commitments message is broadcast publicly, copying the victim's `Commitments`+`sig` is trivial; only the relay/registration of the attacker-controlled `enc_key` under the victim's index is needed, which is within normal untrusted-message reachability for the protocol's threat model.

### Recommendation
Bind `enc_key` into the signed/committed transcript: extend `challenge`/`pop_challenge` to append `enc_key.to_bytes()` (or append it to `cached_msg` in `Commitments::write`/`read`), so the Schnorr PoK authenticates the encryption key together with the polynomial commitments. Alternatively, require a per-participant proof of possession of `enc_key` in `EncryptionKeyMessage`.

### Proof of Concept
```rust
// Attacker observes victim's broadcast EncryptionKeyMessage { msg: Commitments, enc_key: V }.
// Attacker constructs:
let forged = EncryptionKeyMessage { msg: victim_commitments.clone(), enc_key: attacker_enc_key };
// forged.serialize() is fed to honest party's EncryptedMessage/EncryptionKeyMessage::read,
// then verify_r1: sig verifies because challenge() never includes enc_key.
// Honest party calls encryption.encrypt(rng, victim_l, share) ->
//   ecdh(&msg_key, attacker_enc_key) -> attacker decrypts f_j(victim_l) for all j.
```
The only unverified assumption is that the deployment allows an attacker to present a modified per-participant message; within the stated reachability model (untrusted bytes to `read`/`calculate_share`) this holds.
