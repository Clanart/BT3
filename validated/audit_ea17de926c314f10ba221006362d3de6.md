### Title
Unprivileged caller can force-lock a victim's default-pool MGP rewards into vlMGP via `multiclaimFor` - ([File: rewards/MasterMagpie.sol])

### Summary
`multiclaimFor(_stakingTokens, _rewardTokens, _account)` is `external` with no restriction that `msg.sender == _account` or that the caller is a trusted helper/compounder. Any address can pass an arbitrary victim as `_account`, causing `_multiClaim` to route the victim's default-pool MGP rewards into `_sendVlMGPFor`, which calls `vlmgp.lockFor(_amount, _account)` and forcibly locks the victim's MGP without their consent.

### Finding Description
`multiclaimFor` is defined as: [1](#0-0) 
It has only the `whenNotPaused` modifier and forwards `_account` as both `_user` and `_receiver` into `_multiClaim`, with no check that `msg.sender == _account` (unlike `multiclaimOnBehalf`, which is properly restricted via `_onlyCompounder`): [2](#0-1) 

Inside `_multiClaim`, for staking tokens that are neither `vlmgp` nor flagged as `MPGRewardPool` (i.e., "default pools"), the accumulated claimable MGP is accumulated into `defaultPoolAmount` and then passed to `_sendVlMGPFor`: [3](#0-2) 

`_sendVlMGPFor` unconditionally calls `vlmgp.lockFor(_amount, _account)`: [4](#0-3) 

Because `multiclaimFor` allows any caller to specify an arbitrary `_account`, an attacker with no relationship to the victim can call `multiclaimFor([defaultPoolToken], [[]], victim)`. This triggers the victim's pending default-pool MGP reward to be locked into vlMGP via `lockFor`, on the victim's behalf, without the victim's transaction or approval. There is no modifier such as `_onlyPoolHelper`, `_onlyCompounder`, or a `msg.sender == _account` check guarding this path, so the custody assumption ("only the account itself chooses to lock into vlMGP") is violated.

### Impact Explanation
This matches the "theft or permanent freezing of unclaimed yield" impact class. The victim's otherwise-liquid MGP claim from default (non-vlMGP, non-mWOM) pools is forcibly converted into a locked vlMGP position without consent, subjecting it to vlMGP's cooldown/unlock mechanics (a lock/vesting period), which freezes the victim's funds for an extended duration (well over 24 hours, dependent on vlMGP's lock schedule) that the victim did not choose. The victim did not intend to lock this reward and cannot access it as liquid MGP during the enforced lock period.

### Likelihood Explanation
No special privileges are required — the attacker needs only to be an EOA/contract capable of calling a public function. The attacker does not need to hold any relationship to the victim: it only requires that the victim has non-zero pending default-pool MGP rewards, which is a common state for any active staker. This is fully repeatable against any/all users with default-pool reward balances, and costs the attacker only gas.

### Recommendation
Restrict `multiclaimFor` so it can only be called by the account itself (`require(msg.sender == _account)`) or by an explicitly pre-authorized helper/operator mapping (similar to `_onlyPoolHelper` used for `depositFor`/`withdrawFor`), rather than allowing an arbitrary caller to specify `_account`. Alternatively, remove the forced-lock behavior from any function callable by third parties and require the account to opt in via a signed authorization or a dedicated allow-list of delegate callers.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `VLMGP` (vlmgp), MGP token; register a "default pool" staking token (not `vlmgp`, not flagged in `MPGRewardPool`).
2. Victim deposits into the default pool via `deposit()`, accrues MGP rewards over time (`vm.warp`).
3. Attacker (a separate unrelated address with no approvals/relationship to victim) calls:
   `masterMagpie.multiclaimFor(stakingTokens=[defaultPoolToken], rewardTokens=[[]], _account=victim)`.
4. Assert:
   - The call succeeds without reverting despite `msg.sender != victim` and attacker having no operator/helper role.
   - `vlmgp.getUserTotalLocked(victim)` (or equivalent) increased by the victim's pending MGP amount.
   - Victim's liquid/claimable MGP balance did NOT increase (i.e., they received no liquid MGP — it was locked instead).
   - Attempt victim's own `withdraw`/unlock of that vlMGP position to show it is now subject to vlMGP's cooldown, whereas prior to the attacker's call the reward was unlocked/liquid MGP available via normal `multiclaim`.
5. Compare against expected-safe behavior: repeat the test replacing `multiclaimFor` call with an attacker attempting `depositFor`/`withdrawFor` (which correctly revert with `OnlyPoolHelper` for non-helper callers) to demonstrate the inconsistency — `multiclaimFor` lacks the equivalent guard.
