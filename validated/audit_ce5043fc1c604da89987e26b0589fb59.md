### Title
SSRF via unauthenticated on-chain DataLayer mirror URLs causing arbitrary outbound HTTP requests during sync - (File: chia/data_layer/download_data.py)

### Summary
Any wallet holder can spend a `create_mirror_puzzle()` coin (via `dl_new_mirror`) that embeds an arbitrary, attacker-controlled URL string for *any* DataLayer `launcher_id`, with no ownership check tying the mirror to the store it targets. Any node that tracks or subscribes to that `launcher_id` will later ingest that URL as a mirror server and issue outbound `aiohttp` GET requests to it during sync, without any URL/scheme/host validation — the same SSRF bug class described in CVE-2021-28060 (forging GET requests via a URL parameter with no server-side allowlisting).

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a spend to `create_mirror_puzzle().get_tree_hash()` with `memos=[[launcher_id, *urls]]` and does not validate that `launcher_id` is owned by the spender, nor validate the URL contents: [1](#0-0) 

When any node observes such a coin (`coin_added`), if it already tracks that `launcher_id` (i.e., it owns or subscribes to that store), it decodes the URLs from the spend and persists them as a `Mirror` in its local `DataLayerStore`, with no URL validation: [2](#0-1) 

`DataLayer.update_subscriptions_from_wallet()` pulls all mirror URLs for the store and feeds them into the local subscription list unmodified: [3](#0-2) 

During `fetch_and_validate()`, the service iterates `servers_info` (which include the attacker-supplied mirror URL) and calls `insert_from_delta_file` → `download_file` → `http_download`, which performs `session.get(server_info.url + "/" + filename, ...)` directly, with no scheme restriction (e.g. `http://`, `https://`, or others accepted by `aiohttp`), no host allowlist, and no protection against internal/link-local/metadata addresses: [4](#0-3) [5](#0-4) 

The RPC/CLI-facing `add_mirror` path confirms mirror URLs are taken verbatim from user input with only an empty-list check: [6](#0-5) 

### Impact Explanation
Any unprivileged party who can submit a spend bundle (an ordinary XCH spend, no special privileges) can force any other DataLayer-participating node that tracks the target `launcher_id` (store owners and subscribers) to make outbound HTTP requests to attacker-chosen destinations — e.g., internal network services, cloud metadata endpoints (`169.254.169.254`), or localhost admin ports on the victim's machine — at the time DataLayer syncs. This is server-side request forgery from a fully remote, on-chain-only vector: no direct network connection to the victim is required, only knowledge of a `launcher_id` the victim subscribes to. This matches the "Medium" SSRF classification of the CVE analog (information disclosure/internal service probing/potential further pivoting), reachable purely from unauthenticated coin data any wallet can produce.

### Likelihood Explanation
Likelihood is moderate-to-high for active DataLayer users: creating a mirror coin is a normal, permissionless wallet operation (`dl_new_mirror`/`add_mirror` CLI/RPC), requires no special access to the victim, and the only precondition is that the victim tracks/subscribes to the targeted store — a routine DataLayer usage pattern (subscribing to shared stores, marketplaces, oracle feeds, etc.). The attack requires no signature forgery, no protocol violation, and executes automatically on the victim's next periodic sync (`periodically_manage_data()`).

### Recommendation
- Validate mirror URLs before persisting/using them: enforce an allowed scheme list (e.g., `http(s)` only), reject loopback/link-local/private/metadata IP ranges (SSRF-style blocklist or DNS-resolution-time check), and consider requiring an explicit user allowlist/opt-in for mirror servers rather than trusting on-chain-published URLs automatically.
- Ensure `insert_from_delta_file`/`http_download` re-validate the resolved URL/IP at request time (not just string form) to prevent DNS rebinding bypasses.
- Consider requiring `add_mirror`/`dl_new_mirror` to only be effective for stores actually owned by the calling wallet, or add a local user-side confirmation step before untrusted mirror URLs are added to `servers_info`/subscriptions.

### Proof of Concept
1. Attacker (any wallet, no special privileges) runs:
   `chia data add_mirror -i <victim_tracked_store_id> -u "http://169.254.169.254/latest/meta-data/" -a 1 -m 0`
   (calls `add_mirror_cmd` → `DataLayerRpcClient.add_mirror` → `DLNewMirror` RPC) as shown in [7](#0-6) .
2. This creates and pushes a mirror coin via `create_new_mirror()` with the malicious URL embedded in memos [1](#0-0) , with no check that the attacker owns `victim_tracked_store_id`.
3. Once confirmed on-chain, any victim node tracking that `launcher_id` ingests the mirror via `coin_added()` [2](#0-1)  and adds it to its subscription server list [3](#0-2) .
4. On the victim's next `periodically_manage_data()` cycle, `fetch_and_validate()` selects the malicious server and issues `http_download()`'s `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` [4](#0-3) , causing the victim's node to leak internal metadata/probe internal services on the attacker's behalf.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
