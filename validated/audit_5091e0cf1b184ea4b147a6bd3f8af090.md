### Title
Unbounded recursive memo parsing enables Python stack-overflow DoS via `PuzzleWithRestrictions.from_memo` - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody arrangement from an on-chain `Program` memo. When the memo indicates `further_branching` (an `MofN` node), it recurses into `PuzzleWithRestrictions.from_memo(memo)` once per member, with no depth or size limit. The recursion depth is entirely controlled by the shape of the memo `Program`, which is attacker-supplied data delivered as a coin memo/hint.

### Finding Description [1](#0-0) 

`from_memo` reads `further_branching_prog` from the memo and, if set, treats `puzzle_hint_prog` as an `MofNHint` whose `member_memos` are each parsed by another call to `PuzzleWithRestrictions.from_memo`. Because `MofN` members can themselves be `PuzzleWithRestrictions` containing further `MofN` nodes (as documented and tested in [2](#0-1)  and the module-level comment on recursive `MofN` reconstruction in [3](#0-2) ), an attacker can craft an arbitrarily deeply nested memo `Program` (e.g., depth of a few thousand) that causes `from_memo` to recurse past the Python interpreter's default recursion limit, raising `RecursionError` / crashing the process thread that is parsing it.

This is the same bug class as CVE-2016-9597: unbounded recursive parsing of untrusted structured input leading to native/interpreter stack exhaustion, rather than a CLVM-cost-metered operation. Unlike CLVM execution (which is metered by `run_with_cost`/`MAX_BLOCK_COST_CLVM`), this Python-level tree walk over a `Program` memo has no cost accounting and no explicit depth guard — contrasting directly with `sha256_treehash`, which the codebase deliberately made iterative specifically "to avoid Python recursion limits on deeply nested CLVM" ( [4](#0-3) ), showing the project is aware of this exact risk class elsewhere but did not apply the same mitigation here.

`Program` objects (`memo`) are cheaply constructed s-expressions built directly from bytes without CLVM execution cost, so an attacker does not need to pay CLVM execution cost to produce a deeply nested tree — only enough bytes to encode nested pairs, which is inexpensive relative to the resulting Python recursion depth.

### Impact Explanation
A successful trigger causes an unhandled `RecursionError` in the wallet process while it is reconstructing an unknown custody puzzle from a memo it received on-chain (e.g., syncing a coin whose memo/hint encodes a `PuzzleWithRestrictions`/`MofN` structure). Depending on call-site error handling, this can crash or hang the wallet sync/parsing path, denying service to that wallet client when processing an incoming coin. This matches the "spend-triggered transaction-processing halt" impact category (parsing halt on wallet side triggered by data associated with a submitted/received coin), analogous to CVE-2016-9597's stack-overflow DoS from recursive parsing of attacker-controlled structured input.

### Likelihood Explanation
Reachability depends on a wallet actually invoking `PuzzleWithRestrictions.from_memo` on attacker-supplied on-chain data during normal sync/recognition of an unknown puzzle. The only call sites found in the indexed codebase are within the test suite (`chia/_tests/clvm/test_custody_architecture.py`) and one reference in `chia/pools/plotnft_drivers.py`; I could not confirm from the available index that `from_memo` is invoked automatically and unconditionally during standard wallet coin-state sync for arbitrary/unrecognized incoming coins, as opposed to being invoked only in specific custody-wallet flows or on demand. This uncertainty affects confidence in real-world reachability by an unprivileged "coin sender," and should be verified against the full source (the index has coverage limits) before treating this as confirmed-exploitable in production wallet sync.

### Recommendation
Convert `PuzzleWithRestrictions.from_memo` (and the corresponding `MofNHint.from_program`/`memo()` round trip) to an iterative algorithm using an explicit stack, mirroring the pattern already used in `sha256_treehash`. Alternatively/additionally, enforce a maximum nesting depth (and maximum member count per `MofN` node) before recursing, rejecting memos that exceed a sane bound (e.g., matching realistic custody-arrangement depths), and ensure callers that parse untrusted memos catch `RecursionError`/`ValueError` so a malformed memo cannot crash the wallet process.

### Proof of Concept
Conceptually (cannot be executed here, but derivable from the parsing logic):
1. Construct a `Program` memo tree matching the `PuzzleWithRestrictions.memo()` shape for a `MofN` node whose single member is itself a `PuzzleWithRestrictions` memo with `further_branching=1`, and nest this pattern N times (e.g., N = 5,000–10,000), each layer minimal (`m=1`, one member, no restrictions).
2. Encode this nested `Program` as the memo hint associated with a coin sent to a victim wallet, or feed it directly to `PuzzleWithRestrictions.from_memo(memo)`.
3. Calling `from_memo` on the outer memo triggers N nested Python calls; once N exceeds the interpreter recursion limit, a `RecursionError` is raised, terminating/crashing the parsing call and, depending on the caller, the surrounding wallet operation. [1](#0-0)

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
