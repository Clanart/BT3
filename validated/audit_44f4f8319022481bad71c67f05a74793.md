### Title
Nested/Recursive Precompile Calls Cause Double-Application of Bank Balance-Change Events to EVM StateDB - ([File: precompiles/common/precompile.go], [File: precompiles/common/balance_handler.go])

### Summary
The `BalanceHandler` mechanism that synchronizes native `x/bank` coin-movement events into the EVM `StateDB` records only an event-index watermark (`prevEventsLen`) at the start of a precompile call and replays `events[prevEventsLen:]` at the end. This is structurally the same class of flaw as the `ReserveOracle.MAX_CHANGE` issue: a safeguard that is evaluated only "per call" rather than accounting for the cumulative/nested effects of multiple calls sharing the same underlying event stream within a single transaction. When a precompile call triggers a nested/recursive precompile invocation in the same EVM transaction, the same bank events can be replayed and applied to `StateDB.AddBalance`/`SubBalance` more than once.

### Finding Description
`Precompile.runNativeAction` (`precompiles/common/precompile.go:57-126`) creates a fresh `BalanceHandler` for *every* precompile invocation via `p.BalanceHandlerFactory.NewBalanceHandler()` [1](#0-0) , calls `BeforeBalanceChange(ctx)` which snapshots `len(ctx.EventManager().Events())` into `prevEventsLen` [2](#0-1) , then executes the native action, and finally calls `AfterBalanceChange(ctx, stateDB)` which iterates `events[bh.prevEventsLen:]` and applies `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events onto the StateDB [3](#0-2) .

The event manager (`ctx.EventManager()`) is not scoped per-call — it is the same underlying event log threaded through the cache context obtained from `stateDB.GetCacheContext()`. When a precompile's native action recursively invokes the EVM again (e.g. via `evmKeeper.CallEVMWithData`, demonstrated in the test/debug precompile `Call0` at `evmd/tests/testdata/debug/debug.go:58-75`) and that recursive call itself lands on a (possibly the same) precompile, a *second, independent* `BalanceHandler` is created for the inner call, with its own `prevEventsLen` recorded *after* the outer call has already started. The inner handler applies its own event slice to the StateDB correctly. However, when execution returns to the outer call, the outer handler's `AfterBalanceChange` still processes `events[outerPrevEventsLen:]`, which — because `prevEventsLen` is only an index into a shared, ever-growing event log — now also spans the events that were already emitted and already consumed by the inner call. Any bank event within that overlapping window gets applied to `StateDB.AddBalance`/`SubBalance` a second time by the outer handler.

This exact scenario is captured by the repository's own regression test `TestRecursivePrecompileCallsWithDebugPrecompile` (`evmd/tests/integration/balance_handler/balance_handler_test.go:43-106`), whose docstring explicitly states: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [4](#0-3) 

### Impact Explanation
Any protocol precompile registering a `BalanceHandlerFactory` (staking, distribution, gov, slashing, erc20, ics20 — confirmed via grep matches on `BalanceHandlerFactory` in `precompiles/distribution/distribution.go`, `precompiles/erc20/erc20.go`, `precompiles/gov/gov.go`, `precompiles/ics20/ics20.go`, `precompiles/slashing/slashing.go`, `precompiles/staking/staking.go`) is exposed to this pattern whenever a nested precompile call path exists (contract-to-contract recursion, or a precompile method that itself triggers another EVM call that reaches a precompile). If the double-applied event corresponds to a `CoinReceived` (mint-like) event, the caller's EVM `StateDB` balance would be credited twice for a single native bank transfer, producing an EVM-side balance that exceeds the true backing native/bank balance — i.e., unauthorized duplication of spendable EVM value with no corresponding native asset, breaking the 1:1 accounting invariant between native coins and EVM-visible balances. This falls squarely under the allowed "Critical unauthorized minting/duplication/accounting corruption of spendable user value across native balances, EVM balances... or precompile-mediated assets" impact class.

### Likelihood Explanation
The `MaxPrecompileCalls` bound (`x/vm/types/call.go:12-16`, enforced in `StateDB.AddPrecompileFn` at `x/vm/statedb/statedb.go:436-449`) limits the total number of precompile invocations per transaction to 20, but does not prevent nesting/recursion itself — it only caps how many nested calls can occur before the transaction reverts, so up to 20 levels of nested balance-changing precompile calls are permitted per transaction. The repository already contains a dedicated integration test and debug precompile purpose-built to reproduce this exact recursive scenario, indicating the maintainers are aware of and have specifically instrumented this bug class. However, I was not able to fully confirm within the available context whether this specific test currently passes (i.e., whether the bug has already been fixed by some other guard, such as re-fetching/clamping `prevEventsLen` relative to a monotonic call depth, or whether double-application is prevented by some deduplication not visible in the excerpts reviewed). The exact reachability from an unprivileged, non-owner-controlled production precompile path (e.g., whether `ERC20`/`ICS20`/`staking` methods can be chained to trigger genuine nested precompile-to-precompile recursion with real bank transfers, as opposed to only the `debug` precompile built for testing) could not be fully traced with the tools available.

### Recommendation
Scope `BalanceHandler` event tracking to be call-depth aware rather than a flat index into a shared event log — e.g., track events by reference/id already consumed globally (a monotonically advancing global watermark shared across nested handlers, updated after each `AfterBalanceChange` call, rather than a per-instance snapshot taken independently by each nested invocation), or explicitly disallow/isolate nested balance-changing precompile calls from re-processing the same event range. Add invariant checks that assert the summed native bank balance changes for `msg.sender`/related addresses within a transaction equal the summed StateDB balance deltas applied via `BalanceHandler`.

### Proof of Concept
The repository's own reproduction (`evmd/tests/integration/balance_handler/balance_handler_test.go:45-106`) deploys `DebugPrecompileCaller`, funds it, and calls `callback(0)` on the debug precompile, which recursively re-enters the EVM via `CallEVMWithData` ten times (`debug.go` `Call0`) while intermixing state-mutating precompile methods, then asserts on the resulting `debug_precompile` event count and total event count. This test scaffold is the minimal, reproducible harness needed to confirm whether balance-changing (`CoinSpent`/`CoinReceived`) events emitted inside the nested call get replayed by the outer call's `AfterBalanceChange`; a real-world variant of this PoC would replace the no-op `Call1` emit with an actual `bankKeeper.SendCoins` inside the recursive precompile path (as staking/distribution/erc20 precompiles do) and assert `StateDB.GetBalance` against the true native `x/bank` balance after the transaction to detect the double-credit. func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}
