## Title
Unsafe NFT transfer via CW→EVM ERC721 bridge payload can permanently freeze bridged NFTs - (File: `x/evm/client/wasm/query.go`)

### Summary
The wasmbinding query handler that lets CosmWasm contracts move an EVM-side ERC721 token on behalf of a Sei user builds calldata for the unsafe `transferFrom(address,address,uint256)` selector instead of `safeTransferFrom`. Any wasm contract (e.g. the CW721 pointer contract that wraps a real ERC721 collection) that uses this bridge to move a token to a recipient whose associated EVM address is a contract without `onERC721Received` support will permanently freeze that NFT.

### Finding Description
`HandleERC721TransferPayload` in `x/evm/client/wasm/query.go` packs the `transferFrom` selector (not `safeTransferFrom`) to move a real ERC721 token between two Sei-associated EVM addresses: [1](#0-0) 

This handler is reachable from any CosmWasm contract via the `erc721_transfer_payload` wasm query, dispatched in `wasmbinding/queries.go`: [2](#0-1) 

The example CW721 "pointer" wasm contract (a wasm-side representation of a real EVM ERC721 collection, used as the pattern for this bridge) invokes exactly this query to build a `DelegateCallEvm` message that performs the transfer: [3](#0-2) 

Notably, the corresponding ERC1155 bridge handler in the same file correctly uses the **safe** transfer selector: [4](#0-3) 

This inconsistency shows the ERC721 path was not given the same safety treatment. Since `transferFrom` on a standard OpenZeppelin ERC721 contract performs no receiver-capability check (only `safeTransferFrom` does), moving a token to a `recipient` bech32 address whose associated EVM address happens to be a contract account (e.g. a DEX, vault, multisig, or any contract that never registered to receive/handle NFTs) will succeed on-chain but leave the token stuck in that contract forever, since arbitrary contracts have no built-in mechanism to call `transferFrom`/`approve` on assets they never expected to hold.

### Impact Explanation
Any CosmWasm contract built on this bridge pattern (in-scope surface: "CW<->EVM pointers and the wasm bridge") that lets a user specify an arbitrary Sei recipient for an ERC721 transfer can cause permanent, irrecoverable loss of that NFT if the recipient's associated EVM address is a contract lacking NFT-withdrawal logic. This is a permanent freezing of a real, potentially valuable asset, meeting the "permanent freezing" impact bar for Medium severity.

### Likelihood Explanation
Likelihood is moderate: exploitation only requires (1) a wasm contract using this bridge helper as documented/exemplified by the shipped `example/cosmwasm/cw721` contract, and (2) an EVM-associated recipient address that is a contract without ERC721 receiver support (a common scenario, since many contracts have EVM addresses associated with Sei accounts that never anticipated receiving NFTs). No privileged access is needed — any unprivileged wasm caller of `transfer_nft`/`send_nft` on such a bridging contract can trigger the unsafe path.

### Recommendation
Change `HandleERC721TransferPayload` in `x/evm/client/wasm/query.go` to pack `safeTransferFrom(address,address,uint256)` instead of `transferFrom`, matching the safety pattern already used for `HandleERC1155TransferPayload`. If backward compatibility with non-ERC721Receiver-compliant recipients is required, consider exposing both a safe and an explicit "unsafe" variant, with the safe one as default.

### Proof of Concept
1. Deploy (or reuse) a wasm contract analogous to `example/cosmwasm/cw721`, which wraps a real EVM ERC721 collection and exposes `TransferNft`/`SendNft` messages backed by `erc721_transfer_payload`.
2. Associate a Sei address `X` with an EVM contract address `C` that does not implement `IERC721Receiver` (e.g., a plain vault/DEX contract with no NFT-handling code).
3. As the NFT owner, call `execute_transfer_nft`/`transfer_nft` on the wasm pointer/bridge contract with `recipient = X`.
4. `transfer_nft` → `erc721_transfer_payload` (`HandleERC721TransferPayload`) packs `transferFrom(owner, evmAddr(X)=C, tokenId)`, which succeeds because `transferFrom` does not check for receiver support.
5. The NFT is now owned by contract `C`, which has no function capable of calling `transferFrom`/`approve` to move it back out — the NFT is permanently frozen.

func (h *EVMQueryHandler) HandleERC721TransferPayload(ctx sdk.Context, from string, recipient string, tokenId string) ([]byte, error) {
	abi, err := cw721.Cw721MetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	fromEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(from))
	if !found {
		return nil, types.NewAssociationMissingErr(from)
	}
	toEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	t, ok := sdk.NewIntFromString(tokenId)
	if !ok {
		return nil, errors.New("invalid token ID for ERC721, must be a big Int")
	}
	bz, err := abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}

fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
