### Title
Zero-amount input escrowed via the predispatch path permanently locks an order's entire escrow in Tron `IntentGatewayV2` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.placeOrder` has two code paths for escrowing order inputs. The direct-transfer path rejects zero-amount inputs, but the predispatch (call-dispatcher) path does not. A resulting zero-value `_orders[commitment][token]` entry then unconditionally trips the `UnknownOrder()` revert inside `withdraw()`, which has no zero-amount skip (unlike the sibling implementation in `evm/src/apps/intentsv2/IntentsBase.sol`). This mirrors the M-12 pattern: a legitimate zero-value leg is not tolerated by the redemption path, but here the consequence is total, permanent loss of the order's escrowed funds rather than just an inconvenience.

### Finding Description
`placeOrder` validates `order.inputs[i].amount != 0` only on the non-predispatch branch: [1](#0-0) 

The predispatch branch, used when `order.predispatch.call.length > 0`, has no such guard — it computes `requiredAmount = order.inputs[i].amount`, checks only `balance < requiredAmount` (trivially satisfied when `requiredAmount == 0`), and still records the (zero) reduced amount into escrow: [2](#0-1) 

Consequently `_orders[commitment][token]` can be left at `0` for one of the order's input tokens. Every subsequent path that releases escrow (`fillOrder`'s `RedeemEscrow`, `cancelOrder`'s same-chain refund, and the cross-chain `RefundEscrow`/`RedeemEscrow` handler in `onAccept`) funnels into `withdraw()`: [3](#0-2) 

`withdraw()` iterates `body.tokens` (== `order.inputs`) and reverts with `UnknownOrder()` as soon as it reaches any token whose `_orders[commitment][token] == 0` — there is no `if (amount == 0) continue;` guard as exists in the parallel `IntentsBase.sol::_withdraw` implementation: [4](#0-3) 

Because the loop reverts on the zero-value token before any transfers occur, **none** of the order's tokens are released — not just the zero-value one, but every other legitimately escrowed input and any escrowed transaction fee for that commitment.

### Impact Explanation
Any order placed via the predispatch path with one input amount equal to zero becomes permanently unfillable, uncancellable, and unrefundable: `fillOrder`, `cancelOrder`, and the cross-chain redeem/refund handlers all revert with `UnknownOrder()` because they all terminate in `withdraw()`. All tokens escrowed for that commitment (including nonzero legs and fees) are locked in the contract with no recovery path — a direct, permanent loss of funds, matching the bounty's "loss of funds / fund lock" impact class.

### Likelihood Explanation
The direct-transfer path already treats a zero-amount input as invalid (`revert InvalidInput()`), showing the protocol intends to reject this case — but the predispatch path was never given the same guard, so the omission is a straightforward oversight rather than a hardened design choice. Any caller who supplies an `order.inputs` entry with `amount == 0` while using the predispatch/call-dispatcher flow (a normal, documented usage mode, not requiring any privileged role) triggers the bug purely through the public `placeOrder` entrypoint.

### Recommendation
- Add `if (order.inputs[i].amount == 0) revert InvalidInput();` inside the predispatch loop in `placeOrder` (mirroring line 446), preventing zero-amount escrow entries from ever being created.
- Defense in depth: add `if (amount == 0) continue;` inside `withdraw()` before the `_orders[...] == 0` check, matching the guard already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, so a zero-value leg (however it arises) cannot block release of the order's other escrowed assets.

### Proof of Concept
1. Attacker (or any user, even unintentionally) calls `placeOrder` with `order.predispatch.call.length > 0` and `order.predispatch.assets.length > 0`, and `order.inputs` containing two entries: token A with `amount = 100e18` and token B with `amount = 0`.
2. In the predispatch branch, token B's `requiredAmount == 0` passes the balance check trivially; `_orders[commitment][tokenB] += 0` leaves the entry at `0`, while `_orders[commitment][tokenA]` correctly records `100e18` (minus protocol fee).
3. A solver later calls `fillOrder`, or the user calls `cancelOrder`, or a `RedeemEscrow`/`RefundEscrow` message arrives via `onAccept` — all reach `withdraw(body, ...)` with `body.tokens == order.inputs` (both A and B).
4. The loop in `withdraw()` reaches token B, evaluates `_orders[commitment][tokenB] == 0`, and reverts with `UnknownOrder()` before token A's 100e18 is ever transferred.
5. The order can never be filled, cancelled, redeemed, or refunded — the escrowed 100e18 of token A is permanently locked in the contract.
