### Title
Unhandled `IndexError` in mempool canonical-CLVM check on malformed spend-bundle bytes causes transaction-processing crash - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the raw CLVM byte encoding of a submitted coin spend's `puzzle_reveal` and `solution` using direct, unchecked indexing into the input `bytes` buffer. A spend bundle with a truncated/malformed multi-byte atom length prefix (or an atom length that runs past the end of the buffer) makes these functions read past the end of `clvm_buffer`, raising an unhandled `IndexError` instead of returning a validation failure.

### Finding Description
`is_clvm_canonical()` is called directly on attacker-controlled bytes during mempool admission: [1](#0-0) 

Both `is_atom_canonical()` and `is_clvm_canonical()` index into `clvm_buffer` without ever checking `offset` against `len(clvm_buffer)`: [2](#0-1) [3](#0-2) 

Specifically:
- In `is_atom_canonical`, the loop `for i in range(prefix_len): offset += 1; atom_len |= clvm_buffer[offset]` assumes `prefix_len` extra bytes exist after the size-prefix byte. A buffer that ends exactly at or before that point (e.g., a single `0xC0` byte with no trailing byte) causes `clvm_buffer[offset]` to index out of range.
- In `is_clvm_canonical`, after computing `atom_len` the loop advances `offset += atom_len` and, if `tokens_left != 0`, immediately re-reads `b = clvm_buffer[offset]` on the next iteration without checking that `offset < len(clvm_buffer)`. A crafted atom-length value that overruns the buffer (while `tokens_left` remains nonzero, e.g. inside an open list `0xff...`) triggers the same out-of-range access.

This is the direct Python analog of the CVE's root cause class: a decoder that trusts an internal length/offset field derived from untrusted input and dereferences/indexes past the buffer end when the input is truncated or malformed, crashing the parser (there: NULL pointer dereference in `jbig2_huffman_get`; here: unhandled `IndexError` in the mempool's canonical-encoding check).

### Impact Explanation
`is_clvm_canonical()` runs synchronously inside `MempoolManager.validate_spend_bundle()`, which executes under the blockchain/mempool lock as part of transaction admission for every submitted spend bundle (RPC `push_tx`, peer `new_transaction`/`respond_transaction`, and wallet-submitted spends). An unhandled `IndexError` here is not caught by the existing `ValueError`/`ValidationError` handling in `FullNode.add_transaction()`: [4](#0-3) 

Since only `ValueError` and `ValidationError` are caught, an `IndexError` propagates as an unexpected exception out of the transaction-admission path while holding low-priority blockchain locking, which the project's own module notes describe as the atomic admission boundary between chain state and mempool insertion: [5](#0-4) 

This matches the "spend-triggered transaction-processing halt" impact class: a single crafted spend bundle can throw an unhandled exception during mempool admission processing, degrading or crashing the transaction-processing task/lock context rather than being cleanly rejected as `INVALID_COIN_SOLUTION`.

### Likelihood Explanation
Any unprivileged party can submit a spend bundle via the full-node RPC `push_tx` or via the peer transaction protocol; the coin's `puzzle_reveal`/`solution` bytes are fully attacker-controlled and are canonical-checked before any CLVM execution, VM cost, or signature validation rejects them. Crafting a truncated multi-byte atom length prefix, or an atom length exceeding the remaining buffer, is a small, mechanical malformation of otherwise-valid-looking CLVM bytes, making the trigger straightforward once the exact prefix/length boundary math is known.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before indexing `clvm_buffer[offset]` for the length-prefix bytes, and in `is_clvm_canonical()` before dereferencing `clvm_buffer[offset]` on every loop iteration (including immediately after `offset += atom_len`), returning `False` (non-canonical / reject) instead of allowing an `IndexError` to propagate. Additionally, wrap the canonical check (or `validate_spend_bundle`) with a defensive `except (IndexError, ...)` that maps to `Err.INVALID_COIN_SOLUTION` so malformed input is rejected as an ordinary validation failure rather than an unhandled exception during locked mempool admission.

### Proof of Concept
Construct a `CoinSpend` whose `puzzle_reveal` (or `solution`) bytes end immediately after a multi-byte atom size-prefix marker, e.g. `bytes([0xC0])` (5+8 bit length prefix expecting one more length byte that is absent), or a buffer such as `bytes([0xFF, 0xC0])` (opens a pair, then a truncated atom) so that `tokens_left` remains nonzero when the length computation runs past the buffer. Submitting a `SpendBundle` containing this `CoinSpend` through `push_tx` (or the peer tx protocol) drives execution into `MempoolManager.validate_spend_bundle()` → `is_clvm_canonical()` → `is_atom_canonical()`, where `clvm_buffer[offset]` raises `IndexError` instead of returning a clean `False`/`Err.INVALID_COIN_SOLUTION`, propagating out of the locked admission path uncaught by `FullNode.add_transaction()`'s `except ValueError`/`except ValidationError` handlers.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
