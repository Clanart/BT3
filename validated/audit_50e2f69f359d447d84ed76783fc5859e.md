### Title
Aggregator gRPC Server Has No Caller Authentication, Allowing Any Network-Reachable Party to Invoke Privileged Bridge Methods Including `InternalSendTx` - (File: core/src/servers.rs, core/src/rpc/interceptors.rs, core/src/config/mod.rs)

### Summary

The Clementine aggregator gRPC server is intentionally deployed without mTLS client-certificate verification (`Noop` interceptor). Unlike the operator and verifier, the aggregator is explicitly excluded from the mainnet `client_verification` enforcement check. Any network-reachable party can therefore call every aggregator RPC method — including `InternalSendTx`, `Withdraw`, `OptimisticPayout`, `Setup`, and `GetEntityStatuses` — without presenting any credential. This is the direct Clementine analog of the Snap's missing `onRpcRequest` origin validation: the trust boundary that should restrict who may invoke privileged bridge actions is absent at the aggregator's gRPC surface.

### Finding Description

**Root cause — `Noop` interceptor on the aggregator**

`create_grpc_server` selects the interceptor based on `config.client_verification`:

```rust
// core/src/servers.rs L114-138
let service = InterceptedService::new(
    service,
    if config.client_verification {
        OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
    } else {
        Noop   // ← passes every request unconditionally
    },
);
``` [1](#0-0) 

When `Noop` is active the `only_aggregator_and_self` function — which enforces mTLS peer-certificate pinning — is never called. [2](#0-1) 

**`check_mainnet_requirements` deliberately omits the Aggregator actor**

The mainnet guard that makes `client_verification=false` a fatal misconfiguration only covers `Verifier` and `Operator`:

```rust
// core/src/config/mod.rs L299-303
if matches!(actor_type, cli::Actor::Verifier | cli::Actor::Operator)
    && !self.client_verification
{
    misconfigs.push("CLIENT_VERIFICATION=false".to_string());
}
``` [3](#0-2) 

`cli::Actor::Aggregator` is absent. The aggregator therefore starts on mainnet with `Noop` and no error is raised. The code in `create_aggregator_grpc_server` even emits a `warn!` when client verification *is* enabled, confirming the unauthenticated path is the expected production path: [4](#0-3) 

**Exposed privileged methods**

The aggregator's gRPC service definition exposes, among others:

| Method | Privileged action |
|---|---|
| `InternalSendTx` | Queues an arbitrary pre-signed Bitcoin transaction for broadcast via `insert_try_to_send` |
| `Withdraw` | Fans out withdrawal requests to all operators |
| `OptimisticPayout` | Collects verifier partial signatures and broadcasts an optimistic payout tx |
| `Setup` | Re-initialises the entire verifier/operator key-exchange |
| `GetEntityStatuses` (with `restart_tasks=true`) | Restarts background automation tasks on every operator and verifier | [5](#0-4) 

**`InternalSendTx` — arbitrary transaction injection**

```rust
// core/src/rpc/aggregator.rs L1270-1311
async fn internal_send_tx(&self, request: Request<clementine::SendTxRequest>)
    -> Result<Response<Empty>, Status>
{
    let signed_tx: bitcoin::Transaction = send_tx_req.raw_tx…try_into()?;
    self.tx_sender.insert_try_to_send(&mut dbtx, None, &signed_tx, fee_type…).await…
}
``` [6](#0-5) 

No caller identity check precedes the `insert_try_to_send` call. Any unauthenticated caller can enqueue transactions.

### Impact Explanation

1. **Tx-sender queue flooding / liveness failure**: An attacker can submit thousands of syntactically valid but economically invalid transactions. The tx-sender will attempt to broadcast and fee-bump each one, exhausting Bitcoin RPC bandwidth and database capacity. Legitimate time-sensitive bridge transactions — kickoff, challenge, assert, disprove, reimbursement — may miss their timelocks. Operators that miss a challenge or disprove window lose their collateral (bridge amount + `operator_challenge_amount`).

2. **Forced `Setup` re-initialisation**: Calling `Setup` re-distributes operator parameters to all verifiers. Repeated calls can desynchronise verifier state and stall in-flight deposit sessions, permanently locking deposited BTC in the vault UTXO if the move-tx session is aborted.

3. **`GetEntityStatuses` with `restart_tasks=true`**: Restarts automation background tasks on every operator and verifier, interrupting in-progress challenge/disprove flows and potentially causing operators to miss timelocks.

4. **`Withdraw` / `OptimisticPayout` spam**: While these require a valid user taproot signature (which the attacker cannot forge), an attacker can replay observed withdrawal requests or submit crafted requests that cause operators to perform expensive on-chain lookups and signature verification, degrading availability.

### Likelihood Explanation

The aggregator's gRPC port is reachable by the clementine-backend service, which is typically internet-facing or at least reachable from the same network segment as external users. The `Noop` path is the documented and enforced production path for the aggregator. No credential is required — a standard gRPC client with TLS (no client cert) suffices. The attack requires only network access to the aggregator port.

### Recommendation

1. **Enforce caller authentication on the aggregator**: Add `cli::Actor::Aggregator` to the `check_mainnet_requirements` guard so that `client_verification=false` is a fatal misconfiguration for all actors on mainnet.

2. **Restrict `InternalSendTx` to self-calls only**: Prefix it with `Internal` (it already is) and ensure the aggregator's own interceptor enforces the `is_internal` → self-cert-only rule, mirroring the operator/verifier pattern.

3. **Rate-limit and authenticate `Setup` and `GetEntityStatuses`**: These state-mutating methods should require the aggregator's own client certificate or a separate admin credential.

### Proof of Concept

```
# 1. Obtain the aggregator's TLS server certificate (public, no client cert needed).
# 2. Connect with any gRPC client (e.g. grpcurl) using server-only TLS:

grpcurl -insecure \
  -d '{"raw_tx": {"raw_tx": "<hex of any syntactically valid Bitcoin tx>"}, "fee_type": 0}' \
  <aggregator_host>:<port> \
  clementine.ClementineAggregator/InternalSendTx

# Expected: Empty {} response (success) — transaction queued for broadcast.
# Repeat in a loop to flood the tx-sender queue.

# 3. Alternatively, restart all background tasks:
grpcurl -insecure \
  -d '{"restart_tasks": true}' \
  <aggregator_host>:<port> \
  clementine.ClementineAggregator/GetEntityStatuses
```
