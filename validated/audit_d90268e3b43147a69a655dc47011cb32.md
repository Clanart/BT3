### Title
Single `_minRec` value reused for multiple independent reward-token conversions in `ManualCompound.compound()` - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` accepts one `_minRec` slippage-protection parameter but applies it identically to every configured reward token that has a `convertor` set, even though each reward token can have a completely different received balance and a different converter contract. This mirrors the reported bug class in which a single `minAssetAmount` is incorrectly reused across multiple independent swap operations within one external call.

### Finding Description
`compound()` first claims rewards for an arbitrary set of pools via `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, then iterates over the full `rewards` array (configured independently by the owner via `addReward`/`setConvertor`) and, for every reward token that has a non-zero `receivedBalance` and a `convertor` set, calls: [1](#0-0) 

Each iteration passes the *same* caller-supplied `_minRec` to `IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2)` regardless of which token is being converted or how large its `receivedBalance` is: [2](#0-1) 

Downstream, `SmartWomConvert._convertFor` enforces the slippage check as an absolute floor on total output (`convertAmount + amountRec < _minRec`), not a per-unit ratio: [3](#0-2) 

Because the `rewards` array can hold multiple entries each independently pointed at a `convertor` (`addReward`/`setConvertor` impose no restriction that only one reward token may use a convertor), a single unprivileged `compound()` transaction can trigger multiple `convertFor` calls with wildly different `receivedBalance` values but one shared `_minRec` threshold: [4](#0-3) 

### Impact Explanation
- If `_minRec` is calibrated for a large-balance reward token but a smaller-balance reward token is also converted in the same call, the smaller conversion will revert (`MinRecNotMatch`), reverting the entire `compound()` transaction and blocking harvesting/compounding for all pools/rewards claimed in that call (a caller-facing denial-of-service on that batch, requiring the user to retry with a lower threshold, which then weakens protection for the larger conversion).
- If `_minRec` is calibrated low enough to accommodate the smallest conversion, it provides insufficient slippage protection for larger conversions, allowing the caller (or an MEV actor front-running the same transaction) to extract value via sandwiching the WOM→mWom buyback swap inside `SmartWomConvert`, resulting in the user's compounded yield converting at a worse-than-expected rate — a loss of unclaimed/yet-to-be-locked yield for the compounding user.

### Likelihood Explanation
This is reachable by any unprivileged wallet simply by calling `compound()` with multiple pools/reward tokens that have convertors configured; no admin or governance action is needed to trigger it once the (owner-controlled) reward/convertor configuration includes more than one convertible token. Given the current codebase only clearly wires `SmartWomConvert` for the WOM reward, the practical severity depends on the owner's reward configuration, but the code path unconditionally permits multiple convertor-enabled rewards and reuses one `_minRec` for all of them, so the vulnerability is a structural design flaw rather than a hypothetical edge case.

### Recommendation
Change `compound()` to accept an array of `_minRec` values (one per reward-token slot, parallel to the `rewards` array) instead of a single scalar, and pass the corresponding per-token minimum to each `convertFor` call. Alternatively, compute the minimum acceptable output using an on-chain price/ratio check (e.g., via `estimateTotalConversion`) scaled to each token's actual `receivedBalance`.

### Proof of Concept
1. Owner configures two reward tokens in `ManualCompound`, both with `convertor = SmartWomConvert` address (or two different converters), via `addReward`/`setConvertor`.
2. A user calls `compound(_lps, _rewards, _convertRatio, _minRec, _lockMgp)` where the claim yields a large balance of reward token A and a small balance of reward token B.
3. The loop at [1](#0-0)  calls `convertFor(balanceA, _convertRatio, _minRec, msg.sender, 2)` then `convertFor(balanceB, _convertRatio, _minRec, msg.sender, 2)` using the identical `_minRec`.
4. If `_minRec` is sized for balance A, the call for token B reverts with `MinRecNotMatch` in `SmartWomConvert._convertFor` [5](#0-4) , reverting the whole `compound()` transaction and blocking the user's legitimate compounding of token A as well.

        uint256 rewardTokensLength = rewards.length;        
        IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
        // send none compoundable reward back to caller
        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
        for (uint256 i; i< rewardTokensLength; i++) {
            address _tokenAddress = rewards[i].tokenAddress;
            address _helperAddress = rewards[i].tokenHelper;
            address _convertor = rewards[i].convertor;
            address _locker = rewards[i].locker;
            uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));

            if (receivedBalance > 0) {
                if (_convertor != address(0)) {
                    IERC20(_tokenAddress).safeApprove(_convertor, receivedBalance);
                    IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2);
                } else if (_locker != address(0) && _lockMgp) {
                    IERC20(_tokenAddress).safeApprove(_locker, receivedBalance);
                    ILocker(_locker).lockFor(receivedBalance, msg.sender);                        
                } else if (_helperAddress != address(0)) { 
                    IERC20(_tokenAddress).safeApprove(_helperAddress, receivedBalance);
                    ISimpleHelper(_helperAddress).depositFor(receivedBalance, msg.sender);
                } else {
                    IERC20(_tokenAddress).safeTransfer(msg.sender, receivedBalance);
                }
            }
        }

        emit Compounded(msg.sender, rewardTokensLength, _lockMgp);
    }
