### Title
Fixed-cost precompile signature verification is underpriced relative to attacker-controlled message size - (File: `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, `cost-model/src/block_cost_limits.rs`)

### Summary
The `secp256k1` and `ed25519` precompiles perform message hashing/signature verification whose cost scales with the message length embedded in the instruction (up to ~64 KB per signature, and up to 255 signatures per instruction), but the compute cost charged for this work is a fixed, per-signature constant (`SECP256K1_VERIFY_COST = 6690`, `ED25519_VERIFY_STRICT_COST = 2400`) that does not scale with the actual amount of data hashed/processed.

### Finding Description
`agave_precompiles::secp256k1::verify` reads a `message_data_size` (a `u16`, so up to 65535 bytes) out of attacker-controlled instruction offsets and hashes the referenced slice with keccak256 before running `libsecp256k1::recover`, as seen in [1](#0-0) . Similarly, `agave_precompiles::ed25519::verify` reads a message slice of size `offsets.message_data_size` and calls `verify_strict` on it, per [2](#0-1) . The benches in `precompiles/benches/secp256k1_instructions.rs` and `precompiles/benches/ed25519_instructions.rs` confirm the message length can be as large as `u16::MAX` per instruction [3](#0-2) .

Despite this, the cost model attributes a single, size-independent cost per signature: `SIGNATURE_COST`, `SECP256K1_VERIFY_COST`, and `ED25519_VERIFY_STRICT_COST`, all defined as flat products of `COMPUTE_UNIT_TO_US_RATIO` with no dependency on `message_data_size`, in [4](#0-3) . These are the values summed by `CostModel::get_signature_cost` and applied per instruction-signature count, in [5](#0-4) .

At execution time, the actual precompile work is invoked from `InvokeContext::process_precompile`, which pushes the frame and calls the verification callback but never consumes any compute units from `invoke_context.compute_meter` for the verification work itself: [6](#0-5) . This is in contrast to essentially every other cryptographic syscall in the runtime — e.g. `SyscallCurvePointValidation`, `SyscallBigModExp`, BLS12-381 group operations, and `alt_bn128` pairing — which all charge `invoke_context.compute_meter.consume_checked(cost)` proportional to input size before doing the work, as seen throughout `syscalls/src/lib.rs` (e.g. [7](#0-6)  for `alt_bn128` pairing, whose cost explicitly scales `saturating_add(input_size)`).

This is structurally the same bug class described in the Linea report: a fixed refund/cost constant is used where the real work is variable and attacker/user-controlled (there, Merkle proof depth; here, precompile message length and signature count), so once the variable component grows large enough, the fixed charge undershoots the real cost of the work performed.

### Impact Explanation
An unprivileged transaction sender can construct `secp256k1`/`ed25519` precompile instructions with the maximum allowed message size (~64 KB) and the maximum signature count (255) packed into a single instruction, forcing the leader/validators to perform keccak256/SHA-512 hashing and ECDSA/EdDSA verification over tens of megabytes of data per transaction, while the transaction is billed only the fixed per-signature CU cost from `block_cost_limits.rs`. Because this cost feeds directly into the cost-model's block-inclusion accounting (`MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`) and into transaction fee calculation, an attacker can cheaply pack many such transactions into a block, consuming disproportionate CPU time relative to the compute units charged — a compute-underpricing / resource-exhaustion vector reachable by any ordinary user without special privileges.

### Likelihood Explanation
High: constructing maximal-size precompile instructions requires no special access, just standard instruction/offset construction as already exercised by the repository's own benchmarks (`precompiles/benches/secp256k1_instructions.rs`, `precompiles/benches/ed25519_instructions.rs`), which explicitly test message sizes up to `u16::MAX`.

### Recommendation
Charge compute units for `secp256k1`/`ed25519` (and `secp256r1`) precompile verification proportional to the actual bytes hashed/verified (analogous to `sha256_byte_cost` or the `alt_bn128` pairing model that adds `input_size` to the base cost), rather than a single flat per-signature constant, and enforce this charge inside `InvokeContext::process_precompile` via `compute_meter.consume_checked` rather than relying solely on the static per-transaction cost-model estimate.

### Proof of Concept
1. Construct a `secp256k1_program` instruction with `count = 255` and, for each signature, `message_data_size = 65535` (near max), referencing a large accompanying instruction payload — following the pattern used in `precompiles/src/secp256k1.rs` tests/benches (`new_secp256k1_instruction_with_signature`), scaled to `TX_COUNT`-style large messages as in the `bench_secp256k1_len_max` bench.
2. Submit the transaction; the cost model charges only `255 * SECP256K1_VERIFY_COST` (a fixed value from `cost-model/src/block_cost_limits.rs`), independent of the ~16 MB of message data that must actually be keccak-hashed and secp256k1-recovered during `agave_precompiles::secp256k1::verify`.
3. Compare the CPU time consumed (proportional to total message bytes) against the compute units billed for cost-model/block-limit purposes to demonstrate the constant-vs-linear mismatch, mirroring the Linea report's methodology of comparing "actual gas cost" against "current refund" across increasing payload sizes.

    fn get_signature_cost(transaction: &impl TransactionMeta) -> u64 {
        let signatures_count_detail = transaction.signature_details();

        signatures_count_detail
            .num_transaction_signatures()
            .saturating_mul(SIGNATURE_COST)
            .saturating_add(
                signatures_count_detail
                    .num_secp256k1_instruction_signatures()
                    .saturating_mul(SECP256K1_VERIFY_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_ed25519_instruction_signatures()
                    .saturating_mul(ED25519_VERIFY_STRICT_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_secp256r1_instruction_signatures()
                    .saturating_mul(SECP256R1_VERIFY_COST),
            )
    }

    /// Processes a precompile instruction
    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn process_precompile(
        &mut self,
        program_id: &Pubkey,
        instruction_data: &[u8],
        message_instruction_datas_iter: impl Iterator<Item = &'ix_data [u8]>,
    ) -> Result<(), InstructionError> {
        self.push()?;
        let instruction_datas: Vec<_> = message_instruction_datas_iter.collect();
        self.environment_config
            .epoch_stake_callback
            .process_precompile(program_id, instruction_data, instruction_datas)
            .map_err(InstructionError::from)
            .and(self.pop())
    }
