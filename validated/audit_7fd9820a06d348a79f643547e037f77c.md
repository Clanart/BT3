## #Vulnerability found for this question.

### Title
Symlink-based path escape in `getWorkingDirectoryImage` allows reading files outside the repository - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage`, which is invoked from the working-directory image-diff path reachable via the DiffOptions-equipped changes header, joins an attacker-influenced `file.path` directly onto the repository root and reads it with no containment check, unlike other parts of the codebase that guard the same class of read with a symlink-aware `resolveWithin`.

### Finding Description
`getWorkingDirectoryImage` builds the path to read purely with `Path.join` and passes it straight to `readFile`: [1](#0-0) 

`Path.join`/`readFile` do not dereference-check: if the working-directory entry at `file.path` is a symlink whose target lies outside the repository (e.g. a symlink blob `mode 120000` committed by a malicious remote, pointing to `../../../../etc/passwd` or an absolute path such as `~/.ssh/id_rsa`), `readFile` follows the symlink and returns the contents of the out-of-repo target. `file.path` itself never contains `..` segments (git status reports it as a normal working-directory relative path), so the traversal happens purely through the filesystem symlink, not through the string `file.path`.

This is exactly the class of bug the codebase already defends against elsewhere: `buildConflictContext` in `copilot-conflict-context.ts` explicitly calls `resolveWithin` (which does `realpath` on both the root and the resolved path and verifies the real path is still under the real root) before reading any file content that will be sent onward: [2](#0-1) 

The `resolveWithin` helper (and its test coverage, including the explicit "fails for paths that use a symlink to traverse outside of the root" case) exists precisely to prevent this: [3](#0-2) [4](#0-3) 

`getWorkingDirectoryImage` does not use `resolveWithin` (or any `lstat`/`realpath` check) at all, so the containment invariant that other file-reading paths enforce is broken here. The call reaches this function from `getImageDiff`, which is used by `getWorkingDirectoryDiff`/`convertDiff` for binary image extensions, itself driven by the working-directory file selection surfaced in the Changes list/diff viewer (the DiffOptions-equipped header): [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who controls a repository (or its content via a checkout the user performs) can commit a symlink at any path with an image-like extension (e.g. `evil.png`) pointing at an arbitrary absolute path outside the repository. When the user opens that repository in Desktop and views the working-directory diff for that entry, `getWorkingDirectoryImage` follows the symlink, reads the target file's bytes, base64-encodes them into an `Image`, and that content is rendered directly in the UI (an `<img>` data URI) — disclosing local file contents (potentially secrets such as SSH keys, tokens, or other sensitive files readable by the Desktop process) that are outside the intended repository scope. This matches the "read outside the repo" impact category.

### Likelihood Explanation
Requires the user to clone/fetch a malicious repository and have a symlinked, image-extension entry appear as a changed/untracked file in the working directory, then view its diff — a plausible sequence of normal user actions when interacting with an untrusted repository, and does not require local access, malware, or credentials. It is platform-dependent (macOS/Linux checkouts create real symlinks for `120000` mode blobs; Windows behavior can differ), which somewhat limits universal reach but still leaves a broad affected population.

### Recommendation
Route `getWorkingDirectoryImage` (and other working-directory readers in `diff.ts` that do raw `Path.join(repository.path, file.path)` + `readFile`, such as `buildSubmoduleDiff`'s full-path construction and the syntax-highlighting `getNewFileContent`) through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` from `app/src/lib/path.ts`, returning an error/placeholder image when the resolved real path is `null` (outside the repository), mirroring the pattern already used in `buildConflictContext`.

### Proof of Concept
1. Create a repository containing a symlink entry `evil.png` (git mode `120000`) whose target is an absolute path outside the repo, e.g. a sensitive local file.
2. Clone/check out this repository with GitHub Desktop on macOS/Linux so the symlink materializes in the working directory.
3. In the Changes list, select `evil.png`; Desktop calls `getWorkingDirectoryDiff` → `convertDiff` → `getImageDiff` → `getWorkingDirectoryImage(repository, file)`.
4. Observe that `readFile(Path.join(repository.path, 'evil.png'))` follows the symlink and returns the target file's bytes, which get base64-encoded and rendered as an image in the diff viewer — confirming disclosure of content outside `repository.path`. This mirrors the containment tests already present in `app/test/unit/path-test.ts` for `resolveWithin`, which `getWorkingDirectoryImage` does not use.

export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
