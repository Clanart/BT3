### Title
Gasless LendTx repayment uses nominal `Fee()` (GasLimit × GasPrice) instead of actual gas used, letting users pocket unused gas refund at the proposer's expense - (File: kaiax/gasless/impl/getter.go)

### Summary
The gasless module's `lendAmount`/`repayAmount` unit conversion is based on the *nominal* transaction fee (`GasLimit * GasPrice`, i.e. `tx.Fee()`), not the *actual* fee consumed during execution (`GasUsed * effectiveGasPrice`). This mismatch — analogous to the reported "overcomplicated unit conversions" pattern where a fixed-rate accounting value is confused with a variable, execution-dependent one — creates a value leak: unused gas is refunded to the transaction sender's own EOA rather than being reclaimed by the block proposer who funded the loan.

### Finding Description
`GetLendTxGenerator` funds the gasless sender with `lendAmount(approveTxOrNil, swapTx)`: [1](#0-0) 

This is computed from `tx.Fee()` for both the approve and swap transactions, which represents the worst-case nominal cost (`GasLimit * GasPrice`), not the actual gas consumed. The corresponding on-chain `amountRepay` that the sender must repay is likewise computed from the same nominal quantities in `repayAmount`: [2](#0-1) 
and is enforced as an equality check in `VerifyExecutable` (SP4): [3](#0-2) 

However, when the approve/swap transactions actually execute, `buyGas()` deducts the *nominal* `mgval = Gas * gasPrice` up front from the sender's balance, and after execution `returnGas()` refunds the unused portion (`remaining = st.gas * gasPrice`) back to the same address (`validatedFeePayer`, which equals the sender for non-fee-delegated approve/swap transactions): [4](#0-3) 

Because the lent amount (`R2+R3`) is deposited into the sender's own EOA before execution, and the unused-gas refund from `returnGas()` is credited back to that same EOA, any margin between the fixed gas limits used to compute `lendAmount`/`repayAmount` and the actual gas consumed by the approve/swap calls accrues permanently to the sender. The `amountRepay` collected by the swap router is funded independently from the token-swap proceeds (a separate value stream), so it does not claw back this leftover gas refund. The repayment accounting therefore never reconciles nominal vs. actual gas cost — the exact "unit conversion" confusion pattern flagged in the source report (mixing a rate-based/worst-case value with an actual-consumption value without reconciliation), unlike the reconciliation logic already present elsewhere in the codebase for exactly this purpose (`AdjustFeesByReceipts`, which explicitly corrects "the estimated intrinsic gas fee ... against the actual gas used"): [5](#0-4) 

No equivalent reconciliation exists for the production gasless lend/repay flow.

### Impact Explanation
Every gasless transaction pair (approve + swap) that consumes less gas than its statically assumed limit produces a net native-token windfall for the sender, extracted from the block proposer who funded the `LendTx`. Since the gas limits used for `lendAmount`/`repayAmount` are fixed, generous, worst-case values (covering constructor/authorization overhead etc.), and typical ERC-20 `approve`/router `swapForGas` calls consume noticeably less gas than their limit, this margin is systematically and repeatedly extractable by any unprivileged public RPC caller submitting gasless bid/swap transactions — a "gasless user" is explicitly one of the in-scope reachable actors. This constitutes unauthorized value movement (fee-delegation/gasless settlement leakage) from the proposer to the transaction sender on every gasless transaction.

### Likelihood Explanation
High likelihood: no special privileges are needed — any external account can submit a `GaslessApproveTx`/`GaslessSwapTx` pair through the public RPC (`SubmitBid`/tx pool `Ready` promotion described in the gasless README), triggering `GetLendTxGenerator` and the mismatched nominal-vs-actual accounting on every execution. The gas-limit constants are fixed and known in advance, so the exploitable margin is deterministic and repeatable at will.

### Recommendation
Reconcile the lend/repay amounts against the actual gas consumed rather than the nominal gas-limit-based fee, e.g., either (a) have the `LendTx`/repay accounting use `GasUsed * effectiveGasPrice` determined after execution (similar to the `AdjustFeesByReceipts` correction pattern already present in the test account-map utility), or (b) explicitly claw back any unused-gas refund credited to the gasless sender's EOA back to the proposer/rewardbase as part of block finalization for gasless bundles. Document and unify all gas-fee unit conversions (nominal vs. actual, GasLimit vs. GasUsed) used across `lendAmount`, `repayAmount`, and `buyGas`/`returnGas` to avoid this class of accounting drift.

### Proof of Concept
1. A user submits `GaslessApproveTx` (nonce N, to=ERC20 token, `approve(router, MaxUint256)`) followed by `GaslessSwapTx` (nonce N+1, to=SwapRouter, `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)`), both legacy-type transactions per `decodeFunctionCall`'s legacy-only restriction.
2. The proposer's block-building logic invokes `GetLendTxGenerator`, transferring `lendAmount = ApproveTx.Fee() + SwapTx.Fee()` (i.e., `GasLimit_approve * GasPrice + GasLimit_swap * GasPrice`) to the sender's EOA [6](#0-5) .
3. `ApproveTx` and `SwapTx` execute; `buyGas` deducts nominal fee up front, `returnGas` refunds `(GasLimit - GasUsed) * GasPrice` back to the sender's own EOA [4](#0-3) , since actual gas used (e.g. ~46,000 for a standard `approve`, well under the 100,000 assumed) is materially less than the fixed limit.
4. The `SwapForGas` router call repays exactly `amountRepay` (nominal, matching `repayAmount()`) from the swap output, satisfying the `VerifyExecutable` SP4 check, but this repayment is funded from swap proceeds, not from the leftover native-token refund sitting in the sender's wallet.
5. Net result: the sender retains `(GasLimit_approve - GasUsed_approve + GasLimit_swap - GasUsed_swap) * GasPrice` in native KAIA that was originally supplied by the proposer's `LendTx` and is never reclaimed — repeatable on every gasless transaction pair.

Note: I was unable to inspect the Solidity source of the `GaslessSwapRouter`/`swapForGas` implementation (only Go bindings were indexed) to confirm the exact fund-flow of `amountRepay` inside the contract; this may affect whether the leftover refund is fully unrecoverable or partially offset elsewhere. A Devin session with full repository access could verify the router contract logic directly to confirm the exact economic impact.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

// returnGas returns KAIA for remaining gas, exchanged at the original rate.
func (st *StateTransition) returnGas() {
	remaining := new(big.Int).Mul(new(big.Int).SetUint64(st.gas), st.gasPrice)

	validatedFeePayer := st.msg.ValidatedFeePayer()
	validatedSender := st.msg.ValidatedSender()
	feeRatio, isRatioTx := st.msg.FeeRatio()
	if isRatioTx {
		feePayer, feeSender := types.CalcFeeWithRatio(feeRatio, remaining)

		st.state.AddBalance(validatedFeePayer, feePayer)
		st.state.AddBalance(validatedSender, feeSender)
	} else {
		// To make a short circuit, the below routine processes when feeRatio == 100.
		st.state.AddBalance(validatedFeePayer, remaining)
	}
