### Title
Operator accepts a `TapSighashType::None`/`NonePlusAnyoneCanPay` payout signature that commits to zero outputs, letting the payout destination/amount be swapped after signing - (File: core/src/operator.rs)

### Summary
`Operator::withdraw` verifies the user-supplied `taproot::Signature` using whatever `sighash_type` is embedded in it, with no enforcement that it must be `SinglePlusAnyoneCanPay` (only a post-hoc error-message hint says so). If the signature carries `TapSighashType::None`, the BIP-341 sighash it authorizes contains no commitment to any transaction output, so the exact same `(signature, sighash)` pair validates for arbitrary `(out_script_pubkey, out_amount)` pairs passed into `create_payout_txhandler`.

### Finding Description
The claimed binding is: `sighash committed under in_signature.sighash_type` == `output_txout actually paid by create_payout_txhandler`. This binding is broken.

`Operator::withdraw` (`core/src/operator.rs:560-637`) builds `output_txout` directly from the caller-supplied `out_script_pubkey`/`out_amount`, constructs `payout_txhandler` via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`, output written at lines 416/428), computes `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)`, and calls: [1](#0-0) 

Only the *input* side of `create_payout_txhandler` is cross-checked against Citrea's recorded state (`withdrawal_utxo != input_utxo.outpoint`, `core/src/operator.rs:594-596`); `out_script_pubkey`/`out_amount` are never checked against anything else — the signature is the sole authorization for the payout destination.

`calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`) only special-cases the `*PlusAnyoneCanPay` variants for the `Prevouts` selection; plain `TapSighashType::None` falls into `_ => Prevouts::All(&prevouts_vec)`. This only affects which *inputs* are committed — per BIP-341, `SIGHASH_NONE` (with or without ANYONECANPAY) never includes an output commitment (`sha_outputs` is omitted). Since the payout tx has exactly one input, the resulting sighash for `TapSighashType::None` is identical no matter what `output_txout`/`out_amount`/OP_RETURN is placed on the transaction — the destination is entirely unauthenticated by the signature.

The code comment `"Ensure the signature uses SinglePlusAnyoneCanPay sighash type"` (`core/src/operator.rs:637`) confirms the intended design required output-binding sighash types, but no code path enforces `in_signature.sighash_type ∈ {SinglePlusAnyoneCanPay, All, Default}`.

### Impact Explanation
Because the withdrawal-input check only pins the *input* outpoint (already spent once from the vault-fronted move), a `None`-type signature can be replayed across multiple `Operator::withdraw` invocations for the same `withdrawal_index` with different `out_script_pubkey`/`out_amount`, all passing `SECP.verify_schnorr`. This lets a party controlling the withdrawal registration and the RPC parameters redirect vault-fronted payout value to a destination never actually authorized by the signer's intended commitment, or cause the operator to construct/broadcast multiple divergent payouts against a single registered Citrea withdrawal — moving BTC to an unauthorized destination or causing operator funds to be spent without matching, provably-committed authorization. This matches the Critical category "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal."

### Likelihood Explanation
The only precondition is that the withdrawing party crafts a `taproot::Signature` with `sighash_type = TapSighashType::None` (or `NonePlusAnyoneCanPay`) instead of the intended `SinglePlusAnyoneCanPay`, which costs nothing extra and is entirely within an unprivileged withdrawer's control (they choose their own signature and sighash flag). No hashrate, key compromise, or privileged role is required — only the ability to register a withdrawal and submit the resulting parameters to whatever public entry point ultimately calls `Operator::withdraw`.

### Recommendation
Explicitly reject any `in_signature.sighash_type` other than the intended output-binding type(s) (e.g., require `TapSighashType::SinglePlusAnyoneCanPay`, or `All`) before computing/verifying the sighash in `Operator::withdraw`, rather than relying on an error-message comment.
