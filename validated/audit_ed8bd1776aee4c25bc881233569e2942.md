## Title
Stale line-selection state used against a freshly re-diffed file allows silent corruption of partial commits — (`File: app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets users stage a subset of lines/hunks from a file (a "partial commit"). The line selection (`DiffSelection`) is computed by the renderer against a diff snapshot that can be arbitrarily old by the time the commit actually executes. When the commit is finally created, `applyPatchToIndex` re-runs `git diff` against the *current* on-disk content and reuses the old selection's absolute line indices to build the patch. If the file's content on disk has shifted between the time the selection was made and the time of commit, the selection indices no longer correspond to the same logical lines, and Desktop silently stages/comits different content than what the user reviewed and picked — with no re-validation or error. This mirrors the Timeswap bug class: a cached/derived state (`fee growth`/here, `line selection`) is not refreshed against the authoritative current state before a state-mutating action (`mint`/here, `commit`) is performed.

### Finding Description
The partial-commit flow works as follows:

1. The renderer loads a diff and lets the user pick lines via `_selectWorkingDirectoryFiles` → `updateChangesWorkingDirectoryDiff`, which fetches a diff and reconciles selectable lines [1](#0-0) .
2. Later, when the user clicks Commit, `_commitIncludedChanges` reads the files/selection currently cached in `repositoryStateCache` (which may be based on a diff loaded much earlier) and passes them straight to `createCommit` [2](#0-1) .
3. `createCommit` calls `stageFiles`, which for partially-selected files calls `applyPatchToIndex` [3](#0-2) [4](#0-3) .
4. `applyPatchToIndex` re-fetches the diff fresh from disk via `getWorkingDirectoryDiff` at commit time — not the diff the selection was originally computed against — and immediately builds the patch from it using the (potentially stale) `file.selection` object: [5](#0-4) .
5. `formatPatch` decides which lines to include purely by calling `file.selection.isSelected(absoluteIndex)` against the *newly fetched* diff's hunk line indices [6](#0-5) .

The disconnect: `DiffSelection` line indices are positional (`hunk.unifiedDiffStart + lineIndex`), not tied to file content hashes. There is no check anywhere in this path that the diff used to build the selection is the same diff being patched against. The renderer does attempt to reconcile selectable lines when the *renderer's own copy* of the diff changes (`updateChangesWorkingDirectoryDiff`, `withSelectableLines`) [7](#0-6) , but this reconciliation only runs as a side effect of the renderer polling/reloading the diff — it is not guaranteed to run, and is not re-verified at the moment `createCommit`/`applyPatchToIndex` actually executes. If the on-disk content changes between the last renderer reconciliation and the commit git-diff re-fetch (e.g., due to a `.gitattributes` clean/smudge filter, `post-checkout`/`pre-commit` hook, or any file-content-rewriting side effect triggered by a background `git status`/`git diff` that Desktop runs periodically), the indices silently point at different logical lines in the new hunks.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user who reviews a diff, selects specific lines to include (e.g., excluding a secret, excluding an unrelated change, or including only a safe subset), can end up committing and pushing content they never intended — without any warning, since `applyPatchToIndex`/`formatPatch` never error out; they just produce a patch from whatever the (mis-mapped) indices happen to select. Because a cloned/fetched malicious repository fully controls `.gitattributes` filters and hook scripts that run as part of normal git plumbing invoked in the background by Desktop, the attacker-controlled repository is the exact "attacker controls a cloned/fetched repository" primitive in scope.

### Likelihood Explanation
The window between diff-load and commit is normal user behavior (review diff, decide what to stage, click Commit) and can be long. Desktop already runs frequent background `git status`/`git diff` operations to keep its UI fresh, any of which can trigger a repository-defined clean/smudge filter or shell hook if present in `.gitattributes`/`.git/hooks` of a maliciously crafted cloned repo. No unusual local access or admin rights are required — only that the victim cloned/opened the malicious repository and used the ordinary partial-commit feature.

### Recommendation
Before generating the patch in `applyPatchToIndex`, verify that the diff being patched matches the diff the selection was computed from (e.g., by comparing a content hash/blob OID captured when the selection was made, not just positional indices), and refuse/re-prompt the user if the file has changed on disk since the selection was made, rather than silently applying stale indices to a new diff.

### Proof of Concept
1. Attacker publishes a repository with a `.gitattributes` clean/smudge filter (or `pre-commit` hook) that rewrites a tracked file's content the moment any `git diff`/`git status`/`git commit` touches it (e.g., inserting/removing lines near the top of the file).
2. Victim clones the repo in Desktop, edits the file, and opens Changes; Desktop computes a diff and the victim selects a specific subset of lines for a partial commit (e.g., only lines 40–45, deliberately excluding lines 1–10).
3. Victim leaves Desktop open for a while (or performs other actions causing Desktop's periodic background status/diff refresh via `getStatus`/`getWorkingDirectoryDiff`) — the filter/hook rewrites the file, shifting line numbers.
4. Victim clicks Commit. `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` re-runs `git diff` on the now-shifted content [8](#0-7)  and `formatPatch` applies the victim's original absolute-index selection to the new hunks [9](#0-8) , silently including/excluding different lines than what the victim actually reviewed and chose, with the commit succeeding without any warning.
