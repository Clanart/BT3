### Title
Attacker can front-run `queueNewRewards` by staking a dust amount to capture nearly the entire reward distribution via `_provisionReward` - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` computes `rewardPerTokenStored` as a function of the *current spot* `totalStaked()` balance rather than a time-weighted or checkpointed value. Because staking into the pool is fully permissionless via `MasterMagpie.deposit`, an attacker can front-run a manager's `queueNewRewards` call by depositing a tiny (e.g. 1 wei) amount of `stakingToken` right before it, causing the entire reward to be credited almost exclusively to their dust position.

### Finding Description
`_provisionReward` in [1](#0-0)  updates the global accumulator as:
```
rewardInfo.rewardPerTokenStored += (_amountReward + queuedRewards) * 10**stakingDecimals() / this.totalStaked();
```
`totalStaked()` simply reads `IERC20(stakingToken).balanceOf(operator)` at call time [2](#0-1) , i.e. it is a snapshot, not a time-weighted supply.

Staking into the pool is reachable by any unprivileged EOA through `MasterMagpie.deposit(_stakingToken, _amount)` [3](#0-2) , which calls `_deposit` with no minimum amount enforced [4](#0-3) .

Exploit flow:
1. Attacker observes a pending `queueNewRewards(_amountReward, _rewardToken)` transaction from a `manager` in the mempool while `totalStaked() == 0` (or very low).
2. Attacker front-runs with `MasterMagpie.deposit(stakingToken, 1)`, making `totalStaked() == 1`.
3. Manager's `queueNewRewards` executes `_provisionReward`, computing `rewardPerTokenStored += _amountReward * 10**decimals / 1`, an enormous per-token value.
4. `earned(account, token) = balanceOf(account) * (rewardPerTokenStored - paid) / 10**decimals` [5](#0-4) . With `balanceOf(attacker) == 1`, `earned(attacker) ≈ _amountReward`, i.e. essentially the whole reward.
5. Attacker calls `MasterMagpie.multiclaim` → `_claimBaseRewarder` → `rewarder.getReward(attacker, attacker)` [6](#0-5) , which is permitted because the call originates from `MasterMagpie` itself, satisfying `onlyMasterMagpie` on `getReward` [7](#0-6) .
6. Any later, legitimate stakers only start accruing from the now-inflated `rewardPerTokenStored` baseline (their `userRewardPerTokenPaid` is set at first interaction via `_updateFor`), so they receive nothing from the reward event the attacker just drained.

No modifier, `nonReentrant`, or `whenNotPaused` guard mitigates this — those protect against reentrancy/pausing, not against spot-balance reward-index inflation. There is no minimum-stake, virtual-shares, or time-weighting mechanism in `_provisionReward` to prevent a dust depositor from capturing a full reward tranche.

### Impact Explanation
This is a direct theft of unclaimed yield: reward tokens intended to be split across all future/legitimate stakers of a pool are instead almost entirely captured by an attacker who deposits a de-minimis amount immediately before a reward is queued. This matches the "theft of unclaimed yield" impact class. The magnitude of loss scales with the size of `_amountReward` queued by the manager each time `totalStaked()` is low (e.g., right after a fresh pool creation, or after a mass withdrawal event brings the pool down to near-zero stake).

### Likelihood Explanation
- Requires only that the attacker can see the manager's `queueNewRewards` transaction in the mempool and front-run it — standard MEV/front-running, no special privileges.
- Requires the pool's `totalStaked()` to be zero or very small at the time (most likely right after pool creation or after a large withdrawal), which is a realistic and even routine operational scenario (e.g., initial reward seeding for a new pool).
- Capital required is trivial (1 wei of `stakingToken`, plus gas).
- Repeatable every time a manager queues rewards while stake is low, making it a systemic risk during pool bootstrapping.

### Recommendation
Do not use the instantaneous `totalStaked()` spot balance to compute `rewardPerTokenStored` increments. Options:
- Require a minimum non-trivial `totalStaked()` (or lock a permanent minimal stake, e.g., burn/dead-address shares) before `_provisionReward` can distribute rewards, reverting or deferring to `queuedRewards` if supply is below a safety threshold.
- Track a time-weighted / checkpointed total supply for reward accrual instead of a spot balance, so a reward can't be attributed to a supply level that existed only for one block.
- Alternatively, restrict `queueNewRewards` to be time-locked with a public delay so all interested depositors can join before the reward event finalizes, or split the reward disbursement over a duration (streaming) rather than crediting fully at `queueNewRewards` time.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (via `createRewarder`), a mock `stakingToken`, and a mock `rewardToken`; register the pool via `add`.
2. Ensure `totalStaked() == 0` (fresh pool, no deposits).
3. As `attacker`, call `MasterMagpie.deposit(stakingToken, 1)`.
4. As `manager`, call `rewarder.queueNewRewards(_amountReward, rewardToken)` with e.g. `_amountReward = 1000e18`.
5. As `secondStaker`, call `MasterMagpie.deposit(stakingToken, 1000e18)` (a normal-sized deposit) to simulate the "future staker" whose yield is diluted.
6. Assert `IBaseRewardPool(rewarder).earned(attacker, rewardToken) ≈ 1000e18` (i.e., attacker's dust stake captured ~100% of the queued reward), while `earned(secondStaker, rewardToken) == 0` for this reward event.
7. Have attacker call `MasterMagpie.multiclaim([stakingToken])` and assert `rewardToken.balanceOf(attacker) ≈ 1000e18`, confirming actual token drain, disproportionate to attacker's 1-wei principal versus `secondStaker`'s 1000e18 principal — violating conservation/pro-rata distribution invariant.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
