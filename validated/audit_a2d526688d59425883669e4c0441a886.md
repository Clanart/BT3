### Title
Denial of Service via superlinear coin/announcement dependency resolution in `Offer.get_cancellation_coins()` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` in [1](#0-0)  resolves which coins in an offer's `SpendBundle` must be cancelled to invalidate the whole offer, by building `dependencies`/`announcements` maps from every coin's `ASSERT_COINANNOUNCEMENT`/`CREATE_COINANNOUNCEMENT` conditions and then repeatedly calling `detect_dependent_coin()` in an outer `while True` loop, itself with an inner `while True` cleanup loop, until no dependent coin remains.

### Finding Description
`detect_dependent_coin()` [2](#0-1)  iterates over every remaining coin name, every dependency of that coin, and every (coin, announcements) pair in the announcement dictionary — an O(n²·d) scan per call. This function is invoked repeatedly inside the outer `while True` loop of `get_cancellation_coins()` [3](#0-2) , which itself performs an O(n) inner cleanup scan over `dependencies.items()` per iteration and only guarantees termination by removing at least one coin per outer iteration. An attacker who crafts an offer file with many coin spends, each asserting a coin announcement created by a chain of other coins in the same bundle (all reachable via the `ASSERT_COINANNOUNCEMENT`/`CREATE_COINANNOUNCEMENT` opcodes, which any spend puzzle can emit), can drive this algorithm toward its worst-case quartic-ish behavior in the number of coin spends `n`. Unlike CLVM execution itself — which is metered and capped by `max_tx_clvm_cost`/`MAX_BLOCK_COST_CLVM` as enforced elsewhere in `Offer.__post_init__` via `compute_spend_hints_and_additions` [4](#0-3)  — this post-processing loop over parsed conditions has no such cost accounting or hard cap on `n` or on total loop iterations, so it can run for a duration disproportionate to the CLVM cost actually charged.

This mirrors the Quivr bug class: a value derived from attacker-controlled input size (here, chained coin/announcement dependencies) drives a processing loop whose cost is not properly bounded relative to the resource actually consumed/paid for, allowing the client processing the input to be tied up.

### Impact Explanation
`get_cancellation_coins()` is invoked from `chia/wallet/trade_manager.py` when a wallet user's client processes (e.g., inspects/cancels) an untrusted offer received from an offer counterparty. A malicious offer file, once loaded, can cause the wallet process handling it to spend disproportionate CPU/time in this loop, potentially stalling that wallet's ability to process other requests (localized single-request DoS), impacting a wallet user or offer counterparty flow. Note: I was not able to fully verify the exact call path/trigger conditions inside `trade_manager.py` (only confirmed the one call-site match) before running out of investigation budget, so the precise reachability trigger (whether automatic on offer receipt vs. requiring explicit user action) is unconfirmed.

### Likelihood Explanation
Constructing an offer with a chain of coin-announcement dependencies is straightforward CLVM puzzle authoring and does not require any signature validation to be satisfied (the loop runs over parsed conditions from `run_with_cost`, independent of whether the spend bundle would actually be valid/signable). This makes the input easy to craft; the barrier is only that the victim must load/process the malicious offer.

### Recommendation
Add an explicit bound on the number of coin spends / dependency depth processed by `get_cancellation_coins()`, or replace the O(n²) `detect_dependent_coin()` scan with an O(n) graph/topological approach (e.g., precompute an announcement→coin index instead of scanning `announcement_dict.items()` per dependency), and cap total loop iterations relative to `len(coin_names)`.

### Proof of Concept
Not independently constructed/validated — this is a structural complexity finding based on code inspection of `detect_dependent_coin()` and `get_cancellation_coins()`; a concrete high-n offer (many coins, each asserting an announcement created by a distinct other coin in a chain) would need to be built and timed to confirm the superlinear blowup in practice.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

```python
    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```
