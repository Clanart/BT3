### Title
Cached FROST preprocess seed is never reset after use, allowing deterministic nonce reuse across `share`/`complete` re-executions - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The analog to "device not reset on shutdown keeps operating with stale state" is `SigningProtocol::preprocess_internal`: the 32-byte preprocess seed is persisted in `CachedPreprocesses` keyed only by `context` (e.g. `(b"DkgConfirmer", attempt)`), is never deleted after the signing session completes, and is deterministically re-expanded via `ChaCha20Rng` into the same FROST nonces every time `share_internal` or `complete` runs. [1](#0-0) 

### Finding Description
`preprocess_internal` stores the `machine.cache()` seed in the DB the first time a context is seen, and every subsequent call rebuilds `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` with the identical seed (`coordinator/src/tributary/signing_protocol.rs:137-145`). `seeded_preprocess` expands that seed with `ChaCha20Rng::from_seed(*seed.0)` into `Commitments::new`, so the nonces `(d, e)` are byte-for-byte identical across calls (`crypto/frost/src/sign.rs:121-144`).

Both `share_internal` (line 156) and `DkgConfirmer::complete` (lines 321-323) invoke this path, and `DkgConfirmer::share` + `complete` are each called with caller-supplied `preprocesses`/`key_pair` maps (lines 288-327). If `sign` is reached twice under the same `(b"DkgConfirmer", attempt)` context with **different** inputs — a different subset of participant preprocesses, or a different `key_pair` in `set_keys_message` — the same nonces sign a different binding-factor set / challenge, which is precisely the classical FROST nonce-reuse precondition. The code comment itself acknowledges this is "explicitly unsafe" and derives safety solely from BFT input-finality, with a TODO noting the "on-chain-preprocess-matches-presumed-preprocess check" is unimplemented (`coordinator/src/tributary/signing_protocol.rs:25-54`). The seed row is never `del`'d after `complete`, so a re-execution or any logic flaw that feeds divergent preprocess sets into `share_internal` produces two signature shares `s_i = d + e·ρ_i + λ_i·x·c_i` over the same `(d, e)` — a ROS-style equation system that recovers the secret share `x`, exactly what `CachedPreprocess`'s own doc warns against (`crypto/frost/src/sign.rs:85-92, 216-219`).

### Impact Explanation
Recovery of a validator's MuSig secret share under Ristretto compromises the validator's root-of-trust key used for DKG confirmation signatures; combined with threshold-many other compromised or colluding shares it yields the aggregate key. Even absent full key recovery, a forged share lets an attacker complete confirmations or blame an honest validator. This meets the "key share recovery" acceptance bar.

### Likelihood Explanation
Requires two `share`-producing executions under the same context with divergent inputs — e.g., a `share` call followed by `complete` where the preprocess map differs (the map is re-supplied per call, not verified against what was used earlier), or a reboot/re-execution path where finalized inputs differ. The code explicitly leaves this unverified (the TODO at lines 50-54). Likelihood is bounded by BFT input consistency, but the cryptographic layer performs no self-protection (seed never cleared, no commitment-vs-published check), so any input divergence is fatal rather than detectable.

### Recommendation
- Delete the `CachedPreprocesses` row in `complete_internal`/after `share` succeeds, so post-completion re-execution cannot rebuild the same nonces.
- Implement the noted TODO: before publishing a share, verify the locally derived commitments match the preprocess already published on-chain for this context, aborting on mismatch.
- Include the full preprocess set digest (not just `context`) in the cache key so a divergent signing set deterministically yields a different seed.

### Proof of Concept
1. Validator participates in DKG confirmation attempt `a`; `preprocess_internal` stores seed `S` under `(b"DkgConfirmer", a)` and publishes commitments `C`.
2. `DkgConfirmer::share(preprocesses_A, key_pair)` runs `share_internal`: machine rebuilt from `S`, `sign(preprocesses_A, msg)` produces `s_1 = d + e·ρ_A + λ·x·c_A`.
3. `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` is invoked with `preprocesses_B ≠ preprocesses_A` (e.g., a different participant subset). `share_internal` rebuilds from the **same** `S` (line 137: cache still present, never cleared), producing `s_2 = d + e·ρ_B + λ'·x·c_B` with identical `(d, e)`.
4. An observer with both shares and the known ρ values solves the linear system for `d`, `e`, and the secret share `x` — the standard FROST nonce-reuse key-recovery attack the `CachedPreprocess` documentation warns about.

Unverified: whether `handle.rs` can actually feed a divergent `preprocesses`/`key_pair` into `complete` vs `share` for the same attempt under honest-BFT operation — I could not inspect the call sites in this session. The vulnerability is that the crypto layer itself provides zero defense (persistent, never-invalidated deterministic seed), so any such divergence is silently exploitable.
