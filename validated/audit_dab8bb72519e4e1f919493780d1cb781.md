### Title
Aggregate Schnorr signature verification does not bind nonces or public keys, enabling universal forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives each aggregation weight only from the caller-supplied challenges, while omitting the corresponding nonce commitments `Rs` and public keys from the weight transcript. An attacker can therefore choose each `R_i` after seeing the key/challenge pair so every weighted verification statement cancels independently.

### Finding Description
`SchnorrAggregate::read` accepts an attacker-controlled vector of group elements `Rs` and scalar `s`. During verification, the transcript is initialized and only each challenge is appended. The nonce `Rs[i]` and public key are then used directly in the multiexponentiation without being hashed into the aggregation-weight transcript.

Specifically, verification computes:

```rust
pairs.push((z, self.Rs[i]));
pairs.push((z * challenge, *key));
pairs.push((-self.s, C::generator()));
```

For any key `A_i` and challenge `c_i`, an attacker can set:

```text
R_i = -c_i * A_i
s = 0
```

Each pair then evaluates to:

```text
z_i * R_i + z_i * c_i * A_i
= z_i * (-c_i * A_i) + z_i * c_i * A_i
= 0
```

Because `s = 0`, the final generator term is also zero. The aggregate therefore verifies for arbitrary public keys and challenges without knowledge of any private key.

This is not prevented by the documented requirement that `challenge` binds the key, nonce, and message: even if `c_i` is honestly derived as `H(R_i, A_i, m_i)`, the attacker can choose an arbitrary signing nonce scalar `r_i`, set `R_i = r_iG`, compute the resulting `c_i`, and then set `s_i = r_i`; alternatively, the simpler `R_i = -c_iA_i, s_i=0` construction works whenever the externally supplied challenge is already fixed. Since the aggregation weight is independent of `R_i`, the same weight cancels the forged relation.

### Impact Explanation
Any caller using `SchnorrAggregate::verify` as authentication can accept a forged aggregate signature for arbitrary public keys and messages. This constitutes a direct signature forgery reachable entirely through attacker-controlled serialized bytes passed to `SchnorrAggregate::read`, followed by verification.

### Likelihood Explanation
The attack is deterministic and requires no secret key material, malicious validator, broken consensus assumption, or unusual curve input. An attacker only needs a public key/challenge pair accepted by the verifier and the ability to submit the aggregate signature bytes.

### Recommendation
Bind every component of each signature statement into the aggregation-weight transcript before deriving `z_i`, including at least:

- the signature index,
- `Rs[i]`,
- the public key,
- the challenge.

Both `SchnorrAggregator::aggregate` and `SchnorrAggregate::verify` must be updated to use the same complete transcript. A regression test should assert that replacing any `R_i` after challenge derivation causes verification to fail.

### Proof of Concept
The following construction demonstrates the forgery for a single aggregate entry:

```rust
// Given:
// - A: attacker-selected or victim public key
// - c: challenge accepted by the verifier for that key/message

let forged = SchnorrAggregate::<C> {
    Rs: vec![-(c * A)],
    s: C::F::ZERO,
};

assert!(forged.verify(dst, &[(A, c)]));
```

`verify` derives nonzero `z` from the challenge transcript and checks:

```text
z * (-cA) + (z * c) * A + (-0) * G = 0
```

so the forged aggregate is accepted. The same construction extends to any number of entries by setting every `R_i = -c_iA_i` and `s = 0`.
