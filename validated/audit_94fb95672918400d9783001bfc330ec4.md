### Title
Sequential same-epoch KIP-71 bound votes can ratify an inverted `LowerBoundBaseFee > UpperBoundBaseFee`, corrupting base-fee computation - (File: kaiax/gov/headergov/impl/header.go)

### Summary
`checkConsistency` in `kaiax/gov/headergov/impl/header.go` validates a `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` vote only against the *currently ratified* `ParamSet` (via `h.GetParamSet(blockNum)`), not against other votes cast earlier in the same, still-unratified epoch. This mirrors the audited `RioLRTAssetRegistry::_addAsset` bug class: a boundary/consistency check that validates against a stale/incomplete reference instead of the actual final state, allowing an invalid combined value to be accepted.

### Finding Description
`checkConsistency` handles the two KIP-71 bound votes as: [1](#0-0) 

Both branches compare the new vote value against `h.GetParamSet(blockNum)`, which is computed from `PrevEpochStart(blockNum, ...)`: [2](#0-1) [3](#0-2) 

Because `PrevEpochStart` returns a value strictly before the current epoch, `GetParamSet` always reflects the ratified state from the *previous* epoch, never the value of a vote cast earlier in the *same* epoch that has not yet been ratified. Votes accumulated during an epoch are only ratified together at the epoch boundary via `getExpectedGovernance`, which simply takes the last vote per parameter name without any cross-parameter consistency check: [4](#0-3) 

Consequently, the governing node (the sole authorized voter in `single` governance mode, enforced in `VerifyVote`) can:
1. Cast a vote to raise `Kip71LowerBoundBaseFee` to a high value `X` early in the epoch — validated against the old (still low) `UpperBoundBaseFee`, so it passes.
2. Later in the same epoch, cast a vote to lower `Kip71UpperBoundBaseFee` to a value `Y < X` — validated against the old (still low) `LowerBoundBaseFee`, so it also passes.

At the next epoch boundary, both votes are ratified into `header.Governance`, producing an inverted parameter set with `LowerBoundBaseFee (X) > UpperBoundBaseFee (Y)`. All nodes independently but deterministically apply this same corrupted `ParamSet` in `KIP71Config.NextMagmaBlockBaseFee`: [5](#0-4) 

With `lowerBoundBaseFee > upperBoundBaseFee`, the parent-baseFee clamping logic collapses inconsistently (the `>= upperBoundBaseFee` branch fires for most values since the "upper" bound is now smaller than "lower"), producing a base fee that no longer reflects the governance-intended floor/ceiling and can be driven to an unintended low value that persists.

### Impact Explanation
The computed base fee (`baseFeePerGas`) determines the minimum fee every transaction on the network must pay; corrupting the lower/upper bound relationship can push and stick the effective base fee to a degenerate value outside the intended governance-approved range, effectively bypassing the minimum-fee protection meant to be enforced by `LowerBoundBaseFee`, or improperly capping fees below where the network's fee market intends. Since base fee affects fee accounting for every transaction sender network-wide, this is a fee-mechanism integrity issue that persists until governance corrects it (requiring another epoch-length delay), impacting all transaction senders and any KIP-71-dependent fee logic (e.g., cross-chain bridge base-fee syncing seen in `node/sc/sub_bridge_handler.go`).

### Likelihood Explanation
Requires a single vote-casting entity (the governing node in `single` mode, or any council member in `none` mode) to cast two votes with conflicting values within one epoch — an operation directly supported by the `governance_vote` API. No collusion with other validators or off-chain access is needed. This is more likely to occur as an operational mistake than a targeted attack, but the protocol accepts and ratifies it without any safety net, unlike the single-vote checks that exist for the immediate-value case.

### Recommendation
When validating a `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` vote in `checkConsistency`, also account for any pending (not-yet-ratified) vote on the counterpart parameter within the current epoch — e.g., by checking against `max`/`min` of the ratified value and any pending same-epoch vote for the paired parameter — or add a final consistency check in `getExpectedGovernance`/`VerifyGov` that rejects (or normalizes) a ratified governance set where `LowerBoundBaseFee > UpperBoundBaseFee`.

### Proof of Concept
1. At epoch start, `ParamSet.LowerBoundBaseFee = 25e9`, `UpperBoundBaseFee = 750e9`.
2. Governing node casts vote `Kip71LowerBoundBaseFee = 700e9` at block `k*epoch+10`. `checkConsistency` compares `700e9 > params.UpperBoundBaseFee(750e9)`? No → vote accepted.
3. Governing node casts vote `Kip71UpperBoundBaseFee = 50e9` at block `k*epoch+20`. `checkConsistency` compares `50e9 < params.LowerBoundBaseFee(25e9)`? No → vote accepted.
4. At the next epoch boundary, `getExpectedGovernance` ratifies both: `LowerBoundBaseFee = 700e9`, `UpperBoundBaseFee = 50e9` — an inverted, invalid pair — with no rejection anywhere in `VerifyGov`.
5. From `(k+1)*epoch` onward, every node computes `NextMagmaBlockBaseFee` using this inverted config, producing a corrupted, network-wide base fee.
