### Title
Line-index-based partial-commit patch generation lets stale/attacker-modified working-tree content be silently committed under a different selection - ([File: app/src/lib/git/apply.ts])

### Summary
The Sui report's broken invariant is: an operation (`join`) is allowed to mutate the underlying object mid-snapshot, so a value captured before the mutation (`total_supply`) no longer matches the value derived after it (`unlocked_sum + locked_sum`), and nothing locks the object to prevent this. The GitHub Desktop analog is the partial-commit ("stage some lines") pipeline: the user's line selection (`DiffSelection`) is captured against a diff rendered at time T0, but the patch that is actually applied to the index is generated from a diff re-read from disk at time T1 (commit time), using the *same absolute line indices*. Nothing locks or re-validates the working-tree file between T0 and T1, so if the file's content changes in that window, the line-index selection is silently reinterpreted against different content.

### Finding Description
When the user does a partial (line/hunk-level) stage, `WorkingDirectoryFileChange.selection` records a `DiffSelectionType.Partial` selection as a set of **absolute line indices** into the diff that was rendered in the Changes view. This selection object is stored in `IChangesState.workingDirectory.files` in `repositoryStateCache` [1](#0-0) .

When the user clicks "Commit", `_commitIncludedChanges` reads the **currently cached** `selectedFiles` (including their `selection`) out of `repositoryStateCache` and hands them to `createCommit`: [2](#0-1) 

`createCommit` first wipes the index (`unstageAll`) and then calls `stageFiles(repository, files)` [3](#0-2) .

For any file with a `Partial` selection, `stageFiles` calls `applyPatchToIndex`, which **re-reads the diff from disk at this later point in time** via `getWorkingDirectoryDiff(repository, file)` and then builds the patch to apply to the index from that fresh diff plus the *stale* `file.selection`: [4](#0-3) [5](#0-4) 

`formatPatch` then walks the **freshly fetched** diff's hunks and, for each non-context line, decides whether to include it purely by `file.selection.isSelected(absoluteIndex)` - an index-based lookup with no comparison of the line's actual content against what the user saw when they made the selection: [6](#0-5) 

Nothing in this pipeline locks the working tree, hashes the diff to detect drift, or invalidates/re-derives the selection if the on-disk content changed between the moment the diff was rendered (and the user selected lines) and the moment `applyPatchToIndex` regenerates the diff for staging. `withIsCommitting` only guards against **re-entrant commits from the UI** (double-click protection), not against the working tree changing underneath the commit: [7](#0-6) . Likewise `_loadStatus`/`refreshChangesSection` continue to run status refreshes (e.g. background refresh, focus events, file watcher-triggered) concurrently with this window, and `updateChangedFiles` explicitly *preserves* the old `Partial` selection across a status refresh rather than invalidating it: [8](#0-7) 

This is structurally identical to the Sui bug: the value used to validate/build the final result (`selection` indices) is captured against one snapshot of state (T0 diff), while the mutating/consuming operation (`applyPatchToIndex`/`formatPatch`) operates against a second, independently-fetched snapshot (T1 diff), with no lock preventing the object from changing between the two reads.

### Impact Explanation
If the tracked file's on-disk content changes between the time the user reviews a diff and selects specific lines and the time the commit patch is generated (e.g. because a build tool, editor autosave, git smudge/clean filter, checked-in pre-commit tooling, or another concurrent process the attacker influences writes to the file in that window), the resulting commit will silently include or exclude different content than what the user selected and visually confirmed. This is exactly the "silent corruption of what the user commits" impact category: the user believes they are committing lines A-C of the diff they reviewed, but the actual committed patch is derived from a different file state at the same line indices, potentially including attacker-planted content or omitting a security-relevant hunk the user thought they excluded. Because the patch is generated purely from index positions with no content verification, there is no error, warning, or diff-mismatch surfaced to the user - the corruption is silent.

### Likelihood Explanation
The window between diff rendering and `applyPatchToIndex`'s re-fetch is not attacker-triggerable on demand purely from a malicious repository payload without some additional local process racing the write (e.g., an editor, linter/formatter-on-save, or a filter/hook triggered by other legitimate tooling operating on the same working tree), so exploitation likelihood is lower than a pure network/remote-triggered bug and requires a plausible but non-trivial timing condition. This weakens confidence that it maps cleanly onto the "unprivileged, attacker fully controls the trigger" bar requested, since it depends on some other file-mutating actor operating on the working copy concurrently with the review-to-commit window rather than the malicious repository content alone directly forcing the race.

### Recommendation
Introduce a integrity check equivalent to the "locking mechanism" prescribed in the original report: before generating and applying the partial patch, re-fetch (or hash) the diff at staging time and compare it against the diff the selection was made against; if it has changed, abort the partial-commit and force the user to re-review/re-select rather than silently reapplying stale line indices to new content. Alternatively, make `applyPatchToIndex`/`formatPatch` content-aware (e.g., validate hunk headers/line content match what was selected) instead of purely index-based, and surface a hard error to the UI if a mismatch is detected instead of proceeding.

### Proof of Concept
Conceptual sequence (not independently verified end-to-end in a live Desktop instance, since I only have static code access):
1. User modifies `file.txt`, opens the Changes view; Desktop renders a diff (T0) and the user selects only lines 10-12 for partial staging (`DiffSelectionType.Partial`), captured in `repositoryStateCache`.
2. Before the user clicks Commit, an external process (e.g. an editor autosave, a build step, or a git smudge/clean filter defined by a malicious `.gitattributes` in the cloned repo) rewrites `file.txt`, shifting or altering content at the same line offsets without the UI re-rendering the diff (e.g., because a debounced/quiescent refresh hasn't fired yet).
3. User clicks Commit. `_commitIncludedChanges` reads the cached `selection` (indices 10-12) and calls `createCommit` → `stageFiles` → `applyPatchToIndex`, which calls `getWorkingDirectoryDiff` again, obtaining a **new** diff (T1) reflecting the external rewrite [9](#0-8) .
4. `formatPatch` builds the patch using `file.selection.isSelected(absoluteIndex)` against the **T1** hunks/lines, not the T0 ones the user actually reviewed [6](#0-5) .
5. The resulting commit silently contains whatever content occupied lines 10-12 at T1, which may differ from what the user selected and approved at T0 - with no warning shown. [7](#0-6)

    const state = this.repositoryStateCache.get(repository)
    // ensure the user doesn't try and commit again
    if (state.isCommitting) {

    }

      hookProgress: null,
