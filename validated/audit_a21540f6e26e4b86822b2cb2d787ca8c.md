## Analysis

The external report's core broken invariant: a bookkeeping/reward function accepts the zero address as a valid beneficiary/participant without any sanity check, causing funds to accrue to an address nobody can control — resulting in silently locked/misattributed rewards.

Hyperbridge has this exact same code pattern duplicated across two closely related reward paths in `pallet-relayer`, and only one of the two copies has the zero-address guard.

`modules/pallets/relayer/src/outbound_consensus.rs` decodes an EVM `EvmHost._epochs[set_id]` slot via `decode_epochs_slot_address`, which explicitly guards against a decoded zero address: [1](#0-0) 

That guard exists precisely because the pallet's own test suite documents the threat model: "a malicious actor can't claim a reward by writing zeros… the contract on chain could be compromised": [2](#0-1) 

However, the sibling decoder `decode_receipt_relayer` in `modules/pallets/relayer/src/accumulate.rs` — shared by both `accumulate_fees` (relayer fee accounting) and `claim_outbound_request_delivery_reward` (`outbound_request.rs`) — performs **no equivalent zero/degenerate-address check** for either the EVM or Pharos branches: [3](#0-2) 

This value flows directly into `Fees::<T>::try_mutate(state_machine, address, ...)` in `accumulate()`: [4](#0-3) [5](#0-4) 

and into the signer-matching/payout check in `process_outbound_request_delivery_claim`: [6](#0-5) 

### Title
Missing zero-address guard in `decode_receipt_relayer` allows relayer fees/rewards to be attributed to an unclaimable address - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`decode_receipt_relayer`, used by both the `accumulate_fees` fee-accounting path and the `claim_outbound_request_delivery_reward` payout path, decodes a state-proof-verified `RequestReceipts[commitment]` value into a relayer address/bytes with no validation that the result is non-zero/non-degenerate. Its sibling function `decode_epochs_slot_address` (same file family, `outbound_consensus.rs`) treats a decoded zero address as "not proven" and rejects it, explicitly because the codebase's own threat model considers a compromised or malformed destination-host storage slot writing an all-zero value a real risk. `decode_receipt_relayer` has no such check.

### Finding Description
`accumulate()` derives `delivery_address` (or, without a beneficiary redirect, credits `delivery_address` directly) from `decode_receipt_relayer`, then does `Fees::<T>::try_mutate(state_machine, delivery_address, |inner| *inner += total_fee)`. The same decoder feeds `delivered_by` in `process_outbound_request_delivery_claim`, which is matched against `signature.verify(...)` before a treasury-funded reward transfer executes. Neither call site nor the decoder itself rejects an address that decodes to all-zero bytes (EVM 20-byte zero address, or an all-zero/empty substrate byte string), even though `decode_epochs_slot_address` demonstrates the codebase is aware this exact byte pattern can appear from a non-canonical RLP encoding or a compromised/misbehaving destination host contract and defends against it there.

### Impact Explanation
If `RequestReceipts[commitment]` on the destination ever resolves (via state proof) to the zero address/empty bytes, `accumulate_fees` silently credits the corresponding fee into `Fees[state_machine][zero_address]`. Because `withdraw_fees` requires a valid `Signature` that recovers to the exact stored address key, no signature can ever recover to the zero address, so that portion of relayer fees becomes permanently locked and unclaimable — funds move to a beneficiary that structurally can never withdraw them, matching the reward-loss impact category in scope. In the `outbound_request_delivery` path, if `delivered_by` resolves to zero bytes, the treasury payout still requires a signature match, so it is unlikely to reach transfer, but the accounting-side effect on `accumulate_fees` is directly exploitable purely through proof/decoding logic with no privileged actor required at the pallet layer.

### Likelihood Explanation
Likelihood is constrained by how the zero-value bytes get into the destination trie in the first place — normal EVM/relayer behavior can never write a literal zero address into a receipt slot. However, the codebase's own test comment on `decode_epochs_slot_address` acknowledges this exact edge case ("the EVM would never emit this — leading zeros are stripped — but the contract on chain could be compromised") as a real defense-in-depth concern worth coding against, and only implemented it in one of two structurally identical decoders. The asymmetry itself is the bug: any future or already-possible RLP/ABI edge case that produces this byte pattern is unguarded in the fee-accumulation and outbound-request-claim paths.

### Recommendation
Apply the same zero-address rejection used in `decode_epochs_slot_address` to `decode_receipt_relayer` for both the EVM and Pharos branches (and reject empty/all-zero byte strings for the substrate branch), surfacing it as the existing `OutboundDeliveryNotProven` / `ProofValidationError` semantics so a degenerate receipt slot is treated as "not proven" rather than being silently credited.

### Proof of Concept
Not independently reproducible as a live attack without a compromised/misbehaving destination host contract; the finding is a static code-symmetry gap: `decode_epochs_slot_address` (`modules/pallets/relayer/src/outbound_consensus.rs:203-216`) rejects `Address::ZERO`, while `decode_receipt_relayer` (`modules/pallets/relayer/src/accumulate.rs:322-351`), consumed by `accumulate()` and `process_outbound_request_delivery_claim`, performs no such check on the same class of decoded value.

	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
