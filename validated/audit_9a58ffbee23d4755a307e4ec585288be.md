### Title
Unprivileged callers can force `WombatStaking.convertWOM` to permanently lock any WOM balance in the contract into veWOM, freezing unclaimed yield - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.convertWOM(uint256 _amount)` is `external whenNotPaused` with no caller restriction, and it operates on whatever WOM balance happens to sit in the contract, immediately approving and locking it into veWOM for `lockDays` (1461 days) via `IVeWom(veWom).mint`. Because the function is unauthenticated, any address can trigger this lock on transient WOM balances before they are routed to their intended destination (fee recipients / `queueNewRewards`), causing the WOM to become inaccessible for years.

### Finding Description
`convertWOM` is defined as: [1](#0-0) 
It has only the `whenNotPaused` modifier - no `onlyOwner`, no restriction to `mWom`, and it takes an arbitrary `_amount` supplied by the caller rather than reading and consuming the contract's actual balance safely under access control. `convertAllWom()` at line 353-355 similarly has no restriction and simply forwards the entire WOM balance to `convertWOM`.

Normal harvest/deposit flows (`deposit`, `depositLP`, `harvest`, `withdraw`) route harvested WOM synchronously through `_toMasterWomAndSendReward` → `_sendRewards` within the same transaction: [2](#0-1) . That path is atomic per-transaction, so an external caller cannot interleave a call in the *middle* of a single harvest/deposit transaction. However, `mWOM.sol`'s `_lockWom` also calls `IWombatStaking(wombatStaking).convertWOM(_amount)` as a separate step, and fee flows configured with `isMWOM=true` (`addFee`/`setFee`, lines 571-619) route WOM fees to be converted later rather than atomically, meaning WOM belonging to fee recipients can sit in `WombatStaking`'s balance across transactions/blocks, awaiting a follow-up conversion. During that window, `convertWOM` is callable by any EOA with the exact residual amount.

Critically, when an outside, unprivileged address calls `convertWOM` directly, the `IVeWom(veWom).mint(_amount, lockDays)` call is made with `msg.sender == WombatStaking` (the contract calls it directly, not via delegatecall), so the resulting veWOM position is owned by `WombatStaking` itself, not by the calling attacker. This means the attacker does not personally receive locked veWOM value - the real impact is that WOM meant to flow to `mWom` recipients or `queueNewRewards` gets diverted into a 4-year veWOM lock held by the protocol contract, with no corresponding `mWOM` minted to the intended recipients and no reward credited via `queueNewRewards`.

### Impact Explanation
Any residual/dust WOM balance held transiently by `WombatStaking` (e.g., between a fee-flagged-`isMWOM` accrual and the eventual mWOM conversion call) can be force-locked into veWOM by an unprivileged caller. This is a permanent freezing of unclaimed yield: the WOM is irreversibly committed to a `lockDays` (1461-day) veWOM position controlled by the contract, and the intended fee recipients/reward pools never receive the corresponding mWOM/reward-pool credit. This matches the Immunefi "theft or permanent freezing of unclaimed yield" impact class, though as noted the veWOM accrues to `WombatStaking` rather than to the attacker, so it is more precisely a griefing/DoS on protocol fee distribution than a personal-profit theft.

### Likelihood Explanation
Exploitability requires zero capital and zero privileges - any EOA can call `convertWOM(_amount)` at any time the contract holds a nonzero, uncommitted WOM balance and is not paused. The main precondition is the existence of a real, exploitable window where WOM sits in the contract's balance without being atomically consumed in the same transaction (e.g., fee flows configured as `isMWOM=true` that are meant to be swept later, or any direct/accidental WOM transfer into the contract). I was not able to fully inspect `_sendRewards`'s complete body (the file was truncated before I could view lines beyond 720) to confirm exactly how `isMWOM` fees are routed and whether any WOM balance is left un-swept between transactions; this should be verified before treating the exploit window as fully general.

### Recommendation
Restrict `convertWOM`/`convertAllWom` to authorized callers only (e.g., `onlyOwner`, `only mWom`, or an explicit allow-listed caller such as a fee sweeper), and/or have the function operate on a tracked "pending-for-lock" accounting variable rather than an arbitrary caller-supplied `_amount` against the raw contract balance, so unrelated dust/fee balances cannot be swept into a long-term lock by unrelated parties.

### Proof of Concept
Foundry fork test outline:
1. Fork BSC, deploy/attach to `WombatStaking`, `mWOM`, and `veWom`.
2. Configure a fee entry with `isMWOM = true` via `addFee` (owner-only setup step, not part of the exploit) so that WOM fee flow is expected to be separately converted.
3. Have a normal user call `deposit`/`harvest` on a real pool so that WOM ends up sitting in `WombatStaking` (assert `IERC20(wom).balanceOf(wombatStaking) > 0` before any `convertWOM`/`mWOM.lockAllWom` call).
4. From an unrelated attacker EOA (no prior token holdings, no privileged role), call `WombatStaking.convertWOM(amount)` directly with `amount` equal to the observed balance.
5. Assert: `IERC20(veWom).balanceOf(address(wombatStaking))` increases by the minted veWOM amount; `IERC20(wom).balanceOf(wombatStaking)` decreases to (near) zero; and the intended reward pool's `queueNewRewards` balance / `mWOM.totalConverted` does NOT reflect this WOM (i.e., the fee recipients receive nothing for this amount).
6. Confirm the resulting veWOM lock is held by `wombatStaking` (not the attacker), and is not withdrawable for `lockDays` (1461 days), demonstrating permanent freezing of the fee-designated WOM.

    /// @notice convert WOM to mWOM
    /// @param _amount the number of WOM to convert
    /// @dev the WOM must already be in the contract
    function convertWOM(uint256 _amount) whenNotPaused external returns(uint256) {
        uint256 veWomMintedAmount = 0;
        if (_amount > 0) {
            IERC20(wom).safeApprove(veWom, _amount);
            veWomMintedAmount = IVeWom(veWom).mint(_amount, lockDays);
        }

        emit WomLocked(_amount, lockDays, veWomMintedAmount);

        return veWomMintedAmount;
    }
