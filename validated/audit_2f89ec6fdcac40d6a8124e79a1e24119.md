### Title
`ReceivedOutput::read` accepts an attacker-supplied key offset with no binding to `output.script_pubkey`, letting unspendable outputs be reported as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The LiFi bug class is "a security-critical target supplied as a caller-controlled parameter instead of an immutable/bound value" — any address can be passed as `_bridgeData.bridge`, so the contract will interact with whatever the caller chose. In Serai, the analogous shape is `ReceivedOutput::read`, which deserializes the spend-key `offset` and the Bitcoin `TxOut`/`OutPoint` as fully independent fields from untrusted bytes. The offset is the "address-equivalent" parameter: it selects which tweaked Taproot key (`key + offset*G`) must be able to sign for the output, yet nothing in the read path verifies that `output.script_pubkey` actually equals `p2tr(key + offset*G)`. The safe construction (`Scanner::scan_transaction`) derives the offset by lookup in `self.scripts`, but bytes fed to `ReceivedOutput::read` bypass that binding entirely.

### Finding Description
`ReceivedOutput` couples a scalar `offset` with a `TxOut`/`OutPoint` (`mod.rs:90-97`). The offset's purpose is stated in the comment: "The scalar offset to obtain the key usable to spend this output" (`mod.rs:91`). In `Scanner::scan_transaction`, this invariant is enforced by construction — an output is only emitted when `self.scripts.get(&output.script_pubkey)` yields the offset that was registered for exactly that script (`mod.rs:205-211`), and `register_offset` builds that map from `p2tr_script_buf(self.key + G*offset)` (`mod.rs:185-190`).

`ReceivedOutput::read`, however, decodes `offset` via `Secp256k1::read_F` and then independently consensus-decodes `output` and `outpoint` (`mod.rs:122-134`). There is no check that the script in `output` corresponds to `key + offset*G`, nor even that it is a P2TR output at all. Any consumer that ingests serialized `ReceivedOutput`s — which the threat model explicitly treats as untrusted input — therefore accepts a pair where the claimed spend key has no relationship to the actual on-chain output. Downstream, the signing path keys each input's FROST machine from the offset (the `TransactionSignMachine` signs each prevout with `Prevouts::All` over `self.tx.prevouts`, `send.rs:373-391`), so a mismatched offset yields a signature under the wrong tweaked key for that prevout.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ReceivedOutput::read` (or to whatever transports serialized `ReceivedOutput`s) can cause an output to be accepted as a spendable received output whose real spending key is unrelated to the supplied offset — e.g., pairing a legitimate-looking deposit `TxOut`/`OutPoint` with an offset whose tweaked key does not match the output's script. The result is funds reported as received that are not spendable: any spend transaction built over it produces a signature under `key + offset*G` that fails Taproot key-path verification for that prevout, burning time, fees, and potentially locking accounting state on phantom balance. This is a direct analog of the LiFi report — an attacker-supplied selector (offset ≈ bridge address) choosing which key/contract-like target is invoked, unchecked against the data it must bind to.

### Likelihood Explanation
Reachability requires a path where serialized `ReceivedOutput`s cross a trust boundary — e.g., outputs relayed between components, persisted and reloaded, or supplied by an external data source rather than produced locally by `Scanner::scan_*`. Wherever `scan_transaction`/`scan_block` is the sole producer, the invariant holds and the bug is unreachable. Because `ReceivedOutput::read` is a public deserialization API over `Read` with no documented "only consume Scanner-produced bytes" requirement at the type level, the mismatch is exploitable wherever consumers deserialize rather than rescan — a realistic pattern for indexers/relayers feeding the wallet.

### Recommendation
Either verify the binding at deserialization/spend time — recompute `p2tr_script_buf(key + G*offset)` and require it to equal `output.script_pubkey` — or make the unchecked state unrepresentable: keep `ReceivedOutput` construction private to `Scanner` and have `read` take the expected script set (or base key) so validation is mandatory, analogous to the report's recommendation of fixing the target at construction rather than accepting it as a free parameter. Document that `ReceivedOutput::read` must not be used on data that did not originate from the same `Scanner`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs — ReceivedOutput::read (lines 122-134)
// vs. the checked path in Scanner::scan_transaction (lines 199-214)

// Attacker crafts bytes: [attacker_chosen_offset][victim TxOut][victim OutPoint]
// where victim TxOut pays to p2tr(key + G*real_offset), real_offset != chosen.

let mut bytes = chosen_offset.to_bytes().to_vec();
bytes.extend(serialize(&victim_txout));   // script = p2tr(key + real_offset*G)
bytes.extend(serialize(&victim_outpoint));

let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// ro.offset() == chosen_offset, but ro.output().script_pubkey needs key + real_offset*G.
// Scanner::scan_transaction would never emit this pair (scripts map lookup would miss
// or return real_offset), so the read path accepts a pair the checked path rejects.
// Signing this input uses chosen_offset -> signature fails for the prevout ->
// output counted as received yet unspendable.
```

Uncertainty: I confirmed `ReceivedOutput::read` performs no offset/script binding and that `scan_transaction` does, and that the spend path derives per-input keys from offsets with `Prevouts::All` sighashes (`send.rs:373-391`). I could not fully enumerate every consumer of serialized `ReceivedOutput`s within the remaining budget, so the severity depends on whether deployed flows deserialize these bytes from a trust boundary rather than only from a local `Scanner`.
