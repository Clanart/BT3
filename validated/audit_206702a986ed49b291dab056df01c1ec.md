### Title
Instant reward-per-token crediting in `BaseRewardPoolV2`/`BaseRewardPool` lets an attacker deposit right before a permissionless `harvest()`/`vote()` call and steal freshly queued yield with zero holding time - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2._provisionReward` applies the entirety of any newly queued reward to `rewardPerTokenStored` in a single instant, proportional to whatever `totalStaked()` happens to be at that exact moment, with no streaming/vesting period. Because deposits into `MasterMagpie` immediately increase a user's `balanceOf()` in the reward pool, and because `WombatStaking.harvest()` (and vote-triggered harvesting via `WombatBribeManager.castVotes`) are callable by any unprivileged wallet, an attacker can deposit LP tokens immediately before triggering a harvest, capture a full pro-rata share of the newly queued reward with zero time-at-risk, and withdraw right after - diluting/stealing yield that should have accrued to genuine long-term stakers.

### Finding Description
`_provisionReward` in `BaseRewardPoolV2.sol` credits the entire incoming reward amount to `rewardPerTokenStored` based on the current `totalStaked()`: [1](#0-0) 

`totalStaked()` and `balanceOf()` read live balances from `MasterMagpie`, meaning a deposit made in the same block as (or immediately before) a `queueNewRewards` call is fully counted: [2](#0-1) 

`MasterMagpie.deposit`/`withdraw` have no cooldown, minimum holding period, or fee-on-instant-round-trip: [3](#0-2) 

Rewards are queued into the pool whenever `WombatStaking._toMasterWomAndSendReward` is invoked, which happens on `deposit`, `withdraw`, and the permissionless `harvest()` function - any wallet can call `harvest(_lpToken)` to force a reward push: [4](#0-3) [5](#0-4) 

Reward casting from bribes goes through the same `queueNewRewards` path and is also triggerable via `WombatBribeManager.castVotes`, which any address may call: [6](#0-5) [7](#0-6) 

Combining these: an attacker can (1) deposit a large LP/staking-token position into `MasterMagpie`, inflating `totalStaked()` for the target `BaseRewardPoolV2` immediately before a reward push, (2) call the permissionless `harvest()`/`castVotes` to force `queueNewRewards`, which instantly stamps `rewardPerTokenStored` using the attacker's inflated share, (3) immediately call `getReward`/claim, and (4) withdraw the principal - all with no meaningful holding period or risk, capturing yield that honest long-term stakers should have received.

### Impact Explanation
This permits theft of unclaimed yield from genuine stakers: every time new rewards are queued, a flash/sandwich depositor captures a share proportional to capital temporarily parked in the pool rather than capital genuinely staked over the accrual period, permanently diluting the rewards available to long-term stakers. This is a direct instance of "theft ... of unclaimed yield," matching the accepted impact criteria.

### Likelihood Explanation
The attack requires no privileged role and no special conditions: `deposit`, `withdraw`, `harvest`, and `castVotes` are all externally callable by ordinary wallets, and reward provisioning is always instantaneous with no delay/vesting to mitigate flash deposits. On networks with cheap gas, an attacker (or bot) can repeat this every time a reward/harvest event occurs, making exploitation straightforward and repeatable.

### Recommendation
Stream newly queued rewards over a fixed duration (e.g., Synthetix/Convex-style `rewardRate`/`periodFinish` accrual) instead of crediting `rewardPerTokenStored` instantly, and/or require a minimum staking duration before a deposit's balance counts toward reward-per-token accrual, so flash deposits immediately before a reward push cannot capture a disproportionate share of yield.

### Proof of Concept
1. Attacker monitors for an upcoming `harvest()`/`castVotes()` call (or plans to call it themselves) that will queue new rewards into a `BaseRewardPoolV2` instance for pool `P`.
2. Attacker calls `MasterMagpie.deposit(P.stakingToken, largeAmount)` right before triggering the harvest, becoming a large fraction of `totalStaked()`.
3. Attacker calls `WombatStaking.harvest(lpToken)` (or waits for `WombatBribeManager.castVotes`) which calls `_toMasterWomAndSendReward` → `IBaseRewardPool(rewarder).queueNewRewards(...)`.
4. `_provisionReward` immediately updates `rewardPerTokenStored` using the current (attacker-inflated) `totalStaked()`.
5. Attacker calls `getReward`/`multiclaimSpec` to claim their pro-rata share of the newly queued rewards, then immediately calls `MasterMagpie.withdraw(P.stakingToken, largeAmount)` to exit with no time-at-risk, having captured yield meant for long-term stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
