### Title
Permissionless `purchase()` lets any address grief and destroy a victim app's unexpired, already-paid bandwidth allowance via FIFO eviction - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s `Allowance` storage keys prepaid bandwidth subscriptions purely by `(app_chain, app)` from the purchase message body, not by any relationship to the caller. `BandwidthManager.sol::purchase()` on the EVM side is fully permissionless with respect to whose `app`/`chain` is credited — this is intentional "sponsorship" (anyone can top up anyone). But the FIFO subscription list per `(app_chain, app)` is capped at `MAX_SUBSCRIPTIONS = 1024`, and pushing past the cap silently evicts the *oldest* entry regardless of its remaining bytes or time-to-expiry [1](#0-0) . This is structurally the same primitive as the Water.sol bug: an unprivileged caller can invoke a "credit/deposit"-style function targeting a victim's account/state, and the resulting state mutation (queue push) destructively resets/evicts state the victim already legitimately paid for.

### Finding Description
`purchase()` on `BandwidthManager.sol` takes an arbitrary `app` and `chain` argument controlled entirely by the caller, with no check that the caller has any relationship to that app [2](#0-1) . When the purchase message is delivered, `pallet-bandwidth::on_accept` calls `push_subscription(&msg.chain, &key, ...)` which appends to `Allowance::<T>` keyed by `(app_chain, app)` taken straight from the message body [3](#0-2) .

`push_subscription` enforces the 1024-entry cap by evicting index 0 (the oldest entry) whenever the list is already full, with **no regard to whether that entry still has unconsumed `remaining_bytes` or a far-future `expires_at`** — eviction is purely FIFO position-based, not "least valuable" or "already expired":

```
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else { None };
    let _ = list.try_push(new_sub);
    evicted
});
``` [4](#0-3) 

Crucially, `push_subscription` does **not** sweep expired entries before checking the cap — sweeping only happens inside `try_consume` (the gate), which only runs when the victim app actually dispatches an ISMP message [5](#0-4) . So an idle or low-traffic app's list can accumulate a mix of expired and live entries that all still count toward the 1024 cap, making it cheaper for an attacker to force real evictions.

Since `purchase()` requires only that the caller pay the (attacker-chosen) tier price — the cheapest tier — an attacker can call `purchase(victim_app, TierOne, 1, victim_chain)` repeatedly. Each call appends one new subscription entry regardless of `months`/tier size. After enough calls to reach the 1024 cap, every subsequent purchase evicts whatever is currently at the front of the queue and emits `SubscriptionEvicted` — which can be a large, expensive, long-duration subscription the victim (or victim's sponsor) legitimately paid a treasury/dapp fee for [6](#0-5) .

No guard exists anywhere in the call path — `on_accept`, `push_subscription`, or `purchase()` — that restricts who may credit a given `(app_chain, app)` pair or that protects large/high-value/non-expired entries from FIFO eviction by trivial follow-on purchases.

### Impact Explanation
This is a direct, permissionless loss-of-funds / logic attack against the bandwidth market: an attacker who never controls the victim app, a relayer, prover, or governance key can force the destruction of the victim's already-paid, non-expired prepaid bandwidth allocation by making a sequence of cheap purchases against the same `(app_chain, app)` key. The victim's ISMP messages will then be gated/rejected (`GateError::NoAllowance` / `Insufficient`) despite having paid for capacity, and the paid value is unrecoverable (no refund path for evicted-but-unconsumed bytes — `force_credit` requires governance). This matches the "loss of funds" / "logic attacks" categories in the impact gate: real fee-token value paid by a legitimate buyer is destroyed by an unrelated unprivileged party.

### Likelihood Explanation
High for any victim app that is a live target (has a public/known address and receives regular sponsor top-ups) and has a list that is not already near-empty. The attack requires only capital to pay for the cheapest configured tier repeatedly (bounded by however many entries are already in the victim's list up to 1024, or fewer if expired entries have accumulated), and standard RPC/EOA access — no privileged role, relayer collusion, or proof forgery is needed. The cost asymmetry (attacker buys cheap `TierOne`/`months=1` purchases, victim's evicted entry may represent a much larger multi-month/higher-tier purchase) makes this an economically attractive griefing vector.

### Recommendation
- Bind `Allowance` credit rights so only the app itself (or an explicitly authorized sponsor list) can credit its own `(chain, app)` bucket, or separate "self-funded" vs "third-party sponsored" queues with independent caps.
- When evicting on cap overflow, sweep expired entries first (as the gate does) before evicting a live entry, and/or evict based on remaining value (smallest `remaining_bytes` / soonest `expires_at`) rather than strict insertion order.
- Consider a per-purchase minimum bytes/tier floor or a rate limit per `(source, app)` pair to make griefing economically prohibitive, and emit/alert loudly (already done via `SubscriptionEvicted`) with an on-chain governance recovery path (e.g., extend `force_credit` to also restore evicted subscriptions).

### Proof of Concept
1. Governance registers `BandwidthManager` for chain X and configures `TierOne` (cheap) and `TierFour` (expensive, long-duration).
2. Victim's sponsor legitimately buys `TierFour` for `victim_app` on `chain X`, expecting months of bandwidth: `manager.purchase(victim_app, TIER_FOUR, 12, "EVM-X")` → appended as the current queue entries for `(X, victim_app)`.
3. Attacker, an unrelated address, repeatedly calls `manager.purchase(victim_app, TIER_ONE, 1, "EVM-X")` — cheapest tier, `months = 1` — enough times to push the `(X, victim_app)` subscription list to `MAX_SUBSCRIPTIONS = 1024` and beyond.
4. Once the list is full, each additional attacker purchase triggers `push_subscription`'s eviction branch, popping index 0. If the victim's large `TierFour` subscription (or any other live, high-value entry) is at the front of the FIFO (because it hasn't been drained yet, e.g. victim app dispatches infrequently), it gets evicted and `SubscriptionEvicted { lost_bytes }` fires — the paid bytes are gone [7](#0-6) .
5. Victim's subsequent ISMP dispatch through `BandwidthGate::try_consume` now fails with `NoAllowance`/`Insufficient` despite having paid for months of bandwidth, and there is no path to reclaim the lost bytes without a governance `force_credit` bailout.

**Note on verification limits:** I confirmed the storage/eviction logic and the permissionless nature of `purchase()`'s `app`/`chain` parameters directly in `modules/pallets/bandwidth/src/lib.rs` and `evm/src/apps/BandwidthManager.sol`. I was not able to fully review `modules/pallets/testsuite/src/tests/pallet_bandwidth.rs` for whether this exact eviction-of-live-subscription scenario is already covered/mitigated by an off-chain policy or a runtime constant I didn't see (e.g., a much larger `MAX_SUBSCRIPTIONS` in a specific runtime, or a fee floor); if such a mitigation exists it would reduce but likely not eliminate the underlying design gap (FIFO eviction with no "protect live/high-value entries" rule and no per-`(chain,app)` credit authorization).

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );
