### Title
ReDoS in Tendermint RPC `tx_search`/`block_search` via unbounded `MATCHES` regex compiled from client-supplied query - (File: sei-tendermint/internal/state/indexer/tx/kv/kv.go, sei-tendermint/internal/state/indexer/block/kv/kv.go)

### Summary
The Tendermint `tx_search` and `block_search` public JSON-RPC endpoints accept a query string that can include a `MATCHES` condition. The condition's regex pattern is taken verbatim from the client-supplied query and passed straight into `regexp.MatchString` (which compiles the pattern and runs Go's `regexp` engine against attacker/queryable event values) for every indexed entry that shares the tag prefix, with no complexity or timeout guard on the compiled pattern itself.

### Finding Description
`TxSearch` parses the caller-supplied query string with `tmquery.New(req.Query)` and only enforces a maximum query *length*, not regex complexity, before invoking the KV indexer's `search`/`match` routine. [1](#0-0) 

Inside the KV indexer's `match` function, the `TMatches` branch iterates every entry under the tag's key prefix and calls `regexp.MatchString(c.Arg.Value(), eventValue)` on each entry's value, where `c.Arg.Value()` is the raw pattern taken directly from the client's query string: [2](#0-1) 

The same unbounded `regexp.MatchString` pattern exists in the transaction indexer. [3](#0-2) 

A `ScanBudget`/`ScanLease.Visit` mechanism bounds the *number of index entries visited* per query, and the loop checks `ctx.Done()`/`ctx.Err()` between iterations, but neither of these controls can interrupt a single call to `regexp.MatchString` that is already executing. Go's `regexp` package uses an RE2-derived engine that is generally resistant to catastrophic backtracking for most constructs, but pathological patterns combined with large indexed values (event attribute values can be arbitrarily long strings emitted by any contract/message during execution and are stored/indexed as tx/block events) can still produce a `regexp.Compile`/match call that runs for a long time on a single entry, during which neither the budget check nor the context cancellation check can preempt it — the check-points only fire *between* entries, not *inside* a match call.

This is analogous to the VIVO Vitro advisory's root cause: an externally reachable query endpoint accepts a raw, attacker-controlled regular expression that is executed directly against server-held data without bounding regex cost, enabling a denial-of-service via crafted `MATCHES`/`FILTER regex`-style input.

### Impact Explanation
`tx_search` and `block_search` are public, unauthenticated RPC methods reachable by any client. A crafted query with an expensive `MATCHES` pattern targeted at a widely-populated event tag (e.g., `wasm.action`, `message.sender`, or any indexed attribute with long/attacker-influenced values) can tie up the RPC-serving goroutine for an extended period per request. Repeated concurrent requests can exhaust node resources (CPU, goroutines) on any full/RPC node running with the KV event sink enabled (the default configuration for most Tendermint/CometBFT nodes serving RPC), degrading or denying RPC service. This does not directly cause consensus halt or fund loss, but it satisfies the "crash/DoS of default-configuration RPC nodes" impact category.

### Likelihood Explanation
Reaching this code path only requires sending a single `tx_search`/`block_search` RPC request with a `MATCHES` clause containing an adversarial regex — no special privileges, no transaction submission, and no on-chain state changes are needed. The main uncertainty is how effective a specific crafted pattern is against RE2-style regex; unlike backtracking engines (PCRE/Java's, as in the original VIVO CVE), Go's `regexp` is closer to RE2 and bounds worst-case time relative to input length, so the severity of the ReDoS is limited by input length rather than truly exponential blowup. Combined with the existing `ScanBudget` (which limits entries scanned) and `maxQueryLength` check, the practical impact is reduced compared to the original advisory, but the per-entry match cost is still unbounded relative to the value length and is not preemptible mid-call.

### Recommendation
- Impose an explicit maximum length/complexity bound on `MATCHES` regex patterns and/or on the indexed values being matched before invoking `regexp.MatchString`.
- Pre-compile the pattern once with `regexp.Compile` and reject overly complex patterns (e.g., excessive quantifiers/alternations) at query-parse time rather than per-entry.
- Consider running the match with a bounded input-size cap (truncate/skip abnormally long event values) and/or wrap the match call with a timeout that can be observed via `ctx`, since RE2's worst case still scales with input length.
- Rate-limit or cap `MATCHES` usage per RPC request server-side (e.g., disallow `MATCHES` entirely on public/non-authenticated RPC endpoints, matching Tendermint's later hardening for CVE-class ReDoS issues).

### Proof of Concept
1. Populate the chain with transactions that emit an indexed event attribute containing a long string (many chains have long values in memo/log/wasm event attributes).
2. Send a public RPC request: `GET /tx_search?query="wasm.some_attr MATCHES 'a{500}b'"` (or another regex pattern with high backtracking potential) against a node.
3. Observe that the KV indexer iterates all entries under the `wasm.some_attr` prefix, invoking `regexp.MatchString` on each long value; issuing many such concurrent requests against widely-populated tags will consume disproportionate CPU on the RPC-serving node, as the per-entry match cost scales with value length and pattern complexity while `ScanBudget`/context checks cannot interrupt an in-flight match call.
