## Title
Stale, index-based diff-selection reused against a freshly re-fetched diff at commit time causes silent corruption of partially-committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select a subset of lines within a file's diff (a "partial commit"). That selection is stored as an index-based `DiffSelection` (line offsets into a specific diff snapshot), not as content-addressed data. When the commit is actually staged, `applyPatchToIndex` re-fetches a brand-new diff from disk and blindly re-applies the old, index-based selection to it, with no re-validation that the line indices still correspond to the content the user actually reviewed and selected in the UI. This mirrors the reported bug class: a value meant to represent accumulated/reviewed state (there: `cumulative_interest_snapshot`; here: the user's line selection) is silently detached from the history it should be tied to when the underlying object is refreshed, producing an incorrect result (there: underpaid interest; here: wrong lines committed).

### Finding Description
The commit flow is:
1. UI computes a `DiffSelection` against a diff object loaded earlier (`updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts`), and that selection is retained across status refreshes purely by file ID, not content [1](#0-0) .
2. When the user commits, `_commitIncludedChanges` passes the files (with their previously-computed `.selection`) straight to `createCommit` [2](#0-1) .
3. `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex` [3](#0-2) [4](#0-3) .
4. `applyPatchToIndex` does **not** use the diff the UI displayed and validated the selection against. It re-fetches a brand-new diff from disk at that moment (`getWorkingDirectoryDiff`) and immediately builds a patch from it using the old `file.selection` object: [5](#0-4) .
5. `formatPatch` walks the *new* diff's hunks/lines and asks `file.selection.isSelected(absoluteIndex)` — a purely index-based lookup with no correlation to the actual text that was selected in the UI: [6](#0-5) .

The only place that reconciles a stale selection against a changed diff (`withSelectableLines`, dropping selections for lines that no longer exist) is in the UI-facing `updateChangesWorkingDirectoryDiff` path [7](#0-6)  — this guard is never invoked in the `apply.ts` commit-time path. If the working tree file changes between the last time the UI reconciled the selection and the moment `applyPatchToIndex` independently re-diffs the file (a normal TOCTOU window — e.g. an external editor autosave, a build/format-on-save tool, a git smudge/clean filter, or a `post-checkout`/merge driver triggered from a cloned/fetched repository), the absolute line indices in the old selection will silently map onto different lines/content in the new diff. `formatPatch` will happily produce a patch from these mismatched offsets, and `git apply --cached` will stage it without complaint.

### Impact Explanation
This is a "silent corruption of what the user commits" bug. A user could review and consciously deselect a chunk of a diff (e.g., a suspicious change, secret, or unwanted line), yet due to content changing in the file between UI selection and the commit-time re-diff, Desktop can stage and commit content the user never approved, or drop content the user meant to keep — with no indication to the user that this happened. Because the source of the file content is the working tree, this is directly reachable by any actor that can influence working-directory content around commit time (smudge/clean filters or hooks shipped in a cloned/fetched malicious repository, or another local tool racing with Desktop), satisfying the "attacker controls a cloned/fetched repository" criterion and producing a result of "silent corruption of what the user commits."

### Likelihood Explanation
Requires a timing window between when the user builds a line-based selection in the UI and when the commit is executed (staging happens asynchronously and independently re-diffs the file). Filters/hooks defined in a repository (`.gitattributes` smudge/clean filters, post-checkout scripts) or common developer tools (auto-formatters, linters-on-save) are a realistic and repeatable trigger for file content changing during this window, especially in larger repos where commit staging (which serially runs multiple git processes) takes non-trivial time. No elevated privileges or local malware are required beyond what a malicious repository can already configure.

### Recommendation
`applyPatchToIndex` should not perform an independent, unsynchronized re-diff of the file at staging time. Instead, it should either:
- Use the exact diff object that the selection was validated/created against (threading it through from the UI/`_commitIncludedChanges` call), or
- Re-run the same reconciliation used in `updateChangesWorkingDirectoryDiff` (`withSelectableLines`) against the freshly-fetched diff before formatting the patch, and abort/re-prompt the user if the diff has materially changed since the selection was made, rather than silently applying stale offsets to new content.

### Proof of Concept
1. Modify a tracked file so it has multiple hunks; open it in Desktop's Changes view.
2. Deselect a specific hunk/line range (e.g., lines containing a sensitive value) so the resulting `DiffSelection` excludes it.
3. Before clicking "Commit", trigger a change to the same file's content that shifts line offsets without going through Desktop's diff-reload path — e.g. a `.gitattributes` clean/smudge filter configured by the repository, or an external editor auto-save/format-on-save — such that the new diff's hunk boundaries differ from the one the UI last reconciled against.
4. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) applies the stale index-based selection to it.
5. Inspect the resulting commit: it will include/exclude different content than what was visually selected/deselected in the UI, with no warning to the user.
