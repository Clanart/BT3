### Title
Deterministic `CachedPreprocess` reuse across signing rounds leaks the FROST secret share to any party who submits two distinct messages - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Tributary signing protocol persists a 32-byte `CachedPreprocess` seed per `context` and regenerates the identical nonce/commitment pair on every `share_internal` call for that context. Because the seed is reused while the attacker-influenced `msg` and preprocess set vary, an unprivileged party who causes two signing attempts against the same context obtains two Schnorr shares built on the same nonce, enabling direct recovery of the validator's secret share — the analog of "privileged operation executes attacker-controlled input" (CI secrets + attacker PR code → secret exfiltration; cached secret-bearing nonce + attacker-controlled message → secret-share exfiltration).

### Finding Description
`preprocess_internal` derives an encryption key from `"Cached Preprocess Encryption Key" || context || secret_key`, stores a seed under `CachedPreprocesses` keyed only by `self.context`, and only generates a new seed when none exists (`coordinator/src/tributary/signing_protocol.rs:123-145`). [1](#0-0)  Every subsequent call — including each `share_internal` invocation at line 156 — decrypts the same seed and calls `AlgorithmSignMachine::from_cache`, which routes to `seeded_preprocess`. [2](#0-1) 

`seeded_preprocess` feeds that fixed seed into `ChaCha20Rng::from_seed` and derives `nonces` deterministically via `Commitments::new`, so the same `(d, e)` nonce scalars are produced for every reuse of the context. [3](#0-2)  The crate itself warns that a cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share," yet the coordinator reuses it for every share round under that context. [4](#0-3) 

In `sign`, the share is computed as `sign_share` = bound-nonce scalar + interpolation-weighted secret × challenge, where the challenge `c = H::hram(nonce_sum, group_key, msg)` depends on the attacker-supplied `msg` and peer preprocesses. [5](#0-4)  Two shares `s1 = k + λ·x·c1` and `s2 = k + λ·x·c2` with the same nonce `k = d + ρ·e` yield `x = (s1 − s2) / (λ·(c1 − c2))`.

### Impact Explanation
Recovery of a validator's FROST secret share is threshold-key compromise: combined with other leaked shares (or in the n-of-n MuSig context used here via `musig(...)` at line 119, a single colluding signer set suffices) it enables forging signatures on behalf of the Tributary validator set — the Serai analog of CI secret exfiltration. [6](#0-5) 

### Likelihood Explanation
An unprivileged participant reaches this with public inputs only: `msg` and the preprocess map fed to `read_preprocess`/`sign` are externally supplied bytes. Any code path that retries, re-signs, or double-invokes `share_internal` for the same `context` with a different message or signer set produces a nonce reuse. The design explicitly anticipates exactly this failure mode in its own warnings, and the `is_none()` guard guarantees reuse rather than fresh randomness. [7](#0-6) 

Caveat: I could not fully enumerate every `share_internal` call site to confirm a second invocation with distinct `msg` occurs in the same context within the coordinator flow; the vulnerability is structural — the cache intentionally persists the one-time seed — but exploitability depends on that call path being reachable more than once per context, which `share_internal` (line 156) makes possible by re-entering `preprocess_internal` each time.

### Recommendation
Do not regenerate signing nonces from a persistent seed. Either generate a fresh `OsRng` preprocess per `share_internal` call, or derive the seed from `context || msg || sorted participant set` so distinct sessions can never share nonces, and delete/invalidate `CachedPreprocesses` entries after a single use. Alternatively, mix a per-invocation random salt into `ChaCha20Rng::from_seed`.

### Proof of Concept
1. Validator calls `share_internal(ctx, participants, preprocesses_A, msg_A)` → produces share `s1` with nonce scalars derived from `CachedPreprocesses[ctx]`.
2. Same context is invoked again (retry/new round): `share_internal(ctx, participants, preprocesses_B, msg_B)` → same nonces `(d, e)`, share `s2`.
3. `c1 = hram(R_A, group_key, msg_A)`, `c2 = hram(R_B, group_key, msg_B)` with `c1 ≠ c2`.
4. Secret share `x = (s1 − s2) · (λ·(c1 − c2))⁻¹`, reconstructable entirely from the two broadcast shares and public preprocess data — direct key-share recovery matching the documented reuse hazard at `crypto/frost/src/sign.rs:85-87`.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
