### Title
Missing zero-value validation on `kip71.gastarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
The `Kip71GasTarget` governance parameter is registered with a `noopFormatChecker` that accepts any `uint64` value, including `0` [5](#0-4) . `NextMagmaBlockBaseFee` uses `gasTarget` directly as a divisor with no zero-check, unlike the sibling parameter `BaseFeeDenominator`, which is both format-checked to disallow `0` and defensively re-guarded at runtime [4](#0-3) , [3](#0-2) .

### Finding Description
`NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` computes the Magma dynamic base fee. When `parentGasUsed != gasTarget`, the code performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` in both the "increase" and "decrease" branches [7](#0-6) . If governance sets `kip71.gastarget = 0`, and any real block has non-zero gas used (`parentGasUsed > 0 = gasTarget`), the divisor is `0`, causing `big.Int.Div` to panic. This mirrors the reported class of bug in the Teller report where an unguarded divisor (there, `_maxPrincipalPerCollateralAmount`) reaches zero and the transaction always reverts/panics for a legitimate case; here the "always reverts" is a chain-wide panic on every subsequent block once the parameter is applied.

This function is called from `BlockValidator.validateHeader` for every header once the Magma fork is active [1](#0-0) , which is itself invoked from the consensus engine's `Verify()` path for every block proposal/import [2](#0-1) .

### Impact Explanation
Once `kip71.gastarget` is set to `0` via governance (mutable parameter, changeable through header/contract governance per `kaiax/gov`), all subsequent blocks with nonzero gas usage will trigger a divide-by-zero panic inside header validation on every node computing/verifying the expected base fee. This halts block production/validation network-wide — a chain-halting denial of service, not merely a single-transaction revert.

### Likelihood Explanation
`kip71.gastarget` is listed as a mutable governance parameter (`kaiax/gov/README.md`) that can be changed at runtime, and its `FormatChecker` is `noopFormatChecker`, meaning nothing in the parameter validation pipeline rejects `0`. This is a straightforward, single governance vote/update away from being triggered, and the very next block with nonzero gas usage crashes validation. The asymmetric treatment versus `BaseFeeDenominator` (which is explicitly guarded both at format-check and at runtime) strongly indicates this is an oversight rather than an intentional gap.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) that rejects `0`, analogous to the `Kip71BaseFeeDenominator` checker [3](#0-2) . As defense in depth, also add the same runtime zero-guard pattern used for `BaseFeeDenominator` inside `NextMagmaBlockBaseFee` before dividing by `gasTarget` [4](#0-3) .

### Proof of Concept
1. Governance sets `kip71.gastarget = 0` (accepted because `noopFormatChecker` permits it) [5](#0-4) .
2. Any proposer produces a block with `GasUsed > 0` after this parameter takes effect.
3. On processing the next header, `BlockValidator.validateHeader` calls `govParamSet.ToKip71Config().VerifyMagmaHeader(...)` → `NextMagmaBlockBaseFee(...)` [8](#0-7) .
4. Inside `NextMagmaBlockBaseFee`, `parentGasUsed (>0) > gasTarget (0)` is true, so the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` [9](#0-8) , causing a runtime panic (`big.Int` division by zero) on every node validating this and all subsequent blocks — halting the chain.
