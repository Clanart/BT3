Confirmed: the `WithdrawParams.input_signature` is documented and used as a `bitcoin::sighash::TapSighashType::SinglePlusAnyoneCanPay` signature [1](#0-0) , and this exact signature is fed straight into `create_payout_txhandler`, which places it as the key-spend witness for input 0 while separately building an OP_RETURN output (index 2) that embeds whichever `operator_xonly_pk` the calling operator supplies [2](#0-1) .

### Title
Payout-tx OP_RETURN operator-credit field is not covered by the user's `SinglePlusAnyoneCanPay` signature, allowing reimbursement credit hijack - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The user's presigned withdrawal authorization uses `SIGHASH_SINGLE|ANYONECANPAY`, which only commits to input 0 and the single output at the same index (the user's payout output). The OP_RETURN output that records "which operator fronted this peg-out" (and is later used by the bridge circuit/verifiers to decide who gets reimbursed) is a *different* output index and is therefore **not covered by the sighash the user signed**. Anyone holding the broadcast (or even just relayed/mempool) payout transaction and the user's signature can rebuild an equivalent transaction with the same signed input/output pair but an arbitrary OP_RETURN operator pubkey, breaking the intended binding "the operator credited == the party that paid."

### Finding Description
`create_payout_txhandler` builds the payout tx with three outputs: the user payout, an anchor, and an OP_RETURN containing `operator_xonly_pk` [3](#0-2) . The only authentication over the whole transaction is `user_sig`, which per the protobuf contract is `TapSighashType::SinglePlusAnyoneCanPay` [4](#0-3) . Under BIP341/BIP143 semantics, `SIGHASH_SINGLE|ANYONECANPAY` commits only to the current input and the output with the same index (output 0); it explicitly does **not** commit to output 2 (the OP_RETURN carrying the operator's identity) or output 1 (anchor). Downstream, this OP_RETURN value is treated as authoritative proof of "who paid": it is parsed back out by `update_finalized_payouts` to populate `payout_payer_operator_xonly_pk` in the DB [5](#0-4) , is checked against the kickoff's claimed operator in `is_kickoff_malicious` [6](#0-5) , and is read directly inside the ZK bridge circuit itself to compute `deposit_constant` (the value ultimately used to gate/disprove reimbursement) via `parse_op_return_data(&first_op_return_output.script_pubkey)` [7](#0-6) . Because the sighash the user signs never binds this field, an unprivileged party who observes the user's signature/outpoint (visible once the payout tx is broadcast, or leaked via mempool/relay before confirmation) can construct a *different* valid transaction reusing the same input and signature, keeping output 0 identical (satisfying the sighash), but substituting any `operator_xonly_pk` value into the OP_RETURN output. This directly parallels the reported bug class: a commitment (here, "who fronted this payout") that is not cryptographically bound to the actor's identity/authorization can be copied and reattributed by a third party.

### Impact Explanation
This breaks the custody binding "the operator credited == the party that paid": whoever actually funds the payout output no longer controls who is recorded/proved as the funder in the on-chain artifact used for reimbursement bookkeeping and (more importantly) inside the bridge circuit's `deposit_constant`. Depending on how downstream logic reconciles kickoff ownership vs. the OP_RETURN value (partially checked off-chain in `is_kickoff_malicious`, but the ZK circuit itself performs no such cross-check against the kickoff/round owner), this can lead to reimbursement bookkeeping being attributable to an operator who never funded the payout, or a legitimate operator's payout being unrecognized/misattributed, undermining the "operator reimbursed for a payout it never funded" / "honest operator permanently unable to be reimbursed" impact classes.

### Likelihood Explanation
The main precondition is visibility of the user's `input_signature` and `input_outpoint` before/while the transaction is unconfirmed — trivially available once the operator broadcasts the payout tx (public mempool) or if the RPC-returned raw tx is otherwise observed, requiring no operator/verifier/watchtower privilege. Constructing the alternate transaction only requires re-serializing a standard Bitcoin transaction with a different push in the OP_RETURN output and reusing the identical witness, which is a simple, permissionless action.

### Recommendation
Change the user's authorization sighash to cover the entire transaction (e.g., `SIGHASH_ALL` or `SIGHASH_ALL|ANYONECANPAY` restricted to the specific input), or otherwise fold the OP_RETURN operator-attribution bytes into data that the `SIGHASH_SINGLE` output at index 0 commits to (e.g., embed a hash of `(operator_xonly_pk || output_script_pubkey || output_amount)` and require it match). Additionally, the bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs`) should cryptographically verify that the OP_RETURN-derived `operator_xonlypk` matches the operator that actually owns/signed the round/kickoff transaction referenced by `round_txid`/`kickoff_round_vout`, rather than trusting the OP_RETURN value in isolation.

### Proof of Concept
1. Operator (or any observer) obtains a pending/broadcast `payout_tx` built by `create_payout_txhandler`, along with the raw `user_sig` (`SinglePlusAnyoneCanPay`) used for input 0 — visible in the mempool or via the `Withdraw`/`InternalWithdraw` RPC response (`RawSignedTx`) [8](#0-7) .
2. Attacker crafts a new transaction with the identical input (same outpoint) and identical output 0 (script_pubkey/amount unchanged, satisfying `SIGHASH_SINGLE`), reuses the same witness/signature for input 0, but replaces output 2's OP_RETURN payload with a different `operator_xonly_pk` (their own, or an arbitrary target's).
3. Broadcast the alternate transaction (a valid double-spend of the original candidate, replacing it if not yet confirmed, since both spend the same input and only the anchor/OP_RETURN differ and no sighash covers them).
4. Downstream consumers (`update_finalized_payouts`, `is_kickoff_malicious`, and the bridge circuit's `deposit_constant` computation) will attribute the payout to the attacker-chosen `operator_xonly_pk` instead of the operator who actually funded/broadcast the original transaction.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
