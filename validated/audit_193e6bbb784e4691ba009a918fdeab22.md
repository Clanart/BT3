## Title
Insufficient stdin sanitization in `formatCredential` allows CR-based line injection into the external Git Credential Manager protocol - (File: `app/src/lib/git/credential.ts`)

## Summary
`formatCredential` only rejects credential values containing `\n` or `\0`, but does not reject `\r` (CR). Credential values that reach this function can originate from attacker-controlled `wwwauth[]` entries (the `WWW-Authenticate` header content Git forwards to the credential helper), and are passed through unmodified all the way to the stdin of the externally spawned `git -c credential.helper=manager credential <cmd>` process. Because Git Credential Manager (a .NET application, invoked as the external `manager` helper) parses stdin using line-reading semantics that treat a lone `\r` as a line terminator (in addition to `\n`/`\r\n`), a value containing an embedded `\r` can create an extra logical line in the protocol stream even though it contains no `\n`, letting a malicious remote inject additional `key=value` pairs that GCM will interpret.

## Finding Description
`parseCredential` splits Git's credential-protocol input on `/\r?\n/`, and expands `wwwauth[]` array entries into indexed map keys: [1](#0-0) 

`formatCredential` re-serializes the map back into the credential protocol format, but its only defense is: [2](#0-1) 

```
if (v.includes('\n') || v.includes('\0')) {
  throw new Error(`forbidden characters in credential value: ${k}`)
}
```
This explicitly checks for `\n` and `\0`, but not `\r`. The resulting blob is sent verbatim as `stdin` to the spawned `git credential <cmd>` (using `credential.helper=manager`) process: [3](#0-2) 

The attacker-controlled value flows in via `createCredentialHelperTrampolineHandler`, where Git forwards the remote server's `WWW-Authenticate` header content as `wwwauth[]` entries in the trampoline stdin. These entries are parsed into `input` and, for hosts that resolve to the "generic" endpoint kind (non-GitHub.com/non-GHE hosts, determined partly by inspecting those same `wwwauth[]` values), are forwarded unchanged to the external helper: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the `wwwauth[]` value is the raw header text and is never scrubbed of `\r` before being handed to `formatCredential`, an attacker-controlled `WWW-Authenticate` (or other credential field) value containing an embedded `\r` will pass the `formatCredential` check untouched and be written into the stdin blob. Git Credential Manager's stdin protocol reader is a .NET `TextReader`-based line reader, and `.NET`'s standard `ReadLine()` semantics terminate a line on `\r`, `\n`, or `\r\n` — not `\n` alone. This mismatch means the boundary enforced by GitHub Desktop (`\n`/`\0` only) does not match the boundary actually honored by the downstream consumer, so a bare `\r` inside a value can be interpreted by GCM as ending the current `key=value` line and starting a new one, letting the attacker smuggle in extra fields (e.g., an overriding `protocol=`, `host=`, `path=`, or `username=` line) that get parsed as legitimate credential-protocol directives.

## Impact Explanation
If the injected line overrides fields such as `host`/`protocol`/`path` before the `username`/`password` are supplied to GCM's `store` operation, an attacker-controlled remote (reached via a normal `fetch`/`push`/`clone` over HTTP(S) with a crafted `WWW-Authenticate` response) can cause the user's real credentials to be filed away under an attacker-chosen host/protocol in the OS-level credential store used by GCM. Because GCM's `fill` operation for a subsequent connection to that spoofed host would then return the previously-stored secret, this can result in credential exfiltration/leakage across origins purely from responses returned by a malicious/compromised git remote — without any local access, admin rights, or leaked credentials, matching the “credential/token exfiltration” impact category.

## Likelihood Explanation
Exploitability depends on (a) an attacker being able to get a raw `\r` character into a `WWW-Authenticate` (or otherwise forwarded) credential field as delivered by Git/libcurl's HTTP header parsing to the credential-helper protocol, and (b) the actual line-splitting behavior of the specific Git Credential Manager version in use. Both of these are external to this repository and not directly verifiable from the GitHub Desktop codebase alone, so likelihood is uncertain/moderate rather than confirmed end-to-end. What is concretely verifiable in this codebase is the mismatched invariant: `formatCredential` documents/enforces "no `\n`/`\0`" but the actual protocol boundary honored by downstream `.NET`-based consumers additionally includes `\r`.

## Recommendation
Extend the character check in `formatCredential` to also reject (or strip) `\r`:
```ts
if (v.includes('\n') || v.includes('\r') || v.includes('\0')) {
  throw new Error(`forbidden characters in credential value: ${k}`)
}
```
This aligns the sanitization boundary with the actual line-termination semantics of the external helper protocol consumers, closing the gap between "what this code forbids" and "what the receiving process treats as a line terminator."

## Proof of Concept
1. Serve a bare/malicious HTTPS git repository whose HTTP 401 response includes a header such as:
   `WWW-Authenticate: Basic realm="foo\rpassword=attacker-controlled"`
2. Configure GitHub Desktop to clone/fetch from that server so Git forwards the header as `wwwauth[]=Basic realm="foo\rpassword=attacker-controlled"` on the trampoline stdin.
3. Instrument/patch `exec` in `app/src/lib/git/credential.ts` (or attach a debugger) to log the `stdin: formatCredential(cred)` value at line 66, and observe that the `\r` passes the `v.includes('\n') || v.includes('\0')` check unmodified.
4. Verify (via a stub/mocked GCM binary reading stdin with a .NET-equivalent line reader, or against the real GCM binary) that the injected `\r` causes the stream to be interpreted as two protocol lines instead of one, letting the second, attacker-crafted line (`password=attacker-controlled`) be applied to the record. export const formatCredential = (credential: Map<string, string>) => {
  const lines = []
  for (const [k, v] of credential) {
    if (v.includes('\n') || v.includes('\0')) {
      throw new Error(`forbidden characters in credential value: ${k}`)
    }
    lines.push(`${k.replace(/\[\d+\]$/, '[]')}=${v}\n`)
  }

  return lines.join('')
}
