## Finding

### Title
Unconstrained `address` field in `GetRequestsWithProof` lets anyone mint reputation (and skew collator selection) without delivering anything - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
This is the local analog of the zkEVM "unconstrained free variable" class: a value that drives an on-chain accounting effect is never bound to anything the surrounding proof/verification actually attests to, so it can be set arbitrarily by whoever submits the extrinsic.

### Finding Description
`GetRequestsWithProof` carries a raw `address: Vec<u8>` field described only as "Address that should be credited with fees": [1](#0-0) 

`handle_get_requests` verifies the source-chain membership proof and the destination-chain state proof for the `requests`/`response`, but it never verifies any relationship between `address` and the entity that produced, delivered, or is authorized for this proof: [2](#0-1) 

At the end of processing, `address` is used directly — with only a length check, no signature or origin check — to mint `pallet-messaging-incentives`' `ReputationAsset` scaled by total bytes served: [3](#0-2) 

This is called from an unsigned, permissionless extrinsic (`ensure_none` origin, validated only by proof correctness and duplicate-batch hashing, not by `address`): [4](#0-3) 

Contrast this with the sibling pallet `messaging-incentives`, which at least cryptographically recovers the credited account from a signature over the message body: [5](#0-4) 

`state-coprocessor`'s `address` has no equivalent binding at all — it is a completely free variable relative to the proof.

### Impact Explanation
Reputation minted here is the primary input to collator selection: [6](#0-5)  (documented elsewhere for the sibling incentive pallet, and this pallet explicitly shares `pallet_messaging_incentives::MintPerByte` and `ReputationAsset` as "one source of truth": [7](#0-6) ). Because the credited account is an unauthenticated field, any address (including third parties who did no work, or an attacker's own sybil accounts) can be credited reputation for GET responses that only require already-public, already-finalized state data plus a proof — data that requires no special relaying risk or cost to reconstruct. This lets an unprivileged actor inflate their own reputation (or falsely inflate/deflate someone else's) and thereby skew the collator-selection process that determines which accounts author Hyperbridge blocks — a host-management/consensus-integrity effect reachable purely through unauthenticated message flow, matching the stated pivot on cross-chain host-management effects.

### Likelihood Explanation
High for the mechanical exploit (no privileged access needed — just a valid `source`/`response` state proof pair, which is derivable from public chain state and doesn't require being a "real" relayer in any economically meaningful sense), but the direct monetary/fund-loss impact is bounded because `ReputationAsset` is non-transferable and only indirectly affects governance/collator-selection outcomes rather than moving funds directly.

### Recommendation
Bind `address` cryptographically the same way `pallet-messaging-incentives` does: require a signature over the `GetRequestsWithProof` payload (or over `hash_get_response`/the constructed responses) and recover the credited account from that signature instead of trusting a raw, unauthenticated `Vec<u8>`. Alternatively, remove the caller-supplied `address` entirely and derive the beneficiary solely from data the extrinsic's validation logic can independently verify.

### Proof of Concept
1. Observe any already-finalized source-chain state (source proof) and destination-chain state (response proof) for a set of `GetRequest`s that have not yet been responded to (these are public, e.g. visible via RPC/state proofs, not secret to any particular relayer).
2. Construct a `GetRequestsWithProof { requests, source, response, address: <attacker_account_bytes> }` and submit it via `state_coprocessor::handle_unsigned` (unsigned, permissionless per `ensure_none`/`ValidateUnsigned`).
3. `handle_get_requests` verifies the proofs successfully (they are genuine) and, since `MintPerByte` is non-zero, mints `total_bytes × MintPerByte` reputation to `attacker_account_bytes` — an account with no relationship to whoever actually retrieved/assembled the proof data.
4. Repeat across many distinct GET-request batches (each only creditable once due to `dedup_requests`/`response_receipt`, but new batches are continuously available) to accumulate reputation and bias collator selection in the attacker's favor. [8](#0-7)

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
