## Title
Desktop force-disables Git's built-in recursive-clone submodule RCE protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
The reported DeFi bug is: an attacker-controlled input (a fake pool's `slot0()`) is trusted without an upper-bound / authenticity check, letting the attacker corrupt a downstream computation that a victim relies on. The Desktop analog is structurally identical: Desktop's `clone()` function trusts a value it explicitly controls — but deliberately sets it to disable Git's own safety check — while cloning **recursively** from an attacker-supplied, untrusted remote (a malicious repository the victim clones). This removes the exact guard Git added to prevent a known RCE class in nested submodules.

### Finding Description
`clone()` in [1](#0-0)  builds the clone environment and always sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, and always passes `--recursive`: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git introduced specifically to mitigate the class of vulnerabilities where a malicious repository contains submodules with conflicting/case-confusable paths (e.g. a nested `.git` directory reachable via a symlinked or case-collided path on case-insensitive filesystems) that, when checked out recursively, cause files to be written into the top-level `.git` directory (for example, `.git/hooks/post-checkout`), leading to code execution during or immediately after the clone. Setting this variable to `'false'` is an explicit, unconditional opt-out of that guard for every clone Desktop performs — it is not scoped to trusted remotes, and there is no check anywhere in `clone()` on the pool/remote's authenticity (analogous to the missing Uniswap V3 Factory validation of `poolAddress` in the report). Any URL fed into `clone()` — whether typed by the user, provided via `x-github-client://openRepo/...` deep links ( [2](#0-1) ), or a fork `clone_url` from the GitHub API in the PR-checkout flow ( [3](#0-2) ) — results in a recursive clone with the protection removed.

The only mitigations present in `clone.ts` are `isClonePathSensitive()`, which only blocks specific destination directories like `~/.ssh` ( [4](#0-3) ), and nothing validates the *content* of the remote repository or restores Git's own submodule-checkout hardening. This mirrors the report's core flaw exactly: a downstream safety check that should bound/verify an untrusted external input is missing or defeated, and the existing "minimum" checks (here, only path-sensitivity) do not cover the actual attack surface (malicious repository content via `--recursive` submodules).

### Impact Explanation
A victim who clones an attacker-authored public repository (directly, via "Clone repository" URL entry, via an `x-github-client://openRepo/` deep link, or via the PR/fork checkout flow that also calls into recursive submodule update logic — [5](#0-4) ) can have arbitrary files written outside the intended working tree/root, up to code execution on the victim's machine, because Desktop has explicitly turned off the protection Git ships specifically to stop this. This satisfies the "attacker controls a cloned/fetched repository → code execution/file write outside the repo" impact class from the Valid Impact rules.

### Likelihood Explanation
Likelihood is Low/Medium: it requires the underlying Git version and OS/filesystem to still be susceptible to the submodule path-confusion technique that `GIT_CLONE_PROTECTION_ACTIVE` protects against (case-insensitive filesystems, e.g. default macOS/Windows, are the classic targets), and requires the victim to clone a repository the attacker controls — a normal, unprompted Desktop workflow (no special user steps, no local access, no prior compromise needed).

### Recommendation
1. Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` ( [6](#0-5) ) and let Git's default protection remain active for all clones, especially recursive ones.
2. If the override exists to work around a specific compatibility issue, gate it narrowly and document why it's safe, and pair it with independent validation of submodule paths before recursive checkout (reject `.git`-colliding or symlinked submodule paths).
3. Apply the same authenticity/bounds principle from the original report: don't disable an upstream safety mechanism for an operation (`clone --recursive`) whose input (the remote repository content) is fully attacker-controlled.

### Proof of Concept
1. Attacker creates and hosts a public Git repository containing a submodule configured with a path that collides with `.git` on a case-insensitive filesystem (the technique behind Git's `GIT_CLONE_PROTECTION_ACTIVE` mitigation), with a payload hook (e.g., `hooks/post-checkout`).
2. Attacker shares a normal clone URL, or crafts an `x-github-client://openRepo/<attacker-repo-url>` deep link (parsed unconditionally by `parseAppURL`, [7](#0-6) ).
3. Victim clicks the link or pastes the URL into "Clone repository."
4. Desktop calls `clone()`, which runs `git -c ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment ( [8](#0-7) ), disabling Git's own defense against the malicious submodule layout.
5. During recursive submodule checkout, the malicious payload lands inside `.git/hooks` and executes on the victim's machine, or writes files outside the intended repository root.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }
