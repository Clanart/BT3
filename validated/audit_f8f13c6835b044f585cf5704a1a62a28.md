### Title
Unrelated transaction overwrites received-output instructions and origins in the same block - (File: `processor/src/networks/bitcoin.rs`)

### Summary
`Bitcoin::get_outputs` accumulates matching outputs in a block-level `outputs` vector, but applies transaction-specific metadata from every subsequent transaction to all previously collected outputs. An unprivileged user can place an unrelated transaction after a deposit in the same block and erase or replace the deposit’s Serai instruction and presumed origin. The resulting output can be reported without a valid `InInstruction`, causing the deposited funds not to be credited even though they are locked to Serai.

### Finding Description
`Bitcoin::get_outputs` initializes `outputs` before iterating over `block.txdata[1 ..]` [1](#0-0) . For each transaction, matching outputs are appended, and then `if outputs.is_empty()` tests the cumulative block-level list rather than only the outputs found in the current transaction [2](#0-1) . Once any earlier transaction produced an output, every later transaction reaches the metadata-population path and derives `presumed_origin` from its own first input [3](#0-2) . The code then assigns that transaction’s extracted data and origin to every accumulated output, including outputs from earlier transactions [4](#0-3) .

The received-output accounting itself is correct: `Scanner::scan_transaction` records the matching `TxOut`, the correct transaction ID, and the output index in `ReceivedOutput` [5](#0-4) . The bug is in the later accounting/instruction association layer. External output data is converted into a `Shorthand` and then a `RefundableInInstruction`; invalid or erased data causes the output to be skipped rather than credited [6](#0-5) .

### Impact Explanation
A valid Bitcoin deposit can be emitted as a received `Output` but lose its deposit instruction or receive the wrong refund/origin metadata because of an unrelated transaction later in the same block. If the later transaction has no Serai payload, `extract_serai_data(tx)` can replace the deposit’s data with empty data, making `Shorthand::decode` fail and preventing an `InInstructionWithBalance` from being produced [7](#0-6) . This is the Serai analog of receiving assets without updating the user-facing balance: funds are detected and assigned the correct outpoint/value, but the balance-producing instruction is discarded.

### Likelihood Explanation
The attacker only needs to get an ordinary transaction included after the victim’s deposit in the same block. The attack does not require control of Serai keys, validators, peers, or RPC. Bitcoin transaction ordering inside a block is attacker-influenceable but not fully attacker-controlled, so exploitation is opportunistic rather than guaranteed. The flaw is nevertheless reachable entirely through public Bitcoin transaction data processed by `get_outputs`.

### Recommendation
Track matching outputs per transaction and populate metadata only for that transaction’s outputs. For example, maintain `let mut tx_outputs = vec![]` inside the `for tx` loop, append scan results to `tx_outputs`, skip when that list is empty, populate only `tx_outputs`, and then extend the block-level result. Alternatively, record `(transaction index/output)` together with each scanned output and look up its corresponding transaction’s payload and origin rather than mutating all accumulated outputs.

### Proof of Concept
1. Victim broadcasts transaction `T1`, which contains a P2TR output to Serai’s external address and a valid Serai instruction payload.
2. In the same block, after `T1`, include unrelated transaction `T2` controlled by the attacker. `T2` has no Serai output and no valid Serai instruction payload.
3. `get_outputs` scans `T1`, appends the deposit to `outputs`, and correctly gives it the victim transaction ID and metadata.
4. The loop reaches `T2`. Because the cumulative `outputs` vector is still nonempty, the `outputs.is_empty()` check does not skip metadata handling.
5. The code derives `presumed_origin` from `T2.input[0]` and executes the loop over `&mut outputs`, overwriting the `T1` output’s `data` with `Self::extract_serai_data(T2)` and its origin with `T2`’s first input script [8](#0-7) .
6. `instruction_from_output` attempts `Shorthand::decode` on the overwritten data and returns no `InInstructionWithBalance` on failure [9](#0-8) .
7. The deposit remains locked under the Serai key, but the deposit instruction/balance accounting is lost.
