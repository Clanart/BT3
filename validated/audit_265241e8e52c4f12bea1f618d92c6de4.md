### Title
Merge-conflict resolutions are spliced back into files by positional hunk order with no count/consistency check between the two independent marker-parsers — attacker-controlled conflict content can cause silent corruption of committed code - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Sherlock report's root cause is a computed value (`rewardPerLockedToken`) that is derived through an integer operation with no invariant check against the real magnitude, so it silently truncates to zero and the protocol loses value without any revert. Desktop's AI-assisted merge/rebase/cherry-pick conflict resolution feature has a structurally analogous flaw: the value that gets written back into the user's working tree is assembled by positionally matching an LLM's per-hunk output against conflict-marker blocks that are independently re-parsed from disk, with no check that the two counts agree. When they diverge, the wrong resolved content is silently spliced into the wrong conflict location.

### Finding Description
`buildConflictContext` reads the on-disk conflicted file and calls `extractConflictHunks` to find every `<<<<<<< / ======= / >>>>>>>` block, producing an ordered list of hunks that is sent to Copilot as "Conflict 1 of N", "Conflict 2 of N", etc. [1](#0-0) 

After the model responds, `reassembleResolvedFile` walks the same `rawContent` a second time using a **separate, independently implemented** marker-detection state machine (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) and splices `hunkResolutions[hunkIndex]` into place purely by the order it encounters conflict blocks — explicitly "matched by order, not by line number": [2](#0-1) 

Critically, the splice loop has no assertion that the number of conflict blocks it discovers equals `hunkResolutions.length`:
```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  ...
}
hunkIndex++
```
If fewer resolutions than conflict blocks exist, later blocks are silently left with markers stripped but no replacement content; if the model's hunk array is misordered or miscounted relative to what this second parser finds, resolution N's content gets written into conflict block M. The upstream validator (`parseCopilotConflictResolution`) checks only that each `resolvedContent` is a string and doesn't itself contain marker text — it never cross-checks the hunk count against the file's original `IFileConflictContext.hunks.length`: [3](#0-2) 

Because `extractConflictHunks` (used to build the prompt/count) and the reassembly scanner are two hand-written, separately-maintained regex state machines over the same attacker-influenced text, any edge case where they disagree on hunk boundaries (e.g., content on one side of a conflict that contains marker-like text, adjacent/malformed marker sequences, or a case where the model itself miscounts hunks in a large/complex file) causes the exact "nominator/denominator" style divergence from the Sherlock report: a computed index used in an arithmetic/positional mapping that silently produces the wrong result instead of failing loudly.

### Impact Explanation
The corrupted value here is the final on-disk file content written by `reassembleResolutions` → `reassembleResolvedFile`, which becomes the file the user stages and commits/pushes. This falls squarely under the allowed impact category "silent corruption of what the user commits or pushes." Because conflict content originates from a remote/incoming branch (attacker-controlled in a fork/PR/merge scenario) and is fed verbatim into the reassembly parser, a maliciously or adversarially structured conflicting file could cause Desktop's AI conflict resolution to write the wrong branch's code into a location the user believes was correctly resolved by the other branch's changes — with no error, warning, or diff-verification step forcing the user to notice the mismatch before committing.

### Likelihood Explanation
This requires no local access, admin rights, or prior compromise: it only requires the user to hit a merge/rebase/cherry-pick conflict against an attacker-influenced branch and use Desktop's Copilot-based conflict resolution feature (a normal, prompted user workflow). The likelihood of the *specific* divergence between the two independent parsers firing is uncertain without executing the two functions side-by-side against adversarial marker-like inputs — this is the main gap in my analysis, since I could not run the code to construct a concrete input that provably desynchronizes `extractConflictHunks` and `reassembleResolvedFile`'s hunk counts. What is confirmed by static reading is that **no consistency check exists** between the two counts, which is the missing guard needed to make this impossible.

### Recommendation
Add an explicit invariant check in `reassembleResolutions`/`reassembleResolvedFile`: after reassembly, assert `hunkIndex === hunkResolutions.length` (and ideally also equals `ctx.hunks.length` from the original `extractConflictHunks` pass) and throw a `CopilotValidationError` on mismatch instead of silently completing. Additionally, unify the two marker-parsing implementations into one shared function used both for extraction and reassembly so they cannot structurally diverge.

### Proof of Concept
Not independently verified end-to-end (no execution environment available). Conceptual PoC based on code reading:
1. Craft a merge where the incoming ("theirs") branch's conflicting content includes a line matching `reassemblySeparatorMarker` (`=======`) or `reassemblyTheirsMarker` (`>>>>>>> ...`) pattern as literal text (e.g., a code comment or string literal containing `=======`).
2. `extractConflictHunks`, used to build the prompt, may parse the block boundaries one way while `reassembleResolvedFile`'s independent scan (triggered later, purely via regex forward-scan for the first `=======`/`>>>>>>>`) terminates the conflict block early or late relative to what the model was shown.
3. The model returns `resolvedContent` for the hunk it believes it resolved (based on the prompt's boundaries), but `reassembleResolvedFile` splices it in at different, misaligned boundaries determined by its own independent re-parse — resulting in silently corrupted file content once written and committed. /**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
