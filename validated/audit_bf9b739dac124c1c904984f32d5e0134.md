### Title
`rewards()` in the distribution precompile lacks a non-payable check, permanently stranding native value sent with the call - ([File: precompiles/distribution/distribution.go])

### Summary
The distribution precompile's `rewards(address)` view function is missing the `pcommon.ValidateNonPayable(value)` guard that every other view/transaction method in the same file enforces. A caller can invoke `rewards()` on the distribution precompile (`0x0000000000000000000000000000000000001007`) while attaching native SEI value; the EVM will debit that value from the caller and credit it to the precompile's account as part of the standard value-transfer semantics of a `CALL`, but the executor code never consumes, forwards, or refunds it, so the funds become permanently stuck at the precompile address. [1](#0-0) 

### Finding Description
All other query/transaction handlers dispatched from `Execute` for this precompile validate that no value was attached before doing any work, via `p.validateInput` (which calls `pcommon.ValidateNonPayable`) or an explicit `pcommon.ValidateNonPayable` call: `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`, and the mutating withdraw/grant/revoke methods. [2](#0-1) [3](#0-2) 

`rewards()`, however, is dispatched with only `args` (no `value` parameter passed through), and its implementation never calls `ValidateNonPayable`: it only validates argument length and then queries `DelegationTotalRewards`, returning the response: [4](#0-3) [1](#0-0) 

This is exactly the bug class described in the report: a payable-looking (or rather, un-guarded) entry point accepts `msg.value`, the EVM performs the balance transfer to the callee (the precompile address) as part of normal `CALL` semantics, and the executor logic path taken never uses, forwards, or returns that value — so it is permanently frozen. The codebase itself documents awareness of exactly this risk in the integration test suite: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)", explicitly noting the test suite deliberately skips exercising the "view rejects value" case for `rewards()` because it would demonstrate this stranding behavior rather than a revert. [5](#0-4) 

Other precompile methods that intentionally accept value (e.g., `wasmd`'s `execute`/`executeBatch`) explicitly account for every wei via `HandlePaymentUsei`/`HandlePaymentUseiWei`, which refunds the payer's account from the precompile address before debiting the correct amount for the CosmWasm message, and further enforce that the full `value` must be consumed (`"value remaining after execution, must match provided amounts exactly"`). [6](#0-5)  `rewards()` has none of this refund/consumption machinery and no non-payable gate either, so it is the one entry point in this precompile family that can silently accept and lose native funds.

### Impact Explanation
Any unprivileged EVM caller (an externally owned account or a smart contract) can call `rewards(address)` on precompile `0x1007` with a non-zero `value`. The EVM's standard value-transfer mechanics move that usei/wei balance to the distribution precompile's account before/while executing the call, and because `rewards()` performs no ValidateNonPayable check and no refund logic, the funds remain credited to the precompile address with no code path capable of withdrawing or returning them to the sender. This is a permanent, unrecoverable freezing of native funds for any caller who (mistakenly or otherwise) attaches value to this call, matching the "concrete fund loss or permanent freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is low-to-moderate: an EOA or contract must deliberately or mistakenly attach `msg.value` to a static/query call, which is unusual for a `view`-labeled RPC/ABI query but not prevented at the ABI or EVM level (only the sibling precompile methods guard against it). Because every sibling method in the same file enforces `ValidateNonPayable`, this appears to be an oversight/gap rather than the norm — but the codebase's own test comments confirm the team is aware this method uniquely lacks the guard, and any tooling, wallet, or contract that automatically attaches value (e.g. due to a mis-set `msg.value` in a batched multicall) would trigger permanent loss with a single transaction, no special privileges required.

### Recommendation
Add the missing guard to `rewards()`, consistent with every other view method in the file:
```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, rerr error) {
    ...
    if err := pcommon.ValidateNonPayable(value); err != nil {
        rerr = err
        return
    }
    if err := pcommon.ValidateArgsLength(args, 1); err != nil {
        rerr = err
        return
    }
    ...
}
```
and update the call site at the `RewardsMethod` case in `Execute` to pass `value` through, mirroring `p.params(ctx, method, args, value)` etc. [4](#0-3) 

### Proof of Concept
1. An associated EVM account calls the distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)` and a non-zero `value` (e.g. `1 sei` worth of wei), e.g. via `ethers.Contract.rewards(delegatorAddress, { value: ethers.parseEther("1") })`.
2. `Precompile.Run`/`RunAndCalculateGas` forwards `value` into `PrecompileExecutor.Execute`, which dispatches to `case RewardsMethod: return p.rewards(ctx, method, args)` — note `value` is dropped and never checked. [4](#0-3) 
3. `rewards()` proceeds directly to argument validation and the `DelegationTotalRewards` query, returning successfully with the reward data. [1](#0-0) 
4. The transaction succeeds (status 1), the caller's `value` has been debited by the EVM value-transfer machinery to the precompile address, and no code path in `rewards()` or elsewhere refunds it — the funds are stuck at the precompile's balance permanently.

Note: I was not able to directly trace the exact Go-Ethereum `vm.EVM.Call`/`RunPrecompiledContract` value-transfer code within this index to show the literal balance-transfer statement executed for calls to precompile addresses; this is standard go-ethereum `Call` semantics (transfer `value` from caller to callee before invoking the precompiled contract) inherited by this fork, but I could not fetch that exact source snippet from the index in the time available. If precise confirmation of that exact EVM-level transfer call is needed, it would require inspecting the vendored go-ethereum `core/vm/evm.go` `Call` implementation directly in a full checkout.
