### Title
Forged Bitcoin `ReceivedOutput` bytes can fabricate spendable UTXOs and induce threshold signing of nonexistent-input transactions - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an attacker-controlled scalar offset, `TxOut`, and `OutPoint` without proving that the referenced output exists, that the script corresponds to the wallet key under the claimed offset, or that the claimed value is backed by a chain UTXO. A forged serialized output can therefore enter the wallet-signing pipeline as a fabricated spendable input. `SignableTransaction::new` trusts its value and outpoint, while `SignableTransaction::multisig` only checks that the input script matches the offset-derived key, not that the claimed UTXO/value is real. If such bytes are accepted from an unprivileged input path, the wallet can report phantom funds and produce a threshold-signed Bitcoin transaction spending a nonexistent or mis-valued output. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The deserialization routine treats all three security-relevant fields as self-authenticating:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)?;
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
``` [4](#0-3) 

This preserves syntactic validity but not semantic validity. An attacker can choose:

- `outpoint`: any txid/vout, including one that never existed.
- `output.value`: an arbitrary claimed amount.
- `output.script_pubkey`: a genuine wallet P2TR script so downstream key checks pass.
- `offset`: the offset needed so `key + offset*G` derives that script.

`SignableTransaction::new` then copies the forged `outpoint` into a transaction input and trusts the claimed `TxOut` as the corresponding prevout. [2](#0-1) [5](#0-4)  The only relationship checked before constructing per-input FROST machines is whether `p2tr_script_buf(keys.offset(offset).group_key()) == prevout.script_pubkey`. [6](#0-5)  No check ties the supplied `OutPoint` to a confirmed transaction, compares the claimed prevout against chain data, or rejects an externally supplied offset/script pairing that merely happens to belong to the wallet.

During signing, each input’s attacker-influenced prevout set is committed through `Prevouts::All`, so the threshold signature authorizes the fabricated input/value view rather than an independently verified UTXO set. [7](#0-6) 

### Impact Explanation
A successful forged `ReceivedOutput` causes two concrete failures:

1. **Phantom balance / unspendable “received” funds:** the object reports an arbitrary `value()` for an arbitrary `outpoint`, despite no chain output backing it. [8](#0-7) 
2. **Unintended threshold signing:** if passed to `SignableTransaction::new` and then `multisig`, honest participants produce shares for a transaction whose input references a nonexistent or incorrectly valued UTXO. The signed message is real and attacker-selected, even though Bitcoin consensus later rejects the transaction. [3](#0-2) [7](#0-6) 

This is analogous to the report’s forged-validation path: attacker-controlled bytes satisfy the local predicate while bypassing the intended external-state check.

### Likelihood Explanation
Any integration path that accepts serialized `ReceivedOutput` values from peers, persisted data, coordinator messages, or imported wallet state is exposed. The attacker does not need a validator key, consensus control, leaked secrets, malformed curve encodings, or invalid signatures—only the ability to supply bytes parsed by `ReceivedOutput::read` and have the result treated as an available wallet input. Generating the forgery requires only a valid wallet P2TR script and the corresponding registered/known offset; both are normal scanner outputs or can be selected so that the downstream key check succeeds. [9](#0-8) [6](#0-5) 

### Recommendation
Treat `ReceivedOutput` as untrusted evidence rather than proof of ownership:

- In `ReceivedOutput::read`, reject outputs that are not valid P2TR scripts and bind `offset` to the expected wallet key where a key context is available.
- Before accounting or signing, resolve each `outpoint` against verified chain data and compare both `script_pubkey` and `value` to the actual UTXO.
- In `SignableTransaction::new` / `multisig`, require authenticated prevouts rather than caller-claimed `TxOut`s, or maintain a dedicated `VerifiedOutput` type produced only by blockchain scanning/RPC confirmation.
- At minimum, ensure all callers reject serialized `ReceivedOutput`s not derived from `Scanner::scan_transaction`/`scan_block` over confirmed blocks.

### Proof of Concept
Conceptually, for a wallet base key `K` and registered offset `d`:

1. Compute `script = p2tr_script_buf(K + d*G).unwrap()`.
2. Construct a `TxOut` with `script_pubkey = script` and `value = 1_000_000`.
3. Construct an arbitrary `OutPoint`, e.g. `OutPoint { txid: all_zero_txid, vout: 0 }`.
4. Serialize `(d, TxOut, OutPoint)` using `ReceivedOutput::write` equivalent bytes.
5. Feed those bytes to `ReceivedOutput::read`.
6. Pass the result to `SignableTransaction::new`.

The result is accepted as an input, `input_sat` includes the fabricated `1_000_000`, and `multisig` succeeds because the script legitimately belongs to `K + d*G`. The signing machine then commits to `Prevouts::All` containing the forged `TxOut` and produces shares for a transaction spending the fabricated outpoint. [2](#0-1) [6](#0-5) [7](#0-6)
