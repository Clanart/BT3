### Title
Cached FROST nonce seed not bound to validator set — stale `CachedPreprocesses` reused across distinct MuSig groups, enabling private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's MuSig-based DKG confirmation protocol caches its FROST preprocess seed in `CachedPreprocesses`, keyed solely by `context`. For `DkgConfirmer`, that context is only `(b"DkgConfirmer", attempt)` — it does not include the tributary `spec`, the `ExternalValidatorSet`, the genesis, or the `removed` set. The bug class of the external report (a stale per-object pointer, `last_bfqq_created`, surviving a group change and being dereferenced under a new group) maps directly here: a cached nonce seed survives a group/set change and is reused under a different signing context.

### Finding Description
`DkgConfirmer::signing_protocol` builds `context = (b"DkgConfirmer", self.attempt)` and `SigningProtocol::preprocess_internal` does `CachedPreprocesses::get(self.txn, &self.context)`, generating a fresh seed only if none exists for that context, otherwise reusing the stored one. [1](#0-0) [2](#0-1) 

The seed fully determines the preprocess: `seeded_preprocess` feeds it into `ChaCha20Rng::from_seed` and derives the nonces/commitments via `Commitments::new` — the nonce depends on the seed and the validator's own `original_secret_share`, not on the participant set or message. [3](#0-2)  FROST documentation states reuse of a preprocess enables third-party recovery of the private key share. [4](#0-3) 

Two distinct group changes can therefore reuse one seed:

1. **Different tributary/set, same attempt.** The context encodes no `spec.set()`/genesis. Any second validator set whose `DkgConfirmer` runs `attempt = 0` (every set starts at attempt 0) over the same coordinator DB reuses the seed minted for the first set. The MuSig aggregate key, participant list, and `set_keys_message` all differ — but the nonce is identical.

2. **Different `removed` set for the same attempt.** `removed` comes from `removed_as_of_dkg_attempt` and is not part of `context` either; moreover `DkgConfirmer::preprocess` builds MuSig keys over *all* `spec.validators()` while `share`/`complete` remap to the non-removed signers via `threshold_i_map_to_keys_and_musig_i_map`. [5](#0-4) [6](#0-5)  The same deterministic nonces are thus committed into two different MuSig key contexts (full set vs. reduced set) under one cache entry.

### Impact Explanation
Two published `(preprocess, share)` pairs (or two completed Schnorrkel signatures) that share the same nonce `R` but have different binding factors/challenges (`rho` differs per participant set; `msg` differs via `set_keys_message`) yield the textbook Schnorr linear system: `s1 = d + e1·rho1·k`, `s2 = d + e2·rho2·k` — solvable for the nonce `k` and then for the validator's secret share `d`. Since these preprocesses and shares are published to the tributary/coordinator protocol, any observer (including an unprivileged party who merely causes a second set's DKG confirmation to run, or a removed validator) can recover the validator's MuSig private key, breaking the root-of-trust key used to confirm all future DKGs.

### Likelihood Explanation
No attacker sophistication beyond observing public protocol messages is required; the trigger is routine — a validator set rotation, a new tributary, or a removal that changes `removed` for the same attempt number. The design even documents that nonce safety rests entirely on the cached seed never being reused across distinct contexts, yet the cache key omits the group identity. One residual uncertainty: whether the `txn` passed in is scoped per-tributary; `CachedPreprocesses` is a flat `create_db!` table over the coordinator `DbTxn` and `DkgConfirmer::new` receives a caller-provided txn, so nothing in this file namespaces it per spec. [7](#0-6) 

### Recommendation
Bind the cache key to the full signing context: `context = (b"DkgConfirmer", spec.set() / spec.genesis(), removed_hash, attempt)`, so a group change forces a fresh seed — the equivalent of resetting `last_bfqq_created` on group change. Alternatively, derive the seed deterministically as `H(secret_key || set || removed || attempt)` and reject reuse when the derived context differs. Also fix the inconsistency where `preprocess()` uses all `spec.validators()` while `share`/`complete` exclude `removed`, so the MuSig key context is identical across rounds.

### Proof of Concept
1. Validator `V` is in tributary set A. `DkgConfirmer::new(key_V, spec_A, txn, attempt = 0)` is constructed; `preprocess()`/`share()` run, storing `CachedPreprocesses[("DkgConfirmer", 0)] = enc(seed)` and publishing `R_A`, `s_A` for `msg_A = set_keys_message(set_A, removed_A, key_pair_A)`.
2. Set A retires; a new tributary spec B (or the same spec with a changed `removed` set — e.g., a validator removed between preprocess and share rounds) runs `attempt = 0` on the same coordinator DB.
3. `preprocess_internal` finds the existing cache entry, derives the identical `ChaCha20Rng` seed, and — because `Commitments::new` depends only on the seed and `V`'s unchanged secret share — emits identical nonces `R_B = R_A` under a different MuSig aggregate key and `msg_B`.
4. Observer computes `k = (s_A - s_B) / (e_A·rho_A - e_B·rho_B)` and recovers `V`'s Ristretto secret share, forging future DKG confirmations.

// Get the keys of the participants, noted by their threshold is, and return a new map indexed by
// the MuSig is.
fn threshold_i_map_to_keys_and_musig_i_map(
  spec: &TributarySpec,
  removed: &[<Ristretto as Ciphersuite>::G],
  our_key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  mut map: HashMap<Participant, Vec<u8>>,
) -> (Vec<<Ristretto as Ciphersuite>::G>, HashMap<Participant, Vec<u8>>) {
  // Insert our own index so calculations aren't offset
  let our_threshold_i = spec
    .i(removed, <Ristretto as Ciphersuite>::generator() * our_key.deref())
    .expect("MuSig t-of-n signing a for a protocol we were removed from")
    .start;
  assert!(map.insert(our_threshold_i, vec![]).is_none());

  let spec_validators = spec.validators();
  let key_from_threshold_i = |threshold_i| {
    for (key, _) in &spec_validators {
      if threshold_i == spec.i(removed, *key).expect("MuSig t-of-n participant was removed").start {
        return *key;
      }
    }
    panic!("requested info for threshold i which doesn't exist")
  };

  let mut sorted = vec![];
  let mut threshold_is = map.keys().copied().collect::<Vec<_>>();
  threshold_is.sort();
  for threshold_i in threshold_is {
    sorted.push((key_from_threshold_i(threshold_i), map.remove(&threshold_i).unwrap()));
  }

  // Now that signers are sorted, with their shares, create a map with the is needed for MuSig
  let mut participants = vec![];
  let mut map = HashMap::new();
  for (raw_i, (key, share)) in sorted.into_iter().enumerate() {
    let musig_i = u16::try_from(raw_i).unwrap() + 1;
    participants.push(key);
    map.insert(Participant::new(musig_i).unwrap(), share);
  }

  map.remove(&our_threshold_i).unwrap();

  (participants, map)
}

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
