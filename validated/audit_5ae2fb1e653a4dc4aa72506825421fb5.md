The Tron variant of `IntentGatewayV2.placeOrder` contains a real, unpatched analog of the reported bug class.

### Title
Escrow credited with requested amount instead of actual tokens received, enabling shared-pool fund shortfall/theft for fee-on-transfer or rounding-lossy tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` computes the escrowed amount (`reducedInputs[i].amount`) from the order's *requested* input amount rather than the amount actually received by the contract from `safeTransferFrom`. For any token that delivers less than the requested amount on transfer (fee-on-transfer tokens, deflationary tokens, or tokens with `stETH`-style rounding loss), the contract's internal escrow ledger `_orders[commitment][token]` is inflated above the real token balance the contract holds for that transfer.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are pulled with a plain `safeTransferFrom` and the escrow is credited with the pre-transfer accounting value, never the post-transfer balance delta: [1](#0-0) 

Compare this to the canonical EVM implementation of the same contract, which explicitly guards against exactly this class of token by snapshotting the balance before and after the transfer and mutating `order.inputs[i].amount` to the *actual received* amount before it is used to compute `reducedInputs` and the escrow credit: [2](#0-1) 

The comment in the primary EVM contract makes the intent explicit: "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds." [3](#0-2) 

That safeguard is absent in the Tron contract's non-predispatch path — `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the amount the user *claims* to be sending), and this value, not a measured balance delta, is what's added to `_orders[commitment][token]`: [4](#0-3) 

Because `_orders[commitment][token]` is an accounting mapping over a shared token balance pool (all orders for the same token share the contract's single `balanceOf`), an order using a lossy-transfer token inflates the ledger beyond what is actually custodied. When that or another order later redeems/refunds via `withdraw()`, tokens are transferred out based on the ledger value, not validated against actual solvency: [5](#0-4) 

### Impact Explanation
This is an unauthorized/unauthenticated fund-accounting bug reachable by any ordinary user: place an order using a fee-on-transfer, deflationary, or rounding-lossy TRC-20 token as `order.inputs[i]`. The contract credits the escrow ledger with more tokens than it actually received and holds. Because the pool of that token in the contract is shared across all commitments, this creates an insolvency where some legitimate order's later `RedeemEscrow`/`RefundEscrow` withdrawal draws down real balances that belong to a different order's untouched escrow, or reverts entirely, effectively locking/losing funds. This matches the bounty's "stealing or loss of funds" and "order escrow ... must move exactly once and only to the rightful beneficiary and amount" pivot, and requires no relayer/prover/admin compromise — only an unprivileged `placeOrder` call.

### Likelihood Explanation
Likelihood is medium-to-high: it requires only that the input token used exhibits fee-on-transfer/deflationary/rounding behavior (a known category on Tron-style TRC-20 deployments and even mainstream tokens like `stETH`), and no special privilege, timing, or collusion. Any user placing an order with such a token — accidentally or deliberately — triggers the ledger inflation.

### Recommendation
Mirror the fix already present in the primary EVM `IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` in the non-predispatch path, use the measured delta (not the requested `order.inputs[i].amount`) as the basis for `reducedInputs` and the value credited into `_orders[commitment][token]`, and apply the same received-amount discipline to the predispatch/dispatcher sweep path.

### Proof of Concept
1. Deploy/select a fee-on-transfer TRC-20 token (e.g. taking 1% on transfer) as an input asset.
2. Call `placeOrder` with `order.inputs[0].amount = 1000` for that token, no predispatch.
3. `safeTransferFrom(msg.sender, address(this), 1000)` moves only ~990 tokens into the contract (fee-on-transfer), but `_orders[commitment][token] += reducedInputs[0].amount` credits based on `1000` (minus only the protocol fee, not the transfer-fee loss).
4. The escrow ledger for this commitment now claims more tokens than the contract's real balance increase for this specific deposit.
5. When this or another order sharing the same token pool calls `RedeemEscrow`/`RefundEscrow`, `withdraw()` transfers out the inflated ledger amount, drawing on balances that belong to other orders, causing a shortfall/failed withdrawal for whichever order settles last.
