## Title
Silent, unconfirmed rewrite of a repository's git remote URL from an unauthenticated/unverified GitHub API field — ([File: app/src/lib/stores/updates/update-remote-url.ts](app/src/lib/stores/updates/update-remote-url.ts))

### Summary
The external report's broken invariant is: two independently-sourced values (Redstone price / Chainlink price) are combined and trusted without verifying they represent the *same, currently-valid state* — allowing a stale/attacker-influenced value to silently corrupt a downstream decision (collateral valuation) without the user's awareness.

The Desktop analog is `updateRemoteUrl()`, which combines the *locally configured* git remote URL with a `clone_url` field taken from a `GitHubRepository`/`IAPIRepository` object returned by the GitHub API, and — if a loose string-based heuristic matches — silently overwrites the user's local `origin` remote with whatever URL the API reports, with no user confirmation and no verification that the new URL still refers to the same underlying repository identity (e.g. repository ID).

### Finding Description
`updateRemoteUrl` in [1](#0-0)  takes an `apiRepo: IAPIRepository` (an attacker-influenceable GitHub API object — its `clone_url` reflects whatever the GitHub API currently returns for that repository, which can change due to a rename/transfer performed by any user with write access to that repo) and compares it to the locally stored remote using only string/heuristic matching:

- `urlMatchesRemote` (used transitively via `urlMatchesRemote`/`repositoryMatchesRemote` in [2](#0-1) ) only compares parsed `hostname`, `owner`, and `name` strings — there is no repository identity check (no repo ID, no owner-account continuity check).
- `updateRemoteUrl` further only checks that: the URL protocol hasn't changed, and that the *previous* known GitHub clone URL still matches the current local remote (`remoteUrlUnchanged`) — see [3](#0-2) .
- If those loose conditions hold, it calls `gitStore.setRemoteURL(...)` and rewrites `origin` to the new `clone_url` returned by the API — without any user prompt or confirmation, and without validating that the "new" repository is actually a continuation of the "old" one (e.g., same numeric GitHub repo id).

This mirrors the oracle bug's structure exactly: two values from different trust boundaries (local git state vs. remote API state) are combined and one is allowed to silently override the other, using only superficial consistency checks (URL string shape / protocol) rather than a strong identity/freshness guarantee (in the oracle case: timestamp; here: repository ID).

### Impact Explanation
Because the rewrite is silent (no user prompt, confirmed only by unit tests in [4](#0-3) ), a rename/transfer of the tracked GitHub repository — which does not require any local/physical access to the victim's machine, only write access to the repo on GitHub.com/GHE — causes GitHub Desktop to automatically retarget the local `origin` remote URL for future fetches/pushes. If an attacker can cause the API to report a `clone_url` pointing at a repository they control (e.g., by obtaining collaborator/rename rights, or by name-squatting a renamed-away repository name that GitHub's redirect resolves the old identifier to), subsequent `git push`/`git fetch` performed unknowingly by the victim through Desktop's UI would silently be directed at the attacker's repository — a case of "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes.

### Likelihood Explanation
Moderate: this requires an external actor to have some write/administration capability over the GitHub-side repository (rename/transfer), which is a normal, unprivileged GitHub-side action, not local/physical machine access, not leaked credentials, and not social engineering of the Desktop user themselves. The victim does nothing more than continue normal usage (Desktop periodically refreshes `GitHubRepository` metadata and calls `updateRemoteUrl`), matching the "unpromted unnatural user steps" exclusion criteria negatively (i.e., no unnatural steps required). The main mitigating factor is `remoteUrlUnchanged`, which requires the local remote to still match the *previously cached* GitHub clone URL — so a user who has manually customized their remote is safe, but any user relying on the default/auto-managed remote is exposed.

### Recommendation
Before silently rewriting the local `origin` remote, verify a strong identity linkage between the old and new API repository objects (e.g., persisted numeric GitHub repository ID) rather than relying solely on best-effort URL string matching, and/or surface a user-facing confirmation before altering `origin`'s URL, especially when the owner/name portion of the URL changes to a different account than previously observed.

### Proof of Concept
1. User clones `https://github.com/victim-org/repo.git` into Desktop; `origin` is set to that URL and `GitHubRepository.cloneURL` is cached with the same value.
2. Attacker (a collaborator with rename rights, or the repo owner/account being compromised via GitHub-side means unrelated to the Desktop app) renames the repo, or transfers it, such that the API now reports `clone_url: https://github.com/victim-org/renamed-or-transferred-repo.git` (or an equivalent hostname/owner/name combination the attacker controls, e.g. via name squatting after a rename-away).
3. On its next repository metadata refresh, Desktop calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` per [1](#0-0) . Since `protocolsMatch` is true and `remoteUrlUnchanged` is true (user hasn't customized origin) and `urlsMatch` is false (URL changed), the guard at line 42 fires and `gitStore.setRemoteURL('origin', updatedRemoteUrl)` executes — exactly as demonstrated by the existing test "updates the repository's remote url when the github url changes" in [4](#0-3) .
4. The user's next `git push`/`git fetch` in Desktop silently targets the attacker-influenced URL, with no dialog or warning shown.

Note: I was unable to fully trace the exact call site and refresh cadence of `updateRemoteUrl` from `app-store.ts` (the read of that file was truncated to a single import line before iterations ran out), so I cannot confirm additional guard conditions (e.g., account/session checks) that might exist at the call site beyond what's tested in `update-remote-url-test.ts`. This should be verified with a full read of `app-store.ts` around its 3 references to `updateRemoteUrl`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

  it("updates the repository's remote url when the github url changes", async t => {
    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }
    await updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)
    assert.notEqual(originalUrl, updatedUrl)
    assert.equal(gitStore.currentRemote.url, updatedUrl)
  })
