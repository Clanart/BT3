### Title
PedPoP emits a blame proof revealing the ECDH shared key before the message's proof-of-possession is verified — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Severity: Medium-High. Analog of the `export_dmabuf()` UAF class: a "reference" (the per-message ECDH shared key, packaged as a published `EncryptionKeyProof`) is installed/emitted into an error returned to the world **before** the validity check that must precede it (the per-message Schnorr proof-of-possession) has run — the exact "failure exit with the file already created / object exposed before setup finished" pattern fixed in the kernel advisory.

In `KeyMachine::calculate_share`, each incoming `EncryptedMessage` is passed to `Encryption::decrypt`, which *queues* the PoP signature into a `BatchVerifier` but immediately computes `ecdh(enc_key, msg.key)`, applies the keystream, and constructs an `EncryptionKeyProof` revealing that shared key — all before the queued PoP is verified [1](#0-0) . Back in `calculate_share`, if the decrypted bytes are not a canonical scalar, the function returns `PedPoPError::InvalidShare { blame: Some(blame) }` immediately — the batch verification that would catch an invalid PoP is never executed [2](#0-1) .

### Finding Description
The protocol's own comments document the attack this ordering enables: if Eve observes Alice encrypt to Bob with per-message key `X` and then sends Bob a message also claiming key `X`, a blame statement revealing `bX` (Bob's encryption private key times `X`) would reveal Alice's message to Bob — "a massive side effect" [3](#0-2) . The per-message `pop` Schnorr signature exists precisely to prove the sender knows the discrete log of `msg.key`, and `decrypt` deliberately uses a distinct batch ID (`BatchId::Decryption`) so that a PoP failure maps to `blame: None` [4](#0-3) . That protection is bypassed: the `from_repr` early-return at line 480–482 fires before `batch.verify_with_vartime_blame()` at line 493, so the `EncryptionKeyProof` containing `bX` is returned in the error even though Eve's PoP over `X` is invalid. When `blame_vartime` *does* run, it returns the lowest-index failing statement, and `Decryption(l)` is queued before `Share(l)`, so the intended `None` outcome only holds when verification is reached [5](#0-4) . The processor then broadcasts this blame (`ProcessorMessage::InvalidShare { blame }`) to all validators for `AdditionalBlameMachine`/`VerifyBlame` adjudication [6](#0-5)  — the equivalent of the fd being in the descriptor table before setup completes.

### Impact Explanation
The published `EncryptionKeyProof { key: bX, dleq }` lets every observer decrypt the *honest* message Alice sent to Bob under the same per-message key `X`, since `cipher()` derives the ChaCha20 keystream solely from the context and the shared ECDH point [7](#0-6) . That leaks Alice's Pedersen secret share intended for Bob (`SecretShare<C::F>`), a secret protocol value whose disclosure the PoP mechanism was specifically designed to prevent. Deeper compromise (e.g., collusion or repeated attacks across messages) can escalate toward key-share recovery.

### Likelihood Explanation
The attacker is a single DKG participant (no collusion, no broken BFT) sending one crafted `EncryptedMessage` over the normal share channel — bytes fed to `EncryptedMessage::read`/`calculate_share`, an explicitly in-scope surface. They copy an honest participant's `msg.key` `X`, attach a (necessarily invalid) PoP, and choose any ciphertext. The decrypted plaintext is deterministic garbage under keystream `ks(bX)`; it is non-canonical (`from_repr` fails) with probability ≈ 1 − l/2^256 ≈ 94% for Ristretto/Ed25519-order scalars, and the attacker can retry with different ciphertexts across attempts. Note the attacker cannot target the plaintext but only needs *non*-canonical bytes, which is the overwhelmingly likely case.

### Recommendation
Restructure as the kernel fix did — verify before exposing: in `calculate_share`, do not attach a blame proof from `decrypt` until the `BatchVerifier` has confirmed that participant's PoP. Concretely, either (a) verify each message's PoP before decrypting (e.g., a `verify_pop` step ahead of `decrypt`, or making `decrypt` return the proof only on request), or (b) defer building `blames` entries and re-derive the `EncryptionKeyProof` only after `batch.verify_with_vartime_blame()` confirms the `Decryption` statement passed — mirroring "do `fd_install()` only when everything had been set up."

### Proof of Concept
1. Run PedPoP with n participants; attacker Eve is participant `l`, Bob an honest recipient, Alice another honest participant.
2. Alice sends Bob `EncryptedMessage { key: X, pop: sig_X, msg: C_A }` — Eve records `X` (public on the authenticated channel).
3. Eve sends Bob `EncryptedMessage { key: X, pop: <arbitrary bytes parsed as SchnorrSignature>, msg: <arbitrary ciphertext> }`.
4. Bob calls `machine.calculate_share(rng, shares)`. `decrypt` queues the (failing) PoP, computes `bX`, decrypts to garbage, and returns `EncryptionKeyProof{key: bX, dleq}`.
5. With ~94% probability `C::F::from_repr` fails → `calculate_share` returns `InvalidShare { participant: l, blame: Some(proof) }` without ever verifying the PoP.
6. The processor broadcasts the blame; any observer applies `cipher(context, bX)` to `C_A` and recovers Alice's share to Bob — exactly the side effect `encryption.rs` lines 84–90 warn the PoP exists to prevent.

```rust
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
```
