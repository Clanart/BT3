### Title
Untrusted `ThresholdKeys` encoding triggers quadratic verification-share interpolation DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

`ThresholdKeys::read` accepts attacker-supplied `t` and `n` values up to `u16::MAX`, then `ThresholdKeys::new` computes the group key by evaluating each of the first `t` participants’ interpolation factors. Every Lagrange factor iterates over all `t` participants, resulting in `O(t²)` field arithmetic after only a linear-size input is parsed. With `t = n = 65_535`, a roughly 2 MiB serialized Ristretto key forces approximately 4.3 billion inner-loop iterations, causing prolonged unavailability.

### Finding Description

`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from the input, reads either `n` constant coefficients or `n` verification shares, and only then invokes `ThresholdKeys::new` for validation. [1](#0-0) 

For `Interpolation::Lagrange`, `interpolation_factor` loops over the complete included-participant list for each participant. [2](#0-1)  `ThresholdKeys::new` invokes it once for every participant in `1..=t`, making group-key reconstruction quadratic in `t`. [3](#0-2) 

The vulnerable sequence is:

```text
ThresholdKeys::read
  -> attacker-controlled t, n
  -> read n verification shares
  -> ThresholdKeys::new
     -> for each of t participants:
        -> interpolation_factor loops over t participants
```

### Impact Explanation

An unprivileged party able to submit serialized `ThresholdKeys` bytes can make the host perform billions of field operations. For `t = n = 65_535`, the input requires only `65_535` valid point encodings—about 2 MiB for 32-byte group encodings—while reconstruction performs approximately `65_535²` participant-loop iterations. Repeated requests can exhaust CPU capacity and prevent legitimate signing or wallet operations.

This is analogous to the NATS issue’s amplification flaw: a bounded input format causes work in a secondary derived structure whose cost is not independently bounded.

### Likelihood Explanation

The attack requires an application to deserialize attacker-controlled bytes through `ThresholdKeys::read`; that API accepts an arbitrary `io::Read` without an intrinsic protocol limit. [4](#0-3)  The triggering input consists only of well-formed scalar and group encodings plus a declared Lagrange threshold of `u16::MAX`.

The resource bound is technically present because `n` is a `u16`, but that bound permits the maximum computationally expensive case rather than a practical deployment limit.

### Recommendation

- Validate `ThresholdParams::new(t, n, i)` immediately after reading `t`, `n`, and `i`, before allocation or bulk deserialization.
- Enforce a protocol-appropriate maximum participant count before accepting serialized keys.
- Replace the repeated `interpolation_factor` calculation with a linear-time Lagrange-coefficient construction using prefix and suffix products.
- Prefer `Vec::with_capacity` only after validating declared sizes, and consider rejecting serializations larger than the expected size for the configured threshold parameters.

### Proof of Concept

The following byte construction exercises the vulnerable path using `Secp256k1` or another supported `Curve` whose `ID`, scalar encoding, and generator encoding are available:

```rust
use frost::{
  curve::{Curve, Secp256k1},
  dkg::ThresholdKeys,
};
use ciphersuite::group::GroupEncoding;

fn malicious_threshold_keys() -> Vec<u8> {
  let mut bytes = Vec::new();

  // Curve identifier.
  bytes.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
  bytes.extend(Secp256k1::ID);

  // t = 65_535, n = 65_535, i = 1.
  bytes.extend(u16::MAX.to_le_bytes());
  bytes.extend(u16::MAX.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());

  // Lagrange interpolation.
  bytes.push(1);

  // A canonical secret-share scalar. Zero is sufficient to reach parsing.
  bytes.extend(Secp256k1::F::ZERO.to_repr().as_ref());

  // 65_535 valid verification shares. They may all encode the generator.
  let generator = Secp256k1::generator().to_bytes();
  for _ in 0 .. u16::MAX {
    bytes.extend(generator.as_ref());
  }

  bytes
}

let bytes = malicious_threshold_keys();
let _ = ThresholdKeys::<Secp256k1>::read(&mut bytes.as_slice());
```

Parsing itself completes after linear input processing, but `ThresholdKeys::new` then evaluates `65_535` interpolation factors, each scanning all `65_535` included participants.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
