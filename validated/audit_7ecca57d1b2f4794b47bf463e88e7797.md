## Finding

### Title
Forced feeToken refund transfer in `EvmHost.dispatchTimeOut` reverts and permanently un-rolls the timeout, locking escrowed funds if the original payer is blacklisted by the fee token - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchTimeOut` (both the GET and POST variants) deletes the request's commitment record, invokes the destination module's timeout hook, and then unconditionally pushes a forced ERC-20 `safeTransfer` refund of the original relayer fee back to `meta.sender` — the address that paid the fee at dispatch time. Because Hyperbridge's `feeToken` is explicitly documented as swappable to any stablecoin (e.g. USDC), and USDC enforces a transfer blacklist, a blacklisted `meta.sender` causes the refund `safeTransfer` to revert. Since this call is not wrapped in a try/catch, the revert propagates and rolls back the *entire* `dispatchTimeOut` transaction — including the earlier deletion of `_requestCommitments[commitment]` and any state changes the destination module made inside its `onGetTimeout`/`onPostRequestTimeout` hook (e.g., releasing escrowed principal to the user). The request is left permanently un-timed-out and unrecoverable, since `meta.sender` is fixed at dispatch time and cannot be changed on any subsequent retry.

### Finding Description
`dispatch(DispatchPost)` records `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` at request creation time [1](#0-0) . `post.payer` is caller-supplied and immutable once set.

When the request times out, the handler calls `dispatchTimeOut`, which:
1. Deletes `_requestCommitments[commitment]` for replay protection.
2. Calls the destination module's `onPostRequestTimeout`/`onGetTimeout`.
3. If that call succeeds, unconditionally refunds the fee to `meta.sender` via `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`. [2](#0-1) 

The same unconditional-push pattern exists for the GET-request timeout path [3](#0-2)  and for the GET-response relayer reward path [4](#0-3) .

`feeToken` is explicitly configurable to any ERC-20, "typically DAI... but we allow it to be configurable to prevent future regrets" [5](#0-4) , and Hyperbridge's own paymaster/bandwidth infrastructure treats USDC as a first-class fee token elsewhere in the codebase (e.g. `SimplexPaymaster`, Circle paymaster provider), confirming USDC-class blacklistable tokens are in scope as `feeToken`.

There is no try/catch around the `safeTransfer` calls in any of these three functions — a revert in the transfer bubbles up and reverts the whole external call. Because `dispatchTimeOut` deletes the commitment *before* calling into the destination module and only refunds *after*, a revert on the refund rolls back both the commitment deletion and the destination module's timeout-handling state changes (e.g. escrow release), restoring the pre-call state exactly as if the timeout call never happened — while consuming the handler's gas and leaving the request permanently stuck, since `meta.sender` cannot be updated and every future retry hits the same reverting transfer.

### Impact Explanation
This is a High-impact fund-lock / denial-of-settlement bug: once the original request payer is blacklisted by the (governance-chosen) fee token, any request whose fee was paid by that address can never complete its timeout path. Both:
- the protocol-level replay-protection deletion (`_requestCommitments`), and
- the application-level side effects normally triggered inside `onPostRequestTimeout`/`onGetTimeout` (refunding escrowed principal, unlocking bridged assets, etc.)

are permanently blocked, because the revert is unconditional and irreversible for that commitment. This mirrors the reported bug class exactly: a forced token push to a potentially blacklisted party blocks an otherwise-valid state transition and locks funds/state forever, with no internal-balance/claim-based fallback.

### Likelihood Explanation
Likelihood is Low-to-Medium, matching the referenced report's own "Low" likelihood rating for blacklist events: a payer must be blacklisted by whatever ERC-20 governance has configured as `feeToken` (explicitly documented as swappable, e.g. USDC-class assets). No malicious relayer, prover, or admin action is required — an ordinary user who becomes blacklisted by the stablecoin issuer for unrelated reasons (compliance action, sanctions, etc.) is sufficient to trigger a permanent, unrecoverable state lock for any of their pending cross-chain requests.

### Recommendation
Decouple the fee refund/reward from the state-mutating timeout path:
- Perform the commitment deletion and destination-module timeout callback first, and record the refund amount into a per-account claimable balance (`mapping(address => uint256) pendingFeeRefunds`) instead of pushing the transfer inline.
- Add a separate, permissionless `claimFeeRefund()`/`claimRelayerReward()` entry point that performs the actual ERC-20 transfer, so a reverting transfer only blocks that specific claim and never rolls back the underlying request-timeout/settlement state.
- Alternatively wrap the `safeTransfer` calls in a low-level `call` with a `try/catch`-equivalent pattern (or OZ's `Address.functionCall` in a try/catch) and, on failure, credit an internal claimable balance rather than reverting the whole `dispatchTimeOut`/`dispatchIncoming` transaction.

### Proof of Concept
1. Governance configures `feeToken` to a blacklist-capable stablecoin (e.g., USDC), permitted per `updateHostParams` since `feeToken` is fully configurable [6](#0-5) .
2. Alice dispatches a `PostRequest` via `dispatch(DispatchPost)`, setting `post.payer = Alice`, `post.fee > 0`; `_requestCommitments[commitment] = FeeMetadata({sender: Alice, fee: X})` is recorded [1](#0-0) .
3. Before the request is delivered, USDC's issuer blacklists Alice's address (independent, real-world event).
4. The request times out; a relayer submits the timeout proof, triggering `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)`.
5. `_requestCommitments[commitment]` is deleted; the destination module's `onPostRequestTimeout` succeeds and releases escrowed funds/updates its own state.
6. `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts because `meta.sender` (Alice) is blacklisted.
7. The revert unwinds the entire `dispatchTimeOut` call: `_requestCommitments[commitment]` is restored to its pre-call value, and the destination module's timeout-side-effects are rolled back too.
8. Every subsequent retry of `dispatchTimeOut` for this exact commitment repeats steps 5–7 identically since `meta.sender` never changes — the request can never be timed out and any escrow tied to it is permanently stuck.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
