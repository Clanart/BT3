## Analysis

The reported bug is: **an accounting layer marks a value as "spent"/available based on an optimistic calculation, without confirming that the underlying resource was actually settled — allowing the ledger to diverge from real, irrecoverable state.** In Elfi's case, `availableLiquidity` was decremented without ever checking whether the destination action (unrealized shorts payout) would actually succeed.

The closest local analog in Hyperbridge is in `pallet-ismp-relayer`'s fee-withdrawal flow.

### Title
Relayer fee balance is zeroed on dispatch, not on settlement, permanently destroying the claim if the destination-side payout fails - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in [1](#0-0)  zeroes the relayer's `Fees` entry on Hyperbridge immediately after *dispatching* an ISMP POST request that instructs the destination chain to pay out `available_amount`, rather than after the destination-side transfer actually succeeds. Because these withdrawal messages are dispatched with `timeout: 0` (non-timeouting, mirroring the same pattern documented in `pallet-bandwidth`, see [2](#0-1) ), there is no recovery path if delivery reverts on the destination chain.

### Finding Description
The withdrawal flow is:
1. `Fees::<T>::get(dest_chain, address)` reads the accumulated, provable balance.
2. The pallet dispatches a `DispatchPost` to the destination's `HostManager` (EVM) or the substrate `HYPERBRIDGE_MODULE_ID`, encoding `WithdrawalParams{ beneficiary_address, amount: available_amount, token }`.
3. Immediately after the dispatch call returns (i.e., the message is only *enqueued*, not delivered/executed), `Fees::<T>::insert(dest_chain, address, U256::zero())` unconditionally wipes the balance: [3](#0-2) .

On the EVM side, the actual transfer happens later, when a relayer delivers the message and `HostManager.onAccept` calls `IHostManager(host).withdraw(withdrawParams)`, which does a plain `IERC20.safeTransfer` / native `.call{value}` — reverting on insufficient balance: [4](#0-3)  and [5](#0-4) . This is confirmed directly by the test `test_host_manager_insufficient_balance`, which shows the call reverting on a low host balance: [6](#0-5) .

The host's fee-token balance that backs these relayer payouts is **not reserved or ring-fenced** — it is the same pool governance drains via `EvmHost.withdraw` for host revenue (identical function, same balance, same `restrict(hostManager)` gate) and the same balance other in-flight `WithdrawalParams`/outbound consensus/request rewards compete for: [7](#0-6) . There is no check anywhere in `pallet-ismp-relayer::withdraw` that the destination chain's fee-token balance is sufficient to cover `available_amount` *before* the Hyperbridge-side ledger entry is destroyed — directly mirroring the LP pool's failure to account for pending/unrealized obligations before letting `availableLiquidity` be spent.

Since the dispatch uses `timeout: 0`, there is no timeout-triggered refund path to restore the `Fees` entry if the destination-side call reverts (delivery simply fails as a reverted transaction on the destination chain, and the relayer who paid gas for delivery gets nothing back either).

### Impact Explanation
If the destination chain's fee-token balance is insufficient at the time of delivery (e.g., depleted by concurrent governance host-revenue withdrawals, other relayers' payouts, or a fee-token migration under `updateHostParams` requiring the old balance to be drained first — see `CannotChangeFeeToken` check in `EvmHost.sol`), the relayer's on-chain `withdraw()` call already zeroed their Hyperbridge `Fees` balance. The destination-side transfer then reverts, and the relayer's earned reward is **permanently and irrecoverably lost** — no retry, no re-accumulation (the underlying request commitments were already marked `claimed` during `accumulate`), and no timeout refund. This is a direct loss-of-funds bug against the relayer, the exact class the bounty gate accepts ("stealing or loss of funds ... relayer rewards must move exactly once and only to the rightful beneficiary and amount").

### Likelihood Explanation
This requires no malicious actor, relayer collusion, or governance compromise — only an ordinary race between a legitimate relayer withdrawal and any other legitimate consumer of the same destination-chain balance (host revenue sweep, another relayer's larger withdrawal, or a chain simply not yet funded with enough fee token at delivery time). Given relayer withdrawals are permissionless, frequent, and automated (see `tesseract/messaging/relayer/src/fees.rs` withdrawal loop), and host balances are actively drained by governance `withdraw`/`dispatch_withdraw` flows on the same token, this is a realistically reachable condition rather than a contrived edge case.

### Recommendation
Do not zero (or debit) the `Fees` entry at dispatch time. Instead:
- Either zero the balance only after receiving a delivery/settlement confirmation callback (e.g., via response or explicit ack) from the destination chain, or
- Reserve/escrow the destination-side balance for outstanding relayer claims (mirroring `pallet-bandwidth`'s pattern of atomic check-and-deduct with no mutation on insufficiency), and add a pre-dispatch sanity check against a tracked "reserved for relayers" amount so governance withdrawals and other consumers cannot starve pending relayer payouts.
- Alternatively, set a non-zero timeout on the withdrawal `DispatchPost` and re-credit `Fees` in `on_timeout` if delivery fails, giving the relayer a recovery path.

### Proof of Concept
1. Relayer accrues `Fees[dest_chain][relayer] = X` via `accumulate_fees` (backed by real escrowed fee tokens on `dest_chain`, per `RequestCommitments`).
2. Governance (or another large relayer withdrawal, or a fee-token migration) drains `dest_chain`'s `EvmHost` fee-token balance below `X` via `EvmHost.withdraw` / `dispatch_withdraw`, an entirely independent code path sharing the same balance: [4](#0-3) .
3. Relayer calls `withdraw_fees` on Hyperbridge. `Pallet::withdraw` dispatches the ISMP POST and immediately zeroes `Fees[dest_chain][relayer]`: [3](#0-2) .
4. The message is delivered to `HostManager.onAccept` → `EvmHost.withdraw` → `safeTransfer` reverts (insufficient balance), exactly as exercised in `test_host_manager_insufficient_balance`: [6](#0-5) .
5. Because `timeout: 0`, there is no automatic on-chain path to restore `Fees[dest_chain][relayer]` on Hyperbridge. The relayer's `X` tokens are gone: never paid out, and the claim to them destroyed at step 3.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
