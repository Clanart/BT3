### Title
OP_RETURN data is omitted from fee calculation, enabling non-relayable signed transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts up to 80 bytes of caller-controlled `data` and appends it as an `OP_RETURN` transaction output, but `calculate_weight_vbytes` receives only `payments` and `change`, not the serialized data output. [1](#0-0) [2](#0-1) 

### Finding Description
The transaction used for weight estimation is built only from the payment outputs and an optional change output. [3](#0-2)  The real transaction may contain an additional serialized `OP_RETURN` output of up to roughly 92 bytes, but `needed_fee` is calculated from the smaller estimated vsize. [4](#0-3) 

The minimum-relay check uses this underestimated `vbytes`, so `fee_per_vbyte = 1` passes whenever `needed_fee` equals the underestimated vsize. [5](#0-4)  If the input amount equals `payment + needed_fee`, or change is calculated from `fee_with_change`, the completed transaction pays only the underestimated fee. [6](#0-5) 

### Impact Explanation
An unprivileged party supplying transaction data to be signed can cause the wallet to produce a validly signed transaction whose actual fee rate is below both the requested rate and Bitcoin Core's default minimum relay rate. The resulting transaction can be rejected from the mempool, preventing the intended payment and change output from becoming spendable on-chain and requiring a new signing operation. This is analogous to using a present or modeled balance incorrectly instead of accounting for the full resource required by the real object.

### Likelihood Explanation
The issue is deterministic whenever `data` is non-empty, because the data output is always included in `tx_outs` and always omitted from `calculate_weight_vbytes`. [2](#0-1)  The strongest case occurs at the lowest accepted fee rate, where an 80-byte `OP_RETURN` adds approximately 92 serialized bytes while the fee remains based on the smaller transaction. [7](#0-6) [8](#0-7) 

### Recommendation
Include the actual `OP_RETURN` `TxOut` in the transaction passed to `calculate_weight_vbytes`, or pass the serialized data output separately so it is included in both the requested-fee calculation and the minimum-relay check. The maximum-standard-weight check should also use the final transaction shape, including the data output. [9](#0-8) 

### Proof of Concept
Construct one mature input, one payment, and an 80-byte `data` payload:

```rust
let tx = SignableTransaction::new(
  vec![input],              // input.value == payment + underestimated_fee
  &[(payment_script, payment)],
  None,
  Some(vec![0; 80]),
  1,                        // one sat/vbyte
).unwrap();
```

The constructor adds the 80-byte payload as an `OP_RETURN` output before calculating weight. [10](#0-9)  Nevertheless, the estimator is invoked with only the payment list and no data output. [11](#0-10) 

If the estimated transaction is 112 vbytes, `needed_fee` is 112 sats and the minimum-relay check compares it against approximately 112 sats, not the approximately 204 sats required by the final transaction after the added 92-byte output. [8](#0-7)  Since the input equals `payment + 112`, the signed transaction's actual fee is only 112 sats and its actual fee density is approximately 0.55 sats/vbyte, causing default-policy nodes to reject it. [12](#0-11)
