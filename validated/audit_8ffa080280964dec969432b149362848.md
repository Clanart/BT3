### Title
Cached MuSig preprocess (deterministic nonce seed) is not bound to the message or participant set, enabling nonce reuse across distinct `set_keys_message` payloads - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The reported bug class is a registry that stores a pointer under an ID without verifying the stored object actually refers back to the registry's own context, so later lookups silently resolve to the wrong entity. In `signing_protocol.rs`, `CachedPreprocesses` is exactly such a registry: it persists a deterministic FROST preprocess seed keyed only by `context = (b"DkgConfirmer", attempt)` [1](#0-0) [2](#0-1) . The cached entry is never checked against the participant set, the `removed` list, or the `KeyPair` actually being signed — the analog of a `controller` whose `vaultFactory` field points elsewhere. When `share`/`complete` is later invoked for the same `attempt` with a different `KeyPair` or a changed `removed` set, the lookup returns a preprocess minted for a different signing context, and the same nonce is used to sign a different message.

### Finding Description
`preprocess_internal` derives a preprocess once per `context` and caches only the 32-byte seed (XOR-masked with a key derived from `context` and the validator's private key) [3](#0-2) . On every subsequent call for the same context, `from_cache` deterministically reconstructs the identical nonce commitments [4](#0-3) . The file header explicitly acknowledges this fixed-nonce design and states safety depends on the message and received preprocesses being finalized and unique per context [5](#0-4) .

However, the message is not part of the context. `share_internal` builds `msg` from `set_keys_message(set, removed, key_pair)`, where `key_pair` is a caller-supplied argument and `removed` is resolved at `DkgConfirmer::new` time via `removed_as_of_dkg_attempt` [6](#0-5) [7](#0-6) . Nothing verifies that the `key_pair`/`removed`/participant set used in a later `share` or `complete` call matches whatever was implied when the preprocess seed was first cached — the missing back-reference check, directly analogous to the missing `controller.vaultFactory == this` check. The code even contains an unimplemented TODO to verify the on-chain preprocess matches the presumed one before publishing shares [8](#0-7) .

Additionally, `threshold_i_map_to_keys_and_musig_i_map` re-indexes externally supplied preprocesses/shares: it sorts by threshold `Participant` index, then remaps entries to sequential MuSig indices `1..=n` by position [9](#0-8) . If the `removed` set differs between the call that cached the preprocess and the call that consumes it, the same nonce seed is combined with a differently-ordered participant list, changing the MuSig binding factors and aggregate nonce while our own nonce stays fixed — another path where the stored entry is bound to the wrong context.

### Impact Explanation
If a share is produced under the same cached nonce for two distinct `set_keys_message` payloads (different `key_pair` or different `removed` set for the same `attempt`), this is Schnorr/MuSig nonce reuse: two public shares `s = k + e·x` and `s' = k + e'·x` allow any observer to solve for the validator's MuSig private key share, and the module itself notes recovery of the cached preprocess enables private-key recovery [10](#0-9) . Since these are the validators' root-of-trust keys used for DKG confirmation, compromise is High-severity in effect; even absent full key recovery, emitting a share for a context the preprocess wasn't bound to produces a signature on an unintended message. Because the trigger requires a coordinator-initiated second signing pass under the same attempt with divergent parameters rather than a purely attacker-controlled input, and BFT finality is assumed to normally prevent divergence (the file documents the residual reorganization/rebuild edge cases) [11](#0-10) , this lands as Medium.

### Likelihood Explanation
The seed reuse is deterministic and guaranteed whenever the code path executes twice for the same `(b"DkgConfirmer", attempt)` context — `CachedPreprocesses::get` returns the prior seed unconditionally [12](#0-11) . Divergence requires the message or participant set to differ across calls, which the authors anticipated enough to write the safety argument and the unimplemented preprocess-verification TODO [8](#0-7) . The documented reorganization/rebuild path and any retry where `removed` or `key_pair` changes mid-attempt leave the binding unverified. One caveat I could not fully verify within the available context: whether the coordinator message flow can in practice present two distinct `key_pair` values for the same attempt; the missing check means correctness relies entirely on that never happening.

### Recommendation
Bind the cached preprocess to everything it will sign for. Include the `key_pair`, the `removed` set, and the participant list (or their hash) in the `CachedPreprocesses` key/context, and/or implement the existing TODO: before publishing a share, verify on-chain that the preprocess commitments and message match what the cached seed was created for [8](#0-7) . This is the analog of checking `controller.vaultFactory == address(this)` before re-pointing vaults.

### Proof of Concept
1. `DkgConfirmer::new` for attempt `a` with `removed = R0` constructs context `(b"DkgConfirmer", a)`; `preprocess()` caches seed `s` and publishes nonce commitments `N` [13](#0-12) [14](#0-13) .
2. `share(preprocesses, key_pair_A)` signs `set_keys_message(set, R0, key_pair_A)` using nonce derived from `s`, emitting share `σ_A` [15](#0-14) .
3. A second invocation for the same attempt — after `removed_as_of_dkg_attempt` returns `R1 ≠ R0`, or with `key_pair_B ≠ key_pair_A` — hits the same cache entry, regenerates the identical nonce, and emits `σ_B` over a different message (and, if `removed` changed, a differently-ordered MuSig set via `threshold_i_map_to_keys_and_musig_i_map`) [9](#0-8) [16](#0-15) .
4. With both published shares and the two distinct challenges, an observer recovers the validator's MuSig private key share, matching the key-share-recovery consequence class the module itself warns about [5](#0-4) .
