## Finding: Argument injection via malicious branch name in `merge`/`mergeBranch` (missing `--` separator)

### Title
Git argument injection via attacker-controlled branch name starting with `-` in merge operation - (File: `app/src/lib/git/merge.ts`)

### Summary
The `merge()` function builds the `git merge` argv by pushing the raw branch name as the last positional argument, with no `--` separator to terminate option parsing. If a branch name obtained from a fetched remote (attacker-controlled) begins with `-` (e.g. `--no-ff`, `-Xtheirs`, `--strategy=ours`), git will interpret it as an option/flag rather than as a ref, silently changing the semantics of the merge the user thinks they're performing.

### Finding Description
`merge()` constructs the command as: [1](#0-0) 

```
const args = ['merge']
...
args.push(branch)
const { exitCode, stdout } = await git(args, repository.path, 'merge', {...})
```

`branch` here is `branch.name`, taken directly from a `Branch` model that is populated from fetched refs (e.g. a remote-tracking branch synced from an attacker-controlled remote), and passed through from `GitStore.merge` → `merge(repository, branch.name, ...)`: [2](#0-1) 

Unlike `merge.ts`, other git-invoking code paths in this codebase are careful to prevent a ref/path being misinterpreted as an option by appending a `--` end-of-options marker before the ref, e.g. `checkoutBranch`'s `getBranchCheckoutArgs`: [3](#0-2) 

and `checkoutPaths`/`checkoutConflictedFile` which always add `'--'` before the path/ref: [4](#0-3) 

`merge.ts` has no equivalent protection — `branch` is appended with no preceding `--`. There is also no branch-name sanitization applied to fetched remote branches before they reach `merge()`; `sanitizedRefName`/`testForInvalidChars` in `app/src/lib/sanitize-ref-name.ts` strip a leading `-` only when Desktop generates a *new* local branch name, not when a name from a fetched remote ref is later chosen for merging. [5](#0-4) 

Because git's ref-name validation (`check-ref-format`) does not forbid leading dashes, a remote can legitimately publish (and Desktop can fetch) a branch such as `refs/heads/--no-ff` or `refs/heads/-Xtheirs`. When the user selects that branch in the "Merge into current branch" dialog and confirms, `_mergeBranch` in `app-store.ts` calls `gitStore.merge(sourceBranch, ...)` with that branch: [6](#0-5) 

which ultimately runs `git merge --no-ff` (or `git merge -Xtheirs`, `git merge --strategy=ours`, etc.) instead of `git merge --no-ff -- <branch>`/`git merge -- --no-ff`. Git then treats the string purely as a flag, not as a ref to merge, so no merge of the intended branch happens (or a merge with attacker-chosen strategy/flags occurs) while the UI still reports it as a merge of "that branch."

### Impact Explanation
This allows an attacker who controls a remote (via a normal `git fetch`, no privileged access required) to make the "Merge branch" action silently do something other than what the user intends and sees in the UI:
- Corrupt the merge outcome (e.g. force `--strategy=ours`/`-Xtheirs`/`-Xours`, silently discarding the user's own changes or fabricating a merge that looks clean).
- Depending on which git option string collides, potentially alter merge strategy options that affect what gets committed and later pushed — i.e. silent corruption of what the user commits/pushes, one of the explicitly valid impact categories in scope.

### Likelihood Explanation
Requires only that the victim add/fetch an attacker-controlled remote (a normal, expected Desktop workflow) containing a branch literally named e.g. `--no-ff`, and then use the standard "Merge branch..." menu action to merge it. No local access, admin rights, or unnatural steps beyond normal repo/remote usage are needed.

### Recommendation
In `app/src/lib/git/merge.ts`, terminate options before the branch operand, mirroring the pattern already used in `checkout.ts`:
```ts
args.push('--', branch)
```
(or, if `merge.ts`'s prior flags require it, add `'--'` immediately before pushing `branch`). Apply the same audit to any other git subcommands invoked with a directly-attacker-influenced ref/branch name lacking a `--` separator.

### Proof of Concept
1. Create a remote repository with a branch literally named `--no-ff` (`git push origin HEAD:refs/heads/--no-ff`).
2. In GitHub Desktop, add/clone that remote and fetch.
3. On the target branch, invoke the "Merge into current branch" menu action and select the `--no-ff` branch as the branch to merge (this reaches `mergeBranch` → `_mergeBranch` → `GitStore.merge` → `merge()`).
4. Observe the constructed argv is `['merge', '--no-ff']` (no `--` and no positional ref), so git executes `git merge --no-ff` — with no source ref supplied — instead of merging the intended branch, demonstrating the argument-injection/corruption of intended merge behavior. [7](#0-6)
