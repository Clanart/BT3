### Title
Fee-rate integer overflow creates a transaction with an unintended fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` multiplies a caller-controlled `fee_per_vbyte` by the transaction’s virtual size using unchecked `u64` arithmetic. In release builds, a sufficiently large fee rate wraps modulo `2^64`, producing a small `needed_fee` that is then committed into the transaction’s change output and reported by `needed_fee()`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The function accepts `fee_per_vbyte: u64` without an upper bound. It calculates the initial fee as `fee_per_vbyte * vbytes`, and later calculates the change-inclusive fee as `fee_per_vbyte * vbytes_with_change`. [2](#0-1) [4](#0-3) 

For sufficiently large `fee_per_vbyte` values, these multiplications overflow. With ordinary release-mode arithmetic, the result wraps rather than producing an error. If the wrapped fee remains at least the minimum relay fee, it passes the `TooLowFee` check. [5](#0-4) 

When change is enabled, `input_sat - (payment_sat + fee_with_change)` is calculated using the wrapped `fee_with_change`. The resulting change output commits the transaction to the wrapped fee, not the requested fee, and `needed_fee` stores the same incorrect value. [3](#0-2) [6](#0-5) 

### Impact Explanation
The signing path can produce and sign a valid transaction whose effective fee differs from the fee requested by the transaction initiator. Because the fee is represented implicitly as inputs minus outputs, the oversized fee rate is replaced by the wrapped value when the change output is calculated. [7](#0-6) [3](#0-2) 

The resulting transaction is subsequently bound into Taproot sighashes and passed to the FROST signing machines. The threshold therefore signs a different economic transaction than requested: one paying the wrapped fee instead of the specified fee rate. [8](#0-7) 

### Likelihood Explanation
This is reachable when an application accepts a transaction fee rate as untrusted or externally influenced input and passes it directly to `SignableTransaction::new`. No malformed curve encoding, invalid key, validator compromise, or protocol collusion is required; the trigger is only a sufficiently large public `u64` fee-rate argument together with transaction parameters that keep the wrapped result above the minimum relay threshold. [1](#0-0) [5](#0-4) 

The practical impact is constrained because the attacker must control the fee-rate argument, and the wrapped result still has to satisfy the minimum-fee check. It also requires release-mode wrapping arithmetic rather than debug-mode panic behavior.

### Recommendation
Use checked arithmetic for every amount and fee calculation:

- Calculate fees with `checked_mul`.
- Calculate `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Sum payments and inputs with `checked_add` or `try_fold`.
- Return a new `TransactionError::FeeOverflow`/`AmountOverflow` variant instead of panicking or wrapping.
- Consider enforcing a protocol-defined maximum fee rate so absurd values are rejected independently of overflow behavior. [9](#0-8) [10](#0-9) 

### Proof of Concept
The vulnerable arithmetic is:

```rust
// networks/bitcoin/src/wallet/send.rs
let mut needed_fee = fee_per_vbyte * vbytes;

if needed_fee <
  ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000)
{
  Err(TransactionError::TooLowFee)?;
}

let fee_with_change = fee_per_vbyte * vbytes_with_change;
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
    needed_fee = fee_with_change;
  }
}
```

Choose a transaction whose change-inclusive virtual size is `vbytes = 200`. Since `2^64 mod 200 = 16`, choose:

```rust
let vbytes = 200;
let fee_per_vbyte = (u64::MAX / vbytes) + 3;
```

In release mode:

```text
fee_per_vbyte * 200
= (floor((2^64 - 1) / 200) + 3) * 200
≡ 584 (mod 2^64)
```

The constructed transaction therefore behaves as though the requested fee was `584` satoshis, rather than the supplied astronomical fee rate. `584` exceeds the approximate minimum relay requirement of `200` satoshis for a 200-vbyte transaction, so `TooLowFee` is not raised. The change calculation then subtracts only `584` satoshis plus the payments, and the generated transaction commits to that unintended fee. [11](#0-10)
