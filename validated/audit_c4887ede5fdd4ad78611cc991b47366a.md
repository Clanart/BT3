### Title
ERC20/WERC20 precompile `transfer`/`transferFrom` permits sending user tokens to the zero address, permanently locking funds - ([File: precompiles/erc20/tx.go])

### Summary
The external Aave finding is a "missing zero-address check before an outbound transfer" bug class: `claimToTreasury` moves funds to a configurable `treasuryVault` address without ever verifying it is not `address(0)`, which would silently and irreversibly burn/lock the funds. The Cosmos EVM analog is in the `x/erc20` ERC20 precompile's transfer path, which sends user-owned bank-backed tokens to an attacker/user-supplied `to` address without any zero-address (or otherwise-unspendable-address) validation.

### Finding Description
`Precompile.Transfer` and `Precompile.TransferFrom` in `precompiles/erc20/tx.go` take the destination address directly from call arguments (`ParseTransferArgs`/`ParseTransferFromArgs`) and forward it, unchecked, into a bank `MsgSend`: [1](#0-0) 

```go
func (p *Precompile) transfer(
	ctx sdk.Context, contract *vm.Contract, stateDB vm.StateDB,
	method *abi.Method, from, to common.Address, amount *big.Int,
) (data []byte, err error) {
	coins := sdk.Coins{{Denom: p.tokenPair.Denom, Amount: math.NewIntFromBigInt(amount)}}
	msg := banktypes.NewMsgSend(from.Bytes(), to.Bytes(), coins)
	...
	msgSrv := NewMsgServerImpl(p.BankKeeper)
	if err = msgSrv.Send(ctx, msg); err != nil { ... }
``` [2](#0-1) 

There is no check anywhere in this path that `to != common.Address{}` (the EVM zero address). Unlike the standard OpenZeppelin ERC20 `_transfer`/`_update` implementations bundled elsewhere in the repo, which explicitly `require(to != address(0), ...)` before moving value, this precompile relies purely on the Cosmos SDK bank module's `BlockedAddr` mechanism to reject disallowed recipients. That mechanism only blocks specific module accounts (e.g., `x/precisebank` module address is blocked as shown in `x/precisebank/keeper/send.go`), not the all-zero address. A no-op or benign transfer with `to = 0x0000000000000000000000000000000000000000` bech32-encodes to a valid but unspendable/unknown-key account address, so `bank.MsgSend` will succeed and permanently move the caller's or an approved owner's tokens to an address nobody controls.

This is directly analogous to the Aave bug: instead of an owner-configured `treasuryVault` defaulting to `address(0)`, here the recipient of a user-initiated `transfer`/`transferFrom` call can be set to the zero address by any unprivileged caller (or accidentally, by any wallet/dApp misconfiguration), and the funds are irrecoverably lost with no revert, matching the "prevent sending... to address(0)" recommendation from the source report.

### Impact Explanation
Any unprivileged EVM caller invoking the ERC20 precompile's `transfer(address(0), amount)` or `transferFrom(owner, address(0), amount)` (with sufficient allowance) can move native-bank-backed token balances into a permanently unspendable address. This is a direct, user-triggerable path to **permanent freezing/locking of user funds**, which is explicitly in the allowed Critical impact set ("permanent freezing, locking, theft, or unauthorized extraction of user funds ... across native balances, EVM balances, ERC20 representations ... token-pair-backed balances"). Because the ERC20 precompile represents native Cosmos SDK coin balances 1:1 as ERC20 tokens, this affects the underlying bank-module asset, not merely an isolated EVM-side state.

### Likelihood Explanation
High likelihood of triggering (any user can call `transfer`/`transferFrom` with `to = address(0)` directly or be tricked into doing so via a malicious dApp/contract), though it typically requires user error, a buggy integrating contract, or malicious front-end to actually cause the call — it is not something an attacker can force onto an unwilling victim's own balance without the victim's/approved spender's participation. This matches the same likelihood profile as the original Aave finding (owner misconfiguration/oversight leading to fund loss), scaled to any token holder using this Cosmos EVM precompile.

### Recommendation
Add an explicit zero-address (and, ideally, blocked-address) check in `precompiles/erc20/tx.go`'s shared `transfer` helper before constructing/sending the `MsgSend`, e.g.:
```go
if to == (common.Address{}) {
    return nil, errors.New("ERC20: transfer to the zero address")
}
```
Apply the same check to the WERC20 precompile paths and any other precompile/keeper flow (e.g., `x/erc20` `ConvertCoinNativeERC20`, `ConvertERC20`) that accepts an EVM address as a fund destination, mirroring the zero-address requirements already present in the bundled OpenZeppelin ERC20 reference contracts in this repo.

### Proof of Concept
1. Deploy/target an existing ERC20 precompile token pair (native coin ⇄ ERC20 precompile).
2. From an account holding balance of that denom, call the precompile's `transfer(address(0), amount)` via a contract or direct EVM call.
3. Observe: `p.transfer` builds `banktypes.NewMsgSend(from.Bytes(), common.Address{}.Bytes(), coins)` and submits it through `msgSrv.Send`; since the zero address is not in `BlockedAddr`, the send succeeds, the `Transfer` event is emitted, and the caller's balance is deducted with no way to recover the funds (no known private key corresponds to the zero-address-derived account).
4. Repeat via `transferFrom` with an approved spender specifying `to = address(0)` to show the same loss occurs on behalf of a token owner.

Note: I could not directly confirm within the available index whether `x/bank`'s `BlockedAddr` set is customized elsewhere in this repo to include the zero address (the `x/bank` keeper source itself was not indexed/found), so this should be verified in a live Devin session before treating this as fully confirmed; if the zero address is already blocked at the bank-keeper level, this specific precompile path would be mitigated (though the missing explicit check would still be a defense-in-depth gap).
