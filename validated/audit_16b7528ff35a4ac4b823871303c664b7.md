## Finding [1](#0-0) [2](#0-1) 

### Title
Package upgrade unconditionally re-arms lazy self-init `deploy_owner` for every module in the package, silently reviving self-init for modules blocked by the ownership-transfer guard - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`aptos_framework::init` gates a Move-hosted object's lazy self-initialization (`internal_maybe_initialize`) on a per-module `deploy_owner` recorded at each module's "last publish." The design intent, stated in the code's own doc comments and unit tests, is that "republishing one module does not re-arm a sibling" [3](#0-2)  — i.e., only the module actually being (re)published should have its owner record refreshed. However, the real integration path, `code::publish_package`, records the owner for **every module name in the whole package bundle** on every publish/upgrade call, not just modules whose bytecode changed, because Aptos's package model requires every publish transaction to carry the full module set (`check_upgradability` requires all pre-existing module names to still be present) [4](#0-3) .

### Finding Description
`code::publish_package` computes `module_names` from `pack.modules` — the complete module list of the package being published, old and new alike [5](#0-4)  — and then unconditionally calls `init::record_deploy_owner` for every one of those names, stamping the *current* root owner of the object onto each module's `deploy_owner` field:

```
if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
    let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
    module_names.for_each_ref(|name| {
        init::record_deploy_owner(addr, *name.bytes(), owner);
    });
};
``` [1](#0-0) 

This runs on `object_code_deployment::upgrade` as well, since it forwards to `code::publish_package_txn` using a signer minted from the code object's `extend_ref` [6](#0-5) , gated only on `object::is_owner(code_object, publisher_address)` for the *current* owner — with no distinction between modules the new owner is actually changing versus modules that are merely being re-submitted unchanged as part of the mandatory full bundle.

`init::assert_may_self_initialize` is the security control meant to permanently block self-init once an object's ownership diverges from the owner recorded at a module's last publish (a fail-closed "expired lock" state) [7](#0-6) . Because `record_deploy_owner` is invoked for the *entire* module set on *any* upgrade, that "expired" gate is silently reset to match the current owner for modules the new owner never intended to re-authorize, contradicting both the documented invariant ("republishing one module does not re-arm a sibling") and the dedicated regression test `republished_sibling_does_not_rearm_transferred_module`, which exercises `init::record_deploy_owner` directly rather than through the real `code::publish_package` bundle-wide loop and therefore does not catch this discrepancy [8](#0-7) .

### Impact Explanation
An attacker can deploy a package to an object they control containing a malicious module (e.g. `m1`) whose public entry function calls `init::internal_maybe_initialize`, without ever triggering it. The attacker transfers the object to a victim; because `deploy_owner` for `m1` still records the attacker while the current root owner is now the victim, `assert_may_self_initialize` correctly blocks `m1` from minting a signer. However, if the victim later performs *any* legitimate upgrade to the package (e.g. adding a new module `m2`, unrelated to `m1`), `code::publish_package` re-records `deploy_owner = victim` for **all** modules in the bundle, including the still-malicious, unmodified `m1`. Anyone can then call `m1`'s entry function, which now passes the ownership check and mints a `signer` for the object's address — handing attacker-authored bytecode privileged authority (`move_to`, capability retrieval, resource manipulation) over an address the victim believes they fully control. This defeats the entire purpose of the "ownership changed since deploy" guard and can lead to theft or corruption of resources stored under the object.

### Likelihood Explanation
This requires the victim to willingly acquire/own the object (e.g., via a marketplace, NFT-style transfer, or any workflow that hands code-object ownership to a new party) and subsequently perform an upgrade to any single module in that package — a normal, expected maintenance operation that the new owner has every incentive to perform and no reason to suspect re-arms unrelated modules. No cooperation beyond a standard "upgrade my package" transaction from the victim is required, so likelihood is high once the ownership-transfer + package-object pattern is used, which is an explicitly supported use case for `object_code_deployment`.

### Recommendation
`code::publish_package` should only call `init::record_deploy_owner` for modules that are new or whose module bytes actually changed, or `init` should track deploy owner state independent of bulk-bundle republishing (e.g., only refresh `deploy_owner` for a module the first time it is deployed under the current owner, not on every subsequent republish that merely re-submits it unchanged as part of the mandatory full package bundle). At minimum, integration-level tests exercising the full `code::publish_package` / `object_code_deployment::upgrade` path (not just direct `init::record_deploy_owner` calls) should assert that an unrelated sibling module's `deploy_owner` is not rearmed by an upgrade to another module in the same package.

### Proof of Concept
1. Attacker calls `object_code_deployment::publish` with a package containing modules `m1` (malicious, gated by `internal_maybe_initialize(false)`) and never invokes `m1`'s init entry point.
2. Attacker transfers the resulting code object to `victim` via `object::transfer_call`.
3. At this point, calling `m1`'s entry aborts with `EOWNER_CHANGED_SINCE_DEPLOY` (per `assert_may_self_initialize`), confirming the guard is active — mirroring `init_maybe_initialize_object_owner_changed_aborts` [9](#0-8) .
4. `victim` calls `object_code_deployment::upgrade` on the code object to add/fix an unrelated module `m2` (a normal, expected maintenance action).
5. Because `code::publish_package`'s owner-recording loop iterates over the full `module_names` set (which must still include `m1` per `check_upgradability`), `m1`'s `deploy_owner` is now overwritten to `victim`.
6. Attacker (or anyone) calls `m1`'s entry function; `assert_may_self_initialize` now succeeds since recorded owner (`victim`) equals current owner (`victim`), and `m1` obtains a `signer` for the object address — despite the victim never intending to re-authorize `m1`.

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }

    /// The object root owner recorded for `module_id` at its last publish, or `none` if the module
    /// has no such record (an account module, or an object module never recorded).
    fun recorded_deploy_owner(addr: address, module_id: ModuleId): Option<address> {
        if (!exists<InitializationState>(addr)) return option::none();
        let modules = &InitializationState[addr].modules;
        if (modules.contains(&module_id)) modules.borrow(&module_id).deploy_owner else option::none()
    }

    /// Records `owner` as the object root owner of the module named `module_name` at (re)publish, to
    /// gate its later self-init (see `assert_may_self_initialize`). Called per module by
    /// `code::publish_package` for object addresses only.
    package fun record_deploy_owner(addr: address, module_name: vector<u8>, owner: address) {
        let module_id = module_id_from_name(module_name);
        ensure_module_state(addr, module_id);
        InitializationState[addr].modules.borrow_mut(&module_id).deploy_owner = option::some(owner);
    }
