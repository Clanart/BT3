### Title
Single failing request/response dispatch aborts the entire ISMP message batch and skips fee settlement for all other messages - ([File: modules/pallets/ismp/src/impls.rs])

### Summary
This is a direct structural analog of the "invalid Deposit halts the chain" bug: a single bad/rejected item inside a batch is supposed to be tolerated per-item, but a higher-level aggregation step turns that one failure into a hard error for the *entire* batch, discarding all otherwise-valid work.

### Finding Description
`request::handle` and `response::handle` in `modules/ismp/core/src/handlers/request.rs` and `.../response.rs` process a batch of POST requests / GET responses. `request::handle` is explicitly designed to tolerate per-item failures: it wraps each dispatch result as an individual `DispatchResult` inside a `Vec` via plain `.collect::<Vec<_>>()` (no early return), and even documents this intent with "Delete receipt if module callback failed so it can be timed out" [1](#0-0) .

However, `Pallet::<T>::execute` in `modules/pallets/ismp/src/impls.rs` flattens the `events: Vec<DispatchResult>` from every `MessageResult` in the whole submitted batch and then re-collects them with `.collect::<Result<Vec<_>, _>>()?`: [2](#0-1) 

Because this uses `Result`-collecting `?`, the *first* `DispatchResult::Err` anywhere in the batch (e.g., an application module's `on_accept`/`on_response` legitimately rejecting one request for business-logic reasons, or `router.module_for_id` failing for an unregistered destination module) causes the whole `execute()` call to return `Error::<T>::InvalidMessage`. This negates the per-item tolerance intentionally built into `request::handle`/`response::handle`, and additionally means `T::FeeHandler::on_executed` — which charges/settles fees for the batch — is never invoked at all: [3](#0-2) .

`response::handle` itself has the same defect one level lower: unlike `request::handle`, it uses `.collect::<Result<Vec<_>, _>>()?` directly inside the per-message loop, so a single failing `GetResponse` (unknown module, failed state-proof decode, etc.) aborts that entire response message before `MessageResult::Response` is even returned: [4](#0-3) .

### Impact Explanation
Relayers submit messages in batches (the Tesseract relayer explicitly bundles consensus updates with request/response messages in a single call, e.g. `submit_mandatory_batch`) [5](#0-4) . Any single request/response in a submitted batch that legitimately fails at the destination module (a normal, expected outcome per ISMP design — that's exactly why `request::handle` was built to tolerate it) forces the *entire* extrinsic to revert. All storage writes for that transaction (including receipts for otherwise-successfully-processed requests earlier in the loop) are rolled back, and fee settlement via `FeeHandler::on_executed` never runs for any message in the batch. This blocks legitimate cross-chain settlement/delivery for unrelated requests bundled in the same submission and denies relayers their fee for work already paid for in gas, mirroring the seed report's core defect: one bad item improperly escalated from "should be skipped" to "halts everything else."

### Likelihood Explanation
Any unprivileged user can dispatch a POST request destined for an application module that will predictably reject it (a legitimate, expected `on_accept` failure per the ISMP module contract). No malicious relayer, prover, or admin is required — the relayer only needs to batch that request together with other legitimate messages, which is the default/efficient way batches are constructed. This can be triggered repeatedly and deterministically.

### Recommendation
Change `Pallet::<T>::execute` in `modules/pallets/ismp/src/impls.rs` to collect `DispatchResult` events without short-circuiting on individual `Err`s (mirroring `request::handle`'s own tolerant design), only escalating to a hard error for structural/proof failures (which already `?`-abort earlier, before this flatten step) — not for per-item application-level dispatch failures. Apply the same fix to `response::handle`'s internal `.collect::<Result<Vec<_>, _>>()?` so a single bad `GetResponse` doesn't block the rest of its own batch.

### Proof of Concept
1. User A dispatches POST request R1 destined for module M with a payload that legitimately fails `on_accept` (e.g., insufficient balance in app-level logic) — this is a normal, expected outcome.
2. User B dispatches POST request R2 destined for a different module, well-formed and should succeed.
3. A relayer includes both R1 and R2 (with valid membership proofs) in the same `RequestMessage`/extrinsic call to `execute()`.
4. `request::handle` processes both: R1's `on_accept` fails and is embedded as `Err` inside its `DispatchResult`; R2 succeeds and its `Ok` event is embedded — both returned inside `Ok(MessageResult::Request { events, .. })` as designed.
5. `Pallet::execute` flattens both `DispatchResult`s together and calls `.collect::<Result<Vec<_>, _>>()?`, which hits R1's `Err` and aborts, returning `Error::<T>::InvalidMessage` for the whole call.
6. Result: R2's valid, ready-to-settle request is discarded along with R1; `FeeHandler::on_executed` never runs, so no fees are charged/rewarded, and the relayer must resubmit only R2 alone to get it processed — an avoidable failure directly caused by aggregation logic contradicting the per-item tolerance built into the lower-level handler.
