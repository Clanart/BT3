Based on the code, there is a real vulnerability in the predispatch/escrow accounting of `placeOrder`. Let me confirm the release path for escrowed funds.### Title
Predispatch escrow accounting sweeps stale/shared `CallDispatcher` balance instead of only the current caller's contribution, allowing theft of stranded assets via `IntentGatewayV2.placeOrder` - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
In the predispatch branch of `placeOrder`, the amount credited to a new order's escrow is derived from `IERC20(token).balanceOf(dispatcher)` — the *entire* current balance the shared `CallDispatcher` contract holds for a given token — rather than from any accounting that is scoped to what the current caller actually deposited or produced in this transaction. Because `_params.dispatcher` is a single shared contract used by every order across every user, any token balance left stranded on it by a prior order's predispatch call (a token that was part of `predispatch.assets`/produced by `predispatch.call` but not listed in that prior order's `inputs`, and therefore never swept out) remains available to be swept and credited to a completely unrelated, later order.

### Finding Description
`placeOrder`'s predispatch flow (evm/src/apps/IntentGatewayV2.sol) works as follows: [1](#0-0) 

1. Only the assets in `order.predispatch.assets` are pushed to the dispatcher, and `order.predispatch.call` (fully attacker-controlled calldata routed through `CallDispatcher.dispatch`) is executed.
2. The sweep-back step then queries `balance = IERC20(token).balanceOf(dispatcher)` for each token in `order.inputs`, checks only `balance >= requiredAmount`, and sweeps the *entire* dispatcher balance back to the gateway: [2](#0-1) 
3. The amount actually credited toward escrow is computed purely from the gateway's own balance delta, capped at the caller-specified amount when it is exceeded (excess is only logged as `DustCollected`, but any shortfall is silently accepted as legitimate `received`): [3](#0-2) 

There is no accounting anywhere in this path that ties "how much of the swept `balance`" was actually deposited or generated by *this* `placeOrder` call. `order.predispatch.assets` (what the caller pushes in) and `order.inputs` (what gets swept and escrowed) are independent, uncorrelated arrays — a caller can send a trivial/unrelated token as `predispatch.assets` (only constrained by `amount != 0`) while declaring an entirely different token in `order.inputs` that they never personally supplied. If that token happens to already sit on the shared `dispatcher` — left over from a previous, unrelated order whose predispatch produced a token that wasn't part of *that* order's `inputs` and was therefore never swept — the `balance >= requiredAmount` check is satisfied using someone else's stranded funds, and those funds are swept into the *new* caller's order and recorded as its legitimately-supplied input: [4](#0-3) 

This directly violates the intended invariant that "predispatch execution must not let leftover balances, dust, or unrelated assets become part of a new order's escrow or commitment." Escrowed balances that are backed by another user's stranded assets can then be redeemed by the attacker through the normal `fillOrder`/`cancelOrder` release path, which pays out based on `_orders[commitment][token]` without regard to provenance: [5](#0-4) 

The same pattern (unconditional `balanceOf(dispatcher)` sweep gated only by `balance >= requiredAmount`, with no per-caller provenance check) exists identically in the Tron and SDK-bundled copies of the contract. [6](#0-5) 

### Impact Explanation
An attacker can construct an order whose `predispatch.assets`/`predispatch.call` do not actually supply a given `inputs` token, yet still have that token's `requiredAmount` satisfied and escrowed for their own order, using balances stranded in the shared `CallDispatcher` by an unrelated prior order (potentially another user's funds). The attacker can then let a colluding/self-controlled solver fill the order and collect the output, or let the order expire and `cancelOrder` it to redeem the wrongfully-escrowed tokens back to themselves — a direct, wrongful redirection/withdrawal of assets the attacker never contributed. This matches "Critical: wrongful mint, unlock, withdrawal, refund, or redirect of protocol-controlled or user escrowed assets."

### Likelihood Explanation
The `CallDispatcher` is a single shared, permissionless, stateful contract (`_params.dispatcher`) used by every `placeOrder` predispatch call. Any predispatch execution whose produced/leftover token is not exactly enumerated in that same order's `inputs` array will strand a balance on the dispatcher indefinitely (no automatic cleanup exists outside of a subsequent order's sweep, which is unauthenticated as to provenance). An attacker does not need to compromise anyone; they can either (a) wait for/observe naturally occurring dust from legitimate users' predispatch swaps that under/over-produce a non-input token, or (b) deliberately strand their own funds and immediately reclaim them in a second call for no net-loss testing — and once dust from another party appears, harvest it opportunistically. This is directly reachable by any unprivileged caller of `placeOrder`.

### Recommendation
Bind the predispatch sweep to only the balance that this specific call's predispatch step actually generated, not the dispatcher's absolute balance. Take a snapshot of the dispatcher's balance for each `inputs[i].token` *before* transferring predispatch assets and invoking `dispatch`, and only sweep/credit `balanceAfter - balanceBefore` (the delta produced by this transaction's predispatch call), reverting if that delta doesn't cover `requiredAmount`. Any pre-existing dispatcher balance should be left untouched (or handled exclusively through the privileged, governance-gated `SweepDust` cross-chain flow) so no order's escrow can ever be backed by balances it did not itself deposit/produce in the same call.

### Proof of Concept
1. Victim calls `placeOrder` with `predispatch.assets = [{tokenX, 1000}]` and a `predispatch.call` that swaps `tokenX` for `tokenY` (e.g., via Uniswap), but declares only `inputs = [{tokenX-derived-output-they-expect}]`, unintentionally leaving a residual `tokenY` balance on the shared `dispatcher` (partial fill/slippage/reward token not included in `inputs`). After the victim's tx, `dispatcher` holds e.g. 500 `tokenY`, never swept because no `order.inputs` entry references it.
2. Attacker calls `placeOrder` with `predispatch.assets = [{cheapTokenZ, 1}]` (nonzero, trivial value) and a no-op `predispatch.call`, but sets `order.inputs = [{tokenY, 500}]`.
3. In the sweep step, `balance = IERC20(tokenY).balanceOf(dispatcher) == 500 >= requiredAmount (500)` passes; the full 500 `tokenY` is transferred to the gateway and credited as `order.inputs[0].amount = 500` for the attacker's commitment — funds the attacker never supplied.
4. Attacker (or a colluding solver) fills/cancels the order to redeem the 500 `tokenY` escrow, realizing a gain equal to the victim's stranded balance while having supplied only 1 unit of `tokenZ`.
5. Assert: `_orders[attackerCommitment][tokenY] == 500` despite the attacker's own predispatch transfer containing zero `tokenY`, demonstrating cross-order/cross-user balance contamination through the shared dispatcher.
