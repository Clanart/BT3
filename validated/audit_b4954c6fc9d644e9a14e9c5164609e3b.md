### Title
Automatic `--recursive` clone combined with origin-only credential matching lets a malicious repository silently probe/access arbitrary private repositories using the victim's stored GitHub token - ([File: app/src/lib/git/clone.ts], [File: app/src/lib/trampoline/find-account.ts])

### Summary
GitHub Desktop's `clone()` unconditionally passes `--recursive` to `git clone`, so any repository the user clones will immediately have all of its submodules fetched, with no confirmation step. Desktop's credential helper (`createCredentialHelperTrampolineHandler`) supplies the user's stored GitHub OAuth token to any git credential request whose URL shares the same **origin** as one of the user's signed-in accounts - it does not verify that the specific owner/repo being requested is the one the user intended to clone. An attacker who fully controls a public repository (an unprivileged, remotely-served object) can therefore define submodule URLs pointing at arbitrary `github.com` (or the user's GHE host) repositories, and simply having the victim clone the attacker's repo in Desktop will cause Desktop to transparently authenticate to those attacker-chosen targets with the victim's real credentials.

### Finding Description
`clone()` always adds `--recursive` to the git invocation: [1](#0-0) 
This differs from stock `git clone`, which does not initialize submodules unless `--recurse-submodules`/`--recursive` is explicitly requested. As a result, Desktop turns a plain "clone this repo" action into an implicit "fetch every submodule URL declared by the untrusted `.gitmodules` file" action, without any user prompt or review of those URLs.

Credential resolution during that (and any other) git subprocess run goes through the trampoline credential helper. For GitHub-associated accounts, the lookup is origin-based only: [2](#0-1) 
`findGitHubTrampolineAccount` compares only `new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin` - i.e. protocol+host+port - and ignores the owner/repo path entirely. `getGitHubCredential` uses this to hand back the stored account token for *any* request matching that origin: [3](#0-2) 

Because the URL that reaches the credential helper is derived from the credential request git itself constructs (host/path taken from whatever remote/submodule URL git is currently trying to fetch, see `getCredentialUrl`): [4](#0-3) 
the attacker (who authors the `.gitmodules` file / submodule URLs of the cloned repository) fully controls the `path` portion of that request while the trusted origin check only validates the host. The victim's token is released for that request as long as the host matches an account the user is signed into.

This is the same broken invariant as the report's `FeeFollowModule.processFollow`: a privileged operation (`transferFrom` from the user's approved allowance / here, injecting the user's OAuth token into an HTTP auth header) is driven by a parameter (`follower` / here, the target repo path) that the caller does not control but that an attacker-influenced object does, with only a coarse, insufficient check (arbitrary-`from` transferFrom + upgradeable admin / here, origin-only match with no path/consent check) protecting it.

### Impact Explanation
Any GitHub.com/GHE account signed into Desktop can have its OAuth token silently presented to arbitrary repositories on the same host that the account's user did not intend to access, purely by cloning a malicious public repository. This enables:
- Confirming existence of / read access to arbitrary private repositories (an access oracle: submodule fetch success/failure or resulting file contents on disk reveal whether the victim's account can read `owner/name`), leaking information about private organizational repos the victim has access to.
- Forcing the victim's credentialed client to make authenticated requests to targets chosen entirely by the attacker, without the victim ever seeing or approving those URLs, since Desktop performs the recursive submodule fetch automatically on clone.

This does not directly transfer funds like the AAVE Lens report, but it is the same class of "attacker-chosen destination consumes the victim's standing authorization without an explicit, path-scoped consent check."

### Likelihood Explanation
Requires only that the victim clone a public repository the attacker controls or contributed to - a very ordinary, unprompted user action for Desktop (add/clone repo flow). No local access, no elevated privileges, no leaked credentials, and no unnatural steps are needed; only unprivileged control over a repository's `.gitmodules`/submodule URLs is required.

### Recommendation
- Do not default to `--recursive` on `clone()`; require explicit opt-in or prompt the user with the list of submodule URLs before fetching them, similar to stock git behavior.
- Scope credential release in `findGitHubTrampolineAccount`/`getGitHubCredential` to the specific owner/repo (or at minimum warn/prompt) rather than matching solely on origin, especially for submodule/recursive operations triggered on repositories the user has not explicitly reviewed.
- Consider isolating submodule fetches that occur as part of an initial clone from being able to reuse the primary account's token without a scoped, per-repository check.

### Proof of Concept
1. Attacker publishes a public repository `evil/bait` containing a `.gitmodules` file with an entry:
```
[submodule "probe"]
    path = probe
    url = https://github.com/victim-org/target-private-repo.git
```
2. Victim, signed into Desktop with a GitHub.com account that has (or lacks) access to `victim-org/target-private-repo`, clones `evil/bait` via Desktop's normal "Clone repository" flow.
3. Desktop invokes `clone()` with `--recursive` (`app/src/lib/git/clone.ts:88-93`), so git automatically attempts to fetch the submodule at `https://github.com/victim-org/target-private-repo.git`.
4. Git requests credentials for that URL; `createCredentialHelperTrampolineHandler` → `getGitHubCredential` matches the request purely by origin (`github.com`) via `findGitHubTrampolineAccount` (`app/src/lib/trampoline/find-account.ts:20-29`) and returns the victim's stored OAuth token, regardless of the `victim-org/target-private-repo` path.
5. The submodule fetch succeeds or fails depending on whether the victim's token has access, letting the attacker (by observing the victim's resulting repo state, error reports, or by controlling further supply-chain artifacts) determine private repository accessibility - all triggered by a single clone action the victim believed was scoped to `evil/bait`.

```typescript
export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
```

```typescript
export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
```
