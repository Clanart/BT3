### Title
Withdrawal-payout operator attribution derived from unauthenticated OP_RETURN data allows front-running to credit an arbitrary operator - ([File: core/src/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` determines "who funded this withdrawal" purely by parsing the first OP_RETURN output of whatever transaction happens to spend the withdrawal UTXO on-chain, with no cryptographic binding between that OP_RETURN and the actual funder of the transaction's inputs. Because the withdrawal UTXO's spending authorization is a user-supplied, reusable signature/sighash (the attacker-controllable primitives explicitly listed in scope), an attacker can complete/broadcast the withdrawal-spending transaction themselves with a forged OP_RETURN naming a different operator's `xonly_pk`, before the real funder's transaction confirms.

### Finding Description
The binding this code is supposed to preserve is:
`operator_credited (DB column set by update_payout_txs_and_payer_operator_xonly_pk) == operator_whose_funds_actually_paid_the_withdrawal`.

In `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`), for every payout txid found spending a tracked withdrawal UTXO, the code does: [1](#0-0) 

i.e. it takes `get_first_op_return_output` on whichever transaction happened to spend the UTXO, and parses its bytes as an `XOnlyPublicKey` with no signature check that ties this key to the actual signer/funder of the transaction. This value is then persisted verbatim as the credited operator: [2](#0-1) 

Because attribution is a pure data read of attacker-shaped bytes in a transaction the attacker themselves can complete and broadcast (the withdrawal UTXO's spend authorization is a reusable, attacker-controllable Schnorr signature/sighash as scoped in this task), the attacker can front-run the legitimate payout by broadcasting their own completion of the same withdrawal UTXO spend, embedding an arbitrary target operator's `xonly_pk` in the OP_RETURN instead of the real funder's key.

Downstream, each operator's own automation trusts this attribution unconditionally: `PayoutCheckerTask::run_once` looks up unhandled payouts filtered by *its own* `xonly_pk`: [3](#0-2) 

and, upon finding one, proceeds straight into `handle_finalized_payout`, LCP fetch/storage, `end_round`, and `mark_payout_handled` — the full reimbursement pipeline — with no independent verification that the named operator actually funded the withdrawal: [4](#0-3) 

No other guard in the reachable path (`get_first_op_return_output`, `parse_op_return_data`, `update_payout_txs_and_payer_operator_xonly_pk`) re-derives or cross-checks the credited operator against the actual transaction inputs/signers; the DB column is set to whatever bytes appear in OP_RETURN of the confirmed spend.

### Impact Explanation
An attacker who front-runs a withdrawal's fronting transaction can attribute the payout credit to any operator's `xonly_pk` of their choosing, independent of who actually supplied the funds. Any operator whose node observes this forged attribution as "their" unhandled payout will automatically drive it through the reimbursement pipeline (`handle_finalized_payout` → kickoff → `end_round`), resulting in that operator being reimbursed from the shared move-to-vault pool for a payout it never funded — matching the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." This is repeatable for every withdrawal whose UTXO-spend authorization the attacker can race, and the attacker can target any operator whose `xonly_pk` is public knowledge (all operator keys are public in this protocol).

### Likelihood Explanation
This requires only broadcasting a Bitcoin transaction ahead of the legitimate payout-completion transaction, using the withdrawal UTXO's own reusable spend authorization (already available to whoever can construct a valid completion, per the scoped attacker capabilities). This is a plain fee-and-timing race on the Bitcoin P2P network — no privileged key, no majority hashrate, and no verifier/operator/aggregator compromise is needed. Cost is limited to transaction fees and winning a mempool/block race, which is generally feasible for a motivated attacker.

### Recommendation
Do not trust unauthenticated OP_RETURN bytes for operator attribution. Bind the credited operator to a value that is cryptographically committed by that operator (e.g., require the payout's OP_RETURN commitment to be covered by a signature from the claimed operator, or otherwise verify that operator's key/signature actually authorized/funded one of the transaction's inputs) before writing to `update_payout_txs_and_payer_operator_xonly_pk`, and have each operator's `PayoutCheckerTask` independently verify that it, not just the OP_RETURN, actually funded the specific withdrawal before proceeding to `handle_finalized_payout`.
