### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes unvalidated preallocation and unbounded group-element parsing - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg` trusts the serialized participant count `n` (a raw `u16` read from attacker-controlled bytes) before validating it, using it to size a `Vec::with_capacity` allocation and to drive a `for l in (1 ..= n)` loop that parses `n` group elements. This is the same bug class as CVE-2017-6961 in `apng2gif`: a length field inside untrusted input directly determines how much memory is allocated/parsed, with no prior sanity bound against the actual input size or the real threshold parameters of the caller.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`):

- Lines 591-602 read `t`, `n`, `i` straight from the stream with no bound check against the byte length remaining.
- Lines 604-613: when the interpolation byte is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` and pushes `n` scalars via `C::read_F`. The capacity reservation happens **before** any data is confirmed present — a `n = 65535` input of only a handful of bytes forces an immediate allocation of `65535 * size_of::<C::F>()` (~2-4 MB depending on the curve, e.g. 56-byte ed448 scalars ≈ 3.7 MB).
- Lines 620-623: `verification_shares` is populated by `for l in (1 ..= n).map(Participant)` calling `C::read_G` per index — the attacker controls the iteration count directly. [1](#0-0) 

`ThresholdKeys::read` is explicitly one of the deserialization entry points that consumes untrusted bytes in Serai's DKG/signing stack, so an unprivileged peer can feed it a crafted blob.

### Impact Explanation
Each crafted input forces an allocation up to ~4 MB that is proportional to the attacker's chosen `n`, not to the bytes actually sent — a memory amplification of thousands of times on tiny inputs (a ~10-byte message forces a multi-MB reservation). Issued repeatedly or concurrently (e.g. spamming a node deserializing key material or shares), this creates sustained allocator pressure/OOM risk, and on allocation failure Rust aborts the process. The `read_F`/`read_G` loops also burn CPU proportional to `n` against truncated or garbage input. Impact is availability-only (consistent with the referenced Medium CVE), but it is a concrete crash-class amplification reachable purely from public bytes.

### Likelihood Explanation
The reader is on the untrusted-input path (listed reachability: `ThresholdKeys::read`). No authentication, signature check, or threshold-parameter cross-check occurs before `n` is consumed — the validation of `ThresholdParams::new(t, n, i)` happens only *after* all `n`-sized allocations and reads at line 625-630. Exploitation requires only control of the byte stream fed to the deserializer, which an arbitrary participant or peer in the DKG pipeline holds. Amplification per message is bounded by `u16` (~4 MB), so a meaningful crash requires repeated messages rather than a single packet, keeping likelihood moderate.

### Recommendation
Validate `n` (and `t`, `i`) against expected bounds *before* any allocation: reject `n == 0`, `n > MAX_PARTICIPANTS`, or `n` exceeding the caller's expected `ThresholdParams`. Replace `Vec::with_capacity(usize::from(n))` with incremental `push` bounded by what `read_F` actually returns, or pre-check that at least `n * size_of::<C::F>()` bytes remain in the reader. Apply the same early-bound check to the `verification_shares` loop (`1 ..= n`).

### Proof of Concept
Conceptual: serialize a `ThresholdKeys` prefix consisting of a valid `C::ID` length+ID, then `t=1`, `n=0xFFFF`, `i=1`, `interpolation=0x00`, and truncate the input. `ThresholdKeys::read::<&[u8]>` immediately performs `Vec::with_capacity(65535)` (~2-4 MB heap reservation) and then iterates 65535 `read_F`/`read_G` calls before erroring. Repeating this deserializes ~4 MB of allocation per ~20 bytes of input, yielding sustained memory/CPU amplification against any endpoint deserializing `ThresholdKeys` from untrusted bytes.
