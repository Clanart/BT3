## Title
`IntentGatewayV2.withdraw()` on Tron accepts non‑reverting failed ERC‑20 transfers as successful settlement, permanently losing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` moves escrowed order tokens with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself did not revert (`success`), never inspecting the ABI-decoded boolean return value. This is the same bug class as the external report: an asset-movement message is fired and the contract's internal accounting is finalized as if the transfer succeeded, but the actual token movement can silently fail (return `false`) while the call itself returns `success = true`. Just like the LP tokens that were never actually burned while the pool's reserves/LP-supply bookkeeping was already updated, here the escrow can be marked `_filled` and debited from `_orders` while the beneficiary never receives the tokens - and since the request is one-time (`_filled` is set), there is no retry path, so the funds become permanently stuck.

### Finding Description
`withdraw()` is the internal settlement routine invoked from both `onAccept` (for `RedeemEscrow`/`RefundEscrow` cross-chain messages) and `onGetResponse` (for cancel-from-source flows): [1](#0-0) 

It performs Checks-Effects-Interactions in the wrong order with respect to failure detection:
1. `_filled[body.commitment] = beneficiary` is set immediately (finalizing the order).
2. For each escrowed ERC‑20 token, it calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only reverts if the low-level `call` itself fails (`!success`), i.e. if the target reverted or has no code. It never decodes/validates the returned `bool` value.
3. `_orders[body.commitment][token] -= amount` is decremented regardless of whether the token's own `transfer` logic actually succeeded.
4. `EscrowReleased`/`EscrowRefunded` is emitted, and the same pattern repeats for `TRANSACTION_FEES`.

Many real-world and even simple mock ERC‑20 tokens return `false` on a failed transfer instead of reverting (pre-EIP-20-hardened tokens, tokens with pausable/blacklist logic that return `false`, or tokens whose `transfer` returns `false` on insufficient contract balance instead of reverting). For such tokens, `token.call(...)` succeeds (`success = true`) even though the balance was not moved. The elsewhere-used `SafeERC20.safeTransfer` (present in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw`) is exactly the guard that protects against this class of failure by decoding and checking the boolean return value; the Tron contract bypasses it for the settlement path by using a raw `.call` instead: [2](#0-1) 

Compare to the vulnerable Tron path which drops that safety: [3](#0-2) 

Because `_filled[body.commitment]` is set unconditionally before/without verifying the transfer actually moved value, and because `onAccept`/`onGetResponse` are one-shot (there is no code path to re-trigger `withdraw` once `_filled` is non-zero), a failed-but-"successful" transfer permanently finalizes the order with no possibility of the beneficiary later reclaiming the escrowed input tokens or fees - the funds are stuck in the `IntentGatewayV2` contract forever, exactly mirroring the report's core defect: bookkeeping state advances even though the underlying asset movement never happened.

### Impact Explanation
This is a direct, unauthorized loss of escrowed user/solver funds on the Tron deployment of the intent settlement flow: the contract's authoritative state (`_filled`, `_orders`) is updated as if tokens were paid out, while for a broad, realistic class of ERC‑20-like tokens the tokens remain locked in the contract with no recovery mechanism. This matches the bounty's "stealing or loss of funds" and "false ... state acceptance" categories, since the settlement state falsely reflects that the withdrawal happened.

### Likelihood Explanation
No malicious peer, relayer, prover, or governance actor is required. The only precondition is that one of the tokens configured as an order input/output/fee token on the Tron gateway follows a non-reverting-failure ERC‑20 pattern (common among older/non-compliant tokens, and a pattern the audited-for `SafeERC20` usage elsewhere in this same codebase explicitly guards against). Any settlement (`RedeemEscrow`, `RefundEscrow`, or GET-response cancellation) involving such a token silently loses funds the first time the token's `transfer` internally fails without reverting.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and the `SweepDust` handling and fee transfer) in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`, consistent with `evm/src/apps/intentsv2/IntentsBase.sol`, so that non-reverting `false` returns cause the whole settlement to revert instead of being finalized. Additionally, consider not finalizing `_filled` until all transfers are confirmed successful, following true CEI ordering.

### Proof of Concept
1. Deploy an ERC‑20 mock whose `transfer()` returns `false` (without reverting) when e.g. its own internal balance check fails (a still-common implementation pattern, distinct from OpenZeppelin's revert-on-failure version).
2. Place a cross-chain order on the Tron `IntentGatewayV2` using this token as an input, and have it filled on the destination chain.
3. When the `RedeemEscrow`/`RefundEscrow` message arrives via `onAccept`, `withdraw()` executes: `token.call(...)` returns `success = true` (the call didn't revert) but the token's internal logic returned `false` and moved no balance.
4. Observe: `_filled[commitment]` is now set to the beneficiary, `_orders[commitment][token]` is decremented to zero, and `EscrowReleased` is emitted — yet `token.balanceOf(beneficiary)` is unchanged and the tokens remain stuck in the `IntentGatewayV2` contract with no further way to trigger a retry, since the order is already marked `_filled`.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
