### Title
Untrusted `ReceivedOutput` bytes can cause threshold signing of an unspendable Bitcoin transaction - (networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an independently supplied offset, `TxOut`, and `OutPoint` without proving that the outpoint actually contains that output. `SignableTransaction` then treats the claimed output value as spendable funds, while `multisig` verifies only that the claimed `script_pubkey` belongs to the threshold key—not that the referenced UTXO exists or has the claimed value. This can produce a fully signed transaction that Bitcoin rejects.

### Finding Description
The scanner normally creates a valid binding between a transaction output and its outpoint: `scan_transaction` copies the actual `TxOut` and sets `outpoint` to `(tx.compute_txid(), vout)`. [1](#0-0) 

That invariant is not preserved when deserializing untrusted bytes. `ReceivedOutput::read` independently decodes `offset`, `output`, and `outpoint`, then returns them without checking whether `outpoint` resolves to `output` on-chain. [2](#0-1) 

`SignableTransaction::new` trusts the decoded value when calculating available funds and uses the decoded outpoint as the transaction input. [3](#0-2)  It later stores the claimed `TxOut` as the prevout committed to by the Taproot sighash. [4](#0-3) 

The only ownership check occurs in `multisig`, which compares the supplied prevout’s `script_pubkey` to the offset threshold key. [5](#0-4)  An attacker can therefore reference a real Serai-controlled outpoint while claiming a different value, or reference a nonexistent/spent outpoint while supplying a Serai-controlled script.

### Impact Explanation
The threshold signing flow will produce signatures over `Prevouts::All(&self.tx.prevouts)`, committing each input to the attacker-supplied `TxOut`. [6](#0-5)  If the claimed amount differs from the actual UTXO, the Taproot signature is invalid; if the outpoint is nonexistent or already spent, the transaction is also invalid.

This is an availability issue analogous to the reported bug: an object asserts ownership/spendability that the code does not actually possess. A forged `ReceivedOutput` can make the system account for nonexistent funds and expend a threshold-signing session on a transaction that cannot confirm. If this input selection is used for a scheduled withdrawal, the resulting plan can repeatedly fail until the invalid input is rejected.

### Likelihood Explanation
The attack only requires supplying malformed serialized bytes to `ReceivedOutput::read` and having those bytes used as a transaction input. The prompt’s trust boundary explicitly includes untrusted bytes passed to `ReceivedOutput::read`, and the decoder imposes no chain-binding validation. [2](#0-1) 

Outputs produced directly by `Scanner::scan_transaction` are safe because the scanner constructs the `TxOut`/outpoint pair from the same transaction. [1](#0-0)  The vulnerability requires an untrusted serialization path rather than the honest scanner path.

### Recommendation
Do not let deserialized `ReceivedOutput`s be treated as spendable solely because they decode successfully. Before calling `SignableTransaction::new`, resolve each claimed `OutPoint` against a trusted UTXO source and verify:

- the transaction exists and is confirmed,
- `vout` is in range,
- the chain’s `TxOut` exactly equals the serialized `output`, and
- the outpoint is currently unspent.

Also reject duplicate outpoints before constructing `tx_ins`, since `SignableTransaction::new` currently converts every supplied `ReceivedOutput` into an input without uniqueness checks. [3](#0-2) 

If `ReceivedOutput::read` must remain public, document it as requiring subsequent UTXO verification or move untrusted decoding into a separate type that cannot be passed directly to `SignableTransaction::new`.

### Proof of Concept
```rust
// `real_utxo` is an existing outpoint paying to Serai's threshold key.
// `forged_txout` uses the same script_pubkey but declares a larger value.
let forged_txout = TxOut {
  value: Amount::from_sat(real_value + 1_000_000),
  script_pubkey: p2tr_script_buf(group_key).unwrap(),
};

// Construct the exact serialization format accepted by ReceivedOutput::read:
// scalar || consensus TxOut || consensus OutPoint.
let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_bytes());
bytes.extend(bitcoin::consensus::encode::serialize(&forged_txout));
bytes.extend(bitcoin::consensus::encode::serialize(&real_utxo));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// This succeeds: the claimed script belongs to the threshold key.
let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, payment_amount)],
  None,
  None,
  fee_per_vbyte,
).unwrap();

assert!(signable.multisig(&threshold_keys).is_some());
```

The resulting signing session commits the forged `TxOut` through `Prevouts::All`, while the transaction input points to `real_utxo`. [6](#0-5)  Bitcoin nodes will reject the signed transaction because the prevout amount committed in the Taproot sighash does not match the actual UTXO.
