### Title
`smartConvert()` reverts entire harvest on router slippage instead of degrading gracefully, freezing/forfeiting harvested WOM rewards - ([File: wombat/SmartWomConvert.sol])

### Summary
`WombatStaking._sendRewards()` routes harvested WOM through `smartWomConverter.smartConvert()` when a fee is marked `isMWOM`. `smartConvert()` hard-codes `_minRec = _amountIn`, assuming the buyback swap of WOM→mWOM through the Wombat pool always returns at least 1:1. If the swap output is even slightly below the input (due to slippage/fees in the underlying Wombat pool), the whole conversion — and the harvest transaction that triggered it — reverts, forfeiting the harvested rewards for that call.

### Finding Description
`SmartWomConvert.smartConvert()` computes a `convertRatio` and then calls `_convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode)`, passing `_minRec == _amountIn`: [1](#0-0) 

Inside `_convertFor`, the "buyback" portion is swapped through the Wombat router with `amountOutMin` hardcoded to `0`, so the router accepts any output amount: [2](#0-1) 

The final check `convertAmount + amountRec < _minRec` then reverts with `MinRecNotMatch` if the actual swap output (`amountRec`) is not exactly enough to make the total obtained mWOM equal the original WOM input: [3](#0-2) 

Since a WOM→mWOM swap through an AMM pool essentially never returns >= 1:1 output once slippage/pool imbalance/fees are accounted for (it's only exactly 1:1 in an idealized zero-slippage case), this `_minRec == _amountIn` assumption is almost always violated whenever `buybackAmount > 0`, i.e., whenever `currentRatio() < buybackThreshold`. This directly mirrors the reported bug class: a hard "should always match exactly" assumption (`amountAvailableForStaking()` vs `compoundedAvaxNodeOpAmt`) that, in practice, is easily forfeited because real-world conditions (slippage, active withdrawals) make the exact match unlikely, and the code has no fallback other than reverting the whole atomic operation.

This function is invoked from `WombatStaking._sendRewards()` as part of normal, unprivileged fee routing during harvesting, which itself is called from `_toMasterWomAndSendReward()`, reachable by ordinary users through `deposit()`/`withdraw()`/`harvest()` on `WombatStaking` or the pool helpers (e.g. `WombatPoolHelper.harvest()`): [4](#0-3) 

Because `_sendRewards` performs the WOM/mWOM fee split and calls into `smartConvert` synchronously as part of the same reward-harvesting flow, an unexpected `MinRecNotMatch` revert bubbles up and reverts the entire harvest/deposit/withdraw call, including the underlying LP deposit/withdraw and all other reward token transfers batched in the same transaction.

### Impact Explanation
A revert here causes the entire harvest operation (and any deposit/withdraw that triggers it) to fail, meaning legitimately harvested WOM rewards accrued by all stakers in the pool cannot be distributed for that call — the reward-processing transaction is forfeited. Since `_sendRewards` is invoked on every deposit/withdraw/harvest that produces WOM rewards, this can repeatedly block reward distribution and any pool interaction relying on `_toMasterWomAndSendReward` for as long as the pool remains imbalanced enough that `currentRatio() < buybackThreshold`, causing a freeze of unclaimed yield exceeding 24 hours (until pool conditions or governance parameters change).

### Likelihood Explanation
Likelihood is high: `buybackThreshold` defaults to `9000` (90%), and `currentRatio()` compares `mWom -> wom` output for exactly `1e18` — any pool depeg or normal slippage easily pushes `mWomToWom` below this, activating the buyback branch. Once active, the swap essentially always yields less than 1:1 (AMMs charge fees and have slippage), so the `_minRec == _amountIn` check will almost always fail, and this path is triggered by ordinary, permissionless calls to `harvest()`/`deposit()`/`withdraw()` — no privileged role is required.

### Recommendation
Do not require `_minRec == _amountIn` in `smartConvert()`. Instead, quote the expected swap output beforehand (e.g., via `router.getAmountOut`) and use a realistic, slippage-tolerant `_minRec`, or decouple the buyback swap from the mint/deposit path so that a router shortfall degrades gracefully (e.g., skip/limit the swap or accept the lesser output) rather than reverting the whole harvest transaction.

### Proof of Concept
1. Pool's `womAsset` `cash < liability` such that `currentRatio() < buybackThreshold` (routine market condition), see `SmartWomConvert.smartConvert()` [5](#0-4) .
2. Any user calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest()` → `_toMasterWomAndSendReward()` → `_sendRewards()`, which (per fee config with `isMWOM=true`) calls `smartWomConverter.smartConvert(feeAmount, 0)`.
3. `smartConvert` computes `convertRatio < DENOMINATOR`, so `buybackAmount > 0`; it swaps WOM→mWOM via `router.swapExactTokensForTokens(..., amountOutMin=0, ...)`.
4. Real-world AMM slippage/fees mean `amountRec < buybackAmount`, so `convertAmount + amountRec < _amountIn (=_minRec)`.
5. `_convertFor` reverts with `MinRecNotMatch`, reverting the entire harvest transaction and forfeiting the harvested WOM rewards distribution for that call.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
