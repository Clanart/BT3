### Title
Quadratic hash amplification in MuSig key aggregation enables CPU DoS from an attacker-influenced key list - (File: crypto/dkg/musig/src/lib.rs)

### Summary
The Ruby `Time.rfc2822` ReDoS is a bug class where a small untrusted input triggers disproportionate computation inside a parser/verifier. The Serai analog is not a regex but a quadratic re-hashing pattern: MuSig key aggregation clones and re-hashes the full binding transcript (which encodes *all* participant keys) once per key, making `musig_key_vartime`, `musig_key`, and `musig` cost O(n²) in the number of supplied keys. An unprivileged party who can influence the set of keys aggregated (e.g., by registering keys in a MuSig-style n-of-n setup) can force each verifier/signer to hash gigabytes of data from a ~2 MB public input.

### Finding Description
`binding_factor_transcript` builds a transcript of `context || keys_len || key_1 || … || key_n` (~32n bytes). `binding_factor` then does `transcript.clone()` and appends the index `i` before calling `C::hash_to_F`:

- `crypto/dkg/musig/src/lib.rs:81-84` — `binding_factor` clones the whole transcript per call.
- `crypto/dkg/musig/src/lib.rs:94-96` — `musig_key_multiexp` calls `binding_factor(transcript.clone(), i)` in a loop over `1 ..= keys_len`.
- `crypto/dkg/musig/src/lib.rs:143-146` — `musig` repeats the same pattern while building `binding_factors`/`multiexp`.

So each of the n iterations clones and hashes ~32n bytes: total work is O(n²) bytes copied plus hashed. `check_keys` (`crypto/dkg/musig/src/lib.rs:46-63`) permits up to `u16::MAX = 65535` keys, so the input bound is ~2 MB while the hashing cost is ~137 GB — roughly five orders of magnitude of amplification from a single short public input.

This is reachable through the public `musig_key_vartime` / `musig_key` / `musig` APIs (`crypto/dkg/musig/src/lib.rs:103-162`), which take only a context and a `&[C::G]` key list — no secret needed to hit the quadratic path (`musig_key_vartime` requires no private key at all).

### Impact Explanation
Any node that runs MuSig-style key aggregation over a key list an attacker can grow or repeatedly trigger will spend time quadratic in the number of keys inside `hash_to_F`. At the permitted maximum (65535 keys), a single call must clone+hash on the order of 137 GB, stalling the caller for a very long time per invocation. Repeated calls (e.g., per signing session, per `musig` invocation computing `musig_key_vartime` twice — once at line 153 via `debug_assert` in debug builds and once at line 151) turn this into a reliable unprivileged CPU-exhaustion vector, analogous in effect to the `Time.rfc2822` ReDoS: tiny request, hours of compute.

### Likelihood Explanation
Exploitation requires an attacker to influence the `keys` slice passed to `musig_key*`/`musig`. In deployments where the participant set of an n-of-n MuSig ceremony is drawn from unpermissioned registrations or attacker-craftable key lists, this is trivially satisfiable — no signature validity, threshold collusion, or secret is needed. Where the key set is small and fixed (e.g., a bounded validator set), the amplification is still present but bounded to a smaller constant, which is why this is a Medium rather than a Critical.

### Recommendation
Avoid cloning and re-hashing the entire transcript per key. Fix by either:

- Hashing `transcript` once into a digest and deriving per-index binding factors as `hash_to_F(DST, digest || i)` (hashing only ~34 bytes per key), or
- Using the transcript framework's incremental challenge API so each `binding_factor` only absorbs `i` on top of a pre-absorbed state (`transcript.clone().challenge(...)` on a `DigestTranscript` still re-hashes; instead clone a `C::H` digest instance mid-stream, which is O(1) state copy, not O(transcript)).

Either change reduces `musig_key*`/`musig` from O(n²) to O(n) in the number of keys.

### Proof of Concept
```rust
use rand_core::OsRng;
use ciphersuite::{Ciphersuite, group::ff::Field};
use dkg_musig::musig_key_vartime;
use frost::curve::Ristretto;
use std::time::Instant;

// An attacker-controlled key list at the u16::MAX bound permitted by check_keys.
// All keys must be distinct (check_keys rejects duplicates) — generate them.
let keys: Vec<_> = (0 .. u16::MAX)
  .map(|_| Ristretto::generator() * <Ristretto as Ciphersuite>::F::random(&mut OsRng))
  .collect();

let start = Instant::now();
// Each of the 65535 iterations clones and hashes a ~2.1 MB transcript:
// ~137 GB hashed total for a ~2 MB public input.
let _ = musig_key_vartime::<Ristretto>([0; 32], &keys);
println!("elapsed: {:?}", start.elapsed()); // hours-scale, CPU-bound
```

Even without running to completion, the amplification is provable by inspection: `binding_factor` at `crypto/dkg/musig/src/lib.rs:81-84` clones `transcript` (length `34 + 32*keys.len()` bytes) and hashes it, and `musig_key_multiexp` at `crypto/dkg/musig/src/lib.rs:94-96` invokes it once per key — total bytes hashed is `keys.len() * (34 + 32*keys.len())`, quadratic in attacker input.
