### Title
Cached DKG-confirmation preprocess is keyed only by attempt number, so a later validator-set DKG reuses the prior session's nonces and leaks the validator's secret key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's `SigningProtocol` persists a deterministic preprocess seed in `CachedPreprocesses` keyed solely by `context`. `DkgConfirmer` sets `context = (b"DkgConfirmer", self.attempt)` — it does not include the `TributarySpec` set/session or genesis. Because a validator's Ristretto key persists across validator sets and every new DKG begins at `attempt = 0`, the second DKG session reuses the exact same nonce seed as the first, produces identical nonce commitments, and signs a different `set_keys_message`. That is nonce reuse across distinct signed messages, which allows anyone observing the two sessions (all preprocesses and shares are broadcast on-chain) to recover the validator's private key.

### Finding Description
`preprocess_internal` encrypts and stores a 32-byte seed under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)`, and on every subsequent call loads the same seed back (`CachedPreprocesses::get(self.txn, &self.context)`) and reconstructs the machine via `AlgorithmSignMachine::from_cache` (coordinator/src/tributary/signing_protocol.rs:123-145). The determinism is total: `seeded_preprocess` feeds the seed into `ChaCha20Rng::from_seed` and derives the nonces via `Commitments::new(&mut rng, original_secret_share, ...)` (crypto/frost/src/sign.rs:121-144). Same seed + same validator secret share ⇒ same nonces `d, e` ⇒ identical `Preprocess` commitments.

`DkgConfirmer::signing_protocol` builds the context as `(b"DkgConfirmer", self.attempt)` only (signing_protocol.rs:274-277). The `attempt` counter is shared with the DKG protocol and restarts for each new DKG (`removed_as_of_dkg_attempt` per attempt, signing_protocol.rs:271). The `TributarySpec`/validator-set session is not part of the cache key, and `SigningProtocolDb` is a flat coordinator-wide table (create_db! at signing_protocol.rs:86-90). Therefore a validator that confirms DKG attempt N of validator set A, and later confirms attempt N of validator set B (e.g., set rotation → new tributary/genesis), calls `share_internal` → `machine.sign(preprocesses, msg)` twice with the same nonces but different `msg` (`set_keys_message` binds the set and `removed` keys, signing_protocol.rs:296-301) and a different MuSig participant list (different `participants` → different aggregate key and challenge).

### Impact Explanation
FROST/Schnorr nonce reuse across two different challenges is fatal: with shares `s₁ = d + b·e + c₁·λ·x` and `s₂ = d + b·e + c₂·λ·x` under the same commitments (`d`, `e`, hence same `b` binding), an observer solves `(s₁ − s₂)/(c₁ − c₂) = λ·x` and recovers the validator's MuSig secret share (and the aggregate signing key component). The file's own safety analysis (signing_protocol.rs:25-48) only argues safety *within* a fixed context under BFT; it does not account for the cache key colliding across distinct sessions. Result: an unprivileged observer of public chain data recovers a validator's signing key and can forge confirmations. Severity: High.

### Likelihood Explanation
Triggering requires only that the same validator participates in two DKG confirmation rounds that reuse an attempt number — a routine event (validator set rotations each start the attempt counter fresh, and `attempt` is reused across the entire session history since the DB is never re-keyed per spec). No malicious validator, broken BFT, or leaked key is required; the attacker only reads published preprocesses/shares. The only mitigating factor is if the coordinator DB were somehow scoped per spec, which the flat `create_db!` table and the key derivation (context only, no `spec.set()`/`genesis`) show it is not.

### Recommendation
Include the full session identity in the cache context: e.g., `context = (b"DkgConfirmer", spec.set().session/genesis, attempt)`, and likewise incorporate the participant set (or `musig_context`) so the cached seed is bound to one exact signing session. Alternatively, delete the cached preprocess once the confirmation completes so a later session cannot collide with it.

### Proof of Concept
1. Validator `V` with persistent key `x` participates in DKG attempt `0` for validator set A. `DkgConfirmer::new(..., attempt: 0)` → `preprocess()` → `preprocess_internal` generates a random seed, stores it under `CachedPreprocesses[(b"DkgConfirmer", 0)]`, and returns commitments `C = (D, E)`.
2. `share(preprocesses, key_pair_A)` signs `msg_A = set_keys_message(set_A, removed_A, key_pair_A)`; share `s_A` is published.
3. Later, validator set B forms (new `TributarySpec`, new genesis). Its DKG again reaches `attempt 0`. `signing_protocol()` builds the same `context = (b"DkgConfirmer", 0)`; `CachedPreprocesses::get` returns the old seed; `from_cache` → `seeded_preprocess` regenerates identical nonces → identical `C = (D, E)`.
4. `share(preprocesses', key_pair_B)` signs `msg_B ≠ msg_A` with the same nonces; share `s_B` is published.
5. Observer computes the binding factor `b` (identical since commitments match) and recovers `λ·x = (s_A − s_B)·(c_A − c_B)⁻¹`, compromising V's validator key and enabling forged set-keys confirmations.

Note: the exact DB scoping (whether the coordinator ever hosts multiple specs against one DB) could not be fully confirmed within this scan, but the cache key demonstrably omits all session/set identity, which is the defect regardless.
