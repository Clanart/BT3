### Title
`ReceivedOutput::read` trusts an attacker-supplied key offset — untrusted bytes can claim any Bitcoin output under an unspendable/arbitrary offset ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
CVE-2025-64011 is an IDOR: an attacker-chosen identifier (`fileId`) is dereferenced without verifying it is bound to the object/requester. The Serai analog lives in `ReceivedOutput`. A `ReceivedOutput` is a triple `(offset, output, outpoint)` where `offset` is the scalar that selects *which* derived key spends the output — exactly the "object reference" role `fileId` plays in the CVE. `ReceivedOutput::read` deserializes all three fields from attacker-controlled bytes and performs **zero** binding checks: it never verifies that `self.key + offset·G` (tweaked) hashes to `output.script_pubkey`, never checks `outpoint` exists or is unspent, and never checks `offset` is one the `Scanner` actually registered. The consumer is told "we received an output spendable by `key.offset(offset)`" purely on the attacker's say-so.

### Finding Description [1](#0-0)  `read` pulls a `Scalar` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`. Compare with the honest path: `Scanner::scan_transaction` only produces a `ReceivedOutput` when `output.script_pubkey` is present in `self.scripts` — i.e., it proves `p2tr_script_buf(key + offset·G) == output.script_pubkey` and that `offset` was registered via `register_offset` [2](#0-1) . `read` enforces none of this. It is reachable with purely public input (untrusted bytes fed to `ReceivedOutput::read`, an in-scope sink), requires no key material, and the forged object is indistinguishable from a scanner-produced one: same type, same serialization format (`write` emits exactly `offset || TxOut || outpoint` [3](#0-2) ).

Two concrete abuse modes mirror the IDOR class:

1. **Claim someone else's output as received-but-unspendable.** Attacker supplies `offset = 0` (or any scalar not matching the script) together with a real `TxOut`/`outpoint` belonging to an unrelated wallet, or an output paying to `key` while pairing it with an `offset` that doesn't derive that script. Downstream code that consumes `ReceivedOutput` reports the value as received, yet `keys.offset(offset)` produces a key that does not control the output's script — funds reported received that are not spendable.

2. **Script-path injection via crafted offset.** `register_offset` documents that "arbitrary offsets may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" [4](#0-3) . `read` bypasses `register_offset`'s secure-generation requirement entirely — an attacker can hand the wallet an `offset` chosen so the tweaked key has a known script path, redirecting how the wallet believes the output is controlled.

### Impact Explanation
A forged `ReceivedOutput` causes the wallet/processor layer to treat non-existent or non-spendable outputs as received wallet funds (balance inflation, crediting deposits that can never be swept), or to attempt spends under a wrong offset (failed transactions, fee burn, stuck change handling in `send`). In the offset-injection variant, outputs the wallet believes it controls may actually be spendable by an attacker-crafted script path. This is a documented, accepted impact class ("funds reported received that are not spendable"), matching the CVE's unauthorized-object-reference shape: the identifier (offset) is attacker-chosen and never authorized against the referenced object (the output).

### Likelihood Explanation
Reachability is maximal: `read` is a public deserialization API whose input is a raw byte stream — no authentication, no secrets, no privileged position. The only requirement is that some consumer accepts a serialized `ReceivedOutput` from a less-trusted source rather than always constructing it via `Scanner` locally. Severity is Medium: concrete integrity loss (phantom deposits / unspendable reported funds / script-path injection), bounded by the fact that direct theft requires the downstream spend path to also trust the forged offset without re-deriving the script.

### Recommendation
Make `ReceivedOutput` self-validating or drop trust in its serialized form:

- Add a `ReceivedOutput::read`-adjacent verifier, e.g. `fn read_and_verify<R: Read>(r, scanner: &Scanner)` that re-checks `output.script_pubkey == p2tr_script_buf(scanner.key + G·offset)` and that `offset` is a registered offset — i.e., enforce the same binding `scan_transaction` enforces.
- Alternatively, serialize only `(outpoint)` and re-derive `output`/`offset` by re-scanning the referenced transaction, so no attacker-controlled identifier is ever trusted.
- Document loudly that the bare `read`/`serialize` round-trip is trusted-input-only if it must remain.

### Proof of Concept
```rust
// Forge a ReceivedOutput claiming victim's outpoint is spendable by offset 0
let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_bytes());                 // wrong/unregistered offset
bytes.extend(serialize(&victim_txout));                // someone else's TxOut
bytes.extend(serialize(&victim_outpoint));             // someone else's OutPoint
let forged = ReceivedOutput::read(&mut &bytes[..]).unwrap();  // accepted unconditionally
// forged.value() == victim_txout.value; wallet reports it received,
// yet keys.offset(Scalar::ZERO) does not control victim_txout.script_pubkey.
```
For the injection variant, pick `offset` such that `key + offset·G` has a known taptree path, pair it with any output, and hand the bytes to `read` — bypassing `register_offset`'s secure-generation contract entirely.

Confidence note: the concrete misuse (phantom/unspendable reported funds, offset injection bypassing `register_offset`'s contract) is fully proven by `read`/`scan_transaction`/`register_offset` in `networks/bitcoin/src/wallet/mod.rs`. Whether a specific processor call-site actually feeds untrusted bytes into `ReceivedOutput::read` was not fully traced (processor code is out of the listed scope), which is why severity is rated Medium rather than High.

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
