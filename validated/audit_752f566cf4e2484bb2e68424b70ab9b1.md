### Title
Future oracle timestamp collapses staleness delta to zero and poisons the monotonic `last-update` marker, permanently freezing price freshness for a feed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` is meant to gate stale prices out of `price-resolve`, the function every collateral/debt valuation, health check, and liquidation path relies on. Its delta computation silently treats any oracle timestamp greater than the current `stacks-block-time` as "delta = 0" instead of rejecting it, and the accepted timestamp is then written into the monotonic `last-update` map that all future price updates for that feed must be `>=` to.

### Finding Description
`oracle-timestamp-fresh` computes:
```
(delta (if (> ts stacks-block-time) u0 (- stacks-block-time ts)))
(and (<= delta max-staleness) (>= ts prev))
``` [1](#0-0) 

When the feed-reported `ts` (Pyth/DIA `publish-time`) is greater than `stacks-block-time`, the branch sets `delta = u0`, which trivially satisfies `<= max-staleness` regardless of how far in the future `ts` actually is. This is exactly the "start/end can be zero/equal and bypass the intended time window" class from the report: the guard is supposed to bound the age of the price, but the future-timestamp branch degenerates the check into a no-op instead of rejecting the input.

`price-resolve` then persists that accepted (possibly far-future) timestamp:
```
(if (> timestamp last-update-time) (map-set last-update key timestamp) false)
``` [2](#0-1) 

`last-update` is the `prev` value fed back into `oracle-timestamp-fresh` on the next call via `oracle-last-update`. Because the second conjunct requires `(>= ts prev)`, once a poisoned future timestamp is stored, every subsequent legitimate price update (with a real, current `ts`) fails `(>= ts prev)` and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`. `price-resolve` is the sole path for both `price-multi-resolve` (used by `get-assets` for all enabled collateral/debt) and the on-demand disabled-collateral price fetch inside `process-collateral-asset`. [3](#0-2) [4](#0-3) 

### Impact Explanation
Once `last-update` for a feed is poisoned with a future timestamp, that asset's price can no longer be refreshed — every call reverts until real chain time catches up to the poisoned value. Since `get-notional-evaluation`, `get-assets`, borrow/health checks, and `liquidate` all funnel through `price-resolve`/`price-multi-resolve`, this either freezes all operations that need a price for that asset (borrow, withdraw, liquidate) — a temporary freezing of funds/yield for that asset — or, if only some assets are affected while the account's overall position still resolves via other assets, the frozen asset can no longer be liquidated for the freeze window, exposing the protocol to bad debt if collateral value drops in the meantime.

### Likelihood Explanation
This requires only a single upstream price update with a timestamp ahead of `stacks-block-time` — plausible from ordinary clock skew between the oracle publisher and the Stacks node, not solely malicious oracle manipulation, and the bug is in Zest's own `oracle-timestamp-fresh`/`price-resolve` handling of that input, not in the oracle's own correctness. The `is-price-update-more-recent`/staleness logic in `pyth-storage-v4.clar` guards the Pyth storage layer separately, but does not prevent Zest's own `last-update` map (a separate, market-contract-local state) from being poisoned the same way once a slightly-future-timestamped update is accepted by `oracle-timestamp-fresh`.

### Proof of Concept
1. A price update for asset X arrives with `publish-time` a few seconds ahead of the current `stacks-block-time` (e.g., due to clock drift) but still within Pyth's own staleness bound, so `pyth-storage-v4.clar`'s checks pass.
2. `price-resolve` calls `oracle-timestamp-fresh(ts, prev, max-staleness)`; since `ts > stacks-block-time`, `delta` is forced to `u0`, satisfying `<= max-staleness` trivially, and `(>= ts prev)` also holds, so the update is accepted.
3. `map-set last-update key ts` stores the future `ts` as the new baseline. [2](#0-1) 
4. On the next legitimate price fetch (real `ts'` ≈ current `stacks-block-time` < poisoned `ts`), `(>= ts' prev)` fails, so `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every caller (`get-assets`, `liquidate`, borrow/health checks) until real time passes the poisoned `ts`.
5. During that window, any account depending on asset X's price for health/liquidation math cannot be liquidated (or cannot borrow/withdraw against it), freezing that exposure.
