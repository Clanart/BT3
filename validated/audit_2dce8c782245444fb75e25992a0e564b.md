### Title
Fee evasion on ISMP request/response delivery via unparseable `signer` field silently skipping treasury charge - ([File: modules/pallets/ismp/src/fee_handler.rs])

### Summary
`WeightFeeHandler::on_executed` charges the message's weight-based fee only when it can decode `msg.signer` into a `Signature` and recover a valid sr25519 public key. If either step fails, the `originator` is `None` and the entire `if let Some(originator_bytes) = originator { ... }` block — including the treasury transfer — is silently skipped, while the ISMP request/response itself has **already been fully executed** (module `on_accept`/`on_response` called, receipt stored) by `Pallet::<T>::execute` before `on_executed` ever runs.

### Finding Description
`Pallet::<T>::execute` in `modules/pallets/ismp/src/impls.rs` processes the full batch of incoming messages first — running proof verification and dispatching to `IsmpModule::on_accept`/`on_response` (real state/asset effects on the destination) — and only afterwards calls `T::FeeHandler::on_executed(messages_with_weights, events.clone())` to charge for the work already done: [1](#0-0) 

The concrete `FeeHandler` wired via `pallet_ismp::Config` is `fee_handler::WeightFeeHandler`, which recovers the paying account strictly from `msg.signer`: [2](#0-1) 

`msg.signer` is an attacker-controlled, arbitrary `Vec<u8>` field on the `RequestMessage`/`ResponseMessage` — it is **not** used anywhere to authorize or gate delivery of the request/response itself (that authorization comes purely from the state/consensus proof verified earlier in `handlers/request.rs` / `handlers/response.rs`). It is only consulted here, after the fact, to determine who to bill: [3](#0-2) 

If `Signature::decode(&mut &msg.signer[..])` fails to parse, or `verify_and_get_sr25519_pubkey` fails (e.g. `signer` is garbage bytes, an empty vec, or a syntactically valid-but-non-matching signature), `originator` becomes `None`, and the `C::transfer(...)` call — the only place a fee is actually charged to anyone — is never reached. The function then returns `Ok(PostDispatchInfo { pays_fee: Pays::Yes, .. })` as if fee collection succeeded, and the whole extrinsic commits, permanently persisting the message's on-accept side effects (receipts, dispatched requests, any bridged value the destination module already moved) with zero fee paid.

This is the same broken invariant as H-08: an operation that is supposed to be paid for based on parsing/validating attacker-supplied bytes performs the "expensive"/state-changing work (message delivery/execution) *before* the payment step, and when that parsing step throws or is malformed, the charge is unconditionally skipped rather than the whole operation being rejected or charged a fallback fee.

### Impact Explanation
Any unprivileged submitter of an ISMP `RequestMessage`/`ResponseMessage` can set `signer` to bytes that fail to decode/verify, causing the treasury fee for that message's weight to be silently waived while the message still executes normally end-to-end (module `on_accept`/`on_response` runs, receipts are stored, and any assets the destination module moves proceed as usual). This is a logic attack against the protocol's economic gating — unauthorized/unpaid execution of bridge message delivery — resulting in fee-revenue loss to the treasury and message throughput obtained for free rather than being rejected as invalid.

### Likelihood Explanation
High feasibility: `signer` is a free-form byte vector fully controlled by the relayer/submitter and is never checked against the identity that produced the underlying state/consensus proof. No signature over the request payload is otherwise required for delivery — proof verification is independent of `signer`. Any relayer can trivially submit `signer: vec![]` or malformed bytes instead of a real signature to bypass the fee path deterministically, with no elevated privileges, malicious peer, or governance/prover compromise required.

### Recommendation
Do not let fee collection failure/skip be conditioned on optional, unauthenticated data supplied by the same submitter who benefits from the skip. Options:
- Require `msg.signer` to decode and verify successfully as a precondition for message acceptance in `handlers/request.rs`/`handlers/response.rs` (reject the whole message if it can't be attributed), or
- Have `WeightFeeHandler::on_executed` treat a failed decode/recovery as a hard error (bail out and revert the whole extrinsic, per FRAME's automatic dispatch-level storage rollback) instead of silently continuing with `pays_fee: Pays::Yes` and no transfer, or
- Fall back to charging a well-known default payer (e.g., a bond posted at message submission time) when the signer cannot be recovered, so a malformed signer can never result in a completed message with zero paid fee.

### Proof of Concept
1. Attacker crafts a valid `RequestMessage` (or `ResponseMessage`) with a legitimate state/consensus proof for a genuine cross-chain POST request destined to a module that performs real value transfer (e.g. a token gateway).
2. Attacker sets `signer = vec![]` (or any byte sequence that fails `Signature::decode` / `verify_and_get_sr25519_pubkey`).
3. Submits via `pallet_ismp::Pallet::<T>::handle_unsigned`/equivalent extrinsic. `handlers::request::handle` verifies the proof (which does not depend on `signer`) and dispatches to `IsmpModule::on_accept`, which executes normally (e.g., mints/releases bridged funds on the destination), storing the request receipt.
4. `Pallet::<T>::execute` then calls `WeightFeeHandler::on_executed`. `Signature::decode(&mut &[][..])` fails → `originator = None` → the `if let Some(originator_bytes) = originator` branch is skipped → no `C::transfer` occurs.
5. Function returns `Ok(PostDispatchInfo { pays_fee: Pays::Yes, .. })`; the extrinsic succeeds and commits. The message was fully delivered/executed and no fee was ever debited from any account, confirmed by observing the treasury account balance is unchanged versus the `should_charge_fee_for_request` baseline test: [4](#0-3) 

Replacing the valid `signature` used in that test with a malformed/empty `signer` byte vector while keeping the rest of the flow identical reproduces the skip: `final_treasury_balance == initial_treasury_balance` despite the request having been processed exactly as in the passing case.
