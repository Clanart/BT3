### Title
Scanner reports sub-dust outputs as received funds that can never be economically spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` credits any output paying to a registered `script_pubkey` as a `ReceivedOutput` without checking the output's value against the network's dust/economic-spendability floor. This is the analog of the external report's "trusted external numeric value used without a minimum/maximum range check": just as `ChainlinkPriceFeed::getPrice` accepts any positive price regardless of the aggregator's min/max band, `Scanner` accepts any positive satoshi amount regardless of whether the output is worth more than the fee required to spend it.

### Finding Description
`Scanner::new` and `Scanner::register_offset` map `script_pubkey`s to scalar offsets. `scan_transaction` then returns a `ReceivedOutput` for every transaction output whose `script_pubkey` matches, copying `output.value` verbatim into the result:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
``` [1](#0-0) 

There is no check that `output.value.to_sat() >= DUST` (or any other bound). Contrast with the spend path, which does enforce a floor: `SignableTransaction::new` rejects payments below `DUST` and drops change below `DUST`, and `Bitcoin::DUST` is explicitly defined as the value under which an output is not worth spending ("This value MUST exceed the cost to spend said output, and should by a notable margin", set to 10,000 sats, an order of magnitude over the ~285 sat spend cost): [2](#0-1) [3](#0-2) [4](#0-3) 

So Serai's own code defines a minimum acceptable output value — exactly the "acceptable range" the external report says is missing — but enforces it only on outputs Serai *creates*, never on outputs an external party *sends in*. The scanned value flows into `input_sat` in `SignableTransaction::new` (`inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()`), so a dust input is treated as real spendable value when computing whether `input_sat >= payment_sat + needed_fee`: [5](#0-4) 

### Impact Explanation
Any unprivileged party can send a Bitcoin transaction with outputs below `DUST` to the vault's `p2tr_script_buf` address (or to a registered HDKD offset address). The scanner reports these as `ReceivedOutput`s — funds received — yet each such output costs more in fees to spend than it is worth. This is the "funds reported received that are not spendable" consequence class:

- If such outputs are credited (e.g., sriBTC minted against them), the issued token is backed by value that can never actually be recovered — directly analogous to the external report's overvaluation of a crashed asset because the oracle returns `minPrice`.
- If dust inputs are mixed into `SignableTransaction` inputs, they inflate `input_sat`, potentially causing `NotEnoughFunds` failures to be masked at planning time while the effective spendable balance is lower than reported.

### Likelihood Explanation
Reachable entirely by public inputs: an attacker only needs to broadcast a standard Bitcoin transaction paying dust to a known vault/offset address — no validator collusion, no malicious node/RPC, no leaked keys. Vault addresses are public knowledge once used on-chain. The cost to the attacker is the dust output itself (a few thousand sats). The main uncertainty reducing likelihood/severity is whether upstream processor code filters sub-`DUST` `ReceivedOutput`s before crediting them; `processor/src/multisigs/scanner.rs` and the `Scheduler` do apply `N::DUST` filtering to *payments* in `created_output` and `prepare_send`, but I could not confirm within available iterations whether received-output crediting applies an equivalent floor at scan time. The scanner's own documentation only calls out coinbase maturity as requiring a post-processing pass — dust is not mentioned — suggesting the library-level gap is real: [6](#0-5) [7](#0-6) 

### Recommendation
Enforce the already-defined range bound on inbound value: in `Scanner::scan_transaction` (or in the mandatory post-processing documented alongside `scan_block`), skip outputs with `output.value.to_sat() < DUST`, matching the check `SignableTransaction::new` applies to payments and change. If filtering at scan time is undesirable for library purity, the processor must explicitly discard sub-`DUST` `ReceivedOutput`s before they are credited or used as inputs, and this requirement must be documented the same way coinbase maturity is.

### Proof of Concept
1. Obtain the vault group key's address: `p2tr_script_buf(group_key)` (or any registered offset address).
2. Broadcast a Bitcoin transaction paying, e.g., 546 sats (standard P2TR relay dust, far below Serai's `DUST = 10_000`) to that address.
3. `Scanner::scan_block`/`scan_transaction` returns a `ReceivedOutput` with `value() == 546`, indistinguishable in type from a legitimate deposit.
4. Spending that input in `SignableTransaction::new` contributes 546 sats to `input_sat` while consuming ~57 vbytes of weight — at any fee rate ≥ ~10 sat/vB its fee cost exceeds its value, and at the enforced minimum relay fee it can never satisfy the "exceed cost by an order of magnitude" invariant `DUST` encodes. The protocol has reported funds received which are not economically spendable.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));

  }
