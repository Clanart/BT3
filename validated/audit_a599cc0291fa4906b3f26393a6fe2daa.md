### Title
Escrow withdrawal/dust-sweep accepts failed ERC20 `transfer` (unchecked boolean return) as success, permanently locking funds while marking orders fulfilled/refunded - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function and the `SweepDust` branch of `onAccept()` release escrowed order funds using a raw low-level call to the ERC20 `transfer` selector, checking only whether the external call itself reverted (`success`), never inspecting the ABI-decoded boolean return value that ERC20 `transfer` is supposed to return on failure.

### Finding Description
`withdraw()` iterates over `body.tokens` and, for ERC20 tokens, executes: [1](#0-0) 
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and immediately decrements the internal escrow accounting `_orders[body.commitment][token] -= amount` regardless of whether the token actually transferred value [2](#0-1) . The same pattern is used for fee redemption in the same function and for dust sweeping in `onAccept`'s `SweepDust` branch [3](#0-2) .

A low-level `.call()` only sets `success = false` if the callee *reverts*. Several real ERC20 tokens (as enumerated in the referenced audit — BAT, HT, CHSB, cUSDC-style tokens, and similarly non-conforming/deflationary or paused tokens) return `false` from `transfer` instead of reverting on failure (e.g., insufficient balance edge cases, blacklist/pause logic, or fee-on-transfer/rebasing quirks). For such tokens, `token.call(...)` returns `success = true` with return data encoding `false`, so the `if (!success) revert TransferFailed();` guard never triggers. The function proceeds to decrement escrow and emit `EscrowReleased`/`EscrowRefunded` even though the beneficiary received nothing.

Notably, the file imports and declares `using SafeERC20 for IERC20;` [4](#0-3)  and uses `safeTransferFrom` correctly elsewhere for deposits [5](#0-4) , but the withdrawal/refund/dust-sweep paths bypass `SafeERC20.safeTransfer` and instead use the unchecked raw-call pattern — this is precisely the "does not check transfer results" bug class from the report, reproduced on the payout side of the escrow instead of the migration side.

### Impact Explanation
Funds escrowed by users/solvers in `IntentGatewayV2` on Tron can become permanently locked in the contract: once `withdraw()` runs against a non-conforming token, escrow is deleted (`_orders[...] -= amount`) and the order is finalized (`_filled[body.commitment] = beneficiary`, `EscrowReleased`/`EscrowRefunded` emitted) even though no tokens moved. Because the commitment is now marked filled/refunded, there is no path to retry the withdrawal for the affected beneficiary — this is unauthorized/incorrect settlement causing direct loss of escrowed funds, matching the "stealing or loss of funds" and "false state acceptance/logic attack" impact categories.

### Likelihood Explanation
This path is reachable by any legitimate cross-chain `RedeemEscrow`/`RefundEscrow` message or `SweepDust` admin message once an order was created with a non-standard-return-value ERC20 token as its input/output asset — no malicious relayer, prover, or admin action is required; the trigger is simply the token's own semantics combined with a normal, protocol-intended withdrawal flow. The severity is limited to the token set that returns `false` instead of reverting, and to the Tron deployment (`evm/tron/contracts/apps/IntentGatewayV2.sol`), since the primary EVM `IntentGatewayV2.sol`/`IntentsBase.sol` consistently use `SafeERC20.safeTransfer`/`safeTransferFrom` [6](#0-5) .

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` and `onAccept()` (`SweepDust` branch) with `SafeERC20.safeTransfer`, consistent with the rest of the contract (`using SafeERC20 for IERC20;` is already declared but unused for these paths). This ensures both call-reversion and false-boolean-return failures cause the transaction to revert, preventing escrow state from being finalized without an actual transfer of value.

### Proof of Concept
1. Create and fill/cancel an order whose escrowed input or fee token is an ERC20 that returns `false` on `transfer` failure instead of reverting (e.g., a paused/blacklist-style token, matching BAT/HT/CHSB/cUSDC semantics from the referenced audit).
2. Trigger the withdrawal path so that `onAccept` receives a `RedeemEscrow`/`RefundEscrow` request (or a `SweepDust` admin message) that calls `withdraw()` with a beneficiary for whom the token's `transfer` internally fails and returns `false` (e.g., beneficiary is blacklisted by the token, or a transfer-fee/rebase edge case reduces the deliverable amount below what's expected by the contract's assumptions).
3. Observe `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself did not revert) with return data `false`.
4. `if (!success) revert TransferFailed();` does not trigger; execution proceeds to `_orders[body.commitment][token] -= amount`, finalizes `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` — the beneficiary received zero tokens, the escrow is deleted, and the commitment cannot be re-claimed, permanently locking the tokens in the contract.

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {

            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));

        }

        if (isRefund) {

        } else {
