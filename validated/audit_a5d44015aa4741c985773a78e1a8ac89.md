### Title
Honest operator's collateral can be burned via SIGHASH_SINGLE|ANYONECANPAY OP_RETURN malleability of the Payout tx - ([File: core/src/verifier.rs -> fn is_kickoff_malicious])

### Summary
`create_payout_txhandler` signs the Payout tx's withdrawal input with `SinglePlusAnyoneCanPay`, which only commits to input 0 and output 0 (the user payout output), leaving the OP_RETURN output (which encodes the fronting operator's xonly pubkey) and the anchor output completely unsigned. An attacker who observes the operator's unconfirmed Payout tx (or who is the withdrawing user themselves) can rebroadcast a variant with the same signed input/output-0 but a stripped or altered OP_RETURN, get it mined first, and permanently poison the DB record for that withdrawal index to `operator_xonly_pk = NULL`, causing `is_kickoff_malicious` to falsely flag the honest fronting operator's subsequent Kickoff as malicious.

### Finding Description
The binding that must hold is: `operator_xonly_pk_recorded(i) == party_whose_funds_paid_output_0(i)`, i.e., the operator xonly pubkey stored in `withdrawals.payout_payer_operator_xonly_pk` for withdrawal index `i` must equal the operator that actually funded/produced output 0 of the mined Payout tx for index `i`.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the Payout tx with: input 0 = user's withdrawal UTXO (KeySpend), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(move_txid ++ operator_xonly_pk). The witness is set via `set_p2tr_key_spend_witness(&user_sig, 0)`.
- The user signature is required to use `SinglePlusAnyoneCanPay` (`core/src/operator.rs:630-637`, confirmed by the error message "Ensure the signature uses SinglePlusAnyoneCanPay sighash type"). This sighash type commits only to input 0's scriptPubKey/value and output 0 — outputs 1 and 2 (including the OP_RETURN with the operator's identity) and any other inputs are *not* covered by the signature.
- Because the attacker fully controls "a Schnorr signature and its sighash flag" and "the bytes of a withdrawal UTXO" per the threat model, and because the withdrawal UTXO belongs to the withdrawing user (who is by definition unprivileged), the attacker can independently construct an alternate transaction that reuses the exact signed input+output-0 pair but omits or corrupts output 2 (or removes it, or makes it not a valid 32-byte xonly key), and add their own fee-paying input(s), then broadcast/RBF it to be mined before the operator X's legitimate broadcast.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) processes whichever transaction is actually found to spend the withdrawal UTXO (via `get_payout_txs_for_withdrawal_utxos` joining `bitcoin_syncer_spent_utxos`), parses its OP_RETURN with `parse_op_return_data`/`XOnlyPublicKey::from_slice`, and if invalid/absent sets `operator_xonly_pk = None` (`core/src/verifier.rs:2319-2328`), which is then written via `update_payout_txs_and_payer_operator_xonly_pk` keyed only by `withdrawals.idx` (`core/src/database/verifier.rs:198-251`). Since the `withdrawals` table has a single row per `idx` (primary key, `core/src/database/schema.sql:269-281`) and a UTXO can only be spent once, this record becomes canonical and permanent for that withdrawal index.
- `is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) later looks up this record via `get_payout_info_from_move_txid`, and when `operator_xonly_pk_opt` is `None` it unconditionally returns `Ok(true)` (line 1882-1885): "No operator xonly pk found in payout tx OP_RETURN, assuming malicious." This is triggered even though operator X genuinely funded output 0 (fronted the withdrawal to the user) and later legitimately sends Kickoff/Reimburse for the same index.
- `handle_kickoff` (`core/src/verifier.rs:1966-2027`) then treats X's Kickoff as malicious and queues a `Challenge` tx, which drives the Disprove/Challenge path that burns X's collateral built in `create_round_txhandler`.
- No existing guard prevents this: `is_kickoff_malicious` only checks equality of the recorded pubkey with `kickoff_data.operator_xonly_pk`, not whether the recorded `None` resulted from adversarial mutation of an unsigned output. The sighash used for the withdrawal input by design does not cover the OP_RETURN output, so no signature-based defense exists for it.

### Impact Explanation
An honest operator's round-tx burn connector / kickoff collateral is destroyed via a Challenge triggered by a false "malicious" verdict, even though the operator genuinely fronted the payout — this matches the Critical category "an honest operator's collateral burned." The attack is repeatable per withdrawal: any withdrawal can be targeted this way as long as the attacker can win the mining race against the operator's own broadcast, and it does not require compromising any verifier, operator, or aggregator key — only control over the withdrawal UTXO's spending path and standard Bitcoin transaction-relay/fee-bidding capability.

### Likelihood Explanation
The attacker needs to: (1) be the withdrawing user or otherwise obtain the `SinglePlusAnyoneCanPay` signature/witness for the specific UTXO (trivial if they are the user), (2) observe or predict the pending Payout tx in the mempool, and (3) construct and get mined a fee-competitive alternate spend of the same input before the operator's version confirms. This requires only ordinary Bitcoin fees/RBF competition — no key compromise, no majority hashrate, and no privileged access — making it feasible for any user who requests a withdrawal to attack their own fronting operator. Confirmation is required as this analysis is based on static code review of the transaction construction and DB write path; full dynamic validation would require the `cargo test` regtest reproduction below.

### Recommendation
Bind the OP_RETURN operator-identity output to the same signature that authorizes the withdrawal spend — e.g., require `SighashType::All` (or `AllPlusAnyoneCanPay` if additional funding inputs are needed) so the operator xonly pubkey output cannot be altered without invalidating the user's signature, or otherwise commit to the OP_RETURN operator pubkey via a covenant/output-restriction rather than relying on the unsigned-output convention.

### Proof of Concept
```
cargo test -p core --test deposit_and_withdraw_e2e -- payout_op_return_malleation_burns_honest_operator_collateral
```
Plan:
1. Run `run_single_deposit` to fund a deposit and obtain `move_txid`/withdrawal index `i`.
2. Call operator X's `withdraw` to obtain the signed Payout tx (`SinglePlusAnyoneCanPay` sig over input 0/output 0), but do NOT broadcast it.
3. Attacker constructs `payout_tx_mutated`: same input (withdrawal UTXO) + witness (X's signature/output0), but with OP_RETURN output removed/corrupted, funded by attacker's own extra input/fee.
4. Broadcast `payout_tx_mutated` and mine it (regtest) before X's original Payout tx can confirm.
5. Assert via `Database::get_payout_info_from_move_txid` that `operator_xonly_pk_opt == None` for index `i`.
6. Have operator X send its legitimate Kickoff tx referencing round/kickoff index for this deposit.
7. Assert `Verifier::is_kickoff_malicious(...)` returns `Ok(true)` for X's Kickoff, and observe (or assert) that `handle_kickoff` queues/sends the `Challenge` transaction against X's Kickoff, demonstrating collateral is put on the burn path despite X being honest.
