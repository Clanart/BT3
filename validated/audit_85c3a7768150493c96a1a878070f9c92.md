### Title
Unbounded O(n²) Lagrange interpolation in `ThresholdKeys::read`/`ThresholdKeys::new` enables CPU-exhaustion DoS from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2019-9513 (attacker-controlled inputs forcing disproportionate CPU work), `ThresholdKeys::read` accepts an attacker-supplied `n`/`t` up to `u16::MAX` and `ThresholdKeys::new` eagerly computes the group key via per-participant Lagrange interpolation, costing O(t²) field operations — ~4.3 billion field multiplications and 65,535 field inversions for a single small (~4 MB) input.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from the byte stream and forwards them to `ThresholdParams::new`, which only enforces `t <= n` and `i <= n` with `u16` bounds — so `t = n = 65535` is accepted. [1](#0-0) [2](#0-1) 

`ThresholdKeys::new` then computes `group_key` by evaluating `interpolation_factor` for every participant `1..=t`. [3](#0-2)  Each `Interpolation::Lagrange` factor loops over all `t` included participants performing one field multiplication each for `num` and `denom`, plus one field inversion. [4](#0-3)  This makes deserialization O(t²) in field multiplications and O(t) inversions — quadratic work triggered purely by two attacker-chosen u16s, while the input itself is only `n` encoded points (~32–57 bytes each, ~4 MB max).

The same quadratic loop is reachable again via `ThresholdKeys::view`, which computes `interpolation_factor` for every member of `included`. [5](#0-4) 

### Impact Explanation
An unprivileged party who can cause a Serai node/validator to deserialize attacker-supplied `ThresholdKeys` bytes (e.g., keys read over an RPC or gossip path) forces the host to perform billions of field operations single-threaded, stalling the thread for an extended period. Per-invocation amplification is extreme: ~4 MB in → ~10⁹–10¹⁰ field ops. Repeated submissions compound the stall, matching the "resource loop / excess CPU" denial-of-service class of CVE-2019-9513. This is availability-only; no key material or forgery is obtained.

### Likelihood Explanation
Reachability is conditional on the integrator feeding untrusted bytes into `ThresholdKeys::read`, which the scan rules explicitly include as an attacker surface. The trigger requires no protocol participation, valid signature, or threshold of cooperating parties — just a crafted byte stream. Since `Participant`/`t`/`n` are u16, the worst case is bounded but still quadratically explosive within that bound. Likelihood is moderate; severity is Medium given availability-only impact.

### Recommendation
- Cap `n`/`t` at a protocol-appropriate maximum (e.g., the existing `MAX_KEY_SHARES_PER_SET` notion used elsewhere in Serai) inside `ThresholdParams::new` or at least inside `ThresholdKeys::read` before interpolation.
- Alternatively, compute `group_key` lazily or with a faster multi-point evaluation, and/or enforce an explicit size limit in `read` so deserialization cost is linear in input size.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
