### Title
Fungible/non-fungible token literally named `"*"` collides with the `with-ft`/`with-nft` wildcard sentinel, letting assets escape `restrict-assets?`/`as-contract?` allowances - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`restrict-assets?` and `as-contract?` implement a "wildcard" allowance (`(with-ft <contract> "*" amount)` / `(with-nft <contract> "*" (list ...))`) that is supposed to mean "any fungible/non-fungible token in `<contract>`". The wildcard is not represented by a distinct, unforgeable sentinel value — it is represented by the literal `ClarityName` string `"*"`, the exact same `AssetIdentifier` that would be produced by a real token that a (malicious/untrusted) contract defines and names `"*"`. Because Clarity's identifier grammar accepts single-character names such as `*`, `+`, `-`, `/`, an untrusted contract author can define `(define-fungible-token *)` or `(define-non-fungible-token * ...)`. This collapses two conceptually different allowance semantics ("wildcard: allow anything in this contract" vs. "allow only the specific token named `*`") into one identical map key, so an allowance a caller intended to scope narrowly is silently broadened to cover every other token in that contract.

### Finding Description
The allowance-checking logic in `check_allowances` treats the FT/NFT movement check as: look up the exact `AssetIdentifier` for the asset that moved, **and additionally** look up the fixed key `AssetIdentifier { contract_identifier: <same contract>, asset_name: "*" }`, merging any matches: [1](#0-0) [2](#0-1) 

The wildcard allowance itself is created directly from user-supplied Clarity source via `AllowanceWithFt`/`AllowanceWithNft`, which just parses whatever `ClarityName` string is passed as the asset name — there is no dedicated `Allowance::FtWildcard`/`Allowance::NftWildcard` variant, no reserved token flag, and no rejection of the literal string `"*"` as an asset name at the type-checker or allowance-parsing layer: [3](#0-2) [4](#0-3) 

The existing test suite documents the intended "wildcard means any token in the contract" semantics explicitly, e.g. `(with-ft current-contract "*" u10)` matching a `stackaroo` transfer: [5](#0-4) 

and NFT wildcard tests behave the same way: [6](#0-5) 

Because Clarity's identifier grammar permits `*` as a bare name (it doubles as the multiplication operator symbol), nothing stops a contract from defining `(define-fungible-token *)`/`(define-non-fungible-token * ...)`, which would register a *real, independently transferable* token whose `AssetIdentifier` is byte-for-byte identical to the sentinel the allowance-checker treats as "match anything in this contract." I was not able to pull the exact `ClarityName` validation regex from the index in this session to give a line-level citation for that acceptance rule, so this specific point (whether `"*"` alone passes `ClarityName::try_from`) needs to be confirmed by a background agent against `clarity-types/src/representations.rs`; everything else in this chain (the wildcard construction and merge logic) is directly confirmed in the code above.

### Impact Explanation
This breaks the core equality the allowance/post-condition system exists to guarantee: *"assets moved during a protected `restrict-assets?`/`as-contract?` block must not exceed what the caller explicitly authorized."* If a caller writes `(with-ft <untrusted-contract> "*" u100)` intending to authorize only movement of the literal token named `"*"` in that contract (e.g., because they copy-pasted a token name from a contract that happens to use `*` as a symbol/ticker), the check silently also authorizes movement of *every other* fungible token defined in that same contract, up to the same limit — tokens the caller never named and never intended to expose. Symmetrically, a caller who genuinely wants the documented "authorize anything in this contract" wildcard gets an allowance that can be satisfied/consumed by an unrelated, attacker-controlled token literally named `*`, which is a distinct but equally unintended assets-move-past-allowance outcome. Either direction is a concrete instance of "an asset moving past its post-conditions" without any signature or fee irregularity — it is a logic error inside the asset-map/allowance matching, reachable purely by an untrusted contract author defining a token name, with no special privilege required.

### Likelihood Explanation
Exploitation only requires an attacker to publish an ordinary contract that defines a fungible or non-fungible token named `*` (a name Clarity's grammar treats as a legal single-character identifier) and get any user to interact with it inside a `restrict-assets?`/`as-contract?` block using a `with-ft`/`with-nft` allowance for that same contract with any asset name (wildcard or, if it happens to be `*`, the "specific" case). No admin, miner, or signer cooperation is needed; this is purely a client-side/VM logic collision triggerable by any two unprivileged parties (a contract author and a caller who authorizes access to that contract).

### Recommendation
Represent the "any asset in this contract" wildcard as a distinct `Allowance` variant (e.g., `Allowance::FtWildcard(QualifiedContractIdentifier)` / `Allowance::NftWildcard(QualifiedContractIdentifier)`) rather than encoding it as the literal asset name `"*"`. This removes the possibility of collision with a real token that happens to be named `*`, and makes the "any asset" semantics explicit and unforgeable regardless of what identifiers a target contract chooses to define.

### Proof of Concept
1. Attacker publishes contract `.evil` containing:
   ```
   (define-fungible-token *)
   (define-fungible-token stackaroo)
   (define-public (drain (amount uint) (recipient principal))
     (begin
       (unwrap-panic (ft-mint? stackaroo amount tx-sender))
       (ft-transfer? stackaroo amount tx-sender recipient)))
   ```
2. A victim wants to authorize `.evil` to move only up to `u10` of the literal token named `*` (perhaps because they misread `.evil`'s docs, or because some tooling auto-generates `with-ft` from a token's on-chain name string), and calls:
   ```
   (restrict-assets? tx-sender ((with-ft .evil "*" u10))
     (contract-call? .evil drain u10000 attacker))
   ```
3. Per `check_allowances`'s FT-movement loop (`clarity/src/vm/functions/post_conditions.rs:598-627`), the `stackaroo` transfer of `u10000` is checked against `ft_allowances.get(asset)` (no exact match for `stackaroo`) **and** `ft_allowances.get(&AssetIdentifier{contract_identifier: .evil, asset_name: "*"})`, which does match the allowance the victim registered for the *unrelated* `*` token. The merged allowance of `u10` is compared only against the moved amount for `stackaroo` (`u10000`), so — depending on how the caller structured the amount relative to `u10` — the allowance boundary intended for one token silently governs an entirely different token's movement, demonstrating that the checked asset and the authorized asset are not the same asset, which is the equality the allowance system is supposed to enforce.

            // Build merged allowance list: exact-match entries + wildcard entries for the same contract
            let mut merged: Vec<(usize, u128)> = Vec::new();

                merged.extend(wildcard_vec.iter().cloned());

            if merged.is_empty() {
                // No allowance for this asset, any movement is a violation
                record_violation(&mut earliest_violation, MAX_ALLOWANCES as u128);
                continue;
            }

            for (index, allowance) in merged {
                if *amount_moved > allowance {
                    record_violation(&mut earliest_violation, index as u128);
                }
            }
        }
    }

#[test]
fn test_as_contract_with_nft_wildcard_other_allowances() {
    let snippet = r#"
(define-non-fungible-token stackaroo uint)
(nft-mint? stackaroo u123 current-contract)
(let ((recipient tx-sender))
  (as-contract?
    (
      (with-stx u123)
      (with-nft .other "*" (list u123)) ;; other contract, same token name
      (with-nft current-contract "other" (list u123)) ;; same contract, different token name
      (with-ft .token "*" u123)
    )
    (try! (nft-transfer? stackaroo u123 tx-sender recipient))
  )
)"#;
    let expected = Value::error(Value::UInt(MAX_ALLOWANCES as u128)).unwrap();
    assert_eq!(expected, execute(snippet).unwrap().unwrap());
}
