### Title

`SignableTransaction::new` omits `OP_RETURN` outputs from fee and weight accounting - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary

Medium-severity availability vulnerability: when the caller supplies `data`, `SignableTransaction::new` adds an `OP_RETURN` output to the real transaction but calculates `needed_fee`, change, minimum-relay eligibility, and maximum-standard-weight checks using a template transaction that excludes that output. An untrusted data payload can therefore cause construction of a transaction paying less than both the requested fee rate and Bitcoin's minimum relay fee.

### Finding Description

`SignableTransaction::new` appends the `OP_RETURN` output to `tx_outs` before calculating the transaction's weight, but `calculate_weight_vbytes` only receives `tx_ins.len()`, `payments`, and the optional change script. It has no `data` parameter and does not model the `OP_RETURN` output. Both fee calculations consequently omit the data output's serialized size. [1](#0-0) [2](#0-1) 

The minimum-relay and sufficiency checks use that underestimated fee at `send.rs:211` and `send.rs:215`. If change is supplied, the change amount is also calculated from the underestimated `fee_with_change` at `send.rs:225-230`. [3](#0-2) 

An 80-byte payload is permitted at `send.rs:171-173`, but its output contributes roughly 90 additional serialized bytes or vbytes. Because those bytes are absent from the template, the transaction can pass all checks while paying a fee approximately 90 satoshis below the amount required for the requested rate. [4](#0-3) [5](#0-4) 

### Impact Explanation

A publicly supplied `data` argument can produce a signed Bitcoin transaction whose actual fee rate is lower than requested and potentially below the default minimum relay rate. Nodes may reject or fail to propagate it, leaving the selected inputs committed to a transaction that is not readily spendable or confirmable under the intended fee policy. This is a concrete accounting error over transaction bytes controlled by an unprivileged caller, not a merely theoretical fee estimation discrepancy. [6](#0-5) [7](#0-6) 

### Likelihood Explanation

The issue is deterministic whenever `data` is present. The API accepts up to 80 bytes, and normal `OP_RETURN` output serialization adds its script and amount fields to the actual transaction. With a low fee rate such as the default minimum of one satoshi per vbyte, the omitted output alone can reduce the effective rate below relay policy. A change output makes the discrepancy explicit because its value is calculated from the underestimated fee rather than the fee required by the final transaction. [4](#0-3) [5](#0-4) 

### Recommendation

Pass the serialized `OP_RETURN` script or data size into `calculate_weight_vbytes`, and include a zero-value `TxOut` for it in the template transaction for both the no-change and with-change calculations. Alternatively, calculate weight directly from the exact `tx_outs` being constructed so future output types cannot be omitted. Add a regression test asserting `needed_fee() == transaction().vsize() * fee_per_vbyte` when `data` and `change` are both present. [8](#0-7) [9](#0-8) 

### Proof of Concept

1. Construct one spendable `ReceivedOutput`.
2. Call `SignableTransaction::new` with:
   - one ordinary payment,
   - `change: Some(change_script)`,
   - `data: Some(vec![0; 80])`,
   - `fee_per_vbyte: 1`.
3. Observe that `tx_outs` contains the `OP_RETURN` output, while both calls to `calculate_weight_vbytes` only reconstruct `payments` and `change`.
4. Compare the resulting `needed_fee()` with `transaction().vsize() * fee_per_vbyte`; the former is lower by the `OP_RETURN` output's serialized vsize.
5. The minimum-fee check still passes because it also uses the underestimated vsize, allowing construction of a transaction below the intended and default relay fee rate. [10](#0-9)

          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()

        // The script pub key is not of a fixed size and does have to be used here

          script_pubkey: payment.0.clone(),
        })
        .collect(),

      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
