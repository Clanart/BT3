This confirms there is no "preferences import" or "synced settings" feature in GitHub Desktop that would let a remote attacker inject a `bundleID` value. The setting is only persisted to local `localStorage` via `setObject(customShellKey, ...)` and is only ever set through `dispatcher.setCustomShell()` after the preferences UI derives `bundleID` from `validateCustomIntegrationPath()`/`getAppBundleID()`, which reads the actual bundle identifier of the app the *user* picked via the OS file picker [1](#0-0) [2](#0-1) . There is no code path where remote/repo/API/deep-link input feeds into `customShell.bundleID`.

**No vulnerability found for this question.**

Rationale:
- `launchCustomShell` in `app/src/lib/shells/darwin.ts` does execute `spawnCustomIntegration('open', ['-b', customShell.bundleID, ...args])` when `bundleID` is set [3](#0-2) , so if an attacker could control `bundleID`, they could indeed redirect execution to an arbitrary installed app.
- However, `bundleID` is never attacker-controllable via any of the in-scope vectors (repository content, API objects, clicked/deep links, remote/proxy responses). It is set only through the preferences UI flow: the user picks a path via `showOpenDialog` (native OS file picker, requires local interaction), and `validateCustomIntegrationPath` derives the bundle ID directly from the filesystem metadata of the chosen `.app` bundle using `mdls` [4](#0-3) . The dispatcher then persists it only after `isValidCustomIntegration` succeeds [5](#0-4) .
- The stored value lives only in the renderer's `localStorage` (`customShellKey`), loaded via `getObject<ICustomIntegration>(customShellKey)` [6](#0-5) . There is no "preferences import," cloud sync, or settings-sharing feature in the codebase that would let a remote party write to this local storage — a search for import/sync-preferences functionality found nothing.
- Tampering with `localStorage` directly (e.g., via DevTools or editing the on-disk file) requires local filesystem/process access, which is explicitly out of scope per the bounty rules ("Reject local access, admin rights...").

Since the premised attack vector (remote/attacker-controlled `bundleID` via import or sync) does not exist in this codebase, and the only legitimate path to setting `bundleID` requires deliberate local user action validated against the actual filesystem, this does not meet the in-scope criteria.

// Function to retrieve, on macOS, the bundleId of an app given its path
async function getAppBundleID(path: string) {
  try {
    // Ensure the path ends with `.app` for applications
    if (!path.endsWith('.app')) {
      throw new Error(
        'The provided path does not point to a macOS application.'
      )
    }

    // Use mdls to query the kMDItemCFBundleIdentifier attribute
    const { stdout } = await execFileAsync('mdls', [
      '-name',
      'kMDItemCFBundleIdentifier',
      '-raw',
      path,
    ])
    const bundleId = stdout.trim()

    // Check for valid output
    if (!bundleId || bundleId === '(null)') {
      return undefined
    }

    return bundleId
  } catch (error) {
    console.error('Failed to retrieve bundle ID:', error)
    return undefined
  }

export async function validateCustomIntegrationPath(
  path: string
): Promise<{ isValid: boolean; bundleID?: string }> {
  if (path.length === 0) {
    return { isValid: false }
  }

  let bundleID = undefined

  try {
    const pathStat = await lstat(path)
    const canBeExecuted = await access(path, fs.constants.X_OK)
      .then(() => true)
      .catch(() => false)

    // On Windows, `X_OK` is equivalent to `F_OK` so we additionally restrict
    // to extensions that `spawn` can launch directly. Wrappers like `.bat`
    // or `.cmd` require a shell and would silently fail at launch time.
    const hasLaunchableExtension =
      !__WIN32__ ||
      WindowsExecutableExtensions.includes(
        extname(path).replace(/^\./, '').toLowerCase()
      )

    const isExecutableFile =
      (pathStat.isFile() || pathStat.isSymbolicLink()) &&
      canBeExecuted &&
      hasLaunchableExtension

    // On macOS, not only executable files are valid, but also apps (which are
    // directories with a `.app` extension and from which we can retrieve
    // the app bundle ID)
    if (__DARWIN__ && !isExecutableFile && pathStat.isDirectory()) {
      bundleID = await getAppBundleID(path)
    }

    return { isValid: isExecutableFile || !!bundleID, bundleID }
  } catch (e) {
    if (e.code !== 'ENOENT') {
      log.error(`Failed to validate path: ${path}`, e)
    }
    return { isValid: false }
  }
}
