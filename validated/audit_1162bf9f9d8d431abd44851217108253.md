### Title
Permanent freezing of user funds via self-destruct-triggered `DeleteTokenPair` on permissionlessly-registered ERC20 token pairs - (File: `x/erc20/keeper/token_pairs.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`DeleteTokenPair` in `x/erc20/keeper/token_pairs.go` is the direct analog of `clearTokenConfig`: it wipes a `TokenPair`'s registry entries (`erc20<->denom` mappings and allowances) without verifying that no outstanding coin supply or escrowed value depends on that mapping. [1](#0-0) 

### Finding Description
`RegisterERC20` is permissionless when `params.PermissionlessRegistration` is set, letting any unprivileged account register an arbitrary external contract as a `TokenPair` with `OWNER_EXTERNAL` (`IsNativeERC20`). [2](#0-1) 

Both `ConvertERC20` and `ConvertCoin` contain an automatic cleanup branch: if the registered ERC20 contract account no longer has code (e.g., because it self-destructed), the handler calls `k.DeleteTokenPair(ctx, pair)` and returns success, without checking whether coins of `pair.Denom` are still circulating among users who already converted before the contract died. [3](#0-2) [4](#0-3) 

`DeleteTokenPair` itself only removes the erc20↔denom↔allowance mappings from the `x/erc20` store; it never inspects `bankKeeper` supply/balances for `pair.Denom`, nor does it burn or otherwise account for coins already minted against the (now-destroyed) ERC20 backing: [1](#0-0) 

Once the pair is deleted, `MintingEnabled`/`GetTokenPairID` can no longer resolve the denom or address, so any future `ConvertCoin` call by a legitimate holder fails with `ErrTokenPairNotFound`: [5](#0-4) 

Re-registration to restore the mapping is also blocked, because `CreateCoinMetadata` checks whether the bank module already has denom metadata for `types.CreateDenom(contract)` — and `DeleteTokenPair` never removes that bank metadata, only the erc20-module maps: [6](#0-5) 

The net effect: any holder of the wrapped native coin denom, at the moment the underlying contract is destroyed and the pair auto-deleted, is left holding a coin denom that can never again be converted back to (or reconciled against) an ERC20 asset — a permanent, unauthorized freeze of that balance, triggerable entirely by unprivileged actions (permissionless registration + self-destruct + any follow-up convert call).

### Impact Explanation
This falls under "Critical permanent freezing/locking of user funds ... token-pair-backed balances." Users who legitimately converted ERC20 tokens into the native coin representation (via `ConvertERC20`) have real, spendable bank balances. A malicious contract deployer can register a self-destructible ERC20, let other users convert into the coin representation, then self-destruct the contract, after which the very first subsequent `ConvertERC20`/`ConvertCoin` call (by anyone, even the attacker themselves) permanently deletes the token pair mapping — with no way for existing holders to redeem, and no re-registration path since the bank-level metadata blocks recreating the pair.

### Likelihood Explanation
Moderate-to-high likelihood: it requires only (1) `PermissionlessRegistration` enabled (a governance-configurable but plausible/default-style parameter for these forks), (2) the ability to deploy an ordinary self-destructible Solidity contract, and (3) at least one other party trusting the token pair enough to convert into the wrapped coin before the attacker self-destructs. No privileged role, relayer, or validator collusion is required — the entire sequence is executable by ordinary transactions.

### Recommendation
Before auto-deleting a token pair in the selfdestruct-cleanup branches of `ConvertERC20`/`ConvertCoin`, and in `DeleteTokenPair` generally, check the current bank supply of `pair.Denom` (and any escrowed balances in the module account). If supply is nonzero, refuse the automatic deletion (or first burn/settle outstanding balances via governance-supervised reconciliation, and/or provide a redemption/grace window) instead of silently orphaning the mapping. Also ensure `DeleteTokenPair` clears the corresponding bank denom metadata if reuse of that denom is intended, or explicitly document/enforce that the denom can never be reused, and gate that decision on there being zero outstanding supply.

### Proof of Concept
1. With `PermissionlessRegistration=true`, attacker deploys `EvilERC20`, a standard mintable/burnable ERC20 with a public `kill()` function calling `selfdestruct`.
2. Attacker calls `MsgRegisterERC20` for `EvilERC20` → `registerERC20` creates a `TokenPair{OWNER_EXTERNAL}` and bank denom metadata for `erc20:<addr>`. [7](#0-6) 
3. Victim calls `MsgConvertERC20` to convert 1000 `EvilERC20` into the native coin `erc20:<addr>`; module escrows the ERC20 tokens and mints 1000 native coins to victim.
4. Attacker calls `kill()` on `EvilERC20`, destroying the contract (and its storage, including the module's escrowed balance).
5. Any account calls `MsgConvertERC20` or `MsgConvertCoin` referencing the contract address; `acc.HasCodeHash()` is false, so `k.DeleteTokenPair(ctx, pair)` fires and returns success with no error. [3](#0-2) 
6. Victim still holds 1000 `erc20:<addr>` native coins in their bank balance, but `MsgConvertCoin`/`MsgConvertERC20` for that denom now fail permanently with `ErrTokenPairNotFound`, and re-registration is blocked by existing bank metadata — the victim's funds are permanently unredeemable.

Note: I could not fully verify from the index whether any additional governance-only path exists to manually re-map a denom after such a deletion (e.g., a migration/`SetToken` governance message) that might mitigate the permanence of the freeze; this should be confirmed against the full `x/erc20` msg surface in a live environment.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
