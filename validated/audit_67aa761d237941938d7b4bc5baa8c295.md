### Title
Persistent `NewKickoff` event failure permanently halts `MessageConsumerTask`, blocking all subsequent bridge state updates — (File: `core/src/states/task.rs`, `core/src/states/event.rs`)

---

### Summary

The `MessageConsumerTask` consumes `SystemEvent`s from a PGMQ queue in strict `msg_id ASC` order. If `handle_event()` returns a persistent error — concretely, the "Conflicting kickoff detected" error that arises when a reorged kickoff is re-dispatched with mismatched fields — the failing message is **never archived** from the queue. The `recover_from_error` handler only reloads state from the database, which does not resolve the underlying conflict. After 10 consecutive failures the `BufferedErrors` wrapper permanently aborts the task thread. Because the task is not automatically restarted, every subsequent `NewFinalizedBlock`, `NewKickoff`, and `LCPProcessed` event is silently dropped, freezing all operator-round and kickoff state machines and disabling watchtower-challenge and operator-assert automation.

---

### Finding Description

**Queue ordering and archival contract**

`MessageConsumerTask::run_once()` reads exactly one message at a time with visibility-timeout 0 (single-consumer mode) and only archives it on success:

```rust
// core/src/states/task.rs  lines 120-150
let Some(Message { msg_id, message, .. }) = self.inner.queue
    .read_with_cxn(&self.queue_name, 0, &mut *dbtx)   // vt = 0
    .await ...
else { ... return Ok(false); };

self.inner.handle_event(message, arc_dbtx.clone()).await?;   // ← error propagates

self.inner.queue
    .archive_with_cxn(&self.queue_name, msg_id, &mut *dbtx)  // ← only reached on success
    .await ...;
dbtx.commit().await?;
```

If `handle_event()` returns `Err`, the `?` operator propagates it before `archive_with_cxn` is called. The message stays at the head of the queue. [1](#0-0) 

**The persistent error: conflicting kickoff after a reorg**

`handle_event()` for `SystemEvent::NewKickoff` checks for duplicate kickoff data. When the same `kickoff_data` key is already tracked but with different `deposit_data`, `payout_blockhash`, or `kickoff_height` — a scenario the code itself documents as arising from a reorged kickoff being added too early — it returns a hard error:

```rust
// core/src/states/event.rs  lines 218-223
return Err(eyre::eyre!(
    "Conflicting kickoff({:?}) detected: same kickoff_data, mismatches: {}",
    kickoff_data,
    mismatches.join("; "),
).into());
``` [2](#0-1) 

**Why recovery cannot fix it**

`RecoverableTask::recover_from_error` calls `reload_state_manager_from_db()`, which restores the in-memory state from the database — including the original kickoff machine that caused the conflict. The conflicting `NewKickoff` message is still at the head of the queue. On the very next iteration the same check fires again, producing the same error. [3](#0-2) 

**`BufferedErrors` overflow → permanent task death**

The `StateManager` is wrapped with `into_buffered_errors(10, 3, Duration::from_secs(10))`. After 10 consecutive failures (each preceded by up to 3 recovery attempts) the wrapper returns a terminal `Err`, which kills the task thread:

```rust
// core/src/task/mod.rs  lines 268-281
if self.buffer.len() >= self.error_overflow_limit {
    ...
    Err(base_error.into())   // task thread exits
}
``` [4](#0-3) 

The `BackgroundTaskManager` logs the failure and marks the task `NotRunning` but does **not** restart it:

```rust
// core/src/task/manager.rs  lines 58-62
Ok(Err(e)) => {
    tracing::error!("Task {task_variant:?} failed with error: {e:?}");
    format!("Failed due to error: {e:?}")
}
``` [5](#0-4) 

**All subsequent events are blocked**

Because PGMQ delivers messages in strict `msg_id ASC` order and the conflicting message is never archived, every `NewFinalizedBlock`, `NewKickoff`, and `LCPProcessed` event enqueued after it is permanently stuck behind it. Once the task thread exits, none of those events are ever consumed. [6](#0-5) 

---

### Impact Explanation

With the `StateManager` task permanently dead:

- **Round state machines** stop advancing: the operator's collateral-chain position is frozen. Reimbursement outputs and round-tx transitions are never triggered.
- **Kickoff state machines** stop advancing: watchtower-challenge matchers, operator-assert duties, and disprove duties are never dispatched.
- **`LCPProcessed` events** are never consumed: `check_if_kickoff_malicious` is never called, so a malicious operator's kickoff is never challenged even after the light-client proof is available.

A malicious operator who times a kickoff around a reorg can therefore front-run the DoS: once the state manager is frozen, no verifier will ever call `disprove`, and the operator can drain the collateral UTXO unchallenged. This is a permanent loss of bridged BTC and operator collateral.

---

### Likelihood Explanation

Bitcoin reorgs of 1–2 blocks are routine. The code comment at line 190 of `event.rs` explicitly acknowledges the reorg scenario as the motivating case for the conflicting-kickoff check. No malicious actor is required: a natural reorg that causes a kickoff transaction to be re-finalized at a different block height (changing `kickoff_height`) or with a different payout witness is sufficient to enqueue a conflicting `NewKickoff` event. The 10-failure threshold is reached within seconds of the reorg being processed. [7](#0-6) 

---

### Recommendation

1. **Archive the message on unrecoverable errors.** Distinguish transient errors (DB connectivity, RPC timeouts) from permanent logical errors (conflicting kickoff, out-of-order block). For permanent errors, archive the message and emit a high-severity alert rather than retrying indefinitely.

2. **Handle conflicting kickoffs gracefully.** On a reorg the correct behaviour is to replace the stale kickoff machine with the new data, not to error. The existing duplicate-detection path should update the stored machine when `kickoff_data` matches but associated fields differ, mirroring how the code already handles exact duplicates (`return Ok(())`).

3. **Implement task auto-restart.** The `BackgroundTaskManager` should restart critical tasks (at minimum `StateManager` and `FinalizedBlockFetcher`) after a configurable back-off, so a transient burst of errors does not permanently halt bridge automation.

---

### Proof of Concept

1. Operator broadcasts a kickoff transaction at Bitcoin block height *H*; the `BitcoinSyncer` finalizes it and `dispatch_new_kickoff_machine` enqueues `NewKickoff { kickoff_height: H, payout_blockhash: W1, ... }`.
2. A 1-block reorg occurs; the kickoff is re-mined at height *H* but with a different payout witness `W2` (operator re-broadcasts with a different WOTS commitment). `dispatch_new_kickoff_machine` enqueues a second `NewKickoff { kickoff_height: H, payout_blockhash: W2, ... }` with the same `kickoff_data`.
3. `MessageConsumerTask` processes the second event. `handle_event` finds the existing kickoff machine with `payout_blockhash = W1 ≠ W2`, hits the mismatch branch, and returns `Err("Conflicting kickoff detected")`.
4. The message is not archived. `recover_from_error` reloads state from DB — the machine with `W1` is still there.
5. Steps 3–4 repeat 10 times (≈ 30 seconds with the 10-second recovery wait).
6. `BufferedErrors` returns a terminal error; the task thread exits.
7. All subsequent `NewFinalizedBlock` events accumulate in the queue but are never consumed. Watchtower-challenge and operator-assert duties are never dispatched. The operator's kickoff proceeds to payout unchallenged.
